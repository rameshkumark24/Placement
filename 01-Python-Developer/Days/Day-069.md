# Day 069

**L-069** · `concurrent.futures` — the executor abstraction that unifies threads and processes

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `ThreadPoolExecutor` and `ProcessPoolExecutor` have the same API, so
> switching between "concurrency for waiting" and "parallelism for computing" is a one-line change —
> which means you can *measure* the choice instead of arguing about it.**
>
> ⭐ This is the API you should reach for in real code. `threading.Thread` and `multiprocessing.Pool`
> are the layers underneath (Days 066, 068); this is the one with sane defaults, real error handling,
> and a `Future`.

---

# Part 1 — ⭐⭐ One API, two backends

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=20) as ex:        # ⭐⭐ change ONE word to switch
    results = list(ex.map(fetch, urls))

with ProcessPoolExecutor() as ex:                     # ⭐ same call, real cores
    results = list(ex.map(heavy, items))
```

```
⭐⭐ THE DEFAULTS, AND THEY ARE CHOSEN WELL:
⭐   ThreadPoolExecutor()   ⇒ min(32, os.cpu_count() + 4)
⭐        ⇒ ⭐ the +4 is for I/O overlap; the cap of 32 stops you creating hundreds by accident
⭐   ProcessPoolExecutor()  ⇒ os.cpu_count()
⭐        ⇒ ⭐⭐ ⚠️ in a container that is the HOST's core count (Day 064) — set it explicitly
```

| ⭐ Method | ⭐ Behaviour |
|---|---|
| ⭐ `submit(fn, *a)` | schedule one call ⇒ returns a **`Future`** immediately |
| ⭐ `map(fn, iterable)` | ⭐⭐ lazy, **ordered**, re-raises on iteration |
| ⭐⭐ `as_completed(futures)` | ⭐⭐ yields futures **as they finish** — any order |
| `wait(futures, ...)` | block until first/all complete |
| `shutdown(wait, cancel_futures)` | ⭐ the `with` block calls this for you |

```python
# ⭐⭐ THE PATTERN YOU WILL USE MOST — submit, then handle as they land:
with ThreadPoolExecutor(max_workers=10) as ex:
    futures = {ex.submit(fetch, url): url for url in urls}   # ⭐ map future ⇒ its input
    for fut in as_completed(futures, timeout=60):
        url = futures[fut]
        try:
            data = fut.result()          # ⭐⭐ re-raises whatever the worker raised
        except Exception:
            logger.exception("failed: %s", url)   # ⭐ Day 060
```

⭐⭐ **Keeping a `{future: input}` dict is the small habit that makes failures diagnosable** — a bare
future tells you nothing about which call it was.

# Part 2 — ⭐⭐ `Future`, and the exception trap

```python
fut = ex.submit(work, x)
fut.done()                 # ⭐ has it finished
fut.result()               # ⭐⭐ BLOCKS until done, then returns — or RE-RAISES
fut.result(timeout=5)      # ⭐ raises TimeoutError instead of waiting forever
fut.exception()            # ⭐ the exception, or None — does not raise it
fut.cancel()               # ⭐⭐ only works if it has NOT STARTED. Returns False otherwise.
fut.add_done_callback(fn)  # ⭐ called in the worker thread — keep it trivial
```

```
⭐⭐ THE TRAP THAT LOSES ERRORS SILENTLY:
⭐   an exception in a worker is CAPTURED IN THE FUTURE, not raised where you submitted.
⭐   ⇒ ⭐⭐ if you never call .result() or .exception(), the failure is INVISIBLE.
⭐        No traceback. No log. The task simply did not happen.
```

```python
# ⚠️⚠️ ⭐⭐ FIRE-AND-FORGET — every one of these silently swallowed:
for item in items:
    ex.submit(process, item)          # ⭐⭐ no future kept ⇒ no error ever surfaces

# ⭐ CORRECT — collect them and check:
futures = [ex.submit(process, i) for i in items]
for f in as_completed(futures):
    f.result()                        # ⭐⭐ re-raises, so failures are loud
```

⭐⭐ **This is Day 060's "silent failure" in a new costume**, and it is extremely common: a batch job
reports success, half the items were never processed, and there is nothing in the log because nobody
ever asked the future what happened.

⚠️ ⭐ **`ex.map` behaves differently and better:** it re-raises the first exception **when you iterate
to it** — but note that it stops there, so later results are lost, and **the ordering means a slow
first item blocks everything behind it.** `as_completed` avoids both.

⚠️ ⭐⭐ **`cancel()` cannot stop a running task** — same limitation as Day 066: you cannot kill a
thread. It only removes a task from the queue. **`shutdown(wait=False, cancel_futures=True)` (3.9+)
drops everything queued but still waits for what is running.**

# Part 3 — ⭐ Picking the executor, by measuring

```python
# ⭐⭐ THE THREE-LINE EXPERIMENT — run this rather than reasoning about it:
for Ex in (ThreadPoolExecutor, ProcessPoolExecutor):
    t0 = time.perf_counter()
    with Ex() as ex: list(ex.map(work, items))
    print(Ex.__name__, time.perf_counter() - t0)
```

| ⭐ Workload | ⭐⭐ Executor | ⭐ Why |
|---|---|---|
| ⭐ HTTP, DB, files, subprocess | ⭐⭐ **Thread** | the GIL is released while waiting (Day 065) |
| ⭐ Pure Python computation | ⭐⭐ **Process** | the GIL blocks threads (Day 065) |
| NumPy / hashlib / compression | ⭐ **Thread** | ⭐⭐ those release the GIL in C — no pickling cost |
| Large data per task | ⭐ **Thread**, or send paths | pickling dominates (Day 068) |
| Thousands of concurrent waits | ⭐⭐ **neither — `asyncio`** | Day 070 |

⭐⭐ **The NumPy row is the one people miss:** for array work a **thread** pool is usually better than
a process pool, because the GIL is released anyway *and* you skip the serialisation entirely.

```python
# ⭐⭐ initializer — per-worker setup, run ONCE per worker rather than per task:
def init_worker():
    global conn
    conn = psycopg.connect(DSN)        # ⭐ one connection per worker, not one per item

with ThreadPoolExecutor(max_workers=8, initializer=init_worker) as ex: ...
```

⭐ **`initializer` is how you give each worker a database connection, a loaded model or a compiled
regex** — ⚠️ **and note it must not be a lambda for a process pool** (Day 068: pickling).

# Part 4 — ⭐ The failure modes

```
⭐⭐ 1. UNBOUNDED SUBMISSION. `for x in ten_million: ex.submit(f, x)` queues ten million
⭐      Future objects and their arguments in memory before any complete.
⭐      ⇒ ⭐ the pool bounds CONCURRENCY, never the QUEUE.
⭐      ⇒ ⭐⭐ FIX: submit in batches and drain, or use ex.map (lazy), or a bounded Queue.

⭐⭐ 2. NESTED POOLS ⇒ DEADLOCK. A worker that submits to the same pool and waits for the
⭐      result can consume every worker with tasks that are all waiting on tasks that
⭐      cannot be scheduled. ⇒ ⭐ never block on a future from inside a worker of that pool.

⭐⭐ 3. A BLOCKING CALL WITH NO TIMEOUT inside a worker holds that worker forever (Day 060).
⭐      ⇒ every network call in a worker gets a timeout. Every one.

⭐ 4. ⭐⭐ ProcessPoolExecutor + a worker that SEGFAULTS or is OOM-killed
⭐      ⇒ BrokenProcessPool, and the whole pool becomes unusable — ⭐ you must recreate it.

⭐ 5. Forgetting the context manager ⇒ ⭐ the interpreter waits for non-daemon threads
⭐      at exit, so the program hangs instead of finishing.
```

```python
# ⭐ Bounded submission — the shape that does not blow up on a large input:
from itertools import islice
with ThreadPoolExecutor(max_workers=20) as ex:
    it = iter(items)
    futures = {ex.submit(work, x) for x in islice(it, 100)}     # ⭐ prime with 100
    while futures:
        done, futures = wait(futures, return_when=FIRST_COMPLETED)
        for f in done:
            f.result()
            for x in islice(it, 1):                              # ⭐⭐ top up as they finish
                futures.add(ex.submit(work, x))
```

⭐ **The bridge to asyncio** (Day 072 uses it constantly): an executor is how async code escapes the
event loop for something blocking.

```python
await asyncio.to_thread(blocking_fn, arg)                 # ⭐⭐ 3.9+ — the simple form
await loop.run_in_executor(process_pool, cpu_heavy, arg)  # ⭐ for CPU work
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Submitting without keeping the future** | ⭐⭐ Exceptions vanish silently. |
| Never calling `.result()` | ⭐ The error is captured, not raised. |
| Expecting `cancel()` to stop a running task | ⭐⭐ It only removes queued ones. |
| Submitting millions of tasks at once | ⭐ The pool bounds concurrency, not the queue. |
| ⭐ Blocking on a future inside a worker | ⭐⭐ Deadlocks the pool. |
| No timeout on a worker's network call | ⭐ That worker is gone. |
| ⭐ `ProcessPoolExecutor` for I/O | ⭐ Pickling and startup for no benefit. |
| Process pool for NumPy | ⭐⭐ Threads — the GIL is released and there is no pickling. |
| `os.cpu_count()` default in a container | ⭐ Host cores (Day 064). Set it. |
| A lambda as a process-pool `initializer` | ⭐ Not picklable (Day 068). |
| No context manager | ⭐ The program hangs at exit. |
| Ignoring `BrokenProcessPool` | ⭐ The pool is dead; recreate it. |

## Interview questions

**Q: Why use `concurrent.futures` rather than `threading` or `multiprocessing` directly?**
> Because it's one API over both, so choosing between concurrency-for-waiting and
> parallelism-for-computing is a one-word change — which means I can measure the decision instead of
> arguing about it. It also gives me sane defaults, a `Future` with real error propagation, and
> `as_completed` so I can handle results as they land rather than in submission order. The lower-level
> modules are what it's built on; I reach for them when I need a specific primitive.

**Q: What happens to an exception raised inside a worker?**
> It's captured in the `Future`, not raised where you submitted. So it only surfaces when you call
> `.result()` or `.exception()` — and if you submitted fire-and-forget without keeping the future,
> the failure is completely invisible: no traceback, no log, the task simply didn't happen. That's the
> single most common bug with executors, and it presents as a batch job reporting success while half
> the items were never processed. Collect the futures and call `.result()` on each, even if you don't
> need the value.

**Q: `map` or `as_completed`?**
> `map` when I want results in input order and the work is uniform — it's lazy and it re-raises on
> iteration. `as_completed` when durations vary, because `map`'s ordering means one slow first item
> blocks every result behind it, and because `map` stops at the first exception so later results are
> lost. With `as_completed` I can process each as it finishes and handle failures individually, and
> keeping a `{future: input}` dict tells me *which* call failed, which a bare future never does.

**Q: Can you cancel a running task?**
> No. `cancel()` only removes a task that hasn't started — same limitation as threads generally, since
> Python can't kill a thread. `shutdown(cancel_futures=True)` drops the queue but still waits for
> what's running. So anything long-running has to cooperate: check a flag, and put timeouts on every
> blocking call, or shutdown hangs.

**Q: How would you process ten million items with a pool?**
> Not by submitting ten million futures — the pool bounds concurrency, not the queue, so that
> materialises ten million `Future` objects and their arguments before anything completes. Either
> `ex.map`, which is lazy, or a sliding window: prime with a few hundred, then use `wait` with
> `FIRST_COMPLETED` and top up as each finishes. That keeps memory bounded and the pool saturated.

**Q: NumPy work across eight cores — threads or processes?**
> Threads, usually — which surprises people. NumPy releases the GIL for large array operations, so
> threads get real parallelism, and you avoid pickling the arrays entirely. A process pool would
> serialise every array in and out, which for large data can cost more than the computation. It's the
> exception to "threads give no parallelism", and it's worth checking whether the library releases the
> GIL before reaching for processes.

## 🎙️ Articulation drill

Record two minutes: **"Fetch 500 URLs and write the results to a database."**

⭐ Start by classifying: **I/O-bound, so a thread pool** — the GIL is released during the socket wait,
and processes would add pickling and startup for no benefit. ⭐ Bound the concurrency deliberately —
**`max_workers=20`, not 500** — because the limit that matters is the *target's* tolerance and your
file-descriptor budget, not your core count.

⭐ Then the shape: **`submit` into a `{future: url}` dict and consume with `as_completed`**, so slow
URLs do not block fast ones and every failure names its URL. **Every request gets a timeout**, or a
hung server holds a worker forever (Day 060).

⭐⭐ **Then the failure mode I would call out unprompted:** *"the mistake I'd watch for is
fire-and-forget submission. An exception in a worker is captured in the future rather than raised, so
if nobody calls `.result()` it vanishes — no traceback, no log — and the job reports success while a
hundred URLs were never fetched. I collect every future and call `.result()` even when I don't need
the value, precisely so failures are loud."*
