**Time:** 3 hrs · **Mode:** MOCK + SCORED

> ⭐⭐ **The sentence to own: five minutes of arithmetic tells you this is a read-heavy, tiny-payload,

# Part 2 — ⭐⭐ The estimation, done properly

```
⭐ ***ASK FOR ONE NUMBER, DERIVE THE REST. ⭐⭐ NEVER ASK FOR
⭐   FIVE — DERIVING IS THE SKILL BEING TESTED.***

⭐ ***GIVEN:*** ⭐ 100 million new URLs per day.

⭐ ***WRITES:*** ⭐ 100M / 86,400 ≈ ⭐⭐ 1,160 WRITES/SEC.
⭐   ⭐ Peak at 3× ⇒ ~3,500/sec. ⭐⭐ ORDINARY. ⭐ One Postgres
⭐     handles this.

⭐ ***READS:*** ⭐ ⭐⭐ ASK FOR THE RATIO — ⭐ it is the single most
⭐   important number and interviewers expect you to want it.
⭐   ⭐ At 100:1 ⇒ ⭐⭐ 116,000 READS/SEC, ⭐ peak ~350,000.
⭐   ⭐ ⭐⭐ ***THAT*** IS THE SYSTEM. ⭐ Writes are a rounding
⭐     error; ⭐⭐ THE WHOLE DESIGN IS A READ PATH.

⭐ ***STORAGE:*** ⭐ per row ≈ short code 7B + long URL ~200B +
⭐   metadata ~100B ≈ ⭐ 300 bytes.
⭐   ⭐ 100M/day × 365 × 5 years = ⭐⭐ 182 BILLION ROWS × 300B ≈
⭐     55 TB.
⭐   ⭐ ⭐⭐ AND HERE IS THE SENIOR MOVE — ***QUESTION THE
⭐     REQUIREMENT***: ⭐ "182 billion rows is a lot for a URL
⭐     shortener. ⭐⭐ DO LINKS EXPIRE? ⭐ If they expire after two
⭐     years, this is 20 TB and a completely different
⭐     conversation. ⭐⭐ IF THEY REALLY ARE PERMANENT, I NEED
⭐     SHARDING FROM DAY ONE AND I'D WANT TO SAY THAT NOW RATHER
⭐     THAN AT MINUTE FORTY."

⭐ ***KEY SPACE:*** ⭐ base62 (a–z, A–Z, 0–9).
⭐   ⭐ 62⁶ = 56 billion · ⭐⭐ 62⁷ = 3.5 TRILLION.
⭐   ⭐ ⇒ ⭐⭐ 7 CHARACTERS IS ENOUGH FOR 182 BILLION URLS ⭐ with
⭐     room to spare. ⭐ Say the arithmetic, not the answer.

⭐ ***CACHE:*** ⭐ Pareto — 20% of links serve ~80% of traffic.
⭐   ⭐ Hot set ≈ 20M links × 300B ≈ ⭐⭐ 6 GB. ⭐ Fits in memory
⭐     comfortably.
⭐   ⭐ ⭐⭐ ⇒ AT AN 80% HIT RATE THE DATABASE SEES ~23,000
⭐     READS/SEC INSTEAD OF 116,000. ⭐ That single line is why
⭐     the estimation mattered.
```

# Part 3 — ⭐⭐ ID generation is the interesting part

```
⭐ ***THREE APPROACHES. THE COMPARISON ***IS*** THE ROUND.***

⭐ ① ⭐⭐ ***HASH THE URL*** (MD5/SHA, take 7 chars).
⭐   ⭐ ✅ stateless, ⭐ same URL → same code (free dedup).
⭐   ⭐ ❌ ⭐⭐ COLLISIONS ARE CERTAIN AT THIS SCALE ⭐ (birthday
⭐     bound on 3.5T with 182B inserts), ⭐ so you need a
⭐     read-before-write to check — ⭐⭐ WHICH REINTRODUCES
⭐     CHECK-THEN-ACT AND A DATABASE ROUND TRIP ON THE WRITE
⭐     PATH.

⭐ ② ⭐⭐ ***COUNTER + BASE62.***
⭐   ⭐ ✅ no collisions ***by construction***, shortest codes.
⭐   ⭐ ❌ ⭐⭐ A GLOBAL COUNTER IS A SINGLE POINT OF CONTENTION.
⭐   ⭐ ❌ ⭐⭐ ***AND THE REAL PROBLEM: SEQUENTIAL CODES ARE
⭐     ENUMERABLE.*** ⭐ If mine is `dGx4`, the next is `dGx5` —
⭐     ⭐⭐ SO ANYONE CAN WALK EVERY URL IN THE SYSTEM, INCLUDING
⭐     PRIVATE ONES. ⭐ That is a data-leak surface, not an
⭐     aesthetic complaint.
⭐   ⭐ ⇒ ⭐⭐ FIX: ***PERMUTE THE COUNTER*** BEFORE ENCODING —
⭐     ⭐ a Feistel network or multiply-by-a-coprime modulo 62⁷.
⭐     ⭐⭐ BIJECTIVE, SO NO COLLISIONS, AND THE OUTPUT LOOKS
⭐     RANDOM.
⭐   ⭐ ⇒ contention fix: ⭐⭐ ***RANGE ALLOCATION*** — ⭐ each
⭐     server claims 10,000 ids at a time. ⭐ One round trip per
⭐     10,000 writes; ⭐⭐ GAPS ON RESTART ARE HARMLESS.

⭐ ③ ⭐⭐ ***PRE-GENERATED KEYS.*** ⭐ A key-generation service
⭐   fills a table of unused random codes offline; ⭐ writers pop
⭐   one.
⭐   ⭐ ✅ ⭐⭐ NO COLLISIONS, NO ENUMERATION, NO WRITE-PATH
⭐     COMPUTATION.
⭐   ⭐ ❌ another service to run, and ⭐ a table to keep filled.

⭐ ⭐⭐ THE ANSWER THAT SCORES: ⭐ "② with a permutation and range
⭐   allocation. ⭐⭐ IT GIVES ME COLLISION-FREENESS FROM THE
⭐   COUNTER, NON-ENUMERABILITY FROM THE PERMUTATION, AND
⭐   LOW CONTENTION FROM THE RANGES — ⭐ and the only cost is that
⭐   I lose free deduplication of identical URLs, which I'd
⭐   handle with a separate index if the product wants it."
```

# Part 4 — The architecture, and the read path

```
⭐   client
⭐     │  POST /shorten                    GET /{code}
⭐     ▼                                       │
⭐   ┌──────────┐                              ▼
⭐   │   CDN    │ ⭐⭐ REDIRECTS ARE CACHEABLE ── EDGE HANDLES
⭐   └──────────┘                              A LARGE SHARE
⭐     │
⭐     ▼
⭐   ┌──────────────┐   ⭐ read: cache first, 80%+ hit
⭐   │  app (async) │──►┌──────────┐
⭐   │  D453: 3ms   │   │  Redis   │ ⭐⭐ 6 GB HOT SET
⭐   └──────────────┘   └──────────┘
⭐     │  miss                │ ⭐ write-through on create
⭐     ▼                      ▼
⭐   ┌────────────────────────────────┐
⭐   │  Postgres, ⭐⭐ SHARDED BY CODE  │ ⭐ range-allocated ids
⭐   └────────────────────────────────┘
⭐     │  async, never on the request path
⭐     ▼
⭐   ┌──────────┐   ⭐⭐ ANALYTICS VIA A QUEUE — A CLICK MUST NOT
⭐   │  Kafka   │   WAIT FOR AN ANALYTICS WRITE
⭐   └──────────┘
```

```
⭐ ⭐⭐ FOUR DECISIONS WORTH DEFENDING:

⭐ ① ⭐⭐ ***SHARD BY THE SHORT CODE, NOT BY USER OR TIME.***
⭐   ⭐ Every read is a point lookup by code, ⭐⭐ SO SHARDING BY
⭐     CODE MEANS EVERY READ HITS EXACTLY ONE SHARD. ⭐ Sharding
⭐     by creation time creates a hot shard for new links and
⭐     idle shards for old ones.

⭐ ② ⭐⭐ ***301 VS 302 IS AN ANALYTICS DECISION, NOT AN HTTP
⭐   ONE.***
⭐   ⭐ `301` permanent ⇒ ⭐⭐ THE BROWSER CACHES IT AND NEVER
⭐     CALLS YOU AGAIN. ⭐ Cheap; ⭐⭐ AND YOU LOSE ALL CLICK
⭐     ANALYTICS AND THE ABILITY TO EVER CHANGE THE TARGET.
⭐   ⭐ `302` found ⇒ ⭐ every click hits you. ⭐⭐ EXPENSIVE, AND
⭐     IT IS WHAT THE PRODUCT ACTUALLY NEEDS.
⭐   ⭐ ⭐⭐ NAMING THIS TRADE-OFF UNPROMPTED IS ONE OF THE BEST
⭐     SIGNALS IN THE ROUND, ⭐ because it looks like a detail and
⭐     it decides both your traffic and your product.

⭐ ③ ***analytics off the request path*** — ⭐ fire an event,
⭐   return the redirect. ⭐⭐ A CLICK MUST NEVER WAIT ON A WRITE
⭐   TO AN ANALYTICS STORE.

⭐ ④ ⭐⭐ ***CACHE MISS ON A NON-EXISTENT CODE*** ⇒ ⭐ negative
⭐   caching (Day 479), ⭐⭐ OR EVERY 404 IS A DATABASE QUERY AND
⭐   A SCANNER CAN BYPASS YOUR CACHE ENTIRELY.
```

# 💬 Interview

**1. "Design a URL shortener."**

⭐ I'd ask for one number and derive the rest. ⭐⭐ Given a hundred million new URLs a day, that's about
1,160 writes a second, peak maybe 3,500 — which is ordinary, one Postgres handles it. ⭐ Then the number
that actually matters: the read-to-write ratio. ⭐⭐ At 100:1 that's 116,000 reads a second, peak around
350,000 — so writes are a rounding error and the entire design is a read path. ⭐ Five minutes of
arithmetic tells me this is a read-heavy, tiny-payload, cache-friendly system, and every subsequent
decision follows from that sentence.

**2. "Five years of retention. What does storage look like?"**

⭐ About 300 bytes a row, so 100 million a day for five years is 182 billion rows and roughly 55
terabytes. ⭐⭐ And I'd push back on that rather than just design for it: 182 billion rows is a lot for a
URL shortener, so do links expire? ⭐ If they expire after two years it's 20 terabytes and a completely
different conversation. ⭐⭐ If they genuinely are permanent then I need sharding from day one, and I'd
rather say that at minute six than discover it at minute forty. ⭐ Questioning an implausible requirement
is usually worth more than accommodating it silently.

**3. "How do you generate the short codes?"**

⭐ I'd compare three rather than assert one. ⭐⭐ Hashing is stateless and gives free deduplication, but
collisions are certain at 182 billion inserts, so you need a read-before-write to check — which puts
check-then-act and a database round trip on the write path. ⭐ A counter with base62 has no collisions by
construction and gives the shortest codes. ⭐⭐ Pre-generated keys avoid both problems at the cost of
another service. ⭐ I'd take the counter, with two modifications — and the second one is the important
part.

**4. "What's wrong with a plain counter?"**

⭐⭐ Sequential codes are enumerable. ⭐ If my link is `dGx4`, the next one is `dGx5` — so anyone can walk
every URL in the system, including private ones people assumed were unguessable. ⭐⭐ That's a data-leak
surface, not an aesthetic complaint, and it's the thing I'd raise unprompted. ⭐ The fix is permuting the
counter before encoding — a Feistel network or multiplying by a coprime modulo 62⁷ — which is bijective,
so I keep collision-freeness and the output looks random. ⭐⭐ The other issue is contention on a global
counter, and that's range allocation: each server claims ten thousand ids at a time, so it's one round
trip per ten thousand writes and gaps on restart are harmless.

**5. "301 or 302?"**

⭐ It's an analytics decision wearing an HTTP costume, and I'd raise it before being asked. ⭐⭐ A 301 is
permanent, so browsers cache it and never call me again — which is cheap and means I lose all click
analytics *and* the ability to ever change the target. ⭐ A 302 means every click hits my servers, which
is expensive and is what the product actually needs, since analytics is usually the reason the product
exists. ⭐⭐ So 302, and I'd note that this choice is what makes the read path 116,000 requests a second
rather than a fraction of that. ⭐ The traffic estimate and the status code are the same decision.

**6. "How do you shard?"**

⭐ By the short code, because every read is a point lookup by code — so sharding on it means each read
hits exactly one shard with no scatter-gather. ⭐⭐ Sharding by creation time would be the intuitive
choice and it's wrong: new links are hot, so you get one melting shard and a long tail of idle ones. ⭐
Consistent hashing on the code, and since codes come from a permuted counter they're uniformly
distributed by construction — ⭐⭐ which is a nice second benefit of the permutation I hadn't originally
chosen it for.

**7. "What breaks first?"**

⭐ The cache, and specifically the miss path. ⭐⭐ At an 80% hit rate the database sees about 23,000 reads
a second, which is fine; if the hit rate drops to 50% it sees 58,000, which isn't. ⭐ So the thing I'd
watch is hit rate rather than database CPU, because CPU is the lagging indicator. ⭐⭐ And the specific
failure that causes it is a scanner hitting non-existent codes, which misses every time — so negative
caching isn't an optimisation here, it's what stops someone bypassing my cache deliberately.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: the first ten minutes of a system design round.**

Set the structure first. **"I'll spend five minutes on requirements and five on estimation, because the
numbers usually decide the architecture — then I'll draw the system and go deep wherever you'd like."**

Then requirements, including the exclusions. **"Functional: create a short link, redirect it, and I'll
assume click analytics because that's usually why the product exists. Non-functional: redirects need to
be fast — call it under fifty milliseconds at p99 — and highly available, since a broken redirect breaks
someone else's page. Out of scope: I'm not designing the analytics warehouse or user accounts. Two
questions: what's the expected volume, and do links ever expire?"**

Then derive everything from one number. **"A hundred million a day is about 1,160 writes a second, peak
three and a half thousand — ordinary. Now the number that matters: what's the read-to-write ratio? At a
hundred to one that's 116,000 reads a second, peak around 350,000. So writes are a rounding error and
this is entirely a read path. Storage: three hundred bytes a row, five years, 182 billion rows, about 55
terabytes. And I'd push on that — 182 billion rows is a lot for a URL shortener. If links expire after
two years it's 20 terabytes and a different system. If they're genuinely permanent I need sharding from
day one, and I'd rather say so now."**

Close by naming the shape before drawing anything. **"Base62 gives 3.5 trillion codes at seven
characters, so length isn't a constraint. And twenty percent of links will serve eighty percent of
traffic — that hot set is about six gigabytes, which fits in memory, so an eighty percent cache hit rate
takes the database from 116,000 reads a second to 23,000. That's the design: a cache with a database
behind it, and the interesting question is how I generate codes that don't collide and aren't
enumerable."**
