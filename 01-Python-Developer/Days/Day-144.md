# Day 144

**L-144** · **WebSockets in FastAPI** — the upgrade, the fan-out problem, and ⭐⭐ when the answer is not a WebSocket

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a WebSocket turns a request/response server into a stateful one — and
> every hard part today comes from that word *stateful*, because state that lives in one process
> cannot survive a second replica, a deploy, or a dropped connection.**
>
> ⭐ Day 102 said TCP is a stream and every protocol must frame. ⭐⭐ A WebSocket is HTTP borrowing that
> stream back, with framing built in — which is why almost everything you learned about HTTP stops
> applying the moment the handshake completes.

---

# Part 1 — ⭐ The handshake: it starts as HTTP and then stops being HTTP

```
⭐⭐ THE UPGRADE, ON THE WIRE:

⭐   GET /ws HTTP/1.1
⭐   Host: api.example.com
⭐   Upgrade: websocket                    ⭐ "stop speaking HTTP after this"
⭐   Connection: Upgrade
⭐   Sec-WebSocket-Key: dGhlIHNhbXBsZQ==   ⭐ NOT security — see below
⭐   Sec-WebSocket-Version: 13
⭐
⭐   HTTP/1.1 101 Switching Protocols      ⭐⭐ 101, and the ONLY status that
⭐   Upgrade: websocket                       means "the connection is no
⭐   Connection: Upgrade                      longer a request"
⭐   Sec-WebSocket-Accept: s3pPLMBiTxaQ9k...  ⭐ SHA1(key + magic GUID)
⭐
⭐   ⇒ ⭐⭐ `Sec-WebSocket-Key` IS NOT AUTHENTICATION AND NOT ENCRYPTION. It
⭐        exists so a CACHING PROXY that does not understand upgrades cannot
⭐        accidentally replay a cached 101. ⭐ It proves the server understood
⭐        the request; that is all.

⭐⭐ WHAT YOU LOSE AT THE 101 — the list that explains the rest of the day:
⭐   ⭐ NO MORE STATUS CODES. After the upgrade there is no 404, no 500. You
⭐        have frames and a close code.
⭐   ⭐ NO MORE MIDDLEWARE-PER-REQUEST. Your logging, rate limiting and error
⭐        handling middleware ran ONCE, at the handshake, for a connection
⭐        that may live nine hours. ⭐⭐ Every per-message concern is now YOURS.
⭐   ⭐⭐ NO SAME-ORIGIN POLICY. The browser does NOT apply CORS to WebSockets —
⭐        ⭐ it sends the `Origin` header and leaves the decision to you.
⭐        ⇒ ⭐⭐ IF YOU AUTHENTICATE WITH COOKIES AND DO NOT CHECK `Origin`,
⭐          ANY WEBSITE CAN OPEN AN AUTHENTICATED SOCKET TO YOUR API. That is
⭐          CSRF (Day 115) with no preflight to save you. ⭐ It has a name:
⭐          Cross-Site WebSocket Hijacking.
⭐   ⭐ NO LOAD-BALANCER REQUEST BALANCING. The connection is pinned to one
⭐        backend for its whole life ⇒ ⭐⭐ your "even" load becomes whatever
⭐        the connection distribution happens to be.
```

```python
@app.websocket("/ws")
async def ws(websocket: WebSocket, token: str | None = Query(default=None)):
    if websocket.headers.get("origin") not in settings.allowed_origins:
        await websocket.close(code=4403)          # ⭐⭐ CHECK ORIGIN FIRST
        return
    user = authenticate(token)                    # ⭐ Part 2
    if user is None:
        await websocket.close(code=4401)          # ⭐ close BEFORE accept = a failed handshake
        return
    await websocket.accept()
    ...
```

> ⭐ **Closing before `accept()` fails the handshake with an HTTP error**, which is the correct
> way to reject — the client sees a normal HTTP failure rather than a socket that opens and dies.
> ⭐⭐ Close codes 4000–4999 are yours to define; document them like status codes (Day 120).

# Part 2 — ⭐⭐ Authentication, and why it is genuinely awkward

```
⭐⭐ THE PROBLEM: THE BROWSER `WebSocket` API CANNOT SET HEADERS.
⭐   `new WebSocket(url)` — that is the entire API. ⭐ No `Authorization`.
⭐   ⇒ ⭐⭐ SO YOUR Day 140 BEARER SCHEME DOES NOT WORK HERE, AND EVERY
⭐        OPTION BELOW IS A WORKAROUND. Know all four.

⭐  1. ⭐ COOKIE — sent automatically on the handshake. ⭐⭐ Works, and
⭐       REQUIRES the `Origin` check above, because there is no CORS to stop a
⭐       hostile page. ⭐ Best option for a same-site browser app.
⭐  2. ⭐⭐ TOKEN IN THE QUERY STRING — `?token=...`. Works everywhere, and
⭐       ⭐⭐ LEAKS: query strings land in access logs, proxy logs, and
⭐       `Referer`. ⭐ If you must, use a SHORT-LIVED, SINGLE-USE TICKET —
⭐       fetch `POST /ws-ticket` over normal authenticated HTTP, get a 30-second
⭐       nonce, spend it on connect. ⭐⭐ THIS IS THE STANDARD ANSWER.
⭐  3. ⭐ `Sec-WebSocket-Protocol` ABUSE — the one header you CAN set from the
⭐       browser API, so people smuggle the token through it. ⭐⭐ It works and
⭐       it is ugly; you must echo the subprotocol back or the browser closes
⭐       the connection.
⭐  4. ⭐ FIRST-MESSAGE AUTH — accept, then require an auth frame within N
⭐       seconds. ⭐⭐ You must enforce the timeout yourself, and until it
⭐       arrives you are holding an unauthenticated connection — ⭐ which is a
⭐       cheap DoS surface.

⭐   ⇒ ⭐⭐ AND THE ONE EVERYONE FORGETS: AUTHORISATION IS NOT DONE AT CONNECT.
⭐        ⭐ The token expires; the user gets banned; their room membership is
⭐        revoked. ⭐⭐ A nine-hour connection authorised once at hour zero is
⭐        a permission you cannot take back. ⭐ Re-check on every subscribe,
⭐        and close the socket when the session is revoked.
```

# Part 3 — ⭐⭐ The connection manager, and why yours breaks at two replicas

```python
class ConnectionManager:
    def __init__(self) -> None:
        self._rooms: dict[str, set[WebSocket]] = defaultdict(set)   # ⭐ IN MEMORY

    async def join(self, room: str, ws: WebSocket) -> None:
        self._rooms[room].add(ws)

    async def leave(self, room: str, ws: WebSocket) -> None:
        self._rooms[room].discard(ws)
        if not self._rooms[room]:
            del self._rooms[room]                    # ⭐ or the dict grows forever

    async def broadcast(self, room: str, msg: dict) -> None:
        dead = []
        for ws in list(self._rooms[room]):           # ⭐⭐ list() — the set mutates
            try:
                await ws.send_json(msg)
            except (WebSocketDisconnect, RuntimeError):
                dead.append(ws)                      # ⭐ never let one dead peer
        for ws in dead:                              #   abort the whole broadcast
            self._rooms[room].discard(ws)
```

```
⭐⭐ THIS IS CORRECT AND IT IS ALSO A TRAP, BECAUSE:

⭐   ⭐⭐ THE DICT LIVES IN ONE PROCESS. Day 111: you run N workers.
⭐        ⇒ ⭐ Alice connects → worker 1. Bob connects → worker 2.
⭐        ⇒ ⭐⭐ ALICE SENDS A MESSAGE AND BOB NEVER RECEIVES IT.
⭐        ⇒ ⭐ AND IT WORKS PERFECTLY IN DEVELOPMENT, where you run one worker.
⭐          ⭐⭐ THAT is why this bug reaches production so reliably.

⭐⭐ THE FIX: THE PROCESS-LOCAL SET STAYS (it holds the actual sockets), BUT
⭐   THE FAN-OUT GOES THROUGH A SHARED BUS.

⭐   ⭐ publish:   redis.publish(f"room:{id}", json)
⭐   ⭐ subscribe: EVERY worker subscribes; on a message, it broadcasts to the
⭐                sockets IT owns.
⭐   ⇒ ⭐⭐ EACH WORKER IS NOW A DELIVERY AGENT FOR ITS OWN CONNECTIONS, and
⭐        the bus handles the crossing. ⭐ This is the standard architecture;
⭐        Socket.IO and Django Channels both do exactly this.
```

```python
async def redis_listener(app):                       # ⭐ started in lifespan (Day 133)
    pubsub = app.state.redis.pubsub()
    await pubsub.psubscribe("room:*")
    async for msg in pubsub.listen():
        if msg["type"] == "pmessage":
            room = msg["channel"].split(":", 1)[1]
            await manager.broadcast(room, json.loads(msg["data"]))
```

```
⭐⭐ AND THE PROPERTY OF PUB/SUB YOU MUST STATE OUT LOUD:
⭐   ⭐ Redis pub/sub is FIRE AND FORGET. ⭐⭐ A subscriber that is disconnected
⭐     for 200 ms during a deploy MISSES THOSE MESSAGES ENTIRELY. There is no
⭐     buffer, no replay, no ack.
⭐   ⇒ ⭐⭐ SO: PUB/SUB IS FINE FOR "SOMEONE IS TYPING". IT IS NOT FINE FOR
⭐        CHAT MESSAGES YOU PROMISED TO DELIVER.
⭐   ⇒ ⭐ FOR DURABILITY: persist the message to the database FIRST, publish
⭐        second (Day 142's ordering), and let the client RECONNECT AND FETCH
⭐        WHAT IT MISSED by last-seen id. ⭐⭐ Redis Streams or a real broker if
⭐        you need replay in the bus itself.
```

# Part 4 — ⭐⭐ Backpressure, heartbeats, and the connection that is already dead

```
⭐⭐ THE SLOW CONSUMER — the memory leak that looks like a memory leak:

⭐   ⭐ you broadcast 500 msg/s. One client is on a train.
⭐   ⭐ `await ws.send_json(...)` returns as soon as the data is handed to the
⭐     OS/ASGI send buffer — ⭐⭐ IT DOES NOT MEAN DELIVERED.
⭐   ⇒ ⭐ the buffer grows. ⭐⭐ MEMORY PER SLOW CLIENT GROWS WITHOUT BOUND, and
⭐     eventually the whole worker OOMs (Day 082's exit 137) ⭐ because of ONE
⭐     bad network.
⭐
⭐   ⇒ ⭐⭐ THE FIX IS TO DECIDE WHAT TO DROP. Give each connection a BOUNDED
⭐        outbound queue and a policy:
⭐        ⭐ `asyncio.Queue(maxsize=100)` + `put_nowait` → on `QueueFull`:
⭐          · ⭐ DROP THE CLIENT (correct for chat: they reconnect and resync)
⭐          · ⭐ DROP OLDEST (correct for tickers: only the latest matters)
⭐          · ⭐⭐ NEVER `await queue.put()` — that applies backpressure to your
⭐            BROADCASTER, so one slow client slows down EVERYONE. ⭐ That is
⭐            the mistake that turns a client problem into an outage.
```

```python
class Connection:
    def __init__(self, ws: WebSocket) -> None:
        self.ws = ws
        self.out: asyncio.Queue[dict] = asyncio.Queue(maxsize=100)   # ⭐⭐ BOUNDED

    def offer(self, msg: dict) -> bool:
        try:
            self.out.put_nowait(msg)                  # ⭐ never blocks the broadcaster
            return True
        except asyncio.QueueFull:
            return False                              # ⭐⭐ caller closes this connection

    async def writer(self) -> None:                   # ⭐ one task per connection
        while True:
            await self.ws.send_json(await self.out.get())
```

```
⭐⭐ HEARTBEATS — because a dead TCP connection looks IDENTICAL to a quiet one:

⭐   ⭐ Day 103's half-open connection, and here it is the default case: a
⭐     laptop lid closes, a phone loses signal. ⭐⭐ NO FIN ARRIVES. Your server
⭐     holds the socket, the room membership, and the memory FOREVER.
⭐   ⇒ ⭐ WebSocket PING/PONG frames are built into the protocol and handled by
⭐     the browser automatically. ⭐⭐ Send a ping every ~20–30 s; if no pong
⭐     within a timeout, CLOSE — do not wait for the OS's TCP keepalive, which
⭐     defaults to TWO HOURS.
⭐   ⇒ ⭐⭐ AND HEARTBEATS ARE ALSO WHAT KEEPS THE CONNECTION ALIVE THROUGH
⭐     PROXIES: nginx `proxy_read_timeout` defaults to 60 s and will cut an
⭐     idle WebSocket without ceremony. ⭐ Two problems, one mechanism.
⭐
⭐ ⭐ NGINX MUST ALSO BE TOLD (Day 111):
⭐     proxy_http_version 1.1;
⭐     proxy_set_header Upgrade $http_upgrade;
⭐     proxy_set_header Connection "upgrade";
⭐     proxy_read_timeout 3600s;
⭐   ⭐⭐ WITHOUT THE FIRST THREE LINES THE HANDSHAKE SILENTLY DOWNGRADES AND
⭐     THE CLIENT SEES A 400. It is the single most common "works locally,
⭐     fails behind the proxy" WebSocket bug.
```

```
⭐⭐ DEPLOYS DISCONNECT EVERYONE. There is no rolling upgrade for a socket.
⭐   ⇒ ⭐ send a close code the client understands (e.g. 4000 "restarting"),
⭐        ⭐⭐ AND MAKE THE CLIENT RECONNECT WITH EXPONENTIAL BACKOFF **AND
⭐        JITTER** (Day 142) — ⭐ otherwise 10,000 clients reconnect in the
⭐        same second and you have DDoSed yourself with your own users during
⭐        every deploy.
```

# Part 5 — ⭐⭐ When not to use a WebSocket

```
⭐⭐ THE QUESTION TO ASK: DOES DATA FLOW BOTH WAYS, CONTINUOUSLY?
⭐   ⭐ If it only flows SERVER → CLIENT, you probably do not want a WebSocket.

⭐  ⭐⭐ SERVER-SENT EVENTS (SSE) — the underrated answer:
⭐    ⭐ plain HTTP, one long response, `text/event-stream`
⭐    ⭐ + ⭐⭐ AUTOMATIC RECONNECTION WITH `Last-Event-ID` BUILT INTO THE
⭐        BROWSER — you get resume-from-where-I-left-off for free, which is
⭐        the hardest part of the WebSocket design above
⭐    ⭐ + ordinary headers, so ⭐ ORDINARY BEARER AUTH WORKS (Part 2 vanishes)
⭐    ⭐ + proxies, CDNs and your existing middleware all understand it
⭐    ⭐ − one direction only; ⭐ HTTP/1.1's 6-connection-per-domain limit
⭐        (not an issue over HTTP/2)
⭐    ⇒ ⭐⭐ NOTIFICATIONS, LIVE DASHBOARDS, PROGRESS BARS, AI TOKEN STREAMING:
⭐        SSE IS THE RIGHT ANSWER AND ALMOST NOBODY PICKS IT.
⭐
⭐  ⭐ POLLING — every 10–30 s, with `ETag` (Day 124).
⭐    ⭐⭐ Genuinely correct for slow-changing data. Stateless, cacheable,
⭐    debuggable with curl, survives deploys. ⭐ "Poll" is not a dirty word;
⭐    it is the option with the fewest failure modes.
⭐
⭐  ⭐⭐ WEBSOCKET — when the CLIENT sends frequently too: chat, collaborative
⭐    editing, multiplayer, live cursors, trading. ⭐ Then the bidirectionality
⭐    pays for the state.
⭐
⭐   ⇒ ⭐⭐ SAYING "SSE" IN AN INTERVIEW WHEN ASKED FOR REAL-TIME
⭐        NOTIFICATIONS IS ONE OF THE HIGHEST-VALUE ANSWERS IN THIS STAGE.
⭐        ⭐ It shows you optimise for failure modes rather than for novelty.
```

```python
# ⭐ SSE in FastAPI — the whole thing
@app.get("/events")
async def events(request: Request, user=Depends(get_current_user)):   # ⭐ normal auth!
    async def gen():
        async for item in stream_for(user):
            if await request.is_disconnected():                       # ⭐⭐ or you leak
                break
            yield f"id: {item.id}\ndata: {json.dumps(item.payload)}\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-store",
                                      "X-Accel-Buffering": "no"})     # ⭐⭐ nginx buffers!
```

> ⭐⭐ `X-Accel-Buffering: no` is the SSE equivalent of the nginx WebSocket config: ⭐ without it
> nginx buffers your stream and the client receives nothing until the buffer fills. Day 111 said
> nginx buffers slow clients — **here that feature is the bug.**

## Common mistakes

| Mistake | Correction |
|---|---|
| No `Origin` check with cookie auth | Browsers don't apply CORS to WebSockets. Any site can open an authenticated socket. |
| Token in the query string, long-lived | Query strings land in access logs and `Referer`. Use a short-lived single-use ticket. |
| Authorising only at connect | A nine-hour connection is a permission you can't revoke. Re-check per action. |
| In-memory connection registry | Works with one worker, silently broken with two. Fan out over a shared bus. |
| Redis pub/sub for messages that must arrive | Fire-and-forget. Persist first, publish second, resync on reconnect. |
| Unbounded outbound buffering | One slow client OOMs the worker. Bounded queue with an explicit drop policy. |
| `await queue.put()` on a full queue | Backpressures the broadcaster — one slow client slows everyone. |
| No application-level heartbeat | A dead connection is indistinguishable from a quiet one; TCP keepalive is two hours. |
| Missing nginx `Upgrade`/`Connection` headers | The handshake downgrades and the client sees a 400. |
| Default `proxy_read_timeout` | The proxy cuts idle sockets at 60 s. |
| Reconnect without jitter | 10,000 clients reconnect in the same second after every deploy. |
| Iterating the room set while broadcasting | It mutates on disconnect. Copy it first. |
| Letting one failed send abort a broadcast | Collect the dead, send to the rest. |
| WebSocket for one-way notifications | SSE gives automatic reconnection with `Last-Event-ID` and normal auth. |
| SSE without `X-Accel-Buffering: no` | nginx buffers the stream and the client receives nothing. |

## Interview questions

**Q: Your chat works locally and drops half the messages in production. Why?**

> Almost certainly the connection registry is a dict in process memory. Locally I run one worker so
> every connection is in the same dict; production runs four, so Alice is on worker one and Bob on
> worker two, and worker one's broadcast simply cannot reach Bob's socket — it doesn't have it. The
> fix keeps the local registry, because that's where the actual socket objects live, but moves the
> fan-out to a shared bus: publish to Redis on a room channel, every worker subscribes, and each
> worker delivers to the connections it owns. And I'd say the follow-up before being asked — Redis
> pub/sub is fire-and-forget, so a worker that's restarting misses messages entirely. For anything I
> promised to deliver, I persist to the database first and let the client resync by last-seen id on
> reconnect.

**Q: How do you authenticate a WebSocket?**

> Awkwardly, because the browser's `WebSocket` constructor can't set headers, so bearer auth doesn't
> apply. Four options: a cookie, which works and *requires* an `Origin` check because browsers don't
> apply CORS to WebSockets — without it any website can open an authenticated socket to your API,
> which is cross-site WebSocket hijacking. A token in the query string, which leaks into access logs
> and `Referer`, so if I use it I make it a single-use 30-second ticket fetched over normal
> authenticated HTTP. Smuggling it through `Sec-WebSocket-Protocol`, which works and is ugly. Or an
> auth frame after connect, which means enforcing my own timeout and holding unauthenticated
> connections in the meantime. The part people miss is that authorisation isn't a connect-time
> event: a nine-hour connection authorised once is a permission you can't revoke, so I re-check on
> each subscribe and close on revocation.

**Q: One user on a bad network causes your server to run out of memory. Explain.**

> `await ws.send_json(...)` returns when the data is handed to the send buffer, not when it's
> delivered. If I broadcast faster than a client can drain, that buffer grows without bound, and
> since it's per connection, one client on a train can consume all the memory on the worker and OOM
> it — which kills every other connection on that process. The fix is to make the drop explicit: a
> bounded `asyncio.Queue` per connection with `put_nowait`, and on `QueueFull` either close that
> client, which is right for chat because they reconnect and resync, or drop the oldest message,
> which is right for a price ticker. What I never do is `await queue.put()`, because that
> backpressures my broadcaster and turns one slow client into everyone being slow.

**Q: When would you not use a WebSocket?**

> Whenever data only flows server to client. For notifications, dashboards, progress bars or token
> streaming, SSE is better: it's plain HTTP, so normal bearer auth and existing middleware work; the
> browser reconnects automatically and sends `Last-Event-ID`, which gives you resume-from-where-I-
> left-off for free — that's the hardest part of the WebSocket design; and proxies understand it. If
> the data changes slowly, polling with an ETag every fifteen seconds is stateless, cacheable,
> debuggable with curl and survives deploys. I'd reserve WebSockets for genuinely bidirectional
> traffic: chat, collaborative editing, live cursors.

**Q: What happens to WebSockets during a deploy?**

> Everyone disconnects — there's no rolling upgrade for a stateful connection, and the connection is
> pinned to one backend for its life. So I send a specific close code the client understands, and
> the client reconnects with exponential backoff *and jitter*. Without jitter, ten thousand clients
> reconnect in the same second and you've DDoSed yourself with your own users on every deploy. The
> reconnect also has to resync — fetch anything missed by last-seen id — because the bus doesn't
> replay.
