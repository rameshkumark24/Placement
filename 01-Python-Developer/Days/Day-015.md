# Part 1 — ⭐⭐ The pipeline

```
⭐ HTML bytes ─▶ ⭐ PARSE ─▶ ⭐⭐ DOM ────┐
                                        ├─▶ ⭐ RENDER TREE ─▶ ⭐⭐ LAYOUT ─▶ ⭐ PAINT ─▶ ⭐ COMPOSITE
⭐ CSS bytes  ─▶ ⭐ PARSE ─▶ ⭐⭐ CSSOM ───┘        (visible nodes    (geometry)   (pixels)  (GPU layers)
                                                  only)
```

| ⭐ Stage | ⭐ What happens |
|---|---|
| ⭐ **Parse → DOM** | the tree from Day 012, built incrementally as bytes arrive |
| ⭐ **Parse → CSSOM** | ⭐⭐ **render-blocking** — the browser will not paint with partial CSS, because a late rule could change everything |
| ⭐ **Render tree** | DOM + CSSOM, **visible nodes only** — ⭐ `display: none` nodes are absent; `visibility: hidden` nodes are present |
| ⭐⭐ **Layout (reflow)** | ⭐⭐ compute the **geometry** of every box — position and size |
| ⭐ **Paint** | fill pixels — text, colours, shadows, borders |
| ⭐ **Composite** | ⭐ assemble layers on the **GPU** |

```
⭐⭐ WHY CSS BLOCKS RENDERING AND JS BLOCKS PARSING:
⭐   · CSS  ⇒ ⭐⭐ a rule in the last stylesheet could restyle the whole page ⇒ painting early
⭐            would mean repainting everything (a "flash of unstyled content")
⭐   · JS   ⇒ ⭐⭐ a script may call document.write() or mutate the DOM ⇒ the parser CANNOT
⭐            safely continue past it ⇒ ⭐ parsing STOPS at a plain <script>
⭐   ⇒ ⭐⭐ AND: a script can read computed styles, so a <script> also waits for pending CSS.
⭐      ⇒ ⭐⭐ one slow stylesheet in <head> delays your JS, your parse, AND your first paint.
```

## ⭐ The rules that fall out of that

| ⭐ Rule | ⭐ Because |
|---|---|
| CSS in `<head>` | ⭐ needed before first paint anyway; loading it late guarantees a repaint |
| ⭐⭐ **`defer` on scripts** | ⭐ parses in parallel, executes after the DOM, **in order** |
| `async` for independent scripts | ⭐ analytics — no ordering guarantee |
| ⭐ Inline critical CSS | ⭐ removes one round trip before first paint |
| ⭐ `preload`/`preconnect` | start the DNS + TCP + TLS early (Days 007–009) |

# Part 2 — ⭐⭐ Reflow, repaint, and the cheap third option

```
⭐⭐ COST ORDER — this is the whole performance model:

⭐ 1. ⭐⭐ LAYOUT (reflow)  — geometry changed ⇒ recompute, often for ANCESTORS AND DESCENDANTS
⭐                            triggered by: width, height, padding, margin, font-size,
⭐                            position, display, adding/removing nodes
⭐ 2. ⭐ PAINT             — appearance changed, geometry did not
⭐                            triggered by: color, background, box-shadow, visibility
⭐ 3. ⭐⭐ COMPOSITE ONLY   — ⭐⭐ THE CHEAP ONE, runs on the GPU, can skip the main thread
⭐                            triggered by: ⭐⭐ transform, opacity
```

⭐⭐ **This is why every smooth animation on the web uses `transform` and `opacity`** — animating
`left`/`top`/`width` forces a layout on **every frame** on the same single thread you froze on Day
014, and at 60fps you have **16 ms** for the entire loop.

```js
// ⚠️ ⭐⭐ LAYOUT THRASHING — the classic, and it is invisible in code review:
for (const el of items) {
  el.style.height = el.offsetHeight + 10 + "px";
  // ⭐ READ offsetHeight ⇒ forces a SYNCHRONOUS layout (the browser must flush pending writes)
  // ⭐ WRITE style      ⇒ invalidates layout again
  // ⇒ ⭐⭐ read/write/read/write ⇒ N layouts instead of 1.
}
// ⭐ FIX: batch — read ALL, then write ALL.
```

⭐ **The general principle transfers well beyond browsers:** interleaving reads and writes across a
boundary that must be flushed is a performance bug, whether the boundary is the layout engine, a
database (Stage 5's N+1) or a network round trip.

# Part 3 — ⭐ What the pipeline means for your Python service

```
⭐⭐ SERVER-RENDERED (Jinja2 / Django templates):
⭐   HTML arrives complete ⇒ DOM + CSSOM ⇒ ⭐ CONTENT VISIBLE AT FIRST PAINT
⭐   ⇒ ⭐ fast first paint, works without JS, scrapeable and SEO-friendly (Day 012)
⭐   ⇒ ⭐ every interaction is a full page load unless you add JS

⭐⭐ CLIENT-RENDERED (React on top of your FastAPI JSON):
⭐   HTML arrives ~empty ⇒ download JS ⇒ run JS ⇒ ⭐⭐ FETCH your API ⇒ build DOM ⇒ paint
⭐   ⇒ ⭐⭐ FIRST PAINT IS BLANK, and the API round trip is INSIDE the user's wait
⭐   ⇒ ⭐ rich interaction afterwards, and a clean API boundary you can reuse for mobile
```

⭐⭐ **The engineering consequence for you: in a client-rendered app your API's p95 latency is
directly on the critical rendering path.** ⭐ **A 400 ms endpoint is 400 ms of blank screen** — it is
not "backend latency" that someone else measures on a dashboard, it is the user watching nothing
happen. **That is the argument for Stage 5's indexing work stated in a way a product manager
accepts.**

⭐ **Where each fits:** server-rendered for content and forms (a dashboard, a docs site, an admin);
client-rendered for genuinely interactive applications. ⭐⭐ **The hybrid — render on the server,
hydrate on the client — is what Next.js exists for**, and the Python equivalents are HTMX or
Django + Alpine, both of which are entirely respectable for the projects in Stage 7.

# Part 4 — C-10 · ⭐⭐ Hashing vs encryption vs signing

⭐⭐ **These three get confused constantly, and each confusion produces a specific vulnerability.**

| | ⭐⭐ Hashing | ⭐⭐ Encryption | ⭐⭐ Signing |
|---|---|---|---|
| Reversible? | ⭐⭐ **NO — one way** | ⭐ yes, with the key | n/a |
| Keys | none | ⭐ symmetric or asymmetric | ⭐ private signs, public verifies |
| Answers | "is this the same?" | "keep this secret" | ⭐⭐ "who made this, and was it changed?" |
| Examples | SHA-256, bcrypt, argon2 | AES, RSA | RSA, ECDSA, ⭐ HMAC |
| ⭐ Use for | ⭐⭐ **passwords**, integrity | data at rest, secrets | ⭐⭐ **JWTs**, certificates |

```
⭐⭐ THE THREE SENTENCES:
⭐   HASH    ⇒ I can check you know it. I can never recover it.
⭐   ENCRYPT ⇒ I can get it back, if I have the key. ⭐⭐ So I must keep a key.
⭐   SIGN    ⇒ Anyone can verify it came from me and is unmodified. Nothing is hidden.
```

## ⚠️ ⭐⭐ Passwords — the mistake with the largest blast radius

```python
import hashlib
hashlib.sha256(b"hunter2").hexdigest()     # ⚠️⚠️ ⭐⭐ WRONG FOR PASSWORDS
```

```
⭐⭐ WHY SHA-256 IS WRONG FOR PASSWORDS — and it is not because it is "insecure":
⭐   ⭐⭐ IT IS TOO FAST. A GPU computes BILLIONS of SHA-256 hashes per second.
⭐   ⇒ ⭐ a stolen table of SHA-256 password hashes is cracked, not "maybe cracked".
⭐   ⇒ ⭐ rainbow tables: precomputed hash→password lookups for common passwords.
⭐
⭐⭐ WHAT PASSWORD HASHES DO INSTEAD:
⭐   ⭐ SALT      — a unique random value per user, stored alongside
⭐                 ⇒ ⭐⭐ two users with the same password get different hashes
⭐                 ⇒ ⭐ rainbow tables become useless — one table per salt
⭐   ⭐⭐ SLOWNESS — a deliberate work factor (cost / rounds), TUNED so one hash takes ~100 ms
⭐                 ⇒ ⭐⭐ raise the attacker's cost by ~10⁶ while costing you 100 ms per login
⭐   ⭐ MEMORY-HARD (argon2, scrypt) — also expensive in RAM ⇒ ⭐⭐ defeats GPU/ASIC parallelism
```

```python
# ⭐ The right tools in Python — both handle salting for you:
from argon2 import PasswordHasher          # pip install argon2-cffi   ⭐⭐ current best default
ph = PasswordHasher()
h = ph.hash("hunter2")                     # ⭐ salt is generated and embedded IN the string
ph.verify(h, "hunter2")                    # ⭐ raises on mismatch

import bcrypt                              # ⭐ also fine, long-established
bcrypt.hashpw(b"hunter2", bcrypt.gensalt(rounds=12))
```

⚠️ ⭐⭐ **Never store a password encrypted.** Encryption is reversible, which means there is a key,
which means someone can read every password — and there is no legitimate reason to ever recover a
user's password. **"We can email you your password" means "we can be robbed of everyone's
password".**

## ⭐⭐ HMAC, and comparing secrets safely

```python
import hmac, hashlib, secrets

sig = hmac.new(key, msg, hashlib.sha256).hexdigest()   # ⭐ symmetric signature — "I made this"

# ⚠️ ⭐⭐ NEVER compare secrets with ==
if sig == provided:            # ⚠️ ⭐⭐ short-circuits on the first differing byte ⇒ TIMING ATTACK
if hmac.compare_digest(sig, provided):   # ⭐⭐ constant time. ALWAYS this.

secrets.token_urlsafe(32)      # ⭐⭐ for tokens — NOT random.random(), which is predictable (Day 065's note)
```

⭐⭐ **The timing attack is real and it is the reason `compare_digest` exists:** `==` returns as soon
as two bytes differ, so the time taken leaks how many leading bytes were correct, and an attacker can
recover a signature one byte at a time. ⚠️ **`random` is a Mersenne Twister — deterministic and
recoverable from its output. `secrets` is the CSPRNG. Never generate a token, session id or password
reset key with `random`.**

| ⭐ Primitive | ⭐ Use it for |
|---|---|
| ⭐ SHA-256 | file integrity, ETags, content addressing — ⚠️ **not passwords** |
| ⭐⭐ argon2 / bcrypt | ⭐⭐ **passwords, always** |
| ⭐ HMAC-SHA256 | ⭐ webhook signatures, session cookies, symmetric JWTs (HS256) |
| ⭐ RSA / ECDSA | ⭐ certificates, asymmetric JWTs (RS256) — ⭐⭐ verifier does not need the signing key |
| ⭐ AES-GCM | data at rest — ⭐ authenticated encryption |
| MD5 / SHA-1 | ⚠️ ⭐ **broken** — collisions are practical. Non-security checksums only |

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Hashing passwords with SHA-256** | ⭐⭐ Too fast. Use argon2 or bcrypt — salted and deliberately slow. |
| ⭐⭐ **Encrypting passwords** | ⭐⭐ Reversible. Hash them; you never need the original. |
| ⭐ Comparing signatures with `==` | ⭐⭐ Timing attack. `hmac.compare_digest`. |
| ⭐ `random` for tokens | ⭐⭐ Predictable. `secrets`. |
| Writing your own crypto | ⭐ Use a library. This is the one place originality is a bug. |
| "Hashing is encryption without a key" | ⭐ It is not reversible at all. Different operation. |
| Blocking `<script>` in `<head>` | ⭐ Stops parsing and delays first paint. Use `defer`. |
| Animating `left`/`width` | ⭐⭐ Layout every frame. Animate `transform`/`opacity`. |
| Interleaving DOM reads and writes | ⭐ Layout thrashing. Batch reads, then writes. |
| Thinking `display:none` and `visibility:hidden` are the same | ⭐ One leaves the render tree; one keeps its box. |
| Assuming client-rendering is free | ⭐⭐ Your API latency lands on the critical rendering path. |

## Interview questions

**Q: What happens between receiving HTML and seeing pixels?**
> The HTML is parsed into the DOM and the CSS into the CSSOM; both are required, because a rule in
> the last stylesheet could restyle everything, so CSS is render-blocking. They combine into a render
> tree of visible nodes only. Layout computes geometry for every box, paint fills pixels, and
> compositing assembles layers on the GPU. A plain `<script>` also stops parsing, because it might
> mutate the DOM — which is why `defer` exists.

**Q: Which CSS properties are cheap to animate, and why?**
> `transform` and `opacity`, because they can be handled at the compositing stage on the GPU without
> re-running layout or paint on the main thread. Animating `left`, `top` or `width` forces a layout
> every frame, on the same single thread that handles events — and at 60fps the whole frame budget is
> about 16 milliseconds.

**Q: Why not SHA-256 for passwords?**
> Because it's fast, and speed is the attacker's advantage. A GPU does billions of SHA-256 operations
> per second, so a stolen hash table is cracked rather than merely at risk. Password hashes need a
> per-user salt so identical passwords hash differently and precomputed tables are useless, and a
> tunable work factor so a single hash takes on the order of 100 milliseconds. Argon2 adds
> memory-hardness, which is what removes the GPU's parallelism advantage. It's the one place where
> being slow is the feature.

**Q: Hashing, encryption or signing — pick for: passwords, a session cookie, a database backup, a
JWT.**
> Passwords: hashing, with argon2. A session cookie: signing, with HMAC, so I can detect tampering
> without hiding the contents — encrypt it too if it carries anything sensitive. A database backup:
> encryption, AES-GCM, because I genuinely need it back. A JWT: signing — HS256 if the same service
> issues and verifies, RS256 when many services verify but only one issues, since then the verifiers
> only need the public key.

**Q: Why `hmac.compare_digest` instead of `==`?**
> Because `==` short-circuits at the first differing byte, so the comparison time reveals how many
> leading bytes matched. That's enough to recover a signature byte by byte over many attempts.
> `compare_digest` compares in constant time regardless of where the difference is.

**Q: Server-rendered or client-rendered for your project?**
> It depends on what the page is. For content and forms — an admin, a dashboard, anything that must
> be indexable — server-rendered wins: content is visible at first paint and works without
> JavaScript. For a genuinely interactive application, client-rendered is worth the blank first
> paint, and it forces a clean API boundary I can reuse from mobile. The thing I'd say out loud is
> that client-rendering puts my API's p95 directly in front of the user — a 400ms endpoint is 400ms
> of empty screen.

## 🎙️ Articulation drill

Record two minutes: **"How would you store passwords?"**

⭐ Never in plaintext, ⭐⭐ **never encrypted** — encryption implies a key and a path back to the
original, and there is no legitimate reason to ever recover a user's password. ⭐ Hash with **argon2**
(or bcrypt), which salts automatically, so identical passwords produce different hashes and
precomputed tables are worthless. ⭐⭐ **Tune the work factor so a single verification costs about 100
milliseconds on your hardware** — that is invisible at login and multiplies an attacker's cost by
roughly a million.

⭐⭐ **Then the sentence that shows you have thought past the recipe:** *the hash is the last line of
defence, not the first.* It matters only after the database is already stolen — so rate-limit login
attempts, use `compare_digest` for anything comparing secrets, and generate every token with
`secrets` rather than `random`.
