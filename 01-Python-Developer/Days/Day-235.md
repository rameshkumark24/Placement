# Day 235 🔐

**P-235** · 🔐 **Auth in the browser** — ⭐⭐ where the token lives is the whole decision

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `localStorage` is readable by any JavaScript that runs on your page, so
> a token stored there is a token that one XSS — including one from a compromised dependency you
> never wrote — exfiltrates permanently, while an `HttpOnly` cookie is not readable by script at all
> and therefore survives the same attack.**
>
> Today: the storage decision, ⭐ the cookie flags, ⭐⭐ refresh without a race, and logout that works.

---

# Part 1 — ⭐⭐ The decision

| | `localStorage` | ⭐⭐ `HttpOnly` cookie |
|---|---|---|
| Readable by JS | ⭐⭐ **Yes — this is the whole problem** | ⭐ **No.** Not by your code, not by an attacker's |
| Survives XSS | ❌ ⭐⭐ Token stolen, silently, forever | ✅ ⭐ Attacker can *act* while on the page, but **cannot take the token away** |
| Sent automatically | No — you attach it | ⭐ Yes, by the browser |
| CSRF exposure | ⭐ None (nothing is automatic) | ⭐⭐ **Yes — needs `SameSite` + a token** |
| Cross-domain API | ⭐ Easy | ⭐ Needs CORS credentials + `SameSite=None; Secure` |
| Mobile / non-browser clients | ⭐ Fine | ⭐ Awkward |

```
⭐⭐ THE ASYMMETRY THAT DECIDES IT

⭐   XSS + localStorage ⇒ ⭐⭐ THE ATTACKER TAKES THE TOKEN AND USES
⭐     IT FROM THEIR OWN MACHINE, AT LEISURE, UNTIL IT EXPIRES.
⭐     ⭐ Your logout does nothing. Your session list shows nothing.
⭐   XSS + HttpOnly cookie ⇒ ⭐ the attacker can make requests AS the
⭐     user WHILE THE PAGE IS OPEN — bad, but ⭐⭐ BOUNDED IN TIME AND
⭐     BOUNDED TO YOUR ORIGIN, and revoking the session ends it.

⭐   ⇒ ⭐⭐ NEITHER IS "XSS-PROOF". THE COOKIE LIMITS THE BLAST RADIUS.
⭐     THAT IS THE ENTIRE ARGUMENT, AND IT IS ENOUGH.
```

> ⭐⭐ **"But I'll just prevent XSS."** You have ~900 dependencies (Day 221) and one of them will have
> a bad day. **Defence in depth means assuming one control fails.** Choosing storage that survives an
> XSS is free; preventing every XSS forever is not.
>
> ⭐ **`sessionStorage` is not a fix** — same JS-readable problem, shorter life. **In-memory only** (a
> variable) genuinely resists XSS-exfiltration better but dies on refresh, so it needs a refresh cookie
> anyway — at which point use the cookie.

# Part 2 — The flags

```python
# ⭐ FastAPI — the four that matter
response.set_cookie(
    key="session",
    value=token,
    httponly=True,      # ⭐⭐ JS CANNOT READ IT. The one that matters most.
    secure=True,        # ⭐ HTTPS only — never sent in clear
    samesite="lax",     # ⭐⭐ not sent on cross-site POSTs ⇒ kills most CSRF
    max_age=900,        # ⭐ 15 min access token
    path="/",
)
```

| ⭐ Flag | Missing it means |
|---|---|
| `HttpOnly` | ⭐⭐ Any script reads it. **The default failure.** |
| `Secure` | ⭐ Sent over plain HTTP if anything downgrades |
| ⭐⭐ `SameSite=Lax` | Sent on cross-site requests ⇒ **CSRF** |
| `SameSite=None` | ⭐ Required for a genuinely cross-domain API — **and then you must add a CSRF token** |
| `Domain` too broad | ⭐⭐ `.example.com` shares the cookie with **every** subdomain, including the one running someone's marketing widget |

```
⭐⭐ SameSite=Lax IS NOT A COMPLETE CSRF DEFENCE
⭐   · Lax still allows top-level GET navigations ⇒ ⭐⭐ ANY STATE-
⭐     CHANGING GET IS STILL EXPLOITABLE. (Never mutate on GET.)
⭐   · Subdomains are SAME-SITE ⇒ ⭐ a compromised subdomain still
⭐     sends your cookie.
⭐   ⇒ ⭐ FOR ANYTHING THAT MATTERS: Lax + a CSRF token (double-submit
⭐     or origin check). ⭐⭐ CHECK THE `Origin` HEADER SERVER-SIDE —
⭐     it is one line and it is genuinely effective.
```

# Part 3 — ⭐⭐ Refresh, and the race

```
⭐⭐ THE PATTERN
⭐   access token   ⇒ ⭐ SHORT (5–15 min), used on every request
⭐   refresh token  ⇒ ⭐ long (days), HttpOnly cookie, ⭐⭐ ONLY EVER
⭐                     SENT TO /auth/refresh (path-scoped)

⭐⭐ THE RACE NOBODY HANDLES ON THE FIRST ATTEMPT
⭐   the token expires while SIX requests are in flight
⭐   ⇒ all six get 401
⭐   ⇒ ⭐⭐ ALL SIX CALL /auth/refresh
⭐   ⇒ with refresh-token ROTATION, the first succeeds and
⭐     ⭐⭐ THE OTHER FIVE PRESENT A NOW-INVALID TOKEN
⭐   ⇒ ⭐⭐ THE SERVER SEES REUSE, ASSUMES THEFT, AND KILLS THE
⭐     SESSION ⇒ THE USER IS LOGGED OUT AT RANDOM.
```

```javascript
// ⭐⭐ SINGLE-FLIGHT REFRESH — one refresh, five waiters
let refreshing = null;                    // ⭐ the shared promise

async function withAuth(request) {
  let res = await request();
  if (res.status !== 401) return res;

  refreshing ??= refresh().finally(() => { refreshing = null; });
  //          ⭐⭐ every concurrent caller awaits THE SAME promise
  try { await refreshing; } catch { redirectToLogin(); throw; }

  return request();                        // ⭐ retry ONCE. Never loop.
}
```

> ⭐⭐ **This is Day 479's single-flight cache, exactly** — one leader does the work, the rest wait on
> a shared promise, and the failure path must reject *all* waiters or they hang forever. **Same
> pattern, different layer.** Say that in an interview and the LLD round and this one become one
> answer.

# Part 4 — Logout, and what it must actually do

```
⭐⭐ LOGOUT IS A SERVER OPERATION. Deleting a client-side token
⭐   only makes the CURRENT TAB forget it.

⭐   ① ⭐ POST /auth/logout ⇒ ⭐⭐ SERVER REVOKES the refresh token
⭐      (delete the row / add to a denylist)
⭐   ② server clears the cookies (Set-Cookie with Max-Age=0)
⭐   ③ ⭐ client clears its query cache — ⭐⭐ OTHERWISE THE NEXT USER
⭐      ON THIS MACHINE SEES CACHED DATA FROM THE PREVIOUS ONE
⭐   ④ ⭐ redirect

⭐   ⭐⭐ AND ACROSS TABS: a `storage` event or BroadcastChannel, or
⭐     tab 2 happily keeps showing a logged-in UI.
```

| ⭐ Trap | |
|---|---|
| **Access token still valid after logout** | ⭐ Short expiry is the mitigation. **Say the window out loud** — "up to 15 minutes" is an honest answer. |
| **Query cache not cleared** | ⭐⭐ A genuine cross-user data leak on shared machines |
| **Redirect before revoke** | ⭐ Fire-and-forget logout that fails silently (Day 216) |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "where do you store the auth token?"**

Answer with the asymmetry, not the rule — that is what shows you understand it. **An HttpOnly cookie,
because `localStorage` is readable by any JavaScript on the page. With XSS and localStorage, the
attacker takes the token and uses it from their own machine, at leisure, until it expires — my logout
does nothing and my session list shows nothing. With XSS and an HttpOnly cookie they can act as the
user while the page is open, which is bad, but it's bounded in time and to my origin, and revoking the
session ends it. Neither is XSS-proof. The cookie bounds the blast radius, and that's the whole
argument.**

Pre-empt the obvious objection. **People say they'll just prevent XSS. I have around nine hundred
dependencies and one of them will have a bad day — defence in depth means assuming a control fails.
Choosing storage that survives XSS is free; preventing every XSS forever isn't.**

Then the flags and the honest limit. **HttpOnly, Secure, SameSite=Lax, and a tight path. Lax kills most
CSRF but not all — it still allows top-level GETs, so nothing state-changing goes on GET, and
subdomains count as same-site. For anything that matters I also check the Origin header server-side,
which is one line.**

Close on the race, because it is the part people hit in production. **When the token expires with six
requests in flight, all six get a 401 and all six try to refresh. With rotation, the first succeeds and
the other five present an invalidated token, the server reads that as theft and kills the session — so
users get logged out at random. The fix is single-flight: one refresh, everyone else awaits the same
promise, and the failure path has to reject every waiter or they hang. It's the same pattern as a
single-flight cache, one layer up.**
