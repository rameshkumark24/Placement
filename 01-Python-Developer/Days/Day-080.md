# Part 1 — ⭐⭐ `grep`, and the flags that actually matter

```bash
grep ERROR app.log                 # ⭐ the base case
grep -c ERROR app.log              # ⭐ COUNT of matching lines (not matches)
grep -n ERROR app.log              # ⭐⭐ with line numbers
grep -i error app.log              # ⭐ case-insensitive
grep -v DEBUG app.log              # ⭐⭐ INVERT — everything EXCEPT. The one people forget.
grep -r "get_user" src/            # ⭐ recursive
grep -E "4[0-9]{2}|5[0-9]{2}" log  # ⭐ extended regex (Day 076's `re`, mostly)
grep -F "a.b[c]" file              # ⭐⭐ FIXED string — no regex. For paths, versions, IPs.
grep -o "user=[0-9]*" app.log      # ⭐⭐ print only the MATCH — the extractor
grep -C 3 Traceback app.log        # ⭐⭐ 3 lines of CONTEXT — -A after, -B before
grep -l TODO -r .                  # ⭐ just the filenames
```

```
⭐⭐ THE COMBINATION THAT ANSWERS "WHAT ACTUALLY HAPPENED":
⭐   grep -n -C 5 "Traceback" app.log | less
⭐   ⇒ a Python traceback is MULTI-LINE, so a bare grep for "Error" shows you the
⭐     last line and hides the cause. ⭐⭐ -C 5 gives you the frames.
⭐   ⇒ ⭐ and -B is the one that matters for causes: the interesting line is almost
⭐        always BEFORE the error, not after it.
```

⭐ **`rg` (ripgrep) is `grep` for source code** — respects `.gitignore`, skips binaries, is faster, and
is what your editor already uses. **Learn `grep`'s flags anyway**: they are the same, and `grep` is on
every server you will ever SSH into.

# Part 2 — ⭐⭐ The one pipeline to memorise

```bash
⭐⭐ awk '{print $7}' access.log | sort | uniq -c | sort -rn | head -20
⭐  └── pick a column ──┘  └─ group ─┘  └─ count ─┘  └ rank ┘  └ top ┘
```

```
⭐⭐ THIS IS  SELECT col, COUNT(*) FROM log GROUP BY col ORDER BY 2 DESC LIMIT 20.
⭐   ⇒ ⭐⭐ uniq ONLY COLLAPSES ADJACENT LINES. That is why `sort` comes first, and
⭐        forgetting it is THE classic bug — you get counts of 1 forever.
⭐   ⇒ ⭐ sort -rn = reverse numeric. Without -n, "10" sorts before "9".
⭐   ⇒ ⭐⭐ once you own this shape you can answer: top endpoints · top IPs ·
⭐        top error messages · most-changed files in git · biggest offenders in
⭐        any list at all. ⭐ It is ONE pipeline reused forever.
```

| Tool | ⭐ Use |
|---|---|
| `cut -d, -f2,5` | ⭐ fixed delimiter, simple — ⚠️ **cannot handle quoted CSV** |
| `sort -k3 -rn` | ⭐ by the 3rd field · `-u` unique · `-h` human sizes (`10K` < `2M`) |
| `uniq -c` / `-d` | ⭐⭐ count / only duplicates — ⭐ `sort file \| uniq -d` finds dupes |
| `wc -l` | ⭐ how many |
| `head` / `tail -f` | ⭐⭐ `tail -f app.log \| grep -i error` — the live filter |
| `tr -d '\r'` | ⭐ delete characters — ⭐⭐ **the Windows CRLF fixer** |
| `column -t` | ⭐ align columns so a human can read the output |

⚠️ ⭐⭐ **Never parse real CSV with `cut`.** A quoted field containing a comma destroys it silently —
**this is the same class of error as parsing HTML with a regex** (Day 076). `csvkit`, `duckdb`, or six
lines of `csv` from the standard library.

# Part 3 — ⭐⭐ `awk` — a per-line program in one line

```
⭐⭐ awk RUNS A PROGRAM ONCE PER LINE, WITH THE FIELDS PRE-SPLIT:
⭐    $0 = the whole line · $1 $2 … = fields · NF = field count
⭐    $NF = ⭐⭐ THE LAST FIELD · NR = line number
⭐
⭐    awk 'CONDITION { ACTION }'      ⭐ either half may be omitted
```

```bash
awk '{print $1, $7}' access.log            # ⭐ two columns
awk '$9 >= 500' access.log                 # ⭐⭐ FILTER numerically — grep cannot do this
awk -F: '{print $1}' /etc/passwd           # ⭐ custom separator
awk '{s += $10} END {print s}' access.log  # ⭐⭐ SUM a column
awk '{s+=$10} END {print s/NR}' access.log # ⭐ mean
awk '$10 > 1000 {print $7}' access.log     # ⭐⭐ slow requests ⇒ which endpoints
awk '{c[$7]++} END {for (k in c) print c[k], k}' access.log | sort -rn   # ⭐⭐ group-by, in awk
awk 'length($0) > 200' app.log             # ⭐ suspiciously long lines
```

```
⭐⭐ THE ONE THAT WINS ARGUMENTS — p95 LATENCY, WITHOUT LEAVING THE TERMINAL:
⭐   awk '{print $10}' access.log | sort -n | awk '{a[NR]=$1} END {print a[int(NR*0.95)]}'
⭐
⭐   ⇒ ⭐⭐ AND THE POINT IS NOT THE ONE-LINER. It is that you should reach for the
⭐        PERCENTILE and not the MEAN. ⭐ A mean latency of 80 ms hides the 5 % of
⭐        users waiting two seconds; ⭐⭐ the mean is the number that lets a
⭐        problem live in production for months.
```

⭐⭐ **`awk` is worth exactly this much.** Fields, a condition, `sum`, and an associative array for
group-by. **Anything beyond that is a Python script** — and Python is better at it, because it has
tests, types and a debugger.

# Part 4 — ⭐ `sed`, `find` and `xargs`

```bash
sed 's/old/new/'      file       # ⭐ FIRST occurrence per line
sed 's/old/new/g'     file       # ⭐⭐ all occurrences
sed -n '100,120p'     file       # ⭐⭐ print lines 100-120 — for a huge file
sed -n '/Traceback/,/^$/p' app.log   # ⭐⭐ from a match to the next blank line
sed '/^#/d;/^$/d'     config     # ⭐ strip comments and blanks
sed -i.bak 's/a/b/g'  *.py       # ⚠️⚠️ IN-PLACE. -i.bak keeps a backup. ⭐ Test WITHOUT -i first.
```

⚠️ ⭐⭐ **Bare `sed -i` across a repository is how people lose an afternoon.** `-i` on GNU takes an
optional suffix, on macOS it *requires* an argument — the same command corrupts differently on the two
platforms. ⭐⭐ **Do it in Git-clean state, run it without `-i` first, and let `git diff` be the
review.** That is not caution, it is the reason Git exists (Days 084–088).

```bash
find . -name "*.py"                       # ⭐ by name (glob — ⭐⭐ QUOTE IT, Day 079)
find . -type f -size +100M                # ⭐⭐ the big files
find /var/log -mtime +30 -name "*.log"    # ⭐ modified more than 30 days ago
find . -type d -name __pycache__          # ⭐ directories
find . -name "*.py" -newer setup.py       # ⭐ changed since
find . -name "*.pyc" -delete              # ⭐ built-in delete
find . -name "*.py" -exec wc -l {} +      # ⭐⭐ `+` batches; `\;` runs once per file
```

```
⭐⭐ xargs — TURN LINES INTO ARGUMENTS:
⭐   find . -name "*.py" | xargs wc -l
⭐   ⇒ ⚠️⚠️ BREAKS ON FILENAMES WITH SPACES — it is Day 079's word splitting again,
⭐        one layer out. ⭐⭐ THE CORRECT FORM ALWAYS:
⭐        find . -name "*.py" -print0 | xargs -0 wc -l
⭐        ⇒ NUL-separated, and NUL is the one byte a filename cannot contain.
⭐   ⇒ ⭐ xargs -P 4    ⇒ run four at a time — ⭐⭐ a process pool in one flag
⭐        (Day 068, without the pickling).
⭐   ⇒ ⭐ xargs -n 1 -t ⇒ one per invocation, echoing the command: use it to LOOK
⭐        before you run anything destructive.
```

# Part 5 — ⭐⭐ A real incident, end to end

```
⭐⭐ "THE API GOT SLOW AT 14:00." You have access.log. Nothing else. Go.
⭐
⭐ 1. IS IT REAL, AND WHEN?               ⭐ requests per minute
⭐    awk '{print substr($4,2,17)}' access.log | uniq -c | tail -30
⭐
⭐ 2. ⭐⭐ WHAT IS THE ERROR RATE?          ⭐ status codes, ranked
⭐    awk '{print $9}' access.log | sort | uniq -c | sort -rn
⭐
⭐ 3. ⭐⭐ WHICH ENDPOINTS ARE SLOW?        ⭐ not which are POPULAR
⭐    awk '$10 > 1000 {print $7}' access.log | sort | uniq -c | sort -rn | head
⭐
⭐ 4. ONE CLIENT, OR EVERYONE?            ⭐ if one IP dominates ⇒ rate limiting, not capacity
⭐    awk '{print $1}' access.log | sort | uniq -c | sort -rn | head
⭐
⭐ 5. ⭐⭐ DID THE ERRORS START BEFORE THE SLOWNESS?   ⭐⭐ this decides cause vs symptom
⭐    grep " 500 " access.log | head -3      ⇒ compare the timestamp with step 1
⭐
⭐ 6. ⭐ WHAT DOES THE APP SAY AT THAT MINUTE?
⭐    grep -C 5 "14:0[0-5]" app.log | grep -i -C 5 error
⭐
⭐⭐ ⇒ FIVE PIPELINES, EACH THE SAME SHAPE, AND YOU NOW HAVE A HYPOTHESIS RATHER
⭐     THAN AN OPINION. ⭐ That is the whole skill. The tools are incidental.
```

⭐⭐ **And the discipline that makes it count: write the numbers down as you go.** "p95 went from 90 ms
to 2.1 s at 14:02, 500s started at 13:58, one endpoint is 80 % of the slow requests" is an
investigation. **"It feels slow" is a feeling.** Day 100 turns this into a method.

```
⭐⭐ WHEN TO STOP AND OPEN AN EDITOR — say this in an interview, it reads as judgement:
⭐   · you need a JOIN across two files          ⇒ Python (or duckdb over the logs)
⭐   · you need state across lines beyond a sum  ⇒ Python
⭐   · the pipeline is longer than a line        ⇒ Python, or a script (Day 083)
⭐   · ⭐⭐ ANYONE WILL RUN IT TWICE              ⇒ Python, with a test
⭐   ⇒ ⭐ shell for EXPLORING, Python for ANYTHING THAT REPEATS. The mistake in
⭐        both directions is real: a 60-line awk program, or a 40-line Python
⭐        script to count lines.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`uniq -c` without `sort` first** | ⭐⭐ `uniq` only collapses **adjacent** lines. |
| `sort` without `-n` on numbers | ⭐ Lexicographic: `10` before `9`. |
| ⭐ Reporting a **mean** latency | ⭐⭐ Use p95/p99 — the mean hides the tail. |
| ⭐ `xargs` without `-print0`/`-0` | ⭐⭐ Breaks on spaces in filenames. |
| `cut` on real CSV | ⭐⭐ Quoted commas destroy it silently. |
| ⭐⭐ **`sed -i` across a repo, untested** | ⭐ Run without `-i`, in a clean tree, review `git diff`. |
| Unquoted glob in `find -name` | ⭐ The shell expands it first (Day 079). |
| ⭐ `grep Error` for a Python failure | ⭐⭐ Tracebacks are multi-line — `-C 5`, and look **before**. |
| `find -exec cmd \;` on 10k files | ⭐ 10k processes. Use `+` or `xargs`. |
| Writing 40 lines of Python to count | ⭐ One pipeline. |
| ⭐ Writing 60 lines of `awk` | ⭐⭐ Write Python. It has tests and a debugger. |

## Interview questions

**Q: Give me the top ten slowest endpoints from an access log.**
> `awk '$10 > 1000 {print $7}' access.log | sort | uniq -c | sort -rn | head`. The shape is the thing
> worth knowing rather than the specific columns: pick a field, sort so equal values are adjacent,
> `uniq -c` to count, sort numerically descending, take the head. It's `GROUP BY … ORDER BY count
> DESC LIMIT 10` with different syntax. The one trap is that `uniq` only collapses adjacent lines, so
> leaving out the first `sort` gives you counts of one forever and it looks like it worked.

**Q: Why would you report p95 rather than mean latency?**
> Because the mean is dominated by the many fast requests and hides the tail entirely. A service with
> an 80 ms mean can have 5% of users waiting two seconds, and those users are the ones who complain
> and leave. The mean is the number that lets a problem live in production for months. I'd quote p95
> and p99, and I'd also look at the count — a p99 over a hundred requests isn't a measurement, it's
> an anecdote.

**Q: What's wrong with `find . -name "*.py" | xargs grep TODO`?**
> `xargs` splits its input on whitespace, so a filename containing a space becomes two arguments and
> `grep` fails on both halves — it's shell word splitting reappearing one layer out. The fix is
> `-print0` on `find` and `-0` on `xargs`, which makes them communicate in NUL-separated records, and
> NUL is the one byte a filename can't contain. `find -exec … +` avoids the problem entirely by not
> going through a text channel at all.

**Q: When do you stop using the shell and write Python?**
> When it needs a join across two sources, when it needs state beyond a running total, when it's
> longer than one line, or when anyone will run it more than once. Shell is for exploring — the
> feedback loop is unbeatable and the throwaway cost is zero. Python is for anything that repeats,
> because it can have tests, types and a debugger. The mistake goes both ways: a 60-line `awk`
> program that nobody can modify, and a 40-line Python script to count lines in a file.

## 🎙️ Articulation drill

Record two minutes: **"Users report the API is slow. You have SSH and an access log. Walk me
through the first five minutes."**

⭐ **Do not start with a tool.** Start with the shape of the investigation: **"first I want to know
whether it is real and when it started, then whether it is everywhere or one endpoint, then whether
errors preceded the slowness or followed it — because that decides cause versus symptom."**

⭐⭐ **Then be concrete, because vagueness is what this question is testing for:** *"requests per
minute by timestamp to find the onset. Status codes grouped and ranked for the error rate. Then the
one that matters — filter to requests over a second, group by endpoint, rank — because the slowest
endpoint and the most popular endpoint are usually different, and total time spent is what I'd
actually act on. Then group by client IP, because if one address is 80 % of traffic it's a rate-limit
problem, not a capacity problem."*

⭐⭐ **Close on the two things that make it senior rather than competent:** *"I'd quote p95, not the
mean, because the mean hides exactly the users who are complaining. And I'd write the numbers down as
I go — 'p95 went from 90 ms to 2.1 s at 14:02, 500s started four minutes earlier' is a hypothesis
someone else can check. 'It feels slow' is not."*
