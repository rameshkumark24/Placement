# Day 024

**L-024** · ⭐⭐ **Names, bindings and references** — assignment binds a name; there are no variables

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `x = 5` does not put 5 into a box called x. It makes the name `x` refer
> to an object that already exists.** Python has no variables in the C sense — no named storage
> location whose contents you overwrite. It has **names** and **bindings**.
>
> ⭐ This is the day that makes the mutable-default bug (Day 025), the closure bug (Day 030) and
> "why did my list change?" all obvious instead of mysterious.

---

# Part 1 — ⭐⭐ The correct mental model

```
⭐ WRONG (the C/Java model, and it will mislead you constantly):
⭐    x ┌──────┐
⭐      │  5   │   "a box named x containing 5"
⭐      └──────┘

⭐⭐ RIGHT:
⭐    NAMESPACE (a dict)              OBJECTS (on the heap)
⭐    ┌───────────────┐                ┌──────────────┐
⭐    │ "x" ──────────┼───────────────▶│ int  5       │ ⭐ refcount 1
⭐    │ "y" ──────────┼───────────────▶│ (the SAME 5) │ ⭐ refcount 2
⭐    └───────────────┘                └──────────────┘
⭐   ⇒ ⭐⭐ x = 5 means: put the key "x" in the namespace dict, pointing at that object.
```

```python
x = 5
y = x            # ⭐⭐ NOT a copy. A second name for the SAME object.
x is y           # True
id(x) == id(y)   # True

x = 6            # ⭐⭐ REBINDING — "x" now points somewhere else. y is untouched.
y                # 5
```

```
⭐⭐ TWO OPERATIONS THAT LOOK ALIKE AND ARE NOT:
⭐   ⭐⭐ REBINDING:  x = something   ⇒ changes WHICH object the NAME refers to.
⭐                                     ⇒ ⭐ affects only this name, in this namespace.
⭐   ⭐⭐ MUTATION:   x.append(1)     ⇒ changes THE OBJECT ITSELF.
⭐                   x[0] = 9          ⇒ ⭐⭐ VISIBLE THROUGH EVERY NAME BOUND TO IT.
⭐
⭐ ⇒ ⭐⭐ EVERY ALIASING BUG IN PYTHON IS SOMEONE EXPECTING (1) AND GETTING (2).
```

# Part 2 — ⭐⭐ Function arguments: call by sharing

```python
def rebind(lst):
    lst = [9, 9]           # ⭐⭐ rebinds the LOCAL name only. Caller sees nothing.

def mutate(lst):
    lst.append(9)          # ⭐⭐ mutates the shared object. Caller SEES IT.

a = [1]
rebind(a);  a    # [1]        ⭐ unchanged
mutate(a);  a    # [1, 9]     ⭐⭐ changed
```

```
⭐⭐ "IS PYTHON PASS BY VALUE OR PASS BY REFERENCE?" — THE ANSWER IS: NEITHER.
⭐   ⭐ pass by value     ⇒ the callee gets a COPY of the object     ⇒ ✗ Python does not copy
⭐   ⭐ pass by reference ⇒ the callee can REBIND THE CALLER'S NAME ⇒ ✗ Python cannot do this
⭐   ⭐⭐ Python passes THE OBJECT REFERENCE, BY VALUE.
⭐        ⇒ ⭐⭐ called CALL BY SHARING (or "pass by assignment"):
⭐          · you CAN mutate the object the caller gave you
⭐          · you CANNOT change which object the caller's name points at
⭐
⭐ ⭐⭐ THE PRECISE ONE-LINER: "the parameter name is bound to the same object as the argument."
```

⭐⭐ **This is a top-five Python interview question and the "neither" answer is what distinguishes a
real answer from a memorised one** — followed by the two-line demonstration above, which takes ten
seconds and settles it.

⚠️ ⭐ **The practical rule that falls out: do not mutate your arguments.** A function that quietly
appends to the list it was given is a function whose caller has to read its body to use it safely.
**Return a new object, or name the mutation in the function's name** (`sort` vs `sorted`,
`reverse` vs `reversed` — the standard library already tells you which is which).

# Part 3 — ⭐ Namespaces are dicts, and `del` removes a name

```python
x = 1
globals()["x"]           # ⭐ 1 — module globals ARE a dict
globals()["y"] = 99      # ⭐⭐ creates the name y. This actually works.

del x                    # ⭐⭐ removes the NAME from the namespace.
                         # ⭐ It does NOT delete the object — it decrements the refcount (Day 026).
```

```python
a = [1, 2, 3]
b = a
del a          # ⭐ the list is still alive: b refers to it
b              # [1, 2, 3]
```

⭐⭐ **`del x` is `del namespace["x"]`.** The object dies only when *nothing* refers to it, which is
Day 026's subject. ⭐ **`del lst[0]` is different** — that is `__delitem__`, a mutation of the object.

```python
# ⭐ Multiple binding, and the swap that needs no temporary:
a, b = 1, 2
a, b = b, a         # ⭐⭐ the RIGHT side is evaluated to a tuple FIRST, then unpacked
p = q = []          # ⚠️ ⭐⭐ p and q are the SAME list. This bites people.
p.append(1); q      # [1]

first, *rest = [1, 2, 3]     # ⭐ star unpacking — 1, [2, 3]
```

# Part 4 — ⭐⭐ Where this bites, in real code

```python
# ⭐ 1. The shared-default matrix (Day 025 takes this further)
row = [0] * 3
grid = [row] * 3          # ⚠️⚠️ ⭐⭐ THREE REFERENCES TO ONE LIST
grid[0][0] = 1
grid                      # ⭐⭐ [[1,0,0], [1,0,0], [1,0,0]]  — every "row" is the same object
grid = [[0] * 3 for _ in range(3)]   # ⭐ CORRECT — a new list per iteration
```

⚠️ ⭐⭐ **The `[[0]*n]*m` grid bug appears in DSA problems constantly** — dynamic programming tables,
adjacency matrices, game boards. **It produces a plausible-looking wrong answer rather than a crash,
which is the worst possible failure mode under a clock.**

```python
# ⭐ 2. Default arguments, previewed — the binding happens ONCE, at def time (Day 025)
def add(item, target=[]):     # ⚠️⚠️ ⭐⭐ ONE list, shared by every call, forever
    target.append(item); return target

# ⭐ 3. The class attribute that is shared by every instance
class Dog:
    tricks = []               # ⚠️ ⭐⭐ ONE list on the CLASS
    def learn(self, t): self.tricks.append(t)     # ⭐⭐ mutates the CLASS's list
# ⇒ every Dog shares every trick. ⭐ FIX: assign it in __init__, per instance.

# ⭐ 4. Returning an internal collection
class Cart:
    def items(self): return self._items    # ⚠️ ⭐ the caller can now mutate your internals
    def items_safe(self): return list(self._items)   # ⭐ or tuple(...) — a copy
```

⭐ **Rebinding inside a container works the way you would now predict:**

```python
lst = [[1], [2]]
inner = lst[0]
inner.append(9)       # ⭐ lst is [[1, 9], [2]]  — mutation, visible
inner = [7]           # ⭐⭐ lst is UNCHANGED     — rebinding, local to the name `inner`
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"`x = 5` stores 5 in x"** | ⭐⭐ It binds the name `x` to an existing object. |
| ⭐ Expecting `b = a` to copy | ⭐⭐ It never copies. Two names, one object. |
| ⭐⭐ **"Python is pass by reference"** | ⭐⭐ Call by sharing — mutate yes, rebind no. |
| Mutating arguments silently | ⭐ Return a new object, or say so in the name. |
| ⭐⭐ `[[0]*n]*m` | ⭐⭐ One row, m references. Use a comprehension. |
| `p = q = []` expecting two lists | ⭐ One list, two names. |
| Mutable class attributes | ⭐⭐ Shared by every instance. Assign in `__init__`. |
| Returning internal lists | ⭐ The caller can mutate your state. Copy it. |
| Thinking `del x` frees memory | ⭐ It unbinds a name; the object dies at refcount zero. |
| Confusing `del x` with `del lst[0]` | ⭐ One removes a name; one mutates an object. |

## Interview questions

**Q: Is Python pass by value or pass by reference?**
> Neither, and the honest answer is worth giving precisely. The parameter name is bound to the same
> object the caller passed — that's call by sharing. So I can mutate the object and the caller sees
> it, but if I rebind the parameter name I've only changed my local namespace and the caller's name
> is untouched. Two three-line functions demonstrate it: one that appends, one that reassigns.

**Q: What's the difference between rebinding and mutating?**
> Rebinding changes which object a name points at, and only affects that one name in that one
> namespace. Mutation changes the object itself, so it's visible through every name bound to it —
> other locals, list elements, dict values, attributes on other objects. Practically every
> "why did my data change?" bug is someone expecting rebinding and getting mutation.

**Q: `grid = [[0] * 3] * 3` — what's wrong?**
> The outer multiplication copies the *reference* three times, so all three rows are the same list
> object. Writing `grid[0][0] = 1` changes what looks like every row. It shows up constantly in DP
> tables and adjacency matrices, and the nasty part is that it produces a wrong answer rather than an
> error. The fix is a comprehension, which evaluates the inner expression once per iteration.

**Q: What does `del x` do?**
> Removes the binding from the namespace — it's effectively `del namespace["x"]`. The object itself
> is only reclaimed when nothing refers to it, so if another name still points at it, the object is
> fine. That's different from `del lst[0]`, which calls `__delitem__` and mutates the list.

**Q: Why is a mutable class attribute a problem?**
> Because it belongs to the class, not to any instance, so every instance shares one object. A
> `tricks = []` on the class means one dog learning a trick teaches every dog. Reading the attribute
> finds it on the class; mutating it mutates the shared one. Assigning a new value in `__init__`
> creates a per-instance binding instead, which is what people intended.
