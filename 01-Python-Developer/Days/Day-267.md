# Day 267 🏗️

**P-267** · 🏗 **File uploads** — ⭐⭐ presigned URLs, and the eight ways this goes wrong

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: an upload is not a form field. It is an untrusted binary from a stranger
> that you are about to store under a name they chose and serve back to a browser — and every one of
> those four clauses is its own vulnerability class.**
>
> ⭐ `fieldwork` technicians photograph completed work. ⭐⭐ That one sentence brings in memory,
> bandwidth, a state machine, a reconciliation job, content sniffing, stored XSS and a quota.

---

# Part 1 — ⭐⭐ Why the obvious upload is wrong

```python
@app.post("/jobs/{job_id}/photos")
async def upload(job_id: UUID, file: UploadFile):
    data = await file.read()              # ⭐⭐ ALL OF IT, IN MEMORY
    s3.put_object(Bucket=..., Body=data)  # ⭐ and now send it AGAIN
```

```
⭐⭐ FOUR COSTS, AND THE FOURTH IS THE ONE THAT SURPRISES PEOPLE:

⭐ ① ⭐ A 200 MB VIDEO IS 200 MB OF RSS. Four concurrent uploads
⭐     and the pod is OOM-killed — ⭐⭐ TAKING EVERY OTHER IN-FLIGHT
⭐     REQUEST ON THAT PROCESS WITH IT.

⭐ ② ⭐⭐ THE BYTES CROSS THE NETWORK TWICE: client → you → S3.
⭐     Double the time, double the egress bill, and your app's
⭐     bandwidth becomes the ceiling on upload throughput.

⭐ ③ ⭐ AN APP WORKER IS HELD FOR THE WHOLE CLIENT UPLOAD. A
⭐     technician on rural 3G occupies it for 90 seconds doing
⭐     nothing but waiting on a socket.

⭐ ④ ⭐⭐ YOUR REQUEST TIMEOUT BECOMES YOUR FILE SIZE LIMIT —
⭐     and it is a DIFFERENT LIMIT FOR EVERY CLIENT, because it
⭐     depends on their connection speed. ⭐ "Uploads fail for
⭐     some users sometimes" is one of the worst bug reports
⭐     there is, and this is what produces it.
```

```
⭐ ⇒ ⭐⭐ THE FIX IS STRUCTURAL, NOT A TUNING PARAMETER:
⭐   ***THE BYTES MUST NEVER TOUCH YOUR API PROCESS.***
```

# Part 2 — ⭐⭐ The presigned flow, and the state machine

```
⭐⭐ THREE CALLS. YOUR API HANDLES TWO OF THEM, AND NEITHER
⭐   CARRIES A SINGLE BYTE OF THE FILE:

⭐   ① POST /uploads            ⭐ you: authorise, create a row,
⭐                                 return a SIGNED PUT URL
⭐   ② PUT https://s3...        ⭐⭐ CLIENT → STORAGE, DIRECTLY.
⭐                                 Your app is not involved at all.
⭐   ③ POST /uploads/{id}/complete
⭐                              ⭐ you: verify, attach to the job
```

```
⭐⭐ WHAT THE SIGNATURE MUST PIN — MISS ANY OF THESE AND YOU HAVE
⭐   HANDED OUT A WRITEABLE BUCKET:

⭐   ⭐⭐ THE KEY — GENERATED BY THE SERVER:
⭐        tenants/{tenant_id}/2026/08/{uuid}.bin
⭐        ⇒ ⭐⭐ NEVER THE CLIENT'S FILENAME. Not sanitised, not
⭐          escaped — ***NOT USED AT ALL*** as a path component.
⭐        ⇒ ⭐ The tenant prefix is what makes Part 3's
⭐          reconciliation and Part 6's quota possible.

⭐   ⭐ A SIZE CEILING — `content-length-range`, 1 byte .. 20 MB.
⭐        ⇒ ⭐⭐ A PLAIN PRESIGNED `PUT` CANNOT ENFORCE THIS.
⭐          A presigned POST policy can. ⭐⭐ SO A BARE PRESIGNED
⭐          PUT LETS THE HOLDER UPLOAD FIVE TERABYTES TO YOUR
⭐          BUCKET, ON YOUR BILL.

⭐   ⭐ THE CONTENT TYPE, pinned and required to match on the PUT.

⭐   ⭐ AN EXPIRY OF MINUTES, NOT DAYS. ⭐⭐ A presigned URL is a
⭐        bearer credential: whoever holds it has your permission.
```

```
⭐⭐ AND THE STATE MACHINE, WHICH IS THE PART PEOPLE SKIP:
⭐   pending ──► uploaded ──► scanned ──► ready
⭐      │            │            └────► rejected
⭐      └────────────┴──► expired (swept, Part 3)

⭐   ⭐⭐ NOTHING IS VISIBLE TO ANOTHER USER BEFORE `ready`.
⭐     ⭐ Which means: a row exists from step ①, so you can list
⭐       "uploading…" in the UI; and the reference from `job` to
⭐       `photo` is only created at `ready`, so a half-finished
⭐       upload is never attached to anything.
```

# Part 3 — ⭐⭐ The confirm step you cannot trust

```
⭐⭐ STEP ③ IS OPTIONAL FROM THE CLIENT'S POINT OF VIEW.
⭐   ⭐ The app crashes. The tab closes. The tunnel drops between
⭐     the PUT and the POST. The technician walks into a lift.
⭐   ⇒ ⭐⭐ YOU NOW HAVE TWO KINDS OF ORPHAN, AND BOTH COST MONEY:
⭐     ⭐ BYTES IN THE BUCKET THAT NO ROW POINTS TO — invisible,
⭐       billed monthly, forever.
⭐     ⭐ A `pending` ROW WITH NO BYTES — shows as "uploading…"
⭐       in the UI until the end of time.
```

```
⭐⭐ TWO MECHANISMS, AND YOU WANT BOTH:

⭐ ① ⭐⭐ THE STORAGE EVENT — S3 → SNS/SQS → your worker.
⭐      ⇒ ⭐⭐ THIS IS THE AUTHORITATIVE SIGNAL, because it comes
⭐        FROM THE SYSTEM THAT HOLDS THE BYTES, not from the
⭐        client that claims to have sent them.
⭐      ⇒ ⭐ Treat `complete` as a latency optimisation (so the
⭐        UI updates instantly) and the event as the truth.
⭐      ⭐ At-least-once, so the handler is idempotent (Day 265).

⭐ ② ⭐ THE SWEEPER (Day 264), running nightly, in both directions:
⭐      ⭐ rows in `pending` older than 24 h ⇒ delete the row
⭐      ⭐⭐ OBJECTS UNDER THE TENANT PREFIX WITH NO ROW ⇒ delete
⭐        the object — ⭐⭐ AND THIS IS ONLY POSSIBLE BECAUSE THE
⭐        KEY WAS SERVER-GENERATED WITH YOUR OWN IDENTIFIERS IN
⭐        IT (Part 2). ⭐ Exactly the Day 263 lesson: you can only
⭐        reconcile against a foreign system if you put your own
⭐        reference into it at the time you wrote.
⭐      ⭐ Plus a bucket lifecycle rule on the `pending/` prefix
⭐        as the belt-and-braces version.
```

# Part 4 — ⭐⭐ Validating a file you did not create

```
⭐⭐ FIVE THINGS THAT ARE NOT VALIDATION:
⭐   ① ⭐ THE EXTENSION — renamed in one second
⭐   ② ⭐ THE `Content-Type` HEADER — chosen by the client
⭐   ③ ⭐ THE FILENAME — see below; it is worse than useless
⭐   ④ ⭐ A CLIENT-SIDE CHECK — a suggestion to honest users
⭐   ⑤ ⭐⭐ "IT OPENED IN PILLOW" — ***so do polyglots***. A file
⭐        can be a valid GIF and a valid ZIP and a valid PHP
⭐        script simultaneously.
```

```
⭐⭐ WHAT ACTUALLY WORKS, IN ORDER:
⭐   ⭐ SNIFF THE MAGIC BYTES (`python-magic`) and compare against
⭐     an ALLOWLIST of types. ⭐ Allowlist, never blocklist.
⭐   ⭐⭐ RE-ENCODE IMAGES. Decode, then write out a fresh file.
⭐     ⇒ ⭐⭐ THIS IS THE ONLY RELIABLE SANITISATION THERE IS: it
⭐       drops EXIF, drops appended payloads, drops polyglot
⭐       structure, and normalises the format. ⭐ The output is
⭐       a file YOU created, which is the whole point.
⭐   ⭐ Cap decoded dimensions (`Image.MAX_IMAGE_PIXELS`).
⭐     ⇒ ⭐⭐ A 10 KB PNG CAN DECODE TO 40 GB OF PIXELS. The size
⭐       limit you enforced was on the COMPRESSED bytes; the
⭐       decompression bomb is what it does afterwards.
⭐   ⭐ Strip EXIF explicitly — ⭐⭐ PHONE PHOTOS CARRY GPS, and
⭐     serving them back republishes a customer's home address.
```

```
⭐⭐ THREE FORMATS THAT ARE CODE, NOT DATA:
⭐   ⭐⭐ SVG IS HTML. `<script>`, `<foreignObject>`, XXE via
⭐     external entities. ⇒ ⭐ Refuse it, or rasterise it, or
⭐     serve it only from a separate origin.
⭐   ⭐ PDF contains JavaScript and can call out to a network.
⭐   ⭐ ZIP/archive ⇒ zip bombs and path traversal INSIDE the
⭐     archive (`../../` in member names) if you ever extract.

⭐⭐ AND THE FILENAME, WHICH YOU STORE AS A ***LABEL*** IN A COLUMN
⭐   AND NEVER AS A PATH:
⭐   ⭐ `../../../etc/passwd` · NUL bytes · `CON`/`PRN` on Windows
⭐   ⭐⭐ THE ONE PEOPLE HAVE NEVER SEEN: a Unicode
⭐     right-to-left override — `invoice<U+202E>gnp.exe` ⭐⭐ RENDERS
⭐     TO THE USER AS `invoiceexe.png`. ⭐ Which is why you also
⭐     escape it on the way OUT, not just on the way in.
```

# Part 5 — ⭐⭐ Serving it back without hosting an attack

```
⭐⭐ THE PUBLIC BUCKET: "it's only photos" — ⭐ until support
⭐   attaches a signed contract, until a technician photographs a
⭐   customer's ID, until the key turns out to be guessable, until
⭐   someone finds the bucket listing enabled.
⭐   ⇒ ⭐⭐ BUCKETS ARE PRIVATE. Always. No exceptions for images.

⭐⭐ SERVE VIA A SHORT-LIVED PRESIGNED GET, MINTED ONLY AFTER YOUR
⭐   OWN AUTHORISATION CHECK HAS RUN (Day 259).
⭐   ⇒ ⭐ The check runs in YOUR code, on YOUR predicate, and only
⭐     then do you hand out a URL.
```

```
⭐⭐ FOUR TRAPS IN SERVING:
⭐   ① ⭐ PRESIGNED GET URLs GET SHARED — pasted into Slack,
⭐     leaked in `Referer`, cached by a CDN. ⭐⭐ A SHORT EXPIRY
⭐     IS THE ONLY CONTROL YOU HAVE, so make it minutes.
⭐   ② ⭐⭐ SERVING USER-CONTROLLED HTML OR SVG FROM YOUR OWN
⭐     DOMAIN IS STORED XSS with access to your cookies. ⇒ ⭐ A
⭐     separate asset domain, or `Content-Disposition: attachment`
⭐     plus `X-Content-Type-Options: nosniff`.
⭐   ③ ⭐ SET THE RESPONSE CONTENT-TYPE FROM ***YOUR*** SNIFFED
⭐     VALUE, not from what was stored at upload time.
⭐   ④ ⭐ `Cache-Control: private` on every signed URL response
⭐     (Day 266), or a shared cache serves one customer's photo
⭐     to the next requester of that path.
```

# Part 6 — ⭐⭐ Derivatives, quotas, and deletion

```
⭐⭐ THUMBNAILS ARE ASYNC WORK (Day 265), AND THE KEY IS
⭐   DETERMINISTIC:  {original_key}/thumb_400.jpg
⭐   ⇒ ⭐⭐ SO A REDELIVERED TASK OVERWRITES RATHER THAN CREATING
⭐     A SECOND FILE. ⭐ At-least-once plus a deterministic key
⭐     equals idempotent, with no extra bookkeeping.

⭐ ⭐ ON UPLOAD vs ON FIRST REQUEST:
⭐   ⭐ on upload  ⇒ predictable cost, some work wasted on files
⭐     nobody ever views
⭐   ⭐ on request ⇒ ⭐⭐ A STAMPEDE RISK (Day 266): a popular job
⭐     page opened by forty people generates the same thumbnail
⭐     forty times. ⭐ Needs the same per-key lock.
```

```
⭐⭐ QUOTAS ARE ENFORCED AT ***SIGNING*** TIME, NOT AT UPLOAD TIME:
⭐   ⭐ At signing you can refuse BEFORE the bytes exist.
⭐   ⭐⭐ AFTER UPLOAD, THE STORAGE IS ALREADY CONSUMED AND
⭐     ALREADY BILLED — you are deleting something you paid for,
⭐     and an abuser can loop that all day.
⭐   ⇒ ⭐ Keep a per-tenant `bytes_used` counter, updated when an
⭐     upload reaches `ready` and when a file is deleted, and
⭐     reconcile it nightly against the bucket (Part 3).
```

```
⭐⭐ AND DELETION, WHICH IS FOUR DELETES, NOT ONE:
⭐   ⭐ deleting the ROW does not delete the OBJECT
⭐   ⭐ the DERIVATIVES (thumb_400, thumb_1200) are separate keys
⭐   ⭐ the CDN still has a copy until its TTL expires
⭐   ⭐⭐ AND IF BUCKET VERSIONING IS ON, "DELETE" WROTE A DELETE
⭐     MARKER AND THE OBJECT IS STILL THERE — which is excellent
⭐     for ransomware recovery and ⭐⭐ FATAL FOR A GDPR ERASURE
⭐     REQUEST YOU JUST TOLD A CUSTOMER YOU HAD COMPLETED.
⭐   ⇒ ⭐ Day 187's soft-delete cost list, in a second system.
⭐     ⭐⭐ WRITE THE ERASURE PATH DOWN, and test it, because
⭐       "we deleted it" is a legal claim.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `await file.read()` in the handler | Whole file in RAM; four uploads OOM the pod and kill unrelated requests. |
| Proxying bytes through the API | Two network hops, a held worker, and your bandwidth as the ceiling. |
| Relying on a request timeout as a size limit | It's a different limit per client connection speed. |
| Using the client's filename as the key | Path traversal, collisions, and unpredictable keys you can't reconcile. |
| A bare presigned PUT with no size policy | The holder can upload terabytes on your bill. |
| Presigned URLs valid for days | It's a bearer credential; make it minutes. |
| No upload state machine | Half-finished uploads become visible, or attach to records. |
| Trusting the client's `complete` call | The tab closed. Use the storage event as the truth. |
| No orphan sweeper | Bytes with no row bill forever; rows with no bytes say "uploading…" forever. |
| Client-generated keys | Reconciliation becomes impossible after the fact (Day 263). |
| Validating by extension or `Content-Type` | Both are client-chosen. Sniff magic bytes against an allowlist. |
| "It opened in Pillow, so it's an image" | Polyglots are valid in several formats at once. |
| No decoded-pixel cap | A 10 KB PNG decodes to 40 GB. Your size limit was on compressed bytes. |
| Storing images without re-encoding | Re-encoding is the only reliable sanitisation, and it drops EXIF. |
| Serving SVG from your own origin | SVG is HTML: stored XSS with your cookies. |
| A public bucket "just for photos" | Someone will attach a contract, and keys are guessable. |
| Serving the stored content-type back | Serve your own sniffed value with `nosniff`. |
| Generating thumbnails on request with no lock | Forty viewers, forty identical renders (Day 266). |
| Enforcing quotas after upload | The storage is already consumed and billed. Refuse at signing. |
| Deleting the row and calling it deletion | Object, derivatives, CDN copy, and version markers all survive. |

## Interview questions

**Q: How do file uploads work in your system?**

> The bytes never touch my API. The client asks for an upload, I authorise it, create a row in
> `pending`, and return a presigned URL with a server-generated key, a size range, a pinned
> content-type and a five-minute expiry. The client PUTs directly to storage, then calls a complete
> endpoint. The reason is that the naive version holds a worker for the whole client upload, buffers
> the file in memory, sends the bytes twice, and makes the request timeout into a per-client file size
> limit — which is what produces "uploads fail for some users sometimes".

**Q: Why can't you trust the complete call?**

> Because it's optional from the client's point of view — the tab closes, the tunnel drops, the phone
> loses signal between the PUT and the POST. That leaves two kinds of orphan: bytes in the bucket
> that no row points to, which bill monthly forever, and pending rows with no bytes, which say
> "uploading…" in the UI forever. So the authoritative signal is the storage event, because it comes
> from the system that actually holds the bytes, and the complete call is just a latency optimisation.
> Plus a nightly sweeper in both directions — and that's only possible because the key was
> server-generated with my own identifiers in it, which is the same prerequisite as payment
> reconciliation.

**Q: How do you validate an uploaded file?**

> Not by extension, content-type header, filename, or a client-side check — all four are attacker-
> controlled — and not by "it opened in Pillow", because polyglot files are valid in several formats
> simultaneously. I sniff magic bytes against an allowlist, cap the decoded pixel count because a ten
> kilobyte PNG can decode to forty gigabytes and my size limit only covered the compressed bytes, and
> then re-encode images, which is the only reliable sanitisation available: the stored file is one I
> created, so appended payloads, polyglot structure and EXIF GPS are all gone.

**Q: What's wrong with a public bucket?**

> It's fine right up until it isn't, and the transition is invisible. Someone attaches a signed
> contract, or a technician photographs an ID, or the keys turn out to be guessable. Buckets are
> private and I mint short-lived presigned GETs after my own authorisation check runs. The traps are
> that signed URLs get pasted into chat and captured in `Referer` headers, so expiry is the only real
> control; serving user-controlled SVG or HTML from my own domain is stored XSS with access to my
> cookies; and every signed response needs `Cache-Control: private` or a shared cache hands one
> customer's photo to the next requester.

**Q: A customer invokes their right to erasure. What do you delete?**

> Four things, not one. The database row, the object, every derivative under its key prefix, and the
> CDN's cached copy. And if bucket versioning is on — which it usually is, deliberately, for
> ransomware recovery — my delete wrote a delete marker and the object is still there, so erasure
> needs a version-aware delete. That path gets written down and tested, because "we deleted it" is a
> legal claim, not a code comment.

## Today's build

1. ⭐⭐ Write the naive upload endpoint, upload a 200 MB file, and watch the process RSS. Then delete it.
2. ⭐ Build `POST /uploads`: authorise, create the `pending` row, return a presigned URL with a server-generated key.
3. ⭐⭐ Try to enforce a size limit on a plain presigned PUT. Fail. Switch to a POST policy with `content-length-range` and prove a 5 GB upload is refused.
4. ⭐ Implement the full state machine including `rejected`, and assert nothing before `ready` is visible in any list endpoint.
5. ⭐⭐ Wire the storage event to a worker and make the handler idempotent. Deliver it twice and assert one outcome.
6. ⭐ Kill the client between PUT and complete. Confirm you have an orphan, then write the sweeper that finds it.
7. ⭐⭐ Write the reverse sweeper: list the tenant prefix, find objects with no row, and delete them. Note why the key format made this possible.
8. ⭐ Upload a `.png` that is actually a PHP script and confirm your magic-byte check rejects it.
9. ⭐⭐ Build a decompression bomb and confirm `MAX_IMAGE_PIXELS` stops it. Measure RSS with the cap removed.
10. ⭐ Re-encode every accepted image and confirm the EXIF GPS tag is gone from the stored file.
11. ⭐⭐ Upload an SVG containing `<script>`, serve it from your own origin in a scratch branch, and confirm it executes. Then refuse SVG.
12. ⭐ Upload a file named with a right-to-left override and check how it renders in your UI.
13. ⭐⭐ Make the bucket private and serve via presigned GET after the authorisation predicate. Test cross-tenant access.
14. ⭐ Generate thumbnails asynchronously with a deterministic key; redeliver the task and confirm no duplicate object.
15. ⭐⭐ Enforce a per-tenant byte quota at signing time and reconcile the counter against the bucket nightly.
16. ⭐⭐ Write and test the erasure path: row, object, all derivatives, CDN purge, and versioned delete.

## 🎙️ Articulation drill

**Three minutes: "Design file upload for a mobile app."**

Lead with the structural decision and its reason: **the bytes never touch my API.** Give the four
costs of the obvious version and dwell on the fourth, because it's the one that shows experience —
**your request timeout becomes a file size limit that differs per client**, which is exactly the bug
report nobody can reproduce. Then the three-call flow, and be specific about what the signature pins:
a server-generated key, a size range that a bare presigned PUT cannot enforce, a pinned content type,
and an expiry of minutes because **a presigned URL is a bearer credential**. Then the part most people
skip: **the complete call is optional from the client's point of view**, so the storage event is the
truth and the complete call is a latency optimisation — plus a sweeper in both directions, which is
only possible because you put your own identifiers in the key, exactly like payment reconciliation.
Then validation: extension, content-type, filename and client checks are all attacker-controlled, and
"it opened in Pillow" fails on polyglots — so sniff magic bytes, cap decoded pixels because the size
limit only covered compressed bytes, and **re-encode, because the only file you can trust is one you
wrote yourself**. Close on serving: private buckets and short-lived signed GETs minted after your own
authorisation predicate, SVG refused because SVG is HTML, and deletion as four deletes — row, object,
derivatives, CDN — with the versioning trap, **because "we deleted it" is a legal claim.**
