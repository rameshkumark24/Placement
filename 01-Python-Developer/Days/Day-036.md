# Day 036

**L-036** · ⭐ **`set` and `frozenset`** — hashing again, and set algebra as an algorithm

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: converting a list to a set turns O(n) membership into O(1), and that
> single substitution is the most common "make it faster" answer in a Python DSA round.**
>
> ⭐ Sets are Day 035's hash table with the values removed. **The interesting part is not the
> implementation — it is learning to see set *algebra* as a way to express an algorithm** instead of
> writing loops.

---

# Part 1 — ⭐ The structure

```
⭐ A set is an open-addressed hash table (Day 035) storing keys only.
⭐   ⇒ ⭐⭐ NO compact layout ⇒ ⭐⭐ SETS ARE NOT ORDERED. Iteration order depends on hashes,
⭐        the insertion history, and PYTHONHASHSEED — ⚠️ so it can differ between RUNS.
⭐   ⇒ ⭐ a small extra "smalltable" of 8 slots is embedded in the object, so tiny sets
⭐     need no separate allocation — which is why getsizeof(set()) is a surprising 216 bytes.
```

⚠️ ⭐⭐ **Never rely on set iteration order.** It looks stable within one run and changes between
runs, which is the worst kind of bug: **your test passes locally and fails in CI**, and it fails
*intermittently*.

| Operation | ⭐ Cost |
|---|---|
| ⭐⭐ `x in s` | ⭐⭐ **O(1) average** |
| `s.add(x)`, `s.discard(x)` | O(1) |
| `s \| t` (union) | O(len(s) + len(t)) |
| ⭐ `s & t` (intersection) | ⭐⭐ **O(min(len(s), len(t)))** — it iterates the smaller |
| `s - t` (difference) | O(len(s)) |
| `s ^ t` (symmetric difference) | O(len(s) + len(t)) |
| `s <= t` (subset) | O(len(s)) |

⭐ **`x in s` for a `list` is O(n) and for a `set` is O(1)** — and that is the whole reason this day
exists.

```python
# ⭐⭐ THE SUBSTITUTION, and it is worth internalising as a reflex:
seen = []                       # ⚠️ ⭐⭐ `x in seen` is O(n) ⇒ the loop is O(n²)
for x in items:
    if x not in seen: seen.append(x)

seen = set()                    # ⭐⭐ O(1) ⇒ the loop is O(n)
for x in items:
    if x not in seen: seen.add(x)
```

# Part 2 — ⭐⭐ Set algebra as an algorithm

```python
a, b = {1,2,3}, {2,3,4}

a | b        # ⭐ {1,2,3,4}   union            — a.union(b)
a & b        # ⭐ {2,3}       intersection     — a.intersection(b)
a - b        # ⭐ {1}         difference       — a.difference(b)
a ^ b        # ⭐ {1,4}       symmetric diff   — "in exactly one"
a <= b       # subset;  a < b proper subset;  a >= b superset
a.isdisjoint(b)             # ⭐ no overlap — cheaper than building `a & b`
```

```
⭐⭐ THE POINT: THESE REPLACE LOOPS, AND THEY REPLACE THEM WITH A STATEMENT OF INTENT.

⭐ "which users are in both cohorts?"          ⇒ a & b
⭐ "who did we add since yesterday?"           ⇒ today - yesterday
⭐ "who left?"                                 ⇒ yesterday - today
⭐ ⭐⭐ "what CHANGED?"                          ⇒ ⭐⭐ today ^ yesterday
⭐ "does this user have ANY required role?"    ⇒ not roles.isdisjoint(required)
⭐ "does this user have ALL required roles?"   ⇒ ⭐ required <= roles
⭐ "which requested fields are not allowed?"   ⇒ ⭐⭐ requested - ALLOWED   (a real validator)
```

⭐⭐ **The last one is worth stealing.** Validating a request body, a query-string filter, or a config
file becomes one line: `unknown = set(payload) - ALLOWED; if unknown: raise ...`. **It is shorter,
faster and clearer than any loop, and it produces a good error message for free.**

⭐ **The method forms accept any iterable; the operators require sets.**

```python
a | [4, 5]           # ⭐ TypeError
a.union([4, 5])      # ⭐ fine — and this asymmetry catches people
```

## ⭐ Mutating forms

```python
s |= t   /  s.update(t)
s &= t   /  s.intersection_update(t)
s -= t   /  s.difference_update(t)
s.add(x) / s.discard(x)      # ⭐ discard never raises
s.remove(x)                  # ⭐⭐ raises KeyError if absent — the difference IS the point
s.pop()                      # ⚠️ ⭐ an ARBITRARY element (not "the first")
```

# Part 3 — ⭐ `frozenset`, and what sets cannot hold

```python
fs = frozenset([1, 2, 3])
{fs: "value"}                 # ⭐⭐ hashable ⇒ usable as a dict key or inside another set
{{1,2}}                       # ⭐ TypeError: unhashable type: 'set'
{frozenset({1,2})}            # ⭐ fine
```

```
⭐⭐ SET MEMBERS MUST BE HASHABLE — the same Day 029 contract, for the same reason:
⭐   the position of an element is determined by its hash, so a mutating member would
⭐   sit in the wrong bucket and become unreachable.
⭐   ⇒ ⭐ so: no lists, no dicts, no sets. ⇒ ⭐⭐ tuples and frozensets instead.
```

```python
# ⭐ THE COMMON CONVERSION — deduplicating rows or coordinates:
seen = set()
for row in rows:
    key = tuple(row)                 # ⭐⭐ a list is unhashable; a tuple is not
    if key in seen: continue
    seen.add(key)

visited = {(r, c)}                   # ⭐⭐ grid coordinates as tuples — the standard DSA idiom

# ⭐ Deduplicating groups where ORDER within the group does not matter:
unique_pairs = {frozenset(p) for p in pairs}     # ⭐ {1,2} and {2,1} collapse
```

⭐ **`frozenset` is also the right cache key** for "a set of permissions", "a set of enabled
features", "a set of tags" — anything you want to memoise on (Day 051).

# Part 4 — ⭐⭐ Deduplication, and the ordering trap

```python
# ⚠️ ⭐⭐ THE CLASSIC ONE-LINER THAT LOSES YOUR ORDER:
unique = list(set(items))            # ⭐⭐ ORDER IS DESTROYED, and unpredictably

# ⭐⭐ ORDER-PRESERVING DEDUPLICATION — the idiom to memorise:
unique = list(dict.fromkeys(items))  # ⭐⭐ dicts keep insertion order (Day 035). O(n).
```

⭐⭐ **`list(dict.fromkeys(items))` is one of the highest-value one-liners in Python**, and knowing
*why* it works — dicts are ordered, sets are not — proves you understood Day 035 rather than
memorising a trick.

```python
# ⭐ When the items are unhashable, or you need a key function:
def dedupe(items, key=lambda x: x):
    seen = set()
    for x in items:
        k = key(x)
        if k not in seen:
            seen.add(k)
            yield x                  # ⭐ a generator — constant memory (Day 047)
```

| ⭐ Task | ⭐⭐ Reach for |
|---|---|
| "Have I seen this?" | ⭐⭐ `set` |
| "How many times?" | ⭐ `Counter` (Day 038) |
| ⭐ Dedupe, order irrelevant | `set(items)` |
| ⭐⭐ Dedupe, **keep order** | ⭐⭐ `list(dict.fromkeys(items))` |
| Common / missing / changed between two collections | ⭐⭐ `&`, `-`, `^` |
| A set as a dict key or set member | `frozenset` |
| Membership on a **sorted** list without a set | `bisect` (Day 039) |

⚠️ ⭐ **Sets are not free.** `set()` costs 216 bytes empty and each element carries hash-table
overhead, so **converting a 10-element list to a set for one lookup is slower than the linear scan.**
The crossover is small — around a handful of elements — but the rule is: **build a set when you will
query it more than once.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Relying on set iteration order** | ⭐⭐ Unordered, and varies between runs. Tests fail in CI. |
| ⭐⭐ **`list(set(x))` to dedupe** | ⭐⭐ Destroys order. `list(dict.fromkeys(x))`. |
| ⭐ `x in list` in a loop | ⭐⭐ O(n²). Build a set once. |
| Putting a list in a set | ⭐ Unhashable — use a tuple. |
| `{}` for an empty set | ⭐⭐ That is an empty **dict**. Use `set()`. |
| `a \| [1,2]` | ⭐ Operators need sets; methods take any iterable. |
| `remove` where `discard` was meant | ⭐ `remove` raises on a missing element. |
| Expecting `pop()` to be ordered | ⭐ It is arbitrary. |
| Building a set for a single lookup | ⭐ Not worth it below a handful of elements. |
| Forgetting `isdisjoint` | ⭐ Cheaper than materialising an intersection. |

## Interview questions

**Q: Why would you convert a list to a set?**
> Membership. `x in list` is a linear scan; `x in set` is a hash lookup, so a loop that checks
> membership goes from quadratic to linear. It's the single most common optimisation in a Python
> coding round — "have I seen this before" is a set, not a list. The caveat is that building the set
> is O(n) itself and each element carries hash-table overhead, so it pays off when I'll query it more
> than once, not for a single lookup on a tiny list.

**Q: Are sets ordered?**
> No, and this is worth being precise about because dicts are. Dicts got the compact layout in 3.6,
> which stores entries densely in insertion order, and that became a guarantee in 3.7. Sets never got
> that layout — they're a plain open-addressed table of keys — so iteration order depends on hashes
> and insertion history, and since string hashing is randomised per process it can differ between
> runs. Relying on it gives you a test that passes locally and fails intermittently in CI.

**Q: How do you deduplicate a list while preserving order?**
> `list(dict.fromkeys(items))`. It's O(n), it uses the fact that dicts preserve insertion order, and
> it's a single expression. `list(set(items))` is the version people reach for first and it silently
> scrambles the order. If the items aren't hashable or I need a key function, a small generator with
> a `seen` set does the same thing in constant memory.

**Q: What can't go in a set?**
> Anything unhashable — lists, dicts, sets. The reason is the same contract as dict keys: the
> element's position is determined by its hash, so a member that mutates would end up in the wrong
> bucket and become unreachable, present but not findable. The conversions are a tuple instead of a
> list and a `frozenset` instead of a set, which is also how you build a set of sets or use a set of
> permissions as a cache key.

**Q: Give me a case where set algebra replaces a loop.**
> Validating input fields: `unknown = set(payload) - ALLOWED_FIELDS`, and if it's non-empty I raise
> with exactly those names in the message. Or permissions: `required <= user_roles` for "has all of
> them" and `not user_roles.isdisjoint(required)` for "has any". Each of those is a loop with a flag
> variable written as a statement of intent, and the diff case — what changed between yesterday's
> and today's set — is symmetric difference, which is genuinely awkward to write by hand.

## 🎙️ Articulation drill

Record two minutes: **"Given two lists of user IDs, tell me who is new, who left, and who stayed."**

⭐ Answer it as set algebra rather than as loops, and say the complexity as you go: **`today -
yesterday` is new, `yesterday - today` is churned, `today & yesterday` stayed, and `today ^
yesterday` is everything that changed** — each O(n) with O(1) membership underneath, against the
O(n²) you would get comparing lists.

⭐ Then the practical caveat, unprompted: **the results are unordered, so if the output needs to be
stable I sort it or use `dict.fromkeys` — sets are not ordered, and that has bitten me in a test that
passed locally and failed in CI.**

⭐⭐ **Then generalise, because that is what makes it an answer rather than a trick:** *"the useful
habit is recognising when a question is really a set question. 'Which requested fields aren't
allowed', 'does this user have all the required roles', 'what changed between two deploys' — all of
those are one operator, and writing them as loops with flag variables is how they become bugs."*
