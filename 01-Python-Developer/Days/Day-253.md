# Part 3 — ⭐⭐ Settings that fail at boot

```python
# ⭐ Day 150, applied. The whole point is that a misconfiguration is a
#   crash at start-up, not a 500 at 3 a.m.
class Settings(BaseSettings):
    model_config = SettingsConfigDict(extra="forbid")   # ⭐⭐ a typo in
                                                        #    an env var
                                                        #    is a CRASH,
                                                        #    not silence
    env: Literal["local", "ci", "staging", "prod"]
    database_url: PostgresDsn
    redis_url: RedisDsn
    jwt_private_key: SecretStr                # ⭐ never in a traceback
    access_token_ttl_s: int = Field(900, ge=60, le=3600)
    refresh_token_ttl_d: int = Field(30, ge=1, le=90)
    s3_bucket: str
    otel_endpoint: HttpUrl | None = None

    @model_validator(mode="after")
    def prod_is_stricter(self):
        if self.env == "prod":
            # ⭐⭐ A CONFIG *VALUE*, NOT AN ENVIRONMENT *CHECK* (Day 179).
            #    `if env == "prod"` scattered through the codebase means
            #    prod is the ONE environment you never test.
            if self.otel_endpoint is None:
                raise ValueError("otel_endpoint required in prod")
        return self

settings = Settings()      # ⭐⭐ AT IMPORT. Fails the container, not the
                           #    request.
```

```
⭐⭐ AND THE THREE THINGS THAT GO IN `.env.example` AND NOWHERE ELSE:
⭐   ⭐ every variable, with a comment and a safe dummy value
⭐   ⭐⭐ NOTHING REAL. ⭐ Day 150: secrets leak in git history and in
⭐     Docker layers for the same structural reason — both are
⭐     append-only records of everything that was ever there.
⭐   ⭐ a `make check-env` that diffs `.env.example` against `Settings`
⭐     so a new setting cannot be added without documenting it.
```

# Part 4 — ⭐⭐ Migrations, health, and shutdown

```
⭐⭐ ALEMBIC — three things configured TODAY, not later:
⭐   ① ⭐⭐ `lock_timeout` AND `statement_timeout` IN `env.py` (Day 196),
⭐      so a migration behind a slow reader fails the DEPLOY instead of
⭐      taking the SITE down. ⭐ In `env.py`, so no author can forget.
⭐   ② ⭐ the naming convention on `MetaData` (Day 187), so constraints
⭐      have names you can drop portably. ⭐⭐ Retrofitting this renames
⭐      every constraint in the database.
⭐   ③ ⭐ `alembic check` in CI (Day 173's `makemigrations --check`
⭐      equivalent) — ⭐⭐ a model change with no migration is a BUILD
⭐      FAILURE, not a surprise at deploy time.
```

```python
# ⭐⭐ THREE PROBES, DEFINED BY CONSEQUENCE (Day 149) — and the mistake
#    that causes a fleet-wide restart loop is checking the database in
#    liveness.
@app.get("/health/live")     # ⭐⭐ CHECKS NOTHING IT CANNOT FIX BY
async def live():            #    RESTARTING
    return {"status": "ok"}

@app.get("/health/ready")    # ⭐ "should I receive traffic?"
async def ready():
    await db.execute(text("SELECT 1"))      # ⭐ a dependency I need
    # ⭐⭐ AND NOT: the payment provider. A third party in readiness
    #    removes ALL your capacity when THEY have an outage (Day 149).
    return {"status": "ready"}

@app.get("/health/startup")  # ⭐ slow boot: migrations, warm caches
```

```
⭐⭐ SHUTDOWN, AND THE ORDERING RACE PEOPLE DISCOVER IN PRODUCTION:
⭐   ⭐ SIGTERM arrives and the endpoint removal propagates through the
⭐     load balancer at the same time — ⭐⭐ so the pod stops accepting
⭐     while traffic is still arriving. ⭐ The fix is a `preStop: sleep 5`
⭐     (Day 149), and it belongs in the manifest you write today.
⭐   ⭐ Then: stop accepting, finish in-flight (bounded), close the pool,
⭐     flush metrics and traces. ⭐⭐ `tini` or `--init` so PID 1 reaps
⭐     children and forwards signals (Day 151).
```

# Part 5 — ⭐⭐ The four rules, mechanically enforced

```
⭐⭐ A RULE ENFORCED BY DISCIPLINE SURVIVES UNTIL THE FIRST BUSY WEEK.
⭐   THESE FOUR ARE BUILD FAILURES FROM TODAY.

⭐ ① ⭐⭐ THE DOMAIN IMPORTS NOTHING.
⭐    ⭐ `import-linter` with a layered contract, in CI:
⭐        layers = api | services | infra ; domain
⭐    ⭐⭐ Without this, `domain/job.py` imports the session "just for a
⭐      moment" in week three, and the layering is over.
⭐ ② ⭐⭐ NO N+1 MAY BE MERGED.
⭐    ⭐ `lazy="raise"` on every relationship (Day 136) — ⭐⭐ so a lazy
⭐      load is an EXCEPTION, not a silent 400-query page.
⭐    ⭐ Plus a per-endpoint query-count ceiling in tests (Day 141),
⭐      wired today with one dummy endpoint so the harness exists.
⭐ ③ ⭐⭐ NO ENDPOINT WITHOUT A TENANT SCOPE.
⭐    ⭐ RLS makes it structurally impossible (Day 252), ⭐ and a test
⭐      that enumerates the router table asserting every route depends
⭐      on the authenticated principal catches the one you register
⭐      without thinking. ⭐⭐ Day 184 #12: middleware runs before
⭐      routing, so TEST THE ROUTE TABLE.
⭐ ④ ⭐⭐ NO MERGE WITHOUT CI GREEN.
⭐    ⭐ Branch protection on. ⭐ It is a two-minute setting and it is
⭐      the reason the other three hold.

⭐⭐ AND THE ANTI-RULE: ***DO NOT ADD A COVERAGE THRESHOLD TODAY.*** Day
⭐   281 does it properly. ⭐ A 90% gate on an empty repo produces
⭐   assertion-free tests for a month and teaches you to game it.
```

```yaml
# ⭐ CI — five jobs, and the order is the point (Day 154)
jobs:
  lint:     ruff check . && ruff format --check .
  types:    mypy app/                       # ⭐ strict on domain/ at least
  arch:     lint-imports                    # ⭐⭐ rule ①
  test:     pytest -q --maxfail=1           # ⭐ with a real Postgres
                                            #   service, never SQLite
                                            #   (Day 172: it silently
                                            #   ignores FOR UPDATE)
  migrate-check: alembic check
  build:    docker build .                  # ⭐⭐ BUILD ONCE
  deploy:   # ⭐⭐ PROMOTE THE SAME DIGEST (Day 154). Never rebuild
            #    per environment, or staging and prod are different
            #    artefacts and you have tested nothing.
```

# Part 6 — ⭐ The image and the first deploy

```dockerfile
# ⭐ Day 151, condensed to what matters
FROM python:3.12-slim AS builder
WORKDIR /app
COPY pyproject.toml uv.lock ./            # ⭐⭐ LOCKFILE FIRST — the
RUN uv sync --frozen --no-dev             #    layer cache is ordering
COPY . .

FROM python:3.12-slim
RUN useradd -m app                        # ⭐ non-root
COPY --from=builder /app /app             # ⭐⭐ multi-stage: build tools
USER app                                  #    never reach production
ENV PYTHONUNBUFFERED=1                    # ⭐ or logs vanish on crash
EXPOSE 8000
ENTRYPOINT ["tini", "--"]                 # ⭐ PID 1
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
# ⭐⭐ EXEC FORM. Shell form means your process is not PID 1 and never
#    receives SIGTERM (Day 151).
```

```
⭐⭐ TODAY'S DEFINITION OF DONE — all six, or the day is not finished:

⭐      internet, ⭐⭐ not from your laptop
⭐   ② the migration ran there, and `alembic current` proves it
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Deploying at the end | Nine possible causes arrive bundled, under time pressure. |
| Treating the skeleton as throwaway | It's the deployment path you'll use for forty days. |
| Settings read with `os.getenv` at point of use | A missing variable becomes a 500 at 3 a.m. instead of a boot failure. |
| No `extra="forbid"` on settings | A typo'd env var is silently ignored. |
| `if env == "prod"` scattered in the code | Prod becomes the one environment you never test. Config values, not checks. |
| `lock_timeout` in individual migrations | It belongs in `env.py`; a control each author must remember isn't one. |
| No constraint naming convention from day one | Retrofitting renames every constraint in the database. |
| No `alembic check` in CI | A model change with no migration surfaces at deploy time. |
| A database check in liveness | The database blips, Kubernetes kills every pod, and you're in a restart loop. |
| A third party in readiness | Their outage removes all of your capacity. |
| No `preStop` sleep | Termination races endpoint propagation and you drop live requests. |
| Shell-form `CMD` | Your process isn't PID 1 and never receives SIGTERM. |
| Testing against SQLite | It silently ignores `FOR UPDATE` — you'd prove nothing about locking. |
| Rebuilding the image per environment | Staging and production are different artefacts; you tested neither. |
| Layering enforced by code review | It survives until the first busy week. Use `import-linter` in CI. |
| A coverage threshold on an empty repo | A month of assertion-free tests and a habit of gaming the number. |
| Never watching CI fail | An untested gate is a decoration. |

## Interview questions

**Q: Why deploy an empty application on day one?**

> Because deployment problems otherwise arrive bundled with feature problems. If the first deploy is
> on day thirty-five, a failure could be the Dockerfile, the migration, the settings, the health check,
> the network, a secret, the port, the entrypoint or the code — and you're debugging nine things at
> once, at the end, under pressure. Deployed on day one, each is a five-minute problem in isolation and
> every subsequent deploy is a diff against something known to work. There's a second reason specific
> to a portfolio project: a live URL is the single most valuable artefact, because "here's the link"
> ends a category of interview question that no amount of description reaches. And empirically, if it
> isn't deployed on day one the probability it's ever deployed drops a lot.

**Q: What do you enforce mechanically rather than by convention?**

> Four things, because a rule enforced by discipline survives until the first busy week. Layering, with
> `import-linter` in CI asserting the domain imports nothing — otherwise someone imports the session
> into a domain module "just for a moment" in week three and the boundary is gone. No N+1, via
> `lazy="raise"` so a lazy load raises rather than silently issuing four hundred queries, plus
> per-endpoint query-count ceilings in tests. Tenant scoping, structurally through row-level security
> plus a test that walks the route table and asserts every route depends on the authenticated
> principal — because middleware runs before routing, so the route table itself needs testing. And
> branch protection, which is a two-minute setting and the reason the other three actually hold. The
> thing I deliberately *don't* add on day one is a coverage threshold, because a ninety-percent gate on
> an empty repository produces a month of assertion-free tests and teaches you to game the number.

**Q: How do you configure health checks?**

> By consequence rather than by convention. Liveness checks nothing it can't fix by restarting —
> specifically not the database, because if the database blips for thirty seconds the orchestrator
> kills every pod simultaneously, and when the database recovers you're in a restart loop you built
> yourself. Readiness checks the dependencies you genuinely can't serve without, so the database yes,
> and deliberately not a third-party payment provider — putting one in readiness means their outage
> removes all of your capacity. Startup for slow boots so liveness doesn't kill you mid-migration. And
> alongside that, the shutdown ordering: SIGTERM and load-balancer endpoint removal race each other, so
> a `preStop` sleep of a few seconds is what stops you dropping live requests on every deploy, and
> `tini` so PID 1 forwards signals and reaps children.

**Q: What's in your CI pipeline and in what order?**

> Lint, types, architecture, tests, a migration check, build once, then promote. The ordering is
> cheapest-and-most-likely-to-fail first, so feedback is fast. Two details I'd defend. The architecture
> job — `lint-imports` — because it's the only way a layering rule survives; and `alembic check`, which
> makes a model change without a migration a build failure rather than a deploy-time surprise. Tests
> run against real Postgres in a service container, never SQLite, because SQLite silently ignores
> `SELECT FOR UPDATE` and testing locking against it proves nothing. And the build-once-promote rule:
> the same image digest goes to staging and production. Rebuilding per environment means they're
> different artefacts and whatever you verified in staging isn't what shipped.

**Q: What does "done" look like for the skeleton day?**

> Six things. A public URL where `/health/ready` returns 200 — from the internet, not from my laptop.
> The migration having run there, provable with `alembic current`. A structured JSON log line for that
> request, with a request id, visible in whatever collects logs. A `/metrics` endpoint with request
> count and duration. CI having failed on purpose at least once, by breaking the architecture rule
> deliberately and watching it go red — because an untested gate is a decoration. And the deploy being
> one command or one merge, because anything that needs a runbook is something I'll stop doing by week
> two, which defeats the entire purpose.
