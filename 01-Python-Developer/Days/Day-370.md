# Part 1 — ⭐⭐ The shape, end to end

```
⭐⭐ THE FULL PATH FROM COMMIT TO PRODUCTION:

⭐   push/PR
⭐     ├─ ⭐ static     (lint · format · types · secret scan)
⭐     ├─ ⭐ test       (unit · integration · patch coverage)
⭐     └─ ⭐ security   (dependency audit · SAST)
⭐            │  ⭐⭐ ALL THREE IN PARALLEL — WALL TIME IS THE
⭐            │     SLOWEST, NOT THE SUM
⭐            ▼
⭐        ⭐ build      (image · SBOM · scan · sign · push)
⭐            ▼
⭐        ⭐ migrate-staging   ⭐⭐ SEPARATE JOB, SAME IMAGE
⭐            ▼
⭐        ⭐ deploy-staging (by digest)
⭐            ▼
⭐        ⭐ smoke        ⭐⭐ THE GATE THAT DECIDES PROMOTION
⭐            ▼
⭐        ⭐ [approval]   ⭐ environment protection
⭐            ▼
⭐        ⭐ migrate-prod → deploy-prod (⭐⭐ SAME DIGEST) → verify

⭐⭐ THE FOUR STRUCTURAL RULES:
⭐   ① ⭐⭐ ONE ARTEFACT, BUILT ONCE, PROMOTED BY DIGEST. ⭐ The
⭐      image deployed to production is byte-identical to the
⭐      one staging tested.
⭐   ② ⭐⭐ MIGRATIONS ARE A SEPARATE JOB BEFORE THE ROLLOUT
⭐      (Day 366), USING THE SAME IMAGE WITH A DIFFERENT
⭐      COMMAND.
⭐   ③ ⭐ Every deploy step is idempotent and re-runnable.
⭐   ④ ⭐⭐ THE ROLLBACK PATH IS EXERCISED, NOT DOCUMENTED. ⭐ If
⭐      you have never run it, you do not have it.
```

# Part 2 — ⭐⭐ The gates, and what each has actually caught

```
⭐⭐ A GATE THAT HAS NEVER CAUGHT ANYTHING IS EITHER NEW OR
⭐   USELESS, ⭐ and you should know which. ⭐⭐ KEEP A ONE-LINE
⭐   NOTE PER GATE OF THE LAST REAL THING IT STOPPED — ⭐ it is
⭐   the only honest way to justify the time it costs.

⭐   GATE                    WHAT IT CATCHES THAT NOTHING ELSE DOES
⭐   ─────────────────────────────────────────────────────────────
⭐   ⭐ ruff format --check   Nothing. ⭐⭐ IT ENDS AN ARGUMENT,
⭐                           WHICH IS ITS ENTIRE JOB.
⭐   ⭐ ruff check            Unused imports, mutable defaults,
⭐                           ⭐ bare `except`, ⭐⭐ `assert` IN
⭐                           PRODUCTION CODE (stripped under -O).
⭐   ⭐ mypy --strict         ⭐⭐ `None` REACHING SOMETHING THAT
⭐                           CANNOT TAKE IT — the single most
⭐                           common Python production error.
⭐   ⭐ gitleaks              ⭐⭐ THE INCIDENT WITH THE SHORTEST
⭐                           TIME-TO-EXPLOIT. Seconds to run.
⭐   ⭐ pytest (unit)         Logic.
⭐   ⭐ pytest (integration)  ⭐⭐ THE THINGS MOCKS LIE ABOUT:
⭐                           constraints, transactions, SQL that
⭐                           only fails on real Postgres.
⭐   ⭐ patch coverage        New untested code, ⭐ without
⭐                           punishing whoever touched legacy.
⭐   ⭐ pip-audit             Known CVEs in ***your*** deps.
⭐   ⭐ trivy image           CVEs in the base image.
⭐   ⭐ ⭐⭐ MIGRATION LOCK     A `ALTER TABLE` THAT WOULD HAVE
⭐                           LOCKED A 40M-ROW TABLE FOR EIGHT
⭐                           MINUTES. ⭐⭐ THE MOST EXPENSIVE
⭐                           SINGLE INCIDENT THIS LIST PREVENTS.
⭐   ⭐ ⭐⭐ AUTH MATRIX        AN ENDPOINT SHIPPED WITH NO
⭐                           AUTHORISATION CHECK AT ALL.
⭐   ⭐ smoke tests           A deploy that started but cannot
⭐                           serve — ⭐⭐ WRONG CONFIG, MISSING
⭐                           SECRET, UNREACHABLE DEPENDENCY.
```

```python
# ⭐⭐ THE MIGRATION LOCK CHECK — ~40 LINES, PREVENTS AN OUTAGE
DANGEROUS = {
    "ADD COLUMN ... NOT NULL" : "without a default, rewrites the table",
    "ALTER COLUMN TYPE"       : "full rewrite under ACCESS EXCLUSIVE",
    "ADD CONSTRAINT ... CHECK": "use NOT VALID, then VALIDATE",
    "CREATE INDEX"            : "use CREATE INDEX CONCURRENTLY",
    "DROP COLUMN"             : "expand/contract: not in this release",
}

def check(sql: str, table_rows: int) -> list[str]:
    problems = []
    for pattern, why in DANGEROUS.items():
        if _matches(sql, pattern):
            if table_rows > 1_000_000:            # ⭐⭐ SIZE DECIDES
                problems.append(f"{pattern}: {why} ({table_rows:,} rows)")
    return problems
# ⭐⭐ RUN IT AGAINST A RESTORED COPY OF THE PRODUCTION SCHEMA,
# ⭐   WITH REAL ROW COUNTS — ⭐ because the same statement is
# ⭐   harmless on 500 rows and an outage on 40 million.
```

# Part 3 — ⭐⭐ Smoke tests: the gate that decides promotion

```
⭐⭐ NOT A SECOND TEST SUITE. ⭐ Five to ten assertions against
⭐   the ***deployed*** environment, ⭐⭐ ANSWERING ONE QUESTION:
⭐   ***DID THIS DEPLOY PRODUCE A WORKING SYSTEM?***

⭐⭐ WHAT TO ASSERT — ⭐ and each one has a specific failure it
⭐   catches:
⭐   ① ⭐⭐ `/healthz` RETURNS 200 ***AND REPORTS THE EXPECTED
⭐      GIT SHA.*** ⭐ Without the sha, you are testing the
⭐      ***old*** version and calling the deploy a success.
⭐      ⭐⭐ THIS IS THE SINGLE MOST IMPORTANT LINE IN THE
⭐      SMOKE SUITE.
⭐   ② ⭐ `/readyz` reports every dependency reachable.
⭐   ③ ⭐ One authenticated read on real data ⇒ catches a
⭐      missing secret or a broken database URL.
⭐   ④ ⭐ One write and its rollback (a create then delete) ⇒
⭐      ⭐⭐ CATCHES READ-ONLY CREDENTIALS AND A MIGRATION THAT
⭐      DID NOT APPLY.
⭐   ⑤ ⭐ One background job enqueued and observed to complete.
⭐   ⑥ ⭐⭐ THE SCHEMA VERSION MATCHES WHAT THE CODE EXPECTS —
⭐      ⭐ catches a rollout that beat its migration.
⭐   ⑦ ⭐ p99 of a known endpoint under a tiny load is within
⭐      budget ⇒ catches a catastrophic regression.

⭐⭐ THE RULES:
⭐   ⭐ ⭐⭐ UNDER 60 SECONDS. ⭐ It sits between staging and
⭐     production and everybody waits for it.
⭐   ⭐ ⭐⭐ ZERO FLAKINESS TOLERATED. ⭐ A flaky smoke test blocks
⭐     deploys, so it gets disabled within a week and then the
⭐     gate is gone (Day 368).
⭐   ⭐ Run it against ***production*** too, immediately after
⭐     deploying — ⭐⭐ AND WIRE THE FAILURE TO AN AUTOMATIC
⭐     ROLLBACK.
⭐   ⭐ ⭐⭐ USE A DEDICATED TEST ACCOUNT AND CLEAN UP AFTER
⭐     YOURSELF — ⭐ smoke tests that leave rows behind become a
⭐     data-quality problem nobody traces back.
```

# Part 4 — ⭐⭐ Deployment, and what "deployed" means

```
⭐⭐ THE DEPLOY STEP IS NOT `kubectl apply` OR `aws ecs
⭐   update-service`. ⭐⭐ IT IS THAT ***PLUS WAITING FOR THE
⭐   ROLLOUT TO CONVERGE AND FAILING IF IT DOES NOT.***
⭐   ⭐ `kubectl rollout status --timeout=5m` ⇒ ⭐ non-zero exit
⭐     if it stalls.
⭐   ⭐ `aws ecs wait services-stable`.
⭐   ⇒ ⭐⭐ WITHOUT THE WAIT, YOUR PIPELINE GOES GREEN WHILE THE
⭐     NEW PODS ARE CRASH-LOOPING, ⭐ and the first person to
⭐     notice is a customer.

⭐⭐ THE FOUR THINGS A DEPLOY JOB MUST DO:
⭐   ① ⭐ Deploy the ***digest***, not a tag (Day 362).
⭐   ② ⭐⭐ WAIT FOR CONVERGENCE WITH A TIMEOUT.
⭐   ③ ⭐ Run smoke tests against the deployed target.
⭐   ④ ⭐⭐ ROLL BACK AUTOMATICALLY ON FAILURE, AND SAY SO
⭐      LOUDLY. ⭐ A silent rollback is a mystery next morning.

⭐⭐ AND THE ROLLBACK ITSELF:
⭐   ⭐ ⭐⭐ CODE ROLLS BACK; ***DATA DOES NOT*** (Day 283).
⭐   ⇒ ⭐ Which is why migrations must be
⭐     backward-compatible — ⭐⭐ THE ROLLBACK RE-RUNS THE
⭐     ***PREVIOUS IMAGE*** AGAINST THE ***NEW SCHEMA***, AND
⭐     THAT MUST WORK.
⭐   ⇒ ⭐⭐ SO THE RULE, CONCRETELY: ***ADDITIVE MIGRATION →
⭐     DEPLOY → (a release later) DESTRUCTIVE MIGRATION.*** ⭐ A
⭐     `DROP COLUMN` in the same release as the code that stopped
⭐     using it makes rollback impossible.
⭐   ⭐ ⭐⭐ AND NEVER AUTO-RUN `alembic downgrade` IN A ROLLBACK.
⭐     ⭐ Down-migrations are rarely tested and often lossy;
⭐     ⭐⭐ ROLLING BACK CODE WHILE ***LEAVING THE SCHEMA
⭐     FORWARD*** IS THE CORRECT AND SAFE MOVE.
```

# Part 5 — ⭐ Environments and approval

```
⭐⭐ THREE ENVIRONMENTS IS THE USEFUL NUMBER:
⭐   ⭐ ***PREVIEW / PR*** — ephemeral, per pull request,
⭐     ⭐⭐ AND IT MUST DESTROY ITSELF ON MERGE OR CLOSE, OR YOU
⭐     ACCUMULATE COST AND CONFUSION.
⭐   ⭐ ***STAGING*** — ⭐⭐ SHAPED LIKE PRODUCTION: same
⭐     topology, same migrations, same secrets ***mechanism***
⭐     (different values), ⭐ and ideally a scrubbed copy of
⭐     production data.
⭐   ⭐ ***PRODUCTION*** — protected, approved, audited.

⭐⭐ THE HONEST NOTE ABOUT STAGING: ⭐⭐ IT ONLY CATCHES THINGS
⭐   IF IT ***RESEMBLES*** PRODUCTION. ⭐ A staging environment
⭐   with one replica, 100 rows and no TLS proves almost nothing
⭐   (Day 365's gap list, one level up). ⭐⭐ THE THREE THINGS
⭐   THAT MATTER MOST ARE: MORE THAN ONE REPLICA, A REALISTIC
⭐   DATA VOLUME, AND THE SAME PROXY AND TLS PATH.

⭐⭐ APPROVAL GATES — ⭐ and the trap:
⭐   ⭐ Useful for: ⭐ a compliance requirement, ⭐ a
⭐     high-blast-radius change, ⭐ a first deploy of the day
⭐     after an incident.
⭐   ⭐ ⭐⭐ HARMFUL WHEN IT BECOMES A RUBBER STAMP: an approval
⭐     nobody reads is a delay pretending to be a control, ⭐ and
⭐     it slows the ***rollback*** as well as the deploy —
⭐     ⭐⭐ WHICH IS THE WRONG WAY ROUND, BECAUSE ROLLBACK IS THE
⭐     SAFE DIRECTION.
⭐   ⇒ ⭐⭐ SO: NEVER GATE A ROLLBACK. ⭐ Gate forward deploys if
⭐     you must; make going back instantaneous and unblocked.

⭐⭐ AND THE PREVIEW-ENVIRONMENT JUDGEMENT: ⭐ they are
⭐   wonderful for frontend and API-contract review, ⭐⭐ AND
⭐   EXPENSIVE IF EACH ONE NEEDS ITS OWN DATABASE. ⭐ A shared
⭐   database with a per-PR schema is the usual compromise.
```

# Part 6 — ⭐⭐ Making the pipeline observable

```
⭐⭐ A PIPELINE THAT FAILS SILENTLY IS A PIPELINE PEOPLE ROUTE
⭐   AROUND.

⭐⭐ WHAT TO EMIT:
⭐   ⭐ ⭐⭐ A DEPLOYMENT MARKER TO YOUR MONITORING SYSTEM, WITH
⭐     THE COMMIT SHA AND THE DIGEST. ⭐ Then every latency graph
⭐     has a vertical line on it, ⭐⭐ AND "DID SOMETHING CHANGE
⭐     AT 14:32?" IS ANSWERED IN ONE GLANCE INSTEAD OF FIFTEEN
⭐     MINUTES OF ARCHAEOLOGY. ⭐ This is the highest-value
⭐     integration in the whole day.
⭐   ⭐ A changelog line to the team channel: what, who, which
⭐     commit, ⭐ and a link to roll back.
⭐   ⭐ The four DORA numbers, derived from pipeline data rather
⭐     than self-reported.
⭐   ⭐ ⭐⭐ AND A ***DEPLOY-TO-ALERT CORRELATION***: if an alert
⭐     fires within N minutes of a deploy, say so in the alert.
⭐     ⭐ It is the first question anyone asks anyway.

⭐⭐ AND THE POST-DEPLOY VERIFICATION WINDOW:
⭐   ⭐ ⭐⭐ WATCH ERROR RATE AND LATENCY FOR 5–15 MINUTES AFTER
⭐     A DEPLOY AND ROLL BACK AUTOMATICALLY IF THEY BREACH.
⭐   ⇒ ⭐ That is a canary in its simplest form (Day 371), ⭐ and
⭐     it is available to anyone with a metrics system and a
⭐     scripted rollback — ⭐⭐ NO SERVICE MESH REQUIRED.
```

# Part 7 — ⭐ Failure modes of the pipeline itself

```
⭐⭐ ① ***THE PIPELINE IS A SINGLE POINT OF FAILURE.***
⭐   ⭐ CI is down ⇒ ⭐⭐ YOU CANNOT DEPLOY A FIX DURING AN
⭐     INCIDENT.
⭐   ⇒ ⭐ You need a documented, tested ***break-glass***
⭐     procedure: ⭐⭐ HOW DO I DEPLOY WITHOUT CI, WHO IS
⭐     ALLOWED TO, AND HOW IS IT AUDITED? ⭐ Rehearse it once a
⭐     year. ⭐ Most teams discover they cannot, during the
⭐     incident.

⭐⭐ ② ***THE PIPELINE HAS PRODUCTION CREDENTIALS.***
⭐   ⇒ ⭐⭐ IT IS A HIGH-VALUE TARGET (Day 369). ⭐ Least
⭐     privilege, OIDC with pinned trust, required review on
⭐     workflow changes, ⭐ and an audit trail of who deployed
⭐     what.

⭐⭐ ③ ***THE PIPELINE ROTS.***
⭐   ⭐ Pinned actions go stale; ⭐ a suppressed CVE never gets
⭐     revisited; ⭐ a gate is disabled "temporarily".
⭐   ⇒ ⭐⭐ SO: A QUARTERLY REVIEW THAT ASKS, PER GATE, "WHAT DID
⭐     THIS CATCH THIS QUARTER?" ⭐ Delete the ones that caught
⭐     nothing ***and*** could not have, ⭐ and fix the ones that
⭐     were disabled.

⭐⭐ ④ ***THE PIPELINE BECOMES UNTESTABLE.***
⭐   ⭐ A 600-line workflow that can only be tested by pushing to
⭐     `main`.
⭐   ⇒ ⭐ Extract logic into scripts you can run locally
⭐     (`scripts/deploy.sh`), ⭐⭐ AND KEEP THE YAML AS THIN
⭐     ORCHESTRATION. ⭐ The same rule as keeping business logic
⭐     out of a gateway (Day 341) — ⭐⭐ LOGIC BELONGS WHERE IT
⭐     CAN BE TESTED.

⭐⭐ ⇒ AND THE CLOSING TEST FOR TODAY: ***CAN A NEW ENGINEER,
⭐   ALONE, ON THEIR SECOND DAY, SHIP A ONE-LINE CHANGE TO
⭐   PRODUCTION AND ROLL IT BACK — WITHOUT ASKING ANYONE?***
⭐   ⇒ ⭐⭐ IF YES, THE PIPELINE IS DONE. ⭐ If no, whatever
⭐     blocked them is the next thing to fix, and it is usually
⭐     not technical.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Deploy step that doesn't wait for convergence | The pipeline goes green while pods crash-loop, and a customer notices first |
| ⭐⭐ Smoke test that doesn't assert the git sha | You test the old version and call the deploy a success |
| ⭐ Smoke tests longer than a minute | Everyone waits for them between staging and production |
| ⭐⭐ A flaky smoke test | It blocks deploys, gets disabled within a week, and the gate is gone |
| ⭐ Smoke tests that leave data behind | Becomes a data-quality problem nobody traces back |
| ⭐⭐ Auto-running `alembic downgrade` on rollback | Down-migrations are untested and often lossy. Roll back code, leave the schema forward |
| ⭐⭐ `DROP COLUMN` in the same release as the code change | Rollback becomes impossible |
| ⭐ Gating rollbacks behind approval | Rollback is the safe direction; slowing it is exactly backwards |
| ⭐ Approval gates nobody reads | A delay pretending to be a control |
| ⭐⭐ Staging with one replica and 100 rows | Proves almost nothing. Replicas, data volume and the TLS path are what matter |
| ⭐ Preview environments that don't self-destruct | Cost and confusion accumulate |
| ⭐⭐ No deployment markers in monitoring | "Did something change at 14:32?" takes fifteen minutes instead of one glance |
| ⭐⭐ No break-glass procedure | CI is down during the incident, and you can't ship the fix |
| ⭐ A 600-line workflow | Only testable by pushing to main. Extract to scripts; keep YAML thin |
| ⭐ Gates nobody reviews | Suppressed CVEs and "temporarily" disabled checks become permanent |

## Interview questions

**1. "Walk me through your deployment pipeline."**
> ⭐ Three parallel jobs — static checks, tests, security — then one build producing an image with an
> SBOM, scanned and signed. ⭐⭐ Then **migrations as a separate job using the same image with a
> different command**, staging deployed **by digest**, smoke tests, approval, and production getting
> **the same digest**. ⭐ Every deploy step waits for convergence and rolls back on failure. ⭐⭐ And the
> rollback path has actually been run — **if you've never run it, you don't have it.**

**2. "What does a smoke test check?"**
> ⭐ Five to ten assertions against the deployed environment, under a minute, zero flakiness tolerated.
> ⭐⭐ The most important one: **health returns 200 *and reports the expected git sha* — without that
> you're testing the old version and calling the deploy a success.** ⭐ Then dependencies reachable, one
> authenticated read on real data, one write-and-undo which catches read-only credentials and a
> migration that didn't apply, ⭐ a background job completing, and the schema version matching what the
> code expects.

**3. "How do you handle rollback?"**
> ⭐⭐ **Code rolls back; data doesn't.** ⭐ So migrations must be backward-compatible, because the
> rollback runs the *previous image* against the *new schema* and that has to work. ⭐⭐ Concretely:
> **additive migration, deploy, and the destructive migration a release later** — a `DROP COLUMN` in
> the same release as the code change makes rollback impossible. ⭐⭐ And **never auto-run a down-
> migration**: they're rarely tested and often lossy. Roll back the code and leave the schema forward.

**4. "Which gate has earned its place most?"**
> ⭐⭐ The migration lock check. It runs the migration against a restored copy of the production schema
> with real row counts and fails if a statement would take `ACCESS EXCLUSIVE` on a large table —
> **because the same `ALTER TABLE` is harmless on five hundred rows and an eight-minute outage on forty
> million.** ⭐ Second is the generated authorisation matrix, which stops an endpoint shipping with no
> auth check. ⭐ Both are about forty lines. ⭐⭐ And I'd keep **a one-line note per gate of the last real
> thing it caught** — a gate that has never caught anything is either new or useless, and you should
> know which.

**5. "What's the highest-value integration you'd add?"**
> ⭐⭐ **Deployment markers in the monitoring system**, with the commit sha and digest. ⭐ Then every
> latency graph has a vertical line on it, and "did something change at 14:32?" is one glance instead of
> fifteen minutes of archaeology — ⭐ it's the first question anyone asks during an incident. ⭐ Paired
> with a post-deploy verification window: watch error rate and latency for five to fifteen minutes and
> roll back automatically on breach, ⭐⭐ **which is a canary in its simplest form and needs no mesh.**

**6. "What happens when CI is down during an incident?"**
> ⭐⭐ That's the failure mode people don't plan for: **the pipeline is a single point of failure, and
> you can't ship the fix.** ⭐ So there's a documented break-glass procedure — how to deploy without CI,
> who may do it, how it's audited — ⭐⭐ **and it's rehearsed once a year, because most teams discover
> they can't during the incident.** ⭐ I'd also keep deploy logic in scripts rather than YAML, so the
> same commands work by hand.

## 🎙️ Articulation drill

**Two minutes.** Give the shape first: **parallel static, test and security jobs; one build producing a
signed, scanned image; migrations as a separate job using that same image; then staging by digest,
smoke tests, approval, and production getting the identical digest.** Then the four rules — build once
and promote, migrations before rollout, idempotent steps, and a rollback path you have actually
executed, because **if you've never run it you don't have it.** Single out two gates worth more than
their cost: **the migration lock check, which fails a statement that would take an exclusive lock on a
forty-million-row table — the same `ALTER TABLE` that's harmless on five hundred rows** — and the
generated authorisation matrix, so an endpoint can't ship with no auth check. On smoke tests, give the
line that matters: **health returning 200 isn't enough; it has to report the expected git sha, or
you're testing the old version and calling the deploy a success.** Then the deploy step itself: **it's
not `kubectl apply`, it's apply plus waiting for convergence with a timeout** — without the wait the
pipeline goes green while pods crash-loop. On rollback: **code rolls back, data doesn't**, so additive
migration, deploy, destructive migration a release later, and never an automatic down-migration. Close
on two things: **deployment markers in your metrics system, so "did something change at 14:32" is one
glance** — and a rehearsed break-glass procedure, because **the pipeline is a single point of failure
and most teams discover they can't deploy without it during the incident.**
