**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: the test for every alert is whether a tired person who did not write

# Part 1 — ⭐⭐ Logs: structured, correlated, and safe

```
⭐   ❌ logger.info(f"Processing job {job.id} for {user.email}")
⭐   ⭐⭐ logger.info("job.processing", job_id=..., tenant_id=...,
⭐                   trace_id=..., duration_ms=...)

⭐⭐ WHY STRUCTURED, IN ONE LINE: ***YOU CANNOT AGGREGATE PROSE.***
⭐   ⭐ "Show me p95 duration for tenant 42's failed jobs" is a
⭐     query against fields and a regex fight against sentences.

⭐⭐ THE FIELD THAT MAKES LOGS USEFUL IN A MULTI-TENANT SYSTEM:
⭐   ***`tenant_id` ON EVERY LINE.*** ⭐ Without it, "is this
⭐   affecting everyone or one customer?" — ⭐⭐ THE FIRST
⭐   QUESTION OF EVERY INCIDENT — is unanswerable.
```

```
⭐⭐ AND WHAT MUST NEVER BE IN A LOG LINE:
⭐   ⭐ tokens and passwords (⭐⭐ INCLUDING THE QUERY STRING,
⭐     which is where Day 268's WebSocket token ended up)
⭐   ⭐ full request bodies on auth endpoints
⭐   ⭐ PII you would have to delete on an erasure request —
⭐     ⭐⭐ BECAUSE LOGS ARE A DATA STORE WITH A RETENTION
⭐     POLICY AND NO DELETE PATH (Day 267's fourth delete,
⭐     arriving somewhere you did not expect it).
⭐   ⇒ ⭐ A redaction filter in the logging config, plus a test
⭐     that logs a fake token and asserts it does not appear.
```

# Part 2 — ⭐⭐ Correlation, without which async is unreadable

```
⭐⭐ ONE USER ACTION IN YOUR SYSTEM TOUCHES:
⭐   the API → a Postgres transaction → an outbox row (D263)
⭐   → the relay → a queue message (D265) → a worker
⭐   → a provider call → a webhook coming back
⭐ ⇒ ⭐⭐ SIX PROCESSES, POSSIBLY SIX MACHINES, MINUTES APART.
⭐   ⭐ Without a shared id, that is six unrelated log streams
⭐     and you reconstruct the story by matching timestamps —
⭐     which does not work at 200 rps.

⭐⭐ THE CHAIN, AND EVERY LINK IS A PLACE PEOPLE DROP IT:
⭐   ① accept `traceparent` at the edge, or mint one
⭐   ② put it in a `contextvar`; a logging filter adds it to
⭐     EVERY line automatically ⇒ ⭐ nobody has to remember
⭐   ③ ⭐⭐ STORE IT ***IN THE OUTBOX ROW***, because that row
⭐     may be relayed thirty seconds later by another process
⭐   ④ ⭐⭐ PUT IT IN THE QUEUE MESSAGE and restore it in the
⭐     worker before the first log line
⭐   ⑤ send it on the outbound provider call
⭐   ⑥ ⭐ carry your OWN reference on the webhook so the reply
⭐     rejoins the trace (Day 263's reconciliation prerequisite,
⭐     paying off a second time)

⭐ ⇒ ⭐⭐ AND RETURN IT IN THE RESPONSE HEADER, so a support
⭐   ticket carries the trace id and you skip the search entirely.
```

# Part 3 — ⭐⭐ Metrics, and the two things everyone gets wrong

```
⭐   ⭐ RED for services: ⭐ Rate · Errors · Duration
⭐   ⭐ USE for resources: ⭐ Utilisation · Saturation · Errors
⭐   ⇒ ⭐ Every panel you build should be one of these six for
⭐     one component. If it is neither, ask what question it
⭐     answers during an incident.
```

```
⭐⭐ MISTAKE ①: THE AVERAGE.
⭐   ⭐ 999 requests at 50 ms + 1 request at 30 s
⭐     ⇒ mean = ⭐ 80 ms. ⭐⭐ THE DASHBOARD IS GREEN AND A USER
⭐       WAITED HALF A MINUTE.
⭐   ⇒ ⭐ Histograms and quantiles. p50 / p95 / p99, always.

⭐⭐ MISTAKE ②, AND IT IS SUBTLER — ***YOU CANNOT AVERAGE
⭐   PERCENTILES.***
⭐   ⭐ pod A p99 = 100 ms, pod B p99 = 900 ms.
⭐   ⭐⭐ THE FLEET'S p99 IS NOT 500 ms. IT IS NOT COMPUTABLE
⭐     FROM THOSE TWO NUMBERS AT ALL.
⭐   ⇒ ⭐⭐ EXPORT HISTOGRAM ***BUCKETS***, aggregate the buckets,
⭐     then compute the quantile once at query time
⭐     (`histogram_quantile(0.99, sum(rate(...)) by (le))`).
⭐   ⇒ ⭐ Which is also why pre-computed p99 per pod, averaged on
⭐     a dashboard, is one of the most common silently-wrong
⭐     numbers in the industry.
```

```
⭐ ⭐ AND CARDINALITY, WHICH IS HOW PEOPLE BREAK THEIR METRICS
⭐   SYSTEM: ⭐⭐ A LABEL IS A TIME SERIES PER DISTINCT VALUE.
⭐   ⭐ `user_id` as a label with 50,000 users = 50,000 series
⭐     PER METRIC. ⭐⭐ THAT IS AN OUTAGE OF YOUR MONITORING,
⭐     during the incident where you needed it.
⭐   ⇒ ⭐ High-cardinality identifiers belong in LOGS and TRACES.
⭐     Labels are for BOUNDED sets: endpoint, method, status,
⭐     queue name. ⭐ `tenant_id` only if tenants are few and
⭐     you have decided it deliberately.
```

# Part 4 — ⭐ Tracing, and what to sample

```
⭐   ⭐ A SPAN = one unit of work with a duration and attributes.
⭐     ⭐⭐ THE VALUE IS THE WATERFALL: 40 ms of your code and
⭐       380 ms waiting on a provider is a picture, not a number.
⭐   ⭐ Auto-instrument the framework, the client, and the driver;
⭐     then add spans for YOUR domain operations, which is where
⭐     the interesting time actually is.

⭐⭐ SAMPLING — THE DECISION THAT DETERMINES WHETHER TRACING
⭐   HELPS OR JUST COSTS MONEY:
⭐   ⭐ HEAD sampling (decide at the start, e.g. 1%) — cheap,
⭐     ⭐⭐ AND IT THROWS AWAY 99% OF YOUR ERRORS TOO.
⭐   ⭐⭐ TAIL sampling — buffer, then keep the trace if it is
⭐     SLOW or FAILED. ⭐ Costs more, and keeps exactly the
⭐     traces you would have gone looking for.
⭐   ⇒ ⭐ A workable default: 100% of errors and slow requests,
⭐     1–5% of the rest.
```

# Part 5 — ⭐⭐ Alerts: symptoms, not causes

```
⭐⭐ THE RULE: ***ALERT ON WHAT THE USER EXPERIENCES.***
⭐   ⭐ ❌ "CPU > 80%"        — so what? It may be perfectly fine.
⭐   ⭐ ❌ "a pod restarted"  — that is the system self-healing.
⭐   ⭐ ✅ "p99 above the SLO for 5 minutes"
⭐   ⭐ ✅ "error rate above 1% for 2 minutes"
⭐   ⇒ ⭐⭐ CAUSE-BASED ALERTS PAGE YOU FOR THINGS THAT ARE NOT
⭐     PROBLEMS AND MISS PROBLEMS THAT HAVE NO KNOWN CAUSE.
⭐     ⭐ Causes belong on dashboards, where you go AFTER a
⭐       symptom alert fires.

⭐⭐ THE FOUR THAT MATTER IN THIS SYSTEM:
⭐   ① ⭐ availability / error rate  (the request path)
⭐   ② ⭐ latency SLO burn           (the request path)
⭐   ③ ⭐⭐ OLDEST-MESSAGE AGE       (Day 265 — the async path)
⭐   ④ ⭐⭐ DEAD-MAN CHECKS          (Days 264, 270 — the silence)
⭐ ⇒ ⭐ Notice that half of them are about work nobody is
⭐   watching. That is the shape of this system.
```

```
⭐⭐ ERROR BUDGETS, AS ARITHMETIC RATHER THAN VOCABULARY:
⭐   ⭐ 99.9% monthly = ⭐⭐ 43 MINUTES of failure allowed.
⭐   ⭐ 99.99%        = ⭐ 4.3 minutes — ⭐⭐ WHICH IS LESS THAN
⭐     ONE ROLLING DEPLOY GONE WRONG, so promising it commits
⭐     you to blue/green, canaries and an on-call rota.
⭐   ⇒ ⭐⭐ AN SLO IS A BUDGET DECISION ABOUT ENGINEERING TIME,
⭐     NOT AN ASPIRATION.

⭐ ⭐ BURN-RATE ALERTING beats threshold alerting:
⭐   ⭐ fast burn (14× over 1 h) ⇒ ⭐ PAGE — this consumes the
⭐     month in two days
⭐   ⭐ slow burn (3× over 6 h)  ⇒ ⭐ TICKET, not a page
⭐   ⇒ ⭐⭐ ONE SIGNAL, TWO URGENCIES, AND NO ARBITRARY
⭐     THRESHOLD TO ARGUE ABOUT.
```

# Part 6 — ⭐⭐ The 3 a.m. test

```
⭐⭐ EVERY ALERT LINKS TO A RUNBOOK SECTION WITH FOUR THINGS:
⭐   ① ⭐ WHAT IT MEANS, in one sentence, for a user
⭐   ② ⭐ THE FIRST THING TO LOOK AT — a specific dashboard link
⭐     or a specific query, not "check the logs"
⭐   ③ ⭐⭐ THE SAFE ACTIONS, explicitly: restart is safe / a
⭐     re-run is safe (Day 264 made it so) / DO NOT run the
⭐     backfill again
⭐   ④ ⭐ WHEN TO ESCALATE, and to what

⭐⭐ AND THE MEASURE FOR THE WHOLE ALERTING SYSTEM:
⭐   ***WHAT FRACTION OF PAGES WERE ACTIONABLE?***
⭐   ⇒ ⭐ Below ~70%, people start ignoring pages, and then the
⭐     real one is ignored too — ⭐⭐ EXACTLY THE FLAKY-TEST
⭐     DYNAMIC FROM DAY 281, WITH HIGHER STAKES.
⭐   ⇒ ⭐ So a non-actionable page is a BUG IN THE ALERT. Fix
⭐     the alert, or delete it. Do not "get used to it".
```

# Part 7 — ⭐ The one dashboard

```
⭐⭐ ONE PAGE THAT ANSWERS FOUR QUESTIONS, IN THIS ORDER —
⭐   THE ORDER IS THE DESIGN:
⭐   ① ⭐ IS IT UP?          request rate + error rate
⭐   ② ⭐ IS IT SLOW?        p50/p95/p99 by endpoint
⭐   ③ ⭐⭐ IS IT LOSING WORK? queue age · DLQ · outbox backlog ·
⭐        job last-success ages   ⭐⭐ ← THE PANEL NOBODY BUILDS
⭐   ④ ⭐ IS IT RUNNING OUT?  connections · memory · disk · pool
⭐        saturation
⭐ ⇒ ⭐ Everything else is a SECOND page you open once ① – ④
⭐   have told you where to look.
⭐ ⇒ ⭐⭐ AND ANNOTATE DEPLOYS ON EVERY GRAPH. "It started at
⭐   14:02" plus a deploy marker at 14:01 is the fastest
⭐   diagnosis available to anyone, and it is free.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| f-string log messages | You can't aggregate prose. Structured events with fields. |
| No `tenant_id` on log lines | "Everyone or one customer?" is unanswerable, and it's the first question. |
| Logging tokens or query strings | Logs are a data store with retention and no delete path. |
| No redaction test | Redaction that isn't tested isn't redaction. |
| No trace id | Six processes minutes apart become six unrelated log streams. |
| Trace id not stored in the outbox row | The relay runs later, in another process, with no context. |
| Trace id not restored in the worker | The chain breaks exactly where debugging is hardest. |
| Not returning the trace id to the client | Support tickets arrive without the one field that would find it. |
| Alerting on averages | 999 fast requests plus one 30-second request averages to green. |
| Averaging p99 across pods | Not computable from those numbers. Aggregate buckets, then quantile. |
| `user_id` as a metric label | 50,000 series per metric, and your monitoring dies during the incident. |
| Head sampling at 1% | You threw away 99% of your errors too. |
| Alerting on CPU | It's a cause, not a symptom. Causes belong on dashboards. |
| Paging on pod restarts | That's the system self-healing. |
| No async alerts | Half this system's failures are silent. Age and dead-man checks. |
| Promising 99.99% casually | 4.3 minutes a month is less than one bad rolling deploy. |
| Threshold alerts instead of burn rate | Arbitrary numbers, and no distinction between page and ticket. |
| An alert with no runbook | A notification that something is wrong somewhere. |
| A runbook that says "check the logs" | Give the query or the dashboard link. |
| Tolerating non-actionable pages | Below ~70% actionable, people ignore the real one too. |
| A dashboard with 40 panels | Four questions, in order. Everything else is page two. |
| No deploy annotations | The fastest diagnosis available, and it's free. |

## Interview questions

**Q: What does your logging look like?**

> Structured events rather than sentences, because you can't aggregate prose — "p95 duration for
> tenant 42's failed jobs" is a query against fields or a regex fight. Every line carries a trace id
> and a `tenant_id`, and that second field is the one that matters most in a multi-tenant system,
> because the first question in any incident is whether it's everyone or one customer. And there's a
> redaction filter with a test that logs a fake token and asserts it doesn't appear — logs are a data
> store with a retention policy and no delete path, so anything I log about a person is something I
> can't erase when they ask.

**Q: How do you debug something that spans the API, a queue and a worker?**

> With a trace id that survives every hop, and the two links people drop are the interesting ones. It
> goes into the *outbox row*, because that row might be relayed thirty seconds later by a different
> process, and it goes into the queue message and gets restored in the worker before its first log
> line. I also carry my own reference on outbound provider calls so the webhook rejoins the trace —
> which is the same prerequisite reconciliation needed. And the trace id comes back in the response
> header, so a support ticket arrives with the one field that finds everything.

**Q: Why can't you average p99 across your pods?**

> Because a percentile isn't a mean — it's a position in a distribution, and you can't recover the
> combined distribution from two summary numbers. Pod A at 100 ms and pod B at 900 ms doesn't give you
> 500; the fleet p99 isn't computable from those at all. The fix is to export histogram buckets,
> aggregate the buckets, and compute the quantile once at query time. It matters because
> pre-computed per-pod percentiles averaged on a dashboard is one of the most common silently wrong
> numbers there is.

**Q: What do you alert on?**

> Symptoms, not causes. CPU at 80% might be perfectly fine, and a pod restart is the system healing
> itself — cause-based alerts page you for non-problems and miss problems with no known cause, so
> causes go on dashboards where you look *after* a symptom fires. In this system there are four:
> error rate, latency SLO burn, oldest-message age, and dead-man checks on every background component.
> Half of them are about work nobody is watching, which is the shape of this architecture. And I'd use
> burn-rate alerting so one signal gives me a page for a fast burn and a ticket for a slow one, with no
> arbitrary threshold to argue about.

**Q: What makes an alert good?**

> It passes the 3 a.m. test: a tired person who didn't write the code can act on it in five minutes.
> So every alert links to a runbook section with what it means for a user in one sentence, the
> specific query or dashboard to open — never "check the logs" — the explicitly safe actions,
> including whether a re-run is safe, and when to escalate. The measure for the system as a whole is
> the fraction of pages that were actionable; below about seventy percent people start ignoring pages
> and the real one goes with them. So a non-actionable page is a bug in the alert, not something to
> get used to — the same dynamic as flaky tests, with higher stakes.

## 🎙️ Articulation drill

**Three minutes: "How do you know what's happening in production?"**

Start with the test that governs everything: **can a tired person who didn't write the code act on
this in five minutes?** Then the three layers, quickly. Logs: structured, because you can't aggregate
prose, and every line carries a trace id and a `tenant_id` — **the first question in any incident is
whether it's everyone or one customer.** Correlation: one user action touches six processes minutes
apart, so the trace id has to survive every hop, and name the two links people drop — **it goes in the
outbox row, because that row is relayed later by another process, and it's restored in the worker
before the first log line.** Metrics: alert on quantiles not averages, and give the sharp one —
**you cannot average p99 across pods; export buckets and compute the quantile at query time**, because
per-pod percentiles averaged on a dashboard is a silently wrong number in a lot of places. Mention
cardinality, since `user_id` as a label takes your monitoring down during the incident you needed it
for. Then alerting: **symptoms, not causes** — CPU is not an alert, a pod restart is the system
healing — and the four that matter here, half of which are about work nobody is watching. Give the
error budget as arithmetic: **99.99% is 4.3 minutes a month, less than one bad rolling deploy**, so an
SLO is a budget decision about engineering time. Close on the 3 a.m. test: every alert links to a
runbook with what it means, the exact query to run, whether a re-run is safe, and when to escalate —
and **the measure of the whole system is the fraction of pages that were actionable, because below
about seventy percent people ignore the real one too.**
