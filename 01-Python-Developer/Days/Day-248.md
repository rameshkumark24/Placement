# Day 248 🏗️

**P-248** · 🏗 **Choosing the flagship** — ⭐⭐ what makes a project defensible

**Time:** 3 hrs · **Mode:** BUILD

> **⚠️ STAGE 7 RULE — read it once and mean it.**
>
> ⭐⭐ **Every line of both projects is written by you. No AI-generated code. AI for explanation
> always; AI writing your code never.**
>
> ⭐ This is not a purity test. ⭐⭐ **The projects exist so that you can defend them**, and you
> cannot defend a decision you did not make or a line you did not write. The moment someone asks

>
> ⭐⭐ **These days contain decisions, traps and review gates — not code.** The building is yours.

# Part 1 — ⭐⭐ What "defensible" actually means

```
⭐⭐ THE INTERVIEWER IS NOT EVALUATING YOUR PROJECT. THEY ARE EVALUATING
⭐   WHETHER YOU MADE DECISIONS AND CAN EXPLAIN THEM.
⭐   ⭐ A small service with three genuinely hard, well-reasoned
⭐     decisions beats a sprawling clone with none — every time, and it
⭐     is not close.
```

| ⭐ Defensible | ❌ Not defensible |
|---|---|
| ⭐ Solves a problem you can state in **one sentence** | "an e-commerce clone" |
| ⭐ Has **three decisions with real trade-offs** | every choice was the tutorial's default |
| ⭐⭐ Has a **failure mode you designed around** | nothing concurrent, so nothing could go wrong |
| ⭐ Is **deployed and observable** | runs on your laptop |
| ⭐ Has tests that would **catch a regression** | a coverage number with no assertions |
| ⭐ Small enough to **finish** | 40% built, abandoned |

```
⭐⭐ THE SINGLE BEST SENTENCE YOU CAN SAY IN AN INTERVIEW:
⭐   ⭐⭐ "I BUILT X, THEN FOUND IT BROKE UNDER Y, SO I CHANGED IT TO Z —
⭐     AND HERE IS THE MEASUREMENT."
⭐   ⭐ That sentence cannot be faked. It requires a real system, real
⭐     load, a real failure and a real change. ⭐⭐ It is worth more than
⭐     any feature list, and Day 286 exists to manufacture it honestly.
```

# Part 4 — ⭐⭐ Three candidates, analysed — then the worked example

```
⭐⭐ THE TEST FOR A CANDIDATE: ***DOES EACH OF THE TWELVE REQUIREMENTS
⭐   ARISE NATURALLY, OR WOULD I HAVE TO INVENT A REASON FOR IT?***
```

```
⭐ ① A FIELD-SERVICE PLATFORM — companies schedule jobs, technicians
⭐    complete them on site with photos, customers watch the status.
⭐    ⭐⭐ Race: two dispatchers double-book one technician ⇒ Day 187's
⭐      EXCLUDE constraint, arising on its own.
⭐    ⭐⭐ Money: invoices ⇒ outbox + a payment provider + the third
⭐      outcome. ⭐ Uploads: site photos. ⭐ Real-time: live status.
⭐    ⭐ Search: address and notes. ⭐ Reporting: utilisation.
⭐    ⇒ ⭐⭐ ALL TWELVE ARISE FROM THE DOMAIN. Strongest candidate.

⭐ ② AN APPLICANT TRACKING SYSTEM — jobs, candidates, a pipeline,
⭐    interviews, scorecards.
⭐    ⭐ Excellent state machine and RBAC (an interviewer must not see
⭐      other interviewers' scores until they submit theirs — ⭐⭐ a
⭐      genuinely interesting authorisation rule).
⭐    ⭐⭐ Weaker on money and on a race worth testing. ⭐ Fixable by
⭐      adding interview-slot booking, which is honest.

⭐ ③ A USAGE-BILLED API PLATFORM — customers get keys, calls are
⭐    metered, invoices are generated monthly.
⭐    ⭐⭐ Superb on counters, idempotency, rate limiting and the
⭐      reconciliation job. ⭐ Thin on uploads and real-time, and the
⭐      UI is nearly nothing — ⭐⭐ which makes Stage 6's frontend work
⭐      awkward. Consider it only if you have a strong reason.

⭐ ❌ AND THE ONES TO REFUSE: a Twitter clone (no invariants worth
⭐    defending), a URL shortener (too small — ⭐ it is a good SYSTEM
⭐    DESIGN exercise and a bad project), a blog, "an AI wrapper"
⭐    (⭐⭐ Days 288–297 do that deliberately and better).
```

```
⭐⭐ THE WORKED EXAMPLE USED THROUGHOUT DAYS 249–287: ***`fieldwork`***

⭐   ⭐⭐ ONE SENTENCE: "A multi-tenant field-service platform: a company
⭐     schedules jobs, dispatches technicians, captures work on site, and
⭐     invoices the customer."
⭐
⭐   ⭐ ACTORS: owner · dispatcher · technician · customer (read-only,
⭐     one job at a time via a signed link)
⭐   ⭐ CORE ENTITIES: tenant, user, customer, site, job, assignment,
⭐     work_item, photo, invoice, payment
⭐   ⭐⭐ THE STATE MACHINE: draft → scheduled → dispatched → in_progress
⭐     → completed → invoiced → paid, with `cancelled` reachable from

⭐   ⭐⭐ THE RACE: an assignment must not overlap another assignment for
⭐     the same technician. ⭐ Two dispatchers, one technician, adjacent
⭐     slots. ⭐⭐ This is not a contrived example — it is the first bug
⭐     every scheduling system has.

⭐ ⇒ ⭐⭐ USE YOUR OWN PROJECT IF YOU HAVE ONE THAT PASSES THE TEST.
⭐   The days are written so that every instruction maps onto yours —
⭐   ⭐ `fieldwork` exists so the examples can be concrete, not so you
```

# Part 5 — ⭐⭐ Scope: the list that decides whether you finish

```
⭐⭐ THE 40-DAY BUDGET, AND IT IS TIGHT:
⭐   249–252  design and gates            4 days   ⭐ before any code
⭐   253–262  the backend                10 days
⭐   263–270  data and async work         8 days
⭐   271–280  the frontend               10 days   ⭐ → 03-Web-Developer
⭐   281–287  production                  7 days
⭐   ⇒ ⭐⭐ ELEVEN OF FORTY DAYS ARE DESIGN AND PRODUCTION. That ratio is
⭐     the lesson: feature work is the middle of a project, not the
⭐     shape of one.

⭐⭐ WRITE THE OUT-LIST TODAY. It is the single most protective artefact
⭐   in the stage, and Day 249 formalises it. For `fieldwork`:
⭐   ❌ mobile apps (a responsive web app is enough)
⭐   ❌ offline mode (⭐⭐ genuinely interesting, genuinely a second
⭐      project — sync conflict resolution is not a side quest)
⭐   ❌ route optimisation · ❌ payroll · ❌ inventory
⭐   ❌ SSO/SAML (⭐ password + refresh rotation proves the same skill)
⭐   ❌ multi-currency (⭐⭐ one currency, integer minor units, and say
⭐      so out loud — Day 187)
⭐   ❌ a public API with third-party OAuth apps
⭐
⭐   ⭐⭐ THE RULE: ANYTHING ADDED TO SCOPE AFTER TODAY REQUIRES
⭐     SOMETHING ELSE TO COME OUT. Write that rule down. You will need
⭐     to point at it around day 265.
```

```
⭐⭐ AND THE THREE FAILURE MODES OF STAGE 7, NAMED IN ADVANCE:
⭐   ① ⭐⭐ SCOPE CREEP — the project is 60% built on day 287 and there
⭐     is nothing to defend. ⭐ The out-list is the defence.
⭐   ② ⭐⭐ DEFERRING PRODUCTION — "I'll deploy at the end." ⭐ Then you
⭐     do not, and the most valuable thing you could have said in an
⭐     interview ("here is the URL") is unavailable. ⭐⭐ Day 253 deploys
⭐     an empty app on purpose.
⭐   ③ ⭐⭐ BUILDING WITHOUT MEASURING — every optimisation is a claim
⭐     and none is a proof. ⭐ Every performance day in this stage
⭐     demands a before-number, and refusing to record one is the same
⭐     as not doing the day.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Picking a project because it sounds impressive | Pick one where the twelve requirements arise naturally. |
| A clone of a well-known product | There are no decisions to defend; every choice is theirs. |
| Bolting requirements onto a domain that doesn't need them | An invented reason is indefensible in exactly the place it matters. |
| Treating this as a bigger `ticketed` | If the only difference is more endpoints, you built the wrong thing. |
| No out-of-scope list | You will not finish, and you will not be able to explain why. |
| Adding scope without removing scope | Write the swap rule down today; you'll need to point at it. |
| Deferring deployment to the end | Then you never deploy, and lose the single best thing to show. |
| Optimising without a before-number | A claim, not a proof. |
| Letting AI write the code | You cannot defend a line you did not write, and that is the whole point. |

## Interview questions

**Q: Tell me about a project you're proud of.**

> I'd answer with the one sentence first — what problem it solves and for whom — because a project
> someone can't picture is a project they can't ask good questions about. Then I'd go straight to the
> hardest decision rather than the feature list: for the field-service platform, that two dispatchers
> can assign the same technician to overlapping windows, and I enforce that with a Postgres `EXCLUDE`
> constraint over the technician and a time range rather than in application code, because a
> check-then-insert is a race no matter how carefully it's written. Then I'd offer the sentence that
> actually carries weight: what broke under load, what I changed, and the measurement. Everything else
> — the endpoints, the stack — I'd let them ask about, because the choice of what I lead with is
> itself information about what I think matters.

**Q: How did you choose the scope?**

> By writing the out-of-scope list at the same time as the in-scope list, and treating it as the more
> important artefact. For this project I explicitly excluded offline mode, route optimisation, SSO and
> multi-currency — and I can say why for each: offline mode is a sync-conflict problem that's a whole
> project rather than a feature; SSO proves nothing that password auth with refresh rotation and reuse
> detection doesn't already prove; multi-currency changes every money calculation for no additional
> learning. I also wrote down a rule that anything added later requires something else to come out, and
> I had to invoke it once. The reason I'd emphasise this is that most portfolio projects fail by being
> sixty percent built, and the failure is always scope rather than skill.

**Q: What would you do differently?**

> The honest version of this question is the most useful thing in an interview, so I'd have a real
> answer rather than a modest one. I'd want to name something structural — a boundary I drew in the
> wrong place, a decision I made early that cost me later — with the specific consequence, rather than
> "I'd add more tests". And I'd distinguish between what I'd change and what I'd *keep* despite it
> looking odd, because being able to defend a thing that looks wrong is a stronger signal than
> agreeing with every criticism. That's a question I'd prepare for deliberately at the end of the
> stage, from the notes I take during it — which is why Day 249's risk register and the ADRs matter:
> they're the raw material for this answer.

## Today's build

1. ⭐ Write your project's **one sentence**. If it takes two, the scope is wrong.
2. ⭐⭐ Score your candidate against all twelve requirements. Any that would need an invented reason — change the project or change the domain.
3. ⭐ Name the actors. For each, one sentence on what they may and may not see.
4. ⭐⭐ Name **the race**: the two concurrent actions that must not both succeed. If you can't, the project has no interesting concurrency and you need a different one.
5. ⭐ Name **the money moment**: what involves a third party that can time out.
6. ⭐⭐ Write the **out-of-scope list** — at least six items, each with one line of justification.
7. ⭐ Write the swap rule: "anything added requires something removed." Put it in the repo.
8. ⭐⭐ Sketch the state machine on paper. Count the states and the legal transitions. If there are fewer than five states, the domain is too thin.
9. ⭐ Create the repository, `README.md` with the one sentence, and `docs/adr/` (empty).
10. ⭐⭐ Write ADR-0001: "why this project", including the twelve-requirement scoring table.
11. ⭐ Block the 40 days in a calendar. Mark 253 and 287 as immovable.
12. ⭐⭐ Write one paragraph titled "what I expect to get wrong" and date it. You will re-read it on Day 287.

## 🎙️ Articulation drill

**Two minutes: pitch your project to someone who will build it with you.**

One sentence on the problem. One on who uses it and what each actor may see. Then straight to the
three hardest things: **the race, the money moment, and the read path that can't use the write
model** — because those are the parts that will take the time, and naming them on day one is the
difference between a plan and a wish. Then the out-of-scope list, out loud, with a reason for each
exclusion. Close by saying what you expect to get wrong.

Then listen back and check one thing: **did you describe features, or decisions?** If it was features,
you don't have a project yet — you have a backlog.
