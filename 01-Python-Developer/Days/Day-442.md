# Day 442 🧰

**P-442** · 🧰 **Frameworks, or nothing** — ⭐⭐ can you print the bytes you send?

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: adopt a framework for the parts that are boring and standard — loaders,
> tracing, checkpointing — and own the parts that are your product — prompts, tool definitions, control
> flow and evals — because the second category is where all your quality and all your cost live.**

---

# Part 1 — ⭐⭐ The one test

```
⭐ ***CAN YOU PRINT THE EXACT BYTES SENT TO THE PROVIDER?***
⭐   ⭐ The full system prompt. ⭐ Every message. ⭐ Every tool
⭐     schema. ⭐ The sampling parameters. ⭐ The cache markers.

⭐ ⭐⭐ IF THE ANSWER IS NO, YOU CANNOT:
⭐   ⭐ ① ***DEBUG A BAD ANSWER*** — ⭐ the cause is almost always
⭐     in the prompt, and you cannot read it;
⭐   ⭐ ② ***OPTIMISE COST*** — ⭐ you cannot see the 1,800 tokens
⭐     of boilerplate the framework injects on every call;
⭐   ⭐ ③ ***USE PROMPT CACHING*** — ⭐⭐ CACHING NEEDS A
⭐     BYTE-STABLE PREFIX, AND A FRAMEWORK THAT REORDERS OR
⭐     RE-RENDERS YOUR MESSAGES SILENTLY DESTROYS IT (D439);
⭐   ⭐ ④ ***REPRODUCE A PRODUCTION FAILURE*** — ⭐ you cannot
⭐     replay what you never captured;
⭐   ⭐ ⑤ ***VERSION YOUR PROMPTS*** (Day 427) — ⭐⭐ YOU CANNOT
⭐     HASH A PROMPT YOU DO NOT POSSESS.

⭐⭐ THIS IS NOT AN ANTI-FRAMEWORK ARGUMENT. ⭐ It is a
⭐   requirement: ⭐⭐ ANY FRAMEWORK THAT PASSES THIS TEST IS
⭐   ADMISSIBLE; ANY THAT DOES NOT IS DISQUALIFIED REGARDLESS OF
⭐   ITS FEATURE LIST. ⭐ Check it on day one, with a request
⭐   logger, not on day sixty during an incident.
```

# 💬 Interview

**1. "Do you use LangChain?"**

⭐ Parts of it. ⭐⭐ The loaders and splitters are genuinely useful and parsing .docx correctly is nobody's
competitive advantage. ⭐ The chains and agent abstractions I don't use, because they hide the prompt,
and the prompt is where the quality and the cost live. ⭐⭐ My test for any framework is whether I can
print the exact bytes going to the provider — full system prompt, every message, every tool schema, the
sampling parameters, the cache markers. ⭐ If I can't, I can't debug a bad answer, can't see the
boilerplate tokens it injects on every call, can't keep a byte-stable prefix for prompt caching, and
can't hash a prompt I don't possess for versioning. ⭐⭐ I check that on day one with a request logger,
not on day sixty during an incident.

**2. "Isn't writing your own loop reinventing the wheel?"**

⭐ It's about six hundred lines across the wrapper, the loop, the tool registry, retrieval and the eval
harness — and I can read all of it. ⭐⭐ So the question isn't "framework versus five thousand lines",
it's "is this framework worth replacing six hundred lines I understand with a dependency I don't?"
⭐ Sometimes emphatically yes. ⭐ But framed that way the answer changes for a lot of teams, and almost
nobody asks it in that form. ⭐⭐ What I'd never hand-roll is durable execution — suspend, resume,
interrupt for a human approval — because that's genuinely hard and it's the strongest argument for a
framework there is.

**3. "So when would you adopt one?"**

⭐ For the parts that are boring and standard, and never for the parts that are the product. ⭐⭐ Boring
and standard: document loaders, trace viewers, streaming plumbing, checkpointing. ⭐ The product:
prompts, tool definitions, control flow, evals. ⭐ Concretely, I'd reach for LangGraph when suspend and
resume became a product requirement, because an explicit state graph with checkpointing and interrupts
is exactly the durable workflow I'd otherwise be building — ⭐⭐ and it lets me keep my own prompts,
which most agent frameworks don't. ⭐ If the team already ran Temporal, I'd use that instead and skip
the AI framework entirely, because an agent run is just a workflow.

**4. "What's the hidden cost?"**

⭐ Prompts you didn't write. ⭐⭐ A lot of frameworks inject their own instructions into the system
prompt, so your careful prompt engineering is now competing with theirs, and you often can't see it
without a proxy. ⭐ Then debugging through six layers of abstraction for a problem that is one string.
⭐⭐ And the structural one: the abstraction is designed for the common case, but production *is* the
uncommon case — the last fifteen percent of customisation regularly costs more than the first
eighty-five percent you saved. ⭐ Plus tokens you can't see and therefore can't cut.

**5. "How do you avoid lock-in?"**

⭐ Four things stay mine regardless of what I adopt. ⭐ Prompts live in files with content hashes, not
inside framework objects. ⭐ The `TaskConfig` — prompt, schema, model, temperature, retrieval params,
hashed — so a log line is reproducible. ⭐ Thin protocols at every external edge, twenty lines each,
which turn a migration into writing a new class. ⭐⭐ And the eval harness, which must run against *any*
implementation, because that's the only way to evaluate a framework swap honestly. ⭐ "We migrated and
recall went from 0.89 to 0.86" is a sentence you can only say if the harness outlived both.

**6. "What about DSPy?"**

⭐ It's a genuinely different idea — you declare the signature of a step and *compile* the prompt against
a metric instead of writing it. ⭐⭐ The precondition is an eval set, which most teams don't have, and
which is exactly why I'd build one first regardless. ⭐ I'd treat it as a serious option for a
well-defined pipeline with a stable metric, and I'd be cautious where the prompt is a product surface
that humans need to read and reason about. ⭐ It's interesting and still niche, and I'd say so rather
than pretend either way.

## 🎙️ Articulation drill

⭐⭐ **Two minutes, out loud: "what's your view on agent frameworks?"**

Lead with the test, not an opinion. **My first question about any framework is whether I can print the
exact bytes it sends the provider — full system prompt, every message, every tool schema, the sampling
parameters. If I can't, I can't debug a bad answer, because the cause is almost always in the prompt and
I can't read it. I can't see the boilerplate tokens it adds on every call. I can't keep a byte-stable
prefix, which is what prompt caching needs, and that's the biggest cost lever in agent work. And I can't
hash a prompt I don't possess. That's not an anti-framework position — it's a filter, and I check it on
day one with a request logger rather than on day sixty during an incident.**

Then reframe the build-versus-buy honestly. **The loop, the wrapper, the tool registry, retrieval and
the eval harness came to about six hundred lines I understand completely. So the question isn't
framework versus five thousand lines, it's whether the framework is worth replacing six hundred lines I
can read with a dependency I can't. Sometimes yes — and the strongest case by far is durable execution.
Suspend, resume, interrupt for human approval is genuinely hard, and that's exactly what LangGraph's
checkpointing gives you. If a team already ran Temporal I'd use that and skip the AI framework, because
an agent run is just a workflow.**

Then the line I actually draw. **Adopt for what's boring and standard — loaders, tracing, streaming,
checkpointing. Own what's the product — prompts, tool definitions, control flow, evals. That's where all
the quality and all the cost are. The hidden cost is prompts you didn't write: many frameworks inject
their own instructions, so your prompt engineering competes with theirs. And the abstraction is built
for the common case while production is the uncommon one, so the last fifteen percent of customisation
regularly costs more than the eighty-five you saved.**

Close on the exit. **Whatever I adopt, four things stay mine: prompts as hashed files, the task config,
thin protocols at every external edge, and a framework-independent eval harness — because "we migrated
and recall went from 0.89 to 0.86" is a sentence you can only say if the harness outlived both. And I'd
ask how long it would take to remove the dependency. A week means it's a tool. "We'd rewrite the
product" means it was never a dependency, it was an architecture, and that decision deserved more than
an afternoon.**
