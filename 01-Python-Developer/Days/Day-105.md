# Part 1 — ⭐⭐ The response, and the length problem

```python
STATUS_TEXT = {200: "OK", 201: "Created", 204: "No Content", 304: "Not Modified",
               400: "Bad Request", 404: "Not Found", 500: "Internal Server Error"}

def build_response(status: int, headers: list[tuple[str, str]], body: bytes) -> bytes:
    lines = [f"HTTP/1.1 {status} {STATUS_TEXT[status]}"]
    lines += [f"{k}: {v}" for k, v in headers]
    lines += [f"Content-Length: {len(body)}"]         # ⭐⭐ len of BYTES, not of str
    lines += [f"Date: {formatdate(usegmt=True)}"]
    return "\r\n".join(lines).encode("latin-1") + b"\r\n\r\n" + body
```

```
⭐⭐ THERE ARE EXACTLY THREE WAYS TO TELL A CLIENT THE BODY HAS ENDED. THERE IS
⭐   NO FOURTH:
⭐   1. ⭐⭐ Content-Length: N          ⇒ read exactly N bytes. ⭐ The normal case.
⭐   2. ⭐ Transfer-Encoding: chunked  ⇒ read until the 0-length chunk. ⭐ For
⭐        bodies whose size you do not know when the headers go out.
⭐   3. ⭐ Connection: close           ⇒ "the body is everything until EOF".
⭐        ⭐⭐ Costs you the connection — you can never reuse it.
⭐
⭐ ⇒ ⭐⭐ SEND NONE OF THE THREE AND THE CLIENT WAITS FOREVER. That is the
⭐     spinning-tab bug, and it is a server bug every time.
```

| ⚠️ Mistake | ⭐ Symptom — ⭐⭐ and it is worth causing each once |
|---|---|
| ⭐⭐ **No length at all** | ⭐⭐ The browser spins until *its* timeout |
| ⭐ `Content-Length` too **large** | ⭐⭐ Spins, waiting for bytes that never come |
| `Content-Length` too **small** | ⭐ Truncated page — ⭐⭐ and on keep-alive, the extra bytes are parsed as the **next response**, corrupting everything after |
| ⭐ `len(str)` not `len(bytes)` | ⭐⭐ Any non-ASCII character makes the count wrong (Day 037) |
| ⭐ Body on a `204` or `304` | ⭐ Illegal — those must have none |

```
⭐⭐ THE `len(str)` BUG IS THE ONE THAT SHIPS, AND DAY 037 EXPLAINS IT EXACTLY:
⭐   body = "café"            ⇒ len(body) == 4  CHARACTERS
⭐   body.encode("utf-8")     ⇒ ⭐⭐ 5 BYTES
⭐   ⇒ ⭐⭐ Content-Length: 4 ON A 5-BYTE BODY ⇒ ⭐ the last byte is left in the
⭐        socket and becomes the first byte of your NEXT response.
⭐   ⇒ ⭐⭐ SO: ENCODE FIRST, THEN MEASURE. Always. `len()` on the bytes object.
```

# Part 2 — ⭐⭐ Keep-alive changes the loop

```
⭐⭐ HTTP/1.1 KEEPS THE CONNECTION OPEN BY DEFAULT (Day 011). ⭐ Your Day-103
⭐   server closed after one request, which is HTTP/1.0 behaviour and which
⭐   costs a full TCP handshake — and a TLS handshake — per request.
```

```python
def handle_connection(conn):
    conn.settimeout(IDLE_TIMEOUT)                 # ⭐⭐ 5-30s. NOT OPTIONAL (Part 4)
    buf = b""
    requests_served = 0
    try:
        while requests_served < MAX_KEEPALIVE_REQUESTS:      # ⭐ 100 is typical
            try:
                request, buf = read_request(conn, buf)       # ⭐⭐ Day 104, carrying buf
            except socket.timeout:
                return                                        # ⭐ idle client — just close
            except ConnectionError:
                return                                        # ⭐ client went away

            response, close = handle(request)
            conn.sendall(response)
            requests_served += 1
            if close:
                return
    finally:
        conn.close()                                          # ⭐⭐ ALWAYS (Days 052, 082)
```

```
⭐⭐ WHEN MUST YOU CLOSE? FOUR CASES, AND GETTING THEM WRONG DESYNCHRONISES THE
⭐   CONNECTION — WHICH LOOKS LIKE RANDOM CORRUPTION:
⭐   1. the client sent `Connection: close`
⭐   2. the request was HTTP/1.0 without `Connection: keep-alive`
⭐   3. ⭐⭐ YOU FAILED TO READ THE WHOLE BODY. ⭐⭐ If a handler rejects a request
⭐        early (413, or an auth failure) and you leave 2 MB of body unread in
⭐        the socket, ⭐⭐ THOSE BYTES ARE PARSED AS THE NEXT REQUEST. ⭐ Either
⭐        drain the body or close. ⭐⭐ THIS IS THE SUBTLEST BUG ON THE PAGE.
⭐   4. ⭐ you are returning a 5xx and are not sure of your own state.
```

⭐ **`Connection: keep-alive` is implied in HTTP/1.1**, so you only send `Connection: close`. ⭐⭐ **And
`MAX_KEEPALIVE_REQUESTS` exists to bound resource use** — the same reason Gunicorn has
`--max-requests`: it puts a ceiling on the damage any slow leak can do.

# Part 3 — ⭐ Streaming, `HEAD`, and errors

```python
def build_streaming_response(status, headers, chunks) -> Iterator[bytes]:
    """⭐⭐ For a body you cannot hold in memory — an export, a large file."""
    head = [f"HTTP/1.1 {status} {STATUS_TEXT[status]}"]
    head += [f"{k}: {v}" for k, v in headers]
    head += ["Transfer-Encoding: chunked"]           # ⭐⭐ NO Content-Length — we do not know it
    yield "\r\n".join(head).encode("latin-1") + b"\r\n\r\n"
    for chunk in chunks:                             # ⭐ a generator (Day 047)
        if chunk:
            yield f"{len(chunk):x}\r\n".encode() + chunk + b"\r\n"    # ⭐ hex size
    yield b"0\r\n\r\n"                               # ⭐⭐ the terminating chunk
```

```
⭐⭐ WHY THIS MATTERS AND IS NOT AN OPTIMISATION: a 2 GB CSV export built with
⭐   `body = "".join(rows)` needs 2 GB of RAM PER CONCURRENT REQUEST. ⭐⭐ Four
⭐   users ⇒ OOM kill (Day 082). ⭐ Streaming holds ONE ROW at a time — Day 047's
⭐   generator pipeline, with the socket as the consumer, and constant memory
⭐   regardless of file size.
⭐   ⇒ ⚠️ ⭐⭐ AND THE TRAP: ONCE YOU HAVE SENT THE HEADERS YOU CANNOT CHANGE THE
⭐        STATUS. If the query fails on row 400,000 you have already sent
⭐        `200 OK`. ⭐ All you can do is terminate the stream abnormally — so
⭐        do the work that can fail (auth, validation, the first query) BEFORE
⭐        yielding the head.
```

```python
if request.method == "HEAD":
    head, _, _ = response.partition(b"\r\n\r\n")
    conn.sendall(head + b"\r\n\r\n")        # ⭐⭐ SAME HEADERS, INCLUDING Content-Length
```

⭐⭐ **A `HEAD` returns exactly the headers a `GET` would, including the `Content-Length` of the body
it is not sending.** ⭐ Computing a length of 0 breaks caches and health checks that use `HEAD` to ask
"how big is this and has it changed" (Day 102).

```python
def safe_handle(request) -> bytes:
    try:
        return handle(request)
    except HTTPError as e:                       # ⭐ expected (Day 060)
        return build_response(e.status, [("Content-Type", "application/json")],
                              json.dumps({"error": e.message}).encode())
    except Exception:                            # ⭐⭐ unexpected — a BUG
        logger.exception("unhandled", extra={"path": request.path})   # ⭐ log ONCE (Day 099A)
        return build_response(500, [("Content-Type", "application/json")],
                              b'{"error":"internal server error"}')   # ⭐⭐ GENERIC
```

```
⭐⭐ THREE RULES FOR THE ERROR PATH, AND THEY ARE ALL SECURITY RULES:
⭐  1. ⭐⭐ NEVER PUT A TRACEBACK IN A RESPONSE BODY. It leaks file paths, library
⭐       versions, SQL, and sometimes credentials from a repr. ⭐ Log it; return
⭐       a generic message plus the REQUEST ID (Day 099A) so support can find it.
⭐  2. ⭐⭐ ONE HANDLER MUST NOT KILL THE SERVER. Catch at the connection boundary
⭐       (Day 060) — an unhandled exception in a route should end that REQUEST,
⭐       not the process.
⭐  3. ⭐ STILL SEND VALID HTTP when you fail. ⭐⭐ A 500 with no Content-Length
⭐       hangs the client on top of failing.
```

# Part 4 — ⭐ Headers every response should carry

```python
BASE_HEADERS = [
    ("Content-Type", "application/json; charset=utf-8"),   # ⭐⭐ always a charset (Day 102)
    ("Date", formatdate(usegmt=True)),
    ("X-Request-Id", request_id.get()),                    # ⭐⭐ Day 099A — support's lifeline
    # ⭐ security headers (Day 127 in full):
    ("X-Content-Type-Options", "nosniff"),                 # ⭐⭐ stop MIME sniffing
    ("Cache-Control", "private, no-store"),                # ⭐ default for authenticated
]
```

| Header | ⭐ Why |
|---|---|
| ⭐⭐ `Content-Length` | ⭐⭐ or the client hangs |
| ⭐ `Content-Type` + charset | ⭐⭐ without a charset, `text/html` is an XSS vector |
| `Date` | ⭐ caches compute freshness from it |
| ⭐⭐ `X-Request-Id` | ⭐⭐ ties the user's report to your logs |
| ⭐ `X-Content-Type-Options: nosniff` | ⭐ stops a browser guessing a type you did not send |
| ⭐ `Connection: close` | ⭐ only when you mean it |

⚠️ ⭐⭐ **Do not send a `Server` header naming your version.** ⭐ It is free reconnaissance: it tells a
scanner exactly which CVEs to try. **The same applies to `X-Powered-By`.**

# Part 5 — ⭐⭐ Prove the bugs

```
⭐⭐ CAUSE EACH OF THESE ONCE. Twenty minutes, and you will never mis-diagnose a
⭐   hung client again:
⭐
⭐ 1. ⭐⭐ Send NO Content-Length ⇒ `curl -v` sits there. ⭐ Ctrl-C it. Now you
⭐      know what "the API is hanging" looks like from the client's side.
⭐ 2. ⭐⭐ Content-Length TWO TOO LARGE ⇒ ⭐ identical symptom, different cause.
⭐ 3. ⭐⭐ Content-Length TWO TOO SMALL, on a KEEP-ALIVE connection, then send a
⭐      second request ⇒ ⭐⭐ THE SECOND RESPONSE IS GARBAGE, because the client
⭐      is parsing your leftover body bytes as a status line.
⭐ 4. ⭐ `len(str)` on a body containing "café" ⇒ ⭐⭐ off by one, silently.
⭐ 5. ⭐⭐ Return 413 for a big upload WITHOUT draining the body, keep the
⭐      connection open, then send another request ⇒ ⭐ desynchronised again.
⭐ 6. ⭐ Remove the idle timeout, open 200 connections that send nothing ⇒
⭐      ⭐⭐ the server stops accepting (Day 103's slowloris, from the other end).
⭐
⭐ ⇒ ⭐⭐ NOTE THAT 1, 2 AND 3 ALL PRESENT AS "IT HANGS" OR "IT IS CORRUPTED",
⭐     AND HAVE DIFFERENT CAUSES. ⭐ Being able to distinguish them from the
⭐     symptom is worth an hour of anyone's time.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **No `Content-Length`, no chunked, no close** | ⭐⭐ The client hangs. There is no fourth option. |
| ⭐ `len(str)` for the length | ⭐⭐ Encode first, then measure the **bytes**. |
| `Content-Length` too small on keep-alive | ⭐⭐ Leftover bytes become the next response. |
| ⭐⭐ **Rejecting a request without draining the body** | ⭐⭐ Those bytes are parsed as the next request. Drain or close. |
| A body on `204`/`304` | ⭐ Illegal. |
| ⭐ `HEAD` returning `Content-Length: 0` | ⭐⭐ Breaks caches and health checks. |
| ⭐ Buffering a huge export | ⭐⭐ N × size in RAM. Stream it. |
| Validating after starting to stream | ⭐⭐ You already sent `200`. Do the failable work first. |
| ⭐⭐ **A traceback in the response body** | ⭐⭐ Leaks paths, versions, SQL. Generic message + request id. |
| Letting a handler exception kill the server | ⭐ Catch at the connection boundary. |
| ⭐ No idle timeout on keep-alive | ⭐ Connections accumulate until fds run out. |
| Sending `Server: MyServer/0.1` | ⭐ Free reconnaissance. |
| No charset on `text/html` | ⭐⭐ A charset-sniffing XSS vector. |

## Interview questions

**Q: A user says the page loads forever. Your server returns 200. What's wrong?**
> Almost certainly the length. The client can't know a response has ended until you tell it, and there
> are exactly three ways: `Content-Length`, a terminating chunk with `Transfer-Encoding: chunked`, or
> closing the connection. If you send none of them, or a `Content-Length` larger than the body, the
> client sits waiting for bytes that never arrive. The classic source is computing the length from the
> string rather than the encoded bytes — "café" is four characters and five bytes — which is off by
> one and completely silent until someone submits an accent.

**Q: What changes when you support keep-alive?**
> The connection handler becomes a loop rather than a single exchange, and you have to carry the read
> buffer between iterations because the client may have pipelined the next request. You need an idle
> timeout, or connections accumulate until you run out of file descriptors. And you need to know when
> you're obliged to close: the client asked, it's HTTP/1.0, you're returning a 5xx and aren't sure of
> your own state, or — the subtle one — you didn't read the whole request body. If a handler rejects a
> 2 MB upload early and you leave the body in the socket, those bytes get parsed as the next request,
> and the connection is desynchronised in a way that looks like random corruption.

**Q: How do you return a 2 GB export?**
> Stream it with chunked encoding, so the body is a generator and memory stays constant regardless of
> file size. Buffering it means two gigabytes per concurrent request, and four users OOM the process.
> The trap is that once the headers are out you can't change the status — if the query fails on row
> 400,000 you've already sent `200 OK` and all you can do is terminate the stream abnormally. So
> anything that can fail — auth, validation, the first query — happens before you yield the head.

**Q: What must never be in an error response?**
> A traceback. It leaks file paths, library versions, SQL fragments and sometimes credentials from an
> object's repr, and it's handed to whoever triggered the error. Log it with full detail and return a
> generic message plus the request id, so support can tie the user's report to the actual log lines.
> I'd also make sure the error response is still valid HTTP with a `Content-Length` — a 500 that
> hangs the client is failing twice — and that an exception in one handler ends that request rather
> than the process.

**Q: Why not send a `Server` header?**
> Because it's free reconnaissance. Naming the software and version tells a scanner exactly which CVEs
> to try, and it gives an attacker information they'd otherwise have to work for. Same for
> `X-Powered-By`. It's not a serious defence on its own — you shouldn't be relying on obscurity — but
> there's no upside to volunteering it.

## 🎙️ Articulation drill

Record two minutes: **"Users say some requests hang forever. Others come back corrupted. Same
service."**

⭐ **Recognise the shape immediately, because it is one family:** **"both of those are framing bugs —
the client not knowing where the response ends. There are exactly three ways to tell it:
`Content-Length`, a terminating chunk, or closing the connection. Hangs and corruption are the two
failure modes of getting that wrong."**

⭐⭐ **Then separate the causes, which is what the question is testing:** *"a hang means the client is
waiting for bytes that never arrive — either no length header at all, or a `Content-Length` larger than
the body. Corruption means the length was too *small*: the leftover bytes are still in the socket, and
on a keep-alive connection the client parses them as the beginning of the next response. So it's the
request after the bad one that looks broken, which is why it feels random."*

⭐⭐ **Then name the specific causes you'd look for:** *"the most common source is computing the length
from the string instead of the encoded bytes — 'café' is four characters and five bytes, so it's off by
one and silent until someone submits an accent. The other one is a handler rejecting a request early —
a 413 or an auth failure — and not draining the request body. Those unread bytes get parsed as the next
request, and the connection is desynchronised from then on."*

⭐ **Close on the fix and the discipline:** *"so: encode then measure, always; drain or close after an
early rejection; and an idle timeout on every connection so nothing accumulates. And I'd deliberately
cause each of those failures once in a scratch server — twenty minutes, and you never mis-diagnose a
hanging client again."*
