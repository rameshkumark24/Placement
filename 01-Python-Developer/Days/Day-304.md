# Part 1 — ⭐⭐ What DDD is, and what people copy instead

```
⭐⭐ DDD HAS TWO HALVES, AND THE VALUABLE ONE IS NOT THE
⭐   POPULAR ONE:
⭐   ⭐ ⭐⭐ STRATEGIC — ubiquitous language, bounded contexts,
⭐        context maps. ⭐ This is where the leverage is: it
⭐        decides what the software is ***about***.
⭐   ⭐ TACTICAL — entities, value objects, aggregates,
⭐        repositories, domain events. ⭐⭐ THIS IS WHAT PEOPLE
⭐        COPY, because it is a folder layout and can be done
⭐        without talking to anybody.

⭐⭐ AND THE FAILURE MODE THAT FOLLOWS: A PROJECT WITH
⭐   `entities/`, `value_objects/` AND `aggregates/` DIRECTORIES,
⭐   ⭐⭐ IN WHICH NOBODY HAS EVER ASKED A DOMAIN EXPERT WHAT
⭐   "COMPLETED" MEANS. ⭐ That is DDD-shaped code with none of
⭐   the benefit, and it costs more than not doing it.

⭐ ⇒ ⭐⭐ THE HONEST TEST FOR WHETHER YOU ARE DOING DDD:
⭐   ***HAS THE LANGUAGE IN THE CODE CHANGED BECAUSE OF A
⭐      CONVERSATION?*** ⭐ If no class has ever been renamed
⭐   after talking to someone who does the job, you have
⭐   adopted the patterns and not the practice.
```

# Part 2 — ⭐⭐ Ubiquitous language

```
⭐⭐ THE CLAIM: THE SAME WORD, MEANING THE SAME THING, IN THE
⭐   CONVERSATION, THE CODE, THE DATABASE AND THE UI.
⭐   ⭐ Not "a translation layer between business terms and
⭐     technical terms" — ⭐⭐ THE ***SAME WORDS***, because
⭐     every translation is a place a misunderstanding hides.

⭐⭐ THE TEST, AND IT TAKES TEN SECONDS:
⭐   ***READ A METHOD NAME ALOUD TO SOMEONE WHO DOES THE JOB.
⭐      DO THEY UNDERSTAND IT, AND DO THEY AGREE IT IS TRUE?***
⭐   ⭐ `job.complete(at)` ⇒ ⭐ "yes, but only if the technician
⭐     has signed off" ⭐⭐ ← YOU JUST FOUND A MISSING RULE, IN
⭐     ONE SENTENCE, FOR FREE.
⭐   ⭐ `job.update_status(3)` ⇒ ⭐ blank look. ⭐⭐ NO
⭐     CONVERSATION IS POSSIBLE, WHICH IS THE REAL COST OF
⭐     TECHNICAL NAMING.
```

```
⭐⭐ TWO SIGNALS THAT YOUR LANGUAGE IS WRONG:

⭐ ① ⭐⭐ THE SAME WORD MEANS DIFFERENT THINGS TO DIFFERENT
⭐     PEOPLE. ⭐ In `fieldwork`, "job" means:
⭐        ⭐ sales — a thing that was sold
⭐        ⭐ dispatch — a visit to schedule
⭐        ⭐ finance — a line to invoice
⭐   ⇒ ⭐⭐ AND YOUR CODE HAS ***ONE*** `Job` CLASS WITH ALL
⭐     THREE SETS OF FIELDS, which is why it has forty columns
⭐     and changes for three unrelated reasons. ⭐ That is not a
⭐     naming problem — ⭐⭐ IT IS A BOUNDED CONTEXT ANNOUNCING
⭐     ITSELF (Day 305).

⭐ ② ⭐⭐ PEOPLE QUALIFY A WORD WHEN THEY SPEAK.
⭐   ⭐ "a ***cancelled*** booking isn't really a booking"
⭐   ⭐ "that's a ***provisional*** assignment"
⭐   ⇒ ⭐⭐ EVERY QUALIFIER IS A CONCEPT WITH NO NAME. ⭐ The
⭐     moment someone needs an adjective to make a sentence
⭐     true, ⭐⭐ THERE IS A MISSING TYPE — and the code is
⭐     currently expressing it as a boolean flag or a status
⭐     column that four `if` statements have to remember.

⭐ ⇒ ⭐ THE TECHNIQUE: ⭐⭐ WRITE DOWN THE WORDS PEOPLE ACTUALLY
⭐   USE, INCLUDING THE ONES YOU THINK ARE WRONG. ⭐ A glossary
⭐   of twenty terms with definitions, in the repository, is
⭐   worth more than any diagram on this page.
```

# Part 3 — ⭐⭐ Entity or value object?

```
⭐⭐ THE TEST IS NOT "DOES IT HAVE AN ID". IT IS:
⭐   ***DOES IT MATTER ***WHICH ONE*** IT IS?***

⭐   ⭐ Two ₹500 notes ⇒ ⭐ interchangeable. ⭐⭐ VALUE OBJECT.
⭐   ⭐ Two employees both called Priya Sharma ⇒ ⭐ absolutely
⭐        not interchangeable. ⭐⭐ ENTITY.
⭐   ⭐ Two addresses with identical text ⇒ ⭐ usually
⭐        interchangeable ⇒ value object — ⭐⭐ UNLESS YOUR
⭐        DOMAIN TRACKS "THE ADDRESS WE VERIFIED IN MARCH", in
⭐        which case it has a history and an identity.
⭐   ⇒ ⭐⭐ WHICH SHOWS THE REAL POINT: ***THE SAME CONCEPT IS
⭐     AN ENTITY IN ONE CONTEXT AND A VALUE OBJECT IN ANOTHER.***
⭐     ⭐ It is a modelling decision about your domain, not a
⭐       property of the thing.

⭐⭐ THE CONSEQUENCES, WHICH ARE MECHANICAL:
⭐   ⭐ ENTITY — equality by IDENTITY. ⭐ Two loaded copies of
⭐        row 42 are equal even if one is stale. Mutable. Has a
⭐        lifecycle.
⭐   ⭐ VALUE OBJECT — equality by VALUE. ⭐⭐ IMMUTABLE, so it
⭐        can be shared freely, cached, used as a dict key, and
⭐        ⭐ never mutated by someone else's code while you hold
⭐        a reference to it.
```

# Part 4 — ⭐⭐ Value objects in Python, and why they earn their place

```python
@dataclass(frozen=True, slots=True)
class Money:
    minor_units: int                      # ⭐⭐ NEVER A FLOAT
    currency: Currency

    def __post_init__(self) -> None:      # ⭐ self-validating
        if self.minor_units < 0:
            raise NegativeAmount(self.minor_units)

    def __add__(self, other: "Money") -> "Money":
        if other.currency is not self.currency:
            raise CurrencyMismatch(self.currency, other.currency)
        return Money(self.minor_units + other.minor_units, self.currency)
```

```
⭐⭐ THREE THINGS THIS BUYS, AND THE THIRD IS THE ONE THAT
⭐   CHANGES HOW YOU WRITE CODE:

⭐ ① ⭐ AN INVALID `Money` CANNOT EXIST. ⭐⭐ VALIDATION HAPPENS
⭐     ONCE, AT CONSTRUCTION — so every function downstream can
⭐     stop checking, and `if amount < 0` disappears from
⭐     fourteen places.

⭐ ② ⭐ CURRENCY MIXING IS A ***RUNTIME*** ERROR AT THE POINT
⭐     OF THE MISTAKE, not a silently wrong total three layers
⭐     later.

⭐ ③ ⭐⭐ IT KILLS PRIMITIVE OBSESSION — AND THIS IS THE BIG ONE:
⭐     ⭐ ❌ transfer(amount: int, currency: str,
⭐                  from_: str, to: str)
⭐          ⇒ ⭐⭐ `transfer(500, "INR", customer_id, account_id)`
⭐            COMPILES, RUNS, AND IS WRONG. Two of those strings
⭐            are swapped and nothing can tell.
⭐     ⭐ ✅ transfer(amount: Money, from_: AccountId,
⭐                  to: AccountId)
⭐          ⇒ ⭐⭐ THE SWAP IS NOW A ***TYPE ERROR***, CAUGHT BY
⭐            mypy BEFORE THE CODE RUNS.
⭐     ⇒ ⭐ In Day 298's vocabulary: you converted connascence
⭐       of POSITION into connascence of TYPE, ⭐⭐ WHICH IS
⭐       THE WHOLE POINT — a weaker form, checked by a tool.
```

```
⭐ ⭐ AND `NewType` FOR THE CHEAP VERSION, WHEN A FULL CLASS IS
⭐   OVERKILL:
⭐     CustomerId = NewType("CustomerId", UUID)
⭐     AccountId  = NewType("AccountId", UUID)
⭐   ⇒ ⭐ Zero runtime cost, ⭐⭐ AND PASSING A `CustomerId`
⭐     WHERE AN `AccountId` IS EXPECTED FAILS TYPE-CHECKING —
⭐     which is the exact bug that produces "we refunded the
⭐     wrong account" incidents.
```

# Part 5 — ⭐⭐ Money, done properly

```
⭐⭐ THE CANONICAL VALUE OBJECT, AND FIVE RULES THAT ARE ALL
⭐   LEARNED THE EXPENSIVE WAY:
⭐   ① ⭐⭐ INTEGER MINOR UNITS. ⭐ `0.1 + 0.2 != 0.3` and a
⭐     float total drifts by paise over a million rows.
⭐     ⭐ `Decimal` is acceptable; ⭐⭐ AN INT OF PAISE IS
⭐       UNAMBIGUOUS AND STORES EXACTLY.
⭐   ② CURRENCY IS PART OF THE TYPE, not a neighbouring column
⭐     someone forgets to filter on.
⭐   ③ ⭐⭐ ROUND ***ONCE***, AT THE END, WITH A STATED MODE.
⭐     ⭐ Rounding each line and then summing gives a different
⭐       answer from summing and then rounding, and ⭐⭐ THE
⭐       DIFFERENCE IS THE THING FINANCE WILL EMAIL YOU ABOUT.
⭐   ④ ALLOCATION IS A METHOD, NOT A DIVISION: splitting ₹100
⭐     three ways is 33.34 / 33.33 / 33.33 — ⭐⭐ `allocate()`
⭐     DISTRIBUTES THE REMAINDER AND GUARANTEES THE PARTS SUM
⭐     TO THE WHOLE. ⭐ Plain division does not.
⭐   ⑤ ⭐ NO IMPLICIT CONVERSION. Multiplying by a rate returns
⭐     Money; ⭐ dividing two Moneys returns a ratio, not Money.
```

# Part 6 — ⭐⭐ Entity identity

```
⭐   ⭐ EQUALITY IS BY IDENTITY, AND YOU MUST WRITE IT:
⭐        def __eq__(self, other): return (isinstance(other, Job)
⭐                                         and self.id == other.id)
⭐        def __hash__(self): return hash(self.id)
⭐     ⇒ ⭐⭐ DEFAULT `dataclass` EQUALITY COMPARES ***ALL
⭐       FIELDS***, so a stale copy of row 42 is "not equal" to
⭐       a fresh one — ⭐ which produces set and dict bugs that
⭐       are extremely hard to see.

⭐   ⭐ THE ID IS ASSIGNED AT CONSTRUCTION, NOT BY THE DATABASE.
⭐     ⇒ ⭐⭐ GENERATE A UUID IN THE DOMAIN. ⭐ Otherwise an
⭐       unsaved entity has `id=None`, so it cannot be hashed,
⭐       cannot be put in a set, and cannot be compared —
⭐       ⭐⭐ AND YOUR DOMAIN NOW DEPENDS ON A DATABASE ROUND
⭐       TRIP TO HAVE A CONSISTENT IDENTITY, WHICH BREAKS THE
⭐       DEPENDENCY RULE (Day 300) IN A WAY NOBODY NOTICES.

⭐   ⭐ NATURAL vs SURROGATE KEYS: ⭐ use a surrogate for
⭐     identity, ⭐⭐ AND PUT A UNIQUE CONSTRAINT ON THE NATURAL
⭐     KEY ANYWAY (Day 187) — because "email is unique" is a
⭐     domain rule whether or not it is your primary key.
```

# Part 7 — ⭐ Persisting value objects

```
⭐   ⭐ EMBED THEM AS COLUMNS: `amount_minor`, `amount_currency`
⭐     on the owning table. ⭐ SQLAlchemy `composite()` maps
⭐     both columns to one `Money` attribute.
⭐   ⭐⭐ THE RULE: IF A VALUE OBJECT NEEDS ITS OWN TABLE WITH
⭐     ITS OWN PRIMARY KEY, ***IT IS PROBABLY AN ENTITY*** —
⭐     because you just gave it an identity and a lifecycle.
⭐   ⭐ The exception is a value object in a COLLECTION (an
⭐     order's several addresses), which needs a table for
⭐     mechanical reasons — ⭐ and then it is replaced wholesale
⭐     rather than mutated, which keeps the semantics intact.
⭐   ⭐⭐ AND NEVER LET THE VALUE OBJECT KNOW ABOUT THE ORM.
⭐     ⭐ `Money` importing `sqlalchemy` fails Day 299's contract
⭐     and destroys the one thing that made it easy to test.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Adopting the folder layout without the conversation | DDD-shaped code with none of the benefit, at higher cost. |
| A translation layer between business and technical terms | Every translation is a place a misunderstanding hides. |
| Method names a domain expert can't parse | No conversation is possible, which is the real cost of `update_status(3)`. |
| One class for a word three teams define differently | That's a bounded context announcing itself, not a naming problem. |
| Ignoring qualifiers people use when speaking | Every adjective that makes a sentence true is a missing type. |
| "Does it have an id?" as the entity test | Ask whether it matters *which one* it is. |
| Assuming a concept is always an entity | The same concept differs by context; it's a modelling decision. |
| Mutable value objects | You lose sharing, hashing, and safety from other people's code. |
| Floats for money | `0.1 + 0.2 != 0.3`, and totals drift by paise over a million rows. |
| Currency in a neighbouring column | Someone forgets to filter on it. Put it in the type. |
| Rounding per line then summing | A different answer from summing then rounding, and finance will notice. |
| Dividing money three ways | Use `allocate()`; the parts must sum to the whole. |
| Primitive-obsessed signatures | Two swapped strings run happily and are wrong. |
| Default dataclass equality on entities | A stale copy of row 42 isn't equal to a fresh one; set and dict bugs follow. |
| Letting the database assign identity | Unsaved entities can't be hashed or compared, and the domain now needs a round trip. |
| A value object with its own table and key | You gave it identity and a lifecycle — it's an entity. |
| A value object importing the ORM | It fails the purity contract and stops being trivially testable. |

## Interview questions

**Q: What is DDD, in your words?**

> The claim that the hardest problem is agreeing what a word means. It has a strategic half — the
> language, bounded contexts, context maps — and a tactical half of entities, value objects and
> aggregates. The tactical half is what gets copied, because it's a folder layout you can adopt
> without talking to anybody, and that produces DDD-shaped code with none of the benefit at higher
> cost. My honest test for whether it's real: has a class ever been renamed because of a conversation
> with someone who does the job? If not, you've adopted patterns rather than a practice.

**Q: How do you find the right names?**

> By listening for two signals. First, the same word meaning different things to different teams — in
> my project "job" meant a sold thing to sales, a visit to dispatch, and an invoice line to finance,
> which is why one class had forty columns and changed for three unrelated reasons. That's not a
> naming problem, it's a bounded context announcing itself. Second, qualifiers: when someone says "a
> *cancelled* booking isn't really a booking", the adjective is a concept with no name, and the code
> is currently expressing it as a boolean flag four `if` statements have to remember.

**Q: Entity or value object — how do you decide?**

> Not by whether it has an id. By whether it matters *which one* it is. Two five-hundred-rupee notes
> are interchangeable, so money is a value object; two employees with the same name are not, so an
> employee is an entity. And the same concept can differ by context — an address is usually a value
> object, unless your domain tracks "the address we verified in March", at which point it has a
> history and an identity. So it's a modelling decision about the domain, not a property of the thing.

**Q: Why bother with value objects in Python?**

> Mostly to kill primitive obsession, which is where the real bugs are. `transfer(500, "INR",
> customer_id, account_id)` runs happily with two of those strings swapped and nothing can tell.
> `transfer(amount: Money, from_: AccountId, to: AccountId)` makes that swap a type error caught
> before the code runs — I converted connascence of position into connascence of type, which is a
> weaker form checked by a tool. Secondary benefits: validation happens once at construction, so `if
> amount < 0` disappears from fourteen places, and currency mixing fails at the point of the mistake
> rather than as a silently wrong total three layers later.

**Q: Anything special about money?**

> Integer minor units, never floats — `0.1 + 0.2` isn't `0.3` and the error accumulates. Currency in
> the type rather than a neighbouring column. Round once at the end with a stated mode, because
> rounding per line and then summing gives a different total from summing and then rounding, and that
> difference is what finance emails you about. And splitting is a method, not a division: allocating a
> hundred rupees three ways is 33.34 and two of 33.33, and `allocate()` guarantees the parts sum to
> the whole, which plain division does not.
