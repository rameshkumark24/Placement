# Part 1 — ⭐⭐ The artefact

```
⭐⭐ THE PIPELINE, IN EVERY LANGUAGE AND EVERY ERA:

⭐   SOURCE ──▶ BUILD ──▶ ⭐⭐ ARTEFACT ──▶ SHIP ──▶ RUN (with config injected)
⭐                          ▲
⭐                          ⭐⭐ built ONCE, deployed to staging AND production UNCHANGED
```

⭐⭐ **"Build once, deploy many" is the rule that makes staging meaningful.** If production rebuilds
from source, you tested something that was never shipped: a dependency resolved differently, a base
image moved, a transitive version drifted. **The artefact you tested must be the bytes you run.**

| ⭐ Ecosystem | ⭐ Artefact |
|---|---|
| ⭐ Python | ⭐⭐ a **wheel** (`.whl`), or far more often **a Docker image** |
| Java | a jar |
| ⭐ Front end | ⭐ a folder of hashed static files (Day 015: `app.a3f9c1.js`) |
| ⭐ Serverless | a zip, or an image |

```
⭐⭐ WHY PYTHON USUALLY SHIPS A CONTAINER RATHER THAN A WHEEL:
⭐   Python has no self-contained executable by default. A wheel needs
⭐   ⇒ the right interpreter version, C extension build tools (psycopg, lxml, numpy),
⭐     system libraries, and a virtualenv on the target.
⭐   ⇒ ⭐⭐ A container freezes ALL of that — interpreter, libs, OS packages — into one
⭐        content-addressed thing. That is why containers won here specifically.

⭐⭐ AND THE RULE THAT FOLLOWS: ⚠️ NEVER `pip install` AT CONTAINER START.
⭐   ⇒ it is slow, it needs the network at the worst moment, and ⭐⭐ it means your
⭐     running code depends on what PyPI served THAT SECOND. Install at BUILD time.
⭐   ⇒ ⭐⭐ and pin with a LOCK FILE (uv.lock / requirements.txt with hashes), or
⭐        "it worked yesterday" becomes a sentence you say out loud.
```

# Part 2 — ⭐⭐ WSGI, ASGI, and what actually runs your code

```
⭐⭐ A PYTHON WEB APP IS NOT A SERVER. It is a callable that a server calls. (Day 004.)

⭐ WSGI (2003, synchronous) — Django, Flask
⭐   def app(environ, start_response): ...      ⭐ one request, one thread, blocking
⭐   servers: ⭐ gunicorn, uWSGI
⭐
⭐⭐ ASGI (async) — FastAPI, Starlette, Django 4+ (partially)
⭐   async def app(scope, receive, send): ...   ⭐⭐ handles HTTP *and* WEBSOCKETS (Day 017)
⭐   servers: ⭐ uvicorn, hypercorn
⭐
⭐ ⇒ ⭐⭐ WSGI CANNOT do WebSockets or SSE properly, and holds a whole worker per request —
⭐      which is exactly why long polling was catastrophic on it (Day 018).
```

```bash
# ⭐⭐ THE PRODUCTION COMMAND, and every part of it is a decision:
gunicorn app:app -k uvicorn.workers.UvicornWorker -w 4 --bind 0.0.0.0:8000 --timeout 30
#                 ⭐ ASGI worker class          ⭐⭐ 4 PROCESSES  ⭐ never 127.0.0.1 in a container
```

```
⭐⭐ WHY PROCESSES AND NOT THREADS — the whole Python deployment story in four lines:
⭐   · ⭐⭐ THE GIL means threads do not give you CPU parallelism (Day 065)
⭐   · ⇒ ⭐⭐ you need PROCESSES for multiple cores
⭐   · ⇒ ⭐ and an EVENT LOOP inside each process for I/O concurrency (Days 014, 016)
⭐   · ⇒ ⭐⭐ so: WORKERS ≈ CORES (a common start is 2×cores+1 for sync, ~1×cores for async)
⭐
⭐⭐ AND THE CONSEQUENCE THAT KEEPS BITING (Days 003, 016, 017):
⭐   ⭐⭐ EACH WORKER IS A SEPARATE PROCESS WITH SEPARATE MEMORY.
⭐   ⇒ no shared dict, no shared cache, no shared set of WebSockets, no shared rate-limit counter.
⭐   ⇒ ⭐⭐ Anything shared lives in Redis or the database. There is no third option.
```

⭐ **In front of it: a reverse proxy** (Day 018) for TLS, static files, buffering slow clients, and
request limits. ⭐⭐ **Uvicorn is not hardened to face the internet directly** — and the buffering
point is real: without it, one slow reader occupies a worker for the duration.

# Part 3 — ⭐⭐ Configuration, and the rule that prevents the worst outage

```
⭐⭐ THE 12-FACTOR RULE: CONFIG LIVES IN THE ENVIRONMENT, NOT IN THE ARTEFACT.
⭐   ⇒ ⭐ the same image runs in dev, staging and production
⭐   ⇒ ⭐⭐ and secrets are never committed. Ever. Not once. Not "temporarily".

⭐ DATABASE_URL=postgres://...        ⭐ LOG_LEVEL=info
⭐ REDIS_URL=redis://...              ⭐ ENV=production
```

```python
# ⭐ Pydantic Settings — validated config, and it FAILS AT STARTUP rather than at 3am.
from pydantic_settings import BaseSettings
class Settings(BaseSettings):
    database_url: str                 # ⭐⭐ no default ⇒ missing env var ⇒ the app REFUSES TO START
    debug: bool = False               # ⭐⭐ default FALSE. Never True.
settings = Settings()
```

⚠️ ⭐⭐ **Fail fast on missing configuration.** A service that starts happily and discovers at the
first request that `DATABASE_URL` is unset has converted a deploy-time error into a user-facing
outage. **Validate everything at import time.**

⚠️ ⭐⭐ **`DEBUG=True` in production is a genuine, common, catastrophic bug** — Django's debug page
and FastAPI's tracebacks expose source code, environment variables, and often database credentials to
anyone who can trigger an exception. **It is a data breach delivered as a 500 page.**

## ⭐ Static assets, and where the front end goes

```
⭐⭐ The build output (Day 015) is a folder of HASHED files. It does NOT belong in Python.
⭐   ⇒ ⭐ serve it from S3 + CloudFront, Netlify, or nginx — ⭐⭐ never from your app workers
⭐   ⇒ ⭐ hashed names ⇒ Cache-Control: max-age=31536000, immutable
⭐   ⇒ ⭐⭐ index.html ⇒ NO-CACHE (it is the file that points at the new hashes)
⭐   ⇒ ⭐ that pair is the entire cache strategy, and it needs no invalidation (Day 018).
```

| ⭐ Deploy strategy | ⭐ How | ⭐ Cost |
|---|---|---|
| ⭐ Rolling | replace workers a few at a time | ⭐⭐ **two versions live at once** — your DB migrations must tolerate that |
| ⭐ Blue/green | run both, switch traffic | double the resources; instant rollback |
| Canary | 5% of traffic first | ⭐ best signal, most machinery |
| ⚠️ Recreate | stop all, start all | ⭐ downtime |

⭐⭐ **The rolling-deploy consequence is the one that catches people, and it is a Stage 5 rule stated
early: a migration that drops or renames a column breaks the old workers that are still running.**
The safe shape is **expand → migrate → contract**: add the new column, deploy code that writes both
and reads new, backfill, then remove the old column in a *later* deploy.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Rebuilding per environment** | ⭐⭐ Build once. Otherwise staging tested different bytes. |
| ⭐ `pip install` at container start | ⭐⭐ Slow, network-dependent, unpinned. Install at build. |
| No lock file | ⭐ "It worked yesterday" is then a real sentence. |
| Config baked into the image | ⭐ Inject from the environment. |
| ⭐⭐ **Secrets in git** | ⭐⭐ Assume permanently compromised; rotate, don't just delete. |
| ⭐⭐ **`DEBUG=True` in production** | ⭐⭐ Tracebacks leak source and credentials. |
| Config that fails at first request | ⭐ Validate at startup. Fail fast. |
| Threads for CPU parallelism | ⭐⭐ The GIL. Use processes/workers. |
| Shared state between workers | ⭐⭐ Separate processes, separate memory. Redis. |
| Uvicorn exposed directly | ⭐ Reverse proxy for TLS, static files, buffering. |
| ⭐ Dropping a column in a rolling deploy | ⭐⭐ Old workers are still running. Expand → migrate → contract. |
| Serving static files from Python | ⭐ CDN. Hash the names, cache forever, never cache `index.html`. |

## Interview questions

**Q: What does "deploying" actually involve?**
> Building an immutable artefact once, shipping it, and running it with configuration injected from
> the environment. For Python that artefact is usually a container image, because the language has no
> self-contained executable and the dependencies include compiled extensions and system libraries —
> a container freezes the interpreter, the libraries and the OS packages together. Config stays
> outside the image so the same bytes run in staging and production, which is the only thing that
> makes staging meaningful.

**Q: How do you run a FastAPI app in production?**
> Gunicorn managing several uvicorn workers, behind a reverse proxy. The worker count is roughly the
> core count, because the GIL means threads don't give CPU parallelism, so parallelism comes from
> processes and I/O concurrency comes from the event loop inside each one. The proxy does TLS, serves
> static files, and buffers slow clients so one slow reader can't occupy a worker. And each worker is
> a separate process with separate memory, so anything shared — sessions, caches, rate-limit
> counters, WebSocket registries — lives in Redis.

**Q: Why not just run more threads?**
> Because of the GIL: only one thread executes Python bytecode at a time, so threads give concurrency
> for blocking I/O but no CPU parallelism. Processes give real parallelism at the cost of memory and
> no shared state. In an async app the loop already covers I/O concurrency far more cheaply than
> threads, so the useful axis is processes.

**Q: What breaks in a rolling deploy?**
> Anything that assumes one version is running. During a rolling deploy old and new workers serve
> traffic simultaneously, so a migration that drops or renames a column breaks the old code that's
> still live. The safe pattern is expand-migrate-contract: add the new column, ship code that writes
> both and reads the new one, backfill, and only remove the old column in a later deploy once nothing
> references it.

**Q: How do you handle static assets?**
> They're built into hashed filenames and served from a CDN, never from the application workers.
> Hashed files get a one-year immutable cache header because the URL changes whenever the content
> does, so invalidation never comes up. `index.html` is the exception — it references the hashes, so
> it must not be cached.

**Q: Where do secrets live?**
> In the environment, injected by the platform's secret manager — never in the image, never in the
> repository. If one has ever been committed I treat it as compromised and rotate it, because
> deleting the commit doesn't remove it from clones, forks or anyone's local history.

## 🎙️ Articulation drill

Record two minutes: **"Walk me through deploying your project."**

⭐ Push triggers CI: tests, lint, type-check, then **build a Docker image tagged with the commit
SHA** — ⭐⭐ **once**, and that exact image is what reaches production. ⭐ Push to a registry, roll out
behind a load balancer with a readiness probe that touches the database, and keep the previous image
so rollback is a tag change rather than a rebuild.

⭐ Config and secrets come from the environment; the app validates them at import and **refuses to
start if anything is missing**. Static assets are hashed and served from a CDN, immutable for a year,
with `index.html` uncached.

⭐⭐ **Then the sentence that shows you have actually operated something:** *"During the rollout two
versions are live at once, so migrations are expand-migrate-contract — I never drop a column in the
same deploy as the code that stopped using it."*
