# Part 1 — Route 53, and the honest limits of DNS failover

```
⭐ THE PARTS: ⭐ hosted zones (public and private), ⭐ record
⭐   types, ⭐ health checks, ⭐ routing policies.

⭐⭐ ***ALIAS RECORDS ARE THE ONE THING TO ACTUALLY LEARN.***
⭐   ⭐ AWS-specific, ⭐ resolve to an AWS resource, ⭐⭐ FREE TO
⭐     QUERY, ⭐ and — the reason they exist — ⭐⭐ THEY WORK AT
⭐     THE ***ZONE APEX***, WHERE A CNAME IS FORBIDDEN BY THE
⭐     DNS SPEC. ⭐ `example.com → ALB` needs an alias; a CNAME
⭐     there is invalid.

⭐ ROUTING POLICIES, AND WHAT EACH IS FOR:
⭐   ⭐ SIMPLE ..... one answer.
⭐   ⭐⭐ WEIGHTED ... ***CANARY AT THE DNS LAYER*** (DAY 371) —
⭐     ⭐ 99/1 to send 1% at a new stack. ⭐⭐ COARSE, BUT IT WORKS
⭐     ACROSS ENTIRELY SEPARATE INFRASTRUCTURE, WHICH NO LOAD
⭐     BALANCER CAN DO.
⭐   ⭐ LATENCY .... nearest region by measured latency.
⭐   ⭐ FAILOVER ... primary/secondary on a health check.
⭐   ⭐ GEO / GEOPROXIMITY ... compliance and content rules.
⭐   ⭐ MULTIVALUE . up to 8 healthy answers, ⭐ a poor man's
⭐     balancer.

⭐⭐ AND THE HONEST LIMIT, WHICH IS THIS STAGE'S RECURRING
⭐   LESSON FOR THE FOURTH TIME:
⭐   ⭐⭐ ***DNS FAILOVER'S REAL RTO IS TTL + HOW LONG CLIENTS
⭐   TAKE TO OBEY IT — AND MANY CLIENTS DO NOT OBEY IT AT ALL.***
⭐   ⭐ Browsers pin. ⭐ JVMs cache. ⭐⭐ AND CONNECTION POOLS HOLD
⭐     OPEN SOCKETS THAT NEVER RE-RESOLVE (DAYS 387, 388, 390).
⭐   ⭐⭐ ⇒ SO DNS FAILOVER IS A ***COARSE*** TOOL: MINUTES, NOT
⭐     SECONDS, AND WITH A LONG TAIL. ⭐ Use it for regional
⭐     failover. ⭐⭐ NEVER RELY ON IT FOR SUB-MINUTE RECOVERY
⭐     INSIDE A REGION — ⭐ that is the load balancer's job.
```

# Part 2 — What CloudFront actually does

```
⭐ ① ⭐⭐ ***IT TERMINATES TLS AT THE EDGE.*** ⭐ A handshake is
⭐    2–3 round trips; ⭐ for a user 200 ms away that is 400–600
⭐    ms ⭐⭐ BEFORE THE FIRST BYTE OF REQUEST. ⭐ Terminating 20 ms
⭐    away and reusing a warm backbone connection to the origin
⭐    ⭐⭐ SPEEDS UP ***UNCACHEABLE*** REQUESTS TOO — ⭐ which is
⭐    the benefit people do not expect.
⭐ ② ⭐ It caches.
⭐ ③ ⭐⭐ ***IT CHANGES THE BILL, USUALLY DOWNWARD, EVEN AT A 0%
⭐    HIT RATE.*** ⭐ Origin→edge transfer is ***free***, and
⭐    edge→user is cheaper than S3 or EC2 egress. ⭐⭐ SO PUTTING
⭐    CLOUDFRONT IN FRONT OF S3 IS CLOSE TO A PURE WIN, WHICH IS
⭐    WHY DAY 386 SAID SO.
⭐ ④ ⭐ It absorbs volumetric attacks before they reach you, and
⭐    it is where WAF lives.

⭐ BEHAVIOURS: ⭐ per path pattern, ⭐ ordered, ⭐ each with its own
⭐   cache policy, origin, and allowed methods. ⭐⭐ THE NORMAL
⭐   SHAPE IS THREE: ⭐ `/static/*` cached hard, ⭐ `/api/*` not
⭐   cached at all, ⭐ `default` cached briefly.
```

# Part 3 — ⭐⭐ The cache key is a security boundary

```
⭐⭐ ***THE CACHE KEY DEFINES WHAT COUNTS AS "THE SAME REQUEST".
⭐   IF TWO DIFFERENT USERS' REQUESTS PRODUCE THE SAME KEY, THEY
⭐   GET THE SAME RESPONSE.*** ⭐ That sentence is the whole
⭐   security model.

⭐ BY DEFAULT THE KEY IS: ⭐ host + path (+ whatever query
⭐   strings, headers and cookies you explicitly add).
⭐   ⭐⭐ NOTE WHAT IS ***NOT*** THERE BY DEFAULT: ***THE
⭐   `Authorization` HEADER AND THE SESSION COOKIE.***

⭐⭐ SO THE FAILURE IS TWO CONFIGURATION LINES APART:
⭐   ⭐ `/api/me` returns the logged-in user's profile.
⭐   ⭐ Someone caches it to "reduce origin load".
⭐   ⭐⭐ ALICE'S RESPONSE IS STORED UNDER THE KEY `host + /api/me`.
⭐   ⭐⭐ BOB REQUESTS `/api/me` AND RECEIVES ALICE'S PROFILE.
⭐   ⭐ At the edge nearest Bob. ⭐ For the TTL. ⭐⭐ TO EVERYONE.

⭐⭐ THE FOUR RULES, AND THEY ARE NOT OPTIONAL:
⭐ ① ⭐⭐ ***AUTHENTICATED PATHS GET THEIR OWN BEHAVIOUR WITH
⭐    CACHING DISABLED.*** ⭐ Not "a short TTL" — ⭐⭐ DISABLED.
⭐    ⭐ Use the managed `CachingDisabled` policy.
⭐ ② ⭐ The origin sets `Cache-Control: private, no-store` on
⭐    anything user-specific. ⭐⭐ DEFENCE IN DEPTH: THE ORIGIN
⭐    SHOULD BE CORRECT EVEN IF THE DISTRIBUTION IS
⭐    MISCONFIGURED.
⭐ ③ ⭐ If you genuinely must cache per-user, ⭐⭐ THE VARYING
⭐    DIMENSION MUST BE ***IN THE KEY*** — ⭐ and understand that
⭐    a per-user key gives you a near-zero hit rate, ⭐⭐ WHICH
⭐    USUALLY MEANS YOU WANTED A DIFFERENT DESIGN.
⭐ ④ ⭐⭐ ***CACHE POISONING VIA UNKEYED INPUT***: ⭐ if your app
⭐    builds a response using a header that is ***forwarded but
⭐    not keyed*** (`X-Forwarded-Host`, a custom header), ⭐⭐ AN
⭐    ATTACKER POISONS THE CACHED COPY FOR EVERY USER. ⭐ Rule:
⭐    ⭐⭐ ***ANY INPUT THAT CHANGES THE RESPONSE MUST BE IN THE
⭐    KEY, OR MUST NOT BE FORWARDED.***

⭐ ⭐ And `Vary` interacts with all of this. ⭐⭐ `Vary: *` MEANS
⭐   NOTHING IS CACHEABLE; ⭐ a `Vary` on a header you did not
⭐   key on is a bug in one direction or the other.
```

# Part 4 — Invalidation is a smell; versioned URLs are the design

```
⭐ INVALIDATION: ⭐ minutes to propagate, ⭐ rate-limited,
⭐   ⭐ first 1,000 paths/month free then $0.005 each.
⭐   ⭐⭐ AND IT IS SLOWEST EXACTLY WHEN YOU NEED IT — DURING AN
⭐   INCIDENT.

⭐⭐ ⇒ ***CONTENT-ADDRESSED URLs REMOVE THE PROBLEM*** (DAY 327):
⭐   ⭐ `app.a1b2c3d4.js` with `Cache-Control: public, max-age=31536000,
⭐     immutable`
⭐   ⭐⭐ YOU NEVER INVALIDATE. YOU ***PUBLISH A NEW NAME***, and
⭐     the HTML that references it is the only short-TTL object.
⭐   ⭐ One tiny document is the only thing that must ever be
⭐     invalidated, ⭐⭐ AND ROLLBACK IS ALSO FREE, BECAUSE THE OLD
⭐     FILES STILL EXIST AT THEIR OLD NAMES.

⭐⭐ AND THE TWO DIRECTIVES THAT ARE AVAILABILITY FEATURES, NOT
⭐   PERFORMANCE ONES:
⭐   ⭐⭐ `stale-while-revalidate=60` — ⭐ serve the stale copy
⭐     instantly and refresh in the background. ⭐⭐ THE USER NEVER
⭐     WAITS FOR YOUR ORIGIN.
⭐   ⭐⭐ `stale-if-error=86400` — ⭐⭐ ***YOUR SITE KEEPS SERVING
⭐     WHILE YOUR ORIGIN IS COMPLETELY DOWN.*** ⭐ For a
⭐     content-heavy site this is the single highest-leverage
⭐     availability line you will ever write, ⭐⭐ AND IT COSTS
⭐     NOTHING. ⭐ Pair with a CloudFront custom error page.
```

# Part 5 — ⭐⭐ Your origin is still directly reachable

```
⭐⭐ THE MISTAKE THAT MAKES THE WHOLE EDGE DECORATIVE:
⭐   ⭐ You put CloudFront in front, attach WAF, add rate
⭐     limiting, feel secure.
⭐   ⭐⭐ AND `alb-1234.eu-west-1.elb.amazonaws.com` IS STILL
⭐     PUBLIC, SO ANYONE WHO FINDS IT — AND CERTIFICATE
⭐     TRANSPARENCY LOGS AND OLD DNS RECORDS MAKE THAT EASY —
⭐     SKIPS EVERY CONTROL YOU JUST BOUGHT.

⭐ LOCK IT DOWN, PER ORIGIN TYPE:
⭐   ⭐⭐ ① S3 ORIGIN → ***ORIGIN ACCESS CONTROL.*** ⭐ The bucket
⭐      policy allows only this distribution's service principal.
⭐      ⭐ Bucket stays entirely private (Day 386).
⭐   ⭐⭐ ② ALB ORIGIN → ***TWO CONTROLS, BOTH CHEAP:***
⭐      ⭐ (a) restrict the ALB's security group to the
⭐        ***CloudFront managed prefix list*** — ⭐⭐ ONE LINE, AND
⭐        AWS MAINTAINS THE IP RANGES FOR YOU;
⭐      ⭐ (b) have CloudFront send a secret custom header and
⭐        make the ALB listener rule require it — ⭐⭐ SO EVEN
⭐        ANOTHER PERSON'S CLOUDFRONT DISTRIBUTION CANNOT USE
⭐        YOUR ORIGIN. ⭐ Rotate it like any secret (Day 372).
⭐   ⭐ ③ Do both. ⭐⭐ THE PREFIX LIST STOPS THE INTERNET; THE
⭐      HEADER STOPS OTHER CLOUDFRONT CUSTOMERS.

⭐ ⭐ Same logic for API Gateway: a private/regional endpoint
⭐   plus a resource policy, ⭐⭐ NOT AN EDGE-OPTIMISED ENDPOINT
⭐   THAT ANYONE CAN CALL DIRECTLY.
```

# Part 6 — API Gateway vs ALB, decided by five questions

```
⭐ THE THREE PRODUCTS:
⭐   ⭐ REST API — ⭐ the original. ⭐ Every feature. ⭐⭐ ~$3.50/M
⭐     REQUESTS.
⭐   ⭐⭐ HTTP API — ***~$1.00/M, ROUGHLY 70% CHEAPER***, ⭐ lower
⭐     latency, ⭐ JWT authorisers, ⭐⭐ AND ENOUGH FOR MOST THINGS.
⭐     ⭐ Start here.
⭐   ⭐ WebSocket API — for the case that needs it.

⭐⭐ CHOOSE API GATEWAY OVER AN ALB WHEN YOU NEED:
⭐   ⭐ ① usage plans and API keys (⭐⭐ SELLING AN API)
⭐   ⭐ ② request validation and transformation at the edge
⭐   ⭐ ③ per-route authorisers (JWT / Lambda)
⭐   ⭐ ④ per-method throttling
⭐   ⭐ ⑤ Lambda targets with no infrastructure at all
⭐⭐ CHOOSE AN ALB WHEN:
⭐   ⭐⭐ ① VOLUME — ⭐ at 100M requests/month, HTTP API is ~$100
⭐     and an ALB is ~$25 plus LCU. ⭐⭐ THE CROSSOVER ARRIVES
⭐     SOONER THAN PEOPLE EXPECT.
⭐   ⭐⭐ ② ***LONG REQUESTS*** — ⭐ API Gateway's integration
⭐     timeout is ***29–30 seconds***. ⭐ (It became raisable on
⭐     REST APIs with a quota increase; ⭐⭐ DESIGN AS IF IT IS A
⭐     HARD CEILING, BECAUSE A 30-SECOND API CALL IS A DESIGN
⭐     PROBLEM ANYWAY — DAY 393.)
⭐   ⭐ ③ you already run containers and want one fewer thing.

⭐ ⭐ Both sit behind CloudFront happily. ⭐⭐ AND FOR A CONTAINER
⭐   API, THE COMMON GOOD ANSWER IS CLOUDFRONT → ALB → ECS, WITH
⭐   NO API GATEWAY AT ALL.
```

# Part 7 — WAF, and edge compute

```
⭐ WAF: ⭐ managed rule groups (common, bad inputs, SQLi,
⭐   ⭐⭐ AND THE IP REPUTATION LIST, WHICH IS THE ONE THAT EARNS
⭐   ITS KEEP), ⭐ plus your own rules.
⭐   ⭐⭐ ***DEPLOY IN `COUNT` MODE FIRST.*** ⭐ Managed rules
⭐     ***will*** block legitimate traffic — ⭐ a JSON body that
⭐     looks like SQL, an upload that looks like a shell command.
⭐     ⭐⭐ COUNT FOR A WEEK, READ THE SAMPLES, THEN BLOCK.
⭐   ⭐⭐ AND THE HONEST FRAMING (DAY 335): ***WAF IS A FILTER,
⭐     NOT A FIX. IT BUYS TIME.*** ⭐ The part that actually stops
⭐     the common attack is the ⭐⭐ RATE-BASED RULE — ⭐ requests
⭐     per five minutes per IP — ⭐ and that is also the part
⭐     that needs the most tuning, ⭐⭐ BECAUSE ONE CORPORATE NAT
⭐     IS ONE IP FOR TWO THOUSAND USERS.
⭐ ⭐ Shield Standard is free and automatic. ⭐ Shield Advanced is
⭐   $3,000/month ⭐⭐ AND IS BOUGHT FOR THE RESPONSE TEAM AND THE
⭐   BILL PROTECTION, NOT THE FILTERING.

⭐ EDGE COMPUTE, AND THE CHOICE IS EASY:
⭐   ⭐⭐ CLOUDFRONT FUNCTIONS — ⭐ sub-millisecond, JS only, no
⭐     network access, ⭐ ~1/6th the price. ⭐⭐ FOR HEADER
⭐     MANIPULATION, REDIRECTS, URL REWRITES, ⭐ and normalising
⭐     the cache key. ⭐⭐ THIS COVERS 90% OF REAL NEEDS.
⭐   ⭐ LAMBDA@EDGE — ⭐ real runtime, can call the network,
⭐     ⭐⭐ MUCH SLOWER AND CHARGED PER REQUEST AT EVERY EDGE.
⭐     ⭐ For auth checks needing a lookup, or origin selection.
⭐   ⭐⭐ AND NOTE: ***PYTHON IS NOT AVAILABLE IN CLOUDFRONT
⭐     FUNCTIONS AND LAMBDA@EDGE SUPPORTS NODE AND PYTHON*** —
⭐     ⭐ check current support before designing around it.
```

# 💬 Interview

**1. ⭐⭐ "Why is the cache key a security boundary?"**
> ⭐ Because it defines what counts as the same request — ⭐⭐ **and if two users' requests produce the
> same key, they get the same response.** ⭐ The default key is host and path; the `Authorization`
> header and the session cookie are *not* in it. ⭐⭐ **So if someone caches `/api/me` to reduce origin
> load, Alice's profile is stored under that key and Bob gets it — at the edge nearest Bob, for the
> whole TTL, for everyone.** ⭐ The rules are: authenticated paths get their own behaviour with caching
> disabled, not a short TTL; the origin sends `Cache-Control: private, no-store` as defence in depth;
> and if you must vary, the varying dimension goes in the key — ⭐⭐ **though a per-user key gives you a
> near-zero hit rate, which usually means you wanted a different design.** ⭐ Plus the poisoning case:
> ⭐⭐ **any input that changes the response must be in the key or must not be forwarded**, or an
> attacker poisons the cached copy for everyone.

**2. "How do you invalidate a CDN?"**
> ⭐⭐ **You design so you don't have to.** ⭐ Invalidation takes minutes, is rate-limited, costs money
> past a thousand paths, and is slowest exactly when you need it — during an incident. ⭐⭐ **So assets
> get content-addressed names with a one-year immutable max-age, and you publish a new name instead of
> invalidating an old one** — the only short-TTL object is the small HTML document that references
> them. ⭐ Rollback is free too, because the old files still exist at their old names. ⭐ And I'd add the
> two directives people treat as performance and are actually availability: ⭐⭐ **`stale-while-revalidate`
> so users never wait on the origin, and `stale-if-error`, which keeps the site serving while the
> origin is completely down — the highest-leverage availability line you can write, and it's free.**

**3. ⭐⭐ "You put CloudFront and WAF in front. Are you protected?"**
> ⭐ Not yet — ⭐⭐ **the ALB's own DNS name is still public, and certificate transparency logs and stale
> DNS records make it easy to find, so anyone who does skips every control you just bought.** ⭐ Two
> cheap fixes and I'd do both: restrict the ALB's security group to the CloudFront managed prefix
> list, which is one line and AWS maintains the ranges; ⭐⭐ **and have CloudFront send a secret custom
> header that the listener rule requires, so even someone else's CloudFront distribution can't use
> your origin.** ⭐ The prefix list stops the internet, the header stops other CloudFront customers.
> ⭐ For S3 origins it's Origin Access Control and the bucket stays private.

**4. "How reliable is DNS failover?"**
> ⭐ Coarse. ⭐⭐ **The real RTO is the TTL plus how long clients take to obey it, and many clients don't
> obey it at all — browsers pin, JVMs cache, and connection pools hold open sockets that never
> re-resolve.** ⭐ So it's minutes with a long tail, which is fine for regional failover ⭐⭐ **and wrong
> for sub-minute recovery inside a region — that's the load balancer's job.** ⭐ Where Route 53 is
> genuinely good is weighted routing as a canary, ⭐⭐ **because it works across entirely separate
> infrastructure, which no load balancer can do.**

**5. "API Gateway or an ALB?"**
> ⭐ API Gateway when I need what it uniquely does: usage plans and API keys if I'm selling the API,
> request validation, per-route authorisers, per-method throttling, or Lambda targets with no
> infrastructure. ⭐ And HTTP API rather than REST API — ⭐⭐ **it's about 70% cheaper and enough for most
> things.** ⭐ ALB when volume matters — ⭐⭐ **at a hundred million requests a month HTTP API is roughly
> $100 and an ALB is $25 plus LCUs, so the crossover arrives sooner than people expect** — or when I
> need requests longer than the 29-second integration timeout, ⭐⭐ **though I'd treat that as a hard
> ceiling regardless, because a 30-second synchronous API call is a design problem.** ⭐ For a
> container API the common good answer is CloudFront → ALB → ECS with no API Gateway at all.

**6. "How do you roll out WAF?"**
> ⭐⭐ **Count mode first, for a week.** ⭐ Managed rules will block legitimate traffic — a JSON body
> that looks like SQL, an upload that looks like a shell command — so I read the sampled requests
> before switching anything to block. ⭐⭐ **And I'd be honest that WAF is a filter, not a fix: it buys
> time. The part that stops the common attack is the rate-based rule**, and that's also the part
> needing the most tuning, ⭐⭐ **because one corporate NAT is a single IP for two thousand users.**

## 🎙️ Articulation drill

**Two minutes.** Reframe first: **a CDN isn't a performance decision, it's a decision about what
counts as the same request — and the cache key defines that, so the cache key is a security
boundary.** Make it concrete: **the default key is host and path; the Authorization header and session
cookie aren't in it. So caching `/api/me` to reduce origin load stores Alice's profile under that key
and serves it to Bob, at the edge nearest Bob, for the whole TTL.** Rules: authenticated paths get
caching **disabled**, not shortened; the origin sends `private, no-store` as defence in depth; **and
any input that changes the response is in the key or isn't forwarded, or an attacker poisons the
cached copy for everyone.** Then the design point: **invalidation is minutes, rate-limited and slowest
during an incident — so content-address the assets with a one-year immutable max-age and publish a new
name instead. Rollback becomes free, because the old files still exist.** Add the availability
directives: **`stale-if-error` keeps the site serving while the origin is entirely down, and it's
free.** Then the thing people miss: **CloudFront and WAF in front doesn't protect you while the ALB's
own hostname is public — certificate transparency logs make it findable, and anyone who does skips
every control. Restrict the security group to the CloudFront prefix list and require a secret custom
header: the first stops the internet, the second stops other CloudFront customers.** Close on DNS:
**failover's real RTO is the TTL plus how long clients obey it, and pools holding open sockets never
re-resolve at all — so it's a coarse regional tool, minutes with a long tail, and never the answer for
sub-minute recovery inside a region.**
