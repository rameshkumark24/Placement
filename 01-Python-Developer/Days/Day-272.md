# Part 1 — ⭐⭐ The eight

```
⭐⭐ THIS IS THE WHOLE SET. BUILD THESE, STOP.

⭐ ① ⭐ Button      — variant × size × state (Day 224: unions, not booleans)
⭐ ② ⭐ Input       — ⭐⭐ WITH label, error text and aria wiring BUILT IN
⭐ ③ ⭐⭐ Card       — the container everything sits in
⭐ ④ ⭐ Badge       — status. ⭐⭐ YOUR DOMAIN'S STATE MACHINE, VISIBLE
⭐ ⑤ ⭐ Skeleton    — the loading shape (Day 240)
⭐ ⑥ ⭐⭐ EmptyState — icon + message + ACTION. ⭐ Takes 20 minutes and
⭐                    it is the most-noticed component you will write
⭐ ⑦ ⭐⭐ ErrorState — message + retry, branched by status
⭐ ⑧ ⭐ Dialog      — ⭐⭐ FROM A LIBRARY. Do NOT hand-roll focus
⭐                    trapping (Day 239)

⭐ ⭐ PLUS THREE LAYOUT PRIMITIVES, NOT COMPONENTS: Stack, Row, Grid
⭐   (Day 238) — ⭐⭐ these do 90% of your layout with no CSS files.
```

| ⭐ Deliberately absent | Why |
|---|---|
| Table | ⭐ Build the *one* table your app needs, in place. A generic table is a two-week project. |
| Select / Combobox | ⭐⭐ From a library. Keyboard + ARIA + filtering is genuinely hard. |
| Toast | ⭐ From a library, or skip — inline errors are usually better anyway |
| Tabs, Accordion, Tooltip | ⭐ Only if the demo path needs one |

# Part 2 — ⭐⭐ Every component gets its states

```
⭐⭐ THE CHECKLIST. A COMPONENT IS NOT DONE UNTIL ALL FIVE EXIST.

⭐   ① DEFAULT
⭐   ② ⭐ HOVER      ⇒ ⭐⭐ A BUTTON WITH NO HOVER FEELS BROKEN
⭐   ③ ⭐⭐ FOCUS     ⇒ :focus-visible ring. NEVER outline:none (Day 239)
⭐   ④ ⭐ DISABLED   ⇒ ⭐⭐ AND `disabled`, NOT JUST GREY — a grey
⭐                     button that still fires is worse than none
⭐   ⑤ ⭐⭐ LOADING   ⇒ on anything that triggers a request.
⭐                     ⭐ Keep the WIDTH stable — a button that shrinks
⭐                       to fit a spinner moves everything beside it.
```

```tsx
type ButtonProps = {
  variant?: "primary" | "secondary" | "danger";   // ⭐ unions (Day 224)
  size?: "sm" | "md";
  loading?: boolean;
  children: React.ReactNode;
} & React.ButtonHTMLAttributes<HTMLButtonElement>;

export function Button({ variant = "primary", size = "md",
                         loading, disabled, children, ...rest }: ButtonProps) {
  return (
    <button
      {...rest}
      disabled={disabled || loading}          // ⭐⭐ loading implies disabled
      aria-busy={loading || undefined}        // ⭐ announced to screen readers
      data-variant={variant} data-size={size}
    >
      {loading ? <Spinner aria-hidden /> : null}
      <span style={{ visibility: loading ? "hidden" : undefined }}>
        {children}                            {/* ⭐⭐ WIDTH HELD — no jump */}
      </span>
    </button>
  );
}
```

> ⭐ **`{...rest}` before your own props** so callers can pass `type="submit"`, `aria-label`, or
> `onFocus` without you enumerating every HTML attribute. ⭐⭐ And **`type="button"` should be your
> default** — a `<button>` inside a form submits it, which is the cause of a great many "the page
> reloaded when I clicked" bugs.

# Part 3 — ⭐⭐ The abstraction trap

```
⭐⭐ THE HOUR YOU ARE ABOUT TO LOSE

⭐   You write <Card>. ⭐ Then you think: "what if someone wants a
⭐   header? a footer? a collapsible variant? a different padding?"
⭐   ⇒ ⭐⭐ YOU ARE NOW BUILDING FOR A CALLER THAT DOES NOT EXIST,
⭐     AND YOU WILL GUESS THE SEAM WRONG, BECAUSE YOU HAVE ONE
⭐     EXAMPLE AND ABSTRACTION NEEDS TWO.

⭐   ⭐⭐ THE RULE: WRITE IT CONCRETELY THE FIRST TIME. THE SECOND
⭐     TIME, COPY IT. ⭐ THE **THIRD** TIME, ABSTRACT — AND NOW YOU
⭐     HAVE THREE REAL EXAMPLES SHOWING YOU WHERE THE SEAM IS.
```

| ⭐ Smell | ⭐⭐ What it means |
|---|---|
| A prop with exactly one caller passing a non-default | ⭐ You invented a requirement |
| A component with a `variant` used once | ⭐⭐ Inline it |
| `children` **plus** a `content` prop | ⭐ Two ways to do one thing; pick one |
| Configuring padding from outside | ⭐⭐ Let the **parent** own spacing (`Stack` gap), not the child |

> ⭐⭐ **Duplication is cheaper than the wrong abstraction**, and this is the most reliably true
> statement in software design. Two similar cards you can edit independently beat one card with nine
> props that nobody dares change.

# Part 4 — Domain components

```
⭐⭐ THE COMPONENTS THAT MAKE THE PROJECT LOOK LIKE A PRODUCT
⭐   ARE NOT GENERIC ONES — THEY ARE YOURS.

⭐   <OrderStatusBadge status={o.status} />
⭐     ⇒ ⭐⭐ ONE PLACE THAT KNOWS YOUR STATE MACHINE'S COLOURS AND
⭐       LABELS. ⭐ Add a state to the enum ⇒ TypeScript makes you
⭐       handle it here (Day 218's exhaustive switch).
⭐   <Money amount={p} currency={c} />
⭐     ⇒ ⭐⭐ ONE PLACE THAT FORMATS MONEY. ⭐ Day 041: it is minor
⭐       units on the wire, never a float — and this component is
⭐       where that fact stops leaking into every screen.
⭐   <RelativeTime value={iso} />
⭐     ⇒ ⭐ "3 minutes ago", with a title= holding the exact
⭐       timestamp, and ⭐⭐ TIMEZONE HANDLED ONCE INSTEAD OF NEVER.
```

> ⭐ **These three are worth more than five generic components.** They encode a domain rule in one
> place, they make every screen consistent for free, and each one is a concrete answer when an
> interviewer asks *"how do you handle money / time / state?"*

## Today's build

1. Build the eight. ⭐⭐ **Time-box it to one session.** If you are still on Button after an hour, you are designing rather than building.
2. ⭐ Build the three layout primitives. Use **only** them for layout from here.
3. ⭐⭐ **Run the five-state checklist on every component.** Most will fail on focus or loading.
4. ⭐ Build `StatusBadge`, `Money` and `RelativeTime` for **your** domain.
5. ⭐⭐ Make the status badge switch exhaustive. Add a state to the enum on the server and watch the build fail.
6. ⭐ Find any prop you added "in case" and delete it. Count them.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "did you build a design system?"**

Answer with the scope, because the word invites overclaiming. **For one application, a design system is
a token file and about eight components — button, input, card, badge, skeleton, empty state, error
state, and a dialog I took from a library because focus trapping is genuinely hard. Plus three layout
primitives. The whole skill is stopping there.**

Then the discipline you applied. **Every component has five states: default, hover, focus, disabled and
loading. Focus and loading are the two everyone skips, and a button with no hover state feels broken
even when it works. My loading state holds the button's width, because a button that shrinks to fit a
spinner moves everything beside it.**

Then the trap you avoided, which is the real content. **I deliberately didn't generalise. The moment
you write a card you start imagining a caller who wants a header, a footer, a collapsible variant —
and you'll guess the seam wrong, because abstraction needs two examples and you have one. So: write it
concretely, copy it the second time, abstract on the third. Duplication is cheaper than the wrong
abstraction.**

Close on the components that actually matter. **The ones that make it look like a product aren't the
generic ones, they're mine — a status badge that owns my state machine's colours and labels, a money
component so the minor-units-on-the-wire rule lives in one place instead of leaking into every screen,
and a relative time component so timezones are handled once rather than never. The badge's switch is
exhaustive, so adding a state on the server fails the frontend build.**
