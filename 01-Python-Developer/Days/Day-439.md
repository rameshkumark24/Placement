# Part 2 — Four budgets, because they fail differently

```
⭐  ┌─────────────┬──────────────────────────────────────────┐
⭐  │ ① STEPS     │ ⭐⭐ CATCHES LOOPS. ⭐ 6–12 for most tasks. │
⭐  │             │ The doom loop (Day 440) is invisible to   │
⭐  │             │ every other budget until it is expensive. │
⭐  ├─────────────┼──────────────────────────────────────────┤
⭐  │ ② TOKENS    │ ⭐ catches ***one*** runaway tool result   │
⭐  │             │ that no step count would have caught.     │
⭐  ├─────────────┼──────────────────────────────────────────┤
⭐  │ ③ DOLLARS   │ ⭐⭐ THE ONE THE BUSINESS ACTUALLY HAS. ⭐   │
⭐  │             │ Steps and tokens both mispredict cost the │
⭐  │             │ moment you cascade models (Day 421).      │
⭐  ├─────────────┼──────────────────────────────────────────┤
⭐  │ ④ WALL-CLOCK│ ⭐⭐ THE USER'S BUDGET. ⭐ Steps are serial, │
⭐  │             │ so latency = n × (model + tool). ⭐ A       │
⭐  │             │ 12-step run at 3s/step is 36 seconds, and │
⭐  │             │ ⭐⭐ NOBODY WAITS 36 SECONDS AT A CHAT BOX. │
⭐  └─────────────┴──────────────────────────────────────────┘

⭐⭐ ONE BUDGET OBJECT, CHECKED BEFORE EVERY CALL AND EVERY
⭐   TOOL, ⭐ and propagated ***into*** tools as a deadline
⭐   (Day 401): ⭐⭐ A TOOL MUST NOT BE ALLOWED TO OUTLIVE THE
⭐   RUN THAT REQUESTED IT.
```

```python
@dataclass(slots=True)
class Budget:
    max_steps: int = 10
    max_tokens: int = 60_000
    max_usd: float = 0.50
    deadline: float = field(default_factory=lambda: time.monotonic() + 45)

    steps: int = 0
    tokens: int = 0
    usd: float = 0.0

    def remaining_s(self) -> float:
        return self.deadline - time.monotonic()   # ⭐ monotonic (Day 409)

    def check(self) -> None:
        if self.steps >= self.max_steps:   raise BudgetExceeded("steps")
        if self.tokens >= self.max_tokens: raise BudgetExceeded("tokens")
        if self.usd >= self.max_usd:       raise BudgetExceeded("usd")
        if self.remaining_s() <= 0:        raise BudgetExceeded("deadline")
```

# Part 3 — ⭐⭐ The four terminations, and what each owes the user

```
⭐ "DOES IT STOP?" IS THE EASY QUESTION. ⭐⭐ "WHAT DOES IT OWE
⭐   THE USER WHEN IT STOPS?" IS THE ONE THAT SEPARATES A DEMO
⭐   FROM A SYSTEM.

⭐ ① ***NATURAL FINISH*** — no tool call, text returned.
⭐   ⭐ ⇒ return the answer. ⭐ The only happy path.

⭐ ② ***BUDGET EXCEEDED.***
⭐   ⭐⭐ THE BUG EVERYONE SHIPS: RETURN THE LAST ASSISTANT
⭐     MESSAGE AS IF IT WERE THE ANSWER. ⭐ It is mid-thought,
⭐     often confident, and ⭐⭐ INDISTINGUISHABLE FROM A REAL
⭐     ANSWER TO THE USER.
⭐   ⭐ ⇒ ***ONE OF THREE DELIBERATE CHOICES:***
⭐     ⭐ ⓐ fail explicitly: "I couldn't complete this in the
⭐       time available" + ⭐⭐ WHAT WAS ALREADY DONE, BECAUSE
⭐       SIDE EFFECTS HAPPENED AND THE USER MUST KNOW;
⭐     ⭐ ⓑ one final call with tools ***disabled***: "summarise
⭐       what you found and what remains" — ⭐ cheap, honest,
⭐       and the best default for read-only agents;
⭐     ⭐ ⓒ hand off to a human with the trajectory attached.
⭐   ⭐ ⭐⭐ WHAT YOU MAY NOT DO IS RETURN PARTIAL WORK SILENTLY.

⭐ ③ ***TERMINAL ERROR*** — 403, invariant violated, cancelled.
⭐   ⭐ ⇒ stop immediately. ⭐⭐ REPORT COMPLETED SIDE EFFECTS.
⭐     ⭐ If some are not safely leavable, compensate (Day 411)
⭐       — ⭐⭐ AND COMPENSATION IS A NEW VISIBLE FACT, NOT AN
⭐       UNDO.

⭐ ④ ***HUMAN GATE*** — an irreversible action needs approval.
⭐   ⭐ ⇒ ⭐⭐ THE RUN MUST ***SUSPEND***, NOT BLOCK. ⭐ Which
⭐     means the state has to be serialisable, which means
⭐     Part 4.
```

# Part 4 — ⭐⭐ An agent run is a durable workflow

```
⭐ ***THE QUESTION THAT REFRAMES EVERYTHING:*** ⭐ your process
⭐   is redeployed at step 7 of 10. ⭐⭐ WHAT HAPPENS?

⭐ ⭐⭐ IF THE ANSWER IS "THE RUN IS LOST", YOU HAVE BUILT A
⭐   REQUEST HANDLER FOR SOMETHING THAT IS ***NOT A REQUEST***:
⭐   ⭐ it runs for 40 seconds,
⭐   ⭐ it has ***already performed side effects***,
⭐   ⭐ it may need to pause for a human for an hour,
⭐   ⭐ and it costs real money to redo.
⭐   ⭐⭐ THAT IS A WORKFLOW. STAGE 12 ALREADY TAUGHT YOU HOW TO
⭐     RUN ONE.

⭐ ***WHAT MAKES IT DURABLE — FOUR THINGS:***
⭐   ⭐ ① ***PERSIST THE TRANSCRIPT AFTER EVERY STEP.***
⭐     ⭐ The message list ***is*** the state. ⭐⭐ THERE IS NO
⭐       HIDDEN STATE IN THE MODEL (DAY 414) — WHICH IS EXACTLY
⭐       WHY THIS IS EASY.
⭐   ⭐ ② ***A RUN ID, AND AN IDEMPOTENCY KEY PER TOOL CALL***
⭐     (Day 444) — ⭐⭐ SO RESUMING DOES NOT RE-SEND THE EMAIL.
⭐   ⭐ ③ ***A STATUS FIELD***: running | waiting_human |
⭐     succeeded | failed | cancelled. ⭐ Suspension is then a
⭐     row update, not a blocked coroutine.
⭐   ⭐ ④ ***RESUME = LOAD TRANSCRIPT, CONTINUE LOOP.*** ⭐ Two
⭐     lines, ⭐⭐ IF ①–③ EXIST.

⭐ ***AND CANCELLATION, WHICH IS THE COMMON CASE:*** ⭐ the user
⭐   closes the tab mid-run. ⭐⭐ WITHOUT A CANCELLATION CHECK THE
⭐   LOOP KEEPS SPENDING MONEY ON AN ANSWER NOBODY WILL READ —
⭐   ⭐ and with tools, keeps ***taking actions*** on their
⭐   behalf. ⭐ Check the flag before each model call and each
⭐   tool.
```

# Part 6 — The loop, complete

```python
async def run_agent(run_id: str, messages: list[dict], tools, *,
                    tenant_id: str, budget: Budget, store) -> AgentResult:
    while True:
        budget.check()                                  # ⭐ raises on any of 4
        if await store.is_cancelled(run_id):
            return AgentResult.cancelled(messages)

        resp = await client.messages.create(
            model=MODEL, messages=messages, tools=tools.schemas,
            max_tokens=2048, timeout=min(30, budget.remaining_s()),
        )
        budget.steps += 1
        budget.tokens += resp.usage.input_tokens + resp.usage.output_tokens
        budget.usd += price(resp.usage)

        messages.append({"role": "assistant", "content": resp.content})
        await store.save(run_id, messages, budget)      # ⭐⭐ DURABLE, EVERY STEP

        calls = [b for b in resp.content if b.type == "tool_use"]
        if not calls:
            return AgentResult.finished(_text(resp), messages, budget)

        gated = [c for c in calls if tools[c.name].needs_approval]
        if gated:                                       # ⭐⭐ SUSPEND, NOT BLOCK
            await store.set_status(run_id, "waiting_human", pending=gated)
            return AgentResult.awaiting_approval(gated, messages, budget)

        results = await execute(calls, tools, tenant_id=tenant_id,
                                deadline_s=budget.remaining_s())
        messages.append({"role": "user", "content": results})
        await store.save(run_id, messages, budget)
```

```
⭐ ***AND THE CALLER, WHICH IS WHERE TERMINATION POLICY LIVES:***
⭐   ⭐ catch `BudgetExceeded` → ⭐⭐ ONE FINAL CALL WITH
⭐     `tools=[]` ASKING FOR AN HONEST SUMMARY OF PROGRESS,
⭐   ⭐ then return it ***labelled as incomplete***, with the
⭐     list of side effects already performed.
⭐   ⭐⭐ THE LABEL IS THE PRODUCT DECISION. ⭐ Everything else is
⭐     plumbing.
```

# 💬 Interview

**1. "What does an agent run cost?"**

⭐ Roughly quadratic in steps, because the whole transcript is resent every step and tool results are
big. ⭐⭐ A realistic ten-step run with 1,500-token tool results bills about 108,000 input tokens for a
conversation whose final state is 18,500 — you paid nearly six times the size of the thing you built.
⭐ At $2.50 per million that's 27 cents a run, so twenty thousand runs a day is $5,400. ⭐⭐ The single
biggest lever is prompt caching: the transcript is append-only, so every step's input is a prefix
extension of the last, which is near-perfect cache conditions and takes it to about five cents. ⭐ The
corollary is that you must never mutate earlier messages — one edit invalidates the cache from that
point on. ⭐ After that: shrink tool results, then reduce steps, which is quadratic so halving steps
quarters the bill.

**2. "What limits do you put on the loop?"**

⭐ Four, because they fail differently. ⭐ Steps catches loops — the doom loop is invisible to every
other budget until it's expensive. ⭐ Tokens catches a single runaway tool result that no step count
would have caught. ⭐⭐ Dollars is the one the business actually has, and it's the only one that stays
correct when you cascade models. ⭐ And wall-clock is the user's budget: steps are serial, so a
twelve-step run at three seconds a step is thirty-six seconds, and nobody waits that at a chat box.
⭐⭐ One budget object checked before every model call and every tool, with the remaining time
propagated into tools as a deadline — a tool must never outlive the run that requested it.

**3. "What happens when you hit MAX_STEPS?"**

⭐⭐ That's the real question, and the common bug is returning the last assistant message as if it were
the answer — it's mid-thought, it's confident, and the user can't tell it apart from a real answer.
⭐ So MAX_STEPS is a correctness boundary, not a safety net. ⭐ Three legitimate choices: fail explicitly
and say what was already done, because side effects happened and the user has to know; make one final
call with tools **disabled** asking for an honest summary of progress and what remains, which is my
default for read-only agents; or hand off to a human with the trajectory attached. ⭐⭐ What you may not
do is return partial work silently.

**4. "Your process restarts at step 7 of 10. What happens?"**

⭐ Nothing bad, because the run is a durable workflow rather than a request. ⭐⭐ The message list **is**
the state — there's no hidden state inside the model — so I persist the transcript after every step,
and resuming is loading it and continuing the loop. ⭐ There's a run id and an idempotency key per tool
call, so resuming doesn't re-send an email that already went out. ⭐ And a status field, so "waiting for
a human" is a row update rather than a blocked coroutine. ⭐⭐ If the honest answer had been "the run is
lost", I'd have built a request handler for something that runs forty seconds, performs side effects and
may need to pause for an hour — which is a workflow, and Stage 12 already covered how to run one.

**5. "The user closes the tab. What happens?"**

⭐ Without a cancellation check, the loop keeps spending money on an answer nobody will read — and with
tools, keeps **taking actions** on their behalf, which is the part that turns a cost problem into a
correctness problem. ⭐⭐ So the loop checks a cancellation flag before every model call and every tool,
and cancelling sets a status the loop observes. ⭐ Anything already done is recorded and reported, since
cancelling the run doesn't undo the emails it sent.

**6. "What do you show the user during a forty-second run?"**

⭐ The trajectory, not the tokens. ⭐⭐ Tool names mapped to human verbs — "searching contracts",
"checking renewal dates" — and never the raw arguments, which contain ids, internal field names and
sometimes other people's data. ⭐ I specifically don't stream intermediate reasoning as if it were the
answer, because users read it as a commitment and then the agent changes its mind at step six.
⭐⭐ Honestly, though, if a task takes forty seconds it probably shouldn't be a chat box: make it a job
with a reference and a notification. ⭐ That solves durability, cancellation and the human approval gate
in one move, because those are properties jobs already have and requests never do.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "how do you run an agent in production?"**

Start by reclassifying the thing. **An agent run isn't a request. It runs for forty seconds, it performs
side effects along the way, it might need to pause for a human for an hour, and redoing it costs real
money. That's a workflow, so it gets workflow machinery: a run id, a persisted transcript after every
step, a status field, and idempotency keys on tool calls. The nice property is that persisting it is
trivial — the message list *is* the state, because the model holds nothing between calls. Resume is load
the transcript and continue the loop.**

Then the money, with the number. **Cost is roughly quadratic in steps, because the whole transcript is
resent every step and tool results are big. A ten-step run with fifteen-hundred-token results bills
about a hundred and eight thousand input tokens for a conversation whose final state is eighteen
thousand — nearly six times over. Prompt caching is the fix and it's close to free: the transcript is
append-only, so every step is a prefix extension of the last. Twenty-seven cents a run down to about
five. The rule that falls out is never mutate earlier messages, because one edit invalidates the cache
from that point.**

Then the budgets and why there are four. **Steps catches loops. Tokens catches one runaway tool result
that no step count would catch. Dollars is the budget the business actually has and the only one that
survives model cascading. Wall-clock is the user's, and steps are serial so twelve steps at three
seconds is thirty-six — nobody waits that. All four in one object, checked before every model call and
every tool, with the remaining time pushed into tools as a deadline so nothing outlives the run.**

Close on the part that's a product decision rather than plumbing. **The interesting question isn't "does
it stop", it's "what does it owe the user when it stops early". The bug everyone ships is returning the
last assistant message as if it were the answer — it's mid-thought, it's confident, and it's
indistinguishable from a real answer. So we make one final call with tools disabled asking for an honest
summary of what was found and what remains, return it explicitly labelled incomplete, and list the side
effects that already happened, because those don't unhappen. That label is the whole difference between
a demo and a system.**
