# Day 183

**L-183** · ⚖️ **Choosing and migrating** — ⭐⭐ the decision framework, and the strangler that actually works

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: nobody rewrites a working system for technical reasons and succeeds — so
> the real questions are "what should we start with?" and "how do we add the new thing beside the old
> one without a rewrite?", and both have concrete answers.**
>
> ⭐ Day 182 compared them on one endpoint. ⭐⭐ Today: choosing for a real product, the migration
> question you will actually be asked, and the honest answer to "should we rewrite?"

# Part 1 — ⭐⭐ The decision, driven by the product

```
⭐⭐ THE FRAMEWORK QUESTION IS DOWNSTREAM OF FOUR PRODUCT QUESTIONS. ⭐ Ask
⭐   these instead, and the answer usually decides itself:

⭐  1. ⭐⭐ **IS THE DATA MODEL THE PRODUCT?**
⭐       ⭐ Resources with CRUD and relationships (a marketplace, a CMS, an
⭐       admin-heavy B2B tool) ⇒ ⭐⭐ DJANGO. ⭐ Django's gravity points at
⭐       models, and when your product does too, that gravity is free lift.
⭐       ⭐ Verbs and workflows (a payments engine, a scheduler, an ingestion
⭐       pipeline) ⇒ ⭐⭐ FASTAPI. ⭐ DRF wants resources; you will spend the
⭐       project explaining that `refund` is not a noun.
⭐
⭐  2. ⭐⭐ **WHO OPERATES IT DAY TO DAY?**
⭐       ⭐ Non-engineers looking things up and fixing data ⇒ ⭐⭐ THE ADMIN IS
⭐       WORTH MORE THAN EVERY OTHER FACTOR COMBINED. ⭐ Weeks of saved work,
⭐       repeatedly.
⭐       ⭐ Only engineers, only via API ⇒ that advantage is worth nothing.
⭐
⭐  3. ⭐⭐ **WHAT IS THE CONCURRENCY SHAPE?**
⭐       ⭐ Request in, query, respond ⇒ either; ⭐⭐ workers and threads solve
⭐       it and Little's Law tells you how many.
⭐       ⭐ Thousands of LONG-LIVED connections, or fan-out to many slow third
⭐       parties ⇒ ⭐⭐ FASTAPI, because Django's async ORM is a thread-pool
⭐       façade (Day 178).
⭐
⭐  4. ⭐⭐ **WHO ELSE WILL WORK ON IT?**
⭐       ⭐ A rotating team, or one you will hire into ⇒ ⭐⭐ DJANGO. Every
⭐       Django codebase looks like every other Django codebase; ⭐ every
⭐       FastAPI codebase is whatever its first engineer decided.
⭐       ⭐ That is not a small factor — ⭐⭐ it is the one senior engineers
⭐       weigh most and juniors mention least.
⭐
⭐   ⇒ ⭐⭐ AND THE TIEBREAK NOBODY SAYS OUT LOUD: **WHICH DO YOUR PEOPLE
⭐        ALREADY KNOW?** ⭐ A team fluent in one will out-deliver the same
⭐        team learning the other, for at least two quarters. ⭐⭐ Saying this
⭐        in an interview marks you as someone who has shipped rather than
⭐        someone who has benchmarked.
```

```
⭐⭐ AND THE FACTORS THAT ARE **NOT** DECISIVE, WITH THE REASON:
⭐   ⭐ ❌ "FASTAPI IS FASTER." ⭐⭐ Framework overhead is single-digit
⭐        milliseconds; your database query is 5–50 ms and your third-party
⭐        call is 200 ms. ⭐ The framework is not your latency.
⭐   ⭐ ❌ "DJANGO IS BLOATED." ⭐⭐ You import what you use, and the parts you
⭐        do not use cost you startup time you will never notice.
⭐   ⭐ ❌ "ASYNC IS MODERN." ⭐ Day 134 and Day 178: for a CRUD API async
⭐        adds hazards and subtracts nothing.
⭐   ⭐ ❌ "TYPE HINTS." ⭐⭐ Django with `mypy` and `django-stubs` is fine.
⭐        ⭐ FastAPI's advantage is not types, it is that the types are
⭐        LOAD-BEARING — they generate the contract.
```

# Part 2 — ⭐⭐ "Should we rewrite?"

```
⭐⭐ THE HONEST ANSWER IS ALMOST ALWAYS NO, AND YOU SHOULD BE ABLE TO SAY WHY
⭐   WITHOUT SOUNDING CONSERVATIVE:

⭐   ⭐ ⭐⭐ THE OLD SYSTEM CONTAINS YEARS OF BUG FIXES THAT LOOK LIKE UGLY
⭐        CODE. ⭐ Every strange conditional is a customer complaint someone
⭐        resolved. ⭐⭐ A rewrite discards that knowledge and re-earns it in
⭐        production, with real users.
⭐   ⭐ ⭐⭐ THE REWRITE MUST HIT A MOVING TARGET. The old system keeps
⭐        shipping features, or the business stalls for a year. ⭐ Both
⭐        outcomes are bad and the second is usually fatal to the project.
⭐   ⭐ ⭐⭐ THE ESTIMATE IS ALWAYS WRONG IN ONE DIRECTION. ⭐ You can see the
⭐        happy path and not the 400 edge cases encoded in the old one.
⭐
⭐⭐ THE FOUR REASONS THAT **DO** JUSTIFY IT — and they are about the FUTURE,
⭐   not about the code being unpleasant:
⭐  1. ⭐⭐ THE CONCURRENCY MODEL IS WRONG AND CANNOT BE FIXED — ⭐ e.g. you
⭐       need 50,000 concurrent WebSocket connections and you are on
⭐       thread-per-request.
⭐  2. ⭐ THE FRAMEWORK IS UNMAINTAINED OR THE RUNTIME IS END-OF-LIFE. ⭐⭐ A
⭐       security-support cliff is a business risk, not a preference.
⭐  3. ⭐⭐ THE DATA MODEL IS WRONG AT THE ROOT — ⭐ and note that is a
⭐       MIGRATION problem, not a framework one, so the rewrite would not
⭐       have fixed it either.
⭐  4. ⭐ THE SERVICE IS SMALL ENOUGH THAT A REWRITE IS DAYS. ⭐⭐ Then it is
⭐       not a rewrite, it is a refactor with a new import line.
⭐
⭐   ⇒ ⭐⭐ AND THE ANSWER THAT IS ALMOST ALWAYS RIGHT: **DON'T REWRITE. ADD
⭐        THE NEW THING BESIDE THE OLD ONE.** ⭐ Part 3.
```

# Part 3 — ⭐⭐ The strangler that works

```
⭐⭐ THE PATTERN (Day 091, at system scale): PUT A ROUTER IN FRONT, MOVE ONE
⭐   ROUTE AT A TIME, DELETE THE OLD ROUTE WHEN THE NEW ONE IS PROVEN.

⭐        clients
⭐           │
⭐        ⭐⭐ nginx / gateway          ← the seam. It is one config file.
⭐         ╱          ╲
⭐   /api/v2/stream   everything else
⭐        │                │
⭐   ⭐ FastAPI          ⭐ Django (unchanged)
⭐        ╲                ╱
⭐         ⭐⭐ ONE POSTGRES ⭐ ← the part that makes it work

⭐⭐ THE FIVE RULES THAT DECIDE WHETHER THIS SUCCEEDS OR BECOMES TWO SYSTEMS
⭐   FOREVER:
⭐  1. ⭐⭐ **SHARE THE DATABASE, NOT THE MODELS.** ⭐ The new service reads
⭐       the same Postgres with its own SQLAlchemy models mapped to the same
⭐       tables. ⭐⭐ No data migration, no sync, no dual-write, no eventual
⭐       consistency — ⭐ which removes the single biggest source of failure
⭐       in these projects.
⭐  2. ⭐⭐ **DJANGO OWNS THE SCHEMA.** One migration tool, one source of
⭐       truth. ⭐ The new service NEVER migrates; it reads and writes tables
⭐       Django defines. ⭐⭐ Two migration tools against one database is a
⭐       guaranteed incident.
⭐  3. ⭐⭐ **PICK THE FIRST ROUTE FOR THE REASON, NOT THE CONVENIENCE.** ⭐ The
⭐       first move should be one Django genuinely cannot do well — the
⭐       WebSocket endpoint, the streaming export, the 200-concurrent
⭐       third-party fan-out. ⭐⭐ Moving a CRUD endpoint proves nothing and
⭐       buys nothing, and it is what most teams do first.
⭐  4. ⭐⭐ **SHARE SESSIONS DELIBERATELY OR NOT AT ALL.** ⭐ The new service
⭐       can validate Django's signed session cookie (same `SECRET_KEY`, same
⭐       serialiser) — ⭐⭐ or issue its own JWTs. ⭐ Choose once and write it
⭐       down; ⭐⭐ half-shared auth is where these migrations actually die.
⭐  5. ⭐ **ONE OBSERVABILITY STORY.** ⭐⭐ Same request-id header, same trace
⭐       propagation (Day 148), same log shape. ⭐ Otherwise every
⭐       cross-service incident is two investigations.
⭐
⭐   ⇒ ⭐⭐ AND THE HONEST WARNING: MOST STRANGLERS STOP HALFWAY, ⭐ and a
⭐        half-strangled system is worse than either whole one — two
⭐        deployments, two dependency sets, two on-call runbooks.
⭐        ⭐⭐ SO: EITHER COMMIT TO FINISHING, OR SCOPE IT DELIBERATELY AS
⭐        "THIS ONE CAPABILITY LIVES OVER THERE, PERMANENTLY." ⭐ The second is
⭐        a legitimate end state and is much better than an abandoned first.
```

# Part 4 — ⭐ The other direction, and the middle grounds

```
⭐⭐ FASTAPI → DJANGO. RARER, AND IT HAPPENS FOR ONE REASON:
⭐   ⭐ "we need a back-office and we are not building one."
⭐   ⇒ ⭐⭐ AND YOU USUALLY DO NOT NEED A REWRITE. ⭐ Stand Django up beside the
⭐        service, point it at the SAME database with `inspectdb`, and use it
⭐        for the ADMIN ONLY. ⭐⭐ `managed = False` on every model so Django
⭐        never migrates them.
⭐   ⇒ ⭐ You get the admin in a day, ⭐⭐ and you have added exactly one
⭐        deployment with no risk to the API. ⭐ This is a genuinely good
⭐        answer and almost nobody knows it is available.

⭐⭐ THE MIDDLE GROUNDS WORTH KNOWING:
⭐   ⭐ **DJANGO + `django-ninja`** — ⭐⭐ FastAPI-style typed routing and
⭐        automatic OpenAPI, INSIDE Django. ⭐ You keep the ORM, the admin,
⭐        the auth and the migrations, and you get the contract-from-types
⭐        property. ⭐⭐ For "I like FastAPI's API layer and I want the admin",
⭐        this is often the actual right answer — ⭐ and it is the option most
⭐        candidates have never heard of.
⭐   ⭐ **DJANGO FOR THE APP + FASTAPI FOR ONE SERVICE** — Part 3.
⭐   ⭐ **FASTAPI + SQLADMIN / `piccolo_admin`** — ⭐⭐ an admin for SQLAlchemy
⭐        models. ⭐ Real, useful, and honestly some distance behind Django's
⭐        in features and polish. ⭐ Know it exists; do not oversell it.
⭐
⭐   ⇒ ⭐⭐ THE POINT OF THIS SECTION: "WHICH FRAMEWORK" IS OFTEN A FALSE
⭐        BINARY. ⭐ Naming a middle ground is a stronger answer than picking
⭐        a side, because it shows you optimised for the actual constraint
⭐        rather than the question as asked.
```

# Part 5 — ⭐⭐ Answering it in an interview

```
⭐⭐ THE QUESTION IS ALWAYS SOME FORM OF "DJANGO OR FASTAPI?" AND IT IS
⭐   ALWAYS TESTING THE SAME THING: ⭐ do you evaluate, or do you have a
⭐   favourite?

⭐  ⭐⭐ THE STRUCTURE THAT WORKS, IN FOUR MOVES:
⭐   1. ⭐⭐ ASK ONE CLARIFYING QUESTION. ⭐ "Is there a back-office, and who
⭐        operates it?" ⭐⭐ It is the highest-information question available
⭐        and it immediately shows you decide from constraints.
⭐   2. ⭐ COMMIT TO AN ANSWER. ⭐⭐ "Given that, Django" — ⭐ hedging reads as
⭐        not knowing.
⭐   3. ⭐⭐ NAME THE COST OF YOUR OWN CHOICE. ⭐ "The costs I accept are the
⭐        async ORM and that DRF's schema can drift, so I'd snapshot it in
⭐        CI." ⭐⭐ Naming your own trade-off is the single strongest signal in
⭐        this whole conversation.
⭐   4. ⭐ STATE THE CONDITION THAT FLIPS IT. ⭐⭐ "If we needed thousands of
⭐        live connections, I'd move that capability out — not rewrite."
⭐
⭐  ⭐⭐ AND THE ANSWER TO "WHICH DO YOU PREFER?", WHICH IS A TRAP:
⭐   ⭐ ❌ "FastAPI, it's modern." ⭐ ❌ "Django, it's mature."
⭐   ⭐ ✅ ⭐⭐ "I've shipped both. The endpoint I built in each was about
⭐        eighty percent identical — the race, the idempotency, the
⭐        transaction boundary and the dual write were mine either way. ⭐ What
⭐        differed was how much scaffolding surrounded it and which wrong
⭐        thing was the default. ⭐⭐ So I pick from the product, not from
⭐        preference."
⭐
⭐   ⇒ ⭐⭐ THAT ANSWER WORKS BECAUSE IT IS TRUE, AND BECAUSE IT MOVES THE
⭐        CONVERSATION TO THE HARD PARTS — ⭐ which is where you want it, and
⭐        where Days 130–182 have prepared you to be.
```

```
⭐⭐ THE FIVE-LINE SUMMARY:
⭐   ⭐ Choose from the product: data model, operators, concurrency, team.
⭐   ⭐⭐ "Faster", "bloated" and "modern" are not decision criteria.
⭐   ⭐ Rewrites fail because the old code is a record of bugs already fixed.
⭐   ⭐⭐ Strangle instead: shared database, ONE schema owner, and move the
⭐        capability the old stack genuinely cannot do.
⭐   ⭐ Name a middle ground — `django-ninja`, or Django-for-admin-only —
⭐        because the binary is usually false.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Choosing on benchmarks | Framework overhead is single-digit ms; your query is 5–50 ms and your third party is 200. |
| "Django is bloated" | You import what you use; the rest costs startup time you'll never notice. |
| Ignoring who operates the product | If non-engineers fix data daily, the admin outweighs everything else. |
| Ignoring the team's existing fluency | A fluent team out-delivers the same team learning, for quarters. |
| Recommending a rewrite for code quality | The ugly conditionals are bug fixes you'd re-earn in production. |
| Estimating a rewrite from the happy path | The 400 edge cases in the old system are invisible to you. |
| Strangling by moving a CRUD endpoint first | Proves nothing and buys nothing. Move what the old stack can't do. |
| Two migration tools on one database | A guaranteed incident. One schema owner. |
| Duplicating data between old and new | You've added sync, dual-write and eventual consistency to a project that had none. |
| Half-shared authentication | Where these migrations actually die. Decide once and write it down. |
| Different request-id and trace conventions | Every cross-service incident becomes two investigations. |
| Abandoning a strangler halfway | Worse than either whole system. Commit, or scope it as a permanent split. |
| Assuming FastAPI→Django needs a rewrite | Point Django at the same database with `managed = False` and use it for the admin only. |
| Treating it as a binary | `django-ninja` gives typed routing and OpenAPI inside Django. |
| Hedging in the interview | Ask one question, commit, name your own cost, state the flip condition. |

## Interview questions

**Q: How would you choose between Django and FastAPI for a new product?**

> I'd ask four product questions first, because the framework question is downstream of them. Is the
> data model the product — resources with CRUD and relationships, or verbs and workflows? Django's
> gravity points at models, so when the product does too that's free lift, and when it doesn't you'll
> spend the project explaining that `refund` isn't a noun. Who operates it day to day — if
> non-engineers look things up and fix data, the admin is worth more than every other factor
> combined. What's the concurrency shape — request-query-respond is fine either way, but thousands of
> long-lived connections rules Django out, because its async ORM is a thread-pool façade. And who
> else will work on it — every Django codebase looks like every other one, whereas every FastAPI
> codebase is whatever its first engineer decided. Then the tiebreak nobody says out loud: which does
> the team already know, because fluency beats a better tool for at least two quarters.

**Q: The team wants to rewrite a five-year-old Django app in FastAPI. What do you say?**

> Almost certainly no, and I'd give reasons that aren't about being conservative. That codebase
> contains years of bug fixes that look like ugly code — every strange conditional is a customer
> complaint someone resolved, and a rewrite discards that knowledge and re-earns it in production
> with real users. The rewrite has to hit a moving target, so either the old system keeps shipping
> features or the business stalls for a year, and the second usually kills the project. And the
> estimate is always wrong in one direction, because you can see the happy path and not the four
> hundred edge cases encoded in the old one. What does justify it is a concurrency model that can't
> be fixed, an end-of-life runtime, or a service small enough that it's really a refactor. Otherwise
> I'd strangle: put the new thing beside the old one.

**Q: How would you actually run that strangler?**

> A gateway in front routing by path, both services against one Postgres, and five rules. Share the
> database, not the models — the new service maps its own SQLAlchemy models to the same tables, so
> there's no data migration, no sync and no eventual consistency, which removes the biggest source of
> failure in these projects. Django owns the schema; the new service never migrates, because two
> migration tools on one database is a guaranteed incident. Pick the first route for the reason, not
> the convenience — move the WebSocket endpoint or the streaming export, the thing Django genuinely
> can't do well, because moving a CRUD endpoint proves nothing. Decide auth once, fully shared or
> fully separate, because half-shared auth is where these die. And one observability story — same
> request id, same trace propagation — or every cross-service incident is two investigations. Then
> the warning: most strangers stop halfway, and a half-strangled system is worse than either whole
> one. So either commit to finishing or scope it explicitly as "this capability lives over there,
> permanently", which is a legitimate end state.

**Q: We're on FastAPI and we need an admin. Rewrite?**

> No. Stand Django up beside the service, point it at the same database with `inspectdb`, set
> `managed = False` on every model so Django never migrates them, and use it for the admin only. You
> get a full back-office in about a day, with one extra deployment and no risk to the API. Almost
> nobody knows that's available. The other option worth naming is `django-ninja` if you were choosing
> up front — FastAPI-style typed routing with automatic OpenAPI inside Django, so you keep the ORM,
> the admin, the auth and the migrations and still get the contract-from-types property. My general
> point is that "which framework" is often a false binary, and naming the middle ground is a stronger
> answer than picking a side, because it shows you optimised for the actual constraint rather than
> the question as asked.

## 🎙️ Articulation drill

**Two minutes: "We're starting a new product. Django or FastAPI?"**

Ask the one question that carries the most information — is there a back-office, and who operates it
— then commit to an answer rather than hedging. Justify it from the product, not from the framework:
data model shape, operators, concurrency, team. Then do the thing most candidates never do and name
the cost of your own choice, with the mitigation: the async ORM, or DRF's inferrable schema and the
CI snapshot that keeps it honest. State the condition that would flip you, and say you'd move a
capability out rather than rewrite. Close by naming a middle ground — **`django-ninja`, or Django
pointed at the same database for the admin only** — because the binary is usually false, and knowing
that is the difference between choosing a side and solving the problem.
