# Part 1 — ⭐⭐ What a process actually is

Day 001 said a process is "memory + registers + OS bookkeeping". Today, precisely.

## What the OS gives every process

| Component | What it holds | ⭐ Note |
|---|---|---|
| ⭐⭐ **Its own virtual address space** | code, data, heap, stack | ⭐⭐ **process A's address `0x1000` and process B's are different physical memory** |
| **PID** | a unique id | `os.getpid()` |
| **File descriptor table** | open files, sockets, pipes | ⭐ 0 = stdin, 1 = stdout, 2 = stderr |
| **Registers / PC** | saved when descheduled, restored when resumed | this is the context switch |
| Credentials | user, group | why permissions work |
| Environment | env vars, working directory | ⭐ `os.environ` |

```
⭐⭐ VIRTUAL MEMORY IS THE ISOLATION MECHANISM:
   Process A                  Process B
   ┌──────────────┐           ┌──────────────┐
   │ 0x0000 stack │           │ 0x0000 stack │   ⭐⭐ SAME addresses...
   │ 0x1000 heap  │           │ 0x1000 heap  │
   │ 0x2000 code  │           │ 0x2000 code  │
   └──────┬───────┘           └──────┬───────┘
          │  ⭐ MMU translates        │
          ▼                          ▼
   ┌────────────────────────────────────────┐
   │        PHYSICAL RAM                    │   ⭐⭐ ...DIFFERENT physical pages
   └────────────────────────────────────────┘
```

⭐⭐ **This is why one process crashing does not take down another, and why a bug in one cannot read
another's memory.** It is enforced by hardware — the MMU — not by politeness. And it is the reason
`multiprocessing` gives you real isolation while `threading` does not (Days 066–068).

## ⭐ Process vs thread — the distinction that decides Stage 1

| | ⭐ Process | ⭐ Thread |
|---|---|---|
| Memory | ⭐⭐ **its own, isolated** | ⭐⭐ **shared with its siblings** |
| Creation cost | high (~ms) | low (~µs) |
| Crash blast radius | itself only | ⭐⭐ **the whole process** |
| Communication | pipes, sockets, shared memory — **explicit** | ⭐ just shared variables — **implicit, and therefore dangerous** |
| ⭐⭐ **In CPython** | ⭐⭐ **true parallelism** | ⭐⭐ **limited by the GIL for CPU work** (Day 065) |

> **⭐ Write that last row somewhere you will see it again.** It is why a Python web server runs
> *multiple processes* (Gunicorn/Uvicorn workers) rather than just many threads, and it is the single
> most asked Python architecture question.

```python
# Prove isolation in ten lines. Run it.
import os, multiprocessing as mp

counter = 0                       # ⭐ a module-level "global"

def child():
    global counter
    counter += 100
    print(f"child  pid={os.getpid()} counter={counter}")

if __name__ == "__main__":
    p = mp.Process(target=child)
    p.start(); p.join()
    print(f"parent pid={os.getpid()} counter={counter}")   # ⭐⭐ still 0 — separate memory
```

⭐⭐ **The child's `counter` is 100 and the parent's is still 0.** They were never the same variable.
Compare this with the threading version on Day 066, where they *are* the same variable and that is
the entire problem.

# Part 2 — ⭐⭐ What a port actually is

```
⭐ An IP address gets a packet to the right MACHINE.
⭐⭐ A PORT gets it to the right PROGRAM on that machine.

⭐⭐ A port is a 16-bit unsigned integer in the TCP or UDP header. That is all it is.
⭐ Range: 0–65535.
```

| Range | Name | Note |
|---|---|---|
| 0–1023 | ⭐ **Well-known** | ⭐⭐ **binding requires root on Unix** — which is why your dev server uses 8000 |
| 1024–49151 | Registered | 3306 MySQL, 5432 Postgres, 6379 Redis, 8000/8080 dev servers |
| 49152–65535 | ⭐ **Ephemeral** | ⭐⭐ **what the OS assigns to your outgoing connections** |

## ⭐⭐ The four-tuple — the idea that makes servers possible

```
⭐⭐ A TCP connection is identified by FOUR values, not one:
   ( source IP , source port , destination IP , destination port )

⭐ Three browsers connecting to your server on port 8000:
   (10.0.0.5, 51234, 10.0.0.9, 8000)
   (10.0.0.5, 51235, 10.0.0.9, 8000)   ⭐ same client, different ephemeral port
   (10.0.0.7, 60001, 10.0.0.9, 8000)   ⭐ different client
⭐ ⇒ ⭐⭐ THREE DISTINCT CONNECTIONS, all to port 8000. The tuple differs, so the OS keeps them apart.
```

> **⭐⭐ This is the answer to "how does one server handle thousands of clients on one port?"** It does
> not need a port per client. The listening socket is one thing; each *accepted* connection is
> identified by the full four-tuple. **Say the word "four-tuple" in an interview and you have
> answered a question most people fumble.**

## ⭐ Where you meet ports as an engineer

| Situation | What is really happening |
|---|---|
| ⭐⭐ **`Address already in use`** | ⭐⭐ another process holds that port — **or your last one is in `TIME_WAIT`** (Day 008) |
| `docker run -p 8080:8000` | host port 8080 → container port 8000; two different namespaces |
| Uvicorn `--workers 4` | ⭐⭐ **4 processes sharing ONE listening socket** via `SO_REUSEPORT` or a shared fd |
| `localhost:8000` unreachable from Docker | ⭐ the app bound to `127.0.0.1` — **it must bind `0.0.0.0`** |
| A firewall "blocking a port" | dropping packets whose destination port matches a rule |

⚠️ **The `127.0.0.1` versus `0.0.0.0` mistake will cost you an hour at least once.** `127.0.0.1`
accepts connections *only from this machine*; `0.0.0.0` accepts on every interface. **In a container
that difference is the difference between working and not**, and the error looks like a network
problem rather than a config one.

```python
# Prove the four-tuple with real sockets. Terminal 1:
import socket
srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)   # ⭐ Day 008 explains this line
srv.bind(("0.0.0.0", 8000))
srv.listen(5)
print("listening on 0.0.0.0:8000")
while True:
    conn, addr = srv.accept()
    print(f"connection from {addr}  ← client IP and EPHEMERAL PORT")
    conn.sendall(b"hi\n")
    conn.close()
```

```bash
# Terminal 2 — run it three times and watch the client port change each time.
nc localhost 8000
```

# Part 3 — ⭐ How the OS keeps programs separate

| Mechanism | What it isolates | Enforced by |
|---|---|---|
| ⭐⭐ **Virtual memory / MMU** | memory | ⭐⭐ hardware |
| ⭐ **User/kernel mode** | privileged instructions | hardware ring levels |
| ⭐ **File permissions** | files and devices | the kernel |
| ⭐ **The scheduler** | CPU time | the kernel |
| ⭐ Namespaces + cgroups | ⭐⭐ everything else — **this is what a container is** (Stage 10) | the kernel |

```
⭐⭐ THE SYSTEM CALL — the only door between your program and the kernel:
   your code            open() / read() / socket() / accept()
        │                          │
        │ ⭐ user mode              │  ⭐⭐ TRAP — CPU switches to kernel mode
        ▼                          ▼
   ┌──────────────────────────────────────┐
   │ KERNEL: does the privileged thing,   │  ⭐ hardware access, other processes' memory
   │ returns, switches back to user mode  │
   └──────────────────────────────────────┘
```

⭐ **A system call is expensive** — roughly 1–2 µs, thousands of times a register operation. That
cost is why buffered I/O exists, why `print()` in a tight loop is slow, and why an async server tries
to make **one** `epoll` call cover a thousand sockets rather than one call each (Day 070).

```python
# See the syscalls your program actually makes:
#   strace -c python -c "print('hi')"        (Linux)
#   dtruss python -c "print('hi')"           (macOS, needs sudo)
# Count them. A "hello world" makes hundreds — almost all of them are the interpreter starting up.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Thinking a server needs one port per client** | ⭐⭐ Connections are distinguished by the four-tuple. One listening port serves thousands. |
| "A port is a physical thing" | It is a 16-bit number in a header. Nothing more. |
| ⭐⭐ **Binding to `127.0.0.1` in a container** | ⭐⭐ Unreachable from outside. Bind `0.0.0.0`. |
| Assuming `Address already in use` means another app | ⭐ Often your own previous socket in `TIME_WAIT` — Day 008. |
| Thinking threads have separate memory | ⭐⭐ They share it. That is the point, and the danger. |
| ⭐ Believing process isolation is a software convention | ⭐⭐ It is enforced by the MMU in hardware. |
| Ignoring the cost of syscalls | ~1–2 µs each; it is why buffering and `epoll` exist. |
| Using ports below 1024 in development | requires root, for no benefit |

## Interview questions

**Q: What is the difference between a process and a thread?**
> A process has its own virtual address space, enforced by the MMU, so it cannot read another
> process's memory and its crash cannot take another down. Threads live inside one process and share
> its memory, which makes them cheap to create and to communicate between, and also makes every
> shared variable a potential race. In CPython specifically the distinction is sharper than usual:
> processes give true parallelism, while threads are limited by the GIL for CPU-bound work — which is
> why Python web servers run multiple worker processes.

**Q: How does one server handle thousands of clients on a single port?**
> Because a TCP connection is identified by a four-tuple — source IP, source port, destination IP,
> destination port — not by the destination port alone. The listening socket is one object; every
> accepted connection is a separate socket distinguished by the client's IP and ephemeral port. So a
> thousand clients on port 443 are a thousand distinct four-tuples, and the OS demultiplexes them
> without ambiguity.

**Q: You get "address already in use" but nothing is running. Why?**
> Almost always the previous socket is in `TIME_WAIT`, which the kernel holds for a couple of minutes
> to make sure delayed packets from the old connection cannot be delivered to a new one on the same
> tuple. `SO_REUSEADDR` tells the kernel it is safe to bind anyway. The alternative cause is a
> process that is still alive but not obvious — `lsof -i :8000` will show it.

**Q: What is a system call and why does it cost anything?**
> It is the controlled transition from user mode into kernel mode so the kernel can do something
> privileged on your behalf — open a file, send on a socket. The cost is the mode switch and the
> associated cache effects, roughly one to two microseconds, which is thousands of times a normal
> operation. That is why I/O is buffered rather than per-byte, and why an event loop makes one
> `epoll` call covering many sockets instead of one call per socket.

## 🎙️ Articulation drill

Record two minutes: **"How does one web server handle ten thousand simultaneous connections on port
443?"**

⭐ The answer has two halves and most people only give the first. **Half one is the four-tuple** —
connections are distinguished by all four values, so one listening port is never the limit.
**Half two is what the server does with those ten thousand sockets** — one thread each does not scale,
so it uses an event loop making a single `epoll` call over all of them, which is exactly what asyncio
and Uvicorn do (Day 070).

Saying both halves is the difference between a correct answer and a good one.
