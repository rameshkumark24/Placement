# Day 117

**L-117** · 🔐 **Refresh-token rotation** — and ⭐⭐ detecting a stolen token by its reuse

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: rotation plus reuse detection is the only mechanism in ordinary web
> authentication that turns token theft from *silent and permanent* into *detected and terminated* —
> because a token that is used twice proves that two parties hold it, even though you cannot tell which
> one is the thief.**
>
> ⭐ Day 116 ended on a problem: a JWT cannot be revoked. **Today is the standard answer**, and its
> central idea is genuinely clever rather than merely conventional.

---

# Part 1 — ⭐ Two tokens, two jobs

| | ⭐ Access token | ⭐⭐ Refresh token |
|---|---|---|
| Lifetime | ⭐ 5–15 minutes | ⭐ days to weeks |
| Format | ⭐ a JWT (Day 116) | ⭐⭐ **opaque random bytes** |
| Sent to | every API request | ⭐ **only `/auth/refresh`** |
| Verified by | ⭐ signature only — no lookup | ⭐⭐ a **database lookup** |
| Revocable | ⚠️ ⭐ no | ⭐⭐ **yes — that is its whole purpose** |
| Stored | ⭐ memory, or an `HttpOnly` cookie | ⭐ `HttpOnly` cookie, `Path=/auth/refresh` |

```
⭐⭐ THE DESIGN IS A DELIBERATE SPLIT OF ONE UNSOLVABLE TRADE INTO TWO SOLVABLE
⭐   ONES (Day 116): you cannot have both "verify with no lookup" and "revocable".
⭐   ⇒ ⭐⭐ SO: the token used on EVERY request is fast and unrevocable, and is
⭐        made SHORT-LIVED so the unrevocable window is minutes.
⭐   ⇒ ⭐⭐ AND the token that can mint new ones is stateful and revocable, and is
⭐        used RARELY — ⭐ so its lookup costs nothing, because it happens once
⭐        every ten minutes rather than on every call.
⭐   ⇒ ⭐ the refresh token is opaque, not a JWT: it carries no claims, it exists
⭐        only to be looked up, ⭐⭐ and making it a JWT would add a parseable
⭐        payload for no benefit.
```

```python
import secrets, hashlib

def issue_refresh_token(user_id: int, family_id: str | None = None) -> str:
    raw = secrets.token_urlsafe(32)                      # ⭐ Day 115
    db.insert_refresh_token(
        token_hash=hashlib.sha256(raw.encode()).hexdigest(),   # ⭐⭐ STORE THE HASH
        user_id=user_id,
        family_id=family_id or secrets.token_urlsafe(16),      # ⭐ Part 3
        expires_at=now() + REFRESH_TTL,
        used_at=None,
    )
    return raw                                            # ⭐ the raw value goes to the client only
```

```
⭐⭐ HASH THE REFRESH TOKEN BEFORE STORING IT, FOR THE SAME REASON AS A PASSWORD
⭐   (Day 114): ⭐⭐ IF YOUR DATABASE LEAKS, THE STORED VALUES ARE USELESS.
⭐   ⇒ ⭐ a plaintext refresh-token table is a list of working credentials for
⭐        every logged-in user, and it is depressingly common.
⭐   ⇒ ⭐ plain SHA-256 is CORRECT here and wrong for passwords — ⭐⭐ because the
⭐        token has 256 bits of entropy, so there is nothing to brute-force. The
⭐        slow KDF exists to compensate for humans choosing weak inputs.
⭐   ⇒ ⭐ look it up by hash, and compare with `compare_digest`.
```

# Part 2 — ⭐ Rotation

```
⭐⭐ EVERY REFRESH ISSUES A NEW REFRESH TOKEN AND RETIRES THE OLD ONE.
⭐
⭐   client ──refresh_1──▶ /auth/refresh
⭐          ◀── access_2 + refresh_2 ──    ⭐⭐ refresh_1 is now marked USED
⭐   client ──refresh_2──▶ /auth/refresh
⭐          ◀── access_3 + refresh_3 ──    ⭐ refresh_2 marked used
⭐
⭐ ⇒ ⭐⭐ WITHOUT ROTATION, ONE STOLEN REFRESH TOKEN IS VALID FOR ITS WHOLE
⭐     LIFETIME — weeks of access from a single theft, and no signal at all.
⭐ ⇒ ⭐ WITH ROTATION, a stolen token is useful only until the real client
⭐     refreshes next — ⭐⭐ AND, far more importantly, the theft becomes
⭐     DETECTABLE, which is Part 3.
```

```python
def refresh(raw_token: str) -> tuple[str, str]:
    record = db.find_refresh_token(sha256(raw_token))
    if record is None or record.expires_at < now():
        raise InvalidToken("unknown or expired")

    if record.used_at is not None:                        # ⭐⭐ REUSE — see Part 3
        db.revoke_family(record.family_id)
        log.warning("refresh_token_reuse", extra={"user_id": record.user_id,
                                                  "family_id": record.family_id})
        raise InvalidToken("token reuse detected — all sessions revoked")

    db.mark_used(record.id)                               # ⭐ retire it
    new_refresh = issue_refresh_token(record.user_id, family_id=record.family_id)
    return issue_access_token(record.user_id), new_refresh
```

# Part 3 — ⭐⭐ Reuse detection — the idea worth understanding

```
⭐⭐ THE INSIGHT: A ROTATED TOKEN SHOULD NEVER BE PRESENTED TWICE. IF IT IS,
⭐   TWO PARTIES HOLD IT — AND YOU CANNOT TELL WHICH ONE IS LEGITIMATE.
⭐
⭐   CASE A — the thief refreshes first:
⭐     thief   uses refresh_1  ⇒ gets refresh_2   ⭐ (nothing looks wrong yet)
⭐     ⭐⭐ THE REAL USER then uses refresh_1  ⇒ ALREADY USED ⇒ ⭐ REUSE DETECTED
⭐
⭐   CASE B — the real user refreshes first:
⭐     user    uses refresh_1  ⇒ gets refresh_2
⭐     ⭐⭐ THE THIEF then uses refresh_1     ⇒ ALREADY USED ⇒ ⭐ REUSE DETECTED
⭐
⭐   ⇒ ⭐⭐ EITHER WAY, THE SECOND USE FIRES THE ALARM. You do not need to know
⭐        WHICH party is the attacker, because the response is the same for both:
⭐        ⭐⭐ REVOKE THE ENTIRE FAMILY.
⭐   ⇒ ⭐ the legitimate user is logged out and re-authenticates — mildly
⭐        annoying. ⭐⭐ THE THIEF IS LOCKED OUT AND HAS NO PASSWORD. That
⭐        asymmetry is the entire point.
⭐   ⇒ ⭐⭐ AND IT IS THE ONLY MECHANISM HERE THAT MAKES THEFT *OBSERVABLE*:
⭐        without it, a stolen refresh token is silent forever. ⭐ Log it, alert
⭐        on it, and email the user.
```

```
⭐⭐ A "FAMILY" IS THE CHAIN OF TOKENS DESCENDED FROM ONE LOGIN:
⭐        login ⇒ refresh_1 ──▶ refresh_2 ──▶ refresh_3 …     (family_id = F1)
⭐   ⇒ ⭐ revoking the FAMILY kills the whole chain, including whichever token
⭐        the thief holds — ⭐⭐ because you do not know how far down the chain
⭐        they are.
⭐   ⇒ ⭐ one family per login, per device ⇒ a phone and a laptop are separate
⭐        families, so revoking one does not log the other out.
⭐   ⇒ ⭐⭐ "LOG OUT EVERYWHERE" = REVOKE EVERY FAMILY FOR THE USER — and that is
⭐        the capability Day 116 said a pure JWT scheme cannot have.
```

# Part 4 — ⚠️ ⭐⭐ The false positive that will page you

```
⚠️⚠️ ⭐⭐ TWO BROWSER TABS BOTH NOTICE THE ACCESS TOKEN EXPIRED AND BOTH POST
⭐    refresh_1 AT THE SAME MOMENT.
⭐    ⇒ ⭐⭐ ONE SUCCEEDS. THE OTHER SEES `used_at` SET, CONCLUDES THEFT, AND
⭐         LOGS THE USER OUT OF EVERYTHING. ⭐ You have just built a feature that
⭐         randomly terminates sessions, and it will look like an outage.
⭐    ⇒ ⭐ the same happens on a flaky network: the client sends the refresh, the
⭐         RESPONSE is lost, the client retries — ⭐⭐ which is Day 102's "a
⭐         timeout does not mean failure" arriving in the auth system.
⭐
⭐ ⭐⭐ THREE MITIGATIONS, AND YOU WANT AT LEAST TWO:
⭐  1. ⭐⭐ A GRACE WINDOW. Accept a token used within the last ~10-30 seconds
⭐       and RETURN THE SAME NEW PAIR that the first call produced (store it
⭐       against the used token). ⭐ This is idempotency (Day 102) applied to
⭐       refresh: a retry gets the original response instead of an alarm.
⭐  2. ⭐⭐ CLIENT-SIDE SINGLE-FLIGHT. One in-flight refresh per client; other
⭐       tabs await it. ⭐ A shared worker, or a lock in local storage.
⭐  3. ⭐ CORRELATE BEFORE REVOKING: if both calls came from the same IP, user
⭐       agent and within seconds, treat it as a race rather than theft — ⭐⭐ but
⭐       be careful, because that is exactly what a same-device attacker looks like.
⭐
⭐ ⇒ ⭐⭐ SAY THIS IN AN INTERVIEW. Knowing rotation is common; knowing that the
⭐     concurrent-refresh race is its main operational hazard is what shows you
⭐     have run it.
```

# Part 5 — ⭐ Hardening the refresh endpoint

```
⭐⭐ IT IS THE HIGHEST-VALUE ENDPOINT IN YOUR API — it mints credentials —
⭐   SO IT GETS ITS OWN RULES:
⭐   □ ⭐⭐ COOKIE SCOPED: HttpOnly, Secure, SameSite=Lax, ⭐ Path=/auth/refresh
⭐       ⇒ ⭐⭐ the refresh token is then NOT SENT on ordinary API calls, so it is
⭐         not in every log, proxy buffer or crash report (Day 099A).
⭐   □ ⭐ RATE LIMIT it, per user and per IP (Days 114, 123).
⭐   □ ⭐⭐ AN ABSOLUTE LIFETIME on the family — 30 days, say — regardless of
⭐       rotation. ⭐ Otherwise a rotating chain is a permanent credential, and
⭐       you have re-created the problem you were solving.
⭐   □ ⭐ RE-AUTHENTICATE for dangerous actions (change password, change email,
⭐       delete account) ⇒ ⭐⭐ a valid refresh chain should not be enough to take
⭐       an account over permanently.
⭐   □ ⭐ RECORD device, IP and user agent per family ⇒ so the user can see and
⭐       revoke sessions, and so `refresh_token_reuse` alerts have context.
⭐   □ ⭐⭐ ON PASSWORD CHANGE, REVOKE EVERY FAMILY (Day 115's rule, again).
```

```
⭐ THE FULL LIFECYCLE, WORTH BEING ABLE TO DRAW:
⭐   login          ⇒ access(10 min) + refresh(30 days, family F1)
⭐   API calls      ⇒ access only — ⭐ signature check, no lookup
⭐   access expires ⇒ POST /auth/refresh ⇒ ⭐ new access + new refresh, same F1
⭐   logout         ⇒ ⭐ revoke F1 (the access token still works for ≤10 min —
⭐                     ⭐⭐ say this out loud; it is the residual risk of the design)
⭐   log out all    ⇒ revoke every family for the user
⭐   ⭐⭐ REUSE      ⇒ revoke F1, log, alert, email the user
```

⚠️ ⭐⭐ **Be honest about the residual window.** ⭐ After logout the access token remains valid until it
expires — so a "logout" is really "stop being able to get new tokens". **For genuinely sensitive
operations, check a denylist or a `token_version` on those endpoints only** (Day 116), which buys
revocation where it matters without a lookup on every request.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Long-lived access tokens | ⭐⭐ Unrevocable for their whole lifetime. Minutes, not days. |
| ⭐⭐ **Storing refresh tokens in plaintext** | ⭐⭐ A DB leak becomes a list of working credentials. Store the hash. |
| Using argon2 for a refresh token | ⭐ 256 random bits have nothing to brute-force. SHA-256 is right. |
| ⭐ No rotation | ⭐⭐ One theft = weeks of access, with no signal. |
| ⭐⭐ **Rotation without reuse detection** | ⭐⭐ You threw away the only theft *detector* you had. |
| Revoking one token on reuse | ⭐ Revoke the **family** — you do not know which link the thief holds. |
| ⭐⭐ **No grace window** | ⭐⭐ Two tabs racing logs the user out of everything. |
| A refresh chain with no absolute cap | ⭐ A permanent credential by another name. |
| ⭐ Refresh cookie scoped to `/` | ⭐ It then travels on every request, into every log and proxy. |
| Not revoking families on password change | ⭐⭐ The attacker's session survives the remediation. |
| ⭐ Claiming logout is instant | ⭐ The access token lives for its remaining minutes. Say so. |

## Interview questions

**Q: Why two tokens?**
> Because you can't have both "verify with no lookup" and "revocable" in one credential, so the design
> splits the trade. The access token is a JWT, checked by signature alone on every request, and made
> short-lived — five to fifteen minutes — so the window in which it can't be revoked is small. The
> refresh token is opaque, stored server-side, and only ever sent to the refresh endpoint, so its
> database lookup happens once every ten minutes rather than on every call. That's what makes
> revocation affordable.

**Q: What is reuse detection, and why does it matter?**
> With rotation, every refresh issues a new token and retires the old one, so a rotated token should
> never be presented twice. If it is, two parties hold it — and you can't tell which one is
> legitimate. But you don't need to: whichever refreshes second trips the alarm, and the response is
> the same either way, which is to revoke the whole token family. The legitimate user is logged out
> and re-authenticates, mildly annoyed; the thief is locked out and doesn't have the password. That
> asymmetry is the point. And crucially it's the only mechanism in the design that makes theft
> *observable* — without it, a stolen refresh token is silent forever.

**Q: What's a token family?**
> The chain of refresh tokens descended from one login. You revoke the family rather than the
> individual token because you don't know how far down the chain the attacker is — they might be
> holding a token you haven't seen yet. One family per login per device, so revoking the phone doesn't
> log out the laptop, and "log out everywhere" is revoking every family for the user. That last
> capability is exactly what a pure JWT scheme can't offer.

**Q: What breaks in production with rotation?**
> The concurrent-refresh race. Two browser tabs both notice the access token expired and both post the
> same refresh token; one succeeds, the other sees it already used and concludes theft, so the user is
> logged out of everything for no reason. Same thing on a flaky network when the response is lost and
> the client retries — which is "a timeout doesn't mean failure" arriving in the auth system. The fix
> is a short grace window where a recently-used token returns the *same* new pair the first call
> produced, which is idempotency applied to refresh, plus client-side single-flight so only one refresh
> is in the air at a time. Knowing rotation exists is common; knowing this race is what shows you've
> run it.

**Q: After logout, is the user actually logged out?**
> Not completely, and I'd say so. Revoking the family stops them getting new tokens, but the access
> token they already hold stays valid until it expires — so logout really means "can no longer
> refresh". With a ten-minute access lifetime that's a ten-minute residual window. If that's
> unacceptable for particular operations, I'd check a denylist or a per-user token version on those
> endpoints specifically, which buys revocation where it matters without paying for a lookup on every
> request.
