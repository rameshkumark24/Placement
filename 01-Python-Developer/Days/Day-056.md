# Day 056

**L-056** · ⭐⭐ **ABCs and Protocols** — nominal vs structural typing, duck typing formalised

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an ABC asks "did you inherit from me?" A Protocol asks "do you have the
> right methods?" — nominal versus structural typing.**
>
> ⭐ Duck typing (Day 023) was Python's answer for twenty years and it had one real weakness: **the
> interface was never written down.** `Protocol` fixes that without requiring inheritance — and it is
> the single most useful typing feature for testable design.

---

# Part 1 — ⭐ ABCs — nominal

```python
from abc import ABC, abstractmethod

class Storage(ABC):
    @abstractmethod
    def save(self, key: str, data: bytes) -> None: ...
    @abstractmethod
    def load(self, key: str) -> bytes: ...

    def save_text(self, key, text):              # ⭐⭐ a CONCRETE helper — ABCs may have code
        self.save(key, text.encode())

class S3Storage(Storage):
    def save(self, key, data): ...
    def load(self, key): ...

Storage()          # ⭐⭐ TypeError: Can't instantiate abstract class Storage with abstract methods
```

```
⭐⭐ WHAT ABCs ACTUALLY ENFORCE — and the timing is the point:
⭐   the check happens at INSTANTIATION, not at class definition.
⭐   ⇒ ⭐ you can define an incomplete subclass; you just cannot create one.
⭐   ⇒ ⭐⭐ so it is a RUNTIME guard, not a static one — mypy also flags it, but the language
⭐        itself only complains when you try to build an object.
⭐   ⇒ ⭐ implemented by ABCMeta, a metaclass (Day 053).
```

⭐ **`@abstractmethod` combines with the others**, and the order matters:

```python
@property
@abstractmethod
def name(self) -> str: ...          # ⭐ abstract property — abstractmethod INNERMOST

@classmethod
@abstractmethod
def from_row(cls, row): ...
```

⚠️ ⭐ **An ABC with no abstract methods enforces nothing** — it is documentation with a metaclass
attached. **And inheriting from `ABC` is inheritance (Day 055), so it couples the implementation to
your hierarchy** — which is exactly what Part 3 avoids.

# Part 2 — ⭐⭐ `collections.abc` — the free-methods trick

```python
from collections.abc import Sequence, Mapping, Iterable, Sized, Hashable, Callable

class Deck(Sequence):                  # ⭐⭐ implement TWO methods...
    def __init__(self, cards): self._cards = cards
    def __getitem__(self, i): return self._cards[i]
    def __len__(self): return len(self._cards)

# ⭐⭐ ...AND GET FOR FREE: __contains__, __iter__, __reversed__, index, count
d = Deck([1,2,3])
2 in d; list(reversed(d)); d.index(3)          # ⭐ all work, none written
```

```
⭐⭐ THIS IS THE BEST REASON TO INHERIT FROM AN ABC: the MIXIN METHODS.
⭐   Sequence      ← __getitem__, __len__      ⇒ + __contains__, __iter__, __reversed__, index, count
⭐   Mapping       ← __getitem__, __len__, __iter__ ⇒ + get, keys, items, values, __eq__, __contains__
⭐   MutableMapping ← + __setitem__, __delitem__ ⇒ + pop, popitem, clear, update, setdefault
⭐   Set           ← __contains__, __iter__, __len__ ⇒ + all the algebra: |, &, -, ^, <=
⭐ ⇒ ⭐ so `MutableMapping` gives you a full dict-like class from four methods — and unlike
⭐   subclassing dict (Day 055), EVERY path goes through your methods.
```

⭐⭐ **`isinstance(x, Iterable)` works on things that never inherited from it**, because these ABCs
define `__subclasshook__` — a structural check bolted onto a nominal system. ⚠️ **But it only checks
for the method's *existence*, so `isinstance(x, Iterable)` is `True` for a class with a broken
`__iter__`.**

```python
Sequence.register(SomeThirdPartyClass)     # ⭐ virtual subclass — claim conformance without inheriting
```

# Part 3 — ⭐⭐ `Protocol` — structural

```python
from typing import Protocol, runtime_checkable

class Storage(Protocol):                   # ⭐⭐ NOBODY inherits from this
    def save(self, key: str, data: bytes) -> None: ...
    def load(self, key: str) -> bytes: ...

class S3Storage:                           # ⭐⭐ no base class, no import of Storage
    def save(self, key, data): ...
    def load(self, key): return b""

def backup(store: Storage) -> None: ...    # ⭐ mypy accepts S3Storage — the SHAPE matches
backup(S3Storage())                        # ⭐⭐ checked statically, no runtime cost
```

```
⭐⭐ WHY THIS IS THE BIG ONE:
⭐   · ⭐⭐ NO COUPLING — the implementation does not import or inherit your interface.
⭐        ⇒ you can type a THIRD-PARTY class, or a class you do not control, or a test double.
⭐   · ⭐⭐ the interface is WRITTEN DOWN and CHECKED — duck typing with a contract
⭐   · ⭐ the DEPENDENCY DIRECTION INVERTS: the consumer declares what it needs,
⭐        rather than the provider declaring what it is. ⇒ ⭐⭐ that IS dependency inversion.
⭐   · ⭐ zero runtime cost — it is a static-only construct by default
```

```python
# ⭐⭐ THE TESTING PAYOFF — and this is why the day matters (Day 055's DI, typed):
class FakeStorage:                        # ⭐ a test double with NO inheritance and no mock library
    def __init__(self): self.data = {}
    def save(self, key, data): self.data[key] = data
    def load(self, key): return self.data[key]

backup(FakeStorage())                     # ⭐⭐ type-checks. No ABC, no Mock, no patching.
```

⭐ **`@runtime_checkable`** lets `isinstance` work with a Protocol — ⚠️ **but only by checking that the
method *names* exist. Signatures and types are not checked**, so it is a weaker guarantee than the
static check and should not be your validation.

⭐ **Protocols can have default implementations** and can be generic, and **`Callable[[int], str]` is
already a protocol** in everything but name.

# Part 4 — ⭐⭐ Choosing

| | ⭐ ABC | ⭐⭐ `Protocol` |
|---|---|---|
| Typing | ⭐ nominal — you must inherit | ⭐⭐ **structural — shape matches** |
| Coupling | ⭐⭐ implementation imports the base | ⭐⭐ **none** |
| Enforcement | ⭐ runtime, at instantiation | ⭐ static, by mypy |
| Shared code | ⭐⭐ **yes — concrete + mixin methods** | ⭐ defaults only, rarely used |
| Works on code you do not own | ⭐ only via `register` | ⭐⭐ **yes, natively** |
| `isinstance` | ⭐ yes | ⭐ only with `@runtime_checkable`, names only |

```
⭐⭐ THE RULE:
⭐   ⭐⭐ ABC when you OWN the hierarchy AND want to share implementation
⭐        ⇒ a plugin base class, or a Sequence/MutableMapping for the free methods
⭐   ⭐⭐ PROTOCOL when you are declaring what YOUR CODE NEEDS from someone else's
⭐        ⇒ every dependency you inject, every port in a hexagonal architecture,
⭐          every place you would otherwise write `Any` or a Mock
⭐   ⭐ NEITHER when the duck typing is obvious and local — do not ceremonially
⭐        declare an interface for a one-file script.
```

⭐⭐ **The one-line version worth memorising: "ABCs for inheritance and shared code, Protocols for
dependency inversion."** ⭐ And in a design round, saying *"I'd define the repository as a Protocol in
the module that uses it, so the domain doesn't depend on the database layer"* is a Stage 8 answer
arriving from Stage 1.

⚠️ ⭐ **You can combine them:** an ABC gives runtime enforcement and shared methods, and a Protocol
describes it for consumers who should not depend on it. **Most codebases need one or the other, not
both.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **ABC where a Protocol fits** | ⭐⭐ Forces inheritance and couples the implementation. |
| Expecting an ABC to fail at class definition | ⭐ It fails at **instantiation**. |
| An ABC with no abstract methods | ⭐ Enforces nothing. |
| ⭐ `@abstractmethod` outside `@property` | ⭐ `abstractmethod` goes innermost. |
| ⭐ Trusting `@runtime_checkable` `isinstance` | ⭐⭐ Names only — no signatures, no types. |
| Subclassing `dict` instead of `MutableMapping` | ⭐⭐ Day 055 — internal paths bypass you. |
| Writing `__contains__`, `index`, `count` by hand | ⭐ `Sequence` gives them from two methods. |
| Declaring an interface for a one-file script | ⭐ Ceremony. Duck typing is fine locally. |
| Mocking where a Protocol + a hand-written fake works | ⭐⭐ The fake is type-checked; the mock is not. |
| Putting the Protocol in the provider's module | ⭐ It belongs with the **consumer**. |

## Interview questions

**Q: ABC or Protocol?**
> An ABC is nominal — a class conforms because it inherited. A Protocol is structural — it conforms
> because it has the right methods, with no inheritance and no import. So I use an ABC when I own the
> hierarchy and want to share implementation, and a Protocol when I'm declaring what my code needs
> from a collaborator. The short version is: ABCs for inheritance and shared code, Protocols for
> dependency inversion.

**Q: Why is a Protocol better for dependencies?**
> Because it inverts the direction. With an ABC, the implementation has to import and inherit my
> interface, so the provider depends on me. With a Protocol, the consumer declares the shape it needs
> and nothing on the other side knows it exists — so I can type a third-party class, a class I don't
> control, or a hand-written test fake. That's dependency inversion with no runtime cost, since a
> Protocol is a static-only construct by default.

**Q: What does an ABC actually enforce, and when?**
> That every abstract method is implemented — checked at *instantiation*, not at class definition. So
> an incomplete subclass can be defined without complaint and fails the moment you try to build one.
> It's implemented by `ABCMeta`, a metaclass. mypy will also flag it statically, but the language's own
> guarantee is a runtime one.

**Q: What's the best reason to inherit from an ABC?**
> The mixin methods in `collections.abc`. Implementing `__getitem__` and `__len__` and inheriting
> `Sequence` gives me `__contains__`, `__iter__`, `__reversed__`, `index` and `count` for free.
> `MutableMapping` gives a full dict-like class from four methods — and unlike subclassing `dict`,
> every operation routes through my methods, so an invariant I enforce in `__setitem__` actually holds
> for `update` too.

**Q: Is `@runtime_checkable` a real check?**
> Only a shallow one. It makes `isinstance` work against a Protocol, but it verifies that the method
> *names* exist — not their signatures or types. So a class with a `save` taking the wrong arguments
> passes. It's useful for a coarse guard, and it is not validation; the real check is mypy's static
> one.

**Q: How does this change how you test?**
> It removes most of my need for mocking. If a dependency is typed as a Protocol, I can write a
> twenty-line fake with a dict inside, and the type checker verifies it satisfies the same contract as
> the real implementation. That's better than a `Mock`, which will happily accept any call and silently
> drift from the real interface as it changes. A hand-written fake that type-checks catches interface
> drift at the same moment the real caller would.

## 🎙️ Articulation drill

Record two minutes: **"How would you define the interface between your service and its database?"**

⭐ Answer with a Protocol and say why the direction matters: **the service declares what it needs — a
`Repository` with `get`, `save`, `list` — and the Protocol lives in the service's own module. The
database implementation never imports it and never inherits from it.** ⭐⭐ **That is dependency
inversion: the high-level code owns the contract, and the low-level code merely happens to satisfy
it.**

⭐ Then the payoff in testing: **a twenty-line fake with a dict inside satisfies the same Protocol, and
mypy verifies that it does** — which is strictly better than a `Mock`, because a Mock accepts any call
and drifts silently as the real interface changes.

⭐⭐ **Then say when you would use the other tool, because the contrast is the answer:** *"I'd use an
ABC instead when I own the hierarchy and want to share implementation — a plugin base class, or
inheriting `MutableMapping` to get a dict-like type from four methods. The rule I'd give is ABCs for
inheritance and shared code, Protocols for dependency inversion. And for a small local script I'd use
neither — plain duck typing, because declaring an interface for one file is ceremony."*
