# Day 034

**L-034** · `tuple`, `namedtuple`, and when immutability actually buys you something

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a tuple is not "an immutable list" — it is a record.** A list is a
> homogeneous collection you iterate; a tuple is a fixed-shape group of *related but different*
> things, where position carries meaning.
>
> ⭐ Getting that distinction right is a small style point with a large consequence: it decides
> whether your data can be a dict key, cached, shared between threads, or safely returned from a
> function.

---

# Part 1 — ⭐ The two views

```python
# ⭐ LIST: "many of the same thing", variable length, you iterate it
scores = [88, 91, 74, 96]

# ⭐⭐ TUPLE: "one thing made of parts", fixed length, ⭐ you UNPACK it
point   = (3, 4)
record  = ("ada", 36, "london")
lat_lng = (51.5, -0.12)
```

```
⭐⭐ THE TEST THAT DECIDES IT:
⭐   Would it make sense to APPEND to this?           ⇒ it is a LIST
⭐   Does position mean something different per slot? ⇒ ⭐⭐ it is a TUPLE
⭐   ⇒ ⭐ heterogeneous and positional ⇒ tuple. Homogeneous and countable ⇒ list.
```

| | ⭐ `list` | ⭐ `tuple` |
|---|---|---|
| Mutable | yes | ⭐⭐ **no** |
| ⭐⭐ Hashable | ⭐⭐ **no** | ⭐⭐ **yes, if its contents are** |
| ⭐ Memory | 56 B + capacity slack | ⭐ **40 B + exact slots — smaller, no over-allocation** |
| Construction | slower | ⭐ faster (constant-folded when literal) |
| Dict key / set member | ⭐⭐ never | ⭐ yes |
| Semantics | a sequence | ⭐⭐ **a record** |

⭐ **The syntax trap:** it is the **comma**, not the parentheses, that makes a tuple.

```python
t = (1)          # ⭐⭐ an int — the parens are just grouping
t = (1,)         # ⭐ a 1-tuple
t = 1, 2         # ⭐ a tuple — no parens needed
f(1, 2)          # ⭐ two arguments
f((1, 2))        # ⭐ one tuple argument
return a, b      # ⭐⭐ "returning two values" is returning one tuple
```

# Part 2 — ⭐⭐ What immutability actually buys

```
⭐⭐ FOUR CONCRETE THINGS, and none of them is "safety" in the vague sense:

⭐ 1. ⭐⭐ HASHABLE ⇒ usable as a dict key or set member (Day 029's contract holds trivially,
⭐      because the value cannot change while it sits in the container)
⭐ 2. ⭐ SHAREABLE ⇒ no defensive copies, and no data race between threads — nothing can write
⭐ 3. ⭐ CACHEABLE ⇒ lru_cache arguments must be hashable; a tuple key is why *args caching works
⭐ 4. ⭐⭐ SELF-DOCUMENTING ⇒ "this will not change" is enforced, not commented
```

```python
# ⭐⭐ THE MOST COMMON REAL USE — a composite dict key:
cache: dict[tuple[str, int], Result] = {}
cache[(user_id, page)] = result        # ⭐ a list here would raise TypeError: unhashable

# ⭐ And grouping:
from collections import defaultdict
by_city = defaultdict(list)
for r in records: by_city[(r.country, r.city)].append(r)
```

⚠️ ⭐⭐ **Immutability is shallow (Day 025):** `(1, [2])` is a tuple containing a mutable list, so it
is **not hashable** and `hash(t)` raises. **A tuple is hashable exactly when everything inside it
is** — which is the recursive version of the same rule.

⭐ **Unpacking is where tuples earn their keep daily:**

```python
a, b = b, a                        # ⭐ swap
first, *rest = seq                 # ⭐ star unpacking
(name, (x, y)) = ("ada", (1, 2))   # ⭐ nested
for i, item in enumerate(seq): ...           # ⭐⭐ enumerate yields tuples
for k, v in d.items(): ...                   # ⭐ so does items()
for a, b in zip(xs, ys): ...
_, value = pair                    # ⭐ `_` for "I do not need this"
```

⚠️ ⭐ **`zip` stops at the shortest input, silently.** Use `zip(a, b, strict=True)` (3.10+) when the
lengths *should* match — **it turns a silent truncation into an error**, and silent truncation is a
genuinely nasty data bug.

# Part 3 — ⭐⭐ `namedtuple` and `NamedTuple`

```python
# ⚠️ ⭐ The problem tuples have:
p = ("ada", 36, "london")
p[1]                    # ⭐⭐ what is 1? You have to go and look.

from typing import NamedTuple
class Person(NamedTuple):          # ⭐⭐ the modern, typed form — prefer this
    name: str
    age: int
    city: str = "unknown"          # ⭐ defaults allowed

p = Person("ada", 36)
p.name                  # ⭐ "ada"
p[0]                    # ⭐⭐ still "ada" — IT IS STILL A TUPLE
name, age, city = p     # ⭐ unpacks
isinstance(p, tuple)    # ⭐⭐ True — works anywhere a tuple works
p._replace(age=37)      # ⭐ functional update; returns a NEW Person
p._asdict()             # ⭐ dict(name=..., age=..., city=...)
```

```
⭐⭐ WHY namedtuple IS SO CHEAP: it adds NAMES WITHOUT ADDING STORAGE.
⭐   the fields are properties on the class, mapping to tuple indices
⭐   ⇒ ⭐⭐ per-instance memory is a plain tuple's — no __dict__ at all (Day 028)
⭐   ⇒ ⭐ so a million records cost what a million tuples cost, and read like objects.
```

## ⭐⭐ The decision table you will actually use

| ⭐ You need | ⭐⭐ Use |
|---|---|
| A small immutable record, iterable/unpackable, minimal memory | ⭐⭐ **`NamedTuple`** |
| A record with methods, defaults, `__post_init__`, mutability optional | ⭐⭐ **`@dataclass`** |
| ⭐ Immutable **and** hashable, with behaviour | ⭐ `@dataclass(frozen=True)` |
| ⭐ The shape of a **dict** (e.g. a JSON payload) typed | ⭐ `TypedDict` (Day 058) |
| ⭐⭐ **Validation and coercion of external data** | ⭐⭐ **Pydantic** (Stage 3) |
| A closed set of named values | `enum.Enum` (Day 058) |

⭐⭐ **The one-line rule:** *`NamedTuple` for a value you will pass around and unpack; `dataclass` for
a thing with behaviour; Pydantic the moment the data came from outside your program.*

⚠️ ⭐ **`NamedTuple`'s downside is that it is still a tuple** — it compares equal to a plain tuple with
the same values, it unpacks in contexts where you did not intend it to, and `len()`, indexing and
iteration all work whether or not they make sense for your type. **A frozen dataclass does not have
that ambiguity**, which is often the better trade.

# Part 4 — ⭐ Where tuples show up whether you chose them or not

```python
divmod(17, 5)                  # ⭐ (3, 2)
"a,b".partition(",")           # ⭐ ("a", ",", "b")
os.path.splitext("a.tar.gz")   # ("a.tar", ".gz")
def f(*args): ...              # ⭐⭐ args IS a tuple
sys.exc_info()
sorted(d.items(), key=lambda kv: kv[1])    # ⭐ sorting a dict by value
try: ... except (ValueError, TypeError):   # ⭐⭐ a tuple of exception types
"%s is %d" % (name, age)                   # ⭐ old-style formatting takes a tuple
```

⭐⭐ **`*args` being a tuple is the reason it is hashable**, and therefore the reason
`functools.lru_cache` can key on positional arguments at all — ⚠️ **while `**kwargs` is a dict, which
is why `lru_cache` treats `f(1)` and `f(x=1)` as *different* cache entries.**

```python
# ⭐ Tuple comparison is lexicographic, element by element:
(1, 2) < (1, 3)          # True
(1, 2) < (2, 0)          # True — the first element decides
("b", 1) < ("a", 99)     # False
# ⇒ ⭐⭐ which is exactly why key=lambda x: (a, b) sorts by a then b (Day 029).
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"A tuple is an immutable list"** | ⭐ It is a record — heterogeneous and positional. |
| `(1)` expecting a tuple | ⭐⭐ The comma makes it, not the parens. `(1,)`. |
| Assuming every tuple is hashable | ⭐⭐ Only if its contents are — immutability is shallow. |
| Using a list as a dict key | ⭐ `TypeError`. Convert to a tuple. |
| ⭐ Indexing tuples by position everywhere | ⭐⭐ `NamedTuple` — names for free, no extra memory. |
| Relying on `zip` length | ⭐⭐ It truncates silently. `strict=True`. |
| Choosing `NamedTuple` for a rich domain object | ⭐ It is still a tuple — indexable and unpackable. |
| Using `NamedTuple` for external data | ⭐⭐ No validation. Pydantic. |
| Expecting `_replace` to mutate | ⭐ It returns a new instance. |
| Thinking `_asdict`/`_replace` are private | ⭐ The underscore avoids clashing with field names. |

## Interview questions

**Q: List or tuple — how do you choose?**
> By what the data *is*, not by whether it changes. A list is a homogeneous collection of arbitrary
> length that I iterate; a tuple is a fixed-shape record where each position means something
> different, and I unpack it. The practical consequences are that tuples are hashable so they work as
> dict keys and set members, they're smaller because there's no over-allocation, and immutability
> means I can share them without defensive copies.

**Q: When is a tuple not hashable?**
> When something inside it isn't. Immutability in Python is shallow, so `(1, [2])` is a perfectly
> valid tuple whose `hash()` raises `TypeError`. It's the recursive form of the same rule: a
> container is hashable exactly when its contents are, which is what keeps the hash-contract
> guarantee — nothing reachable from the key can change while it's in the dict.

**Q: What's a `namedtuple` and why is it so cheap?**
> A tuple subclass whose fields are exposed as properties mapping to indices. So it reads like an
> object — `p.name` — while the instance storage is exactly a tuple's, with no `__dict__` at all.
> That means a million records cost what a million tuples cost. The typed form,
> `class Person(NamedTuple)`, is the one I'd write now, because it gives the annotations as well.

**Q: `NamedTuple` or `dataclass`?**
> `NamedTuple` when the value is genuinely a small immutable record I'll unpack and pass around, and
> memory matters. `dataclass` when it's an object with behaviour, defaults, or post-init logic —
> and `frozen=True` when it also needs to be hashable. The downside of `NamedTuple` is that it's
> still a tuple, so it compares equal to a plain tuple, and it can be indexed, iterated and unpacked
> whether or not that makes sense for the type. A frozen dataclass has no such ambiguity, and I'd
> reach for Pydantic instead the moment the data comes from outside the program, because then I need
> validation rather than just structure.

**Q: Anything to watch with `zip`?**
> It stops at the shortest input without saying anything, which silently drops data when two
> sequences that should be parallel aren't. `strict=True` in 3.10 and later raises instead, and I'd
> use it whenever the lengths are supposed to match — turning a silent data bug into an exception is
> almost always the right trade.

## 🎙️ Articulation drill

Record two minutes: **"When would you use a tuple instead of a list?"**

⭐ Lead with semantics rather than mutability, because that is the part most candidates get backwards:
**a list is many of the same thing; a tuple is one thing made of differently-meaning parts.** A
coordinate pair, a database row, a return value carrying two things. **The test is whether appending
to it would make any sense.**

⭐ Then the concrete payoffs: **hashable, so it can be a dict key or set member; smaller, because
there is no over-allocation; shareable without defensive copies.**

⭐⭐ **Then close on the honest caveat, which shows you know the boundary of the tool:** *"immutability
here is shallow — a tuple containing a list is unhashable, and its contents can still be mutated. So
a tuple guarantees the shape, not the contents. And once a record needs methods or defaults I'd move
to a frozen dataclass, because a `NamedTuple` is still a tuple: it compares equal to a plain one and
can be indexed and unpacked whether or not that makes sense for the type."*
