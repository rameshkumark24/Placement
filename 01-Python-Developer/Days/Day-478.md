# Part 2 — ⭐⭐ Templates as data, not code

```
⭐ ***THE DESIGN THAT FAILS, AND IT IS THE COMMON ONE:***
⭐   ⭐ a class per notification type, ⭐ a method per channel:
⭐     `class OrderShipped: def to_email(...) def to_sms(...)`
⭐   ⭐ ⭐⭐ NOW ADDING A NOTIFICATION IS A CODE CHANGE, A REVIEW,
⭐     A DEPLOY AND A RELEASE WINDOW — ⭐ for changing the word
⭐     "dispatched" to "shipped".
⭐   ⭐ ⭐⭐ AND IT MULTIPLIES: 40 TYPES × 4 CHANNELS = 160 METHODS
⭐     THAT ARE ALL THE SAME SHAPE.

⭐ ✅ ***THE DESIGN THAT WORKS: A TEMPLATE IS A ROW.***
⭐   ⭐ `(type, channel, locale) → subject, body, variables`
⭐   ⭐ ⭐⭐ SENDING IS THEN ***ONE*** CODE PATH FOR ALL TYPES: ⭐
⭐     look up the template, render it with the event payload,
⭐     hand it to the channel.
⭐   ⭐ ⭐⭐ ADDING A NOTIFICATION TYPE BECOMES AN INSERT.

⭐ ***THE THREE CONSEQUENCES YOU MUST NAME, OR IT SOUNDS
⭐   NAIVE:***
⭐   ⭐ ① ⭐⭐ ***TEMPLATES ARE NOW UNTRUSTED INPUT.*** ⭐ Render in
⭐     a sandboxed engine (Jinja2 with autoescape, ***no***
⭐     arbitrary attribute access), ⭐⭐ BECAUSE A TEMPLATE THAT
⭐     CAN EXECUTE PYTHON IS A REMOTE CODE EXECUTION FEATURE YOU
⭐     BUILT ON PURPOSE.
⭐   ⭐ ② ***a missing variable is now a runtime failure***, not
⭐     a compile error. ⭐ ⇒ validate the template's declared
⭐     variables against the event schema ***at save time***, and
⭐     ⭐⭐ RENDER WITH `StrictUndefined` SO A TYPO FAILS LOUDLY
⭐     RATHER THAN EMAILING "HELLO ".
⭐   ⭐ ③ ⭐⭐ TEMPLATES NEED VERSIONING AND A PREVIEW. ⭐ Same
⭐     argument as prompts being versioned config (Day 427) —
⭐     ⭐⭐ IT IS PRODUCTION BEHAVIOUR THAT LIVES OUTSIDE YOUR
⭐     REPOSITORY, SO IT NEEDS THE SAME DISCIPLINE.
```

# Part 3 — The shape

```python
from dataclasses import dataclass, field
from datetime import datetime
from enum import Enum
from typing import Protocol, Any

class Channel(Enum):
    EMAIL = "email"; SMS = "sms"; PUSH = "push"; IN_APP = "in_app"

class Priority(Enum):
    CRITICAL = 0     # ⭐⭐ OTP, SECURITY — bypasses quiet hours
    TRANSACTIONAL = 1
    MARKETING = 2    # ⭐ first to be dropped under load

@dataclass(frozen=True, slots=True)
class NotificationRequest:
    event_id: str            # ⭐⭐ THE IDEMPOTENCY KEY (PART 4)
    user_id: str
    type: str                # ⭐ "order.shipped" — data, not a class
    payload: dict[str, Any]
    priority: Priority
    created_at: datetime

class Sender(Protocol):
    """⭐⭐ ONE METHOD. Providers are swappable and testable."""
    async def send(self, *, to: str, subject: str | None,
                   body: str, idempotency_key: str) -> str: ...
    # ⭐⭐ RETURNS A PROVIDER MESSAGE ID — you need it to
    # reconcile delivery webhooks later, and forgetting it is
    # the design mistake you only notice in month three.
```

```
⭐ ⭐⭐ NOTE THREE THINGS IN THAT SKETCH:
⭐   ⭐ ① `type` is a ***string***, not a class. ⭐⭐ THAT IS THE
⭐     PART 2 DECISION MADE CONCRETE.
⭐   ⭐ ② `Sender` is a `Protocol`, so a fake in tests implements
⭐     it ⭐⭐ WITHOUT INHERITING ANYTHING.
⭐   ⭐ ③ ⭐⭐ `idempotency_key` IS ON THE INTERFACE, ⭐ so every
⭐     provider is forced to deal with it — ⭐⭐ THE SAME MOVE AS
⭐     MAKING `tenant_id` REQUIRED (DAY 434).
```

# Part 4 — ⭐⭐ Delivery guarantees, honestly

```
⭐ ***THE QUESTION THEY WILL ASK: "IS IT AT-LEAST-ONCE OR
⭐   AT-MOST-ONCE?" ⭐⭐ THE ANSWER IS THAT YOU DO NOT GET TO
⭐   CHOOSE EXACTLY-ONCE, SO YOU CHOOSE WHICH FAILURE YOU
⭐   PREFER.***

⭐ ⭐⭐ AT-MOST-ONCE ⭐ (send, don't retry) ⇒ ***lost messages.***
⭐   ⭐ Unacceptable for a password reset.
⭐ ⭐⭐ AT-LEAST-ONCE ⭐ (retry until acked) ⇒ ***duplicates.***
⭐   ⭐ Two "your order shipped" emails is embarrassing;
⭐     ⭐⭐ TWO "YOUR CARD WAS CHARGED" IS A SUPPORT TICKET.
⭐ ⇒ ⭐⭐ CHOOSE AT-LEAST-ONCE AND MAKE DUPLICATES ***INVISIBLE***
⭐   — ⭐ which is what a dedup key buys you.

⭐ ***THE THREE-LAYER DEFENCE:***
⭐   ⭐ ① ⭐⭐ A DEDUP KEY ON THE WAY ***IN***: ⭐ `event_id` unique
⭐     in your own table. ⭐⭐ A DUPLICATE INSERT FAILS AND YOU
⭐     STOP — ⭐ the database decides, not your control flow
⭐     (Day 412).
⭐   ⭐ ② ***an idempotency key to the provider***, so a retry
⭐     after a timeout does not send twice. ⭐⭐ MOST EMAIL AND SMS
⭐     PROVIDERS SUPPORT THIS AND ALMOST NOBODY USES IT.
⭐   ⭐ ③ ⭐⭐ A ***DEDUP WINDOW*** ON `(user, type, hash(payload))`
⭐     — ⭐ "you have already been told this in the last hour."
⭐     ⭐⭐ THIS IS THE ONE THAT SAVES YOU WHEN AN UPSTREAM
⭐     SERVICE REPLAYS ITS ENTIRE EVENT LOG AT 3AM, ⭐ which is a
⭐     real Tuesday and not a hypothetical.

⭐ ***AND THE THIRD OUTCOME, WHICH IS THE HARD ONE (DAY 398):***
⭐   ⭐ the provider call times out. ⭐⭐ DID IT SEND?
⭐   ⭐ ⇒ record `PENDING` ***before*** calling, never after —
⭐     ⭐⭐ WRITING AFTER IS THE DUAL-WRITE BUG AND IT LOSES
⭐     EXACTLY THE RECORD YOU CANNOT RECONSTRUCT (DAY 444).
⭐   ⭐ ⇒ on retry, ***ask the provider by your key*** rather than
⭐     re-sending blind.
```

# Part 5 — Preferences, priority and the fan-out

```
⭐ ***PREFERENCES ARE A ***POLICY LAYER***, EVALUATED BEFORE
⭐   SENDING, NOT SCATTERED THROUGH THE SENDERS:***
⭐   ⭐ per (user, type, channel) opt-out
⭐   ⭐ ⭐⭐ QUIET HOURS IN THE USER'S TIMEZONE — ⭐ and the rule
⭐     that `CRITICAL` bypasses them, ⭐⭐ BECAUSE AN OTP HELD
⭐     UNTIL 8AM IS A BROKEN LOGIN, NOT A COURTESY
⭐   ⭐ ***frequency caps*** — ⭐⭐ "AT MOST 3 MARKETING EMAILS PER
⭐     WEEK". ⭐ This is the control that stops the incident where
⭐     a loop emails one user 400 times.
⭐   ⭐ ⭐⭐ GLOBAL UNSUBSCRIBE AND LEGAL SUPPRESSION LISTS —
⭐     ⭐ checked ***last***, and non-overridable. ⭐⭐ A HARD
⭐     BOUNCE OR AN UNSUBSCRIBE MUST NOT BE BEATABLE BY A
⭐     PRIORITY FLAG.

⭐ ***FAN-OUT — THE ARCHITECTURAL FORK:***
⭐   ⭐ ⭐⭐ FAN-OUT ***ON WRITE*** ⭐ (expand to 2M rows now) ⇒
⭐     ⭐ predictable send, huge write burst.
⭐   ⭐ ⭐⭐ FAN-OUT ***ON READ*** ⭐ (store the campaign, expand
⭐     lazily) ⇒ ⭐ cheap write, complex delivery tracking.
⭐   ⭐ ⇒ ⭐⭐ TRANSACTIONAL ON WRITE, CAMPAIGNS AS A SEPARATE
⭐     BATCH PIPELINE WITH ITS OWN QUEUE AND ITS OWN RATE LIMIT.
⭐     ⭐ ⭐⭐ THE KEY SENTENCE: ***A MARKETING BLAST MUST NOT BE
⭐       ABLE TO DELAY A PASSWORD RESET*** — ⭐ separate queues,
⭐       not one queue with a priority field, because a single
⭐       queue's consumers are still shared.

⭐ ***AND THE PUBLISHING PATH:*** ⭐ the calling service writes
⭐   the event to ***its own outbox*** in the same transaction as
⭐   its business change (Day 407). ⭐⭐ NEVER A DIRECT CALL FROM
⭐   INSIDE A TRANSACTION — ⭐ an order that commits without its
⭐   email is recoverable; ⭐⭐ AN EMAIL SENT FOR AN ORDER THAT
⭐   ROLLED BACK IS NOT.
```

# 💬 Interview

**1. "Design a notification service."**

⭐ The design driver is one requirement: ⭐⭐ what varies constantly is the notification *types* and their
*content*, and it varies without engineering involvement. ⭐ So the test I'd hold the design to is
whether a product manager can add a new notification on a Tuesday afternoon without a deploy. ⭐⭐ That
means a template is a row — keyed by type, channel and locale — and sending is one code path for all
types: look up the template, render it with the event payload, hand it to a channel. ⭐ Adding a
notification type becomes an insert. ⭐⭐ The alternative, a class per type with a method per channel, is
forty types times four channels of near-identical code, and a release window to change one word.

**2. "What does 'templates as data' cost you?"**

⭐ Three things, and I'd name them unprompted or it sounds naive. ⭐⭐ Templates become untrusted input,
so rendering has to be sandboxed — autoescaping on, no arbitrary attribute access — because a template
that can execute Python is a remote code execution feature you built deliberately. ⭐ A missing variable
becomes a runtime failure rather than a compile error, so I'd validate declared variables against the
event schema at save time and render with strict undefined, or a typo emails someone "Hello ".
⭐⭐ And templates need versioning and a preview, because it's production behaviour living outside the
repository — the same argument as versioning prompts.

**3. "At-least-once or at-most-once?"**

⭐ You don't get exactly-once, so the question is which failure you prefer. ⭐⭐ At-most-once loses
messages, which is unacceptable for a password reset. At-least-once duplicates, and two "your order
shipped" emails are embarrassing while two "your card was charged" are a support ticket. ⭐ So:
at-least-once, with duplicates made invisible. ⭐⭐ Three layers — a unique `event_id` on the way in so a
duplicate insert fails and the database decides; a provider idempotency key so a retry after a timeout
doesn't send twice; and a dedup window on user plus type plus payload hash. ⭐ That last one is what
saves you when an upstream service replays its whole event log at 3am, which is a real Tuesday.

**4. "The provider call times out. Did it send?"**

⭐ That's the third outcome, and it's why the record is written *before* the call rather than after.
⭐⭐ Writing after is the dual-write bug and it loses precisely the record I can't reconstruct — I'd have
no idea a send was ever attempted. ⭐ So a row goes in as PENDING first, then the call, then the update.
⭐⭐ On retry I don't re-send blind: I query the provider by my idempotency key, because the provider is
the only component that actually knows. ⭐ Which is also why `send` returns the provider's message id —
you need it to reconcile delivery webhooks later, and forgetting it is the design mistake you notice in
month three.

**5. "How do you stop a marketing blast delaying a password reset?"**

⭐ Separate queues, not one queue with a priority field. ⭐⭐ A priority field sounds equivalent and
isn't, because the consumers are still shared — two million marketing messages occupy every worker
regardless of what the field says, and your OTP sits behind them. ⭐ So transactional notifications get
their own queue and their own workers, campaigns get a separate batch pipeline with its own rate limit.
⭐⭐ It's the same reasoning as separate API keys per workload class so a nightly job can't starve
interactive traffic.

**6. "Where do preferences live?"**

⭐ In a policy layer evaluated once before sending, not scattered through the senders — otherwise the
quiet-hours check exists in four places and drifts. ⭐⭐ Per user-type-channel opt-outs, quiet hours in
the user's timezone, and frequency caps, which is the control that prevents the incident where a loop
emails one person four hundred times. ⭐ Two rules matter: `CRITICAL` bypasses quiet hours, because an
OTP held until 8am is a broken login rather than a courtesy. ⭐⭐ And suppression lists — hard bounces,
legal unsubscribes — are checked last and are *not* bypassable by a priority flag. ⭐ Those two rules
pull in opposite directions on purpose, and being able to say why is the point.

**7. "How does the event get to you?"**

⭐ Through the calling service's outbox, written in the same transaction as its business change.
⭐⭐ Never a direct call from inside a transaction, because the failure modes are asymmetric: an order
that commits without its email is recoverable by a relay, and an email sent for an order that rolled
back is not. ⭐ That also gives at-least-once delivery into my service for free, which is exactly the
guarantee my dedup layers are built to absorb.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "design a notification service."**

Lead with the requirement that drives the design. **"The thing that varies constantly here is the
notification types and their content — and it varies without engineering involvement. So the test I'd
hold this to is whether a product manager can add a new notification on a Tuesday afternoon without a
deploy. Everything structural follows from taking that seriously."**

Then the structural consequence. **"That means templates are data, not code. A template is a row keyed
by type, channel and locale, and sending becomes one code path for every type: look up, render with the
payload, hand to a channel. Adding a notification is an insert. The alternative — a class per type with a
method per channel — is forty types times four channels of near-identical code, plus a release window to
change one word."**

Then name the costs before being asked. **"That choice costs three things and I'd rather say them up
front. Templates become untrusted input, so rendering is sandboxed with autoescaping and no arbitrary
attribute access — otherwise you've built remote code execution on purpose. Missing variables become
runtime failures, so I validate declared variables against the event schema at save time and render with
strict undefined. And templates need versioning and preview, because it's production behaviour living
outside the repo."**

Then delivery, which is where the interviewer will push. **"You don't get exactly-once, so I'd choose
at-least-once and make duplicates invisible: a unique event id so a duplicate insert fails and the
database decides, a provider idempotency key so a timeout retry doesn't double-send, and a dedup window
on user-plus-type-plus-payload-hash — which is what saves you when an upstream service replays its whole
event log at 3am. And the row goes in as PENDING before the provider call, never after, because writing
after loses exactly the record I can't reconstruct."**

Close on the isolation point. **"Last thing: separate queues for transactional and marketing, not one
queue with a priority field. A priority field sounds equivalent but the consumers are shared — two
million marketing messages occupy every worker regardless of the field, and the password reset waits
behind them."**
