# Day 014

**L-014** · ⭐⭐ **What JavaScript actually is in a browser** — the engine, the call stack, the event loop

**Time:** 3 hrs · **Mode:** NEW

> No parallel track. Take the whole session.
>
> ⭐⭐ **This is the most important Stage 0 day for a Python developer, and not because of
> JavaScript.** The browser's event loop and Python's `asyncio` event loop are **the same
> architecture**: one thread, a queue of callbacks, and a hard rule that nothing may block. Every
> intuition you build today is reused verbatim on Days 070–072, and **Day 072 — "the blocking call
> inside an `async def`" — is the single most common bug in production Python.**

# Part 1 — ⭐ The engine, and one thread

```
⭐ THE ENGINE (V8 in Chrome/Node, SpiderMonkey in Firefox, JavaScriptCore in Safari):
⭐   source ──▶ parse ──▶ bytecode ──▶ ⭐⭐ JIT: hot functions compiled to machine code
⭐   ⇒ ⭐ compare Day 002: Python compiles to bytecode too, but ⭐⭐ CPython has NO JIT —
⭐      which is a large part of why the same loop is 10–100× slower in Python.

⭐⭐ AND THE RULE THAT DEFINES EVERYTHING ELSE:
⭐   ⭐⭐ JAVASCRIPT IN A BROWSER RUNS ON EXACTLY ONE THREAD.
⭐   One call stack. One thing happening at a time. No pre-emption.
```

⭐⭐ **So how does it do ten things at once?** It does not. **The runtime around the engine does the
waiting**, and hands results back to the single thread when it is free. That distinction — *the
language is single-threaded, the runtime is not* — is the whole model.

# Part 2 — ⭐⭐ The event loop

```
⭐⭐ THE FOUR PIECES:

  ┌─────────────┐        ┌──────────────────────────────────┐
  │ ⭐ CALL      │        │ ⭐ WEB APIs / runtime              │
  │   STACK     │───────▶│  timers, fetch, DOM events, I/O  │
  │  (one)      │        │  ⭐⭐ these run OUTSIDE the thread   │
  └─────────────┘        └──────────────────────────────────┘
        ▲                             │ when done, push a callback
        │                             ▼
        │              ┌────────────────────────────────────┐
        │              │ ⭐⭐ MICROTASK QUEUE  (promises)      │  ⭐ drained COMPLETELY
        │              ├────────────────────────────────────┤
        └──────────────│ ⭐ MACROTASK QUEUE   (timers, I/O)  │  ⭐ ONE per turn
                       └────────────────────────────────────┘
                        ⭐⭐ THE EVENT LOOP: if the stack is empty →
                           drain ALL microtasks → take ONE macrotask → repeat
```

```js
console.log("1");
setTimeout(() => console.log("2"), 0);      // ⭐ macrotask
Promise.resolve().then(() => console.log("3"));  // ⭐⭐ microtask
console.log("4");

// ⭐⭐ OUTPUT: 1 4 3 2
// ⭐ 1 and 4 are synchronous. Then the stack empties.
// ⭐⭐ ALL microtasks drain first (3), THEN one macrotask (2).
```

⭐⭐ **`setTimeout(fn, 0)` does not mean "run now". It means "run after the current stack empties and
all microtasks have drained".** The number is a *minimum* delay, not a schedule.

# Part 3 — ⭐⭐ The freeze — and this is the Python lesson

```js
// ⭐⭐ Paste this into a browser console and try to scroll or click.
const end = Date.now() + 5000;
while (Date.now() < end) { /* burn CPU */ }
```

```
⭐⭐ THE PAGE IS COMPLETELY FROZEN FOR FIVE SECONDS.
⭐   · no clicks, no scrolling, no rendering, no animation
⭐   · ⭐⭐ because rendering and event handlers ALSO run on that one thread,
⭐     and they only get a turn when the stack is EMPTY.
⭐   ⇒ ⭐⭐ ONE SLOW FUNCTION BLOCKS EVERYTHING. There is no other thread to take over.
```

⭐⭐ **Now hold that image, because here is the same bug in Python, and you will write it:**

```python
# ⭐⭐ Days 070–072 in advance. THE SAME ARCHITECTURE, THE SAME FAILURE.
import asyncio, time, requests

async def handler():
    time.sleep(5)            # ⚠️⚠️ ⭐⭐ BLOCKS THE ENTIRE EVENT LOOP
    requests.get(url)        # ⚠️⚠️ ⭐⭐ SO DOES THIS — it is synchronous I/O
    # ⇒ ⭐⭐ EVERY other request being served by this worker waits. All of them.

async def handler_ok():
    await asyncio.sleep(5)               # ⭐ yields control back to the loop
    await client.get(url)                # ⭐ httpx.AsyncClient — non-blocking
    await asyncio.to_thread(cpu_work)    # ⭐⭐ CPU-bound work OFF the loop thread
```

⚠️ ⭐⭐ **This is the most damaging bug in modern Python backends, and the reason it is so common is
that it does not look wrong.** The code runs, the tests pass, and it is only under concurrency that
one slow call makes every unrelated request slow. **The browser freeze above is that bug, made
visible.** ⭐⭐ **`async def` does not make anything asynchronous — it makes a function that is
*allowed to await*. If it never awaits, it is a plain blocking function running on the one thread
that must never block.**

## ⭐ The two ways out, in both languages

| | ⭐ Browser | ⭐ Python |
|---|---|---|
| ⭐ Concurrent **I/O** | `fetch`, promises, `async/await` | `asyncio`, `httpx.AsyncClient`, async drivers |
| ⭐⭐ Parallel **CPU** | ⭐ **Web Workers** — a real second thread, no shared DOM | ⭐⭐ **processes** (`ProcessPoolExecutor`) — the GIL blocks threads (Day 065) |

⭐⭐ **The symmetry is exact and it is worth saying aloud in an interview:** in both runtimes, an
event loop gives you *concurrency for waiting*, and only a separate thread or process gives you
*parallelism for computing*. **Confusing those two is the root of both bugs.**

# Part 4 — ⭐ How JavaScript actually gets used

| ⭐ What | ⭐ Note |
|---|---|
| ⭐ Reading/changing the **DOM** | `document.querySelector(".card h2")` — ⭐ Day 013's selectors |
| Handling events | `el.addEventListener("click", fn)` — ⭐⭐ the callback goes on the queue |
| ⭐⭐ **Calling your API** | `fetch("/api/users")` — ⭐ **this is the client of everything you build** |
| Storage | `localStorage`, cookies (Day 019) |

```js
// ⭐ The three-line version of every front end you will write for your own API:
const res = await fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },   // ⭐⭐ or your API rejects it (Day 010)
  body: JSON.stringify({ name: "Ada" }),
});
if (!res.ok) throw new Error(res.status);            // ⭐⭐ fetch does NOT throw on 4xx/5xx
const data = await res.json();
```

⚠️ ⭐⭐ **`fetch` only rejects on a *network* failure — a 500 response is a perfectly successful
fetch.** You must check `res.ok`. ⭐ That is the opposite of `httpx`/`requests` in Python, where you
call `raise_for_status()` explicitly and nothing is checked either. **Both libraries make you opt in;
neither does it for you.**

⭐ **`async`/`await` in JavaScript is syntax over promises**, exactly as Python's is syntax over
coroutines and futures. ⭐⭐ **In both languages, `await` means "suspend me here and let the loop run
something else until this resolves"** — it does not mean "wait".

# Part 5 — ⭐ Where the JavaScript comes from, and why it matters to you

```html
<script src="/app.js"></script>            <!-- ⚠️ ⭐ BLOCKS HTML parsing while it downloads+runs -->
<script src="/app.js" defer></script>      <!-- ⭐⭐ downloads in parallel, runs AFTER parsing, IN ORDER -->
<script src="/app.js" async></script>      <!-- ⭐ downloads in parallel, runs WHENEVER ready — no order -->
```

⭐⭐ **`defer` is the right default**, and Day 015 explains why in terms of the rendering pipeline.

```
⭐⭐ AND THE CONSEQUENCE FOR YOUR PYTHON CODE (Day 012, again):
⭐   Server-rendered (Jinja2/Django)  ⇒ ⭐ HTML arrives complete ⇒ requests.get() sees the content
⭐   Client-rendered (React/Vue)      ⇒ ⭐⭐ HTML arrives ~EMPTY, JS fetches JSON and builds the DOM
⭐                                       ⇒ ⭐⭐ requests.get() sees an empty <div id="root">
⭐   ⇒ ⭐⭐ So "the page is dynamic" is not vague — it means the DOM was built by code that
⭐        never ran in your scraper, because your scraper has no JavaScript engine.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"JavaScript is multithreaded because it does things at once"** | ⭐⭐ One thread. The **runtime** does the waiting. |
| ⭐⭐ **Believing `setTimeout(fn, 0)` runs immediately** | ⭐ It runs after the stack empties and microtasks drain. |
| Mixing up microtasks and macrotasks | ⭐⭐ All microtasks drain before **one** macrotask. |
| ⭐⭐ **Blocking the loop with a long computation** | ⭐⭐ Freezes rendering and input. Same as Python's Day 072 bug. |
| Assuming `fetch` throws on 500 | ⭐⭐ Check `res.ok`. |
| Thinking `async def`/`async function` makes code parallel | ⭐⭐ It enables *awaiting*. Nothing more. |
| Using an event loop for CPU work | ⭐ Workers in JS, **processes** in Python. |
| Forgetting `defer` | ⭐ A blocking `<script>` in `<head>` delays first paint. |
| Expecting `requests` to run page JavaScript | ⭐⭐ It has no engine. There is nothing to run it. |

## Interview questions

**Q: Explain the event loop.**
> JavaScript runs on one thread with one call stack. Asynchronous work — timers, network, DOM events
> — is handled by the runtime outside that thread, and when it completes, a callback is placed on a
> queue. The event loop's rule is: when the call stack is empty, drain the entire microtask queue —
> promise callbacks — and then take exactly one macrotask, such as a timer or an I/O callback, and
> run it. That's why `setTimeout(fn, 0)` runs after synchronous code and after every pending promise
> callback: the delay is a minimum, not a schedule.

**Q: Then how is anything concurrent?**
> Because waiting isn't done on the thread. The single thread only ever executes callbacks; the
> waiting happens in the runtime. So the model gives you concurrency for I/O — thousands of
> in-flight requests on one thread — and no parallelism at all for computation. For CPU work you need
> a Web Worker, which is a genuinely separate thread with no shared DOM.

**Q: How does that map onto Python?**
> Almost exactly. `asyncio` is the same architecture: one thread, one loop, callbacks and coroutines,
> and the same absolute rule that nothing may block. The failure mode transfers too — a `time.sleep`
> or a `requests.get` inside an `async def` stalls the entire loop, so every other request that
> worker is serving waits. It's the browser freeze, in a server. And the escape hatches match: async
> libraries for I/O, `asyncio.to_thread` or a process pool for CPU — with the extra Python wrinkle
> that the GIL means threads don't give real CPU parallelism, so it has to be processes.

**Q: What actually freezes a page?**
> Anything that keeps the call stack non-empty for a long time — a tight loop, a huge synchronous
> JSON parse, a heavy layout computation. Rendering and event handling run on the same thread and
> only get a turn when the stack empties, so the page stops responding entirely. Anything over about
> 50 ms is perceptible; the fix is to move it to a Worker or to break it into chunks that yield.

**Q: Why does your scraper see an empty `div`?**
> Because a client-rendered app ships a nearly empty HTML document and builds the DOM in JavaScript
> after fetching JSON. `requests` has no JavaScript engine, so none of that ever runs — I get exactly
> what the server sent. Either I call the same JSON API directly, which is usually cleaner, or I use
> a real browser via Playwright.

## 🎙️ Articulation drill

Record two minutes: **"Explain the event loop, and then explain why it is the same bug in Python."**

⭐ One thread, one stack, a queue of callbacks, and a runtime that does the waiting. ⭐⭐ **Then the
payoff sentence: the model buys you enormous concurrency for waiting, and exactly zero parallelism
for computing — so the one unforgivable act is to compute, or to wait synchronously, on the loop
thread.**

⭐⭐ **Then land it in Python:** a `time.sleep` or a `requests.get` inside an `async def` is that
unforgivable act. It looks harmless, it passes every test, and in production it makes one slow
dependency into every user's latency. ⭐ **The tell is that the function is `async def` but contains
no `await` around the slow thing** — and that is a code review you can now do in five seconds.
