# Day 126

**L-126** · **OpenAPI by hand** — spec-first vs code-first, and ⭐⭐ documentation that cannot drift

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a specification is only worth having if something breaks when it stops
> being true — so the question that matters is not "do we have OpenAPI" but "what enforces it", and a
> hand-written YAML file nobody validates against is a wiki page in a costume.**
>
> ⭐ Day 101 ranked documentation by how long it stays true. **Today is how to get an API description
> onto the top of that list.**

# Part 1 — ⭐ The document

```yaml
openapi: 3.1.0
info: {title: Orders API, version: "1.0.0"}
servers: [{url: https://api.acme.com/v1}]

paths:
  /orders/{order_id}:
    get:
      operationId: getOrder                    # ⭐⭐ becomes the CLIENT METHOD NAME
      summary: Fetch one order
      security: [{bearerAuth: []}]
      parameters:
        - {name: order_id, in: path, required: true, schema: {type: integer}}
      responses:
        "200":
          description: The order
          content:
            application/json:
              schema: {$ref: "#/components/schemas/Order"}    # ⭐ reuse
        "404": {$ref: "#/components/responses/NotFound"}      # ⭐⭐ errors ARE the contract
        "429": {$ref: "#/components/responses/RateLimited"}

components:
  schemas:
    Order:
      type: object
      required: [id, total, status]            # ⭐⭐ REQUIRED means the client may rely on it
      properties:
        id:     {type: integer}
        total:  {type: string, format: decimal, example: "50.00"}   # ⭐⭐ money as a STRING
        status: {type: string, enum: [pending, paid, shipped]}
  securitySchemes:
    bearerAuth: {type: http, scheme: bearer, bearerFormat: JWT}
```

```
⭐⭐ FOUR THINGS PEOPLE LEAVE OUT, EACH OF WHICH MAKES THE SPEC LESS USEFUL THAN
⭐   IT LOOKS:
⭐  1. ⭐⭐ ERROR RESPONSES. A spec listing only `200` documents the happy path
⭐       and leaves every client to discover failures in production. ⭐ Day 120's
⭐       codes belong here.
⭐  2. ⭐⭐ `required`. Without it EVERY FIELD IS OPTIONAL, so a generated client
⭐       makes everything `Optional[...]` and callers write `if order.id` forever.
⭐  3. ⭐ `operationId` — ⭐⭐ it becomes the method name in every generated
⭐       client, so `getOrder` or `get_order_by_id` is a naming decision that
⭐       reaches other people's codebases.
⭐  4. ⭐⭐ MONEY AS A STRING with `format: decimal`. ⭐ JSON numbers are IEEE
⭐       doubles (Days 041, 076) — ⭐⭐ a generated client will parse `50.10` into
⭐       a float and you have lost pennies before the code even runs.
```

# Part 2 — ⭐⭐ Spec-first or code-first

| | ⭐ Spec-first | ⭐ Code-first |
|---|---|---|
| Source of truth | ⭐ the YAML | ⭐ the code (Pydantic + routes) |
| ⭐⭐ Drift | ⭐⭐ **possible — the spec can lie** | ⭐ impossible **if** it is truly generated |
| Design review | ⭐⭐ **before implementation** | ⭐ after |
| Parallel work | ⭐⭐ front-end mocks from day one | ⭐ front-end waits |
| Effort | ⭐ writing YAML by hand | ⭐ near zero |
| Multi-team | ⭐⭐ the natural fit | ⭐ awkward |

```
⭐⭐ THE HONEST POSITION, AND IT IS NOT "PICK ONE":
⭐   · ⭐⭐ CODE-FIRST FOR A TEAM THAT OWNS BOTH SIDES. FastAPI generates the
⭐        spec from the same Pydantic models that validate the requests
⭐        (Day 119), ⭐⭐ SO THE SPEC CANNOT DRIFT — it is derived from the thing
⭐        that actually runs. ⭐ That is a genuinely strong property and it is
⭐        free.
⭐   · ⭐⭐ SPEC-FIRST WHEN THE API IS A PRODUCT, or when several teams must agree
⭐        before anyone builds. ⭐ The spec becomes a negotiable artefact, the
⭐        front end mocks from it on day one, and ⭐⭐ THE API GETS DESIGN REVIEW
⭐        BEFORE IT EXISTS — which is Day 100B's point that design comments must
⭐        arrive before someone has polished 400 lines.
⭐   ⇒ ⭐⭐ AND THE HYBRID THAT ACTUALLY WORKS: design the shape in YAML, discuss
⭐        it, then implement — ⭐ and have CI assert that the generated spec still
⭐        matches the agreed one (Part 4). ⭐⭐ You get the design conversation AND
⭐        the no-drift guarantee.
```

⚠️ ⭐ **Code-first is only drift-proof if the spec reflects real behaviour.** ⭐⭐ **A route that
returns a bare `dict` documents nothing** — the generated spec says "an object" and the client learns
nothing. ⭐ **The response model (Day 119) is what makes generation truthful**, which is a second
reason for it beyond the security one.

# Part 3 — ⭐ Generating it from your own framework

```python
def generate_openapi(app) -> dict:
    paths = {}
    for route in app.router.routes:                       # ⭐⭐ routes are DATA (Day 107)
        path = re.sub(r"\{(\w+):\w+\}", r"{\1}", route.template)     # ⭐ strip converters
        operation = {
            "operationId": route.name,
            "parameters": [
                {"name": n, "in": "path", "required": True,
                 "schema": {"type": OPENAPI_TYPES[route.converters[n]]}}
                for n in route.converters
            ],
            "responses": {"200": {"description": "OK"}},
        }
        if (model := getattr(route.handler, "__response_model__", None)):
            operation["responses"]["200"]["content"] = {
                "application/json": {"schema": model.model_json_schema()}   # ⭐⭐ free
            }
        for method in route.methods:
            paths.setdefault(path, {})[method.lower()] = operation
    return {"openapi": "3.1.0", "info": {...}, "paths": paths}
```

```
⭐⭐ THIS IS WHY DAY 107 INSISTED ROUTES BE DATA RATHER THAN CONTROL FLOW. An
⭐   `if/elif` router cannot be enumerated, so it cannot be documented, reversed,
⭐   or validated at startup. ⭐ A route table can be all three.
⭐   ⇒ ⭐⭐ AND PYDANTIC'S `model_json_schema()` DOES THE HARD HALF FOR FREE,
⭐        because JSON Schema is what OpenAPI 3.1 uses for its schemas. ⭐ The
⭐        validation model and the documentation model are the same object —
⭐        which is precisely the property that removes drift.
⭐   ⇒ ⭐ this is also Day 112's signature inspection doing a second job: the
⭐        same introspection that resolves handler parameters describes them.
```

⭐ **Serve it at `/openapi.json`** and put Swagger UI or Redoc in front of it. ⭐⭐ **Interactive docs
that make real calls are worth more than any amount of prose**, because a developer's first question
is always "what does the response actually look like" — and now they can press a button.

# Part 4 — ⭐⭐ Making the spec load-bearing

```python
# ⭐⭐ 1. VALIDATE RESPONSES AGAINST THE SPEC, IN THE TEST SUITE:
def test_responses_match_spec(client, spec):
    for method, path, params in EVERY_ENDPOINT:
        r = client.request(method, path, **params)
        schema = spec_response_schema(spec, method, path, r.status)
        jsonschema.validate(json.loads(r.body), schema)     # ⭐ fails on ANY divergence
```

```
⭐⭐ THAT SINGLE TEST IS WHAT PROMOTES THE SPEC FROM DOCUMENTATION TO CONTRACT.
⭐   ⇒ ⭐ Day 101's ranking: a test cannot lie, a README usually does. ⭐⭐ A spec
⭐        with a validation test is a test; a spec without one is a README.
⭐   ⇒ ⭐ it also catches the subtle divergences — a field documented as an
⭐        integer that is sometimes null, an enum that gained a value nobody
⭐        documented (Day 125).
```

```bash
# ⭐⭐ 2. FAIL CI ON A BREAKING SPEC CHANGE:
oasdiff breaking openapi-main.json openapi-pr.json      # ⭐ exits non-zero on a break

# ⭐ 3. LINT THE SPEC ITSELF:
spectral lint openapi.yaml    # ⭐ missing descriptions, missing errors, naming drift

# ⭐ 4. GENERATE CLIENTS:
openapi-generator generate -i openapi.json -g python -o ./client
```

```
⭐⭐ THE FOUR TOGETHER TURN A DOCUMENT INTO INFRASTRUCTURE:
⭐   · validation tests ⇒ the spec is TRUE
⭐   · ⭐⭐ oasdiff in CI ⇒ ⭐⭐ A BREAKING CHANGE BECOMES A FAILED BUILD RATHER
⭐        THAN A CUSTOMER EMAIL. ⭐ This is Day 125's whole problem, solved by a
⭐        machine.
⭐   · linting ⇒ the spec is USABLE — every endpoint described, every error listed
⭐   · generated clients ⇒ ⭐ consumers get a typed library instead of writing
⭐        `requests` calls, ⭐⭐ and now `operationId` and `required` matter
⭐        because they shape somebody else's code.
```

# Part 5 — ⭐ What a spec cannot say

```
⭐⭐ OPENAPI DESCRIBES SHAPES. IT DOES NOT DESCRIBE BEHAVIOUR, AND THE GAP IS
⭐   WHERE YOUR PROSE DOCUMENTATION EARNS ITS PLACE:
⭐   ✘ ⭐⭐ IDEMPOTENCY — that `Idempotency-Key` exists, what a repeat returns,
⭐       and the TTL (Day 122)
⭐   ✘ ⭐ RATE LIMITS — the numbers, the dimensions, and the backoff you expect
⭐       (Day 123)
⭐   ✘ ⭐⭐ ORDERING AND CONSISTENCY — "this is eventually consistent; a read
⭐       immediately after a write may not see it". ⭐ Nothing in a schema can
⭐       say that, and it is the single most surprising property of a real API.
⭐   ✘ ⭐ PAGINATION SEMANTICS — cursor stability, what `null` means (Day 121)
⭐   ✘ ⭐⭐ WHICH CHANGES YOU CONSIDER BREAKING, and the rule that clients must
⭐       tolerate unknown fields and enum values (Day 125) — ⭐⭐ if you never
⭐       write that down, "additive" is not true.
⭐   ✘ ⭐ side effects: does `POST /orders` send an email? Charge a card?
⭐   ⇒ ⭐⭐ SO: SPEC FOR SHAPES, PROSE FOR BEHAVIOUR, AND A QUICKSTART THAT GETS
⭐        SOMEONE TO A SUCCESSFUL CALL IN FIVE MINUTES. ⭐ Day 101's README test,
⭐        applied to an API.
```

```
⭐ THE DOCUMENTATION SET THAT ACTUALLY GETS USED, IN ORDER OF HOW OFTEN:
⭐   1. ⭐⭐ A QUICKSTART — auth, one working `curl`, one real response. ⭐ This
⭐        is read more than everything else combined.
⭐   2. ⭐ interactive reference (Swagger UI over your generated spec)
⭐   3. ⭐⭐ THE BEHAVIOUR PAGES: errors, idempotency, rate limits, pagination,
⭐        versioning policy — ⭐ one page each, and they are what a serious
⭐        integrator reads before committing
⭐   4. ⭐ a changelog with dates ⇒ ⭐⭐ and the deprecations from Day 125, so
⭐        nobody can say they were not told
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **A spec nothing validates against** | ⭐⭐ It is a README in a costume. Add a response-validation test. |
| Documenting only `200` | ⭐ Clients discover your failures in production. |
| ⭐ Omitting `required` | ⭐⭐ Every generated field becomes `Optional` and callers hedge forever. |
| ⭐ Money as a JSON number | ⭐⭐ Parsed as a float by the client. String with `format: decimal`. |
| No `operationId` | ⭐ The generator invents method names in other people's code. |
| ⭐ Handlers returning a bare `dict` | ⭐⭐ Code-first documents nothing. The response model is what makes it truthful. |
| ⭐⭐ **Assuming code-first cannot drift** | ⭐ It cannot only if the spec is generated from what actually runs. |
| Hand-editing a generated spec | ⭐ It is regenerated tomorrow. Fix the code. |
| ⭐ No breaking-change check in CI | ⭐⭐ A break becomes a customer email instead of a failed build. |
| Documenting shapes and stopping | ⭐⭐ Idempotency, rate limits and consistency are invisible to a schema. |
| ⭐ No quickstart | ⭐ The most-read page, missing. |

## Interview questions

**Q: Spec-first or code-first?**
> Code-first when one team owns both sides, because the spec is generated from the same models that
> validate the requests, so it can't drift — it's derived from what actually runs, and that's a strong
> property for free. Spec-first when the API is a product or several teams have to agree before
> anyone builds, because then the spec is a negotiable artefact, the front end can mock from it on day
> one, and the API gets design review before it exists. In practice I like the hybrid: sketch the
> shape in YAML, have the design conversation, implement it, and then have CI assert the generated
> spec still matches what was agreed. That gets both properties.

**Q: What makes a spec worth having?**
> That something breaks when it stops being true. A YAML file nobody validates against is a wiki page
> in a costume — it drifts, people stop trusting it, and then it's worse than nothing because it
> misleads. The minimum is a test that validates real responses against the spec, which catches the
> subtle divergences: a field documented as an integer that's sometimes null, or an enum that gained a
> value nobody wrote down. On top of that, `oasdiff` in CI so a breaking change is a failed build
> rather than a customer email.

**Q: What do people leave out of a spec?**
> Error responses, most often — a spec listing only `200` documents the happy path and leaves clients
> to discover failures in production. `required`, without which every field in a generated client is
> optional and callers hedge forever. `operationId`, which becomes the method name in other people's
> code, so it's a naming decision with unusual reach. And money as a JSON number rather than a string
> — JSON numbers are IEEE doubles, so a generated client parses `50.10` as a float and you've lost
> pennies before any of your code runs.

**Q: What can't OpenAPI describe?**
> Behaviour. It describes shapes. It can't say that an endpoint accepts an idempotency key and what a
> repeat returns, or what the rate limits and expected backoff are, or — the one that surprises people
> most — that a read immediately after a write may not see it. Nothing in a schema expresses eventual
> consistency. It also can't state which changes you consider breaking, or the rule that clients must
> tolerate unknown fields and enum values, and if that's never written down then "additive" isn't
> actually true. So: spec for shapes, prose for behaviour, and a quickstart that gets someone to a
> successful call in five minutes — which is the page that gets read more than everything else
> combined.

**Q: Why could you generate a spec from your own framework so easily?**
> Because routes were data rather than control flow from the start. An `if/elif` router can't be
> enumerated, so it can't be documented, reversed or validated at startup. A route table can be all
> three. And Pydantic's `model_json_schema()` does the other half free, because OpenAPI 3.1 uses JSON
> Schema — so the validation model and the documentation model are literally the same object, which is
> exactly the property that removes drift.
