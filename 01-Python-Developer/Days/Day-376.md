# Day 376 🕸️

**P-376** · 🕸️ **Distributed tracing with OpenTelemetry**

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a trace answers "where did the time go?" across process boundaries, and
> the entire value depends on one fragile thing — context propagating unbroken through every hop,
> including the two that always break it in Python, which are the queue and the thread pool.**

---

# Part 1 — ⭐⭐ The model, in five terms

```
⭐⭐ ***TRACE*** — one logical operation end to end, identified
⭐   by a `trace_id`.
⭐⭐ ***SPAN*** — one unit of work within it: an HTTP handler, a
⭐   query, an outbound call. ⭐ Has a start, a duration, a
⭐   `parent_span_id`, attributes, events and a status.
⭐⭐ ***CONTEXT*** — the `(trace_id, span_id, flags)` that must
⭐   travel with the work. ⭐⭐ THIS IS THE WHOLE PROBLEM.
⭐⭐ ***PROPAGATION*** — serialising context across a boundary.
⭐   ⭐ W3C `traceparent: 00-<trace_id>-<span_id>-<flags>`.
⭐⭐ ***SAMPLING*** — deciding which traces to keep (Part 5).

⭐⭐ AND WHY OTEL SPECIFICALLY:
⭐   ⭐ ⭐⭐ ONE INSTRUMENTATION API, ONE WIRE PROTOCOL (OTLP),
⭐     ONE COLLECTOR THAT CAN PROCESS, SAMPLE AND ROUTE.
⭐   ⇒ ⭐⭐ INSTRUMENT ONCE, CHANGE VENDORS WITH A CONFIG FILE —
⭐     ⭐ which matters because you ***will*** change vendors, and
⭐     re-instrumenting an estate is a quarter of work nobody
⭐     budgets for.
⭐   ⭐ ⭐⭐ AND THE COLLECTOR IS THE UNDERRATED PIECE: it does
⭐     tail sampling, attribute scrubbing, batching and
⭐     multi-destination fan-out ***outside your process***, so
⭐     none of that logic lives in your application.
```

# Part 2 — ⭐⭐ Getting it working in Python

```python
# ⭐ Auto-instrumentation first: it is genuinely a good hour.
FastAPIInstrumentor.instrument_app(app)
SQLAlchemyInstrumentor().instrument(engine=engine.sync_engine)
HTTPXClientInstrumentor().instrument()
RedisInstrumentor().instrument()
CeleryInstrumentor().instrument()          # ⭐⭐ PART 4 MATTERS

# ⭐⭐ THEN THE PART THAT MAKES TRACES ACTUALLY USEFUL
tracer = trace.get_tracer(__name__)

async def price_order(order_id: UUID, tenant_id: str) -> Money:
    with tracer.start_as_current_span("price_order") as span:
        span.set_attribute("tenant.id", tenant_id)          # ⭐⭐ YOURS
        span.set_attribute("order.id", str(order_id))
        span.set_attribute("order.line_count", len(lines))
        try:
            result = await _compute(lines)
        except PricingError as exc:
            span.set_status(Status(StatusCode.ERROR))        # ⭐⭐ REQUIRED
            span.record_exception(exc)
            raise
        span.set_attribute("pricing.rule_version", result.version)
        span.set_attribute("cache.hit", result.from_cache)
        return result.total
```

```
⭐⭐ THE DIVISION OF LABOUR:
⭐   ⭐ ***AUTO-INSTRUMENTATION*** gives you the skeleton: HTTP
⭐     in, DB out, HTTP out, cache, queue. ⭐⭐ IT TELLS YOU A
⭐     QUERY TOOK 800 ms.
⭐   ⭐ ⭐⭐ ***YOUR ATTRIBUTES*** TELL YOU IT WAS SLOW ***FOR
⭐     ENTERPRISE TENANTS WITH MORE THAN TEN THOUSAND ORDERS***
⭐     — ⭐ and that is the difference between a trace you look at
⭐     and a trace that answers something.
⭐   ⇒ ⭐ Business attributes worth adding everywhere:
⭐     `tenant.id`, `user.plan`, `result.count`, `cache.hit`,
⭐     `retry.count`, `feature_flag.x`.

⭐⭐ THE FIVE RULES FOR ATTRIBUTES:
⭐   ① ⭐⭐ SET STATUS TO ERROR ON EXCEPTIONS. ⭐ Otherwise a
⭐      failed span looks identical to a successful one and your
⭐      error-trace filters return nothing.
⭐   ② ⭐ Use the semantic conventions where they exist
⭐      (`http.*`, `db.*`, `messaging.*`) ⇒ ⭐⭐ TOOLING
⭐      UNDERSTANDS THEM AND BUILDS VIEWS AUTOMATICALLY.
⭐   ③ ⭐⭐ NEVER PUT A SECRET, A FULL REQUEST BODY, OR PII IN AN
⭐      ATTRIBUTE. ⭐ Spans go to a vendor. Day 375's rules apply
⭐      identically, ⭐⭐ AND `db.statement` CAN CONTAIN LITERAL
⭐      VALUES — check what your SQL instrumentation captures.
⭐   ④ ⭐ High cardinality is ***fine*** here (unlike metrics) —
⭐      ⭐⭐ THAT IS PRECISELY WHY TRACES EXIST (Day 338).
⭐   ⑤ ⭐ Do not create a span per loop iteration ⇒ ⭐⭐ A TRACE
⭐      WITH 40,000 SPANS IS UNREADABLE AND MAY BE DROPPED BY
⭐      THE BACKEND. ⭐ One span for the loop, with a count
⭐      attribute.
```

# Part 3 — ⭐⭐ Where propagation breaks (and it is always these)

```
⭐⭐ ① ***THE QUEUE.*** ⭐ The single most common break.
⭐   ⭐ HTTP request → publish → ⭐⭐ TRACE ENDS. ⭐ Worker
⭐     consumes → ⭐⭐ A BRAND NEW ROOT TRACE. ⭐ The two halves
⭐     of one operation can never be joined.
⭐   ⇒ ⭐⭐ FIX: INJECT `traceparent` INTO THE MESSAGE HEADERS ON
⭐     PUBLISH AND EXTRACT ON CONSUME.
⭐   ⇒ ⭐⭐ AND THE HOP EVERYONE FORGETS (Days 263, 285, 338):
⭐     ***THE OUTBOX ROW.*** ⭐ If the message is written to a
⭐     table first, ⭐⭐ `traceparent` MUST BE A ***COLUMN*** ON
⭐     THAT ROW, OR THE RELAY PUBLISHES WITH NO CONTEXT AND YOU
⭐     HAVE BROKEN IT AT A PLACE NOBODY THINKS TO LOOK.
⭐   ⇒ ⭐ Link, don't nest: ⭐⭐ USE A ***SPAN LINK*** RATHER THAN
⭐     A PARENT WHEN THE CONSUMER RUNS MINUTES LATER — ⭐ a child
⭐     span that starts an hour after its parent produces a
⭐     one-hour trace that is meaningless.

⭐⭐ ② ***THREAD POOLS AND `run_in_executor`.***
⭐   ⭐ ⭐⭐ CONTEXT LIVES IN `contextvars`, AND A `contextvars`
⭐     CONTEXT DOES ***NOT*** AUTOMATICALLY CROSS INTO A
⭐     `ThreadPoolExecutor` WORKER.
⭐   ⇒ ⭐ `asyncio.to_thread` copies the context (⭐ good);
⭐     ⭐⭐ A RAW `executor.submit` DOES NOT — ⭐ wrap with
⭐     `contextvars.copy_context().run`.
⭐   ⇒ ⭐⭐ SYMPTOM: THE SPAN FOR YOUR CPU-BOUND WORK APPEARS AS
⭐     AN ORPHAN ROOT, AND THE TIME IT TOOK IS SIMPLY MISSING
⭐     FROM THE PARENT TRACE.

⭐⭐ ③ ***`asyncio.create_task` / BACKGROUND TASKS.***
⭐   ⭐ A task created ***inside*** a request inherits the
⭐     context — ⭐⭐ SO ITS SPAN IS A CHILD OF A REQUEST THAT
⭐     HAS ALREADY RETURNED, AND THE PARENT SPAN'S DURATION IS
⭐     ALREADY CLOSED.
⭐   ⇒ ⭐ Use a span link, ⭐ or start a fresh root with an
⭐     attribute pointing at the originating trace.

⭐⭐ ④ ***PROCESS BOUNDARIES YOU FORGOT.*** ⭐ A `subprocess`
⭐   call, ⭐ a Lambda invocation, ⭐⭐ A CRON JOB THAT PICKS UP
⭐   WORK LEFT BY A REQUEST.
⭐   ⇒ ⭐ Pass `traceparent` in the environment or the payload.

⭐⭐ ⑤ ***A GATEWAY OR PROXY THAT STRIPS UNKNOWN HEADERS.***
⭐   ⇒ ⭐⭐ EVERY TRACE STARTS AT YOUR SERVICE AND THE CLIENT
⭐     HALF IS INVISIBLE. ⭐ Allow-list `traceparent` and
⭐     `tracestate`.

⭐⭐ ⇒ THE TEST FOR ALL FIVE: ***TRIGGER ONE OPERATION THAT
⭐   CROSSES EVERY BOUNDARY YOU HAVE, AND CONFIRM IT IS ***ONE
⭐   TRACE***.*** ⭐ Do this after every architectural change;
⭐   ⭐⭐ PROPAGATION REGRESSES SILENTLY AND NOTHING FAILS.
```

# Part 4 — ⭐ Celery, and the async-worker specifics

```
⭐⭐ CELERY'S INSTRUMENTATION PROPAGATES CONTEXT THROUGH TASK
⭐   HEADERS — ⭐ but only if you publish through Celery.
⭐   ⭐ ⭐⭐ IF YOU USE AN OUTBOX AND A RELAY (Day 263), ***THE
⭐     RELAY IS THE PUBLISHER***, SO IT MUST RESTORE THE CONTEXT
⭐     FROM THE ROW BEFORE CALLING `.delay()`.

⭐⭐ THE SPAN SHAPE THAT IS ACTUALLY USEFUL FOR A TASK:
⭐   ⭐ ⭐⭐ RECORD ***QUEUE TIME*** SEPARATELY FROM ***EXECUTION
⭐     TIME***. ⭐ `enqueued_at` on the message; the consumer
⭐     computes the wait.
⭐   ⇒ ⭐⭐ WITHOUT IT, "THE TASK TOOK FOUR MINUTES" IS
⭐     AMBIGUOUS BETWEEN "IT WAS SLOW" AND "IT SAT IN A QUEUE
⭐     FOR THREE MINUTES AND FIFTY SECONDS" — ⭐ and those have
⭐     completely different fixes.
⭐   ⭐ Attributes: `messaging.message.id`, `retry.count`,
⭐     ⭐⭐ AND THE TERMINAL OUTCOME (succeeded / retried /
⭐     dead-lettered).

⭐⭐ AND THE RETRY QUESTION: ⭐⭐ SHOULD A RETRY BE THE SAME
⭐   TRACE?
⭐   ⭐ Same trace ⇒ ⭐ you see all attempts together, ⭐⭐ AND THE
⭐     TRACE SPANS HOURS.
⭐   ⭐ New trace with a link ⇒ ⭐ each attempt is readable,
⭐     ⭐ and you can still navigate between them.
⭐   ⇒ ⭐⭐ PREFER THE SECOND, AND CARRY THE ORIGINAL
⭐     `trace_id` AS AN ATTRIBUTE. ⭐ Readable beats complete.
```

# Part 5 — ⭐⭐ Sampling, properly

```
⭐⭐ YOU CANNOT KEEP EVERY TRACE AT VOLUME. ⭐ The question is
⭐   ***which***.

⭐⭐ ***HEAD SAMPLING*** — decide at the root, propagate the
⭐   decision in the flags.
⭐   ⭐ ✔ Cheap, no buffering, ⭐⭐ AND CONSISTENT BY
⭐     CONSTRUCTION — every service honours the same decision,
⭐     so you never get half a trace.
⭐   ⭐ ✘ ⭐⭐ AT 1% YOU KEEP 1% OF THE ERRORS — WHICH ARE THE
⭐     ONLY TRACES YOU WANTED.

⭐⭐ ***TAIL SAMPLING*** — buffer the whole trace in the
⭐   collector, decide after it completes.
⭐   ⭐ ✔ ⭐⭐ KEEP 100% OF ERRORS, 100% OF SLOW TRACES, 0.1% OF
⭐     FAST SUCCESSES. ⭐ Exactly the policy you want.
⭐   ⭐ ✘ The collector holds traces in memory for a window
⭐     (typically 10–30 s), ⭐⭐ SO IT NEEDS SIZING, AND ALL SPANS
⭐     OF A TRACE MUST REACH THE ***SAME*** COLLECTOR INSTANCE —
⭐     which means load-balancing by `trace_id`, and that is the
⭐     operational detail people miss.
⭐   ⇒ ⭐⭐ TAIL SAMPLING IS THE ANSWER, AND THE POLICY IS ALWAYS
⭐     THE SAME SHAPE: ***KEEP EVERYTHING INTERESTING, SAMPLE
⭐     THE BORING.***

⭐⭐ THREE RULES REGARDLESS:
⭐   ① ⭐⭐ THE DECISION MUST BE CONSISTENT ACROSS SERVICES. ⭐ A
⭐      partial trace is worse than none: ⭐⭐ IT LIES ABOUT WHERE
⭐      THE TIME WENT, BECAUSE A MISSING SPAN LOOKS LIKE A GAP
⭐      IN THE PARENT.
⭐   ② ⭐⭐ RECORD THE SAMPLE RATE ON THE SPAN. ⭐ Without it,
⭐      counts derived from traces are wrong by an unknown
⭐      factor — ⭐ "23 errors" might be 2,300.
⭐   ③ ⭐⭐ NEVER DERIVE SLOs FROM SAMPLED TRACES. ⭐ Use metrics
⭐      for rates and percentiles; ⭐ use traces to explain them.

⭐⭐ AND THE CHEAPEST WIN: ⭐⭐ ***EXEMPLARS.*** ⭐ Attach a
⭐   `trace_id` to a histogram bucket sample, ⭐⭐ AND A CLICK ON
⭐   A LATENCY SPIKE IN GRAFANA LANDS YOU IN THE ACTUAL SLOW
⭐   REQUEST. ⭐ It is the single best connection between metrics
⭐   and traces and it costs almost nothing once OTel is wired.
```

# Part 6 — ⭐ Reading a trace

```
⭐⭐ THE FOUR SHAPES, AND WHAT EACH MEANS INSTANTLY:
⭐   ① ⭐⭐ ***ONE LONG SPAN WITH NOTHING INSIDE*** ⇒ time spent
⭐      in code you have not instrumented. ⭐ Either add spans,
⭐      or it is genuinely CPU-bound.
⭐   ② ⭐⭐ ***A STAIRCASE OF IDENTICAL SHORT SPANS*** ⇒
⭐      ***N+1***. ⭐ Forty queries of 3 ms each. ⭐⭐ THE MOST
⭐      RECOGNISABLE AND MOST COMMON PATTERN IN ANY TRACE
⭐      VIEWER, AND ONE GLANCE IDENTIFIES IT (Day 197).
⭐   ③ ⭐⭐ ***A GAP BETWEEN A PARENT'S START AND ITS FIRST
⭐      CHILD*** ⇒ ⭐ queueing, lock waiting, connection-pool
⭐      waiting, ⭐⭐ OR CFS THROTTLING (Day 361) — ⭐ all of which
⭐      are invisible as spans and visible as empty space.
⭐   ④ ⭐ ***PARALLEL SPANS THAT SHOULD BE PARALLEL AND ARE
⭐      NOT*** ⇒ ⭐ awaited sequentially where `asyncio.gather`
⭐      would do.

⭐⭐ AND THE HABIT WORTH BUILDING:
⭐   ⭐ ⭐⭐ COMPARE A FAST TRACE AND A SLOW TRACE OF THE ***SAME
⭐     ENDPOINT*** SIDE BY SIDE. ⭐ The difference is the answer,
⭐     ⭐ and it is far faster than reading either one alone.
⭐   ⭐ ⭐⭐ AND FILTER BY ATTRIBUTE, NOT BY ENDPOINT: "SLOW
⭐     TRACES FOR TENANT X" IS THE QUERY THAT SOLVES REAL
⭐     INCIDENTS, ⭐ and it only works because you added business
⭐     attributes in Part 2.
```

# Part 7 — ⭐ Cost, overhead and the honest limits

```
⭐⭐ OVERHEAD, MEASURED:
⭐   ⭐ ⭐⭐ 1–3% CPU FOR TYPICAL AUTO-INSTRUMENTATION. ⭐ Real,
⭐     small, and worth it.
⭐   ⭐ ⭐⭐ AND THE ONE THAT IS NOT SMALL: A SPAN PER ROW IN A
⭐     LOOP. ⭐ Span creation is not free; forty thousand of them
⭐     is a measurable share of a request.
⭐   ⭐ ⭐⭐ ALWAYS USE THE ***BATCH*** SPAN PROCESSOR IN
⭐     PRODUCTION. ⭐ The simple processor exports synchronously,
⭐     ⭐⭐ SO YOUR REQUEST LATENCY NOW INCLUDES A NETWORK CALL
⭐     TO YOUR OBSERVABILITY VENDOR — which is Day 375's
⭐     "never let telemetry block the request" rule, in a
⭐     different costume.
⭐   ⭐ ⭐⭐ AND THE EXPORT PATH MUST FAIL OPEN: if the collector
⭐     is unreachable, spans are dropped and the application
⭐     continues. ⭐ Verify this rather than assuming it.

⭐⭐ COST:
⭐   ⭐ Vendors bill per span or per gigabyte ⇒ ⭐⭐ SPANS PER
⭐     REQUEST IS A NUMBER YOU SHOULD KNOW. ⭐ Twenty is
⭐     reasonable; two hundred means you are instrumenting a
⭐     loop.
⭐   ⭐ Tail sampling in the collector is the main lever, ⭐ and
⭐     it is applied ***before*** you pay.

⭐⭐ AND WHAT TRACING DOES ***NOT*** SOLVE — ⭐ say this
⭐   unprompted:
⭐   ⭐ ⭐⭐ IT DOES NOT REPLACE METRICS. ⭐ Sampled data cannot
⭐     give you an accurate rate or percentile.
⭐   ⭐ ⭐⭐ IT DOES NOT REPLACE LOGS. ⭐ A span tells you a
⭐     function took 800 ms; ⭐ a log tells you which branch it
⭐     took and why.
⭐   ⭐ ⭐⭐ IT DOES NOT WORK AT ALL WITHOUT PROPAGATION, ⭐ and
⭐     propagation breaks silently — ⭐⭐ WHICH IS WHY PART 3'S
⭐     TEST BELONGS IN CI, NOT IN A WIKI.
⭐   ⇒ ⭐ The progression stands (Day 338): ⭐⭐ ***METRIC ALERTS
⭐     → TRACE LOCATES → LOG EXPLAINS.***
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ No context propagation through the queue | The two halves of one operation can never be joined |
| ⭐⭐ Forgetting `traceparent` on the outbox row | The relay publishes with no context — broken where nobody thinks to look |
| ⭐ A child span starting an hour after its parent | A one-hour trace that means nothing. Use a span link |
| ⭐⭐ `executor.submit` without copying context | The span appears as an orphan root and its time vanishes from the parent |
| ⭐ Background tasks as children of a completed request | The parent span is already closed |
| ⭐⭐ A gateway stripping `traceparent` | Every trace starts at your service and the client half is invisible |
| ⭐ Not setting span status on exceptions | A failed span looks identical to a successful one; error filters return nothing |
| ⭐⭐ Secrets or bodies in span attributes | Spans go to a vendor. Check what `db.statement` captures |
| ⭐ A span per loop iteration | 40,000 spans is unreadable, measurably slow, and may be dropped |
| ⭐⭐ Head sampling at 1% | You keep 1% of the errors — the only traces you wanted |
| ⭐⭐ Inconsistent sampling across services | A partial trace lies about where the time went |
| ⭐ Not recording the sample rate | Counts derived from traces are wrong by an unknown factor |
| ⭐ Deriving SLOs from sampled traces | Use metrics for rates and percentiles; traces explain them |
| ⭐⭐ Simple span processor in production | Export becomes synchronous, so request latency includes a call to your vendor |
| ⭐ Not measuring queue time separately in workers | "Took four minutes" is ambiguous between slow and queued |
| ⭐ Auto-instrumentation only | You learn a query was slow, never for whom |

## Interview questions

**1. "What does tracing give you that metrics don't?"**
> ⭐ Metrics say *that* something is wrong; ⭐⭐ **traces say *where* the time went, across process
> boundaries** — and they carry high cardinality, which metrics can't afford. ⭐ The progression is
> metric alerts, trace locates, log explains, ⭐⭐ and **a team that skips traces jumps from "something's
> wrong" straight to grepping, which is most of their MTTR.**

**2. "Where does propagation break?"**
> ⭐⭐ Always the same places. **The queue** — publish ends the trace, consume starts a new root, and the
> two halves can never be joined. ⭐⭐ **And within that, the outbox row: if the message is written to a
> table first, `traceparent` has to be a column, or the relay publishes with no context.** ⭐ Then thread
> pools, because context lives in `contextvars` and a raw `executor.submit` doesn't carry it — the span
> becomes an orphan and its time vanishes from the parent. ⭐ Then background tasks, subprocesses, and a
> gateway that strips unknown headers. ⭐⭐ **The test is to trigger one operation crossing every
> boundary and confirm it's one trace — in CI, because propagation regresses silently.**

**3. "Head or tail sampling?"**
> ⭐⭐ Tail. Head sampling at one percent keeps **one percent of the errors, which are the only traces
> you wanted.** ⭐ Tail buffers the trace in the collector and decides after completion, so you keep all
> errors and slow traces and a fraction of a percent of fast successes. ⭐⭐ The operational detail people
> miss: **all spans of a trace must reach the same collector instance**, so you load-balance by
> trace id. ⭐ And regardless: consistent decisions across services, because a partial trace lies about
> where the time went, and record the sample rate or your counts are wrong by an unknown factor.

**4. "How do you make auto-instrumentation useful?"**
> ⭐ Auto-instrumentation gives the skeleton and tells you a query took 800 ms. ⭐⭐ **Your own attributes
> tell you it was slow for enterprise tenants with more than ten thousand orders** — tenant id, plan,
> result count, cache hit, retry count, flag state. ⭐ That's what makes "slow traces for tenant X" a
> query that solves an incident. ⭐ Plus setting span status on exceptions, or failed spans look
> identical to successful ones.

**5. "What does a trace look like when there's an N+1?"**
> ⭐⭐ **A staircase of identical short spans** — forty queries of three milliseconds each — and it's the
> most recognisable pattern in any trace viewer; one glance identifies it. ⭐ The other three shapes
> worth knowing: one long span with nothing inside means uninstrumented or genuinely CPU-bound work;
> ⭐⭐ **a gap between a parent's start and its first child means queueing, lock waiting, pool waiting or
> CFS throttling — all invisible as spans and visible as empty space**; and sequential spans that could
> have been gathered.

**6. "What does tracing cost, and what doesn't it solve?"**
> ⭐ One to three percent CPU for auto-instrumentation, which is worth it — ⭐⭐ **and you must use the
> batch span processor, because the simple one exports synchronously and your request latency then
> includes a network call to your observability vendor.** ⭐ Cost is per span, so spans-per-request is a
> number to know: twenty is reasonable, two hundred means you're instrumenting a loop. ⭐⭐ And it
> doesn't replace metrics — **sampled data can't give an accurate rate or percentile** — or logs, which
> tell you which branch was taken and why.

## 🎙️ Articulation drill

**Two minutes.** Say what a trace is for and what it depends on: **it answers "where did the time go?"
across process boundaries, and the whole value rests on context propagating unbroken through every
hop.** Then go straight to where that breaks, because it's always the same places: **the queue — publish
ends the trace, consume starts a new root — and within that, the outbox row, where `traceparent` has to
be a column or the relay publishes with no context, which breaks it somewhere nobody thinks to look.**
Then thread pools, since context lives in contextvars and a raw executor submit doesn't carry it, **so
the span becomes an orphan and its time simply vanishes from the parent.** Give the test: **trigger one
operation crossing every boundary and assert it's one trace — in CI, because propagation regresses
silently and nothing fails.** On value: auto-instrumentation is a good first hour and tells you a query
took eight hundred milliseconds; **your own attributes tell you it was slow for enterprise tenants with
more than ten thousand orders**, which is the difference between a trace you look at and one that
answers something. On sampling: **tail, not head, because one percent head sampling keeps one percent
of the errors** — with the operational catch that all spans must reach the same collector, so you
balance by trace id. Close on the shapes you read instantly — **a staircase of identical short spans is
an N+1, and a gap before the first child is queueing, lock waiting or CFS throttling** — and on the
honest limit: traces don't replace metrics or logs, they sit between them.
