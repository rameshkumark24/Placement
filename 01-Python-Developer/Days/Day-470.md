# Day 470 📂

**P-470** · 📂 **The code walk** — ⭐⭐ ninety seconds decide whether they read further

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: nobody reads your repository — they sample it, in about ninety seconds, in
> a predictable order, and everything they conclude about your engineering comes from that sample, so

# Part 1 — ⭐⭐ The ninety-second sample

```
⭐ ***WHAT A REVIEWER ACTUALLY DOES, IN ORDER:***
⭐   ⭐ ① ⭐⭐ THE README — first screen only. ⭐ 20 seconds.
⭐     ⭐ Decides whether there is a second minute.
⭐   ⭐ ② ***THE FILE TREE*** — 10 seconds. ⭐⭐ THEY ARE READING
⭐     YOUR ***MODEL OF THE PROBLEM***, ⭐ not your folder names.
⭐     ⭐ A flat directory of 40 files says you never had one.
⭐   ⭐ ③ ⭐⭐ ONE FILE THEY EXPECT TO BE MESSY ⭐ — the core
⭐     abstraction, or whatever the README bragged about.
⭐   ⭐ ④ ***THE TESTS*** — ⭐⭐ DO THEY EXIST, AND ARE THEY REAL?
⭐     ⭐ 20 seconds, and it is the highest-information 20 seconds
⭐     in the whole sample.
⭐   ⭐ ⑤ ***`git log --oneline`*** — ⭐⭐ 40 COMMITS SAYING
⭐     "UPDATE" IS A SIGNAL AND SO IS A SINGLE "INITIAL COMMIT"
⭐     CONTAINING 8,000 LINES.

⭐ ⭐⭐ THREE CONSEQUENCES WORTH ACTING ON:
⭐   ⭐ ⭐⭐ THE FIRST SCREEN OF THE README IS THE MOST VALUABLE
⭐     REAL ESTATE YOU OWN. ⭐ Not the middle. The first screen.
⭐   ⭐ ⭐⭐ MAKE ***THREE*** FILES BEAUTIFUL, NOT THIRTY. ⭐ You
⭐     cannot polish a whole repo and you do not need to.
⭐   ⭐ ⭐⭐ COMMIT HISTORY IS PART OF THE ARTEFACT ⭐ and almost
⭐     nobody treats it that way.
```

# Part 3 — ⭐⭐ The three files worth making beautiful

```
⭐ ***PICK THREE. POLISH THEM PROPERLY. LEAVE THE REST HONEST.***

⭐ ① ⭐⭐ ***THE CORE ABSTRACTION*** — ⭐ your `Retriever`, your
⭐   `LLMClient`, your `Tool` protocol.
⭐   ⭐ ⭐⭐ TYPED, SMALL, WITH THE INVARIANTS VISIBLE IN THE
⭐     SIGNATURE: ⭐ `tenant_id` required and keyword-only,
⭐     `idempotency_key` mandatory on mutating tools.
⭐   ⭐ ⭐⭐ A REVIEWER READING ONE SIGNATURE AND SEEING THAT A
⭐     PERMISSION LEAK WOULD BE A ***TYPE ERROR*** LEARNS MORE
⭐     ABOUT YOU THAN FROM ANY PARAGRAPH YOU COULD WRITE.

⭐ ② ***THE EVAL HARNESS*** — ⭐ because it is what most
⭐   candidates do not have at all. ⭐ Readable metrics, the gold
⭐   set format documented, ⭐⭐ AND THE GATE VISIBLE IN CI.

⭐ ③ ⭐⭐ ***THE TEST THAT PROVES THE SECURITY INVARIANT*** — ⭐ the
⭐   cross-tenant canary. ⭐ Short, obvious, and devastating in a
⭐   code walk:
```

```python
CANARY = "ZZQX-CANARY-7741"

@pytest.mark.parametrize("question", EVAL_QUESTIONS)
async def test_no_cross_tenant_leak(question, retriever):
    hits = await retriever.retrieve(question, tenant_id=TENANT_A)
    for h in hits:
        assert CANARY not in h.body
        assert h.tenant_id == TENANT_A          # ⭐⭐ BELT AND BRACES

async def test_tenant_is_not_optional(retriever):
    with pytest.raises(TypeError):
        await retriever.retrieve("anything")    # ⭐ no tenant_id
```

```
⭐ ⭐⭐ THAT SECOND TEST IS FOUR LINES AND IT SAYS: ⭐ "I made the
⭐   dangerous thing structurally impossible rather than
⭐   remembering not to do it." ⭐⭐ THAT IS A SENIOR SENTENCE
⭐   WRITTEN IN CODE.
```

# Part 4 — What a reviewer is actually reading for

```
⭐ ***THEY ARE NOT CHECKING CORRECTNESS.*** ⭐ They are answering
⭐   five questions about ***you***:

⭐ ① ⭐⭐ ***DO THEY KNOW WHAT THE HARD PART WAS?*** ⭐ Read from
⭐   where the care went. ⭐ Beautiful CRUD and a scary
⭐   500-line retrieval function says you did not know.

⭐ ② ***DO THEY WRITE TESTS FOR THINGS THAT ARE HARD TO TEST?***
⭐   ⭐ Anyone tests a pure function. ⭐⭐ TESTING A
⭐     NON-DETERMINISTIC SYSTEM IS A SKILL, ⭐ and an eval harness
⭐     plus a leak canary demonstrates it instantly.

⭐ ③ ⭐⭐ ***ARE THE ABSTRACTIONS AT THE RIGHT ALTITUDE?*** ⭐ Both
⭐   directions fail: ⭐ a `BaseAbstractRetrieverFactory` over one
⭐   implementation, ⭐⭐ AND A 400-LINE FUNCTION DOING PARSING,
⭐   EMBEDDING, SEARCH AND FORMATTING.

⭐ ④ ***DO ERRORS GET HANDLED OR SWALLOWED?***
⭐   ⭐ ⭐⭐ `except Exception: pass` IS THE SINGLE MOST DAMAGING
⭐     LINE YOU CAN LEAVE IN A REPOSITORY. ⭐ Grep for it today.
⭐   ⭐ Also: bare `except`, ⭐⭐ AND `try/except` AROUND FIFTY
⭐     LINES SO NOBODY CAN TELL WHAT WAS EXPECTED TO FAIL.

⭐ ⑤ ⭐⭐ ***COULD SOMEONE ELSE RUN THIS?*** ⭐ Pinned dependencies,
⭐   `.env.example`, a seed script, a Makefile.
⭐   ⭐ ⭐⭐ A PROJECT ONLY YOU CAN RUN IS A PROJECT THAT WAS NEVER
⭐     REVIEWED BY ANYONE.

⭐ ***THE PYTHON-SPECIFIC TELLS A REVIEWER NOTICES IMMEDIATELY:***
⭐   ⭐ ⭐⭐ MUTABLE DEFAULT ARGUMENTS ⭐ · missing type hints on
⭐     public functions · ⭐⭐ `requests` INSIDE AN `async def`
⭐     (D453) ⭐ · secrets in the repo · a 200-line `utils.py` ·
⭐     ⭐⭐ NO `pyproject.toml`, OR A `requirements.txt` WITH NO
⭐     VERSIONS ⭐ · f-strings in SQL.
```

# Part 5 — Walking someone through it live

```
⭐ ***THE FORMAT:*** ⭐ they share your screen or you share
⭐   yours. ⭐ Fifteen to twenty minutes. ⭐⭐ YOU DRIVE.

⭐ ***THE SEQUENCE:***
⭐   ⭐ ① ⭐⭐ START AT THE ***INTERFACE***, NOT AT `main.py`. ⭐ "This
⭐     is the retriever's public surface — one method, and the
⭐     tenant is required and keyword-only, which is deliberate."
⭐   ⭐ ② ***follow one request end to end.*** ⭐ Rewrite → embed →
⭐     hybrid search → rerank → budget → order. ⭐⭐ ONE PATH,
⭐     NARRATED, BEATS A TOUR OF EVERY MODULE.
⭐   ⭐ ③ ⭐⭐ STOP AT THE ONE PLACE THAT IS INTERESTING ⭐ and go
⭐     deep for three minutes. ⭐ The RRF fusion, or the
⭐     three-state step record.
⭐   ⭐ ④ ***show a test that proves something non-obvious.***
⭐   ⭐ ⑤ ⭐⭐ VOLUNTEER THE UGLIEST PART BEFORE THEY FIND IT.

⭐ ⭐⭐ ⑤ IS THE MOVE. ⭐ "This module is the worst thing here —
⭐   it grew organically and I'd split it into parse/normalise/
⭐   validate. ⭐⭐ IT'S ON MY LIST AND IT HASN'T HURT ME YET,
⭐   WHICH IS WHY IT'S STILL LIKE THAT."
⭐   ⭐ ⭐⭐ THAT SENTENCE DOES THREE THINGS AT ONCE: ⭐ proves you
⭐     can assess your own code, removes their gotcha, and
⭐     demonstrates prioritisation. ⭐⭐ IT IS THE HIGHEST-RETURN
⭐     THIRTY SECONDS IN A CODE WALK.

⭐ ***AND WHAT NOT TO DO:*** ⭐ do not apologise repeatedly, do
⭐   not narrate every import, ⭐⭐ AND DO NOT SAY "THIS IS JUST A
⭐   PERSONAL PROJECT" MORE THAN ONCE. ⭐ Say it once at the start
⭐   (Day 467) and then behave as though it matters — ⭐⭐ BECAUSE
⭐   THE WAY YOU TALK ABOUT IT IS ALSO EVIDENCE.
```

# 💬 Interview

**1. "Walk me through your codebase."**

⭐ I'd start at the interface rather than at `main.py`, because the interface is where the design
decisions are visible. ⭐⭐ "This is the retriever's public surface — one method, and `tenant_id` is
required and keyword-only, so forgetting it is a type error rather than a code-review miss." ⭐ Then I'd
follow one request end to end — rewrite, embed, hybrid search, rerank, budget, ordering — because one
narrated path teaches more than a tour of every module. ⭐⭐ Then stop at the one genuinely interesting
place and go deep for three minutes. ⭐ And I'd volunteer the ugliest part before they find it.

**2. "What's the worst code in your project?"**

⭐ The ingestion module. ⭐⭐ It grew organically as I added file types and it's now doing parsing,
normalisation and validation in one place with an unclear boundary between them. ⭐ I'd split it three
ways, and I know exactly how. ⭐⭐ The honest reason it's still like that is that it hasn't hurt me yet —
it's stable, it's covered by tests at the boundary, and everything above it on my list moves a number.
⭐ If I were adding a fifth file type I'd do the split first.

**3. "What do you look for when reviewing someone else's project?"**

⭐ Five things, and none of them is correctness. ⭐⭐ Whether they know what the hard part was — you can
read that from where the care went, and beautiful CRUD next to a scary five-hundred-line retrieval
function tells you they didn't. ⭐ Whether they test things that are hard to test, because anyone can
test a pure function. ⭐ Whether the abstractions are at the right altitude — a factory over one
implementation fails as badly as a four-hundred-line function. ⭐⭐ Whether errors are handled or
swallowed, and `except Exception: pass` is the single most damaging line you can leave in a repo.
⭐ And whether anyone else could run it.

**4. "Your README has a 'what this doesn't do' section. Why?"**

⭐ Because it's what makes the rest of the README believable. ⭐⭐ Nobody trusts a project with no
limits — a page of claims with no boundaries reads as either inexperience or marketing. ⭐ So it says
nine percent of questions have no correct chunk retrieved and those are multi-hop, aggregations route to
SQL, ACL changes take up to thirty seconds to propagate, and it hasn't been load-tested above fifty
requests per second. ⭐⭐ Every one of those is something a reviewer would otherwise have to find, and
finding it themselves costs me far more than telling them does.

**5. "What's in your repo that most projects don't have?"**

⭐ Three things. ⭐⭐ A numbers table on the first screen of the README — recall, abstention, cost p50 and
p99, rebuild time — which almost no comparable project has. ⭐ An eval harness, which is the thing that
separates a system from a demo. ⭐⭐ And a four-line test asserting that constructing a retriever without
a tenant raises a `TypeError`. ⭐ That last one is tiny and it says the thing I most want said: I made
the dangerous case structurally impossible rather than remembering not to do it.

**6. "How much of this would you rewrite?"**

⭐ Not much, and I'd be specific about what and why rather than saying "all of it", which is a reflex
that reads as either false modesty or lack of judgement. ⭐⭐ The ingestion split I mentioned. The
retrieval service I'd keep as-is — it's about two hundred lines behind one protocol and it's been stable
through two storage changes, which is the actual test of an abstraction. ⭐ And I'd build the eval
harness on day one next time instead of week three. ⭐⭐ That's not a rewrite so much as a reordering,
and it's the change that would have saved the most time.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: walk someone through your repository.**

Start at the interface, and say why it looks like that. **"I'll start at the retriever's public surface
rather than at main, because that's where the decisions are. One method, and `tenant_id` is required and
keyword-only — no default, no optional, no filters dict. That's deliberate: it means forgetting the
tenant is a type error rather than something code review has to catch. The same shape appears on
mutating tools, where the idempotency key is required."**

Then follow one request, not every module. **"Let me follow a single question through. It gets rewritten
if it's multi-turn, embedded through a function that enforces the query prefix — there are two functions,
`embed_query` and `embed_passages`, and never one with a boolean, because getting that flag wrong costs a
full reindex. Then hybrid search, where the tenant predicate is inside the SQL rather than applied
afterwards. Then reranking with an absolute floor, so this can return nothing. Then the token budget,
enforced rather than assumed. Then ordering — best first, second-best last, because of
lost-in-the-middle."**

Then go deep on one thing and show a test. **"The piece I'd point at is the fusion. We use reciprocal
rank fusion rather than adding scores, because cosine sits in a narrow band while BM25 is unbounded and
its distribution shifts per query — so there's no normalisation that makes them comparable. And here's
the test I'd most want you to see: four lines asserting that constructing a retriever without a tenant
raises a TypeError. That's the whole philosophy in four lines — make the dangerous case impossible rather
than remembering not to do it."**

Close by handing them the flaw. **"The worst code here is the ingestion module. It grew as I added file
types and it's doing parsing, normalisation and validation with no clear boundary. I'd split it three
ways and I know how. The honest reason it hasn't happened is that it's stable and covered at the
boundary, and everything above it on my list moves a number. If I were adding a fifth file type, I'd do
the split first."**
