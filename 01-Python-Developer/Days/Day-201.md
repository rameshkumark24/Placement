# Part 1 — ⭐ Physical replication, in one diagram

```
⭐   PRIMARY                                    STANDBY
⭐   ┌──────────────────┐                    ┌──────────────────┐
⭐   │ COMMIT           │                    │ walreceiver      │
⭐   │  → WAL record    │──── TCP stream ───▶│  → write WAL     │
⭐   │  → fsync         │      (walsender)   │  → REPLAY        │
⭐   │  → return ✅     │                    │ ⭐ read-only      │
⭐   └──────────────────┘                    └──────────────────┘
⭐        ⭐⭐ THREE DELAYS, AND THEY ARE DIFFERENT THINGS:
⭐          write lag  — has the standby RECEIVED it?
⭐          flush lag  — has it written it to DISK?
⭐          ⭐⭐ replay lag — has it APPLIED it so a QUERY CAN SEE IT?
⭐        ⇒ ⭐⭐ REPLAY LAG IS THE ONE YOUR USERS FEEL, AND IT IS THE ONE
⭐          PEOPLE FORGET TO GRAPH.
```

```sql
-- ⭐ On the primary — the monitoring query worth memorising:
SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(sent_lsn,   write_lsn)  AS write_lag_b,
       pg_wal_lsn_diff(write_lsn,  flush_lsn)  AS flush_lag_b,
       pg_wal_lsn_diff(flush_lsn,  replay_lsn) AS replay_lag_b,
       write_lag, flush_lag, replay_lag        -- ⭐ as intervals
FROM pg_stat_replication;

-- ⭐ On the standby — "how stale am I, in seconds?"
SELECT now() - pg_last_xact_replay_timestamp() AS replication_delay;
-- ⭐⭐ CAREFUL: on an IDLE primary this grows forever and looks like an
--    outage. ⭐ Combine it with `pg_is_wal_replay_paused()` and a
--    heartbeat write on the primary, or you will page yourself at 3 a.m.
--    over a quiet Sunday.
```

```
⭐⭐ REPLICATION SLOTS — and the warning from Day 194, now in context:
⭐   ⭐ A slot makes the primary RETAIN WAL until the standby confirms
⭐     it. ⭐ Without one, a standby that falls behind past
⭐     `wal_keep_size` is broken permanently and must be rebuilt.
⭐   ⭐⭐ WITH ONE, A STANDBY THAT IS *GONE* MAKES THE PRIMARY RETAIN
⭐     WAL ***FOREVER*** — until the disk fills and the primary stops.
⭐   ⇒ ⭐⭐ SET `max_slot_wal_keep_size`. It is the setting that turns
⭐     "we lose a replica" into a recoverable event instead of a
⭐     primary outage. ⭐ And alert on inactive slots.
```

# Part 2 — ⭐⭐ Synchronous or asynchronous: an RPO decision

```
⭐   `synchronous_commit` — how far must the WAL get before COMMIT
⭐     returns?
⭐   ⭐ off          — not even to the local disk. ⭐ ~200 ms of loss on
⭐                     a crash, no corruption (Day 186).
⭐   ⭐ local        — local fsync only. ⭐⭐ THE STANDBY IS ASYNC.
⭐   ⭐ remote_write — standby RECEIVED it (OS buffer).
⭐   ⭐ on           — standby FLUSHED it to disk. ⭐⭐ ZERO DATA LOSS on
⭐                     a primary failure.
⭐   ⭐ remote_apply — standby has APPLIED it. ⭐⭐ THE ONLY SETTING THAT
⭐                     GIVES READ-YOUR-WRITES FROM A REPLICA — and it
⭐                     adds the full replay time to every commit.

⭐⭐ THE TRADE, IN ONE LINE: ASYNC = FAST COMMITS + AN RPO OF SECONDS.
⭐   SYNC = ZERO RPO + EVERY COMMIT PAYS A NETWORK ROUND TRIP.
⭐   ⭐ Same-AZ sync ≈ +1 ms. ⭐⭐ Cross-region sync ≈ +60 ms ON EVERY
⭐     WRITE. That is a product decision, not an ops one.
```

```
⭐⭐ AND THE TRAP THAT TAKES DOWN THE PRIMARY:
⭐   synchronous_standby_names = 'standby1'
⭐   ⭐⭐ standby1 DIES ⇒ ***EVERY COMMIT ON THE PRIMARY HANGS***,
⭐     waiting for an acknowledgement that will never come. ⭐⭐ YOU
⭐     ADDED A REPLICA FOR AVAILABILITY AND CREATED A SINGLE POINT OF
⭐     FAILURE.
⭐   ⇒ ⭐⭐ ALWAYS QUORUM: `ANY 1 (standby1, standby2)` — any one of two
⭐     is enough, so either may die. ⭐ `FIRST 1 (s1, s2)` prefers s1
⭐     and falls back.
⭐   ⭐ Per-transaction override is legal and useful: `SET LOCAL
⭐     synchronous_commit = 'on'` for payments, `'local'` for analytics
⭐     events. ⭐⭐ You do not have to buy one RPO for the whole system.
```

# Part 3 — ⭐⭐ The three lag anomalies your application will hit

```
⭐⭐ ① READ-YOUR-WRITES VIOLATION — the one that ships to production.

⭐   POST /articles      → primary   ⭐ committed, id=91
⭐   302 → GET /articles/91 → REPLICA ⭐ 40 ms of replay lag
⭐   ⇒ ⭐⭐ 404 NOT FOUND. ⭐ The user just created it. They refresh and
⭐     it appears. ⭐⭐ It is unreproducible in staging (no lag) and it
⭐     looks like a caching bug.

⭐   ⭐⭐ THE THREE FIXES, RANKED:
⭐   ⓐ ⭐⭐ ROUTE BY INTENT, NOT BY LOAD. Anything in a user's own
⭐      session that follows a write goes to the primary. ⭐ Simplest,
⭐      and the one to build first: a "sticky to primary for N seconds
⭐      after a write" flag in the session.
⭐   ⓑ ⭐⭐ LSN TOKENS — the correct version. After a write, capture
⭐      `pg_current_wal_insert_lsn()`. Send it with the read; on the
⭐      replica, check `pg_last_wal_replay_lsn() >= token` and fall back
⭐      to the primary if not. ⭐ Precise, no guessing, needs plumbing.
⭐   ⓒ ⭐ `remote_apply` — correct, and it taxes every write everywhere.

⭐⭐ ② MONOTONIC READS VIOLATION — two replicas, different lag.
⭐   Read 1 hits replica A (fresh): balance £900.
⭐   Read 2 hits replica B (behind): ⭐⭐ balance £1000. TIME WENT
⭐   BACKWARDS.
⭐   ⇒ ⭐ Fix: pin a session to ONE replica for its duration.

⭐⭐ ③ CAUSAL / CROSS-ENTITY VIOLATION — the subtle one.
⭐   The comment is replicated; the post it belongs to is not yet.
⭐   ⭐⭐ A JOIN ON THE REPLICA RETURNS A COMMENT WITH NO PARENT — and
⭐     your code raises a `NoneType` error on a foreign key that is
⭐     enforced and valid. ⭐ (Within one Postgres standby, replay is
⭐     ordered, so this is really a LOGICAL-replication and
⭐     multi-datastore hazard — ⭐⭐ which is exactly Day 199's search
⭐     index and Day 143's cache.)
```

```
⭐⭐ AND THE HONEST ADVICE MOST TEAMS NEED FIRST:
⭐   ⭐⭐ DO NOT ADD READ REPLICAS TO FIX SLOW QUERIES. A replica has the
⭐     same schema, same indexes, same plans, and the same N+1. ⭐ You
⭐     will move the load and keep the latency, and you will have bought
⭐     an eventual-consistency bug for it.
⭐   ⭐ Replicas are RIGHT for: HA/failover, genuinely read-heavy
⭐     workloads you have already optimised, and ⭐⭐ ISOLATING
⭐     ANALYTICS FROM OLTP (Day 193's monthly export) — which is the
⭐     single best use, because it needs neither freshness nor low
⭐     latency.
```

# Part 4 — ⭐ Query conflicts, and the setting that moves the problem

```
⭐⭐ ON A HOT STANDBY, REPLAY AND QUERIES FIGHT.
⭐   The primary vacuums away a row version. The standby must replay
⭐   that. ⭐ But a long query on the standby is still reading it.
⭐   ⇒ ⭐⭐ `ERROR: canceling statement due to conflict with recovery`
⭐     ⭐ Your analytics query dies at minute nine of ten. Repeatedly.

⭐⭐ TWO DIALS, AND THEY MOVE THE PAIN RATHER THAN REMOVING IT:
⭐   ⭐ `max_standby_streaming_delay = 30s` — let replay fall behind up
⭐     to 30 s to protect queries. ⭐⭐ COST: THE STANDBY IS NOW UP TO
⭐     30 s STALE, and in a failover that is your RPO.
⭐   ⭐⭐ `hot_standby_feedback = on` — the standby tells the PRIMARY
⭐     what it still needs, so the primary does not vacuum it away.
⭐     ⭐⭐ COST: ***IT PINS THE PRIMARY'S xmin HORIZON*** (Day 194).
⭐     A long query on your reporting replica now causes BLOAT ON YOUR
⭐     PRODUCTION PRIMARY. ⭐ People enable this to fix cancellations
⭐     and cause a much worse problem three weeks later.
⭐   ⇒ ⭐⭐ THE REAL FIX IS A DEDICATED REPORTING REPLICA with generous
⭐     delay AND feedback OFF, so its problems stay its own.
```

# Part 5 — ⭐ Logical replication, and what it is actually for

```sql
-- ⭐ PRIMARY:  CREATE PUBLICATION pub FOR TABLE orders, order_items;
-- ⭐ TARGET :  CREATE SUBSCRIPTION sub CONNECTION '…' PUBLICATION pub;
```

```
⭐⭐ PHYSICAL replicates BYTES — whole cluster, identical, same version.
⭐⭐ LOGICAL replicates ROW CHANGES — selected tables, across versions,
⭐   into a DIFFERENT SCHEMA, and the target is WRITABLE.

⭐ ⭐⭐ THE FOUR THINGS IT IS ACTUALLY FOR:
⭐   ① ⭐⭐ MAJOR-VERSION UPGRADES WITH SECONDS OF DOWNTIME. Replicate
⭐      15 → 17, verify, switch. ⭐ The main reason to learn it.
⭐   ② Replicating a subset to a reporting or regional database.
⭐   ③ ⭐⭐ CDC — feeding a search index, a cache, a warehouse, or an
⭐      event bus. ⭐⭐ THIS IS DAY 199's ELASTICSEARCH SYNC AND DAY
⭐      142's DUAL-WRITE PROBLEM, SOLVED PROPERLY: the WAL is already
⭐      the transaction log, so reading it cannot diverge from the
⭐      database. Debezium does exactly this.
⭐   ④ Consolidating many databases into one.

⭐ ⭐⭐ THE FIVE LIMITS THAT BITE:
⭐   ⭐ DDL IS NOT REPLICATED. Add a column on the source and the
⭐     subscription breaks. ⭐⭐ You now run every migration twice, in
⭐     the right order.
⭐   ⭐ SEQUENCES are not replicated — ⭐⭐ after a switchover your ids
⭐     restart. A real, embarrassing outage.
⭐   ⭐ Tables need a PRIMARY KEY or `REPLICA IDENTITY FULL` (which
⭐     logs the whole old row into WAL — expensive).
⭐   ⭐ TRUNCATE, large objects, and (before PG 16) no cascading.
⭐   ⭐⭐ Initial sync of a huge table is a `COPY` that holds a slot open
⭐     — ⭐ which pins WAL and the xmin horizon while it runs.
```

# Part 6 — ⭐⭐ Failover and PITR: the parts people skip until it matters

```
⭐⭐ FAILOVER IS FOUR PROBLEMS, AND PROMOTION IS THE EASY ONE:
⭐  ① PROMOTE a standby (`pg_ctl promote`). ⭐ Seconds.
⭐  ② ⭐⭐ FENCE THE OLD PRIMARY. If it comes back thinking it is
⭐     primary, ⭐⭐ TWO NODES ACCEPT WRITES = SPLIT BRAIN = DIVERGED
⭐     DATA THAT CANNOT BE MERGED. ⭐ This is why you use Patroni with
⭐     etcd/Consul: a distributed lock decides who is primary, not a
⭐     script's opinion.
⭐  ③ ⭐⭐ TELL THE APPLICATIONS. And this is where Python bites:
⭐     ⭐ DNS TTLs are cached — by the resolver, and ⭐⭐ BY YOUR OWN
⭐       PROCESS, potentially forever.
⭐     ⭐⭐ AND EVERY POOLED CONNECTION IS STILL OPEN TO THE OLD HOST.
⭐       ⇒ ⭐ `pool_pre_ping=True` (Day 197) is what turns a failover
⭐         into a handful of retried requests instead of a dead app.
⭐     ⭐⭐ THE BETTER ANSWER: LIBPQ MULTI-HOST WITH
⭐       `target_session_attrs=read-write` —
⭐       `postgresql://h1,h2/db?target_session_attrs=read-write`
⭐       ⭐⭐ THE DRIVER TRIES EACH HOST AND KEEPS THE ONE THAT IS
⭐       WRITABLE. No DNS, no proxy, no orchestration. ⭐ Supported by
⭐       psycopg3 and asyncpg.
⭐  ④ ⭐ RE-ATTACH THE OLD PRIMARY as a standby — `pg_rewind`, or a
⭐     fresh base backup.
```

```
⭐⭐ PITR = A BASE BACKUP + EVERY WAL SEGMENT SINCE.
⭐   ⭐ `pg_basebackup` or pgBackRest/WAL-G (⭐⭐ use one of the latter:
⭐     parallel, compressed, incremental, and they verify).
⭐   ⭐ `archive_command` ships each segment to object storage.
⭐   ⭐ Restore: put the base back, set `recovery_target_time`, start.
⭐   ⇒ ⭐⭐ THIS IS THE ONLY THING THAT SAVES YOU FROM `DELETE FROM
⭐     users;` AT 14:32. ⭐⭐ A REPLICA DOES NOT — IT REPLICATED THE
⭐     DELETE FAITHFULLY, IN MILLISECONDS. ⭐ Replication is not backup,
⭐     and confusing the two is the most expensive mistake here.

⭐⭐ THE TWO NUMBERS, DEFINED PROPERLY:
⭐   ⭐ RPO — RECOVERY POINT objective: how much DATA may we lose?
⭐        ⭐ async replication ⇒ seconds. ⭐ WAL archive every 60 s ⇒ up
⭐          to 60 s. ⭐ sync standby ⇒ zero.
⭐   ⭐ RTO — RECOVERY TIME objective: how LONG may we be down?
⭐        ⭐⭐ RESTORING 2 TB FROM S3 AND REPLAYING SIX DAYS OF WAL IS
⭐          HOURS. ⭐ If your RTO is 15 minutes, PITR alone cannot meet
⭐          it and you need a standby too. ⭐⭐ THEY ARE DIFFERENT TOOLS
⭐          FOR DIFFERENT FAILURES: a standby for hardware, PITR for
⭐          humans.

⭐⭐ AND THE RULE THAT MATTERS MORE THAN ANY SETTING:
⭐   ⭐⭐ ***A BACKUP YOU HAVE NOT RESTORED IS NOT A BACKUP.***
⭐   ⭐ Restore to a scratch instance monthly. ⭐ Automate it. ⭐⭐ TIME
⭐     IT — that measurement IS your real RTO, and it is always larger
⭐     than the one in the document. ⭐ Then check row counts against
⭐     production, because a restore that starts is not a restore that
⭐     is complete.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Adding read replicas to fix slow queries | Same schema, same plans, same N+1 — you moved load and bought a consistency bug. |
| Graphing only write lag | Replay lag is what users feel. |
| Alerting on `pg_last_xact_replay_timestamp` alone | It grows forever on an idle primary. Add a heartbeat write. |
| A replication slot with no `max_slot_wal_keep_size` | A dead standby fills the primary's disk and stops it. |
| `synchronous_standby_names = 'standby1'` | If it dies, every commit on the primary hangs. Use `ANY 1 (...)`. |
| One RPO for the whole system | `SET LOCAL synchronous_commit` per transaction — sync for payments, local for events. |
| Redirecting to a replica read right after a write | Read-your-writes violation: a 404 on the thing the user just created. |
| Load-balancing reads across replicas within a session | Monotonic reads violation — time appears to go backwards. |
| `hot_standby_feedback = on` to stop query cancellations | It pins the primary's xmin horizon and bloats production. |
| Expecting logical replication to carry DDL | It doesn't. Every migration runs twice, in order. |
| Forgetting sequences in a logical switchover | Your ids restart. |
| Treating promotion as the whole of failover | Fencing, client redirection and re-attaching are the hard parts. |
| Relying on DNS for failover in Python | Caches plus already-open pooled connections. Use multi-host with `target_session_attrs`. |
| Treating a replica as a backup | It replicated your `DELETE` faithfully, in milliseconds. |
| Confusing RPO and RTO | Data loss versus downtime — different failures, different tools. |
| Never restoring a backup | Then you don't have one, and your documented RTO is fiction. |

## Interview questions

**Q: You add a read replica and users report items disappearing right after they create them. What's happening?**

> A read-your-writes violation. The write went to the primary, the redirect's read went to a replica
> that's forty milliseconds behind in replay, and the row isn't there yet — so the user gets a 404 for
> something they just created, refreshes, and it appears. It's invisible in staging because there's no
> lag there, and it looks like a caching bug. Three fixes, and I'd build them in this order. Route by
> intent rather than by load: anything in a user's own session following a write goes to the primary,
> usually with a sticky flag for a few seconds. Then, if you need precision, LSN tokens — capture
> `pg_current_wal_insert_lsn()` after the write, pass it with the read, and have the replica compare
> against `pg_last_wal_replay_lsn()` and fall back to the primary if it's behind. And `remote_apply` is
> the third option, correct but it taxes every write in the system to fix one path. I'd also ask why
> the replica was added — if it was to fix slow queries, it won't, because the replica has the same
> schema, indexes and N+1s.

**Q: Synchronous or asynchronous replication?**

> It's an RPO decision, so I'd want the business answer first: how much committed data may we lose?
> Asynchronous gives fast commits and an RPO of seconds; synchronous gives zero data loss and charges
> every commit a network round trip — about a millisecond within an availability zone and around sixty
> across regions, which makes cross-region synchronous a product decision rather than an ops one. The
> trap I'd flag is configuring a single synchronous standby by name: when it dies, every commit on the
> primary hangs waiting for an acknowledgement that will never arrive, so you added a replica for
> availability and created a single point of failure. Quorum syntax — `ANY 1 (s1, s2)` — fixes that.
> And you don't have to buy one RPO for everything: `SET LOCAL synchronous_commit` per transaction lets
> payments be synchronous while analytics events are local.

**Q: Analytics queries on the standby keep getting cancelled. How do you fix it?**

> That's a recovery conflict — the primary vacuumed away row versions the standby's long query is still
> reading, and replay has to win. There are two dials and both move the problem rather than removing
> it. `max_standby_streaming_delay` lets replay fall behind to protect queries, at the cost of the
> standby being that much staler, which becomes your RPO in a failover. `hot_standby_feedback` tells
> the primary not to vacuum what the standby still needs — and that pins the *primary's* xmin horizon,
> so a long report on your reporting replica now causes bloat on production. People enable it to stop
> the cancellations and create a much worse problem three weeks later. The real fix is a dedicated
> reporting replica with a generous delay and feedback off, so its problems stay its own.

**Q: What's the difference between replication and backup?**

> Replication protects against a machine failing; backup protects against a human or an application
> failing. If someone runs `DELETE FROM users` at 14:32, the replica replicated that faithfully in
> milliseconds — you have two copies of the deletion. Point-in-time recovery is what saves you: a base
> backup plus every WAL segment since, restored with `recovery_target_time` set to 14:31. They're
> different tools for different failures and you need both, which is also the cleanest way to explain
> RPO versus RTO. Async replication gives an RPO of seconds and a very fast RTO; PITR gives an RPO of
> however often you archive WAL and an RTO of hours if you're restoring terabytes from object storage
> and replaying days of WAL. So if the RTO target is fifteen minutes, PITR alone can't meet it,
> regardless of how good the backups are.

**Q: A failover happens. What does your Python application do?**

> Ideally, retries a handful of requests and carries on — but only if it was set up for it. Promotion
> is the easy part; the application-side problems are that DNS is cached, potentially inside the
> process for the life of it, and that every pooled connection is still open to the old host. So
> `pool_pre_ping` matters, because it turns "the pool hands out dead connections until it's restarted"
> into "one wasted round trip per checkout". The better answer is libpq multi-host with
> `target_session_attrs=read-write` — list both hosts in the URL and the driver tries each and keeps
> the writable one, with no DNS, no proxy and no orchestration involved. psycopg3 and asyncpg both
> support it. On the infrastructure side, the part I'd be most careful about is fencing: if the old
> primary comes back believing it's still primary, you get two nodes accepting writes and diverged data
> that can't be merged, which is why you want Patroni with a distributed lock deciding who's primary
> rather than a script's opinion.

## 🎙️ Articulation drill

**Two minutes: "How do you make a database highly available?"**

Start from the WAL, because it unifies everything: the same log that makes crash recovery possible is
streamed for replication and archived for point-in-time recovery — one mechanism, four features. Then
the choice that's actually a business question: sync gives zero RPO and charges every commit a round
trip, async gives fast commits and seconds of loss, and you can pick per transaction rather than for
the whole system. Flag the trap that a single named synchronous standby hangs the primary when it
dies. Then move to the part interviewers rarely hear and always value: **replication is not backup**
— a replica replicated your accidental `DELETE` in milliseconds, so you need PITR for human failures
and a standby for hardware ones, and RPO and RTO are different numbers. Then the application half:
**adding a read replica changes your consistency model, and the first bug is a user creating something
and immediately getting a 404** — fixed by routing on intent, not load. Close on the discipline point:
**a backup you haven't restored isn't a backup, and the time it takes to restore is your real RTO,
which is always larger than the one in the document.**
