**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: every list endpoint is an unauthenticated performance contract with the
> world. Whatever `limit`, `sort` and `filter` you accept, someone will send the worst legal
> combination — so the allowlist is not tidiness, it is the boundary of what a client may make your
> database do.**

> production problems.

# Part 1 — ⭐⭐ Cursor pagination, implemented properly

```python
# ⭐ The cursor is the SORT KEY of the last row, plus a tiebreaker.
@dataclass(frozen=True)
class JobCursor:
    scheduled_for: datetime
    id: int

def encode(c: JobCursor) -> str:
    payload = f"{c.scheduled_for.isoformat()}|{c.id}"
    sig = hmac.new(SECRET, payload.encode(), "sha256").digest()[:8]
    return b64url(payload.encode() + b"." + sig)      # ⭐⭐ SIGNED

def decode(raw: str) -> JobCursor:
    body, _, sig = b64url_decode(raw).rpartition(b".")
    if not hmac.compare_digest(sig, hmac.new(SECRET, body, "sha256")
                                        .digest()[:8]):
        raise InvalidCursor()                          # ⭐ 422, not 500
    ts, _, id_ = body.decode().partition("|")
    return JobCursor(datetime.fromisoformat(ts), int(id_))
```

```sql
-- ⭐⭐ THE PREDICATE: A ROW COMPARISON, NOT TWO ANDed CONDITIONS
WHERE (scheduled_for, id) < (:cursor_ts, :cursor_id)
ORDER BY scheduled_for DESC, id DESC
LIMIT :limit + 1                       -- ⭐⭐ +1 gives `has_more` free
```

```
⭐⭐ FIVE THINGS THAT MAKE THIS CORRECT RATHER THAN NEARLY CORRECT:
⭐  ① ⭐⭐ THE TIEBREAKER IS NOT OPTIONAL. Two jobs scheduled at the same
⭐     instant, and without `id` in both the cursor and the `ORDER BY`,
⭐     one row is silently SKIPPED and another REPEATED at every page
⭐     boundary. ⭐ It only shows up with real data, which is why it
⭐     ships.
⭐  ② ⭐⭐ WRITE IT AS A ROW COMPARISON. The hand-expanded version —
⭐     `ts < :ts OR (ts = :ts AND id < :id)` — is correct and Postgres
⭐     plans it worse; the row form maps straight onto the composite
⭐     index.
⭐  ③ ⭐⭐ SIGN THE CURSOR. It is attacker-supplied input that becomes a
⭐     query parameter. ⭐ Signing also means you may change the encoding
⭐     later without accepting old shapes.
⭐  ④ ⭐ `limit + 1` and drop the extra: `has_more` with no second query
⭐     and no `count(*)` (Day 251).
⭐  ⑤ ⭐⭐ THE INDEX MUST MATCH THE `ORDER BY` EXACTLY, INCLUDING
⭐     DIRECTION AND THE TENANT COLUMN FIRST:
⭐     `(tenant_id, scheduled_for DESC, id DESC)` — Day 190's E-S-R.
⭐     ⭐⭐ VERIFY WITH `EXPLAIN`: no `Sort` node, `Rows Removed by
⭐     Filter: 0`.

⭐⭐ AND THE HONEST LIMITATION, STATED IN THE CONTRACT: no "jump to page
⭐   40". ⭐ If a screen genuinely needs it, that screen gets `OFFSET`
⭐   with a hard page cap and a comment saying why — ⭐⭐ rather than
⭐   pretending cursors do something they do not.
```

# Part 2 — ⭐⭐ Filtering and sorting: allowlists, and why

```python
SORTABLE: dict[str, tuple[ColumnElement, str]] = {
    "scheduled_for": (jobs.c.scheduled_for, "ix_jobs_tenant_sched_id"),
    "created_at":    (jobs.c.created_at,    "ix_jobs_tenant_created_id"),
}   # ⭐⭐ EVERY SORTABLE FIELD NAMES ITS INDEX. If you cannot name one,
    #    it is not sortable — that is the rule, and it is enforceable in
    #    a test that checks each named index exists.

FILTERABLE = {
    "status":        (jobs.c.status, JobState),
    "technician_id": (assignments.c.technician_id, int),
    "customer_id":   (jobs.c.customer_id, int),
    "scheduled_from":(jobs.c.scheduled_for, datetime, "ge"),
    "scheduled_to":  (jobs.c.scheduled_for, datetime, "lt"),
}
```

```
⭐⭐ WHY AN ALLOWLIST AND NOT "ANY COLUMN":
⭐   ⭐ A generic filter interface is an interface to your SCHEMA.
⭐     ⭐⭐ Rename a column and you break clients; add a private column
⭐     and you expose it.
⭐   ⭐⭐ AND IT IS A DoS SURFACE (Day 176): a sort on an unindexed
⭐     column is a full scan of a 10M-row table that any client can
⭐     trigger, repeatedly, for free.
⭐   ⭐ `limit` capped at 100, default 25. ⭐⭐ Never unbounded, and
⭐     never "0 means all" — that is an unbounded endpoint wearing a
⭐     disguise.

⭐⭐ THREE MORE LIMITS PEOPLE FORGET:
⭐   ⭐ A CAP ON THE NUMBER OF FILTERS. Twenty `IN` clauses is a query
⭐     you did not design.
⭐   ⭐⭐ A CAP ON `IN` LIST LENGTH. `?technician_id=1,2,…,50000` is a
⭐     50,000-element array in one query. ⭐ Cap at ~100.
⭐   ⭐ A MINIMUM LENGTH ON FREE-TEXT SEARCH (3 chars) — ⭐⭐ plus its
⭐     own rate limit, because search is the most expensive thing on the
⭐     endpoint (Day 199).
```

# Part 3 — ⭐ Search, and keeping it in its lane

```sql
-- ⭐ Day 199, applied: a stored generated tsvector, a GIN index, and
--   `websearch_to_tsquery` — the only parser safe for user input.
ALTER TABLE jobs ADD COLUMN search tsvector GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(reference,'')),'A') ||
    setweight(to_tsvector('english', coalesce(site_address,'')),'B') ||
    setweight(to_tsvector('english', coalesce(notes,'')),'C')
) STORED;
CREATE INDEX ON jobs USING gin (search);
```

```
⭐⭐ THE FOUR RULES FOR THE SEARCH ENDPOINT:
⭐  ① ⭐⭐ NARROW BY TENANT FIRST — always. Ranking scores every match
⭐     (Day 199), so an unscoped search over 10M rows is seconds, and it
⭐     is your most-run query.
⭐  ② ⭐ `websearch_to_tsquery`, never `to_tsquery` — the latter raises a
⭐     syntax error on ordinary text like `c++` and hands your user a 500.
⭐  ③ ⭐ Its own rate limit (20/min) and a minimum query length.
⭐  ④ ⭐⭐ A ZERO-RESULT FALLBACK TO TRIGRAM SIMILARITY as "did you
⭐     mean" — ⭐ cheap, and it closes most of the perceived gap with a
⭐     search engine. ⭐⭐ Do not run it always; run it only on zero.
```

# Part 4 — ⭐⭐ Bulk endpoints, and the case for refusing them

```
⭐   POST /v1/jobs/bulk-cancel  {"job_ids": [1,2,3,…,500]}

⭐⭐ THE PROBLEM IS NOT PERFORMANCE, IT IS ***PARTIAL SUCCESS***.
⭐   Three of five succeed. ⭐ What is the status code? What is the
⭐   body? ⭐⭐ What does the client retry — and how does it retry
⭐   without repeating the two that worked?
⭐   ⭐ `207 Multi-Status` exists and almost no client library handles
⭐     it well; ⭐⭐ people return 200 with a per-item result array,
⭐     which means SUCCESS AND FAILURE NOW SHARE A STATUS CODE and
⭐     every client must remember to inspect the body.

⭐⭐ THE THREE HONEST OPTIONS:
⭐  ① ⭐⭐ ALL-OR-NOTHING IN ONE TRANSACTION. Simple semantics, and it
⭐     is a long transaction and a big lock set (Day 196). ⭐ Cap the
⭐     batch hard (50) and it is fine.
⭐  ② ⭐ PER-ITEM, RETURNING A RESULT ARRAY, with an idempotency key
⭐     PER ITEM so a retry re-does only the failures. ⭐⭐ This is the
⭐     honest version and it is more work than people expect.
⭐  ③ ⭐⭐ REFUSE. Return 202 with a job id, do it asynchronously, and
⭐     expose a status endpoint. ⭐ For anything above a few dozen items
⭐     this is the right answer and it turns a hard API problem into a
⭐     background-work problem you already know how to solve.
⭐ ⇒ ⭐⭐ AND THE DEFAULT ANSWER FOR A PROJECT THIS SIZE: DO NOT SHIP A
⭐   BULK ENDPOINT UNTIL A REAL SCREEN NEEDS ONE. ⭐ Most do not.
```

# Part 5 — ⭐ Concurrency control, rate limits, and the operational surface

```python
# ⭐⭐ ETag / If-Match — optimistic locking as an HTTP feature (Day 251)
@router.patch("/{job_id}")
def update(job_id, body: JobPatch,
           if_match: str = Header(..., alias="If-Match")):  # ⭐⭐ REQUIRED
    ...                                                     #    not optional
# ⭐ The ETag is the row's `version` column, bumped on every write.
# ⭐⭐ A mismatch is 412 PRECONDITION FAILED — which turns a silent lost
#    update (Day 195) into a visible conflict the UI can resolve.
# ⭐ Required rather than optional, because optional means not sent.
```

```
⭐⭐ RATE LIMITS PER ENDPOINT CLASS (Day 208), declared next to the route
⭐   so the limit and the endpoint cannot drift apart:
⭐     auth      5/min   per account AND per IP, ⭐⭐ FAIL CLOSED
⭐     writes   60/min   per user,               ⭐ fail open
⭐     reads   600/min   per user,               ⭐ fail open
⭐     search   20/min   per user,               ⭐ fail open
⭐     uploads  10/min   per user,               ⭐ fail open
⭐   ⭐⭐ AND A PER-TENANT OCCUPANCY CAP ON TOP, or 10,000 users each
⭐     within their limit still take the service down (Day 153).
⭐   ⭐ Every 429 carries `Retry-After`; every 200 carries
⭐     `RateLimit-Remaining` so a good client can self-throttle.
```

```
⭐⭐ THE OPERATIONAL ENDPOINTS — and the security decision about each:
⭐   ⭐ `/health/live` `/health/ready` `/health/startup` — Day 253.
⭐   ⭐⭐ `/metrics` — ⭐⭐ NOT PUBLIC. It leaks tenant names in labels,
⭐      request volumes, error rates and your route table. ⭐ Bind it to
⭐      an internal port or restrict at the network, not with a password.
⭐   ⭐ `/version` — commit sha, build time, ⭐⭐ AND NOTHING ELSE. No
⭐      dependency list, no environment. ⭐ It exists so that "which
⭐      version is live?" is answerable in one second during an incident.
⭐   ⭐⭐ `/admin/*` — the routes that get registered without the normal
⭐      dependency. ⭐ The Day 257 route-table test is what catches them,
⭐      and network restriction is the belt to that braces.
⭐   ⭐ NO `/debug`, no `/docs` in production unless deliberately
⭐      authenticated. ⭐⭐ An open OpenAPI spec is a map of every
⭐      endpoint and every field name for an attacker.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| A cursor with no tiebreaker | Rows are skipped and repeated at page boundaries, only with real data. |
| Hand-expanding the row comparison | Correct but plans worse; the row form maps onto the composite index. |
| An unsigned cursor | Attacker-supplied input flowing into a query, and an encoding you can never change. |
| A `count(*)` for `has_more` | `limit + 1` gives it free. |
| An index that doesn't match `ORDER BY` direction | You get a sort of the whole result set. |
| Pretending cursors support "jump to page 40" | State the limitation; use capped offset where a screen truly needs it. |
| A generic filter over any column | That's an interface to your schema, and a DoS surface. |
| A sortable field with no index | A full scan any client can trigger for free. |
| `limit=0` meaning all | An unbounded endpoint in disguise. |
| No cap on `IN` list length | A fifty-thousand-element array in one query. |
| `to_tsquery` on user input | It raises a syntax error on `c++` and returns a 500. |
| Unscoped search | Ranking scores every match; it's your most-run query and the slowest. |
| Running the trigram fallback always | Run it only on zero results. |
| A bulk endpoint with partial success | Success and failure share a status code and every client must inspect the body. |
| Optional `If-Match` | It won't be sent, and you're back to silent lost updates. |
| A public `/metrics` | It leaks tenant names, volumes, error rates and your route table. |
| `/version` returning dependencies or environment | It exists to answer one question in one second. |
| Public `/docs` in production | A map of every endpoint and field name. |
| No spec-drift check in CI | "Spec first" lasts about three weeks. |

## Interview questions

**Q: How is your pagination implemented?**

> Keyset, with a signed opaque cursor encoding the sort key and a tiebreaker, and a row comparison in
> the predicate: `WHERE (scheduled_for, id) < (:ts, :id)` ordered by the same pair descending. Five
> details make it correct rather than nearly correct. The tiebreaker isn't optional — two jobs at the
> same instant means a row is silently skipped and another repeated at every page boundary, and it only
> manifests with real data, which is why it ships. The row comparison rather than the hand-expanded
> `OR` form, because it maps directly onto the composite index. The cursor is signed, because it's
> attacker-supplied input flowing into a query and because signing lets me change the encoding later.
> `limit + 1` gives `has_more` with no count. And the index has to match the `ORDER BY` exactly
> including direction, with the tenant column first — verified with `EXPLAIN` showing no sort node and
> zero rows removed by filter. The limitation I state in the contract rather than hide: no jump-to-page.

**Q: Why allowlist filters and sorts?**

> Because a generic filter interface is an interface to your schema — rename a column and you break
> clients, add a private one and you expose it — and because it's a denial-of-service surface. A sort
> on an unindexed column is a full scan of a ten-million-row table that any client can trigger
> repeatedly for free. So sortable fields are a map, and my rule is that each entry names the index
> that serves it: if you can't name one, it isn't sortable, and that's testable by asserting each named
> index exists. Alongside that, three caps people forget: a limit on the number of filters, a limit on
> `IN` list length so nobody sends fifty thousand ids, and a minimum length plus a separate rate limit
> on free-text search, because search is the most expensive thing on the endpoint.

**Q: Would you build a bulk endpoint?**

> Reluctantly, and probably not until a real screen needs one. The problem isn't performance, it's
> partial success: three of five succeed, and now you have to answer what status code that is, what the
> body looks like, and — the hard one — how a client retries without repeating the two that worked.
> `207 Multi-Status` exists and few client libraries handle it well, so people return 200 with a
> per-item result array, which means success and failure share a status code and every client has to
> remember to inspect the body. The three honest options are all-or-nothing in one transaction with a
> hard batch cap, per-item results with an idempotency key per item so retries only redo failures, or
> refusing: return 202 with a job id and do it asynchronously. Above a few dozen items the third is
> right, and it converts a hard API design problem into a background-work problem I already know how
> to solve.

**Q: What operational endpoints do you expose, and how are they protected?**

> The three health probes, `/metrics`, and `/version`. The security decision that matters is that
> `/metrics` is not public — it leaks tenant names in labels, request volumes, error rates and
> effectively your entire route table, so it's bound to an internal port or restricted at the network
> rather than behind a password. `/version` returns the commit sha and build time and nothing else,
> because it exists so "which version is live?" is answerable in one second during an incident, and
> listing dependencies or the environment turns it into reconnaissance. `/docs` is off in production
> unless deliberately authenticated, since an open OpenAPI spec is a map of every endpoint and field
> name. And admin routes are exactly the ones registered without the normal dependency, which is why
> the route-table test from the web layer day exists — with network restriction as defence in depth.

**Q: How do you stop the OpenAPI spec drifting from the code?**

> A CI job that exports the spec from the running app and diffs it against the committed one, with
> both normalised through `jq -S`. Without that job, "spec first" lasts about three weeks — someone
> adds a field, the generated spec changes, nobody updates the committed one, and the document quietly
> becomes fiction. With it, changing the API is a deliberate two-file change and a reviewer sees the
> contract diff, which is the point of having written the spec first in the first place. It's also
> what makes generated clients trustworthy, because the contract a frontend generated against is the
> contract CI enforces.
