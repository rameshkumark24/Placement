# Day 118

**L-118** · 🔐 **Authorisation, RBAC, and ⭐⭐ IDOR** — the number-one API vulnerability, and why it is a query-shape problem

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: authentication asks *who are you*, authorisation asks *may you do this to
> this object* — and the second half of that sentence is the one systems forget, which is why "broken
> object-level authorisation" is the most common serious API vulnerability there is.**
>
> ⭐ Days 114–117 established identity. **Today is what identity is allowed to do**, and the central
> fix is not a framework feature — **it is the shape of your queries.**

---

# Part 1 — ⭐⭐ IDOR

```python
# ⚠️⚠️ ⭐⭐ AUTHENTICATED, AND COMPLETELY BROKEN:
@app.route("/orders/{order_id:int}")
def get_order(request, order_id: int, user: User):        # ⭐ user IS authenticated
    return JSONResponse(db.get_order(order_id))            # ⚠️⚠️ WHOSE ORDER?
```

```
⭐⭐ CHANGE 1042 TO 1043 IN THE URL AND YOU ARE READING SOMEONE ELSE'S ORDER.
⭐   ⇒ ⭐⭐ THAT IS **IDOR** — Insecure Direct Object Reference, or in current
⭐        OWASP terms **BROKEN OBJECT-LEVEL AUTHORIZATION**, and it has been
⭐        NUMBER ONE in the OWASP API Top 10 since the list existed.
⭐   ⇒ ⭐ it requires no tools, no skill and no exploit — ⭐⭐ JUST A LOOP OVER
⭐        INTEGERS. Bug-bounty reports are full of it because it is trivial to
⭐        find and often exposes everything.
⭐   ⇒ ⭐⭐ AND NOTICE WHY IT SLIPS THROUGH REVIEW: the endpoint IS authenticated.
⭐        A middleware check passed. The route decorator is there. ⭐ The missing
⭐        check is not about the ROUTE, it is about the OBJECT — and nothing in
⭐        the route's shape suggests anything is absent.
```

```python
# ⭐ FIX 1 — fetch, then check. Correct, and FRAGILE:
order = db.get_order(order_id)
if order is None or order.user_id != user.id:
    raise HTTPError(404, "not found")          # ⭐ 404, not 403 — see Part 2

# ⭐⭐ FIX 2 — SCOPE THE QUERY. Correct, and hard to get wrong:
order = db.get_order(order_id, user_id=user.id)     # ⭐⭐ WHERE id = ? AND user_id = ?
if order is None:
    raise HTTPError(404, "not found")
```

```
⭐⭐ BOTH ARE CORRECT TODAY. THE SECOND IS CORRECT IN A YEAR, AND THAT IS THE
⭐   WHOLE ARGUMENT:
⭐   · ⭐⭐ FIX 1 IS AN EXTRA STEP SOMEONE CAN FORGET — and they will, on the
⭐        fourteenth endpoint, at 6 p.m., copying an existing handler.
⭐   · ⭐⭐ FIX 2 MAKES THE UNSAFE QUERY UNWRITEABLE: if the repository method
⭐        REQUIRES an actor, you cannot express "fetch any order" by accident.
⭐   ⇒ ⭐⭐ THE PRINCIPLE, AND IT GENERALISES FAR BEYOND AUTHORISATION: MAKE THE
⭐        WRONG THING HARD TO WRITE, RATHER THAN RELYING ON EVERY AUTHOR
⭐        REMEMBERING THE RIGHT THING. ⭐ It is Day 089's design pressure and
⭐        Day 062's "types encode what you have already checked".
⭐   ⇒ ⭐ and it composes: a `for_user(user)` repository, or a session-scoped
⭐        filter, or Postgres row-level security, all enforce it at the layer
⭐        where forgetting is impossible (Day 090).
```

⚠️ ⭐ **UUIDs are not an authorisation control.** ⭐⭐ Unguessable ids raise the cost of *discovery* and
change nothing about *access* — the id still leaks through logs, referrers, shared links, and any
other endpoint that returns it. **Use them, and still check ownership.**

# Part 2 — ⭐ Where the check belongs

```
⭐⭐ FOUR PLACES A CHECK CAN LIVE, AND ONLY ONE OF THEM CAN SEE THE OBJECT:
⭐
⭐  1. ⚠️ ⭐⭐ THE UI. Hiding the delete button is UX, NOT SECURITY. The endpoint
⭐       is still there and `curl` does not read your CSS.
⭐  2. ⭐ MIDDLEWARE (Day 108) — good for "is there a valid session", ⭐⭐ USELESS
⭐       for ownership, because it runs before you know which object is involved.
⭐  3. ⭐ THE ROUTE / DECORATOR — good for coarse role checks ("admins only").
⭐  4. ⭐⭐ THE DATA ACCESS — the ONLY layer that can answer "is this object
⭐       yours". ⭐ Which is why Part 1's fix lives in the query.
⭐
⭐ ⇒ ⭐⭐ SO YOU NEED BOTH: coarse checks early (fail fast, cheaply) AND
⭐     object-level scoping at the data layer. ⭐ Neither substitutes for the other,
⭐     and systems that have only the first are the ones in the bug-bounty reports.
```

```
⭐⭐ 403 OR 404 FOR AN OBJECT YOU DO NOT OWN? A REAL DESIGN DECISION:
⭐   · ⭐ 403 is honest: "it exists, you may not have it" ⇒ ⭐⭐ AND CONFIRMS THE
⭐        OBJECT EXISTS, which is an enumeration oracle (Day 114) — an attacker
⭐        can map your id space and learn how many customers you have.
⭐   · ⭐⭐ 404 leaks nothing, and is what I would default to for anything a user
⭐        should not even know about.
⭐   ⇒ ⭐ 403 is right when the user CAN legitimately know the object exists —
⭐        a document shared with their team that they lack edit rights on.
⭐   ⇒ ⭐⭐ THE POINT IS TO DECIDE, PER RESOURCE, RATHER THAN LET THE FRAMEWORK'S
⭐        DEFAULT DECIDE FOR YOU.
```

# Part 3 — ⭐⭐ RBAC, and checking permissions rather than roles

```python
# ⚠️ ⭐⭐ THE VERSION THAT DOES NOT SURVIVE CONTACT WITH A SECOND REQUIREMENT:
if user.role == "admin":
    ...
# ⇒ ⭐ then "support can issue refunds up to £50" arrives, and you get
#    `if user.role in ("admin", "support", "finance", "team_lead")` in nineteen
#    places, ⭐⭐ and adding a role means finding all nineteen.

# ⭐⭐ CHECK A PERMISSION, NOT A ROLE:
if not user.can("orders:refund"):
    raise HTTPError(403, "forbidden")
```

```
⭐⭐ THE MODEL: USERS → ROLES → PERMISSIONS.
⭐        alice ──▶ [support]        ──▶ {orders:read, orders:refund}
⭐        bob   ──▶ [admin, finance] ──▶ {orders:*, users:*, ledger:read}
⭐
⭐   ⇒ ⭐⭐ ROLES ARE FOR ASSIGNING, PERMISSIONS ARE FOR CHECKING. ⭐ Code names
⭐        permissions; administrators manage roles. ⭐⭐ Adding a role then
⭐        changes ZERO lines of code, which is the entire benefit.
⭐   ⇒ ⭐ name permissions `resource:action` so they sort, group and wildcard.
⭐   ⇒ ⭐⭐ AND THE PART PEOPLE SKIP: `user.can()` MUST BE FRESH ENOUGH. If
⭐        permissions live in a JWT (Day 116), a revoked role stays live until
⭐        the token expires — ⭐ so put roles in the token only if you accept
⭐        that window, and re-check from the database for anything dangerous.
```

```
⭐ WHEN RBAC IS NOT ENOUGH — the rule depends on the OBJECT, not just the user:
⭐   "the owner, or a manager in the same department, may approve"
⭐   "only during business hours, and only under £500"
⭐   ⇒ ⭐⭐ THAT IS ABAC / ReBAC, and in Python it is just a FUNCTION:
⭐        def can_approve(user, expense) -> bool: ...
⭐   ⇒ ⭐⭐ KEEP THOSE POLICY FUNCTIONS IN ONE MODULE, PURE, AND UNIT-TESTED WITH
⭐        NO DATABASE (Days 089, 090). ⭐ Authorisation logic scattered through
⭐        handlers is unreviewable and untestable; gathered into pure functions
⭐        it is both, and it is the best-tested code you own.
```

# Part 4 — ⭐⭐ Deny by default, and multi-tenancy

```python
# ⚠️⚠️ ⭐⭐ THE DEFAULT THAT SHIPS THE VULNERABILITY:
@app.route("/admin/users")          # ⭐ someone forgot @requires("users:read")
def list_users(request): ...        # ⇒ ⭐⭐ PUBLIC. Silently. Forever.

# ⭐⭐ INVERT IT — every route declares its requirement, and a missing one is
#    a STARTUP ERROR (Day 112):
@app.route("/admin/users", permission="users:read")
@app.route("/health", permission=PUBLIC)          # ⭐ public must be EXPLICIT
```

```
⭐⭐ "FORGOT THE DECORATOR" IS A VULNERABILITY CLASS, NOT AN ACCIDENT — and the
⭐   fix is structural: ⭐⭐ MAKE THE ABSENCE OF A DECISION IMPOSSIBLE. Validate
⭐   at startup that every registered route declares a permission, PUBLIC
⭐   included. ⭐ Twenty lines, one boot failure, and an entire bug class gone.
⭐   ⇒ ⭐ this is Day 112's route validation doing security work, and Day 099's
⭐        "let the machine catch what a machine can catch".
```

```
⭐⭐ MULTI-TENANCY IS IDOR AT COMPANY SCALE, AND THE BLAST RADIUS IS TOTAL:
⭐   one missing `WHERE tenant_id = ?` and CUSTOMER A READS CUSTOMER B'S DATA.
⭐   ⭐ That is not a bug report, it is a breach notification and possibly a
⭐   contract termination.
⭐   ⇒ ⭐⭐ DO NOT ENFORCE IT IN HANDLERS. Enforce it where it CANNOT be
⭐        forgotten:
⭐        · ⭐ a session-scoped ORM filter applied to every query
⭐        · ⭐⭐ POSTGRES ROW-LEVEL SECURITY — the database itself refuses to
⭐          return another tenant's rows, ⭐ so even a hand-written query is safe
⭐        · ⭐ a separate schema or database per tenant (strongest, most operationally
⭐          expensive)
⭐   ⇒ ⭐⭐ AND TEST IT DELIBERATELY: a test that creates data for tenant A and
⭐        asserts tenant B's requests see NOTHING, on every list endpoint. ⭐ That
⭐        test is worth more than any amount of code review.
```

# Part 5 — ⭐ Testing authorisation

```python
@pytest.mark.parametrize("actor, expected", [        # ⭐ Day 094
    ("owner",     200),
    ("other_user", 404),        # ⭐⭐ THE IDOR TEST — the one that is always missing
    ("admin",     200),
    ("anonymous", 401),
])
def test_get_order_authorisation(client, actor, expected):
    ...
```

```
⭐⭐ THE AUTHORISATION MATRIX: FOR EVERY ENDPOINT, FOUR ACTORS.
⭐        owner · another user · a privileged role · anonymous
⭐   ⇒ ⭐⭐ THE "ANOTHER USER" ROW IS THE ONE ALMOST NOBODY WRITES, and it is
⭐        the only one that catches IDOR. ⭐ The happy path is tested by
⭐        everyone; the cross-user path is tested by nobody.
⭐   ⇒ ⭐ make it a fixture that yields all four clients, so adding an endpoint
⭐        without the matrix feels like the omission it is.
⭐   ⇒ ⭐⭐ AND FOR MULTI-TENANCY, ADD A FIFTH: another tenant. Assert EMPTY,
⭐        not 403 — a list endpoint that leaks counts still leaks.
```

```
⭐ THE REVIEW CHECKLIST FOR ANY NEW ENDPOINT (Day 100B):
⭐   □ ⭐⭐ is the query scoped by the actor, or does it fetch-then-check?
⭐   □ ⭐ does it declare a permission — and is `PUBLIC` explicit?
⭐   □ ⭐ 403 or 404 for a foreign object, and was that decided?
⭐   □ ⭐⭐ can the request body set a field it should not (`is_admin`,
⭐       `user_id`, `price`)? ⭐ Mass assignment — Day 119.
⭐   □ ⭐ does a list endpoint filter by actor AND tenant?
⭐   □ ⭐ does the authorisation test include another user?
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Authenticated but not authorised on the object** | ⭐⭐ IDOR — number one in the OWASP API Top 10. |
| Fetch, then check ownership | ⭐ Correct today, forgotten on the fourteenth endpoint. Scope the query. |
| ⭐ UUIDs as an access control | ⭐⭐ They raise discovery cost, not access. Still check. |
| Ownership checks in middleware | ⭐ It runs before you know which object is involved. |
| ⭐ Hiding the button | ⭐ `curl` does not read CSS. |
| ⭐⭐ **`if user.role == "admin"`** | ⭐⭐ Check permissions; roles are for assigning. |
| Roles in a JWT with no refresh | ⭐ A revoked role stays live until expiry. |
| ⭐ Policy logic scattered in handlers | ⭐ Pure functions in one module, unit-tested. |
| ⭐⭐ **A route with no permission declared** | ⭐⭐ Silently public. Make `PUBLIC` explicit and validate at startup. |
| Tenant filtering in handlers | ⭐⭐ One omission is a cross-tenant breach. Enforce at the data layer or with RLS. |
| ⭐ 403 for an object that should be invisible | ⭐ Confirms existence — an enumeration oracle. |
| ⭐⭐ **No "another user" test** | ⭐⭐ The only test that catches IDOR, and the one nobody writes. |

## Interview questions

**Q: What is IDOR and how do you prevent it?**
> Broken object-level authorisation — the endpoint authenticates you but never checks that the object
> you asked for is yours, so changing 1042 to 1043 in the URL reads someone else's data. It's number
> one in the OWASP API Top 10 because it needs no skill to find: you loop over integers. The reason it
> survives review is that the endpoint *is* authenticated and the decorator *is* there — nothing about
> the route's shape suggests anything is missing. The fix I'd insist on isn't fetch-then-check, which
> is correct but is an extra step someone will forget on the fourteenth endpoint. It's scoping the
> query by the actor, so `WHERE id = ? AND user_id = ?` — because then the unsafe query is
> unwriteable. Make the wrong thing hard to write rather than relying on everyone remembering.

**Q: Where does an authorisation check belong?**
> Two places, and they don't substitute for each other. Coarse checks early — middleware or a route
> declaration — for "is there a session" and "is this an admin endpoint", because they fail fast and
> cheaply. And object-level scoping at the data-access layer, because that's the only layer that can
> answer "is this object yours"; middleware runs before you know which object is involved. Systems
> that have only the first are the ones filling bug-bounty reports. And definitely not the UI — hiding
> a button is UX, and `curl` doesn't read CSS.

**Q: Why check permissions rather than roles?**
> Because `if user.role == "admin"` doesn't survive the second requirement. As soon as support can
> issue small refunds you get a tuple of role names in nineteen places, and adding a role means
> finding all nineteen. With users mapped to roles mapped to permissions, code names permissions and
> administrators manage roles, so adding a role changes zero lines of code. The wrinkle worth flagging
> is freshness: if permissions live in a JWT, a revoked role stays live until the token expires — so
> either accept that window or re-check from the database for anything dangerous.

**Q: How do you stop cross-tenant data leaks?**
> Not by remembering `WHERE tenant_id = ?` in every handler, because one omission is a breach
> notification rather than a bug report. I'd enforce it where it can't be forgotten — a session-scoped
> filter applied to every query, or Postgres row-level security, where the database itself refuses to
> return another tenant's rows so even a hand-written query is safe. And I'd write a deliberate test:
> create data as tenant A, assert tenant B's requests see nothing, on every list endpoint. That test
> is worth more than any amount of review.

**Q: 403 or 404 for something you don't own?**
> It depends on whether the user should know it exists. 403 is honest but confirms existence, which is
> an enumeration oracle — an attacker can map your id space and learn how many customers you have. So
> I'd default to 404 for anything a user has no business knowing about, and use 403 where they can
> legitimately know it exists, like a document shared with their team that they can't edit. The point
> is to decide per resource rather than let the framework's default decide.
