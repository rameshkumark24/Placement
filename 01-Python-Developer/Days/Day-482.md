# Day 482 📰

**P-482** · 📰 **System design round 2 — a news feed** — ⭐⭐ one user with 50M followers breaks the whole design

**Time:** 3 hrs · **Mode:** MOCK + SCORED

> ⭐⭐ **The sentence to own: fan-out on write is correct for the average user and catastrophic for the
> exceptional one, and since every real social product has both, the answer is never one strategy — it
> is a per-user decision made at post time.**

---

# Part 1 — The estimation that frames the fork

```
⭐ ***GIVEN:*** ⭐ 500M daily active users.

⭐ ***READS:*** ⭐ each opens the feed ~10×/day
⭐   ⭐ 5B reads/day ≈ ⭐⭐ 58,000 READS/SEC, ⭐ peak ~175,000.
⭐ ***WRITES:*** ⭐ ~2 posts/day per active poster, say 10% post
⭐   ⭐ 100M posts/day ≈ ⭐⭐ 1,160 POSTS/SEC.
⭐ ⇒ ⭐⭐ ROUGHLY 50:1 READ-HEAVY. ⭐ Same shape as Day 481, and
⭐   the same instinct applies: ⭐ optimise the read.

⭐ ***AND THE NUMBER THAT ACTUALLY DECIDES THE ARCHITECTURE:***
⭐   ⭐ ⭐⭐ AVERAGE FOLLOWERS ≈ 200.
⭐   ⭐ ⇒ fan-out on write = 1,160 posts/sec × 200 =
⭐     ⭐⭐ 232,000 FEED-ROW WRITES/SEC. ⭐ Large, and entirely
⭐     doable — it is just appends.
⭐   ⭐ ⭐⭐ NOW THE ONE THAT BREAKS IT: ⭐ a celebrity with
⭐     ***50 million*** followers posts once.
⭐     ⭐ ⭐⭐ THAT SINGLE ACTION IS 50 MILLION WRITES.
⭐     ⭐ ⭐⭐ AT 232,000/SEC OF NORMAL CAPACITY, IT IS ***215
⭐       SECONDS OF THE ENTIRE SYSTEM'S WRITE BUDGET*** FOR ONE
⭐       POST.
⭐   ⭐ ⭐⭐ THE AVERAGE IS 200. THE MAXIMUM IS 50,000,000. ⭐ Any
⭐     design reasoning from the average is wrong, and this is
⭐     the general lesson: ⭐⭐ IN SOCIAL SYSTEMS THE DISTRIBUTION
⭐     IS POWER-LAW AND THE AVERAGE IS MEANINGLESS.
```

# Part 2 — ⭐⭐ The two strategies, stated as a trade

```
⭐  ┌──────────────┬──────────────────┬──────────────────────┐
⭐  │              │ ***FAN-OUT ON     │ ***FAN-OUT ON READ*** │
⭐  │              │ WRITE (PUSH)***   │ (PULL)                │
⭐  ├──────────────┼──────────────────┼──────────────────────┤
⭐  │ on post      │ ⭐ write a row to │ ⭐ write ***one*** row │
⭐  │              │ every follower's │                      │
⭐  │              │ feed             │                      │
⭐  │ on read      │ ⭐⭐ ONE SEQUENTIAL│ ⭐ query N followees, │
⭐  │              │ SCAN. VERY FAST. │ merge, sort. ⭐⭐ SLOW  │
⭐  │ read latency │ ⭐⭐ ~5ms          │ ⭐ 100ms–1s           │
⭐  │ write cost   │ ⭐⭐ O(FOLLOWERS)  │ ⭐ O(1)               │
⭐  │ storage      │ ⭐ duplicated per │ ⭐⭐ ONE COPY          │
⭐  │              │ follower         │                      │
⭐  │ breaks when  │ ⭐⭐ SOMEONE HAS   │ ⭐⭐ SOMEONE FOLLOWS   │
⭐  │              │ 50M FOLLOWERS    │ 5,000 ACCOUNTS       │
⭐  └──────────────┴──────────────────┴──────────────────────┘

⭐ ⭐⭐ NOTE THE SYMMETRY: ⭐ push breaks on ***out-degree***,
⭐   pull breaks on ***in-degree***. ⭐⭐ THEY FAIL ON DIFFERENT
⭐   USERS, WHICH IS EXACTLY WHY A HYBRID WORKS.

⭐ ⇒ ⭐⭐ ***THE HYBRID, AND IT IS THE ANSWER:***
⭐   ⭐ ① ***push*** for normal users — 99.9% of posts, and the
⭐     read stays a single scan;
⭐   ⭐ ② ⭐⭐ ***PULL*** FOR ACCOUNTS ABOVE A FOLLOWER THRESHOLD
⭐     ⭐ (say 100,000) — one row written, ⭐⭐ NOT 50 MILLION;
⭐   ⭐ ③ ⭐⭐ AT READ TIME: ***READ THE MATERIALISED FEED, THEN
⭐     MERGE IN RECENT POSTS FROM THE FEW CELEBRITIES THIS USER
⭐     FOLLOWS.***
⭐   ⭐ ⭐⭐ THE ARITHMETIC THAT MAKES IT WORK: ⭐ a user follows
⭐     200 accounts, of which maybe 5 are celebrities. ⭐⭐ SO THE
⭐     MERGE IS 5 SMALL QUERIES, NOT 200 — ⭐ which is why pull's
⭐     usual cost does not apply to the subset you use it for.

⭐ ⭐⭐ AND THE THRESHOLD IS A ***TUNABLE***, NOT A CONSTANT: ⭐ it
⭐   is wherever `followers × post_rate` stops being worth the
⭐   write amplification, ⭐⭐ AND YOU MEASURE IT RATHER THAN
⭐   GUESS IT.
```

# Part 3 — The feed table, and what you do not store

```
⭐ ***THE MATERIALISED FEED IS ***POINTERS***, NOT CONTENT.***
⭐   ⭐ Store `(user_id, post_id, created_at)` — ~24 bytes.
⭐   ⭐ ⭐⭐ NEVER COPY THE POST BODY INTO 50 MILLION ROWS: ⭐ an
⭐     edit would require rewriting all of them, and storage
⭐     explodes for no benefit.
⭐   ⭐ ⇒ hydrate post content from a separate store at read
⭐     time, ⭐⭐ WHICH IS A BATCH GET BY ID AND IS TRIVIALLY
⭐     CACHEABLE — ⭐ a popular post is fetched once and served
⭐     to millions.

⭐ ***AND CAP THE FEED.***
⭐   ⭐ ⭐⭐ NOBODY SCROLLS PAST ~800 ITEMS. ⭐ Keep the newest N
⭐     per user and drop the rest.
⭐   ⭐ ⭐⭐ THIS TURNS AN UNBOUNDED WRITE-AMPLIFIED STORE INTO A
⭐     BOUNDED ONE: ⭐ 500M users × 800 × 24B ≈ 9.6 TB, ⭐ which
⭐     is a fixed cost rather than a growing one.
⭐   ⭐ ⭐ Deep history comes from pull, which is fine because
⭐     ⭐⭐ ALMOST NOBODY ASKS FOR IT AND THOSE WHO DO CAN WAIT.

⭐ ***THE STORAGE CHOICE:***
⭐   ⭐ ⭐⭐ THE FEED IS AN APPEND-ORDERED LIST PER USER, ⭐ read as
⭐     a range from the newest. ⭐ Redis sorted sets or a
⭐     wide-column store with `(user_id, created_at)` as the key
⭐     are both natural. ⭐⭐ A RELATIONAL TABLE WORKS TOO AND
⭐     WANTS THAT EXACT COMPOSITE INDEX.
```

# Part 4 — ⭐⭐ Cursor pagination is not a preference

```
⭐ ***THE BUG WITH `LIMIT 20 OFFSET 40`:***
⭐   ⭐ user reads page 3 (items 41–60);
⭐   ⭐ ⭐⭐ SIX NEW POSTS ARRIVE AT THE TOP;
⭐   ⭐ user requests page 4 (offset 60) — ⭐⭐ WHICH IS NOW WHERE
⭐     ITEM 54 USED TO BE, ⭐ so they ***re-read six items they
⭐     have already seen***.
⭐   ⭐ ⭐⭐ ON A FEED WHERE THE TOP CHANGES CONSTANTLY, THIS
⭐     HAPPENS ON EVERY SINGLE PAGE, ⭐ and users experience it
⭐     as "the app keeps showing me the same posts".

⭐ ⭐⭐ AND THE SECOND, WORSE PROBLEM: ⭐ `OFFSET 100000` makes the
⭐   database ***scan and discard*** a hundred thousand rows.
⭐   ⭐⭐ DEEP PAGINATION GETS LINEARLY SLOWER AND IT IS A
⭐   TRIVIAL DENIAL-OF-SERVICE.

⭐ ✅ ***CURSOR (KEYSET) PAGINATION:***
⭐   ⭐ `WHERE (created_at, post_id) < (:cursor_ts, :cursor_id)
⭐      ORDER BY created_at DESC, post_id DESC LIMIT 20`
⭐   ⭐ ⭐⭐ STABLE UNDER INSERTS — ⭐ the cursor names a
⭐     ***position in the data***, not a count.
⭐   ⭐ ⭐⭐ CONSTANT TIME AT ANY DEPTH ⭐ — it is an index seek.
⭐   ⭐ ⭐ The composite tie-break on `post_id` is not optional:
⭐     ⭐⭐ TWO POSTS IN THE SAME MILLISECOND WOULD OTHERWISE SKIP
⭐     OR REPEAT ONE.
⭐   ⭐ ⭐⭐ OPAQUE-ENCODE THE CURSOR ⭐ so clients cannot forge it
⭐     and you can change the format later.
```

# Part 5 — The three things that get asked next

```
⭐ ① ⭐⭐ ***READ-YOUR-OWN-WRITES.***
⭐   ⭐ You post, your feed is fanned out asynchronously,
⭐     ⭐⭐ AND YOUR OWN POST ISN'T THERE YET. ⭐ Users read that
⭐     as "the app lost my post" and post again.
⭐   ⭐ ⇒ ⭐⭐ INSERT INTO YOUR ***OWN*** FEED SYNCHRONOUSLY, ⭐ fan
⭐     out to everyone else asynchronously. ⭐ One special case,
⭐     and it removes the entire class of complaint.

⭐ ② ⭐⭐ ***RANKING VS CHRONOLOGICAL.***
⭐   ⭐ Chronological: ⭐⭐ THE FEED ***IS*** THE STORED ORDER. ⭐ Cheap.
⭐   ⭐ Ranked: ⭐ you must fetch a candidate set (say 500),
⭐     score it, and return 20. ⭐⭐ SO RANKING TURNS A SEQUENTIAL
⭐     SCAN INTO A SCORING PIPELINE ON EVERY READ ⭐ — a different
⭐     system, with a feature store and a model server.
⭐   ⭐ ⭐⭐ SAY WHICH YOU ARE BUILDING. ⭐ "Chronological, and I'd
⭐     note that ranking is not a feature you add later — it
⭐     changes the read path from a scan into a pipeline."

⭐ ③ ***DELETES, BLOCKS AND PRIVACY.***
⭐   ⭐ ⭐⭐ A DELETED POST IS STILL IN 50 MILLION MATERIALISED
⭐     FEEDS. ⭐ Chasing them is unbounded work.
⭐   ⭐ ⇒ ⭐⭐ FILTER AT ***HYDRATION*** TIME: ⭐ the feed holds
⭐     pointers, so a deleted or blocked post simply fails to
⭐     hydrate and is dropped. ⭐⭐ THIS IS THE SECOND MAJOR
⭐     PAYOFF FOR STORING POINTERS RATHER THAN CONTENT ⭐ — and
⭐     it means over-fetching slightly, since some of the 20 you
⭐     fetched will vanish.
⭐   ⭐ ⭐⭐ THE SAME MECHANISM HANDLES BLOCKS, MUTES AND
⭐     VISIBILITY CHANGES — ⭐ permissions are evaluated at read
⭐     time against live state, never baked into the fan-out
⭐     (D434's stale-ACL problem, in a different costume).
```

# 💬 Interview

**1. "Design a news feed."**

⭐ I'd ask for the follower *distribution* rather than the average, because that's the number that decides
the architecture. ⭐⭐ The average is around 200 and the maximum is 50 million, and any design reasoning
from the average is wrong. ⭐ With 500 million DAU I get roughly 58,000 reads a second and 1,160 posts —
so it's 50:1 read-heavy and the instinct is to optimise the read, which means fan-out on write. ⭐⭐ That
gives 232,000 feed-row writes a second, which is large but fine because they're appends. ⭐ Then one
celebrity posts and that single action is 50 million writes — 215 seconds of the entire system's write
budget for one post.

**2. "So which strategy?"**

⭐ Neither alone, and the reason is a symmetry worth naming: ⭐⭐ push breaks on out-degree, pull breaks
on in-degree. ⭐ Push is catastrophic when someone has 50 million followers; pull is slow when someone
follows 5,000 accounts. ⭐⭐ They fail on *different* users, which is exactly why a hybrid works. ⭐ So:
push for normal accounts, which is 99.9% of posts and keeps the read a single scan; pull for accounts
above a follower threshold, where posting writes one row instead of 50 million; and at read time, merge
the materialised feed with recent posts from the few celebrities this user follows. ⭐⭐ The arithmetic
that makes it work is that a user follows 200 accounts of which maybe five are celebrities — so the merge
is five small queries, not two hundred.

**3. "Where's the threshold?"**

⭐ It's a tunable, not a constant, and I'd measure rather than guess. ⭐⭐ Conceptually it's wherever
followers times post-rate stops being worth the write amplification — someone with 200,000 followers who
posts once a month is cheap to push, and someone with 50,000 followers who posts forty times a day may
not be. ⭐ So the real predicate is expected fan-out volume, not raw follower count. ⭐⭐ And it has to be
re-evaluated as accounts grow, which means the push/pull decision is made *at post time* per account,
not stored as a permanent property.

**4. "What's in the feed table?"**

⭐ Pointers, not content — user id, post id, timestamp, about 24 bytes. ⭐⭐ Copying the post body into 50
million rows means an edit rewrites all of them, and storage explodes for no benefit. ⭐ Content gets
hydrated at read time as a batch get by id, which is trivially cacheable — a popular post is fetched once
and served to millions. ⭐⭐ And I'd cap the feed at around 800 items, because nobody scrolls past that,
which turns an unbounded write-amplified store into a bounded one: 500 million users times 800 times 24
bytes is under ten terabytes, fixed rather than growing.

**5. "How do you paginate?"**

⭐ Cursors, and it's not a style preference — offset pagination is broken here for two separate reasons.
⭐⭐ First, correctness: if six new posts arrive while someone is reading, page four starts where item 54
used to be, so they re-read six posts they've already seen. On a feed where the top changes constantly
that happens on *every* page, and users experience it as the app repeating itself. ⭐ Second, `OFFSET
100000` makes the database scan and discard a hundred thousand rows, so deep pagination gets linearly
slower and is a trivial denial of service. ⭐⭐ Keyset pagination is stable under inserts and constant
time at any depth, because the cursor names a position in the data rather than a count. ⭐ And the cursor
needs a composite tie-break on post id, or two posts in the same millisecond skip or repeat one.

**6. "A user posts and doesn't see it."**

⭐ That's read-your-own-writes, and it's the complaint that generates duplicate posts — people assume the
app lost it and post again. ⭐⭐ The fix is one special case: insert into your *own* feed synchronously,
fan out to everyone else asynchronously. ⭐ Your feed is the one you're about to look at, and it's a
single row. ⭐⭐ Everyone else's can be eventually consistent, because nobody notices a friend's post
arriving 800 milliseconds late.

**7. "Someone deletes a post that's in 50 million feeds."**

⭐ I don't chase it — that's unbounded work triggered by one user action. ⭐⭐ Because the feed holds
pointers, a deleted post simply fails to hydrate and gets dropped at read time. ⭐ That's the second big
payoff for storing pointers rather than content, and it means over-fetching slightly since some of the
twenty I fetch will vanish. ⭐⭐ The same mechanism handles blocks, mutes and visibility changes —
permissions are evaluated at read time against live state, never baked into the fan-out. ⭐ Baking them
in is the stale-ACL problem: the permission changes and the copies don't.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: the fan-out decision, argued from numbers.**

Open by asking for the right number. **"Before I choose anything: what does the follower distribution
look like — not the average, the maximum? Because the average is around two hundred and if the maximum
is fifty million, those two numbers imply completely different systems, and reasoning from the average
gives me the wrong one."**

Then do the arithmetic that forces the fork. **"With five hundred million DAU I get about fifty-eight
thousand reads a second and eleven hundred posts — fifty to one read-heavy, so the instinct is fan-out on
write: do the work once at post time so the read is a single sequential scan. At two hundred followers
that's two hundred and thirty-two thousand feed-row writes a second, which is large but fine, because
they're appends. Then one celebrity posts, and that single action is fifty million writes — two hundred
and fifteen seconds of the entire system's write budget for one post."**

Then name the symmetry, which is the insight. **"So push doesn't work universally. But pull doesn't
either — reading becomes a query across every account you follow, merged and sorted, on every refresh.
The useful observation is that they break on opposite things: push breaks on out-degree, pull breaks on
in-degree. They fail on different users. That's exactly why a hybrid works rather than being a
compromise."**

Close with the hybrid and the arithmetic that justifies it. **"Push for normal accounts — ninety-nine
point nine percent of posts, and the read stays a scan. Pull for accounts above a follower threshold: one
row written instead of fifty million. Then at read time, read the materialised feed and merge in recent
posts from the celebrities this user follows. And that merge is cheap for a reason worth stating: a user
follows two hundred accounts of which maybe five are celebrities, so it's five small queries, not two
hundred. Pull's usual cost simply doesn't apply to the subset I'm using it for. The threshold itself is a
tunable — really it's expected fan-out volume rather than raw follower count, because someone with
fifty thousand followers posting forty times a day costs more than someone with two hundred thousand
posting monthly."**
