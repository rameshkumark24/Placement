# Part 1 — ⭐⭐ What a gate is actually for

```
⭐⭐ THREE HONEST STATEMENTS ABOUT GATES:

⭐ ① ⭐⭐ A GATE NOBODY CAN FAIL IS A DECORATION. If it has never
⭐     gone red, it is not protecting anything — it is costing
⭐     you 90 seconds per push and buying zero information.
⭐     ⇒ ⭐ The first question about any check is: ***what change
⭐       would this have caught?*** Answer it with a real example
⭐       or delete the check.

⭐ ② ⭐⭐ A GATE THAT IS RED FOR UNRELATED REASONS IS WORSE THAN
⭐     NO GATE. People learn to re-run it, then to skip it, then
⭐     to merge past it — ⭐ and the day it is right, nobody
⭐     believes it. ⭐⭐ CREDIBILITY IS THE RESOURCE YOU ARE
⭐     SPENDING, and it does not refill.

⭐ ③ ⭐ A GATE SLOWER THAN THE REVIEW IS A GATE PEOPLE ROUTE
⭐     AROUND. Speed is a correctness property here (Part 7).
```

```
⭐⭐ AND THE FRAMING THAT MAKES THE REST OF THE DAY OBVIOUS:
⭐   ***A GATE IS NOT A QUALITY MEASURE. IT IS A WRITTEN-DOWN
⭐      LIST OF WHAT YOU REFUSE TO SHIP.***
⭐   ⇒ ⭐ Which means each one should map to a failure you can
⭐     describe. "80% coverage" describes no failure.
⭐     ⭐⭐ "A NEW ENDPOINT WITH NO AUTHORISATION TEST" DOES.
```

# Part 2 — ⭐⭐ Coverage as a floor on new code

```
⭐⭐ THE GLOBAL THRESHOLD IS THE WRONG SHAPE:
⭐   ⭐ `fail_under = 80` on a 40,000-line project ⇒ the number
⭐     barely moves whatever you do, so it gates nothing.
⭐   ⭐⭐ AND WHEN IT ***DOES*** BITE, IT BITES THE WRONG PERSON:
⭐     someone deletes 300 well-tested lines, coverage drops,
⭐     and CI blocks a refactor that improved the codebase.
⭐   ⭐ Worse: it produces TEST-SHAPED CODE — tests written to
⭐     execute lines rather than to assert behaviour, which
⭐     Day 261 already named as the thing that only feels like
⭐     testing.

⭐⭐ THE RIGHT SHAPE IS PATCH COVERAGE:
⭐   ⭐ `diff-cover coverage.xml --compare-branch=origin/main
⭐        --fail-under=90`
⭐   ⇒ ⭐⭐ THE RULE BECOMES "NEW CODE ARRIVES TESTED", which is
⭐     a rule about behaviour you can actually defend in review,
⭐     ⭐ and legacy debt stops blocking unrelated work.
⭐   ⇒ ⭐ Old code improves when you touch it. That is the only
⭐     way old code ever improves.
```

```
⭐⭐ AND THE EXCLUSION LIST IS PART OF THE GATE, NOT AN ESCAPE:
⭐   ⭐ `# pragma: no cover` on a `TYPE_CHECKING` block ⇒ fine.
⭐   ⭐⭐ ON AN `except` BRANCH ⇒ that is the branch you most
⭐     needed a test for, and now it is invisible.
⭐   ⇒ ⭐ Grep for pragmas in review. ⭐⭐ AN EXCLUSION IS A
⭐     DECISION AND SHOULD CARRY A REASON ON THE SAME LINE.
```

# Part 3 — ⭐⭐ What the number cannot see

```python
def price(order, customer):
    total = sum(l.amount for l in order.lines)
    if customer.is_vip:                 # ⭐ both branches "covered"
        total = total * Decimal("0.9")
    return total.quantize(Decimal("0.01"))
```

```
⭐⭐ 100% LINE COVERAGE. TWO TESTS. ZERO GUARANTEES:
⭐   ⭐ test_vip_price_runs()   → asserts it did not raise
⭐   ⭐ test_normal_price_runs()→ asserts it did not raise
⭐   ⇒ ⭐⭐ THE DISCOUNT COULD BE 0.9, 0.99, OR 9.0 AND EVERY
⭐     TEST STILL PASSES. ⭐ Coverage measured that the line RAN.
⭐     It cannot measure that anything CHECKED THE RESULT.

⭐⭐ AND LINE COVERAGE HIDES A SECOND THING — BRANCHES:
⭐   `if a and b:` on one line is ONE LINE and FOUR PATHS.
⭐   ⇒ ⭐ `--cov-branch`. The number always drops when you turn
⭐     it on, and ⭐⭐ THE DROP IS THE POINT: it is the first
⭐     honest measurement you have taken.
```

```
⭐⭐ SO THE HONEST CHECK IS MUTATION TESTING (Day 261), SCOPED:
⭐   ⭐ Run `mutmut` (or `cosmic-ray`) over `domain/` ONLY —
⭐     the pure code where a surviving mutant is unambiguous.
⭐   ⭐⭐ NIGHTLY, NEVER ON A PR. It takes minutes to hours,
⭐     and Part 1 rule ③ applies.
⭐   ⭐ The output is a REPORT YOU TRIAGE, not a threshold.
⭐     ⇒ ⭐⭐ A SURVIVING MUTANT IS EITHER A MISSING ASSERTION
⭐       OR A LINE THAT DOES NOT MATTER. ⭐ Both findings are
⭐       worth having, and the second one is more interesting.
```

# Part 4 — ⭐⭐ The gates that are worth more than coverage

```
⭐⭐ RANKED BY WHAT THEY ACTUALLY CATCH IN THIS PROJECT:

⭐ ① ⭐⭐ THE AUTHORISATION MATRIX (Day 261) as its own CI job.
⭐      ⭐ Parametrised over the route table, so a new endpoint
⭐        is covered without anyone remembering. ⭐⭐ THIS IS THE
⭐        HIGHEST-VALUE CHECK YOU OWN.

⭐ ② ⭐⭐ THE OPENAPI DRIFT CHECK (Day 260) — generate the spec,
⭐      diff against the committed one, fail on difference.
⭐      ⭐ Without it, "spec first" survives about three weeks.

⭐ ③ ⭐ QUERY-COUNT CEILINGS (Day 255) — the only automated
⭐      defence against an N+1 introduced by a serialiser change.

⭐ ④ ⭐⭐ THE MIGRATION CHECK, AND ALMOST NOBODY HAS IT:
⭐      ⭐ apply every migration to a seeded database in CI
⭐      ⭐ assert `alembic downgrade` works (or that the
⭐        migration is explicitly marked irreversible)
⭐      ⭐⭐ ASSERT NO STATEMENT TOOK AN `ACCESS EXCLUSIVE` LOCK
⭐        FOR MORE THAN N MILLISECONDS — because Day 196 says a
⭐        waiting lock blocks every reader behind it, and
⭐        ⭐⭐ THAT IS A DEPLOY-TIME OUTAGE THAT PASSES EVERY
⭐        OTHER TEST YOU HAVE.

⭐ ⑤ ⭐ TYPES — `mypy --strict` on `domain/` and `services/`,
⭐      looser at the edges. ⭐⭐ Strict everywhere on day one is
⭐      how type checking gets turned off in month two.

⭐ ⑥ ⭐ LINT AND FORMAT AS ERRORS (`ruff`), so style is never
⭐      discussed in a review again. That is the entire benefit.

⭐ ⑦ ⭐ SECURITY: dependency audit (`pip-audit`), secret scanning
⭐      on the diff, and `bandit` on new code.
⭐      ⭐⭐ SECRET SCANNING RUNS ON THE ***HISTORY***, NOT JUST
⭐        THE DIFF — a secret committed and then deleted is
⭐        still in the pack file and still leaked.
```

# Part 5 — ⭐⭐ Flakiness, which is a credibility problem

```
⭐⭐ THE ARITHMETIC THAT ENDS THE ARGUMENT:
⭐   ⭐ 400 tests, each 99.9% reliable
⭐   ⇒ 0.999^400 = ⭐⭐ 67% — ***ONE RUN IN THREE IS RED FOR NO
⭐     REASON.*** ⭐ And each individual test looks fine.
⭐   ⇒ ⭐⭐ FLAKINESS IS MULTIPLICATIVE, WHICH IS WHY IT ALWAYS
⭐     ARRIVES SUDDENLY: nothing is wrong until everything is.
```

```
⭐ THE POLICY, WRITTEN DOWN BEFORE YOU NEED IT:
⭐   ⭐ a flaky test is QUARANTINED THE SAME DAY (`@pytest.mark
⭐     .flaky_quarantine`, excluded from the gate, still run and
⭐     reported)
⭐   ⭐⭐ QUARANTINE HAS AN EXPIRY DATE IN THE MARKER. Past it,
⭐     the suite fails. ⭐ Otherwise quarantine is deletion with
⭐     a nicer name, and the quarantine list only ever grows.
⭐   ⭐ randomised order (`-p no:randomly` OFF) so ordering
⭐     dependencies surface today rather than in six months
⭐   ⭐ `--durations=10` in CI output, because the slowest test
⭐     is usually the flakiest one too
```

# Part 6 — ⭐⭐ Making the gate fast enough to be obeyed

```
⭐⭐ THE ARITHMETIC OF ATTENTION:
⭐   ⭐ under 5 min  ⇒ you wait for it
⭐   ⭐ 5–15 min     ⇒ you context-switch and come back
⭐   ⭐⭐ over 15 min ⇒ you MERGE ON GREEN-ISH AND MOVE ON, which
⭐     means the gate is now advisory, whatever the branch
⭐     protection settings say.

⭐⭐ SO SPLIT BY WHAT A FAILURE MEANS:
⭐   ⭐ PR GATE (target < 8 min): lint · types · unit · integration
⭐     · patch coverage · auth matrix · spec drift · migrations
⭐     ⇒ ⭐ everything whose failure means "this change is wrong"
⭐   ⭐ MAIN / NIGHTLY: mutation testing · full E2E · dependency
⭐     audit · load smoke · the slow container scan
⭐     ⇒ ⭐⭐ everything whose failure means "something is wrong",
⭐       which is a different sentence and a different urgency.

⭐ HOW YOU GET THERE:
⭐   ⭐ `pytest -n auto` with a template database (Day 261)
⭐   ⭐ cache the dependency layer, not the source layer (Day 282)
⭐   ⭐ run jobs in PARALLEL, and ⭐⭐ FAIL FAST ONLY ON LINT —
⭐     cancelling the test job to save 90 seconds costs you the
⭐     other four failures you would have fixed in one pass.
```

# Part 7 — ⭐ The gate file as a document

```
⭐⭐ ONE FILE, `docs/quality-gates.md`, WITH FOUR COLUMNS:
⭐   | Check | What it catches | Where it runs | Who can waive |

⭐⭐ THE FOURTH COLUMN IS THE INTERESTING ONE:
⭐   ⭐ Some checks are waivable with a written reason in the PR.
⭐   ⭐⭐ SOME ARE NOT — the authorisation matrix, secret scanning,
⭐     the migration lock check. ⭐ Writing down which is which,
⭐     in advance, is exactly the Part 1 point: ⭐⭐ THE DECISION
⭐     IS MADE WHILE YOU ARE CALM.
⭐   ⇒ ⭐ And an unwaivable check must be one you can trust, which
⭐     closes the loop back to flakiness.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| A check that has never gone red | It buys no information. Name the change it would catch, or delete it. |
| Tolerating an unreliable gate | People re-run, then skip, then merge past. Credibility doesn't refill. |
| A global coverage threshold | It gates nothing on a large codebase and blocks refactors that delete tested code. |
| Coverage as a target rather than a floor | You get test-shaped code that executes lines and asserts nothing. |
| Line coverage without `--cov-branch` | `if a and b` is one line and four paths. |
| `# pragma: no cover` on an `except` | That's the branch you most needed to test, now invisible. |
| Mutation testing on every PR | Minutes to hours. Nightly, scoped to the domain layer. |
| Treating surviving mutants as a score | It's a triage list: a missing assertion, or a line that doesn't matter. |
| No authorisation-matrix job | The single highest-value check in this project. |
| No spec-drift check | "Spec first" lasts about three weeks. |
| No migration check in CI | A deploy-time `ACCESS EXCLUSIVE` lock passes every other test you have. |
| Never testing `downgrade` | You find out during the rollback you're doing under pressure. |
| `mypy --strict` everywhere on day one | It gets switched off in month two. Strict in the core, loose at the edges. |
| Secret scanning on the diff only | The deleted secret is still in history and still leaked. |
| Quarantine with no expiry | Deletion with a nicer name, and the list only grows. |
| Deterministic test ordering | Ordering dependencies surface in six months instead of today. |
| A 20-minute PR gate | It becomes advisory regardless of branch protection. |
| Fail-fast on the test job | You fix one failure per push instead of four. |
| No written list of what is unwaivable | The decision gets made at 6 p.m. on a Friday instead. |

## Interview questions

**Q: What coverage do you require?**

> Ninety percent on the diff, nothing globally. A global threshold on a large codebase barely moves,
> so it gates nothing — and when it does bite, it blocks someone for deleting well-tested code during
> a refactor. Patch coverage encodes the rule I actually want, which is that new code arrives tested
> and old code improves when you touch it. And I'd say plainly that the number is a floor, not a
> measure: a hundred percent line coverage is compatible with a discount factor of nine instead of
> nought point nine, because coverage records that a line ran, not that anything checked the result.

**Q: So how do you know the tests assert anything?**

> Mutation testing, scoped and nightly. I run it over the domain layer, where the code is pure and a
> surviving mutant is unambiguous, and I treat the output as a triage list rather than a threshold —
> a survivor is either a missing assertion or a line that doesn't matter, and the second finding is
> often the more interesting one. It doesn't go on the PR gate because it takes minutes to hours, and
> a gate slower than the review is a gate people route around.

**Q: Which gate has caught the most real problems for you?**

> The authorisation matrix, because it's parametrised over the route table, so an endpoint added on a
> Friday is covered without anyone remembering to cover it. After that, the migration check — almost
> nobody has one, and it's the only thing that catches a statement taking an `ACCESS EXCLUSIVE` lock
> at deploy time, which blocks every reader behind it and passes every other test in the suite. And
> the spec-drift check, without which "spec first" lasts about three weeks.

**Q: What's your position on flaky tests?**

> That it's an arithmetic problem, not an annoyance. Four hundred tests at 99.9% reliability each
> gives you a red run one time in three, and every individual test looks fine — which is why
> flakiness always seems to arrive suddenly. So there's a written policy: quarantine the same day,
> and the quarantine marker carries an expiry date after which the suite fails, because otherwise
> quarantine is deletion with a nicer name and the list only grows. Plus randomised ordering, so
> ordering dependencies surface today rather than in six months.

**Q: How long should CI take?**

> Under eight minutes for the PR gate, and I'd treat that as a correctness property rather than a
> nicety. Under five minutes you wait; over fifteen you merge on green-ish and move on, which makes
> the gate advisory no matter what branch protection says. So I split by what a failure means: the PR
> gate holds everything whose failure means "this change is wrong", and nightly holds everything
> whose failure means "something is wrong" — mutation testing, full E2E, dependency audit, the slow
> scans.

## 🎙️ Articulation drill

**Two minutes: "How do you enforce quality?"**

Lead with what a gate is for, because it reframes everything after it: **a gate exists so the decision
gets made while you're calm** — every rule enforced on a Tuesday is a rule you don't argue about at
6 p.m. on a Friday with a release waiting. Then three honest statements: a check that's never gone red
buys no information, an unreliable gate spends credibility that doesn't refill, and a gate slower than
the review gets routed around. On coverage, take the position clearly: **ninety percent on the diff,
nothing globally**, because a global threshold gates nothing on a big codebase and blocks the person
deleting well-tested code — and say the limit out loud, that a hundred percent coverage is compatible
with a discount factor of nine instead of nought point nine, since coverage records that a line ran,
not that anything checked the result. **Mutation testing is the honest check**, scoped to the domain
layer and run nightly. Then name the gates that beat coverage in this project: the authorisation matrix
parametrised over the route table, the spec-drift job, query-count ceilings, and **the migration check
almost nobody has — the one that catches a deploy-time `ACCESS EXCLUSIVE` lock, which passes every
other test in the suite.** Close on flakiness as arithmetic — four hundred tests at 99.9% is red one
run in three — and on speed as a correctness property, with the PR gate holding everything whose
failure means "this change is wrong" and nightly holding everything whose failure means "something is
wrong."
