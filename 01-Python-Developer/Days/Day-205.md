# Day 205

**L-205** · 🧠 **Persistence** — ⭐⭐ RDB, AOF, and what "durable" honestly means for Redis

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: persistence protects you from a *restart*. It does not protect you from
> a *failover* — because Redis replication is asynchronous, always, and no persistence setting changes
> that.**
>
> ⭐ Almost every "Redis lost my data" story is a failover, not a crash, and the team had persistence
> configured perfectly. ⭐⭐ Today is the honest version: what each mode costs, what the ceiling
> actually is, and the decision table by use case — including the case where the right answer is to
> turn persistence **off**.

---

# Part 1 — ⭐ RDB: a point-in-time snapshot

```
⭐   save 900 1        ⭐ snapshot if ≥1 key changed in 900 s
⭐   save 300 10       ⭐ …or ≥10 in 300 s
⭐   save 60  10000    ⭐ …or ≥10,000 in 60 s
⭐   dbfilename dump.rdb · dir /var/lib/redis
⭐   rdbcompression yes · rdbchecksum yes

⭐⭐ HOW: `BGSAVE` ***forks***; the child walks memory and writes a
⭐   compact binary file. ⭐ Day 203's copy-on-write bill applies to
⭐   every snapshot.
⭐ ⭐⭐ NEVER RUN `SAVE` (no BG). It snapshots ON THE MAIN THREAD and
⭐   freezes the server for the whole write.

⭐ ✅ ⭐ COMPACT — much smaller than AOF; ⭐ FAST TO RESTART (load a
⭐      binary image, no replay); ⭐⭐ IT IS YOUR BACKUP ARTEFACT — one
⭐      file you can copy anywhere.
⭐ ❌ ⭐⭐ YOU LOSE EVERYTHING SINCE THE LAST SNAPSHOT. With the default
⭐      rules that is up to 15 MINUTES.
⭐ ❌ ⭐ The fork cost, and a latency spike proportional to dataset size.
```

# Part 2 — ⭐⭐ AOF: an append-only log of every write

```
⭐   appendonly yes
⭐   appendfsync everysec        ⭐⭐ ← THE ONLY DIAL THAT MATTERS
⭐   auto-aof-rewrite-percentage 100    ⭐ rewrite when 2× the last size
⭐   auto-aof-rewrite-min-size 64mb

⭐⭐ `appendfsync` — AND IT IS EXACTLY DAY 186'S `synchronous_commit`:
⭐   ⭐ `always`   — fsync after every write command.
⭐        ⭐⭐ ~1,000–10,000 ops/sec instead of 100,000+. ⭐ You have
⭐        traded away the reason you chose Redis.
⭐   ⭐⭐ `everysec` — fsync once a second, in a BACKGROUND THREAD.
⭐        ⭐⭐ ***UP TO 1 SECOND OF LOSS.*** ⭐ Essentially full speed.
⭐        ⭐⭐ THIS IS THE ANSWER FOR ~99% OF DEPLOYMENTS.
⭐   ⭐ `no`       — leave it to the OS. Up to 30 s of loss.

⭐⭐ THE REWRITE: the log would grow forever (`INCR k` a million times =
⭐   a million lines). ⭐ `BGREWRITEAOF` forks and writes the MINIMAL
⭐   set of commands that reproduces current state — a million `INCR`s
⭐   become one `SET k 1000000`. ⭐⭐ IT FORKS TOO, so the Day 203 bill
⭐   is paid on rewrites as well as snapshots.

⭐ ✅ ⭐ ~1 second worst-case loss. ⭐ Human-readable-ish; a bad command
⭐      can be edited out of the tail after an incident.
⭐ ❌ ⭐ Bigger files. ⭐⭐ SLOWER RESTART — a 20 GB AOF must be REPLAYED,
⭐      which can be minutes of unavailability after a reboot.
```

```
⭐⭐ SO: USE BOTH. THE PRODUCTION DEFAULT.
⭐   appendonly yes · appendfsync everysec · save 900 1
⭐   ⭐⭐ `aof-use-rdb-preamble yes` (default since 4.0) — ⭐⭐ THE
⭐     REWRITE WRITES AN RDB-FORMAT BASE PLUS AN AOF TAIL.
⭐     ⇒ ⭐⭐ FAST RESTART ***AND*** ONE-SECOND DURABILITY. You stop
⭐       choosing. ⭐ Redis 7 splits this into a manifest plus base and
⭐       incremental files, which makes rewrites cheaper again.
⭐   ⭐ On restart Redis prefers the AOF, because it is more complete.
```

# Part 3 — ⭐⭐ The ceiling: what Redis durability actually is

```
⭐⭐ EVEN WITH `appendfsync always`, REDIS IS NOT POSTGRES. FOUR REASONS,
⭐   AND THE FOURTH IS THE ONE THAT MATTERS:

⭐  ① ⭐ NO TRANSACTIONS WITH ROLLBACK. `MULTI/EXEC` is isolation, not
⭐     atomicity-with-recovery (Day 203). A partially-applied logical
⭐     operation stays partially applied.
⭐  ② ⭐ NO CONSTRAINTS. Nothing checks the data on the way back in.
⭐  ③ ⭐ THE ACK CAN PRECEDE THE FSYNC in some paths, and a `fsync` that
⭐     fails is handled less conservatively than in a database whose
⭐     whole job is that.
⭐  ④ ⭐⭐ ***REPLICATION IS ASYNCHRONOUS. ALWAYS. THERE IS NO
⭐     SYNCHRONOUS MODE.***
⭐     ⇒ ⭐⭐ THE PRIMARY ACKS YOUR WRITE, THEN SENDS IT TO REPLICAS. IF
⭐       IT DIES IN BETWEEN AND A REPLICA IS PROMOTED, ⭐⭐ THAT WRITE IS
⭐       GONE — and your persistence settings were irrelevant, because
⭐       the promoted replica never had it.
```

```
⭐⭐ `WAIT numreplicas timeout` — and why it is not the fix people hope:
⭐   WAIT 1 100     -- ⭐ block until ≥1 replica ACKNOWLEDGED the write
⭐   ⭐⭐ IT CONFIRMS ***RECEIPT IN MEMORY***, NOT `fsync` ON THE REPLICA.
⭐   ⭐⭐ AND IT DOES NOT PREVENT DATA LOSS ON FAILOVER — a replica that
⭐     received it can still be passed over for one that did not.
⭐   ⭐ `WAITAOF` (7.0+) does wait for fsync on replicas, which is
⭐     stronger — ⭐⭐ and still not a synchronous-commit guarantee,
⭐     because failover selection is not tied to it.
⭐   ⇒ ⭐⭐ THE HONEST STATEMENT OF REDIS'S DURABILITY CEILING:
⭐     ⭐⭐ "ABOUT ONE SECOND OF LOSS ON A CRASH, AND AN UNBOUNDED-BUT-
⭐        SMALL AMOUNT ON A FAILOVER."
⭐   ⇒ ⭐⭐ WHICH IS WHY MONEY, ORDERS AND ANYTHING WITH A LEGAL
⭐     CONSEQUENCE LIVE IN POSTGRES, AND REDIS HOLDS THE FAST COPY.
⭐     ⭐ Say this sentence in an interview; it is the whole judgement.
```

# Part 4 — ⭐⭐ The decision, by use case

```
⭐⭐ ① PURE CACHE ⇒ ***TURN PERSISTENCE OFF.***
⭐    appendonly no · save ""
⭐    ⭐⭐ THIS IS NOT LAZINESS, IT IS CORRECT: a cache miss is defined
⭐      behaviour (Day 143). ⭐ You gain: no fork, no copy-on-write
⭐      spike, no snapshot latency, no disk, half the memory headroom.
⭐    ⭐⭐ THE ONE COST TO PLAN FOR: A RESTART GIVES YOU A COLD CACHE,
⭐      AND A COLD CACHE IS A THUNDERING HERD AT THE DATABASE (Day 143's
⭐      stampede). ⭐ Mitigate with single-flight, staged warm-up, or
⭐      restarting one node at a time.

⭐⭐ ② SESSIONS ⇒ AOF everysec.
⭐    ⭐ Losing sessions logs everybody out — survivable, visible, and
⭐      bad. ⭐⭐ Losing 1 second of sessions is invisible.

⭐⭐ ③ QUEUES / JOBS ⇒ AOF everysec + replica, ⭐⭐ AND AN IDEMPOTENT
⭐    CONSUMER, because you will replay. ⭐ If losing a job is
⭐    unacceptable, the queue belongs in Postgres (`SKIP LOCKED`) or a
⭐    real broker — ⭐⭐ Redis is the wrong home for the ONLY copy of
⭐    work that must happen.

⭐⭐ ④ COUNTERS / ANALYTICS ⇒ RDB is usually enough. ⭐ Losing 15
⭐    minutes of a rate-limit counter is fine; ⭐⭐ losing 15 minutes of
⭐    billing counters is not — so periodically flush those to Postgres
⭐    and treat Redis as the accumulator, not the ledger.

⭐⭐ ⑤ LOCKS ⇒ ⭐⭐ PERSISTENCE DOES NOT SAVE YOU, AND THIS IS THE CORE
⭐    OF TOMORROW'S ARGUMENT: a failover can promote a replica that
⭐    never received the lock key, ⭐⭐ SO TWO CLIENTS HOLD THE SAME
⭐    LOCK, WITH NO ERROR ANYWHERE. ⭐ Day 207.

⭐⭐ ⑥ PRIMARY DATA ⇒ ⭐⭐ DO NOT. If Redis holds the only copy of
⭐    something you cannot recompute, you have chosen a durability
⭐    ceiling of one second plus failover loss for your source of truth.
⭐    ⭐ (Redis-as-database exists — Redis Enterprise, persistence
⭐      tuned hard — but that is a deliberate, funded architecture, not
⭐      a default.)
```

# Part 5 — ⭐ Operating it: backups, restore, and the setting that stops all writes

```sql
redis> LASTSAVE                     -- ⭐ unix ts of last successful save
redis> INFO persistence
--  rdb_last_bgsave_status:ok       ⭐⭐ WATCH THIS
--  rdb_last_bgsave_time_sec:12     ⭐ how long the fork took
--  rdb_changes_since_last_save     ⭐ your current exposure, in writes
--  aof_last_write_status:ok
--  aof_last_bgrewrite_status:ok
--  aof_rewrite_in_progress:0
--  loading:0                       ⭐⭐ 1 = still replaying, NOT READY
```

```
⭐⭐ THE OUTAGE NOBODY EXPECTS — AND IT IS A DEFAULT:
⭐   `stop-writes-on-bgsave-error yes`   ⭐⭐ ← THE DEFAULT
⭐   ⇒ ⭐⭐ IF A BACKGROUND SAVE FAILS ***ONCE***, REDIS REFUSES ***ALL
⭐     WRITES*** UNTIL A SAVE SUCCEEDS:
⭐        MISCONF Redis is configured to save RDB snapshots, but is
⭐        currently not able to persist on disk.
⭐   ⭐ CAUSES: disk full, ⭐⭐ `vm.overcommit_memory = 0` making fork
⭐     fail (Day 203!), permissions, a read-only filesystem.
⭐   ⇒ ⭐⭐ IT IS TRYING TO PROTECT YOU AND IT PRESENTS AS A TOTAL WRITE
⭐     OUTAGE WITH A MESSAGE NOBODY RECOGNISES. ⭐ Alert on
⭐     `rdb_last_bgsave_status` and on disk free, and decide DELIBERATELY
⭐     whether a cache should have this off.
```

```
⭐⭐ BACKUP AND RESTORE — the actual procedure:
⭐   ⭐ BACKUP: `BGSAVE`, then copy `dump.rdb` to object storage.
⭐     ⭐⭐ THE FILE IS ATOMIC — Redis writes to a temp file and renames,
⭐     so copying it while Redis runs is safe.
⭐   ⭐ VERIFY: `redis-check-rdb dump.rdb` · `redis-check-aof --fix`
⭐     ⭐⭐ (`--fix` truncates a torn tail; it is the standard recovery
⭐     after a hard power loss.)
⭐   ⭐ RESTORE: stop Redis, put the file in `dir`, start. ⭐⭐ Watch
⭐     `loading:1` — the instance answers `-LOADING` to every command
⭐     until it finishes. ⭐ For 20 GB that is minutes, and it is your
⭐     RTO (Day 201).
⭐   ⭐⭐ AND THE SAME RULE AS DAY 201: ***RESTORE IT, ON A SCHEDULE, AND
⭐     TIME IT.*** A dump.rdb nobody has loaded is not a backup.

⭐⭐ THE MANAGED-SERVICE REALITY, because most of you will use one:
⭐   ⭐ ElastiCache: ⭐⭐ APPEND-ONLY IS NOT AVAILABLE ON ALL NODE TYPES
⭐     AND SNAPSHOTS ARE THE DURABILITY STORY. Automatic backups are
⭐     ⭐⭐ OFF BY DEFAULT on many setups. ⭐ Check yours today.
⭐   ⭐ Managed failover is still async ⇒ Part 3 ④ applies unchanged.
⭐   ⭐ `MEMORY` and `CONFIG SET` may be restricted, so plan tuning
⭐     through the parameter group, not the CLI.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Running `SAVE` instead of `BGSAVE` | It snapshots on the main thread and freezes the server. |
| RDB only, with default rules | Up to fifteen minutes of loss. |
| `appendfsync always` "to be safe" | 10–100× throughput loss; you gave up the reason you chose Redis. |
| Assuming AOF means no data loss | `everysec` means up to one second. |
| Forgetting AOF rewrite also forks | The copy-on-write bill is paid on rewrites too. |
| Believing persistence protects a failover | Replication is asynchronous, always. The promoted replica never had the write. |
| Treating `WAIT` as synchronous replication | It confirms receipt in memory and doesn't govern failover selection. |
| Persisting a pure cache | You're paying forks and latency for data whose absence is defined behaviour. |
| Turning persistence off without a warm-up plan | A cold cache is a thundering herd at the database. |
| Keeping the only copy of jobs in Redis | If losing one is unacceptable, use Postgres `SKIP LOCKED` or a real broker. |
| Using Redis as the ledger for billing counters | Accumulate in Redis, flush to Postgres. |
| Not knowing `stop-writes-on-bgsave-error` defaults to yes | One failed save turns into a total write outage with an unfamiliar error. |
| Not alerting on `rdb_last_bgsave_status` | It's the early warning for that outage. |
| Ignoring `loading:1` after a restart | The instance rejects commands until replay finishes — that's your RTO. |
| Assuming a managed Redis has backups on | On many ElastiCache setups they're off by default. |
| Never restoring a dump | Then you don't have a backup, same as Day 201. |

## Interview questions

**Q: How does Redis persistence work, and what would you configure?**

> Two mechanisms. RDB takes point-in-time snapshots by forking and writing a compact binary image —
> small, fast to load, and it's your backup artefact, but you lose everything since the last snapshot,
> which with the default rules is up to fifteen minutes. AOF appends every write command, with
> `appendfsync` as the only dial that really matters: `always` costs you an order of magnitude of
> throughput, `everysec` gives up to one second of loss at essentially full speed, and `no` leaves it
> to the OS. In production I'd run both with `everysec`, because `aof-use-rdb-preamble` means the AOF
> rewrite produces an RDB-format base plus an AOF tail — so you get fast restart *and* one-second
> durability instead of choosing. And I'd remember that the rewrite forks too, so the copy-on-write
> memory bill from the architecture day gets paid on rewrites as well as snapshots.

**Q: With AOF `always`, is Redis as durable as Postgres?**

> No, and the reason people miss is the fourth one. There's no transaction rollback — `MULTI/EXEC` is
> isolation, not atomicity with recovery. There are no constraints. The acknowledgement can precede
> the fsync in some paths. And the decisive one: **Redis replication is asynchronous, always — there
> is no synchronous mode.** The primary acknowledges your write and then sends it to replicas, so if
> it dies in between and a replica is promoted, that write is gone regardless of how you configured
> persistence, because the promoted replica never had it. `WAIT` doesn't fix that: it confirms receipt
> in memory rather than fsync, and it doesn't govern which replica gets promoted. So the honest
> statement of the ceiling is "about one second of loss on a crash, and a small unbounded amount on a
> failover" — which is exactly why money and orders live in Postgres and Redis holds the fast copy.

**Q: You're running Redis purely as a cache. What persistence do you use?**

> None — `appendonly no` and an empty `save`. That's a deliberate choice rather than laziness: a cache
> miss is defined behaviour, so there's nothing to protect. What you gain is real — no fork, so no
> copy-on-write memory spike and no snapshot latency, no disk IO, and roughly half the memory headroom
> you'd otherwise need. The one thing you have to plan for is that a restart gives you a completely
> cold cache, and a cold cache is a thundering herd at the database, which is the stampede problem.
> So the mitigations are single-flight on misses, restarting one node at a time rather than the whole
> tier, and possibly a staged warm-up for the keys you know dominate. I'd also turn off
> `stop-writes-on-bgsave-error` explicitly in that configuration, since there are no saves to fail.

**Q: Redis started refusing writes with a `MISCONF` error. What happened?**

> A background save failed, and `stop-writes-on-bgsave-error` defaults to yes — so Redis refuses every
> write until a save succeeds. It's trying to protect you from accumulating unsaveable data, and it
> presents as a total write outage with a message most people have never seen. The usual causes are a
> full disk, a permissions or read-only filesystem problem, or `fork()` failing because
> `vm.overcommit_memory` is zero and Redis is above half of RAM — which ties straight back to the
> architecture day. The immediate fix is to make saving possible again; the durable fixes are alerting
> on `rdb_last_bgsave_status` and on disk free, and deciding deliberately whether this protection
> makes sense for the workload, because for a pure cache it doesn't.

**Q: What's your Redis restore procedure and how long does it take?**

> `BGSAVE`, then copy `dump.rdb` to object storage — and the file is safe to copy live, because Redis
> writes to a temporary file and renames, so it's atomic. Verify with `redis-check-rdb`, and
> `redis-check-aof --fix` if an AOF tail was torn by a hard power loss, which truncates the incomplete
> tail. To restore: stop Redis, place the file in the data directory, start it — and watch for
> `loading:1` in `INFO persistence`, because the instance answers `-LOADING` to every command until
> replay finishes. For a twenty-gigabyte AOF that's minutes, and that number is your RTO in exactly
> the sense from the replication day. And the same rule applies: a dump nobody has ever loaded is not
> a backup, so it gets restored on a schedule and timed. If it's a managed service I'd check whether
> automatic backups are even enabled, because on several ElastiCache configurations they aren't by
> default.

## Mini task

1. ⭐ Configure RDB only with `save 60 1000`. Write 2,000 keys, kill -9 Redis, restart, and count what survived.
2. ⭐⭐ Repeat with `appendonly yes, appendfsync everysec`. Measure the loss window empirically.
3. ⭐⭐ Benchmark writes with `appendfsync` set to `always`, `everysec` and `no`. Record all three.
4. ⭐ `INCR` a key one million times, check the AOF size, run `BGREWRITEAOF`, check again.
5. ⭐⭐ Load 4 GB, trigger `BGSAVE` under a write-heavy workload, and watch RSS and latency during the fork.
6. ⭐ Confirm `aof-use-rdb-preamble` is on, then inspect the first bytes of the AOF base file.
7. ⭐⭐ Set up a replica, write with `WAIT 1 100`, kill the primary before replication, promote, and prove the write is gone.
8. ⭐⭐ Fill the disk (or make `dir` read-only), trigger a save, and reproduce the `MISCONF` write refusal. Recover from it.
9. ⭐ Restart with a 5 GB AOF and time how long `loading:1` lasts. That's your RTO.
10. ⭐⭐ Corrupt the tail of an AOF file deliberately, then recover it with `redis-check-aof --fix`.
11. ⭐ Turn persistence fully off on a cache instance and measure the latency p99 difference during what would have been a save.
12. ⭐⭐ Restart a cold cache under load and observe the database's QPS spike. Then add single-flight and repeat.

## 🎙️ Articulation drill

**Two minutes: "Can you trust Redis with your data?"**

Start by splitting the question, because it's really two: surviving a restart and surviving a failover.
Cover persistence quickly and correctly — RDB for snapshots and backups, AOF with `everysec` for about
a second of loss, both together with the RDB preamble so you're not choosing between fast restart and
durability, and note that both mechanisms fork. Then make the pivot that shows judgement: **persistence
protects a restart, not a failover, because Redis replication is asynchronous with no synchronous
mode** — the primary acks, then ships, and a promoted replica never had the write. Say `WAIT` confirms
receipt rather than fsync and doesn't govern promotion. Then state the ceiling in one sentence: about a
second of loss on a crash and a small unbounded amount on a failover, which is why money lives in
Postgres and Redis holds the fast copy. Close with the decision table in ten seconds — cache off,
sessions AOF, queues AOF plus idempotent consumers, and locks are a problem persistence cannot solve,
which is tomorrow.
