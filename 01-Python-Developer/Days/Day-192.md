# Part 1 — ⭐⭐ The three algorithms, with their cost models

```
⭐⭐ ① NESTED LOOP
⭐    for each row in OUTER:
⭐        find matching rows in INNER
⭐
⭐    ⭐ COST: O(N) × cost-of-inner-lookup
⭐      ⭐⭐ WITHOUT AN INNER INDEX: O(N × M). 10k × 100k = 1 BILLION.
⭐      ⭐⭐ WITH AN INNER INDEX:    O(N × log M). 10k × 17 = 170k. Fine.
⭐    ⭐ START-UP COST: ~ZERO. First row comes out immediately.
⭐    ⇒ ⭐⭐ THE WINNER WHEN: the outer side is SMALL (tens/hundreds) and
⭐      the inner side is INDEXED on the join key. ⭐⭐ ALSO THE WINNER
⭐      UNDER `LIMIT`, because zero start-up cost beats everything when
⭐      you only want 10 rows.
⭐    ⇒ ⭐⭐ THE CATASTROPHE WHEN: the outer estimate was wrong. This is
⭐      the single most common cause of a query going from 40 ms to 9
⭐      minutes with no code change.

⭐⭐ ② HASH JOIN
⭐    BUILD:  read the SMALLER side, hash it on the join key into memory
⭐    PROBE:  stream the LARGER side, hash each row, look it up
⭐
⭐    ⭐ COST: O(N + M). ⭐ Each side read exactly once.
⭐    ⭐ START-UP COST: HIGH — nothing comes out until the build finishes.
⭐    ⭐⭐ REQUIRES AN EQUALITY CONDITION. `ON a.x < b.y` cannot hash.
⭐    ⭐⭐ REQUIRES MEMORY: the build side must fit in `work_mem`, or it
⭐      SPILLS: `Batches: 8` in the plan means it partitioned to disk and
⭐      read both sides multiple times.
⭐    ⇒ ⭐⭐ THE WINNER WHEN: both sides are large, the condition is
⭐      equality, and you want ALL the rows.

⭐⭐ ③ MERGE JOIN
⭐    sort both sides on the join key, then walk them in lockstep
⭐
⭐    ⭐ COST: O(N + M) IF ALREADY SORTED; otherwise + two sorts.
⭐    ⭐ Handles inequality range joins; ⭐ streams with bounded memory.
⭐    ⇒ ⭐⭐ THE WINNER WHEN: both inputs arrive sorted for free (from
⭐      indexes on the join keys), or the data is enormous and hashing
⭐      would spill anyway.
⭐    ⭐ In practice on OLTP workloads you will see it far less than the
⭐      other two — ⭐⭐ and seeing it WITH two `Sort` nodes underneath
⭐      usually means the planner had no better option, not a good one.
```

```
⭐⭐ THE DECISION TABLE — memorise the shape, not the numbers:

⭐   OUTER   INNER   INDEX ON INNER?  EQUALITY?  LIMIT?  ⇒  CHOICE
⭐   small   large       yes            any       any    ⇒  NESTED LOOP
⭐   small   large       NO             yes       no     ⇒  HASH
⭐   large   large       —              yes       no     ⇒  HASH
⭐   large   large       —              yes       no     ⇒  MERGE if both
⭐                                                          pre-sorted
⭐   any     any         —              NO        —      ⇒  NESTED LOOP
⭐                                                          or MERGE
⭐                                                          (never HASH)
⭐   any     any         —              any       YES    ⇒  NESTED LOOP
⭐                                                          becomes far
⭐                                                          more likely
```

# Part 2 — ⭐ Join order, and the query that gets a random plan

```
⭐⭐ A JOIN OF N TABLES HAS UP TO N! ORDERINGS, AND THE ORDER MATTERS
⭐   ENORMOUSLY: joining the two most selective tables first keeps every
⭐   intermediate result small.

⭐   `join_collapse_limit` (default 8) — ⭐ above this many tables in one
⭐        FROM, the planner STOPS reordering explicit JOINs and uses the
⭐        order you wrote.
⭐   `from_collapse_limit` (default 8) — the same for subqueries.
⭐   `geqo_threshold`     (default 12) — ⭐⭐ above 12 relations, Postgres
⭐        switches to a ***GENETIC ALGORITHM***. It is STOCHASTIC.
⭐        ⇒ ⭐⭐ THE SAME QUERY CAN GET A DIFFERENT PLAN ON DIFFERENT
⭐          RUNS. ⭐ If you have a 15-table report that is "sometimes
⭐          slow", this is very often why, and no amount of indexing
⭐          fixes it.
⭐   ⇒ ⭐⭐ FIXES, IN ORDER OF PREFERENCE: split the query; materialise an
⭐     intermediate result; raise `geqo_threshold`/`join_collapse_limit`
⭐     for that session (planning time grows fast); or `SET geqo = off`
⭐     and accept exhaustive planning if the table count is survivable.
```

# Part 3 — ⭐⭐ The four pathologies

## ⭐⭐ ① The nested loop with a lying outer side — the 40 ms → 9 min case

```
⭐   ->  Nested Loop  (actual time=0.1..540000 rows=190000 loops=1)
⭐         ->  Seq Scan on a  (cost … rows=40) (actual … rows=190000)
⭐                                    ^^^^^^              ^^^^^^^^^^
⭐                                    ⭐⭐ THE LIE       ⭐⭐ THE TRUTH
⭐         ->  Index Scan on b  (actual time=2.8 rows=1 loops=190000)
⭐
⭐⭐ THE PLANNER WAS *CORRECT*: 40 index lookups is the cheapest plan for
⭐   40 rows. ⭐⭐ FIX THE ESTIMATE, NOT THE JOIN.
⭐   ⭐ ANALYZE · CREATE STATISTICS · SET STATISTICS 1000 · an expression
⭐     index to give the planner stats for a computed predicate.
⭐ ⭐⭐ AND THE EMERGENCY LEVER, for when it is 3 a.m. and you need the
⭐   site back: `SET LOCAL enable_nestloop = off;` around that one
⭐   statement. ⭐⭐ IT IS A TOURNIQUET, NOT A TREATMENT — write the
⭐   ticket to fix the estimate before you close the incident.
```

## ⭐ ② The hash join that spilled

```
⭐   Hash Join … ⭐⭐ Buckets: 16384  Batches: 32  Memory Usage: 4096kB
⭐                                   ^^^^^^^^^^^ ⭐⭐ >1 MEANS DISK
⭐   ⇒ the build side did not fit in `work_mem`, so both sides were
⭐     partitioned to temp files and re-read per batch.
⭐   ⭐ FIXES: `SET LOCAL work_mem` (Day 191's warning applies) · reduce
⭐     the build side by filtering EARLIER · select fewer columns so rows
⭐     are narrower · ⭐⭐ or fix the estimate, because the planner chose
⭐     the build side by size and may have picked the wrong one.
```

## ⭐ ③ The join that was never a join — ⭐⭐ `LEFT JOIN` + `WHERE`

```sql
-- ⭐⭐ THIS IS NOT A PERFORMANCE BUG. IT SILENTLY CHANGES YOUR ANSWER.
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';          -- ⭐⭐ ← DESTROYS THE LEFT JOIN

-- ⭐ WHY: LEFT JOIN produces NULLs for users with no orders. Then
--   `WHERE o.status = 'paid'` evaluates NULL = 'paid' → ⭐⭐ UNKNOWN →
--   the row is DROPPED (Day 187!).
-- ⇒ ⭐⭐ YOU WROTE A LEFT JOIN AND EXECUTED AN INNER JOIN. The planner
--   even rewrites it as one — you will see `Hash Join`, not `Hash Left
--   Join`, in the plan, which is the tell.

-- ✅ THE FIX — the predicate belongs in the ON clause:
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid'
-- ⭐⭐ ON  = "which rows may pair"  (applied DURING the join)
-- ⭐⭐ WHERE = "which result rows survive" (applied AFTER)
-- ⭐ For an INNER JOIN they are equivalent. ⭐⭐ FOR AN OUTER JOIN THEY
--   ARE COMPLETELY DIFFERENT, and this is the #1 SQL bug in reporting
--   code — "users with no paid orders" quietly vanish from the report.
-- ⭐ The exception: `WHERE o.id IS NULL` after a LEFT JOIN is the
--   deliberate ANTI-JOIN idiom, and is correct.
```

## ⭐⭐ ④ Row multiplication — the wrong number, not the slow query

```
⭐   orders ⋈ order_items (3) ⋈ payments (2)
⭐   ⇒ ⭐⭐ 3 × 2 = 6 ROWS FOR ONE ORDER.
⭐   ⇒ ⭐⭐ SUM(items.amount) IS NOW DOUBLED. SUM(payments.amount) IS
⭐     TRIPLED. ⭐ And it returns plausible numbers, so it ships.
⭐
⭐   ⭐⭐ THIS IS THE SAME FACT AS THREE THINGS YOU ALREADY KNOW:
⭐     ⭐ Day 171: `select_related` (JOIN) vs `prefetch_related` (2nd
⭐       query) — ⭐⭐ prefetch exists BECAUSE of row multiplication.
⭐     ⭐ Day 172: two `Count()` annotations both silently wrong.
⭐     ⭐ Day 136: SQLAlchemy's `joinedload` vs `selectinload` — same
⭐       distinction, same reason.
⭐   ⇒ ⭐⭐ THE RULE: JOIN TO AT MOST ONE MULTI-VALUED RELATION PER
⭐     QUERY. For a second one, use a subquery, a lateral, or a second
⭐     round trip.
⭐   ⭐ Fixes: `COUNT(DISTINCT x)` (works, and is slow), scalar
⭐     subqueries, or ⭐⭐ aggregate each side in its own subquery and
⭐     join the aggregates — which is the correct and fast answer.
```

# Part 4 — ⭐ Semi-joins, anti-joins, and `LATERAL`

```sql
-- ⭐⭐ SEMI-JOIN — "does a match exist?" Returns each LEFT row AT MOST
--    ONCE, no matter how many matches. ⭐ NO row multiplication.
SELECT * FROM users u WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- ⭐ vs `JOIN orders ... GROUP BY u.id` — same answer, more work, and a
--   distinct step you have to remember.

-- ⭐⭐ ANTI-JOIN — "does no match exist?" Day 187's NULL-safe form.
SELECT * FROM users u WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- ⭐⭐ NEVER `NOT IN` WITH A NULLABLE COLUMN. It returns zero rows.

-- ⭐⭐ LATERAL — the "top N per group" tool, and the answer to a question
--    people otherwise solve with a window function and a filter.
SELECT u.id, recent.*
FROM users u
CROSS JOIN LATERAL (
    SELECT o.id, o.total_cents
    FROM orders o
    WHERE o.user_id = u.id            -- ⭐⭐ CAN SEE `u` — that is the
    ORDER BY o.created_at DESC        --    whole point of LATERAL
    LIMIT 3                           -- ⭐⭐ 3 PER USER
) recent;
-- ⭐ With an index on (user_id, created_at DESC) this is 3 leaf reads
--   per user. ⭐⭐ The window-function version
--   (`row_number() OVER (PARTITION BY ...) <= 3`) must SORT EVERY ORDER
--   IN THE TABLE first. On a big table the lateral is 100× faster.
-- ⭐ `CROSS JOIN LATERAL` drops users with no orders; `LEFT JOIN LATERAL
--   ... ON true` keeps them.
```

# Part 5 — ⭐⭐ Postgres has no hints, and that is on purpose

```
⭐   Oracle: /*+ USE_NL(a b) */    MySQL: STRAIGHT_JOIN
⭐   ⭐⭐ POSTGRES: NOTHING. DELIBERATELY.
⭐   ⭐ The argument: a hint is a guess frozen at write time. Data
⭐     distribution changes; the hint does not. Every hint is a future
⭐     incident, and it hides the real problem (a bad estimate) instead
⭐     of surfacing it.
⭐   ⭐ The counter-argument, which is fair: at 3 a.m. you want a lever.
⭐   ⇒ ⭐ `pg_hint_plan` exists as an extension if you truly need one.

⭐⭐ THE SANCTIONED LEVERS, IN THE ORDER YOU SHOULD TRY THEM:
⭐   1. ⭐⭐ FIX THE ESTIMATE — ANALYZE, CREATE STATISTICS, SET
⭐        STATISTICS, an expression index. ⭐ 80% of cases end here.
⭐   2. ⭐ ADD OR REORDER AN INDEX so the good plan becomes obviously
⭐        cheap (Day 190).
⭐   3. ⭐ REWRITE THE QUERY — EXISTS instead of IN, a lateral instead of
⭐        a window, aggregate-then-join instead of join-then-aggregate.
⭐   4. ⭐⭐ AN OPTIMISATION FENCE, when you genuinely know better:
⭐        `WITH x AS MATERIALIZED (...)` — ⭐ the modern, explicit way.
⭐        `OFFSET 0` in a subquery — ⭐⭐ the old folk trick; it blocks
⭐          subquery pull-up. Works, but write a comment or the next
⭐          person deletes it.
⭐   5. ⭐⭐ `SET LOCAL enable_nestloop = off` — TOURNIQUET ONLY, scoped
⭐        to one statement, with a ticket attached.
⭐   ⭐⭐ AND NEVER: setting `enable_*` in postgresql.conf. You have then
⭐      globally banned a strategy that is correct for a thousand other
⭐      queries.
```

```python
# ⭐ Where this touches your Python, concretely:
session.execute(
    text("SET LOCAL work_mem = '256MB'")          # ⭐ per-transaction
)
# ⭐⭐ `SET LOCAL` REQUIRES A TRANSACTION and resets at commit — which is
#    exactly what you want, and why plain `SET` from a pooled connection
#    is a bug: it leaks into whoever gets that connection next.
# ⭐ Same hazard as Day 186's prepared statements through PgBouncer, and
#   Day 160's tenant `SET` for row-level security. One rule, three days:
#   ⭐⭐ NEVER LEAVE SESSION STATE ON A POOLED CONNECTION.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Thinking `JOIN` is one operation | Three algorithms with three cost curves, chosen by a row estimate. |
| Blaming the nested loop | It was correct for the estimated rows. Fix the estimate. |
| Ignoring `Batches: > 1` on a hash join | The build side spilled to disk and both sides were re-read. |
| A `WHERE` predicate on the right table of a `LEFT JOIN` | Silently becomes an inner join. Move it into `ON`. |
| Joining two one-to-many relations and aggregating | Rows multiply; every aggregate is silently inflated. |
| Fixing multiplication with `COUNT(DISTINCT)` only | Works, but slow. Aggregate each side in a subquery and join the aggregates. |
| `NOT IN` with a nullable column | Zero rows, silently. Use `NOT EXISTS`. |
| `row_number() OVER (...) <= 3` for top-N-per-group | Sorts the whole table. `LATERAL` with a limit reads three rows per group. |
| A 15-table report that's "sometimes slow" | Above `geqo_threshold` the planner is stochastic. Split the query. |
| Setting `enable_nestloop = off` in postgresql.conf | You've globally banned a strategy that's right for a thousand queries. |
| Using `OFFSET 0` without a comment | It's an intentional optimisation fence and looks like dead code. |
| Plain `SET` on a pooled connection | It leaks to the next borrower. `SET LOCAL` inside a transaction. |

## Interview questions

**Q: What are the three join algorithms and when is each right?**

> Nested loop iterates the outer side and looks up matches in the inner — it's `O(N)` times the inner
> lookup cost, so it's excellent when the outer side is small and the inner side is indexed on the
> join key, and catastrophic when the outer estimate was wrong. It also has near-zero start-up cost,
> which makes it the natural choice under a `LIMIT`. Hash join builds a hash table from the smaller
> side and probes it with the larger — `O(N + M)`, each side read once, which makes it the workhorse
> for large-to-large equality joins, but it needs an equality condition and it needs the build side to
> fit in `work_mem` or it partitions to disk. Merge join walks two sorted inputs in lockstep, which is
> great when indexes deliver both sides already sorted, and handles range conditions that hashing
> can't. In OLTP work you mostly see nested loop and hash, and a merge join sitting on top of two
> explicit sort nodes usually means the planner ran out of better options.

**Q: A query went from 40 milliseconds to nine minutes with no code change. What happened?**

> Almost always a nested loop whose outer estimate collapsed. The scan estimated a few dozen rows so
> the planner picked a nested loop, which is genuinely the cheapest plan for a few dozen rows, and the
> scan actually returned a couple of hundred thousand — so the inner index scan ran a couple of hundred
> thousand times. `EXPLAIN ANALYZE` shows it as a huge `loops` count on the inner node. The trigger is
> usually data change plus stale statistics: a bulk load, a backfill, or a tenant that grew, with
> autoanalyze not having caught up. So the fix is the estimate — `ANALYZE`, or `CREATE STATISTICS` if
> the predicate involves correlated columns, or raising the statistics target on a skewed column. If
> the site is down while I'm diagnosing, `SET LOCAL enable_nestloop = off` around that one statement
> is a legitimate tourniquet, but it goes in with a ticket to fix the real cause, and never in the
> config file.

**Q: What does `LEFT JOIN orders ... WHERE orders.status = 'paid'` do?**

> It quietly becomes an inner join. The left join produces NULL columns for users with no matching
> orders, then the `WHERE` compares NULL to `'paid'`, which is UNKNOWN rather than true, and `WHERE`
> only keeps true — so exactly the rows the left join was written to preserve get dropped. You can
> see it in the plan: the node says `Hash Join`, not `Hash Left Join`, because the planner recognises
> the predicate and rewrites it. The fix is that the predicate belongs in `ON`, not `WHERE`, and the
> distinction is worth stating precisely: `ON` decides which rows may pair during the join, `WHERE`
> decides which result rows survive afterwards. For inner joins they're interchangeable; for outer
> joins they're completely different, and this is the most common correctness bug in reporting SQL —
> "users with no paid orders" silently disappear from a report about users. The deliberate exception
> is `WHERE o.id IS NULL` after a left join, which is the anti-join idiom.

**Q: Why does joining two one-to-many relations give wrong totals?**

> Because the join multiplies rows. An order with three line items and two payments produces six rows,
> so summing line item amounts triples them and summing payments doubles them — and it returns
> plausible numbers rather than an error, so it ships and someone notices months later that a
> dashboard is inflated. It's the same underlying fact as three things I already knew from the
> framework layer: it's why `prefetch_related` and `selectinload` exist as alternatives to a join,
> and it's why two `Count()` annotations over different relations are both wrong. The rule I follow is
> to join at most one multi-valued relation per query. If I need two, I aggregate each in its own
> subquery and join the aggregates, which is both correct and fast — `COUNT(DISTINCT)` also fixes the
> correctness but pays for deduplicating a cartesian product.

**Q: Postgres has no query hints. Is that a problem?**

> It's a deliberate design position and I mostly agree with it. A hint is a guess frozen at the moment
> you wrote the query, and data distribution changes while the hint doesn't — so every hint is a future
> incident, and worse, it hides the real problem, which is nearly always a bad row estimate. The
> sanctioned levers are better in that order: fix the estimate with `ANALYZE`, extended statistics, a
> higher statistics target or an expression index — which resolves most cases; then indexing so the
> good plan is obviously cheap; then rewriting, like `EXISTS` instead of `IN` or a lateral instead of
> a window function; then an explicit fence with `WITH ... AS MATERIALIZED` when I genuinely know
> something the planner can't; and only then session-scoped `enable_*` as an incident tourniquet.
> `pg_hint_plan` exists if you truly need hints, but I'd want to know why the estimate is wrong first.

## 🎙️ Articulation drill

**Two minutes: "How does Postgres join two tables?"**

and probe, sort and walk — and attach the condition each needs: an indexed inner side, an equality
plus memory, pre-sorted inputs. Then make the point that matters: **the choice is made from a row
estimate, so a join problem is usually an estimate problem**, and give the cascade in one sentence —
