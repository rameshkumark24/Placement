# Part 1 — ⭐⭐ Two philosophies, stated fairly

```
⭐⭐ FASTAPI: A LIBRARY THAT COMPOSES.
⭐   ⭐ you choose the ORM, the migration tool, the auth, the admin, the
⭐        settings library, the background worker
⭐   ⭐ + ⭐⭐ nothing you did not choose · every piece replaceable · the
⭐        composition IS your architecture
⭐   ⭐ − ⭐⭐ YOU MAKE FIFTEEN DECISIONS BEFORE WRITING A FEATURE, and Days
⭐        130–169 were largely those decisions. ⭐ Every team makes them
⭐        differently, so every FastAPI codebase is a different shape.
⭐
⭐⭐ DJANGO: A FRAMEWORK THAT PROVIDES.
⭐   ⭐ ORM, migrations, auth with users/groups/permissions, sessions, admin,
⭐        forms, templates, i18n, caching, email, CSRF, security middleware,
⭐        a test client — ⭐⭐ ALL IN ONE VERSIONED, JOINTLY-TESTED PACKAGE
⭐   ⭐ + ⭐⭐ THE INTEGRATION IS THE PRODUCT. `python manage.py startproject`
⭐        to a working authenticated CRUD app with an admin UI is under an
⭐        hour. ⭐ In FastAPI that is a week.
⭐   ⭐ + ⭐⭐ ANY DJANGO CODEBASE IS RECOGNISABLE TO ANY DJANGO DEVELOPER.
⭐        ⭐ That is a genuine, underrated economic property.
⭐   ⭐ − ⭐⭐ REPLACING A PIECE IS HARD ON PURPOSE. Swap the ORM and you lose
⭐        the admin, `ModelForm`, DRF's `ModelSerializer`, the auth system's
⭐        models and half the ecosystem. ⭐ The integration is also the trap.
⭐   ⭐ − ⭐ async is retrofitted (Day 178), and the ORM is where it shows.
⭐
⭐   ⇒ ⭐⭐ THE HONEST SUMMARY: **DJANGO OPTIMISES FOR THE MEDIAN FEATURE OF A
⭐        CONTENT-AND-CRUD PRODUCT. FASTAPI OPTIMISES FOR THE SHAPE YOU
⭐        CHOOSE.** ⭐ Neither statement is a criticism, and an interviewer
⭐        asking "which is better" is testing whether you know that.
```

```
⭐⭐ WHERE DJANGO GENUINELY WINS — say these, they are concrete:
⭐  1. ⭐⭐ THE ADMIN (Day 177). ⭐ A working back-office for every model, free.
⭐       ⭐⭐ For an internal tool or an early-stage product this is often
⭐       WEEKS of saved work, and there is no FastAPI equivalent.
⭐  2. ⭐⭐ AUTH THAT ALREADY EXISTS — users, groups, permissions, password
⭐       hashing with upgrade paths, password reset flows, session handling.
⭐       ⭐ You built all of that across Days 113–118 and 165.
⭐  3. ⭐ MIGRATIONS THAT UNDERSTAND YOUR MODELS NATIVELY (Day 173).
⭐  4. ⭐⭐ SERVER-RENDERED PAGES. ⭐ If the product is pages rather than an
⭐       API, Django's templates + forms + CSRF is a complete answer and
⭐       FastAPI has no story at all.
⭐  5. ⭐ THE ECOSYSTEM: `django-allauth`, `django-guardian`,
⭐       `django-storages`, `django-filter`, `wagtail`. ⭐⭐ Batteries you did
⭐       not have to evaluate.
⭐
⭐⭐ WHERE FASTAPI GENUINELY WINS:
⭐  1. ⭐⭐ ASYNC I/O AT SCALE — many concurrent slow calls (Day 134).
⭐  2. ⭐ TYPED, GENERATED OPENAPI as a first-class product (Day 126).
⭐  3. ⭐ SMALL SERVICES where Django's floor is more than the whole job.
⭐  4. ⭐⭐ WHEN THE DATA MODEL IS NOT RELATIONAL-CRUD — ⭐ event streams, ML
⭐       inference, proxies, gateways. ⭐⭐ Django's gravity is toward models
⭐       and you will be fighting it the whole way.
```

# Part 2 — ⭐ The vocabulary, translated

```
⭐⭐ EVERY DJANGO CONCEPT MAPS TO SOMETHING YOU BUILT. LEARN THE MAP AND THE
⭐   FRAMEWORK STOPS BEING STRANGE:

⭐   DJANGO                    ⇒ WHAT YOU ALREADY KNOW
⭐   ─────────────────────────────────────────────────────────────
⭐   project                   ⭐ your `src/app/` package
⭐   app                       ⭐ a router + models + services module
⭐   `settings.py`             ⭐ `pydantic-settings` (⭐⭐ but see Part 4 —
⭐                                it is a MODULE, not a validated object)
⭐   `urls.py`                 ⭐ `APIRouter` + `include_router`
⭐   view                      ⭐ a path operation function
⭐   model                     ⭐ a SQLAlchemy model
⭐   `Model.objects`           ⭐⭐ the repository — ⭐ BUILT IN, and therefore
⭐                                everywhere (Part 3)
⭐   `QuerySet`                ⭐ a lazy `select()` (Day 171)
⭐   middleware                ⭐ Starlette middleware ⭐⭐ (different contract)
⭐   `ModelForm`               ⭐ a Pydantic model bound to a table
⭐   serializer (DRF)          ⭐ a Pydantic model that ALSO writes (Day 175)
⭐   signals                   ⭐⭐ event handlers — ⭐ and mostly a trap (Part 5)
⭐   `manage.py`               ⭐ your CLI + Alembic + a shell
⭐
⭐   ⇒ ⭐⭐ THE ONE WITH NO EQUIVALENT: **THE ADMIN.** ⭐ There is nothing in
⭐        the FastAPI world that generates a full CRUD interface with search,
⭐        filters, permissions and audit from your models. ⭐⭐ That absence is
⭐        most of why Django is still chosen for new products.
```

```
⭐⭐ "MTV" — MODEL, TEMPLATE, VIEW. ⭐ Django's name for MVC, and the naming
⭐   confuses everyone once:
⭐   ⭐ Django's VIEW = MVC's CONTROLLER (it handles the request)
⭐   ⭐ Django's TEMPLATE = MVC's VIEW (it renders)
⭐   ⭐ Django's MODEL = MVC's MODEL, plus ⭐⭐ the data-access layer, because
⭐        `objects` lives on it.
⭐   ⇒ ⭐ Do not spend time on the acronym. ⭐⭐ Spend it on the last clause:
⭐        DATA ACCESS LIVES ON THE MODEL, and that single design choice
⭐        explains most of what follows.
```

# Part 3 — ⭐⭐ The consequence of `Model.objects`

```
⭐⭐ IN YOUR CAPSTONE, QUERIES LIVED IN REPOSITORIES (Day 139) — ⭐ one file
⭐   per table, tenant scoping in one place, loading strategy in one place.

⭐⭐ IN DJANGO, `Order.objects.filter(...)` WORKS FROM ANYWHERE:
⭐   ⭐ a view, a template, a management command, a signal handler, a serializer
⭐   ⇒ ⭐⭐ THIS IS DJANGO'S GREATEST CONVENIENCE AND ITS GREATEST LIABILITY,
⭐        AND IT IS THE SAME PROPERTY.
⭐
⭐   ⭐ + a feature is one file and twenty lines
⭐   ⭐ − ⭐⭐ THE TENANT FILTER CAN BE FORGOTTEN IN ANY OF THOSE PLACES
⭐        (Day 160), ⭐ the `select_related` can be missing in any of them
⭐        (Day 171), and ⭐⭐ "why is this endpoint slow" has no single file to
⭐        open.
⭐   ⭐ − ⭐⭐ A TEMPLATE CAN TRIGGER A DATABASE QUERY. ⭐ `{% for o in
⭐        user.orders.all %}` is N queries authored by someone editing HTML.
⭐
⭐⭐ THE DJANGO-NATIVE ANSWERS, AND THEY ARE GOOD ONES:
⭐   ⭐ **CUSTOM MANAGERS AND QUERYSETS** — ⭐⭐ this IS the repository, and
⭐        Django's idiomatic form of it:
⭐        `Order.objects.for_user(u).with_items()`
⭐        ⭐ chainable, reusable, testable, and it puts the scoping and the
⭐        loading strategy in ONE place.
⭐   ⭐ **`Meta.base_manager_name` / a default manager that always filters**
⭐        for tenancy — ⭐⭐ though be careful: a default manager that filters
⭐        can hide rows from the admin and from cascade deletes.
⭐   ⭐ **`.only()` / `lazy` discipline + `nplusone` or `django-zen-queries`**
⭐        to make an unexpected query an ERROR (⭐ Day 136's `lazy="raise"`).
⭐
⭐   ⇒ ⭐⭐ SAY THIS IN AN INTERVIEW: "Django's active-record style trades
⭐        locality for convenience. ⭐ I get the locality back with custom
⭐        QuerySets, and I make the failure loud with query-count assertions."
⭐        ⭐⭐ That is a senior answer; "Django is too magic" is not.
```

# Part 4 — ⭐ The request cycle, and settings

```
⭐⭐ THE PATH OF A REQUEST — compare it to Day 109's ASGI and Day 110's
⭐   middleware order:

⭐   WSGI/ASGI server (gunicorn + uvicorn worker)
⭐     → `django.core.handlers`
⭐     → ⭐⭐ MIDDLEWARE, IN ORDER (request phase, top → bottom)
⭐     → URL RESOLUTION                     ⭐ regex/path, first match wins
⭐     → view middleware hooks
⭐     → ⭐ THE VIEW  (returns an `HttpResponse`)
⭐     → ⭐⭐ MIDDLEWARE, IN REVERSE (response phase, bottom → top)
⭐     → server
⭐
⭐   ⇒ ⭐⭐ SAME ONION AS STARLETTE, WITH ONE IMPORTANT DIFFERENCE: Django
⭐        middleware runs BEFORE URL resolution too — ⭐ so Day 140's argument
⭐        holds here as well. ⭐⭐ AUTH BY MIDDLEWARE CANNOT KNOW THE VIEW; put
⭐        authorisation on the view (a decorator or a DRF permission class),
⭐        not in middleware.
⭐   ⇒ ⭐ AND ORDER IS CORRECTNESS, EXACTLY AS BEFORE: `SecurityMiddleware`
⭐        first, ⭐⭐ `SessionMiddleware` BEFORE `AuthenticationMiddleware`
⭐        (auth reads the session), ⭐ `CsrfViewMiddleware` after session.
⭐        ⭐⭐ Getting this order wrong produces errors that look like bugs in
⭐        Django.
```

```python
# ⭐⭐ settings.py IS A PYTHON MODULE, AND THAT IS A REAL WEAKNESS (Day 150)
DEBUG = os.environ.get("DEBUG", "False") == "True"     # ⭐ string comparison, by hand
ALLOWED_HOSTS = os.environ.get("ALLOWED_HOSTS", "").split(",")
```

```
⭐⭐ WHAT YOU LOSE COMPARED TO `pydantic-settings`, AND WHAT TO DO:
⭐   ⭐ NO VALIDATION — a typo'd env var silently uses the default (Day 150)
⭐   ⭐ NO TYPES — everything is a string until you convert it
⭐   ⭐ NO `extra="forbid"` — ⭐⭐ `ALOWED_HOSTS = [...]` is a valid module
⭐        attribute that nothing reads, and nothing will ever tell you
⭐   ⭐ ⭐⭐ IT EXECUTES AT IMPORT, so an error is an import error, and
⭐        settings can (and do) get read at import time all over the codebase
⭐
⭐   ⇒ ⭐ USE `django-environ` or `pydantic-settings` INSIDE `settings.py`,
⭐        ⭐⭐ and add boot-time assertions:
⭐        `if not DEBUG: assert ALLOWED_HOSTS and SECRET_KEY != "dev"`
⭐   ⇒ ⭐⭐ AND THE THREE THAT ARE ACTUAL SECURITY CONTROLS:
⭐        ⭐ `DEBUG = False` — ⭐⭐ True in production renders every local
⭐          variable, including settings, to whoever triggers an error
⭐        ⭐ `ALLOWED_HOSTS` — ⭐⭐ empty with `DEBUG=False` refuses everything
⭐          (a good failure); wrong, and you enable Host-header poisoning of
⭐          password-reset links
⭐        ⭐ `SECRET_KEY` — signs sessions and password-reset tokens.
⭐          ⭐⭐ A leaked one is a forged-session vulnerability (Day 116's JWT
⭐          key, in a different costume).
```

# Part 5 — ⭐⭐ The three pieces of Django magic, judged

```
⭐⭐ 1. THE APP REGISTRY AND IMPORT ORDER.
⭐   ⭐ `django.setup()` populates a registry; ⭐⭐ models cannot be imported
⭐     before it. ⭐ That is why a script that imports a model at the top and
⭐     is run directly explodes, and why you use `manage.py` or
⭐     `django.setup()` first.
⭐   ⇒ ⭐ Understand it once, and `AppRegistryNotReady` stops being mysterious.

⭐⭐ 2. SIGNALS — and this is the one to have an opinion about.
⭐   ⭐ `post_save`, `pre_delete`: hooks fired implicitly on model events.
⭐   ⭐ + genuinely useful for CROSS-CUTTING concerns you do not own —
⭐        ⭐ invalidating a cache, auditing, third-party integrations.
⭐   ⭐ − ⭐⭐ THEY MAKE CONTROL FLOW INVISIBLE. `order.save()` may fire six
⭐        handlers in three apps. ⭐ You cannot see them from the call site,
⭐        stack traces are confusing, ⭐⭐ and ORDERING IS UNDEFINED.
⭐   ⭐ − ⭐⭐ THEY DO NOT FIRE FOR `bulk_create`, `bulk_update`,
⭐        `queryset.update()` OR `queryset.delete()` — ⭐ so business logic in
⭐        a signal is SILENTLY SKIPPED the day someone optimises a loop into a
⭐        bulk operation. ⭐⭐ That is a genuinely nasty class of bug.
⭐   ⇒ ⭐⭐ RULE: NO BUSINESS LOGIC IN SIGNALS. ⭐ If it must happen, call it
⭐        explicitly from a service function. ⭐⭐ Use signals only for things
⭐        that are optional and observational.
⭐   ⇒ ⭐ And `transaction.on_commit()` is the exception worth loving —
⭐        ⭐⭐ Day 142's after-commit hook, built in and correct.

⭐⭐ 3. THE DEFAULT MANAGER AND IMPLICIT QUERIES.
⭐   ⭐ attribute access crosses a foreign key and queries (Day 136's N+1).
⭐   ⭐⭐ Django will do this cheerfully and silently, in templates too.
⭐   ⇒ ⭐ Day 171 is entirely about making it visible.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| "Django is too magic" | A weak answer. Name the specific mechanisms and how you'd contain each. |
| "FastAPI is faster so it's better" | Different axes. Django's win is integration and the admin; FastAPI's is async I/O and typed contracts. |
| Queries scattered across views, templates and signals | Use custom managers/QuerySets — that *is* Django's repository. |
| Auth in middleware | Middleware runs before URL resolution, so it can't know the view. |
| Middleware in the wrong order | `SessionMiddleware` must precede `AuthenticationMiddleware`; the errors look like Django bugs. |
| `settings.py` with raw `os.environ` | No validation, no types, and a typo'd name is silently ignored. |
| `DEBUG=True` in production | Renders every local variable, including settings, to whoever triggers an error. |
| Empty or wrong `ALLOWED_HOSTS` | Host-header poisoning of password-reset links. |
| Treating `SECRET_KEY` as ordinary config | It signs sessions and reset tokens — a leak is forged-session capability. |
| Business logic in signals | Invisible control flow, undefined ordering, and skipped entirely by bulk operations. |
| Assuming signals fire on `bulk_create` / `queryset.update()` | They don't. Logic silently disappears when someone optimises a loop. |
| Importing models before `django.setup()` | `AppRegistryNotReady` — the registry has to be populated first. |

## Interview questions

**Q: Django or FastAPI?**

> Different optimisation targets, and the honest answer names both. Django ships an ORM, migrations,
> an auth system with users, groups and permissions, sessions, forms, CSRF, caching and an admin as
> one jointly-tested package — so `startproject` to a working authenticated CRUD app with a
> back-office is under an hour, where in FastAPI that's a week of decisions. That integration is the
> product. The cost is that replacing a piece is hard on purpose: swap the ORM and you lose the
> admin, `ModelForm`, DRF's `ModelSerializer` and half the ecosystem. FastAPI wins on async I/O at
> scale, typed OpenAPI as a first-class artefact, small services where Django's floor exceeds the
> whole job, and anything whose data model isn't relational CRUD — because Django's gravity is toward
> models and you'll be fighting it. My rule: pages, back-office, or a CRUD product with a team →
> Django. Async-heavy API, gateway, or an unusual data model → FastAPI.

**Q: What's the biggest architectural difference in practice?**

> Where data access lives. In my FastAPI service queries live in repositories — one file per table,
> so tenant scoping has one place it can be forgotten and the eager-loading strategy has one place to
> live. Django puts `objects` on the model, so `Order.objects.filter(...)` works from a view, a
> template, a management command or a signal handler. That's simultaneously its greatest convenience
> and its greatest liability, and it's the same property: a feature is twenty lines in one file, but
> the tenant filter can be missing anywhere, and a *template* can trigger queries — `{% for o in
> user.orders.all %}` is an N+1 authored by someone editing HTML. The Django-native answer is custom
> managers and QuerySets, which is genuinely the repository pattern in Django's idiom, plus
> query-count assertions so the failure is loud.

**Q: What's your view on Django signals?**

> Useful for cross-cutting concerns I don't own — cache invalidation, audit, integrations — and I'd
> keep business logic out of them entirely. Two reasons. They make control flow invisible: `save()`
> can fire six handlers across three apps that you can't see from the call site, with undefined
> ordering. And more dangerously, they don't fire for `bulk_create`, `bulk_update`,
> `queryset.update()` or `queryset.delete()` — so the day someone optimises a loop into a bulk
> operation, business logic silently stops happening, with no error anywhere. If it must happen, I
> call it explicitly from a service function. The one signal-adjacent thing I do love is
> `transaction.on_commit`, which is the after-commit hook that solves half the dual-write problem,
> built in and correct.

**Q: Which settings are security controls rather than configuration?**

> Three. `DEBUG` — if it's True in production, an error page renders every local variable in the
> frame, including your settings object, to whoever triggered the error. `ALLOWED_HOSTS` — empty with
> `DEBUG=False` refuses everything, which is a good failure, but a wrong value enables Host-header
> poisoning, where an attacker's Host makes your password-reset email link point at their domain.
> And `SECRET_KEY`, which signs sessions and password-reset tokens — a leak is forged-session
> capability, exactly like a leaked JWT signing key. I'd also note that `settings.py` being a plain
> module means none of this is validated, so I put boot-time assertions in it or use
> `pydantic-settings` inside it, because a typo'd setting name is just an unused module attribute
> that nothing will ever complain about.

## 🎙️ Articulation drill

**Two minutes: "You've used both — which would you pick for our product?"**

Refuse the framing that one is better, then be decisive anyway. Name what Django actually ships and
say the honest thing: the integration is the product, and `startproject` to a working back-office in
an hour is a real economic fact, not a toy demo. Name the cost with a concrete example — swap the ORM
and you lose the admin, `ModelForm` and `ModelSerializer`. Then give your rule: pages, back-office,
or CRUD with a team → Django; async-heavy, gateway, or a non-relational data model → FastAPI. Close
on the difference that actually changes your code: **data access lives on the model, so queries can
happen anywhere — including in a template — and the fix is custom QuerySets plus query-count
assertions**, which is the same locality argument you made for repositories.
