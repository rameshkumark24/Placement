# Day 444 ♻️

**P-444** · ♻️ **Idempotency in a non-deterministic system** — ⭐⭐ retry no longer replays

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every retry pattern you learned in Stage 12 rested on one unstated
> assumption — that retrying replays the same request — and with a model in the loop it does not, so an
> idempotency key derived from the content of a request is now derived from a coin flip.**

---

# Part 1 — ⭐⭐ The assumption that just broke

```
⭐ ***STAGE 12'S MODEL OF A RETRY:***
⭐   ⭐ send request R → timeout → ⭐ the third outcome: did it
⭐     happen? (Day 398) → ⭐ send ***R again*** → the server
⭐     recognises the key and returns the first result.
⭐   ⭐⭐ THE KEY WORKED BECAUSE R WAS THE SAME BYTES BOTH TIMES.
⭐     ⭐ `hash(payload)` was a legitimate idempotency key.

⭐ ***WHAT HAPPENS NOW:***
⭐   ⭐ step 4 asks the model what to do → it emits
⭐     `refund_order(id=88, amount_cents=4500)`
⭐   ⭐ the tool call times out. ⭐⭐ DID THE REFUND HAPPEN?
⭐   ⭐ you retry the ***step***, which means you call the model
⭐     again, ⭐ and it emits
⭐     `refund_order(id=88, amount_cents=4500, reason="goodwill")`
⭐     ⭐ — or `partial_refund(id=88, amount_cents=4500)`
⭐     ⭐ — or asks a clarifying question instead.
⭐   ⭐⭐ DIFFERENT BYTES. DIFFERENT HASH. DIFFERENT KEY.
⭐     ⭐⭐ THE DEDUPLICATION SILENTLY DOES NOTHING AND YOU HAVE
⭐       REFUNDED TWICE.

⭐⭐ ⇒ THE RULE THAT FIXES IT, AND IT IS THE WHOLE DAY:
⭐   ***THE IDEMPOTENCY KEY MUST BE ASSIGNED BY THE CALLER AT
⭐   THE POINT OF INTENT — NEVER DERIVED FROM THE MODEL'S
⭐   OUTPUT.***
⭐   ⭐ `key = f"{run_id}:{step_index}:{tool_name}"`
⭐   ⭐ ⭐⭐ RUN ID AND STEP INDEX ARE ***YOURS***. THEY ARE STABLE
⭐     ACROSS A RESUME. THE ARGUMENTS ARE NOT.
```

# Part 2 — Three layers of retry, three different problems

```
⭐ ① ***THE HTTP CALL TO THE PROVIDER.***
⭐   ⭐ Connection drops after generation completed.
⭐   ⭐⭐ YOU WERE BILLED. YOU HAVE NO OUTPUT. ⭐ Retrying costs
⭐     again ***and produces a different completion.***
⭐   ⭐ ⇒ providers support an idempotency key on the request —
⭐     ⭐⭐ USE IT. ⭐ It returns the ***same*** stored completion
⭐     rather than sampling again, ⭐ which makes the retry both
⭐     free and deterministic.
⭐   ⭐ ⭐⭐ AND NOTE WHAT `temperature=0` DOES ***NOT*** BUY YOU:
⭐     ⭐ it is greedy, not deterministic (Day 418), so two
⭐     identical requests can still differ. ⭐⭐ IT IS NOT AN
⭐     IDEMPOTENCY MECHANISM.

⭐ ② ***THE TOOL EXECUTION.***
⭐   ⭐ Classic distributed idempotency — ⭐ except the key must
⭐     come from Part 1's rule, not from the arguments.
⭐   ⭐ ⭐⭐ AT-LEAST-ONCE IS THE ONLY SEMANTIC YOU CAN ACHIEVE
⭐     (Day 404). ⭐ Exactly-once requires the ***resource*** to
⭐     deduplicate — ⭐⭐ CORRECTNESS LIVES IN THE RESOURCE, NOT
⭐     THE COORDINATOR (Day 412).

⭐ ③ ***THE WHOLE RUN.***
⭐   ⭐ The process died at step 7. ⭐ You resume.
⭐   ⭐⭐ THIS IS THE ONE PEOPLE GET WRONG, AND PART 3 IS ENTIRELY
⭐     ABOUT IT.
```

# Part 3 — ⭐⭐ Resume must replay, not re-decide

```
⭐ ***TWO POSSIBLE RESUME DESIGNS:***

⭐ ❌ ***REGENERATE.*** ⭐ Reload the transcript, call the model,
⭐   let it decide what to do next.
⭐   ⭐⭐ THE MODEL MAY NOW TAKE A DIFFERENT PATH THAN THE ONE
⭐     WHOSE SIDE EFFECTS ALREADY EXIST. ⭐ You created a ticket
⭐     at step 3; the new path never creates one and never
⭐     references it. ⭐⭐ THE TICKET IS ORPHANED AND NOTHING IN
⭐     THE SYSTEM KNOWS.
⭐   ⭐ Worse: it re-decides step 5 and issues a ***second***
⭐     refund with a new key.

⭐ ✅ ***REPLAY FROM THE LOG.***
⭐   ⭐ The transcript ***is*** the event log (Day 410).
⭐   ⭐ On resume, ⭐⭐ REPLAY RECORDED STEPS FROM THE STORE
⭐     WITHOUT CALLING THE MODEL OR THE TOOLS AT ALL, ⭐ until
⭐     you reach the ***frontier*** — the first step with no
⭐     recorded result. ⭐ Only there do you make a live call.
⭐   ⭐ ⭐⭐ SO THE PAST IS FIXED AND ONLY THE FUTURE IS
⭐     GENERATED. ⭐ Exactly event sourcing's rule: ***you do not
⭐     re-derive history, you read it.***

⭐ ***THE THREE-STATE RECORD PER STEP*** — this is the crux:
⭐  ┌──────────────┬───────────────────────────────────────────┐
⭐  │ `pending`    │ ⭐⭐ WE DECIDED TO CALL, AND DO NOT KNOW IF │
⭐  │              │ IT RAN. ⭐ The dangerous state. ⭐ On       │
⭐  │              │ resume: ***ASK THE RESOURCE***, do not     │
⭐  │              │ re-call blindly and do not skip.          │
⭐  ├──────────────┼───────────────────────────────────────────┤
⭐  │ `completed`  │ ⭐ result stored → replay it verbatim.     │
⭐  ├──────────────┼───────────────────────────────────────────┤
⭐  │ `failed`     │ ⭐ recorded terminal failure → replay the  │
⭐  │              │ error into the transcript.                │
⭐  └──────────────┴───────────────────────────────────────────┘
⭐   ⭐⭐ WRITE `pending` ***BEFORE*** EXECUTING. ⭐ Writing after
⭐     is the dual-write bug (Day 407) and it loses the record
⭐     of the exact call you are least able to reconstruct.
```

```python
async def execute_step(run_id: str, step: int, call, tool, store, *, tenant_id):
    key = f"{run_id}:{step}:{call.name}"          # ⭐⭐ PART 1'S RULE

    prior = await store.get_step(run_id, step)
    if prior and prior.status == "completed":
        return prior.result                        # ⭐ REPLAY, no side effect
    if prior and prior.status == "failed":
        return prior.error

    if prior and prior.status == "pending":
        # ⭐⭐ THE INTERESTING CASE. We crashed mid-flight.
        # ⭐ Ask the RESOURCE whether our key already landed —
        # ⭐⭐ THE ONLY COMPONENT THAT ACTUALLY KNOWS.
        existing = await tool.lookup_by_key(key)
        if existing is not None:
            await store.complete(run_id, step, existing)
            return existing

    await store.mark_pending(run_id, step, key, call.input)   # ⭐⭐ BEFORE
    result = await tool.run(call.input, tenant_id=tenant_id,
                            idempotency_key=key)              # ⭐ passed down
    await store.complete(run_id, step, result)
    return result
```

```
⭐⭐ NOTE THE TWO REQUIREMENTS THIS PUTS ON EVERY MUTATING TOOL:
⭐   ⭐ ① it ***accepts*** an idempotency key and honours it;
⭐   ⭐ ② it can be ***queried*** by that key.
⭐   ⭐⭐ A TOOL THAT CANNOT DO ② TURNS EVERY CRASH INTO A
⭐     MANUAL RECONCILIATION. ⭐ Make ② a requirement in your
⭐     tool contract, the same way you made `tenant_id` one.
```

# Part 4 — The tools you do not control

```
⭐ ***THE HONEST PROBLEM:*** ⭐ half your tools are third-party
⭐   APIs, and ⭐⭐ MANY HAVE NO IDEMPOTENCY SUPPORT AT ALL.

⭐ ***FOUR STRATEGIES, BEST FIRST:***
⭐   ⭐ ① ⭐⭐ ***A UNIQUE CONSTRAINT SOMEWHERE YOU OWN.*** ⭐ Day
⭐     412's first answer, and still the best: insert
⭐     `(run_id, step, tool)` into a table with a unique index
⭐     ***before*** the external call. ⭐ Duplicate insert fails →
⭐     you already did it. ⭐⭐ THE DATABASE DECIDES, NOT YOUR
⭐     CONTROL FLOW.
⭐   ⭐ ② ***SEARCH BEFORE WRITE.*** ⭐ Query the API for
⭐     something carrying your run id — a reference field, an
⭐     external id, a subject line tag. ⭐⭐ RACY, BUT VASTLY
⭐     BETTER THAN NOTHING.
⭐   ⭐ ③ ***MAKE IT REVERSIBLE INSTEAD.*** ⭐ Create a ***draft***
⭐     rather than sending; ⭐⭐ ONE HUMAN CLICK CONVERTS AN
⭐     AT-LEAST-ONCE PROBLEM INTO AN EXACTLY-ONCE ONE (D440).
⭐   ⭐ ④ ***PUT IT BEHIND THE GATE.*** ⭐ If it is irreversible
⭐     and undeduplicable, ⭐⭐ IT REQUIRES APPROVAL. ⭐ That is
⭐     not a cop-out, it is the correct engineering answer to a
⭐     resource that cannot protect itself.

⭐⭐ AND THE OUTBOX, WHICH YOU ALREADY BUILT (DAY 407): ⭐ if an
⭐   agent run needs to ***emit events*** — "refund issued" —
⭐   write them to the outbox in the same transaction as the
⭐   step record. ⭐⭐ NEVER PUBLISH DIRECTLY FROM THE LOOP: ⭐ a
⭐   crash between "tool ran" and "event published" is the same
⭐   dual-write bug Stage 12 spent a day on.
```

# Part 5 — ⭐⭐ Compensation must be computed from the log

```
⭐ ***THE MISTAKE THAT LOOKS CLEVER:*** ⭐ the run failed, so ask
⭐   the model to clean up. ⭐ "You created a ticket and issued a
⭐   refund. Undo them."
⭐   ⭐⭐ NOW YOUR ***RECOVERY PATH*** IS NON-DETERMINISTIC TOO —
⭐     ⭐ it can hallucinate which actions happened, miss one, or
⭐     invent a compensation for something it never did.
⭐   ⭐⭐ THE RECOVERY PATH IS THE ***LAST*** PLACE YOU WANT
⭐     SAMPLING.

⭐ ✅ ***COMPENSATION IS DERIVED FROM THE STEP LOG, IN CODE.***
⭐   ⭐ walk `completed` steps in reverse;
⭐   ⭐ each mutating tool declares its own `compensate(result)`;
⭐   ⭐ ⭐⭐ COMPENSATIONS CARRY THEIR ***OWN*** IDEMPOTENCY KEYS —
⭐     `f"{run_id}:{step}:compensate"` — ⭐ because the cleanup
⭐     can crash and be retried too;
⭐   ⭐ ⭐⭐ AND EACH IS A NEW VISIBLE FACT, NOT AN ERASURE
⭐     (Day 411). ⭐ A reversal entry, a cancellation notice.

⭐ ***AND THE `pending` STEP DURING COMPENSATION*** — ⭐ the
⭐   genuinely hard one: ⭐⭐ YOU DO NOT KNOW WHETHER IT RAN, SO
⭐   YOU CANNOT KNOW WHETHER TO COMPENSATE IT.
⭐   ⭐ ⇒ query the resource by key (Part 3). ⭐ If it cannot be
⭐     queried, ⭐⭐ ESCALATE TO A HUMAN WITH THE EXACT KEY AND
⭐     ARGUMENTS. ⭐ "We may have sent this email; here is the
⭐     recipient and the body" is a ***usable*** handoff.
⭐     ⭐⭐ SILENTLY GUESSING IS NOT.
```

# Part 6 — Proving it

```
⭐ ***THE TEST THAT MATTERS — CHAOS, BUT SMALL AND EXACT:***
⭐   ⭐ for `i` in `range(n_steps)`:
⭐     ⭐ run the agent, ⭐⭐ KILL THE PROCESS AT STEP i,
⭐     ⭐ resume it,
⭐     ⭐ ⭐⭐ ASSERT: EXACTLY ONE EMAIL, EXACTLY ONE REFUND,
⭐       EXACTLY ONE TICKET.
⭐   ⭐ Then kill it ***between*** `mark_pending` and the tool
⭐     call, and ***between*** the tool call and `complete` —
⭐     ⭐⭐ THOSE TWO WINDOWS ARE WHERE ALL THE REAL BUGS LIVE.

⭐ ***AND THE METRIC TO CARRY TO PRODUCTION:***
⭐   ⭐ ⭐⭐ `duplicate_suppressed_total` BY TOOL. ⭐ It should be
⭐     small and non-zero — ⭐⭐ ZERO USUALLY MEANS YOUR KEYS ARE
⭐     NOT ACTUALLY BEING CHECKED, NOT THAT CRASHES NEVER
⭐     HAPPEN.
⭐   ⭐ plus `steps_pending_on_resume` — ⭐ your exposure to the
⭐     unknown-outcome case, quantified.
```

# 💬 Interview

**1. "How do you make agent tool calls idempotent?"**

⭐ The key insight is that the usual approach breaks. ⭐⭐ In an ordinary service you can hash the request
payload, because a retry sends the same bytes. ⭐ With a model in the loop, retrying a step means asking
the model again, and it may emit different arguments — a `reason` field it didn't include last time, or
a different tool entirely. ⭐⭐ Different bytes, different hash, different key, and your deduplication
silently does nothing while you refund twice. ⭐ So the key is assigned by the caller at the point of
intent: run id, step index, tool name. ⭐⭐ Those are mine and they're stable across a resume. The
model's output isn't.

**2. "The process dies at step 7. How do you resume?"**

⭐ By replaying, not re-deciding. ⭐⭐ If I reload the transcript and just ask the model what to do next,
it may take a different path from the one whose side effects already exist — so the ticket created at
step 3 is orphaned and nothing in the system references it, or it re-decides step 5 and issues a second
refund under a new key. ⭐ So resume replays recorded steps from the store without calling the model or
the tools, until it reaches the frontier — the first step with no recorded result — and only there does
it make a live call. ⭐⭐ The past is fixed and only the future is generated, which is exactly event
sourcing's rule: you don't re-derive history, you read it.

**3. "What about a step that was in flight when you crashed?"**

⭐ That's the genuinely hard state and it needs its own record. ⭐⭐ I write `pending` **before**
executing, never after — writing after is the dual-write bug and it loses precisely the record I'm least
able to reconstruct. ⭐ On resume, a `pending` step is neither replayed nor blindly re-called: I query
the resource by my idempotency key, because the resource is the only component that actually knows
whether it happened. ⭐⭐ That puts two requirements on every mutating tool — it must accept an
idempotency key and it must be queryable by it. ⭐ A tool that can't be queried turns every crash into
manual reconciliation, so I make that part of the tool contract the same way I made `tenant_id`
required.

**4. "A third-party API has no idempotency support. Now what?"**

⭐ Four options, best first. ⭐⭐ A unique constraint somewhere I own: insert run-id-step-tool into a table
with a unique index *before* the external call, so a duplicate insert fails and the database decides
rather than my control flow. ⭐ Search before write — query the API for something carrying my run id in
a reference field; racy, but far better than nothing. ⭐ Make it reversible instead: create a draft
rather than sending, so one human click converts an at-least-once problem into an exactly-once one.
⭐⭐ And if it's irreversible and undeduplicable, it goes behind an approval gate. ⭐ That's not a
cop-out, it's the correct answer to a resource that can't protect itself.

**5. "The run half-completed. How do you clean up?"**

⭐ From the step log, in code — never by asking the model. ⭐⭐ "You created a ticket and issued a refund,
undo them" makes the *recovery path* non-deterministic, and that's the last place I want sampling: it
can hallucinate which actions happened, miss one, or invent a compensation for something it never did.
⭐ So I walk completed steps in reverse, each mutating tool declares its own compensation, and
compensations carry their own idempotency keys because the cleanup can crash too. ⭐⭐ Each is a new
visible fact — a reversal entry, a cancellation notice — not an erasure. ⭐ And a `pending` step during
compensation is escalated to a human with the exact key and arguments: "we may have sent this email,
here's the recipient and body" is a usable handoff; silently guessing isn't.

**6. "Doesn't temperature=0 solve the determinism problem?"**

⭐ No, and it's a useful thing to be precise about. ⭐⭐ `temperature=0` is greedy sampling, not
determinism — floating-point non-associativity and batch-dependent reduction order mean two identical
requests can still produce different outputs. ⭐ So it's not an idempotency mechanism. ⭐⭐ What does
help at that layer is the provider's own idempotency key on the HTTP request, which returns the stored
completion rather than sampling again — that makes a retry both free and identical, which matters
because a connection that drops after generation means you were billed and got nothing.

**7. "How do you prove any of this works?"**

⭐ A small, exact chaos test rather than a big vague one. ⭐⭐ For each step index, run the agent, kill
the process at that step, resume, and assert exactly one email, one refund, one ticket. ⭐ Then kill it
in the two windows that matter — between marking pending and the tool call, and between the tool call
and recording completion — because that's where all the real bugs live. ⭐⭐ In production I track
`duplicate_suppressed_total` by tool, and I treat **zero** as suspicious: it usually means the keys
aren't being checked, not that crashes never happen.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "how do you get exactly-once behaviour out of an agent?"**

Open by naming what broke, because the interviewer expects a standard answer. **Every retry pattern I
know rests on an assumption nobody states: that retrying replays the same request. That's why hashing
the payload works as an idempotency key. With a model in the loop it stops being true. Retrying a step
means asking the model again, and it might emit a `reason` field it didn't include last time, or call a
different tool entirely. Different bytes, different hash, different key — the deduplication silently
does nothing and you've refunded twice.**

Then the replacement rule. **So the key is assigned by the caller at the point of intent: run id, step
index, tool name. Those are mine and they're stable across a resume; the model's output isn't. And every
mutating tool has to do two things — accept that key, and be queryable by it. A tool that can't be
queried turns every crash into a manual reconciliation, so it's part of the tool contract, like the
tenant argument.**

Then resume, which is where the real design decision is. **Resume replays, it doesn't re-decide. If I
reload the transcript and ask the model what's next, it may take a different path from the one whose
side effects already exist — the ticket from step three is orphaned and nothing references it, or step
five gets re-decided and issues a second refund under a new key. So I replay recorded steps from the
store, no model calls and no tool calls, until I hit the frontier — the first step with no recorded
result — and only there do I go live. The past is fixed, only the future is generated. That's event
sourcing's rule: you don't re-derive history, you read it.**

Then the hard state and the cleanup. **A step marked `pending` is the interesting one — written before
execution, never after, because writing after is the dual-write bug and it loses exactly the record I
can't reconstruct. On resume I don't skip it and I don't blindly re-call it: I query the resource by my
key, because the resource is the only component that knows. And compensation comes from the step log in
code, never by asking the model to clean up — that would make the recovery path non-deterministic, which
is the last place I want sampling. Compensations carry their own keys, and each is a new visible fact
rather than an erasure.**

Close on proof. **I test it by killing the process at every step index, and specifically in the two
windows between marking pending and calling, and between calling and recording — then asserting exactly
one email, one refund, one ticket. And in production I watch duplicate-suppressed counts per tool, where
zero is suspicious rather than reassuring: it usually means the keys aren't being checked.**
