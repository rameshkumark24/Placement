# Day 053

**L-053** · Classes and instances · `__init__` vs `__new__` · class vs instance attributes · metaclasses

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `class` is a statement that executes its body as a namespace and then
> calls a metaclass to build an object.** Classes are created at runtime by ordinary machinery
> (Day 023), which is why Django, SQLAlchemy and Pydantic can do what they do.
>
> ⭐ Today also settles the two questions people get wrong: **when you actually need `__new__`**, and
> **why a mutable class attribute is shared.**

---

# Part 1 — ⭐⭐ What `class` does

```python
class Order:
    tax = 0.2                      # ⭐ these lines RUN, in order, in a fresh namespace
    print("body executing")        # ⭐⭐ this prints AT IMPORT — the body is real code
    def total(self): ...
```

```
⭐⭐ THE THREE STEPS:
⭐   1. evaluate the bases and find the METACLASS (default: `type`)
⭐   2. ⭐ execute the class body in a fresh namespace dict ⇒ collect names
⭐   3. ⭐⭐ call metaclass(name, bases, namespace) ⇒ the class OBJECT
⭐
⭐ ⇒ ⭐ exactly equivalent to: Order = type("Order", (), {"tax": 0.2, "total": <function>})
```

⭐⭐ **The class body executing at import is why decorators and field descriptors work** — `@property`,
a SQLAlchemy `Column()`, a Pydantic annotation are all evaluated then, and the metaclass sees the
finished namespace. **It is also why an expensive expression in a class body costs you at startup.**

```python
# ⭐⭐ INSTANCE CREATION — two steps, and this is what people mix up:
obj = Order(5)
# ⇒ type(Order).__call__(Order, 5) which does:
#     ⭐ obj = Order.__new__(Order, 5)        ⇒ ALLOCATE
#     ⭐ if isinstance(obj, Order):
#           Order.__init__(obj, 5)            ⇒ INITIALISE
#     ⇒ ⭐⭐ __new__ CREATES; __init__ CONFIGURES an already-created object.
```

⚠️ ⭐⭐ **If `__new__` returns something that is not an instance of the class, `__init__` is never
called.** That is not a bug — it is how `__new__` can act as a factory — **and it is a genuinely
confusing failure when it happens by accident.**

# Part 2 — ⭐⭐ When you actually need `__new__`

```
⭐⭐ THE HONEST ANSWER: almost never. Three real cases:
⭐   1. ⭐⭐ SUBCLASSING AN IMMUTABLE TYPE — int, str, tuple, bytes, frozenset.
⭐        the value is fixed at ALLOCATION, so __init__ is too late.
⭐   2. ⭐ SINGLETONS / instance caching / interning
⭐   3. ⭐ __new__ returning a different class entirely (a factory) — ⚠️ usually a classmethod is better
```

```python
# ⭐⭐ CASE 1 — the one you cannot work around:
class Currency(str):
    def __new__(cls, code):
        if code not in {"GBP", "USD"}: raise ValueError(code)
        return super().__new__(cls, code.upper())    # ⭐⭐ the str's value is set HERE
```

```python
# ⭐ CASE 2 — a singleton. Correct, and rarely what you want:
class Registry:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
# ⚠️ ⭐⭐ __init__ STILL RUNS ON EVERY CALL — so it re-initialises the singleton each time.
#     ⇒ that is the classic singleton bug in Python. Guard it, or use a module-level object.
```

⭐⭐ **In Python, a module *is* a singleton** — imported once, cached in `sys.modules`. **A
module-level object is the idiomatic singleton, and it is simpler, testable and has no `__init__`
problem.** ⭐ For dependency injection, Stage 4's DI is better than either.

⚠️ ⭐ **`__init__` must return `None`.** Returning anything else raises `TypeError`.

# Part 3 — ⭐⭐ Class vs instance attributes

```python
class Dog:
    species = "canis"              # ⭐ CLASS attribute — one object, shared
    tricks = []                    # ⚠️⚠️ ⭐⭐ ONE LIST, SHARED BY EVERY INSTANCE (Day 024)

    def __init__(self, name):
        self.name = name           # ⭐ INSTANCE attribute — one per object
```

```
⭐⭐ THE LOOKUP (Day 032, restated for attributes): instance __dict__, then the class,
⭐   then the MRO. ⇒ so READING finds the class attribute; ASSIGNING creates an INSTANCE one.
⭐
⭐   d.species             ⇒ ⭐ found on the class
⭐   d.species = "x"       ⇒ ⭐⭐ creates d.__dict__["species"] — SHADOWS, does not change the class
⭐   Dog.species = "x"     ⇒ ⭐ changes it for every instance that has not shadowed it
⭐
⭐ ⭐⭐ BUT: d.tricks.append("sit")  ⇒ MUTATES the class's list. No assignment happened,
⭐      so no instance attribute was created. ⇒ ⭐⭐ EVERY DOG NOW KNOWS THAT TRICK.
```

⭐⭐ **The rule: a class attribute is fine if it is immutable. A mutable one is shared state.**
Assign mutable defaults in `__init__`, or use a dataclass `field(default_factory=list)` (Day 057) —
**which exists precisely because this and the mutable-default-argument bug (Day 025) are the same
mistake.**

⭐ **Legitimate uses of class attributes:** constants, configuration defaults, a registry the class
itself owns, and counters incremented via `type(self)` or the class name explicitly.

## ⭐ Naming: `_x` and `__x`

```python
class C:
    def __init__(self):
        self._internal = 1         # ⭐ convention: "don't touch". Nothing enforces it.
        self.__mangled = 2         # ⭐⭐ becomes self._C__mangled — NAME MANGLING
```

⭐⭐ **Double underscore is not privacy — it is collision avoidance.** It exists so a base class's
attribute cannot be accidentally overwritten by a subclass using the same name, which matters in
mixins and frameworks. **`c._C__mangled` is fully accessible.** ⭐ Use a single underscore by default;
reach for `__` only in a base class designed for inheritance.

# Part 4 — ⭐ `__init_subclass__` and metaclasses

```python
# ⭐⭐ THE MODERN HOOK — solves 90% of what people used metaclasses for:
class Plugin:
    registry = {}
    def __init_subclass__(cls, /, name=None, **kwargs):
        super().__init_subclass__(**kwargs)
        Plugin.registry[name or cls.__name__] = cls      # ⭐⭐ every subclass self-registers

class CsvPlugin(Plugin, name="csv"): ...     # ⭐ registered at import, no metaclass needed
```

⭐⭐ **`__init_subclass__` is an implicit classmethod called when a *subclass* is created.** ⭐ Its
sibling `__set_name__` (Day 032) gives descriptors their own name. **Between them they cover
registries, validation of subclasses, and field naming — the three classic metaclass uses.**

```python
# ⭐ A METACLASS — for completeness, and this is the shape:
class Meta(type):
    def __new__(mcls, name, bases, ns, **kw):
        # ⭐⭐ inspect/modify `ns` BEFORE the class exists
        ns["fields"] = [k for k, v in ns.items() if isinstance(v, Field)]
        return super().__new__(mcls, name, bases, ns, **kw)

class Model(metaclass=Meta): ...
```

| ⭐ Metaclass hook | ⭐ When |
|---|---|
| `__prepare__` | before the body runs — return a custom namespace mapping |
| ⭐ `__new__` | the namespace is complete, the class does not exist yet |
| `__init__` | the class exists |
| ⭐ `__call__` | ⭐⭐ **every instantiation** — this is where singletons and caching really belong |

```
⭐⭐ WHERE YOU ALREADY USE METACLASSES:
⭐   · Django models — collect Fields, build _meta, register with the app
⭐   · SQLAlchemy's declarative base — map columns to a table
⭐   · Pydantic BaseModel — build validators from annotations
⭐   · ⭐ abc.ABCMeta — enforce abstract methods (Day 056)
⭐   · Enum's EnumMeta — turn class attributes into singleton members (Day 058)
⭐
⭐ ⭐⭐ AND THE VERDICT: do not write one. Reach for __init_subclass__, a class DECORATOR,
⭐   or a descriptor first. A metaclass makes a class hierarchy hard to read, hard to type-check,
⭐   and it conflicts with other metaclasses — which is a real problem when two libraries
⭐   both want one.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Mutable class attribute** | ⭐⭐ Shared by every instance. Assign in `__init__`. |
| Thinking `d.x = 1` changes the class | ⭐ It creates an instance attribute that shadows it. |
| ⭐ Using `__new__` where `__init__` works | ⭐ Almost never needed — three real cases. |
| Singleton via `__new__` without guarding `__init__` | ⭐⭐ `__init__` re-runs on every call. |
| Returning a value from `__init__` | ⭐ `TypeError`. |
| ⭐ Believing `__x` is private | ⭐⭐ It is name mangling for collision avoidance. |
| Expensive work in a class body | ⭐ It runs at import. |
| Writing a metaclass for a registry | ⭐⭐ `__init_subclass__`. |
| Two libraries' metaclasses on one class | ⭐ Metaclass conflict — a real, hard failure. |
| Not knowing `__new__` skips `__init__` on a foreign return | ⭐ Confusing when accidental. |

## Interview questions

**Q: What happens when you define a class?**
> The body executes as ordinary code in a fresh namespace, collecting names into a dict; then the
> metaclass — `type` by default — is called with the name, bases and that namespace, and returns the
> class object. It's the same as calling `type()` with three arguments. The fact that the body runs at
> import is what makes descriptors, decorators and annotation-driven frameworks work: `@property`, a
> SQLAlchemy `Column`, a Pydantic field are all evaluated then, and the metaclass sees the finished
> namespace.

**Q: `__new__` versus `__init__`?**
> `__new__` allocates and returns the object; `__init__` configures an object that already exists.
> Instantiation calls both, via the metaclass's `__call__`. I need `__new__` in essentially one case:
> subclassing an immutable type like `str`, `int` or `tuple`, where the value is fixed at allocation
> so `__init__` is too late to influence it. The other uses — singletons and instance caching — work,
> but there's a catch people miss: `__init__` still runs on every call, so a `__new__`-based singleton
> gets re-initialised each time unless you guard it. In Python a module-level object is a simpler
> singleton, since modules are imported once and cached.

**Q: Why does one instance's list appear on all of them?**
> Because the list is a class attribute, so there's one object shared by the class. Reading
> `self.tricks` finds it on the class, and `append` mutates it in place — no assignment happens, so no
> instance attribute is ever created to shadow it. Assigning `self.tricks = []` would create a
> per-instance one, which is why mutable defaults belong in `__init__`, or in a dataclass's
> `default_factory`. It's the same mistake as a mutable default argument, one level up.

**Q: Is a double-underscore attribute private?**
> No — it's name mangling. `__x` inside class `C` becomes `_C__x`, and you can access it directly. It
> exists so a base class's internal attribute can't be silently clobbered by a subclass using the same
> name, which matters in mixins and frameworks. A single underscore is the convention for "internal",
> and it's enforced by nothing but agreement, which in practice is enough.

**Q: When would you write a metaclass?**
> Realistically, not at all. Nearly everything people reach for one for is covered by
> `__init_subclass__` for subclass registration or validation, `__set_name__` for descriptors knowing
> their own name, or a plain class decorator. Metaclasses make a hierarchy hard to read and hard to
> type-check, and they conflict — if two libraries each want a metaclass on the same class, you have a
> genuine problem with no clean fix. I use them constantly through Django, SQLAlchemy, Pydantic and
> `ABCMeta`; I don't write them.

## 🎙️ Articulation drill

Record two minutes: **"Explain `__new__` versus `__init__`, and when you would use `__new__`."**

⭐ Split the responsibilities cleanly: **`__new__` allocates and returns the object; `__init__`
configures one that already exists.** Both are called by the metaclass's `__call__`, and if `__new__`
returns something that is not an instance of the class, `__init__` is skipped entirely.

⭐ Then the honest answer on when: **subclassing an immutable type**, because the value of a `str` or
`tuple` is fixed at allocation and `__init__` cannot change it. That is the case with no workaround.

⭐⭐ **Then the trap, because it is what separates having read about it from having used it:** *"the
other common use is a singleton, and it has a bug people ship: `__new__` returns the cached instance,
but `__init__` still runs on every call, so the singleton is re-initialised each time you 'construct'
it. In Python I would not do this at all — a module is imported once and cached in `sys.modules`, so a
module-level object is already a singleton, and it is testable in a way that a class-level cache is
not."*
