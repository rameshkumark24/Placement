# Day 176

**L-176** · 🎸 **DRF II** — ⭐⭐ authentication, permissions, throttling, pagination, and the object permission that never runs

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: DRF's `has_object_permission` is not called on list views — it cannot be,
> because there is no single object — so if your tenant isolation lives in a permission class, your
> list endpoint returns everyone's data.**
>
> ⭐ That one fact is the most consequential thing in this day, and it is a real, repeatedly-shipped
> vulnerability. ⭐⭐ Everything else here is Days 113–123 with DRF's names on it.

# Part 1 — ⭐ Authentication classes

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.SessionAuthentication",   # ⭐ browser
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
    "DEFAULT_PERMISSION_CLASSES": ["rest_framework.permissions.IsAuthenticated"],
    #                              ⭐⭐ DEFAULT-DENY. Set this on day one.
}
```

```
⭐⭐ THE FOUR OPTIONS, WITH THE HONEST VERDICT ON EACH:

⭐  ⭐ `SessionAuthentication` — the Django session cookie.
⭐       ⭐ + revocable server-side, HttpOnly, no token storage problem
⭐       ⭐ − ⭐⭐ CSRF APPLIES (Day 174). DRF enforces CSRF **only** for session
⭐            auth, which is correct and confuses everyone: ⭐ a cookie is
⭐            ambient authority, a header token is not.
⭐       ⇒ ⭐ correct for a same-site browser SPA.
⭐
⭐  ⭐ `TokenAuthentication` — a random opaque token in a DB table.
⭐       ⭐ + revocable, simple. ⭐ − ⭐⭐ ONE TOKEN PER USER FOREVER by
⭐            default: no expiry, no rotation, no scopes. ⭐ Fine for a
⭐            service-to-service key; ⭐⭐ not a session system.
⭐
⭐  ⭐⭐ `simplejwt` — access + refresh (Days 116, 117).
⭐       ⭐ + stateless, scales, standard.
⭐       ⭐ − ⭐⭐ NOT REVOCABLE WITHOUT SERVER STATE. ⭐ A banned user keeps
⭐            working until expiry unless you add a blacklist — ⭐⭐ and
⭐            `simplejwt`'s blacklist app is exactly that server state, which
⭐            means you have traded away the stateless property you chose JWT
⭐            for. ⭐ Say that trade out loud; it is the whole JWT argument.
⭐       ⇒ ⭐ short access TTL (5–15 min) + refresh rotation with reuse
⭐            detection (Day 117).
⭐
⭐  ⭐ `BasicAuthentication` — ⭐⭐ development only. Credentials on every
⭐       request, and browsers cache them in ways you cannot control.
⭐
⭐⭐ AND THE MECHANIC WORTH KNOWING: authentication classes are tried IN
⭐   ORDER; the FIRST that returns a user wins, ⭐ and one that RAISES stops
⭐   the chain. ⭐⭐ So putting `BasicAuthentication` first in production means
⭐   a wrong Basic header 401s before your JWT is ever examined.
```

```
⭐⭐ THE 401 vs 403 QUIRK THAT PEOPLE FILE BUGS ABOUT:
⭐   ⭐ DRF returns **403** for an unauthenticated request when no
⭐        authentication class provides a `WWW-Authenticate` header —
⭐        ⭐⭐ notably with `SessionAuthentication` alone.
⭐   ⭐ It returns **401** when one does (JWT, Token, Basic).
⭐   ⇒ ⭐ It is deliberate: the RFC requires `WWW-Authenticate` on a 401
⭐        (Day 140), so DRF downgrades rather than emit an invalid response.
⭐   ⇒ ⭐⭐ THE CONSEQUENCE: your SPA cannot distinguish "log in" from
⭐        "forbidden" unless you fix it — ⭐ either include a
⭐        header-providing auth class or override the exception handler.
```

# Part 2 — ⭐⭐ Permissions, and the one that never runs

```python
class IsOrderOwner(BasePermission):
    def has_permission(self, request, view):            # ⭐ runs for EVERY request
        return request.user.is_authenticated
    def has_object_permission(self, request, view, obj):  # ⭐⭐ ONLY via get_object()
        return obj.user_id == request.user.id
```

```
⭐⭐ THE MOST IMPORTANT MECHANIC IN DRF, AND IT IS A REAL VULNERABILITY:

⭐   ⭐ `has_permission`        → called on EVERY request, before the view.
⭐   ⭐⭐ `has_object_permission` → called ONLY by `get_object()`.
⭐
⭐   ⇒ ⭐⭐ THEREFORE IT IS **NOT CALLED ON `list`**. There is no single object
⭐        to check, so DRF cannot call it — ⭐ and it does not warn you.
⭐   ⇒ ⭐⭐ SO IF YOUR OWNERSHIP CHECK LIVES ONLY IN `has_object_permission`:
⭐        ⭐ `GET /orders/7/`  → 403 ✅ correctly denied
⭐        ⭐ `GET /orders/`    → ⭐⭐ **RETURNS EVERY ORDER IN THE DATABASE** ❌
⭐        ⭐ And every test you wrote for the detail view passes.
⭐   ⇒ ⭐⭐ THIS SHIPS. REGULARLY. ⭐ It is Day 118's IDOR wearing a permission
⭐        class as a disguise.
⭐
⭐⭐ THE FIX, AND IT IS THE SAME ANSWER AS EVERY OTHER DAY:
⭐   ⭐⭐ **SCOPE IN `get_queryset`.** Then `list` is filtered, and `get_object`
⭐        derives from the same queryset — so a wrong id is a 404 (Day 118's
⭐        "do not confirm existence"), and ⭐ there is no code path that can
⭐        return another user's row, because the query cannot express it.
⭐   ⭐ Keep `has_object_permission` as a SECOND layer for non-ownership rules
⭐        (⭐⭐ "may this user refund?"), ⭐ not as the isolation mechanism.
⭐
⭐⭐ AND ONE MORE THAT CATCHES PEOPLE: `has_object_permission` IS **NOT**
⭐   CALLED ON `create` EITHER — ⭐ there is no object yet. ⭐⭐ So "may this
⭐   user create an order for this event?" must be checked in the serializer's
⭐   `validate()` or in the service, never in an object permission.
```

```python
# ⭐⭐ THE CORRECT SHAPE
class OrderViewSet(viewsets.ModelViewSet):
    permission_classes = [IsAuthenticated, CanRefund]      # ⭐ role/action rules
    def get_queryset(self):
        return Order.objects.for_user(self.request.user)   # ⭐⭐ ISOLATION LIVES HERE
```

```
⭐ PERMISSION COMPOSITION, worth knowing:
⭐   ⭐ `permission_classes = [A, B]` is AND — every one must pass.
⭐   ⭐ DRF supports `A | B` and `A & B` and `~A` since 3.9 — ⭐⭐ useful for
⭐        "staff OR owner", which is otherwise a custom class.
⭐   ⭐ ⭐⭐ `AllowAny` ON ONE VIEW SILENTLY OVERRIDES YOUR GLOBAL DEFAULT-DENY.
⭐        ⭐ Grep for it in review, and write the Day 140 route-table test:
⭐        walk the router's URLs and assert each view's permissions are not
⭐        `AllowAny` unless explicitly listed.
⭐   ⭐ For per-object rules at scale, `django-guardian` gives real
⭐        row-level permissions — ⭐⭐ at the cost of a join per check.
```

# Part 3 — ⭐ Throttling, and what it is not

```python
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_CLASSES": ["rest_framework.throttling.ScopedRateThrottle"],
    "DEFAULT_THROTTLE_RATES": {"anon": "60/hour", "user": "1000/hour",
                               "login": "5/min", "burst": "30/min"},
}
class LoginView(APIView):
    throttle_scope = "login"                # ⭐⭐ per-endpoint, Day 153
```

```
⭐⭐ DRF'S THROTTLING IS A **FIXED WINDOW OVER THE CACHE** (Day 123, 153).
⭐   KNOW ITS FOUR LIMITS AND SAY THEM:
⭐  1. ⭐⭐ IT IS NOT ATOMIC. Read-modify-write on the cache, ⭐ so under real
⭐       concurrency across replicas it over-admits. ⭐⭐ Day 153's race,
⭐       shipped in the framework.
⭐  2. ⭐⭐ WITH LOCMEM CACHE IT IS PER-PROCESS — ⭐ N workers means N× the
⭐       limit. ⭐⭐ It MUST be backed by shared Redis to mean anything.
⭐  3. ⭐ FIXED WINDOW ⇒ ⭐⭐ the 2× boundary burst (Day 123).
⭐  4. ⭐ `AnonRateThrottle` KEYS ON IP ⇒ ⭐⭐ one corporate NAT is thousands of
⭐       users sharing a bucket (Day 153).
⭐   ⇒ ⭐⭐ VERDICT: FINE AS A COARSE GUARD AND FOR PER-ENDPOINT POLICY. ⭐ For
⭐        anything you actually rely on, use a Lua-backed limiter (Day 153) or
⭐        enforce at the edge. ⭐⭐ And it can never protect you from a
⭐        volumetric attack — by the time DRF counts, you have paid for TLS
⭐        and a worker.

⭐⭐ AND THE LOGIN CASE (Day 140/165): throttle per ACCOUNT **and** per IP.
⭐   ⭐ DRF gives you per-IP easily and per-account not at all — ⭐⭐ you write
⭐        that one. ⭐ And throttle unknown emails identically, or the throttle
⭐        itself is your account-enumeration oracle.
```

# Part 4 — ⭐⭐ Pagination and filtering

```python
REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.CursorPagination",
    "PAGE_SIZE": 50,
}
class OrderPagination(CursorPagination):
    page_size = 50
    max_page_size = 200          # ⭐⭐ or a client asks for 1,000,000 and you comply
    ordering = "-created_at"     # ⭐ must be a stable, indexed ordering
```

```
⭐⭐ THE THREE CLASSES, JUDGED (Day 121):
⭐   ⭐ `PageNumberPagination` — `?page=3`. ⭐ Familiar. ⭐⭐ OFFSET/LIMIT
⭐        underneath: page 5,000 makes the database count and discard 250,000
⭐        rows, ⭐ AND a deletion between pages SILENTLY SKIPS A ROW — the
⭐        drift from Day 121, which nobody notices because nothing errors.
⭐   ⭐ `LimitOffsetPagination` — same problems, explicit.
⭐   ⭐⭐ `CursorPagination` — KEYSET. ⭐ Constant time at any depth, ⭐⭐ and no
⭐        drift: it is `WHERE created_at < :cursor`. ⭐ Costs you the ability
⭐        to jump to page 27, which almost no API needs.
⭐   ⇒ ⭐⭐ CURSOR BY DEFAULT. Page numbers only when a human is clicking
⭐        pages in a back-office.
⭐   ⚠ ⭐ `CursorPagination` REQUIRES A STABLE, UNIQUE, INDEXED `ordering` —
⭐        ⭐⭐ ties in the ordering field cause skipped or repeated rows.
⭐        ⭐ Order by `("-created_at", "-id")` to break ties.

⭐⭐ FILTERING — `django-filter`, and its one real hazard:
⭐   ⭐ `filterset_fields = ["status", "event"]` gives `?status=paid`.
⭐   ⭐ ⭐⭐ `SearchFilter` WITH `search_fields = ["__all__"]` OR AN UNINDEXED
⭐        `icontains` IS A `LIKE '%term%'` FULL SCAN — ⭐ a public endpoint
⭐        that anyone can use to table-scan your largest table on demand.
⭐        ⭐⭐ THAT IS A DENIAL-OF-SERVICE VECTOR WITH A SEARCH BOX ON IT.
⭐   ⇒ ⭐ index what you filter, cap what you allow, ⭐⭐ and use Postgres
⭐        full-text search or a trigram index for real search.
⭐   ⭐ ⭐⭐ AND: `OrderingFilter` WITH `ordering_fields = "__all__"` LETS A
⭐        CLIENT SORT BY ANY COLUMN, INCLUDING UNINDEXED ONES. ⭐ Same problem,
⭐        different query parameter. ⭐ Enumerate the allowed fields.
```

# Part 5 — ⭐ Versioning, schema, and the production settings

```
⭐⭐ VERSIONING (Day 125) — DRF offers five schemes; ⭐ URL-path is the one to
⭐   use (`/api/v1/`): visible, cacheable, and greppable. ⭐⭐ Accept-header
⭐   versioning is more "correct" and makes every CDN and log line ambiguous.
⭐   ⇒ ⭐ And remember what actually breaks clients: removing a field,
⭐        narrowing a type, adding a required input, ⭐⭐ or changing the
⭐        MEANING of a field — the silent one.

⭐⭐ SCHEMA (Day 126): DRF's built-in generator is deprecated in favour of
⭐   `drf-spectacular`.
⭐   ⭐ ⭐⭐ THE HONEST COMPARISON WITH FASTAPI: FastAPI's OpenAPI is derived
⭐        from the same type annotations that do the validation, so it CANNOT
⭐        drift. ⭐ DRF's is INFERRED from serializers and views, ⭐⭐ and needs
⭐        `@extend_schema` decorators wherever the inference is wrong — which
⭐        is every custom `@action`, every non-model response, and every
⭐        polymorphic field.
⭐   ⇒ ⭐ So: snapshot the generated schema and fail CI on an unreviewed diff
⭐        (Day 141). ⭐⭐ In FastAPI that check is a nicety; in DRF it is how
⭐        you find out the docs stopped matching reality.

⭐⭐ THE PRODUCTION SETTINGS CHECKLIST:
⭐   □ ⭐⭐ `DEFAULT_PERMISSION_CLASSES = [IsAuthenticated]` — default-deny
⭐   □ ⭐⭐ `DEFAULT_RENDERER_CLASSES = [JSONRenderer]` — ⭐ the browsable API
⭐        renderer in production leaks your form structure and is a
⭐        surprisingly effective reconnaissance tool
⭐   □ ⭐ `DEFAULT_PAGINATION_CLASS` + `max_page_size`
⭐   □ ⭐ `DEFAULT_THROTTLE_RATES` with a Redis cache backend
⭐   □ ⭐⭐ a custom `EXCEPTION_HANDLER` (Day 175) — one shape, stable codes
⭐   □ ⭐ `PAGE_SIZE` set, `ordering` stable and indexed
⭐   □ ⭐⭐ `DEBUG = False` — ⭐ DRF's error responses include far more detail
⭐        with DEBUG on
```

```
⭐⭐ THE THREE THINGS TO TAKE FROM TODAY:
⭐   ⭐⭐ **ISOLATION LIVES IN `get_queryset`, NOT IN A PERMISSION CLASS** —
⭐        because `has_object_permission` is not called on list or create.
⭐   ⭐ DRF'S THROTTLING IS A COARSE GUARD, NOT A DEFENCE.
⭐   ⭐⭐ CURSOR PAGINATION BY DEFAULT, AND ENUMERATE YOUR FILTERABLE AND
⭐        ORDERABLE FIELDS — because an open search box on an unindexed
⭐        column is a DoS vector you published on purpose.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Tenant isolation in `has_object_permission` | Not called on `list` — the list endpoint returns everyone's data while detail tests pass. |
| Expecting object permissions on `create` | There's no object yet. Check in the serializer or the service. |
| No `DEFAULT_PERMISSION_CLASSES` | The default is `AllowAny`. Set default-deny on day one. |
| `AllowAny` on one view | Silently overrides your global default. Grep for it and write the route-table test. |
| `BasicAuthentication` first in the list | A wrong Basic header 401s before JWT is examined. |
| Filing a bug about DRF's 403-instead-of-401 | It's deliberate — a 401 requires `WWW-Authenticate`. Fix it with an auth class or a handler. |
| JWT without a blacklist, assuming revocation works | A banned user works until expiry — and the blacklist reintroduces the state you avoided. |
| `TokenAuthentication` as a session system | One token per user, forever, with no expiry or rotation. |
| DRF throttling with LocMem cache | Per-process, so N workers means N× the limit. |
| Relying on DRF throttling for correctness | Read-modify-write, non-atomic, fixed-window, IP-keyed. Coarse guard only. |
| Login throttled by IP only | You need per-account too, and unknown emails must throttle identically. |
| `PageNumberPagination` on a large table | Offset scans, plus silent row-skipping when rows are deleted. |
| `CursorPagination` on a non-unique ordering | Ties cause skipped or repeated rows. Add a tiebreaker. |
| No `max_page_size` | A client asks for a million rows and you comply. |
| `search_fields` with unindexed `icontains` | A public full-table-scan endpoint with a search box on it. |
| `ordering_fields = "__all__"` | The client can sort by any unindexed column. Enumerate them. |
| Browsable API renderer in production | Leaks form structure — effective reconnaissance. |
| Assuming the OpenAPI schema matches reality | DRF infers it; snapshot it and fail CI on a diff. |

## Interview questions

**Q: Where do you enforce that a user only sees their own orders?**

> In `get_queryset`, not in a permission class — and this is the DRF mechanic I'd most want to get
> across. `has_object_permission` is only called by `get_object()`, which means it is *not* called on
> `list`, because there's no single object to check. So if ownership lives only there,
> `GET /orders/7/` correctly returns 403 while `GET /orders/` returns every order in the database —
> and every test you wrote for the detail view passes. It ships regularly; it's an IDOR wearing a
> permission class as a disguise. Scoping the queryset fixes both: list is filtered, `get_object`
> derives from the same queryset so a wrong id is a 404 rather than a 403, and there's no code path
> that can return someone else's row because the query can't express it. I keep object permissions as
> a second layer for non-ownership rules like "may this user issue a refund". And note it isn't
> called on `create` either — there's no object yet — so "may you create this?" belongs in the
> serializer or the service.

**Q: Which authentication class would you choose?**

> Depends on the client, and the trade is the same one as anywhere: cookies versus header tokens. For
> a same-site browser SPA, `SessionAuthentication` — revocable server-side, HttpOnly, no storage
> problem — and CSRF applies, which is why DRF enforces CSRF for session auth and not token auth. A
> cookie is ambient authority; a header token isn't. For mobile or service-to-service, `simplejwt`
> with a short access TTL and refresh rotation with reuse detection. The honest caveat I'd state:
> JWT isn't revocable without server state, so a banned user keeps working until expiry — and adding
> `simplejwt`'s blacklist app *is* that server state, which trades away the statelessness you chose
> JWT for. `TokenAuthentication` is one token per user with no expiry or rotation, which is fine as a
> service key and isn't a session system.

**Q: Is DRF's throttling enough?**

> As a coarse guard and for per-endpoint policy, yes. As a defence, no, and there are four specific
> reasons. It's a read-modify-write against the cache, so it isn't atomic and over-admits under
> concurrency across replicas. With the LocMem cache it's per-process, so four workers means four
> times the limit — it has to be Redis-backed to mean anything. It's a fixed window, so it allows the
> classic two-times burst at the boundary. And the anonymous throttle keys on IP, so one corporate
> NAT is thousands of users sharing a bucket. For anything I rely on I'd use an atomic Lua-backed
> limiter or enforce at the edge. And for login specifically, DRF gives me per-IP easily and
> per-account not at all — I have to write that, and throttle unknown emails identically or the
> throttle itself becomes my account-enumeration oracle.

**Q: Which pagination class, and why?**

> `CursorPagination` by default. Page-number and limit-offset are offset scans underneath, so page
> five thousand makes the database count and discard a quarter of a million rows — and worse, a
> deletion between requests silently *skips* a row, which nobody notices because nothing errors.
> Cursor pagination is keyset: `WHERE created_at < :cursor`, constant time at any depth, no drift.
> The cost is that you can't jump to page twenty-seven, which almost no API actually needs. The
> requirement is a stable, unique, indexed ordering — ties in the ordering field cause skipped or
> repeated rows, so I order by created-at plus id. And a `max_page_size` always, or a client asks for
> a million rows and I comply.

**Q: What's the security risk in DRF's filtering?**

> An open search box on an unindexed column is a denial-of-service vector you published deliberately.
> `SearchFilter` with an `icontains` on a non-indexed field compiles to `LIKE '%term%'`, which is a
> full table scan that any anonymous user can trigger on demand against your largest table.
> `OrderingFilter` with `ordering_fields = "__all__"` is the same problem through a different query
> parameter — the client sorts by whatever unindexed column they like. So I enumerate the allowed
> filter and ordering fields explicitly, index what I allow, and use Postgres full-text or a trigram
> index for real search. It's the same principle as everywhere else: allow-list rather than
> deny-list, and never let untrusted input choose the query plan.

## 🎙️ Articulation drill

**Two minutes: "How do you secure a DRF API?"**

Lead with the mechanic, because it's the thing that separates someone who has run DRF from someone
who has read the docs: `has_object_permission` isn't called on list or create, so isolation in a
permission class means your list endpoint returns everyone's data while every detail test passes.
Then the fix and its two side benefits — scoped queryset gives you 404 instead of 403 and removes the
code path entirely. Then default-deny with a route-table test, and the auth choice framed as the
cookie-versus-token trade with the JWT revocation caveat stated honestly. Close on the two things
people leave open by accident: **DRF's throttle is a coarse guard, not a defence — non-atomic,
per-process by default, and IP-keyed — and an unindexed search filter is a full-table-scan endpoint
you published with a search box on it.**
