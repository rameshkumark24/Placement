# Part 1 — ⭐⭐ The method

```
⭐⭐ SIX STEPS. THE ORDER IS THE SKILL.
⭐
⭐ 1. ⭐⭐ REPRODUCE IT RELIABLY.
⭐      ⇒ ⭐⭐ A BUG YOU CANNOT REPRODUCE IS A BUG YOU CANNOT CONFIRM YOU FIXED.
⭐        ⭐ Everything after this is worthless without it — you will "fix" it,
⭐        deploy, and find out in three weeks that you did not.
⭐      ⇒ ⭐ if it is intermittent, first work out what makes it MORE likely:
⭐        load, a specific tenant, a time of day, a cold cache.
⭐
⭐ 2. ⭐ WRITE IT DOWN. Exact input, exact output, expected output.
⭐      ⇒ ⭐⭐ AS A FAILING TEST if you can (Day 096) — then step 1 is permanent.
⭐
⭐ 3. ⭐⭐ ASK "WHAT CHANGED?" BEFORE ANYTHING ELSE.
⭐      ⇒ ⭐⭐ a deploy · a config change · a dependency upgrade · a data shape ·
⭐        a traffic pattern · someone else's service. ⭐ If it worked on Tuesday
⭐        and not on Wednesday, the cause is in the diff — and `git bisect`
⭐        (Day 087) turns that into ten tests.
⭐
⭐ 4. ⭐⭐ FORM A HYPOTHESIS THAT COULD BE WRONG.
⭐      ⚠️ "something is wrong with the cache" ⇒ ⭐ NOT a hypothesis. Untestable.
⭐      ⭐⭐ "the cache key omits the tenant id, so tenant B sees tenant A's row"
⭐        ⇒ ⭐⭐ TESTABLE, and it makes a PREDICTION: two tenants, same key.
⭐      ⇒ ⭐⭐ SAY THE PREDICTION OUT LOUD BEFORE YOU LOOK. If you were wrong,
⭐        you learned something. ⭐ If you never predict, you learn nothing and
⭐        you are just editing.
⭐
⭐ 5. ⭐⭐ TEST THE SMALLEST THING THAT DISTINGUISHES HYPOTHESES. ⭐ One change
⭐      at a time. Two changes and you cannot attribute the result (Day 091).
⭐
⭐ 6. ⭐ NARROW. Repeat until the surviving hypothesis is one line.
```

```
⭐⭐ AND THE MOVE THAT UNDERLIES ALL OF IT — BINARY SEARCH, IN FOUR DIMENSIONS:
⭐   OVER HISTORY   git bisect          ⇒ which COMMIT (Day 087)
⭐   OVER DATA      halve the input     ⇒ which RECORD
⭐   OVER CODE      log/assert midway   ⇒ which LAYER (Day 090)
⭐   OVER CONFIG    default everything, ⇒ which SETTING
⭐                  then re-add half
⭐   ⇒ ⭐⭐ EVERY ONE IS THE SAME MOVE: FIND A PLACE WHERE IT IS CORRECT AND A
⭐        PLACE WHERE IT IS WRONG, AND HALVE THE GAP. ⭐ Ten steps covers a
⭐        thousand possibilities, and it works when you have no idea what is wrong.
```

# Part 2 — ⭐ Reading a traceback properly

```python
Traceback (most recent call last):
  File "myapp/api/orders.py", line 42, in place_order       # ⭐ YOUR code — the path in
    return service.place(payload)
  File "myapp/services/orders.py", line 88, in place        # ⭐⭐ YOUR LAST FRAME ← start here
    total = pricing.total(order.items)
  File "site-packages/somelib/money.py", line 210, in total # ⭐ library code
    return sum(i.price for i in items)
TypeError: unsupported operand type(s) for +: 'int' and 'str'   # ⭐ WHAT happened
```

```
⭐⭐ HOW TO READ IT — THREE PASSES, IN THIS ORDER:
⭐   1. ⭐⭐ THE BOTTOM LINE: what went wrong (the exception and its message).
⭐   2. ⭐⭐ YOUR LAST FRAME — the deepest file that belongs to YOU. ⭐ That is
⭐        almost always where the bad value was passed in, even though the
⭐        exception was raised inside a library.
⭐   3. ⭐ TOP-DOWN for the path, when the *route* to that call is the question.
⭐   ⇒ ⭐⭐ AND WITH `raise ... from` (Day 059) YOU GET TWO TRACEBACKS JOINED BY
⭐        "The above exception was the direct cause of…". ⭐⭐ READ THE FIRST ONE:
⭐        it is the original cause; the second is the translation.
```

⚠️ ⭐ **The most common misreading is stopping at the last line of the traceback**, which is usually
library code and usually not where the bug is. ⭐⭐ **Your last frame is the useful one.**

# Part 3 — ⭐⭐ `pdb`

```python
breakpoint()                       # ⭐⭐ 3.7+. Honours PYTHONBREAKPOINT — set it to
                                   #    0 to disable all of them, or to your IDE's hook.
```

| ⭐ Command | |
|---|---|
| `n` / `s` | next line / **step into** |
| ⭐ `c` / `q` | continue / quit |
| ⭐⭐ `l` / `ll` | source around here / the whole function |
| ⭐⭐ `p x` / `pp x` | print / **pretty-print** |
| ⭐⭐ `w` (`where`) | ⭐ the stack — **where am I** |
| ⭐ `u` / `d` | **up / down a frame** — ⭐⭐ inspect the caller's variables |
| `b file:42` / `b` | set a breakpoint / list them |
| ⭐ `b 42, x > 100` | ⭐⭐ a **conditional** breakpoint — the loop-iteration saver |
| `until 60` | run until past line 60 — ⭐ escape a loop |
| ⭐ `retval` | the return value of the frame you just stepped out of |
| ⭐⭐ `interact` | ⭐ a full REPL with the frame's locals |

```
⭐⭐ POST-MORTEM — DEBUG A CRASH THAT ALREADY HAPPENED, WITH THE STATE INTACT:
⭐   python -m pdb -c continue app.py   ⇒ runs; on an exception, drops into pdb
⭐   pytest --pdb                        ⇒ ⭐⭐ drops in AT THE FAILING ASSERTION
⭐   pytest -x --pdb --lf                ⇒ ⭐⭐ THE INNER LOOP: last failure, stop
⭐                                          at the first, debugger open, state alive
⭐   import pdb; pdb.pm()                ⇒ post-mortem on the last traceback in a REPL
⭐
⭐   ⇒ ⭐⭐ THIS IS THE BIGGEST WIN AVAILABLE FOR A FAILING TEST, and most people
⭐        never use it: instead of adding prints and re-running, you are standing
⭐        inside the failed frame with every local variable still available.
```

⭐ **`breakpoint()` beats `print` for state and `print` beats `breakpoint()` for sequence.** ⭐⭐ When
the question is *"what is this value here"*, use the debugger; when it is *"in what order did these
happen, across threads or requests"*, use logging with a request id (Day 099A) — **a debugger changes
the timing and destroys the thing you are investigating.**

# Part 4 — ⭐ Bug classes and their tells

| ⭐ Symptom | ⭐⭐ Suspect first |
|---|---|
| ⭐⭐ **Works alone, fails in the suite** | ⭐⭐ Shared state / order dependence (Days 092, 093) |
| ⭐ Fails only in CI | ⭐ Timezone, locale, resources, parallelism, missing env var |
| ⭐⭐ **Works in dev, fails in prod** | ⭐⭐ Config, data shape, scale, permissions (Day 078) |
| ⭐ Works the first time, then not | ⭐ Caching, or state that was not reset |
| ⭐⭐ **Disappears when you add logging** | ⭐⭐ A race — you changed the timing (Day 067) |
| Intermittent under load only | ⭐ Concurrency, pool exhaustion, a timeout |
| ⭐ Wrong number, no error | ⭐⭐ Float or rounding (Day 041), or a join fan-out (Part 5) |
| ⭐ Slower over time, then a restart fixes it | ⭐⭐ A leak — memory, fds, or connections (Day 082) |

```
⭐⭐ WHEN YOU ARE STUCK — AND THESE ARE NOT JOKES, THEY ARE THE HIGHEST-YIELD
⭐   MOVES AVAILABLE AFTER AN HOUR:
⭐   1. ⭐⭐ EXPLAIN IT ALOUD TO SOMEONE (or to nobody). ⭐ Articulating forces
⭐        you to state assumptions, and you will hear the wrong one yourself.
⭐        ⭐⭐ This is the same mechanism as this roadmap's articulation drills.
⭐   2. ⭐⭐ QUESTION AN ASSUMPTION YOU HAVE NOT CHECKED. "The config is loaded."
⭐        "This function is even called." ⭐ Put a print at the top. It is
⭐        embarrassing how often it is not called.
⭐   3. ⭐ TAKE A BREAK. Genuinely effective, and there is no substitute.
⭐   4. ⭐⭐ RE-READ THE ERROR MESSAGE. Slowly. All of it. It very often says
⭐        exactly what is wrong, and you skimmed it forty minutes ago.
```

# Part 5 — D-08 · ⭐⭐ Joins, and the fan-out that breaks your `SUM`

| Join | ⭐ Returns |
|---|---|
| ⭐ `INNER` | rows with a match on both sides |
| ⭐⭐ `LEFT` | all of A; NULLs where B has no match |
| `RIGHT` | ⭐ all of B — *write it as a LEFT with the tables swapped, for readability* |
| `FULL OUTER` | everything from both |
| ⭐ `CROSS` | ⭐⭐ every combination — `σ(A × B)` with no σ (Day 095) |
| ⭐ **Self join** | ⭐ a table to itself — employee → manager |
| ⭐⭐ **Semi** (`EXISTS`) | rows of A that **have** a match — ⭐ no columns from B, **no duplication** |
| ⭐⭐ **Anti** (`NOT EXISTS`) | rows of A with **no** match — ⭐ the "customers who never ordered" query |

```
⭐⭐ THE FAN-OUT BUG — the most expensive silent SQL error after NULL, and the
⭐   reason people distrust their own dashboards:
⭐
⭐   orders (1) ──< order_items (many)
⭐   SELECT SUM(o.total) FROM orders o JOIN order_items i ON i.order_id = o.id;
⭐   ⇒ ⚠️⚠️ ⭐⭐ AN ORDER WITH 3 ITEMS APPEARS 3 TIMES ⇒ ITS TOTAL IS COUNTED
⭐        THREE TIMES. ⭐ No error. Just a revenue figure that is too high, on a
⭐        dashboard somebody is making decisions with.
⭐   ⇒ ⭐⭐ THE TELL: the number is plausible but wrong, and it gets worse as
⭐        the child table grows.
⭐
⭐   ⭐⭐ THE THREE FIXES:
⭐     · ⭐ aggregate the child side FIRST, in a subquery, then join
⭐     · ⭐⭐ SUM(DISTINCT …) only if the values are genuinely unique — ⚠️ two
⭐          orders of exactly £30 would collapse into one. ⭐ Usually wrong.
⭐     · ⭐⭐ IF YOU ONLY NEED "DOES A CHILD EXIST", USE A SEMI-JOIN (`EXISTS`)
⭐          ⇒ ⭐⭐ IT CANNOT DUPLICATE ROWS, BY CONSTRUCTION. ⭐ This is the real
⭐          lesson: choosing the right join type removes the class of bug.
⭐   ⇒ ⭐ AND THE GENERAL RULE: `SELECT DISTINCT` added to "fix duplicates" is
⭐        almost always a fan-out you have not diagnosed.
```

⭐ **Join order does not change the *result* of inner joins** (they are commutative and associative)
— **but it changes the plan**, and the planner reorders them for you using the algebra from Day 095.
⭐⭐ **`EXPLAIN ANALYZE` is where you find out what it actually chose**, and Stage 5 is thirty days of
that.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Changing code before reproducing** | ⭐⭐ You cannot confirm a fix for a bug you cannot trigger. |
| ⭐ An untestable hypothesis | ⭐⭐ Make a prediction that could be wrong, and say it before you look. |
| Changing two things at once | ⭐ You cannot attribute the result. |
| ⭐ Skipping "what changed?" | ⭐⭐ If it worked Tuesday, the cause is in the diff. Bisect. |
| Reading only the traceback's last line | ⭐⭐ That is usually library code. Find **your** last frame. |
| ⭐ Ignoring the first traceback in a chain | ⭐ It is the original cause. |
| `print` debugging a race | ⭐⭐ You changed the timing. Logging with ids, or `py-spy`. |
| ⭐ Not using `pytest --pdb` | ⭐⭐ You are standing in the failed frame with all locals alive. |
| Stepping through a loop with `n` | ⭐ Conditional breakpoint: `b 42, x > 100`. |
| ⭐ Not re-reading the error message | ⭐ It often says exactly what is wrong. |
| ⭐⭐ **`JOIN` to a one-to-many then `SUM`** | ⭐⭐ Fan-out — the total is multiplied. Aggregate first, or use `EXISTS`. |
| `SELECT DISTINCT` to remove duplicates | ⭐ Usually an undiagnosed fan-out. |
| `NOT IN` on a nullable column | ⭐ Returns nothing (Day 097). `NOT EXISTS`. |

## Interview questions

**Q: Walk me through how you debug something you don't understand.**
> Reproduce it reliably first, because a bug I can't trigger is one I can't confirm I've fixed — and
> if I can, I turn the reproduction into a failing test so it's permanent. Then, before anything else,
> "what changed?" — a deploy, a config change, a dependency bump, a data shape — because if it worked
> on Tuesday the cause is in the diff, and `git bisect` turns a thousand commits into ten tests. Then
> I form a hypothesis specific enough to be wrong: not "something's wrong with the cache" but "the
> cache key omits the tenant id, so tenant B sees tenant A's row" — that makes a prediction I can
> check. Then I test the smallest thing that distinguishes hypotheses, one change at a time, and
> narrow. The underlying move throughout is binary search: find a place where it's correct and a place
> where it's wrong, and halve the gap.

**Q: How do you read a traceback?**
> Bottom line first for what went wrong, then I find my last frame — the deepest file that belongs to
> me. The final frame is usually library code and usually not where the bug is; my last frame is where
> the bad value got passed in. Then top-down if the route to that call is the question. And with
> chained exceptions from `raise ... from`, I read the *first* traceback, because that's the original
> cause and the second is just the translation at the layer boundary.

**Q: What's your `pdb` workflow?**
> `breakpoint()` rather than `import pdb`, so `PYTHONBREAKPOINT` can disable them all or route to an
> IDE. The commands I actually use are `w` for where I am, `u`/`d` to move up into the caller's frame
> — which is usually where the interesting variables are — `pp` for structures, and conditional
> breakpoints like `b 42, x > 100` so I'm not stepping through ten thousand loop iterations. But the
> highest-value thing is post-mortem: `pytest -x --pdb --lf` drops me straight into the failing
> assertion with every local still alive, instead of adding prints and re-running. Most people never
> use it.

**Q: When do you not use a debugger?**
> When the question is about sequence or timing rather than state. A debugger changes timing, so
> attaching one to a race often makes it disappear — which is itself diagnostic, but useless for
> fixing. There I'd use logging with a request id, or `py-spy` from outside the process. The rule I
> use: debugger for "what is this value here", logs for "in what order did these happen across
> threads or requests".

**Q: Your revenue dashboard is showing numbers that are too high. First guess?**
> A join fan-out. If you join orders to order_items and sum the order total, an order with three items
> appears three times and its total is counted three times. There's no error — just a plausible,
> wrong number that gets worse as the child table grows. The fixes are to aggregate the child side in
> a subquery before joining, or — if you only need to know whether a child exists — use a semi-join
> with `EXISTS`, which can't duplicate rows by construction. That's the real lesson: choosing the
> right join type removes the class of bug. And a `SELECT DISTINCT` that was added to "fix
> duplicates" is almost always an undiagnosed fan-out.

## 🎙️ Articulation drill

Record two minutes: **"Tell me about a difficult bug you debugged."** — asked in almost every
interview, and answered badly by almost everyone, because they tell the story instead of the method.

⭐ **Structure the answer as symptom → method → cause → prevention**, and let the method be the star:
**"the symptom was X. What made it hard was Y. Here's how I narrowed it, the cause was Z, and here's
what I changed so it can't recur."**

⭐⭐ **Spend most of the time on the narrowing, because that is the transferable part:** *"the first
thing I did was make it reproducible — it was intermittent, so I looked for what made it more likely,
and it turned out to be load rather than a specific input. Then I asked what changed, because it
worked the previous week, and bisected the deploy range. Then I formed a hypothesis specific enough to
be wrong — not 'something's wrong with the cache' but 'the cache key omits the tenant id, so under
concurrency tenant B can read tenant A's row' — which makes a prediction I could check with two
requests."*

⭐⭐ **Include one thing you got wrong, because it makes the whole answer credible:** *"my first
hypothesis was wrong — I assumed the config was loaded and never checked. I lost half an hour to that,
and the lesson I actually took is to verify the assumption I haven't checked before the one I have."*

⭐ **Close on prevention, which is what separates a story from an engineer:** *"then I wrote the
failing test first, before the fix, so I could prove I'd reproduced the reported problem rather than
something adjacent — and now that bug can't come back silently. And I added the request id to the log
lines, because the reason it took a day rather than an hour was that I couldn't tell which lines
belonged to which request."*
