# Part 1 — ⭐⭐ Resolution, in full

```
⭐⭐ You type example.com. In order, each step stopping if it finds an answer:

⭐ 1. BROWSER CACHE          ⭐ chrome://net-internals/#dns — its own TTL, often ~60 s
⭐ 2. OS CACHE               ⭐ the stub resolver
⭐ 3. /etc/hosts             ⭐⭐ a FILE. It wins over everything below. Remember this at 2am.
⭐ 4. RECURSIVE RESOLVER     ⭐ your ISP's, or 8.8.8.8 / 1.1.1.1 — ⭐⭐ this is where caching really happens
⭐        │ if not cached, it does the walk:
⭐ 5.     ├─▶ ROOT server (13 logical sets)    "ask the .com servers, here they are"
⭐ 6.     ├─▶ TLD server (.com)                "ask example.com's nameservers, here they are"
⭐ 7.     └─▶ AUTHORITATIVE server             ⭐⭐ "example.com is 93.184.216.34, TTL 3600"
⭐ 8. the resolver CACHES it for the TTL and returns it to you
```

| ⭐ Term | ⭐ Meaning |
|---|---|
| ⭐⭐ **Recursive resolver** | ⭐⭐ does the whole walk **for** you and caches the result — the only party that caches at scale |
| **Authoritative server** | holds the actual records for a zone |
| ⭐⭐ **TTL** | ⭐⭐ **how long anyone may cache this answer** — the single most consequential number in DNS |
| **Zone** | a domain and its records |
| **Glue record** | an A record for a nameserver inside the zone it serves — breaks the chicken-and-egg |

## ⭐ The record types you must know

| Type | Holds | ⭐ Note |
|---|---|---|
| ⭐ **A** | an IPv4 address | |
| **AAAA** | an IPv6 address | |
| ⭐ **CNAME** | an alias to another name | ⭐⭐ **cannot exist at the zone apex** — a real constraint (Stage 11) |
| **MX** | mail servers, with priority | |
| ⭐ **TXT** | arbitrary text | ⭐ domain verification, SPF, DKIM |
| **NS** | the nameservers for a zone | |
| ⭐ **SOA** | zone metadata, incl. the negative-caching TTL | |

⚠️ ⭐⭐ **The CNAME-at-apex restriction bites everyone once.** `example.com` cannot be a CNAME, so
pointing a bare domain at a load balancer whose address changes needs a provider-specific record type
(Route 53's alias records, for instance). **You will meet this on your first real deployment.**

# Part 2 — ⭐⭐ TTL, and why DNS changes "take hours"

```
⭐ TTL = 3600 means: any cache may hold this answer for an hour.
⭐   ⇒ ⭐⭐ You change the record. Resolvers that cached it 5 minutes ago keep the OLD value for 55 more.
⭐   ⇒ ⭐⭐ There is NO invalidation. You cannot push an update. You can only WAIT OUT the TTL.
⭐   ⇒ ⭐⭐ And some resolvers and applications ignore the TTL entirely and cache longer.
```

| ⭐ Consequence | |
|---|---|
| ⭐⭐ **Lower the TTL BEFORE a migration** | ⭐⭐ drop to 60 s a day ahead, migrate, then raise it back |
| ⭐ Low TTL costs | more queries, more latency, more load on your authoritative servers |
| ⭐⭐ **DNS failover is minutes, not seconds** | ⭐⭐ detection + TTL + resolvers that ignore TTL + **a long tail that never moves** |
| ⭐ Negative caching | ⭐ NXDOMAIN is cached too — a typo can "stick" |

> ⭐⭐ **This is why DNS is a disaster-recovery mechanism and not a high-availability one.** Within a
> region, availability comes from a load balancer that fails over in seconds without involving
> clients. You will make exactly this argument in Stage 11 — **today is where the reason is
> established.**

## ⭐⭐ The Python-specific trap, established early

```python
# Python's socket layer does NOT cache DNS itself — the OS and the resolver do.
# ⭐⭐ But long-lived clients and connection pools DO hold on to resolved addresses.
import socket
print(socket.gethostbyname("example.com"))     # ⭐ one lookup

# ⭐⭐ A pooled HTTP client or a database driver may resolve ONCE at startup and reuse
# ⭐   that address for the process's lifetime.
# ⭐ ⇒ ⭐⭐ Your DNS-based failover completes; your long-running worker never notices.
```

⚠️ ⭐⭐ **Write this in your notes now: "a long-lived client may hold a resolved address for the life
of the process."** In Stage 11 you will meet the AWS version of this — a database fails over by
repointing DNS, and a worker with a warm connection pool keeps talking to the old address. **The fix
is bounded connection lifetimes and validating connections**, and knowing to look for it is the whole
skill.

# Part 3 — ⭐ Doing it by hand

```bash
dig example.com                     # ⭐ the answer, with the TTL — watch it count DOWN on repeat
dig +trace example.com              # ⭐⭐ the FULL walk: root → TLD → authoritative. Run this one.
dig example.com NS                  # its nameservers
dig @8.8.8.8 example.com            # ask a specific resolver
dig example.com +short              # just the answer
dig -x 93.184.216.34                # reverse lookup
```

⭐⭐ **Run `dig +trace` once and read every line.** You will see the root servers answer, then the
`.com` servers, then the authoritative ones. **It is the clearest possible demonstration that DNS is
a hierarchy of delegations rather than a database.**

⭐ **Run `dig example.com` twice in a row** and watch the TTL in the answer decrease. That is the
resolver's cache counting down in front of you.

# Part 4 — C-05 · ⭐⭐ TCP reliability

## Retransmission

```
⭐ Sender transmits bytes 1000–1499 and starts a timer.
⭐   ACK arrives  ⇒ ⭐ good, move on
⭐   ⭐⭐ Timer expires (RTO) ⇒ ⭐⭐ RETRANSMIT
⭐ ⇒ ⭐ The RTO is derived from measured round-trip time plus its variance — it ADAPTS.
⭐ ⇒ ⭐⭐ FAST RETRANSMIT: three duplicate ACKs mean "I am still missing that one" ⇒ resend
⭐     immediately without waiting for the timer.
```

⭐⭐ **Fast retransmit matters because the timeout is deliberately conservative** — waiting for it
would add hundreds of milliseconds. Three duplicate ACKs are strong evidence of a single lost segment
while later ones are arriving fine, so the sender acts on that evidence rather than on the clock.

## ⭐⭐ The sliding window and flow control

```
⭐ Sending one segment and waiting for its ACK would cap you at one segment per round trip.
⭐ ⇒ ⭐⭐ Instead: send a WINDOW of unacknowledged data, and slide it forward as ACKs arrive.

⭐⭐ THE RECEIVER ADVERTISES ITS WINDOW in every ACK: "I have room for 64 KB."
⭐   ⇒ ⭐⭐ FLOW CONTROL: the receiver protects itself from a faster sender.
⭐   ⇒ ⭐⭐ Window = 0 means STOP. The sender waits and probes.
```

| ⭐ Concept | ⭐ Why it matters to you |
|---|---|
| ⭐⭐ **Bandwidth-delay product** | ⭐⭐ **max throughput = window ÷ RTT** |
| ⭐ Worked example | ⭐ 64 KB window, 130 ms RTT ⇒ **~500 KB/s**, no matter how fat the pipe |
| ⭐⭐ **Window scaling** | ⭐⭐ the TCP option that allows windows beyond 64 KB — **without it, long-distance transfers are capped** |
| ⭐ Flow control ≠ congestion control | ⭐⭐ flow control protects the **receiver**; congestion control protects the **network** (Day 008) |

⭐⭐ **That worked example is worth internalising.** It explains why a transfer across the world can be
slow on a gigabit link, and it is the same shape as Little's Law in Stage 9 — **throughput is limited
by how much you can have in flight divided by how long each item takes.** You will meet that formula
three more times in this roadmap under different names.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Expecting a DNS change to apply immediately** | ⭐⭐ There is no invalidation. You wait out the TTL — and some caches ignore it. |
| Not lowering the TTL before a migration | ⭐ Do it a day ahead, then raise it after. |
| ⭐⭐ **Treating DNS as a failover mechanism** | ⭐⭐ Minutes, plus a tail that never moves. It is disaster recovery, not HA. |
| Forgetting `/etc/hosts` wins | ⭐ It overrides everything below it, and it is invisible until you check. |
| Trying to CNAME the zone apex | ⭐ Not allowed; you need a provider alias record. |
| ⭐ Ignoring that clients cache resolved addresses | ⭐⭐ A pooled client can hold an address for the process's lifetime. |
| Confusing flow control with congestion control | ⭐ Receiver protection vs network protection. |
| "A gigabit link means gigabit throughput" | ⭐⭐ Throughput = window ÷ RTT until window scaling is in play. |

## Interview questions

**Q: Walk me through what happens when you type a domain name.**
> Browser cache, then OS cache, then `/etc/hosts`, then the recursive resolver. If the resolver has no
> cached answer it walks the hierarchy: a root server delegates to the `.com` servers, those delegate
> to the domain's authoritative nameservers, and the authoritative server returns the record with a
> TTL. The resolver caches it for that TTL and answers you. The important structural point is that
> DNS is a hierarchy of delegations rather than one database, and the only party caching at scale is
> the recursive resolver.

**Q: You changed a DNS record and some users still hit the old server. Why?**
> Because DNS is a distributed cache with no invalidation. Every resolver that fetched the record
> before your change holds it until its TTL expires, and you cannot push an update — you can only wait.
> Worse, some resolvers and some client libraries ignore the TTL and cache longer. That is why you
> lower the TTL a day before a migration and raise it afterwards, and why DNS failover is a
> disaster-recovery mechanism rather than a high-availability one.

**Q: What is the difference between flow control and congestion control?**
> Flow control protects the receiver: it advertises a window saying how much unacknowledged data it
> can buffer, and the sender must not exceed it. Congestion control protects the network: the sender
> infers available capacity from loss and delay and limits itself accordingly. They are separate
> mechanisms with separate windows, and the effective send rate is the minimum of the two.

**Q: Why can a transfer be slow on a fast link?**
> Because throughput is the window divided by the round-trip time. With a sixty-four kilobyte window
> and a hundred and thirty millisecond round trip you get about five hundred kilobytes a second no
> matter how much bandwidth exists, because you can only have one window in flight at a time. That is
> what TCP window scaling exists to fix. It is the same shape as Little's Law — throughput equals
> concurrency divided by latency — and it turns up repeatedly in system design.

**Q: What is fast retransmit and why does it exist?**
> When a receiver gets out-of-order segments it re-acknowledges the last in-order byte, so three
> duplicate acknowledgements are strong evidence that one specific segment was lost while later ones
> arrived. The sender retransmits immediately rather than waiting for the retransmission timeout,
> which is deliberately conservative and would otherwise cost hundreds of milliseconds. It is acting
> on evidence instead of on a clock.
