**P-257** · 🏗 **The web layer** — ⭐⭐ schemas as a security control, and one exception handler

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: your response schema is a security control, not a serialisation
> convenience — and the test that proves it is one that asserts the *absence* of a field.**
>
> ⭐ The web layer should be the most boring code in the project: parse, authenticate, call, translate.
> ⭐⭐ It becomes the most dangerous when a schema is reused in both directions, because that is how
> a client sets a field you never meant to expose.

# Part 1 — ⭐ Four jobs, and nothing else

```python
@router.post("/{job_id}/dispatch", response_model=JobResponse,
             status_code=200,
             responses={409: {"model": ErrorResponse}})
def dispatch(
    job_id: JobId,
    body: DispatchRequest,                          # ⭐ ① PARSE + VALIDATE
    actor: Principal = Depends(require_role("dispatcher")),  # ⭐ ② AUTH
    uow: UnitOfWork = Depends(get_uow),
    idem: str | None = Header(None, alias="Idempotency-Key"),
) -> JobResponse:
    view = job_service.dispatch_job(                # ⭐ ③ CALL
        uow, actor, job_id, body.technician_id,
        TimeWindow(body.start, body.end), now=utcnow(), key=idem)
    return JobResponse.from_view(view)              # ⭐ ④ TRANSLATE
# ⭐⭐ NO `try`. NO STATUS-CODE LOGIC. NO BUSINESS RULE. If a router has
#    an `if`, ask which layer that `if` belongs to — the answer is
#    almost never "this one".
```

# Part 2 — ⭐⭐ Request and response schemas are different types

```python
# ⭐⭐ THE MISTAKE THAT CAUSES MASS ASSIGNMENT (Day 175):
class Job(BaseModel):            # ❌ ONE model used for input AND output
    id: int
    tenant_id: int               # ⭐⭐ a client can now SET this
    state: str                   # ⭐⭐ …and this, skipping the state
    internal_cost_cents: int     #     machine entirely
    total_cents: int             # ⭐⭐ …and this leaks your margin
```

```python
# ✅ TWO TYPES, TWO DIRECTIONS, NO OVERLAP OF CONCERN
class DispatchRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")   # ⭐⭐ NON-NEGOTIABLE.
    technician_id: UserId                       #    An unknown field is
    start: AwareDatetime                        #    a 422, not silence —
    end:   AwareDatetime                        #    which turns a
                                                #    client's typo into
    @model_validator(mode="after")              #    an error instead of
    def window_is_positive(self):               #    a missing feature
        if self.end <= self.start:
            raise ValueError("end must be after start")
        return self

class JobResponse(BaseModel):
    id: JobId
    state: JobState
    customer_name: str
    scheduled_for: datetime
    total_cents: int
    available_actions: list[JobAction]   # ⭐⭐ published from the
                                         #    transition table (Day 254)
                                         #    so the UI never
                                         #    reimplements it
# ⭐⭐ NOTE WHAT IS ABSENT: `tenant_id`, `internal_cost_cents`,
#    `created_by_ip`. ⭐ The absence is the control.
```

```
⭐⭐ THE THREE RULES:
⭐  ① ⭐⭐ AN INPUT SCHEMA LISTS ONLY WHAT A CLIENT MAY SET. Anything a
⭐     client must not set is simply not a field — ⭐ not "read-only", not
⭐     "ignored later". ⭐⭐ ABSENT.
⭐  ② ⭐⭐ `extra="forbid"` ON EVERY INPUT MODEL. Without it, `{"tenant_id":
⭐     9}` is silently dropped today and silently ACCEPTED the day
⭐     someone adds that field. ⭐ Day 161: `extra="ignore"` is right for
⭐     EVENTS you consume; `extra="forbid"` is right for REQUESTS you own.
⭐  ③ ⭐⭐ AN OUTPUT SCHEMA IS AN ALLOWLIST. ⭐ `response_model` makes
⭐     FastAPI serialise through it, so an extra attribute on the object
⭐     cannot escape. ⭐⭐ THAT IS THE MECHANISM — and it fails the moment
⭐     someone returns a plain `dict` or sets `response_model=None`.
```

```python
# ⭐⭐ THE TEST THAT MAKES IT REAL — Day 184 #10, as one function:
FORBIDDEN = {"tenant_id", "internal_cost_cents", "password_hash",
             "created_by_ip", "deleted_at"}

@pytest.mark.parametrize("path", ALL_GET_PATHS)   # ⭐ from the route table
def test_no_response_leaks_internal_fields(client, path, seeded):
    body = client.get(path, headers=auth()).json()
    assert FORBIDDEN.isdisjoint(_all_keys(body)), path
# ⭐⭐ ASSERT THE ABSENCE. A test that checks the fields you EXPECT will
#    happily pass while a new one leaks — and the leak arrives via a
#    model change, not an endpoint change, which is why nobody reviews it.
```

# Part 3 — ⭐ Four levels of validation, and where each belongs

```
⭐   ① ⭐ FIELD    — type, range, length, format
⭐        `Field(ge=1)`, `AwareDatetime`, `EmailStr`
⭐        ⇒ ⭐ Pydantic, in the request schema. ⭐⭐ Rejects garbage
⭐          before a single line of your code runs.
⭐   ② ⭐ CROSS-FIELD — "end after start", "either X or Y"
⭐        ⇒ ⭐ `@model_validator`, still in the schema.
⭐   ③ ⭐⭐ DOMAIN   — "a job in `paid` cannot be dispatched"
⭐        ⇒ ⭐⭐ THE DOMAIN. Not the schema: the schema cannot see the
⭐          current state, and duplicating the state machine into
⭐          validation is how the two versions diverge.
⭐   ④ ⭐⭐ SYSTEM   — "no overlapping assignments", "this key is unique"
⭐        ⇒ ⭐⭐ THE DATABASE. It is the only layer that sees other rows
⭐          and other transactions (Day 250).

⭐ ⇒ ⭐⭐ THE DIAGNOSTIC: IF A VALIDATOR NEEDS A DATABASE QUERY, IT IS IN
⭐   THE WRONG LAYER. ⭐ A Pydantic validator that checks "does this
⭐   technician exist?" is a query in the parsing layer, it is a race
⭐   (checked before the write), and it is usually a foreign key you
⭐   already have.
```

# Part 4 — ⭐⭐ One exception handler, one translation table

```python
# ⭐⭐ ONE PLACE. If translation is scattered, two endpoints will
#    eventually disagree about what a conflict is.
TRANSLATION: dict[type[Exception], tuple[int, str]] = {
    NotFound:              (404, "not_found"),
    Forbidden:             (403, "forbidden"),
    InvalidTransition:     (409, "invalid_state_transition"),
    AssignmentConflict:    (409, "assignment_conflict"),
    IdempotencyKeyReuse:   (422, "idempotency_key_reuse"),
    RequestInProgress:     (409, "request_in_progress"),
    RateLimited:           (429, "rate_limited"),
}

@app.exception_handler(AppError)
async def app_error_handler(request: Request, exc: AppError):
    status, code = TRANSLATION[type(exc)]
    return JSONResponse(status_code=status, content={"error": {
        "code": code,
        "message": exc.public_message,      # ⭐⭐ PUBLIC. Never str(exc).
        "details": exc.details,
        "request_id": request.state.request_id,   # ⭐ Day 146
    }}, headers=exc.extra_headers)          # ⭐ Retry-After, WWW-Authenticate

@app.exception_handler(Exception)
async def unhandled(request: Request, exc: Exception):
    log.exception("unhandled", extra={"request_id": request.state.request_id})
    return JSONResponse(500, {"error": {
        "code": "internal_error",           # ⭐⭐ NOTHING ELSE. No type,
        "request_id": request.state.request_id}})   # no message, no trace
```

```
⭐⭐ FOUR THINGS THIS HANDLER GETS RIGHT THAT AD-HOC `try` BLOCKS DO NOT:
⭐  ① ⭐⭐ `exc.public_message`, NOT `str(exc)`. ⭐ `str(exc)` on a
⭐     database error contains your SQL and your column names.
⭐  ② ⭐ THE REQUEST ID IS ON EVERY ERROR, INCLUDING THE 500 — which is
⭐     the only one where you will actually need it.
⭐  ③ ⭐ Headers travel with the exception, so `Retry-After` and
⭐     `WWW-Authenticate` cannot be forgotten by one endpoint.
⭐  ④ ⭐⭐ THE CATCH-ALL EXISTS. Without it, an unexpected exception
⭐     produces a framework default page whose body you do not control.

⭐⭐ AND THE VALIDATION HANDLER — override FastAPI's default so a 422
⭐   from Pydantic has THE SAME SHAPE as everything else. ⭐ Otherwise
⭐   your API has two error formats and every client handles both.
```

# Part 5 — ⭐ The dependency chain

```python
# ⭐⭐ ORDER MATTERS — each depends on the previous, so failure is
#    ordered too: no token ⇒ 401 before any tenant lookup happens.
def get_request_id(request: Request) -> str: ...        # ⭐ Day 146
def get_principal(token = Depends(bearer)) -> Principal: ...   # ⭐ 401
def get_tenant_session(p = Depends(get_principal)):     # ⭐⭐ SET LOCAL
    with session_factory() as s:                        #    app.tenant_id
        s.execute(text("SET LOCAL app.tenant_id = :t"), {"t": p.tenant_id})
        yield s                                         # ⭐⭐ LOCAL, or
def require_role(*roles):                               #    it leaks to
    def dep(p = Depends(get_principal)):                #    the next
        if p.role not in roles: raise Forbidden()       #    borrower
        return p                                        #    (Day 197)
    return dep
```

```
⭐⭐ AND THE THREE THINGS PEOPLE GET WRONG HERE:
⭐  ① ⭐⭐ AUTH IS A DEPENDENCY, NOT MIDDLEWARE (Day 140). Middleware
⭐     runs BEFORE routing, so it must match paths by prefix — which
⭐     means it 401s your CORS preflight and misses the route someone
⭐     registers under a new prefix. ⭐⭐ A dependency is attached to the
⭐     ROUTE, so a new route without it is visible in the router table.
⭐  ② ⭐ `Depends` WITH `yield` IS THE TEARDOWN SEAM. The `SET LOCAL`
⭐     and the session close both happen there — ⭐⭐ and note the
⭐     ordering trap: FastAPI runs teardown AFTER the response is
⭐     generated, so anything lazily evaluated in the response is
⭐     evaluated after the session closed. ⭐ Another reason schemas are
⭐     built from views, not entities (Day 256).
⭐  ③ ⭐⭐ `dependency_overrides` IS THE TESTING SEAM (Day 141) — and the
⭐     rule from Day 165 applies: ⭐⭐ THE AUTHORISATION TEST FILE
⭐     OVERRIDES NOTHING. If your auth tests stub `get_principal`, they
⭐     test your stub.
```

```python
# ⭐⭐ THE ROUTE-TABLE TEST — Day 184 #12, and it catches the route
#    somebody registers on a Friday:
def test_every_route_is_authenticated():
    for route in app.routes:
        if route.path in PUBLIC_PATHS: continue
        deps = {d.call for d in route.dependant.dependencies}
        assert get_principal in _flatten(deps), route.path
```

## Common mistakes

| Mistake | Correction |
|---|---|
| One Pydantic model for input and output | That's mass assignment — a client sets `tenant_id` or `state`. |
| Marking sensitive fields read-only instead of omitting them | Absent is a control; "read-only" is a convention. |
| No `extra="forbid"` on request models | An unknown field is silently dropped until the day it's silently accepted. |
| Returning a plain `dict` or `response_model=None` | The allowlist mechanism is bypassed. |
| Testing that expected fields are present | It passes while a new field leaks. Assert the absence. |
| A Pydantic validator that queries the database | Wrong layer, it's a race, and it's usually a foreign key. |
| Duplicating the state machine into request validation | The schema can't see current state; the two versions diverge. |
| `try/except` in routers | Two endpoints will eventually disagree about what a conflict is. |
| `str(exc)` in an error response | It contains your SQL and column names. |
| No catch-all handler | An unexpected exception renders a body you don't control. |
| FastAPI's default 422 shape | Your API now has two error formats and clients handle both. |
| Auth as middleware | It runs before routing, matches by prefix, and 401s CORS preflights. |
| Stubbing `get_principal` in authorisation tests | You tested your stub. |
| No route-table test | The route registered on a Friday has no auth and nothing says so. |
| Lazily evaluating anything in the response | Dependency teardown has already closed the session. |

## Interview questions

**Q: Why do you have separate request and response schemas?**

> Because a single model used in both directions is mass assignment. If the same class defines
> `tenant_id`, `state` and `internal_cost_cents`, then a client can set the tenant, skip the state
> machine by setting the state directly, and read your margin — all without anyone writing a line of
> code intending it. So an input schema lists only what a client may set, and anything they may not set
> is *absent* rather than marked read-only, because absent is a control and a convention isn't. Every
> input model gets `extra="forbid"`, which turns an unknown field into a 422 instead of silence —
> otherwise `{"tenant_id": 9}` is quietly ignored today and quietly accepted the day someone adds that
> field. And the output schema is an allowlist: FastAPI serialises through `response_model`, so an
> extra attribute can't escape unless someone returns a raw dict.

**Q: How do you prove your API doesn't leak internal fields?**

> With a test that asserts the *absence*. I keep a set of forbidden key names — `tenant_id`,
> `password_hash`, `internal_cost_cents`, `created_by_ip` — and parametrise over every GET route from
> the app's route table, recursing through the response body and asserting the sets are disjoint. The
> reason it has to be absence rather than presence is that a test checking the fields you expect will
> pass perfectly while a new one leaks — and the leak almost always arrives via a model change rather
> than an endpoint change, which is exactly the kind of diff nobody reviews carefully. It's one
> function, it covers every endpoint including the ones added later, and it's the concrete form of
> treating the schema as a security control.

**Q: Where does validation belong?**

> Four levels, and the diagnostic is simple: if a validator needs a database query, it's in the wrong
> layer. Field-level — types, ranges, formats — is Pydantic in the request schema, so garbage is
> rejected before any of my code runs. Cross-field, like "end after start", is a model validator, still
> in the schema. Domain rules like "a paid job cannot be dispatched" belong in the domain, because the
> schema can't see current state and duplicating the state machine into validation is how the two
> versions drift apart. And system-level rules — no overlapping assignments, this key is unique —
> belong in the database, because it's the only layer that sees other rows and other transactions. The
> anti-pattern I'd name is a Pydantic validator checking whether a technician exists: it's a query in
> the parsing layer, it's a race because it's checked before the write, and it's usually a foreign key
> you already have.

**Q: How is error handling structured?**

> One exception handler with one translation table mapping exception types to a status and a stable
> error code, plus a catch-all. Scattering `try/except` through routers guarantees that two endpoints
> eventually disagree about what a conflict is. Four things the central handler gets right: it uses a
> deliberate `public_message` rather than `str(exc)`, because stringifying a database error puts your
> SQL and column names in the response; the request id is on every error including the 500, which is
> the one where you actually need it; headers like `Retry-After` and `WWW-Authenticate` travel with the
> exception so one endpoint can't forget them; and the catch-all exists at all, so an unexpected
> exception doesn't render a framework page whose body you don't control. I'd also override FastAPI's
> default validation handler so a Pydantic 422 has the same shape as everything else — otherwise the
> API has two error formats and every client has to handle both.

**Q: Why is authentication a dependency rather than middleware?**

> Because middleware runs before routing, so it has to match paths by prefix rather than knowing which
> endpoint was hit. That produces four failures: it 401s CORS preflight requests, it misses routes
> registered under a prefix nobody added to the list, it can't express per-route requirements like
> "this one needs the dispatcher role", and the protection is invisible at the endpoint. A dependency
> attaches to the route, so requirements are visible where the endpoint is defined and a new route
> without one is detectable — which I make concrete with a test that walks the app's route table and
> asserts every non-public route depends on `get_principal`. That test is what catches the endpoint
> someone adds on a Friday. And the corresponding rule for the authorisation tests is that they
> override nothing: if they stub the principal dependency, they've tested the stub.

## 🎙️ Articulation drill

**Two minutes: "How do you keep an API layer safe and boring?"**

Open with the four jobs and the size test, then go straight to the schema argument, because it's the
one with a real vulnerability attached: **one model for input and output is mass assignment — a client
sets the tenant, skips the state machine, and reads your internal cost.** Say that anything a client
may not set is absent rather than read-only, and that `extra="forbid"` turns a typo into a 422 instead
of silence. Then the proof: **a test that asserts the absence of forbidden field names across every
route**, and why absence rather than presence — a leak arrives via a model change, which is the diff
nobody reviews. Then error handling in one sentence: one table, one handler, `public_message` rather
than `str(exc)`, request id on everything. Close on auth as a dependency rather than middleware, with
the concrete reason — **middleware runs before routing, so it matches by prefix and 401s your CORS
preflight** — and the route-table test that catches the endpoint added on a Friday.
