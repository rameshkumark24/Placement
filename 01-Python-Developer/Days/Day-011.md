# Day 011

**L-011** · ⭐⭐ **HTTP evolution** — 1.0 → 1.1 (keep-alive) → 2 (multiplexing) → 3 (QUIC)

**Time:** 3 hrs · **Mode:** NEW

> No parallel track. This is a shorter day and it is **one idea repeated four times**: every HTTP
> version exists to remove round trips. You already know why round trips are expensive (Day 006),
> what a connection costs (Days 005, 008, 009) and what head-of-line blocking is (Day 008).
>
> ⭐⭐ **The sentence to own: the history of HTTP is the history of trying to stop paying for TCP.**

---

# Part 1 — ⭐ HTTP/1.0 — one request, one connection

```
⭐ 1996. Every request:
⭐   TCP handshake (1 RTT) ──▶ request ──▶ response ──▶ ⭐⭐ CLOSE
⭐
⭐ A page with 30 images = 30 connections = ⭐⭐ 30 handshakes, 30 cold congestion windows.
⭐   ⇒ ⭐⭐ At 100 ms RTT that is 3 seconds of pure waiting, before HTTPS existed to make it worse.
```

⭐ **No `Host` header** either — so one IP could serve exactly one site. That single omission is why
`Host` became mandatory in 1.1 (Day 010).

---

# Part 2 — ⭐⭐ HTTP/1.1 — keep-alive, and the limit that shaped the web

```
⭐⭐ KEEP-ALIVE: the connection stays open and is REUSED.
⭐   ⇒ one handshake, many requests
⭐   ⇒ ⭐⭐ and the congestion window stays warm (Day 008)

⭐⭐ BUT — the fatal limitation:
⭐   requests on one connection are STRICTLY SEQUENTIAL.
⭐   request A ──▶ response A ──▶ request B ──▶ response B
⭐   ⇒ ⭐⭐ a slow response A BLOCKS B behind it. HEAD-OF-LINE BLOCKING, at the HTTP layer.
```

⭐ **Pipelining** (send B before A returns) was specified and is effectively dead: responses still
had to come back **in order**, so one slow response still blocked the rest, and buggy proxies
mangled it. **Browsers disabled it.**

## ⭐⭐ The six-connection limit, and every hack it caused

```
⭐⭐ Browsers open ~6 parallel TCP connections PER DOMAIN. That number is why:
⭐   · ⭐ DOMAIN SHARDING — img1.site.com, img2.site.com, to buy 6 more connections each
⭐   · ⭐ SPRITE SHEETS   — 50 icons in one image, to make 50 requests into 1
⭐   · ⭐ CSS/JS BUNDLING — concatenate everything, for the same reason
⭐   · ⭐ INLINING assets as data: URIs
⭐ ⇒ ⭐⭐ EVERY ONE OF THESE IS A WORKAROUND FOR A TRANSPORT LIMITATION,
⭐      and HTTP/2 made all of them obsolete — or actively harmful.
```

⚠️ ⭐⭐ **This is the best example on the roadmap of a whole generation of "best practices" that were
really compensations for one protocol constraint.** When the constraint went away, the practices
became anti-patterns — sharding on HTTP/2 *costs* you performance. **Ask of any best practice: what
constraint is this compensating for, and does it still exist?**

# Part 3 — ⭐⭐ HTTP/2 — multiplexing

```
⭐⭐ ONE TCP connection. Many independent STREAMS, interleaved.

  connection ═══════════════════════════════════════════▶
   stream 1  ──█──────█────█──────────▶   (the HTML)
   stream 3  ─────█──────█─────█───────▶  (a CSS file)
   stream 5  ───────█───────█──────────▶  (an image)
   ⭐⭐ frames from different streams SHARE the connection, in any order.
```

| ⭐ Feature | ⭐ What it buys |
|---|---|
| ⭐⭐ **Multiplexing** | ⭐⭐ no more 6-connection limit; **no HTTP-layer head-of-line blocking** |
| ⭐⭐ **Binary framing** | parsers stop guessing; frames have explicit types and lengths |
| ⭐ **HPACK header compression** | ⭐ repeated headers (cookies!) cost ~nothing after the first request |
| ⭐ Stream priority | "the CSS before the footer image" |
| Server push | ⭐⭐ **removed** — badly specified, barely used, replaced by `103 Early Hints` |

⭐⭐ **Header compression is underrated.** In HTTP/1.1 every request re-sent the same 1 KB of cookies
and user-agent. With 100 requests that is 100 KB of duplicate headers; HPACK sends them once and
refers to them by index afterwards.

## ⚠️ ⭐⭐ The limitation HTTP/2 could not fix

```
⭐⭐ HTTP/2 removed head-of-line blocking at the HTTP layer.
⭐   ⚠️ ⭐⭐ IT COULD NOT REMOVE IT AT THE TCP LAYER.
⭐
⭐   One TCP connection, six streams. A single segment is LOST.
⭐   ⇒ TCP will not deliver ANY later bytes to the application until it is retransmitted —
⭐     because TCP guarantees ORDER and does not know the streams are independent.
⭐   ⇒ ⭐⭐ ALL SIX STREAMS STALL, waiting for a packet that only one of them needed.
⭐
⭐ ⇒ ⭐⭐ On a lossy network, HTTP/2 can be SLOWER than HTTP/1.1 with six connections,
⭐      because six connections meant loss stalled only one of them.
```

⭐⭐ **That paragraph is the whole reason HTTP/3 exists**, and being able to say it is a genuine
signal in an interview.

# Part 4 — ⭐⭐ HTTP/3 and QUIC — moving the transport

```
⭐⭐ THE REALISATION: the problem is TCP itself. You cannot fix TCP —
⭐   it is implemented in every OS kernel and every middlebox on earth.
⭐   ⇒ ⭐⭐ SO BUILD A NEW TRANSPORT IN USER SPACE, ON TOP OF UDP.

⭐⭐ QUIC = reliability + ordering + congestion control + TLS 1.3, over UDP.
```

| ⭐ QUIC property | ⭐ Why it matters |
|---|---|
| ⭐⭐ **Per-stream ordering** | ⭐⭐ loss on stream 1 does **not** stall stream 3 — HOL blocking finally gone |
| ⭐⭐ **TLS is built in** | ⭐ handshake + encryption in **1 RTT**, 0-RTT on resumption |
| ⭐⭐ **Connection IDs** | ⭐⭐ **survives an IP change** — wifi → 5G without dropping the connection |
| ⭐ User-space implementation | can be upgraded by shipping a library, not a kernel |
| ⭐ Always encrypted | there is no plaintext QUIC |

⭐⭐ **Connection migration is the most user-visible win.** A TCP connection is identified by the
four-tuple (Day 003), so changing networks kills it. A QUIC connection is identified by a connection
ID, so it just continues — your video call does not drop when you walk out of the building.

⚠️ ⭐ **The costs:** UDP is blocked or throttled on some corporate networks (so clients fall back to
TCP), and QUIC uses noticeably more CPU because congestion control runs in user space instead of in
the kernel.

## ⭐ Where Python sits

```python
# ⭐ requests is HTTP/1.1 ONLY. It will never do HTTP/2.
# ⭐⭐ httpx does HTTP/2 — but only if you ask, and only if the extra is installed.
#     pip install 'httpx[http2]'
import httpx
with httpx.Client(http2=True) as client:
    r = client.get("https://example.com")
    print(r.http_version)          # ⭐ "HTTP/2" or "HTTP/1.1"
```

⭐⭐ **Almost nothing in Python speaks HTTP/3 yet** (`aioquic` is the reference implementation), and
that is fine — ⭐ **in practice HTTP/2 and /3 terminate at your CDN or load balancer, which then
speaks HTTP/1.1 to your uvicorn workers on the local network** where RTT is a fraction of a
millisecond and none of this matters. **Knowing where each version actually runs in your own
architecture is the senior version of this answer.**

# Part 5 — ⭐ What changes for you, practically

| | ⭐ HTTP/1.1 era | ⭐⭐ HTTP/2+ era |
|---|---|---|
| Bundling JS/CSS | ⭐ essential | ⭐ still useful (compression), but not for request count |
| Domain sharding | helped | ⭐⭐ **harmful** — defeats multiplexing, adds handshakes |
| Sprite sheets | essential | ⭐ obsolete |
| Many small files | expensive | ⭐ cheap |
| Cookie size | ⭐ costly on every request | ⭐ compressed after the first |
| Connection reuse | ⭐⭐ **essential** | ⭐⭐ **still essential** |

⭐⭐ **The last row is the one that never changes.** Every version of this story ends with: reuse the
connection. Day 005 (handshake), Day 008 (congestion window), Day 009 (TLS), today (everything).
**It is the same lesson as a database connection pool in Stage 5.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Thinking HTTP/2 removed all HOL blocking** | ⭐⭐ It removed it at the HTTP layer; TCP still blocks. |
| Sharding domains on HTTP/2 | ⭐⭐ Actively harmful — more handshakes, less multiplexing. |
| "HTTP/3 is HTTP over UDP" | ⭐ It is HTTP over **QUIC**, which rebuilds reliability over UDP. |
| Thinking pipelining solved concurrency | ⭐ Responses still had to return in order. It is dead. |
| Assuming your Python app speaks HTTP/2 | ⭐⭐ Usually the CDN/LB does; your worker sees 1.1. |
| Using `requests` and expecting HTTP/2 | ⭐ It cannot. Use `httpx` with the extra installed. |
| Forgetting the 6-connection limit exists in 1.1 | ⭐ It explains a decade of front-end practice. |
| Treating old best practices as timeless | ⭐⭐ Ask which constraint they compensated for. |

## Interview questions

**Q: Walk me through HTTP 1.0 to 3, and say what problem each version solved.**
> 1.0 opened and closed a TCP connection per request, so a page paid a handshake and a cold
> congestion window per asset. 1.1 added keep-alive to reuse the connection, plus `Host` for virtual
> hosting — but requests on a connection remained sequential, so a slow response blocked the ones
> behind it, and browsers worked around it with six connections per domain. HTTP/2 introduced binary
> framing and multiplexed streams over one connection, plus header compression. HTTP/3 replaces TCP
> with QUIC over UDP, because the remaining head-of-line blocking was in TCP and could not be fixed
> there. Every step removes round trips.

**Q: Why can HTTP/2 be slower than HTTP/1.1?**
> On a lossy network. HTTP/2 puts all streams on one TCP connection, and TCP delivers bytes in order,
> so a single lost segment stalls every stream sharing that connection — TCP doesn't know they're
> independent. With HTTP/1.1's six connections, that loss stalls only one of the six. That is exactly
> the problem QUIC solves by tracking ordering per stream.

**Q: What does QUIC give you beyond removing head-of-line blocking?**
> A built-in TLS 1.3 handshake, so connection setup and encryption cost one round trip instead of
> two separate negotiations; deployability, because it lives in user space and can be updated by
> shipping a library rather than a kernel; and connection migration — the connection is identified by
> a connection ID rather than the IP four-tuple, so it survives moving from wifi to cellular.

**Q: You're told to shard assets across four subdomains for performance. Response?**
> I'd ask which HTTP version we serve. On 1.1 that buys parallelism past the six-connection limit. On
> HTTP/2 it costs us: four domains means four TCP and TLS handshakes and four separate multiplexing
> contexts, when the whole point of HTTP/2 is that one connection is enough. It's a good example of a
> best practice that was really a workaround, and the workaround outliving its constraint.

**Q: Does your FastAPI service speak HTTP/2?**
> Almost certainly not directly — uvicorn speaks HTTP/1.1. In a normal deployment HTTP/2 or /3
> terminates at the CDN or load balancer, which then talks HTTP/1.1 to the workers over a local
> network where round trips are sub-millisecond, so the benefits are mostly irrelevant on that hop.
> What still matters on that hop is keep-alive between the proxy and the workers.

## 🎙️ Articulation drill

Record two minutes: **"Why does HTTP/3 use UDP?"**

⭐ Start with the constraint: **HTTP/2's remaining head-of-line blocking lives in TCP**, because TCP
guarantees byte order over a connection and has no idea the streams above it are independent. ⭐⭐
**You cannot fix TCP** — it is in every kernel and every middlebox on the internet, and a change
takes a decade to deploy. ⭐ So QUIC rebuilds reliability, ordering and congestion control in user
space on top of UDP, which is just "IP with ports" and gets out of the way. ⭐⭐ **UDP was not chosen
for speed. It was chosen because it is the only transport that lets you deploy a new transport.**
