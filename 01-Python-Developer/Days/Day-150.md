# Part 1 — ⭐⭐ Config as a parsed type, not a lookup

```
⭐⭐ THE FAILURE MODE THAT MAKES THIS WORTH A DAY:

⭐   ❌ TIMEOUT = int(os.environ.get("TIMEOUT", "30"))
⭐   ❌ if os.environ.get("DEBUG"): ...
⭐
⭐   ⭐ `DEBUG=false` ⇒ ⭐⭐ THE STRING "false" IS TRUTHY ⇒ DEBUG MODE IS ON IN
⭐        PRODUCTION. ⭐ Tracebacks with source code, to the internet.
⭐   ⭐ a typo'd `DATBASE_URL` ⇒ the default is used ⇒ ⭐⭐ YOU SILENTLY POINT
⭐        AT THE WRONG DATABASE and find out from data, not from an error.
⭐   ⭐ `os.environ` read at line 400 of a module ⇒ ⭐ a `KeyError` on the
⭐        first request that reaches that branch, ⭐⭐ possibly WEEKS after the
⭐        deploy, in the one code path nobody exercises.
⭐
⭐   ⇒ ⭐⭐ CONFIG IS UNTRUSTED INPUT AND IT DESERVES DAY 119's TREATMENT:
⭐        PARSE IT ONCE, AT THE EDGE, INTO A TYPED OBJECT — AND FAIL LOUDLY.
```

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env", env_prefix="APP_",
        extra="forbid",                        # ⭐⭐ a typo'd key is a BOOT FAILURE
        frozen=True,                           # ⭐ immutable — see Part 2
    )
    environment: Literal["local", "staging", "production"]   # ⭐⭐ no default: REQUIRED
    database_url: PostgresDsn                                # ⭐ parsed, not a string
    redis_url: RedisDsn
    jwt_secret: SecretStr                                    # ⭐⭐ Part 3
    request_timeout_s: float = Field(default=5.0, gt=0, le=60)   # ⭐ bounded
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"
    allowed_origins: list[AnyHttpUrl] = []

    @model_validator(mode="after")
    def _production_is_strict(self) -> "Settings":
        if self.environment == "production":
            if "*" in [str(o) for o in self.allowed_origins]:
                raise ValueError("wildcard CORS is not allowed in production")  # ⭐⭐
            if self.log_level == "DEBUG":
                raise ValueError("DEBUG logging leaks data in production")
        return self
```

```
⭐⭐ WHAT EACH LINE BUYS, BECAUSE THIS IS THE ARGUMENT TO MAKE:
⭐   ⭐ NO DEFAULT ⇒ ⭐⭐ MISSING = CRASH AT BOOT. A pod that cannot boot is
⭐        caught by your rollout (Day 149) and rolled back automatically.
⭐        ⭐ A pod that boots and 500s later is an incident.
⭐   ⭐ `extra="forbid"` ⇒ ⭐⭐ `APP_DATBASE_URL` is an ERROR, not a silent
⭐        fallback. ⭐ This one line catches the most expensive class of
⭐        config bug there is.
⭐   ⭐ `Literal` ⇒ `environment=prod` (instead of `production`) fails at
⭐        boot, ⭐⭐ rather than making every `if env == "production"` branch
⭐        quietly false — ⭐ which disables your security settings one by one.
⭐   ⭐ BOUNDS ⇒ `request_timeout_s=0` is rejected instead of meaning
⭐        "no timeout" or "instant failure" depending on the library.
⭐   ⭐⭐ CROSS-FIELD VALIDATION ⇒ THE RULES YOU ACTUALLY CARE ABOUT ARE
⭐        RELATIONAL. "Not DEBUG in production" cannot be expressed on one
⭐        field, and it is the check that would have prevented the leak.
```

# Part 2 — ⭐ Precedence, layering, and one object

```
⭐⭐ THE ORDER, HIGHEST WINS — and it must be WRITTEN DOWN somewhere:
⭐   1. ⭐ explicit arguments (tests)
⭐   2. ⭐ environment variables          ⭐⭐ what production actually uses
⭐   3. ⭐ secrets files (`/run/secrets/*`, `secrets_dir=`)
⭐   4. ⭐ `.env`                          ⭐⭐ LOCAL DEVELOPMENT ONLY
⭐   5. ⭐ defaults in code
⭐
⭐   ⇒ ⭐⭐ `.env` MUST NEVER SHIP. It is in `.gitignore` and `.dockerignore`,
⭐        and it is a CONVENIENCE FOR HUMANS. ⭐ The day a `.env` is baked into
⭐        an image, it is in every layer forever (Part 3).

⭐⭐ ONE SETTINGS OBJECT, CONSTRUCTED ONCE, INJECTED:
⭐   ⭐ @lru_cache def get_settings() -> Settings: return Settings()
⭐   ⭐ routes take `s: Settings = Depends(get_settings)` (Day 132)
⭐   ⇒ ⭐⭐ THE PAYOFF IS TESTING: overriding one dependency configures the
⭐        whole app, with no monkeypatching of `os.environ` and no import-order
⭐        problems. ⭐ Day 141's rule — use the seam.
⭐   ⇒ ⭐⭐ AND `frozen=True`: config that mutates at runtime is a global
⭐        variable with a nicer name. ⭐ If a value must change while running,
⭐        it is a FEATURE FLAG, not config (Part 5).

⭐ ⭐⭐ VALIDATE AT BOOT, EXPLICITLY — before the server binds a port:
⭐     def main(): get_settings(); uvicorn.run(...)
⭐   ⭐ Otherwise lazy construction means the first REQUEST discovers the
⭐     problem, ⭐⭐ and Day 149's readiness probe already told the load
⭐     balancer you were fine.
```

# Part 3 — ⭐⭐ Where secrets actually leak

```
⭐⭐ NOT "someone stole the vault". THESE, IN ROUGH ORDER OF FREQUENCY:

⭐  1. ⭐⭐ COMMITTED TO GIT. And Day 084's fact makes this permanent: history
⭐       is a hash chain, so ⭐ deleting it in a later commit changes NOTHING —
⭐       the blob is still reachable, still cloned, still on GitHub's servers.
⭐       ⇒ ⭐⭐ ROTATE FIRST, REWRITE SECOND (Day 087). Rewriting alone is
⭐         theatre; the secret was public the moment it was pushed.
⭐
⭐  2. ⭐⭐ BAKED INTO A DOCKER IMAGE. `ARG API_KEY` or `COPY .env .` —
⭐       ⭐ EVERY LAYER IS RETAINED. `docker history` shows build args;
⭐       ⭐⭐ deleting the file in a LATER layer does not remove it from the
⭐       EARLIER one. ⭐ Same structural fact as git, for the same reason.
⭐       ⇒ ⭐ FIX: BuildKit `--mount=type=secret`, or inject at RUNTIME.
⭐
⭐  3. ⭐⭐ LOGGED. Day 146. A `SecretStr` is the mechanical defence:
⭐       ⭐ `print(settings)` → `jwt_secret=SecretStr('**********')`
⭐       ⭐⭐ AND CRUCIALLY, IT IS REDACTED IN TRACEBACKS AND IN ANY ERROR
⭐         REPORTER — Sentry captures local variables, ⭐ and a plain string
⭐         in a frame is a secret in a third-party SaaS forever.
⭐       ⭐ You must write `.get_secret_value()` to use it, which makes every
⭐         use site GREPPABLE and reviewable.
⭐
⭐  4. ⭐ IN A URL. `postgres://user:pass@host/db` in logs, in traces
⭐       (Day 148), in `Referer`, in an exception message. ⭐⭐ Redact the
⭐       password when logging any DSN — libraries print them freely.
⭐
⭐  5. ⭐ IN CI. Echoed by a debug step, in a build log a contractor can read,
⭐       ⭐⭐ or exposed to a fork's pull-request workflow.
⭐
⭐  6. ⭐ `/metrics` (Day 147) OR AN ERROR PAGE. ⭐⭐ `DEBUG=1` in production
⭐       renders local variables — INCLUDING YOUR SETTINGS OBJECT — to
⭐       whoever triggered the error. ⭐ Which is why Part 1 made that a
⭐       boot-time check.
```

```python
# ⭐⭐ Dockerfile: the right way and the two wrong ways
# ❌ ARG DB_PASSWORD                     # ⭐ visible in `docker history`, forever
# ❌ COPY .env /app/.env                 # ⭐⭐ in the layer even if deleted later
# ✅ RUN --mount=type=secret,id=pip_token \
#        pip install --index-url "https://$(cat /run/secrets/pip_token)@..."
# ✅ secrets arrive at RUNTIME as env vars or mounted files
```

# Part 4 — ⭐⭐ Secret managers and rotation

```
⭐⭐ WHY AN ENV VAR IS NOT THE END OF THE STORY — THE ROTATION PROBLEM:
⭐   ⭐ env vars are read ONCE at process start. ⭐⭐ SO ROTATING A SECRET
⭐     REQUIRES A RESTART OF EVERY PROCESS THAT USES IT.
⭐   ⇒ ⭐ that is a deploy, coordinated across services, ⭐⭐ WHICH IS WHY
⭐     NOBODY ROTATES — the cost is a rollout, so it never gets scheduled,
⭐     so your database password is four years old.
⭐
⭐⭐ WHAT A SECRET MANAGER (Vault, AWS Secrets Manager, GCP SM) ACTUALLY BUYS:
⭐   ⭐ AUDIT — who read which secret, when. ⭐⭐ After an incident this is the
⭐        difference between "we rotated everything" and "we rotated what was
⭐        exposed".
⭐   ⭐ ACCESS CONTROL per service, ⭐ so a compromised report-generator does
⭐        not hold the payments key
⭐   ⭐⭐ ROTATION WITHOUT A DEPLOY — the real prize
⭐   ⭐ SHORT-LIVED / DYNAMIC CREDENTIALS: ⭐⭐ Vault can issue a database user
⭐        valid for one hour. ⭐ A leaked credential then has an expiry, which
⭐        changes the whole risk calculus.
⭐
⭐⭐ AND THE PATTERN THAT MAKES ROTATION SAFE — it is the same shape as
⭐   Day 138's expand/contract and Day 116's key rotation:
⭐   1. ⭐ create the NEW secret; ⭐⭐ ACCEPT BOTH old and new
⭐   2. ⭐ roll services to USE the new one
⭐   3. ⭐ verify nothing still uses the old (⭐⭐ the audit log answers this)
⭐   4. ⭐ revoke the old
⭐   ⇒ ⭐⭐ THERE IS NEVER A MOMENT WHERE A RUNNING PROCESS HOLDS AN INVALID
⭐        CREDENTIAL. ⭐ Any rotation design without an overlap window is an
⭐        outage with a date on it.
⭐
⭐ ⭐ FILE-MOUNTED SECRETS ARE THE PRACTICAL MIDDLE GROUND: mount at
⭐   `/run/secrets/db_password`, ⭐⭐ read on USE rather than at import, and a
⭐   rotation becomes a file update — ⭐ no restart, no vault client, and it
⭐   works with Kubernetes Secrets and Docker Swarm out of the box.
```

# Part 5 — ⭐ Config vs feature flags, and the environment trap

```
⭐⭐ THE DISTINCTION, WHICH PREVENTS A LOT OF BAD DESIGN:
⭐   ⭐ CONFIG      — differs per ENVIRONMENT, changes at DEPLOY, ⭐ read once.
⭐        (database URL, pool size, log level)
⭐   ⭐ FEATURE FLAG — differs per USER/REQUEST, changes at RUNTIME, ⭐ read
⭐        every time. (new checkout for 5% of users)
⭐   ⇒ ⭐⭐ CONFUSING THEM: putting a flag in an env var means a DEPLOY to turn
⭐        a feature off — ⭐ i.e. your kill switch takes ten minutes during
⭐        the incident it exists for. ⭐⭐ A kill switch that requires a deploy
⭐        is not a kill switch.

⭐⭐ AND THE `if environment == "production"` TRAP — worth naming explicitly:
⭐   ⭐ every such branch means ⭐⭐ THE CODE PATH YOU TEST IS NOT THE CODE PATH
⭐     YOU RUN. ⭐ The production branch is exercised for the first time in
⭐     production, by users.
⭐   ⇒ ⭐⭐ PREFER A CONFIG *VALUE* OVER AN ENVIRONMENT *CHECK*:
⭐        ❌ if settings.environment == "production": use_real_email()
⭐        ✅ mailer = build_mailer(settings.mailer_backend)   ⭐ same path,
⭐                                                            different value
⭐   ⇒ ⭐ Then staging can run the production configuration, and the branch
⭐        that differs is one factory function you can test directly.
```

```
⭐⭐ THE TWELVE-FACTOR CLAIM, WITH THE HONEST CAVEAT — both halves are worth
⭐   saying:
⭐   ⭐ "Store config in the environment" ⇒ ⭐⭐ THE SAME ARTEFACT (image,
⭐     commit) RUNS IN EVERY ENVIRONMENT. ⭐ That is what makes "it worked in
⭐     staging" meaningful — ⭐⭐ if the build differs per environment, staging
⭐     proved nothing about production.
⭐   ⭐ CAVEAT: env vars are ⭐ visible in `/proc/<pid>/environ` (Day 081),
⭐     ⭐ inherited by child processes (including anything you `subprocess`),
⭐     and ⭐⭐ dumped by crash reporters. ⭐ For high-value secrets, mounted
⭐     files beat env vars — narrower blast radius, and they can be rotated.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `os.environ.get` scattered through modules | A `KeyError` weeks later on a rarely-taken branch. Parse once at the edge. |
| `if os.environ.get("DEBUG")` | `"false"` is truthy — debug mode in production. Parse to `bool`. |
| Defaults for required values | A typo'd key silently points at the wrong database. No default = crash at boot. |
| No `extra="forbid"` | `APP_DATBASE_URL` falls back silently. One line catches the costliest config bug. |
| `str` where a `Literal` belongs | `env=prod` makes every `== "production"` branch false, disabling security settings one by one. |
| Only per-field validation | The rules that matter are relational — "not DEBUG in production" needs `model_validator`. |
| Lazy settings construction | The first request discovers the problem, after readiness said you were fine. |
| Mutable settings | A global variable with a nicer name. `frozen=True`. |
| `.env` in the image | It's in the layer forever, even if a later layer deletes it. |
| `ARG` for secrets | Visible in `docker history`. Use BuildKit secret mounts or runtime injection. |
| Plain `str` for secrets | Leaks into tracebacks and error reporters. `SecretStr` redacts and makes uses greppable. |
| Logging a DSN | The password is in the URL, and libraries print DSNs freely. |
| Deleting a committed secret without rotating | History is a hash chain; the blob is still there. Rotate first. |
| Feature flags in env vars | Your kill switch needs a deploy — which makes it not a kill switch. |
| `if environment == "production"` branches | The path you test isn't the path you run. Use a config *value*. |
| Rotation with no overlap window | An outage with a date on it. Accept both, roll, verify, revoke. |

## Interview questions

**Q: How do you handle configuration?**

> As untrusted input that gets parsed once at the edge into a typed object — the same discipline as
> request validation. A `pydantic-settings` class with no defaults for required values, so a missing
> variable crashes at boot rather than raising a `KeyError` weeks later on a branch nobody exercises;
> `extra="forbid"`, so a typo like `DATBASE_URL` is a boot failure instead of a silent fallback to a
> default that points at the wrong database; `Literal` for enums, because `env=prod` instead of
> `production` would quietly make every production branch false and disable security settings one at
> a time; and bounds on numbers. Plus a cross-field validator, because the rules I actually care
> about are relational — "wildcard CORS is not allowed in production" can't be expressed on a single
> field. The point of all of it is that a pod which can't boot gets caught by the rollout and rolled
> back automatically, whereas a pod that boots and 500s later is an incident.

**Q: Where do secrets actually leak?**

> Almost never from the vault. In rough order: committed to git — and because history is a hash
> chain, deleting it later changes nothing, the blob is still reachable and already cloned, so you
> rotate first and rewrite second. Baked into a Docker image via `ARG` or `COPY .env`, which is the
> same structural fact: every layer is retained, so deleting the file in a later layer doesn't remove
> it from the earlier one. Logged, which is what `SecretStr` defends against — and the important part
> is that it's redacted in tracebacks and error reporters too, because Sentry captures local
> variables and a plain string in a frame is a secret sitting in a third-party SaaS forever. In a
> DSN, since libraries print connection URLs freely. In CI logs. And on a debug error page, which is
> why "no DEBUG in production" is a boot-time assertion rather than a convention.

**Q: Env vars are fine for secrets. Why would you use a secret manager?**

> Because env vars are read once at process start, so rotating a secret means restarting every
> process that uses it — a coordinated deploy. The result is that nobody rotates, because the cost is
> a rollout, so the database password is four years old. A secret manager buys rotation without a
> deploy, an audit trail of who read what and when — which after an incident is the difference
> between rotating everything and rotating what was actually exposed — per-service access control, so
> a compromised report generator doesn't hold the payments key, and short-lived dynamic credentials.
> Whatever the backend, rotation needs an overlap window: create the new one, accept both, roll
> services over, verify from the audit log that nothing uses the old, then revoke. A rotation design
> with no overlap is an outage with a date on it.

**Q: What's the difference between config and a feature flag?**

> Config differs per environment, changes at deploy time, and is read once. A feature flag differs
> per user or request, changes at runtime, and is read every time. Confusing them has a specific
> cost: if the flag lives in an env var, turning a feature off requires a deploy — so your kill
> switch takes ten minutes during exactly the incident it exists for, which means it isn't a kill
> switch.

**Q: What's wrong with `if settings.environment == "production"`?**

> It means the code path you test is not the code path you run — the production branch is exercised
> for the first time in production, by users. I prefer a config *value* over an environment check:
> instead of branching on the environment to decide whether to send real email, I have a
> `mailer_backend` setting and one factory that builds it. Same code path everywhere, different
> value, and staging can run the production configuration to prove something real. The one thing I do
> branch on is boot-time assertions — refusing to start with wildcard CORS or DEBUG logging in
> production — because those aren't behaviour, they're guard rails.
