# Day 131

**L-131** · **Pydantic v2** — validators, `model_config`, serialisation, and ⭐⭐ why v2 is a Rust core

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a Pydantic model is not a class with checks bolted on — it is a compiled
> validation schema built once at class-definition time, which is why it is fast, why the errors are
> structured, and why "just add a check in `__init__`" is the wrong instinct.**
>
> ⭐ Day 119 said *parse, don't validate*. **This is the tool that does it**, and the parts worth
> knowing are the ones that decide behaviour you did not ask for.

---

# Part 1 — ⭐⭐ What v2 actually is

```
⭐⭐ PYDANTIC V2 IS TWO PIECES:
⭐   · ⭐ a PYTHON layer that reads your annotations and BUILDS A SCHEMA — once,
⭐        when the class is defined (a metaclass, Day 053)
⭐   · ⭐⭐ `pydantic-core`, a RUST library that EXECUTES that schema
⭐   ⇒ ⭐⭐ SO VALIDATION IS NOT INTERPRETED PYTHON PER FIELD PER REQUEST. The
⭐        schema is compiled once and run in Rust — ⭐ 5-50× faster than v1, and
⭐        the reason FastAPI can validate on every request without thinking
⭐        about it (Day 073's "do fewer Python operations", taken to its limit).
⭐   ⇒ ⭐ AND THE CONSEQUENCE THAT MATTERS DAILY: ⭐⭐ THE MORE VALIDATION YOU
⭐        EXPRESS IN THE TYPE, THE LESS PYTHON RUNS. A `Field(gt=0)` executes in
⭐        Rust; a `@field_validator` that checks `> 0` executes in Python, per
⭐        field, per request. ⭐ Prefer constraints to validators when both work.
```

```python
from pydantic import BaseModel, Field, ConfigDict, field_validator, model_validator
from decimal import Decimal

class OrderIn(BaseModel):
    model_config = ConfigDict(
        extra="forbid",              # ⭐⭐ Day 119 — unknown fields are a 422
        str_strip_whitespace=True,   # ⭐ normalise at the boundary
        frozen=True,                 # ⭐ immutable after construction (Day 057)
    )

    sku: str = Field(min_length=1, max_length=64, pattern=r"^[A-Z0-9-]+$")
    qty: int = Field(gt=0, le=100)
    unit_price: Decimal = Field(gt=0, max_digits=12, decimal_places=2)   # ⭐⭐ Day 041
    note: str | None = Field(default=None, max_length=500)
```

⭐⭐ **Every constraint here is also documentation** — `model_json_schema()` emits all of them, so the
OpenAPI spec gains `minLength`, `maximum` and `pattern` for free (Day 126). ⭐ **A `@field_validator`
that duplicates a constraint is invisible to the schema**, which is a second reason to prefer `Field`.

# Part 2 — ⭐ Validators, and which kind

```python
class Signup(BaseModel):
    email: EmailStr
    password: str = Field(min_length=12)
    password_confirm: str
    born: date

    @field_validator("email")                        # ⭐ ONE field, AFTER coercion
    @classmethod
    def lowercase(cls, v: str) -> str:
        return v.lower()                              # ⭐⭐ validators may TRANSFORM

    @field_validator("born")
    @classmethod
    def not_future(cls, v: date) -> date:
        if v > date.today():
            raise ValueError("date of birth cannot be in the future")   # ⭐⭐ ValueError, not HTTPException
        return v

    @model_validator(mode="after")                    # ⭐⭐ needs MORE THAN ONE field
    def passwords_match(self):
        if self.password != self.password_confirm:
            raise ValueError("passwords do not match")
        return self
```

```
⭐⭐ FOUR RULES:
⭐  1. ⭐ `field_validator` FOR ONE FIELD; `model_validator` when the rule spans
⭐       fields. ⭐⭐ Trying to reach another field from a field validator is the
⭐       most common v1 habit that no longer works.
⭐  2. ⭐⭐ `mode="after"` (the default for model validators) RUNS ON THE PARSED
⭐       OBJECT — types are already correct, so you write ordinary Python.
⭐       `mode="before"` sees the RAW INPUT, which you want only when you must
⭐       reshape it (a legacy payload, a field rename).
⭐  3. ⭐⭐ RAISE `ValueError`, NEVER `HTTPException`. Pydantic catches
⭐       `ValueError` and folds it into the structured error list with the field
⭐       path; ⭐ an `HTTPException` escapes as a 500 from inside the parser.
⭐  4. ⭐ VALIDATORS MAY RETURN A CHANGED VALUE — that is parsing (Day 119), and
⭐       normalising at the boundary means nothing downstream has to.
```

⚠️ ⭐⭐ **Do not put business rules in a validator.** ⭐ "Passwords match" is validation; **"this SKU is
in stock" is a domain rule** that needs a database and belongs in the service (Day 119). ⭐⭐ **A model
that queries in a validator cannot be constructed in a test, cannot be reused off the request path,
and turns a 422 into something that should have been a 409.**

# Part 3 — ⭐⭐ Strict vs lax, and the coercion that surprises

```python
class M(BaseModel):
    n: int
    flag: bool

M(n="5", flag="yes")        # ⭐⭐ LAX MODE (the default): n=5, flag=True
```

```
⭐⭐ LAX COERCION IS RIGHT FOR QUERY STRINGS AND FORMS — everything arrives as a
⭐   string, so `?limit=20` must become `20`.
⭐   ⇒ ⚠️ ⭐⭐ AND IT IS SURPRISING IN A JSON BODY, where the client had types
⭐        available and chose to send `"5"`. ⭐ You silently accept a client bug
⭐        and it becomes permanent behaviour someone depends on (Day 125).
⭐   ⇒ ⭐ `model_config = ConfigDict(strict=True)`, or `Strict[int]` per field.
⭐   ⇒ ⭐⭐ MY POSITION: STRICT FOR JSON BODIES, LAX FOR QUERY AND PATH. ⭐ Decide
⭐        it per boundary and write it down; ⭐⭐ the default is neither, and
⭐        "whatever Pydantic does" is not a design.
⭐
⭐ ⚠️ ⭐⭐ AND THE FLOAT TRAP, WHICH IS DAY 041 ARRIVING THROUGH JSON:
⭐    `Decimal` FROM A JSON NUMBER GOES THROUGH A FLOAT unless the input is a
⭐    string. ⭐ `{"price": 19.99}` ⇒ Decimal('19.989999999999998...') in the
⭐    worst case. ⭐⭐ SO: MONEY IS A STRING ON THE WIRE (Day 126), AND STRICT
⭐    MODE ON THAT FIELD.
```

| ⭐ Input | ⭐ Lax | ⭐ Strict |
|---|---|---|
| `"5"` → `int` | ⭐ `5` | ⭐ error |
| `5.0` → `int` | ⭐ `5` | ⭐ error |
| `5.7` → `int` | ⭐⭐ **error** (no silent truncation) | error |
| `"yes"`/`"on"`/`1` → `bool` | ⭐ `True` | ⭐ error |
| `19.99` → `Decimal` | ⚠️ ⭐⭐ via float | ⭐ error |
| `"2026-08-18"` → `date` | ⭐ parsed | ⭐ parsed (strings are the native form) |

# Part 4 — ⭐⭐ Serialisation, and the aliases

```python
class OrderOut(BaseModel):
    model_config = ConfigDict(from_attributes=True,       # ⭐⭐ build from an ORM object
                              populate_by_name=True)

    order_id: int = Field(serialization_alias="orderId")   # ⭐ snake in, camel out
    total: Decimal
    created_at: datetime
    internal_score: float = Field(exclude=True)            # ⭐⭐ never serialised

    @computed_field                                        # ⭐ derived, appears in the schema
    @property
    def total_with_vat(self) -> Decimal:
        return (self.total * Decimal("1.20")).quantize(Decimal("0.01"))

order.model_dump()                       # ⭐ dict, Python types (Decimal stays Decimal)
order.model_dump(mode="json")            # ⭐⭐ JSON-SAFE types — Decimal→str, datetime→ISO
order.model_dump_json()                  # ⭐ bytes, serialised in Rust
order.model_dump(exclude_none=True)      # ⭐ drop nulls
order.model_dump(by_alias=True)          # ⭐ camelCase out
```

```
⭐⭐ THREE THINGS TO GET RIGHT:
⭐  1. ⭐⭐ `from_attributes=True` IS WHAT LETS YOU RETURN AN ORM OBJECT and have
⭐       it filtered through the schema (Day 119's security control). ⭐ Without
⭐       it, `OrderOut.model_validate(orm_object)` fails.
⭐  2. ⭐⭐ `mode="json"` vs the default. ⭐ `model_dump()` keeps `Decimal` and
⭐       `datetime` as Python objects; ⭐⭐ passing that to `json.dumps` raises,
⭐       and passing it to a template silently renders a repr. Use `mode="json"`
⭐       whenever the destination is not Python.
⭐  3. ⭐ ALIASES: `validation_alias` for what you ACCEPT, `serialization_alias`
⭐       for what you EMIT. ⭐⭐ Keeping both means you can present camelCase to a
⭐       JavaScript client without camelCase leaking into your Python code.
⭐   ⇒ ⚠️ ⭐ `exclude=True` on a field is a blunt tool — ⭐⭐ prefer a separate
⭐        output model, because `exclude` is easy to forget on a new field
⭐        whereas a separate model is allowlist-by-construction (Day 119).
```

# Part 5 — ⭐ Reuse, and where models belong

```python
class OrderBase(BaseModel):                          # ⭐ shared fields
    sku: str
    qty: int = Field(gt=0)

class OrderCreate(OrderBase): pass                    # ⭐ what a POST accepts
class OrderUpdate(BaseModel):                         # ⭐⭐ PATCH: everything optional
    sku: str | None = None
    qty: int | None = Field(default=None, gt=0)
class OrderOut(OrderBase):                            # ⭐ what you return
    model_config = ConfigDict(from_attributes=True)
    id: int
    created_at: datetime
```

```
⭐⭐ THREE MODELS PER RESOURCE IS NOT DUPLICATION — IT IS THE POINT:
⭐   · ⭐ CREATE has no `id`; the server assigns it. ⭐⭐ A shared model means a
⭐        client can send an `id` — mass assignment (Day 119).
⭐   · ⭐ UPDATE has everything optional, and needs `model_dump(exclude_unset=
⭐        True)` so ⭐⭐ "field omitted" is distinguishable from "field set to
⭐        null" — ⭐ without that, a PATCH nulls every field the client did not
⭐        mention.
⭐   · ⭐⭐ OUT has fields the input never had, and OMITS fields the input had
⭐        (a password).
⭐   ⇒ ⭐ if the duplication genuinely hurts, generate the variants — ⭐⭐ but do
⭐        not merge them, because the whole security value is that they differ.
```

```
⭐⭐ WHERE PYDANTIC BELONGS (Days 057, 090): AT THE EDGE.
⭐   · ⭐ HTTP request/response schemas          ⇒ ✔ Pydantic
⭐   · ⭐ settings (`pydantic-settings`)          ⇒ ✔ (Day 133)
⭐   · ⭐ parsing an external API's response      ⇒ ✔ — it is untrusted too
⭐   · ⭐⭐ YOUR DOMAIN OBJECTS                    ⇒ ⭐⭐ dataclasses. They validate
⭐        on every construction, which you do not want on data you already
⭐        trusted, and they tie your business rules to a validation library.
⭐   ⇒ ⭐ the honest counterweight: on a small service, using Pydantic
⭐        throughout is pragmatic and fine. ⭐⭐ The boundary matters when the
⭐        domain has real rules worth testing without HTTP.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Checks in `__init__` | ⭐⭐ The schema is compiled once. Use `Field` constraints or validators. |
| ⭐ A validator duplicating a `Field` constraint | ⭐ Slower, and invisible to the JSON Schema. |
| Reaching another field from `field_validator` | ⭐ Use `model_validator(mode="after")`. |
| ⭐⭐ **Raising `HTTPException` in a validator** | ⭐⭐ Escapes as a 500. Raise `ValueError`. |
| Business rules in a validator | ⭐ Needs a database, untestable, and it is a 409 not a 422. |
| ⭐ Lax coercion in a JSON body | ⭐⭐ You silently accept `"5"` and it becomes permanent behaviour. |
| ⭐⭐ **`Decimal` from a JSON number** | ⭐⭐ Goes through a float. Money is a string on the wire. |
| `model_dump()` then `json.dumps` | ⭐ Raises on `Decimal`/`datetime`. Use `mode="json"`. |
| ⭐ `exclude=True` instead of an output model | ⭐⭐ Easy to forget on a new field; a separate model is an allowlist. |
| One model for create, update and output | ⭐⭐ Mass assignment, and a PATCH that nulls everything. |
| ⭐ PATCH without `exclude_unset=True` | ⭐⭐ Cannot distinguish omitted from null. |
| Pydantic for domain objects | ⭐ Re-validates trusted data; ties business rules to a library. |

## Interview questions

**Q: What changed in Pydantic v2?**
> The core moved to Rust. The Python layer reads your annotations and builds a validation schema once,
> at class-definition time, and `pydantic-core` executes it — so validation isn't interpreted Python
> per field per request. That's the 5-to-50× speedup, and it has a practical consequence: the more you
> express in the type, the less Python runs. A `Field(gt=0)` executes in Rust; a `field_validator`
> doing the same check executes in Python on every request. So I prefer constraints to validators when
> both work — and constraints also appear in the JSON Schema, where a validator is invisible.

**Q: When do you use a model validator rather than a field validator?**
> When the rule spans more than one field — password confirmation, or a date range where the end must
> follow the start. A field validator only sees its own value, and trying to reach another field is
> the most common v1 habit that no longer works. I'd use `mode="after"` by default, because it runs on
> the parsed object so the types are already correct and you write ordinary Python; `mode="before"` is
> for reshaping raw input, like accepting a legacy payload shape.

**Q: What's the coercion trap?**
> Lax mode is the default, so `"5"` becomes `5` and `"yes"` becomes `True`. That's right for query
> strings and forms, where everything arrives as text. It's surprising in a JSON body, where the
> client had types available and chose to send a string — you silently accept a client bug and it
> becomes behaviour someone depends on. My position is strict for JSON bodies, lax for query and path
> parameters, decided per boundary and written down. The worst case is `Decimal` from a JSON number,
> which goes through a float, so money has to be a string on the wire.

**Q: Why three models per resource rather than one?**
> Because they genuinely differ, and the differences are the point. Create has no `id`, because the
> server assigns it — a shared model lets a client send one, which is mass assignment. Update has
> everything optional and needs `exclude_unset=True` so you can tell "field omitted" from "field set
> to null", otherwise a PATCH nulls every field the client didn't mention. And the output model omits
> things the input had, like a password, and includes things it didn't, like `created_at`. Merging them
> throws away exactly the property that makes them useful.

**Q: Should your domain objects be Pydantic models?**
> Generally no — dataclasses inside, Pydantic at the edge. Pydantic validates on every construction,
> which you don't want on data you already validated and trusted, and it ties your business rules to a
> validation library. The boundary matters when the domain has real rules you want to test without
> HTTP. That said, on a small service using Pydantic throughout is pragmatic and I wouldn't argue
> about it — the principle is worth applying where it pays.

## 🎙️ Articulation drill

Record two minutes: **"How do you use Pydantic well?"**
