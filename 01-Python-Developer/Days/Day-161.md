# Day 161

**L-161** · **Event-driven architecture** — events vs commands, schema evolution, ⭐⭐ and the ordering you cannot have

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an event says something *happened* and a command says something *should
> happen* — and the difference is who owns the failure, because a command that fails is the sender's
> problem and an event that fails to be handled is the receiver's.**
>
> ⭐ Day 142 gave you a queue and an outbox. ⭐⭐ Today: what to put in the messages, how to change them
> without breaking every consumer, and the three guarantees you will be asked about and cannot have
> all of.

# Part 1 — ⭐⭐ Events vs commands

```
⭐⭐ THE DISTINCTION IS ABOUT COUPLING, AND IT DECIDES YOUR ARCHITECTURE:

⭐   ⭐ COMMAND: `SendWelcomeEmail(user_id=7)`
⭐        ⭐ imperative · ⭐ ONE intended handler · ⭐ the sender KNOWS what
⭐          should happen next ⇒ ⭐⭐ THE SENDER IS COUPLED TO THE RECEIVER
⭐        ⭐ failure is the SENDER'S problem — it must retry or report
⭐
⭐   ⭐ EVENT: `UserRegistered(user_id=7, at=...)`
⭐        ⭐ past tense, a FACT · ⭐ ZERO OR MORE handlers · ⭐⭐ THE SENDER DOES
⭐          NOT KNOW OR CARE WHO LISTENS
⭐        ⭐ failure is each CONSUMER'S problem
⭐
⭐   ⇒ ⭐⭐ THE PAYOFF: ADDING A CONSUMER TO AN EVENT REQUIRES NO CHANGE TO THE
⭐        PRODUCER. ⭐ Analytics, a CRM sync, a fraud check — each subscribes.
⭐        ⭐⭐ With commands, the registration service accumulates a call to
⭐        every new feature, forever, and eventually its job is "know about
⭐        everything".
⭐   ⇒ ⭐ A PAST-TENSE NAME IS NOT COSMETIC. `UserRegistered` cannot be
⭐        rejected; ⭐⭐ `CreateUser` can. Naming an event in the imperative is
⭐        how a command sneaks in wearing an event's clothes — and then a
⭐        consumer's failure starts meaning the producer was wrong.

⭐⭐ AND THE HONEST COST, WHICH YOU MUST SAY OUT LOUD:
⭐   ⭐ ⭐⭐ NOBODY OWNS THE END-TO-END FLOW ANY MORE. ⭐ "What happens when a
⭐        user registers?" has no answer in any one file — ⭐⭐ you must search
⭐        every subscriber, in every repository. Tracing (Day 148) stops being
⭐        a nice-to-have and becomes the ONLY map you have.
⭐   ⭐ debugging is harder: ⭐⭐ a bug is now "somewhere between publish and
⭐        some consumer", ⭐ and the failing consumer may be owned by another
⭐        team.
⭐   ⇒ ⭐⭐ SO: EVENTS BETWEEN BOUNDED CONTEXTS, DIRECT CALLS INSIDE ONE.
⭐        ⭐ Using events between two modules of the same service buys you the
⭐        costs and none of the decoupling — you deploy them together anyway.
```

# Part 2 — ⭐⭐ What goes in the event

```
⭐⭐ THREE STYLES, AND THE THIRD IS THE ONE PEOPLE GET WRONG:

⭐  1. ⭐ NOTIFICATION — `{"type":"order.placed","order_id":812}`
⭐       ⭐ + tiny, no stale data, ⭐⭐ no accidental data leak between services
⭐       ⭐ − ⭐⭐ EVERY CONSUMER CALLS BACK ⇒ 6 consumers = 6 API calls per
⭐            event. ⭐ You have replaced a queue with a thundering herd
⭐            pointed at yourself.
⭐
⭐  2. ⭐⭐ EVENT-CARRIED STATE TRANSFER — the full payload.
⭐       ⭐ + consumers need NO callback ⇒ ⭐⭐ they keep working when you are
⭐            DOWN. ⭐ That availability property is the real argument.
⭐       ⭐ − ⭐⭐ THE PAYLOAD IS A PUBLIC API (Part 3), and it can be stale by
⭐            the time it is processed.
⭐
⭐  3. ⭐ EVENT SOURCING — the event log IS the source of truth; state is a
⭐       projection. ⭐⭐ POWERFUL AND EXPENSIVE: you cannot delete an event
⭐       (⭐ GDPR becomes genuinely hard), replay must be deterministic
⭐       forever, and ⭐⭐ EVERY OLD EVENT VERSION MUST STAY READABLE FOR THE
⭐       LIFE OF THE SYSTEM. ⭐ Know what it is; do not adopt it by accident.
⭐
⭐   ⇒ ⭐⭐ THE PRACTICAL DEFAULT: A HYBRID. Send ids, a type, a timestamp, a
⭐        version — ⭐ PLUS the handful of fields consumers actually need, ⭐⭐ and
⭐        document that anything else must be fetched. ⭐ You get availability
⭐        for the common case and a small contract to maintain.
```

```json
{
  "id": "evt_01HQ...",              // ⭐⭐ idempotency key for consumers (Day 122)
  "type": "order.placed",
  "version": 2,                      // ⭐⭐ Part 3
  "occurred_at": "2026-08-18T10:00:00Z",   // ⭐ NOT "published_at" — see below
  "tenant_id": "acme",               // ⭐ Day 160 — carry it explicitly
  "traceparent": "00-4bf9...",       // ⭐⭐ Day 148 — or the trace ends here
  "data": { "order_id": 812, "user_id": 7, "total": "49.00" }
}
```

```
⭐⭐ FOUR FIELDS THAT ARE NOT OPTIONAL, AND WHY:
⭐   ⭐ `id`          — ⭐⭐ consumers dedupe on it. Without it, at-least-once
⭐                       delivery is unusable by anyone.
⭐   ⭐ `occurred_at` — ⭐⭐ WHEN IT HAPPENED, NOT WHEN IT WAS SENT. ⭐ A retry
⭐                       three days later must carry the ORIGINAL time, or
⭐                       every consumer's ordering logic is wrong.
⭐   ⭐ `version`     — Part 3
⭐   ⭐ `traceparent` — ⭐ Day 148. ⭐⭐ Without it every consumer starts a new
⭐                       trace and you have no end-to-end picture at exactly
⭐                       the moment you most need one.
⭐
⭐ ⭐⭐ AND WHAT MUST NOT GO IN: PII BEYOND WHAT CONSUMERS NEED. ⭐ An event is
⭐   COPIED into every consumer's database and every log (Day 146) — ⭐⭐ you
⭐   have just multiplied your GDPR surface by the number of subscribers, and
⭐   you no longer know where the data is.
```

# Part 3 — ⭐⭐ Schema evolution: the payload is a public API

```
⭐⭐ THE FACT PEOPLE LEARN LATE: ONCE PUBLISHED, YOU DO NOT CONTROL WHO
⭐   CONSUMES IT OR WHEN. ⭐ There are messages in the queue right now written
⭐   by yesterday's code and read by tomorrow's. ⭐⭐ Day 125's breaking-change
⭐   rules apply, with one thing WORSE: ⭐ A BROKEN CONSUMER DOES NOT RETURN AN
⭐   ERROR TO ANYONE. It fails into a dead-letter queue you may not be watching.

⭐  ⭐⭐ SAFE (backward compatible):
⭐       ⭐ ADD AN OPTIONAL FIELD ⭐ (consumers must ignore unknown fields —
⭐          ⭐⭐ so `extra="ignore"` on consumer models, NOT `forbid`. This is
⭐          the exact opposite of Day 150's config rule, and for the opposite
⭐          reason: you control config, you do not control producers.)
⭐       ⭐ add a new event TYPE
⭐       ⭐ widen a range
⭐
⭐  ⭐⭐ BREAKING:
⭐       ⭐ remove or rename a field · ⭐ change a type (`"49.00"` → `49.0` —
⭐          ⭐⭐ and note this one is silent: it parses, then rounds money)
⭐       ⭐ change semantics with the same name — ⭐⭐ THE WORST, because
⭐          nothing fails. `total` including tax where it did not.
⭐       ⭐ make an optional field required
⭐
⭐  ⭐⭐ HOW TO MAKE A BREAKING CHANGE — the same shape as Day 138:
⭐       1. ⭐ publish v1 AND v2 in parallel (both topics, or both fields)
⭐       2. ⭐ consumers migrate on their own schedule
⭐       3. ⭐⭐ MEASURE v1 CONSUMPTION UNTIL IT IS ZERO — ⭐ you need a metric
⭐            per consumer group, or step 4 is a guess
⭐       4. ⭐ retire v1
⭐   ⇒ ⭐⭐ EXPAND/CONTRACT AGAIN. It is the same answer as schema migrations,
⭐        API versioning and cache keys — ⭐ because it is the same problem
⭐        every time: TWO VERSIONS ARE LIVE AND YOU DO NOT CONTROL BOTH.

⭐ ⭐⭐ AND ENFORCE IT MECHANICALLY: a SCHEMA REGISTRY (or a JSON Schema in CI)
⭐   that FAILS THE BUILD on an incompatible change. ⭐ Otherwise "we agreed
⭐   not to remove fields" lasts until the first busy sprint.
```

# Part 4 — ⭐⭐ Ordering, and the guarantee you cannot have

```
⭐⭐ THE THREE THINGS EVERYONE WANTS: EXACTLY-ONCE, GLOBAL ORDERING, AND HIGH
⭐   THROUGHPUT. ⭐ YOU GET TWO.

⭐  ⭐⭐ EXACTLY-ONCE — does not exist (Day 142). ⭐ At-least-once + an
⭐       idempotent consumer, keyed on `event.id`. ⭐⭐ Say it that way.
⭐
⭐  ⭐⭐ GLOBAL ORDERING — requires ONE partition, i.e. ONE consumer, i.e.
⭐       ⭐ NO PARALLELISM. ⭐⭐ Your throughput ceiling is one consumer, and it
⭐       is almost never worth it.
⭐       ⇒ ⭐⭐ WHAT YOU ACTUALLY WANT IS PER-KEY ORDERING: partition by
⭐         `order_id` or `user_id`, and ⭐ all events for ONE entity go to ONE
⭐         partition and are processed in order, while ⭐⭐ different entities
⭐         run in parallel. ⭐ Kafka partitions, SQS FIFO message groups.
⭐       ⇒ ⭐ AND THE COST: ⭐⭐ ONE SLOW ENTITY BLOCKS ITS WHOLE PARTITION.
⭐         ⭐ Head-of-line blocking, again (Days 105, 142), now keyed.
⭐
⭐  ⭐⭐ AND EVEN WITH PER-KEY ORDERING, A RETRY REORDERS. ⭐ Event A fails and
⭐       retries in 30 s; event B succeeds immediately ⇒ ⭐⭐ B IS APPLIED
⭐       BEFORE A. ⭐ Unless you block the partition on failure, which trades
⭐       availability for order.
⭐
⭐   ⇒ ⭐⭐ THEREFORE: MAKE CONSUMERS ORDER-INSENSITIVE WHERE YOU CAN. It is
⭐        cheaper than any ordering guarantee, and it always works:
⭐        ⭐ carry a VERSION or `occurred_at` and ⭐⭐ IGNORE ANYTHING OLDER
⭐          THAN WHAT YOU HAVE STORED (last-write-wins)
⭐        ⭐ prefer SET over INCREMENT (Day 142's idempotency rule)
⭐        ⭐ or fetch current state on receipt (Day 158's rule 3b)
⭐   ⇒ ⭐⭐ "WE HANDLE OUT-OF-ORDER RATHER THAN PREVENTING IT" IS THE STRONGER
⭐        ANSWER IN AN INTERVIEW, because it does not cost throughput and does
⭐        not break under retries.
```

# Part 5 — ⭐ Choreography vs orchestration, and the saga

```
⭐⭐ A BUSINESS PROCESS SPANS SERVICES: order → payment → inventory → shipping.
⭐   ⭐ There is no distributed transaction. ⭐⭐ So how do you keep it
⭐   consistent when step 3 fails?

⭐  ⭐ CHOREOGRAPHY — each service reacts to events. No coordinator.
⭐       ⭐ + fully decoupled, no single point of failure
⭐       ⭐ − ⭐⭐ THE PROCESS EXISTS NOWHERE. ⭐ To answer "why is this order
⭐            stuck?" you read four services' code and correlate four logs.
⭐            ⭐⭐ Cycles are easy to create and impossible to see.
⭐
⭐  ⭐⭐ ORCHESTRATION — one coordinator sends commands and tracks state.
⭐       ⭐ + ⭐⭐ THE PROCESS IS IN ONE PLACE, READABLE, AND ITS STATE IS
⭐            QUERYABLE — ⭐ "where is order 812?" has an answer.
⭐       ⭐ − the orchestrator is a coupling point and must itself be durable
⭐       ⇒ ⭐⭐ FOR ANYTHING WITH MONEY OR MORE THAN THREE STEPS, ORCHESTRATE.
⭐            ⭐ The ability to answer "where is it stuck?" is worth more than
⭐            the decoupling you give up.

⭐⭐ THE SAGA: NO ROLLBACK, ONLY COMPENSATION.
⭐   ⭐ payment captured, inventory reserved, ⭐ SHIPPING FAILS.
⭐   ⭐⭐ YOU CANNOT UN-CAPTURE. You issue a REFUND — a NEW transaction that
⭐        compensates. ⭐ Release the reservation. Notify the customer.
⭐   ⇒ ⭐⭐ COMPENSATION IS A BUSINESS DECISION, NOT A TECHNICAL ONE. ⭐ "Refund
⭐        in full", "refund minus a fee", "ship a replacement" — ⭐⭐ only the
⭐        product owner can decide, and this is the conversation people skip.
⭐   ⇒ ⭐ COMPENSATIONS MUST BE IDEMPOTENT AND MUST THEMSELVES BE RETRIED.
⭐        ⭐⭐ A failed compensation is the worst state in the system: money
⭐        taken, nothing delivered, and no automated path out.
⭐   ⇒ ⭐⭐ AND THE INTERMEDIATE STATES ARE VISIBLE TO USERS. ⭐ Between capture
⭐        and shipping the order is genuinely in a half-state — ⭐⭐ so your UI
⭐        needs a `pending` status, and "eventually consistent" becomes a
⭐        product requirement rather than an implementation detail.
```

```
⭐⭐ AND THE QUESTION TO ASK BEFORE ADOPTING ANY OF IT:
⭐   ⭐ "IS THIS ACTUALLY ASYNCHRONOUS IN THE BUSINESS?" ⭐⭐ If the user is
⭐     staring at a spinner waiting for the result, an event bus has added
⭐     latency, complexity and failure modes to a synchronous call.
⭐   ⭐⭐ EVENTS EARN THEIR KEEP WHEN: multiple consumers care, the consumers
⭐     are owned by other teams, the work can be late, or the producer must
⭐     stay up when the consumer is down. ⭐ If none of those hold, ⭐⭐ CALL THE
⭐     FUNCTION.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Imperative event names | A command in an event's clothes — then a consumer's failure means the producer was wrong. |
| Events between modules of one service | All the cost, none of the decoupling — you deploy them together anyway. |
| Notification-only events with many consumers | Six consumers means six callbacks per event — a herd pointed at yourself. |
| Adopting event sourcing by accident | You can't delete an event, and every old version must stay readable forever. |
| No `id` on the event | At-least-once delivery becomes unusable for every consumer. |
| `published_at` instead of `occurred_at` | A retry three days later breaks every consumer's ordering logic. |
| No `traceparent` in the payload | Every consumer starts a new trace; no end-to-end picture. |
| Full PII in the payload | Copied into every consumer's database and logs — your GDPR surface multiplies. |
| `extra="forbid"` on consumer models | You don't control producers. Ignore unknown fields. |
| Removing or retyping a field | Breaking, and a string-to-float money change is *silent*. |
| Changing semantics under the same name | The worst kind: nothing fails, everything is wrong. |
| Retiring v1 without measuring consumption | Step four becomes a guess. |
| No schema registry or CI check | "We agreed not to remove fields" lasts until the first busy sprint. |
| Promising exactly-once | At-least-once plus an idempotent consumer keyed on `event.id`. |
| Demanding global ordering | One partition, one consumer, no parallelism. |
| Assuming per-key ordering survives retries | A failed event retried in 30s is applied after one that succeeded. |
| Choreography for a money flow | "Why is this order stuck?" has no answer in any one place. |
| Expecting rollback in a saga | There's only compensation, and compensation is a business decision. |
| Non-idempotent, non-retried compensations | Money taken, nothing delivered, no automated way out. |
| No `pending` state in the UI | Eventual consistency is a product requirement, not an implementation detail. |
| An event bus for a synchronous user-facing call | Latency and failure modes added to something that wanted a function call. |

## Interview questions

**Q: Event or command?**

> A command is imperative with one intended handler — the sender knows what should happen next, so
> it's coupled to the receiver, and failure is the sender's problem. An event is past tense, a
> statement of fact, with zero or more handlers — the sender doesn't know who listens, and failure is
> each consumer's problem. The payoff is that adding a consumer requires no change to the producer:
> analytics, CRM sync and fraud checks all subscribe to `UserRegistered`, whereas with commands the
> registration service accumulates a call to every new feature until its job becomes "know about
> everything". Naming matters more than it looks — `UserRegistered` can't be rejected, `CreateUser`
> can, so an imperative event name is a command sneaking in. And the honest cost is that nobody owns
> the end-to-end flow any more; "what happens when a user registers" has no answer in any one file,
> which makes tracing the only map you have. So: events between bounded contexts, direct calls
> inside one.

**Q: What goes in an event payload?**

> A hybrid. Ids, type, version, `occurred_at`, tenant, `traceparent`, plus the handful of fields
> consumers actually need — and documentation that anything else must be fetched. Pure notification
> means every consumer calls back, so six consumers is six API calls per event, which is a thundering
> herd pointed at yourself. Full state transfer means consumers keep working while you're down,
> which is the real argument for it, but the payload becomes a public API you have to maintain. Four
> fields aren't optional: `id`, because consumers dedupe on it and without it at-least-once delivery
> is unusable; `occurred_at` rather than published-at, because a retry three days later must carry
> the original time or every consumer's ordering logic is wrong; `version`; and `traceparent`, or
> each consumer starts a fresh trace. And I'd keep PII out, because an event is copied into every
> consumer's database and every log — you've multiplied your data surface by the number of
> subscribers and no longer know where it lives.

**Q: How do you change an event schema?**

> Treating the payload as a public API, because there are messages in the queue right now written by
> yesterday's code and read by tomorrow's. Adding an optional field is safe *provided* consumers
> ignore unknown fields — so consumer models use `extra="ignore"`, which is the exact opposite of
> what I do for config, and for the opposite reason: I control my config, I don't control producers.
> Breaking changes are removals, renames, type changes — and note a money field going from string to
> float is *silent*, it parses and then rounds — and worst of all, changing semantics under the same
> name, where nothing fails and everything is wrong. For a real break I publish both versions in
> parallel, let consumers migrate on their own schedule, measure v1 consumption per consumer group
> until it's zero, then retire it. It's expand/contract again, which by now is the answer to every
> two-versions-live problem. And I'd enforce compatibility with a schema registry or a JSON Schema
> check in CI, because a shared agreement lasts until the first busy sprint.

**Q: Can you guarantee events are processed in order?**

> Globally, only by having one partition and therefore one consumer, which caps throughput at one
> consumer and is almost never worth it. What people actually want is per-key ordering: partition by
> `order_id` or `user_id`, so all events for one entity are ordered while different entities process
> in parallel. The cost is head-of-line blocking — one slow entity blocks its whole partition. And
> even then, a retry reorders: if event A fails and retries in thirty seconds while B succeeds
> immediately, B is applied first, unless you block the partition on failure and trade availability
> for order. So my preferred answer is to make consumers order-insensitive instead: carry a version
> or `occurred_at` and ignore anything older than what's stored, prefer set over increment, or fetch
> current state on receipt. Handling out-of-order is cheaper than preventing it and doesn't break
> under retries.

**Q: Payment succeeded, shipping failed. What now?**

> A saga — there's no distributed transaction, so there's no rollback, only compensation. You can't
> un-capture a payment, so you issue a refund, which is a new transaction that compensates, release
> the inventory reservation, and notify the customer. Two things people miss. Compensation is a
> business decision, not a technical one — full refund, refund minus a fee, ship a replacement — and
> only the product owner can decide, which is the conversation that gets skipped. And compensations
> must themselves be idempotent and retried, because a failed compensation is the worst state in the
> system: money taken, nothing delivered, no automated path out. I'd also orchestrate rather than
> choreograph for anything involving money, because with choreography "why is this order stuck" means
> reading four services and correlating four logs, whereas an orchestrator holds the process state
> and can answer it. And the intermediate states are visible to users, so a `pending` status is a
> product requirement rather than an implementation detail.

## Mini task

1. ⭐ Take one existing direct call between services and model it both as a command and as an event. Write down what changes about who owns failure.
2. ⭐⭐ Define an event envelope with all four required fields. Publish it, and confirm the trace spans producer and consumer as one trace.
3. ⭐ Publish with `published_at` instead of `occurred_at`, then replay an event from three days ago and watch a consumer's ordering logic get it wrong.
4. ⭐⭐ Set `extra="forbid"` on a consumer model, add an optional field to the producer, and break the consumer. Then fix it with `ignore`.
5. ⭐⭐ Change a money field from `"49.00"` to `49.0` and confirm the consumer silently rounds. That's the silent break.
6. ⭐ Add a JSON Schema compatibility check to CI and make it fail on a field removal.
7. ⭐⭐ Partition by `user_id` and prove per-key ordering holds. Then make one event fail and retry, and prove ordering does *not* hold.
8. ⭐⭐ Make a consumer order-insensitive with `occurred_at` last-write-wins. Replay events out of order and confirm the final state is correct.
9. ⭐⭐ Implement a three-step saga with an orchestrator and a compensating refund. Fail step three, and then fail the compensation too — decide what you do.
10. ⭐ Add a `pending` status to the UI for the window between capture and shipping.

## 🎙️ Articulation drill

**Two minutes: "Should we move to an event-driven architecture?"**

Start by asking what problem it solves, and give the honest test: events earn their keep when
multiple consumers care, the consumers belong to other teams, the work can be late, or the producer
must stay up while the consumer is down — otherwise call the function. Then, assuming it's justified,
cover the three decisions that actually matter: events not commands with past-tense names, a hybrid
payload with the four mandatory envelope fields, and schema evolution treated as a public API with
expand/contract enforced in CI. Then the guarantees, honestly: no exactly-once, per-key rather than
global ordering, and — the strongest line — **handle out-of-order rather than preventing it, because
it's cheaper and doesn't break under retries**. Close on the cost you're accepting: **the end-to-end
flow now exists nowhere, so tracing stops being optional and becomes the only map you have.**
