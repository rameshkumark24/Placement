# Day 086

**L-086** · ⭐⭐ **Branching, the three-way merge, and merge vs rebase** — argued, not asserted

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a merge combines two lines of history into one new commit with two
> parents; a rebase throws your commits away and writes new ones on a different base — so merge
> preserves what happened and rebase produces what you wish had happened.**
>
> ⭐ Everything today follows from Day 084's one fact: **a commit's hash covers its parent's hash.**

---

# Part 1 — ⭐ Branches, and the commands worth switching to

```bash
git switch -c feature/rate-limit     # ⭐⭐ create and switch  (modern; use this)
git switch main                      # ⭐ switch
git switch -                         # ⭐ the previous branch — like `cd -`
git branch -vv                       # ⭐⭐ branches + their upstream + ahead/behind
git branch -d old                    # ⭐ delete if merged · -D to force
git branch --merged main             # ⭐⭐ what is safe to delete — run this monthly
```

⭐⭐ **`git switch` and `git restore` replaced `git checkout`** for a good reason: `checkout` did three
unrelated jobs (move HEAD, create a branch, overwrite files from the index) — **and the third one
silently destroys work.** ⭐ `switch` moves, `restore` overwrites. **Two verbs, two risks, no
ambiguity.**

```
⭐⭐ FROM DAY 084: A BRANCH IS A 41-BYTE FILE. THEREFORE:
⭐   · creating one is instant and costs nothing ⇒ ⭐ branch for everything
⭐   · ⭐⭐ COMMITTING MOVES THE POINTER THE BRANCH YOU ARE ON. That is all "being
⭐     on a branch" means.
⭐   · deleting one deletes the pointer ⇒ ⭐ the commits survive (Day 087)
```

# Part 2 — ⭐⭐ Fast-forward, and the three-way merge

```
⭐⭐ CASE 1 — FAST-FORWARD. main has not moved since you branched:
⭐
⭐   main ──A──B                        main ──A──B──C──D
⭐               ╲                                      ▲
⭐   feature       C──D        ⇒ merge:                 └── main just MOVES here
⭐
⭐   ⇒ ⭐⭐ B IS AN ANCESTOR OF D, so there is nothing to combine — Git just moves
⭐        the pointer forward. ⭐ NO MERGE COMMIT IS CREATED. This is not a
⭐        "special case", it is the absence of a merge.
⭐   ⇒ ⭐ git merge --no-ff  forces a merge commit anyway, to record that a feature
⭐        branch existed as a unit.
```

```
⭐⭐ CASE 2 — THREE-WAY MERGE. Both branches moved:
⭐
⭐                 ┌──C──D── feature
⭐   ──A──B────────┤                          B = ⭐⭐ THE MERGE BASE
⭐                 └──E──F── main                 (the common ancestor)
⭐
⭐   ⇒ result: a NEW commit M with TWO PARENTS (D and F).
⭐   ⇒ ⭐ that is what HEAD^1 and HEAD^2 mean (Day 084).
```

```
⭐⭐ WHY THREE-WAY AND NOT JUST "DIFF THE TWO TIPS"? DERIVE IT — this is a real
⭐   interview question and the answer is genuinely nice:
⭐
⭐   A line exists in `main` and NOT in `feature`. With only those two versions,
⭐   there are TWO possible histories and NO WAY TO TELL THEM APART:
⭐        (a) main ADDED it        ⇒ keep it
⭐        (b) feature DELETED it   ⇒ remove it
⭐   ⇒ ⭐⭐ THE MERGE BASE DISAMBIGUATES: if the line is in the base, feature
⭐        deleted it. If it is not, main added it.
⭐   ⇒ ⭐⭐ A CONFLICT IS EXACTLY THE CASE WHERE BOTH SIDES CHANGED THE SAME
⭐        REGION relative to the base — so Git has two competing intentions and
⭐        no basis to choose. ⭐ It is not a failure; it is Git correctly refusing
⭐        to guess.
⭐   ⇒ ⭐ `git merge-base main feature` prints it. `git diff $(git merge-base …)`
⭐        shows what you REALLY changed, minus what main did meanwhile.
```

# Part 3 — ⭐⭐ Rebase, and the golden rule

```
⭐⭐ REBASE = REPLAY. "Pretend I started from the current tip."
⭐
⭐   before:              ┌──C──D── feature
⭐            ──A──B──────┤
⭐                        └──E──F── main
⭐
⭐   git switch feature && git rebase main
⭐
⭐   after:   ──A──B──E──F──C'──D'── feature      ⭐⭐ NOTE THE PRIMES.
⭐
⭐   ⇒ ⭐⭐ C' IS NOT C. Its parent changed ⇒ its hash changed (Day 084) ⇒ IT IS A
⭐        DIFFERENT OBJECT with the same diff and message. C and D still exist,
⭐        unreachable, until gc (Day 087 gets them back).
⭐   ⇒ ⭐ history is now LINEAR: no merge commit, and `git log` reads as a story.
```

```
⭐⭐⭐ THE GOLDEN RULE: NEVER REBASE COMMITS THAT OTHER PEOPLE HAVE.
⭐    And the reason, which is what you should actually say:
⭐
⭐    Your colleague's clone has C and D. You rebase and force-push C' and D'.
⭐    ⇒ their `git pull` sees a history that no longer contains their commits
⭐    ⇒ ⭐⭐ IT MERGES THE TWO VERSIONS ⇒ NOW BOTH C,D AND C',D' ARE IN main.
⭐    ⇒ ⭐⭐ EVERY COMMIT IS DUPLICATED, and the "fix" everyone tries — merging
⭐         again — makes it worse. ⭐ Untangling it is a genuinely bad afternoon.
⭐
⭐    ⇒ ⭐⭐ THEREFORE THE PRACTICAL RULE: rebase YOUR OWN unpushed work freely.
⭐         Merge to integrate anything shared. ⭐ "Is anyone else's clone holding
⭐         this commit?" is the only question you need to ask.
```

```bash
git rebase main                     # ⭐ replay my branch on the current main
git rebase --continue / --abort     # ⭐⭐ --abort ALWAYS gets you back. Remember it.
git rebase --onto main old new      # ⭐ surgical: move a range to a new base
git pull --rebase                   # ⭐⭐ fetch + rebase — no "Merge branch main" noise
git config --global pull.rebase true    # ⭐⭐ worth setting once, forever
```

⭐⭐ **`git pull --rebase` as a default is one of the highest-value settings in Git.** A plain `pull`
creates a merge commit every time two people work on the same branch, and a history full of *"Merge
branch 'main' of github.com:… into main"* is pure noise that hides the real merges.

# Part 4 — ⭐⭐ Interactive rebase — cleaning up before review

```bash
git rebase -i main          # ⭐ or HEAD~5 — edit the last five commits
```

```
pick  a1b2c3  Add rate limiter
squash b4c5d6  fix typo                 ⭐⭐ squash = fold in, COMBINE the messages
fixup  c7d8e9  oops forgot the import   ⭐⭐ fixup  = fold in, DISCARD the message
reword d0e1f2  Add tests                ⭐ change the message only
edit   e3f4a5  Refactor limiter         ⭐ stop here so I can amend the content
drop   f6a7b8  debugging print          ⭐ remove entirely
       ⭐ reorder the lines to reorder the commits
```

```bash
git commit --fixup <sha>            # ⭐⭐ tag a commit as "a fix for THAT one"
git rebase -i --autosquash main     # ⭐⭐ arranges every fixup automatically
git config --global rebase.autosquash true
```

```
⭐⭐ THE WORKFLOW THIS ENABLES, AND IT IS THE POINT OF THE WHOLE DAY:
⭐   commit MESSILY while you work — wip, fix, oops, actually-fix — because
⭐   stopping to craft a commit interrupts thinking.
⭐   ⇒ ⭐⭐ THEN, BEFORE PUSHING, rebase -i INTO THE COMMITS YOU WISH YOU HAD MADE.
⭐   ⇒ ⭐⭐ Your reviewer reads a clean, logical sequence; you never had to work
⭐        that way. ⭐ This is rebase's actual purpose, and it is why "history
⭐        should record what happened" is the wrong frame: ⭐⭐ HISTORY IS A
⭐        DOCUMENT WRITTEN FOR FUTURE READERS, not a court transcript.
```

⚠️ ⭐ **`edit` and `--abort` are your safety line.** If an interactive rebase goes wrong at any point,
`git rebase --abort` restores the exact state you started from — **and if you have already finished
it, `git reflog` still has the original** (tomorrow).

# Part 5 — ⭐⭐ The decision

| | ⭐ Merge | ⭐ Rebase |
|---|---|---|
| History | ⭐ true, branching | ⭐⭐ linear, readable |
| Hashes | ⭐ preserved | ⭐⭐ **rewritten** |
| Conflicts | ⭐ once, at the end | ⚠️ ⭐⭐ **possibly once per commit** |
| Safe on shared branches | ⭐⭐ **yes** | ⭐⭐ **no** |
| `git log` reads as | what happened | ⭐ what you meant |
| ⭐ Bisect | ⭐ fine either way | ⭐ fine — ⚠️ if every replayed commit still builds |

```
⭐⭐ THE POSITION WORTH DEFENDING IN AN INTERVIEW — take one, do not hedge:
⭐   1. ⭐⭐ REBASE YOUR OWN BRANCH onto main before opening a PR ⇒ the reviewer
⭐        sees your work against current main, not against a week-old base.
⭐   2. ⭐⭐ CLEAN IT UP with rebase -i ⇒ atomic commits (Day 085), no "wip".
⭐   3. ⭐⭐ MERGE THE PR (or squash-merge) ⇒ the integration is recorded, and
⭐        nobody's shared history was rewritten.
⭐   4. ⭐ NEVER rebase main, a release branch, or anything someone else has pulled.
⭐
⭐   ⇒ ⭐⭐ ONE SENTENCE: "rebase to prepare, merge to integrate."
```

⚠️ ⭐⭐ **The conflict cost is the real argument against rebasing a long branch.** A merge resolves
each conflicting region **once**; a rebase replays every commit in turn, so the *same* conflict can
reappear at commit after commit. ⭐ `git rerere` (`rerere.enabled true`) records your resolutions and
replays them — **it is the specific fix for that specific pain**, and almost nobody has it on.

⭐ **`git merge --squash feature`** is the third option: takes the whole branch as *one* staged change
with no merge commit and no branch history. ⭐⭐ Useful when the branch's internal commits are
worthless — and lossy in exactly the same way, which is the trade-off Day 088 revisits as
"squash-merge on the platform".

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Rebasing a shared branch** | ⭐⭐ Everyone's clone duplicates every commit. Merge instead. |
| ⭐ Force-pushing after a rebase without warning | ⭐ `--force-with-lease` (Day 088), and tell people. |
| Panicking mid-rebase | ⭐⭐ `git rebase --abort` restores exactly where you were. |
| ⭐ Rebasing a 40-commit branch | ⭐⭐ The same conflict, forty times. Merge, or enable `rerere`. |
| Plain `git pull` on a shared branch | ⭐⭐ Merge-commit noise. `pull.rebase true`. |
| ⭐ Treating a conflict as an error | ⭐⭐ It is Git refusing to guess between two intentions. |
| Thinking fast-forward is a kind of merge | ⭐ It is the **absence** of one — the base *is* the tip. |
| ⭐ `git checkout` for everything | ⭐ `switch` to move, `restore` to overwrite. |
| ⭐ `git checkout .` "to be safe" | ⭐⭐ That silently destroys uncommitted work. |
| Long-lived feature branches | ⭐⭐ Divergence grows superlinearly — merge daily (Day 088). |

## Interview questions

**Q: Why does a merge need three commits and not two?**
> Because with only the two tips you can't tell an addition from a deletion. If a line is in `main`
> and not in `feature`, either `main` added it or `feature` removed it, and those need opposite
> outcomes. The merge base — the common ancestor — settles it: if the line is in the base, `feature`
> deleted it; if it isn't, `main` added it. That framing also explains conflicts precisely: a conflict
> is where both sides changed the same region relative to the base, so there are two competing
> intentions and no basis to choose. It's not a failure, it's Git declining to guess.

**Q: Merge or rebase?**
> Rebase to prepare, merge to integrate. I rebase my own branch onto main before opening a PR so the
> reviewer sees my work against current main rather than a week-old base, and I clean it up with an
> interactive rebase so the commits are atomic instead of "wip, fix, oops". Then the PR gets merged,
> which records the integration and rewrites nobody's history. The rule underneath is a single
> question: has anyone else's clone got these commits? If yes, never rebase them.

**Q: What actually goes wrong if you rebase a shared branch?**
> Rebasing rewrites hashes, because a commit's hash covers its parent's. Your colleague's clone still
> has the originals, so when they pull, Git sees a history that no longer contains their commits and
> merges the two versions — and now both the old and new copies of every commit are in the branch.
> Everything is duplicated, and the instinctive fix of merging again makes it worse. That's the whole
> content of the golden rule; it isn't superstition.

**Q: How do you prepare a branch for review?**
> I commit messily while working, because stopping to craft a commit interrupts thinking. Then before
> pushing I rebase interactively onto main: squash the fixups, drop the debug commits, reword anything
> unclear, and reorder so the sequence tells a story. `git commit --fixup` plus `--autosquash` does
> most of it mechanically. The reviewer gets a clean logical progression I never actually worked in —
> which I think is the right frame: history is a document for future readers, not a court transcript.

**Q: When would you avoid rebasing your own branch?**
> When it's long and conflicts. A merge resolves each conflicting region once; a rebase replays every
> commit against the new base, so the same conflict can come back at commit after commit. If I'm
> forty commits deep into a conflicting area, I'll merge main in instead, or enable `git rerere` so
> Git replays my earlier resolutions automatically. That's the specific tool for that specific pain
> and almost nobody has it switched on.

   was created**, and explain why.

## 🎙️ Articulation drill

Record two minutes: **"Merge or rebase?"** — a question designed to find out whether you have an
opinion or a memorised slogan.

⭐ **Answer with a policy, not a preference:** **"rebase to prepare, merge to integrate. I rebase my
own branch onto main before opening a PR, clean it up interactively so the commits are atomic, and
then the PR gets merged. The only rule I need underneath that is one question — has anyone else's
clone got these commits?"**

⭐⭐ **Then prove you know the mechanism, because this is where most answers stop:** *"rebase rewrites
hashes, because a commit's hash covers its parent's hash. So if I rebase something a colleague already
has, their clone still holds the originals; their pull sees a history missing their commits, merges
the two versions, and now every commit exists twice. That's not superstition about history purity,
it's a concrete failure with a concrete cause."*

⭐ **Then give the counter-case, which is what makes it a real opinion:** *"and I don't rebase
reflexively. A merge resolves each conflicting region once; a rebase replays every commit against the
new base, so on a long branch the same conflict can reappear ten times. There I'd merge main in
instead, or turn on `rerere` so Git replays my earlier resolutions."*

⭐⭐ **Close on the framing:** *"the reason I like rebasing my own work is that I don't think history
is a transcript. I commit messily while I'm thinking, and then I write the commits I wish I'd made —
because the reader is a colleague at 2 a.m. bisecting a failure, and what helps them is a clean logical
sequence, not an honest record of my false starts."*
