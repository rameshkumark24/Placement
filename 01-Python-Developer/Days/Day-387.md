# Part 2 — Multi-AZ is not a read replica

```
⭐⭐ THE DISTINCTION AN INTERVIEWER IS ACTUALLY TESTING:

⭐ MULTI-AZ (instance) ⭐⭐ — ***AVAILABILITY. NOT SCALE.***
⭐   ⭐ A synchronous standby in another AZ.
⭐   ⭐⭐ YOU CANNOT READ FROM IT. IT SERVES NO TRAFFIC EVER.
⭐   ⭐ Failover: ***60–120 s***, automatic, ⭐ zero data loss.
⭐   ⭐⭐ IT DOUBLES YOUR DATABASE COST TO BUY NOTHING BUT
⭐     SURVIVAL — ⭐ which is correct for prod and wasteful for
⭐     dev, and people buy it in both or neither.

⭐ READ REPLICA ⭐⭐ — ***SCALE. NOT AVAILABILITY.***
⭐   ⭐ Asynchronous. ⭐⭐ IT LAGS — MILLISECONDS NORMALLY,
⭐     ***MINUTES*** DURING A BIG WRITE OR A VACUUM.
⭐   ⭐ Readable. ⭐ Promotable manually (⭐⭐ WITH DATA LOSS EQUAL
⭐     TO THE LAG).
⭐   ⭐⭐ AND THE APPLICATION CONSEQUENCE IS DAY 328's, EXACTLY:
⭐     ***READ-YOUR-WRITES BREAKS.*** ⭐ User posts a comment,
⭐     next page load hits a replica, ⭐⭐ COMMENT IS GONE. ⭐ The
⭐     fix is routing: writes and the reads that must see them
⭐     go to the writer; ⭐ everything else may go to a replica.
⭐     ⭐⭐ THAT IS AN APPLICATION DECISION AND NO AWS SETTING
⭐     MAKES IT FOR YOU.

⭐ MULTI-AZ ***CLUSTER*** (newer) — ⭐ three instances, two of
⭐   them ***readable*** standbys, ⭐⭐ FAILOVER UNDER 35 s.
⭐   ⭐ Semi-synchronous. ⭐ The better default for new prod
⭐     Postgres if the region offers it.

⭐ AURORA — ⭐ replicas share the ***same storage volume***, so
⭐   ⭐⭐ REPLICA LAG IS TYPICALLY 10–20 ms RATHER THAN SECONDS,
⭐   ⭐ failover ~30 s, ⭐ six copies across three AZs.
⭐   ⭐ Separate `writer` and `reader` endpoints, ⭐⭐ AND THE
⭐     READER ENDPOINT DNS-ROUND-ROBINS, WHICH INTERACTS BADLY
⭐     WITH POOLS (PART 3).
```

# Part 3 — ⭐⭐ The failover trap, Python edition

> The Java track has this day too, and its version is about the JVM caching DNS forever. **Python's
> problem is different, and worse, because it is not a DNS cache at all.**

```
⭐ WHAT A FAILOVER ACTUALLY IS: ⭐⭐ THE ENDPOINT CNAME IS
⭐   REPOINTED AT THE STANDBY'S ADDRESS. ⭐ TTL is 5 s. ⭐ AWS's
⭐   part finishes in about a minute.

⭐⭐ NOW THE FOUR LAYERS THAT CAN STILL BE WRONG:
⭐ ① ⭐ The OS resolver cache. ⭐ Usually short. ⭐ Rarely the
⭐    problem.
⭐ ② ⭐⭐ ***CPython DOES NOT CACHE DNS AT ALL*** — ⭐ so the
⭐    famous JVM answer does not apply and you should say so.
⭐ ③ ⭐⭐ ***BUT YOUR CONNECTION POOL HOLDS ALREADY-OPEN SOCKETS
⭐    TO THE OLD IP.*** ⭐ Re-resolving changes ***nothing***,
⭐    because nobody is resolving — ⭐⭐ THE SOCKET IS ALREADY
⭐    ESTABLISHED AND SQLALCHEMY IS HANDING IT OUT.
⭐ ④ ⭐⭐ AND HERE IS THE PART THAT MAKES IT VICIOUS: ***AFTER AN
⭐    AURORA FAILOVER THE OLD WRITER IS DEMOTED TO A READER — SO
⭐    THE SOCKET IS STILL ALIVE AND STILL ANSWERS.***

⭐⭐ ⇒ THE SYMPTOM, WHICH IS NOTHING LIKE A NETWORK ERROR:
⭐   ⭐⭐ `psycopg.errors.ReadOnlySqlTransaction:
⭐     cannot execute INSERT in a read-only transaction`
⭐   ⭐ Reads work perfectly. ⭐ Writes fail. ⭐⭐ AND BECAUSE THE
⭐     CONNECTION IS ***HEALTHY***, NOTHING IN YOUR POOL, YOUR
⭐     RETRY LOGIC OR YOUR HEALTH CHECK EVER DECIDES TO
⭐     RECONNECT. ⭐ It stays broken until a human restarts the
⭐     service. ⭐⭐ THE DATABASE RECOVERED IN 30 SECONDS AND YOUR
⭐     OUTAGE LASTED FORTY MINUTES.
```

```python
# ⭐⭐ THE FIX — three settings and one listener.
engine = create_engine(
    DSN,
    pool_pre_ping=True,       # ⭐ cheap liveness check on checkout
    pool_recycle=300,         # ⭐⭐ NO SOCKET LIVES > 5 MIN
    pool_size=10, max_overflow=5,
    connect_args={
        "connect_timeout": 5,
        # ⭐⭐ THE ONE MOST PEOPLE MISS: ASK libpq FOR A WRITER.
        "target_session_attrs": "read-write",
    },
)

from sqlalchemy import event
from psycopg.errors import ReadOnlySqlTransaction

@event.listens_for(engine, "handle_error")
def _drop_stale_pool(ctx):
    if isinstance(ctx.original_exception, ReadOnlySqlTransaction):
        # ⭐⭐ NOT ONE CONNECTION — THE ***WHOLE POOL*** IS POINTED
        # ⭐   AT A DEMOTED INSTANCE. INVALIDATE ALL OF IT.
        ctx.invalidate_pool_on_disconnect = True
        engine.dispose(close=False)
```

```
⭐⭐ AND THE THREE THINGS THAT MAKE IT ACTUALLY SURVIVABLE:
⭐   ⭐ `pool_pre_ping` catches the ***dead*** socket case.
⭐   ⭐⭐ `pool_recycle` BOUNDS HOW LONG ***ANY*** WRONGNESS CAN
⭐     LAST — ⭐ it is the setting that turns "until a human
⭐     notices" into "at most five minutes", ⭐ and it costs one
⭐     reconnect per connection per five minutes.
⭐   ⭐⭐ `target_session_attrs=read-write` MAKES libpq ITSELF
⭐     REFUSE A READ-ONLY SERVER, ⭐ which converts the silent
⭐     wrong-node case into a loud connection failure — ⭐⭐ AND A
⭐     LOUD FAILURE RETRIES, WHILE A SILENT ONE DOES NOT.
⭐   ⭐⭐ ⇒ THEN ***TEST IT***: RDS HAS A "REBOOT WITH FAILOVER"
⭐     BUTTON. ⭐ Press it under load. ⭐ Measure how long your
⭐     write error rate stays above zero. ⭐⭐ THAT NUMBER — NOT
⭐     AWS'S — IS YOUR FAILOVER TIME.
```

# Part 4 — Connections, and why Python runs out of them

```
⭐⭐ POSTGRES ON RDS: `max_connections` DEFAULTS TO A FORMULA —
⭐   `LEAST({DBInstanceClassMemory/9531392}, 5000)`
⭐   ⭐ db.t3.medium (4 GB) → ⭐⭐ ~410
⭐   ⭐ db.r6g.large (16 GB) → ~1,600

⭐⭐ NOW COUNT YOURS, BECAUSE PYTHON'S PROCESS MODEL MULTIPLIES:
⭐   ⭐ 6 ECS tasks × 4 gunicorn workers × pool_size 10
⭐     ⭐⭐ = 240 CONNECTIONS AT IDLE
⭐   ⭐ + max_overflow 5 each → ⭐⭐ 360 UNDER LOAD
⭐   ⭐ + 2 Celery workers × 8 threads → ⭐⭐ OVER THE LIMIT
⭐   ⭐ + a migration job, + someone's psql, + Metabase
⭐   ⭐⭐ ⇒ `FATAL: remaining connection slots are reserved` —
⭐     ⭐ AND IT ARRIVES DURING A DEPLOY, WHEN OLD AND NEW TASKS
⭐     BOTH HOLD POOLS (DAY 371).
⭐   ⭐⭐ EACH POSTGRES CONNECTION IS ALSO A ***PROCESS*** WITH
⭐     ~5–10 MB OF ITS OWN — ⭐ so this is memory, not just a
⭐     counter.

⭐⭐ ⇒ ***RDS PROXY*** — ⭐ multiplexes many client connections
⭐   onto few database ones, ⭐ and survives failover by holding
⭐   the client side open. ⭐⭐ IT IS THE STANDARD ANSWER FOR
⭐   LAMBDA (DAY 391) AND A GOOD ONE FOR CONTAINERS.
⭐   ⭐ Costs $0.015/vCPU-hour of the database. ⭐ Adds ~1–2 ms.
⭐   ⭐⭐ AND THE CAVEAT NOBODY MENTIONS — ***PINNING***: ⭐ session
⭐     state (a `SET`, an advisory lock, a prepared statement, an
⭐     open transaction) ⭐⭐ PINS YOUR CLIENT TO ONE BACKEND
⭐     CONNECTION AND DEFEATS THE MULTIPLEXING ENTIRELY. ⭐ With
⭐     psycopg3's default prepared-statement threshold you can
⭐     pin almost everything — ⭐⭐ SO WATCH THE
⭐     `DatabaseConnectionsCurrentlySessionPinned` METRIC, OR YOU
⭐     ARE PAYING FOR A PROXY THAT IS NOT PROXYING.
⭐ ⭐ The alternative is PgBouncer in transaction mode, which you
⭐   then operate. ⭐⭐ SAME TRADE AS EVERY DAY IN THIS STAGE.
```

# Part 5 — Aurora, judged rather than sold

```
⭐ WHAT IS GENUINELY DIFFERENT: ⭐ storage is a distributed
⭐   service, ⭐ six copies across three AZs, ⭐⭐ REPLICAS READ THE
⭐   ***SAME*** VOLUME SO THEY DO NOT REPLAY A LOG — ⭐ hence
⭐   10–20 ms lag, ⭐ 15 replicas, ⭐ ~30 s failover, ⭐ instant
⭐   clones for a test environment (⭐⭐ COPY-ON-WRITE, SO A 2 TB
⭐   CLONE IS FREE AND TAKES SECONDS).

⭐ WHAT IT COSTS: ⭐ ~20% more per instance-hour, ⭐⭐ PLUS AN I/O
⭐   CHARGE PER MILLION REQUESTS THAT IS UNBOUNDED AND HAS
⭐   SURPRISED A LOT OF PEOPLE. ⭐ Aurora I/O-Optimized removes
⭐   the I/O charge for a higher instance price — ⭐⭐ WORTH IT
⭐   ABOVE ROUGHLY 25% OF SPEND GOING TO I/O.

⭐ SERVERLESS v2: ⭐ scales in ACUs (2 GB each) in seconds.
⭐   ⭐⭐ GOOD FOR SPIKY AND FOR DEV. ⭐ At a steady high load it
⭐   is more expensive than a provisioned instance, ⭐ and the
⭐   minimum ACU floor means it is not free when idle.

⭐⭐ ⇒ THE HONEST POSITION: ***TAKE AURORA WHEN YOU NEED READ
⭐   REPLICAS WITH LOW LAG, FAST FAILOVER, OR CHEAP CLONES.***
⭐   ⭐ For one modest Postgres with no replicas, ⭐⭐ PLAIN RDS
⭐   MULTI-AZ IS CHEAPER, SIMPLER AND ENTIRELY SUFFICIENT — ⭐ and
⭐   saying that in an interview is worth more than reciting
⭐   Aurora's feature list.
```

# 💬 Interview

**1. "Multi-AZ or a read replica?"**
> ⭐ They solve different problems and people conflate them. ⭐⭐ **Multi-AZ is a synchronous standby you
> can never read from — it buys availability and nothing else, doubles the cost, and fails over in 60
> to 120 seconds with no data loss. A read replica is asynchronous and readable — it buys read scale,
> lags, and promoting it loses whatever was in flight.** ⭐ And the replica has an application
> consequence no AWS setting solves: ⭐⭐ **read-your-writes breaks**, so writes and the reads that must
> observe them go to the writer while everything else can go to a replica — that's a routing decision
> in my code.

**2. ⭐⭐ "Your database failed over in thirty seconds and your app was broken for forty minutes. Explain."**
> ⭐ The failover is a DNS repoint, but nothing in my process was waiting on DNS. ⭐⭐ **My connection
> pool held already-open sockets to the old IP — and after an Aurora failover the old writer is
> demoted to a reader, so those sockets are still alive and still answering.** ⭐ Reads worked fine;
> writes failed with "cannot execute INSERT in a read-only transaction". ⭐⭐ **And because the
> connection was healthy, nothing in the pool, the retry logic or the health check ever decided to
> reconnect** — it stayed broken until a human restarted the service. ⭐ The fix is `pool_pre_ping` for
> dead sockets, ⭐⭐ **`pool_recycle` to bound how long any wrongness can last, and
> `target_session_attrs=read-write` so libpq refuses a read-only server outright — which converts a
> silent wrong-node into a loud connection failure, and loud failures retry.** ⭐ Then I press "reboot
> with failover" under load and measure how long my write errors last, because that number is my
> failover time, not AWS's.

**3. "Why do Python apps run out of database connections?"**
> ⭐ Because the process model multiplies. ⭐⭐ **Six tasks times four gunicorn workers times a pool of
> ten is 240 connections at idle before overflow, before Celery, before a migration job and someone's
> psql** — and a db.t3.medium's default `max_connections` is about 410. ⭐ It usually breaks during a
> deploy, when old and new tasks both hold pools. ⭐⭐ **And each Postgres connection is a process with
> its own five to ten megabytes, so it's a memory problem, not just a counter.** ⭐ RDS Proxy or
> PgBouncer in transaction mode is the answer, ⭐⭐ **with the caveat that session state — a `SET`, an
> advisory lock, prepared statements — pins a client to a backend connection and defeats the
> multiplexing**, so I'd watch the session-pinned metric or I'm paying for a proxy that isn't
> proxying.

**4. "Aurora or RDS?"**
> ⭐ Aurora when I need low-lag read replicas, sub-30-second failover, or cheap copy-on-write clones
> for test environments — ⭐⭐ **replicas read the same storage volume rather than replaying a log,
> which is why lag is ten to twenty milliseconds instead of seconds.** ⭐ It costs about 20% more per
> hour plus an unbounded I/O charge, which is what surprises people; I/O-Optimized removes that above
> roughly 25% of spend. ⭐⭐ **For one modest Postgres with no replicas, plain RDS Multi-AZ is cheaper,
> simpler and entirely sufficient** — I'd rather say that than recite Aurora's feature list.

**5. ⭐⭐ "What's your RTO for a database restore?"**
> ⭐ Whatever I measured, not what the runbook says. ⭐⭐ **A point-in-time restore creates a new
> instance with a new endpoint and takes twenty to forty minutes for a large database — then I have to
> repoint the application, and then the buffer cache is cold so the first ten minutes are slow.** ⭐ The
> whole sequence is the RTO. ⭐ I'd also point out that a snapshot in the same account isn't a backup
> against the threat that matters, ⭐⭐ **so snapshots get copied to a separate account with a separate
> KMS key** — that's the copy that survives a compromised credential.

**6. "Two Postgres settings you'd always set."**
> ⭐⭐ **`statement_timeout` per role rather than globally** — ten seconds for the app role, unlimited
> for the migration role — so one bad query can't hold a connection for an hour while migrations still
> run. ⭐⭐ **And `idle_in_transaction_session_timeout`, because that's the one that saves you from a
> Python bug that opened a transaction and then made an HTTP call** — an idle-in-transaction
> connection holds locks and blocks vacuum, and it's a leading cause of "the database is stuck".
