**P-275** · 🔀 **The workflow screen** — ⭐⭐ the state machine, made visible

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: the UI must never decide which transitions are legal — it must *display*
> the decision the server already made, because a client that computes "can I cancel this?" is a
> second copy of your state machine that will drift from the real one and offer the user a button
> that fails.**
>
> Today: ⭐ the machine on screen, ⭐⭐ actions from the server, the in-between states, and the
> confirmation that is worth the friction.

```

⭐   ⭐ THE SCREEN'S JOB IS TO ANSWER THREE QUESTIONS AT A GLANCE:

⭐                            the user's language — not "PENDING_2"
⭐   ② ⭐⭐ HOW DID I GET HERE? ⇒ a timeline / history. ⭐ THE MOST
```

|---|---|

| **The timeline** | ⭐⭐ You kept history — so you can answer *"what happened to order 4471?"* |

# Part 2 — ⭐⭐ Actions come from the server

```jsx
// ❌ THE CLIENT REIMPLEMENTING THE MACHINE
{order.status === "paid" && !order.refundedAt && user.role === "admin"
  && daysSince(order.paidAt) < 30 && <RefundButton />}
// ⭐⭐ FOUR RULES, DUPLICATED, IN JSX. ⭐ The server changes the
//    window to 14 days and this button lies until someone redeploys.

// ✅ THE SERVER DECIDES, THE CLIENT RENDERS
{order.actions.map(a => (
  <ActionButton key={a.name} action={a} disabled={!a.available}
                title={a.reason} />          // ⭐⭐ THE REASON, SHOWN
))}
```

```python
# ⭐ FastAPI — computed by the same code that ENFORCES it (Day 236)
class Action(BaseModel):
    name: str                # "refund"
    label: str               # "Refund order"
    available: bool
    reason: str | None       # ⭐⭐ "Already refunded on 3 March 2026"
    destructive: bool = False

def actions_for(order: Order, actor: User) -> list[Action]:
    can, why = can_refund(order, actor)      # ⭐⭐ THE ENFORCEMENT FUNCTION
    return [Action(name="refund", label="Refund order",
                   available=can, reason=why, destructive=True), ...]
```

> ⭐⭐ **`can_refund` is called by the serialiser *and* by the endpoint.** One function, two callers.
> That is what makes drift impossible rather than unlikely — and it is Day 236's argument applied to
> transitions rather than fields.
>
> ⭐ **Send disabled actions with reasons rather than omitting them.** A missing button leaves the
> user wondering; a disabled button that says why is an *explanation*. It also stops support tickets.

# Part 3 — ⭐⭐ The in-between states

```
⭐⭐ EVERY TRANSITION HAS A MIDDLE, AND THE MIDDLE IS WHERE UIs LIE.

⭐   idle → ⭐ SUBMITTING → ⭐⭐ SERVER PROCESSING → done
⭐                          ⭐ (async! webhook! queue!)

⭐   ⭐⭐ IF YOUR REFUND IS QUEUED, THE SERVER RETURNS 202 AND THE
⭐     ORDER IS **NOT** REFUNDED YET.
⭐   ❌ showing "Refunded ✅" on a 202 is ⭐⭐ THE UI LYING ABOUT
⭐      SOMETHING IRREVERSIBLE.
⭐   ✅ ⭐ "Refund requested — processing" + poll or subscribe
⭐      (Day 277) until the state actually changes.

⭐   ⇒ ⭐⭐ YOUR ASYNC BACKEND (Stage 7) MEANS THE UI NEEDS A
⭐     "PENDING" VOCABULARY. A synchronous-looking UI over an
⭐     asynchronous system is a bug waiting to be reported.
```

| ⭐ Server says | ⭐ UI must show |
|---|---|
| `200` + new state | The new state |
| ⭐⭐ `202 Accepted` | **"Processing…"**, and keep watching |
| `409 Conflict` | ⭐⭐ *"Someone else changed this — refresh to see the current state"* |
| `422` | The rule that was violated, in the user's words |
| Timeout / no response | ⭐⭐ **"We're not sure this completed"** + a way to check. **Never assume success or failure.** |

> ⭐⭐ **That last row is Day 484's payments lesson.** Some outcomes are genuinely unknown, and the
> honest UI says so rather than guessing. **Most candidates' UIs assume success on timeout, which is
> the worst of the three options.**

# Part 4 — Confirmation, and when it is worth the friction

```
⭐⭐ CONFIRM ONLY WHEN THE ACTION IS **IRREVERSIBLE** OR **WIDE**.
⭐   ⭐ Confirming everything trains the user to click through
⭐     dialogs without reading, which makes the ONE that mattered
⭐     useless. ⭐⭐ CONFIRMATION FATIGUE IS A REAL SAFETY LOSS.

⭐   ✅ CONFIRM: delete · refund · send to N people · publish
⭐   ❌ DON'T:   save · edit · filter · anything undoable

⭐   ⭐⭐ AND MAKE THE DIALOG SAY WHAT WILL HAPPEN, SPECIFICALLY:
⭐     ❌ "Are you sure?"
⭐     ✅ "Refund £240.00 to Ada Lovelace? This cannot be undone."
⭐        ⭐ The amount and the name are what stop the wrong click.

⭐   ⭐ BETTER THAN CONFIRMATION WHERE POSSIBLE: **UNDO**.
⭐     ⇒ act immediately, show "Deleted — Undo" for 8 seconds.
⭐       ⭐⭐ FASTER FOR THE 99% AND SAFER FOR THE 1%.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "walk me through your main screen."**

Frame it as a state machine, which immediately raises the level. **The screen answers three questions:
where this order is, how it got here, and what can be done next. Most project UIs answer only the
first, which makes them a database row with CSS. The timeline is the one interviewers ask about,
because it means I kept history and can answer what happened to a specific order.**

Then the design decision that matters. **The client never computes which actions are legal. The server
sends a list of actions, each with an availability flag and a reason, computed by the same function
that enforces the rule on the endpoint. One function, two callers — so drift is impossible rather than
unlikely. If I'd written four conditions in JSX, changing the refund window on the server would leave
the button lying until someone redeployed the frontend.**

Add the detail that reads as production software. **I send disabled actions with their reason rather
than hiding them, so the user sees "cannot refund: already refunded on 3 March" instead of wondering
where the button went. That detail alone stops support tickets.**

Close on the async honesty. **My backend queues some of this, so the server returns 202 and the refund
hasn't happened yet. Showing "Refunded" on a 202 is the UI lying about something irreversible, so the
UI has a pending vocabulary and keeps watching until the state actually changes. And on a timeout it
says we're not sure this completed and offers a way to check — assuming success on a timeout is the
worst of the three options, and it's what most UIs do.**
