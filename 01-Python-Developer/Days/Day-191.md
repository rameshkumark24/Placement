# Day 191 ⭐

**L-191** · 🐘 **`EXPLAIN ANALYZE`** — ⭐⭐ reading a plan like a diagnosis, not a wall of text

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: you are not looking for the slow node. You are looking for the deepest
> node where the *estimated* row count and the *actual* row count disagree — because everything above
> it is a consequence of that lie, and fixing anything above it is treating a symptom.**
>
> ⭐ Most people read a plan by scanning for the biggest number. ⭐⭐ That finds where the time went,
> which you already knew. **The estimate/actual gap tells you *why*, and why is what you can fix.**

---

# Part 1 — ⭐ The commands, and the one that will delete your data

```sql
EXPLAIN SELECT ...;
-- ⭐ Plan only. Nothing runs. Estimates only. ⭐ Safe, and half-useless.

EXPLAIN ANALYZE SELECT ...;
-- ⭐⭐ ***THIS ACTUALLY EXECUTES THE QUERY.***
-- ⭐⭐ SO `EXPLAIN ANALYZE DELETE FROM orders` ***DELETES YOUR ORDERS.***
BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;   -- ✅ ⭐ the only safe way

-- ⭐⭐ THE FORM YOU SHOULD ACTUALLY TYPE, EVERY TIME:
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, FORMAT TEXT) SELECT ...;
--        ⭐ real      ⭐ IO      ⭐ cols   ⭐ non-default GUCs
-- ⭐ BUFFERS   → Day 186's shared hit/read. Without it a timing is a
--               rumour.
-- ⭐ SETTINGS  → prints non-default planner settings. ⭐⭐ Catches the
--               "someone left enable_nestloop=off in the session" case.
-- ⭐ WAL       → for DML, how much WAL the statement generated.
-- ⭐ FORMAT JSON → for tooling (pev2, explain.dalibo.com).
```

```
⭐⭐ AND THE THREE WAYS THE MEASUREMENT LIES TO YOU:
⭐ ① ⭐⭐ IT IS ONE RUN, ON WHATEVER THE CACHE STATE HAPPENS TO BE. Run
⭐    it three times. Report which run you are quoting.
⭐ ② ⭐⭐ `ANALYZE` ADDS TIMING OVERHEAD — per-node `gettimeofday()` calls.
⭐    On a plan with millions of loops the reported total can exceed the
⭐    real query time noticeably. ⭐ `EXPLAIN (ANALYZE, TIMING OFF)`
⭐    removes it if you only need row counts.
⭐ ③ ⭐⭐ IT PLANS FOR *THESE* PARAMETERS. A different `tenant_id` can get
⭐    a completely different plan. ⭐ Test with your WORST tenant, not a
⭐    convenient one.
```

# Part 2 — ⭐⭐ Reading the tree: five numbers, and the one everyone misreads

```
⭐ A PLAN IS A TREE. ⭐⭐ READ IT INSIDE-OUT: the most-indented nodes run
⭐   FIRST and feed their parents. The top line is the LAST thing to
⭐   happen, not the first.

Limit  (cost=1245.10..1245.15 rows=20 width=88)
        (actual time=812.443..812.449 rows=20 loops=1)
  ->  Sort  (cost=1245.10..1289.32 rows=17688 width=88)
            (actual time=812.441..812.444 rows=20 loops=1)
        Sort Key: o.created_at DESC
        ⭐⭐ Sort Method: external merge  Disk: 84720kB
        ->  Hash Join  (cost=88.50..775.20 rows=17688 width=88)
                       (actual time=1.204..640.112 rows=1284003 loops=1)
              Hash Cond: (o.user_id = u.id)
              ->  Seq Scan on orders o  (cost=0..500 rows=17688 width=64)
                    (actual time=0.011..210.4 rows=1284003 loops=1)
                    Filter: (status = 'paid')
                    ⭐⭐ Rows Removed by Filter: 3716000
                    Buffers: shared hit=12 read=41207
              ->  Hash  (cost=60..60 rows=2280 width=24) ...
```

```
⭐⭐ THE FIVE NUMBERS ON EVERY NODE:

⭐ ① cost=START..TOTAL   — ⭐ ARBITRARY UNITS. Not milliseconds, not
⭐      anything. Only comparable BETWEEN PLANS OF THE SAME QUERY.
⭐      ⭐⭐ START cost = work before the FIRST row (a Sort must consume
⭐      everything ⇒ high start cost; a Seq Scan can emit immediately).
⭐      ⇒ ⭐ THIS IS WHY `LIMIT` CHANGES PLANS SO DRAMATICALLY: with a
⭐        LIMIT, start cost dominates.
⭐ ② rows=N (in `cost=`)  — ⭐⭐ THE ESTIMATE.
⭐ ③ actual time=FIRST..LAST — ⭐ ms to first row .. ms to last row.
⭐ ④ rows=N (in `actual`) — ⭐⭐ THE TRUTH.
⭐ ⑤ ⭐⭐ loops=N          — THE NUMBER EVERY BEGINNER MISREADS.

⭐⭐ ***`actual time` AND `actual rows` ARE PER LOOP AVERAGES.***
⭐   -> Index Scan on order_items
⭐        (actual time=0.021..0.028 rows=3 loops=248000)
⭐   ⭐ Looks like 0.028 ms. ⭐⭐ IT IS 0.028 × 248,000 = ***7 SECONDS***,
⭐     AND IT RETURNED 744,000 ROWS, NOT 3.
⭐   ⇒ ⭐⭐ ALWAYS MULTIPLY BY `loops`. This single misreading is why
⭐     people stare at a plan for ten minutes and conclude "nothing is
⭐     slow". ⭐ (`FORMAT JSON` and pev2 do the multiplication for you.)
```

# Part 3 — ⭐⭐ The diagnosis: estimate vs actual

```
⭐⭐ THE PROCEDURE. Six steps, in order, every time.

⭐ 1. ⭐⭐ SCAN EVERY NODE FOR `rows=ESTIMATE` vs `rows=ACTUAL`.
⭐      Ratio under ~10× ⇒ ignore. ⭐⭐ Over 100× ⇒ THIS IS THE BUG.
⭐ 2. ⭐⭐ GO TO THE ***DEEPEST*** NODE WITH A BAD RATIO. Bad estimates
⭐      PROPAGATE UPWARD: one wrong scan estimate makes every join above
⭐      it choose the wrong algorithm. ⭐ Fixing the top node fixes
⭐      nothing.
⭐ 3. ASK WHY THE ESTIMATE IS WRONG — ⭐ there are only five answers:
⭐      ⭐ stale stats (Day 189 ⑥) → ANALYZE
⭐      ⭐ correlated columns → CREATE STATISTICS
⭐      ⭐ a function in the predicate the planner cannot estimate →
⭐        ⭐⭐ Postgres assumes a FIXED selectivity for an opaque
⭐        function. Wrap it, or add an expression index (which gets its
⭐        OWN statistics — a genuinely underused trick).
⭐      ⭐ skewed data + too-small sample → SET STATISTICS 1000
⭐      ⭐ a join of two subqueries whose own estimates were wrong
⭐ 4. ⭐ THEN look at `Rows Removed by Filter`. Large ⇒ the index is
⭐      missing or has the wrong column order (Day 190).
⭐ 5. ⭐ THEN look at Buffers: `read` ≫ `hit` ⇒ IO-bound, not CPU-bound.
⭐ 6. ⭐ ONLY THEN consider rewriting the query.
```

```
⭐⭐ WHY STEP 2 MATTERS — the classic cascade, in three lines:
⭐   Seq Scan estimates 40 rows, actually returns 190,000
⭐     ⇒ planner picks a NESTED LOOP ("only 40 iterations, cheap!")
⭐       ⇒ ⭐⭐ THE INNER SIDE RUNS 190,000 TIMES. 40 ms becomes 9 minutes.
⭐   ⭐ The nested loop is NOT the bug. It was a REASONABLE choice given a
⭐     lie. ⭐⭐ FIX THE LIE AND THE JOIN FIXES ITSELF.
```

# Part 4 — ⭐ The node catalogue, with what each one is telling you

```
⭐⭐ SCANS
⭐ Seq Scan          ⭐ fine on small/most-of-table. ⭐⭐ Check `Rows
⭐                     Removed by Filter` — that is the wasted work.
⭐ Index Scan        ⭐ good for few rows. ⭐⭐ Bad for many (random IO).
⭐ Index Only Scan   ⭐ best. ⭐⭐ CHECK `Heap Fetches:` — non-zero means
⭐                     the visibility map is stale ⇒ VACUUM (Day 194).
⭐ Bitmap Heap Scan  ⭐ the middle ground. ⭐⭐ `Recheck Cond` + a big
⭐                     `lossy` count ⇒ work_mem too small; it degraded
⭐                     from row precision to PAGE precision.

⭐⭐ JOINS — full treatment tomorrow, recognition today
⭐ Nested Loop  ⭐ correct for a SMALL outer side. ⭐⭐ `loops=248000` on
⭐                the inner side is the SQL-level N+1.
⭐ Hash Join    ⭐ the workhorse for big ⋈ big equality.
⭐              ⭐⭐ `Batches: 8` (not 1) means the hash SPILLED TO DISK.
⭐ Merge Join   ⭐ both inputs already sorted (usually via indexes).

⭐⭐ THE ONES THAT REVEAL MEMORY PRESSURE
⭐ Sort  ⭐⭐ `Sort Method: quicksort  Memory: 25kB`      ✅ in memory
⭐       ⭐⭐ `Sort Method: external merge  Disk: 84720kB` ❌ SPILLED
⭐          ⇒ raise `work_mem` FOR THAT QUERY (`SET LOCAL work_mem`),
⭐            ⭐⭐ NOT GLOBALLY — work_mem is PER SORT, PER NODE, PER
⭐            CONNECTION. 100 connections × 3 sorts × 256 MB is 75 GB.
⭐          ⇒ ⭐ or delete the sort entirely with an index (Day 190).
⭐ HashAggregate  ⭐ fast. ⭐⭐ `Disk Usage:` present ⇒ spilled (PG 13+).
⭐ GroupAggregate ⭐ needs sorted input; often means a sort happened.

⭐⭐ THE ONES THAT CONFUSE PEOPLE
⭐ Materialize  ⭐ "I cached this inner result because I'll rescan it."
⭐ Memoize      ⭐⭐ PG 14+. A CACHE INSIDE A NESTED LOOP. Seeing it with
⭐                a high hit ratio means the nested loop is fine.
⭐ Gather / Gather Merge + `Workers Launched: 4`
⭐              ⭐⭐ PARALLEL QUERY. `Workers Planned: 4, Launched: 0`
⭐                MEANS YOU HIT `max_parallel_workers` AND GOT NONE —
⭐                a silent 4× slowdown with no other symptom.
⭐ CTE Scan     ⭐⭐ Before PG 12 a `WITH` was an OPTIMISATION FENCE —
⭐                always materialised, no predicate pushdown. PG 12+
⭐                inlines it unless you write `MATERIALIZED`.
⭐                ⇒ ⭐⭐ `AS MATERIALIZED` is now how you FORCE the fence
⭐                  on purpose — occasionally exactly what you want.
⭐ SubPlan      ⭐⭐ A correlated subquery. If it shows `loops=N` with big
⭐                N, that is a per-row query — rewrite as a join or a
⭐                lateral.
⭐ InitPlan     ⭐ an uncorrelated subquery, evaluated once. Harmless.
```

# Part 5 — ⭐ Buffers, and where the time actually went

```
⭐   Buffers: shared hit=12 read=41207 dirtied=3 written=0
⭐            temp read=10604 written=10604
⭐
⭐ ⭐ shared hit    — found in shared_buffers. Free.
⭐ ⭐ shared read   — NOT in shared_buffers (may be OS cache or disk).
⭐                   ⭐⭐ 41,207 × 8 KB = 322 MB READ TO RETURN 20 ROWS.
⭐ ⭐ dirtied       — pages this query modified (yes, SELECTs can dirty
⭐                   pages — hint bits. Day 194).
⭐ ⭐⭐ temp read/written — ***THIS IS A SPILL TO DISK.*** A sort or hash
⭐                   exceeded `work_mem`. ⭐ Non-zero temp on a hot query
⭐                   is one of the highest-value findings in a plan.
⭐
⭐⭐ THE HABIT WORTH BUILDING: convert buffers to megabytes out loud.
⭐   "It read 322 megabytes to return twenty rows" is a sentence that
⭐   ends an argument. "It took 812 ms" starts one.
```

```sql
-- ⭐⭐ CAPTURING PLANS FROM PRODUCTION, WHERE YOU CANNOT SIT AND RETYPE:
-- postgresql.conf / ALTER SYSTEM:
--   shared_preload_libraries = 'auto_explain'
--   auto_explain.log_min_duration = '500ms'   ⭐ log plans of slow ones
--   auto_explain.log_analyze = on             ⭐⭐ REAL overhead — start
--   auto_explain.log_buffers = on                with sampling:
--   auto_explain.sample_rate = 0.01           ⭐ 1% of statements
--   auto_explain.log_nested_statements = on   ⭐ inside functions too
-- ⭐⭐ THIS IS HOW YOU GET THE PLAN FOR THE 3 A.M. SLOW QUERY THAT YOU
--    CANNOT REPRODUCE — because it planned differently for THOSE
--    parameters, on THAT cache state.
```

# Part 6 — ⭐⭐ Six plans and their one-line diagnoses

```
⭐ ① `Seq Scan … Rows Removed by Filter: 4,900,000` returning 200 rows
⭐    ⇒ ⭐⭐ MISSING INDEX. Textbook. Apply E-S-R (Day 190).
⭐
⭐ ② `Index Scan … rows=3 loops=248000` under a Nested Loop
⭐    ⇒ ⭐⭐ THE SQL-LEVEL N+1. Estimate on the outer side was wrong, or
⭐      you genuinely need a hash join. Check the outer node first.
⭐
⭐ ③ `Sort Method: external merge Disk: 84720kB`
⭐    ⇒ ⭐⭐ `SET LOCAL work_mem='128MB'` for this query — or delete the
⭐      sort with an index. ⭐ Prefer deleting it.
⭐
⭐ ④ `Index Only Scan … Heap Fetches: 1,284,003`
⭐    ⇒ ⭐⭐ The visibility map is stale. `VACUUM` the table; check
⭐      autovacuum settings for it (Day 194).
⭐
⭐ ⑤ `Bitmap Heap Scan … Recheck Cond … lossy=41000`
⭐    ⇒ ⭐⭐ The bitmap outgrew `work_mem` and fell back to page
⭐      granularity, so it re-checks every row on those pages.
⭐
⭐ ⑥ `Seq Scan … Filter: (data ->> 'status' = 'x')` estimate 1 actual 91k
⭐    ⇒ ⭐⭐ The planner has NO statistics for a JSONB expression and
⭐      guesses a fixed selectivity. ⭐ An EXPRESSION INDEX on
⭐      `(data ->> 'status')` gives it real statistics AND an index —
⭐      two problems, one DDL.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Running `EXPLAIN ANALYZE` on a `DELETE`/`UPDATE` | It executes. Wrap in `BEGIN … ROLLBACK`. |
| Omitting `BUFFERS` | Without IO counts a timing is a rumour. |
| Reading `actual time` on a node with many loops | Both time and rows are per-loop averages. Multiply. |
| Hunting for the slowest node | Hunt for the deepest node with a bad estimate/actual ratio. |
| Fixing the join algorithm | The join is a consequence of a bad row estimate. Fix the estimate. |
| Comparing `cost` between different queries | Arbitrary units, comparable only between plans of the same query. |
| Ignoring `Rows Removed by Filter` | That number is the wasted work, and it names the missing index. |
| Raising `work_mem` globally to stop spills | It's per sort, per node, per connection. Use `SET LOCAL`. |
| Treating `Materialize`/`Memoize` as problems | They're usually the planner helping. Memoize with a high hit rate means the nested loop is fine. |
| Assuming a `WITH` is an optimisation fence | PG 12+ inlines it. Use `AS MATERIALIZED` when you *want* the fence. |
| Ignoring `Workers Launched: 0` | You hit `max_parallel_workers` — a silent multiple-times slowdown. |
| Testing with a convenient parameter | Plans are parameter-specific. Use the worst tenant. |
| Quoting a single run | Run it three times and say which cache state you're quoting. |
| Enabling `auto_explain.log_analyze` at 100% | Real overhead. Sample at 1% first. |

## Interview questions

**Q: Walk me through how you read a query plan.**

> First I make sure I'm reading a useful one — `EXPLAIN (ANALYZE, BUFFERS)`, three runs, and I say
> which cache state I'm quoting. Then I read the tree inside-out, because the most indented nodes run
> first. But the thing I'm actually scanning for isn't time, it's the ratio between estimated rows and
> actual rows on every node. If that's within an order of magnitude everywhere, the planner had good
> information and any slowness is real work. If it's off by a hundred times somewhere, I go to the
> *deepest* node where it's wrong, because bad estimates propagate upward — one wrong scan estimate
> makes every join above it pick the wrong algorithm, and fixing the join is treating a symptom. Then
> I check `Rows Removed by Filter` for missing indexes, and the buffer counts to know whether I'm
> IO-bound or CPU-bound. The habit I'd want on a team is converting buffers to megabytes out loud —
> "it read three hundred megabytes to return twenty rows" ends an argument in a way that "it took 812
> milliseconds" doesn't.

**Q: What's the most commonly misread number in a plan?**

> `loops`. Both `actual time` and `actual rows` are per-loop averages, so an index scan showing
> `actual time=0.028 rows=3 loops=248000` looks trivially fast and is actually seven seconds returning
> three quarters of a million rows. That single misreading is why people stare at a plan and conclude
> nothing is slow. It's also the SQL-level version of the N+1 — a nested loop whose inner side runs
> once per outer row — and the fix is usually upstream: the outer side's estimate was wrong, so the
> planner thought forty iterations, not two hundred and forty thousand. The JSON format and tools like
> pev2 do the multiplication for you, which is a good way to learn it, but I'd still want to be able
> to do it from text.

**Q: You see `Sort Method: external merge Disk: 84 MB`. What do you do?**

> That's a spill — the sort exceeded `work_mem` and went to temporary files, which also shows up as
> `temp read/written` in the buffers line. There are two fixes and I'd prefer the second. The first is
> `SET LOCAL work_mem` for that statement — deliberately local, because `work_mem` is allocated per
> sort node, per connection, so a hundred connections running a three-sort query at 256 megabytes is
> seventy-five gigabytes of potential allocation, and raising it globally is how people OOM a database
> while trying to speed it up. The second and better fix is to remove the sort entirely with an index
> in the right order, since a B-tree's leaves are already sorted — that's the E-S-R point from
> yesterday. If the sort is genuinely unavoidable, for example a big report aggregation, then a local
> `work_mem` bump for that one job is the right call.

**Q: The query is slow only in production and you can't reproduce it. How do you get the plan?**

> `auto_explain`, preloaded, with `log_min_duration` set to something like five hundred milliseconds
> so only slow executions log, `log_analyze` and `log_buffers` on, and a sample rate well below one to
> start with, because analyze-level instrumentation has real overhead. That gets you the plan for the
> actual slow execution — which matters, because plans are parameter-specific and cache-state-specific,
> so the reason you can't reproduce it is usually that your test parameter has different selectivity
> from the one that was slow at three in the morning. `log_nested_statements` if the query is inside a
> function. Alongside that I'd look at `pg_stat_statements` for the same normalised query to see
> whether it's always slow or occasionally slow, because those have different causes — a bad plan
> versus lock waits or a cold cache.

**Q: `EXPLAIN` says one thing, `EXPLAIN ANALYZE` says another. Which do you trust?**

> They're answering different questions. Plain `EXPLAIN` shows what the planner *believes* — estimates
> only, nothing executed. `ANALYZE` runs the query and adds what actually happened. The gap between
> them is the diagnosis, so I want both in the same output, which is what `EXPLAIN ANALYZE` gives you.
> The caveats are that `ANALYZE` executes the statement — so on a `DELETE` you wrap it in a
> transaction and roll back, and people have genuinely deleted production data by forgetting that —
> and that the per-node timing instrumentation itself costs something, so on a plan with millions of
> loops the reported total can exceed the real query time. `TIMING OFF` removes that if I only need
> row counts.

## Mini task

1. ⭐ Run `EXPLAIN (ANALYZE, BUFFERS)` on your capstone's slowest endpoint query. Convert buffers to MB and write one sentence.
2. ⭐⭐ Deliberately construct a plan with `loops` over 100,000. Compute the true total time by hand, then confirm with `FORMAT JSON`.
3. ⭐⭐ Find a query where estimate and actual differ by >100×. Fix the estimate with `ANALYZE` or `CREATE STATISTICS` and watch the join algorithm change on its own.
4. ⭐ Force a sort spill by lowering `work_mem` to `64kB`. Read `Sort Method` and the `temp` buffers. Then fix it with an index instead.
5. ⭐⭐ Produce a `Heap Fetches` non-zero index-only scan, then `VACUUM` and re-run.
6. ⭐ Produce a lossy bitmap heap scan by shrinking `work_mem`. Find the `lossy=` count.
7. ⭐⭐ Write a correlated subquery that appears as a `SubPlan` with large loops. Rewrite as a join and compare.

## 🎙️ Articulation drill

**Two minutes: "A query is slow. Talk me through it."**

Resist naming a fix. Start with the measurement — `EXPLAIN (ANALYZE, BUFFERS)`, three runs, and state
the cache state — then say what you're actually looking for, because that's the differentiator:
**not the slowest node, the deepest node where estimate and actual disagree**, since bad estimates
propagate upward and the wrong join algorithm is a consequence, not a cause. Give the cascade in one
line: the scan estimated forty rows and returned a hundred and ninety thousand, so the planner picked
a nested loop and the inner side ran a hundred and ninety thousand times. Then mention `loops` as the
number everyone misreads, with the arithmetic. Then `Rows Removed by Filter` for a missing index and
`temp` buffers for a spill. Close on the discipline point: **convert buffers to megabytes and say the
sentence out loud** — "three hundred megabytes read to return twenty rows" — because that's a fact,
and "it takes 812 milliseconds" is an opinion about a cache.
