# Day 104

**L-104** · **Parsing an HTTP request from bytes** — framing, headers, chunked encoding, and ⭐⭐ the limits that stop a parser being a vulnerability

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a parser is the one part of your system that runs on attacker-controlled
> input before any authentication happens — so every limit it does not enforce is a denial of service
> available to anyone who can open a socket.**
>
> ⭐ Today you turn the raw bytes from Day 103 into a `Request` object. **The parsing is
> straightforward; the limits and the ambiguities are the lesson.**

---

# Part 1 — ⭐ The wire format

```
POST /orders?draft=true HTTP/1.1\r\n          ⭐ REQUEST LINE: method, target, version
Host: api.example.com\r\n                     ⭐ headers, one per line, "Name: value"
Content-Type: application/json\r\n
Content-Length: 27\r\n
\r\n                                          ⭐⭐ THE BLANK LINE — headers end here
{"item": "book", "qty": 2}                    ⭐ body: EXACTLY Content-Length bytes
```

```
⭐⭐ THREE FACTS THAT DECIDE THE PARSER'S SHAPE:
⭐  1. ⭐⭐ LINES END WITH \r\n (CRLF), NOT \n. ⭐ Be strict about what you SEND
⭐       and tolerant about what you accept — but ⭐⭐ log the tolerance, because
⭐       a client sending bare \n is usually a hand-rolled client with other bugs.
⭐  2. ⭐⭐ b"\r\n\r\n" ENDS THE HEADERS. That is the delimiter framing from
⭐       Day 103, and it is the only thing you can scan for before you know
⭐       anything else about the request.
⭐  3. ⭐⭐ THE BODY IS LENGTH-FRAMED. You must read EXACTLY Content-Length more
⭐       bytes — no more (they belong to the NEXT request on a keep-alive
⭐       connection) and no fewer (you will block, or truncate).
```

# Part 2 — ⭐⭐ Reading, in the only correct order

```python
from dataclasses import dataclass, field

MAX_LINE       = 8 * 1024        # ⭐ request line + any single header
MAX_HEADERS    = 100             # ⭐⭐ header COUNT (see Part 4)
MAX_HEAD_BYTES = 64 * 1024       # ⭐ all headers together
MAX_BODY       = 10 * 1024 * 1024

@dataclass
class Request:
    method: str
    path: str
    query: dict[str, list[str]]
    headers: "Headers"
    body: bytes = b""

def read_request(conn, buf: bytes) -> tuple[Request, bytes]:
    # ⭐⭐ 1. READ UNTIL THE BLANK LINE — carrying the leftover buffer between
    #        requests, because a keep-alive connection may have given us part
    #        of the NEXT request already.
    while b"\r\n\r\n" not in buf:
        chunk = conn.recv(4096)
        if not chunk:
            raise ConnectionError("closed before end of headers")
        buf += chunk
        if len(buf) > MAX_HEAD_BYTES:
            raise HTTPError(431, "headers too large")      # ⭐ 431, a real status

    head, buf = buf.split(b"\r\n\r\n", 1)                  # ⭐⭐ buf keeps the remainder

    # ⭐ 2. PARSE THE HEAD (Part 3)
    request_line, *header_lines = head.split(b"\r\n")
    if len(header_lines) > MAX_HEADERS:
        raise HTTPError(431, "too many headers")
    method, target, version = request_line.decode("latin-1").split(" ", 2)   # ⭐ Day 103
    headers = parse_headers(header_lines)

    # ⭐⭐ 3. READ EXACTLY THE BODY — never more, never less
    length = int(headers.get("content-length", 0))
    if length > MAX_BODY:
        raise HTTPError(413, "payload too large")          # ⭐⭐ BEFORE reading it
    while len(buf) < length:
        chunk = conn.recv(min(4096, length - len(buf)))
        if not chunk:
            raise ConnectionError("closed mid-body")
        buf += chunk
    body, buf = buf[:length], buf[length:]                 # ⭐⭐ THE SPLIT THAT MATTERS

    path, _, qs = target.partition("?")
    return Request(method, unquote(path), parse_qs(qs), headers, body), buf
```

```
⭐⭐ THE TWO LINES THAT SEPARATE A WORKING PARSER FROM A BROKEN ONE:
⭐   `head, buf = buf.split(b"\r\n\r\n", 1)`   and
⭐   `body, buf = buf[:length], buf[length:]`
⭐   ⇒ ⭐⭐ BOTH RETURN THE LEFTOVER. On a keep-alive connection (Day 105) the
⭐        client may pipeline — sending request 2 before reading response 1 —
⭐        ⭐⭐ so bytes belonging to the next request are ALREADY IN YOUR BUFFER.
⭐        ⭐ Discard them and request 2 is corrupt or lost, intermittently,
⭐        under load only. ⭐⭐ Carry the buffer.
⭐
⭐ ⭐⭐ AND NOTE `raise HTTPError(413)` BEFORE READING THE BODY, not after. ⭐ A
⭐   parser that reads 4 GB into memory and then rejects it has already lost.
```

# Part 3 — ⭐ Headers, and their four rules

```python
class Headers:
    """⭐⭐ Case-insensitive, multi-valued, order-preserving."""
    def __init__(self, pairs: list[tuple[str, str]]):
        self._pairs = pairs
        self._map: dict[str, list[str]] = {}
        for k, v in pairs:
            self._map.setdefault(k.lower(), []).append(v)     # ⭐⭐ lower() is the key

    def get(self, name, default=None):
        vals = self._map.get(name.lower())
        return vals[0] if vals else default

    def get_all(self, name) -> list[str]:
        return self._map.get(name.lower(), [])
```

```
⭐⭐ THE FOUR RULES, EACH OF WHICH IS A BUG IF YOU MISS IT:
⭐  1. ⭐⭐ NAMES ARE CASE-INSENSITIVE. `content-type`, `Content-Type` and
⭐       `CONTENT-TYPE` are the same header. ⭐ Store lowercased; a plain dict
⭐       keyed on the raw name will miss a client that capitalises differently.
⭐  2. ⭐⭐ A HEADER MAY APPEAR MORE THAN ONCE. Formally that is equivalent to one
⭐       header with comma-joined values — ⭐⭐ EXCEPT `Set-Cookie`, which may NOT
⭐       be joined (its value contains commas in the Expires date). ⭐ So the
⭐       storage must be multi-valued, not a dict of strings.
⭐  3. ⭐ WHITESPACE around the value is stripped; ⭐⭐ whitespace BEFORE the colon
⭐       is ILLEGAL and must be rejected, not trimmed (it is a smuggling vector).
⭐  4. ⭐ VALUES ARE LATIN-1 ON THE WIRE (Day 037). Non-ASCII in a header needs
⭐       encoding (RFC 5987) — ⭐⭐ which is why a filename with an accent in
⭐       `Content-Disposition` is a recurring bug.
```

```python
from urllib.parse import parse_qs, unquote

parse_qs("a=1&a=2&b=hello+world")   # ⭐ {"a": ["1","2"], "b": ["hello world"]}
```

```
⭐⭐ QUERY STRING TRAPS, ALL THREE REAL:
⭐   · ⭐ EVERY VALUE IS A LIST — `?a=1&a=2` is legal, and a client can send it
⭐        deliberately. ⭐⭐ Code that does `params["a"]` expecting a string
⭐        breaks; code that takes the FIRST value where the framework takes the
⭐        LAST is a parameter-pollution bug that can bypass a filter.
⭐   · ⭐⭐ `+` MEANS SPACE IN A QUERY STRING BUT NOT IN A PATH. `parse_qs`
⭐        handles it; `unquote` does NOT. ⭐ Using the wrong one turns
⭐        "a+b@x.com" into a broken address.
⭐   · ⭐ EVERYTHING IS A STRING. `?limit=10` is `"10"`. ⭐⭐ Validate and coerce
⭐        at the boundary (Day 119), never deep inside.
```

# Part 4 — ⭐⭐ Chunked encoding, and the ambiguity that is a vulnerability

```
⭐ WHEN THE SENDER DOES NOT KNOW THE LENGTH IN ADVANCE (a stream, a generated
⭐ export), it uses `Transfer-Encoding: chunked`:
⭐
⭐   1b\r\n                    ⭐ chunk size in HEX
⭐   {"item": "book", "qty":2}\r\n
⭐   0\r\n                     ⭐⭐ a ZERO-LENGTH chunk ends the body
⭐   \r\n                      ⭐ optional trailers, then blank
```

```python
def read_chunked(conn, buf, max_total=MAX_BODY):
    out, total = b"", 0
    while True:
        line, buf = read_line(conn, buf)                   # ⭐ up to \r\n
        size = int(line.split(b";")[0], 16)                # ⭐ ignore chunk extensions
        if size == 0:
            break
        total += size
        if total > max_total:                              # ⭐⭐ LIMIT THE TOTAL, not the chunk
            raise HTTPError(413, "payload too large")
        while len(buf) < size + 2:                         # ⭐ +2 for the trailing \r\n
            buf += conn.recv(4096)
        out, buf = out + buf[:size], buf[size + 2:]
    return out, buf
```

```
⚠️⚠️ ⭐⭐ REQUEST SMUGGLING — WHY A PARSER MUST REJECT RATHER THAN GUESS:
⭐    IF A REQUEST HAS **BOTH** `Content-Length` AND `Transfer-Encoding: chunked`,
⭐    THE SPEC SAYS TE WINS. ⭐⭐ BUT IF YOUR SERVER AND THE PROXY IN FRONT OF IT
⭐    DISAGREE — one honours CL, the other TE — THEY DISAGREE ABOUT WHERE THE
⭐    REQUEST ENDS.
⭐    ⇒ ⭐⭐ SO THE ATTACKER'S TRAILING BYTES BECOME THE *START OF THE NEXT
⭐         USER'S REQUEST*. They can prepend headers to a stranger's request —
⭐         ⭐⭐ steal their session, or route them to an endpoint of their choosing.
⭐    ⇒ ⭐⭐ THE RULE: IF BOTH HEADERS ARE PRESENT, RETURN 400. If Content-Length
⭐         appears TWICE with different values, 400. ⭐⭐ AMBIGUITY IN A PARSER IS
⭐         NOT A COMPATIBILITY PROBLEM TO BE SMOOTHED OVER — IT IS AN ATTACK
⭐         SURFACE, AND REJECTING IS ALWAYS CORRECT.
```

| ⭐ Limit | ⭐ Stops |
|---|---|
| ⭐⭐ Header **count** | ⭐⭐ hash-collision DoS, and memory blow-up |
| ⭐ Total header bytes | ⭐ slow buffer growth |
| ⭐ Request-line length | ⭐ a 10 MB URL |
| ⭐⭐ Body size, **checked before reading** | ⭐⭐ OOM from one request |
| ⭐⭐ Read timeout (Day 103) | ⭐⭐ slowloris |
| Chunked **total**, not per chunk | ⭐ 1,000,000 small chunks |

⭐⭐ **Notice that every one of these is a resource limit, and every one is checkable before you have
authenticated anyone.** ⭐ That is the whole argument for putting them in the parser rather than in the
application.

# Part 5 — ⭐ Bodies you will actually receive

| ⭐ `Content-Type` | ⭐ Parse with |
|---|---|
| `application/json` | ⭐ `json.loads(body)` — ⭐⭐ wrap it: bad JSON is a **400**, not a 500 |
| `application/x-www-form-urlencoded` | ⭐ `parse_qs(body.decode())` |
| ⭐ `multipart/form-data` | ⭐⭐ the hard one — a boundary from the header, per-part headers. **Stream to disk, never into memory** |
| `text/plain` | ⭐ decode with the declared charset |
| anything else | ⭐ `415 Unsupported Media Type` |

```python
try:
    data = json.loads(request.body)
except json.JSONDecodeError as e:
    raise HTTPError(400, "invalid JSON") from e     # ⭐⭐ Day 059's `from`, and a 4xx
```

⚠️ ⭐⭐ **A parse failure on user input is a `400`, never a `500`** (Day 102) — a `500` here means your
error rate alarms on every client that sends a stray comma. ⚠️ ⭐ **And never put the parser's message
into the response body verbatim**: it can echo attacker content back (Day 127) and it leaks your
internals.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Discarding the leftover buffer** | ⭐⭐ The next pipelined request is already in it. Carry it. |
| Reading the body before checking its size | ⭐⭐ 4 GB into memory, then rejected. Check first. |
| ⭐ Case-sensitive header lookup | ⭐ Names are case-insensitive. Store lowercased. |
| A `dict[str, str]` for headers | ⭐ Headers repeat — and `Set-Cookie` must not be joined. |
| ⭐ Trimming space before the colon | ⭐⭐ Illegal. Reject — it is a smuggling vector. |
| ⭐⭐ **Accepting both `Content-Length` and `Transfer-Encoding`** | ⭐⭐ Request smuggling. Return 400. |
| `params["a"]` expecting a string | ⭐ Every query value is a list; `?a=1&a=2` is legal. |
| `unquote` on a query value | ⭐ It leaves `+` as `+`. Use `parse_qs`. |
| ⭐ No header count limit | ⭐⭐ Hash-collision DoS, pre-authentication. |
| Limiting chunk size but not the total | ⭐ A million small chunks. |
| ⭐ 500 on malformed JSON | ⭐⭐ 400. Otherwise your alerting fires on client typos. |
| Echoing the parse error into the response | ⭐ Leaks internals, and reflects attacker input. |
| Splitting on `\n` | ⭐ HTTP uses `\r\n`. |

## Interview questions

**Q: How do you know where an HTTP request ends?**
> In two stages, because HTTP uses two framing mechanisms. The headers are delimiter-framed: read
> until `\r\n\r\n`. Then the body is length-framed: read exactly `Content-Length` bytes — or, if
> `Transfer-Encoding: chunked`, read chunk by chunk until a zero-length chunk. The critical detail is
> that you keep the leftover bytes, because on a keep-alive connection a pipelining client may have
> already sent the start of the next request, and if you throw that away, request two is corrupted
> intermittently under load.

**Q: What is HTTP request smuggling?**
> It happens when a request carries both `Content-Length` and `Transfer-Encoding: chunked` and two
> servers in the chain disagree about which wins — say a proxy honours `Content-Length` and the
> backend honours `Transfer-Encoding`. They then disagree about where the request ends, so the
> attacker's trailing bytes get treated as the beginning of the *next* user's request. That lets them
> prepend headers to a stranger's request — steal a session, or redirect it. The defence in my own
> parser is simple: if both headers are present, return 400, and if `Content-Length` appears twice
> with different values, 400. Ambiguity in a parser isn't a compatibility problem to smooth over,
> it's an attack surface.

**Q: What limits does a request parser need, and why there?**
> Header count, total header bytes, request-line length, body size checked *before* reading, a read
> timeout, and for chunked bodies a limit on the total rather than per chunk. They belong in the
> parser because every one of them is checkable before any authentication has happened — the parser is
> the code that runs on attacker-controlled input first. Without a body limit, one request OOMs the
> process. Without a header count limit you get hash-collision denial of service. Without a timeout,
> slowloris. All of them are free to an attacker.

**Q: What's tricky about HTTP headers?**
> Three things. Names are case-insensitive, so a plain dict keyed on the raw name misses a client that
> capitalises differently. Headers can repeat — formally that's equivalent to comma-joining, except
> `Set-Cookie`, which mustn't be joined because its value contains commas — so the storage has to be
> multi-valued. And values are latin-1 on the wire, which is why a filename with an accent in
> `Content-Disposition` needs explicit encoding and is a recurring bug.

**Q: What should happen when the JSON body is malformed?**
> A 400, with a generic message. Not a 500 — that's the client's mistake, not mine, and 5xx is what
> alerting watches, so returning 500 for a stray comma means the error-rate alarm fires on client
> typos and the team learns to ignore it. And I wouldn't echo the parser's message into the response
> body, because it can reflect attacker-supplied content and it leaks internals.

## 🎙️ Articulation drill

Record two minutes: **"You're writing an HTTP parser. What are you worried about?"**

⭐ **Frame the position first, because it explains every decision after it:** **"the parser is the
first code that touches attacker-controlled bytes, and it runs before any authentication. So I'm less
worried about parsing correctly than about what happens on input designed to hurt me."**

⭐⭐ **Then the limits, as a list with consequences:** *"a body size limit checked *before* I read the
body, or one request OOMs the process. A header count limit, because thousands of headers is a
hash-collision denial of service. A cap on total header bytes and on the request line. A read timeout
on every connection, because a client that connects and sends nothing holds the socket forever — that's
slowloris, and it costs the attacker one laptop. And for chunked bodies, a limit on the total rather
than per chunk, or a million tiny chunks gets through."*

⭐⭐ **Then the ambiguity point, which is the one that reads as real experience:** *"and where the
spec is ambiguous, I reject rather than guess. If a request has both `Content-Length` and
`Transfer-Encoding`, I return 400 — because if my server and the proxy in front of me resolve that
differently, we disagree about where the request ends, and the attacker's trailing bytes become the
start of the next user's request. That's request smuggling, and it lets someone prepend headers to a
stranger's session. Ambiguity in a parser isn't a compatibility problem to smooth over."*

⭐ **Close on the mechanical detail people miss:** *"the other thing I'd get right is carrying the
leftover buffer between requests. On a keep-alive connection a client can pipeline, so bytes belonging
to the next request are already in my buffer — discard them and the second request is corrupted
intermittently, under load only, which is the worst kind of bug to chase."*
