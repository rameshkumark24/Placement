# Day 054

**L-054** · ⭐ **Inheritance and the MRO** — C3 linearisation, `super()` in multiple inheritance

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `super()` does not mean "my parent". It means "the next class in the
> MRO of `type(self)`" — which may be a class my class has never heard of.**
>
> ⭐ That distinction is the whole of multiple inheritance, and it is why cooperative `super()` works
> at all. **"What does `super()` do?" is a standard senior probe, and "calls the parent class" is the
> wrong answer.**

---

# Part 1 — ⭐⭐ The MRO

```python
class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass          # ⭐ the diamond

D.__mro__
# ⭐⭐ (D, B, C, A, object)
```

```
⭐⭐ THE MRO IS A LINEAR ORDER over the whole hierarchy. Attribute lookup walks it once,
⭐   left to right, and takes the FIRST match (Day 032, step 1).
⭐
⭐ ⭐⭐ NOTE what the diamond does: D ⇒ B ⇒ C ⇒ A.
⭐   ⇒ ⭐⭐ A comes AFTER C, even though B inherits directly from A.
⭐        ⇒ because A must not be visited before every class that inherits from it.
⭐        ⇒ ⭐⭐ THAT is why super() in B can land in C — two unrelated siblings.
```

## ⭐ C3 linearisation — the two rules

```
⭐⭐ THE MRO IS THE UNIQUE ORDER SATISFYING:
⭐   1. ⭐ LOCAL PRECEDENCE ORDER — a class's bases appear in the order you wrote them
⭐   2. ⭐⭐ MONOTONICITY — if X precedes Y in some class's MRO, X precedes Y in every
⭐        subclass's MRO too. ⇒ the order never gets rearranged as you go deeper.
⭐
⭐ ⇒ ⭐ plus: a class always precedes its own bases.
⭐ ⇒ ⭐⭐ IF NO SUCH ORDER EXISTS, THE CLASS CANNOT BE CREATED:
```

```python
class X: pass
class Y: pass
class A(X, Y): pass
class B(Y, X): pass
class C(A, B): pass
# ⭐⭐ TypeError: Cannot create a consistent method resolution order (MRO) for bases A, B
# ⭐ A demands X before Y; B demands Y before X. Both cannot hold. Python refuses at CLASS
#   CREATION time rather than producing a hierarchy with undefined behaviour.
```

⭐⭐ **Failing at class-creation time is the right design and worth saying so:** the alternative — C++'s
approach before virtual inheritance, or a language that silently picks one — hides the contradiction
until a method is called. **Python makes the contradiction a build error.**

# Part 2 — ⭐⭐ What `super()` actually does

```python
class Base:
    def greet(self): return "base"
class Mid(Base):
    def greet(self): return "mid " + super().greet()
class Leaf(Mid):
    def greet(self): return "leaf " + super().greet()

Leaf().greet()      # "leaf mid base"
```

```
⭐⭐ super() TAKES TWO IMPLICIT ARGUMENTS: super(__class__, self)
⭐   · __class__  = the class where the CODE IS WRITTEN (a compiler-provided closure cell!)
⭐   · self       = the instance ⇒ ⭐⭐ so the MRO used is type(self).__mro__, NOT __class__'s
⭐
⭐ ⇒ ⭐⭐ super() = "the class AFTER __class__ in type(self)'s MRO"
⭐ ⇒ ⭐⭐ WHICH MEANS: the target depends on the ACTUAL type of the instance, so a class can
⭐      delegate to a sibling it was never written to know about.
```

⭐⭐ **The zero-argument `super()` is compiler magic, and it connects directly to Day 043:** the
compiler adds a `__class__` cell to any method that mentions `super` or `__class__`, exactly like a
closure over the class. ⚠️ **Which is why `super()` fails inside a nested function, a lambda, or a
comprehension in some cases** — the cell is not in scope. **Use the explicit `super(MyClass, self)`
form there.**

```python
super(Mid, self).greet()          # ⭐ explicit — start the search AFTER Mid
super(Leaf, Leaf).greet           # ⭐ unbound, for classmethod-style access
```

# Part 3 — ⭐⭐ Cooperative multiple inheritance

```python
class Loggable:
    def __init__(self, **kwargs):
        self.log = []
        super().__init__(**kwargs)          # ⭐⭐ MUST call super, and pass the rest on

class Timestamped:
    def __init__(self, **kwargs):
        self.created = now()
        super().__init__(**kwargs)          # ⭐⭐ same

class Order(Loggable, Timestamped):
    def __init__(self, total, **kwargs):
        self.total = total
        super().__init__(**kwargs)          # ⭐ walks Loggable ⇒ Timestamped ⇒ object
```

```
⭐⭐ THE THREE RULES OF COOPERATIVE INHERITANCE — break any one and it silently half-works:
⭐   1. ⭐⭐ EVERY class in the chain calls super().__init__()
⭐        ⇒ one class that forgets TRUNCATES the chain — every class after it is skipped,
⭐          with no error, so half your mixins never initialise.
⭐   2. ⭐⭐ SIGNATURES MUST BE COMPATIBLE ⇒ accept and forward **kwargs
⭐        ⇒ because a class does not know who comes next, or what they need.
⭐   3. ⭐ object.__init__ takes no arguments ⇒ everything must be consumed before it.
```

⚠️ ⭐⭐ **Rule 1's failure is the nastiest bug in this area** because it is silent: your `Order` works,
`self.log` exists, and `self.created` does not — because `Loggable.__init__` forgot its `super()`
call. **There is no warning, and the missing attribute surfaces somewhere else entirely.**

⭐ **Mixin ordering matters:** the leftmost base is consulted first, so **mixins go on the left and
the "real" base on the right** — `class Order(Loggable, Timestamped, Base)`. **Reversing it means the
base's method wins and the mixin never runs.**

```python
# ⭐ Reading an MRO you did not write — the debugging move:
import inspect
Order.__mro__                          # ⭐ the order
inspect.getmro(Order)
Order.mro()                            # same, as a list
# ⭐⭐ then: which class actually provides `save`?
next(c for c in Order.__mro__ if "save" in c.__dict__)
```

# Part 4 — ⭐ When inheritance is the right tool

```
⭐⭐ INHERITANCE IS THE TIGHTEST COUPLING THE LANGUAGE OFFERS. A subclass depends on the base's
⭐   internals, not just its interface — ⇒ ⭐ the FRAGILE BASE CLASS problem: a safe-looking
⭐   change to the base breaks subclasses you have never read.
⭐
⭐ ⭐⭐ USE IT FOR:  · a genuine is-a relationship that satisfies substitutability
⭐                 · ⭐ ABCs defining an interface (Day 056)
⭐                 · ⭐ small, stateless MIXINS with one concern (Day 055)
⭐                 · framework extension points you are told to subclass
⭐ ⭐⭐ AVOID IT FOR: · code reuse — ⭐⭐ that is what composition is for (Day 055)
⭐                 · "it has some of the same methods"
```

⭐⭐ **The Liskov test, stated usefully: anywhere the base works, the subclass must work.** If your
subclass narrows what a method accepts, widens what it raises, or overrides a method to do nothing,
**it is not a subtype and inheritance is lying about it.**

⭐ **Two classic Python violations to recognise:** subclassing `list` or `dict` to add invariants
(Day 038 — `update()` bypasses your `__setitem__`), and subclassing to reuse one helper method
(**that helper wants to be a function**).

```python
# ⭐ Overriding well:
class Base:
    def process(self, data):
        self.validate(data)      # ⭐⭐ TEMPLATE METHOD — the base defines the order,
        return self.transform(data)  #   the subclass fills in the steps

class Impl(Base):
    def transform(self, data): ...   # ⭐ override the hook, not the algorithm
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"`super()` calls the parent"** | ⭐⭐ The next class in `type(self)`'s MRO — possibly a sibling. |
| ⭐⭐ **A class in the chain not calling `super()`** | ⭐⭐ Silently truncates — later mixins never initialise. |
| Fixed signatures in cooperative `__init__` | ⭐ Accept and forward `**kwargs`. |
| Mixins on the right of the base | ⭐ Leftmost wins; the mixin never runs. |
| ⭐ `super()` in a nested function/lambda | ⭐ No `__class__` cell — use the explicit form. |
| Expecting the diamond to visit `A` before `C` | ⭐⭐ A base comes after all its subclasses. |
| Treating an MRO `TypeError` as a bug | ⭐ It is a genuine contradiction, caught at class creation. |
| Inheriting for code reuse | ⭐⭐ Composition. Inheritance is the tightest coupling available. |
| Subclassing `list`/`dict` for invariants | ⭐ Built-in methods bypass your overrides. |
| Overriding a method to do nothing | ⭐ An LSP violation — it is not a subtype. |

## Interview questions

**Q: What does `super()` do?**
> It returns a proxy that starts attribute lookup at the class *after* the current one in the MRO of
> `type(self)` — not of the class where the code is written. So the next class depends on the actual
> type of the instance, which means a class can delegate to a sibling it was never written to know
> about. That's what makes cooperative multiple inheritance possible, and it's why "calls the parent"
> is wrong: in a diamond, `super()` in the left branch lands in the right branch, not in the shared
> base.

**Q: What is the MRO, and how is it computed?**
> A single linear order over the whole hierarchy, used for every attribute lookup. It's computed by C3
> linearisation, which produces the unique order satisfying two constraints: a class's bases appear in
> the order they were declared, and if X precedes Y anywhere, X precedes Y in every subclass — so the
> order is never rearranged as you go deeper. Plus every class precedes its own bases. If no such
> order exists — two bases demanding opposite orderings — Python refuses to create the class at all,
> which I'd argue is the right call: the contradiction becomes a build error instead of a surprise at
> call time.

**Q: In a diamond `D(B, C)` where both inherit `A`, what's the MRO and why?**
> `D, B, C, A, object`. `A` comes after `C` even though `B` inherits from `A` directly, because a base
> must not be visited before any class that derives from it — otherwise `C`'s override of an `A`
> method would be skipped when reached through `B`. That ordering is what makes `super()` in `B` land
> in `C`, and it's the mechanism behind cooperative mixins.

**Q: What are the rules for cooperative multiple inheritance?**
> Every class in the chain must call `super().__init__()`, and each must accept and forward
> `**kwargs`, because no class knows who comes next or what arguments they need. `object.__init__`
> takes nothing, so everything must be consumed before the chain reaches it. The failure mode for the
> first rule is the dangerous one: if one class forgets its `super()` call, the chain is truncated
> silently — every mixin after it never initialises, and the missing attribute shows up as an error
> somewhere completely unrelated.

**Q: When would you use inheritance rather than composition?**
> For a genuine is-a relationship that satisfies substitutability, for an ABC defining an interface,
> for small stateless mixins with a single concern, and where a framework tells me to subclass. Not
> for code reuse — inheritance is the tightest coupling the language offers, because the subclass
> depends on the base's internals rather than its interface, which is the fragile base class problem.
> The test I apply is Liskov: anywhere the base works, the subclass must work. If an override narrows
> what's accepted, widens what's raised, or does nothing, it isn't a subtype and the inheritance is
> lying.

it is the next class in the MRO of `type(self)`, which may be a class the current one has never heard
of.** Give the diamond: `super()` in the left branch lands in the right branch, not in the shared
base.

consistent order exists, turning a contradiction into a build error.
