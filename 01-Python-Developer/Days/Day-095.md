# Day 095

**L-095** · 🧪 **Test doubles** — and ⭐⭐ **when mocking is a design smell**
**D-06** · Relational algebra — the mental model behind SQL

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every mock is a claim that you know how a collaborator behaves — so a
> test full of mocks is a test of your beliefs rather than of your system, and the number of mocks a
> unit needs is a measurement of how many collaborators it has.**
>
> ⭐ This day has a strong opinion. **Mocking is a legitimate and sometimes necessary tool, and it is
> the single most over-used technique in Python testing.**

---

# Part 1 — ⭐ The five doubles, precisely

```
⭐⭐ "MOCK" IS USED FOR ALL FIVE IN CONVERSATION. KNOW THE ACTUAL DEFINITIONS —
⭐   it is a common interview question and the distinctions decide design:
⭐
⭐ 1. DUMMY   ⭐ passed to satisfy a signature, never used.        `None`, object()
⭐ 2. STUB    ⭐⭐ returns canned answers. NO ASSERTIONS ON IT.
⭐               "when asked for user 7, return this user"
⭐ 3. SPY     ⭐ a stub that also RECORDS what happened, checked afterwards
⭐ 4. MOCK    ⭐⭐ pre-programmed with EXPECTATIONS. ⭐⭐ THE TEST FAILS IF THE
⭐               EXPECTED CALLS DID NOT HAPPEN. ⭐ It asserts on INTERACTIONS.
⭐ 5. FAKE    ⭐⭐ A REAL, WORKING IMPLEMENTATION — simplified. An in-memory
⭐               repository, SQLite instead of Postgres, a dict instead of Redis.
⭐
⭐ ⇒ ⭐⭐ THE AXIS THAT MATTERS: STATE vs INTERACTION.
⭐     STUBS AND FAKES let you assert on the RESULT ("the order was saved").
⭐     MOCKS make you assert on the CONVERSATION ("save() was called once with X").
⭐   ⇒ ⭐⭐ AND THE CONVERSATION IS IMPLEMENTATION (Day 092). That single sentence
⭐        is the whole argument of today.
```

# Part 2 — ⭐ `unittest.mock`, used correctly

```python
from unittest.mock import Mock, patch, create_autospec

gateway = Mock()
gateway.charge.return_value = Receipt(id="r_1")          # ⭐ a stub
gateway.charge.side_effect = GatewayTimeout()            # ⭐ raise instead
gateway.charge.side_effect = [Receipt("a"), Receipt("b")]  # ⭐ successive calls

gateway.charge.assert_called_once_with(order.id, Decimal("10"))   # ⭐ now it is a mock
assert gateway.charge.call_count == 1
gateway.charge.call_args.kwargs["idempotency_key"]
```

```
⚠️⚠️ ⭐⭐ THE FLAW IN A PLAIN Mock, AND IT IS SERIOUS: IT ACCEPTS ANY ATTRIBUTE
⭐    AND ANY CALL SIGNATURE.
⭐      gateway.chrage(...)              ⇒ ⭐⭐ NO ERROR. Returns another Mock.
⭐      gateway.charge(1, 2, 3, 4, 5)    ⇒ ⭐⭐ NO ERROR.
⭐    ⇒ ⭐⭐ SO YOU RENAME charge() TO capture() IN PRODUCTION CODE AND EVERY TEST
⭐         STILL PASSES — while the application is broken. ⭐ That is the exact
⭐         opposite of what a test is for.
⭐    ⇒ ⭐⭐ THE FIX, AND IT SHOULD BE AUTOMATIC:
⭐         create_autospec(PaymentGateway, instance=True)
⭐         @patch("myapp.orders.gateway", autospec=True)
⭐         ⇒ ⭐ the double now has the REAL signature; a typo or a wrong arity
⭐           raises immediately, and a rename breaks the test as it should.
```

⭐⭐ **Patch where it is used, not where it is defined** — the same rule as Day 094, for the same
reason from Day 074: `from x import y` bound a name in *your* module. ⭐ `@patch` decorators apply
**bottom-up**, so the closest decorator is the *first* parameter.

```python
@patch("myapp.orders.notify", autospec=True)     # ⭐ applied first ⇒ first arg
@patch("myapp.orders.gateway", autospec=True)    # ⭐ applied second ⇒ second arg
def test_order_charges_and_notifies(mock_gateway, mock_notify): ...
```

# Part 3 — ⭐⭐ When mocking is a design smell

```
⭐⭐ FOUR SIGNALS. THE FIRST TWO ARE ABOUT THE TEST; THE LAST TWO ARE ABOUT THE CODE.
⭐
⭐ 1. ⚠️ ⭐⭐ YOU ARE MOCKING SOMETHING YOU DO NOT OWN.
⭐      Mocking `stripe.Charge.create` encodes YOUR BELIEF about Stripe's API into
⭐      your test. ⭐⭐ When Stripe changes, your test still passes and production
⭐      breaks — ⭐ the mock cannot know it is now wrong.
⭐      ⇒ ⭐⭐ RULE: MOCK THE ADAPTER *YOU* WROTE, NOT THE THIRD-PARTY CLIENT.
⭐        You own `PaymentGateway`, so you can keep the double honest. Then verify
⭐        the adapter itself against the real thing, rarely (Day 097's contract test).
⭐
⭐ 2. ⚠️ ⭐⭐ ASSERTIONS ON *HOW*, NOT *WHAT*.
⭐      assert_called_once_with(...) says "the implementation made this call".
⭐      ⇒ ⭐⭐ a pure refactor that achieves the same outcome differently BREAKS IT
⭐        ⇒ by Day 092's checkable definition, the test was wrong.
⭐      ⇒ ⭐ legitimate when the CALL *IS* the behaviour: "we must not charge the
⭐        card twice", "the audit event must be emitted". ⭐⭐ Then the interaction
⭐        is the requirement, and asserting on it is correct.
⭐
⭐ 3. ⚠️ ⭐⭐ FIVE MOCKS IN ONE TEST.
⭐      ⇒ ⭐⭐ THAT IS NOT A TESTING PROBLEM. It is a MEASUREMENT: this unit has
⭐        five collaborators. ⭐ Day 089's rule again — the test is telling you
⭐        the decision and the I/O are tangled.
⭐      ⇒ ⭐⭐ THE FIX IS IN THE CODE: extract the decision as a pure function and
⭐        test THAT with no doubles at all; keep the thin orchestrating layer
⭐        covered by one integration test.
⭐
⭐ 4. ⚠️ ⭐ THE TEST IS LONGER THAN THE CODE, AND MOSTLY SETUP.
⭐      ⇒ ⭐ nobody will maintain it; it will be deleted or ignored within a year.
```

```python
# ⚠️ ⭐⭐ MOCK-HEAVY — and it verifies almost nothing:
@patch("myapp.orders.db")
@patch("myapp.orders.gateway")
@patch("myapp.orders.emailer")
@patch("myapp.orders.metrics")
def test_place_order(m_metrics, m_email, m_gw, m_db):
    m_db.get_customer.return_value = Mock(tier="pro", is_active=True)
    m_gw.charge.return_value = Mock(id="r_1")
    place_order(order_id=1)
    m_gw.charge.assert_called_once()        # ⚠️ ⭐ asserts the code did what the code does

# ⭐⭐ THE SAME BEHAVIOUR, RESTRUCTURED — the RULE is now pure (Days 089, 090):
def discount_for(tier: str, subtotal: Decimal) -> Decimal:      # ⭐ pure
    return subtotal * Decimal("0.1") if tier == "pro" else Decimal("0")

def test_pro_customers_get_10_percent():                        # ⭐⭐ NO MOCKS AT ALL
    assert discount_for("pro", Decimal("100")) == Decimal("10")
```

⭐⭐ **The second test will still be true in five years.** The first breaks the next time someone
reorders two lines. ⭐ **And notice what happened: the mocking problem was solved by changing the
design, not by choosing a better mocking library.**

# Part 4 — ⭐⭐ Fakes, and the contract test

```python
class OrderRepository(Protocol):              # ⭐ Day 056 — structural typing
    def get(self, order_id: int) -> Order | None: ...
    def save(self, order: Order) -> None: ...

class InMemoryOrderRepository:                # ⭐⭐ A FAKE. ~15 lines, real behaviour.
    def __init__(self): self._items: dict[int, Order] = {}
    def get(self, order_id): return self._items.get(order_id)
    def save(self, order):   self._items[order.id] = order

def test_cancelling_a_shipped_order_is_rejected():
    repo = InMemoryOrderRepository()          # ⭐ no patching, no mock library
    repo.save(Order(id=1, status=Status.SHIPPED))
    with pytest.raises(CannotCancelShipped):
        cancel_order(repo, order_id=1)
    assert repo.get(1).status is Status.SHIPPED    # ⭐⭐ assert on STATE, not calls
```

```
⭐⭐ WHY A FAKE BEATS A MOCK, WHEN YOU CAN HAVE ONE:
⭐   · ⭐⭐ WRITTEN ONCE, USED BY EVERY TEST — where mocks are re-stubbed in each
⭐   · ⭐⭐ SURVIVES REFACTORING: it implements a CONTRACT, so how the code calls
⭐        it is free to change
⭐   · ⭐ you assert on STATE ("the order is still shipped"), which is behaviour
⭐   · ⭐ the tests read like the domain, not like a mocking DSL
⭐   · ⭐⭐ it FORCES a seam (the Protocol) — ⭐ which is Day 090's layering,
⭐        arrived at from the test side
⭐
⭐ ⚠️ ⭐⭐ AND THE HONEST WEAKNESS, WHICH YOU MUST VOLUNTEER: A FAKE CAN DRIFT
⭐    FROM THE REAL IMPLEMENTATION. Your in-memory repo does not enforce the
⭐    unique constraint, or returns rows in insertion order when Postgres does not.
⭐    ⇒ ⭐⭐ THE ANSWER IS A CONTRACT TEST: ONE test class, PARAMETRIZED over
⭐         [the fake, the real one] (Day 094), asserting the shared contract.
⭐         ⭐ Runs in milliseconds against the fake and in CI against Postgres.
⭐    ⇒ ⭐ that is the technique that makes fakes safe, and almost nobody does it.
```

# Part 5 — D-06 · ⭐⭐ Relational algebra

```
⭐⭐ SQL IS DECLARATIVE — you say WHAT. The PLANNER (Day 078, D-01) converts it
⭐   into an ALGEBRA EXPRESSION and rewrites that expression into a cheaper but
⭐   EQUIVALENT one. ⭐⭐ THAT REWRITING *IS* QUERY OPTIMISATION, and this is the
⭐   language it happens in.
```

| ⭐ Operation | ⭐ Symbol | ⭐ SQL |
|---|---|---|
| ⭐ **Selection** — pick **rows** | σ | `WHERE` |
| ⭐ **Projection** — pick **columns** | π | `SELECT a, b` (⭐ set semantics ⇒ dedupe) |
| Rename | ρ | `AS` |
| Union / Difference / Intersection | ∪ − ∩ | `UNION` / `EXCEPT` / `INTERSECT` |
| Cartesian product | × | `CROSS JOIN` — ⭐⭐ every row with every row |
| ⭐⭐ **Natural / theta join** | ⋈ | `JOIN … ON` |
| ⭐ **Semi-join** | ⋉ | ⭐⭐ `WHERE EXISTS (…)` — rows of A that *have* a match |
| ⭐ **Anti-join** | ▷ | ⭐⭐ `WHERE NOT EXISTS (…)` — rows of A with *no* match |
| Division | ÷ | ⭐ "customers who bought **every** product" — no direct syntax |

```
⭐⭐ A JOIN IS DEFINED AS σ(A × B) — a cartesian product, then a selection.
⭐   ⇒ ⭐⭐ WHICH IS EXACTLY WHY A MISSING JOIN CONDITION RETURNS n×m ROWS: you
⭐        did not write a broken join, ⭐ YOU WROTE THE PRODUCT AND FORGOT THE
⭐        SELECTION. The engine did exactly what you asked.
⭐   ⇒ ⭐ and no engine actually materialises the product — the planner uses a
⭐        hash or merge join. ⭐⭐ The algebra defines the MEANING; the plan
⭐        chooses the METHOD. Keeping those two apart is most of what makes
⭐        EXPLAIN readable (Stage 5).
```

```
⭐⭐ THE MOST USEFUL EQUIVALENCE, AND IT IS THE ONE OPTIMISERS LIVE BY:
⭐        σ(A ⋈ B)  ≡  σ(A) ⋈ B          ⭐⭐ "PUSH THE SELECTION DOWN"
⭐   ⇒ filter BEFORE joining and you join far fewer rows.
⭐   ⇒ ⭐⭐ the planner does this for you — ⭐ which is precisely why `WHERE` and
⭐        `ON` usually perform identically on an INNER join…
⭐   ⇒ ⚠️ ⭐⭐ …AND WHY THEY DIFFER ON AN OUTER JOIN: a condition in `ON` filters
⭐        BEFORE the outer join preserves unmatched rows; the same condition in
⭐        `WHERE` filters AFTER, discarding the NULL-extended rows and silently
⭐        turning your LEFT JOIN back into an INNER JOIN. ⭐⭐ That is a real,
⭐        common bug, and the algebra is what explains it.
```

⭐ **And the tie back to today:** a *semi-join* is "does a match exist" — ⭐⭐ **an interaction
question**. A *join* returns the matched data — **a state question.** The same distinction you just
drew between mocks and fakes, in a different notation.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Plain `Mock()` with no spec** | ⭐⭐ Accepts typos and wrong arity ⇒ a rename leaves tests green. `autospec`. |
| ⭐⭐ **Mocking a third-party client** | ⭐⭐ You encode your belief about their API. Mock your own adapter. |
| `assert_called_once_with` everywhere | ⭐ Asserting on *how*. A pure refactor breaks it. |
| ⭐ Five mocks in one test | ⭐⭐ A measurement of collaborators. Fix the design, not the test. |
| Patching where defined | ⭐ Patch where it is **used** (Days 074, 094). |
| ⭐ Confusing decorator order | ⭐ `@patch` applies bottom-up. |
| Mock where a fake would do | ⭐⭐ A fake is written once, survives refactoring, and asserts on state. |
| ⭐ A fake with no contract test | ⭐⭐ It will drift. Parametrize one contract test over both. |
| ⭐⭐ Forgetting the join condition | ⭐⭐ A join **is** `σ(A × B)` — you wrote the product. |
| Outer-join filter in `WHERE` | ⭐⭐ Silently becomes an inner join. Put it in `ON`. |
| `SELECT DISTINCT` to fix duplicates | ⭐ Usually a fan-out from a join — fix the join. |

## Interview questions

**Q: What's the difference between a stub, a mock and a fake?**
> A stub returns canned answers and you never assert on it. A mock is pre-programmed with
> expectations, so the test fails if the expected calls didn't happen — it asserts on interactions. A
> fake is a real, simplified implementation, like an in-memory repository. The axis that matters is
> state versus interaction: stubs and fakes let you assert on the result, mocks make you assert on the
> conversation. And the conversation is implementation, which is why mock-heavy tests break on
> refactors that don't change behaviour.

**Q: Why is `create_autospec` important?**
> Because a plain `Mock` accepts any attribute and any signature. `gateway.chrage(1,2,3,4,5)` returns
> another Mock quite happily. So if you rename `charge` to `capture` in production code, every test
> still passes while the application is broken — the exact opposite of what a test is for.
> `autospec` gives the double the real signature, so typos and wrong arity fail immediately and a
> rename breaks the test the way it should.

**Q: When is mocking a design smell?**
> Four signals. Mocking something you don't own, because you're encoding your belief about a
> third-party API and it can't tell you when that belief goes stale — mock your own adapter instead,
> and verify the adapter against the real thing separately. Asserting on how rather than what, because
> a pure refactor then breaks the test. Five mocks in one test, which isn't a testing problem at all —
> it's a measurement that the unit has five collaborators, and the fix is to extract the decision as a
> pure function. And a test that's longer than the code and mostly setup, because nobody maintains
> that.

**Q: When is asserting on a call the right thing?**
> When the call *is* the behaviour. "We must not charge the card twice" and "an audit event must be
> emitted" are requirements about interactions, so asserting on the interaction is correct and a fake
> wouldn't capture it. The distinction I use is whether a reasonable alternative implementation could
> satisfy the requirement without making that call. If yes, I'm testing implementation. If no, the
> call is the contract.

**Q: What is a contract test, and why do fakes need one?**
> A fake can drift from the real implementation — my in-memory repository doesn't enforce the unique
> constraint, or returns rows in insertion order when Postgres doesn't. A contract test is one test
> class parametrized over both the fake and the real implementation, asserting the shared contract. It
> runs in milliseconds against the fake in the fast suite and against a real database in CI. That's
> the technique that makes fakes safe, and almost nobody does it.

**Q: Why does a missing join condition return millions of rows?**
> Because a join is defined as a selection over a cartesian product — `σ(A × B)`. Without the
> condition you've written the product and omitted the selection, so the engine returns every
> combination, exactly as asked. That framing also explains the outer-join bug: a condition in `ON`
> applies before the outer join preserves unmatched rows, while the same condition in `WHERE` applies
> after, discarding the NULL-extended rows and silently turning a LEFT JOIN back into an INNER JOIN.

## 🎙️ Articulation drill

Record two minutes: **"How do you decide what to mock?"**

⭐ **Start with a rule that has an edge:** **"as little as possible, and never something I don't own.
If I mock Stripe's client, I've encoded my belief about Stripe's API into my test — and when Stripe
changes, my test still passes while production breaks. So I mock the adapter I wrote, and verify that
adapter against the real thing separately."**

⭐⭐ **Then the state-versus-interaction distinction, which is the heart of it:** *"beyond that I
prefer fakes to mocks. A fake is a real, simplified implementation — an in-memory repository behind a
Protocol, maybe fifteen lines — and it lets me assert on state: the order is still marked shipped.
Mocks make me assert on the conversation, that `save` was called once with these arguments, and the
conversation is implementation. A pure refactor that achieves the same outcome differently breaks a
mock-based test, and by the definition I use, that means the test was wrong."*

⭐⭐ **Then the design point, and be explicit that it's a measurement:** *"and if a test needs five
mocks, I stop treating it as a testing problem. Five mocks means the unit has five collaborators —
that's a measurement of the design. The fix is in the code: pull the decision out as a pure function
and test that with no doubles at all, then cover the thin orchestrating layer with one integration
test. The mocking problem gets solved by changing the design, not by picking a better mocking
library."*

⭐ **Then give the exceptions, because a rule with no exceptions sounds rehearsed:** *"there are two
places I do reach for a mock. When the call *is* the requirement — 'we must not charge the card twice',
'an audit event must be emitted' — asserting on the interaction is correct. And when the real thing is
genuinely unavailable or slow. In both cases I'd use `autospec`, because a plain Mock accepts typos
and wrong arity, so renaming a method leaves every test green while the app is broken."*

⭐ **Close on the thing almost nobody does:** *"and if I'm relying on a fake, I'd write one contract
test parametrized over the fake and the real implementation. Fakes drift, and that's the cheap way to
find out before production does."*
