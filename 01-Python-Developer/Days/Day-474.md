**Time:** 3 hrs · **Mode:** MOCK + SCORED

> ⭐⭐ **The sentence to own: people fail DP because they try to invent the table, and the table is the

> already correct before you have thought about a single array index.**

# Part 1 — ⭐⭐ The four-step method

```
⭐ ***DP IS NOT INSPIRATION. IT IS A PROCEDURE, AND THE ORDER
⭐   MATTERS MORE THAN THE CLEVERNESS.***

⭐ ① ⭐⭐ ***WRITE THE BRUTE-FORCE RECURSION.***
⭐   ⭐ Ask one question: ⭐⭐ ***"AT THIS POSITION, WHAT ARE MY
⭐     CHOICES?"*** ⭐ Take each, recurse, combine.
⭐   ⭐ ⭐⭐ IGNORE EFFICIENCY COMPLETELY. ⭐ Exponential is fine
⭐     and expected.
⭐   ⭐ ⭐⭐ THIS STEP IS 80% OF THE DIFFICULTY AND PEOPLE SKIP IT
⭐     TO GO STRAIGHT TO A TABLE THEY CANNOT DERIVE.

⭐ ② ⭐⭐ ***IDENTIFY THE STATE.*** ⭐ What arguments actually
⭐   change between calls?
⭐   ⭐ ⭐⭐ THAT IS YOUR CACHE KEY AND, LATER, YOUR TABLE
⭐     DIMENSIONS. ⭐ It falls out of ① rather than being invented.
⭐   ⭐ ⭐ If a parameter never changes, it does not belong in the
⭐     state — ⭐⭐ CLOSE OVER IT INSTEAD, OR YOUR CACHE IS
⭐     UNNECESSARILY LARGE.

⭐ ③ ⭐⭐ ***ADD `@cache`. YOU ARE NOW DONE ON CORRECTNESS.***
⭐   ⭐ Top-down memoisation, ⭐⭐ AND IN AN INTERVIEW THIS IS
⭐     OFTEN THE FINAL ANSWER. ⭐ Say so.

⭐ ④ ***CONVERT TO BOTTOM-UP ONLY IF ASKED*** — ⭐ or if you need
⭐   the space optimisation. ⭐⭐ TABULATION IS A ***REWRITE OF A
⭐   WORKING SOLUTION***, NOT A NEW PROBLEM.

⭐ ⭐⭐ THE PAYOFF: ⭐ at step ③ you have a correct, complete
⭐   answer with the right complexity. ⭐⭐ EVERYTHING AFTER THAT
⭐   IS OPTIMISATION YOU CAN DISCUSS RATHER THAN A CLIFF YOU CAN
⭐   FALL OFF.
```

# Part 2 — `functools.cache`, and its two sharp edges

```python
from functools import cache          # ⭐ Python 3.9+; lru_cache(None) before

def coin_change(coins: list[int], amount: int) -> int:
    @cache                           # ⭐⭐ THE ENTIRE OPTIMISATION
    def fewest(remaining: int) -> float:
        if remaining == 0:
            return 0
        if remaining < 0:
            return float("inf")
        # ⭐ THE CHOICE: which coin do I use next?
        return 1 + min((fewest(remaining - c) for c in coins),
                       default=float("inf"))

    result = fewest(amount)
    return -1 if result == float("inf") else int(result)
# ⭐ O(amount × len(coins)) time, O(amount) space.
```

```
⭐ ⭐⭐ EDGE ① — ***ARGUMENTS MUST BE HASHABLE.***
⭐   ⭐ You cannot `@cache` a function taking a `list`.
⭐   ⭐ ⇒ pass a `tuple`, or pass ***indices into*** a list you
⭐     closed over. ⭐⭐ THE SECOND IS ALMOST ALWAYS BETTER AND IT
⭐     IS THE HABIT TO BUILD: ⭐ recurse on `i`, not on `arr[i:]`
⭐     — ⭐⭐ WHICH ALSO AVOIDS THE O(k) SLICE COPY FROM DAY 472.

⭐ ⭐⭐ EDGE ② — ***`@cache` ON A METHOD LEAKS.*** ⭐ It holds a
⭐   reference to `self` forever, ⭐⭐ SO THE INSTANCE IS NEVER
⭐   COLLECTED. ⭐ Fine inside one call, ⭐⭐ A REAL MEMORY LEAK IN
⭐   A LONG-LIVED SERVICE. ⭐ Define the helper ***inside*** the
⭐   method, as above — ⭐ then the cache dies with the call.
⭐   ⭐ ⭐⭐ SAYING THIS UNPROMPTED IS A PRODUCTION SIGNAL, NOT AN
⭐     INTERVIEW TRICK.
```

# Part 3 — ⭐⭐ The five state shapes

```
⭐ ***ALMOST EVERY INTERVIEW DP IS ONE OF THESE. IDENTIFY THE
⭐   SHAPE AND THE RECURSION WRITES ITSELF.***

⭐ ① ⭐⭐ ***ONE INDEX — `f(i)`.***
⭐   ⭐ "Best answer considering the first i items."
⭐   ⭐ Climbing stairs · house robber · ⭐ word break ·
⭐     decode ways.
⭐   ⭐ ⭐⭐ THE CHOICE IS USUALLY BINARY: TAKE i OR SKIP i.

⭐ ② ⭐⭐ ***TWO INDICES — `f(i, j)`.***
⭐   ⭐ Two sequences, or a range.
⭐   ⭐ Edit distance · LCS · ⭐ regex matching · ⭐⭐ PALINDROMIC
⭐     SUBSTRINGS (RANGE DP).
⭐   ⭐ ⭐ For two sequences the choice is: match, or skip one
⭐     side.

⭐ ③ ⭐⭐ ***INDEX + CAPACITY — `f(i, remaining)`.***
⭐   ⭐ ***The knapsack family***, and it is the one people fail
⭐     to recognise.
⭐   ⭐ 0/1 knapsack · ⭐⭐ PARTITION EQUAL SUBSET SUM ⭐ · target
⭐     sum · coin change.
⭐   ⭐ ⭐⭐ THE TELL: "CAN I HIT EXACTLY X USING SOME SUBSET?"

⭐ ④ ⭐⭐ ***INDEX + A SMALL MODE — `f(i, state)`.***
⭐   ⭐ Buy/sell stock with cooldown or a transaction limit.
⭐   ⭐ ⭐⭐ THE STATE IS A TINY ENUM — HOLDING / NOT HOLDING /
⭐     COOLING — ⭐ and forgetting it is why people get stock
⭐     problems wrong.

⭐ ⑤ ***INTERVALS — `f(i, j)` OVER A RANGE, SPLIT AT k.***
⭐   ⭐ Matrix chain · burst balloons · ⭐⭐ AND THE LOOP ORDER IS
⭐     BY ***LENGTH***, NOT BY INDEX, ⭐ which is the thing that
⭐     breaks tabulated versions.

⭐ ⭐⭐ AND THE DIAGNOSTIC WHEN YOU ARE STUCK: ⭐ ***"WHAT DO I
⭐   NEED TO KNOW, BEYOND MY POSITION, TO MAKE THE NEXT
⭐   DECISION?"*** ⭐ Whatever that is, ⭐⭐ IT IS THE SECOND
⭐   DIMENSION OF YOUR STATE.
```

# Part 4 — The mock: four problems, 45 minutes

```
⭐ ***P1 (8 min) — HOUSE ROBBER.*** ⭐ Then: ⭐⭐ "OPTIMISE TO O(1)
⭐   SPACE."
⭐ ***P2 (15 min) — COIN CHANGE*** — fewest coins. ⭐ Then:
⭐   ⭐⭐ "NOW COUNT THE NUMBER OF WAYS" ⭐ (the loop order changes
⭐   and that is the lesson).
⭐ ***P3 (15 min) — EDIT DISTANCE.***
⭐ ***P4 (7 min) — PARTITION EQUAL SUBSET SUM.*** ⭐⭐ RECOGNISE
⭐   THE KNAPSACK.
```

```python
# ⭐ P1 — step ① then step ④, shown together.
def rob(nums: list[int]) -> int:
    @cache
    def best(i: int) -> int:
        if i >= len(nums):
            return 0
        # ⭐ THE CHOICE, stated plainly:
        return max(nums[i] + best(i + 2),   # rob this one
                   best(i + 1))             # skip it
    return best(0)

# ⭐⭐ THE O(1) FOLLOW-UP — note it is a REWRITE, not a rethink.
def rob_optimised(nums: list[int]) -> int:
    take = skip = 0                # ⭐ best if we rob i / skip i
    for x in nums:
        take, skip = skip + x, max(skip, take)
    return max(take, skip)
# ⭐⭐ ONLY THE LAST TWO VALUES EVER MATTERED — that observation
# is the whole space optimisation, and it generalises.
```

```python
# ⭐⭐ P2 FOLLOW-UP — THE LOOP ORDER *IS* THE ANSWER.
def change_ways(coins: list[int], amount: int) -> int:
    dp = [0] * (amount + 1)
    dp[0] = 1
    for c in coins:                     # ⭐⭐ COINS OUTSIDE
        for a in range(c, amount + 1):  # ⭐ amounts inside
            dp[a] += dp[a - c]
    return dp[amount]

# ⭐⭐ SWAP THE LOOPS AND YOU COUNT *PERMUTATIONS*, NOT
# COMBINATIONS: {1,2} and {2,1} become two answers.
# ⭐ Coins-outside means each coin is considered once per
# amount, so order never varies. ⭐⭐ BE READY TO EXPLAIN THIS —
# IT IS THE MOST COMMON FOLLOW-UP IN THE WHOLE TOPIC.
```

```python
# ⭐ P3 — the classic f(i, j). Three choices, one line each.
def edit_distance(a: str, b: str) -> int:
    @cache
    def d(i: int, j: int) -> int:
        if i == len(a): return len(b) - j    # ⭐ insert the rest
        if j == len(b): return len(a) - i    # ⭐ delete the rest
        if a[i] == b[j]:
            return d(i + 1, j + 1)           # ⭐⭐ FREE MATCH
        return 1 + min(d(i + 1, j),          # delete a[i]
                       d(i, j + 1),          # insert b[j]
                       d(i + 1, j + 1))      # substitute
    return d(0, 0)
# ⭐ O(len(a)·len(b)) time and space.
# ⭐⭐ NOTE: RECURSING ON INDICES, NOT ON SLICES — hashable,
# and no O(k) copy per call (Day 472).
```

```python
# ⭐ P4 — the recognition IS the problem.
def can_partition(nums: list[int]) -> bool:
    total = sum(nums)
    if total % 2:                    # ⭐ odd total ⇒ impossible
        return False
    target = total // 2
    # ⭐⭐ NOW IT IS SUBSET-SUM: "can I hit exactly `target`?"
    reachable = {0}
    for x in nums:
        # ⭐ set-based knapsack — concise and genuinely fast
        reachable |= {r + x for r in reachable if r + x <= target}
        if target in reachable:
            return True
    return target in reachable
# ⭐ O(n · target). ⭐⭐ SAY THE COMPLEXITY HONESTLY: THIS IS
# *PSEUDO*-POLYNOMIAL — it scales with the VALUE of the sum, not
# just the input length. That distinction is a real signal.
```

# 💬 Interview

**1. "How do you approach a DP problem?"**

⭐ As a procedure, not as inspiration. ⭐⭐ First I write the brute-force recursion, and the only question
I ask is "at this position, what are my choices?" — take it or skip it, match or advance one side, use
this coin or don't. ⭐ I ignore efficiency completely at that stage; exponential is expected. ⭐⭐ Then
the state falls out for free: it's whichever arguments actually change between calls. ⭐ Then `@cache`,
and at that point I have a correct solution with the right complexity — which in most interviews is the
final answer, and I'd say so rather than assume tabulation is required. ⭐⭐ Bottom-up is a rewrite of a
working solution, so it's the last step and only if asked or if I need the space optimisation.

**2. "Why not go straight to the table?"**

⭐ Because the table is the hardest thing to invent and the easiest thing to derive. ⭐⭐ If I try to
start with dimensions and transitions, I'm guessing — and if I guess wrong I have nothing, with twenty
minutes gone. ⭐ If I start with the recursion, I have a correct answer at minute ten and everything
after is optimisation I can discuss. ⭐⭐ It also means the state isn't something I chose, it's something
I read off the function signature, which is why it's usually right.

**3. "Coin change: fewest coins versus number of ways."**

⭐ Same state, different loop order, and the loop order *is* the answer. ⭐⭐ For counting ways with
combinations, coins go on the outside and amounts on the inside — that way each coin is considered once
per amount, so order never varies and {1,2} and {2,1} are one answer. ⭐ Swap the loops and you count
permutations instead, because for each amount you reconsider every coin. ⭐⭐ It's the most common
follow-up in the whole topic and it's a two-line change that silently changes the problem, so I'd state
which one I'm computing before writing it.

**4. "What are the sharp edges of `@cache`?"**

⭐ Two. ⭐⭐ Arguments have to be hashable, so I can't cache a function taking a list — which pushes me
toward recursing on indices rather than on slices, and that's the right habit anyway because slicing
copies and turns a linear recursion into a quadratic one. ⭐ The second is production-shaped: `@cache` on
a *method* holds a reference to `self` forever, so the instance is never collected. ⭐⭐ Inside a single
call that's harmless; in a long-lived service it's a genuine memory leak. ⭐ Defining the helper inside
the method fixes it, because then the cache dies with the call.

**5. "You said pseudo-polynomial. What does that mean here?"**

⭐ That the complexity depends on the *value* of the input, not just its length. ⭐⭐ Subset-sum is O(n ×
target), and `target` is a number in the input rather than a count of items — so doubling the number of
bits in the target doubles the runtime exponentially in input *size*, even though it looks polynomial.
⭐ Practically it means the algorithm is fine for small sums and useless for large ones, and it's why
subset-sum is NP-complete despite having a "polynomial" DP. ⭐⭐ I'd rather say that than quote O(n ×
target) as if it were straightforwardly efficient.

**6. "Optimise house robber to O(1) space."**

⭐ It's a rewrite rather than a rethink, which is the general shape of these follow-ups. ⭐⭐ The
observation is that `best(i)` only ever depends on `best(i+1)` and `best(i+2)` — so the whole table is
never needed, only the last two values. ⭐ That becomes two rolling variables and one line in the loop.
⭐⭐ The same observation generalises: whenever the recurrence reaches back a fixed number of steps, the
table collapses to that many variables, and it's worth stating the reason rather than just producing the
tighter code.

## 🎙️ Articulation drill

⭐⭐ **Two minutes, out loud: solve edit distance from scratch, narrating the method.**

Start with the method, not the problem. **"I'll write the brute-force recursion first and add memoisation
after — that way I have a correct answer before I think about any table."**

Then generate the recursion by asking one question. **"I'm at position i in the first string and j in the
second. What are my choices? If the characters match, that's free — advance both. If they don't, I have
exactly three options: delete from the first, insert from the second, or substitute — and each costs one,
so it's one plus the minimum of the three. Base cases: if I've run out of the first string, I insert
whatever's left of the second, and vice versa."**

Then read the state off the signature. **"The state is (i, j) — those are the only things changing
between calls, and I'm recursing on indices rather than slices, both because slices aren't hashable so
`@cache` would reject them, and because slicing copies, which would turn each call into O(k) and quietly
change my complexity."**

Then close it out. **"Add `@cache` and I'm done: the state space is len(a) times len(b), each state does
constant work, so it's O(mn) time and space. If you want O(min(m,n)) space I'd convert to bottom-up and
keep two rows, because row i only ever depends on row i−1 — but that's a rewrite of a working solution,
not a different idea, and I'd only do it if you want to see it."**
