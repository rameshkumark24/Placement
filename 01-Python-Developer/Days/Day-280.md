# Part 2 — ⭐⭐ The failure drill

**Do all five live. If any surprises you, it is not ready.**

- [ ] **⭐⭐ Kill the API mid-demo.** The UI shows a named error and a working Retry — not a white screen, not a spinner forever.
- [ ] **⭐⭐ Expire the session while a form is half-filled.** It refreshes silently and the save succeeds. Break the refresh too: a modal appears and **nothing typed is lost** (Day 274).
- [ ] **⭐ Filter to zero results.** The empty state says *"no matches for X"* with a Clear button — **not** "no orders yet" (Day 240).
- [ ] **⭐⭐ Deploy while a tab is open**, then click a lazy route. The reload-once guard recovers it (Day 245).
- [ ] **⭐ Disconnect the network for 60 s during a live view**, then reconnect. The indicator changes and the data **resyncs** rather than staying quietly stale (Day 277).

```
⭐⭐ AND THE ONE THAT PROVES THE SECURITY MODEL:
⭐   ⭐ OPEN DEVTOOLS, DELETE THE `hidden` ATTRIBUTE ON A BUTTON
```

## 🎙️ Articulation drill

⭐⭐ **Three minutes: the full project walkthrough, frontend included.**

Open with the system, not the stack. **It's an X for Y. FastAPI and Postgres behind it, React and
TypeScript in front, and I wrote both — which matters more than either, because building the client is
where I found out what was wrong with the API.**

Give the demo shape verbally. **Login lands you on the deep link you actually asked for. The list keeps
its filters in the URL, so it's shareable and Back works. The detail screen shows where an order is,
how it got there, and what can be done next — and the available actions come from the server, computed
by the same function that enforces them, so the UI can't offer a button that fails.**

Then the failure, deliberately. **The part I'd actually demo is what happens when it breaks. I can kill
the API mid-demo and the UI names the error and offers a working retry. I can expire the session while
a form is half-filled and the save still succeeds silently — and if the refresh fails too, a modal
appears over the still-mounted form and nothing typed is lost. And I can open DevTools, un-hide a button
I'm not allowed to use, click it, and get a 403 — because authorization is server-side or it doesn't
exist.**

Close on the findings, which is the answer to "was this real work". **Building the client surfaced
seven server-side defects. The one I'd pick is pagination: offset was silently skipping rows whenever
anything was created or deleted between page loads. No error, not reproducible on demand, and the user
simply never saw some of their data. I replaced it with keyset pagination including an id tie-break.
I'd never have found that from the server side, because every individual query was correct.**
