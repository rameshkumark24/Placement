# Day 358 ⌨️

**P-358** · ⌨️ **Design 14 — autocomplete** — ⭐⭐ precompute top-K, and the hot layer

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: autocomplete looks like a data-structures question and is actually a
> latency-budget question — you have about fifty milliseconds end to end and a query on every
> keystroke, which means nothing can be computed at request time, so the design is entirely about how
> the precomputed answers get built and refreshed.**

---

# Part 1 — ⭐ 0–8: scope and the budget

```
⭐⭐ FUNCTIONAL:
⭐   ① Given a prefix, return the top 5–10 completions.
⭐   ② ⭐ Ranked by popularity (and personalisation).
⭐   ③ ⭐ Trending terms appear within minutes.
⭐   ④ ⭐ Typo tolerance.
⭐   ⭐⭐ OUT: the search itself (Day 337), spell correction of
⭐     the ***query results***, multilingual tokenisation.

⭐⭐ NON-FUNCTIONAL — ⭐⭐ AND THE FIRST ONE IS THE WHOLE DESIGN:
⭐   ⭐ ⭐⭐ p99 < 50 ms ***END TO END, INCLUDING THE NETWORK.***
⭐     ⭐ That leaves ~10–20 ms of server time. ⭐⭐ ANYTHING THAT
⭐     TOUCHES A DISK ON THE REQUEST PATH IS ALREADY TOO SLOW.
⭐   ⭐ ⭐⭐ A QUERY PER KEYSTROKE: 10 M searches/day BECOMES
⭐     ***~150 M AUTOCOMPLETE REQUESTS/DAY*** at ~15 characters
⭐     each. ⭐ 1,700/s average, ⭐ 5,000/s peak.
⭐   ⇒ ⭐⭐ SO AUTOCOMPLETE HANDLES ***15× MORE TRAFFIC THAN
⭐     SEARCH ITSELF***, AND SAYING THAT NUMBER EARLY REFRAMES
⭐     THE PROBLEM FOR THE INTERVIEWER.
⭐   ⭐ ⭐⭐ STALENESS OF MINUTES IS ACCEPTABLE (except for
⭐     trending), WHICH IS WHAT MAKES PRECOMPUTATION LEGAL.

⭐⭐ THE CLIENT-SIDE HALF, WHICH IS FREE AND OFTEN OMITTED:
⭐   ⭐ ⭐⭐ DEBOUNCE ~100–150 ms ⇒ CUTS REQUEST VOLUME BY
⭐     50–70% AT NO COST TO PERCEIVED SPEED.
⭐   ⭐ Cancel in-flight requests on a new keystroke — ⭐⭐ AND
⭐     DISCARD OUT-OF-ORDER RESPONSES, or the suggestions
⭐     "flicker" backwards to an older prefix.
⭐   ⭐ Cache locally: ⭐⭐ IF "IPH" RETURNED NOTHING, "IPHO"
⭐     CANNOT RETURN ANYTHING — ⭐ don't ask.
⭐   ⇒ ⭐⭐ MENTIONING THE CLIENT IS A DIFFERENTIATOR: IT IS THE
⭐     CHEAPEST CAPACITY IN THE SYSTEM.
```

# Part 2 — ⭐⭐ The trie, and why the naive version fails

```
⭐⭐ THE OBVIOUS STRUCTURE: a trie. ⭐ Walk the prefix, then
⭐   collect completions in the subtree.
⭐   ⇒ ⭐⭐ AND THAT COLLECTION IS THE PROBLEM: THE SUBTREE UNDER
⭐     "a" CONTAINS ***MILLIONS*** OF TERMS. ⭐ Traversing it and
⭐     sorting by popularity per request is far outside a 10 ms
⭐     budget.

⭐⭐ ✔ ***STORE THE TOP-K AT EVERY NODE.***
⭐   ⭐ Each node holds a precomputed list of its 10 best
⭐     completions with scores.
⭐   ⇒ ⭐⭐ A LOOKUP IS: WALK ***p*** CHARACTERS, RETURN A LIST.
⭐     ***O(p)*** WITH p ≤ 20, AND ***NO SEARCH AT ALL.***
⭐   ⭐ Memory: 10 M terms × 20 prefixes × 10 entries × ~50 B
⭐     ⇒ ⭐⭐ ~100 GB IF STORED NAIVELY.
⭐   ⇒ ⭐ FIXES: ⭐⭐ ONLY MATERIALISE PREFIXES OF LENGTH 1–5
⭐     (⭐ beyond five characters the candidate set is small
⭐     enough to compute on the fly), ⭐ store term ***ids***
⭐     rather than strings, ⭐ and drop prefixes with no traffic.
⭐   ⇒ ⭐⭐ THAT TYPICALLY BRINGS IT UNDER 10 GB, WHICH FITS IN
⭐     MEMORY ON EVERY NODE — ⭐ and "it fits in memory
⭐     everywhere" is the property the latency budget requires.

⭐⭐ AND THE SIMPLER SHAPE THAT IS OFTEN BETTER IN PRACTICE:
⭐   ⭐ ⭐⭐ A PLAIN HASH MAP FROM PREFIX → TOP-K LIST. ⭐ You
⭐     lose the shared-structure memory saving and gain ***O(1)
⭐     lookup, trivial sharding by prefix, and trivial
⭐     updates.***
⭐   ⇒ ⭐⭐ SAYING "A TRIE IS THE TEXTBOOK ANSWER, BUT SINCE I
⭐     ONLY EVER LOOK UP WHOLE PREFIXES AND NEVER TRAVERSE, A
⭐     HASH MAP IS SIMPLER AND SHARDS BETTER" IS A STRONG,
⭐     CONFIDENT ANSWER — ⭐ it shows you chose the structure for
⭐     the access pattern rather than reciting one.
```

# Part 3 — ⭐⭐ The write path is the actual design

```
⭐⭐ THE PIPELINE:
⭐   ① ⭐ ***COLLECT*** — every executed search is logged
⭐      (query, timestamp, locale, ⭐ result count).
⭐   ② ⭐⭐ ***AGGREGATE*** — count query frequency over a
⭐      window. ⭐ 150 M events/day, so this is a streaming or
⭐      batch job, not a database `GROUP BY`.
⭐   ③ ⭐ ***SCORE*** — Part 4.
⭐   ④ ⭐⭐ ***BUILD*** — for every prefix, compute the top-K.
⭐   ⑤ ⭐⭐ ***SHIP*** — publish the new structure and swap it
⭐      atomically.

⭐⭐ THE BUILD FREQUENCY IS A TRADE:
⭐   ⭐ Daily ⇒ cheap, ⭐⭐ AND TRENDING TERMS TAKE A DAY TO
⭐     APPEAR, WHICH IS USELESS FOR NEWS AND EVENTS.
⭐   ⭐ Every few minutes ⇒ fresh, expensive.
⭐   ⇒ ⭐⭐ THE ANSWER: ***TWO LAYERS.***
⭐      ⭐ A ***BASE*** index rebuilt daily from the full history
⭐        — large, stable, high quality.
⭐      ⭐ ⭐⭐ A ***HOT*** LAYER UPDATED EVERY FEW MINUTES FROM A
⭐        STREAMING COUNT OVER THE LAST HOUR — small, volatile.
⭐      ⭐ ⭐⭐ MERGE AT QUERY TIME: BOTH LOOKUPS ARE O(1) AND
⭐        THE MERGE IS TWENTY ELEMENTS. ⭐ Cost: microseconds.
⭐   ⇒ ⭐⭐ THIS IS THE SAME LAMBDA-ARCHITECTURE SHAPE AS A
⭐     BATCH LAYER PLUS A SPEED LAYER, AND IT IS THE RIGHT
⭐     ANSWER HERE BECAUSE THE MERGE IS SO CHEAP.

⭐⭐ DEPLOYMENT: ⭐⭐ BUILD INTO A ***NEW*** STRUCTURE AND SWAP A
⭐   POINTER — never mutate the live one.
⭐   ⇒ ⭐ Day 337's alias swap, again: ⭐⭐ ONE PROCEDURE COVERS
⭐     REBUILDS, SCHEMA CHANGES, ROLLBACK AND CORRUPTION.
```

# Part 4 — ⭐⭐ Ranking, and the feedback loop that ruins it

```
⭐⭐ THE SCORE IS NOT RAW FREQUENCY. ⭐ Four components:
⭐   ① ⭐ ***FREQUENCY*** — how often the query is issued.
⭐   ② ⭐⭐ ***RECENCY*** — time-decayed, so last month's news
⭐        fades. ⭐ An exponential decay with a half-life of a
⭐        few days is the standard, cheap approach.
⭐   ③ ⭐⭐ ***SUCCESS*** — did the query lead to a click or a
⭐        conversion? ⭐⭐ A POPULAR QUERY THAT ALWAYS RETURNS
⭐        NOTHING SHOULD NOT BE SUGGESTED, AND FREQUENCY ALONE
⭐        WILL HAPPILY SUGGEST IT FOREVER.
⭐   ④ ⭐ ***CONTEXT*** — locale, device, category, and
⭐        (carefully) the user's own history.

⭐⭐ ⇒ AND THE PROBLEM THAT DEFINES THIS SYSTEM:
⭐   ***THE POPULARITY FEEDBACK LOOP.*** ⭐ Suggested terms get
⭐   clicked, which makes them more popular, ⭐⭐ WHICH MAKES
⭐   THEM MORE SUGGESTED. ⭐ The top ten ossify and nothing new
⭐   ever surfaces.
⭐   ⇒ FIXES: ⭐ log ***typed*** queries separately from
⭐     ***suggested-and-clicked*** ones and weight them
⭐     differently; ⭐ inject a small amount of exploration;
⭐     ⭐⭐ AND MEASURE ***COVERAGE*** — what fraction of
⭐     distinct queries are ever suggested — because a system
⭐     that only ever offers its own top ten looks fine on
⭐     click-through and is quietly useless.

⭐⭐ AND THE SAFETY LAYER, WHICH IS NOT OPTIONAL:
⭐   ⭐ ⭐⭐ AUTOCOMPLETE PUTS WORDS IN YOUR PRODUCT'S MOUTH.
⭐     ⭐ Suggesting a defamatory or hateful completion for
⭐     someone's name is a real, repeated, and litigated
⭐     failure mode.
⭐   ⇒ ⭐ A blocklist, ⭐ classifier filtering at ***build***
⭐     time (⭐⭐ NOT AT QUERY TIME — YOUR 10 ms BUDGET CANNOT
⭐     RUN A MODEL), ⭐ suppression around names and protected
⭐     attributes, ⭐⭐ AND A FAST MANUAL REMOVAL PATH THAT DOES
⭐     NOT REQUIRE A FULL REBUILD. ⭐ That last one is the
⭐     operational requirement people forget.
```

# Part 5 — ⭐ Typo tolerance and personalisation, cheaply

```
⭐⭐ TYPOS — ⭐ and the constraint is the 10 ms budget:
⭐   ⭐ ❌ Edit distance against millions of terms at query
⭐     time. ⭐⭐ FAR TOO SLOW.
⭐   ⭐ ✔ ⭐⭐ ***PRECOMPUTE THE COMMON MISSPELLINGS.*** ⭐ Mine
⭐     them from real behaviour: a query, no clicks, then a
⭐     similar query 3 seconds later with clicks ⇒ ⭐⭐ THE FIRST
⭐     WAS A TYPO FOR THE SECOND. ⭐ Add it as an alias.
⭐   ⇒ ⭐⭐ THIS IS ***BETTER THAN EDIT DISTANCE***, BECAUSE IT
⭐     CAPTURES REAL CONFUSIONS — WRONG-KEYBOARD-LAYOUT,
⭐     TRANSLITERATION, BRAND MISSPELLINGS — THAT NO STRING
⭐     METRIC PREDICTS.
⭐   ⭐ ✔ A small ***symmetric-delete*** (SymSpell-style) index
⭐     for distance-1 corrections is a cheap fallback, ⭐ built
⭐     offline.

⭐⭐ PERSONALISATION — ⭐ and the honest cost:
⭐   ⭐ ⭐⭐ A FULLY PERSONALISED TOP-K CANNOT BE PRECOMPUTED PER
⭐     USER — that is users × prefixes, which does not fit.
⭐   ⇒ ⭐ THE CHEAP ANSWER: ⭐⭐ FETCH THE GLOBAL TOP-20, THEN
⭐     RE-RANK USING A ***SMALL*** PER-USER SIGNAL (their recent
⭐     searches) HELD IN A COMPACT PER-USER BLOB.
⭐   ⇒ ⭐⭐ RETRIEVE-THEN-RERANK ***AGAIN*** — Days 293, 337,
⭐     351, 355 and now here. ⭐ Five appearances, one shape:
⭐     ***a cheap wide filter followed by an expensive narrow
⭐     rank.*** ⭐ Naming that pattern across domains is worth
⭐     more than any single design.
⭐   ⭐ ⭐⭐ AND THE PRODUCT CAVEAT: THE USER'S OWN RECENT
⭐     SEARCHES ARE OFTEN THE ***BEST*** SUGGESTIONS AND COST
⭐     NOTHING TO SERVE — ⭐ but they must be
⭐     device/session-scoped and easy to clear, because
⭐     suggesting someone's private search on a shared device is
⭐     a genuine harm.
```

# Part 6 — ⭐⭐ Serving: sharding and caching

```
⭐⭐ SHARD BY ***PREFIX***, not by term.
⭐   ⭐ A request carries exactly one prefix ⇒ ⭐⭐ IT ROUTES TO
⭐     EXACTLY ONE SHARD. ⭐ No scatter-gather, ever.
⭐   ⇒ ⭐⭐ AND THAT IS THE PROPERTY THE LATENCY BUDGET NEEDS,
⭐     BECAUSE A SCATTER-GATHER IS AS SLOW AS ITS SLOWEST SHARD
⭐     (Day 329) AND YOU HAVE 10 MILLISECONDS.
⭐   ⭐ Shard by the first 1–2 characters, ⭐⭐ WEIGHTED BY
⭐     TRAFFIC: prefixes starting with "a" are far busier than
⭐     "z", so ***equal alphabet ranges give unequal load.***

⭐⭐ CACHING:
⭐   ⭐ ⭐⭐ THE PREFIX DISTRIBUTION IS EXTREMELY SKEWED: SHORT
⭐     PREFIXES ARE ASKED CONSTANTLY, AND EVERY LONGER QUERY
⭐     PASSES THROUGH THEM. ⭐ A tiny cache of 1–3 character
⭐     prefixes serves a large share of all traffic.
⭐   ⭐ ⭐⭐ AND THE EDGE OPTION: SHORT-PREFIX RESULTS ARE
⭐     ***PUBLIC AND IDENTICAL FOR EVERYONE***, so they can be
⭐     CDN-cached with a 60-second TTL — ⭐⭐ WHICH REMOVES THE
⭐     MAJORITY OF REQUESTS FROM YOUR ORIGIN ENTIRELY AND CUTS
⭐     THE NETWORK HALF OF THE LATENCY BUDGET TOO.
⭐   ⇒ ⭐ Personalised results are `private, no-store`
⭐     (Day 327) — ⭐⭐ AND MIXING THE TWO ON ONE ENDPOINT IS
⭐     THE ONE-LINE BREACH, SO USE SEPARATE PATHS.

⭐⭐ AND THE TRANSPORT DETAIL WORTH ONE LINE: ⭐⭐ AT 5,000 RPS
⭐   OF TINY RESPONSES, CONNECTION SETUP DOMINATES. ⭐ Keep-alive
⭐   and HTTP/2 matter more here than in almost any other
⭐   design, ⭐ and the response should be a few hundred bytes,
⭐   not a wrapped envelope with metadata.
```

# Part 7 — ⭐ Bottlenecks and the summary

```
⭐⭐ WHAT BREAKS:
⭐   ① ⭐⭐ THE BUILD JOB, NOT THE SERVE PATH. ⭐ Computing
⭐      top-K for every prefix over billions of events is the
⭐      expensive part, ⭐ and it must finish inside its
⭐      schedule or freshness silently degrades. ⭐⭐ ALERT ON
⭐      BUILD DURATION AND ON INDEX AGE.
⭐   ② ⭐ Memory per node ⇒ prefix-length limits, ids not
⭐      strings, ⭐ traffic-based pruning.
⭐   ③ ⭐ Hot shard for common prefixes ⇒ ⭐⭐ REPLICATE THE
⭐      SHARD; IT IS READ-ONLY, SO REPLICATION IS FREE.
⭐   ④ ⭐ The hot-layer streaming job ⇒ it is a small count over
⭐      a short window, ⭐ so it is cheap by construction.

⭐⭐ WHAT TO MEASURE:
⭐   ⭐ p99 latency; ⭐ ⭐⭐ SUGGESTION CLICK-THROUGH RATE (the
⭐     product metric); ⭐ ⭐⭐ COVERAGE (Part 4's anti-ossify
⭐     metric); ⭐ index age; ⭐ zero-result prefixes.

⭐⭐ THE SUMMARY:
⭐   ***"It looks like a data-structures question and it's a
⭐      latency-budget question: fifty milliseconds end to end
⭐      and a request per keystroke, which is about fifteen
⭐      times the traffic of search itself. So nothing is
⭐      computed at request time — the top-K is precomputed per
⭐      prefix, and a lookup is a hash-map hit rather than a
⭐      subtree traversal. The interesting design is the write
⭐      path: a daily base index plus a hot layer refreshed
⭐      every few minutes, merged at query time because merging
⭐      twenty elements is free. Shard by prefix so a request
⭐      touches exactly one shard, CDN-cache short prefixes
⭐      because they're identical for everyone, and keep the
⭐      personalised path on a separate endpoint. And the two
⭐      things I'd watch are the popularity feedback loop, which
⭐      ossifies the top ten, and the safety layer, because
⭐      autocomplete puts words in your product's mouth."***
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Traversing the trie subtree at query time | The subtree under "a" has millions of terms. Precompute top-K per node |
| ⭐⭐ Anything touching disk on the request path | 10 ms of server budget. It must be in memory |
| ⭐ Materialising every prefix length | ~100 GB. Cap at 4–5 characters and store ids, not strings |
| ⭐⭐ A single daily rebuild | Trending terms take a day to appear, which is useless for news |
| ⭐ Mutating the live index | Build new and swap a pointer — one procedure for rebuild, rollback and corruption |
| ⭐⭐ Ranking on raw frequency | You'll suggest popular queries that return nothing, forever |
| ⭐⭐ Ignoring the popularity feedback loop | The top ten ossify, click-through looks fine, and the system is quietly useless |
| ⭐ No coverage metric | The only thing that detects the ossification |
| ⭐⭐ Safety filtering at query time | Your budget cannot run a classifier. Filter at build, plus a fast manual removal path |
| ⭐ Edit distance at query time | Far too slow. Mine real misspellings from behaviour — and it's more accurate anyway |
| ⭐⭐ Sharding by term rather than prefix | A scatter-gather is as slow as its slowest shard, and you have 10 ms |
| ⭐ Equal alphabet ranges per shard | "a" is far busier than "z". Weight by traffic |
| ⭐⭐ One endpoint for public and personalised results | A cacheable path serving personal data is the one-line breach |
| ⭐ No client debounce | 50–70% of your traffic is avoidable at zero cost to perceived speed |

## Interview questions

**1. "What's the actual constraint here?"**
> ⭐⭐ Latency, and volume as a consequence. **Fifty milliseconds end to end including the network leaves
> ten to twenty milliseconds of server time**, so nothing touching disk can be on the request path.
> ⭐⭐ And a request per keystroke means **autocomplete carries about fifteen times the traffic of search
> itself** — a hundred and fifty million requests a day for ten million searches. ⭐ Which is also why
> I'd start with the client: a hundred-millisecond debounce removes half to seventy percent of that for
> free.

**2. "Trie or hash map?"**
> ⭐ A trie is the textbook answer, and the naive version fails because collecting the subtree under "a"
> means millions of terms. ⭐ So you store the top-K at every node, and then ⭐⭐ **the lookup never
> traverses — it walks the prefix and returns a list.** ⭐ At which point I'd ask what the trie is still
> buying: **since I only ever look up whole prefixes, a hash map from prefix to top-K is simpler, O(1),
> and shards trivially.** ⭐ I'd pick the structure for the access pattern rather than the name.

**3. "How do trending terms appear within minutes?"**
> ⭐⭐ Two layers. A base index rebuilt daily from full history — large, stable, high quality — and a
> **hot layer refreshed every few minutes from a streaming count over the last hour**, small and
> volatile. ⭐ Merge at query time, which costs microseconds because both lookups are O(1) and the merge
> is twenty elements. ⭐ It's the batch-plus-speed-layer shape, and it's right here precisely because
> the merge is so cheap.

**4. "How do you rank?"**
> ⭐ Frequency, time-decayed recency, ⭐⭐ **success — because a popular query that always returns
> nothing should never be suggested, and frequency alone will suggest it forever** — and context.
> ⭐⭐ Then the problem that defines the system: **the popularity feedback loop.** Suggested terms get
> clicked, which makes them more suggested, so the top ten ossify. ⭐ Fixes: weight typed queries
> differently from suggested-and-clicked ones, inject a little exploration, ⭐⭐ **and measure coverage
> — what fraction of distinct queries are ever suggested — because click-through looks great while the
> system is quietly useless.**

**5. "Typo tolerance in ten milliseconds?"**
> ⭐ Not by computing edit distance — far too slow. ⭐⭐ **Mine real misspellings from behaviour: a query
> with no clicks, then a similar query three seconds later with clicks, means the first was a typo for
> the second.** ⭐ Add it as an alias at build time. ⭐⭐ That's better than any string metric, because
> it captures wrong-keyboard-layout, transliteration and brand misspellings that edit distance never
> predicts. ⭐ A small offline symmetric-delete index handles the rest.

**6. "How do you shard and cache it?"**
> ⭐ Shard by prefix, so **a request routes to exactly one shard and there is never a scatter-gather** —
> which matters because a scatter is as slow as its slowest shard and I have ten milliseconds. ⭐ Weight
> the ranges by traffic, since "a" is far busier than "z". ⭐⭐ Then the cheap win: **short-prefix
> results are identical for everyone, so they're CDN-cacheable with a sixty-second TTL**, which removes
> most requests from the origin and cuts the network half of the budget too. ⭐ Personalised results go
> on a separate `no-store` path, because mixing them on one endpoint is the one-line breach.

```

⭐    generated Zipf distribution). ⭐⭐ MEASURE MEMORY AT
⭐    PREFIX LENGTHS 3, 5 AND UNLIMITED.
⭐ ② Serve it and measure p99. ⭐⭐ THEN DELIBERATELY MOVE IT TO
⭐    A DATABASE QUERY AND MEASURE AGAIN. That gap is the day.
```

## 🎙️ Articulation drill

**Two minutes.** Reframe it immediately: **this looks like a data-structures question and it's a
latency-budget question** — fifty milliseconds end to end leaves about ten of server time, so nothing
can touch disk on the request path, and a request per keystroke means **autocomplete carries roughly
fifteen times the traffic of search itself.** Start with the free half: **a hundred-millisecond client
debounce removes half your traffic at no cost to perceived speed.** Then the structure: a trie is the
textbook answer, but the naive traversal collects millions of terms under "a", **so you precompute the
top-K at every node — and once the lookup never traverses, a hash map from prefix to top-K is simpler
and shards better**, which is choosing the structure for the access pattern rather than reciting one.
Then say where the real design is: **the write path.** A daily base index plus a hot layer refreshed
every few minutes, merged at query time because merging twenty elements is free. Cover ranking honestly
— **frequency, decay, success, context** — and name the failure that defines the system: **the
popularity feedback loop, where suggested terms become more suggested, the top ten ossify, click-through
still looks great, and coverage is the only metric that notices.** Close on two cheap wins and one
obligation: **shard by prefix so a request touches exactly one shard; CDN-cache short prefixes because
they're identical for everyone; and filter for safety at build time, because autocomplete puts words in
your product's mouth and you cannot run a classifier in ten milliseconds.**
