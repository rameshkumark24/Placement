# Day 368 🚦

**P-368** · 🚦 **CI/CD concepts** — ⭐⭐ the pipeline as a quality gate

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a pipeline's job is to be the cheapest possible place to discover that
> something is wrong, and every decision in it follows from one number — how long a developer waits
> for feedback — because a gate that takes forty minutes gets bypassed, and a bypassed gate is worse
> than no gate at all.**

---

# Part 1 — ⭐⭐ Three words that get used interchangeably

```
⭐⭐ ***CONTINUOUS INTEGRATION*** — everyone merges to trunk
⭐   frequently, and every merge is verified automatically.
⭐   ⇒ ⭐⭐ THE POINT IS NOT THE BUILD SERVER. ⭐ It is
⭐     ***integrating often enough that conflicts and
⭐     incompatibilities are small.*** ⭐ A team running Jenkins
⭐     on six-week feature branches is not doing CI.

⭐⭐ ***CONTINUOUS DELIVERY*** — every commit that passes is
⭐   ***deployable***, and deploying is a button.
⭐⭐ ***CONTINUOUS DEPLOYMENT*** — that button presses itself.

⭐   ⇒ ⭐⭐ THE GAP BETWEEN DELIVERY AND DEPLOYMENT IS ***TRUST
⭐     IN THE TESTS***, NOT TOOLING. ⭐ Teams that cannot deploy
⭐     automatically almost always have a test suite they do not
⭐     believe, ⭐⭐ AND THE FIX IS TESTS, NOT A BETTER RELEASE
⭐     PROCESS.

⭐⭐ AND THE FOUR NUMBERS (DORA) THAT MAKE THIS MEASURABLE
⭐   RATHER THAN CULTURAL:
⭐   ⭐ ***DEPLOYMENT FREQUENCY*** · ***LEAD TIME FOR CHANGES***
⭐   ⭐ ***CHANGE FAILURE RATE*** · ***TIME TO RESTORE***
⭐   ⇒ ⭐⭐ THE COUNTER-INTUITIVE FINDING WORTH KNOWING:
⭐     ***SPEED AND STABILITY MOVE ***TOGETHER***, NOT AGAINST
⭐     EACH OTHER.*** ⭐ Teams that deploy more often have
⭐     ***lower*** failure rates — because small changes are
⭐     easier to verify and easier to revert.
⭐   ⇒ ⭐ Which reframes the whole argument: ⭐⭐ "WE DEPLOY
⭐     CAREFULLY, ONCE A MONTH" IS NOT A SAFETY POSITION, IT IS
⭐     A ***RISK CONCENTRATION*** POSITION.
```

# Part 2 — ⭐⭐ The feedback-time budget

```
⭐⭐ THE ONE NUMBER EVERYTHING ELSE FOLLOWS FROM:
⭐   ⭐ ⭐⭐ UNDER 10 MINUTES ⇒ the developer waits, ⭐ stays in
⭐     context, fixes it immediately.
⭐   ⭐ ⭐⭐ 10–20 MINUTES ⇒ they switch tasks. ⭐ Fixing costs a
⭐     context switch each way.
⭐   ⭐ ⭐⭐ OVER 20 MINUTES ⇒ they stop watching, ⭐ start
⭐     batching changes, ⭐⭐ AND THE BATCHING DEFEATS CI'S ENTIRE
⭐     PREMISE.
⭐   ⭐ ⭐⭐ OVER 40 MINUTES ⇒ people start merging on red and
⭐     "fixing forward", ⭐ and the gate has become decorative.

⭐⭐ SO THE PIPELINE IS ***TIERED*** — this is the structural
⭐   answer:
⭐   ⭐ ***TIER 1 — ON EVERY PUSH, < 5 MIN, BLOCKING***
⭐     ⭐ lint · format check · type check · unit tests ·
⭐       ⭐⭐ SECRET SCAN.
⭐   ⭐ ***TIER 2 — ON EVERY PR, < 15 MIN, BLOCKING***
⭐     ⭐ integration tests against real dependencies (Day 365) ·
⭐       build the image · scan it · migration check.
⭐   ⭐ ***TIER 3 — POST-MERGE OR NIGHTLY, NON-BLOCKING***
⭐     ⭐ end-to-end · load tests · mutation tests ·
⭐       ⭐⭐ FULL DEPENDENCY AUDIT.
⭐   ⇒ ⭐⭐ THE RULE: ***A SLOW CHECK EITHER GETS FASTER OR MOVES
⭐     TO A LATER TIER. IT DOES NOT GET TO SLOW DOWN TIER 1.***

⭐⭐ AND THE FIVE LEVERS FOR MAKING TIER 1 FAST:
⭐   ① ⭐⭐ PARALLELISE — `pytest -n auto`, ⭐ and split the suite
⭐      across runners by ***timing data***, not alphabetically.
⭐   ② ⭐ Cache dependencies (Day 369), ⭐ keyed on the lockfile
⭐      hash.
⭐   ③ ⭐⭐ RUN ONLY WHAT CHANGED — path filters, ⭐ or
⭐      test-impact analysis in a monorepo.
⭐   ④ ⭐ Fail fast — ⭐⭐ LINT BEFORE TESTS, BECAUSE A FORMATTING
⭐      FAILURE AFTER TWELVE MINUTES OF TESTS IS AN INSULT.
⭐   ⑤ ⭐⭐ DELETE OR FIX THE SLOWEST 1% OF TESTS. ⭐ Profile the
⭐      suite; ⭐ in most Python projects a handful of tests are
⭐      a large share of the runtime, ⭐ usually because they
⭐      `sleep`, hit the network, or rebuild fixtures per test.
```

# Part 3 — ⭐⭐ What belongs in the pipeline

```
⭐⭐ THE GATES, IN THE ORDER THEY SHOULD RUN — ⭐ cheapest and
⭐   most-likely-to-fail first:
⭐   ① ⭐ ***FORMAT + LINT*** (`ruff`) — seconds.
⭐   ② ⭐⭐ ***SECRET SCAN*** (gitleaks) — ⭐⭐ SECONDS, AND IT
⭐      CATCHES THE INCIDENT THAT COSTS THE MOST. ⭐ A leaked key
⭐      is exploited in minutes and needs no exploit at all.
⭐   ③ ⭐ ***TYPE CHECK*** (`mypy --strict`) — ⭐⭐ A WHOLE CLASS
⭐      OF PYTHON BUG THAT TESTS WOULD OTHERWISE HAVE TO CATCH.
⭐   ④ ⭐ ***UNIT TESTS*** with coverage — ⭐⭐ ON THE ***PATCH***,
⭐      NOT GLOBALLY (Day 281): a global threshold punishes
⭐      whoever touches legacy code and lets new untested code
⭐      through.
⭐   ⑤ ⭐ ***INTEGRATION TESTS*** against real Postgres/Redis.
⭐   ⑥ ⭐⭐ ***MIGRATION CHECKS*** — ⭐ does it apply to a copy of
⭐      the production schema? ⭐⭐ DOES IT TAKE AN `ACCESS
⭐      EXCLUSIVE` LOCK FOR MORE THAN N SECONDS? ⭐ Is there a
⭐      model change with no migration? ⭐ This gate is rare and
⭐      it prevents the most expensive incidents.
⭐   ⑦ ⭐ ***BUILD THE IMAGE, SCAN IT, SIGN IT*** (Days 362–363).
⭐   ⑧ ⭐⭐ ***AUTHORISATION-MATRIX TEST*** — for every endpoint,
⭐      assert the wrong role gets 403 (Day 281). ⭐ It is
⭐      generated, not hand-written, ⭐⭐ SO A NEW ENDPOINT WITH
⭐      NO AUTH CHECK ***FAILS THE BUILD*** RATHER THAN SHIPPING.

⭐⭐ AND WHAT MUST ***NEVER*** BE IN A PIPELINE:
⭐   ⭐ ⭐⭐ MANUAL STEPS. ⭐ "Then Priya runs the migration" is
⭐     not a pipeline, it is a ritual with YAML attached.
⭐   ⭐ ⭐⭐ SECRETS IN LOGS, ⭐ in build args (Day 362), ⭐ or in
⭐     `env` echoed by a debug step.
⭐   ⭐ ⭐⭐ LONG-LIVED CLOUD CREDENTIALS — use OIDC (Day 369).
⭐   ⭐ ⭐⭐ ANYTHING NON-DETERMINISTIC AS A ***BLOCKING*** GATE.
⭐     ⭐ A flaky test that blocks merges teaches the team to
⭐     re-run until green, ⭐⭐ WHICH TRAINS THEM TO IGNORE ***ALL***
⭐     FAILURES.
```

# Part 4 — ⭐⭐ Flaky tests: the arithmetic

```
⭐⭐ THE MULTIPLICATION PEOPLE NEVER DO:
⭐   ⭐ A suite of 500 tests, each passing 99.9% of the time.
⭐   ⭐ P(all pass) = 0.999^500 = ⭐⭐ 0.606.
⭐   ⇒ ⭐⭐ ***FOUR RUNS IN TEN FAIL, AND NOTHING IS BROKEN.***
⭐   ⭐ At 99.99% each: 0.951 ⇒ ⭐ one in twenty still fails.
⭐   ⇒ ⭐⭐ SO "MOSTLY RELIABLE" TESTS PRODUCE AN UNRELIABLE
⭐     SUITE, AND THE EFFECT IS MULTIPLICATIVE RATHER THAN
⭐     ADDITIVE. ⭐ This is the argument that wins the "is
⭐     flakiness worth fixing?" conversation, and it is
⭐     arithmetic rather than opinion.

⭐⭐ THE COST IS NOT THE RE-RUN. ⭐⭐ IT IS THAT PEOPLE STOP
⭐   READING FAILURES. ⭐ Once "just re-run it" is the reflex,
⭐   ⭐⭐ A ***REAL*** FAILURE GETS RE-RUN TOO, AND SHIPS.

⭐⭐ THE FIVE CAUSES IN PYTHON, IN ORDER OF FREQUENCY:
⭐   ① ⭐⭐ ***SHARED STATE BETWEEN TESTS*** — a module-level
⭐      cache, a singleton, a database row a previous test left.
⭐      ⭐ Symptom: passes alone, fails in the suite.
⭐      ⇒ ⭐⭐ FIND IT WITH `pytest -p no:randomly` OFF —
⭐        i.e. ***RUN IN RANDOM ORDER DELIBERATELY***
⭐        (`pytest-randomly`). ⭐ If random order breaks it, you
⭐        have order dependence.
⭐   ② ⭐ ***TIME*** — `datetime.now()`, timezone, ⭐⭐ AND TESTS
⭐      THAT FAIL AT MIDNIGHT OR ON 29 FEBRUARY. ⭐ Freeze it.
⭐   ③ ⭐ ***CONCURRENCY*** — a race the test sometimes wins.
⭐      ⭐⭐ AND THIS ONE IS OFTEN A REAL BUG, NOT A TEST BUG.
⭐   ④ ⭐ ***EXTERNAL DEPENDENCIES*** — a real network call in a
⭐      unit test. ⭐ Never.
⭐   ⑤ ⭐ ***RESOURCE CONTENTION UNDER `-n auto`*** — two workers
⭐      using the same port, temp file or database name.
⭐      ⭐⭐ EACH WORKER NEEDS ITS OWN SCHEMA OR DATABASE.

⭐⭐ THE POLICY THAT WORKS:
⭐   ⭐ ⭐⭐ QUARANTINE, DO NOT DELETE AND DO NOT IGNORE. ⭐ Mark
⭐     it, move it out of the blocking suite, ⭐⭐ AND OPEN A
⭐     TICKET WITH AN OWNER AND A DATE.
⭐   ⭐ ⭐⭐ TRACK FLAKE RATE AS A METRIC. ⭐ A team that cannot
⭐     say what its flake rate is has one.
⭐   ⭐ ⭐⭐ AND NEVER ADD AN AUTOMATIC RETRY TO THE WHOLE SUITE.
⭐     ⭐ It converts a visible problem into an invisible one,
⭐     and the suite gets slower and less trustworthy at once.
```

# Part 5 — ⭐⭐ Trunk-based development and the branching argument

```
⭐⭐ ***LONG-LIVED BRANCHES ARE THE ENEMY OF CI BY DEFINITION.***
⭐   ⭐ A two-week branch means two weeks of unintegrated
⭐     change; ⭐⭐ THE MERGE IS A BIG-BANG EVENT AND THE
⭐     CONFLICTS ARE PROPORTIONAL TO THE DURATION.
⭐   ⇒ ⭐ Short-lived branches (hours to two days), merged to
⭐     trunk, ⭐ with trunk always releasable.

⭐⭐ AND THE OBJECTION, ANSWERED PROPERLY: ⭐⭐ "HOW DO I MERGE AN
⭐   UNFINISHED FEATURE?"
⭐   ① ⭐⭐ ***FEATURE FLAGS*** — merge the code, keep it off.
⭐      ⭐ Deploy ≠ release, ⭐⭐ WHICH IS THE SINGLE MOST USEFUL
⭐      DISTINCTION IN DELIVERY.
⭐   ② ⭐ ***BRANCH BY ABSTRACTION*** — introduce the interface,
⭐      migrate callers incrementally, delete the old path.
⭐   ③ ⭐ ***KEYSTONE INTERCEPT*** — build everything, wire up
⭐      the entry point last.
⭐   ⇒ ⭐⭐ AND THE FLAG DEBT WARNING: ***A FEATURE FLAG IS A
⭐     BRANCH IN YOUR CODE THAT LIVES FOREVER UNLESS SOMEONE
⭐     REMOVES IT.*** ⭐ Every flag needs an owner and an expiry,
⭐     ⭐ and a stale-flag report; ⭐⭐ OTHERWISE YOU HAVE TRADED
⭐     MERGE DEBT FOR CONDITIONAL DEBT AND THE SECOND IS HARDER
⭐     TO SEE.

⭐⭐ THE MERGE MECHANICS THAT MATTER:
⭐   ⭐ ⭐⭐ REQUIRE BRANCHES TO BE UP TO DATE BEFORE MERGE, ⭐ or
⭐     two independently-green PRs can merge into a broken
⭐     trunk. ⭐⭐ THIS IS THE "SEMANTIC CONFLICT" — NEITHER
⭐     BRANCH CONFLICTS TEXTUALLY, AND THE COMBINATION IS
⭐     BROKEN.
⭐   ⭐ ⭐ A merge queue solves this without serialising humans.
⭐   ⭐ ⭐⭐ AND PROTECT TRUNK: NO DIRECT PUSHES, REQUIRED
⭐     CHECKS, REQUIRED REVIEW. ⭐ Mechanisms, not policies
⭐     (Day 362's recurring theme).
```

# Part 6 — ⭐ Build once, promote the artefact

```
⭐⭐ THE RULE (Day 283, and this is where it is enforced):
⭐   ***BUILD ONE ARTEFACT. PROMOTE ***THAT DIGEST*** THROUGH
⭐      ENVIRONMENTS. NEVER REBUILD PER ENVIRONMENT.***

⭐⭐ WHY REBUILDING IS WRONG — ⭐ three reasons:
⭐   ① ⭐⭐ THE STAGING IMAGE AND THE PRODUCTION IMAGE ARE
⭐      DIFFERENT BYTES, SO ***STAGING PROVED NOTHING ABOUT
⭐      PRODUCTION.***
⭐   ② ⭐ A dependency published between the two builds changes
⭐      the result (Day 362's tag lie).
⭐   ③ ⭐ It is slower, and the second build can fail after the
⭐      first passed, which is baffling.

⭐⭐ SO WHAT DIFFERS BETWEEN ENVIRONMENTS? ⭐⭐ CONFIGURATION
⭐   ONLY, INJECTED AT RUN TIME (Day 364).
⭐   ⇒ ⭐ And the test: ⭐⭐ ***CAN I RUN THE PRODUCTION IMAGE
⭐     LOCALLY BY CHANGING ONLY ENVIRONMENT VARIABLES?*** ⭐ If
⭐     not, something is baked in.

⭐⭐ THE PROMOTION PIPELINE:
⭐   ⭐ build → test → push (tag: `git-<sha>`) → deploy to
⭐     staging by ***digest*** → smoke tests → ⭐⭐ DEPLOY THE
⭐     ***SAME DIGEST*** TO PRODUCTION.
⭐   ⭐ ⭐⭐ AND THE DEPLOYED DIGEST IS RECORDED SOMEWHERE
⭐     QUERYABLE, ⭐ so "what is running right now, and which
⭐     commit is it?" is one lookup rather than an
⭐     investigation.
```

# Part 7 — ⭐ The pipeline as a communication device

```
⭐⭐ A GOOD PIPELINE TELLS YOU ***WHAT IS WRONG***, NOT THAT
⭐   SOMETHING IS.
⭐   ⭐ ⭐⭐ NAME THE JOBS AFTER WHAT THEY PROTECT: "auth matrix",
⭐     "migration lock duration", "image CVEs" — ⭐ not "job-3".
⭐   ⭐ ⭐⭐ FAIL WITH THE ***FIX*** IN THE MESSAGE. ⭐ "Coverage
⭐     on changed lines is 62%, below 80%. Uncovered:
⭐     app/billing/refund.py:44-71" beats "coverage check
⭐     failed."
⭐   ⭐ ⭐⭐ SURFACE THE DIFF, NOT THE ABSOLUTE. ⭐ "This PR adds
⭐     40 MB to the image" is actionable; "image is 230 MB" is
⭐     not.
⭐   ⭐ Annotate the PR rather than burying it in a log.

⭐⭐ AND THE FOUR PIPELINE METRICS WORTH TRACKING:
⭐   ⭐ ⭐⭐ p50 AND p95 DURATION — ⭐ p95 is what people actually
⭐     experience and remember.
⭐   ⭐ ⭐⭐ FLAKE RATE (failures that pass on re-run with no
⭐     change).
⭐   ⭐ Queue time — ⭐⭐ WAITING FOR A RUNNER IS INDISTINGUISHABLE
⭐     FROM A SLOW PIPELINE TO THE PERSON WAITING.
⭐   ⭐ ⭐⭐ CACHE HIT RATE — ⭐ a silent regression here doubles
⭐     everyone's wait and nobody attributes it.

⭐⭐ ⇒ THE CLOSING PRINCIPLE: ***THE PIPELINE IS INFRASTRUCTURE
⭐   YOUR WHOLE TEAM USES DOZENS OF TIMES A DAY. IT DESERVES
⭐   THE SAME OWNERSHIP, MONITORING AND ON-CALL ATTENTION AS A
⭐   PRODUCTION SERVICE*** — ⭐ and treating it as somebody's
⭐   side project is why most pipelines are slow.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ A 40-minute blocking pipeline | People merge on red and fix forward. The gate becomes decorative |
| ⭐⭐ Tolerating flaky tests | 500 tests at 99.9% each means four runs in ten fail with nothing broken |
| ⭐⭐ Auto-retrying the whole suite | Converts a visible problem into an invisible one, and slows it too |
| ⭐ Global coverage thresholds | Punishes whoever touches legacy code and lets new untested code through |
| ⭐ Lint after tests | A formatting failure after twelve minutes is an insult |
| ⭐⭐ Rebuilding per environment | Staging proved nothing about production — different bytes |
| ⭐⭐ Manual steps in the pipeline | "Then Priya runs the migration" is a ritual with YAML attached |
| ⭐⭐ Long-lived cloud credentials in CI | Use OIDC. A leaked static key is exploited in minutes |
| ⭐ No secret scanning | The cheapest gate that prevents the most expensive incident |
| ⭐ Long-lived branches | The merge is a big-bang event and conflicts scale with duration |
| ⭐⭐ Feature flags with no owner or expiry | You traded merge debt for conditional debt, and it's harder to see |
| ⭐ Not requiring branches to be up to date | Two green PRs merge into a broken trunk — the semantic conflict |
| ⭐ Jobs named "job-3" | A failure tells you something is wrong rather than what |
| ⭐⭐ Treating the pipeline as nobody's job | It's infrastructure the team uses dozens of times a day |

## Interview questions

**1. "What makes a good pipeline?"**
> ⭐⭐ One number drives everything: **how long a developer waits.** Under ten minutes they stay in
> context; over twenty they batch changes, which defeats CI's premise; over forty they merge on red.
> ⭐ So it's tiered: **lint, types, unit tests and a secret scan on every push in under five minutes;
> integration tests, image build and scan on every PR under fifteen; end-to-end, load and mutation
> tests post-merge or nightly.** ⭐⭐ And the rule: **a slow check either gets faster or moves to a later
> tier — it doesn't get to slow down tier one.**

**2. "How bad are flaky tests really?"**
> ⭐⭐ Multiplicatively bad, and this is arithmetic rather than opinion: **five hundred tests each
> passing 99.9% of the time gives a 60% chance the suite passes — four runs in ten fail with nothing
> broken.** ⭐ And the cost isn't the re-run, ⭐⭐ **it's that "just re-run it" becomes the reflex, so a
> real failure gets re-run too and ships.** ⭐ Policy: quarantine with an owner and a date, track flake
> rate as a metric, and never auto-retry the whole suite — that converts a visible problem into an
> invisible one.

**3. "Why build once and promote?"**
> ⭐⭐ Because if you rebuild per environment, **staging and production are different bytes, so staging
> proved nothing about production** — and a dependency published between the two builds changes the
> result. ⭐ So: build one image, push it, deploy that **digest** to staging, smoke test, deploy the same
> digest to production. ⭐ The only thing that differs between environments is injected configuration,
> ⭐⭐ and the test is **whether you can run the production image locally by changing only environment
> variables.**

**4. "How do you do CI with unfinished features?"**
> ⭐ Short-lived branches and **feature flags — merge the code, keep it off**, because deploy and release
> are different events and that's the most useful distinction in delivery. ⭐ Branch by abstraction for
> larger migrations; keystone intercept, wiring the entry point last. ⭐⭐ And the warning: **a flag is a
> branch in your code that lives forever unless someone removes it** — every flag needs an owner, an
> expiry and a stale-flag report, or you've traded merge debt for conditional debt that's harder to see.

**5. "Two PRs are both green and trunk breaks. Why?"**
> ⭐⭐ A **semantic conflict**: neither branch conflicts textually, and the combination is broken —
> one renames a function, the other adds a caller. ⭐ Requiring branches to be up to date before merge
> catches it, and a merge queue does that without serialising humans. ⭐ It's the same reason trunk needs
> protection as a mechanism — no direct pushes, required checks — rather than as a policy people are
> asked to follow.

**6. "What gates would you add that most teams don't have?"**
> ⭐ Three. ⭐⭐ **A migration check** — does it apply to a copy of the production schema, and does it
> hold an `ACCESS EXCLUSIVE` lock for more than a few seconds — because that gate prevents the most
> expensive incidents. ⭐⭐ **A generated authorisation-matrix test**, so a new endpoint with no auth
> check fails the build rather than shipping. ⭐ And **secret scanning**, which takes seconds and
> prevents the incident with the shortest time-to-exploit, because a leaked key needs no exploit at all.

## 🎙️ Articulation drill

**Two minutes.** Start from the one number: **a pipeline's job is to be the cheapest place to discover
something is wrong, and everything follows from how long a developer waits.** Under ten minutes they
stay in context; over twenty they batch changes, which defeats CI entirely; over forty they merge on
red and the gate is decorative. So it's tiered — **lint, types, unit tests and a secret scan under five
minutes on every push; integration and image scanning under fifteen on every PR; end-to-end and load
tests nightly** — with the rule that a slow check gets faster or moves tier, never slows tier one. Then
flakiness, and give the arithmetic because it ends the argument: **five hundred tests at 99.9% each
means four runs in ten fail with nothing broken** — and the cost isn't the re-run, **it's that "just
re-run it" becomes the reflex and a real failure ships.** Quarantine with an owner, track flake rate,
never auto-retry. Then the artefact rule: **build once and promote the digest, because rebuilding means
staging and production are different bytes and staging proved nothing.** Close on two things most teams
miss: **a migration check that fails on a long exclusive lock, and a generated authorisation matrix so
a new endpoint with no auth check fails the build** — and on the framing that fixes slow pipelines,
which is that **this is infrastructure the whole team uses dozens of times a day, and it deserves the
ownership and monitoring of a production service.**
