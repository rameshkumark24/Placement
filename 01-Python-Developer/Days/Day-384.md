# Day 384 🧱

**P-384** · 🧱 **VPC II** — security groups, NACLs, endpoints, ⭐⭐ and debugging connectivity

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a security group is a stateful allow-list on an interface and a NACL is a
> stateless ordered rule list on a subnet — and the difference between "stateful" and "stateless" is
> exactly the bug where your traffic goes out and never comes back.**

# Part 1 — Security groups, and the feature nobody uses

```
⭐⭐ FIVE PROPERTIES, AND EVERY ONE OF THEM MATTERS:
⭐ ① ⭐⭐ ***STATEFUL.*** ⭐ Allow the inbound request and the
⭐    response is automatically permitted outbound. ⭐ You never
⭐    write a return rule. ⭐⭐ THIS IS WHY SECURITY GROUPS ARE
⭐    EASY AND NACLs ARE NOT.
⭐ ② ⭐⭐ ***ALLOW-ONLY. THERE IS NO DENY RULE.*** ⭐ You cannot
⭐    express "everyone except this IP" in a security group.
⭐    ⭐ If you need a deny, ⭐⭐ THAT IS THE ONE LEGITIMATE REASON
⭐    TO REACH FOR A NACL.
⭐ ③ ⭐ DEFAULT INBOUND = nothing. ⭐ DEFAULT OUTBOUND = all.
⭐ ④ ⭐⭐ ***ATTACHED TO AN ENI, NOT TO AN INSTANCE.*** ⭐ Multiple
⭐    groups on one interface are evaluated as a ***union*** —
⭐    ⭐⭐ SO ADDING A GROUP CAN ONLY EVER OPEN MORE. ⭐ There is no
⭐    ordering and no precedence. ⭐ Five groups is a permission
⭐    set, not a policy chain.
⭐ ⑤ ⭐⭐ ***A SOURCE CAN BE ANOTHER SECURITY GROUP.***

⭐⭐ AND ⑤ IS THE BEST FEATURE IN VPC AND ALMOST NOBODY USES IT:

⭐   ⭐ BAD:  allow 5432 from 10.0.16.0/20
⭐     ⭐⭐ BREAKS WHEN YOU ADD AN AZ, A SUBNET, OR A SECOND
⭐     SERVICE IN THE SAME RANGE — ⭐ and silently grants access
⭐     to anything else that lands in that CIDR.
⭐   ⭐⭐ GOOD: ***allow 5432 from sg-app***
⭐     ⭐ Self-maintaining as tasks come and go, ⭐ survives
⭐     re-subnetting, ⭐⭐ AND IT ***READS LIKE THE INTENT***: "the
⭐     app may reach the database". ⭐ The rule now names a role
⭐     rather than a location.

⭐⭐ THE NAMING CONVENTION THAT MAKES REVIEW POSSIBLE: ⭐ one
⭐   security group ***per role***, named for the role, ⭐ with
⭐   rules that reference other roles. ⭐⭐ THEN THE WHOLE NETWORK
⭐   POLICY OF YOUR SYSTEM IS READABLE AS A LIST OF SENTENCES —
⭐   `alb → app:8000`, `app → db:5432`, `app → redis:6379` —
⭐   ⭐⭐ AND ANYTHING NOT IN THAT LIST IS IMPOSSIBLE.

⭐ ⭐ Quotas worth knowing: 60 rules per group, 5 groups per ENI
⭐   by default. ⭐⭐ IF YOU ARE APPROACHING 60 RULES YOU ARE
⭐   LISTING IP ADDRESSES — ⭐ use group references or a prefix
⭐   list instead.
```

# Part 2 — NACLs, and the ephemeral-port bug

```
⭐⭐ FOUR PROPERTIES, AND THE FIRST ONE IS THE WHOLE PROBLEM:
⭐ ① ⭐⭐ ***STATELESS.*** ⭐ Inbound and outbound are evaluated
⭐    completely independently. ⭐⭐ THE RESPONSE TO AN ALLOWED
⭐    REQUEST IS ***NOT*** AUTOMATICALLY ALLOWED.
⭐ ② ⭐ Ordered by rule number, ⭐⭐ FIRST MATCH WINS AND
⭐    EVALUATION STOPS. ⭐ Leave gaps (100, 200, 300).
⭐ ③ ⭐ Has ***both*** allow and deny. ⭐ This is its only real
⭐    capability advantage.
⭐ ④ ⭐ Subnet-scoped, so it applies to everything in the subnet
⭐    whether you remembered it or not.

⭐⭐ THE CLASSIC BUG, IN FULL:
⭐   ⭐ You write a "tight" NACL: inbound allow 443, outbound
⭐     allow 443. ⭐ Looks symmetric. ⭐ Looks correct.
⭐   ⭐⭐ YOUR SERVER'S ***REPLY*** GOES OUT FROM PORT 443 TO THE
⭐     CLIENT'S ***EPHEMERAL*** PORT — ⭐ some number in
⭐     32768–60999 on Linux, 1024–65535 to be safe.
⭐   ⭐⭐ THE OUTBOUND RULE ALLOWS ONLY 443, SO THE REPLY IS
⭐     DROPPED. ⭐ The connection hangs. ⭐⭐ TCPDUMP ON THE SERVER
⭐     SHOWS THE REQUEST ARRIVING AND THE RESPONSE SENT — ⭐ which
⭐     is why this burns an entire afternoon.
⭐   ⭐⭐ ⇒ ***EVERY NACL NEEDS AN EPHEMERAL-PORT RULE IN THE
⭐     RETURN DIRECTION.*** ⭐ Both directions, for both roles,
⭐     because your instance is a client too.

⭐⭐ ⇒ SO THE PRACTICAL POSITION: ***LEAVE THE DEFAULT NACL
⭐   (ALLOW ALL) ALONE AND DO YOUR WORK IN SECURITY GROUPS.***
⭐   ⭐ Reach for a NACL only for the two things it uniquely
⭐   does: ⭐ ① blanket-deny a hostile CIDR at the subnet edge,
⭐   ⭐ ② satisfy an auditor who requires two enforcement layers.
⭐   ⭐⭐ USING NACLs AS YOUR PRIMARY FIREWALL IS A CHOICE TO
⭐   DEBUG STATELESSNESS FOREVER FOR NO SECURITY GAIN.
```

# Part 3 — ⭐⭐ Endpoints: the free one and the one you must justify

```
⭐⭐ ***GATEWAY ENDPOINTS — S3 AND DYNAMODB ONLY. FREE.***
⭐   ⭐ Mechanically they are a ***route table entry***, not a
⭐     device: a prefix list for S3 pointing at `vpce-xxx`.
⭐   ⭐ Traffic to S3 leaves via the endpoint instead of the NAT.
⭐   ⭐⭐ WHAT YOU GET, AND IT IS THREE SEPARATE WINS:
⭐     ⭐⭐ ① $0.045/GB OF NAT PROCESSING → ***ZERO***
⭐     ⭐⭐ ② THE NAT'S BANDWIDTH CEILING (45 Gbps, SHARED) STOPS
⭐        BEING YOUR S3 THROUGHPUT CEILING — ⭐ this is why data
⭐        jobs get faster as well as cheaper
⭐     ⭐⭐ ③ AN ENDPOINT POLICY: ⭐ "traffic through this endpoint
⭐        may only touch ***these*** buckets" — ⭐⭐ WHICH BLOCKS
⭐        EXFILTRATION TO AN ATTACKER'S OWN S3 BUCKET, AND
⭐        NOTHING IN IAM CAN EXPRESS THAT AS CLEANLY
⭐   ⭐⭐ ⇒ THERE IS NO ARGUMENT AGAINST ONE. ⭐ Add it on day one.

⭐⭐ ***INTERFACE ENDPOINTS (PrivateLink) — EVERYTHING ELSE.***
⭐   ⭐ Mechanically an ***ENI in your subnet*** with a private
⭐     DNS name that shadows the public one.
⭐   ⭐ ~$0.01/hour per endpoint ***per AZ*** ≈ $7.30/mo,
⭐     ⭐ plus $0.01/GB.
⭐   ⭐⭐ THE HONEST BREAK-EVEN: THREE AZs ≈ $22/MONTH FIXED, SO
⭐     YOU NEED ROUGHLY ***600 GB/MONTH*** THROUGH NAT ON THAT
⭐     SERVICE BEFORE IT PAYS FOR ITSELF ON MONEY ALONE.
⭐   ⭐⭐ ⇒ WHICH MEANS YOU USUALLY BUY IT FOR THE ***OTHER***
⭐     PROPERTY: ⭐ with endpoints for ECR, Secrets Manager,
⭐     CloudWatch and STS, ⭐⭐ YOUR PRIVATE SUBNETS NEED NO
⭐     INTERNET ROUTE AT ALL — ⭐ you can delete the NAT, and the
⭐     app tier joins the database tier in being unable to
⭐     exfiltrate anywhere. ⭐⭐ THAT IS A SECURITY ARCHITECTURE
⭐     DECISION WEARING A COST DISGUISE, AND IT IS WORTH SAYING
⭐     THAT WAY IN AN INTERVIEW.
⭐   ⭐ Note ECR needs ***three***: `ecr.api`, `ecr.dkr`, ⭐⭐ AND
⭐     THE S3 GATEWAY ENDPOINT, BECAUSE LAYERS LIVE IN S3 —
⭐     ⭐ forgetting the third is the commonest "why does the pull
⭐     still fail" in a no-NAT VPC.
```

# Part 4 — ⭐⭐ The connectivity debugging ladder

> The most useful half-page in the stage. Work it **in order** — each step is cheaper than the one
> below it, and stopping at the first failure is the whole method.

```
⭐⭐ FIRST, READ THE SYMPTOM — ⭐ it names the layer before you
⭐   touch anything:

⭐   ⭐⭐ ***CONNECTION REFUSED*** → ⭐ YOU REACHED THE HOST AND
⭐     NOTHING WAS LISTENING. ⭐⭐ THE NETWORK IS ***FINE***. ⭐ Go
⭐     look at the process, the port, and whether it bound
⭐     `127.0.0.1` instead of `0.0.0.0` (Day 364).
⭐   ⭐⭐ ***CONNECTION TIMED OUT*** → ⭐ SOMETHING SILENTLY ATE
⭐     THE PACKET. ⭐⭐ THAT IS A FIREWALL: SECURITY GROUP, NACL,
⭐     OR ROUTING. ⭐ Do not look at the application.
⭐   ⭐ ***NAME OR SERVICE NOT KNOWN*** → DNS. ⭐ Stop here.
⭐   ⭐ ***CONNECTION RESET*** → ⭐ something accepted and then
⭐     closed: ⭐ a TLS mismatch, a proxy, or the app crashing.

⭐⭐ THEN THE LADDER:
⭐ ① ⭐ DNS. `dig +short host` / `socket.getaddrinfo`.
⭐    ⭐⭐ RESOLVE BEFORE YOU BLAME ANYTHING ELSE.
⭐ ② ⭐ ROUTE. Is there a route from source subnet to
⭐    destination? ⭐ Local for in-VPC; ⭐⭐ NAT/IGW FOR OUT.
⭐ ③ ⭐ SOURCE SG ***EGRESS***. ⭐ Open by default — ⭐⭐ BUT NOT IN
⭐    A HARDENED ACCOUNT, AND PEOPLE FORGET THEY TIGHTENED IT.
⭐ ④ ⭐⭐ ***DESTINATION SG INGRESS. THIS IS THE ANSWER ABOUT 60%
⭐    OF THE TIME.*** ⭐ Right port, right protocol, ⭐ and the
⭐    source is the ***source's security group***, not its IP.
⭐ ⑤ ⭐ NACL, ***both directions***, ⭐⭐ INCLUDING EPHEMERAL
⭐    PORTS.
⭐ ⑥ ⭐⭐ IS THE PROCESS ACTUALLY LISTENING ON 0.0.0.0?
⭐    `ss -ltnp`. ⭐ (If you got "refused", start here.)
⭐ ⑦ ⭐ Is the target healthy — ⭐ and if a load balancer is
⭐    involved, is it in the target group and passing?

⭐⭐ AND THE TWO TOOLS THAT SHORT-CIRCUIT ALL OF IT:
⭐   ⭐⭐ ***VPC REACHABILITY ANALYZER*** — ⭐ give it a source and
⭐     a destination ENI and it tells you ***which component***
⭐     blocks the path, statically, without sending a packet.
⭐     ⭐⭐ IT COSTS PENNIES AND PEOPLE DEBUG FOR AN HOUR INSTEAD.
⭐   ⭐ ***FLOW LOGS*** — a REJECT record names srcaddr, dstport
⭐     and the action:
⭐     `2 111 eni-abc 10.0.1.5 10.0.3.9 41234 5432 6 1 40 ... REJECT`
⭐     ⭐⭐ A REJECT ON THE ***INBOUND*** SIDE IS A SECURITY GROUP
⭐     OR NACL; ⭐ no record at all means it never arrived, which
⭐     is routing.
```

# Part 5 — The Python view of a firewall problem

```python
# ⭐⭐ THE DIAGNOSTIC THAT DISTINGUISHES THE TWO SYMPTOMS —
# ⭐ keep this in your head, it is four lines.
import socket, time
t = time.perf_counter()
try:
    socket.create_connection(("db.internal", 5432), timeout=3)
    print("OPEN")
except ConnectionRefusedError:      # ⭐⭐ FAST. NETWORK IS FINE.
    print("REFUSED — process/port problem", time.perf_counter()-t)
except socket.timeout:              # ⭐⭐ SLOW. FIREWALL.
    print("TIMEOUT — SG/NACL/route", time.perf_counter()-t)
except socket.gaierror:
    print("DNS")
```

```
⭐⭐ AND WHY A MISSING SECURITY-GROUP RULE PRESENTS AS A ***SLOW
⭐   APP*** RATHER THAN AN ERROR — ⭐ this is the part that makes
⭐   it hard to recognise:

⭐   ⭐ A dropped SYN is not an error, it is ***silence***.
⭐   ⭐ Linux retries the SYN with exponential backoff, ⭐⭐ SO THE
⭐     CONNECT SITS THERE FOR ~130 SECONDS BEFORE FAILING.
⭐   ⭐ Your request handler blocks that whole time.
⭐   ⭐ Gunicorn's worker timeout (30 s) fires first and
⭐     ⭐⭐ KILLS THE WORKER WITH SIGKILL — SO YOU GET
⭐     `WORKER TIMEOUT`, NOT A CONNECTION ERROR.
⭐   ⭐⭐ ⇒ THE LOGS SAY "WORKERS KEEP DYING" AND THE CAUSE IS A
⭐     MISSING INGRESS RULE. ⭐ Nothing in the traceback says
⭐     "firewall".

⭐⭐ ⇒ SO: ***SET CONNECT TIMEOUTS EXPLICITLY, EVERYWHERE.***
⭐   ⭐ `psycopg` → `connect_timeout=5`
⭐   ⭐ `redis-py` → `socket_connect_timeout=2`
⭐   ⭐ `requests` → `timeout=(3, 10)` ⭐⭐ — THE TUPLE. A BARE
⭐     `timeout=10` IS THE ***READ*** TIMEOUT ONLY.
⭐   ⭐ `boto3` → `Config(connect_timeout=3, read_timeout=10,
⭐     retries={"max_attempts": 3, "mode": "standard"})`
⭐   ⭐⭐ A TWO-SECOND FAILURE IS A DIAGNOSABLE INCIDENT. A
⭐   130-SECOND ONE IS A MYSTERY (DAY 336).
```

# 💬 Interview

**1. ⭐⭐ "Security group versus NACL."**
> ⭐ A security group is stateful, allow-only, attached to an interface, and multiple groups union.
> ⭐ A NACL is stateless, ordered with first-match-wins, has allow and deny, and is subnet-scoped.
> ⭐⭐ **Stateless is the whole practical difference: with a NACL you must explicitly allow the return
> traffic on ephemeral ports, so a "tight" NACL allowing 443 in and 443 out drops every response** —
> because the reply goes from 443 to the client's ephemeral port. ⭐ tcpdump shows the response being
> sent, which is why it burns an afternoon. ⭐⭐ **So I do my work in security groups and leave the
> default NACL alone**, reaching for one only to blanket-deny a hostile CIDR or to satisfy an auditor
> who wants two layers.

**2. "What's the best feature of security groups?"**
> ⭐⭐ **That a source can be another security group.** ⭐ `allow 5432 from sg-app` instead of a CIDR:
> it's self-maintaining as tasks come and go, it survives re-subnetting, and it reads as the intent —
> "the app may reach the database" — ⭐⭐ **rather than as a location that some other service might
> later occupy.** ⭐ One group per role, rules referencing roles, ⭐⭐ **and then the entire network
> policy of the system is a readable list of sentences and anything not on the list is impossible.**

**3. ⭐⭐ "Talk me through debugging 'I can't connect to the database'."**
> ⭐ First I read the symptom, because it names the layer. ⭐⭐ **Connection refused means I reached the
> host and nothing was listening — the network is fine, go look at the process and whether it bound
> 127.0.0.1. Connection timed out means something silently ate the packet, which is a firewall or a
> route — don't look at the app.** ⭐ Then the ladder in order: DNS resolves; is there a route; source
> egress; ⭐⭐ **destination ingress, which is the answer about sixty percent of the time**; NACL both
> directions including ephemeral ports; is the process listening on 0.0.0.0; is the target healthy.
> ⭐ And I'd reach for Reachability Analyzer early — ⭐⭐ **it names the blocking component statically
> without sending a packet, and people debug for an hour instead of spending pennies.**

**4. "Why put an S3 gateway endpoint in?"**
> ⭐ Three reasons and it's free. ⭐⭐ **S3 traffic stops crossing the NAT, so $0.045 a gigabyte becomes
> zero for data that never left AWS; the NAT's bandwidth stops being your S3 throughput ceiling, so
> data jobs get faster as well as cheaper; and an endpoint policy can say "only these buckets", which
> blocks exfiltration to an attacker's own bucket** — something IAM can't express as cleanly. ⭐ There
> is no argument against one.

**5. "When is an interface endpoint worth $22 a month?"**
> ⭐ On pure cost you need roughly 600 GB a month through NAT for that service before it pays back.
> ⭐⭐ **So usually you're not buying the money — you're buying the property that with endpoints for
> ECR, Secrets Manager, CloudWatch and STS, your private subnets need no internet route at all.**
> ⭐ You delete the NAT, and the app tier joins the database tier in being unable to exfiltrate
> anywhere. ⭐⭐ **That's a security decision wearing a cost disguise.** ⭐ And ECR needs three
> endpoints — `ecr.api`, `ecr.dkr` and the S3 gateway, because layers live in S3.

**6. ⭐⭐ "Our gunicorn workers keep timing out after a deploy. Where do you look?"**
> ⭐ A missing security group rule is high on my list, because of how it presents. ⭐⭐ **A dropped SYN
> isn't an error, it's silence — Linux retries with backoff for about 130 seconds, the handler blocks
> the whole time, and gunicorn's 30-second worker timeout fires first and SIGKILLs the worker.** ⭐ So
> the logs say "workers keep dying" and nothing in the traceback mentions a firewall. ⭐ The fix is
> structural: ⭐⭐ **explicit connect timeouts on every client — and for `requests` that means the
> tuple, because a bare `timeout=10` is only the read timeout.** ⭐ A two-second failure is a
> diagnosable incident; a 130-second one is a mystery.
