# Part 2 — ⭐⭐ The key factory

```typescript
// src/api/keys.ts — ⭐⭐ ONE FILE. THE WHOLE CACHE DESIGN LIVES HERE.
export const keys = {
  orders: {
    all:    ["orders"] as const,
    list:   (f: OrderFilters) => [...keys.orders.all, "list", f] as const,
    detail: (id: string)      => [...keys.orders.all, "detail", id] as const,
  },
  users: {
    all:    ["users"] as const,
    me:     ()                => [...keys.users.all, "me"] as const,
  },
} as const;
```

| ⭐ Why a factory rather than inline arrays | |
|---|---|
| **Typos become compile errors** | ⭐⭐ `["oders", id]` inline is a **silent cache miss forever** — no error, just a refetch every time and two components disagreeing |
| **Hierarchy is enforced** | ⭐ `invalidate(keys.orders.all)` provably covers list **and** detail |
| **Filters are part of the key** | ⭐⭐ Different filters are different cache entries, which is correct — and easy to forget when writing keys by hand |
| **One place to read** | ⭐ "What does invalidating orders touch?" is answerable in ten seconds |

> ⭐⭐ **Key design is cache design** (Day 228). A key factory turns that from a convention you must
> remember into a structure the compiler checks.

# Part 3 — The hook shape

```typescript
// src/api/orders.ts
export function useOrders(filters: OrderFilters) {
  return useQuery({
    queryKey: keys.orders.list(filters),
    queryFn: ({ signal }) => client.GET("/orders", { params: { query: filters }, signal }),
    staleTime: 30_000,                    // ⭐ decided, not defaulted (Day 228)
  });
}

export function useCreateOrder() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (body: CreateOrder) =>
      client.POST("/orders", {
        body,
        headers: { "Idempotency-Key": body.clientId },   // ⭐⭐ Day 229/444
      }),
    onSuccess: () => qc.invalidateQueries({ queryKey: keys.orders.all }),
  });                                     // ⭐⭐ THE LINE PEOPLE FORGET
}
```

```
⭐⭐ THE FOUR DECISIONS EACH HOOK MAKES EXPLICIT — write them down

⭐   ① THE KEY        ⇒ what this data IS
⭐   ② ⭐ staleTime    ⇒ how current it must be. ⭐⭐ NEVER LEAVE AT
⭐                       THE DEFAULT WITHOUT DECIDING.
⭐   ③ ⭐⭐ INVALIDATION ⇒ what this write makes wrong
⭐   ④ ⭐ RETRY        ⇒ safe? (Day 227 — never a bare POST)
```

| ⭐ Resource | staleTime | ⭐ Why |
|---|---|---|
| `users.me` | ⭐ 5 min | Changes rarely; refetch on focus covers it |
| `orders.list` | 30 s | ⭐ Others create orders |
| `orders.detail` | ⭐⭐ 0 | The screen you act on — must be current |
| Reference data | ⭐ 1 hr | It does not change |

# Part 4 — ⭐⭐ The one rule that keeps it honest

```
⭐⭐ THE TRANSPORT LAYER OWNS EVERY CROSS-CUTTING CONCERN,
⭐   AND OWNS THEM **ONCE**:

⭐   · ⭐ AUTH        ⇒ credentials: "include" + single-flight
⭐                     refresh (Day 235). ⭐⭐ NOT IN EVERY HOOK.
⭐   · ⭐⭐ 401        ⇒ refresh once, retry once, then redirect.
⭐                     ⭐ A SCREEN MUST NEVER HANDLE A 401 ITSELF.
⭐   · ERROR MAPPING ⇒ ApiError with status + parsed body (Day 217)
⭐   · ⭐ RETRY       ⇒ 5xx/429 with jitter; NEVER 4xx; never a
⭐                     non-idempotent POST without a key
⭐   · ⭐⭐ TRACING    ⇒ generate a request id per call, send it as a
⭐                     header, ⭐ LOG IT WITH THE ERROR. Now a user's
⭐                     "it broke" is a server-log query (Day 279).
⭐   · TIMEOUTS      ⇒ AbortSignal.timeout on every request

⭐   ⇒ ⭐⭐ IF A SCREEN CONTAINS A `catch` THAT INSPECTS status === 401,
⭐     THE LAYER LEAKED. Fix the layer, not the screen.
```

```typescript
// ⭐⭐ the request id — 6 lines that make production debuggable
const requestId = crypto.randomUUID();
headers["X-Request-Id"] = requestId;
// ...on failure:
reportError(err, { requestId, path, status });   // ⭐ Day 279
```

> ⭐ **On the FastAPI side, log that header on every request.** Then a screenshot from a user contains
> an id you can grep, which is the difference between debugging a report and dismissing it.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how is your frontend's API layer structured?"**

State the principle and the enforcement together. **Three layers. A transport layer that owns auth,
refresh, error mapping, retries and timeouts. A query layer of one hook per resource that owns the
cache key, staleness and invalidation. And screens, which call hooks and never learn that a URL exists.
The test is grepping components for `fetch` — every hit is a component that silently opted out of auth,
retry, error handling and caching. There's a lint rule so it stays true.**

Then the key factory, with the reason it beats convention. **All cache keys come from one typed factory.
An inline typo'd key is a silent cache miss forever — no error, just a refetch every time and two
components disagreeing about the same record. In a factory it's a compile error, and the hierarchy is
enforced so invalidating orders provably covers both the list and the detail.**

Then what each hook decides explicitly. **The key, the staleness, what a write invalidates, and whether
retry is safe. I never leave staleTime at the default without deciding — the detail screen I act on is
zero, a reference list is an hour. And the mutation carries an idempotency key, because a double-click
on a create endpoint made two records.**

Close on the operational piece, which is the part most people don't build. **Every request carries a
generated request id as a header, the API logs it, and errors report it. So when a user sends a
screenshot, there's an id I can grep — that's the difference between debugging a report and dismissing
it. And no screen ever handles a 401; if I find a `catch` inspecting a status code in a component, the
layer leaked and I fix the layer.**
