# Part 1 — The object model, in four nouns

```
⭐ CLUSTER .......... ⭐ a namespace. ⭐⭐ ALMOST NOTHING. ⭐ Not a
⭐                    machine, not a control plane you manage.
⭐ TASK DEFINITION .. ⭐⭐ AN ***IMMUTABLE, VERSIONED*** DOCUMENT:
⭐                    containers, cpu/memory, env, secrets, IAM
⭐                    role, logging, ports.
⭐                    ⭐⭐ EVERY CHANGE MAKES A NEW REVISION, WHICH
⭐                    IS WHY ROLLBACK IS "USE REVISION 41" AND
⭐                    TAKES SECONDS (DAY 371).
⭐ TASK ............. ⭐ one running instantiation. ⭐ ≈ a pod.
⭐ SERVICE .......... ⭐ desired count + deployment strategy +
⭐                    load-balancer registration + placement.
⭐                    ⭐⭐ THE THING THAT KEEPS N TASKS ALIVE —
⭐                    I.E. DAY 377's RECONCILIATION LOOP, WITH
⭐                    FEWER NOUNS.

⭐⭐ ⇒ AND THAT IS THE ENTIRE MENTAL MODEL. ⭐ Compare Day 377's
⭐   Kubernetes list — Deployment, ReplicaSet, Pod, Service,
⭐   Ingress, ConfigMap, Secret, ServiceAccount, HPA, PDB.
⭐   ⭐⭐ THE SMALLER VOCABULARY IS NOT A LIMITATION; IT IS THE
⭐   PRODUCT.
```

# Part 2 — Fargate vs EC2 launch type, with the real number

```
⭐ EC2 LAUNCH TYPE: ⭐ you own the instances, the AMI, the
⭐   patching, the capacity, ⭐ the bin-packing, ⭐ and the ECS
⭐   agent. ⭐⭐ CHEAPER PER UNIT OF COMPUTE AND YOU CAN GET HIGH
⭐   UTILISATION IF YOU WORK AT IT.

⭐ FARGATE: ⭐ you declare cpu and memory, a task appears. ⭐ No
⭐   instances exist as far as you are concerned. ⭐ Per-second
⭐   billing.

⭐⭐ THE HONEST COST COMPARISON — ⭐ and you should be able to
⭐   state it, because "Fargate is expensive" is repeated by
⭐   people who have not:
⭐   ⭐⭐ FARGATE IS ROUGHLY ***20–30% MORE*** PER vCPU-HOUR THAN
⭐     THE EQUIVALENT EC2 ***AT 100% UTILISATION.***
⭐   ⭐⭐ BUT NOBODY RUNS EC2 AT 100%. ⭐ At a realistic 40–50%
⭐     bin-packing efficiency, ⭐⭐ FARGATE IS OFTEN ***CHEAPER***,
⭐     ⭐ because you pay for the task rather than the gap around
⭐     it.
⭐   ⭐⭐ ⇒ SO THE THRESHOLD IS NOT A UTILISATION NUMBER, IT IS A
⭐     SALARY: ***RUN FARGATE UNTIL THE ANNUAL DELTA EXCEEDS THE
⭐     COST OF THE PERSON WHO WOULD OTHERWISE MAINTAIN THE
⭐     INSTANCES.*** ⭐ For most teams that is never.
⭐   ⭐ Fargate Spot: ~70% off for interruptible work (Day 385).
⭐   ⭐⭐ AND A COMPUTE SAVINGS PLAN COVERS FARGATE TOO (DAY 385),
⭐     WHICH PEOPLE FORGET WHEN DOING THIS COMPARISON.

⭐ ⭐ Where EC2 launch type still wins: ⭐ GPUs, ⭐ very large
⭐   memory, ⭐ workloads needing privileged mode or a custom
⭐   kernel, ⭐ and genuinely enormous steady fleets.
```

```
⭐⭐ THE SIX DECISIONS HIDING IN THAT FILE:
⭐ ① ⭐⭐ ***THE IMAGE IS A DIGEST, NOT A TAG*** (DAY 362). ⭐ A
⭐    tag is a mutable pointer; ⭐⭐ A DIGEST MEANS THE ROLLBACK
⭐    ACTUALLY ROLLS BACK.
⭐ ② ⭐⭐ ***TWO ROLES, AND PEOPLE CONFLATE THEM.*** ⭐ The
⭐    ***execution*** role is used by the ECS agent to pull the
⭐    image and fetch secrets ***before your code runs***; ⭐ the
⭐    ***task*** role is what `boto3` gets at runtime (Day 382).
⭐    ⭐⭐ "IT CANNOT PULL THE IMAGE" IS ALWAYS THE EXECUTION
⭐    ROLE. "AccessDenied IN MY CODE" IS ALWAYS THE TASK ROLE.
⭐ ③ ⭐⭐ ***SECRETS BY ARN, NOT ENV VARS*** (DAY 372) — ⭐ they
⭐    are injected at start and ⭐⭐ NEVER APPEAR IN THE TASK
⭐    DEFINITION, WHICH IS READABLE BY ANYONE WITH
⭐    `ecs:DescribeTaskDefinition`.
⭐ ④ ⭐⭐ `"mode": "non-blocking"` ON THE LOG DRIVER. ⭐ Without
⭐    it, ⭐⭐ IF CLOUDWATCH IS SLOW YOUR CONTAINER'S `write()` TO
⭐    STDOUT ***BLOCKS*** AND YOUR APP STALLS — ⭐ a logging
⭐    backend becoming a latency dependency (Day 375).
⭐ ⑤ ⭐ `startPeriod` — ⭐⭐ THE GRACE WINDOW FOR A SLOW PYTHON
⭐    BOOT, EXACTLY DAY 377's STARTUP PROBE. ⭐ Without it a
⭐    30-second import time is an infinite restart loop.
⭐ ⑥ ⭐ `cpu`/`memory` must be a ***valid Fargate pair*** —
⭐    ⭐⭐ YOU CANNOT ASK FOR 1 vCPU AND 512 MB. ⭐ And 1024 cpu
⭐    units = 1 vCPU, ⭐⭐ WHICH IS THE NUMBER YOUR DAY 366
⭐    `_cgroup_cpus()` HELPER READS.
```

# Part 4 — ⭐⭐ Deployments, and the one setting that is off by default

```
⭐ ROLLING UPDATE, GOVERNED BY TWO PERCENTAGES:
⭐   ⭐ `minimumHealthyPercent` / `maximumPercent`
⭐   ⭐ 100 / 200 → ⭐⭐ START ALL THE NEW ONES FIRST. ⭐ Fast, no
⭐     capacity dip, ⭐ briefly doubles cost. ⭐ The right default.
⭐   ⭐ 50 / 100 → ⭐⭐ NEVER EXCEED DESIRED COUNT, BUT RUN AT HALF
⭐     CAPACITY DURING THE DEPLOY. ⭐ Only if capacity is capped.
⭐   ⭐ 100 / 100 → ⭐⭐ DEADLOCK-ISH: NOTHING CAN START UNTIL
⭐     SOMETHING STOPS, AND NOTHING MAY STOP. ⭐ Deploys crawl.

⭐⭐ AND THE SETTING THAT MATTERS MOST AND IS ***OFF BY
⭐   DEFAULT***:
⭐   ⭐⭐ ***DEPLOYMENT CIRCUIT BREAKER, WITH `rollback: true`.***
⭐   ⭐ ECS watches whether new tasks reach a steady state. ⭐ If
⭐     they keep failing, ⭐⭐ IT STOPS THE DEPLOY AND ROLLS BACK
⭐     TO THE PREVIOUS TASK DEFINITION AUTOMATICALLY.
⭐   ⭐⭐ ⇒ THIS IS THE SINGLE SETTING THAT CONVERTS A BAD DEPLOY
⭐     FROM AN OUTAGE INTO A BLIP, ⭐ it is one line of Terraform,
⭐     ⭐⭐ AND MOST TEAMS SHIP FOR YEARS WITHOUT IT.
⭐   ⭐ Pair with `deployment_alarms` on your 5xx rate ⭐⭐ SO A
⭐     DEPLOY THAT IS "HEALTHY" BUT ERRORING ALSO ROLLS BACK.

⭐ ⭐ `enableExecuteCommand` gives you `aws ecs execute-command`
⭐   — ⭐⭐ A SHELL IN A RUNNING TASK, VIA SSM, LOGGED IN
⭐   CLOUDTRAIL, WITH NO SSH AND NO BASTION. ⭐ Turn it on in
⭐   prod; ⭐ it is the debugging story that makes distroless
⭐   images survivable (Day 363).
```

# Part 5 — Networking: `awsvpc`, and the IP arithmetic

```
⭐⭐ ***EVERY TASK GETS ITS OWN ENI, ITS OWN PRIVATE IP AND ITS
⭐   OWN SECURITY GROUP.***

⭐ WHY THAT IS GOOD: ⭐⭐ DAY 384's GROUP-REFERENCING WORKS
⭐   PERFECTLY — ⭐ `allow 5432 from sg-flagship-api` is now a
⭐   statement about ***that service***, not about a subnet or a
⭐   host that runs six things. ⭐⭐ NETWORK POLICY BECOMES
⭐   PER-SERVICE WITHOUT A MESH.

⭐⭐ WHY IT BITES: ***ONE TASK = ONE IP.***
⭐   ⭐ 20 tasks + rolling deploy at 200% = ⭐⭐ 40 IPs, BRIEFLY.
⭐   ⭐ Plus the ALB's own ENIs, plus interface endpoints, plus
⭐     RDS, plus anything else in that subnet.
⭐   ⭐⭐ A /28 SUBNET HAS ***ELEVEN*** USABLE ADDRESSES (DAY 383),
⭐     ⭐ so it dies on the first real deploy with
⭐     `RESOURCE:ENI` placement failures — ⭐⭐ AND THE ERROR DOES
⭐     NOT SAY "OUT OF IP ADDRESSES" IN ANY OBVIOUS WAY.
⭐   ⭐⭐ ⇒ /20 SUBNETS. ⭐ This is the concrete reason Day 383
⭐     said to be generous.

⭐ ⭐ Tasks in private subnets need either a NAT or interface
⭐   endpoints to pull from ECR — ⭐⭐ AND REMEMBER ECR NEEDS
⭐   `ecr.api`, `ecr.dkr` ***AND*** THE S3 GATEWAY ENDPOINT
⭐   (DAY 384). ⭐ Missing the third is the classic no-NAT
⭐   failure.
⭐ ⭐ `assignPublicIp: ENABLED` in a public subnet works and is
⭐   the cheap dev setup; ⭐⭐ IT IS ALSO HOW PEOPLE ACCIDENTALLY
⭐   EXPOSE A TASK.

⭐ SERVICE DISCOVERY: ⭐ ECS Service Connect (preferred) or
⭐   Cloud Map. ⭐⭐ AND THE PYTHON WARNING FROM DAY 342 APPLIES —
⭐   ⭐ a DNS-based discovery record changing does not move an
⭐   already-open pooled connection. ⭐⭐ SAME LESSON AS DAY 387,
⭐   THIRD TIME THIS STAGE: ***POOLS OUTLIVE DNS.***
```

# 💬 Interview

**1. "Fargate or EC2?"**
> ⭐ Fargate, and I'd give the cost honestly rather than repeating that it's expensive. ⭐⭐ **It's
> roughly 20–30% more per vCPU-hour than equivalent EC2 at 100% utilisation — but nobody runs EC2 at
> 100%, and at a realistic 40–50% bin-packing efficiency Fargate is often cheaper, because you pay for
> the task rather than the gap around it.** ⭐ And a Compute Savings Plan covers Fargate, which people
> forget in that comparison. ⭐⭐ **So the threshold isn't a utilisation number, it's a salary: run
> Fargate until the annual delta exceeds the cost of the person who'd otherwise maintain instances.**
> ⭐ EC2 launch type still wins for GPUs, very large memory, or privileged workloads.

**2. ⭐⭐ "ECS or EKS?"**
> ⭐ It isn't a capability question — EKS can do everything ECS can and the workload doesn't care.
> ⭐⭐ **The first question is whether there's a named person who will own the cluster, because
> Kubernetes is a permanent upgrade treadmill: three minor releases a year, about fourteen months of
> support, each with deprecations that break manifests.** ⭐ No owner means ECS, and that decides most
> cases alone. ⭐ Then: do you need the ecosystem — Argo, Istio, KEDA — ⭐⭐ **because if the ecosystem
> *is* the product you're buying, that's a real and sufficient reason, and the only one that gets
> stronger over time.** ⭐ Then, are you multi-cloud in reality or on a slide. ⭐ And roughly: under
> fifteen services with no platform person, ECS. ⭐⭐ **I'd also say that "we used App Runner because it
> was enough" is a stronger engineering answer than an unnecessary EKS cluster.**

**3. ⭐⭐ "Your task can't pull the image. Where do you look?"**
> ⭐ The execution role, not the task role — ⭐⭐ **and conflating those two costs people a lot of time.
> The execution role is what the ECS agent uses to pull the image and fetch secrets before your code
> runs; the task role is what boto3 gets at runtime.** ⭐ So "can't pull the image" or "can't resolve
> the secret" is always the execution role, and an AccessDenied inside my own code is always the task
> role. ⭐ If it's a private-subnet cluster with no NAT, I'd also check the endpoints, ⭐⭐ **because ECR
> needs `ecr.api`, `ecr.dkr` and the S3 gateway endpoint — layers live in S3, and missing the third is
> the classic failure.**

**4. "What's the one ECS setting you'd insist on?"**
> ⭐⭐ **The deployment circuit breaker with rollback enabled — it's off by default.** ⭐ ECS watches
> whether new tasks reach a steady state and, if they keep failing, stops the deploy and reverts to
> the previous task definition automatically. ⭐⭐ **One line of Terraform that converts a bad deploy
> from an outage into a blip, and teams ship for years without it.** ⭐ I'd pair it with deployment
> alarms on the 5xx rate, so a deploy that's technically healthy but erroring also rolls back.

**5. "What does `awsvpc` mode change?"**
> ⭐⭐ **Every task gets its own ENI, IP and security group** — which is excellent, because network
> rules become per-service: `allow 5432 from sg-flagship-api` is a statement about that service rather
> than about a host running six things. ⭐ You get per-service network policy without a mesh. ⭐ The
> cost is IP consumption: ⭐⭐ **one task equals one IP, and twenty tasks deploying at 200% is forty
> briefly — so a /28 subnet with eleven usable addresses dies on the first real deploy with an ENI
> placement failure that doesn't obviously say "out of IPs".** ⭐ That's the concrete reason to size
> subnets generously.

**6. "How do migrations run?"**
> ⭐ As a separate one-off `RunTask` in the pipeline, ⭐⭐ **never in the container entrypoint — because
> in the entrypoint every task runs them concurrently, they race for the lock, and startup time now
> includes a schema change.** ⭐ It's the same reason the pipeline has a migration gate with a lock
> check: ⭐⭐ **the same ALTER TABLE is harmless on five hundred rows and an eight-minute outage on forty
> million**, and I want that decision at a reviewable step, not at boot.

## 🎙️ Articulation drill

**Two minutes.** Start with the model, because its smallness is the point: **cluster, task definition,
task, service — four nouns against Kubernetes' ten, and the task definition being immutable and
versioned is why rollback is "use revision 41" and takes seconds.** Then the cost answer, stated
honestly: **Fargate is 20–30% more per vCPU-hour at 100% utilisation, but nobody runs EC2 at 100%, so
at realistic bin-packing it's often cheaper — and the threshold isn't a utilisation number, it's a
salary.** Then the setting: **the deployment circuit breaker with rollback is one line and it's off by
default — it converts a bad deploy from an outage into a blip, and teams ship for years without it.**
Give the distinction that saves debugging time: **execution role pulls the image and fetches secrets
before your code runs; task role is what boto3 gets at runtime — so "can't pull the image" is always
the first and AccessDenied in my code is always the second.** Then `awsvpc` with both halves: **each
task gets its own ENI and security group, so network policy becomes per-service without a mesh — and
one task is one IP, so twenty tasks deploying at 200% is forty, and a /28 dies on the first real
deploy.** Close on the decision people get wrong: **ECS versus EKS isn't about capability. The first
question is whether a named person will own the cluster, because Kubernetes is a permanent upgrade
treadmill — and if the answer is no, it's ECS. The only reason that gets stronger over time is needing
the ecosystem. "We used App Runner because it was enough" is a stronger answer than an unnecessary
cluster.**
