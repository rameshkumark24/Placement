# Part 1 — ⭐ The specification, held constant

```
⭐⭐ `POST /v1/orders` — IDENTICAL REQUIREMENTS IN BOTH. ⭐ Holding the spec
⭐   constant is what makes the comparison mean anything.

⭐   INPUT   `{"hold_id": 42, "qty": 2}` + `Idempotency-Key` header (REQUIRED)
⭐   AUTH    authenticated user; the hold must be THEIRS
⭐   RULES   ⭐ hold must be unexpired · ⭐⭐ inventory must not oversell ·
⭐           ⭐⭐ a retry with the same key returns the SAME order, never a
⭐              second charge
⭐   EFFECTS ⭐ one transaction: claim key → consume hold → decrement stock →
⭐              create order → write outbox row
⭐   OUTPUT  201 + `{id, status, total_cents}` · ⭐ 409 `sold_out` ·
⭐           410 `hold_expired` · 422 `validation_failed` · 400 `missing_key`
⭐   NON-FUNC ⭐⭐ exactly-one-order under 200 concurrent identical retries ·
⭐              ⭐ ≤ 4 queries · ⭐ no `password_hash` in any response
```

# Part 2 — ⭐⭐ FastAPI

```python
# api/orders.py
@router.post("/orders", status_code=201, response_model=OrderOut,
             responses={409: {"model": Problem}, 410: {"model": Problem}})
def create_order(
    body: OrderCreate,                                    # ⭐ parsed, typed, documented
    idempotency_key: str = Header(..., alias="Idempotency-Key", max_length=200),
    user: User = Depends(get_current_user),               # ⭐ auth as a dependency
    svc: OrderService = Depends(get_order_service),       # ⭐⭐ overridable in tests
) -> OrderOut:
    order = svc.place(user_id=user.id, hold_id=body.hold_id,
                      qty=body.qty, idem_key=idempotency_key)
    return OrderOut.model_validate(order)                 # ⭐⭐ explicit output schema

# services/orders.py — ⭐⭐ imports no FastAPI
def place(self, *, user_id, hold_id, qty, idem_key) -> Order:
    claimed = self._db.execute(
        insert(Order).values(...).on_conflict_do_nothing(index_elements=["idempotency_key"])
        .returning(Order.id)).scalar_one_or_none()
    if claimed is None:
        return self._existing_for(idem_key, user_id)      # ⭐ same response, no charge
    hold = self._holds.claim(hold_id, user_id=user_id)    # ⭐ FOR UPDATE
    if hold is None: raise HoldExpired(hold_id)
    if self._stock.decrement(hold.ticket_type_id, hold.qty) == 0:
        raise SoldOut(hold.ticket_type_id)                # ⭐⭐ conditional UPDATE
    self._db.add(Outbox(topic="order.created", payload={"order_id": claimed}))
    self._db.commit()                                     # ⭐⭐ ONE commit, in the service
    return self._db.get(Order, claimed)

# api/errors.py — ⭐ domain error → HTTP, in ONE place
@app.exception_handler(SoldOut)
def _sold_out(request, exc): return problem(409, "sold_out")
```

```
⭐⭐ WHAT FASTAPI MADE EASY:
⭐   ⭐ THE CONTRACT IS THE SIGNATURE. Types drive parsing, validation,
⭐        OpenAPI and the editor. ⭐⭐ The docs CANNOT drift, because they are
⭐        generated from the same annotations that do the validating.
⭐   ⭐ ⭐⭐ THE LAYERING IS ENFORCED BY IMPORTS. The service knows nothing
⭐        about HTTP, so the Celery worker calls it unchanged (Day 166).
⭐   ⭐ `Depends` makes auth, the session and the service one uniform,
⭐        overridable mechanism — ⭐⭐ tests swap the seam, never a patch.
⭐   ⭐ The output schema is a separate class, so ⭐⭐ adding a model column
⭐        cannot leak into the response.
⭐
⭐⭐ WHAT FASTAPI MADE HARD:
⭐   ⭐ ⭐⭐ YOU WROTE ALL OF IT. Settings, session lifecycle, migrations,
⭐        auth, permissions, pagination, admin — every one a decision
⭐        (Days 130–169 were largely those decisions).
⭐   ⭐ ⭐⭐ NO BACK-OFFICE AT ALL. Support cannot look an order up without a
⭐        tool you build.
⭐   ⭐ Four files for one endpoint: schema, route, service, repository.
⭐        ⭐ Right at scale, ⭐⭐ heavy for a small CRUD app.
```

# Part 3 — ⭐⭐ Django + DRF

```python
# api/serializers.py
class OrderCreateSerializer(serializers.Serializer):      # ⭐⭐ plain, not Model-
    hold_id = serializers.IntegerField()
    qty = serializers.IntegerField(min_value=1, max_value=10)

class OrderReadSerializer(serializers.ModelSerializer):
    class Meta:
        model = Order
        fields = ["id", "status", "total_cents"]          # ⭐⭐ explicit, never __all__

# api/views.py
class OrderViewSet(mixins.CreateModelMixin, mixins.RetrieveModelMixin,
                   viewsets.GenericViewSet):              # ⭐⭐ NOT ModelViewSet — no destroy
    permission_classes = [IsAuthenticated]
    def get_queryset(self):
        return Order.objects.filter(user=self.request.user).select_related("user")
        #  ⭐⭐ isolation HERE, not in a permission class (Day 176)

    def create(self, request):
        key = request.headers.get("Idempotency-Key")
        if not key:
            raise ValidationError({"code": "missing_key"})
        s = OrderCreateSerializer(data=request.data); s.is_valid(raise_exception=True)
        order = place_order(user=request.user, idem_key=key, **s.validated_data)
        return Response(OrderReadSerializer(order).data, status=201)

# services/orders.py — ⭐⭐ imports no DRF
@transaction.atomic                                       # ⭐⭐ NOT autocommit (Day 172)
def place_order(*, user, hold_id, qty, idem_key) -> Order:
    order, created = Order.objects.get_or_create(
        idempotency_key=idem_key, defaults={"user": user, "status": "pending"})
    if not created:
        return order                                      # ⭐ same response, no charge
    hold = (Hold.objects.select_for_update()
            .filter(id=hold_id, user=user, released_at__isnull=True,
                    expires_at__gt=timezone.now()).first())
    if hold is None: raise HoldExpired(hold_id)
    updated = (TicketType.objects
               .filter(pk=hold.ticket_type_id,
                       quantity_sold__lte=F("quantity_total") - hold.qty)
               .update(quantity_sold=F("quantity_sold") + hold.qty))   # ⭐⭐ conditional
    if not updated: raise SoldOut(hold.ticket_type_id)
    Outbox.objects.create(topic="order.created", payload={"order_id": order.id})
    transaction.on_commit(lambda: publish_order_created.delay(order.id))  # ⭐⭐ Day 172
    return order
```

```
⭐⭐ WHAT DJANGO MADE EASY:
⭐   ⭐ ⭐⭐ THE ADMIN. Support can find, filter and inspect this order today,
⭐        for free. ⭐ In FastAPI that is a project.
⭐   ⭐ `transaction.atomic` + `on_commit` + `F()` + `select_for_update` are
⭐        ⭐⭐ all first-party and all correct. ⭐ No library evaluation.
⭐   ⭐ Auth, users, groups, permissions, password hashing and reset flows
⭐        ⭐⭐ already existed.
⭐   ⭐ Migrations understand the models natively; ⭐ `makemigrations` needs
⭐        no database.
⭐   ⭐ ⭐⭐ FEWER FILES AND FEWER DECISIONS. A second developer recognises
⭐        this codebase immediately.
⭐
⭐⭐ WHAT DJANGO MADE HARD:
⭐   ⭐ ⭐⭐ THREE DEFAULTS ARE WRONG AND SILENT: autocommit (so `atomic` is
⭐        on you), `ModelViewSet` publishing `destroy`, and
⭐        `has_object_permission` not running on `list`.
⭐   ⭐ ⭐⭐ THE CONTRACT IS INFERRED, NOT DECLARED. `drf-spectacular` guesses,
⭐        needs decorators, and CAN DRIFT — so the schema needs a CI snapshot
⭐        to stay honest (Day 176).
⭐   ⭐ `Model.objects` works anywhere, ⭐⭐ so nothing structurally prevents a
⭐        query in a view, a template or a signal.
⭐   ⭐ ⭐⭐ ASYNC IS A THREAD-POOL FAÇADE (Day 178).
```

# Part 4 — ⭐⭐ What was identical

```
⭐⭐ THE MOST IMPORTANT SECTION OF THE DAY. **THE HARD PARTS WERE THE SAME
⭐   PARTS**, and neither framework helped with any of them:

⭐   ⭐⭐ THE RACE. A conditional UPDATE plus a row lock plus a CHECK
⭐        constraint. ⭐ Identical logic, identical SQL, identical reasoning.
⭐   ⭐⭐ IDEMPOTENCY. An atomic claim against a unique constraint. ⭐ The
⭐        syntax differs (`on_conflict_do_nothing` vs `get_or_create`); the
⭐        idea does not.
⭐   ⭐⭐ THE TRANSACTION BOUNDARY. One commit, owned by the service, never
⭐        held across I/O.
⭐   ⭐⭐ THE DUAL WRITE. An outbox row in the same transaction; enqueue after
⭐        commit.
⭐   ⭐ THE ERROR CONTRACT. One shape, stable machine-readable codes.
⭐   ⭐ THE N+1, THE INDEXES, THE QUERY-COUNT CEILING.
⭐   ⭐ AUTHORISATION IN THE QUERY, not after the fetch.
⭐   ⭐ THE CONCURRENCY TEST — real threads, real commits, exactly 500 sold.
⭐
⭐   ⇒ ⭐⭐ **ROUGHLY 80% OF THE DIFFICULTY WAS FRAMEWORK-INDEPENDENT.** ⭐ The
⭐        framework decided how much boilerplate surrounded the hard part, not
⭐        what the hard part was.
⭐   ⇒ ⭐⭐ WHICH IS WHY "WHICH FRAMEWORK" IS A WEAK INTERVIEW QUESTION AND
⭐        "HOW DO YOU PREVENT A DOUBLE CHARGE" IS A STRONG ONE. ⭐ Say that.

⭐⭐ AND THE LINE COUNT, HONESTLY:
⭐   ⭐ FastAPI: ~95 lines across 4 files, ⭐ plus ~400 lines of foundation
⭐        you wrote once (settings, session, auth, errors, pagination).
⭐   ⭐ Django:  ~70 lines across 3 files, ⭐ plus ~40 lines of settings.
⭐   ⇒ ⭐⭐ DJANGO WINS THE FIRST ENDPOINT BY A LARGE MARGIN. ⭐ The gap closes
⭐        as endpoints multiply, ⭐⭐ and reverses if the app is
⭐        operation-shaped rather than model-shaped.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Comparing frameworks with a toy endpoint | A CRUD `GET` compares boilerplate. A race plus money compares what matters. |
| Changing the spec between implementations | Then you're comparing two designs, not two frameworks. |
| "Django is magic" / "FastAPI is fast" | Unfalsifiable. Name the mechanism and the cost. |
| Concluding one framework is better | They optimise different things. State the condition that flips your choice. |
| Missing that most of the difficulty was identical | That's the actual insight, and most candidates never notice it. |
| `ModelViewSet` in the Django version | Publishes `destroy` you didn't ask for. Compose the mixins. |
| Ownership in a permission class | Not called on `list`. Scope `get_queryset`. |
| Forgetting `@transaction.atomic` | Django's autocommit means the multi-step operation isn't atomic. |
| `.delay()` without `on_commit` | The worker reads before commit. |
| `fields = "__all__"` in the read serializer | A future column leaks into your API. |
| Committing in the repository in the FastAPI version | Two calls in one operation become two transactions. |
| Comparing line counts without the foundation | FastAPI's ~400 setup lines are real and amortise across endpoints. |

## Interview questions

**Q: You've built the same endpoint in both. What did you learn?**

> That about eighty percent of the difficulty was framework-independent. The race needed a
> conditional update plus a row lock plus a check constraint — identical logic and near-identical SQL
> in both. Idempotency needed an atomic claim against a unique constraint; the syntax differs,
> `on_conflict_do_nothing` versus `get_or_create`, and the idea doesn't. The transaction boundary,
> the outbox for the dual write, the error contract, the query-count ceiling, authorisation in the
> query rather than after the fetch, and the concurrency test were all the same. The framework
> decided how much boilerplate surrounded the hard part, not what the hard part was. Which is why
> "which framework do you prefer" is a weak question and "how do you prevent a double charge" is a
> strong one.

**Q: Which one shipped the endpoint faster?**

> Django, clearly, for the first endpoint — about seventy lines across three files plus forty lines
> of settings, against ninety-five lines across four files plus roughly four hundred lines of
> foundation I had to write once in FastAPI: settings, session lifecycle, auth, error handling,
> pagination. And Django gave me an admin, so support could look the order up the same afternoon,
> which in FastAPI is a separate project. The gap narrows as endpoints multiply, because that
> foundation amortises, and it reverses if the API is operation-shaped rather than model-shaped —
> `place_order`, `refund` and `capture` are verbs, and DRF wants resources.

**Q: Which defaults would have shipped a bug?**

> In Django, four. Autocommit, so my multi-step operation isn't atomic unless I remember
> `@transaction.atomic` — and it *reads* atomic. `ModelViewSet` publishing a DELETE endpoint I never
> asked for. `fields = "__all__"` meaning a column someone adds later appears in the API with no
> review. And `has_object_permission` not being called on `list`, so ownership in a permission class
> gives a correct 403 on detail and returns everyone's data on list. In FastAPI, fewer defaults but
> also fewer guardrails: no default pagination, no auth on a router unless you add it, and nothing
> structurally stops you committing inside a repository. Django's wrong defaults are more numerous
> and more silent; FastAPI's problem is that there's no default at all, so it depends entirely on
> whether you knew to add one.

**Q: So which would you choose?**

> Django if the product is model-shaped CRUD with a back-office, a team that rotates, or
> server-rendered pages — the integration is genuinely the product, and the admin alone is often
> weeks. FastAPI if the API is operation-shaped, if I need real async I/O, or if the typed contract
> is a first-class deliverable, because its OpenAPI is derived from the same annotations that
> validate, so it cannot drift, whereas DRF's is inferred and needs a CI snapshot to stay honest. The
> condition that would flip me either way: if the app needs a serious back-office I lean Django even
> for an operation-shaped API, and if I need thousands of concurrent long-lived connections I leave
> Django regardless, because its async ORM is a thread-pool façade.

## 🎙️ Articulation drill

**Two minutes: "Compare Django and FastAPI."**

Refuse the sales pitch and lead with the finding: you built the same endpoint twice and about eighty
percent of the difficulty was identical — the race, the idempotency, the transaction boundary, the
dual write, the query count. Say the framework decided how much boilerplate surrounded the hard part,
not what the hard part was. *Then* give the differences, with mechanisms rather than adjectives:
Django's contract is inferred and can drift while FastAPI's is derived from the annotations that
validate; Django's autocommit means your service isn't atomic unless you remember; DRF's object
permission never runs on list. Give your choice and the condition that flips it. Close on the line
that shows judgement: **both frameworks let me ship it correctly, neither stopped me shipping it
incorrectly — what differed was how much I built around the hard part, and which wrong thing was the
default.**
