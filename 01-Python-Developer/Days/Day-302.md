# Day 302 🏛️

**P-302** · 🏛️ **The service layer** — ⭐⭐ application logic vs domain logic

**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: would this rule still exist if the application were a paper form? If
> yes it is domain logic; if it mentions HTTP, a queue or a transaction it is application logic — and
> that one question resolves almost every "where does this go?" argument you will ever have.**
>
> ⭐ Day 256 gave the service the transaction boundary. ⭐⭐ Today is the harder half: what belongs
> *in* it, what belongs below it, and why the distinction decays in every codebase that doesn't name
> it.

---

# Part 1 — ⭐⭐ The two kinds of logic

```
⭐⭐ DOMAIN LOGIC answers: ***IS THIS ALLOWED? WHAT DOES THIS
⭐   MEAN? WHAT IS IT WORTH?***
⭐   ⭐ "A job can only be completed from `in_progress`."
⭐   ⭐ "A technician cannot hold two overlapping assignments."
⭐   ⭐ "The total is the sum of the lines plus tax at the rate
⭐     in force on the service date."
⭐   ⇒ ⭐ These are TRUE ABOUT THE BUSINESS. ⭐⭐ THEY WERE
⭐     TRUE BEFORE THE SOFTWARE EXISTED AND WOULD SURVIVE ITS
⭐     DELETION.

⭐⭐ APPLICATION LOGIC answers: ***WHAT HAPPENS, IN WHAT ORDER,
⭐   IN WHAT TRANSACTION, AND WHAT DO WE TELL THE WORLD?***
⭐   ⭐ "Load the job, complete it, write an outbox row, commit,
⭐     return a DTO."
⭐   ⭐ "If the provider times out, mark it unknown and return
⭐     202."
⭐   ⇒ ⭐ These are TRUE ABOUT ***THIS SYSTEM***. ⭐⭐ THEY
⭐     WOULD CHANGE IF YOU REBUILT IT AS A BATCH JOB — and the
⭐     domain rules would not.
```

```
⭐⭐ THE TEST, AND IT IS WORTH MEMORISING VERBATIM:
⭐   ***WOULD THIS RULE STILL EXIST IF THE APPLICATION WERE A
⭐      PAPER FORM PROCESSED BY A CLERK?***
⭐   ⭐ "Only pending orders can be cancelled" ⇒ ⭐⭐ YES. The
⭐     clerk would refuse. ***DOMAIN.***
⭐   ⭐ "Cancelling sends an email and refunds via Stripe" ⇒
⭐     ⭐ no — the clerk would post a letter and walk to the
⭐     bank. ⭐⭐ THE ***SEQUENCE*** SURVIVES; THE ***MECHANISM***
⭐     DOES NOT. ***APPLICATION.***
⭐   ⭐ "A refund cannot exceed the amount paid" ⇒ ⭐⭐ YES.
⭐     ***DOMAIN*** — and note it is a rule about two numbers,
⭐     which is why it belongs in an entity and not in a
⭐     service that happens to have both numbers to hand.
```

# Part 2 — ⭐⭐ What the service owns

```
⭐   ⭐ ① ⭐⭐ THE TRANSACTION BOUNDARY (Day 256) — the one
⭐        thing only it can own, because the domain must not
⭐        know about transactions and the web layer must not
⭐        hold them.
⭐   ⭐ ② ORCHESTRATION — the order of steps, and which of them
⭐        are inside the transaction and which are outside.
⭐   ⭐ ③ TRANSLATION — DTO in, DTO out. ⭐ The domain never
⭐        sees a request schema and the web never sees an entity
⭐        (Day 299).
⭐   ⭐ ④ CALLING PORTS — payments, email, search (Day 300).
⭐   ⭐ ⑤ AUTHORISATION AT THE ***OPERATION*** LEVEL, when it
⭐        depends on data — ⭐ role checks belong at the edge
⭐        (Day 259), but "may this user cancel THIS order"
⭐        needs the order.

⭐⭐ AND THE FOUR REFUSALS (Day 256, restated because they are
⭐   the ones that decay):
⭐   ⭐ ❌ no HTTP concepts — ⭐⭐ IF IT RAISES `HTTPException`
⭐     IT CANNOT BE CALLED BY A WORKER, WHICH IS THE TEST
⭐   ⭐ ❌ no business rules that belong in an entity
⭐   ❌ no SQL — that is the repository's job (Day 301)
⭐   ⭐ ❌ no network call inside a transaction
```

# Part 3 — ⭐⭐ The anaemic domain, diagnosed and repaired

```python
# ❌ EVERYTHING IN THE SERVICE
def complete_job(self, job_id, tenant_id, completed_at, notes):
    job = self.uow.jobs.get(job_id)
    if job.tenant_id != tenant_id:            # ⭐ authorisation
        raise Forbidden()
    if job.status != "in_progress":           # ⭐⭐ DOMAIN RULE
        raise InvalidTransition()
    if completed_at < job.started_at:         # ⭐⭐ DOMAIN RULE
        raise ValidationError()
    job.status = "completed"                  # ⭐⭐ DOMAIN CHANGE
    job.completed_at = completed_at
    job.duration_minutes = (completed_at - job.started_at).seconds // 60
    self.uow.outbox.add(JobCompleted(job.id))
    self.uow.commit()
```

```
⭐⭐ THE PROBLEM IS NOT LENGTH — IT IS THAT THREE DOMAIN RULES
⭐   ARE NOW ***REACHABLE ONLY THROUGH THIS ONE PATH***.
⭐   ⇒ ⭐ The technician's mobile sync writes `status` directly.
⭐   ⇒ ⭐ A bulk import sets `completed_at` without a duration.
⭐   ⇒ ⭐⭐ AND THE ADMIN SCRIPT SOMEONE RUNS AT 2 A.M. DOES
⭐     BOTH. ⭐ Each path re-implements two of the three rules
⭐     and forgets the third.
```

```python
# ⭐⭐ THE RULES MOVE INTO THE ENTITY
class Job:
    def complete(self, at: datetime) -> None:
        if self.status is not Status.IN_PROGRESS:
            raise InvalidTransition(self.status, Status.COMPLETED)
        if at < self.started_at:
            raise CompletionBeforeStart(at, self.started_at)
        self.status = Status.COMPLETED
        self.completed_at = at
        self.duration_minutes = (at - self.started_at).seconds // 60

# ⭐ THE SERVICE KEEPS THE SEQUENCING
def complete_job(self, cmd: CompleteJob) -> JobDTO:
    with self.uow:
        job = self.uow.jobs.get_for_tenant(cmd.job_id, cmd.tenant_id)
        job.complete(cmd.completed_at)          # ⭐⭐ ONE LINE
        self.uow.outbox.add(JobCompleted(job.id))
        self.uow.commit()
    return JobDTO.from_domain(job)
```

```
⭐⭐ WHAT CHANGED, AND IT IS NOT AESTHETICS:
⭐   ⭐ The rule now has ***ONE HOME***, so the mobile sync and
⭐     the import call `job.complete()` and cannot bypass it.
⭐   ⭐ `duration_minutes` can no longer be inconsistent with
⭐     its own inputs — ⭐⭐ THE INVARIANT MOVED INSIDE THE
⭐     THING IT CONSTRAINS.
⭐   ⭐ The rule is testable in microseconds with no database.
⭐   ⭐ And the service now reads like a ***description of the
⭐     use case***, which is what a service is for.
```

# Part 4 — ⭐⭐ Where cross-aggregate rules go

```
⭐⭐ THE AWKWARD CASE, AND IT IS THE ONE THAT ACTUALLY COMES UP:
⭐   ⭐ "A technician may not be assigned two overlapping jobs."
⭐   ⇒ ⭐ It involves TWO assignments, so it lives in neither.
⭐   ⇒ ⭐⭐ AND PUTTING IT IN THE SERVICE MAKES IT APPLICATION
⭐     LOGIC, WHICH IS A LIE — it would exist on paper.

⭐⭐ THREE PLACES IT CAN GO, IN ORDER OF PREFERENCE:
⭐   ① ⭐⭐ A DATABASE CONSTRAINT — `EXCLUDE USING gist`
⭐        (Day 250). ⭐ The only option that makes it impossible
⭐        rather than merely checked, ⭐⭐ INCLUDING FROM A
⭐        SCRIPT AND A MIGRATION.
⭐   ② ⭐ A ***DOMAIN SERVICE*** — a pure function in `domain/`
⭐        taking the relevant objects:
⭐        `def overlaps(existing: list[Assignment], new: Assignment) -> bool`
⭐        ⭐ Still domain, still testable without a database,
⭐        ⭐ just not a method on one entity because it isn't
⭐          about one entity.
⭐   ③ ⭐ THE APPLICATION SERVICE — ⭐⭐ THE LAST RESORT, AND
⭐        ONLY WHEN THE RULE GENUINELY DEPENDS ON I/O.
⭐   ⇒ ⭐⭐ IN PRACTICE: ① AND ② TOGETHER. THE CONSTRAINT MAKES
⭐     IT IMPOSSIBLE; THE DOMAIN SERVICE LETS YOU GIVE A GOOD
⭐     ERROR MESSAGE BEFORE THE CONSTRAINT FIRES. ⭐ Neither is
⭐     redundant: one is correctness, one is user experience.
```

# Part 5 — ⭐ Modules of functions, or use-case classes?

```
⭐⭐ THE JAVA/DDD DEFAULT IS ONE CLASS PER USE CASE:
⭐   `class CompleteJobHandler:` with `__init__(self, uow, clock)`
⭐   and one `handle()` method.
⭐   ⭐ + Explicit dependencies, trivially injectable, small.
⭐   ⭐ − ⭐ One file per operation, and forty of them.

⭐⭐ THE PYTHONIC DEFAULT IS A MODULE OF FUNCTIONS:
⭐   `services/jobs.py` with `complete_job(uow, cmd)`.
⭐   ⭐ + Reads well, imports are cheap, no ceremony.
⭐   ⭐ − ⭐ Dependencies arrive as parameters on every call.

⭐ ⇒ ⭐⭐ IN PYTHON, START WITH FUNCTIONS. ⭐ A function taking
⭐   `uow` explicitly is DI already (Day 303), and it is
⭐   testable without constructing anything.
⭐ ⇒ ⭐ MOVE TO A CLASS when a group of operations shares three
⭐   or more dependencies — ⭐⭐ AT WHICH POINT THE CLASS IS
⭐   DOING REAL WORK (holding the wiring) RATHER THAN
⭐   CEREMONIAL WORK.
⭐ ⇒ ⭐⭐ AND EITHER WAY, TAKE A ***COMMAND OBJECT***, NOT
⭐   SEVEN ARGUMENTS. ⭐ It gives the operation a name, makes
⭐   the inputs validatable in one place, and — ⭐ Day 298 —
⭐   converts connascence of position into connascence of name.
```

# Part 6 — ⭐⭐ The smells, and what each one means

```
⭐   ⭐⭐ `request` OR `Request` IN A SERVICE SIGNATURE
⭐        ⇒ the service is HTTP-shaped and no worker can call
⭐          it. ⭐ The single fastest smell to check for: grep.
⭐   ⭐⭐ A SERVICE METHOD NAMED AFTER A ROUTE (`post_orders`)
⭐        ⇒ ⭐ it is a controller in a different directory.
⭐          Name it for the business operation.
⭐   ⭐ A DOMAIN OBJECT IMPORTING `session` OR A REPOSITORY
⭐        ⇒ ⭐⭐ THE DEPENDENCY ARROW REVERSED (Day 300); the
⭐          entity can now do I/O, and your "pure" unit tests
⭐          are hitting a database.
⭐   ⭐ A SERVICE THAT CALLS ANOTHER SERVICE
⭐        ⇒ ⭐⭐ TWO TRANSACTION BOUNDARIES, AND THE INNER ONE
⭐          CAN COMMIT WHILE THE OUTER ROLLS BACK (Day 256).
⭐          ⭐ Extract the shared part into a domain service or
⭐            a function both call inside ONE transaction.
⭐   ⭐ THE SAME `if` IN THREE SERVICES
⭐        ⇒ ⭐ a domain rule with no home (Day 299).
⭐   ⭐ A SERVICE METHOD OVER ~40 LINES
⭐        ⇒ ⭐ usually a domain rule hiding in an orchestration,
⭐          ⭐⭐ AND IT IS ALMOST ALWAYS THE `if` STATEMENTS
⭐          THAT BELONG ELSEWHERE, not the sequencing.
```

# Part 7 — ⭐ The payoff you can measure

```
⭐   ⭐ DOMAIN TESTS: hundreds, ⭐⭐ SUB-SECOND, NO FIXTURES.
⭐     ⭐ If yours need a database, the rules are still in
⭐       services (Day 300's speed test).
⭐   ⭐ SERVICE TESTS: fewer, against real Postgres, ⭐ asserting
⭐     sequencing, transactions and error mapping.
⭐   ⭐⭐ AND THE STRUCTURAL TEST THAT SETTLES THE ARGUMENT:
⭐     ***CAN A CELERY TASK CALL THIS SERVICE, UNCHANGED?***
⭐     ⇒ ⭐ You built the worker in Days 264–265. ⭐⭐ SO THIS
⭐       IS NOT HYPOTHETICAL — GO AND CHECK. Every service the
⭐       worker cannot call is one with HTTP leaked into it, and
⭐       you will find at least one.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| No stated rule for where logic goes | The paper-form test resolves almost every argument. |
| Rules in the service "because it has the data" | Then the mobile sync and the import bypass them. |
| Treating the anaemic domain as a style issue | It's a correctness issue: the rule is reachable by only one path. |
| A derived field set by the caller | The invariant belongs inside the thing it constrains. |
| Putting a cross-aggregate rule in the service | It would exist on paper, so calling it application logic is a lie. |
| Only a domain service for an overlap rule | A constraint makes it impossible; the domain service makes the error good. |
| One class per use case by default in Python | A function taking `uow` is already DI. Move to a class when wiring justifies it. |
| Seven positional arguments | A command object names the operation and converts position into name. |
| `HTTPException` in a service | A worker can't call it — that's the test. |
| Service methods named after routes | It's a controller in a different directory. |
| A domain object importing the session | The arrow reversed, and your unit tests hit a database. |
| A service calling another service | Two transaction boundaries; the inner can commit while the outer rolls back. |
| Long service methods accepted as normal | It's usually the `if` statements, not the sequencing. |
| Domain tests that need fixtures | The rules are still in the services. |

## Interview questions

**Q: How do you decide whether logic goes in the entity or the service?**

> One question: would this rule still exist if the application were a paper form processed by a clerk?
> "Only pending orders can be cancelled" — yes, the clerk would refuse, so it's domain. "Cancelling
> sends an email and refunds via Stripe" — no; the sequence survives but the mechanism doesn't, so
> it's application. That test resolves nearly every argument, and it has a nice property: it stops
> people putting a rule in a service just because the service happens to have both values to hand.

**Q: What's actually wrong with an anaemic domain?**

> It's a correctness problem, not a style one. If the rule lives in the service, it's reachable only
> through that one path — so the mobile sync writes the status directly, a bulk import sets a
> completion time with no duration, and the admin script at 2 a.m. does both. Each path
> re-implements two of the three rules and forgets the third. Moving `complete()` onto the entity
> gives the rule one home, makes the derived field impossible to leave inconsistent with its inputs,
> and makes it testable in microseconds. The service then reads like a description of the use case,
> which is what it's for.

**Q: Where does "a technician can't have two overlapping jobs" live?**

> Nowhere comfortable, which is why it's the interesting case — it involves two assignments, so it
> belongs to no single entity, and putting it in the service would call it application logic, which is
> a lie because it would exist on paper. I use two things together: an `EXCLUDE` constraint in the
> database, which is the only option that makes it impossible rather than merely checked — including
> from a script or a migration — and a pure domain service that checks it first so I can return a good
> error message before the constraint fires. Neither is redundant: one is correctness, the other is
> user experience.

**Q: Classes or functions for services?**

> Functions, in Python, until the wiring justifies otherwise. A function that takes the unit of work as
> a parameter is already dependency injection and is testable without constructing anything. I move to
> a class when a group of operations shares three or more dependencies, because at that point the class
> is doing real work holding the wiring rather than ceremonial work. Either way the operation takes a
> command object rather than seven arguments — it names the operation, puts validation in one place,
> and turns connascence of position into connascence of name.

**Q: How do you know your service layer is clean?**

> One structural test: can a Celery task call this service unchanged? I actually have workers, so it's
> not hypothetical — and every service the worker can't call has HTTP leaked into it, usually an
> `HTTPException` raised for a business condition. Beyond that: domain tests run in under a second with
> no fixtures, and if they need a database then the rules are still in the services regardless of what
> the directory is called.

13. ⭐ Time your domain test suite. If it isn't sub-second, find the fixture and the rule hiding behind it.

## 🎙️ Articulation drill

**Two minutes: "Where does business logic live in your application?"**

Lead with the test, because it's the reusable part: **would this rule still exist if the application
were a paper form processed by a clerk?** Yes means domain — "only pending orders can be cancelled",
because the clerk would refuse. No means application — "cancelling sends an email and refunds via
Stripe", where the sequence survives but the mechanism doesn't. Then say what the service owns: **the
transaction boundary, which is the one thing only it can own**, orchestration, translation, and calls
to ports. Then explain why the anaemic domain is a correctness problem rather than a style one:
**if the rule lives in the service it's reachable through one path only**, so the mobile sync writes
the status directly, the bulk import forgets the derived field, and the admin script does both. Moving
it into the entity gives the rule one home and makes the derived value impossible to leave
inconsistent. Cover the awkward case honestly: a rule spanning two aggregates belongs to neither, so
**an `EXCLUDE` constraint makes it impossible and a pure domain service makes the error message
good** — correctness and user experience, not redundancy. Close on the structural test: **can a Celery
task call this service unchanged?** You have workers, so it isn't hypothetical, and every service that
fails it has HTTP leaked into it.
