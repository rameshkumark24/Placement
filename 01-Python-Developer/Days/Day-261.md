# Day 261 🏗️

**P-261** · 🧪 **Testing the backend** — ⭐⭐ the four types that catch what matters

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: coverage measures which lines ran, not which behaviours are protected.
> A suite at 92% that mocks the database has verified that your Python parses — and every guarantee
> you actually made lives in a constraint, a transaction or a race that mocks cannot reach.**
>
> ⭐ Your invariants table (Day 250) already has a "how it is proved" column. ⭐⭐ Today that column
> becomes the test plan, and four specific test types do almost all the work.

# Part 1 — ⭐⭐ The shape that actually works here

```
⭐⭐ THE CLASSIC PYRAMID IS DRAWN FOR CODE WHOSE RISK IS IN ITS LOGIC.
⭐   ⭐⭐ YOUR RISK IS IN THE INTERACTIONS: constraints, transactions,
⭐     concurrency, authorisation, query counts. ⭐ So the shape is
⭐     different, and saying so is worth more than reciting the pyramid.

⭐   ⭐ UNIT (domain)        ~200 tests, ⭐⭐ < 1 s total, NO I/O
⭐        ⇒ state machine, value objects, calculations (Day 254)
⭐   ⭐⭐ INTEGRATION (service + real Postgres)   ~150 tests, ~60 s
⭐        ⇒ ⭐⭐ THE BULK OF THE VALUE. Real constraints, real
⭐          transactions, real SQL, real RLS.
⭐   ⭐ API (through the app, real DB)           ~80 tests
⭐        ⇒ status codes, schemas, auth matrix, query ceilings
⭐   ⭐ E2E / smoke (against a deployed URL)     ~5 tests
⭐        ⇒ ⭐⭐ ONLY the paths whose failure means "the deploy is
⭐          broken". ⭐ Slow, flaky-prone, and worth exactly five.

⭐ ⇒ ⭐⭐ THE MIDDLE BAND IS FAT ON PURPOSE. Every argument against
⭐   integration tests ("slow", "brittle") is an argument about a suite
⭐   that shares state between tests — which Part 2 fixes.
```

# Part 2 — ⭐⭐ The fixtures that make integration tests cheap

```python
@pytest.fixture(scope="session")
def engine():                       # ⭐ ONE database, migrated ONCE
    run_migrations(TEST_URL)        # ⭐⭐ via Alembic, not create_all —
    return create_engine(TEST_URL)  #    or you never test your migrations

@pytest.fixture
def session(engine):
    conn = engine.connect()
    outer = conn.begin()                       # ⭐⭐ OUTER TRANSACTION
    s = Session(bind=conn, join_transaction_mode="create_savepoint")
    yield s                                    # ⭐ the service may commit;
    s.close()                                  #   it becomes a savepoint
    outer.rollback()                           # ⭐⭐ EVERYTHING UNDONE
    conn.close()
```

```
⭐⭐ WHY THIS FIXTURE IS THE WHOLE GAME:
⭐   ⭐ Tests run inside a transaction that is rolled back, so ⭐⭐ NO
⭐     TEST SEES ANOTHER'S DATA and there is no truncate step.
⭐   ⭐⭐ `join_transaction_mode="create_savepoint"` MEANS THE CODE UNDER
⭐     TEST CAN CALL `commit()` FOR REAL — it becomes a savepoint
⭐     release inside your outer transaction. ⭐ Without it you must
⭐     avoid committing, which means you are not testing your service.
⭐   ⭐ Speed: a rollback is microseconds; a truncate of 20 tables is
⭐     milliseconds ×  every test.
⭐   ⭐⭐ AND THE LIMITS, STATED HONESTLY — this fixture CANNOT test:
⭐     ⭐ anything with real concurrency (two connections cannot see one
⭐       uncommitted transaction) ⇒ ⭐⭐ concurrency tests need their own
⭐       fixture with real commits and explicit cleanup (Part 3 ②);
⭐     ⭐ `ON COMMIT` behaviour and deferred constraints;
⭐     ⭐ anything that inspects a second connection.
```

```python
# ⭐ FACTORIES, not fixture files — Day 180's argument
def a_job(session, *, tenant=None, state=JobState.SCHEDULED, **kw) -> Job:
    tenant = tenant or a_tenant(session)
    return session.merge(Job(tenant_id=tenant.id, state=state,
                             customer_id=a_customer(session, tenant).id, **kw))
# ⭐⭐ EVERY FACTORY TAKES OVERRIDES AND CREATES ITS OWN DEPENDENCIES.
#    ⭐ A test that says `a_job(session, state=IN_PROGRESS)` states
#      exactly what it cares about; a shared JSON fixture states nothing
#      and every test depends on invisible details of it.
```

# Part 3 — ⭐⭐ The four test types that carry the project

```
⭐⭐ ① QUERY-COUNT CEILINGS (Day 255)
⭐    ⭐ Seed 200 rows. `with max_queries(4): client.get(...)`.
⭐    ⭐⭐ CATCHES: the N+1, and — more importantly — the serialiser
⭐      field someone adds later that touches a new relation. ⭐ That
⭐      diff is the one nobody reviews carefully.
⭐    ⭐ Cost: three lines per endpoint. ⭐⭐ Value: the single highest
⭐      per-line return in the suite.

⭐⭐ ② CONCURRENCY TESTS
⭐    ⭐ Real threads, real connections, real commits, explicit cleanup.
⭐    def test_no_double_booking():
⭐        with ThreadPoolExecutor(50) as ex:
⭐            results = list(ex.map(try_assign, repeat(overlapping)))
⭐        assert results.count("ok") == 1          # ⭐⭐ EXACTLY ONE
⭐    ⭐⭐ ASSERT AN EXACT COUNT, NEVER "at most". "At most one" passes
⭐      when a bug rejects all of them.
⭐    ⭐⭐ AND RUN IT AGAINST POSTGRES, NEVER SQLITE — SQLite silently
⭐      ignores `FOR UPDATE` and has no `EXCLUDE`, so the test would
⭐      prove nothing while passing (Day 172).
⭐    ⭐ Also: the refresh-token race (Day 258), the idempotency race
⭐      (two identical requests, one execution), and the lost update.

⭐⭐ ③ THE AUTHORISATION MATRIX (Day 259)
⭐    ⭐ Parametrised over the grid, plus cross-tenant over every path
⭐      from the route table.
⭐    ⭐⭐ OVERRIDES NOTHING. ⭐ It is the threat model, executable.

⭐⭐ ④ CONTRACT / SCHEMA TESTS (Day 257)
⭐    ⭐ The forbidden-field absence test over every GET route.
⭐    ⭐ The route-table authentication test.
⭐    ⭐ The OpenAPI drift check (Day 260).
⭐    ⭐⭐ ALL THREE ARE PARAMETRISED OVER THE APPLICATION ITSELF, so a
⭐      new endpoint is covered without anyone remembering to add it.
⭐      ⭐⭐ THAT PROPERTY — TESTS THAT ENUMERATE THE APP — IS WORTH
⭐      MORE THAN ANY COVERAGE NUMBER.
```

# Part 4 — ⭐⭐ What not to test, and the tests that only feel like testing

```
⭐ ❌ ① MOCKING YOUR OWN CODE. A test where the service is mocked and
⭐    the router is exercised asserts that you called a function you
⭐    wrote with arguments you chose. ⭐⭐ It fails only when you rename
⭐    something, which is exactly when you did not want a failure.
⭐ ❌ ② FAKE REPOSITORIES (Day 139). ⭐⭐ An in-memory dict has no
⭐    constraints, no transactions, no `EXCLUDE`, no RLS and no N+1 —
⭐    so a suite built on them passes while ***EVERY GUARANTEE YOU MADE
⭐    IS UNTESTED***. ⭐ Fake the payment provider. Never fake Postgres.
⭐ ❌ ③ TESTING GETTERS, `__repr__`, AND PYDANTIC ITSELF. ⭐ You are
⭐    testing a library that has its own tests.
⭐ ❌ ④ ASSERTING ON THE EXACT ERROR MESSAGE TEXT. ⭐⭐ Assert the
⭐    `code`; the message is allowed to change (Day 251).
⭐ ❌ ⑤ SNAPSHOT-TESTING WHOLE JSON RESPONSES. ⭐⭐ Every change updates
⭐    the snapshot, nobody reads the diff, and the test becomes a
⭐    ratchet that records behaviour instead of asserting it.

⭐⭐ AND THE COVERAGE POSITION, STATED SO IT IS DEFENSIBLE:
⭐   ⭐ Coverage tells you what did NOT run. ⭐⭐ That is genuinely
⭐     useful and it is ALL it tells you.
⭐   ⭐ Use it as a FLOOR on new code, not a target overall (Day 281).
⭐   ⭐⭐ THE HONEST CHECK IS MUTATION TESTING: `mutmut` flips a `>` to
⭐     `>=`, deletes a line, and asks whether any test notices.
⭐     ⭐ Run it once on your domain module. ⭐⭐ A surviving mutant in
⭐     the state machine is a hole that 100% coverage did not show you.
```

# Part 5 — ⭐ Flakiness and speed, treated as policy

```
⭐⭐ FLAKINESS IS A SOCIAL PROBLEM BEFORE IT IS A TECHNICAL ONE (Day
⭐   154): one tolerated flaky test teaches the team to re-run CI, and
⭐   after that a real failure is indistinguishable from noise.
⭐   ⭐⭐ THE POLICY: A FLAKY TEST IS QUARANTINED WITHIN A DAY AND FIXED
⭐     OR DELETED WITHIN A WEEK. Write it down now, while there are none.

⭐⭐ THE FIVE CAUSES, AND YOU WILL MEET ALL OF THEM:
⭐   ① ⭐ SHARED STATE — fixed by the rollback fixture.
⭐   ② ⭐⭐ TIME. `datetime.now()` in a test near midnight, a DST
⭐      boundary, a TTL that expires mid-run. ⭐ Day 254's "time is a
⭐      parameter" removes most of this at the source.
⭐   ③ ⭐ ORDERING — a test that passes only after another ran.
⭐      ⭐⭐ `pytest -p no:randomly` off; RUN RANDOMISED so ordering
⭐      dependencies surface immediately rather than in six months.
⭐   ④ ⭐ REAL SLEEPS AND POLLING in async tests. ⭐⭐ Poll with a
⭐      deadline and a tight interval, never `sleep(2)`.
⭐   ⑤ ⭐ EXTERNAL SERVICES — fake them at the HTTP boundary
⭐      (`respx`/`responses`), not by mocking your own client class.

⭐⭐ SPEED, WITH A BUDGET:
⭐   ⭐ unit < 1 s · ⭐ integration + API < 90 s · ⭐ full CI < 5 min.
⭐   ⭐ `pytest -n auto` with a database per worker (`--create-db` or a
⭐     template database) — ⭐⭐ template databases are the trick people
⭐     miss: `CREATE DATABASE x TEMPLATE migrated_db` is far faster than
⭐     re-running migrations per worker.
⭐   ⭐⭐ AND A CI JOB THAT FAILS IF THE SUITE EXCEEDS THE BUDGET. A
⭐     suite that creeps to twelve minutes is a suite people stop
⭐     running locally, and that is how the feedback loop dies.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Applying the classic pyramid unchanged | Your risk is in interactions, not logic. Fatten the integration band. |
| `create_all()` in test setup | You never test your migrations. Run Alembic. |
| Truncating tables between tests | Roll back an outer transaction instead — microseconds, not milliseconds. |
| A fixture that forbids `commit()` | Then you aren't testing your service. Use `create_savepoint`. |
| Running concurrency tests inside the rollback fixture | Two connections can't see one uncommitted transaction. |
| Concurrency tests on SQLite | It ignores `FOR UPDATE` and has no `EXCLUDE`. They pass and prove nothing. |
| `assert count <= 1` in a race test | It passes when a bug rejects everything. Assert exactly. |
| Shared JSON fixture files | Every test depends on invisible details; factories state what they care about. |
| Mocking your own service to test the router | It fails only on a rename. |
| Fake repositories | No constraints, no transactions, no RLS — every guarantee untested. |
| Asserting on error message text | Assert the code; messages are allowed to change. |
| Snapshot-testing whole responses | It records behaviour instead of asserting it, and nobody reads the diff. |
| Treating coverage as a quality measure | It tells you what didn't run. That's all. |
| Never running mutation testing | A surviving mutant is a hole 100% coverage didn't show you. |
| Tolerating one flaky test | The team learns to re-run CI, and real failures become noise. |
| Deterministic test ordering | Ordering dependencies surface in six months instead of today. |
| `sleep(2)` in async tests | Poll with a deadline and a tight interval. |
| Mocking your HTTP client class | Fake at the HTTP boundary so your client code is exercised. |
| No time budget on the suite | It creeps to twelve minutes and people stop running it. |

## Interview questions

**Q: What does your test suite look like?**

> Not a classic pyramid, and I'd say why: the pyramid is drawn for code whose risk is in its logic,
> and my risk is in interactions — constraints, transactions, concurrency, authorisation, query counts.
> So there's a fast base of about two hundred domain unit tests that run in under a second with no I/O,
> a deliberately fat middle band of integration tests against real Postgres where most of the value is,
> a layer of API tests through the app for status codes and schemas, and about five end-to-end smoke
> tests against a deployed URL — only the paths whose failure means the deploy is broken. The usual
> objections to integration tests, that they're slow and brittle, are really objections to suites that
> share state, and the rollback fixture removes that.

**Q: How do integration tests stay fast and isolated?**

> Each test runs inside an outer transaction that's rolled back at the end, with the session bound to
> that connection using `join_transaction_mode="create_savepoint"`. That last part is the key detail:
> it means the code under test can call `commit()` for real and it becomes a savepoint release inside
> my transaction — without it you have to write tests that avoid committing, which means you aren't
> testing your service. Rollback is microseconds where truncating twenty tables is milliseconds times
> every test. Migrations run once per session via Alembic rather than `create_all`, so the migrations
> themselves are exercised. And I'd state the fixture's limits honestly: it can't test real concurrency,
> because a second connection can't see an uncommitted transaction, so race tests need their own
> fixture with real commits and explicit cleanup.

**Q: Which tests actually earn their place?**

> Four types. Query-count ceilings — three lines per endpoint, and they catch not just the original
> N+1 but the serialiser field someone adds six weeks later that touches a new relation, which is the
> diff nobody reviews. Concurrency tests with real threads asserting an *exact* count, because "at most
> one" passes when a bug rejects everything, and run against Postgres rather than SQLite, since SQLite
> silently ignores `FOR UPDATE` and has no exclusion constraints, so the test would pass and prove
> nothing. The authorisation matrix, parametrised over the grid plus cross-tenant over every route, and
> overriding nothing. And contract tests — forbidden-field absence, route-table authentication, and
> the OpenAPI drift check. What those last ones share is that they enumerate the application itself, so
> a new endpoint is covered without anyone remembering — and that property is worth more than any
> coverage number.

**Q: What's your position on coverage?**

> It tells you which lines didn't run, which is genuinely useful and is all it tells you. A suite at
> ninety-two percent that mocks the database has verified that my Python parses, while every guarantee
> I actually made lives in a constraint, a transaction or a race that mocks can't reach. So I use it as
> a floor on new code rather than a target overall, and I'd deliberately not add a threshold at the
> start of a project, because a high gate on an empty repository buys a month of assertion-free tests
> and teaches the team to game the number. The honest check is mutation testing — flip a `>` to `>=`,
> delete a line, and see whether any test notices. Running it once over the domain module is
> illuminating: a surviving mutant in the state machine is a hole that a hundred percent coverage never
> showed you.

**Q: How do you handle flaky tests?**

> As a social problem first. One tolerated flake teaches everyone to re-run CI, and once that's the
> habit a real failure is indistinguishable from noise — so the policy goes in writing while there are
> still none: quarantined within a day, fixed or deleted within a week. Then the five causes, all of
> which you'll meet: shared state, fixed by the rollback fixture; time, mostly removed at source by
> making `now` a parameter rather than something the code reads; ordering, which I surface immediately
> by running tests in randomised order rather than deterministically; real sleeps in async tests,
> replaced by polling with a deadline; and external services, faked at the HTTP boundary rather than by
> mocking my own client class, so my client code is still exercised. And a CI job that fails if the
> suite exceeds its time budget, because a suite that creeps to twelve minutes is one people stop
> running locally.

## 🎙️ Articulation drill

**Two minutes: "How do you test a backend like this?"**

Start by rejecting the default shape with a reason: **the pyramid is drawn for code whose risk is in
its logic, and my risk is in interactions** — constraints, transactions, races, authorisation — so the
integration band is fat on purpose, and the usual objection that integration tests are slow and
brittle is really an objection to shared state. Explain the rollback fixture in one sentence and name
the detail that makes it work: savepoint mode, so the code under test can genuinely commit. Then the
four test types that carry the project, and pick two to expand: **query-count ceilings, which catch
the serialiser field added six weeks later**, and **concurrency tests asserting an exact count, run
against Postgres because SQLite would pass and prove nothing.** Close on coverage: it tells you what
didn't run and nothing else, so it's a floor on new code — and mutation testing is the honest check,
