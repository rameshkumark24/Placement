**Time:** 3 hrs · **Mode:** BUILD

# Part 1 — ⭐⭐ The dashboard that is actually useful

```
⭐⭐ FOUR PANELS. NOT FORTY. ⭐ A dashboard with forty panels is one nobody
⭐   reads at 3 a.m., and the point of a dashboard is 3 a.m.

⭐  1. ⭐⭐ RED (Day 147) — rate, ERROR RATIO, p50/p95/p99, ⭐ SPLIT BY VERSION
⭐       (Day 155) so a deploy's effect is visible without a second query.
⭐  2. ⭐⭐ SATURATION — DB pool in-use / waiting / WAIT TIME · queue depth ·
⭐       ⭐ OLDEST message age · event-loop lag. ⭐⭐ These move BEFORE latency
⭐       does, which is what makes them worth a panel.
⭐  3. ⭐⭐ THE BUSINESS PANEL — the one engineers skip and the one that
⭐       catches real incidents: ⭐ holds created/min · orders/min ·
⭐       ⭐⭐ `count(status='payment_unknown')` · outbox oldest age ·
⭐       webhook delivery success by endpoint.
⭐  4. ⭐ DEPENDENCIES — payment provider p95 and error rate, breaker state.

⭐⭐ WHY PANEL 3 EARNS ITS PLACE: ⭐ every technical metric can look perfect
⭐   while orders/min is ZERO. ⭐⭐ A bug that makes every purchase fail
⭐   validation returns a fast, correct 422 — ⭐ no errors, no latency, no
⭐   saturation. ⭐⭐ THE ONLY SIGNAL IS THAT NOBODY IS BUYING ANYTHING.
⭐   ⇒ ⭐ Day 147's "alert on absence", made concrete for this system.
```

```
⭐⭐ THE FIVE ALERTS. IF IT WOULD NOT WAKE YOU, IT IS A DASHBOARD, NOT AN
⭐   ALERT (Day 147):
⭐   ⭐ ERROR-BUDGET FAST BURN (14.4× over 1 h)      ⇒ page
⭐   ⭐ ERROR-BUDGET SLOW BURN (3× over 6 h)          ⇒ ticket
⭐   ⭐⭐ ORDERS/MIN == 0 FOR 10 MIN DURING AN ON-SALE ⇒ page
⭐        ⭐ (absence — the alert nothing else can produce)
⭐   ⭐⭐ OUTBOX OLDEST AGE > 60 s                     ⇒ page (the relay is dead)
⭐   ⭐ `payment_unknown` COUNT > 10 OR RISING        ⇒ page (provider trouble)
⭐   ⇒ ⭐⭐ NOTHING ELSE. ⭐ CPU, memory and disk are dashboards. ⭐⭐ A page for
⭐        high CPU wakes you for a machine doing its job and trains you to
⭐        ignore pages — which is how the real one gets missed.
```

# Part 2 — ⭐⭐ Build the N+1 deliberately, then let the tooling find it

```python
# ⭐ api/reports.py — the naive version. Write this ON PURPOSE.
@router.get("/events/{event_id}/report")
def event_report(event_id: int, ctx = Depends(get_organiser_context),
                 db: Session = Depends(get_db)) -> ReportOut:
    event = repo.get_event(event_id, organiser_id=ctx.organiser_id)
    rows = []
    for tt in event.ticket_types:                     # ⭐ query 2 (lazy load)
        for order in tt.orders:                       # ⭐⭐ query 3..N
            rows.append(ReportRow(
                buyer=order.user.email,               # ⭐⭐ query N..2N
                qty=order.qty, total=order.total_cents,
            ))
    return ReportOut(rows=rows)
```

```
⭐⭐ NOW DO NOT READ THE CODE. LET EACH TOOL FIND IT IN TURN — ⭐ the point of
⭐   today is confirming your instrumentation works, not fixing a bug you
⭐   already know about:

⭐  1. ⭐⭐ THE QUERY-COUNT CEILING (Day 141) FAILS FIRST, IN CI:
⭐       `assert len(query_counter) <= 4` ⇒ ⭐ got 213.
⭐       ⭐⭐ This is the only defence that catches it BEFORE production, on
⭐       the commit that introduced it, with the author still holding context.
⭐  2. ⭐ THE TRACE (Day 148) SHOWS THE STAIRCASE — 200 identical thin
⭐       sequential spans. ⭐⭐ Visible from across the room.
⭐  3. ⭐⭐ THE SLOW-QUERY LOG SHOWS **NOTHING**. ⭐ Every one of those 213
⭐       queries is 0.2 ms. ⭐⭐ THAT IS THE PROPERTY THAT LETS N+1s SURVIVE IN
⭐       SYSTEMS WITH MONITORING, and you should see the empty log yourself.
⭐  4. ⭐ `py-spy record` (Day 157) SHOWS THE REPEATED NARROW TOWER — ⭐⭐ or, if
⭐       you profile without `--idle`, it shows almost nothing, because you
⭐       are WAITING, not busy.

⭐   ⇒ ⭐⭐ FIX WITH LOADING STRATEGIES, DERIVED NOT MEMORISED (Day 136):
⭐        `selectinload(TicketType.orders)` — TO-MANY, ⭐ separate query, no
⭐          row multiplication
⭐        `.joinedload(Order.user)`          — TO-ONE, ⭐ one join, no fan-out
⭐        ⇒ ⭐ 213 queries → 3. ⭐⭐ Then SET THE CEILING AT 4 AND LEAVE IT.
⭐   ⇒ ⭐⭐ AND `lazy="raise"` ON EVERY RELATIONSHIP, so the NEXT one is an
⭐        exception at development time rather than a slow page in production.
⭐        ⭐ Day 118's principle: make the wrong thing hard to write.
```

# Part 3 — ⭐⭐ Hardening: the pass over everything you built

```
⭐⭐ WORK THE LIST. EACH LINE IS ONE EARLIER DAY, AND EACH IS A REAL BUG IF
⭐   MISSING:

⭐  ⭐ INPUT (Days 119, 131)
⭐    □ every list endpoint has a BOUNDED `limit` ⭐⭐ (`le=100`)
⭐    □ every string field has `max_length` — ⭐ a 10 MB event name is a
⭐         database problem and a rendering problem
⭐    □ ⭐⭐ separate In/Out/Update models; `EventCreate` HAS NO `organiser_id`
⭐         (mass assignment) and no `id`
⭐    □ ⭐⭐ THE OUTPUT SCHEMA IS THE SECURITY CONTROL — a test asserts
⭐         `password_hash` and `$argon2` appear in NO response body
⭐
⭐  ⭐ ERRORS (Day 120)
⭐    □ ONE shape everywhere, including 422 — ⭐⭐ override
⭐         `RequestValidationError` or you ship two error formats
⭐    □ ⭐ no internal detail leaks: no SQL, no file paths, no library names
⭐    □ ⭐⭐ the 500 handler logs with `trace_id` and returns the trace id to
⭐         the caller — ⭐ so a bug report is one query, not an archaeology dig
⭐
⭐  ⭐ HTTP (Days 124, 127)
⭐    □ ⭐⭐ `Cache-Control: no-store` on every authenticated response — ⭐ or a
⭐         shared cache serves one attendee's order to another
⭐    □ CORS: an explicit origin list, ⭐⭐ never `*` with credentials
⭐    □ security headers: `nosniff`, `X-Frame-Options`, HSTS
⭐    □ ⭐ `/metrics` on an internal port; `/docs` off in production
⭐
⭐  ⭐ LIMITS (Days 152, 153)
⭐    □ ⭐⭐ a timeout on EVERY outbound call — ⭐ grep for `httpx`/`requests`
⭐         and check each one
⭐    □ `statement_timeout` and `lock_timeout` set on the pool
⭐    □ ⭐⭐ rate limits: login (IP + account), hold creation PER USER
⭐         (⭐ the hold-exhaustion abuse case from Day 162), and a global cap
⭐    □ ⭐ a request body size limit at the proxy (Day 145)
⭐
⭐  ⭐ DATA (Days 138, 146, 150)
⭐    □ ⭐⭐ no PII in logs: user ids not emails, and the redaction processor
⭐         is a TEST, not a habit
⭐    □ `SecretStr` for every secret; ⭐ `print(settings)` in a test asserts
⭐         nothing leaks
⭐    □ ⭐ migrations are expand-only, with `lock_timeout`
```

# Part 4 — ⭐ Caching, deliberately narrow

```python
# ⭐ the ONE thing worth caching here — and note what is NOT cached
def get_public_event(db: Session, event_id: int) -> EventOut:
    key = f"event:v1:{event_id}"                       # ⭐⭐ v1 — Day 143's rolling deploy
    if (raw := r.get(key)) is not None:
        return EventOut.model_validate_json(raw)
    out = EventOut.model_validate(repo.get_public(db, event_id))
    r.set(key, out.model_dump_json(), ex=60 + random.randint(0, 20))   # ⭐⭐ TTL + jitter
    return out
```

```
⭐⭐ THE DECISIONS, AND THE NEGATIVE ONES MATTER MORE:
⭐   ⭐ CACHE the public event page: hot, ⭐ and "60 seconds stale" is an
⭐        acceptable answer to Day 143's first question.
⭐   ⭐⭐ DO **NOT** CACHE `quantity_sold` FOR THE PURCHASE DECISION. ⭐ Cache
⭐        it for DISPLAY ("12 left") if you like; ⭐⭐ the decision reads the
⭐        row under a lock, always. ⭐ Day 143: if "how long may this be
⭐        wrong?" is "never", the answer is not a cache.
⭐   ⭐⭐ DO NOT CACHE ANYTHING TENANT- OR USER-SCOPED WITHOUT THE ID IN THE
⭐        KEY. ⭐ That is the shared-cache leak, inside your own process.
⭐   ⭐ ON WRITE: ⭐⭐ WRITE THE DATABASE, THEN DELETE THE KEY. ⭐ Not update,
⭐        not delete-first.
⭐   ⭐ TTL JITTER, because ⭐⭐ 5,000 event pages warmed at deploy with an
⭐        identical TTL expire in the same second, forever after.
⭐
⭐ ⭐⭐ AND THE ON-SALE CASE, WHICH IS WHY THIS SECTION IS SHORT: at 10:00,
⭐   50,000 people load ONE event page. ⭐ A 60-second cache turns 50,000
⭐   database reads into ~1 — ⭐⭐ but the PURCHASE path is uncacheable by
⭐   definition, so caching does nothing for the part that will actually
⭐   break tomorrow. ⭐ Know which half you helped.
```

# Part 5 — ⭐⭐ The self-review

```
⭐⭐ REVIEW YOUR OWN CODE AS A STRANGER (Day 101). ⭐ In this order, because
⭐   order is what makes a review find things:

⭐  1. ⭐⭐ READ THE TESTS FIRST. ⭐ What do they claim? What is NOT claimed?
⭐       ⭐⭐ The gap between "what my tests assert" and "what my README
⭐       promises" is where the bugs are.
⭐  2. ⭐ READ THE MIGRATIONS. Is any of them destructive? Would a rollback
⭐       work?
⭐  3. ⭐⭐ FOR EVERY ENDPOINT ASK: "WHAT HAPPENS IF THIS IS CALLED TWICE,
⭐       CONCURRENTLY, BY THE WRONG USER, WITH A HUGE PAYLOAD, WHEN THE
⭐       DATABASE IS SLOW?" ⭐ Five questions, every route. ⭐⭐ Most bugs you
⭐       will ever have are one of those five.
⭐  4. ⭐ GREP FOR THE SPECIFICS:
⭐       `httpx|requests` without `timeout=` · `except:`/`except Exception:`
⭐       that swallow · `print(` · `TODO` · `.all()` without a `limit`
⭐       · `commit()` outside a service · `HTTPException` inside `services/`
⭐  5. ⭐⭐ RUN THE APP WITH THE DATABASE STOPPED. ⭐ What does the user see?
⭐       ⭐⭐ Is it your error shape or a 500 with a traceback? ⭐ Does
⭐       `/readyz` go 503 while `/healthz` stays 200 (Day 149)?

⭐⭐ AND THE THREE QUESTIONS THAT ARE WORTH MORE THAN ANY CHECKLIST:
⭐   ⭐ "WHAT IS THE WORST THING A LOGGED-IN USER CAN DO?" ⭐ Answer it
⭐        honestly, then test that answer.
⭐   ⭐ "IF I GET PAGED AT 3 A.M., WHAT IS MY FIRST QUERY?" ⭐⭐ If you cannot
⭐        name it, your observability is decorative.
⭐   ⭐ "WHAT WOULD I HAVE TO DO TO LOSE A CUSTOMER'S MONEY?" ⭐⭐ Every path
⭐        you find is either impossible, tested, or a ticket. ⭐ There is no
⭐        fourth category.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| A forty-panel dashboard | Nobody reads it at 3 a.m., which is the only time it matters. |
| No business metrics | A validation bug returns fast, correct 422s — the only signal is that nobody is buying. |
| Alerting on CPU or memory | Wakes you for a machine doing its job and trains you to ignore pages. |
| Fixing the N+1 by reading the code | You learn nothing about whether your tooling works. |
| Expecting the slow-query log to show an N+1 | Every one of those 213 queries is fast. That's why they survive. |
| `joinedload` for a to-many relationship | Row multiplication. `selectinload` for to-many, `joinedload` for to-one. |
| Fixing the N+1 without setting a ceiling | The next one ships silently. |
| No `lazy="raise"` after the fix | You fixed this instance rather than the class. |
| Unbounded `limit` or unbounded string fields | A client asks for a million rows, or names an event 10 MB. |
| `organiser_id` accepted on a create model | Mass assignment straight into another tenant. |
| Not overriding `RequestValidationError` | You ship two different error formats. |
| Authenticated responses without `no-store` | A shared cache serves one attendee's order to another. |
| An outbound call without a timeout | One slow dependency consumes every worker, health check included. |
| Caching `quantity_sold` for the purchase decision | "How long may this be wrong?" is "never" — so it isn't cacheable. |
| Cache key without the tenant or user | The shared-cache leak, inside your own process. |
| Identical TTLs on bulk-warmed keys | Every event page expires in the same second, forever. |
| Reviewing the code before the tests | The gap between what tests assert and what the README promises is where bugs live. |
| Never running the app with the database down | You've no idea what a user sees during your most likely incident. |

## Interview questions

**Q: What's on your dashboard?**

> Four panels. RED — rate, error ratio, and percentiles split by version so a deploy's effect is
> visible without a second query. Saturation — pool wait time, queue depth, oldest message age,
> event-loop lag — because those move before latency does, which is what makes them worth watching.
> Dependencies, with the provider's p95 and the breaker state. And the one engineers skip: business
> metrics — orders per minute, holds per minute, the count of orders sitting in `payment_unknown`,
> outbox age. That panel earns its place because every technical metric can look perfect while
> nobody can buy anything: a bug that makes every purchase fail validation returns a fast, correct
> 422, so there are no errors, no latency and no saturation. The only signal is absence.

**Q: You built the report endpoint as an N+1 on purpose. Why?**

> To find out whether my instrumentation actually works, rather than to fix a bug I already knew
> about. The query-count ceiling in CI fails first — 213 against a limit of 4 — which is the only
> defence that catches it before production, on the commit that introduced it. The trace shows the
> staircase of identical thin spans, visible instantly. And the slow-query log shows *nothing*, which
> is the thing I wanted to see with my own eyes: every one of those queries is a fraction of a
> millisecond, and that's exactly why N+1s survive in systems that have monitoring. Then I fix it
> with `selectinload` for the to-many and `joinedload` for the to-one, set the ceiling at four, and
> add `lazy="raise"` — so I've fixed the class rather than the instance.

**Q: What do you cache, and what do you refuse to cache?**

> The public event page, with a sixty-second TTL plus jitter and a version segment in the key. At an
> on-sale, fifty thousand people load one event page, so that turns fifty thousand database reads
> into roughly one. What I refuse to cache is `quantity_sold` for the *purchase decision* — I'll
> cache it for display, showing "12 left", but the decision reads the row under a lock every time,
> because if the answer to "how long may this be wrong" is "never", then it isn't a cache. And
> nothing tenant- or user-scoped without the id in the key, since that's the shared-cache leak inside
> my own process. Worth saying honestly: caching helps the browse path and does nothing for the
> purchase path, which is the half that will actually break under load.

**Q: How do you review your own work?**

> Tests first, because the gap between what my tests assert and what my README promises is where the
> bugs are. Then the migrations, asking whether any is destructive and whether a rollback would work.
> Then five questions at every endpoint: what happens if this is called twice, concurrently, by the
> wrong user, with a huge payload, when the database is slow — most bugs I will ever have are one of
> those five. Then targeted greps: HTTP calls without timeouts, bare excepts, `.all()` without a
> limit, `commit()` outside a service, `HTTPException` inside `services/`. And finally I run the app
> with the database stopped and look at what a user actually sees, because that's my most likely
> incident and I'd rather find out now than during it.

## 🎙️ Articulation drill

**Two minutes: "How do you know your service is healthy?"**

validation bug returns fast correct 422s, so every technical signal is green while nobody can buy
anything. Then the alerting discipline — five alerts, symptoms not causes, and one on absence. Then
tell the N+1 story as evidence rather than theory: you wrote it deliberately, and the ceiling caught
