# Part 1 — ⭐ Two pools, two jobs

```
⭐   ┌── app instance 1 ──┐  ┌── app instance 2 ──┐   ⭐ 3 instances ×
⭐   │ worker × 8         │  │ worker × 8         │     8 workers = 24
⭐   │  ↓ SQLAlchemy pool │  │  ↓ SQLAlchemy pool │     PROCESSES
⭐   │  5 + 10 overflow   │  │  5 + 10 overflow   │   ⭐⭐ EACH WITH ITS
⭐   └────────┬───────────┘  └────────┬───────────┘     ***OWN*** POOL
⭐            └──────────┬─────────────┘
⭐                  ┌────▼─────┐   ⭐⭐ 24 × 15 = 360 POSSIBLE
⭐                  │ PgBouncer │      CONNECTIONS ARRIVE HERE
⭐                  └────┬─────┘
⭐                       │        ⭐⭐ AND ONLY 25 LEAVE
⭐                  ┌────▼─────┐
⭐                  │ Postgres │  max_connections = 100
⭐                  └──────────┘

⭐⭐ THE APPLICATION POOL EXISTS TO: avoid a TCP handshake + auth per
⭐   request, and to CAP how many queries one process runs at once.
⭐   ⭐ It cannot help across processes — it does not know they exist.
⭐⭐ PGBOUNCER EXISTS TO: make the number of Postgres BACKENDS
⭐   independent of the number of application PROCESSES.
⭐   ⭐ It cannot save you a round trip inside one process.
```

# Part 2 — ⭐⭐ The SQLAlchemy pool, parameter by parameter

```python
engine = create_engine(
    url,
    pool_size=5,          # ⭐ steady-state connections kept open
    max_overflow=10,      # ⭐⭐ EXTRA connections allowed under burst,
                          #    CLOSED when returned. ⭐ SO YOUR REAL
                          #    CEILING IS 15, NOT 5 — and this is the
                          #    number people forget in the arithmetic.
    pool_timeout=10,      # ⭐⭐ seconds to WAIT for a free connection
                          #    before raising `QueuePool limit of size 5
                          #    overflow 10 reached`. ⭐ Default 30 s is
                          #    far too long: it turns pool exhaustion
                          #    into a 30-second hang instead of a fast
                          #    503. Day 152's timeout hierarchy.
    pool_recycle=1800,    # ⭐⭐ close and reopen after 30 min. DEFENDS
                          #    AGAINST: a NAT gateway, firewall or load
                          #    balancer silently dropping idle TCP.
                          #    ⭐ Must be LOWER than the shortest idle
                          #      timeout anywhere in the path.
    pool_pre_ping=True,   # ⭐⭐ cheap `SELECT 1` before handing a
                          #    connection out. Costs a round trip;
                          #    ⭐ buys immunity to "server closed the
                          #      connection unexpectedly" after a
                          #      failover. ⭐⭐ WORTH IT ALMOST ALWAYS.
)
```

```
⭐⭐ THE OTHER POOL CLASSES, AND WHEN EACH IS RIGHT:
⭐   ⭐ QueuePool   — the default. Use it.
⭐   ⭐⭐ NullPool  — no pooling at all; connect per checkout.
⭐        ⭐ RIGHT FOR: AWS Lambda and other environments where the
⭐          process may be frozen between invocations (a pooled socket
⭐          resumed 40 minutes later is dead), ⭐ and sometimes behind
⭐          PgBouncer (Part 5).
⭐   ⭐ StaticPool — one connection, reused. ⭐ Tests with in-memory
⭐        SQLite, essentially nowhere else.
⭐   ⭐⭐ AND THE FORK TRAP: A POOL CREATED BEFORE `fork()` IS SHARED BY
⭐     EVERY CHILD — ⭐⭐ TWO PROCESSES USING ONE SOCKET, WHICH PRODUCES
⭐     GARBLED PROTOCOL ERRORS THAT LOOK LIKE DATA CORRUPTION.
⭐     ⇒ ⭐ gunicorn: create the engine in `post_fork`, or call
⭐       `engine.dispose()` in the worker's startup hook. ⭐ Celery:
⭐       `worker_process_init`. ⭐⭐ THIS BITES EVERY TEAM ONCE.
```

# Part 3 — ⭐⭐ The arithmetic, both halves

```
⭐⭐ HALF ONE — "WILL WE BE REFUSED?" (Day 186's FATAL)
⭐   instances × workers × (pool_size + max_overflow)
⭐   + celery_instances × workers × (pool + overflow)
⭐   + cron jobs + migrations + your psql + the metrics exporter
⭐   ─────────────────────────────────────────────────────────
⭐   ⭐⭐ MUST BE < max_connections − superuser_reserved_connections
⭐
⭐   ⭐ 3 × 8 × 15 = 360.  ⭐⭐ max_connections = 100. YOU ARE 3.6×
⭐     OVER, AND YOU FIND OUT DURING A DEPLOY WHEN EVERY INSTANCE OPENS
⭐     ITS POOL AT ONCE.
```

```
⭐⭐ HALF TWO — "WHAT IS THE RIGHT SIZE?" — and the answer is smaller
⭐   than everyone's instinct.

⭐   ⭐⭐ A CONNECTION THAT IS NOT RUNNING A QUERY IS DOING NOTHING. The
⭐     database can genuinely execute about (cores + effective_spindles)
⭐     queries at once. ⭐ Everything beyond that QUEUES — inside
⭐     Postgres, where you cannot see it, instead of inside your pool,
⭐     where you can.
⭐   ⇒ ⭐⭐ THE CLASSIC HEURISTIC: `connections ≈ 2 × cores + disks`.
⭐     For an 8-core server that is ~20 ACTIVE connections TOTAL,
⭐     across the whole fleet. ⭐ Not per instance. Total.
⭐   ⭐ Little's Law again (Day 156): if each query takes 5 ms and you
⭐     need 4,000 queries/sec, you need 4000 × 0.005 = ⭐⭐ 20
⭐     CONCURRENT CONNECTIONS. ⭐ Not 400. The pool size follows from
⭐     throughput and latency, not from optimism.
⭐   ⇒ ⭐⭐ SO: A SMALL POOL WITH A SHORT `pool_timeout` IS A LOAD
⭐     SHEDDER (Day 152). A HUGE POOL IS AN UNBOUNDED QUEUE THAT MOVES
⭐     THE PROBLEM SOMEWHERE YOU CANNOT INSTRUMENT.
```

# Part 4 — ⭐⭐ PgBouncer: three modes, and what transaction mode breaks

```
⭐⭐ SESSION MODE     — a client keeps its backend until it disconnects.
⭐   ⭐ Everything works. ⭐⭐ AND IT BUYS YOU ALMOST NOTHING: you still
⭐     need one backend per concurrent client. ⭐ Use it only when
⭐     something below genuinely cannot be given up.
⭐⭐ TRANSACTION MODE — ⭐⭐ THE ONE WORTH HAVING. A backend is assigned
⭐   at BEGIN and returned at COMMIT/ROLLBACK.
⭐   ⇒ ⭐⭐ 1,000 IDLE CLIENTS CAN SHARE 25 BACKENDS, because idle
⭐     clients hold none.
⭐⭐ STATEMENT MODE   — returned after every statement. ⭐⭐ MULTI-
⭐   STATEMENT TRANSACTIONS ARE IMPOSSIBLE. Effectively unusable for an
⭐   application; it exists for sharding proxies.
```

```
⭐⭐ WHAT TRANSACTION MODE BREAKS — ***THE CHECKLIST***. Every item is
⭐   the same fact: ⭐⭐ ANYTHING THAT LIVES IN A SESSION RATHER THAN A
⭐   TRANSACTION IS GONE.

⭐ ① ⭐⭐ PREPARED STATEMENTS (Day 186). psycopg3 auto-prepares after 5
⭐    executions ⇒ `prepared statement "_pg3_0" does not exist`.
⭐    ⇒ ⭐ psycopg3: `prepare_threshold=None`. ⭐ asyncpg:
⭐      `statement_cache_size=0`. ⭐⭐ Or PgBouncer 1.21+, which finally
⭐      tracks prepared statements — check your version before assuming.
⭐ ② ⭐⭐ `SET` / `SET search_path` — ⭐⭐ AND THIS IS A ***SECURITY***
⭐    BUG, NOT A COMPATIBILITY ONE. Day 160 set a tenant with
⭐    `SET app.tenant_id` for row-level security. Under transaction
⭐    pooling that setting can persist onto a backend handed to a
⭐    DIFFERENT TENANT'S REQUEST. ⭐⭐ CROSS-TENANT DATA EXPOSURE, WITH
⭐    NO ERROR ANYWHERE.
⭐    ⇒ ⭐⭐ ALWAYS `SET LOCAL` INSIDE THE TRANSACTION (Day 192). Never
⭐      plain `SET`. ⭐ And `server_reset_query` is not a substitute in
⭐      transaction mode — it only runs on session release.
⭐ ③ ⭐ SESSION-SCOPED ADVISORY LOCKS (Day 196) — you may not get the
⭐    same backend back to release it. ⭐⭐ Use `_xact_` variants.
⭐ ④ ⭐ `LISTEN` / `NOTIFY` — the listener may be on a backend nobody
⭐    notifies. ⭐⭐ Silently receives nothing.
⭐ ⑤ ⭐ TEMPORARY TABLES — created on one backend, invisible on the next.
⭐ ⑥ ⭐ `WITH HOLD` CURSORS and server-side named cursors that outlive a
⭐    transaction (Day 186's streaming pattern — check it).
⭐ ⑦ ⭐ Session-level `statement_timeout` set once at connect.
⭐ ⭐⭐ THE ONE-LINE TEST FOR ANY FEATURE: "DOES THIS SURVIVE A COMMIT?"
⭐    If not, it does not survive a transaction pooler either.
```

# Part 5 — ⭐ Running it

```ini
# pgbouncer.ini
[databases]
appdb = host=10.0.0.5 port=5432 dbname=appdb

[pgbouncer]
pool_mode = transaction
max_client_conn = 2000        ; ⭐ how many APP connections may arrive
default_pool_size = 25        ; ⭐⭐ how many BACKENDS per (db,user)
                              ;    ⭐ THIS is the number that must fit
                              ;      inside max_connections
reserve_pool_size = 5         ; ⭐ emergency headroom
reserve_pool_timeout = 3
server_lifetime = 3600        ; ⭐ recycle backends hourly
server_idle_timeout = 600
query_wait_timeout = 15       ; ⭐⭐ fail fast rather than queue forever
ignore_startup_parameters = extra_float_digits, options
```

```
⭐⭐ THE FOUR NUMBERS TO WATCH — `SHOW POOLS;` and `SHOW STATS;`
⭐   ⭐ `cl_active` / `cl_waiting` — ⭐⭐ `cl_waiting > 0` SUSTAINED MEANS
⭐        `default_pool_size` IS TOO SMALL. This is the single most
⭐        important pooler metric and almost nobody graphs it.
⭐   ⭐ `maxwait` — ⭐⭐ the longest a client has waited. It should be 0.
⭐        Any non-zero value is latency your APM will blame on the
⭐        database while the database looks idle.
⭐   ⭐ `sv_active` / `sv_idle` — backend utilisation.
⭐   ⭐ `avg_query_time` vs `avg_wait_time` — ⭐⭐ separates "the database
⭐        is slow" from "the pool is too small". Two different fixes.

⭐⭐ AND THE OPERATIONAL FACTS PEOPLE DISCOVER TOO LATE:
⭐   ⭐⭐ PGBOUNCER IS SINGLE-THREADED. One process saturates one core at
⭐     roughly 10–20k queries/sec. ⭐ Run several with `so_reuseport`,
⭐     or use pgcat/Supavisor which are multi-threaded.
⭐   ⭐⭐ IT IS NOW A SINGLE POINT OF FAILURE ON THE HOT PATH. Run it as
⭐     a SIDECAR on each app node (fault isolation, no extra hop) or as
⭐     a small HA pair. ⭐ A single central instance is the design that
⭐     causes a full outage from one restart.
⭐   ⭐ It adds ~0.1–0.5 ms per query. ⭐⭐ Irrelevant next to what it
⭐     saves — unless your queries are 0.2 ms, in which case measure.
```

```python
# ⭐⭐ DOUBLE POOLING: what to do with the SQLAlchemy pool once PgBouncer
#    is in front. ⭐ The honest answer is "shrink it", not "remove it".
engine = create_engine(
    url,                     # ⭐ pointing at PgBouncer, port 6432
    pool_size=3,             # ⭐⭐ small: PgBouncer does the multiplexing
    max_overflow=2,
    pool_pre_ping=True,
    connect_args={"prepare_threshold": None},   # ⭐ psycopg3 + txn mode
)
# ⭐ WHY NOT `NullPool`? Because you would pay a TCP connect + auth to
#   PgBouncer on every single checkout. ⭐⭐ PgBouncer's auth is cheap
#   but not free, and at 2,000 rps it is measurable.
# ⭐⭐ WHY NOT A BIG POOL? Because every connection your app holds open
#   occupies a `max_client_conn` slot, and an idle-but-checked-out
#   connection inside a transaction holds a BACKEND too. ⭐ A big app
#   pool in front of a transaction pooler recreates the problem you
#   installed the pooler to solve.
# ⇒ ⭐⭐ SMALL APP POOL + LARGE `max_client_conn` + SMALL
#   `default_pool_size`. That is the shape.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Thinking PgBouncer replaces the application pool | They solve different problems: one saves round trips, the other multiplexes processes. |
| Forgetting `max_overflow` in the connection arithmetic | Your ceiling is `pool_size + max_overflow`, not `pool_size`. |
| Leaving `pool_timeout` at 30 s | Pool exhaustion becomes a 30-second hang instead of a fast 503. |
| No `pool_recycle` | A NAT or firewall idle timeout silently kills pooled connections. |
| Creating the engine before `fork()` | Children share one socket; you get protocol errors that look like corruption. |
| Assuming a bigger pool means more throughput | Past `2 × cores`, everything queues inside Postgres where you can't see it. |
| Using session mode "to be safe" | You still need one backend per client, so you've bought almost nothing. |
| Auto-prepared statements through transaction mode | `prepare_threshold=None` / `statement_cache_size=0`, or PgBouncer 1.21+. |
| Plain `SET app.tenant_id` behind a transaction pooler | It can persist onto another tenant's request. `SET LOCAL`, always. |
| Session-scoped advisory locks behind a pooler | You may not get the same backend back. |
| `LISTEN`/`NOTIFY` behind transaction mode | The listener may sit on a backend nobody notifies — silent. |
| Not graphing `cl_waiting` and `maxwait` | The only two numbers that separate "database slow" from "pool too small". |
| One central PgBouncer | Single-threaded, and now a single point of failure on the hot path. |
| Keeping a large app pool after installing PgBouncer | It occupies client slots and recreates the problem you were solving. |

## Interview questions

**Q: You have PgBouncer. Do you still need a pool in the application?**

> Yes, a small one, because they solve different problems. The application pool avoids a TCP handshake
> and authentication per request and caps how many queries a single process runs at once — and it
> can't help across processes because it doesn't know they exist. PgBouncer makes the number of
> Postgres backends independent of the number of application processes, which is what lets a thousand
> clients share twenty-five backends. So the right shape is a small app pool, a large `max_client_conn`
> and a small `default_pool_size`. Going to `NullPool` means paying a connect and auth to PgBouncer on
> every checkout, which is cheap but measurable at high rates; keeping a large app pool means every
> held connection occupies a client slot, and any that's inside a transaction pins a backend — which
> recreates the exact problem you installed the pooler to solve. The exception where `NullPool` is
> genuinely right is Lambda, where the process can be frozen between invocations and a pooled socket
> resumed forty minutes later is dead.

**Q: How do you size a connection pool?**

> Two calculations, and people only do the first. The first is the ceiling: instances times workers
> times `pool_size + max_overflow`, plus Celery, plus cron and migrations and the metrics exporter,
> has to stay under `max_connections` minus the superuser reservation — and it fails during a deploy
> when every instance opens its pool at once. The second is the one that matters more: the right size
> is much smaller than instinct, because a connection that isn't executing does nothing, and Postgres
> can genuinely run about `2 × cores` queries at a time. Beyond that, work queues inside Postgres where
> you can't instrument it, instead of inside your pool where you can. Little's Law gives the number
> directly — four thousand queries a second at five milliseconds each is twenty concurrent connections,
> not four hundred. So a small pool with a short `pool_timeout` is really a load shedder, and a large
> pool is an unbounded queue in the wrong place.

**Q: What does PgBouncer transaction mode break?**

> Everything that is session state rather than transaction state, and the one-line test is "does this
> survive a commit?" Concretely: prepared statements, which psycopg3 creates automatically after five
> executions and which then fail with "prepared statement does not exist"; plain `SET`, including
> `search_path`; session-scoped advisory locks, because you may not get the same backend back to
> release one; `LISTEN`/`NOTIFY`, where the listener sits on a backend nobody notifies and silently
> receives nothing; temporary tables; and `WITH HOLD` cursors. The one I'd flag hardest is `SET`,
> because it isn't a compatibility issue, it's a security one: if you set a tenant id in a session
> variable for row-level security, that value can persist onto a backend handed to a different
> tenant's request, and you get cross-tenant exposure with no error anywhere. `SET LOCAL` inside the
> transaction fixes it, which is the same rule as never leaving session state on a pooled connection.

**Q: The app is slow, the database looks idle. Where do you look?**

> Between them. Either the application pool is exhausted — which shows up as `QueuePool limit reached`
> if `pool_timeout` is short, or as unexplained latency if it's long — or PgBouncer is queueing. The
> two numbers that settle it are `cl_waiting` and `maxwait` from `SHOW POOLS`: sustained waiting
> clients means `default_pool_size` is too small, and any non-zero `maxwait` is latency that an APM
> will attribute to the database while the database's own metrics look fine. `SHOW STATS` splits
> `avg_query_time` from `avg_wait_time`, which is exactly the distinction between "the database is
> slow" and "the pool is too small" — two different fixes. The third possibility is that PgBouncer
> itself is saturated, because it's single-threaded and one process tops out around ten to twenty
> thousand queries a second, which is why you run several with `so_reuseport` or use a multi-threaded
> alternative.

**Q: Your app returns protocol errors that look like data corruption after a deploy. First guess?**

> The engine was created before `fork()`, so the gunicorn or Celery workers inherited a pool whose
> sockets are shared between processes — two processes writing to one connection produces garbled
> protocol responses that look alarming and aren't corruption at all. The fix is to create the engine
> after the fork, in gunicorn's `post_fork` hook or Celery's `worker_process_init`, or to call
> `engine.dispose()` at worker startup so each child opens its own connections. It's a one-time lesson
> for most teams and it's worth checking proactively, because the symptom is scary enough that people
> start looking at the database rather than at process startup.

## 🎙️ Articulation drill

**Two minutes: "How do you handle database connections at scale?"**

Start with why it's a problem at all, in one line: a Postgres connection is an OS process costing
megabytes, so connections are expensive to create *and* to hold, which is a worse combination than
most databases. Then separate the two pools clearly, because that's the distinction interviewers are
listening for — the app pool saves round trips inside one process, PgBouncer makes backend count
independent of process count. Then do the arithmetic out loud, both halves: the ceiling that fails
during a deploy, and Little's Law giving twenty connections where instinct says four hundred. Land the
insight: **a big pool doesn't add capacity, it moves the queue inside Postgres where you can't see
it.** Finish on the pooler checklist, and pick the security one to state in full: **`SET` for a tenant
id under transaction pooling can persist onto another tenant's request, so it's `SET LOCAL` inside the
transaction, always** — same rule as never leaving session state on a pooled connection.
