# Part 1 — What a token actually is

```
⭐ ⭐⭐ NOT A WORD. NOT A CHARACTER. ⭐ A ***sub-word unit***
⭐   produced by a learned compression scheme (BPE — byte-pair
⭐   encoding), chosen so that common sequences are one token and
⭐   rare ones are several.

⭐   "hello"        → 1 token
⭐   "unbelievable" → 3 tokens  (un·believ·able)
⭐   "Ramesh"       → 2–3 tokens
⭐   " the"         → 1 token   ⭐⭐ (THE LEADING SPACE IS PART OF
⭐                              THE TOKEN — WHICH IS WHY
⭐                              TRAILING WHITESPACE IN A PROMPT
⭐                              CHANGES THE OUTPUT)
⭐   "1234567890"   → 3–4 tokens ⭐⭐ AND THE SPLIT IS ARBITRARY,
⭐                              WHICH IS PART OF WHY ARITHMETIC
⭐                              IS HARD (DAY 414)

⭐⭐ THE RULES OF THUMB THAT ARE ACCURATE ENOUGH TO PLAN WITH:
⭐   ⭐ ENGLISH PROSE ....... ~4 characters / token
⭐                           ⭐⭐ ~750 WORDS ≈ 1,000 TOKENS
⭐   ⭐ CODE ................ ~3 characters / token ⭐ (worse)
⭐   ⭐⭐ JSON ............... ***MUCH WORSE*** — ⭐ every brace,
⭐     quote and key is tokens, and keys repeat on every object.
⭐   ⭐⭐ NON-ENGLISH ........ 2–5× WORSE. ⭐ Tamil, Hindi, Chinese
⭐     and Arabic tokenise far less efficiently than English,
⭐     ⭐⭐ SO THE SAME SENTENCE COSTS SEVERAL TIMES MORE — ⭐ which
⭐     is a real fairness and cost issue in an Indian product
⭐     and almost nobody budgets for it.

⭐ ⭐ Count properly rather than estimating:
⭐   `pip install tiktoken`
⭐   `len(tiktoken.encoding_for_model("gpt-4o").encode(text))`
⭐   ⭐⭐ AND NOTE EACH VENDOR TOKENISES DIFFERENTLY, SO A TOKEN
⭐     COUNT IS NOT PORTABLE ACROSS PROVIDERS (DAY 458).
```

# Part 2 — ⭐⭐ The context window, and what "128k" does not mean

```
⭐⭐ ***THE CONTEXT WINDOW IS INPUT ***PLUS*** OUTPUT, IN ONE
⭐   CALL.*** ⭐ A 128k window with a 120k prompt leaves you 8k of
⭐   answer, ⭐⭐ AND YOU WILL DISCOVER THIS AS A TRUNCATED
⭐   RESPONSE RATHER THAN AN ERROR.
⭐ ⭐ It is a ***hard architectural limit***, not a quota you can
⭐   raise. ⭐ Exceed it and the call fails.

⭐⭐ AND THE FOUR THINGS "128k CONTEXT" DOES ***NOT*** MEAN:
⭐ ① ⭐⭐ ***IT DOES NOT MEAN THE MODEL USES ALL OF IT WELL.***
⭐    ⭐ The measured phenomenon is ***"lost in the middle"***:
⭐    ⭐⭐ RECALL IS HIGH FOR CONTENT AT THE START AND THE END OF A
⭐    LONG CONTEXT AND MEASURABLY WORSE IN THE MIDDLE. ⭐ So
⭐    burying the important instruction at position 60,000 of
⭐    120,000 is a real degradation.
⭐    ⭐⭐ ⇒ PUT THE INSTRUCTION AT THE END, AFTER THE DOCUMENTS.
⭐    ⭐ It costs nothing and it measurably helps.
⭐ ② ⭐⭐ ***IT DOES NOT MEAN IT IS AFFORDABLE.*** ⭐ 120k input
⭐    tokens at $2.50/M is $0.30 ***per call***. ⭐ Ten thousand
⭐    calls a day is $3,000/day. ⭐⭐ "JUST PUT THE WHOLE MANUAL IN
⭐    THE CONTEXT" IS A $90,000/MONTH ARCHITECTURE, ⭐ and that
⭐    arithmetic is the honest argument for RAG (Day 429) — not
⭐    elegance.
⭐ ③ ⭐ ***IT DOES NOT MEAN IT IS FAST.*** ⭐ Prefill is parallel
⭐    but not free; ⭐⭐ A 120k PROMPT ADDS SECONDS OF
⭐    TIME-TO-FIRST-TOKEN.
⭐ ④ ⭐⭐ ***IT DOES NOT PROTECT YOU FROM OVERFLOW.*** ⭐ Your
⭐    conversation grows, your retrieved chunks grow,
⭐    ⭐⭐ AND ONE DAY A USER PASTES A 400-PAGE PDF. ⭐ You need an
⭐    explicit budget and a truncation strategy (Part 4), ⭐ not a
⭐    large limit.
```

# Part 3 — The pricing model, and where the money actually goes

```
⭐ TWO PRICES, AND THE ASYMMETRY IS THE WHOLE GAME:
⭐   ⭐ INPUT ........... $X per million
⭐   ⭐⭐ OUTPUT ......... ***TYPICALLY 3–5× $X***

⭐⭐ ⇒ SO OUTPUT LENGTH IS SIMULTANEOUSLY YOUR LATENCY DRIVER
⭐   (DAY 414) ***AND*** YOUR COST DRIVER. ⭐ It is the one number
⭐   worth constraining hardest, and `max_tokens` plus "answer in
⭐   under 100 words" are both real engineering controls,
⭐   ⭐⭐ NOT STYLE PREFERENCES.

⭐ ⭐⭐ AND THE ONE THAT SAVES THE MOST MONEY IN PRACTICE:
⭐   ***PROMPT CACHING.*** ⭐ A long, ***stable*** prefix — your
⭐   system prompt, your few-shot examples, a fixed document —
⭐   can be cached by the provider and re-read at a large
⭐   discount (often ~90% off, sometimes free reads for a short
⭐   window).
⭐   ⭐⭐ ⇒ WHICH IMPOSES A DESIGN RULE THAT IS EASY TO GET
⭐     BACKWARDS: ***PUT EVERYTHING STABLE FIRST AND EVERYTHING
⭐     VARIABLE LAST.***
⭐   ⭐ Stable: system prompt → few-shot examples → retrieved
⭐     corpus that rarely changes.
⭐   ⭐ Variable: this user's question, the current timestamp.
⭐   ⭐⭐ PUTTING A TIMESTAMP OR A USER ID AT THE ***TOP*** OF YOUR
⭐     PROMPT INVALIDATES THE ENTIRE CACHE ON EVERY SINGLE
⭐     REQUEST, ⭐ and it is a one-line mistake that costs 5–10×.

⭐ ⭐ Batch APIs: ⭐⭐ ~50% OFF FOR ASYNCHRONOUS WORK WITH A
⭐   24-HOUR TURNAROUND. ⭐ If the work is not interactive —
⭐   nightly classification, backfilling embeddings, bulk
⭐   summarisation — ⭐⭐ USING THE SYNCHRONOUS API IS PAYING
⭐   DOUBLE FOR LATENCY NOBODY WANTED.
```

# Part 4 — ⭐⭐ The token budget: count before you send

```python
# ⭐⭐ THE RULE: NEVER BUILD A PROMPT WITHOUT A BUDGET. ⭐ Not
# ⭐   "usually it fits" — an explicit allocation, enforced.
import tiktoken
ENC = tiktoken.encoding_for_model("gpt-4o")
def ntok(s: str) -> int: return len(ENC.encode(s))

WINDOW        = 128_000
RESERVE_OUT   =   2_000     # ⭐⭐ RESERVE THE ANSWER FIRST
SAFETY        =     500     # ⭐ tokeniser differences, role overhead

budget = WINDOW - RESERVE_OUT - SAFETY
budget -= ntok(SYSTEM_PROMPT)          # ⭐ fixed
budget -= ntok(user_question)          # ⭐ non-negotiable

# ⭐⭐ WHAT IS LEFT GETS SPLIT BETWEEN HISTORY AND RETRIEVAL —
# ⭐   AND THAT SPLIT IS A PRODUCT DECISION, NOT A DEFAULT.
history_budget   = int(budget * 0.3)
retrieval_budget = budget - history_budget

chunks, used = [], 0
for c in ranked_chunks:               # ⭐ best first (Day 433)
    t = ntok(c.text)
    if used + t > retrieval_budget:
        break                         # ⭐⭐ DROP, DO NOT TRUNCATE
    chunks.append(c); used += t
```

```
⭐⭐ AND THE FOUR TRUNCATION STRATEGIES, RANKED BY HOW BADLY
⭐   THEY FAIL:
⭐ ① ⭐⭐ ***DROP WHOLE UNITS, WORST-RANKED FIRST.*** ⭐ Drop the
⭐    5th-best chunk entirely rather than cutting every chunk in
⭐    half. ⭐⭐ A HALF-CHUNK IS OFTEN WORSE THAN NO CHUNK, BECAUSE
⭐    IT ENDS MID-SENTENCE AND THE MODEL COMPLETES IT ITSELF.
⭐ ② ⭐ ***SUMMARISE OLDER HISTORY*** into a running summary
⭐    (Day 443). ⭐ Costs a call; ⭐⭐ PRESERVES CONTINUITY.
⭐ ③ ⭐ ***SLIDING WINDOW*** — keep the last N turns.
⭐    ⭐⭐ SIMPLE, AND IT SILENTLY FORGETS THINGS THE USER SAID
⭐    EARLY, WHICH THEY WILL NOTICE.
⭐ ④ ⭐⭐ ***HARD CHARACTER TRUNCATION — NEVER.*** ⭐ It cuts
⭐    mid-token and mid-sentence, ⭐⭐ AND IT WILL EVENTUALLY CUT
⭐    THE CLOSING INSTRUCTION OFF YOUR PROMPT AND CHANGE THE
⭐    BEHAVIOUR IN A WAY NOTHING LOGS.

⭐ ⭐⭐ AND ***ALWAYS COUNT BEFORE YOU SEND***: ⭐ discovering
⭐   overflow from a 400 error after a 3-second round trip is a
⭐   worse failure than rejecting locally in a microsecond.
```

# Part 5 — Rate limits are denominated in tokens too

```
⭐ PROVIDERS LIMIT ***BOTH***:
⭐   ⭐ RPM — requests per minute
⭐   ⭐⭐ TPM — ***TOKENS*** PER MINUTE ⭐ (and it usually counts
⭐     your `max_tokens` reservation, ⭐⭐ NOT WHAT YOU ACTUALLY
⭐     USED — ⭐ so an inflated `max_tokens` burns quota you never
⭐     consumed).

⭐⭐ ⇒ THE CONSEQUENCE THAT SURPRISES PEOPLE: ***YOU CAN BE
⭐   RATE-LIMITED AT A HANDFUL OF REQUESTS PER MINUTE.*** ⭐ Ten
⭐   concurrent RAG calls with 100k-token contexts is a million
⭐   tokens a minute, ⭐⭐ AND YOUR REQUEST COUNT IS TRIVIAL WHILE
⭐   YOUR TPM IS EXHAUSTED. ⭐ The 429 says "rate limit" and your
⭐   dashboard says "12 requests/min", and the two look
⭐   contradictory until you know this.

⭐ ⇒ ⭐ Handle 429 with backoff ***and*** respect
⭐   `Retry-After` / `x-ratelimit-reset-tokens` (Day 336's
⭐   backoff, Day 458's multi-provider), ⭐⭐ AND TRACK TPM
⭐   HEADROOM AS A METRIC, NOT JUST ERROR RATE — ⭐ because the
⭐   error arrives only after you have already lost the capacity.
```

# Part 6 — The architectural consequences

```
⭐⭐ ① ***YOUR DATA MODEL IS A COST DECISION.*** ⭐ Sending rows
⭐    as JSON is expensive: every key repeats on every object.
⭐    ⭐ The same 50 records:
⭐      ⭐ JSON with verbose keys ...... ~4,000 tokens
⭐      ⭐ CSV / TSV with a header ..... ~1,200 tokens
⭐      ⭐⭐ MARKDOWN TABLE ............. ~1,400 tokens
⭐    ⭐⭐ ⇒ A 3× COST REDUCTION FROM CHANGING A SERIALISER, ⭐ and
⭐      models read tables and CSV perfectly well. ⭐⭐ DO NOT SEND
⭐      PRETTY-PRINTED JSON TO A MODEL.

⭐⭐ ② ***"SUMMARISE THIS DOCUMENT" DOES NOT SCALE LINEARLY.***
⭐    ⭐ A 400-page PDF does not fit, so you need map-reduce
⭐    summarisation — ⭐⭐ N CALLS TO SUMMARISE CHUNKS, THEN A CALL
⭐    TO SUMMARISE THE SUMMARIES, ⭐ which costs N+1 calls and
⭐    loses cross-chunk detail. ⭐ Know that before you promise
⭐    the feature.

⭐⭐ ③ ***CONVERSATION LENGTH IS A PRODUCT DECISION WITH A
⭐    PRICE.*** ⭐ "Unlimited chat history" means quadratic cost
⭐    (Day 414). ⭐⭐ SOMEBODY MUST CHOOSE THE WINDOW, AND IF
⭐    ENGINEERING DOES NOT, THE BILL WILL.

⭐⭐ ④ ***MULTILINGUAL PRODUCTS COST MORE PER USER***, ⭐ unevenly,
⭐    by language. ⭐⭐ IF YOU PRICE PER SEAT AND YOUR TAMIL AND
⭐    HINDI USERS COST 3× YOUR ENGLISH ONES, THAT IS A UNIT
⭐    ECONOMICS PROBLEM (DAY 396) AND YOU SHOULD FIND IT BEFORE
⭐    FINANCE DOES.
```

# 💬 Interview

**1. ⭐⭐ "How do you estimate the cost of an LLM feature?"**
> ⭐ In tokens, not requests. ⭐⭐ **English prose is about four characters a token, so 750 words is
> roughly 1,000 tokens; code is worse at three; JSON is much worse because every key repeats on every
> object; and non-English text is two to five times worse, which matters a lot in an Indian product
> and almost nobody budgets for it.** ⭐ Then I'd separate input from output, ⭐⭐ **because output is
> typically three to five times the price and is also the latency driver — so it's the number worth
> constraining hardest, and `max_tokens` plus "answer in under 100 words" are engineering controls,
> not style preferences.**

**2. ⭐⭐ "What does a 128k context window actually give you?"**
> ⭐ Less than people assume, in four ways. ⭐⭐ **It's input plus output, so a 120k prompt leaves 8k of
> answer and you discover that as truncation rather than an error.** ⭐⭐ **The model doesn't use all of
> it equally — recall is high at the start and end and measurably worse in the middle, so the
> instruction goes after the documents, which costs nothing and helps.** ⭐⭐ **And it isn't affordable:
> 120k input tokens is about thirty cents a call, so ten thousand calls a day is $3,000 a day — "just
> put the whole manual in the context" is a $90,000-a-month architecture, and that arithmetic is the
> honest argument for RAG rather than elegance.** ⭐ Plus it doesn't protect you from overflow, so you
> still need an explicit budget.

**3. "What's the highest-leverage cost optimisation?"**
> ⭐⭐ **Prompt caching, and it imposes a design rule that's easy to get backwards: everything stable
> goes first and everything variable goes last.** ⭐ System prompt, few-shot examples and a fixed corpus
> at the top; this user's question and the timestamp at the bottom. ⭐⭐ **Putting a timestamp or a user
> id at the top of the prompt invalidates the entire cache on every request — a one-line mistake that
> costs five to ten times.** ⭐ After that, the batch API at roughly half price for anything
> non-interactive: ⭐⭐ **using the synchronous API for nightly classification is paying double for
> latency nobody wanted.**

**4. ⭐⭐ "You're getting 429s at twelve requests a minute. Explain."**
> ⭐ Rate limits are denominated in tokens as well as requests, ⭐⭐ **and the TPM limit usually counts
> your `max_tokens` reservation rather than what you actually used.** ⭐ So ten concurrent RAG calls
> with 100k contexts is a million tokens a minute — ⭐⭐ **the request count is trivial while the token
> quota is exhausted, which is why the error and the dashboard look contradictory.** ⭐ Fixes: an honest
> `max_tokens` rather than an inflated one, backoff that respects the reset headers, ⭐⭐ **and tracking
> TPM headroom as a metric rather than waiting for the error, because by the time you get the 429
> you've already lost the capacity.**

**5. "How do you handle a prompt that might not fit?"**
> ⭐⭐ **Count before sending — always.** ⭐ Discovering overflow from a 400 after a three-second round
> trip is worse than rejecting locally in a microsecond. ⭐ I reserve the output allocation first, then
> the system prompt and the user's question, and split what's left between history and retrieval as an
> explicit product decision. ⭐ For truncation: ⭐⭐ **drop whole units worst-ranked first, because a
> half-chunk is often worse than no chunk — it ends mid-sentence and the model completes it itself.**
> ⭐ Summarise older history if continuity matters. ⭐⭐ **And never hard character truncation, because it
> will eventually cut the closing instruction off your prompt and change the behaviour in a way
> nothing logs.**

**6. ⭐⭐ "Any cheap win people miss?"**
> ⭐ Serialisation. ⭐⭐ **Fifty records as pretty-printed JSON is about 4,000 tokens; the same records as
> CSV with a header are about 1,200 — a threefold cost reduction from changing a serialiser, and
> models read tables and CSV perfectly well.** ⭐ It's the clearest case of the data model being a cost
> decision.

## 🎙️ Articulation drill

**Two minutes.** Establish the unit: **the token is what you're billed in, what latency scales with,
what the context limit is measured in, and what the rate limit counts — so it's the unit the
architecture is denominated in, and a team reasoning in "documents" gets surprised by its bill, its
p99 and its 429s in that order.** Give the estimation rules: **four characters a token for English,
worse for code, much worse for JSON because keys repeat, and two to five times worse for Indian
languages — which is a real unit-economics problem if you price per seat.** Then correct the context
window: **128k is input plus output, so a 120k prompt leaves 8k of answer and you find out by
truncation. The model doesn't use it evenly — recall is worse in the middle, so put the instruction
after the documents. And it isn't affordable: thirty cents a call is $3,000 a day at ten thousand
calls, which is the honest argument for retrieval, not elegance.** Then the money: **output is three to
five times input, so it's the number to constrain hardest — and the biggest single win is prompt
caching, which forces everything stable to the front and everything variable to the back. A timestamp
at the top of your prompt invalidates the cache on every request and costs five to ten times.** Close
on discipline: **count before you send, reserve the output allocation first, drop whole chunks rather
than truncating them, and never hard-truncate characters — because eventually that cuts the closing
instruction off your prompt and changes the behaviour with nothing in the logs.**
