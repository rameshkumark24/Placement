# Day 485 ⏰

**P-485** · ⏰ **System design round 5 — a distributed scheduler** — ⭐⭐ exactly-once execution is not on the menu

**Time:** 3 hrs · **Mode:** MOCK + DEBRIEF

> ⭐⭐ **The sentence to own: "run this job exactly once at time T across N workers" is not achievable,
> and the honest design is at-least-once claiming with a lease plus idempotent jobs — because the thing
> you can actually guarantee is that no *two* workers believe they hold the same job at the same time,
> which is a different and weaker promise.**

---

# Part 1 — ⭐⭐ Why exactly-once is unavailable

```
⭐ ***THE REQUEST:*** ⭐ "run job X at 09:00, exactly once, across
⭐   fifty workers."
⭐ ***THE PROBLEM, IN THREE STEPS:***
⭐   ⭐ worker A claims the job at 09:00;
⭐   ⭐ ⭐⭐ WORKER A PAUSES — GC, A SLOW DISK, A NETWORK PARTITION,
⭐     A VM MIGRATION — ⭐ for ninety seconds;
⭐   ⭐ the system must now decide: ⭐⭐ IS A DEAD, OR SLOW?
⭐   ⭐ ⭐⭐ IT CANNOT TELL (D412). ⭐ So it chooses an error:
⭐     ⭐ assume dead and re-run ⇒ ***possible double execution***;
⭐     ⭐ assume alive and wait ⇒ ***possible never executed***.

⭐ ⇒ ⭐⭐ ***SO YOU CHOOSE WHICH FAILURE, AND YOU MAKE IT
⭐   HARMLESS:***
⭐   ⭐ ⭐⭐ CHOOSE AT-LEAST-ONCE ⭐ (re-run on suspected death),
⭐   ⭐ ⭐⭐ AND REQUIRE JOBS TO BE ***IDEMPOTENT***, ⭐ so a double
⭐     execution is invisible.
⭐   ⭐ ⭐⭐ THAT REQUIREMENT IS PART OF THE PLATFORM'S CONTRACT,
⭐     NOT A HOPE: ⭐ every job takes an `execution_id`, and any
⭐     side effect it performs carries that as its idempotency
⭐     key (D444).

⭐ ***THE SENTENCE THAT SCORES:*** ⭐⭐ "I CAN'T GIVE YOU
⭐   EXACTLY-ONCE ***EXECUTION***. ⭐ What I can give you is
⭐   ***mutual exclusion at any instant*** — no two workers
⭐   believing they hold the same job — ⭐⭐ PLUS AT-LEAST-ONCE
⭐   DELIVERY AND AN IDEMPOTENCY CONTRACT. ⭐ Anyone promising
⭐   exactly-once across a network is describing the happy path."
```

# Part 2 — ⭐⭐ Claim with a lease

```
⭐ ***THE DATA MODEL — ONE TABLE, AND MOST OF THE DESIGN IS IN
⭐   IT:***
```

```sql
CREATE TABLE jobs (
  id             uuid PRIMARY KEY,
  schedule       text        NOT NULL,      -- ⭐ cron expression
  next_run_at    timestamptz NOT NULL,      -- ⭐⭐ THE WORK QUEUE
  leased_until   timestamptz,               -- ⭐⭐ NULL = UNCLAIMED
  leased_by      text,                      -- ⭐ worker id
  lease_epoch    bigint      NOT NULL DEFAULT 0,  -- ⭐⭐ FENCING
  status         text        NOT NULL,
  attempt        int         NOT NULL DEFAULT 0
);
-- ⭐⭐ THE INDEX THAT MAKES CLAIMING CHEAP:
CREATE INDEX ON jobs (next_run_at)
  WHERE status = 'ready';
```

```python
CLAIM = text("""
    UPDATE jobs
       SET leased_by    = :worker,
           leased_until = now() + interval '60 seconds',
           lease_epoch  = lease_epoch + 1,      -- ⭐⭐ FENCING TOKEN
           status       = 'running'
     WHERE id IN (
        SELECT id FROM jobs
         WHERE status = 'ready'
           AND next_run_at <= now()
         ORDER BY next_run_at
         LIMIT 10
           FOR UPDATE SKIP LOCKED              -- ⭐⭐ THE WHOLE TRICK
     )
    RETURNING id, lease_epoch
""")
```

```
⭐ ⭐⭐ `FOR UPDATE SKIP LOCKED` IS WHY THIS WORKS AND IT IS WORTH
⭐   EXPLAINING RATHER THAN JUST USING:
⭐   ⭐ fifty workers poll simultaneously. ⭐⭐ WITHOUT `SKIP
⭐     LOCKED` THEY ALL BLOCK ON THE SAME ROWS AND YOU HAVE
⭐     SERIALISED YOUR ENTIRE FLEET.
⭐   ⭐ ⭐⭐ WITH IT, EACH WORKER ***SKIPS*** ROWS OTHERS ARE
⭐     TOUCHING AND CLAIMS DIFFERENT ONES. ⭐ No coordinator, no
⭐     distributed lock, ⭐⭐ AND THE DATABASE PROVIDES THE MUTUAL
⭐     EXCLUSION — ⭐ correctness in the resource (D412) once
⭐     again.

⭐ ***THE LEASE IS THE FAILURE HANDLER:***
⭐   ⭐ a worker that dies never releases anything;
⭐   ⭐ ⭐⭐ `leased_until` PASSES AND THE JOB BECOMES CLAIMABLE
⭐     AGAIN, ⭐ with no cleanup process and no crash handler.
⭐   ⭐ ⭐⭐ CORRECTNESS DOES NOT DEPEND ON A DYING PROCESS DOING
⭐     ANYTHING — ⭐ which is the same property as the chat
⭐     registry's TTL (D483) and the same idea as a fencing lease
⭐     (D411).

⭐ ***LONG JOBS ⇒ ***RENEW***, DO NOT EXTEND:***
⭐   ⭐ a 60-second lease with a 30-minute job needs a
⭐     ***heartbeat*** every ~20s that pushes `leased_until`
⭐     forward.
⭐   ⭐ ⭐⭐ WHY NOT JUST A 30-MINUTE LEASE? ⭐ Because then a
⭐     worker that dies one second in blocks that job for thirty
⭐     minutes. ⭐⭐ SHORT LEASE + HEARTBEAT GIVES FAST RECOVERY
⭐     ***AND*** LONG JOBS.
```

# Part 3 — ⭐⭐ The zombie worker, and fencing

```
⭐ ***THE FAILURE THE LEASE DOES NOT FIX — AND IT IS THE HARD
⭐   ONE:***
⭐   ⭐ worker A claims a job, lease expires during a 90-second GC
⭐     pause;
⭐   ⭐ worker B claims it and starts running;
⭐   ⭐ ⭐⭐ WORKER A WAKES UP. ⭐ It does not know time passed.
⭐     ⭐⭐ IT BELIEVES IT STILL HOLDS THE LEASE AND WRITES ITS
⭐     RESULT.
⭐   ⭐ ⭐⭐ TWO WORKERS, ONE JOB, AND THE LEASE DID NOTHING —
⭐     BECAUSE A LEASE IS A ***TIMING ASSUMPTION***, AND A PAUSED
⭐     PROCESS VIOLATES IT.

⭐ ⭐⭐ THE FIX: ***A FENCING TOKEN*** (D411).
⭐   ⭐ every claim increments `lease_epoch`;
⭐   ⭐ the worker carries its epoch and ⭐⭐ PASSES IT ON EVERY
⭐     WRITE;
⭐   ⭐ ⭐⭐ THE RESOURCE REJECTS ANY WRITE WITH AN EPOCH LOWER
⭐     THAN THE HIGHEST IT HAS SEEN.
⭐   ⭐ ⇒ ⭐⭐ WORKER A'S LATE WRITE CARRIES EPOCH 7 WHILE THE
⭐     RESOURCE HAS SEEN 8. IT IS REFUSED.
⭐   ⭐ ⭐⭐ THE INSIGHT: ***CORRECTNESS MOVED OUT OF THE
⭐     COORDINATOR AND INTO THE RESOURCE.*** ⭐ The scheduler no
⭐     longer has to be right about who holds the lease —
⭐     ⭐⭐ THE RESOURCE ENFORCES IT REGARDLESS.

⭐ ***AND THE HONEST LIMIT:*** ⭐ fencing only works if the
⭐   resource ***can*** check the token. ⭐⭐ AN EXTERNAL API THAT
⭐   ACCEPTS NO EPOCH CANNOT BE FENCED, ⭐ so for those you fall
⭐   back to idempotency keys and accept at-least-once — ⭐⭐ WHICH
⭐   IS WHY THE IDEMPOTENCY CONTRACT IN PART 1 IS NOT OPTIONAL.
```

# Part 4 — Time, herds and catch-up

```
⭐ ① ⭐⭐ ***THE MIDNIGHT HERD.***
⭐   ⭐ Everyone writes `0 0 * * *`. ⭐⭐ AT 00:00:00 EVERY JOB IN
⭐     THE SYSTEM BECOMES READY SIMULTANEOUSLY ⭐ — a
⭐     self-inflicted thundering herd on your workers, your
⭐     database and every downstream service.
⭐   ⭐ ⇒ ⭐⭐ JITTER THE SCHEDULE: ⭐ derive a stable per-job
⭐     offset from `hash(job_id) % 300` seconds. ⭐⭐ STABLE, SO
⭐     THE JOB RUNS AT THE SAME TIME EVERY DAY — ⭐ but spread
⭐     across five minutes rather than one instant. ⭐ Same fix as
⭐     TTL jitter (D479).

⭐ ② ⭐⭐ ***CLOCKS DISAGREE*** (D409).
⭐   ⭐ Worker clocks skew by seconds; ⭐⭐ A LEASE COMPARED
⭐     AGAINST A ***LOCAL*** CLOCK IS A BUG.
⭐   ⭐ ⇒ ⭐⭐ ALL TIME COMPARISONS HAPPEN IN THE DATABASE, ⭐ using
⭐     ***one*** clock: `leased_until < now()` is evaluated
⭐     server-side. ⭐⭐ THE SCHEDULER HAS EXACTLY ONE CLOCK AND
⭐     THAT IS DELIBERATE.

⭐ ③ ⭐⭐ ***CATCH-UP AFTER AN OUTAGE — A PRODUCT QUESTION, NOT A
⭐   TECHNICAL ONE.***
⭐   ⭐ The scheduler is down four hours. ⭐ An hourly job missed
⭐     four runs. ⭐⭐ DO YOU RUN IT FOUR TIMES, OR ONCE?
⭐   ⭐ ⭐⭐ "SEND THE DAILY DIGEST" — ONCE. ⭐ Four digests is a
⭐     bug.
⭐   ⭐ ⭐⭐ "BILL EACH HOUR OF USAGE" — ALL FOUR. ⭐ Skipping is
⭐     lost revenue.
⭐   ⭐ ⇒ ⭐⭐ IT IS A ***PER-JOB POLICY***: `catch_up: all | latest
⭐     | skip`. ⭐ Asking this question unprompted is one of the
⭐     strongest signals in the round, ⭐⭐ BECAUSE IT SHOWS YOU
⭐     HAVE THOUGHT ABOUT WHAT HAPPENS AFTER THE INCIDENT RATHER
⭐     THAN ONLY DURING IT.
⭐   ⭐ ⭐ And cap it: `all` with a 24-hour outage must not
⭐     enqueue 1,440 runs at once.
```

# 💬 Interview

**1. "Run a job exactly once at a given time across fifty workers."**

⭐ I can't, and I'd say so immediately rather than describe a happy path. ⭐⭐ A worker claims the job,
then pauses for ninety seconds — GC, a slow disk, a VM migration — and the system has to decide whether
it's dead or slow. It can't tell. ⭐ Assume dead and re-run means possible double execution; assume alive
and wait means possible never executed. ⭐⭐ So I choose at-least-once and make double execution harmless:
every job takes an `execution_id`, and any side effect it performs carries that as an idempotency key.
⭐ What I *can* guarantee is mutual exclusion at any instant — no two workers believing they hold the same
job — which is a different and weaker promise, and being precise about that distinction is the answer.

**2. "How do workers claim jobs?"**

⭐ A single conditional update with `FOR UPDATE SKIP LOCKED`, and no coordinator at all. ⭐⭐ Fifty
workers poll simultaneously; without `SKIP LOCKED` they all block on the same rows and I've serialised my
entire fleet. With it, each worker skips rows others are touching and claims different ones. ⭐ The
database provides the mutual exclusion, so there's no distributed lock to get wrong. ⭐⭐ And the claim
sets a lease — `leased_until = now() + 60 seconds` — which is the failure handler: a worker that dies
never releases anything, the lease expires, and the job becomes claimable again with no cleanup process.
⭐ Correctness doesn't depend on a dying process doing anything.

**3. "A job takes thirty minutes."**

⭐ Then it heartbeats rather than taking a thirty-minute lease. ⭐⭐ A long lease means a worker that dies
one second in blocks that job for half an hour. ⭐ So: a sixty-second lease renewed every twenty seconds
while the job runs. ⭐⭐ Short lease plus heartbeat gives me fast recovery *and* long jobs, which a single
lease duration can't. ⭐ And if the heartbeat fails — the worker is partitioned — the job legitimately
becomes claimable by someone else, which is exactly when I need fencing.

**4. "The paused worker wakes up."**

⭐ That's the failure the lease doesn't fix, and it's the interesting one. ⭐⭐ Worker A's lease expired
during a GC pause, worker B claimed and started, then A wakes up believing it still holds the lease and
writes its result. ⭐ Two workers, one job — because a lease is a *timing assumption*, and a paused
process violates it. ⭐⭐ The fix is a fencing token: every claim increments an epoch, the worker carries
it on every write, and the resource rejects any write with an epoch lower than the highest it has seen.
⭐ A's late write carries epoch 7 while the resource has seen 8, so it's refused. ⭐⭐ Correctness moves
out of the coordinator and into the resource — the scheduler no longer has to be right about who holds
the lease.

**5. "What if the resource can't check a token?"**

⭐ Then it can't be fenced, and I'd say that plainly rather than pretend. ⭐⭐ An external API that accepts
no epoch — a third-party email provider, say — will happily take the zombie's write. ⭐ Which is exactly
why the idempotency contract isn't optional: those side effects have to be keyed on `execution_id` so a
duplicate is absorbed at the far end. ⭐⭐ Fencing where I can, idempotency where I can't, and being clear
about which resources are in which category is part of the design rather than an afterthought.

**6. "Everyone schedules jobs at midnight."**

⭐ Then at 00:00:00 every job in the system becomes ready simultaneously, which is a self-inflicted
thundering herd on my workers, my database and every downstream service. ⭐⭐ The fix is a stable
per-job offset — hash the job id modulo three hundred seconds — so the job runs at the same time every
day but the fleet is spread over five minutes rather than one instant. ⭐ Stable matters: users notice if
their report arrives at a different time each day. ⭐⭐ It's the same fix as jittering cache TTLs, and
it's the sort of thing nobody writes until after the first incident.

**7. "The scheduler was down for four hours. What happens to the hourly job?"**

⭐ That's a product question, not a technical one, and asking it unprompted is the point. ⭐⭐ "Send the
daily digest" should run once — four digests is a bug. "Bill each hour of usage" should run all four —
skipping is lost revenue. ⭐ So it's a per-job policy: catch-up all, latest, or skip. ⭐⭐ And whichever
they choose, I'd cap it, because `all` after a twenty-four-hour outage means enqueueing 1,440 runs at
once, which turns a recovery into a second outage.

**8. "What did the five system design rounds have in common?"**

⭐ Six things. ⭐⭐ The estimation decided the architecture every time — 100:1 reads means a cache, 50
million followers means a hybrid, fifty thousand sockets per box means a registry. ⭐ The average lied in
every round, so I ask for the distribution. ⭐⭐ Every round put correctness in the resource: `SKIP
LOCKED`, a unique index, a check constraint, a conditional update. ⭐ Every one persisted before acking,
which converts downstream failures into retries. ⭐⭐ Exactly-once was never available, so at-least-once
plus an idempotency key. ⭐ And in every round the dangerous failure was the one that returns 200 — a
stale registry, a silent leak, a cached permission bypass, an unreconciled payment.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "build a distributed scheduler."**

Refuse the premise precisely, in the first thirty seconds. **"The request is usually 'run this exactly
once at time T across fifty workers', and I can't do that — so I'd rather say why up front than describe
a happy path. A worker claims the job and then pauses for ninety seconds: GC, a slow disk, a VM
migration. The system has to decide whether it's dead or slow, and it fundamentally cannot tell. Assume
dead and re-run gives possible double execution; assume alive and wait gives possible never executed. So
I choose at-least-once and make double execution harmless. What I can guarantee is mutual exclusion at
any instant — no two workers believing they hold the same job — which is a different and weaker
promise."**

Then the mechanism, and why it needs no coordinator. **"Claiming is one conditional update with `FOR
UPDATE SKIP LOCKED`. Fifty workers poll at once; without skip-locked they all block on the same rows and
I've serialised my whole fleet. With it, each skips what others are touching. The database provides the
mutual exclusion, so there's no distributed lock to get wrong. And the claim sets a lease, which is the
failure handler — a worker that dies releases nothing, the lease expires, the job becomes claimable
again. Correctness never depends on a dying process doing anything. Long jobs heartbeat rather than
taking a long lease, because a thirty-minute lease means a worker dying one second in blocks that job for
half an hour."**

Then the failure the lease doesn't cover. **"The interesting case is the zombie. Worker A's lease expires
during a pause, B claims and starts, then A wakes up believing it still holds the lease and writes. A
lease is a timing assumption, and a paused process violates it. So every claim increments an epoch, the
worker carries it on every write, and the resource refuses anything with an epoch below the highest it
has seen — A's write carries seven, the resource has seen eight, refused. Correctness moves out of the
coordinator and into the resource. And I'd name the limit: an external API that accepts no epoch can't be
fenced, which is exactly why the idempotency contract on every job isn't optional."**

Close on the two operational things. **"Two more I'd raise unprompted. Everyone writes cron for midnight,
so at exactly 00:00:00 every job becomes ready at once — a self-inflicted herd on my own workers. A
stable per-job offset from hashing the id spreads it over five minutes while keeping the run time
consistent day to day. And after an outage: does an hourly job that missed four runs execute four times
or once? 'Send the daily digest' should be once; 'bill each hour of usage' should be all four. That's a
per-job policy, and it's a product question rather than a technical one — with a cap, because catching up
on a twenty-four-hour outage shouldn't enqueue fourteen hundred runs and cause the next outage."**
