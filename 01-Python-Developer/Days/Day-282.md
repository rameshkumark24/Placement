**P-282** · 📦 **The container image** — ⭐⭐ small, layered, non-root, and sized correctly

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a container is one process, not a small machine — and almost every
> container bug people spend a day on is a consequence of forgetting that, starting with the fact
> that your carefully written graceful shutdown never runs.**

> ⭐ Day 253 gave you *an* image on day one, deliberately unexamined. ⭐⭐ Today you make it small,

# Part 1 — ⭐⭐ The trap that is in almost every Dockerfile

```dockerfile
CMD uvicorn app.main:app --host 0.0.0.0 --port 8000     # ❌ SHELL FORM
```

```
⭐⭐ SHELL FORM BECOMES:  /bin/sh -c "uvicorn …"
⭐   ⇒ ⭐ PID 1 IS `sh`. Your app is a CHILD.
⭐   ⇒ ⭐⭐ THE ORCHESTRATOR SENDS `SIGTERM` TO PID 1. `sh` DOES
⭐     NOT FORWARD IT. Your app receives NOTHING.
⭐   ⇒ ⭐ 30 seconds later the platform sends `SIGKILL`.
⭐   ⇒ ⭐⭐ SO: IN-FLIGHT REQUESTS ARE CUT MID-RESPONSE. THE
⭐     CONNECTION DRAIN YOU WROTE ON DAY 268 NEVER RUNS. THE
⭐     WORKER'S "FINISH THE CURRENT TASK" NEVER RUNS, WHICH
⭐     MEANS EVERY DEPLOY LOSES IN-FLIGHT TASKS (Day 265).

⭐⭐ THE FIX IS ONE CHARACTER CLASS:
⭐   CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]   ⭐ EXEC FORM
⭐   ⇒ ⭐ Your process IS PID 1 and receives signals directly.

⭐ ⭐ AND BECAUSE IT IS PID 1, IT INHERITS PID 1'S DUTIES:
⭐   ⭐ no default SIGTERM handler (⭐ Python installs one, so
⭐     you are fine; a shell script wrapper is not)
⭐   ⭐⭐ IT MUST REAP ZOMBIES if it spawns children. If your
⭐     entrypoint forks (gunicorn does), use `--init` / `tini`.
```

```
⭐⭐ AND THE NUMBER THAT MAKES SHUTDOWN CORRECT:
⭐   ***terminationGracePeriod > your longest in-flight request.***
⭐   ⭐ Default is 30 s. ⭐ Your export endpoint takes 45 s.
⭐   ⇒ ⭐⭐ EVERY DEPLOY KILLS SOME EXPORTS, and the users who
⭐     notice are the ones with the most data. ⭐ Which is also
⭐     the argument for Day 269's "an export is a job".
```

# Part 2 — ⭐⭐ Layers, and the build that takes 20 seconds

```dockerfile
# ❌ THE ORDERING EVERYONE WRITES FIRST
COPY . .
RUN pip install -r requirements.txt
```

```
⭐⭐ WHY IT IS SLOW: DOCKER CACHES PER LAYER, AND A LAYER IS
⭐   INVALIDATED BY ITS INPUTS.
⭐   ⇒ ⭐ `COPY . .` changes on EVERY source edit ⇒ the pip
⭐     layer below it is invalidated ⇒ ⭐⭐ YOU REINSTALL EVERY
⭐     DEPENDENCY BECAUSE YOU FIXED A TYPO IN A DOCSTRING.
⭐   ⇒ ⭐ 4 minutes per build, 30 builds a day.

⭐⭐ THE ORDERING RULE: ***LEAST-CHANGING FIRST.***
```

```dockerfile
COPY pyproject.toml uv.lock ./          # ⭐ changes rarely
RUN uv sync --frozen --no-dev           # ⭐⭐ CACHED ACROSS EDITS
COPY src/ ./src/                        # ⭐ changes constantly
```

```
⭐⭐ AND `.dockerignore`, WHICH IS TWO THINGS AT ONCE:
⭐   ⭐ SPEED — the whole build context is uploaded to the
⭐     daemon before anything runs. `.git`, `.venv`,
⭐     `node_modules`, `.pytest_cache` can be hundreds of MB.
⭐   ⭐⭐ AND A SECURITY CONTROL — `COPY . .` WITH NO IGNORE
⭐     FILE COPIES YOUR LOCAL `.env` INTO THE IMAGE.
⭐     ⇒ ⭐⭐ AND IT STAYS THERE EVEN IF A LATER LAYER DELETES
⭐       IT (Part 5). ⭐ This is one of the most common real
⭐       credential leaks there is, and it leaks to everyone
⭐       who can pull the image.
```

# Part 3 — ⭐⭐ Multi-stage, and the base image argument

```dockerfile
FROM python:3.12-slim AS build
RUN apt-get update && apt-get install -y --no-install-recommends build-essential
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev            # ⭐ compilers live HERE

FROM python:3.12-slim AS runtime         # ⭐⭐ AND NOWHERE ELSE
COPY --from=build /app/.venv /app/.venv
COPY src/ ./src/
```

```
⭐⭐ THE POINT IS NOT THE MEGABYTES. IT IS THE ATTACK SURFACE:
⭐   ⭐ `gcc`, `make`, headers and a package manager in a running
⭐     production container are ⭐⭐ EXACTLY THE TOOLKIT AN
⭐     ATTACKER WANTS AFTER THEY GET A SHELL.
⭐   ⭐ Size matters too, and the arithmetic is real:
⭐     ⭐ `python:3.12`        ≈ 1.0 GB
⭐     ⭐ `python:3.12-slim`   ≈ 150 MB
⭐     ⭐ distroless / chiselled ≈ 60–90 MB
⭐   ⇒ ⭐ Size is a DEPLOY-SPEED and SCALE-OUT property: a
⭐     900 MB pull on a cold node delays every scale event.
```

```
⭐⭐ AND THE ALPINE ARGUMENT, WHICH MOST PEOPLE GET BACKWARDS:
⭐   ⭐ Alpine is smaller, so it looks obviously right.
⭐   ⭐⭐ BUT ALPINE USES musl, NOT glibc ⇒ MANYLINUX WHEELS DO
⭐     NOT APPLY ⇒ ⭐⭐ pip COMPILES numpy, pandas, psycopg AND
⭐     cryptography FROM SOURCE. Your build goes from 40 seconds
⭐     to 20 minutes, and the image ends up LARGER because the
⭐     toolchain had to be installed.
⭐   ⭐ And musl's allocator is measurably slower under threaded
⭐     workloads.
⭐   ⇒ ⭐⭐ FOR PYTHON, `-slim` IS THE DEFAULT ANSWER, and
⭐     distroless is the answer when you want no shell at all.
⭐     ⭐ Distroless costs you `docker exec sh` when debugging —
⭐       state that trade rather than discovering it at 2 a.m.
```

# Part 4 — ⭐⭐ Non-root, and the rest of the hardening

```dockerfile
RUN useradd --system --uid 10001 app
USER 10001                              # ⭐⭐ NUMERIC, not a name
```

```
⭐⭐ WHY NUMERIC: Kubernetes `runAsNonRoot` CANNOT VERIFY A
⭐   USERNAME before starting the container — it can only check
⭐   a UID. ⭐ A named `USER app` fails that admission check on
⭐   some platforms with a confusing message.

⭐ THE REST OF THE RUNTIME POSTURE, ALL OF IT ONE LINE EACH:
⭐   ⭐ `readOnlyRootFilesystem: true` + an explicit `emptyDir`
⭐     for `/tmp` ⇒ ⭐⭐ AN ATTACKER CANNOT DROP A BINARY
⭐   ⭐ `allowPrivilegeEscalation: false`, drop ALL capabilities
⭐   ⭐ no package manager, no `curl`, no shell if you can manage it
⭐   ⭐ ⭐⭐ AND CHECK WHAT YOUR APP ACTUALLY WRITES: matplotlib
⭐     configs, `~/.cache`, prometheus multiprocess dirs. A
⭐     read-only filesystem finds them all at once, loudly, which
⭐     is the correct time to find them.
```

# Part 5 — ⭐⭐ What must not be in the image

```
⭐⭐ LAYERS ARE APPEND-ONLY. DELETING A FILE IN A LATER LAYER
⭐   DOES NOT REMOVE IT FROM THE IMAGE — IT ADDS A WHITEOUT.
⭐   ⭐ RUN cp secret.pem . && pip install && rm secret.pem
⭐   ⇒ ⭐⭐ `docker history` AND ANY LAYER EXTRACTION STILL HAVE
⭐     IT. ⭐ Same for `ARG GITHUB_TOKEN=…`, which is visible in
⭐     the image metadata to anyone who can pull.
⭐   ⇒ ⭐ Build secrets go through `RUN --mount=type=secret`,
⭐     which never lands in a layer at all.
```

```
⭐⭐ AND THE RULE THAT SHAPES THE WHOLE PIPELINE (Day 283):
⭐   ***CONFIGURATION COMES FROM THE ENVIRONMENT AT RUNTIME, SO
⭐      THE IMAGE IS IDENTICAL IN EVERY ENVIRONMENT.***
⭐   ⇒ ⭐⭐ ONE DIGEST IS BUILT ONCE AND ***PROMOTED*** — staging
⭐     to production — RATHER THAN REBUILT PER ENVIRONMENT.
⭐   ⇒ ⭐ If you rebuild for production, ⭐⭐ YOU TESTED AN
⭐     ARTEFACT YOU DID NOT SHIP. Different base digest,
⭐     different transitive wheel, different everything.
⭐   ⭐ Which also means: no `ENV DATABASE_URL=` in the Dockerfile,
⭐     and no `if ENVIRONMENT == "prod"` branches inside it.
```

# Part 6 — ⭐⭐ Health checks, and the probe that causes the outage

```
⭐⭐ TWO PROBES, TWO CONSEQUENCES, AND THEY ARE NOT THE SAME:
⭐   ⭐ LIVENESS  fails ⇒ ⭐⭐ THE CONTAINER IS RESTARTED
⭐   ⭐ READINESS fails ⇒ ⭐ IT IS REMOVED FROM THE LOAD BALANCER
⭐     (and put back when it passes)

⭐⭐ THE CLASSIC OUTAGE, IN FOUR LINES:
⭐   ① liveness probe = `SELECT 1` against Postgres
⭐   ② the database has a 30-second blip (a failover, Day 201)
⭐   ③ ⭐⭐ EVERY POD FAILS LIVENESS AND IS RESTARTED — ALL AT
⭐     ONCE, IN EVERY AZ
⭐   ④ ⭐⭐ THEY COME BACK COLD, WITH EMPTY CACHES AND EMPTY
⭐     POOLS, AND STAMPEDE THE DATABASE THAT WAS JUST RECOVERING
⭐   ⇒ ⭐⭐ A 30-SECOND DEPENDENCY BLIP BECAME A TEN-MINUTE
⭐     SELF-INFLICTED OUTAGE.

⭐⭐ THE RULE:
⭐   ⭐ LIVENESS CHECKS ***ONLY*** THAT THIS PROCESS IS NOT
⭐     WEDGED — an in-process `return "ok"`. Nothing external.
⭐     ⭐ Because the only correct response to failing it is
⭐       "restart me", and restarting never fixes a dependency.
⭐   ⭐ READINESS MAY CHECK DEPENDENCIES — the correct response
⭐     to a dead database IS to stop taking traffic.
⭐   ⭐ STARTUP PROBE for slow boots, so a slow start is not
⭐     mistaken for a wedge and restarted in a loop forever.
```

# Part 7 — ⭐ Provenance and scanning

```
⭐ ⭐ PIN THE BASE BY DIGEST, not by tag:
⭐     FROM python:3.12-slim@sha256:…
⭐   ⇒ ⭐⭐ A TAG IS MUTABLE. "It built fine last week" and "it
⭐     builds fine now" can be two different base images, which
⭐     is a genuinely horrible class of bug to debug.
⭐   ⭐ And a lockfile with hashes for your Python dependencies.

⭐ ⭐ STAMP THE IMAGE so a running container can be traced back:
⭐     LABEL org.opencontainers.image.revision=$GIT_SHA
⭐   ⭐ and expose that sha at `/version` (Day 260).

⭐ ⭐ SCAN IT (`trivy`, `grype`), and be honest about the noise:
⭐   ⭐⭐ MOST CVEs IN A BASE IMAGE ARE IN PACKAGES YOUR PROCESS
⭐     NEVER EXECUTES. ⭐ Gate on HIGH/CRITICAL ***with a fix
⭐     available***, and keep an allowlist WITH EXPIRY DATES —
⭐     ⭐⭐ THE SAME MECHANISM AS DAY 281'S QUARANTINE, and for
⭐     the same reason: an exception without an expiry is a
⭐     permanent decision made by accident.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Shell-form `CMD` | `sh` is PID 1 and swallows `SIGTERM`; graceful shutdown never runs. |
| Forking entrypoint with no init | Zombie processes accumulate; use `--init` or `tini`. |
| Grace period shorter than the longest request | Every deploy kills your slowest users' work. |
| `COPY . .` before installing dependencies | A docstring typo reinstalls every dependency. |
| No `.dockerignore` | Slow builds, and your local `.env` ends up inside the image. |
| Build tools in the runtime stage | You shipped an attacker's toolkit alongside your app. |
| Alpine for Python | musl means no manylinux wheels: 20-minute builds and a larger image. |
| Distroless without acknowledging the trade | No shell to exec into at 2 a.m. Decide before, not during. |
| `USER app` by name | `runAsNonRoot` can only verify a numeric UID. |
| No read-only root filesystem | An attacker can write a binary; you also never learn what your app writes. |
| `rm` a secret in a later `RUN` | Layers are append-only. It's still in `docker history`. |
| Secrets via `ARG` | Visible in image metadata to anyone who can pull. |
| Baking config into the image | You can no longer promote one digest across environments. |
| Rebuilding per environment | You tested an artefact you didn't ship. |
| A liveness probe that checks the database | A 30-second blip restarts every pod and stampedes the recovering database. |
| No readiness probe | Traffic hits a pod whose pool isn't warm. |
| No startup probe on a slow boot | A slow start is read as a wedge and restarted forever. |
| Base image pinned by tag | "It built fine last week" was a different base image. |
| Gating on every CVE | Most are in code you never execute; you'll learn to ignore the scanner. |
| A CVE allowlist with no expiry | A permanent decision made by accident. |

## Interview questions

**Q: Why does exec form matter?**

> Because with shell form, `/bin/sh` is PID 1 and your process is its child, and `sh` doesn't forward
> `SIGTERM`. So the orchestrator asks politely, nothing happens, and thirty seconds later it sends
> `SIGKILL` — which means in-flight requests get cut mid-response, the connection drain never runs,
> and workers lose whatever task they were on, on every single deploy. It presents as "we occasionally
> drop requests during releases", and the cause is one character class in the Dockerfile. The related
> number is the grace period: it has to exceed your longest in-flight request, or every deploy kills
> your slowest users' work.

**Q: How do you keep the image small?**

> Multi-stage, so compilers and headers live in the build stage and never ship — and I'd frame that as
> attack surface first and megabytes second, because `gcc` and a package manager in a running
> container are exactly what someone wants after they get a shell. Slim base rather than alpine: alpine
> looks obviously right until you remember it's musl, so manylinux wheels don't apply, and pip compiles
> psycopg and cryptography from source — a twenty-minute build producing a *larger* image. Distroless
> if I want no shell, accepting that I've given up `docker exec` when debugging.

**Q: A secret got into an image. Is deleting it in a later layer enough?**

> No. Layers are append-only, so a delete just adds a whiteout — the file is still in `docker history`
> and in any layer extraction, and so is anything passed via `ARG`. The fix is `RUN --mount=type=secret`
> so it never lands in a layer, and then rotating the secret, because it was published to everyone who
> could pull that image. Prevention is a `.dockerignore`, which is the reason your local `.env` doesn't
> get swept up by `COPY . .` in the first place.

**Q: What's the difference between liveness and readiness?**

> The consequence. Failing liveness restarts the container; failing readiness takes it out of the load
> balancer. Which is why liveness must never check a dependency: the only correct response to failing
> it is "restart me", and restarting has never fixed a database. The classic outage is a liveness probe
> running `SELECT 1` — the database has a thirty-second failover, every pod in every AZ fails liveness
> simultaneously, they all restart cold with empty pools and caches, and they stampede the database
> that was just recovering. A thirty-second blip becomes a ten-minute self-inflicted outage. Readiness
> may check dependencies, because there the correct response really is to stop taking traffic.

**Q: Why promote a digest instead of rebuilding?**

> Because if I rebuild for production, I tested an artefact I didn't ship — a different base digest, a
> different transitive wheel, potentially different behaviour. Build once, and the same digest moves
> from staging to production, which forces the discipline that configuration comes from the environment
> at runtime and there's nothing environment-specific inside the image. It also makes rollback exact:
> a rollback is a digest change, not a rebuild that might not reproduce.

## Today's build

1. ⭐⭐ Convert `CMD` to exec form. Send `SIGTERM` to the container and confirm your shutdown handler logs.
2. ⭐ Measure the grace period against your slowest endpoint and raise it. Kill a pod mid-export to see the old behaviour first.
3. ⭐⭐ Reorder the Dockerfile least-changing-first. Time a rebuild after a one-character source edit, before and after.
4. ⭐ Write `.dockerignore`, then check whether your previous image contained `.env` or `.git`.
5. ⭐⭐ Split into build and runtime stages. Record the size at each step: full, slim, multi-stage.
6. ⭐ Try an alpine build and time it. Write down the result as your own evidence.
7. ⭐⭐ Add a numeric `USER`, a read-only root filesystem, and dropped capabilities. Fix everything that breaks — and list what your app was writing.
8. ⭐⭐ Pass a fake secret via `ARG`, build, then find it with `docker history`.
9. ⭐ Rebuild using `RUN --mount=type=secret` and confirm it's absent.
10. ⭐⭐ Remove every environment-specific value from the image and prove the same digest runs in both environments.
11. ⭐⭐ Set your liveness probe to hit the database, stop Postgres for 40 seconds, and watch every pod restart. Then fix it.
12. ⭐ Add a startup probe and confirm a slow boot is no longer restarted in a loop.
13. ⭐ Pin the base image by digest and add the revision label; expose the sha at `/version`.
14. ⭐⭐ Run `trivy`, then write your gating policy: severity, fix-available, and an allowlist with expiry dates.

## 🎙️ Articulation drill

**Two minutes: "Walk me through your Dockerfile."**

Start with the framing, because it explains most of the content: **a container is one process, not a
small machine.** Then lead with the trap, since it's the one with real production consequences —
**shell-form `CMD` makes `sh` PID 1, and `sh` doesn't forward `SIGTERM`**, so your graceful shutdown
never runs and every deploy cuts in-flight requests and loses in-flight tasks. Exec form, and a grace
period longer than your slowest request. Then layers: least-changing first, dependencies before
source, and `.dockerignore` as **both a speed fix and a security control, because `COPY . .` without
one puts your local `.env` in the image.** Multi-stage next, framed as attack surface rather than
megabytes — compilers and a package manager in a running container are the toolkit an attacker wants
— and take the alpine question head-on: **musl means no manylinux wheels, so you get a twenty-minute
build and a bigger image.** Non-root with a numeric UID, read-only root filesystem, dropped
capabilities. Then the two rules that reach outside the file: **layers are append-only, so a deleted
secret is still in `docker history`**, and **config comes from the environment so one digest is
promoted rather than rebuilt** — because rebuilding means you tested something you didn't ship. Close
on probes, with the outage story: **a liveness probe that checks the database turns a thirty-second
failover into every pod restarting cold in every AZ and stampeding the database that was recovering.**
Liveness checks only that this process isn't wedged; readiness is where dependencies belong.
