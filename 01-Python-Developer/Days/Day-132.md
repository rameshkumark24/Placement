# Day 132

**L-132** · **Dependency injection in FastAPI** — sub-dependencies, `yield` teardown, and ⭐⭐ overrides that make integration tests fast

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `Depends` is signature inspection with a resolution graph and a
> per-request cache — you already built the first part on Day 112, and the three additions (sub-
> dependencies, `yield` teardown, and overrides) are what turn it from a convenience into the seam your
> tests hang on.**
>
> ⭐ This is FastAPI's best feature. **It is also the one people use as a global-variable smuggler**,
> so half of today is about where it stops being appropriate.

# Part 1 — ⭐ The graph

```python
def get_settings() -> Settings:                       # ⭐ leaf
    return Settings()

async def get_db(settings: Annotated[Settings, Depends(get_settings)]) -> AsyncSession:
    ...                                               # ⭐ depends on settings

async def current_user(
    token: Annotated[str, Depends(oauth2_scheme)],
    db: Annotated[AsyncSession, Depends(get_db)],
) -> User:                                            # ⭐⭐ depends on TWO things
    user = await db.get(User, decode(token)["sub"])
    if user is None:
        raise credentials_exception
    return user

@app.get("/me")
async def me(user: Annotated[User, Depends(current_user)]) -> UserOut:
    return user                                        # ⭐ the whole graph resolved for you
```

```
⭐⭐ FASTAPI WALKS THE GRAPH DEPTH-FIRST AND CACHES EACH RESULT **PER REQUEST**:
⭐        me → current_user → oauth2_scheme
⭐                          → get_db → get_settings
⭐   ⇒ ⭐⭐ `get_settings` IS CALLED ONCE PER REQUEST EVEN IF FIVE DEPENDENCIES
⭐        ASK FOR IT. ⭐ That is the property that makes deep graphs safe — and it
⭐        is why `get_db` yielding a session gives every dependency in one request
⭐        THE SAME session, which is what makes a per-request transaction possible
⭐        (Day 135).
⭐   ⇒ ⭐ turn it off with `Depends(f, use_cache=False)` when you genuinely want
⭐        a fresh value each time. ⭐⭐ Rare, and usually a sign the dependency is
⭐        doing something it should not.
⭐   ⇒ ⭐⭐ THE CACHE KEY IS THE CALLABLE PLUS ITS ARGUMENTS — so two dependencies
⭐        that both call `Depends(get_db)` share, but `Depends(paginator(50))`
⭐        and `Depends(paginator(100))` do not.
```

⭐⭐ **This is Day 093's fixture graph with different vocabulary** — same introspection, same
resolve-by-name, same composition. ⭐ Recognising them as one pattern is worth more than either API.

# Part 2 — ⭐⭐ `yield` dependencies, and where the teardown runs

```python
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with SessionLocal() as session:              # ⭐ Day 052's context manager
        try:
            yield session                              # ⭐⭐ the request runs here
            await session.commit()                     # ⭐ commit on success
        except Exception:
            await session.rollback()                   # ⭐⭐ roll back on ANY failure
            raise
```

```
⭐⭐ THE SHAPE IS EXACTLY A pytest FIXTURE (Day 093) AND EXACTLY A CONTEXT
⭐   MANAGER (Day 052) — setup, yield, teardown — and the teardown runs even when
⭐   the handler raises. ⭐ That is what makes it safe for anything that must be
⭐   released: sessions, file handles, locks, spans.
⭐
⭐ ⚠️⚠️ ⭐⭐ AND THE ORDERING FACT THAT CAUSES REAL BUGS: THE TEARDOWN RUNS
⭐    **AFTER THE RESPONSE IS GENERATED**, BUT **BEFORE IT IS SENT** — and, since
⭐    FastAPI 0.106, ⭐⭐ AFTER THE BACKGROUND TASKS TOO.
⭐    ⇒ ⭐ so an exception raised in the teardown cannot change the status code;
⭐         the response is already built. ⭐⭐ A `commit()` that fails there turns
⭐         into a 500 from the framework rather than your error handler.
⭐    ⇒ ⭐⭐ WHICH IS THE ARGUMENT FOR COMMITTING IN THE SERVICE LAYER RATHER THAN
⭐         IN THE DEPENDENCY: then a constraint violation is a domain error you
⭐         can translate (Day 120), not a mystery 500 after the fact.
⭐    ⇒ ⭐ and a `BackgroundTasks` job that uses the session is using a session
⭐         that is about to close — ⭐⭐ open a new one in the task.
```

```python
async def get_current_active_user(
    user: Annotated[User, Depends(current_user)],
) -> User:
    if not user.is_active:
        raise HTTPException(403, "inactive user")      # ⭐ dependencies may REJECT
    return user
```

⭐⭐ **A dependency that raises short-circuits the request** — the handler never runs. ⭐ That is how
authorisation composes: `current_user` → `active_user` → `admin_user`, each adding one check, **and the
handler's signature declares exactly which level it needs** (Day 118).

# Part 3 — ⭐ Parameterised and class dependencies

```python
class Paginator:                                       # ⭐ a class as a dependency
    def __init__(self, default: int = 20, maximum: int = 100):
        self.default, self.maximum = default, maximum
    def __call__(self, limit: int | None = None, cursor: str | None = None) -> Page:
        return Page(limit=min(limit or self.default, self.maximum), cursor=cursor)

paginate = Paginator(default=20, maximum=100)          # ⭐ configured once

@app.get("/orders")
async def list_orders(page: Annotated[Page, Depends(paginate)]): ...   # ⭐ Day 121
```

```python
def require(permission: str):                          # ⭐⭐ a dependency FACTORY
    async def checker(user: Annotated[User, Depends(current_user)]) -> User:
        if not user.can(permission):                   # ⭐ Day 118
            raise HTTPException(403, "forbidden")
        return user
    return checker

@app.delete("/orders/{order_id}",
            dependencies=[Depends(require("orders:delete"))])          # ⭐⭐ no argument needed
async def delete_order(order_id: int, db: DB): ...
```

```
⭐⭐ `dependencies=[...]` ON THE DECORATOR IS FOR SIDE-EFFECT-ONLY DEPENDENCIES —
⭐   ones whose RETURN VALUE the handler does not need. ⭐ Permission checks, rate
⭐   limits, audit hooks.
⭐   ⇒ ⭐⭐ AND THE RULE FROM DAY 108 STILL APPLIES: IF THE HANDLER USES THE
⭐        VALUE, MAKE IT A PARAMETER. `dependencies=[Depends(current_user)]` and
⭐        then reading the user from somewhere else is the smuggling pattern —
⭐        ⭐ invisible in the signature, and untestable in isolation.
⭐
⭐ ⭐ THREE SCOPES, WIDEST FIRST:
⭐   app = FastAPI(dependencies=[Depends(verify_api_key)])   ⭐ every route
⭐   router = APIRouter(dependencies=[Depends(require("admin"))])  ⭐ every route in it
⭐   @app.get(..., dependencies=[...])                       ⭐ one route
⭐   ⇒ ⚠️ ⭐⭐ AN APP-WIDE AUTH DEPENDENCY MUST HAVE AN ESCAPE HATCH for `/health`
⭐        and `/login`, or you have made login impossible (Day 108). ⭐ Prefer a
⭐        router-level dependency and an explicitly public router.
```

# Part 4 — ⭐⭐ Overrides: the reason DI is worth having

```python
# ⭐⭐ THE FEATURE THAT PAYS FOR THE WHOLE MECHANISM:
@pytest.fixture
def client(app, db_session):
    app.dependency_overrides[get_db] = lambda: db_session      # ⭐⭐ swap the real one
    app.dependency_overrides[current_user] = lambda: test_user
    yield TestClient(app)
    app.dependency_overrides.clear()                            # ⭐ ALWAYS clear
```

```
⭐⭐ WHAT THIS BUYS, AND IT IS DAY 095'S ARGUMENT ARRIVING IN A FRAMEWORK:
⭐   · ⭐⭐ NO PATCHING. You are not monkeypatching a module attribute and hoping
⭐        you patched where it is USED (Day 094) — you are replacing a node in a
⭐        graph, by identity.
⭐   · ⭐⭐ NO MOCKS. The override returns a REAL session bound to a transaction
⭐        that gets rolled back (Day 097), or a real fake repository (Day 095).
⭐   · ⭐ the whole stack still runs: routing, validation, serialisation,
⭐        middleware, error handling. ⭐⭐ That is a genuine integration test at
⭐        millisecond cost, which is what makes Day 092's fat middle affordable.
⭐   ⇒ ⚠️ ⭐ THE OVERRIDE KEY IS THE FUNCTION OBJECT, so importing `get_db` from
⭐        two places (Day 074!) gives you two keys and a silently ineffective
⭐        override. ⭐⭐ One canonical import path.
⭐   ⇒ ⚠️ ⭐ `dependency_overrides` IS APP-LEVEL AND PERSISTS — forget to clear it
⭐        and the next test runs against your override. ⭐ Day 092's order
⭐        dependence, self-inflicted.
```

```
⭐⭐ AND THE DESIGN PRESSURE, WHICH IS THE REAL POINT: A DEPENDENCY IS A SEAM.
⭐   ⇒ ⭐ anything you might want to replace in a test — the clock (Day 096),
⭐        the HTTP client, the payment gateway, the queue — ⭐⭐ SHOULD BE A
⭐        DEPENDENCY RATHER THAN A MODULE-LEVEL IMPORT.
⭐   ⇒ ⭐⭐ WHICH IS DAY 089's "PUSH I/O TO THE EDGES" AND DAY 096's "INJECT THE
⭐        CLOCK", enforced by the framework: if it is not a dependency, the only
⭐        way to replace it is patching, and patching is where tests go to rot.
```

# Part 5 — ⭐ Where DI stops being the answer

```
⚠️⚠️ ⭐⭐ THE ANTI-PATTERN: `Depends` AS A GLOBAL-VARIABLE SMUGGLER.
⭐    A dependency that returns "the current tenant" by reading a context
⭐    variable, or one that mutates `request.state`, is not injection — ⭐ it is
⭐    a global with extra syntax, and it is invisible in the handler.
⭐    ⇒ ⭐⭐ THE TEST: CAN THE HANDLER BE CALLED DIRECTLY, IN A UNIT TEST, WITH
⭐         ORDINARY ARGUMENTS? ⭐ If yes, the dependency is a seam. If no, it is
⭐         hidden state.
⭐
⭐ ⭐⭐ AND THE LAYERING RULE (Day 090): DEPENDENCIES ARE AN **HTTP-LAYER**
⭐   CONCEPT. Your service functions must take plain arguments:
⭐        ✘ ⭐ async def place_order(db = Depends(get_db))       ⇒ the domain now
⭐             imports FastAPI and cannot run in a Celery worker or a CLI
⭐        ✔ ⭐⭐ async def place_order(db: AsyncSession, user: User, ...)
⭐             ⇒ ⭐ the ROUTE resolves the dependencies and passes them down
⭐   ⇒ ⭐⭐ THE ROUTE IS THE ONLY PLACE `Depends` APPEARS. Everything below takes
⭐        ordinary parameters, which is what keeps the domain testable without
⭐        HTTP and callable from anywhere.
```

| ⭐ Concern | ⭐ Use |
|---|---|
| ⭐⭐ Applies to every request, sees the response | ⭐ middleware (Day 108) |
| ⭐ Applies to some routes, no return value | ⭐ `dependencies=[...]` |
| ⭐⭐ **The handler needs the value** | ⭐⭐ a parameter with `Depends` |
| Needed by a service | ⭐ an ordinary argument, passed by the route |

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Expecting a dependency to run once per app | ⭐ Once per **request**, cached within it. |
| ⭐⭐ **Committing in the `get_db` teardown** | ⭐⭐ Runs after the response is built — a failure becomes a mystery 500. |
| A background task using the request's session | ⭐ It is about to close. Open a new one. |
| ⭐ `dependencies=[Depends(current_user)]` then reading the user elsewhere | ⭐⭐ Smuggling. If the handler uses it, make it a parameter. |
| ⭐ App-wide auth with no exemptions | ⭐ Login becomes impossible. |
| ⭐⭐ **Importing `get_db` from two paths** | ⭐⭐ Two override keys; the override silently does nothing. |
| Not clearing `dependency_overrides` | ⭐ Order-dependent tests (Day 092). |
| ⭐ Patching instead of overriding | ⭐⭐ You have a seam. Use it. |
| ⭐⭐ **`Depends` in a service signature** | ⭐⭐ The domain now imports FastAPI and cannot run in a worker. |
| A dependency that mutates `request.state` | ⭐ A global with extra syntax. |
| `use_cache=False` by default | ⭐ Usually a sign the dependency is doing too much. |

## Interview questions

**Q: How does `Depends` work?**
> Signature inspection plus a resolution graph. FastAPI reads the handler's parameters, and for each
> `Depends` it resolves that callable — which may itself have dependencies — depth-first, caching each
> result per request. So `get_settings` runs once even if five things ask for it, and more importantly
> `get_db` yields one session that every dependency in that request shares, which is what makes a
> per-request transaction possible. It's the same mechanism as pytest fixtures: same introspection,
> same resolve-by-name, same composition into a graph rather than an inheritance hierarchy.

**Q: What's special about a `yield` dependency?**
> It's setup, yield, teardown — the same shape as a context manager or a pytest fixture — and the
> teardown runs even if the handler raises, which is what makes it safe for sessions, locks and file
> handles. The detail that causes bugs is *when*: the teardown runs after the response has been
> generated but before it's sent, and after background tasks. So an exception there can't change the
> status code — a failing `commit()` in the teardown becomes a framework 500 rather than something your
> error handler shaped. That's my argument for committing in the service layer instead, where a
> constraint violation is a domain error you can translate.

**Q: Why are dependency overrides better than patching?**
> Because you're replacing a node in a graph by identity rather than monkeypatching a module attribute
> and hoping you patched where it's used. The override returns a real session bound to a transaction
> that gets rolled back, so the whole stack still runs — routing, validation, serialisation, middleware
> — and you get a genuine integration test at millisecond cost. The gotchas are that the key is the
> function object, so importing `get_db` from two paths gives you two keys and a silently ineffective
> override; and overrides are app-level and persist, so a test that forgets to clear them poisons the
> next one.

**Q: Should service functions take `Depends`?**
> No. `Depends` is an HTTP-layer concept, and putting it in a service signature means the domain
> imports FastAPI and can't run in a Celery worker, a CLI or a test without one. The route is the only
> place `Depends` should appear: it resolves the dependencies and passes ordinary arguments down. That
> keeps the business rules testable without HTTP, which is the whole reason for the layering.

**Q: When is a dependency the wrong tool?**
> When it's smuggling hidden state — a dependency that reads a context variable or mutates
> `request.state`, so the handler's signature doesn't tell you what it depends on. The test I use is
> whether the handler can be called directly in a unit test with ordinary arguments; if it can, the
> dependency is a seam, and if it can't, it's a global with extra syntax. And for anything that applies
> to every request and needs to see the response — request ids, timing, CORS — middleware is the right
> layer, not a dependency.

## 🎙️ Articulation drill

Record two minutes: **"How do you test a FastAPI application?"**

⭐ **Lead with the seam, because it decides everything else:** **"the thing that makes it pleasant is
dependency overrides. Anything I might want to replace — the database session, the current user, the
clock, the payment gateway — is a dependency, and in tests I swap the node in the graph rather than
monkeypatching a module and hoping I patched where it's used."**

⭐⭐ **Then what that buys, concretely:** *"the override returns a real session bound to a transaction
that's rolled back after the test, so it isn't a mock — the whole stack still runs. Routing,
validation, serialisation, middleware, error handling, all exercised, in about a millisecond because
the test client calls the app in-process. That's what makes a fat integration layer affordable, and I'd
rather have three hundred tests through the real stack than three hundred unit tests full of mocks,
because in a backend most bugs are at the seams."*

⭐⭐ **Then the two traps, since they're both silent:** *"two things bite. The override key is the
function object, so if `get_db` is imported from two different paths you get two keys and the override
silently does nothing — the test passes against your real database and you don't notice. And overrides
are app-level and persist, so forgetting to clear them poisons the next test. I'd clear them in the
fixture teardown and run with `pytest-randomly` so order dependence surfaces immediately."*

⭐ **Close on the design consequence:** *"and the deeper point is that dependencies create design
pressure. If something isn't a dependency, the only way to replace it in a test is patching — so the
framework nudges you toward pushing I/O to the edges, which is what you'd want anyway. The rule I keep
is that `Depends` appears only in routes; services take ordinary arguments, so the domain stays
callable from a worker or a script."*
