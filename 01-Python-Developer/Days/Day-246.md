# Day 246 🔗

**P-246** · 🔗 **The full-stack contract** — ⭐⭐ making a renamed field a build failure

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the boundary between your API and your client is the only place in your
> whole system with no type checking and no test — both sides are individually correct and nothing
> compares them — so the single highest-leverage thing you can build is a generated client that turns
> a contract change into a compile error.**
>
> Today: ⭐ the drift, ⭐⭐ generation from OpenAPI, versioning, and what generation does **not** give you.

# Part 1 — ⭐⭐ The gap

```
⭐⭐ EVERY OTHER BOUNDARY IN YOUR SYSTEM IS CHECKED:

⭐   Python function → function ...... ⭐ mypy
⭐   Python → Postgres ............... ⭐ the schema + migrations
⭐   component → component ........... ⭐ TypeScript
⭐   ⭐⭐ FASTAPI → REACT ............... **NOTHING**

⭐   ⇒ ⭐ you rename user.full_name → user.name
⭐   ⇒ ⭐ mypy: clean ✅   pytest: green ✅   tsc: clean ✅
⭐        ⭐ every frontend test passes (⭐⭐ THE MOCKS WERE UPDATED
⭐          BY HAND, OR NEVER)
⭐   ⇒ ⭐⭐ PRODUCTION RENDERS THE WORD "undefined" TO A CUSTOMER.
⭐     ⭐ NO ERROR. NO ALERT. THE MOST-TESTED SYSTEM IN THE WORLD
⭐       DOES NOT CATCH THIS, BECAUSE BOTH SIDES ARE CORRECT AND
⭐       NOBODY COMPARED THEM.
```

| ⭐ The four ways teams "solve" this | Reality |
|---|---|
| Careful communication | ⭐ Works until someone is on holiday |
| Hand-written TS types | ⭐⭐ A **second** source of truth that drifts silently — worse than none, because it looks safe |
| Integration tests against a live API | ⭐ Catches it, slowly, and only for paths you tested |
| ⭐⭐ **Generate the client from the spec** | ⭐ Catches it **at compile time**, for every field, free |

# Part 2 — ⭐⭐ Generation

```
⭐⭐ THE PIPELINE — and note that step 1 already exists

⭐   ① FastAPI ⇒ ⭐ /openapi.json  (⭐⭐ FREE. You already have it.)
⭐   ② generator ⇒ TypeScript types + a typed client + Zod schemas
⭐   ③ ⭐ COMMIT THE OUTPUT ⇒ diffs are REVIEWABLE in the PR
⭐   ④ ⭐⭐ CI REGENERATES AND FAILS IF THE DIFF IS NON-EMPTY
⭐      ⇒ ⭐ "you changed the API and did not regenerate" becomes
⭐        a BUILD FAILURE, WITH THE DIFF ATTACHED.
```

```bash
# ⭐ one command, in package.json
npx openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts
```

```typescript
// ⭐⭐ now every call is checked against the real contract
import createClient from "openapi-fetch";
const client = createClient<paths>({ baseUrl: "/api" });

const { data, error } = await client.GET("/users/{id}", {
  params: { path: { id } },      // ⭐ wrong param name ⇒ compile error
});
data.nmae;                       // ⭐⭐ COMPILE ERROR. THE TYPO IS CAUGHT.
```

```python
# ⭐⭐ make the generated output good by making the spec good
@app.get(
    "/users/{id}",
    response_model=UserPublic,       # ⭐ the allow-list (Day 236)
    responses={404: {"model": ErrorBody}, 422: {"model": ValidationBody}},
    operation_id="getUser",          # ⭐⭐ becomes the CLIENT METHOD NAME —
)                                    #    without it you get getUserUsersIdGet
async def get_user(id: UUID): ...
```

| ⭐ Spec hygiene | Why |
|---|---|
| **`operation_id` on every route** | ⭐⭐ Readable generated method names |
| **Declare error responses** | ⭐ Otherwise the client types errors as `unknown` |
| **`response_model` everywhere** | ⭐⭐ A route without one generates `any` — **and leaks fields** |
| **Named Pydantic models, not inline dicts** | ⭐ Inline shapes generate anonymous types you cannot import |

# Part 3 — Versioning the contract

```
⭐⭐ TWO VERSIONS ARE ALWAYS LIVE (Day 245's stale tab).
⭐   ⇒ ⭐ SO EVERY API CHANGE IS EITHER ADDITIVE OR A MIGRATION.

⭐   ✅ SAFE (additive)
⭐     · add an OPTIONAL field
⭐     · add a new endpoint
⭐     · ⭐ add a value to an enum ⇒ ⭐⭐ ONLY IF CLIENTS HANDLE
⭐       UNKNOWN VALUES. If your switch is exhaustive, this BREAKS
⭐       THEM — add a default branch first.

⭐   ❌ BREAKING (needs a migration)
⭐     · remove or rename a field   · change a type
⭐     · make an optional field required
⭐     · ⭐⭐ NARROW AN ENUM (removing a value)

⭐   ⭐⭐ THE EXPAND–MIGRATE–CONTRACT DANCE — the same one you used
⭐     for database columns in Stage 5:
⭐     ① ADD the new field alongside the old (both populated)
⭐     ② SHIP the client that reads the new one
⭐     ③ ⭐ WAIT for old clients to age out (measure it — see below)
⭐     ④ REMOVE the old field
```

> ⭐ **"Wait for old clients to age out" needs a number.** Send a build id or version header from the
> client and log it. **Then "how many users are still on the old contract?" is a query rather than a
> guess** — and that is what makes step ④ safe instead of nervous.

# Part 4 — ⭐⭐ What generation does NOT give you

```
⭐⭐ SAY THIS PART OUT LOUD — IT IS WHERE PEOPLE OVERTRUST THE TOOL.

⭐   ❌ ⭐⭐ IT DOES NOT VALIDATE AT RUNTIME. The generated type is
⭐      still erased (Day 218). If the server sends something the
⭐      spec does not describe — ⭐ AND SERVERS DO, VIA A BUG OR A
⭐      PROXY OR AN ERROR PAGE — ⭐⭐ YOU GET THE undefined ANYWAY.
⭐      ⇒ ⭐ KEEP ZOD AT THE BOUNDARY (Day 219) FOR RESPONSES THAT
⭐        MATTER. Generation kills the DRIFT; validation catches
⭐        the LIE.
⭐   ❌ IT DOES NOT CHECK **SEMANTICS**. `amount: number` says
⭐      nothing about pence vs pounds. ⭐⭐ A UNIT CHANGE PASSES
⭐      EVERY TYPE CHECK AND BILLS SOMEONE 100×.
⭐   ❌ IT DOES NOT CHECK NULLABILITY YOU DID NOT DECLARE.
⭐      ⭐ An `Optional[str]` you forgot to mark generates `string`.
⭐   ❌ IT DOES NOT TEST BEHAVIOUR — Day 244 still applies.
```

| ⭐ Layer | Catches |
|---|---|
| Generated types | ⭐⭐ Shape drift, at compile time |
| Runtime validation (Zod) | ⭐ The server lying about its own spec |
| ⭐⭐ Contract tests | Behaviour: does 404 actually return the error body you documented? |
| E2E | ⭐ The whole path, once |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you keep the frontend and backend in sync?"**

Name the gap precisely — that framing is the whole answer. **The API-to-client boundary is the only
place in my system with no type checking and no test. I rename a field, mypy is clean, pytest is green,
TypeScript compiles, every frontend test passes because the mocks were updated by hand or never — and
production renders the word "undefined" to a customer. Both sides are individually correct and nothing
compared them.**

Then the fix, and why the cheap-looking alternative is worse. **I generate the TypeScript client from
the OpenAPI spec FastAPI already produces. Hand-written types are worse than none, because they're a
second source of truth that drifts silently while looking safe. The generated output is committed so
diffs are reviewable, and CI regenerates and fails on a non-empty diff — so "you changed the API and
didn't regenerate" is a build failure with the diff attached.**

Then versioning, tied to something you already do. **Two versions are always live because of open tabs,
so every change is additive or a migration — expand, migrate, contract, the same dance as a database
column. And I send a build id from the client so "how many users are still on the old contract" is a
query rather than a guess, which is what makes the contract step safe instead of nervous.**

Close on the limits, because overtrusting this is the failure mode. **Generation kills drift; it doesn't
validate at runtime. The types are erased, so if the server sends something the spec doesn't describe —
a bug, a proxy, an error page — I get the undefined anyway. So Zod stays at the boundary for responses
that matter. And no type check catches a unit change from pounds to pence, which passes everything and
bills someone a hundred times over.**
