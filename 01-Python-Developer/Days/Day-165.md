# Part 1 — ⭐ The chain, assembled

```python
# api/deps.py
def get_current_user(
    cred: HTTPAuthorizationCredentials | None = Depends(HTTPBearer(auto_error=False)),
    db: Session = Depends(get_db),
) -> User:
    if cred is None:
        raise unauthorised("missing_token")
    try:
        claims = jwt.decode(cred.credentials, PUBLIC_KEY,
                            algorithms=["RS256"],              # ⭐⭐ a list YOU control
                            audience=S.jwt_audience, issuer=S.jwt_issuer)
    except jwt.ExpiredSignatureError:
        raise unauthorised("token_expired")                    # ⭐ distinct: client refreshes
    except jwt.PyJWTError:
        raise unauthorised("invalid_token")
    user = db.get(User, int(claims["sub"]))
    if user is None or not user.is_active:                     # ⭐⭐ revocation takes effect
        raise unauthorised("invalid_token")                    # ⭐ SAME message — no oracle
    return user

def get_organiser_context(user: User = Depends(get_current_user)) -> OrganiserCtx:
    if user.organiser_id is None:
        raise forbidden("not_an_organiser")                    # ⭐⭐ 403, not 401
    set_tenant(user.organiser_id)                              # ⭐ ContextVar + SET LOCAL
    return OrganiserCtx(user=user, organiser_id=user.organiser_id)
```

```
⭐⭐ FOUR DECISIONS BAKED INTO THAT, EACH DEFENSIBLE:
⭐  1. ⭐⭐ TWO SEPARATE DEPENDENCIES. `get_current_user` answers WHO;
⭐       `get_organiser_context` answers WHICH TENANT. ⭐ Attendee routes need
⭐       only the first, ⭐⭐ so an attendee route CANNOT accidentally acquire
⭐       tenant scope. ⭐ The type system carries the distinction.
⭐  2. ⭐ 401 CARRIES `WWW-Authenticate`; 403 DOES NOT. ⭐⭐ 401 = I don't know
⭐       you (refresh may help). 403 = I know you and no (refresh will not).
⭐       ⭐ Getting it wrong makes clients refresh-loop on a permissions error.
⭐  3. ⭐⭐ `token_expired` IS THE ONLY DISTINGUISHED FAILURE. ⭐ "no such
⭐       user", "deactivated", "bad signature" are one message, or you have an
⭐       account oracle (Day 114).
⭐  4. ⭐⭐ THE DB LOOKUP IS DELIBERATE. Without it a banned organiser keeps
⭐       selling until their token expires. ⭐ `Depends` caches per request, so
⭐       three dependencies needing the user cost one query (Day 132).
```

# Part 2 — ⭐⭐ Object-level authorisation: the part scopes do not cover

```
⭐⭐ THE MISTAKE, WRITTEN OUT SO YOU CAN RECOGNISE IT ANYWHERE:

⭐   ❌ order = repo.get(order_id)                 # ⭐ fetch
⭐      if order.user_id != user.id:               # ⭐ then check
⭐          raise HTTPException(403)
⭐
⭐   ⭐ CORRECT TODAY. ⭐⭐ AND IT FAILS THE MOMENT ANYONE ADDS A SECOND CALL
⭐     SITE AND FORGETS THE SECOND LINE — ⭐ because the first line still
⭐     works perfectly.
⭐   ⭐ AND IT LEAKS EXISTENCE: 403 says "this order exists and is not
⭐     yours". ⭐⭐ 404 says nothing. ⭐ For an id you can enumerate, prefer 404.
⭐
⭐   ✅ ⭐⭐ PUT THE SCOPE IN THE QUERY (Day 118, Day 139):
⭐        def get_for_user(self, order_id: int, *, user_id: int) -> Order | None:
⭐            return self._db.scalar(select(Order).where(
⭐                Order.id == order_id, Order.user_id == user_id))
⭐        ⇒ ⭐ a wrong id returns None ⇒ 404. ⭐⭐ There is no code path that
⭐          returns someone else's row, because the query cannot express it.
```

```
⭐⭐ THE THREE AUTHORISATION QUESTIONS, ANSWERED IN THREE DIFFERENT PLACES —
⭐   BEING ABLE TO SEPARATE THESE IS THE POINT OF TODAY:

⭐   1. ⭐ AUTHENTICATION — "who are you?"        ⇒ ⭐ the dependency
⭐   2. ⭐ ROLE — "may your KIND do this at all?" ⇒ ⭐ the router dependency
⭐        (attendees cannot reach `POST /events` — ⭐⭐ 403 before any query)
⭐   3. ⭐⭐ OBJECT — "may you do this to THIS one?" ⇒ ⭐⭐ THE `WHERE` CLAUSE
⭐        (⭐ and for organisers, RLS underneath it — Day 160)
⭐
⭐   ⇒ ⭐⭐ SCOPES AND ROLES CANNOT ANSWER (3), AND NO AMOUNT OF ROLE CHECKING
⭐        WILL EVER CATCH AN IDOR. ⭐ They are different mechanisms for
⭐        different questions, and conflating them is the single most common
⭐        authorisation design error.
```

# Part 3 — ⭐⭐ Tenant isolation, enforced by the database

```sql
-- ⭐ Day 160, applied to every organiser-scoped table
ALTER TABLE events        ENABLE ROW LEVEL SECURITY;
ALTER TABLE events        FORCE  ROW LEVEL SECURITY;      -- ⭐⭐ or the owner bypasses
CREATE POLICY tenant ON events
  USING (organiser_id = current_setting('app.organiser_id', true)::uuid);
```

```python
def set_tenant(organiser_id: UUID) -> None:
    db.execute(text("SET LOCAL app.organiser_id = :t"), {"t": str(organiser_id)})
    #                    ⭐⭐ LOCAL. `SET` persists on a pooled connection and
    #                       the NEXT request inherits this tenant.
```

```
⭐⭐ THE FOUR-LAYER DEFENCE FOR CROSS-TENANT ACCESS, AND WHY EACH EXISTS:
⭐   1. ⭐ the router dependency establishes the tenant from the TOKEN,
⭐        ⭐⭐ never from the request (a body-supplied `organiser_id` is IDOR)
⭐   2. ⭐ the repository requires `organiser_id` as a keyword-only argument
⭐        ⇒ ⭐⭐ forgetting it is a TypeError at test-collection time
⭐   3. ⭐ RLS refuses at the database ⇒ ⭐⭐ raw SQL, a future endpoint, and a
⭐        psql session are all covered
⭐   4. ⭐⭐ AND THE TEST: for every organiser-scoped endpoint, a test where
⭐        organiser A requests organiser B's object and gets 404.
⭐
⭐   ⇒ ⭐⭐ THE PROPERTY THAT MATTERS: WITH RLS, FORGETTING THE FILTER RETURNS
⭐        **ZERO ROWS**, NEVER SOMEONE ELSE'S. ⭐ `current_setting(..., true)`
⭐        is NULL when unset, and `organiser_id = NULL` is NULL, which is not
⭐        true. ⭐⭐ Fail closed by construction, not by care.
```

```
⭐⭐ AND THE PLACE TENANT ISOLATION IS ACTUALLY LOST (Day 160): BACKGROUND
⭐   JOBS. ⭐ The request is gone, the `ContextVar` is gone, and `SET LOCAL`
⭐   was scoped to a transaction that ended.
⭐   ⇒ ⭐ EVERY queued payload carries `organiser_id` EXPLICITLY, and every
⭐        task re-establishes it at the top. ⭐⭐ Tomorrow's worker is where
⭐        this gets tested; today is where you make it possible.
```

# Part 4 — ⭐⭐ Login, and the four traps

```python
@router.post("/auth/login")
def login(body: LoginIn, response: Response, db: Session = Depends(get_db)):
    #  ⭐⭐ TRAP 4: `def`, NOT `async def`. argon2 is ~200 ms of CPU; on the
    #     event loop, credential stuffing is a whole-API denial of service.
    check_rate_limit(f"login:ip:{client_ip}", 20, 60)        # ⭐⭐ TRAP 3: BOTH keys
    check_rate_limit(f"login:acct:{body.email}", 5, 300)     # ⭐ or a botnet wins

    user = db.scalar(select(User).where(User.email == body.email))
    hashed = user.password_hash if user else DUMMY_HASH      # ⭐⭐ TRAP 1: always hash
    ok = argon2.verify(hashed, body.password)                # ⭐ constant-ish time
    if not user or not ok:
        raise unauthorised("invalid_credentials")            # ⭐ ONE message
    if argon2.check_needs_rehash(user.password_hash):
        user.password_hash = argon2.hash(body.password); db.commit()

    sid = new_session(db, user)                              # ⭐⭐ TRAP 2: NEW id (fixation)
    response.set_cookie("session", sid, httponly=True, secure=True,
                        samesite="lax", max_age=900, path="/")
    return {"expires_in": 900}
```

```
⭐⭐ AND THE ACCOUNT-ENUMERATION AUDIT — five places, and people fix one:
⭐   1. ⭐ login response body      ⇒ one message ✅
⭐   2. ⭐⭐ login response TIME     ⇒ the dummy hash ✅
⭐   3. ⭐⭐ REGISTRATION            ⇒ "email already in use" is an oracle.
⭐        ⭐ Return 202 and send an email either way — ⭐⭐ "we've sent you a
⭐        link" is true in both cases and leaks nothing.
⭐   4. ⭐ PASSWORD RESET           ⇒ same. Always 202.
⭐   5. ⭐⭐ RATE-LIMIT RESPONSES    ⇒ ⭐ if a real account rate-limits after 5
⭐        attempts and an unknown one never does, ⭐⭐ THE RATE LIMITER IS THE
⭐        ORACLE. ⭐ Limit unknown emails identically.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| One dependency for identity and tenant | An attendee route can accidentally acquire tenant scope. Separate them. |
| 401 without `WWW-Authenticate` | Required by the RFC and the most-skipped header in it. |
| 403 where 401 belongs | Clients refresh-loop on a permissions error. |
| Distinguishing "no such user" from "wrong password" | An account oracle — in the body *and* in the timing. |
| Skipping the DB lookup in `get_current_user` | A banned organiser keeps selling until their token expires. |
| Fetch-then-check ownership | Correct until the second call site forgets. Put the scope in the `WHERE`. |
| 403 for someone else's object | Confirms it exists. Prefer 404 for enumerable ids. |
| Treating roles as sufficient authorisation | No amount of role checking catches an IDOR. |
| Tenant taken from the request body | IDOR with extra steps. It comes from the token. |
| `SET` instead of `SET LOCAL` | The next request on that pooled connection inherits this tenant. |
| RLS without `FORCE` | Your app connects as the owner, so the policy does nothing. |
| Forgetting tenant context in queued payloads | The job runs with no tenant, or worse, a default. |
| `async def` login | 200 ms of argon2 on the event loop; credential stuffing becomes a DoS. |
| Rate limiting login by IP only | A botnet defeats it; account-only lets one IP spray thousands. |
| Rate limiting only known accounts | The rate limiter becomes the enumeration oracle. |
| "Email already in use" on registration | An oracle. Return 202 and send an email either way. |
| Security tests that use `dependency_overrides` | They prove nothing about auth. This file overrides nothing. |
| A hand-written list of protected routes | It covers the endpoints you remembered — the ones least likely to be wrong. |

## Interview questions

**Q: How is authorisation structured in your service?**

> As three separate questions answered in three places. Authentication — who are you — is a
> dependency that verifies the token with an explicit algorithm list, audience and issuer, and then
> looks the user up so a ban takes effect immediately rather than at token expiry. Role — may your
> kind do this at all — is a router-level dependency, so an attendee hitting an organiser route gets
> 403 before any query runs and default-deny is the structure rather than a habit. And object-level —
> may you do this to *this* one — lives in the `WHERE` clause, so a wrong id returns `None` and
> becomes a 404. The key point is that the third question is the one roles and scopes can't answer:
> `orders:write` says you may write orders, not that you may write *this* order, and no amount of
> role checking catches an IDOR.

**Q: Why 404 rather than 403 for someone else's order?**

> Because 403 confirms the object exists. If order ids are sequential or guessable, a 403-versus-404
> difference lets someone enumerate how many orders exist and which ids are real, which is
> information I never intended to publish. Returning 404 says nothing. And the way I get it for free
> is by scoping in the query rather than fetching and then checking — `WHERE id = :id AND user_id =
> :me` returns `None` for a row that isn't mine, which is indistinguishable from one that doesn't
> exist. That's also more durable: fetch-then-check is correct until someone adds a second call site
> and forgets the check, because the fetch line still works perfectly on its own.

**Q: How do you guarantee an organiser can't see another organiser's data?**

> Four layers, and the fourth is the one that makes it a guarantee. The tenant comes from the token,
> never from the request — a body-supplied organiser id is IDOR. The repository takes `organiser_id`
> as a required keyword-only argument, so forgetting it is a `TypeError` at collection time rather
> than a leak in production. Row-level security enforces it in Postgres with `FORCE`, so raw SQL, a
> psql session, and endpoints that don't exist yet are all covered. And a test per organiser-scoped
> endpoint where organiser A asks for organiser B's object and gets 404. The property that makes RLS
> different in kind is that it fails closed: `current_setting` is NULL when unset, and
> `organiser_id = NULL` is NULL rather than true, so forgetting to set the tenant returns zero rows —
> never someone else's.

**Q: Your test suite is green. What does it prove about security?**

> On its own, very little, and that's worth saying. Most of my tests override `get_current_user`,
> because they're about orders rather than JWT — which is correct, but it means those two hundred
> tests have replaced the security boundary with a function that always says yes. So there's a
> separate file that overrides nothing and clears `dependency_overrides` in a fixture: real login,
> real token, missing token gives 401 with `WWW-Authenticate`, expired token, wrong signing key, an
> `alg=none` forgery, a deactivated user's still-valid token, cross-user and cross-tenant access
> returning 404, no password hash in any response body, and RLS refusing raw SQL. And crucially the
> list of protected routes is derived from `app.routes` minus an explicit public list, not
> hand-written — otherwise it tests the endpoints I remembered, which are exactly the ones least
> likely to be wrong.

**Q: Where can someone still enumerate accounts?**

> Five places, and people usually fix one. The login response body, which is one shared message. The
> login response *time*, which needs a dummy hash so a missing user costs the same as a wrong
> password. Registration, where "email already in use" is a straight oracle — I return 202 and send
> an email either way, since "we've sent you a link" is true in both cases. Password reset, same
> thing. And the one that gets missed entirely: rate-limit responses. If a real account starts
> returning 429 after five attempts and an unknown email never does, the rate limiter *is* the
> oracle, so unknown emails have to be limited identically.

## 🎙️ Articulation drill

**Two minutes: "How did you secure this service?"**

Structure it as three questions in three places — identity in a dependency, role at the router,
object in the `WHERE` clause — and make the point that the third is the one roles cannot answer, so
an IDOR is invisible to any amount of role checking. Then tenant isolation as four layers ending at
RLS, and explain why RLS is different in kind: the guarantee moves out of your discipline and into
the database, and forgetting the filter returns zero rows rather than someone else's. Name both silent
RLS failures. Then be honest about the test suite: most tests override auth, which is correct and
means they prove nothing about it, so there's a file that overrides nothing and derives its route
list from the app. Close with the strongest line available: **every "must not" in my threat model has
a test number next to it.**
