# Day 135

**L-135** · **SQLAlchemy 2.0** — the engine, the session, and ⭐⭐ the unit of work you have to understand

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the Session is a unit of work — it tracks the objects you have touched
> and writes them all at once, which means most of SQLAlchemy's surprising behaviour is it deciding to
> flush at a moment you did not choose.**
>
> ⭐ SQLAlchemy is the hardest thing in this stage, and **almost all of the difficulty is the session
> lifecycle** rather than the query syntax.

# Part 1 — ⭐ Engine, session, and models

```python
from sqlalchemy import create_engine, String, ForeignKey, select
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship, sessionmaker

engine = create_engine(settings.database_url, pool_size=10, max_overflow=5,
                       pool_pre_ping=True, echo=False)          # ⭐ one per process (Day 133)
SessionLocal = sessionmaker(engine, expire_on_commit=False)      # ⭐⭐ see Part 4

class Base(DeclarativeBase): pass

class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)            # ⭐⭐ 2.0 style: annotations
    sku: Mapped[str] = mapped_column(String(64), index=True)
    qty: Mapped[int]
    total: Mapped[Decimal] = mapped_column(Numeric(12, 2))       # ⭐⭐ NUMERIC, never FLOAT (Day 041)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)
    user: Mapped["User"] = relationship(back_populates="orders")
```

```
⭐⭐ THREE THINGS ABOUT THE ENGINE THAT DECIDE PRODUCTION BEHAVIOUR:
⭐  1. ⭐⭐ IT OWNS A CONNECTION POOL. `pool_size × workers × pods` against
⭐       `max_connections` (Days 111, 133) — ⭐ the arithmetic that presents as
⭐       "the database is down".
⭐  2. ⭐⭐ `pool_pre_ping=True` sends a cheap `SELECT 1` before handing out a
⭐       connection ⇒ ⭐ it costs a round trip and it eliminates the "server
⭐       closed the connection unexpectedly" class of error after a database
⭐       restart or an idle timeout. ⭐⭐ Worth it, essentially always.
⭐  3. ⭐ `echo=True` logs every statement — ⭐⭐ invaluable in development and
⭐       exactly how you find an N+1 (Day 136).
```

⭐ **`Numeric`, not `Float`, for money** — Day 041, at the schema level. ⭐⭐ **A `FLOAT` column is
wrong before any of your code runs**, and it is a migration to fix once there is data in it.

# Part 2 — ⭐⭐ The unit of work

```python
with SessionLocal() as session:
    order = Order(sku="ABC", qty=2, total=Decimal("50.00"), user_id=7)
    session.add(order)                    # ⭐ PENDING — no SQL yet
    print(order.id)                        # ⭐⭐ None. The database has not seen it.
    session.flush()                        # ⭐⭐ SQL is sent; id is now populated
    print(order.id)                        # ⭐ 42 — but NOT committed
    session.commit()                       # ⭐ transaction ends
```

```
⭐⭐ THE THREE VERBS, AND CONFUSING THEM CAUSES MOST SQLALCHEMY BUGS:
⭐   `add()`    ⇒ ⭐ track this object. NO SQL.
⭐   `flush()`  ⇒ ⭐⭐ SEND the pending SQL. ⭐ Still inside the transaction, so
⭐                  it is invisible to other connections and can be rolled back.
⭐                  ⭐⭐ This is where you get generated ids and where INTEGRITY
⭐                  ERRORS surface.
⭐   `commit()` ⇒ ⭐ flush + COMMIT. Now it is durable and visible.
⭐
⭐ ⭐⭐ AND THE PART THAT SURPRISES EVERYONE: **AUTOFLUSH**. The session flushes
⭐   AUTOMATICALLY before any query, so that your query sees your own pending
⭐   changes.
⭐   ⇒ ⭐⭐ THEREFORE A `SELECT` CAN RAISE AN `IntegrityError` FROM AN `INSERT`
⭐        YOU MADE THREE FUNCTIONS AGO — ⭐ and the traceback points at the
⭐        SELECT, which is somewhere else entirely.
⭐   ⇒ ⭐ that is the single most confusing SQLAlchemy error, and now you know
⭐        the shape: ⭐⭐ THE STATEMENT THAT RAISED IS NOT THE STATEMENT THAT WAS
⭐        WRONG. Look at what was added before it.
⭐   ⇒ ⭐ `with session.no_autoflush:` suppresses it in the rare case you need to.
```

```python
# ⭐ 2.0 QUERY STYLE — `select()`, not `session.query()`
stmt = select(Order).where(Order.user_id == user_id).order_by(Order.created_at.desc()).limit(20)
orders = session.scalars(stmt).all()                    # ⭐⭐ scalars ⇒ Order objects
one = session.scalars(select(Order).where(Order.id == 7)).one_or_none()
order = session.get(Order, 7)                            # ⭐ by primary key — checks the identity map
```

⭐⭐ **`session.get()` checks the identity map first**, so fetching the same row twice in one session
returns **the same Python object** and may issue no SQL at all. ⭐ That is the identity map, and it is
why mutating an object you fetched earlier is visible to code that fetches it again.

# Part 3 — ⭐⭐ Session per request

```python
# ⭐ deps.py (Day 132)
def get_db() -> Iterator[Session]:
    with SessionLocal() as session:
        yield session                       # ⭐ the request runs here

# ⭐⭐ and the SERVICE owns the transaction (Day 132's argument):
def place_order(db: Session, user: User, sku: str, qty: int) -> Order:
    product = db.scalars(select(Product).where(Product.sku == sku).with_for_update()).one()
    if product.stock < qty:
        raise InsufficientStock(sku)         # ⭐ no commit happened; nothing to undo
    product.stock -= qty                     # ⭐⭐ tracked — no UPDATE written yet
    order = Order(sku=sku, qty=qty, total=product.price * qty, user_id=user.id)
    db.add(order)
    db.commit()                              # ⭐⭐ BOTH changes, in ONE transaction
    return order
```

```
⭐⭐ ONE SESSION PER REQUEST, ONE TRANSACTION PER UNIT OF WORK — AND THE PAYOFF
⭐   IS ATOMICITY YOU DID NOT HAVE TO WRITE: the stock decrement and the order
⭐   insert either both happen or neither does. ⭐ No compensating logic, no
⭐   half-completed order.
⭐   ⇒ ⭐⭐ WHICH IS ALSO WHY A SESSION MUST NOT BE SHARED ACROSS REQUESTS OR
⭐        THREADS: it holds a transaction and mutable identity state. ⭐ A global
⭐        session gives you cross-request contamination and errors that make no
⭐        sense (Day 132's per-request dependency cache is what prevents this).
⭐   ⇒ ⭐ `with_for_update()` takes a row lock so two concurrent orders cannot
⭐        both read `stock = 1` — ⭐⭐ Day 067's race, at the database. Without
⭐        it, you oversell.
⭐   ⇒ ⚠️ ⭐⭐ AND HOLDING A LOCK ACROSS AN HTTP CALL IS DAY 066'S RULE: never
⭐        call a payment gateway between `with_for_update()` and `commit()`.
```

```
⚠️ ⭐⭐ THE ROLLBACK RULE: AFTER AN EXCEPTION, THE SESSION IS UNUSABLE UNTIL YOU
⭐    ROLL BACK. ⭐ Any further statement raises `PendingRollbackError`.
⭐    ⇒ ⭐ the `with SessionLocal()` block rolls back on exit if there was no
⭐         commit, which is why the dependency shape above is safe by default.
⭐    ⇒ ⭐⭐ BUT IF YOU CATCH AN `IntegrityError` AND WANT TO CONTINUE — say, to
⭐         return a friendly 409 — YOU MUST `db.rollback()` FIRST, and then
⭐         everything before it is gone too. ⭐ Which is an argument for checking
⭐         first, or for a SAVEPOINT (`db.begin_nested()`).
```

# Part 4 — ⭐⭐ `expire_on_commit`, and the detached object

```
⚠️⚠️ ⭐⭐ THE DEFAULT THAT CATCHES EVERY FASTAPI USER ONCE:
⭐    `expire_on_commit=True` (the default) MARKS EVERY OBJECT STALE AFTER
⭐    COMMIT. ⭐ The next attribute access issues a fresh SELECT to reload it.
⭐    ⇒ ⭐⭐ SO A HANDLER THAT COMMITS AND THEN RETURNS THE OBJECT triggers a
⭐         reload during serialisation — ⭐ an extra query per response, and if
⭐         the session has already closed, ⭐⭐ `DetachedInstanceError`.
⭐    ⇒ ⭐ `sessionmaker(expire_on_commit=False)` is the usual fix in a web app:
⭐         the object keeps the values it had at commit time, which is exactly
⭐         what you want to serialise.
⭐    ⇒ ⚠️ ⭐ THE TRADE: those values are now a SNAPSHOT. If another transaction
⭐         changed the row, your object is stale — ⭐⭐ which is fine for a
⭐         response you are about to send and wrong for a long-lived object.
```

```
⭐⭐ THE FOUR OBJECT STATES, WHICH EXPLAIN EVERY "WHY IS THIS NONE" QUESTION:
⭐   TRANSIENT  ⭐ new, not in a session          ⇒ no id
⭐   PENDING    ⭐ added, not flushed             ⇒ no id yet
⭐   PERSISTENT ⭐⭐ in the session, in the database ⇒ tracked, has an id
⭐   ⭐⭐ DETACHED ⇒ ⭐⭐ the session is CLOSED. Loaded attributes still work;
⭐                  ⭐ ANY UNLOADED ONE RAISES `DetachedInstanceError`.
⭐   ⇒ ⭐⭐ DETACHED IS THE ONE THAT BITES: you return an ORM object from a
⭐        service, the session closes with the request, and something later —
⭐        a background task, a serialiser, a template — touches a lazy
⭐        relationship. ⭐ The error appears far from the cause.
⭐   ⇒ ⭐⭐ THE STRUCTURAL FIX (Days 090, 119): DO NOT LET ORM OBJECTS ESCAPE THE
⭐        REPOSITORY. Convert to a Pydantic model or a dataclass at the boundary,
⭐        and the whole class of error stops existing.
```

# Part 5 — ⭐ Core, bulk, and when to drop the ORM

```python
# ⭐ Core — no ORM objects, no identity map, no unit of work
rows = session.execute(
    select(Order.sku, func.sum(Order.qty).label("total"))
    .where(Order.created_at >= since)
    .group_by(Order.sku)
    .having(func.sum(Order.qty) > 10)                    # ⭐ Day 097's D-07
).all()                                                   # ⭐⭐ Row tuples, not entities
```

```
⭐⭐ USE CORE (OR RAW SQL) WHEN YOU DO NOT WANT OBJECTS:
⭐   · ⭐ reports and aggregates ⇒ ⭐⭐ hydrating 100,000 ORM objects to sum a
⭐        column is pure waste — the identity map and change tracking cost real
⭐        memory and time (Day 100A)
⭐   · ⭐ bulk inserts/updates ⇒ `session.execute(insert(Order), [{...}, ...])`
⭐        ⇒ ⭐⭐ one statement instead of N, and often 10-100× faster
⭐   · ⭐ a query the ORM makes awkward ⇒ ⭐⭐ `text()` IS FINE — with BOUND
⭐        PARAMETERS (Day 127), never an f-string
⭐   ⇒ ⭐⭐ THE ORM IS FOR THE TRANSACTIONAL PATH, WHERE ITS UNIT OF WORK AND
⭐        IDENTITY MAP EARN THEIR KEEP. ⭐ For analytics it is overhead, and
⭐        knowing when to drop to Core is most of using it well.
```

```
⭐ WHERE SQLALCHEMY LIVES (Day 090): THE REPOSITORY LAYER, AND NOWHERE ELSE.
⭐   ✘ ⭐⭐ a route handler running `select()`     ⇒ the HTTP layer knows your schema
⭐   ✘ ⭐ a service importing ORM models          ⇒ the domain cannot be tested
⭐        without a database, and cannot change storage
⭐   ✔ ⭐ `repositories/orders.py` takes a session and returns domain objects
⭐   ⇒ ⭐⭐ ENFORCE IT: ruff's banned-api on `sqlalchemy` outside `repositories/`
⭐        (Day 090). ⭐ It is one config line and it holds the line for years.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Expecting an id after `add()` | ⭐ It arrives at `flush()`. |
| ⭐⭐ **Confusion from autoflush** | ⭐⭐ A `SELECT` can raise from an earlier `INSERT`. The failing statement is not the wrong one. |
| Sharing a session across requests | ⭐⭐ It holds a transaction and identity state. One per request. |
| ⭐ Committing in the route rather than the service | ⭐ The transaction boundary belongs with the unit of work. |
| ⭐ Continuing after `IntegrityError` without rollback | ⭐⭐ `PendingRollbackError` on the next statement. |
| ⭐⭐ **Read-modify-write with no lock** | ⭐⭐ Two orders both read `stock = 1`. `with_for_update()`. |
| Holding a row lock across an HTTP call | ⭐ Day 066 — never hold a lock across I/O. |
| ⭐⭐ **`expire_on_commit=True` in a web app** | ⭐⭐ An extra query per response, or `DetachedInstanceError`. |
| ORM objects escaping the repository | ⭐⭐ Detached errors far from the cause. Convert at the boundary. |
| ⭐ `Float` for money | ⭐ `Numeric`. Wrong before your code runs. |
| Hydrating objects for an aggregate | ⭐⭐ Use Core. The identity map is pure cost here. |
| ⭐ `text(f"...")` | ⭐⭐ SQL injection (Day 127). Bound parameters. |
| SQLAlchemy in routes or services | ⭐ Repository layer only, enforced by the linter. |

## Interview questions

**Q: What is a SQLAlchemy Session?**
> A unit of work. It tracks the objects you've added or modified and writes them all at once, inside
> one transaction. `add` records intent and issues no SQL; `flush` sends the SQL but stays in the
> transaction, which is where generated ids appear and where integrity errors surface; `commit` flushes
> and commits. Most of SQLAlchemy's surprising behaviour is the session deciding to flush at a moment
> you didn't choose — autoflush runs before every query so your query sees your own pending changes,
> which means a `SELECT` can raise an `IntegrityError` caused by an `INSERT` three functions earlier.
> That's the most confusing error in the library, and the shape to remember is that the statement that
> raised isn't the statement that was wrong.

**Q: How do you manage the session in a web app?**
> One session per request, provided as a dependency with a `yield`, and the transaction boundary owned
> by the service rather than the route or the dependency. That gives you atomicity for free — the stock
> decrement and the order insert either both happen or neither does — with no compensating logic. The
> session must never be shared across requests or threads, because it holds a transaction and mutable
> identity state; a global session gives you cross-request contamination and errors that make no sense.

**Q: What's `expire_on_commit`, and why change it?**
> By default, committing marks every object stale, so the next attribute access issues a fresh SELECT.
> In a web app that means a handler which commits and then returns the object triggers a reload during
> serialisation — an extra query per response, or `DetachedInstanceError` if the session has already
> closed. So `expire_on_commit=False` is the usual setting. The trade is that the object is now a
> snapshot from commit time, which is exactly right for a response you're about to send and wrong for
> anything long-lived.

**Q: What causes `DetachedInstanceError`?**
> Touching an unloaded attribute on an object whose session has closed. It usually happens because an
> ORM object escaped the repository — a service returns it, the session closes with the request, and
> then a serialiser or a background task touches a lazy relationship. The error surfaces a long way
> from the cause. The structural fix is not to let ORM objects escape at all: convert to a Pydantic
> model or a dataclass at the repository boundary, and the whole class of error stops existing.

**Q: When would you drop to Core or raw SQL?**
> For anything where I don't want objects. Aggregates and reports, because hydrating a hundred
> thousand ORM instances to sum a column is pure waste — the identity map and change tracking cost
> real memory and time. Bulk inserts, where one statement replaces N and is often two orders of
> magnitude faster. And queries the ORM makes awkward, where `text()` with bound parameters is
> perfectly respectable. The ORM earns its keep on the transactional path where the unit of work and
> identity map matter; knowing when to leave it is most of using it well.

## 🎙️ Articulation drill

Record two minutes: **"Explain how SQLAlchemy's session works."**

⭐ **Lead with the concept, because the API follows from it:** **"the Session is a unit of work. It
tracks every object you've added or changed and writes them all at once inside one transaction. `add`
records intent with no SQL, `flush` sends the SQL but stays inside the transaction — that's where
generated ids appear — and `commit` makes it durable."**

⭐⭐ **Then the behaviour that explains most confusion:** *"and most surprising SQLAlchemy behaviour is
the session flushing at a moment you didn't choose. Autoflush runs before every query so your query
