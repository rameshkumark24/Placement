# Day 457 💰

**P-457** · 💰 **Cost engineering** — ⭐⭐ the p99 request is a bug, not a heavy user

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: you cannot optimise a cost you cannot attribute, so the work starts with a
> unit — cost per resolved ticket, per processed document, per active user per month — and ends at the
> point where cutting further means answering slightly worse, which is a product decision and not
> yours alone to make.**

---

# Part 1 — ⭐⭐ Unit economics before optimisation

```
⭐ ***THE WRONG QUESTION:*** ⭐ "how do we reduce the OpenAI
⭐   bill?"
⭐ ***THE RIGHT ONE:*** ⭐⭐ "WHAT DOES ONE UNIT OF VALUE COST,
⭐   AND WHAT IS IT WORTH?"

⭐   ⭐ cost per ***resolved support ticket*** — ⭐ compare
⭐     against £4–15 for a human one. ⭐⭐ IF YOURS IS £0.14, THE
⭐     CONVERSATION IS "SPEND MORE FOR BETTER RESOLUTION", NOT
⭐     "CUT COSTS".
⭐   ⭐ cost per ***processed document***
⭐   ⭐ cost per ***active user per month*** — ⭐⭐ COMPARE TO
⭐     SUBSCRIPTION REVENUE PER USER. ⭐ This is the number that
⭐     decides whether the feature is viable ***at all***, and it
⭐     is the number nobody computes before shipping.
⭐   ⭐ cost per ***agent run that succeeded***
⭐     ⭐⭐ — NOT PER RUN. ⭐ Failed runs cost full price and
⭐     deliver nothing, so folding them in is the honest figure.

⭐ ⭐⭐ AND THE OUTCOME THIS REFRAMING PRODUCES: ⭐ sometimes the
⭐   right answer is ***spend 3× more per request***, because a
⭐   deflected ticket is worth £8 and you are spending 14p.
⭐   ⭐⭐ AN ENGINEER WHO ONLY EVER OPTIMISES DOWNWARDS IS
⭐     OPTIMISING THE WRONG DIRECTION HALF THE TIME.
```

# Part 2 — Attribution, or you optimise the wrong thing

```
⭐ ***A SINGLE PROVIDER INVOICE TELLS YOU NOTHING ACTIONABLE.***
⭐   ⭐⭐ YOU NEED COST BY: ⭐ feature · tenant · user · model ·
⭐     ***pipeline stage***.
⭐   ⭐ You already emit it — Day 455's wide event carries
⭐     `feature`, `tenant_id`, `model` and `cost_usd`.
⭐     ⭐⭐ SO THIS IS A `GROUP BY`, NOT A PROJECT.

⭐ ***WHAT ATTRIBUTION REVEALS, RELIABLY:***
⭐   ⭐ one feature nobody uses is 40% of spend;
⭐   ⭐ ⭐⭐ THREE TENANTS ARE 60% OF COST AND TWO OF THEM ARE ON
⭐     THE FREE TIER;
⭐   ⭐ ***the eval suite and the guardrails*** are 20% of the
⭐     bill — ⭐⭐ NOBODY EVER BUDGETS THE OBSERVER;
⭐   ⭐ the reranker costs more than the generation;
⭐   ⭐ ⭐⭐ RETRIES AND REPAIRS ARE 8% — ⭐ money spent purely on
⭐     things that went wrong the first time (Day 424).

⭐ ***AND THE HIDDEN LINES PEOPLE FORGET ENTIRELY:***
⭐   ⭐ embeddings at ingest and on every reindex (Day 431);
⭐   ⭐ the eval suite in CI, on every PR;
⭐   ⭐ ⭐⭐ THE LLM-AS-JUDGE, WHICH READS THE ANSWER ***AND*** THE
⭐     CONTEXT (D426/448);
⭐   ⭐ guardrail calls on both sides of every request;
⭐   ⭐ agent steps, which are quadratic (Day 439);
⭐   ⭐ multi-agent overhead at 3–10× (Day 441);
⭐   ⭐ ⭐⭐ SHADOW/CANARY TRAFFIC AND THE 1% FALLBACK CANARY
⭐     (D456).
```

# Part 4 — The ladder, priced

```
⭐  ┌───────────────────────────────┬─────────┬──────────────┐
⭐  │ RUNG                          │ SAVING  │ QUALITY COST │
⭐  ├───────────────────────────────┼─────────┼──────────────┤
⭐  │ ⓪ ⭐⭐ DON'T CALL THE MODEL     │ ⭐⭐ 100% │ ⭐ none       │
⭐  │ (rules, cache, deterministic  │ of those│              │
⭐  │ path, a `WHERE` clause)       │ requests│              │
⭐  │ ① ⭐⭐ PROMPT CACHING — REORDER │ 40–60%  │ ⭐⭐ NONE      │
⭐  │ ② fewer/better chunks (k↓)    │ 20–40%  │ ⭐ often ***up***│
⭐  │ ③ shorter output; terse       │ 10–30%  │ ⭐ small      │
⭐  │ schema (output is 4–5× input) │         │              │
⭐  │ ④ model cascade (D421)        │ 50–80%  │ ⭐ measurable │
⭐  │ ⑤ ⭐⭐ BATCH API FOR OFFLINE    │ ⭐⭐ 50%  │ ⭐ none, but  │
⭐  │ WORK (24h SLA)                │         │ 24h latency  │
⭐  │ ⑥ fine-tune a small model     │ ~90%    │ ⭐ measurable │
⭐  │ (D451)                        │         │ + ownership  │
⭐  │ ⑦ self-host (D452)            │ varies  │ ⭐⭐ + AN ON-  │
⭐  │                               │         │ CALL ROTATION│
⭐  └───────────────────────────────┴─────────┴──────────────┘

⭐⭐ NOTE RUNG ⓪, WHICH IS ALWAYS AVAILABLE AND ALWAYS SKIPPED.
⭐   ⭐ "Which of these requests did not need a model at all?"
⭐   ⭐ Classification with 12 known inputs → ⭐ a dict.
⭐   ⭐ "What's my balance?" → ⭐⭐ A DATABASE QUERY AND A
⭐     TEMPLATE.
⭐   ⭐ ⭐⭐ AN LLM IS THE MOST EXPENSIVE WAY TO DO ANYTHING A
⭐     REGEX CAN DO, AND SOME FRACTION OF YOUR TRAFFIC IS
⭐     EXACTLY THAT.

⭐⭐ AND NOTE RUNG ② GOING THE OTHER WAY: ⭐ cutting k from 12 to
⭐   6 usually ***improves*** quality — lost-in-the-middle
⭐   (Day 415) plus fewer distractors — ⭐⭐ WHICH MAKES IT THE
⭐   ONLY ROW WHERE CHEAPER AND BETTER POINT THE SAME WAY.
⭐   ⭐ Do ⓪, ①, ② before anything else, always.
```

# Part 5 — Cost as a gate, and as a product decision

```
⭐ ***COST IS A ***GATE***, NOT A REPORT*** (Day 425):
⭐   ⭐ ⭐⭐ CI FAILS IF MEAN COST PER EVAL CASE RISES > 15%.
⭐     ⭐ A prompt that adds 400 tokens is a ***bill***, and it
⭐       should be as visible in review as a slow query.
⭐   ⭐ per-request cap → ⭐ refuse or downgrade before spending;
⭐   ⭐ ⭐⭐ PER-TENANT DAILY BUDGET → ⭐ the abuse control ***and***
⭐     the honest-mistake control. ⭐⭐ WITHOUT IT, ONE CUSTOMER
⭐     SCRIPTING A LOOP IS AN UNCAPPED LIABILITY (D421).
⭐   ⭐ per-user rate limits — ⭐ a counter, not a model (D448).

⭐ ⭐⭐ AND THE CONVERSATION THAT IS NOT AN ENGINEERING
⭐   DECISION:
⭐   ⭐ "We can cut cost 80% by switching to the small model.
⭐     ⭐⭐ ACCURACY GOES FROM 91% TO 86% ON OUR EVAL. ⭐ That is
⭐     five extra wrong answers per hundred. ⭐⭐ AT OUR VOLUME
⭐     THAT IS 400 WRONG ANSWERS A DAY AND £9,000 A MONTH
⭐     SAVED."
⭐   ⭐ ⭐⭐ PUT BOTH NUMBERS IN ONE SENTENCE AND LET THE BUSINESS
⭐     CHOOSE. ⭐ That sentence is only possible because you have
⭐     an eval (Day 425) ***and*** attribution (Part 2).
⭐   ⭐ ⭐⭐ AN ENGINEER WHO SILENTLY SWAPS THE MODEL TO SAVE
⭐     MONEY HAS MADE A PRODUCT DECISION WITHOUT TELLING ANYONE
⭐     — ⭐ and one who refuses to consider it has made the
⭐     opposite one.

⭐ ***FORECASTING, SO THE NUMBER IS NOT A SURPRISE:***
⭐   ⭐ cost per DAU × projected DAU × ⭐⭐ A GROWTH FACTOR FOR
⭐     USAGE PER USER ⭐ — ⭐⭐ WHICH RISES AS THE FEATURE GETS
⭐     GOOD. ⭐ Success increases unit usage, so the bill grows
⭐     faster than the user count. ⭐ Say that out loud in
⭐     planning.
```

# 💬 Interview

**1. "How would you reduce our LLM costs?"**

⭐ I'd start by refusing the framing for a minute. ⭐⭐ The first question is what one unit of value costs
and what it's worth — cost per resolved ticket against four to fifteen pounds for a human one, or cost
per active user against revenue per user. ⭐ If a deflected ticket is worth eight pounds and we're
spending fourteen pence, the right move might be to spend three times more for better resolution.
⭐⭐ An engineer who only ever optimises downwards is pointing the wrong way half the time. ⭐ Then I'd
attribute — by feature, tenant, model and pipeline stage — because a single invoice tells you nothing
actionable, and it's a `GROUP BY` on data I already emit.

**2. "What does attribution usually reveal?"**

⭐ Something nobody predicted. ⭐⭐ Commonly: one feature nobody uses is forty percent of spend; three
tenants are sixty percent of cost and two are on the free tier; and the eval suite plus the guardrails
are twenty percent of the bill, because nobody ever budgets the observer. ⭐ Also the reranker costing
more than the generation, and retries and repairs at eight percent — money spent purely on things that
went wrong the first time. ⭐⭐ The forgotten lines are embeddings at ingest and every reindex, evals in
CI on every PR, the LLM judge which reads the answer *and* the context, guardrails on both sides, and
canary traffic.

**3. "Your p99 cost is $2.40 against a p50 of a penny. What's happening?"**

⭐ I'd go and read twenty of those requests, and I'd expect them to be bugs rather than power users.
⭐⭐ In practice it's an agent doom loop that ran ten steps, a two-hundred-page PDF pasted into a chat
box, a retrieval that returned forty chunks because a token budget wasn't enforced, a three-hundred-turn
conversation with no trimming, the repair loop running four times, or one tenant's document being
re-embedded nightly because its content hash keeps changing. ⭐ Cost is long-tailed because input length
is user-controlled, so the top one percent is routinely thirty to fifty percent of the bill. ⭐⭐ So the
first cost work is bug fixing, not optimisation — usually the cheapest thirty percent you'll ever save.
⭐ I alert on per-request cost above a threshold and treat each one as an incident until it's explained.

**4. "What's the optimisation order?"**

⭐ Rung zero first: which of these requests didn't need a model at all? ⭐⭐ Classification over twelve
known inputs is a dict; "what's my balance" is a database query and a template. ⭐ An LLM is the most
expensive possible way to do anything a regex can do, and some fraction of traffic is exactly that.
⭐ Then prompt caching, which is forty to sixty percent for reordering the prompt and costs zero quality.
⭐⭐ Then fewer, better chunks — and that one is special, because cutting k from twelve to six usually
*improves* quality thanks to lost-in-the-middle and fewer distractors. ⭐ It's the only row where
cheaper and better point the same way. ⭐ After that: shorter outputs since output is four to five times
the input price, a model cascade, the batch API at fifty percent off for anything offline, fine-tuning,
and self-hosting last.

**5. "When does this stop being an engineering decision?"**

⭐ The moment the next saving costs quality. ⭐⭐ My job then is to produce one sentence with both numbers
in it: "we can cut cost eighty percent by switching models; accuracy goes from 91 to 86 percent on our
eval, which is five extra wrong answers per hundred — four hundred a day at our volume — and saves nine
thousand a month." ⭐ Then the business chooses. ⭐⭐ An engineer who silently swaps the model to save
money has made a product decision without telling anyone, and one who refuses to consider it has made
the opposite one. ⭐ That sentence is only possible because there's an eval and there's attribution.

**6. "How do you stop cost regressing?"**

⭐ It's a gate, not a report. ⭐⭐ CI fails if mean cost per eval case rises more than fifteen percent, so
a prompt that adds four hundred tokens is as visible in review as a slow query. ⭐ Then a per-request
cap that downgrades or refuses before spending, a per-tenant daily budget — which is both the abuse
control and the honest-mistake control — and per-user rate limits, which are a counter rather than a
model. ⭐⭐ Without a tenant budget, one customer scripting a loop is an uncapped liability, and that's
the specific thing that makes this cost model different from every other service you've run.

**7. "How do you forecast it?"**

⭐ Cost per daily active user times projected users, times a growth factor for usage *per* user — ⭐⭐ and
that last factor is the one people omit. ⭐ As the feature gets good, people use it more, so the bill
grows faster than the user count. ⭐ Success is a cost event. ⭐⭐ I'd say that explicitly in planning,
because the alternative is discovering it in month four when the finance conversation is already
adversarial.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "our LLM bill is too high. Fix it."**

Start by reframing, briefly and without being difficult. **My first question isn't how to cut the bill,
it's what one unit of value costs and what it's worth. Cost per resolved ticket against four to fifteen
pounds for a human one. Cost per active user against revenue per user. Because if a deflected ticket is
worth eight pounds and we're spending fourteen pence, the right answer might be to spend three times
more for better resolution. Optimising downwards by reflex is wrong about half the time.**

Then attribution. **Then I'd break the bill down by feature, tenant, model and pipeline stage — which is
a group-by on data we already emit, not a project. It reliably surfaces something nobody predicted: a
feature nobody uses at forty percent of spend, three tenants at sixty percent with two on the free tier,
and the eval suite plus guardrails at twenty percent, because nobody budgets the observer.**

Then the distribution, which is where the money actually is. **Cost is long-tailed because input length
is user-controlled — p50 a penny, p99 two forty, and the top one percent is thirty to fifty percent of
the bill. So I read twenty p99 requests by hand, and they're almost never valuable power users. They're

chunks because nobody enforced the token budget, a repair loop running four times. The first cost work
is bug fixing, and it's usually the cheapest thirty percent you'll ever save.**

Close on the ladder and the handoff. **Then the ladder, in order: which requests didn't need a model at
all — classification over twelve known inputs is a dict, and an LLM is the most expensive way to do
