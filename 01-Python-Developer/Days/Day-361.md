# Day 361 🔬

**P-361** · 🔬 **Container internals** — namespaces, cgroups, and ⭐⭐ the Python process that gets OOMKilled

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the two production surprises that cost teams the most days are that PID 1
> does not behave like an ordinary process, and that your language runtime reads the *host's* CPU and
> memory rather than the container's limits — and both are consequences of the same fact, which is
> that a container is a restricted view rather than a machine.**

# Part 1 — ⭐⭐ Namespaces: what the process can see

```
⭐⭐ SEVEN NAMESPACES. ⭐ Four matter to you daily:

⭐⭐ ① ***PID*** — the process gets its own process tree.
⭐   ⭐ ⭐⭐ YOUR PROCESS IS PID 1 INSIDE AND SOMETHING ELSE
⭐     OUTSIDE. ⭐ That single fact causes Part 3.
⭐   ⭐ It cannot see or signal host processes. ⭐ The host can
⭐     see and signal it.

⭐⭐ ② ***MOUNT*** — its own filesystem tree.
⭐   ⭐ The image's layers are mounted as `/`; ⭐ volumes are
⭐     mounted in. ⭐⭐ THIS IS WHY `/etc/hosts` INSIDE DIFFERS
⭐     FROM THE HOST'S, AND WHY A BIND MOUNT CAN SHADOW A
⭐     DIRECTORY YOUR IMAGE CAREFULLY POPULATED — ⭐ mounting a
⭐     volume over `/app/static` hides the files you built.

⭐⭐ ③ ***NETWORK*** — its own interfaces, routes, ports.
⭐   ⭐ ⭐⭐ `localhost` INSIDE THE CONTAINER IS ***NOT*** THE
⭐     HOST'S `localhost`. ⭐ This is the number-one beginner
⭐     confusion: your app cannot reach a database running on
⭐     the host at `127.0.0.1`, ⭐ and `-p 8000:8000` is a NAT
⭐     rule, not "the app is on the host".
⭐   ⭐ ⭐⭐ AND IN A KUBERNETES POD, ***ALL CONTAINERS SHARE ONE
⭐     NETWORK NAMESPACE***, so a sidecar ***can*** reach your
⭐     app on `localhost` — which is exactly how service meshes
⭐     intercept traffic (Day 341).

⭐⭐ ④ ***USER*** — UID mapping between container and host.
⭐   ⭐ ⭐⭐ WITHOUT USER-NAMESPACE REMAPPING, ROOT INSIDE THE
⭐     CONTAINER IS ***UID 0 ON THE HOST***. ⭐ It is
⭐     constrained by capabilities and seccomp rather than by
⭐     being a different user.
⭐   ⇒ ⭐⭐ WHICH IS THE REAL REASON FOR `USER app`: NOT TIDINESS,
⭐     BUT THAT A CONTAINER ESCAPE FROM A ROOT PROCESS LANDS AS
⭐     ROOT ON THE HOST.
⭐   ⭐ ⭐⭐ AND THE BIND-MOUNT CONSEQUENCE: FILES A CONTAINER
⭐     WRITES TO A MOUNTED HOST DIRECTORY ARE OWNED BY THE
⭐     CONTAINER'S UID — ⭐ which is why `docker compose up`
⭐     leaves root-owned files in your repo that you then cannot
⭐     delete without `sudo`.

⭐⭐ ⑤–⑦ UTS (hostname), IPC (shared memory), cgroup. ⭐ Know
⭐   they exist. ⭐⭐ IPC MATTERS ONCE: `/dev/shm` DEFAULTS TO
⭐   64 MB, AND SOME LIBRARIES (torch DataLoader, some
⭐   multiprocessing patterns, Chrome) FAIL MYSTERIOUSLY
⭐   BECAUSE OF IT.
```

# Part 2 — ⭐⭐ Cgroups: what the process can use

```
⭐⭐ CGROUPS LIMIT AND ACCOUNT FOR RESOURCES. ⭐ Three matter:

⭐⭐ ① ***MEMORY*** — `--memory=512m`
⭐   ⭐ Exceed it ⇒ ⭐⭐ THE KERNEL OOM KILLER TERMINATES A
⭐     PROCESS IN THE CGROUP. ⭐ Usually yours. ⭐ Usually PID 1.
⭐     ⭐⭐ USUALLY WITH ***NO PYTHON TRACEBACK AT ALL*** — the
⭐     process receives SIGKILL, which cannot be caught.
⭐   ⇒ ⭐⭐ THE SYMPTOM YOU WILL ACTUALLY SEE: EXIT CODE 137
⭐     (128 + 9), AND AN EMPTY LOG. ⭐ Memorise 137; it is the
⭐     single most useful number in container operations.
⭐   ⭐ ⭐⭐ AND THE PART PEOPLE MISS: ***PAGE CACHE COUNTS
⭐     TOWARD THE LIMIT.*** ⭐ A process that reads a large file
⭐     can be OOMKilled without its own RSS ever being high —
⭐     ⭐ which makes the memory graph look innocent.

⭐⭐ ② ***CPU*** — two different mechanisms, constantly confused:
⭐   ⭐ ***SHARES / WEIGHT*** — relative priority ***under
⭐     contention only***. ⭐ Unlimited when the host is idle.
⭐   ⭐ ⭐⭐ ***QUOTA*** (`--cpus=1.5`, or Kubernetes CPU limits)
⭐     — a hard cap: 150 ms of CPU per 100 ms period.
⭐   ⇒ ⭐⭐ AND HERE IS THE TRAP: EXCEEDING QUOTA DOES NOT KILL
⭐     YOU, IT ***THROTTLES*** YOU. ⭐ The process is frozen
⭐     until the next period.
⭐   ⇒ ⭐⭐ WHICH PRESENTS AS ***LATENCY SPIKES WITH NO ERRORS
⭐     AND NO OBVIOUS CAUSE***: p50 fine, p99 terrible, CPU
⭐     graph showing 60%. ⭐ The metric to look at is
⭐     `container_cpu_cfs_throttled_seconds_total`, and
⭐     ⭐⭐ ALMOST NOBODY LOOKS AT IT.

⭐⭐ ③ ***PIDS*** — `--pids-limit`. ⭐ Prevents a fork bomb, and
⭐   ⭐⭐ CATCHES RUNAWAY `multiprocessing` OR THREAD CREATION
⭐   BEFORE IT TAKES THE HOST DOWN.
```

# Part 3 — ⭐⭐ PID 1, and the signal that never arrives

```
⭐⭐ PID 1 IS SPECIAL IN LINUX — TWO WAYS, AND BOTH HURT:
⭐   ① ⭐⭐ ***DEFAULT SIGNAL HANDLERS DO NOT APPLY TO PID 1.***
⭐      ⭐ An ordinary process with no `SIGTERM` handler dies.
⭐      ⭐⭐ PID 1 WITH NO HANDLER ***IGNORES IT ENTIRELY.***
⭐   ② ⭐ PID 1 must reap orphaned children, or they become
⭐      zombies forever.

⭐⭐ SO THE FAILURE, IN THE ORDER YOU MEET IT:
⭐   ⭐ You write `CMD python main.py`. ⭐ Python installs its
⭐     own `SIGTERM` handler? ⭐⭐ NO — CPython's default for
⭐     `SIGTERM` is the kernel default, and as PID 1 that means
⭐     ***ignore***.
⭐   ⇒ ⭐⭐ `docker stop` SENDS SIGTERM, WAITS 10 SECONDS,
⭐     THEN SIGKILLS. ⭐ Every deploy takes ten seconds per
⭐     container and kills in-flight requests.
⭐   ⇒ ⭐ FIX ①: install a handler explicitly —
⭐     `signal.signal(signal.SIGTERM, handler)` — ⭐⭐ WHICH
⭐     WORKS, AND IS WHAT UVICORN AND GUNICORN ALREADY DO.

⭐⭐ AND THE ***WORSE*** FAILURE, FROM DAY 282:
⭐   ⭐ `CMD python main.py` in ***shell form*** becomes
⭐     `/bin/sh -c "python main.py"`.
⭐   ⇒ ⭐⭐ NOW `sh` IS PID 1, IT DOES NOT FORWARD SIGNALS, AND
⭐     YOUR APP RECEIVES ***NOTHING*** NO MATTER WHAT HANDLERS
⭐     IT INSTALLED.
⭐   ⇒ ⭐⭐ USE EXEC FORM: `CMD ["python", "main.py"]`. ⭐ Or
⭐     `exec python main.py` at the end of an entrypoint script,
⭐     ⭐ which replaces the shell rather than spawning under it.

⭐⭐ AND WHEN YOU GENUINELY NEED AN INIT:
⭐   ⭐ ⭐⭐ IF YOUR CONTAINER SPAWNS CHILDREN (gunicorn workers,
⭐     `multiprocessing`, a subprocess call), USE `--init` OR
⭐     `tini`. ⭐ It reaps zombies and forwards signals.
⭐   ⇒ ⭐ Gunicorn is itself a competent PID 1 for its own
⭐     workers; ⭐⭐ AN AD-HOC `subprocess.Popen` IS NOT, AND
⭐     THAT IS WHERE ZOMBIES ACCUMULATE UNTIL THE PID LIMIT IS
⭐     HIT.
```

# Part 4 — ⭐⭐ The Python-specific traps

```
⭐⭐ ① ***`os.cpu_count()` REPORTS THE ***HOST'S*** CPUs.***
⭐   ⭐ A 64-core host, a container limited to 1 CPU ⇒ ⭐⭐ IT
⭐     STILL SAYS 64.
⭐   ⇒ ⭐ Every library that sizes a pool from it gets it wrong:
⭐     ⭐⭐ `ProcessPoolExecutor()`, gunicorn's `workers =
⭐     2*cpu+1` RECIPE, `numpy`/OpenBLAS THREAD POOLS, `polars`,
⭐     `torch`.
⭐   ⇒ ⭐⭐ RESULT: 129 GUNICORN WORKERS IN A ONE-CPU CONTAINER.
⭐     ⭐ Each is a full Python process with its own memory —
⭐     ⭐⭐ SO YOU OOM ***AND*** THROTTLE, AND THE LOGS SHOW
⭐     NEITHER CAUSE.
⭐   ⇒ FIXES: ⭐⭐ `len(os.sched_getaffinity(0))` IS BETTER BUT
⭐     STILL DOES NOT SEE A ***QUOTA***; ⭐ read
⭐     `/sys/fs/cgroup/cpu.max` directly; ⭐⭐ OR SIMPLY SET THE
⭐     WORKER COUNT EXPLICITLY FROM AN ENV VAR AND STOP
⭐     GUESSING. ⭐ The explicit answer is the correct one.
⭐   ⇒ ⭐ Also set `OMP_NUM_THREADS` / `OPENBLAS_NUM_THREADS=1`
⭐     in scientific images, ⭐⭐ OR EVERY WORKER SPAWNS 64
⭐     THREADS AND THEY FIGHT EACH OTHER FOR ONE CORE.

⭐⭐ ② ***MEMORY IS NOT VISIBLE EITHER.*** ⭐ `psutil.virtual_
⭐   memory().total` reports the host's RAM. ⭐⭐ ANY CACHE SIZED
⭐   AS "10% OF AVAILABLE MEMORY" IS SIZED FROM THE WRONG
⭐   NUMBER — read `/sys/fs/cgroup/memory.max`.

⭐⭐ ③ ***PYTHON DOES NOT RETURN MEMORY TO THE OS EAGERLY.***
⭐   ⭐ Freed objects go back to CPython's allocator arenas,
⭐     ⭐ and arenas are only released when entirely empty.
⭐   ⇒ ⭐⭐ SO RSS RISES TO A HIGH-WATER MARK AND STAYS THERE.
⭐     ⭐ A one-off large request permanently raises your
⭐     footprint, ⭐⭐ AND WITH A TIGHT CGROUP LIMIT THAT MEANS A
⭐     RARE ENDPOINT CAUSES AN OOMKILL ***MINUTES LATER*** ON AN
⭐     UNRELATED REQUEST.
⭐   ⇒ ⭐ MITIGATIONS: ⭐⭐ `--max-requests` WITH
⭐     `--max-requests-jitter` IN GUNICORN — recycle workers
⭐     periodically. ⭐ It is a crude fix and it is the standard
⭐     one, ⭐ and the jitter matters or all workers restart
⭐     together.

⭐⭐ ④ ***`multiprocessing` NEEDS `/dev/shm`*** and a sane start
⭐   method. ⭐⭐ THE 64 MB DEFAULT `/dev/shm` BREAKS LARGE
⭐   SHARED ARRAYS; ⭐ `--shm-size=1g` fixes it.

⭐⭐ ⑤ ***`PYTHONUNBUFFERED=1`*** — ⭐⭐ WITHOUT IT, STDOUT IS
⭐   BLOCK-BUFFERED WHEN NOT A TTY, SO YOUR LOGS APPEAR IN 4 KB
⭐   CHUNKS OR ***NOT AT ALL BEFORE A CRASH.*** ⭐ One env var,
⭐   and it is the difference between debugging and guessing.
```

# Part 5 — ⭐ Capabilities, seccomp, and hardening that is cheap

```
⭐⭐ A CONTAINER'S ROOT IS NOT THE HOST'S FULL ROOT: ⭐ Docker
⭐   drops most capabilities by default and applies a seccomp
⭐   profile blocking ~44 syscalls.
⭐   ⇒ ⭐ Which is why `mount`, `reboot` and loading kernel
⭐     modules fail even as root inside.

⭐⭐ THE HARDENING THAT COSTS NOTHING AND IS ALMOST NEVER DONE:
⭐   ⭐ `--user 10001:10001` — ⭐⭐ NUMERIC, NOT A NAME, so
⭐     Kubernetes `runAsNonRoot` can verify it (Day 282).
⭐   ⭐ `--read-only` + `--tmpfs /tmp` — ⭐⭐ AN ATTACKER WHO
⭐     GETS EXECUTION CANNOT WRITE A PAYLOAD ANYWHERE.
⭐   ⭐ `--cap-drop=ALL` and add back only what you need
⭐     (⭐ almost always: nothing).
⭐   ⭐ `--security-opt=no-new-privileges` ⇒ ⭐⭐ SETUID BINARIES
⭐     CANNOT ESCALATE.
⭐   ⭐ ⭐⭐ NEVER `--privileged`. ⭐ It disables essentially all
⭐     of the above and is equivalent to root on the host.
⭐   ⭐ ⭐⭐ AND NEVER MOUNT `/var/run/docker.sock` INTO A
⭐     CONTAINER YOU DO NOT FULLY TRUST — ⭐ it is a full
⭐     root-equivalent API to the host, and "the CI container
⭐     needs to build images" is how it usually gets in.

⭐⭐ ⇒ THE POINT: ⭐⭐ THESE ARE FIVE FLAGS. ⭐ They turn "an
⭐   RCE in your app is an RCE on the node" into "an RCE in your
⭐   app is stuck in a read-only filesystem as an unprivileged
⭐   user with no capabilities."
```

# Part 6 — ⭐⭐ Debugging a container that is misbehaving

```
⭐⭐ THE SEQUENCE, IN ORDER:
⭐   ① ⭐⭐ `docker inspect <id> --format '{{.State.ExitCode}}
⭐      {{.State.OOMKilled}}'`
⭐      ⇒ ⭐⭐ EXIT 137 + OOMKilled=true ⇒ MEMORY LIMIT. ⭐ Stop
⭐        looking at your code.
⭐      ⇒ ⭐ Exit 137 + OOMKilled=false ⇒ SIGKILL from outside —
⭐        usually the orchestrator after a failed graceful stop.
⭐      ⇒ ⭐ Exit 143 = SIGTERM, handled. ⭐ That is a clean stop.
⭐   ② ⭐ `docker stats` — live CPU, memory, I/O.
⭐   ③ ⭐⭐ CHECK THROTTLING: `cat /sys/fs/cgroup/cpu.stat` inside
⭐      ⇒ `nr_throttled` and `throttled_usec`. ⭐⭐ NON-ZERO AND
⭐      GROWING EXPLAINS LATENCY THAT NOTHING ELSE EXPLAINS.
⭐   ④ ⭐ `docker exec -it <id> sh` — ⭐⭐ AND IF THE IMAGE IS
⭐      DISTROLESS THERE IS NO SHELL, WHICH IS THE POINT. ⭐ Use
⭐      `docker debug`, or an ephemeral debug container sharing
⭐      the namespaces (`kubectl debug` does exactly this).
⭐   ⑤ ⭐ `docker logs --tail 200 -f` — ⭐⭐ AND IF IT IS EMPTY,
⭐      SUSPECT BUFFERING BEFORE YOU SUSPECT THE APP.

⭐⭐ AND THE ONE THAT SAVES HOURS:
⭐   ***`docker run --rm -it --entrypoint sh <image>`***
⭐   ⇒ ⭐⭐ START THE ***IMAGE*** WITHOUT STARTING THE ***APP***.
⭐     ⭐ Then look: is the file there? is it executable? what
⭐     user am I? what does `env` say? ⭐⭐ MOST "IT CRASHES
⭐     IMMEDIATELY" BUGS ARE VISIBLE IN THIRTY SECONDS THIS WAY.
```

# Part 7 — ⭐ Sizing limits honestly

```
⭐⭐ THE PROCESS:
⭐   ① ⭐ Run under realistic load with ***no*** limits.
⭐   ② ⭐ Measure RSS at p99 and peak; ⭐⭐ INCLUDING DURING YOUR
⭐      WORST ENDPOINT AND DURING STARTUP, WHICH IS OFTEN THE
⭐      PEAK.
⭐   ③ ⭐ Set the memory limit at ~1.5–2× the observed peak.
⭐   ④ ⭐ Set CPU ***requests*** from observed average.
⭐   ⑤ ⭐⭐ AND THE CONTROVERSIAL ONE, WHICH IS WORTH SAYING
⭐      BECAUSE IT IS A REAL DEBATE: ***CONSIDER NOT SETTING A
⭐      CPU ***LIMIT*** AT ALL.***
⭐      ⭐ Requests guarantee a floor; limits add throttling.
⭐      ⭐⭐ FOR LATENCY-SENSITIVE SERVICES, THROTTLING OFTEN
⭐        HURTS MORE THAN OCCASIONAL BURSTING HELPS ANYONE ELSE.
⭐      ⭐ Memory limits, by contrast, ***are*** needed —
⭐        ⭐⭐ BECAUSE MEMORY IS NOT COMPRESSIBLE: EXCEEDING IT
⭐        KILLS SOMETHING, AND WITHOUT A LIMIT IT MIGHT NOT BE
⭐        YOU.

⭐⭐ AND THE ARITHMETIC FOR A PYTHON WEB SERVICE:
⭐   ⭐ Base interpreter + imports: ⭐ ~60–120 MB (⭐⭐ MORE WITH
⭐     numpy/pandas — 300 MB+ IS NORMAL).
⭐   ⭐ Per gunicorn worker: ⭐ roughly that again, ⭐ minus
⭐     copy-on-write sharing that ⭐⭐ ERODES OVER TIME BECAUSE
⭐     CPYTHON'S REFCOUNTS TOUCH OBJECT HEADERS AND DIRTY THE
⭐     SHARED PAGES.
⭐   ⇒ ⭐⭐ SO "PREFORK SHARES MEMORY" IS ONLY BRIEFLY TRUE, AND
⭐     BUDGETING AS IF IT WERE PERMANENT IS HOW YOU GET
⭐     OOMKILLED IN HOUR THREE.
⭐   ⇒ ⭐ 4 workers ⇒ budget ~600–800 MB for a plain API.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Shell-form `CMD` | `sh` becomes PID 1, doesn't forward signals, and your app never sees SIGTERM |
| ⭐⭐ Assuming PID 1 dies on SIGTERM | PID 1 ignores signals it has no handler for. Every deploy then takes the full grace period |
| ⭐⭐ Sizing pools from `os.cpu_count()` | It reports the host's CPUs. 129 gunicorn workers in a one-CPU container |
| ⭐ Sizing caches from `psutil.virtual_memory()` | Same bug for memory. Read `/sys/fs/cgroup/memory.max` |
| ⭐⭐ Ignoring CPU throttling | Latency spikes with no errors and a 60% CPU graph. Check `nr_throttled` |
| ⭐⭐ Expecting a traceback on OOM | SIGKILL can't be caught. Exit 137 and an empty log is the whole signal |
| ⭐ Forgetting page cache counts toward the memory limit | You're OOMKilled while your own RSS looks fine |
| ⭐ No `PYTHONUNBUFFERED` | Logs appear in 4 KB chunks, or not at all before a crash |
| ⭐⭐ Spawning subprocesses without an init | Zombies accumulate until you hit the PID limit |
| ⭐ Assuming prefork memory sharing persists | Refcounts dirty shared pages; the saving erodes within hours |
| ⭐⭐ `--privileged` or mounting the Docker socket | Root-equivalent access to the host. "CI needs to build images" is how it gets in |
| ⭐ Running as root because it's easier | An escape from a root process lands as root on the host |
| ⭐ A CPU *limit* on a latency-sensitive service | Throttling often hurts more than bursting helps. Requests guarantee the floor |

## Interview questions

**1. "Your container gets exit code 137. What happened?"**
> ⭐⭐ 128 + 9, so SIGKILL. ⭐ First check `OOMKilled` in `docker inspect`: **true means the cgroup memory
> limit was hit and the kernel killed it — there is no traceback, because SIGKILL can't be caught.**
> ⭐ False means something outside killed it, usually the orchestrator after a graceful stop timed out.
> ⭐ And I'd remember that **page cache counts toward the limit**, so a process reading large files can
> be killed while its own RSS looks innocent.

**2. "Why does my app ignore `docker stop`?"**
> ⭐ Two possibilities, both about PID 1. ⭐⭐ **PID 1 ignores signals it has no handler for** — that's a
> kernel rule, not a Python one — so a process with no SIGTERM handler just sits there for the grace
> period. ⭐⭐ And worse: **shell-form `CMD` makes `/bin/sh` PID 1, and it doesn't forward signals**, so
> your app never sees it regardless of what handlers it installed. ⭐ Exec form, or `exec` at the end of
> an entrypoint script, and `--init` if you spawn children.

**3. "What's the Python-specific container trap?"**
> ⭐⭐ **The runtime reads the host, not the cgroup.** `os.cpu_count()` on a 64-core host reports 64 even
> in a one-CPU container, so the gunicorn `2×cpu+1` recipe gives you a hundred and twenty-nine full
> Python processes — ⭐⭐ **you OOM and throttle simultaneously, and neither cause appears in the logs.**
> ⭐ Same for memory-derived cache sizes. ⭐ The fix isn't a cleverer detection call; it's setting the
> worker count explicitly from an env var and stopping guessing. ⭐ Plus `OMP_NUM_THREADS=1`, or every
> worker spawns 64 BLAS threads fighting over one core.

**4. "Latency spikes, no errors, CPU at 60%. Where do you look?"**
> ⭐⭐ **CFS throttling.** A CPU *limit* is a quota per 100 ms period, and exceeding it doesn't kill you,
> it freezes you until the next period — so p50 looks fine and p99 is terrible while the average CPU
> graph looks healthy. ⭐ `nr_throttled` and `throttled_usec` in `cpu.stat`, or
> `container_cpu_cfs_throttled_seconds_total` in Prometheus. ⭐ Almost nobody has that on a dashboard.

**5. "Why does memory only go up?"**
> ⭐ CPython returns freed objects to its own allocator arenas and only releases an arena when it's
> entirely empty, so **RSS rises to a high-water mark and stays there.** ⭐⭐ With a tight cgroup limit
> that means **a rare expensive request can cause an OOMKill minutes later on an unrelated one.**
> ⭐ The standard mitigation is crude and correct: recycle workers with `--max-requests` plus jitter, so
> they don't all restart together.

**6. "How would you harden a container in five minutes?"**
> ⭐ Five flags: a **numeric** non-root user so `runAsNonRoot` can verify it; `--read-only` with a tmpfs
> for `/tmp`; `--cap-drop=ALL`; `no-new-privileges`; and no `--privileged` and no Docker socket mount
> ever. ⭐⭐ Together those turn **"an RCE in the app is an RCE on the node" into "an RCE stuck in a
> read-only filesystem as an unprivileged user with no capabilities."**

## 🎙️ Articulation drill

**Two minutes.** Frame the two facts that cause most container incidents: **PID 1 doesn't behave like an
ordinary process, and your runtime reads the host rather than the cgroup** — both consequences of a
container being a restricted view rather than a machine. On PID 1: **it ignores signals it has no
handler for**, so a process without a SIGTERM handler waits out the full grace period on every deploy —
and worse, **shell-form `CMD` puts `/bin/sh` at PID 1, and it doesn't forward signals at all**, so your
handlers are irrelevant. On the runtime: **`os.cpu_count()` on a sixty-four-core host reports
sixty-four inside a one-CPU container**, so the standard gunicorn worker formula gives you a hundred
and twenty-nine Python processes and you OOM and throttle at once, with neither cause in the logs — and
the fix is an explicit env var, not a cleverer detection call. Then the two symptoms worth memorising:
**exit 137 with OOMKilled means the memory cgroup, and there is no traceback because SIGKILL can't be
caught**; and **latency spikes with no errors and a healthy CPU graph means CFS throttling**, which
almost nobody has on a dashboard. Close on the five hardening flags — numeric non-root user, read-only
root, drop all capabilities, no-new-privileges, and never the Docker socket — which together turn an
RCE in your app into an RCE stuck in a read-only filesystem with no capabilities.
