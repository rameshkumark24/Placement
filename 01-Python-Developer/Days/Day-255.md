# Part 1 — ⭐ Mapping the domain without dissolving it

```
⭐⭐ THREE OPTIONS, AND THE MIDDLE ONE IS ALMOST ALWAYS RIGHT:

⭐ ① ⭐ ACTIVE RECORD — the ORM model IS the domain object.
⭐    ⭐ Fast to write. ⭐⭐ The domain now imports SQLAlchemy, so Day
⭐      254's layer does not exist and `lint-imports` fails. ⭐ Fine for
⭐      a small app; incompatible with what you built yesterday.
⭐ ② ⭐⭐ IMPERATIVE MAPPING — plain dataclasses, mapped to tables in
⭐    `infra/`. SQLAlchemy's `registry.map_imperatively()`.
⭐    ⭐⭐ THE DOMAIN STAYS PURE AND YOU STILL GET THE UNIT OF WORK,
⭐      identity map and dirty tracking. ⭐ The mapping code is ugly and
⭐      lives in one file nobody reads twice.
⭐ ③ ⭐ FULL SEPARATION — domain objects and ORM entities are different
⭐    classes with translation functions both ways.
⭐    ⭐⭐ Maximum purity, and you have hand-written a mapper AND lost
⭐      dirty tracking, so every change must be explicitly copied back.
⭐      ⭐ Choose it only if you genuinely might change persistence.

⭐ ⇒ ⭐⭐ TAKE ②. State it in ADR-0006, including the honest cost: the
⭐   imperative mapping is unfamiliar and the error messages are worse.
```

```python
# ⭐ infra/mapping.py — the one ugly file
registry.map_imperatively(
    Job, jobs_table,
    properties={
        "work_items": relationship(
            WorkItem,
            lazy="raise",              # ⭐⭐ NON-NEGOTIABLE (Day 136).
            cascade="all, delete-orphan",
        ),
    },
)
# ⭐⭐ `lazy="raise"` ON EVERY RELATIONSHIP. A lazy load becomes an
#    EXCEPTION IN DEVELOPMENT rather than 400 queries in production —
#    ⭐ and it is the single highest-value line in this file.
```

# Part 2 — ⭐⭐ The repository: what it is actually for

```
⭐⭐ THE USUAL JUSTIFICATION — "so we could swap the database" — IS
⭐   FALSE AND EVERYONE KNOWS IT (Day 139). ⭐ You will not swap
⭐   Postgres. THE TWO REAL REASONS:

⭐ ① ⭐⭐ QUERY LOCALITY. Every query about jobs lives in ONE file. So
⭐    "which queries touch this table?" is answerable by opening a file
⭐    rather than grepping a codebase — ⭐ and that is the question you
⭐    ask when adding an index, changing a column, or diagnosing a lock.
⭐ ② ⭐⭐ LIFECYCLE CONTAINMENT. The session does not escape into the
⭐    web layer. ⭐ Without it, a router holds a session, a template
⭐    triggers a lazy load, and the transaction boundary is wherever the
⭐    last person left it.

⭐⭐ AND THE THREE RULES THAT KEEP IT HONEST:
⭐   ⭐ THE REPOSITORY DOES NOT COMMIT. ⭐⭐ THE SERVICE OWNS THE
⭐     TRANSACTION, because only the service knows what "one operation"
⭐     is (Day 139).
⭐   ⭐ It returns DOMAIN objects or explicit read models — ⭐⭐ never a
⭐     `Query`, never a lazy-loadable ORM object that escapes the
⭐     session.
⭐   ⭐⭐ NO `get_all()`. A method with no bound is a full table scan
⭐     with a friendly name.
```

```python
class JobRepository:
    def __init__(self, session: Session) -> None: self._s = session

    def get(self, job_id: JobId) -> Job | None:
        return self._s.scalar(
            select(Job).where(Job.id == job_id)
                       .options(selectinload(Job.work_items)))
        # ⭐⭐ NO tenant filter here — RLS does it (Day 252). ⭐ If you
        #    are NOT on RLS, the tenant filter goes in EVERY method and
        #    a forgotten one is a data leak, which is the whole argument.

    def get_for_update(self, job_id: JobId) -> Job | None:
        return self._s.scalar(
            select(Job).where(Job.id == job_id).with_for_update())
        # ⭐ A SEPARATE METHOD. ⭐⭐ A boolean flag on `get()` means the
        #   caller can take a row lock by accident.

    def list_page(self, *, cursor: Cursor | None, limit: int,
                  status: JobState | None) -> Page[JobListItem]:
        ...   # ⭐⭐ RETURNS A PROJECTION, NOT ENTITIES — Part 4
```

# Part 3 — ⭐⭐ The query-count ceiling: the gate that makes this real

```python
# tests/conftest.py — ⭐ Day 141's fixture, promoted to a gate
@pytest.fixture
def query_counter(engine):
    stmts: list[str] = []
    @event.listens_for(engine, "before_cursor_execute")
    def _rec(conn, cur, statement, *a): stmts.append(statement)
    yield stmts

@contextmanager
def max_queries(counter, n: int):
    before = len(counter)
    yield
    used = len(counter) - before
    assert used <= n, (
        f"{used} queries, ceiling {n}:\n" +
        "\n".join(counter[before:]))          # ⭐⭐ PRINT THE SQL. A
                                              #    failure that shows
                                              #    the queries is fixed
                                              #    in a minute.
```

```python
def test_job_list_query_ceiling(client, seed, query_counter):
    seed.jobs(200, work_items_each=5)          # ⭐⭐ 200 jobs, 1000 items
    with max_queries(query_counter, 4):        # ⭐ auth + count-free page
        r = client.get("/v1/jobs?limit=50")    #   + items + customers
    assert len(r.json()["data"]) == 50
```

```
⭐⭐ WHY THE NUMBER MUST BE FIXED AND SMALL:
⭐   ⭐ Seed 200 rows, not 3. ⭐⭐ AN N+1 IS INVISIBLE AT 3 ROWS — the
⭐     test passes, the endpoint is broken, and you find out in
⭐     production. ⭐ The seed size IS the test.
⭐   ⭐⭐ ASSERT `<= n`, AND CHOOSE `n` DELIBERATELY. "About twenty" is
⭐     not a ceiling. ⭐ Every increase to `n` should require a sentence
⭐     in the pull request.
⭐   ⭐ Put it on your THREE most important endpoints today, with a
⭐     dummy implementation if necessary — ⭐⭐ the harness existing is
⭐     what makes it get used.

⭐⭐ AND THE SECOND-ORDER EFFECT, WHICH IS THE REAL VALUE: this test
⭐   FAILS WHEN SOMEONE ADDS A FIELD TO A SERIALISER THAT TOUCHES A NEW
⭐   RELATION. ⭐ That is the change nobody reviews carefully, and it is
⭐   how a fast endpoint becomes a slow one without anyone editing a
⭐   query.
```

# Part 4 — ⭐⭐ Projections: the read path is not the write path

```
⭐⭐ LOADING FULL AGGREGATES FOR A LIST IS THE MOST COMMON SOURCE OF
⭐   SLOWNESS IN AN ORM APPLICATION, AND IT IS NOT AN N+1 — it is
⭐   hydrating 50 objects with 250 children to render 6 columns.

⭐   ❌ `select(Job).options(selectinload(Job.work_items))` for a list
⭐      ⇒ ⭐ 4 queries (fine) and ⭐⭐ 300 Python objects, identity-map
⭐        entries and change tracking for data you will discard.
⭐   ✅ ⭐⭐ A PROJECTION — select exactly the columns the response
⭐      needs, into a frozen dataclass:
```

```python
@dataclass(frozen=True, slots=True)
class JobListItem:
    id: int; state: str; scheduled_for: datetime
    customer_name: str; item_count: int; total_cents: int

stmt = (
    select(jobs.c.id, jobs.c.state, jobs.c.scheduled_for,
           customers.c.name.label("customer_name"),
           func.count(work_items.c.id).label("item_count"),
           func.coalesce(func.sum(work_items.c.amount_cents), 0)
               .label("total_cents"))
    .select_from(jobs.join(customers).outerjoin(work_items))
    .where(...)                     # ⭐ cursor predicate + filters
    .group_by(jobs.c.id, customers.c.name)
    .order_by(jobs.c.scheduled_for.desc(), jobs.c.id.desc())
    .limit(limit + 1)               # ⭐⭐ +1 to compute `has_more`
)                                   #    without a second query
```

```
⭐⭐ FOUR THINGS TO NOTICE, EACH FROM A DIFFERENT EARLIER DAY:
⭐   ① ⭐ `outerjoin` on work_items — an inner join would silently drop
⭐      jobs with no items (Day 192's LEFT JOIN bug).
⭐   ② ⭐⭐ ONLY ***ONE*** MULTI-VALUED RELATION IS JOINED. Adding
⭐      `photos` here would multiply rows and inflate BOTH aggregates
⭐      (Day 192). ⭐ A second one needs a subquery or a second pass.
⭐   ③ ⭐ `limit + 1` gives `has_more` for free — ⭐⭐ and there is no
⭐      `count(*)`, by design (Day 251).
⭐   ④ ⭐⭐ THE `ORDER BY` MATCHES YOUR CURSOR AND YOUR INDEX EXACTLY —
⭐      `(tenant_id, scheduled_for DESC, id DESC)`, which is Day 190's
⭐      E-S-R with the tenant as the leading equality.
⭐ ⇒ ⭐⭐ AND THE RULE THAT FOLLOWS: ***AGGREGATES FOR WRITES,
⭐   PROJECTIONS FOR READS.*** They are different models of the same
⭐   data and pretending otherwise is what makes ORM applications slow.
```

# Part 5 — ⭐ The transaction boundary, and the four rules

```python
# services/job_service.py
def complete_job(uow: UnitOfWork, job_id: JobId, items: list[WorkItemIn],
                 now: datetime) -> None:
    with uow:                                   # ⭐⭐ BEGIN, here
        job = uow.jobs.get_for_update(job_id)
        if job is None: raise NotFound()
        job.add_work_items(items)               # ⭐ domain
        events = job.apply(JobAction.COMPLETE, now=now)
        uow.outbox.add_all(events)              # ⭐⭐ SAME TRANSACTION
        uow.commit()                            # ⭐⭐ ONE commit, here
```

```
⭐⭐ THE FOUR RULES, EACH WITH THE FAILURE IT PREVENTS:
⭐  ① ⭐⭐ ONE TRANSACTION PER USE CASE, OPENED AND COMMITTED IN THE
⭐     SERVICE. ⭐ Not per repository call (nothing is atomic), not per
⭐     request (Day 172: it holds a transaction open across any I/O the
⭐     request happens to do).
⭐  ② ⭐⭐ NEVER HOLD A TRANSACTION ACROSS NETWORK I/O. The payment call
⭐     happens OUTSIDE, driven by the outbox relay (Days 142, 166).
⭐     ⭐ A transaction open across a 30-second third-party timeout is a
⭐       row lock held for 30 seconds, and a pool exhausted behind it.
⭐  ③ ⭐ EVENTS GO TO THE OUTBOX ***INSIDE*** THE TRANSACTION. ⭐⭐ That
⭐     is the entire dual-write fix, and it is one line.
⭐  ④ ⭐⭐ THE ROUTER DOES NOT SEE A SESSION. It calls the service and
⭐     translates exceptions to status codes. ⭐ If a router can commit,
⭐     eventually one will.

⭐⭐ AND THE ERROR MAPPING, WHICH BELONGS HERE AND NOWHERE ELSE:
⭐   `IntegrityError` → inspect `orig.diag.constraint_name` (Day 187)
⭐     `no_double_booking`    → 409 `assignment_conflict`
⭐     `uq_idempotency_key`   → replay the stored response
⭐     any CHECK violation    → ⭐⭐ 500, AND ALERT. A CHECK firing means
⭐                              your validation has a hole; a friendly
⭐                              4xx would hide it.
⭐   ⭐ Match on the CONSTRAINT NAME, never the message text.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Active-record models after building a domain layer | The domain then imports SQLAlchemy and `lint-imports` fails. |
| Any relationship without `lazy="raise"` | A lazy load in production is 400 silent queries. |
| Justifying a repository as "swappable persistence" | The real reasons are query locality and lifecycle containment. |
| The repository committing | Only the service knows what one operation is. |
| Returning lazy-loadable entities to the web layer | The transaction boundary ends up wherever the last person left it. |
| A `get_all()` method | A full table scan with a friendly name. |
| `get(id, for_update=True)` as a flag | Callers take row locks by accident. Separate method. |
| Query-count tests seeded with three rows | An N+1 is invisible at three rows. The seed size *is* the test. |
| A ceiling of "about twenty" | Choose a number; every increase needs a sentence in the PR. |
| Loading full aggregates for a list endpoint | 300 tracked objects to render six columns. Project instead. |
| An inner join to a nullable child in a list | Rows with no children vanish silently. |
| Joining two multi-valued relations for aggregates | Both numbers are inflated, and they look plausible. |
| A `count(*)` for `has_more` | `limit + 1` gives it for free. |
| `ORDER BY` that doesn't match the cursor and the index | Either wrong pages or a sort of the whole table. |
| A transaction per request | It's held open across every third-party call the request makes. |
| Calling a payment API inside the transaction | A 30-second row lock and a drained pool behind it. |
| The router holding a session | If it can commit, eventually it will. |
| Matching `IntegrityError` on message text | Match `diag.constraint_name`; messages change between versions. |
| Mapping a CHECK violation to a friendly 4xx | It means your validation has a hole. Let it be a 500 and alert. |

## Interview questions

**Q: Do you use the repository pattern, and why?**

> Yes, but not for the reason it's usually sold. "So we could swap the database" is false and everyone
> knows it — I'm not going to swap Postgres, and if I did, the repository interface would be the least
> of it. The two real reasons are query locality and lifecycle containment. Locality means every query
> about jobs lives in one file, so "which queries touch this table?" is answerable by opening a file
> rather than grepping — and that's exactly the question you ask when adding an index, changing a
> column, or working out what's holding a lock. Containment means the session doesn't escape into the
> web layer, so the transaction boundary is a decision rather than an accident. Three rules keep it
> honest: the repository never commits, because only the service knows what constitutes one operation;
> it returns domain objects or explicit read models, never something lazily loadable that escapes the
> session; and there's no `get_all`, because an unbounded method is a full table scan with a friendly
> name.

**Q: How do you stop N+1s from reaching production?**

> Two mechanisms, because one isn't enough. `lazy="raise"` on every relationship, so a lazy load is an
> exception during development rather than four hundred silent queries in production — that's the
> single highest-value line in the mapping file. And a query-count ceiling per endpoint in CI:
> instrument the engine, count statements, and assert the endpoint stays under a fixed small number.
> Two details make the difference between a real gate and a decorative one. The seed size — you have to
> seed a couple of hundred rows, because an N+1 is completely invisible at three, so the test passes
> while the endpoint is broken. And printing the captured SQL in the assertion message, because a
> failure that shows you the queries is fixed in a minute. The second-order benefit is the one I value
> most: that test fails when someone adds a field to a serialiser that touches a new relation, which is
> exactly the change nobody reviews carefully and exactly how a fast endpoint quietly becomes a slow
> one.

**Q: How do you build a list endpoint?**

> With a projection, not with aggregates. Loading fifty jobs with two hundred and fifty children to
> render six columns isn't an N+1 — the query count is fine — it's three hundred tracked objects,
> identity-map entries and change tracking for data that gets discarded. So the list query selects
> exactly the columns the response needs into a frozen dataclass. Four details in that query all come
> from earlier lessons: an outer join to the child table so jobs with no items don't silently vanish;
> only one multi-valued relation joined, because a second would multiply rows and inflate both
> aggregates with plausible-looking numbers; `limit + 1` to compute `has_more` without a count; and an
> `ORDER BY` that matches the cursor and the composite index exactly, with the tenant as the leading
> equality column. The rule underneath is that aggregates are for writes and projections are for reads
> — they're different models of the same data, and pretending otherwise is what makes ORM applications
> slow.

**Q: Where's your transaction boundary?**

> In the service, one per use case, opened and committed there. Not per repository call, because then
> nothing is atomic; and not per request, because that holds a transaction open across whatever I/O the
> request happens to do. The rule I'd emphasise is never holding a transaction across network I/O — the
> payment call happens outside it, driven by the outbox relay, because a transaction open across a
> thirty-second third-party timeout is a row lock held for thirty seconds with a drained connection
> pool behind it. Domain events are written to the outbox *inside* the transaction, which is the entire
> dual-write fix in one line: the state change and the intent to notify commit atomically or not at
> all. And the router never sees a session — it calls the service and translates exceptions to status
> codes, because if a router *can* commit then eventually one will.

**Q: How do you map database errors to HTTP responses?**

> In the service, by inspecting the constraint name rather than the message text, because messages
> change between Postgres versions and locales. A violation of the no-double-booking exclusion
> constraint becomes a 409 with `assignment_conflict`; a duplicate idempotency key becomes a replay of
> the stored response; a foreign-key violation is usually a 422. The one I'd single out is a `CHECK`
> violation, which I deliberately do *not* map to a friendly 4xx — it becomes a 500 and it alerts,
> because a check constraint firing means my validation layer has a hole, and turning that into a
> polite error message hides exactly the bug I want to know about. That's the same principle as the
> constraint existing at all: the database is the last line of defence, so when it speaks, something
> upstream was wrong.

defence has to be structural. Give the two mechanisms: `lazy="raise"` so it's an exception in
development, and a query-count ceiling in CI. Then the detail that separates a real gate from a
decorative one: **seed two hundred rows, because an N+1 is invisible at three**, and print the SQL in
