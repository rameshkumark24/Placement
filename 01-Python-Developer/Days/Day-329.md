# Day 329 🪓

**P-329** · 🪓 **Sharding** — the key, the hotspot, and ⭐⭐ the resharding you cannot afford

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: sharding is the only technique that scales writes, and it pays for that
> by taking away joins, transactions, uniqueness and every query that doesn't carry the shard key —
> so the shard key is not a database decision, it is the single most expensive product decision in
> the system.**

# Part 1 — ⭐⭐ Do not shard. Then, do not shard. Then shard.

```
⭐⭐ THE HONEST ORDER OF OPERATIONS, AND SAYING IT SCORES:
⭐   ① ⭐ Index properly (Day 195). ⭐⭐ MOST "WE NEED TO SHARD"
⭐        IS A SEQUENTIAL SCAN.
⭐   ② ⭐ Read replicas for read load (Day 328).
⭐   ③ ⭐ Cache (Day 326).
⭐   ④ ⭐ Bigger box (Day 324) — ⭐⭐ 128 CORES AND 2 TB OF RAM
⭐        IS A REAL PURCHASE AND IT IS CHEAPER THAN THIS DAY.
⭐   ⑤ ⭐ Move cold data out — archive tables, object storage.
⭐   ⑥ ⭐ Split by ***table*** (functional partitioning): move
⭐        the events table to its own database.
⭐   ⑦ ⭐⭐ ONLY NOW: SHARD.

⭐⭐ THE THREE SIGNALS THAT SHARDING IS ACTUALLY REQUIRED:
⭐   ⭐ ① ***WRITE*** throughput exceeds one node — ⭐⭐ THE ONLY
⭐     PROBLEM SHARDING UNIQUELY SOLVES.
⭐   ⭐ ② The dataset exceeds one node's storage or, more often,
⭐     ⭐⭐ THE WORKING SET NO LONGER FITS IN RAM AND EVERY
⭐     QUERY BECAME A DISK READ.
⭐   ⭐ ③ Blast radius: one tenant's load must not be able to
⭐     take down everyone.

⭐⭐ NOTE WHAT IS ***NOT*** ON THAT LIST: "we have a lot of
⭐   users", "it feels slow", "the table has 100 million rows".
⭐   ⭐ A hundred million rows with the right index is a
⭐   millisecond query on one box.
```

# Part 2 — ⭐⭐ Choosing the key: the four questions

```
⭐⭐ ① ⭐⭐ WHAT IS ON ***EVERY*** QUERY? ⭐ The key must appear
⭐      in the WHERE clause of your top queries, or every read
⭐      becomes a ***scatter-gather*** across all shards.
⭐      ⇒ ⭐⭐ AND A SCATTER-GATHER IS AS SLOW AS THE SLOWEST
⭐        SHARD — ⭐ so with 20 shards, your p50 becomes
⭐        something like your old p95 (Day 322's tail
⭐        amplification, now structural).

⭐⭐ ② DOES IT DISTRIBUTE EVENLY? ⭐ Cardinality high, values
⭐      not skewed.
⭐      ⇒ ⭐⭐ `country` HAS 200 VALUES AND 40% OF THEM ARE ONE
⭐        COUNTRY. THAT IS NOT A SHARD KEY.

⭐⭐ ③ DOES IT KEEP RELATED DATA TOGETHER? ⭐ If a "unit of
⭐      work" spans shards you have lost transactions (Day 342).
⭐      ⇒ ⭐ Shard by `tenant_id` and a tenant's orders, users
⭐        and invoices all land together. ⭐⭐ THIS IS DAY 305'S
⭐        AGGREGATE BOUNDARY, PROMOTED TO INFRASTRUCTURE.

⭐⭐ ④ ⭐⭐ IS IT IMMUTABLE? ⭐ Changing a row's shard key means
⭐      ***moving the row between databases***, which is a
⭐      distributed transaction for a field update.
⭐      ⇒ ⭐ So: never shard on status, plan tier, region-of-
⭐        residence, or anything a user can edit.
```

```
⭐⭐ THE CANDIDATES, JUDGED:
⭐   ⭐ ✔ `tenant_id` / `org_id` — ⭐⭐ THE BEST KEY IN B2B SaaS.
⭐     Immutable, on every query, keeps a unit together, and
⭐     gives blast-radius isolation for free.
⭐     ⭐ ✘ Except: one enormous tenant. See Part 4.
⭐   ⭐ ✔ `user_id` — good for consumer apps ⭐ if your queries
⭐     are user-scoped. ⭐⭐ SOCIAL GRAPHS ARE NOT USER-SCOPED,
⭐     which is why Day 351 is hard.
⭐   ⭐ ✘ `created_at` — ⭐⭐ ALL WRITES GO TO ONE SHARD, ALWAYS.
⭐     The definition of a hotspot. ⭐ (Legitimate ***only***
⭐     for time-series with retention, where old shards get
⭐     dropped whole — that is `pg_partman`'s job, and it is
⭐     partitioning, not sharding.)
⭐   ⭐ ✘ Auto-increment id — ⭐⭐ SAME PROBLEM: MONOTONIC KEYS
⭐     CONCENTRATE WRITES ON THE LAST SHARD.
⭐   ⭐ ✔ `hash(user_id)` — even, ⭐⭐ AND DESTROYS RANGE QUERIES
⭐     COMPLETELY.
```

# Part 3 — ⭐⭐ Range vs hash vs directory

```
⭐⭐ RANGE: shard 1 = A–F, shard 2 = G–M…
⭐   ⭐ ✔ Range queries work. ✔ Rebalancing is a split.
⭐   ⭐ ✘ ⭐⭐ HOTSPOTS ARE THE DEFAULT, not the exception —
⭐     sequential ids, timestamps, and alphabetical skew all
⭐     concentrate.
⭐   ⇒ ⭐ HBase, Bigtable, ⭐ and Postgres declarative range
⭐     partitioning.

⭐⭐ HASH: shard = hash(key) mod N, or better, ⭐⭐ CONSISTENT
⭐   HASHING (Day 326 — and this is the day that reference pays
⭐   off, because here a rehash means ***moving terabytes***,
⭐   not just a cold cache).
⭐   ⭐ ✔ Even distribution, essentially free.
⭐   ⭐ ✘ ⭐⭐ NO RANGE QUERIES AT ALL. "All orders in March"
⭐     becomes a scatter-gather.
⭐   ⇒ ⭐ Cassandra, DynamoDB, most application-level sharding.

⭐⭐ DIRECTORY (lookup table): an explicit map key → shard.
⭐   ⭐ ✔ ⭐⭐ TOTAL FLEXIBILITY: move ONE tenant to its own
⭐     shard by updating one row. ⭐ Pin the noisy neighbour.
⭐   ⭐ ✘ The directory is a lookup on every request (⭐ cache
⭐     it) and ⭐⭐ A NEW SINGLE POINT OF FAILURE.
⭐   ⇒ ⭐⭐ THIS IS WHAT MOST MATURE B2B SaaS ACTUALLY RUNS,
⭐     and saying so is a strong signal — it is the pragmatic
⭐     choice, not the textbook one.

⭐⭐ THE HYBRID THAT IS USUALLY RIGHT:
⭐   ***HASH INTO A FIXED, LARGE NUMBER OF LOGICAL SHARDS
⭐      (e.g. 1024), THEN MAP LOGICAL → PHYSICAL IN A
⭐      DIRECTORY.***
⭐   ⇒ ⭐⭐ GROWING FROM 4 TO 8 MACHINES MOVES ***LOGICAL
⭐     SHARDS***, NOT ROWS. No rehashing, no key recomputation,
⭐     and the mapping is one small table.
⭐   ⇒ ⭐ Vitess, Citus, Redis Cluster's 16,384 slots and
⭐     Elasticsearch all do exactly this. ⭐⭐ PRE-SPLIT FROM DAY
⭐     ONE: 1024 logical shards on 2 machines costs nothing and
⭐     saves the migration that would otherwise cost a quarter.
```

# Part 4 — ⭐⭐ The hotspot you created

```
⭐⭐ SHARDING GIVES YOU A NEW FAILURE MODE: ***ONE SHARD IS THE
⭐   WHOLE SYSTEM'S BOTTLENECK WHILE THE OTHERS IDLE.***

⭐⭐ CAUSE ① — ***THE CELEBRITY / WHALE TENANT.***
⭐   ⭐ Shard by `tenant_id`; one customer is 60% of your data.
⭐   ⇒ FIXES: ⭐ (a) the directory — give them a dedicated
⭐     shard; ⭐⭐ (b) A ***COMPOUND*** KEY — `(tenant_id,
⭐     bucket)` where big tenants get many buckets and small
⭐     ones get one. ⭐ (c) Accept it and price it.

⭐⭐ CAUSE ② — ***MONOTONIC WRITE KEYS.*** Time or sequence.
⭐   ⇒ FIX: ⭐⭐ SALT THE PREFIX. `f"{hash(id) % 16}#{date}"`
⭐     spreads today's writes over 16 shards, ⭐ at the cost of
⭐     16 queries to read a day. ⭐ Explicit trade, stated.

⭐⭐ CAUSE ③ — ***A SINGLE HOT ROW.*** One product in a flash
⭐   sale. ⭐⭐ SHARDING CANNOT HELP: ONE ROW IS ONE SHARD.
⭐   ⇒ ⭐ This is Day 326's hot key, and the fixes are the same
⭐     family: split the row into N counter rows and sum them,
⭐     or move the contention into Redis, or queue it (Day 356).

⭐⭐ THE MEASUREMENT THAT MATTERS: ⭐⭐ NOT AVERAGE SHARD LOAD.
⭐   ***max(shard load) / mean(shard load).*** ⭐ If that ratio
⭐   is 4, you have 4× the hardware you need and a system that
⭐   behaves as though you have one machine.
```

# Part 5 — ⭐⭐ What sharding takes away

```
⭐⭐ THIS IS THE PART CANDIDATES SKIP AND INTERVIEWERS PROBE.

⭐⭐ ① ⭐⭐ CROSS-SHARD JOINS ARE GONE. ⭐ You denormalise, or
⭐      you join in application code (fetch, fetch, merge in
⭐      Python), or you keep a small reference table replicated
⭐      to every shard.
⭐⭐ ② ⭐⭐ TRANSACTIONS DO NOT SPAN SHARDS. ⭐ You get 2PC
⭐      (slow, blocking) or sagas (Day 342). ⭐⭐ WHICH IS WHY
⭐      QUESTION ③ IN PART 2 IS THE ONE THAT MATTERS: put the
⭐      unit of atomicity inside one shard and you never pay
⭐      this.
⭐⭐ ③ ⭐⭐ GLOBAL UNIQUENESS IS GONE. `UNIQUE(email)` cannot be
⭐      enforced by a database that only sees a twelfth of the
⭐      rows.
⭐      ⇒ ⭐ FIX: a small global "unique registry" table (one
⭐        unsharded database owning just emails), or make the
⭐        uniqueness scope match the shard (`UNIQUE(tenant_id,
⭐        email)` — ⭐⭐ WHICH IS USUALLY WHAT THE BUSINESS
⭐        ACTUALLY WANTED ANYWAY).
⭐⭐ ④ ⭐⭐ AUTO-INCREMENT IDs ARE GONE. ⭐ Two shards both
⭐      produce id 1000.
⭐      ⇒ ⭐ FIX: UUIDv7 / ULID (⭐⭐ TIME-ORDERED, SO INDEX
⭐        LOCALITY SURVIVES — a plain UUIDv4 primary key wrecks
⭐        B-tree insert locality), or Snowflake ids
⭐        (timestamp | machine | sequence), or a per-shard id
⭐        range.
⭐⭐ ⑤ ⭐ `ORDER BY … LIMIT 20` ACROSS SHARDS means fetching 20
⭐      from ***each*** shard and merging — ⭐⭐ AND `OFFSET
⭐      10000` MEANS FETCHING 10,020 FROM EVERY SHARD. ⭐ Offset
⭐      pagination is not merely slow here; it is untenable.
⭐      ⇒ ⭐ Cursor pagination (Day 194) stops being a nicety
⭐        and becomes a requirement.
⭐⭐ ⑥ ⭐ SCHEMA MIGRATIONS NOW RUN N TIMES, ⭐⭐ AND CAN BE
⭐      HALF-APPLIED. Day 283's expand/contract is now
⭐      mandatory rather than good practice.
```

# Part 6 — ⭐⭐ Resharding without downtime

```
⭐⭐ THE HARD TRUTH: ***RESHARDING A LIVE SYSTEM IS ONE OF THE
⭐   MOST EXPENSIVE PROJECTS AN ENGINEERING TEAM CAN TAKE ON.***
⭐   ⇒ ⭐⭐ WHICH IS THE ENTIRE ARGUMENT FOR PRE-SPLITTING INTO
⭐     LOGICAL SHARDS ON DAY ONE. It costs nothing then.

⭐⭐ THE SIX-STEP MOVE (the same shape as Day 283's
⭐   expand/contract, and worth noticing that it is):
⭐   ① ⭐ DUAL WRITE: writes go to old ***and*** new shard.
⭐   ② ⭐ BACKFILL historical rows in batches (Day 260).
⭐   ③ ⭐⭐ VERIFY: compare row counts and checksums per key
⭐      range. ⭐⭐ DO NOT SKIP. This is where you learn your
⭐      dual-write had a bug three weeks ago.
⭐   ④ ⭐ SHIFT READS to the new shard, behind a flag, a
⭐      percentage at a time.
⭐   ⑤ ⭐ STOP writing to the old shard.
⭐   ⑥ ⭐ Drop the old data ***after*** a safety window.

⭐⭐ AND THE CUTOVER RACE THAT EATS WRITES:
⭐   ⭐ Between "backfill finished" and "dual write started"
⭐     there is a gap. ⭐⭐ ANY WRITE IN THAT GAP EXISTS IN
⭐     EXACTLY ONE PLACE.
⭐   ⇒ ⭐⭐ SO THE ORDER IS ALWAYS: ***DUAL-WRITE FIRST, BACKFILL
⭐     SECOND.*** ⭐ Backfill must be idempotent (upsert) because
⭐     it will race the live writes — ⭐ and that is fine, by
⭐     construction, if it is an upsert.
```

# Part 7 — ⭐ Doing it in Python without a framework

```
⭐⭐ THE THREE PIECES, AND ONLY THREE:
⭐   ① ⭐ A resolver: `shard_for(tenant_id) -> engine`.
⭐   ② ⭐⭐ CONTEXT PROPAGATION: the current shard held in a
⭐      `ContextVar`, set once at the request boundary. ⭐ Day
⭐      285's trace-id plumbing, reused exactly.
⭐   ③ ⭐ A guard that ***fails loudly*** when a query has no
⭐      shard key.

⭐⭐ AND THE PIECE THAT SAVES YOU LATER:
⭐   ***MAKE "NO SHARD KEY" A TEST FAILURE, NOT A PRODUCTION
⭐      SCATTER-GATHER.*** ⭐ One `before_execute` hook that
⭐   raises in dev/test if the statement lacks the shard column
⭐   and is not explicitly marked `@fanout`. ⭐⭐ THIS IS THE
⭐   SINGLE HIGHEST-VALUE FIFTY LINES IN A SHARDED CODEBASE,
⭐   because the alternative is discovering it at 200 rps.
```

```python
# ⭐ The resolver + context, in the shape you'd actually ship
_shard: ContextVar[int | None] = ContextVar("shard", default=None)

LOGICAL = 1024                                  # ⭐⭐ PRE-SPLIT

def logical_shard(tenant_id: str) -> int:
    return int.from_bytes(
        hashlib.blake2b(tenant_id.encode(), digest_size=4).digest(),
        "big") % LOGICAL

def engine_for(tenant_id: str) -> AsyncEngine:
    ls = logical_shard(tenant_id)
    physical = DIRECTORY[ls]                    # ⭐ cached map
    return ENGINES[physical]

@app.middleware("http")
async def bind_shard(request, call_next):
    tid = request.state.tenant_id               # ⭐ from auth
    _shard.set(logical_shard(tid))              # ⭐⭐ ONE PLACE
    return await call_next(request)
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Sharding before indexing | Most "we must shard" is a sequential scan. You just bought a quarter of pain for a `CREATE INDEX` |
| ⭐⭐ Sharding on a mutable column | Changing the key means moving the row between databases — a distributed transaction for a field update |
| ⭐⭐ Sharding on time or a sequence | Every write goes to the newest shard. That is the definition of a hotspot |
| ⭐ Choosing a key not present in your queries | Every read becomes a scatter-gather, as slow as the slowest shard |
| ⭐⭐ Not pre-splitting into logical shards | Growing from 4 to 8 machines becomes a rehash of terabytes instead of a directory update |
| ⭐⭐ Backfilling before dual-writing | Writes in the gap exist in exactly one place, and you will not notice for weeks |
| ⭐ Skipping the verification step | The dual write had a bug and you find out after dropping the source |
| ⭐⭐ Expecting `UNIQUE(email)` to still work | No shard sees all rows. Global registry, or scope uniqueness to the tenant |
| ⭐ Keeping auto-increment ids | Two shards both emit 1000. UUIDv7 or Snowflake |
| ⭐ Keeping OFFSET pagination | `OFFSET 10000` fetches 10,020 rows from *every* shard |
| ⭐⭐ Monitoring average shard load | The number that matters is max over mean. At 4, you own 4× the hardware you need |

## Interview questions

**1. "How do you choose a shard key?"**
> ⭐ Four questions: is it on every query, does it distribute evenly, does it keep a unit of work
> together, and ⭐⭐ **is it immutable** — because changing a shard key means moving a row between
> databases. ⭐ In B2B SaaS `tenant_id` usually wins all four and gives blast-radius isolation as a
> bonus. ⭐⭐ And I'd say what I'm *giving up* in the same breath: cross-shard joins, cross-shard
> transactions, global uniqueness and auto-increment ids — **because a candidate who only lists
> benefits hasn't run one.**

**2. "One tenant is 60% of your data. Now what?"**
> ⭐ That's the whale problem, and hash sharding can't fix it because one key is one shard. ⭐⭐ Two
> real answers: a **directory** mapping, so I move that tenant to a dedicated shard by updating one
> row; or a **compound key** — `(tenant_id, bucket)` — where large tenants get many buckets and small
> ones get one. ⭐ The third answer is commercial: give them a dedicated cluster and charge for it.

**3. "You need to grow from 4 shards to 8. What happens?"**
> ⭐⭐ If I sharded with plain modulo, roughly half the rows move and I need a months-long migration.
> ⭐ If I pre-split into 1024 logical shards mapped to physical ones, **I move logical shards, not
> rows** — the key computation never changes and the mapping is one small table. ⭐⭐ That's why the
> pre-split happens on day one, when it costs nothing: it's Vitess, Citus and Redis Cluster's model,
> and it's the difference between a config change and a quarter of engineering.

**4. "How do you enforce unique emails across shards?"**
> ⭐ You can't with a constraint — no shard sees all the rows. ⭐⭐ Either a small unsharded registry
> table that owns email→user_id and is written first, or **scope the uniqueness to the shard:
> `UNIQUE(tenant_id, email)`, which is usually what the business actually meant anyway.** ⭐ I'd ask
> that question before building the registry, because half the time the global constraint was an
> accident.

**5. "Walk me through a live reshard."**
> ⭐⭐ Dual-write first, backfill second — **never the other way round, because writes landing between
> "backfill done" and "dual write on" exist in exactly one place.** ⭐ Backfill in idempotent batches
> so it can race live writes safely. ⭐ Then verify with per-range checksums, shift reads behind a
> percentage flag, stop the old writes, and drop the source only after a safety window. ⭐ It's
> expand/contract from deployments, applied to data.

**6. "When is sharding the wrong answer?"**
> ⭐ Whenever the problem is read load, dataset size that a bigger box would hold, or a query pattern
> that a missing index would fix. ⭐⭐ **Sharding uniquely solves exactly one problem: write throughput
> beyond one node** — plus blast-radius isolation as a design goal. ⭐ Everything else on the list has
> a cheaper answer, and I'd exhaust indexes, replicas, caching, a bigger instance and functional
> splits first.

## 🎙️ Articulation drill

**Two minutes.** Open with the reluctance, because it's the senior signal: **index, replicate, cache,
buy a bigger box, archive cold data, split by table — and only then shard**, since most "we need to
shard" is a sequential scan. Then name the one problem it uniquely solves: **write throughput beyond a
single node.** Give the four key questions — on every query, distributes evenly, keeps a unit of work
together, and **immutable, because changing a shard key means moving a row between databases** — and
say `tenant_id` usually wins all four in B2B. Then, unprompted, list what you're giving up: **joins,
transactions, global uniqueness, auto-increment ids, offset pagination, and single-run migrations** —
that list is what separates someone who has run a sharded system from someone who has read about one.
Cover the hotspot honestly: **the whale tenant needs a directory or a compound key, monotonic keys
need salting, and a single hot row can't be sharded at all because one row is one shard.** Close on
the two operational lines that matter most: **pre-split into a thousand logical shards on day one,
because then growing from four machines to eight moves logical shards rather than rows** — and when
you do migrate, **dual-write first and backfill second, because anything written in the gap exists in
exactly one place and you won't find out for weeks.**
