# Day 456 🪜

**P-456** · 🪜 **Reliability and fallback** — ⭐⭐ an untested fallback is not a fallback

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: your model provider has worse availability than your database and fails in
> ways your database never does, so reliability here is not redundancy — it is a ladder of increasingly
> worse answers, each one labelled honestly, ending in an error you are not ashamed of.**

---

# Part 1 — What kind of dependency this is

```
⭐ ***A MODEL PROVIDER IS NOT LIKE YOUR DATABASE:***
⭐   ⭐ published SLAs cluster around ⭐⭐ 99.5–99.9%, ⭐ which is
⭐     ***hours*** per month, not minutes;
⭐   ⭐ ⭐⭐ FAILURES ARE CORRELATED ACROSS THE WHOLE INDUSTRY —
⭐     ⭐ when a major provider is down, ***every competitor's
⭐     product is down too***, ⭐⭐ WHICH IS A GENUINE BUSINESS
⭐     ARGUMENT FOR ACCEPTING A LOWER TARGET AND A GENUINE
⭐     ARGUMENT AGAINST BEING THE ONE WHO STAYS UP;
⭐   ⭐ ***degradation beats outage***: ⭐⭐ 429s, SLOW FIRST
⭐     TOKENS, TRUNCATED STREAMS AND CAPACITY-DRIVEN LATENCY ARE
⭐     FAR MORE COMMON THAN A CLEAN 503;
⭐   ⭐ ⭐⭐ AND SOME FAILURES ARE ***PARTIAL***: ⭐ long prompts
⭐     fail while short ones succeed, one model is degraded while
⭐     another is fine, one region is sick.
⭐   ⭐ ⭐⭐ THAT LAST ONE BREAKS NAIVE CIRCUIT BREAKERS (PART 4).
```

# Part 2 — ⭐⭐ The degradation ladder

```
⭐ ***SEVEN RUNGS. EACH IS WORSE THAN THE ONE ABOVE, AND EACH
⭐   MUST BE ***LABELLED*** WHEN THE USER-VISIBLE QUALITY
⭐   CHANGES.***

⭐ ① ***RETRY, SAME PROVIDER*** — ⭐ transient only. Part 3.
⭐ ② ***SAME PROVIDER, DIFFERENT REGION/DEPLOYMENT*** — ⭐ often
⭐   the cheapest real redundancy, ⭐⭐ AND IT REQUIRES NO PROMPT
⭐   CHANGES, WHICH MAKES IT THE ONLY FREE RUNG.
⭐ ③ ***DIFFERENT MODEL, SAME PROVIDER*** — ⭐ a smaller model
⭐   still answers. ⭐⭐ QUALITY DROPS MEASURABLY, SO YOU NEED ITS
⭐   EVAL SCORE ***BEFORE*** THE INCIDENT, NOT DURING.
⭐ ④ ***DIFFERENT PROVIDER*** — ⭐ needs the Day 442 seam ⭐⭐ AND
⭐   ITS OWN PROMPT VERSION (PART 5).
⭐ ⑤ ***CACHED OR STALE ANSWER***, ⭐⭐ LABELLED WITH ITS AGE —
⭐   ⭐ `stale-if-error` from Day 454. ⭐ Free, and it works
⭐   precisely when nothing else does.
⭐ ⑥ ⭐⭐ ***THE NON-AI PATH.*** ⭐ Keyword search results. The
⭐   FAQ. A form. The document list. ⭐⭐ THIS RUNG IS SKIPPED BY
⭐   ALMOST EVERYONE AND IT IS OFTEN THE BEST ONE — ⭐ "here are
⭐   the four most relevant documents" is genuinely useful and
⭐   ***completely independent of the failing dependency***.
⭐ ⑦ ⭐⭐ ***AN HONEST ERROR WITH AN ESCAPE HATCH.*** ⭐ "This
⭐   isn't available right now — here's how to reach a person."
⭐   ⭐⭐ A GOOD RUNG ⑦ BEATS A BAD RUNG ③.

⭐ ***AND THE RULE THAT MAKES THE LADDER SAFE:***
⭐   ⭐ ⭐⭐ ***IF THE ANSWER IS WORSE, SAY SO.*** ⭐ A silently
⭐     degraded answer is the worst outcome on this page,
⭐     because the user makes a decision on it believing it is
⭐     your normal quality — ⭐⭐ AND YOUR ERROR RATE STILL SAYS
⭐     ZERO (DAY 455).
⭐   ⭐ Log the rung on every request. ⭐⭐ "PERCENTAGE OF TRAFFIC
⭐     SERVED BELOW RUNG ②" IS A REAL SLO AND A BETTER ONE THAN
⭐     UPTIME.
```

# Part 3 — Retries that do not make it worse

```
⭐ ***RETRY ONLY:*** ⭐ 429, 500/502/503/504, connection errors,
⭐   ⭐ and ***read timeouts before the first token***.
⭐ ***NEVER RETRY:*** ⭐ 400 (your prompt is wrong — ⭐⭐ IT WILL
⭐   BE WRONG AGAIN), ⭐ 401/403, ⭐ context-length errors,
⭐   ⭐ content-filter refusals.
⭐   ⭐ ⭐⭐ AND NEVER BLIND-RETRY A ***MID-STREAM*** FAILURE:
⭐     ⭐ you were billed for what generated, and a naive retry
⭐       regenerates from scratch at full cost, ⭐⭐ POSSIBLY WITH
⭐       A DIFFERENT ANSWER THE USER HAS ALREADY PARTLY READ.

⭐ ***EXPONENTIAL BACKOFF WITH ***FULL*** JITTER*** — ⭐ `sleep =
⭐   random(0, min(cap, base × 2^n))`. ⭐⭐ WITHOUT JITTER EVERY
⭐   CLIENT RETRIES AT THE SAME INSTANT AND YOU RE-CREATE THE
⭐   SPIKE THAT CAUSED THE FAILURE.
⭐   ⭐ Honour `Retry-After` when the provider sends it — ⭐⭐ IT
⭐     KNOWS MORE THAN YOUR BACKOFF FORMULA DOES.

⭐ ⭐⭐ ***AND THE RETRY BUDGET, WHICH IS THE PART PEOPLE MISS***
⭐   (Day 405):
⭐   ⭐ retries add load ***exactly when the dependency is
⭐     struggling***. ⭐ 3 retries each turns a 30% failure rate
⭐     into ⭐⭐ 2× THE TRAFFIC AGAINST A SYSTEM THAT IS ALREADY
⭐     FAILING.
⭐   ⭐ ⇒ cap retries at ⭐⭐ ~10% OF TOTAL REQUESTS IN A ROLLING
⭐     WINDOW. ⭐ Over budget → stop retrying and drop to the next
⭐     rung immediately. ⭐⭐ THIS SINGLE CONTROL IS THE
⭐     DIFFERENCE BETWEEN RIDING OUT A BROWNOUT AND AMPLIFYING
⭐     IT.
```

```
⭐ ⭐⭐ AND STREAMING NEEDS ***THREE*** TIMEOUTS, NOT ONE:
⭐   ⭐ ① ***TIME TO FIRST TOKEN*** (~10–20s) — ⭐ the provider
⭐     is queueing you. ⭐⭐ SAFE TO RETRY: NOTHING GENERATED.
⭐   ⭐ ② ***INTER-TOKEN TIMEOUT*** (~5–10s) — ⭐⭐ THE STREAM
⭐     STALLED MID-ANSWER. ⭐ The one everybody forgets, and the
⭐     one that hangs connections for minutes.
⭐   ⭐ ③ ***TOTAL WALL-CLOCK*** — ⭐ the user's budget (Day 439).
⭐   ⭐ ⇒ ⭐⭐ ALL THREE MUST BE SHORTER THAN THE DEADLINE ABOVE
⭐     THEM, ⭐ and shorter than every proxy idle timeout in the
⭐     path (Day 453).
```

# Part 4 — Circuit breakers, and the partial-failure problem

```
⭐ ***THE STANDARD BREAKER:*** ⭐ N failures in a window → open →
⭐   fail fast → half-open probe → close.
⭐   ⭐ ⭐⭐ IT EXISTS TO STOP YOU SPENDING 30 SECONDS OF EVERY
⭐     USER'S TIME DISCOVERING SOMETHING YOU ALREADY KNEW.

⭐ ⭐⭐ THE TWIST HERE: ***THE FAILURE IS OFTEN PARTIAL.***
⭐   ⭐ Long prompts fail on context limits while short ones
⭐     succeed. ⭐ One model is degraded, another is fine. ⭐ One
⭐     tenant's giant documents trip it for everyone.
⭐   ⭐ ⇒ ⭐⭐ A GLOBAL BREAKER TRIPS ON A PROBLEM AFFECTING 5% OF
⭐     TRAFFIC AND TAKES DOWN THE OTHER 95%. ⭐ You caused the
⭐     outage.
⭐   ⭐ ⇒ ⭐⭐ SCOPE BREAKERS PER (PROVIDER, MODEL), ⭐ and consider
⭐     per size bucket. ⭐ Key the state by what actually varies.

⭐ ***AND TWO MORE THINGS A BREAKER MUST DO HERE:***
⭐   ⭐ ⭐⭐ FALLING BACK IS NOT FAILING FAST — ⭐ an open breaker
⭐     should route to rung ③ or ④, not return an error, or you
⭐     have built an outage amplifier with good intentions;
⭐   ⭐ ***half-open probes cost money and produce a real
⭐     answer***. ⭐⭐ USE A CHEAP, SHORT PROBE REQUEST RATHER
⭐     THAN A REAL USER'S 8,000-TOKEN PROMPT.
```

# Part 5 — ⭐⭐ Prompts are not portable

```
⭐ ***THE ASSUMPTION THAT BREAKS EVERY FALLBACK PLAN:*** ⭐ "we
⭐   can switch providers, we have an abstraction."
⭐   ⭐ ⭐⭐ THE ***INTERFACE*** IS PORTABLE. THE ***PROMPT*** IS
⭐     NOT.

⭐ ***WHAT DIFFERS BETWEEN PROVIDERS:***
⭐   ⭐ system-prompt handling and how strongly it is followed;
⭐   ⭐ ⭐⭐ TOOL-CALLING FORMAT AND RELIABILITY;
⭐   ⭐ structured-output support — ⭐⭐ CONSTRAINED DECODING VS
⭐     "PLEASE RETURN JSON" IS A ***CAPABILITY*** DIFFERENCE, NOT
⭐     A SYNTAX ONE (DAY 418);
⭐   ⭐ tokenisation, so your token budgets are wrong;
⭐   ⭐ refusal behaviour and safety thresholds;
⭐   ⭐ how well few-shot examples transfer;
⭐   ⭐ ⭐⭐ AND WHETHER YOUR PROMPT CACHE STRATEGY EXISTS AT ALL.

⭐ ⇒ ***THE FALLBACK NEEDS:***
⭐   ⭐ ① its ***own prompt version*** (Day 427's `TaskConfig`
⭐     already versions the model, ⭐⭐ SO THIS COSTS YOU NOTHING
⭐     STRUCTURALLY);
⭐   ⭐ ② ⭐⭐ ITS OWN EVAL SCORES, MEASURED BEFORE THE INCIDENT;
⭐   ⭐ ③ its own cost and latency numbers;
⭐   ⭐ ④ ⭐⭐ AND CONTINUOUS EXERCISE — ⭐ route 1% of production
⭐     traffic to the fallback ***permanently***.
⭐   ⭐ ⭐⭐ ④ IS THE WHOLE POINT: A FALLBACK EXERCISED ONLY
⭐     DURING INCIDENTS IS AN UNTESTED CODE PATH THAT RUNS ONLY
⭐     WHEN YOU CAN LEAST AFFORD A SURPRISE. ⭐ It will have
⭐     rotted: an expired key, a deprecated model name, a schema
⭐     the new provider rejects.
```

⭐   ⭐ ⭐⭐ FOR MANY PRODUCTS "DEGRADED TO KEYWORD SEARCH,

# 💬 Interview

**1. "Your provider goes down. What happens?"**

⭐ We walk a ladder rather than switch to a spare. ⭐⭐ Retry for transients, then a different region on
the same provider — which is the only free rung because it needs no prompt changes — then a smaller
model on the same provider, then a different provider, then a cached answer labelled with its age, then
the non-AI path, then an honest error with a route to a human. ⭐ Each rung is worse than the one above,
and the rule that makes it safe is that if the answer is worse, we say so. ⭐⭐ A silently degraded answer
is the worst outcome available, because the user acts on it believing it's our normal quality — and the
error rate still reads zero. ⭐ We log the rung on every request, and "percentage of traffic served below
rung two" is a better SLO than uptime.

**2. "Which rung do people skip?"**

⭐ The non-AI path, and it's often the best one. ⭐⭐ "Here are the four most relevant documents" from
keyword search is genuinely useful, costs nothing, and is completely independent of the failing
dependency. ⭐ Teams jump from "smaller model" straight to "error page" because the fallback feels like
it has to be AI. ⭐⭐ And a good honest error with an escape hatch beats a bad answer from a weak model —
that's a product decision that should be made explicitly with eval numbers on the table, not by an
engineer at two in the morning.

**3. "How do you retry safely?"**

⭐ Only on transients — 429s, 5xx, connection errors, and read timeouts *before the first token*. ⭐⭐ Never
on a 400, because the prompt will be wrong again; never on context-length or content-filter errors; and
never blind-retry a mid-stream failure, because you were billed for what generated and a naive retry
regenerates from scratch at full cost, possibly with a different answer the user has partly read.
⭐ Exponential backoff with **full** jitter, because without jitter every client retries at the same
instant and recreates the spike. ⭐⭐ And a retry budget — retries add load exactly when the dependency
is struggling, so three retries each turns a thirty percent failure rate into double the traffic against
a system that's already failing. ⭐ Cap retries at about ten percent of requests in a rolling window;
over budget, stop retrying and drop a rung. ⭐⭐ That one control is the difference between riding out a
brownout and amplifying it.

**4. "How many timeouts does a streaming request need?"**

⭐ Three. ⭐⭐ Time to first token, around ten to twenty seconds, which is safe to retry because nothing
generated. An inter-token timeout of five to ten seconds for a stream that stalls mid-answer — that's
the one everyone forgets and it hangs connections for minutes. And a total wall-clock budget. ⭐ All
three have to be shorter than the deadline above them and shorter than every proxy idle timeout in the
path, or something upstream kills the connection first and you get a confusing failure.

**5. "What's different about a circuit breaker here?"**

⭐ The failure is often partial. ⭐⭐ Long prompts fail on context limits while short ones succeed; one
model is degraded while another is fine; one tenant's oversized documents trip it for everybody. ⭐ So a
global breaker trips on a problem affecting five percent of traffic and takes down the other
ninety-five — you caused the outage. ⭐⭐ I scope breakers per provider and model, and sometimes per
size bucket. ⭐ Two other differences: an open breaker should route to the next rung, not return an
error, or you've built an outage amplifier with good intentions; and half-open probes cost real money
and produce a real answer, so the probe is a cheap short request rather than a user's eight-thousand-token
prompt.

**6. "You have an abstraction, so switching providers is easy?"**

⭐ The interface is portable; the prompt isn't. ⭐⭐ System-prompt adherence, tool-calling format and
reliability, whether structured output is constrained decoding or a polite request, tokenisation — so
your budgets are wrong — refusal thresholds, how few-shot examples transfer, and whether your prompt
caching strategy exists at all. ⭐ So the fallback needs its own prompt version, its own eval scores
measured *before* the incident, and its own cost and latency numbers. ⭐⭐ And it needs continuous
exercise: we route one percent of production traffic to the fallback permanently. ⭐ A fallback
exercised only during incidents is an untested code path that runs when you can least afford a
surprise — it'll have an expired key, a deprecated model name, or a schema the new provider rejects.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "how do you handle a provider outage?"**

Start with the dependency profile, because it sets expectations. **A model provider isn't like a
database. Published SLAs sit around 99.5 to 99.9 percent, which is hours a month. Failures are
correlated across the industry, so when a major provider is down every competitor is down too. And
degradation beats outage — 429s, twenty-second first tokens and streams that stall mid-answer are far
more common than a clean 503. Some failures are partial: long prompts fail while short ones succeed.**

Then the ladder, which is the actual answer. **So reliability here isn't redundancy, it's a ladder of
increasingly worse answers. Retry for transients. A different region on the same provider — the only
free rung, because it needs no prompt changes. A smaller model. A different provider. A cached answer
labelled with its age. Then the rung everyone skips: the non-AI path — keyword search results, the FAQ,
the document list. That's genuinely useful and completely independent of the failing dependency. And
finally an honest error with a route to a human, which beats a bad answer from a weak model. The rule
that makes the ladder safe is that if the answer is worse, we say so — a silently degraded answer is the
worst outcome available, because the user acts on it believing it's normal quality while the error rate
still reads zero.**

Then the two controls that stop us making it worse. **Retries only on transients, with full jitter, and
a retry budget capped at about ten percent of requests — because retries add load exactly when the
dependency is struggling, so three retries each turns a thirty percent failure rate into double the
traffic against a failing system. And circuit breakers scoped per provider and model rather than
globally, because the failure is often partial and a global breaker trips on a problem affecting five
percent of traffic and takes down the other ninety-five. An open breaker routes to the next rung; it
doesn't return an error.**

Close on the thing that makes it real. **The assumption that breaks most fallback plans is "we have an
abstraction so we can switch providers." The interface is portable; the prompt isn't. Tool-calling
formats, whether structured output is constrained decoding or a polite request, tokenisation so your
budgets are wrong, refusal thresholds. So the fallback carries its own prompt version and its own eval
scores measured before the incident — and we route one percent of production traffic to it permanently.
A fallback exercised only during incidents is an untested code path that runs when you can least afford
a surprise, and it will have rotted: an expired key, a deprecated model name, a schema the new provider
rejects.**
