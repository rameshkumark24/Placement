# Part 1 — ⭐⭐ What persists, and what does not

```
⭐⭐ THE WRITABLE LAYER IS EPHEMERAL AND SLOW.
⭐   ⭐ Gone on `docker rm`, on a pod reschedule, on a node
⭐     failure — ⭐⭐ AND ON EVERY DEPLOY, WHICH IS THE ONE THAT
⭐     ACTUALLY BITES.
⭐   ⭐ Every write to an existing file triggers copy-up
⭐     (Day 362), ⭐⭐ SO A DATABASE ON THE WRITABLE LAYER IS
⭐     BOTH TEMPORARY ***AND*** MEASURABLY SLOWER.

⭐⭐ THREE MOUNT TYPES, AND THEY ARE NOT INTERCHANGEABLE:
⭐   ① ⭐⭐ ***NAMED VOLUME*** — `-v pgdata:/var/lib/postgresql/data`
⭐      ⭐ Managed by the runtime, ⭐ bypasses the union
⭐        filesystem entirely (⭐⭐ SO NO COPY-UP PENALTY),
⭐        ⭐ portable across drivers.
⭐      ⇒ ⭐⭐ THE DEFAULT FOR ANY DATA THAT MUST SURVIVE.
⭐   ② ⭐ ***BIND MOUNT*** — `-v ./src:/app/src`
⭐      ⭐ A host path, exactly as it is.
⭐      ⇒ ⭐⭐ FOR DEVELOPMENT HOT-RELOAD, AND ***ALMOST NEVER***
⭐        IN PRODUCTION — ⭐ it couples the container to the
⭐        host's layout, which is the thing you containerised to
⭐        escape.
⭐      ⇒ ⭐ Two traps: ⭐⭐ IT ***SHADOWS*** WHATEVER THE IMAGE
⭐        PUT THERE (mount over `/app` and your installed venv
⭐        or built assets disappear), ⭐ and on macOS/Windows it
⭐        crosses a VM boundary and is ⭐⭐ 10–50× SLOWER, WHICH
⭐        IS WHY `pytest` FEELS BROKEN IN DOCKER ON A MAC.
⭐   ③ ⭐ ***tmpfs*** — `--tmpfs /tmp`
⭐      ⭐ RAM-backed, vanishes on stop. ⭐⭐ THE COMPANION TO
⭐        `--read-only` (Day 361), and where a read-only
⭐        container writes its scratch files.

⭐⭐ AND THE PRODUCTION QUESTION THAT DECIDES THE DESIGN:
⭐   ***DOES THIS CONTAINER NEED TO BE ON A PARTICULAR MACHINE?***
⭐   ⇒ ⭐⭐ A LOCAL VOLUME PINS IT TO ONE NODE. ⭐ The scheduler
⭐     cannot move it, so you have lost the main operational
⭐     benefit of containers for that workload.
⭐   ⇒ ⭐ Which is why stateless services use ***no*** volumes,
⭐     ⭐ and stateful ones use network storage (EBS, EFS,
⭐     Kubernetes PersistentVolumes) — ⭐⭐ AND WHY "JUST PUT IT
⭐     IN A VOLUME" IS NOT AN ANSWER TO A STATE PROBLEM
⭐     (Day 324).
```

# Part 2 — ⭐⭐ Networking: four modes and the one you use

```
⭐⭐ ① ***BRIDGE*** (default) — a private virtual network with
⭐   NAT to the host.
⭐   ⭐ `-p 8080:8000` is a ***DNAT rule***: host 8080 →
⭐     container 8000.
⭐   ⇒ ⭐⭐ THE CONTAINER IS NOT "ON THE HOST'S NETWORK"; TRAFFIC
⭐     IS TRANSLATED. ⭐ Which is why the app sees the gateway's
⭐     IP as the client address unless you handle
⭐     `X-Forwarded-For` (Day 325).

⭐⭐ ② ***USER-DEFINED BRIDGE*** — ⭐⭐ WHAT COMPOSE CREATES, AND
⭐   THE IMPORTANT ONE.
⭐   ⭐ ⭐⭐ CONTAINERS RESOLVE EACH OTHER ***BY SERVICE NAME***
⭐     VIA AN EMBEDDED DNS SERVER. ⭐ `postgres://db:5432` works
⭐     because `db` is a DNS name on that network.
⭐   ⭐ ⭐⭐ AND THE DNS RECORD UPDATES WHEN A CONTAINER
⭐     RESTARTS WITH A NEW IP — ⭐ which is why caching a
⭐     resolved IP for the lifetime of a pooled connection is
⭐     the Day 341 trap, in miniature.
⭐   ⭐ The default bridge does ***not*** do name resolution,
⭐     which is why "it works in Compose but not with plain
⭐     `docker run`" is a common confusion.

⭐⭐ ③ ***HOST*** — no network namespace; the container uses the
⭐   host's stack directly.
⭐   ⭐ ⭐⭐ NO NAT OVERHEAD, NO PORT MAPPING, AND NO ISOLATION —
⭐     ⭐ a port conflict with the host is now possible, and
⭐     `localhost` inside ***is*** the host's.
⭐   ⇒ ⭐ Legitimate for high-throughput proxies and some
⭐     monitoring agents. ⭐⭐ NOT A DEFAULT, AND NOT AVAILABLE
⭐     IN THE SAME FORM ON DOCKER DESKTOP.

⭐⭐ ④ ***NONE*** — no networking at all. ⭐ For batch jobs that
⭐   must not talk to anything, ⭐⭐ WHICH IS A REAL AND
⭐   UNDER-USED CONTROL FOR PROCESSING UNTRUSTED INPUT.

⭐⭐ AND THE THREE THINGS PEOPLE GET WRONG:
⭐   ⭐ ⭐⭐ `localhost` INSIDE A CONTAINER IS THE CONTAINER.
⭐     ⭐ To reach a service on the host, use
⭐     `host.docker.internal` (Desktop) or the bridge gateway
⭐     IP — ⭐⭐ AND NOTE THIS IS A DEV CONVENIENCE THAT DOES NOT
⭐     EXIST IN PRODUCTION.
⭐   ⭐ ⭐⭐ `EXPOSE` DOCUMENTS; IT DOES NOT PUBLISH. ⭐ Only `-p`
⭐     or the orchestrator's Service does that.
⭐   ⭐ ⭐⭐ BINDING TO `127.0.0.1` INSIDE A CONTAINER MAKES IT
⭐     UNREACHABLE FROM OUTSIDE, ***EVEN WITH `-p`.*** ⭐ You
⭐     must bind `0.0.0.0`. ⭐ This is the single most common
⭐     "my container starts but I get connection refused" bug,
⭐     ⭐ and it is why every uvicorn command in this curriculum
⭐     says `--host 0.0.0.0`.
```

# Part 3 — ⭐⭐ Configuration: what goes where

```
⭐⭐ THE PARTITION, AND IT IS THE WHOLE DAY:
⭐   ⭐ ⭐⭐ ***IN THE IMAGE***: anything identical in every
⭐     environment — code, dependencies, default settings, the
⭐     entrypoint.
⭐   ⭐ ⭐⭐ ***INJECTED AT RUN TIME***: anything that differs —
⭐     database URL, log level, feature flags, replica-specific
⭐     values, ⭐ and every secret.
⭐   ⇒ ⭐⭐ THE TEST: ***CAN I PROMOTE THIS EXACT IMAGE DIGEST
⭐     FROM STAGING TO PRODUCTION WITHOUT REBUILDING?*** ⭐ If
⭐     not, something environment-specific is baked in, and
⭐     Day 283's promotion model is broken.

⭐⭐ THE FOUR INJECTION MECHANISMS:
⭐   ① ⭐⭐ ***ENVIRONMENT VARIABLES*** — universal, simple, and
⭐      the 12-factor default.
⭐      ⭐ ✘ ⭐⭐ VISIBLE IN `docker inspect`, IN `/proc/<pid>/
⭐        environ`, AND INHERITED BY ***EVERY CHILD PROCESS*** —
⭐        including a subprocess you shell out to.
⭐      ⭐ ✘ Strings only; ⭐ no structure, no rotation.
⭐   ② ⭐ ***MOUNTED FILES*** — a config file or secret mounted
⭐      as a volume.
⭐      ⭐ ✔ Structured, ⭐⭐ AND CAN BE UPDATED WITHOUT A
⭐        RESTART IF THE APP WATCHES THE FILE.
⭐      ⭐ ✔ ⭐⭐ AND NOT INHERITED BY CHILD PROCESSES, WHICH IS
⭐        A REAL SECURITY ADVANTAGE FOR SECRETS.
⭐   ③ ⭐ ***A CONFIG SERVICE*** fetched at startup — dynamic,
⭐      ⭐⭐ AND A NEW STARTUP DEPENDENCY, SO IT NEEDS A CACHED
⭐      FALLBACK (Day 339's static stability).
⭐   ④ ⭐⭐ ***A SECRETS MANAGER*** fetched at startup or via a
⭐      sidecar — the right answer for credentials (Day 372).

⭐⭐ THE PRECEDENCE ORDER THAT AVOIDS ARGUMENTS:
⭐   ***DEFAULTS IN CODE < CONFIG FILE < ENVIRONMENT <
⭐      EXPLICIT OVERRIDE***, ⭐⭐ AND ***VALIDATE ALL OF IT AT
⭐      STARTUP AND CRASH IF IT IS WRONG.***
⭐   ⇒ ⭐⭐ A SERVICE THAT STARTS WITH A MISSING DATABASE URL AND
⭐     FAILS ON THE FIRST REQUEST IS STRICTLY WORSE THAN ONE
⭐     THAT REFUSES TO START — ⭐ because the orchestrator will
⭐     happily roll out the broken version and mark it healthy.
```

```python
# ⭐ Pydantic Settings — validation at startup, one place
class Settings(BaseSettings):
    database_url: PostgresDsn                    # ⭐⭐ TYPED
    redis_url: RedisDsn
    log_level: Literal["DEBUG","INFO","WARNING","ERROR"] = "INFO"
    workers: int = Field(default=4, ge=1, le=64)  # ⭐ bounded
    secret_key: SecretStr                        # ⭐⭐ NOT IN repr()

    model_config = SettingsConfigDict(env_file=".env", extra="forbid")
    # ⭐⭐ `extra="forbid"` CATCHES THE TYPO `DATBASE_URL` AT
    # ⭐   STARTUP INSTEAD OF SILENTLY USING THE DEFAULT.

settings = Settings()      # ⭐⭐ IMPORT-TIME CRASH IF INVALID
```

# Part 4 — ⭐ The container's own configuration

```
⭐⭐ THINGS THAT ARE CONFIGURATION BUT DO NOT LOOK LIKE IT:
⭐   ⭐ ***RESOURCE LIMITS*** (Day 361) — ⭐⭐ AND THE WORKER
⭐     COUNT MUST BE DERIVED FROM THEM, NOT FROM
⭐     `os.cpu_count()`.
⭐   ⭐ ***`STOPSIGNAL`*** — defaults to SIGTERM; ⭐ some
⭐     applications want SIGQUIT for a graceful drain (⭐⭐ NGINX
⭐     AND GUNICORN BOTH TREAT SIGQUIT AS "FINISH IN-FLIGHT AND
⭐     STOP").
⭐   ⭐ ***THE STOP GRACE PERIOD*** — ⭐⭐ MUST EXCEED YOUR
⭐     READINESS-OFF SLEEP + p99 REQUEST TIME + POOL CLOSE
⭐     (Day 324). ⭐ The default 10 s is often too short and it
⭐     is a one-line fix.
⭐   ⭐ ***TIMEZONE AND LOCALE*** — ⭐⭐ CONTAINERS DEFAULT TO
⭐     UTC, WHICH IS CORRECT — ⭐ and it means a container can
⭐     disagree with a host you were comparing logs against.
⭐   ⭐ ***`ulimit nofile`*** — ⭐⭐ AN ASYNC PYTHON SERVICE WITH
⭐     THOUSANDS OF CONNECTIONS HITS THE FILE-DESCRIPTOR LIMIT
⭐     AND FAILS WITH `OSError: [Errno 24] Too many open
⭐     files`, ⭐ which reads like an application bug and is not.
⭐   ⭐ ***DNS OPTIONS*** — ⭐⭐ KUBERNETES' DEFAULT `ndots:5`
⭐     MEANS `api.example.com` IS TRIED WITH ***FIVE SEARCH
⭐     SUFFIXES FIRST***, so every external lookup costs
⭐     multiple failed queries. ⭐ A real and commonly-missed
⭐     latency source; fix with a trailing dot or a custom
⭐     `dnsConfig`.

⭐⭐ AND THE HEALTHCHECK QUESTION:
⭐   ⭐ Docker's `HEALTHCHECK` is useful for Compose;
⭐     ⭐⭐ IN KUBERNETES IT IS IGNORED — THE ORCHESTRATOR'S
⭐     PROBES ARE WHAT COUNT (Day 378).
⭐   ⇒ ⭐ Define liveness and readiness ***separately*** (Day
⭐     325), ⭐⭐ AND NEVER LET LIVENESS TOUCH A DEPENDENCY.
```

# Part 5 — ⭐⭐ Development vs production, without two Dockerfiles

```
⭐⭐ THE TEMPTATION: `Dockerfile.dev` and `Dockerfile.prod`.
⭐   ⇒ ⭐⭐ THEY DIVERGE. ⭐ Within two months dev has a
⭐     dependency prod does not, and a bug appears only in
⭐     production — ⭐⭐ WHICH IS EXACTLY THE FAILURE
⭐     CONTAINERS WERE ADOPTED TO PREVENT.

⭐⭐ THE ANSWER: ***ONE DOCKERFILE, MULTIPLE TARGETS*** (Day
⭐   363).
⭐   ⭐ `--target dev` adds dev dependencies and a reload
⭐     command; ⭐ `--target prod` is the shipped image.
⭐   ⭐ ⭐⭐ SAME BASE, SAME DEPENDENCY RESOLUTION, SAME LAYER
⭐     ORDER.

⭐⭐ AND WHAT LEGITIMATELY DIFFERS IN DEV — ⭐ name these
⭐   explicitly rather than letting them drift:
⭐   ⭐ A bind mount for source, so edits are visible without a
⭐     rebuild.
⭐   ⭐ `--reload`, ⭐⭐ WHICH MUST NEVER BE ON IN PRODUCTION —
⭐     it watches the filesystem, uses more memory, and
⭐     restarts workers on a stray file write.
⭐   ⭐ Debug ports, ⭐ verbose logging, ⭐ seeded data.
⭐   ⭐ ⭐⭐ AND THE ONE THAT CATCHES PEOPLE: A BIND MOUNT OVER
⭐     `/app` HIDES THE IMAGE'S INSTALLED PACKAGE. ⭐ Mount only
⭐     the source subdirectory, ⭐ or install the project in
⭐     editable mode and keep the venv outside the mounted path
⭐     — ⭐⭐ WHICH IS EXACTLY WHY DAY 363 PUT THE VENV IN
⭐     `/opt/venv` RATHER THAN `/app/.venv`.
```

# Part 6 — ⭐ Compose networks and dependency ordering

```
⭐⭐ COMPOSE CREATES ONE USER-DEFINED BRIDGE PER PROJECT, ⭐ so
⭐   every service resolves every other by name. ⭐ That is 90%
⭐   of what you need.

⭐⭐ THE ORDERING TRAP — ⭐ and it is the most common Compose
⭐   bug:
⭐   ⭐ ⭐⭐ `depends_on` WAITS FOR THE CONTAINER TO ***START***,
⭐     NOT FOR THE SERVICE INSIDE IT TO BE ***READY***.
⭐   ⇒ ⭐ Postgres takes 3–10 seconds to accept connections;
⭐     ⭐⭐ YOUR APP CONNECTS AT SECOND ONE AND CRASHES.
⭐   ⇒ FIXES, IN ORDER OF QUALITY:
⭐      ⭐ (a) ⭐⭐ `depends_on: condition: service_healthy` PLUS
⭐        A REAL `healthcheck` ON THE DEPENDENCY. ⭐ Correct for
⭐        Compose.
⭐      ⭐ (b) ⭐⭐ ***RETRY ON CONNECT IN THE APPLICATION*** —
⭐        which is the ***right*** answer, because ⭐⭐ IN
⭐        PRODUCTION THERE IS NO `depends_on` AT ALL, AND YOUR
⭐        DATABASE WILL RESTART UNDERNEATH YOU EVENTUALLY.
⭐      ⭐ (c) A wait-for-it script — ⭐ works, and papers over
⭐        (b).
⭐   ⇒ ⭐⭐ SAY (b) IN AN INTERVIEW: ***"ORDERING TOOLS HIDE A
⭐     MISSING RETRY, AND THE RETRY IS WHAT PRODUCTION ACTUALLY
⭐     NEEDS."***

⭐⭐ AND NETWORK SEGMENTATION, WHICH IS FREE AND SKIPPED:
⭐   ⭐ Put the database on an ***internal*** network with no
⭐     published ports; ⭐ put only the proxy on the network with
⭐     external access.
⭐   ⇒ ⭐⭐ THEN "DID SOMEONE EXPOSE POSTGRES TO THE INTERNET?"
⭐     IS ANSWERED BY THE TOPOLOGY RATHER THAN BY VIGILANCE.
⭐   ⇒ ⭐ Day 341's network-policy argument, at Compose scale.
```

# Part 7 — ⭐ The volume operations nobody plans for

```
⭐⭐ FOUR THINGS THAT WILL HAPPEN:
⭐   ① ⭐⭐ BACKUP. ⭐ A named volume is not backed up by
⭐      anything. ⭐ `docker run --rm -v pgdata:/data -v
⭐      $PWD:/backup alpine tar czf /backup/db.tgz /data` —
⭐      ⭐⭐ AND FOR A DATABASE, USE ITS OWN DUMP TOOL, BECAUSE
⭐      TARRING A LIVE DATA DIRECTORY GIVES YOU AN INCONSISTENT
⭐      COPY THAT ***APPEARS*** TO WORK.
⭐   ② ⭐⭐ RESTORE — ⭐ and the only backup that counts is one
⭐      you have restored. ⭐ Day 286's timed restore.
⭐   ③ ⭐ PERMISSIONS. ⭐⭐ A NON-ROOT CONTAINER CANNOT WRITE TO A
⭐      VOLUME OWNED BY ROOT. ⭐ Fix the ownership at volume
⭐      creation or use an init container — ⭐ and note that
⭐      Kubernetes' `fsGroup` exists precisely for this.
⭐   ④ ⭐ GROWTH. ⭐⭐ VOLUMES FILL SILENTLY AND THE FIRST SYMPTOM
⭐      IS A DATABASE THAT CANNOT WRITE. ⭐ Alert on filesystem
⭐      usage, ⭐ and remember Day 348's point that some systems
⭐      cannot recover by deleting data once the disk is full.

⭐⭐ AND THE CLEANUP THAT SAVES A LAPTOP:
⭐   ⭐ `docker system df` ⇒ what is actually using space.
⭐   ⭐ `docker system prune -a --volumes` ⇒ ⭐⭐ AND READ THAT
⭐     FLAG CAREFULLY — `--volumes` DELETES YOUR LOCAL DATABASE
⭐     DATA. ⭐ It is the single most common self-inflicted data
⭐     loss in development.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Binding to `127.0.0.1` inside a container | Unreachable from outside even with `-p`. The commonest connection-refused bug |
| ⭐⭐ Expecting `EXPOSE` to publish a port | It documents. Only `-p` or a Service publishes |
| ⭐ Reaching the host on `localhost` | `localhost` is the container. And `host.docker.internal` doesn't exist in production |
| ⭐⭐ `depends_on` without a health condition | It waits for the container to start, not the service to be ready |
| ⭐⭐ Fixing startup ordering instead of adding a retry | Production has no `depends_on`, and your database will restart eventually |
| ⭐ Bind mount over `/app` | It shadows the image's installed package and your built assets vanish |
| ⭐ Bind mounts in production | Couples the container to the host's layout — the thing you containerised to escape |
| ⭐⭐ Local volumes for a service you want rescheduled | It's pinned to one node; the scheduler can't move it |
| ⭐ Secrets in environment variables | Visible in `inspect` and `/proc`, and inherited by every child process |
| ⭐⭐ Config that fails on first request rather than at startup | The orchestrator rolls out the broken version and marks it healthy |
| ⭐ No `extra="forbid"` on settings | A typo'd env var silently uses the default |
| ⭐⭐ Separate dev and prod Dockerfiles | They diverge within two months, reintroducing the bug containers prevented |
| ⭐ `--reload` in production | Watches the filesystem, uses more memory, restarts on a stray write |
| ⭐⭐ Tarring a live database volume | An inconsistent copy that appears to work until you need it |
| ⭐ `docker system prune --volumes` without reading it | Deletes your local database data |

## Interview questions

**1. "What persists in a container and what doesn't?"**
> ⭐ Only what's in a volume. ⭐⭐ The writable layer is gone on `rm`, on a reschedule, and on every
> deploy — **and it's slow, because writing to an existing file triggers copy-up**, so a database on
> the writable layer is both temporary and measurably slower. ⭐ Named volumes for data that must
> survive, since they bypass the union filesystem; bind mounts for development only; tmpfs as the
> companion to a read-only root. ⭐⭐ And the design question: **a local volume pins the container to
> one node**, so the scheduler can't move it.

**2. "How do containers find each other?"**
> ⭐ On a user-defined bridge — which is what Compose creates — **an embedded DNS server resolves
> service names**, so `postgres://db:5432` works. ⭐ The default bridge doesn't do name resolution,
> which is why things work in Compose and not with plain `docker run`. ⭐⭐ And the record updates when
> a container restarts with a new IP, **which is why a pooled connection caching a resolved address is
> the DNS-failover trap in miniature.**

**3. "My container starts but I get connection refused."**
> ⭐⭐ Almost always binding to `127.0.0.1` inside the container. **`-p` forwards to the container's
> interface, and a process listening only on loopback isn't on it** — you have to bind `0.0.0.0`.
> ⭐ That's why every uvicorn command here says `--host 0.0.0.0`. ⭐ Second candidate: `EXPOSE` without
> `-p`, since `EXPOSE` only documents.

**4. "What belongs in the image and what's injected?"**
> ⭐⭐ Anything identical in every environment goes in; anything that differs comes from outside.
> **The test is whether I can promote this exact digest from staging to production without
> rebuilding** — if not, something environment-specific is baked in and the promotion model is broken.
> ⭐ Env vars are the default but are visible in `inspect` and inherited by every child process, so
> secrets prefer mounted files or a secrets manager. ⭐⭐ And all of it is **validated at startup with a
> crash on failure, because a service that starts broken and fails on the first request gets rolled
> out and marked healthy.**

**5. "Compose: how do you handle service startup order?"**
> ⭐ `depends_on` alone waits for the container to start, not the service to be ready, so the app
> connects at second one and crashes. ⭐ `condition: service_healthy` with a real healthcheck fixes it
> in Compose. ⭐⭐ But the right answer is **retry-on-connect in the application** — because production
> has no `depends_on` at all and the database will restart underneath you eventually. **Ordering tools
> hide a missing retry, and the retry is what production actually needs.**

**6. "Dev and prod differences — how do you manage them?"**
> ⭐⭐ One Dockerfile with multiple targets, never two files — **two files diverge within two months and
> you get a bug that only appears in production, which is exactly what containers were adopted to
> prevent.** ⭐ Dev legitimately adds a source bind mount, `--reload`, debug ports and seed data. ⭐ And
> the trap: **a bind mount over `/app` shadows the image's installed package**, which is why the venv
> lives in `/opt/venv` rather than inside the mounted directory.

## 🎙️ Articulation drill

**Two minutes.** Start from the principle: **the image is the part that's identical everywhere, so
anything that differs between environments has to arrive at run time** — and the test is whether you
can promote the same digest from staging to production without rebuilding. On storage: only volumes
persist, the writable layer is gone on every deploy and slow because of copy-up, ⭐ and **a local volume
pins the container to one node**, which costs you the scheduling benefit you containerised for. On
networking, give the three things people get wrong: **`localhost` inside a container is the container;
`EXPOSE` documents rather than publishes; and binding to `127.0.0.1` makes the app unreachable even
with `-p`** — that last one is the commonest connection-refused bug there is. Note that Compose's
user-defined bridge gives DNS by service name, which the default bridge doesn't. On configuration:
env vars are the 12-factor default but are visible in `inspect` and inherited by every child process,
so secrets prefer files — **and everything gets validated at startup with a crash, because a service
that starts broken and fails on the first request gets rolled out and marked healthy.** Close on the
Compose ordering answer, because it generalises: **`depends_on` waits for the container, not the
service — and the real fix is retry-on-connect, because production has no `depends_on` and your
database will restart underneath you eventually.**
