# Day 037

**L-037** · ⭐ **Strings** — immutability, interning, encoding, `str` vs `bytes`, and why `+=` is O(n²)

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `str` is a sequence of Unicode code points; `bytes` is a sequence of
> numbers. Encoding converts the first to the second, and every `UnicodeDecodeError` you will ever
> see is someone who forgot which one they had.**
>
> ⭐ This is a backend day disguised as a language day. **Files, HTTP bodies, database drivers,
> subprocess output and CSV imports all hand you bytes**, and the moment you guess at the encoding
> you have a production bug that only fires on one customer's data.

# Part 1 — ⭐ Immutability and its consequences

```python
s = "hello"
s[0] = "H"          # ⭐⭐ TypeError — strings are immutable (Day 025)
s = "H" + s[1:]     # ⭐ rebinds to a NEW string
```

```
⭐⭐ THE QUADRATIC TRAP — the one that costs you a DSA round:
⭐   out = ""
⭐   for piece in pieces: out += piece      ⇒ ⭐⭐ a NEW string, copying everything, EVERY iteration
⭐   ⇒ 1 + 2 + 3 + ... + n = ⭐⭐ O(n²)
⭐
⭐ ⭐⭐ THE FIX:  "".join(pieces)   ⇒ ⭐ ONE pass to total the length, ONE allocation, ONE copy ⇒ O(n)
```

⚠️ ⭐⭐ **CPython has an optimisation that makes this worse, not better:** when the string's refcount
is exactly 1, `s += x` can resize in place, so the loop *is* fast — until someone keeps another
reference, or you run on PyPy, and it silently becomes quadratic again. **Never depend on it.**

```python
# ⭐ Building strings — in preference order:
"".join(parts)                        # ⭐⭐ the default
f"{a} and {b}"                        # ⭐ for a fixed small number of pieces
io.StringIO()                          # ⭐ when you are writing incrementally in a stream shape
```

⭐ **Interning (Day 028)** applies here: identifier-like literals share one object, which is why `is`
appears to work on strings and must not be trusted. `sys.intern` is for parsing workloads with
millions of duplicates.

# Part 2 — ⭐⭐ `str` vs `bytes` — the distinction that matters most

```
⭐⭐ str    = a sequence of UNICODE CODE POINTS. Abstract. No bytes involved. "é" is ONE element.
⭐⭐ bytes  = a sequence of INTEGERS 0–255. Concrete. What files, sockets and disks actually hold.

⭐   str ──.encode("utf-8")──▶ bytes            ⭐⭐ ENCODE = go OUT of your program
⭐   bytes ──.decode("utf-8")──▶ str            ⭐⭐ DECODE = come IN to your program
⭐
⭐ ⭐⭐ THE MNEMONIC: str is what you THINK in, bytes is what you TRANSMIT.
```

```python
s = "café"
len(s)                    # ⭐ 4 — four code points
b = s.encode("utf-8")
b                         # ⭐ b'caf\xc3\xa9'
len(b)                    # ⭐⭐ 5 — é takes TWO bytes in UTF-8
b.decode("utf-8")         # "café"
b.decode("ascii")         # ⭐⭐ UnicodeDecodeError
b.decode("latin-1")       # ⭐⭐ "cafÃ©" — ⚠️ NO ERROR, and WRONG. This is mojibake.
```

⚠️ ⭐⭐ **The `latin-1` case is the important one: decoding with the wrong encoding does not always
fail.** Latin-1 maps every byte to a character, so it *never* raises — it just silently produces
garbage that gets written to your database and discovered six months later. **An exception would have
been the kind outcome.**

| ⭐ Encoding | ⭐ Note |
|---|---|
| ⭐⭐ **UTF-8** | ⭐⭐ **the answer.** ASCII-compatible, variable width 1–4 bytes, the web's default |
| UTF-16 | 2 or 4 bytes; used internally by Java/JS/Windows APIs |
| ⭐ Latin-1 | ⭐⭐ never raises on decode ⇒ **silently corrupts** |
| ⭐ `cp1252` | ⚠️ ⭐⭐ **Windows' default locale encoding** — the source of most surprises |
| ASCII | 7-bit; raises on anything above 127 |

```python
# ⚠️⚠️ ⭐⭐ THE PORTABILITY BUG THAT BITES EVERY WINDOWS DEVELOPER:
open("data.csv")                          # ⭐⭐ uses the LOCALE encoding — cp1252 on Windows, utf-8 on Linux
open("data.csv", encoding="utf-8")        # ⭐⭐ ALWAYS PASS IT. Every time. No exceptions.
```

⭐⭐ **"Always pass `encoding=`" is the single most valuable habit on this page.** The same code
reads correctly on your Linux CI and corrupts data on a Windows machine, and the failure appears as
weird characters in a report rather than as an error. ⭐ *(Python 3.15 makes UTF-8 the default; until
then, and for any code that must run on older versions, be explicit.)*

```python
# ⭐ When you must survive bad data:
b.decode("utf-8", errors="replace")   # ⭐ bad bytes ⇒ U+FFFD "�" — visible, lossy
b.decode("utf-8", errors="ignore")    # ⚠️ ⭐⭐ silently DROPS bytes — almost never right
b.decode("utf-8", errors="strict")    # ⭐ the default — raise
```

⭐⭐ **Prefer `strict` and fix the source.** `errors="ignore"` converts a data problem into a
*quieter* data problem, which is the wrong direction.

# Part 3 — ⭐ Unicode is harder than "one character"

```python
len("👍")            # ⭐ 1 code point (Python 3 handles this correctly)
len("é")             # ⭐ 1 — if it is U+00E9
len("é")             # ⭐⭐ 2 — if it is "e" + U+0301 COMBINING ACUTE. IDENTICAL ON SCREEN.
"é" == "é"           # ⭐⭐ False. Same appearance, different code points.

import unicodedata
unicodedata.normalize("NFC", s)     # ⭐⭐ compose ⇒ compare, store, and index in ONE form
```

⚠️ ⭐⭐ **Normalise at the boundary.** Usernames, email addresses, search terms and dedupe keys must
be normalised (NFC) on input, or "the same" string fails to match itself. **This is a real
authentication bug**: a user registers with a composed `é` and logs in with a decomposed one.

⭐ **Case:** `.lower()` is for display; **`.casefold()` is for comparison** — it handles cases
`.lower()` does not (German `ß` → `ss`). ⚠️ And Turkish dotless `ı` means **case-insensitive
comparison is locale-dependent** — one more reason security decisions should not rest on string
casing.

```python
# ⭐ The methods worth having in your fingers:
s.strip() / .lstrip() / .rstrip()     # ⚠️ ⭐ strip("abc") strips any of those CHARACTERS, not the prefix
s.removeprefix("api/") / .removesuffix(".json")    # ⭐⭐ 3.9+ — what people wrongly used strip for
s.split(",")           # ⭐ split() with no args splits on ANY whitespace and drops empties
s.split(",", 1)        # ⭐ maxsplit
s.partition("=")       # ⭐⭐ always a 3-tuple — great for "key=value" parsing
s.startswith(("a","b"))   # ⭐ accepts a tuple
s.replace(a, b) / .find(x) / .index(x)    # ⭐ find returns -1; index raises
"".join(...) / s.zfill(3) / s.center(20)
```

⭐⭐ **`removeprefix` deserves the star**, because `"api/users".strip("api/")` does *not* remove the
prefix — it strips any of the characters `a`, `p`, `i`, `/` from both ends, which gives `"users"` by
coincidence and mangles other inputs. **A genuine bug that looks like it works.**

# Part 4 — ⭐ Formatting, and where strings meet the outside world

```python
name, n = "ada", 3.14159
f"{name} has {n:.2f}"          # ⭐⭐ f-strings — fastest and clearest
f"{n=}"                        # ⭐⭐ "n=3.14159" — the debugging spec, 3.8+
f"{n:>10,.2f}"                 # align, thousands separator, precision
f"{value!r}"                   # ⭐ repr — Day 031
"{} {}".format(a, b)           # ⭐ when the template is not a literal
"%s" % (a,)                    # ⭐ legacy; still what the logging module uses
```

⭐⭐ **Logging is the exception to f-strings**, and it matters:

```python
log.info(f"user {user_id} did {action}")     # ⚠️ ⭐ formats even when the level is disabled
log.info("user %s did %s", user_id, action)  # ⭐⭐ deferred — formatted only if it is emitted
```

⚠️⚠️ ⭐⭐ **And never f-string user input into SQL, HTML or a shell command** — that is injection in
each of the three cases (Days 012, Stage 3, Stage 5). **Parameterised queries, autoescaping
templates, `subprocess` with a list of arguments.**

```python
# ⭐ bytes has its own literals and its own methods:
b"abc"; rb"\d+"                # ⭐ regexes on bytes need bytes patterns
b.hex(); bytes.fromhex("ff00")
import base64; base64.b64encode(b)     # ⭐⭐ ENCODING, NOT ENCRYPTION. It is reversible by anyone.
bytearray(b"abc")              # ⭐ the MUTABLE version — for building binary buffers efficiently
```

⭐⭐ **"Base64 is encoding, not encryption"** — worth saying plainly, because base64 in a config file
gets mistaken for a secured secret regularly.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`s += x` in a loop** | ⭐⭐ O(n²). `"".join(parts)`. The CPython optimisation is a trap. |
| ⭐⭐ **`open()` without `encoding=`** | ⭐⭐ Locale-dependent — cp1252 on Windows. Always pass it. |
| Decoding with the wrong codec | ⭐⭐ Latin-1 never raises; it silently corrupts. |
| `errors="ignore"` | ⭐ Turns a loud data problem into a quiet one. |
| Confusing `str` and `bytes` | ⭐ Encode going out, decode coming in. |
| Assuming `len` counts characters | ⭐⭐ Code points — combining marks make two look like one. |
| Not normalising at the boundary | ⭐⭐ "Equal-looking" strings compare unequal. |
| `.lower()` for comparison | ⭐ `.casefold()`, and beware locale. |
| ⭐ `strip("prefix")` | ⭐⭐ Strips characters, not a prefix. `removeprefix`. |
| f-strings in logging calls | ⭐ Formats even when the log is suppressed. |
| f-strings into SQL/HTML/shell | ⭐⭐ Injection. Parameterise or escape. |
| Treating base64 as encryption | ⭐ It is encoding. Anyone can reverse it. |

## Interview questions

**Q: `str` versus `bytes`?**
> `str` is a sequence of Unicode code points — an abstract text type with no encoding attached.
> `bytes` is a sequence of integers 0–255, which is what actually exists in files, sockets and
> databases. Encoding turns text into bytes on the way out; decoding turns bytes into text on the way
> in. Python 3's separation of the two is the reason encoding bugs surface at the boundary rather
> than deep inside the program, which is a genuine improvement over Python 2.

**Q: Why is string concatenation in a loop a problem?**
> Strings are immutable, so each `+=` allocates a new string and copies everything accumulated so
> far — quadratic overall. `"".join` computes the total length once, allocates once, and copies once,
> which is linear. There's a CPython optimisation that resizes in place when the refcount is exactly
> one, and I'd treat that as a hazard rather than a feature: the code is fast until a stray reference
> or a different interpreter makes it silently quadratic again.

**Q: What causes a `UnicodeDecodeError` in production?**
> Bytes decoded with the wrong codec — most often data that's UTF-8 being read as ASCII or as the
> platform's locale encoding. The worse case is the one that doesn't raise: Latin-1 maps every
> possible byte to some character, so decoding UTF-8 as Latin-1 succeeds and produces mojibake that
> gets written to the database and found months later. An exception would have been the kind outcome.
> The fix is to be explicit about encoding everywhere, especially in `open()`, which otherwise uses
> the locale — cp1252 on Windows and UTF-8 on Linux, so the same code corrupts data on one platform
> and not the other.

**Q: Why can two strings look identical and compare unequal?**
> Unicode normalisation. An accented character can be a single composed code point or a base letter
> plus a combining mark, and both render identically. `len` differs, equality fails, and dictionary
> lookups miss. The fix is to normalise — usually NFC — at the system boundary, before storing or
> comparing. It's a real authentication bug: someone registers with one form and logs in with the
> other.

**Q: Why not use f-strings in logging calls?**
> Because the f-string is evaluated before the logging call, so the formatting cost is paid even when
> the level is disabled — and in a debug log inside a hot loop that's real overhead. Passing the
> format string and arguments separately lets logging defer it until it knows the record will
> actually be emitted. It also keeps the message template stable, which is what log aggregators group
> on.

## 🎙️ Articulation drill

Record two minutes: **"A user reports strange characters in a CSV export. Walk me through it."**

⭐ Start by naming the layer, because that is the whole diagnosis: **this is an encoding mismatch —
somewhere, bytes were decoded with a different codec than the one they were encoded with.** ⭐ Then
the usual suspects in order: an `open()` with no explicit `encoding` picking up the platform locale,
UTF-8 data read as cp1252 or Latin-1, or a database column and driver disagreeing.

⭐⭐ **Then the observation that makes it a real answer:** *"the reason this reaches a user at all is
that the wrong decode often doesn't raise. Latin-1 maps every byte to some character, so it succeeds
and produces garbage — the data is corrupted at the point of reading and everything downstream is
faithfully storing nonsense. An exception would have caught it at the boundary."*

⭐ Close on the habit: **be explicit about encoding at every boundary — files, HTTP, the database
driver — and normalise text to NFC on input so the same string always compares equal to itself.**
