# Day 120

**L-120** · **Error contracts** — problem details, ⭐⭐ why clients must branch on a code, and what an error must never leak

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: your errors are part of your API, so a client will write code against
> them — and if the only stable thing you give them is prose, they will parse your prose, and you can
> never reword an error message again.**
>
> ⭐ Day 060 was error handling inside the process. **Today is the contract that crosses the wire**,
> and it is the part of an API that is designed last and regretted first.

---

# Part 1 — ⭐ The problem with ad-hoc errors

```json
{"error": "not found"}                                   ⭐ endpoint A
{"message": "User does not exist", "success": false}     ⭐ endpoint B
{"errors": ["invalid email"]}                            ⭐ endpoint C
"Internal Server Error"                                  ⭐ endpoint D — not even JSON
```

```
⭐⭐ FOUR SHAPES IN ONE API MEANS EVERY CLIENT WRITES FOUR PARSERS, AND THE COST
⭐   COMPOUNDS IN A SPECIFIC WAY:
⭐   ⇒ ⭐ the client cannot write ONE error handler, so error handling ends up
⭐        copied per call site — and then diverges.
⭐   ⇒ ⭐⭐ THEY START MATCHING ON PROSE: `if "does not exist" in msg`. ⭐⭐ NOW
⭐        YOUR ERROR MESSAGES ARE AN API YOU CANNOT CHANGE. Fixing a typo breaks
⭐        production for someone else, and you will not find out for months.
⭐   ⇒ ⭐ mobile clients are the worst case: an old version lives on phones for
⭐        years, so a message you reworded is still being matched in 2029.
⭐   ⇒ ⭐⭐ SO THE FIX IS TO GIVE THEM SOMETHING STABLE AND MACHINE-READABLE THAT
⭐        IS *NOT* THE MESSAGE.
```

# Part 2 — ⭐⭐ One shape, with a code

```json
{
  "type":       "https://api.example.com/errors/insufficient-funds",
  "title":      "Insufficient funds",
  "status":     409,
  "code":       "insufficient_funds",
  "detail":     "Your balance is £12.40 and the transfer is £50.00.",
  "instance":   "/accounts/42/transfers",
  "request_id": "01J7ZK3M8Q…",
  "balance":    "12.40"
}
```

```
⭐⭐ THAT IS RFC 7807 / RFC 9457 "PROBLEM DETAILS" PLUS TWO ADDITIONS. THE
⭐   FIELDS, AND WHO EACH IS FOR:
⭐   `type`       ⭐ a URI identifying the KIND of problem — ⭐ ideally one that
⭐                  actually resolves to documentation
⭐   `title`      ⭐ a short, stable, human summary — the same for every instance
⭐   `status`     ⭐ mirrors the HTTP status, so it survives being logged alone
⭐   ⭐⭐ `code`   ⭐⭐ THE FIELD CLIENTS BRANCH ON. Stable, snake_case, documented
⭐   `detail`     ⭐⭐ THIS instance, for a HUMAN — ⭐ free to reword, ever
⭐   `instance`   which resource it happened to
⭐   ⭐ `request_id` ⭐⭐ Day 099A — the single most useful field in a support ticket
⭐   extensions   ⭐ typed extras the client can use (`balance`, `retry_after`)
⭐
⭐ ⇒ ⭐⭐ THE CONTRACT IN ONE LINE: **CLIENTS BRANCH ON `code`; HUMANS READ
⭐     `detail`.** ⭐ Document that explicitly, because if you do not say it,
⭐     someone will match on `detail` anyway.
⭐ ⇒ ⭐ send it as `Content-Type: application/problem+json` so intermediaries and
⭐     generated clients recognise it.
```

```python
class APIError(Exception):                       # ⭐ one hierarchy (Days 059, 112)
    status = 500
    code = "internal_error"
    title = "Internal server error"

class InsufficientFunds(APIError):
    status, code, title = 409, "insufficient_funds", "Insufficient funds"
    def __init__(self, balance, required):
        self.extra = {"balance": str(balance), "required": str(required)}
        super().__init__(f"Balance {balance} is less than {required}")
```

⭐⭐ **One exception hierarchy, one handler, one shape** — registered on the MRO-walking registry from
Day 112. ⭐ **The consistency is not aesthetic: it is what lets a client write exactly one error
handler**, and what lets you add a new error type without touching any client.

# Part 3 — ⭐⭐ What an error must never leak

```python
# ⚠️⚠️ ⭐⭐ EVERY ONE OF THESE HAS SHIPPED, REPEATEDLY:
{"error": "Traceback (most recent call last): File \"/srv/app/…"}   # ⭐ paths, versions
{"error": "duplicate key value violates unique constraint \"users_email_key\""}
{"error": "connection to server at \"10.0.3.14\", port 5432 failed"}
{"error": "No user with email alice@example.com"}                   # ⭐⭐ enumeration
{"error": "Invalid token: expected signature 3f8a… got 91bb…"}      # ⭐ an oracle
```

```
⭐⭐ EACH LEAKS SOMETHING SPECIFIC AND USEFUL TO AN ATTACKER:
⭐   · ⭐ A TRACEBACK ⇒ file paths, library versions to look up CVEs for, your
⭐        directory layout, and sometimes credentials in a repr (Day 105).
⭐   · ⭐⭐ A DATABASE ERROR ⇒ table names, column names, constraint names — ⭐ a
⭐        free schema dump, one field at a time, and the starting point for
⭐        SQL injection (Day 127).
⭐   · ⭐ INTERNAL HOSTS AND PORTS ⇒ your network layout, and SSRF targets.
⭐   · ⭐⭐ "NO USER WITH THAT EMAIL" ⇒ account enumeration (Day 114), from an
⭐        endpoint nobody thought of as an auth endpoint.
⭐   · ⭐ COMPARISON DETAIL ⇒ an oracle: anything that reports HOW CLOSE you were
⭐        turns guessing into search.
⭐
⭐ ⭐⭐ THE RULE, AND IT IS SHARP: **4xx MAY BE SPECIFIC, 5xx MUST BE GENERIC.**
⭐   ⇒ ⭐ a 4xx is the client's mistake and telling them how to fix it is the
⭐        entire point — with the enumeration exception above.
⭐   ⇒ ⭐⭐ A 5xx IS YOUR BUG, AND THE CLIENT CAN DO NOTHING WITH THE DETAIL.
⭐        Log it in full with the traceback; return `{"code":"internal_error",
⭐        "request_id":"…"}`. ⭐ The request id is what turns a useless generic
⭐        message into a two-minute investigation (Day 099A).
```

⭐ **Never let an ORM or driver exception reach the client.** ⭐⭐ **Translate at the layer boundary
with `raise ... from`** (Day 059): the cause stays in your logs, and a clean domain error crosses the
wire.

# Part 4 — ⭐ Validation errors, and retryability

```json
{
  "code": "validation_error", "status": 422, "request_id": "01J7…",
  "errors": [
    {"field": "items.0.qty", "code": "greater_than", "message": "must be > 0"},
    {"field": "email",       "code": "invalid_format", "message": "not a valid email"}
  ]
}
```

⭐⭐ **All errors at once, a field path, and a per-field `code`** (Day 119). ⭐ **The per-field code is
what lets a client highlight the right input and show its own translated message** — which is also the
answer to internationalisation: **translate `title` and `detail`, never `code`.**

```
⭐⭐ TELL THE CLIENT WHETHER TO RETRY — THE STATUS ALREADY DOES MOST OF IT, AND
⭐   THAT IS BETTER THAN A CUSTOM FLAG:
⭐   4xx           ⇒ ⭐ do NOT retry unchanged. Nothing will improve.
⭐   ⭐⭐ 429       ⇒ ⭐⭐ RETRY AFTER `Retry-After`. Sending that header is not
⭐                     optional — without it the client guesses, and guesses badly.
⭐   ⭐ 503        ⇒ retry with backoff; `Retry-After` if you know.
⭐   ⭐ 502 / 504  ⇒ ⭐⭐ MAYBE — and this is where Day 102 returns: the request
⭐                     may have SUCCEEDED upstream, so retrying is only safe if
⭐                     the operation is idempotent (Day 122).
⭐   500           ⇒ ⭐ usually not; a retry hits the same bug.
⭐   ⇒ ⭐⭐ SO A RETRY POLICY IS A PROPERTY OF THE OPERATION, NOT OF THE ERROR.
⭐        ⭐ Do not invent a `"retryable": true` field that contradicts the
⭐        status code — say it in the documentation and honour the standard
⭐        semantics.
```

# Part 5 — ⭐ Errors are part of the contract

```
⭐⭐ TREAT ERROR CODES LIKE ANY OTHER PART OF YOUR API:
⭐   □ ⭐⭐ DOCUMENT EVERY CODE an endpoint can return, in OpenAPI (Day 126).
⭐        ⭐ "It returns 400 sometimes" is not a contract.
⭐   □ ⭐ ADDING a new code is a MINOR change — ⭐⭐ IF clients handle unknown
⭐        codes by falling back on the status. ⭐ Say that in the docs, and they
⭐        will; leave it unsaid and someone writes an exhaustive match that
⭐        breaks (Day 125).
⭐   □ ⭐⭐ CHANGING or REMOVING a code is BREAKING. Treat it as such.
⭐   □ ⭐ CHANGING `detail` is free — ⭐⭐ which is the entire reason for having
⭐        `code` in the first place.
⭐   □ ⭐ keep the codes in ONE enum (Day 058) so they are enumerable, testable,
⭐        and impossible to typo into existence.
```

```python
def test_error_shape_is_consistent(client):
    for method, path, body in EVERY_ERROR_CASE:          # ⭐ a table of known failures
        r = client.request(method, path, body=body)
        problem = json.loads(r.body)
        assert set(problem) >= {"code", "status", "request_id"}   # ⭐⭐ the invariant
        assert problem["status"] == r.status
        assert "Traceback" not in r.body.decode()                  # ⭐⭐ the security assertion
        assert problem["code"] in KNOWN_CODES                       # ⭐ no ad-hoc codes
```

```
⭐⭐ THAT TEST IS WORTH MORE THAN THE SPEC. ⭐ A written convention decays the
⭐   first time someone is in a hurry; ⭐⭐ a test that asserts EVERY error path
⭐   has a code, a matching status, a request id, no traceback, and a code from
⭐   the known set makes drift impossible.
⭐   ⇒ ⭐ pair it with a route-level check: hit every registered route with
⭐        deliberately invalid input and assert the shape.
⭐   ⇒ ⭐⭐ AND ADD ONE ASSERTION THAT PAYS FOR ITSELF: that no 5xx body contains
⭐        any of your table names. ⭐ It catches the ORM exception someone let
⭐        through at 6 p.m.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ A different error shape per endpoint | ⭐ The client writes N parsers, then diverges. |
| ⭐⭐ **No machine-readable code** | ⭐⭐ Clients match on prose; you can never reword a message. |
| Clients branching on `detail` | ⭐ Document `code` as the contract — say it, or they will. |
| ⭐⭐ **A traceback in the body** | ⭐⭐ Paths, versions, and sometimes credentials. |
| A database error reaching the client | ⭐⭐ A free schema dump. Translate with `raise ... from`. |
| ⭐ Specific 5xx messages | ⭐ 4xx may be specific; 5xx must be generic + a request id. |
| ⭐ "No user with that email" | ⭐⭐ Account enumeration from a non-auth endpoint. |
| No `request_id` in errors | ⭐ The single most useful field in a support ticket. |
| ⭐ 429 without `Retry-After` | ⭐ The client guesses, and guesses badly. |
| A custom `"retryable"` flag | ⭐⭐ Retryability is a property of the operation. Use the status. |
| ⭐ Undocumented error codes | ⭐ "It returns 400 sometimes" is not a contract. |
| Changing a code to "improve" it | ⭐⭐ Breaking. Rewording `detail` is free — that is the point. |

## Interview questions

**Q: How do you design error responses?**
> One shape for the whole API, based on RFC 7807 problem details, with two things added: a stable
> machine-readable `code` and the request id. The rule I document explicitly is that clients branch on
> `code` and humans read `detail` — because if I don't give them something stable that isn't the
> message, they'll match on the message, and then I can never reword an error again. That's especially
> bad with mobile clients, where an old version lives on phones for years. And one exception hierarchy
> feeding one handler, so adding a new error type doesn't touch any client.

**Q: What must an error never contain?**
> Anything that helps an attacker. A traceback leaks file paths, library versions to look up CVEs for,
> and sometimes credentials from a repr. A raw database error leaks table, column and constraint names
> — a free schema dump one field at a time, and the starting point for injection. Internal hostnames
> give away network layout. "No user with that email" is account enumeration from an endpoint nobody
> thinks of as auth. And anything that reports how *close* a guess was is an oracle. The rule I use is
> that 4xx may be specific, because it's the client's mistake and telling them how to fix it is the
> point, but 5xx must be generic — it's my bug, the client can do nothing with the detail, so log it
> fully and return a code plus a request id.

**Q: Why does the request id matter so much in an error?**
> Because it turns a deliberately useless message into a two-minute investigation. The user quotes it
> in a ticket, I run one query, and I have every log line for that request in order. Without it, "I
> got an internal error at some point this afternoon" is genuinely unactionable on a busy service. It
> also means I don't have to trade safety for debuggability — the response can stay generic while I
> keep everything in the logs.

**Q: How should a client know whether to retry?**
> From the status code, mostly — 4xx don't retry unchanged, 429 retries after `Retry-After`, 503
> retries with backoff. The interesting one is 502 and 504, because the request may have succeeded
> upstream and only the response was lost, so retrying is safe only if the operation is idempotent.
> Which means retryability is really a property of the operation rather than of the error, and I'd
> document it per endpoint rather than invent a `"retryable": true` field that can contradict the
> status.

**Q: Are error codes part of your API contract?**
> Yes, and I'd treat them accordingly. Every code an endpoint can return is documented in the OpenAPI
> spec, kept in one enum so it's enumerable and can't be typo'd into existence. Adding a code is a
> minor change *provided* clients fall back on the status for unknown codes — which I'd say
> explicitly in the docs, because unsaid, someone writes an exhaustive match that breaks. Changing or
> removing a code is breaking. Rewording `detail` is free, and that freedom is the whole reason `code`
> exists.

## 🎙️ Articulation drill

Record two minutes: **"How do you design the error responses for an API?"**

⭐ **Start from the fact that decides everything:** **"errors are part of the API, and clients will
write code against them. So the first question is: what am I giving them that's stable? If it's only
prose, they'll match on prose — and then I can never reword an error message, which is especially bad
with mobile clients where an old version lives on phones for years."**

⭐⭐ **Then the shape and the rule:** *"one shape for the whole API — problem details, plus a
machine-readable `code` and the request id. And I document explicitly that clients branch on `code`
and humans read `detail`, because if I don't say it, someone will branch on the message anyway. That
split is what makes rewording free and gives me somewhere stable to hang a contract. One exception
hierarchy, one handler, one shape, so adding a new error type touches no client."*

⭐⭐ **Then the security half, with concrete leaks:** *"and I'm strict about what an error can contain.
A traceback leaks paths and library versions to look up CVEs for. A raw database error leaks table and
column names — a free schema dump and the starting point for injection. 'No user with that email' is
account enumeration from an endpoint nobody thinks of as auth. My rule is that 4xx can be specific,
because it's the client's mistake and helping them is the point, but 5xx must be generic — it's my bug
and they can do nothing with the detail."*

⭐ **Close on the thing that makes generic errors acceptable, and the test:** *"the request id is what
makes that trade disappear: the response stays generic, the user quotes the id, and one query gives me
every log line for that request. And I'd write a test that hits every error path and asserts there's a
code from a known enum, a matching status, a request id, and no traceback — because a written
convention decays the first time someone's in a hurry, and a test doesn't."*
