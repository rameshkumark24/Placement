# Day 048

**L-048** · Generators as coroutines — `send`, `throw`, `close`, and the ancestor of `async`/`await`

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `async def` is a generator with different syntax and a scheduler
> attached. `await` is `yield from`.** Not "similar to" — **that is literally how it was built**, in
> two PEPs, and the machinery is still shared.
>
> ⚠️ ⭐ **You will not write coroutine-style generators in modern code.** You are learning them
> because they make Day 070's asyncio obvious instead of magical, and because
> `@contextlib.contextmanager` (Day 052) uses `throw` in a way that explains a rule you would
> otherwise memorise.

---

# Part 1 — ⭐⭐ `yield` is an expression

```python
def echo():
    while True:
        received = yield              # ⭐⭐ yield can RECEIVE a value, not just produce one
        print("got", received)

g = echo()
next(g)                               # ⭐⭐ PRIMING — run to the first yield. Mandatory.
g.send("hello")                       # ⭐ "got hello"
g.send("world")                       # ⭐ "got world"
```

```
⭐⭐ THE SHIFT: a generator is not only a producer. It is a SUSPENDABLE FUNCTION —
⭐   ⇒ ⭐ `x = yield v`   sends v OUT, and the value passed to send() comes back IN as x
⭐   ⇒ ⭐⭐ so control flows BOTH WAYS across the yield. That is a coroutine.
⭐
⭐ ⚠️ ⭐⭐ PRIMING: send() on a not-yet-started generator raises
⭐      "TypeError: can't send non-None value to a just-started generator"
⭐   ⇒ because there is no suspended `yield` to receive it yet. next(g) or g.send(None) first.
⭐   ⇒ ⭐ this awkwardness is a large part of why `async def` replaced the idiom.
```

```python
def averager():                       # ⭐ the classic example — state with no class
    total = count = 0
    while True:
        x = yield (total / count if count else None)
        total += x; count += 1

avg = averager(); next(avg)
avg.send(10)      # 10.0
avg.send(20)      # 15.0
```

⭐ **Note what this replaces:** an object with `__init__`, two attributes and an `add` method. **The
generator holds the state in its suspended frame** (Day 047) — which is elegant, and also why
debugging it is harder, since there is nothing to inspect from outside.

# Part 2 — ⭐ `throw` and `close`

```python
g.throw(ValueError("bad"))      # ⭐⭐ raises ValueError AT THE YIELD POINT inside the generator
g.close()                       # ⭐ raises GeneratorExit at the yield point
```

```python
def worker():
    try:
        while True:
            item = yield
            process(item)
    except ValueError:                 # ⭐⭐ the generator can HANDLE an injected exception
        yield "recovered"              # ⭐ and keep going
    except GeneratorExit:              # ⭐ close() — clean up and do NOT yield again
        cleanup()
        raise                          # ⚠️ ⭐⭐ yielding after GeneratorExit ⇒ RuntimeError
    finally:
        release()                      # ⭐⭐ runs on every path — Day 047's rule
```

```
⭐⭐ THIS EXPLAINS @contextlib.contextmanager, and it is worth the whole day for this alone:

⭐   @contextmanager
⭐   def managed():
⭐       r = acquire()
⭐       try:
⭐           yield r          ⭐⭐ ← the `with` body runs HERE
⭐       finally:
⭐           release(r)

⭐ ⇒ ⭐⭐ if the `with` body raises, contextlib calls gen.throw(exc) — the exception is
⭐      RAISED AT THE YIELD, inside your generator.
⭐   ⇒ ⭐⭐ WITHOUT try/finally it propagates straight out and `release()` is NEVER REACHED.
⭐   ⇒ ⭐ THAT is why "always use try/finally in a @contextmanager" is a rule and not a style note.
```

⭐⭐ **That derivation is worth stating in an interview**, because most people know the rule and
cannot say why. **The exception is not "around" your generator — it is injected *into* it, at the
`yield`.**

# Part 3 — ⭐⭐ The line to `async`

```
⭐⭐ THE HISTORY, AND IT IS ONE STORY IN FOUR STEPS:

⭐ 1. PEP 255 (2001) — `yield`. Generators produce values lazily.                 ⇒ Day 047
⭐ 2. PEP 342 (2005) — `send`, `throw`, `close`. ⭐ Generators become COROUTINES.  ⇒ Part 1
⭐ 3. ⭐ PEP 380 (2012) — `yield from`. Delegation that forwards send/throw/close
⭐      and returns a value ⇒ ⭐⭐ you can now BUILD a coroutine out of other coroutines.
⭐ 4. ⭐⭐ PEP 492 (2015) — `async def` / `await`. ⭐⭐ NEW SYNTAX FOR STEP 3,
⭐      plus a scheduler (the event loop) that decides who resumes next.
```

```python
# ⭐ Python 3.4 — asyncio before the syntax existed. THIS IS REAL, WORKING CODE:
@asyncio.coroutine
def fetch(url):
    data = yield from session.get(url)      # ⭐⭐ yield from
    return data

# ⭐ Python 3.5+ — the same thing:
async def fetch(url):
    data = await session.get(url)           # ⭐⭐ await
    return data
```

```
⭐⭐ WHAT `await` ACTUALLY DOES:
⭐   suspends this coroutine, hands control back to the EVENT LOOP,
⭐   and the loop resumes it — via the same send() machinery — when the awaited thing is ready.
⭐   ⇒ ⭐⭐ `await` IS a yield point. The suspended frame is the same suspended frame (Day 047).
⭐   ⇒ ⭐ the loop is Day 016's selectors loop: epoll tells it which sockets are ready,
⭐        and it send()s into the corresponding coroutines.
```

⭐⭐ **This is why Day 072's bug is inevitable and mechanical:** a blocking call inside `async def`
never reaches a `yield`, so it **never returns control to the loop**, so no other coroutine can be
resumed and `epoll` is never called. **Not a slowdown — a full stop.** ⭐ You now have that from
three angles: the browser freeze (Day 014), the `selectors` loop (Day 016), and the suspension
machinery (today).

⚠️ ⭐ **They are not interchangeable in modern Python:** `async def` produces a *coroutine object*,
not a generator; it is awaitable, not iterable; and you cannot `next()` it. **The distinction was
deliberate** — separating the two prevented a large class of confusion — **but the underlying frame
suspension is the same.**

# Part 4 — ⭐ What to actually do with this

```
⭐⭐ THE MODERN VERDICT — say this plainly:
⭐   ✗ ⭐ do NOT write generator-based coroutines. `async def` is clearer, typed, and supported.
⭐   ✗ ⭐ do NOT hand-roll pipelines with send(). Use async generators or a queue.
⭐   ✓ ⭐⭐ DO understand this, because it explains await, contextmanager, and why
⭐        blocking inside async def is fatal rather than slow.
```

```python
# ⭐ Async generators — the modern form of "produce lazily, asynchronously" (Day 071):
async def fetch_pages(urls):
    for u in urls:
        yield await client.get(u)          # ⭐⭐ `async def` + `yield` = an async generator

async for page in fetch_pages(urls): ...   # ⭐ __aiter__ / __anext__ (Day 031)
```

⭐⭐ **Async generators are the pattern you *will* use**: streaming a large database result to an HTTP
response, consuming a message queue, paginating an API — **all of Day 047's memory argument, with
awaits in the middle.** ⚠️ **And the same cleanup trap applies, harder**: an abandoned async
generator needs `aclose()`, which is why `contextlib.aclosing` exists.

| ⭐ Generator | ⭐ Coroutine (`async def`) |
|---|---|
| `yield` produces | ⭐ `await` suspends |
| driven by `next()` / `send()` | ⭐⭐ driven by the **event loop** |
| consumer decides when to resume | ⭐ the scheduler decides |
| iterable | ⭐⭐ awaitable |
| `yield from` delegates | `await` delegates |

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Forgetting to prime with `next()` | ⭐ `send` on a fresh generator raises `TypeError`. |
| ⭐⭐ **`@contextmanager` without `try/finally`** | ⭐⭐ `throw` injects at the yield; cleanup is skipped. |
| Yielding after `GeneratorExit` | ⭐ `RuntimeError`. Clean up and re-raise. |
| Writing coroutine generators today | ⭐ `async def`. This is history, not practice. |
| Thinking `await` is "wait" | ⭐⭐ It suspends and yields control to the loop. |
| Treating coroutines as generators | ⭐ Distinct types; not iterable, not `next()`-able. |
| Missing why blocking kills asyncio | ⭐⭐ No yield point ⇒ the loop never regains control. |
| Abandoning an async generator | ⭐ Use `aclose()` / `contextlib.aclosing`. |

## Interview questions

**Q: What's the relationship between generators and `async`/`await`?**
> Direct descent, not analogy. `yield` gave lazy production in 2001; `send`, `throw` and `close` in
> PEP 342 made generators two-way, so they became coroutines; `yield from` in PEP 380 added
> delegation that forwards all of that and returns a value; and PEP 492 gave that mechanism dedicated
> syntax — `async def` and `await` — plus an event loop to decide who resumes. Before 3.5, asyncio
> code was written with `yield from` and it worked. They're distinct types now, deliberately, but the
> frame-suspension machinery underneath is the same.

**Q: What does `await` actually do?**
> Suspends the current coroutine at that point and returns control to the event loop, which resumes
> it — through the same `send` machinery — when the awaited operation is ready. So `await` is a yield
> point. That's the mechanical reason a blocking call inside `async def` is catastrophic rather than
> merely slow: there's no yield point, so control never returns to the loop, `epoll` is never called,
> and every other coroutine on that worker is frozen until the blocking call returns.

**Q: Why must a `@contextmanager` use `try`/`finally`?**
> Because of `throw`. When the `with` body raises, `contextlib` calls `gen.throw(exc)`, which raises
> the exception *inside* the generator, at the `yield` statement. Without a `try`, that propagates
> straight out and everything after the `yield` — the cleanup — is never executed. The exception
> isn't around the generator, it's injected into it, which is why the rule exists rather than being
> a stylistic preference.

**Q: What's priming, and why does it exist?**
> A generator hasn't reached its first `yield` until you advance it once, so there's no suspended
> yield expression to receive a sent value — `send` with a non-None value on a fresh generator raises
> `TypeError`. You prime it with `next(g)` or `g.send(None)`. It's the kind of ceremony that people
> wrapped in a decorator, and the awkwardness is part of why dedicated `async` syntax was worth
> adding.

**Q: Should you write generator-based coroutines today?**
> No. `async def` is clearer, better typed, better supported by tooling, and doesn't need priming. I
> learn this because it explains three things that otherwise have to be memorised: what `await` is,
> why `@contextmanager` needs `try/finally`, and why blocking in an async function stops everything.
> The pattern I do use is async generators — `async def` with `yield` — for streaming a large query
> to an HTTP response or consuming a queue, which is the memory argument from generators with awaits
> in the middle.

## 🎙️ Articulation drill

Record two minutes: **"What is `async`/`await`, really?"**

⭐ Refuse the vague answer. **`async def` is a generator with dedicated syntax and a scheduler
attached, and `await` is a yield point** — that is not an analogy, it is the implementation history:
`send` and `throw` made generators two-way, `yield from` made them composable, and PEP 492 gave that
machinery its own keywords.

⭐ Then what actually happens at an `await`: **the coroutine suspends its frame, control returns to
the event loop, and the loop resumes it later through the same `send` mechanism when the awaited
thing is ready.**

⭐⭐ **Then cash it out in the one consequence that matters in production:** *"which is why a blocking
call inside `async def` is fatal and not merely slow. There is no yield point, so control never
returns to the loop, `epoll` is never called, and every other request that worker is serving is
frozen — not delayed proportionally, stopped. Understanding `await` as a yield point is what turns
that from a rule I was told into something I can derive."*
