# Day 154

**L-154** · **CI/CD for a Python service** — ⭐⭐ the pipeline as a contract, and what must never be manual

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: CI does not exist to run your tests — it exists to be the only authority
> on whether a commit is deployable, which means anything it does not check is something you are
> deciding to find out in production.**
>
> ⭐ Day 099 said pre-commit is advisory and CI is authoritative. ⭐⭐ Today is the full pipeline, and
> the rule that generates most of it: **build the artefact once, and deploy that same artefact
> everywhere.**

---

# Part 1 — ⭐⭐ Build once, promote the artefact

```
⭐⭐ THE MISTAKE THAT LOOKS COMPLETELY REASONABLE:

⭐   staging deploy  → checkout, build image, push, deploy
⭐   production deploy → checkout, build image, push, deploy
⭐
⭐   ⇒ ⭐⭐ THESE ARE TWO DIFFERENT BUILDS. Even from the same commit, they
⭐        can differ: a dependency was republished, a base image moved, a
⭐        transitive pin resolved differently (Day 151).
⭐   ⇒ ⭐⭐ SO "IT PASSED IN STAGING" PROVED NOTHING ABOUT THE THING YOU JUST
⭐        SHIPPED. ⭐ You tested a different program with the same name.

⭐⭐ THE RULE: BUILD ONE ARTEFACT, TEST *THAT* ARTEFACT, PROMOTE *THAT*
⭐   ARTEFACT.
⭐        commit ──> build ──> image@sha256:abc  ⭐⭐ ONE immutable artefact
⭐                              │
⭐                              ├──> test suite runs against it
⭐                              ├──> deployed to staging
⭐                              └──> ⭐ SAME DIGEST deployed to production
⭐
⭐   ⇒ ⭐⭐ "PROMOTION" MEANS CHANGING WHICH ENVIRONMENT POINTS AT A DIGEST.
⭐        IT NEVER MEANS BUILDING AGAIN. ⭐ And Day 150's rule is the other
⭐        half: the artefact carries no environment-specific config, so the
⭐        same image CAN run everywhere.
⭐   ⇒ ⭐ Rollback becomes trivial and instant: point at the previous digest.
⭐        ⭐⭐ A rollback that requires a rebuild is not a rollback, it is a
⭐        hopeful redeploy — and it takes four minutes during an incident.
```

# Part 2 — ⭐⭐ The stages, and what each one is *for*

```
⭐⭐ ORDER BY "FASTEST FEEDBACK ON THE MOST LIKELY FAILURE" — a pipeline that
⭐   runs a 12-minute test suite before a 4-second lint is wasting the thing
⭐   CI actually optimises: how long a developer waits to learn they are wrong.

⭐  1. ⭐ LINT + FORMAT (~10 s)   `ruff check` · `ruff format --check`
⭐  2. ⭐ TYPES (~30 s)           `mypy`  ⭐⭐ Day 099 — catches the null and
⭐                                 signature bugs no test was written for
⭐  3. ⭐ UNIT TESTS (~1 min)
⭐  4. ⭐⭐ BUILD THE IMAGE        ⭐ the artefact, once
⭐  5. ⭐⭐ INTEGRATION TESTS AGAINST THE IMAGE, with a real Postgres and
⭐        Redis as services (Day 141)
⭐  6. ⭐ SECURITY: `pip-audit` (deps) · `trivy` (image) · ⭐⭐ SECRET SCANNING
⭐        (`gitleaks`) — ⭐ which must ALSO run on the whole history, because
⭐        Day 084 means a secret from six months ago is still there
⭐  7. ⭐ MIGRATION CHECK (Day 138/141): `alembic upgrade head` on an empty DB
⭐        + ⭐⭐ an autogenerate diff that MUST be empty
⭐  8. ⭐ PUSH the image, tagged by commit sha ⭐⭐ (never `:latest`)
⭐  9. ⭐ DEPLOY to staging → smoke tests → ⭐ promote

⭐   ⇒ ⭐⭐ AND THE PART PEOPLE SKIP: STEPS 1–3 SHOULD **FAIL FAST AND IN
⭐        PARALLEL**. ⭐ You want all three failures in one report, not three
⭐        sequential 4-minute round trips to learn about three one-line fixes.
```

```yaml
# ⭐ the shape that matters, not the vendor
jobs:
  static:                                    # ⭐⭐ fast lane, runs in parallel
    steps:
      - uses: actions/checkout@v4
      - run: uv sync --frozen                # ⭐ Day 151 — fail on a stale lock
      - run: ruff check . && ruff format --check .
      - run: mypy .

  test:
    services:
      postgres: { image: postgres:16 }       # ⭐⭐ REAL Postgres, not SQLite
      redis:    { image: redis:7 }
    steps:
      - run: pytest --cov --cov-fail-under=80 -n auto
      # ⭐⭐ -n auto needs a DB PER WORKER (Day 141) or you get real flakes
```

# Part 3 — ⭐⭐ Speed: the three levers, in order

```
⭐⭐ A SLOW PIPELINE IS NOT AN INCONVENIENCE — IT IS A CORRECTNESS PROBLEM,
⭐   AND THIS IS THE ARGUMENT TO MAKE:
⭐   ⭐ 30-minute CI ⇒ people batch changes into bigger PRs (Day 088) ⇒
⭐        ⭐⭐ bigger PRs get worse reviews and are harder to bisect (Day 088) ⇒
⭐        ⭐ more bugs, each harder to attribute.
⭐   ⭐ 30-minute CI ⇒ ⭐⭐ people stop running it locally and "just push to
⭐        see", which turns your CI into a shared debugger.
⭐   ⇒ ⭐⭐ TARGET: UNDER 10 MINUTES TO A MERGE DECISION. Under 5 is better.

⭐⭐ THE LEVERS, IN THE ORDER THAT PAYS:
⭐  1. ⭐⭐ CACHE THE DEPENDENCY INSTALL. Keyed on the LOCKFILE HASH, not on
⭐       the branch — ⭐ so the cache is shared by everyone and invalidated
⭐       only when it should be. ⭐⭐ Usually the single biggest win, and the
⭐       most commonly misconfigured (a cache key that includes the commit sha
⭐       never hits).
⭐  2. ⭐ PARALLELISE. Split static/unit/integration into separate jobs;
⭐       `pytest -n auto` inside. ⭐⭐ Measure first (`--durations=20`,
⭐       Day 100A) — ⭐ a suite that is 80% one integration test does not
⭐       benefit from sharding.
⭐  3. ⭐ DOCKER LAYER CACHING in CI (`cache-from` a registry image).
⭐       ⭐⭐ Without it, every CI build is a cold build and Day 151's careful
⭐       ordering buys you nothing at all.
⭐  4. ⭐ RUN THE EXPENSIVE THINGS ON A SCHEDULE, NOT PER COMMIT: mutation
⭐       testing (Day 098), full dependency audits, long load tests.
⭐
⭐ ⭐⭐ AND THE ANTI-LEVER: DO NOT "FIX" A SLOW PIPELINE BY SKIPPING TESTS ON
⭐   MAIN. ⭐ The one commit you did not check is the one that breaks the
⭐   deploy — and now you have no signal about which commit did it.
```

# Part 4 — ⭐⭐ Flaky tests: the thing that actually kills a pipeline

```
⭐⭐ A FLAKY TEST IS WORSE THAN A MISSING TEST, AND THE REASON IS SOCIAL, NOT
⭐   TECHNICAL:
⭐   ⭐ a test that fails 2% of the time teaches everyone to press "re-run".
⭐   ⇒ ⭐⭐ NOW EVERY RED BUILD IS RE-RUN BY REFLEX, INCLUDING THE REAL ONES.
⭐        ⭐ You have not lost one test — you have lost the SIGNAL that a red
⭐        build means something.

⭐⭐ THE FOUR CAUSES, AND THEY ARE ALWAYS ONE OF THESE:
⭐  1. ⭐⭐ SHARED STATE BETWEEN TESTS — a session-scoped mutable fixture
⭐       (Day 093), a real database not rolled back (Day 141), a module-level
⭐       cache. ⭐ Detect it: `pytest -p no:randomly` off, i.e. RUN IN RANDOM
⭐       ORDER (`pytest-randomly`) — ⭐⭐ order dependence becomes visible
⭐       immediately instead of appearing when someone adds a test.
⭐  2. ⭐⭐ TIME. `datetime.now()`, a 0.1-second sleep, a token that expires
⭐       mid-suite, ⭐ a test that fails only between 23:00 and 00:00 UTC or
⭐       on the 31st. ⭐⭐ Inject the clock (Day 133's seam) — this is the
⭐       single highest-value fix.
⭐  3. ⭐ CONCURRENCY / ORDERING — asserting on the order of results from
⭐       `gather`, or on a set's iteration order.
⭐  4. ⭐ EXTERNAL DEPENDENCIES — a real HTTP call in a test. ⭐⭐ Now your
⭐       merge depends on someone else's uptime.

⭐   ⇒ ⭐⭐ THE POLICY THAT WORKS: QUARANTINE, WITH A DEADLINE. A flaky test
⭐        is moved out of the blocking suite AND gets an issue with an owner
⭐        and a date. ⭐ Not deleted (you lose the coverage), not left in (you
⭐        lose the signal). ⭐⭐ And track the flake RATE as a metric — if it
⭐        rises, that is a real regression in your ability to ship.
⭐   ⇒ ⭐ `pytest --reruns 2` is a PAINKILLER, not a cure. ⭐⭐ Use it to keep
⭐        moving while the issue is open, never as the resolution.
```

# Part 5 — ⭐⭐ CD: what must never be manual, and the gates that matter

```
⭐⭐ THE THINGS THAT MUST BE AUTOMATED, EACH FOR A SPECIFIC REASON:
⭐   ⭐ THE BUILD — ⭐⭐ a human-built artefact is unreproducible and
⭐        unattributable
⭐   ⭐ MIGRATIONS — ⭐ as a job in the pipeline, not `ssh` + `alembic`
⭐        (Day 138)
⭐   ⭐ THE DEPLOY ITSELF — ⭐⭐ because a manual deploy is a procedure that is
⭐        followed correctly until 2 a.m. on a Friday
⭐   ⭐ ROLLBACK — ⭐⭐ ONE COMMAND OR ONE BUTTON. If rollback requires
⭐        thinking, people will "fix forward" under pressure, ⭐ which is how a
⭐        five-minute incident becomes an hour.
⭐   ⭐ SMOKE TESTS AFTER DEPLOY — ⭐ and an AUTOMATIC rollback if they fail.
⭐
⭐⭐ AND THE ONE THING THAT SHOULD OFTEN STAY MANUAL: THE DECISION TO PROMOTE
⭐   TO PRODUCTION. ⭐ Not the mechanism — the DECISION. ⭐⭐ A one-click
⭐   promotion of an already-tested digest is different from a human running
⭐   deployment steps, and conflating "automated" with "unsupervised" is how
⭐   teams end up afraid of their own pipeline.
```

```
⭐⭐ BRANCH PROTECTION — the mechanical enforcement of Day 088:
⭐   ⭐ required status checks · ⭐ required review · ⭐ linear history
⭐   ⭐⭐ AND "REQUIRE BRANCHES TO BE UP TO DATE" — because of ⭐⭐ SEMANTIC
⭐        CONFLICTS: your PR passes, mine passes, and MERGED they break, with
⭐        no textual conflict for git to find. ⭐ I delete a function, you add
⭐        a caller. ⭐⭐ Git merges it cleanly and main is broken.
⭐   ⇒ ⭐ Merge queues solve this properly at scale: test the RESULT of the
⭐        merge, not the branch.

⭐⭐ SECRETS IN CI (Day 150), because this is where they leak most often:
⭐   ⭐ ⭐⭐ NEVER expose secrets to workflows triggered by a fork's PR.
⭐        `pull_request_target` + a checkout of the fork's code = ⭐ an
⭐        attacker running arbitrary code WITH YOUR SECRETS. ⭐⭐ This is a
⭐        real, repeatedly-exploited pattern.
⭐   ⭐ prefer OIDC federation over long-lived cloud keys — ⭐⭐ short-lived
⭐        credentials minted per run, with nothing to steal at rest
⭐   ⭐ scope one credential per pipeline; ⭐ mask them; ⭐⭐ and remember
⭐        `set -x` in a script prints them.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Rebuilding for each environment | Staging tested a different program. Build once, promote the digest. |
| Deploying `:latest` | Two pods can differ under one tag, and rollback has no target. |
| Slow stages before fast ones | CI optimises how long a developer waits to learn they're wrong. |
| Cache key including the commit sha | It never hits. Key on the lockfile hash. |
| No Docker layer cache in CI | Every build is cold and Day 151's ordering buys nothing. |
| SQLite in CI, Postgres in production | Testing a different program. |
| `pytest -n auto` with one shared database | Real races that look like flakes. |
| Tolerating flaky tests | Everyone re-runs red builds by reflex, including the real ones. |
| `--reruns` as the fix | A painkiller. Quarantine with an owner and a date. |
| Tests using `datetime.now()` | Fails on the 31st, or between 23:00 and midnight. Inject the clock. |
| Real HTTP calls in tests | Your merge now depends on someone else's uptime. |
| Migrations run by hand over SSH | Unrepeatable, unlogged, and unavailable at 2 a.m. |
| Rollback that needs thinking | People fix forward under pressure and a 5-minute incident becomes an hour. |
| Skipping checks on `main` to save time | The one unchecked commit breaks the deploy and you can't attribute it. |
| No "branch up to date" requirement | Semantic conflicts merge cleanly and break `main`. |
| Secret scanning on the diff only | Day 084 — a secret from six months ago is still in history. |
| Secrets exposed to fork PR workflows | Arbitrary attacker code running with your credentials. |
| Long-lived cloud keys in CI | Use OIDC federation and mint short-lived credentials per run. |

## Interview questions

**Q: Why build the image once rather than per environment?**

> Because two builds of the same commit are not guaranteed to be the same program — a dependency
> gets republished, a base image tag moves, a transitive pin resolves differently. So if I build for
> staging and build again for production, "it passed in staging" proved nothing about the artefact I
> just shipped. Build once, test that artefact, and promote it by changing which environment points
> at that digest. It also makes rollback instant: point at the previous digest. A rollback that
> requires a rebuild isn't a rollback, it's a hopeful redeploy that takes four minutes during an
> incident. The other half of the rule is that the artefact carries no environment-specific config,
> which is what makes one image runnable everywhere.

**Q: Your CI takes 30 minutes. Why does that matter beyond convenience?**

> Because it changes behaviour, and the behaviour change costs correctness. People batch work into
> bigger pull requests to amortise the wait, and bigger PRs get worse reviews and are harder to
> bisect. And people stop running checks locally and just push to see what happens, which turns CI
> into a shared debugger. I'd target under ten minutes to a merge decision. The levers in order:
> cache the dependency install keyed on the lockfile hash — that's usually the biggest win and the
> most commonly misconfigured, because a cache key with the commit sha in it never hits; then
> parallelise, after measuring with `--durations`, because a suite that's eighty percent one
> integration test doesn't benefit from sharding; then Docker layer caching, without which every CI
> build is cold; then move mutation testing and long load tests to a schedule.

**Q: How do you handle flaky tests?**

> First by naming why they're worse than missing tests: a test failing two percent of the time
> teaches everyone to press re-run, so every red build gets re-run by reflex including the real ones.
> You haven't lost one test, you've lost the meaning of a red build. The causes are always one of
> four — shared state between tests, which random test ordering exposes immediately; time, which is
> the big one and is fixed by injecting a clock rather than calling `datetime.now()`; concurrency and
> ordering assumptions; and real external calls. The policy is quarantine with a deadline: out of the
> blocking suite, but with an issue, an owner and a date, because deleting loses coverage and leaving
> it loses signal. And I'd track the flake rate as a metric, since a rising one is a real regression
> in the ability to ship.

**Q: What should never be manual, and what should stay manual?**

> Never manual: the build, migrations, the deploy mechanism, rollback, and post-deploy smoke tests
> with automatic rollback if they fail. Rollback especially — if it requires thinking, people fix
> forward under pressure and turn five minutes into an hour. What often *should* stay manual is the
> *decision* to promote to production, as distinct from the mechanism. A one-click promotion of an
> already-tested digest is completely different from a human running deployment steps, and conflating
> "automated" with "unsupervised" is how teams end up afraid of their own pipeline.

**Q: Both PRs passed CI and `main` is broken. How?**

> A semantic conflict. I delete a function, you add a caller for it; each branch is green against its
> own base and there's no textual conflict for git to detect, so the merge is clean and the result is
> broken. The cheap mitigation is requiring branches to be up to date before merge, which forces a
> rebase and re-run. The proper fix at scale is a merge queue, which tests the *result* of the merge
> rather than the branch — because that's the artefact you're actually shipping.

## Mini task

1. ⭐ Split your pipeline into parallel `static` and `test` jobs. Compare wall-clock time to the sequential version.
2. ⭐⭐ Add dependency caching keyed on the lockfile hash. Check the cache-hit rate over five runs; then deliberately key it on the sha and confirm it never hits.
3. ⭐⭐ Build the image in CI and run integration tests **against the image**, not against the source tree. Note what broke.
4. ⭐ Add `gitleaks` over the full history and see what it finds.
5. ⭐⭐ Add the migration job: `alembic upgrade head` on an empty database, then assert an empty autogenerate diff. Change a model without a migration and confirm the failure.
6. ⭐⭐ Install `pytest-randomly` and run the suite five times. Fix whatever order-dependence it exposes.
7. ⭐ Write a test using `datetime.now()` that fails on the 31st. Then inject a clock and make it deterministic.
8. ⭐⭐ Implement promotion: tag the built digest and deploy the same digest to two environments. Prove they run identical images with `docker inspect`.
9. ⭐ Time your rollback end to end. If it's over a minute, fix that before anything else.

## 🎙️ Articulation drill

**Two minutes: "Describe your CI/CD pipeline."**

Lead with the invariant, not the stages — build once, promote the digest — and give the reason it
matters: two builds of one commit can be different programs, so rebuilding per environment makes
staging meaningless. Then walk the stages in fast-feedback order and say what each is *for*, calling
out the two people forget: the Alembic job that proves migrations run on an empty database, and
secret scanning over full history. Then the speed argument as a correctness argument, with the
lockfile cache key as the concrete lever. Close on flakiness — **a two percent flake teaches everyone
to re-run red builds, which costs you the signal, not the test** — and on rollback being one button,
because if it needs thinking people will fix forward under pressure.
