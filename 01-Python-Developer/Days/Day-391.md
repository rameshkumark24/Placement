# Part 1 — The execution model, and what it deletes

```
⭐⭐ ***ONE ENVIRONMENT SERVES ONE REQUEST AT A TIME.*** ⭐ To
⭐   serve 200 concurrent requests, AWS runs 200 environments.

⭐ THE LIFECYCLE:
⭐   ⭐⭐ INIT ...... download the package, start the runtime,
⭐               ***RUN YOUR MODULE-LEVEL CODE.***
⭐   ⭐ INVOKE .... your handler runs.
⭐   ⭐⭐ FREEZE .... THE PROCESS IS ***SUSPENDED***, NOT KILLED.
⭐               ⭐ Memory persists. ⭐⭐ BACKGROUND THREADS STOP
⭐               MID-EXECUTION AND RESUME ON THE NEXT INVOKE,
⭐               MINUTES OR HOURS LATER.
⭐   ⭐ INVOKE .... warm: skips INIT entirely.
⭐   ⭐ SHUTDOWN .. after ~5–15 minutes idle.

⭐⭐ ⇒ AND THE CONSEQUENCES THAT CATCH PYTHON DEVELOPERS
⭐   SPECIFICALLY:
⭐   ⭐⭐ ① ***YOUR async CODE DOES NOT INCREASE THROUGHPUT.***
⭐      ⭐ `asyncio` inside one invocation still serves one
⭐      request. ⭐⭐ CONCURRENCY IS AWS'S JOB NOW, AND THE ENTIRE
⭐      GIL/THREADS/ASYNC ARGUMENT OF DAYS 065–072 STOPS BEING
⭐      ABOUT REQUEST THROUGHPUT. ⭐ (It still matters ***inside***
⭐      one invocation — five parallel HTTP calls, yes.)
⭐   ⭐⭐ ② ***A BACKGROUND THREAD IS A BUG.*** ⭐ A metrics
⭐      flusher, a batching thread, an APM background sender:
⭐      ⭐⭐ THE FREEZE STOPS IT MID-WORK AND IT MAY NEVER RUN
⭐      AGAIN. ⭐ Flush synchronously before returning.
⭐   ⭐⭐ ③ ***GLOBAL STATE PERSISTS BETWEEN INVOCATIONS ON THE
⭐      SAME ENVIRONMENT.*** ⭐ Excellent for a boto3 client or a
⭐      loaded config. ⭐⭐ CATASTROPHIC FOR A MODULE-LEVEL
⭐      `current_user` — ⭐ you will serve one tenant's data to
⭐      another, ⭐⭐ INTERMITTENTLY, WHICH IS DAY 323's HIDDEN
⭐      STATE WITH THE WORST POSSIBLE FAILURE MODE.
⭐   ⭐ ④ `/tmp` (512 MB–10 GB) persists across warm invocations
⭐      too. ⭐⭐ USEFUL AS A CACHE, DANGEROUS AS AN ASSUMPTION.
```

# Part 2 — ⭐⭐ Cold starts, measured

```
⭐ INIT = ⭐ fetch and unpack the package
⭐       + ⭐ start the Python runtime (~100–200 ms)
⭐       + ⭐⭐ ***RUN EVERY MODULE-LEVEL IMPORT AND STATEMENT***
⭐       + ⭐ (in a VPC: an ENI is attached — ⭐⭐ ONCE ~10 s,
⭐          NOW ~100 ms SINCE THE 2019 REWRITE. ⭐ Older advice
⭐          says "never put Lambda in a VPC"; ⭐⭐ THAT ADVICE IS
⭐          OBSOLETE AND KNOWING SO IS WORTH SAYING.)

⭐⭐ AND FOR PYTHON, ***IMPORT TIME DOMINATES***:
⭐   ⭐ `import json`              ~0 ms
⭐   ⭐ `import boto3` + a client  ⭐⭐ ~300–500 ms
⭐   ⭐ `import requests`          ~50 ms
⭐   ⭐ `import pandas`            ⭐⭐ ~800–1,500 ms
⭐   ⭐ `import torch`             ⭐⭐ SEVERAL SECONDS
⭐   ⭐ a full Django app          ⭐⭐ 2–4 s

⭐⭐ ⇒ SO THE TOOL IS THE ONE FROM DAY 366: ***`python -X
⭐   importtime -c "import app"` AND READ THE TREE.*** ⭐ Nine
⭐   times out of ten there is one import costing 600 ms that a
⭐   single code path needs.

⭐ THE FIXES, RANKED BY VALUE PER EFFORT:
⭐ ① ⭐⭐ ***LAZY-IMPORT WHAT ONLY SOME PATHS NEED.*** ⭐ Move
⭐    `import pandas` inside the one function that uses it.
⭐    ⭐⭐ FREE, AND OFTEN HALVES THE COLD START.
⭐ ② ⭐⭐ ***CONSTRUCT CLIENTS AT MODULE LEVEL***, so warm
⭐    invocations reuse them (Day 382: client construction is
⭐    ~100 ms).
⭐ ③ ⭐ Trim the package. ⭐⭐ SHIP NO TESTS, NO `.pyc`, NO
⭐    `botocore` IF THE RUNTIME PROVIDES IT.
⭐ ④ ⭐ arm64 — ⭐⭐ ~20% CHEAPER AND USUALLY A FASTER INIT.
⭐ ⑤ ⭐ SnapStart (now available for Python) — ⭐ snapshots the
⭐    initialised environment and restores it. ⭐⭐ CHECK THE
⭐    CURRENT SUPPORT AND PRICING RATHER THAN TRUSTING ANY BLOG
⭐    POST, INCLUDING THIS ONE.
⭐ ⑥ ⭐ Provisioned concurrency — ⭐⭐ PRE-WARMED ENVIRONMENTS,
⭐    BILLED HOURLY WHETHER USED OR NOT. ⭐ Correct when p99
⭐    matters and traffic is predictable. ⭐⭐ IT IS ALSO AN
⭐    ADMISSION THAT YOU ARE PAYING FOR IDLE CAPACITY, WHICH IS
⭐    THE THING SERVERLESS WAS SUPPOSED TO REMOVE.
⭐ ⑦ ⭐⭐ AND THE HONEST ONE: ***IF COLD STARTS MATTER THIS MUCH,
⭐    THE WORKLOAD WANTS A CONTAINER.***

⭐ ⭐ On billing: initialisation is billed differently from
⭐   invocation and ⭐⭐ AWS HAS CHANGED THE RULES — ⭐ read the
⭐   current pricing page, ⭐⭐ AND TREAT "INIT IS FREE" AS
⭐   SOMETHING TO VERIFY, NOT TO REPEAT.
```

# Part 3 — ⭐⭐ Concurrency, and the database Lambda kills

```
⭐ ACCOUNT CONCURRENCY: ⭐ 1,000 by default, ⭐ raisable.
⭐ RESERVED CONCURRENCY: ⭐⭐ BOTH A CAP ***AND*** A GUARANTEE.
⭐   ⭐ Reserving 100 for a function means it can never exceed
⭐     100, ⭐⭐ AND THAT NOBODY ELSE CAN STARVE IT OF THOSE 100.
⭐   ⭐⭐ IT IS THEREFORE A BULKHEAD (DAY 336), AND IT IS THE
⭐     RIGHT TOOL FOR PROTECTING A DOWNSTREAM.
⭐ THROTTLED → `TooManyRequestsException` / 429. ⭐ Async
⭐   invocations retry; ⭐⭐ SYNCHRONOUS ONES JUST FAIL.

⭐⭐ NOW THE FAILURE THAT DEFINES SERVERLESS OPERATIONS:
⭐ ① ⭐ Traffic spikes. ⭐ Lambda scales to 800 concurrent
⭐    environments in seconds. ⭐ This is the feature.
⭐ ② ⭐⭐ EACH ONE OPENS A POSTGRES CONNECTION.
⭐ ③ ⭐⭐ YOUR db.t3.medium's `max_connections` IS ~410
⭐    (DAY 387).
⭐ ④ ⭐⭐ `FATAL: remaining connection slots are reserved` — ⭐ AND
⭐    NOT ONLY FOR LAMBDA. ⭐⭐ THE ECS SERVICE, THE WORKERS AND
⭐    THE ON-CALL ENGINEER'S psql ALL FAIL TOO.
⭐ ⑤ ⭐⭐ ⇒ A SPIKE ON ONE FUNCTION TOOK DOWN THE WHOLE PLATFORM,
⭐    AND THE AUTOSCALING WORKED PERFECTLY.

⭐⭐ ⇒ THE ANSWERS, IN ORDER:
⭐   ⭐⭐ ① ***RDS PROXY.*** ⭐ It exists for exactly this. ⭐ It
⭐      multiplexes and it absorbs the burst (Day 387 — ⭐ mind
⭐      the pinning caveat).
⭐   ⭐⭐ ② ***RESERVED CONCURRENCY AS A BULKHEAD*** — ⭐ cap the
⭐      function below what the database can survive. ⭐⭐ ONE
⭐      SETTING, NO NEW COMPONENT, AND IT IS THE ANSWER PEOPLE
⭐      FORGET.
⭐   ⭐ ③ Don't use a relational database from a
⭐      massively-concurrent Lambda at all — ⭐ DynamoDB's HTTP
⭐      model has no connection concept, ⭐⭐ WHICH IS THE REAL
⭐      REASON IT AND LAMBDA ARE PAIRED SO OFTEN. ⭐ That pairing
⭐      is architectural, not marketing.
```

# Part 4 — ⭐⭐ The cost curve, and where it inverts

```
⭐ PRICE: ⭐ $0.20 per million requests
⭐      + ⭐ $0.0000166667 per GB-second

⭐⭐ WORK ONE EXAMPLE ALL THE WAY THROUGH — ⭐ a 200 ms handler
⭐   at 512 MB, ***100 requests/second***:
⭐   ⭐ requests: 259M/month × $0.20/M ........ ⭐ $52
⭐   ⭐ compute: 259M × 0.2 s × 0.5 GB
⭐     = 25.9M GB-s × $0.0000167 ............. ⭐⭐ $432
⭐   ⭐⭐ TOTAL ≈ $484/MONTH
⭐   ⭐ The same load on ***two*** Fargate tasks
⭐     (1 vCPU / 2 GB): ⭐⭐ ≈ $70/MONTH.

⭐⭐ ⇒ SO STATE IT PRECISELY, BECAUSE BOTH SLOGANS ARE WRONG:
⭐   ⭐⭐ ***SERVERLESS IS DRAMATICALLY CHEAPER AT LOW AND SPIKY
⭐   VOLUME, AND SEVERAL TIMES MORE EXPENSIVE AT STEADY HIGH
⭐   VOLUME.*** ⭐ For a typical Python API the crossover is
⭐   somewhere around ***30–80 requests/second sustained***,
⭐   ⭐ depending on duration and memory.
⭐   ⭐⭐ AND AT 1 REQUEST/SECOND, LAMBDA COSTS ABOUT $5 AND
⭐   FARGATE STILL COSTS $70 — ⭐ which is the case people
⭐   correctly love it for.

⭐ ⭐⭐ THE MEMORY DIAL IS ALSO A ***CPU*** DIAL: ⭐ vCPU scales
⭐   with memory (1,769 MB ≈ 1 vCPU). ⭐⭐ SO DOUBLING MEMORY CAN
⭐   ***HALVE*** DURATION AND COST THE SAME OR LESS. ⭐ Never
⭐   assume the smallest memory is cheapest — ⭐⭐ MEASURE IT.
⭐   AWS Lambda Power Tuning does this automatically and it is
⭐   twenty minutes well spent.
```

# Part 5 — Where Python + Lambda is genuinely the best answer

```
⭐⭐ THE SHAPE IT FITS: ***EVENT-DRIVEN GLUE THAT IS IDLE MOST OF
⭐   THE TIME AND MUST NOT BE OPERATED.***

⭐ ① ⭐⭐ S3 EVENT → PROCESS. ⭐ Thumbnails, virus scan, metadata
⭐    extraction, ⭐ the upload confirmation from Day 386.
⭐ ② ⭐ SQS CONSUMER. ⭐⭐ AWS OWNS THE POLLING LOOP, THE
⭐    CONCURRENCY AND THE DLQ ROUTING — ⭐ genuinely less code
⭐    than Celery, and less to operate.
⭐ ③ ⭐ SCHEDULED JOBS. ⭐⭐ A CRON THAT NEEDS NO SERVER AND
⭐    CANNOT SILENTLY STOP RUNNING BECAUSE A BOX WAS REPLACED.
⭐ ④ ⭐ SPIKY LOW-VOLUME APIs. ⭐ Internal tools, webhooks,
⭐    admin endpoints.
⭐ ⑤ ⭐ Step Functions steps, ⭐ EventBridge targets, ⭐ custom
⭐    Terraform/CloudFormation resources.

⭐ THE IDIOMS THAT MAKE IT PROFESSIONAL:
⭐   ⭐⭐ ① ***THE HANDLER IS THREE LINES: PARSE, CALL A PLAIN
⭐      FUNCTION, FORMAT.*** ⭐ Business logic lives in an
⭐      importable module ⭐⭐ SO IT IS TESTABLE WITHOUT AWS AND
⭐      PORTABLE OFF LAMBDA.
⭐   ⭐ ② `aws-lambda-powertools` — ⭐ structured logging with
⭐      the request id, ⭐ tracing, metrics, ⭐⭐ AND AN
⭐      `@idempotent` DECORATOR BACKED BY DYNAMODB, WHICH IS DAY
⭐      335's DEDUP GUARD AS A DEPENDENCY.
⭐   ⭐⭐ ③ ***BATCH ITEM FAILURES.*** ⭐ Return
⭐      `{"batchItemFailures": [{"itemIdentifier": id}, ...]}`
⭐      ⭐⭐ OR ONE POISON MESSAGE REDELIVERS THE WHOLE BATCH OF
⭐      TEN AND YOU REPROCESS NINE SUCCESSES (DAY 393).
⭐   ⭐ ④ A DLQ, ⭐ and an alarm on it. ⭐⭐ A DLQ NOBODY WATCHES IS
⭐      A DATA-LOSS DEVICE WITH EXTRA STEPS.
```

# Part 7 — Packaging Python for Lambda

```
⭐ ZIP (250 MB unzipped) vs ⭐ CONTAINER IMAGE (10 GB).
⭐   ⭐⭐ USE THE IMAGE FOR ANYTHING WITH REAL DEPENDENCIES — ⭐ it
⭐   also means one build system for Lambda and ECS (Day 363).

⭐⭐ AND THE TRAP THAT IS DAY 360's C-EXTENSION ARGUMENT COMING
⭐   BACK TO COLLECT:
⭐   ⭐⭐ ***A WHEEL BUILT ON YOUR MAC WILL NOT LOAD IN LAMBDA.***
⭐   ⭐ `pydantic-core`, `cryptography`, `numpy`, `psycopg[binary]`
⭐     are compiled against a specific libc and CPU.
⭐   ⭐⭐ THE ERROR IS `Runtime.ImportModuleError: No module named
⭐     'pydantic_core._pydantic_core'` — ⭐ which reads like a
⭐     missing dependency and is actually an architecture
⭐     mismatch.
⭐   ⭐⭐ ⇒ ALWAYS BUILD IN `public.ecr.aws/lambda/python:3.12`
⭐     OR WITH `--platform manylinux2014_aarch64`, ⭐ and match
⭐     the function's architecture. ⭐⭐ THIS IS EXACTLY WHY
⭐     CONTAINERS EXIST (DAY 360), AND IT IS SATISFYING THAT THE
⭐     ARGUMENT LANDS HERE.

⭐ LAYERS: ⭐ shared dependencies across functions. ⭐⭐ AND THE
⭐   HONEST DOWNSIDE — ⭐ they are versioned artefacts with their
⭐   own lifecycle, they do not appear in your lockfile,
⭐   ⭐⭐ AND "WHICH LAYER VERSION IS THIS FUNCTION ON" BECOMES A
⭐   QUESTION YOU CANNOT ANSWER FROM THE REPOSITORY. ⭐ Prefer
⭐   container images.
```

# 💬 Interview

**1. ⭐⭐ "Explain Lambda's concurrency model."**
> ⭐ One execution environment serves exactly one request at a time, so serving two hundred concurrent
> requests means two hundred environments. ⭐⭐ **That single fact explains everything else: async code
> doesn't raise throughput because concurrency is now AWS's job; a background thread is a bug because
> the environment is frozen between invocations and the thread stops mid-work; and global state
> persists across invocations on the same environment — which is great for a boto3 client and
> catastrophic for a module-level `current_user`, because you'll serve one tenant's data to another,
> intermittently.**

**2. "What's a Python cold start made of, and how do you reduce it?"**
> ⭐ Package fetch, runtime start at a hundred to two hundred milliseconds, ⭐⭐ **and then every
> module-level import — which for Python is the part that dominates: boto3 with a client is 300–500
> ms, pandas is a second or more, a full Django app is two to four seconds.** ⭐ So I run
> `python -X importtime` and read the tree; there's almost always one import costing 600 ms that only
> one code path needs. ⭐⭐ **Lazy-import those, construct clients at module level so warm invocations
> reuse them, trim the package, and use arm64.** ⭐ Provisioned concurrency if p99 matters and traffic
> is predictable — ⭐⭐ **though that's an admission you're paying for idle capacity, which is the thing
> serverless was meant to remove.** ⭐ And I'd note the VPC advice people still repeat is obsolete: the
> ENI attachment was rearchitected and it's around a hundred milliseconds now, not ten seconds.

**3. ⭐⭐ "A Lambda spike took down our database. Walk me through it."**
> ⭐ The autoscaling worked perfectly, which is the problem. ⭐⭐ **Lambda scaled to eight hundred
> environments in seconds, each opened a Postgres connection, and `max_connections` on a t3.medium is
> about 410 — so the database refused connections not just to Lambda but to the ECS service, the
> workers, and the on-call engineer's psql.** ⭐ One function's spike became a platform outage. ⭐ Three
> answers in order: ⭐⭐ **RDS Proxy, which exists for exactly this; reserved concurrency as a bulkhead,
> capping the function below what the database survives — one setting, no new component, and it's the
> one people forget; or don't use a relational database from a massively concurrent Lambda at all,**
> ⭐ which is the actual architectural reason DynamoDB and Lambda are paired so often — HTTP has no
> connection concept.

**4. ⭐⭐ "Is serverless cheaper?"**
> ⭐ At low and spiky volume, dramatically. At steady high volume, no — and I'd do the arithmetic.
> ⭐⭐ **A 200 ms handler at 512 MB serving 100 requests a second is about $484 a month; two Fargate
> tasks handling the same load are about $70.** ⭐ At one request a second it's five dollars against
> seventy, which is the case people rightly love it for. ⭐⭐ **So the crossover for a typical Python
> API is somewhere around 30 to 80 requests a second sustained.** ⭐ One more thing worth knowing:
> ⭐⭐ **the memory dial is also a CPU dial, so doubling memory can halve duration and cost the same or
> less — never assume the smallest memory setting is cheapest, measure it.**

**5. "When would you not use Lambda?"**
> ⭐ Sustained high throughput, per the arithmetic. ⭐ Anything with large memory-resident state — a two
> gigabyte model reloaded on every cold start is fatal, ⭐⭐ **and provisioned concurrency to avoid that
> is just paying to keep a server warm with worse ergonomics.** ⭐ Anything wanting a persistent
> connection pool. ⭐ And the fifteen-minute ceiling, ⭐⭐ **where the real cost isn't the limit — it's
> that you now build checkpointing and resumption for something that would otherwise have been a for
> loop.** ⭐ That complexity is the price and it's rarely counted. ⭐ Plus the honest operational one:
> ⭐⭐ **no shell, no profiler on a live process, approximate local emulation — that cost lands on
> whoever is on call.**

**6. ⭐⭐ "`No module named 'pydantic_core._pydantic_core'` in Lambda. What is it?"**
> ⭐ Not a missing dependency — ⭐⭐ **an architecture mismatch. The wheel was built on a Mac, and
> pydantic-core is a compiled extension linked against a specific libc and CPU architecture.** ⭐ The
> fix is to build inside the AWS Lambda Python base image, or with an explicit
> `--platform manylinux2014_aarch64`, matching the function's architecture. ⭐⭐ **It's the exact
> problem containers were invented to solve, arriving one more time.**

## 🎙️ Articulation drill

**Two minutes.** Open with the one fact: **an execution environment serves exactly one request at a
time — and everything surprising follows from it.** Async doesn't increase throughput because
concurrency is AWS's job now; **a background thread is a bug, because the environment is frozen
between invocations and the thread stops mid-work**; and global state persisting is great for a boto3
client and catastrophic for anything request-scoped. Then cold starts, with numbers: **import time
dominates for Python — boto3 is 300–500 ms, pandas over a second, Django two to four seconds — so I
run `-X importtime` and lazy-import the one thing that costs 600 ms and is used by one path.** Then
the operational story: **a Lambda spike scaled to 800 environments, each opened a Postgres connection
against a 410-connection database, and the database refused everyone — the ECS service, the workers,
and the on-call engineer's psql. Autoscaling worked perfectly and took down the platform.** Fixes:
**RDS Proxy, or reserved concurrency as a bulkhead capping the function below what the database
survives — one setting, and the one people forget.** Then the cost, precisely: **a 200 ms handler at
512 MB and 100 rps is about $484 a month against $70 of Fargate; at 1 rps it's $5 against $70. So
serverless is dramatically cheaper when spiky and several times more expensive when steady, and the
crossover is roughly 30 to 80 rps.** Close on where it's genuinely best — **event glue that's idle
most of the time and must not be operated** — and the packaging trap: **a wheel built on a Mac won't
load, because pydantic-core is compiled against a specific libc, which is the exact problem containers
exist to solve.**
