# Day 074

**L-074** · ⭐ **Modules, packages and imports** — `sys.path`, circular imports, `__init__.py`

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `import` executes a file, once, and caches the result in
> `sys.modules`.** Every confusing import behaviour — circular imports, stale state, a module that
> "ran twice" — follows from that one sentence.
>
> ⭐ This is the day that fixes `ModuleNotFoundError` for good, and explains why a circular import
> sometimes works and sometimes does not.

---

# Part 1 — ⭐⭐ What `import` does

```
⭐⭐ import foo  ⇒
⭐   1. ⭐⭐ IS "foo" IN sys.modules?  ⇒ YES: bind the name and STOP. Nothing re-executes.
⭐   2. find it — walk sys.path, using the FINDERS in sys.meta_path
⭐   3. ⭐ create an empty module object and ⭐⭐ PUT IT IN sys.modules IMMEDIATELY
⭐        ⇒ ⭐⭐ BEFORE executing it. This is the key to circular imports (Part 3).
⭐   4. ⭐ EXECUTE the file top to bottom, populating that module's namespace
⭐   5. bind the name in the importing namespace
```

```python
import sys
sys.modules["json"]           # ⭐ the cached module object
sys.path                      # ⭐⭐ the search order — a plain list you can inspect
json.__file__                 # ⭐ where it came from
```

```
⭐⭐ sys.path IS BUILT FROM, IN ORDER:
⭐   1. ⭐⭐ the SCRIPT'S DIRECTORY (for `python app.py`) — or the CWD (for `python -m` / -c / REPL)
⭐   2. PYTHONPATH
⭐   3. the standard library
⭐   4. site-packages (your virtualenv)
⭐
⭐ ⇒ ⭐⭐ ENTRY 1 IS THE ENTIRE SOURCE OF ModuleNotFoundError CONFUSION:
⭐      `python app.py` puts app.py's OWN directory first;
⭐      `python -m app` puts the CURRENT WORKING DIRECTORY first.
⭐   ⇒ ⭐⭐ so the same code imports fine one way and fails the other — and `-m` is
⭐        almost always the one that behaves like an installed package.
```

⚠️ ⭐⭐ **The shadowing trap:** a file called `json.py`, `random.py`, `email.py` or `types.py` in your
project directory **shadows the standard library**, because entry 1 comes before entry 3. **The error
is bizarre and distant** — something deep inside a library fails because it imported *your* `json`.
**Check `module.__file__` when an import behaves impossibly.**

⭐ **The real fix for import paths: install your project.** `pip install -e .` (or `uv pip install
-e .`) puts your package on `sys.path` properly, and **then it works identically from anywhere** —
tests, scripts, the REPL. ⚠️ **`sys.path.append` at the top of a file is the hack that keeps working
until it does not.**

# Part 2 — ⭐ Packages and `__init__.py`

```
⭐ myapp/
⭐   __init__.py          ⭐⭐ makes it a REGULAR package; runs when the package is imported
⭐   models.py
⭐   services/
⭐     __init__.py
⭐     billing.py
```

```python
from myapp.services import billing        # ⭐⭐ ABSOLUTE — always prefer this
from . import models                      # ⭐ relative — only inside a package
from .models import User                  # ⭐ one level up: from ..models import User
```

⭐⭐ **Absolute imports are the default for a reason:** they work identically in a script, a test and
an installed package, and they say where the thing lives. ⚠️ **Relative imports break the moment a
file is run directly** (`python myapp/services/billing.py` fails with *"attempted relative import
with no known parent package"*) — **because a directly-run file has no package context.**

```python
# ⭐⭐ __init__.py has one genuinely good use: DEFINING THE PUBLIC API.
# myapp/__init__.py
from .models import User, Order
__all__ = ["User", "Order"]        # ⭐ what `from myapp import *` exports, and a signal to readers
```

⚠️ ⭐⭐ **And one bad one: heavy work at import time.** Anything in `__init__.py` runs whenever
*anything* in the package is imported — **so a `__init__.py` that connects to a database or loads a
model makes `import myapp.utils` slow and fragile**, and it is a common cause of a slow CLI or a cold
Lambda (Day 073's `-X importtime`).

⭐ **Namespace packages** (no `__init__.py`, PEP 420) let one package span directories — useful for
plugin systems, ⚠️ **and a frequent accident**: a missing `__init__.py` silently creates one, and then
two directories with the same name merge in confusing ways. **Be deliberate.**

```python
if __name__ == "__main__":       # ⭐⭐ "am I the entry point, or was I imported?"
    main()
# ⭐ __name__ is "__main__" when run directly, "myapp.cli" when imported.
# ⇒ ⭐⭐ and this is what Day 068 needed for `spawn`.
```

# Part 3 — ⭐⭐ Circular imports

```python
# a.py
from b import helper
def thing(): ...

# b.py
from a import thing              # ⭐⭐ ImportError: cannot import name 'thing' from partially
def helper(): ...                #    initialized module 'a' (most likely due to a circular import)
```

```
⭐⭐ WHY, FROM STEP 3 OF PART 1 — this is the whole explanation:
⭐   import a ⇒ `a` is put in sys.modules (EMPTY) ⇒ a.py starts executing
⭐   ⇒ line 1: `from b import helper` ⇒ b.py starts executing
⭐   ⇒ b line 1: `from a import thing` ⇒ ⭐⭐ `a` IS in sys.modules, so it is NOT re-executed —
⭐        but it is only PARTIALLY BUILT: `thing` has not been defined yet.
⭐   ⇒ ⭐⭐ ImportError.
⭐
⭐ ⭐⭐ THE ASYMMETRY THAT MAKES THIS CONFUSING:
⭐   `import a` then `a.thing()`  ⇒ ⭐ often WORKS — the lookup happens at CALL time, by
⭐                                   which point `a` is fully built.
⭐   `from a import thing`        ⇒ ⭐⭐ FAILS — the name must exist NOW, at import time.
⭐   ⇒ ⭐ which is why the same cycle appears to work or break depending on import STYLE,
⭐        and why it can start failing when someone changes an import for tidiness.
```

```
⭐⭐ THE FIXES, IN ORDER — and the first is the only real one:
⭐ 1. ⭐⭐ FIX THE DESIGN. A cycle means two modules are one concept, or a dependency
⭐      points the wrong way. ⇒ ⭐⭐ extract the shared piece into a third module, or
⭐      invert the dependency with a Protocol (Day 056) so the low-level module
⭐      no longer imports the high-level one.
⭐ 2. ⭐ `import a` instead of `from a import thing` — defers the lookup to call time
⭐ 3. ⭐ MOVE THE IMPORT INSIDE THE FUNCTION — runs at call time, when both are built
⭐      ⇒ ⭐ legitimate, and worth a comment saying why
⭐ 4. ⭐⭐ TYPE-ONLY imports ⇒ `if TYPE_CHECKING:` (Day 061) — ⭐⭐ costs nothing at runtime
⭐      and is the right answer when the cycle exists ONLY because of annotations.
```

⭐⭐ **Option 4 covers a surprising share of real cycles**, because type hints create dependencies
that do not exist at runtime — `models.py` needing `services.py` only to annotate a return type.

# Part 4 — ⭐ Module-level state

```python
# ⭐⭐ A MODULE IS A SINGLETON: imported once, cached in sys.modules, shared by everything.
# config.py
settings = Settings()            # ⭐ built ONCE, at first import
```

```
⭐⭐ THE CONSEQUENCES, GOOD AND BAD:
⭐   ✓ ⭐⭐ this is the IDIOMATIC PYTHON SINGLETON (Day 053) — no metaclass, no __new__,
⭐        no double-checked locking, and it is thread-safe because import is locked.
⭐   ✗ ⭐ import order becomes load-bearing if modules mutate each other's state
⭐   ✗ ⭐⭐ it is PER PROCESS (Days 021, 016) — four uvicorn workers means four `settings`
⭐        objects, four caches, four rate-limit counters. Anything shared goes in Redis.
⭐   ✗ ⭐ it makes testing harder — a module-level client is hard to substitute
⭐        ⇒ ⭐⭐ which is Day 055's argument for injecting collaborators
```

⚠️ ⭐⭐ **Reading configuration at import time is the specific version that bites.** A module-level
`API_KEY = os.environ["API_KEY"]` fails at *import*, so your test suite cannot even collect without
the variable set. ⭐ **Read config in a function, or in a lazily-created settings object** (Day 021's
`pydantic-settings` validated at startup is the better shape — it still fails fast, but at *startup*,
not at import of any module that happens to touch it).

```python
importlib.reload(module)     # ⚠️ ⭐ re-executes it, but existing objects keep the OLD classes
                             #    ⇒ isinstance breaks. Useful in a REPL, never in production.
importlib.import_module("myapp.plugins." + name)     # ⭐ dynamic import — a plugin loader
```

⭐ **`python -m module` runs a module as a script** with the CWD on `sys.path`, and **it is the right
way to run anything inside a package** — `python -m myapp.cli`, `python -m pytest`, `python -m
http.server`. ⭐⭐ **Using `python -m pip` rather than `pip` guarantees you get the pip belonging to
that interpreter**, which is the fix for half of all "I installed it and it is not there" problems.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **A file named `json.py` / `types.py`** | ⭐⭐ Shadows the stdlib. Check `module.__file__`. |
| ⭐ `sys.path.append` to fix imports | ⭐⭐ Install the project with `-e .`. |
| ⭐ `python app.py` vs `python -m app` | ⭐⭐ Different `sys.path[0]`. Prefer `-m`. |
| Relative imports in a runnable file | ⭐ No parent package. Use absolute. |
| Heavy work in `__init__.py` | ⭐⭐ Runs on any import of the package. |
| Missing `__init__.py` by accident | ⭐ Silently becomes a namespace package. |
| ⭐⭐ **Working around a cycle instead of fixing it** | ⭐⭐ A cycle is a design signal. |
| Not knowing why `import a` works and `from a import x` fails | ⭐ Call-time vs import-time lookup. |
| Config read at import time | ⭐⭐ Tests cannot even collect. Read it in a function. |
| Expecting module state to be shared across workers | ⭐ Per process. Redis. |
| `importlib.reload` in production | ⭐ Old objects keep old classes; `isinstance` breaks. |
| `pip install` with the wrong interpreter | ⭐ `python -m pip`. |

## Interview questions

**Q: What actually happens on `import foo`?**
> Python checks `sys.modules` first — if it's there, it binds the name and stops, so a module is
> executed exactly once per process. Otherwise it searches `sys.path`, creates an empty module object,
> puts it in `sys.modules` *before* executing the file, then runs the file top to bottom to populate
> its namespace. That "insert before execute" step is the key to understanding circular imports, and
> the "once per process" part is why a module is Python's natural singleton.

**Q: Why do circular imports sometimes work and sometimes fail?**
> Because of *when* the name is looked up. During a cycle, the partially-initialised module is already
> in `sys.modules`, so it isn't re-executed — but the names defined below the import line don't exist
> yet. `from a import thing` needs `thing` to exist immediately, so it raises; plain `import a`
> followed by `a.thing()` defers the attribute lookup to call time, by which point the module is fully
> built. That asymmetry is why a cycle can break when someone tidies an import, with no other change.

**Q: How do you fix a circular import?**
> Fix the design first — a cycle usually means two modules are really one concept, or a dependency
> points the wrong way, and the answer is to extract the shared part into a third module or invert the
> dependency with a Protocol so the low-level module stops importing the high-level one. If the cycle
> exists only because of type annotations, `if TYPE_CHECKING:` removes it at zero runtime cost, and
> that covers a surprising share of real cases. Moving an import inside a function works and is worth
> a comment explaining why, but it's a workaround rather than a fix.

**Q: What's `__init__.py` for?**
> Marking a regular package and, more usefully, defining the package's public API — re-exporting the
> names you want callers to use and setting `__all__`. What it shouldn't contain is work, because it
> runs whenever anything in the package is imported: a database connection or a model load in
> `__init__.py` makes `import myapp.utils` slow and fragile, and it's a common cause of slow CLI
> startup or cold-start latency. Since PEP 420 an absent `__init__.py` creates a namespace package
> rather than an error, which is useful for plugins and a frequent accident otherwise.

**Q: Why does `python app.py` import differently from `python -m app`?**
> Because `sys.path[0]` differs: running a script puts *the script's directory* first, while `-m` puts
> the current working directory first and imports the module through the normal package machinery. So
> the same code can import fine one way and fail the other, and `-m` is the one that behaves like an
> installed package. The real fix for both is to install the project in editable mode, so the package
> is on `sys.path` properly and it works identically from tests, scripts and the REPL — rather than
> appending to `sys.path` at the top of a file.

**Q: What are the consequences of module-level state?**
> A module is imported once and cached, so module-level objects are effectively singletons — and
> that's the idiomatic Python singleton, with no metaclass or double-checked locking, and thread-safe
> because import is locked. The costs are that it's per *process*, so four workers means four separate
> caches and counters and anything shared belongs in Redis; that it makes testing harder, since a
> module-level client is hard to substitute; and specifically that reading configuration at import
> time means the test suite can't even collect without the environment set. Config belongs in a
> function or a settings object validated at startup.
