**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: dependency injection is "pass what you need in" — it is a design
> decision, not a library. And in Python you can get almost all of it with a function parameter,
> which is why importing Java's container culture is one of the most common unforced errors in the
> language.**
>
> ⭐ Days 300–302 defined ports, repositories and services. ⭐⭐ Today is the boring, load-bearing
> question of who constructs them, where, and what that does to your tests.

# Part 1 — ⭐⭐ What DI is, before any framework

```python
# ❌ THE DEPENDENCY IS HIDDEN AND UNCHANGEABLE
class OrderService:
    def __init__(self):
        self.payments = StripeClient(os.environ["STRIPE_KEY"])   # ⭐⭐ HERE

# ⭐⭐ THE DEPENDENCY IS DECLARED AND SUPPLIED
class OrderService:
    def __init__(self, payments: PaymentPort):
        self.payments = payments
```

```
⭐⭐ THAT IS THE ENTIRE PATTERN. THE SECOND VERSION:
⭐   ⭐ says in its signature what it needs — ⭐⭐ THE
⭐     CONSTRUCTOR IS NOW DOCUMENTATION THAT CANNOT GO STALE
⭐   ⭐ can be given a fake in a test with no patching
⭐   ⭐ cannot reach out and construct something at import time
⭐   ⇒ ⭐⭐ AND CRUCIALLY: THE FIRST VERSION IS UNTESTABLE
⭐     WITHOUT `mock.patch`, AND `mock.patch` COUPLES YOUR TEST
⭐     TO AN ***IMPORT PATH*** — so moving the file breaks a
⭐     test that never mentioned the moved thing.

⭐ ⭐ THE THREE STYLES, AND WHEN EACH FITS:
⭐   ⭐ CONSTRUCTOR — the default. Required collaborators.
⭐   ⭐ PARAMETER   — ⭐⭐ THE MOST PYTHONIC. Pass `uow` to the
⭐        function that needs it (Day 302). ⭐ Nothing to
⭐        construct at all.
⭐   ⭐ SETTER      — ⭐ almost never. It permits a
⭐        half-constructed object, which is a state you then
⭐        have to defend against forever.
```

# Part 2 — ⭐⭐ The composition root

```
⭐⭐ ONE PLACE KNOWS HOW EVERYTHING IS WIRED, AND IT IS AT THE
⭐   ***EDGE*** — `main.py`, the worker entrypoint, the CLI.

⭐   ⭐ It reads configuration.
⭐   ⭐ It constructs adapters (Stripe, Postgres, Redis).
⭐   ⭐ It constructs services, passing those adapters in.
⭐   ⭐ It hands the assembled object graph to the framework.

⭐⭐ AND THE RULE THAT MAKES IT WORTH HAVING:
⭐   ***NOTHING ELSE CONSTRUCTS INFRASTRUCTURE.***
⭐   ⇒ ⭐ One `StripeClient(...)` buried in a service is enough
⭐     to break the whole property, ⭐⭐ BECAUSE NOW THERE ARE
⭐     TWO PLACES THAT KNOW ABOUT STRIPE AND ONLY ONE OF THEM
⭐     IS OBVIOUS.
⭐   ⇒ ⭐ It is greppable: `grep -rn "Client(" app/ --exclude
⭐     main.py` should return nothing.

⭐⭐ THE PAYOFF IS THAT YOU HAVE ***THREE*** COMPOSITION ROOTS
⭐   AND THEY SHARE THE SAME SERVICES:
⭐   ⭐ the API — real adapters
⭐   ⭐ the worker — ⭐⭐ THE SAME SERVICES, DIFFERENT ENTRY
⭐        (Day 302's structural test, made structural)
⭐   ⭐ the tests — fakes for ports, real Postgres for storage
⭐   ⇒ ⭐⭐ IF YOU CANNOT WRITE THE THIRD ONE IN TWENTY LINES,
⭐     YOUR DEPENDENCIES ARE NOT INJECTED — THEY ARE IMPORTED.
```

# Part 3 — ⭐⭐ Python's advantages, used properly

```
⭐⭐ ① DEFAULT ARGUMENTS — DI WITH ZERO CEREMONY:
⭐     def send_receipt(order, mailer: Mailer = default_mailer):
⭐     ⭐ Production passes nothing; tests pass a fake.
⭐     ⭐⭐ AND THE TRAP: THE DEFAULT IS EVALUATED ***AT IMPORT
⭐       TIME***, so `= SMTPClient()` opens a connection when
⭐       the module is imported. ⭐ Use a sentinel or a factory.

⭐⭐ ② `functools.partial` — pre-bind the dependency:
⭐     `complete = partial(complete_job, uow=uow)`
⭐     ⭐ A "configured service" with no class involved.

⭐⭐ ③ `Protocol` (Day 300) — ⭐⭐ THE TYPE OF A DEPENDENCY
⭐     WITHOUT AN IMPORT OF ITS IMPLEMENTATION.

⭐⭐ ④ MODULES ARE SINGLETONS — an import caches. ⭐ Genuinely
⭐     useful for stateless config; ⭐⭐ AND IT IS EXACTLY WHY
⭐     PART 4'S BUG IS SO COMMON.

⭐ ⇒ ⭐⭐ THE HONEST CONCLUSION: ***A FUNCTION PARAMETER WITH A
⭐   DEFAULT GETS YOU 90% OF WHAT A JAVA DI FRAMEWORK PROVIDES,
⭐   BECAUSE PYTHON HAS FIRST-CLASS FUNCTIONS AND NO COMPILE
⭐   STEP.*** ⭐ The remaining 10% is lifecycle management
⭐   (Part 6), and you should adopt machinery for that only
⭐   when you actually have the problem.
```

# Part 4 — ⭐⭐ The global singleton, and the bug it causes

```python
# app/db.py
engine = create_engine(os.environ["DATABASE_URL"])   # ⭐⭐ AT IMPORT TIME
SessionLocal = sessionmaker(bind=engine)
```

```
⭐⭐ WHAT THIS COSTS, AND THE THIRD ONE IS THE ONE THAT WASTES
⭐   A WHOLE AFTERNOON:
⭐   ① ⭐ `DATABASE_URL` MUST EXIST TO IMPORT THE MODULE — so
⭐     the import graph now depends on the environment.
⭐   ② ⭐ You cannot use a different database per test without
⭐     patching a module attribute.
⭐   ③ ⭐⭐ `pytest --collect-only` ***CONNECTS TO A DATABASE***.
⭐     ⭐ Collection imports every test module, which imports
⭐       the app, which builds an engine. ⭐⭐ SO "LIST MY
⭐       TESTS" FAILS IN CI BECAUSE A DATABASE IS UNREACHABLE,
⭐       and the error message mentions neither collection nor
⭐       the database.
⭐   ④ ⭐ In a forking worker (Day 265), a connection created
⭐     before the fork is ⭐⭐ SHARED BETWEEN PROCESSES, which
⭐     corrupts the protocol in ways that look like random
⭐     database errors.

⭐⭐ THE FIX IS NOT A LIBRARY — IT IS A FUNCTION:
⭐   ⭐ `def make_engine(settings) -> Engine:` called by the
⭐     composition root. ⭐⭐ NOTHING HAPPENS AT IMPORT TIME.
⭐   ⇒ ⭐ Rule of thumb: ⭐⭐ IMPORTING A MODULE MUST NEVER
⭐     OPEN A SOCKET, READ A FILE, OR REQUIRE AN ENVIRONMENT
⭐     VARIABLE. ⭐ Verify it: `python -c "import app.main"`
⭐     with an empty environment should succeed.
```

```
⭐⭐ AND `mock.patch` AS A SUBSTITUTE FOR DI:
⭐   ⭐ It works, which is why it is everywhere.
⭐   ⭐⭐ BUT IT COUPLES THE TEST TO ***WHERE THE THING IS
⭐     IMPORTED***, not to what it does. ⭐ Move the import and
⭐     the test breaks. ⭐ Patch the wrong path and the test
⭐     silently passes against the real thing.
⭐   ⇒ ⭐⭐ THE SEAM IS ***DISCOVERED*** RATHER THAN DESIGNED,
⭐     and discovered seams move.
```

# Part 5 — ⭐⭐ FastAPI's `Depends` is a container — with a boundary

```python
def get_uow(session: Session = Depends(get_session)) -> UnitOfWork:
    return SqlUnitOfWork(session)

@router.post("/jobs/{id}/complete")
def complete(id: UUID, uow: UnitOfWork = Depends(get_uow),
             user: User = Depends(current_user)):
    return jobs.complete_job(uow, CompleteJob(id, user.tenant_id))
```

```
⭐⭐ WHAT IT GENUINELY GIVES YOU:
⭐   ⭐ REQUEST-SCOPED LIFECYCLE, with teardown, done correctly
⭐     — ⭐ the thing hand-rolled DI gets wrong most often.
⭐   ⭐ `app.dependency_overrides[get_uow] = fake` in tests, ⭐⭐
⭐     WHICH IS A ***DESIGNED*** SEAM RATHER THAN A PATCHED ONE.
⭐   ⭐ Caching within a request, so `current_user` resolves once.

⭐⭐ AND THE BOUNDARY PEOPLE MISS:
⭐   ⭐⭐ `Depends` ONLY WORKS AT THE HTTP EDGE. ⭐ Your Celery
⭐     task, your cron job and your CLI have no request, so they
⭐     ⭐⭐ CANNOT USE IT AT ALL.
⭐   ⇒ ⭐⭐ SO SERVICES MUST STILL TAKE THEIR DEPENDENCIES AS
⭐     PARAMETERS. `Depends` WIRES THE ***EDGE***; IT MUST NOT
⭐     REACH INTO THE SERVICE LAYER.
⭐   ⇒ ⭐ A service with `= Depends(...)` in its signature is a
⭐     service only the web can call — ⭐⭐ WHICH FAILS DAY
⭐     302'S TEST, AND IT FAILS IT INVISIBLY, BECAUSE THE CODE
⭐     LOOKS TIDY.
```

# Part 6 — ⭐ When to build or adopt a container

```
⭐⭐ THE TWO HONEST SIGNALS:
⭐   ① ⭐ THE COMPOSITION ROOT IS LONGER THAN A SCREEN and
⭐     changing one adapter means editing four call sites.
⭐   ② ⭐⭐ LIFECYCLE MANAGEMENT HAS BECOME MANUAL — singleton
⭐     vs per-request vs per-task, with teardown, ⭐ and you
⭐     have written the same `try/finally` five times.

⭐ ⇒ ⭐ Until then, ⭐⭐ A DICT AND A FUNCTION ARE A CONTAINER:
```

```python
@dataclass(frozen=True)
class Container:
    settings: Settings
    engine: Engine
    payments: PaymentPort
    mailer: Mailer

    def uow(self) -> UnitOfWork:              # ⭐ per-call scope
        return SqlUnitOfWork(Session(self.engine))

def build(settings: Settings) -> Container:   # ⭐⭐ THE ROOT
    engine = make_engine(settings)
    return Container(
        settings=settings,
        engine=engine,
        payments=StripeAdapter(settings.stripe_key),
        mailer=SesMailer(settings.region),
    )
```

```
⭐⭐ FORTY LINES, NO DEPENDENCY, AND IT DOES EVERYTHING YOU
⭐   NEED: ⭐ explicit, typed, greppable, ⭐⭐ AND
⭐   `build(test_settings)` GIVES YOU THE ENTIRE TEST WIRING IN
⭐   ONE CALL.
⭐ ⇒ ⭐ If you later adopt `dependency-injector` or `svcs`, you
⭐   will be replacing something you understand, ⭐⭐ WHICH IS
⭐   THE ONLY GOOD REASON TO ADOPT ANY FRAMEWORK.
```

# Part 7 — ⭐⭐ What good DI does to your tests

```
⭐   ⭐ ❌ `@mock.patch("app.services.jobs.StripeClient")`
⭐        ⇒ ⭐ couples to an import path; breaks on a move;
⭐          silently passes if the path is wrong.
⭐   ⭐ ✅ `complete_job(uow, cmd, payments=FakePayments())`
⭐        ⇒ ⭐⭐ COUPLES TO THE INTERFACE, WHICH IS THE THING
⭐          YOU ACTUALLY DEPEND ON.

⭐⭐ AND THE DIAGNOSTIC WORTH RUNNING TODAY:
⭐   ***COUNT `mock.patch` CALLS IN YOUR TEST SUITE.***
⭐   ⇒ ⭐ Each one is a place where a dependency was not
⭐     injected. ⭐⭐ THE NUMBER IS A DESIGN METRIC, AND IT IS
⭐     ONE OF THE FEW HONEST ONES AVAILABLE — ⭐ it cannot be
⭐     gamed by writing more tests, only by improving the seams.
⭐   ⭐ Legitimate remaining uses: patching `time`, freezing a
⭐     clock, and third-party code you do not own and cannot
⭐     wrap. ⭐⭐ EVERYTHING ELSE IS A MISSING PARAMETER.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Constructing dependencies inside a class | Hidden, unchangeable, and untestable without patching. |
| Treating DI as a library | It's "pass what you need in" — a design decision, not a dependency. |
| Setter injection | It permits a half-constructed object you defend against forever. |
| Infrastructure constructed outside the composition root | Two places know about Stripe and only one is obvious. |
| A mutable default like `= SMTPClient()` | Defaults evaluate at import time; that opens a connection on import. |
| Module-level `create_engine` | `pytest --collect-only` connects to a database, and the error names neither. |
| A connection created before a fork | Shared across processes; looks like random database errors. |
| Any import-time side effect | Importing must never open a socket, read a file, or need an env var. |
| `mock.patch` as the injection mechanism | Couples to an import path; moving a file breaks unrelated tests. |
| `Depends` in a service signature | Only the web can call it, and it fails the worker test invisibly. |
| Expecting `Depends` to work in Celery | There's no request; services must take parameters. |
| Adopting a DI framework early | Adopt one to replace something you understand, or not at all. |
| Ignoring lifecycle scope | Singleton, per-request and per-task are different, and getting it wrong leaks connections. |
| Not counting your `mock.patch` calls | It's a design metric that can't be gamed by writing more tests. |

## Interview questions

**Q: What is dependency injection?**

> Passing a collaborator in rather than constructing it inside. That's the whole pattern, and in
> Python it usually needs no framework at all — a function parameter with a default gets you most of
> what a Java container provides, because there's no compile step and functions are first class. The
> practical consequences are that the constructor becomes documentation that can't go stale, tests
> supply a fake with no patching, and nothing reaches out to build infrastructure at import time.

**Q: What's a composition root?**

> The one place that knows how everything is wired — `main.py`, the worker entrypoint, the CLI. It
> reads configuration, constructs adapters, constructs services with those adapters, and hands the
> graph to the framework. The rule that makes it worth having is that nothing else constructs
> infrastructure, and it's greppable: searching for `Client(` outside that file should return nothing.
> The payoff is that I have three roots — API, worker and tests — sharing the same services, and if I
> can't write the test one in twenty lines, my dependencies aren't injected, they're imported.

**Q: What's wrong with a module-level engine?**

> Four things, and the third wastes an afternoon. The module can't be imported without the environment
> variable. You can't point a test at a different database without patching a module attribute.
> `pytest --collect-only` connects to a database — because collection imports every test module, which
> imports the app, which builds an engine — so "list my tests" fails in CI with an error that mentions
> neither collection nor the database. And in a forking worker, a connection created before the fork
> is shared between processes and produces errors that look random. The fix isn't a library, it's a
> function: `make_engine(settings)`, called by the composition root, so importing a module never opens
> a socket.

**Q: Is FastAPI's `Depends` a DI container?**

> Effectively yes, and a good one for its scope: request-scoped lifecycle with teardown, which is what
> hand-rolled DI most often gets wrong, plus `dependency_overrides` in tests, which is a designed seam
> rather than a patched one. The boundary people miss is that it only works at the HTTP edge — a
> Celery task or a cron job has no request, so it can't use `Depends` at all. Which means services
> must still take their dependencies as parameters. A service with `Depends` in its signature is one
> only the web can call, and it fails that test invisibly because the code looks tidy.

**Q: When would you adopt a DI framework?**

> Two signals: the composition root outgrows a screen and changing one adapter means editing several
> call sites, or lifecycle management has become manual — singleton versus per-request versus per-task
> with teardown, and I've written the same `try/finally` five times. Until then a frozen dataclass and
> a `build()` function is forty lines, fully typed, greppable, and `build(test_settings)` gives me the
> entire test wiring in one call. If I do adopt one later, I'll be replacing something I understand,
> which is the only good reason to adopt any framework.

## 🎙️ Articulation drill

**Two minutes: "How do you handle dependencies in Python?"**

Start by deflating the topic: **dependency injection is "pass what you need in" — a design decision,
not a library** — and in Python a function parameter with a default gets you most of what a Java
container provides, because there's no compile step and functions are first class. Then the
composition root: one place at the edge that reads config, builds adapters, builds services, and hands
over the graph, **with the rule that nothing else constructs infrastructure — which is greppable.**
Mention that you have three roots — API, worker, tests — and **if the test one isn't twenty lines, your
dependencies aren't injected, they're imported.** Then the concrete failure that makes it real:
**a module-level `create_engine` means `pytest --collect-only` connects to a database**, because
collection imports every test module which imports the app, and the error mentions neither collection
nor the database — plus a pre-fork connection shared across worker processes producing errors that look
random. So the rule is that **importing a module never opens a socket or requires an environment
variable**, verified with a one-line check. On frameworks: `Depends` is a real container for
request-scoped lifecycle and gives you a designed test seam, **but it stops at the HTTP edge — a
Celery task has no request** — so services take parameters, and a service with `Depends` in its
signature fails the worker test invisibly. Close on the metric: **count `mock.patch` in your suite;
each one is a dependency you didn't inject**, and it's honest because you can't game it by writing more
tests.
