# Part 1 — ⭐⭐ The project: `ticketed`

```
⭐⭐ AN EVENT TICKETING API. CHOSEN DELIBERATELY, BECAUSE IT FORCES EVERY
⭐   HARD PROBLEM IN THIS STAGE TO APPEAR NATURALLY:

⭐   ⭐⭐ A REAL RACE — two people buy the last ticket (Day 135's `FOR UPDATE`)
⭐   ⭐⭐ MONEY — so retries must not double-charge (Day 122's idempotency)
⭐   ⭐ AN EXTERNAL PROVIDER — payments, with webhooks in and out (Day 158)
⭐   ⭐ MULTI-TENANCY — organisers own events (Day 160)
⭐   ⭐ OBJECT-LEVEL AUTHORISATION — you may read YOUR ticket (Day 118)
⭐   ⭐ EXPIRING STATE — a hold that must be released (Day 159)
⭐   ⭐ A REPORTING ENDPOINT — which will be an N+1 (Day 136)
⭐   ⭐ A TRAFFIC SPIKE — on-sale at 10:00 is Day 156's whole day
⭐
⭐   ⇒ ⭐⭐ AND IT IS EXPLAINABLE IN ONE SENTENCE TO AN INTERVIEWER, which is
⭐        a requirement, not a nicety. ⭐ A project you cannot summarise is a
⭐        project you cannot defend.

⭐⭐ SCOPE — WRITE THIS DOWN AND DEFEND IT:
⭐   ✅ IN: organisers create events with ticket types and inventory ·
⭐        attendees hold then purchase · payment via a provider · tickets
⭐        issued with a QR code · organiser reporting · refunds
⭐   ❌ OUT: seat maps, discount codes, a UI, real payment processing
⭐        (⭐⭐ a FAKE provider you control, so you can make it fail on demand —
⭐        ⭐ which is worth more for learning than a real one)
⭐
⭐   ⇒ ⭐⭐ AN EXPLICIT "OUT" LIST IS THE MOST USEFUL PART OF ANY DESIGN DOC.
⭐        ⭐ It is what stops the project from never finishing, and in an
⭐        interview it demonstrates that you scope rather than sprawl.
```

# Part 2 — ⭐⭐ The data model, and the two decisions inside it

```
⭐⭐ SKETCH IT AS TABLES, NOT AS CLASSES. THE CLASSES FOLLOW; THE TABLES ARE
⭐   WHAT YOU LIVE WITH.

⭐   organisers   (id, name, …)                          ⭐ = TENANT
⭐   users        (id, email UNIQUE, password_hash, …)
⭐   events       (id, organiser_id, name, starts_at, status)
⭐   ticket_types (id, event_id, name, price_cents, ⭐⭐ quantity_total,
⭐                                                    quantity_sold)
⭐   holds        (id, ticket_type_id, user_id, qty, ⭐ expires_at)
⭐   orders       (id, user_id, ticket_type_id, qty, status,
⭐                 ⭐⭐ idempotency_key UNIQUE, total_cents)
⭐   tickets      (id, order_id, code UNIQUE, status)
⭐   outbox       (id, topic, payload, published_at)     ⭐ Day 142
⭐   webhook_deliveries (id, endpoint_id, event_id, attempts, …)  ⭐ Day 158

⭐⭐ DECISION 1 — MONEY IS `price_cents INTEGER`. NEVER FLOAT.
⭐   ⭐ `0.1 + 0.2 != 0.3` (Day 026). ⭐⭐ `Decimal` in Python, INTEGER MINOR
⭐     UNITS in the database, and the currency stored alongside it.
⭐   ⭐ Day 131's trap: a `Decimal` field fed by JSON goes through float and
⭐     is already wrong before validation sees it.

⭐⭐ DECISION 2 — HOW DO YOU COUNT REMAINING TICKETS? THREE OPTIONS, AND THIS
⭐   IS THE MOST CONSEQUENTIAL CHOICE IN THE PROJECT:
⭐   ⭐ (a) `COUNT(*) FROM tickets` ⇒ ⭐ always correct, ⭐⭐ and it cannot be
⭐        locked cheaply, so it does not solve the race.
⭐   ⭐ (b) `quantity_sold` COUNTER ON `ticket_types` ⇒ ⭐⭐ ONE ROW TO LOCK,
⭐        which makes `SELECT … FOR UPDATE` cheap and the race solvable —
⭐        ⭐ at the cost of denormalisation you must keep honest.
⭐   ⭐ (c) a Redis counter ⇒ ⭐ fast, ⭐⭐ and it is a SECOND SOURCE OF TRUTH
⭐        that can disagree with the database (Day 143). ⭐ Only as a cache
⭐        for DISPLAY, never for the decision.
⭐   ⇒ ⭐⭐ CHOOSE (b), AND ADD A CHECK CONSTRAINT SO THE DATABASE ITSELF
⭐        REFUSES TO OVERSELL:
⭐        `CHECK (quantity_sold <= quantity_total)`
⭐   ⇒ ⭐⭐ THAT CONSTRAINT IS THE POINT. Your lock can have a bug; your
⭐        constraint cannot. ⭐ Day 160's principle: put the guarantee where it
⭐        cannot be bypassed.
```

# Part 3 — ⭐⭐ The contract, written before the code

```
⭐⭐ SPEC-FIRST (Day 126). WRITE THE OPENAPI PATHS BY HAND — ⭐ it takes 45
⭐   minutes and it changes what you build, because ⭐⭐ every awkward
⭐   endpoint is obvious in the spec and invisible in the code.

⭐   POST   /v1/events                         ⭐ organiser · 201
⭐   GET    /v1/events?after=&limit=           ⭐ public · keyset (Day 121)
⭐   POST   /v1/ticket-types/{id}/holds        ⭐⭐ 201 · expires_at in body
⭐   POST   /v1/orders                         ⭐⭐ Idempotency-Key REQUIRED
⭐   GET    /v1/orders/{id}                    ⭐ owner only (Day 118)
⭐   POST   /v1/orders/{id}/refund             ⭐ organiser · idempotent
⭐   GET    /v1/events/{id}/report             ⭐ organiser · the N+1 trap
⭐   POST   /v1/webhooks/payments              ⭐⭐ signed, from the provider
⭐   GET    /healthz · /readyz · /metrics      ⭐ Days 147, 149

⭐⭐ FOUR CONTRACT DECISIONS TO MAKE NOW, NOT LATER:
⭐  1. ⭐⭐ THE ERROR SHAPE (Day 120). ONE shape, everywhere, with a stable
⭐       machine-readable `code`. ⭐ Write the enum of codes TODAY:
⭐       `sold_out` · `hold_expired` · `payment_declined` · `not_found` ·
⭐       `rate_limited` · `idempotency_conflict` · `validation_failed`
⭐       ⇒ ⭐⭐ Clients branch on `code`. If you invent codes ad hoc while
⭐         coding, you will have forty of them and no client can handle them.
⭐  2. ⭐ THE HOLD MODEL. ⭐⭐ Why a hold at all? Because payment takes 10–30
⭐       seconds, and without a hold you either oversell or you lock a row
⭐       across a network call (⭐ Day 135's rule: never hold a lock across
⭐       I/O). ⭐⭐ A hold is a SHORT-LIVED RESERVATION THAT REPLACES A LONG
⭐       LOCK — say exactly that in the interview.
⭐  3. ⭐⭐ IDEMPOTENCY IS REQUIRED ON `POST /orders`, NOT OPTIONAL. ⭐ Reject
⭐       with 400 if the header is missing. ⭐⭐ Optional idempotency is
⭐       idempotency nobody uses.
⭐  4. ⭐ VERSION IN THE PATH (`/v1`) from day one (Day 125) — ⭐⭐ adding a
⭐       version later is a breaking change in itself.
```

# Part 4 — ⭐⭐ The threat model, in thirty minutes

```
⭐⭐ FOUR QUESTIONS. WRITE THE ANSWERS DOWN; THEY BECOME TESTS ON Day 165.

⭐  1. ⭐ WHAT ARE THE ASSETS?
⭐       ⭐ money (orders, refunds) · ⭐ tickets (the thing of value) ·
⭐       ⭐ PII (emails) · ⭐⭐ organiser revenue data (a competitor wants it)
⭐
⭐  2. ⭐⭐ WHO ARE THE ACTORS, AND WHAT SHOULD EACH *NOT* BE ABLE TO DO?
⭐       ⭐ anonymous → may browse events; ⭐⭐ MUST NOT enumerate orders
⭐       ⭐ attendee  → may buy, may read THEIR OWN order (Day 118);
⭐         ⭐⭐ MUST NOT read another attendee's, MUST NOT refund
⭐       ⭐ organiser → may manage THEIR events; ⭐⭐ MUST NOT see another
⭐         organiser's revenue (Day 160)
⭐       ⭐ the payment provider → may POST signed webhooks ONLY
⭐
⭐  3. ⭐⭐ WHAT ARE THE ABUSE CASES? (This is the list people skip, and it is
⭐       where the interesting work is.)
⭐       ⭐ HOLD EXHAUSTION — someone holds all 5,000 tickets and never buys.
⭐         ⇒ ⭐⭐ per-user hold limits + short expiry + rate limits (Day 153).
⭐         ⭐ NOTE THIS IS NOT A SECURITY BUG IN ANY SINGLE REQUEST — every
⭐         request is legitimate. ⭐⭐ It is only visible as a POLICY.
⭐       ⭐ CARD TESTING — thousands of cheap orders to test stolen cards.
⭐       ⭐ SCALPING — one person, many accounts. ⭐⭐ Partially unsolvable;
⭐         say so rather than pretending.
⭐       ⭐ REFUND ABUSE — refund after the QR code has been scanned.
⭐
⭐  4. ⭐ WHAT MUST NEVER APPEAR IN A LOG OR A RESPONSE? (Days 119, 146)
⭐       ⭐ password hashes · payment tokens · ⭐⭐ another tenant's ANYTHING ·
⭐       ⭐ the ticket `code` before purchase completes
⭐
⭐   ⇒ ⭐⭐ THE OUTPUT IS A TABLE OF "ACTOR × RESOURCE × ALLOWED?" — ⭐ and on
⭐        Day 165 every ❌ cell becomes a test that asserts 403 or 404.
```

# Part 5 — ⭐ The ADRs, and what "done" means

```
⭐⭐ WRITE FIVE ADRs TODAY (Day 101). ⭐ Two paragraphs each: context,
⭐   decision, consequences. ⭐⭐ Immutable — you supersede, never edit.

⭐   ADR-001 ⭐ Shared-schema multi-tenancy with RLS (Day 160)
⭐        ⭐⭐ consequence: every table carries `organiser_id`; a dedicated
⭐        database for a large customer is a migration, not a rewrite
⭐   ADR-002 ⭐ Sync `def` handlers with a threadpool (Day 134)
⭐        ⭐⭐ consequence: simpler and safe; revisit if we exceed ~600 rps
⭐        (⭐ Little's Law gives you that number — Day 156)
⭐   ADR-003 ⭐ Holds + `FOR UPDATE` on the counter row, not Redis
⭐        ⭐⭐ consequence: correctness over throughput; the counter row is a
⭐        contention point we accept and will measure on Day 168
⭐   ADR-004 ⭐ Transactional outbox for all external effects (Day 142)
⭐        ⭐⭐ consequence: one extra table and a relay; no lost emails or
⭐        webhooks, ever
⭐   ADR-005 ⭐ Idempotency required on all money-moving POSTs (Day 122)
⭐
⭐   ⇒ ⭐⭐ THE VALUE IS NOT THE DECISION, IT IS THE *CONSEQUENCE* LINE. ⭐ In
⭐        an interview, "we chose X" is weak and "we chose X, which cost us Y,
⭐        and here is the number at which we would revisit it" is strong.

⭐⭐ DEFINITION OF DONE FOR THE WHOLE CAPSTONE (Days 163–168) — ⭐ write it
⭐   now so you cannot move the goalposts later:
⭐   □ ⭐ deployed and reachable, with CI green on every commit
⭐   □ ⭐⭐ no oversell under 200 concurrent buyers — PROVEN by a test
⭐   □ ⭐⭐ a retried purchase charges once — PROVEN by a test
⭐   □ ⭐ every ❌ cell in the authorisation table has a passing test
⭐   □ ⭐ p95 < 200 ms at your target rate, with the knee measured
⭐   □ ⭐ query-count ceilings on every list endpoint (Day 141)
⭐   □ ⭐⭐ logs, metrics and traces joined by `trace_id` (Day 148)
⭐   □ ⭐ a README that a stranger can run in one command
⭐   □ ⭐⭐ a 10-minute spoken walkthrough you can give without notes
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Starting with code | The expensive decisions are the data model, contract, transaction boundaries and tenancy. |
| No explicit "out of scope" list | The project never finishes, and you can't demonstrate scoping. |
| Floats for money | `0.1 + 0.2 != 0.3`. Integer minor units in the database, `Decimal` in Python. |
| Counting inventory with `COUNT(*)` | Correct, but there's nothing cheap to lock, so the race stays. |
| Redis as the inventory source of truth | A second source of truth that can disagree with the database. |
| No `CHECK (sold <= total)` | Your lock can have a bug; the constraint cannot. |
| Inventing error codes while coding | You end with forty and no client can branch on them. |
| Optional idempotency | Idempotency nobody uses. |
| No `/v1` from day one | Adding a version later is itself a breaking change. |
| Holding a row lock across the payment call | Never hold a lock across I/O — that's what a hold replaces. |
| Skipping abuse cases | Hold exhaustion is legitimate at every single request and only visible as policy. |
| Claiming scalping is solvable | It's partially unsolvable. Saying so is stronger than pretending. |
| ADRs with no consequences section | "We chose X" is weak; "which cost Y, revisit at Z" is strong. |
| A definition of done written afterwards | Then it describes whatever you happened to build. |

## Interview questions

**Q: Walk me through how you designed this service.**

> I started with scope, including an explicit out-of-scope list, because that's what stops a project
> sprawling and it's the part that shows I can scope rather than just build. Then the data model as
> tables, not classes, because the tables are what you live with. Then the API contract written as
> OpenAPI by hand before any code — that takes about forty-five minutes and changes what you build,
> because an awkward endpoint is obvious in a spec and invisible in code. Then a thirty-minute threat
> model producing an actor-by-resource table, where every "not allowed" cell becomes a test later.
> And five ADRs, each with a consequences line, because the decision on its own isn't interesting —
> what's interesting is what it cost and the number at which I'd revisit it.

**Q: How do you represent ticket inventory, and why?**

> A `quantity_sold` counter on the ticket type, not a `COUNT(*)` over tickets and not a Redis
> counter. `COUNT(*)` is always correct but there's no single cheap row to lock, so it doesn't solve
> the oversell race. Redis is fast but becomes a second source of truth that can drift from the
> database, so I'd use it for displaying "12 left" and never for the decision. A counter column gives
> me one row to take `SELECT ... FOR UPDATE` on, which makes the race solvable at the cost of
> denormalisation I have to keep honest. And the important part: I add
> `CHECK (quantity_sold <= quantity_total)`, so even if my locking has a bug the database refuses to
> oversell. Put the guarantee where it can't be bypassed.

**Q: Why have a "hold" at all — why not just take the payment?**

> Because payment takes ten to thirty seconds against a third party, and there are only two
> alternatives, both bad. Either you decrement inventory only after payment succeeds, in which case
> two hundred people can all be paying for the last ticket and you oversell. Or you hold a database
> row lock across the payment call, which violates the rule about never holding a lock across I/O —
> one slow provider and every buyer for that event is blocked behind a single locked row. A hold is a
> short-lived reservation that replaces a long lock: it decrements availability immediately, has an
> expiry so abandoned checkouts self-heal, and lets the lock be held for microseconds rather than
> thirty seconds.

**Q: What abuse cases did you consider?**

> Hold exhaustion first, because it's the interesting one: someone holds all five thousand tickets
> and never pays. What makes it hard is that no individual request is illegitimate — each one is
> exactly what the API is for — so it isn't visible as a security bug in any single request, only as
> a policy. That means per-user hold limits, short expiry, and rate limiting. Then card testing,
> which is thousands of small orders probing stolen cards; refund abuse after a QR code has already
> been scanned; and scalping via many accounts, which I'd say plainly is only partially solvable —
> claiming otherwise is worse than admitting it.

# 🚪 Exit questions

*Answer aloud, no notes.*

1. Which decisions are expensive to change later, and why does that make today document-only?
2. Why is the out-of-scope list the most useful part of a design doc?
3. How is money represented, in the database and in Python, and why?
4. Give the three ways to represent inventory and the deciding argument for one.
5. Why is the `CHECK` constraint more important than the lock?
6. Why write the OpenAPI spec before the code?
7. Why must error codes be decided up front?

11. What makes an ADR useful, and what makes one worthless?
12. Name four items from your definition of done that are *proven* rather than *claimed*.

## 🎙️ Articulation drill

**Two minutes: "Tell me about a system you designed."**

Give the one-sentence description first, then the two or three decisions that were genuinely hard,
not a tour of the endpoints. Inventory representation with the three options and why the counter row
won. The hold, framed as a short-lived reservation replacing a long lock across I/O. And the
constraint, framed as putting the guarantee where a bug can't reach it. Then show that you scoped:
name something you deliberately left out. Close on an ADR consequence with a number in it — **"sync
handlers, which caps us near six hundred requests per second by Little's Law, and that's the number
at which we'd revisit it"** — because a stated limit is more convincing than a claimed strength.
