# Day 159

**L-159** · **Scheduled jobs** — ⭐⭐ the cron that ran twice, the one that never ran, and the hour that happened twice

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a schedule is a distributed system with one instruction — "run this at
> this time" — and every hard part comes from the fact that "this time" is ambiguous, "run" is not
> atomic across replicas, and "missed" is indistinguishable from "not yet".**
>
> ⭐ Day 142 made background work durable. ⭐⭐ Today the trigger is a clock rather than a user, which
> removes the one thing that made everything else easy: **nobody is waiting for the result, so
> failure is silent.**

# Part 1 — ⭐⭐ Where the schedule lives, and the failure of each option

```
⭐⭐ FOUR PLACES, AND THE FAILURE MODE IS THE DECIDING FACTOR:

⭐  1. ⭐ SYSTEM `cron` ON A BOX. ⭐ Simple, battle-tested.
⭐       ⭐⭐ FAILS: no visibility (output goes to mail nobody reads), ⭐ dies
⭐       with the box, ⭐⭐ and it is a PET — Day 151's whole argument. ⭐ Also
⭐       runs in a minimal environment with no `PATH` and no venv, which is
⭐       why "it works when I run it manually" is the classic cron complaint.
⭐
⭐  2. ⭐⭐ A `while True: sleep(3600)` LOOP IN YOUR APP. ⭐ Tempting.
⭐       ⭐⭐ FAILS IMMEDIATELY AT N REPLICAS: every pod runs it, so the job
⭐       runs N times. ⭐ And it drifts: sleep(3600) plus the job's own
⭐       runtime means it slowly walks away from the hour.
⭐
⭐  3. ⭐ CELERY BEAT / APScheduler. ⭐ Integrated, visible, uses your queue.
⭐       ⭐⭐ FAILS: BEAT IS A SINGLE PROCESS. Two beats = every job twice.
⭐       ⭐ One beat = a single point of failure, and if it is down for six
⭐       hours ⭐⭐ NOTHING FIRES AND NOTHING TELLS YOU.
⭐
⭐  4. ⭐⭐ AN ORCHESTRATOR (`CronJob` in Kubernetes, EventBridge, Cloud
⭐       Scheduler). ⭐ Each run is a fresh pod with logs, retries and history.
⭐       ⭐⭐ THE DEFAULT ANSWER for anything running in Kubernetes.
⭐       ⭐ FAILS: `concurrencyPolicy` defaults to `Allow` ⇒ ⭐⭐ a job that
⭐       takes 70 minutes on an hourly schedule OVERLAPS ITSELF FOREVER.
⭐       ⭐ Set `Forbid`. And `startingDeadlineSeconds` — ⭐⭐ if the controller
⭐       was down past it, the run is SKIPPED SILENTLY.
⭐
⭐   ⇒ ⭐⭐ WHATEVER YOU PICK, THE SCHEDULER ONLY *TRIGGERS*. ⭐ The job itself
⭐        must still be idempotent, locked, observable and bounded — ⭐⭐ because
⭐        every one of these can fire twice, and none of them can promise not to.
```

# Part 2 — ⭐⭐ Exactly-once does not exist here either

```
⭐⭐ THE SAME FACT AS Day 142, IN A NEW COSTUME: A SCHEDULER GUARANTEES
⭐   AT-LEAST-ONCE AT BEST. ⭐ Kubernetes CronJob says so explicitly.

⭐   ⭐ THE JOB RUNS TWICE WHEN: the scheduler restarts mid-trigger · two
⭐        beats run · a pod is evicted after starting · a retry fires while
⭐        the first attempt is still alive · ⭐⭐ or a human runs it manually
⭐        "to check" while it is already running — ⭐ which is the most common
⭐        cause and the one no design accounts for.
⭐
⭐⭐ THEREFORE, TWO INDEPENDENT MECHANISMS, AND YOU NEED BOTH:

⭐  ⭐⭐ (A) A DISTRIBUTED LOCK — prevents CONCURRENT runs.
⭐       ⭐ Day 143 was explicit: a Redis lock is an EFFICIENCY lock. ⭐⭐ For a
⭐       job that must not double-run, use the DATABASE:
⭐         `SELECT pg_try_advisory_lock(hashtext('nightly_billing'))`
⭐       ⭐⭐ Held for the session, released automatically if the connection
⭐       dies — ⭐ so a killed pod does not leave a stuck lock, which is
⭐       exactly the failure a TTL-based lock has.
⭐
⭐  ⭐⭐ (B) IDEMPOTENCY — prevents SEQUENTIAL double-effect.
⭐       ⭐ A lock does nothing about "it ran fully at 02:00 and again at
⭐       02:05". ⭐⭐ Key the WORK by the period it is for:
⭐         `INSERT INTO job_runs (job, period) VALUES ('billing','2026-08')`
⭐         `ON CONFLICT DO NOTHING` ⇒ ⭐⭐ rowcount 0 MEANS ALREADY DONE.
⭐       ⭐ Day 122's claim, with the period as the idempotency key.
⭐
⭐   ⇒ ⭐⭐ THE PHRASE THAT SHOWS YOU UNDERSTAND IT: "THE LOCK STOPS TWO AT
⭐        ONCE; THE IDEMPOTENCY KEY STOPS TWO AT ALL." ⭐ People implement one
⭐        and believe they have both.
```

# Part 3 — ⭐⭐ Time: the three bugs that only appear twice a year

```
⭐⭐ BUG 1 — THE HOUR THAT HAPPENED TWICE.
⭐   ⭐ In a DST fall-back zone, 01:30 local occurs TWICE.
⭐   ⇒ ⭐⭐ A JOB SCHEDULED AT 01:30 LOCAL RUNS TWICE — and it is a
⭐        genuinely different failure from a scheduler bug, so nobody looks
⭐        for it. ⭐ In spring, 02:30 does not exist at all ⇒ ⭐⭐ THE JOB NEVER
⭐        RUNS, once a year, silently.
⭐   ⇒ ⭐⭐ FIX: SCHEDULE EVERYTHING IN UTC. ⭐ Always. ⭐⭐ THEN, IF THE
⭐        BUSINESS MEANING IS LOCAL ("send at 9 a.m. in the customer's
⭐        timezone"), that is APPLICATION LOGIC INSIDE the job — run hourly in
⭐        UTC and select the users for whom it is now 9 a.m. locally.
⭐        ⭐ Never push local-time semantics into the scheduler.
⭐
⭐⭐ BUG 2 — THE MONTH-END BOUNDARY.
⭐   ⭐ "Run on the 31st" ⇒ ⭐⭐ SKIPS FOUR MONTHS A YEAR. ⭐ "Run on the 29th"
⭐        skips three years in four.
⭐   ⇒ ⭐ Use "last day of month" logic in code, or run daily and check.
⭐   ⭐ AND: `datetime.now()` at 23:59:59.9 in a job that computes "today"
⭐        ⇒ ⭐⭐ ROWS SPLIT ACROSS TWO DAYS. ⭐ Compute the period ONCE at the
⭐        start and pass it everywhere — ⭐⭐ never call `now()` twice in one job.
⭐
⭐⭐ BUG 3 — THE OVERLAPPING WINDOW.
⭐   ⭐ Hourly job: `WHERE created_at > now() - interval '1 hour'`.
⭐   ⭐⭐ IF THE RUN IS LATE, DELAYED OR SKIPPED, THE MISSING ROWS ARE NEVER
⭐        PROCESSED — the next run's window has already moved past them.
⭐   ⇒ ⭐⭐ FIX: A WATERMARK, NOT A WINDOW. Store the last successfully
⭐        processed position; ⭐ process from there to now; ⭐⭐ advance it only
⭐        on success. ⭐ Then a missed run self-heals on the next one, and
⭐        catch-up is automatic rather than a manual backfill at 3 a.m.
⭐   ⇒ ⭐ (This is exactly Day 121's keyset pagination, applied to time —
⭐        ⭐⭐ and it fails for the same reason offsets do: the window moves
⭐        independently of what you actually consumed.)
```

```python
# ⭐⭐ THE WATERMARK PATTERN — the highest-value 15 lines in this day
def run_hourly_export(db: Session) -> None:
    period = datetime.now(timezone.utc)                # ⭐ ONCE
    state = db.execute(
        select(JobState).where(JobState.job == "export").with_for_update()
    ).scalar_one()                                     # ⭐⭐ lock the watermark row
    rows = fetch_since(db, state.last_id, limit=10_000)   # ⭐ bounded! Part 4
    if not rows:
        return
    export(rows)
    state.last_id = rows[-1].id                        # ⭐⭐ advance ONLY on success
    state.last_run_at = period
    db.commit()
```

# Part 4 — ⭐⭐ Bounding the job, and the failure nobody sees

```
⭐⭐ THE THREE WAYS A SCHEDULED JOB DESTROYS A HEALTHY SYSTEM:

⭐  1. ⭐⭐ IT PROCESSES EVERYTHING. Fine at 10,000 rows. ⭐ At 40 million,
⭐       it holds one transaction for four hours ⇒ ⭐⭐ table bloat, replica
⭐       lag, and on Postgres it BLOCKS VACUUM so dead tuples accumulate
⭐       across the whole database. ⭐ Day 138: batch it, commit per batch.
⭐  2. ⭐⭐ IT RUNS AT 02:00 UTC — AND SO DOES EVERY OTHER JOB IN THE COMPANY.
⭐       ⭐ Nobody chose 02:00 together; everyone chose it separately.
⭐       ⇒ ⭐⭐ STAGGER THE SCHEDULES, and add JITTER. Day 142 and Day 143's
⭐         herd, one more time — ⭐ correlated timing is the recurring bug of
⭐         this entire stage.
⭐  3. ⭐ IT COMPETES WITH USER TRAFFIC. ⭐⭐ Give batch work its own queue AND
⭐       ITS OWN DATABASE REPLICA if the work is read-heavy — ⭐ Day 152's
⭐       bulkhead. Otherwise a report starves checkout.

⭐⭐ AND THE DEFINING PROBLEM OF SCHEDULED WORK: **NOBODY IS WAITING**, SO
⭐   FAILURE IS SILENT. ⭐ A broken endpoint produces angry users in minutes.
⭐   ⭐⭐ A JOB THAT STOPPED FIRING IN MARCH IS DISCOVERED IN JULY, BY AN
⭐   ACCOUNTANT.
⭐
⭐   ⇒ ⭐⭐ THE ANSWER IS DEAD-MAN MONITORING — ALERT ON *ABSENCE*, NOT ON
⭐        FAILURE (Day 147's rule, and this is its most important application):
⭐        ⭐ the job pings a heartbeat URL on SUCCESS
⭐        ⭐ if no ping arrives within the expected interval + grace, ⭐⭐ ALERT
⭐        ⇒ ⭐ this catches the case NO other monitoring can: ⭐⭐ THE JOB NEVER
⭐          STARTED. ⭐ There is no error log, no failed run, no exception —
⭐          because nothing ran to produce one.
⭐   ⇒ ⭐ Also emit, per run: ⭐⭐ duration, rows processed, and watermark LAG.
⭐        ⭐ A job that "succeeds" in 0.1 s having processed 0 rows is broken,
⭐        and success/failure alone will never say so.
```

# Part 5 — ⭐ Making a job operable

```
⭐⭐ THE SIX PROPERTIES OF A JOB YOU CAN LIVE WITH:
⭐  1. ⭐⭐ RE-RUNNABLE. You can run it again, right now, safely. ⭐ If you
⭐       cannot, every incident involving it starts with a scary decision.
⭐  2. ⭐⭐ RESUMABLE. It processes in batches and records progress, so a kill
⭐       at 80% does not mean starting over.
⭐  3. ⭐ PARAMETERISABLE BY PERIOD — `--for 2026-08-01`. ⭐⭐ So backfilling a
⭐       missed day is one command, not a code change.
⭐  4. ⭐ BOUNDED — a max batch size AND a timeout (Day 142's `time_limit`).
⭐  5. ⭐ OBSERVABLE — structured logs with a run id (Day 146), duration,
⭐       counts. ⭐⭐ And it should log a SUMMARY LINE at the end, always,
⭐       including on the zero-work path.
⭐  6. ⭐⭐ DRY-RUNNABLE. `--dry-run` that reports what it WOULD do. ⭐ For
⭐       anything that deletes or charges, this is the difference between a
⭐       confident deploy and a hopeful one.

⭐⭐ AND THE ARCHITECTURAL QUESTION WORTH ASKING BEFORE ANY OF THIS:
⭐   ⭐ "DOES THIS NEED TO BE SCHEDULED AT ALL?"
⭐   ⭐⭐ A NIGHTLY JOB THAT SWEEPS FOR EXPIRED THINGS IS OFTEN A MISSING
⭐        `expires_at` COLUMN AND A `WHERE` CLAUSE. ⭐ Computing the state on
⭐        READ is stateless, always correct, and cannot fail at 3 a.m.
⭐   ⭐ A job that reacts to something is usually an EVENT (Day 161), not a
⭐        schedule — ⭐⭐ and an event-driven version has no window, no
⭐        watermark, no DST bug and no dead-man alert to configure.
⭐   ⇒ ⭐⭐ THE BEST SCHEDULED JOB IS THE ONE YOU DELETED. ⭐ Reach for a
⭐        schedule when the work is genuinely periodic (billing periods,
⭐        reports, retention) — not because you needed something to happen
⭐        "eventually".
```

## Common mistakes

| Mistake | Correction |
|---|---|
| A `while True: sleep()` loop in the app | Every replica runs it, and it drifts by the job's own runtime. |
| Two Celery beats for HA | Every job fires twice. Beat is inherently single-instance. |
| One beat with no monitoring | It's down for six hours, nothing fires, and nothing tells you. |
| `concurrencyPolicy: Allow` (the default) | A 70-minute hourly job overlaps itself forever. |
| Ignoring `startingDeadlineSeconds` | A run is skipped silently if the controller was down past it. |
| Assuming the scheduler gives exactly-once | It doesn't. Nothing does. |
| A lock without an idempotency key | The lock stops two at once; only the key stops two at all. |
| A Redis TTL lock for a must-not-double-run job | A crashed holder or a paused VM can produce two holders. Use an advisory lock. |
| Scheduling in local time | 01:30 runs twice in autumn and 02:30 never runs in spring. |
| Pushing "9 a.m. local" into the scheduler | Run hourly in UTC and select users for whom it's now 9 a.m. |
| "Run on the 31st" | Skips four months a year. |
| Calling `now()` more than once in a job | Rows split across two periods at a midnight boundary. |
| `WHERE created_at > now() - interval '1 hour'` | A late or missed run loses those rows permanently. Use a watermark. |
| Advancing the watermark before success | You've marked work done that never happened. |
| Processing everything in one transaction | Four-hour locks, replica lag, and vacuum blocked across the database. |
| Every job at 02:00 UTC | Nobody chose it together; everybody chose it separately. Stagger and jitter. |
| Batch work sharing the user-traffic queue and database | A report starves checkout. |
| Alerting only on job failure | The job that never started produces no failure to alert on. |
| Success/failure as the only signal | A run that "succeeds" in 0.1 s having done nothing is broken. |
| A job that can't be re-run or backfilled | Every incident involving it starts with a scary decision. |
| Scheduling a sweep for expired things | Often a missing `expires_at` and a `WHERE` clause. |

## Interview questions

**Q: Where would you put a scheduled job, and why?**

> For anything on Kubernetes, a `CronJob` — each run is a fresh pod with its own logs, history and
> retry policy, versus system cron which is invisible and lives on a pet box, or a `sleep` loop in
> the app which runs N times because every replica has one. Celery beat works but is inherently a
> single process, so two for high availability means every job fires twice and one means a silent
> single point of failure. Whatever I pick, the two settings that bite are `concurrencyPolicy`, which
> defaults to `Allow` so a seventy-minute job on an hourly schedule overlaps itself forever, and
> `startingDeadlineSeconds`, past which a missed run is skipped silently. And the framing that
> matters: the scheduler only *triggers*. It can't promise not to fire twice, so the job still needs
> to be idempotent, locked, bounded and observable regardless.

**Q: How do you stop a job running twice?**

> Two independent mechanisms, because they solve different problems. A distributed lock prevents
> *concurrent* runs — and for anything that must not double-run I'd use a Postgres advisory lock
> rather than Redis, because it's held for the session and released automatically when the connection
> dies, so a killed pod doesn't leave a stuck lock the way a TTL-based one does. But a lock does
> nothing about "it ran fully at 02:00 and again at 02:05", so I also key the work by the period it's
> for: insert a row for `('billing', '2026-08')` with `ON CONFLICT DO NOTHING`, and a rowcount of
> zero means already done. The sentence is: the lock stops two at once, the idempotency key stops two
> at all. People implement one and believe they have both.

**Q: What goes wrong with time in scheduled jobs?**

> Three things, and two of them appear twice a year so nobody's looking. Daylight saving: in a
> fall-back zone 01:30 local happens twice, so a job scheduled then runs twice; in spring 02:30
> doesn't exist, so it never runs — silently, once a year. The fix is to schedule everything in UTC
> and put local-time semantics in application logic: run hourly in UTC and select the users for whom
> it's now nine a.m. locally. Second, month boundaries — "run on the 31st" skips four months a year.
> And calling `now()` more than once in a job, which at a midnight boundary splits rows across two
> periods; compute the period once at the start and pass it down.

**Q: Your hourly job uses `WHERE created_at > now() - interval '1 hour'`. What's wrong?**

> If a run is late, delayed, or skipped, the rows in the gap are never processed, because the next
> run's window has already moved past them — and nothing reports it, since the job succeeded. It's
> the same defect as offset pagination: the window moves independently of what you actually consumed.
> The fix is a watermark instead of a window — store the last successfully processed position,
> process from there to now, and advance it *only* on success. Then a missed run self-heals on the
> next one and catch-up is automatic rather than a manual backfill at three in the morning. I'd also
> bound the batch, so a job that's been down for a day doesn't try to process a day's data in one
> transaction.

**Q: How do you know a scheduled job is healthy?**

> Not from failure alerts, because the defining property of scheduled work is that nobody is waiting
> — a broken endpoint produces angry users in minutes, whereas a job that stopped firing in March
> gets discovered in July by an accountant. So the primary alert is dead-man monitoring: the job pings
> a heartbeat on success, and if no ping arrives within the interval plus a grace period, that fires.
> That's the one thing that catches "the job never started", where there's no error, no failed run
> and no exception, because nothing ran to produce one. Beyond that I'd emit duration, rows
> processed, and watermark lag per run — because a job that "succeeds" in a tenth of a second having
> processed zero rows is broken, and success versus failure will never tell you that.

## 🎙️ Articulation drill

**Two minutes: "Design a nightly billing job."**

Start by questioning whether it must be scheduled at all, then commit — billing genuinely is
periodic. Say where it lives and why, then the two mechanisms with the sentence that separates them:
the lock stops two at once, the period key stops two at all. Then time: UTC always, the period
computed once, and the DST bug named explicitly because it's the one that only shows up twice a year.
Then the watermark instead of a window, and say it's keyset pagination applied to time. Bound the
batches and give the reason — a four-hour transaction blocks vacuum across the whole database. Close
on the defining property of scheduled work: **nobody is waiting, so failure is silent — which is why
the primary alert is a dead man's switch on absence, not an alert on failure.**
