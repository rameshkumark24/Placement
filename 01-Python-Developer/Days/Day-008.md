# Day 008

**L-008** · ⭐⭐ **What a TCP connection actually is** — the state machine, TIME_WAIT, CLOSE_WAIT
**C-06** · TCP III — congestion control: slow start, AIMD, Reno, BBR

**Time:** 3 hrs · **Mode:** NEW

> **A TCP connection is not a pipe. It is a pair of state machines and two buffers, one on each
> machine, agreeing about which bytes have arrived.** Once you see it as state rather than as a
> channel, `CLOSE_WAIT` piling up in production stops being a mystery and becomes a diagnosis.

# Part 1 — ⭐⭐ The state machine

```
⭐ CLOSED ──listen()──▶ LISTEN ──SYN received──▶ SYN_RCVD ──ACK──▶ ⭐⭐ ESTABLISHED
⭐ CLOSED ──connect()──▶ SYN_SENT ──SYN-ACK──▶ ⭐⭐ ESTABLISHED

⭐⭐ CLOSING — and this is the half that matters operationally:

   ACTIVE closer (calls close() first)      PASSIVE closer
        ESTABLISHED                              ESTABLISHED
            │ FIN ──────────────────────────────────▶ │
        FIN_WAIT_1                              ⭐⭐ CLOSE_WAIT   ⭐ ("the app must now close")
            │ ◀────────────────────────────── ACK     │
        FIN_WAIT_2                                    │  ⭐⭐ waiting for YOUR code to call close()
            │ ◀────────────────────────────── FIN     │
            │ ACK ──────────────────────────────────▶ │  LAST_ACK
        ⭐⭐ TIME_WAIT  (~60 s)                          CLOSED
            │
         CLOSED
```

## ⭐⭐ The two states you will actually debug

| State | ⭐ Meaning | ⭐⭐ What it tells you |
|---|---|---|
| ⭐⭐ **`TIME_WAIT`** | ⭐ **you** closed first, and the kernel is holding the tuple | ⭐⭐ **normal** — but thousands means you are opening too many short connections |
| ⭐⭐ **`CLOSE_WAIT`** | ⭐⭐ **the peer closed and YOUR CODE HAS NOT CALLED `close()`** | ⭐⭐ **a bug in your program. Always. It is a leaked file descriptor.** |

```
⭐⭐ THE DIAGNOSIS THAT WILL SAVE YOU A DAY:
⭐   many TIME_WAIT   ⇒ ⭐ you are the client, opening and closing constantly
⭐                       ⇒ ⭐⭐ FIX: connection pooling / keep-alive, not a kernel tunable
⭐   ⭐⭐ many CLOSE_WAIT ⇒ ⭐⭐ YOUR CODE LEAKS SOCKETS. Some path does not close.
⭐                       ⇒ ⭐⭐ FIX: context managers. `with socket.socket() as s:` — Day 052.
⭐   ⇒ ⭐⭐ Eventually: "Too many open files" — ⭐ which is a file-descriptor limit, not a memory problem.
```

⚠️ ⭐⭐ **`CLOSE_WAIT` is one of the highest-value things on this page.** It appears in production as a
service that works fine for six hours and then stops accepting connections. **The count climbs, the
descriptor limit is hit, and the error message points at "too many open files" rather than at the
missing `close()`.** Seeing `CLOSE_WAIT` in `ss -tan` names the bug immediately.

## ⭐ Why `TIME_WAIT` exists

```
⭐ Two reasons, both about correctness:
⭐ 1. ⭐⭐ A delayed packet from THIS connection must not be delivered to a NEW connection
⭐    reusing the same four-tuple. Holding the tuple for 2× the max segment lifetime guarantees
⭐    any straggler has expired.
⭐ 2. ⭐ The final ACK might be lost. If the peer retransmits its FIN, someone must be there to
⭐    ACK it again — that is the side in TIME_WAIT.
⭐ ⇒ ⭐⭐ So SO_REUSEADDR (the line you have typed since Day 003) says: "I accept that risk, bind anyway."
```

```bash
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn    # ⭐⭐ your connection states, counted
lsof -p <pid> | wc -l                                     # ⭐ open descriptors for a process
ulimit -n                                                 # ⭐ your descriptor limit
```

⭐ **Run that first command on any machine you use.** Learning to read the state distribution at a
glance is a genuinely useful skill and it takes ten minutes to acquire.

# Part 2 — ⭐⭐ What "reliable, ordered" actually costs

| ⭐ Guarantee | ⭐ Mechanism | ⭐⭐ Cost |
|---|---|---|
| ⭐ Ordered | sequence numbers + a reassembly buffer | ⭐⭐ **head-of-line blocking** — one lost segment stalls everything behind it |
| ⭐ Reliable | ACKs + retransmission | latency spikes on loss |
| ⭐ Connection-oriented | the handshake | ⭐⭐ one round trip before any data |
| ⭐ Flow-controlled | the advertised window | throughput = window ÷ RTT (Day 007) |
| ⭐ Congestion-controlled | see Part 3 | ⭐ deliberately slow start |

⭐⭐ **Head-of-line blocking is the one to remember**, because it is the reason HTTP/2's multiplexing
did not fully deliver and why HTTP/3 moved to QUIC over UDP (Day 011). **If six HTTP/2 streams share
one TCP connection and one segment is lost, all six stall** — TCP does not know they are independent.

## ⭐ When TCP is the wrong choice

| ⭐ Use **UDP** when | ⭐ Example |
|---|---|
| Late data is worthless | live audio and video |
| ⭐ You will implement your own reliability | ⭐⭐ QUIC does exactly this |
| One small request, one small reply | DNS |
| ⭐ You cannot afford the handshake | real-time gaming |

# Part 3 — C-06 · ⭐⭐ Congestion control

```
⭐⭐ FLOW CONTROL protects the RECEIVER. ⭐⭐ CONGESTION CONTROL protects THE NETWORK.
⭐ The sender maintains its own limit — the congestion window (cwnd) —
⭐   and sends min(cwnd, advertised window).
```

## ⭐ Slow start and AIMD

```
⭐⭐ SLOW START — despite the name, it is EXPONENTIAL:
⭐   cwnd starts around 10 segments, and DOUBLES every round trip
⭐   ⇒ ⭐⭐ until loss occurs, or a threshold is reached

⭐⭐ CONGESTION AVOIDANCE — AIMD, the core algorithm of the internet:
⭐   ⭐ ADDITIVE INCREASE:      no loss ⇒ cwnd += 1 segment per RTT   (probe gently)
⭐   ⭐⭐ MULTIPLICATIVE DECREASE: loss  ⇒ cwnd /= 2                    (back off hard)
⭐ ⇒ ⭐⭐ Gentle up, sharp down. That asymmetry is what makes it STABLE and FAIR when
⭐   millions of independent senders share a link with no coordination at all.
```

⭐⭐ **AIMD is worth admiring for a moment.** There is no central controller and no negotiation —
every sender independently follows "increase slowly, halve on loss", and the emergent result is
approximately fair sharing of a bottleneck. **It is one of the most successful distributed algorithms
ever deployed**, and the same shape reappears whenever you write backoff logic (Stage 12).

## ⭐ The consequence you will feel

```
⭐⭐ Slow start means a NEW connection does not start at full speed.
⭐   ⇒ ⭐⭐ short-lived connections NEVER REACH their available bandwidth
⭐   ⇒ ⭐⭐ so connection reuse is not only about avoiding the handshake —
⭐        ⭐⭐ it is about keeping a WARMED congestion window.
⭐ ⇒ ⭐ This is another argument for keep-alive, HTTP/2, and connection pools.
```

| ⭐ Algorithm | ⭐ Idea |
|---|---|
| **Reno / NewReno** | classic AIMD with fast recovery |
| ⭐ **CUBIC** | ⭐ the Linux default — a cubic growth function, better on high-bandwidth long-distance links |
| ⭐⭐ **BBR** | ⭐⭐ **models bandwidth and RTT directly instead of treating loss as the only signal** |

⭐⭐ **Why BBR matters conceptually:** loss-based algorithms assume loss means congestion, which is
false on wireless links and on paths with deep buffers (**bufferbloat** — routers absorbing so much
that latency balloons before anything is dropped). **BBR measures delivery rate and round-trip time
and paces accordingly**, which is a different philosophy: measure the thing you care about rather than
infer it from a proxy.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Treating `CLOSE_WAIT` as normal** | ⭐⭐ It is always your bug — a socket you did not close. |
| Trying to tune `TIME_WAIT` away | ⭐ Usually the real fix is connection reuse, not a kernel flag. |
| Not using context managers on sockets | ⭐⭐ `with` guarantees close on every path, including exceptions. |
| Blaming "memory" for "too many open files" | ⭐ It is the descriptor limit, and leaked sockets are the usual cause. |
| Assuming TCP prevents all data loss | ⭐ It retransmits or fails. It cannot fix a cut cable. |
| Ignoring head-of-line blocking | ⭐⭐ It is why HTTP/3 abandoned TCP. |
| Thinking slow start is slow | ⭐ It is exponential — the name describes the starting point. |
| Believing a new connection runs at full speed | ⭐⭐ It has a cold congestion window. Reuse keeps it warm. |
| Assuming loss always means congestion | ⭐ False on wireless and with bufferbloat — hence BBR. |

## Interview questions

**Q: What does it mean that a TCP connection is "established"?**
> Both endpoints have completed the three-way handshake and now hold state: sequence numbers, buffers,
> window sizes and a state machine entry. A connection is not a physical channel — it is agreement
> between two state machines about which bytes have been received. That is why a connection can exist
> while no data flows, why one side can be closed while the other is still open, and why the kernel
> keeps holding state after you call close.

**Q: You see thousands of sockets in `CLOSE_WAIT`. What is wrong?**
> Your application. `CLOSE_WAIT` means the peer sent a FIN and your code has not called `close()` on
> that socket, so the file descriptor is leaked. It accumulates until you hit the descriptor limit and
> the service stops accepting connections, usually surfacing as "too many open files" — which points
> at the symptom rather than the cause. The fix is to close sockets on every path, which in Python
> means a context manager rather than a `close()` you hope is reached.

**Q: And thousands in `TIME_WAIT`?**
> That is normal but tells you something: you are the side closing first, and doing it very often —
> typically opening a new connection per request instead of reusing one. The kernel holds the tuple
> for roughly twice the maximum segment lifetime so a delayed packet from the old connection cannot
> land on a new one with the same four-tuple, and so the final ACK can be retransmitted. The right fix
> is connection reuse — keep-alive and pooling — rather than tuning the kernel to hide it.

**Q: What is AIMD and why is it fair?**
> Additive increase, multiplicative decrease: while no loss occurs the sender adds roughly one segment
> per round trip, and on loss it halves its window. The asymmetry is what produces stability — gentle
> probing upward, sharp backoff downward — and when many independent senders all follow it on a shared
> bottleneck, the result converges to approximately fair sharing with no coordination whatsoever. It
> is the same shape as good retry backoff, which is not a coincidence.

**Q: Why does connection reuse matter beyond avoiding the handshake?**
> Because of slow start. A new connection begins with a small congestion window and doubles it each
> round trip, so short-lived connections finish before they ever reach the available bandwidth. Reusing
> a connection keeps a warmed congestion window as well as skipping the handshake and the TLS
> negotiation. That is three separate reasons pointing the same way, and together they are why HTTP
> keep-alive, HTTP/2 and database connection pools all exist.

## 🎙️ Articulation drill

Record two minutes: **"Your service works for six hours and then stops accepting connections. Walk me
through your diagnosis."**

⭐ **The first command is `ss -tan` and the first thing you look for is `CLOSE_WAIT`.** If it is
climbing, the diagnosis is complete before you have opened any code: the peer closed, your process did
not, and you have leaked file descriptors until you hit the limit — which surfaces as "too many open
files" and points at the wrong thing.

⭐⭐ **Then the fix, and the reason it is a design fix rather than a patch:** every socket, file and
connection is acquired in a `with` block, because a `close()` at the end of a function is not reached
when an exception is raised — and the path that throws is exactly the path that runs at 3am.
