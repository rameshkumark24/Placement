# Day 270 🚪

**P-270** · 🚪 **The data and async review gate** — ⭐⭐ how would you know within fifteen minutes?

**Time:** 3 hrs · **Mode:** BUILD · **Gate**

> ⭐⭐ **The sentence to own: everything built in Days 263–269 shares one property — it happens where
> no user is watching it fail. So this gate is not "does it work". It is "how would I know, within
> fifteen minutes, that it stopped?"**
>
> ⭐ Day 262 gated the request path, where a failure produces a 500, a graph and a complaint.
> ⭐⭐ Nothing in this block does that. A relay that stopped, a cron entry deleted in a Helm
> refactor, a cache serving last Tuesday, a socket that never reconnected — ⭐⭐ **all of them
> produce silence**, and silence is indistinguishable from a quiet weekend.

# Part 3 — ⭐⭐ Ten failure injections, against the deployed system

> ⭐ Staging, with production-shaped data. ⭐⭐ Each one: **do it, write down what happened, and
> write down what it means.** A prediction that turns out wrong is the most valuable line you will
> write today.

```
⭐⭐ ① KILL A WORKER MID-TASK (`kill -9`, not SIGTERM)
⭐   ⭐ EXPECT: the task is redelivered and its effect happened
⭐     EXACTLY ONCE.
⭐   ⭐⭐ IF IT VANISHED ⇒ `acks_late` is off.
⭐   ⭐⭐ IF IT HAPPENED TWICE ⇒ the task is not idempotent, and
⭐     you have been relying on luck.

⭐⭐ ② STOP THE RELAY FOR TEN MINUTES
⭐   ⭐ EXPECT: outbox backlog grows, the dead-man alert fires
⭐     BEFORE you go looking, and on restart it drains with no
⭐     duplicate visible to any consumer.
⭐   ⭐⭐ IF NO ALERT FIRED, THAT IS THE FINDING — not the backlog.

⭐⭐ ③ `FLUSHALL` THE CACHE UNDER LOAD
⭐   ⭐ EXPECT: p99 rises, error rate stays at zero.
⭐   ⭐⭐ IF ANYTHING 500s OR TIMES OUT ⇒ the cache is LOAD-BEARING
⭐     (Day 266) and you have an undocumented single point of
⭐     failure. ⭐ Record the throughput you sustained.

⭐⭐ ④ MAKE STORAGE RETURN 500 FOR TWO MINUTES
⭐   ⭐ EXPECT: uploads fail cleanly, nothing reaches `ready`, no
⭐     orphan rows, the retry works, and reads of EXISTING files
⭐     still work if they are signed and cached.

⭐⭐ ⑤ RESTART EVERY APP POD WITH 500 SOCKETS CONNECTED
⭐   ⭐ EXPECT: clients reconnect with JITTER, refetch, and end
⭐     up showing exactly what REST says.
⭐   ⭐⭐ WATCH THE REST TIER: the reconnect storm and the refetch
⭐     storm arrive together (Day 268).

⭐⭐ ⑥ ENQUEUE 10,000 BULK TASKS
⭐   ⭐ EXPECT: a password reset still completes in under five
⭐     seconds. ⭐⭐ THIS IS THE ONLY REAL TEST OF YOUR QUEUE
⭐     TOPOLOGY, and it fails whenever queues were split by
⭐     feature instead of by duration.

⭐⭐ ⑦ RUN THE NIGHTLY JOB TWICE — CONCURRENTLY, THEN SERIALLY
⭐   ⭐ Concurrently ⇒ the advisory lock holds; one exits.
⭐   ⭐ Serially ⇒ ⭐⭐ THE SECOND RUN CHANGES ZERO ROWS. If it
⭐     changes any, your job is not re-runnable, which means it
⭐     is not safe to re-run during an incident — which is the
⭐     only time anyone ever re-runs it.

⭐⭐ ⑧ SKEW A ROW'S TIMESTAMP BACKWARDS
⭐   ⭐ Insert a row with `created_at` 90 seconds in the past,
⭐     just behind the watermark. ⭐⭐ EXPECT IT TO STILL BE
⭐     PROCESSED. If it is not, you have found the replica-clock
⭐     bug from Day 264 before it found you.

⭐⭐ ⑨ REPLAY A PROVIDER WEBHOOK FIVE TIMES
⭐   ⭐ EXPECT: one state change, four no-ops, and five 2xx
⭐     responses — ⭐⭐ because a webhook you answer with a 500
⭐     will be retried forever by the provider.

⭐⭐ ⑩ CHANGE A USER'S ROLE AND IMMEDIATELY RE-REQUEST
⭐   ⭐ EXPECT: the new permissions, on the very next request.
⭐   ⭐⭐ IF THE OLD VIEW IS SERVED FOR 300 SECONDS, `perm_version`
⭐     is missing from the key (Day 266) — and that is a
⭐     SECURITY finding, not a caching one.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Reviewing async code by reading it | The bugs are in the timing between lines, and timing isn't in a diff. |
| Ticking audit items from memory | Open the code or run the query. "Fairly sure" is a finding. |
| `SIGTERM` instead of `kill -9` in the worker test | Graceful shutdown hides exactly the failure you're testing. |
| Treating a grown backlog as the finding | The finding is that no alert fired before you went looking. |
| Not flushing the cache under load | You never learn whether it's an optimisation or a load-bearing wall. |
| Testing the queue with an empty queue | Topology only fails when a slow queue is full. |
| Only testing the job concurrently | Serial re-run is the incident case, and it must change zero rows. |
| No clock-skew test | The replica-clock watermark bug is invisible until production has three replicas. |
| Answering a webhook with a 500 | The provider retries forever, and you built your own traffic spike. |
| "The pod is running" as proof of work | A process can be healthy and doing nothing. |
| Only machinery metrics | Every one can be green while the due-and-not-done count climbs. |
| Measuring at one data size | One number can't show you a slope. |
| Accepting "small drift" | Drift you can't explain is proportional to a bug rate you haven't measured. |
| Never reading the DLQ | It's a stored queue of unknown bugs you're paying to keep. |
| Undated baselines | Uncomparable next month, which was the entire point. |
| A runbook that omits "is a re-run safe?" | That's the only question anyone asks at 3 a.m. |
| Recording a pass with zero findings | The injections were too gentle. Say so. |

## Interview questions

**Q: How do you review async and background code?**

> Not by reading it, because the bugs aren't in the lines — they're in the timing between them: the
> commit that hadn't landed, the worker that died between two statements, the second delivery. None
> of that shows up in a diff. So I break things on purpose against a deployed instance: kill a worker
> mid-task and check the effect happened exactly once, stop the relay and check whether the alert
> fires before I go looking, flush the cache under load, restart pods with sockets connected, run the
> nightly job twice. The most useful output is a prediction that turned out wrong.

**Q: What's the defining question for this part of the system?**

> "How would I know within fifteen minutes that it stopped?" Everything here fails silently — a
> deleted cron entry raises nothing, a stopped relay produces no errors, a cache serves last Tuesday
> perfectly happily. So I keep a table with one row per background component: what proves it ran,
> what alerts on the absence of that, and how long detection takes. Two rows are automatic findings —
> any row where the detection path is "a customer emails us", and any row whose proof is "the pod is
> running", because a process can be up, passing its liveness probe, and doing nothing at all.

**Q: You reconcile and find 0.3% drift. What do you do?**

> Treat it as unexplained rather than small. A drift I can't explain is proportional to a bug rate I
> haven't measured, so there's no reason to believe it stays at 0.3%. I take one example, trace it end
> to end, and name the mechanism. Then I decide — fix it, or write it in `known-gaps.md` with the
> blast radius and the trigger that would change the decision. Both are legitimate outcomes. Not
> looking isn't.

**Q: Your review found nothing. Is that good?**

> No, and I'd say so out loud. Ten deliberate failure injections against a system with a relay, a
> scheduler, a queue, a cache, uploads, sockets and reports will surface something — so zero findings
> means the injections were too gentle, not that the system is clean. The honest move is to run them
> harder rather than record a pass, and that's the same rule I applied at the backend gate.

## 🎙️ Articulation drill

**Three minutes: "How do you know your background systems are healthy?"**

Start with the property that defines the whole block: **all of this happens where nobody is watching
it fail** — a broken endpoint produces a 500 and a complaint, but a stopped relay, a deleted cron
entry, a cache serving last Tuesday and a socket that never reconnected all produce silence, and
silence looks exactly like a quiet weekend. So the question isn't "does it work", it's **"how would I
know within fifteen minutes that it stopped?"** Then say how you answer it: you can't review this by
reading, because the bugs live in the timing between the lines and timing isn't in a diff — so you
break things deliberately against a deployed instance. Give three injections with what each one
proves: kill a worker mid-task and the effect must have happened exactly once, or your acknowledgement
setting or your idempotency is wrong; stop the relay, where **the finding isn't the backlog, it's that
no alert fired before you went looking**; flush the cache under load, and if anything 500s then the
cache is a load-bearing wall rather than an optimisation. Then the silence table, with its two
automatic findings — a detection path that ends at "a customer emails us", and **a proof that amounts
to "the pod is running", because a process can be healthy and doing nothing at all.** Close on
correctness and honesty: four reconciliations where **zero is the only acceptable answer, since drift
you can't explain is proportional to a bug rate you haven't measured**, a DLQ that a human has
actually read, and the rule that a gate producing no findings produced no gate — so if ten deliberate
failures surfaced nothing, the injections were too gentle and you say so.
