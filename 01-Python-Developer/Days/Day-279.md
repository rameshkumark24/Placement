# Day 279 🔭

**P-279** · 🔭 **Frontend observability** — ⭐⭐ your error count is mostly noise

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a frontend error feed is dominated by things you cannot fix and must not
> chase — browser extensions, crawler bots, dead network on a train — so the discipline is not
> collecting more errors but filtering hard enough that the ones left are actionable, because an alert
> that fires on noise trains you to ignore alerts.**
>
> Today: ⭐ what to capture, ⭐⭐ the noise, source maps, and the context that makes a report usable.

---

# Part 1 — The four signals

```
⭐⭐ WHAT A FRONTEND MUST REPORT — AND WHERE EACH COMES FROM

⭐ ① ⭐ UNCAUGHT ERRORS      ⇒ window.onerror + the error boundary
⭐                             (Day 240) — ⭐⭐ THE BOUNDARY CATCHES
⭐                             RENDER ONLY, so you need both
⭐ ② ⭐⭐ UNHANDLED REJECTIONS ⇒ the Day 216 listener. ⭐ THIS IS
⭐                             MOST OF YOUR REAL ERRORS.
⭐ ③ ⭐ FAILED REQUESTS      ⇒ from the transport layer (Day 273),
⭐                             ⭐⭐ WITH THE REQUEST ID
⭐ ④ ⭐ WEB VITALS           ⇒ the Day 241 beacon

⭐   ⇒ ⭐⭐ ①+② WITHOUT ③ IS THE COMMON MISTAKE: your API errors are
⭐     "handled" (you rendered an error state), so they never reach
⭐     the error tracker — ⭐ AND YOU HAVE NO IDEA HOW OFTEN YOUR
⭐     OWN API FAILS FOR REAL USERS.
```

# Part 2 — ⭐⭐ The noise

```
⭐⭐ IN A REAL FRONTEND ERROR FEED, THE MAJORITY IS NOT YOUR BUG.

⭐   · ⭐⭐ BROWSER EXTENSIONS injecting scripts that throw
⭐   · ⭐ "Script error." with no stack ⇒ a cross-origin script and
⭐     no CORS header. ⭐⭐ ZERO INFORMATION. Filter it.
⭐   · ⭐ ResizeObserver loop limit exceeded ⇒ ⭐⭐ BENIGN. It is
⭐     famously noisy and almost never a real bug.
⭐   · ⭐ NETWORK ERRORS FROM USERS ON TRAINS / IN LIFTS
⭐   · ⭐⭐ CHUNK LOAD ERRORS AFTER A DEPLOY (Day 245) — expected,
⭐     and handled by the reload-once guard
⭐   · bots and scrapers running with JS disabled or ancient engines

⭐   ⇒ ⭐⭐ FILTER AGGRESSIVELY, AND WRITE DOWN WHY YOU FILTERED
⭐     EACH ONE. ⭐ AN UNFILTERED FEED IS AN IGNORED FEED, AND AN
⭐     IGNORED FEED IS WORSE THAN NO FEED — because you believe
⭐     you have monitoring.
```

| ⭐ Filter | ⭐⭐ Keep |
|---|---|
| `Script error.` with no stack | Anything with a stack in **your** bundle |
| Errors from extension URLs (`chrome-extension://`) | ⭐⭐ Errors correlated with a **deploy** |
| `ResizeObserver loop…` | ⭐ Errors affecting **many users** |
| Network errors on a single session | ⭐⭐ A **rate** change, not a count |

> ⭐⭐ **Alert on rate, never on count.** "12 errors today" is meaningless. **"The error rate for
> checkout tripled after the 14:02 deploy"** is actionable, and it is the same lesson as Day 455: the
> signal is the *change*, and a raw count of a noisy stream will page you at 3 a.m. for nothing.

# Part 3 — Making a report actionable

```typescript
Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,     // ⭐ public by design (Day 222)
  release: __BUILD_ID__,                     // ⭐⭐ WHICH BUILD. Essential.
  environment: import.meta.env.MODE,
  tracesSampleRate: 0.1,
  ignoreErrors: [ "ResizeObserver loop", "Script error." ],   // ⭐ Part 2
  denyUrls: [ /extensions\//i, /^chrome-extension:\/\// ],
  beforeSend(event) {
    if (event.request?.url) event.request.url = stripPII(event.request.url);
    return event;                            // ⭐⭐ SCRUB BEFORE SENDING
  },
});

Sentry.setUser({ id: user.id });              // ⭐⭐ ID ONLY — never email/name
Sentry.setTag("requestId", requestId);        // ⭐ ties to your server logs
```

```
⭐⭐ THE FIVE THINGS THAT TURN "IT BROKE" INTO A FIX

⭐   ① ⭐ THE RELEASE/BUILD ID ⇒ "only on build 4f2a" answers half
⭐      the question instantly
⭐   ② ⭐⭐ THE REQUEST ID ⇒ Day 273. ⭐ NOW YOU CAN GREP THE SERVER
⭐      LOG FOR THE SAME REQUEST. ⭐⭐ THIS IS THE SINGLE HIGHEST-VALUE
⭐      LINE IN YOUR OBSERVABILITY SETUP.
⭐   ③ BREADCRUMBS ⇒ the clicks and requests before the error
⭐   ④ ⭐ USER ID (not name/email) ⇒ "how many users?" and "the
⭐      same user 40 times?" are different bugs
⭐   ⑤ ⭐⭐ SOURCE MAPS UPLOADED, NOT SERVED ⇒ readable stacks for
⭐      you, no .map files on the CDN (Day 222)
```

| ⭐ Privacy | ⭐⭐ Day 450 applies here too |
|---|---|
| **No PII in tags or user context** | ⭐ An id, not an email |
| **Scrub URLs** | ⭐⭐ Tokens and ids in query strings end up in your error tracker forever (Day 233) |
| **Mask inputs in session replay** | ⭐⭐ Replay is the **most sensitive telemetry you can collect** — it can record a password field or a medical form. Mask by default, allow-list exceptions. |
| **Have a retention answer** | ⭐ "How long do we keep this?" is a question you should not meet for the first time in an audit |

# Part 4 — What to actually watch

```
⭐⭐ FOUR NUMBERS. ⭐ NOT A DASHBOARD OF FORTY.

⭐   ① ⭐⭐ ERROR RATE PER SESSION, split BY RELEASE
⭐      ⇒ ⭐ the deploy-regression detector. The most useful single
⭐        chart a frontend has.
⭐   ② ⭐ API FAILURE RATE, by endpoint, from the CLIENT's view
⭐      ⇒ ⭐⭐ THIS DIFFERS FROM YOUR SERVER'S NUMBER, and the
⭐        difference IS the network, the CDN, and CORS.
⭐   ③ ⭐ LCP / INP p75 from real users (Day 241)
⭐   ④ ⭐⭐ THE RATE OF ONE BUSINESS EVENT — "orders created per
⭐      hour". ⭐ It catches what no technical metric does: a
⭐      deploy where nothing errors and the button no longer works.

⭐   ⇒ ⭐⭐ ④ IS THE ONE PEOPLE SKIP AND THE ONE THAT CATCHES THE
⭐     WORST OUTAGES. Everything returns 200 and the funnel is dead.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you know when the frontend is broken?"**

Start with the counterintuitive part, because it demonstrates you have actually run one. **The hard
problem isn't collecting errors, it's filtering them. A real frontend error feed is dominated by things
I can't fix — browser extensions injecting scripts, "Script error" with no stack from cross-origin
files, ResizeObserver noise, users losing signal on a train. An unfiltered feed is an ignored feed, and
an ignored feed is worse than none because I'd believe I had monitoring.**

Then the signal that hides. **The one people miss is failed API requests. Those are "handled" — I
rendered a nice error state — so they never reach the error tracker, and I'd have no idea how often my
own API fails for real users. That number also differs from my server's, and the difference is the
network, the CDN and CORS.**

Then what makes a report usable. **Release id, so "only on build 4f2a" answers half the question. Then
the request id my transport layer generates and my API logs — that's the highest-value line in the whole
setup, because a user's screenshot becomes a server-log query. Source maps uploaded rather than served,
user id rather than email, and URLs scrubbed, because tokens in query strings otherwise live in the
error tracker forever.**

Close on alerting and the metric people skip. **I alert on rate split by release, never on count —
twelve errors today is meaningless, the checkout error rate tripling after the 14:02 deploy is
actionable. And I track one business event, orders created per hour, because the worst outage is the
one where nothing throws, everything returns 200, and the button just doesn't work any more.**
