# Day 430 ✂️

**P-430** · ✂️ **Chunking is the ceiling** — ⭐⭐ no reranker fixes a bad chunk

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a chunk is simultaneously the unit you search over and the unit you hand
> to the model, and those two jobs want opposite sizes — every chunking strategy that exists is an
> attempt to stop one object from having to be both.**

---

# Part 1 — ⭐⭐ Why this is the ceiling and not a tuning knob

```
⭐ THE ORDER OF OPERATIONS MATTERS: ⭐ everything downstream —
⭐   embeddings, hybrid search, reranking, the prompt — ⭐⭐ CAN
⭐   ONLY ***REORDER*** WHAT CHUNKING PRODUCED. ⭐ None of them
⭐   can create information that no chunk contains.

⭐⭐ ⇒ IF THE ANSWER IS SPLIT ACROSS TWO CHUNKS SO THAT NEITHER
⭐   CONTAINS IT, ***RECALL@k IS ZERO AT EVERY k***, and a
⭐   $2,000/month reranker reranks nothing.

⭐ THE CONCRETE VERSION, WHICH YOU WILL HIT:
⭐   ⭐ Chunk 14 ends: "…the refund window is"
⭐   ⭐ Chunk 15 begins: "30 days from delivery, except for…"
⭐   ⭐⭐ NEITHER CHUNK ANSWERS "HOW LONG IS THE REFUND WINDOW?"
⭐   ⭐ Chunk 14 embeds near the question and is retrieved.
⭐   ⭐⭐ THE MODEL THEN ANSWERS FROM PARAMETRIC MEMORY AND SAYS
⭐     "14 DAYS", FLUENTLY, WITH YOUR CITATION ATTACHED.
```

⭐⭐ **This is why chunking is the first thing you fix and the last thing people look at.**

# Part 2 — The tension, stated exactly

```
⭐ ***THE CHUNK IS THE RETRIEVAL UNIT.*** ⭐ It gets embedded to
⭐   a single vector. ⭐⭐ A VECTOR IS A CENTROID OF MEANING —
⭐   ⭐ the more topics a chunk covers, the more the vector drifts
⭐   to the average of all of them ⭐⭐ AND MATCHES NONE OF THEM
⭐   WELL. ⭐ → this pressure says ***SMALL***.

⭐ ***THE CHUNK IS ALSO THE GENERATION UNIT.*** ⭐ It is what the
⭐   model reads. ⭐⭐ A 120-TOKEN FRAGMENT THAT SAYS "THIS DOES
⭐   NOT APPLY IN THAT CASE" IS UNUSABLE WITHOUT THE PARAGRAPH
⭐   ABOVE IT. ⭐ → this pressure says ***LARGE***.

⭐⭐ THESE ARE NOT PREFERENCES YOU BALANCE — ⭐ they are two
⭐   different jobs. ⭐⭐ EVERY SERIOUS TECHNIQUE IN THIS DAY IS A
⭐   WAY OF ***SEPARATING THE TWO UNITS***: ⭐ embed one thing,
⭐   return a different thing.

⭐  ┌────────────┬──────────────────┬──────────────────────────┐
⭐  │ SIZE       │ RETRIEVAL        │ GENERATION               │
⭐  ├────────────┼──────────────────┼──────────────────────────┤
⭐  │ 100–200 tk │ ⭐ precise       │ ❌ no context, unusable  │
⭐  │ 400–800 tk │ ⭐ good          │ ⭐ usually enough         │
⭐  │ 1500+ tk   │ ❌ centroid drift│ ⭐ complete              │
⭐  │ whole doc  │ ❌ matches every │ ❌ blows the budget and  │
⭐  │            │   question badly │   triggers lost-in-middle│
⭐  └────────────┴──────────────────┴──────────────────────────┘

⭐⭐ THE DEFAULT THAT IS RIGHT MORE OFTEN THAN IT DESERVES TO BE:
⭐   ***~600 TOKENS, ~15% OVERLAP, SPLIT ON STRUCTURE.***
⭐   ⭐ Start there, then let the eval move it (Day 435).
```

# Part 3 — The five strategies, ranked by what they actually buy

```
⭐ ① ***FIXED-SIZE + OVERLAP.*** ⭐ Split every N tokens, repeat
⭐   the last M. ⭐⭐ ONLY DEFENSIBLE FOR UNSTRUCTURED PROSE WITH
⭐   NO MARKUP AT ALL. ⭐ Overlap is a patch for the split-answer
⭐   bug, not a fix — it halves the chance, doesn't remove it,
⭐   and it inflates your index by the overlap fraction.

⭐ ② ***RECURSIVE CHARACTER SPLITTING.*** ⭐ Try to split on
⭐   "\n\n", then "\n", then ". ", then " ". ⭐⭐ THE CORRECT
⭐   BASELINE. ⭐ Cheap, no model, respects paragraphs. ⭐ This is
⭐   what LangChain's RecursiveCharacterTextSplitter does and it
⭐   is genuinely fine.

⭐ ③ ***DOCUMENT-STRUCTURE-AWARE.*** ⭐⭐ THE ONE THAT ACTUALLY
⭐   WINS. ⭐ Split on the document's own semantics: markdown
⭐   headings, HTML sections, PDF outline, code functions,
⭐   Confluence blocks. ⭐⭐ THE AUTHOR ALREADY DID THE SEMANTIC
⭐   SEGMENTATION FOR YOU — ⭐ headings exist precisely because
⭐   a human decided "this is one idea". ⭐⭐ USE THEIR WORK.
⭐   ⭐ Then merge sections under ~200 tokens and split ones over
⭐     ~800 recursively.

⭐ ④ ***SEMANTIC CHUNKING.*** ⭐ Embed each sentence, split where
⭐   consecutive similarity drops below a threshold. ⭐⭐ SOUNDS
⭐   OBVIOUSLY BETTER. ⭐ In practice: one embedding call per
⭐   sentence (expensive at corpus scale), a threshold you must
⭐   tune per corpus, and ⭐⭐ ON STRUCTURED DOCUMENTS IT USUALLY
⭐   LOSES TO JUST USING THE HEADINGS. ⭐ Worth trying only when
⭐   ③ is impossible — transcripts, OCR, chat logs.

⭐ ⑤ ***LLM-ASSISTED / AGENTIC CHUNKING.*** ⭐ Ask a model where
⭐   the boundaries are. ⭐⭐ REAL QUALITY, ABSURD COST AT SCALE,
⭐   AND NON-DETERMINISTIC BOUNDARIES BREAK YOUR CONTENT-HASH
⭐   CACHE (Day 431). ⭐ Reserve for small, high-value corpora.
```

# Part 4 — ⭐⭐ The contextual prefix: biggest win per line of code

```
⭐ THE PROBLEM, IN ONE CHUNK:
⭐   ⭐ "It must be renewed within 30 days of expiry, otherwise
⭐     a new application is required."
⭐   ⭐⭐ WHAT MUST? ⭐ The chunk does not say. ⭐ It embeds near
⭐     "renewal", "30 days", "application" — ⭐⭐ AND EQUALLY NEAR
⭐     EVERY OTHER RENEWAL RULE IN THE CORPUS.

⭐ THE FIX: ***PREPEND THE DOCUMENT AND HEADING PATH TO THE TEXT
⭐   YOU EMBED.***
⭐   ⭐ "Driver Licensing Handbook > Section 4: Renewals >
⭐     4.2 Late renewal — It must be renewed within 30 days…"
⭐   ⭐⭐ THE VECTOR NOW ENCODES ***WHICH*** RENEWAL, ⭐ and the
⭐     model reading it knows too.

⭐⭐ MEASURED EFFECT ON MOST REAL CORPORA: ⭐ recall@5 up by
⭐   10–20 points, for ~15 lines of code and zero extra
⭐   inference. ⭐⭐ NOTHING ELSE IN THIS SUB-STAGE HAS THAT
⭐   RATIO. ⭐ Do it before you consider a reranker.

⭐ ⭐ Day 436's "contextual retrieval" is the expensive,
⭐   stronger version of exactly this idea.
```

```python
import re, hashlib
from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Chunk:
    doc_id: str
    text: str                    # ⭐ what the model reads
    heading_path: str            # ⭐ "Handbook > Renewals > 4.2 Late renewal"
    ordinal: int
    tenant_id: str               # ⭐⭐ Day 434 — NOT optional, ever
    source_uri: str
    updated_at: str
    token_count: int

    @property
    def embed_text(self) -> str:
        """⭐⭐ WHAT GETS EMBEDDED IS NOT WHAT GETS SHOWN.
        ⭐ This one property is the contextual prefix."""
        return f"{self.heading_path}\n\n{self.text}"

    @property
    def content_hash(self) -> str:
        # ⭐ Day 431 — the key that stops you re-embedding
        # unchanged text every night.
        return hashlib.sha256(self.embed_text.encode()).hexdigest()[:16]
```

# Part 5 — Markdown-structure chunking, end to end

```python
HEADING = re.compile(r"^(#{1,6})\s+(.*)$")

def split_markdown(text: str, *, target: int = 600, hard_max: int = 900,
                   count_tokens=len) -> list[tuple[str, str]]:
    """⭐ Returns (heading_path, body) pairs.
    ⭐⭐ THE HEADING STACK IS THE WHOLE TRICK — it gives every
    chunk its ancestry for free."""
    sections: list[tuple[str, list[str]]] = []
    stack: list[str] = []
    buf: list[str] = []

    def flush():
        if buf and any(l.strip() for l in buf):
            sections.append((" > ".join(stack), buf[:]))
        buf.clear()

    for line in text.splitlines():
        m = HEADING.match(line)
        if m:
            flush()
            level = len(m.group(1))
            stack[:] = stack[: level - 1]          # ⭐ pop to depth
            stack.append(m.group(2).strip())
        else:
            buf.append(line)
    flush()

    # ⭐⭐ NOW THE TWO REPAIRS THAT MAKE IT PRODUCTION-GRADE.
    out: list[tuple[str, str]] = []
    for path, lines in sections:
        body = "\n".join(lines).strip()
        n = count_tokens(body)
        if n == 0:
            continue
        if n <= hard_max:
            out.append((path, body))
            continue
        # ⭐ too big: split on paragraphs, keeping the SAME path
        # so every piece retains its ancestry.
        cur, size = [], 0
        for para in body.split("\n\n"):
            p = count_tokens(para)
            if size + p > target and cur:
                out.append((path, "\n\n".join(cur)))
                cur, size = [], 0
            cur.append(para); size += p
        if cur:
            out.append((path, "\n\n".join(cur)))

    # ⭐ merge runaway-small sections into their neighbour —
    # a 12-token chunk is pure index noise.
    merged: list[tuple[str, str]] = []
    for path, body in out:
        if merged and count_tokens(body) < 120 and count_tokens(merged[-1][1]) < target:
            merged[-1] = (merged[-1][0], merged[-1][1] + "\n\n" + body)
        else:
            merged.append((path, body))
    return merged
```

⭐ Swap `count_tokens=len` for `tiktoken` in production. ⭐⭐ Do not tune sizes in characters — the
budget you actually spend is in tokens (Day 415), and the ratio differs 3× between English prose and a
table of numbers.

# Part 6 — ⭐⭐ Tables, code and PDFs: where naive chunking dies

```
⭐⭐ ① ***TABLES ARE THE #1 SILENT KILLER.***
⭐   ⭐ A pricing table split at row 8 puts the ***headers*** in
⭐     chunk 3 and the ***numbers*** in chunk 4.
⭐   ⭐⭐ CHUNK 4 IS A GRID OF DIGITS WITH NO LABELS. ⭐ It embeds
⭐     near nothing, and if it is ever retrieved the model will
⭐     invent what the columns mean.
⭐   ⭐ FIXES, in order of preference:
⭐     ⭐ never split a table — one table = one chunk, even at
⭐       1,500 tokens;
⭐     ⭐ if you must split, ***repeat the header rows*** in each
⭐       piece;
⭐     ⭐⭐ OR CONVERT THE TABLE TO SENTENCES AT INGEST — "The
⭐       Pro plan costs £49/month and includes 10 seats." ⭐ Ugly,
⭐       enormously effective, and it embeds properly.

⭐⭐ ② ***CODE.*** ⭐ Split on function/class boundaries, never on
⭐   line count. ⭐ Keep the imports or the class signature as the
⭐   heading path. ⭐⭐ A CHUNK CONTAINING THE BODY OF A METHOD
⭐   WITHOUT ITS NAME IS UNRETRIEVABLE — the name is the only
⭐   part anyone searches for.

⭐⭐ ③ ***PDFs.*** ⭐ The honest warning: ⭐⭐ PDF EXTRACTION IS A
⭐   HARDER PROBLEM THAN EVERYTHING ELSE IN THIS SUB-STAGE
⭐   COMBINED. ⭐ Two-column layouts interleave, headers and
⭐   footers appear mid-sentence, ligatures break words, scanned
⭐   pages need OCR. ⭐⭐ BUDGET REAL TIME FOR IT AND ***READ 20
⭐   EXTRACTED DOCUMENTS BY EYE*** BEFORE YOU EMBED ANYTHING.
⭐   ⭐ Half the "the model is stupid" bugs are extraction bugs.

⭐⭐ ④ ***BOILERPLATE.*** ⭐ Nav bars, cookie banners, "Confidential
⭐   — do not distribute" footers. ⭐⭐ THEY REPEAT IN EVERY CHUNK,
⭐   SO EVERY CHUNK LOOKS SIMILAR TO EVERY OTHER, AND YOUR
⭐   SIMILARITY SCORES ALL COMPRESS TOWARDS EACH OTHER. ⭐ Strip
⭐   them at ingest and your recall goes up for free.
```

# Part 8 — You cannot argue your way to a chunk size

```
⭐ EVERY BLOG POST SAYS A DIFFERENT NUMBER BECAUSE ⭐⭐ THE RIGHT

⭐   QUESTIONS***, NOT OF CHUNKING.

⭐   ⭐ structure-aware + prefix beats everything else by a
⭐     margin larger than any size difference;

⭐     stop arguing about it;

⭐   your per-request input bill. ⭐ 600 × 8 = 4,800 tokens.

⭐     FOR THE SAME ANSWER.***
```

# 💬 Interview

**1. "How did you decide your chunk size?"**

⭐ I measured it rather than picking it. ⭐⭐ I built a 30-question eval set with known-correct source
documents, then swept size, overlap, splitting strategy and the contextual prefix — about forty
configurations — scoring only **recall@5**, deliberately with no generation involved so nothing else
could confound it. ⭐ Two things came out. ⭐⭐ The size curve was flat between 400 and 900 tokens, so
that argument doesn't matter as much as people think; and structure-aware splitting with a heading
prefix beat every fixed-size variant by more than any size difference. ⭐ Then cost broke the tie:
chunk size times k is my per-request input bill, so 600 tokens at k=8 rather than 1,400 is less than
half the cost for the same measured recall.

**2. "Why does chunking matter more than the reranker?"**

⭐⭐ Because everything downstream can only reorder what chunking produced. ⭐ An embedding model, a
hybrid search, a cross-encoder reranker — none of them can create information that no chunk contains.
⭐ If the answer is split so that neither chunk holds it, recall is zero at every k and the reranker is
sorting a list that doesn't contain the answer. ⭐⭐ That's why I call it the ceiling: it sets the
maximum score every other component is competing for a fraction of.

**3. "What is the contextual prefix and why does it work?"**

⭐ Before embedding, I prepend the document title and the heading path to the chunk text — so what gets
embedded is `"Handbook > Renewals > 4.2 Late renewal\n\n It must be renewed within 30 days…"`, while
what gets *shown* stays the raw text. ⭐⭐ It works because a chunk full of pronouns embeds near
nothing — "it must be renewed" is equally close to every renewal rule in the corpus. ⭐ The prefix puts
the missing subject back into the vector. ⭐⭐ On our corpus it moved recall@5 by about 15 points for
fifteen lines of code and no extra inference cost, which is a better ratio than anything else I did in
that pipeline.

**4. "What broke when you first shipped ingestion?"**

⭐ Tables. ⭐⭐ A pricing table got split mid-way, so the column headers were in one chunk and the
numbers in another. ⭐ The numbers chunk was a grid of digits with no labels — it embedded near nothing
and was never retrieved, and when it *was*, the model confidently invented what the columns meant. ⭐ I
fixed it by treating a table as atomic — one table, one chunk, even at 1,500 tokens — and for the huge
ones, converting rows to sentences at ingest: "The Pro plan costs £49 per month and includes 10 seats."
⭐⭐ That's ugly and it works far better than anything clever, because that sentence embeds the way the
question is asked.

**5. "What metadata do you attach, and which field did you wish you'd added earlier?"**

⭐ Tenant, ACL, doc id, source URI, heading path, ordinal, updated-at, content hash, token count, and
the embedding model version. ⭐⭐ The one I'd insist on from day one is `doc_id`, because without it
"this document was deleted" is unanswerable — you can't find the chunks to remove and your index leaks
deleted content indefinitely. ⭐ The index is derived state, and derived state needs a key back to its
source. ⭐ Second is the embedding model version: without it a reindex becomes guesswork about which
vectors are stale.

**6. "Would you use semantic chunking?"**

⭐ I'd try it, but I'd expect to lose. ⭐⭐ Semantic chunking embeds every sentence and splits where
similarity drops — that's one embedding call per sentence at ingest, plus a threshold you have to tune
per corpus, and on documents that already have headings it's competing against segmentation a human
author did deliberately. ⭐ Headings exist precisely because someone decided "this is one idea". ⭐⭐ I'd
reach for semantic chunking where that structure genuinely doesn't exist — meeting transcripts, OCR
output, chat logs — and even then I'd measure it against recursive splitting before paying for it.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "walk me through your ingestion pipeline."**

Lead with the claim, because it inverts what the interviewer expects. **Chunking is the highest-leverage
decision in a RAG system and almost nobody treats it that way — everything downstream, embeddings,
hybrid search, reranking, can only reorder what chunking produced. If the answer isn't in any chunk,
recall is zero at every k and the reranker is sorting a list that doesn't contain it.**

Then name the tension, which is the part that shows you understand the mechanism. **One object is doing
two jobs. It's the retrieval unit, so it gets compressed to a single vector — and the more topics it
covers, the more that vector drifts to an average that matches nothing. And it's the generation unit,
so a hundred-token fragment saying "this doesn't apply in that case" is useless without the paragraph
above it. Small for search, large for reading. Every serious technique in this area is a way of
separating those two units — embed one thing, return a different thing.**

Then what you actually built. **We split on the document's own structure rather than on character
counts, because headings exist because a human decided "this is one idea" — that's free semantic
segmentation. We merge sections under about 120 tokens and split ones over 900, keeping the heading
path on every piece. Then the highest-return line in the whole pipeline: we prepend the document title
and heading path to the text before embedding, while showing the raw text to the user. That moved
recall@5 by about fifteen points for fifteen lines of code.**

Close with measurement and a scar. **We didn't pick 600 tokens from a blog post — we swept forty
configurations against thirty questions and scored recall@5 with no generation involved, so nothing
could confound it. The size curve was flat from 400 to 900, so cost broke the tie: size times k is the
per-request bill. And the scar is tables. A pricing table split mid-way put the headers in one chunk
and the numbers in another, and the model invented what the columns meant. Now tables are atomic, and
the big ones get flattened into sentences at ingest — which is ugly, and it works, because that's how
the question gets asked.**
