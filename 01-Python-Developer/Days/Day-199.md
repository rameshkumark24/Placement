# Day 199

**L-199** · 🐘 **Full-text search** — ⭐⭐ how far Postgres actually gets you, and the honest line

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: "search" is four different problems, and most teams reach for
> Elasticsearch because they picked the wrong one — not because Postgres was too small.**
>
> ⭐ Substring matching, full-text search, fuzzy matching and semantic search have different data

# Part 1 — ⭐⭐ Four problems people call "search"

```
⭐⭐ ① SUBSTRING / "CONTAINS"    — `LIKE '%widget%'`
⭐    ⭐ Users think: "find this exact fragment anywhere."
⭐    ⭐⭐ TOOL: pg_trgm + GIN (Day 190). NOT full-text search.
⭐    ⭐ FTS would MISS `'idge'` inside `'bridge'` entirely.

⭐⭐ ② FULL-TEXT SEARCH          — "running shoes" matches "ran to shoe"
⭐    ⭐ Word-aware: stemming, stopwords, ranking, phrases.
⭐    ⭐⭐ TOOL: tsvector/tsquery + GIN. Today's subject.

⭐⭐ ③ FUZZY / TYPO TOLERANCE    — "wirless" finds "wireless"
⭐    ⭐⭐ TOOL: pg_trgm `similarity()` / `<->`, or `levenshtein()` from
⭐      fuzzystrmatch. ⭐⭐ FTS DOES NOT DO THIS AT ALL — a misspelling
⭐      stems to a different lexeme and matches nothing.

⭐⭐ ④ SEMANTIC / MEANING        — "cheap laptop" matches "budget notebook"
⭐    ⭐⭐ TOOL: embeddings + pgvector (HNSW index). Different problem
⭐      entirely, and increasingly the one people actually want.

⭐ ⇒ ⭐⭐ A REAL PRODUCT SEARCH BOX IS USUALLY ② + ③, SOMETIMES + ④.
⭐   ⭐ Building ② and complaining it cannot do ③ is the single most
⭐     common reason teams conclude "Postgres search is bad".
```

# Part 2 — ⭐ The pipeline: text to lexemes

```sql
SELECT to_tsvector('english', 'The Running Shoes were running fast');
--  ⇒ 'fast':6 'run':2,5 'shoe':3
--    ⭐ 'The','were' dropped     → STOPWORDS
--    ⭐ 'Running','running' → 'run' → STEMMING (and case folded)
--    ⭐ ':2,5' → POSITIONS, which is what makes phrase search possible

SELECT to_tsvector('simple', 'The Running Shoes');
--  ⇒ 'running':2 'shoes':3 'the':1
--    ⭐⭐ 'simple' = LOWERCASE AND SPLIT, NOTHING ELSE. ⭐ Use it for
--      codes, SKUs, tags, usernames — anything where 'running' must not
--      become 'run'.
```

```
⭐⭐ THE FOUR QUERY PARSERS, AND ONLY ONE IS SAFE FOR USER INPUT:

⭐   to_tsquery('english', 'run & shoe')     ⭐ full operator syntax
⭐     ⭐⭐ RAISES A SYNTAX ERROR ON ORDINARY USER TEXT. Typing
⭐        `shoes & ` or `c++` gives your user a 500.
⭐   plainto_tsquery('running shoes')        ⭐ ANDs the words. Safe,
⭐     but no phrases, no OR, no negation.
⭐   phraseto_tsquery('running shoes')       ⭐ words adjacent, in order
⭐   ⭐⭐ websearch_to_tsquery('shoes -red "trail running" or boots')
⭐     ⭐⭐ ***THE ONE TO USE.*** Google-style syntax: quotes for
⭐        phrases, `-` for exclusion, `or` for alternatives. ⭐⭐ NEVER
⭐        RAISES ON MALFORMED INPUT. ⭐ PG 11+.
⭐   ⇒ ⭐⭐ IF YOU REMEMBER ONE LINE FROM TODAY: PASS USER INPUT TO
⭐     `websearch_to_tsquery`, NEVER TO `to_tsquery`.
```

# Part 3 — ⭐⭐ Building it properly

```sql
-- ⭐⭐ THE MODERN DESIGN (PG 12+): A STORED GENERATED COLUMN.
ALTER TABLE articles ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
      setweight(to_tsvector('english', coalesce(title,   '')), 'A') ||
      setweight(to_tsvector('english', coalesce(summary, '')), 'B') ||
      setweight(to_tsvector('english', coalesce(body,    '')), 'C')
  ) STORED;
CREATE INDEX ON articles USING gin (search);

-- ⭐⭐ WHY GENERATED RATHER THAN A TRIGGER OR AN EXPRESSION INDEX:
--   ⭐ vs TRIGGER: no code to maintain, ⭐⭐ and impossible to bypass —
--     `bulk_create`, a data migration or psql all keep it correct
--     (Day 172's "bulk ops skip everything" cannot bite you).
--   ⭐ vs EXPRESSION INDEX: the vector is stored once, not recomputed
--     for ranking on every matching row. ⭐⭐ That matters in Part 4.
--   ⭐ COST: it is STORED (roughly +30–50% of the text size), and
--     changing the expression rewrites the table.
--   ⭐⭐ `coalesce` IS NOT OPTIONAL — one NULL makes the whole
--     concatenation NULL and that row becomes unsearchable, silently.

-- ⭐ `setweight` A/B/C/D lets a title match outrank a body match. ⭐⭐ It
--   is the only relevance control you get, and you should use it.

SELECT id, title FROM articles
WHERE search @@ websearch_to_tsquery('english', $1)
LIMIT 20;
-- ⭐ `@@` uses the GIN index. ⭐⭐ CHECK IT — `EXPLAIN` should show a
--   Bitmap Index Scan on the GIN index, not a Seq Scan with a Filter.
```

# Part 4 — ⭐⭐ Ranking, and the limitation you must know before you promise anything

```sql
SELECT id, title, ts_rank_cd(search, q) AS rank
FROM articles, websearch_to_tsquery('english', $1) q
WHERE search @@ q
ORDER BY rank DESC
LIMIT 10;
-- ⭐ `ts_rank`    — term frequency and weights
-- ⭐ `ts_rank_cd` — also rewards terms appearing CLOSE together.
--   ⭐⭐ Usually better for multi-word queries. Try both on real data.
```

```
⭐⭐ THE LIMITATION, STATED PLAINLY BECAUSE IT DECIDES ARCHITECTURES:

⭐   ⭐⭐ THE GIN INDEX FINDS MATCHES. IT KNOWS NOTHING ABOUT RANK.
⭐   ⇒ ⭐⭐ `ORDER BY ts_rank ... LIMIT 10` MUST SCORE ***EVERY MATCHING
⭐     ROW*** BEFORE IT CAN PICK TEN.
⭐   ⭐ 200 matches   → invisible.
⭐   ⭐ 50,000 matches → hundreds of milliseconds.
⭐   ⭐⭐ 2,000,000 matches (a common word) → SECONDS. And it is your
⭐     MOST COMMON query, because common words are common.
⭐
⭐⭐ THE THREE RESPONSES:
⭐   ① ⭐ NARROW FIRST. Almost every real search has a tenant, a
⭐        category, a date window or a status. ⭐⭐ Filter on an indexed
⭐        column so the match set is thousands, not millions. This
⭐        solves it for most products.
⭐   ② ⭐ PRE-FILTER WITH A CHEAPER RANK: take the top N by a stored
⭐        popularity/recency column, then re-rank those N by relevance.
⭐   ③ ⭐⭐ THE RUM INDEX EXTENSION — stores positions and ranking
⭐        information IN the index, so it can return rows ALREADY
⭐        ORDERED BY RANK. ⭐ Larger and slower to write; solves exactly
⭐        this problem. ⭐⭐ Not available on most managed Postgres,
⭐        which is often what actually forces the decision.
```

```sql
-- ⭐ HIGHLIGHTING — and its cost:
SELECT ts_headline('english', body, q, 'MaxWords=35, MinWords=15')
FROM articles, websearch_to_tsquery('english', $1) q
WHERE search @@ q LIMIT 10;
-- ⭐⭐ `ts_headline` RE-PARSES THE ORIGINAL DOCUMENT FOR EACH ROW. It
--    cannot use the index at all.
-- ⇒ ⭐⭐ ONLY EVER RUN IT ON THE PAGE YOU ARE RETURNING — i.e. AFTER
--    the LIMIT, in a subquery or a second pass. ⭐ Running it across
--    the full match set is a classic self-inflicted timeout.
```

```sql
-- ⭐ FUZZY, layered on top — because FTS alone cannot do typos:
CREATE EXTENSION pg_trgm;
CREATE INDEX ON articles USING gin (title gin_trgm_ops);
SELECT title, similarity(title, $1) s FROM articles
WHERE title % $1 ORDER BY s DESC LIMIT 5;   -- ⭐ `%` = similar enough
-- ⭐⭐ THE PRODUCTION PATTERN: run FTS first; if it returns 0 rows,
--    fall back to trigram similarity as "did you mean". ⭐ Cheap, and
--    it removes 90% of the perceived quality gap with a search engine.

-- ⭐ ACCENTS: `unaccent` so 'cafe' finds 'café'.
CREATE EXTENSION unaccent;
-- ⭐⭐ Wire it into a CUSTOM TEXT SEARCH CONFIGURATION rather than
--    calling `unaccent()` in the query — a function call in the
--    predicate is Day 189 ① all over again.
```

# Part 5 — ⭐⭐ The honest line: when to leave Postgres

```
⭐⭐ STAY IN POSTGRES WHEN — and this covers more products than people
⭐   believe:
⭐   ✅ corpus under ~10M documents
⭐   ✅ ranking needs are "title beats body, recent beats old"
⭐   ✅ searches are naturally scoped (tenant, category, date)
⭐   ✅ near-real-time indexing matters ⭐⭐ (Postgres FTS is
⭐        TRANSACTIONAL — a document is searchable the instant it
⭐        commits, with NO sync lag. A search engine cannot offer this.)
⭐   ✅ permissions must be enforced per row ⭐⭐ (your WHERE clause
⭐        already does it — Day 184's invariant #9. In a search engine,
⭐        per-row permissions are a genuinely hard problem.)

⭐⭐ LEAVE WHEN — each of these is a real wall, not a preference:
⭐   ❌ ⭐⭐ RELEVANCE IS THE PRODUCT. Postgres's ranking is not BM25,
⭐        has no field boosting worth the name, no learning-to-rank, no
⭐        per-query analyzers. ⭐ If a relevance engineer will be tuning
⭐        this weekly, you need a system built for it.
⭐   ❌ FACETING AND AGGREGATIONS over large result sets on every query
⭐        ("1,204 in Electronics, 88 in Books") — ⭐⭐ Postgres computes
⭐        those by scanning the matches; a search engine keeps them in
⭐        the index.
⭐   ❌ TYPO TOLERANCE, SYNONYMS, "DID YOU MEAN", AUTOCOMPLETE AND
⭐        MULTI-LANGUAGE ANALYSIS ALL AT ONCE ⭐ — each is doable alone
⭐        in Postgres; ⭐⭐ all together is a project.
⭐   ❌ ⭐⭐ THE INDEX NO LONGER FITS IN RAM and you need horizontal
⭐        scale-out of the search layer specifically.
⭐   ❌ ⭐ Write rates where GIN maintenance dominates your write budget.

⭐⭐ AND THE PRICE OF LEAVING, WHICH MUST BE IN THE DECISION:
⭐   ⭐⭐ YOU NOW OWN THE DUAL-WRITE PROBLEM (Day 142). Postgres commits
⭐     and Elasticsearch does not ⇒ a document that exists and cannot be
⭐     found, forever, with no error.
⭐   ⇒ ⭐⭐ THE ONLY CORRECT SYNC IS THE OUTBOX OR CDC (Debezium /
⭐     logical replication) — ⭐ NOT a `.delay()` after commit, and
⭐     certainly not a write inside the transaction.
⭐   ⭐ Plus: a reindex runbook, permission filtering, a second thing to
⭐     monitor and secure, and results that lag writes by seconds.
⭐   ⇒ ⭐⭐ THAT IS THE REAL COMPARISON. Not "is Postgres FTS as good as
⭐     Elasticsearch" (it is not) but "is the relevance gap worth a
⭐     distributed data-sync problem" — ⭐ which, for most products
⭐     below ten million documents, it is not.
```

# Part 6 — ⭐ In Python

```python
# ⭐ SQLAlchemy
from sqlalchemy.dialects.postgresql import TSVECTOR
from sqlalchemy import func, Index, Computed

class Article(Base):
    search: Mapped[str] = mapped_column(
        TSVECTOR,
        Computed("setweight(to_tsvector('english', coalesce(title,'')),'A') "
                 "|| setweight(to_tsvector('english', coalesce(body,'')),'C')",
                 persisted=True),                 # ⭐ STORED
    )
    __table_args__ = (Index("ix_articles_search", "search",
                            postgresql_using="gin"),)

q = func.websearch_to_tsquery("english", user_input)   # ⭐⭐ never
stmt = (select(Article)                                #    to_tsquery
        .where(Article.tenant_id == tenant_id)         # ⭐⭐ NARROW FIRST
        .where(Article.search.op("@@")(q))
        .order_by(func.ts_rank_cd(Article.search, q).desc())
        .limit(20))
```

```python
# ⭐ Django — the same design, different spelling
from django.contrib.postgres.search import (
    SearchVector, SearchQuery, SearchRank, SearchVectorField)
from django.contrib.postgres.indexes import GinIndex

class Article(models.Model):
    search = SearchVectorField(null=True)          # ⭐ populated by a
    class Meta:                                    #   generated column
        indexes = [GinIndex(fields=["search"])]    #   or a trigger

q = SearchQuery(user_input, search_type="websearch")   # ⭐⭐ THE FLAG
Article.objects.filter(tenant_id=t, search=q).annotate(
    rank=SearchRank("search", q)).order_by("-rank")[:20]
# ⭐⭐ AND THE DJANGO TRAP: `SearchVector("title","body")` in the QUERY
#    computes the vector AT QUERY TIME FOR EVERY ROW — ⭐⭐ a full scan,
#    no index, and it is what every tutorial shows. ⭐ The vector must
#    be a STORED COLUMN.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Using FTS for substring matching | It's word-aware; `'idge'` won't match `'bridge'`. Use trigram. |
| Expecting FTS to handle typos | A misspelling stems to a different lexeme and matches nothing. |
| Passing user input to `to_tsquery` | It raises a syntax error on ordinary text. Use `websearch_to_tsquery`. |
| Using `'english'` for SKUs, tags or usernames | Stemming mangles them. Use `'simple'`. |
| Omitting `coalesce` in the vector expression | One NULL makes the whole concatenation NULL and the row unsearchable. |
| Computing the tsvector at query time | Full scan, no index — and it's what most tutorials show. |
| A trigger instead of a generated column | The generated column can't be bypassed by bulk operations or psql. |
| Not using `setweight` | It's the only relevance control you get. |
| Promising `ORDER BY ts_rank` on a huge match set | Ranking scores every match; the index doesn't know rank. |
| Running `ts_headline` before the `LIMIT` | It re-parses each document and can't use the index. |
| Calling `unaccent()` in the predicate | A function on the column. Build a text search configuration instead. |
| Concluding "Postgres search is bad" without a fallback | FTS then trigram "did you mean" closes most of the perceived gap. |
| Adding a search engine without an outbox or CDC | You've bought the dual-write problem: findable-nowhere documents, no error. |
| Ignoring per-row permissions when comparing | Your `WHERE` clause does it for free; in a search engine it's genuinely hard. |

## Interview questions

**Q: How would you add search to an existing Postgres application?**

> First I'd work out which of four problems it is, because that decides everything: substring
> matching, full-text search, typo tolerance, or semantic similarity. They need different data
> structures, and most "Postgres search is bad" conclusions come from building full-text search and
> complaining it can't do substrings or typos. Assuming it's genuinely full-text: a stored generated
> `tsvector` column combining the fields with `setweight` so a title match outranks a body match, a GIN
> index on it, and `websearch_to_tsquery` for the user's input. I'd choose the generated column over a
> trigger because it can't be bypassed by a bulk insert, a data migration or psql, and over an
> expression index because the vector needs to be stored for ranking anyway. And I'd make sure every
> search is narrowed by tenant or category first, for the reason in the next answer.

**Q: What's the main scaling limitation of Postgres full-text search?**

> Ranking. The GIN index finds matches but knows nothing about relevance, so
> `ORDER BY ts_rank ... LIMIT 10` has to score *every* matching row before it can pick ten. With two
> hundred matches that's invisible; with two million — which happens on your most common query, because
> common words are common — it's seconds. There are three responses. Narrow the match set first with an
> indexed filter, which almost every real product can do because searches are scoped by tenant,
> category or date; pre-filter by a cheap stored signal like popularity and re-rank the top N; or use
> the RUM extension, which stores ranking information in the index so it can return rows already
> ordered — at the cost of a bigger, slower-to-write index, and it isn't available on most managed
> Postgres, which is often what actually forces the decision.

**Q: When would you move to Elasticsearch?**

> When relevance is the product — Postgres's ranking isn't BM25, has no serious field boosting, no
> learning-to-rank, and if someone will be tuning relevance weekly they need a system built for that.
> Also when you need faceted counts over large result sets on every query, since Postgres computes
> those by scanning matches while a search engine keeps them in the index; when you need typo
> tolerance, synonyms, autocomplete and multi-language analysis all at once, each of which is doable
> alone in Postgres but together is a project; or when the search index genuinely needs to scale
> horizontally on its own. What I'd insist on putting in the decision is the price: you now own the
> dual-write problem, so Postgres commits and Elasticsearch doesn't and you have a document that exists
> and can never be found, with no error anywhere. The only correct sync is an outbox or CDC, not a
> `.delay()` after commit. Plus a reindex runbook, permission filtering, and seconds of lag. For most
> products under about ten million documents, the relevance gap isn't worth a distributed data-sync
> problem.

**Q: What does Postgres give you that a search engine can't?**

> Two things that people undervalue until they've lost them. First, transactional search: a document
> is searchable the instant its transaction commits, in the same transaction as the write, with no
> sync lag and no possibility of divergence — you can create a record and search for it in the same
> request and it's there. No external search engine can offer that. Second, per-row permissions for
> free: your search query is a `WHERE` clause, so tenant scoping and row-level security apply exactly
> as they do everywhere else, which is the invariant that authorisation lives in the query. In a search
> engine, per-row permission filtering at scale is a genuinely hard problem that people solve with
> denormalised ACL fields, reindexing on permission changes, and post-filtering that breaks pagination
> counts.

**Q: A user searches "wirless headphones" and gets nothing. Why, and what do you do?**

> Because full-text search is exact at the lexeme level — "wirless" stems to something that simply
> isn't in the index, so there's no partial credit and no near-miss. FTS doesn't do typo tolerance at
> all, and that's a category difference, not a tuning problem. The production pattern is to layer:
> run the full-text query first, and if it returns zero rows, fall back to trigram similarity with
> `pg_trgm` — either as results or as an explicit "did you mean". That's cheap, it uses a GIN trigram
> index, and it removes most of the perceived quality gap with a search engine. I'd also add
> `unaccent` wired into a custom text search configuration rather than called in the predicate, since
> a function on the column kills the index, and use the `'simple'` configuration for any field like a
> SKU or username where stemming does more harm than good.

## 🎙️ Articulation drill

**Two minutes: "Would you use Postgres for search, or Elasticsearch?"**

Refuse the binary first: name the four problems and say which one the product actually has, because
half of "Postgres search is bad" is people building full-text search and needing substring or typo
matching. Then describe what a proper Postgres implementation is — stored generated `tsvector` with
weights, GIN index, `websearch_to_tsquery` for user input — in three sentences, so it's clear you'd
build it well rather than badly and then blame the tool. Then state the real limitation with its
mechanism: **the index finds matches but knows nothing about rank, so ordering by relevance scores
every match, and your most common query is the worst case.** Give the three responses, leading with
narrowing by tenant. Then flip to the decision, and make the price explicit: **the day you add a
search engine you own the dual-write problem, so the sync has to be an outbox or CDC, and a failed
sync is a document that exists and can never be found with no error anywhere.** Close on the two things
you'd be giving up: transactional freshness and permissions that are just a `WHERE` clause.
