# Day 217 📡

**P-217** · 📡 **`fetch`** — ⭐⭐ the HTTP client whose error model has no errors in it

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `fetch` only rejects when the request never happened — a 500 with an
> HTML stack trace is a *successful* fetch, so every codebase that does not check `res.ok` has a
> silent bug where server errors render as blank screens instead of error states.**
>
> Today: the one-line trap, ⭐ the wrapper you write once, ⭐⭐ the four states of every request, and
> cancellation.

# Part 1 — ⭐⭐ The trap

```javascript
// ❌ THE BUG THAT IS IN EVERY TUTORIAL
try {
  const res = await fetch("/api/items");
  const data = await res.json();
  setItems(data);
} catch (e) {
  setError(e);            // ⭐⭐ NEVER RUNS FOR A 404 OR A 500
}
```

```
⭐⭐ WHEN DOES fetch ACTUALLY REJECT?

⭐ ✅ IT REJECTS (throws) ONLY WHEN:
⭐    · the network is down / DNS fails
⭐    · CORS blocked it            (Day 237)
⭐    · the request was aborted    (Part 4)
⭐    · ⭐ THE REQUEST NEVER COMPLETED AS AN HTTP EXCHANGE

⭐ ❌ IT DOES **NOT** REJECT FOR:
⭐    · 400  401  403  404  422  429  500  502  503
⭐    ⭐⭐ ALL OF THESE ARE "SUCCESSFUL" FETCHES.
⭐    res.ok is false, and NOTHING ELSE TELLS YOU.

⭐⭐ ⇒ AND THEN res.json() THROWS A **SYNTAX ERROR**, because the
⭐   500 returned an HTML error page. So your catch block finally
⭐   runs — with "Unexpected token '<'" — and you spend an hour
⭐   debugging a JSON parser instead of reading the status code.
```

> ⭐⭐ **Why this design.** `fetch` models *"did an HTTP exchange occur"*, not *"did you get what you
> wanted"*. That is defensible and it is not what anyone expects. **The failure is dangerous
> specifically because it is quiet** — no exception, no red console, just `undefined` flowing into a
> component that renders nothing. It is Day 455's lesson in a client: *the dangerous failure returns
> a response.*

# Part 2 — ⭐ The wrapper you write once

Never call raw `fetch` from a component. This is the same argument as Day 420's API wrapper: one place
to fix, one place to test, one place to add a header.

```javascript
export class ApiError extends Error {
  constructor(status, body, url) {
    super(`${status} on ${url}`);
    this.status = status;      // ⭐ so callers can branch on 401 vs 422
    this.body = body;          // ⭐⭐ the PARSED problem detail, for field errors
    this.url = url;
  }
}

export async function api(path, { method = "GET", body, signal, ...rest } = {}) {
  let res;
  try {
    res = await fetch(`${BASE}${path}`, {
      method,
      signal,                                    // ⭐ Part 4
      credentials: "include",                    // ⭐⭐ cookies — Day 235
      headers: {
        ...(body ? { "Content-Type": "application/json" } : {}),
        ...rest.headers,
      },
      body: body ? JSON.stringify(body) : undefined,
    });
  } catch (cause) {
    if (cause.name === "AbortError") throw cause;          // ⭐ not an error
    throw new ApiError(0, null, path, { cause });          // ⭐⭐ network/CORS
  }

  if (res.status === 204) return null;                     // ⭐ no content

  const text = await res.text();                           // ⭐⭐ text FIRST
  let data = null;
  try { data = text ? JSON.parse(text) : null; } catch { data = { raw: text }; }
  //    ⭐ so an HTML 500 becomes {raw:"<html>..."} instead of a SyntaxError

  if (!res.ok) throw new ApiError(res.status, data, path); // ⭐⭐ THE LINE
  return data;
}
```

| ⭐ Decision | Why |
|---|---|
| **`res.text()` then `JSON.parse`** | ⭐⭐ An error page is not JSON. Parsing text you already hold lets you keep the body for the bug report instead of losing it to a parser exception. |
| **`status` on the error** | ⭐ Callers branch: 401 → re-auth, 422 → field errors, 429 → back off, 5xx → retry. Without it every failure is one undifferentiated blob. |
| **`body` on the error** | ⭐⭐ Your FastAPI 422 carries `loc` per field. That is what puts the message next to the right input (Day 229). |
| **`AbortError` re-thrown as-is** | ⭐ A cancelled request is **not a failure** and must never render an error. Part 4. |
| **`credentials: "include"`** | ⭐⭐ Cookies are **not** sent cross-origin by default. Day 235. |

```python
# ⭐ your FastAPI side — make the client's job possible
@app.exception_handler(RequestValidationError)
async def validation_handler(request, exc):
    return JSONResponse(
        status_code=422,
        content={"detail": [                     # ⭐⭐ field-addressable
            {"field": ".".join(str(p) for p in e["loc"][1:]), "message": e["msg"]}
            for e in exc.errors()
        ]},
    )
```

> ⭐⭐ **This is the Day 214 point arriving early.** You cannot render a good error state against an
> error shape that does not name the field. The client is where you discover that, and the fix is on
> the server.

# Part 3 — ⭐⭐ The four states

Every request has four outcomes. Most projects render one.

```
⭐⭐ LOADING · ERROR · EMPTY · SUCCESS

⭐   loading → ⭐ a skeleton, not a spinner that shifts the layout
⭐   error   → ⭐⭐ WHAT HAPPENED + WHAT THE USER CAN DO. A retry
⭐             button is the minimum. "Something went wrong" alone
⭐             is a shrug rendered as a component.
⭐   empty   → ⭐⭐ ZERO RESULTS IS NOT AN ERROR AND NOT A BLANK BOX.
⭐             It is the state most often missed, and the one
⭐             reviewers notice immediately.
⭐   success → the boring one everyone builds first
```

| ⭐ State | The mistake | The fix |
|---|---|---|
| Loading | A spinner that replaces content, so the page jumps | ⭐ Skeleton the same size as the content |
| Error | One message for every status | ⭐⭐ Branch on `status`. 401 ≠ 422 ≠ 503. |
| Empty | Renders as an error, or as nothing at all | ⭐ "No orders yet" + the action that creates one |
| Success | — | ⭐ Also handle *partially* successful (Day 216's `allSettled`) |

# Part 4 — Cancellation, and the race you will lose

```
⭐⭐ THE STALE RESPONSE RACE

⭐   user types "a"  → request A fires
⭐   user types "ab" → request B fires
⭐   ⭐ B RETURNS FIRST (faster path, smaller result)
⭐   ⭐ A RETURNS SECOND
⭐   ⇒ ⭐⭐ THE SCREEN NOW SHOWS RESULTS FOR "a" WHILE THE BOX
⭐     SAYS "ab". No error. No warning. Just wrong.
```

```javascript
const controller = new AbortController();
const data = await api("/search?q=ab", { signal: controller.signal });
controller.abort();                    // ⭐ cancels the in-flight request

// ⭐ timeout, for free
await api("/slow", { signal: AbortSignal.timeout(5000) });

// ⭐⭐ both: whichever fires first wins
await api("/slow", { signal: AbortSignal.any([controller.signal,
                                              AbortSignal.timeout(5000)]) });
```

> ⭐⭐ **Cancel the previous request whenever a new one supersedes it** — search-as-you-type, tab
> switches, a component that unmounted. This is the same *last-write-wins* problem you solved with
> fencing tokens on Day 411: **you cannot rely on responses arriving in the order you sent them.** On
> Day 228 the query library does this for you; you should be able to say what it is doing.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you handle API errors on the client?"**

Open with the trap, because it establishes you have actually shipped this. **`fetch` only rejects when
the request never happened — network, CORS, abort. A 500 is a successful fetch. So the tutorial
try/catch never runs for server errors, and then `res.json()` throws a syntax error because the 500
returned an HTML page, and you debug a JSON parser instead of reading a status code.**

Then the wrapper, framed as one decision. **Components never call `fetch`. There's one wrapper that
reads the body as text before parsing, so an HTML error page becomes data I can log instead of an
exception that loses it, and it throws a typed error carrying the status and the parsed body. Status
matters because 401, 422, 429 and 503 are four different user experiences.**

Then the bit that reveals backend judgement. **Building the client changed my server. My 422 was a
nested blob I couldn't attach to an input, so I flattened it to a field name and a message — you can't
render a good error state against an error shape that doesn't name the field.**

Close on the race. **Search-as-you-type sends overlapping requests and they don't return in order, so
the results for "a" can land after the results for "ab" and the screen is silently wrong. Cancel the
superseded request with an AbortController — it's the same problem as any last-write-wins ordering
issue, and an abort is not a failure, so it must never render as an error.**
