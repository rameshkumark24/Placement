# Day 348 🗝️

**P-348** · 🗝️ **Design 4 — a distributed key-value store** — ⭐⭐ LSM trees and vector clocks

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a distributed KV store is two independent designs stacked — a partitioning
> and replication scheme that decides how nodes agree, and a storage engine that decides how one node
> makes a durable write cheap — and the second one, the LSM tree, is the answer to "how can a write be
> faster than a disk seek", which is a memory append plus a sequential log.**

# Part 1 — ⭐ 0–8: scope, and stating the model

```
⭐⭐ FUNCTIONAL:
⭐   ① `get(key) -> value, version`
⭐   ② `put(key, value, version?)`
⭐   ③ `delete(key)`
⭐   ④ ⭐ TTL per key.
⭐   ⭐⭐ OUT: range scans (⭐ they change the partitioning
⭐     answer completely — hash partitioning kills them), ⭐
⭐     transactions, secondary indexes.
⭐   ⇒ ⭐⭐ SAY THE RANGE-SCAN EXCLUSION EXPLICITLY. It is the
⭐     single biggest scoping decision in this problem.

⭐⭐ NON-FUNCTIONAL — ⭐ and state the CAP position up front:
⭐   ⭐ 1 M ops/s. Values up to 1 MB, typical 1 KB.
⭐   ⭐ p99 < 10 ms. 100 TB total.
⭐   ⭐ ⭐⭐ ***AP WITH TUNABLE CONSISTENCY*** — always writable,
⭐     reads may be stale unless you pay for a quorum.
⭐   ⇒ ⭐⭐ THAT ONE SENTENCE DETERMINES HALF THE DESIGN, AND
⭐     SAYING IT AT MINUTE FIVE RATHER THAN MINUTE THIRTY IS
⭐     THE DIFFERENCE.

⭐⭐ ESTIMATE:
⭐   ⭐ 100 TB ÷ (a comfortable ~2 TB/node) × ***replication
⭐     factor 3*** = ⭐ ~150 nodes.
⭐   ⭐ 1 M ops/s ÷ 150 = ⭐ ~7k ops/s/node. ⭐⭐ ENTIRELY
⭐     ORDINARY — the problem is coordination, not throughput.
```

# Part 2 — ⭐⭐ Partitioning and replication

```
⭐⭐ PARTITIONING: ***CONSISTENT HASHING WITH VIRTUAL NODES***
⭐   (Day 326). ⭐ 150–256 vnodes per physical node.
⭐   ⇒ ⭐ Adding a node moves ~1/N of keys.
⭐   ⇒ ⭐⭐ AND A DEAD NODE'S SHARE SPREADS ACROSS ***ALL***
⭐     SURVIVORS RATHER THAN ONE NEIGHBOUR — ⭐ which is the
⭐     property that stops a single failure from cascading.

⭐⭐ REPLICATION: ⭐⭐ THE KEY'S ***N SUCCESSORS CLOCKWISE ON THE
⭐   RING***, skipping vnodes that map to a physical node
⭐   already holding it.
⭐   ⇒ ⭐⭐ THAT SKIP IS ESSENTIAL AND EASY TO MISS: WITHOUT IT,
⭐     THREE "REPLICAS" CAN LAND ON ONE MACHINE AND YOUR
⭐     REPLICATION FACTOR IS SECRETLY 1.
⭐   ⇒ ⭐ Rack/AZ awareness: spread the N replicas across
⭐     failure domains.

⭐⭐ QUORUMS (Day 328): N=3, and W and R chosen per operation.
⭐   ⭐ W+R > N ⇒ read and write sets intersect ⇒ a read sees
⭐     the latest completed write.
⭐   ⭐ W=1, R=1 ⇒ fastest, weakest. ⭐ W=3, R=1 ⇒ fast reads,
⭐     ⭐⭐ AND WRITES FAIL IF ***ANY*** REPLICA IS DOWN.
⭐   ⭐ ⭐⭐ W=2, R=2 IS THE DEFAULT: SURVIVES ONE NODE LOSS FOR
⭐     BOTH READS AND WRITES.
⭐   ⇒ ⭐⭐ AND THE CAVEAT TO STATE UNPROMPTED: ***W+R>N IS NOT
⭐     LINEARIZABILITY.*** ⭐ Concurrent writes, sloppy quorums
⭐     and hinted handoff all break it. ⭐ It gives a high
⭐     probability of freshness, not a guarantee.

⭐⭐ AVAILABILITY EXTRAS:
⭐   ⭐ ***SLOPPY QUORUM + HINTED HANDOFF*** — if a home replica
⭐     is down, write to the next healthy node with a hint, and
⭐     it forwards later.
⭐   ⇒ ⭐⭐ THIS IS WHAT MAKES IT "ALWAYS WRITABLE" — AND IT IS
⭐     EXACTLY WHAT BREAKS THE QUORUM GUARANTEE. ⭐ Naming both
⭐     halves in the same breath is the signal.
⭐   ⭐ ***READ REPAIR*** — on a read, if replicas disagree,
⭐     write the newest back.
⭐   ⭐ ***ANTI-ENTROPY*** — background ***Merkle tree***
⭐     comparison per key range, so nodes exchange hashes rather
⭐     than data and find divergence in O(log n) transfers.
```

# Part 3 — ⭐⭐ Conflict detection: version vectors, not timestamps

```
⭐⭐ THE PROBLEM: two clients write the same key concurrently
⭐   to different replicas. ⭐ Which wins?

⭐⭐ ❌ ***LAST WRITE WINS BY WALL CLOCK***
⭐   ⭐ Clock skew is 10–100 ms routinely (Day 343).
⭐   ⇒ ⭐⭐ THE "LAST" WRITE MAY BE THE EARLIER ONE, AND THE
⭐     LOSER IS SILENTLY DELETED. ⭐ It is a data-loss policy
⭐     with a reassuring name.
⭐   ⇒ ⭐ Cassandra defaults to this. ⭐⭐ IT IS A CHOICE, AND
⭐     KNOWING IT IS A CHOICE IS THE POINT.

⭐⭐ ✔ ***VERSION VECTORS*** — `{node_a: 3, node_b: 1}`
⭐   ⭐ Each coordinating replica increments its own counter.
⭐   ⭐ ⭐⭐ COMPARISON GIVES ***THREE*** OUTCOMES, NOT TWO:
⭐     ⭐ A dominates B (every entry ≥, one >) ⇒ A wins, safely.
⭐     ⭐ B dominates A ⇒ B wins.
⭐     ⭐ ⭐⭐ NEITHER DOMINATES ⇒ ***CONCURRENT***. ⭐ The system
⭐       cannot decide, and pretending otherwise is where data
⭐       loss comes from.
⭐   ⇒ ⭐⭐ THE HONEST DESIGN RETURNS ***BOTH SIBLINGS*** TO THE
⭐     CLIENT AND LETS THE APPLICATION MERGE. ⭐ Dynamo's
⭐     shopping cart merges by union — ⭐⭐ A RESURRECTED
⭐     DELETED ITEM BEATS A LOST ADD (Day 330).
⭐   ⭐ ✘ The cost: ⭐⭐ VECTORS GROW WITH THE NUMBER OF
⭐     COORDINATORS, SO YOU CAP THEM AND EVICT THE OLDEST
⭐     ENTRY — ⭐ which can produce false conflicts. ⭐ A real,
⭐     acknowledged limitation.

⭐⭐ AND THE DELETE PROBLEM PEOPLE FORGET:
⭐   ⭐ ⭐⭐ A DELETE MUST BE A ***TOMBSTONE***, NOT AN ABSENCE.
⭐   ⇒ ⭐ Otherwise a replica that was down comes back, finds
⭐     the key present locally and absent elsewhere, ⭐⭐ AND
⭐     ***RESURRECTS THE DELETED VALUE*** via read repair.
⭐   ⇒ ⭐ Tombstones must outlive the maximum node downtime
⭐     before compaction removes them (`gc_grace_seconds`),
⭐     ⭐⭐ AND A NODE OFFLINE LONGER THAN THAT MUST BE REBUILT
⭐     FROM SCRATCH, NOT REJOINED.
```

# Part 4 — ⭐⭐ The storage engine: LSM trees

```
⭐⭐ THE QUESTION: how does one node take 7,000 durable
⭐   writes/s when a random disk write is expensive?

⭐⭐ ❌ B-TREE (what Postgres does): update in place ⇒ ⭐ a
⭐   random write per update. ⭐ Excellent for reads and range
⭐   scans; ⭐ write-limited.

⭐⭐ ✔ ***LSM TREE*** — ⭐⭐ THE INSIGHT: NEVER UPDATE IN PLACE.
⭐   APPEND, AND SORT LATER.
⭐   ① ⭐ Write to a ***WAL*** (sequential append, fsync) —
⭐        ⭐⭐ THIS IS THE ONLY DURABILITY MECHANISM (Day 186,
⭐        Day 317's vending machine — third appearance).
⭐   ② ⭐ Write to the ***MEMTABLE*** (an in-memory sorted
⭐        structure — a skip list or a red-black tree).
⭐   ③ ⭐ Acknowledge. ⭐⭐ THE WRITE IS NOW ***A SEQUENTIAL
⭐        APPEND PLUS A MEMORY INSERT***, WHICH IS WHY IT IS
⭐        FAST.
⭐   ④ ⭐ When the memtable fills, flush it to disk as an
⭐        immutable, sorted ***SSTable***.
⭐   ⑤ ⭐ ***COMPACTION*** merges SSTables in the background,
⭐        dropping superseded values and expired tombstones.

⭐⭐ THE READ PATH, AND ITS COST:
⭐   ⭐ Memtable → SSTables newest to oldest.
⭐   ⇒ ⭐⭐ A READ MAY TOUCH ***MANY*** FILES — THIS IS ***READ
⭐     AMPLIFICATION***, AND IT IS THE PRICE OF THE FAST WRITE.
⭐   ⭐ Mitigations, all three:
⭐     ⭐ ⭐⭐ A ***BLOOM FILTER*** PER SSTABLE ⇒ "definitely not
⭐       here" in O(1), so most files are skipped without a disk
⭐       read. ⭐ False positives cost a wasted read; false
⭐       negatives are impossible, which is exactly the
⭐       asymmetry you need.
⭐     ⭐ A sparse index per SSTable ⇒ seek to the right block.
⭐     ⭐ Block cache.

⭐⭐ THE THREE AMPLIFICATIONS — ⭐⭐ AND THE SENTENCE THAT SHOWS
⭐   YOU UNDERSTAND STORAGE ENGINES:
⭐   ⭐ ***WRITE*** amplification — bytes written to disk per
⭐     byte of data (compaction rewrites).
⭐   ⭐ ***READ*** amplification — files touched per lookup.
⭐   ⭐ ***SPACE*** amplification — disk used per byte of live
⭐     data (superseded versions still present).
⭐   ⇒ ⭐⭐ ***YOU CAN OPTIMISE TWO. THE COMPACTION STRATEGY IS
⭐     THE CHOICE OF WHICH TWO.***
⭐     ⭐ ***LEVELLED*** ⇒ low read and space amplification,
⭐       ⭐⭐ HIGH WRITE AMPLIFICATION (10–30×). ⭐ Read-heavy.
⭐     ⭐ ***SIZE-TIERED*** ⇒ low write amplification,
⭐       ⭐⭐ HIGH SPACE AMPLIFICATION (can transiently need
⭐       2× the data size free). ⭐ Write-heavy.
```

# Part 5 — ⭐ Membership, failure detection and joining

```
⭐⭐ ***GOSSIP*** — each node periodically exchanges state with
⭐   a few random peers. ⭐ Membership, load and health converge
⭐   in O(log N) rounds without a coordinator.
⭐   ⇒ ⭐⭐ NO SINGLE POINT OF FAILURE, AND NO CONSENSUS NEEDED
⭐     FOR MEMBERSHIP ***IN AN AP SYSTEM*** — ⭐ which is
⭐     exactly why this design doesn't need Day 343's Raft.
⭐     ⭐ Say that connection; it shows the choices hang together.

⭐⭐ FAILURE DETECTION — ⭐ and the honest framing:
⭐   ⭐ ⭐⭐ YOU STILL CANNOT DISTINGUISH DEAD FROM SLOW. ⭐ A
⭐     ***φ-accrual*** detector outputs a suspicion ***level***
⭐     rather than a boolean, ⭐ so the caller chooses its own
⭐     threshold per operation.
⭐   ⇒ ⭐ In an AP system a wrong guess is cheap: you write to
⭐     the next node with a hint. ⭐⭐ IN A CP SYSTEM THE SAME
⭐     WRONG GUESS IS AN UNNECESSARY FAILOVER (Day 328) — ⭐ the
⭐     same uncertainty, two very different prices.

⭐⭐ JOINING A NODE — ⭐ the part nobody plans:
⭐   ⭐ Claim vnodes ⇒ stream the ranges from current owners ⇒
⭐     ⭐⭐ AND ***THROTTLE THE STREAMING***, or bootstrapping a
⭐     node saturates the network and degrades the cluster you
⭐     were trying to expand.
⭐   ⭐ ⭐⭐ THE NEW NODE MUST NOT SERVE READS UNTIL IT IS
⭐     COMPLETE, OR IT ANSWERS "NOT FOUND" AUTHORITATIVELY FOR
⭐     KEYS IT SIMPLY HASN'T RECEIVED YET.
```

# Part 6 — ⭐⭐ The failure modes that make this real

```
⭐⭐ ① ***THE HOT PARTITION.*** ⭐ One key with 40% of traffic.
⭐   ⇒ ⭐⭐ SHARDING CANNOT HELP — ONE KEY IS ONE PARTITION.
⭐   ⇒ ⭐ Client-side caching, ⭐ replicating that key more
⭐     widely, ⭐ or key-splitting in the application.

⭐⭐ ② ***THE LARGE PARTITION / WIDE ROW.*** ⭐ A key whose
⭐   value grows unboundedly.
⭐   ⇒ ⭐⭐ COMPACTION OF ONE ENORMOUS PARTITION CAN STALL A
⭐     NODE, AND IT CANNOT BE SPLIT ACROSS NODES. ⭐ This is a
⭐     data-modelling bug that presents as an operations
⭐     problem, ⭐ which is why it takes so long to diagnose.

⭐⭐ ③ ***TOMBSTONE ACCUMULATION.*** ⭐ Delete-heavy workloads
⭐   ⇒ reads scan thousands of tombstones to return nothing.
⭐   ⇒ ⭐⭐ THE CANONICAL SYMPTOM: "READS GOT SLOWER AFTER WE
⭐     CLEANED UP DATA." ⭐ Use TTLs rather than deletes where
⭐     possible.

⭐⭐ ④ ***COMPACTION FALLING BEHIND.*** ⭐ Write rate exceeds
⭐   compaction throughput ⇒ SSTable count climbs ⇒ ⭐⭐ READ
⭐   AMPLIFICATION CLIMBS ⇒ EVERYTHING GETS SLOWER, AND
⭐   ***COMPACTION COMPETES WITH THE WRITES FOR I/O***.
⭐   ⇒ ⭐⭐ A DOOM LOOP, AND THE ONLY REAL FIX IS TO SHED WRITE
⭐     LOAD. ⭐ Alert on SSTable count and pending compactions.

⭐⭐ ⑤ ***THE FULL-DISK CLIFF.*** ⭐ Size-tiered compaction can
⭐   transiently need free space equal to the data being merged.
⭐   ⇒ ⭐⭐ AT 80% FULL YOU MAY BE UNABLE TO COMPACT AT ALL,
⭐     WHICH MEANS YOU CANNOT RECOVER BY DELETING DATA.
⭐   ⇒ ⭐ Alert well before that, and know your strategy's
⭐     headroom requirement.
```

⭐   ***"Two stacked designs. On the cluster side: consistent
⭐      hashing with vnodes, N=3 replication across failure
⭐      domains, tunable W and R with W=2/R=2 as the default,
⭐      and sloppy quorum with hinted handoff to stay writable —

⭐      siblings rather than picking a winner by a wall clock

⭐      amplifications to optimise."***

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Last-write-wins by wall clock | Skew is 10–100 ms; the "last" write may be the earlier one, and the loser is deleted |
| ⭐⭐ Assuming W+R>N gives linearizability | Concurrent writes, sloppy quorums and hinted handoff all break it |
| ⭐⭐ Replicas on the same physical node | Skip vnodes that map to a node already holding it, or RF 3 is secretly RF 1 |
| ⭐⭐ Delete as absence rather than a tombstone | A returning node resurrects deleted values via read repair |
| ⭐ Rejoining a node offline past `gc_grace_seconds` | It reintroduces deleted data. Rebuild it instead |
| ⭐⭐ Ignoring read amplification | It's the price of the fast write. Bloom filters and compaction strategy pay it down |
| ⭐ Thinking compaction is free | It competes with writes for I/O, and falling behind is a doom loop |
| ⭐⭐ Running size-tiered compaction near a full disk | You may be unable to compact, so you can't recover by deleting |
| ⭐ Delete-heavy workloads | Reads scan tombstones. "Reads got slower after we cleaned up" is the symptom |
| ⭐ Unbounded partition size | Compaction of one huge partition stalls a node and can't be split |
| ⭐ Serving reads from a bootstrapping node | It answers "not found" authoritatively for keys it hasn't received |
| ⭐ Unthrottled streaming on join | Adding a node degrades the cluster you were expanding |

## Interview questions

**1. "How do you partition and replicate?"**
> ⭐ Consistent hashing with a couple of hundred virtual nodes per physical node, so adding one moves
> 1/N of keys ⭐⭐ **and a dead node's share spreads across every survivor rather than one neighbour.**
> ⭐ Replicas are the next N successors on the ring — ⭐⭐ **skipping vnodes that map to a node already
> holding the key, or three replicas can land on one machine and your replication factor is secretly
> one** — spread across failure domains.

**2. "What quorum settings and why?"**
> ⭐ N=3, W=2, R=2 as the default: W+R>N so read and write sets intersect, and it survives one node loss
> for both operations. ⭐ W=3/R=1 gives fast reads but writes fail if any replica is down. ⭐⭐ And I'd
> state the caveat unprompted: **this is not linearizability** — concurrent writes, sloppy quorums and
> hinted handoff all break it. It buys a high probability of freshness, not a guarantee.

**3. "Two clients write the same key concurrently. Who wins?"**
> ⭐⭐ Not "whoever has the later timestamp" — clock skew is tens of milliseconds, so **last-write-wins
> is a data-loss policy with a reassuring name.** ⭐ Version vectors give three outcomes, not two: A
> dominates, B dominates, or neither — and that third case is real concurrency. ⭐⭐ The honest design
> **returns both siblings and lets the application merge**, the way Dynamo's cart merges by union,
> because a resurrected item beats a lost add. ⭐ The cost is vectors growing with coordinator count, so
> they're capped, which can produce false conflicts.

**4. "Explain the LSM tree."**
> ⭐⭐ Never update in place — **append, and sort later.** ⭐ A write is a sequential WAL append plus an
> insert into an in-memory sorted memtable, then acknowledge; that's why it's fast. ⭐ When the memtable
> fills it flushes as an immutable sorted SSTable, and compaction merges them in the background. ⭐⭐ The
> price is read amplification — a lookup may touch many files — paid down with **a Bloom filter per
> SSTable, which gives "definitely not here" in constant time and can never produce a false negative**,
> plus a sparse index and a block cache.

**5. "Levelled or size-tiered compaction?"**
> ⭐⭐ It's a choice of which two amplifications to optimise, and **you can only have two.** ⭐ Levelled
> gives low read and space amplification with write amplification of ten to thirty times — right for
> read-heavy. ⭐ Size-tiered gives low write amplification with high space amplification, and can
> transiently need free space equal to the data being merged — ⭐⭐ **which is why a size-tiered cluster
> at eighty percent disk may be unable to compact at all, and therefore unable to recover by deleting
> data.**

**6. "Why does a delete make reads slower?"**
> ⭐ Because a delete is a tombstone, not an absence — it has to be, or a node that was down comes back
> and resurrects the value through read repair. ⭐⭐ So a delete-heavy workload leaves reads scanning
> thousands of tombstones to return nothing, and **"reads got slower after we cleaned up data" is the
> canonical symptom.** ⭐ Prefer TTLs to explicit deletes, ⭐ and know that tombstones must outlive your
> maximum node downtime — a node offline longer than `gc_grace_seconds` must be rebuilt rather than
> rejoined.

## 🎙️ Articulation drill

**Two minutes.** Frame it as two stacked designs, because that keeps the answer organised: **a cluster
design for how nodes agree, and a storage engine for how one node makes a write cheap.** On the cluster
side: consistent hashing with virtual nodes so a dead node's load spreads across everyone; replicas as
the next N successors **skipping any that land on a machine already holding the key, or replication
factor three is secretly one**; N=3, W=2, R=2 by default; and sloppy quorum with hinted handoff to stay
writable — **which is also exactly what breaks the quorum guarantee**, and saying both halves together
is the point. On conflicts, refuse the easy answer: **last-write-wins by wall clock is a data-loss
policy with a reassuring name**, because skew is tens of milliseconds — version vectors give three
outcomes, and the honest system returns both siblings for the third. On storage: **the LSM insight is
never update in place, append and sort later**, so a write is a sequential log append plus a memory
insert, and the price is read amplification, paid with a Bloom filter that can never give a false
negative. Close on the sentence that shows you understand storage engines: **write, read and space
amplification — you can optimise two, and the compaction strategy is the choice of which two** — and on
the operational payoff, which is being able to explain why reads got slower after a cleanup, and why a
cluster at eighty percent disk may be unable to recover by deleting data.
