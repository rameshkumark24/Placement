# Part 2 — ⭐⭐ The eviction policy that isn't

```
⭐⭐ ELASTICACHE'S DEFAULT `maxmemory-policy` IS ***volatile-lru***.
⭐   ⭐ Read that as: ⭐⭐ "EVICT THE LEAST-RECENTLY-USED KEY
⭐   ***THAT HAS A TTL***."

⭐ NOW THE FAILURE, AND IT IS ENTIRELY ORDINARY:
⭐ ① ⭐ Someone writes `redis.set("feature_flags", json)` with
⭐    no TTL. ⭐ Someone else stores a session with no TTL.
⭐    ⭐ A rate-limit counter. ⭐ A lock. ⭐⭐ NORMAL CODE.
⭐ ② ⭐ Memory fills to `maxmemory`.
⭐ ③ ⭐⭐ REDIS LOOKS FOR A TTL-BEARING KEY TO EVICT. ⭐ It finds
⭐    few, or none.
⭐ ④ ⭐⭐ EVERY WRITE NOW FAILS:
⭐    `OOM command not allowed when used memory > 'maxmemory'`
⭐ ⑤ ⭐⭐ AND ***READS KEEP WORKING PERFECTLY.***

⭐⭐ ⇒ SO THE CACHE SILENTLY BECOMES READ-ONLY. ⭐ Your hit rate
⭐   looks fine. ⭐ Your latency looks fine. ⭐⭐ AND EVERY CODE
⭐   PATH THAT ***WRITES*** TO REDIS — SESSIONS, LOCKS (DAY 343),
⭐   RATE LIMITERS (DAY 347), CACHE FILLS — THROWS. ⭐ Nothing in
⭐   the dashboard says "cache".

⭐⭐ THE POLICIES, AND HOW TO CHOOSE:
⭐   ⭐⭐ `allkeys-lru`  — ***THE RIGHT ANSWER FOR A CACHE.***
⭐     ⭐ Anything may be evicted. ⭐ A cache miss is by definition
⭐     survivable.
⭐   ⭐ `allkeys-lfu` — better when a small hot set dominates
⭐     (Day 326's hot key).
⭐   ⭐ `volatile-ttl` / `volatile-lru` — only if ***every***
⭐     evictable key has a TTL and you are certain.
⭐   ⭐⭐ `noeviction` — ***THE RIGHT ANSWER FOR A QUEUE OR A
⭐     SESSION STORE***, ⭐ where silently losing data is worse
⭐     than a loud failure. ⭐⭐ IT MAKES THE OOM EXPLICIT, WHICH
⭐     IS CORRECT WHEN THE DATA MATTERS.

⭐⭐ ⇒ AND HERE IS THE REAL LESSON, WHICH IS AN ARCHITECTURE
⭐   POINT AND NOT A SETTING: ***THE CORRECT POLICY DEPENDS ON
⭐   WHETHER REDIS IS A CACHE OR A DATABASE — AND MOST TEAMS HAVE
⭐   BOTH IN ONE CLUSTER, WHICH IS WHY NO SINGLE SETTING IS
⭐   RIGHT.***
⭐   ⭐⭐ THE FIX IS TWO CLUSTERS: ⭐ a disposable one with
⭐   `allkeys-lru` for caching, ⭐ and a small, monitored one with
⭐   `noeviction` for sessions, locks and counters.
⭐   ⭐ It costs $15/month. ⭐⭐ IT REMOVES AN ENTIRE FAILURE
⭐   CATEGORY, AND IT IS THE ANSWER THAT SHOWS YOU HAVE THOUGHT
⭐   ABOUT IT RATHER THAN MEMORISED A FLAG.

⭐ ⭐ Alarm on `Evictions` (a rising count means you are too
⭐   small) ⭐⭐ AND ON `DatabaseMemoryUsagePercentage` ABOVE 75%.
```

# Part 3 — Cluster mode, and what it does to your Python

```
⭐ CLUSTER MODE ***DISABLED*** — ⭐ one shard: a primary plus up
⭐   to 5 replicas. ⭐ One primary endpoint, one reader endpoint.
⭐   ⭐⭐ SCALES ***VERTICALLY ONLY***. ⭐ Simple, and correct for
⭐   most workloads: ⭐ a cache.r6g.xlarge holds 26 GB.

⭐ CLUSTER MODE ***ENABLED*** — ⭐ 16,384 hash slots spread over
⭐   N shards, each with replicas. ⭐ Horizontal, resharding
⭐   online. ⭐⭐ THIS IS DAY 326's CONSISTENT HASHING, SHIPPED.

⭐⭐ AND THE CONSEQUENCE THAT BREAKS PYTHON CODE:
⭐   ⭐⭐ ***A MULTI-KEY COMMAND ONLY WORKS IF EVERY KEY IS IN THE
⭐   SAME SLOT.***
⭐   ⭐ `MGET user:1 user:2` → ⭐⭐ CROSSSLOT KEYS IN REQUEST DON'T
⭐     HASH TO THE SAME SLOT
⭐   ⭐ Same for `MSET`, multi-key `DEL`, transactions, ⭐ and any
⭐     Lua script touching several keys ⭐⭐ — WHICH INCLUDES YOUR
⭐     RATE LIMITER AND YOUR LOCK SCRIPT.

⭐   ⭐⭐ THE FIX IS ***HASH TAGS***: ⭐ only the part inside `{}`
⭐     is hashed.
⭐     `{user:123}:profile` and `{user:123}:prefs`
⭐     ⭐⭐ ⇒ SAME SLOT, SO MULTI-KEY WORKS ***AND*** THE TWO KEYS
⭐     MOVE TOGETHER DURING A RESHARD.
⭐   ⭐⭐ AND THE COUNTER-TRAP: OVER-TAGGING RECREATES A HOT SLOT.
⭐     ⭐ `{tenant:acme}:*` puts one large tenant's entire working
⭐     set on one shard — ⭐⭐ DAY 326's HOT KEY, REINVENTED BY
⭐     SOMEONE TRYING TO FIX CROSSSLOT.

⭐ ⭐⭐ ⇒ HONEST DEFAULT: ***START WITH CLUSTER MODE DISABLED.***
⭐   ⭐ Go to cluster mode when one node cannot hold the data or
⭐   serve the throughput, ⭐⭐ NOT BECAUSE IT SOUNDS MORE SERIOUS.
⭐   ⭐ You will change client code either way, so decide once.
```

# Part 4 — Failover, and redis-py's default silence

```
⭐ THE PRIMARY ENDPOINT IS A CNAME. ⭐ Failover repoints it,
⭐   ⭐ ~15–30 s for ElastiCache.
⭐⭐ AND IT IS DAY 387's PROBLEM AGAIN, WITH A DIFFERENT ERROR:
⭐   ⭐ Your pooled connection points at the old primary, which
⭐     is now a ***replica***.
⭐   ⭐⭐ `redis.exceptions.ReadOnlyError:
⭐     READONLY You can't write against a read only replica.`
⭐   ⭐⭐ READS SUCCEED. WRITES FAIL. NOTHING RECONNECTS.
```

```python
# ⭐⭐ THE CONFIG THAT SURVIVES A FAILOVER. All five lines earn
# ⭐   their place.
from redis import Redis
from redis.backoff import ExponentialBackoff
from redis.retry import Retry
from redis.exceptions import ReadOnlyError, ConnectionError, TimeoutError

r = Redis(
    host=PRIMARY_ENDPOINT, port=6379, ssl=True,
    socket_connect_timeout=2,       # ⭐ never hang on a firewall
    socket_timeout=2,               # ⭐⭐ DAY 384: BOUND EVERY WAIT
    health_check_interval=30,       # ⭐⭐ PINGS IDLE POOLED CONNS
    retry=Retry(ExponentialBackoff(cap=1.0, base=0.05), retries=3),
    retry_on_error=[ReadOnlyError,  # ⭐⭐ THE ONE PEOPLE OMIT —
                    ConnectionError, TimeoutError],
    decode_responses=False,         # ⭐ decode where you know the type
)
# ⭐⭐ WITHOUT `ReadOnlyError` IN retry_on_error, A FAILOVER IS AN
# ⭐   OUTAGE THAT LASTS UNTIL A DEPLOY. ⭐ With it, redis-py drops
# ⭐   the connection, re-resolves, and the blip is seconds.
```

```
⭐ ⭐ Use the ***reader endpoint*** for reads only if you can
⭐   tolerate replica lag — ⭐⭐ AND A CACHE READ FROM A LAGGING
⭐   REPLICA CAN RETURN A VALUE YOU JUST INVALIDATED, ⭐ which is
⭐   a stale-cache bug that only appears under load.
⭐ ⭐ For cluster mode use `RedisCluster`, ⭐⭐ WHICH DISCOVERS
⭐   TOPOLOGY AND FOLLOWS `MOVED` REDIRECTS FOR YOU.
```

# Part 5 — Four ways to hurt yourself, all Redis-specific

```
⭐ ① ⭐⭐ ***`KEYS *` IN PRODUCTION.*** ⭐ Redis is single-
⭐    threaded. ⭐ `KEYS` is O(N) and blocks ***everything*** —
⭐    ⭐⭐ ON A 10-MILLION-KEY NODE THAT IS SECONDS OF TOTAL
⭐    STALL, AND EVERY SERVICE THAT TOUCHES THE CACHE TIMES OUT
⭐    AT ONCE. ⭐ Use `SCAN` with a cursor. ⭐⭐ SAME FOR `FLUSHALL`,
⭐    `SMEMBERS` ON A BIG SET, AND `LRANGE 0 -1`.

⭐ ② ⭐⭐ ***BIG KEYS.*** ⭐ A 200 MB list or a hash with a million
⭐    fields. ⭐ Every operation on it is O(N) on a single thread;
⭐    ⭐⭐ DELETING IT BLOCKS TOO (USE `UNLINK`); ⭐ and in cluster
⭐    mode ⭐⭐ IT CANNOT BE SPLIT ACROSS SHARDS, SO IT PINS AN
⭐    ENTIRE SHARD'S SIZE TO ONE VALUE. ⭐ Find them:
⭐    `redis-cli --bigkeys`.

⭐ ③ ⭐⭐ ***`reserved-memory-percent`.*** ⭐ A snapshot forks the
⭐    process, and copy-on-write means the fork can need
⭐    substantial extra memory while pages are dirtied.
⭐    ⭐⭐ IF YOU HAVE NOT RESERVED ~25%, THE BACKUP CAN OOM THE
⭐    NODE — ⭐ so the mechanism that protects your data is the
⭐    thing that kills it. ⭐ ElastiCache defaults are reasonable
⭐    now; ⭐⭐ CHECK YOURS RATHER THAN ASSUMING.

⭐ ④ ⭐ ***CROSS-AZ CHARGES.*** ⭐ Replication traffic between AZs
⭐    is billed (Day 380), ⭐ and so is every client read that
⭐    crosses an AZ. ⭐⭐ AT HIGH THROUGHPUT THIS IS A REAL LINE ON
⭐    THE BILL, AND IT IS INVISIBLE UNTIL YOU LOOK.
```

# Part 6 — When ElastiCache is the wrong home for the data

```
⭐⭐ ***REDIS ON ELASTICACHE IS NOT A DATABASE, AND THE
⭐   PERSISTENCE OPTIONS DO NOT MAKE IT ONE.***
⭐   ⭐ Snapshots are point-in-time. ⭐ AOF is unavailable on many
⭐     node types and discouraged.
⭐   ⭐⭐ A FAILOVER PROMOTES A REPLICA THAT WAS ***ASYNCHRONOUSLY***
⭐     REPLICATED — ⭐ so the last seconds of writes can simply
⭐     not exist. ⭐⭐ THERE IS NO ERROR. THE DATA WAS
⭐     ACKNOWLEDGED AND THEN WAS NOT THERE.

⭐⭐ ⇒ SO APPLY DAY 359's SHAPE ④ — ***EPHEMERAL VS DURABLE*** —
⭐   AND ASK ONE QUESTION OF EVERY KEY:
⭐   ⭐⭐ ***IF THIS VANISHED RIGHT NOW, WHAT BREAKS?***
⭐   ⭐ "A slow page" → cache. ⭐ Correct home.
⭐   ⭐ "Users are logged out" → annoying, ⭐ usually acceptable,
⭐     ⭐⭐ SAY IT OUT LOUD AND DECIDE.
⭐   ⭐⭐ "WE LOSE ORDERS" / "WE DOUBLE-CHARGE" → ***IT IS NOT
⭐     CACHE DATA AND IT DOES NOT LIVE HERE.*** ⭐ Postgres, or a
⭐     queue with durability (Day 393).
⭐   ⭐ "Two workers run the same job" → ⭐⭐ THE LOCK NEEDS A
⭐     FENCING TOKEN, BECAUSE THE LOCK ITSELF CAN VANISH
⭐     (DAY 343). ⭐ Redis locks are an optimisation, ⭐⭐ NEVER A
⭐     CORRECTNESS GUARANTEE.
```

# Part 7 — Python that uses it well

```python
# ⭐⭐ ① PIPELINE. THE ROUND TRIP IS THE COST, NOT THE COMMAND.
#    1,000 sequential GETs at 0.5 ms RTT = ⭐⭐ 500 ms
#    1,000 in one pipeline               = ⭐⭐ ~2 ms
with r.pipeline(transaction=False) as p:
    for k in keys: p.get(k)
    values = p.execute()

# ⭐ ② SCAN, never KEYS.
for key in r.scan_iter(match="sess:*", count=500):
    ...

# ⭐⭐ ③ SET WITH A TTL, ALWAYS. Make it impossible to forget:
def cache_set(key, value, ttl=300):
    assert ttl and ttl > 0, "no TTL-less writes to the cache"
    r.set(key, value, ex=ttl)
# ⭐⭐ A THREE-LINE WRAPPER THAT PREVENTS PART 2 ENTIRELY.

# ⭐ ④ Pool sized to your actual concurrency (Day 386's lesson
# ⭐   again): default max_connections is 2**31 — effectively
# ⭐   unbounded — ⭐⭐ SO A THREAD LEAK BECOMES A CONNECTION LEAK
# ⭐   AND YOU HIT THE NODE'S 65,000 LIMIT.
# ⭐   Set it explicitly to workers × threads.

# ⭐ ⑤ Jittered TTLs — ⭐⭐ DAY 326's AVALANCHE: 10,000 KEYS
# ⭐   WRITTEN IN ONE WARM-UP ALL EXPIRE IN THE SAME SECOND.
ttl = 300 + random.randint(0, 60)
```

# 💬 Interview

**1. ⭐⭐ "Your Redis-backed writes started failing but reads are fine. What happened?"**
> ⭐ That's the eviction-policy default. ⭐⭐ **ElastiCache defaults `maxmemory-policy` to
> `volatile-lru`, which only evicts keys that have a TTL — so once memory fills and there aren't
> enough TTL-bearing keys, Redis returns OOM on every write while continuing to serve reads
> perfectly.** ⭐ The cache silently becomes read-only, hit rate and latency both look healthy, ⭐⭐ **and
> everything that writes — sessions, locks, rate limiters, cache fills — throws, with nothing on the
> dashboard pointing at the cache.** ⭐ For a pure cache the policy should be `allkeys-lru`, because a
> miss is by definition survivable. ⭐ But the real answer is architectural: ⭐⭐ **the right policy
> depends on whether Redis is a cache or a datastore, and most teams have both in one cluster — so I'd
> split them, `allkeys-lru` for the disposable one and `noeviction` for sessions and locks.** ⭐ Fifteen
> dollars a month to delete a failure category.

**2. "Cluster mode enabled or disabled?"**
> ⭐ Disabled by default. ⭐ One shard with replicas scales vertically and a single r6g.xlarge holds 26
> gigabytes, which is more than most workloads need. ⭐⭐ **I'd move to cluster mode when one node can't
> hold the data or serve the throughput, not because it sounds more serious — because it changes my
> client code.** ⭐ Multi-key commands only work when all keys hash to the same slot, ⭐⭐ **so `MGET`
> across arbitrary keys fails with CROSSSLOT, and so does any Lua script touching several keys — which
> includes the rate limiter and the lock.** ⭐ Hash tags fix it by making only the braced part hash,
> ⭐⭐ **and the counter-trap is over-tagging: `{tenant:acme}` puts one big tenant's whole working set
> on one shard, which is a hot key reinvented by someone fixing CROSSSLOT.**

**3. ⭐⭐ "Why is Redis latency spiking for every service at once?"**
> ⭐ Redis is single-threaded, so a single O(N) command blocks all clients. ⭐⭐ **`KEYS *` on a
> ten-million-key node is seconds of total stall — every service that touches the cache times out
> simultaneously, which looks like a network event and isn't.** ⭐ Same for `SMEMBERS` on a large set,
> `LRANGE 0 -1`, and deleting a big key, which is why `UNLINK` exists. ⭐ I'd look for big keys with
> `--bigkeys`, replace `KEYS` with `SCAN`, ⭐⭐ **and check `reserved-memory-percent`, because a
> snapshot forks the process and copy-on-write can OOM the node — the mechanism protecting the data
> being the thing that kills it.**

**4. "Can you store sessions in ElastiCache?"**
> ⭐ Yes, if you've decided what losing them costs. ⭐⭐ **Replication is asynchronous, so a failover
> promotes a replica that may be missing the last seconds of writes — with no error; the write was
> acknowledged and then wasn't there.** ⭐ For sessions that usually means some users get logged out,
> which is normally fine as long as it's a stated decision. ⭐⭐ **What must never live there is anything
> where the answer to "if this vanished now, what breaks?" is "we lose orders" or "we double-charge".**
> ⭐ And Redis locks are an optimisation, never a correctness guarantee — ⭐⭐ **if correctness depends on
> the lock, it needs a fencing token, because the lock itself can disappear.**

**5. "How do you make 1,000 cache reads fast?"**
> ⭐⭐ **Pipeline them — the round trip is the cost, not the command.** ⭐ A thousand sequential GETs at
> half a millisecond of RTT is 500 milliseconds; the same thousand in one pipeline is about two.
> ⭐ I'd also set the connection pool explicitly, ⭐⭐ **because redis-py's default `max_connections` is
> effectively unbounded, so a thread leak becomes a connection leak until you hit the node's limit** —
> and jitter my TTLs, or ten thousand keys written during one warm-up all expire in the same second
> and stampede the database.

**6. "What breaks during an ElastiCache failover?"**
> ⭐ The same thing as RDS, with a different exception. ⭐⭐ **The primary endpoint repoints, but the
> pooled connection is to the old primary which is now a replica, so writes fail with
> `ReadOnlyError` while reads succeed and nothing reconnects.** ⭐ redis-py won't retry that by
> default — ⭐⭐ **`ReadOnlyError` has to be in `retry_on_error` explicitly, and without it a
> fifteen-second failover is an outage lasting until someone deploys.** ⭐ With it, plus
> `health_check_interval` and bounded socket timeouts, the blip is seconds.
