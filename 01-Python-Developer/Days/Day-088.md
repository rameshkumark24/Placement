# Day 088

**L-088** · Remotes, workflows, and ⭐⭐ **PR discipline** — why a 900-line pull request gets a worse review than a 90-line one

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a remote is just another set of refs, `origin/main` is a cache that only
> `fetch` updates, and everything people find confusing about pushing and pulling comes from
> forgetting that the cache can be stale.**
>
> ⭐ The second half of today is not a Git feature at all. **It is the working agreement that decides
> whether a team ships**, and it is asked about in every interview above junior level.

---

# Part 1 — ⭐⭐ Remotes are refs

```
⭐⭐ THREE THINGS THAT ALL LOOK LIKE "MAIN" AND ARE NOT THE SAME:
⭐
⭐   main                ⭐ YOUR branch. A local ref. You move it by committing.
⭐   origin/main         ⭐⭐ A REMOTE-TRACKING REF — a LOCAL CACHE of where main
⭐                          was on the server ⭐⭐ THE LAST TIME YOU FETCHED.
⭐                          ⭐ You can never move it by committing.
⭐   the real main        ⭐ on the server. You cannot see it without asking.
⭐
⭐ ⇒ ⭐⭐ "Your branch is behind 'origin/main' by 3 commits" IS A STATEMENT ABOUT
⭐     YOUR CACHE. ⭐ If you have not fetched today, it is stale — which is why
⭐     `git fetch` first is the answer to half of all "git is confusing" moments.
```

```bash
git fetch origin            # ⭐⭐ UPDATE THE CACHE. Touches nothing of yours. Always safe.
git fetch --prune           # ⭐ also delete refs for branches deleted on the server
git status                  # ⭐ now the ahead/behind numbers mean something

git pull                    # ⭐⭐ = fetch + merge   (⚠️ two operations in one word)
git pull --rebase           # ⭐⭐ = fetch + rebase  (Day 086 — set pull.rebase true)

git push -u origin feature  # ⭐ push and set the upstream, first time
git push                    # ⭐ thereafter
git remote -v               # ⭐ where am I actually pushing
```

⭐⭐ **`git fetch` is the safest command in Git and the most under-used.** It cannot touch your working
tree, your index or your branches. ⭐ **Fetch freely, then look before you decide** — `git log
main..origin/main` shows exactly what arrived, and `git log origin/main..main` shows what you have
that they do not.

```
⭐⭐ --force vs --force-with-lease — AND THE DERIVATION MATTERS:
⭐   git push --force              ⇒ ⭐⭐ "make the remote look like me, whatever
⭐                                     is there" ⇒ ⚠️ silently DELETES a colleague's
⭐                                     commit if they pushed while you were rebasing.
⭐   git push --force-with-lease   ⇒ ⭐⭐ "overwrite ONLY IF the remote is still at
⭐                                     the commit I last fetched" ⇒ ⭐ if someone
⭐                                     pushed in between, IT REFUSES.
⭐   ⇒ ⭐⭐ IT IS COMPARE-AND-SWAP (Day 067). Exactly the same idea as an atomic
⭐        check-then-set, applied to a ref. ⭐ Use it always; alias `--force` away.
⭐   ⚠️ ⭐ CAVEAT: some tools fetch in the background, which refreshes your "lease"
⭐        and weakens the guarantee. Still far better than `--force`.
```

# Part 2 — ⭐ Two workflows, honestly compared

```
⭐⭐ TRUNK-BASED — one long-lived branch (main), short branches off it.
⭐   · ⭐ branches live HOURS TO DAYS, never weeks
⭐   · ⭐⭐ main is ALWAYS DEPLOYABLE; CI runs on every push
⭐   · ⭐⭐ unfinished work ships DISABLED, behind a FEATURE FLAG
⭐   ⇒ ⭐ suits: web services, continuous deployment, small-to-large teams
⭐
⭐ GIT-FLOW — main + develop + feature/* + release/* + hotfix/*
⭐   · ⭐ release branches allow stabilising v2.3 while v2.4 develops
⭐   ⇒ ⭐ suits: SHIPPED, VERSIONED software with supported old releases
⭐   ⇒ ⚠️ ⭐⭐ overkill for a web service that deploys ten times a day — you get
⭐        five branch types and permanent merge overhead to solve a problem
⭐        ("customers on old versions") that you do not have.
```

```
⭐⭐ THE ARGUMENT FOR SHORT BRANCHES IS ARITHMETIC, NOT TASTE:
⭐   merge pain grows with (your changes) × (their changes) — ⭐⭐ roughly the
⭐   PRODUCT, not the sum, because conflicts arise where both sides touched
⭐   the same region.
⭐   ⇒ ⭐ 1 day of divergence  ⇒ trivial
⭐   ⇒ ⭐⭐ 3 weeks            ⇒ a day of conflict resolution, done tired, on code
⭐        you have half forgotten — ⭐⭐ and every conflict resolution is an
⭐        UNREVIEWED CODE CHANGE (Day 087).
⭐   ⇒ ⭐⭐ THEREFORE: merge main INTO your branch daily, and keep branches short.
⭐        "Integration is expensive" is why you should do it MORE OFTEN, not less.
```

⭐ **Feature flags are what make trunk-based possible** — they decouple *deploying* code from
*releasing* behaviour, so half-finished work can live on main safely. ⭐⭐ **And they carry their own
cost:** every flag is a branch in the code and a combination to test, so flags need an owner and a
removal date or they become permanent complexity.

# Part 3 — ⭐⭐ Pull requests that get a real review

```
⭐⭐ THE FINDING THAT SHOULD CHANGE YOUR BEHAVIOUR: REVIEW QUALITY COLLAPSES
⭐   WITH SIZE. Beyond roughly 400 lines, defect detection per line falls sharply,
⭐   and past ~1000 lines review becomes performative — ⭐ "LGTM" is what a
⭐   reviewer says when the diff has defeated them.
⭐
⭐   ⇒ ⭐⭐ SO A 900-LINE PR IS NOT "MORE WORK REVIEWED". IT IS LESS WORK REVIEWED,
⭐        with a rubber stamp on top. ⭐ Two 200-line PRs get more real scrutiny
⭐        than one 400-line PR.
⭐   ⇒ ⭐⭐ AND THE CONSEQUENCE FOR YOU: splitting a PR is not politeness, it is
⭐        the only way to actually get your code checked.
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐⭐ **One concern per PR** | ⭐⭐ Mixing a refactor with a fix means neither is reviewed properly |
| ⭐ Under ~400 lines | ⭐ Past that, review quality falls off a cliff |
| ⭐⭐ **Self-review first** | ⭐⭐ Read your own diff on the platform — you will find something, every time |
| Description says **why** | ⭐ The diff says what (Day 085, again) |
| ⭐ Green CI before requesting | ⭐ A human's time is the scarce resource |
| Draft PR for early feedback | ⭐ "Is this the right shape?" costs minutes; the wrong shape costs days |
| ⭐ Refactor **separately** | ⭐⭐ A formatting pass mixed into a fix hides the fix in 300 lines of noise |

```
⭐⭐ A PR DESCRIPTION THAT EARNS A GOOD REVIEW:
⭐   WHAT   one sentence.
⭐   ⭐⭐ WHY  the problem, and what happens if we do nothing.
⭐   HOW    only the non-obvious decisions — ⭐ and the alternative you rejected.
⭐   RISK   ⭐⭐ what could break, and how you would notice. ⭐ Migrations, feature
⭐          flags, and anything not covered by tests belong here.
⭐   TEST   how you verified it, beyond "CI is green".
⭐   ⇒ ⭐⭐ THE RISK SECTION IS THE ONE THAT MARKS OUT A SENIOR ENGINEER, because
⭐        it is the only one that requires you to think about the system rather
⭐        than the change.
```

⭐ **Stacked PRs** — a chain where each builds on the last — let you keep every PR small when a change
is genuinely big. ⭐⭐ **The cheaper version of the same idea:** land the refactor first as its own PR,
then the behaviour change on top. **Two reviewable diffs instead of one unreviewable one.**

# Part 4 — ⭐ Merging on the platform, and protection

| Strategy | ⭐ History | ⭐⭐ Note |
|---|---|---|
| **Merge commit** | ⭐ true, branchy | ⭐ preserves every commit — including "wip" |
| ⭐⭐ **Squash merge** | ⭐⭐ one commit per PR, linear | ⭐⭐ **clean and bisect-friendly** — ⚠️ loses granularity inside the PR |
| Rebase merge | linear, all commits | ⚠️ every commit is rewritten; ⭐ needs them all to be good |

```
⭐⭐ THE RECOMMENDATION, AND THE REASONING:
⭐   SQUASH MERGE for most teams. ⭐ main becomes one commit per PR — each atomic,
⭐   each with a real message (the PR title), each individually revertable, and
⭐   ⭐⭐ each one a valid bisect step (Day 087). ⭐ You lose the internal commits,
⭐   which for a branch of "wip / fix / oops" is not a loss at all.
⭐   ⇒ ⭐⭐ BUT: if your team writes genuinely good atomic commits (Day 085) and
⭐        cleans up with rebase -i (Day 086), a rebase or merge strategy preserves
⭐        real information and squashing throws it away. ⭐ The right answer depends
⭐        on the commit hygiene you actually have — say that, rather than picking
⭐        a side.
```

```
⭐ BRANCH PROTECTION — the settings worth arguing for on main:
⭐   · ⭐⭐ require a PR (no direct pushes)
⭐   · ⭐⭐ require status checks to pass (⭐ tests, lint, types — Day 099)
⭐   · require at least one approval · ⭐ dismiss stale approvals on new commits
⭐   · ⭐ require the branch to be up to date before merging
⭐   · ⭐⭐ FORBID FORCE-PUSH AND DELETION ⇒ ⭐ this is what makes Day 086's golden
⭐        rule an enforced property rather than a hope
⭐   · CODEOWNERS ⇒ ⭐ the right reviewer is requested automatically
```

⭐ **The fork workflow** (open source, or an external contractor): clone your fork, add the original as
a second remote — `git remote add upstream <url>` — and sync with `git fetch upstream && git rebase
upstream/main`. ⭐⭐ **`origin` is yours, `upstream` is theirs**; PRs go from your fork's branch to
their `main`.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Trusting ahead/behind without fetching | ⭐⭐ `origin/main` is a **cache**. `git fetch` first. |
| ⭐⭐ **`git push --force`** | ⭐⭐ Use `--force-with-lease` — it is compare-and-swap on a ref. |
| ⭐ Three-week feature branches | ⭐⭐ Conflict pain grows with the **product** of both sides' changes. |
| Git-flow on a web service | ⭐ Five branch types to solve a problem you do not have. |
| ⭐⭐ **A 900-line PR** | ⭐⭐ Gets a *worse* review than 90 lines. Split it. |
| Refactor mixed with a fix | ⭐ The fix disappears into the noise. |
| ⭐ Requesting review on red CI | ⭐ Spends the reviewer's time on what a machine catches. |
| A description that restates the diff | ⭐⭐ Say **why**, and what could break. |
| ⭐ No risk section | ⭐ The section that separates senior from competent. |
| Squash-merging genuinely good commits | ⭐ Then you are discarding real information. |
| `main` unprotected | ⭐⭐ Force-push protection is what enforces the golden rule. |

## Interview questions

**Q: What is `origin/main`?**
> A remote-tracking ref — a local cache of where `main` was on the server the last time you fetched.
> It isn't the server, and you can't move it by committing. That's why "your branch is behind by 3" is
> a statement about your cache and not about reality: if you haven't fetched today, the number is
> stale. Fetching is the safest command in Git — it can't touch your branches, index or working tree —
> so I fetch freely and then look at `git log main..origin/main` to see exactly what arrived before
> deciding anything.

**Q: Why `--force-with-lease` rather than `--force`?**
> `--force` says "make the remote look like me regardless of what's there", so if a colleague pushed
> while I was rebasing, their commit is silently deleted. `--force-with-lease` says "overwrite only if
> the remote is still where I last saw it", so it refuses when someone else has pushed in between.
> It's compare-and-swap applied to a ref — the same idea as an atomic check-then-set. The caveat is
> that a tool fetching in the background can refresh the lease and weaken the guarantee, but it's
> still strictly better than `--force`.

**Q: Trunk-based or git-flow?**
> Trunk-based for a web service that deploys continuously: short branches, main always deployable, and
> unfinished work shipped disabled behind a feature flag. Git-flow earns its complexity when you ship
> versioned software and support old releases, because release branches let you stabilise 2.3 while
> 2.4 develops. On a service deploying ten times a day it's five branch types and permanent merge
> overhead solving a problem you don't have. The underlying reason I prefer short branches is
> arithmetic: conflict pain grows roughly with the product of both sides' changes, so three weeks of
> divergence is a day of conflict resolution done tired — and every conflict resolution is an
> unreviewed code change.

**Q: What makes a good pull request?**
> Small and single-purpose, because review quality collapses with size — past a few hundred lines,
> defects found per line drops sharply, and "LGTM" is what a reviewer says when the diff has defeated
> them. So a 900-line PR isn't more work reviewed, it's less work reviewed with a rubber stamp. Beyond
> size: self-review on the platform first, green CI before asking a human, and a description that says
> why rather than what, including what could break and how we'd notice. If the change is genuinely
> big, I'd land the refactor as its own PR and the behaviour change on top — two reviewable diffs
> instead of one unreviewable one.

**Q: Squash, merge or rebase on the platform?**
> It depends on the commit hygiene the team actually has. Squash gives you one commit per PR on main —
> atomic, individually revertable, and a valid bisect step — and if the branch was "wip, fix, oops"
> you've lost nothing. But if people genuinely write atomic commits and clean up with an interactive
> rebase before pushing, squashing throws away real information, and a merge or rebase strategy
> preserves it. I'd default to squash for most teams and say so with that reasoning rather than
> claiming one is correct.

## Mini task

1. ⭐⭐ `git fetch` then `git log main..origin/main` and `git log origin/main..main`. **Say what each
   list is.**
2. ⭐ Delete a branch on the server and run `git fetch --prune`. Watch the stale ref disappear.
3. ⭐⭐ **In two clones of a scratch repo:** push from clone B, then rebase and `--force-with-lease`
   from clone A. **Watch it refuse.** Then fetch and try again.
4. ⭐ Do the same with `--force` and confirm clone B's commit is gone. **Then recover it from clone
   B's reflog** (Day 087).
5. ⭐⭐ Take a PR you have open (or a large past commit) and **split it into two logical PRs.** Note
   how much clearer each is.
6. ⭐⭐ Write a full PR description with the five sections — **especially the risk section.**
7. ⭐ Self-review your own diff on the platform before requesting review. **Write down what you found.**
8. ⭐ Enable branch protection on a personal repo: require a PR, require checks, forbid force-push.
   **Then try to push to main directly.**
9. ⭐⭐ Fork a public repo, add `upstream`, and sync your fork with `git fetch upstream && git rebase
   upstream/main`.
10. ⭐ Add a `CODEOWNERS` file and open a PR touching that path.
11. ⭐⭐ Merge the same branch three ways in scratch repos — merge commit, squash, rebase — and compare
    `git log --graph --oneline` for each.

## 🎙️ Articulation drill

Record two minutes: **"How does your team work with Git?"** — an open question that is really asking
whether you have shipped with other people.

⭐ **Give a policy with reasons, not a list of commands:** **"trunk-based. Short branches off main,
hours to days rather than weeks, main always deployable, CI on every push, and anything unfinished
ships disabled behind a flag."**

⭐⭐ **Justify the short branches with the arithmetic, because that is the part people cannot fake:**
*"the reason isn't taste — conflict pain grows roughly with the product of my changes and theirs, so
three weeks of divergence is a day of conflict resolution done tired on code I've half forgotten. And
every conflict resolution is a code change nobody reviewed, which is the part that actually worries me.
So I merge main into my branch daily. 'Integration is expensive' is an argument for doing it more
often, not less."*

⭐⭐ **Then PRs, and lead with the finding rather than the etiquette:** *"I keep pull requests small,
and not out of politeness — review quality collapses with size. Past a few hundred lines, defects
found per line drops sharply, and 'LGTM' is what a reviewer says when the diff has beaten them. So a
900-line PR is less code reviewed, not more. If a change is genuinely big I land the refactor first as
its own PR and the behaviour change on top."*

⭐ **Close on the two habits and one guard rail:** *"I self-review my own diff on the platform before
requesting a human, and I never ask for review on red CI. And I'd want main protected — PR required,
checks required, force-push forbidden — because that's what turns 'never rewrite shared history' from
a convention people forget into a property the server enforces."*
