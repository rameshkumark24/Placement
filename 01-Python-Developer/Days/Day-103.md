# Part 1 — ⭐⭐ The five calls

```python
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)     # ⭐ IPv4 + TCP
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)   # ⭐⭐ see below
server.bind(("127.0.0.1", 8000))                               # ⭐ claim the port (Day 003)
server.listen(128)                                             # ⭐ backlog
print("listening on 8000")

while True:                                                     # ⭐⭐ THE SERVER LOOP (Day 004)
    conn, addr = server.accept()                                # ⭐⭐ BLOCKS until a client arrives
    with conn:
        data = conn.recv(4096)
        conn.sendall(b"hello\n")
```

```
⭐⭐ THE DISTINCTION THAT EVERYTHING ELSE RESTS ON — AND PEOPLE MISS IT FOR YEARS:
⭐   `server`  is the LISTENING socket. It never carries data. Its only job is
⭐             to be the thing accept() returns connections from.
⭐   `conn`    is a NEW SOCKET, ⭐⭐ ONE PER CLIENT, created by accept().
⭐             ⭐ THAT is what you read and write.
⭐   ⇒ ⭐⭐ SO ONE LISTENING SOCKET ON PORT 8000 CAN HAVE 10,000 LIVE CONNECTIONS.
⭐        A TCP connection is identified by the FOUR-TUPLE (src ip, src port,
⭐        dst ip, dst port) — Day 008 — so the shared destination port is not a
⭐        collision. ⭐ This is the answer to "how does one port serve many users".
```

```
⭐⭐ WHY SO_REUSEADDR, AND IT IS A REAL DAY-008 PAYOFF:
⭐   restart your server and you get `OSError: [Errno 98] Address already in use`
⭐   — even though nothing is running.
⭐   ⇒ ⭐⭐ BECAUSE THE OLD CONNECTIONS ARE IN TIME_WAIT (60s), and the kernel
⭐        will not let you bind a port with lingering connections.
⭐   ⇒ ⭐ SO_REUSEADDR says "bind anyway; those are dead". ⭐⭐ Every server sets
⭐        it, and now you know it is not a magic incantation.
⭐   ⇒ ⭐ SO_REUSEPORT is different: it lets SEVERAL PROCESSES bind the SAME port
⭐        and the kernel load-balances between them. ⭐⭐ That is how Gunicorn can
⭐        run N workers on one port (Day 106).
```

| ⭐ Call | ⭐ What it does |
|---|---|
| `socket()` | ⭐ create an endpoint — a file descriptor (Day 078) |
| ⭐ `bind()` | claim an address + port ⇒ ⭐ `EADDRINUSE` if taken |
| ⭐⭐ `listen(n)` | ⭐⭐ become a **server**; `n` = the **accept queue** depth |
| ⭐⭐ `accept()` | ⭐⭐ block until a client connects; **return a new socket** |
| `recv(n)` / `sendall()` | ⭐ read up to n bytes / write all bytes |
| `close()` | ⭐ send FIN ⇒ ⭐ **if you forget: `CLOSE_WAIT` on the peer** (Day 082) |

⭐ **The backlog is the queue of connections the kernel has completed the handshake for but you have
not `accept()`ed yet.** ⭐⭐ **A full backlog means new clients are refused or dropped** — which is
what "the server is up but not responding" looks like when your accept loop is blocked doing work.

# Part 2 — ⭐⭐ TCP is a stream, not messages

```python
# ⚠️⚠️ ⭐⭐ THIS IS WRONG, AND IT WORKS ON YOUR LAPTOP:
data = conn.recv(4096)          # ⚠️ assumes one recv == one whole message
```

```
⭐⭐ WHAT recv ACTUALLY GUARANTEES — this is the single most important paragraph
⭐   on the page:
⭐   · it returns BETWEEN 1 AND n BYTES. ⭐⭐ NOT "the message".
⭐   · it may return HALF of what the client sent.
⭐   · it may return TWO messages GLUED TOGETHER.
⭐   · ⭐⭐ it returns b"" — AND ONLY b"" — WHEN THE PEER HAS CLOSED. That empty
⭐     bytes object is the end-of-stream signal, and checking for it is how your
⭐     loop terminates.
⭐   · ⭐ it BLOCKS if nothing has arrived yet.
⭐
⭐ ⇒ ⭐⭐ WHY: TCP GUARANTEES ORDER AND DELIVERY. IT DOES NOT GUARANTEE
⭐     BOUNDARIES. ⭐ The sender's writes are coalesced (Nagle) or split (MSS,
⭐     Day 008) freely by the kernel and by every router in between.
⭐ ⇒ ⭐⭐ IT "WORKS" LOCALLY BECAUSE LOOPBACK IS FAST AND YOUR MESSAGES ARE
⭐     SMALL — so one recv usually does get everything. ⭐⭐ THEN IT BREAKS IN
⭐     PRODUCTION UNDER LOAD, INTERMITTENTLY, WHICH IS THE WORST WAY TO FIND OUT.
```

```
⭐⭐ THEREFORE EVERY PROTOCOL MUST FRAME. THERE ARE ONLY THREE WAYS:
⭐   1. ⭐ A DELIMITER          ⇒ read until you see it. ⭐⭐ HTTP headers:
⭐                                 read until b"\r\n\r\n"
⭐   2. ⭐⭐ A LENGTH PREFIX     ⇒ read the length, then exactly that many bytes.
⭐                                 ⭐⭐ HTTP bodies: Content-Length
⭐   3. ⭐ CLOSE THE CONNECTION ⇒ "the message is everything until EOF".
⭐                                 ⭐ HTTP/1.0's default, and why it could not
⭐                                 reuse connections (Day 011)
⭐   ⇒ ⭐⭐ HTTP USES ALL THREE, IN THAT ORDER — and once you see that, Day 104's
⭐        parser writes itself.
```

```python
# ⭐⭐ THE CORRECT SHAPE — accumulate into a buffer until you have what you need:
def recv_until(conn, delimiter: bytes, max_size: int = 65536) -> bytes:
    buf = b""
    while delimiter not in buf:
        chunk = conn.recv(4096)
        if not chunk:                                  # ⭐⭐ b"" ⇒ peer closed
            raise ConnectionError("closed before delimiter")
        buf += chunk
        if len(buf) > max_size:                        # ⭐⭐ MANDATORY (Day 104)
            raise ValueError("request too large")
    return buf
```

⚠️ ⭐⭐ **The size limit is not optional.** Without it, a client that opens a connection and sends
`"A"` forever grows your buffer until the process is OOM-killed (Day 082) — **one connection, no
authentication needed, whole service down.**

# Part 3 — ⭐ An HTTP server, in twenty lines

```python
import socket

RESPONSE = (
    b"HTTP/1.1 200 OK\r\n"
    b"Content-Type: text/html; charset=utf-8\r\n"
    b"Content-Length: 48\r\n"                   # ⭐⭐ MUST match the body exactly
    b"Connection: close\r\n"                    # ⭐ keep it simple today (Day 105)
    b"\r\n"                                     # ⭐⭐ THE BLANK LINE ends the headers
    b"<h1>Served by 20 lines of Python</h1>"
)

server = socket.socket()
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(("127.0.0.1", 8000))
server.listen(128)

while True:
    conn, addr = server.accept()
    with conn:
        request = recv_until(conn, b"\r\n\r\n")     # ⭐ headers only, for now
        print(request.decode("latin-1").splitlines()[0])   # ⭐ the request line
        conn.sendall(RESPONSE)
```

```
⭐⭐ OPEN http://127.0.0.1:8000 IN A BROWSER. IT RENDERS.
⭐   ⇒ ⭐⭐ There is nothing between your `sendall` and the pixels except TCP.
⭐        ⭐ Every framework you use for the rest of your career is a layer over
⭐        exactly this, and you have now seen the bottom.
⭐
⭐ ⭐ THREE THINGS TO NOTICE IMMEDIATELY:
⭐   1. ⭐ THE BROWSER MAKES TWO REQUESTS — yours and /favicon.ico. ⭐ Your
⭐      server answers both with the same HTML, which is wrong but harmless.
⭐   2. ⭐⭐ THE CONTENT-LENGTH MUST BE EXACT. Too small ⇒ the page is truncated.
⭐      Too large ⇒ ⭐⭐ THE BROWSER HANGS waiting for bytes that never come.
⭐      ⭐ Try both. It is the single most instructive two minutes here.
⭐   3. ⭐⭐ decode("latin-1") FOR THE REQUEST LINE, NOT utf-8 — ⭐ Day 037:
⭐      latin-1 maps every byte to a character and NEVER RAISES, so a malformed
⭐      or hostile request cannot crash your parser before you have inspected it.
```

⭐ **`nc -l 8000` on one side and `curl` on the other** shows you the exact bytes a real client sends.
⭐⭐ **Do that once**; it is the cheapest way to see that HTTP really is just text over a socket.

# Part 4 — ⭐ Errors, timeouts, and the client side

| ⭐ Exception | ⭐ Cause |
|---|---|
| `OSError` / `EADDRINUSE` | ⭐ port taken, or `TIME_WAIT` — `SO_REUSEADDR` |
| ⭐ `ConnectionResetError` | ⭐⭐ the peer sent RST — usually **it gave up while you were slow** |
| ⭐⭐ `BrokenPipeError` | ⭐⭐ you wrote to a socket the peer already closed (Day 079's `SIGPIPE`) |
| `socket.timeout` | ⭐ your `settimeout` fired |
| `b""` from `recv` | ⭐ not an error — **an orderly close** |

```python
conn.settimeout(30)              # ⭐⭐ NON-NEGOTIABLE ON A SERVER SOCKET
```

```
⭐⭐ WHY A TIMEOUT ON EVERY CONNECTION IS A SECURITY CONTROL, NOT A NICETY:
⭐   a client connects, sends "GET / HTT" and stops. ⭐ Your recv_until blocks
⭐   forever. ⭐⭐ THE CONNECTION, ITS FD AND (TOMORROW) ITS THREAD ARE HELD
⭐   PERMANENTLY. Open 500 of those from one laptop ⇒ ⭐⭐ THE SERVER IS DOWN.
⭐   ⇒ ⭐ THAT IS SLOWLORIS, it costs the attacker nothing, and a read timeout
⭐        is the whole defence (Day 106 adds the rest).
```

```python
# ⭐ THE CLIENT SIDE, for completeness — and it is what every library does:
client = socket.create_connection(("example.com", 80), timeout=10)   # ⭐ DNS + connect
client.sendall(b"GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")
chunks = []
while chunk := client.recv(4096):        # ⭐⭐ Day 040's walrus, ending on b""
    chunks.append(chunk)
client.close()
```

⭐⭐ **`Host:` is mandatory in HTTP/1.1** — it is what allows one IP to serve many sites (Day 011), and
omitting it gets you a `400` from any real server.

⭐ **`socketserver` in the standard library** wraps all of this (`TCPServer`, `ThreadingMixIn`), and
`http.server` gives you a whole HTTP server. ⭐⭐ **We are not using either, deliberately** — the point
of Stage 3 is that nothing between the socket and the route handler is unknown to you.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Assuming one `recv` = one message** | ⭐⭐ TCP is a stream. Works locally, breaks under load. |
| Not checking for `b""` | ⭐ That is the peer closing — your loop never ends. |
| ⭐ Buffering with no size limit | ⭐⭐ One connection can OOM the process. |
| Forgetting `SO_REUSEADDR` | ⭐ `EADDRINUSE` on every restart, because of `TIME_WAIT`. |
| ⭐⭐ **No `settimeout`** | ⭐⭐ Slowloris — 500 idle connections kill the server. |
| ⭐ `Content-Length` too large | ⭐⭐ The client hangs forever. |
| `send()` instead of `sendall()` | ⭐ `send` may write **fewer bytes** and returns the count. |
| ⭐ Decoding a request as UTF-8 | ⭐⭐ Use `latin-1` for the line — it never raises on hostile bytes. |
| Confusing the listening and connection sockets | ⭐ `accept()` returns a **new** socket per client. |
| Not closing `conn` | ⭐ `CLOSE_WAIT` on the peer, and fd exhaustion here (Day 082). |
| Omitting `Host` as a client | ⭐ Mandatory in HTTP/1.1. |

## Interview questions

**Q: What does `accept()` return, and why does that matter?**
> A new socket, one per client, plus the peer's address. The listening socket never carries data — its
> only job is to hand out connections. That's the answer to "how does one port serve thousands of
> users": a TCP connection is identified by the four-tuple of source IP, source port, destination IP
> and destination port, so sharing the destination port isn't a collision. And it's why the accept
> loop must be fast — anything slow you do before looping back leaves new clients sitting in the
> kernel's backlog queue.

**Q: Why can't you assume one `recv` returns one message?**
> Because TCP guarantees order and delivery but not boundaries. `recv(4096)` returns between one and
> 4096 bytes — it can give you half a message, or two messages glued together, depending on how the
> kernel and the network happened to split the stream. It appears to work locally because loopback is
> fast and test messages are small, so one `recv` usually does get everything, and then it breaks
> intermittently in production under load, which is the worst way to find out. Every protocol has to
> frame: a delimiter, a length prefix, or close-means-end. HTTP uses all three — `\r\n\r\n` for
> headers, `Content-Length` for the body, and connection close in HTTP/1.0.

**Q: Why does every server set `SO_REUSEADDR`?**
> Because after a restart the previous connections are in `TIME_WAIT` for a minute or so, and the
> kernel won't let you bind a port with lingering connections — you get "address already in use" even
> though nothing is running. `SO_REUSEADDR` says bind anyway. It's worth distinguishing from
> `SO_REUSEPORT`, which lets several *processes* bind the same port with the kernel load-balancing
> between them — that's how a multi-worker server runs on one port.

**Q: What is slowloris, and what stops it?**
> A client opens a connection and sends a partial request very slowly — "GET / HTT" and then nothing.
> The server's read blocks forever, holding the connection, its file descriptor, and with a
> thread-per-connection model its thread. A few hundred of those from one laptop take the service
> down, with no authentication and almost no bandwidth. The primary defence is a read timeout on every
> connection, plus limits on header size and count, and a cap on concurrent connections per IP. It's
> the clearest case of a timeout being a security control rather than a nicety.

**Q: Why decode a request line as latin-1 rather than utf-8?**
> Because latin-1 maps every possible byte to a character and never raises, so a malformed or hostile
> request can't crash the parser before I've had a chance to inspect and reject it. UTF-8 decoding
> raises on invalid bytes, which turns a bad request into an exception in my parsing layer. It's the
> one place where latin-1's "never fails" property — which is a silent-corruption hazard everywhere
> else — is exactly what you want.

## 🎙️ Articulation drill

Record two minutes: **"What actually happens when a request reaches your server?"** — now answerable
from the bottom rather than from the framework's documentation.

⭐ **Start below HTTP:** **"the kernel completes the TCP handshake and puts the connection on the
listen queue. My process is blocked in `accept()`, which returns a new socket — one per client,
separate from the listening socket, which never carries data."**

⭐⭐ **Then the part that shows you have actually written it:** *"then I read, and the important thing
is that TCP is a byte stream with no message boundaries. `recv` gives me between one and n bytes — it
might be half the headers, or the headers plus part of the body. So I loop, accumulating into a buffer
until I see `\r\n\r\n`, which is HTTP's delimiter framing for headers. Then I read exactly
`Content-Length` bytes for the body, which is length-prefix framing. HTTP uses both, and a third —
close-means-end — which is what HTTP/1.0 did and why it couldn't reuse connections."*

⭐⭐ **Then the two things you would be wrong not to mention:** *"and I'd have a read timeout and a
buffer size limit from the first version, because both are security controls. Without a timeout, a
client that connects and sends nothing holds the connection and its file descriptor forever — a few
hundred of those is slowloris, and it takes the service down from one laptop. Without a size limit, one
connection sending 'A' forever grows my buffer until the process is OOM-killed."*

⭐ **Close on what it demystifies:** *"writing the twenty-line version is worth doing once, because
after it there's nothing between `sendall` and the browser rendering except TCP — and every framework
after that is a layer over exactly this."*
