# Day 107

**L-107** · **Routing and path params** — from an `if/elif` chain to a real router

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a router answers two questions in a fixed order — which path, and then
> which method — and collapsing them into one lookup is why so many APIs return `404` when they mean
> `405`, hiding endpoints that exist from clients trying to use them correctly.**
>
> ⭐ Routing looks trivial until path parameters, method dispatch, ordering and trailing slashes each
> arrive with their own bug. **All four are here.**

---

# Part 1 — ⭐ From `if/elif` to a table

```python
# ⚠️ ⭐ WHERE EVERYONE STARTS — and it is fine for about ten minutes:
def handle(request):
    if request.path == "/": return home(request)
    elif request.path == "/health": return health(request)
    ...
```

```
⚠️ ⭐⭐ FOUR THINGS WRONG WITH IT, AND EACH ONE MOTIVATES A PIECE OF THE ROUTER:
⭐   1. ⭐ O(n) string comparisons per request
⭐   2. ⭐⭐ NO PARAMETERS — /users/42 cannot be expressed at all
⭐   3. ⭐⭐ NO METHOD DISPATCH — GET and DELETE on the same path are one branch
⭐   4. ⭐ the route table is not DATA, so nothing can enumerate it: no OpenAPI
⭐        (Day 126), no reverse routing, no "list all endpoints"
```

```python
ROUTES = {("GET", "/"): home, ("GET", "/health"): health}    # ⭐ O(1)... but still no params
```

⭐⭐ **Making routes *data* rather than *control flow* is the actual step forward here**, and it is
what every later feature depends on — a table can be printed, validated at startup, turned into a spec,
and reversed.

# Part 2 — ⭐⭐ Path parameters

```python
import re
from dataclasses import dataclass

CONVERTERS = {
    "int":  (r"[0-9]+",       int),
    "str":  (r"[^/]+",        str),      # ⭐⭐ NOTE: [^/]+ — a str param must NOT match a slash
    "uuid": (r"[0-9a-f-]{36}", str),
    "path": (r".+",           str),      # ⭐ the only one that DOES match slashes
}

def compile_path(template: str) -> tuple[re.Pattern, dict]:
    """⭐ '/users/{user_id:int}/orders' -> a compiled regex + converters."""
    converters, regex = {}, "^"
    for part in re.split(r"(\{[^}]+\})", template):
        if part.startswith("{"):
            name, _, kind = part[1:-1].partition(":")
            pattern, conv = CONVERTERS[kind or "str"]
            converters[name] = conv
            regex += f"(?P<{name}>{pattern})"          # ⭐ named group
        else:
            regex += re.escape(part)                    # ⭐⭐ ESCAPE the literal parts
    return re.compile(regex + "$"), converters          # ⭐⭐ compile ONCE (Day 076)
```

```
⭐⭐ THREE DETAILS THAT ARE EACH A REAL BUG IF YOU MISS THEM:
⭐  1. ⭐⭐ re.escape ON THE LITERAL PARTS. A path containing `.` or `+` becomes a
⭐       wildcard otherwise — ⭐ `/files/report.pdf` would match `/files/reportXpdf`.
⭐  2. ⭐⭐ `[^/]+` FOR A str PARAM, NOT `.+`. With `.+`, `/users/{name}` swallows
⭐       `/users/a/b/c` and your "user name" contains slashes ⇒ ⭐ path traversal
⭐       one layer up (Day 078).
⭐  3. ⭐⭐ ANCHOR BOTH ENDS (^ and $). Without `$`, `/users` matches
⭐       `/users/../../etc/passwd`. ⭐ Anchoring is a security control here.
⭐  ⇒ ⭐ and compile at REGISTRATION, not per request. A hundred routes recompiled
⭐       per request is measurable (Day 100A).
```

```python
@dataclass
class Route:
    template: str
    pattern: re.Pattern
    converters: dict
    methods: set[str]
    handler: Callable
    name: str
```

# Part 3 — ⭐⭐ Match path first, then method

```python
def resolve(self, path: str, method: str):
    allowed: set[str] = set()
    for route in self.routes:
        m = route.pattern.match(path)
        if not m:
            continue
        allowed |= route.methods                      # ⭐⭐ remember what this PATH supports
        if method in route.methods:
            params = {k: route.converters[k](v) for k, v in m.groupdict().items()}
            return route.handler, params
    if allowed:                                        # ⭐⭐ the path exists, the method does not
        raise HTTPError(405, "method not allowed",
                        headers=[("Allow", ", ".join(sorted(allowed)))])   # ⭐ REQUIRED on a 405
    raise HTTPError(404, "not found")
```

```
⭐⭐ THIS IS THE STRUCTURAL POINT OF THE WHOLE DAY. A router that looks up
⭐   (method, path) AS ONE KEY cannot tell these two cases apart:
⭐     · ⭐ the path does not exist                     ⇒ 404
⭐     · ⭐⭐ the path exists but not for this method    ⇒ 405 + Allow
⭐   ⇒ ⭐⭐ SO IT RETURNS 404 FOR BOTH — and a client doing DELETE on a real
⭐        resource is told the resource does not exist. ⭐ They then debug the
⭐        wrong thing for an hour, and your API has actively lied.
⭐   ⇒ ⭐⭐ THE FIX IS THE TWO-PASS SHAPE ABOVE, AND IT IS ALSO WHERE `OPTIONS`
⭐        COMES FROM FOR FREE: the `allowed` set is exactly the CORS preflight
⭐        answer (Day 020).
⭐   ⇒ ⭐ HEAD should fall back to the GET handler (Day 105), with the body dropped.
```

# Part 4 — ⭐⭐ Ordering, and the trap everyone hits

```python
router.add("/users/{id:int}", get_user)      # ⭐ registered first
router.add("/users/me",       get_me)        # ⚠️⚠️ UNREACHABLE if id were :str
```

```
⭐⭐ TWO POSSIBLE POLICIES, AND YOU MUST PICK ONE DELIBERATELY:
⭐
⭐  A. ⭐⭐ FIRST MATCH WINS (Flask, FastAPI, Starlette). Simple and predictable
⭐       — ⭐⭐ AND ORDER OF REGISTRATION BECOMES SEMANTIC. `/users/{name}` before
⭐       `/users/me` makes `/users/me` DEAD CODE, silently, with no warning, and
⭐       it looks like an auth bug because `me` starts returning a stranger.
⭐       ⭐ This is the single most common FastAPI gotcha: DECLARE STATIC ROUTES
⭐       BEFORE DYNAMIC ONES.
⭐
⭐  B. ⭐ MOST SPECIFIC WINS — sort by "static segments beat dynamic ones".
⭐       ⭐⭐ Order-independent, which is friendlier; ⭐ but "specificity" needs a
⭐       defined total ordering, and when two routes tie you are back to
⭐       registration order anyway.
⭐
⭐  ⇒ ⭐⭐ WHICHEVER YOU CHOOSE, DETECT AND REJECT THE PROBLEM AT STARTUP:
⭐       warn (or raise) when a newly added route can never be reached because
⭐       an earlier pattern subsumes it. ⭐⭐ A startup error is worth ten
⭐       production hours — and it is ten lines.
```

```
⭐⭐ TRAILING SLASHES — pick a policy, and mind the redirect code:
⭐   /users  and  /users/  are DIFFERENT PATHS. Options:
⭐     · treat them as identical (normalise before matching)
⭐     · ⭐ redirect one to the other  ⇐ most frameworks
⭐     · 404 the non-canonical one
⭐   ⇒ ⚠️⚠️ ⭐⭐ IF YOU REDIRECT, USE 308 (or 307), NOT 301/302.
⭐        ⭐⭐ 301 AND 302 ALLOW THE CLIENT TO CHANGE POST INTO GET — historically
⭐        they do — ⭐ so a POST to /orders redirects to /orders/ and arrives as a
⭐        GET with NO BODY. ⭐⭐ 307/308 PRESERVE THE METHOD AND BODY. This is a
⭐        genuine, hard-to-diagnose data-loss bug.
⭐   ⇒ ⚠️ ⭐ AND A REDIRECT ON AN AUTHENTICATED POST can drop the body, drop
⭐        headers, or leak to another origin if the target is not carefully
⭐        constructed. ⭐⭐ Prefer normalising to redirecting.
```

# Part 5 — ⭐ Reverse routing, mounting, and scale

```python
def url_for(self, name: str, **params) -> str:
    route = self.by_name[name]
    path = route.template
    for k, v in params.items():
        path = re.sub(r"\{" + k + r"(:[^}]+)?\}", str(v), path)
    return path

url_for("get_user", id=42)      # ⭐ "/users/42"
```

```
⭐⭐ WHY REVERSE ROUTING EARNS ITS KEEP: THE URL IS DECLARED IN EXACTLY ONE
⭐   PLACE. ⇒ ⭐ change `/users/{id}` to `/v2/users/{id}` and every generated
⭐   link, redirect and test follows. ⭐⭐ Hardcoded URLs scattered through
⭐   templates and tests are a refactor you will not do, so the URL becomes
⭐   permanent by accident.
```

```python
api = Router(prefix="/api/v1")           # ⭐ mounting a sub-router
api.add("/users/{id:int}", get_user)
app.mount(api)                            # ⭐ prefixes are composed at registration
```

```
⭐ SCALE: A LIST OF COMPILED REGEXES IS O(n) PER REQUEST.
⭐   · ⭐ 100 routes × a compiled regex ≈ microseconds ⇒ ⭐⭐ irrelevant next to
⭐     one database query. ⭐ Do not optimise this.
⭐   · ⭐ thousands of routes ⇒ a RADIX TREE (split the path on "/" and walk a
⭐     trie) gives O(path segments) instead. ⭐⭐ That is what Go's and Rust's
⭐     fast routers do, and what `Starlette` deliberately does NOT, because
⭐     the regex list is fast enough at real API sizes.
⭐   ⇒ ⭐⭐ SAY THAT IN AN INTERVIEW: knowing WHEN the simple structure stops
⭐        being adequate is worth more than knowing the clever one.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Looking up `(method, path)` as one key** | ⭐⭐ You cannot distinguish 404 from 405. Match path, then method. |
| `405` without an `Allow` header | ⭐ It is required, and it is the client's only hint. |
| ⭐ Not escaping literal path segments | ⭐⭐ `.` and `+` become wildcards. |
| ⭐ `.+` for a string parameter | ⭐⭐ It swallows slashes — traversal one layer up. |
| Not anchoring the regex | ⭐⭐ `/users` matches `/users/../../etc/passwd`. |
| ⭐ Compiling per request | ⭐ Compile at registration. |
| ⭐⭐ **Dynamic route registered before a static one** | ⭐⭐ The static route is silently dead. Detect it at startup. |
| ⭐ `301`/`302` for a trailing-slash redirect | ⭐⭐ POST can become GET — **the body is dropped**. Use `308`. |
| Hardcoding URLs | ⭐ Reverse routing, so the URL is declared once. |
| Building a radix tree for 40 routes | ⭐ A regex list is microseconds. Optimise the query instead. |
| ⭐ No `HEAD` fallback to `GET` | ⭐ Caches and health checks use `HEAD` (Day 102). |

## Interview questions

**Q: How would you implement a router?**
> Routes as data, not control flow — a list of records with a compiled regex, converters, allowed
> methods and a handler. Path templates get compiled once at registration: literal parts escaped,
> parameters turned into named groups with a converter, and the whole thing anchored at both ends.
> Then resolution is two passes rather than one lookup: find routes whose *path* matches, collecting
> the union of their methods, and only then check the method. Making routes data is the step that
> everything else depends on — it's what lets you generate an OpenAPI spec, reverse URLs, and validate
> the table at startup.

**Q: Why does the two-pass shape matter?**
> Because a single `(method, path)` lookup can't distinguish "this path doesn't exist" from "this path
> exists but not for this method". So it returns 404 for both, and a client doing DELETE on a real
> resource is told the resource doesn't exist — they debug the wrong thing for an hour and the API has
> actively lied to them. The two-pass version returns 405 with an `Allow` header listing what the path
> does support. It also gives you the CORS preflight answer for free, because the set of allowed
> methods is exactly what `OPTIONS` needs to report.

**Q: What's the classic route-ordering bug?**
> Registering `/users/{name}` before `/users/me`. With first-match-wins — which is what Flask, FastAPI
> and Starlette do — the dynamic route matches "me" as a username, so `/users/me` is dead code. It's
> silent, there's no warning, and it presents as an auth bug because `/users/me` starts returning a
> stranger's profile. The rule is to declare static routes before dynamic ones, but I'd rather not
> rely on a rule: detect at startup when a newly registered route can never be reached because an
> earlier pattern subsumes it, and raise. It's about ten lines and it's worth ten production hours.

**Q: What's dangerous about a trailing-slash redirect?**
> The status code. 301 and 302 permit the client to change the method — historically they do — so a
> POST to `/orders` that redirects to `/orders/` arrives as a GET with no body. That's silent data
> loss and it's genuinely hard to diagnose, because the redirect looks innocuous in the logs. 307 and
> 308 preserve the method and body. Better still, normalise the path before matching rather than
> redirecting at all, because a redirect on an authenticated POST can also drop headers.

**Q: When would you need something faster than a list of regexes?**
> Almost never at API sizes. A hundred compiled regexes is microseconds, which is irrelevant next to
> one database query — Starlette deliberately keeps the linear scan for that reason. If I genuinely
> had thousands of routes I'd use a radix tree keyed on path segments, so lookup is proportional to
> path depth rather than route count, which is what the fast Go and Rust routers do. But knowing when
> the simple structure stops being adequate matters more than reaching for the clever one.
