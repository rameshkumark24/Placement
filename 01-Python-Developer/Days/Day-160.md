# Day 160

**L-160** · **Multi-tenancy** — shared schema, row-level security, ⭐⭐ and the one `WHERE` clause that must never be forgotten

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: in a multi-tenant system, every query is one forgotten `WHERE` clause
> away from a data breach — so the only durable designs are the ones where forgetting it produces
> *no rows* or *an error*, never *someone else's rows*.**
>
> ⭐ Day 118 said IDOR is a query-shape problem and Day 139 put scoping in the repository. ⭐⭐ Today
> that principle becomes an architectural decision with three legitimate answers and very different
> costs.

# Part 1 — ⭐⭐ The three models

```
⭐⭐ THE AXIS IS ISOLATION VS COST-PER-TENANT, AND EVERY OTHER DIFFERENCE
⭐   FOLLOWS FROM IT:

⭐  1. ⭐⭐ SHARED SCHEMA — one database, one set of tables, a `tenant_id`
⭐       column on every row.
⭐       ⭐ + cheapest by far: ⭐⭐ 10,000 tenants cost the same as one to
⭐            operate. One migration, one pool, one backup.
⭐       ⭐ + a new tenant is an INSERT — ⭐ signup is instant
⭐       ⭐ − ⭐⭐ ONE MISSING `WHERE` CLAUSE IS A CROSS-TENANT BREACH
⭐       ⭐ − noisy neighbours share every resource (Part 4)
⭐       ⭐ − ⭐ "delete this tenant's data" is a careful DELETE, not a DROP;
⭐            ⭐⭐ "give me my data" and "we are GDPR-deleting you" are both
⭐            real work rather than a file copy
⭐       ⇒ ⭐⭐ THE DEFAULT FOR SaaS, AND THE RIGHT ONE UNTIL A CUSTOMER PAYS
⭐            YOU TO CHANGE IT.
⭐
⭐  2. ⭐ SCHEMA PER TENANT — one database, `tenant_1.orders`, `tenant_2.orders`.
⭐       ⭐ + isolation is enforced by the search path; ⭐ per-tenant backup
⭐       ⭐ − ⭐⭐ MIGRATIONS RUN N TIMES. At 5,000 schemas that is hours, and
⭐            a partial failure leaves tenants on DIFFERENT SCHEMA VERSIONS —
⭐            ⭐ your code must then handle both, which is the cost nobody
⭐            budgets for.
⭐       ⭐ − ⭐⭐ POSTGRES CATALOG BLOAT: 5,000 schemas × 40 tables = 200,000
⭐            relations. ⭐ Planning slows, `pg_dump` slows, connection setup
⭐            slows. ⭐⭐ It stops being pleasant somewhere in the low thousands.
⭐       ⇒ ⭐ A genuine middle ground for hundreds of tenants; ⭐⭐ a trap at
⭐            tens of thousands.
⭐
⭐  3. ⭐⭐ DATABASE PER TENANT — full isolation.
⭐       ⭐ + ⭐⭐ THE STRONGEST GUARANTEE: a cross-tenant query is not a bug,
⭐            it is IMPOSSIBLE. ⭐ Per-tenant restore, per-tenant region
⭐            (data residency), per-tenant scaling.
⭐       ⭐ − ⭐⭐ CONNECTION POOLS DO NOT DIVIDE. 500 tenants × a pool each is
⭐            impossible; ⭐ you need a proxy (PgBouncer) or per-request
⭐            connections. ⭐⭐ THIS IS THE PRACTICAL BLOCKER, not the cost of
⭐            the databases.
⭐       ⭐ − migrations, monitoring and cost scale linearly with tenants
⭐       ⇒ ⭐ Right for enterprise, regulated, or few-large-customer products.
⭐
⭐   ⇒ ⭐⭐ AND THE HYBRID THAT REAL COMPANIES CONVERGE ON: SHARED SCHEMA BY
⭐        DEFAULT, WITH A DEDICATED DATABASE FOR THE TENANTS WHO PAY FOR IT.
⭐        ⭐ Which means your code must be tenancy-model-agnostic from day
⭐        one — ⭐⭐ i.e. resolve the connection FROM the tenant, rather than
⭐        assuming one global engine. ⭐ That one decision keeps the door open.
```

# Part 2 — ⭐⭐ Making the filter impossible to forget

```
⭐⭐ THE PROBLEM WITH "ALWAYS ADD `WHERE tenant_id = :t`": IT IS A CONVENTION,
⭐   AND ⭐ A CONVENTION IS A CONTROL THAT FAILS SILENTLY THE FIRST TIME
⭐   SOMEONE IS IN A HURRY. ⭐⭐ Day 118's rule: make the wrong thing hard to
⭐   write. Four levels, weakest to strongest:

⭐  1. ⭐ CODE REVIEW. ⭐⭐ Not a control. A reviewer sees a correct-looking
⭐       query and cannot see the missing clause — ⭐ absence is invisible.
⭐
⭐  2. ⭐ THE REPOSITORY (Day 139) with a required keyword-only `tenant_id`.
⭐       ⭐⭐ Good: forgetting it is a TypeError at import time. ⭐ Limit: it
⭐       only protects queries that go THROUGH the repository, and the raw
⭐       SQL someone writes for a report does not.
⭐
⭐  3. ⭐⭐ A QUERY-LEVEL GUARD. SQLAlchemy's `with_loader_criteria` or a
⭐       `before_compile` event that injects the filter for every mapped
⭐       class implementing `TenantMixin`. ⭐ Now it is applied by DEFAULT
⭐       rather than by memory.
⭐       ⭐ − ⭐⭐ still bypassed by `text()`, by a raw connection, by a
⭐            different service, and by anyone in `psql`.
⭐
⭐  4. ⭐⭐ ROW-LEVEL SECURITY — THE DATABASE ENFORCES IT.
⭐       ⭐ The strongest, because ⭐⭐ IT CANNOT BE BYPASSED BY ANY CODE PATH,
⭐         INCLUDING ONES THAT DO NOT EXIST YET, INCLUDING psql, INCLUDING A
⭐         COMPROMISED ORM. ⭐ It moves the guarantee from your discipline to
⭐         the database's.
```

```sql
-- ⭐⭐ POSTGRES RLS — about six lines for the whole guarantee
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;      -- ⭐⭐ applies to the OWNER too
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

```python
# ⭐ set it per request, in the same transaction as the queries
await db.execute(text("SET LOCAL app.tenant_id = :t"), {"t": str(tenant.id)})
```

```
⭐⭐ THE FOUR THINGS THAT MAKE RLS WORK OR SILENTLY NOT WORK:
⭐  1. ⭐⭐ `SET LOCAL`, NOT `SET`. ⭐ `SET` persists on the CONNECTION, and
⭐       connections are POOLED (Day 135) ⇒ ⭐⭐ THE NEXT REQUEST INHERITS THE
⭐       PREVIOUS TENANT'S ID. That is a cross-tenant leak caused by the fix.
⭐       ⭐ `SET LOCAL` is transaction-scoped and resets on commit/rollback.
⭐  2. ⭐⭐ `FORCE ROW LEVEL SECURITY`. Without it, ⭐ THE TABLE OWNER BYPASSES
⭐       THE POLICY ENTIRELY — and your app usually connects as the owner, so
⭐       ⭐⭐ RLS appears to be on and does nothing at all.
⭐  3. ⭐ `current_setting('app.tenant_id', true)` returns NULL if unset;
⭐       ⭐⭐ `tenant_id = NULL` IS NULL, WHICH IS NOT TRUE ⇒ ZERO ROWS. ⭐ That
⭐       is the correct failure: forgetting to set the tenant returns nothing,
⭐       never everything. ⭐⭐ FAIL CLOSED BY CONSTRUCTION.
⭐  4. ⭐ You still need `tenant_id` FIRST IN YOUR COMPOSITE INDEXES —
⭐       ⭐⭐ RLS adds a predicate, and without the index it becomes a filter
⭐       AFTER a scan. ⭐ RLS is a correctness feature with a performance
⭐       precondition.
⭐
⭐   ⇒ ⭐⭐ AND THE HONEST CAVEAT: RLS IS DEFENCE IN DEPTH, NOT A REPLACEMENT
⭐        FOR SCOPED QUERIES. ⭐ Keep the repository filter too — you want the
⭐        query to be correct AND the database to refuse if it is not.
```

# Part 3 — ⭐ Resolving the tenant, and the traps in each method

```
⭐⭐ WHERE DOES `tenant_id` COME FROM? ⭐ NEVER FROM THE REQUEST BODY OR A
⭐   QUERY PARAMETER — ⭐⭐ that is IDOR with extra steps (Day 118): the user
⭐   simply sends someone else's id.

⭐  ⭐⭐ FROM THE AUTHENTICATED SESSION/TOKEN — ⭐ the default and the safest.
⭐       The tenant is a property of WHO YOU ARE, not of WHAT YOU ASKED FOR.
⭐  ⭐ FROM A SUBDOMAIN (`acme.app.com`) — ⭐ good UX, ⭐⭐ but you MUST verify
⭐       the authenticated user belongs to that tenant. ⭐ Otherwise logging in
⭐       and changing the subdomain is the entire attack.
⭐  ⭐ FROM A PATH SEGMENT (`/t/acme/orders`) — same rule, same verification.
⭐  ⭐⭐ AND FOR USERS IN MULTIPLE TENANTS: the ACTIVE tenant is part of the
⭐       SESSION, and switching it must ⭐ re-issue the session (Day 113's
⭐       fixation rule) and ⭐⭐ invalidate anything cached under the old one.

⭐⭐ THEN PUT IT IN A `ContextVar` (Day 146) AND BIND IT TO:
⭐   ⭐ every log line ⭐ every span ⭐ every metric label ⭐⭐ (as a TIER,
⭐        not a tenant id — Day 147's cardinality rule still applies)
⭐   ⭐⭐ AND EVERY QUEUED MESSAGE. ⭐ A Celery task that loses the tenant
⭐        context (Day 142) either fails or — much worse — runs with a
⭐        default. ⭐⭐ Pass `tenant_id` explicitly in the payload and set it
⭐        again at the top of the task. ⭐ Background jobs are where tenant
⭐        isolation is most often lost, because the request that carried the
⭐        context is long gone.
```

# Part 4 — ⭐⭐ The noisy neighbour, at every layer

```
⭐⭐ SHARING RESOURCES MEANS ONE TENANT CAN DEGRADE EVERY OTHER. Day 153
⭐   covered request rates; ⭐ here is the rest of the surface, which is bigger:

⭐   ⭐ ⭐⭐ THE DATABASE. One tenant with 50 million rows makes queries slow
⭐        FOR EVERYONE on a shared table — ⭐ shared indexes get deeper, the
⭐        shared buffer cache is evicted by their data, and autovacuum spends
⭐        its time on their churn.
⭐        ⇒ ⭐⭐ PARTITION BY `tenant_id` for the biggest tables: ⭐ each
⭐          tenant's data is physically separate, so a scan touches one
⭐          partition and a bulk delete becomes `DROP PARTITION`.
⭐   ⭐ ⭐⭐ THE CONNECTION POOL. One tenant's slow report holds 18 of your 20
⭐        connections ⇒ everyone waits. ⭐ Day 152's bulkhead: a per-tenant
⭐        semaphore, and a SEPARATE POOL for analytical work.
⭐   ⭐ THE CACHE (Day 143). ⭐⭐ One tenant's working set evicts everyone
⭐        else's under `allkeys-lru`. ⭐ Namespace keys by tenant, and consider
⭐        a per-tenant memory bound.
⭐   ⭐ THE QUEUE (Day 142). ⭐⭐ 100,000 jobs from one tenant means everyone
⭐        else's password reset waits behind them. ⭐ Per-tenant queues, fair
⭐        scheduling, or a concurrency cap.
⭐   ⭐ ⭐⭐ AND THE ONE THAT IS ALWAYS FORGOTTEN: A "DELETE TENANT" OR
⭐        "IMPORT 2 MILLION ROWS" OPERATION. ⭐ It is a bulk write on shared
⭐        tables — ⭐⭐ replication lag, lock contention, and vacuum pressure
⭐        for everyone. ⭐ Batch it, rate-limit it, and run it off-peak.

⭐⭐ THE PRINCIPLE: EVERY SHARED RESOURCE NEEDS A PER-TENANT CAP. ⭐ And the
⭐   cap must be on RESOURCE OCCUPANCY (concurrency, rows, memory), ⭐⭐ not
⭐   only on request rate — because one slow query consumes more than a
⭐   thousand fast ones, and no rate limit will see it (Day 153).
```

# Part 5 — ⭐ Operating a multi-tenant system

```
⭐⭐ THE FOUR CAPABILITIES YOU WILL BE ASKED FOR, AND EACH ONE IS EASY TO
⭐   BUILD EARLY AND EXPENSIVE TO RETROFIT:

⭐  1. ⭐⭐ PER-TENANT OBSERVABILITY. ⭐ "Is it slow for everyone or for
⭐       Acme?" ⭐⭐ Global p99 hides one tenant at 8 seconds completely.
⭐       ⇒ ⭐ tenant on every log and span (high cardinality is fine there,
⭐            Day 148); ⭐⭐ tenant TIER on metrics (low cardinality only).
⭐  2. ⭐⭐ EXPORT AND DELETE. ⭐ GDPR/contractual: "give us everything" and
⭐       "delete everything". ⭐⭐ On a shared schema this is a traversal of
⭐       every table — ⭐ including the ones people forget: audit logs, event
⭐       tables, the outbox (Day 142), object storage (Day 145), your search
⭐       index, and your ANALYTICS WAREHOUSE. ⭐⭐ Maintain the list as code,
⭐       not as institutional memory.
⭐  3. ⭐⭐ IMPERSONATION FOR SUPPORT — ⭐ and it must be: explicitly consented
⭐       or policy-bound, ⭐⭐ AUDIT-LOGGED WITH THE REAL ACTOR (not the
⭐       impersonated user), time-limited, and ⭐ read-only by default.
⭐       ⭐⭐ An impersonation feature with no audit trail is a backdoor with a
⭐       nice UI.
⭐  4. ⭐ PER-TENANT FEATURE FLAGS AND LIMITS (Day 155) — ⭐⭐ because tenants
⭐       are exactly the unit you want to roll features out by, and a canary
⭐       by tenant is more meaningful than a canary by request.

⭐⭐ AND THE MIGRATION QUESTION, ASKED IN EVERY SaaS INTERVIEW:
⭐   ⭐ "A CUSTOMER DEMANDS A DEDICATED DATABASE. HOW BAD IS IT?"
⭐   ⇒ ⭐⭐ EASY IF you resolve the connection from the tenant (Part 1) and
⭐        never assume a single global engine. ⭐ Then it is: provision, copy
⭐        their rows, dual-write briefly, cut over, delete the originals.
⭐   ⇒ ⭐⭐ HARD IF anything assumes one database — cross-tenant reports,
⭐        global sequences, a single Alembic version table, or a join across
⭐        tenants in an admin screen. ⭐ Those joins are the real blocker, and
⭐        they are usually in code nobody remembers writing.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Relying on convention for the tenant filter | A convention fails silently the first time someone is in a hurry. |
| Treating code review as the control | A reviewer can't see a clause that isn't there. |
| Schema-per-tenant at scale | Migrations run N times, partial failure splits versions, and the catalog bloats. |
| Database-per-tenant without solving pooling | Pools don't divide — this is the practical blocker, not database cost. |
| Assuming one global engine | The day a customer pays for isolation, everything must change. |
| RLS with `SET` instead of `SET LOCAL` | The setting persists on a pooled connection — the next request inherits the tenant. |
| RLS without `FORCE` | The table owner bypasses the policy, and your app usually *is* the owner. |
| RLS as a replacement for scoped queries | Defence in depth. Keep both. |
| RLS without `tenant_id` first in the index | The policy becomes a filter after a scan. |
| Reading the tenant from the request body or query string | IDOR with extra steps. |
| Subdomain or path tenancy without verifying membership | Log in, change the subdomain — that's the whole attack. |
| Switching active tenant without re-issuing the session | Session fixation, and stale cached data under the old tenant. |
| Losing tenant context in a background job | It fails, or worse, runs with a default. Pass it in the payload explicitly. |
| Tenant id as a metric label | Cardinality explosion. Tier on metrics, id on logs and spans. |
| Rate limits without occupancy caps | One slow query outweighs a thousand fast ones. |
| No partitioning for the largest tables | One huge tenant slows queries for everyone via shared indexes and cache. |
| Bulk tenant import/delete run at full speed | Replication lag and lock contention for every other tenant. |
| Global p99 only | It hides one tenant sitting at eight seconds. |
| Export/delete lists kept in people's heads | Audit logs, outbox, object storage and the warehouse get missed. |
| Impersonation without an audit trail naming the real actor | A backdoor with a nice UI. |

## Interview questions

**Q: Shared schema, schema per tenant, or database per tenant?**

> Shared schema by default — one database, a `tenant_id` column, and ten thousand tenants cost the
> same to operate as one: one migration, one pool, one backup, and signup is an INSERT. The cost is
> that a single missing `WHERE` clause is a cross-tenant breach, and that noisy neighbours share
> everything. Schema-per-tenant sounds like a middle ground and is fine for hundreds, but migrations
> run N times, a partial failure leaves tenants on different schema versions so your code must handle
> both, and Postgres catalog bloat makes it unpleasant in the low thousands. Database-per-tenant
> gives the strongest guarantee — a cross-tenant query isn't a bug, it's impossible — plus per-tenant
> restore and data residency, but the practical blocker isn't the cost of databases, it's that
> connection pools don't divide, so you need PgBouncer or per-request connections. Where real
> companies land is a hybrid: shared by default, dedicated for whoever pays for it. Which means from
> day one the code should resolve the connection *from* the tenant rather than assume one global
> engine — that single decision keeps the door open.

**Q: How do you guarantee the tenant filter is never forgotten?**

> By making forgetting it produce no rows rather than someone else's. Four levels: code review isn't
> a control, because a reviewer can't see a clause that isn't there. A repository with a required
> keyword-only `tenant_id` makes forgetting a `TypeError`, but only protects queries that go through
> it — not the raw SQL someone writes for a report. A query-level guard like
> `with_loader_criteria` applies it by default, but is bypassed by `text()`, a raw connection, or
> psql. So the strongest is row-level security, because the database enforces it and it can't be
> bypassed by any code path, including ones that don't exist yet. And crucially it fails closed:
> `current_setting` returns NULL when unset, `tenant_id = NULL` is NULL rather than true, so
> forgetting to set the tenant returns zero rows. I'd still keep the repository filter — I want the
> query to be correct *and* the database to refuse if it isn't.

**Q: What are the two ways RLS silently doesn't work?**

> `SET` instead of `SET LOCAL`, and missing `FORCE`. `SET` persists on the connection, and
> connections are pooled — so the next request on that connection inherits the previous tenant's id,
> which is a cross-tenant leak *caused by* the isolation mechanism. `SET LOCAL` is transaction-scoped
> and resets on commit. And without `ALTER TABLE ... FORCE ROW LEVEL SECURITY`, the table owner
> bypasses the policy entirely — and your application usually connects as the owner, so RLS appears
> enabled and does absolutely nothing. There's also a performance precondition: RLS adds a predicate,
> so `tenant_id` needs to be first in your composite indexes or the policy becomes a filter after a
> scan.

**Q: Where does the tenant id come from?**

> From the authenticated session or token — never from the request body or a query parameter, because
> then the user just sends someone else's id and you've built IDOR with extra steps. The tenant is a
> property of who you are, not of what you asked for. Subdomain or path-based tenancy is fine for UX
> but you must verify that the authenticated user belongs to that tenant, or logging in and editing
> the subdomain is the entire attack. For users in multiple tenants, the active tenant lives in the
> session, and switching it re-issues the session and invalidates anything cached under the old one.
> Then I'd put it in a `ContextVar` and bind it to logs and spans — and pass it explicitly in every
> queued message, because background jobs are where tenant isolation is most often lost: the request
> that carried the context is long gone, so the task either fails or, much worse, runs with a default.

**Q: One tenant is making the product slow for everyone. What do you do?**

> Identify which layer, because rate limiting only covers one of them. On the database, a tenant with
> fifty million rows deepens shared indexes and evicts everyone else's pages from the buffer cache,
> so I'd partition the largest tables by `tenant_id` — which also turns "delete this tenant" into
> `DROP PARTITION`. On the pool, one slow report holding eighteen of twenty connections is a bulkhead
> problem: a per-tenant semaphore and a separate pool for analytical work. On the cache, one tenant's
> working set evicting everyone else's under LRU. On the queue, a hundred thousand jobs from one
> tenant putting everyone's password reset behind them. The principle is that every shared resource
> needs a per-tenant cap, and the cap has to be on occupancy — concurrency, rows, memory — not just
> request rate, because one slow query consumes more than a thousand fast ones and no rate limit will
> ever see it.

## 🎙️ Articulation drill

**Two minutes: "How would you design multi-tenancy?"**

Lead with the model choice and justify shared schema economically — ten thousand tenants cost the
same as one — while naming its single risk honestly. Then spend most of your time on the interesting
part: making the filter impossible to forget, walking the four levels from code review up to RLS, and
explaining why RLS is different in kind because the guarantee moves from your discipline into the
database. Name both silent failures — `SET` on a pooled connection, and missing `FORCE` — because
they show you've actually run it. Then the noisy neighbour across four layers, with the observation
that caps must be on occupancy, not rate. Close on the forward-looking decision: **resolve the
connection from the tenant, so the day a customer pays for a dedicated database it's a migration
rather than a rewrite.**
