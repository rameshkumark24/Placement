# Part 1 — Filters live in the URL

```typescript
// ⭐⭐ ONE hook owns the URL ↔ filter mapping. Screens never parse params.
function useOrderFilters() {
  const [params, setParams] = useSearchParams();
  const filters = {
    status: params.get("status") ?? "all",
    q:      params.get("q") ?? "",
    cursor: params.get("cursor") ?? undefined,
  };
  const set = (patch: Partial<Filters>) => setParams(p => {
    for (const [k, v] of Object.entries(patch)) {
      v ? p.set(k, String(v)) : p.delete(k);   // ⭐ empty ⇒ remove, not "="
    }
    p.delete("cursor");                        // ⭐⭐ ANY FILTER CHANGE
    return p;                                  //    RESETS PAGINATION
  });
  return { filters, set };
}
```

| ⭐ Rule | Why |
|---|---|
| **⭐⭐ Changing a filter clears the cursor** | Otherwise the user is on page 7 of a result set with 3 pages, and sees an empty screen that looks like a bug |
| **Empty values are removed** | ⭐ `?status=&q=` is ugly and makes two different URLs for one view — which means **two cache entries** |
| **The filter object is the cache key** | ⭐⭐ Day 273's key factory — different filters are different data |
| **`replace` while typing** | ⭐ Day 233 — otherwise Back is unusable |

# Part 2 — ⭐⭐ Offset vs cursor

```
⭐⭐ OFFSET PAGINATION IS WRONG ON ANY LIST THAT IS BEING WRITTEN TO.

⭐   GET /orders?limit=20&offset=0   ⇒ rows 1–20
⭐   ⭐ someone deletes row 5
⭐   GET /orders?limit=20&offset=20  ⇒ ⭐⭐ ROW 21 IS NOW ROW 20,
⭐     SO THE USER **NEVER SEES IT**. It was silently skipped.
⭐   ⭐ someone INSERTS a row instead ⇒ ⭐⭐ A ROW APPEARS TWICE.

⭐   ⇒ ⭐ NO ERROR. NO WARNING. ⭐⭐ THE USER SIMPLY DOES NOT SEE
⭐     SOME OF THEIR DATA, AND YOU CANNOT REPRODUCE IT ON DEMAND.
⭐   ⇒ AND `OFFSET 10000` MAKES POSTGRES COUNT AND DISCARD 10,000
⭐     ROWS ON EVERY REQUEST (Stage 5).
```

```python
# ⭐⭐ CURSOR (keyset) — stable, and it uses the index
@app.get("/orders")
async def list_orders(cursor: str | None = None, limit: int = 20):
    q = select(Order).order_by(Order.created_at.desc(), Order.id.desc())
    if cursor:
        ts, id_ = decode_cursor(cursor)
        q = q.where(tuple_(Order.created_at, Order.id) < (ts, id_))
        #   ⭐⭐ THE TIE-BREAK ON id IS NOT OPTIONAL — two rows with the
        #      same timestamp will otherwise repeat or vanish
    rows = (await db.execute(q.limit(limit + 1))).scalars().all()
    has_more = len(rows) > limit
    return {"items": rows[:limit],
            "next_cursor": encode_cursor(rows[limit - 1]) if has_more else None}
```

| ⭐ | Offset | ⭐⭐ Cursor |
|---|---|---|
| Stable under writes | ❌ ⭐⭐ skips + duplicates | ✅ |
| Deep-page performance | ❌ degrades linearly | ✅ ⭐ constant |
| "Jump to page 7" | ✅ | ❌ ⭐ **not possible** |
| Total count | ✅ | ⭐ Expensive — often show "20+" instead |

> ⭐ **Offset is acceptable for a small, stable, admin-only list where jumping to a page matters.** Say
> that trade out loud rather than treating cursor as dogma — **naming when the simpler thing is fine
> is what makes the other answer credible.**

# Part 3 — ⭐⭐ The search box

```
⭐⭐ WITHOUT DEBOUNCE, TYPING "invoice" = 7 REQUESTS.
⭐   ⭐ 20 users typing = 140 requests, ⭐⭐ EACH RUNNING A LIKE
⭐     QUERY ON YOUR DATABASE. ⭐ You have built a load generator
⭐     and pointed it at yourself.
⭐   ⇒ ⭐⭐ AND THE RESULTS RACE (Day 217): the response for "inv"
⭐     can land after the response for "invoice".
```

```typescript
const [input, setInput] = useState(filters.q);    // ⭐ instant, local
const debounced = useDebounce(input, 300);        // ⭐⭐ what gets QUERIED

useEffect(() => { set({ q: debounced }); }, [debounced]);   // ⭐ URL follows

// ⭐⭐ the query cancels superseded requests via its signal (Day 227)
const { data, isPending, isPlaceholderData } = useQuery({
  queryKey: keys.orders.list(filters),
  queryFn: ({ signal }) => client.GET("/orders", { params: { query: filters }, signal }),
  placeholderData: keepPreviousData,   // ⭐⭐ SHOW OLD RESULTS WHILE LOADING
});                                    //    ⇒ no flash to empty on every keystroke
```

| ⭐ Control | ⭐⭐ Effect |
|---|---|
| **Debounce 300 ms** | ⭐⭐ 7 requests → 1 |
| **`keepPreviousData`** | ⭐ The list stops flashing empty between queries — **the single biggest perceived-quality win in a search UI** |
| **Cancel superseded** | ⭐⭐ Kills the stale-response race |
| **Minimum length** | ⭐ Do not query on 1 character — it matches everything |
| **⭐⭐ Server-side limit** | Debounce is a *client* control. **The endpoint still needs a rate limit** — a client control is never a server guarantee (Day 236). |

# Part 4 — The list's states, for real

```
⭐⭐ SIX, NOT FOUR — A LIST HAS TWO EXTRA

⭐   ① LOADING (first time) ⇒ ⭐ skeleton ROWS, not a spinner
⭐   ② ⭐⭐ REFETCHING (has data) ⇒ ⭐ KEEP THE ROWS, add a subtle
⭐      indicator. ⭐⭐ NEVER REPLACE CONTENT WITH A SPINNER — that
⭐      is a layout shift AND it hides working data
⭐   ③ ERROR ⇒ message + retry, ⭐ keeping any rows you already had
⭐   ④ ⭐⭐ EMPTY — NEVER HAD ANY ⇒ "No orders yet" + [Create]
⭐   ⑤ ⭐⭐ EMPTY — FILTERED TO ZERO ⇒ "No orders match 'xyz'"
⭐      + [Clear filters]  ⇒ ⭐ DIFFERENT WORDS, DIFFERENT ACTION
⭐   ⑥ SUCCESS + more available ⇒ [Load more] / infinite scroll

⭐   ⇒ ⭐ ④ vs ⑤ IS THE ONE REVIEWERS NOTICE (Day 240).
```

> ⭐ **Infinite scroll vs a Load more button:** the button is better for a work tool — it keeps the
> footer reachable, it does not break the back button, and it does not fire requests while someone
> scrolls past. **Infinite scroll is for feeds.** Choose deliberately and say why.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how does pagination work in your app?"**

Lead with the failure that justifies the choice. **Cursor-based, because offset silently skips and
duplicates rows whenever the data changes between requests. If someone deletes a row while I'm on page
one, row twenty-one shifts into position twenty and the user never sees it. No error, no warning — they
just don't see some of their data, and it's not reproducible on demand. Offset also makes Postgres
count and discard ten thousand rows on every deep page.**

Then the implementation detail that shows you actually built it. **The cursor is the sort column plus
the id as a tie-break. Without the tie-break, two rows sharing a timestamp will repeat or vanish at the
page boundary — which is the same bug in miniature.**

Be fair about the trade. **The cost is that you can't jump to page seven, and a total count is
expensive. For a small admin list that's stable and where jumping matters, offset is genuinely fine —
I'd say that rather than treat cursors as dogma.**

Close on the search box. **Undebounced, typing "invoice" is seven requests, each running a LIKE query —
twenty users is a load generator pointed at my own database. So: three hundred milliseconds of debounce,
superseded requests cancelled, and previous results kept on screen while the new ones load so the list
doesn't flash empty on every keystroke. But debounce is a client control, so the endpoint is still rate
limited — a client control is never a server guarantee.**
