# Part 1 — ⭐ Two families of lock, and the six-word summary of each

```
⭐⭐ TABLE LOCKS — 8 modes. ⭐ You need to know 4 of them by heart:

⭐  MODE                        TAKEN BY                    CONFLICTS WITH
⭐  ACCESS SHARE                SELECT                      ⭐ only ACCESS
⭐                                                            EXCLUSIVE
⭐  ROW EXCLUSIVE               INSERT/UPDATE/DELETE        ⭐ SHARE and up
⭐  SHARE UPDATE EXCLUSIVE      VACUUM, ANALYZE,            ⭐ itself, and
⭐                              CREATE INDEX CONCURRENTLY,    stronger
⭐                              ALTER TABLE … VALIDATE
⭐  ⭐⭐ ACCESS EXCLUSIVE        ALTER TABLE, DROP,          ⭐⭐ ***EVERY-
⭐                              TRUNCATE, VACUUM FULL,        THING,
⭐                              REINDEX, most DDL             INCLUDING
⭐                                                            SELECT***

⭐⭐ THE PRACTICAL COMPRESSION — memorise THIS, not the 8×8 matrix:
⭐   ⭐ Readers and writers do NOT block each other. (MVCC — Day 194.)
⭐   ⭐ Writers on DIFFERENT rows do not block each other.
⭐   ⭐ Writers on the SAME row DO block each other.
⭐   ⭐⭐ ANYTHING TAKING ACCESS EXCLUSIVE BLOCKS ABSOLUTELY EVERYTHING.
⭐   ⭐ VACUUM/CREATE INDEX CONCURRENTLY block only each other and DDL.
```

```
⭐⭐ ROW LOCKS — 4 modes, and the two nobody knows are the ones that
⭐   cause the confusing incidents:

⭐  FOR UPDATE         ⭐ strongest. Blocks all other row locks.
⭐  FOR NO KEY UPDATE  ⭐ taken automatically by a plain UPDATE that
⭐                       does NOT change a key column.
⭐  FOR SHARE          ⭐ "I read this and it must not change."
⭐  ⭐⭐ FOR KEY SHARE   ⭐⭐ TAKEN AUTOMATICALLY ON A ***PARENT*** ROW
⭐                       WHEN YOU INSERT A CHILD ROW REFERENCING IT.
```

```
⭐⭐ AND THAT LAST ONE EXPLAINS AN INCIDENT YOU WILL OTHERWISE NEVER
⭐   SOLVE:

⭐   session A: INSERT INTO orders (user_id, …) VALUES (42, …);
⭐              ⇒ ⭐⭐ TAKES `FOR KEY SHARE` ON users WHERE id=42, to
⭐                stop that user being deleted mid-insert.
⭐   session B: UPDATE users SET email='…' WHERE id=42;
⭐              ⇒ ⭐⭐ ***BLOCKS.*** Until A commits.
⭐
⭐   ⇒ ⭐⭐ "WHY IS UPDATING A USER BLOCKED BY AN ORDER INSERT?" — and
⭐     nothing in either statement mentions locking. ⭐ On a hot parent
⭐     row (a tenant, a global counter, a popular product) this
⭐     serialises your whole application against one row.
⭐   ⭐ Mitigations: keep child-inserting transactions SHORT; do not
⭐     update parent rows in the same transaction as bulk child inserts;
⭐     ⭐⭐ and reconsider foreign keys to a single super-hot row (this
⭐     is one of the few honest arguments for dropping an FK).
```

# Part 2 — ⭐⭐ The queue, built in front of you

```
⭐⭐ RUN THIS. THREE PSQL WINDOWS. IT IS THE MOST IMPORTANT EXPERIMENT
⭐   IN THE STAGE.

⭐   A: BEGIN; SELECT * FROM orders LIMIT 1;   -- ⭐ holds ACCESS SHARE,
⭐                                             --   does not commit
⭐   B: ALTER TABLE orders ADD COLUMN x int;   -- ⭐⭐ WANTS ACCESS
⭐                                             --   EXCLUSIVE ⇒ WAITS
⭐   C: SELECT count(*) FROM orders;           -- ⭐⭐ ***ALSO WAITS.***

⭐⭐ C IS AN ORDINARY READ. IT CONFLICTS WITH NOTHING A IS HOLDING.
⭐   IT WAITS BECAUSE THE LOCK QUEUE IS ***FIFO*** AND B IS IN FRONT.

⭐   [ A: holds ACCESS SHARE ]
⭐        ↑
⭐   [ B: waiting ACCESS EXCLUSIVE ]  ⭐⭐ ← the wall
⭐        ↑
⭐   [ C: waiting ACCESS SHARE ]  ⭐ D, E, F, … every request, piling up
⭐
⭐ ⇒ ⭐⭐ THE ALTER TABLE TAKES 2 MILLISECONDS. THE OUTAGE LASTS AS LONG
⭐   AS A'S TRANSACTION. ⭐ And A can be an analytics query, a forgotten
⭐   psql window, or a Celery task that opened a session and went to
⭐   sleep (Day 194 ①).
⭐ ⇒ ⭐⭐ THIS IS *THE* MECHANISM BEHIND "THE MIGRATION TOOK THE SITE
⭐   DOWN". Not a slow migration — a fast one behind a slow reader.
```

```sql
-- ⭐⭐ THE FIX, AND IT IS TWO LINES IN EVERY MIGRATION YOU EVER WRITE:
SET lock_timeout = '3s';          -- ⭐ give up rather than queue
SET statement_timeout = '30s';    -- ⭐ and never run long under DDL
ALTER TABLE orders ADD COLUMN x int;
-- ⭐⭐ NOW THE FAILURE MODE IS "THE DEPLOY FAILED", NOT "THE SITE IS
--    DOWN". ⭐ That is the entire trade, and it is always worth taking.
-- ⭐ Then RETRY the migration in a loop — most attempts succeed within
--   seconds because the blocking reader finishes.
```

```python
# ⭐ In Alembic, so it applies to every migration and nobody can forget:
def run_migrations_online():
    ...
    with connectable.connect() as connection:
        connection.execute(text("SET lock_timeout = '3s'"))
        connection.execute(text("SET statement_timeout = '60s'"))
        context.configure(connection=connection, ...)
# ⭐⭐ PUT IT IN `env.py`, NOT IN INDIVIDUAL MIGRATIONS. A safety control
#    that each author must remember is not a safety control (Day 187).
```

# Part 3 — ⭐ `FOR UPDATE`, `SKIP LOCKED`, `NOWAIT`

```sql
-- ⭐ THE THREE BEHAVIOURS WHEN A ROW IS ALREADY LOCKED:
SELECT * FROM jobs WHERE id=1 FOR UPDATE;             -- ⭐ WAIT
SELECT * FROM jobs WHERE id=1 FOR UPDATE NOWAIT;      -- ⭐ ERROR at once
SELECT * FROM jobs WHERE status='pending'
  ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1; -- ⭐⭐ SKIP IT

-- ⭐⭐ `SKIP LOCKED` IS WHAT MAKES A DATABASE A WORK QUEUE (Day 166's
--    outbox relay, Day 159's scheduler). Ten workers each grab a
--    different row with NO coordination, NO broker, and NO possibility
--    of two workers taking the same job.
-- ⭐ It is also the only lock clause where you WANT to see fewer rows
--   than you asked for — `LIMIT 1` may return 0 rows while work exists.
--   ⭐⭐ Loop, don't assume "0 rows means the queue is empty".

-- ⭐ AND THE FK TRAP FROM DAY 172, NOW EXPLAINED:
SELECT * FROM orders WHERE id=1 FOR UPDATE;  -- with a JOIN to users
-- ⭐⭐ LOCKS THE JOINED `users` ROW TOO. Use `FOR UPDATE OF orders`.
```

# Part 4 — ⭐⭐ Deadlocks: how, how to read one, how to prevent them

```
⭐⭐ A DEADLOCK IS A CYCLE. Two transactions, two rows, opposite order:

⭐   A: UPDATE accounts SET … WHERE id=1;   ⭐ holds row 1
⭐   B: UPDATE accounts SET … WHERE id=2;   ⭐ holds row 2
⭐   A: UPDATE accounts SET … WHERE id=2;   ⭐ waits for B
⭐   B: UPDATE accounts SET … WHERE id=1;   ⭐⭐ waits for A ⇒ CYCLE

⭐ ⭐ Postgres runs a cycle detector after `deadlock_timeout` (1 s) and
⭐   ⭐⭐ KILLS ONE TRANSACTION with SQLSTATE 40P01, `ERROR: deadlock
⭐   detected`. ⭐ The other proceeds.
⭐ ⇒ ⭐⭐ SO A DEADLOCK IS ALWAYS AT LEAST A ONE-SECOND LATENCY SPIKE
⭐   BEFORE IT IS AN ERROR — which is why "we get occasional 500s AND
⭐   occasional slow requests" is often one problem, not two.
```

```
⭐⭐ READING THE LOG, WHICH TELLS YOU EXACTLY WHAT TO FIX:
⭐   ERROR:  deadlock detected
⭐   DETAIL: Process 4512 waits for ShareLock on transaction 88231;
⭐           blocked by process 4498.
⭐           Process 4498 waits for ShareLock on transaction 88230;
⭐           blocked by process 4512.
⭐   HINT:   See server log for query details.
⭐   ⭐⭐ SET `log_lock_waits = on` AND `deadlock_timeout = '1s'` SO THE
⭐     ***QUERIES*** APPEAR TOO. Without that you get pids and nothing
⭐     actionable — and pids are gone by the time you look.
```

```
⭐⭐ THE ONE PREVENTION RULE, AND IT IS SUFFICIENT:
⭐   ⭐⭐ ***ALWAYS ACQUIRE LOCKS IN A CONSISTENT ORDER.*** A cycle
⭐     requires two transactions to disagree about order. Remove the
⭐     disagreement and cycles become impossible.

⭐   ⭐ For a transfer: lock the LOWER account id first, always —
⭐     regardless of who is sending.
⭐   ⭐⭐ FOR A BULK UPDATE, THE ORM-SPECIFIC KILLER:
⭐        UPDATE items SET x=1 WHERE id IN (5,2,9);
⭐        ⭐⭐ THE ROWS ARE LOCKED IN WHATEVER ORDER THE PLAN RETURNS
⭐        THEM. Two concurrent statements with overlapping id sets can
⭐        deadlock even though neither wrote any code that "takes locks".
⭐        ⇒ ⭐⭐ FIX: `SELECT … WHERE id IN (…) ORDER BY id FOR UPDATE;`
⭐          first, THEN update. ⭐ Or sort the id list in Python before
⭐          issuing per-row updates.
⭐   ⭐ In SQLAlchemy: a `session.flush()` writes objects in a
⭐     deterministic-but-not-obvious order (insert order per mapper).
⭐     ⭐⭐ Two workers flushing overlapping sets is the same trap.
⭐     ⭐ Sort your collections before adding them.
⭐   ⭐ KEEP TRANSACTIONS SHORT. A cycle needs two transactions to
⭐     overlap in time; the shorter they are, the rarer that is.
⭐   ⭐⭐ AND RETRY ANYWAY. 40P01 goes in the SAME retry decorator as
⭐     40001 (Day 195) — deadlocks are a normal, expected outcome of
⭐     concurrency, not a defect to be eliminated to zero.
```

# Part 5 — ⭐⭐ Finding the culprit in thirty seconds

```sql
-- ⭐⭐ QUERY 1 — "WHO IS BLOCKING WHOM?" The only one you must memorise.
SELECT
    a.pid, a.state, now() - a.xact_start AS txn_age,
    ⭐ pg_blocking_pids(a.pid)      AS blocked_by,
    left(a.query, 80)              AS query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
   OR a.pid = ANY (SELECT unnest(pg_blocking_pids(p.pid))
                   FROM pg_stat_activity p)
ORDER BY txn_age DESC;
-- ⭐⭐ `pg_blocking_pids()` DOES THE ENTIRE pg_locks SELF-JOIN FOR YOU.
--    ⭐ Most blog posts still show the 30-line version. This is PG 9.6+.

-- ⭐ QUERY 2 — the head of the queue: the oldest transaction, blocking
--   or not. ⭐⭐ THE ROOT CAUSE IS ALMOST ALWAYS THE OLDEST ONE.
SELECT pid, state, now()-xact_start AS age, left(query,100)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5;

-- ⭐ QUERY 3 — what mode is actually held/waited on:
SELECT l.pid, l.mode, l.granted, l.relation::regclass, a.state
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.relation = 'orders'::regclass ORDER BY l.granted, l.pid;

-- ⭐⭐ AND THE TWO BUTTONS, IN ORDER:
SELECT pg_cancel_backend(4512);     -- ⭐ cancel the QUERY. Try first.
SELECT pg_terminate_backend(4512);  -- ⭐⭐ kill the CONNECTION. Rolls
                                    --   back the transaction. Use when
                                    --   cancel does nothing (an idle
                                    --   in transaction session has no
                                    --   query to cancel).
```

```
⭐⭐ THE PERMANENT SETTINGS THAT TURN THIS FROM ARCHAEOLOGY INTO A LOG
⭐   LINE — set them before you need them:
⭐   log_lock_waits = on               ⭐⭐ logs anything waiting longer
⭐                                       than deadlock_timeout, WITH the
⭐                                       query. Highest value here.
⭐   deadlock_timeout = '1s'           ⭐ the detection interval
⭐   log_min_duration_statement = '1s' ⭐ context around the wait
⭐   idle_in_transaction_session_timeout = '60s'   ⭐⭐ Day 194
⭐   statement_timeout = '30s'         ⭐ per-role for the app, higher
⭐                                       for the reporting role
```

```
⭐⭐ ADVISORY LOCKS — a mutex with no row attached (Day 159's cron):
⭐   SELECT pg_try_advisory_xact_lock(hashtext('nightly-report'));
⭐   ⭐ `_xact_` ⇒ released automatically at commit/rollback. ⭐⭐ USE
⭐     THIS FORM. The session-scoped `pg_advisory_lock` must be released
⭐     by hand and leaks forever if the process dies.
⭐   ⭐ `try_` ⇒ returns false instead of waiting. ⭐ "Someone else is
⭐     already running it" is usually the answer you want.
⭐   ⭐⭐ AND THE POOLER WARNING FROM DAY 186: A SESSION-SCOPED ADVISORY
⭐     LOCK THROUGH PGBOUNCER IN TRANSACTION MODE IS MEANINGLESS — you
⭐     may not get the same backend back. ⭐ Transaction-scoped is safe.
⭐   ⭐ The 64-bit key space is global and unpartitioned: ⭐⭐ hash a
⭐     namespaced string (`'myapp:job:nightly'`) so two features cannot
⭐     collide on the integer 1.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Believing a fast `ALTER TABLE` is safe | It queues behind any open reader, and everything queues behind it. |
| Running migrations without `lock_timeout` | The failure mode should be a failed deploy, not an outage. |
| Putting `lock_timeout` in individual migrations | Put it in `env.py`; a control each author must remember isn't one. |
| Being baffled that a user update blocks on an order insert | The child insert takes `FOR KEY SHARE` on the parent row. |
| Keeping foreign keys to a single super-hot row without thinking | It can serialise the whole application on that row. |
| `SELECT … FOR UPDATE` with a join | It locks the joined tables too. Use `OF <table>`. |
| Treating "0 rows" from `SKIP LOCKED` as "queue empty" | Rows may exist but be locked. Loop. |
| Trying to eliminate deadlocks entirely | They're a normal outcome of concurrency. Order locks, and retry. |
| Not logging queries with lock waits | `log_lock_waits = on`, or you get pids that are gone by the time you look. |
| `UPDATE … WHERE id IN (…)` from two workers | Rows lock in plan order. Sort with `ORDER BY id FOR UPDATE` first. |
| Handling 40001 but not 40P01 | Both belong in the same retry decorator. |
| Writing the 30-line `pg_locks` self-join | `pg_blocking_pids()` does it, since 9.6. |
| `pg_terminate_backend` as the first response | Try `pg_cancel_backend` first; terminate rolls back the transaction. |
| Session-scoped advisory locks | They leak if the process dies, and are meaningless through a transaction pooler. |
| Unnamespaced advisory lock keys | The key space is global; hash a namespaced string. |

## Interview questions

**Q: Why can a migration that takes two milliseconds cause a ten-minute outage?**

> Because the lock queue is FIFO and a waiting lock blocks everything behind it. `ALTER TABLE` needs
> ACCESS EXCLUSIVE, which conflicts with everything including plain `SELECT`. If any transaction is
> already holding ACCESS SHARE — a slow analytics query, a forgotten psql session, a Celery worker
> that opened a transaction and went to sleep — the ALTER waits. And every query that arrives after it
> queues behind the ALTER, even though those queries conflict with nothing that's actually held. So
> the DDL is instant and the outage lasts as long as the *pre-existing* transaction. The fix is two
> lines: `SET lock_timeout` to a few seconds and `statement_timeout` in the migration session, so the
> failure mode becomes a failed deploy instead of a down site, then retry the migration in a loop
> because most attempts succeed within seconds. I'd put those in Alembic's `env.py` rather than in
> individual migrations, since a safety control each author has to remember isn't a control.

**Q: An `UPDATE users` is blocked and the blocking query is an `INSERT INTO orders`. Explain.**

> The insert takes a `FOR KEY SHARE` lock on the referenced user row, because the foreign key means
> the parent must not disappear or have its key changed while the child is being created. So updating
> that user waits for the inserting transaction to finish. It's confusing because neither statement
> mentions locking and they're on different tables. It matters most on hot parent rows — a tenant row,
> a popular product, a global counter — where a stream of child inserts can effectively serialise any
> update to the parent, and it looks like a mystery contention problem. Mitigations are to keep the
> child-inserting transactions short, not to update parent rows in the same transaction as bulk child
> inserts, and in extreme cases to reconsider the foreign key to that one row — which is one of the
> few honest arguments for dropping an FK, and I'd want the orphan-detection job in exchange.

**Q: How do you prevent deadlocks?**

> Acquire locks in a consistent order, which is sufficient rather than merely helpful — a cycle
> requires two transactions to disagree about ordering, so removing the disagreement makes cycles
> impossible. For a money transfer that means always locking the lower account id first, regardless of
> who's sending. The case people miss is that they can deadlock without writing anything that looks
> like locking: `UPDATE items SET x = 1 WHERE id IN (5, 2, 9)` locks rows in whatever order the plan
> returns them, so two concurrent statements with overlapping id sets can cycle. The fix is to
> `SELECT ... ORDER BY id FOR UPDATE` first, or to sort the list before issuing the updates — and the
> same applies to an ORM flush over an unsorted collection. Beyond that, keep transactions short so
> overlap is rarer, and retry anyway: 40P01 goes in the same retry decorator as 40001, because
> deadlocks are a normal outcome of concurrency rather than a defect you drive to zero.

**Q: The application is hanging. Walk me through the first sixty seconds.**

> One query: `pg_stat_activity` filtered by `pg_blocking_pids()`, which does the whole `pg_locks`
> self-join for me and shows who's blocked and by whom. Alongside it I'd look at the oldest
> transaction by `xact_start`, because the root of a queue is almost always the oldest transaction,
> and its state tells me a lot — `idle in transaction` means an application bug, `active` with a long
> query means a runaway report. Then two buttons in order: `pg_cancel_backend` to cancel the query,
> and `pg_terminate_backend` only if that does nothing, which is the case for an idle-in-transaction
> session because there's no query to cancel. Afterwards, the durable fixes are settings rather than
> heroics — `log_lock_waits` so the queries appear in the log instead of just pids that are gone by
> the time anyone looks, `idle_in_transaction_session_timeout`, and a `statement_timeout` per role
> with a higher value for the reporting role.

**Q: How would you implement a job queue in Postgres?**

> `SELECT ... WHERE status = 'pending' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1`, then mark
> it in progress in the same transaction. `SKIP LOCKED` is what makes it work: ten workers each grab a
> different row with no coordination, no broker and no chance of two workers taking the same job.
> Three details matter. Zero rows returned doesn't mean the queue is empty — it may mean everything
> available is locked — so the worker loops rather than sleeping on that signal. The transaction has
> to stay short and must not span the actual work if the work is slow, or you hold the row lock across
> I/O. And the failure story needs a visibility timeout or a heartbeat, because a worker that dies
> mid-job rolls back and the row becomes available again, which is what you want, but a worker that
> hangs holds it indefinitely. It's the same mechanism behind the outbox relay, and for moderate
> volumes it's genuinely better than adding a broker — one fewer system with its own delivery
> semantics.

## 🎙️ Articulation drill

**Two minutes: "How do you debug a database that's hanging?"**

Lead with the queue, because it's the mechanism behind the most common serious incident: **locks are
FIFO, so a waiting `ALTER TABLE` blocks every read that arrives after it, and a two-millisecond
migration behind one slow `SELECT` takes the site down for as long as that `SELECT` runs.** Then the
diagnosis, in the order you'd actually do it: `pg_blocking_pids()` to get the blocking tree in one
query, the oldest `xact_start` because the root is almost always the oldest transaction, then cancel
before terminate. Then the durable half, which is what separates fixing an incident from preventing
one: `lock_timeout` in `env.py` so a bad moment fails the deploy instead of the site,
`log_lock_waits` so the log has queries rather than dead pids, and
`idle_in_transaction_session_timeout`. If you have time, add the fact that surprises people — **an
insert into a child table takes a lock on the parent row**, which is why updating a user can block on
an order insert, with nothing in either statement mentioning locks.
