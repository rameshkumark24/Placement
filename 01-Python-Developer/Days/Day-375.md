# Part 1 — ⭐⭐ Why logs cost what they do

```
⭐⭐ THE ECONOMICS, WHICH ARE UNLIKE METRICS ENTIRELY:
⭐   ⭐ A metric costs per ***series***: constant regardless of
⭐     traffic (Day 373).
⭐   ⭐ ⭐⭐ A LOG COSTS PER ***EVENT***: LINEAR IN TRAFFIC.
⭐   ⇒ ⭐ 10,000 rps × 5 log lines × 400 bytes = ⭐⭐ 20 MB/s =
⭐     ***1.7 TB PER DAY.*** ⭐ At typical vendor pricing that
⭐     is thousands of pounds a month for one service.
⭐   ⇒ ⭐⭐ WHICH IS WHY IT IS COMMON FOR THE LOGGING BILL TO
⭐     EXCEED THE COMPUTE BILL, AND WHY THAT SURPRISES PEOPLE
⭐     WHO HAVE NEVER LOOKED (Day 338).

⭐⭐ AND THE ASYMMETRY THAT MAKES IT WORSE:
⭐   ⭐ ⭐⭐ ADDING A LOG LINE IS THE CHEAPEST LOCAL DECISION AN
⭐     ENGINEER CAN MAKE, AND ITS COST LANDS ON A BILL NOBODY
⭐     ATTRIBUTES TO THEM. ⭐ So volume only ever grows.
⭐   ⇒ ⭐ The structural fix is a budget with an owner, ⭐⭐ AND A
⭐     PER-SERVICE VOLUME METRIC SO THE COST IS ***VISIBLE TO
⭐     THE TEAM THAT CREATED IT.***

⭐⭐ SO THE QUESTION FOR EVERY LOG LINE IS NOT "MIGHT THIS BE
⭐   USEFUL?" — ⭐⭐ IT IS ***"WHAT QUESTION WOULD I ANSWER WITH
⭐   THIS, AND COULD A METRIC OR A TRACE ANSWER IT MORE
⭐   CHEAPLY?"***
⭐   ⭐ "How many?" ⇒ ⭐⭐ A METRIC. Never a log you count later.
⭐   ⭐ "Where did the time go?" ⇒ ⭐⭐ A TRACE (Day 376).
⭐   ⭐ ⭐⭐ "WHY DID ***THIS SPECIFIC*** REQUEST DO THAT?" ⇒
⭐     ***THAT*** IS A LOG, AND IT IS THE ONLY THING LOGS ARE
⭐     UNIQUELY GOOD AT.
```

# Part 2 — ⭐⭐ Structured logging, and the shape that matters

```
⭐⭐ ❌ `logger.info(f"User {uid} bought {n} items for {total}")`
⭐   ⇒ ⭐ Unparseable at scale. ⭐⭐ TO ANSWER "WHICH USERS SPENT
⭐     OVER £500?" YOU NEED A REGEX, AND THE REGEX BREAKS THE
⭐     DAY SOMEONE REWORDS THE MESSAGE.

⭐⭐ ✔ `logger.info("purchase_completed", user_id=uid,
⭐   item_count=n, total_pence=total, currency="GBP")`
⭐   ⇒ ⭐ Queryable: `total_pence > 50000`. ⭐ Aggregatable.
⭐     ⭐⭐ AND THE MESSAGE BECOMES A ***STABLE EVENT NAME***
⭐     RATHER THAN PROSE, WHICH MEANS DASHBOARDS AND ALERTS
⭐     BUILT ON IT DO NOT BREAK WHEN SOMEONE IMPROVES THE
⭐     WORDING.

⭐⭐ THE FIELDS EVERY LINE SHOULD CARRY, AUTOMATICALLY:
⭐   ⭐ `timestamp` (⭐⭐ ISO 8601, UTC, WITH THE TIMEZONE
⭐     EXPLICIT), `level`, `event`, `logger`.
⭐   ⭐ ⭐⭐ `trace_id` AND `span_id` — ⭐ the join key to your
⭐     traces (Day 376). ⭐⭐ WITHOUT IT, LOGS AND TRACES ARE TWO
⭐     SEPARATE PRODUCTS YOU PAY FOR TWICE.
⭐   ⭐ `service`, `version`, `environment`, `pod`.
⭐   ⭐ ⭐⭐ `tenant_id` AND `user_id` — ⭐ high-cardinality, which
⭐     is exactly why they belong in ***logs*** and not in
⭐     metrics (Day 338's labels-vs-fields rule).
⭐   ⭐ `duration_ms` on anything that took time.

⭐⭐ AND THE PRINCIPLE THAT REPLACES MOST LOGGING ADVICE:
⭐   ***ONE WIDE EVENT PER UNIT OF WORK, WITH FIFTY FIELDS,
⭐      BEATS FIFTEEN NARROW LINES.***
⭐   ⇒ ⭐ Accumulate context through the request and emit ***once
⭐     at the end***: outcome, duration, user, tenant, cache
⭐     hits, rows returned, retries, downstream latencies.
⭐   ⇒ ⭐⭐ CHEAPER (one event instead of fifteen), MORE USEFUL
⭐     (everything correlated in one record), AND IT MAKES THE
⭐     UNANTICIPATED QUESTION ANSWERABLE — ⭐ which is Day 338's
⭐     definition of observability.
```

```python
# ⭐ structlog: context bound once, carried everywhere
import structlog

structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,   # ⭐⭐ ASYNC-SAFE
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso", utc=True),
        structlog.processors.format_exc_info,
        redact_secrets,                            # ⭐⭐ PART 5
        structlog.processors.JSONRenderer(),
    ],
)

@app.middleware("http")
async def logging_middleware(request, call_next):
    structlog.contextvars.clear_contextvars()      # ⭐⭐ MANDATORY
    structlog.contextvars.bind_contextvars(        # ⭐ on every line
        trace_id=get_current_trace_id(),
        request_id=request.headers.get("x-request-id", str(uuid4())),
        path=request.scope["route"].path if request.scope.get("route") else None,
        tenant_id=getattr(request.state, "tenant_id", None),
    )
    start = time.perf_counter()
    response = await call_next(request)
    log.info("http_request",                       # ⭐⭐ ONE WIDE EVENT
             status=response.status_code,
             duration_ms=round((time.perf_counter() - start) * 1000, 2))
    return response
```

```
⭐⭐ THE TWO PYTHON DETAILS THAT MATTER:
⭐   ① ⭐⭐ `contextvars`, NOT THREAD-LOCALS. ⭐ In async code a
⭐      thread serves many requests concurrently, ⭐⭐ SO A
⭐      THREAD-LOCAL CONTEXT LEAKS ONE REQUEST'S USER ID ONTO
⭐      ANOTHER REQUEST'S LOGS — ⭐ which is both a debugging
⭐      disaster and a privacy incident.
⭐   ② ⭐⭐ `clear_contextvars()` AT THE START. ⭐ Without it,
⭐      context from a previous request on the same task can
⭐      persist and you get silently wrong attribution.
```

# Part 3 — ⭐ Levels, and what they should mean

```
⭐⭐ MOST TEAMS USE FIVE LEVELS AND MEAN THREE THINGS. ⭐ Define
⭐   them by ***who acts***:
⭐   ⭐ ***ERROR*** ⇒ ⭐⭐ SOMETHING IS BROKEN AND A HUMAN SHOULD
⭐     EVENTUALLY LOOK. ⭐ If nobody ever looks at your ERRORs,
⭐     they are WARNs.
⭐   ⭐ ***WARNING*** ⇒ unexpected but handled — ⭐ a retry
⭐     succeeded, a fallback was used, ⭐⭐ A DEPRECATED PATH WAS
⭐     HIT.
⭐   ⭐ ***INFO*** ⇒ ⭐⭐ THE ***BUSINESS*** EVENTS: request
⭐     completed, order placed, job finished. ⭐ Not "entering
⭐     function".
⭐   ⭐ ***DEBUG*** ⇒ ⭐⭐ OFF IN PRODUCTION. ⭐ Often 80% of volume
⭐     and near-zero value (Day 338).
⭐   ⭐ ***CRITICAL*** ⇒ rarely useful; ⭐ if it means "page
⭐     someone", ⭐⭐ THAT IS AN ALERT'S JOB, NOT A LOG LEVEL'S.

⭐⭐ THE THREE RULES:
⭐   ① ⭐⭐ AN EXPECTED CONDITION IS NOT AN ERROR. ⭐ A 404 for a
⭐      mistyped URL, a 401 for a bad password, a validation
⭐      failure — ⭐⭐ THESE ARE INFO. ⭐ Logging them as ERROR is
⭐      how an error dashboard becomes meaningless.
⭐   ② ⭐⭐ LOG AN EXCEPTION ***ONCE***, WHERE IT IS HANDLED.
⭐      ⭐ Catching, logging and re-raising at three levels
⭐      produces three copies of one stack trace, ⭐⭐ AND MAKES
⭐      COUNTING ERRORS IMPOSSIBLE.
⭐   ③ ⭐⭐ RUNTIME-ADJUSTABLE LEVELS ARE WORTH BUILDING. ⭐ An
⭐      endpoint or signal that raises one logger to DEBUG for
⭐      ten minutes ⭐⭐ TURNS "REDEPLOY WITH MORE LOGGING" INTO
⭐      A THIRTY-SECOND ACTION DURING AN INCIDENT.
```

# Part 4 — ⭐⭐ The pipeline, and where it breaks

```
⭐⭐ THE STANDARD SHAPE:
⭐   ***APP → stdout → COLLECTOR → BUFFER → STORE → QUERY***
⭐   ⭐ ⭐⭐ APPS WRITE TO stdout. ***ALWAYS.*** ⭐ Not to files, not
⭐     directly to a remote endpoint.
⭐   ⇒ ⭐⭐ BECAUSE A DIRECT SHIPPER MAKES YOUR APPLICATION
⭐     DEPEND ON THE LOG BACKEND — ⭐ and when the backend is
⭐     slow, your ***requests*** get slow, which is a
⭐     spectacular way to convert an observability outage into a
⭐     product outage.
⭐   ⭐ Collector (Fluent Bit, Vector, Promtail) reads container
⭐     logs, parses, enriches, ships.

⭐⭐ THE FOUR PLACES IT BREAKS:
⭐   ① ⭐⭐ BACKPRESSURE. ⭐ The backend is slow; the collector
⭐      buffers; ⭐ the buffer fills; ⭐⭐ AND THEN IT EITHER
⭐      DROPS LOGS OR FILLS THE DISK. ⭐ Both are bad and you must
⭐      choose which, ***in advance***. ⭐⭐ DROPPING IS ALMOST
⭐      ALWAYS RIGHT — ⭐ a full disk takes the ***node*** down.
⭐   ② ⭐⭐ MULTILINE. ⭐ A Python traceback is fifteen lines, and
⭐      a naive collector ships fifteen ***separate events***,
⭐      ⭐⭐ SO THE ONE THING YOU MOST WANT TO READ IS THE ONE
⭐      THING THAT ARRIVES SHREDDED. ⭐ Configure multiline
⭐      joining — ⭐⭐ OR EMIT TRACEBACKS AS A JSON ***FIELD***,
⭐      WHICH SIDESTEPS IT ENTIRELY AND IS THE BETTER ANSWER.
⭐   ③ ⭐ Log rotation ⇒ ⭐⭐ CONTAINER LOGS ARE ROTATED BY THE
⭐      RUNTIME, AND A COLLECTOR THAT IS BEHIND WHEN ROTATION
⭐      HAPPENS LOSES DATA SILENTLY. ⭐ Size the rotation
⭐      generously.
⭐   ④ ⭐⭐ CLOCK SKEW AND INGEST DELAY ⇒ ⭐ events appear out of
⭐      order. ⭐⭐ ALWAYS SORT AND FILTER BY THE ***APPLICATION
⭐      TIMESTAMP***, NOT THE INGEST TIME, ⭐ or a correlation
⭐      you make during an incident will be wrong.

⭐⭐ AND THE COMPONENT PEOPLE FORGET TO MONITOR:
⭐   ⭐ ⭐⭐ THE COLLECTOR ITSELF: DROPPED-EVENT COUNT, BUFFER
⭐     USAGE, SHIP LATENCY. ⭐ A logging pipeline that silently
⭐     stops is worse than none, ⭐⭐ BECAUSE YOU WILL SEARCH AN
⭐     EMPTY WINDOW AND CONCLUDE NOTHING HAPPENED.
```

# Part 5 — ⭐⭐ What must never be logged

```
⭐⭐ THE PERMANENT LIST:
⭐   ⭐ ❌ Passwords, tokens, API keys, session cookies.
⭐   ⭐ ❌ Card numbers, CVVs, ⭐ bank details.
⭐   ⭐ ❌ ⭐⭐ FULL REQUEST BODIES ON AUTH ENDPOINTS — ⭐ that is
⭐     how passwords get logged without anyone deciding to log
⭐     passwords.
⭐   ⭐ ❌ ⭐⭐ `Authorization` HEADERS. ⭐ And note that a
⭐     ***partially*** redacted bearer token is often still
⭐     enough to be dangerous.
⭐   ⭐ ⚠️ PII — ⭐ names, emails, addresses — ⭐⭐ SUBJECT TO
⭐     RETENTION AND ERASURE OBLIGATIONS, AND LOGS ARE THE PLACE
⭐     PEOPLE FORGET WHEN HONOURING A DELETION REQUEST (Day 295).

⭐⭐ THE THREE MECHANISMS, AND YOU NEED ALL THREE:
⭐   ① ⭐⭐ A REDACTION PROCESSOR IN THE LOGGING PIPELINE — ⭐ a
⭐      denylist of key names (`password`, `token`, `secret`,
⭐      `authorization`, `card`) plus regexes for card-shaped
⭐      and JWT-shaped strings.
⭐   ② ⭐⭐ TYPES THAT CANNOT BE PRINTED: `SecretStr` (Day 372),
⭐      or a domain type whose `__repr__` masks itself.
⭐      ⭐⭐ THIS IS THE ONLY MECHANISM THAT WORKS ***BY
⭐      CONSTRUCTION*** RATHER THAN BY VIGILANCE.
⭐   ③ ⭐ A CI check that greps for obvious mistakes, ⭐ and a
⭐      periodic scan of the log store for secret-shaped strings
⭐      — ⭐⭐ WHICH IS THE ONLY CONTROL THAT FINDS WHAT THE
⭐      FIRST TWO MISSED.

⭐⭐ AND THE ONE PEOPLE DO NOT EXPECT:
⭐   ⭐ ⭐⭐ ERROR-REPORTING SDKs (SENTRY AND FRIENDS) ATTACH
⭐     LOCAL VARIABLES AND THE ENVIRONMENT TO EVERY EXCEPTION BY
⭐     DEFAULT. ⭐ Your database password is in `os.environ`;
⭐     a request handler's locals contain the raw body.
⭐   ⇒ ⭐⭐ CONFIGURE THE SCRUBBER DELIBERATELY, AND TEST IT BY
⭐     TRIGGERING AN EXCEPTION WITH A FAKE SECRET IN SCOPE.
⭐     ⭐ Almost nobody does this, and it is a five-minute check.
```

# Part 6 — ⭐⭐ Cost control that keeps the useful logs

```
⭐⭐ THE LEVERS, IN ORDER OF EFFECT AND ALL OF THEM SAFE:
⭐   ① ⭐⭐ DEBUG OFF IN PRODUCTION ⇒ ⭐ frequently 80% of volume.
⭐   ② ⭐⭐ ***SAMPLE SUCCESSES, KEEP ALL FAILURES.*** ⭐ 1% of
⭐      200s, 100% of 5xx and slow requests.
⭐      ⇒ ⭐⭐ NOBODY HAS EVER DEBUGGED A SUCCESSFUL REQUEST THEY
⭐        DIDN'T ALREADY KNOW ABOUT. ⭐ This is the single best
⭐        ratio of savings to lost value.
⭐      ⇒ ⭐⭐ AND SAMPLE ***CONSISTENTLY BY TRACE ID***, SO YOU
⭐        KEEP A ***WHOLE*** REQUEST'S LOGS OR NONE OF THEM —
⭐        ⭐ half a request's logs is worse than none, because it
⭐        implies a gap that isn't there.
⭐   ③ ⭐⭐ THE WIDE-EVENT REWRITE (Part 2) ⇒ fifteen lines
⭐      becomes one. ⭐ An 80–90% reduction with ***more***
⭐      information.
⭐   ④ ⭐ TIERED RETENTION: 7 days hot and searchable, ⭐ 30 days
⭐      warm, ⭐ a year as compressed JSON/Parquet in object
⭐      storage you can query with Athena when you truly must.
⭐   ⑤ ⭐ Drop noisy known-benign events at the ***collector***,
⭐      ⭐ so you do not pay to ship or store them.
⭐   ⑥ ⭐⭐ SHORTEN THE FIELDS: `msg` NOT `message`, ⭐ and drop
⭐      duplicated fields the collector already adds. ⭐ Boring
⭐      and it is 10–20%.

⭐⭐ AND THE GOVERNANCE THAT STOPS IT GROWING BACK:
⭐   ⭐ ⭐⭐ A PER-SERVICE VOLUME METRIC ON A DASHBOARD THE TEAM
⭐     OWNS, ⭐ with an alert on a step change — ⭐⭐ BECAUSE THE
⭐     CAUSE IS ALMOST ALWAYS A SINGLE LOG LINE ADDED IN A LOOP
⭐     LAST TUESDAY, AND IT IS TRIVIAL TO FIND IF YOU LOOK
⭐     WITHIN A DAY AND IMPOSSIBLE IF YOU LOOK IN A QUARTER.
```

# Part 7 — ⭐ Searching well, and the incident workflow

```
⭐⭐ THE WORKFLOW THAT ACTUALLY HAPPENS (Day 338's progression):
⭐   ① ⭐ An ***alert*** fires — a metric said something is wrong.
⭐   ② ⭐ A ***trace*** shows ***where*** the time or the error is.
⭐   ③ ⭐⭐ ***LOGS*** FOR THAT `trace_id` SHOW ***WHY***.
⭐   ⇒ ⭐⭐ WHICH IS WHY `trace_id` ON EVERY LINE IS THE SINGLE
⭐     HIGHEST-VALUE FIELD: ⭐ it converts "search two billion
⭐     lines for something relevant" into "show me these forty
⭐     lines".

⭐⭐ FOUR SEARCH HABITS WORTH HAVING:
⭐   ⭐ ⭐⭐ ALWAYS BOUND THE TIME RANGE FIRST. ⭐ An unbounded
⭐     query over a large store is slow, expensive, and in some
⭐     systems it is a self-inflicted outage.
⭐   ⭐ Filter on indexed fields (service, level, status) before
⭐     any full-text search.
⭐   ⭐ ⭐⭐ SEARCH FOR THE ***EVENT NAME***, NOT THE PROSE —
⭐     ⭐ which only works because Part 2 made the message a
⭐     stable identifier.
⭐   ⭐ ⭐⭐ SAVE THE QUERY THAT SOLVED AN INCIDENT INTO THE
⭐     RUNBOOK. ⭐ You will need it again, and the person who
⭐     needs it next will not be you.

⭐⭐ AND THE HONEST NOTE ON TOOLING:
⭐   ⭐ ⭐⭐ ELASTICSEARCH INDEXES EVERYTHING — ⭐ fast arbitrary
⭐     search, ⭐ expensive to run and store.
⭐   ⭐ ⭐⭐ LOKI INDEXES ONLY ***LABELS*** AND STORES THE BODY
⭐     COMPRESSED IN OBJECT STORAGE — ⭐ dramatically cheaper,
⭐     ⭐⭐ AND YOU MUST NARROW BY LABEL FIRST OR THE QUERY
⭐     SCANS. ⭐ That constraint is a feature: it enforces the
⭐     search habits above.
⭐   ⇒ ⭐⭐ THE CHOICE IS "DO WE PAY TO INDEX EVERYTHING, OR DO
⭐     WE ACCEPT A DISCIPLINE ABOUT HOW WE SEARCH?" — ⭐ and for
⭐     most teams the second is the better trade.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ f-string log messages | Unparseable at scale, and the regex breaks when someone rewords it |
| ⭐⭐ Fifteen narrow lines instead of one wide event | Costs more, correlates less, and can't answer unanticipated questions |
| ⭐⭐ Thread-locals for request context in async code | One request's user id leaks onto another's logs — a privacy incident, not just confusion |
| ⭐ No `clear_contextvars()` at request start | Context persists and attribution is silently wrong |
| ⭐⭐ No `trace_id` on log lines | Logs and traces become two products you pay for twice |
| ⭐ Logging expected conditions as ERROR | The error dashboard becomes meaningless |
| ⭐ Catch-log-reraise at three levels | Three copies of one trace, and error counts become impossible |
| ⭐⭐ Shipping logs directly from the app | A slow log backend makes your requests slow. Always stdout |
| ⭐⭐ No multiline configuration | A Python traceback arrives as fifteen separate events — the one thing you most want to read |
| ⭐ Sorting by ingest time | Clock skew and delay reorder events, and your incident correlation is wrong |
| ⭐⭐ Not monitoring the collector | It stops silently, you search an empty window, and conclude nothing happened |
| ⭐ Buffering to disk without a limit | A full disk takes the node down. Choose dropping, in advance |
| ⭐⭐ Full request bodies on auth endpoints | That's how passwords get logged without anyone deciding to |
| ⭐⭐ Default error-SDK settings | Sentry attaches locals and the environment — including your database password |
| ⭐ Sampling logs per line rather than per trace | Half a request's logs is worse than none; it implies a gap that isn't there |
| ⭐ No per-service volume metric | A log line added in a loop last Tuesday is trivial to find within a day and impossible in a quarter |

## Interview questions

**1. "Why are logs expensive?"**
> ⭐⭐ Because **they cost per event and scale linearly with traffic, while metrics cost per series and
> stay constant.** ⭐ Ten thousand requests a second with five lines each at four hundred bytes is
> **1.7 terabytes a day for one service** — which is why it's common for the logging bill to exceed the
> compute bill. ⭐⭐ And the asymmetry that makes it grow: **adding a log line is the cheapest local
> decision an engineer can make, and its cost lands on a bill nobody attributes to them.**

**2. "What makes a good log line?"**
> ⭐ Structured, with a stable event name rather than prose — so a dashboard built on it doesn't break
> when someone improves the wording — and fields you can query rather than regex. ⭐⭐ Better still:
> **one wide event per unit of work with fifty fields, rather than fifteen narrow lines.** Accumulate
> context and emit once at the end with outcome, duration, tenant, cache hits, retries. ⭐ It's cheaper,
> everything is correlated in one record, ⭐⭐ **and it's what makes the unanticipated question
> answerable.**

**3. "What's the Python-specific trap?"**
> ⭐⭐ **Thread-locals for request context in async code.** One thread serves many requests
> concurrently, so a thread-local binding leaks one request's user id onto another request's logs —
> ⭐⭐ **which is a privacy incident, not just a debugging annoyance.** ⭐ `contextvars` is the correct
> mechanism, and you must clear it at the start of each request or context persists and attribution is
> silently wrong.

**4. "How do you cut logging cost without losing value?"**
> ⭐ Debug off in production, which is often eighty percent of volume. ⭐⭐ **Sample successes and keep
> all failures — one percent of 200s, all 5xx and slow requests — because nobody has ever debugged a
> successful request they didn't already know about.** ⭐⭐ And **sample consistently by trace id**, so
> you keep a whole request's logs or none, since half a request implies a gap that isn't there. ⭐ Then
> the wide-event rewrite, which is an eighty percent reduction with *more* information, and tiered
> retention. ⭐ Plus a per-service volume metric, because a step change is trivial to find within a day
> and impossible within a quarter.

**5. "How do secrets end up in logs?"**
> ⭐ Three ways, and only one is deliberate. ⭐⭐ **Logging full request bodies on auth endpoints — that's
> how passwords get logged without anyone deciding to log passwords.** ⭐ `Authorization` headers in
> access logs. ⭐⭐ And the one people don't expect: **error-reporting SDKs attach local variables and
> the environment to every exception by default**, so your database password and the raw request body
> go to a third-party SaaS. ⭐ Mechanisms: a redaction processor, types that mask themselves in
> `__repr__` — which is the only one that works by construction — and a periodic scan of the store for
> secret-shaped strings.

**6. "Why write to stdout rather than shipping directly?"**
> ⭐⭐ Because a direct shipper makes your application depend on the log backend — **when the backend is
> slow, your requests get slow, which converts an observability outage into a product outage.** ⭐ stdout
> is a local, non-blocking write; the collector owns buffering, retries and backpressure. ⭐ And you have
> to decide in advance what the collector does when its buffer fills: ⭐⭐ **dropping is almost always
> right, because filling the disk takes the whole node down.**

## 🎙️ Articulation drill

**Two minutes.** Start with economics, because they drive every decision: **logs cost per event and
scale with traffic, while metrics cost per series and stay flat** — ten thousand requests a second with
five lines each is nearly two terabytes a day, which is why the logging bill often exceeds compute.
And the growth mechanism: **adding a log line is the cheapest local decision anyone can make, and the
cost lands on a bill nobody attributes to them.** So the question per line isn't "might this be
useful", it's **which signal answers this most cheaply — "how many" is a metric, "where did the time
go" is a trace, and "why did this specific request do that" is the only thing logs are uniquely good
at.** Then the shape: structured with a stable event name, and **one wide event per unit of work with
fifty fields rather than fifteen narrow lines** — cheaper, correlated, and it answers questions you
didn't anticipate. Name the Python trap: **thread-locals leak one request's user id onto another's
logs in async code, which is a privacy incident**, so contextvars, cleared per request. On cost:
**sample successes and keep all failures, consistently by trace id**, because half a request's logs is
worse than none. Close on the two things people get bitten by: **write to stdout, never ship from the
app, because a slow log backend otherwise makes your requests slow** — and **error-reporting SDKs
attach locals and the environment by default, so your database password goes to a third-party SaaS
unless you configure the scrubber and test it.**
