> ⭐⭐ **The sentence to own: a queue is not a guarantee. It is a place to put a message — and every
> property you actually wanted (not lost, not duplicated, not stale, not stuck) is something you add
> on top of it, deliberately, with a name.**

# Part 1 — ⭐⭐ You already have a queue

```sql
-- ⭐⭐ POSTGRES AS A QUEUE. Day 196 gave you the one clause that
--    makes it work; this is the whole implementation.
SELECT id, payload FROM tasks
 WHERE state = 'ready' AND run_after <= now()
 ORDER BY priority, run_after
 LIMIT 10
 FOR UPDATE SKIP LOCKED;                  -- ⭐⭐ no two workers collide
```

```
⭐⭐ WHAT THIS BUYS, AND IT IS MORE THAN PEOPLE ADMIT:
⭐   ⭐⭐ IT IS TRANSACTIONAL WITH YOUR DATA. Enqueue in the same
⭐     transaction as the write that caused it ⇒ ⭐⭐ PART 4 OF
⭐     TODAY SIMPLY DOES NOT EXIST FOR YOU.
⭐   ⭐ It is visible in SQL: "what is queued" is a query, not a
⭐     dashboard you have to install.
⭐   ⭐ It is in your backups and your PITR window (Day 200).
⭐   ⭐ It does ⭐ SEVERAL HUNDRED TO A FEW THOUSAND JOBS/SEC,
⭐     which is more than this project will ever need.

⭐⭐ WHAT IT COSTS:
⭐   ⭐ Bloat — a queue table is the highest-churn table you own,
⭐     so it needs an aggressive autovacuum setting (Day 194) and
⭐     completed rows must be deleted or partitioned away.
⭐   ⭐ No fan-out, no routing, no built-in scheduling UI.
⭐   ⭐ Polling adds latency unless you use LISTEN/NOTIFY.

⭐ ⇒ ⭐⭐ THE HONEST BAR FOR ADDING CELERY + REDIS: you need
⭐   scheduling, retries, routing and a worker model that already
⭐   exists, and you'd rather operate one more system than write
⭐   four hundred lines. ⭐ That is a real answer. "It's what
⭐   people use" is not.
```

```
⭐⭐ THE TRAP THAT DELETES YOUR TASKS — AND IT IS COMMON:
⭐   Redis as a Celery broker, on the same instance as your cache,
⭐   with `maxmemory-policy allkeys-lru` (Day 205).
⭐   ⇒ ⭐⭐ UNDER MEMORY PRESSURE, REDIS EVICTS YOUR QUEUE.
⭐     Not "delays". EVICTS. Your tasks are gone, silently, and
⭐     the only symptom is that some emails never arrived.
⭐   ⇒ ⭐⭐ RULE: THE BROKER REDIS AND THE CACHE REDIS ARE
⭐     DIFFERENT INSTANCES. The broker is `noeviction` with AOF
⭐     (Day 206); the cache is `allkeys-lru` with no persistence.
⭐     ⭐ They have opposite configurations because they have
⭐       opposite jobs.
```

# Part 2 — ⭐⭐ The acknowledgement, and the two ways to lose work

```
⭐⭐ CELERY'S DEFAULT IS `acks_late = False`:
⭐   worker receives ──► ⭐ ACK IMMEDIATELY ──► then runs the task

⭐   ⇒ ⭐⭐ THE WORKER IS KILLED MID-TASK — a rolling deploy, an
⭐     OOM kill, a spot instance reclaimed, `SIGKILL` after the
⭐     grace period — ⭐⭐ AND THE TASK IS SIMPLY GONE.
⭐     No error. No retry. No trace. Nothing to grep for.
⭐   ⭐ This is the single most common root cause behind
⭐     "we occasionally don't send the confirmation email".
⭐   ⭐⭐ AND IT HAPPENS ON EVERY DEPLOY, which is why the rate
⭐     correlates with release frequency and nobody notices.
```

```
⭐⭐ `acks_late = True`: ack AFTER the task returns.
⭐   ⇒ ⭐ A kill now means REDELIVERY, which is what you want.
⭐   ⇒ ⭐⭐ AND IT MEANS AT-LEAST-ONCE, SO EVERY TASK MUST BE
⭐     IDEMPOTENT (Day 263). ⭐ You are choosing duplicates over
⭐     losses ON PURPOSE, because ⭐⭐ ONE OF THOSE TWO PROBLEMS
⭐     HAS A FIX AND THE OTHER DOES NOT.

⭐⭐ AND IT INTRODUCES THE POISON MESSAGE:
⭐   a task that CRASHES the worker (segfault, OOM, unbounded
⭐   memory) is never acked ⇒ redelivered ⇒ crashes the next
⭐   worker ⇒ ⭐⭐ FOREVER, AND IT TAKES DOWN EVERY WORKER IN
⭐   ROTATION WHILE DOING IT.
⭐   ⇒ ⭐⭐ BOUND IT WITH A DELIVERY COUNT INCREMENTED ***ON
⭐     CLAIM***, NOT ON FAILURE (Day 263) — a process that dies
⭐     never reaches its own failure handler, so a counter in
⭐     the `except` block counts exactly zero of these.
```

```
⭐⭐ THE THIRD SETTING NOBODY READS: THE VISIBILITY TIMEOUT.
⭐   ⭐ SQS default 30 s · Celery-on-Redis default 1 HOUR.
⭐   ⇒ ⭐⭐ A TASK THAT RUNS LONGER THAN IT IS REDELIVERED ***WHILE
⭐     THE FIRST COPY IS STILL RUNNING***. Two copies. Concurrently.
⭐   ⇒ ⭐ The symptom is a duplicate charge or a duplicate export,
⭐     on exactly your slowest tasks, at exactly your busiest hour.
⭐   ⇒ ⭐⭐ RULE: VISIBILITY TIMEOUT > THE p99 DURATION OF THE
⭐     SLOWEST TASK ON THAT QUEUE — which is a reason to separate
⭐     queues by duration (Part 6), since one number must cover
⭐     everything sharing the queue.
```

# Part 3 — ⭐⭐ What goes in a message

```python
send_invoice.delay(invoice)        # ❌
send_invoice.delay(invoice.id)     # ⭐⭐ an ID, and nothing else
```

```
⭐⭐ THREE REASONS, AND THE SECOND ONE IS THE ONE THAT BITES:

⭐   ① ⭐ STALENESS — the message is a SNAPSHOT from enqueue time.
⭐     The row was edited while the message sat in a queue for
⭐     90 seconds, and your worker emails the old total.

⭐   ② ⭐⭐ VERSION SKEW ACROSS A DEPLOY. During a rollout you have
⭐     OLD workers and NEW producers at the same time, for minutes.
⭐     ⇒ New producer adds a field ⇒ old worker's deserialiser
⭐       rejects it ⇒ ⭐⭐ EVERY MESSAGE FAILS UNTIL THE ROLLOUT
⭐       FINISHES, and with `acks_late` they all retry into the
⭐       same wall.
⭐     ⇒ ⭐ An ID has no schema, so it has no skew. ⭐⭐ THE
⭐       CONSUMER READS THE CURRENT ROW WITH THE CURRENT CODE.

⭐   ③ ⭐ SIZE — brokers have message limits (SQS 256 KB), and
⭐     50,000 × 2 MB payloads is a memory incident in the broker,
⭐     not in your app, where you have no tooling.

⭐⭐ THE ONE LEGITIMATE EXCEPTION: when the value AT EVENT TIME
⭐   IS THE FACT (Day 187 — snapshot vs current). "The price the
⭐   customer was quoted" belongs in the message, because re-reading
⭐   it later gives a DIFFERENT AND WRONG answer.
⭐   ⇒ ⭐ Include it explicitly, name it `quoted_price_cents`, and
⭐     write the comment saying why. ⭐⭐ The default is an ID; the
⭐     exception is a deliberate snapshot.
```

```
⭐⭐ AND THE SERIALISER IS A SECURITY SETTING:
⭐   ⭐ `task_serializer = "pickle"` ⇒ ⭐⭐ ANYONE WHO CAN WRITE TO
⭐     THE BROKER GETS REMOTE CODE EXECUTION ON EVERY WORKER.
⭐     ⭐ And the broker is usually the box with the weakest auth
⭐       on your network, because "it's internal".
⭐   ⇒ ⭐ JSON. Always. Accept the inconvenience of not passing a
⭐     `datetime` directly — that inconvenience is the feature.
```

# Part 4 — ⭐⭐ The one line that enqueues a job for a row that does not exist

```python
with uow:
    job = create_job(...)
    notify_technician.delay(job.id)     # ⭐⭐ THE MESSAGE IS SENT NOW
    uow.commit()                        # ⭐ ...and this may still fail
```

```
⭐⭐ TWO BUGS, ONE LINE:
⭐   ① ⭐ THE COMMIT FAILS (a constraint, a deadlock, a 40001
⭐     retry — Day 195) ⇒ a worker processes a job that ⭐⭐ DOES
⭐     NOT EXIST. The error reads "job not found", which looks
⭐     like a data problem, so you go and look at the data.
⭐   ② ⭐⭐ THE COMMIT SUCCEEDS, BUT THE WORKER GOT THERE FIRST.
⭐     ⭐ The gap is microseconds — so it never reproduces locally,
⭐       where the worker is cold and your database is on the same
⭐       machine. ⭐⭐ IN PRODUCTION IT IS ~1% OF MESSAGES, FOREVER,
⭐       AND IT IS THE SAME "job not found" ERROR.
⭐   ⇒ ⭐⭐ ONE SYMPTOM, TWO CAUSES, BOTH INTERMITTENT. This is
⭐     among the most expensive bugs in this entire stage.
```

```
⭐⭐ THREE FIXES, IN INCREASING ORDER OF ACTUALLY BEING ONE:

⭐   ① ❌ `countdown=5` — "give the commit time to land".
⭐        ⇒ ⭐⭐ NOT A FIX. A SMALLER WINDOW. It converts a 1%
⭐          failure into a 0.01% failure, which is worse, because
⭐          now it is unreproducible AND rare enough to dismiss.

⭐   ② ⭐ `after_commit` — register the enqueue on the session's
⭐        commit event so it fires only if the commit succeeded.
⭐        ⇒ ⭐ Fixes bug ① and bug ② completely.
⭐        ⇒ ⭐⭐ BUT IF THE ENQUEUE ITSELF FAILS (broker down) THE
⭐          WORK IS LOST WITH THE ROW ALREADY COMMITTED — which is
⭐          the dual write again, just moved.

⭐   ③ ⭐⭐ THE OUTBOX (Day 263) — write the intent as a ROW in the
⭐        same transaction; a relay enqueues it.
⭐        ⇒ ⭐⭐ THE ONLY OPTION WITH A GUARANTEE rather than a
⭐          smaller window. ⭐ And if your queue IS Postgres
⭐          (Part 1), the outbox and the queue are the same table
⭐          and there is nothing left to solve.
```

# Part 5 — ⭐⭐ Retries, backoff, and the dead-letter queue nobody reads

```
⭐⭐ RETRY ONLY WHAT RETRYING CAN FIX:
⭐   ⭐ TRANSIENT  — timeout, 502/503, connection reset,
⭐     deadlock (40P01), serialisation failure (40001, Day 195)
⭐        ⇒ ⭐ RETRY, with backoff.
⭐   ⭐⭐ PERMANENT — ValidationError, 404, 403, a NOT NULL
⭐     violation, a missing row
⭐        ⇒ ⭐⭐ DO NOT RETRY. Five attempts buy you five identical
⭐          failures, five times the log noise, ⭐ and — the part
⭐          people miss — ⭐⭐ THEY OCCUPY WORKER SLOTS THAT REAL
⭐          WORK IS QUEUED BEHIND.
⭐   ⇒ ⭐ Which means your task code must DISTINGUISH them, which
⭐     means the error taxonomy from Day 256 is load-bearing here.
```

```
⭐⭐ BACKOFF, AND THE WORD THAT MATTERS IS `jitter`:
⭐   ⭐ 2^n seconds, capped, ⭐⭐ PLUS RANDOMISATION.
⭐   ⇒ ⭐⭐ WITHOUT JITTER: a provider goes down for 60 s, 40,000
⭐     tasks fail in that window, and they ALL RETRY IN THE SAME
⭐     SECOND. ⭐ You hand the recovering provider a thundering
⭐     herd and knock it over again — and now the outage is
⭐     partly yours.
⭐   ⭐ `retry_backoff=True, retry_jitter=True, retry_backoff_max=600`
```

```
⭐⭐ AND THEN THE MESSAGE DIES. WHERE DOES IT GO?
⭐   ⭐⭐ A DEAD-LETTER QUEUE WITH NO ALERT AND NO REPLAY TOOL IS
⭐     A DELETE WITH EXTRA STEPS — and worse, it is a delete you
⭐     believe is a safety net.
⭐   ⇒ ⭐ THREE REQUIREMENTS, ALL OF THEM:
⭐     ① an alert at depth > 0 (⭐⭐ not > 100 — the first one is
⭐        the interesting one)
⭐     ② enough context stored to diagnose: the args, the last
⭐        exception, the attempt count, the trace id
⭐     ③ ⭐⭐ A REPLAY COMMAND. Because the outcome of a DLQ is
⭐        always either "fix the bug and replay" or "decide it
⭐        doesn't matter" — and only one of those needs a tool.
```

# Part 6 — ⭐⭐ Topology, concurrency and the prefetch trap

```
⭐⭐ SPLIT QUEUES BY LATENCY CLASS, NOT BY FEATURE:
⭐   ⭐ `interactive` — under ~5 s, a human is waiting
⭐        (password reset, thumbnail, notification)
⭐   ⭐ `bulk`        — minutes, nobody is waiting
⭐        (export, reindex, monthly invoicing)

⭐⭐ WHY: ONE 40-MINUTE EXPORT IN A SHARED QUEUE PUTS A PASSWORD
⭐   RESET EMAIL BEHIND IT. ⭐ Feature queues (`billing`, `search`)
⭐   do not prevent that at all, because ⭐⭐ THE THING THAT HURTS
⭐   IS DURATION — SO PARTITION ON DURATION.
⭐   ⇒ ⭐ It also gives each queue its own visibility timeout
⭐     (Part 2), its own worker count, and its own alert
⭐     thresholds, all of which want different values.
```

```
⭐⭐ THE PREFETCH TRAP — "the queue is 5,000 deep and my workers
⭐   are at 12% CPU":
⭐   ⭐ Worker A has `prefetch_multiplier = 4`, concurrency 8
⭐     ⇒ it RESERVES 32 messages.
⭐   ⭐ Those 32 are each 5 minutes long.
⭐   ⇒ ⭐⭐ WORKERS B AND C SIT IDLE WITH AN EMPTY QUEUE WHILE
⭐     A CHEWS THROUGH ITS PRIVATE BACKLOG FOR TWO HOURS.
⭐   ⇒ ⭐⭐ FOR LONG TASKS, SET `worker_prefetch_multiplier = 1`.
⭐     ⭐ Prefetch is a throughput optimisation for tiny tasks;
⭐       on long tasks it is a load-balancing bug.
```

```
⭐⭐ CONCURRENCY, AND THE ARITHMETIC THAT SURPRISES PEOPLE:
⭐   ⭐ CPU-bound (image resize, PDF) ⇒ processes ≈ cores. More is
⭐     slower, not faster.
⭐   ⭐ I/O-bound (HTTP calls, waiting on a provider) ⇒ higher
⭐     concurrency, or async workers.
⭐   ⇒ ⭐⭐ BUT EACH CONCURRENT WORKER HOLDS A DATABASE CONNECTION:
⭐     6 workers × concurrency 16 = ⭐⭐ 96 CONNECTIONS FROM YOUR
⭐     "IDLE" QUEUE TIER — on top of the API's pool (Day 197).
⭐   ⇒ ⭐ This is how a background system that processes nothing
⭐     exhausts a database that is serving users perfectly well.
```

# Part 7 — ⭐⭐ The two numbers, and which one is honest

```
⭐   ⭐ QUEUE DEPTH is the leading indicator — it moves first.
⭐   ⭐⭐ OLDEST MESSAGE AGE IS THE TRUTHFUL ONE.

⭐⭐ WHY, IN TWO LINES:
⭐   ⭐ depth 5,000, oldest age 8 s  ⇒ ⭐ FINE. It is draining.
⭐   ⭐ depth 5, oldest age 40 min   ⇒ ⭐⭐ AN OUTAGE. Something
⭐     is stuck, or a poison message is looping, or every worker
⭐     for that queue died and nobody noticed because the depth
⭐     never looked scary.
⭐ ⇒ ⭐⭐ ALERT ON AGE. GRAPH THE DEPTH.

⭐ THE REST OF THE PANEL:
⭐   ⭐ task duration p95 BY TASK NAME (an aggregate hides the one
⭐     task that regressed)
⭐   ⭐ failure rate by task name and by error class
⭐   ⭐ retries per task — ⭐⭐ a task retrying 80% of the time and
⭐     eventually succeeding reports a 0% failure rate
⭐   ⭐ DLQ depth, alert at > 0
⭐   ⭐⭐ A WORKER HEARTBEAT / DEAD-MAN CHECK (Day 264) — because
⭐     "no workers are running" produces an empty graph, and an
⭐     empty graph looks exactly like a quiet Sunday.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Adding Celery + Redis without stating what it buys | `SELECT ... FOR UPDATE SKIP LOCKED` is transactional with your data and fast enough. |
| Broker and cache on one Redis with `allkeys-lru` | Memory pressure silently evicts your queue. Separate instances, opposite configs. |
| Leaving `acks_late=False` | Every worker kill during a deploy silently drops in-flight tasks. |
| `acks_late=True` without idempotent tasks | You chose duplicates; now you have to handle them. |
| Counting deliveries in the `except` block | A process that dies never reaches it. Count on claim. |
| Ignoring the visibility timeout | A task slower than the timeout runs twice, concurrently, on your slowest work. |
| Passing objects instead of IDs | Staleness, and a rollout where old workers can't deserialise new messages. |
| Never allowing a snapshot in the message | The quoted price *is* the fact. Include it deliberately and name it. |
| `pickle` as the serialiser | Broker write access becomes RCE on every worker. |
| `.delay()` before `commit()` | "Job not found", intermittently, in production only. Two distinct causes. |
| `countdown=5` as the fix | A smaller window, not a fix — and now it's unreproducible. |
| Retrying permanent errors | Zero extra successes, and worker slots stolen from real work. |
| Backoff without jitter | Forty thousand tasks retry in the same second and re-break the provider. |
| A DLQ with no alert | A delete with extra steps that you believe is a safety net. |
| A DLQ with no replay tool | You can diagnose it and do nothing about it. |
| Splitting queues by feature | Duration is what hurts. Split by latency class. |
| High prefetch on long tasks | One worker hoards the backlog while the others idle. |
| Sizing concurrency without counting connections | Workers × concurrency is a second pool against the same Postgres. |
| Alerting on queue depth | Depth 5 stuck for an hour is an outage; depth 5,000 draining is fine. Alert on age. |
| No worker heartbeat | "All workers dead" and "quiet Sunday" produce the same empty graph. |

## Interview questions

**Q: How do you decide between a Postgres queue and a real broker?**

> I start from what Postgres gives me for free: `FOR UPDATE SKIP LOCKED` is a working queue, it's
> transactional with my data — which deletes the whole class of enqueue-before-commit bugs — it's
> visible in SQL, it's in my backups, and it handles far more throughput than this project needs. So
> the broker has to buy something specific: scheduling, routing, fan-out, or a worker model I don't
> want to write. If it does, fine. What I won't accept as a reason is "it's what people use", because
> the queue table costs me one migration and the broker costs me an instance to operate forever.

**Q: What does `acks_late` change?**

> Where the acknowledgement happens relative to the work. With the default, the worker acks on
> receipt, so a kill mid-task loses the task with no error and no trace — and since that happens on
> every rolling deploy, the loss rate quietly tracks your release frequency. With `acks_late` the ack
> comes after the task returns, so a kill means redelivery. That's at-least-once, so every task has
> to be idempotent, and it introduces poison messages: a task that crashes the worker gets
> redelivered forever and takes down workers in rotation. The bound is a delivery counter incremented
> on claim, not on failure — because a process that dies never reaches its own failure handler.

**Q: Why not put the object in the message?**

> Three reasons, and the second is the one that causes incidents. Staleness — the message is a
> snapshot and the row moved on. Version skew — during a rollout you have old workers and new
> producers simultaneously, and a new field breaks deserialisation for every message until the
> rollout finishes, with retries piling into the same wall. And size limits. An ID has no schema, so
> it has no skew, and the worker reads the current row with the current code. The exception is when
> the value at event time *is* the fact — a quoted price — and then I put it in on purpose and name
> it so that it reads as a snapshot rather than an accident.

**Q: What's wrong with calling `.delay()` inside the transaction?**

> It's two bugs in one line with a single symptom. If the commit fails, a worker processes a row that
> doesn't exist. If the commit succeeds but the worker gets there first, you get exactly the same
> "not found" error, intermittently, only in production, because locally the worker is cold and the
> gap is microseconds. `after_commit` fixes both, but leaves the enqueue itself unguarded, so if the
> broker is down the row is committed and the work is lost — the dual write, moved. The outbox is the
> only version with a guarantee rather than a smaller window, and if the queue is Postgres, the
> outbox and the queue are the same table.

**Q: How do you know your queue is healthy?**

> Not by depth. Depth five thousand with an oldest-message age of eight seconds is a healthy system
> draining a spike; depth five with an oldest age of forty minutes is an outage — something is stuck
> or every worker for that queue is dead. So I alert on oldest-message age and graph depth. Then
> duration p95 per task name rather than in aggregate, failure rate by error class, retry counts —
> because a task that retries eighty percent of the time and eventually succeeds reports zero
> failures — DLQ depth alerting above zero, and a worker heartbeat, since "no workers running" and
> "quiet Sunday" produce the same empty graph.

## 🎙️ Articulation drill

**Three minutes: "Walk me through your async work."**

Open by refusing the default: **I already have a queue — `FOR UPDATE SKIP LOCKED` on a table — and
its best property is that it's transactional with my data**, which deletes an entire bug class. So a
broker has to buy something I can name. Then the guarantee, stated as a choice: the default
acknowledgement loses in-flight tasks on every worker kill, which means the loss rate tracks your
deploy frequency and nobody notices; `acks_late` converts that into redelivery, which is at-least-once,
**so I'm choosing duplicates over losses on purpose, because only one of those two has a fix.** Mention
poison messages and the counter incremented on claim, since a process that dies never runs its own
`except` block. Then messages carry IDs, not objects — and give the rollout reason, because staleness
is the obvious one and version skew is the one that causes the incident. Spend thirty seconds on
`.delay()` before commit: **two distinct bugs, one symptom, production-only**, and say that `countdown`
is a smaller window rather than a fix while the outbox is a guarantee. Close on operations: retry only
what retrying can fix, jitter or you re-break the provider you were waiting for, a DLQ needs an alert
at one and a replay command, queues split by duration rather than feature, and **alert on
oldest-message age, because depth five thousand and draining is fine while depth five and stuck for an
hour is an outage.**
