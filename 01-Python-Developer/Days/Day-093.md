# Day 093

**L-093** · 🧪 **pytest I** — discovery, assertion rewriting, ⭐⭐ **fixtures as dependency injection**, `conftest.py`, scope

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a pytest fixture is dependency injection — a test declares what it needs
> by naming it as a parameter, and pytest builds it, caches it according to scope, and tears it down
> — which is why the fixture system is the whole framework and everything else is a convenience.**
>
> ⭐ Two mechanisms today that look like magic until you see them: **assertion rewriting**, and
> **`conftest.py`**.

---

# Part 1 — ⭐ Discovery, and plain `assert`

```python
# tests/test_orders.py
from myapp.orders import total

def test_empty_order_totals_zero():
    assert total([]) == 0
```

```
⭐ DISCOVERY RULES — files, classes, functions:
⭐   files      test_*.py  or  *_test.py
⭐   classes    Test*      ⭐ and ⚠️ WITHOUT an __init__ method (pytest skips those)
⭐   functions  test_*
⭐   directories: whatever `testpaths` says, else the rootdir
⭐   ⇒ ⭐⭐ "my test is not running" is nearly always a name that does not match,
⭐        or a class with __init__.
```

```
⭐⭐ WHY YOU NEVER WRITE assertEqual AGAIN — ASSERTION REWRITING:
⭐   pytest imports your test modules through its own IMPORT HOOK, which REWRITES
⭐   THE AST: every `assert X` becomes code that records the sub-expressions
⭐   before evaluating the comparison.
⭐   ⇒ ⭐⭐ so a bare `assert a == b` FAILS WITH A FULL DIFF — which value, which
⭐        key, which element — where plain Python would only say AssertionError.
⭐   ⇒ ⭐ it is Day 073's "Python is introspectable" turned into a feature, and
⭐        it is the single biggest ergonomic reason pytest beat unittest.
⭐   ⇒ ⚠️ ⭐ CAVEAT: rewriting applies to TEST modules and to plugins that ask for
⭐        it. ⭐⭐ Assertions inside a HELPER module you import are NOT rewritten
⭐        ⇒ you get a bare AssertionError. Fix: pytest.register_assert_rewrite("myhelpers")
```

```python
assert result == expected                       # ⭐ full diff on failure
assert "error" in caplog.text                   # ⭐ substring, with context
assert user.email == "a@b.com", f"got {user!r}" # ⭐ a message when the diff is not enough
assert total == pytest.approx(0.3)              # ⭐⭐ FLOATS — Day 041. Always.
```

# Part 2 — ⭐⭐ Fixtures are dependency injection

```python
import pytest

@pytest.fixture
def user():                                  # ⭐ the fixture's NAME is the contract
    return User(email="a@b.com", is_active=True)

def test_active_user_can_order(user):        # ⭐⭐ ASK FOR IT BY NAME. pytest supplies it.
    assert can_order(user)
```

```
⭐⭐ WHAT JUST HAPPENED, AND WHY IT MATTERS MORE THAN IT LOOKS:
⭐   pytest inspects the test's SIGNATURE (Day 042's introspection), finds a
⭐   fixture with each parameter name, calls it, and passes the result.
⭐   ⇒ ⭐⭐ THAT IS DEPENDENCY INJECTION, and it gives you three things setUp
⭐        never could:
⭐        1. ⭐⭐ EACH TEST DECLARES EXACTLY WHAT IT NEEDS ⇒ you can read a test's
⭐           requirements from its signature alone.
⭐        2. ⭐ UNUSED SETUP IS NOT RUN. With setUp, every test pays for everything.
⭐        3. ⭐⭐ FIXTURES COMPOSE — a fixture can request other fixtures, so you
⭐           build a graph rather than a base-class hierarchy.
```

```python
@pytest.fixture
def db_session(engine):                     # ⭐⭐ FIXTURES REQUEST FIXTURES
    ...

@pytest.fixture
def user(db_session):                       # ⭐ and so on — pytest resolves the graph
    return create_user(db_session)

def test_x(user): ...                       # ⭐ gets engine → db_session → user, in order
```

```python
# ⭐⭐ SETUP AND TEARDOWN — a yield fixture IS a context manager (Day 052):
@pytest.fixture
def temp_table(db_session):
    table = create_table(db_session)        # ⭐ setup
    yield table                             # ⭐⭐ the test runs here
    drop_table(db_session, table)           # ⭐ teardown — ⭐⭐ runs even if the test FAILS
```

⭐⭐ **The teardown runs on failure**, which is the property that makes fixtures safe — the same
guarantee as `finally` (Day 059). ⚠️ ⭐ **It does not run if the setup itself raised**, which is
correct: there is nothing to tear down.

# Part 3 — ⭐⭐ Scope, and the trap inside it

```python
@pytest.fixture(scope="session")      # ⭐ once per test run
@pytest.fixture(scope="module")       # ⭐ once per test file
@pytest.fixture(scope="class")        # once per test class
@pytest.fixture                       # ⭐⭐ DEFAULT: function — once per test
```

```
⭐⭐ THE RULE, DERIVED FROM DAY 092'S "I" IN FIRST:
⭐   EXPENSIVE **AND IMMUTABLE**  ⇒ ⭐ session   (a started container, a compiled
⭐                                    schema, a loaded model file)
⭐   ANYTHING MUTABLE            ⇒ ⭐⭐ FUNCTION. No exceptions worth learning.
⭐
⭐   ⇒ ⚠️⚠️ ⭐⭐ THE TRAP: a session-scoped fixture returning a MUTABLE object is
⭐        SHARED BY EVERY TEST. One test appends to the list, another asserts its
⭐        length ⇒ ⭐⭐ PASSES ALONE, FAILS IN THE SUITE, OR FAILS ONLY IN A
⭐        CERTAIN ORDER. That is precisely the order dependence Day 092 called the
⭐        worst kind of flake, and this is where it usually comes from.
⭐   ⇒ ⭐⭐ THE STANDARD RESOLUTION FOR DATABASES: a SESSION-scoped ENGINE
⭐        (expensive, immutable) plus a FUNCTION-scoped TRANSACTION that is
⭐        ROLLED BACK after every test. ⭐ You pay the connection cost once and
⭐        still get a clean database per test. (Day 097 builds it.)
⭐   ⇒ ⚠️ ⭐ A narrower-scoped fixture cannot be requested by a wider-scoped one —
⭐        pytest raises ScopeMismatch. ⭐⭐ That error is pytest protecting you from
⭐        exactly this bug.
```

# Part 4 — ⭐⭐ `conftest.py`

```
tests/
├── conftest.py              ⭐⭐ fixtures for EVERY test below this directory
├── unit/
│   └── test_pricing.py
└── integration/
    ├── conftest.py          ⭐ fixtures for integration tests only (db, client)
    └── test_orders_api.py
```

```
⭐⭐ THE MECHANISM, SO IT STOPS BEING MAGIC: pytest AUTOMATICALLY IMPORTS every
⭐   conftest.py on the path from the rootdir down to a test file, before
⭐   collecting it. Fixtures defined there are available to every test below,
⭐   ⭐⭐ WITH NO IMPORT STATEMENT — and a nearer conftest OVERRIDES a further one.
⭐   ⇒ ⭐ that is why `from conftest import ...` is wrong and unnecessary.
⭐   ⇒ ⭐⭐ AND THE PRACTICAL USE OF OVERRIDING: define a real `client` at the top
⭐        and a fake one in a subdirectory, and every test underneath switches
⭐        with no edits.
```

```python
# tests/conftest.py
import pytest

@pytest.fixture(scope="session")
def settings():
    return Settings(database_url="postgresql://localhost/test", env="test")

@pytest.fixture
def anyio_backend():                   # ⭐ async tests (Day 097)
    return "asyncio"
```

⚠️ ⭐ **`conftest.py` is where fixtures go to become a mystery.** A 600-line root `conftest.py` with
forty fixtures is Day 089's `utils.py` in a new costume. ⭐⭐ **Keep fixtures close to the tests that
use them**, and push a fixture up a level only when a second directory genuinely needs it.

# Part 5 — ⭐ `autouse`, and the factory pattern

```python
@pytest.fixture(autouse=True)          # ⚠️ runs for EVERY test in scope, unrequested
def reset_registry():
    REGISTRY.clear()
    yield
    REGISTRY.clear()
```

⭐⭐ **`autouse` hides a dependency**, which is the exact opposite of what makes fixtures good. ⭐ Use
it only for **cross-cutting hygiene** — resetting a global, freezing the environment, failing the test
if a real network call is attempted. ⚠️ **Never for supplying data**: a test that mysteriously has a
user in the database is a test nobody can read.

```python
# ⭐⭐ THE FACTORY FIXTURE — the pattern that solves "but I need THREE users":
@pytest.fixture
def make_user(db_session):
    created = []
    def _make(email="a@b.com", **kwargs):        # ⭐ a fixture that RETURNS A FUNCTION
        user = User(email=email, **kwargs)
        db_session.add(user); db_session.flush()
        created.append(user)
        return user
    yield _make
    for u in created: db_session.delete(u)       # ⭐ it still cleans up

def test_admin_sees_all_orders(make_user):
    admin  = make_user(email="admin@x.com", is_admin=True)   # ⭐⭐ parameterised per test
    normal = make_user(email="user@x.com")
```

⭐⭐ **This is the most useful fixture pattern there is**, because it keeps the *arrangement* visible
inside the test — the reader sees that this test needs an admin and a normal user — while the
*plumbing* stays in the fixture. ⭐ It is the answer to the "one fixture per data shape" explosion.

```
⭐ BUILT-IN FIXTURES YOU GET FOR FREE (Day 094 uses them in anger):
⭐   tmp_path       ⭐⭐ a fresh Path per test — never write to the CWD
⭐   monkeypatch    ⭐⭐ patch attributes and env vars, auto-undone
⭐   capsys         captured stdout/stderr
⭐   caplog         captured log records
⭐   request        ⭐ metadata about the running test (and indirect parametrization)
⭐   pytestconfig   the resolved configuration
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Test not collected | ⭐ Name must match `test_*`; a `Test*` class must have no `__init__`. |
| `from conftest import fixture` | ⭐⭐ Never needed — pytest imports it and injects by name. |
| ⭐⭐ **Session-scoped mutable fixture** | ⭐⭐ Shared state ⇒ order dependence. Function scope. |
| Not understanding `ScopeMismatch` | ⭐ pytest refusing to let a wide fixture depend on a narrow one. |
| ⭐ `autouse` for data | ⭐⭐ Hides the dependency; the test becomes unreadable. |
| A 600-line root `conftest.py` | ⭐ Day 089's `utils.py` in disguise. Keep fixtures near their tests. |
| ⭐ A fixture per data variation | ⭐⭐ One **factory** fixture. |
| Asserts in an imported helper | ⭐ Not rewritten — `pytest.register_assert_rewrite`. |
| ⭐ `assert 0.1 + 0.2 == 0.3` | ⭐⭐ `pytest.approx` (Day 041). |
| Writing files into the repo | ⭐ `tmp_path`. |
| Teardown code after `yield` that must run on setup failure | ⭐ It will not — setup raised, so there is nothing to undo. |

## Interview questions

**Q: What is a pytest fixture?**
> Dependency injection for tests. A test declares what it needs by naming it as a parameter, and
> pytest finds a fixture with that name, calls it, passes the result and tears it down afterwards. The
> practical wins over `setUp` are that each test declares exactly what it needs — so you can read its
> requirements from the signature — that unused setup isn't run, and that fixtures compose, because a
> fixture can request other fixtures. You end up with a dependency graph rather than a base-class
> hierarchy.

**Q: How does `conftest.py` work?**
> pytest automatically imports every `conftest.py` on the path from the rootdir down to each test file
> before collecting it, so fixtures defined there are available below without any import — and a
> nearer `conftest` overrides a further one. That override behaviour is genuinely useful: a real
> client fixture at the top and a fake one in a subdirectory switches every test underneath with no
> edits. The failure mode is a 600-line root `conftest.py` where nobody can find anything, so I keep
> fixtures near the tests that use them and only promote one when a second directory needs it.

**Q: When would you use a session-scoped fixture?**
> When the thing is expensive *and* immutable — a started database container, a compiled schema, a
> loaded model file. Anything mutable stays function-scoped, because a session-scoped mutable object
> is shared by every test, and that's exactly how you get a test that passes alone and fails in the
> suite. The standard pattern for a database is both: a session-scoped engine, so you pay the
> connection cost once, and a function-scoped transaction that gets rolled back after each test, so
> every test still sees a clean database.

**Q: Why can you use a plain `assert` in pytest?**
> Because pytest imports test modules through its own import hook and rewrites the AST, so `assert a
> == b` becomes code that records the sub-expressions before comparing. That's what produces the full
> diff on failure instead of a bare `AssertionError`. The gotcha is that rewriting only applies to
> test modules and plugins that opt in — assertions inside a helper module you import give you the
> unhelpful bare error, and you fix that with `pytest.register_assert_rewrite`.

**Q: When is `autouse` appropriate?**
> Rarely, and only for cross-cutting hygiene: resetting a global registry, freezing the environment,
> or failing a test that attempts a real network call. It's inappropriate for supplying data, because
> it hides a dependency — and the whole value of fixtures is that a test's signature tells you what it
> needs. A test that mysteriously has a user in the database is one nobody can read or safely move.

## 🎙️ Articulation drill

Record two minutes: **"Explain pytest fixtures to someone who has only used `setUp`."**

⭐ **Name the idea first, because it reframes everything:** **"a fixture is dependency injection. The
test declares what it needs by naming it as a parameter, and pytest finds a fixture with that name,
builds it, passes it in, and tears it down afterwards."**

⭐⭐ **Then the three concrete advantages, each with its mechanism:** *"first, the test's signature is
its requirements — I can read what a test depends on without opening anything else, where with `setUp`
every test in the class silently gets everything. Second, unused setup isn't run, so tests don't pay
for things they don't touch. Third, and this is the big one, fixtures compose: a fixture can request
other fixtures, so you build a dependency graph instead of a base-class hierarchy — and inheritance
was always the wrong tool for 'this test needs a database and a logged-in user'."*

⭐⭐ **Then scope, because that's where the real bug lives:** *"scope decides how often a fixture is
built — function by default, up to session. The rule I use is: expensive and immutable can be
session-scoped; anything mutable stays function-scoped. A session-scoped mutable object is shared by
every test, and that's the classic 'passes alone, fails in the suite' flake. For a database I'd use
both — a session-scoped engine so the connection cost is paid once, and a function-scoped transaction
rolled back after each test so every test still sees a clean database."*

⭐ **Close on the piece that looks like magic:** *"and `conftest.py` isn't magic — pytest imports every
`conftest` from the rootdir down to the test file before collecting, which is why fixtures there need
no import and why a nearer one overrides a further one."*
