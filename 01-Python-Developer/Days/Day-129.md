# Part 1 — 🚪 ⭐⭐ The six answers

⭐ **Record each. Two minutes, no notes.** Same gate as Days 022, 077 and 101.

```
⭐⭐ 1. "WHAT HAPPENS WHEN A REQUEST HITS YOUR SERVER?"          (Days 103-106)
⭐   · the kernel completes the handshake; accept() returns a NEW socket per client
⭐   · ⭐⭐ TCP IS A STREAM — recv gives 1..n bytes, so you FRAME: delimiter for
⭐     headers, Content-Length for the body, close as the last resort
⭐   · ⭐ a read timeout and a size limit from the first version — both are
⭐     SECURITY controls (slowloris, OOM), not tidiness
⭐   · ⇒ ⭐ concurrency: threads, a bounded pool, or selectors — and the
⭐     production shape is processes for the cores, an event loop for the waiting

⭐⭐ 2. "WSGI OR ASGI — AND WHY DOES ASGI EXIST?"                 (Days 109, 110)
⭐   · WSGI: one callable, called once, returns an iterable of bytes
⭐   · ⭐⭐ THEREFORE no channel for further messages ⇒ WebSockets are IMPOSSIBLE,
⭐     not merely unimplemented; synchronous ⇒ an event loop cannot help;
⭐     no lifespan ⇒ lazy pools and no graceful shutdown
⭐   · ⭐ ASGI: a coroutine living as long as the connection, with receive/send
⭐     ⇒ ⭐⭐ all four limits dissolve from ONE design change
⭐   · ⭐⭐ and the honest half: ASGI is more capable AND easier to get wrong

⭐⭐ 3. "MAKE THIS PAYMENT ENDPOINT SAFE TO RETRY."               (Days 102, 122)
⭐   · ⭐⭐ a timeout does not mean failure — the response may have been lost
⭐   · something ALWAYS retries; you only choose whether it is safe
⭐   · ⇒ PUT with a client-chosen id, or POST with an idempotency key
⭐   · ⭐⭐ scoped per user, body fingerprinted, ATOMIC claim (SET NX), full
⭐     response stored so a replay is indistinguishable
⭐   · ⭐ and prefer a natural UNIQUE constraint when one exists

⭐⭐ 4. "WHAT IS THE MOST COMMON SERIOUS API VULNERABILITY?"      (Day 118)
⭐   · ⭐⭐ IDOR / broken object-level authorisation
⭐   · ⭐ it survives review because the endpoint IS authenticated — the missing
⭐     check is about the OBJECT, and nothing in the route's shape shows it
⭐   · ⇒ ⭐⭐ SCOPE THE QUERY BY THE ACTOR, so the unsafe version is unwriteable
⭐   · ⇒ ⭐ and test it: the "another user" row nobody writes

⭐⭐ 5. "HOW DO YOU DO AUTHENTICATION?"                           (Days 114-117)
⭐   · argon2id, tuned to ~150ms; ⭐ the threat model is an OFFLINE attacker
⭐   · ⭐⭐ constant-time login (hash a dummy) or you leak the user list
⭐   · sessions for a normal web app — ⭐⭐ because revocation works
⭐   · ⭐ JWT + refresh rotation with REUSE DETECTION when you need it
⭐   · ⭐⭐ "stateless auth" is stateful at the refresh token

⭐⭐ 6. "WHAT IS THE PRINCIPLE BEHIND INJECTION?"                 (Days 127, 128)
⭐   · ⭐⭐ data reaching a position where it is read as INSTRUCTIONS
⭐   · ⇒ the fix is never better escaping — escaping is context-specific and
⭐     the contexts multiply. ⭐⭐ USE A CHANNEL WHERE CODE AND DATA ARE SEPARATE
⭐   · ⭐ you have seen it five times: SQL, the shell, HTML, `alg=none`, `pickle`
```

⭐⭐ ARTEFACT 4 — THE PRODUCTION API.                             Days 119-128
