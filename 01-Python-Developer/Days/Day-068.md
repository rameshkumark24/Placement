# Day 068

**L-068** · ⭐⭐ **`multiprocessing`** — true parallelism, pickling costs, fork vs spawn, shared memory

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: processes give you real cores, and you pay for every byte that crosses
> between them.** The whole art is making the work per item large enough that the serialisation cost
> disappears.
>
> ⭐ This is the answer to CPU-bound Python (Day 065) — and the single most common way to get it
> wrong is to parallelise something dominated by data transfer, making it slower.

---

# Part 1 — ⭐ Real parallelism

```python
from multiprocessing import Pool

def heavy(n): return sum(i*i for i in range(n))

if __name__ == "__main__":              # ⭐⭐ MANDATORY — see Part 2. Not optional. Not style.
    with Pool() as pool:                # ⭐ defaults to os.cpu_count()
        results = pool.map(heavy, [10**6] * 8)
```

```
⭐⭐ WHY IT WORKS: N processes ⇒ N independent interpreters ⇒ ⭐⭐ N GILs ⇒ N cores.
⭐   ⇒ ⭐ the GIL is per-interpreter, so separate processes never contend (Day 065).
⭐   ⇒ ⭐⭐ and memory is isolated (Day 003), so there are NO RACES — the entire
⭐        category of bug from Day 067 does not exist here.
⭐
⭐ ⭐⭐ WHAT YOU PAY INSTEAD:
⭐   · process startup: ~10–100 ms each (spawn is the slow end)
⭐   · ⭐⭐ EVERY argument and EVERY result is PICKLED, sent over a pipe, and UNPICKLED
⭐   · memory: each process has its own interpreter, its own imports, its own heap
```

```python
pool.map(f, items)                 # ⭐ ordered, blocks, materialises everything
pool.imap(f, items)                # ⭐⭐ ordered, LAZY — results as they finish, in order
pool.imap_unordered(f, items)      # ⭐ as they finish, any order — fastest
pool.map(f, items, chunksize=100)  # ⭐⭐ THE tuning knob — see below
pool.apply_async(f, args)          # one call, with a future
pool.starmap(f, [(a,b), ...])      # multiple arguments
```

⭐⭐ **`chunksize` is the parameter that decides whether this helps at all.** With `chunksize=1` and
fast items, **you pay one round trip of IPC per item** and the pool is slower than a plain loop.
**Send batches: `chunksize = len(items) // (workers * 4)` is a reasonable starting point.**

# Part 2 — ⭐⭐ fork vs spawn — and the mandatory guard

| | ⭐ `fork` | ⭐⭐ `spawn` | `forkserver` |
|---|---|---|---|
| How | copy the process | ⭐⭐ **fresh interpreter, re-import the module** | fork from a clean server process |
| Speed | ⭐ fast | slow (~50–100 ms) | fast after the first |
| ⭐ Inherits state | ⭐⭐ **everything** — globals, open files, loaded modules | ⭐ almost nothing | minimal |
| ⭐⭐ Safe with threads | ⭐⭐ **NO** | ⭐ yes | yes |
| Default | ⭐ Linux (⚠️ **changing to `spawn` in 3.14**) | macOS, Windows | opt-in |

```
⭐⭐ WHY `if __name__ == "__main__":` IS MANDATORY:
⭐   under SPAWN, the child starts a fresh interpreter and RE-IMPORTS YOUR MODULE to find
⭐   the target function.
⭐   ⇒ ⭐⭐ without the guard, the module-level code that STARTED the pool runs AGAIN
⭐        in the child ⇒ which starts another pool ⇒ ⭐⭐ INFINITE PROCESS SPAWNING
⭐        until the machine gives up.
⭐   ⇒ ⭐ on Linux with fork it "worked", which is why the bug appears the day someone
⭐        runs it on macOS — or the day you upgrade to 3.14.
```

```
⭐⭐ WHY FORK + THREADS IS UNSAFE — and this is a genuine production hang:
⭐   fork() copies ONLY THE CALLING THREAD. Every other thread vanishes in the child.
⭐   ⇒ ⭐⭐ if one of them held a lock — the allocator's, logging's, a driver's —
⭐        that lock is now HELD FOREVER by a thread that does not exist.
⭐   ⇒ ⭐⭐ the child DEADLOCKS the first time it touches that subsystem.
⭐   ⇒ ⭐ symptom: a worker that hangs at startup, sometimes, under load. Nothing in the logs.
⭐   ⇒ ⭐⭐ THIS is why Python 3.14 changes the Linux default to `spawn`, and why you should
⭐        never fork from a process that has already started threads or opened DB connections.
```

⭐ **Set it explicitly rather than relying on the platform:**

```python
import multiprocessing as mp
mp.set_start_method("spawn", force=True)     # ⭐ once, at startup, inside the __main__ guard
```

# Part 3 — ⭐⭐ Pickling — the cost model

```
⭐⭐ EVERYTHING CROSSING A PROCESS BOUNDARY IS SERIALISED:
⭐   argument ─pickle─▶ pipe ─unpickle─▶ worker ─pickle─▶ pipe ─unpickle─▶ result
⭐   ⇒ ⭐⭐ FOUR conversions and two copies, per item.
```

```python
# ⚠️ ⭐⭐ THE CLASSIC MISTAKE — parallelising something dominated by transfer:
with Pool() as p:
    results = p.map(count_words, list_of_10mb_documents)
# ⭐⭐ 10 MB pickled + piped + unpickled per document. If count_words takes 50 ms,
#    you spend far longer moving the data than processing it ⇒ SLOWER than a loop.

# ⭐ THE FIX — send a REFERENCE, let the worker load it:
with Pool() as p:
    results = p.map(count_words_from_path, list_of_paths)    # ⭐⭐ send 40 bytes, not 10 MB
```

```
⭐⭐ THE RULE: multiprocessing pays off when
⭐        WORK PER ITEM  >>  (SERIALISE + TRANSFER + DESERIALISE)
⭐   ⇒ ⭐ big compute on small data  ⇒ ⭐⭐ excellent
⭐   ⇒ ⭐ small compute on big data  ⇒ ⭐⭐ worse than sequential
⭐   ⇒ ⭐⭐ MEASURE IT. The sequential baseline is the only honest comparison.
```

⚠️ ⭐⭐ **What cannot be pickled** — and Days 043/045 explain why:

| ⭐ Not picklable | ⭐ Do this instead |
|---|---|
| ⭐⭐ lambdas, closures, local functions | ⭐⭐ a **module-level** function, plus `functools.partial` |
| Open files, sockets, DB connections | ⭐ open them **inside** the worker |
| Locks, threads, generators | redesign |
| `functools.partial` of a lambda | `partial` of a named function |

⭐⭐ **`AttributeError: Can't pickle local object '<lambda>'` is the error you will hit**, and Day 043
already gave you the reason: a closure has no importable name, so the child has nothing to look up.
⭐ **`dill` and `cloudpickle` lift this restriction and are what Celery and Ray use.**

# Part 4 — ⭐ Sharing state, and the memory trap

```python
from multiprocessing import Value, Array, shared_memory, Manager

v = Value("i", 0)                    # ⭐ a shared C int, with a built-in lock
with v.get_lock():                   # ⭐⭐ still needed — `v.value += 1` is Day 067's race
    v.value += 1

arr = Array("d", 1000)               # ⭐ a shared C array

shm = shared_memory.SharedMemory(create=True, size=n_bytes)   # ⭐⭐ 3.8+
np_arr = np.ndarray(shape, dtype=np.float64, buffer=shm.buf)  # ⭐⭐ ZERO-COPY NumPy over it
# ⚠️ ⭐ you MUST shm.close() in each process and shm.unlink() ONCE, or the segment leaks
#    and survives your process — a real, findable-in-/dev/shm resource leak.

with Manager() as m:                 # ⭐ proxy objects: m.dict(), m.list(), m.Queue()
    d = m.dict()                     # ⚠️ ⭐⭐ EVERY access is an IPC round trip to a SERVER
                                     #    process ⇒ ~1000× slower than a plain dict.
```

⭐⭐ **`Manager` is convenient and slow.** It is a real server process, and each read or write is a
pickled round trip — **fine for coordination and configuration, catastrophic in a hot loop.**
⭐ `shared_memory` + NumPy is the right answer for large numeric data, because the array is never
copied at all.

```
⭐⭐ THE COPY-ON-WRITE TRAP (Day 026, and it belongs here):
⭐   parent loads a 2 GB model, forks 8 workers ⇒ EXPECTED 2 GB, ⭐⭐ ACTUAL creeping to 16 GB.
⭐   ⇒ ⭐⭐ because merely READING a Python object INCREFs it ⇒ writes the object header
⭐        ⇒ copies the page. ⭐⭐ Reading is a write, in CPython.
⭐   ⇒ ⭐ MITIGATIONS: gc.freeze() before forking (Day 027) · keep bulk data in NumPy or
⭐        mmap where the payload has no per-element refcount · or don't share by fork.
```

```
⭐⭐ WHEN NOT TO USE multiprocessing:
⭐   ✗ ⭐⭐ I/O-bound work — pure overhead; it was only ever waiting (Days 064, 066)
⭐   ✗ ⭐ small tasks — IPC dominates
⭐   ✗ large data per task — ⭐⭐ transfer dominates
⭐   ✗ shared mutable state — you are fighting the model
⭐   ✗ ⭐ when NumPy already does it — vectorised code releases the GIL and uses SIMD;
⭐        one core doing the right thing beats eight doing the wrong thing (Day 028)
```

⚠️ ⭐ **Always use a context manager or call `pool.close(); pool.join()`.** A leaked pool leaves
orphaned processes, and a worker that dies mid-task can leave the parent waiting forever — **bound it
with `pool.map(..., timeout=)` via `apply_async` or use `concurrent.futures` (Day 069), which handles
this better.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **No `if __name__ == "__main__"`** | ⭐⭐ Under spawn, infinite process spawning. |
| ⭐⭐ **Forking a process that has threads** | ⭐⭐ Locks held by vanished threads ⇒ deadlock in the child. |
| Relying on the platform default | ⭐ Set the start method explicitly. |
| Sending large objects to workers | ⭐⭐ Send a path or an id; load inside the worker. |
| `chunksize=1` for fast items | ⭐ One IPC round trip per item. |
| Passing a lambda or closure | ⭐⭐ Not picklable. Module-level + `partial`. |
| Passing an open connection | ⭐ Open it inside the worker. |
| `Manager().dict()` in a hot loop | ⭐⭐ Every access is an IPC round trip. |
| `v.value += 1` without the lock | ⭐ Day 067's race, across processes. |
| Forgetting `shm.unlink()` | ⭐ The segment leaks and outlives the process. |
| Expecting fork + COW to save memory | ⭐⭐ Refcounting writes to every page you read. |
| Using it for I/O | ⭐ Threads or asyncio. |

## Interview questions

**Q: Why does `multiprocessing` give real parallelism when threads don't?**
> Because the GIL is per interpreter, and each process has its own — so N processes are N interpreters
> on N cores with no contention. You also get memory isolation as a bonus: the entire category of race
> conditions simply doesn't exist, because there's nothing shared to race on. What you pay for is
> startup cost, per-process memory, and serialisation of everything that crosses the boundary.

**Q: What's the cost model?**
> Every argument and every result is pickled, written to a pipe, and unpickled — four conversions and
> two copies per item. So it pays off when the work per item greatly exceeds the transfer cost: big
> compute on small data is excellent, small compute on big data is slower than a sequential loop. The
> classic mistake is mapping over ten-megabyte documents where the function takes fifty milliseconds
> — you spend longer moving the data than processing it. The fix is to send a path or an id and let
> the worker load it. And I'd always measure against the sequential baseline, because it's the only
> honest comparison.

**Q: Why is `if __name__ == "__main__"` mandatory?**
> Because under `spawn`, the child starts a fresh interpreter and re-imports your module to find the
> target function. Without the guard, the module-level code that created the pool runs again in the
> child, which creates another pool, and you get unbounded process spawning until the machine gives
> up. On Linux with `fork` it appeared to work, which is exactly why the bug surfaces the day someone
> runs it on macOS — or when 3.14 changes the Linux default to spawn.

**Q: Why is forking a threaded process unsafe?**
> `fork` copies only the calling thread; every other thread disappears in the child. If one of them
> held a lock — the memory allocator's, logging's, a database driver's — that lock is now held forever
> by a thread that doesn't exist, so the child deadlocks the first time it touches that subsystem. The
> symptom is a worker that hangs at startup, sometimes, under load, with nothing in the logs. It's why
> you should never fork after starting threads or opening connections, and why the default is
> changing.

**Q: How do you share data between processes?**
> Prefer not to — the model is message passing, and fighting it is where the bugs are. If I must:
> `Value` and `Array` for small amounts of C-typed data, with explicit locking because `v.value += 1`
> is still a read-modify-write race. `shared_memory` with a NumPy array on top for large numeric data,
> which is genuinely zero-copy — remembering to `close` in each process and `unlink` exactly once, or
> the segment leaks and outlives the program. And `Manager` for convenience, knowing every access is
> an IPC round trip to a server process, so it's fine for coordination and catastrophic in a loop.

**Q: You fork eight workers after loading a 2GB model and memory grows to 16GB. Why?**
> Copy-on-write doesn't protect you, because reading a Python object increments its reference count,
> and that's a write into the object header — so touching the shared pages copies them. Within minutes
> each worker has privately copied most of what it walks over. Mitigations are `gc.freeze()` before
> forking, keeping the bulk data in NumPy or a memory-mapped buffer where the payload has no
> per-element refcounts, or not sharing by fork at all.

## 🎙️ Articulation drill

Record two minutes: **"Process ten thousand images. How?"**

⭐ Classify first: **image work is CPU-bound, so this needs real parallelism** — threads would give
none (Day 065), so a process pool sized to the core count. **Check the container's CPU limit rather
than `os.cpu_count()`** (Day 064).

⭐⭐ **Then the design detail that decides whether it helps:** *"I'd send file paths, not image data.
Every argument is pickled and piped, so mapping over decoded images means moving megabytes per item —
often more time than the processing. Sending a path is forty bytes and the worker opens the file
itself. And I'd set `chunksize`, because with one item per round trip the IPC dominates."*

⭐ Then the correctness details: **a `__main__` guard, because under spawn the child re-imports the
module and without it you get unbounded process spawning; and don't fork after starting threads or
opening database connections, because the child inherits locks held by threads that no longer exist.**

⭐⭐ **And close with the check that keeps you honest:** *"I'd measure against the sequential baseline
before shipping it. Parallelism has a real cost, and the outcome I'd want to rule out is that a
library like Pillow or NumPy is already releasing the GIL and using SIMD — in which case one core
doing the right thing beats eight doing the wrong thing."*
