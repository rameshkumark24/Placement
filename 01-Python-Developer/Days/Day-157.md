# Part 1 — ⭐⭐ `py-spy`: profiling a process you did not prepare

```bash
py-spy dump --pid 4211                    # ⭐⭐ INSTANT: every thread's stack, right now
py-spy top  --pid 4211                    # ⭐ live `top`, per function
py-spy record --pid 4211 -d 60 -o out.svg # ⭐⭐ a 60-second FLAME GRAPH
py-spy record --pid 4211 --idle           # ⭐ include threads that are WAITING
py-spy record --pid 4211 --subprocesses   # ⭐ gunicorn: profile the workers too
```

```
⭐⭐ WHY py-spy IS THE TOOL AND cProfile IS NOT, FOR THIS JOB:
⭐   ⭐ IT ATTACHES TO A RUNNING PROCESS. No restart, no code change, no
⭐        import, ⭐⭐ no redeploy — so you can use it DURING the incident.
⭐   ⭐⭐ IT READS MEMORY FROM OUTSIDE THE PROCESS (`process_vm_readv`), so
⭐        ⭐ THE GIL IS NEVER TAKEN AND YOUR SERVICE IS NOT PAUSED. Overhead is
⭐        ~1%. ⭐⭐ `cProfile` instruments every call and can be 2–10× slower —
⭐        ⭐ which does not just cost time, it CHANGES WHICH THING IS SLOW.
⭐   ⭐ SAMPLING, not tracing: it takes ~100 stack snapshots/sec. ⭐⭐ So it
⭐        finds what you spend TIME in, and is blind to a function that is
⭐        called a million times and returns instantly — ⭐ which is exactly
⭐        the trade you want in production.
⭐
⭐⭐ THE ONE-LINE DIAGNOSTIC THAT SOLVES MOST INCIDENTS — Day 082's ladder:
⭐   ⭐ CPU ~100%? ⇒ `py-spy top` ⇒ ⭐⭐ THE TOP FUNCTION IS YOUR ANSWER.
⭐   ⭐ CPU ~0% AND HUNG? ⇒ `py-spy dump` ⇒ ⭐⭐ EVERY THREAD'S STACK SHOWS
⭐        EXACTLY WHAT IT IS BLOCKED ON — ⭐ a socket read with no timeout, a
⭐        lock, `queue.get()`. ⭐⭐ `dump` on a hung process is the single
⭐        highest-value command in this entire day.
⭐
⭐ ⚠ ⭐ IN DOCKER/K8s IT NEEDS `SYS_PTRACE`:
⭐     `docker run --cap-add SYS_PTRACE`, or `kubectl debug` with a profiling
⭐     sidecar sharing the process namespace. ⭐⭐ SORT THIS OUT BEFORE THE
⭐     INCIDENT — ⭐ discovering you cannot attach, while the site is down, is
⭐     a bad time to learn about Linux capabilities.
```

# Part 2 — ⭐⭐ Reading a flame graph

```
⭐⭐ THE RULES, AND THEY ARE NOT OBVIOUS FROM LOOKING AT ONE:

⭐   ⭐ X AXIS IS **NOT TIME**. It is alphabetical, merged by stack. ⭐⭐ A wide
⭐        box does not mean "happened late"; it means "was on the stack in
⭐        many samples". ⭐ Everyone reads it as a timeline once.
⭐   ⭐⭐ WIDTH = TOTAL TIME ON THE STACK (inclusive — Day 100A's `cumtime`).
⭐   ⭐ HEIGHT = STACK DEPTH. ⭐⭐ Depth means nothing about cost.
⭐   ⭐⭐ WHAT YOU ARE LOOKING FOR IS A WIDE **PLATEAU** — a wide box with
⭐        NOTHING WIDE ABOVE IT. ⭐ That is where time is actually SPENT
⭐        (`tottime`), rather than merely passed through.
⭐
⭐   ⭐⭐ THREE SHAPES AND THEIR DIAGNOSES:
⭐    ▁▁▁███████▁▁▁   ⭐ one wide plateau  ⇒ ⭐⭐ ONE HOT FUNCTION. Best case:
⭐                                            fix one thing, win everything.
⭐    ███████████     ⭐ wide at the BOTTOM, ⇒ ⭐⭐ DEATH BY A THOUSAND CUTS.
⭐    ▁▂▁▃▁▂▁▄▁▂▁       thin everywhere above   No single fix; usually means
⭐                                            too many operations, i.e. an
⭐                                            ALGORITHMIC problem, not a
⭐                                            code-speed one.
⭐    ▁▁▁█▁▁▁█▁▁▁█▁   ⭐ the SAME narrow    ⇒ ⭐⭐ A LOOP CALLING SOMETHING
⭐                      tower repeated        EXPENSIVE — the N+1 shape again
⭐                                            (Day 136), seen from the CPU.
⭐
⭐⭐ AND THE PYTHON-SPECIFIC READING SKILL: IF THE WIDEST PLATEAU IS
⭐   `socket.recv` OR `select`, ⭐ YOU ARE NOT CPU-BOUND AT ALL — you are
⭐   waiting on I/O, and ⭐⭐ NO AMOUNT OF CODE OPTIMISATION WILL HELP.
⭐   ⭐ Run with `--idle` to see it; run without to see only CPU.
⭐   ⇒ ⭐⭐ THAT SINGLE DISTINCTION — "am I busy or am I waiting?" — DECIDES
⭐        WHETHER TODAY'S TOOLS OR Day 156's ARE THE RIGHT ONES.
```

# Part 3 — ⭐⭐ The memory-leak playbook

```
⭐⭐ FIRST, ESTABLISH WHICH OF THREE THINGS YOU HAVE, BECAUSE THE FIX DIFFERS:

⭐  1. ⭐ A TRUE LEAK — RSS rises monotonically and never returns. ⭐⭐ Objects
⭐       are still REFERENCED. Python has a GC, so this is almost never a
⭐       "leak" in the C sense — ⭐ it is a container you keep appending to.
⭐  2. ⭐⭐ FRAGMENTATION / ARENA RETENTION — RSS rises during a spike and
⭐       DOES NOT COME BACK DOWN, but plateaus. ⭐ Python's allocator does not
⭐       always return arenas to the OS. ⭐⭐ NOT A BUG, and chasing it wastes
⭐       days.
⭐  3. ⭐ LEGITIMATE GROWTH — a cache filling to its bound. ⭐⭐ Which is only
⭐       fine if the bound EXISTS.
⭐
⭐   ⇒ ⭐⭐ DISTINGUISH THEM WITH TIME: run for hours (Day 156's soak) and
⭐        look at the SHAPE. ⭐ Monotonic = 1. Step-then-flat = 2 or 3.

⭐⭐ THE FIVE USUAL CAUSES IN A PYTHON WEB SERVICE — check in this order:
⭐  1. ⭐⭐ AN UNBOUNDED MODULE-LEVEL DICT/LIST. `_cache = {}` with no eviction
⭐       and no TTL. ⭐ BY FAR THE MOST COMMON, and it is usually two lines
⭐       someone added "temporarily". ⭐⭐ Fix: `functools.lru_cache(maxsize=N)`
⭐       or move it to Redis with a TTL (Day 143).
⭐  2. ⭐⭐ `lru_cache` ON A METHOD. ⭐ `self` becomes part of the key, so
⭐       EVERY INSTANCE IS RETAINED FOREVER. ⭐⭐ A cache decorator that pins
⭐       objects — the sneakiest one on this list.
⭐  3. ⭐ AN EVER-GROWING LOGGER, list of tasks, or `set` of connections
⭐       (Day 144's manager without cleanup).
⭐  4. ⭐⭐ REFERENCE CYCLES CONTAINING `__del__` in older Pythons, or an
⭐       exception traceback retained in a variable — ⭐ a traceback references
⭐       every frame, and every frame references every local. ⭐⭐ One retained
⭐       exception can pin an entire request's worth of objects.
⭐  5. ⭐ A C EXTENSION LEAKING. ⭐⭐ Invisible to every Python-level tool,
⭐       because the objects are not Python objects. ⭐ Diagnosis: `tracemalloc`
⭐       shows FLAT Python memory while RSS climbs. That gap IS the finding.
```

```python
# ⭐⭐ tracemalloc — the right tool, and it compares SNAPSHOTS rather than
#    reporting totals, which is what makes it usable
tracemalloc.start(25)                       # ⭐ 25 frames of traceback
snap1 = tracemalloc.take_snapshot()
# ... let the service run for an hour ...
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:10]:
    print(stat)          # ⭐⭐ "+412 MB at app/services/cache.py:31"
```

```
⭐⭐ THE THREE-STEP PLAYBOOK, IN ORDER, BECAUSE ORDER SAVES HOURS:
⭐  1. ⭐ CONFIRM IT IS REAL: RSS over 24 h. ⭐⭐ If it plateaus, stop — you do
⭐       not have a leak, you have a working cache.
⭐  2. ⭐⭐ IS IT PYTHON OBJECTS OR NOT? `tracemalloc` growth vs RSS growth.
⭐       ⭐ Diverge ⇒ it is a C extension or fragmentation, and no Python tool
⭐       will find it.
⭐  3. ⭐ IF PYTHON: `compare_to` between snapshots names the LINE. ⭐⭐ Then
⭐       `gc.get_referrers()` on a sample object tells you WHO IS HOLDING IT,
⭐       which is the question you actually need answered.
⭐
⭐ ⭐⭐ AND THE PRAGMATIC MITIGATION WHILE YOU INVESTIGATE:
⭐   `--max-requests 1000 --max-requests-jitter 100` (gunicorn) recycles
⭐   workers. ⭐ It is a BANDAGE, and it is a legitimate one — ⭐⭐ it buys you
⭐   a week of sleep to find the cause properly. ⭐ The jitter matters: without
⭐   it every worker recycles at once (Day 142's herd, again).
```

# Part 4 — ⭐ Continuous profiling, and profiling in production safely

```
⭐⭐ THE PROBLEM WITH ALL OF THE ABOVE: IT REQUIRES YOU TO BE THERE. ⭐ The
⭐   regression happened at 3 a.m. on Tuesday and the process has restarted.

⭐   ⇒ ⭐⭐ CONTINUOUS PROFILING: sample ~1–2% continuously, ship to a store,
⭐        and ⭐ DIFF TWO TIME RANGES OR TWO VERSIONS.
⭐        ⭐⭐ "What changed between v41 and v42?" becomes a flame-graph DIFF,
⭐        which is a categorically better question than "what is slow now?"
⭐   ⭐ Tools: Pyroscope/Grafana Phlare, Datadog, `py-spy` on a timer to S3.
⭐   ⭐⭐ THE PAYOFF THAT JUSTIFIES IT: a canary (Day 155) can then be judged
⭐        on CPU-per-request PROFILE, not just on the number — ⭐ so you see
⭐        WHICH function got more expensive, on the release that caused it.

⭐⭐ SAFETY RULES FOR TOUCHING PRODUCTION:
⭐   ⭐ ⭐⭐ NEVER `cProfile` A PRODUCTION PROCESS. 2–10× overhead on a service
⭐        already under pressure is how a slowdown becomes an outage.
⭐   ⭐ profile ONE instance, not the fleet — ⭐ take it out of the load
⭐        balancer first if you can (Day 149's readiness flag makes this one
⭐        curl away, which is a nice payoff to notice).
⭐   ⭐⭐ `py-spy dump` IS SAFE AND INSTANT. ⭐ Reach for it first, always: it
⭐        costs nothing and answers "what is it doing right now?"
⭐   ⭐ ⭐⭐ `faulthandler.register(signal.SIGUSR1)` IN EVERY SERVICE, ALWAYS.
⭐        ⭐ Then `kill -USR1 <pid>` dumps every thread's traceback to stderr —
⭐        ⭐⭐ a free, dependency-free hang debugger you can use even where
⭐        `py-spy` cannot attach.
```

```
⭐⭐ AND THE OPTIMISATION LADDER, REVISITED FROM Day 100A WITH PRODUCTION
⭐   RUNGS ADDED — ⭐ note the order is by RETURN, and parallelism is still
⭐   last:
⭐   1. ⭐⭐ DO IT LESS OFTEN — cache (Day 143), batch, ⭐ delete the call.
⭐        ⭐⭐ The fastest code is the code that does not run, and the biggest
⭐        wins in real services are almost always here, not in the code.
⭐   2. ⭐⭐ FIX THE ALGORITHM / THE QUERY — the N+1, the missing index, the
⭐        O(n²) in a loop over request data.
⭐   3. ⭐ MOVE IT OFF THE REQUEST PATH — a queue (Day 142).
⭐   4. ⭐ USE A FASTER LIBRARY — `orjson`, a Rust-backed parser, Pydantic v2.
⭐   5. ⭐ OPTIMISE THE PYTHON — ⭐⭐ and by now you usually do not need to.
⭐   6. ⭐ ADD MACHINES — ⭐⭐ the honest last resort, and legitimately correct
⭐        when engineering time costs more than the instance does.
```

# Part 5 — ⭐ A worked incident

```
⭐⭐ "p99 WENT FROM 200 ms TO 4 s AT 14:00. NOTHING WAS DEPLOYED."

⭐  1. ⭐ METRICS (Day 147): p99 up, p50 FLAT, ⭐⭐ error rate flat, CPU flat.
⭐       ⇒ ⭐⭐ FLAT p50 + FLAT CPU = NOT A SPEED PROBLEM. Something is
⭐         QUEUEING for a resource. ⭐ Already this rules out half the tree.
⭐  2. ⭐ SATURATION metrics: ⭐⭐ DB POOL WAIT TIME is up 100×. Pool exhausted.
⭐  3. ⭐ TRACE (Day 148): the wide span is `db.acquire`, ⭐⭐ NOT the query.
⭐       ⇒ ⭐ so the database is fine; WE are out of connections.
⭐  4. ⭐⭐ `py-spy dump`: 38 of 40 threads are inside one endpoint, blocked in
⭐       `socket.recv` on an OUTBOUND HTTP call.
⭐  5. ⭐⭐ THE CAUSE: a third party got slow. Our call had NO TIMEOUT
⭐       (Day 152). Each request holds its DB connection while waiting on
⭐       HTTP — ⭐ Day 135's rule broken: DO NOT HOLD A LOCK OR A CONNECTION
⭐       ACROSS I/O.
⭐  6. ⭐ FIX NOW: add the timeout; open the circuit (Day 152). ⭐ FIX
⭐       PROPERLY: release the connection before the HTTP call.
⭐
⭐   ⇒ ⭐⭐ NOTICE WHAT NEVER HAPPENED: NOBODY PROFILED ANY PYTHON CODE. The
⭐        answer came from saturation metrics, one trace and one stack dump.
⭐        ⭐ Profiling is rung five; ⭐⭐ most production performance problems
⭐        are resolved on rungs one to four, and going straight to the
⭐        profiler is the most common way to waste an afternoon.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `cProfile` on a production process | 2–10× overhead turns a slowdown into an outage — and changes what's slow. |
| Reading the flame graph x-axis as time | It's alphabetical and merged. Width is total time on the stack. |
| Chasing the tallest tower | Depth means nothing. Look for a wide plateau with nothing wide above it. |
| Optimising code when the plateau is `socket.recv` | You're waiting, not busy. No code change helps. |
| Discovering `SYS_PTRACE` is missing during an incident | Sort out attach permissions before you need them. |
| Assuming rising RSS is a leak | Could be arena retention or a cache filling to its bound. Check the shape over 24 h. |
| Hunting a Python leak when `tracemalloc` is flat | The gap between it and RSS *is* the finding — a C extension or fragmentation. |
| `lru_cache` on a method | `self` is in the key, so every instance is retained forever. |
| A module-level dict with no bound | The most common leak in Python services, usually added "temporarily". |
| Keeping an exception in a variable | Its traceback pins every frame and every local in the request. |
| Treating `--max-requests` as a fix | It's a legitimate bandage that buys time — not a diagnosis. |
| `--max-requests` without jitter | Every worker recycles at once. |
| Profiling the whole fleet | Profile one instance, ideally out of the load balancer. |
| No `faulthandler` signal handler | A free hang debugger you didn't install. |
| Going straight to the profiler | Most production issues are saturation, not code speed. |
| Optimising code before removing the call | The fastest code is the code that doesn't run. |

## Interview questions

**Q: A production process is hung at 0% CPU. What do you run?**

> `py-spy dump --pid`. It attaches to a running process without any preparation — no restart, no
> code change, no imports — and prints every thread's current stack, which tells me exactly what
> each one is blocked on. Zero CPU and hung means waiting, so the stacks will show a socket read with
> no timeout, a lock acquire, or a `queue.get`. It's safe to run because py-spy reads the process's
> memory from outside with `process_vm_readv`, so it never takes the GIL and the service isn't
> paused — about one percent overhead. The prerequisite people discover too late is `SYS_PTRACE`
> capability in the container, which is a bad thing to learn about while the site is down. As a free
> backup I register `faulthandler` on SIGUSR1 in every service, so `kill -USR1` dumps every thread's
> traceback even where py-spy can't attach.

**Q: How do you read a flame graph?**

> Width is total time on the stack — inclusive, so a wide box may just be a caller. Height is stack
> depth and means nothing about cost, so chasing the tallest tower is a beginner mistake. And the
> x-axis is not time; it's alphabetical and merged by stack, so a wide box doesn't mean "happened
> late". What I'm looking for is a wide *plateau*: a wide box with nothing wide above it, because
> that's where time is actually spent rather than passed through. Three shapes matter: one wide
> plateau is one hot function and the best case; wide at the bottom with thin spikes everywhere is
> death by a thousand cuts, which usually means an algorithmic problem rather than slow code; and the
> same narrow tower repeated is a loop calling something expensive — the N+1 shape seen from the CPU
> side. And the Python-specific check: if the widest plateau is `socket.recv` or `select`, I'm not
> CPU-bound at all and no code optimisation will help.

**Q: RSS climbs all day. Walk me through diagnosing it.**

> Three steps, in order, because the order saves hours. First confirm it's real: watch over
> twenty-four hours and look at the shape. Monotonic growth is a leak; a step up during a spike that
> then plateaus is probably allocator arena retention, which isn't a bug and can waste days. Second,
> is it Python objects at all: compare `tracemalloc` growth against RSS growth. If Python memory is
> flat while RSS climbs, that divergence *is* the finding — it's a C extension or fragmentation, and
> no Python-level tool will ever show it. Third, if it is Python, `snapshot.compare_to` between two
> snapshots an hour apart names the line, and `gc.get_referrers` on a sample object tells me who's
> holding it, which is the question I actually need answered. Meanwhile I'd set `--max-requests` with
> jitter to recycle workers — a bandage, but a legitimate one that buys a week of sleep.

**Q: What are the usual causes of memory growth in a Python service?**

> An unbounded module-level dict or list is by far the most common — a `_cache = {}` with no eviction
> that someone added temporarily. Then `lru_cache` on a *method*, which is the sneaky one, because
> `self` becomes part of the cache key so every instance is retained forever — a cache decorator that
> pins objects. Then ever-growing collections of connections or tasks, like a WebSocket manager that
> never removes dead entries. Then a retained exception, because a traceback references every frame
> and every frame references every local, so one exception held in a variable can pin an entire
> request's worth of objects. And finally a C extension, which is invisible to every Python-level
> tool.

**Q: p99 jumped from 200 ms to four seconds with nothing deployed. Talk me through it.**

> Metrics first: p99 up but p50 flat, errors flat, CPU flat. Flat p50 and flat CPU means it isn't a
> speed problem — something is queueing, which already rules out most of the tree. So I'd look at
> saturation signals, and typically find the database pool wait time up a hundredfold. A trace
> confirms it: the wide span is connection acquire, not the query, so the database is fine and we're
> out of connections. Then `py-spy dump` shows most threads blocked in `socket.recv` inside one
> endpoint on an outbound HTTP call. The cause is a third party got slow, our call had no timeout,
> and each request was holding its database connection across that call — which is the rule about not
> holding a connection across I/O. Fix now is a timeout and a circuit breaker; fix properly is
> releasing the connection before the HTTP call. What's worth noticing is that nobody profiled any
> Python code — profiling is the fifth rung, and going straight to it is the most common way to waste
> an afternoon.

## 🎙️ Articulation drill

**Two minutes: "Production is slow. What do you do?"**

Do not start with a profiler — start with the branch. Is p50 up or only p99, and is CPU up or flat,
because flat CPU with rising latency means blocked rather than busy and that halves the search
immediately. Then saturation signals, then one trace compared against a fast one, then `py-spy dump`
because it's instant and free and answers "what is it doing right now". Only then a flame graph, and
say how you'd read it — a wide plateau, not the tallest tower, and `socket.recv` at the top means
stop optimising code. Close on the ladder and be honest about where the wins are: **do it less often,
fix the query, move it off the request path — and by the time you get to optimising Python you
usually don't need to.**
