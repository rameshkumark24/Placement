# Part 1 — ⭐⭐ Three probes, three questions

```
⭐⭐ THEY ARE NOT THREE FLAVOURS OF THE SAME THING. EACH HAS A DIFFERENT
⭐   CONSEQUENCE, AND THE CONSEQUENCE IS THE DEFINITION:

⭐  ⭐⭐ LIVENESS  → FAILURE MEANS: KILL AND RESTART THE CONTAINER.
⭐       ⭐ Question: "is this process wedged beyond recovery?"
⭐       ⭐⭐ ANSWER WITH ALMOST NOTHING. `return {"status": "ok"}`.
⭐       ⭐ It should fail ONLY for deadlock, an unrecoverable loop, or a
⭐         corrupted process. ⭐⭐ RESTARTING CANNOT FIX A BROKEN DATABASE —
⭐         so a database check here is not just useless, it is HARMFUL.
⭐
⭐  ⭐⭐ READINESS → FAILURE MEANS: STOP SENDING TRAFFIC. DO NOT KILL.
⭐       ⭐ Question: "can I serve a request RIGHT NOW?"
⭐       ⭐⭐ THIS is where dependencies belong — and even here, carefully
⭐         (Part 2).
⭐       ⭐ Recoverable: the pod rejoins automatically when it passes again.
⭐
⭐  ⭐ STARTUP   → FAILURE MEANS: still booting; ⭐⭐ SUPPRESS THE OTHER TWO.
⭐       ⭐ Exists for slow-starting apps. ⭐⭐ WITHOUT IT you must set a
⭐         liveness `initialDelaySeconds` long enough for the worst boot,
⭐         which means a genuinely wedged process is not detected for that
⭐         long, every time. ⭐ Startup probes decouple "slow to boot" from
⭐         "slow to detect death".
```

```
⭐⭐ THE INCIDENT THIS PREVENTS — say it exactly like this:

⭐   liveness → checks the database.
⭐   ⭐ the database has a 30-second blip (failover, a lock storm, Day 138).
⭐        ↓
⭐   ⭐ EVERY pod fails liveness SIMULTANEOUSLY — they share the dependency.
⭐        ↓
⭐   ⭐⭐ KUBERNETES KILLS EVERY POD AT ONCE.
⭐        ↓
⭐   ⭐ they restart, cold: empty caches, new connections, ⭐⭐ AND A THUNDERING
⭐        HERD OF CONNECTION ATTEMPTS AT THE DATABASE THAT IS ALREADY SICK.
⭐        ↓
⭐   ⭐⭐ THE DATABASE RECOVERS AFTER 30 s. YOUR SERVICE IS DOWN FOR TEN
⭐        MINUTES, IN A RESTART LOOP YOU BUILT YOURSELF.
⭐
⭐   ⇒ ⭐⭐ THE RULE: LIVENESS CHECKS *NOTHING* IT CANNOT FIX BY RESTARTING.
⭐        ⭐ A blip should degrade you, not decapitate you.
```

```python
@app.get("/healthz", include_in_schema=False)      # ⭐⭐ LIVENESS
async def healthz():
    return {"status": "ok"}                        # ⭐ that is the whole endpoint

@app.get("/readyz", include_in_schema=False)       # ⭐⭐ READINESS
async def readyz():
    if not app.state.ready:                        # ⭐⭐ Part 3 — the drain flag
        raise HTTPException(503, detail={"code": "draining"})
    checks = await run_checks()                    # ⭐ Part 2
    if any(c.critical and not c.ok for c in checks):
        raise HTTPException(503, detail={"code": "not_ready", "checks": ...})
    return {"status": "ready"}
```

# Part 2 — ⭐⭐ What readiness may check, and the trap inside it

```
⭐⭐ EVEN READINESS CAN TAKE YOU DOWN, VIA A DIFFERENT ROUTE:

⭐   ⭐ readiness checks the database, Redis, AND the payments provider.
⭐   ⭐ the payments provider has an outage.
⭐        ↓
⭐   ⭐⭐ EVERY POD GOES NOT-READY ⇒ THE LOAD BALANCER HAS ZERO HEALTHY
⭐        BACKENDS ⇒ ⭐ 100% OF TRAFFIC FAILS —
⭐   ⭐⭐ INCLUDING THE 95% OF ENDPOINTS THAT NEVER TOUCH PAYMENTS.
⭐
⭐   ⇒ ⭐⭐ THE RULE: READINESS CHECKS ONLY WHAT IS REQUIRED FOR *EVERY*
⭐        REQUEST. Usually: THE DATABASE, and often not even that.
⭐   ⇒ ⭐ Everything else is a DEPENDENCY HEALTH endpoint for humans and
⭐        dashboards — ⭐⭐ never wired to the load balancer.
⭐   ⇒ ⭐⭐ AND IT MUST BE **SHALLOW**: `SELECT 1`, not a real query, with a
⭐        SHORT TIMEOUT (~1 s) and ⭐ a cached result (2–5 s), because a probe
⭐        every 5 s × 40 pods × 3 dependencies is real load — ⭐⭐ and if your
⭐        health check is slow, the probe TIMES OUT and you take yourself down
⭐        for being busy.
```

```
⭐⭐ THE DEEPER PRINCIPLE, WHICH IS THE INTERVIEW ANSWER:
⭐   ⭐ A HEALTH CHECK THAT IS TOO STRICT CAUSES OUTAGES IT WAS MEANT TO
⭐     PREVENT. ⭐⭐ Cascading failure is usually built out of correct-looking
⭐     health checks: each one honestly reports "I depend on something that is
⭐     unhealthy", and the aggregate removes all capacity at once.
⭐   ⇒ ⭐⭐ PREFER PARTIAL DEGRADATION: serve what you can, fail the endpoints
⭐     that genuinely cannot work, and STAY IN THE POOL. ⭐ A pod serving 95%
⭐     of routes is worth infinitely more than no pod.
```

# Part 3 — ⭐⭐ Graceful shutdown, and the `sleep` that is not a hack

```
⭐⭐ THE SEQUENCE PEOPLE ASSUME:
⭐   SIGTERM → stop accepting → finish in-flight → exit. ⭐ Clean.
⭐
⭐⭐ THE SEQUENCE THAT ACTUALLY HAPPENS, AND THE RACE INSIDE IT:
⭐   1. ⭐ the orchestrator decides to remove the pod
⭐   2. ⭐⭐ IT DOES TWO THINGS **IN PARALLEL, NOT IN ORDER**:
⭐        a. sends SIGTERM to the container
⭐        b. removes the pod from the Service's endpoint list
⭐   3. ⭐⭐ (b) MUST THEN PROPAGATE — to kube-proxy on every node, to the
⭐        ingress controller, to nginx's upstream list, to any client-side
⭐        load balancer. ⭐ THAT TAKES HUNDREDS OF MILLISECONDS TO SECONDS.
⭐
⭐   ⇒ ⭐⭐ SO YOUR PROCESS BEGINS SHUTTING DOWN WHILE THE LOAD BALANCER IS
⭐        STILL SENDING IT NEW REQUESTS. ⭐ Those requests hit a closed
⭐        listener ⇒ CONNECTION REFUSED ⇒ ⭐⭐ 502s ON EVERY DEPLOY.
⭐        ⭐ This is Day 083's third way, and this is its actual mechanism.
```

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 15"]     # ⭐⭐ THE FIX, AND IT IS NOT A HACK
terminationGracePeriodSeconds: 60           # ⭐⭐ > preStop + longest request
```

```
⭐⭐ WHY `sleep` IS THE CORRECT ANSWER, STATED PROPERLY:
⭐   ⭐ `preStop` runs BEFORE SIGTERM is sent. So during those 15 seconds:
⭐        ⭐ the endpoint removal propagates everywhere
⭐        ⭐ the pod is STILL SERVING NORMALLY — nothing has been asked to stop
⭐   ⭐ THEN SIGTERM arrives, and by that point ⭐⭐ NO NEW TRAFFIC IS BEING
⭐        ROUTED TO YOU. Draining now succeeds.
⭐   ⇒ ⭐⭐ YOU ARE NOT SLEEPING TO "WAIT FOR THINGS TO SETTLE". YOU ARE
⭐        CLOSING A RACE BETWEEN TWO ASYNCHRONOUS SYSTEMS BY ORDERING THEM.
⭐        ⭐ Say it that way and it stops sounding like superstition.
⭐
⭐ ⭐⭐ THE ALTERNATIVE (better, more work): a SIGTERM handler that flips
⭐   `app.state.ready = False`, keeps serving, and waits for readiness to fail
⭐   twice before draining. ⭐ Same ordering, driven by observation instead of
⭐   a constant. ⭐⭐ Most teams use the sleep, and are right to.
```

```
⭐⭐ AND `terminationGracePeriodSeconds` MUST EXCEED preStop + YOUR LONGEST
⭐   REQUEST. ⭐ If it does not, SIGKILL arrives mid-request (Day 083) and you
⭐   have truncated exactly the slow, important work you were protecting.
⭐   ⭐⭐ DEFAULT IS 30 s. preStop 15 + a 40-second report = TRUNCATED, always.
```

# Part 4 — ⭐ Draining in Python: uvicorn, gunicorn, and PID 1 again

```
⭐⭐ WHAT UVICORN DOES ON SIGTERM (and it is good):
⭐   ⭐ stops accepting new connections
⭐   ⭐ finishes in-flight requests
⭐   ⭐ runs the lifespan SHUTDOWN handler (Day 133) — ⭐⭐ pools closed,
⭐        background tasks cancelled, connections released
⭐   ⭐ exits
⭐
⭐⭐ AND THE THREE WAYS YOU BREAK IT:
⭐  1. ⭐⭐ PID 1 (Day 083). `CMD python -m app` makes Python PID 1, and PID 1
⭐       ⭐ ONLY RECEIVES SIGNALS IT HAS INSTALLED A HANDLER FOR. Python
⭐       installs one for SIGINT and NOT for SIGTERM ⇒ ⭐⭐ `docker stop` DOES
⭐       NOTHING, you wait the full grace period, then SIGKILL. ⭐ Every
⭐       deploy truncates every in-flight request, silently.
⭐       ⇒ ⭐ FIX: `tini`/`dumb-init` as PID 1, or `CMD ["uvicorn", ...]` in
⭐         EXEC FORM. ⭐⭐ SHELL FORM (`CMD uvicorn ...`) puts `/bin/sh` at PID
⭐         1, which does not forward signals — ⭐ the same bug wearing a
⭐         different hat.
⭐  2. ⭐ A LONG `finally` or shutdown hook that exceeds the grace period.
⭐  3. ⭐⭐ BACKGROUND TASKS YOU NEVER TRACKED. `asyncio.create_task(...)`
⭐       with no reference: ⭐ not awaited at shutdown, so it is cancelled
⭐       mid-flight — ⭐⭐ and if it was writing to the database, you have a
⭐       partial write with no error anywhere. ⭐ Keep a task set and await it.
```

```python
# ⭐ THE THREE THINGS THE ASGI SIDE MUST DO
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.ready = True
    app.state.tasks = set()
    yield
    app.state.ready = False                      # ⭐ readiness fails immediately
    await asyncio.gather(*app.state.tasks, return_exceptions=True)   # ⭐⭐ finish work
    await app.state.engine.dispose()             # ⭐ release connections cleanly
```

```
⭐⭐ AND THE OTHER PROCESSES PEOPLE FORGET AT DEPLOY TIME:
⭐   ⭐ GUNICORN: SIGTERM = graceful (workers finish), ⭐ SIGQUIT = immediate.
⭐        ⭐⭐ `graceful_timeout` must exceed your longest request too.
⭐   ⭐ CELERY (Day 142): SIGTERM = warm shutdown, finishes the CURRENT task.
⭐        ⭐⭐ A 10-minute task with a 30-second grace period is KILLED, and
⭐        with `acks_late` it is REDELIVERED — ⭐ which is fine only because
⭐        you made it idempotent. ⭐⭐ This is where that discipline pays.
⭐   ⭐ WEBSOCKETS (Day 144): they do not "drain" — ⭐ they are open forever.
⭐        ⭐⭐ Close them explicitly with a reconnect code, or the grace period
⭐        expires and every client gets an abrupt reset.
```

# Part 5 — ⭐⭐ Startup, and the four ways a deploy still hurts

```
⭐⭐ STARTUP IS THE MIRROR IMAGE AND IS SKIPPED MORE OFTEN:

⭐  1. ⭐⭐ DO NOT REPORT READY BEFORE YOU ARE. If readiness passes while the
⭐       pool is still warming or the cache is empty, ⭐ the first 200 requests
⭐       hit a cold pod and time out — ⭐⭐ which, during a rolling deploy, is
⭐       a latency spike on every single release that nobody attributes to
⭐       this.
⭐  2. ⭐ CREATE POOLS IN LIFESPAN, AFTER THE FORK (Day 133). ⭐⭐ Not at
⭐       import time, and never under `--preload`.
⭐  3. ⭐⭐ FAIL FAST ON BAD CONFIG (Day 150). A missing env var must crash at
⭐       BOOT, not on the first request that needs it. ⭐ A pod that boots and
⭐       then 500s passes every probe you wrote.
⭐  4. ⭐ NO MIGRATIONS AT STARTUP (Day 138) — N replicas racing.

⭐⭐ AND THE FOUR REMAINING WAYS A DEPLOY HURTS EVEN WITH ALL OF THIS RIGHT:
⭐   ⭐ CONNECTION REUSE: keep-alive connections from nginx to a pod outlive
⭐        the endpoint change. ⭐⭐ Set `keepalive_timeout` below your preStop
⭐        sleep, or nginx reuses a socket to a draining pod.
⭐   ⭐ IN-FLIGHT BACKGROUND WORK (above)
⭐   ⭐ CACHE COLDNESS — ⭐⭐ a rolling deploy replaces every pod, so 100% of
⭐        your in-process caches are lost. ⭐ If p99 spikes for two minutes
⭐        after every deploy, this is why, and the fix is either a shared
⭐        cache (Day 143) or accepting it.
⭐   ⭐⭐ SCHEMA/CODE SKEW — old and new pods run together for the length of
⭐        the deploy. ⭐ Day 138's expand/contract exists for exactly this
⭐        window, and Day 143's cache key version exists for the same reason.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Checking the database in liveness | A 30-second blip restarts every pod at once and turns into a ten-minute outage. |
| Liveness and readiness pointing at the same handler | They answer different questions with different consequences. |
| Readiness checking non-essential dependencies | One third-party outage removes every backend, including for routes that don't use it. |
| A deep or slow health check | Probes time out and you take yourself down for being busy. `SELECT 1`, short timeout, cached. |
| No `preStop` hook | Endpoint removal races SIGTERM; the LB sends traffic to a closing listener. 502s every deploy. |
| `terminationGracePeriodSeconds` shorter than preStop + longest request | SIGKILL truncates the slow work you were protecting. |
| Python as PID 1 | It ignores SIGTERM entirely — every deploy waits the grace period then SIGKILLs. |
| `CMD uvicorn ...` in shell form | `/bin/sh` becomes PID 1 and doesn't forward signals. Use exec form. |
| Untracked `create_task` background work | Cancelled mid-write at shutdown, with no error anywhere. |
| Celery grace period shorter than the longest task | The task is killed and redelivered — survivable only because it's idempotent. |
| WebSockets left to the grace period | They never drain. Close them with a reconnect code. |
| Reporting ready before pools are warm | Every rolling deploy produces a latency spike nobody attributes to the deploy. |
| nginx `keepalive_timeout` above the preStop sleep | Reused connections still reach the draining pod. |
| No startup probe on a slow-booting app | You must inflate liveness delay, so real deadlocks go undetected for that long. |

## Interview questions

**Q: What's the difference between liveness and readiness?**

> They're defined by their consequences. Liveness failing means kill and restart the container, so it
> should only check things a restart can fix — deadlock, a wedged process. Readiness failing means
> stop routing traffic here but leave it alone, which is recoverable, so that's where a dependency
> check can live. The classic incident is putting a database check in liveness: the database has a
> thirty-second blip, every pod fails simultaneously because they share the dependency, Kubernetes
> kills all of them at once, they come back cold with empty caches and stampede the database that's
> already sick — and a thirty-second blip becomes a ten-minute self-inflicted outage. Restarting
> can't fix a broken database, so checking it there isn't just useless, it's harmful.

**Q: Is it safe to check dependencies in readiness?**

> Only the ones required for *every* request, and even then shallowly. If readiness checks the
> payments provider and they go down, every pod goes not-ready, the load balancer has zero healthy
> backends, and a hundred percent of traffic fails — including the ninety-five percent of endpoints
> that never touch payments. Cascading failures are usually built out of health checks that are each
> individually honest. So: readiness checks the database with `SELECT 1`, a one-second timeout and a
> cached result, and everything else goes on a dependency-status endpoint for humans that is never
> wired to the load balancer. The principle is that partial degradation beats removing capacity — a
> pod serving ninety-five percent of routes is worth infinitely more than no pod.

**Q: Why do you need a `sleep` in `preStop`? Isn't that a hack?**

> No — it's closing a race by imposing an order. When a pod is removed, the orchestrator sends
> SIGTERM and removes the pod from the endpoint list *in parallel*, and the endpoint removal then has
> to propagate to kube-proxy on every node, to the ingress, to nginx's upstream list. That takes
> hundreds of milliseconds to seconds. So without a preStop hook the process starts shutting down
> while the load balancer is still routing new requests to it, and those hit a closed listener as
> connection-refused — which is exactly why deploys produce 502s. `preStop` runs *before* SIGTERM, so
> during that sleep the pod is still serving normally while the removal propagates, and by the time
> SIGTERM arrives no new traffic is coming. The more precise version flips a readiness flag on
> SIGTERM and waits for the probe to fail twice, which is the same ordering driven by observation
> rather than a constant.

**Q: You `docker stop` your container and it takes ten seconds and kills everything mid-request. Why?**

> Python is PID 1 and PID 1 only receives signals it has explicitly installed a handler for. Python
> installs one for SIGINT but not SIGTERM, so `docker stop`'s SIGTERM is discarded entirely — nothing
> happens until the grace period expires and SIGKILL arrives, which can't be caught. So every deploy
> silently truncates every in-flight request. Two fixes: run an init like `tini` as PID 1, or use
> exec-form `CMD` so uvicorn itself is PID 1 and installs its own handlers. The subtle version of the
> same bug is shell-form `CMD`, which puts `/bin/sh` at PID 1, and it doesn't forward signals either.

**Q: What else breaks during a deploy even after all that?**

> Four things. Keep-alive connections from nginx outlive the endpoint change, so `keepalive_timeout`
> needs to be below the preStop sleep. Background tasks created with `create_task` and never tracked
> get cancelled mid-write with no error anywhere, so I keep a task set and await it in lifespan
> shutdown. In-process caches are lost on every pod, which is why p99 spikes for a couple of minutes
> after each release. And old and new code run simultaneously for the length of the rollout, which is
> the entire reason for expand/contract migrations and versioned cache keys.

## 🎙️ Articulation drill

**Two minutes: "How do you deploy without dropping requests?"**

Start with the probes, defined by consequence rather than by name, and lead with the anti-pattern
that makes the distinction land — a database check in liveness restarts your whole fleet over a
thirty-second blip. Then readiness, and the rule that it only checks what every request needs,
because a strict health check builds cascading failures out of honest signals. Then shutdown: name
the race between SIGTERM and endpoint propagation, and explain `preStop` as the fix that orders two
asynchronous systems. Add the grace period arithmetic. Close on PID 1 — **a Python process at PID 1
ignores SIGTERM entirely, so every deploy waits and then SIGKILLs** — and on the fact that old and
new code run together, which is why the migration and cache-key rules from earlier days exist.
