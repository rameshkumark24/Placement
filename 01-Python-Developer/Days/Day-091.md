# Day 091

**L-091** · ⭐ **Refactoring** — the smells catalogue, safe steps, and the strangler
**D-05** · Normalization — 1NF → BCNF, and deliberate denormalization

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: refactoring means changing structure without changing behaviour — so it
> is only refactoring if you have a way to know the behaviour did not change, which means the tests
> come first and are not optional.**
>
> ⭐ And today's quiet symmetry: **normalization is refactoring for data.** Both are the same
> principle — *one fact in one place* — and both have the same deliberate exception for performance.

---

# Part 1 — ⭐⭐ The definition, and the precondition

```
⭐⭐ REFACTORING = A BEHAVIOUR-PRESERVING TRANSFORMATION.
⭐   ⇒ ⭐⭐ "I refactored it and fixed the bug" IS NOT REFACTORING. It is two
⭐        changes, and it is the single most common way a "safe cleanup" ships
⭐        a regression — because nobody reviews a 400-line diff for behaviour.
⭐   ⇒ ⭐⭐ THE COMMIT RULE (Days 085, 088): REFACTOR AND BEHAVIOUR CHANGE ARE
⭐        NEVER THE SAME COMMIT. One is reviewed by reading; the other by testing.
⭐   ⇒ ⭐ Kent Beck's version, worth quoting: "make the change easy, then make
⭐        the easy change" — ⭐⭐ TWO COMMITS, IN THAT ORDER.
```

```
⭐⭐ THE PRECONDITION: HOW WILL YOU KNOW BEHAVIOUR DID NOT CHANGE?
⭐   · ⭐ there are tests           ⇒ run them after every step
⭐   · ⭐⭐ there are NO tests      ⇒ ⭐⭐ WRITE CHARACTERISATION TESTS FIRST:
⭐        tests that assert what the code CURRENTLY does — bugs included, without
⭐        judgement. ⭐ You are not documenting correct behaviour; you are
⭐        building a tripwire. ⭐⭐ If a characterisation test looks wrong, that is
⭐        a SEPARATE ticket, not something to fix while you are in here.
⭐   · ⭐ you cannot test it at all ⇒ ⭐⭐ then you are not refactoring, you are
⭐        rewriting and hoping. Say so out loud, and get the smallest seam under
⭐        test first (Day 095).
```

⭐⭐ **This is why refactoring appears in Stage 2 next to testing rather than next to clean code.**
**Without tests, "refactoring" is a synonym for "changing things I believe are equivalent"** — and the
whole value of the practice is that belief is replaced by evidence.

# Part 2 — ⭐⭐ The smells, Python-flavoured

| ⭐ Smell | ⭐ What it looks like | ⭐⭐ The move |
|---|---|---|
| Long function | won't fit on a screen; you describe it by listing steps | extract function |
| ⭐ Long parameter list | 5+ params | ⭐ introduce a parameter object (Day 057) |
| ⭐⭐ **Data clump** | `start, end, tz` appear together **everywhere** | ⭐⭐ they are one concept — name it |
| ⭐⭐ **Primitive obsession** | `str` that is really an email; `float` that is money | ⭐⭐ a value object (Days 041, 057) |
| ⭐ Stringly typed | `if status == "shipped"` | ⭐ an `Enum` (Day 058) |
| Feature envy | a method that mostly touches *another* object's data | move it to that object |
| ⭐⭐ **Shotgun surgery** | one change ⇒ edits in eight files | ⭐⭐ the concept is scattered — gather it |
| Divergent change | one module edited for unrelated reasons | ⭐ split it; it has two jobs |
| ⭐ Temporal coupling | must call `init()` before `run()` | ⭐⭐ do it in `__init__`, or return a ready object |
| Flag argument | `render(doc, True)` | ⭐ two functions (Day 089) |
| ⭐ Nested conditionals | arrow-shaped code | ⭐ guard clauses |
| ⭐⭐ **God module** | `utils.py`, 1200 lines | ⭐ split by domain (Day 089) |
| Mutable default | `def f(x=[])` | ⭐ `None` sentinel (Day 025) |
| ⭐ Comment explaining a name | `# the user's total spend` | ⭐ rename it |
| ⭐⭐ **Duplicated logic** | the same rule in three places | ⭐⭐ extract — **but read Part 5 first** |

```
⭐⭐ THE TWO WITH THE BIGGEST PAYOFF, BECAUSE THEY PREDICT FUTURE PAIN RATHER
⭐   THAN DESCRIBING PRESENT UGLINESS:
⭐
⭐  SHOTGUN SURGERY — "add a currency field" means editing eight files. ⭐⭐ THE
⭐    CONCEPT IS SMEARED ACROSS THE CODEBASE. Every future change to it costs
⭐    eight edits and one of them will be forgotten. ⭐ It is Day 090's structure
⭐    problem, seen from the inside.
⭐
⭐  PRIMITIVE OBSESSION — an email as a `str` means EVERY function that receives
⭐    one must decide whether to trust it. ⭐⭐ An `Email` value object validates
⭐    ONCE at construction, and then its TYPE is the proof (Day 057's boundary,
⭐    and Day 062's "types encode what you have already checked").
```

# Part 3 — ⭐ The moves, and how to make them safely

| ⭐ Move | ⭐ When |
|---|---|
| ⭐⭐ **Rename** | ⭐⭐ the highest-value and most-avoided refactor. Do it the moment a name is wrong |
| Extract function | a block you can name, or a comment introducing a section |
| Extract variable | a complex condition — ⭐ `is_eligible = a and b and not c` |
| Inline | ⭐ a badly-named indirection that only obscures |
| ⭐ Introduce parameter object | ⭐ a data clump |
| ⭐⭐ **Replace conditional with dispatch** | ⭐ a growing `if/elif` on a type or a key → a dict or `singledispatch` (Day 051) |
| Replace flag with two functions | ⭐ a boolean parameter |
| ⭐ Guard clauses | nesting |
| Extract class | ⭐ a group of fields and methods that only talk to each other |

```
⭐⭐ THE TECHNIQUE, AND IT IS THE WHOLE SKILL:
⭐   1. ⭐ RUN THE TESTS. Green before you start, or you cannot attribute a failure.
⭐   2. ⭐⭐ MAKE ONE SMALL MOVE.
⭐   3. ⭐⭐ RUN THE TESTS AGAIN.
⭐   4. COMMIT.
⭐   5. Repeat.
⭐   ⇒ ⭐⭐ THE POINT OF SMALL STEPS IS NOT CAUTION, IT IS LOCALISATION: when
⭐        something breaks you know EXACTLY which move did it, and `git reset`
⭐        costs you ninety seconds instead of an afternoon.
⭐   ⇒ ⭐ Let the tools do the mechanical ones — your editor's rename is safe
⭐        across a package in a way that find-and-replace never is.
```

```
⭐⭐ WHEN *NOT* TO REFACTOR — the judgement half, and the part interviews probe:
⭐   · ⭐⭐ code that works and nobody touches ⇒ ⭐ ugly is not a cost until it is
⭐        READ or CHANGED. Refactor code you are ALREADY WORKING IN.
⭐   · before you understand it ⇒ ⭐ read it, characterise it, THEN change it
⭐   · with no tests and no time to write them ⇒ ⭐⭐ that is a rewrite in disguise
⭐   · ⭐ as an unrequested 900-line PR ⇒ (Day 088) it will not be reviewed
⭐   ⇒ ⭐⭐ THE SUSTAINABLE VERSION: the boy-scout rule — leave each file you touch
⭐        slightly better. ⭐ Continuous small improvement beats a heroic cleanup
⭐        that never gets scheduled and never gets reviewed.
```

# Part 4 — ⭐⭐ The strangler fig

```
⭐⭐ THE PROBLEM: a 15,000-line legacy module everyone is afraid of. The instinct
⭐   is a rewrite. ⚠️ THE INSTINCT IS USUALLY WRONG, AND THE REASON IS SPECIFIC:
⭐   ⇒ ⭐⭐ THE OLD CODE ENCODES YEARS OF UNDOCUMENTED REQUIREMENTS — the odd
⭐        edge case, the customer-specific hack, the workaround for a supplier's
⭐        broken API. ⭐⭐ NONE OF IT IS WRITTEN DOWN, AND ALL OF IT IS LOAD-BEARING.
⭐        A rewrite discovers them one production incident at a time.
⭐   ⇒ ⭐ and the rewrite must hit a moving target: the old system keeps shipping
⭐        features while you catch up.

⭐⭐ THE STRANGLER FIG — named after the plant that grows around a tree until the
⭐   tree is gone and the shape remains:
⭐   1. ⭐⭐ PUT A FACADE IN FRONT of the old code. Everything calls the facade.
⭐        ⭐ Nothing has changed yet — and this step alone is worth committing.
⭐   2. ⭐ Implement ONE behaviour behind the facade, in the new code.
⭐   3. ⭐⭐ ROUTE THAT ONE CALL to the new implementation. ⭐ Run both and compare
⭐        outputs in production if the stakes are high.
⭐   4. Repeat. ⭐ Delete each piece of the old code as it is orphaned.
⭐   5. ⭐⭐ The old module dies of natural causes.
⭐
⭐   ⇒ ⭐⭐ WHY IT WINS: EVERY STEP IS SHIPPABLE AND REVERSIBLE. You are never
⭐        more than one small change from working software, and the project can
⭐        be paused for a quarter without leaving a half-migrated ruin.
⭐   ⇒ ⭐ AND THE HONEST CASE FOR A REWRITE: when the platform itself is dead
⭐        (Python 2, an unsupported framework) or the domain has genuinely
⭐        changed. ⭐⭐ Even then, budget for the invisible requirements — they are
⭐        the actual cost, not the code.
```

# Part 5 — D-05 · ⭐⭐ Normalization, and the DRY parallel

```
⭐⭐ THE PROBLEM. One table: (student_id, student_email, course_id, course_name, grade)
⭐   ⇒ ⭐ UPDATE ANOMALY  a course is renamed ⇒ you must update EVERY enrolment
⭐        row, and if you miss one the database now holds two contradictory facts.
⭐   ⇒ ⭐ INSERT ANOMALY  you cannot add a course until someone enrols in it.
⭐   ⇒ ⭐ DELETE ANOMALY  the last enrolment leaves ⇒ ⭐⭐ THE COURSE VANISHES.
⭐   ⇒ ⭐⭐ ALL THREE HAVE ONE CAUSE: A FACT IS STORED IN MORE THAN ONE PLACE, OR
⭐        STORED IN THE WRONG PLACE.
```

| Form | ⭐ Rule (from D-04's FDs) | ⭐ Fix |
|---|---|---|
| **1NF** | ⭐ atomic values — no lists, no repeating groups | ⭐⭐ a separate row (Day 084's M:N) |
| **2NF** | ⭐ 1NF + no non-key attribute depends on **part** of a composite key | split out the partial dependency |
| ⭐ **3NF** | ⭐⭐ 2NF + no **transitive** dependency (key → A → B) | move `A, B` to their own table |
| ⭐⭐ **BCNF** | ⭐⭐ **every determinant is a superkey** | ⭐ the general form; ⭐⭐ this is the one to state |

```
⭐⭐ SAY BCNF, NOT THE LADDER — IT SUBSUMES 2NF AND 3NF AND IT IS ONE SENTENCE:
⭐   "FOR EVERY NON-TRIVIAL FD X → Y, X MUST BE A SUPERKEY."
⭐   ⇒ ⭐⭐ AND THE INTUITION UNDERNEATH: an FD says "X determines Y". If X is a
⭐        key, that fact is stored once — on X's row. ⭐⭐ IF X IS NOT A KEY, X
⭐        REPEATS, SO Y REPEATS, so the same fact is written many times ⇒ THE
⭐        THREE ANOMALIES. ⭐ Normalization is not arithmetic; it is "put each fact
⭐        where its determinant lives".
⭐
⭐ WORKED: (student_id, course_id) is the key. But `course_id → course_name`,
⭐   and course_id is NOT a superkey ⇒ ⭐⭐ BCNF VIOLATION ⇒ courses(course_id,
⭐   course_name) and enrolments(student_id, course_id, grade). ⭐ All three
⭐   anomalies disappear at once, which is the confirmation that the split was real.
```

```
⭐⭐ AND HERE IS THE SYMMETRY WORTH CARRYING OUT OF TODAY:
⭐        DRY IN CODE            =    NORMALIZATION IN DATA
⭐        one rule, one place         one fact, one place
⭐   ⇒ ⭐⭐ duplicated logic drifts when someone updates one copy — EXACTLY the
⭐        update anomaly. ⭐ Same disease, two media.
⭐   ⇒ ⭐⭐ AND THE SAME EXCEPTION: deliberate DENORMALIZATION for read performance
⭐        is the data version of deliberate duplication — ⭐ legitimate, and only
⭐        with a mechanism that keeps the copies consistent (one writer, a trigger,
⭐        or a materialized view you REBUILD rather than edit).
⭐   ⇒ ⚠️ ⭐⭐ NORMALIZE FIRST, DENORMALIZE WITH A MEASUREMENT. Denormalizing
⭐        before you have a slow query is guessing, and you pay the consistency
⭐        cost forever for a speedup you never verified.
```

⭐ **And the DRY counterweight, which matters as much as the rule:** two pieces of code that *look*
the same but change for different reasons are not duplication — **merging them couples two things that
should move independently**, and the next requirement splits them again with a flag argument (Day 089).
⭐⭐ **Duplication is cheaper than the wrong abstraction.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"Refactored it and fixed the bug"** | ⭐⭐ Two changes, two commits. Nobody reviews 400 lines for behaviour. |
| Refactoring without tests | ⭐⭐ Write characterisation tests first — assert what it **does**, bugs included. |
| ⭐ Fixing a bug found while characterising | ⭐ Separate ticket. You are building a tripwire, not a fix. |
| Big-bang steps | ⭐⭐ Small steps localise the failure; that is the point, not caution. |
| ⭐ Refactoring code nobody touches | ⭐ Ugly costs nothing until it is read. Refactor what you are in. |
| ⭐⭐ A 900-line unrequested cleanup PR | ⭐ It will not be reviewed (Day 088). |
| Rewriting a legacy module | ⭐⭐ It encodes undocumented requirements. Strangle it. |
| ⭐ Avoiding renames | ⭐⭐ Highest value, lowest risk, most avoided. |
| ⭐ Merging code that merely looks alike | ⭐⭐ Duplication is cheaper than the wrong abstraction. |
| Storing a comma-separated list | ⭐ Not 1NF. A row each. |
| ⭐⭐ **Denormalizing on a hunch** | ⭐⭐ Normalize first; denormalize against a measured slow query. |
| Denormalizing with no consistency mechanism | ⭐ One writer, a trigger, or a rebuilt view. |

## Interview questions

**Q: What is refactoring, and what does it require?**
> A behaviour-preserving change to structure. Which means the definition contains its own
> precondition: it's only refactoring if I can tell that behaviour didn't change, so tests come
> first. If there aren't any, I write characterisation tests — tests asserting what the code
> currently does, bugs included and without judgement, because I'm building a tripwire rather than
> documenting correct behaviour. And I never mix a refactor with a behaviour change in one commit;
> one gets reviewed by reading and the other by testing, and combining them is how a "safe cleanup"
> ships a regression.

**Q: Which code smell would you prioritise?**
> Shotgun surgery — where one conceptual change means editing eight files. It's the one that predicts
> future pain rather than describing present ugliness: the concept is smeared across the codebase, so
> every future change costs eight edits and eventually someone forgets one. Primitive obsession is
> close behind, because an email as a bare `str` means every function receiving one has to decide
> whether to trust it, where a value object validates once at construction and then the type is the
> proof.

**Q: How would you replace a 15,000-line legacy module?**
> Strangler fig, not a rewrite. Put a facade in front so everything calls one interface — that step
> alone changes no behaviour and is worth committing. Then implement one behaviour behind the facade
> in new code, route that one call across, and repeat, deleting old code as it's orphaned. Every step
> is shippable and reversible, and the project can be paused for a quarter without leaving a
> half-migrated ruin. The reason I'd avoid the rewrite is specific: the old code encodes years of
> undocumented requirements — edge cases, customer-specific hacks, workarounds for someone else's
> broken API — none of it written down and all of it load-bearing. A rewrite discovers those one
> production incident at a time.

**Q: Explain normalization without reciting the forms.**
> The point is that a fact should be stored in exactly one place. When it isn't, you get three
> anomalies: renaming a course means updating every enrolment row and contradicting yourself if you
> miss one; you can't add a course until someone enrols; and deleting the last enrolment deletes the
> course. BCNF states the whole thing in one sentence — for every non-trivial functional dependency
> X → Y, X must be a superkey. The intuition is that if X is a key, the fact lives once on X's row;
> if X isn't a key then X repeats, so Y repeats, so the same fact is written many times. It's exactly
> DRY, applied to data — and duplicated logic drifting when someone updates one copy *is* the update
> anomaly.

**Q: When would you denormalize?**
> Against a measured slow query, never on a hunch — and with a mechanism that keeps the copies
> consistent: a single writer, a trigger, or a materialized view I rebuild rather than edit.
> Denormalizing speculatively means paying the consistency cost forever for a speedup nobody verified.
> It's the same trade as deliberate duplication in code, and it deserves the same scrutiny — I'd want
> the query plan in the PR description.

## Mini task

1. ⭐⭐ Take an untested function and write **characterisation tests** for it — including one that
   asserts behaviour you think is wrong. **Note it as a separate ticket.**
2. ⭐⭐ Refactor that function in five small commits, running the tests after each.
3. ⭐ Deliberately break a step and confirm you know instantly which move did it.
4. ⭐⭐ Find a data clump in your code and introduce a parameter object.
5. ⭐⭐ Find a primitive-obsessed `str` (email, currency, id) and make it a value object with
   validation in `__post_init__`.
6. ⭐ Find a growing `if/elif` chain and replace it with a dispatch dict or `singledispatch`.
7. ⭐⭐ Find temporal coupling — two methods that must be called in order — and remove it.
8. ⭐⭐ Take a scary module and **put a facade in front of it.** Commit that alone, with no behaviour
   change. Then move one behaviour behind it.
9. ⭐ Practise "make the change easy, then make the easy change" as two commits on a real task.
10. ⭐⭐ **D-05:** take a spreadsheet-shaped table (orders with customer name, address and product
    names in it) and **normalize it to BCNF.** Name each anomaly you removed.
11. ⭐⭐ Then denormalize one column deliberately, **write down the query it speeds up, measure it**,
    and state how you would keep it consistent.
12. ⭐ Find two functions that look alike but change for different reasons. **Do not merge them.**
    Write down why.

## 🎙️ Articulation drill

Record two minutes: **"There's a 15,000-line module everyone's afraid of. What do you do?"**

⭐ **Refuse the rewrite first, and give the specific reason rather than a general caution:** **"I
wouldn't rewrite it. That code encodes years of undocumented requirements — edge cases, a
customer-specific hack, a workaround for a supplier's broken API — none of it written down and all of
it load-bearing. A rewrite discovers those one production incident at a time, and meanwhile it's
chasing a moving target because the old system keeps shipping features."**

⭐⭐ **Then the method, as concrete steps:** *"strangler fig. Put a facade in front so everything calls
one interface — that changes no behaviour and is worth committing on its own. Then implement one
behaviour behind the facade in new code, route that single call across, and repeat, deleting old code
as it's orphaned. If the stakes are high I'd run both implementations and compare outputs in
production before switching. The property that makes it work is that every step is shippable and
reversible — I'm never more than one small change away from working software, and if the project gets
paused for a quarter it doesn't leave a half-migrated ruin."*

⭐⭐ **Then the precondition, which is the part that makes it safe rather than merely incremental:**
*"before touching anything I'd get characterisation tests around the seam I'm about to move — tests
asserting what it currently does, bugs included. I'm not documenting correct behaviour, I'm building a
tripwire. And if one of those tests looks wrong, that's a separate ticket; fixing it while I'm in
there is exactly how a refactor turns into a regression."*

⭐ **Close on the discipline:** *"and every step is its own commit — refactor and behaviour change
never together, because one gets reviewed by reading and the other by testing."*
