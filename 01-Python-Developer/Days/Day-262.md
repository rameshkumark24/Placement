# Part 1 — ⭐⭐ How to review your own code and find something

```
⭐⭐ THE PROBLEM: RE-READING CODE CONFIRMS IT. You reconstruct the
⭐   intention as you read and the intention always matches. ⭐ So use
⭐   techniques that block reconstruction:

⭐ ① ⭐⭐ READ THE DIFF, NOT THE FILE. `git diff design-freeze..HEAD`
⭐    ⭐ A diff has no narrative, so you cannot fill in the reasoning.
⭐ ② ⭐⭐ READ IT IN A DIFFERENT ORDER: alphabetically by filename, or
⭐    smallest file first. ⭐ Reading in execution order re-runs the
⭐    story you already believe.
⭐ ③ ⭐⭐ READ THE TESTS FIRST AND THE CODE SECOND. ⭐ Ask "what could
⭐    break without any of these failing?" — that question produces
⭐    findings; "is this correct?" does not.
⭐ ④ ⭐ EXPLAIN THE HARDEST FUNCTION OUT LOUD TO NOBODY. ⭐⭐ The place
⭐    you hesitate is a finding, every time.
⭐ ⑤ ⭐⭐ GREP FOR YOUR OWN HABITS. Everyone has three or four. Search
⭐    for `except Exception`, `# TODO`, `# type: ignore`, `sleep(`,
⭐    `datetime.now(`, `.all()`, `print(`, `SELECT *`.

⭐⭐ AND THE RULE FOR TODAY: ***RECORD EVERY FINDING, EVEN THE ONES YOU
⭐   FIX IN THIRTY SECONDS.*** ⭐ The list is the artefact. A review that
⭐   produces no list produced no review, and "I checked and it was fine"
⭐   is the single least credible sentence in engineering.
```

# Part 3 — ⭐⭐ The adversarial pass: ten things to actually try

```
⭐⭐ NOT A CHECKLIST — A SESSION WITH `curl`. Try these against your
⭐   deployed instance and record what happened.

⭐  ① ⭐⭐ Fetch another tenant's job by id with a valid token. ⇒ 404
⭐  ② ⭐ `PATCH /users/me {"role":"owner"}` ⇒ 422 (`extra="forbid"`)
⭐  ③ ⭐⭐ `GET /jobs/{mine}/photos/{theirs}` ⇒ 404, not the photo
⭐  ④ ⭐ `GET /jobs?limit=100000` ⇒ capped, not honoured
⭐  ⑤ ⭐ `GET /jobs?sort=internal_cost_cents` ⇒ 422, not a scan
⭐  ⑥ ⭐⭐ Tamper one byte of a cursor ⇒ 422, not a 500 and not a leak
⭐  ⑦ ⭐ Send `Idempotency-Key: X` twice with different bodies ⇒ 422
⭐  ⑧ ⭐⭐ Log in 50 times with a wrong password ⇒ 429 with `Retry-After`,
⭐       and the account is NOT locked
⭐  ⑨ ⭐⭐ Present a rotated refresh token ⇒ generic error, family
⭐       revoked, metric incremented
⭐  ⑩ ⭐ Trigger a 500 deliberately ⇒ body contains ONLY a code and a
⭐       request id, and that id finds the trace in your logs

⭐⭐ AND THE TWO THAT ARE NOT `curl`:
⭐   ⭐⭐ ⑪ RUN THE DOUBLE-BOOKING TEST AT 200 THREADS AGAINST THE
⭐      DEPLOYED DATABASE, not a local one. ⭐ Exactly one succeeds.
⭐   ⭐⭐ ⑫ KILL THE APP MID-REQUEST (`kill -9` a worker during a
⭐      dispatch) AND CHECK THE DATABASE. ⭐ Either the job moved and the
⭐      outbox row exists, or neither. ⭐⭐ Any other state is a
⭐      transaction boundary in the wrong place.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Re-reading files to review them | Reading reconstructs intention. Read the diff, in a different order. |
| Asking "is this correct?" | Ask "what could break with none of these tests failing?" |
| A review that produces no findings | Then it produced no review. "I checked and it was fine" is the least credible sentence in engineering. |
| Fixing findings without recording them | The list is the artefact. |
| Checking `lazy="raise"` from memory | Grep. Everyone has an exception they forgot. |
| Testing the adversarial probes only locally | The deployed instance has different config, and config is where these fail. |
| Skipping the kill-mid-request test | It's the only check of your transaction boundary that isn't self-reported. |
| No baseline before optimising | You can never claim an improvement, only assert one. |
| Not recording endpoints that were already fast | "It was 4 ms and I didn't optimise it" is defensible; silence isn't. |
| Fixing everything you find | Some findings are correct decisions. Put them in known-gaps with a trigger. |
| No `known-gaps.md` | It's the document that separates "I didn't know" from "I knew and chose". |

## Interview questions

**Q: How do you review your own code?**

> With techniques that stop me reconstructing my own intention, because re-reading a file just
> confirms it — you rebuild the reasoning as you go and it always matches. So: read the diff rather
> than the files, since a diff has no narrative; read in a deliberately wrong order, alphabetically or
> smallest first, because execution order re-runs the story I already believe; read the tests first
> and ask "what could break with none of these failing?", which produces findings where "is this
> correct?" doesn't; explain the hardest function out loud, because the place I hesitate is always a
> finding; and grep for my own habits, which everyone has three or four of. The rule I'd hold to is
> recording every finding even the thirty-second ones, because the list is the artefact — a review that
> produces no list produced no review.

**Q: What did your audit find?**

> That's the question I want to be asked, and the answer should be specific. In a review like this the
> recurring categories are: a relationship somewhere without `lazy="raise"`, because you add one in a
> hurry and the grep is the only thing that catches it; a sortable field whose index was never created;
> a service that grew a `select()` when someone needed one more field; an endpoint returning a raw dict
> so the response allowlist silently doesn't apply; and a `SET` that should have been `SET LOCAL`. The
> pattern is that they're all things enforced by convention rather than mechanically — which is itself
> the finding, and the fix is usually to add the check to CI rather than just to fix the instance.

**Q: What's the most valuable thing you'd try against your own API?**

> Killing a worker mid-request and inspecting the database. Every other probe checks something I
> designed for; that one checks whether my transaction boundary is actually where I think it is. Either
> the job moved state *and* the outbox row exists, or neither does — any other combination means the
> boundary is in the wrong place, and it's a state you'd otherwise discover during an incident. After
> that, the cross-tenant fetch with a valid token, because it's the failure with the worst consequence
> and it must return 404 rather than 403; and running the concurrency test against the *deployed*
> database rather than a local one, since the constraint being enforced is a property of that database,
> not of my laptop.

**Q: How do you know whether you improved performance later?**

> Because I wrote the baseline down today, before optimising anything: p50, p95, query count and
> buffers read for the five busiest endpoints, at two data volumes — a couple of hundred rows and
> twenty thousand. The two-volume comparison is the useful part, because the endpoint whose timing
> grows with row count while its query count doesn't is exactly the one with a missing index or an
> unbounded scan, and that comparison finds more at this stage than a profiler would. I'd also record
> the endpoints that were *already* fast, because "this was four milliseconds at twenty thousand rows
> and I chose not to optimise it" is a defensible sentence and silence isn't.

**Q: What's in your known-gaps document?**

> Things I know are wrong or incomplete and have deliberately not fixed, each with a reason and a
> trigger that would change the decision — for example, that search has no result cache, that it'll
> need one above roughly twenty searches a second, and that we currently do a fifth of one. The reason
> it matters more than it looks is that nobody expects a system to be perfect, and everybody notices
> the difference between "I didn't know" and "I knew and chose". It's also the document that makes the
> rest of the review credible: an audit with no findings reads as either a trivial system or an
> incurious engineer, and a gaps list with triggers reads as someone who has run something.

## 🎙️ Articulation drill

**Three minutes: present your audit to a reviewer.**

Don't narrate the checklist. Lead with the findings — three of them, with what you found, why it
happened, and what you changed so it can't recur — because **the fix that adds a CI check is worth
more than the fix that corrects the instance.** Then the adversarial pass: name the two probes with
the highest information, the cross-tenant fetch and killing a worker mid-request, and say what each
proved. Then the baseline, with two row counts and the reasoning: the endpoint whose latency grows
while its query count doesn't is the one with a missing index. Close on the gaps document, and say
what it's really for: **nobody expects a perfect system, and everyone notices the difference between
"I didn't know" and "I knew and chose."**
