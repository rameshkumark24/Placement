# Part 1 — ⭐⭐ Choosing a type is the cheapest validation you will ever write

```
⭐⭐ THE FIVE CHOICES THAT ACTUALLY MATTER. Everything else is detail.

⭐ 1. TEXT vs VARCHAR(n)
⭐    ⭐⭐ IN POSTGRES THEY ARE THE SAME TYPE WITH A CHECK. `varchar(n)` is
⭐       not faster and not smaller. ⭐ There is exactly one reason to use
⭐       a length: when the length is a REAL DOMAIN RULE (a 2-letter
⭐       country code). ⭐⭐ `varchar(255)` IS A MYSQL HABIT, NOT A DESIGN.
⭐    ⭐⭐ AND THE COST: changing `varchar(50)` → `varchar(100)` is free,
⭐       but 100 → 50 rewrites the table. Length limits are one-way doors.

⭐ 2. numeric vs float8  ⭐⭐ — Day 041, now enforced by the schema
⭐    ⭐ `numeric(12,2)` — exact decimal. ⭐ `float8` — binary, ~2× faster,
⭐      and 0.1 + 0.2 ≠ 0.3.
⭐    ⇒ ⭐⭐ MONEY IS `numeric`, OR `bigint` CENTS. Never float. And the
⭐      one that catches people: `SUM(float8)` over a million rows gives
⭐      DIFFERENT ANSWERS DEPENDING ON ROW ORDER, so a report changes
⭐      after a VACUUM. ⭐ Yes, really.

⭐ 3. ⭐⭐ timestamptz vs timestamp — THE MOST CONSEQUENTIAL DEFAULT HERE
⭐    ⭐⭐ `timestamptz` DOES NOT STORE A TIME ZONE. It stores UTC, and
⭐       converts on input and output using the session's `TimeZone`.
⭐    ⭐ `timestamp` stores wall-clock digits with NO meaning attached —
⭐       two rows written by servers in different regions are silently
⭐       incomparable.
⭐    ⇒ ⭐⭐ USE `timestamptz` FOR EVERY POINT IN TIME. Use `date` for a
⭐      birthday. Use `timestamp` essentially never.
⭐    ⭐⭐ THE PYTHON HALF: a naive `datetime.now()` written into a
⭐       `timestamptz` is interpreted in the SESSION timezone — so the
⭐       same code produces different rows on your laptop and in
⭐       production. `datetime.now(timezone.utc)`, always.

⭐ 4. IDENTITY vs SERIAL vs UUID for primary keys
⭐    ⭐ `bigint GENERATED ALWAYS AS IDENTITY` — ⭐⭐ the modern spelling.
⭐       `serial` is a legacy macro with sequence-ownership quirks.
⭐    ⭐ `uuid` v4: 16 bytes, ⭐⭐ RANDOM ⇒ every insert lands on a
⭐       different B-tree page ⇒ write amplification and a bloated index
⭐       (Day 189 makes this visible).
⭐    ⭐ `uuid` v7 / ULID: time-ordered ⇒ ⭐⭐ THE BEST OF BOTH — globally
⭐       unique AND sequential inserts. Use this when you need opaque IDs.
⭐    ⭐⭐ AND THE SECURITY POINT FROM DAY 118: sequential IDs leak volume
⭐       ("order 8,412") and make IDOR trivially enumerable. That is an
⭐       argument for UUIDs in URLs — NOT for UUIDs as the clustered key.
⭐       ⭐ You can have both: bigint PK, uuid external id, unique index.

⭐ 5. ENUM vs CHECK vs LOOKUP TABLE — for a status column
⭐    ⭐ native `enum`:  fast, tiny, ⭐⭐ ADDING A VALUE IS EASY, REMOVING
⭐         OR REORDERING MEANS A TYPE REWRITE.
⭐    ⭐ `text` + CHECK: ⭐⭐ THE PRAGMATIC DEFAULT. Changing the allowed
⭐         set is one `ALTER ... NOT VALID` away.
⭐    ⭐ lookup table + FK: ⭐⭐ THE RIGHT ANSWER WHEN THE SET HAS DATA
⭐         ATTACHED (a label, a sort order, an is_active flag) or when
⭐         NON-DEVELOPERS MUST ADD VALUES.
⭐    ⇒ ⭐ Decide by asking "who adds a value, and how often?"
```

```sql
-- ⭐ Types that replace code you would otherwise write badly
inet          -- ⭐ an IP address, with containment operators. Beats text.
interval      -- ⭐ a duration. `now() + interval '15 minutes'`
jsonb         -- ⭐ Day 198. Indexable, but NOT an excuse for no schema.
tstzrange     -- ⭐⭐ a time RANGE — and the basis of Part 3's best trick.
text[]        -- ⭐ an array. ⭐⭐ Convenient and a trap: no FK into an
              --   array, and "which rows contain X" needs a GIN index.
citext        -- ⭐ case-insensitive text. ⭐⭐ Prefer a unique index on
              --   lower(email); citext has collation surprises.
```

# Part 2 — ⭐⭐ NULL, and the three-valued logic that will ambush you

```
⭐⭐ NULL IS NOT A VALUE. IT IS THE ABSENCE OF ONE. SQL therefore has
⭐   THREE truth values: TRUE, FALSE, and ⭐⭐ UNKNOWN.

⭐   NULL = NULL          → ⭐⭐ UNKNOWN (not TRUE!)  ⇒ use `IS NULL`
⭐   NULL <> 'x'          → ⭐⭐ UNKNOWN               ⇒ row NOT returned
⭐   TRUE  OR  UNKNOWN    → TRUE
⭐   FALSE AND UNKNOWN    → FALSE
⭐   ⭐⭐ A WHERE CLAUSE RETURNS ROWS ONLY FOR *TRUE*. UNKNOWN IS DROPPED
⭐      EXACTLY LIKE FALSE — and that asymmetry is where the bugs live.
```

```sql
-- ⭐⭐ THE ONE THAT HAS SILENTLY BROKEN PRODUCTION FOR EVERYONE:
SELECT * FROM users
WHERE id NOT IN (SELECT owner_id FROM projects);
-- ⭐⭐ IF ANY `owner_id` IS NULL, THIS RETURNS ***ZERO ROWS***. Always.
-- ⭐ Because `id NOT IN (1, 2, NULL)` is `id<>1 AND id<>2 AND id<>NULL`
--   → TRUE AND TRUE AND UNKNOWN → UNKNOWN → dropped.
-- ⭐ No error. No warning. An empty list where you expected 40,000 users.

-- ⭐⭐ THE FIX, AND WHY IT IS ALSO THE HABIT:
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM projects p WHERE p.owner_id = u.id);
-- ⭐⭐ `NOT EXISTS` IS NULL-SAFE *AND* USUALLY PLANS BETTER (anti-join).
--    ⇒ ⭐ Prefer NOT EXISTS to NOT IN unconditionally. Two wins, no cost.
```

```
⭐⭐ THE OTHER FOUR NULL BEHAVIOURS TO HAVE MEMORISED:

⭐ 1. UNIQUE ALLOWS UNLIMITED NULLS. Two rows with NULL email do not
⭐    conflict — ⭐⭐ NULLs are "distinct" by default. So a UNIQUE index
⭐    does NOT stop duplicate "no value" rows.
⭐    ⭐ PG 15+: `UNIQUE NULLS NOT DISTINCT` reverses it. Before that, a
⭐      partial unique index or a sentinel value.
⭐ 2. AGGREGATES SKIP NULLS. `avg(score)` over (10, NULL, 20) is 15, not
⭐    10. ⭐⭐ AND `count(col)` ≠ `count(*)`. Reports quietly disagree.
⭐ 3. `NULL || 'x'` IS NULL. Any concatenation with NULL erases the
⭐    string. ⭐ `concat()` does not do this; `||` does.
⭐ 4. ORDER BY puts NULLs LAST for ASC, FIRST for DESC. ⭐⭐ So flipping a
⭐    sort direction can move a block of rows from the end of page 40 to
⭐    the top of page 1. `NULLS LAST` explicitly.
```

> ⭐⭐ **The design consequence: `NOT NULL` is not paperwork. Every nullable column adds a branch to
> every query that touches it, and most of those branches are never written.** ⭐ Default to
> `NOT NULL` and justify each exception — the opposite of what most schemas do.

# Part 3 — ⭐ The five constraint types, in order of how often they save you

```sql
-- ⭐ 1. NOT NULL — the most valuable and the least respected.

-- ⭐ 2. CHECK — an arbitrary boolean over the row.
ALTER TABLE orders ADD CONSTRAINT orders_total_nonneg
  CHECK (total_cents >= 0);
ALTER TABLE ticket_types ADD CONSTRAINT tt_no_oversell
  CHECK (quantity_sold <= quantity_total);   -- ⭐⭐ Day 164's third defence
-- ⭐⭐ A CHECK CANNOT SEE OTHER ROWS OR OTHER TABLES. It is per-row only.
--    ⇒ ⭐ "no two active subscriptions per user" is NOT a CHECK. It is a
--      partial unique index (below), or an EXCLUDE constraint.

-- ⭐ 3. UNIQUE, and its far more useful partial form:
CREATE UNIQUE INDEX one_active_sub_per_user
  ON subscriptions (user_id) WHERE status = 'active';
-- ⭐⭐ THIS IS THE SINGLE MOST UNDERUSED FEATURE IN THIS ENTIRE DAY.
--    "Only one X may be active" is a rule people enforce in Python with
--    a SELECT-then-INSERT — which is a race (Day 164) — when ONE INDEX
--    makes it impossible.

-- ⭐ 4. FOREIGN KEY — and the ON DELETE choice is a domain decision:
--    RESTRICT/NO ACTION ⭐ refuse   · CASCADE ⭐⭐ delete children
--    SET NULL ⭐ orphan deliberately · SET DEFAULT ⭐ rare
-- ⭐⭐ CASCADE ON A USER ROW IS HOW PEOPLE ACCIDENTALLY DELETE A MILLION
--    ORDERS FROM ONE ADMIN CLICK (Day 177's liability, at the DB layer).
-- ⭐⭐ AND: POSTGRES DOES NOT INDEX THE REFERENCING SIDE FOR YOU. An
--    unindexed FK makes every parent delete/update a full scan of the
--    child table, and takes locks while it does. ⭐ Day 190 revisits it.

-- ⭐ 5. ⭐⭐ EXCLUDE — the constraint almost nobody knows, which solves a
--    problem everybody has: NO OVERLAPPING BOOKINGS.
CREATE EXTENSION btree_gist;
ALTER TABLE bookings ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (
      room_id WITH =,
      during  WITH &&        -- ⭐ && is "ranges overlap"
  );
-- ⭐⭐ READ IT AS: "NO TWO ROWS MAY HAVE THE SAME room_id AND OVERLAPPING
--    `during`." ⭐⭐ ENFORCED BY THE DATABASE, UNDER FULL CONCURRENCY,
--    WITH NO LOCK YOU WROTE AND NO RACE YOU CAN LOSE.
-- ⭐ The application version of this is 40 lines, holds a lock across a
--   read, and is wrong under concurrency. This is 4 lines and is not.
```

```
⭐⭐ DEFERRABLE — for the genuine circular case:
⭐   ALTER TABLE ... ADD CONSTRAINT ... DEFERRABLE INITIALLY IMMEDIATE;
⭐   SET CONSTRAINTS ALL DEFERRED;   -- ⭐ checked at COMMIT instead
⭐   ⭐ Use: swapping two rows' unique `position` values; inserting two
⭐     rows that reference each other.
⭐   ⭐⭐ THE COST: a deferred constraint cannot use the fast index path
⭐     for enforcement and the violation surfaces at COMMIT, far from the
⭐     statement that caused it. ⭐ Reach for it rarely and deliberately.
```

# Part 4 — ⭐⭐ Four places a rule can live, and what each actually defends against

```
⭐⭐ THE SAME RULE — "an order total is never negative" — FOUR TIMES:

⭐ ① HTML / client                  ⭐ defends: the user's typo
⭐    <input min="0">               ⭐⭐ DEFENDS AGAINST NOTHING ELSE. curl
⭐                                     exists. It is UX, not a control.
⭐ ② Pydantic / DRF serializer      ⭐ defends: a bad API caller
⭐    total_cents: int = Field(ge=0) ⭐⭐ BYPASSED BY: a management command,
⭐                                     a data migration, a Celery task, a
⭐                                     signal, `queryset.update()`, psql,
⭐                                     the Django admin, a second service.
⭐ ③ Domain / service layer         ⭐ defends: your own call sites
⭐    if total < 0: raise ...       ⭐⭐ BYPASSED BY: anything that does not
⭐                                     go through the service. Which, in
⭐                                     any real system, is a long list.
⭐ ④ ⭐⭐ CHECK CONSTRAINT            ⭐⭐ DEFENDS AGAINST *EVERYTHING*,
⭐    CHECK (total_cents >= 0)         including you, including a rogue
⭐                                     UPDATE typed at 2 a.m., including
⭐                                     a bug you have not written yet.
```

> ⭐⭐ **They are not redundant. ② gives a 422 with a helpful message and a field name. ④ gives an
> ugly 500 unless you map it — but it is TRUE.** ⭐ Ship both: ② for the error message, ④ for the
> guarantee. If you can only have one, keep ④, because a data-corruption bug outlives the release
> that caused it.

```
⭐⭐ THE ARGUMENT AGAINST DB CONSTRAINTS, STATED FAIRLY, THEN ANSWERED:
⭐   "Constraints make the schema rigid; business rules change."
⭐   ⭐ TRUE for rules like "gold customers get free shipping over £50" —
⭐     ⭐⭐ THOSE ARE POLICY, AND POLICY DOES NOT BELONG IN DDL.
⭐   ⭐ FALSE for rules like "a total is not negative", "an order has a
⭐     customer", "a room is not double-booked" — ⭐⭐ THOSE ARE
⭐     INVARIANTS. If one becomes false, the data is corrupt, not
⭐     out of date.
⭐   ⇒ ⭐⭐ THE TEST: "IF THIS BECAME FALSE FOR ONE ROW, WOULD I CALL IT A
⭐     POLICY CHANGE OR A DATA BUG?" ⭐ Data bug ⇒ constraint. Policy ⇒
⭐     application.
```

# Part 5 — ⭐ Living with constraints in Python

```python
# ⭐⭐ A CONSTRAINT VIOLATION IS AN EXCEPTION AT THE COMMIT, NOT A RETURN
#    VALUE — so the error contract from Day 152 has to cover it.

from sqlalchemy.exc import IntegrityError
from psycopg import errors

try:
    session.add(Order(...))
    session.commit()
except IntegrityError as e:
    session.rollback()                        # ⭐⭐ MANDATORY — Day 172's
                                              #    poisoned transaction
    orig = e.orig
    if isinstance(orig, errors.UniqueViolation):
        # ⭐⭐ MATCH ON THE CONSTRAINT NAME, NOT THE MESSAGE TEXT.
        if orig.diag.constraint_name == "uq_orders_idempotency_key":
            return existing_order(...)        # ⭐ Day 184 invariant #6
        raise Conflict("already exists")      # → 409
    if isinstance(orig, errors.ForeignKeyViolation):
        raise UnprocessableEntity(...)        # → 422
    if isinstance(orig, errors.CheckViolation):
        raise                                 # ⭐⭐ → 500, AND IT SHOULD.
        # ⭐ A CHECK violation means your validation layer has a hole.
        #   Do not map it to a friendly 4xx; you want the alert.
```

```python
# ⭐⭐ NAME YOUR CONSTRAINTS, OR ALEMBIC WILL NAME THEM FOR YOU AND YOU
#    WILL NOT BE ABLE TO DROP THEM PORTABLY.
from sqlalchemy import MetaData
NAMING = {
    "ix":  "ix_%(table_name)s_%(column_0_N_name)s",
    "uq":  "uq_%(table_name)s_%(column_0_N_name)s",
    "ck":  "ck_%(table_name)s_%(constraint_name)s",
    "fk":  "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk":  "pk_%(table_name)s",
}
metadata = MetaData(naming_convention=NAMING)
# ⭐⭐ SET THIS ON DAY ONE OF A PROJECT. Retrofitting it means a migration
#    that renames every constraint in the database.
```

```
⭐⭐ ADDING A CONSTRAINT TO A BIG TABLE — Day 138's lock lesson, applied:

⭐   ❌ ALTER TABLE orders ADD CHECK (total_cents >= 0);
⭐      ⇒ ⭐⭐ ACCESS EXCLUSIVE + FULL TABLE SCAN TO VALIDATE. On 200M
⭐        rows that is minutes of total outage.
⭐
⭐   ✅ TWO STEPS:
⭐      ALTER TABLE orders ADD CONSTRAINT ck_total NOT VALID;   -- ⭐ ms
⭐         ⇒ ⭐⭐ ENFORCED FOR ALL NEW AND MODIFIED ROWS IMMEDIATELY;
⭐           existing rows unchecked.
⭐      ALTER TABLE orders VALIDATE CONSTRAINT ck_total;        -- ⭐ scan
⭐         ⇒ ⭐⭐ TAKES ONLY SHARE UPDATE EXCLUSIVE — reads AND writes
⭐           continue.
⭐
⭐   ⭐⭐ AND `NOT NULL` — the historically painful one:
⭐      PG 12+: add the CHECK (col IS NOT NULL) NOT VALID, VALIDATE it,
⭐      THEN `SET NOT NULL` — ⭐⭐ Postgres reuses the validated CHECK and
⭐      SKIPS THE SCAN. ⭐ A genuinely useful trick very few people know.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `varchar(255)` everywhere | A MySQL habit. Use `text` unless the length is a real domain rule. |
| `float` for money | Use `numeric` or integer cents. `SUM(float)` even varies with row order. |
| `timestamp` instead of `timestamptz` | Stores digits with no meaning. Use `timestamptz` for every instant. |
| Naive `datetime.now()` into a `timestamptz` | Interpreted in the session timezone — different rows on laptop vs prod. |
| Random UUID v4 as the primary key | Every insert hits a different index page. Use bigint identity, or UUID v7. |
| `NOT IN (subquery)` | One NULL returns zero rows, silently. Use `NOT EXISTS`. |
| Expecting UNIQUE to stop duplicate NULLs | NULLs are distinct by default. Partial unique index, or `NULLS NOT DISTINCT`. |
| Assuming `count(col) = count(*)` | Aggregates skip NULLs. Two reports quietly disagree. |
| Nullable by default | Every nullable column is an unwritten branch in every query. Default to `NOT NULL`. |
| Enforcing "only one active" in Python | SELECT-then-INSERT is a race. A partial unique index makes it impossible. |
| A CHECK that references another table | CHECKs are per-row. Use a unique index, EXCLUDE, or a trigger. |
| `ON DELETE CASCADE` on user | One admin click deletes a million rows. |
| Leaving foreign keys unindexed | Every parent delete becomes a full scan of the child table, holding locks. |
| Validating only in the serializer | Bypassed by migrations, shell, admin, Celery, `queryset.update()`, psql. |
| Matching `IntegrityError` on message text | Match `diag.constraint_name`. Messages change between versions. |
| Not calling `rollback()` after `IntegrityError` | The transaction is poisoned; every later statement fails. |
| Unnamed constraints | Alembic invents names and you cannot drop them portably. Set a naming convention on day one. |
| `ADD CONSTRAINT` on a large live table | ACCESS EXCLUSIVE plus a full scan. Use `NOT VALID` then `VALIDATE`. |

## Interview questions

**Q: `timestamp` or `timestamptz`?**

> `timestamptz`, nearly always — and the name misleads everyone, because it doesn't store a time zone.
> It stores an absolute instant in UTC and converts on input and output using the session's timezone
> setting. Plain `timestamp` stores wall-clock digits with no meaning attached, so two rows written by
> servers in different regions are silently incomparable and arithmetic across a DST boundary is
> wrong. The Python half matters just as much: a naive `datetime.now()` inserted into a `timestamptz`
> column is interpreted in the session's timezone, which means the same code produces different stored
> instants on a developer laptop and in production. So the rule I'd enforce is `timestamptz` in the
> schema, timezone-aware UTC datetimes in Python, and conversion to local time only at the
> presentation layer. `date` for a birthday is the honest exception — that genuinely isn't an instant.

**Q: What's wrong with `WHERE id NOT IN (SELECT owner_id FROM projects)`?**

> If any `owner_id` is NULL it returns zero rows, always, with no error. `NOT IN` expands to a chain
> of `<>` comparisons, and a comparison with NULL is UNKNOWN rather than false, so the whole
> conjunction becomes UNKNOWN and `WHERE` only keeps TRUE. What makes it dangerous is that it's
> silent and data-dependent: it works in development where the column happens to be fully populated,
> and it returns an empty list in production the day someone inserts one row without an owner. I use
> `NOT EXISTS` instead as an unconditional habit, because it's NULL-safe *and* it usually plans better
> — the planner turns it into an anti-join rather than a filter over a materialised list.

**Q: Where should validation live?**

> In at least two places, defending against different things. The serializer layer gives you a 422
> with a field name and a human message, which is what an API consumer needs, but it's bypassed by
> every path that doesn't go through it — data migrations, management commands, the Django admin,
> a Celery task, `queryset.update()`, a second service, or someone in psql. The database constraint
> is the only layer that nothing bypasses, so it's where the *guarantee* lives. The test I use for
> whether something belongs in the schema is: if this became false for one row, would I call it a
> policy change or a data bug? "Total is non-negative" and "a room isn't double-booked" are data bugs,
> so they're constraints. "Gold customers get free shipping over fifty pounds" is policy and belongs
> in the application, because putting it in DDL means a migration every time marketing changes their
> mind.

**Q: How do you stop double bookings?**

> With an `EXCLUDE` constraint using GiST, over `room_id WITH =` and a `tstzrange` `WITH &&`. That
> reads as "no two rows may have the same room and overlapping time ranges", and the database enforces
> it under full concurrency with no lock I wrote and no race I can lose. The alternative people reach
> for is a `SELECT` for conflicts followed by an `INSERT`, which is the classic check-then-act race
> from the capstone — two requests both find no conflict and both insert. You can make that correct
> with `SELECT ... FOR UPDATE` on a parent row or an advisory lock, but that's forty lines that
> serialise bookings for the whole room, versus four lines of DDL that don't. It's the clearest
> example in the whole stage of the invariant: put the guarantee where a bug can't reach it.

**Q: How do you add a `NOT NULL` column constraint to a 200-million-row table without downtime?**

> Never as a single `ALTER TABLE ... SET NOT NULL`, because that takes ACCESS EXCLUSIVE and scans the
> whole table to verify, and — from Day 138 — an ACCESS EXCLUSIVE request queues behind any running
> query and everything else queues behind *it*, so one long analytics query turns a fast ALTER into a
> total outage. The sequence is: backfill in batches with a bounded loop and a sleep, add a
> `CHECK (col IS NOT NULL) NOT VALID` which takes a brief lock and immediately enforces the rule for
> all new and modified rows, then `VALIDATE CONSTRAINT`, which scans under a much weaker
> SHARE UPDATE EXCLUSIVE lock that doesn't block reads or writes. On Postgres 12 and later you can
> then `SET NOT NULL` and the planner reuses the validated check to skip the second scan. And I'd set
> `lock_timeout` on the migration regardless, so a bad moment fails the deploy instead of taking the
> site down.

## 🎙️ Articulation drill

**Two minutes: "Where do you enforce business rules?"**

Start by refusing the premise that it's one place. Name the four layers and what each defends against
— client for UX, serializer for the API caller and the good error message, service for your own call
sites, constraint for everything including the paths you forgot exist. Then give the list that makes
it concrete: migrations, management commands, the admin, Celery, `queryset.update()`, psql, a second
service — all of them walk straight past your Pydantic model. Give the test for what belongs in DDL:
if it became false, is that a policy change or a data bug? Then spend your remaining time on the two
demonstrations that show depth — `NOT IN` returning zero rows because of one NULL, and the EXCLUDE
constraint replacing forty lines of racy booking code with four lines of DDL. Close on the operational
half, because it's what separates theory from practice: **adding a constraint to a large live table is
`NOT VALID` then `VALIDATE`, or it's an outage.**
