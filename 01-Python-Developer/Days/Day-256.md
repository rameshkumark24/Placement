# Day 256 🏗️

**P-256** · 🏗 **The service layer** — ⭐⭐ orchestration, the transaction, and what does *not* belong here

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: the service layer owns exactly one thing that nothing else can own —
> the transaction boundary — because only the service knows what "one operation" is. Everything else
> it does, it does because it is the only layer allowed to talk to both sides.**
>
> ⭐ This is the layer that most often decays into a bag of functions called `utils` and `manager`.
> ⭐⭐ Today's discipline is negative: a short list of what a service does, and a longer list of what
> it must refuse.

# Part 1 — ⭐⭐ One function per use case

```python
# services/job_service.py
def dispatch_job(
    uow: UnitOfWork,                 # ⭐ the transaction + repositories
    actor: Principal,                # ⭐⭐ WHO — decided in the web layer
    job_id: JobId,
    technician_id: UserId,
    window: TimeWindow,              # ⭐ a VALUE OBJECT, already valid
    now: datetime,                   # ⭐⭐ time is an input (Day 254)
    idempotency_key: str | None = None,
) -> JobView:
```

```
⭐⭐ FIVE THINGS TO NOTICE IN THAT SIGNATURE, AND EACH IS A DECISION:
⭐  ① ⭐⭐ NO `Request`, NO `Session`, NO `Depends`. The service is
⭐     callable from a Celery task, a management command and a test with
⭐     no HTTP anywhere. ⭐ That is the property that makes it worth
⭐     having — and Day 264's background job is where you cash it in.
⭐  ② ⭐ IT TAKES A `Principal`, NOT A TOKEN. Decoding is the web layer's
⭐     job; ⭐⭐ deciding what this actor may do is the service's.
⭐  ③ ⭐⭐ IT TAKES VALIDATED VALUE OBJECTS. If `TimeWindow` arrives, it
⭐     is already positive and timezone-aware — ⭐ the service never
⭐     re-validates shapes, only rules.
⭐  ④ ⭐ `now` is passed, so a test can dispatch at a DST boundary
⭐     without patching the clock.
⭐  ⑤ ⭐⭐ IT RETURNS A VIEW, NOT AN ORM OBJECT. Returning an entity
⭐     means the web layer can lazily load, and the session is gone by
⭐     then. ⭐ Day 255's rule, enforced by the return type.
```

```python
def dispatch_job(uow, actor, job_id, technician_id, window, now, key=None):
    with uow:                                        # ⭐⭐ BEGIN
        if key and (prior := uow.idempotency.get(key)):
            return prior.response                    # ⭐ Day 251, case ②

        job = uow.jobs.get_for_update(job_id)
        if job is None:
            raise NotFound("job", job_id)            # ⭐⭐ domain-ish
        require(actor.can_dispatch(job))             # ⭐ Day 259

        assignment = Assignment.create(
            job_id=job.id, technician_id=technician_id,
            window=window, created_by=actor.id, at=now)
        uow.assignments.add(assignment)              # ⭐⭐ the EXCLUDE
                                                     #    constraint will
                                                     #    decide (Day 250)
        events = job.apply(JobAction.DISPATCH, now=now)
        uow.outbox.add_all(events)                   # ⭐⭐ SAME TXN

        view = JobView.from_domain(job)
        if key:
            uow.idempotency.record(key, request_hash, 200, view)
        uow.commit()                                 # ⭐⭐ ONE commit
        return view
```

# Part 2 — ⭐⭐ The four things a service must refuse

```
⭐ ❌ ① HTTP CONCERNS. No status codes, no `HTTPException`, no headers.
⭐    ⭐⭐ The service raises `JobNotCompletable`; the web layer decides
⭐      that is a 409. ⭐ Why it matters: a Celery task calling this
⭐      service would otherwise have to catch `HTTPException`, which is
⭐      absurd and is exactly what you find in real codebases.
⭐ ❌ ② QUERY CONSTRUCTION. No `select()`, no `.join()`. ⭐⭐ The moment
⭐    a service builds a query, Day 255's query locality is gone and
⭐    "which queries touch this table?" is unanswerable again.
⭐ ❌ ③ DOMAIN RULES. `if job.state != COMPLETED: raise` in a service is
⭐    a rule that now lives in two places, and the second one is the one
⭐    the background job forgot. ⭐⭐ Call `job.apply()`.
⭐ ❌ ④ PRESENTATION. No formatting, no localisation, no "£%.2f".
⭐    ⭐ Return `Money`; let the edge render it.

⭐⭐ AND THE POSITIVE LIST — SERVICES DO EXACTLY FIVE THINGS:
⭐   ① open and close the transaction
⭐   ② fetch aggregates via repositories
⭐   ③ ⭐⭐ COORDINATE between aggregates (the rules that fit in none)
⭐   ④ ⭐ record intent for the outside world (the outbox)
⭐   ⑤ return a view
```

# Part 3 — ⭐ The Unit of Work

```python
class UnitOfWork:
    def __init__(self, session_factory): self._sf = session_factory
    def __enter__(self):
        self.session = self._sf()
        self.jobs = JobRepository(self.session)         # ⭐ repositories
        self.assignments = AssignmentRepository(self.session)
        self.outbox = OutboxRepository(self.session)    #   share ONE
        self.idempotency = IdempotencyRepository(self.session)
        return self                                     #   session
    def __exit__(self, exc_type, *_):
        if exc_type: self.session.rollback()            # ⭐⭐ ALWAYS
        self.session.close()
    def commit(self): self.session.commit()
```

```
⭐⭐ WHAT THE UoW BUYS, BEYOND TIDINESS:
⭐   ⭐⭐ ONE SESSION SHARED BY EVERY REPOSITORY, so `uow.jobs` and
⭐     `uow.outbox` are genuinely in the same transaction. ⭐ Without it,
⭐     two repositories with two sessions is the dual-write problem
⭐     inside your own process.
⭐   ⭐ A single place where rollback-on-exception is guaranteed.
⭐   ⭐⭐ A seam for tests: `UnitOfWork` bound to a session inside an
⭐     outer transaction that the fixture rolls back (Day 141) — ⭐ so
⭐     integration tests use the REAL repositories, the REAL constraints
⭐     and the REAL SQL, and still leave no state behind.

⭐⭐ AND WHAT IT IS NOT: A REASON TO FAKE THE DATABASE. Day 139's
⭐   fake-repository trap — an in-memory dict has no constraints, no
⭐   transactions, no `EXCLUDE`, no N+1 — ⭐⭐ so a test suite built on
⭐   fakes passes while every one of your real guarantees is untested.
⭐   ⭐ Fake the PAYMENT PROVIDER. Never fake Postgres.
```

# Part 4 — ⭐⭐ Third parties: the rule that shapes everything

```
⭐⭐ ***NEVER CALL AN EXTERNAL SERVICE INSIDE A TRANSACTION.***

⭐   ❌ with uow:
⭐        invoice = uow.invoices.get_for_update(id)
⭐        result = stripe.charge(...)          # ⭐⭐ 30 s TIMEOUT
⭐        invoice.mark_paid(result)
⭐        uow.commit()
⭐   ⇒ ⭐⭐ A ROW LOCK HELD FOR 30 SECONDS, A CONNECTION HELD FOR 30
⭐     SECONDS, AND EVERY OTHER REQUEST FOR THAT INVOICE QUEUED BEHIND
⭐     IT. ⭐ At 20 concurrent payments your pool is gone (Day 197).
⭐   ⇒ ⭐ And if the process dies mid-call, you have charged a card and
⭐     recorded nothing.

⭐⭐ THE SHAPE THAT WORKS — THREE TRANSACTIONS, NOT ONE:
⭐   T1 (service):  validate, create `payment` row as `pending`,
⭐                  write `PaymentRequested` to the outbox, COMMIT
⭐   ⭐ (relay):     read the outbox, call the provider OUTSIDE any
⭐                  transaction (Day 263)
⭐   T2 (worker):   record the outcome, transition the invoice, COMMIT
⭐   ⇒ ⭐⭐ THE USER'S REQUEST RETURNS IN 40 ms WITH `202` AND A STATUS
⭐     URL, INSTEAD OF BLOCKING FOR 30 SECONDS AND SOMETIMES LYING.
⭐   ⭐ And the third outcome — the timeout — has a place to live
⭐     (`payment_unknown`), which is Day 166 and Day 263.
```

```
⭐ THE ONE LEGITIMATE EXCEPTION, STATED SO IT IS NOT ABUSED: a call to
⭐   a service YOU control, in the same datacentre, with a tight timeout
⭐   (<100 ms), where a failure MUST abort the transaction. ⭐⭐ Even
⭐   then, prefer not to — and write the timeout down.
```

# Part 5 — ⭐ Errors: who raises, who translates

```
⭐⭐ THREE FAMILIES, AND KNOWING WHICH IS WHICH DECIDES WHO HANDLES IT:

⭐ ① ⭐ DOMAIN ERRORS — an invariant refused.
⭐    `InvalidTransition`, `CannotInvoiceEmptyJob`
⭐    ⭐⭐ RAISED BY: the domain. ⭐ MEANING: the caller asked for
⭐      something the business forbids. ⭐ → 409 or 422.
⭐ ② ⭐ APPLICATION ERRORS — a use case cannot proceed.
⭐    `NotFound`, `Forbidden`, `IdempotencyKeyReuse`, `Conflict`
⭐    ⭐⭐ RAISED BY: the service. ⭐ → 404 / 403 / 422 / 409.
⭐ ③ ⭐⭐ INFRASTRUCTURE ERRORS — something broke.
⭐    `OperationalError`, `TimeoutException`, `RedisError`
⭐    ⭐⭐ MOSTLY NOT CAUGHT AT ALL. ⭐ → 500, alert, and a request id.
⭐    ⭐⭐ THE EXCEPTION: `IntegrityError` on a constraint you EXPECTED
⭐      is really family ①, so the service catches it and re-raises the
⭐      domain error (Day 255) — matching on constraint NAME.

⭐⭐ AND THE RULE: ***THE SERVICE NEVER IMPORTS A STATUS CODE, AND THE
⭐   WEB LAYER NEVER INVENTS A BUSINESS MEANING.*** One translation
⭐   table, in one exception handler (Day 257).
```

# Part 6 — ⭐⭐ The three ways this layer decays

```
⭐ ① ⭐⭐ THE PASS-THROUGH SERVICE
⭐    def get_job(uow, id): return uow.jobs.get(id)
⭐    ⭐ Twelve of these and the layer is pure ceremony.
⭐    ⇒ ⭐⭐ THE FIX IS NOT TO DELETE THE LAYER — it is to notice that
⭐      READS DO NOT NEED IT. ⭐ A read endpoint may call a QUERY object
⭐      (Day 269's read path) directly. ⭐⭐ Services exist for WRITES,
⭐      where there is a transaction to own.
⭐ ② ⭐⭐ THE GOD SERVICE — `JobService` with 40 methods, importing
⭐    every repository, 900 lines.
⭐    ⇒ ⭐ Split by USE CASE, not by entity. `dispatch_job`,
⭐      `complete_job`, `invoice_job` can be three modules. ⭐⭐ The unit
⭐      of cohesion is the transaction, not the table.
⭐ ③ ⭐⭐ SERVICES CALLING SERVICES
⭐    ⭐ `invoice_job()` calls `send_notification()` which opens its own
⭐      transaction ⇒ ⭐⭐ NESTED OR SIBLING TRANSACTIONS, AND NOW
⭐      "ONE OPERATION" IS UNDEFINED. ⭐ Worse: the inner one commits
⭐      while the outer rolls back.
⭐    ⇒ ⭐⭐ RULE: A SERVICE MAY CALL THE DOMAIN AND REPOSITORIES. IF IT
⭐      NEEDS ANOTHER USE CASE'S EFFECT, IT EMITS AN EVENT. ⭐ That is
⭐      what the outbox is for, and it keeps the transaction boundary
⭐      exactly one function deep.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `Request`, `Session` or `Depends` in a service signature | Then a Celery task can't call it, which was the point. |
| Passing a raw token instead of a `Principal` | Decoding is the web layer's job; deciding is the service's. |
| Returning ORM entities from a service | The web layer lazily loads after the session is gone. |
| `HTTPException` raised in a service | A background job would have to catch it. |
| Building queries in a service | Query locality is gone and the repository is pointless. |
| Re-checking domain rules in the service | The rule now lives in two places, and one gets forgotten. |
| Two repositories with two sessions | That's the dual-write problem inside your own process. |
| Faking the repository in tests | No constraints, no transactions, no `EXCLUDE` — your guarantees go untested. |
| Calling a payment API inside the transaction | A 30-second row lock, a drained pool, and a charge with no record. |
| A `get_x` service that only forwards to a repository | Reads don't need this layer. Services exist for writes. |
| A 900-line `JobService` | Split by use case; the unit of cohesion is the transaction. |
| Services calling other services | Nested or sibling transactions, and "one operation" becomes undefined. |
| Formatting money in a service | Return `Money`; the edge renders. |

## Interview questions

**Q: What does your service layer actually do?**

> Exactly five things: opens and closes the transaction, fetches aggregates through repositories,
> coordinates between aggregates for the rules that fit in neither, records intent for the outside
> world in the outbox, and returns a view. The one thing nothing else can own is the transaction
> boundary, because only the service knows what constitutes one operation — a repository call isn't
> atomic and a whole request holds the transaction open across whatever I/O it happens to do. The
> negative list is more useful though: no HTTP concerns, no query construction, no domain rules, no
> presentation. The test I apply is whether a Celery task could call the function unchanged. If a
> service raises `HTTPException`, a background job has to catch it, which is absurd — and it's exactly
> what you find in real codebases.

**Q: Why not call the payment provider inside the transaction?**

> Because a transaction open across a network call is a row lock held for the duration of that call,
> plus a database connection held with it. A thirty-second provider timeout means a thirty-second lock,
> every other request for that invoice queued behind it, and at twenty concurrent payments the pool is
> gone. And if the process dies mid-call you've charged a card and recorded nothing. The shape that
> works is three transactions instead of one: the first validates, creates a pending payment row and
> writes an event to the outbox, then commits; a relay makes the external call outside any transaction;
> a second transaction records the outcome. The user's request returns in tens of milliseconds with a
> 202 and a status URL rather than blocking and sometimes lying. And it gives the third outcome — the
> timeout, where you genuinely don't know what happened — somewhere to live.

**Q: How do you decide where an error is handled?**

> By which of three families it belongs to. Domain errors are invariants refusing — `InvalidTransition`
> — raised by the domain, meaning the caller asked for something the business forbids. Application
> errors are use cases that can't proceed — not found, forbidden, idempotency key reuse — raised by
> the service. Infrastructure errors are things breaking, and mostly they aren't caught at all: they
> become a 500 with a request id and an alert. The one crossover is an `IntegrityError` on a constraint
> I expected, like the no-double-booking exclusion — that's really a domain error wearing an
> infrastructure exception, so the service catches it, matches on the constraint *name* rather than the
> message, and re-raises the domain error. The rule underneath is that the service never imports a
> status code and the web layer never invents a business meaning; there's one translation table in one
> exception handler.

**Q: Your service layer looks like it's just forwarding to repositories. Is it worth having?**

> If that's true for reads, then no — and the right response isn't to delete the layer, it's to notice
> that reads don't need it. A read endpoint can call a query object directly, because there's no
> transaction to own and nothing to coordinate. Services exist for writes. If it's true for writes too,
> then the domain logic has probably leaked into the routers or the models and the layer is genuinely
> ceremony. The other decay mode is the opposite: a nine-hundred-line `JobService` importing every
> repository. The fix there is splitting by use case rather than by entity, because the unit of
> cohesion is the transaction, not the table — `dispatch_job` and `invoice_job` have almost nothing in
> common except a noun.

**Q: Can one service call another?**

> No, and it's one of the few rules I'd hold firmly. The moment `invoice_job` calls `send_notification`
> and that opens its own transaction, you have nested or sibling transactions and "one operation" is
> undefined — worse, the inner one can commit while the outer rolls back, so you've notified about
> something that didn't happen. The rule is that a service may call the domain and repositories, and if
> it needs another use case's effect it emits an event to the outbox instead. That keeps the
> transaction boundary exactly one function deep and makes the coupling explicit and asynchronous
> rather than implicit and synchronous. It's also what makes the effect retryable, which a direct call
> isn't.

## 🎙️ Articulation drill

**Two minutes: "Walk me through what happens when someone dispatches a job."**

Trace one request through the layers and name what each is responsible for: the router parses and
authenticates and does nothing else; the service opens the transaction, loads the aggregate, asks the
domain to apply the transition, writes the resulting events to the outbox, and commits once; the
domain decides whether the transition is legal; the database decides whether the assignment overlaps.
Then say the sentence that shows you know why the layering exists: **the service takes no `Request` and
no `Session`, so a Celery task can call it unchanged — and that's the property you cash in on the
background-jobs day.** Close on the rule that shapes the whole design: **never call an external service
inside a transaction**, with the three-transaction shape and the reason — a thirty-second provider
timeout is a thirty-second row lock and a drained connection pool.
