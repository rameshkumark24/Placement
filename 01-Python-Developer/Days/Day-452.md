# Part 4 — The memory formula that decides your capacity

```
⭐ ***TWO TERMS. GET BOTH RIGHT OR YOUR CAPACITY PLAN IS
⭐   FICTION.***

⭐ ① ***WEIGHTS***
⭐   ⭐ fp16: ⭐⭐ 2 BYTES × PARAMS. ⭐ 7B → 14GB. 70B → 140GB.
⭐   ⭐ int8: 1 byte → 7B → 7GB
⭐   ⭐ int4 (AWQ/GPTQ): 0.5 → ⭐⭐ 7B → 3.5GB, 70B → 35GB
⭐     ⭐ (fits one 48GB card)

⭐ ② ⭐⭐ ***KV CACHE — THE ONE PEOPLE FORGET, AND IT SCALES WITH
⭐   ***CONCURRENCY × CONTEXT***.***
⭐   ⭐ ≈ 2 (K and V) × layers × kv_heads × head_dim × 2 bytes
⭐     × tokens
⭐   ⭐ For a 7B-class model with GQA: ⭐⭐ ROUGHLY 0.1–0.5 MB PER
⭐     TOKEN.
⭐   ⭐ ⇒ 50 concurrent × 4,000 tokens × 0.2MB ≈ ⭐⭐ 40GB — ⭐ more
⭐     than the weights.

⭐ ***THE PLANNING RULE:***
⭐   ⭐ ⭐⭐ USABLE KV MEMORY = GPU RAM − WEIGHTS − ~2GB OVERHEAD
⭐   ⭐ ⭐⭐ MAX CONCURRENCY ≈ USABLE KV ÷ (AVG CONTEXT × PER-TOKEN
⭐     KV)
⭐   ⭐ ⇒ ⭐⭐ CONTEXT LENGTH AND CONCURRENCY TRADE DIRECTLY
⭐     AGAINST EACH OTHER (DAY 416). ⭐ Doubling your context
⭐     halves your throughput. ⭐ Every retrieved chunk you add
⭐     (Day 433) costs concurrency, ⭐⭐ WHICH IS THE SAME
⭐     DECISION AS COST, EXPRESSED IN HARDWARE.

⭐ ***QUANTISATION, HONESTLY:***
⭐   ⭐ int8: ⭐ ~1% quality, 2× memory saved. ⭐⭐ USUALLY FREE
⭐     MONEY.
⭐   ⭐ int4 AWQ: ⭐ 2–5% on reasoning-heavy tasks, 4× saved.
⭐     ⭐⭐ MEASURE ON ***YOUR*** EVAL — the loss is task-dependent
⭐     and benchmarks hide it.
⭐   ⭐ ⭐⭐ AND IT IS NOT ONLY A MEMORY WIN: LESS MEMORY PER
⭐     SEQUENCE MEANS MORE CONCURRENT SEQUENCES, ⭐ so throughput
⭐     rises superlinearly.
```

# 💬 Interview

**1. "Would you self-host an open model?"**

⭐ For part of the stack, yes; for the frontier generation, usually not. ⭐⭐ The cost model inverts: an
API bills you for what you consume and a GPU bills you for what you reserve, so self-hosting is a bet on
sustained utilisation. ⭐ An A100 is fifteen hundred to three thousand a month running 24/7 whether
you use it or not, and you need two for any availability story. ⭐⭐ Three thousand a month buys roughly
ten billion tokens from a small frontier model — so unless you're pushing billions of tokens monthly,
"self-hosting is cheaper" is usually false before you count a single hour of engineering. ⭐ And half an
engineer for GPU nodes, driver versions, twenty-gigabyte images and minutes-long cold starts is five to
eight thousand a month, which is often larger than the API bill you were avoiding.

**2. "So when is it right?"**

⭐ One reason decides it outright: the data can't leave. ⭐⭐ Regulatory, contractual, or a customer
requirement — and when that applies the arithmetic is irrelevant. ⭐ After that: model pinning, which is
worth real money if you've validated a model for a regulated use and don't want it changing behind a
stable name; latency and rate limits, which matter most for small models on hot paths; and high, *steady*
volume on a task a small model handles. ⭐⭐ Steady is doing the work in that sentence — spiky traffic
destroys utilisation, and utilisation is the entire bet. ⭐ What isn't a reason is "avoiding vendor
lock-in", because you've swapped a vendor for an on-call rotation.

**3. "What determines how many requests one GPU serves?"**

⭐ Two memory terms, and people forget the second. ⭐ Weights are two bytes per parameter at fp16 — a 7B
is 14GB. ⭐⭐ The KV cache is the one that decides capacity, and it scales with concurrency times context
length: roughly 0.1 to 0.5 megabytes per token for a 7B-class model, so fifty concurrent requests at
four thousand tokens is about forty gigabytes — more than the weights. ⭐ So usable KV memory is GPU RAM
minus weights minus overhead, and max concurrency is that divided by average context times per-token KV.
⭐⭐ Which means context length and concurrency trade directly against each other — every extra retrieved
chunk costs throughput. ⭐ That's the same decision as cost, expressed in hardware.

**4. "Your self-hosted throughput is terrible. What's wrong?"**

⭐ Almost certainly the serving stack rather than the model. ⭐⭐ If you're calling `generate()` in a
loop, static batching means one eight-hundred-token request holds seven short ones hostage while the GPU
idles — continuous batching evicts finished sequences and admits new ones every step, and that's five to
twenty times throughput on real traffic. ⭐ And naive serving reserves `max_length` of KV cache per
sequence up front, so a four-thousand-token reservation for a two-hundred-token answer wastes
ninety-five percent of it. ⭐⭐ PagedAttention pages the KV cache like virtual memory and gets you two to
four times more concurrent sequences in the same RAM. ⭐ So: vLLM or SGLang, never a hand-rolled loop —
and since vLLM exposes an OpenAI-compatible endpoint, my client protocol switches with a base-URL
change.

**5. "How much does quantisation cost you?"**

⭐ int8 is about one percent of quality for half the memory, which is usually free money. ⭐ int4 with
AWQ is two to five percent on reasoning-heavy tasks for a quarter of the memory, and I'd measure that on
my own eval rather than trusting a benchmark, because the loss is task-dependent and aggregate scores
hide it. ⭐⭐ The part people miss is that it isn't only a memory win: less memory per sequence means more
concurrent sequences, so throughput rises superlinearly. ⭐ A 70B at int4 fits on a single 48GB card,
which changes what hardware you need entirely.

**6. "Any non-technical risks?"**

⭐ Two. ⭐⭐ Licences — "open weights" isn't "open source". Some very strong models are research-only,
which is fine for a prototype and fatal in a product, and prototypes have a habit of becoming products.
Llama's licence is permissive in practice but carries an acceptable-use policy and a scale threshold
worth reading if you might get large. ⭐ And customers increasingly ask about training-data provenance,
so that's a question to have an answer to. ⭐⭐ The second is evaluation: an open model needs *more*
evaluation, not less. No provider is silently improving it, public benchmarks are routinely contaminated
so a leaderboard position says nothing about your task, and instruction-following and refusal behaviour
vary far more between open models than between frontier ones. ⭐ My own harness is the only thing that
tells me a swap is safe, which is exactly why it had to be framework-independent.

**7. "What would you actually run?"**

⭐ A hybrid, split by call frequency rather than by ideology. ⭐⭐ Self-host the small, hot, high-volume
things — embeddings, rerankers, guardrail classifiers, intent routing, narrow fine-tunes. ⭐ Each is
called on every request so utilisation is genuinely high, each fits on modest hardware, and locally
they're forty milliseconds rather than four hundred, which is exactly what makes a guardrail layer
affordable. ⭐ API for final generation, planning and hard reasoning, where quality decides the product
and traffic is spiky. ⭐⭐ And keep one client protocol with vLLM's OpenAI-compatible endpoint behind it,
so "self-host or not" stays a config decision I can revisit per task instead of an architecture I
committed to.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "should we self-host?"**

Start with the inversion, because it makes the rest arithmetic. **The cost model flips. An API bills you
for what you consume — zero traffic, zero cost. A GPU bills you for what you reserve — zero traffic, full
cost. So self-hosting is a bet on sustained utilisation. An A100 is fifteen hundred to three thousand a
month running around the clock, and you need two for any availability story. Three thousand a month buys
roughly ten billion tokens from a small frontier model. So unless we're pushing billions of tokens a
month, "cheaper" is usually false — before counting half an engineer at five to eight thousand a month
for GPU nodes, driver versions, twenty-gigabyte images and minutes-long cold starts.**

Then the reasons that do hold. **One decides it outright: the data can't leave. Regulatory or
contractual — and then the arithmetic is irrelevant. After that, model pinning, which matters if you've
validated a model for a regulated use and don't want it changing behind a stable name; latency and rate
limits on hot paths; and genuinely high, steady volume. Steady is doing the work there — spiky traffic
destroys utilisation, and utilisation is the whole bet.**

Then the engineering that decides whether the numbers are real. **If you serve with `generate()` in a
loop your throughput will be an order of magnitude worse than it should be, and you'll conclude wrongly
that self-hosting doesn't work. Continuous batching evicts finished sequences and admits new ones every
step instead of letting one long request hold seven short ones hostage — five to twenty times on real
traffic. And PagedAttention pages the KV cache instead of reserving max-length per sequence, which is

scales with concurrency times context, so fifty concurrent requests at four thousand tokens is more
memory than the weights. Doubling your context halves your throughput — the same cost decision, expressed
in hardware.**

Close with the recommendation. **So: a hybrid, split by call frequency. Self-host the small, hot,
high-volume things — embeddings, rerankers, guardrail classifiers, routing — because they're called on
every request so utilisation is real, they fit on modest hardware, and locally they're forty milliseconds
instead of four hundred, which is what makes a guardrail layer affordable at all. API for the frontier
generation where quality decides the product and traffic is spiky. And keep one client protocol with an
OpenAI-compatible endpoint behind it, so this stays a config decision per task rather than an
architecture we committed to.**
