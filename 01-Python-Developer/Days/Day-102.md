# Day 102

**L-102** · 🌐 **Stage 3 opens** — HTTP for backends: idempotency, conditional requests, caching

**Time:** 3 hrs · **Mode:** NEW · ⭐ **RECALL** on Day 010's basics

> ⭐⭐ **The sentence to own: HTTP is not a transport you send JSON over — it is a contract with
> defined semantics for retrying, caching and concurrency, and a backend that ignores those semantics
> re-implements all three badly, in application code, later.**
>
> ⭐ Stage 3 builds a web framework from a socket upward. **It starts here because you cannot
> implement a protocol you only half know**, and because the three ideas today — idempotency,
> conditional requests and cache control — are asked about in every backend interview.

# Part 1 — ⭐⭐ Safe, idempotent, cacheable — three different properties

| Method | ⭐ Safe? | ⭐⭐ Idempotent? | ⭐ Cacheable? |
|---|---|---|---|
| `GET` | ✔ | ✔ | ✔ |
| `HEAD` | ✔ | ✔ | ✔ |
| ⭐⭐ `POST` | ✗ | ⭐⭐ **✗** | ⭐ only with explicit headers |
| ⭐ `PUT` | ✗ | ⭐⭐ **✔** | ✗ |
| ⭐ `DELETE` | ✗ | ⭐⭐ **✔** | ✗ |
| `PATCH` | ✗ | ⭐ ✗ (usually) | ✗ |

```
⭐⭐ THE DEFINITIONS, PRECISELY — they are not the same property:
⭐   SAFE        ⇒ no intended change of state. ⭐ A crawler may call it freely.
⭐   IDEMPOTENT  ⇒ ⭐⭐ N IDENTICAL CALLS LEAVE THE SAME STATE AS ONE. ⭐ Note:
⭐                  about STATE, not about the RESPONSE — DELETE twice gives
⭐                  204 then 404, and it is still idempotent, because the
⭐                  server's state is the same either way.
⭐   CACHEABLE   ⇒ a response may be stored and reused.
⭐
⭐ ⇒ ⭐⭐ WHY IDEMPOTENCE IS THE ONE THAT MATTERS: IT IS WHAT MAKES A RETRY SAFE.
⭐     A client times out at 30 s. ⭐⭐ THE REQUEST MAY HAVE SUCCEEDED — the
⭐     response was simply lost. Retrying a PUT is harmless. ⭐⭐ RETRYING A POST
⭐     CHARGES THE CARD TWICE.
⭐   ⇒ ⭐⭐ AND SOMETHING WILL RETRY: the client library, the load balancer, the
⭐        queue, or an impatient user pressing the button again. ⭐ You do not
⭐        get to opt out of retries; you only get to decide whether they are safe.
⭐   ⇒ ⭐⭐ THEREFORE: EITHER USE PUT WITH A CLIENT-CHOSEN ID, OR GIVE POST AN
⭐        IDEMPOTENCY KEY (Day 122). Those are the only two options.
```

⚠️ ⭐ **"POST creates, PUT updates" is a widespread and wrong summary.** ⭐⭐ **The real distinction is
who chooses the identifier:** `POST /orders` lets the *server* choose (so the client cannot repeat it
safely), while `PUT /orders/{client-chosen-id}` lets the *client* choose — **which is exactly what
makes it idempotent.**

# Part 2 — ⭐ Status codes as a contract

```
⭐⭐ THE ONE RULE THAT DECIDES THE FAMILY: 4xx MEANS "YOU MADE A MISTAKE",
⭐   5xx MEANS "I MADE A MISTAKE". ⭐⭐ AND IT IS OPERATIONALLY LOAD-BEARING —
⭐   your 5xx rate is an alert (Day 099A); your 4xx rate is a client bug or a
⭐   probing attacker. ⭐ Returning 500 for bad user input trains everyone to
⭐   ignore the alert.
```

| ⭐ Code | ⭐ Use it for |
|---|---|
| `200` / `201` | OK / ⭐ **created** — and `201` must carry a `Location` header |
| ⭐ `202` | accepted, **not yet done** — ⭐ the async/queued answer |
| `204` | success, no body — ⭐ typical `DELETE` |
| ⭐ `400` vs `422` | ⭐ malformed (unparseable) vs **well-formed but semantically invalid** |
| ⭐⭐ `401` vs `403` | ⭐⭐ **not authenticated** (who are you?) vs **not authorised** (I know, and no) |
| `404` vs `410` | not found vs ⭐ **was here, is gone permanently** |
| ⭐ `409` | conflict — ⭐ duplicate, or a state machine violation |
| ⭐⭐ `412` | ⭐⭐ precondition failed — **`If-Match` lost the race** (Part 3) |
| `415` | unsupported media type |
| ⭐ `429` | rate limited — ⭐⭐ **must include `Retry-After`** (Day 123) |
| ⭐ `500` / `502` / `503` / `504` | ⭐ my bug / bad upstream reply / not accepting work / upstream timeout |

⭐⭐ **`401` vs `403` is asked constantly and answered wrongly.** ⭐ `401` means *authenticate and try
again* — it must carry `WWW-Authenticate`. `403` means *authenticated fine, still not allowed* —
**retrying with the same credentials is pointless.** ⚠️ ⭐ Returning `404` instead of `403` to avoid
leaking existence is a legitimate, deliberate choice — **make it deliberately** (Day 118).

# Part 3 — ⭐⭐ Conditional requests, and the lost update

```
⭐⭐ THE LOST UPDATE PROBLEM — the reason ETags exist, and the best thing on
⭐   today's page:
⭐
⭐   Alice GET /doc/7  ⇒ {"title": "Draft", "body": "..."}     (version 1)
⭐   Bob   GET /doc/7  ⇒ the same                              (version 1)
⭐   Alice PUT /doc/7  ⇒ changes the title    ✔
⭐   Bob   PUT /doc/7  ⇒ changes the body, ⚠️⚠️ SENDING THE WHOLE OBJECT HE READ
⭐                         ⇒ ⭐⭐ ALICE'S TITLE CHANGE IS SILENTLY GONE.
⭐   ⇒ ⭐ No error. No conflict. Nobody finds out until Alice notices next week.
```

```http
GET /doc/7                     ⇒  200 OK
                                  ETag: "a1b2c3"          ⭐ a version identifier

PUT /doc/7                        ⭐⭐ THE FIX — one header:
If-Match: "a1b2c3"             ⇒  200 OK    (still v1 ⇒ applied)
                               ⇒  ⭐⭐ 412 Precondition Failed (someone changed it first)
```

```
⭐⭐ THAT IS OPTIMISTIC CONCURRENCY CONTROL, AND IT IS THE SAME IDEA AS:
⭐   · ⭐ git push --force-with-lease           (Day 088 — compare-and-swap on a ref)
⭐   · ⭐ a compare-and-swap instruction        (Day 067)
⭐   · a `version` column with `WHERE version = ?` (Stage 5)
⭐   ⇒ ⭐⭐ ONE PATTERN, FOUR PLACES: "APPLY MY CHANGE ONLY IF NOBODY HAS MOVED
⭐        SINCE I LOOKED." ⭐ Recognising that it is one pattern is worth more
⭐        than remembering any of the four spellings.
```

```http
GET /users/42
If-None-Match: "a1b2c3"     ⇒  ⭐⭐ 304 Not Modified   (no body — bandwidth saved)
                            ⇒  200 OK + a new ETag    (it changed)
```

| ⭐ Validator | ⭐ Note |
|---|---|
| ⭐⭐ `ETag` (strong) | ⭐ byte-identical. A hash of the body, or a version number |
| ⭐ `W/"..."` (weak) | ⭐ semantically equivalent — ⚠️ **cannot be used with `If-Match`** |
| `Last-Modified` | ⚠️ ⭐⭐ **one-second resolution** ⇒ two changes in the same second are indistinguishable ⇒ prefer ETag |

# Part 4 — ⭐⭐ Cache-Control, and the header that leaks data

```http
Cache-Control: public, max-age=3600                    ⭐ any cache, 1 hour
Cache-Control: private, max-age=60                     ⭐⭐ BROWSER ONLY — never a shared cache
Cache-Control: no-cache                                ⭐⭐ store it, but REVALIDATE every time
Cache-Control: no-store                                ⭐ never write it down at all
Cache-Control: public, max-age=31536000, immutable     ⭐ a hashed asset filename
Cache-Control: max-age=60, stale-while-revalidate=600  ⭐⭐ serve stale, refresh in background
```

```
⭐⭐ `no-cache` DOES NOT MEAN "DO NOT CACHE". It means "cache it, but ask me
⭐   before using it" — a conditional request every time (Part 3). ⭐⭐ THE ONE
⭐   THAT MEANS DO NOT CACHE IS `no-store`, and it is what you want on anything
⭐   containing personal data or a token. ⭐ Getting these two backwards is the
⭐   most common caching mistake in a backend.
```

```
⚠️⚠️ ⭐⭐ THE `Vary` BUG THAT LEAKS ONE USER'S DATA TO ANOTHER:
⭐    a shared cache (a CDN, or nginx) keys entries BY URL. If two users hit
⭐    /api/me with different Authorization headers, ⭐⭐ THE SECOND USER GETS THE
⭐    FIRST USER'S CACHED RESPONSE.
⭐    ⇒ ⭐⭐ `Vary: Authorization` tells the cache the header is part of the key.
⭐    ⇒ ⭐⭐ AND THE SAFER RULE, WHICH IS WHAT I WOULD ACTUALLY SHIP:
⭐         ANY AUTHENTICATED RESPONSE GETS `Cache-Control: private, no-store`
⭐         UNLESS YOU HAVE DELIBERATELY DECIDED OTHERWISE. ⭐ Rely on `private`
⭐         and `no-store`, not on every intermediary honouring `Vary` correctly.
⭐    ⇒ ⭐ `Vary: Accept-Encoding` is the other one you almost always want, or
⭐         a cache may serve gzipped bytes to a client that did not ask for them.
```

⭐ **`Accept` / `Content-Type` are the negotiation pair:** the client says what it *wants*, the server
says what it *sent*. ⭐⭐ **Always send a `charset`** (`application/json` is UTF-8 by spec, but
`text/html` without one is a real XSS vector via charset sniffing — Day 127).

# Part 5 — ⭐ What your server must get right tomorrow

```
⭐⭐ THE MINIMUM CONTRACT FOR THE SERVER YOU START BUILDING ON DAY 103:
⭐   1. ⭐⭐ Content-Length ON EVERY RESPONSE (or chunked, or close the
⭐        connection) ⇒ ⭐ otherwise the client waits forever. Day 105's first bug.
⭐   2. ⭐ Content-Type with a charset.
⭐   3. ⭐⭐ HTTP/1.1 KEEPS THE CONNECTION OPEN BY DEFAULT ⇒ your loop must handle
⭐        MORE THAN ONE REQUEST per connection, or send `Connection: close`.
⭐   4. ⭐ A HEAD request returns the SAME HEADERS as GET and NO BODY —
⭐        ⭐⭐ including the same Content-Length. ⭐ Getting that wrong breaks
⭐        every cache and health checker that uses HEAD.
⭐   5. ⭐ Date, and a status line the client can actually parse.
⭐   6. ⭐⭐ AND THE SECURITY MINIMUM (Day 127): never echo a traceback into a
⭐        response body.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ "POST creates, PUT updates" | ⭐⭐ The distinction is **who chooses the id** — that is what makes PUT idempotent. |
| Assuming a timeout means it failed | ⭐⭐ The request may have succeeded and the *response* was lost. |
| ⭐⭐ **A retryable POST with no idempotency key** | ⭐⭐ Something will retry. Double charge. |
| 500 for invalid user input | ⭐ 4xx is you, 5xx is me — and 5xx is an alert. |
| ⭐ 403 when unauthenticated | ⭐⭐ 401 means *authenticate and retry*, with `WWW-Authenticate`. |
| ⭐ 201 without `Location` | ⭐ The client cannot find what you created. |
| ⭐⭐ **Read-modify-write with no `If-Match`** | ⭐⭐ Silent lost updates. Nobody notices for weeks. |
| `Last-Modified` for concurrency | ⭐ One-second resolution. Use an ETag. |
| ⭐⭐ **`no-cache` meaning "do not cache"** | ⭐⭐ It means revalidate. `no-store` is the one you meant. |
| ⭐ Cacheable authenticated response, no `Vary` | ⭐⭐ A shared cache serves one user's data to another. |
| `429` without `Retry-After` | ⭐ The client can only guess, and will guess badly. |
| ⭐ No `Content-Length` | ⭐ The client hangs. |

## Interview questions

**Q: What does idempotent mean, and why does it matter?**
> That N identical calls leave the server in the same state as one — it's about state, not about the
> response, so DELETE twice giving 204 then 404 is still idempotent. It matters because it's what
> makes a retry safe, and something will always retry: the client library, the load balancer, the
> queue, or a user pressing the button again. The dangerous case is a timeout, because a timeout
> doesn't mean it failed — the request may have succeeded and the response was lost. So retrying a PUT
> is harmless and retrying a POST charges the card twice. You don't get to opt out of retries; you
> only choose whether they're safe, which means either PUT with a client-chosen id or POST with an
> idempotency key.

**Q: 401 or 403?**
> 401 is "I don't know who you are — authenticate and try again", and it should carry a
> `WWW-Authenticate` header, because retrying with credentials is the expected next step. 403 is "I
> know who you are and you still can't", so retrying with the same credentials is pointless. The
> nuance worth mentioning is that returning 404 instead of 403 is sometimes right, to avoid leaking
> that a resource exists — but that should be a deliberate decision, not an accident.

**Q: Two users edit the same document. How do you stop one overwriting the other?**
> Optimistic concurrency with ETags. The GET returns an `ETag`, and the client sends it back as
> `If-Match` on the PUT. If the resource has changed since, the server returns 412 and the client has
> to re-read and merge. Without it you get silent lost updates — Bob sends the whole object he read
> five minutes ago, Alice's change disappears, no error, and nobody notices for a week. It's the same
> pattern as `git push --force-with-lease` and a compare-and-swap: apply my change only if nobody has
> moved since I looked.

**Q: What's the difference between `no-cache` and `no-store`?**
> `no-cache` means the response may be stored but must be revalidated before every use — a
> conditional request each time. `no-store` means don't write it down at all. People reach for
> `no-cache` when they mean `no-store`, which is the most common caching mistake in a backend. For
> anything with personal data or a token I'd use `private, no-store`.

**Q: How can caching leak one user's data to another?**
> A shared cache — a CDN or a reverse proxy — keys entries by URL. If `/api/me` is cacheable and two
> users hit it with different `Authorization` headers, the second gets the first user's response.
> `Vary: Authorization` tells the cache the header is part of the key, and that's the mechanical fix.
> But I wouldn't rely on every intermediary honouring `Vary` correctly — I'd make authenticated
> responses `private, no-store` by default and only opt into caching deliberately.

   the ones that would double-charge on a retry.

   the leak happen.** Then fix it two ways.

9. ⭐ Return `429` with `Retry-After` and honour it in a small client.

## 🎙️ Articulation drill

Record two minutes: **"Design the payment endpoint for a checkout."**

⭐ **Lead with the property, not the URL:** **"the first question isn't the path or the payload, it's
what happens when the client times out — because a timeout doesn't mean it failed, it means the
response was lost, and something will retry regardless of what I want."**

⭐⭐ **Then the design that follows:** *"so the endpoint has to be safe to repeat. Either it's a PUT to
a client-chosen id, or it's a POST carrying an idempotency key that the client generates. On a repeat
with the same key I return the *original* response rather than charging again — same status, same
body — so the retry is indistinguishable from success. That's the whole design; everything else is
detail."*

⭐⭐ **Then show the same pattern elsewhere, which is what makes it read as understanding:** *"and if
the endpoint were updating a resource rather than creating one, I'd want optimistic concurrency —
ETag on the GET, `If-Match` on the write, 412 if someone moved first. It's the same shape as
`--force-with-lease` in Git and a compare-and-swap: apply my change only if nobody has moved since I
looked. Without it you get silent lost updates, which nobody notices for weeks."*

⭐ **Close on the operational half:** *"and I'd be careful with status codes, because they're not
cosmetic — 5xx is an alert and 4xx isn't, so returning 500 for invalid input trains the team to ignore
the alert. Invalid card details are a 422; a downstream gateway timing out is a 504; my bug is a 500.
And the response gets `private, no-store`, because it has payment data in it."*
