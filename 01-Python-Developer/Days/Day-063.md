# Part 1 — ⭐⭐ `__repr__` is an operational feature

```python
# ⚠️ ⭐⭐ WITHOUT IT — this is what your log, your debugger and your test failure show:
[<app.models.Order object at 0x7f8a3c2d1e50>, <app.models.Order object at 0x7f8a3c2d1f10>]

# ⭐⭐ WITH IT:
[Order(id=1138, status=Status.SHIPPED, total=Decimal('49.99')),
 Order(id=1139, status=Status.PENDING, total=Decimal('12.00'))]
```

```
⭐⭐ THE RULES FOR __repr__, in priority order:
⭐   1. ⭐⭐ INCLUDE WHAT IDENTIFIES IT — the id, the key, the state. Not every field.
⭐   2. ⭐ MAKE IT LOOK CONSTRUCTIBLE: ClassName(field=value, ...) — ⭐ use !r on the values
⭐        so "" and None and "None" are distinguishable
⭐   3. ⭐⭐ NEVER RAISE. A __repr__ that touches a lazy relationship or a closed connection
⭐        FAILS EXACTLY WHEN YOU ARE DEBUGGING — the error report itself crashes.
⭐   4. ⭐⭐ NEVER INCLUDE SECRETS. It ends up in logs, in Sentry, in a screenshot.
⭐   5. ⭐ KEEP IT SHORT. A repr containing a 5,000-row list makes the log unreadable.
```

```python
@dataclass
class User:
    id: int
    email: str
    password_hash: str = field(repr=False)       # ⭐⭐ Day 057 — one argument, one leak prevented
    orders: list[Order] = field(default_factory=list, repr=False)   # ⭐ would print thousands
```

⚠️ ⭐⭐ **The lazy-relationship trap is worth naming:** a SQLAlchemy `__repr__` that includes
`self.orders` issues a query — **so printing a list of 100 users runs 100 queries** (Day 032's N+1,
triggered by a debug statement), and it raises if the session has closed. **Reprs touch only loaded,
local state.**

⭐ **`__str__`** is for the end user and falls back to `__repr__`. **If you implement one, implement
`__repr__`** — it is what containers, the REPL, the debugger and `logging`'s `%r` use.

# Part 2 — ⭐ Error messages are a design surface

```python
# ⚠️ ⭐⭐ USELESS — all three of these have appeared in real production logs:
raise ValueError("invalid input")
raise ValueError(f"bad value: {value}")          # ⭐ better, but bad how?
assert x > 0                                     # ⚠️ ⭐⭐ and asserts are STRIPPED by python -O

# ⭐⭐ USEFUL — what, what was expected, and where:
raise ValueError(
    f"discount must be between 0 and 1, got {value!r} for product {product_id!r}"
)
```

```
⭐⭐ A GOOD ERROR MESSAGE ANSWERS THREE QUESTIONS:
⭐   1. WHAT WENT WRONG        — "discount out of range"
⭐   2. ⭐ WITH WHAT VALUE      — {value!r}  ⇒ ⭐⭐ !r, so "" and None and "None" differ
⭐   3. ⭐⭐ WHERE / WHICH ONE   — which product, which row, which config key
⭐ ⇒ ⭐ and where practical, HOW TO FIX IT: "set DATABASE_URL, e.g. postgres://..."
```

⚠️ ⭐⭐ **Never use `assert` for validation.** `python -O` removes every assert statement, so your
input validation vanishes in exactly the configuration someone chose for production. **Asserts are for
invariants you believe cannot be false — a `raise` is for anything that can.**

⭐ **And the same applies to the `!r`:** an error saying `got None` is ambiguous between the object
`None` and the string `"None"` — **which is precisely the confusion you are trying to resolve at 3am.**

# Part 3 — ⭐ Operator overloading, judged

```
⭐⭐ THE TEST: would a reader guess what it does, correctly, without looking?
⭐   ✓ ⭐ Vector + Vector, Money + Money, Path / "sub", timedelta arithmetic
⭐   ✓ ⭐ `in` for containment, `<` for a natural order, `[]` for genuine indexing
⭐   ✗ ⭐⭐ `+` for "send to", `>>` for "pipe into", `%` for "apply template",
⭐        `&` for "and then" — ⭐⭐ every one of these has shipped in a real library,
⭐        and every one costs the reader a trip to the documentation.
```

```python
# ⭐ Money — a good case, and note what it REFUSES:
@dataclass(frozen=True)
class Money:
    amount: Decimal
    currency: str

    def __add__(self, other: "Money") -> "Money":
        if not isinstance(other, Money): return NotImplemented    # ⭐ Day 031
        if self.currency != other.currency:
            raise ValueError(f"cannot add {self.currency} to {other.currency}")   # ⭐⭐ refuse
        return Money(self.amount + other.amount, self.currency)

    def __mul__(self, n: int | Decimal) -> "Money": ...
    __rmul__ = __mul__                       # ⭐ 3 * money (Day 031)
    # ⭐⭐ deliberately NO __add__ for int — money plus 5 is meaningless without a currency
```

⭐⭐ **Refusing an operation is a design decision, not an omission.** `Money + 5` raising is better
than guessing a currency, and **saying "I deliberately did not define that" in a review is a stronger
answer than defining it.**

⭐ **Comparison and hashing (Day 029) are the two that must agree**: define `__eq__` and `__hash__`
over the *same* fields, or use `@dataclass(frozen=True)` and get both consistently.

# Part 4 — ⭐⭐ The debuggability checklist

```
⭐⭐ RUN THROUGH THIS BEFORE A CLASS IS "DONE":

⭐ IDENTITY & OUTPUT
⭐  □ ⭐⭐ __repr__ that identifies the object, never raises, and hides secrets
⭐  □ __eq__ and __hash__ agree, or frozen=True (Day 029)
⭐
⭐ CONSTRUCTION
⭐  □ ⭐⭐ __init__ does NO I/O — no network, no database, no file reads
⭐       ⇒ ⭐⭐ because a constructor that connects cannot be tested, cannot be constructed
⭐         in a REPL, and turns object creation into a failure point
⭐  □ collaborators are INJECTED, not constructed (Day 055)
⭐  □ ⭐ invalid states are unrepresentable — validate in __post_init__ or at the edge
⭐
⭐ SURFACE
⭐  □ ⭐ the public API is small; internals are _prefixed
⭐  □ ⭐⭐ immutable by default (frozen=True) unless mutation is the point
⭐  □ ⭐ type hints on every public method (Day 061)
⭐
⭐ FAILURE
⭐  □ ⭐⭐ errors name the value AND the context, with !r
⭐  □ raises specific exceptions from your package's base (Day 059)
⭐  □ ⭐ no bare except; no assert for validation (Day 060)
⭐
⭐ SIZE
⭐  □ ⭐ one responsibility; ⭐⭐ if the class name contains "Manager", "Handler", "Helper"
⭐       or "Util", ask what it actually does — those names usually mean "several things"
```

```python
# ⚠️ ⭐⭐ THE CONSTRUCTOR-I/O ANTI-PATTERN, and it is extremely common:
class Report:
    def __init__(self, user_id):
        self.user = db.query(User).get(user_id)      # ⭐⭐ a DB call to build an object
        self.rows = api.fetch(user_id)               # ⭐⭐ and a network call

# ⭐ THE FIX — construction is cheap and total; loading is explicit and testable:
@dataclass
class Report:
    user: User
    rows: list[Row]

    @classmethod                                     # ⭐ Day 045
    def load(cls, user_id: int, db: Repo, api: Client) -> "Report":
        return cls(db.get_user(user_id), api.fetch(user_id))
```

⭐⭐ **"Constructors do not perform I/O" is a rule worth defending in review**, and the argument is
practical rather than aesthetic: **you can build the object in a test, in a REPL, and from a fixture,
and there is exactly one place — `load` — where failure can happen.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **No `__repr__`** | ⭐⭐ Every log, debugger and test failure is worse. |
| ⭐ A `__repr__` that can raise | ⭐⭐ It fails exactly when you are debugging. |
| Secrets or huge collections in a repr | ⭐ `field(repr=False)`. |
| A repr that triggers a lazy load | ⭐⭐ N+1 queries from a debug print. |
| ⭐ `assert` for validation | ⭐⭐ Stripped by `python -O`. |
| Error messages without the value | ⭐ Name the value with `!r` and the context. |
| Overloading operators for novelty | ⭐ If a reader must look it up, use a method. |
| Defining `__eq__` without `__hash__` | ⭐ Day 029 — they must agree. |
| ⭐⭐ **I/O in `__init__`** | ⭐⭐ Untestable, unconstructible, failure at creation. |
| Constructing collaborators internally | ⭐ Inject them (Day 055). |
| A class named `...Manager` | ⭐ Usually several responsibilities. |

## Interview questions

**Q: What makes a class easy to debug?**
> A `__repr__` that identifies it, never raises, and doesn't leak secrets — because that string is
> what appears in every log line, debugger view and failing assertion. Error messages that name the
> offending value with `!r` and the context it came from. A constructor that does no I/O, so the object
> can be built in a test or a REPL and there's exactly one place where loading can fail. And a small
> public surface, so a reader knows what they're allowed to depend on.

**Q: Why does `__repr__` matter more than `__str__`?**
> Because `__repr__` is what the machinery uses. Containers call it on their elements, so printing a
> list of your objects uses it; the REPL uses it, the debugger uses it, `logging`'s `%r` uses it, and
> pytest uses it in assertion failures. `__str__` falls back to it, so implementing `__repr__` gives
> you both. It's the highest value-per-character method in the language, and `@dataclass` gives you a
> good one for free.

**Q: What could go wrong with a `__repr__`?**
> Three things. It can raise — if it touches a lazily-loaded relationship after the session closed, the
> error report itself crashes, which is a genuinely miserable experience. It can be slow or trigger
> queries: a SQLAlchemy repr including a relationship issues a query per object, so printing a hundred
> users runs a hundred queries from a debug statement. And it can leak — password hashes, tokens and
> API keys end up in logs and error trackers. So: local loaded state only, short, and
> `field(repr=False)` on anything sensitive.

**Q: Why shouldn't a constructor do I/O?**
> Because it makes the object impossible to create without its dependencies being live. I can't build
> one in a unit test, in a REPL, or from a fixture; every construction is a potential failure; and the
> class is now coupled to a database and an HTTP client. Splitting it — a plain constructor taking
> values, and a classmethod like `load` that does the fetching — means construction is total and
> cheap, there's exactly one place that can fail, and the collaborators are injected so I can pass
> fakes.

**Q: When is operator overloading a good idea?**
> When a reader would guess correctly without looking it up. `Money + Money`, `Vector + Vector`,
> `Path / "subdir"`, `in` for containment — those match existing intuitions. Using `>>` for "pipe
> into" or `+` for "send to" costs every reader a trip to the docs, which is a permanent tax for a
> one-time cleverness. I'd also say refusing an operation is a design decision: `Money + 5` should
> raise rather than guess a currency, and deliberately not defining something is a legitimate answer.

**Q: Why not use `assert` for validation?**
> Because `python -O` removes every assert statement, so validation written that way silently
> disappears in the configuration someone may well choose for production. Asserts are for invariants I
> believe cannot be false — a sanity check on my own logic. Anything that can legitimately be false at
> runtime, especially anything derived from input, needs a `raise`.

## 🎙️ Articulation drill

Record two minutes: **"What do you look for when reviewing a new class?"**

⭐ Start with the thing that costs the most later: **can I tell what an instance is from a log line?**
A `__repr__` that names the identifying fields, never raises, and excludes secrets and large
collections — because that string is what appears in every debugger, every test failure and every
error report.

⭐ Then construction: **does `__init__` do I/O?** If it queries a database or calls an API, the class
cannot be built in a test or a REPL, every construction is a failure point, and the dependencies are
hardcoded. **The fix is a plain constructor plus a `load` classmethod with the collaborators passed
in.**

⭐ Then failure: **do the errors name the offending value and its context**, do they use a specific
exception from the package's base, and is anything validated with `assert` — which `python -O`
deletes.

⭐⭐ **Then close on the framing that ties the block together:** *"all of it is the same question asked
five ways — will the person debugging this at 3am, who did not write it and cannot reproduce it, have
enough information from a traceback and a log line? Every one of these is cheap to add while writing
and impossible to add during an incident."*
