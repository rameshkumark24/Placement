# Day 139

**L-139** · **The repository pattern** — ⭐⭐ where it earns its keep, and where it is pure ceremony

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a repository is not "a layer for swapping databases" — nobody swaps
> databases. It is a place to put the queries so that the ORM's lifecycle rules stay inside one
> module, and the rest of the codebase cannot violate them by accident.**
>
> ⭐ Day 135 ended on `DetachedInstanceError` and said the structural fix was "don't let ORM objects
> escape". Day 136 said "put the `selectinload` in the repository". ⭐⭐ **Today is the module those
> two sentences were pointing at** — and the honest argument about when you don't need it.

---

# Part 1 — ⭐ The bad argument, and the real one

```
⭐⭐ THE ARGUMENT YOU WILL BE TOLD, AND SHOULD NOT REPEAT:

⭐   "A repository lets you swap Postgres for MongoDB later."
⭐
⭐   ⭐⭐ THIS IS FALSE IN PRACTICE, AND YOU SHOULD BE ABLE TO SAY WHY:
⭐   ⭐ nobody swaps. And when they do, the interface leaks anyway — your
⭐     `list_orders(limit, offset)` is a SQL idea; keyset pagination
⭐     (Day 121), transactions, and `SELECT ... FOR UPDATE` (Day 135) have no
⭐     Mongo equivalent. ⭐⭐ The abstraction that survives a real swap has to
⭐     be so thin it does nothing.

⭐⭐ THE THREE ARGUMENTS THAT ACTUALLY HOLD:

⭐  1. ⭐⭐ LIFECYCLE CONTAINMENT. ORM objects are only valid inside a session
⭐       (Day 135). ⭐ If they escape into routes, templates and background
⭐       tasks, every one of those places can trigger a lazy load, a detached
⭐       error, or an accidental write on `flush`. ⭐⭐ The repository is the
⭐       wall those objects do not cross.
⭐
⭐  2. ⭐⭐ QUERY LOCALITY. Every query against `orders` lives in ONE file.
⭐       ⭐ So "why is this endpoint slow" has one place to look, `selectinload`
⭐       has one place to live (Day 136), and ⭐⭐ tenant scoping has ONE place
⭐       it can be forgotten — which is Day 118's IDOR argument exactly.
⭐
⭐  3. ⭐ TESTABILITY OF THE LAYER ABOVE. Not "so I can fake the database" —
⭐       ⭐⭐ see Part 5, where I argue against that — but so the service reads
⭐       as domain logic with no query syntax in it.
⭐
⭐   ⇒ ⭐⭐ SAY THE REAL ONE IN AN INTERVIEW. "Swappability" marks you as
⭐        someone repeating a book. "Lifecycle containment and query locality"
⭐        marks you as someone who has debugged a `DetachedInstanceError`.
```

# Part 2 — ⭐⭐ The boundary: what crosses it

```python
# app/repositories/orders.py
class OrderRepository:
    def __init__(self, db: Session) -> None:
        self._db = db                                 # ⭐ session injected, never created

    def get(self, order_id: int, *, user_id: int) -> Order | None:
        stmt = (
            select(Order)
            .where(Order.id == order_id, Order.user_id == user_id)   # ⭐⭐ Day 118
            .options(selectinload(Order.items))                       # ⭐ Day 136
        )
        return self._db.scalars(stmt).one_or_none()

    def add(self, order: Order) -> None:
        self._db.add(order)                           # ⭐⭐ NO COMMIT — see Part 3

    def list_for_user(self, user_id: int, *, after_id: int | None, limit: int) -> list[Order]:
        stmt = select(Order).where(Order.user_id == user_id)
        if after_id is not None:
            stmt = stmt.where(Order.id > after_id)    # ⭐ keyset, Day 121
        return list(self._db.scalars(stmt.order_by(Order.id).limit(limit)))
```

```
⭐⭐ THE FOUR RULES OF THE BOUNDARY:

⭐  1. ⭐⭐ THE REPOSITORY NEVER COMMITS. It reads, adds, and deletes. The
⭐       TRANSACTION belongs to the caller — otherwise two repository calls in
⭐       one operation cannot be atomic, and Day 135's whole unit-of-work
⭐       argument collapses.
⭐
⭐  2. ⭐⭐ THE REPOSITORY NEVER RETURNS A `Query` OR A `Select`.
⭐       ⭐ `def query_orders(self) -> Select` is the anti-pattern: the caller
⭐       now composes SQL, so the query is NOT local, and every rule you moved
⭐       in here can be bypassed by adding one more `.where()` outside.
⭐       ⭐⭐ IT RETURNS RESULTS, NOT QUERIES.
⭐
⭐  3. ⭐ IT RAISES DOMAIN ERRORS OR RETURNS `None` — never `HTTPException`
⭐       (Day 130), never a `Response`. It does not know HTTP exists.
⭐
⭐  4. ⭐⭐ IT TAKES THE SCOPE AS A REQUIRED ARGUMENT. `get(order_id, *,
⭐       user_id)` — keyword-only and non-defaulted, so ⭐ forgetting the
⭐       tenant is a TypeError at import-test time, not an IDOR in production.
⭐       ⭐ Day 118: make the wrong thing hard to write.
```

# Part 3 — ⭐⭐ Who owns the transaction

```
⭐⭐ THE QUESTION THAT DECIDES YOUR ARCHITECTURE: WHERE DOES `commit()` LIVE?

⭐   ❌ IN THE REPOSITORY — every `add()` commits.
⭐        ⇒ ⭐⭐ two repository calls in one operation are TWO transactions.
⭐          Debit succeeds, credit fails, money vanishes. ⭐ Non-negotiable no.
⭐
⭐   ❌ IN THE DEPENDENCY (`get_db` commits on the way out).
⭐        ⇒ ⭐ tempting — one line, always correct-looking. ⭐⭐ But Day 132:
⭐          teardown runs AFTER the response is generated, so a commit failure
⭐          there cannot be turned into a 409. You get a 500 and a response
⭐          your handler already promised was a 201.
⭐
⭐   ✅ ⭐⭐ IN THE SERVICE — one commit at the end of the operation.
⭐        ⇒ ⭐ the service IS the unit of work. It knows what "the operation"
⭐          means; nothing below it does. ⭐⭐ A failure is catchable and
⭐          mappable to a status code, and the rollback is the session's
⭐          context manager doing its job.
```

```python
# app/services/orders.py         ⭐⭐ NOTE: imports no FastAPI (Day 133)
class OrderService:
    def __init__(self, db: Session, orders: OrderRepository, stock: StockRepository) -> None:
        self._db, self._orders, self._stock = db, orders, stock

    def place(self, user_id: int, sku: str, qty: int) -> OrderDTO:
        item = self._stock.reserve(sku, qty)             # ⭐ may raise OutOfStock
        order = Order(user_id=user_id, sku=sku, qty=qty)
        self._orders.add(order)
        self._db.commit()                                # ⭐⭐ ONE commit, one boundary
        return OrderDTO.model_validate(order)            # ⭐⭐ Part 4 — DTO out, not Order
```

> ⭐⭐ **"The service owns the transaction" is the single most useful sentence in this day.** It
> makes atomicity a property of an operation rather than of a call, and it is why the repository
> is deliberately incomplete on its own.

```
⭐ IF YOU HAVE MANY REPOSITORIES, NAME THE OWNER EXPLICITLY — the Unit of Work:

⭐   class UnitOfWork:
⭐       def __enter__(self):  self.orders = OrderRepository(self.db); return self
⭐       def __exit__(self, exc_type, *_):
⭐           self.db.rollback() if exc_type else self.db.commit()
⭐
⭐   ⇒ ⭐ Worth it when several repositories must move together and the
⭐        grouping is not obvious. ⭐⭐ Not worth it when `get_db` already gives
⭐        you one session per request and services are the only committers —
⭐        that IS a unit of work, just without the class.
```

# Part 4 — ⭐⭐ Do ORM objects leave the repository?

```
⭐⭐ THE HONEST ANSWER: IT DEPENDS, AND HERE IS THE DECIDING QUESTION —
⭐   ⭐ "DOES THIS OBJECT OUTLIVE THE SESSION?"

⭐  OPTION A — RETURN ORM OBJECTS, KEEP THE SESSION OPEN FOR THE WHOLE REQUEST
⭐    ⭐ Pros: no mapping code, no duplication, `model_validate` handles
⭐      serialisation, ⭐ and it is what 90% of FastAPI codebases do.
⭐    ⭐ Cons: ⭐⭐ any layer can lazy-load, so an N+1 can be introduced by
⭐      someone writing a template or a background task — ⭐ the containment
⭐      argument from Part 1 is weakened.
⭐    ⭐⭐ MAKE IT SAFE WITH: `lazy="raise"` (Day 136) + `expire_on_commit=False`
⭐      (Day 135). ⭐ Those two settings recover most of the discipline for free.
⭐
⭐  OPTION B — RETURN DTOs (dataclasses or Pydantic models)
⭐    ⭐ Pros: ⭐⭐ objects are inert. They cannot lazy-load, cannot be
⭐      accidentally mutated into an UPDATE on the next flush, and are safe to
⭐      hand to a Celery task or cache. ⭐ The service is genuinely testable
⭐      without a database.
⭐    ⭐ Cons: mapping code for every model, and ⭐⭐ two shapes to keep in sync.
⭐
⭐  ⇒ ⭐⭐ MY RULE: Option A inside the request, Option B for anything that
⭐       CROSSES A BOUNDARY — a queue, a cache, a response schema, a thread.
⭐       ⭐ i.e. the moment the session's lifetime stops guaranteeing validity,
⭐       the ORM object stops being the right type.
```

```
⭐⭐ THE MUTATION QUESTION PEOPLE GET WRONG:

⭐   order = repo.get(1, user_id=u)
⭐   order.status = "cancelled"          # ⭐⭐ THIS IS ALREADY AN UPDATE
⭐   # no repo.save() call anywhere
⭐   db.commit()                          # ⭐ ...and it persists
⭐
⭐   ⇒ ⭐⭐ SQLAlchemy's unit of work TRACKS the object; there is no `save()`.
⭐        ⭐ So a repository with an `update()` method is often theatre — the
⭐        mutation already happened. ⭐⭐ THIS IS PRECISELY WHY LETTING ORM
⭐        OBJECTS ROAM IS RISKY: mutating a field ANYWHERE in the request
⭐        writes to the database, with no call that looks like a write.
```

# Part 5 — ⭐⭐ Testing: the fake repository trap

```
⭐⭐ THE PROMISE: "with a repository interface, I can test services against an
⭐   in-memory fake and never touch a database."
⭐   ⭐⭐ THE PROBLEM: THE FAKE PASSES AND PRODUCTION FAILS. Every time, for the
⭐   same reasons:
⭐
⭐   ⭐ · the fake has no UNIQUE constraint → your duplicate-email test passes,
⭐        production raises IntegrityError
⭐   ⭐ · the fake has no NULL/type coercion, no CHECK, no foreign key
⭐   ⭐ · the fake has no transactions → your rollback path is never exercised
⭐   ⭐ · the fake's `list()` sorts by insertion; Postgres does not sort at all
⭐        unless you ORDER BY ⭐⭐ (the classic "works locally" pagination bug)
⭐   ⭐ · ⭐⭐ AND THE BIG ONE: it cannot catch an N+1, a missing index, or a
⭐        wrong join — the entire class of bug the repository exists to hold.
⭐
⭐   ⇒ ⭐⭐ Day 096's contract-test rule, applied: a double is only safe when
⭐        the real thing's behaviour is FULLY CAPTURED by the interface. ⭐ A
⭐        database's behaviour is not. It is constraints, ordering, isolation
⭐        and cost — none of which live in your method signatures.
```

```python
# ⭐⭐ THE ALTERNATIVE THAT ACTUALLY WORKS: A REAL DATABASE, ROLLED BACK.
@pytest.fixture
def db(engine):
    conn = engine.connect()
    trans = conn.begin()                       # ⭐⭐ outer transaction
    session = Session(bind=conn, join_transaction_mode="create_savepoint")
    yield session
    session.close()
    trans.rollback()                           # ⭐⭐ every test starts clean
    conn.close()
```

```
⭐⭐ WHY THIS IS THE RIGHT DEFAULT:
⭐   ⭐ real constraints, real types, real transactions, real query plans
⭐   ⭐ ~1–5 ms per test — ⭐⭐ fast enough that "it's slow" is usually a myth
⭐        measured against an idea rather than a stopwatch (Day 100A)
⭐   ⭐ `join_transaction_mode="create_savepoint"` means the SERVICE can call
⭐        `commit()` for real — ⭐⭐ it commits to a SAVEPOINT, so you are
⭐        testing the actual commit path and still rolling everything back
⭐   ⭐ one Docker/testcontainers Postgres for the suite; ⭐⭐ NOT SQLite —
⭐        different types, different constraint enforcement, no `RETURNING` on
⭐        old versions. ⭐ Testing on a different database is testing a
⭐        different program.
⭐
⭐ ⭐⭐ WHEN THE FAKE IS STILL RIGHT: for a repository that talks to something
⭐   SLOW OR EXTERNAL (a payment API, S3), where the interface really does
⭐   capture the behaviour you depend on — ⭐ and then you owe it a contract
⭐   test against the real thing (Day 096).
```

# Part 6 — ⭐ When you do not need this at all

```
⭐⭐ THE CEREMONY CASE — say this out loud in a design review:

⭐   class UserRepository:
⭐       def get(self, id): return self._db.get(User, id)
⭐       def add(self, u):  self._db.add(u)
⭐       def delete(self, u): self._db.delete(u)
⭐
⭐   ⇒ ⭐⭐ THIS IS A SESSION WITH EXTRA STEPS. It adds a file, an injection,
⭐        and a mock, and removes nothing. ⭐ SQLAlchemy's Session IS already a
⭐        repository + unit of work — that is literally the pattern it
⭐        implements. Wrapping it thinly is duplication (Day 090).
⭐
⭐⭐ THE DECISION RULE:
⭐   ADD A REPOSITORY WHEN a table has ⭐ NON-TRIVIAL queries, ⭐ a scoping rule
⭐   that must never be forgotten (Day 118), ⭐ loading strategies that matter
⭐   (Day 136), or ⭐ more than a couple of call sites.
⭐   ⭐⭐ SKIP IT for a CRUD table with three fields and one caller. ⭐ Add it
⭐   the day the third query appears — ⭐⭐ that is not "technical debt", that is
⭐   introducing structure when the structure has something to hold.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Justifying repositories with "so we can swap the database" | ⭐⭐ Nobody swaps, and the interface leaks anyway. Say lifecycle containment and query locality. |
| Committing inside the repository | Two calls in one operation become two transactions. The **service** owns the commit. |
| Returning a `Select`/`Query` | The caller composes SQL, so queries are no longer local and scoping can be bypassed. |
| Scope passed as an optional argument | Make it keyword-only and required, so forgetting it is a `TypeError`, not an IDOR. |
| Handing ORM objects to a Celery task or cache | They're only valid inside the session. Convert to a DTO at the boundary. |
| Writing an `update()` method | The mutation already happened; the unit of work tracks it. The method is theatre. |
| Testing services against an in-memory fake repo | No constraints, no transactions, no ordering, no N+1 detection. Use a real DB with rollback. |
| Using SQLite for tests, Postgres in production | Different types and constraint enforcement — you are testing a different program. |
| A repository that only forwards to the session | The `Session` **is** a repository + unit of work. Don't wrap it thinly. |
| `HTTPException` raised from a repository | It doesn't know HTTP exists. Domain error or `None`. |

## Interview questions

**Q: Why use a repository pattern with SQLAlchemy, given the Session already is one?**

> The swappability argument is wrong and I wouldn't use it — nobody replaces Postgres with Mongo,
> and if they did the interface would leak, because pagination, transactions and `FOR UPDATE` are
> SQL ideas. The two arguments that hold are lifecycle containment and query locality. ORM objects
> are only valid inside their session, so if they roam freely then any layer can trigger a lazy
> load, a detached error, or an accidental write — because mutating an attribute *is* an UPDATE.
> And query locality means every query for a table is in one file, so the tenant scoping has exactly
> one place it can be forgotten and the eager-loading strategy has one place to live. That said, for
> a three-field CRUD table with one caller, I'd skip it — a repository that only forwards to the
> session is a session with extra steps.

**Q: Where does `commit()` belong?**

> In the service, not the repository and not the dependency. Not the repository, because then two
> repository calls in one operation are two transactions — debit commits, credit fails, money
> disappears. Not the `get_db` dependency, because teardown runs after the response has already been
> generated, so a commit failure there can't be shaped into a 409; you get a 500 on a request whose
> handler already returned a 201. The service is the thing that knows what "the operation" means,
> so the service is the unit of work.

**Q: You've built repository interfaces so services can be tested against in-memory fakes. What's your concern?**

> That the fakes pass and production fails. A dict-backed fake has no UNIQUE constraint, so the
> duplicate-email test is green while production raises `IntegrityError`. It has no transactions, so
> the rollback path is never exercised. Its `list()` returns insertion order, so pagination bugs hide
> until Postgres returns rows in whatever order it likes. And most importantly it cannot detect an
> N+1 or a missing index — the exact class of bug the repository exists to contain. This is the
> contract-test rule: a double is only safe when the interface fully captures the real thing's
> behaviour, and a database's behaviour is constraints, ordering, isolation and cost. I'd use a real
> Postgres with a per-test transaction rollback instead — a couple of milliseconds per test.

**Q: What should not cross the repository boundary?**

> Outward: `Select` or `Query` objects, because then the caller composes SQL and the locality
> guarantee is gone; and ORM objects that will outlive the session — anything going to a queue, a
> cache, or another thread becomes a DTO first. Inward: HTTP concepts. The repository takes a user
> id, not a `Request`; it returns `None` or raises a domain error, never `HTTPException`, because
> the same function has to be callable from a Celery worker where there is no response to raise into.

## 🎙️ Articulation drill

**Two minutes: "Do you use the repository pattern? Why?"**

Open by rejecting the textbook reason out loud — it signals you have used this rather than read about
it. Then give the two real ones: ORM objects have a lifetime, and the repository is the wall they
don't cross; and every query for a table lives in one file, so scoping and eager-loading each have
exactly one place they can be forgotten. Say where the commit lives and why. Then give the limit
honestly: for a three-field CRUD table it's a session with extra steps, and you'd add it when the
third non-trivial query appears. Close on the testing point — **the fake repository is the trap, not
the feature**, because the bugs it hides are precisely the ones the layer exists to contain.
