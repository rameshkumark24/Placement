> ⭐⭐ **The sentence to own: Redis Pub/Sub is at-most-once with no persistence — a subscriber that is
> offline for two seconds misses everything published in those two seconds, permanently, and nothing
> anywhere reports it.**
>
> ⭐ That is not a flaw; it is the contract, and there are four things it is genuinely the best tool
> for. ⭐⭐ But if a message *must* be processed, you want Streams — and the whole difference is one
> data structure: **the pending entries list.**

# Part 1 — ⭐ Pub/Sub: the contract, stated honestly

```
⭐   SUBSCRIBE news          ⭐ PSUBSCRIBE news.*      ⭐ pattern
⭐   PUBLISH news "hello"    ⭐⭐ returns the NUMBER OF SUBSCRIBERS that
⭐                              received it — ⭐ your only feedback, and
⭐                              a 0 is often the bug you are looking for

⭐⭐ THE PROPERTIES, ALL OF THEM:
⭐   ⭐⭐ AT-MOST-ONCE. No persistence, no replay, no acknowledgement.
⭐   ⭐⭐ IF NOBODY IS LISTENING, THE MESSAGE IS DISCARDED SILENTLY.
⭐   ⭐ Delivered to ALL current subscribers (fan-out, not work sharing).
⭐   ⭐ No ordering guarantee across channels; no history; no offset.
⭐   ⇒ ⭐⭐ A DEPLOY IS A GAP. Every rolling restart drops whatever was
⭐     published while a consumer was reconnecting, and your logs will
⭐     be completely clean.
```

```
⭐⭐ THE FOUR THINGS IT IS GENUINELY BEST FOR — note what they share:
⭐   ① ⭐⭐ CACHE INVALIDATION BROADCAST (Day 206's L1 problem). ⭐ A
⭐      missed invalidation is bounded by the L1 TTL, so loss degrades
⭐      to staleness, not to error.
⭐   ② ⭐ LIVE CONFIG / FEATURE-FLAG RELOAD — same reasoning, plus a
⭐      periodic poll as the backstop.
⭐   ③ ⭐⭐ WEBSOCKET FAN-OUT ACROSS APP INSTANCES — Day 144's exact
⭐      problem. User A is connected to pod 3; the event happens on pod
⭐      7. ⭐ A dropped message is a missed live update, and the client
⭐      refetches on reconnect anyway.
⭐   ④ ⭐ PRESENCE, TYPING INDICATORS, LIVE COUNTERS — inherently
⭐      ephemeral.
⭐   ⇒ ⭐⭐ THE COMMON PROPERTY: ***THE NEXT MESSAGE MAKES THE LOST ONE
⭐     IRRELEVANT.*** ⭐ If that is not true of your data, Pub/Sub is
⭐     the wrong tool and no amount of care will fix it.
```

```
⭐⭐ THE THREE GOTCHAS THAT BITE IN PRODUCTION:
⭐  ① ⭐⭐ A SUBSCRIBED CONNECTION CAN ONLY RUN SUBSCRIBE COMMANDS.
⭐     ⇒ ⭐ You need a DEDICATED connection for the listener, outside
⭐       your normal pool (Day 197). ⭐⭐ People take one from the pool
⭐       and then wonder why the pool is exhausted.
⭐  ② ⭐⭐ A SLOW SUBSCRIBER IS ***DISCONNECTED***, NOT BUFFERED.
⭐     `client-output-buffer-limit pubsub 32mb 8mb 60` ⇒ exceed it and
⭐     ⭐⭐ REDIS DROPS THE CLIENT. ⭐ Your consumer reconnects, misses
⭐     everything in between, and logs nothing but a reconnect.
⭐     ⇒ ⭐ Consume fast and hand off to a queue; never do work inside
⭐       the message handler.
⭐  ③ ⭐ IN CLUSTER MODE, `PUBLISH` IS BROADCAST TO ***EVERY NODE*** —
⭐     ⭐⭐ so pub/sub traffic does not shard and becomes a scaling
⭐     ceiling. ⭐ Redis 7's `SPUBLISH`/`SSUBSCRIBE` (sharded pub/sub)
⭐     confines it to one shard. Use it if you are on a cluster.
```

# Part 2 — ⭐⭐ Streams: the append-only log

```sql
XADD events '*' type "order.paid" order_id 91
--  ⇒ ⭐ "1755590412345-0"   ⭐⭐ ms-timestamp + sequence, MONOTONIC
XADD events MAXLEN '~' 100000 '*' …    -- ⭐⭐ TRIM. See Part 5.
XRANGE   events - +                    -- ⭐ history, both directions
XREAD BLOCK 5000 STREAMS events '$'    -- ⭐ tail -f, from "now"
XLEN events
```

```
⭐⭐ WHAT A STREAM IS AND PUB/SUB IS NOT:
⭐   ⭐ PERSISTENT — it is a data structure; it survives, it replicates,
⭐     it is in your RDB/AOF (Day 205).
⭐   ⭐⭐ REPLAYABLE — `XRANGE` from any id. A consumer that was down
⭐     for ten minutes catches up.
⭐   ⭐ ORDERED, with a total order and an id you can bookmark.
⭐   ⭐⭐ AND — the actual reason it exists — ***CONSUMER GROUPS***.
```

# Part 3 — ⭐⭐ Consumer groups and the PEL

```sql
XGROUP CREATE events workers '$' MKSTREAM    -- ⭐ '$'=new only, '0'=all
XREADGROUP GROUP workers worker-3 COUNT 10 BLOCK 5000 STREAMS events '>'
--  ⭐⭐ '>' = "entries never delivered to ANY consumer in this group"
--  ⭐    an explicit id = "MY pending entries, redelivered"
XACK events workers 1755590412345-0          -- ⭐⭐ done. Remove from PEL.
```

```
⭐⭐ THE PEL — PENDING ENTRIES LIST — IS THE WHOLE FEATURE.
⭐   ⭐ When `XREADGROUP` hands you an entry, Redis records:
⭐        (entry id, consumer name, delivery time, delivery count)
⭐   ⭐⭐ IT STAYS THERE UNTIL YOU `XACK`.
⭐   ⇒ ⭐⭐ IF YOUR WORKER DIES MID-JOB, THE ENTRY IS STILL PENDING AND
⭐     ANOTHER WORKER CAN CLAIM IT. ⭐⭐ THAT IS AT-LEAST-ONCE DELIVERY,
⭐     WHICH IS EXACTLY WHAT DAY 142 SAID IS THE ONLY REAL GUARANTEE —
⭐     ⭐ and therefore your consumer must be IDEMPOTENT (Day 184 #6).
⭐   ⭐ A list (Day 204) has no PEL, which is precisely why it is not a
⭐     reliable queue.
```

```sql
-- ⭐ INSPECT: what is stuck, with whom, for how long, how many times
XPENDING events workers - + 10
XPENDING events workers IDLE 60000 - + 10 worker-3
-- ⭐⭐ RECLAIM stalled work — the reaper, in one command (6.2+):
XAUTOCLAIM events workers worker-9 60000 0 COUNT 10
--        ⭐ min-idle-time: only entries untouched for 60 s
-- ⭐ XCLAIM is the older, per-id form.
```

```python
# ⭐⭐ THE CONSUMER LOOP, COMPLETE — this is the shape worth memorising
def consume(group, name):
    while True:
        # ⭐ ① reclaim anything abandoned by a dead worker
        _, claimed, _ = r.xautoclaim("events", group, name,
                                     min_idle_time=60_000, start_id="0-0",
                                     count=10)
        for eid, fields in claimed:
            handle_with_dlq(eid, fields, group)

        # ⭐ ② read new entries
        resp = r.xreadgroup(group, name, {"events": ">"},
                            count=10, block=5000)
        for _stream, entries in resp or []:
            for eid, fields in entries:
                handle_with_dlq(eid, fields, group)

def handle_with_dlq(eid, fields, group):
    # ⭐⭐ THE POISON-PILL GUARD (Day 142). Without it, one bad message
    #    is redelivered forever and blocks nothing but wastes everything.
    info = r.xpending_range("events", group, eid, eid, 1)
    if info and info[0]["times_delivered"] > 5:
        r.xadd("events:dlq", {"id": eid, **fields})   # ⭐ park it
        r.xack("events", group, eid)                  # ⭐⭐ and ACK, or
        return                                        #    it stays
    try:
        process(fields)                    # ⭐⭐ MUST BE IDEMPOTENT
        r.xack("events", group, eid)       # ⭐⭐ ACK ***AFTER*** the
    except Exception:                      #    work, never before
        log.exception("stream handler failed", extra={"entry": eid})
        # ⭐ no ack ⇒ it stays pending ⇒ it will be reclaimed
```

# Part 4 — ⭐⭐ Choosing: Streams, Kafka, SQS, or Postgres

```
⭐⭐ THE HONEST COMPARISON:

⭐   REDIS PUB/SUB   at-most-once · no history · fan-out
⭐        ⇒ ⭐ live updates where the next message supersedes the last
⭐   REDIS LIST      at-most-once (no ack) · one consumer per message
⭐        ⇒ ⭐ throwaway work; ⭐⭐ do not use for anything that matters
⭐   ⭐⭐ REDIS STREAMS  at-least-once · replay · consumer groups ·
⭐        ⭐ retention bounded by MEMORY
⭐        ⇒ ⭐⭐ RIGHT WHEN: you already run Redis, volume is moderate
⭐          (tens of thousands/sec), retention is hours-to-days, and you
⭐          do not want another system. ⭐ This covers a lot of real
⭐          applications.
⭐   KAFKA           at-least-once · ⭐⭐ retention in DAYS/WEEKS ON DISK
⭐        · partitions · replay from any offset · huge throughput
⭐        ⇒ ⭐⭐ RIGHT WHEN: multiple independent consumer groups,
⭐          long retention, event sourcing, or volume beyond one box's
⭐          RAM. ⭐ Cost: a real distributed system to operate.
⭐   SQS / PUBSUB    at-least-once · managed · effectively infinite
⭐        ⇒ ⭐ right when you want none of the operations.
⭐   ⭐⭐ POSTGRES + SKIP LOCKED (Day 196)
⭐        ⇒ ⭐⭐ RIGHT WHEN: the work is transactional with your data.
⭐          ⭐⭐ ENQUEUE IN THE SAME TRANSACTION AS THE WRITE AND THE
⭐          DUAL-WRITE PROBLEM ***DISAPPEARS ENTIRELY*** — no outbox
⭐          needed, because the queue IS the database. ⭐ This is
⭐          underrated and should be your default below ~1,000 jobs/sec.

⭐⭐ AND THE POINT TO MAKE ABOUT ALL OF THEM: ***THE DELIVERY GUARANTEE
⭐   IS THE SAME — AT-LEAST-ONCE.*** ⭐ So the consumer is idempotent
⭐   regardless of which you pick, and choosing a fancier broker does not
⭐   remove that obligation. ⭐⭐ Day 184's invariant #6, one more time.
```

# Part 5 — ⭐ Operating streams

```
⭐⭐ THE #1 STREAMS INCIDENT: ***THEY GROW FOREVER.*** `XADD` with no
⭐   trimming, 5,000/sec, 200 bytes each ⇒ ⭐⭐ ~86 GB/DAY, IN RAM.
⭐   ⭐ `XADD s MAXLEN ~ 100000 * …` — ⭐⭐ THE `~` IS NOT OPTIONAL: it
⭐     trims to "approximately" that length at radix-tree node
⭐     boundaries, which is O(1)-ish. ⭐⭐ EXACT `MAXLEN` (no `~`) IS
⭐     O(n) AND CAN BLOCK THE SERVER (Day 203).
⭐   ⭐ `MINID ~ <ts>` trims by age instead — usually what you mean.
⭐   ⭐⭐ AND TRIMMING DOES NOT RESPECT THE PEL: you can trim away
⭐     entries a consumer group has not acked. ⭐ Keep retention
⭐     comfortably longer than your worst consumer lag, and alert on lag.

⭐⭐ THE #2 INCIDENT: ***THE PEL GROWS FOREVER.*** A consumer dies with
⭐   entries pending; nobody claims them; the group's PEL grows without
⭐   limit and `XPENDING` gets slower.
⭐   ⇒ ⭐⭐ AN `XAUTOCLAIM` REAPER IS NOT OPTIONAL. It is part of the
⭐     design, not an enhancement.
⭐   ⇒ ⭐ Delete consumers that are gone: `XGROUP DELCONSUMER`.

⭐⭐ THE THREE METRICS:
⭐   ⭐ `XLEN` — stream length (is trimming working?)
⭐   ⭐⭐ LAG: `XINFO GROUPS` gives `lag` and `pending` per group.
⭐     ⭐⭐ RISING `pending` MEANS CONSUMERS ARE FAILING OR DYING —
⭐     it is the single most important stream metric.
⭐   ⭐ Oldest-pending idle time from `XPENDING` — how stale is the
⭐     worst stuck entry?
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Using Pub/Sub for work that must happen | At-most-once with no persistence; an offline subscriber loses everything silently. |
| Ignoring `PUBLISH`'s return value | Zero subscribers is often exactly the bug you're chasing. |
| Taking the subscriber connection from the pool | A subscribed connection can only run subscribe commands. |
| Doing work inside the message handler | A slow subscriber gets disconnected by the output buffer limit. |
| Regular `PUBLISH` in cluster mode | It broadcasts to every node. Use `SPUBLISH` on Redis 7. |
| Using a list where a Stream belongs | No PEL means no acknowledgement and no reclaim. |
| Acking before doing the work | The entry leaves the PEL and a crash loses it. |
| No `XAUTOCLAIM` reaper | Entries from dead workers stay pending forever. |
| No delivery-count check | One poison message is redelivered forever. |
| Parking a message in a DLQ without acking it | It stays pending as well as being in the DLQ. |
| `XADD` with no `MAXLEN` | 5,000/sec at 200 bytes is ~86 GB a day, in RAM. |
| Exact `MAXLEN` without `~` | It's O(n) and can block the server. |
| Trimming shorter than your worst consumer lag | Trimming ignores the PEL and discards unacked entries. |
| Not graphing `pending` per group | Rising pending is the clearest signal consumers are dying. |
| Assuming a fancier broker removes idempotency | Every option here is at-least-once. |

## Interview questions

**Q: Pub/Sub or Streams?**

> Depends on one question: if a message is lost, does it matter? Pub/Sub is at-most-once with no
> persistence, no replay and no acknowledgement — a subscriber that's offline for two seconds during a
> rolling deploy misses everything published in those two seconds, permanently, with clean logs. That's
> the contract, and it's genuinely the right tool for four things: cache invalidation broadcast, live
> config reload, WebSocket fan-out across app instances, and presence. What they share is that the
> next message makes the lost one irrelevant, so loss degrades to staleness rather than error. If
> that's not true of your data, you want Streams — persistent, replayable, ordered, and crucially with
> consumer groups and a pending entries list, so an entry stays pending until acknowledged and can be
> reclaimed if a worker dies. That's at-least-once delivery, which means the consumer has to be
> idempotent, and that obligation doesn't go away no matter which broker you pick.

**Q: How do Redis Streams handle a worker dying mid-job?**

> Through the PEL. When `XREADGROUP` hands an entry to a consumer, Redis records the entry id, the
> consumer name, the delivery time and a delivery count, and it stays there until `XACK`. So a worker
> that dies leaves its entries pending rather than losing them, and another worker can take them over
> with `XAUTOCLAIM` filtered by minimum idle time. That's the piece that makes it a real queue and the
> piece a Redis list doesn't have. Two things have to be built deliberately though. The reaper isn't
> optional — without a running `XAUTOCLAIM` loop, entries from dead workers stay pending forever and
> the PEL grows unbounded. And you need a delivery-count check, because a message that always throws
> gets redelivered forever; past a threshold it goes to a dead-letter stream and gets acked, since
> parking it without acking leaves it pending as well.

**Q: When would you use Redis Streams over Kafka?**

> When I already run Redis, the volume is moderate — tens of thousands a second rather than millions —
> retention is measured in hours or days rather than weeks, and I don't want another distributed system
> to operate. That covers a lot of real applications. Kafka earns its complexity when you need long
> disk-based retention, many independent consumer groups replaying from arbitrary offsets, event
> sourcing, or throughput beyond what one machine's RAM can hold — because Streams retention is bounded
> by memory, which is the real ceiling. The option I'd actually raise first though is Postgres with
> `SKIP LOCKED`, because if the work is transactional with your data you can enqueue in the same
> transaction as the write, and the dual-write problem disappears entirely — no outbox needed, because
> the queue *is* the database. Below roughly a thousand jobs a second that's usually the best answer
> and it's the one people skip past.

**Q: What's the most common Streams incident?**

> Unbounded growth. `XADD` doesn't trim by default, so at five thousand entries a second at two hundred
> bytes you're adding around eighty-six gigabytes a day, in RAM, until the instance dies. The fix is
> `MAXLEN ~` or `MINID ~` on every `XADD`, and the tilde matters: it trims approximately, at radix-tree
> node boundaries, which is cheap, whereas exact `MAXLEN` is O(n) and can block the server — which on
> a single-threaded server means an outage. The subtlety is that trimming doesn't respect the PEL, so
> you can trim away entries a consumer group hasn't acknowledged, which means retention has to stay
> comfortably longer than your worst consumer lag and you need to alert on that lag. The second
> incident is the mirror image: the PEL itself growing forever because consumers died and nothing
> claims their entries.

**Q: What do you lose if Redis dies right now?**

> That's the question I'd want every team to be able to answer in one sentence, and it's the honest
> summary of the whole block. For a well-designed system: the cache, which degrades to slow rather than
> broken; up to a second of counters if AOF is on `everysec`, plus whatever hadn't replicated if it's a
> failover rather than a crash, because Redis replication is always asynchronous; any locks, which
> means duplicate work but not incorrect data, since the actual invariants are database constraints;
> and rate limits, which fail open for capacity and closed for login. What should *not* be on that list
> is anything I can't recompute — if losing Redis loses data that matters, then Redis became a database
> without anyone deciding it should, and the durability ceiling of about a second plus failover loss is
> now the ceiling for something that needed better.
