# Day 345 🔗

**P-345** · 🔗 **Design 1 — the URL shortener** — ⭐⭐ key generation, and the analytics write

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a URL shortener is a trivial read path and a deceptively hard write path —
> the interesting problems are generating short keys without coordination or collisions, and
> absorbing a click-analytics write on every single redirect, which is a hundred times more writes
> than the feature that gets all the attention.**

---

# Part 1 — ⭐ 0–5: scope and non-functionals

```
⭐⭐ FUNCTIONAL — THREE, AND SAY WHAT IS OUT:
⭐   ① Create a short URL from a long one.
⭐   ② Redirect a short URL to the long one.
⭐   ③ ⭐ Custom aliases and expiry.
⭐   ⭐⭐ OUT: user accounts, spam detection, QR codes,
⭐     link-in-bio pages, ⭐ and ***detailed*** analytics
⭐     dashboards (⭐ though the click ***write*** stays in,
⭐     because it is the interesting half).

⭐⭐ NON-FUNCTIONAL:
⭐   ⭐ 100 M new URLs/day. Read:write = 100:1. 10-year
⭐     retention.
⭐   ⭐ ⭐⭐ REDIRECT p99 < 50 ms — this is a link click; the
⭐     user is staring at a blank tab.
⭐   ⭐ ⭐⭐ AVAILABILITY MATTERS MORE THAN CONSISTENCY FOR
⭐     REDIRECTS. ⭐ A newly created link taking 200 ms to be
⭐     globally visible is fine; ⭐ a redirect returning 500 is
⭐     not.
⭐   ⭐ Short keys — ⭐⭐ SHORTNESS IS THE PRODUCT.
```

# Part 2 — ⭐⭐ 5–10: the estimate, and what it decides

```
⭐⭐ WRITES: 10^8 / 10^5 s = ***1,000/s***; ⭐ peak ×3 = 3,000/s.
⭐⭐ READS:  100× ⇒ ***100,000/s***; ⭐ peak ***300,000/s***.
⭐   ⇒ ⭐⭐ SO THE READ PATH MUST BE A CACHE OR A CDN, AND THE
⭐     WRITE PATH CAN BE ORDINARY.

⭐⭐ STORAGE: ~500 B/row × 10^8/day = 50 GB/day
⭐   ⇒ ⭐ 18 TB/year, ***180 TB over ten years***.
⭐   ⇒ ⭐⭐ SO IT IS SHARDED — AND NOW I HAVE A REASON.

⭐⭐ KEY SPACE — ⭐⭐ THE ESTIMATE THAT DECIDES THE PRODUCT:
⭐   ⭐ 10^8/day × 365 × 10 = ***3.65 × 10^11 URLs***.
⭐   ⭐ Base62: 62^7 = 3.5 × 10^12.
⭐   ⇒ ⭐⭐ SEVEN CHARACTERS IS ENOUGH WITH ~10× HEADROOM. SIX
⭐     (5.6 × 10^10) IS NOT. ⭐ Say this out loud — it is a
⭐     one-line calculation that answers "how long is the key?"
⭐     definitively instead of by taste.

⭐⭐ HOT SET: assume 20% of links get 80% of traffic on any
⭐   day ⇒ 2 × 10^7 × 500 B = ***10 GB***.
⭐   ⇒ ⭐⭐ ONE REDIS NODE ANSWERS 300,000 READS/S. ⭐ That is
⭐     the whole read architecture, and it costs almost nothing.
```

# Part 3 — ⭐⭐ 10–18: API and data model

```
⭐⭐ API:
⭐   ⭐ `POST /v1/urls`
⭐       `{long_url, custom_alias?, expires_at?}`
⭐       `-> 201 {short_url, key, expires_at}`
⭐       ⭐ Header: `Idempotency-Key` (Day 335).
⭐   ⭐ `GET /{key}` ⇒ ***302*** + `Location` (Part 5).
⭐   ⭐ `DELETE /v1/urls/{key}`
⭐   ⭐ `GET /v1/urls/{key}/stats?from=&to=`

⭐⭐ DATA MODEL:
⭐   `urls(key PK, long_url, owner_id, created_at, expires_at)`
⭐   ⭐ ⭐⭐ SHARD KEY = `key`. ⭐ Every read is by key, it is
⭐     immutable, it is uniformly distributed by construction
⭐     (it is a hash or a counter encoding), ⭐⭐ AND IT PASSES
⭐     ALL FOUR OF DAY 329'S TESTS. ⭐ Say that.
⭐   ⭐ `clicks` — ⭐⭐ NOT IN THE SAME DATABASE. Part 6.

⭐⭐ AND THE SIZING NOTE WORTH MAKING:
⭐   ⭐ The `long_url` is the bulk of the row and averages
⭐     ~200–500 B (⭐ tracking parameters make real URLs long).
⭐   ⇒ ⭐ Nothing to do about it, ⭐⭐ BUT SAYING IT SHOWS THE
⭐     STORAGE NUMBER WASN'T INVENTED.
```

# Part 4 — ⭐⭐ 18–30: key generation — four approaches

```
⭐⭐ ① ***HASH THE URL, TAKE 7 CHARACTERS.***
⭐   ⭐ `base62(md5(url))[:7]`
⭐   ⭐ ✔ Deterministic ⇒ the same URL gives the same key ⇒ free
⭐     deduplication.
⭐   ⭐ ✘ ⭐⭐ COLLISIONS ARE CERTAIN AT THIS SCALE. ⭐ Birthday
⭐     bound: with 3.5 × 10^12 slots, collisions become likely
⭐     around √(3.5×10^12) ≈ ***1.9 million keys*** —
⭐     ⭐⭐ SO YOU HIT THEM ON DAY ONE, NOT IN YEAR NINE.
⭐   ⇒ ⭐ Fix: on collision, append a salt and rehash — ⭐⭐ WHICH
⭐     REQUIRES A READ-BEFORE-WRITE ***OR*** A UNIQUE
⭐     CONSTRAINT AND A RETRY LOOP. ⭐ The constraint is
⭐     correct; the read-check is a race (Day 310).
⭐   ⇒ ⭐ Also ✘: dedup is often ***wrong product behaviour*** —
⭐     two users shortening the same URL usually want separate
⭐     analytics.

⭐⭐ ② ***RANDOM 7 CHARACTERS, RETRY ON CONFLICT.***
⭐   ⭐ ✔ Simple, unguessable, no coordination.
⭐   ⭐ ✔ ⭐⭐ AT 3.65×10^11 USED OF 3.5×10^12, OCCUPANCY IS
⭐     ~10%, SO A COLLISION RETRY HAPPENS ~1 IN 10 INSERTS AT
⭐     THE ***END*** OF TEN YEARS AND ESSENTIALLY NEVER BEFORE.
⭐   ⭐ ✘ One extra round trip on conflict; ⭐ needs the unique
⭐     constraint to be the arbiter, not a `SELECT`.
⭐   ⇒ ⭐⭐ THIS IS THE ANSWER FOR MOST SYSTEMS.

⭐⭐ ③ ***COUNTER + BASE62 ENCODE.***
⭐   ⭐ ✔ No collisions ever, by construction. ⭐ ✔ Shortest
⭐     possible keys early on.
⭐   ⭐ ✘ ⭐⭐ SEQUENTIAL KEYS ARE ENUMERABLE — anyone can walk
⭐     your entire link database, ⭐ which is a real privacy
⭐     problem for "unlisted" links.
⭐   ⭐ ✘ A global counter is a coordination point.
⭐   ⇒ ⭐⭐ FIX BOTH AT ONCE: ***RANGE ALLOCATION***. Each app
⭐     instance takes a block of 10,000 ids from a counter
⭐     service, ⭐ then encodes them ⭐⭐ WITH A KEYED
⭐     PERMUTATION (e.g. Feistel/multiply-by-a-coprime mod 62^7)
⭐     SO THE OUTPUT IS NON-SEQUENTIAL WHILE STILL BIJECTIVE.
⭐   ⇒ ⭐ A crash loses up to 10,000 keys. ⭐⭐ WHO CARES — THE
⭐     KEY SPACE IS 3.5 TRILLION. ⭐ Saying that is the point:
⭐     you priced the downside.

⭐⭐ ④ ***PRE-GENERATED KEY POOL*** — a background job fills a
⭐   table of unused keys; creation pops one.
⭐   ⭐ ✔ ⭐⭐ CREATION IS A SINGLE `UPDATE … RETURNING` WITH NO
⭐     RETRY LOOP AND NO COLLISION LOGIC AT ALL.
⭐   ⭐ ✘ A pool to monitor — ⭐⭐ AND IF IT EMPTIES, CREATION
⭐     STOPS. Alert on pool depth.
⭐   ⇒ ⭐ Nice answer, and mentioning it shows you thought past
⭐     the obvious two.

⭐⭐ AND THE CUSTOM-ALIAS INTERACTION: ⭐⭐ CUSTOM ALIASES SHARE
⭐   THE KEY SPACE, SO THEY MUST GO THROUGH THE SAME UNIQUE
⭐   CONSTRAINT — ⭐ and you need a reserved-words list
⭐   (`api`, `admin`, `login`, `static`) ⭐⭐ OR SOMEONE WILL
⭐   REGISTER `/api` AND BREAK YOUR OWN ROUTING.
```

# Part 5 — ⭐⭐ The redirect: 301 vs 302, and it is not a trivia question

```
⭐⭐ ***301 PERMANENT***
⭐   ⭐ ✔ The browser caches it — ⭐⭐ SUBSEQUENT CLICKS NEVER
⭐     REACH YOU. ⭐ Enormous load reduction.
⭐   ⭐ ✘ ⭐⭐ AND THEREFORE: NO ANALYTICS AFTER THE FIRST CLICK,
⭐     AND ***YOU CANNOT CHANGE OR DELETE THE LINK*** — the
⭐     browser will keep going to the old target, sometimes for
⭐     months, ⭐ and there is no way to purge it.
⭐   ⇒ ⭐⭐ A 301 ON A LINK THAT LATER TURNS OUT TO POINT AT
⭐     MALWARE IS A PROBLEM YOU CANNOT FIX.

⭐⭐ ***302 FOUND (or 307)***
⭐   ⭐ ✔ Every click hits you ⇒ ⭐⭐ ANALYTICS, REVOCATION,
⭐     EXPIRY, A/B TARGETS, GEO ROUTING.
⭐   ⭐ ✘ 100× more traffic.
⭐   ⇒ ⭐⭐ CHOOSE 302, AND SAY WHY: ***THE ANALYTICS AND THE
⭐     ABILITY TO REVOKE ARE THE PRODUCT.*** ⭐ Bitly, TinyURL
⭐     and the rest all serve 302 for exactly this reason.
⭐   ⇒ ⭐ And add `Cache-Control: private, max-age=0` so
⭐     intermediaries don't cache it anyway.

⭐⭐ THE READ PATH, END TO END:
⭐   ⭐ `GET /{key}` → app → ⭐⭐ REDIS (10 GB HOT SET, ~99%
⭐     HIT) → on miss, the shard → populate → 302.
⭐   ⭐ ⭐⭐ NEGATIVE CACHE MISSING KEYS (Day 326's penetration)
⭐     — otherwise `GET /aaaaaaa` in a loop is a free attack on
⭐     your database.
⭐   ⭐ TTL jitter, ⭐ and probabilistic early expiry for the
⭐     genuinely hot links.
```

# Part 6 — ⭐⭐ The deep dive: the analytics write, which is the real problem

```
⭐⭐ THE NUMBER PEOPLE MISS: ⭐⭐ 300,000 REDIRECTS/S AT PEAK
⭐   MEANS 300,000 ***CLICK WRITES***/S. ⭐ That is 100× the
⭐   URL-creation write rate, ⭐⭐ AND IT IS THE ACTUAL SCALING
⭐   PROBLEM IN THIS SYSTEM.

⭐⭐ ❌ WHAT NOT TO DO: `INSERT INTO clicks …` on the redirect
⭐   path.
⭐   ⇒ ⭐ Adds latency to a p99-50 ms path; ⭐⭐ 300k INSERTS/s
⭐     IS 300k DEAD TUPLES/s (Day 320's arithmetic again); ⭐ and
⭐     a database hiccup now breaks ***redirects***, which are
⭐     the product.

⭐⭐ ✔ THE THREE-LAYER ANSWER, AND SAY ALL THREE:
⭐   ① ⭐⭐ FIRE-AND-FORGET TO A ***BOUNDED*** IN-PROCESS QUEUE,
⭐      FLUSHED IN BATCHES. ⭐ The redirect returns without
⭐      waiting. ⭐⭐ BOUNDED, AND DROP ON FULL (Day 336) — a
⭐      lost click beats a failed redirect, and that trade
⭐      should be stated as a decision.
⭐   ② ⭐ Batch to Kafka (or Kinesis), keyed by `key` so one
⭐      link's clicks stay ordered and co-located.
⭐   ③ ⭐⭐ CONSUMERS WRITE ***PRE-AGGREGATED COUNTS***, NOT RAW
⭐      ROWS: `(key, hour, country, referrer) -> count`, upserted.
⭐      ⇒ ⭐⭐ 300k EVENTS/s BECOMES A FEW THOUSAND UPSERTS/s,
⭐        BECAUSE THE CARDINALITY OF ***HOT KEYS × BUCKETS*** IS
⭐        FAR SMALLER THAN THE EVENT COUNT.
⭐      ⇒ ⭐ Raw events go to S3 in Parquet for the rare "we
⭐        need the detail" query.

⭐⭐ AND THE HONEST STATEMENT OF WHAT YOU GAVE UP:
⭐   ***CLICK COUNTS ARE EVENTUALLY CONSISTENT AND SLIGHTLY
⭐      LOSSY UNDER OVERLOAD.*** ⭐ For a link-click counter that
⭐   is correct engineering. ⭐⭐ FOR A BILLING METER IT WOULD
⭐   NOT BE — AND KNOWING WHICH ONE YOU ARE BUILDING IS THE
⭐   WHOLE JUDGEMENT.
```

# Part 7 — ⭐ 40–45: bottlenecks, failure and what changes at 10×

```
⭐⭐ THE BOTTLENECKS, IN ORDER:
⭐   ① ⭐ At today's numbers: ⭐⭐ NOTHING. Redis serves the
⭐      reads; Postgres takes 3,000 writes/s comfortably.
⭐   ② ⭐ At 10×: the click pipeline first — ⭐ 3 M events/s
⭐      needs more partitions and more consumers, ⭐⭐ AND THE
⭐      AGGREGATION KEY BECOMES THE HOT SPOT (one viral link).
⭐      ⇒ ⭐ Key-split the counter (Day 326), sum on read.
⭐   ③ ⭐ Then the cache: 100 GB hot set ⇒ a Redis cluster,
⭐      ⭐ and now Day 326's consistent hashing is load-bearing.

⭐⭐ FAILURE MODES:
⭐   ⭐ ⭐⭐ REDIS DOWN ⇒ 300,000 READS/S HIT THE SHARDS. ⭐ Can
⭐     they take it? ⭐⭐ IF NOT, THE CACHE IS INFRASTRUCTURE,
⭐     NOT AN OPTIMISATION (Day 326) — replicate it, and put a
⭐     CDN in front of the redirect for the very hottest links
⭐     with a 60-second TTL.
⭐   ⭐ One shard down ⇒ ⭐ that slice of links 503s. ⭐ Replicas.
⭐   ⭐ Kafka down ⇒ ⭐⭐ REDIRECTS STILL WORK. ⭐ That is the
⭐     point of layer ①, and it is worth saying explicitly.

⭐⭐ AND THE THINGS THAT MAKE THIS A ***PRODUCT***, mentioned in
⭐   thirty seconds each:
⭐   ⭐ ⭐⭐ ABUSE: shorteners are phishing infrastructure.
⭐     Scan destinations against a threat feed asynchronously,
⭐     ⭐ and be able to revoke — ⭐⭐ WHICH IS THE SECOND
⭐     ARGUMENT FOR 302.
⭐   ⭐ Rate-limit creation per key/IP (Day 336).
⭐   ⭐ ⭐⭐ NEVER REUSE AN EXPIRED KEY. ⭐ Old links exist in
⭐     emails forever; recycling a key sends someone's traffic
⭐     to a stranger's site.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Writing a click row synchronously on redirect | 300k writes/s on a 50 ms path, and a DB hiccup breaks the product |
| ⭐⭐ Choosing 301 for the load saving | You lose analytics, expiry and revocation — and a malicious link becomes unfixable |
| ⭐⭐ Hashing the URL without pricing collisions | The birthday bound puts first collisions at ~1.9 M keys, i.e. day one |
| ⭐ `SELECT` to check the key is free, then insert | Check-then-act. The unique constraint must be the arbiter |
| ⭐ Sequential base62 keys with no permutation | The whole database is enumerable, which breaks "unlisted" links |
| ⭐⭐ No negative caching | `GET /aaaaaaa` in a loop is a free attack on your database |
| ⭐ Storing raw click rows | Pre-aggregate by (key, hour, dimension). Raw goes to object storage |
| ⭐⭐ Unbounded in-process click queue | A crash with a delay. Bound it and drop, and say that a lost click beats a failed redirect |
| ⭐ Reusing expired keys | Links live in emails forever; you'd send a stranger's traffic to a new owner |
| ⭐ Forgetting reserved aliases | Someone registers `/api` and breaks your own routing |
| ⭐ No key-length calculation | Six characters is 5.6 × 10^10 and you run out. It's a one-line calculation |

## Interview questions

**1. "How do you generate the keys?"**
> ⭐ First the length, by calculation: 10^8 a day for ten years is 3.65 × 10^11 URLs, and base62 to the
> seventh is 3.5 × 10^12 — ⭐⭐ **so seven characters with about ten times headroom, and six would not
> be enough.** ⭐ Then random-with-retry, arbitrated by a unique constraint rather than a `SELECT`,
> because at ten percent occupancy retries are essentially free. ⭐ If I wanted zero retries I'd
> pre-generate a key pool and pop one, ⭐⭐ and if I wanted counters I'd allocate ranges per instance
> **and pass them through a keyed permutation so the output isn't enumerable.**

**2. "301 or 302?"**
> ⭐ 302, and not for a subtle reason. ⭐⭐ A 301 is cached by the browser, so **you lose analytics after
> the first click, and you can never change or revoke the link** — the browser keeps going to the old
> target for months and there is no purge. ⭐ For a shortener, which is phishing infrastructure whether
> you like it or not, revocation is non-negotiable. ⭐ The cost is that every click reaches me, which is
> what the cache and CDN are for.

**3. "What's the actual scaling problem here?"**
> ⭐⭐ Not the redirects — **the click writes.** Three hundred thousand redirects a second means three
> hundred thousand analytics writes a second, which is a hundred times the URL-creation rate. ⭐ So:
> fire-and-forget into a bounded in-process queue that drops on full, batch to Kafka keyed by the short
> key, and ⭐⭐ **consumers upsert pre-aggregated counts by (key, hour, dimension) rather than raw
> rows**, which collapses three hundred thousand events a second into a few thousand upserts. ⭐ Raw
> events go to S3 as Parquet.

**4. "What did that cost you?"**
> ⭐ Click counts become eventually consistent and slightly lossy under overload. ⭐⭐ I'd say that as a
> decision, not a defect: **a lost click beats a failed redirect.** ⭐ And I'd draw the line — that
> trade is correct for a vanity counter and wrong for a billing meter, so if these clicks were billable
> I'd need at-least-once delivery with idempotent aggregation and I'd accept the extra latency.

**5. "Redis goes down at peak. What happens?"**
> ⭐ Three hundred thousand reads a second hit the shards. ⭐⭐ If they can't take it, **then the cache
> was never an optimisation — it's load-bearing infrastructure** and needs replication, alerting and a
> warm-up plan like a database. ⭐ I'd also put a CDN in front of the redirect for the hottest links
> with a sixty-second TTL, which gives me a second layer that survives a Redis outage entirely. ⭐ And
> I'd note Kafka being down doesn't affect redirects at all, which is the point of the fire-and-forget
> layer.

**6. "What breaks at 10×?"**
> ⭐ The click pipeline first — three million events a second needs more partitions and consumers, ⭐⭐
> and **the aggregation key becomes the hot spot when one link goes viral**, so I key-split the counter
> and sum on read. ⭐ Then the cache: a hundred-gigabyte hot set means a Redis cluster, and that's where
> consistent hashing with virtual nodes stops being theory. ⭐ The URL table itself is fine — it was
> sharded by key from the start and the key distributes uniformly by construction.

## 🎙️ Articulation drill

**Two minutes.** Open with the shape, because it reframes the whole problem: **the read path is trivial
and the write path is where the system actually lives.** Do the estimate in four lines and let each one
decide something — a hundred million a day is a thousand writes a second and a hundred thousand reads;
five hundred bytes gives a hundred and eighty terabytes over ten years, so it's sharded by key; **and
base62 to the seventh is three and a half trillion against three hundred and sixty-five billion used,
so seven characters, and six would not be enough.** Then key generation: random with retry, arbitrated
by a unique constraint rather than a select, because the check-then-select is a race. Then the redirect,
and give the real reason: **302, because a 301 is cached forever and you lose analytics, expiry and —
critically — the ability to revoke a link that turns out to point at malware.** Then the deep dive, and
name the number people miss: **three hundred thousand redirects a second means three hundred thousand
click writes a second, a hundred times the creation rate** — so a bounded in-process queue that drops
on full, batched to a log, with consumers writing pre-aggregated counts rather than rows. Close by
pricing it honestly: **click counts are eventually consistent and slightly lossy, because a lost click
beats a failed redirect — and that trade would be wrong if these clicks were billable.**
