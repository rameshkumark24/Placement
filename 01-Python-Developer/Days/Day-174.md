# Part 1 — ⭐ URLs, and the differences that catch you

```python
urlpatterns = [
    path("orders/", views.order_list, name="order-list"),
    path("orders/<int:pk>/", views.order_detail, name="order-detail"),
    re_path(r"^legacy/(?P<slug>[-\w]+)/$", views.legacy),
    path("api/", include("orders.urls")),          # ⭐ composition, like include_router
]
```

```
⭐⭐ FIVE THINGS THAT DIFFER FROM FASTAPI:
⭐  1. ⭐⭐ FIRST MATCH WINS, TOP TO BOTTOM. ⭐ So `orders/<int:pk>/` before
⭐       `orders/summary/` means `summary` never resolves — ⭐⭐ Day 107's
⭐       ordering trap, and `<int:>` makes it LESS likely (a converter that
⭐       does not match falls through), while `<str:pk>` makes it certain.
⭐  2. ⭐⭐ THE URL IS MATCHED, THEN THE METHOD IS THE VIEW'S PROBLEM. ⭐ A
⭐       function view that only handles POST returns whatever you wrote for
⭐       GET — often a 200 with nothing. ⭐⭐ There is no automatic 405 unless
⭐       you use `require_http_methods` or a CBV. ⭐ Day 107 said match path
⭐       then method and return 405 with `Allow`; ⭐⭐ Django makes that YOUR
⭐       job in function views.
⭐  3. ⭐⭐ TRAILING SLASHES ARE LOAD-BEARING. `APPEND_SLASH=True` (default)
⭐       makes `/orders` redirect to `/orders/` — ⭐ but ONLY for safe methods.
⭐       ⭐⭐ A POST to `/orders` (no slash) DOES NOT REDIRECT; it 404s, and the
⭐       body is gone. ⭐ Day 107's 301-vs-308 lesson, with Django choosing
⭐       "do not redirect" instead — which is the safe choice and a confusing one.
⭐  4. ⭐⭐ NAMED URLS AND `reverse()`. ⭐ `reverse("order-detail", args=[7])`
⭐       generates the path. ⭐⭐ This is genuinely better than hard-coding, and
⭐       it is why Django URLs can be restructured without touching templates.
⭐  5. ⭐ NAMESPACES — `app_name = "orders"` ⇒ `reverse("orders:order-detail")`.
⭐       ⭐⭐ Without them, two apps with a `detail` route silently shadow.
```

# Part 2 — ⭐⭐ Function views vs class-based views

```python
# ⭐ FUNCTION VIEW — explicit, obvious, and it is 8 lines
@require_http_methods(["GET"])
@login_required
def order_list(request):
    orders = Order.objects.for_user(request.user).with_details()[:50]
    return render(request, "orders/list.html", {"orders": orders})

# ⭐ CLASS-BASED VIEW — 4 lines, and a hierarchy you inherited
class OrderListView(LoginRequiredMixin, ListView):
    model = Order
    paginate_by = 50
    def get_queryset(self):
        return Order.objects.for_user(self.request.user).with_details()
```

```
⭐⭐ THE HONEST TRADE, BECAUSE THIS IS A REAL AND ONGOING ARGUMENT:

⭐   ⭐ CBVs GIVE YOU: pagination, form handling, object lookup with 404,
⭐        context building, and the GET/POST split — ⭐⭐ all for free, all
⭐        conventionally named, all reusable across a team.
⭐   ⭐ CBVs COST YOU: ⭐⭐ `ListView` inherits from six classes. To answer
⭐        "where does `object_list` come from?" you must know the MRO. ⭐ The
⭐        code you are reading is mostly NOT ON THE PAGE.
⭐   ⇒ ⭐⭐ AND THE ASYMMETRY THAT DECIDES IT: A CBV IS EXCELLENT UNTIL YOU
⭐        NEED SOMETHING IT DID NOT ANTICIPATE. ⭐ Then you override
⭐        `get_context_data`, `get_queryset`, `form_valid` and `dispatch`,
⭐        each calling `super()`, ⭐⭐ and you have written MORE code than the
⭐        function view, spread across four methods, in an order you cannot
⭐        see.
⭐
⭐⭐ THE RULE THAT ACTUALLY WORKS IN A CODEBASE:
⭐   ⭐ ✅ CBV when your view IS the pattern — a plain list, a plain detail, a
⭐        plain `ModelForm` create. ⭐⭐ You are consuming the convention.
⭐   ⭐ ✅ FUNCTION VIEW when the logic is specific. ⭐⭐ Eight explicit lines
⭐        beat four lines plus six base classes, every time, for anything
⭐        anyone will need to debug.
⭐   ⭐ ❌ ⭐⭐ NEVER BUILD YOUR OWN DEEP MIXIN HIERARCHY. ⭐ Two levels is the
⭐        practical limit before nobody can trace `dispatch`.
```

```
⭐⭐ THE MRO PROBLEM, CONCRETELY — this is the thing to be able to explain:
⭐   `class MyView(LoginRequiredMixin, PermissionRequiredMixin, UpdateView)`
⭐   ⇒ ⭐ `dispatch()` runs left to right through the MRO. ⭐⭐ ORDER MATTERS:
⭐        put `LoginRequiredMixin` AFTER a permission mixin and an anonymous
⭐        user hits the permission check first — ⭐ which may raise a 403 where
⭐        you intended a redirect to login.
⭐   ⇒ ⭐⭐ AND MIXINS THAT FORGET `super()` SILENTLY BREAK EVERYTHING TO THEIR
⭐        RIGHT. ⭐ No error; the later mixin's hook simply never runs — which
⭐        for an authorisation mixin means it is not enforcing anything.
⭐   ⇒ ⭐ `print(MyView.__mro__)` is the debugging tool, and needing it is the
⭐        signal that the hierarchy is too deep.
```

# Part 3 — ⭐⭐ Middleware: a different contract from ASGI

```python
def timing_middleware(get_response):          # ⭐ called ONCE at startup
    def middleware(request):                  # ⭐ called per request
        start = time.perf_counter()
        response = get_response(request)      # ⭐⭐ everything inward happens here
        response["X-Duration-Ms"] = f"{(time.perf_counter()-start)*1000:.1f}"
        return response
    return middleware
```

```
⭐⭐ SAME ONION AS STARLETTE (Day 110), WITH FOUR DJANGO SPECIFICS:

⭐  1. ⭐⭐ IT RUNS **BEFORE URL RESOLUTION**. ⭐ So middleware does not know
⭐       which view will handle the request. ⭐⭐ Day 140's argument holds
⭐       identically: AUTHORISATION BELONGS ON THE VIEW (a decorator, a mixin,
⭐       or a DRF permission class), NOT IN MIDDLEWARE — ⭐ because middleware
⭐       can only decide from the raw path, and a path prefix allow-list is
⭐       how endpoints end up unprotected.
⭐  2. ⭐ EXTRA HOOKS BEYOND THE ONION: `process_view` (⭐⭐ runs AFTER
⭐       resolution, so it DOES know the view — ⭐ this is the one place
⭐       middleware can be view-aware), `process_exception`,
⭐       `process_template_response`.
⭐  3. ⭐⭐ ORDER IS CORRECTNESS, AND THE REQUIRED ORDER IS NOT OBVIOUS:
⭐          SecurityMiddleware          ⭐ outermost — HSTS, redirects
⭐          SessionMiddleware           ⭐⭐ MUST precede Auth (Auth reads it)
⭐          CommonMiddleware            ⭐ APPEND_SLASH
⭐          CsrfViewMiddleware          ⭐⭐ MUST come after Session
⭐          AuthenticationMiddleware    ⭐ sets `request.user`
⭐          MessageMiddleware
⭐       ⇒ ⭐⭐ GET THIS WRONG AND THE ERRORS LOOK LIKE DJANGO BUGS —
⭐          `request.user` missing, CSRF failing for everyone, ⭐ and nothing
⭐          points at `settings.MIDDLEWARE`.
⭐  4. ⭐⭐ `request.user` IS **LAZY**. ⭐ It is a `SimpleLazyObject`, so
⭐       touching it triggers a session lookup and a database query. ⭐⭐ That
⭐       means a middleware that logs `request.user.id` on EVERY request adds
⭐       a query to every request — including to `/healthz` — ⭐ which is a
⭐       genuinely common and invisible cost.
```

# Part 4 — ⭐⭐ Sessions and CSRF, built in

```
⭐⭐ SESSIONS (Day 113, provided):
⭐   ⭐ a signed session-id cookie; data in `django_session`, cache, or the
⭐        cookie itself (⭐⭐ `signed_cookies` backend: signed but NOT
⭐        encrypted — ⭐ the user can READ it, so never put anything secret
⭐        there, and it cannot be revoked server-side).
⭐   ⭐ ⭐⭐ `cycle_key()` ON LOGIN — Django's `login()` does this for you, and
⭐        it is exactly Day 113's session-fixation defence.
⭐   ⭐ ⭐⭐ `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_HTTPONLY`,
⭐        `SESSION_COOKIE_SAMESITE = "Lax"` — ⭐ HttpOnly is the default,
⭐        Secure is NOT. ⭐⭐ Setting `Secure` is on you, in production.
⭐   ⭐ `SESSION_EXPIRE_AT_BROWSER_CLOSE`, `SESSION_COOKIE_AGE` — ⭐⭐ and note
⭐        the DB backend does NOT clean up expired rows: ⭐ `clearsessions`
⭐        is a management command you must schedule (Day 159), or the table
⭐        grows forever.

⭐⭐ CSRF (Day 115, provided) — the double-submit pattern, and Django's is
⭐   worth understanding because it is a good implementation:
⭐   ⭐ a token in a cookie AND in the form/header; the middleware compares.
⭐   ⭐ ⭐⭐ IT IS MASKED PER REQUEST (XOR'd with a random salt), which defends
⭐        against BREACH-style compression side channels — ⭐ a detail most
⭐        hand-rolled implementations miss.
⭐   ⭐ ⭐⭐ IT ALSO CHECKS `Origin`/`Referer` FOR HTTPS REQUESTS. ⭐ That is a
⭐        second, independent defence, and it is why `CSRF_TRUSTED_ORIGINS`
⭐        exists and why deploys behind a proxy suddenly fail CSRF.
⭐   ⭐ ⭐⭐ EXEMPT ONLY WITH `@csrf_exempt`, AND ONLY WHERE THERE IS NO AMBIENT
⭐        AUTHORITY — ⭐ a webhook endpoint authenticated by HMAC (Day 166) is
⭐        the legitimate case. ⭐⭐ `@csrf_exempt` on a cookie-authenticated
⭐        endpoint is a straight CSRF vulnerability.
⭐
⭐   ⇒ ⭐⭐ AND THE POINT THAT MATTERS FOR TOMORROW: **IF YOU AUTHENTICATE
⭐        WITH A TOKEN IN A HEADER, CSRF DOES NOT APPLY AT ALL** — there is no
⭐        ambient authority for a hostile page to abuse. ⭐ CSRF exists
⭐        BECAUSE cookies are sent automatically. ⭐⭐ Day 140's trade, and DRF
⭐        (Day 175) enforces CSRF only for session authentication, which
⭐        confuses people until they know this.
```

```
⭐⭐ THE OTHER SECURITY MIDDLEWARE YOU GET FREE (Day 127):
⭐   ⭐ `SECURE_HSTS_SECONDS` · `SECURE_SSL_REDIRECT` ·
⭐        `SECURE_CONTENT_TYPE_NOSNIFF` (default on) · `X_FRAME_OPTIONS`
⭐        (default `DENY`)
⭐   ⭐ ⭐⭐ `python manage.py check --deploy` ⭐ RUN THIS. It audits exactly
⭐        these settings and tells you what is unsafe. ⭐⭐ It is a free
⭐        security review and most people have never run it.
```

# Part 5 — ⭐ Templates, and the autoescaping that saves you

```
⭐⭐ EVEN IF YOU ARE BUILDING AN API, KNOW THIS, BECAUSE IT IS THE ONE PLACE
⭐   DJANGO'S DEFAULT IS BETTER THAN MOST FRAMEWORKS':

⭐   ⭐⭐ TEMPLATES AUTOESCAPE BY DEFAULT. `{{ user_input }}` is HTML-escaped,
⭐        so ⭐ XSS (Day 127) requires you to OPT OUT.
⭐   ⭐⭐ THE OPT-OUTS ARE THE VULNERABILITY: `|safe`, `{% autoescape off %}`,
⭐        and `mark_safe()` in Python. ⭐ Grep for those three in any review —
⭐        ⭐⭐ they are the complete list of places stored XSS can enter a
⭐        Django template.
⭐   ⭐ ⭐⭐ AND THE GAP: AUTOESCAPING IS **HTML** ESCAPING. Inside a `<script>`
⭐        tag or a JS string it is NOT sufficient — ⭐ use
⭐        `json_script` (which escapes correctly for that context) rather than
⭐        interpolating into JavaScript.
⭐
⭐⭐ AND THE PERFORMANCE HAZARD FROM Day 171, RESTATED HERE BECAUSE THIS IS
⭐   WHERE IT LIVES:
⭐   ⭐ `{% for item in order.items.all %}` INSIDE `{% for order in orders %}`
⭐        ⇒ ⭐⭐ AN N+1 WRITTEN IN HTML, invisible to anyone reading the view,
⭐        authored by someone who may not know what a query is.
⭐   ⇒ ⭐ Defence: `prefetch_related` in `get_queryset`, `assertNumQueries` on
⭐        the view, and ⭐⭐ `django-zen-queries` to mark template rendering
⭐        query-forbidden — which is the only mechanical answer.
```

```
⭐⭐ THE THREE THINGS TO TAKE FROM TODAY IF YOU TAKE NOTHING ELSE:
⭐   ⭐ A VIEW IS A CALLABLE. CBVs are convenience, and they stop being
⭐        convenient exactly when your view stops being generic.
⭐   ⭐⭐ MIDDLEWARE RUNS BEFORE ROUTING, SO AUTHORISATION GOES ON THE VIEW.
⭐   ⭐ ⭐⭐ DJANGO'S SESSION, CSRF, AND ESCAPING DEFAULTS ARE GOOD — ⭐ the
⭐        vulnerabilities come from OPTING OUT (`csrf_exempt`, `|safe`,
⭐        `mark_safe`), which makes them all greppable.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| A broad `<str:pk>` pattern above a literal path | First match wins; the literal route never resolves. |
| Expecting an automatic 405 in a function view | Method handling is yours. Use `require_http_methods` or a CBV. |
| Assuming `APPEND_SLASH` fixes POSTs | It doesn't redirect unsafe methods — you get a 404 and the body is gone. |
| Hard-coding URLs | `reverse()` and named URLs are why Django URLs can be restructured. |
| No `app_name` namespace | Two apps with a `detail` route silently shadow each other. |
| A deep custom mixin hierarchy | Nobody can trace `dispatch`. Two levels is the practical limit. |
| Mixin order chosen arbitrarily | `LoginRequiredMixin` after a permission mixin gives a 403 where you wanted a login redirect. |
| A mixin that forgets `super()` | Everything to its right silently stops running — including authorisation. |
| Authorisation in middleware | It runs before URL resolution, so it can only match on the raw path. |
| Wrong `MIDDLEWARE` order | Missing `request.user` or CSRF failing for everyone, with nothing pointing at the cause. |
| Logging `request.user` in middleware | It's lazy — you've added a session lookup and a query to every request. |
| Secrets in the `signed_cookies` session backend | Signed is not encrypted; the user can read it, and it can't be revoked. |
| Not setting `SESSION_COOKIE_SECURE` | HttpOnly is the default; Secure is not. |
| Never scheduling `clearsessions` | The session table grows forever. |
| `@csrf_exempt` on a cookie-authenticated endpoint | A straight CSRF vulnerability. |
| Confused why DRF doesn't enforce CSRF for token auth | CSRF exists because cookies are ambient. Tokens aren't. |
| Never running `check --deploy` | A free security review most people have never run. |
| `|safe` or `mark_safe` on user input | The complete list of ways stored XSS enters a Django template. |
| HTML escaping inside a `<script>` tag | Wrong context. Use `json_script`. |
| Relation loops in templates | An N+1 in HTML, invisible from the view. |

## Interview questions

**Q: Function-based or class-based views?**

> Depends whether my view *is* the pattern. A plain list, a plain detail, a plain `ModelForm` create —
> a CBV gives me pagination, object lookup with 404, and the GET/POST split for free, all
> conventionally named, which is real value on a team. But CBVs have an asymmetry: they're excellent
> until you need something the hierarchy didn't anticipate, and then you're overriding
> `get_queryset`, `get_context_data`, `form_valid` and `dispatch`, each calling `super()`, and you've
> written more code than the function view would have been, spread across four methods in an order
> you can't see on the page. So generic view, CBV; specific logic, function view — eight explicit
> lines beat four lines plus six base classes for anything anyone will have to debug. And I'd never
> build a deep custom mixin hierarchy: mixin order changes behaviour, and a mixin that forgets
> `super()` silently stops everything to its right from running, which for an authorisation mixin
> means it's enforcing nothing.

**Q: Why can't Django middleware handle authorisation?**

> Because it runs before URL resolution, so it doesn't know which view will handle the request — it
> can only decide from the raw path, which means a prefix allow-list, which is how endpoints end up
> unprotected when someone adds a route under a public prefix. Same argument as FastAPI. So
> authorisation goes on the view: a decorator, a mixin, or a DRF permission class. The one exception
> is `process_view`, which runs *after* resolution and does know the view, so that's the hook if you
> genuinely need view-aware middleware. What does belong in middleware is what applies to every
> request regardless of route — request ids, security headers, timing.

**Q: Explain Django's CSRF protection.**

> Double-submit: a token in a cookie and the same token in the form or an `X-CSRFToken` header, and
> the middleware compares them, on the reasoning that a cross-site attacker can cause the cookie to
> be sent but can't read it to put it in the body. Two details Django gets right that hand-rolled
> versions usually miss: the token is masked per request by XOR-ing with a random salt, which defends
> against BREACH-style compression side channels; and for HTTPS requests it also checks
> `Origin`/`Referer` as an independent second defence — which is why `CSRF_TRUSTED_ORIGINS` exists
> and why CSRF suddenly fails when you deploy behind a proxy. The thing to understand underneath is
> *why* CSRF exists at all: cookies are ambient authority, sent automatically. So if you authenticate
> with a token in a header there's no CSRF exposure, which is exactly why DRF enforces CSRF for
> session authentication and not for token authentication.

**Q: What are the free security wins in Django, and where do the holes come from?**

> The defaults are genuinely good: templates autoescape, `X-Frame-Options` defaults to DENY,
> `nosniff` is on, sessions are signed with rotation on login, CSRF is wired in. What's notable is
> that the vulnerabilities almost all come from *opting out* — `@csrf_exempt`, `|safe`,
> `{% autoescape off %}` and `mark_safe`. That's a short, greppable list, which is a much better
> security posture than a framework where you have to remember to opt in. The things you must set
> yourself are `DEBUG=False`, `ALLOWED_HOSTS`, and `SESSION_COOKIE_SECURE` — HttpOnly is the default
> but Secure isn't. And `manage.py check --deploy` audits all of it and tells you what's unsafe,
> which is a free security review most people have never run.

## 🎙️ Articulation drill

**Two minutes: "How do views and middleware work in Django?"**

Start from the minimal definition — a callable taking a request and returning a response — because it
makes the CBV hierarchy a choice rather than a mystery. Give the CBV trade with the asymmetry, and
your rule. Then middleware: same onion as any framework, with the one structural fact that matters —
it runs before routing, so authorisation belongs on the view, and `process_view` is the exception.
Mention that order is correctness and the symptoms look like Django bugs. Close on security, which is
where Django is genuinely strong: **the defaults are good and nearly every vulnerability comes from
opting out — `csrf_exempt`, `|safe`, `mark_safe` — which makes the audit a grep**, and add that
`check --deploy` is a free security review most people have never run.
