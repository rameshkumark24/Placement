# Day 203

**L-203** · 🧠 **Redis architecture** — ⭐⭐ why single-threaded is fast, and what that one decision forbids

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: Redis executes commands on one thread, and that is not a limitation you
> tolerate — it is the property you build on. Every command is atomic for free, which is why
> `INCR`, `SETNX` and Lua give you correctness that would need locks anywhere else.**
>
> ⭐⭐ **And the same fact is the entire danger: one slow command blocks *every other client*. There
> is no "slow query" in Redis. There is only "the server stopped".**
>
> ⭐ Day 143 used Redis as a cache and told you to trust three rules. ⭐⭐ Seven days now say why.

# Part 1 — ⭐ Redis is not a cache

```
⭐⭐ THE MENTAL MODEL SHIFT: Redis is an ***IN-MEMORY DATA STRUCTURE
⭐   SERVER***. Caching is one thing you can do with it.

⭐   ⭐ memcached: a hash map of bytes → bytes. That is a cache.
⭐   ⭐⭐ REDIS: strings, lists, hashes, sets, sorted sets, bitmaps,
⭐     hyperloglogs, streams, geospatial indexes — ⭐ each with
⭐     server-side operations. ⭐⭐ YOU MOVE THE ALGORITHM TO THE DATA
⭐     INSTEAD OF THE DATA TO THE ALGORITHM.
⭐
⭐   ⭐ "Top 10 scores" = ⭐⭐ ONE COMMAND (`ZREVRANGE k 0 9`), not
⭐     "fetch a million, sort in Python". ⭐ That difference — a 40 MB
⭐     transfer becoming a 200-byte one — is the whole point, and it is
⭐     why Day 204 exists.
```

```
⭐⭐ AND THE HONEST BOUNDARY, STATED NOW SO THE REST OF THE WEEK IS
⭐   CALIBRATED (Day 143 said this; here is why):
⭐   ⭐ IT IS ALL IN RAM. Your dataset must fit, plus headroom for
⭐     replication buffers and a fork (Part 5).
⭐   ⭐⭐ ITS DURABILITY IS WEAKER THAN POSTGRES'S BY DESIGN (Day 205).
⭐   ⭐ No joins, no query planner, no constraints, no transactions in
⭐     the Postgres sense (Day 195's rollback does not exist here).
⭐   ⇒ ⭐⭐ REDIS IS NOT YOUR DATABASE. It is the place where a small,
⭐     hot, structurally simple slice of state lives so that the
⭐     database does not have to answer for it.
```

# Part 2 — ⭐⭐ The event loop, and the arithmetic that makes it fast

```
⭐⭐ ONE THREAD. ONE LOOP. FOR EVER.

⭐   while (true) {
⭐       events = epoll_wait(...)          ⭐ Day 016's epoll, again
⭐       for (e in events) {
⭐           read command  →  ⭐⭐ EXECUTE IT COMPLETELY  →  queue reply
⭐       }
⭐       process expirations, serve replies
⭐   }

⭐⭐ WHY THIS IS FAST — four reasons, and none of them is "C is fast":
⭐   ① ⭐⭐ NO LOCKS. No mutexes, no atomics, no contention. A shared
⭐        hash map with fine-grained locking is SLOWER than one thread
⭐        at this granularity.
⭐   ② ⭐ NO CONTEXT SWITCHES between commands.
⭐   ③ ⭐ EVERYTHING IS IN RAM: ~100 ns per operation. There is no IO to
⭐        overlap, so threads would buy nothing.
⭐   ④ ⭐ Purpose-built data structures with O(1)/O(log n) operations.
⭐   ⇒ ⭐⭐ 100,000–1,000,000 OPS/SEC ON ***ONE CORE***.
```

```
⭐⭐ AND THE PROPERTY THAT MATTERS MORE THAN THE SPEED:
⭐   ⭐⭐ ***EVERY COMMAND IS ATOMIC. AUTOMATICALLY. ALWAYS.***
⭐   ⭐ There is no interleaving, because there is no second thread to
⭐     interleave with. ⭐⭐ `INCR` cannot lose an update. `SETNX`
⭐     cannot race. A Lua script runs to completion with nothing in
⭐     between.
⭐   ⇒ ⭐⭐ THIS IS WHY REDIS IS THE DEFAULT ANSWER FOR COUNTERS, RATE
⭐     LIMITERS AND LOCKS (Days 207–208). Not because it is fast —
⭐     because it is SERIALISED, and serialised is what those problems
⭐     need. ⭐ Day 195's lost update is structurally impossible here.
```

```
⭐⭐ WHAT IS ACTUALLY THREADED NOW (people get this wrong in interviews):
⭐   ⭐ `io-threads` (6.0+) — ⭐⭐ PARALLELISES SOCKET READ/WRITE AND
⭐     PROTOCOL PARSING ONLY. ⭐⭐ COMMAND EXECUTION IS STILL ONE
⭐     THREAD. ⭐ Helps at very high throughput with large values;
⭐     changes nothing about atomicity.
⭐   ⭐ Background threads: `BGSAVE` (a forked child), AOF `fsync`,
⭐     lazy freeing (`UNLINK`), and slow `DEL`s when `lazyfree-*` is on.
⭐   ⭐ Redis 7 has a bit more; ⭐⭐ the model has not changed: ONE
⭐     COMMAND AT A TIME, IN ORDER.
```

# Part 3 — ⭐⭐ The catastrophe: one slow command

```
⭐   redis> KEYS *          -- ⭐⭐ 10,000,000 keys
⭐   ⭐⭐ THE SERVER IS FROZEN FOR ~4 SECONDS. Every other client — your
⭐     entire fleet — waits. ⭐ Health checks fail. Timeouts fire.
⭐     Retries pile on (Day 152). ⭐⭐ AND YOUR MONITORING SAYS REDIS
⭐     CPU IS 100%, WHICH LOOKS LIKE LOAD RATHER THAN ONE BAD COMMAND.

⭐⭐ THE BANNED LIST — memorise it, and grep your codebase tonight:
⭐   ⭐⭐ KEYS pattern      ⇒ ***SCAN*** (cursor-based, incremental)
⭐   ⭐⭐ FLUSHALL/FLUSHDB  ⇒ `FLUSHALL ASYNC`
⭐   ⭐⭐ SMEMBERS bigset   ⇒ `SSCAN`
⭐   ⭐⭐ HGETALL bighash   ⇒ `HSCAN`, or split the hash
⭐   ⭐⭐ LRANGE key 0 -1   ⇒ paginate
⭐   ⭐⭐ DEL bigcollection ⇒ ***UNLINK*** (frees in a background thread)
⭐   ⭐ ZRANGEBYSCORE with a huge range · SORT · SINTERSTORE on big sets
⭐   ⭐⭐ A LUA SCRIPT WITH A LOOP — you can freeze the server in five
⭐     lines of your own code, and `SCRIPT KILL` will not stop one that
⭐     has written.

⭐⭐ NOTE THE SHAPE: EVERY ONE IS "AN O(N) COMMAND WHERE N IS DATA
⭐   SIZE". ⭐ The rule is not a list to memorise — it is
⭐   ⭐⭐ "KNOW THE BIG-O OF EVERY COMMAND YOU SHIP", which is realistic
⭐   because there are only about forty you will ever use.
```

```
⭐ SCAN, and the three things people get wrong about it:
⭐   redis> SCAN 0 MATCH "session:*" COUNT 100
⭐   ⭐ Returns (cursor, keys). Loop until cursor == 0.
⭐   ⭐⭐ ① `MATCH` FILTERS ***AFTER*** SCANNING. `SCAN 0 MATCH x COUNT
⭐        100` still examines 100 keys and may return ZERO. ⭐⭐ AN EMPTY
⭐        BATCH IS NOT THE END — only cursor 0 is.
⭐   ⭐⭐ ② GUARANTEES: every key present for the whole scan IS
⭐        returned; keys added/removed during it MAY OR MAY NOT be; and
⭐        ⭐ a key can be returned TWICE. Deduplicate.
⭐   ⭐ ③ `COUNT` is a hint, not a limit.
```

```sql
-- ⭐⭐ FINDING THESE BEFORE YOUR USERS DO:
redis> CONFIG SET slowlog-log-slower-than 10000   -- ⭐ µs ⇒ 10 ms
redis> SLOWLOG GET 10
redis> LATENCY RESET; LATENCY HISTORY command; LATENCY DOCTOR
redis> INFO commandstats     -- ⭐⭐ calls + usec_per_call PER COMMAND
redis> INFO latencystats     -- ⭐ 7.0+: percentiles per command
-- ⭐⭐ `INFO commandstats` IS THE `pg_stat_statements` OF REDIS (Day
--    202): sort by TOTAL usec, not by usec_per_call.
```

# Part 4 — ⭐⭐ The real cost is the round trip

```
⭐⭐ THE ARITHMETIC THAT CHANGES HOW YOU WRITE REDIS CODE:
⭐   ⭐ Redis executes a `GET` in ~0.0001 ms.
⭐   ⭐⭐ THE NETWORK ROUND TRIP IS ~0.2 ms (same DC) — 2,000× MORE.
⭐   ⇒ ⭐⭐ YOU ARE NEVER OPTIMISING REDIS. YOU ARE OPTIMISING ROUND
⭐     TRIPS. 1,000 sequential `GET`s = 200 ms of pure waiting.
```

```python
# ⭐ SEQUENTIAL — 1,000 round trips, ~200 ms
for k in keys: vals.append(r.get(k))

# ⭐ MGET — one round trip, ~0.4 ms.  ⭐⭐ 500× FASTER.
vals = r.mget(keys)

# ⭐⭐ PIPELINE — for heterogeneous commands. One round trip.
pipe = r.pipeline(transaction=False)      # ⭐⭐ note the flag
for k in keys:
    pipe.hincrby(f"stats:{k}", "hits", 1)
    pipe.expire(f"stats:{k}", 3600)
pipe.execute()
# ⭐⭐ `transaction=False` ⇒ plain pipelining, NO `MULTI/EXEC` wrapper.
#    ⭐ redis-py defaults to True, which wraps everything in MULTI —
#      ⭐⭐ that is a DIFFERENT feature with a different cost, and most
#      code that wants batching does not want atomicity.
# ⭐ Keep batches to ~100–1,000 commands: a 100k-command pipeline
#   builds a huge reply buffer and is itself a latency spike.
```

```
⭐⭐ THREE WAYS TO SEND MANY COMMANDS, AND THEY ARE NOT THE SAME THING:
⭐   ⭐ PIPELINE — ⭐⭐ BATCHING. Fewer round trips. ⭐ NOT atomic:
⭐        other clients' commands CAN interleave between yours.
⭐   ⭐ MULTI/EXEC — ⭐⭐ ATOMICITY. All queued commands run with nothing
⭐        in between. ⭐⭐ BUT: NO ROLLBACK. A command that fails at
⭐        runtime (wrong type) does NOT abort the others. ⭐ It is
⭐        "isolated", not "transactional" in the Day 195 sense.
⭐        ⭐ `WATCH` adds optimistic locking (check-and-set) on top.
⭐   ⭐⭐ LUA (`EVALSHA`) — ⭐⭐ ATOMICITY ***PLUS LOGIC***. The only one
⭐        where a later command can depend on an earlier one's RESULT.
⭐        ⇒ ⭐ This is why Days 207 and 208 are written in Lua: "if the
⭐          value is mine, delete it" cannot be expressed in MULTI.
```

# Part 5 — ⭐⭐ Memory, and the fork that kills you

```
⭐⭐ THE #1 REDIS OUTAGE, AND IT IS NOT WHAT PEOPLE EXPECT:

⭐   `BGSAVE` (or a replica syncing, or AOF rewrite) calls ⭐⭐ fork().
⭐   ⭐ The child shares the parent's memory COPY-ON-WRITE.
⭐   ⭐⭐ EVERY PAGE THE PARENT WRITES DURING THE SAVE MUST BE COPIED.
⭐   ⇒ ⭐⭐ A WRITE-HEAVY WORKLOAD DURING A SAVE CAN APPROACH ***2×
⭐     MEMORY USAGE***. On a box sized for 1×, the OOM killer arrives.
⭐
⭐   ⭐⭐ THE THREE MITIGATIONS, ALL REQUIRED:
⭐     ⭐ `vm.overcommit_memory = 1` — ⭐⭐ WITHOUT IT, fork() ITSELF
⭐       FAILS when Redis uses >50% of RAM, and your saves and
⭐       replication silently stop. ⭐ Redis logs a warning at boot that
⭐       everyone ignores.
⭐     ⭐⭐ DISABLE TRANSPARENT HUGE PAGES. With THP, copy-on-write
⭐       copies ***2 MB*** pages instead of 4 KB ones — ⭐⭐ 512× the
⭐       copying, and latency spikes that are impossible to diagnose if
⭐       you do not know this.
⭐     ⭐ Size the box for ~2× your dataset, or take snapshots on a
⭐       REPLICA instead of the primary.
```

```
⭐⭐ THE MEMORY NUMBERS THAT MATTER — `INFO memory`:
⭐   ⭐ `used_memory`      — what Redis thinks it holds
⭐   ⭐ `used_memory_rss`  — what the OS says the process uses
⭐   ⭐⭐ `mem_fragmentation_ratio` = rss / used
⭐        ⭐ ~1.0–1.5 healthy · ⭐⭐ >1.5 fragmented (turn on
⭐          `activedefrag`) · ⭐⭐ <1.0 MEANS ***SWAPPING***, which for
⭐          an in-memory database is a total performance collapse.
⭐          ⭐ Disable swap for Redis, or set `vm.swappiness = 0`.
⭐   ⭐ `used_memory_peak` — ⭐⭐ if peak ≫ used, something transient
⭐        (a fork, a big pipeline reply, a replication buffer) is your
⭐        real sizing constraint.
⭐   ⭐ `maxmemory` + `maxmemory-policy` — ⭐⭐ Day 206. And the fact
⭐        that catches everyone: ⭐⭐ THE DEFAULT POLICY IS `noeviction`,
⭐        SO A FULL REDIS RETURNS ***WRITE ERRORS*** RATHER THAN
⭐        EVICTING. ⭐ Which is right for a queue and catastrophic for a
⭐        cache.
⭐   ⭐ `MEMORY USAGE key` — per-key cost. ⭐⭐ `redis-cli --bigkeys` and
⭐        `--memkeys` find the ones destroying you.
```

```python
# ⭐ redis-py, configured like an adult (Day 152's timeouts, again):
import redis
pool = redis.ConnectionPool(
    host=..., port=6379,
    max_connections=50,            # ⭐ per process (Day 197 arithmetic)
    socket_connect_timeout=1,      # ⭐⭐ NEVER leave these unset
    socket_timeout=1,              # ⭐⭐ or a frozen Redis hangs every
                                   #    worker in your fleet
    health_check_interval=30,      # ⭐ pre-ping equivalent
    retry_on_timeout=False,        # ⭐⭐ a timed-out write may HAVE
                                   #    happened — retry only
                                   #    idempotent operations
    decode_responses=True,         # ⭐ str, not bytes. Pick one and be
)                                  #   consistent, or you will have
r = redis.Redis(connection_pool=pool)   #   `b'x'` bugs forever
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Thinking of Redis as "a fast cache" | It's a data structure server; the algorithms run next to the data. |
| Treating Redis as a database | RAM-bound, weaker durability, no joins or constraints. |
| Thinking single-threaded is a weakness | It's why every command is atomic, which is what counters and locks need. |
| Believing `io-threads` made execution parallel | It parallelises socket IO and parsing only. |
| `KEYS *` anywhere | It freezes the entire server. `SCAN`. |
| `DEL` on a huge collection | `UNLINK` frees in a background thread. |
| Treating an empty `SCAN` batch as the end | Only cursor 0 is the end, and keys can repeat. |
| Sequential `GET`s in a loop | You're paying 2,000× the operation cost in round trips. `MGET` or pipeline. |
| Assuming a pipeline is atomic | It's batching. Other clients interleave. |
| Assuming `MULTI/EXEC` rolls back | There is no rollback; a runtime error doesn't abort the rest. |
| Expressing conditional logic in `MULTI` | Later commands can't see earlier results. Use Lua. |
| Ignoring `vm.overcommit_memory` | `fork()` fails above 50% memory and saves silently stop. |
| Leaving transparent huge pages on | Copy-on-write copies 2 MB pages — 512× the work, unexplainable spikes. |
| Sizing the box for 1× the dataset | A save forks; write-heavy load can approach 2×. |
| Not knowing `maxmemory-policy` defaults to `noeviction` | A full cache starts returning write errors instead of evicting. |
| No socket timeouts in redis-py | A frozen Redis hangs every worker in the fleet. |

## Interview questions

**Q: Redis is single-threaded. Isn't that a bottleneck?**

> It's the design, and mostly it's the feature. Four reasons it's fast anyway: there are no locks, so
> no contention — a shared hash map with fine-grained locking is actually slower at this granularity;
> no context switching between commands; everything is in RAM at around a hundred nanoseconds an
> operation, so there's no IO to overlap and threads would buy nothing; and the data structures are
> purpose-built. That gets you a hundred thousand to a million operations a second on one core. But
> the more important consequence is atomicity: because there's no second thread, every command runs to
> completion with nothing interleaved, so `INCR` can't lose an update and `SETNX` can't race. That's
> why Redis is the default answer for counters, rate limiters and locks — not because it's fast, but
> because it's serialised, and serialisation is what those problems need. The genuine cost is that one
> slow command blocks everyone, so there's no such thing as a slow query in Redis, only "the server
> stopped".

**Q: Someone ran `KEYS *` in production. What happened?**

> The server froze for as long as it took to walk every key — on ten million keys, several seconds.
> Because execution is single-threaded, that's not a slow query for one client, it's a total outage
> for every client. Health checks fail, application timeouts fire, retries pile on and make the
> recovery worse, and monitoring shows Redis at a hundred percent CPU, which looks like load rather
> than one bad command. `SCAN` is the replacement — cursor-based and incremental — with three things
> people get wrong: `MATCH` filters after scanning so a batch can legitimately return zero keys, only
> cursor zero means the end, and the same key can be returned twice so you deduplicate. The general
> rule isn't a banned list though, it's knowing the big-O of every command you ship, which is
> realistic because there are only about forty you'll ever use. And I'd have `slowlog` configured with
> a low threshold so this shows up as a log entry rather than an incident.

**Q: How do you make a hundred Redis operations fast?**

> By reducing round trips, because that's the actual cost. A `GET` executes in about a ten-thousandth
> of a millisecond and a same-datacentre round trip is around two tenths of a millisecond — so the
> network is two thousand times the operation. A thousand sequential gets is two hundred milliseconds
> of pure waiting, and `MGET` makes it one round trip. For heterogeneous commands it's a pipeline, and
> I'd pass `transaction=False` in redis-py because it defaults to wrapping everything in `MULTI`,
> which is a different feature with a different cost and most batching code doesn't want atomicity.
> I'd keep batches to a few hundred commands, because a hundred-thousand-command pipeline builds a
> huge reply buffer and becomes its own latency spike. And the three mechanisms are genuinely
> different: pipelining is batching, `MULTI/EXEC` is atomicity with no rollback, and Lua is atomicity
> plus logic — Lua being the only one where a later command can branch on an earlier result.

**Q: What's the most common way Redis falls over in production?**

> The fork. `BGSAVE`, an AOF rewrite, or a replica doing a full sync all call `fork()`, and the child
> shares memory copy-on-write — so every page the parent writes during the save has to be copied. A
> write-heavy workload during a save can approach double the memory, and if the box was sized for one
> times the dataset the OOM killer arrives. Three things have to be true to survive it. `vm.overcommit_memory = 1`,
> because without it `fork()` itself fails once Redis is above half of RAM, and then saves and
> replication silently stop — Redis warns about this at boot and everyone ignores it. Transparent huge
> pages disabled, because with THP the copy-on-write unit becomes two megabytes instead of four
> kilobytes, which is five hundred times the copying and produces latency spikes that are impossible
> to diagnose unless you know. And either headroom for roughly double, or take snapshots on a replica
> instead of the primary.

**Q: What do you check first when Redis is slow?**

> `INFO commandstats` sorted by total microseconds — it's the `pg_stat_statements` of Redis, and the
> same rule applies: rank by total, not by per-call, because the command costing you most is usually a
> cheap one called constantly. Then `SLOWLOG` for individual blocking commands, and `LATENCY DOCTOR`,
> which is genuinely good at spotting fork and expiry-related spikes. Then `INFO memory`, specifically
> `mem_fragmentation_ratio` — above about 1.5 means fragmentation and `activedefrag` is worth turning
> on, and *below* 1.0 means the process is swapping, which for an in-memory database is a total
> collapse rather than a slowdown. And I'd check whether latency correlates with saves, because if the
> spikes are periodic the answer is the fork, not any command.
