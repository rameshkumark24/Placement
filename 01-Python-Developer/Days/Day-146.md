**L-146** · **Structured logging and request IDs** — ⭐⭐ making an incident answerable instead of narratable

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a log line is not a message to a human, it is a row in a table you have
> not written the schema for yet — so the only question that matters is "what will I want to filter
> by at 3 a.m.?", and the answer is never a sentence.**

# Part 1 — ⭐⭐ The reframe: a log is a query target

```
⭐⭐ THE TWO LINES, AND WHY ONE OF THEM IS USELESS AT 3 A.M.:

⭐  ❌ log.info(f"User {uid} failed to place order {oid}: {e}")
⭐       ⇒ ⭐ to answer "how many users hit this in the last hour?" you must
⭐         write a REGEX AGAINST PROSE. ⭐⭐ And the day someone rewords the
⭐         message — which is a harmless-looking edit — your alert silently
⭐         stops matching. ⭐ The message is now load-bearing and nobody knows.
⭐
⭐  ✅ log.info("order.place.failed", user_id=uid, order_id=oid,
⭐             reason="out_of_stock", sku=sku, duration_ms=41)
⭐       ⇒ ⭐⭐ `event` IS AN IDENTIFIER, NOT A SENTENCE. It is stable, it is
⭐         greppable, and it survives rewording because there is no wording.
⭐       ⇒ ⭐ every other key is a FILTER: `reason:out_of_stock AND
⭐         sku:ABC | count by user_id`.
⭐
⭐   ⇒ ⭐⭐ THE RULE: THE EVENT NAME IS A STABLE, DOTTED, PAST-TENSE
⭐        IDENTIFIER. Everything variable is a FIELD. ⭐ If you find yourself
⭐        f-stringing a value into the message, that value wanted to be a key.
```

```python
import structlog

structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,       # ⭐⭐ Part 2 — the request id
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso", utc=True),   # ⭐ ISO + UTC, always
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,
        structlog.processors.JSONRenderer(),           # ⭐ dev: ConsoleRenderer()
    ],
)
log = structlog.get_logger()
```

```
⭐⭐ THE FIELDS EVERY LINE SHOULD CARRY, AND WHY EACH ONE EARNS ITS BYTES:

⭐   timestamp      ⭐⭐ ISO 8601, UTC. Local time across three regions during
⭐                     an incident is how you misorder cause and effect.
⭐   level          ⭐ see Part 4 — most codebases use these meaninglessly
⭐   event          ⭐⭐ the stable identifier
⭐   service, version, environment   ⭐⭐ `version` is the one people skip and
⭐                     then cannot answer "did the deploy cause this?"
⭐   request_id     ⭐⭐ Part 2
⭐   trace_id       ⭐ Day 148 — the join key to your traces
⭐   user_id / tenant_id            ⭐ the two highest-value filters you own
⭐   duration_ms    ⭐⭐ on completion lines. A log without a duration cannot
⭐                     answer "was it slow?", which is half of all questions.
```

# Part 2 — ⭐⭐ The request id, and why `ContextVar` is the only mechanism that works

```
⭐⭐ THE PROBLEM: A REQUEST TOUCHES 30 FUNCTIONS ACROSS 8 MODULES. THREADS AND
⭐   TASKS INTERLEAVE. ⭐ Without a correlation id, your logs are 40 requests'
⭐   lines shuffled together, ⭐⭐ and "what happened to THIS user's checkout"
⭐   is unanswerable — not hard, UNANSWERABLE.

⭐⭐ AND THE THREE WRONG FIXES:
⭐   ❌ a GLOBAL variable → ⭐⭐ one worker serves many requests concurrently;
⭐        they overwrite each other's id. ⭐ Silent, and the corruption looks
⭐        like a logic bug.
⭐   ❌ `threading.local()` → ⭐⭐ correct for threads, WRONG FOR asyncio:
⭐        many coroutines share ONE thread (Day 072), so they share the slot.
⭐   ❌ passing it as a parameter → ⭐ correct, and it pollutes 30 signatures
⭐        with something none of them are about.
⭐
⭐   ✅ ⭐⭐ `ContextVar` — Day 072's tool. It is copied into each Task and each
⭐        thread-pool submission, so ⭐ every coroutine and every threadpool
⭐        call sees ITS OWN value. ⭐⭐ It is the ONE mechanism that is correct
⭐        under both concurrency models, which is exactly why the stdlib
⭐        added it for asyncio.
```

```python
# ⭐⭐ ONE middleware, and every log line in the request is tagged forever
@app.middleware("http")
async def request_context(request: Request, call_next):
    rid = request.headers.get("x-request-id") or uuid4().hex   # ⭐ TRUST-THEN-VERIFY, below
    structlog.contextvars.clear_contextvars()                  # ⭐⭐ or values leak between
    structlog.contextvars.bind_contextvars(                    #    requests on a reused task
        request_id=rid,
        path=request.url.path,
        method=request.method,
    )
    start = time.perf_counter()
    try:
        response = await call_next(request)
    except Exception:
        log.exception("request.failed",
                      duration_ms=round((time.perf_counter() - start) * 1000, 2))
        raise                                                   # ⭐⭐ RE-RAISE — Part 3
    log.info("request.completed", status=response.status_code,
             duration_ms=round((time.perf_counter() - start) * 1000, 2))
    response.headers["x-request-id"] = rid                      # ⭐⭐ GIVE IT BACK
    return response
```

```
⭐⭐ THREE DETAILS IN THAT MIDDLEWARE THAT ARE EACH A SEPARATE QUESTION:

⭐  1. ⭐⭐ RETURNING `x-request-id` TO THE CLIENT IS THE WHOLE POINT OF SUPPORT
⭐       WORKFLOWS. A user screenshots an error containing the id; you paste
⭐       it into your log search; ⭐ you have the exact request in one query
⭐       instead of guessing from a timestamp and an email address.
⭐  2. ⭐ ACCEPTING AN INBOUND `x-request-id` lets a caller's id flow through
⭐       your service — ⭐⭐ but it is UNTRUSTED INPUT: cap its length, restrict
⭐       its charset, or an attacker injects newlines into your logs
⭐       (⭐ LOG INJECTION — a forged log line in your own audit trail).
⭐       ⭐ Only accept it from internal callers; generate your own at the edge.
⭐  3. ⭐⭐ `clear_contextvars()` FIRST. Under some servers a task is reused;
⭐       without the clear, ⭐ request N's `user_id` appears on request N+1's
⭐       lines and you will chase a data-leak ghost that is a logging bug.
```

# Part 3 — ⭐⭐ Log once, at the boundary

```
⭐⭐ THE PATTERN THAT PRODUCES 90% OF LOG NOISE:

⭐   def charge():
⭐       try: gateway.charge()
⭐       except Exception as e:
⭐           log.error("charge failed: %s", e)     # ⭐ logged (1)
⭐           raise
⭐   def place_order():
⭐       try: charge()
⭐       except Exception as e:
⭐           log.error("order failed: %s", e)      # ⭐ logged (2)
⭐           raise
⭐   # ⭐ + the middleware logs it                  # ⭐ logged (3)
⭐   # ⭐ + your error handler logs it              # ⭐ logged (4)
⭐
⭐   ⇒ ⭐⭐ ONE FAILURE, FOUR LINES, THREE OF THEM WITH LESS CONTEXT THAN THE
⭐        LAST. ⭐ Your error count is 4× reality, so your alert thresholds are
⭐        fiction, and every incident starts by deduplicating your own logs.

⭐⭐ THE RULE — Day 099A's, stated as a decision procedure:
⭐   ⭐ LOG WHERE YOU HANDLE. If you re-raise, you did not handle it: ADD
⭐     CONTEXT INSTEAD OF A LOG LINE.
⭐        raise OrderFailed("charge declined", order_id=oid) from e
⭐   ⭐⭐ THE BOUNDARY LOGS ONCE, WITH THE FULL CHAIN — and because you used
⭐     `raise ... from e`, the traceback already contains every layer.
⭐     ⭐ You were never adding information; you were adding lines.
⭐
⭐ ⭐⭐ AND `log.exception` NOT `log.error(str(e))`: `str(e)` on a
⭐   `KeyError` is literally `'user_id'` — ⭐ no type, no file, no line.
⭐   ⭐⭐ THE MOST COMMON SELF-INFLICTED DEBUGGING WOUND IN PYTHON.
```

```
⭐ WHERE THE BOUNDARIES ACTUALLY ARE — log once at each:
⭐   ⭐ the HTTP request (middleware above)
⭐   ⭐ a background task (Day 142 — its own correlation id, plus the id of
⭐        the request that ENQUEUED it, so the chain survives the queue)
⭐   ⭐ a consumer loop iteration
⭐   ⭐ a scheduled job run
⭐   ⭐⭐ a call OUT to a third party — ⭐ log the attempt and the outcome with
⭐        duration and status, because when they say "we were up", ⭐⭐ this is
⭐        the only evidence you will have.
```

# Part 4 — ⭐⭐ What must never be in a log, and levels that mean something

```
⭐⭐ LOGS ARE THE MOST WIDELY-READ, LEAST-PROTECTED COPY OF YOUR DATA.
⭐   ⭐ They go to a third-party SaaS, they are retained for a year, ⭐⭐ and
⭐   support engineers with no database access can read all of them.

⭐  ⭐⭐ NEVER LOG:
⭐   · passwords, ⭐ even on failure, ⭐⭐ even "to debug just this once"
⭐   · tokens, session ids, API keys, refresh tokens (Day 117)
⭐        ⭐⭐ A LOGGED SESSION ID IS A LOGIN. Treat it as a credential leak
⭐        requiring rotation (Day 087: rotate first, clean up second).
⭐   · full card numbers, national ids, health data
⭐   · ⭐⭐ WHOLE REQUEST BODIES — the seductive one. "Log the payload so we
⭐        can debug" is how PII enters your logging vendor permanently.
⭐   · ⭐ raw emails/phones if you are under GDPR-style rules: ⭐⭐ your logs
⭐        are then in scope for deletion requests, and nobody can delete a
⭐        line from an append-only index.
⭐
⭐  ⭐ INSTEAD:
⭐   · ⭐ a user_id, not an email. ⭐⭐ An id is a JOIN KEY; an email is PII.
⭐   · ⭐ a hash or last-4 when you truly need to correlate
⭐   · ⭐⭐ AN AUTOMATED REDACTION PROCESSOR — because "remember not to" is
⭐        not a control (Day 118). ⭐ Drop keys named `password`, `token`,
⭐        `secret`, `authorization`, `card*` at the PROCESSOR level, so a new
⭐        developer cannot leak them even deliberately.
```

```python
SENSITIVE = {"password", "token", "secret", "authorization", "api_key", "cookie"}
def redact(logger, method, event_dict):
    for k in list(event_dict):
        if any(s in k.lower() for s in SENSITIVE):
            event_dict[k] = "[REDACTED]"       # ⭐⭐ a control, not a convention
    return event_dict
```

```
⭐⭐ LEVELS, GIVEN AN ACTUAL DEFINITION — most teams have none, which is why
⭐   everything is INFO and nothing is actionable:

⭐   DEBUG    ⭐ for a developer, off in production. ⭐⭐ May be verbose; may
⭐              not be expensive to CONSTRUCT (see below).
⭐   INFO     ⭐ a business event happened: order placed, user registered.
⭐              ⭐⭐ Ask "would I want this in an audit trail?"
⭐   WARNING  ⭐⭐ THE HARDEST ONE. Definition: *degraded but handled* — a
⭐              retry succeeded, a cache missed hard, a fallback fired.
⭐              ⭐ If nobody would act on it EVER, it is INFO.
⭐   ERROR    ⭐⭐ A REQUEST FAILED FOR A REASON THAT IS OURS. ⭐ A 400 from a
⭐              client is NOT an error — it is the system working. ⭐⭐ Logging
⭐              validation failures as ERROR is the single biggest cause of
⭐              alert fatigue, and alert fatigue is how real errors get missed.
⭐   CRITICAL ⭐ the process cannot continue.
⭐
⭐   ⇒ ⭐⭐ THE TEST: "IF THIS FIRES 100 TIMES TONIGHT, DOES SOMEONE NEED TO
⭐        WAKE UP?" ⭐ Yes → ERROR. No → INFO/WARNING. ⭐⭐ There is no third
⭐        answer, and "it's important" is not one of them.
```

```
⭐ COST AND VOLUME — the part that gets logging deleted after the bill:
⭐   ⭐⭐ SAMPLE HIGH-VOLUME SUCCESS. Log 100% of errors and 1% of successful
⭐     `GET /health` lines. ⭐ Keep the sampling DECISION in the line
⭐     (`sampled: 0.01`) so counts can be scaled back up correctly.
⭐   ⭐ LOG TO STDOUT, ONE JSON OBJECT PER LINE (Day 079). ⭐⭐ Not to a file:
⭐     the container has no persistent disk, and rotation is not your job.
⭐   ⭐⭐ AND `PYTHONUNBUFFERED=1` — Day 079's empty-`docker logs` trap. ⭐ A
⭐     perfectly instrumented service whose logs are stuck in a 4 KB buffer
⭐     is an uninstrumented service.
⭐   ⭐ use `log.debug("x", value=expensive)` carefully: ⭐⭐ arguments are
⭐     EVALUATED even when the level is off. ⭐ Guard genuinely costly ones.
```

# Part 5 — ⭐ Three pillars, and which question each answers

```
⭐⭐ LOGS, METRICS AND TRACES ARE NOT THREE VIEWS OF THE SAME THING. THEY
⭐   ANSWER DIFFERENT QUESTIONS AND HAVE DIFFERENT COST CURVES:

⭐   ⭐ METRICS (Day 147)  — "IS something wrong, and how much?"
⭐        ⭐⭐ cheap, aggregated, LOW cardinality, retained for years.
⭐        ⭐ Cannot tell you about ONE request. That is the trade.
⭐   ⭐ TRACES (Day 148)   — "WHERE in the call graph is the time going?"
⭐        ⭐ per-request, sampled, structured as a tree.
⭐   ⭐ LOGS (today)       — "WHAT EXACTLY HAPPENED to this one request?"
⭐        ⭐⭐ highest cardinality, highest cost, unbeatable detail.
⭐
⭐   ⇒ ⭐⭐ THE WORKFLOW THEY ARE DESIGNED FOR:
⭐        ⭐ metric alert fires → ⭐ trace shows which span is slow →
⭐        ⭐ log lines for that trace_id show why.
⭐   ⇒ ⭐⭐ WHICH IS WHY EVERY LOG LINE MUST CARRY `trace_id`: it is the JOIN
⭐        KEY between the three, and without it you have three tools that
⭐        cannot talk to each other. ⭐ One field, and the whole workflow works.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| f-stringing values into the message | The message becomes load-bearing; a reword breaks your alerts. Values are fields. |
| A global or `threading.local` request id | Wrong under asyncio — coroutines share a thread. `ContextVar` is the only correct one. |
| Not clearing contextvars per request | Request N's fields appear on request N+1 and look like a data leak. |
| Not returning `x-request-id` to the client | You lose the one-query path from a user's screenshot to their request. |
| Trusting an inbound `x-request-id` unvalidated | Log injection — forged lines in your own audit trail. Cap length and charset. |
| Logging at every layer and re-raising | One failure, four lines, thresholds become fiction. Log at the boundary; add context in between. |
| `log.error(str(e))` | `str(KeyError)` is just `'user_id'`. Use `log.exception`. |
| Logging client 4xx as ERROR | Alert fatigue, and then real errors get missed. That's the system working. |
| Logging request bodies "for debugging" | This is how PII permanently enters your logging vendor. |
| Logging tokens or session ids | A logged session id is a login. Treat it as a credential leak. |
| Relying on people to remember not to log secrets | Not a control. Redact in a processor. |
| Logging to a file in a container | No persistent disk, and rotation isn't your job. stdout, one JSON object per line. |
| Missing `PYTHONUNBUFFERED` | Logs sit in a buffer; `docker logs` is empty during the incident. |
| No `duration_ms` on completion lines | "Was it slow?" is half of all questions and you can't answer it. |
| No `version` field | You can't answer "did the deploy cause this?" |
| No `trace_id` in logs | The three pillars can't join, and the intended workflow doesn't exist. |

## Interview questions

**Q: Why structured logs rather than formatted strings?**

> Because a log line isn't a message to a human, it's a row in a table. The moment I write
> `f"User {uid} failed"`, answering "how many users hit this in the last hour" means writing a regex
> against prose — and the day someone rewords that message, which looks like a harmless edit, my
> alert silently stops matching. With `log.info("order.place.failed", user_id=..., reason=...)` the
> event name is a stable identifier with no wording to break, and everything variable is a filterable
> field. My rule of thumb: if I'm interpolating a value into the message, that value wanted to be a
> key.

**Q: How do you correlate log lines belonging to one request?**

> A request id in a `ContextVar`, bound once in middleware. A global is wrong because one worker
> serves many requests concurrently and they'd overwrite each other silently. `threading.local` is
> right for threads and wrong for asyncio, because many coroutines share one thread. `ContextVar` is
> the only mechanism correct under both — it's copied into each task and each threadpool submission,
> which is exactly why it was added for asyncio. Two details beyond the basics: I return the id in
> the response header, so a user's screenshot of an error is a one-query path to their exact request;
> and if I accept an inbound id from a caller I validate its length and charset, because otherwise
> it's log injection — forged lines in my own audit trail.

**Q: You have four log lines for one failure. What's wrong and what's the rule?**

> Each layer logged and re-raised, plus the middleware and the error handler. So the error count is
> four times reality, the alert thresholds are fiction, and every incident starts by deduplicating my
> own logs. The rule is log where you handle. If I re-raise, I didn't handle it — so instead of a log
> line I add context to the exception and `raise ... from e`, which means the boundary's single
> `log.exception` already has the full chain in the traceback. I was never adding information, only
> lines. And it has to be `log.exception`, not `log.error(str(e))` — `str` on a `KeyError` is just
> the key name, with no type, file or line.

**Q: What must never appear in a log?**

> Credentials of any kind — passwords, tokens, session ids, API keys — because logs are the most
> widely read and least protected copy of your data: they go to a third-party vendor, they're
> retained for a year, and support engineers with no database access read all of them. A logged
> session id is a login, so it's a credential leak requiring rotation. Also whole request bodies,
> which is the seductive one — "log the payload so we can debug" is how PII permanently enters your
> logging vendor, and you can't delete a line from an append-only index when a deletion request
> arrives. I log user ids rather than emails, because an id is a join key and an email is PII. And I
> enforce it with a redaction processor that drops keys named password, token, secret or
> authorization, because "remember not to" isn't a control.

**Q: When is something ERROR versus WARNING versus INFO?**

> ERROR means a request failed for a reason that's ours. A 400 from a client isn't an error, it's the
> system working correctly, and logging validation failures as ERROR is the biggest single cause of
> alert fatigue — which is how real errors get missed. WARNING is the hard one: degraded but handled
> — a retry that succeeded, a fallback that fired. If nobody would ever act on it, it's INFO. The
> test I use is: if this fires a hundred times tonight, does someone need to wake up? Yes means
> ERROR, no means INFO or WARNING, and "it's important" isn't a third answer.

## 🎙️ Articulation drill

**Two minutes: "How do you make a service debuggable in production?"**

Open with the reframe — logs are query targets, so events are identifiers and everything variable is
a field. Then the correlation id, with `ContextVar` justified by why the two obvious alternatives
fail, and the detail that pays off in support: return it to the client. Then the discipline that
keeps logs usable — log once at the boundary, add context in between — and the discipline that keeps
them legal: redaction as a processor, ids not emails, never a request body. Give the ERROR test in
one line. Close on the three pillars and the join key: **metrics tell you something is wrong, traces
tell you where, logs tell you what — and `trace_id` on every line is what makes that a workflow
rather than three tools.**
