# Part 1 — ⭐⭐ The protocol

```python
with open(path) as f:      # ⭐ f = open(path).__enter__()
    data = f.read()
# ⭐⭐ open(path).__exit__(exc_type, exc_value, traceback) — ALWAYS
```

```python
class Transaction:
    def __enter__(self):
        self.conn = pool.acquire()
        self.conn.begin()
        return self.conn                      # ⭐⭐ THIS is what `as conn` binds
    def __exit__(self, exc_type, exc, tb):
        if exc_type is None:
            self.conn.commit()                # ⭐ success
        else:
            self.conn.rollback()              # ⭐⭐ any exception ⇒ roll back
        pool.release(self.conn)               # ⭐ released on BOTH paths
        return False                          # ⭐⭐ do NOT suppress — let it propagate
```

```
⭐⭐ __exit__'s RETURN VALUE IS THE WHOLE SUBTLETY:
⭐   False / None  ⇒ ⭐ the exception propagates. ⭐⭐ THE DEFAULT YOU WANT.
⭐   True          ⇒ ⭐⭐ the exception is SWALLOWED. The `with` statement completes normally.
⭐
⭐ ⚠️ ⭐⭐ SO: a __exit__ that ends with a call returning something truthy silently eats every
⭐      exception in the block. A transaction that rolls back AND hides the error is worse
⭐      than one that does neither, because nothing upstream ever learns it failed.
```

⭐⭐ **The transaction example is the canonical one**, and it is worth being able to write from
memory: **commit on success, roll back on failure, release on both, and never suppress.**

# Part 2 — ⭐⭐ `@contextmanager`

```python
from contextlib import contextmanager

@contextmanager
def transaction(pool):
    conn = pool.acquire()
    conn.begin()
    try:
        yield conn                # ⭐⭐ the `with` body runs HERE
    except Exception:
        conn.rollback()
        raise                     # ⭐⭐ re-raise — do not swallow
    else:
        conn.commit()
    finally:
        pool.release(conn)        # ⭐⭐ EVERY path
```

```
⭐⭐ WHY try/finally IS MANDATORY — derived on Day 048, restated because it is the rule people
⭐   know and cannot justify:
⭐   if the `with` body raises, contextlib calls gen.throw(exc), which raises the exception
⭐   AT THE YIELD, INSIDE your generator.
⭐   ⇒ ⭐⭐ without a try, it propagates straight out and everything after the yield —
⭐        your cleanup — is NEVER EXECUTED.
⭐   ⇒ ⭐ the exception is not around your generator. It is injected into it.
```

⭐ **`@contextmanager` gives you both roles in one readable function** and is the right default;
reach for a class when the manager needs state, methods, or to be reusable/reentrant.

⚠️ ⭐⭐ **A `@contextmanager` generator must yield exactly once.** Zero yields raises
`RuntimeError: generator didn't yield`; two raises `generator didn't stop`. **And it is single-use —
`cm = transaction(pool)` then two `with cm:` blocks fails**, because the generator is exhausted
(Day 046). **Call the factory again each time.**

# Part 3 — ⭐ The `contextlib` toolkit

```python
from contextlib import (contextmanager, closing, suppress, nullcontext,
                        ExitStack, redirect_stdout, aclosing, asynccontextmanager)

with closing(urlopen(url)) as page: ...        # ⭐ wraps anything with .close() but no protocol

with suppress(FileNotFoundError):              # ⭐⭐ instead of try/except/pass
    os.remove(path)

with nullcontext():                            # ⭐⭐ a manager that does nothing — see below
    ...

with redirect_stdout(buf):                     # ⭐ capture print() output — useful in tests
    ...
```

```python
# ⭐⭐ nullcontext — the fix for the duplicated block:
cm = open(path) if path else nullcontext(sys.stdin)     # ⭐⭐ ONE code path, conditional manager
with cm as f:
    process(f)
# ⭐ the alternative is an if/else with the body written twice, which is where they diverge.
```

⚠️ ⭐ **`suppress` is not a licence to ignore errors.** It is right when the exception genuinely means
"already in the desired state" — deleting a file that is not there, closing something already closed.
**`with suppress(Exception):` around real work is a bare `except: pass` with better marketing.**

## ⭐⭐ `ExitStack` — a dynamic number of managers

```python
# ⚠️ ⭐ You cannot write `with` for an unknown number of files:
with ExitStack() as stack:
    files = [stack.enter_context(open(p, encoding="utf-8")) for p in paths]
    # ⭐⭐ ALL of them are closed on exit, in reverse order, even if one open() fails partway
    merge(files)
```

```python
# ⭐⭐ THE OTHER USE — a manual rollback stack, which is the saga pattern in miniature (Stage 12):
with ExitStack() as stack:
    conn = stack.enter_context(db.transaction())
    stack.callback(lambda: cache.invalidate(key))   # ⭐ run on exit, whatever happens
    user = create_user(conn)
    stack.pop_all()                                 # ⭐⭐ SUCCESS ⇒ cancel all the cleanups
```

⭐⭐ **`pop_all()` is the "commit" idiom:** register undo actions as you go, and **cancel them all
once you know you have succeeded.** ⭐ That is a genuinely useful pattern for multi-step operations
where each step needs its own compensating action.

⭐ **Multiple managers in one `with`** — and the parenthesised form (3.10+) that finally allows line
breaks:

```python
with (
    open(src, encoding="utf-8") as fin,
    open(dst, "w", encoding="utf-8") as fout,
):
    fout.write(fin.read())
# ⭐⭐ equivalent to nesting: if the second open fails, the first is still closed.
```

# Part 4 — ⭐ Where context managers earn their keep

| ⭐ Use | ⭐ Manager |
|---|---|
| Files, sockets, subprocess pipes | ⭐⭐ `open`, `socket`, `Popen` |
| ⭐⭐ **Database transactions** | ⭐ commit/rollback/release |
| ⭐ Locks | ⭐⭐ `with lock:` — releases even if the body raises |
| Temporary directories/files | `tempfile.TemporaryDirectory` |
| ⭐ Changing global state and restoring | `os.chdir`, `decimal.localcontext`, `warnings.catch_warnings` |
| Timing / instrumentation | Day 031's `Timer` |
| Patching in tests | `unittest.mock.patch` |
| ⭐ Async resources | ⭐ `async with` — sessions, connections, `TaskGroup` (Day 071) |

```python
# ⭐⭐ THE LOCK CASE IS THE ONE THAT WOULD DEADLOCK WITHOUT IT:
lock.acquire()
do_work()            # ⚠️ ⭐⭐ raises ⇒ the lock is NEVER released ⇒ every other thread blocks forever
lock.release()

with lock:           # ⭐⭐ released on every path, including the exception
    do_work()
```

```python
# ⭐ Async context managers (Day 048) — same protocol, awaitable:
class Session:
    async def __aenter__(self): ...
    async def __aexit__(self, *exc): ...

async with httpx.AsyncClient() as client: ...
from contextlib import asynccontextmanager     # ⭐⭐ FastAPI's `lifespan` is one of these
```

⭐⭐ **`asynccontextmanager` is what FastAPI's `lifespan` uses** — everything before the `yield` runs
at startup, everything after at shutdown — **so the pattern you learn here is the one you will use to
open a database pool in Stage 4.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Returning truthy from `__exit__`** | ⭐⭐ Silently swallows every exception in the block. |
| ⭐⭐ **`@contextmanager` without `try/finally`** | ⭐⭐ Cleanup skipped when the body raises. |
| Swallowing after rollback | ⭐ Roll back **and** re-raise. |
| Reusing a `@contextmanager` object | ⭐ Single-use — the generator is exhausted. |
| Yielding twice, or not at all | ⭐ `RuntimeError`. |
| `try/except/pass` | ⭐ `suppress`, and only for expected states. |
| `with suppress(Exception):` around real work | ⭐⭐ A bare except with better marketing. |
| Duplicating a block for a conditional manager | ⭐⭐ `nullcontext`. |
| Hand-managing N resources | ⭐ `ExitStack`. |
| `lock.acquire()` without `with` | ⭐⭐ An exception deadlocks every other thread. |
| Relying on `__del__` or a trailing `close()` | ⭐ Days 026, 047. |

## Interview questions

**Q: What does `with` guarantee?**
> That `__exit__` runs on every way out of the block — normal completion, an exception, a `break`, a
> `continue`, an early `return`. That's why it's the only reliable cleanup in Python: `__del__` runs
> whenever the object happens to be collected, which under a reference cycle or on a different
> implementation may be much later, and a `close()` at the end of a function is skipped by exactly
> the paths that matter — the ones that raise.

**Q: What does `__exit__`'s return value do?**
> Truthy suppresses the exception; falsy lets it propagate. Falsy is what you want almost always, and
> the failure mode is subtle: if `__exit__` ends with a call that happens to return something truthy,
> every exception inside the block disappears silently. A transaction manager that rolls back *and*
> hides the error is worse than one that does neither, because nothing upstream ever learns the
> operation failed.

**Q: Why must a `@contextmanager` use `try`/`finally`?**
> Because when the body raises, `contextlib` calls `gen.throw()`, which raises the exception inside
> the generator at the `yield` statement. Without a `try`, that propagates straight out and the
> cleanup after the `yield` never runs. The exception isn't wrapped around the generator — it's
> injected into it, which is why this is a correctness requirement rather than a style rule.

**Q: How do you manage a number of resources known only at runtime?**
> `ExitStack`. You enter each one with `stack.enter_context`, and all of them are exited in reverse
> order when the block ends — including the case where the fifth acquisition fails and the first four
> still need releasing. It also takes plain callbacks with `stack.callback`, which gives you a
> rollback stack: register the undo action for each step as you perform it, and call `pop_all()` once
> everything has succeeded to cancel them. That's a compensating-action pattern, and it's the same
> shape as a saga at a much smaller scale.

**Q: Write a transaction context manager.**
> Acquire a connection and begin in `__enter__`, returning the connection. In `__exit__`, commit if
> `exc_type` is None and roll back otherwise, release the connection on both paths, and return False
> so the exception still propagates. As a generator it's the same logic with `try/except/else/finally`
> around the `yield` — rollback and re-raise in the except, commit in the else, release in the
> finally.

**Q: Where do you meet async context managers?**
> HTTP clients and database sessions, where acquiring and releasing themselves need to await. And
> `asynccontextmanager` is what FastAPI's `lifespan` is — everything before the `yield` runs at
> application startup, everything after at shutdown, which is where a connection pool gets opened and
> closed.
