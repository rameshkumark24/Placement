# Day 239 ♿

**P-239** · ♿ **Accessibility** — ⭐⭐ four things, and the keyboard test that finds most of them

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: almost all real accessibility failures come from using a `div` where the
> platform already gave you a `button`, `a`, `label` or `input` — so the fix is usually deleting
> code and ARIA attributes rather than adding them, and unplugging your mouse for five minutes finds
> more issues than any audit tool.**
>
> Today: ⭐ why this is not optional, the four categories, ⭐⭐ the keyboard test, and the ARIA rule.

---

# Part 1 — Why bother, honestly

| ⭐ Reason | |
|---|---|
| **It is a large share of your users** | ⭐ Roughly 15% of people have a disability. Not an edge case. |
| **⭐⭐ It is legally required in most markets** | ⭐ For anything public-facing at a real company, this is compliance, not virtue |
| **It correlates with quality** | ⭐⭐ Keyboard support, focus management and real labels make the app better for *everyone* — power users live on the keyboard |
| **⭐ Interviewers check** | Tabbing through your demo takes them ten seconds. **It is the cheapest signal of care you can give.** |

> ⭐⭐ **The honest framing for an interview:** *"I don't claim WCAG AA compliance — I haven't audited
> it. I do the four things that catch most real failures, and I test with the keyboard."* That is
> credible. Claiming full compliance you have not measured is not.

# Part 2 — ⭐⭐ The four that matter

```
⭐⭐ ① SEMANTIC HTML — ⭐ THE ONE THAT FIXES EVERYTHING ELSE

⭐   ❌ <div onClick={x} className="btn">Save</div>
⭐      ⭐⭐ NOT FOCUSABLE · NOT IN TAB ORDER · NO ENTER/SPACE ·
⭐        ANNOUNCED AS NOTHING · NO DISABLED STATE
⭐   ✅ <button onClick={x}>Save</button>
⭐      ⭐ ALL OF THAT, FREE, FOREVER.

⭐   ⭐⭐ THE DECISION IS ONE QUESTION:
⭐     NAVIGATES SOMEWHERE?  ⇒ <a href>   (⭐ works with Cmd-click,
⭐                               middle-click, "open in new tab")
⭐     DOES SOMETHING?       ⇒ <button>
⭐   ⇒ ⭐ A LINK STYLED AS A BUTTON IS FINE. A DIV PRETENDING TO BE
⭐     EITHER IS NOT.
```

```
⭐⭐ ② LABELS — every input, always
⭐   ✅ <label htmlFor="email">Email</label><input id="email" />
⭐   ⭐⭐ A PLACEHOLDER IS NOT A LABEL: it vanishes when you type,
⭐     it fails contrast, and screen readers treat it inconsistently.
⭐   ⭐ Icon-only button ⇒ aria-label="Delete order"

⭐⭐ ③ FOCUS — ⭐ NEVER `outline: none` WITH NO REPLACEMENT
⭐   ✅ :focus-visible { outline: 2px solid var(--primary);
⭐                       outline-offset: 2px; }
⭐   ⭐⭐ :focus-visible SHOWS THE RING FOR KEYBOARD USERS AND HIDES
⭐     IT FOR MOUSE CLICKS — which is the actual reason people
⭐     removed it, now solved properly.
⭐   ⭐ MOVE FOCUS DELIBERATELY: into a dialog on open, back to the
⭐     trigger on close, to the first error on failed submit.

⭐⭐ ④ CONTRAST — 4.5:1 for body text, 3:1 for large text
⭐   ⭐ Grey-on-grey placeholder text is the single most common
⭐     failure, and it fails for everyone in sunlight too.
⭐   ⭐⭐ AND NEVER USE COLOUR ALONE: a red border with no message
⭐     says nothing to a colour-blind user OR a screen reader.
```

# Part 3 — ⭐⭐ The keyboard test

```
⭐⭐ UNPLUG YOUR MOUSE. FIVE MINUTES. THIS FINDS MOST OF IT.

⭐   ① Tab through the whole page.
⭐      ⭐ CAN YOU REACH EVERY INTERACTIVE THING?
⭐      ⭐⭐ CAN YOU SEE WHERE YOU ARE, AT ALL TIMES?
⭐      ⭐ Is the order the visual order? (⭐⭐ a CSS reorder that does
⭐        not match DOM order is a classic trap)
⭐   ② Enter on links and buttons. Space on buttons and checkboxes.
⭐   ③ Open a modal:
⭐      ⭐⭐ DOES FOCUS GO INTO IT? DOES TAB **STAY** INSIDE IT?
⭐      ⭐ Does Escape close it? Does focus RETURN to the trigger?
⭐      ⭐⭐ "TAB ESCAPES THE MODAL AND STARTS CLICKING THINGS
⭐        BEHIND IT" IS THE MOST COMMON DIALOG BUG THERE IS.
⭐   ④ Submit an invalid form ⇒ ⭐ does focus land on the first error?
⭐   ⑤ ⭐ Is there a "skip to content" link before a long nav?
```

| ⭐ Also cheap | |
|---|---|
| **Zoom to 200%** | ⭐ Does anything overlap or become unreachable? |
| **Turn on `prefers-reduced-motion`** | ⭐⭐ Large animations cause real nausea — respect it |
| **Run axe DevTools** | ⭐ Catches contrast and missing labels. **Catches ~30% of issues** — it cannot judge whether your focus order makes sense |

# Part 4 — ⭐⭐ The ARIA rule

```
⭐⭐ THE FIRST RULE OF ARIA: **DO NOT USE ARIA.**
⭐   ⭐ If a native element does the job, use it. Every ARIA attribute
⭐     is a PROMISE you must now implement by hand — roles, states,
⭐     keyboard handling, focus management.

⭐   ❌ <div role="button" tabIndex={0} onKeyDown={...}>
⭐      ⭐⭐ YOU HAVE NOW REIMPLEMENTED <button> BADLY, and you
⭐        still owe: disabled, form submission, Space vs Enter,
⭐        and the browser's own AT quirks.
⭐   ✅ <button>

⭐⭐ ⇒ BAD ARIA IS **WORSE THAN NONE**. role="button" on something
⭐   that is not focusable announces an interactive control that
⭐   cannot be reached — you have advertised a door with no handle.
```

| ⭐ Legitimate ARIA | For |
|---|---|
| `aria-label` | ⭐ Icon-only controls |
| `aria-describedby` | ⭐⭐ Linking an input to its error text |
| `aria-invalid` | Marking a failed field |
| `aria-live="polite"` | ⭐⭐ Announcing async results — "3 results found", a toast, a save confirmation. **The one people always miss**, because a screen reader user gets no signal that anything happened. |
| `aria-expanded` / `aria-controls` | Disclosure widgets |

## Today's build

1. ⭐⭐ **Unplug the mouse. Use your app for five minutes.** Write down everything you cannot do. This list is the day.
2. Find every `div` with an `onClick`. ⭐ Convert to `button` or `a`. **Count how much code you deleted.**
3. ⭐ Add `:focus-visible` rings. Remove every `outline: none` that has no replacement.
4. ⭐⭐ Test your modal: focus in, trap, Escape, focus returns. Fix what fails.
5. ⭐ Run axe. Fix the contrast failures. Note that it said nothing about your focus order.
6. ⭐⭐ Add `aria-live` to your search results count and confirm it announces.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you approach accessibility?"**

Start with where the failures actually come from, which is not where people expect. **Almost all of it
comes from using a div where the platform already gave me a button, a link, a label or an input. A div
with an onClick isn't focusable, isn't in tab order, doesn't respond to Enter or Space, announces as
nothing, and has no disabled state. A button gives me all of that for free. So the fix is usually
deleting code, not adding ARIA.**

Then the test, because it is concrete and cheap. **I unplug the mouse for five minutes. Tab through
everything: can I reach every control, can I always see where I am, is the order the visual order.
Open a modal — does focus go in, does Tab stay inside, does Escape close it, does focus return to the
trigger. Tab escaping a modal and clicking things behind it is the most common dialog bug there is,
and no automated tool catches it.**

Then the ARIA rule. **The first rule of ARIA is don't use ARIA. Every attribute is a promise I now have
to implement by hand. `role="button"` on something that isn't focusable advertises a door with no
handle — that's worse than nothing. The legitimate uses are narrow: labels for icon buttons, describedby
for error text, and aria-live for async results, which is the one everyone misses, because otherwise a
screen reader user gets no signal that anything happened.**

Close honestly, which is the part that makes it credible. **I don't claim WCAG AA compliance because I
haven't audited for it. I do the four things that catch most real failures — semantic elements, real
labels, visible focus, and contrast — and I test with the keyboard. Overclaiming compliance you haven't
measured is worse than scoping it honestly.**
