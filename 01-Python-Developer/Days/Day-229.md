# Part 1 — Controlled vs uncontrolled

```jsx
// ⭐ CONTROLLED — React owns the value
<input value={name} onChange={e => setName(e.target.value)} />
// ⭐⭐ re-renders on EVERY KEYSTROKE. Fine for 5 fields.
//    Noticeable on 40 fields with expensive siblings.

// ⭐ UNCONTROLLED — the DOM owns it, you read it at submit
<input name="name" defaultValue={user.name} />
const data = Object.fromEntries(new FormData(e.target));
// ⭐⭐ NO re-renders while typing. This is what form libraries do.
```

| ⭐ Use controlled when | ⭐ Use uncontrolled when |
|---|---|
| You need the value **as it changes** — live search, a character counter, a field that enables a button | ⭐⭐ Most forms. You only need values at submit. |
| Cross-field logic on every keystroke | Big forms where typing lag appears |

> ⭐ **`value` without `onChange` makes an input read-only and React warns.** Use `defaultValue` for
> uncontrolled, `value` + `onChange` for controlled. Switching a field from one to the other mid-life
> is a genuine React warning you should never silence.

# Part 2 — ⭐⭐ One schema, two validators

```typescript
// schema.ts — ⭐⭐ ONE definition. Day 219's Zod, now doing double duty.
export const CreateUser = z.object({
  email: z.string().email("Enter a valid email"),
  age: z.number().int().min(18, "Must be 18 or over"),
  role: z.enum(["admin", "user"]),
});
export type CreateUser = z.infer<typeof CreateUser>;
```

```python
# ⭐ the SAME rules on the server — the boundary that actually protects you
class CreateUser(BaseModel):
    email: EmailStr
    age: int = Field(ge=18)
    role: Literal["admin", "user"]
```

```
⭐⭐ WHY BOTH, AND WHY THAT IS NOT DUPLICATION

⭐   CLIENT ⇒ ⭐ UX. Instant feedback, no round trip, no lost typing.
⭐            ⭐⭐ IT IS NOT SECURITY. curl ignores it entirely.
⭐   SERVER ⇒ ⭐⭐ THE ACTUAL BOUNDARY. Assume every request is
⭐            hand-crafted, because it can be.

⭐   ⇒ ⭐⭐ THE REAL RISK IS NOT DUPLICATION — IT IS **DRIFT**.
⭐     Server tightens age to 21, client still says 18 ⇒ the user
⭐     submits a valid-looking form and gets a mystery rejection.
⭐   ⇒ ⭐ FIX: GENERATE ONE FROM THE OTHER (Day 246), or keep both
⭐     in one reviewed file with a test that asserts they agree.
```

# Part 3 — ⭐⭐ Landing the server's error on the right field

This is the payoff of Day 217's error shape.

```jsx
const form = useForm({ resolver: zodResolver(CreateUser) });

const onSubmit = form.handleSubmit(async (values) => {
  try {
    await api("/users", { method: "POST", body: values });
  } catch (e) {
    if (e instanceof ApiError && e.status === 422) {
      for (const { field, message } of e.body.detail) {
        form.setError(field, { message });        // ⭐⭐ ON THE INPUT
      }
      return;
    }
    form.setError("root", { message: "Could not save. Try again." });
  }
});
```

| ⭐ Server says | ⭐⭐ The user must see |
|---|---|
| 422, `email` already taken | ⭐⭐ The message **under the email box** — not a toast |
| 422, several fields | ⭐ Each on its own field, **focus the first** |
| 409 conflict (someone else edited) | ⭐ A form-level message + what to do |
| 500 | ⭐ Form-level, generic, ⭐⭐ **and the draft is not cleared** |
| 401 | ⭐ Re-auth, then **resubmit the same values** |

> ⭐⭐ **Never clear the form on failure.** The single most user-hostile thing a form can do is discard
> what someone typed because the server said no. Keep the values, mark the fields, let them fix it.

# Part 4 — The four things every real form needs

```
⭐⭐ ① DOUBLE-SUBMIT PROTECTION
⭐   ❌ user double-clicks Save ⇒ ⭐⭐ TWO ORDERS.
⭐   ✅ disable while pending — ⭐ NECESSARY BUT NOT SUFFICIENT:
⭐      a slow network + Enter key can still race.
⭐   ⭐⭐ THE REAL FIX IS SERVER-SIDE: an idempotency key generated
⭐     ONCE PER FORM INSTANCE and sent with the request (Day 444).
⭐     The client control is UX; the server control is correctness.

⭐⭐ ② VALIDATION TIMING
⭐   ❌ validate on every keystroke ⇒ "invalid email" while typing "a"
⭐   ✅ ⭐ VALIDATE ON BLUR, RE-VALIDATE ON CHANGE ONCE IT HAS ERRORED

⭐⭐ ③ THE UNSAVED-CHANGES GUARD
⭐   ⭐ if dirty, warn before navigating away. beforeunload for the
⭐     tab, a router block for in-app navigation.

⭐⭐ ④ ACCESSIBILITY — see Day 239, but the minimum is here:
⭐   · ⭐⭐ EVERY INPUT HAS A <label htmlFor>. Placeholder is NOT a label.
⭐   · aria-invalid + aria-describedby pointing at the error text
⭐   · ⭐ the error is TEXT, not just a red border (colour alone fails)
⭐   · focus moves to the first error on failed submit
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you handle form validation?"**

Separate the two jobs immediately — this is what most candidates blur. **Client validation is a
user-experience feature; server validation is the security boundary. They're not duplicates of each
other, because curl ignores the client entirely. So I never describe client validation as protecting
anything.**

Then name the risk that actually bites. **The problem isn't duplication, it's drift. If the server
tightens a rule and the client doesn't, the user fills in a form that passes locally and gets a mystery
rejection. So the rules come from one place — I share a Zod schema for the client and generate against
the same OpenAPI contract, with a test asserting they agree.**

Then the payoff that shows end-to-end thinking. **A 422 has to land under the right input, not in a
toast. That requires the server's error to carry a field name — which is a change I made to my API
after building the client, because I couldn't render a good error state against a nested validation
blob. And the form never clears on failure; discarding what someone typed because the server said no
is the most user-hostile thing a form can do.**

Close on the correctness point. **Disabling the submit button while pending is UX, not a fix — a slow
network and the Enter key still race, and you get two orders. The real control is an idempotency key
generated once per form instance and enforced on the server.**
