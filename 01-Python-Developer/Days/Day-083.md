# Day 083

**L-083** · Bash scripting — ⭐⭐ `set -euo pipefail`, `trap`, and knowing when to stop

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a shell script's default behaviour is to ignore errors and keep going —
> so the first three lines of every script exist to switch that off, and a script without them will
> one day do half of a dangerous thing and report success.**
>
> ⭐ You are not becoming a bash programmer. **You are becoming someone whose CI scripts, entrypoints
> and Makefiles are not a liability** — and who knows exactly when to stop and open a `.py` file.

---

# Part 1 — ⭐⭐ The header, derived one flag at a time

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'
```

```
⭐⭐ WHY EACH LINE EXISTS. Do not memorise them — derive them, because the interview
⭐   question is "what does that line do" and the good answer is a failure mode.
⭐
⭐ #!/usr/bin/env bash   ⭐ find bash on PATH. ⭐⭐ NOT #!/bin/bash (missing on some
⭐                         images) and NOT #!/bin/sh — ⭐ on Debian sh is dash, which
⭐                         has no arrays and no [[ ]], so your script fails ONLY THERE.
⭐
⭐ set -e   ⭐⭐ EXIT ON ERROR. Default: a failing command is IGNORED and the next
⭐          line runs anyway. ⇒ ⭐⭐ `cd /srv/app` fails ⇒ `rm -rf ./data` RUNS IN
⭐          THE WRONG DIRECTORY. That is the whole argument for this flag.
⭐
⭐ set -u   ⭐⭐ ERROR ON UNDEFINED VARIABLE. Default: an unset variable expands to
⭐          the EMPTY STRING ⇒ ⭐⭐ `rm -rf "$PREFIX/"` becomes `rm -rf /`.
⭐          ⭐ This is not folklore; it has shipped in real installers.
⭐
⭐ set -o pipefail   ⭐⭐ A PIPELINE FAILS IF ANY STAGE FAILS. Default is the LAST
⭐          stage only (Day 079) ⇒ ⭐⭐ `python fetch.py | tee out.json` exits 0
⭐          even when fetch.py crashed ⇒ CI is green over an empty artefact.
⭐
⭐ IFS=$'\n\t'   ⭐ remove SPACE from the split characters ⇒ ⭐ filenames with
⭐          spaces stop being a hazard in the few places splitting still happens.
```

```
⚠️⚠️ ⭐⭐ THE HONEST PART — WHERE `set -e` DOES *NOT* FIRE. Knowing these is what
⭐    separates "I copied the header" from "I understand it":
⭐    1. in a condition:  `if grep -q x f; then`      ⭐ correct — a test may fail
⭐    2. left of && or || : `cmd || echo "oops"`      ⭐ you handled it
⭐    3. ⭐⭐ `local x=$(failing)` ⇒ the exit status is `local`'s, NOT the command's.
⭐         ⇒ ⭐⭐ DECLARE FIRST, ASSIGN SECOND:   local x ; x=$(failing)
⭐    4. ⭐ inside a function called in a condition — -e is suspended for the whole call
⭐    5. any command not last in a pipeline (⭐ which is exactly what pipefail fixes)
⭐    ⇒ ⭐⭐ SO: the header is a SAFETY NET, NOT A GUARANTEE. Check what matters
⭐         EXPLICITLY, the same way Day 060 says to handle expected errors on purpose.
```

# Part 2 — ⭐ The language, in one screen

```bash
name="world"                      # ⭐⭐ NO SPACES around = (a space makes it a command)
readonly MAX=10                   # ⭐ a constant
local tmp                         # ⭐ inside a function — ⭐⭐ everything is GLOBAL otherwise

echo "hello $name"                # ⭐⭐ ALWAYS QUOTE (Day 079)
echo "${name}s"                   # ⭐ braces disambiguate
"${1:?usage: deploy.sh ENV}"      # ⭐⭐ REQUIRED ARG — errors with a message if missing
env="${1:-staging}"               # ⭐ default if unset
count="${#name}"                  # length
```

```bash
if [[ -f "$file" ]]; then ... fi          # ⭐⭐ [[ ]] ALWAYS — it is bash's, and safer
# ⭐ -f file · -d dir · -e exists · -r readable · -z empty string · -n non-empty
if [[ "$a" == "b" ]]; then ... fi          # ⭐ string compare (== does globbing! use = for literal)
if [[ "$n" -gt 5 ]]; then ... fi           # ⭐ NUMERIC: -eq -ne -lt -le -gt -ge
if (( n > 5 )); then ... fi                # ⭐⭐ arithmetic context — reads far better
if [[ "$s" =~ ^v[0-9]+$ ]]; then ... fi    # ⭐ regex, unquoted right side
```

⚠️ ⭐⭐ **`[ ]` is a *program*, `[[ ]]` is bash syntax.** With `[ ]`, an empty variable disappears
before the test runs and you get "unary operator expected"; **`[[ ]]` does not word-split, so it just
works.** ⭐ Use `[[ ]]` unconditionally and stop thinking about it.

```bash
files=("a.txt" "b file.txt")      # ⭐ array
for f in "${files[@]}"; do        # ⭐⭐ THE QUOTED [@] — anything else re-splits
    echo "$f"
done

for f in *.py; do ... done                    # ⭐ glob directly — never `$(ls)`
while IFS= read -r line; do ... done < f      # ⭐⭐ THE CORRECT LINE READER
find . -name "*.py" -print0 | while IFS= read -r -d '' f; do ... done   # ⭐⭐ NUL-safe (Day 080)
```

```
⭐⭐ `while IFS= read -r line` — three defences in six characters:
⭐   IFS=     ⇒ do not strip leading/trailing whitespace
⭐   -r       ⇒ ⭐⭐ do NOT interpret backslashes (a Windows path would be mangled)
⭐   "$line"  ⇒ do not split when you use it
⭐ ⇒ ⭐ and `for line in $(cat f)` is wrong for all three reasons at once.
```

```bash
deploy() {                        # ⭐ function
    local env="$1"                # ⭐⭐ ALWAYS local — no local means global
    [[ -n "$env" ]] || { echo "env required" >&2; return 2; }   # ⭐⭐ errors to STDERR (Day 079)
    printf 'deploying to %s\n' "$env"
}
deploy "$@"                       # ⭐⭐ "$@" — all args, correctly quoted
```

# Part 3 — ⭐⭐ `trap` — the shell's context manager

```bash
tmpdir="$(mktemp -d)"                     # ⭐ safe unique temp dir
cleanup() { rm -rf "$tmpdir"; }
trap cleanup EXIT                         # ⭐⭐ RUNS ON ANY EXIT — success, error, or Ctrl-C
```

```
⭐⭐ trap ... EXIT IS EXACTLY `finally` (Day 059) AND EXACTLY A CONTEXT MANAGER (Day 052).
⭐   Same problem, same solution, three languages deep:
⭐        Python    with open(...) / try: ... finally:
⭐        Bash      trap cleanup EXIT
⭐        C         goto cleanup;
⭐   ⇒ ⭐⭐ AND THE SAME LIMIT: it does NOT run on SIGKILL (Day 081). Cleanup code is
⭐        a courtesy, never a guarantee.
```

| Trap | ⭐ When |
|---|---|
| ⭐⭐ `trap cleanup EXIT` | ⭐⭐ **the one you want** — covers normal exit, `set -e`, and signals that terminate |
| `trap 'echo interrupted' INT TERM` | ⭐ a message before dying |
| ⭐ `trap 'echo "line $LINENO"' ERR` | ⭐⭐ a cheap stack trace: **prints where it failed** |

```bash
# ⭐⭐ A REAL SCRIPT — every idea from today, in fifteen lines
#!/usr/bin/env bash
set -euo pipefail

readonly DB="${DATABASE_URL:?DATABASE_URL is required}"     # ⭐ fail fast, with a message
readonly OUT="${1:-./backups}"

tmp="$(mktemp -d)"
trap 'rm -rf "$tmp"' EXIT                                    # ⭐⭐ cleanup, always

log() { printf '%s %s\n' "$(date -Is)" "$*" >&2; }           # ⭐⭐ logs to stderr

log "dumping"
pg_dump "$DB" > "$tmp/dump.sql"                              # ⭐ -e aborts here on failure
gzip "$tmp/dump.sql"

mkdir -p "$OUT"
mv "$tmp/dump.sql.gz" "$OUT/$(date +%F).sql.gz"              # ⭐⭐ move LAST = atomic-ish (Day 076)
log "done: $OUT"
```

⭐⭐ **Note the shape, because it is the same shape as good Python:** validate inputs at the top, fail
fast with a message, do the work in a scratch area, **publish by moving into place at the very end**,
and clean up in a handler. ⭐ **A half-finished backup never appears in the backup directory** — that
is Day 076's atomic write, at script level.

# Part 4 — ⭐ `shellcheck`, and when to stop

```bash
shellcheck deploy.sh          # ⭐⭐ catches ~every mistake on this page, statically
```

⭐⭐ **`shellcheck` is bash's `mypy`** (Day 062). It finds unquoted expansions, `[ ]` misuse,
`$(ls)`, useless `cat`, and the `local x=$(...)` trap. ⭐ **Run it in CI on every `.sh` file**; it is
one line and it removes a whole category of incident. ⭐ In pre-commit (Day 099) it costs nothing.

```
⭐⭐ WHEN TO STOP WRITING BASH — the judgement question, and worth saying out loud:
⭐   WRITE BASH when it is:
⭐     · a sequence of commands you would otherwise type
⭐     · under ~50 lines, with linear flow
⭐     · glue: an entrypoint, a CI step, a Makefile target
⭐     · ⭐ something whose whole job is running OTHER programs
⭐
⭐   ⭐⭐ SWITCH TO PYTHON THE MOMENT you need:
⭐     · ⭐⭐ DATA STRUCTURES — bash has strings, and arrays it barely means
⭐     · ⭐⭐ ERROR HANDLING beyond "abort" — retries, backoff, partial recovery
⭐     · ⭐⭐ ANY JSON — ⭐ if you are reaching for jq inside a loop, you are writing
⭐          a program in the wrong language
⭐     · CONCURRENCY beyond `&` and `wait`
⭐     · ⭐⭐ TESTS. ⭐ This is the decisive one: if it must not break, it needs a
⭐          test, and testing bash is miserable while pytest is a joy (Days 093-094).
⭐   ⇒ ⭐⭐ THE RULE: BASH FOR GLUE, PYTHON FOR LOGIC. The failure happens in both
⭐        directions — a 400-line bash script nobody dares edit, and a Python script
⭐        that shells out for everything anyway.
```

⭐ **Two habits that pay immediately:** `set -x` (echo each command as it runs — the shell's
`print` debugging) and `bash -n script.sh` (syntax check without executing). ⭐⭐ **And run destructive
scripts with `--dry-run` support you built in from the start**, printing what it *would* do — the same
instinct as Day 080's `xargs -t`.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **No `set -euo pipefail`** | ⭐⭐ Errors are ignored by default; half the job runs and exits 0. |
| Believing `-e` catches everything | ⭐⭐ Five documented holes — `local x=$(...)` is the common one. |
| `#!/bin/sh` with bash syntax | ⭐ `sh` is `dash` on Debian: no arrays, no `[[ ]]`. |
| ⭐ `[ ]` with a possibly-empty variable | ⭐⭐ "unary operator expected". Use `[[ ]]`. |
| `name = value` | ⭐ Spaces make it a command. No spaces around `=`. |
| ⭐ Forgetting `local` | ⭐⭐ Everything is global; two functions quietly share a variable. |
| `for line in $(cat f)` | ⭐⭐ `while IFS= read -r line; do … done < f`. |
| `for f in $(ls)` | ⭐ Use a glob. |
| ⭐ `"${arr}"` for an array | ⭐ `"${arr[@]}"`. |
| Errors printed to stdout | ⭐⭐ `>&2` — or they contaminate the pipeline (Day 079). |
| No cleanup on failure | ⭐⭐ `trap cleanup EXIT`. |
| ⭐ Writing the artefact in place | ⭐ Build in a temp dir, `mv` into place at the end. |
| ⭐ 300 lines of bash with `jq` in a loop | ⭐⭐ That is a Python program. |
| Not running `shellcheck` | ⭐ One CI line; catches nearly all of the above. |

## Interview questions

**Q: What does `set -euo pipefail` do, and why is it the first line?**
> Each flag turns off a default that's actively dangerous. `-e` exits on a failing command, because
> otherwise a failed `cd` is followed by an `rm` running in the wrong directory. `-u` errors on an
> unset variable rather than expanding it to empty, which is what turns `rm -rf "$PREFIX/"` into
> `rm -rf /`. `pipefail` makes a pipeline fail if any stage failed, not just the last — otherwise
> `python fetch.py | tee out.json` exits zero when the Python crashed and CI goes green over an empty
> file. I'd add that it's a safety net rather than a guarantee: `-e` doesn't fire inside conditions,
> on the left of `||`, or for `local x=$(failing)`, where the exit status belongs to `local`. So
> anything that really matters still gets checked explicitly.

**Q: Why `trap cleanup EXIT`?**
> Because it's `finally`. It runs on normal exit, on a `set -e` abort, and on Ctrl-C, so the temp
> directory gets removed on every path rather than only the happy one. It's the same idea as a
> context manager in Python and `goto cleanup` in C — the problem is universal, and so is the shape
> of the answer. And it has the same limit: it doesn't run on `SIGKILL`, so cleanup code is a courtesy
> and never a correctness argument.

**Q: When do you stop writing bash?**
> When I need data structures, real error handling like retries with backoff, JSON, concurrency, or
> tests. The JSON one is the everyday signal — if `jq` has appeared inside a loop, I'm writing a
> program in a language that doesn't have types. The decisive one is tests: if the script must not
> break, it needs tests, and testing bash is painful where pytest is pleasant. So bash for glue —
> entrypoints, CI steps, sequences of commands I'd otherwise type — and Python the moment there's
> logic. The mistake happens in both directions: a 400-line bash script no one dares edit, and a
> Python script that shells out for everything anyway.

**Q: What's the difference between `[` and `[[`?**
> `[` is a program — `test` — so its arguments go through normal word splitting, which means an empty
> variable vanishes before the test runs and you get "unary operator expected". `[[` is bash syntax,
> so it doesn't split or glob its operands, and it supports `=~` and `&&` directly. There's no case
> where I'd prefer `[` in a bash script, so I use `[[` unconditionally and remove the whole class of
> bug.

## 🎙️ Articulation drill

Record two minutes: **"Talk me through the top of a shell script you would put in production."**

⭐ **Do not recite the flags. Give each one its disaster**, because that is the difference between
copying a header and understanding it: **"`set -e`, because otherwise a failed `cd` is followed by an
`rm` in whatever directory I happened to be in. `set -u`, because an unset variable expanding to empty
is how `rm -rf "$PREFIX/"` becomes `rm -rf /`. And `pipefail`, because a pipeline reports only its
last command, so a crashed Python script piped into `tee` exits zero and CI goes green over an empty
file."**

⭐⭐ **Then show you know its limits, which is what makes it convincing:** *"but that header is a
safety net, not a guarantee. `-e` doesn't fire inside an `if`, on the left of `||`, or for
`local x=$(...)`, where the exit status is `local`'s and not the command's. So the things that really
matter still get an explicit check — same principle as handling expected errors deliberately rather
than hoping a broad catch covers them."*

⭐ **Then the cleanup and the boundary:** *"`trap cleanup EXIT` for anything temporary, because it's
`finally` and it fires on error and Ctrl-C too. Build into a scratch directory and move into place at
the end, so a half-finished artefact never appears. `shellcheck` in CI. And I'd keep the script short
— bash for glue, Python the moment there's logic, because the moment it needs a test, bash is the
wrong language."*
