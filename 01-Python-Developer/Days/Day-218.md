# Part 1 — Why the backend engineer insists

```
⭐⭐ THE ARGUMENT THAT WINS, AND IT IS NOT "FEWER BUGS"

⭐   Your API returns a shape. ⭐ THE CLIENT ASSUMES A SHAPE.
⭐   ⭐⭐ NOTHING CHECKS THAT THESE ARE THE SAME SHAPE.

⭐   You rename user.full_name -> user.name on the server.
⭐   ⭐ Python: mypy catches it in your backend. ✅
⭐   ⭐ The React app: renders "undefined" to a customer. ❌
⭐     ⭐⭐ NO ERROR. NO CRASH. JUST THE WORD "undefined" ON SCREEN.

⭐   ⇒ ⭐⭐ TYPESCRIPT + A GENERATED CLIENT (Day 246) TURNS THAT
⭐     INTO A BUILD FAILURE. That is the whole argument, and it is
⭐     a BACKEND argument — it protects YOUR contract.
```

| ⭐ Objection | Answer |
|---|---|
| *"It slows me down"* | ⭐ For a script, yes. For a codebase you return to in three months, the annotation is the documentation you would otherwise not write. |
| *"React apps are small"* | Until they are not. ⭐⭐ The refactor you are afraid to do is the cost of not having types. |
| *"Types don't catch real bugs"* | ⭐ They catch exactly one class — **shape drift** — which happens to be the most common client-side production bug and the one with no runtime symptom. |

> ⭐ **Same claim as Day 062.** `Any` is a defect there; `any` is a defect here. The difference is that
> mypy is a step you can quietly skip, while TypeScript sits between you and a working build.

# Part 2 — ⭐⭐ Structural, exactly like `Protocol`

```typescript
type HasId = { id: string };

function show(x: HasId) { console.log(x.id); }

show({ id: "a", extra: 1 });   // ⭐ fits — it HAS an id
                               // (⭐ object literals get excess-property
                               //  checking; a variable would pass silently)
```

```python
# ⭐ Day 056 — the identical idea
class HasId(Protocol):
    id: str

def show(x: HasId) -> None: ...
```

| | Python | TypeScript | Java |
|---|---|---|---|
| **Matching** | `Protocol` = structural | ⭐⭐ **always** structural | ⭐ nominal (`implements`) |
| **Declared?** | no | **no** | yes |
| **Enforced at runtime** | ❌ no | ❌ **no — erased entirely** | ✅ yes |

> ⭐⭐ **Types are erased.** There is no TypeScript at runtime — it compiles to plain JavaScript with
> the annotations stripped. A JSON response is `any`-shaped in reality no matter what you *declared*
> it to be. **So a type is a claim about data you have not validated**, which is why Day 246 pairs
> types with a runtime validator at the boundary. Believing the annotation checked your API response
> is the single most common TypeScript misunderstanding.

# Part 3 — The subset you actually write

```typescript
// ⭐ objects — prefer `type`, use `interface` when you need declaration merging
type User = {
  id: string;
  name: string;
  email?: string;          // ⭐ optional  -> string | undefined
  role: "admin" | "user";  // ⭐⭐ UNION OF LITERALS — the best feature here
  createdAt: string;       // ⭐ it is a STRING on the wire, not a Date
};

// ⭐⭐ discriminated union — models your four states exactly (Day 217)
type Result<T> =
  | { status: "loading" }
  | { status: "error"; error: ApiError }
  | { status: "success"; data: T };

function render(r: Result<User[]>) {
  switch (r.status) {
    case "loading": return <Skeleton />;
    case "error":   return <ErrorBox e={r.error} />;   // ⭐ r.error known here
    case "success": return <List items={r.data} />;    // ⭐⭐ r.data known here
  }                     // ⭐ forget a case and the compiler tells you
}
```

| ⭐ Feature | Python analogue |
|---|---|
| `"admin" \| "user"` | `Literal["admin","user"]` — ⭐⭐ the highest-value annotation you can write |
| Discriminated union | tagged union / `match` on a field |
| `T[]`, `Record<K,V>` | `list[T]`, `dict[K,V]` |
| `Partial<T>`, `Pick<T,K>`, `Omit<T,K>` | ⭐ no clean equivalent — genuinely better here |
| `as const` | frozen literal — ⭐ narrows `string` to the exact value |

> ⭐⭐ **The discriminated union is the single most useful thing in this stage.** It makes the four
> states of Day 217 *unrepresentable-if-wrong*: you cannot have `data` while `status` is `"loading"`,
> and the compiler forces you to handle every branch. That is the same "make illegal states
> unrepresentable" argument from Stage 8.

# Part 4 — ⭐⭐ `any` vs `unknown`, and the config

```typescript
const a: any = JSON.parse(text);
a.foo.bar.baz;              // ⭐⭐ COMPILES. CRASHES AT RUNTIME.
                            //    `any` disables checking, and it SPREADS —
                            //    everything derived from it is unchecked too.

const u: unknown = JSON.parse(text);
u.foo;                      // ✅ compile error — good
if (isUser(u)) u.name;      // ⭐ must narrow first. THIS is the right default.
```

| | `any` | `unknown` |
|---|---|---|
| Assign anything **to** it | ✅ | ✅ |
| Use it without checking | ⭐⭐ ✅ **(the problem)** | ❌ must narrow |
| Spreads through your code | ⭐ yes, silently | no |

```jsonc
// tsconfig.json — ⭐⭐ without these, TypeScript is decoration
{
  "compilerOptions": {
    "strict": true,                        // ⭐⭐ THE ONE THAT MATTERS
    "noUncheckedIndexedAccess": true,      // ⭐ arr[0] is T | undefined — correct!
    "noImplicitOverride": true,
    "exactOptionalPropertyTypes": true
  }
}
```

> ⭐⭐ **`strict: false` is the most common way a TypeScript codebase is fake.** Without it,
> everything untyped is implicitly `any`, `null` is assignable everywhere, and you get the syntax of
> types with none of the guarantees. **Same finding as mypy without `--strict` on Day 062: the tool
> reports success because you asked it a weaker question.**
>
> ⭐ Ban `any` in CI (`@typescript-eslint/no-explicit-any`). Where you genuinely need an escape hatch,
> `unknown` plus a narrowing function is the honest version — it forces the check to be *written*
> rather than assumed.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "why TypeScript?"**

Do not say "fewer bugs" — everyone says it and it invites an argument. Make it a contract argument,
which is a backend argument. **My API returns a shape and the client assumes a shape, and nothing
checks those are the same shape. I rename `full_name` to `name` on the server, mypy catches every
Python caller, and the React app renders the literal word "undefined" to a customer — no error, no
crash. TypeScript plus a client generated from my OpenAPI spec turns that into a build failure. It
protects my contract, not just their code.**

Then show you know its limits, which is what separates use from belief. **Types are erased — there's
no TypeScript at runtime. So annotating a JSON response as `User` doesn't check anything; it's a claim
about data I haven't validated. That's why the boundary gets a runtime validator and the interior gets
types.**

Close on the two things that decide whether it is real. **`strict: true`, or it's decoration — without
it everything untyped is implicitly `any` and null is assignable everywhere, which is the same finding
as running mypy without strict: the tool reports success because you asked it a weaker question. And
`any` is banned, because it doesn't just skip one check, it spreads to everything derived from it.
`unknown` forces the narrowing to actually be written.**
