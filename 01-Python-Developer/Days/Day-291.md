# Day 291 ⚙️

**P-291** · ⚙️ **The rules engine II** — ⭐⭐ evaluation, safe change, and operating it

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: "we want to change this threshold from 3 to 6" is not a code question,
> it is an evidence question — and the only honest answer is a number of past cases whose outcome
> would have flipped, produced before the change ships.**
>
> ⭐ Day 290 made rules into data. ⭐⭐ Today that pays off in the one way that matters: because a
> rule set is data and decisions store their inputs, a proposed change can be *evaluated against
> history* rather than argued about in a meeting.

---

# Part 1 — ⭐⭐ The question that makes the design real

```
⭐⭐ SOMEONE ASKS: "CAN WE RELAX THE TENURE RULE TO 6 MONTHS?"
⭐   ⭐ ❌ "It's a one-line change." ⭐⭐ TRUE AND IRRELEVANT.
⭐   ⭐ ❌ "It should be fine." ⭐ Based on what?
⭐   ⭐ ✅ ⭐⭐ "OF THE LAST 12,000 DECISIONS, 340 WOULD FLIP FROM
⭐        DECLINE TO APPROVE. 91% OF THOSE WERE DECLINED SOLELY
⭐        BY THIS RULE; 9% HAD A SECOND DECLINE REASON AND ARE
⭐        UNAFFECTED. NO APPROVALS BECOME DECLINES."
⭐   ⇒ ⭐⭐ THAT LAST CLAUSE IS THE ONE PEOPLE FORGET TO CHECK,
⭐     AND IT IS WHERE THE SURPRISES LIVE — a "relaxation" that
⭐     tightens something is always an interaction with another
⭐     rule, and it is never anticipated.

⭐ ⇒ ⭐ You can only answer this because Day 289 stored the
⭐   INPUTS with each decision. ⭐⭐ WITHOUT THAT, THERE IS NO
⭐   BACKTEST, AND EVERY RULE CHANGE IS SHIPPED ON AN OPINION.
```

# Part 2 — ⭐⭐ Backtesting

```
⭐⭐ THE MECHANISM IS SIMPLE. THE DISCIPLINE IS NOT:
⭐   ① take N historical decisions with their stored inputs
⭐   ② evaluate each against the CANDIDATE rule set
⭐   ③ ⭐⭐ DIFF THE OUTCOMES — a confusion table of what
⭐     changed, in which direction
⭐   ④ ⭐ sample the changed ones and READ THEM. Actually read
⭐     them. ⭐⭐ TWENTY CASES READ BY A HUMAN TELLS YOU MORE
⭐     THAN THE AGGREGATE, EVERY TIME.

⭐⭐ |            | new: approve | new: decline | new: refer |
⭐   | old approve| ⭐ 8,410      | ⭐⭐ 0 ← CHECK | 12         |
⭐   | old decline| ⭐ 340        | ⭐ 3,100      | 0          |
⭐   | old refer  | ⭐ 4          | 0            | ⭐ 134      |
```

```
⭐⭐ FOUR THINGS THAT MAKE A BACKTEST HONEST:

⭐ ① ⭐⭐ REPLAY AT THE ORIGINAL `as_of` DATE (Day 289). ⭐ If
⭐     you replay March's cases against June's thresholds, you
⭐     measured the wrong change and the number is garbage.

⭐ ② ⭐⭐ THE CLASS-IMBALANCE TRAP. ⭐ Declines are 0.4% of
⭐     traffic ⇒ a random sample of 1,000 contains FOUR. ⭐⭐ YOU
⭐     WILL CONCLUDE "NO IMPACT" FROM A SAMPLE THAT COULD NOT
⭐     POSSIBLY HAVE SHOWN ONE. ⇒ ⭐ Stratify: sample the
⭐     minority classes heavily and weight the results back.

⭐ ③ ⭐ IT MEASURES WHAT WOULD HAVE HAPPENED, ⭐⭐ NOT WHAT
⭐     WILL. Behaviour changes: relax a rule and more people
⭐     who would have been declined now apply. ⭐ Backtests
⭐     cannot see induced demand, and saying so out loud is the
⭐     difference between using a tool and believing it.

⭐ ④ ⭐ THE CASES YOU HAVE ARE THE CASES THAT REACHED YOU.
⭐     ⭐⭐ SURVIVORSHIP: if a front-end filter stops people
⭐     applying, your history under-represents exactly the
⭐     population a relaxation would newly admit.
```

# Part 3 — ⭐⭐ Shipping a rule change safely

```
⭐⭐ A RULE CHANGE IS A DEPLOY. ⭐ It changes behaviour in
⭐   production, it can be wrong, and it must be reversible.
⭐   ⇒ ⭐⭐ SO IT GETS THE SAME GATES AS CODE (Day 281), EVEN
⭐     THOUGH IT IS A DATABASE ROW AND NOTHING FORCES IT.

⭐⭐ THE LADDER, AND EACH STEP ANSWERS A DIFFERENT QUESTION:
⭐   ① ⭐ STATIC CHECKS (Day 290) — "is the rule set coherent?"
⭐   ② ⭐ CASE TABLE + PROPERTIES — "does it do what we meant?"
⭐   ③ ⭐⭐ BACKTEST — "what would have changed?"
⭐   ④ ⭐⭐ SHADOW MODE — evaluate BOTH rule sets on live
⭐        traffic, serve the old one, log the difference.
⭐        ⇒ ⭐⭐ THE ONLY STEP THAT SEES ***TODAY'S*** INPUT
⭐          DISTRIBUTION rather than last year's. ⭐ Run it for
⭐          a week; it is nearly free and it catches the change
⭐          that was correct on history and wrong on reality.
⭐   ⑤ ⭐ CANARY BY SEGMENT — one category, one region, watch
⭐        the reason-code distribution (Part 4).
⭐   ⑥ ⭐ FULL, with the previous version one row away.

⭐ ⇒ ⭐ And rollback is Day 283's lesson unchanged: ⭐⭐ ROLL
⭐   BACK THE RULE SET INSTANTLY; ***DO NOT*** RETROACTIVELY
⭐   RE-DECIDE. ⭐ Past decisions stand as made. Re-deciding is
⭐   a separate, deliberate, communicated act — because someone
⭐   has already been told the answer.
```

# Part 4 — ⭐⭐ The metrics of a decision system

```
⭐⭐ YOU CANNOT MEASURE "CORRECT". YOU CAN MEASURE FIVE THINGS
⭐   THAT MOVE WHEN CORRECTNESS DOES:

⭐ ① ⭐ OUTCOME MIX — approve / decline / refer, over time.
⭐      ⭐⭐ ALERT ON THE ***DISTRIBUTION SHIFTING***, NOT ON
⭐        INDIVIDUAL DECISIONS. ⭐ A jump from 4% to 11% refer
⭐        overnight is either a rule change or a data change,
⭐        and you want to know within an hour either way.
⭐ ② ⭐⭐ REASON-CODE DISTRIBUTION — the single best early
⭐      warning. ⭐ One code going from 2% to 30% means an
⭐      upstream field changed shape (an integration started
⭐      sending nulls, a category was renamed) — ⭐⭐ AND
⭐      NOTHING ELSE IN YOUR SYSTEM WILL NOTICE, because every
⭐      individual decision was computed correctly.
⭐ ③ ⭐⭐ OVERRIDE RATE — ***THE MOST VALUABLE NUMBER YOU
⭐      HAVE*** (Part 5).
⭐ ④ ⭐ REFER RATE — your human cost. ⭐ It is also the metric
⭐      people game: making everything refer is "safe" and
⭐      quietly moves the entire problem onto a person.
⭐ ⑤ ⭐ COVERAGE — which rules fired at all this month
⭐      (Day 290's cheapest audit, run on production data).
```

# Part 5 — ⭐⭐ The override rate

```
⭐⭐ AN OVERRIDE IS A HUMAN DISAGREEING WITH THE ENGINE, IN
⭐   PUBLIC, WITH A REASON. ⭐ It is the only labelled feedback
⭐   this system ever produces for free.

⭐   ⭐ EVERY OVERRIDE RECORDS: who, when, the decision id, the
⭐     new outcome, ⭐⭐ AND A REASON FROM A FIXED LIST plus
⭐     free text. ⭐ Free text alone is unanalysable; a list
⭐     alone loses the case you did not anticipate.
⭐   ⇒ ⭐⭐ THE OVERRIDE QUEUE, GROUPED BY REASON, IS THE
⭐     BACKLOG FOR THE NEXT RULE CHANGE. ⭐ It tells you what
⭐     the rules get wrong, ranked by frequency, for free.

⭐⭐ AND THE TWO READINGS THAT ARE BOTH BAD:
⭐   ⭐ A ***HIGH*** OVERRIDE RATE (say > 15%) ⇒ the rules do
⭐     not encode the real policy. ⭐ The humans are the system
⭐     and the engine is decoration.
⭐   ⭐⭐ AN OVERRIDE RATE NEAR ***ZERO*** IS NOT A TRIUMPH —
⭐     IT USUALLY MEANS THE HUMANS STOPPED LOOKING. ⭐ Automation
⭐     complacency is well documented: a reviewer who agrees 400
⭐     times in a row stops reading by case 40.
⭐   ⇒ ⭐⭐ SO YOU MEASURE REVIEW ***TIME***, NOT JUST OUTCOME.
⭐     ⭐ A median review of four seconds is a rubber stamp, and
⭐       you have a control that exists only on the org chart.
```

# Part 6 — ⭐ Governance: who may change a rule

```
⭐   ⭐ AUTHORING is separate from APPROVING. ⭐⭐ FOUR EYES ON
⭐     EVERY RULE CHANGE, enforced in the app rather than in a
⭐     policy document, because a policy document has never
⭐     stopped anything at 6 p.m.
⭐   ⭐ The change record answers: WHO, WHEN, WHAT CHANGED
⭐     (a diff), WHY (a link to a ticket or policy update), and
⭐     ⭐⭐ WHAT THE BACKTEST SAID — stored WITH the change, so
⭐     the evidence and the decision live together forever.
⭐   ⭐ Changes are effective-dated (Day 289): "effective from
⭐     1 July" is scheduled, not remembered by a human on
⭐     1 July at 09:00.
⭐   ⭐⭐ AND AN EMERGENCY PATH THAT IS THE SAME PATH WITH A
⭐     FLAG (Day 283) — logged, reviewed after the fact, and
⭐     ⭐ reported weekly, or "emergency" becomes the normal
⭐     route within a month.
```

# Part 7 — ⭐⭐ When rules stop being the right tool

```
⭐⭐ THE HONEST BOUNDARY, IN THREE SIGNALS:
⭐   ① ⭐ THE RULE SET EXCEEDS ~200 AND INTERACTS — nobody can
⭐     predict the effect of a change, and every backtest
⭐     surprises you. ⭐⭐ THAT IS THE SYSTEM TELLING YOU IT
⭐     HAS OUTGROWN THE REPRESENTATION.
⭐   ② ⭐ THE SIGNAL IS GENUINELY STATISTICAL — "which of these
⭐     is likely fraudulent" has no expressible rule, only a
⭐     pattern.
⭐   ③ ⭐ THE OVERRIDE RATE STAYS HIGH AFTER SEVERAL ROUNDS OF
⭐     RULE CHANGES ⇒ the policy is not rule-shaped.

⭐⭐ AND THE COUNTER-ARGUMENT, WHICH IS USUALLY DECISIVE:
⭐   ***A MODEL YOU CANNOT EXPLAIN IS UNUSABLE FOR A DECISION
⭐      THAT MUST BE JUSTIFIED*** — and in several jurisdictions
⭐   an adverse decision legally requires a specific reason.
⭐   ⇒ ⭐⭐ SO THE USUAL ANSWER IS NOT "REPLACE THE RULES" BUT
⭐     ***RULES PLUS A MODEL AS ONE INPUT***: the model scores,
⭐     a rule turns the score into an outcome, and the trace
⭐     says "declined because risk_score 0.87 ≥ 0.80", which is
⭐     ⭐ explicable, testable, versionable and backtestable —
⭐     ⭐⭐ EVERY PROPERTY OF THE LAST TWO DAYS, PRESERVED.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Shipping a rule change on an opinion | It's an evidence question. Backtest it. |
| Only checking the direction you intended | The surprise is always the flips the other way. |
| Replaying at today's date | You measured the wrong change, and the number is garbage. |
| Random sampling with imbalanced classes | A 1,000-case sample contains four declines and can't show impact. |
| Believing a backtest predicts the future | It can't see induced demand or survivorship. |
| Not reading the changed cases | Twenty cases read by a human beat the aggregate, every time. |
| Treating a rule change as "just data" | It changes production behaviour and must get the same gates as code. |
| Skipping shadow mode | It's the only step that sees today's input distribution. |
| Retroactively re-deciding after a rollback | Someone has already been told the answer. Re-deciding is a separate, communicated act. |
| Alerting on individual decisions | Alert on the distribution shifting. |
| Not watching reason-code distribution | One code jumping means an upstream field changed shape, and nothing else will notice. |
| Ignoring the refer rate | It's the metric people game; "safe" moves the whole problem onto a person. |
| Free-text-only override reasons | Unanalysable. A fixed list plus free text. |
| Celebrating a near-zero override rate | It usually means the humans stopped looking. |
| Not measuring review time | A four-second median review is a rubber stamp. |
| The same person authoring and approving | Four eyes, enforced in the app, not in a document. |
| Not storing the backtest with the change | The evidence and the decision must live together. |
| An emergency path outside the normal one | It becomes the normal route within a month. |
| Reaching for a model too early | Explicability is usually the binding constraint, not accuracy. |

## Interview questions

**Q: Someone wants to change a threshold. What do you do?**

> Backtest it before it ships. I replay the last several thousand stored decisions against the
> candidate rule set — at their original `as_of` dates, or I've measured the wrong change — and
> produce a confusion table of what would have flipped and in which direction. The cell people forget
> is the unintended direction: a relaxation that turns some approvals into declines is always an
> interaction with another rule, and it's never anticipated. Then I sample twenty changed cases and
> actually read them, because that tells me more than the aggregate every time. And I'd state the
> limits out loud: a backtest can't see induced demand or survivorship, so it measures what would have
> happened, not what will.

**Q: How do you ship it?**

> Like a deploy, because it is one — it changes production behaviour, it can be wrong, and it has to
> be reversible, even though it's a database row and nothing forces any of that. Static checks, case
> and property tests, backtest, then shadow mode for a week where both rule sets evaluate live traffic
> and only the old one serves. Shadow is the only step that sees today's input distribution rather
> than last year's, and it's nearly free. Then a canary by segment watching the reason-code
> distribution, then full, with the previous version one row away. Rollback is instant — but I don't
> retroactively re-decide, because someone has already been told the answer.

**Q: What's the most valuable metric in a decision system?**

> The override rate, because it's the only labelled feedback the system produces for free — a human
> disagreeing in public with a recorded reason. Grouped by reason, the override queue is a
> frequency-ranked backlog of what the rules get wrong. And both extremes are bad: high means the
> rules don't encode the real policy and the humans are the system; near zero usually means the
> humans stopped looking, because automation complacency is real and a reviewer who agrees four
> hundred times stops reading around case forty. Which is why I measure review *time* as well — a
> four-second median is a rubber stamp, and you have a control that exists only on the org chart.

**Q: When would you replace the rules with a model?**

> When the rule set is large and interacting enough that nobody can predict the effect of a change,
> when the signal is genuinely statistical rather than expressible, or when the override rate stays
> high after several rounds of rule changes — that last one means the policy isn't rule-shaped. But
> usually the answer isn't replacement, because a model you can't explain is unusable for a decision
> that must be justified, and in several jurisdictions an adverse decision legally requires a specific
> reason. So it's rules plus a model as one input: the model scores, a rule converts the score into an
> outcome, and the trace says "declined because risk score 0.87 is at or above 0.80" — which keeps
> every property I built for.

## 🎙️ Articulation drill

**Three minutes: "How do you change a rule safely?"**

Start by refusing the framing: **"it's a one-line change" is true and irrelevant** — it's an evidence
question. The good answer is a number: of the last twelve thousand decisions, this many flip, in this
direction, and **none the other way — which is the cell people forget to check, and where the
surprises are**, because a relaxation that tightens something is always an unanticipated interaction.
Note that you can only answer this because decisions stored their inputs. Then the honesty about the
tool: replay at original dates or you measured a different change, stratify or a thousand-case sample
contains four declines and proves nothing, and **a backtest measures what would have happened, not
what will** — it can't see induced demand or survivorship. Then the ladder: static checks, case and
property tests, backtest, **shadow mode, which is the only step that sees today's input distribution**,
canary by segment, full — with the previous version one row away, and no retroactive re-deciding,
because someone has already been told the answer. Close on operations: alert on the distribution
shifting rather than on decisions, watch reason codes because **one code going from 2% to 30% means an
upstream field changed shape and nothing else in the system will notice**, and treat the override rate
as the most valuable number you own — **high means the rules aren't the policy, near zero usually means
the humans stopped looking**, which is why you measure review time as well.
