# Part 1 — ⭐⭐ A server is a program in a loop

## The whole thing, in six calls

```
⭐⭐ EVERY server on earth — nginx, Postgres, Uvicorn, Redis — does exactly this:

   1. socket()    ⭐ create an endpoint
   2. bind()      ⭐ claim an (address, port) — ⭐⭐ this is where "address already in use" happens
   3. listen()    ⭐ tell the kernel to start queueing incoming connections
   4. accept()    ⭐⭐ BLOCK until a client connects; return a NEW socket for that client
   5. recv/send   ⭐ talk on that new socket
   6. close()     ⭐ and loop back to 4
```

⭐⭐ **Step 4 is the one that matters.** `accept()` returns a *different* socket from the listening
one. The listening socket never carries data — its only job is to produce connection sockets. That is
the mechanical version of Day 003's four-tuple.

## ⭐ Write one. Now.

```python
# server.py — a web server. No framework. No library beyond the stdlib socket module.
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)   # ⭐ IPv4, TCP
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1) # ⭐ Day 008 explains this
server.bind(("0.0.0.0", 8000))                               # ⭐⭐ 0.0.0.0, not 127.0.0.1 (Day 003)
server.listen(5)                                             # ⭐ backlog of 5
print("listening on http://localhost:8000")

while True:                                   # ⭐⭐ THE LOOP. This is the server.
    conn, addr = server.accept()              # ⭐⭐ BLOCKS here until someone connects
    request = conn.recv(65536)                # ⭐ read the raw bytes
    print(f"--- from {addr} ---")
    print(request.decode(errors="replace"))

    body = b"<h1>Hello from a hand-written server</h1>"
    response = (
        b"HTTP/1.1 200 OK\r\n"
        b"Content-Type: text/html\r\n"
        b"Content-Length: " + str(len(body)).encode() + b"\r\n"
        b"Connection: close\r\n"
        b"\r\n" + body
    )
    conn.sendall(response)
    conn.close()
```

Run it, then open `http://localhost:8000` in a browser.

⭐⭐ **Look at what just printed in your terminal.** That is a real HTTP request, in text, that a
browser sent you. You did not use a web framework. **HTTP is a text protocol over TCP, and you just
proved it.**

```
GET / HTTP/1.1
Host: localhost:8000
User-Agent: Mozilla/5.0 ...
Accept: text/html,...
```

| ⭐ What you should notice | |
|---|---|
| ⭐⭐ **You wrote the status line yourself** | ⭐⭐ `200 OK` is not magic — it is bytes you chose |
| ⭐⭐ **`\r\n` not `\n`** | ⭐ HTTP requires CRLF. Get it wrong and browsers reject the response |
| ⭐⭐ **The blank line before the body** | ⭐⭐ that is what separates headers from body — **the whole protocol hinges on it** |
| ⭐ `Content-Length` | ⭐ without it the client does not know when you have finished (Day 010) |
| ⭐ Your browser sent a favicon request too | you will see two requests, not one |

> (WebSockets), Day 022 (the capstone) and again in Stage 3 when you build a micro-framework on top
> of it.

# Part 2 — ⭐⭐ The problem this server has

```python
# Add this line inside the loop, right after accept():
import time
time.sleep(5)          # ⭐ simulate a slow database query
```

Now open two browser tabs at once.

⭐⭐ **The second tab waits five seconds for the first.** One client at a time. This server can serve
exactly one person, and everyone else queues. **This single observation motivates the next 400 days.**

## ⭐⭐ The four ways out — the entire history of server architecture

| Approach | How | ⭐ Cost | Who uses it |
|---|---|---|---|
| ⭐ **Process per connection** | `fork()` on accept | ⭐⭐ ~MBs and ~ms each — dies at a few hundred | old Apache (prefork) |
| ⭐ **Thread per connection** | a thread per client | ⭐⭐ ~8 MB stack each; **in Python, the GIL limits CPU work** | Java servers, Gunicorn sync workers |
| ⭐ **Thread pool** | N threads, a queue of connections | ⭐ bounded, but a slow handler blocks a thread | most classic web servers |
| ⭐⭐ **Event loop** | ⭐⭐ **ONE thread, `epoll` over thousands of sockets** | ⭐⭐ **cheapest by far for I/O-bound work** | ⭐⭐ **nginx, Node, asyncio/Uvicorn** |

```
⭐⭐ THE EVENT LOOP IDEA, in one line:
   instead of one worker WAITING on each socket,
   ⭐⭐ ONE worker asks the kernel "which of these 10,000 sockets is ready?" and handles those.
⭐ ⇒ ⭐⭐ waiting costs nothing, because nobody is waiting — the kernel is.
```

⭐ **This is why Python's asyncio exists**, why FastAPI is async, and why a single Uvicorn worker can
hold thousands of idle WebSocket connections. **Day 070 builds it properly; today you only need to
know that the problem you just created is the reason it exists.**

⚠️ **And the trap you will meet in Stage 4, stated now so it lands twice:** an event loop is one
thread, so **a blocking call inside an `async def` stalls every other connection.** Your `time.sleep(5)`
above is exactly that bug, in miniature. Day 072.

## ⭐ Why real deployments use processes *and* an event loop

```
⭐⭐ Uvicorn with 4 workers on a 4-core machine:
   ⭐ 4 PROCESSES  ⇒ true parallelism across cores, ⭐⭐ side-stepping the GIL (Day 065)
   ⭐ each running ONE EVENT LOOP ⇒ thousands of concurrent connections per process
   ⇒ ⭐⭐ processes for CPU parallelism, an event loop for I/O concurrency.
   ⇒ ⭐ they solve DIFFERENT problems, which is why you use both.
```

**⭐ That box is a complete answer to "how would you scale a Python API?"** and it is worth being able
to say on demand.

# Part 3 — ⭐ Client and server are roles, not machines

| | |
|---|---|
| ⭐ **Client** | the side that **initiates** the connection |
| ⭐ **Server** | the side that **waits** for connections |
| ⭐⭐ **The same program is often both** | ⭐⭐ your API is a server to the browser and a client to Postgres |

# Part 4 — C-03 · The network layer

## IP addresses and CIDR

```
⭐ IPv4: 32 bits, written as four bytes    192.168.1.10
⭐ IPv6: 128 bits, hex, colon-separated    2001:db8::1

⭐⭐ CIDR — the notation you must read fluently:
   192.168.1.0/24   ⇒ ⭐ first 24 bits are the NETWORK, last 8 are the HOST
                    ⇒ ⭐ 2^8 = 256 addresses, ⭐⭐ 254 usable (network + broadcast reserved)
   10.0.0.0/16      ⇒ 65,536 addresses
   10.0.0.0/8       ⇒ 16.7 million
⭐ ⇒ ⭐⭐ SMALLER number after the slash = BIGGER network. This is backwards from intuition.
```

| ⭐ Private ranges — memorise these | |
|---|---|
| `10.0.0.0/8` | ⭐⭐ big — **what you will use in AWS VPCs** (Stage 11) |
| `172.16.0.0/12` | ⭐ Docker's default lives here |
| `192.168.0.0/16` | ⭐ your home router |
| `127.0.0.0/8` | ⭐⭐ loopback — never leaves the machine |

⚠️ ⭐⭐ **A CIDR plan is a decision you cannot undo cheaply.** Using `10.0.0.0/16` in every environment
means those networks can never be connected to each other, and the fix is rebuilding. You will meet
this exact problem again in Stage 11 — **it is worth knowing on Day 4 that the notation carries a
design decision.**

## ⭐ Routing — how a packet finds its way

```
⭐ Every machine has a ROUTING TABLE. For each packet it asks:
   "Is the destination on a network I am directly attached to?"
      ⭐ yes ⇒ send it directly (ARP for the MAC — Day 002)
      ⭐ no  ⇒ ⭐⭐ send it to the DEFAULT GATEWAY and let it be someone else's problem
⭐ ⇒ ⭐⭐ Routers repeat this, hop by hop. ⭐ LONGEST PREFIX MATCH wins: /32 beats /24 beats 0.0.0.0/0.
```

```bash
ip route            # or `route -n` / `netstat -rn` — read your own routing table
traceroute google.com    # watch the hops, and their latencies
```

⭐ **Run `traceroute` and look at where the latency jumps.** That jump is usually the moment your
packet leaves your ISP or crosses an ocean, and it is the physical floor from Day 002 made visible.

## ⭐⭐ NAT — why your laptop has no public address

```
⭐ You have 192.168.1.10. That address is meaningless on the internet — millions of people have it.
⭐⭐ NAT (in your router) rewrites the SOURCE of outgoing packets:
   out:  (192.168.1.10 : 51234) ──▶ ⭐⭐ rewritten to (203.0.113.7 : 61001)
   ⭐ the router remembers the mapping in a table
   in:   (203.0.113.7 : 61001) ──▶ ⭐ rewritten back to (192.168.1.10 : 51234)
```

| ⭐ Consequences that matter | |
|---|---|
| ⭐⭐ **Outbound works, inbound does not** | ⭐⭐ nothing on the internet can start a connection to you — **this is why port forwarding exists** |
| ⭐ It is why IPv4 survived | address exhaustion was postponed by two decades |
| ⭐⭐ **NAT tables have entries with timeouts** | ⭐⭐ an idle connection can be silently dropped — the reason for TCP keepalives |
| ⭐ Peer-to-peer is hard | STUN/TURN exist entirely to work around NAT |

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"A server is a special computer"** | ⭐⭐ It is a *program* in a loop calling `accept()`. Your laptop is a server the moment you run one. |
| Thinking `accept()` returns the listening socket | ⭐ It returns a **new** socket per connection. |
| Using `\n` instead of `\r\n` in HTTP | The protocol requires CRLF; browsers will reject it. |
| Forgetting the blank line before the body | The client will hang waiting for more headers. |
| ⭐ Omitting `Content-Length` | The client cannot tell when the response ends. |
| ⭐⭐ **Assuming one server = one client at a time** | ⭐ True of your first loop — and the reason threads, pools and event loops exist. |
| Confusing an event loop with parallelism | ⭐⭐ It is concurrency on **one** thread. Parallelism needs processes. |
| Reading `/24` as bigger than `/16` | ⭐ Smaller suffix = bigger network. |
| Thinking NAT is a firewall | It blocks inbound as a side effect, not as a security design. |

## Interview questions

**Q: What is a server?**
> A program that has created a socket, bound it to an address and port, told the kernel to listen, and
> is now sitting in a loop calling `accept()`. Each accept returns a new socket representing one
> client connection, which is why a single listening port can serve thousands of clients — they are
> distinguished by the four-tuple. There is nothing special about the hardware; "server" is a role a
> process is playing.

**Q: Your simple server handles one client at a time. How do you fix that?**
> Four historical answers. A process per connection, which is isolated but costs megabytes and
> milliseconds each. A thread per connection, cheaper but still around eight megabytes of stack each,
> and in Python limited by the GIL for CPU work. A bounded thread pool, which caps the damage but
> still blocks a thread per slow request. Or an event loop — one thread asking the kernel which of
> thousands of sockets are ready, which is what nginx, Node and asyncio do and is by far the cheapest
> for I/O-bound work. In production Python you usually combine two: several worker processes for CPU
> parallelism, each running an event loop for I/O concurrency.

**Q: Why does a Python web server run multiple processes rather than just more threads?**
> Because of the GIL. Threads in CPython cannot execute Python bytecode in parallel, so adding threads
> does not add CPU throughput — it only helps while threads are blocked on I/O and have released the
> lock. Processes have separate interpreters and therefore separate GILs, so they genuinely use
> multiple cores. That is why the standard deployment is N worker processes, usually around the core
> count, each handling many connections concurrently via its event loop.

**Q: What does CIDR notation mean, and what is `/24`?**
> The number after the slash is how many leading bits identify the network, with the rest identifying
> hosts. A `/24` fixes 24 bits, leaving 8 for hosts — 256 addresses, 254 usable after the network and
> broadcast addresses. The counter-intuitive part is that a smaller number means a bigger network, so
> a `/8` is far larger than a `/24`.

**Q: What is NAT and what does it break?**
> The router rewrites the source address and port of outgoing packets to its own public address, keeps
> a mapping table, and reverses the translation on the way back. It let IPv4 survive address
> exhaustion, but it means nothing on the internet can initiate a connection to you — hence port
> forwarding — and mapping entries expire, so idle connections get silently dropped unless keepalives
> hold them open.
