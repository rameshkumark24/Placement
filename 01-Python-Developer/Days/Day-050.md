# Day 050

**L-050** · Comprehensions and generator expressions — and when a loop is clearer

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a comprehension is for *building a collection from another one*. If
> you are not building a collection, you want a loop — and if you cannot read it in one pass, you
> want a loop too.**
>
> ⭐ Comprehensions are the most recognisably Pythonic construct and the easiest to overuse. Today
> is as much about the boundary as the syntax.

---

# Part 1 — ⭐ The four forms

```python
[x*2 for x in xs]                       # ⭐ list
{x for x in xs}                         # ⭐ set
{k: v for k, v in pairs}                # ⭐ dict
(x*2 for x in xs)                       # ⭐⭐ GENERATOR EXPRESSION — lazy, not a "tuple comprehension"
tuple(x*2 for x in xs)                  # ⭐ that is how you get a tuple
```

```
⭐⭐ THE SHAPE:  [ EXPRESSION  for TARGET in ITERABLE  if CONDITION ]
⭐   · the `if` at the END filters — items failing it are not produced at all
⭐   · a TERNARY goes in the EXPRESSION — it transforms, it does not filter:
⭐        [x if x > 0 else 0 for x in xs]      ⭐ transform every element
⭐        [x for x in xs if x > 0]             ⭐ keep some elements
⭐   ⇒ ⭐⭐ "if before the for" means TERNARY. "if after the for" means FILTER.
⭐        Getting these confused is the single most common comprehension error.
```

```python
# ⭐ Nested loops read LEFT TO RIGHT, exactly like the equivalent nested for statements:
[(x, y) for x in range(3) for y in range(3)]        # ⭐ outer first, then inner
[[cell for cell in row] for row in grid]            # ⭐⭐ nested COMPREHENSION — inner is an expression

# ⭐⭐ THE MATRIX FIX from Day 024 — and now you can see why it works:
grid = [[0] * cols for _ in range(rows)]            # ⭐ the inner expression runs ONCE PER ROW
grid = [[0] * cols] * rows                          # ⚠️ ⭐⭐ one row object, `rows` references
```

⭐ **Comprehensions have their own scope** (Day 030): the loop variable does not leak, and — the
obscure consequence — **a comprehension inside a class body cannot see the class's other names**,
because a class body is not a function scope.

# Part 2 — ⭐⭐ Generator expressions

```python
sum(x*x for x in range(10**7))          # ⭐⭐ constant memory — parens omitted as the sole argument
sum([x*x for x in range(10**7)])        # ⚠️ ⭐⭐ builds a 10-million-element list first
any(is_bad(r) for r in rows)            # ⭐ short-circuits (Day 046)
max((score(x) for x in items), default=0)   # ⚠️ ⭐ parens REQUIRED when there is a second argument
```

```
⭐⭐ THE ONE-CHARACTER DECISION:
⭐   [ ... ]  ⇒ builds the whole list NOW.     ⭐ Use when you need len, indexing, or MULTIPLE passes.
⭐   ( ... )  ⇒ produces items ON DEMAND.      ⭐⭐ Use when you consume ONCE, or the data is large.
⭐
⭐ ⇒ ⭐⭐ inside sum/any/all/min/max/join/set/dict, ALWAYS use the generator form.
⭐      Those functions consume exactly once, so the list is pure waste.
```

⚠️ ⭐⭐ **`"".join(...)`** is the exception people get backwards: `join` is *faster* with a list,
because it needs two passes (total the length, then copy — Day 037). ⭐ For a small number of items
it does not matter; **for a very large one, `join(list)` beats `join(genexp)`.**

⭐ **A generator expression is single-pass** (Day 046), so the exhaustion bug applies in full: assign
one to a name, consume it, and the second consumer silently gets nothing.

# Part 3 — ⭐ Why comprehensions are faster

```
⭐⭐ [x*2 for x in xs]  vs  the loop:
⭐     out = []
⭐     for x in xs: out.append(x*2)
⭐
⭐   THE LOOP does, per element: LOAD out ⇒ LOAD_METHOD append ⇒ CALL a Python-level method
⭐   ⭐⭐ THE COMPREHENSION uses the LIST_APPEND opcode — no name lookup, no method call.
⭐   ⇒ ⭐ roughly 20–40% faster for a simple body. ⭐⭐ Not a reason to use one; a bonus if you do.
```

⭐⭐ **The right reason to use a comprehension is that it *declares intent*:** "this is a new list,
derived from that one, with these items excluded". **A `for` loop declares nothing — the reader must
follow it to find out whether it builds, mutates, prints or returns early.**

```python
# ⚠️ ⭐⭐ THE ANTI-PATTERN: a comprehension used for side effects
[send_email(u) for u in users]          # ⭐⭐ builds a list of Nones and throws it away
for u in users: send_email(u)           # ⭐ say what you mean

# ⭐ dict/set comprehensions that earn their place:
{v: k for k, v in d.items()}            # ⭐ invert a mapping
{k: v for k, v in d.items() if v}       # ⭐ drop falsy values (⚠️ Day 029 — is that what you meant?)
{u.email.casefold() for u in users}     # ⭐ dedupe, normalised (Day 037)
{k: heavy(v) for k, v in d.items()}     # ⭐ transform values
```

# Part 4 — ⭐⭐ When a loop is clearer

```
⭐⭐ USE A LOOP WHEN:
⭐  1. ⭐⭐ THE PURPOSE IS A SIDE EFFECT — writing, sending, printing, mutating
⭐  2. ⭐ you need `break`, `continue`, `else`, or an early `return`
⭐  3. ⭐ you need try/except around each item
⭐  4. ⭐⭐ there are more than two `for` clauses, or a `for` and two `if`s
⭐  5. ⭐ the expression needs more than one line to read
⭐  6. ⭐⭐ you are building SEVERAL collections in one pass
```

```python
# ⚠️ ⭐⭐ TOO FAR — technically one expression, practically unreadable:
result = [transform(y) for x in data if x.valid for y in x.items if y.score > threshold]

# ⭐ The honest version:
result = []
for x in data:
    if not x.valid:
        continue
    for y in x.items:
        if y.score > threshold:
            result.append(transform(y))
```

⭐⭐ **The rule I would defend in a review: one `for` and one `if` is always fine; two `for`s is the
limit; anything more is a loop.** **Nesting depth is a proxy for how many things the reader must hold
at once, and a comprehension gives them no place to rest.**

```python
# ⭐ Building several collections — a loop wins outright:
valid, invalid = [], []
for r in rows:
    (valid if r.ok else invalid).append(r)
# ⭐⭐ two comprehensions would iterate `rows` TWICE, and `rows` may be a generator (Day 046).
```

⭐ **The walrus in a comprehension** (Day 040) has one genuinely good use: **avoiding a double
computation.**

```python
[y for x in data if (y := expensive(x)) is not None]     # ⭐⭐ expensive() runs ONCE per item
[expensive(x) for x in data if expensive(x) is not None]  # ⚠️ ⭐⭐ runs TWICE per item
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Comprehension for side effects** | ⭐⭐ Builds a list of `None`s. Write a loop. |
| ⭐ Confusing filter-`if` and ternary-`if` | ⭐⭐ After the `for` filters; before it transforms. |
| `sum([...])` instead of `sum(...)` | ⭐⭐ Materialises the whole list first. |
| `join(genexp)` on huge input | ⭐ `join` wants a list — it makes two passes. |
| Three or more clauses | ⭐ Unreadable. A loop. |
| Reusing a generator expression | ⭐⭐ Single pass (Day 046). |
| `[[0]*n]*m` | ⭐⭐ Day 024 — the comprehension is the fix. |
| Two comprehensions over one generator | ⭐ The second sees nothing. One loop. |
| Calling an expensive function twice | ⭐ Walrus, once. |
| Assuming the loop variable leaks | ⭐ Own scope in Python 3. |
| Comprehension over class attributes in a class body | ⭐⭐ Class scope is invisible inside it (Day 030). |

## Interview questions

**Q: When do you use a comprehension and when a loop?**
> A comprehension when I'm building a collection from another one — that's what it declares, and the
> reader knows the result before reading the body. A loop when the point is a side effect, when I
> need `break`, `continue` or an early return, when each item needs its own `try`, or when there's
> more than about two clauses. The line I'd defend is: one `for` and one `if` is always fine, two
> `for`s is the limit, past that it's a loop. And a comprehension whose result is discarded is always
> wrong — that's a loop written to look clever.

**Q: List comprehension or generator expression?**
> Square brackets when I need `len`, indexing, or more than one pass; parentheses when I consume once
> or the data is large. Inside `sum`, `any`, `all`, `min`, `max` and `set`, always the generator form,
> because those consume exactly once so the list is pure waste — and `any` and `all` short-circuit,
> so with brackets you evaluate everything before the function even starts. The one exception is
> `str.join`, which is faster with a list because it makes two passes over the input.

**Q: Are comprehensions faster than loops?**
> Somewhat — roughly 20 to 40% for a simple body, because the comprehension uses a dedicated
> `LIST_APPEND` opcode instead of looking up and calling the `append` method each iteration. But
> that's a bonus rather than a reason. The reason is that it declares intent: a comprehension tells
> the reader "new collection, derived, filtered" before they read the body, and a loop tells them
> nothing until they've followed it to the end.

**Q: What's the difference between `if` before and after the `for`?**
> After the `for` it's a filter — items failing it aren't produced. Before it, it's part of the
> expression, so it must be a ternary with an `else`, and it transforms every element rather than
> excluding any. `[x for x in xs if x > 0]` keeps some; `[x if x > 0 else 0 for x in xs]` keeps all
> and rewrites some. Mixing them up is probably the most common comprehension error, and the syntax
> error you get when you forget the `else` is at least a loud one.

**Q: You need to split rows into valid and invalid. Two comprehensions?**
> No — one loop. Two comprehensions iterate the source twice, which is wasted work on a list and
> silently broken on a generator, since the second pass sees an exhausted iterator. Whenever a single
> pass has to produce more than one output, a loop is the right shape, and trying to force it into
> comprehensions is where the exhaustion bugs come from.

## 🎙️ Articulation drill

Record two minutes: **"When would you tell someone in code review to replace a comprehension with a
loop?"**

⭐ Give the principle first: **a comprehension declares that a new collection is being built from an
existing one. If that is not what the code is doing, the form is lying about its purpose.** ⭐ Then
the concrete triggers: the result is discarded, so it is really a loop with a wasted list of `None`s;
it needs `break`, `continue` or a per-item `try`; or it has grown past two `for` clauses and the
reader has nowhere to rest.

⭐⭐ **Then the case that is a correctness argument rather than a readability one:** *"the one I would
insist on is building two collections from one source. Two comprehensions iterate it twice — wasted
work on a list, and silently wrong on a generator, because the second pass sees an exhausted
iterator and produces an empty result with no error. That is not a style preference; it is a bug that
only appears when someone upstream makes the source lazy."*

⭐ Close by conceding the other direction: **a well-chosen comprehension is strictly better than the
loop it replaces**, because the reader knows the shape of the result before reading the body — the
goal is not fewer comprehensions, it is honest ones.
