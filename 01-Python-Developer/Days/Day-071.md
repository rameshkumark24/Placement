# Part 1 — ⭐⭐ Tasks and the reference trap

```python
task = asyncio.create_task(fetch(url))     # ⭐⭐ SCHEDULES it — it starts at the next await
result = await task                        # ⭐ later, collect it
task.cancel(); task.done(); task.result()
```

```python
# ⚠️⚠️ ⭐⭐ THE FIRE-AND-FORGET BUG, and it is in the official documentation:
asyncio.create_task(background_work())     # ⭐⭐ the loop keeps only a WEAK reference
# ⇒ ⭐⭐ if nothing else holds it, the GC can collect the task MID-EXECUTION.
#    ⇒ the work stops. No error. No log. Non-deterministically, under memory pressure.

# ⭐⭐ THE FIX — hold a strong reference until it completes:
_background: set[asyncio.Task] = set()
def spawn(coro):
    t = asyncio.create_task(coro)
    _background.add(t)                     # ⭐ strong reference
    t.add_done_callback(_background.discard)   # ⭐⭐ and release it when finished
```

⭐⭐ **This is Day 069's fire-and-forget problem with an extra failure mode:** with an executor the
*exception* vanished; here **the whole task can vanish.** ⭐ And the same rule applies — **an
un-awaited task's exception is only reported when the task is garbage-collected**, as
*"Task exception was never retrieved"*, long after the fact and detached from any request.

```
⭐⭐ THE THREE WAYS TO RUN THINGS CONCURRENTLY, IN ORDER OF PREFERENCE:
⭐   1. ⭐⭐ TaskGroup  — structured; failures cancel siblings; nothing outlives the block
⭐   2. ⭐ gather      — flat, simple, returns results in order
⭐   3. ⭐ create_task — when the lifetime genuinely exceeds this function ⇒ ⭐⭐ hold the reference
```

# Part 2 — ⭐⭐ `gather` and `TaskGroup`

```python
results = await asyncio.gather(a(), b(), c())                    # ⭐ ordered results
results = await asyncio.gather(*coros, return_exceptions=True)   # ⭐⭐ exceptions AS VALUES
```

```
⭐⭐ gather's DEFAULT FAILURE SEMANTICS ARE THE TRAP:
⭐   the FIRST exception propagates immediately —
⭐   ⇒ ⚠️ ⭐⭐ but the OTHER tasks KEEP RUNNING, unawaited and unsupervised.
⭐   ⇒ so you get one error, some work still in flight, and possibly
⭐        "Task exception was never retrieved" minutes later.
⭐
⭐ ⭐ return_exceptions=True ⇒ everything completes, and exceptions come back as RESULTS
⭐        ⇒ ⭐⭐ which means you MUST check each one — `isinstance(r, Exception)` — or
⭐          you have silently converted failures into data.
```

```python
# ⭐⭐ TaskGroup (3.11+) — STRUCTURED CONCURRENCY. Prefer this.
async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(a())
    t2 = tg.create_task(b())
# ⭐⭐ on exit: ALL tasks are complete. Guaranteed.
# ⭐⭐ if any raises: the others are CANCELLED, and an ExceptionGroup is raised (Day 059)
```

```
⭐⭐ WHY TaskGroup IS BETTER — three properties `gather` cannot give you:
⭐   1. ⭐⭐ NOTHING OUTLIVES THE BLOCK. No orphaned tasks, ever. The `async with` is a
⭐        lifetime boundary, exactly like a `with` for a file (Day 052).
⭐   2. ⭐ FAILURE CANCELS SIBLINGS — you do not keep doing work for a request that has
⭐        already failed.
⭐   3. ⭐⭐ ALL failures are reported, as an ExceptionGroup, handled with `except*`.
⭐        ⇒ ⭐ with one call stack one exception sufficed; with five parallel tasks
⭐          reporting only the first loses the rest. That is why Day 059's groups exist.
```

⭐⭐ **"Structured concurrency" means concurrency has the same lifetime discipline as a block scope**
— you cannot leave a task running past the `async with`, the same way you cannot leave a file open
past a `with`. **It removes a whole class of leak by construction.**

# Part 3 — ⭐⭐ Timeouts and cancellation

```python
async with asyncio.timeout(5):          # ⭐⭐ 3.11+ — preferred
    await slow_operation()              # ⇒ TimeoutError, and the operation is CANCELLED

result = await asyncio.wait_for(slow(), timeout=5)   # ⭐ the older form, same semantics
```

```
⭐⭐ HOW CANCELLATION ACTUALLY WORKS — this is the part to understand, not memorise:
⭐   task.cancel() ⇒ ⭐⭐ CancelledError is THROWN INTO the coroutine at its current await
⭐        ⇒ ⭐ exactly Day 048's gen.throw(). The exception appears AT the suspension point.
⭐   ⇒ ⭐⭐ so cancellation is COOPERATIVE: a coroutine that never awaits cannot be cancelled,
⭐        and a coroutine that catches CancelledError can refuse.
⭐   ⇒ ⭐⭐ CancelledError inherits from BaseException (3.8+), NOT Exception —
⭐        ⇒ ⭐⭐ deliberately, so `except Exception` does NOT swallow a cancellation.
```

```python
# ⭐⭐ CLEANING UP UNDER CANCELLATION — the correct shape:
async def worker():
    try:
        while True:
            await do_work()
    except asyncio.CancelledError:
        await flush()               # ⭐ cleanup that may itself await
        raise                       # ⭐⭐ ALWAYS RE-RAISE. Swallowing it breaks shutdown.
    finally:
        release()                   # ⭐ runs either way (Day 052)
```

⚠️ ⭐⭐ **Swallowing `CancelledError` is the async equivalent of ignoring `SIGTERM`.** The task
continues, `TaskGroup` and `wait_for` wait for it, and your graceful shutdown hangs until the
orchestrator SIGKILLs the process — **which is Day 066's un-stoppable thread, in a new form.**

```python
shielded = await asyncio.shield(critical())   # ⭐ protect from OUTER cancellation
```

⭐ **`shield` is for the operation that must complete even if the caller gave up** — a payment
capture, a final write. ⚠️ **Use it rarely: it breaks the timeout guarantee you just asked for.**

⚠️ ⭐⭐ **A timeout does not stop work that is not awaiting.** `asyncio.timeout(5)` around a
CPU-bound loop does nothing at all — **the cancellation cannot be delivered because there is no
suspension point to deliver it to.** That is Day 072, arriving early.

# Part 4 — ⭐⭐ Bounding, and the primitives

```python
# ⚠️⚠️ ⭐⭐ THE MISTAKE THAT TAKES DOWN THE OTHER SERVICE:
await asyncio.gather(*(fetch(u) for u in ten_thousand_urls))
# ⭐⭐ TEN THOUSAND SIMULTANEOUS CONNECTIONS. You will exhaust your file descriptors,
#    saturate your NIC, and DoS the target — which will rate-limit or ban you.

# ⭐⭐ THE FIX — a semaphore, and it should be your default:
sem = asyncio.Semaphore(20)
async def bounded(u):
    async with sem:                      # ⭐ at most 20 in flight
        return await fetch(u)
await asyncio.gather(*(bounded(u) for u in urls))
```

⭐⭐ **`asyncio` removes the natural limit that threads gave you.** ⭐ With a thread pool,
`max_workers` bounded you whether you thought about it or not; **with `gather` there is no bound
unless you write one.** **Every fan-out gets a semaphore.**

| ⭐ Primitive | ⭐ For |
|---|---|
| ⭐⭐ `Semaphore(n)` | ⭐⭐ **bounding fan-out** — the one you will always need |
| `Lock` | an invariant across an `await` (Day 070) |
| `Event` | signalling, shutdown |
| ⭐ `Queue(maxsize=n)` | ⭐ producer/consumer with backpressure (Day 066's shape, async) |
| `Condition`, `Barrier` | as in threading |

```python
# ⭐ Waiting for whichever finishes first, and the rest of the toolkit:
done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
for t in pending: t.cancel()             # ⭐⭐ ALWAYS cancel the losers, or they leak

async for result in asyncio.as_completed(tasks): ...   # ⭐ results as they land
await asyncio.sleep(0)                   # ⭐⭐ yield to the loop without waiting —
                                         #    a manual cooperation point in a long loop
```

```python
# ⭐ Graceful shutdown — the shape a real service needs:
async def main():
    stop = asyncio.Event()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(sig, stop.set)          # ⭐ POSIX only
    async with asyncio.TaskGroup() as tg:
        tg.create_task(server(stop))                    # ⭐⭐ TaskGroup guarantees the join
    await cleanup()
```

⭐ **`asyncio.sleep(0)` is the cooperative yield** — inside a long CPU loop it lets the loop breathe.
⚠️ **It is a mitigation, not a fix; Day 072 gives the real one.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`create_task` without keeping a reference** | ⭐⭐ The task can be GC'd mid-execution. |
| Not retrieving a task's exception | ⭐ Reported late, detached, or never. |
| ⭐⭐ **`gather` on an unbounded fan-out** | ⭐⭐ Ten thousand connections. Use a `Semaphore`. |
| Relying on `gather`'s failure semantics | ⭐ Siblings keep running unsupervised. |
| `return_exceptions=True` without checking | ⭐⭐ Failures silently became data. |
| ⭐⭐ **Swallowing `CancelledError`** | ⭐⭐ Shutdown hangs until SIGKILL. Always re-raise. |
| `except Exception` expecting to catch cancellation | ⭐ It is a `BaseException` — deliberately. |
| Expecting a timeout to stop CPU work | ⭐⭐ No suspension point, no delivery (Day 072). |
| `shield` by default | ⭐ It defeats the timeout you asked for. |
| Not cancelling `pending` after `FIRST_COMPLETED` | ⭐ They leak. |
| `gather` where a `TaskGroup` fits | ⭐ No lifetime guarantee, no sibling cancellation. |

## Interview questions

**Q: What's wrong with `asyncio.create_task(work())` on its own?**
> The loop keeps only a weak reference, so if nothing else holds the task it can be garbage-collected
> while it's still running — the work stops, silently and non-deterministically, typically under
> memory pressure. It's documented behaviour, not folklore. The fix is to hold it in a module-level
> set and discard it in a done-callback. And separately, an un-awaited task's exception is only
> surfaced when the task is collected, as "Task exception was never retrieved", long after the fact
> and detached from whatever request caused it.

**Q: `gather` or `TaskGroup`?**
> `TaskGroup`, when I'm on 3.11 or later. It's structured concurrency: nothing outlives the `async
> with` block, so orphaned tasks are impossible by construction; a failure cancels the siblings, so I
> don't keep doing work for a request that has already failed; and all failures are reported as an
> `ExceptionGroup` rather than just the first. `gather`'s defaults are the trap — the first exception
> propagates while the others keep running unsupervised, so you can get an error plus work still in
> flight plus a stray "exception was never retrieved" minutes later.

**Q: How does cancellation work?**
> `task.cancel()` throws `CancelledError` into the coroutine at its current `await` — mechanically the
> same as `gen.throw` from Day 048, so the exception appears at the suspension point. That makes it
> cooperative: a coroutine with no `await` can't be cancelled at all, and one that catches the error
> can refuse. `CancelledError` inherits from `BaseException` rather than `Exception`, deliberately, so
> a broad `except Exception` doesn't swallow it. If I catch it for cleanup I always re-raise —
> swallowing it is the async equivalent of ignoring SIGTERM: the task continues, the `TaskGroup`
> waits, and graceful shutdown hangs until something SIGKILLs the process.

**Q: You need to fetch ten thousand URLs. What do you write?**
> Not a bare `gather` over ten thousand coroutines — that opens ten thousand simultaneous
> connections, exhausts file descriptors, saturates the NIC and will get me rate-limited or banned by
> the target. A `Semaphore` around each fetch, bounding it to something like twenty or fifty, then
> gather the bounded versions. The general point is that asyncio removes the natural limit threads
> gave you: a thread pool's `max_workers` bounded you whether you thought about it or not, and with
> `gather` there's no bound unless you write one. Every fan-out gets a semaphore.

**Q: Does `asyncio.timeout(5)` guarantee the operation stops after five seconds?**
> Only if the operation reaches an `await`. The timeout works by cancelling the task, and cancellation
> is delivered at a suspension point — so a CPU-bound loop inside the block ignores it completely,
> because there's nowhere to deliver the exception. That's the same underlying fact as the blocking
> call problem: no yield point means no cooperation, and the loop can't do anything about code that
> never gives it control.

**Q: What's structured concurrency?**
> Giving concurrency the same lifetime discipline as a block scope. A `TaskGroup` guarantees every
> task it started has finished when the `async with` exits, exactly as a `with` guarantees the file is
> closed — so you can't leak a running task past the function that spawned it. It also means failure
> propagates properly: one task failing cancels the rest and the group reports all the errors, rather
> than leaving orphans running with nobody watching.
