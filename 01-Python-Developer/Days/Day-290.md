# Day 290 ⚙️

**P-290** · ⚙️ **The rules engine I** — ⭐⭐ rules as data, and the trace that *is* the product

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: the verdict is not the output. The trace is — because a decision nobody
> can explain cannot be appealed, audited, corrected or trusted, and in a surprising number of
> domains it cannot legally be made at all.**
>
> ⭐ Day 254 built a state machine as data and got testability for free. ⭐⭐ Today the same move
> applies to logic, and it buys three things `if` statements cannot give you at any price.

---

# Part 1 — ⭐⭐ Why not just write `if` statements

```
⭐   if applicant.tenure_months < 3 and applicant.type == "contractor":
⭐       return Decline("insufficient tenure")
⭐   ⭐ This is fine. It is readable, testable and fast.
⭐   ⭐⭐ IT FAILS ON EXACTLY THREE THINGS, AND ALL THREE ARE
⭐     REQUIREMENTS RATHER THAN PREFERENCES:

⭐ ① ⭐ CHANGE VELOCITY — the threshold changes four times a year,
⭐     ⭐⭐ AND THE PERSON WHO KNOWS IT SHOULD CHANGE IS NOT THE
⭐     PERSON WHO CAN DEPLOY. Every change becomes a ticket, a
⭐     PR, a release and a week.
⭐ ② ⭐⭐ AUDITABILITY — "which version of this logic decided
⭐     that?" ⭐ With code, the honest answer is a git archaeology
⭐     exercise against a deploy timeline you probably don't have.
⭐ ③ ⭐⭐ EXPLICABILITY — you must show WHICH RULES FIRED, in
⭐     order, with their rationale. ⭐ A function that returns
⭐     `Decline` knows why. It just didn't tell anyone, and by
⭐     the time you ask, the stack frame is gone.

⭐⭐ AND THE HONEST COST, STATED FIRST: ***A RULE ENGINE IS A
⭐   LANGUAGE YOU NOW OWN.*** ⭐ It has a parser, a semantics, a
⭐   debugger you must build, and an error message quality you
⭐   are responsible for. ⭐⭐ IT IS ONLY WORTH IT IF ALL THREE
⭐   REASONS ABOVE ARE REAL. If only ① is real, use config.
```

# Part 2 — ⭐⭐ The representation ladder — stop early

```
⭐⭐ | LEVEL | WHAT IT IS | WHEN TO STOP HERE |
⭐   | ① HARDCODED | `if` in Python | ⭐ < 10 stable rules |
⭐   | ② CONFIG-DRIVEN | fixed predicate shapes with values
⭐        in a table: (field, op, value) | ⭐⭐ MOST PROJECTS.
⭐        ⭐ Thresholds change without a deploy; the SHAPE of
⭐          the logic still changes with code — which is honest,
⭐          because shape changes need thought anyway |
⭐   | ③ EXPRESSION DSL | a small safe language over a fixed
⭐        context | ⭐ when non-engineers author rules |
⭐   | ④ FULL ENGINE (Rete, forward chaining) | ⭐⭐ WHEN RULES
⭐        DERIVE FACTS THAT TRIGGER OTHER RULES. ⭐ Very rarely
⭐        what people actually need |

⭐ ⇒ ⭐⭐ THE FAILURE IS ALWAYS THE SAME: PEOPLE BUILD ④ AND
⭐   NEEDED ②. ⭐ Then they own an interpreter, a cycle-detection
⭐   problem, and a rule set nobody can reason about — for a
⭐   system with forty rules that never chain.
⭐ ⇒ ⭐ `clearline` stops at ③, and only because "the policy team
⭐   writes rules" is a stated requirement. ⭐⭐ SAY THAT OUT
⭐   LOUD IN THE ADR (Day 295), because choosing a level and
⭐   defending it is the whole lesson.
```

```
⭐⭐ AND IF YOU BUILD ③, THE SAFETY RULE IS ABSOLUTE:
⭐   ⭐ ❌ `eval()`. ⭐⭐ NEVER. A rule is data supplied by a
⭐     user, and `eval` on user data is remote code execution
⭐     with a friendly name.
⭐   ⭐ ✅ A restricted AST: parse with `ast.parse`, walk it, and
⭐     ALLOWLIST node types — comparisons, boolean ops, literals,
⭐     names from a fixed context. ⭐ Everything else is a
⭐     rejection at AUTHORING time, not at evaluation time.
```

# Part 3 — ⭐⭐ The rule, as a row

```
⭐   ⭐ id             — stable, human-readable: `TENURE_MIN_CONTRACTOR`
⭐   ⭐ version        — ⭐⭐ rules are VERSIONED, never edited
⭐   ⭐ valid_from / valid_to — ⭐ effective-dated (Day 289), with
⭐        the same EXCLUDE constraint on (id, during)
⭐   ⭐ priority       — an integer, and Part 4 is about it
⭐   ⭐ condition      — the predicate
⭐   ⭐ outcome        — decline / approve / refer / set a value
⭐   ⭐ reason_code    — ⭐⭐ A STABLE ENUM, not prose. Downstream
⭐        systems, metrics and translations all key off this.
⭐   ⭐ rationale      — ⭐ prose FOR HUMANS, and a link to the
⭐        policy section that justifies the rule's existence
⭐   ⭐ enabled        — so disabling is a data change, not a delete

⭐⭐ TWO FIELDS EARN THEIR PLACE FOR NON-OBVIOUS REASONS:
⭐   ⭐ `reason_code` SEPARATE FROM `rationale` — ⭐⭐ BECAUSE
⭐     THE MOMENT YOU MEASURE REASON DISTRIBUTION (Day 291) OR
⭐     TRANSLATE A MESSAGE, PROSE IS USELESS AS A KEY.
⭐   ⭐ THE LINK TO THE POLICY SECTION — ⭐⭐ IT IS WHAT LETS
⭐     YOU ANSWER "WHY DOES THIS RULE EXIST?" ⭐ A rule with no
⭐     provenance is one nobody will ever dare delete, and your
⭐     rule set grows forever.
```

# Part 4 — ⭐⭐ Conflict, where the bugs actually live

```
⭐⭐ TWO RULES MATCH. ONE SAYS APPROVE, ONE SAYS DECLINE.
⭐   ⭐ This is not an edge case. ⭐⭐ IT IS THE NORMAL STATE OF
⭐     ANY RULE SET ABOVE ABOUT THIRTY RULES, and it arrives
⭐     the day someone adds an exception for one category.

⭐⭐ FOUR RESOLUTION STRATEGIES:
⭐   ⭐ FIRST MATCH — order is the semantics. ⭐ Simple, and
⭐     ⭐⭐ CATASTROPHICALLY FRAGILE: inserting a rule in the
⭐     middle changes unrelated outcomes.
⭐   ⭐ PRIORITY — an explicit integer. ⭐ Predictable.
⭐     ⭐⭐ Needs Part 5's static check, or two rules share a
⭐       priority and you are back to first-match by accident.
⭐   ⭐ SPECIFICITY — the most specific condition wins. ⭐⭐
⭐     "MOST SPECIFIC" IS SURPRISINGLY HARD TO DEFINE and
⭐     produces arguments rather than answers.
⭐   ⭐⭐ MOST-RESTRICTIVE-WINS — any decline beats any approve.
⭐     ⭐ For a compliance system this is usually RIGHT, and it
⭐       has a property the others lack: ⭐⭐ IT IS SAFE UNDER
⭐       AN INCOMPLETE RULE SET, which is the state your rule
⭐       set is permanently in.

⭐ ⇒ ⭐⭐ WHATEVER YOU CHOOSE: IT IS ***STATED***, ***TESTED***,
⭐   AND ***DETERMINISTIC***. ⭐ A rule set whose outcome depends
⭐   on evaluation order that nobody wrote down is a system that
⭐   changes its mind when you add an index.
```

```
⭐⭐ AND THE THING ALMOST NOBODY BUILDS — ***STATIC ANALYSIS OF
⭐   THE RULE SET ITSELF***, run in CI as a test:
⭐   ① ⭐⭐ CONFLICT: two enabled rules, same priority,
⭐     overlapping conditions, contradictory outcomes ⇒ FAIL
⭐   ② ⭐ SHADOWED: a rule that can never fire because an
⭐     earlier, broader rule always matches first ⇒ warn
⭐   ③ ⭐ UNREACHABLE: a condition that is never satisfiable
⭐     (`tenure > 12 AND tenure < 6`) ⇒ FAIL
⭐   ④ ⭐⭐ GAP: an input combination matched by NO rule ⇒
⭐     ⭐⭐ AND THE DEFAULT OUTCOME FOR A GAP MUST BE `REFER`,
⭐        NEVER `APPROVE`. ⭐ "No rule matched" means you don't
⭐        know, and a system that approves what it doesn't
⭐        understand is the failure mode that ends products.
⭐   ⇒ ⭐ Simple interval/set reasoning over the condition space
⭐     gets you all four. It does not need a SAT solver.
```

# Part 5 — ⭐⭐ The trace is the product

```
⭐   ⭐ evaluate(facts, as_of) → ⭐⭐ Decision(
⭐         outcome, reason_codes,
⭐         trace = [
⭐           RuleEval(id, version, matched: bool,
⭐                    values_used: {...}, ⭐⭐ why_not: str|None),
⭐           …
⭐         ],
⭐         ruleset_version, as_of)

⭐⭐ THE FIELD THAT MAKES IT USEFUL IS `why_not` ON THE RULES
⭐   THAT DID ***NOT*** MATCH.
⭐   ⭐ "TENURE_MIN did not fire: tenure_months = 5, needs < 3"
⭐   ⇒ ⭐⭐ BECAUSE ALMOST EVERY SUPPORT QUESTION IS "WHY WASN'T
⭐     THIS APPROVED?" AND ITS TWIN "WHY WAS IT?" — and both are
⭐     answered by the rules that *nearly* fired, not by the one
⭐     that did. ⭐ A trace of only the matches answers half the
⭐     questions you will actually receive.
```

```
⭐⭐ AND THE TWO-LAYER RULE FOR EXPLANATIONS:
⭐   ⭐ THE TRACE is generated by the ENGINE. Deterministic,
⭐     stored (Day 289), diffable, testable.
⭐   ⭐ THE PROSE EXPLANATION may be generated by a model FROM
⭐     the trace — ⭐ turning reason codes into a sentence in the
⭐     user's language is a genuinely good use of one.
⭐   ⇒ ⭐⭐ BUT THE PROSE IS A ***RENDERING***, NEVER A SOURCE.
⭐     ⭐ Store the trace; regenerate the prose freely.
⭐     ⭐⭐ IF THE MODEL IS UNAVAILABLE, THE SYSTEM STILL
⭐       EXPLAINS ITSELF — in reason codes, plainly. ⭐ Which
⭐       is the test: turn the provider off and confirm every
⭐       decision is still explicable.
```

# Part 6 — ⭐⭐ Testing a rule set

```
⭐⭐ RULES ARE DATA, SO TESTS ARE DATA:
⭐   ⭐ A table of cases: inputs → expected outcome + expected
⭐     reason codes. ⭐ Reviewed by whoever owns the policy,
⭐     because ⭐⭐ THEY CAN READ IT AND THEY CANNOT READ PYTEST.

⭐⭐ THREE KINDS OF TEST, AND THE SECOND IS THE ONE THAT FINDS
⭐   REAL BUGS:
⭐   ① ⭐ CASE TESTS — the table above. Necessary, unexciting.
⭐   ② ⭐⭐ PROPERTY TESTS — assertions about the rule set as a
⭐     whole, over generated inputs:
⭐       ⭐ MONOTONICITY: increasing tenure must never turn an
⭐         approve into a decline. ⭐⭐ VIOLATIONS ARE ALMOST
⭐         ALWAYS REAL BUGS, and they are essentially impossible
⭐         to find by reading — they emerge from the INTERACTION
⭐         of two rules written months apart.
⭐       ⭐ TOTALITY: every generated input produces a decision
⭐         (no crash, no `None`).
⭐       ⭐ DETERMINISM: same inputs + same `as_of` + same
⭐         version ⇒ byte-identical trace.
⭐   ③ ⭐ SNAPSHOT TESTS on the trace, so a rule edit shows up
⭐     as a reviewable diff of decisions rather than a silent
⭐     behaviour change.

⭐⭐ AND THE COVERAGE QUESTION THAT IS SPECIFIC TO RULES:
⭐   ***WHICH RULES HAVE NEVER FIRED — IN TESTS, OR IN
⭐      PRODUCTION?***
⭐   ⇒ ⭐ A rule that never fires is dead, wrong, or shadowed
⭐     (Part 4). ⭐⭐ ALL THREE ARE FINDINGS, and this is one
⭐     query — which makes it the cheapest audit in the project.
```

# Part 7 — ⭐ Versioning, and the rule-set as an artefact

```
⭐   ⭐ A RULE SET HAS A VERSION — a hash of all enabled rules
⭐     and their versions at a moment in time.
⭐   ⭐ Every decision stores it (Day 289).
⭐   ⭐ Every change produces a NEW version; ⭐⭐ RULES ARE
⭐     NEVER EDITED IN PLACE, for exactly the reason thresholds
⭐     are not: it destroys the past.
⭐   ⭐ Changes are reviewed like code: an author, a reviewer,
⭐     a diff, a timestamp — ⭐⭐ EVEN THOUGH IT IS A DATABASE
⭐     ROW AND NOTHING TECHNICALLY FORCES ANY OF THAT.
⭐   ⇒ ⭐ Which sets up tomorrow's question, the one that makes
⭐     a rule engine real: ⭐⭐ "WE WANT TO CHANGE THIS
⭐     THRESHOLD — ***WHAT WOULD HAVE HAPPENED?***"
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Building a rule engine because it sounds architectural | It's a language you now own. Justify all three reasons or use config. |
| Building a full inference engine | Almost nobody needs chaining. Stop at config or a small DSL. |
| `eval()` for conditions | Rules are user data; that's RCE with a friendly name. Use a restricted AST. |
| Editing rules in place | It destroys the ability to explain any past decision. |
| Prose as the reason key | Metrics, translations and downstream systems all need a stable enum. |
| No link from rule to policy source | Nobody will dare delete it, and the rule set grows forever. |
| First-match ordering | Inserting a rule changes unrelated outcomes. |
| Undocumented conflict resolution | The outcome depends on evaluation order nobody wrote down. |
| Two enabled rules at the same priority | You're back to first-match, by accident. |
| No static analysis of the rule set | Conflicts, shadowing and gaps are all detectable, cheaply, in CI. |
| Defaulting a gap to approve | A system that approves what it doesn't understand is the failure that ends products. |
| A trace containing only matches | Most support questions are about rules that nearly fired. |
| Treating generated prose as the explanation | It's a rendering. Store the trace; regenerate prose freely. |
| No provider-off test | The system must still explain itself when the model is unavailable. |
| Only case tests | Monotonicity violations come from interactions and can't be read out of the code. |
| Never asking which rules never fire | Dead, wrong or shadowed — three findings from one query. |
| Rule changes without review | It's a database row, so nothing forces review. Force it anyway. |

## Interview questions

**Q: Why a rule engine rather than `if` statements?**

> Only if three things are true, and I'd say the cost first: a rule engine is a language you now own,
> with a parser, a semantics and a debugger you have to build. It's worth it when the thresholds
> change several times a year and the person who knows they should change can't deploy; when you need
> to answer "which version of this logic decided that?" without git archaeology against a deploy
> timeline; and when you have to show which rules fired, in order, with rationale. If only the first
> is true, that's config, not an engine — and most projects that build a full inference engine needed
> a table of values.

**Q: Two rules match with opposite outcomes. What happens?**

> Whatever I wrote down, tested, and can state — that's the actual requirement. For a compliance
> system I'd default to most-restrictive-wins, because it has a property the others don't: it's safe
> under an incomplete rule set, which is the permanent state of every rule set. First-match is the
> one I'd avoid, because inserting a rule in the middle changes unrelated outcomes. And I'd back it
> with static analysis in CI: two enabled rules at the same priority with overlapping conditions and
> contradictory outcomes fails the build, along with unreachable conditions and gaps — and a gap
> defaults to refer, never approve, because a system that approves what it doesn't understand is the
> failure mode that ends products.

**Q: What does the engine return?**

> A decision, reason codes, and a full trace: every rule evaluated, its version, whether it matched,
> the values used, and — for the ones that didn't match — why not. That last field is the one that
> makes it useful, because almost every support question is "why wasn't this approved?" and its twin
> "why was it?", and both are answered by the rules that nearly fired rather than the one that did.
> The trace is generated by the engine and stored; a model may turn it into a sentence in the user's
> language, but that prose is a rendering, never a source. The test is turning the provider off and
> confirming every decision still explains itself.

**Q: How do you test rules?**

> Rules are data, so the tests are data — a table of inputs to expected outcomes and reason codes,
> reviewed by whoever owns the policy, because they can read a table and can't read pytest. Then
> property tests over generated inputs, which is where the real bugs are: monotonicity, so increasing
> tenure can never turn an approve into a decline. Violations there are almost always genuine, and
> they're essentially impossible to find by reading, because they emerge from two rules written months
> apart interacting. And one query I'd run regularly: which rules have never fired, in tests or in
> production? Each one is dead, wrong, or shadowed — three findings for almost no effort.

## Today's build

1. ⭐⭐ Write twenty real rules from your corpus as prose first. Only then choose a representation level.
2. ⭐ Justify the level you chose in three sentences, naming the requirement each addresses.
3. ⭐⭐ Implement the rule row with all nine fields, effective-dated with an exclusion constraint.
4. ⭐⭐ If you built a DSL, implement it as a restricted AST walker with an allowlist. Try to smuggle in `__import__` and confirm rejection at authoring time.
5. ⭐ Separate `reason_code` from `rationale` and link every rule to a policy section.
6. ⭐⭐ Choose and document a conflict strategy. Write the test that proves it.
7. ⭐⭐ Build the static analyser: conflicts, shadowing, unreachable conditions, gaps. Wire it into CI.
8. ⭐⭐ Introduce a deliberate conflict and confirm the build fails.
9. ⭐ Make the gap default `refer` and test the path.
10. ⭐⭐ Return the full trace including `why_not` for non-matching rules.
11. ⭐ Render a prose explanation from the trace with a model, then turn the provider off and confirm decisions are still explicable.
12. ⭐⭐ Write the case table with 40+ cases and have someone non-technical read it.
13. ⭐⭐ Write the monotonicity property test over generated inputs. Fix whatever it finds.
14. ⭐ Add determinism and totality property tests.
15. ⭐⭐ Compute the rule-set version hash and store it on every decision.
16. ⭐ Query which rules have never fired. Categorise each as dead, wrong or shadowed.

## 🎙️ Articulation drill

**Three minutes: "How does the decision engine work?"**

Lead with the justification and the cost together, because that's the senior move: **a rule engine is
a language you now own**, so it needs three real requirements — thresholds changing faster than
deploys, auditability of which logic version decided what, and explicability. If only the first is
true, it's config. Then say where you stopped on the ladder and why, because **the usual failure is
building a full inference engine when you needed a table of values.** Then conflict, which is where
the bugs are: **two rules matching with opposite outcomes is the normal state of any rule set above
about thirty rules**, so the strategy is stated, tested and deterministic — most-restrictive-wins for
compliance, because it's the only one that's safe under an incomplete rule set, which is your
permanent condition. Mention the static analyser, since almost nobody builds one: conflicts,
shadowing, unreachable conditions and gaps, all detectable in CI — **and a gap defaults to refer,
never approve, because a system that approves what it doesn't understand is the failure that ends
products.** Then the centrepiece: **the trace is the product, not the verdict**, and it includes
`why_not` for the rules that didn't fire, because most support questions are about the rule that
nearly fired. Close on the two layers — **the engine generates the trace and stores it; a model may
render it into a sentence, but prose is a rendering, never a source** — and the test is turning the
provider off and confirming every decision still explains itself.
