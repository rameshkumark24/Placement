# Day 298 🏛️

**P-298** · 🏛️ **Why architecture exists** — ⭐⭐ coupling, cohesion, and the cost of change

**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: architecture is the set of decisions that are expensive to reverse, and
> the only reason to think about it is the cost of change — which means every architectural argument
> that does not name a change it makes cheaper is an aesthetic argument wearing a suit.**
>
> ⭐ Stage 8 opens after Stage 7 for a reason: ⭐⭐ you now have two systems and an audit, so every
> question in the next twenty-four days can be asked about code you actually wrote.

# Part 1 — ⭐⭐ The only justification

```
⭐⭐ THREE BAD REASONS TO RESTRUCTURE CODE:
⭐   ⭐ "it's cleaner"        — ⭐ cleaner for whom, doing what?
⭐   ⭐ "it's best practice"  — ⭐⭐ AN APPEAL TO AUTHORITY WITH
⭐        THE AUTHORITY LEFT OUT
⭐   ⭐ "we might need it later" — ⭐ a bet, unnamed and unpriced

⭐⭐ THE ONE GOOD REASON, AND IT IS TESTABLE:
⭐   ***THIS CHANGE IS LIKELY, AND THE STRUCTURE MAKES IT
⭐      CHEAPER — HERE IS THE CHANGE, AND HERE IS THE COST
⭐      BEFORE AND AFTER.***

⭐ ⇒ ⭐⭐ SO THE ASSESSMENT OF AN ARCHITECTURE IS NOT A DIAGRAM.
⭐   ⭐ It is: ⭐⭐ TAKE FIVE REALISTIC CHANGE REQUESTS AND
⭐   TRACE WHAT EACH ONE TOUCHES.
⭐   ⭐ "add a field to an order"      → how many files?
⭐   ⭐ "support a second payment provider" → how many?
⭐   ⭐ "make one endpoint 10× faster" → what must you know?
⭐   ⭐ "add a new tenant-level permission" → how many places?
⭐   ⭐ "swap Postgres for X"          → ⭐ and be honest that
⭐        the answer is "you don't", which is itself information
⭐   ⇒ ⭐ Four files is a good architecture for that change.
⭐     ⭐⭐ FOURTEEN FILES ACROSS FIVE MODULES IS A FINDING,
⭐     and it is a finding with a NUMBER, which is the entire
⭐     difference between this and a style argument.
```

# Part 2 — ⭐⭐ Coupling and cohesion, defined so they're usable

```
⭐⭐ THE TEXTBOOK DEFINITIONS ARE TRUE AND USELESS. USE THESE:
⭐   ⭐ COUPLING  — ⭐⭐ "IF I CHANGE X, WHAT ELSE MUST I
⭐        CHANGE?" ⭐ Coupling is not "A calls B". It is
⭐        ⭐⭐ "A CANNOT CHANGE WITHOUT B CHANGING."
⭐   ⭐ COHESION  — ⭐⭐ "DO THE THINGS IN THIS MODULE CHANGE
⭐        FOR THE SAME REASON?" ⭐ Not "are they related in my
⭐        head" — ⭐⭐ DO THEY APPEAR IN THE SAME COMMITS?

⭐ ⇒ ⭐⭐ AND YOU CAN ***MEASURE*** COHESION FROM GIT:
⭐   ⭐ `git log --name-only` ⇒ which files change together?
⭐   ⭐⭐ TWO FILES IN DIFFERENT MODULES THAT CHANGE TOGETHER
⭐     IN 80% OF COMMITS ARE ***ONE MODULE THAT IS MISFILED***,
⭐     ⭐ and no amount of diagramming will tell you that,
⭐       because the diagram records intent and the log records
⭐       what happened.
```

```
⭐⭐ THE INVERSE FAILURE, WHICH IS MORE COMMON THAN PEOPLE
⭐   ADMIT: LOW COUPLING BOUGHT WITH HIGH INDIRECTION.
⭐   ⭐ Five interfaces, three factories, and a plugin registry
⭐     — and every change still touches five files, ⭐⭐ NOW
⭐     SPREAD ACROSS SEVEN.
⭐   ⇒ ⭐ Indirection is not decoupling. ⭐⭐ IT IS DECOUPLING
⭐     ***IF AND ONLY IF*** THE THING BEHIND THE INTERFACE
⭐     ACTUALLY VARIES. ⭐ One implementation behind an
⭐     interface is a cost with no purchase.
```

# Part 3 — ⭐⭐ Connascence: the precise vocabulary

```
⭐⭐ "COUPLING" IS ONE WORD FOR NINE DIFFERENT THINGS.
⭐   CONNASCENCE NAMES THEM, ⭐ WEAKEST TO STRONGEST:

⭐⭐ STATIC — visible by reading the code:
⭐   ⭐ NAME     — both refer to `total_cents`. ⭐ Unavoidable,
⭐        and the weakest form.
⭐   ⭐ TYPE     — both agree it is a `Decimal`.
⭐   ⭐ MEANING  — ⭐⭐ BOTH AGREE THAT `status = 2` MEANS
⭐        "shipped". ⭐ Fix with an `Enum`. Magic strings and
⭐        numbers are exactly this.
⭐   ⭐ POSITION — ⭐⭐ `create(a, b, c)` AND THE CALLER MUST
⭐        KNOW THE ORDER. ⭐ Fix with keyword-only arguments —
⭐        `def create(*, name, price, qty)` — which converts
⭐        position into name, ⭐⭐ AND THAT IS AN ARCHITECTURAL
⭐        IMPROVEMENT IN ONE CHARACTER.
⭐   ⭐ ALGORITHM — ⭐⭐ TWO PLACES MUST IMPLEMENT THE SAME
⭐        RULE IDENTICALLY: a cache key built in two modules, a
⭐        signature computed on both sides, a slug generated in
⭐        the app and in a migration. ⭐ Strongest static form,
⭐        and the one that breaks silently.

⭐⭐ DYNAMIC — only visible at runtime, and therefore worse:
⭐   ⭐ EXECUTION ORDER — B must run after A. ⭐ Nothing
⭐        enforces it, and a refactor reorders two lines.
⭐   ⭐ TIMING          — ⭐⭐ IT WORKS BECAUSE A IS USUALLY
⭐        FASTER. ⭐ Day 265's `.delay()` before commit.
⭐   ⭐ VALUE           — two values must change together
⭐        (a `total` and its `lines`). ⭐⭐ THIS IS WHAT AN
⭐        AGGREGATE BOUNDARY EXISTS TO CONTAIN (Day 250).
⭐   ⭐ IDENTITY        — two components must reference the
⭐        same instance.
```

```
⭐⭐ AND THE THREE RULES THAT MAKE IT ACTIONABLE:
⭐   ① ⭐ MINIMISE OVERALL DEGREE — how many places share it.
⭐   ② ⭐⭐ MINIMISE ***STRENGTH*** — convert strong forms into
⭐     weak ones. Position → name. Meaning → type.
⭐   ③ ⭐⭐ MAXIMISE ***LOCALITY*** — ⭐ strong connascence
⭐     inside one function is fine; ⭐⭐ THE SAME STRENGTH
⭐     ACROSS TWO SERVICES IS AN INCIDENT WAITING TO HAPPEN.
⭐   ⇒ ⭐⭐ WHICH GIVES THE RULE OF THUMB: ***THE FURTHER APART
⭐     TWO THINGS ARE, THE WEAKER THEIR CONNASCENCE MUST BE.***
```

# Part 4 — ⭐⭐ The coupling that is not in your imports

```
⭐⭐ THE MOST DANGEROUS SENTENCE IN THIS DAY:
⭐   ***THE DEPENDENCY GRAPH OF YOUR IMPORTS IS NOT THE
⭐      DEPENDENCY GRAPH OF YOUR SYSTEM.***

⭐   ⭐ TWO MODULES SHARING A DATABASE TABLE are coupled at the
⭐     strongest possible level — ⭐⭐ SCHEMA — and there is
⭐     not one import between them. ⭐ Add a NOT NULL column and
⭐     the other module breaks in production.
⭐   ⭐ A QUEUE MESSAGE SCHEMA (Day 265) couples producer and
⭐     consumer across a deploy boundary, ⭐⭐ ACROSS TIME —
⭐     the consumer is reading a message the producer wrote
⭐     twenty minutes and one release ago.
⭐   ⭐ A CACHE KEY FORMAT built in two places is connascence
⭐     of algorithm across a network (Day 266).
⭐   ⭐ A SHARED ENUM PERSISTED AS AN INTEGER couples every
⭐     future reader to today's ordering.
⭐   ⭐⭐ AND THE URL ITSELF: once a client depends on your
⭐     response shape, that shape is coupling you cannot see
⭐     from inside the repository at all (Day 260's spec).

⭐ ⇒ ⭐⭐ SO "WE SPLIT IT INTO MODULES AND IT IS DECOUPLED NOW"
⭐   IS ALMOST ALWAYS FALSE. ⭐ The imports moved. ⭐⭐ THE
⭐   SCHEMA, THE MESSAGE FORMAT AND THE SHARED ASSUMPTIONS
⭐   DIDN'T — and those are the ones that break at 3 a.m.
```

# Part 5 — ⭐ The cost of an abstraction

```
⭐   ⭐ EVERY ABSTRACTION IS A ***BET ON WHICH AXIS WILL
⭐     CHANGE***. ⭐ A payment interface bets the provider
⭐     changes. A repository bets the storage changes.
⭐   ⇒ ⭐⭐ WIN THE BET AND THE CHANGE IS ONE FILE. ⭐⭐ LOSE
⭐     IT AND YOU HAVE PAID FOREVER FOR FLEXIBILITY ON AN AXIS
⭐     THAT NEVER MOVED — ***AND, WORSE, THE ABSTRACTION NOW
⭐     OBSTRUCTS THE AXIS THAT DID.***
⭐   ⭐ Concretely: a repository that hides SQL makes swapping
⭐     databases easy (never happened) and makes adding a
⭐     window function awkward (happens monthly).

⭐   ⭐⭐ THE RULE OF THREE IS A REASONABLE DEFAULT: don't
⭐     abstract until the third instance, ⭐ because two points
⭐     define a line and the third tells you whether it was
⭐     ever a line.
⭐   ⭐ And the honest exception: ⭐⭐ ABSTRACT EARLY WHEN THE
⭐     COST OF BEING WRONG IS ASYMMETRIC — a boundary you can
⭐     add later is cheap to defer; ⭐ a boundary you cannot
⭐     retrofit (a schema, a public API, a message format) is
⭐     not.
```

# Part 6 — ⭐⭐ Reversibility is the real axis

```
⭐⭐ SORT EVERY DECISION BY ***HOW EXPENSIVE IT IS TO
⭐   REVERSE***, NOT BY HOW IMPORTANT IT FEELS:

⭐   ⭐ CHEAP (hours)   — a library, a file layout, a function
⭐        signature, a cache TTL. ⭐⭐ DECIDE FAST, MOVE ON.
⭐        ⭐ Time spent deliberating here is pure waste.
⭐   ⭐ MEDIUM (weeks)  — a framework, a service boundary, an
⭐        auth model. ⭐ Worth a day and an ADR.
⭐   ⭐⭐ EXPENSIVE (months, or never) — the database engine,
⭐        the public API shape, the tenancy model, a message
⭐        format other teams consume, ⭐⭐ AND ANY DATA MODEL
⭐        THAT HAS ACCUMULATED PRODUCTION DATA.
⭐        ⇒ ⭐⭐ THESE ARE THE ONLY DECISIONS THAT DESERVE THE
⭐          WORD "ARCHITECTURE", and they deserve real time.

⭐ ⇒ ⭐⭐ THE COMMONEST PROFESSIONAL MISTAKE IS SPENDING THE
⭐   DELIBERATION BUDGET ON THE CHEAP ROW. ⭐ Two days choosing
⭐   a logging library, twenty minutes choosing whether tenancy
⭐   is a column or a schema — ⭐⭐ AND ONLY ONE OF THOSE IS
⭐   STILL WITH YOU IN THREE YEARS.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| "It's cleaner" as a justification | Cleaner for whom, doing what? Name the change it makes cheaper. |
| "Best practice" | An appeal to authority with the authority left out. |
| Assessing architecture from a diagram | Trace five realistic change requests and count the files. |
| Defining coupling as "A calls B" | It's "A cannot change without B changing". |
| Judging cohesion by intuition | Measure it: which files appear in the same commits? |
| Buying low coupling with high indirection | One implementation behind an interface is a cost with no purchase. |
| Using "coupling" for nine different things | Connascence names them, and the name tells you the fix. |
| Positional arguments across a module boundary | Keyword-only converts position into name in one character. |
| Magic strings and integers | Connascence of meaning; an enum converts it to type. |
| The same algorithm implemented twice | Strongest static form, and it breaks silently. |
| Ignoring locality | The same strength across two services is an incident waiting to happen. |
| Believing imports show your dependencies | A shared table couples two modules with zero imports. |
| "We split it into modules, so it's decoupled" | The imports moved; the schema and message formats didn't. |
| Abstracting on the first instance | Two points define a line; the third tells you if it was one. |
| Never abstracting early | Boundaries you can't retrofit — schema, public API, message format — are the exception. |
| Deliberating over cheap decisions | Two days on a logging library, twenty minutes on the tenancy model. |

## Interview questions

**Q: How do you evaluate an architecture?**

> By the cost of change, not by a diagram. I take five realistic change requests — add a field to an
> order, support a second payment provider, add a tenant-level permission, make one endpoint ten times
> faster — and trace how many files and modules each one touches. That gives a number, which is the
> difference between an architectural argument and a style argument. It also surfaces the honest
> answers: "swap the database" is a change nobody makes, and knowing that tells you a repository
> abstraction was bought for the wrong reason.

**Q: Define coupling in a way you can act on.**

> "If I change X, what else must I change?" — not "A calls B", because a call you never have to
> revisit costs nothing. And cohesion is "do these things change for the same reason?", which I can
> actually measure rather than guess: `git log --name-only` tells me which files appear in the same
> commits, and two files in different modules that change together in eighty percent of commits are
> one module that's been misfiled. The diagram records intent; the log records what happened.

**Q: What's connascence and why bother with the vocabulary?**

> Because "coupling" is one word for about nine different situations that have different fixes.
> Connascence names them from weakest to strongest — name, type, meaning, position, algorithm — and
> then the dynamic ones, execution order, timing, value and identity, which are worse because you
> can't see them by reading. The value is that the name implies the remedy: connascence of position is
> fixed by keyword-only arguments, connascence of meaning by an enum. And there are three rules —
> reduce the number of places, reduce the strength, and maximise locality — which give you the useful
> heuristic that the further apart two things are, the weaker their connascence must be.

**Q: You've split a monolith into modules. Is it decoupled?**

> Probably not, and I'd say why: the dependency graph of your imports isn't the dependency graph of
> your system. Two modules sharing a database table are coupled at the schema level with zero imports
> between them, and adding a `NOT NULL` column breaks the other one in production. A queue message
> format couples a producer and consumer across a deploy boundary and across time. A cache key built
> in two places is connascence of algorithm over a network. Those are the couplings that break at
> 3 a.m., and moving imports around doesn't touch any of them.

**Q: When do you introduce an abstraction?**

> When I can name the axis I think will change and I'm willing to be judged on that bet. Every
> abstraction bets on an axis: a payment port bets the provider changes, a repository bets the storage
> changes. Win and the change is one file; lose and you pay forever for flexibility that never
> materialised — and worse, the abstraction obstructs the axis that did move, which is exactly what a
> SQL-hiding repository does when you need a window function. So the rule of three by default, with
> one exception: boundaries you can't retrofit — schema, public API, message format — deserve to be
> decided early because the cost of being wrong is asymmetric.

## 🎙️ Articulation drill

**Two minutes: "What does good architecture mean to you?"**

Lead with the definition that makes it falsifiable: **architecture is the set of decisions that are
expensive to reverse, and the only reason to care is the cost of change** — so any architectural
argument that doesn't name a change it makes cheaper is an aesthetic one. Say how you'd assess it:
**not from a diagram, but by tracing five realistic change requests and counting files** — four files
is good, fourteen across five modules is a finding, and it's a finding with a number. Then give the
operational definitions: **coupling is "if I change X, what else must change", and cohesion is "do
these change for the same reason"** — and note you can measure cohesion from the git log rather than
guessing, because two files in different modules that change together in most commits are one misfiled
module. Introduce connascence as the precise vocabulary, and give one example where the name implies
the fix: **positional arguments across a boundary become keyword-only in one character.** Then the
line that matters most in practice: **the dependency graph of your imports is not the dependency graph
of your system** — a shared table, a queue message format and a cache key built in two places are all
strong coupling with no import between them, and they're the ones that break at 3 a.m. Close on
budget: **sort decisions by reversibility, decide the cheap ones fast, and spend the deliberation on
the schema and the tenancy model** — because those are the ones still with you in three years.
