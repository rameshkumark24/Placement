# Part 1 — ⭐ Fixed window: the simplest one, and its flaw

```lua
-- ⭐ ONE round trip, atomic. ⭐⭐ The two-command version (INCR then
--    EXPIRE) can leave a key with NO TTL if the process dies between
--    them — a permanently-full window. Hence Lua.
local c = redis.call("INCR", KEYS[1])
if c == 1 then redis.call("PEXPIRE", KEYS[1], ARGV[1]) end
return c
```

```
⭐ KEY: `rl:{user:42}:1755590400`   ⭐ the window start, floor(now/60)
⭐ MEMORY: ⭐⭐ ONE SMALL INTEGER PER ACTIVE CLIENT PER WINDOW. Nothing.
⭐ COST: O(1). ⭐ It is genuinely excellent — except for one thing.

⭐⭐ THE BOUNDARY BURST. LIMIT = 100 PER MINUTE:
⭐   12:00:59  →  100 requests   ⭐ window [12:00, 12:01) is now full ✅
⭐   12:01:00  →  100 requests   ⭐ NEW WINDOW. All allowed ✅
⭐   ⇒ ⭐⭐ ***200 REQUESTS IN ONE SECOND***, and every one was
⭐     "within the limit". ⭐ Your backend sees 2× the rate you designed
⭐     for, at a moment attackers and retry storms both favour.
⭐   ⭐⭐ AND IT IS WORSE THAN "2× ONCE": clients that back off to the
⭐     window boundary SYNCHRONISE there (Day 152's retry storm), so the
⭐     spike repeats every minute.

⭐ ⇒ ⭐ USE IT WHEN: the limit is generous, the client is trusted, and
⭐   2× is survivable. ⭐⭐ DO NOT USE IT as your only defence on an
⭐   expensive endpoint.
```

# Part 2 — ⭐⭐ Sliding window log: exact, and unaffordable

```lua
-- ⭐ KEYS[1]=key  ARGV: now_ms, window_ms, limit, member
redis.call("ZREMRANGEBYSCORE", KEYS[1], 0, ARGV[1] - ARGV[2]) -- ⭐ evict
local n = redis.call("ZCARD", KEYS[1])
if n < tonumber(ARGV[3]) then
    redis.call("ZADD", KEYS[1], ARGV[1], ARGV[4])   -- ⭐ record this one
    redis.call("PEXPIRE", KEYS[1], ARGV[2])
    return {1, ARGV[3] - n - 1}                      -- ⭐ allowed, left
end
return {0, 0}
```

```
⭐ ✅ ⭐⭐ EXACT. A true rolling window: no boundary burst, ever.
⭐ ✅ ⭐ It can tell you exactly when the next slot frees up
⭐      (`ZRANGE key 0 0 WITHSCORES` + window) ⇒ ⭐⭐ A PRECISE
⭐      `Retry-After`, which no other algorithm here gives you.
⭐ ❌ ⭐⭐ MEMORY. ONE SORTED-SET MEMBER PER ***REQUEST***:
⭐      100,000 users × 1,000 req/min × ~70 bytes
⭐      ⇒ ⭐⭐ ~7 GB, RECYCLED EVERY MINUTE.
⭐ ❌ ⭐ O(log n) per op, plus the eviction scan.
⭐ ⇒ ⭐⭐ CORRECT AND UNAFFORDABLE AT SCALE. ⭐ Right for LOW-VOLUME,
⭐   HIGH-VALUE limits: password attempts, OTP sends, payment retries,
⭐   expensive report generation — ⭐⭐ where exactness matters and the
⭐   volume is tiny. That is a real and common case; do not dismiss it.
```

# Part 3 — ⭐⭐ Sliding window counter: the one most people should use

```
⭐⭐ THE IDEA: keep TWO fixed-window counters and INTERPOLATE.

⭐   now = 12:01:15, window = 60 s ⇒ ⭐ 25% into the current window
⭐   previous window count = 80 · current window count = 12
⭐   ⭐⭐ estimate = 80 × (1 − 0.25) + 12 = 60 + 12 = ***72***
⭐
⭐⭐ WHY IT KILLS THE BOUNDARY BURST: at 12:01:00 the previous window is
⭐   weighted ~100%, so the 100 requests from 12:00 still count almost
⭐   fully. ⭐ The 2× spike is impossible.
⭐ MEMORY: ⭐⭐ TWO INTEGERS PER CLIENT. Same as fixed window.
⭐ ACCURACY: ⭐ assumes requests were spread evenly across the previous
⭐   window. ⭐⭐ Cloudflare measured the error at well under 1% on real
⭐   traffic. ⭐ It can occasionally allow slightly over, or reject
⭐   slightly early — both bounded and small.
⭐ ⇒ ⭐⭐ FIXED-WINDOW MEMORY, NEAR-SLIDING-LOG ACCURACY. THIS IS THE
⭐   DEFAULT ANSWER FOR AN API RATE LIMIT.
```

```lua
-- ⭐ KEYS[1]=cur KEYS[2]=prev  ARGV: limit, window_ms, elapsed_ms
local cur  = tonumber(redis.call("GET", KEYS[1]) or "0")
local prev = tonumber(redis.call("GET", KEYS[2]) or "0")
local w    = 1 - (tonumber(ARGV[3]) / tonumber(ARGV[2]))
local est  = prev * w + cur
if est >= tonumber(ARGV[1]) then return {0, 0} end
redis.call("INCR", KEYS[1])
redis.call("PEXPIRE", KEYS[1], tonumber(ARGV[2]) * 2)  -- ⭐⭐ 2× so it
return {1, math.floor(tonumber(ARGV[1]) - est - 1)}    --   survives to
                                                       --   be "prev"
```

# Part 4 — ⭐⭐ Token bucket: when bursts are a feature

```
⭐⭐ A BUCKET OF `capacity` TOKENS, REFILLED AT `rate` PER SECOND.
⭐   Each request takes one. Empty ⇒ rejected.
⭐   ⭐⭐ THE REFILL IS ***LAZY***: you do not run a timer. You store
⭐     `(tokens, last_refill_ms)` and compute the refill on read.
⭐     ⇒ ⭐ O(1), two hash fields, no background process.

⭐⭐ WHAT IT GIVES YOU THAT THE OTHERS DO NOT: ***CONTROLLED BURST***.
⭐   capacity 100, rate 10/s ⇒ ⭐ an idle client may fire 100 at once,
⭐   then settles to 10/s. ⭐⭐ THAT IS USUALLY WHAT YOU ACTUALLY WANT
⭐   FROM AN API: a page that loads 40 resources should not be throttled,
⭐   but a client cannot sustain 40/s.
⭐   ⭐ Capacity and rate are two SEPARATE dials — burst tolerance and
⭐     steady rate. ⭐⭐ Every other algorithm here conflates them.
⭐   ⭐ LEAKY BUCKET / GCRA is the smooth cousin: no burst at all,
⭐     perfectly even output. ⭐ Right for protecting a downstream that
⭐     genuinely cannot absorb spikes.
```

```lua
-- ⭐⭐ ARGV: capacity, refill_per_sec, now_ms, cost
local b = redis.call("HMGET", KEYS[1], "t", "ts")
local cap, rate, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)   -- ⭐ lazy
local cost = tonumber(ARGV[4])
local ok = 0
if tokens >= cost then tokens = tokens - cost; ok = 1 end
redis.call("HSET", KEYS[1], "t", tokens, "ts", now)
redis.call("PEXPIRE", KEYS[1], math.ceil(cap / rate * 2000)) -- ⭐ self-
return {ok, math.floor(tokens),                              --   cleaning
        ok == 1 and 0 or math.ceil((cost - tokens) / rate * 1000)}
-- ⭐⭐ THAT THIRD RETURN VALUE IS `Retry-After` IN MILLISECONDS, computed
--    exactly. ⭐ Token bucket gives you a precise retry hint for free.
-- ⭐⭐ AND `cost` MEANS WEIGHTED LIMITING: a search costs 10 tokens, a
--    health check costs 1. ⭐ One limiter, priced by expense.
```

# Part 5 — ⭐⭐ The details that decide whether it works

```
⭐⭐ ① USE ***REDIS'S*** CLOCK, NOT YOURS.
⭐    `local t = redis.call("TIME")` ⇒ {seconds, microseconds}
⭐    ⭐⭐ APPLICATION SERVERS DISAGREE BY SECONDS. NTP drift, a VM
⭐      resumed from suspend, a container with a skewed clock — ⭐⭐ AND
⭐      A CLIENT WHOSE `now` IS 3 SECONDS AHEAD GETS A FREE WINDOW.
⭐    ⭐ Redis is one machine, so its clock is at least CONSISTENT for
⭐      all callers, which is the property you need.
⭐    ⭐⭐ CAVEAT: pre-Redis 7, `TIME` made a script non-deterministic
⭐      and was banned in scripts replicated by command. ⭐ Modern Redis
⭐      replicates effects, so it is fine — ⭐ but check your version
⭐      before assuming, because this is a real historical trap.

⭐⭐ ② ATOMICITY IS NOT OPTIONAL. Read-then-write from the application
⭐    is Day 195's lost update: two requests both read 99, both allow.
⭐    ⭐⭐ ONE LUA SCRIPT, `EVALSHA`, ONE ROUND TRIP.

⭐⭐ ③ THE KEY IS THE POLICY. `rl:{tenant:7}:user:42:POST:/search:v1`
⭐    ⭐ dimension (user/ip/api-key/tenant) · ⭐ endpoint class ·
⭐    ⭐ a version segment so you can change the algorithm without
⭐      inheriting stale state · ⭐⭐ and `{braces}` in cluster mode so
⭐      multi-key scripts stay on one node (Day 204).

⭐⭐ ④ LIMIT IN LAYERS, AND SAY WHY EACH EXISTS:
⭐    ⭐ per-API-key   — the commercial contract
⭐    ⭐ per-user      — abuse by one account
⭐    ⭐ per-IP        — abuse before login (⭐⭐ and the caveat: NAT and
⭐         mobile carriers put thousands of real users behind one IP, so
⭐         an IP limit must be generous or it becomes an availability
⭐         bug for a whole country)
⭐    ⭐⭐ global / per-tenant occupancy — ⭐⭐ THE ONE PEOPLE OMIT.
⭐         Without it, 10,000 users each under their limit still take
⭐         the service down. ⭐ Day 153's fairness point.
⭐    ⇒ ⭐ Evaluate cheapest first and short-circuit; ⭐⭐ but decrement
⭐      only what you actually consumed, or a rejection at layer 3 has
⭐      already burned quota at layers 1 and 2.

⭐⭐ ⑤ THE RESPONSE CONTRACT (Day 153, now exact):
⭐      HTTP/1.1 429 Too Many Requests
⭐      Retry-After: 12                    ⭐ seconds — ⭐⭐ ALWAYS SEND
⭐      RateLimit-Limit: 100               ⭐ IETF draft headers
⭐      RateLimit-Remaining: 0
⭐      RateLimit-Reset: 12
⭐    ⭐⭐ WITHOUT `Retry-After` A WELL-BEHAVED CLIENT CANNOT BEHAVE
⭐      WELL — it guesses, and guessing means retrying immediately.
⭐    ⭐ Send `RateLimit-Remaining` on SUCCESSFUL responses too, so
⭐      clients can self-throttle before they are rejected.
⭐    ⭐⭐ AND DECIDE DELIBERATELY: DO REJECTED REQUESTS COUNT? ⭐ For
⭐      capacity, no (you did no work). ⭐⭐ For abuse, YES — otherwise
⭐      a brute-force attacker gets unlimited attempts at the rejection
⭐      path, which is exactly the endpoint you were protecting.
```

```python
# ⭐⭐ ⑥ FAIL OPEN OR CLOSED — Day 153, and this is where it is decided
try:
    allowed, remaining, retry_ms = LIMITER(keys=[key], args=[...])
except redis.RedisError:
    allowed = not IS_SECURITY_LIMIT          # ⭐⭐ THE WHOLE RULE
    # ⭐ CAPACITY limit + Redis down ⇒ FAIL OPEN. Rejecting all traffic
    #   because the limiter is down is a self-inflicted outage.
    # ⭐⭐ SECURITY limit (login, OTP, password reset) + Redis down ⇒
    #   FAIL CLOSED. An unlimited brute-force window is worse than
    #   downtime, and it is the window an attacker will wait for.
    metrics.limiter_errors.inc()             # ⭐ and ALERT, because
                                             #   silently failing open
                                             #   is indistinguishable
                                             #   from having no limiter
# ⭐ A local in-process fallback limiter (a rough per-pod cap) is a good
#   middle ground: not exact, but not unlimited either.
```

# Part 6 — ⭐ Choosing, and where to enforce

```
⭐⭐ THE DECISION TABLE:

⭐   NEED                                   ALGORITHM
⭐   cheap, generous limit, trusted client   ⭐ fixed window
⭐   ⭐⭐ a general API rate limit           ⭐⭐ SLIDING WINDOW COUNTER
⭐   burst tolerance + steady rate           ⭐⭐ TOKEN BUCKET
⭐   weighted cost per endpoint              ⭐⭐ token bucket (`cost`)
⭐   exactness on a low-volume, high-value   ⭐⭐ sliding window LOG
⭐     action (login, OTP, payment retry)
⭐   protect a downstream that cannot spike  ⭐ leaky bucket / GCRA
⭐   monthly quota, not a rate               ⭐⭐ NOT A RATE LIMITER —
⭐                                             a counter in Postgres
⭐                                             (Day 153: quotas are
⭐                                             billing, and billing is
⭐                                             not eventually consistent)
```

```
⭐⭐ GATEWAY OR APPLICATION? ***BOTH, FOR DIFFERENT REASONS.***
⭐   ⭐ GATEWAY (nginx, Envoy, API gateway, CDN): ⭐⭐ rejects before
⭐     your process is involved, which is the only kind of protection
⭐     that survives an actual flood. ⭐ Coarse: per-IP, per-key, per
⭐     route class.
⭐   ⭐ APPLICATION: ⭐⭐ knows the tenant, the plan, the endpoint cost
⭐     and the user's role. ⭐ It cannot save you from a flood, because
⭐     the request already reached it.
⭐   ⇒ ⭐⭐ GATEWAY FOR SURVIVAL, APPLICATION FOR POLICY. A limiter that
⭐     only exists in your app cannot protect you from the traffic that
⭐     makes you need one.
⭐ ⭐ AND TEST IT: ⭐⭐ a rate limiter with no test asserting the exact
⭐   allowed count under 500 concurrent requests is a rate limiter you
⭐   have not verified is atomic. ⭐ That test is the Day 164 pattern,
⭐   reused.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `INCR` then `EXPIRE` as two commands | A crash between them leaves a permanently-full window. One Lua script. |
| Fixed window as the only defence | It permits 2× the limit across the boundary, and clients synchronise there. |
| Sliding window log at scale | One sorted-set member per request — gigabytes recycled per minute. |
| Dismissing the log entirely | It's exactly right for login attempts and OTP sends. |
| Conflating burst tolerance with rate | Only token bucket gives you two separate dials. |
| A background refill timer for token bucket | Refill lazily from a stored timestamp; no timer, O(1). |
| Using the application's clock | App servers disagree by seconds; a fast clock is a free window. Use Redis `TIME`. |
| Reading then writing from Python | Two requests both read 99 and both allow. It must be atomic. |
| No version segment in the key | Changing the algorithm inherits stale state. |
| Only limiting per user | Ten thousand users each under their limit still take you down. |
| A tight per-IP limit | NAT and carriers put thousands of real users behind one address. |
| Consuming quota at every layer before rejecting | A rejection at layer three already burned layers one and two. |
| No `Retry-After` | A well-behaved client cannot behave well, so it retries immediately. |
| Not deciding whether rejected requests count | For abuse limits they must, or brute force gets unlimited attempts. |
| Failing open on a login limiter | That's the window an attacker waits for. |
| Failing closed on a capacity limiter | You turned a limiter outage into a total outage. |
| Only limiting in the application | The flood already reached your process. Gateway for survival. |
| No concurrency test | You haven't verified the limiter is atomic. |

## Interview questions

**Q: Implement a rate limiter. Which algorithm?**

> For a general API limit, a sliding window counter — two fixed-window counters with the previous one
> weighted by how far into the current window we are. The reason is that it has fixed-window memory,
> two integers per client, with accuracy close to an exact sliding log; Cloudflare measured the error
> well under one percent on real traffic. What it fixes is the fixed-window boundary burst: with a
> limit of a hundred a minute, a client can send a hundred at 12:00:59 and a hundred at 12:01:00 —
> two hundred requests in one second, every one of them "within the limit". And it's worse than a
> one-off, because clients that back off to the window boundary synchronise there, so the spike
> repeats every minute. If the requirement includes burst tolerance I'd use a token bucket instead,
> because it's the only one of the four that gives you capacity and rate as separate dials.

**Q: When is a token bucket the right choice?**

> When bursts are legitimate, which for an API they usually are. Capacity a hundred, refill ten a
> second means an idle client can fire a hundred requests at once — a page loading forty resources
> isn't throttled — but can't sustain more than ten a second. Every other algorithm here conflates
> burst tolerance with steady rate; token bucket separates them into two knobs. Two implementation
> points. The refill is lazy: you store tokens and a last-refill timestamp and compute the refill on
> read, so it's O(1) with no background timer. And the `cost` parameter gives you weighted limiting
> almost free — a search costs ten tokens and a health check costs one — so one limiter can price
> endpoints by expense. It also computes an exact `Retry-After` for you, since you know the deficit
> and the refill rate. The smooth cousin is leaky bucket or GCRA, which permits no burst at all, and
> that's what I'd use to protect a downstream that genuinely can't absorb spikes.

**Q: What's the most commonly missed detail?**

> Using the application's clock instead of Redis's. App servers disagree by seconds — NTP drift, a VM
> resumed from suspend, a container with a skewed clock — and a client routed to a pod whose clock
> runs three seconds fast gets a free window. Redis is one machine, so `redis.call("TIME")` inside the
> script is at least consistent for all callers, which is the property the algorithm actually needs.
> The historical caveat is that on older Redis, `TIME` made a script non-deterministic and was
> disallowed under command-based replication; modern Redis replicates effects so it's fine, but it's
> worth checking the version rather than assuming. The second most missed detail is the global or
> per-tenant occupancy limit: everyone builds per-user limits, and ten thousand users each comfortably
> under theirs will still take the service down.

**Q: Redis is down. Does your rate limiter allow or reject?**

> It depends on what the limiter is for, and that's a decision to make explicitly at design time
> rather than discover in an incident. Capacity limiters fail open — rejecting all traffic because the
> limiter is unavailable is a self-inflicted outage, and the thing you were protecting against might
> not even be happening. Security limiters — login, OTP, password reset — fail closed, because an
> unlimited brute-force window is worse than downtime, and it's precisely the window an attacker will
> wait for. In both cases I'd emit a metric and alert, because a limiter that silently fails open is
> indistinguishable from not having one, and you'll find out months later. A local in-process fallback
> is a good middle ground for the capacity case: a rough per-pod cap isn't exact but it isn't
> unlimited either.

**Q: Where do you enforce rate limits?**

> Both at the gateway and in the application, for different reasons. The gateway — nginx, Envoy, a CDN
> or an API gateway — rejects before your process is involved, and that's the only kind of protection
> that survives an actual flood, because a limiter that lives only in your app has already spent a
> worker and a connection on the request it's about to reject. But the gateway only knows coarse
> dimensions: IP, API key, route class. The application knows the tenant, the plan, the user's role
> and how expensive the specific endpoint is, which is where the actual policy lives. So: gateway for
> survival, application for policy. And whichever you build, I'd want a test that fires five hundred
> concurrent requests and asserts the exact allowed count — because without it you haven't verified
> the thing that matters, which is that the check-and-decrement is atomic.

## 🎙️ Articulation drill

**Two minutes: "How would you build a rate limiter?"**

Open with the flaw in the obvious answer, because that's the fastest way to show you've built one:
**a fixed-window counter lets a client send twice the limit in a two-second span, and clients backing
off to the boundary synchronise there so it repeats every minute.** Then the four algorithms with a
number attached to each — the log is exact but costs one sorted-set member per request, which is
gigabytes a minute at scale; the sliding window counter interpolates two counters for fixed-window
memory and sub-one-percent error, and it's the default answer; the token bucket separates burst
capacity from steady rate, which is what an API actually wants, and gives you an exact `Retry-After`
for free. Then the three details that decide whether it works at all: **it must be one atomic Lua
script**, **it must use Redis's clock because app servers disagree by seconds**, and **there must be a
global or per-tenant cap, because ten thousand users each under their limit still take you down.**
Close on the operational half: always send `Retry-After`, fail open for capacity and closed for login,
and put a coarse limit at the gateway because a limiter inside your app has already spent a worker on
the request it's rejecting.
