# Day 360 📦

**P-360** · 📦 **Why containers** — ⭐⭐ and what they are not

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a container is not a small virtual machine — it is one or more ordinary
> Linux processes on the host kernel, with a restricted view of the filesystem, the network and the
> process table, and almost every container surprise you will ever hit comes from forgetting that
> second half of the sentence.**

# Part 2 — ⭐⭐ The problem containers actually solve

```
⭐⭐ NOT "IT WORKS ON MY MACHINE" — ⭐ that is the marketing
⭐   version. ⭐⭐ THE REAL PROBLEM IS THIS:

⭐   ***A DEPLOYABLE UNIT USED TO BE "SOME FILES, PLUS A LIST OF
⭐      THINGS THAT MUST ALREADY BE TRUE ABOUT THE MACHINE."***
⭐   ⭐ Python 3.11 with these exact wheels. ⭐ libpq installed.
⭐   ⭐ ImageMagick at this version. ⭐ These env vars. ⭐ This
⭐     user. ⭐ This directory writable.
⭐   ⇒ ⭐⭐ THAT LIST WAS NEVER WRITTEN DOWN COMPLETELY, AND IT
⭐     DRIFTED — so "staging works, production doesn't" was a
⭐     week of archaeology, every time.

⭐⭐ A CONTAINER IMAGE MAKES THE LIST ***EXECUTABLE AND
⭐   VERSIONED***:
⭐   ⭐ Filesystem, interpreter, libraries, entrypoint, user,
⭐     env — ⭐⭐ ALL IN ONE IMMUTABLE ARTEFACT WITH A DIGEST.
⭐   ⇒ ⭐⭐ THE REAL WIN IS NOT ISOLATION. IT IS THAT
⭐     ***THE ARTEFACT IS THE SAME BYTES IN CI, STAGING AND
⭐     PRODUCTION*** — which is what makes "promote the digest"
⭐     (Day 283) a meaningful sentence rather than a slogan.

⭐⭐ AND THE PYTHON-SPECIFIC VERSION, WHICH IS SHARPER THAN
⭐   JAVA'S:
⭐   ⭐ Java ships a JAR that mostly runs anywhere with a JVM.
⭐   ⭐ ⭐⭐ PYTHON'S DEPENDENCIES INCLUDE ***COMPILED C
⭐     EXTENSIONS*** — `psycopg`, `numpy`, `Pillow`, `lxml`,
⭐     `cryptography` — which are built against a specific
⭐     libc, OpenSSL and CPython ABI.
⭐   ⇒ ⭐⭐ A `requirements.txt` IS NOT A DEPLOYABLE ARTEFACT.
⭐     IT IS A ***RECIPE THAT MAY PRODUCE DIFFERENT BINARIES ON
⭐     DIFFERENT MACHINES.*** ⭐ Containers are what turn it
⭐     back into an artefact, and this is a genuinely better
⭐     answer than the generic one.
```

# Part 3 — ⭐⭐ Container vs VM: the sentence and the consequences

```
⭐⭐ ***A VM VIRTUALISES HARDWARE AND RUNS ITS OWN KERNEL.
⭐      A CONTAINER SHARES THE HOST KERNEL AND VIRTUALISES THE
⭐      ***VIEW***.***

⭐⭐ WHAT FOLLOWS — SIX CONSEQUENCES, AND THE LAST THREE ARE
⭐   THE ONES THAT BITE:
⭐   ① ⭐ START-UP: milliseconds vs tens of seconds. ⭐ It is a
⭐        `fork`+`exec`, not a boot.
⭐   ② ⭐ OVERHEAD: near zero vs a whole OS per instance.
⭐   ③ ⭐ DENSITY: hundreds per host vs tens.
⭐   ④ ⭐⭐ ***ISOLATION IS WEAKER.*** ⭐ A kernel vulnerability
⭐        is a container escape. ⭐⭐ VMs HAVE A HARDWARE
⭐        BOUNDARY; CONTAINERS HAVE A ***SOFTWARE*** ONE.
⭐   ⑤ ⭐⭐ ***YOU CANNOT RUN A DIFFERENT KERNEL.*** ⭐ No Linux
⭐        containers on a Windows kernel — ⭐⭐ WHICH IS WHY
⭐        DOCKER DESKTOP ON MACOS AND WINDOWS RUNS A HIDDEN
⭐        LINUX VM, and why file I/O across that boundary is
⭐        slow enough to change how you work.
⭐   ⑥ ⭐⭐ ***HOST KERNEL SETTINGS ARE SHARED.*** ⭐ `somaxconn`,
⭐        file-descriptor limits, TCP tuning, ⭐ and the OOM
⭐        killer — ⭐⭐ THEY BELONG TO THE HOST, NOT TO YOU.

⭐⭐ THE SECURITY CONSEQUENCE STATED PLAINLY:
⭐   ***CONTAINERS ARE AN ISOLATION ***CONVENIENCE***, NOT A
⭐      SECURITY BOUNDARY FOR UNTRUSTED CODE.***
⭐   ⇒ ⭐ Running a customer's arbitrary Python in a container
⭐     on your host is ⭐⭐ NOT SAFE ⭐ — that needs gVisor,
⭐     Firecracker or a real VM. ⭐ Saying this unprompted is a
⭐     strong signal, because most people assert the opposite.
```

# Part 4 — ⭐⭐ What a container actually is: five primitives

```
⭐⭐ THERE IS NO "CONTAINER" OBJECT IN THE LINUX KERNEL. ⭐ There
⭐   are five features, combined by a runtime:
⭐   ① ⭐⭐ ***NAMESPACES*** — restrict what a process can
⭐        ***see***: PID, mount, network, UTS, IPC, user,
⭐        cgroup.
⭐   ② ⭐⭐ ***CGROUPS*** — restrict what it can ***use***: CPU,
⭐        memory, I/O, PIDs.
⭐   ③ ⭐ ***UNION FILESYSTEM*** (overlayfs) — layered images
⭐        with a copy-on-write writable layer.
⭐   ④ ⭐ ***CAPABILITIES + SECCOMP + LSM*** — restrict what it
⭐        can ***do***: which syscalls, which privileged
⭐        operations.
⭐   ⑤ ⭐ ***OCI RUNTIME*** — `runc` assembles all of the above
⭐        and `exec`s your process.
⭐   ⇒ ⭐⭐ SAY THIS LIST AND THE INTERVIEW MOVES ON. ⭐ Day 361
⭐     goes into ① and ② properly, because that is where the
⭐     production surprises live.

⭐⭐ AND THE VOCABULARY THAT PEOPLE MUDDLE:
⭐   ⭐ ***IMAGE*** — an immutable, layered filesystem plus
⭐     metadata (entrypoint, env, user, exposed ports).
⭐   ⭐ ***CONTAINER*** — a running process with a writable
⭐     layer on top of an image.
⭐   ⭐ ⭐⭐ ***REGISTRY*** — where images live. ⭐ A ***TAG*** is
⭐     a mutable pointer; ⭐⭐ A ***DIGEST*** IS THE CONTENT
⭐     HASH AND IS THE ONLY THING THAT IDENTIFIES AN IMAGE
⭐     (Day 362).
⭐   ⭐ ***DOCKER*** is one implementation. ⭐ `containerd`,
⭐     `podman`, `runc` and `buildkit` are the pieces —
⭐     ⭐ and Kubernetes stopped using Docker as its runtime
⭐     years ago, which surprises people who conflate the two.
```

# Part 5 — ⭐⭐ What containers do *not* solve

```
⭐⭐ SAY THIS SECTION UNPROMPTED. IT IS WHERE JUDGEMENT SHOWS.

⭐⭐ ① ***THEY DO NOT MAKE A BAD APPLICATION GOOD.*** ⭐ A
⭐      process that leaks memory leaks it in a container —
⭐      ⭐⭐ AND NOW IT GETS OOMKILLED WITH LESS WARNING (Day
⭐      361), because the limit is lower and enforced.
⭐⭐ ② ***THEY DO NOT GIVE YOU STATE MANAGEMENT.*** ⭐ The
⭐      writable layer is ephemeral by design. ⭐⭐ ANYTHING
⭐      WRITTEN INSIDE A CONTAINER IS GONE ON RESTART — which
⭐      is Day 324's local-filesystem lesson with an enforcement
⭐      mechanism attached.
⭐⭐ ③ ***THEY DO NOT SOLVE CONFIGURATION.*** ⭐ You still need
⭐      to decide what is baked in and what is injected
⭐      (Day 364, Day 372).
⭐⭐ ④ ***THEY DO NOT REPLACE DEPENDENCY MANAGEMENT.*** ⭐ An
⭐      unpinned `pip install` in a Dockerfile produces a
⭐      ***different image every build***, ⭐⭐ WHICH DESTROYS
⭐      THE ONE PROPERTY YOU ADOPTED CONTAINERS FOR.
⭐⭐ ⑤ ***THEY DO NOT MAKE YOU CLOUD-PORTABLE.*** ⭐ Your image
⭐      is portable; ⭐⭐ YOUR IAM ROLES, LOAD BALANCERS,
⭐      MANAGED DATABASE AND SECRET STORE ARE NOT.
⭐⭐ ⑥ ***THEY DO NOT REDUCE COMPLEXITY. THEY MOVE IT.*** ⭐ You
⭐      traded "which Python is on this box" for "which base
⭐      image, which registry, which scanner, which orchestrator,
⭐      which network plugin". ⭐⭐ THAT TRADE IS USUALLY WORTH
⭐      IT AND IT IS STILL A TRADE.
```

# Part 6 — ⭐ When *not* to containerise

```
⭐⭐ THE ANSWER THAT SEPARATES YOU FROM A CHECKLIST:
⭐   ⭐ ✘ ***A SINGLE SCRIPT ON A SINGLE VM*** with no
⭐     dependencies beyond the standard library ⇒ ⭐ a systemd
⭐     unit and a cron entry. ⭐⭐ CONTAINERISING IT ADDS A
⭐     REGISTRY, A BUILD AND A RUNTIME TO SAVE NOTHING.
⭐   ⭐ ✘ ***DESKTOP OR GUI SOFTWARE*** — possible, painful,
⭐     rarely worth it.
⭐   ⭐ ✘ ⭐⭐ ***EXTREME I/O OR LATENCY WORK*** where the
⭐     network namespace and overlay filesystem cost measurable
⭐     percentages. ⭐ Rare, real, and measurable.
⭐   ⭐ ✘ ***A TEAM WITH NO PIPELINE.*** ⭐⭐ CONTAINERS WITHOUT
⭐     AUTOMATED BUILDS ARE JUST A HARDER WAY TO COPY FILES,
⭐     ⭐ and the team ends up building images by hand on a
⭐     laptop, which is worse than what they had.
⭐   ⭐ ✔ ⭐⭐ AND THE STATEFUL CASE, CAREFULLY: DATABASES ***IN***
⭐     CONTAINERS ARE FINE FOR DEV AND A DELIBERATE DECISION IN
⭐     PRODUCTION — ⭐ the storage, backup, failover and upgrade
⭐     story is the hard part, not the packaging, ⭐⭐ AND A
⭐     MANAGED DATABASE USUALLY WINS ON EXACTLY THOSE FOUR
⭐     POINTS.
```

# Part 7 — ⭐ The mental model to keep

```
⭐⭐ FOUR SENTENCES THAT WILL SERVE YOU FOR THE WHOLE STAGE:
⭐   ① ⭐⭐ ***IT IS A PROCESS.*** ⭐ `ps aux` on the host shows
⭐      it. `kill` works on it. ⭐ It has a PID on the host and
⭐      a different PID inside.
⭐   ② ⭐⭐ ***THE IMAGE IS THE CONTRACT; THE CONTAINER IS THE
⭐      EXECUTION.*** ⭐ Debug image problems by inspecting
⭐      layers; debug container problems by inspecting the
⭐      process.
⭐   ③ ⭐⭐ ***ANYTHING NOT IN A VOLUME IS TEMPORARY.***
⭐   ④ ⭐⭐ ***THE HOST KERNEL IS SHARED, SO THE HOST'S LIMITS,
⭐      CLOCK, AND OOM KILLER ARE YOURS TOO.***

⭐⭐ AND THE ONE COMMAND THAT MAKES IT CONCRETE:
⭐   ⭐ `docker run --rm -d --name x python:3.12-slim sleep 300`
⭐   ⭐ `ps -ef | grep sleep` ***on the host*** ⇒ ⭐⭐ THERE IT
⭐     IS, AN ORDINARY PROCESS WITH AN ORDINARY PID.
⭐   ⭐ `docker exec x ps -ef` ⇒ ⭐⭐ THE SAME PROCESS, CALLING
⭐     ITSELF PID 1.
⭐   ⇒ ⭐⭐ ONE PROCESS, TWO PIDs. ⭐ That single observation
⭐     dissolves most container confusion permanently, and it is
⭐     the thing to run before reading Day 361.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ "A container is a lightweight VM" | It shares the host kernel. No own kernel, weaker isolation, shared sysctls and OOM killer |
| ⭐⭐ Treating a container as a security boundary for untrusted code | A kernel bug is an escape. That needs gVisor, Firecracker or a real VM |
| ⭐⭐ Unpinned `pip install` in a Dockerfile | A different image every build — destroying the reproducibility you adopted containers for |
| ⭐ Writing data inside the container | The writable layer is ephemeral by design. Volumes or object storage |
| ⭐ Assuming portability means cloud portability | The image is portable; your IAM, load balancer and secret store are not |
| ⭐⭐ Containerising with no build pipeline | A harder way to copy files, built by hand on someone's laptop |
| ⭐ Conflating Docker with containers | Docker is one implementation; Kubernetes hasn't used it as a runtime for years |
| ⭐ Treating a tag as an identity | Tags are mutable pointers. The digest is the identity |
| ⭐⭐ Expecting containers to reduce complexity | They move it — from "which Python is on this box" to a registry, scanner and orchestrator |

## Interview questions

**1. "What is a container?"**
> ⭐⭐ One or more ordinary Linux processes on the host kernel, with a restricted view of the filesystem,
> network and process table — **namespaces restrict what it can see, cgroups restrict what it can use,
> capabilities and seccomp restrict what it can do**, and an overlay filesystem gives it a layered
> image with an ephemeral writable layer. ⭐ There's no "container" object in the kernel; there's a
> runtime assembling five features and calling `exec`.

**2. "Container or VM?"**
> ⭐ Containers for application workloads: millisecond starts, near-zero overhead, hundreds per host,
> and one artefact that's byte-identical across CI, staging and production. ⭐⭐ VMs when you need a
> different kernel, or **a real security boundary** — because a container's isolation is software, so a
> kernel vulnerability is an escape. ⭐ Running untrusted customer code in a plain container on your
> host isn't safe; that's what gVisor and Firecracker exist for.

**3. "What problem do containers actually solve, for Python specifically?"**
> ⭐ Not "works on my machine" — ⭐⭐ **a deployable unit used to be some files plus an unwritten list of
> things that had to already be true about the machine**, and that list drifted. ⭐ The Python version
> is sharper than most: **dependencies include compiled C extensions built against a specific libc,
> OpenSSL and CPython ABI**, so a `requirements.txt` is a recipe that can produce different binaries on
> different machines. ⭐ The container turns it back into an artefact with a digest.

**4. "What don't containers solve?"**
> ⭐ They don't fix a bad application — ⭐⭐ **a leak still leaks, and now it's OOMKilled sooner because
> the limit is real.** ⭐ They don't manage state; anything outside a volume is gone on restart. They
> don't solve configuration or dependency pinning. They don't make you cloud-portable — your image is,
> your IAM and load balancer aren't. ⭐⭐ And they don't reduce complexity, they relocate it.

**5. "When would you not containerise?"**
> ⭐ A single stdlib-only script on one VM — a systemd unit and a cron entry, because containerising it
> adds a registry, a build and a runtime to save nothing. ⭐ Latency-critical work where the network
> namespace and overlay cost measurable percentages. ⭐⭐ And **a team with no build pipeline**, because
> containers without automated builds are a harder way to copy files, and you end up with images built
> by hand on a laptop.

**6. "Would you run Postgres in a container?"**
> ⭐ In development, always. ⭐ In production, it's a deliberate decision and the packaging isn't the
> hard part — ⭐⭐ **storage, backup, failover and version upgrades are**, and a managed database
> usually wins on exactly those four. ⭐ If I did run it myself I'd want persistent volumes with known
> IOPS, a tested restore, and an upgrade path I'd rehearsed — and at that point I'd ask what I'm
> actually saving.

## 🎙️ Articulation drill

**Two minutes.** Define it precisely and refuse the lightweight-VM framing: **a container is one or
more ordinary Linux processes on the host kernel with a restricted view** — namespaces for what it can
see, cgroups for what it can use, capabilities and seccomp for what it can do, and an overlay
filesystem underneath. Then say what problem it actually solved, which isn't "works on my machine":
**a deployable unit used to be some files plus an unwritten list of things that had to already be true
about the machine, and that list drifted.** Give the Python sharpening, because it's more specific than
the generic answer: **compiled C extensions are built against a particular libc, OpenSSL and CPython
ABI, so a requirements file is a recipe that can produce different binaries** — the image is what turns
it back into an artefact with a digest. Then the consequences of the shared kernel, and lead with the
uncomfortable one: **isolation is software, so a kernel bug is an escape, and containers are an
isolation convenience rather than a security boundary for untrusted code.** Close on judgement, because
that's what's actually being tested: **they don't fix a leaking application, they don't manage state,
they don't make you cloud-portable, and they don't reduce complexity — they move it** — and a
stdlib-only script on one VM should stay a systemd unit.
