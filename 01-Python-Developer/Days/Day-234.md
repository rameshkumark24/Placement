# Day 234 🖥️

**P-234** · 🖥️ **Rendering strategies** — ⭐⭐ CSR, SSR, SSG, ISR, RSC, and the question that picks one

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every rendering strategy is answering one question — *when* does the HTML
> get built, and *where* — and the correct answer per route follows from two facts you already know
> about your data: how often it changes, and whether it is the same for everyone.**
>
> Today: the five strategies, ⭐ hydration and its cost, ⭐⭐ the decision table, and server components.

---

# Part 1 — The five, in one table

| | ⭐ HTML built | Where | ⭐ Good for | ⭐⭐ The cost |
|---|---|---|---|---|
| **CSR** | In the browser, after JS loads | Client | Dashboards behind a login | ⭐⭐ Blank screen until JS parses. **Bad SEO, bad on slow phones.** |
| **SSR** | Per request | Server | Personalised, always-fresh pages | ⭐ Server CPU per request; TTFB is your API's latency |
| **SSG** | At build time | Build | Docs, marketing, blogs | ⭐⭐ Stale until you rebuild. A 10k-page rebuild is slow. |
| **ISR** | Build, then re-built in the background on a timer | Build + server | Catalogues, listings | ⭐ Users can see stale content for up to the revalidation window |
| **RSC** | ⭐ On the server, streamed, **no JS shipped for those components** | Server | ⭐⭐ Data-heavy pages | ⭐ New mental model; a hard client/server boundary |

```
⭐⭐ THE TWO QUESTIONS THAT DECIDE IT

⭐   ① ⭐ IS THIS PAGE THE SAME FOR EVERYONE?
⭐        YES ⇒ SSG or ISR (⭐⭐ cache it at the CDN, serve it in 20 ms)
⭐        NO  ⇒ SSR or CSR
⭐   ② ⭐ HOW STALE CAN IT BE?
⭐        forever ⇒ SSG      ·  minutes ⇒ ISR
⭐        seconds ⇒ SSR      ·  live    ⇒ CSR + polling/websocket

⭐   ⇒ ⭐⭐ IT IS A CACHE-FRESHNESS DECISION, NOT A FRAMEWORK
⭐     PREFERENCE — and you have been making it since Stage 5.
⭐   ⇒ ⭐ IT IS PER-ROUTE. A marketing page and a dashboard in the
⭐     same app should NOT use the same strategy.
```

# Part 2 — ⭐ Hydration, and what it actually costs

```
⭐⭐ SSR IS TWO PHASES, AND PEOPLE ONLY COUNT THE FIRST

⭐   ① server sends HTML ⇒ ⭐ USER SEES CONTENT FAST ✅
⭐   ② browser downloads JS, ⭐⭐ RE-RUNS EVERY COMPONENT, and
⭐      attaches event listeners  ⇒ ⭐ THE PAGE IS **VISIBLE BUT
⭐      NOT INTERACTIVE** IN BETWEEN.

⭐   ⇒ ⭐⭐ THE UNCANNY VALLEY: the button is on screen and clicking
⭐     it does NOTHING. Users click three times, then rage-click.
⭐   ⇒ ⭐ SSR IMPROVES *PERCEIVED* LOAD AND CAN MAKE TIME-TO-
⭐     INTERACTIVE **WORSE**, because you now ship HTML *and* JS.
```

| ⭐ Hydration mismatch | ⭐⭐ A real, common bug |
|---|---|
| `new Date()` / `Math.random()` in render | ⭐⭐ Server and client disagree ⇒ React warns and **discards the server HTML**, re-rendering from scratch |
| `window` / `localStorage` accessed during render | ⭐ Crashes on the server — it does not exist there |
| Content that depends on the user, rendered statically | ⭐⭐ The wrong name, cached at the CDN, **shown to a different user** |

> ⭐⭐ **That last row is a real security incident shape**, not a rendering bug. Anything user-specific
> must never be produced by a route that a shared cache can store — and this is exactly Day 454's
> "cache key that bypasses the permission filter", now at the HTML layer.

# Part 3 — Server components

```jsx
// ⭐ SERVER COMPONENT (the default in the App Router)
async function OrderList() {
  const orders = await db.query("SELECT ...");   // ⭐⭐ runs on the SERVER
  return <ul>{orders.map(o => <li key={o.id}>{o.total}</li>)}</ul>;
}
// ⇒ ⭐⭐ ZERO JAVASCRIPT SHIPPED for this component.
//    ⭐ It cannot use useState, useEffect, or onClick.

"use client";                              // ⭐ opt back in, explicitly
function AddButton() {                     // ⭐ ships JS, can hold state
  const [busy, setBusy] = useState(false);
  return <button onClick={...}>Add</button>;
}
```

| ⭐ Server component | ⭐ Client component |
|---|---|
| ✅ `await` a database, read a secret, use a big library for free | ✅ `useState`, effects, event handlers, browser APIs |
| ❌ No state, no effects, no `onClick` | ❌ ⭐⭐ **Everything it imports ships to the browser** |
| ⭐⭐ Bundle cost: **zero** | ⭐ Bundle cost: itself + its whole import tree |

```
⭐⭐ THE RULE THAT KEEPS THIS SANE
⭐   PUSH "use client" AS FAR DOWN THE TREE AS POSSIBLE.
⭐   ⭐ A "use client" at the top of a page makes the ENTIRE PAGE
⭐     a client component and you have gained nothing.
⭐   ⇒ ⭐⭐ SERVER COMPONENTS CAN RENDER CLIENT ONES AS children,
⭐     so the interactive LEAVES ship JS and the data-heavy TRUNK
⭐     does not.
```

> ⭐⭐ **The security note that matters most.** A server component can read secrets and query the
> database directly — which means **a mistaken `"use client"` on a file that touches a secret ships
> that secret to the browser** (Day 222). Keep secret-touching code in files that can never be
> client-side, and check it in review. `server-only` as an import is the guard.

# Part 4 — Streaming

```jsx
<Suspense fallback={<Skeleton />}>
  <SlowRecommendations />        {/* ⭐⭐ streams in when ready */}
</Suspense>
```

> ⭐ **Streaming removes the "slowest query decides the whole page" problem.** The shell and fast
> content arrive immediately; slow sections fill in. **This is Day 456's degradation ladder as a
> rendering feature** — the page is useful before it is complete.

```
⭐⭐ WHAT TO PICK, FOR THE FLAGSHIP YOU ARE BUILDING
⭐   marketing / landing   ⇒ SSG    (same for everyone, rarely changes)
⭐   docs                  ⇒ SSG
⭐   public catalogue      ⇒ ISR    (same for everyone, changes hourly)
⭐   ⭐ THE DASHBOARD       ⇒ ⭐⭐ CSR OR RSC BEHIND AUTH — it is
⭐                            per-user, so it CANNOT be shared-cached
⭐   an admin panel        ⇒ CSR    (SEO irrelevant, always fresh)
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you choose a rendering strategy?"**

Reframe it as something you already know. **Every strategy answers one question: when is the HTML
built, and where. And I pick per route from two facts about the data — is this page the same for
everyone, and how stale can it be. Same for everyone and rarely changing is static, cached at the CDN
and served in twenty milliseconds. Per-user is server-rendered or client-rendered, because it can't be
shared-cached at all. It's a cache-freshness decision, not a framework preference.**

Then the cost people skip. **SSR is two phases and everyone counts only the first. The server sends
HTML so content appears fast, then the browser downloads the JS and re-runs every component to attach
handlers. In between, the page is visible but not interactive — the button is there and clicking does
nothing. So SSR improves perceived load and can make time-to-interactive worse, because now I ship HTML
and JS.**

Then the one that is actually a security answer. **A personalised page rendered by a route a shared
cache can store is an incident, not a rendering bug — you serve one user's name to another. That's the
same failure as a cache key that bypasses a permission filter, one layer up.**

Close on server components. **They ship zero JavaScript and can query the database directly, so the
data-heavy trunk costs nothing and only the interactive leaves ship code. The discipline is pushing
`"use client"` as far down as possible — at the top of a page it makes the whole page a client
component and you've gained nothing. And because server components can read secrets, a mistaken
`"use client"` on the wrong file ships one to the browser.**
