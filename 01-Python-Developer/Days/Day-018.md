# Day 018

**L-018** · ⭐⭐ **WebSockets vs SSE vs long-polling** — the decision table
**C-12** · Proxies, reverse proxies, load balancers (L4 vs L7), CDN

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: pick the weakest mechanism that solves the problem.** A WebSocket is
> more capable than SSE, and *that is a cost* — it gives up statelessness, it needs heartbeats and
> reconnect logic, and it pins a client to a process. **Most "real-time" features are one-directional
> and should be SSE.**

---

# Part 1 — ⭐⭐ The decision table

| | ⭐ Short polling | ⭐ Long polling | ⭐⭐ SSE | ⭐⭐ WebSocket |
|---|---|---|---|---|
| Direction | request/response | request/response | ⭐⭐ **server → client only** | ⭐⭐ **both, any time** |
| Protocol | HTTP | HTTP | ⭐ HTTP (a streaming response) | ⭐ ws:// after a 101 |
| ⭐ Latency | ⭐⭐ up to the interval | ~immediate | ~immediate | ~immediate |
| ⭐ Efficiency | ⭐⭐ terrible | poor | ⭐ good | ⭐⭐ best |
| ⭐⭐ Auto-reconnect | n/a | manual | ⭐⭐ **built into the browser** | ⭐ you write it |
| Works through old proxies | ⭐ always | usually | ⭐ usually | ⚠️ sometimes not |
| ⭐ Complexity | trivial | ⭐ moderate | ⭐ **low** | ⭐⭐ high |
| ⭐ Binary | no | no | ⭐⭐ **no — text only** | yes |
| HTTP/2 multiplexed | yes | yes | ⭐ yes | ⭐⭐ no — its own connection |

```
⭐⭐ THE DECISION, IN FOUR LINES:
⭐   Does the CLIENT need to send frequently, at any moment?     ⇒ ⭐⭐ WEBSOCKET
⭐   Server → client only (feeds, notifications, progress, logs)? ⇒ ⭐⭐ SSE
⭐   Rare updates, and staleness is acceptable?                   ⇒ ⭐ POLLING (and it is FINE)
⭐   Stuck with an ancient proxy and need push?                   ⇒ ⭐ LONG POLLING
```

⭐⭐ **Say "polling is fine" out loud when it is true.** A dashboard refreshing every 30 seconds does
not need a persistent connection, and reaching for WebSockets there is the kind of over-engineering a
design round is specifically looking for.

# Part 2 — ⭐⭐ SSE — the underrated one

```
⭐ Content-Type: text/event-stream        ⭐ and then the response NEVER ENDS.

event: message
data: {"user":"ada","text":"hello"}
                                         ⭐⭐ ← BLANK LINE terminates an event

id: 42                                   ⭐⭐ the browser remembers this
data: another message

retry: 5000                              ⭐ reconnect delay in ms
: this is a comment, often used as a keepalive
```

```python
# ⭐⭐ SSE in FastAPI is a generator. That is the whole implementation.
from fastapi.responses import StreamingResponse
import asyncio, json

async def events():
    while True:
        msg = await queue.get()
        yield f"data: {json.dumps(msg)}\n\n"      # ⭐⭐ TWO newlines end an event. One is a bug.

@app.get("/stream")
async def stream():
    return StreamingResponse(events(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache",
                                      "X-Accel-Buffering": "no"})   # ⭐⭐ tell nginx not to buffer
```

```js
// ⭐ The client is three lines and reconnects by itself.
const es = new EventSource("/stream");
es.onmessage = (e) => console.log(JSON.parse(e.data));
```

| ⭐⭐ SSE wins because | |
|---|---|
| ⭐⭐ **Automatic reconnection** | ⭐ the browser retries, and **replays from `Last-Event-ID`** — you get resumption for free |
| ⭐ It is just HTTP | ⭐ same auth, same cookies, same proxies, same logging, same CORS rules |
| ⭐ Simple server side | ⭐⭐ a generator that yields strings |
| ⭐ HTTP/2 friendly | ⭐ multiplexed with everything else |

⚠️ ⭐⭐ **The two traps, and both are real:** *(1)* **`X-Accel-Buffering: no`** — nginx buffers proxied
responses by default and your "stream" arrives all at once at the end, which is the classic "SSE
works locally, not in production"; *(2)* over **HTTP/1.1**, browsers cap ~6 connections per origin
(Day 011), so **an SSE stream open in six tabs exhausts the budget and the seventh request hangs
forever**. HTTP/2 removes this.

⭐ **Send a comment line (`: keepalive\n\n`) every 15–30 seconds** — same reason as a WebSocket
heartbeat: proxies kill idle connections.

# Part 3 — ⭐ Long polling, honestly

```
⭐ CLIENT: GET /updates?since=42
⭐ SERVER: ⭐⭐ does not answer. Holds the request open — 30 s, or until there is news.
⭐         ⇒ then responds, and the client IMMEDIATELY requests again.
```

⭐ **In async Python this is cheap** (a suspended coroutine costs a few KB), which is worth
knowing — ⚠️ **but in a synchronous WSGI deployment it is catastrophic**, because every held request
occupies a whole worker process or thread. **Twenty workers means twenty clients.** ⭐⭐ **That
asymmetry is one of the strongest practical arguments for ASGI over WSGI**, and it will return in
Stage 4.

# Part 4 — C-12 · ⭐⭐ Proxies, load balancers, CDN

```
⭐⭐ FORWARD PROXY — sits in front of the CLIENT. The SERVER does not know the real client.
⭐   corporate filtering, VPNs, scrapers.  ⭐ "a proxy protects the client"

⭐⭐ REVERSE PROXY — sits in front of the SERVER. The CLIENT does not know which server.
⭐   nginx, Traefik, an ALB.               ⭐ "a reverse proxy protects the server"
⭐   ⇒ ⭐ TLS termination (Day 009) · static files · compression · rate limiting · buffering
```

⭐⭐ **You will always run a reverse proxy in front of uvicorn**, and the reasons are worth having
ready: TLS, serving static files without waking Python, buffering slow clients so a slow reader
cannot occupy a worker, request size limits, and a place to do rate limiting before your code runs.

| | ⭐⭐ L4 (transport) | ⭐⭐ L7 (application) |
|---|---|---|
| Sees | ⭐ IPs and ports only | ⭐⭐ the full HTTP request |
| Can route on | four-tuple | ⭐ **path, host, header, cookie** |
| TLS | ⭐ passes it through | ⭐ terminates it |
| Speed | ⭐⭐ faster, less CPU | slower |
| Examples | AWS NLB, `ipvs` | ⭐ nginx, AWS ALB, Envoy |

⚠️ ⭐⭐ **The trap that recurs in Stage 12:** an **L4** balancer balances *connections*, not requests.
For anything that multiplexes many requests over one long-lived connection — **HTTP/2, gRPC,
WebSockets** — that means one backend gets the whole connection and the load is not balanced at all.
**You need an L7 balancer that understands streams.**

| ⭐ Algorithm | ⭐ Note |
|---|---|
| Round robin | ⭐ fine when requests are uniform |
| ⭐⭐ **Least connections** | ⭐ better when durations vary — usually the right default |
| ⭐ Consistent hashing | ⭐⭐ same key → same backend; **minimal reshuffling when a node leaves** (Stage 9) |
| ⚠️ Sticky sessions | ⭐⭐ a workaround for statelessness you failed to achieve (Day 016) |

⭐ **Health checks** decide which backends exist at all. ⚠️ ⭐⭐ **A health check that only proves the
process is running is nearly useless** — it must exercise the dependencies the service actually needs
(`/health` vs `/ready`), or the balancer keeps routing to a worker whose database connection died.

```
⭐⭐ CDN — a reverse proxy, geographically distributed:
⭐   · ⭐ serves cached content from the EDGE ⇒ RTT drops from 200 ms to 10 ms (Day 006)
⭐   · absorbs traffic your origin never sees ⇒ ⭐⭐ and cost: egress from a CDN is cheaper
⭐     than egress from your origin (Stage 11 puts numbers on this)
⭐   · ⭐ terminates TLS near the user ⇒ the handshake round trips are short
⭐   · ⭐⭐ CACHE INVALIDATION is the hard part ⇒ FIX: CONTENT HASHING in filenames
⭐     (app.a3f9c1.js) ⇒ a new deploy is a NEW URL ⇒ you never invalidate anything.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **WebSockets for one-way updates** | ⭐⭐ SSE: simpler, auto-reconnect, plain HTTP. |
| Dismissing polling | ⭐ For rare updates it is correct and cheapest. |
| ⭐⭐ **SSE behind nginx without `X-Accel-Buffering: no`** | ⭐⭐ Buffered — the stream arrives at the end. |
| One `\n` after `data:` | ⭐⭐ Two. Nothing is dispatched otherwise. |
| Many SSE streams over HTTP/1.1 | ⭐ Six-connection cap per origin — the seventh hangs. |
| Long polling on WSGI | ⭐⭐ One worker per held request. ASGI or don't. |
| No keepalive on a stream | ⭐ Proxies drop idle connections. |
| ⭐ L4 balancing gRPC/HTTP-2 | ⭐⭐ Balances connections, not requests — one backend gets it all. |
| Sticky sessions as a design | ⭐ It is a symptom of state in a worker's memory. |
| Health check that only pings the process | ⭐⭐ Must exercise real dependencies. |
| Invalidating CDN caches by hand | ⭐ Hash the filename; a deploy becomes a new URL. |

## Interview questions

**Q: WebSockets, SSE or polling — how do you choose?**
> By what the client needs to send. If it sends frequently and at arbitrary times — chat,
> collaborative editing, gaming — it's a WebSocket. If the flow is server-to-client only —
> notifications, a live feed, job progress, log tailing — it's SSE, which is plain HTTP, reconnects
> automatically with event-id resumption, and on the server is just a generator yielding strings. If
> updates are rare and a little staleness is acceptable, polling is genuinely the right answer and I'd
> say so. The principle is to pick the weakest mechanism that solves the problem, because the extra
> capability is paid for in operational complexity.

**Q: What does a WebSocket cost you that SSE doesn't?**
> Statelessness, first — it pins a client to one process. Then heartbeats, because proxies close idle
> connections and there's no other way to notice a dead peer; reconnect logic with backoff and jitter,
> because every deploy drops every connection simultaneously; and a pub/sub bus to deliver across
> workers. SSE reconnects itself, rides the normal HTTP stack, and gets the same auth, logging and
> CORS treatment as everything else.

**Q: Your SSE endpoint works locally and delivers nothing in production. Why?**
> Almost certainly buffering in the reverse proxy. nginx buffers proxied responses by default, so
> the stream is accumulated and delivered when it ends — which for a stream is never. Setting
> `X-Accel-Buffering: no` on the response, or `proxy_buffering off`, fixes it. The other candidate is
> the six-connections-per-origin limit on HTTP/1.1 if the user has several tabs open.

**Q: L4 or L7 load balancing?**
> L4 sees only IPs and ports, so it's fast and protocol-agnostic and can pass TLS straight through.
> L7 parses HTTP, so it can route on path, host, header or cookie, terminate TLS, and retry
> individual requests. The trap is that L4 balances *connections* — with HTTP/2, gRPC or WebSockets,
> where many requests share one long-lived connection, one backend receives all of that client's
> traffic and nothing is actually balanced. That's a real production incident, not a footnote.

**Q: How do you invalidate a CDN cache?**
> Ideally you don't. You put a content hash in the filename, so every deploy produces new URLs and the
> old entries simply age out — that turns invalidation into a non-problem and lets you cache assets
> for a year. For content that genuinely must change at a stable URL, you use short TTLs plus explicit
> purge, and accept that purges propagate at their own pace.

**Q: What makes a good health check?**
> One that fails when the service can't actually do its job. A check that only proves the process is
> listening will happily keep a worker in rotation after its database pool has died. I'd separate
> liveness — am I running, restart me if not — from readiness, which touches the dependencies and
> decides whether the balancer should send traffic. And readiness has to be cheap, because it runs
> constantly from every balancer.

## 🎙️ Articulation drill

Record two minutes: **"Add live notifications to an existing app. What do you use?"**

⭐ Ask the direction question first, out loud: **do notifications only flow server→client?** If yes,
⭐⭐ **SSE — one HTTP endpoint that yields strings, automatic browser reconnection with
`Last-Event-ID` resumption, and the same authentication, logging and proxy behaviour as every other
route.** ⭐ Then name the two traps you will hit anyway: proxy buffering, and the HTTP/1.1 connection
cap when a user has several tabs open.

⭐⭐ **Then the sentence that shows judgement rather than knowledge:** *"I would only move to
WebSockets when the client genuinely needs to push — and I would say clearly that it costs me
statelessness, heartbeats, reconnect logic and a Redis pub/sub bus for cross-worker delivery. That is
a lot of machinery to buy a direction I may not need."*
