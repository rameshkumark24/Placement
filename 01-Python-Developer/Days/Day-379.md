# Part 1 — ⭐⭐ Why infrastructure as code, and the one honest justification

```
⭐⭐ THE JUSTIFICATION THAT MATTERS (Day 286):
⭐   ***"IF THIS ACCOUNT WERE DELETED TONIGHT, HOW LONG UNTIL WE
⭐      ARE SERVING TRAFFIC AGAIN, AND HOW MUCH OF THAT DEPENDS
⭐      ON SOMEONE REMEMBERING?"***
⭐   ⇒ ⭐⭐ THAT IS THE WHOLE ARGUMENT. ⭐ Everything else —
⭐     review, drift detection, self-service — is downstream of
⭐     it.

⭐⭐ AND WHAT IaC ACTUALLY BUYS, HONESTLY:
⭐   ⭐ ⭐⭐ A ***REVIEWABLE DIFF*** BEFORE A CHANGE TO
⭐     PRODUCTION INFRASTRUCTURE. ⭐ The `plan` is the feature,
⭐     more than the `apply`.
⭐   ⭐ Reproducibility across environments from one module.
⭐   ⭐ ⭐⭐ AN ANSWER TO "WHY DOES THIS SECURITY GROUP ALLOW
⭐     0.0.0.0/0?" THAT IS A GIT BLAME RATHER THAN A GUESS.
⭐   ⭐ Deletion that is complete — ⭐⭐ CLICKOPS LEAVES ORPHANS
⭐     THAT COST MONEY FOR YEARS.

⭐⭐ AND WHAT IT DOES ***NOT*** BUY — ⭐ say this unprompted:
⭐   ⭐ ⭐⭐ IT DOES NOT MAKE YOU CLOUD-PORTABLE. ⭐ Your Terraform
⭐     is full of `aws_*` resources; moving cloud is a rewrite
⭐     either way.
⭐   ⭐ ⭐⭐ IT DOES NOT PREVENT MISTAKES — ⭐ it makes them
⭐     ***repeatable and fast***. ⭐ A bad module applied to
⭐     twelve accounts is twelve incidents.
⭐   ⭐ It does not remove the need to understand the underlying
⭐     service. ⭐⭐ TERRAFORM IS A THIN WRAPPER OVER APIs YOU
⭐     STILL HAVE TO KNOW.
```

# Part 2 — ⭐⭐ State: the whole story

```
⭐⭐ ***STATE MAPS YOUR CODE TO REAL RESOURCE IDs.***
⭐   ⭐ `aws_instance.web` ⇒ `i-0a1b2c3d`.
⭐   ⇒ ⭐⭐ WITHOUT IT, TERRAFORM CANNOT TELL "CREATE A NEW ONE"
⭐     FROM "UPDATE THE EXISTING ONE" — ⭐ it has no way to look
⭐     up what it made.

⭐⭐ FOUR CONSEQUENCES, AND EVERY TERRAFORM DISASTER IS ONE OF
⭐   THEM:
⭐   ① ⭐⭐ ***LOSE THE STATE AND YOU LOSE CONTROL.*** ⭐ The
⭐      resources still exist; ⭐ Terraform will try to
⭐      ***create them again***, ⭐ and then fail on name
⭐      conflicts or silently build a duplicate estate.
⭐   ② ⭐⭐ ***STATE CONTAINS SECRETS IN PLAIN TEXT.*** ⭐ RDS
⭐      passwords, generated keys, anything marked `sensitive`
⭐      is ***still stored***. ⭐⭐ `sensitive` ONLY HIDES IT FROM
⭐      THE ***OUTPUT***, NOT FROM THE FILE. ⭐ So the bucket
⭐      holding state must be encrypted and tightly
⭐      access-controlled, ⭐⭐ AND ANYONE WITH READ ACCESS TO
⭐      STATE HAS YOUR DATABASE PASSWORD.
⭐   ③ ⭐⭐ ***CONCURRENT WRITES CORRUPT IT.*** ⭐ Two pipelines
⭐      applying at once ⇒ ⭐⭐ HENCE ***LOCKING*** (DynamoDB, or
⭐      S3 native locking) — ⭐ and without it you will
⭐      eventually get a state file describing a reality that
⭐      never existed.
⭐   ④ ⭐ State is ***per configuration***, so its granularity
⭐      determines your blast radius (Part 4).

⭐⭐ ⇒ SO THE MINIMUM VIABLE SETUP, ALWAYS:
⭐   ⭐ Remote backend (S3/GCS/Terraform Cloud), ⭐ encrypted,
⭐   ⭐ ***versioned*** (⭐⭐ SO YOU CAN RECOVER FROM A BAD
⭐     APPLY), ⭐ with locking, ⭐ and access restricted to the
⭐     pipeline role.
⭐   ⇒ ⭐⭐ LOCAL STATE ON SOMEBODY'S LAPTOP IS THE SINGLE MOST
⭐     COMMON TERRAFORM FAILURE, AND IT IS ALWAYS DISCOVERED
⭐     WHEN THAT PERSON IS ON HOLIDAY.
```

# Part 3 — ⭐⭐ Drift, and the three ways it happens

```
⭐⭐ ***DRIFT*** = reality no longer matches state.

⭐⭐ ① ***SOMEONE CHANGED IT IN THE CONSOLE.***
⭐   ⇒ ⭐⭐ THE NEXT `apply` SILENTLY REVERTS THEIR FIX — ⭐ which
⭐     may have been a legitimate emergency change made at 3
⭐     a.m., ⭐⭐ AND REVERTING IT MID-INCIDENT IS ITS OWN
⭐     INCIDENT.
⭐   ⇒ ⭐ FIX: ⭐⭐ RUN `plan` ON A SCHEDULE AND ALERT ON A
⭐     NON-EMPTY DIFF. ⭐ That converts drift from a surprise
⭐     into a ticket. ⭐ And provide a documented break-glass
⭐     path so the console change is followed by a code change
⭐     the same week.

⭐⭐ ② ***THE PROVIDER CHANGED SOMETHING.*** ⭐ AWS adds a
⭐   default, a new field appears, ⭐ a provider upgrade
⭐   reinterprets an attribute.
⭐   ⇒ ⭐⭐ A `plan` YOU DID NOT AUTHOR SUDDENLY WANTS TO CHANGE
⭐     THINGS. ⭐ Pin provider versions, ⭐ and read the upgrade
⭐     guide rather than accepting the plan.

⭐⭐ ③ ***SOMETHING ELSE OWNS IT.*** ⭐ An autoscaler changed the
⭐   desired count; ⭐ a Kubernetes controller edited a tag.
⭐   ⇒ ⭐ `lifecycle { ignore_changes = [desired_count] }` —
⭐     ⭐⭐ WHICH IS DECLARING "THIS FIELD IS NOT MINE", AND IS
⭐     THE CORRECT ANSWER RATHER THAN A HACK.

⭐⭐ AND THE THREE OPERATIONS FOR REPAIRING STATE:
⭐   ⭐ `terraform import` ⇒ adopt an existing resource.
⭐     ⭐⭐ AND SINCE 1.5, `import` BLOCKS ARE ***PLANNABLE***,
⭐     SO ADOPTION IS REVIEWABLE RATHER THAN A BLIND COMMAND.
⭐   ⭐ ⭐⭐ `terraform state rm` ⇒ FORGET A RESOURCE ***WITHOUT
⭐     DELETING IT***. ⭐ The escape hatch when ownership moves.
⭐   ⭐ `terraform state mv` ⇒ rename without recreating.
⭐   ⇒ ⭐⭐ ALL THREE ARE SURGERY. ⭐ Back up state first — ⭐ and
⭐     versioning on the bucket is what makes that automatic.
```

# Part 4 — ⭐⭐ Structure and blast radius

```
⭐⭐ THE MISTAKE: ***ONE STATE FILE FOR EVERYTHING.***
⭐   ⭐ ⭐⭐ EVERY `plan` REFRESHES EVERY RESOURCE ⇒ TEN MINUTES
⭐     TO CHANGE A SECURITY GROUP RULE.
⭐   ⭐ ⭐⭐ AND ONE MISTAKE CAN DESTROY THE DATABASE WHILE YOU
⭐     WERE EDITING A DNS RECORD.
⭐   ⭐ Everyone contends on one lock.

⭐⭐ THE SPLIT THAT WORKS — ***BY RATE OF CHANGE AND BY BLAST
⭐   RADIUS***:
⭐   ⭐ ***FOUNDATION*** (VPC, subnets, IAM roles) — ⭐ changes
⭐     rarely, ⭐⭐ CATASTROPHIC IF WRONG.
⭐   ⭐ ***DATA*** (RDS, S3, ElastiCache) — ⭐ changes rarely,
⭐     ⭐⭐ IRREPLACEABLE.
⭐   ⭐ ***PLATFORM*** (cluster, load balancers) — ⭐ occasional.
⭐   ⭐ ***APPLICATION*** (services, DNS, alarms) — ⭐ changes
⭐     daily, ⭐ low blast radius.
⭐   ⇒ ⭐⭐ THE DAILY-CHANGE LAYER MUST NOT SHARE A STATE FILE
⭐     WITH THE IRREPLACEABLE ONE. ⭐ That is the whole principle,
⭐     and it is the same argument as separating a hot path from
⭐     a durable one.
⭐   ⇒ ⭐ Layers reference each other by ***data sources or
⭐     remote state outputs***, not by hard-coded IDs.

⭐⭐ MODULES:
⭐   ⭐ ⭐⭐ WRITE A MODULE WHEN YOU HAVE THE ***THIRD***
⭐     COPY-PASTE, NOT THE FIRST. ⭐ A premature module with
⭐     twenty variables is harder to read than the resources it
⭐     wraps.
⭐   ⭐ ⭐⭐ AND THE MODULE RULE THAT MATTERS: ***A MODULE SHOULD
⭐     ENCODE A DECISION, NOT JUST GROUP RESOURCES.*** ⭐ "Our
⭐     standard service: ECS task, ALB rule, log group, alarms,
⭐     IAM role" is a decision. ⭐ A module that wraps one
⭐     resource with pass-through variables is indirection with
⭐     no benefit.
⭐   ⭐ Pin module and provider versions.

⭐⭐ AND ENVIRONMENTS: ⭐⭐ DIRECTORIES WITH SEPARATE STATE, NOT
⭐   `terraform workspace`. ⭐ Workspaces share one configuration
⭐   and one backend key structure, ⭐⭐ SO PRODUCTION AND DEV
⭐   DIFFER ONLY BY A VARIABLE — ⭐ and a mistyped `-var` applies
⭐   dev's plan to production.
```

# Part 5 — ⭐⭐ Terraform in a pipeline

```
⭐⭐ THE FLOW:
⭐   ⭐ PR ⇒ `fmt -check` · `validate` · `tflint` ·
⭐     ⭐⭐ `tfsec`/`checkov` (SECURITY POLICY AS A GATE) ·
⭐     ⭐ `plan` ⇒ ⭐⭐ ***POST THE PLAN AS A PR COMMENT.***
⭐   ⭐ Merge ⇒ `apply` with ⭐⭐ THE ***SAVED PLAN FILE***, not
⭐     a fresh plan.
⭐   ⇒ ⭐⭐ BECAUSE A FRESH PLAN AT APPLY TIME CAN DIFFER FROM
⭐     THE ONE THAT WAS REVIEWED — ⭐ someone else merged, or
⭐     reality drifted. ⭐⭐ APPLYING A SAVED PLAN IS THE ONLY WAY
⭐     "APPROVED" MEANS ANYTHING.

⭐⭐ THE FIVE RULES:
⭐   ① ⭐⭐ NEVER `apply` FROM A LAPTOP TO PRODUCTION. ⭐ The
⭐      pipeline holds the credentials (OIDC, Day 369) and the
⭐      audit trail.
⭐   ② ⭐⭐ ***REVIEW THE PLAN, NOT JUST THE CODE.*** ⭐ The code
⭐      diff says what you changed; ⭐⭐ THE PLAN SAYS WHAT WILL
⭐      HAPPEN — AND THE INTERESTING WORD IS ***REPLACE***.
⭐   ③ ⭐⭐ ***`-/+ MUST BE REPLACED` IS THE LINE TO READ.*** ⭐ It
⭐      means destroy-then-create. ⭐⭐ ON AN RDS INSTANCE THAT IS
⭐      YOUR DATABASE. ⭐ On a security group it may be a brief
⭐      outage. ⭐ Add `prevent_destroy` to anything
⭐      irreplaceable.
⭐   ④ ⭐ `terraform plan -detailed-exitcode` on a schedule ⇒
⭐      drift detection (Part 3).
⭐   ⑤ ⭐⭐ NEVER RUN `terraform destroy` IN AUTOMATION AGAINST
⭐      ANYTHING THAT IS NOT AN EPHEMERAL ENVIRONMENT.

⭐⭐ AND THE TWO GUARDRAILS THAT ARE WORTH THE HOUR:
⭐   ⭐ ⭐⭐ `prevent_destroy = true` ON DATABASES, STATE BUCKETS
⭐     AND ANYTHING WITH DATA. ⭐ It turns a catastrophic plan
⭐     into an error.
⭐   ⭐ ⭐⭐ POLICY AS CODE (OPA/Sentinel/checkov) FOR RULES LIKE
⭐     "NO PUBLIC S3", "NO 0.0.0.0/0 ON PORT 22", "ENCRYPTION
⭐     REQUIRED" — ⭐ so a policy becomes a ***mechanism***
⭐     rather than a review comment somebody may forget.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Local state on a laptop | Discovered when that person is on holiday. Remote, locked, versioned, always |
| ⭐⭐ Unencrypted or widely-readable state | It contains secrets in plain text; `sensitive` only hides them from output |
| ⭐⭐ No state locking | Two concurrent applies produce a state file describing a reality that never existed |
| ⭐⭐ One state file for everything | A ten-minute plan, one lock for everyone, and a DNS edit that can destroy the database |
| ⭐ `terraform workspace` for environments | Prod and dev differ by a variable, and a mistyped `-var` applies the wrong plan |
| ⭐⭐ Applying a fresh plan rather than the reviewed one | "Approved" means nothing if the plan can change between review and apply |
| ⭐⭐ Reviewing the code diff and not the plan | The code says what changed; the plan says what will happen — and `must be replaced` is the word |
| ⭐ No `prevent_destroy` on data resources | One bad plan destroys the database, and the plan looked fine at a glance |
| ⭐ Unpinned provider versions | A plan you didn't author suddenly wants to change things |
| ⭐ Fighting an autoscaler instead of `ignore_changes` | Declaring "this field isn't mine" is the correct answer, not a hack |
| ⭐⭐ No scheduled drift detection | Console changes get silently reverted, sometimes mid-incident |
| ⭐ Modules at the first copy-paste | Twenty pass-through variables are harder to read than the resources they wrap |
| ⭐⭐ Claiming zero-downtime without a load test | It's a claim, not a property, until you deploy mid-test and count errors |
| ⭐⭐ A rollback procedure that has never been run | You don't have it |
| ⭐ No measured rebuild time | Your RTO is a guess, and almost nobody has measured theirs |

## Interview questions

**1. "What's hard about Terraform?"**
> ⭐⭐ **The state file, and everything else is downstream of it.** It's the only thing mapping your code
> to real resource IDs, so: lose it and Terraform tries to create everything again; ⭐⭐ **it contains
> secrets in plain text, and `sensitive` only hides them from output — anyone who can read state has
> your database password**; concurrent applies corrupt it, hence locking; and its granularity is your
> blast radius. ⭐ Remote, encrypted, versioned, locked, pipeline-only access.

**2. "How do you structure it?"**
> ⭐ By rate of change and blast radius: foundation, data, platform, application. ⭐⭐ **The layer that
> changes daily must not share a state file with the one that's irreplaceable** — otherwise a DNS edit
> can destroy a database, and every plan refreshes everything so a security-group change takes ten
> minutes. ⭐ Layers reference each other through remote state outputs or data sources. ⭐ And separate
> directories per environment rather than workspaces, ⭐⭐ **because workspaces mean prod and dev differ
> by a variable, and a mistyped `-var` applies the wrong plan.**

**3. "What do you look for in a plan?"**
> ⭐⭐ **The word `replace`.** A create is usually fine, an update usually fine — ⭐⭐ **`-/+ must be
> replaced` means destroy then create, and on an RDS instance that's your database.** ⭐ So I review the
> plan, not just the code diff: the diff says what I changed, the plan says what will happen. ⭐ And I'd
> put `prevent_destroy` on anything with data, so a catastrophic plan becomes an error instead of an
> apply.

**4. "Someone changed something in the console. Now what?"**
> ⭐ The next apply silently reverts it — ⭐⭐ **which may have been a legitimate emergency fix, and
> reverting it mid-incident is its own incident.** ⭐ So: scheduled `plan -detailed-exitcode` with an
> alert on a non-empty diff, which turns drift into a ticket rather than a surprise; ⭐ a documented
> break-glass path so the console change is followed by a code change the same week; ⭐ and
> `ignore_changes` for fields another system legitimately owns, ⭐⭐ **which is declaring "this field
> isn't mine" rather than hacking around it.**

**5. "How do you prove zero-downtime deploys?"**
> ⭐⭐ You don't claim it, you demonstrate it: **run a load test, deploy in the middle of it, and show
> the error count is zero.** ⭐ Same for pod deletion. ⭐ Underneath that: `maxUnavailable: 0`, a
> `preStop` sleep so endpoint removal propagates, readiness failing on SIGTERM but not liveness, and a
> grace period exceeding drain plus p99. ⭐⭐ **Until you've run it under load, it's a configuration you
> hope works.**

**6. "What does Stage 10 give you as an engineer?"**
> ⭐⭐ The ability to say **"I don't just write the service, I ship it"** — with numbers. ⭐ The image is
> 190 MB because the toolchain lives in a build stage; the pipeline is twelve minutes and its
> migration-lock gate caught an `ALTER TABLE` that would have locked a forty-million-row table; deploys
> drop zero requests and I can show you the load test; ⭐⭐ **and when something breaks I go alert →
> trace → log in under five minutes, because the trace id is on the outbox row.** ⭐ Four clauses, each
> a number or a demonstration.

## 🎙️ Articulation drill

**Two minutes.** On Terraform, go straight to the thing everything else derives from: **the state file
is the only link between your code and real resources, so every hard question is really about state —
who holds it, who can write it at once, what happens when it disagrees with reality.** Give the four
consequences: lose it and Terraform recreates your estate; **it stores secrets in plain text, and
`sensitive` only hides them from output, so anyone who can read state has your database password**;
concurrent applies corrupt it, hence locking; and its granularity is your blast radius — **which is why
the layer that changes daily must not share a state file with the one that's irreplaceable.** On
process: review the plan rather than the diff, **because the interesting word is `replace`, and on an
RDS instance that means destroy-then-create**; apply the saved plan, or "approved" means nothing; and
`prevent_destroy` on anything with data. On drift: **a console change gets silently reverted by the
next apply, possibly mid-incident**, so scheduled plans with alerts turn it into a ticket. Then close
on the stage: **it wasn't about Docker or Kubernetes, it was about software you can't deploy, observe
