# Part 1 — ⭐ `multipart/form-data`, and what `UploadFile` actually is

```
⭐⭐ THE WIRE FORMAT, BECAUSE IT EXPLAINS THE COSTS:

⭐   Content-Type: multipart/form-data; boundary=----X7MA4
⭐
⭐   ------X7MA4
⭐   Content-Disposition: form-data; name="file"; filename="report.pdf"
⭐   Content-Type: application/pdf        ⭐⭐ CLIENT-SUPPLIED. A CLAIM, NOT A FACT.
⭐
⭐   <binary bytes>
⭐   ------X7MA4--
⭐
⭐   ⇒ ⭐⭐ THERE IS NO LENGTH PREFIX PER PART. The parser scans for the
⭐        boundary, ⭐ so it cannot know a part's size until the part ENDS.
⭐        ⭐⭐ THAT IS WHY "reject if too big" MUST BE ENFORCED WHILE READING,
⭐        NOT AFTER. Day 102's framing problem, in a body.
⭐   ⇒ ⭐ `filename` is a client-supplied string. ⭐⭐ It is attacker input, in
⭐        the position where people are most tempted to use it as a path.
```

```python
@router.post("/upload")
async def upload(file: UploadFile = File(...)):        # ⭐ needs `python-multipart`
    ...
```

```
⭐⭐ `UploadFile` IS A `SpooledTemporaryFile`, AND THAT ONE FACT IS THE ANSWER
⭐   TO "does FastAPI load the file into memory?":

⭐   ⭐ ≤ 1 MB  → held in RAM (`BytesIO`)
⭐   ⭐ > 1 MB  → ⭐⭐ AUTOMATICALLY ROLLS OVER TO A TEMP FILE ON DISK
⭐   ⇒ ⭐ so a 2 GB upload does NOT consume 2 GB of RAM — ⭐⭐ IT CONSUMES 2 GB
⭐        OF DISK IN `/tmp`, WHICH IS A SMALLER PROBLEM THAT IS STILL A PROBLEM.
⭐        ⭐ On a container with a 1 GB writable layer, ten concurrent uploads
⭐        fill the disk and ⭐⭐ EVERY OTHER PART OF THE APP THAT WRITES A FILE
⭐        STARTS FAILING — logs, sqlite, the temp dir itself.
⭐
⭐   ⭐⭐ AND THE ONE THAT ACTUALLY KILLS SERVERS:
⭐        `content = await file.read()`        # ⭐⭐ THE WHOLE FILE INTO RAM.
⭐        ⭐ Everything the spooling saved you, thrown away in one line.
⭐        ⇒ ⭐ 10 concurrent × 2 GB = OOM (Day 082: exit 137, empty logs).
```

```python
# ⭐⭐ STREAM IT. ALWAYS. And count as you go.
CHUNK = 1024 * 1024
async def save_streaming(file: UploadFile, dest: Path, max_bytes: int) -> int:
    total = 0
    hasher = hashlib.sha256()
    with dest.open("wb") as out:
        while chunk := await file.read(CHUNK):        # ⭐ bounded memory, always
            total += len(chunk)
            if total > max_bytes:                     # ⭐⭐ CHECK *DURING*, not after
                out.close(); dest.unlink(missing_ok=True)
                raise HTTPException(413, detail={"code": "file_too_large"})
            hasher.update(chunk)                      # ⭐ hash in the same pass
            out.write(chunk)
    return total
```

# Part 2 — ⭐⭐ Limits: four places, and only one that actually protects you

```
⭐⭐ THE FOUR GATES A BYTE PASSES THROUGH, OUTERMOST FIRST:

⭐  1. ⭐⭐ THE PROXY — nginx `client_max_body_size 100m;`
⭐       ⭐ DEFAULT IS 1 MB, and this is the #1 "works locally, 413 in
⭐       production" bug. ⭐⭐ It is ALSO your only real defence, because it is
⭐       the only gate that rejects bytes BEFORE THEY REACH PYTHON.
⭐  2. ⭐ THE ASGI SERVER — uvicorn `--limit-max-requests`, h11 header limits.
⭐       ⭐ Mostly header-shaped, not body-shaped.
⭐  3. ⭐ THE MULTIPART PARSER — `starlette` `max_part_size` / `max_files` /
⭐       `max_fields`. ⭐⭐ THESE MATTER: a body with 100,000 tiny fields is a
⭐       parser DoS that has nothing to do with file size.
⭐  4. ⭐ YOUR HANDLER — the running total above.
⭐
⭐   ⇒ ⭐⭐ THE UNCOMFORTABLE TRUTH ABOUT #4: BY THE TIME YOU COUNT, THE BYTES
⭐        HAVE ALREADY ARRIVED AND BEEN WRITTEN TO YOUR DISK. Your check
⭐        stops you from STORING them; it does not stop you from RECEIVING
⭐        them. ⭐ You can burn 2 GB of bandwidth and disk to return a 413.
⭐   ⇒ ⭐⭐ THEREFORE THE LIMIT MUST EXIST AT THE PROXY. The handler check is a
⭐        backstop for when you are behind something you do not control.
```

```
⭐⭐ AND `Content-Length` IS NOT A LIMIT:
⭐   ⭐ it is a client-supplied number. ⭐⭐ `Transfer-Encoding: chunked` omits
⭐     it entirely, so "reject if Content-Length > N" is bypassed by not
⭐     sending one. ⭐ Day 104's smuggling lesson: never trust a length you
⭐     did not count. ⭐⭐ Use it for a FAST early rejection, never as the
⭐     enforcement.
⭐
⭐ ⭐ AND RETURN THE RIGHT CODE: ⭐⭐ 413 Content Too Large. Not 400, not 422 —
⭐   ⭐ clients and proxies treat 413 specially, and Day 120 said the code is
⭐   the machine-readable part.
```

# Part 3 — ⭐⭐ The filename and the content type are both lies

```
⭐⭐ THREE ATTACKS, ALL THROUGH FIELDS PEOPLE TREAT AS METADATA:

⭐  1. ⭐⭐ PATH TRAVERSAL (Day 128)
⭐       filename = "../../../etc/cron.d/pwn"
⭐       dest = UPLOAD_DIR / filename        ⭐⭐ pathlib HAPPILY ESCAPES
⭐       ⇒ ⭐⭐ NEVER USE THE CLIENT'S FILENAME AS A PATH. GENERATE YOUR OWN:
⭐            stored = UPLOAD_DIR / f"{uuid4().hex}{safe_ext}"
⭐         ⭐ Keep the original name as a DATABASE COLUMN for display, and
⭐         escape it on the way out. ⭐⭐ The name is DATA; it is never a PATH.
⭐       ⭐ Also: NUL bytes, `C:\`, absolute paths, unicode look-alikes, and
⭐         reserved Windows names (`CON`, `NUL`, `LPT1`).
⭐
⭐  2. ⭐⭐ CONTENT-TYPE IS A CLAIM. `Content-Type: image/png` on a PHP file
⭐       costs the attacker nothing. ⭐ Sniff the MAGIC BYTES (`python-magic`,
⭐       or check the header yourself) and ⭐⭐ REJECT ON A MISMATCH between
⭐       claim, extension, and content — the disagreement is itself the signal.
⭐       ⇒ ⭐⭐ AND ALWAYS SERVE UPLOADS WITH:
⭐            Content-Type: <what YOU determined>   ⭐ not what they said
⭐            X-Content-Type-Options: nosniff       ⭐⭐ or the browser sniffs
⭐            Content-Disposition: attachment       ⭐ for anything not an image
⭐            ⭐⭐ AND FROM A DIFFERENT ORIGIN — a stored HTML file served from
⭐            your domain is STORED XSS with your session cookie (Day 127).
⭐
⭐  3. ⭐ DECOMPRESSION / IMAGE BOMBS. A 10 KB PNG can declare 50,000×50,000
⭐       pixels = ⭐⭐ 10 GB WHEN DECODED. A 4 MB zip can be 8 TB.
⭐       ⇒ ⭐ `Image.MAX_IMAGE_PIXELS` in Pillow (it warns by default —
⭐         ⭐⭐ make it an ERROR), and NEVER decode user media in your web
⭐         process. ⭐ Do it in a worker (Day 142) with a memory limit, so the
⭐         blast radius is one job rather than every request on that box.
```

```python
def safe_extension(filename: str) -> str:
    ext = Path(filename).suffix.lower()
    return ext if ext in {".png", ".jpg", ".jpeg", ".pdf", ".csv"} else ""   # ⭐ ALLOW-LIST

# ⭐⭐ ALLOW-LIST, NEVER DENY-LIST. A deny-list loses to `.pHp`, `.php5`,
#    `.phtml`, a trailing dot, a trailing space, and a double extension.
#    ⭐ Day 127's principle: enumerate what is permitted, not what is banned.
```

# Part 4 — ⭐⭐ Presigned URLs: stop being in the data path

```
⭐⭐ THE ARCHITECTURAL MOVE. EVERYTHING ABOVE ASSUMED BYTES FLOW THROUGH YOUR
⭐   APP. ⭐ THE BETTER ANSWER IS THAT THEY DO NOT.

⭐   ⭐ THROUGH YOUR APP:
⭐      client → [YOUR SERVER: 90 s, 2 GB disk, a worker slot] → S3
⭐      ⭐⭐ A 90-SECOND UPLOAD OCCUPIES A WORKER FOR 90 SECONDS. Day 111:
⭐         you have maybe 4×8 of those. ⭐ 32 uploads = your API is down.
⭐
⭐   ⭐⭐ PRESIGNED:
⭐      1. client → your API:  "I want to upload report.pdf, 4 MB, image/png"
⭐      2. your API           → checks auth, quota, type, size
⭐                            → generates a signed PUT URL (expires in 5 min)
⭐                            → writes an `uploads` row: status=pending
⭐                            → ⭐ returns in ~5 ms
⭐      3. client → S3 directly (⭐⭐ YOUR SERVER IS NOT INVOLVED)
⭐      4. client → your API:  "done, key=..."   ⭐ OR S3 → your webhook
⭐      5. your API           → HEAD the object: verify SIZE and TYPE
⭐                            → status=ready
⭐
⭐   ⇒ ⭐⭐ THE COST MOVES FROM YOUR WORKERS TO S3, AND S3 IS BUILT FOR IT.
⭐        ⭐ Your slowest endpoint becomes a 5 ms one.
```

```python
url = s3.generate_presigned_url(
    "put_object",
    Params={
        "Bucket": settings.bucket,
        "Key": f"uploads/{user.id}/{uuid4().hex}",   # ⭐⭐ YOU choose the key, not the client
        "ContentType": body.content_type,            # ⭐ signed in ⇒ cannot be changed
    },
    ExpiresIn=300,                                    # ⭐⭐ short. It is a capability.
)
```

```
⭐⭐ THE FIVE THINGS PEOPLE GET WRONG WITH PRESIGNED URLS:

⭐  1. ⭐⭐ LETTING THE CLIENT CHOOSE THE KEY. Then they upload to
⭐       `uploads/<someone-else's-id>/avatar.png` and overwrite it.
⭐       ⭐ IDOR (Day 118) in object storage. ⭐⭐ THE SERVER PICKS THE KEY.
⭐  2. ⭐⭐ NO SIZE LIMIT. A presigned PUT has NO size cap unless you sign one.
⭐       ⭐ Use POST policies with `content-length-range`, or ⭐ a bucket rule,
⭐       or accept that a user can upload 5 TB to your bill.
⭐  3. ⭐⭐ TRUSTING THE CLIENT'S "I'M DONE". They may never call it, or lie.
⭐       ⇒ ⭐ HEAD the object yourself and check real size/type before marking
⭐         it ready. ⭐⭐ AND run a lifecycle rule that deletes `pending`
⭐         objects after 24 h — otherwise abandoned uploads accumulate forever.
⭐  4. ⭐ EXPIRY TOO LONG. ⭐⭐ A presigned URL IS a bearer token for one
⭐       object (Day 140) — it needs no login. 5 minutes, not 7 days.
⭐  5. ⭐ FORGETTING CORS ON THE BUCKET. The browser PUT is cross-origin, so
⭐       the bucket needs its own CORS config. ⭐⭐ Symptom: works in curl,
⭐       fails in the browser with no useful error.

⭐ ⭐⭐ AND FOR DOWNLOADS, THE SAME MOVE IN REVERSE: a presigned GET, short
⭐   expiry, ⭐ generated only after YOUR authorisation check. ⭐⭐ Never make
⭐   the bucket public and rely on an unguessable key — that is security by
⭐   URL secrecy, and URLs leak through `Referer`, logs, and screenshots.
```

# Part 5 — ⭐ The state machine, and the two-phase rule

```
⭐⭐ AN UPLOAD IS NOT AN EVENT. IT IS A STATE MACHINE, AND MODELLING IT AS ONE
⭐   IS WHAT MAKES IT RELIABLE:

⭐   pending ──(bytes arrive, verified)──> ready ──(processed)──> available
⭐      │                                    │
⭐      └──(24 h, no bytes)──> expired       └──(bad content)──> rejected
⭐
⭐   ⇒ ⭐⭐ THE ROW EXISTS BEFORE THE BYTES DO. That is what makes cleanup
⭐        possible: you can list what SHOULD exist and compare it to what
⭐        DOES. ⭐ Without the row, an abandoned object is invisible garbage.

⭐⭐ THE TWO-PHASE RULE — an instance of Day 142's dual write:
⭐   ⭐ storage and your database are two systems. ⭐⭐ Whichever you write
⭐     first, a crash between them leaves an inconsistency. So CHOOSE THE
⭐     ORDER THAT LEAVES GARBAGE, NOT A BROKEN LINK:
⭐   ⭐ ✅ write the OBJECT first, the DB row second → ⭐ worst case: an orphan
⭐        object, which a reconciliation job sweeps.
⭐   ⭐ ❌ write the DB row first → ⭐⭐ worst case: a row pointing at an object
⭐        that does not exist ⇒ a 500 every time anyone opens that record.
⭐   ⇒ ⭐⭐ ORPHANED DATA IS CHEAP. A DANGLING REFERENCE IS AN INCIDENT.
⭐        ⭐ (The `pending` row above is not a violation of this — it is a
⭐        RESERVATION, and it is explicitly marked as not-yet-usable.)

⭐ ⭐ AND ALWAYS: process media in a WORKER, never in the request (Day 142).
⭐   ⭐⭐ Thumbnailing, virus scanning, PDF text extraction and transcoding are
⭐   all unbounded, memory-hungry, and run untrusted input through C
⭐   libraries with CVE histories. ⭐ That belongs in a process you can
⭐   memory-limit and restart, not in the one serving your API.
```

```
⭐⭐ RESUMABLE / LARGE UPLOADS, IN ONE BOX:
⭐   ⭐ S3 MULTIPART: initiate → upload parts (≥5 MB, presign EACH part) →
⭐     complete. ⭐⭐ Gives you resume, parallelism, and per-part retry for free.
⭐   ⭐ Above ~100 MB this stops being optional: a single 2 GB PUT that fails
⭐     at 98% ⭐⭐ starts again from zero, on a mobile connection.
⭐   ⭐ Set a lifecycle rule to abort incomplete multipart uploads — ⭐⭐ their
⭐     parts are STORED AND BILLED and are invisible in the normal object
⭐     listing. ⭐ A genuinely common surprise line item.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `await file.read()` with no argument | Loads the whole file into RAM and undoes the spooling. Stream in chunks. |
| Checking size after the upload finishes | You already paid the bandwidth and disk. Count during the read, and cap at the proxy. |
| Trusting `Content-Length` | Client-supplied, and absent entirely under chunked encoding. Count bytes yourself. |
| Returning 400 or 422 for oversize | ⭐⭐ 413 — proxies and clients treat it specially. |
| nginx default `client_max_body_size` | 1 MB. The classic "works locally, 413 in production". |
| Using the client's filename as a path | ⭐⭐ `../../` escapes `pathlib` happily. Generate a UUID name; keep the original as data. |
| Trusting the declared `Content-Type` | It's a claim. Sniff magic bytes and reject disagreements. |
| Deny-listing extensions | Loses to `.pHp`, `.php5`, double extensions, trailing dots. Allow-list. |
| Serving uploads from your own origin | A stored HTML file is stored XSS with your cookies. Separate origin + `nosniff` + `attachment`. |
| Decoding user images in the web process | Image bombs. Do it in a memory-limited worker. |
| No `max_files` / `max_fields` on the parser | 100,000 tiny fields is a parser DoS unrelated to file size. |
| Letting the client choose the storage key | IDOR in object storage — they overwrite someone else's file. |
| Presigned URL with no size limit | No cap unless you sign one. Use a POST policy with `content-length-range`. |
| Trusting the client's "upload complete" | HEAD the object and verify. Expire `pending` rows on a schedule. |
| Long presigned expiry | It's a bearer token for that object. Minutes, not days. |
| DB row written before the object exists | A dangling reference 500s forever. Object first, row second. |
| No lifecycle rule for incomplete multipart uploads | The parts are stored and billed, and invisible in listings. |

## Interview questions

**Q: A user uploads a 2 GB file. Walk me through what happens to your server's memory.**

> With `UploadFile`, nothing terrible by default — it's a `SpooledTemporaryFile`, so under about a
> megabyte it stays in RAM and above that it rolls over to a temp file on disk. So the naive fear,
> "FastAPI loads it all into memory", isn't true. The disk is the real exposure: ten concurrent 2 GB
> uploads fill `/tmp`, and on a container that means everything else that writes a file starts
> failing too. What *does* blow up memory is `await file.read()` with no argument — that materialises
> the whole file and throws away everything the spooling bought you. So I stream in chunks with a
> running byte count, check the limit during the read rather than after, and hash in the same pass.

**Q: Where do you enforce the size limit?**

> At the proxy, primarily — `client_max_body_size` in nginx — because that's the only gate that
> rejects bytes before they reach Python. The check in my handler is a backstop: by the time it
> fires, I've already received the bytes and written them to disk, so I can burn two gigabytes of
> bandwidth to return a 413. I also set the multipart parser's `max_files` and `max_fields`, because
> a body with a hundred thousand tiny fields is a denial of service that has nothing to do with file
> size. And I never enforce with `Content-Length` — it's client-supplied and simply absent under
> chunked transfer encoding.

**Q: What do you do with the uploaded filename?**

> Treat it as data, never as a path. It's attacker-controlled input in the position where people are
> most tempted to concatenate — `UPLOAD_DIR / filename` with `../../` in it escapes the directory
> quite happily, because that's what `pathlib` is *for*. I generate my own key, a UUID plus an
> extension from an allow-list, and store the original name in a database column for display,
> escaped on the way out. Allow-list rather than deny-list, because a deny-list loses to `.pHp`,
> `.php5`, `.phtml`, a trailing dot, and double extensions. The declared content type gets the same
> treatment — it's a claim, so I sniff the magic bytes and treat a disagreement between claim,
> extension and content as itself the signal to reject.

**Q: Why use presigned URLs?**

> Because otherwise a ninety-second upload occupies a worker for ninety seconds, and I only have a
> few dozen workers — thirty concurrent uploads and the API is effectively down. With a presigned
> URL my endpoint does auth, quota and type checks, writes a pending row, returns a signed URL in
> about five milliseconds, and the bytes go straight from the client to S3 without touching me. The
> things to get right: the server picks the key, not the client, or they'll write into someone
> else's prefix; sign a size limit, because a presigned PUT has no cap otherwise; verify with a HEAD
> rather than trusting the client's "done"; keep the expiry to minutes because that URL is a bearer
> token for that object; and configure CORS on the bucket, or it works in curl and fails in the
> browser.

**Q: The object uploaded fine but the database write failed. What state are you in, and did you design for it?**

> That's the dual-write problem again — two systems, no shared transaction. I deliberately order it
> so the failure leaves garbage rather than a broken link: write the object first, the row second.
> Worst case is an orphaned object that a reconciliation job sweeps by comparing storage against the
> pending rows. The other order leaves a row pointing at an object that doesn't exist, which 500s
> every time anyone opens that record — orphaned data is cheap, a dangling reference is an incident.
> The pending row I create *before* the upload isn't a violation of that: it's a reservation, marked
> explicitly as not yet usable, and it's what makes the cleanup job possible at all, because you
> can't sweep objects you have no record of.

## 🎙️ Articulation drill

**Two minutes: "Design file upload for our app."**

Start with the architecture, not the code: you don't want the bytes. Presigned URL, server picks the
key, signed size and type, short expiry, verify with HEAD, pending row first so cleanup is possible.
Then cover the case where you *are* in the path — stream in chunks, count during the read, and say
plainly that the real limit lives at the proxy because your handler's check runs after you've
already paid. Then the three lies: the filename is not a path, the content type is a claim, and the
declared length isn't a length. Close on the ordering rule — **object first, row second, because
orphaned data is cheap and a dangling reference is an incident** — and on processing media in a
worker rather than a request.
