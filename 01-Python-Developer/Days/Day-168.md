# Day 168

**L-168** · 🏗 **Capstone VII — deploy, load test, tune** — ⭐⭐ the on-sale spike, the knee, and one fix you can prove

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a performance claim without a before number, an after number and a named
> cause is a story — today you produce all three for exactly one bottleneck, because one measured fix
> is worth more in an interview than five plausible ones.**
>
> ⭐ The scenario is real: **50,000 people hit one event at 10:00:00 for 500 tickets.** ⭐⭐ Almost
> everyone will fail, by design — the question is whether they fail *fast and correctly*.

# Part 1 — ⭐⭐ Predict before you measure

```
⭐⭐ DO THIS FIRST AND WRITE IT DOWN. ⭐ A prediction you got wrong teaches you
⭐   something; a measurement with no prediction teaches you a number.

⭐   ⭐ LITTLE'S LAW (Day 156), FORWARDS AND BACKWARDS:
⭐        4 workers × 8 threads = 32 concurrent slots
⭐        browse p50 ≈ 15 ms ⇒ ⭐⭐ CEILING ≈ 32 / 0.015 ≈ 2,100 rps
⭐        purchase p50 ≈ 80 ms ⇒ ⭐ 32 / 0.08 ≈ 400 rps
⭐   ⭐ DB POOL: 4 workers × pool_size 5 = ⭐⭐ 20 CONNECTIONS TOTAL.
⭐        ⇒ ⭐⭐ 20 < 32 SLOTS. THE POOL IS THE BOTTLENECK BEFORE THE THREADS
⭐          ARE, AND YOU KNEW THAT WITHOUT RUNNING ANYTHING.
⭐   ⭐⭐ THE LOCK: every purchase for one ticket type serialises on one row
⭐        (Day 164). ⭐ If the locked section takes 3 ms, ⭐⭐ THE ABSOLUTE
⭐        CEILING FOR ONE TICKET TYPE IS ~330 PURCHASES/SEC, no matter how
⭐        many machines you add. ⭐ That is a design property, not a tuning
⭐        problem — ⭐⭐ and being able to state it is the interview answer.

⭐⭐ NOW WRITE YOUR THREE PREDICTIONS:
⭐   1. what breaks first?          ⭐ (mine: the pool)
⭐   2. at what offered rate?
⭐   3. what does the failure LOOK like — errors, or just latency?
⭐   ⇒ ⭐⭐ THE THIRD IS THE ONE PEOPLE GET WRONG. Pool exhaustion produces
⭐        NO ERRORS AND NO CPU — ⭐ only waiting. ⭐⭐ It looks exactly like "the
⭐        database is slow" and is not.
```

# Part 2 — ⭐⭐ The test that matches reality

```javascript
// ⭐⭐ k6 — OPEN MODEL. Arrivals do not wait for responses (Day 156).
export const options = {
  scenarios: {
    browse: {                                  // ⭐ the realistic mix, not one endpoint
      executor: 'constant-arrival-rate',
      rate: 800, timeUnit: '1s', duration: '5m',
      preAllocatedVUs: 500, maxVUs: 3000,      // ⭐⭐ VUs must be able to GROW
    },
    onsale: {                                  // ⭐⭐ the spike
      executor: 'ramping-arrival-rate',
      startTime: '2m',
      stages: [{ target: 5000, duration: '10s' }, { target: 5000, duration: '60s' }],
      preAllocatedVUs: 2000, maxVUs: 20000,
    },
  },
};
```

```
⭐⭐ FIVE THINGS THAT MAKE THIS TEST HONEST (Day 156):
⭐  1. ⭐⭐ OPEN MODEL. A closed model slows down when you do, so it cannot
⭐       reproduce an on-sale — ⭐ the one failure you are here to study.
⭐  2. ⭐⭐ A MIX. 90% browse, 8% hold, 2% purchase. ⭐ One endpoint alone
⭐       misses the contention that matters — they share the pool.
⭐  3. ⭐⭐ REALISTIC DATA. Zipfian event selection (one event is 95% of
⭐       traffic — that IS an on-sale) and ⭐ a production-sized database.
⭐       ⭐⭐ 1,000 rows means every query is a fast seq scan and you are
⭐       testing a different program.
⭐  4. ⭐ DISCARD THE FIRST 60 SECONDS — cold pools, cold caches.
⭐  5. ⭐⭐ WATCH THE GENERATOR'S OWN CPU. ⭐ Above ~70% you are measuring the
⭐       generator, and everything after that is fiction.
⭐
⭐ ⭐⭐ AND THE ASSERTION THAT MATTERS MORE THAN ANY LATENCY NUMBER:
⭐      `tickets_sold == 500` — EXACTLY. ⭐ Under 5,000 rps of real
⭐      concurrency, ⭐⭐ correctness is the result you are actually testing.
⭐      A fast oversell is a failed load test.
```

# Part 3 — ⭐⭐ Find the knee, then read the evidence

```
⭐⭐ RAMP AND PLOT. YOU ARE LOOKING FOR THE SHAPE, NOT A NUMBER:

⭐   completed/s │        ┌──────────  ⭐ FLAT = saturated
⭐               │      ╱               ⭐⭐ FALLING = congestion collapse
⭐               │    ╱
⭐   p99         │────────┴──╱⭐⭐ hockey stick
⭐                        ▲
⭐                    ⭐⭐ THE KNEE

⭐⭐ THEN DIAGNOSE IN THIS ORDER (Days 156, 157) — ⭐ and DO NOT open a
⭐   profiler until step 4:

⭐  1. ⭐⭐ IS THE GENERATOR SATURATED? Always check first, always.
⭐  2. ⭐⭐ ERRORS OR LATENCY? ⭐ 429s and 503s are the system WORKING
⭐       (Days 152, 153). ⭐⭐ 500s and timeouts are the system failing.
⭐       ⭐ Separate them before drawing any conclusion.
⭐  3. ⭐⭐ SATURATION SIGNALS: pool wait time, queue depth, event-loop lag,
⭐       DB CPU, app CPU.
⭐       ⭐⭐ FLAT APP CPU + RISING LATENCY = BLOCKED, NOT BUSY. ⭐ That single
⭐       reading eliminates half the search space.
⭐  4. ⭐ COMPARE A FAST TRACE WITH A SLOW ONE (Day 148). ⭐⭐ The span that
⭐       grew is your answer — and it is usually not the one you expected.
⭐  5. ⭐ `py-spy dump` on a saturated worker: ⭐⭐ what are the 8 threads
⭐       actually doing right now?

⭐⭐ THE ANSWER YOU WILL ALMOST CERTAINLY GET, AND WHY IT IS SUBTLE:
⭐   ⭐ the widest span is `db.acquire`, ⭐ NOT the query.
⭐   ⇒ ⭐⭐ THE DATABASE IS IDLE. YOUR APP IS IDLE. EVERY REQUEST IS WAITING
⭐        FOR A CONNECTION. ⭐ 20 connections, 32 threads, and Little's Law
⭐        said you needed 40+. ⭐⭐ In a trace this is indistinguishable from
⭐        "the provider/database is slow" unless you instrumented acquire
⭐        time separately — which is why Day 148 said to.
```

# Part 4 — ⭐⭐ Fix exactly one thing, and prove it

```
⭐⭐ THE LADDER (Days 100A, 157). ⭐ WORK DOWN IT; DO NOT START AT THE BOTTOM:

⭐  1. ⭐⭐ DO IT LESS OFTEN — ⭐ the event page cache (Day 167) turns 50,000
⭐       reads into ~1. ⭐⭐ Biggest single win available, and it is not code.
⭐  2. ⭐ FIX THE QUERY — the report N+1 is already done; ⭐ check for a
⭐       missing index on `holds(ticket_type_id) WHERE released_at IS NULL`.
⭐  3. ⭐ MOVE IT OFF THE PATH — confirmation email is already async (Day 166).
⭐  4. ⭐⭐ RIGHT-SIZE THE POOL. ⭐ `pool_size` per worker × workers must exceed
⭐       your concurrency, ⭐⭐ AND STAY UNDER POSTGRES `max_connections`
⭐       (default 100). ⭐ 4 × 20 = 80 ✅. ⭐⭐ 8 workers × 20 = 160 ❌ — the
⭐       database starts REFUSING CONNECTIONS, ⭐ which is a much worse outage
⭐       than being slow. ⭐⭐ Above that, PgBouncer in transaction mode.
⭐  5. ⭐ FASTER LIBRARY — `orjson`, and Pydantic v2 is already Rust.
⭐  6. ⭐ MORE MACHINES — ⭐⭐ and note this does NOT help the lock contention
⭐       in Part 1, which is the honest and impressive thing to say.

⭐⭐ CHANGE **ONE** THING. RE-RUN THE IDENTICAL TEST. RECORD:
⭐        BEFORE: knee 420 rps · p99 3,200 ms · pool wait p95 890 ms
⭐        CHANGE: pool_size 5 → 20 per worker (80 total, max_connections 100)
⭐        AFTER:  knee 1,150 rps · p99 240 ms · pool wait p95 4 ms
⭐        ⭐⭐ CAUSE: 20 connections served 32 threads; requests queued for a
⭐             connection while both app and database were idle.
⭐   ⇒ ⭐⭐ THAT FOUR-LINE BLOCK IS THE MOST VALUABLE ARTEFACT OF THE ENTIRE
⭐        CAPSTONE. ⭐ It is a story with a mechanism, a measurement and a
⭐        number — ⭐⭐ and it is what separates "I load tested it" from "I
⭐        found and fixed a bottleneck".
⭐   ⇒ ⭐ CHANGING TWO THINGS AT ONCE COSTS YOU THE CAUSE, which is the part
⭐        that was worth having.
```

```
⭐⭐ THEN FIND THE **SECOND** BOTTLENECK, BECAUSE IT IS ALWAYS SOMEWHERE ELSE:
⭐   ⭐ pool fixed ⇒ ⭐⭐ now DB CPU is 100%, or the `FOR UPDATE` row is the
⭐     limit, or the event-loop lag spikes. ⭐ Each moves the constraint, and
⭐     ⭐⭐ NOTICING THAT THE BOTTLENECK MOVED IS ITSELF THE FINDING.
⭐   ⇒ ⭐ Two documented fixes is plenty. ⭐⭐ STOP AT THE KNEE YOU ACTUALLY
⭐     NEED — Day 156: operate at 50–70% of it, and tuning beyond your
⭐     requirement is a hobby.
```

# Part 5 — ⭐⭐ Behaviour under overload, and the deploy

```
⭐⭐ THE QUESTION THAT MATTERS MORE THAN THE KNEE: **WHAT HAPPENS PAST IT?**

⭐   ⭐ ❌ BAD: p99 climbs to 40 s, every client times out, ⭐⭐ you did 100%
⭐        of the work and delivered 0% of the value (Day 152).
⭐   ⭐ ✅ GOOD: ⭐⭐ rate limits return 429 with `Retry-After` (Day 153) ·
⭐        load shedding returns 503 fast when in-flight exceeds a threshold ·
⭐        ⭐ p99 for ACCEPTED requests stays flat · ⭐⭐ `tickets_sold` is still
⭐        exactly 500.
⭐   ⇒ ⭐⭐ AND THE PROPERTY TO PROVE EXPLICITLY: DROP THE LOAD TO ZERO AND
⭐        WATCH IT RECOVER **WITHOUT INTERVENTION**. ⭐ A system that stays
⭐        down after the load stops is metastable (Day 152) — ⭐⭐ and that is
⭐        the single most valuable finding a stress test can produce.

⭐⭐ THE ON-SALE CHECKLIST, WHICH IS A PRODUCT DECISION AS MUCH AS A TECHNICAL
⭐   ONE:
⭐   □ ⭐ pre-scale before 10:00 — ⭐⭐ autoscaling reacts in minutes and the
⭐        spike is seconds. ⭐ It will not save you; provisioning will.
⭐   □ ⭐ warm the caches and the pools (⭐⭐ or the first 200 requests hit a
⭐        cold pod — Day 149)
⭐   □ ⭐⭐ a per-user hold rate limit (the Day 162 abuse case, now real)
⭐   □ ⭐ shed browse traffic before purchase traffic — ⭐⭐ shed by PRIORITY
⭐   □ ⭐ a queue/waiting-room page is the honest answer at extreme scale
```

```
⭐⭐ AND FINALLY, DEPLOY IT PROPERLY (Days 149, 155):
⭐   ⭐ deploy under load and count the 5xx. ⭐⭐ It must be ZERO.
⭐        ⭐ If it is not: `preStop` sleep, grace period > longest request,
⭐        exec-form CMD, nginx `keepalive_timeout` below the preStop sleep.
⭐   ⭐ ⭐⭐ ROLL BACK UNDER LOAD AND TIME IT. ⭐ If it is over a minute, fix
⭐        that before anything else on this page — ⭐⭐ rollback time is on
⭐        your recovery path for every future incident.
⭐   ⭐ deploy a deliberately broken image and confirm ⭐⭐ the smoke test
⭐        catches it and it rolls back AUTOMATICALLY.
⭐   ⭐ ⭐ then check the dashboard split by version (Day 167) and confirm you
⭐        can see the deploy without being told about it.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Measuring without predicting first | A wrong prediction teaches you something; a number alone doesn't. |
| Not computing the pool ceiling from Little's Law | You could have known the bottleneck without running anything. |
| A closed-model tool | It slows when you do, so it can't reproduce an on-sale. |
| Testing one endpoint | The contention that matters comes from a mix sharing the pool. |
| Uniform event selection | An on-sale *is* a Zipfian distribution — one event is 95% of traffic. |
| A small test database | Different query plans; you're testing a different program. |
| Ignoring the generator's CPU | Above ~70% everything you measured is fiction. |
| Only asserting latency | `tickets_sold == 500` matters more. A fast oversell is a failed test. |
| Counting 429s and 503s as failures | Those are the system working. Separate them from 500s and timeouts. |
| Opening a profiler first | Flat CPU with rising latency means blocked, not busy. |
| Reading a wide `db.acquire` span as a slow database | It's your own pool exhaustion, and it looks identical unless you instrumented acquire time. |
| Raising `pool_size` past `max_connections` | The database starts refusing connections — worse than slow. |
| Changing two things at once | You keep the improvement and lose the cause, which was the valuable part. |
| Stopping after one fix | The bottleneck moves; noticing where it moved to *is* the finding. |
| Tuning far past your requirement | Operate at 50–70% of the knee. Beyond that it's a hobby. |
| Not testing recovery after overload | Whether you're metastable is the most valuable stress-test result. |
| Relying on autoscaling for a spike | It reacts in minutes; the spike is seconds. Pre-provision. |
| Never deploying under load | You don't know whether your graceful shutdown works. |
| Never timing a rollback | It's on the recovery path for every future incident. |

## Interview questions

**Q: Walk me through load testing this service.**

> I predicted first and wrote it down, because a wrong prediction teaches you something and a bare
> number doesn't. Little's Law: four workers times eight threads is thirty-two concurrent slots, and
> a pool of five per worker is twenty connections — so the pool is the bottleneck before the threads
> are, and I knew that without running anything. Then an open-model test, because a closed generator
> slows down when the server does and therefore can't reproduce an on-sale, with a realistic mix and
> a Zipfian event distribution, since an on-sale *is* one event taking ninety-five percent of
> traffic. I ramped to find the knee and watched three things: whether the generator was saturated,
> whether failures were 429s and 503s — the system working — or 500s and timeouts, and the saturation
> signals. Flat app CPU with rising latency meant blocked rather than busy, which eliminated half the
> search space before I opened anything.

**Q: What did you find and how did you prove the fix?**

> The widest span was `db.acquire`, not the query — so the database was idle, the app was idle, and
> every request was queueing for a connection. That's important because in a trace it's
> indistinguishable from "the database is slow" unless you instrumented acquire time separately. I
> changed exactly one thing, pool size from five to twenty per worker, keeping the total under
> Postgres's `max_connections` — because overshooting that means the database starts refusing
> connections, which is a far worse outage than being slow. Then I re-ran the identical test: the
> knee went from about 420 to 1,150 requests per second, p99 from 3.2 seconds to 240 milliseconds,
> and pool wait p95 from 890 milliseconds to four. One change, so I kept the cause — if I'd changed
> two things I'd have the improvement and no explanation, and the explanation was the valuable part.

**Q: What happens past the knee?**

> That's the question that matters more than the knee itself. The bad answer is that p99 climbs to
> forty seconds and every client times out, so you've done a hundred percent of the work and
> delivered zero percent of the value. What I want instead is rate limits returning 429 with
> `Retry-After` and load shedding returning a fast 503 when in-flight exceeds a threshold, so p99 for
> *accepted* requests stays flat — serving seventy percent and rejecting thirty beats failing a
> hundred slowly. And I shed by priority, browse before purchase. The thing I explicitly prove is
> recovery: drop the load to zero and confirm it comes back without intervention, because a system
> that stays down after the load stops is metastable, and that's the single most valuable finding a
> stress test can produce.

**Q: Can you just add more servers for the on-sale?**

> For browsing, yes — that path scales horizontally and the cache does most of the work anyway.
> For purchasing, no, and this is the interesting limit. Every purchase for one ticket type
> serialises on one row under `SELECT ... FOR UPDATE`, so if the locked section takes three
> milliseconds, the ceiling is around three hundred and thirty purchases per second for that ticket
> type no matter how many machines I add. That's a design property, not a tuning problem. If I needed
> more I'd have to change the design — shard the inventory into buckets and pick one at random, or
> move to a queue-based allocation — and both trade complexity and fairness for throughput. I'd also
> pre-provision rather than rely on autoscaling, because autoscaling reacts in minutes and the spike
> is seconds.

## Today's build

1. ⭐⭐ Write your three predictions before touching a tool. Seal them.
2. ⭐ Seed a production-sized database. Compare one query's `EXPLAIN` against the small dataset.
3. ⭐⭐ Write the k6 scenario: open model, realistic mix, Zipfian event selection.
4. ⭐ Ramp and plot throughput and p99 together. Mark the knee.
5. ⭐⭐ Assert `tickets_sold == 500` after the spike. Every time.
6. ⭐⭐ Diagnose without a profiler: generator CPU, error classes, saturation signals, then a trace comparison.
7. ⭐ `py-spy dump` a saturated worker and read what the threads are doing.
8. ⭐⭐ Change one thing. Re-run identically. Record the four-line before/change/after/cause block.
9. ⭐⭐ Find the second bottleneck and note where the constraint moved to.
10. ⭐⭐ Push past the knee, then drop to zero and confirm unaided recovery.
11. ⭐⭐ Deploy under load. Count the 5xx. Fix until it's zero.
12. ⭐ Time a rollback under load. Then deploy a broken image and confirm automatic rollback.

## 🎙️ Articulation drill

**Two minutes: "Tell me about a performance problem you fixed."**

Use the four-line structure and nothing else: before, change, after, cause. Lead with the prediction
you made from Little's Law, because it shows you reasoned rather than guessed, and mention that the
symptom — flat CPU, rising latency, a wide `db.acquire` span — looked exactly like a slow database
and wasn't. Give the numbers. Say you changed one thing so you kept the cause. Then add the two
details that make it sound like production experience: **the pool can't grow past `max_connections`
or the database starts refusing connections, and after the fix the bottleneck moved** — which you
noticed, and which is itself the finding. Close on behaviour past the knee and unaided recovery,
because that is what an interviewer with operational scars is listening for.
