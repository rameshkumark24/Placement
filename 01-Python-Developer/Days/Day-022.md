# Part 1 — ⭐⭐ The trace

## ⭐ 0. Before anything leaves the machine

```
⭐ You press Enter. The browser decides whether this is even a URL or a search.
⭐ It checks HSTS — ⭐⭐ if the domain is on the preload list, http:// is REWRITTEN to https://
⭐   BEFORE any request exists. (Day 009 — this is why a downgrade attack has nothing to attack.)
```

## ⭐⭐ 1. DNS — Day 007

```
⭐ Browser cache → OS cache → hosts file → configured RESOLVER
⭐ The resolver, if it has nothing cached, walks it ITERATIVELY (Day 012's C-08):
⭐   root  ⇒ "ask the .com servers"
⭐   TLD   ⇒ "ask ns1.example.com"
⭐   auth  ⇒ ⭐ "93.184.216.34", with a TTL
⭐ ⇒ ⭐⭐ Everything is cached at every step with no invalidation — which is why a migration
⭐      means lowering the TTL FIRST and waiting out the old one.
```

## ⭐ 2. TCP — Days 005, 008

```
⭐ SYN → SYN-ACK → ACK.   ⭐⭐ ONE ROUND TRIP before a single byte of anything useful.
⭐ Both sides now hold state: sequence numbers, buffers, windows. ⭐ A connection is agreement,
⭐   not a pipe. The congestion window starts SMALL and doubles per RTT (slow start).
```

## ⭐⭐ 3. TLS — Day 009

```
⭐ ClientHello (versions, ciphers, ⭐ SNI in the clear, ephemeral key)
⭐ ServerHello (cipher, ephemeral key, ⭐⭐ CERTIFICATE CHAIN, signature)
⭐ ⇒ both DERIVE the same secret — never transmitted ⇒ ⭐ forward secrecy
⭐ ⇒ ⭐ client verifies: chain to a trusted root, not expired, ⭐⭐ HOSTNAME MATCHES, not revoked
⭐ ⇒ ⭐⭐ TLS 1.3: one more round trip. Running total: 2 RTT + DNS, before any HTTP.
```

## ⭐ 4. The HTTP request — Days 010, 011

```
⭐ GET / HTTP/2      (⭐⭐ negotiated during TLS via ALPN — not a separate step)
⭐ :authority, :method, :path as pseudo-headers; ⭐ headers compressed with HPACK
⭐ ⭐ cookies attached automatically for this origin (Day 019) — ⭐⭐ and this is exactly
⭐   the automatic attachment that makes CSRF possible (Day 020).
```

## ⭐⭐ 5. The path through your infrastructure — Days 018, 021

```
⭐ CDN edge (Day 018)
⭐   ⇒ ⭐ cache HIT for a hashed asset ⇒ answered here, ~10 ms, your origin never knows
⭐   ⇒ MISS ⇒ onward
⭐ Load balancer (⭐ L7 — it can route on path and host; ⭐⭐ TLS TERMINATES HERE)
⭐   ⇒ picks a healthy backend by least-connections; ⭐ health checks decide who exists
⭐   ⇒ ⭐⭐ adds X-Forwarded-For / X-Forwarded-Proto — the ONLY reason your app can know
⭐        the real client IP and that the user was on https (Day 009's redirect-loop bug)
⭐ nginx (Day 018) ⇒ static files served here; the rest proxied to
⭐ gunicorn ⇒ ⭐⭐ one of FOUR uvicorn worker PROCESSES — separate memory, no shared state
```

## ⭐⭐ 6. Inside the Python process — Days 003, 014, 016

```
⭐ The kernel had the socket ready; ⭐⭐ the event loop's epoll noticed it (Day 016's selectors loop)
⭐ ⇒ the ASGI server parses the request into a `scope` and calls your app
⭐ ⇒ middleware: CORS (⭐⭐ outermost, so preflights are answered before auth — Day 020),
⭐    then authentication, then the route
⭐ ⇒ ⭐ session cookie → Redis lookup → user (Day 019 — NOT a process dict, because
⭐    there are four processes and the user would log in and out at random)
⭐ ⇒ your handler runs, awaits the database, ⭐⭐ and MUST NOT BLOCK — because while it runs,
⭐    epoll is not being called, and every other connection this worker owns is frozen (Day 014).
⭐ ⇒ a response model serialises ONLY the declared fields — ⭐⭐ never the ORM object,
⭐    or password_hash goes on the wire (Day 016).
⭐ ⇒ status code chosen deliberately: 200/201/202/400/403/409/503 (Day 010), because
⭐    ⭐⭐ that code is the instruction to every retry policy and alert in the system.
```

## ⭐ 7. Back out, and into the browser — Days 012–015

```
⭐ Response → nginx → LB → CDN (⭐ cached if Cache-Control allows) → browser
⭐ ⇒ HTML parsed into the ⭐⭐ DOM; CSS into the CSSOM (⭐ render-blocking)
⭐ ⇒ a plain <script> STOPS parsing; `defer` does not
⭐ ⇒ render tree ⇒ ⭐⭐ LAYOUT ⇒ paint ⇒ composite ⇒ ⭐ FIRST PAINT
⭐ ⇒ JS runs on ⭐⭐ ONE THREAD with an event loop; fetch() calls your API for the data
⭐ ⇒ ⭐⭐ and THAT call's p95 is on the critical rendering path — 400 ms of endpoint
⭐    is 400 ms of blank screen (Day 015).
```

⭐⭐ **The count that makes the whole trace land: DNS + TCP + TLS ≈ three round trips before your
Python function has been called.** ⭐ At 100 ms RTT that is 300 ms you did not spend on anything —
which is why **connection reuse** appeared in Days 005, 008, 009 and 011 as four independent
arguments for the same conclusion.

## Interview questions

**Q: What happens when you type a URL and press Enter?**
> *(This is the ten-minute answer. Use the seven checkpoints, name a failure at each, and finish on
> the caching line. Do not summarise it — the length is the point.)*

**Q: Which part of that would you optimise first?**
> Time to first byte, because it's the part I own and usually the largest single number. `curl -w`
> decomposes the request into DNS, connect, TLS, TTFB and transfer in one command, so I'd start
> there rather than guessing. If TTFB dominates, the investigation is my application and its
> database. If TLS and connect dominate, the answer is connection reuse and a CDN closer to the
> user — and connection reuse is the same fix that shows up for the handshake, the cold congestion
> window and the TLS negotiation, which is why it's worth doing once and properly.

**Q: Where does caching happen in that path?**
> More places than people expect, and mostly without invalidation: the browser's DNS cache and the
> resolver's, the browser's HTTP cache, the CDN edge, the reverse proxy, and then application-level
> caches like Redis. Three of those — DNS, CDN and browser — expire rather than invalidate, so
> changing something means either waiting out a TTL or changing the URL. That's why hashed asset
> filenames are the whole cache strategy for static files.

**Q: You deployed, and some users still see the old version. Why?**
> Almost certainly `index.html` being cached, or a CDN edge still holding it. The hashed assets are
> fine — a new build produces new URLs — but if the document that points at those hashes is cached,
> the browser keeps requesting the old ones. `index.html` must be no-cache. The other candidate is a
> rolling deploy still in progress, in which case some requests genuinely are hitting old workers,
> which is also why migrations have to tolerate both versions running.
