# Part 1 — ⭐⭐ `src` layout, and why it is not cosmetic

```
myproject/
├── pyproject.toml          ⭐ (Day 075)
├── README.md
├── src/
│   └── myapp/              ⭐⭐ THE PACKAGE — the only importable thing
│       ├── __init__.py
│       ├── api/
│       ├── domain/
│       ├── repositories/
│       └── config.py
├── tests/                  ⭐ mirrors src/myapp/
│   ├── conftest.py         ⭐ (Day 093)
│   └── domain/test_orders.py
└── .github/workflows/ci.yml
```

```
⭐⭐ WHY src/ RATHER THAN A PACKAGE AT THE TOP LEVEL — the reason is mechanical,
⭐   and it comes straight from Day 074:
⭐
⭐   FLAT LAYOUT:  myproject/myapp/…   and you run pytest from myproject/
⭐   ⇒ ⭐⭐ '' (the CWD) IS ON sys.path ⇒ `import myapp` finds the DIRECTORY,
⭐        whether or not the package is installed or even installable.
⭐   ⇒ ⚠️ ⭐⭐ SO YOUR TESTS PASS AGAINST YOUR SOURCE TREE AND SAY NOTHING ABOUT
⭐        THE ARTEFACT YOU SHIP.
⭐
⭐   src LAYOUT: ⭐⭐ myapp is NOT importable from the project root at all. The only
⭐   way to import it is to INSTALL it (`uv pip install -e .`).
⭐   ⇒ ⭐⭐ THEREFORE YOUR TESTS RUN AGAINST THE INSTALLED PACKAGE — the same thing
⭐        your users get.
⭐   ⇒ ⭐⭐ AND IT CATCHES THE CLASSIC RELEASE BUG: a subpackage missing from the
⭐        wheel, or a data file that was never declared. ⭐ Flat layout hides both
⭐        until a user reports ModuleNotFoundError in production.
```

⭐ **`tests/` sits outside the package**, mirroring its shape, so tests ship with the repo but not with
the wheel. ⭐⭐ **And a `conftest.py` at the `tests/` root is what makes the whole tree work** (Day
093).

# Part 2 — ⭐⭐ Layers, and the direction of dependency

```
⭐⭐ THE FOUR LAYERS OF ALMOST EVERY BACKEND, AND THE ONE RULE:
⭐
⭐    api/          ⭐ HTTP. Routes, request/response schemas, status codes.
⭐      │                Knows FastAPI. Knows nothing about SQL.
⭐      ▼
⭐    services/     ⭐⭐ THE DOMAIN. Business rules. "A refund over £500 needs
⭐      │                approval." ⭐⭐ KNOWS NOTHING ABOUT HTTP OR SQL.
⭐      ▼
⭐    repositories/ ⭐ Persistence. SQLAlchemy lives here and NOWHERE ELSE.
⭐      │
⭐      ▼
⭐    db / external ⭐ Postgres, Redis, the payment gateway.
⭐
⭐   ⭐⭐ THE RULE: DEPENDENCIES POINT DOWNWARD (or inward). ⭐ A lower layer NEVER
⭐   imports an upper one. `domain` importing `fastapi` is a violation; so is
⭐   `domain` importing a SQLAlchemy model.
```

```
⭐⭐ AND THE THREE PAYOFFS, WHICH ARE THE ONLY REASON TO BOTHER:
⭐  1. ⭐⭐ THE DOMAIN IS TESTABLE WITH NO DATABASE AND NO HTTP CLIENT. Rules are
⭐       pure functions over plain objects ⇒ ⭐ milliseconds, no fixtures, no mocks
⭐       (Day 089's argument, now at architectural scale).
⭐  2. ⭐ CHANGING FRAMEWORK TOUCHES ONE LAYER. Not because you will — ⭐⭐ but
⭐       because the code that WOULD survive that change is exactly the code
⭐       that expresses your business, and separating it is valuable for its own sake.
⭐  3. ⭐⭐ YOU CAN FIND THINGS. "Where is the refund rule?" has one answer.
⭐
⭐  ⚠️ ⭐ AND THE HONEST COST: for a 300-line CRUD service, four layers is
⭐     ceremony — you write a repository that does nothing but forward. ⭐⭐ SAY
⭐     THAT OUT LOUD IN AN INTERVIEW: layering earns its keep when the DOMAIN has
⭐     RULES. If the app is "read the row, return it as JSON", ⭐ two layers is honest.
```

```python
# ⚠️ ⭐⭐ THE VIOLATION THAT HAPPENS WITHOUT ANYONE DECIDING TO:
# services/orders.py
from myapp.db.models import Order          # ⭐ a SQLAlchemy model
def cancel(order: Order):
    if order.status == "shipped": raise ...
    order.status = "cancelled"
    db.session.commit()                    # ⚠️⚠️ the domain now knows about sessions

# ⭐⭐ THE FIX IS A SEAM: the domain speaks in ITS OWN types, and someone else
# translates. (Day 056's dependency inversion, and Day 057's boundary.)
def cancel(order: OrderDTO) -> OrderDTO:   # ⭐ a dataclass. No ORM, no session.
    if order.status is Status.SHIPPED: raise CannotCancelShipped()
    return replace(order, status=Status.CANCELLED)
```

# Part 3 — ⭐⭐ A circular import is a design problem

```
⭐⭐ RECLASSIFY DAY 074'S BUG. A circular import is not "Python being awkward":
⭐
⭐   services/user.py    imports  services/order.py
⭐   services/order.py   imports  services/user.py
⭐   ⇒ ⭐⭐ YOU HAVE TWO MODULES THAT ARE REALLY ONE CONCEPT, OR A DEPENDENCY
⭐        POINTING THE WRONG WAY. The ImportError is the symptom; the design is
⭐        the disease.
⭐
⭐ ⭐ THE FOUR FIXES, RANKED BY HOW MUCH THEY ACTUALLY FIX:
⭐   1. ⭐⭐ MERGE THEM — if they genuinely are one concept, stop pretending.
⭐   2. ⭐⭐ EXTRACT THE SHARED PART into a third module both depend on ⇒ the
⭐        cycle becomes a tree. ⭐ Usually the right answer.
⭐   3. ⭐⭐ INVERT ONE DEPENDENCY with a Protocol (Day 056) ⇒ the low-level module
⭐        defines what it needs; the high-level one supplies it.
⭐   4. ⭐ `if TYPE_CHECKING:` ⇒ ⭐⭐ ONLY VALID WHEN THE CYCLE IS PURELY IN
⭐        ANNOTATIONS. ⭐ It covers a surprising share of real cycles (Day 074),
⭐        but it SILENCES rather than solves a runtime cycle.
⭐   ⚠️ ⭐ AND THE NON-FIX: moving the import inside the function. It works, and
⭐      it hides a structural problem behind a local workaround. ⭐⭐ Legitimate
⭐      only for a genuinely optional or expensive dependency.
```

```python
# ⭐⭐ MAKE THE RULE MACHINE-CHECKED — otherwise it decays in a month:
# pyproject.toml, with ruff (Day 099)
[tool.ruff.lint.flake8-tidy-imports.banned-api]
"myapp.api".msg      = "Domain code must not import the API layer."
"sqlalchemy".msg     = "Only myapp.repositories may import SQLAlchemy."
```

⭐⭐ **`import-linter`** goes further — you declare the layers and it fails CI on any violation.
⭐ **A layering rule that only lives in a README is a rule that lasts until the first deadline.**

# Part 4 — ⭐ By type or by feature, and the package's public face

```
⭐ BY TYPE (fine while small)          ⭐⭐ BY FEATURE (scales)
⭐   myapp/                              myapp/
⭐     models.py                           orders/
⭐     services.py                           router.py  service.py  repo.py  schemas.py
⭐     routers.py                          users/
⭐     schemas.py                            router.py  service.py  repo.py  schemas.py
⭐                                          shared/
⭐
⭐ ⭐⭐ THE ARGUMENT IS ABOUT WHERE CHANGES LAND: "add a field to an order" touches
⭐   FOUR FILES in the by-type layout and ONE DIRECTORY in the by-feature one.
⭐   ⇒ ⭐ by-type is honest below ~10 modules and becomes four parallel piles above it
⭐   ⇒ ⭐⭐ by-feature also makes deletion possible: a feature you can delete by
⭐        removing one directory was genuinely separable. ⭐ That is the test.
⭐   ⇒ ⭐ Django forces by-feature (apps); FastAPI leaves it to you, which is why
⭐        FastAPI projects drift into a 2000-line routers.py.
```

```python
# myapp/orders/__init__.py
from .service import cancel_order, place_order      # ⭐⭐ the package's PUBLIC API
__all__ = ["place_order", "cancel_order"]           # ⭐ and what `import *` exports

# ⇒ ⭐⭐ callers write:  from myapp.orders import place_order
#    ⭐ NOT:            from myapp.orders.service.internal import _place_impl
#    ⇒ ⭐⭐ you can restructure everything inside the package without breaking a
#         single caller — which is the entire point of a package boundary.
```

⚠️ ⭐ **Keep `__init__.py` cheap.** Everything imported there runs at `import myapp` (Day 074) — a
heavy `__init__` makes your CLI slow to start and can create cycles that only appear on install.
⭐⭐ **Re-export the public names; do not do work.**

```python
# ⭐⭐ CONFIG: read the environment ONCE, at the edge — never in the middle of a function.
# myapp/config.py
class Settings(BaseSettings):            # ⭐ pydantic-settings (Stage 4)
    database_url: str
    max_retries: int = 3

# ⚠️ ⭐⭐ THE ANTI-PATTERN, AND ITS THREE COSTS:
def charge():
    key = os.environ["STRIPE_KEY"]       # ⚠️ 1. untestable without patching the env
                                         # ⚠️ 2. fails at REQUEST time, not at STARTUP
                                         # ⚠️ 3. invisible — the dependency is not in the signature
# ⇒ ⭐⭐ BUILD SETTINGS ONCE AT STARTUP AND PASS THEM DOWN. ⭐ A missing variable
#    should stop the process on boot, loudly — not surprise one user at 3 a.m.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Flat layout | ⭐⭐ You test the source tree, not the artefact you ship. |
| ⭐⭐ **SQLAlchemy imported in the domain** | ⭐⭐ Persistence belongs to one layer. Use a DTO at the seam. |
| ⭐ A domain module importing `fastapi` | ⭐ Dependencies point downward only. |
| ⭐⭐ **Treating a circular import as a Python quirk** | ⭐⭐ It is a design violation with a compiler-enforced symptom. |
| Moving an import inside a function to "fix" it | ⭐ Hides a structural problem. Extract or invert instead. |
| ⭐ Layering rules only in the README | ⭐⭐ Enforce with `ruff` banned-api or `import-linter`. |
| Four layers for a 300-line CRUD app | ⭐ Ceremony. Layering pays when the domain has **rules**. |
| ⭐ A 2000-line `routers.py` | ⭐ By-type stopped scaling several hundred lines ago. |
| Heavy work in `__init__.py` | ⭐⭐ It runs on import — slow starts and surprise cycles. |
| ⭐⭐ **`os.environ` in the middle of a function** | ⭐⭐ Untestable, invisible, and fails at request time. |
| `tests/` inside the package | ⭐ They ship in the wheel. Keep them outside. |

## Interview questions

**Q: Why the `src` layout?**
> Because without it the current directory is on `sys.path`, so `import myapp` finds the source
> directory whether or not the package is installed or even installable — which means your tests pass
> against your source tree and tell you nothing about the artefact you ship. With `src`, the only way
> to import the package is to install it, so tests run against the same thing users get. It catches
> the classic release bug where a subpackage or a data file was never declared in the build config,
> which a flat layout hides until someone hits `ModuleNotFoundError` in production.

**Q: How do you structure a backend project?**
> By dependency direction rather than by folders. Roughly four layers — HTTP at the top, then the
> domain, then persistence, then the outside world — with the rule that dependencies only point
> downward. The important half is that the domain knows nothing about HTTP or SQL, because that's what
> makes the business rules testable with no database and no client, in milliseconds and without mocks.
> I'd also say honestly that this can be ceremony: for a 300-line CRUD service you end up writing
> repositories that just forward calls. Layering earns its keep when the domain actually has rules.

**Q: You've got a circular import. What does it mean?**
> That two modules are really one concept, or that a dependency points the wrong way. The
> `ImportError` is the symptom, not the disease — so I don't reach for the workaround first. In order:
> merge them if they genuinely are one thing; extract the shared part into a third module so the cycle
> becomes a tree, which is usually the right answer; or invert one direction with a Protocol so the
> lower module declares what it needs and the higher one supplies it. `TYPE_CHECKING` is legitimate
> when the cycle exists only in annotations, and it covers a surprising number of real cases. Moving
> the import inside a function works but hides the structural problem.

**Q: By type or by feature?**
> By feature past about ten modules. The argument is where changes land: "add a field to an order"
> touches four files in a by-type layout and one directory in a by-feature one. The other test I like
> is deletion — if you can remove a feature by deleting one directory, it was genuinely separable, and
> if you can't, the structure was lying about the coupling. By-type is honest while a project is small;
> the failure mode is a FastAPI project that's drifted into a 2000-line `routers.py`.

**Q: Where should configuration be read?**
> Once, at startup, into a settings object that gets passed down. Reading `os.environ` in the middle
> of a function costs you three things: the test has to patch the environment, the dependency is
> invisible because it isn't in the signature, and a missing variable fails at request time rather
> than at boot. I want a misconfigured process to die loudly on startup, not surprise one user at 3
> a.m. That's also the fix for the related Day 074 problem, where config read at import time means
> the test suite can't even collect.

   fail to import. Then `uv pip install -e .`.

   would ship.

    delete a required variable** and confirm it fails at boot.

## 🎙️ Articulation drill

Record two minutes: **"How would you structure a new Python backend?"**

⭐ **Lead with the principle, because folder lists are forgettable and the principle is not:**
**"structure is about which way the imports point, not about folders. I'd have HTTP at the top, the
domain in the middle, persistence at the bottom, and one rule: dependencies only point downward."**

⭐⭐ **Then justify it with the payoff rather than the theory:** *"the half that matters is that the
domain knows nothing about HTTP or SQL. That means the business rules are pure functions over plain
objects, so I can test them in milliseconds with no database, no client and no mocks. Everything else
— being able to swap a framework, being able to find where a rule lives — is secondary to that."*

⭐ **Then two concrete choices with reasons:** *"`src` layout, because otherwise the current directory
is on `sys.path` and my tests are running against my source tree rather than the artefact I ship —
which is how a missing subpackage reaches production. And by-feature packages once there are more than
about ten modules, because 'add a field to an order' should touch one directory, not four parallel
piles."*

⭐⭐ **Then the enforcement point, which is what separates a preference from a practice:** *"and I'd
make the layering machine-checked — ruff's banned-api or import-linter — because a rule that only
lives in a README lasts until the first deadline. That also reframes circular imports: they're not a
Python quirk, they're a dependency pointing the wrong way, and the ImportError is just the compiler
noticing before we did."*

⭐ **Close with the honest limit:** *"though for a small CRUD service four layers is ceremony — you end
up writing repositories that only forward. Layering earns its keep when the domain actually has
rules."*
