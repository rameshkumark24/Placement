# Day 245 🚀

**P-245** · 🚀 **Deploying a frontend** — ⭐⭐ the deploy that breaks every open tab

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: deploying a frontend does not replace the running application — every
> user with an open tab is still executing yesterday's bundle against today's API, so a frontend
> deploy is a *rollout* with two versions live, and the failure it causes is a chunk that no longer
> exists on the server.**
>
> Today: ⭐ static hosting and cache headers, ⭐⭐ the stale-tab problem, config without rebuilding,
> and rollback.

---

# Part 1 — Cache headers, the two rules

```
⭐⭐ THE ENTIRE STRATEGY IS TWO LINES, AND GETTING THEM BACKWARDS
⭐   IS THE CLASSIC FRONTEND OUTAGE.

⭐   /index.html          ⇒ ⭐⭐ Cache-Control: no-cache
⭐     ⭐ MUST be revalidated every time. It is the MANIFEST that
⭐       points at the hashed files. ⭐⭐ CACHE THIS AND USERS RUN
⭐       THE OLD APP FOREVER — and no deploy will fix it.

⭐   /assets/app.9f2c1a.js ⇒ ⭐⭐ Cache-Control: public,
⭐                             max-age=31536000, immutable
⭐     ⭐ Safe for a YEAR because ⭐⭐ THE FILENAME CHANGES WHEN THE
⭐       CONTENT CHANGES (Day 222). ⭐ There is nothing to invalidate.

⭐   ⇒ ⭐⭐ THIS IS CONTENT-ADDRESSED CACHING. ⭐ The same idea as a
⭐     git object or a content-hash key (Day 431) — the NAME IS the
⭐     version, so cache invalidation stops being a problem you have.
```

| ⭐ Getting it wrong | Symptom |
|---|---|
| `index.html` cached | ⭐⭐ Users stuck on an old app; deploys appear to do nothing |
| Hashed assets `no-cache` | ⭐ Every visit re-downloads the whole bundle |
| No hashing at all | ⭐⭐ You must purge the CDN on every deploy and pray |

# Part 2 — ⭐⭐ The stale tab

```
⭐⭐ THE FAILURE, IN ORDER

⭐   ① user opens the app at 09:00 — running build A
⭐   ② you deploy build B at 10:00. ⭐ Old chunks are DELETED.
⭐   ③ at 10:05 the user clicks a link to a lazy route
⭐   ④ ⭐⭐ THE BROWSER REQUESTS /assets/reports.OLDHASH.js
⭐   ⑤ ⭐⭐ 404. THE APP THROWS A CHUNK LOAD ERROR AND — because it
⭐     happens during render — ⭐ THE WHITE SCREEN (Day 240).

⭐   ⇒ ⭐⭐ THE USER DID NOTHING WRONG AND SEES A DEAD APP.
⭐     ⭐ It is the most common frontend production incident there is.
```

| ⭐ Fix | |
|---|---|
| **⭐⭐ Keep old assets** | Do **not** delete previous builds. Storage is pennies; keep 2–3 deploys. **This alone fixes most of it.** |
| **⭐⭐ Catch chunk errors and reload once** | A boundary that detects `ChunkLoadError`, sets a flag, and reloads — **once**, or you get a reload loop |
| **Version endpoint + a prompt** | ⭐ Poll `/version`; on change show "A new version is available — Reload". **Respectful, and it lets the user finish typing.** |
| **⭐ Service worker** | Powerful and easy to get badly wrong. Not required for this. |

```jsx
// ⭐⭐ the reload-once guard — the loop is the trap
if (/ChunkLoadError|Loading chunk .* failed/.test(error.message)) {
  if (!sessionStorage.getItem("chunk-reloaded")) {
    sessionStorage.setItem("chunk-reloaded", "1");   // ⭐ ONCE
    location.reload();
  }
}
```

> ⭐⭐ **This is a compatibility window, exactly like a database migration** (Stage 5) or a schema
> change (Day 405). **Two versions are live at once, and old clients must keep working** — which also
> means your API cannot break a contract the moment the new frontend ships.

# Part 3 — Config without rebuilding

```
⭐⭐ THE PROBLEM: import.meta.env IS BAKED IN AT BUILD TIME.
⭐   ⇒ ⭐ "same artefact to every environment" (Stage 10) is
⭐     IMPOSSIBLE if the API URL is compiled into the bundle —
⭐     you must rebuild per environment, so ⭐⭐ THE THING YOU
⭐     TESTED IN STAGING IS NOT THE THING YOU SHIP.
```

| ⭐ Approach | Trade |
|---|---|
| **Build-time env** | ⭐ Simple. One build per environment. Fine for most apps. |
| **⭐⭐ Runtime config endpoint** | `/config.json` fetched at startup, `no-cache`. **One artefact, every environment.** Costs one request before the app starts. |
| **Injected `<script>` in `index.html`** | ⭐ The server templates `window.__CONFIG__`. No extra request, needs a real server. |
| **Same-origin `/api`** | ⭐⭐ **Removes the problem entirely** — no URL to configure (Day 237) |

> ⭐ **And whichever you pick: no secrets** (Day 222). Runtime config is still public — it is a
> deployment convenience, not a confidentiality mechanism.

# Part 4 — Rollout and rollback

```
⭐⭐ THE FRONTEND'S ADVANTAGE: ROLLBACK IS ALMOST FREE.

⭐   ⭐ There is no state, no migration, no draining connections —
⭐     just a different set of static files. ⭐⭐ SO REVERTING IS
⭐     REPOINTING A SYMLINK OR AN ALIAS, AND IT IS SECONDS.
⭐   ⇒ ⭐⭐ WHICH MEANS: ROLL FORWARD FAST, ROLL BACK FASTER, AND
⭐     RANK CHANGES BY ROLLBACK COST (Day 459) — a frontend change
⭐     sits at the CHEAP end, so ship small and often.

⭐   ⭐ THE EXCEPTION THAT IS NOT CHEAP: a frontend change that
⭐     required an API change. ⭐⭐ NOW ROLLING BACK THE UI LEAVES
⭐     THE API AHEAD. ⇒ SHIP THE API FIRST, BACKWARD-COMPATIBLE,
⭐     THEN THE UI.
```

| ⭐ Practice | |
|---|---|
| **Preview deploys per PR** | ⭐⭐ Every branch gets a URL. **Reviewers click instead of imagining.** The highest-value CI feature a frontend has. |
| **Smoke test after deploy** | ⭐ Load the page, assert the bundle parses, assert one API call works |
| **⭐ Source maps to Sentry, not the CDN** | Day 222 |
| **Deploy = a new immutable directory** | ⭐ Never overwrite in place; that is what makes rollback trivial |

## Today's build

1. Deploy your app. ⭐⭐ **Inspect the response headers** for `index.html` and a hashed asset. Fix them if wrong.
2. ⭐⭐ **Reproduce the stale-tab failure.** Open the app, deploy a change that removes an old chunk, then click a lazy route in the *old* tab. **Watch the white screen.**
3. ⭐ Add the reload-once guard. Verify it does not loop.
4. ⭐⭐ Cache `index.html` for an hour on purpose. Deploy twice. **Confirm nothing changes for the user** — then fix it.
5. ⭐ Move your API URL to a runtime `/config.json`. Deploy the *same* artefact to two environments.
6. ⭐ Set up preview deploys, then roll back a deploy and time it.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "what happens when you deploy a frontend?"**

Lead with the thing that reframes it. **Deploying doesn't replace the running app. Every user with an
open tab is still executing yesterday's bundle against today's API. So a frontend deploy is a rollout
with two versions live, not a swap.**

Then the failure that follows from that. **The tab was opened at nine, I deploy at ten and the old
chunks are deleted, and at five past the user clicks a lazily loaded route. The browser requests a
chunk that no longer exists, gets a 404, and because it fails during render the whole app unmounts —
white screen. The user did nothing wrong. It's the most common frontend production incident there is,
and most of it is fixed by simply not deleting the previous build.**

Then the caching rules, briefly, because they are the other classic outage. **`index.html` is
`no-cache` because it's the manifest pointing at the hashed files — cache it and users run the old app
forever and no deploy fixes it. Hashed assets are immutable for a year, safely, because the name
changes when the content does. That's content-addressed caching: the name is the version, so
invalidation stops being a problem I have.**

Close on what makes frontend deploys pleasant. **Rollback is nearly free — no state, no migration, just
a different set of static files, so reverting is repointing an alias in seconds. That means shipping
small and often is the right strategy. The exception is a UI change that needed an API change: rolling
back the UI then leaves the API ahead, so the API ships first and backward-compatible.**
