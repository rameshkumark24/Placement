# Day 198

**L-198** · 🐘 **JSONB** — ⭐⭐ schemaless columns in a relational database, and the three times it is the wrong answer

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: "schemaless" does not mean there is no schema. It means the schema moved
> into your application code, undocumented, unenforced, duplicated in three places — and old rows keep
> the old shape forever, because nothing migrates them.**
>
> ⭐ JSONB is genuinely excellent, and it is the most misused feature in Postgres. ⭐⭐ Today is
> both halves: how to index and query it properly, and the honest list of when a column would have
> been better.

---

# Part 1 — ⭐ `json` vs `jsonb`, in one table

```
⭐   json                          ⭐⭐ jsonb
⭐   stores the TEXT verbatim      stores a PARSED BINARY tree
⭐   preserves key order           ⭐ keys reordered (sorted by
⭐                                   length then bytes)
⭐   preserves whitespace          whitespace discarded
⭐   keeps DUPLICATE keys          ⭐⭐ duplicates collapsed, last wins
⭐   ⭐ fast to WRITE              ⭐ slightly slower to write
⭐   ⭐⭐ RE-PARSED ON EVERY READ   ⭐⭐ NO PARSING ON READ
⭐   ⭐⭐ CANNOT BE INDEXED         ⭐⭐ GIN-INDEXABLE
⭐
⭐ ⇒ ⭐⭐ USE `jsonb`. ALWAYS. The single exception: an audit or webhook
⭐   log where you must prove you stored EXACTLY the bytes you received
⭐   (Day 158's HMAC over raw bytes is the same principle) — ⭐ and then
⭐   store the raw payload as `text` or `bytea` and a `jsonb` copy for
⭐   querying. ⭐⭐ Not `json`; that gives you neither.
```

# Part 2 — ⭐⭐ Operators, and the one that decides your index

```sql
data = '{"user":{"name":"Priya","tags":["a","b"]},"score":42,"ok":true}'

data -> 'score'              -- ⭐ 42        AS JSONB
data ->> 'score'             -- ⭐ '42'      AS TEXT   ⭐⭐ note the type
data -> 'user' ->> 'name'    -- ⭐ 'Priya'
data #> '{user,name}'        -- ⭐ path, as jsonb
data #>> '{user,name}'       -- ⭐ path, as text

-- ⭐⭐ CONTAINMENT — the operator the whole indexing story is built on:
data @> '{"score": 42}'                    -- ⭐⭐ "contains this"
data @> '{"user": {"name": "Priya"}}'      -- ⭐ nested, works
data @> '{"user": {"tags": ["a"]}}'        -- ⭐⭐ array containment too

data ? 'score'               -- ⭐ has key
data ?| array['a','b']       -- ⭐ has any of these keys
data ?& array['a','b']       -- ⭐ has all
data || '{"x":1}'            -- ⭐ merge (shallow!)
data - 'score'               -- ⭐ delete key
data #- '{user,name}'        -- ⭐ delete at path
jsonb_set(data,'{score}','99')          -- ⭐ set at path
data @? '$.user.tags[*] ? (@ == "a")'   -- ⭐ jsonpath exists
data @@ '$.score > 40'                  -- ⭐ jsonpath predicate
```

```
⭐⭐ THE TYPE TRAP THAT PRODUCES WRONG ANSWERS SILENTLY:
⭐   WHERE data ->> 'score' > '40'      -- ⭐⭐ TEXT COMPARISON.
⭐                                      --   '9' > '40' IS TRUE.
⭐   WHERE (data ->> 'score')::int > 40 -- ✅ ⭐ cast, always
⭐   WHERE data @> '{"score": 42}'      -- ✅ ⭐ typed, and INDEXABLE
⭐ ⇒ ⭐⭐ EVERY `->>` IN A COMPARISON NEEDS A CAST, AND EVERY CAST IS A
⭐   FUNCTION ON THE COLUMN (Day 189 ①) — which is why Part 3 exists.
```

# Part 3 — ⭐⭐ Indexing, and the statistics problem nobody mentions

```sql
-- ⭐ ① GIN, default operator class — the general-purpose choice
CREATE INDEX ON events USING gin (data);
-- ⭐ supports: @>  ?  ?|  ?&  and jsonpath @? @@
-- ⭐⭐ indexes EVERY key AND EVERY value ⇒ large.

-- ⭐ ② GIN with jsonb_path_ops — ⭐⭐ ~2–3× SMALLER AND FASTER
CREATE INDEX ON events USING gin (data jsonb_path_ops);
-- ⭐⭐ SUPPORTS ONLY `@>`. ⭐ If containment is your only query shape —
--    and it usually is — this is the right choice.

-- ⭐ ③ GIN on a SUB-PATH — when you only query one branch
CREATE INDEX ON events USING gin ((data -> 'user') jsonb_path_ops);

-- ⭐⭐ ④ AN EXPRESSION B-TREE INDEX — and this is the one that matters
--    most, for a reason that has nothing to do with speed:
CREATE INDEX ON events ((data ->> 'status'));
CREATE INDEX ON events (((data ->> 'score')::int));
```

```
⭐⭐ WHY ④ IS THE HIGHEST-VALUE INDEX HERE:

⭐   ⭐⭐ THE PLANNER HAS ***NO STATISTICS*** FOR A JSONB EXPRESSION.
⭐     `WHERE data ->> 'status' = 'failed'` is opaque to it, so it falls
⭐     back to a FIXED DEFAULT SELECTIVITY guess (~0.5% for equality).
⭐   ⇒ ⭐⭐ IT ESTIMATES 1 ROW AND GETS 91,000 (Day 193, Query 6). ⇒
⭐     nested loop ⇒ minutes.
⭐   ⭐⭐ AN EXPRESSION INDEX GETS ***ITS OWN STATISTICS***: ANALYZE
⭐     builds a histogram and MCV list for the expression.
⭐   ⇒ ⭐⭐ SO IT FIXES THE ESTIMATE ***AND*** GIVES YOU AN INDEX. Two
⭐     problems, one DDL — and the estimate half is usually the bigger
⭐     win. ⭐ Very few people know this.

⭐⭐ AND THE B-TREE-ONLY CAPABILITIES: RANGES AND SORTING. GIN cannot do
⭐   `ORDER BY (data->>'score')::int` or `> 40`. ⭐ Only an expression
⭐   B-tree can.

⭐⭐ THE COST SIDE, STATED PLAINLY (Day 190): GIN IS SLOW TO UPDATE. It
⭐   maintains a pending list flushed in bulk, so ⭐⭐ ONE UNLUCKY INSERT
⭐   PAYS FOR EVERYBODY'S — a latency spike with no query to blame.
⭐   ⭐ `fastupdate=off` trades steady slower writes for no spikes; on a
⭐     latency-sensitive path that is often the right trade.
```

# Part 4 — ⭐⭐ The write amplification nobody warns you about

```
⭐⭐ MVCC (DAY 194) + TOAST (DAY 186) MEET HERE, AND THE RESULT IS BAD:

⭐   UPDATE events SET data = jsonb_set(data, '{seen}', 'true')
⭐   WHERE id = 5;                 -- ⭐ "I changed one boolean"

⭐   ⭐⭐ WHAT ACTUALLY HAPPENS:
⭐     ① there is no partial update of a jsonb value. The WHOLE document
⭐        is rewritten.
⭐     ② MVCC writes a NEW ROW VERSION containing the whole document.
⭐     ③ if it is >2 KB it is COMPRESSED AND TOASTED — ⭐⭐ the entire
⭐        TOAST chain is rewritten too.
⭐     ④ the WAL record contains all of it.
⭐     ⑤ every index on the table gets a new entry (unless HOT, and a
⭐        50 KB row rarely fits twice on a page, ⭐⭐ SO HOT ALMOST NEVER
⭐        APPLIES TO BIG JSONB ROWS).
⭐
⭐   ⇒ ⭐⭐ FLIPPING ONE BOOLEAN IN A 50 KB DOCUMENT WRITES ~50 KB TO
⭐     THE HEAP, ~50 KB TO THE WAL, AND BLOATS THE TABLE BY 50 KB UNTIL
⭐     VACUUM. ⭐ Do that on every request and you have built a
⭐     write-amplification machine.
⭐   ⇒ ⭐⭐ THE RULE: ***JSONB IS FOR DATA THAT IS WRITTEN ONCE AND READ
⭐     MANY TIMES.*** A frequently-mutated field belongs in its own
⭐     column — where an update is 4 bytes and can be HOT.
```

# Part 5 — ⭐⭐ When it is right, when it is wrong, and the hybrid

```
⭐⭐ USE JSONB WHEN:
⭐   ✅ ⭐ AN EXTERNAL PAYLOAD STORED VERBATIM — a webhook body, a
⭐        provider response. ⭐⭐ You did not design it and it will change
⭐        without telling you. Perfect fit.
⭐   ✅ ⭐ GENUINELY USER-DEFINED ATTRIBUTES — custom fields your
⭐        customers create. ⭐⭐ This is the case EAV was invented for
⭐        (Day 188) and jsonb does it better in every respect.
⭐   ✅ ⭐ SPARSE, HETEROGENEOUS ATTRIBUTES across product types where a
⭐        table would be 200 mostly-null columns.
⭐   ✅ ⭐ A SETTINGS / FEATURE-FLAG BLOB read as a whole.
⭐   ✅ ⭐ AN EVENT PAYLOAD in an outbox or audit table — ⭐ append-only,
⭐        which is exactly Part 4's ideal.

⭐⭐ DO ***NOT*** USE JSONB WHEN — and each of these is a real cost:
⭐   ❌ ⭐⭐ YOU FILTER OR SORT ON IT EVERY REQUEST. That is a column.
⭐   ❌ ⭐⭐ IT SHOULD HAVE A FOREIGN KEY. `data->>'user_id'` CANNOT
⭐        REFERENCE `users`. There is no integrity, ever, and orphans
⭐        accumulate silently (Day 188's polymorphic argument again).
⭐   ❌ ⭐⭐ IT HAS A REAL CONSTRAINT — NOT NULL, UNIQUE, a CHECK. You
⭐        can partly fake these; you will not maintain the fakes.
⭐   ❌ ⭐⭐ IT IS UPDATED FREQUENTLY (Part 4).
⭐   ❌ ⭐⭐ THE SHAPE IS ACTUALLY FIXED AND YOU ARE AVOIDING MIGRATIONS.
⭐        ⭐ This is the real reason most jsonb columns exist, and the
⭐        bill arrives later: ⭐⭐ THERE IS NO MIGRATION, SO ROWS FROM
⭐        2024 STILL HAVE THE 2024 SHAPE, AND EVERY READER MUST HANDLE
⭐        EVERY HISTORICAL SHAPE FOREVER. You did not avoid the
⭐        migration; you deferred it into every code path.
```

```sql
-- ⭐⭐ THE HYBRID, WHICH IS ALMOST ALWAYS THE RIGHT DESIGN:
CREATE TABLE events (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   int  NOT NULL REFERENCES tenants,   -- ⭐ promoted
    type        text NOT NULL,                      -- ⭐ promoted
    occurred_at timestamptz NOT NULL,               -- ⭐ promoted
    status      text NOT NULL DEFAULT 'new',        -- ⭐⭐ promoted
                                                    --   BECAUSE IT
                                                    --   CHANGES OFTEN
    payload     jsonb NOT NULL                      -- ⭐ the tail
);
-- ⭐⭐ THE RULE: ***PROMOTE ANYTHING YOU FILTER ON, SORT ON, JOIN ON,
--    CONSTRAIN, OR UPDATE.*** Everything else stays in the document.

-- ⭐⭐ AND THE MIDDLE GROUND — A GENERATED COLUMN:
ALTER TABLE events ADD COLUMN score int
  GENERATED ALWAYS AS ((payload ->> 'score')::int) STORED;
CREATE INDEX ON events (score);
ALTER TABLE events ADD CHECK (score >= 0);
-- ⭐⭐ A REAL, TYPED, INDEXABLE, CONSTRAINABLE COLUMN THAT CANNOT DRIFT
--    FROM THE DOCUMENT, because you cannot write to it directly.
-- ⭐ Cost: it is STORED (extra space), and changing the expression
--   rewrites the table. ⭐⭐ Still the best of both for a hot field.

-- ⭐ AND YOU CAN CONSTRAIN THE DOCUMENT ITSELF:
ALTER TABLE events ADD CHECK (jsonb_typeof(payload) = 'object');
ALTER TABLE events ADD CHECK (payload ? 'version');
-- ⭐⭐ `pg_jsonschema` gives you full JSON Schema validation in a CHECK
--    if you need it. ⭐ Most teams should at least assert the two above.
```

# Part 6 — ⭐⭐ The Python side, and the silent data loss

```python
from sqlalchemy.dialects.postgresql import JSONB
from sqlalchemy.ext.mutable import MutableDict

class Event(Base):
    payload: Mapped[dict] = mapped_column(JSONB)

# ⭐⭐ THE BUG. THIS IS THE MOST IMPORTANT THING ON THIS PAGE.
event.payload["seen"] = True
session.commit()
# ⭐⭐ ***NOTHING IS WRITTEN.*** No error. No warning. The change is
#    silently discarded, and it comes back on the next request.
# ⭐ WHY: SQLAlchemy detects changes by comparing ATTRIBUTE IDENTITY.
#   `event.payload` is the SAME dict object before and after, so the
#   unit of work (Day 135) sees no change. ⭐⭐ MUTATING A NESTED
#   STRUCTURE IS INVISIBLE TO THE ORM.

# ✅ FIX ①  — replace the object:
event.payload = {**event.payload, "seen": True}
# ✅ FIX ②  — tell it explicitly:
from sqlalchemy.orm.attributes import flag_modified
event.payload["seen"] = True
flag_modified(event, "payload")
# ✅ FIX ③ ⭐⭐ — THE STRUCTURAL ONE. Make the type track mutations:
payload: Mapped[dict] = mapped_column(MutableDict.as_mutable(JSONB))
# ⭐ Now `event.payload["seen"] = True` is detected. ⭐⭐ Note it is
#   SHALLOW: nested dicts still need `MutableList`/nested handling or
#   fix ①. ⭐ Django has the identical trap with `JSONField`.
```

```python
# ⭐⭐ AND THE DISCIPLINE THAT SAVES THE COLUMN FROM ITSELF:
#    VALIDATE ON THE WAY IN, EVEN THOUGH THE DATABASE WILL NOT.
class WebhookPayload(BaseModel):
    version: Literal[1, 2]
    event_id: str
    amount_cents: int = Field(ge=0)
    model_config = ConfigDict(extra="allow")   # ⭐ Day 161: keep
                                               #   unknown fields
event.payload = WebhookPayload(**body).model_dump()
# ⭐⭐ YOU HAVE JUST REBUILT A SCHEMA — in one place, in code, versioned,
#    testable. ⭐⭐ THAT IS THE MINIMUM PRICE OF "SCHEMALESS". Teams that
#    skip it discover, two years in, that six shapes exist in the column
#    and no document says which.
# ⭐ And ALWAYS write a `version` key. ⭐⭐ It is the only thing that
#   makes a future migration of the documents possible at all.
```

```sql
-- ⭐ Querying from SQLAlchemy, so it stays indexable:
select(Event).where(Event.payload.contains({"status": "failed"}))   # @>
select(Event).where(Event.payload["score"].as_integer() > 40)
select(Event).where(Event.payload["user"]["name"].astext == "Priya")
-- ⭐⭐ CHECK THE GENERATED SQL FOR EACH ONE AND `EXPLAIN` IT. The ORM
--    makes it easy to write a query that cannot use your GIN index.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Using `json` instead of `jsonb` | Re-parsed on every read and cannot be indexed. |
| `data ->> 'score' > '40'` | Text comparison — `'9' > '40'` is true. Cast, or use `@>`. |
| A default GIN index when you only use `@>` | `jsonb_path_ops` is 2–3× smaller and faster. |
| Expecting GIN to serve ranges or `ORDER BY` | Only an expression B-tree can. |
| Not knowing the planner has no JSONB statistics | It guesses a fixed selectivity. An expression index gives it real ones. |
| GIN on a high-write column | The pending-list flush spikes one unlucky insert. Consider `fastupdate=off`. |
| Updating one key in a large document per request | The whole document, TOAST chain and WAL are rewritten, and HOT rarely applies. |
| Putting a frequently filtered field in JSONB | That's a column. |
| Expecting referential integrity from `data->>'user_id'` | There is none, ever. Orphans accumulate silently. |
| Using JSONB to avoid migrations | You deferred the migration into every code path, forever. |
| No `version` key in the document | Nothing makes a future document migration possible. |
| No validation on write | Six shapes end up in the column and no document says which. |
| `obj.payload["x"] = 1` with plain `JSONB` | Silently discarded. Use `MutableDict`, `flag_modified`, or reassign. |
| Assuming `MutableDict` handles nested mutation | It's shallow. |
| Not checking the SQL the ORM generates for JSONB filters | It's easy to write a query that can't use your GIN index. |

## Interview questions

**Q: When would you use JSONB and when is it a mistake?**

> It's right for data you didn't design and can't control — a webhook body or a provider response
> stored verbatim; genuinely user-defined custom fields, which is the case EAV was invented for and
> which jsonb does better in every respect; sparse heterogeneous attributes that would otherwise be two
> hundred mostly-null columns; and append-only event or audit payloads. It's wrong when you filter or
> sort on it every request, because that's a column; when it should have a foreign key, because
> `data->>'user_id'` can't reference anything and orphans accumulate with nothing to catch them; when
> it has a real constraint you'd want enforced; and when it's updated frequently. And the one people
> don't admit: using it to avoid writing migrations. That's the real reason most jsonb columns exist,
> and the bill is that rows written two years ago still have the two-year-old shape, so every reader
> has to handle every historical shape forever. You didn't avoid the migration, you deferred it into
> every code path.

**Q: How do you index a JSONB column?**

> It depends on the query shape, and there are really two families. For containment queries — `@>` —
> a GIN index, and specifically `jsonb_path_ops` rather than the default operator class if containment
> is all you use, because it's two to three times smaller and faster; the default supports key-existence
> operators too, which you often don't need. For equality on one key, or any range or `ORDER BY`, you
> need an expression B-tree on `(data ->> 'status')` or the cast version, because GIN simply can't
> order. The thing I'd emphasise is that the expression index isn't primarily about speed. The planner
> has *no statistics* for a JSONB expression, so it falls back to a fixed default selectivity —
> estimates one row, gets ninety thousand, picks a nested loop, and the query takes minutes. An
> expression index gets its own histogram and most-common-values list from `ANALYZE`, so it fixes the
> estimate as well as providing the index. Two problems, one piece of DDL, and the estimate half is
> usually the bigger win.

**Q: What happens when you update one key in a large JSONB document?**

> The whole thing is rewritten. There's no partial update of a jsonb value, so `jsonb_set` produces a
> complete new document; MVCC then writes an entirely new row version containing it; if it's over about
> two kilobytes the TOAST chain is rewritten and recompressed; the WAL record carries all of it; and
> every index gets a new entry, because HOT needs the new version to fit on the same page and a large
> document rarely does. So flipping one boolean in a fifty-kilobyte document writes about fifty
> kilobytes to the heap, fifty to the WAL, and bloats the table by fifty until vacuum. That gives a
> simple design rule: JSONB is for data written once and read many times. Anything mutated per request
> belongs in its own column, where the update is a few bytes and can be heap-only.

**Q: What's the SQLAlchemy trap with JSONB?**

> Mutating in place doesn't mark the object dirty. `event.payload["seen"] = True` followed by a commit
> writes nothing — no error, no warning, and the change reappears as missing on the next request.
> SQLAlchemy's unit of work detects changes by comparing attribute identity, and the dict object is the
> same object before and after, so the mutation is invisible. There are three fixes: reassign a new
> dict, call `flag_modified` explicitly, or — the structural one — declare the column as
> `MutableDict.as_mutable(JSONB)` so the type tracks mutations, with the caveat that it's shallow and
> nested structures still need care. Django's `JSONField` has exactly the same trap. It's worth
> knowing because the failure is silent data loss rather than an exception, which is the worst kind.

**Q: How do you keep a JSONB column from becoming a swamp?**

> Four things, all of which are just rebuilding the guarantees you gave up. Validate on write with a
> Pydantic model, so the schema exists in one versioned, testable place rather than implicitly across
> six call sites — that's the minimum price of "schemaless" and skipping it is how a column ends up
> with six shapes and no document saying which. Always write a `version` key, because it's the only
> thing that makes a future document migration possible at all. Add cheap CHECK constraints —
> `jsonb_typeof(payload) = 'object'` and existence of the required keys, or full JSON Schema via
> `pg_jsonschema`. And promote anything you filter on, sort on, join on, constrain or update into a
> real column — with a generated column as the middle ground, since
> `GENERATED ALWAYS AS ((payload->>'score')::int) STORED` gives you a typed, indexable, constrainable
> column that can't drift from the document because you can't write to it directly.

## 🎙️ Articulation drill

**Two minutes: "When would you use JSONB?"**

Open by refusing the framing that it's relational-versus-document. Give the cases where it genuinely
wins — a payload you didn't design, user-defined custom fields, sparse attributes, append-only event
bodies — and then the promotion rule, which is the real content: **anything you filter on, sort on,
join on, constrain or update belongs in a column; the tail stays in the document.** Then two facts that
show you've operated one. First the write cost: **updating one key rewrites the entire document, the
TOAST chain and the WAL, and HOT rarely applies to a large row** — so JSONB is for write-once,
read-many. Second the planner: **there are no statistics for a JSONB expression, so it guesses, and an
expression index fixes the estimate as well as adding an index.** Close on the honest line: schemaless
doesn't mean no schema, it means the schema moved into your code undocumented, and old rows keep their
old shape forever — so you validate on write, you write a `version` key, and you accept that's the
minimum price.
