# Day 092

**L-092** · 🧪 **The testing block opens** — the pyramid, FIRST, and what a test is actually for

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a test suite's job is not to prove your code is correct — it is to let
> you change your code without fear, which is why a slow, flaky or implementation-coupled suite is
> worse than useless: it costs you the confidence it was bought to provide.**
>
> ⭐ Seven days on testing, because it is the largest single gap between someone who can write Python
> and someone a team will hire. **Today is the thinking; Days 093–094 are pytest itself.**

---

# Part 1 — ⭐⭐ What tests are for

```
⭐⭐ FOUR JOBS, IN ORDER OF HOW MUCH THEY ARE WORTH:
⭐
⭐ 1. ⭐⭐ THEY LET YOU CHANGE THE CODE. This is the whole product. Day 091 said
⭐      refactoring requires a way to know behaviour did not change — ⭐⭐ THE TEST
⭐      SUITE IS THAT WAY. Without it you do not refactor; you rewrite and hope.
⭐ 2. ⭐ THEY CATCH REGRESSIONS — the thing that worked last month and quietly
⭐      stopped working. ⭐ Humans are bad at re-checking; machines are not.
⭐ 3. ⭐ THEY DOCUMENT BEHAVIOUR — ⭐⭐ and unlike a comment (Day 089) or a README,
⭐      a test that drifts out of date FAILS. It is the only documentation with
⭐      an enforcement mechanism.
⭐ 4. ⭐⭐ THEY APPLY DESIGN PRESSURE. Code that is hard to test is badly designed
⭐      (Day 089) — ⭐ testing tells you before your users do.
⭐
⭐ ⚠️ ⭐⭐ AND WHAT THEY DO NOT DO: PROVE CORRECTNESS. Dijkstra's line is exactly
⭐    right — testing shows the presence of bugs, never their absence. ⭐ A green
⭐    suite means "the things I thought of still work". ⭐⭐ Say that out loud;
⭐    people who oversell tests are trusted less, not more.
```

```
⭐⭐ THE COROLLARY MOST PEOPLE MISS: A TEST SUITE IS CODE YOU MAINTAIN FOREVER.
⭐   ⇒ ⭐ every test costs: it must be read, updated, and re-understood after each
⭐        refactor. ⭐⭐ A test that breaks on every refactor without ever catching
⭐        a bug is a NET LIABILITY, and deleting it is a legitimate act.
⭐   ⇒ ⭐⭐ SO THE QUESTION IS NOT "IS THIS TESTED?" BUT "WHAT WOULD THIS TEST
⭐        CATCH, AND WHAT WILL IT COST ME WHEN I RESTRUCTURE?"
```

# Part 2 — ⭐⭐ The pyramid, and the honest version

```
⭐              ╱╲          E2E — the real system, a browser or a live HTTP call
⭐             ╱  ╲         ⭐ seconds each · ⭐⭐ flaky · ⭐ tells you IT WORKS
⭐            ╱────╲
⭐           ╱      ╲       INTEGRATION — your code + a real database / real HTTP
⭐          ╱        ╲      ⭐ tens to hundreds of ms · ⭐⭐ finds SEAM bugs
⭐         ╱──────────╲
⭐        ╱            ╲    UNIT — one function or class, no I/O
⭐       ╱______________╲   ⭐⭐ MILLISECONDS · ⭐ pinpoints the failure exactly
⭐
⭐⭐ THE AXIS IS NOT "SIZE". IT IS SPEED × BLAST RADIUS:
⭐   ⇒ ⭐⭐ FAST tests get run constantly ⇒ they catch mistakes SECONDS after you
⭐        make them, when the context is still in your head. ⭐ That is where
⭐        nearly all of the value comes from.
⭐   ⇒ ⭐ A SLOW test gets run in CI ⇒ you find out 20 minutes later, having moved on.
⭐   ⇒ ⭐⭐ A test that only fails SOMETIMES is worse than no test (Part 4).
```

| ⚠️ Anti-shape | ⭐ Why it fails |
|---|---|
| ⭐⭐ **Ice-cream cone** (mostly e2e) | ⭐⭐ 40-minute suite, flaky, and a failure says "something broke somewhere" |
| ⭐ Hourglass (unit + e2e, no middle) | ⭐ Every unit passes, the system does not work — nothing tests the seams |
| ⭐ All unit, heavily mocked | ⭐⭐ Green suite, broken app: **you tested your mocks** (Day 095) |

```
⭐⭐ AND THE HONEST POSITION, WHICH IS BETTER THAN RECITING THE PYRAMID:
⭐   THE "TESTING TROPHY" ARGUMENT (Kent C. Dodds) is that for a typical BACKEND
⭐   SERVICE the fat layer should be INTEGRATION, not unit — because most real
⭐   bugs are AT THE SEAMS: the query, the serialisation, the migration, the
⭐   HTTP contract. ⭐⭐ A unit test of a pure pricing rule rarely fails in
⭐   production; the ORM relationship does.
⭐
⭐   ⇒ ⭐⭐ MY POSITION, AND SAY IT THIS WAY: many fast unit tests for anything
⭐        with real LOGIC (Day 090's domain layer — no database needed, so they
⭐        are cheap), a SUBSTANTIAL layer of integration tests through the API
⭐        with a real database, and a HANDFUL of e2e tests over the critical
⭐        journeys only. ⭐ The pyramid's proportions are a heuristic; ⭐⭐ the
⭐        speed-versus-confidence trade-off is the actual law.
```

# Part 3 — ⭐ FIRST, and what each letter prevents

| ⭐ Letter | ⭐ Means | ⭐⭐ The failure it prevents |
|---|---|---|
| ⭐⭐ **F**ast | milliseconds | ⭐⭐ A slow suite is **not run**. Unrun tests catch nothing |
| ⭐⭐ **I**solated | ⭐ no shared state, any order | ⭐⭐ Order dependence — **the worst kind of flake** |
| **R**epeatable | same result every time | ⭐ No network, no real clock, no unseeded random |
| **S**elf-validating | pass/fail, no human | ⭐ A test whose output you must *read* is a script |
| ⭐ **T**imely | written with the code | ⭐ Tests written months later test what the code *does* |

```
⭐⭐ ISOLATION IS THE ONE THAT GOES WRONG QUIETLY, AND THE FIX IS ONE FLAG:
⭐   test_a creates a user; test_b assumes that user exists. ⇒ ⭐ passes today.
⭐   ⇒ ⭐⭐ then someone runs `pytest -k b`, or the suite is parallelised with
⭐        xdist, or a test is renamed and the ORDER CHANGES ⇒ mysterious failure.
⭐   ⇒ ⭐⭐ THE FIX AS A HABIT: `pytest-randomly` shuffles test order every run.
⭐        ⭐ It turns a latent order dependence into an immediate, obvious failure
⭐        — which is exactly what you want a test suite to do.
```

# Part 4 — ⭐⭐ Test behaviour, not implementation

```python
# ⚠️ ⭐⭐ COUPLED TO IMPLEMENTATION — this test's job is now to break:
def test_discount():
    calc = PriceCalculator()
    assert calc._apply_tier_rules(order) == 90          # ⚠️ a PRIVATE method
    assert calc._cache_hits == 1                        # ⚠️ an internal detail

# ⭐⭐ COUPLED TO BEHAVIOUR — survives any refactor that keeps the promise:
def test_orders_over_100_get_10_percent_discount():
    order = Order(items=[Item(price=Decimal("100"))])
    assert PriceCalculator().total(order) == Decimal("90")
```

```
⭐⭐ THE TEST: IF A PURE REFACTOR (Day 091 — behaviour unchanged) BREAKS YOUR
⭐   TEST, THE TEST WAS WRONG, NOT THE REFACTOR.
⭐   ⇒ ⭐⭐ that is the precise, checkable definition of "testing implementation",
⭐        and it is worth stating exactly like that in an interview.
⭐   ⇒ ⭐ so: test through the PUBLIC interface. Assert on RETURN VALUES and on
⭐        OBSERVABLE EFFECTS (the row that exists, the email that was queued) —
⭐        ⭐⭐ not on which private methods were called in which order (Day 095).
⭐   ⇒ ⚠️ ⭐ AND THE COUNTERWEIGHT: a complex private algorithm sometimes deserves
⭐        direct tests. ⭐⭐ But that usually means it wants to BE a public unit of
⭐        its own — the test is telling you about a missing seam (Day 090).
```

```python
def test_refund_over_500_requires_approval():      # ⭐⭐ THE NAME STATES THE RULE
    refund = Refund(amount=Decimal("501"))         # ⭐ ARRANGE

    result = process(refund)                       # ⭐ ACT

    assert result.status is Status.PENDING_APPROVAL  # ⭐ ASSERT — one behaviour
```

⭐⭐ **The name is the most under-used feature of a test.** `test_process_2` tells a failing CI run
nothing; **`test_refund_over_500_requires_approval` tells you the broken business rule from the
failure line alone**, before you open a single file. ⭐ And a suite named this way *is* a readable
specification of the system.

# Part 5 — ⭐⭐ Flaky tests

```
⭐⭐ A FLAKY TEST — one that passes and fails on the same code — IS WORSE THAN NO
⭐   TEST, AND THE REASON IS SOCIAL RATHER THAN TECHNICAL:
⭐   ⇒ ⭐⭐ IT TRAINS THE TEAM TO RE-RUN CI INSTEAD OF READING FAILURES. Once that
⭐        habit exists, ⭐⭐ A REAL FAILURE GETS RE-RUN TOO, and the suite has
⭐        stopped protecting anything while still costing twenty minutes a build.
```

| ⭐ Cause | ⭐ Fix |
|---|---|
| ⭐ Real clock / `datetime.now()` | ⭐⭐ Inject the clock (Day 089); `freezegun`/`time-machine` |
| ⭐⭐ **Order dependence / shared state** | ⭐⭐ Fresh fixtures; `pytest-randomly` to expose it |
| Network calls | ⭐ Stub the boundary (Day 095) |
| ⭐ Unseeded randomness | ⭐ Seed it, and print the seed on failure |
| ⭐⭐ Concurrency / `sleep(0.1)` and hope | ⭐⭐ Wait on a **condition**, never a duration (Day 066) |
| Filesystem / CWD | ⭐ `tmp_path` (Day 094) |
| Test-order-dependent DB ids | ⭐ Do not assert on generated ids |

```
⭐⭐ THE POLICY, AND HAVING ONE IS THE ANSWER TO "HOW DO YOU HANDLE FLAKES":
⭐   1. ⭐ a flaky test is a BUG with a ticket, not background noise
⭐   2. ⭐⭐ QUARANTINE it (mark it, exclude it from the gate) THE SAME DAY
⭐   3. fix it or delete it within a sprint
⭐   4. ⭐⭐ NEVER "re-run until green" as a norm — that is the habit that kills
⭐        the suite
⭐   ⇒ ⚠️ ⭐ `pytest-rerunfailures` is a PAINKILLER. Used as policy it is how a
⭐        team stops noticing that its tests no longer work.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ "Tests prove the code is correct" | ⭐⭐ They show the presence of bugs, never absence. |
| ⭐⭐ **Asserting on private methods** | ⭐⭐ A pure refactor breaks it ⇒ the test was wrong. |
| Asserting on call order | ⭐ That is the implementation, not the behaviour. |
| ⭐⭐ **Mostly e2e tests** | ⭐ Slow, flaky, and a failure names nothing. |
| All unit, heavily mocked | ⭐⭐ Green suite, broken app — you tested your mocks. |
| ⭐ Tests that depend on each other | ⭐⭐ Breaks under `-k`, xdist, or a rename. `pytest-randomly`. |
| `time.sleep` in a test | ⭐⭐ Wait on a condition. |
| ⭐ `test_process_2` | ⭐ Name the behaviour; the failure line should tell you the rule. |
| ⭐⭐ **Re-running until green** | ⭐⭐ The habit that turns a suite into decoration. |
| Multiple unrelated assertions | ⭐ The first failure hides the rest. |
| Keeping a test that never catches anything | ⭐ It is a maintenance cost. Deleting it is legitimate. |

## Interview questions

**Q: What is a test suite for?**
> Primarily so I can change the code without fear. Refactoring means changing structure without
> changing behaviour, and the only way to know behaviour didn't change is a suite — without one you're
> not refactoring, you're rewriting and hoping. After that: catching regressions, documenting
> behaviour in a form that actually fails when it drifts, and applying design pressure, because code
> that's hard to test is usually badly designed. What it doesn't do is prove correctness — a green
> suite means the things I thought of still work.

**Q: How much of each kind of test?**
> The pyramid is the standard answer and I'd modify it. Lots of fast unit tests for anything with real
> logic, because the domain layer needs no database and those tests run in milliseconds. A
> substantial layer of integration tests through the API against a real database, because in a backend
> most bugs are at the seams — the query, the serialisation, the migration, the HTTP contract — not in
> a pure pricing function. And a handful of end-to-end tests over the critical journeys only. The real
> constraint isn't the shape, it's speed versus confidence: fast tests get run constantly and catch
> mistakes seconds after you make them, which is where nearly all the value is.

**Q: What does "test behaviour, not implementation" mean concretely?**
> There's a checkable version of it: if a pure refactor breaks your test, the test was wrong. So I
> assert on return values and observable effects — the row that exists, the email that was queued —
> through the public interface, rather than on which private methods got called in which order. A test
> that names a private method has taken on a second job, which is to break every time I reorganise.
> The counterweight is that a genuinely complex private algorithm sometimes deserves direct tests, but
> that usually means it wants to be its own public unit and the test is telling me about a missing
> seam.

**Q: How do you handle a flaky test?**
> Treat it as a bug with a ticket, and quarantine it the same day so it isn't gating merges. Then fix
> or delete it within the sprint. What I won't do is normalise re-running until green, because that's
> a social failure rather than a technical one: once the team's reflex is to re-run instead of read,
> real failures get re-run too, and the suite has stopped protecting anything while still costing
> twenty minutes a build. Automatic retries are a painkiller — fine to stop the bleeding, not a policy.

**Q: Would you ever delete a test?**
> Yes. A test suite is code you maintain forever — every test has to be read, updated and
> re-understood after each refactor. A test that breaks on every restructure and has never caught a
> bug is a net liability, and so is a duplicate of a case already covered. The question I ask isn't
> "is this tested" but "what would this catch, and what will it cost me when I restructure".

## Mini task

1. ⭐⭐ Take a test you have written and ask: **would a pure refactor break it?** If yes, rewrite it
   against behaviour.
2. ⭐ Rename five tests to state the behaviour. **Read the list of names as a spec.**
3. ⭐⭐ Time your suite. Split it into "under 1 second" and "the rest" and **count each group.**
4. ⭐⭐ Install `pytest-randomly` and run your suite three times. **Note any new failures** — those
   are order dependencies you already had.
5. ⭐ Deliberately create an order dependency (a module-level list) and watch it surface.
6. ⭐⭐ Write a test that uses `datetime.now()` and make it fail by changing your system clock. **Then
   inject the clock** and make it deterministic.
7. ⭐ Take a test with five assertions and split it. Break the first one and note what you *cannot*
   see in the original.
8. ⭐⭐ Find a test in your codebase that has never failed. **Break the code it covers on purpose** and
   check that it actually fails.
9. ⭐⭐ Write down your team policy for flaky tests in four lines.
10. ⭐ Classify every test in one project as unit / integration / e2e and **draw the actual shape.**

## 🎙️ Articulation drill

Record two minutes: **"What's your approach to testing?"** — the most common testing question, and
one that is really asking whether you have opinions or slogans.

⭐ **Lead with purpose, because everything else follows from it:** **"the point of a test suite is that
I can change the code without fear. Refactoring means changing structure without changing behaviour,
and the suite is the only thing that tells me the behaviour didn't change. Catching regressions and
documenting behaviour are real, but they're second."**

⭐⭐ **Then the shape, with a position rather than a recitation:** *"I'd want lots of fast unit tests
around anything with real logic — the domain layer needs no database, so those cost milliseconds — a
substantial layer of integration tests through the API against a real database, and only a handful of
end-to-end tests on critical journeys. I'd push back gently on the strict pyramid for a backend:
most real bugs are at the seams, in the query or the serialisation or the migration, not in a pure
pricing function. The proportions are a heuristic; the speed-versus-confidence trade-off is the law."*

⭐⭐ **Then the discipline that keeps a suite alive:** *"I test behaviour, not implementation, and I
have a checkable version of that rule — if a pure refactor breaks a test, the test was wrong. And I'd
treat flaky tests as bugs with tickets, quarantined the same day. That one's social rather than
technical: once a team's reflex is to re-run CI instead of read the failure, real failures get
re-run too, and you're paying twenty minutes a build for something that no longer protects you."*

⭐ **Close on the honesty that makes the rest credible:** *"and I'd say plainly that tests don't prove
correctness. A green suite means the things I thought of still work. That's worth a lot, and it isn't
the same claim."*
