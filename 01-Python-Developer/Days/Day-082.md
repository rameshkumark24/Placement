# Day 082

**L-082** · ⭐⭐ **Observing a live process** — `/proc`, `lsof`, `strace`, `ss`, and diagnosing a hang without restarting it

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a running process will tell you exactly what it is doing — what it has
> open, what syscall it is blocked in, and which Python line it is on — and "restart it and see"
> destroys all of that evidence permanently.**
>
> ⭐ This is the day that changes how you behave during an incident. **Everything here works on a
> process that is already running, in production, without a debugger, without a restart, and without
> having planned ahead.**

# Part 1 — ⭐⭐ `/proc` — the kernel as a filesystem

```
⭐⭐ /proc IS NOT ON DISK. Reading a file there asks the kernel a question. (Day 078)
⭐
⭐   /proc/PID/cmdline   ⭐ the exact argv          ⇒ tr '\0' ' ' < /proc/PID/cmdline
⭐   /proc/PID/cwd       ⭐ symlink to its working directory ⭐⭐ ← resolves "file not found"
⭐   /proc/PID/exe       ⭐⭐ WHICH interpreter — ⭐ settles "is it running the venv python"
⭐   /proc/PID/environ   ⭐ its environment (NUL-separated) ⚠️ ⭐⭐ secrets are visible here
⭐   /proc/PID/fd/       ⭐⭐ EVERY OPEN FILE AND SOCKET, as symlinks ← the most useful one
⭐   /proc/PID/status    ⭐ VmRSS, Threads, State, and the uid it is really running as
⭐   /proc/PID/limits    ⭐⭐ the ACTUAL limits in force (not what your shell says)
⭐   /proc/PID/stack     kernel stack (root)
```

```bash
ls -l /proc/4242/fd | wc -l           # ⭐⭐ HOW MANY FDs — the leak detector
ls -l /proc/4242/fd | tail            # ⭐ WHAT they are: files, sockets, pipes
cat /proc/4242/limits | grep -i files # ⭐ the ceiling it will hit
grep VmRSS /proc/4242/status          # ⭐ real memory right now
```

```
⭐⭐ THE DIAGNOSIS THIS GIVES YOU FOR FREE — "OSError: [Errno 24] Too many open files":
⭐   1. count the fds ⇒ compare with the limit    ⇒ ⭐ are you actually at the ceiling
⭐   2. ⭐⭐ LOOK AT WHAT THEY ARE. The pattern names the bug:
⭐        · hundreds of sockets to ONE host   ⇒ ⭐⭐ an httpx/requests client created
⭐          PER REQUEST instead of once ⇒ no connection reuse ⇒ fd exhaustion
⭐          ⭐ AND a TIME_WAIT flood (Day 008).
⭐        · hundreds of the same file         ⇒ ⭐ open() without a `with` (Day 052)
⭐        · hundreds of pipes                 ⇒ ⭐ subprocess without wait (Day 081)
⭐   3. ⭐ raise the limit only AFTER you know which — ulimit -n is a painkiller,
⭐      ⭐⭐ and if it is a leak, a bigger limit just moves the crash to 3 a.m.
```

⭐⭐ **`Errno 24` is one of the few errors whose *cause* is visible directly.** Most bugs need a
hypothesis; **this one needs `ls`.**

# Part 2 — ⭐ `lsof` and `ss` — files and sockets

```bash
lsof -p 4242                 # ⭐ everything this process has open
lsof -i :8000                # ⭐⭐ WHO IS HOLDING PORT 8000 (the "address in use" answer)
lsof +D /var/lib/app         # ⭐ who is using this directory (before you unmount it)
lsof | grep deleted          # ⭐⭐ THE DISK-FULL ANSWER from Day 078
lsof -u app                  # everything one user has open
```

```bash
ss -tanp                     # ⭐⭐ TCP, all, numeric, with the owning process
ss -tanp | awk '{print $1}' | sort | uniq -c | sort -rn   # ⭐⭐ Day 080's pipeline, on sockets
ss -s                        # summary counts
```

| ⭐ State (Day 008) | ⭐⭐ What a pile of them means |
|---|---|
| `ESTAB` | ⭐ healthy, in use |
| ⭐⭐ `CLOSE_WAIT` | ⭐⭐ **the peer closed and YOUR code never called `close()`** — ⭐ your bug, and a leak |
| `TIME_WAIT` | ⭐ *you* closed; normal, 60 s — ⭐⭐ thousands ⇒ **no connection reuse** |
| `SYN_SENT` | ⭐ cannot reach the peer — firewall, or wrong host |
| `LISTEN` | ⭐ the server socket (Day 004) |

```
⭐⭐ CLOSE_WAIT IS THE MOST DIAGNOSTIC STATE IN THE TABLE, and it is worth knowing
⭐   why: the TCP teardown is four-way. The peer sent FIN; the kernel ACKed it and
⭐   put the socket in CLOSE_WAIT; ⭐⭐ THE FINAL FIN IS SENT BY YOUR close() CALL.
⭐   ⇒ ⭐⭐ so the socket is stuck waiting for YOUR APPLICATION, not the network.
⭐   ⇒ ⭐ it is Day 052 (context managers) and Day 026 (refcounting) with a
⭐        network consequence: a response object nobody closed.
```

# Part 3 — ⭐⭐ `strace` — what the process is asking the kernel for

```bash
strace -p 4242                              # ⭐ attach to a running process
strace -f -p 4242                           # ⭐⭐ -f follows THREADS and children
strace -p 4242 -e trace=network             # ⭐ only sockets · file,openat · %file
strace -p 4242 -T -tt                       # ⭐⭐ TIME PER CALL and a wall clock ← the good one
strace -c -p 4242                           # ⭐⭐ SUMMARY: which syscall dominates
strace -f -e trace=openat python app.py 2>&1 | grep -i config    # ⭐ "which config did it read"
```

```
⭐⭐ STRACE ANSWERS EXACTLY ONE QUESTION, AND IT IS THE RIGHT ONE:
⭐   "IS THIS PROCESS WAITING ON THE OUTSIDE WORLD, OR BUSY INSIDE ITSELF?"
⭐
⭐   You attach to a hung process and see:
⭐   · ⭐⭐ recvfrom(7, ...  <hangs>       ⇒ BLOCKED ON A SOCKET. Not your code's fault.
⭐        ⇒ ⭐⭐ `ls -l /proc/PID/fd/7` NAMES THE PEER ⇒ that is your slow dependency.
⭐        ⇒ ⭐⭐ AND THE REAL FINDING: THERE WAS NO TIMEOUT. (Day 060.)
⭐   · futex(...) over and over          ⇒ ⭐ lock contention between threads (Day 066)
⭐   · epoll_wait(...) forever            ⇒ ⭐ an idle event loop — normal (Days 016, 070)
⭐   · ⭐⭐ NOTHING AT ALL, 100 % CPU      ⇒ ⭐⭐ NOT A SYSCALL PROBLEM. It is executing
⭐        Python. ⇒ strace has told you all it can. GO TO py-spy.
⭐   · openat() thousands of times/sec    ⇒ ⭐ a cache miss, or an import inside a loop
```

⚠️ ⭐ **`strace` slows the target substantially** — every syscall traps twice. Use it briefly, prefer
`-c` or `-e` to narrow it, and never leave it attached to a busy production service. ⭐ On macOS the
equivalents are `dtruss`/Instruments; **on a Linux container you may need `--cap-add=SYS_PTRACE`.**

# Part 4 — ⭐⭐ `py-spy` — the Python-level view, and the ladder

```bash
pip install py-spy            # ⭐ or uv tool install py-spy

py-spy top --pid 4242         # ⭐⭐ LIVE `top` FOR PYTHON FUNCTIONS
py-spy dump --pid 4242        # ⭐⭐ THE STACK OF EVERY THREAD, RIGHT NOW ← the hang-killer
py-spy record -o out.svg --pid 4242 --duration 30    # ⭐ a flame graph
```

⭐⭐ **`py-spy` reads another process's memory from outside** — no code change, no restart, no import,
almost no overhead (Day 073). ⭐ **It is the single most valuable tool in this stage.**

```
⭐⭐ THE LADDER — memorise this and you can debug a production hang in five minutes:
⭐
⭐   1. IS IT ALIVE?                 ps / systemctl status              (Day 081)
⭐        └─ dead & restarting? ⇒ ⭐⭐ exit code. 137 = 128+9 = SIGKILL ⇒ suspect OOM.
⭐
⭐   2. ⭐⭐ HOW MUCH CPU?             top
⭐        ├─ ~100 % of one core ⇒ ⭐⭐ IT IS COMPUTING (or spinning).
⭐        │      ⇒ py-spy top      ⇒ the function
⭐        │      ⇒ ⭐ suspects: an accidental O(n²), a ReDoS (Day 076),
⭐        │        ⭐⭐ or a blocking CPU call inside async def (Day 072)
⭐        └─ ~0 %                ⇒ ⭐⭐ IT IS WAITING. Go to 3.
⭐
⭐   3. ⭐⭐ WAITING ON WHAT?          strace -p / py-spy dump
⭐        ├─ blocked in recvfrom/read ⇒ ⭐ lsof the fd ⇒ ⭐⭐ name the dependency
⭐        │                              ⇒ and confirm there is no timeout
⭐        ├─ futex, forever            ⇒ ⭐⭐ DEADLOCK ⇒ py-spy dump shows ALL threads:
⭐        │                              ⭐ two stacks each holding what the other wants
⭐        └─ epoll_wait, and no work   ⇒ ⭐ the loop is idle — the queue upstream is empty
⭐
⭐   4. MEMORY CLIMBING?              RSS over time ⇒ tracemalloc / memray  (Day 100A)
⭐   5. FDs CLIMBING?                 ls /proc/PID/fd | wc -l               (Part 1)
⭐
⭐⭐ ⇒ EVERY STEP NARROWS. ⭐ And say the ladder out loud in an interview — the
⭐     structure is worth more than any individual tool.
```

```
⭐⭐ THE TWO THINGS PY-SPY DUMP SOLVES THAT NOTHING ELSE DOES:
⭐   · ⭐⭐ A DEADLOCK. All thread stacks at once, so you can SEE the cycle. There is
⭐        no other way to get this from a live process without prior instrumentation.
⭐   · ⭐⭐ "IT IS SLOW BUT ONLY IN PRODUCTION." Sampling profilers change nothing
⭐        about the process, so what you measure is what is actually happening — no
⭐        instrumentation overhead distorting the answer.
```

# Part 5 — ⭐ Limits, the OOM killer, and journal

```bash
ulimit -a                  # ⭐ YOUR shell's limits · ⭐⭐ /proc/PID/limits for the process
ulimit -n                  # ⭐ open files — the one you will hit
free -h                    # ⭐ memory · ⚠️ "available", not "free", is the number
df -h ; df -i              # ⭐ disk · ⭐ inodes (Day 078)
uptime                     # ⭐⭐ load average — see below
dmesg -T | grep -i "killed process"      # ⭐⭐ THE OOM KILLER'S CONFESSION
```

```
⭐⭐ "THE CONTAINER RESTARTS RANDOMLY, THERE IS NOTHING IN THE LOGS."
⭐   ⇒ ⭐⭐ THAT IS THE SIGNATURE OF AN OOM KILL, AND THE ABSENCE OF LOGS IS THE
⭐        EVIDENCE, NOT THE MYSTERY: SIGKILL (Day 081) runs no handler, flushes
⭐        no buffer ⇒ ⭐ the last few log lines were in the stdout buffer (Day 079)
⭐        and died with the process.
⭐   ⇒ CONFIRM: exit code 137 · dmesg · k8s "OOMKilled" · a memory graph that
⭐     climbs to a flat ceiling and drops vertically.
⭐   ⇒ ⭐ CAUSE, usually: too many workers × per-worker RSS (Day 021), a request
⭐     that loads a whole file into memory, or a genuine leak (Days 026, 051).
```

| ⭐ Load average | ⭐⭐ Reading it |
|---|---|
| `uptime` ⇒ `2.4 1.9 1.2` | ⭐ 1, 5, 15-minute averages of **runnable + uninterruptible** tasks |
| ⭐⭐ Compare with `nproc` | ⭐⭐ load 4 on 4 cores ≈ saturated; **load 40 on 4 cores = queueing** |
| ⚠️ High load, low CPU | ⭐⭐ Tasks stuck in `D` — **disk or network I/O**, not compute |

⭐ **`journalctl`** (Day 081) closes the loop: `journalctl -u api --since "14:00" --until "14:10"` puts
the application's own account next to the evidence you gathered. ⭐⭐ **Correlate by timestamp** — the
OOM kill in `dmesg`, the 502s in the access log (Day 080), and the last line the app managed to flush.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Restarting a hung process immediately** | ⭐⭐ You destroyed the only evidence. `py-spy dump` first — it takes two seconds. |
| Raising `ulimit -n` to fix Errno 24 | ⭐⭐ Look at *what* the fds are first. A leak just crashes later. |
| ⭐ Ignoring `CLOSE_WAIT` | ⭐⭐ It means **your** code never closed. Always a bug. |
| ⭐ Reading `free` "free" | ⭐ Use **available**; Linux uses spare RAM as cache deliberately. |
| Leaving `strace` on a busy service | ⭐ Every syscall traps twice. Use `-c`/`-e`, briefly. |
| ⭐ Assuming high load = high CPU | ⭐⭐ Load counts `D` state — often disk or network. |
| "Restarts, no logs, no idea" | ⭐⭐ Check exit code 137 and `dmesg`. Missing logs is a *clue*. |
| Using `strace` on a 100 %-CPU Python process | ⭐⭐ Wrong tool — it is not making syscalls. `py-spy`. |
| ⭐ `top` per-process only | ⭐ Press `1`: one core pegged with 7 idle is a very different story. |

## Interview questions

**Q: A production service is hung. It's not responding but it hasn't crashed. What do you do?**
> First, resist restarting, because that destroys the evidence and the problem comes back at 3 a.m.
> with nothing to go on. Then I follow a ladder. Check CPU: near 100% of one core means it's computing
> — an accidental quadratic, a catastrophic regex, or a CPU-bound call inside an `async def` — and
> `py-spy top` names the function. Near zero means it's waiting, and then `strace -p` shows the
> blocked syscall: if it's `recvfrom` on a socket, `/proc/PID/fd` names the peer and I've found a
> dependency with no timeout. If it's `futex` forever, that's a deadlock, and `py-spy dump` gives me
> every thread's stack at once, which is the only way to see the cycle in a live process. All of this
> takes under five minutes and none of it requires a restart or a code change.

**Q: You get `OSError: Too many open files`. Walk me through it.**
> Count the file descriptors in `/proc/PID/fd` and compare with `/proc/PID/limits`, then — the part
> people skip — actually look at what they are. Hundreds of sockets to one host means an HTTP client
> being constructed per request instead of reused, so there's no connection pooling; you'd normally
> see a `TIME_WAIT` pile-up alongside it. Hundreds of the same file means `open()` without a `with`.
> Hundreds of pipes means subprocesses that were never waited on. Raising `ulimit -n` is a painkiller:
> if it's a leak, the bigger limit just moves the crash to a worse hour.

**Q: What does a pile of `CLOSE_WAIT` sockets tell you?**
> That the remote end sent FIN, the kernel acknowledged it, and the final FIN is waiting on my
> application to call `close()`. So the socket is stuck on *my code*, not on the network — it's
> always a bug on my side, usually a response or connection object that nothing closed. It's the
> context-manager lesson with a network consequence. `TIME_WAIT` is the opposite: normal, mine, and a
> flood of it means I'm opening a new connection per request instead of reusing one.

**Q: A container restarts every few hours with nothing in the logs.**
> The absent logs are the clue, not the mystery. `SIGKILL` runs no handler and flushes no buffer, so
> anything still sitting in Python's block-buffered stdout dies with the process — which is exactly
> what an OOM kill looks like. I'd confirm with the exit code, 137, which is 128 plus 9, then `dmesg`
> or the pod's `OOMKilled` status, then look at whether memory climbs to a flat ceiling and drops
> vertically. Cause is usually worker count times per-worker RSS exceeding the limit, or a request
> that loads something unbounded into memory. And separately I'd set `PYTHONUNBUFFERED` so the next
> occurrence leaves evidence.

**Q: Load average is 40 on a 4-core box but CPU is 30%. What's going on?**
> Load average on Linux counts uninterruptible tasks as well as runnable ones, so processes blocked in
> `D` state — disk or network I/O — inflate it without using CPU. Forty on four cores with low CPU says
> things are queueing on I/O, not compute. I'd check `ps` for `D`, look at disk latency, and stop
> considering "add more workers" as the fix, because more workers waiting on the same slow disk makes
> it worse.

## Mini task

1. ⭐⭐ Start a Python process, find its PID, and read `cmdline`, `cwd`, `exe`, and `fd/` from `/proc`.
2. ⭐⭐ Open 50 files in a loop **without** closing them and watch `ls /proc/PID/fd | wc -l` climb.
   **Then use `with` and watch it stay flat.**
3. ⭐ Lower `ulimit -n` to 30 in a shell and reproduce `Errno 24` deliberately.
4. ⭐⭐ Write a client that creates a new `httpx.Client` per request in a loop. **Count fds and
   `TIME_WAIT` sockets.** Then hoist the client and compare both numbers.
5. ⭐⭐ Write a server that accepts a connection and never closes it; connect and disconnect the client;
   find the `CLOSE_WAIT` with `ss -tanp`.
6. ⭐⭐ `strace -p` on a process blocked in `input()` or a socket read. **Identify the fd, then
   `ls -l /proc/PID/fd/N` to name it.**
7. ⭐ `strace -c -f python -c "import pandas"` and read which syscall dominates. Explain the result.
8. ⭐⭐ Write a deliberate two-lock deadlock (Day 066). **Diagnose it with `py-spy dump` alone** and
   read the cycle out of the two stacks.
9. ⭐⭐ Write an infinite `while True: pass` inside a thread and find it with `py-spy top`.
10. ⭐⭐ Run a container with a 100 MB memory limit and allocate 200 MB. **Read the exit code, then
    `dmesg`.**
11. ⭐ `uptime` and `nproc`. Start a CPU-bound process per core (Day 068) and watch the load average
    move.

## 🎙️ Articulation drill

Record two minutes: **"The API stopped responding. It is still running. You have SSH. Go."**

⭐ **Open with the discipline, not a tool — this is what is actually being assessed:** **"the first
thing I would say to the room is 'do not restart it yet'. A restart fixes it for twenty minutes and
destroys the only evidence, and then it happens again at 3 a.m. with nothing to look at. Capture
first, restart second — and capture takes about two minutes."**

⭐⭐ **Then the ladder, as a decision tree rather than a list of commands:** *"CPU is the first fork.
Near 100% of one core means it is computing, not stuck — `py-spy top` names the function, and the
usual suspects are an accidental quadratic, a catastrophic regex, or a blocking CPU call inside an
`async def`, which stops every connection that worker owns. Near zero means it is waiting, and then
`strace -p` tells me which syscall — blocked in `recvfrom` on a socket means `/proc/PID/fd` names the
peer, and the real finding is not the slow dependency, it is that the call had no timeout. Blocked in
`futex` forever is a deadlock, and `py-spy dump` gives me every thread's stack at once, which is the
only way to see the cycle without having planned for it."*

⭐⭐ **Close on the thing that makes this a senior answer:** *"and I'd grab `py-spy dump`, the fd
count, and RSS before restarting — three commands, two minutes — so that whatever we do next is based
on evidence. The point of all of it is to turn 'it hung' into 'it was blocked reading from the
payments API with no timeout', because only the second one can be fixed."*
