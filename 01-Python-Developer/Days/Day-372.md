# Part 1 — ⭐⭐ 12-factor config, and where it stops

```
⭐⭐ THE PRINCIPLE IS SOUND: ***CONFIG IS EVERYTHING THAT VARIES
⭐   BETWEEN DEPLOYS, AND IT LIVES IN THE ENVIRONMENT, NOT IN
⭐   THE CODE.***
⭐   ⭐ The test (Day 364): ⭐⭐ COULD YOU OPEN-SOURCE THIS
⭐     REPOSITORY RIGHT NOW WITHOUT LEAKING ANYTHING?

⭐⭐ AND THE FOUR PLACES ENVIRONMENT VARIABLES STOP BEING
⭐   ENOUGH — ⭐ this is the "honestly" in the title:
⭐   ① ⭐⭐ ***THEY ARE FLAT STRINGS.*** ⭐ Nested or list-shaped
⭐      config becomes `FEATURE_A_LIMITS_0_MAX=10`, ⭐⭐ WHICH IS
⭐      A DATA STRUCTURE ENCODED IN A NAMING CONVENTION AND
⭐      NOBODY CAN READ IT.
⭐   ② ⭐⭐ ***THEY ARE READ ONCE AT STARTUP.*** ⭐ Changing one
⭐      means a restart — ⭐⭐ SO EVERY CONFIG CHANGE IS A DEPLOY,
⭐      AND ROTATION BECOMES A ROLLING RESTART OF EVERYTHING.
⭐   ③ ⭐⭐ ***THEY ARE INHERITED BY EVERY CHILD PROCESS.*** ⭐ A
⭐      `subprocess.run(["convert", ...])` gets your database
⭐      password in its environment, ⭐⭐ AND SO DOES ANY CRASH
⭐      HANDLER THAT DUMPS `os.environ`.
⭐   ④ ⭐ ***THEY ARE VISIBLE*** — `docker inspect`,
⭐      `/proc/<pid>/environ`, ⭐⭐ AND MOST ERROR-REPORTING SDKs
⭐      ATTACH THE ENVIRONMENT TO THE EVENT BY DEFAULT, WHICH
⭐      IS HOW SECRETS END UP IN A THIRD-PARTY SaaS.

⭐⭐ ⇒ SO THE HONEST RULE: ***ENV VARS FOR NON-SECRET CONFIG AND
⭐   FOR ***POINTERS*** TO SECRETS; FILES OR A SECRETS MANAGER
⭐   FOR THE SECRETS THEMSELVES.***
⭐   ⭐ `DATABASE_URL` pointing at a host is config.
⭐   ⭐ ⭐⭐ THE PASSWORD INSIDE IT IS NOT, AND IS THE REASON
⭐     `DATABASE_URL` IS AWKWARD — ⭐ it mixes the two, ⭐⭐ WHICH
⭐     IS WHY ROTATING A DATABASE PASSWORD IS HARDER THAN IT
⭐     SHOULD BE IN MOST PYTHON APPS.
```

# Part 2 — ⭐ Configuration done well in Python

```python
# ⭐⭐ ONE SETTINGS OBJECT, VALIDATED AT STARTUP, TYPED
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_nested_delimiter="__",       # ⭐ DB__POOL__SIZE=20
        extra="forbid",                  # ⭐⭐ CATCHES TYPOS
        frozen=True,                     # ⭐⭐ NOBODY MUTATES CONFIG
    )

    environment: Literal["dev", "staging", "prod"]
    database_url: PostgresDsn
    secret_key: SecretStr                # ⭐⭐ MASKED IN repr()
    workers: int = Field(4, ge=1, le=64)
    feature_new_checkout: bool = False

    @model_validator(mode="after")
    def _prod_is_strict(self) -> "Settings":
        if self.environment == "prod":
            if self.secret_key.get_secret_value().startswith("dev-"):
                raise ValueError("dev secret in production")   # ⭐⭐ CRASH
        return self
```

```
⭐⭐ THE SIX RULES THAT MAKE CONFIG BORING:
⭐   ① ⭐⭐ ***VALIDATE AT STARTUP AND CRASH.*** ⭐ A missing
⭐      value must never be discovered by a user (Day 364).
⭐   ② ⭐⭐ `extra="forbid"` — ⭐ `DATBASE_URL` is a silent
⭐      default without it, and that bug takes a day to find.
⭐   ③ ⭐ `SecretStr` so a secret cannot be logged accidentally
⭐      by a `repr()` or an exception dump.
⭐   ④ ⭐ `frozen=True` — ⭐⭐ CONFIG THAT MUTATES AT RUNTIME IS A
⭐      SOURCE OF IRREPRODUCIBLE BEHAVIOUR ACROSS WORKERS.
⭐   ⑤ ⭐⭐ ***CROSS-FIELD VALIDATION FOR ENVIRONMENT-SPECIFIC
⭐      RULES*** — ⭐ debug mode in production, a dev key in
⭐      prod, a localhost URL in staging. ⭐⭐ THIS CATCHES THE
⭐      MISCONFIGURATION CLASS THAT CAUSES REAL INCIDENTS.
⭐   ⑥ ⭐ One object, imported once, ⭐⭐ AND ***NEVER*** READ
⭐      `os.environ` DEEP INSIDE A FUNCTION — ⭐ that makes
⭐      configuration untestable and invisible.

⭐⭐ AND THE THING WORTH BUILDING ONCE: ⭐⭐ A `/config` ENDPOINT
⭐   (AUTHENTICATED, ADMIN-ONLY) THAT SHOWS ***NON-SECRET***
⭐   RESOLVED CONFIG AND THE ***SOURCE*** OF EACH VALUE.
⭐   ⇒ ⭐ "Which value is this pod actually using, and where did
⭐     it come from?" is a question you will ask during an
⭐     incident, ⭐⭐ AND GUESSING IT FROM THREE LAYERS OF
⭐     DEFAULTS AND OVERRIDES IS HOW INCIDENTS GET LONGER.
```

# Part 3 — ⭐⭐ Where secrets should live

```
⭐⭐ THE LADDER, WORST TO BEST:
⭐   ⭐ ❌ ***IN THE REPOSITORY*** — ⭐⭐ AND REMEMBER GIT NEVER
⭐     FORGETS: DELETING IT IN A LATER COMMIT LEAVES IT IN
⭐     HISTORY, SO THE ONLY RESPONSE IS ROTATION.
⭐   ⭐ ❌ ***IN THE IMAGE*** — Day 362's layer trap.
⭐   ⭐ ⚠️ ***IN CI SECRETS*** — better, ⭐ still long-lived,
⭐     ⭐ still readable by anyone who can add a workflow.
⭐   ⭐ ⚠️ ***ENVIRONMENT VARIABLES AT RUNTIME*** — ⭐ the
⭐     common case, ⭐ acceptable for many things, ⭐⭐ WITH PART
⭐     1'S FOUR WEAKNESSES.
⭐   ⭐ ✔ ***MOUNTED FILES*** (Kubernetes Secret as a volume,
⭐     Docker secret) — ⭐⭐ NOT INHERITED BY CHILD PROCESSES,
⭐     NOT IN `inspect`, ⭐ and ***updatable in place***, so an
⭐     app that watches the file can rotate without a restart.
⭐   ⭐ ✔✔ ⭐⭐ ***A SECRETS MANAGER*** (Vault, AWS Secrets
⭐     Manager, GCP Secret Manager) — ⭐ audited access, ⭐ TTLs,
⭐     ⭐ automatic rotation, ⭐ fine-grained policy.
⭐   ⭐ ✔✔✔ ⭐⭐ ***DYNAMIC SECRETS*** — Vault generates a
⭐     ***unique database credential per application instance***
⭐     with a 1-hour TTL.
⭐     ⇒ ⭐⭐ A LEAK EXPIRES BY ITSELF, AND THE AUDIT LOG SHOWS
⭐       ***WHICH INSTANCE*** DID SOMETHING. ⭐ This is the state
⭐       of the art and it is worth naming even if you have
⭐       never run it.

⭐⭐ AND THE KUBERNETES SECRET CAVEAT, WHICH IS COMMONLY
⭐   OVERSTATED AND COMMONLY UNDERSTATED:
⭐   ⭐ ⭐⭐ THEY ARE ***BASE64***, NOT ENCRYPTED, IN etcd BY
⭐     DEFAULT. ⭐ Base64 is an encoding, not a protection.
⭐   ⇒ ⭐ Enable encryption at rest, ⭐ restrict RBAC (⭐⭐ ANYONE
⭐     WHO CAN `get secrets` IN A NAMESPACE HAS THEM ALL, AND
⭐     ANYONE WHO CAN CREATE A POD CAN MOUNT THEM), ⭐ and
⭐     prefer an external secrets operator that syncs from a
⭐     real manager.
⭐   ⇒ ⭐⭐ BUT ALSO: THEY ARE ***BETTER*** THAN ENV VARS BAKED
⭐     INTO A DEPLOYMENT MANIFEST IN GIT, WHICH IS WHAT THEY ARE
⭐     USUALLY BEING COMPARED AGAINST.
```

# Part 4 — ⭐⭐ Rotation is the thing that actually matters

```
⭐⭐ THE QUESTION THAT REFRAMES SECRET MANAGEMENT:
⭐   ***A CREDENTIAL LEAKED FIVE MINUTES AGO. HOW LONG UNTIL IT
⭐      IS USELESS?***
⭐   ⭐ ⭐⭐ IF THE ANSWER IS "WE'D HAVE TO COORDINATE A DEPLOY
⭐     ACROSS FOUR SERVICES", YOU DO NOT HAVE SECRET MANAGEMENT.
⭐     YOU HAVE SECRET ***STORAGE***.

⭐⭐ WHY ROTATION IS HARD, AND IT IS ALWAYS THE SAME REASON:
⭐   ⭐ ⭐⭐ THERE IS A MOMENT WHEN SOME INSTANCES HAVE THE OLD
⭐     CREDENTIAL AND SOME HAVE THE NEW ONE. ⭐ It is Day 371's
⭐     coexistence problem wearing a different hat.
⭐   ⇒ ⭐⭐ SO ROTATION REQUIRES ***TWO VALID CREDENTIALS AT
⭐     ONCE***, WHICH IS AN ***APPLICATION*** AND ***PROVIDER***
⭐     CAPABILITY, NOT A STORAGE ONE.

⭐⭐ THE THREE PATTERNS:
⭐   ① ⭐⭐ ***TWO ACTIVE KEYS*** — most APIs support a primary
⭐      and secondary key. ⭐ Create the new, deploy, ⭐ verify
⭐      nothing uses the old (⭐⭐ VIA THE PROVIDER'S
⭐      LAST-USED TIMESTAMP), then revoke.
⭐   ② ⭐ ***OVERLAPPING VALIDITY*** — for signing keys, publish
⭐      a JWKS with both, ⭐ sign with the new, ⭐⭐ ACCEPT BOTH
⭐      UNTIL EVERY OLD TOKEN HAS EXPIRED. ⭐ The overlap must
⭐      exceed your longest token lifetime.
⭐   ③ ⭐⭐ ***SHORT-LIVED BY CONSTRUCTION*** — dynamic secrets,
⭐      IAM roles, OIDC. ⭐⭐ NO ROTATION PROCEDURE EXISTS
⭐      BECAUSE NOTHING LASTS LONG ENOUGH TO NEED ONE. ⭐ This is
⭐      the right answer wherever it is available.

⭐⭐ AND THE DATABASE-PASSWORD CASE SPECIFICALLY, BECAUSE IT IS
⭐   THE ONE EVERYONE HAS:
⭐   ⭐ ⭐⭐ POSTGRES SUPPORTS ONLY ***ONE*** PASSWORD PER ROLE,
⭐     SO THE TWO-KEY PATTERN DOES NOT WORK DIRECTLY.
⭐   ⇒ ⭐ Options: ⭐⭐ TWO ROLES (`app_a`, `app_b`) WITH IDENTICAL
⭐     GRANTS, ALTERNATING; ⭐ a connection proxy (pgbouncer,
⭐     RDS Proxy) that holds the credential; ⭐⭐ OR IAM
⭐     AUTHENTICATION, WHICH ISSUES A 15-MINUTE TOKEN AND
⭐     REMOVES THE PROBLEM ENTIRELY.
⭐   ⇒ ⭐⭐ KNOWING THIS SPECIFIC CONSTRAINT IS A STRONG SIGNAL,
⭐     BECAUSE IT IS WHERE MOST ROTATION PLANS QUIETLY FAIL.

⭐⭐ AND THE PART THAT MAKES ROTATION REAL:
⭐   ***ROTATE ON A SCHEDULE, NOT ONLY ON A LEAK.*** ⭐ A
⭐   procedure exercised quarterly works during an incident.
⭐   ⭐⭐ A PROCEDURE WRITTEN DOWN AND NEVER RUN DOES NOT.
```

# Part 5 — ⭐ Getting secrets into the process

```
⭐⭐ FOUR MECHANISMS, WITH THE HONEST TRADE:
⭐   ① ⭐ ***INJECTED BY THE PLATFORM AS ENV/FILES*** —
⭐      Kubernetes, ECS task definitions. ⭐ Simple, ⭐ no code,
⭐      ⭐⭐ AND RESTART-TO-ROTATE.
⭐   ② ⭐⭐ ***FETCHED AT STARTUP FROM A MANAGER*** — ⭐ the
⭐      application authenticates (IAM role, service account,
⭐      OIDC) and reads. ⭐ ✔ Audited, ✔ rotatable.
⭐      ⭐ ✘ ⭐⭐ THE SECRETS MANAGER IS NOW A STARTUP DEPENDENCY:
⭐        IF IT IS DOWN, NOTHING STARTS — INCLUDING DURING AN
⭐        INCIDENT WHEN EVERYTHING IS RESTARTING AT ONCE.
⭐      ⇒ ⭐ So: cache locally with a TTL, ⭐⭐ AND SERVE STALE ON
⭐        ERROR (Day 339's static stability).
⭐   ③ ⭐ ***A SIDECAR OR CSI DRIVER*** that fetches and refreshes
⭐      into a mounted file. ⭐ ✔ ⭐⭐ ROTATION WITHOUT A RESTART,
⭐      ***IF*** THE APP RE-READS THE FILE. ⭐ ✘ More moving
⭐      parts.
⭐   ④ ⭐⭐ ***NO SECRET AT ALL*** — IAM roles, workload identity,
⭐      mTLS. ⭐ ✔✔ Nothing to leak, nothing to rotate.
⭐      ⇒ ⭐⭐ ALWAYS ASK THIS FIRST. ⭐ Half the secrets in a
⭐        typical AWS application should be an IAM role, and are
⭐        an access key because that was the first thing that
⭐        worked.

⭐⭐ AND THE APPLICATION-SIDE DETAIL THAT MAKES ② AND ③ WORK:
⭐   ⭐ ⭐⭐ THE CREDENTIAL MUST BE READ ***AT USE***, NOT
⭐     CAPTURED AT IMPORT. ⭐ A module-level
⭐     `engine = create_engine(settings.database_url)` freezes
⭐     the password forever.
⭐   ⇒ ⭐ SQLAlchemy's `creator` hook or a connection-time
⭐     callback lets the pool fetch a fresh credential per new
⭐     connection, ⭐⭐ WHICH IS WHAT MAKES 15-MINUTE IAM TOKENS
⭐     USABLE AT ALL.
```

# Part 6 — ⭐⭐ Detection, because prevention fails

```
⭐⭐ ASSUME A SECRET WILL LEAK. ⭐ The controls that matter then:

⭐⭐ ① ***PRE-COMMIT AND CI SCANNING*** (gitleaks, trufflehog).
⭐   ⭐ Pre-commit stops most of it; ⭐⭐ CI CATCHES WHAT SOMEONE
⭐     BYPASSED WITH `--no-verify`.
⭐   ⭐ ⭐⭐ AND SCAN HISTORY, NOT JUST THE DIFF — ⭐ the secret is
⭐     usually already three commits back.
⭐⭐ ② ***PROVIDER-SIDE DETECTION*** — ⭐⭐ GITHUB PUSH PROTECTION
⭐   AND SECRET SCANNING NOTIFY THE ***PROVIDER*** (AWS, Stripe),
⭐   WHO OFTEN QUARANTINE THE KEY AUTOMATICALLY. ⭐ Turn it on;
⭐   it costs nothing.
⭐⭐ ③ ***CANARY TOKENS*** — ⭐ a credential that does nothing
⭐   except alert when used. ⭐⭐ PUT ONE IN A PLAUSIBLE PLACE:
⭐   IF IT IS EVER EXERCISED, SOMEONE IS READING THINGS THEY
⭐   SHOULD NOT BE, ⭐ and you learn it in seconds rather than
⭐   months.
⭐⭐ ④ ***USAGE ALERTING*** — ⭐ alert on a credential used from
⭐   an unexpected region, ⭐ at an unexpected volume, ⭐⭐ OR ON
⭐   AN API IT HAS NEVER TOUCHED BEFORE. ⭐ This is the control
⭐   that catches a leak nobody noticed.
⭐⭐ ⑤ ***LEAST PRIVILEGE*** — ⭐⭐ THE ONLY CONTROL THAT LIMITS
⭐   THE ***DAMAGE*** RATHER THAN THE PROBABILITY. ⭐ A read-only
⭐   key leaked is an incident; ⭐ an admin key leaked is a
⭐   company event.

⭐⭐ AND THE INCIDENT PROCEDURE, WRITTEN BEFORE YOU NEED IT:
⭐   ① ⭐⭐ ROTATE FIRST. ⭐ Not investigate — ***rotate***. ⭐ The
⭐      investigation can happen while the key is already dead.
⭐   ② ⭐ Revoke the old one explicitly and confirm.
⭐   ③ ⭐⭐ CHECK THE AUDIT LOG FOR USE ***BEFORE*** YOU ROTATED
⭐      — ⭐ that is the actual blast radius.
⭐   ④ ⭐ Purge from history if it is in a repository
⭐      (⭐⭐ AND STILL TREAT IT AS COMPROMISED — someone may
⭐      have a clone).
⭐   ⑤ ⭐ Post-mortem: ⭐⭐ WHY WAS IT POSSIBLE TO PUT IT THERE?
⭐      ⭐ That is the fix; the rotation was the response.
```

# Part 7 — ⭐ Config as a deployment risk

```
⭐⭐ THE UNCOMFORTABLE STATISTIC: ⭐⭐ A LARGE SHARE OF MAJOR
⭐   OUTAGES ARE CONFIGURATION CHANGES, NOT CODE CHANGES.
⭐   ⭐ Config often bypasses code review, tests, canaries and
⭐     rollback tooling — ⭐⭐ SO IT IS THE ***LEAST GOVERNED***
⭐     AND ***MOST IMMEDIATE*** WAY TO CHANGE PRODUCTION
⭐     BEHAVIOUR.

⭐⭐ SO GIVE CONFIG THE SAME TREATMENT AS CODE:
⭐   ⭐ ⭐⭐ VERSION IT, REVIEW IT, AND MAKE CHANGES REVERSIBLE.
⭐   ⭐ ⭐⭐ VALIDATE IT AGAINST A SCHEMA ***BEFORE*** APPLYING —
⭐     ⭐ a typo in a limit or a malformed connection string
⭐     should fail in the pipeline, not on a pod.
⭐   ⭐ ⭐⭐ ROLL IT OUT GRADUALLY WHERE POSSIBLE — ⭐ a feature
⭐     flag is a canaried config change, which is exactly what
⭐     makes flags safer than env vars (Day 371).
⭐   ⭐ ⭐⭐ EMIT A CHANGE EVENT TO YOUR MONITORING SYSTEM, LIKE
⭐     A DEPLOY MARKER (Day 370) — ⭐ so "what changed at 14:32?"
⭐     includes config, ⭐⭐ WHICH IS THE ANSWER SURPRISINGLY
⭐     OFTEN AND THE ONE NOBODY LOOKS FOR.

⭐⭐ AND THE THREE CONFIG CHANGES THAT MOST OFTEN CAUSE
⭐   OUTAGES — ⭐ worth naming, because they recur:
⭐   ① ⭐⭐ A LIMIT LOWERED "TO BE SAFE" — a rate limit, a pool
⭐      size, a memory limit — ⭐ that turns out to be below
⭐      actual demand.
⭐   ② ⭐⭐ A TIMEOUT SHORTENED, CAUSING RETRIES AND THEN A
⭐      CASCADE (Day 339).
⭐   ③ ⭐⭐ A FEATURE FLAG FLIPPED FOR 100% WITHOUT A RAMP.
⭐   ⇒ ⭐ All three are one-line changes with no code review,
⭐     ⭐⭐ WHICH IS PRECISELY WHY THEY ARE DANGEROUS.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Judging secret management by storage rather than rotation speed | A credential you can't rotate in an hour can't be responded to |
| ⭐⭐ Secrets in env vars for high-value credentials | Inherited by every child process, and error SDKs attach the environment by default |
| ⭐ Committing a secret and deleting it later | Git never forgets. The only response is rotation |
| ⭐⭐ Assuming Kubernetes Secrets are encrypted | Base64 is an encoding. Anyone who can `get secrets` has them all |
| ⭐⭐ A rotation plan that ignores two-credential coexistence | There's always a moment when some instances have each. Rotation is an app capability |
| ⭐⭐ Assuming two-key rotation works for Postgres | One password per role. You need two roles, a proxy, or IAM auth |
| ⭐ A rotation procedure that's never been run | It won't work during the incident |
| ⭐ A secrets manager as an uncached startup dependency | It's down, nothing starts — during the incident when everything restarts |
| ⭐⭐ Capturing the credential at import time | The password is frozen forever, so short-lived tokens can't work |
| ⭐ Using an access key where an IAM role would do | Half the secrets in a typical AWS app shouldn't exist |
| ⭐ `os.environ` read deep inside functions | Configuration becomes untestable and invisible |
| ⭐ No `extra="forbid"` | A typo'd variable silently uses the default, and it takes a day to find |
| ⭐⭐ Config changes outside review, tests and rollback | Config causes a large share of major outages precisely because it's ungoverned |
| ⭐ No config-change marker in monitoring | "What changed at 14:32?" misses the answer surprisingly often |

## Interview questions

**1. "How do you manage secrets?"**
> ⭐⭐ I'd reframe it: **the interesting question isn't where they're stored, it's how fast I can change
> one.** ⭐ If the answer to "this leaked five minutes ago" is "we'd coordinate a deploy across four
> services", that's secret *storage*, not secret management. ⭐ So: a manager rather than env vars for
> anything high-value, mounted files rather than environment so they aren't inherited by child
> processes, ⭐⭐ **and short-lived credentials wherever available — because then no rotation procedure
> exists, since nothing lasts long enough to need one.**

**2. "Why is rotation hard?"**
> ⭐⭐ Because **there's always a moment when some instances have the old credential and some have the
> new one** — it's the same coexistence problem as a rolling deploy. ⭐ So rotation requires two valid
> credentials simultaneously, which is an application and provider capability rather than a storage
> one. ⭐⭐ And the case everyone has is the awkward one: **Postgres supports one password per role**, so
> two-key rotation doesn't work directly — you need two roles with identical grants, a connection proxy
> holding the credential, or IAM authentication with fifteen-minute tokens.

**3. "Where do environment variables stop being enough?"**
> ⭐ Four places. They're flat strings, so nested config becomes a data structure encoded in a naming
> convention. ⭐ They're read once at startup, ⭐⭐ **so every config change is a deploy and rotation
> becomes a rolling restart.** ⭐⭐ They're inherited by every child process, so a `subprocess.run` gets
> your database password. ⭐ And they're visible in `inspect` and `/proc` — ⭐⭐ **and most error-
> reporting SDKs attach the environment to events by default, which is how secrets end up in a
> third-party SaaS.**

**4. "A key leaked. What do you do?"**
> ⭐⭐ **Rotate first, investigate second** — the investigation can happen while the key is already dead.
> ⭐ Then revoke the old one explicitly and confirm it's revoked; ⭐⭐ **check the audit log for use
> *before* the rotation, because that's the actual blast radius**; purge from history if it's in a repo,
> while still treating it as compromised because someone may have a clone. ⭐ Then the post-mortem
> question that matters: **why was it possible to put it there?** The rotation was the response; that's
> the fix.

**5. "What controls actually work?"**
> ⭐ Pre-commit and CI scanning that checks history rather than just the diff, because the secret is
> usually three commits back. ⭐ Provider-side scanning, which often gets the key quarantined
> automatically and costs nothing to enable. ⭐⭐ **Canary tokens — a credential that does nothing but
> alert when used**, so you learn about unauthorised reading in seconds rather than months. ⭐ Usage
> alerting on unexpected region, volume or API. ⭐⭐ And least privilege, **the only control that limits
> the damage rather than the probability — a read-only key leaked is an incident, an admin key is a
> company event.**

**6. "What's the riskiest change you can make to production?"**
> ⭐⭐ A configuration change, and it surprises people. **A large share of major outages are config, not
> code, because config bypasses review, tests, canaries and rollback tooling — so it's the least
> governed and most immediate way to change behaviour.** ⭐ The three that recur: a limit lowered to be
> safe that's below actual demand; a timeout shortened, causing retries and then a cascade; and a flag
> flipped to 100% with no ramp. ⭐ So config gets versioned, reviewed, schema-validated before it
> applies, rolled out gradually, ⭐⭐ **and emits a change marker to monitoring, because "what changed at
> 14:32" is the first question and config is the answer more often than anyone expects.**

coordinate a deploy across four services", that's storage, not management. Then give the honest limits
of the twelve-factor default: **env vars are flat strings, read once at startup so every change is a
deploy, inherited by every child process, and attached to error reports by most SDKs by default** —
which is how secrets end up in a third-party SaaS. So env vars for non-secret config and pointers,
files or a manager for the secrets themselves. Then the part that's actually hard: **rotation requires
two valid credentials at once, because there's always a moment when some instances have each** — which
makes it an application capability, not a storage one — ⭐ and give the case everyone has: **Postgres
allows one password per role, so two-key rotation doesn't work; you need two roles, a proxy, or IAM
auth with short tokens.** Say the best answer out loud: **short-lived credentials, where no rotation
procedure exists because nothing lasts long enough to need one.** Close on detection and on the
surprising risk: **rotate first and investigate second, check the audit log for use before rotation
because that's the blast radius** — and **config causes a large share of major outages precisely
because it bypasses review, tests, canaries and rollback.**
