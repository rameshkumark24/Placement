# Day 409 ⏱️

**P-409** · ⏱️ **Time and ordering** — clocks, Lamport, vector clocks

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: there is no "now" in a distributed system — physical clocks disagree and
> jump — so ordering must come from causality you track explicitly, and any design that resolves a
> conflict by comparing two machines' timestamps is losing data it will never notice losing.**

---

# Part 1 — How physical clocks actually lie

```
⭐ ① ⭐ ***DRIFT.*** ⭐ A typical crystal drifts tens of
⭐    microseconds per second. ⭐ NTP corrects it, ⭐⭐ AND NTP
⭐    ITSELF IS ACCURATE TO ROUGHLY 1–50 ms ON A GOOD NETWORK AND
⭐    WORSE ON A BUSY OR VIRTUALISED ONE.
⭐ ② ⭐⭐ ***SKEW ACROSS A FLEET.*** ⭐ Two servers can differ by
⭐    tens or hundreds of milliseconds ***right now***, ⭐ and
⭐    nothing in your monitoring is looking.
⭐ ③ ⭐⭐ ***STEPS.*** ⭐ NTP can ***jump*** the clock — forwards or
⭐    ***backwards*** — when the offset is large. ⭐ A VM resumed
⭐    from suspend jumps. ⭐ A container on a throttled host
⭐    (Day 361) sees time move oddly.
⭐ ④ ⭐ ***LEAP SECONDS*** and smearing.

⭐⭐ ⇒ AND THE PYTHON RULE THAT FALLS OUT OF ③, WHICH IS A REAL
⭐   BUG PEOPLE SHIP:
⭐   ⭐⭐ ***`time.time()` IS NOT MONOTONIC. IT CAN GO BACKWARDS.***
⭐   ⭐ So a duration computed with it can be ***negative***, and
⭐     a timeout computed with it can be ***infinite***:

⭐   ❌ deadline = time.time() + 30
⭐      while time.time() < deadline:   ⭐⭐ NTP STEPS BACK 60 s
⭐          ...                          ⭐⭐ → LOOPS FOR 90 s
⭐   ✅ deadline = time.monotonic() + 30
⭐      while time.monotonic() < deadline: ...

⭐   ⭐⭐ ***`time.monotonic()` FOR DURATIONS AND TIMEOUTS.
⭐   `time.time()` FOR WALL-CLOCK DISPLAY AND STORAGE. NEVER THE
⭐   REVERSE.*** ⭐ `time.perf_counter()` for benchmarks.
⭐   ⭐ And store timezone-aware UTC: `datetime.now(timezone.utc)`
⭐     — ⭐⭐ `datetime.utcnow()` RETURNS A ***NAIVE*** DATETIME AND
⭐     IS DEPRECATED, ⭐ and naive datetimes compared against
⭐     aware ones raise at exactly the wrong moment.
```

# Part 2 — ⭐⭐ Why last-write-wins silently loses data

```
⭐ THE SETUP — ⭐ and every part of it is ordinary:
⭐   ⭐ Server A's clock is 500 ms ***ahead***.
⭐   ⭐ 10:00:00.000 (real) — A writes `status=shipped`,
⭐     ⭐⭐ STAMPS IT 10:00:00.500
⭐   ⭐ 10:00:00.200 (real) — B writes `status=cancelled`,
⭐     ⭐ stamps it 10:00:00.200
⭐   ⭐ Conflict resolution compares timestamps.
⭐   ⭐⭐ ***10:00:00.500 > 10:00:00.200, SO `shipped` WINS.***
⭐   ⭐⭐ THE ***LATER*** WRITE — THE CANCELLATION — IS SILENTLY
⭐     DISCARDED. ⭐ No error. ⭐ No conflict reported. ⭐⭐ THE
⭐     CUSTOMER'S CANCELLATION SIMPLY DID NOT HAPPEN.

⭐⭐ ⇒ THIS IS NOT A THOUGHT EXPERIMENT. ⭐ It is the documented
⭐   behaviour of last-write-wins in Cassandra and
⭐   Dynamo-style stores, ⭐ of `SET`-based cache invalidation,
⭐   ⭐⭐ AND OF ANY MULTI-LEADER SETUP WHERE SOMEONE PICKED "USE
⭐   THE NEWER TIMESTAMP" BECAUSE IT SOUNDED OBVIOUS.

⭐⭐ ⇒ ***NEVER RESOLVE A CONFLICT BY COMPARING TWO MACHINES'
⭐   WALL CLOCKS UNLESS YOU CAN BOUND THE SKEW — AND YOU
⭐   CANNOT.*** ⭐ (Spanner can, at enormous cost. Part 7.)
⭐ ⭐ LWW is acceptable in exactly one case: ⭐⭐ WHEN LOSING A
⭐   WRITE IS GENUINELY FINE — ⭐ a cached view count, a
⭐   last-seen timestamp. ⭐⭐ SAY SO EXPLICITLY WHEN YOU CHOOSE
⭐   IT.
```

# Part 3 — Happened-before, and Lamport clocks

```
⭐⭐ ***HAPPENED-BEFORE (→), DEFINED IN THREE RULES:***
⭐   ⭐ ① a → b if they are in the same process and a came first
⭐   ⭐ ② send(m) → receive(m)
⭐   ⭐ ③ transitivity: a → b and b → c ⇒ a → c
⭐   ⭐⭐ AND IF NEITHER a → b NOR b → a, THEY ARE
⭐   ***CONCURRENT***. ⭐ Not "simultaneous" — ⭐⭐ ***CAUSALLY
⭐   UNRELATED***, ⭐ which is a much stronger and more useful
⭐   statement, because it says no information could have flowed
⭐   between them.

⭐ ***LAMPORT CLOCK*** — one integer per node:
⭐   ⭐ on any local event: `L += 1`
⭐   ⭐ on send: `L += 1`, attach L
⭐   ⭐ on receive: ⭐⭐ `L = max(L, received) + 1`

⭐⭐ WHAT IT GIVES YOU — ⭐ and the asymmetry is the whole point:
⭐   ⭐⭐ ✅ ***IF a → b THEN L(a) < L(b).***
⭐   ⭐⭐ ❌ ***THE CONVERSE IS FALSE. L(a) < L(b) DOES ***NOT***
⭐      MEAN a HAPPENED BEFORE b*** — ⭐ they may be concurrent
⭐      and the numbers merely differ.

⭐⭐ ⇒ SO A LAMPORT CLOCK GIVES YOU A ***TOTAL ORDER*** (break
⭐   ties with the node id) THAT IS ***CONSISTENT WITH
⭐   CAUSALITY*** — ⭐ but it ***invents*** an order between
⭐   concurrent events.
⭐   ⭐ ✅ USE IT FOR: a deterministic, everywhere-agreed tiebreak.
⭐   ⭐⭐ ❌ NEVER USE IT TO ***DETECT*** A CONFLICT, ⭐ because it
⭐     cannot tell "b came after a" from "b and a were
⭐     concurrent". ⭐⭐ IT WILL HAPPILY ORDER TWO CONFLICTING
⭐     WRITES AND THROW ONE AWAY.
```

# Part 4 — ⭐⭐ Vector clocks: the ones that can detect a conflict

```
⭐ ONE COUNTER ***PER NODE***: ⭐ `V = {A:3, B:7, C:2}`
⭐   ⭐ on a local event: increment your own entry
⭐   ⭐ on receive: ⭐⭐ ELEMENT-WISE `max`, THEN INCREMENT YOUR OWN

⭐ COMPARISON:
⭐   ⭐ `V1 < V2` iff every element of V1 ≤ V2 ***and*** at least
⭐     one is strictly less ⭐ ⇒ ***V1 happened before V2.***
⭐   ⭐⭐ IF NEITHER `V1 < V2` NOR `V2 < V1`, THEY ARE
⭐   ***CONCURRENT*** — ⭐⭐ AND YOU HAVE ***DETECTED A CONFLICT***,
⭐   WHICH IS THE THING LAMPORT CLOCKS CANNOT DO.

⭐   ⭐ {A:2, B:1} vs {A:3, B:1} → ⭐ the second descends from the
⭐     first. ⭐ Safe to overwrite.
⭐   ⭐ {A:2, B:1} vs {A:1, B:2} → ⭐⭐ CONCURRENT. TWO PEOPLE
⭐     EDITED. ⭐ You must now ***decide***, not guess.

⭐⭐ ⇒ AND THIS IS EXACTLY DAY 348's DYNAMO SIBLINGS: ⭐ the store
⭐   keeps ***both*** versions and hands them to the client to
⭐   merge. ⭐⭐ THAT FEELS LIKE THE DATABASE PASSING THE PROBLEM
⭐   BACK TO YOU, AND IT IS — ⭐ but the alternative is silently
⭐   losing one of them, ⭐⭐ AND A CONFLICT YOU CAN SEE IS
⭐   INFINITELY BETTER THAN ONE YOU CANNOT.

⭐ THE COST: ⭐⭐ THE VECTOR GROWS WITH THE NUMBER OF WRITERS,
⭐   ⭐ so a system where every client writes has a vector the
⭐   size of your user base. ⭐⭐ AND PRUNING OLD ENTRIES IS WHERE
⭐   IMPLEMENTATIONS GET IT WRONG — ⭐ prune too eagerly and you
⭐   report a conflict that is not one, ⭐⭐ OR WORSE, MISS ONE
⭐   THAT IS.
```

# Part 5 — Hybrid logical clocks: the modern practical answer

```
⭐⭐ THE PROBLEM WITH BOTH SO FAR: ⭐ a Lamport or vector value is
⭐   a ***number with no relationship to wall-clock time***, ⭐ so
⭐   you cannot use it for a TTL, cannot show it to a human,
⭐   ⭐ cannot ask "what happened around 3 p.m.".

⭐⭐ ***HLC: PHYSICAL TIME IN THE HIGH BITS, A LOGICAL COUNTER IN
⭐   THE LOW BITS.***
⭐   ⭐ On an event: ⭐ `l' = max(l, physical_now)`;
⭐     ⭐ if `l' == l` then `c += 1` else `c = 0`.
⭐   ⭐ On receive: ⭐ take the max across local, received and
⭐     physical, ⭐ bumping the counter on ties.

⭐⭐ ⇒ WHAT YOU GET, AND IT IS THE BEST OF BOTH:
⭐   ⭐⭐ ① IT IS ***CAUSALLY CONSISTENT*** — a → b ⇒ HLC(a) <
⭐      HLC(b), like Lamport.
⭐   ⭐⭐ ② IT IS ***MONOTONIC*** — it never goes backwards, even
⭐      if the physical clock steps.
⭐   ⭐⭐ ③ IT STAYS ***CLOSE TO WALL-CLOCK TIME*** (bounded by
⭐      the clock skew), ⭐ so it is human-readable and usable for
⭐      retention and TTLs.
⭐   ⭐ ④ Fixed size — 64 bits — ⭐⭐ UNLIKE A VECTOR CLOCK.
⭐ ⭐ Used by CockroachDB, MongoDB, YugabyteDB.
⭐ ⭐⭐ THE LIMITATION TO STATE: LIKE LAMPORT, IT CANNOT ***DETECT***
⭐   CONCURRENCY. ⭐ It orders everything. ⭐ If you need conflict
⭐   detection you still need vectors ⭐⭐ — SO THE HONEST SUMMARY
⭐   IS: HLC FOR ***ORDERING AND TIMESTAMPS***, VECTORS FOR
⭐   ***CONFLICT DETECTION***, AND THEY SOLVE DIFFERENT PROBLEMS.

⭐ ⭐ Practical Python cousins: ⭐⭐ ***ULID AND UUIDv7*** —
⭐   timestamp-prefixed, ***lexicographically sortable***
⭐   identifiers. ⭐ They give you rough time ordering and good
⭐   index locality (Day 187) ⭐⭐ WITHOUT PRETENDING TO BE A
⭐   CLOCK — ⭐ two ULIDs generated on different machines in the
⭐   same millisecond have no meaningful order, ⭐⭐ AND YOU MUST
⭐   NOT TREAT THEIR ORDER AS CAUSAL.
```

# Part 6 — Where this shows up in your actual code

```
⭐ ① ⭐⭐ ***CACHE INVALIDATION.*** ⭐ "Only overwrite if my
⭐    timestamp is newer" across two app servers ⭐⭐ IS PART 2's
⭐    BUG, IN YOUR CODE, TODAY. ⭐ Use a version number from the
⭐    database (Day 405), ⭐ not a clock.
⭐ ② ⭐ ***`updated_at`-BASED SYNC.*** ⭐ "Give me everything
⭐    changed since T" ⭐⭐ MISSES ROWS WHOSE TRANSACTION STARTED
⭐    BEFORE T AND COMMITTED AFTER — ⭐ which is Day 407's gap bug
⭐    wearing a timestamp. ⭐⭐ USE A SEQUENCE OR AN LSN, OR CLAIM
⭐    AND DELETE.
⭐ ③ ⭐ ***DISTRIBUTED LOCK TTLs.*** ⭐⭐ A LOCK EXPIRING "IN 30
⭐    SECONDS" MEANS 30 SECONDS ON ***WHOSE*** CLOCK? ⭐ Day 411.
⭐ ④ ⭐⭐ ***JWT `exp` VALIDATION.*** ⭐ Skew between the issuer and
⭐    the verifier means a token can be rejected as expired
⭐    before it is, ⭐ or accepted after. ⭐⭐ ALLOW A LEEWAY
⭐    (30–60 s) AND KNOW THAT YOU ARE TRADING SECURITY FOR SKEW
⭐    TOLERANCE.
⭐ ⑤ ⭐ ***LOG CORRELATION.*** ⭐⭐ TWO SERVICES' LOGS INTERLEAVED
⭐    BY TIMESTAMP CAN SHOW THE RESPONSE BEFORE THE REQUEST.
⭐    ⭐ This is why you correlate by ***trace id and span
⭐    parentage***, not by time (Day 376).
⭐ ⑥ ⭐ ***SCHEDULED JOBS.*** ⭐ "Run at midnight" on twelve
⭐    servers with 200 ms of skew ⭐⭐ IS TWELVE SLIGHTLY
⭐    DIFFERENT MIDNIGHTS, ⭐ and a job that reads "yesterday"
⭐    can see a boundary row twice or not at all.
```

# Part 7 — Spanner and TrueTime, read correctly

```
⭐ ⭐⭐ GOOGLE DID NOT SOLVE CLOCK UNCERTAINTY. ⭐ They
⭐   ***bounded*** it and then ***paid*** for it.
⭐   ⭐ Atomic clocks and GPS receivers in every datacentre give
⭐     an API that returns an ***interval***: `[earliest,
⭐     latest]`, typically a few milliseconds wide.
⭐   ⭐⭐ AND THEN — THIS IS THE PART PEOPLE MISS — ***SPANNER
⭐     WAITS OUT THE UNCERTAINTY BEFORE COMMITTING.*** ⭐ Commit
⭐     wait: sleep until you are certain the timestamp is in the
⭐     past everywhere. ⭐ Roughly 7 ms, ⭐⭐ ON EVERY WRITE.

⭐⭐ ⇒ THE INSIGHT WORTH TAKING: ***THEY CONVERTED AN UNKNOWN
⭐   INTO A KNOWN BOUND, AND THEN BOUGHT CERTAINTY WITH
⭐   LATENCY.*** ⭐ That is the only way anyone has ever made
⭐   wall-clock ordering safe.

⭐⭐ ⇒ AND THE TAKEAWAY FOR YOU: ***YOU DO NOT HAVE TRUETIME.***
⭐   ⭐ Your clock uncertainty is unbounded and unmeasured.
⭐   ⭐⭐ SO ANY DESIGN OF YOURS THAT ASSUMES SYNCHRONISED CLOCKS
⭐   IS WRONG, AND THE CORRECT MOVES ARE THE ONES IN THIS DAY:
⭐   ⭐ version numbers for conflicts, ⭐ sequences or LSNs for
⭐   "what changed since", ⭐ causal metadata for ordering,
⭐   ⭐⭐ AND WALL CLOCKS ONLY FOR DISPLAYING THINGS TO HUMANS.
```

# 💬 Interview

**1. ⭐⭐ "What's wrong with last-write-wins?"**
> ⭐ It loses data silently, and the example is ordinary. ⭐⭐ **If server A's clock is 500 ms ahead, a
> write it makes at 10:00:00.000 real time is stamped 10:00:00.500, and a write server B makes 200 ms
> *later* is stamped 10:00:00.200 — so comparing timestamps discards the later write. The customer's
> cancellation simply didn't happen, with no error and no conflict reported.** ⭐ That's the documented
> behaviour of LWW in Dynamo-style stores and of any timestamp-based cache invalidation. ⭐⭐ **So never
> resolve a conflict by comparing two machines' wall clocks unless you can bound the skew — and you
> can't.** ⭐ LWW is fine in exactly one case: when losing a write is genuinely acceptable, like a view
> count — and you say so explicitly when you choose it.

**2. ⭐⭐ "Lamport clocks versus vector clocks."**
> ⭐ Both track causality, but only one can detect a conflict. ⭐⭐ **A Lamport clock is a single integer
> and gives you: if a happened before b, then L(a) < L(b). The converse is false — L(a) < L(b) does
> not mean a happened before b, because they may be concurrent.** ⭐ So a Lamport clock gives you a
> total order consistent with causality, ⭐⭐ **but it invents an order between concurrent events, which
> means it will happily order two conflicting writes and throw one away.** ⭐ A vector clock is one
> counter per node, ⭐⭐ **and if neither vector dominates the other the events are concurrent — you have
> detected a conflict, which Lamport cannot do.** ⭐ That's exactly Dynamo's siblings. ⭐ The cost is
> that the vector grows with the number of writers, and pruning it is where implementations get it
> wrong.

**3. "What's a hybrid logical clock?"**
> ⭐⭐ **Physical time in the high bits and a logical counter in the low bits** — so you get a value
> that's causally consistent like Lamport, monotonic even when the physical clock steps, ⭐⭐ **and stays
> close to wall-clock time, so it's human-readable and usable for TTLs and retention** — in a fixed 64
> bits, unlike a vector. ⭐ CockroachDB and MongoDB use them. ⭐ The honest limitation is that ⭐⭐ **like
> Lamport it orders everything and cannot detect concurrency — so HLC for ordering and timestamps,
> vectors for conflict detection; they solve different problems.**

**4. ⭐⭐ "Is there a Python-specific clock bug?"**
> ⭐ Yes, and it's a real one. ⭐⭐ **`time.time()` is not monotonic — NTP can step it backwards — so a
> deadline computed as `time.time() + 30` can loop for ninety seconds after a sixty-second backward
> step, and a duration computed from it can be negative.** ⭐ The rule is `time.monotonic()` for
> durations and timeouts, `time.time()` for wall-clock display and storage, never the reverse, and
> `perf_counter()` for benchmarks. ⭐⭐ **And store timezone-aware UTC with `datetime.now(timezone.utc)`
> — `utcnow()` returns a naive datetime and is deprecated, and naive-versus-aware comparisons raise at
> exactly the wrong moment.**

**5. "What did Spanner actually solve?"**
> ⭐⭐ **Nothing — they bounded the uncertainty rather than removing it, and then paid for it.** ⭐ Atomic
> clocks and GPS give an API that returns an interval rather than a point, a few milliseconds wide,
> ⭐⭐ **and then Spanner *waits out* that interval before committing — about seven milliseconds of
> commit-wait on every write.** ⭐ The insight worth taking is that they converted an unknown into a
> known bound and then bought certainty with latency, ⭐⭐ **and the takeaway for me is that I don't have
> TrueTime: my clock uncertainty is unbounded and unmeasured, so any design of mine assuming
> synchronised clocks is wrong.**

**6. ⭐⭐ "Where does this bite in ordinary code?"**
> ⭐ Four places I'd look. ⭐⭐ **Cache invalidation with "only overwrite if my timestamp is newer" is
> the LWW bug in your own codebase today — use a version number from the database, not a clock.**
> ⭐⭐ **`updated_at`-based sync misses rows whose transaction started before T and committed after,
> which is the outbox gap bug wearing a timestamp — use a sequence, an LSN, or claim-and-delete.**
> ⭐ JWT `exp` validation needs a leeway for skew, and that leeway is a security trade you should name.
> ⭐ And ⭐⭐ **correlating two services' logs by timestamp can show the response before the request,
> which is why you correlate by trace id and span parentage instead.**
