# Part 0 — ⭐ Build the dataset (20 minutes, then leave it alone)

```sql
CREATE TABLE users (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL,
    country     text NOT NULL,
    city        text NOT NULL,
    created_at  timestamptz NOT NULL
);
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     bigint NOT NULL REFERENCES users,
    tenant_id   int NOT NULL,
    status      text NOT NULL,
    total_cents bigint NOT NULL,
    notes       text,                       -- ⭐ for the TOAST case

    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL REFERENCES orders,

);
CREATE TABLE payments (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL REFERENCES orders,
    amount_cents bigint NOT NULL
);
-- ⭐⭐ NO INDEXES BEYOND THE PRIMARY KEYS. That is the point.
```

# ⭐ Query 1 — the report that filters on a date

```sql
SELECT count(*) FROM orders WHERE date(created_at) = '2026-03-14';
-- ⭐ 4.2 s · Seq Scan · Rows Removed by Filter: 4,994,000
```

<details><summary>⭐⭐ Diagnose first. Then open.</summary>

```
⭐⭐ CAUSE: NON-SARGABLE — a function wraps the column, so no B-tree
⭐   ordering on `created_at` can apply (Day 189 ①).
⭐ FIX — a half-open range, which is also correct across timezones:
⭐   CREATE INDEX ON orders (created_at);
⭐   WHERE created_at >= '2026-03-14' AND created_at < '2026-03-15'
⭐ RESULT: 4.2 s → ⭐⭐ 6 ms. Buffers 41,000 → 38.
⭐ ⭐ ALTERNATIVE if you cannot change the query (an ORM you don't
⭐   control): `CREATE INDEX ON orders (date(created_at));` — an
⭐   expression index. ⭐⭐ Note it also gives the planner statistics for
⭐   that expression, which is a second, invisible win.
```
</details>

# ⭐⭐ Query 2 — the list endpoint

```sql
SELECT * FROM orders
WHERE tenant_id = 7 AND status = 'paid'
  AND created_at > now() - interval '30 days'
ORDER BY created_at DESC LIMIT 20;
-- ⭐ 890 ms, with `CREATE INDEX ON orders (created_at)` already present
-- ⭐ Index Scan Backward … Rows Removed by Filter: 164,000
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: THE INDEX EXISTS BUT THE COLUMN ORDER IS WRONG. It can order,
⭐   so there is no Sort node and it LOOKS healthy — but every equality
⭐   is a per-row FILTER, so it walks 164,000 entries to find 20.
⭐ FIX — E-S-R (Day 190): equality, sort, range.
⭐   CREATE INDEX ON orders (tenant_id, status, created_at DESC);
⭐ RESULT: 890 ms → ⭐⭐ 0.4 ms. Rows Removed by Filter: 0.
⭐ ⭐⭐ THE LESSON THAT GENERALISES: "there is no Sort node" is NOT proof
⭐   the index is right. `Rows Removed by Filter` is.
```
</details>

# ⭐⭐ Query 3 — page 2,500 of the admin table

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 50000;
-- ⭐ page 1: 0.3 ms · ⭐⭐ page 2500: 1,100 ms — and getting worse daily
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: `OFFSET` DOES NOT SKIP. IT FETCHES AND DISCARDS. Page 2,500
⭐   reads 50,020 rows to return 20. ⭐⭐ COST GROWS LINEARLY WITH PAGE
⭐   NUMBER — the last page of a table is a full scan, every time.
⭐ FIX — KEYSET (cursor) PAGINATION: remember the last row, not a count.
⭐   SELECT * FROM orders
⭐   WHERE (created_at, id) < ($1, $2)      -- ⭐ ROW COMPARISON, and the
⭐   ORDER BY created_at DESC, id DESC      --   `id` breaks ties so no
⭐   LIMIT 20;                              --   row is skipped/repeated
⭐   ⭐ index: (created_at DESC, id DESC)
⭐ RESULT: ⭐⭐ 0.4 ms ON EVERY PAGE, FOREVER.
⭐ ⭐⭐ THE COST YOU MUST STATE HONESTLY: NO "JUMP TO PAGE 500". You get
⭐   next/previous. ⭐ That is why Day 176 called cursor pagination the
⭐   right default for APIs — and why an admin UI may keep OFFSET with a
⭐   hard page cap.
```
</details>

# ⭐⭐ Query 4 — "and the total, for the pagination footer"

```sql
SELECT count(*) FROM orders WHERE tenant_id = 7;
-- ⭐⭐ 2.8 s, EVERY REQUEST, next to a 0.4 ms page query.
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: MVCC. Postgres CANNOT keep a row count, because a row's
⭐   visibility depends on YOUR transaction (Day 194). ⭐⭐ `count(*)` IS
⭐   ALWAYS A SCAN of everything matching. An index-only scan helps and
⭐   does not save you.
⭐ ⭐⭐ THIS IS THE MOST COMMON UNNECESSARY QUERY IN WEB APPLICATIONS —
⭐   the exact count exists purely to render "Page 1 of 6,213", which no
⭐   user has ever used.
⭐ THE FOUR HONEST OPTIONS, in the order to try them:
⭐   ① ⭐⭐ DELETE IT. Cursor pagination needs no total (see Query 3).
⭐   ② APPROXIMATE: `SELECT reltuples::bigint FROM pg_class WHERE
⭐        relname='orders'` — ⭐ instant, whole-table only, stale by one
⭐        autovacuum. ⭐⭐ Fine for "about 5,000,000 orders".
⭐        For a filtered estimate: parse the planner's own row estimate
⭐        out of `EXPLAIN (FORMAT JSON)`. ⭐ Legitimate and underused.
⭐   ③ CAP IT: `SELECT count(*) FROM (SELECT 1 FROM orders
⭐        WHERE tenant_id=7 LIMIT 1001) t` ⇒ ⭐ "1000+". Bounded work.
⭐   ④ MAINTAIN IT: a counters table (Day 188) — ⭐⭐ with the
⭐        reconciliation job, or it will drift.
⭐ RESULT: 2.8 s → ⭐⭐ 0 ms (option ①) or 0.1 ms (option ②).
```
</details>

# ⭐ Query 5 — product search

```sql
SELECT * FROM order_items WHERE product_name ILIKE '%widget%' LIMIT 50;
-- ⭐ 6.1 s · Seq Scan on 15M rows
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: a leading wildcard. A B-tree is sorted by PREFIX; there is no
⭐   prefix here. ⭐ No amount of B-tree indexing helps (Day 189 ③).
⭐ FIX:
⭐   CREATE EXTENSION pg_trgm;
⭐   CREATE INDEX ON order_items USING gin (product_name gin_trgm_ops);
⭐ RESULT: 6.1 s → ⭐⭐ 12 ms, and `ILIKE` works too (trigrams are
⭐   case-folded).
⭐ ⭐⭐ STATE THE COST OUT LOUD: the GIN index is large, and GIN writes
⭐   are slow with a pending-list flush that spikes one unlucky insert.
⭐   ⭐ Right for a catalogue. Wrong for a high-write event stream —
⭐     there the answer is a separate search index or FTS (Day 199).
```
</details>

# ⭐⭐ Query 6 — the N+1, seen from the database side

```
⭐ pg_stat_statements shows:
⭐   SELECT * FROM order_items WHERE order_id = $1
⭐   calls: 2,340,000   mean: 0.3 ms   ⭐⭐ total: 11.7 minutes/hour
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: THE N+1 (Day 136). And note HOW IT PRESENTS: every individual
⭐   execution is FAST. ⭐⭐ NOTHING IN A SLOW-QUERY LOG WILL EVER SHOW
⭐   THIS — it only appears when you sort `pg_stat_statements` by TOTAL
⭐   time. ⭐ That is the whole reason Day 190 said "rank by total".
⭐ FIX — at the application layer, not the database:
⭐   ⭐ SQLAlchemy: `selectinload(Order.items)` (2 queries, no row
⭐     multiplication) or `joinedload` for a single parent.
⭐   ⭐ Django: `prefetch_related("items")`.
⭐   ⭐⭐ AND THE PREVENTION, WHICH IS WORTH MORE THAN THE FIX:
⭐     `lazy="raise"` + a per-endpoint query-count ceiling in tests
⭐     (Day 141). ⭐ This bug should be impossible to merge, not fast to
⭐     find.
⭐ RESULT: 2,340,000 calls/hour → ⭐⭐ ~2,000.
```
</details>

# ⭐⭐ Query 7 — the dashboard number that is wrong *and* slow

```sql
SELECT o.id, sum(i.amount_cents) AS items, sum(p.amount_cents) AS paid
FROM orders o
JOIN order_items i ON i.order_id = o.id
JOIN payments    p ON p.order_id = o.id
WHERE o.tenant_id = 7
GROUP BY o.id;
-- ⭐ 14 s ⭐⭐ AND THE NUMBERS DO NOT MATCH THE SOURCE DATA
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: ROW MULTIPLICATION (Day 192 ④). 3 items × 2 payments = 6 rows
⭐   per order. `items` is DOUBLED, `paid` is TRIPLED. ⭐⭐ THE QUERY IS
⭐   NOT JUST SLOW — IT IS WRONG, and it returns plausible numbers.
⭐ ❌ THE FIX PEOPLE REACH FOR: `sum(DISTINCT ...)` — ⭐⭐ WHICH IS ALSO
⭐   WRONG. Two identical £10 line items would collapse into one.
⭐ ✅ THE FIX — aggregate each side BEFORE joining:
⭐   SELECT o.id, i.items, p.paid
⭐   FROM orders o
⭐   LEFT JOIN (SELECT order_id, sum(amount_cents) items
⭐              FROM order_items GROUP BY order_id) i ON i.order_id=o.id
⭐   LEFT JOIN (SELECT order_id, sum(amount_cents) paid
⭐              FROM payments    GROUP BY order_id) p ON p.order_id=o.id
⭐   WHERE o.tenant_id = 7;
⭐   ⭐ plus indexes on order_items(order_id), payments(order_id).
⭐ RESULT: 14 s → ⭐⭐ 340 ms, and the numbers are now correct.
⭐ ⭐⭐ THE FACT WORTH CARRYING: `COUNT(DISTINCT)` FIXES COUNTS AND
⭐   `SUM(DISTINCT)` DOES NOT FIX SUMS. Different bugs, same shape.
```
</details>

# ⭐ Query 8 — the monthly export

```sql
SELECT user_id, count(*), sum(total_cents) FROM orders
WHERE created_at >= '2026-01-01' GROUP BY user_id ORDER BY 3 DESC;
-- ⭐ 38 s · Sort Method: external merge  Disk: 512MB
-- ⭐ Buffers: … temp read=64000 written=64000
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: A SPILL. The aggregate and sort exceeded `work_mem` (4 MB
⭐   default) and went to temp files — 512 MB written and read back.
⭐ FIX, in order of preference:
⭐   ① ⭐ REDUCE THE DATA FIRST: is the date filter selective? Is
⭐        `SELECT *` pulling columns you discard? (See Query 10.)
⭐   ② ⭐⭐ `SET LOCAL work_mem = '256MB'` FOR THIS ONE JOB — inside its
⭐        transaction, never globally (Day 191's arithmetic: per node,
⭐        per connection).
⭐   ③ ⭐ Run it on a REPLICA. A monthly export has no business
⭐        competing with checkouts for `work_mem` and shared buffers.
⭐   ④ ⭐ If it runs every day over the same history, it is a
⭐        MATERIALISED VIEW refreshed nightly (Day 188), not a query.
⭐ RESULT: 38 s → ⭐⭐ 6 s with (②), 0.2 s with (④).
```
</details>

# ⭐⭐ Query 9 — "it was fine yesterday"

```sql
-- ⭐ after a backfill inserted 3M rows into `orders` an hour ago
SELECT u.email, o.total_cents FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.country = 'IN' AND u.city = 'Chennai';
-- ⭐ Nested Loop … Index Scan on orders (rows=1 loops=1,240,000)
-- ⭐⭐ Seq Scan on users (cost … rows=61) (actual … rows=66,000)
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: TWO BUGS STACKED, AND THAT IS DELIBERATE.
⭐   ⓐ ⭐⭐ CORRELATED COLUMNS. Chennai is only ever in India, but the
⭐      planner assumes independence and MULTIPLIES the selectivities:
⭐      P(country='IN') × P(city='Chennai') ⇒ estimate 61, truth 66,000.
⭐   ⓑ STALE STATISTICS on `orders` after the backfill.
⭐   ⇒ the 61-row estimate made a nested loop look cheap; it ran 1.24
⭐     million times (Day 192 ①).
⭐ FIX:
⭐   ANALYZE orders;                             -- ⭐ ⓑ
⭐   CREATE STATISTICS s_geo (dependencies, ndistinct)
⭐     ON country, city FROM users;              -- ⭐⭐ ⓐ
⭐   ANALYZE users;
⭐ RESULT: nested loop → hash join, 47 s → ⭐⭐ 210 ms, ⭐⭐ WITH NO INDEX
⭐   ADDED AND NO QUERY CHANGED. ⭐ That is the point of the exercise:
⭐   not every slow query is a missing index, and "add an index" would
⭐   have made this one *worse*.
```
</details>

# ⭐ Query 10 — the endpoint that got slow when nothing changed

```sql
SELECT * FROM orders WHERE tenant_id = 7 ORDER BY created_at DESC LIMIT 50;
-- ⭐ correct index present · returns 50 rows · ⭐⭐ 780 ms
-- ⭐ Buffers: shared hit=52 read=6100
```

<details><summary>⭐⭐ Diagnose first.</summary>

```
⭐⭐ CAUSE: `SELECT *` AND TOAST (Day 186). `notes` is ~2 KB, so it is
⭐   stored out of line — and fetching 50 rows means 50 extra TOAST
⭐   lookups plus decompression, for a column the endpoint DISCARDS.
⭐   ⭐ The index found the rows in microseconds. The 780 ms is all
⭐     detoasting.
⭐ ⭐⭐ AND THE REASON "NOTHING CHANGED": someone added a `notes` column
⭐   three weeks ago. The query text is identical.
⭐ FIX — name your columns. In the ORM:
⭐   ⭐ SQLAlchemy: `select(Order.id, Order.total_cents, ...)` or
⭐     `deferred()` / `load_only()` on the wide column.
⭐   ⭐ Django: `.only("id","total_cents")` or `.defer("notes")`.
⭐ RESULT: 780 ms → ⭐⭐ 1.2 ms. Buffers 6,152 → 54.
⭐ ⭐⭐ THE GENERAL LESSON: "SELECT * is bad style" is a weak argument
⭐   people ignore. "SELECT * costs 780 ms here because of TOAST" is a
⭐   physical fact people act on. ⭐ Learn to state the physical version.
```
</details>

# Part 3 — ⭐⭐ The debrief: five patterns covered all ten

```
⭐⭐ ① THE PREDICATE CANNOT USE AN INDEX      (1, 5)
⭐      function on the column · leading wildcard
⭐      ⇒ ⭐ make it sargable, or index the expression / use trigram
⭐⭐ ② THE INDEX IS WRONG, NOT MISSING        (2, 10)
⭐      wrong column order · fetching columns you discard
⭐      ⇒ ⭐ E-S-R, and name your columns
⭐⭐ ③ THE WORK GROWS WITH SOMETHING IT SHOULD NOT   (3, 4)
⭐      offset with page number · count with table size
⭐      ⇒ ⭐ keyset pagination · delete/approximate/cap the count
⭐⭐ ④ THE ESTIMATE IS A LIE                  (9)
⭐      stale stats · correlated columns
⭐      ⇒ ⭐ ANALYZE, CREATE STATISTICS — no index will fix it
⭐⭐ ⑤ THE SHAPE OF THE QUERY IS WRONG        (6, 7, 8)
⭐      per-row round trips · row multiplication · spilling
⭐      ⇒ ⭐ batch it · aggregate before joining · reduce or relocate
⭐
⭐⭐ AND THE META-LESSON: ***ONLY THREE OF TEN WERE FIXED BY ADDING AN
⭐   INDEX.*** ⭐ "Add an index" is the reflex; it is right less than a
⭐   third of the time, and in Query 9 it would have made things worse.
```

```
⭐⭐ THE DECISION CARD — copy this into your notes and use it for a year:

⭐   Is estimate ≈ actual on every node?
⭐     NO  → deepest bad node → ⭐ ANALYZE · CREATE STATISTICS ·
⭐            SET STATISTICS · expression index                    ⇒ STOP
⭐     YES ↓
⭐   Is `Rows Removed by Filter` large?
⭐     YES → ⭐ is the column bare? → make sargable
⭐           ⭐ is the order E-S-R? → rebuild the index               ⇒ STOP
⭐     NO  ↓
⭐   Is there `temp read/written` or `Batches > 1` or `external merge`?
⭐     YES → ⭐ reduce rows · SET LOCAL work_mem · replica · matview ⇒ STOP
⭐     NO  ↓
⭐   Is `loops` large on an inner node?
⭐     YES → ⭐ N+1 (app) or bad outer estimate (go to the top)      ⇒ STOP
⭐     NO  ↓
⭐   Are buffers huge relative to rows returned?
⭐     YES → ⭐ SELECT * / TOAST / wide rows → name your columns     ⇒ STOP
⭐     NO  → ⭐⭐ the query is doing genuine work. Change the QUESTION:
⭐            precompute, cache, paginate differently, or say no.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Reaching for an index first | Only three of these ten were index problems, and one got worse with an index. |
| Trusting "no Sort node" as proof the index is right | Check `Rows Removed by Filter`. |
| Believing `OFFSET` skips rows | It fetches and discards. Cost grows with page number. |
| Shipping an exact `count(*)` next to a fast page query | MVCC means it's always a scan. Delete, approximate, or cap it. |
| `SUM(DISTINCT)` to fix row multiplication | It collapses genuinely equal values. Aggregate before joining. |
| Looking for N+1 in a slow-query log | Every execution is fast. Sort `pg_stat_statements` by total time. |
| Raising `work_mem` globally for one report | Per node, per connection. `SET LOCAL`, or move it to a replica. |
| Assuming "nothing changed" means the query is innocent | Someone added a wide column three weeks ago and `SELECT *` found it. |
| Arguing `SELECT *` is bad style | Say the physical version: it costs 780 ms here because of TOAST. |
| Optimising without recording before/after | If you can't state the cause in one sentence, you got lucky. |

## Interview questions

**Q: Take me through how you'd approach a slow endpoint.**

> I'd start by refusing to guess. Get the actual SQL — from `pg_stat_statements` sorted by total time
> rather than mean, because the query that dominates is usually a fast one run two million times, and
> the N+1 in particular never appears in a slow-query log. Then `EXPLAIN (ANALYZE, BUFFERS)` on the
> real parameters, ideally the worst tenant rather than a convenient one. Then I work a fixed
> checklist: estimate versus actual on every node first, because if the estimate is wrong everything
> above it is a consequence; then `Rows Removed by Filter` for a missing or wrongly ordered index; then
> temp buffers for a spill; then `loops` for an N+1 or a bad nested loop; then buffers relative to rows
> returned, which catches `SELECT *` on a TOASTed table. If none of those fire, the query is doing
> genuine work and the fix isn't a query change — it's precomputing, caching, or changing what the
> product asks for.

**Q: Deep pagination is slow. What do you do?**

> Move to keyset pagination — remember the last row's sort key instead of an offset, and use a row
> comparison like `(created_at, id) < ($1, $2)` with a matching composite index, including a tiebreaker
> column so no row is skipped or repeated when timestamps collide. `OFFSET` doesn't skip rows, it
> fetches and discards them, so page 2,500 reads fifty thousand rows to return twenty and gets slower
> every day the table grows. Keyset is constant time on every page. The cost has to be stated honestly:
> you lose "jump to page 500", so you get next and previous only — which is fine and even preferable
> for an API or an infinite scroll, and genuinely a regression for an admin table where someone wants
> page 40. There I'd keep offset with a hard page cap rather than pretend.

**Q: The pagination footer needs a total count and it takes three seconds.**

> The first question is whether it needs one, because that count usually exists to render "page 1 of
> 6,213" and nobody uses it — deleting it is a legitimate and often correct fix. If it's needed, the
> reason it's slow is MVCC: a row's visibility depends on the reading transaction, so Postgres can't
> keep a maintained count and `count(*)` is always a scan of everything matching. So the options are an
> approximation from `reltuples` for whole-table counts, or pulling the planner's own row estimate out
> of `EXPLAIN (FORMAT JSON)` for a filtered one, which is accurate enough for "about 12,000 results";
> a capped count using a `LIMIT 1001` subquery to render "1000+" with bounded work; or a maintained
> counter table with a reconciliation job, accepting that any denormalised counter drifts. I'd take
> them in that order.

**Q: A query got slow overnight with no deploy. Where do you look first?**

> Statistics, before anything else. The classic sequence is a bulk load or a backfill that changed the
> data distribution, autoanalyze not having caught up, and a plan that was correct for the old
> distribution — usually a nested loop that now runs hundreds of thousands of times. I'd confirm with
> `EXPLAIN ANALYZE` and `pg_stat_user_tables` for `n_mod_since_analyze` and `last_autoanalyze`. The
> variant worth knowing is correlated columns: filtering on country and city, the planner assumes
> independence and multiplies selectivities, so it estimates dozens of rows and gets tens of thousands.
> No index fixes that — `CREATE STATISTICS` does. That case is a good reminder that "add an index" is
> the wrong reflex: in the version I've worked through, adding one made it worse, and the actual fix
> changed neither the query nor the schema.

**Q: When do you stop optimising?**

> When the plan shows the estimates are honest, filters aren't discarding rows, nothing is spilling,
> and the buffer count is proportional to the rows returned. At that point the query is doing genuine
> work, and further tuning is scraping percentages. The next move isn't a database move, it's a
> product one — precompute it into a materialised view or a read model, cache it with an explicit
> staleness budget, paginate differently, or push back on the requirement. The failure mode I'd watch
> for is the opposite: optimising a query that shouldn't be running at all. Query 4 in this workshop is
> exactly that — three seconds of work to render a page number nobody reads.
