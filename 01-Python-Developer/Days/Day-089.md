# Day 089

**L-089** · Clean code — naming, function size, side effects, and ⭐ **when a comment is a failure**

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: code is read far more often than it is written, so the cost of code is
> the cost of understanding it — and every rule today is a way of lowering that number, not a rule for
> its own sake.**
>
> ⭐ This is the day most easily turned into dogma. **It is not a style guide.** The test at the end of
> every section is the same: *can the next reader answer "what does this do, and can I change it
> safely?"*

# Part 1 — ⭐⭐ Naming

```python
# ⚠️ what is this?
def proc(d, f=False):
    r = []
    for i in d:
        if i[3] > 0 and (f or i[7] == 1):
            r.append(i)
    return r

# ⭐⭐ the same function, renamed. Nothing else changed.
def select_billable_orders(orders, include_cancelled=False):
    billable = []
    for order in orders:
        if order.total > 0 and (include_cancelled or order.is_active):
            billable.append(order)
    return billable
```

```
⭐⭐ THE SECOND VERSION IS NOT "TIDIER". IT IS REVIEWABLE — you can now see that
⭐   `include_cancelled` reads `is_active`, which is at best confusing and quite
⭐   possibly a bug. ⭐⭐ THE FIRST VERSION HID THAT. ⭐ Good names do not decorate
⭐   logic; they EXPOSE it.
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐⭐ **Name length ∝ scope** | ⭐ `i` in a three-line loop is fine; `d` as a module global is not |
| ⭐ Reveal intent, not type | `users`, not `user_list` — ⭐ the type is in the annotation (Day 061) |
| ⭐⭐ **One word per concept** | ⭐⭐ `get_`/`fetch_`/`retrieve_` for the same idea forces the reader to check whether they differ |
| ⭐ Encode cost in the verb | ⭐⭐ `get_user` (cheap) vs `fetch_user` (network) vs `compute_score` (slow) |
| Booleans: `is_`, `has_`, `should_` | ⭐ reads as a sentence at the call site |
| ⭐⭐ **No negative names** | ⭐⭐ `if not is_not_disabled` — ⭐ double negatives are where bugs live |
| Searchable names | ⭐ `MAX_RETRIES = 3`, never a bare `3` in the middle of a line |
| ⭐ Pronounceable | ⭐ you will discuss this code out loud |
| No `l`, `I`, `O` | ⭐ indistinguishable from `1` and `0` |

```
⭐⭐ THE HARDEST AND MOST VALUABLE NAMING RULE: NAME BY *WHAT IT MEANS*, NOT BY
⭐   *WHAT IT IS MADE OF*.
⭐     user_dict          ⇒ ⭐ user            (dict is an implementation detail)
⭐     process_data       ⇒ ⭐⭐ normalise_addresses  ("process" says nothing)
⭐     helper / utils.py  ⇒ ⭐⭐ THE WORST NAMES IN SOFTWARE — a module named
⭐                             `utils` becomes a landfill, because nothing can
⭐                             ever be judged not to belong in it.
⭐     data / info / manager / handler ⇒ ⭐ ask "of what? doing what?"
⭐   ⇒ ⭐⭐ AND THE DIAGNOSTIC: IF YOU CANNOT NAME IT, YOU DO NOT YET UNDERSTAND IT.
⭐        A struggle to name is information — usually that the thing does two jobs.
```

⭐ **Python conventions carry meaning, so use them:** `snake_case` functions, `PascalCase` classes,
`UPPER_CASE` constants, `_private` by convention, `__dunder` only for the data model (Day 031).
⭐⭐ **A leading underscore is a message to a human, not a compiler** — it says *"I may change this
without telling you"*, which is the only access control Python offers and is worth honouring.

# Part 2 — ⭐⭐ Functions

```
⭐⭐ ONE FUNCTION, ONE JOB. THE TEST IS THE NAME: if an honest name needs "AND",
⭐   it is two functions.
⭐     validate_and_save_user()      ⇒ ⭐⭐ two functions
⭐     parse_and_send_report()       ⇒ two functions
⭐   ⇒ ⭐ SIZE IS A SYMPTOM, NOT THE RULE. A 40-line function that does one thing
⭐        is fine; a 6-line function that does three is not.
```

```
⭐⭐ ARGUMENT COUNT IS A DESIGN SIGNAL:
⭐   0-2   ⭐ good
⭐   3     ⭐ acceptable; look at it
⭐   4+    ⭐⭐ SOMETHING IS MISSING — usually an object. If three arguments always
⭐         travel together (start_date, end_date, timezone), ⭐⭐ THEY ARE ONE
⭐         CONCEPT (a DateRange) that has not been named yet. Day 057's dataclass.
⭐   ⇒ ⭐ and past two, make them KEYWORD-ONLY (Day 042):
⭐        def create_user(email, *, is_admin=False, send_welcome=True)
⭐        ⇒ ⭐⭐ call sites become self-documenting and CANNOT silently reorder.
```

```python
# ⚠️⚠️ ⭐⭐ THE FLAG ARGUMENT — two functions wearing a trenchcoat:
def render(doc, minify: bool):
    if minify:
        ...      # ⭐ one whole behaviour
    else:
        ...      # ⭐ a completely different one

# ⭐⭐ DERIVE THE FIX FROM THE BODY: the boolean SPLITS the function in half at the
# top and the halves share nothing. ⇒ they were never one function.
def render(doc): ...
def render_minified(doc): ...
```

⭐⭐ **`render(doc, True)` at the call site is unreadable, and that is the observable symptom.** ⭐ The
exception worth allowing: a flag that genuinely *tweaks* one behaviour rather than choosing between
two — and even then, keyword-only.

```python
# ⭐⭐ GUARD CLAUSES — the single highest-value structural refactor there is:
def charge(order):                              # ⚠️ arrow-shaped
    if order is not None:
        if order.total > 0:
            if order.customer.is_active:
                return gateway.charge(order)
            else: raise InactiveCustomer()
        else: raise EmptyOrder()
    else: raise ValueError("no order")

def charge(order):                              # ⭐⭐ flat. Preconditions first.
    if order is None:          raise ValueError("no order")
    if order.total <= 0:       raise EmptyOrder()
    if not order.customer.is_active: raise InactiveCustomer()
    return gateway.charge(order)                # ⭐ the happy path, unindented
```

⭐⭐ **Nesting depth is the most reliable complexity signal there is**, because each level is a
condition the reader must hold in their head. ⭐ **Return early, and the happy path ends up at
indentation level one** — where it belongs, because it is the point of the function.

⭐ **One level of abstraction per function.** A function that opens a socket, parses JSON *and* applies
a discount rule is mixing altitudes; the reader has to change gear mid-paragraph. ⭐⭐ **The tell is a
function you can only describe by listing its steps.**

# Part 3 — ⭐⭐ Side effects, and why they decide testability

```python
# ⚠️ ⭐⭐ THE NAME PROMISES A QUESTION. THE BODY PERFORMS SURGERY.
def check_password(user, password):
    if verify(user.hash, password):
        session.create(user)          # ⚠️⚠️ a hidden side effect
        user.last_login = now()       # ⚠️ and another
        db.commit()                   # ⚠️ and a third
        return True
    return False
```

```
⭐⭐ COMMAND-QUERY SEPARATION: a function either RETURNS SOMETHING or CHANGES
⭐   SOMETHING. Not both.
⭐   ⇒ ⭐ QUERY   is_valid(), total(), find_user()      ⇒ no observable change
⭐   ⇒ ⭐ COMMAND save(), send(), delete()              ⇒ returns None (or an id)
⭐   ⇒ ⭐⭐ WHY IT MATTERS, CONCRETELY: a query is safe to call twice, safe to call
⭐        in a log line, safe to call in a debugger, and safe to reorder.
⭐        ⭐⭐ A HIDDEN COMMAND MAKES ALL FOUR UNSAFE — and nothing in the signature
⭐        warns you.
```

```
⭐⭐ AND THE CONSEQUENCE THAT DECIDES YOUR TEST SUITE (Day 095 in full):
⭐   PURE FUNCTION      inputs ⇒ output, no I/O, no globals, no clock, no random
⭐     ⇒ ⭐⭐ TESTABLE WITH NO MOCKS AT ALL. Call it, assert on the result.
⭐   IMPURE FUNCTION    reads a database, writes a file, calls now()
⭐     ⇒ ⭐⭐ every test needs setup, patching, or a fixture.
⭐
⭐   ⇒ ⭐⭐ THEREFORE: PUSH I/O TO THE EDGES AND KEEP THE DECISIONS PURE.
⭐        read data → ⭐ decide (pure) → write result
⭐   ⇒ ⭐⭐ "THIS IS HARD TO TEST" IS ALMOST NEVER A TESTING PROBLEM. It is the
⭐        code telling you the decision and the I/O are tangled together.
```

```python
# ⭐⭐ THE MOVE, IN ITS SMALLEST FORM — inject what varies:
def is_expired(token, now: datetime):        # ⭐ pure: `now` is an argument
    return token.expires_at < now

# ⇒ ⭐⭐ testing "expires in one second" needs no freezegun, no patching, no clock.
```

⚠️ ⭐ **Mutating your arguments is the side effect people miss**, because Python passes by sharing
(Day 024): a function that `.sort()`s the list it was given has changed the caller's data. ⭐⭐ **Return
a new object, or name it so the mutation is expected** (`sort_in_place`).

# Part 4 — ⭐ Comments, docstrings, and the honest counterweight

```python
# ⚠️ adds one to i
i += 1

# ⚠️ loop through the users
for user in users:

# ⭐⭐ COMPARE — this one earns its place:
# The gateway rejects amounts over 100k, so we split large refunds into
# chunks. Their support confirmed there is no bulk endpoint (ticket #4412).
for chunk in chunked(refunds, MAX_GATEWAY_AMOUNT):
```

```
⭐⭐ THE RULE: THE CODE SAYS WHAT. ONLY A COMMENT CAN SAY WHY. (Day 085, again —
⭐   the same principle as a commit message, at a smaller scale.)
⭐
⭐ ⭐ THE FIVE COMMENTS THAT EARN THEIR PLACE:
⭐   1. ⭐⭐ WHY — a non-obvious decision, a constraint, a workaround with a ticket
⭐   2. ⭐ WARNING — "this is O(n²); fine at n<1000, do not use it on the full set"
⭐   3. ⭐ CLARIFYING an unavoidably dense thing — a regex, a formula, a bit trick
⭐   4. TODO/FIXME ⭐⭐ WITH A TICKET NUMBER — otherwise it is a wish, not a task
⭐   5. legal / licence headers
⭐
⭐ ⚠️ ⭐⭐ AND THE FAILURES:
⭐   · ⭐⭐ COMMENTED-OUT CODE ⇒ DELETE IT. Git has it (Day 084) and nobody will
⭐     ever dare remove it later because nobody knows if it is still needed.
⭐   · a comment that restates the line ⇒ noise, and it will drift out of date
⭐   · ⭐⭐ A COMMENT THAT IS NOW WRONG ⇒ WORSE THAN NO COMMENT. Code is checked
⭐     by tests; comments are checked by nobody.
⭐   · ⭐ a comment explaining a bad name ⇒ ⭐⭐ FIX THE NAME. Every comment of
⭐     this shape is a rename waiting to happen.
```

```python
def transfer(source: Account, target: Account, amount: Decimal) -> Transfer:
    """Move money between accounts.                    ⭐ WHAT — one line

    Raises:                                            ⭐⭐ THE CONTRACT — Day 060
        InsufficientFunds: if source cannot cover amount.
        AccountFrozen: if either account is frozen.

    The transfer is atomic: either both balances change or neither does.
    """                                                # ⭐ the guarantee a caller relies on
```

⭐⭐ **A docstring is a *contract* — arguments, return, and what it raises. A comment is *rationale*.**
⭐ Not every function needs a docstring; **every public one does**, and the `Raises:` section is the
part people omit and callers most need (Day 060).

```
⭐⭐ THE HONEST COUNTERWEIGHT, AND SAY THIS IN AN INTERVIEW BECAUSE IT SHOWS
⭐   JUDGEMENT RATHER THAN OBEDIENCE:
⭐   "clean code" applied as dogma produces FIFTEEN THREE-LINE FUNCTIONS where one
⭐   thirty-line function was clearer — and now the reader must jump around the
⭐   file to reconstruct a sequence they could previously read top to bottom.
⭐   ⇒ ⭐⭐ EXTRACTION HAS A COST: a name to learn and a jump to make. It is worth
⭐        paying when the extracted piece is REUSED, TESTED SEPARATELY, or NAMED
⭐        SOMETHING THE READER WANTED ANYWAY.
⭐   ⇒ ⭐⭐ THE ONLY METRIC THAT MATTERS: can the next person answer "what does
⭐        this do, and can I change it safely?" Everything today is in service of
⭐        that, and nothing today outranks it.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ `utils.py`, `helpers.py`, `manager` | ⭐⭐ Names that nothing can fail to belong to. Name by domain. |
| ⭐ `user_list`, `data_dict` | ⭐ The type is in the annotation. Name the meaning. |
| Mixing `get`/`fetch`/`retrieve` | ⭐ One word per concept, or readers assume they differ. |
| ⭐ Negative booleans | ⭐⭐ `not is_not_disabled` — double negatives hide bugs. |
| ⭐⭐ **`and` in a function name** | ⭐⭐ Two functions. |
| ⭐ A boolean flag parameter | ⭐⭐ Two functions; the body already splits at the top. |
| Four-plus positional arguments | ⭐ A missing object, and unreadable call sites. Keyword-only. |
| ⭐⭐ **Deep nesting** | ⭐⭐ Guard clauses; happy path at indent level one. |
| A query with a hidden side effect | ⭐⭐ Command-query separation. |
| ⭐ Mutating an argument | ⭐ Python passes by sharing — the caller's data changed. |
| ⭐⭐ "This is hard to test" | ⭐⭐ Not a testing problem. The decision and the I/O are tangled. |
| ⭐ Commented-out code | ⭐⭐ Delete it. Git has it. |
| A comment explaining a bad name | ⭐ Rename it. |
| ⭐ `TODO` with no ticket | ⭐ A wish, not a task. |
| Extracting everything on principle | ⭐⭐ Extraction costs a name and a jump. Charge for it. |

## Interview questions

**Q: What makes a good name?**
> That it reveals intent, so the reader doesn't have to read the body to know what it's for. A few
> concrete rules: length proportional to scope, so `i` in a three-line loop is fine but a
> module-level `d` isn't; name the meaning rather than the type, because the type is in the
> annotation; and one word per concept, because if some functions say `get` and others say `fetch`
> for the same idea, everyone has to check whether the difference is meaningful. The one I'd
> emphasise is that struggling to name something is information — usually it means the thing does two
> jobs, and the naming problem is really a design problem.

**Q: What's wrong with a boolean parameter?**
> Look at the body: the flag almost always splits the function in half at the top, and the halves
> share nothing — so it was never one function. It also makes call sites unreadable, because
> `render(doc, True)` tells the reader nothing without opening the definition. I'd split it into two
> named functions. The exception is a flag that genuinely tweaks one behaviour rather than choosing
> between two, and even then I'd make it keyword-only so the call site still reads.

**Q: Someone says a piece of code is hard to test. What does that usually tell you?**
> That it isn't a testing problem. It's the code saying the decision and the I/O are tangled together
> — the function reads a database, calls `now()`, decides something, and writes a file, so every test
> needs setup and patching to reach the two lines of logic. The fix is to push I/O to the edges: read,
> then decide in a pure function, then write. A pure function needs no mocks at all — you call it and
> assert on the result. That's also why an accumulation of mocks in a test suite is a design signal
> rather than a testing style.

**Q: When should you write a comment?**
> When the code can't say it. The code says what; only a comment can say why — a constraint, a
> workaround with a ticket number, a warning that this is quadratic and fine only at small n, or an
> explanation of something unavoidably dense like a regex. Everything else is a liability, because
> comments are checked by nobody: a comment that's drifted out of date is worse than no comment at
> all. And the specific one I'd always act on is a comment explaining a bad name — that's a rename
> waiting to happen. Commented-out code I just delete; Git has it.

**Q: Is there a downside to "clean code"?**
> Yes, when it's applied as dogma. Taken far enough you get fifteen three-line functions where one
> thirty-line function was clearer, and now the reader jumps around the file to reconstruct a sequence
> they could previously read top to bottom. Extraction has a cost — a name to learn and a jump to make
> — and it's worth paying when the piece is reused, tested separately, or named something the reader
> wanted anyway. The only metric I actually care about is whether the next person can answer "what
> does this do, and can I change it safely", and no rule outranks that.

## Mini task

1. ⭐⭐ Take the worst function in your own code. **Rename everything in it and change nothing else.**
   Read it again. Write down what you now notice.
2. ⭐ Search your projects for `utils`, `helpers`, `data`, `manager`. **Pick one and rename it to
   something domain-specific.**
3. ⭐⭐ Find a function with `and` in its name and split it.
4. ⭐⭐ Find a boolean parameter and split that function in two. **Compare the call sites.**
5. ⭐⭐ Find a function nested three deep and flatten it with guard clauses.
6. ⭐ Find four positional parameters and turn the ones that always travel together into a dataclass
   (Day 057).
7. ⭐⭐ Find a function that both returns a value **and** changes state. Split it, and check whether
   any caller depended on the hidden behaviour.
8. ⭐⭐ Take an impure function and **make it pure by injecting the clock or the fetcher.** Then write
   a test for it with no mocking at all.
9. ⭐ Delete every commented-out block in one project.
10. ⭐ Find a comment that is now wrong. **Note how long it survived.**
11. ⭐⭐ Write a docstring with a real `Raises:` section for a function that has none.
12. ⭐⭐ **The counterweight exercise:** find code you over-extracted and inline it back. Decide
    honestly which version reads better.

## 🎙️ Articulation drill

Record two minutes: **"What does clean code mean to you?"** — a question that rewards a position and
punishes a recitation.

⭐ **Start with the economics, not the rules:** **"code is read far more often than it's written, so
the cost of code is the cost of understanding it. Everything I do under the heading of 'clean' is
trying to lower that number, and if a rule doesn't lower it, I don't follow it."**

⭐⭐ **Then two or three concrete things, each with its mechanism:** *"names that reveal intent, because
a good name means you don't have to read the body — and when I can't name something, that's usually
information that it does two jobs. Guard clauses over nesting, because each level of indentation is a
condition the reader has to hold in their head, and the happy path belongs at indent level one. And
command-query separation: a function either returns something or changes something. A query with a
hidden side effect isn't safe to call twice, or in a log line, or in a debugger, and nothing in the
signature warns you."*

⭐⭐ **Then the one that generalises furthest:** *"the biggest one for me is pushing I/O to the edges.
Read, decide, write — with the decision pure. When someone says code is hard to test, that's almost
never a testing problem; it's the code telling you the decision and the I/O are tangled. A pure
function needs no mocks at all."*

⭐ **Close on the counterweight, because that is what makes it an opinion rather than a creed:** *"and
I'd push back on clean code as dogma. Taken too far you get fifteen three-line functions where one
thirty-line function was clearer, and the reader now jumps around a file to reconstruct something they
could have read top to bottom. Extraction costs a name and a jump. The only test I actually apply is
whether the next person can answer 'what does this do and can I change it safely'."*
