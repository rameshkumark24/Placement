# Day 140

**L-140** · 🔐 **Authentication in FastAPI** — the dependency chain, and ⭐⭐ why auth is not middleware

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: authentication belongs in a dependency and not in middleware, because
> middleware runs before routing — so middleware cannot know which route it is protecting, and
> therefore has to decide with a URL prefix match.** ⭐ Every "we forgot to protect that endpoint"
> incident starts with a prefix match.
>
> ⭐ Days 113–118 built sessions, hashing, JWT, refresh rotation and IDOR **from scratch**. Today is
> the wiring, and every FastAPI-specific trap in it.

# Part 1 — ⭐⭐ Dependency, not middleware

```
⭐⭐ THE ORDER OF EVENTS IN A STARLETTE APP (Day 109):

⭐   request → middleware stack → ⭐⭐ ROUTER MATCHES → dependencies → handler
⭐                    ↑
⭐            ⭐⭐ THE ROUTE IS NOT KNOWN YET

⭐   ⇒ ⭐ MIDDLEWARE-BASED AUTH MUST THEREFORE SAY:
⭐        if not request.url.path.startswith("/public"): require_auth()
⭐
⭐   ⭐⭐ AND THAT IS A DENY-LIST OR AN ALLOW-LIST OF STRINGS. FOUR FAILURES:
⭐    1. ⭐⭐ a new route added under a public prefix is silently unprotected
⭐    2. ⭐ path normalisation: `/public/../admin`, `//admin`, `/ADMIN`,
⭐         trailing slashes, URL-encoded separators — ⭐⭐ every one of these is
⭐         a real reported bypass in some framework's history
⭐    3. ⭐ it cannot express "this route needs the `admin` scope" without
⭐         re-implementing routing inside the middleware
⭐    4. ⭐⭐ it runs on OPTIONS preflights, which carry no credentials
⭐         (Day 110) — so it 401s the preflight and CORS breaks
⭐
⭐   ⇒ ⭐⭐ A DEPENDENCY IS DECLARED ON THE ROUTE. The protection travels with
⭐        the endpoint, shows up in the signature, and appears in OpenAPI.
⭐        ⭐ You cannot add a route "outside" it by accident — you can only
⭐        add one that visibly lacks it, which review and a test can catch.
```

```python
# ⭐⭐ AND THE DEFAULT-DENY VERSION — protection you cannot forget:
router = APIRouter(prefix="/orders", dependencies=[Depends(require_user)])   # ⭐ router-wide

app.include_router(public_router)                                            # ⭐ explicit opt-out
app.include_router(orders_router)
```

> ⭐⭐ **Router-level dependencies give you default-deny with an explicit, greppable exception
> list** — the same shape as Day 118's argument: make the insecure thing require an action.
> ⭐ Middleware still owns what genuinely applies to every request regardless of route: request IDs,
> CORS, error handling, timing.

# Part 2 — ⭐ The chain

```python
# app/api/deps.py
bearer = HTTPBearer(auto_error=False)          # ⭐ auto_error=False → WE shape the 401

def get_token(cred: HTTPAuthorizationCredentials | None = Depends(bearer)) -> str:
    if cred is None:
        raise unauthorised("missing_token")
    return cred.credentials

def get_claims(token: str = Depends(get_token)) -> dict:
    try:
        return jwt.decode(
            token, PUBLIC_KEY,
            algorithms=["RS256"],              # ⭐⭐ A LIST YOU CONTROL — Day 116, alg=none
            audience=settings.jwt_audience,    # ⭐⭐ both of these are verified only
            issuer=settings.jwt_issuer,        # ⭐ if you PASS them. Silence is not safety.
        )
    except jwt.ExpiredSignatureError:
        raise unauthorised("token_expired")    # ⭐⭐ distinct code → client knows to refresh
    except jwt.PyJWTError:
        raise unauthorised("invalid_token")    # ⭐ everything else is one opaque answer

def get_current_user(claims: dict = Depends(get_claims), db: Session = Depends(get_db)) -> User:
    user = db.get(User, int(claims["sub"]))
    if user is None or not user.is_active:     # ⭐⭐ the token outlives the account
        raise unauthorised("invalid_token")    # ⭐ same message — no enumeration (Day 114)
    return user
```

```python
def unauthorised(code: str) -> HTTPException:
    return HTTPException(
        status_code=401,
        detail={"code": code},                                  # ⭐ Day 120's machine code
        headers={"WWW-Authenticate": 'Bearer realm="api"'},     # ⭐⭐ 401 REQUIRES this header
    )
```

```
⭐⭐ FOUR THINGS IN THAT CHAIN THAT ARE ASKED IN INTERVIEWS:

⭐  1. ⭐⭐ 401 vs 403. 401 = "I don't know who you are" (⭐ and MUST carry
⭐       `WWW-Authenticate`, per the RFC — this is the most-skipped header in
⭐       the spec). 403 = "I know exactly who you are, and no."
⭐       ⭐ Getting this wrong makes clients retry-with-refresh on a permission
⭐       failure, which loops.
⭐
⭐  2. ⭐⭐ THE DATABASE LOOKUP IS NOT OPTIONAL, and it is the answer to
⭐       Day 116's "you cannot log out". ⭐ A JWT is valid until it expires;
⭐       the ONLY way a ban, a deletion or a password change takes effect
⭐       before then is to check something server-side. ⭐⭐ If you skip the
⭐       lookup for speed, you have chosen "banned users keep working for 15
⭐       minutes" — ⭐ which is fine if you SAID SO, and a vulnerability if you
⭐       didn't.
⭐
⭐  3. ⭐ `Depends` caches per request (Day 132) — so `get_current_user` on
⭐       three sub-dependencies is ⭐⭐ ONE decode and ONE query, not three.
⭐
⭐  4. ⭐⭐ EVERY FAILURE RETURNS THE SAME BODY except `token_expired`.
⭐       ⭐ "user not found", "user inactive" and "bad signature" must be
⭐       indistinguishable, or you have built an account oracle (Day 114).
```

# Part 3 — ⭐⭐ Cookies or bearer? Decide it once, on the client

```
⭐⭐ THE DECISION IS MADE BY THE CLIENT TYPE, NOT BY TASTE:

⭐  BROWSER, SAME SITE  → ⭐⭐ HttpOnly COOKIE
⭐    ⭐ + JS cannot read it, so XSS cannot steal it outright (Day 127)
⭐    ⭐ + the browser handles expiry, sending, and clearing
⭐    ⭐ − ⭐⭐ SENT AUTOMATICALLY ⇒ CSRF EXISTS (Day 115) ⇒ you MUST add
⭐          `SameSite=Lax` (or `Strict`) and, for state-changing cross-origin
⭐          flows, a CSRF token
⭐
⭐  MOBILE / SERVER-TO-SERVER / THIRD-PARTY API → ⭐⭐ BEARER HEADER
⭐    ⭐ + no ambient authority ⇒ ⭐⭐ CSRF IS STRUCTURALLY IMPOSSIBLE
⭐    ⭐ − the client must store it. In a browser that means JS-readable
⭐          storage ⇒ ⭐⭐ XSS steals it. THAT IS THE WHOLE TRADE.
⭐
⭐   ⇒ ⭐⭐ THE TRADE IN ONE LINE: COOKIES TRADE CSRF-RISK FOR XSS-SAFETY;
⭐        BEARER TOKENS TRADE XSS-RISK FOR CSRF-SAFETY.
⭐   ⇒ ⭐ AND THE ANSWER THAT IMPRESSES: for a browser SPA, cookies —
⭐        because ⭐⭐ CSRF has a complete, mechanical defence and XSS does not.
⭐        ⭐ You can prove SameSite+token is correct; you cannot prove your
⭐        dependency tree has no XSS.
```

```python
response.set_cookie(
    "session", token,
    httponly=True,      # ⭐⭐ JS cannot read it
    secure=True,        # ⭐ HTTPS only
    samesite="lax",     # ⭐⭐ blocks cross-site POST — most of CSRF, for free
    max_age=900,
    path="/",
)
```

> ⭐ **`OAuth2PasswordBearer` does less than its name suggests.** It reads the `Authorization`
> header and declares the security scheme in OpenAPI so the `/docs` **Authorize** button appears.
> ⭐⭐ It performs no OAuth, issues nothing, and validates nothing. Use it for the docs integration;
> never mistake it for an implementation.

# Part 4 — ⭐⭐ The login endpoint, with its four traps

```python
@router.post("/login")
def login(body: LoginIn, response: Response, db: Session = Depends(get_db)):
    user = db.scalar(select(User).where(User.email == body.email))

    # ⭐⭐ TRAP 1 — TIMING. Always hash, even when the user does not exist,
    #    or "no such user" returns in 1 ms and "wrong password" in 300 ms
    #    (Day 114). ⭐ That difference is a user-enumeration oracle.
    hashed = user.password_hash if user else DUMMY_HASH
    ok = verify(body.password, hashed)

    if not user or not ok:
        raise HTTPException(401, detail={"code": "invalid_credentials"})  # ⭐ one message

    # ⭐⭐ TRAP 2 — SESSION FIXATION (Day 113): issue a NEW session id on
    #    login. Never elevate the id the client arrived with.
    # ⭐⭐ TRAP 3 — RATE LIMIT PER ACCOUNT *AND* PER IP (Day 123). Per-IP alone
    #    loses to a botnet; per-account alone lets one IP spray 10k accounts.
    # ⭐⭐ TRAP 4 — `def`, NOT `async def` (Day 134). argon2 burns ~200 ms of
    #    CPU; on the event loop that is 200 ms of TOTAL server stall per login.

    if user.needs_rehash:                 # ⭐ argon2 params change over time
        user.password_hash = hash_pw(body.password); db.commit()

    return issue_tokens(user, response)
```

```
⭐⭐ THE `def` POINT IS THE ONE PEOPLE MISS AND IT IS WORTH THE WHOLE DAY:
⭐   ⭐ login is the single most CPU-expensive endpoint you own — BY DESIGN
⭐     (Day 114: slow hashing is the feature).
⭐   ⭐⭐ Written `async def`, a credential-stuffing attack becomes a DENIAL OF
⭐     SERVICE on your entire API: 20 login attempts per second × 200 ms =
⭐     ⭐ the event loop is saturated and EVERY endpoint stops responding.
⭐   ⇒ ⭐ Plain `def` puts it in the threadpool, and argon2's C
⭐     implementation releases the GIL, so it genuinely parallelises.
⭐   ⇒ ⭐⭐ AND STILL RATE-LIMIT IT — the threadpool is 40 threads, not ∞.
```

# Part 5 — ⭐ Scopes, roles, and the `Security` helper

```python
def require_scopes(*required: str):
    def dep(user: User = Depends(get_current_user)) -> User:
        if not set(required) <= set(user.scopes):
            raise HTTPException(403, detail={"code": "insufficient_scope"})   # ⭐⭐ 403
        return user
    return dep

@router.delete("/orders/{oid}")
def cancel(oid: int, user: User = Depends(require_scopes("orders:write"))):
    ...
```

```
⭐⭐ AND THE PART THAT IS *NOT* SOLVED BY SCOPES — say this unprompted:

⭐   `orders:write` says the CALLER may write orders.
⭐   ⭐⭐ IT DOES NOT SAY THEY MAY WRITE ***THIS*** ORDER.
⭐   ⇒ ⭐⭐ That is Day 118. The object-level check belongs in the QUERY:
⭐        `WHERE id = :oid AND user_id = :me` — ⭐ so a wrong id is a 404, and
⭐        the row that isn't yours is invisible rather than forbidden.
⭐   ⇒ ⭐⭐ SCOPES ARE COARSE AUTHORISATION. IDOR LIVES UNDERNEATH THEM, AND
⭐        NO AMOUNT OF SCOPE CHECKING WILL CATCH IT.
```

```
⭐ FastAPI's `Security(dep, scopes=[...])` + `SecurityScopes` exists for the
⭐ OAuth2 flavour: sub-dependencies can READ the accumulated scope list, and
⭐ OpenAPI documents which scopes each route needs. ⭐⭐ Use it if you are
⭐ genuinely doing OAuth2; ⭐ the closure above is clearer for plain RBAC —
⭐ and "which is clearer here" is a legitimate answer to give in an interview.
```

# Part 6 — ⭐ Testing auth without disabling it

```python
# ⭐⭐ THE OVERRIDE (Day 132) — for the 200 tests that are ABOUT something else
def _fake_user():
    return User(id=1, email="t@example.com", scopes=["orders:write"], is_active=True)

app.dependency_overrides[get_current_user] = _fake_user
```

```
⭐⭐ AND THE RULE THAT MAKES THAT SAFE:

⭐   ⭐ Overriding `get_current_user` in 200 tests is right — those tests are
⭐     about orders, not about JWT.
⭐   ⭐⭐ BUT IT MEANS 200 TESTS NO LONGER PROVE AUTH WORKS AT ALL. ⭐ You have
⭐     replaced the security boundary with a function that always says yes.
⭐   ⇒ ⭐⭐ SO YOU OWE A SMALL SUITE THAT OVERRIDES NOTHING:
⭐        · real login → real token → real protected route → 200
⭐        · no header → 401 ⭐ AND `WWW-Authenticate` present
⭐        · expired token → 401 `token_expired`
⭐        · token signed with the wrong key → 401
⭐        · ⭐⭐ `alg=none` token → 401  (Day 116 — assert your own fix)
⭐        · valid token, another user's object id → ⭐⭐ 404 (Day 118)
⭐        · deactivated user's still-valid token → 401
⭐
⭐ ⭐⭐ PLUS THE TEST THAT CATCHES THE INCIDENT NOBODY PLANS FOR — walk the
⭐   route table and assert every route is either protected or on an explicit
⭐   public allow-list:
⭐
⭐     for route in app.routes:
⭐         assert route.path in PUBLIC or has_auth_dependency(route)
⭐
⭐   ⇒ ⭐ A new unprotected endpoint now fails CI instead of shipping.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Auth in middleware with a path prefix check | ⭐⭐ Middleware runs before routing, so it decides by string matching. Use route/router dependencies. |
| 401 without `WWW-Authenticate` | The RFC requires it on 401. Most-skipped header in the spec. |
| 403 where 401 belongs (or vice versa) | 401 = unknown identity, 403 = known and refused. Wrong code makes clients refresh-loop. |
| `jwt.decode` without `algorithms=`, `audience=`, `issuer=` | Unverified claims are decoration. `alg=none` and token-reuse across services follow. |
| Skipping the DB lookup for speed | Then a ban or password change takes effect only at token expiry. Fine if stated; a hole if not. |
| Different errors for "no such user" and "wrong password" | An enumeration oracle — including via response *time*. Always hash a dummy. |
| `async def` on the login route | 200 ms of argon2 on the event loop; credential stuffing becomes a whole-API DoS. |
| `OAuth2PasswordBearer` assumed to validate | It reads a header and documents a scheme. It validates nothing. |
| Scopes treated as sufficient authorisation | Scopes are coarse. Object-level ownership belongs in the `WHERE` clause. |
| Overriding `get_current_user` everywhere | Then no test proves auth works. Keep a small no-override suite. |

## Interview questions

**Q: Why put authentication in a dependency rather than middleware?**

> Because middleware runs before the router matches, so it doesn't know which endpoint it's
> protecting — it can only decide from the raw path, which means a prefix allow-list. That fails in
> four ways: a new route added under a public prefix is silently unprotected; path normalisation
> tricks like double slashes or encoded traversal can dodge the match; it can't express per-route
> scope requirements without reimplementing routing; and it runs on CORS preflights, which carry no
> credentials, so it 401s the OPTIONS and breaks the browser. A dependency is declared on the route,
> so protection travels with the endpoint and shows up in OpenAPI. I put it on the router for
> default-deny, with an explicit, greppable public list, and a test that walks `app.routes` and
> asserts every route is either protected or on that list.

**Q: Cookie or `Authorization` header?**

> Cookies trade CSRF risk for XSS safety; bearer tokens trade XSS risk for CSRF safety. With an
> HttpOnly cookie, JavaScript can't read the credential, so an XSS can act as the user during the
> page's life but can't exfiltrate a token for later — but the browser attaches it automatically,
> which is the definition of CSRF. A bearer token has no ambient authority so CSRF is structurally
> impossible, but in a browser it has to live somewhere JavaScript can reach, so XSS steals it
> outright. For a browser SPA I choose cookies with `SameSite=Lax`, `HttpOnly`, `Secure` — because
> CSRF has a complete mechanical defence I can prove correct, and XSS doesn't. For mobile or
> service-to-service, bearer.

**Q: Should `get_current_user` hit the database?**

> Yes, unless you've explicitly accepted the alternative. A JWT is valid until it expires, so if you
> trust the claims alone, a banned user, a deleted user, or a user who just changed their password
> after a breach keeps working until expiry. That's a legitimate design choice with a short TTL —
> but it must be a stated choice, not an accident. The lookup is also nearly free in practice
> because `Depends` caches per request, so three dependencies needing the user cost one query.

**Q: Someone writes the login endpoint as `async def`. What do you say?**

> That they've just built a denial-of-service switch. Password hashing is deliberately expensive —
> argon2 at ~200 ms is the security feature. On the event loop, that's 200 ms during which *no*
> request on that worker progresses, including health checks. Twenty login attempts a second, which
> is a modest credential-stuffing run, saturates the loop and takes the whole API down. Plain `def`
> sends it to the threadpool, and argon2's C code releases the GIL so it actually parallelises. And
> it still needs rate limiting per account *and* per IP, because the threadpool is 40 threads, not
> infinite.

**Q: You have `orders:write` scope checking. Is authorisation done?**

> No — that's coarse authorisation. It says this caller may write orders; it says nothing about
> whether they may write *this* order. Object-level authorisation belongs in the query, as
> `WHERE id = :oid AND user_id = :me`, so a row that isn't yours is invisible and returns 404 rather
> than 403 — which also avoids confirming the object exists. Scopes and ownership are two different
> checks, and no amount of scope checking catches an IDOR.

## 🎙️ Articulation drill

**Two minutes: "Design authentication for our API."**

Lead with the structural claim — a dependency, not middleware, and say why in terms of ordering.
Then walk the chain: extract, verify with an explicit algorithm list and audience and issuer, look
up the user so a ban takes effect immediately, and return one indistinguishable failure except
expiry. State the cookie/bearer trade as a trade and then commit to an answer with a reason. Name
`def` on the login route and why. Finish on the two things people forget: the route-table test that
makes an unprotected endpoint fail CI, and the fact that **scopes are not ownership** — the object
check lives in the `WHERE` clause.
