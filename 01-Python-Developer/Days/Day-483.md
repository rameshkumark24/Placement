# Day 483 💬

**P-483** · 💬 **System design round 3 — chat** — ⭐⭐ A is on server 3, B is on server 17

**Time:** 3 hrs · **Mode:** MOCK + SCORED

> ⭐⭐ **The sentence to own: every other system you have designed is stateless behind a load balancer,
> and chat is not — the connection *is* the state, it lives on one specific machine, and the entire
> design is answering how a message reaches the machine holding the other end.**

---

# Part 1 — ⭐⭐ Why this round is different

```
⭐ ***IN A NORMAL SERVICE:*** ⭐ any pod can serve any request.
⭐   ⭐ Scaling is adding pods. ⭐ Failure is removing one.
⭐   ⭐ ⭐⭐ THE LOAD BALANCER OWES YOU NOTHING BEYOND ROUTING.

⭐ ***IN CHAT:*** ⭐ Alice holds an open WebSocket to ***server
⭐   3***. ⭐ That is not a request — ⭐⭐ IT IS A LONG-LIVED,
⭐   BIDIRECTIONAL, ***STATEFUL*** ATTACHMENT TO ONE MACHINE.
⭐   ⭐ Bob is on ***server 17***.
⭐   ⭐ ⭐⭐ WHEN BOB SENDS TO ALICE, SERVER 17 MUST GET THE
⭐     MESSAGE TO SERVER 3. ⭐ There is no load balancer move
⭐     that solves this.

⭐ ⇒ ***THREE CONSEQUENCES THAT SHAPE EVERYTHING:***
⭐   ⭐ ① ⭐⭐ YOU NEED A ***REGISTRY***: WHO IS ON WHICH SERVER?
⭐     ⭐ (Part 2)
⭐   ⭐ ② ⭐⭐ YOU NEED ***INTER-SERVER ROUTING***. ⭐ (Part 3)
⭐   ⭐ ③ ⭐⭐ A DEPLOY DISCONNECTS EVERY USER ON THAT SERVER —
⭐     ⭐ so reconnection is a first-class flow, not an error
⭐     path. ⭐⭐ THIS IS WHY "WHAT HAPPENS ON DEPLOY?" IS A REAL
⭐     QUESTION HERE AND NOT PEDANTRY.

⭐ ***AND THE CAPACITY NUMBER YOU WILL BE ASKED FOR:***
⭐   ⭐ a tuned box holds ⭐⭐ ~50,000–100,000 CONCURRENT
⭐     WEBSOCKETS ⭐ (file descriptors, ~10–40 KB of kernel and
⭐     app memory each).
⭐   ⭐ ⇒ 50 million concurrent users ⇒ ⭐⭐ ~500–1,000 GATEWAY
⭐     SERVERS. ⭐ Say that arithmetic; it makes the registry's
⭐     size concrete — ⭐⭐ 50M ENTRIES, WHICH IS A FEW GIGABYTES
⭐     IN REDIS AND ***NOT*** A PROBLEM.
```

# Part 2 — The connection registry

```
⭐ ***THE DATA:*** ⭐ `user_id → {server_id, session_id,
⭐   connected_at}` ⭐ in Redis.
⭐   ⭐ ⭐⭐ A USER MAY HAVE ***SEVERAL*** — phone, laptop, tablet.
⭐     ⭐ So it is a set per user, not a single value. ⭐⭐ MISSING
⭐     THIS IS THE MOST COMMON MODELLING ERROR IN THE ROUND.

⭐ ***THE HARD PART IS NOT WRITING IT — IT IS KEEPING IT
⭐   TRUE:***
⭐   ⭐ ⭐⭐ A SERVER CRASHES. ⭐ It cannot clean up after itself.
⭐     ⭐ Every user it held is now registered to a dead machine,
⭐     ⭐⭐ AND MESSAGES ROUTE INTO A VOID WITH NO ERROR.
⭐   ⭐ ⇒ ⭐⭐ ***TTL PLUS HEARTBEAT.*** ⭐ Entries expire in ~60s;
⭐     each gateway refreshes its own every ~20s.
⭐     ⭐ ⭐⭐ A DEAD SERVER'S ENTRIES SIMPLY EXPIRE. ⭐ No cleanup
⭐       job, no crash handler, and correctness does not depend
⭐       on the dying process doing anything.
⭐   ⭐ ⭐⭐ THAT IS A ***LEASE*** (D411), ⭐ and naming it is the
⭐     signal.

⭐ ***THE STALE-ENTRY WINDOW IS REAL AND YOU MUST OWN IT:***
⭐   ⭐ for up to 60 seconds, the registry says Alice is on a
⭐     server that is gone. ⭐⭐ MESSAGES SENT IN THAT WINDOW MUST
⭐     NOT VANISH.
⭐   ⭐ ⇒ ⭐⭐ THE MESSAGE IS ***PERSISTED FIRST***, ALWAYS, ⭐ and
⭐     delivery is an optimisation on top (Part 4). ⭐⭐ IF ROUTING
⭐     FAILS, THE MESSAGE IS STILL IN THE DATABASE AND ARRIVES ON
⭐     RECONNECT.

⭐ ***THE ALTERNATIVE WORTH MENTIONING AND REJECTING:***
⭐   ⭐ ⭐⭐ CONSISTENT HASHING — "USER X ALWAYS CONNECTS TO SERVER
⭐     hash(X) % N". ⭐ No registry at all.
⭐   ⭐ ❌ ⭐⭐ BUT REBALANCING ON DEPLOY REASSIGNS A CHUNK OF
⭐     USERS AND FORCES MASS RECONNECTION, ⭐ and you lose the
⭐     ability to route a user to a nearby region.
⭐   ⭐ ⇒ ⭐⭐ A REGISTRY IS MORE MOVING PARTS AND FAR MORE
⭐     OPERATIONALLY FORGIVING. ⭐ Say both sides.
```

# Part 3 — ⭐⭐ Routing between servers

```
⭐ ***OPTION A — DIRECT SERVER-TO-SERVER.***
⭐   ⭐ 17 looks up Alice, finds server 3, opens a connection,
⭐     sends.
⭐   ⭐ ✅ lowest latency.
⭐   ⭐ ❌ ⭐⭐ N² CONNECTIONS BETWEEN 1,000 SERVERS, ⭐ and every
⭐     gateway must handle every other gateway's failure.
⭐     ⭐⭐ OPERATIONALLY UNPLEASANT AT SCALE.

⭐ ***OPTION B — A MESSAGE BUS. ⭐⭐ THE STANDARD ANSWER.***
⭐   ⭐ ⭐⭐ EACH GATEWAY SUBSCRIBES TO ***ITS OWN TOPIC***:
⭐     `gateway.17`.
⭐   ⭐ Server 17 looks up Alice → server 3 → publishes to
⭐     `gateway.3`. ⭐ Server 3 pushes down the socket.
⭐   ⭐ ✅ ⭐⭐ NO N², ⭐ gateways are decoupled, ⭐ a dead gateway's
⭐     topic just drains.
⭐   ⭐ ❌ one extra hop (~1–5 ms) and a bus to operate.
⭐   ⭐ ⭐⭐ THE KEY DESIGN POINT: ⭐ topic per ***gateway***, not
⭐     per user. ⭐⭐ FIFTY MILLION TOPICS WOULD DESTROY ANY
⭐     BROKER; ⭐ a thousand is trivial.

⭐ ***AND THE THIRD OPTION PEOPLE FORGET:***
⭐   ⭐ ⭐⭐ IF BOTH USERS HAPPEN TO BE ON THE SAME GATEWAY, SKIP
⭐     EVERYTHING AND WRITE DIRECTLY TO THE SOCKET. ⭐ Cheap,
⭐     obvious, and worth one line in the design.

⭐ ***THE FULL SEND PATH, IN ORDER — AND THE ORDER IS THE
⭐   DESIGN:***
⭐   ⭐ ① ⭐⭐ PERSIST THE MESSAGE ⭐ (assign `conversation_seq`)
⭐   ⭐ ② ack the ***sender*** — ⭐⭐ "SENT" MEANS "DURABLE", NOT
⭐     "DELIVERED"
⭐   ⭐ ③ look up recipients in the registry
⭐   ⭐ ④ publish to each recipient's gateway topic
⭐   ⭐ ⑤ ⭐⭐ IF NO ACTIVE CONNECTION → PUSH NOTIFICATION
⭐   ⭐ ⭐⭐ PERSISTING ***BEFORE*** ACKING IS THE WHOLE
⭐     RELIABILITY STORY. ⭐ Everything after step ① is best-
⭐     effort, and that is fine ***because*** step ① happened.
```

# Part 4 — ⭐⭐ Ordering and delivery, precisely

```
⭐ ***ORDERING — AND THE ANSWER IS NOT TIMESTAMPS.***
⭐   ⭐ ⭐⭐ CLIENT CLOCKS ARE WRONG, SKEWED AND SOMETIMES
⭐     DELIBERATELY FALSE. ⭐ Server clocks disagree across
⭐     machines (D409).
⭐   ⭐ ⇒ ⭐⭐ A MONOTONIC ***PER-CONVERSATION*** SEQUENCE NUMBER,
⭐     ASSIGNED AT PERSIST TIME BY ONE AUTHORITY.
⭐   ⭐ ⭐⭐ AND NOTE THE SCOPE: ***PER CONVERSATION, NOT
⭐     GLOBAL.*** ⭐ A global sequence is a single point of
⭐     contention and nobody needs it — ⭐⭐ ORDERING IS ALWAYS
⭐     PER-SOMETHING (STAGE 12'S SHAPE).
⭐   ⭐ ⭐ The client sorts by sequence and can detect a gap:
⭐     ⭐⭐ "I HAVE 41 AND 43" MEANS FETCH 42, ⭐ which turns a
⭐     lost message into a self-healing condition.

⭐ ***DELIVERY SEMANTICS — THREE ACKS, THREE MEANINGS:***
⭐   ⭐ ⭐⭐ ***SENT*** ⭐ = persisted on the server. ⭐ One tick.
⭐   ⭐ ⭐⭐ ***DELIVERED*** ⭐ = the recipient's device acked. ⭐ Two
⭐     ticks.
⭐   ⭐ ⭐⭐ ***READ*** ⭐ = the recipient opened it. ⭐ Blue ticks.
⭐   ⭐ ⭐⭐ EACH IS A SEPARATE ROUND TRIP AND A SEPARATE WRITE —
⭐     ⭐ read receipts for a busy group chat can generate more
⭐     traffic than the messages themselves, ⭐⭐ WHICH IS WORTH
⭐     SAYING BECAUSE IT IS COUNTERINTUITIVE AND TRUE.

⭐ ***THE GUARANTEE, HONESTLY:*** ⭐⭐ AT-LEAST-ONCE.
⭐   ⭐ The client acks; ⭐ if the ack is lost, the server redelivers.
⭐   ⭐ ⇒ ⭐⭐ THE CLIENT DEDUPLICATES BY MESSAGE ID. ⭐ You cannot
⭐     have exactly-once across a network, ⭐⭐ SO YOU MAKE
⭐     DUPLICATES INVISIBLE (D444/478).

⭐ ***OFFLINE:*** ⭐ messages are already persisted, so "offline
⭐   delivery" is just ⭐⭐ `WHERE conversation_seq > :last_seen`
⭐   ON RECONNECT. ⭐ No separate queue per user, no separate
⭐   mechanism — ⭐⭐ WHICH IS THE PAYOFF FOR PERSISTING FIRST.
```

# Part 5 — Groups, presence and the deploy

```
⭐ ***GROUP CHAT IS FAN-OUT AGAIN*** (Day 482):
⭐   ⭐ small groups (< 500) ⇒ ⭐ resolve members, route to each.
⭐   ⭐ ⭐⭐ LARGE GROUPS / CHANNELS (100,000 MEMBERS) ⇒ ⭐ that is
⭐     broadcast, not chat. ⭐⭐ ONE WRITE, AND CLIENTS PULL ON
⭐     RECONNECT — ⭐ the same push/pull hybrid, same reasoning.

⭐ ⭐⭐ ***PRESENCE IS THE MOST EXPENSIVE FEATURE AND NOBODY
⭐   BUDGETS IT.***
⭐   ⭐ "Alice is online" must reach everyone who can see her.
⭐   ⭐ ⭐⭐ A USER WITH 1,000 CONTACTS GENERATES 1,000 PUSHES ON
⭐     EVERY CONNECT ***AND*** EVERY DISCONNECT — ⭐ and mobile
⭐     clients connect and disconnect constantly.
⭐   ⭐ ⇒ ⭐⭐ SUBSCRIBE-ON-DEMAND: ⭐ only push presence for
⭐     conversations the user currently has ***open***. ⭐ Cuts it
⭐     by orders of magnitude.
⭐   ⭐ ⇒ ⭐ debounce — a 30-second grace before "offline", ⭐⭐ SO A
⭐     TUNNEL DOES NOT FLAP THE ENTIRE CONTACT GRAPH.

⭐ ***AND THE QUESTION THAT SEPARATES PEOPLE: "WHAT HAPPENS ON
⭐   DEPLOY?"***
⭐   ⭐ ⭐⭐ EVERY CONNECTION ON THAT GATEWAY DROPS. ⭐ 50,000 users
⭐     reconnect at once — ⭐⭐ AND IF THEY ALL RECONNECT
⭐     IMMEDIATELY, THAT IS A SELF-INFLICTED THUNDERING HERD ON
⭐     YOUR AUTH SERVICE AND YOUR REGISTRY.
⭐   ⭐ ⇒ ⭐⭐ CLIENT-SIDE EXPONENTIAL BACKOFF ***WITH JITTER*** ⭐ —
⭐     the single most important line of client code in the
⭐     system.
⭐   ⭐ ⇒ ⭐⭐ DRAIN RATHER THAN KILL: ⭐ stop accepting new
⭐     connections, send a "please reconnect" frame, let clients
⭐     move gradually.
⭐   ⭐ ⇒ ⭐ roll one gateway at a time, ⭐⭐ AND NOTE THAT WITH
⭐     1,000 GATEWAYS A FULL DEPLOY IS THEREFORE MEASURED IN
⭐     HOURS — ⭐ which is a real operational consequence of this
⭐     architecture and worth stating.
```

# 💬 Interview

**1. "Design a chat system."**

⭐ The thing that makes this different from everything else is that the connection is state, and it lives
on one specific machine. ⭐⭐ Alice holds a WebSocket to server 3, Bob to server 17, and when Bob sends to
Alice, server 17 has to get that message to server 3 — there's no load balancer configuration that solves
it. ⭐ So three things fall out immediately: I need a registry of who's on which server, I need routing
between servers, and reconnection has to be a first-class flow rather than an error path, because a
deploy disconnects everyone on that box. ⭐⭐ On capacity, a tuned server holds fifty to a hundred
thousand concurrent sockets, so fifty million users is five hundred to a thousand gateways.

**2. "How do you track who's connected where?"**

⭐ Redis, mapping user to a *set* of connections — server, session, connected-at — because one user has a
phone, a laptop and a tablet, and modelling it as a single value is the most common error here. ⭐⭐ The
hard part isn't writing it, it's keeping it true: if a server crashes it can't clean up after itself, so
every user it held is registered to a dead machine and messages route into a void with no error.
⭐ So entries carry a TTL of about sixty seconds and each gateway heartbeats its own every twenty.
⭐⭐ A dead server's entries just expire — no cleanup job, and correctness doesn't depend on a dying
process doing anything. ⭐ That's a lease.

**3. "So messages sent during that stale window are lost?"**

⭐ No, and that's why the send order matters more than the routing. ⭐⭐ The message is persisted first,
always, with a sequence number assigned — then the sender is acked, and only then do I try to route it.
⭐ "Sent" means durable, not delivered. ⭐⭐ So everything after persistence is best-effort, and that's
acceptable *because* persistence happened: if routing fails or the registry is stale, the message is
still in the database and arrives on reconnect. ⭐ It also means offline delivery isn't a separate
mechanism — it's `WHERE conversation_seq > last_seen`, which is the real payoff for persisting first.

**4. "How does server 17 reach server 3?"**

⭐ Through a bus, with a topic per gateway. ⭐⭐ Each gateway subscribes to `gateway.{id}`, so server 17
looks up Alice, finds server 3, publishes to `gateway.3`, and server 3 pushes down the socket. ⭐ The
alternative is direct server-to-server, which has lower latency and gives you N² connections between a
thousand gateways plus every gateway handling every other's failure. ⭐⭐ The design point worth stating
is topic per *gateway*, not per user — fifty million topics would destroy any broker, a thousand is
trivial. ⭐ And if both users happen to be on the same gateway, skip all of it and write straight to the
socket.

**5. "How do you order messages?"**

⭐ Not by timestamp. ⭐⭐ Client clocks are wrong, skewed, and sometimes deliberately false; server clocks
disagree across machines. ⭐ So a monotonic sequence number per conversation, assigned at persist time by
one authority. ⭐⭐ Per conversation, not global — a global sequence is a single point of contention and
nobody needs it, because ordering is always per-something. ⭐ The nice property is that the client can
detect gaps: if it has 41 and 43, it fetches 42. ⭐⭐ That turns a lost message from a silent failure into
a self-healing condition.

**6. "What's the most expensive feature?"**

⭐ Presence, and almost nobody budgets it. ⭐⭐ "Alice is online" has to reach everyone who can see her, so
a user with a thousand contacts generates a thousand pushes on every connect *and* every disconnect —
and mobile clients connect and disconnect constantly as they move between cells. ⭐ So: subscribe on
demand, pushing presence only for conversations the user currently has open, which cuts it by orders of
magnitude. ⭐⭐ And debounce with a thirty-second grace before showing offline, so someone going through
a tunnel doesn't flap their entire contact graph. ⭐ Read receipts have the same shape — in a busy group
chat they can generate more traffic than the messages do.

**7. "What happens when you deploy?"**

⭐ Every connection on that gateway drops — fifty thousand users at once. ⭐⭐ And if they all reconnect
immediately that's a self-inflicted thundering herd on my auth service and my registry, which is how a
routine deploy becomes an outage. ⭐ So client-side exponential backoff with jitter is arguably the most
important line of client code in the system. ⭐⭐ On the server, drain rather than kill: stop accepting
new connections, send a "please reconnect" frame, let clients move gradually. ⭐ Roll one gateway at a
time — ⭐⭐ and the honest consequence is that with a thousand gateways a full deploy is measured in
hours, which is a real cost of this architecture and worth saying out loud rather than discovering.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "what makes chat harder than a normal service?"**

Start with the structural difference. **"Every other system I've designed is stateless behind a load
balancer — any pod serves any request, scaling is adding pods, failure is removing one. Chat isn't. The
connection is state, and it lives on one specific machine. Alice holds a WebSocket to server three, Bob
to server seventeen, and when Bob sends to Alice, server seventeen has to reach server three. There's no
load balancer setting that solves that."**

Then the three things that fall out. **"So I need a registry of who's on which server, routing between
servers, and reconnection as a first-class flow — because a deploy disconnects everyone on that box, and
that's a normal Tuesday rather than an incident. Capacity-wise, a tuned server holds fifty to a hundred
thousand sockets, so fifty million concurrent users is five hundred to a thousand gateways, and the
registry is fifty million entries, which is a few gigabytes in Redis and not a problem."**

Then the design decision that makes everything else survivable. **"The registry's hard part isn't writing
it, it's keeping it true — a crashed server can't clean up after itself, so its users are registered to a
dead machine and messages route into a void with no error. TTL plus heartbeat fixes that: entries expire
in sixty seconds, gateways refresh every twenty, and correctness doesn't depend on a dying process doing
anything. That's a lease. But it leaves a stale window, and I handle that by ordering the send path
correctly: persist the message first with a sequence number, then ack the sender, then route. 'Sent'
means durable, not delivered. Everything after persistence is best-effort, and that's fine *because*
persistence happened — a message that fails to route is still in the database and arrives on reconnect.
Offline delivery is then just a query, not a separate queue."**

Close on the thing that only comes from imagining operating it. **"Two costs I'd raise before being
asked. Presence is the most expensive feature in the system — a user with a thousand contacts generates a
thousand pushes on every connect and disconnect, and mobile clients do that constantly, so it's
subscribe-on-demand plus a thirty-second debounce. And deploys: fifty thousand users dropping at once
will thundering-herd my auth service unless clients back off with jitter. Rolling one gateway at a time
with a thousand gateways means a full deploy takes hours, which is a real consequence of choosing this
architecture."**
