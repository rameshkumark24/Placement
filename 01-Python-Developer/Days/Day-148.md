# Day 148

**L-148** · **Distributed tracing** — spans, context propagation, ⭐⭐ and the question logs and metrics cannot answer

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a trace is the only telemetry that preserves *causality* — logs are a
> shuffled list of moments and metrics are a shape over time, but a trace records what caused what,
> and how long the waiting was rather than the working.**
>
> ⭐ Day 147 told you *something* is slow. ⭐⭐ Today tells you *where*, without adding a print
> statement to nine services and redeploying them.

# Part 1 — ⭐ The model: three ids and a tree

```
⭐⭐ THE VOCABULARY, WHICH IS THE WHOLE DATA MODEL:

⭐   TRACE   = one logical operation end to end. ⭐ ONE trace_id.
⭐   SPAN    = one unit of work inside it. Has: ⭐ span_id, parent_span_id,
⭐             name, start, end, status, attributes, events.
⭐   ⇒ ⭐⭐ parent_span_id IS THE ENTIRE STRUCTURE. Spans form a TREE, and the
⭐        tree IS the call graph.

⭐   trace 7f3a…  ────────────────────────────────────────────── 812 ms
⭐   ├─ POST /checkout                        [====================] 812
⭐   │  ├─ auth.verify_token                  [=]                     4
⭐   │  ├─ db.SELECT cart                     [==]                   11
⭐   │  ├─ http POST payments.example.com     [==============]      620  ⭐⭐
⭐   │  ├─ db.INSERT orders                   [=]                     6
⭐   │  └─ redis.DEL cart:912                 [=]                     1
⭐   │
⭐   ⇒ ⭐⭐ 620 OF 812 ms IS ONE OUTBOUND CALL. ⭐ You did not add a timer, you
⭐        did not guess, and you did not redeploy. ⭐⭐ THAT is the value —
⭐        ATTRIBUTION OF TIME, which neither logs nor metrics can give you
⭐        because neither records containment.

⭐⭐ AND THE SHAPE THAT IS DIAGNOSTIC ON SIGHT — the reason people fall in
⭐   love with tracing:
⭐   ├─ db.SELECT orders     [=]
⭐   ├─ db.SELECT user       [=]   ⭐ ×50, sequential, thin, identical
⭐   ├─ db.SELECT user       [=]
⭐   ⇒ ⭐⭐ A STAIRCASE OF IDENTICAL SPANS IS AN N+1 (Day 136), VISIBLE FROM
⭐        ACROSS THE ROOM. ⭐ The slow-query log cannot show it because every
⭐        query is fast; the trace shows it because it shows the COUNT and the
⭐        SEQUENCE.
```

# Part 2 — ⭐⭐ Propagation: the header that makes it distributed

```
⭐⭐ WITHOUT PROPAGATION YOU HAVE FIVE UNRELATED TRACES INSTEAD OF ONE. The
⭐   mechanism is a single W3C standard header:

⭐   traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
⭐                │  └─ trace-id (16 bytes) ────────┘ └ parent-span ┘  │
⭐                version                                          flags
⭐                                                        ⭐⭐ 01 = SAMPLED
⭐
⭐   ⇒ ⭐⭐ SERVICE A PUTS IT ON THE OUTBOUND REQUEST. SERVICE B READS IT AND
⭐        MAKES ITS SPANS CHILDREN. That is the whole protocol.
⭐   ⇒ ⭐ `tracestate` carries vendor-specific extras. ⭐⭐ The sampling flag
⭐        travelling WITH the request is what makes a trace complete rather
⭐        than half-recorded — see Part 4.

⭐⭐ THE FOUR PLACES PROPAGATION BREAKS, AND YOU WILL MEET ALL OF THEM:
⭐  1. ⭐ AN UNINSTRUMENTED HTTP CLIENT — you used `requests` directly instead
⭐       of the instrumented one. ⭐⭐ The child service starts a NEW trace and
⭐       your tree is silently truncated at the most interesting point.
⭐  2. ⭐⭐ A QUEUE (Day 142). Headers do not cross a broker by themselves —
⭐       ⭐ you must put `traceparent` IN THE MESSAGE BODY and restore it in
⭐       the worker. ⭐⭐ Otherwise every async job is an orphan trace, which
⭐       is exactly where the hard bugs live.
⭐  3. ⭐ A PROXY OR GATEWAY THAT STRIPS UNKNOWN HEADERS. ⭐⭐ Symptom: perfect
⭐       traces locally, broken traces in production. ⭐ Allow-list it.
⭐  4. ⭐ `asyncio.create_task` / a threadpool without context propagation —
⭐       ⭐⭐ the same `ContextVar` mechanism as Day 146, and it fails the same
⭐       way: the span's parent is lost and the child floats to the root.
```

```python
# ⭐⭐ CARRYING CONTEXT THROUGH A QUEUE — the piece everyone omits
from opentelemetry.propagate import inject, extract

def enqueue(payload: dict) -> None:
    carrier: dict[str, str] = {}
    inject(carrier)                                  # ⭐ writes traceparent
    send_task.delay({"data": payload, "otel": carrier})

@celery_app.task
def send_task(msg: dict) -> None:
    ctx = extract(msg["otel"])                       # ⭐⭐ restores the parent
    with tracer.start_as_current_span("send_task", context=ctx):
        ...
```

# Part 3 — ⭐ Instrumenting: auto first, manual for meaning

```bash
pip install opentelemetry-distro opentelemetry-exporter-otlp
opentelemetry-bootstrap -a install          # ⭐ installs matching instrumentors
OTEL_SERVICE_NAME=orders-api \
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4317 \
opentelemetry-instrument uvicorn app.main:app      # ⭐⭐ zero code changes
```

```
⭐⭐ AUTO-INSTRUMENTATION MONKEY-PATCHES THE LIBRARIES AND GIVES YOU, FREE:
⭐   ⭐ a server span per request, with route/method/status
⭐   ⭐ a client span per outbound `httpx`/`requests` call, WITH PROPAGATION
⭐   ⭐ a span per SQLAlchemy statement — ⭐⭐ so the N+1 staircase appears
⭐        without you writing anything
⭐   ⭐ Redis, Celery, boto3
⭐   ⇒ ⭐⭐ START HERE. 80% of the value, one command, no diff to review.

⭐⭐ THEN ADD MANUAL SPANS ONLY WHERE THEY CARRY MEANING:
⭐   ⭐ a business operation whose name you want in the tree
⭐        (`price.recalculate`, `fraud.score`)
⭐   ⭐ ⭐⭐ CPU-BOUND WORK — because otherwise a 400 ms gap between two spans
⭐        is UNEXPLAINED, and unexplained gaps are the most confusing thing in
⭐        a trace. ⭐ A span with no children is what says "this was compute".
⭐   ⇒ ⭐ DO NOT span every function. ⭐⭐ A 400-span trace is unreadable, and
⭐        you have rebuilt a profiler with a network hop (Day 100A).
```

```python
tracer = trace.get_tracer(__name__)

def score(order: Order) -> float:
    with tracer.start_as_current_span("fraud.score") as span:
        span.set_attribute("order.id", order.id)              # ⭐ high cardinality IS OK
        span.set_attribute("order.item_count", len(order.items))
        try:
            result = model.predict(order)
        except Exception as e:
            span.record_exception(e)
            span.set_status(Status(StatusCode.ERROR))          # ⭐⭐ or it looks successful
            raise
        span.set_attribute("fraud.score", result)
        return result
```

```
⭐⭐ THE PROPERTY THAT MAKES TRACES DIFFERENT FROM METRICS, AND IT IS THE
⭐   FIRST THING TO SAY WHEN ASKED TO COMPARE THEM:
⭐   ⭐⭐ SPAN ATTRIBUTES MAY BE HIGH-CARDINALITY. user_id, order_id, sku —
⭐        all fine. ⭐ There is no series explosion (Day 147) because a span is
⭐        an EVENT, not a dimension of a counter.
⭐   ⇒ ⭐⭐ SO THE CARDINALITY YOU WERE FORBIDDEN IN METRICS LIVES HERE.
⭐        ⭐ "Show me the traces for tenant X where duration > 2 s" is exactly
⭐        the query metrics could not answer, and it is native here.
⭐
⭐ ⭐ AND SET `span.set_status(ERROR)` — ⭐⭐ an exception that is recorded but
⭐   not status-flagged leaves the span GREEN in every UI, so your error
⭐   filter misses it entirely.
```

# Part 4 — ⭐⭐ Sampling: the cost decision, and the one that is worth understanding

```
⭐⭐ YOU CANNOT KEEP EVERY TRACE. At 10k rps with 30 spans each, that is
⭐   300,000 spans/sec — ⭐ more data than your application produces in
⭐   business value. ⭐⭐ So you sample, and WHERE you decide is the whole topic.

⭐  ⭐ HEAD SAMPLING — decide at the ROOT, before anything has happened.
⭐     ⭐ e.g. keep 1%. The decision rides in `traceparent`'s flag, so
⭐        ⭐⭐ EVERY SERVICE AGREES AND THE TRACE IS COMPLETE.
⭐     ⭐ + trivial, cheap, no buffering.
⭐     ⭐ − ⭐⭐ YOU KEEP 1% OF ERRORS AND SLOW REQUESTS TOO. You threw away
⭐          99% of the only traces you wanted. ⭐ That is the whole problem.
⭐
⭐  ⭐⭐ TAIL SAMPLING — buffer the WHOLE trace in a collector, decide when it
⭐     COMPLETES, when you know the outcome.
⭐     ⭐ + ⭐⭐ KEEP 100% OF ERRORS, 100% OF SLOW TRACES, 1% OF BORING ONES.
⭐          ⭐ Exactly the distribution you want, for the cost of the boring 1%.
⭐     ⭐ − the collector must HOLD every span until the trace ends ⇒ memory,
⭐          and a decision window that must exceed your slowest request.
⭐     ⇒ ⭐⭐ THIS IS THE ANSWER TO GIVE. "Head sampling for volume control at
⭐          the edge, tail sampling in the collector so we never drop an error."
⭐
⭐  ⭐ AND ALWAYS: sample by TRACE, never by SPAN. ⭐⭐ Half a trace is worse
⭐     than no trace — it shows a gap that looks like latency and is actually
⭐     a missing span, and people chase it for hours.
```

```
⭐⭐ THE COLLECTOR, AND WHY YOU RUN ONE:
⭐   ⭐ your app → OTLP → ⭐ COLLECTOR (sidecar or daemonset) → vendor
⭐   ⭐ + ⭐⭐ THE APP NEVER BLOCKS ON YOUR TELEMETRY VENDOR. ⭐ Without it, a
⭐        slow exporter adds latency to real requests — ⭐⭐ your observability
⭐        becomes an outage cause, which is the worst irony in operations.
⭐   ⭐ + batching, retry, and ⭐ REDACTION of attributes (Day 146's rule
⭐        applies to spans too — ⭐⭐ people put auth headers in span attributes
⭐        constantly)
⭐   ⭐ + swap vendors by changing config, not code
⭐   ⭐ ⭐⭐ AND USE THE BATCH SPAN PROCESSOR, NOT THE SIMPLE ONE: `Simple`
⭐        exports synchronously per span. ⭐ In a hot path that is a network
⭐        round trip per database call.
```

# Part 5 — ⭐⭐ Joining the pillars, and reading a trace

```
⭐⭐ ONE FIELD MAKES THE THREE PILLARS ONE TOOL:

⭐   structlog.contextvars.bind_contextvars(
⭐       trace_id=format(span.get_span_context().trace_id, "032x"),
⭐   )
⭐   ⇒ ⭐⭐ NOW: metric alert → open a slow trace → click the span →
⭐        FILTER LOGS BY trace_id → see exactly what that code logged.
⭐   ⇒ ⭐ Day 146 said `trace_id` was the join key. ⭐⭐ This is the line that
⭐        creates it, and it is three lines of code for the entire workflow.

⭐⭐ HOW TO READ A TRACE — in the order that finds things fastest:
⭐  1. ⭐⭐ LOOK FOR THE WIDEST BAR. Attribution first, always.
⭐  2. ⭐⭐ LOOK FOR GAPS. Unaccounted time between spans = CPU work,
⭐       GIL contention, GC, ⭐ or a blocking call in `async def` (Day 134).
⭐       ⭐⭐ A GAP IS A MISSING SPAN, AND THE MISSING SPAN IS USUALLY THE BUG.
⭐  3. ⭐ LOOK FOR STAIRCASES → N+1 (Day 136).
⭐  4. ⭐⭐ LOOK FOR SEQUENTIAL BARS THAT COULD BE PARALLEL → three independent
⭐       200 ms calls in a row is 600 ms that `asyncio.gather` makes 200
⭐       (Day 069). ⭐ The trace makes the opportunity VISIBLE.
⭐  5. ⭐ COMPARE A FAST TRACE WITH A SLOW ONE — ⭐⭐ the difference between two
⭐       traces of the SAME endpoint is the fastest diagnosis in this toolkit.
⭐
⭐⭐ AND THE HONEST LIMIT: ⭐ A TRACE SHOWS *WHERE* THE TIME WENT, NOT *WHY*.
⭐   ⭐ "620 ms in the payments call" does not say whether the payment
⭐   provider is slow, the network is slow, or you are waiting for a
⭐   connection from an exhausted pool. ⭐⭐ THE POOL CASE IS THE ONE PEOPLE
⭐   MISS: the span looks like a slow dependency and is actually YOUR
⭐   saturation (Day 147's USE). ⭐ Instrument acquire time separately.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| No propagation across a queue | Every background job is an orphan trace — where the hard bugs live. Put `traceparent` in the message. |
| Using an uninstrumented HTTP client | The child service starts a new trace; the tree is silently truncated. |
| A proxy stripping `traceparent` | Perfect locally, broken in production. Allow-list the header. |
| Spanning every function | A 400-span trace is unreadable — you rebuilt a profiler with a network hop. |
| No span around CPU-bound work | An unexplained gap in the trace, which is the most confusing artefact there is. |
| Recording an exception without setting span status | The span stays green and your error filter misses it. |
| Fearing high-cardinality span attributes | Spans are events, not counter dimensions. `user_id` belongs here. |
| Sampling per span | Half a trace shows a gap that looks like latency and isn't. Sample per trace. |
| Head sampling only | You keep 1% of errors — the only traces you wanted. |
| Exporting straight to the vendor from the app | A slow exporter adds latency to real requests; observability becomes an outage cause. |
| `SimpleSpanProcessor` in production | A synchronous network round trip per span. |
| Secrets in span attributes | Same rule as logs — redact at the collector. |
| No `trace_id` in logs | The pillars can't join, and the whole workflow doesn't exist. |
| Reading "slow dependency" off a span without checking pool acquire time | Your own saturation looks exactly like their slowness. |

## Interview questions

**Q: What does a trace tell you that logs and metrics can't?**

> Causality and attribution of time. Metrics give you a shape over time but throw away which request;
> logs give you moments but no containment — a log line can't tell you that these eleven lines
> happened *inside* that outbound call. A trace is a tree, so you can say "812 milliseconds total,
> 620 of them in one call to the payments provider" without adding a timer or redeploying anything.
> And some diagnoses are visual: fifty identical thin sequential spans is an N+1, obvious from across
> the room, and invisible to a slow-query log because every one of those queries is fast.

**Q: How does a trace span services?**

> The W3C `traceparent` header: version, trace id, parent span id, and flags including whether the
> trace is sampled. The caller injects it, the callee extracts it and makes its spans children of the
> parent. The sampling flag travelling with the request is what makes traces complete rather than
> half-recorded. It breaks in four places, and I've hit all of them: an HTTP client that isn't
> instrumented, so the child starts a fresh trace; a message queue, because headers don't cross a
> broker — you have to put the carrier in the message body and restore it in the worker, and if you
> don't, every async job is an orphan trace; a proxy that strips unknown headers, which shows up as
> "works locally, broken in production"; and tasks or threads that don't propagate context.

**Q: Head sampling or tail sampling?**

> Both, at different places. Head sampling decides at the root before anything has happened, so it's
> cheap and every service agrees — but you keep one percent of your errors and slow requests too,
> which is exactly the one percent you wanted to keep. Tail sampling buffers the whole trace in the
> collector and decides when it completes, when you know the outcome: keep a hundred percent of
> errors and slow traces and one percent of the boring ones. The cost is that the collector holds
> spans in memory and needs a decision window longer than your slowest request. Either way I sample
> per trace, never per span — half a trace shows a gap that looks like latency and is actually a
> missing span, and people chase that for hours.

**Q: You told me not to put `user_id` in a metric label. Why is it fine in a span attribute?**

> Because they're different data structures with different cost models. A metric label creates a
> distinct time series that persists and consumes memory forever, so cardinality multiplies. A span
> is an event — one record of one thing that happened — so an attribute is just a field on that
> record. There's no series to explode. That's precisely the division of labour between the pillars:
> metrics gave up cardinality to be cheap and permanent, and traces carry the cardinality metrics
> couldn't. "Show me traces for tenant X where duration exceeded two seconds" is the query metrics
> can't answer and tracing answers natively.

**Q: A span shows 600 ms in a call to another service. What have you learned?**

> Where the time went, not why. Six hundred milliseconds in that span could be the other service
> being slow, the network, or — the one people miss — my own connection pool being exhausted, so most
> of that span is waiting to acquire a connection before the request is even sent. That looks
> identical in the trace and has the opposite fix: their problem versus my saturation. So I
> instrument acquire time as its own span or metric. The next step either way is to compare a fast
> trace and a slow trace of the same endpoint, which is the fastest diagnostic move in this toolkit.

## 🎙️ Articulation drill

**Two minutes: "Walk me through debugging a slow endpoint in production."**

Start at the alert — a symptom-based one on p99 — then say what each pillar contributes and in which
order. Open a slow trace and read it in the order that finds things fastest: widest bar first, then
gaps, then staircases, then sequential-that-could-be-parallel. Say what each shape means. Then click
through to the logs by `trace_id` and explain that one bound field is what makes three tools one
workflow. Close on the two pieces of judgement that show experience: **tail sampling, because head
sampling throws away the errors you wanted**, and the fact that a wide outbound span might be your
own exhausted pool rather than their slow service.
