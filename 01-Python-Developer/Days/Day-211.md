# Day 211 ⭐

**L-211** · 🍃 **Embedding vs referencing** — ⭐⭐ the only schema decision that really matters

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: embed what is bounded and read together; reference what grows or is
> accessed independently. Everything else in MongoDB schema design is a variation on that one
> sentence — and the failure mode is always the same, an array that grows without a bound.**
>
> ⭐ This decision determines your query shapes, your write amplification, your consistency story and
> your sharding options. ⭐⭐ It is also the most expensive one to reverse, because reversing it
> means rewriting every document *and* every query that reads them.

---

# Part 1 — ⭐⭐ The decision, derived from three questions

```
⭐⭐ ASK THESE THREE, IN THIS ORDER. THEY DECIDE ALMOST EVERY CASE.

⭐ ① ⭐⭐ IS IT BOUNDED? Will this collection of children ever exceed a
⭐    few hundred, ever, for the worst customer you can imagine?
⭐    ⭐⭐ UNBOUNDED ⇒ ***REFERENCE.*** No further discussion. This
⭐      question alone settles more cases than the other two combined.
⭐ ② ⭐ IS IT READ TOGETHER? Do you fetch the parent and immediately
⭐    want the children, essentially always?
⭐    ⭐ Yes ⇒ embedding saves a round trip and a join.
⭐    ⭐ No ⇒ embedding makes every parent read carry data nobody wanted.
⭐ ③ ⭐ IS IT ACCESSED OR UPDATED INDEPENDENTLY? Does anything query the
⭐    child on its own, or update it without the parent?
⭐    ⭐⭐ Yes ⇒ REFERENCE. An embedded document has no independent
⭐      identity, cannot be the target of a `$lookup` from elsewhere,
⭐      and cannot be indexed as a first-class entity.

⭐⭐ MONGODB'S OWN TAXONOMY, WHICH IS GENUINELY USEFUL:
⭐   ⭐ ONE-TO-FEW (an address list, ≤ dozens)     ⇒ ⭐⭐ EMBED
⭐   ⭐ ONE-TO-MANY (order line items, ≤ hundreds) ⇒ ⭐ embed, or embed
⭐        a SUBSET and reference the rest
⭐   ⭐ ONE-TO-SQUILLIONS (log lines, messages,    ⇒ ⭐⭐ REFERENCE —
⭐        events, followers)                          ⭐ and put the
⭐        reference on the ***CHILD***, pointing up, so the parent never
⭐        grows at all.
```

# Part 2 — ⭐⭐ The unbounded array: the mistake, in full

```
⭐   { _id: "post:91", title: "…", comments: [ … , … , … ] }
⭐   ⭐ Beautiful for the first thousand posts. ⭐⭐ Then one goes viral.

⭐⭐ WHAT ACTUALLY BREAKS, IN ORDER — and notice how much of it happens
⭐   LONG BEFORE THE 16 MB LIMIT:

⭐  ① ⭐⭐ EVERY `$push` REWRITES THE ENTIRE DOCUMENT. There is no
⭐     partial update of a BSON document, exactly as there is no partial
⭐     update of a jsonb value (Day 198). ⭐⭐ APPENDING COMMENT 10,000
⭐     REWRITES 9,999 COMMENTS.
⭐  ② ⭐ The document outgrows its allocated space and is MOVED, so
⭐     ⭐⭐ EVERY INDEX ENTRY POINTING AT IT MUST BE UPDATED.
⭐  ③ ⭐⭐ EVERY READ OF THE POST CARRIES ALL 40,000 COMMENTS OVER THE
⭐     NETWORK — including the listing page that wanted the title.
⭐     ⭐ Projection helps the network but not the disk read.
⭐  ④ ⭐ "Page 3 of the comments" becomes `$slice` gymnastics, and
⭐     ⭐⭐ sorting an embedded array by anything other than its stored
⭐     order means sorting it in memory, per document, per read.
⭐  ⑤ ⭐ A multikey index on `comments.author` indexes ONE ENTRY PER
⭐     ARRAY ELEMENT — ⭐⭐ so the index for one document has 40,000
⭐     entries, and Day 212's restrictions start biting.
⭐  ⑥ ⭐⭐ AT 16 MB, ***WRITES SIMPLY FAIL***, in production, on your
⭐     most popular content, which is the worst possible correlation.

⭐ ⇒ ⭐⭐ THE RULE, STATED SO IT CANNOT BE MISREAD: ***IF A USER ACTION
⭐   CAN APPEND TO IT, IT IS UNBOUNDED.*** Comments, messages, events,
⭐   audit entries, likes, followers, versions, line items on a
⭐   subscription — ⭐ all unbounded, all referenced.
⭐ ⭐ THE FIX: a `comments` collection with `post_id`, indexed. ⭐⭐ The
⭐   parent stops growing entirely, and "page 3" becomes a normal
⭐   paginated query with a normal index.
```

# Part 3 — ⭐⭐ The six patterns you will actually use

```
⭐⭐ ① THE EXTENDED REFERENCE — reference, plus the fields you always
⭐    need, copied.
⭐    { _id, customer_id: "c:42",
⭐      customer: { name: "Priya", email: "…" } }   ⭐ duplicated
⭐    ⭐ Kills the join for the 95% case; the full customer document is
⭐      one fetch away when you need it.
⭐    ⭐⭐ AND THE CRUCIAL DISTINCTION, WHICH IS DAY 188 EXACTLY:
⭐      ⭐ IS THE COPY A ***CACHE*** OR A ***SNAPSHOT***?
⭐      ⭐⭐ CACHE ("show the current name") ⇒ you now own an
⭐        invalidation job: when the customer renames, you must update
⭐        every order. ⭐ That is a real background process with a real
⭐        failure mode, and people forget to write it.
⭐      ⭐⭐ SNAPSHOT ("the name this invoice was issued to") ⇒ ***YOU
⭐        MUST NOT UPDATE IT.*** It is not stale; it is history.
⭐      ⇒ ⭐⭐ HALF THE "DENORMALISATION CONSISTENCY PROBLEMS" PEOPLE
⭐        DESCRIBE ARE SNAPSHOTS THEY MISTOOK FOR CACHES. ⭐ Decide
⭐        which, per field, and write it in a comment.

⭐⭐ ② THE SUBSET PATTERN — embed the first N, reference the rest.
⭐    { _id, review_count: 8412,
⭐      top_reviews: [ …5 items… ] }        ⭐ the product page
⭐    ⭐ The 95% read is one document; "see all reviews" is a query.
⭐    ⭐⭐ THE COST: a background job maintains `top_reviews`, and
⭐      "top" now needs a definition you can recompute.

⭐⭐ ③ THE BUCKET PATTERN — the time-series answer, and the best idea
⭐    here. Instead of one document per reading:
⭐    { sensor: "s1", hour: "2026-08-19T14",
⭐      count: 3600, sum: 74210,             ⭐ pre-aggregated
⭐      readings: [ {t: 0, v: 21}, … ] }     ⭐⭐ BOUNDED BY THE HOUR
⭐    ⇒ ⭐⭐ 3,600 DOCUMENTS BECOME 1. Index entries drop by 3,600×,
⭐      per-document overhead disappears, and the array is bounded BY
⭐      CONSTRUCTION rather than by hope.
⭐    ⭐ Mongo 5.0's native time-series collections do this for you —
⭐      ⭐⭐ but knowing the pattern is what lets you apply it to
⭐      anything with a natural bucket (a day's chat messages, a
⭐      session's events).

⭐⭐ ④ THE COMPUTED PATTERN — store the answer, not the inputs.
⭐    `order_count`, `total_spend`, `avg_rating` on the parent.
⭐    ⭐⭐ Day 188's maintained counter, with the same obligation: A
⭐      RECONCILIATION JOB THAT RECOMPUTES AND ALERTS ON DRIFT. Every
⭐      denormalised counter drifts.

⭐ ⑤ THE OUTLIER PATTERN — embed for the normal case, and add an
⭐    `has_overflow: true` flag plus a spill collection for the 0.01% of
⭐    documents that break the bound. ⭐⭐ Honest, ugly, and correct when
⭐    99.99% of your data genuinely is bounded and one celebrity account
⭐    is not.

⭐ ⑥ THE SCHEMA VERSIONING PATTERN — Day 210's `schema_version`, used
⭐    to migrate lazily: read v1, write v2, backfill in the background,
⭐    ⭐⭐ and delete the compatibility branch only when the counter of
⭐    v1 documents reaches zero.
```

# Part 4 — ⭐⭐ Duplication, and the update you cannot make atomic

```
⭐⭐ YOU EMBEDDED `customer.name` IN 400,000 ORDERS. THE CUSTOMER RENAMES.

⭐   db.orders.updateMany({customer_id: "c:42"},
⭐                        {$set: {"customer.name": "Priya R"}})
⭐   ⭐⭐ THIS IS NOT ATOMIC ACROSS DOCUMENTS. It is atomic per document.
⭐   ⇒ ⭐ Mid-update, some orders show the old name and some the new.
⭐   ⇒ ⭐⭐ AND IF THE PROCESS DIES HALFWAY, IT ***STAYS*** HALF-DONE,
⭐     with nothing recording that fact.

⭐⭐ THE FOUR RESPONSES, RANKED:
⭐  ① ⭐⭐ ASK WHETHER IT SHOULD BE UPDATED AT ALL. If it is a snapshot
⭐     (Part 3 ①), you are done — ⭐ and this is genuinely the most
⭐     common correct answer.
⭐  ② ⭐ ACCEPT EVENTUAL CONSISTENCY, and make it real: a job with a
⭐     watermark (Day 159), retries, idempotency, and a metric for
⭐     documents still stale. ⭐⭐ "It'll catch up" without a metric is
⭐     not eventual consistency, it is hope.
⭐  ③ ⭐ A MULTI-DOCUMENT TRANSACTION (Day 213) — ⭐⭐ and 400,000
⭐     documents will blow the 60-second transaction limit, so this
⭐     works only for small fan-outs.
⭐  ④ ⭐⭐ DON'T DUPLICATE IT. Reference, and pay one extra lookup on the
⭐     rare screen that needs the live name.
⭐ ⇒ ⭐⭐ THE POINT: ***EMBEDDING TRADES READ SIMPLICITY FOR A WRITE
⭐   FAN-OUT YOU NOW OWN.*** In Postgres the join did this for free and
⭐   you never thought about it. That is the actual cost of the document
⭐   model, and it is invisible until the first rename.
```

# Part 5 — ⭐ Worked example: one order, three ways

```
⭐ THE QUERIES DECIDE, SO WRITE THEM DOWN FIRST:
⭐   Q1 show one order with everything          ⭐ 1,000/min
⭐   Q2 list a customer's orders (id, total, date) ⭐ 500/min
⭐   Q3 revenue by product this month            ⭐ 10/day
⭐   Q4 rename a customer                        ⭐ 2/day
⭐   Q5 change a product's price                 ⭐ 20/day
```

```
⭐ ❌ FULLY EMBEDDED — customer AND full product docs inside the order.
⭐    Q1 ✅ one read · Q2 ❌ carries everything · Q3 ❌ · Q4 ❌ fan-out ·
⭐    Q5 ⭐⭐ ***MUST NOT PROPAGATE*** — historical prices would change.

⭐ ❌ FULLY REFERENCED — order holds only ids.
⭐    Q1 ❌ 1 + N lookups (⭐⭐ the N+1, in a database with no planner to
⭐    help you) · Q4 ✅ · Q5 ✅ · Q3 still a pipeline.

⭐ ✅ ⭐⭐ THE ANSWER — EXTENDED REFERENCE WITH SNAPSHOTS:
⭐    {
⭐      _id, schema_version: 2,
⭐      customer_id: "c:42",                    ⭐ reference (Q4 is free)
⭐      customer_snapshot: { name, email },     ⭐⭐ SNAPSHOT: the invoice
⭐                                                 was issued to this
⭐      shipping_address: { … },                ⭐⭐ SNAPSHOT: where it
⭐                                                 actually went
⭐      items: [ { product_id, name,            ⭐ bounded — an order has
⭐                 unit_price_cents, qty } ],   ⭐⭐ SNAPSHOTS: Day 188
⭐      total_cents, status, created_at
⭐    }
⭐    Q1 ✅ one read · Q2 ✅ with a projection · Q4 ✅ nothing to update
⭐    · Q5 ✅ nothing to update · ⭐ Q3 is an aggregation over orders,
⭐    which at 10/day is fine (⭐⭐ and if it were 10/second it would be
⭐    a maintained rollup collection, not a better schema).

⭐ ⇒ ⭐⭐ NOTICE THAT THE SCHEMA FELL OUT OF THE QUERY LIST PLUS ONE
⭐   DOMAIN QUESTION PER FIELD: "cache or snapshot?" ⭐ That is the
⭐   method. ⭐⭐ And notice the answer is IDENTICAL to the Postgres
⭐   design from Day 188 — because the snapshot rule is about the
⭐   DOMAIN, not the database.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Embedding anything a user action can append to | That's unbounded by definition. Reference it. |
| Thinking the 16 MB limit is the problem | Rewrites, moves, index churn and network cost hit far earlier. |
| `$push` on a large array | It rewrites the whole document every time. |
| Embedding data that's queried independently | An embedded document has no identity and can't be a `$lookup` target. |
| Duplicating a field without deciding cache or snapshot | Half of all "denormalisation consistency problems" are snapshots mistaken for caches. |
| Propagating a price change into historical orders | That's Day 188's bug, in a different database. |
| `updateMany` treated as atomic | It's atomic per document. A crash leaves it half-done with no record. |
| "It'll catch up eventually" with no metric | That's hope, not eventual consistency. |
| A transaction for a 400,000-document fan-out | It will blow the 60-second limit. |
| A maintained counter with no reconciliation job | Every denormalised counter drifts. |
| One document per sensor reading | The bucket pattern turns 3,600 documents into one. |
| Designing the schema before listing the queries | In Mongo the queries *are* the design input. |
| Fully referencing everything | You've rebuilt the N+1 in a database with no planner to rescue you. |

## Interview questions

**Q: How do you decide whether to embed or reference?**

> Three questions in order. Is it bounded — will this ever exceed a few hundred for the worst customer
> I can imagine? If it's unbounded, reference, and that settles more cases than the other two combined.
> Is it read together, essentially always? If not, embedding makes every parent read carry data nobody
> asked for. And is it accessed or updated independently? If so, reference, because an embedded
> document has no independent identity — nothing else can `$lookup` it and it can't be treated as a
> first-class entity. The heuristic I'd give a team is blunter: **if a user action can append to it,
> it's unbounded.** Comments, messages, events, audit entries, likes, followers — all unbounded, all
> referenced, and the reference goes on the child pointing up so the parent never grows at all.

**Q: What actually goes wrong with a large embedded array?**

> Almost all of it happens long before the 16 MB limit, which is what people don't expect. There's no
> partial update of a BSON document, so every `$push` rewrites the entire document — appending comment
> ten thousand rewrites the previous nine thousand nine hundred and ninety-nine. The document outgrows
> its allocation and gets moved, so every index entry pointing at it has to be updated. Every read of
> the parent carries the whole array over the network, including the listing page that only wanted the
> title. Pagination inside an array becomes `$slice` gymnastics and any non-stored sort order means
> sorting in memory per document per read. A multikey index on a field inside the array creates one
> index entry per element. And then at 16 MB writes simply start failing — in production, on your most
> popular content, which is the worst possible correlation. So the limit is really the enforcement
> mechanism for a rule you should already be following.

**Q: You embedded a customer's name in 400,000 orders and they renamed. What now?**

> First I'd ask whether it should be updated at all, and that's genuinely the most common correct
> answer. If the embedded name is the name the invoice was *issued to*, it's a snapshot, not a cache —
> it isn't stale, it's history, and updating it would be the bug. That's the same distinction as an
> order line copying a product's price in a relational schema: a fact about the event rather than a
> fact about the entity. Half the denormalisation consistency problems people describe are snapshots
> they mistook for caches. If it genuinely is a cache — "show the current name" — then `updateMany` is
> atomic per document but not across documents, so a crash halfway leaves it half-done with nothing
> recording that fact. That needs a real background job with a watermark, retries, idempotency and a
> metric for documents still stale, because "it'll catch up" without a metric is hope. A transaction
> won't help at that fan-out — it'll blow the sixty-second limit. And the fourth option is to not
> duplicate it and pay one lookup on the rare screen that needs a live name.

**Q: What's the bucket pattern and why does it matter?**

> Instead of one document per event, you store one document per time bucket with an array of events
> inside it plus pre-aggregated fields — one document per sensor per hour holding thirty-six hundred
> readings, a count and a sum. It turns thirty-six hundred documents into one, so index entries drop
> by the same factor and the per-document overhead disappears. The important property is that the
> array is bounded *by construction* rather than by hope: an hour can only contain an hour's worth of
> readings, so the thing that makes embedded arrays dangerous doesn't apply. Mongo 5.0's native
> time-series collections implement this for you, but knowing the pattern is what lets you apply it
> elsewhere — a day's chat messages, a session's clickstream, anything with a natural bucket. It's the
> best single idea in Mongo schema design.

**Q: How do you approach designing a Mongo schema from scratch?**

> By writing the query list first, with frequencies, because in Mongo the queries are the design input
> rather than something you derive afterwards. Then for each piece of data, the three embed-or-
> reference questions, and for anything duplicated, one domain question per field: is this a cache or a
> snapshot? In the order example that method produces an extended reference — a customer id for the
> live link, plus snapshotted name, address and line-item prices — and the interesting part is that the
> answer is *identical* to the relational design, because the snapshot rule is about the domain, not
> the database. Then I'd apply the patterns where they fit: subset for a product page's top reviews,
> bucket for anything time-series, computed for counters with the reconciliation job that obligation
> implies. And a `schema_version` field, because I'm going to get some of this wrong and I need a way
> to finish a migration.

## 🎙️ Articulation drill

**Two minutes: "How do you design a MongoDB schema?"**

Start with the method rather than a rule: **write the query list with frequencies first, because in
Mongo the queries are the design input.** Then the three questions — bounded, read together,
independently accessed — and the blunt heuristic that if a user action can append to it, it's
unbounded. Spend real time on why that matters, because the reasons are more interesting than the
16 MB limit: **every `$push` rewrites the whole document, the document gets moved so every index entry
follows, and every read carries the array over the network** — all of which hurt long before the limit.
Then the pattern that shows depth: **the extended reference, and the question of whether each copied
field is a cache or a snapshot** — because half of all denormalisation consistency problems are
snapshots people mistook for caches, and a snapshot must never be updated. Close on the honest cost of
the whole model: **embedding trades read simplicity for a write fan-out you now own**, which in Postgres
the join did for free and you never thought about.
