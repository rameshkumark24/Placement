# Day 236 🚫

**P-236** · 🚫 **Authorization is server-side or it doesn't exist** — ⭐⭐ a hidden button is not a permission

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: everything the browser does is a suggestion the user can decline — they
> can edit your JavaScript, flip a variable in the console, or skip your app entirely and call the API
> with curl — so a UI that hides a button has changed what is *convenient*, not what is *permitted*,
> and the only place permission exists is the endpoint.**
>
> Today: the model, ⭐ the four ways the client is bypassed, ⭐⭐ mirroring rules without enforcing
> them, and the leak that is not a button at all.

---

# Part 1 — The model

```
⭐⭐ TWO DIFFERENT JOBS THAT SOUND LIKE ONE

⭐   THE CLIENT'S JOB ⇒ ⭐ SHOW THE USER WHAT IS RELEVANT.
⭐     Hiding a Delete button they cannot use is GOOD UX.
⭐     ⭐⭐ IT IS NOT SECURITY AND MUST NEVER BE COUNTED AS ANY.

⭐   THE SERVER'S JOB ⇒ ⭐⭐ DECIDE WHETHER THIS ACTOR MAY DO THIS
⭐     THING TO THIS RESOURCE. ⭐ On EVERY request. No exceptions.

⭐   ⇒ ⭐⭐ THE TEST: IF I DELETE YOUR ENTIRE FRONTEND AND CALL THE
⭐     API WITH curl, IS ANYTHING DIFFERENT? IF YES, YOUR
⭐     AUTHORIZATION IS IN THE WRONG PLACE.
```

| ⭐ The four bypasses, none of which are exotic | |
|---|---|
| **The console** | ⭐ `document.querySelector("[hidden]").click()`, or set `isAdmin = true` in React DevTools |
| **The API directly** | ⭐⭐ `curl -X DELETE /api/orders/7 -H "Cookie: ..."` — **your UI is not involved at all** |
| **A modified bundle** | ⭐ Save the JS, edit the check, serve it locally |
| **A stale client** | ⭐⭐ Yesterday's bundle, with yesterday's rules, still running in an open tab. **Not even an attack** — just a user who has not refreshed. |

# Part 2 — ⭐⭐ Mirror the rules, do not implement them

```jsx
// ❌ THE CLIENT DECIDING — brittle, duplicated, and wrong the moment
//    the server's rules change
{user.role === "admin" && <DeleteButton id={o.id} />}

// ✅ THE SERVER DECIDING, THE CLIENT REFLECTING
{o.permissions.canDelete && <DeleteButton id={o.id} />}
```

```python
# ⭐ FastAPI — the server states what this actor may do with this row
class OrderOut(BaseModel):
    id: UUID
    total: Decimal
    permissions: Permissions      # ⭐⭐ computed by the SAME code that
                                  #    enforces it on the write endpoint

def permissions_for(order, actor) -> Permissions:
    return Permissions(
        can_delete=actor.id == order.owner_id or actor.is_admin,
        can_refund=order.status == "paid" and actor.can("refund"),
    )
```

| ⭐ Why this is better than a role check in JSX | |
|---|---|
| **One source of truth** | ⭐⭐ The rule that renders the button is the rule that guards the endpoint. **They cannot drift** — which is Day 229's argument again. |
| **Rules are usually not just roles** | ⭐ "Owner *or* admin, if not archived, and within 30 days" does not fit in `role === "admin"` |
| **The client stays dumb** | ⭐ New rule ⇒ server change only. No frontend deploy. |
| **It stays honest** | ⭐⭐ You are *reflecting* a decision, not *making* one — the naming makes the boundary obvious in review |

> ⭐ **Keep the enforcement and the projection in the same function** on the server. If `can_delete`
> is computed in the serialiser and enforced by a separate `if` in the handler, they will diverge —
> and the divergence that says *"yes"* in the serialiser and *"no"* in the handler is merely annoying,
> while the reverse is a vulnerability.

# Part 3 — ⭐⭐ The leak that is not a button

```
⭐⭐ HIDING A FIELD IS NOT REDACTING IT.

⭐   GET /api/users/7  ⇒
⭐     { "id":7, "name":"Ada", "email":"...",
⭐       "salary": 95000,          ⭐⭐ NOT RENDERED. STILL SENT.
⭐       "passwordHash": "$2b$..." ⭐⭐ NOT RENDERED. STILL SENT. }

⭐   ⇒ ⭐ THE UI SHOWS name ONLY. ⭐⭐ THE DATA IS IN THE NETWORK TAB,
⭐     IN THE BROWSER CACHE, IN ANY LOGGING PROXY, AND IN THE
⭐     QUERY CACHE PERSISTED TO disk BY A DEVTOOL.

⭐   ⇒ ⭐⭐ THE FIX IS ON THE SERVER: A RESPONSE MODEL THAT CANNOT
⭐     CONTAIN THE FIELD. ⭐ NOT A `delete obj.salary` IN THE CLIENT.
```

```python
# ⭐⭐ FastAPI: response_model is an ALLOW-LIST, and that is the point
@app.get("/users/{id}", response_model=UserPublic)   # ⭐ never leaks a new
async def get_user(id: UUID) -> User:                #   field added later
    return await repo.get(id)
```

> ⭐⭐ **This is the third repo-README failure — "cross-user data leak" — and its most common form is
> not a missing `WHERE` clause but an over-broad serialiser.** The Stage 4 rule *"never return an ORM
> object from a controller"* exists for exactly this, and the frontend is where you notice it, because
> you can see the whole payload in DevTools.

| ⭐ Also check | |
|---|---|
| **List endpoints** | ⭐ `GET /orders` returning *everyone's* orders because the filter is applied in the UI |
| **Error messages** | ⭐⭐ A 403 body containing the resource you were not allowed to see |
| **Search / autocomplete** | ⭐ Frequently the endpoint nobody scoped to the tenant |
| **The 404 vs 403 choice** | ⭐⭐ `403` on a resource that exists confirms it exists. For sensitive ids, `404` is the safer answer. |

# Part 4 — What good looks like

```
⭐⭐ THE THREE LAYERS, EACH DOING ONLY ITS OWN JOB

⭐   ① UI       ⇒ hide/disable what the server said is not allowed
⭐                ⭐ PURELY COSMETIC. NEVER TRUSTED.
⭐   ② ⭐⭐ API   ⇒ AUTHORIZE EVERY REQUEST. THE ONLY REAL BOUNDARY.
⭐                ⭐ scope every query by actor — Day 434's permission
⭐                  filter, in an ordinary CRUD app
⭐   ③ ⭐ DATA   ⇒ RLS / row ownership as the backstop for the day
⭐                someone writes a query that forgot the filter

⭐   ⇒ ⭐⭐ AND A TEST THAT PROVES IT: for each protected endpoint,
⭐     call it as the WRONG user and assert 403/404. ⭐ If that test
⭐     does not exist, the authorization is a claim, not a fact.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you handle authorization in the frontend?"**

Open by refusing the premise, politely. **I don't. Authorization is server-side or it doesn't exist.
Everything the browser does is a suggestion the user can decline — they can edit my JavaScript, flip a
flag in React DevTools, or skip my app entirely and use curl. My test is simple: if I delete the whole
frontend and call the API directly, is anything different? If yes, the authorization is in the wrong
place.**

Then what the client *does* do, and why the shape matters. **The UI's job is showing what's relevant,
which is good UX and zero security. But I don't put role checks in JSX — the server sends a permissions
object per resource, computed by the same function that enforces the rule on the write path. So the
rule that renders the button is the rule that guards the endpoint and they can't drift. It also handles
real rules, which are rarely just roles — owner or admin, if not archived, within thirty days.**

Then the leak that isn't a button, because it is the one people miss. **Hiding a field isn't redacting
it. If the endpoint returns a salary and I just don't render it, it's still in the network tab, the
browser cache and any logging proxy. The fix is a response model on the server that can't contain the
field — an allow-list, so a column added next year doesn't leak by default. Building the client is
where you notice this, because you can see the whole payload.**

Close on proof. **For every protected endpoint there's a test that calls it as the wrong user and
asserts a 403 or 404. Without that test, the authorization is a claim rather than a fact.**
