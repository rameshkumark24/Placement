⭐⭐ THE THINGS PEOPLE REACH FOR A DISTRIBUTED LOCK TO DO, AND WHAT

⭐     ❌ lock  ⇒ ⭐⭐ ✅ `UPDATE … SET sold = sold+1 WHERE sold < total`

⭐     ❌ lock  ⇒ ✅ ⭐ a UNIQUE constraint (Day 187).
⭐   "Don't charge the card twice"
⭐     ❌ lock  ⇒ ✅ ⭐⭐ an IDEMPOTENCY KEY with a unique index
⭐        (Day 184 #6). ⭐ The lock protects a window; the key protects
⭐        forever.
⭐   "Don't run the nightly job on two boxes"
⭐     ⭐⭐ ✅ A LOCK IS GENUINELY RIGHT HERE — and it is an EFFICIENCY
⭐        lock (Part 5). ⭐ `pg_try_advisory_xact_lock` is often better
⭐        (Day 196), because it dies with the connection.
⭐   "Only one worker may process this job"
⭐     ❌ lock  ⇒ ✅ ⭐ `SELECT … FOR UPDATE SKIP LOCKED` (Day 196) or a

⭐ ⇒ ⭐⭐ THE TEST: "IF THIS LOCK FAILED SILENTLY, WOULD THE DATABASE
⭐   STILL REFUSE THE BAD OUTCOME?" ⭐ Yes ⇒ the lock is an optimisation.
⭐   ⭐⭐ No ⇒ you are relying on a lock for correctness, and the rest of

# Part 2 — ⭐⭐ Four bugs, built one at a time

## ⭐ Bug 1 — no expiry

```python
if r.setnx("lock:job", "1"):        # ⭐ atomic, thanks to Day 203
    do_work()
    r.delete("lock:job")
```
```
⭐⭐ THE PROCESS DIES (OOM kill, deploy, panic) BETWEEN THE TWO LINES.
⭐   ⇒ ⭐⭐ THE LOCK IS HELD ***FOREVER***. Nobody ever runs the job
⭐     again, and there is no error — just silence, which is the worst
⭐     failure mode there is. ⭐ Somebody notices in a week.
```

## ⭐ Bug 2 — expiry as a second command

```python
if r.setnx("lock:job", "1"):
    r.expire("lock:job", 30)        # ⭐⭐ CRASH HERE ⇒ Bug 1 again
```
```
⭐⭐ FIX: ONE ATOMIC COMMAND.  r.set(key, token, nx=True, ex=30)
⭐   ⭐ Day 204's `SET … NX EX` exists precisely for this.
```

## ⭐⭐ Bug 3 — you delete someone else's lock

```python
r.set("lock:job", "1", nx=True, ex=30)
do_work()                            # ⭐⭐ takes 35 seconds today
r.delete("lock:job")                 # ⭐⭐ ← DELETES ***B'S*** LOCK
```
```
⭐   t=0   A acquires, TTL 30 s
⭐   t=30  ⭐⭐ THE LOCK EXPIRES. A is still working and does not know.
⭐   t=31  B acquires the lock legitimately and starts working.
⭐   t=35  A finishes and calls DEL — ⭐⭐ REMOVING ***B'S*** LOCK.
⭐   t=36  C acquires. ⭐⭐ NOW B AND C ARE BOTH IN THE CRITICAL SECTION,
⭐         and the cascade continues indefinitely.

⭐⭐ FIX: A UNIQUE TOKEN PER HOLDER, AND A COMPARE-AND-DELETE.
⭐   ⭐⭐ AND IT MUST BE ATOMIC — GET-then-DEL has the same race in
⭐     miniature. ⭐⭐ `MULTI` CANNOT DO IT (a later command cannot
⭐     branch on an earlier result — Day 203). ⭐ THEREFORE: LUA.
```

```lua
-- ⭐⭐ THE RELEASE SCRIPT. Memorise this; it is five lines and it is the
--    single most-quoted piece of Redis code in existence.
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

## ⭐⭐ Bug 4 — the one no token can fix

```
⭐   t=0    A acquires, TTL 30 s.
⭐   t=5    ⭐⭐ A's PROCESS STOPS FOR 40 SECONDS. Causes, all real:
⭐            ⭐ a stop-the-world GC pause · ⭐ the VM is live-migrated ·
⭐            ⭐ the container is CPU-throttled by its cgroup quota ·
⭐            ⭐ a 40-second network partition · ⭐ swap · ⭐ SIGSTOP
⭐   t=30   the lock expires. ⭐ Redis is behaving correctly.
⭐   t=31   B acquires. B is legitimately the holder.
⭐   t=45   ⭐⭐ A WAKES UP, BELIEVES IT HOLDS THE LOCK, AND WRITES.
⭐   ⇒ ⭐⭐ TWO WRITERS IN THE CRITICAL SECTION. THE TOKEN DID NOT HELP:
⭐     ⭐⭐ ***THE TOKEN PROTECTS THE RELEASE, NOT THE CRITICAL
⭐     SECTION.*** A's release will correctly fail — after A has already
⭐     corrupted the data.

⭐⭐ THERE ARE ONLY THREE HONEST RESPONSES:
⭐  ① ⭐⭐ FENCING TOKENS. The lock hands out a monotonically increasing
⭐     number; every write carries it; ⭐⭐ THE RESOURCE REJECTS ANY
⭐     WRITE WITH A TOKEN LOWER THAN THE HIGHEST IT HAS SEEN.
⭐     ⇒ ⭐⭐ THIS IS THE ONLY CONSTRUCTION THAT ACTUALLY SOLVES IT —
⭐       and it requires the RESOURCE to cooperate. ⭐ A `WHERE
⭐       fence_token < :t` clause in your `UPDATE` is a fencing token,
⭐       and most people who have implemented one did not know its name.
⭐  ② ⭐⭐ MAKE THE OPERATION IDEMPOTENT OR CONDITIONAL, so a second
⭐     writer changes nothing. ⭐ Which is Part 1 again, and is usually
⭐     the cheapest answer.
⭐  ③ ⭐ ACCEPT IT — for efficiency locks, where a rare double-execution
⭐     costs wasted CPU rather than money.
```

# Part 3 — ⭐ The correct single-instance lock

```python
import uuid, time, contextlib

RELEASE = r.register_script("""
if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1])
else return 0 end""")
EXTEND = r.register_script("""
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else return 0 end""")

@contextlib.contextmanager
def redis_lock(name, ttl_ms=30_000, wait_s=0.0):
    key, token = f"lock:{name}", uuid.uuid4().hex   # ⭐⭐ unique per hold
    deadline = time.monotonic() + wait_s
    while True:
        if r.set(key, token, nx=True, px=ttl_ms):   # ⭐ atomic acquire
            break
        if time.monotonic() >= deadline:
            raise LockNotAcquired(name)             # ⭐⭐ FAIL FAST, and
        time.sleep(0.05 + random.random() * 0.05)   #    JITTER the retry
    try:
        yield token                                 # ⭐⭐ hand the token
    finally:                                        #    out — it is your
        RELEASE(keys=[key], args=[token])           #    fencing value
```

```
⭐⭐ THE FOUR DESIGN POINTS IN THAT CODE:
⭐   ⭐ TTL > worst-case work time, but ⭐⭐ NOT "GENEROUSLY LONG": a
⭐     long TTL means a crashed holder blocks everyone for that long.
⭐     ⭐⭐ THE TTL IS A TRADE BETWEEN "TWO HOLDERS" AND "NO HOLDER".
⭐   ⭐ FAIL FAST rather than blocking forever — an unbounded wait turns
⭐     one stuck job into a saturated worker pool (Day 152).
⭐   ⭐ JITTER the retry, or every waiter retries in lockstep.
⭐   ⭐⭐ RELEASE IN `finally`, AND ONLY WITH THE TOKEN.

⭐⭐ THE WATCHDOG (auto-renewal): a background thread calls `EXTEND`
⭐   every ttl/3 while the work runs.
⭐   ⭐ ✅ Long jobs no longer need a huge TTL.
⭐   ⭐⭐ ❌ IT DOES NOT FIX BUG 4. A GC pause freezes the watchdog TOO —
⭐     ⭐ the renewal stops exactly when you most need it. ⭐⭐ A
⭐     watchdog shrinks the window; it does not close it. ⭐ Say this
⭐     when someone offers a watchdog as "the fix".
```

# Part 4 — ⭐⭐ Redlock, and the argument to know both sides of

```
⭐⭐ REDLOCK: N (usually 5) ***INDEPENDENT*** Redis masters — not
⭐   replicas of one another.
⭐   ① get the current time
⭐   ② try to acquire on all N, with a small per-node timeout
⭐   ③ ⭐⭐ SUCCESS IF: acquired on a MAJORITY (3/5) ***AND*** the total
⭐      elapsed time is well under the TTL
⭐   ④ ⭐ VALIDITY = TTL − elapsed − clock drift allowance
⭐   ⑤ on failure, release on ALL nodes (including ones you may have got)

⭐⭐ THE PROBLEM IT SOLVES, WHICH IS REAL: with ONE Redis and a replica,
⭐   Day 205 ④ applies — ⭐⭐ replication is asynchronous, so a failover
⭐   can promote a replica that never received the lock key, and TWO
⭐   CLIENTS HOLD THE SAME LOCK WITH NO ERROR. ⭐ Redlock removes that
⭐   specific failure by not relying on replication at all.
```

```
⭐⭐ KLEPPMANN'S OBJECTION (2016), stated properly:
⭐   ⭐ Redlock is neither one thing nor the other. For EFFICIENCY it is
⭐     overkill; for CORRECTNESS it is insufficient.
⭐   ⭐⭐ IT DEPENDS ON TIMING ASSUMPTIONS: bounded clock drift, bounded
⭐     pauses, bounded network delay. ⭐⭐ A GC PAUSE OR AN NTP JUMP
⭐     BREAKS IT — and those are not exotic.
⭐   ⭐⭐ AND BUG 4 IS UNTOUCHED: no amount of quorum stops A waking
⭐     from a pause and writing. ⭐ Only FENCING TOKENS do, and Redlock
⭐     provides no monotonic token.
⭐   ⇒ ⭐ If you need correctness, use a consensus system (ZooKeeper,
⭐     etcd) that issues monotonic tokens — ⭐⭐ AND STILL FENCE AT THE
⭐     RESOURCE.

⭐⭐ ANTIREZ'S REPLY, also fair:
⭐   ⭐ ANY auto-expiring lock relies on a timing model; that is not
⭐     unique to Redlock. ⭐ Systems with leases (including ZooKeeper
⭐     sessions) have the same class of assumption.
⭐   ⭐⭐ FENCING TOKENS REQUIRE THE ***RESOURCE*** TO ENFORCE THEM, and
⭐     most resources (an S3 object, a third-party API, a file) cannot.
⭐     ⭐ If your resource can enforce a token, you probably did not need
⭐       the lock for correctness in the first place — which is Part 1.
⭐   ⭐ Redlock is a pragmatic improvement over single-instance for
⭐     efficiency locks in a multi-master world.

⭐⭐ THE SYNTHESIS — the answer to give, because it is the useful one:
⭐   ⭐⭐ ***SPLIT THE PROBLEM.***
⭐   ⭐ EFFICIENCY LOCK (a duplicate run wastes work): a SINGLE Redis
⭐     instance with `SET NX PX` + Lua release is ⭐⭐ ENTIRELY
⭐     SUFFICIENT. Redlock's five nodes buy you very little.
⭐   ⭐ CORRECTNESS LOCK (a double execution costs money or corrupts
⭐     data): ⭐⭐ DO NOT USE A REDIS LOCK AS THE GUARANTEE. Put the
⭐     invariant in the database — constraint, conditional update, or
⭐     idempotency key — and let the lock be an optimisation on top.
⭐   ⇒ ⭐⭐ THE POSITION IS NOT "REDLOCK IS BAD". IT IS "IF YOU NEED
⭐     REDLOCK, YOU PROBABLY NEED A DIFFERENT DESIGN."
```

# Part 5 — ⭐ Choosing, in practice

```
⭐⭐ THE DECISION TABLE:

⭐   NEED                              USE
⭐   dedupe a cron run                 ⭐ single Redis SET NX PX + Lua
⭐                                     ⭐⭐ or `pg_try_advisory_xact_lock`
⭐   avoid duplicate cache computes    ⭐ single Redis (Day 206)
⭐   one worker per job                ⭐⭐ SKIP LOCKED / consumer group
⭐   no double charge                  ⭐⭐ idempotency key + unique index
⭐   no oversell                       ⭐⭐ conditional UPDATE + CHECK
⭐   leader election                   ⭐ etcd / ZooKeeper / K8s Lease
⭐   ordered writes to a shared file   ⭐⭐ fencing token, or single writer
⭐
⭐⭐ AND THE UNDERRATED OPTION: POSTGRES ADVISORY LOCKS (Day 196).
⭐   ⭐ `pg_try_advisory_xact_lock(hashtext('nightly'))`
⭐   ⭐⭐ NO TTL AT ALL — the lock is held by a CONNECTION, so if the
⭐     process dies the connection drops and the lock releases
⭐     IMMEDIATELY AND CORRECTLY. ⭐⭐ THAT ELIMINATES BUGS 1, 2 AND 4
⭐     BY CONSTRUCTION, because there is no expiry to be wrong about.
⭐   ⭐ Cost: it holds a database connection (Day 197's arithmetic), it
⭐     is not usable through a transaction pooler in session form, and
⭐     it ties the lock to database availability.
⭐   ⇒ ⭐⭐ IF YOUR DATA IS ALREADY IN POSTGRES, THIS IS FREQUENTLY THE
⭐     RIGHT ANSWER AND ALMOST NOBODY CONSIDERS IT.
```

```python
# ⭐ Libraries, and what to check before trusting one:
# ⭐ redis-py's `r.lock(name, timeout=…, blocking_timeout=…)` — uses a
#   token and a Lua release. ⭐⭐ CHECK: does it release with a token?
#   Does it bound the wait? Does `.extend()` verify ownership?
# ⭐ `pottery`, `redlock-py`, `python-redis-lock` — read the release
#   path before adopting. ⭐⭐ A surprising number of blog-post
#   implementations still call plain `DEL`.
# ⭐⭐ AND THE OPERATIONAL RULE: EMIT A METRIC EVERY TIME A RELEASE
#   RETURNS 0. That means "my lock had already expired" — ⭐ it is the
#   early warning that your TTL is too short, and it is silent by
#   default.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Reaching for a lock first | Ask whether a constraint, conditional update or idempotency key makes it impossible. |
| `SETNX` with no expiry | The holder dies and the lock is held forever, silently. |
| `SETNX` then `EXPIRE` | A crash between them recreates the same deadlock. One atomic `SET NX PX`. |
| Releasing with `DEL` | You'll eventually delete someone else's lock and cascade. |
| `GET` then `DEL` to check ownership | Same race, smaller. It has to be Lua. |
| Using `MULTI` for compare-and-delete | Later commands can't branch on earlier results. |
| Believing the token protects the critical section | It protects the release. Bug 4 is untouched. |
| Offering a watchdog as the fix for Bug 4 | A GC pause freezes the watchdog too. It shrinks the window. |
| A generously long TTL | You traded "two holders" for "no holder for a long time". |
| Blocking forever to acquire | One stuck job saturates the worker pool. |
| No jitter on acquire retries | Every waiter retries in lockstep. |
| Single Redis + replica for a correctness lock | Async replication means a failover can hand the lock to two clients. |
| Reaching for Redlock for correctness | It has no fencing token; a pause still breaks it. |
| Dismissing Redlock entirely | For efficiency locks across multiple masters it's a reasonable pragmatic choice. |
| Forgetting Postgres advisory locks exist | No TTL, released on disconnect — Bugs 1, 2 and 4 vanish by construction. |
| Not alerting when a release returns 0 | That's "my lock had already expired", and it's silent. |

## Interview questions

**Q: Implement a distributed lock with Redis.**

> `SET key <unique-token> NX PX 30000` to acquire — one atomic command, because `SETNX` followed by
> `EXPIRE` leaves a window where a crash holds the lock forever. Release with a Lua script that
> compares the stored value to my token and only then deletes, because a plain `DEL` will eventually
> remove someone else's lock: if my work overruns the TTL, the lock expires, another client acquires
> it, and my delete removes theirs — and that cascades. It has to be Lua rather than `MULTI`, because
> a later command in a transaction can't branch on an earlier one's result. Around that: a bounded
> acquire wait with jitter rather than blocking forever, release in a `finally`, and a metric on
> releases that return zero, because that means my lock had already expired and it's the early warning
> that the TTL is too short. And I'd say up front that this is a correct *efficiency* lock, not a
> correctness guarantee — which leads to the next thing.

**Q: What's the failure that a token doesn't fix?**

> The holder pausing. At t=0 I acquire with a thirty-second TTL; at t=5 my process stops for forty
> seconds — a stop-the-world GC pause, a live migration, cgroup CPU throttling, a network partition,
> swapping; at t=30 the lock expires, which is Redis behaving correctly; at t=31 another client
> legitimately acquires it; at t=45 I wake up still believing I hold it and write. Two writers in the
> critical section. The token doesn't help because **the token protects the release, not the critical
> section** — my release will correctly fail, after I've already corrupted the data. A watchdog that
> renews the lease doesn't fix it either, because the same pause freezes the watchdog. There are only
> three honest responses: fencing tokens, where the lock issues a monotonically increasing number and
> the *resource* rejects any write with a lower one — a `WHERE fence_token < :t` clause is a fencing
> token, and most people who've written one didn't know its name; making the operation idempotent or
> conditional so a second writer changes nothing; or accepting it, which is fine for efficiency locks.

**Q: Should we use Redlock?**

> I'd argue both sides and then split the problem. Redlock's real motivation is legitimate: with a
> single Redis and a replica, replication is asynchronous, so a failover can promote a replica that
> never received the lock key and two clients hold the same lock with no error. Redlock avoids that by
> using independent masters and a majority. Kleppmann's objection is that it's neither one thing nor
> the other — overkill for efficiency, insufficient for correctness — because it relies on timing
> assumptions about clock drift, pauses and network delay, and it provides no fencing token, so the
> pause failure is untouched. Antirez's reply is fair too: any auto-expiring lock has a timing model,
> and fencing requires the resource to enforce tokens, which most resources can't. My position is that
> if the lock is for efficiency, a single Redis instance with `SET NX PX` and a Lua release is entirely
> sufficient and Redlock buys very little; and if the lock is for correctness, the guarantee belongs in
> the database as a constraint, a conditional update or an idempotency key, with the lock as an
> optimisation on top. Which is really: **if you think you need Redlock, you probably need a different
> design.**

**Q: What would you use instead of a Redis lock, given the choice?**

> Whatever makes the bad outcome impossible rather than unlikely. For overselling, a conditional
> `UPDATE ... WHERE sold < total` with a rowcount check plus a `CHECK` constraint — one statement, no
> lock, and no code path can bypass it. For duplicate charges, an idempotency key with a unique index,
> which protects forever rather than for the length of a window. For one-worker-per-job,
> `SELECT ... FOR UPDATE SKIP LOCKED` or a Stream consumer group, since the queue already provides
> exclusivity. And for the case where a lock genuinely is right — deduplicating a scheduled job —
> I'd seriously consider `pg_try_advisory_xact_lock` instead, because it has no TTL at all: the lock
> is held by a connection, so if the process dies the connection drops and the lock releases
> immediately and correctly. That removes the "lock held forever" and "expired while I was working"
> failures by construction. The costs are that it occupies a database connection, it's incompatible
> with transaction pooling in its session form, and it ties the lock to database availability — but if
> the data is already in Postgres it's frequently the right answer and almost nobody considers it.

**Q: How do you choose the TTL?**

> It's a trade between two failure modes, and I'd say it that way. Too short and the lock expires
> while work is still running, which gives you two holders. Too long and a crashed holder blocks
> everyone for that entire duration, which gives you no holder. So I'd start from a measured p99 of the
> protected work, add generous headroom, and then reduce the exposure from the other side rather than
> just inflating the number: a watchdog that renews every third of the TTL lets me keep the TTL short
> while supporting long work, and instrumenting failed releases tells me empirically how often I'm
> overrunning. And I'd keep the protected section as small as possible — particularly never holding
> the lock across an external HTTP call, which is the same rule as never holding a database
> transaction across I/O.

## 🎙️ Articulation drill

**Three minutes: "Implement a distributed lock, then tell me why it's wrong."**

Build it out loud in order, because the order is the argument: `SETNX` alone deadlocks forever if the
holder dies; adding `EXPIRE` as a second command has the same hole; `SET NX PX` fixes acquisition;
plain `DEL` deletes someone else's lock once your work overruns, so you need a token and a Lua
compare-and-delete — and it has to be Lua because `MULTI` can't branch on a result. Then make the turn
that matters: **the token protects the release, not the critical section.** Give the pause timeline —
acquire, freeze for forty seconds, lock expires, someone else acquires, you wake up and write — and
name the only real fixes: fencing tokens that the resource enforces, or an idempotent operation. Say a
watchdog freezes with you. Then Redlock in thirty seconds with both sides, and land the synthesis:
**efficiency locks are fine on one Redis; correctness locks belong in the database, and if you think
you need Redlock you probably need a different design.** Close by mentioning `pg_try_advisory_xact_lock`
as the option nobody considers — no TTL, released on disconnect, three bugs gone by construction.
