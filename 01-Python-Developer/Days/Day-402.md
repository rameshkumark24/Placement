# Part 1 — The group, and the cap nobody notices until production

```
⭐ A ***GROUP*** IS A SET OF CONSUMERS SHARING A SUBSCRIPTION.
⭐   ⭐ The coordinator assigns partitions to members.
⭐   ⭐⭐ ***AT MOST ONE CONSUMER PER PARTITION PER GROUP.***

⭐⭐ ⇒ SO ***CONSUMER PARALLELISM IS CAPPED BY PARTITION
⭐   COUNT.*** ⭐ Twelve partitions and twenty consumers means
⭐   ⭐⭐ EIGHT CONSUMERS SIT IDLE, FOREVER, DOING NOTHING, ⭐ and
⭐   your autoscaler will happily keep adding more.
⭐   ⭐⭐ THIS IS THE SINGLE COMMONEST "WE SCALED OUT AND NOTHING
⭐   GOT FASTER" IN KAFKA, ⭐ and it is why Day 401 said to
⭐   over-provision partitions.
⭐   ⭐ ⇒ Scale a Kafka consumer on ***lag***, and cap the
⭐     replica count at the partition count (Day 389).

⭐ ⭐ Different groups are fully independent: ⭐ each has its own
⭐   cursor over the same data. ⭐⭐ ADDING A NEW GROUP IS FREE AND
⭐   INVISIBLE TO EVERYONE ELSE — ⭐ that is the fan-out property.
```

# Part 2 — ⭐⭐ Offsets: two options, both wrong

```
⭐ AN OFFSET COMMIT SAYS "MY GROUP HAS PROCESSED UP TO HERE".
⭐   ⭐ It is stored in the `__consumer_offsets` topic.

⭐⭐ AND THERE ARE EXACTLY TWO PLACES TO PUT THE COMMIT:

⭐ ① ⭐⭐ ***COMMIT BEFORE PROCESSING*** → ***AT-MOST-ONCE.***
⭐    ⭐ Crash after the commit, before the work → ⭐⭐ THE MESSAGE
⭐    IS NEVER PROCESSED AND NOBODY EVER FINDS OUT.
⭐ ② ⭐⭐ ***COMMIT AFTER PROCESSING*** → ***AT-LEAST-ONCE.***
⭐    ⭐ Crash after the work, before the commit → ⭐⭐ THE MESSAGE
⭐    IS PROCESSED TWICE.

⭐⭐ ⇒ ***THERE IS NO THIRD OPTION THAT DOES NOT INVOLVE YOUR OWN
⭐   STORAGE*** (PART 7). ⭐ And between the two, ⭐⭐ AT-LEAST-ONCE
⭐   IS ALWAYS THE RIGHT CHOICE, ⭐ because a duplicate is a
⭐   problem you can solve with an idempotency key (Day 335) and
⭐   a lost message is a problem you cannot solve at all.

⭐⭐ AND NOW THE TRAP: ***AUTO-COMMIT IS AT-MOST-ONCE IN
⭐   DISGUISE.***
⭐   ⭐ `enable.auto.commit=true` (the default) commits every
⭐     `auto.commit.interval.ms` (5 s) ⭐⭐ — BUT IT COMMITS
⭐     ***INSIDE `poll()`***, AND IT COMMITS THE OFFSETS OF
⭐     EVERYTHING THE ***PREVIOUS*** `poll()` RETURNED.
⭐   ⭐⭐ SO IF YOU CALL `poll()` IN A LOOP AND HAND THE BATCH TO A
⭐     THREAD POOL — OR JUST TAKE LONGER THAN 5 SECONDS ON
⭐     MESSAGE THREE OF TEN — ⭐⭐ THE OFFSETS FOR MESSAGES YOU
⭐     HAVE NOT FINISHED ARE ALREADY COMMITTED, ⭐ and a crash
⭐     loses them.
⭐   ⭐⭐ ⇒ ***TURN AUTO-COMMIT OFF.*** ⭐ It is the default and it
⭐     is wrong for anything that matters.
```

# Part 3 — ⭐⭐ The rebalance, and the spiral

```
⭐ A REBALANCE REASSIGNS PARTITIONS. ⭐ Triggers:
⭐   ⭐ a member joins (a deploy, a scale-out)
⭐   ⭐ a member leaves cleanly
⭐   ⭐ `session.timeout.ms` passes with no heartbeat (the
⭐     process died or is unreachable)
⭐   ⭐⭐ `max.poll.interval.ms` PASSES BETWEEN `poll()` CALLS —
⭐     ⭐⭐ I.E. ***YOUR PROCESSING WAS TOO SLOW***, and the
⭐     coordinator concludes you are stuck

⭐ ⭐⭐ WITH THE ***EAGER*** PROTOCOL, A REBALANCE STOPS THE
⭐   WORLD: ⭐ every member revokes ***every*** partition, then
⭐   the leader recomputes, then everyone re-fetches.
⭐   ⭐ For a few seconds, ⭐⭐ NOTHING IS BEING CONSUMED AT ALL.

⭐⭐ ***THE SPIRAL*** — Day 334's, with the mechanism:
⭐ ① ⭐ One consumer is slow and exceeds `max.poll.interval.ms`.
⭐ ② ⭐ Rebalance. ⭐⭐ ITS PARTITIONS GO TO THE OTHERS.
⭐ ③ ⭐⭐ THE OTHERS NOW HAVE ***MORE*** PARTITIONS AND ARE
⭐    THEREFORE SLOWER.
⭐ ④ ⭐ Another one exceeds the interval.
⭐ ⑤ ⭐⭐ REBALANCE. GOTO ②.
⭐ ⭐⭐ ⇒ THE GROUP SPENDS ALL ITS TIME REBALANCING AND
⭐   THROUGHPUT GOES TO ***ZERO*** WHILE EVERY PROCESS LOOKS
⭐   ALIVE AND BUSY. ⭐ Lag rises vertically. ⭐⭐ AND RESTARTING
⭐   THE CONSUMERS — THE INSTINCT — TRIGGERS MORE REBALANCES AND
⭐   MAKES IT WORSE.

⭐⭐ THE FIX SET, IN ORDER:
⭐ ① ⭐⭐ ***REDUCE `max.poll.records`.*** ⭐ Fetch 50, not 500.
⭐    ⭐ The loop returns to `poll()` sooner. ⭐⭐ THIS IS USUALLY
⭐    THE WHOLE FIX AND IT IS ONE LINE.
⭐ ② ⭐ Raise `max.poll.interval.ms` to comfortably exceed
⭐    ***p99 batch processing time***, not the mean.
⭐ ③ ⭐⭐ `partition.assignment.strategy = cooperative-sticky` —
⭐    ⭐⭐ INCREMENTAL REBALANCING: ONLY THE PARTITIONS THAT
⭐    ACTUALLY MOVE ARE REVOKED. ⭐ No stop-the-world.
⭐ ④ ⭐ Separate the heartbeat concern: ⭐ `session.timeout.ms`
⭐    governs liveness (a background thread heartbeats), ⭐⭐ WHILE
⭐    `max.poll.interval.ms` GOVERNS PROGRESS. ⭐ Different
⭐    problems, different knobs, ⭐⭐ AND PEOPLE TUNE THE WRONG
⭐    ONE.
```

# Part 4 — ⭐⭐ Static membership, the best setting for containers

```
⭐ EVERY ROLLING DEPLOY NORMALLY COSTS ***TWO*** REBALANCES PER
⭐   POD: ⭐ one when the old pod leaves, ⭐ one when the new pod
⭐   joins. ⭐⭐ TEN PODS = TWENTY REBALANCES = MINUTES OF
⭐   DEGRADED CONSUMPTION ON EVERY DEPLOY.

⭐⭐ ⇒ ***`group.instance.id` MAKES THE MEMBER STATIC.*** ⭐ The
⭐   coordinator remembers the assignment and holds it for
⭐   `session.timeout.ms` while the pod restarts.
⭐   ⭐⭐ ⇒ A RESTART WITHIN THE TIMEOUT CAUSES ***NO REBALANCE AT
⭐   ALL.*** ⭐ The same pod comes back and reclaims exactly the
⭐   partitions it had.
⭐ ⭐ In Kubernetes use the StatefulSet ordinal; ⭐ in ECS use the
⭐   task's stable identifier, ⭐⭐ OR ANY VALUE THAT IS STABLE
⭐   ACROSS A RESTART AND UNIQUE ACROSS MEMBERS.
⭐ ⭐ The cost: ⭐⭐ A GENUINELY DEAD POD IS NOT REPLACED UNTIL
⭐   `session.timeout.ms` EXPIRES, ⭐ so set it to a real
⭐   restart time (45–120 s), not to ten minutes.

⭐⭐ THIS IS THE SINGLE HIGHEST-VALUE KAFKA CONSUMER SETTING FOR
⭐   ANYONE RUNNING ON KUBERNETES OR ECS, ⭐ and it is routinely
⭐   unset.
```

# Part 5 — The Python consumer loop, done properly

```python
from confluent_kafka import Consumer, KafkaError

c = Consumer({
    "bootstrap.servers": BROKERS,
    "group.id": "orders-projector",
    "group.instance.id": os.environ["POD_NAME"],   # ⭐⭐ STATIC
    "enable.auto.commit": False,                   # ⭐⭐ ALWAYS
    "auto.offset.reset": "earliest",               # ⭐ or latest —
    #   ⭐⭐ DECIDE DELIBERATELY: `latest` SILENTLY SKIPS THE
    #   ⭐   BACKLOG THE FIRST TIME A NEW GROUP STARTS.
    "max.poll.records": 50,                        # ⭐⭐ SMALL
    "max.poll.interval.ms": 300_000,               # ⭐ > p99 batch
    "session.timeout.ms": 45_000,
    "partition.assignment.strategy": "cooperative-sticky",
})

def _on_revoke(consumer, partitions):
    # ⭐⭐ COMMIT WHAT YOU FINISHED BEFORE LOSING THE PARTITION —
    # ⭐   otherwise the next owner reprocesses it all.
    consumer.commit(asynchronous=False)

c.subscribe([TOPIC], on_revoke=_on_revoke)

try:
    while running:
        msgs = c.consume(num_messages=50, timeout=1.0)
        for m in msgs:
            if m.error():
                if m.error().code() == KafkaError._PARTITION_EOF:
                    continue                       # ⭐ not an error
                raise KafkaException(m.error())
            handle(m)                              # ⭐⭐ IDEMPOTENT
        if msgs:
            c.commit(asynchronous=False)           # ⭐⭐ AFTER work
finally:
    c.close()          # ⭐⭐ LEAVES THE GROUP CLEANLY = FAST
                       # ⭐   REBALANCE INSTEAD OF A TIMEOUT
```

```
⭐⭐ AND THE PATTERN FOR WORK THAT IS GENUINELY SLOW — ⭐ where
⭐   raising `max.poll.interval.ms` is not honest:
⭐   ⭐⭐ ***`pause()` THE PARTITIONS, DO THE WORK, KEEP CALLING
⭐   `poll()` (WHICH NOW RETURNS NOTHING BUT KEEPS YOU ALIVE),
⭐   THEN `resume()`.*** ⭐ You stay in the group without
⭐   pretending the batch is fast, ⭐⭐ AND THE COORDINATOR NEVER
⭐   SUSPECTS YOU.
```

# Part 6 — Lag: the only consumer metric that matters

```
⭐⭐ ***LAG = LOG END OFFSET − COMMITTED OFFSET, PER PARTITION.***
⭐ ⭐ Throughput is not the metric: ⭐⭐ A CONSUMER PROCESSING
⭐   1,000/s LOOKS HEALTHY WHILE FALLING BEHIND A PRODUCER DOING
⭐   1,200/s.

⭐⭐ AND THE ARITHMETIC THAT TURNS LAG INTO A DECISION:
⭐   ⭐⭐ ***TIME TO CATCH UP = LAG ÷ (CONSUME RATE − PRODUCE
⭐   RATE)***
⭐   ⭐ If the denominator is ≤ 0, ⭐⭐ THE ANSWER IS "NEVER" AND
⭐     YOU PAGE NOW.
⭐   ⭐ 400,000 lag, consuming 5,000/s, producing 3,000/s
⭐     ⭐ ⇒ 200 seconds. ⭐⭐ FINE. DO NOT PAGE.
⭐   ⭐⭐ ⇒ SO THE ALERT IS NOT "LAG > 100,000". ⭐ It is
⭐     ⭐⭐ ***LAG IS RISING*** (DERIVATIVE) ⭐ or ⭐⭐ ***TIME TO
⭐     CATCH UP EXCEEDS THE SLO***. ⭐ Same lesson as Day 393's
⭐     age-not-depth, with better arithmetic available.

⭐ ⭐ Lag in ***messages*** is meaningless without cost per
⭐   message: ⭐⭐ 10,000 THUMBNAIL JOBS AND 10,000 COUNTER
⭐   INCREMENTS ARE NOT THE SAME NUMBER. ⭐ Where you can, expose
⭐   lag in ***seconds*** (timestamp of the next unprocessed
⭐   message vs now) — ⭐⭐ WHICH IS THE FORM A HUMAN CAN ACT ON.
```

# Part 7 — ⭐⭐ The third option: own your offsets

```
⭐⭐ FOR A CONSUMER WHOSE SINK IS A ***DATABASE***, THERE IS A
⭐   STRICTLY BETTER PATTERN THAN COMMITTING TO KAFKA:

⭐   ⭐⭐ ***STORE THE OFFSET IN YOUR OWN DATABASE, IN THE SAME
⭐   TRANSACTION AS THE WRITE, AND `seek()` TO IT ON START.***
```

```sql
BEGIN;
  INSERT INTO order_read_model (...) VALUES (...)
    ON CONFLICT (id) DO UPDATE SET ...;
  UPDATE consumer_offsets
     SET "offset" = :offset
   WHERE topic = :t AND partition = :p;   -- ⭐⭐ SAME TXN
COMMIT;
```

```
⭐⭐ ⇒ NOW THE WRITE AND THE POSITION COMMIT OR ROLL BACK
⭐   ***TOGETHER***, ⭐ so a crash cannot leave them disagreeing.
⭐   ⭐⭐ AT-LEAST-ONCE DELIVERY BECOMES ***EFFECTIVELY-ONCE
⭐   PROCESSING*** WITHOUT KAFKA TRANSACTIONS, WITHOUT A DEDUP
⭐   TABLE, AND WITHOUT ANY IMPOSSIBILITY BEING VIOLATED
⭐   (DAY 335) — ⭐ because the atomicity came from the database
⭐   you already had.
⭐ ⭐ On `on_assign`, read the stored offsets and `seek()`.
⭐ ⭐⭐ THIS IS THE SAME IDEA AS THE OUTBOX (DAY 407), POINTING THE
⭐   OTHER WAY: ***MAKE THE BOOKKEEPING A CONSEQUENCE OF THE
⭐   WRITE INSTEAD OF A SECOND ACTION.*** ⭐ It is the recurring
⭐   move of this whole stage.
```

# 💬 Interview

**1. ⭐⭐ "We added consumers and throughput didn't change."**
> ⭐ Almost certainly more consumers than partitions. ⭐⭐ **At most one consumer per partition per
> group, so with twelve partitions and twenty consumers, eight sit idle forever doing nothing — and
> the autoscaler happily keeps adding more.** ⭐ It's the commonest "we scaled out and nothing got
> faster" in Kafka. ⭐ The fixes are to scale on lag rather than CPU, cap replicas at the partition
> count, ⭐⭐ **and to have over-provisioned partitions in the first place, since adding them later moves
> keys and breaks ordering across the resize.**

**2. ⭐⭐ "Where do you commit the offset?"**
> ⭐ There are only two places and both are wrong in a specific way. ⭐⭐ **Before processing gives
> at-most-once — crash after the commit and the message is never processed and nobody finds out. After
> processing gives at-least-once — crash before the commit and it's processed twice.** ⭐ At-least-once
> is always the right choice, ⭐⭐ **because a duplicate is solvable with an idempotency key and a lost
> message isn't solvable at all.** ⭐ And the trap is that ⭐⭐ **auto-commit is at-most-once in disguise:
> it commits inside `poll()`, and it commits the offsets of everything the previous poll returned — so
> if message three of ten takes longer than the interval, the offsets for messages you haven't
> finished are already committed.** ⭐ Turn it off; it's the default and it's wrong for anything that
> matters.

**3. ⭐⭐ "Explain the rebalance spiral."**
> ⭐ One consumer is slow and exceeds `max.poll.interval.ms`, so the coordinator concludes it's stuck
> and rebalances. ⭐⭐ **Its partitions go to the others, which now have more partitions and are
> therefore slower, so another one exceeds the interval, and it repeats.** ⭐ The group ends up spending
> all its time rebalancing, throughput goes to zero, ⭐⭐ **and every process looks alive and busy while
> lag rises vertically — and restarting the consumers, which is the instinct, triggers more rebalances
> and makes it worse.** ⭐ The fix is usually one line: ⭐⭐ **reduce `max.poll.records` so the loop
> returns to `poll()` sooner.** ⭐ Then raise `max.poll.interval.ms` above p99 batch time, and switch to
> `cooperative-sticky` so only the partitions that actually move get revoked instead of a
> stop-the-world.

**4. "What's your favourite Kafka consumer setting?"**
> ⭐⭐ **`group.instance.id` — static membership.** ⭐ Normally every rolling deploy costs two rebalances
> per pod, one when the old leaves and one when the new joins, ⭐⭐ **so ten pods is twenty rebalances
> and minutes of degraded consumption on every deploy.** ⭐ With static membership the coordinator holds
> the assignment across a restart within the session timeout, ⭐⭐ **so a normal deploy causes no
> rebalance at all and each pod reclaims exactly its own partitions.** ⭐ The cost is that a genuinely
> dead pod isn't replaced until the session timeout expires, so I set it to a realistic restart time.
> ⭐ It's the highest-value setting for anyone on Kubernetes or ECS and it's routinely unset.

**5. ⭐⭐ "How do you alert on a Kafka consumer?"**
> ⭐ On lag, but not on a raw threshold. ⭐⭐ **Time to catch up equals lag divided by consume rate minus
> produce rate — so 400,000 lag while consuming 5,000 a second and producing 3,000 is 200 seconds,
> which is fine and I would not page. If the denominator is zero or negative, the answer is "never"
> and I page immediately.** ⭐ So the alert is on the derivative — lag rising — or on time-to-catch-up
> exceeding the SLO. ⭐⭐ **And I'd expose lag in seconds rather than messages where I can, because
> 10,000 thumbnail jobs and 10,000 counter increments are not the same number, and seconds is the form
> a human can act on.**

**6. ⭐⭐ "How do you avoid duplicates in a database sink?"**
> ⭐ I don't commit the offset to Kafka at all. ⭐⭐ **I store the offset in my own database in the same
> transaction as the write, and `seek()` to it on partition assignment.** ⭐ Then the write and the
> position commit or roll back together, so a crash can't leave them disagreeing — ⭐⭐ **at-least-once
> delivery becomes effectively-once processing with no Kafka transactions, no dedup table, and no
> impossibility violated, because the atomicity came from the database I already had.** ⭐ It's the same
> move as the outbox pointing the other way: ⭐⭐ **make the bookkeeping a consequence of the write
> rather than a second action.**

## 🎙️ Articulation drill

**Two minutes.** Frame the group as a lease system, then give the cap: **at most one consumer per
partition per group, so twelve partitions and twenty consumers means eight sit idle forever — the
commonest "we scaled out and nothing got faster".** Then offsets, as a forced choice: **commit before
processing and you get at-most-once, where a crash loses the message and nobody finds out; commit
after and you get at-least-once, where a crash reprocesses. At-least-once always, because a duplicate
is solvable with an idempotency key and a lost message isn't.** Then the trap: **auto-commit is
at-most-once in disguise — it commits inside `poll()`, for everything the previous poll returned, so
if message three of ten is slow the offsets for unfinished work are already committed.** Then the
operational story: **the rebalance spiral — one slow consumer exceeds the poll interval, its
partitions move to the others, which are now slower, so another exceeds it, and throughput reaches
zero while every process looks alive and busy. Restarting them, which is the instinct, makes it
worse.** The fix is usually one line — `max.poll.records` — then cooperative-sticky so only moving
partitions get revoked. Give the setting people don't know: **`group.instance.id`, because a ten-pod
rolling deploy otherwise costs twenty rebalances, and static membership makes a normal deploy cause
none.** Close on alerting and on the better pattern: **alert on lag rising or time-to-catch-up, not a
raw threshold — and for a database sink, store the offset in your own database in the same transaction
as the write, which turns at-least-once delivery into effectively-once processing with no Kafka
transactions at all, because the atomicity came from the database you already had.**
