# Part 1 — ⭐ Request and Response objects

```python
from functools import cached_property        # ⭐ Day 051

class Request:
    def __init__(self, method, path, query, headers, body, params=None):
        self.method, self.path, self.headers = method, path, headers
        self.query, self.body = query, body
        self.params = params or {}           # ⭐ path params from the router
        self.state: dict = {}                # ⭐⭐ where middleware leaves things

    @cached_property                          # ⭐⭐ LAZY — parsed once, and only if used
    def json(self):
        if not self.headers.get("content-type", "").startswith("application/json"):
            raise HTTPError(415, "expected application/json")
        try:
            return json.loads(self.body)
        except json.JSONDecodeError as e:
            raise HTTPError(400, "invalid JSON") from e    # ⭐ Days 059, 104

    @cached_property
    def form(self):
        return parse_qs(self.body.decode("utf-8"))
```

```
⭐⭐ WHY LAZY, AND IT IS NOT MICRO-OPTIMISATION: a health-check endpoint should
⭐   not pay to parse a JSON body, and a request that will be rejected by an auth
⭐   middleware (Part 3) should never be parsed at all. ⭐⭐ Eager parsing means
⭐   attacker-controlled JSON is deserialised BEFORE authentication runs, which
⭐   is a security position as well as a performance one.
⭐   ⇒ ⭐ `cached_property` gives you parse-once-on-first-access with no flag
⭐        variable — and Day 051 already told you the cache lives on the INSTANCE,
⭐        which is exactly right here because the instance is one request.
```

```python
class Response:
    def __init__(self, body=b"", status=200, headers=None, content_type="text/plain"):
        self.body = body if isinstance(body, bytes) else str(body).encode("utf-8")
        self.status, self.headers = status, list(headers or [])
        self.headers.append(("Content-Type", f"{content_type}; charset=utf-8"))

class JSONResponse(Response):
    def __init__(self, data, status=200, headers=None):
        super().__init__(json.dumps(data, default=str).encode("utf-8"),
                         status, headers, "application/json")
```

⚠️ ⭐ **`default=str` on `json.dumps` is a convenience with a cost** (Days 041, 076): it will silently
stringify a `Decimal` and a `datetime`. ⭐⭐ **That is fine for a datetime and wrong for money** —
`Decimal("10.00")` becomes `"10.00"` if you are lucky and a float if you are not. **Serialise money
explicitly.**

⭐ **`request.state` is the channel between middleware and handlers** — where `request.state.user`
lands after authentication. ⭐⭐ **Keep it small and documented**, or it becomes a global bag that
nothing can reason about.

# Part 2 — ⭐⭐ Middleware is a decorator

```python
Handler = Callable[[Request], Response]

def timing_middleware(next_handler: Handler) -> Handler:      # ⭐⭐ takes next, returns a handler
    def wrapped(request: Request) -> Response:
        start = time.perf_counter()
        response = next_handler(request)                       # ⭐ call the next layer
        elapsed = (time.perf_counter() - start) * 1000
        response.headers.append(("X-Response-Time", f"{elapsed:.1f}ms"))
        return response
    return wrapped

# ⭐⭐ COMPOSITION — the whole mechanism, in one line:
from functools import reduce
app = reduce(lambda h, mw: mw(h), reversed(middlewares), router.dispatch)
```

```
⭐⭐ THIS IS EXACTLY DAY 044'S DECORATOR, WITH A DIFFERENT NAME:
⭐     @timing            def wrapped(...): ... return wrapped
⭐     middleware(next)   def wrapped(...): ... return wrapped
⭐   ⇒ ⭐ so decorator STACKING ORDER (Day 044) and middleware ORDER are the same
⭐        rule, and you already know it.
⭐
⭐ ⭐⭐ THE ONION:
⭐        request  ──▶ ErrorHandler ──▶ Logging ──▶ CORS ──▶ Auth ──▶ handler
⭐        response ◀── ErrorHandler ◀── Logging ◀── CORS ◀── Auth ◀── handler
⭐   ⇒ ⭐⭐ EVERY MIDDLEWARE SEES THE REQUEST ON THE WAY IN AND THE RESPONSE ON
⭐        THE WAY OUT. ⭐ The FIRST registered is the OUTERMOST — so it sees the
⭐        request first and the response LAST.
```

# Part 3 — ⭐⭐ The order is a correctness property

```
⭐⭐ OUTERMOST FIRST, WITH THE REASON EACH ONE SITS WHERE IT DOES:
⭐
⭐ 1. ⭐⭐ ERROR HANDLING  — must be OUTERMOST, because it can only catch what is
⭐      INSIDE it. ⭐⭐ Put it second and an exception raised by the first
⭐      middleware escapes to the socket ⇒ a bare connection reset instead of a
⭐      500, and nothing logged.
⭐ 2. ⭐⭐ REQUEST ID / LOGGING — near the outside, so EVERY request is logged
⭐      including the ones later middleware rejects. ⭐ Put logging inside auth
⭐      and you have no record of failed authentication attempts, ⭐⭐ which is
⭐      exactly the traffic you most want to see (Day 099A).
⭐ 3. ⭐ CORS — before auth, because ⭐⭐ A PREFLIGHT `OPTIONS` REQUEST CARRIES NO
⭐      CREDENTIALS. ⭐ Put CORS inside auth and every preflight gets a 401,
⭐      the browser blocks the real request, and you spend a day blaming CORS
⭐      when the bug is ordering (Day 020).
⭐ 4. ⭐ RATE LIMITING — before auth if you are protecting the login endpoint
⭐      itself (Day 123); after, if the limit is per-user.
⭐ 5. ⭐⭐ AUTHENTICATION — before the handler, obviously; ⭐ and it may
⭐      SHORT-CIRCUIT, returning 401 without ever calling `next_handler`.
⭐ 6. ⭐ COMPRESSION — innermost of the response-modifying ones, so it compresses
⭐      the FINAL body. ⭐⭐ Compress too early and later middleware appends to a
⭐      gzip stream, producing bytes no client can read.
⭐
⭐ ⇒ ⭐⭐ EVERY ONE OF THOSE IS A REAL BUG WITH A CONFUSING SYMPTOM. That is why
⭐     "order matters" is worth stating as a correctness property rather than a
⭐     convention — and why frameworks document their default order.
```

```python
def auth_middleware(next_handler):
    def wrapped(request):
        token = request.headers.get("authorization", "").removeprefix("Bearer ")
        user = verify(token)
        if user is None:
            return JSONResponse({"error": "unauthorized"}, 401,   # ⭐⭐ SHORT-CIRCUIT
                                headers=[("WWW-Authenticate", "Bearer")])  # ⭐ Day 102
        request.state["user"] = user                               # ⭐ hand it downstream
        return next_handler(request)
    return wrapped
```

⚠️ ⭐⭐ **A middleware that applies to *everything* must handle the endpoints that should be exempt** —
health checks, metrics, and the login route itself. ⭐ **An auth middleware with no exemption list
makes login impossible**, and the workaround people reach for (checking `request.path` inside the
middleware) is a hardcoded route list that drifts. ⭐⭐ **Prefer per-route dependencies for anything
that has exceptions** (Part 5).

# Part 4 — ⭐ The body-consumption trap

```
⚠️⚠️ ⭐⭐ A MIDDLEWARE THAT READS THE REQUEST BODY BREAKS EVERYTHING DOWNSTREAM,
⭐    AND IT IS THE HARDEST MIDDLEWARE BUG TO DIAGNOSE.
⭐    ⇒ in a STREAMING model (ASGI, Day 110), the body arrives as a sequence of
⭐      messages from `receive()`. ⭐⭐ ONCE CONSUMED, IT IS GONE — the handler
⭐      calls receive() and gets nothing, so `request.json` is empty and the
⭐      endpoint reports "missing field" on a request that plainly had one.
⭐    ⇒ ⭐⭐ SO A BODY-READING MIDDLEWARE (audit logging, signature verification)
⭐      MUST BUFFER AND REPLAY: read it all, then hand downstream a `receive`
⭐      that yields the buffered copy.
⭐    ⇒ ⚠️ ⭐ AND THAT REINTRODUCES THE MEMORY PROBLEM Day 104 solved: you are
⭐      now holding the whole body. ⭐⭐ Cap it, and exempt large-upload routes.
⭐    ⇒ ⭐ In our simple synchronous framework the body is already `bytes`, so
⭐      this is free — ⭐⭐ which is worth noticing, because it is exactly the
⭐      convenience ASGI trades away to gain streaming.
```

```python
def error_middleware(next_handler):
    def wrapped(request):
        try:
            return next_handler(request)
        except HTTPError as e:                       # ⭐ expected (Day 060)
            return JSONResponse({"error": e.message,
                                 "request_id": request_id.get()}, e.status)
        except Exception:                            # ⭐⭐ unexpected — a bug
            logger.exception("unhandled", extra={"path": request.path})  # ⭐ log ONCE
            return JSONResponse({"error": "internal server error",
                                 "request_id": request_id.get()}, 500)   # ⭐⭐ generic (Day 105)
    return wrapped
```

⭐⭐ **Returning the request id in the error body** is the Day 099A payoff: the user quotes it, you
find every log line for that request in one query.

# Part 5 — ⭐ Middleware, decorator, or dependency?

| ⭐ Use | ⭐ When |
|---|---|
| ⭐⭐ **Middleware** | ⭐⭐ applies to **every** request, needs to see requests **and** responses — error handling, request ids, timing, CORS, compression |
| ⭐ **Route decorator** | ⭐ applies to *some* routes, decided at registration — `@requires("admin")` |
| ⭐⭐ **Dependency / handler argument** | ⭐⭐ the handler **needs a value** — the current user, a DB session. ⭐ Visible in the signature, and therefore testable |

```
⭐⭐ THE HEURISTIC: IF THE HANDLER NEEDS TO *USE* THE RESULT, IT SHOULD BE A
⭐   PARAMETER, NOT A SIDE EFFECT IN request.state.
⭐     def get_profile(request):  user = request.state["user"]     ⚠️ ⭐ invisible
⭐     def get_profile(request, user: User):                        ⭐⭐ declared
⭐   ⇒ ⭐⭐ the second is Day 093's fixture argument and Day 089's "make
⭐        dependencies visible in the signature", and it is why FastAPI's
⭐        `Depends` exists rather than everything being middleware.
⭐   ⇒ ⭐ middleware is for things the handler should NOT know about.
```

⭐ **Do not over-build.** ⭐⭐ Four middlewares — errors, request id/logging, CORS, auth — cover almost
every service. **A chain of twelve is a service where nobody can say what happens to a request**, and
each layer is a place a header can be silently rewritten.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Error handling not outermost** | ⭐⭐ It can only catch what is inside it. |
| ⭐ Logging inside auth | ⭐⭐ No record of failed auth attempts — the traffic you most want. |
| ⭐⭐ **CORS inside auth** | ⭐⭐ Preflight carries no credentials ⇒ 401 ⇒ a day lost blaming CORS. |
| Compression not innermost | ⭐ Later layers append to a gzip stream — unreadable bytes. |
| ⭐ Auth middleware with no exemptions | ⭐⭐ Login becomes impossible. |
| Hardcoding exempt paths in a middleware | ⭐ It drifts. Use per-route dependencies. |
| ⭐⭐ **Reading the body in middleware** | ⭐⭐ Downstream gets nothing. Buffer and replay — and cap it. |
| Eager body parsing | ⭐⭐ You deserialise attacker JSON before authenticating. |
| ⭐ `request.state` as a general bag | ⭐ If the handler uses it, make it a parameter. |
| A traceback in the response | ⭐ Generic message + request id (Day 105). |
| ⭐ Twelve middlewares | ⭐ Nobody can say what happens to a request. |
| `json.dumps(default=str)` for money | ⭐⭐ Serialise `Decimal` explicitly (Day 041). |

## Interview questions

**Q: What is middleware, mechanically?**
> A function that takes the next handler and returns a replacement handler — which is exactly a
> decorator. You compose them by folding the list over the router's dispatch function, and the result
> is an onion: each layer sees the request on the way in and the response on the way out, with the
> first registered being outermost. Once you see it's a decorator, the stacking rules are ones you
> already know.

**Q: Why does middleware order matter?**
> Because it's the nesting order, so it's a correctness property rather than a preference. Error
> handling has to be outermost, because it can only catch what's inside it — put it second and an
> exception in the first layer escapes to the socket as a connection reset with nothing logged.
> Logging goes near the outside so you record the requests that later layers reject; put it inside
> auth and you have no record of failed authentication attempts, which is exactly the traffic you want
> to see. CORS goes before auth, because a preflight `OPTIONS` carries no credentials — inside auth
> every preflight 401s, the browser blocks the real request, and you lose a day blaming CORS. And
> compression is innermost of the response-modifying layers, or something later appends plain bytes to
> a gzip stream. Every one of those is a real bug with a confusing symptom.

**Q: What's the trap with a middleware that reads the request body?**
> In a streaming model the body arrives as messages from `receive`, and once consumed it's gone. So an
> audit-logging or signature-verifying middleware that reads the body leaves the handler with nothing
> — `request.json` is empty and the endpoint reports a missing field on a request that clearly had
> one, which is horrible to diagnose. The fix is to buffer and replay: read it fully, then pass
> downstream a `receive` that yields the buffered copy. That reintroduces the memory problem, so it
> needs a size cap and an exemption for large uploads.

**Q: Middleware, decorator, or dependency?**
> Middleware for things that apply to every request and need to see both the request and the response
> — errors, request ids, timing, CORS. A route decorator for things that apply to some routes, decided
> at registration. And a dependency, passed as a handler argument, whenever the handler actually
> *uses* the value — the current user, a database session. The heuristic is that if the handler needs
> the result, it should be a parameter rather than a side effect hidden in `request.state`, because a
> parameter is visible in the signature and testable in isolation. That's why FastAPI has `Depends`
> instead of making everything middleware.

**Q: Why parse the body lazily?**
> Because a request that a later middleware will reject should never be parsed at all — eager parsing
> means you deserialise attacker-controlled JSON before authentication has run, which is a security
> position as much as a performance one. And a health check shouldn't pay for a body parser it never
> uses. `cached_property` gives you parse-once-on-first-access with no flag variable, and the cache
> lives on the instance, which is right here because the instance is one request.

## 🎙️ Articulation drill

Record two minutes: **"Explain middleware, and why the order matters."**

⭐ **Define it mechanically first, because that makes everything after it obvious:** **"a middleware is
a function that takes the next handler and returns a replacement handler — which is just a decorator.
You fold the list over your dispatch function and you get an onion: every layer sees the request going
in and the response coming out, with the first registered being outermost."**

⭐⭐ **Then make ordering concrete, with failures rather than principles:** *"and the order isn't a
style preference, it's a correctness property, because it's the nesting order. Error handling has to be
outermost — it can only catch what's inside it, so if it's second, an exception from the first layer
escapes to the socket as a connection reset with nothing logged. Logging goes near the outside, or you
have no record of the requests that auth rejected — which is the traffic you most want. CORS has to be
