> default.**

# Part 1 — Replication and the ISR

```
⭐ EACH PARTITION HAS ONE ***LEADER*** AND N−1 ***FOLLOWERS.***
⭐   ⭐ All reads and writes go to the leader. ⭐⭐ FOLLOWERS ARE
⭐   NOT READ REPLICAS — ⭐ they exist for durability, not scale.
⭐   ⭐ (Modern Kafka can serve some fetches from followers for
⭐   rack locality; ⭐⭐ THAT IS A COST OPTIMISATION, NOT A SCALING
⭐   ONE.)

⭐⭐ ***THE ISR IS THE SET OF REPLICAS CAUGHT UP WITH THE
⭐   LEADER.*** ⭐ A follower is in-sync if it has fetched within
⭐   `replica.lag.time.max.ms` (30 s by default).
⭐   ⭐⭐ THE ISR IS ***DYNAMIC***: A SLOW BROKER SILENTLY DROPS
⭐     OUT, AND YOUR DURABILITY GUARANTEE SHRINKS WITH IT
⭐     — ⭐ which is why `UnderReplicatedPartitions` and
⭐     `IsrShrinksPerSec` are the two broker metrics to alarm on.

⭐⭐ ***THE HIGH WATERMARK*** — ⭐ the offset up to which a record
⭐   is present on ***all*** ISR members.
⭐   ⭐⭐ CONSUMERS CANNOT SEE PAST IT. ⭐ And that gives you a fact
⭐   that surprises people:
⭐   ⭐⭐ ***A RECORD CAN BE ACKED TO THE PRODUCER WITH `acks=1`
⭐   AND NEVER BE VISIBLE TO ANY CONSUMER***, ⭐ because the
⭐   leader died before replication and the new leader never had
⭐   it. ⭐⭐ THE PRODUCER'S SUCCESS AND THE CONSUMER'S REALITY
⭐   DISAGREED, AND NOTHING LOGGED AN ERROR.
```

# Part 2 — ⭐⭐ `unclean.leader.election` — CAP as a config flag

```
⭐ THE SITUATION: ⭐ every ISR member for a partition is down.
⭐   ⭐ An out-of-sync replica is alive but ***behind***.

⭐   ⭐⭐ `unclean.leader.election.enable = false` (DEFAULT)
⭐     ⭐⭐ → THE PARTITION GOES ***OFFLINE***. ⭐ Producers and
⭐       consumers both error. ⭐⭐ NO DATA IS LOST. ⭐ You have
⭐       chosen ***C*** over ***A***.
⭐   ⭐⭐ `unclean.leader.election.enable = true`
⭐     ⭐⭐ → THE STALE REPLICA BECOMES LEADER. ⭐ Availability
⭐       returns immediately, ⭐⭐ AND EVERY ACKNOWLEDGED RECORD
⭐       AFTER ITS LAST FETCH IS ***PERMANENTLY GONE***, ⭐ with
⭐       consumers' offsets now pointing past the end of a
⭐       shorter log. ⭐ You have chosen ***A*** over ***C***.

⭐⭐ ⇒ THIS IS DAY 329's CAP THEOREM AS A SINGLE BOOLEAN IN A
⭐   PROPERTIES FILE, ⭐ and it is the cleanest real example there
⭐   is. ⭐⭐ THE DEFAULT IS `false`, WHICH IS CORRECT FOR ANYTHING
⭐   CARRYING BUSINESS FACTS. ⭐ Set it `true` only for a topic
⭐   where a gap is genuinely preferable to a stall — ⭐ metrics,
⭐   clickstream — ⭐⭐ AND WRITE DOWN THAT YOU CHOSE IT.
```

# Part 3 — Retention, and why deletion is later than you think

```
⭐ `retention.ms` (default 7 days) and `retention.bytes`.
⭐   ⭐ Whichever triggers first.

⭐⭐ AND THE MECHANIC PEOPLE GET WRONG: ***RETENTION IS ENFORCED
⭐   PER LOG ***SEGMENT***, NOT PER RECORD.***
⭐   ⭐ A segment is closed when it reaches `segment.bytes` (1 GB)
⭐     or `segment.ms` (7 days).
⭐   ⭐⭐ A SEGMENT IS ONLY ELIGIBLE FOR DELETION WHEN ITS
⭐     ***NEWEST*** RECORD IS OLDER THAN THE RETENTION.
⭐   ⭐⭐ ⇒ SO `retention.ms = 24h` ON A LOW-TRAFFIC TOPIC CAN KEEP
⭐     DATA FOR ***WEEKS***, ⭐ because the active segment has not
⭐     filled or rolled.
⭐   ⭐⭐ ⇒ AND THAT MATTERS THE MOMENT SOMEONE ASKS "IS PERSONAL
⭐     DATA DELETED WITHIN 30 DAYS?" ⭐ — the honest answer is
⭐     "not necessarily", ⭐⭐ AND THE FIX IS TO SET `segment.ms`
⭐     TOO, OR TO NOT PUT PERSONAL DATA IN THE LOG AND USE
⭐     CRYPTO-SHREDDING INSTEAD (DAY 395, DAY 405).
```

# Part 4 — ⭐⭐ Compaction: the log as a table

```
⭐ `cleanup.policy = compact` ⭐ (or `compact,delete`).
⭐   ⭐⭐ KAFKA RETAINS ***THE LATEST VALUE PER KEY***, FOREVER,
⭐   AND DISCARDS SUPERSEDED ONES.
⭐   ⭐ A record with a `null` value is a ***tombstone***: it
⭐     means "this key is deleted", ⭐ and it survives for
⭐     `delete.retention.ms` (24 h) ⭐⭐ SO CONSUMERS HAVE TIME TO
⭐     OBSERVE THE DELETION BEFORE IT VANISHES. ⭐ A consumer
⭐     offline longer than that ***misses the delete entirely***
⭐     and keeps a phantom row.

⭐⭐ ***THE MENTAL MODEL, AND IT IS THE POINT OF THE DAY:***
⭐   ⭐⭐ ***A COMPACTED TOPIC IS A TABLE. READING IT FROM OFFSET 0
⭐   GIVES YOU THE CURRENT STATE OF EVERY KEY.***
⭐   ⭐ A normal topic is a stream of ***changes***; ⭐ a compacted
⭐     topic is the ***current state***. ⭐⭐ SAME LOG, DIFFERENT
⭐     READING — THAT IS THE STREAM-TABLE DUALITY.

⭐⭐ ⇒ AND WHAT IT UNLOCKS: ***A NEW SERVICE CAN BOOTSTRAP ITS
⭐   ENTIRE LOCAL VIEW BY READING THE TOPIC FROM THE BEGINNING,
⭐   THEN STAY CURRENT BY CONTINUING TO READ.*** ⭐ No backfill
⭐   job, no export, no coordination with the owning team.
⭐   ⭐⭐ THAT IS DAY 359's SHAPE ⑦ — DERIVED STORES ARE
⭐   REBUILDABLE — WITH THE INFRASTRUCTURE PROVIDING IT.
⭐ ⭐ Uses: `__consumer_offsets` itself, changelog topics for
⭐   stream state, reference data (products, pricing, feature
⭐   flags), and CDC output (Day 407).
⭐ ⭐ Caveats: ⭐⭐ COMPACTION IS ASYNCHRONOUS AND LAZY — ⭐ the
⭐   active segment is never compacted, so ***duplicate keys are
⭐   normal on read*** and your consumer must be
⭐   last-write-wins by design. ⭐⭐ AND A KEY WITH NO TOMBSTONE IS
⭐   RETAINED FOREVER, SO AN UNBOUNDED KEY SPACE ON A COMPACTED
⭐   TOPIC GROWS WITHOUT LIMIT.
```

# Part 5 — ⭐⭐ Exactly-once, described honestly

```
⭐ WHAT KAFKA TRANSACTIONS ACTUALLY DO:
⭐   ⭐ `init_transactions()` → `begin_transaction()` →
⭐     produce to N topics → ⭐⭐ `send_offsets_to_transaction()`
⭐     → `commit_transaction()`
⭐   ⭐ Consumers set `isolation.level=read_committed` and never
⭐     see records from aborted or in-flight transactions.
⭐   ⭐⭐ ⇒ SO THE ***CONSUMED OFFSET*** AND THE ***PRODUCED
⭐     RECORDS*** COMMIT ATOMICALLY.

⭐⭐ ***WHAT THAT GIVES YOU, STATED PRECISELY: ATOMIC
⭐   READ-PROCESS-WRITE ***WITHIN KAFKA***.*** ⭐ Kafka in, Kafka
⭐   out, offsets included. ⭐ That is a real and useful
⭐   guarantee.

⭐⭐ AND WHAT IT DOES ***NOT*** GIVE YOU — ⭐ this is the part
⭐   that separates the marketing from the engineering:
⭐   ⭐ ❌ Exactly-once when the side effect is an ***HTTP call***.
⭐   ⭐ ❌ Exactly-once when the side effect is an ***email*** or
⭐      an SMS.
⭐   ⭐ ❌ Exactly-once when the side effect is a write to
⭐      ***Postgres***, ⭐ because Postgres is not in the Kafka
⭐      transaction and there is no 2PC between them (Day 341).
⭐   ⭐⭐ ⇒ THE MOMENT AN EXTERNAL SYSTEM IS INVOLVED, YOU ARE
⭐     BACK TO DAY 335's FOUR-LINE IMPOSSIBILITY AND THE ANSWER
⭐     IS IDEMPOTENCY, NOT A FLAG.

⭐ AND THE COST, WHICH IS RARELY MENTIONED:
⭐   ⭐ Transactions add a commit round trip and a marker record
⭐     per partition; ⭐⭐ THROUGHPUT DROPS AND LATENCY RISES,
⭐     TYPICALLY 10–30% ⭐ depending on transaction size.
⭐   ⭐ `read_committed` consumers ⭐⭐ CANNOT READ PAST AN
⭐     ***OPEN*** TRANSACTION — ⭐ so one stuck producer stalls
⭐     every reader of that partition, ⭐⭐ WHICH IS A LIVENESS
⭐     COUPLING PEOPLE DO NOT EXPECT.
⭐   ⭐ `transaction.timeout.ms` bounds it; ⭐ tune it.

⭐⭐ ⇒ ***THE HONEST RECOMMENDATION: MOST PIPELINES ARE BETTER
⭐   SERVED BY AT-LEAST-ONCE PLUS AN IDEMPOTENT SINK*** (DAY
⭐   402's OFFSETS-IN-YOUR-DATABASE PATTERN). ⭐ Use transactions
⭐   when the pipeline is genuinely Kafka→Kafka and correctness
⭐   is worth the throughput. ⭐⭐ SAYING THAT IS WORTH MORE IN AN
⭐   INTERVIEW THAN RECITING THE API.
⭐ ⭐ Python note: ⭐⭐ `confluent-kafka` SUPPORTS TRANSACTIONS.
⭐   `kafka-python` DOES NOT. ⭐ That alone decides the client.
```

# Part 6 — Stream processing in Python, honestly

```
⭐⭐ ***THERE IS NO KAFKA STREAMS FOR PYTHON.*** ⭐ This is a real
⭐   ecosystem gap and pretending otherwise wastes months.
⭐   ⭐ Kafka Streams and ksqlDB are JVM. ⭐ They give you
⭐     windowing, joins, state stores backed by changelog topics,
⭐     and exactly-once — ⭐⭐ AND NONE OF IT IS AVAILABLE TO YOU
⭐     FROM PYTHON.

⭐ THE REAL OPTIONS, RANKED:
⭐ ① ⭐⭐ ***PLAIN CONSUMERS PLUS YOUR OWN STATE IN POSTGRES OR
⭐    REDIS.*** ⭐ Unglamorous, ⭐⭐ AND CORRECT FOR THE LARGE
⭐    MAJORITY OF WHAT PEOPLE CALL STREAM PROCESSING, ⭐ which is
⭐    usually "enrich and write somewhere". ⭐ Combine with Day
⭐    402's offsets-in-the-same-transaction and you have
⭐    effectively-once with tools you already operate.
⭐ ② ⭐ ***FLINK VIA PyFlink*** — real windowing and state,
⭐    ⭐⭐ AND A JVM CLUSTER TO OPERATE PLUS A PYTHON/JAVA BOUNDARY
⭐    THAT LEAKS INTO YOUR STACK TRACES.
⭐ ③ ⭐ ***Faust / faust-streaming*** — the original is
⭐    effectively unmaintained; ⭐⭐ THE FORK IS COMMUNITY-RUN.
⭐    ⭐ Evaluate its commit activity ***today*** before adopting;
⭐    ⭐⭐ DO NOT INHERIT A DEAD FRAMEWORK AT THE CENTRE OF YOUR
⭐    PIPELINE.
⭐ ④ ⭐ ***Quix / Bytewax*** — newer Python-native options worth
⭐    a look for windowed work.

⭐⭐ ⇒ AND THE DESIGN CONSEQUENCE: ***IF YOUR PIPELINE NEEDS
⭐   HEAVY WINDOWED JOINS AND EXACTLY-ONCE STREAM STATE, PYTHON
⭐   IS A WEAKER STORY AND YOU SHOULD SAY SO — EITHER ACCEPT A
⭐   JVM COMPONENT OR DESIGN THE PIPELINE SO IT IS NOT NEEDED.***
⭐   ⭐ Most teams can do the second.
```

# Part 7 — When Kafka is the wrong choice

```
⭐ ① ⭐⭐ LOW VOLUME. ⭐ At 100 messages/second, Kafka is an
⭐    operational commitment — ⭐ ZooKeeper or KRaft, brokers,
⭐    rebalances, retention, monitoring — ⭐⭐ FOR A WORKLOAD SQS
⭐    HANDLES WITH ZERO OPERATIONS AND A $0.40/MILLION BILL.
⭐ ② ⭐ PER-MESSAGE SEMANTICS: ⭐⭐ RETRY WITH BACKOFF, DELAY,
⭐    PRIORITY, PER-MESSAGE NACK. ⭐ Kafka has none of these
⭐    (Day 404).
⭐ ③ ⭐ SMALL NUMBER OF CONSUMERS, NO REPLAY REQUIREMENT — ⭐ you
⭐    are paying for the log and using it as a queue.
⭐ ④ ⭐⭐ NO ONE TO OPERATE IT. ⭐ Same question as Day 390's
⭐    Kubernetes one: ⭐ MSK or Confluent Cloud removes most of
⭐    it, ⭐⭐ AND SELF-MANAGED KAFKA IS A TEAM'S WORTH OF WORK.

⭐⭐ ⇒ AND THE POSITIVE STATEMENT: ***TAKE KAFKA WHEN YOU NEED
⭐   REPLAY, MULTIPLE INDEPENDENT CONSUMERS OF THE SAME STREAM,
⭐   ORDERED PER-KEY HISTORY, OR THROUGHPUT A BROKER CANNOT
⭐   REACH.*** ⭐ Those four. ⭐⭐ IF NONE APPLIES, A QUEUE IS
⭐   SIMPLER AND YOU SHOULD SAY SO.
```

# 💬 Interview

**1. ⭐⭐ "What is the ISR and why does it matter?"**
> ⭐ The set of replicas caught up with the leader, where "caught up" means having fetched within
> `replica.lag.time.max.ms`. ⭐⭐ **It matters because every durability guarantee is phrased in terms of
> it, and it's dynamic — a slow broker silently drops out and your guarantee shrinks with it**, which
> is why `UnderReplicatedPartitions` and ISR shrink rate are the broker metrics I alarm on. ⭐ And the
> high watermark gives a fact people find surprising: ⭐⭐ **a record can be acked to the producer with
> `acks=1` and never be visible to any consumer, because the leader died before replication — the
> producer's success and the consumer's reality disagreed and nothing logged an error.**

**2. ⭐⭐ "What's `unclean.leader.election`?"**
> ⭐ It's CAP as a single boolean, and it's the cleanest real example there is. ⭐⭐ **When every in-sync
> replica is down and only a stale one is alive: false — the default — takes the partition offline,
> producers and consumers both error, and no data is lost. True elects the stale replica, availability
> returns immediately, and every acknowledged record after its last fetch is permanently gone.** ⭐ So
> false is choosing consistency and true is choosing availability, per topic. ⭐ The default is right
> for anything carrying business facts, ⭐⭐ **and I'd only set it true where a gap is genuinely
> preferable to a stall — metrics, clickstream — and write down that we chose it.**

**3. "Explain log compaction."**
> ⭐ Kafka keeps the latest value per key and discards superseded ones, with a null value acting as a
> tombstone. ⭐⭐ **The mental model is that a compacted topic is a table: reading it from offset zero
> gives you the current state of every key, whereas a normal topic is a stream of changes. Same log,
> different reading — that's the stream-table duality.** ⭐ What it unlocks is real: ⭐⭐ **a new service
> can bootstrap its entire local view by reading from the beginning and then stay current by
> continuing to read — no backfill job, no export, no coordination with the owning team.** ⭐ Two
> caveats: ⭐⭐ **compaction is lazy and the active segment is never compacted, so duplicate keys are
> normal on read and consumers must be last-write-wins by design; and a key without a tombstone is
> retained forever, so an unbounded key space grows without limit.**

**4. ⭐⭐ "Does Kafka give you exactly-once?"**
> ⭐ Within Kafka, yes, and I'd state the boundary precisely. ⭐⭐ **Transactions commit the produced
> records and the consumed offsets atomically, and `read_committed` consumers never see aborted or
> in-flight data — so you get atomic read-process-write where the input is Kafka and the output is
> Kafka.** ⭐ What it doesn't give you is exactly-once when the side effect is an HTTP call, an email,
> or a write to Postgres, ⭐⭐ **because Postgres isn't in the Kafka transaction and there's no 2PC
> between them — so the moment an external system is involved you're back to the impossibility, and
> the answer is idempotency, not a flag.** ⭐ There's also a cost people skip: ⭐⭐ **10–30% throughput,
> and a `read_committed` consumer cannot read past an *open* transaction, so one stuck producer stalls
> every reader of that partition.** ⭐ My default is at-least-once plus an idempotent sink, with the
> offset stored in my own database.

**5. "Why can retention not delete my data on time?"**
> ⭐⭐ **Because retention is enforced per log segment, not per record — a segment is only eligible for
> deletion when its *newest* record is older than the retention.** ⭐ So on a low-traffic topic, a
> 24-hour retention can hold data for weeks because the active segment hasn't rolled. ⭐⭐ **That matters
> the moment someone asks whether personal data is deleted within thirty days, where the honest answer
> is "not necessarily"** — the fixes are to set `segment.ms` as well, or to keep personal data out of
> the log and use crypto-shredding instead.

**6. ⭐⭐ "How do you do stream processing in Python?"**
> ⭐ Honestly: ⭐⭐ **there is no Kafka Streams for Python, and pretending otherwise wastes months.**
> ⭐ Kafka Streams and ksqlDB are JVM, and they're where windowing, joins and exactly-once state stores
> live. ⭐ So the options are: ⭐⭐ **plain consumers with your own state in Postgres or Redis — which is
> unglamorous and correct for the majority of what people call stream processing, since it's usually
> "enrich and write somewhere"** — PyFlink if you genuinely need windowed state and can operate a JVM
> cluster, or one of the Python-native newcomers. ⭐⭐ **And the design consequence is worth saying out
> loud: if the pipeline needs heavy windowed joins with exactly-once stream state, Python is the
> weaker story, so either accept a JVM component or design so it isn't needed — and most teams can do
> the second.**
