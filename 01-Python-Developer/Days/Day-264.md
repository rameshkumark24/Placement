# Part 1 — ⭐⭐ Why work leaves the request, and the one bad reason

```
⭐⭐ FOUR GOOD REASONS:
⭐   ① ⭐ TOO SLOW to hold a connection for — a 40 s PDF render
⭐   ② ⭐⭐ IT MUST BE RETRIED — an email, a provider call (Day 263)
⭐   ③ ⭐ IT IS ON A CLOCK — expire holds nightly, invoice on the 1st
⭐   ④ ⭐ IT IS CHEAPER IN BULK — one statement for 10,000 rows

⭐⭐ AND ONE BAD REASON, WHICH IS THE COMMON ONE:
⭐   ⑤ ❌ "the endpoint is slow, so let's make it async"
⭐     ⇒ ⭐⭐ YOU HAVE NOT MADE IT FASTER. YOU HAVE MADE IT INVISIBLE.
⭐       The user still waits — now by polling — and the slow query
⭐       has moved to a process with no request timeout, no p99
⭐       panel, and nobody to complain when it degrades.
⭐     ⭐ Measure first (Day 202). Async work you didn't need is a
⭐       second system to operate, forever.
```

```
⭐⭐ TWO SHAPES OF BACKGROUND WORK, WITH DIFFERENT FAILURES:
⭐   ⭐ QUEUED    — an event says "do this one thing"
⭐        ⇒ risk: LOST, or DUPLICATED           (Day 265)
⭐   ⭐⭐ SCHEDULED — a clock says "do everything now due"
⭐        ⇒ ⭐⭐ risk: RAN TWICE · RAN NOWHERE · RAN OVER A GAP

⭐ ⇒ ⭐⭐ TODAY IS THE SECOND, AND IT IS THE HARDER ONE, because a
⭐   queue at least proves the message existed. ⭐ A schedule proves
⭐   nothing: the absence of a run and the absence of work due look
⭐   exactly the same from outside.
```

**The worked example.** `fieldwork` places a *hold* on a technician's slot when a customer starts
booking. Holds expire after 15 minutes. Nothing in the request path can expire them — the customer
who created the hold has closed the tab. So: a job, every minute, forever.

# Part 2 — ⭐⭐ Three replicas, one job

```
⭐⭐ YOU ADD APScheduler IN THE APP'S LIFESPAN. IT WORKS LOCALLY.
⭐   ⇒ ⭐⭐ IN PRODUCTION YOU RUN 3 REPLICAS ⇒ IT RUNS THREE TIMES,
⭐     EVERY MINUTE, FOREVER. ⭐ And staging had one replica, so
⭐     staging was correct — which is why nobody caught it.

⭐⭐ FOUR WAYS OUT, WORST TO BEST:
⭐   ① ❌ "only replica 0 runs it" ⇒ ⭐ which pod is 0 mid-rollout?
⭐        And during a rollout, sometimes none of them is.
⭐   ② ⭐ A DEDICATED SCHEDULED WORKLOAD (k8s CronJob, ECS scheduled
⭐        task, a `worker-cron` process type)
⭐        ⇒ ⭐⭐ ONE PROCESS BY CONSTRUCTION — the best answer when
⭐          the platform gives it to you. ⭐ Still needs Parts 3–6.
⭐   ③ ⭐⭐ AN ADVISORY LOCK — everyone tries, one wins:
⭐        SELECT pg_try_advisory_lock(hashtext('expire_holds'));
⭐        ⇒ ⭐ NON-BLOCKING: the losers get `false` and exit.
⭐        ⇒ ⭐⭐ SESSION-SCOPED, so it is held for the whole run and
⭐          RELEASED AUTOMATICALLY IF THE PROCESS DIES (Day 196).
⭐          A row-based `is_running` flag does NOT have that
⭐          property — ⭐⭐ a crash leaves it stuck at `true` and
⭐          the job never runs again until a human notices.
⭐   ④ ⭐ A scheduler with a shared store (Celery beat as a single
⭐        process, Temporal, an external trigger hitting an endpoint)
```

```
⭐⭐ THREE THINGS THE CLOCK DOES TO YOU:

⭐   ① ⭐⭐ THE OVERLAP — the 02:00 run is still going at 02:01.
⭐        ⇒ Two runs, same rows, at the same time.
⭐        ⇒ ⭐ The advisory lock already fixes it: run two finds it
⭐          held and exits. ⭐⭐ BUT LOG AND COUNT THE SKIP — a job
⭐          that silently skips every night is a job you believe is
⭐          running. ⭐ A rising skip count is your early warning
⭐          that the duration crossed the interval.

⭐   ② ⭐⭐ THE MISSED RUN — the box was down at 02:00.
⭐        ⇒ ⭐⭐ CRON DOES NOT CATCH UP. 03:00 is an ordinary run,
⭐          and 02:00 simply never happened. ⭐ No error anywhere.
⭐        ⇒ ⭐⭐ PART 3 IS THE ONLY REAL FIX.

⭐   ③ ⭐ THE DST HOUR — 02:30 happens twice, or not at all.
⭐        ⇒ ⭐⭐ SCHEDULE IN UTC, ALWAYS. Convert for humans at the
⭐          edge. ⭐ A "runs at 2 a.m. local" schedule runs twice a
⭐          year twice, and once a year not at all.
```

# Part 3 — ⭐⭐ The watermark, and why a time window is a bug

```python
# ❌ THE WINDOW EVERY TUTORIAL WRITES
cutoff = datetime.now(UTC) - timedelta(hours=24)
rows = session.scalars(select(Hold).where(Hold.created_at > cutoff))
```

```
⭐⭐ WHY IT IS WRONG, IN THREE STEPS:
⭐   ① The job does not run for 30 hours — a bad deploy, an outage,
⭐     a lock held by a hung run.
⭐   ② ⭐⭐ THE ROWS IN THE 6-HOUR GAP ARE NEVER PROCESSED. The next
⭐     run's window begins after them, and they fall through.
⭐   ③ ⭐ NOTHING ERRORS. Those holds sit forever, blocking slots
⭐     nobody booked, and you find them in a support ticket in March.

⭐⭐ THE FIX IS TO TRACK ***PROGRESS***, NOT TIME:
```

```sql
CREATE TABLE job_runs (
  job_name    text PRIMARY KEY,
  watermark   timestamptz NOT NULL,   -- ⭐⭐ how far we have PROCESSED
  last_ok_at  timestamptz NOT NULL,   -- ⭐ how recently we SUCCEEDED
  last_error  text,
  runs_total  bigint NOT NULL DEFAULT 0
);
```

```
⭐⭐ THE TWO COLUMNS DO DIFFERENT JOBS, AND CONFLATING THEM IS THE
⭐   MISTAKE: `watermark` decides WHAT TO PROCESS NEXT.
⭐   `last_ok_at` decides WHETHER TO PAGE SOMEONE (Part 6).
⭐   ⇒ ⭐ A job can succeed while making no progress. That is a bug,
⭐     and only two separate columns can show it to you.

⭐⭐ THE RULE THAT MAKES IT CORRECT:
⭐   ***THE WATERMARK MOVES IN THE SAME TRANSACTION AS THE WORK.***
⭐   ⇒ ⭐ Move it FIRST, then crash ⇒ rows SKIPPED. Silent.
⭐   ⇒ ⭐ Move it AFTER, in its own transaction, then crash ⇒ rows
⭐     REPROCESSED — which is fine, IF Part 4 is done.
⭐   ⇒ ⭐⭐ MOVE IT IN THE SAME TRANSACTION AND THERE IS NO GAP.
⭐     ⭐ This is the same shape as the outbox (Day 263): when two
⭐       writes must agree, make them ONE write.
```

```
⭐⭐ THE COLUMN YOU WATERMARK ON HAS THREE REQUIREMENTS:
⭐   ⭐ INDEXED  — or every run seq-scans the table (Day 189)
⭐   ⭐ MONOTONIC — set by the DATABASE (`now()`), not by an app
⭐     process. ⭐⭐ THREE REPLICAS HAVE THREE CLOCKS; a row written
⭐     by the replica whose clock is 400 ms slow lands BEHIND a
⭐     watermark you already moved, and is never seen.
⭐   ⭐ COMPARED WITH `>=`, NOT `>` — timestamps tie, and `>` drops
⭐     every row that shares the exact watermark instant.
⭐     ⇒ ⭐⭐ WHICH MEANS YOU WILL REPROCESS SOME ROWS. On purpose.
⭐       Which is Part 4's entire job.
```

# Part 4 — ⭐⭐ Idempotent, because it *will* run twice

```
⭐⭐ ASSUME TWO RUNS. IT WILL HAPPEN: a redelivery, an overlap, a
⭐   `>=` tie, and — the one people forget — ⭐⭐ YOU, RE-RUNNING IT
⭐   BY HAND AT 3 A.M. DURING AN INCIDENT, because that is when
⭐   re-running a job is the obvious thing to do.
```

```sql
-- ❌ NOT IDEMPOTENT: the side effect is driven by a SELECT
--    rows = SELECT ... WHERE expires_at < now();   (then loop, expire, email)

-- ⭐⭐ IDEMPOTENT: the guard lives in the WHERE clause
UPDATE holds
   SET status = 'expired', expired_at = now()
 WHERE expires_at < :run_started_at
   AND status = 'active'            -- ⭐⭐ THE GUARD
 RETURNING id, customer_id;         -- ⭐ drives the side effects
```

```
⭐⭐ WHY THIS IS THE WHOLE LESSON:
⭐   ⭐ The SECOND run matches ***ZERO ROWS***. Not "matches and
⭐     overwrites harmlessly" — MATCHES NOTHING. So `RETURNING`
⭐     yields nothing, so ⭐⭐ THE EMAILS IN THE NEXT STEP ARE
⭐     ALSO ZERO, without a single extra line of code.

⭐⭐ THE PATTERN, GENERALISED — WRITE THIS ONE DOWN:
⭐   ***DRIVE SIDE EFFECTS FROM WHAT THE WRITE ACTUALLY CHANGED,
⭐      NEVER FROM WHAT YOU SELECTED BEFOREHAND.***
⭐   ⇒ ⭐ SELECT-then-loop-then-UPDATE is also a TOCTOU race: the
⭐     customer completes the booking between your SELECT and your
⭐     UPDATE, and you expire a hold that is now a confirmed job.
⭐   ⇒ ⭐⭐ THE `AND status = 'active'` GUARD FIXES BOTH PROBLEMS
⭐     AT ONCE — the second run and the concurrent writer.
```

```
⭐ AND THE SIDE EFFECTS THEMSELVES: the UPDATE is idempotent, the
⭐   EMAIL IS NOT. ⭐⭐ SO THE EMAIL DOES NOT GO IN THIS JOB —
⭐   IT GOES IN THE OUTBOX (Day 263), in the same transaction,
⭐   and the relay owns delivery. ⭐ The job's only output is a
⭐   state change and a row. That is what makes it re-runnable.
```

# Part 5 — ⭐⭐ The 40-minute transaction that takes down a database it barely touches

```
⭐   BEGIN;
⭐     -- 40 minutes updating 4,000,000 rows
⭐   COMMIT;

⭐ ⇒ ⭐⭐ FOR 40 MINUTES THE xmin HORIZON DOES NOT MOVE, SO
⭐   AUTOVACUUM CANNOT REMOVE DEAD TUPLES ***ANYWHERE IN THE
⭐   DATABASE*** (Day 194).
⭐   ⇒ ⭐ Your hottest OLTP table bloats. Index scans read more
⭐     pages. Plans drift. p99 climbs on endpoints that have
⭐     nothing to do with this job.
⭐   ⇒ ⭐⭐ AND THE INCIDENT LOOKS NOTHING LIKE "THE NIGHTLY JOB".
⭐     It looks like "the API got slow around 2 a.m. for no reason",
⭐     which is the hardest kind of incident there is.

⭐ ⭐⭐ SECOND COST: 4M rows in one transaction is one enormous
⭐   commit, one enormous WAL burst (Day 188), and if it fails at
⭐   minute 39 ⇒ ⭐⭐ ALL OF IT ROLLS BACK AND YOU START AT ZERO.
```

```python
run_started_at = now_from_db(session)      # ⭐⭐ CAPTURED ONCE — see below
while True:
    with session.begin():                          # ⭐ ONE TXN PER CHUNK
        ids = session.scalars(
            select(Hold.id)
            .where(Hold.expires_at < run_started_at, Hold.status == "active")
            .order_by(Hold.id)                     # ⭐⭐ KEYSET, not OFFSET
            .limit(1_000)
            .with_for_update(skip_locked=True)     # ⭐ Day 196
        ).all()
        if not ids:
            break
        expire_and_enqueue(session, ids)           # ⭐ update + outbox rows
        bump_watermark(session, "expire_holds", run_started_at)
    time.sleep(0.05)                               # ⭐ leave I/O for users
```

```
⭐⭐ FOUR DETAILS, EACH OF WHICH IS A BUG IF YOU MISS IT:
⭐   ① `run_started_at` IS CAPTURED ONCE. ⭐⭐ Use `now()` inside the
⭐     loop and the target set moves as you work — new holds keep
⭐     becoming due, and ⭐⭐ ON A BUSY SYSTEM THE JOB NEVER
⭐     TERMINATES. It just runs until someone kills it.
⭐   ② ORDER BY id + LIMIT, ⭐⭐ NEVER OFFSET — OFFSET 900000 reads
⭐     and throws away 900,000 rows (Day 260), so each chunk is
⭐     slower than the last and the job is quadratic.
⭐   ③ `SKIP LOCKED` ⇒ a row locked by a live user request is left
⭐     for the next run instead of blocking the whole chunk.
⭐   ④ ⭐ THE SLEEP IS NOT POLITENESS — it is what stops a bulk job
⭐     from saturating disk I/O and pushing every user query's
⭐     latency up while it runs.
```

# Part 6 — ⭐⭐ Proving it ran

```
⭐⭐ THE FAILURE MODE THAT DEFINES SCHEDULED WORK:
⭐   ***IT DOES NOT FAIL. IT STOPS.***
⭐   ⭐ A job that raises pages you. ⭐⭐ A JOB WHOSE CRON ENTRY WAS
⭐     DROPPED IN A HELM REFACTOR RAISES NOTHING, FOREVER, and your
⭐     error rate stays at zero the whole time.

⭐⭐ SO YOU ALERT ON THE ABSENCE OF SUCCESS, NOT ON ERRORS:
⭐   ① ⭐⭐ DEAD-MAN — now() − last_ok_at > 2 × interval ⇒ PAGE.
⭐        ⭐ This one alert catches: the deleted cron, the stuck
⭐          lock, the crash loop, the pod that never scheduled,
⭐          and the credential that expired. ⭐⭐ IT IS THE SINGLE
⭐          HIGHEST-VALUE ALERT IN THE WHOLE SYSTEM.
⭐   ② ⭐ DURATION p95 — the number that tells you, a month early,
⭐        that you are heading for a permanent overlap.
⭐   ③ ⭐ ROWS AFFECTED — and ⭐⭐ ALERT ON ZERO IF ZERO IS UNUSUAL.
⭐        "Processed 0 rows" is exactly what a broken filter, a
⭐        wrong watermark, or an empty tenant looks like, and it
⭐        is reported as a SUCCESS by every job runner there is.
⭐   ④ ⭐⭐ BACKLOG — count of rows that are DUE but not yet done.
⭐        ⇒ ⭐⭐ THE ONLY METRIC THAT MEASURES THE OUTCOME rather
⭐          than the machinery. Every other number can look
⭐          healthy while this one climbs.
```

```
⭐ AND TWO OPERATIONAL HABITS:
⭐   ⭐ A RUN ID in every log line of the run, so one run's story
⭐     can be read out of a shared log stream.
⭐   ⭐⭐ A RUNBOOK LINE PER ALERT: what it means, the first query
⭐     to run, and ⭐ whether it is safe to re-run by hand — which,
⭐     if Part 4 is done, is always "yes", and that is the point
⭐     of Part 4.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Moving slow work to a job instead of measuring it | You made it invisible, not fast. Profile first (Day 202). |
| Scheduling inside the web app | N replicas run it N times. Use a cron workload or an advisory lock. |
| "Only replica 0 runs it" | Undefined during rollouts — sometimes zero replicas run it. |
| An `is_running` boolean column as a lock | A crash leaves it `true` forever. Session advisory locks release on disconnect. |
| A blocking `pg_advisory_lock` | Every replica queues and then runs in sequence. Use `pg_try_advisory_lock`. |
| Not counting skipped runs | A job that skips every night looks identical to one that runs. |
| Scheduling in local time | DST runs it twice a year twice, and once a year never. |
| A rolling time window (`last 24 h`) | A missed run creates a permanent gap that nothing reports. |
| Watermark committed separately from the work | Before → skipped rows; after → duplicates. Same transaction. |
| Watermarking on an app-generated timestamp | Replicas have different clocks; slow-clock rows land behind the watermark. |
| `>` on the watermark | Ties are dropped. Use `>=` and make the work idempotent. |
| Driving side effects from a prior `SELECT` | TOCTOU: the row changed underneath you. Drive from `RETURNING`. |
| Sending email directly from the job | Not idempotent, so the job stops being re-runnable. Outbox it. |
| One transaction for millions of rows | Freezes the xmin horizon and bloats the whole database (Day 194). |
| `now()` re-evaluated inside the chunk loop | The target set keeps growing; the job never terminates. |
| `OFFSET` for chunking | Quadratic. Keyset pagination on the primary key. |
| No `SKIP LOCKED` | One user-held row blocks an entire chunk. |
| Alerting only on job errors | The dominant failure is silence. Alert on stale `last_ok_at`. |
| Treating "0 rows processed" as success | It is what a broken filter looks like. |
| No backlog metric | Every machinery metric can be green while the work piles up. |

## Interview questions

**Q: You have three replicas and a job that must run once a minute. How?**

> Ideally a dedicated scheduled workload so there is exactly one process by construction. If that
> isn't available, all replicas try `pg_try_advisory_lock` on a stable key and only the winner runs —
> non-blocking, so the losers exit immediately rather than queueing up to run it again in turn. I'd
> use a session-scoped advisory lock rather than a flag column specifically because it's released if
> the process dies; a boolean column that says `is_running = true` after a crash means the job never
> runs again until someone notices, which could be weeks.

**Q: Why is "process everything from the last 24 hours" wrong?**

> Because it assumes the job ran. If it didn't run for thirty hours — a bad deploy, an outage, a run
> that hung — the rows in the six-hour gap are never processed by anything, and nothing errors. I
> track a watermark instead: a persisted marker of how far I've actually processed, moved in the same
> transaction as the work. Then a missed run just means the next one does more, which is the correct
> behaviour and requires no intervention.

**Q: Why must the watermark move in the same transaction as the work?**

> Because otherwise it's the dual-write problem again. Move it first and a crash skips rows silently;
> move it afterwards in its own transaction and a crash reprocesses rows. One transaction removes the
> gap entirely. And since I'd rather have the duplicate risk than the skip risk anyway, the job is
> written to be idempotent regardless — the guard goes in the `WHERE` clause, so a second run matches
> zero rows rather than doing the work twice.

**Q: How do you know a background job is healthy?**

> Not by its error rate, because the dominant failure mode is that it stops rather than fails —
> a deleted cron entry raises nothing, forever. So the primary alert is a dead-man check on
> `last_ok_at`: if a job hasn't succeeded in more than twice its interval, page. On top of that,
> duration p95 to see an overlap coming, rows-affected with an alert if zero is unusual, and a
> backlog count of items that are due but not done — which is the only one of the four that measures
> the outcome rather than the machinery.

**Q: What's wrong with a job that processes four million rows in one transaction?**

> It holds an open snapshot for the whole run, which freezes the xmin horizon so autovacuum can't
> clean dead tuples anywhere in the database. The visible symptom is unrelated OLTP endpoints getting
> slower at 2 a.m. Chunked commits fix it — a thousand rows per transaction, keyset-ordered so it's
> resumable, `SKIP LOCKED` so a user-held row doesn't block the chunk, and a small sleep so a bulk
> job doesn't saturate I/O for everyone else.

## 🎙️ Articulation drill

**Two minutes: "How do you run a nightly job safely?"**

Start with the shape of the risk, because it's what separates this from ordinary code: **a scheduled
job has nobody watching it, so all of its failures are silent.** Then the four problems in order.
One: three replicas run it three times, and staging didn't show it because staging had one replica —
so a dedicated cron workload, or a non-blocking advisory lock that's released automatically if the
process dies. Two: **a time window is a bug** — one missed run creates a permanent gap that nothing
reports, so track a watermark, and move it in the same transaction as the work, because otherwise
it's the dual write again. Three: it will run twice, so **the guard goes in the `WHERE` clause and
side effects are driven by `RETURNING`, never by a prior `SELECT`** — which also closes the TOCTOU
race with live users for free. Four: never one giant transaction, because a forty-minute snapshot
freezes the xmin horizon and bloats the whole database, and the incident looks like "the API got slow
at 2 a.m. for no reason." Close on observability: **you alert on the absence of success, not on
errors, because the job that was deleted from the manifest raises nothing forever** — plus a backlog
metric, which is the only number that measures the work instead of the machinery.
