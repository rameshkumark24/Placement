**P-314** · 🚦 **Rate limiter** — ⭐⭐ four algorithms, one interface, and the boundary burst

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a fixed window lets through twice the limit across its boundary, and
> that is not an edge case — it is the exact instant every scheduled client in the world fires, which
> is why "100 per minute" quietly means "200 in one second" at 12:00:00.**
>

> algorithms compared honestly, and the questions that follow.

# Part 1 — ⭐ 0–5: scope

```
⭐⭐ FIVE QUESTIONS:
⭐   ① ⭐⭐ "WHAT IS THE LIMIT ***PER***?" ⇒ per user, per IP,
⭐        per API key, per endpoint, or a combination.
⭐        ⭐⭐ THE KEY DESIGN IS THE ACTUAL DESIGN, and per-IP
⭐        limits break NAT'd offices while per-user limits do
⭐        nothing against a login-brute-force from one IP.
⭐   ② ⭐ "Should bursts be allowed?" ⇒ ⭐⭐ DECIDES TOKEN
⭐        BUCKET VS SLIDING LOG. A hard "no more than N per
⭐        second, ever" is a different algorithm from "N per
⭐        minute, spend it how you like."
⭐   ③ ⭐ "Single process, or a fleet?" ⇒ in-memory vs Redis.
⭐   ④ ⭐ "Reject, or queue and delay?"
⭐   ⑤ ⭐ "Do different tiers have different limits?"

⭐ ASSUMED: per (api_key, endpoint), small bursts allowed,
⭐ a fleet, reject with 429, tiers yes.
⭐⭐ OUT: billing, quota accounting, DDoS (that is upstream).
```

# Part 2 — ⭐⭐ One interface

```python
@dataclass(frozen=True)
class Decision:
    allowed: bool
    remaining: int
    retry_after: float | None     # ⭐⭐ SECONDS, and see Part 6

class RateLimiter(Protocol):
    def check(self, key: str, cost: int = 1) -> Decision: ...
```

```
⭐⭐ THREE THINGS IN THAT SIGNATURE ARE DELIBERATE:
⭐   ⭐ ⭐⭐ `cost` — not every request is worth one. ⭐ A bulk
⭐     endpoint costs 10; a health check costs 0. ⭐⭐ ADDING
⭐     THIS LATER MEANS CHANGING EVERY IMPLEMENTATION AND EVERY
⭐     CALLER, so it goes in on day one.
⭐   ⭐ IT RETURNS A `Decision`, NOT A BOOL — ⭐⭐ BECAUSE THE
⭐     CALLER MUST SET `Retry-After` AND `X-RateLimit-*`, AND A
⭐     BOOL CANNOT CARRY THAT.
⭐   ⭐ IT DOES NOT RAISE — ⭐ the limiter decides, the web
⭐     layer converts to 429 (Day 257).
```

# Part 3 — ⭐⭐ The four algorithms, honestly

```
⭐⭐ ① FIXED WINDOW — a counter per (key, minute).
⭐   ⭐ + trivial, one integer, cheapest possible
⭐   ⭐⭐ − ***THE BOUNDARY BURST***: 100 requests at 11:59:59.9
⭐        and 100 at 12:00:00.1 ⇒ ⭐⭐ 200 IN 200 MILLISECONDS
⭐        WITH THE LIMIT NEVER EXCEEDED.
⭐   ⇒ ⭐ And this is not theoretical: ⭐⭐ EVERY CRON, EVERY
⭐     SCHEDULED CLIENT AND EVERY RETRY-AT-THE-TOP-OF-THE-MINUTE
⭐     FIRES AT EXACTLY THAT INSTANT, so the pathological case
⭐     is the normal case.

⭐⭐ ② SLIDING LOG — a sorted set of timestamps per key.
⭐   ⭐ + exact, no burst, ⭐ trivially explains itself
⭐   ⭐⭐ − MEMORY IS O(LIMIT) ***PER KEY***. ⭐ 10,000 users ×
⭐        1,000/hour = 10 million timestamps. ⭐ Fine at small
⭐        limits, fatal at large ones.

⭐⭐ ③ SLIDING WINDOW COUNTER — weight the previous window:
⭐        count = cur + prev × (1 − elapsed_fraction)
⭐   ⭐ + ⭐⭐ TWO INTEGERS PER KEY, AND THE BOUNDARY BURST IS
⭐        GONE. ⭐ The usual right answer.
⭐   ⭐ − approximate: it assumes the previous window's traffic
⭐        was uniform, ⭐ so it can be slightly wrong in both
⭐        directions — ⭐⭐ SAY THAT, because knowing your
⭐        approximation's direction is the senior part.

⭐⭐ ④ TOKEN BUCKET — capacity + refill rate.
⭐   ⭐ + ⭐⭐ EXPRESSES ***BURST*** AND ***SUSTAINED RATE***
⭐        SEPARATELY, which the others cannot: "60/minute but up
⭐        to 10 at once" is one line.
⭐   ⭐ + two numbers per key (tokens, last_refill), ⭐ and
⭐        refill is computed lazily on read — no timer.
⭐   ⭐ − a full bucket after idle means a burst is allowed,
⭐        ⭐ which is the feature, and occasionally the bug.
⭐   ⇒ ⭐⭐ LEAKY BUCKET IS THE SAME STRUCTURE WITH SMOOTHING
⭐     INSTEAD OF BURSTING — mention it, do not implement it.

⭐ ⇒ ⭐⭐ THE ANSWER: ***TOKEN BUCKET FOR APIs*** (bursts are
⭐   real and desirable), ***SLIDING WINDOW COUNTER WHEN THE
⭐   LIMIT IS A HARD PROMISE***, and ⭐ fixed window only when
⭐   you can prove the boundary does not matter.
```

# Part 4 — ⭐⭐ 15–30: token bucket, in-process then distributed

```python
class TokenBucket:
    def __init__(self, capacity: int, refill_per_sec: float,
                 clock: Callable[[], float] = time.monotonic):
        self._cap, self._rate, self._clock = capacity, refill_per_sec, clock
        self._state: dict[str, tuple[float, float]] = {}   # tokens, last
        self._lock = Lock()

    def check(self, key: str, cost: int = 1) -> Decision:
        with self._lock:
            now = self._clock()
            tokens, last = self._state.get(key, (float(self._cap), now))
            tokens = min(self._cap, tokens + (now - last) * self._rate)
            if tokens >= cost:                       # ⭐⭐ CHECK+ACT, LOCKED
                self._state[key] = (tokens - cost, now)
                return Decision(True, int(tokens - cost), None)
            self._state[key] = (tokens, now)
            wait = (cost - tokens) / self._rate
            return Decision(False, int(tokens), wait)
```

```
⭐⭐ FOUR DETAILS:
⭐   ⭐ ⭐⭐ LAZY REFILL — no background timer, no thread. ⭐ The
⭐     refill is arithmetic done at read time, which is why this
⭐     algorithm scales.
⭐   ⭐ `min(cap, …)` ⇒ ⭐⭐ TOKENS DO NOT ACCUMULATE FOREVER;
⭐     without it, a key idle for a day gets 86,400 requests.
⭐   ⭐ `monotonic`, not `time.time()` — ⭐⭐ AN NTP STEP
⭐     BACKWARDS MAKES A WALL-CLOCK LIMITER GRANT INFINITE
⭐     TOKENS OR NONE.
⭐   ⭐ `retry_after` IS COMPUTED, not guessed — ⭐ the client
⭐     can obey it exactly, which is what makes it useful.

⭐⭐ AND THE DISTRIBUTED VERSION (Day 208): ⭐ the same
⭐   arithmetic in a Lua script on Redis, so read-modify-write
⭐   is atomic on the server.
⭐   ⇒ ⭐⭐ WITHOUT ATOMICITY YOU HAVE CHECK-THEN-ACT ACROSS A
⭐     NETWORK (Day 310), AND N REPLICAS EACH ALLOW THE LIMIT —
⭐     so "100/min" becomes "100 × replicas".
⭐   ⇒ ⭐ AND USE ***REDIS'S*** CLOCK, not the app's: ⭐⭐ SIX
⭐     APP SERVERS HAVE SIX SLIGHTLY DIFFERENT CLOCKS, AND A
⭐     LIMITER IS ARITHMETIC ON TIME.
```

# Part 5 — ⭐⭐ 30–40: the questions that follow

```
⭐⭐ ① "WHAT IF REDIS IS DOWN?" ⇒ ⭐⭐ FAIL ***OPEN*** OR
⭐     ***CLOSED***, AND IT IS A BUSINESS DECISION:
⭐     ⭐ fail open ⇒ the limiter stops limiting; ⭐ correct for
⭐       general API protection, since availability beats
⭐       fairness.
⭐     ⭐⭐ FAIL CLOSED ⇒ correct for a login endpoint, where
⭐       the limiter ***is*** the security control.
⭐     ⇒ ⭐ Different limiters, different answers. Say both.

⭐⭐ ② "WHERE DOES IT RUN?" ⇒ ⭐ at the edge (gateway) it
⭐     protects your app; ⭐ in the app it can use identity and
⭐     tier. ⭐⭐ USUALLY BOTH: A COARSE PER-IP LIMIT AT THE
⭐     EDGE AND A PRECISE PER-KEY LIMIT IN THE APP.

⭐⭐ ③ "WHAT DO YOU RETURN?" ⇒ ⭐ 429, `Retry-After`,
⭐     `X-RateLimit-Limit/Remaining/Reset`. ⭐⭐ AND THE RULE:
⭐     ***NEVER LEAK WHETHER THE ACCOUNT EXISTS*** — a login
⭐     limiter that responds differently for known and unknown
⭐     users is an enumeration oracle (Day 258).

⭐⭐ ④ "HOW DO YOU LIMIT LOGINS?" ⇒ ⭐⭐ TWO LIMITERS, AND
⭐     THIS IS THE ONE PEOPLE GET WRONG: per-IP catches one
⭐     attacker; ⭐ per-account catches a distributed attack on
⭐     one user — ⭐⭐ AND PER-ACCOUNT ALONE IS A DENIAL OF
⭐     SERVICE ON YOUR OWN USERS (Day 258), because I can lock
⭐     you out by failing your password.

⭐⭐ ⑤ "HOW DO YOU TEST IT?" ⇒ ⭐ a fake clock, ⭐⭐ AND A
⭐     CONCURRENCY TEST ASSERTING ***EXACTLY*** N SUCCEED OUT OF
⭐     N + 50 (Day 310) — not "at most N".
```

# Part 6 — ⭐ Details that show experience

```
⭐   ⭐⭐ `Retry-After` WITH JITTER. ⭐ If you tell 5,000 clients
⭐     to retry in 30 seconds, ⭐⭐ THEY ALL RETURN IN THE SAME
⭐     SECOND (Day 265) — you built a synchronised herd with a
⭐     header. ⭐ Return a jittered value.
⭐   ⭐ COST-AWARE LIMITS — an expensive endpoint costs more
⭐     tokens; ⭐ the `cost` parameter from Part 2 already
⭐     supports it.
⭐   ⭐ ⭐⭐ SHADOW MODE FIRST — log what you ***would*** have
⭐     rejected for a week before enforcing (Day 291). ⭐ Every
⭐     rate limiter turned on without this rejects a legitimate
⭐     integration on day one.
⭐   ⭐ AN ALLOWLIST for internal services, ⭐ and monitoring:
⭐     rejection rate per key — ⭐⭐ A SUDDEN RISE IS EITHER AN
⭐     ATTACK OR A CUSTOMER'S DEPLOY, and you want to know which
⭐     within minutes.
⭐ ⇒ ⭐ CLOSE: three tests; one change (per-tier config from a
⭐   database); ⭐⭐ AT 100×: one Redis key per user is a hot
⭐   key — shard by key hash, or accept approximate limiting at
⭐   the edge.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Not asking what the limit is *per* | The key design is the actual design; per-IP breaks NAT, per-user misses brute force. |
| Fixed window without naming the boundary burst | 2× the limit, at exactly the instant every scheduled client fires. |
| Sliding log at large limits | O(limit) memory per key; ten million timestamps. |
| Presenting the sliding window counter as exact | It assumes uniform prior traffic; say which direction it errs. |
| No `cost` parameter | Adding it later changes every implementation and caller. |
| Returning a bool | The caller needs `Retry-After` and remaining. |
| Unbounded token accumulation | A key idle for a day gets 86,400 requests. |
| `time.time()` | An NTP step backwards grants infinite tokens or none. |
| Read-modify-write across the network | Check-then-act, so N replicas each allow the full limit. |
| The app's clock in a distributed limiter | Six servers, six clocks, and the limiter is arithmetic on time. |
| No fail-open/closed decision | It's a business decision, and it differs for login versus general API. |
| One limiter for login | Per-IP alone misses distributed attacks; per-account alone is a DoS on your users. |
| Different responses for known and unknown accounts | An enumeration oracle. |
| `Retry-After` without jitter | You built a synchronised herd with a header. |
| Enforcing without shadow mode | You reject a legitimate integration on day one. |
| `assert successes <= N` | Passes when everything fails. Assert exactly N. |

## Interview questions

**Q: Which algorithm and why?**

> Token bucket for a general API, because it's the only one that expresses burst and sustained rate
> separately — "sixty a minute but up to ten at once" is one line, and real clients are bursty. Sliding
> window counter when the limit is a hard promise, because it removes the boundary burst for two
> integers per key. Sliding log only at small limits, since it's O(limit) memory per key. And fixed
> window only if I can prove the boundary doesn't matter — which is rarely true, because every cron and
> scheduled client fires at the top of the minute, so the pathological case is the normal case.

**Q: What's the boundary burst?**

> A fixed window counts per calendar minute, so a hundred requests at 11:59:59.9 and another hundred at
> 12:00:00.1 is two hundred in two hundred milliseconds without ever exceeding the limit. It sounds
> like an edge case and isn't: that instant is exactly when scheduled clients fire, so you get the
> worst case on a schedule. The sliding window counter fixes it by weighting the previous window's
> count by how much of it is still in view — approximate, because it assumes the previous window was
> uniform, and I'd say which direction that errs in.

**Q: How does it work across a fleet?**

> The same arithmetic, executed atomically on Redis in a Lua script. Without atomicity you have
> check-then-act across a network, so each replica independently allows the full limit and "a hundred
> a minute" becomes a hundred times the number of replicas. And it must use Redis's clock rather than
> the application's, because six app servers have six slightly different clocks and a rate limiter is
> arithmetic on time.

**Q: What if Redis is down?**

> A business decision that differs by limiter, and I'd give both. Fail open for general API
> protection, where availability beats fairness and the limiter is there to stop accidents. Fail closed
> for a login endpoint, where the limiter *is* the security control and losing it means unlimited
> credential stuffing. Related: login needs two limiters, not one — per-IP catches a single attacker,
> per-account catches a distributed attack on one user, and per-account alone is a denial of service on
> your own users, because I can lock you out by repeatedly failing your password.

## 🎙️ Articulation drill

**Two minutes.** Start with the design question people skip: **what is the limit *per*?** — per IP
breaks NAT'd offices, per user does nothing against brute force, so it's usually a composite key. Then
the four algorithms, led by the failure: **a fixed window allows twice the limit across its boundary,
and that instant is exactly when every scheduled client fires** — so the pathological case is the
normal case. Sliding log is exact and O(limit) memory per key; the sliding window counter fixes the
burst for two integers and is approximate in a direction you should be able to name; **token bucket is
the answer for APIs because it's the only one that separates burst from sustained rate.** Mention lazy
refill so there's no timer, capping so an idle key doesn't accumulate a day of tokens, and monotonic
time because an NTP step would grant infinite tokens. Then distribution: **the same arithmetic in a
Lua script, or you have check-then-act across a network and every replica allows the full limit** —
using Redis's clock, since six servers have six clocks. Close on the operational questions: **fail
open for general protection and closed for login**, two limiters for login because per-account alone
is a DoS on your own users, jittered `Retry-After` so you don't build a synchronised herd with a
header, and shadow mode first.
