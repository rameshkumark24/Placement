# Day 075

**L-075** · ⭐⭐ **Packaging with `uv` and `pyproject.toml`** — virtualenvs, lockfiles, resolution

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a `requirements.txt` without pinned versions is not a dependency
> specification — it is a wish.** The build that worked yesterday and fails today is almost always an
> unpinned transitive dependency that released a new version overnight.
>
> ⭐ Day 021 said "build once, deploy many" and "pin with a lock file". **Today is how.**

---

# Part 1 — ⭐⭐ Environments

```
⭐⭐ WHY VIRTUALENVS EXIST: without one, every project on the machine shares ONE site-packages.
⭐   ⇒ project A needs django 3, project B needs django 5 ⇒ ⭐⭐ one of them is broken,
⭐        and you find out at runtime.
⭐   ⇒ ⭐ a virtualenv is a directory with its own site-packages and its own interpreter
⭐        symlink. "Activating" it just puts that directory first on PATH.
⭐   ⇒ ⭐⭐ NEVER `pip install` into the system Python. Modern Linux distros now REFUSE
⭐        (PEP 668, "externally-managed-environment") because it broke system tools.
```

```bash
uv venv                      # ⭐⭐ creates .venv — near-instant
source .venv/bin/activate    # ⭐ Windows: .venv\Scripts\activate
uv run python app.py         # ⭐⭐ or skip activation entirely — uv resolves the env itself
python -m pip install x      # ⭐ if using pip: `python -m` guarantees the RIGHT pip (Day 074)
```

⭐⭐ **`uv` is the reason this day is short.** It is a Rust reimplementation of pip, pip-tools,
virtualenv, pipx and pyenv — **10–100× faster, with a real resolver and a lockfile** — and it is
now the default recommendation for new projects. ⭐ **Poetry and PDM are equally valid**; the concepts
below are identical and only the commands differ.

# Part 2 — ⭐⭐ `pyproject.toml`

```toml
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "fastapi>=0.115",          # ⭐⭐ a RANGE — what your code actually needs
    "sqlalchemy>=2.0,<3.0",    # ⭐ cap the major version: 3.0 may break you
    "httpx>=0.27",
]

[project.optional-dependencies]
dev = ["pytest>=8", "mypy>=1.11", "ruff>=0.6"]     # ⭐ installed with `.[dev]`

[project.scripts]
myapp = "myapp.cli:main"       # ⭐⭐ creates a `myapp` command on install

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]                    # ⭐ one file for every tool's config (Days 062, 076)
line-length = 100
[tool.mypy]
strict = true
```

```
⭐⭐ ONE FILE REPLACED FIVE: setup.py, setup.cfg, requirements.txt, MANIFEST.in and
⭐   every tool's own dotfile. ⇒ ⭐ PEP 518/621 standardised it, so it is not a
⭐   tool-specific format — Poetry, PDM, hatch, uv and pip all read the same `[project]`.
```

⚠️ ⭐⭐ **`dependencies` is not a lockfile.** It says what your code *needs*; the lockfile says what
was *installed*. **You need both, and they answer different questions.**

# Part 3 — ⭐⭐ The lockfile — the actual point

```
⭐⭐ TWO FILES, TWO JOBS — and conflating them is the whole problem:

⭐   pyproject.toml   ⇒ ⭐ ABSTRACT: "fastapi>=0.115"  — human-written, ranges, intent
⭐   ⭐⭐ uv.lock       ⇒ ⭐⭐ CONCRETE: "fastapi==0.115.4, starlette==0.38.6, anyio==4.4.0,
⭐                        idna==3.8, ..." — machine-written, EXACT, every transitive
⭐                        dependency, with HASHES.
⭐
⭐ ⇒ ⭐⭐ COMMIT BOTH. The lockfile is what makes the build reproducible.
```

```bash
uv add fastapi               # ⭐ updates pyproject.toml AND the lock, and installs
uv sync                      # ⭐⭐ install EXACTLY the lock — this is what CI and Docker run
uv sync --frozen             # ⭐⭐ fail if the lock is stale, rather than silently updating it
uv lock --upgrade-package httpx    # ⭐ deliberately move ONE dependency
uv export --format requirements-txt > requirements.txt   # ⭐ for tools that need it
```

```
⭐⭐ WHY IT MATTERS — the failure it prevents, concretely:
⭐   `requirements.txt` says `fastapi>=0.115`. It has no transitive pins.
⭐   ⇒ ⭐⭐ Tuesday: a transitive dependency you have never heard of releases 4.5.0.
⭐   ⇒ ⭐⭐ your CI, your teammate's machine and production now install DIFFERENT CODE
⭐        from the same commit. ⇒ ⭐ "it works on my machine" is now literally true.
⭐   ⇒ ⭐⭐ AND: the build is not reproducible, so you cannot bisect, and you cannot
⭐        redeploy last week's release and get last week's behaviour.
```

⭐⭐ **The hashes in a lockfile are a supply-chain control, not a formality:** they mean an installer
verifies the artefact it downloaded is byte-identical to the one that was resolved — **so a
compromised or replaced package on the index fails the install rather than silently shipping.**

⭐ **The version rule:** ⭐⭐ **an application pins (commit the lock); a library does not (declare
ranges).** A library that pins exact versions makes itself uninstallable alongside anything else.

# Part 4 — ⭐ Resolution, and the ecosystem

```
⭐⭐ DEPENDENCY RESOLUTION IS A CONSTRAINT-SATISFACTION PROBLEM, and it is NP-hard:
⭐   A needs C>=2.0 · B needs C<2.0 ⇒ ⭐⭐ NO SOLUTION EXISTS.
⭐   ⇒ ⭐ pip historically installed whatever it saw last and produced a BROKEN environment
⭐        silently; modern pip and uv REFUSE and tell you which packages conflict.
⭐   ⇒ ⭐⭐ refusing is correct: an unsatisfiable constraint set should be a build error,
⭐        not a runtime surprise (⭐ compare Day 054's MRO refusal).
```

| ⭐ Term | ⭐ Meaning |
|---|---|
| ⭐⭐ **wheel** (`.whl`) | ⭐⭐ a **pre-built** artefact — just unzipped. Fast, no compiler needed. |
| **sdist** | source; ⚠️ ⭐ must be *built* on install — needs a compiler for C extensions |
| ⭐ `manylinux` | a wheel tagged as compatible with most Linux distros |
| ⭐ `abi3` | a wheel that works across several Python versions |
| ⭐⭐ editable (`-e .`) | ⭐ your source directory on the path — edits take effect immediately |

⚠️ ⭐⭐ **"It installs on my Mac and fails in the Docker build" is nearly always a missing wheel:** there
is a wheel for macOS/ARM and only an sdist for your slim Linux image, so pip tries to *compile* it and
the image has no compiler. ⭐ **Fix by using a base image with build tools for that stage, or by
choosing a package that ships `manylinux` wheels.**

```dockerfile
# ⭐⭐ THE DOCKER PATTERN — dependencies cached separately from source (Day 021):
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project     # ⭐⭐ this layer is cached until deps change
COPY . .
RUN uv sync --frozen                          # ⭐ then the project itself
```

⭐⭐ **Copying the lockfile before the source is the single highest-value line in a Python
Dockerfile** — it means a code change rebuilds in seconds instead of re-resolving and re-downloading
every dependency.

| ⭐ Tool | ⭐ What it is |
|---|---|
| ⭐⭐ **uv** | ⭐ resolver + installer + venv + Python version manager. Fast. The current default. |
| pip | the baseline installer; ⭐ no lockfile of its own |
| pip-tools | `pip-compile` produces a pinned `requirements.txt` — ⭐ the lockfile for pip users |
| Poetry / PDM | ⭐ full project managers with their own lockfiles |
| pipx / `uv tool` | ⭐⭐ install *applications* (ruff, httpie) in isolated envs, not into your project |
| ⭐ `ruff` | linter + formatter, replaces flake8/isort/black — ⭐ instant |

⚠️ ⭐ **Do not install dev tools into your project's environment** if you can avoid it — `uv tool
install ruff` or `pipx` keeps them isolated, so a tool's dependencies cannot conflict with your
application's.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **No lockfile** | ⭐⭐ The same commit installs different code on different days. |
| Committing only `requirements.txt` with ranges | ⭐ That is intent, not a build. |
| ⭐ Installing into the system Python | ⭐⭐ PEP 668 now refuses. Always a venv. |
| ⭐ Pinning exact versions in a *library* | ⭐ Makes it uninstallable alongside others. |
| No upper bound on a major version | ⭐ A 3.0 release can break you overnight. |
| ⭐⭐ `COPY . .` before installing deps in Docker | ⭐⭐ Every code change re-installs everything. |
| `pip install` at container start | ⭐ Day 021 — slow, networked, unpinned. |
| Ignoring a resolution conflict | ⭐ It is unsatisfiable; refusing is correct. |
| ⭐ Expecting an sdist to install anywhere | ⭐⭐ It needs a compiler. Check for wheels. |
| Dev tools in the project env | ⭐ `uv tool` / `pipx`. |
| `pip` rather than `python -m pip` | ⭐ You may be using another interpreter's pip (Day 074). |

## Interview questions

**Q: What's the difference between `pyproject.toml` and a lockfile?**
> They answer different questions. `pyproject.toml` is abstract and human-written — "fastapi 0.115 or
> later" — and describes what my code needs. The lockfile is concrete and machine-generated: exact
> versions for every direct *and transitive* dependency, with hashes, describing what was actually
> installed. You commit both. Without the lockfile, the same commit installs different code on
> different days, because an unpinned transitive dependency released overnight — so CI, my machine and
> production diverge, "works on my machine" becomes literally true, and you can't redeploy last week's
> release and get last week's behaviour.

**Q: Why do the hashes matter?**
> They're a supply-chain control. The installer verifies that what it downloaded is byte-identical to
> what was resolved, so a package that was replaced or tampered with on the index fails the install
> rather than silently shipping to production. It's cheap and it's the difference between trusting the
> index every time and trusting it once.

**Q: Should a library pin its dependencies?**
> No — applications pin, libraries declare ranges. A library that pins exact versions is
> uninstallable alongside anything else that pins differently, and it makes the *consumer's* resolver
> job impossible. So a library declares the range it genuinely supports, usually with an upper bound
> on the major version, and the application at the top of the tree resolves everything and commits the
> lock.

**Q: Why does resolution sometimes fail outright?**
> Because it's a constraint-satisfaction problem, and constraints can be unsatisfiable — one package
> needs C 2.0 or later, another needs C below 2.0, and no version exists that satisfies both. Older
> pip installed whatever it saw last and produced a quietly broken environment; modern pip and uv
> refuse and name the conflict. Refusing is the right behaviour — it's the same principle as Python
> refusing to build a class with an inconsistent MRO: an impossible constraint should be a build
> error, not a runtime surprise.

**Q: Why does a package install on macOS and fail in a Docker build?**
> Almost always a missing wheel. Wheels are pre-built artefacts, so installing them is just unzipping;
> an sdist has to be *compiled* at install time. If the package ships a macOS ARM wheel but only an
> sdist for your slim Linux image, pip tries to build it and there's no compiler in the image. Either
> use a build stage with the toolchain, or pick a package that publishes `manylinux` wheels.

**Q: What's the most important line in a Python Dockerfile?**
> Copying `pyproject.toml` and the lockfile and installing dependencies *before* copying the source.
> Docker caches layers, so if the source is copied first, every one-character code change invalidates
> the dependency layer and reinstalls everything. With the split, a code change rebuilds in seconds.
> And nothing should be installed at container *start* — that's slow, needs the network at the worst
> moment, and makes the running code depend on what the index served that second.

## 🎙️ Articulation drill

Record two minutes: **"The build worked yesterday and fails today. Nothing changed."**

⭐ Answer with the diagnosis first: **something did change — a dependency you do not pin.** If the
project declares ranges without a lockfile, then any direct *or transitive* dependency that published
overnight is now in your build, and the same commit produces a different environment than it did
yesterday.

⭐ Then what that costs beyond today's failure: **the build is not reproducible, so you cannot bisect
it, and you cannot redeploy last week's release and get last week's behaviour** — which turns a
five-minute rollback into an investigation.

⭐⭐ **Then the fix, stated as the two-file distinction:** *"`pyproject.toml` is intent — ranges, what
my code needs. The lockfile is the build — exact versions for every transitive dependency, with
hashes. Commit both. CI and Docker run `uv sync --frozen`, which fails if the lock is stale rather
than silently resolving something new, so the environment is identical on my machine, in CI and in
production. And the hashes mean a package that was replaced on the index fails the install instead of
shipping."*

⭐ Close on the Docker consequence: **copy the lockfile and install before copying the source**, so a
code change rebuilds in seconds — **and never `pip install` at container start, or your running code
depends on what the index served that second.**
