# Part 1 — ⭐ `TestClient`, and what it actually is

```python
from fastapi.testclient import TestClient

def test_create_order(client: TestClient):
    r = client.post("/orders", json={"sku": "ABC", "qty": 2})
    assert r.status_code == 201
    assert r.json()["sku"] == "ABC"
```

```
⭐⭐ WHAT `TestClient` IS: an `httpx.Client` with an ASGI transport.
⭐   ⭐⭐ THERE IS NO SOCKET, NO PORT, NO SERVER. Your request is a dict handed
⭐   straight to the app (Day 109's ASGI scope). ⭐ That is why it is fast, and
⭐   why it needs no cleanup.

⭐⭐ AND THE ONE MECHANICAL FACT THAT EXPLAINS ITS ODDITIES: it is a SYNC
⭐   client driving an ASYNC app, so it ⭐ SPINS UP AN EVENT LOOP IN A
⭐   SEPARATE THREAD (via `anyio`) and blocks the calling thread on it.
⭐
⭐   ⇒ ⭐⭐ CONSEQUENCE 1: your test function is sync, but your app's code runs
⭐        on a DIFFERENT loop in a DIFFERENT thread. ⭐ So an async fixture that
⭐        created a connection on the test's loop hands the app an object bound
⭐        to the wrong loop → ⭐⭐ "attached to a different loop" / "Future
⭐        attached to a different loop". ⭐ This is trap #1 and it eats hours.
⭐
⭐   ⇒ ⭐ CONSEQUENCE 2: `with TestClient(app) as c:` runs LIFESPAN
⭐        (Day 133). Without the `with`, ⭐⭐ startup NEVER RUNS — so your pool
⭐        is `None` and the error looks nothing like the cause.
```

```python
@pytest.fixture
def client(app):
    with TestClient(app) as c:        # ⭐⭐ the `with` is not optional
        yield c
```

```
⭐ TWO MORE FLAGS WORTH KNOWING:
⭐   · `TestClient(app, raise_server_exceptions=False)` — ⭐⭐ by default an
⭐     unhandled exception is RE-RAISED into your test instead of becoming a
⭐     500. ⭐ That default is right (you see the traceback), but you must turn
⭐     it off to test your own 500 handler.
⭐   · `client.post(..., follow_redirects=False)` — ⭐ to assert the 308 from
⭐     Day 107's trailing-slash redirect rather than silently following it.
```

# Part 2 — ⭐⭐ `httpx.AsyncClient` — for an async app you actually test async

```python
import httpx
from httpx import ASGITransport

@pytest_asyncio.fixture
async def aclient(app):
    transport = ASGITransport(app=app)
    async with httpx.AsyncClient(transport=transport, base_url="http://test") as c:
        yield c

async def test_create_order(aclient):
    r = await aclient.post("/orders", json={"sku": "ABC", "qty": 2})
    assert r.status_code == 201
```

```
⭐⭐ WHY BOTHER, WHEN `TestClient` ALREADY WORKS?

⭐  1. ⭐⭐ ONE LOOP. Your async fixtures (async engine, async session,
⭐       Day 137) and your app run on THE SAME event loop. ⭐ Trap #1 from
⭐       Part 1 disappears structurally rather than being worked around.
⭐  2. ⭐ You can `await` things inside the test — check the database directly
⭐       with the same `AsyncSession`, run two requests concurrently with
⭐       `asyncio.gather` to test a race (Day 122's idempotency, Day 135's
⭐       `FOR UPDATE`).
⭐  3. ⭐ It is the same client library you would use against a real server, so
⭐       swapping the transport turns the same test into a smoke test.
⭐
⭐   ⇒ ⭐⭐ THE RULE: async app + async database ⇒ `httpx.AsyncClient`.
⭐        Sync app ⇒ `TestClient`. ⭐ Mixing them is where the loop errors
⭐        come from.
⭐   ⚠ ⭐ `ASGITransport` does NOT run lifespan. ⭐⭐ Start your pools in a
⭐        fixture, or use `asgi-lifespan`'s `LifespanManager`.
```

```python
# ⭐⭐ THE TEST THAT ONLY THE ASYNC CLIENT CAN WRITE — a real concurrency test:
async def test_idempotency_key_under_concurrency(aclient):
    body = {"sku": "ABC", "qty": 1}
    h = {"Idempotency-Key": "k-1"}
    r1, r2 = await asyncio.gather(
        aclient.post("/orders", json=body, headers=h),
        aclient.post("/orders", json=body, headers=h),
    )
    assert {r1.status_code, r2.status_code} == {201, 409}     # ⭐⭐ exactly one won
    assert await count_orders() == 1                          # ⭐ Day 122 proven, not assumed
```

# Part 3 — ⭐⭐ The database fixture

```python
@pytest.fixture(scope="session")
def engine():
    # ⭐⭐ A REAL POSTGRES. testcontainers, or a compose service in CI.
    eng = create_engine(TEST_URL)
    Base.metadata.create_all(eng)         # ⭐ or run `alembic upgrade head` — see below
    yield eng
    eng.dispose()

@pytest.fixture
def db(engine):
    conn = engine.connect()
    trans = conn.begin()                                          # ⭐⭐ outer transaction
    session = Session(bind=conn, join_transaction_mode="create_savepoint")
    yield session
    session.close()
    trans.rollback()                                              # ⭐⭐ undo everything
    conn.close()

@pytest.fixture
def app(db):
    application = create_app()                                    # ⭐ Day 133's factory
    application.dependency_overrides[get_db] = lambda: db         # ⭐⭐ Day 132, not patching
    return application
```

```
⭐⭐ WHY THIS SHAPE, POINT BY POINT:

⭐  · ⭐⭐ ROLLBACK, NOT TRUNCATE. Truncating tables between tests is slow and
⭐      grows with your schema. A rollback is O(what the test wrote).
⭐  · ⭐⭐ `join_transaction_mode="create_savepoint"` IS THE WHOLE TRICK: your
⭐      SERVICE calls `commit()` for real (Day 139), it commits to a SAVEPOINT
⭐      inside your outer transaction, and the outer rollback still wipes it.
⭐      ⭐ You test the real commit path AND get isolation. (Pre-2.0 this was
⭐      the fiddly `after_transaction_end` event recipe.)
⭐  · ⭐⭐ OVERRIDE `get_db`, DO NOT PATCH IT. The override is the supported
⭐      seam (Day 132); patching guesses at an import path (Day 094) and
⭐      breaks the day someone re-exports the symbol.
⭐  · ⭐ THE TEST AND THE APP SHARE ONE SESSION — so `db.scalar(...)` in the
⭐      test sees rows the request just wrote, ⭐⭐ WITHOUT them being committed.
⭐  · ⭐ ONE ENGINE PER SESSION, ONE TRANSACTION PER TEST: ⭐⭐ session scope
⭐      for the expensive thing, function scope for the mutable thing —
⭐      Day 093's scope trap, applied.
```

```
⭐⭐ `create_all` OR `alembic upgrade head` IN TESTS? — a real interview question.

⭐   ⭐ `create_all` is faster and simpler, ⭐⭐ but it means YOUR MIGRATIONS ARE
⭐     NEVER EXECUTED BY YOUR TEST SUITE. A broken migration ships.
⭐   ⇒ ⭐⭐ THE ANSWER THAT IS BOTH: `create_all` for the fast suite, PLUS one
⭐     CI job that runs `alembic upgrade head` on an empty database and then
⭐     ⭐ asserts the result matches the models — `alembic check` (or an
⭐     autogenerate that must produce an EMPTY diff). ⭐⭐ That single job
⭐     catches the "someone changed a model and forgot the migration" bug,
⭐     which is the most common Alembic failure in a team (Day 138).
```

# Part 4 — ⭐ Overriding the rest of the graph

```python
app.dependency_overrides[get_current_user] = lambda: FAKE_USER      # ⭐ Day 140
app.dependency_overrides[get_clock]        = lambda: FixedClock("2026-01-01T00:00:00Z")
app.dependency_overrides[get_payments]     = lambda: FakePaymentGateway()

@pytest.fixture(autouse=True)
def _clear_overrides(app):
    yield
    app.dependency_overrides.clear()      # ⭐⭐ overrides are APP-LEVEL AND PERSIST
```

```
⭐⭐ WHAT TO OVERRIDE AND WHAT NEVER TO — the line, stated once:

⭐  OVERRIDE (you do not own it, or it is nondeterministic):
⭐   ⭐ the clock ⭐⭐ (Day 133's seam — the single highest-value one)
⭐   ⭐ third-party HTTP: payments, email, SMS, S3
⭐   ⭐ randomness, uuid generation
⭐   ⭐ `get_current_user` in tests that are ABOUT something else (Day 140 —
⭐        and remember the debt that creates)
⭐
⭐  ⭐⭐ NEVER OVERRIDE (you own it, and it is the thing under test):
⭐   ⭐ the database ⭐⭐ — a fake repo has no constraints (Day 139)
⭐   ⭐ validation / Pydantic models
⭐   ⭐ your own services — ⭐⭐ if a test needs the service faked, it is a
⭐        UNIT test of the route and should not be going through HTTP at all
⭐   ⭐ routing, middleware, exception handlers ⭐ — these ARE the integration
⭐
⭐   ⇒ ⭐⭐ ONE-LINE RULE: FAKE THE THINGS OUTSIDE YOUR DEPLOY.
```

```python
# ⭐ THIRD-PARTY HTTP THAT ISN'T BEHIND A DEPENDENCY — intercept the transport:
import respx
@respx.mock
async def test_payment_declined(aclient):
    respx.post("https://api.stripe.test/charges").respond(402, json={"error": "declined"})
    r = await aclient.post("/orders", json={...})
    assert r.status_code == 402
    assert r.json()["code"] == "payment_declined"     # ⭐ Day 120's contract
```

# Part 5 — ⭐⭐ What to actually assert

```
⭐⭐ THE FOUR LEVELS, AND ROUGHLY WHERE THE TIME GOES:

⭐  1. ⭐ UNIT — services and pure functions, no HTTP, no DB where possible.
⭐       ⭐⭐ The bulk of your logic assertions live here. Fast, precise.
⭐  2. ⭐⭐ API — through `TestClient`/`AsyncClient` with a real database.
⭐       ⭐ This is where FastAPI-specific behaviour is proven: status codes,
⭐       validation shape, auth, headers, serialisation.
⭐  3. ⭐ CONTRACT — the OpenAPI schema itself (Day 126). ⭐⭐ Snapshot
⭐       `app.openapi()` and fail the build on an unreviewed diff: that turns
⭐       an accidental breaking change (Day 125) into a review conversation.
⭐  4. ⭐ SMOKE — a handful against a real deployed instance. Different job.

⭐⭐ THE ASSERTIONS PEOPLE FORGET, ALL OF WHICH ARE REAL BUGS:
⭐   · ⭐⭐ THE ERROR BODY, not just the status. A 422 with a shape nobody
⭐        agreed on breaks clients as surely as a 500 (Day 120).
⭐   · ⭐⭐ WHAT IS *NOT* IN THE RESPONSE. `assert "password_hash" not in
⭐        r.json()` — Day 119: the output schema is a SECURITY control, so
⭐        assert the control.
⭐   · ⭐ the 404-not-403 for another user's object (Day 118)
⭐   · ⭐ `Cache-Control` on authenticated responses (Day 124's shared-cache leak)
⭐   · ⭐⭐ THE QUERY COUNT (Day 136) — the ceiling assertion, below.
```

```python
# ⭐⭐ THE QUERY-COUNT CEILING — the only test that catches an N+1 BEFORE production
@pytest.fixture
def query_counter(engine):
    counts = []
    event.listen(engine, "before_cursor_execute", lambda *a, **k: counts.append(1))
    yield counts

def test_list_orders_is_not_n_plus_1(client, query_counter, seed_50_orders):
    client.get("/orders?limit=50")
    assert len(query_counter) <= 3          # ⭐⭐ a NUMBER, not "it feels fast"
```

> ⭐⭐ **This is the highest-value test in the file.** Every other performance regression is caught
> by a human noticing. ⭐ This one is caught by CI, on the commit that introduced it, with the
> author still holding the context — which is Day 099's whole argument about where a check belongs.

```
⭐ SPEED, WHEN THE SUITE GETS SLOW — in order:
⭐   1. ⭐⭐ `pytest -x --ff` locally; ⭐ `-n auto` (xdist) needs one DATABASE
⭐        PER WORKER (`--create-db` / a per-worker name), or you get flakes
⭐        that look like race conditions and are.
⭐   2. ⭐ session-scoped engine + schema; function-scoped transaction — ⭐⭐ do
⭐        NOT recreate the schema per test (that is usually 90% of the runtime)
⭐   3. ⭐ mark the slow ones and run them separately in CI
⭐   4. ⭐⭐ PROFILE BEFORE OPTIMISING: `pytest --durations=20`. Day 100A's rule
⭐        applies to test suites too — the slow part is almost never what you
⭐        guessed.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `TestClient(app)` without `with` | Lifespan never runs; pools are `None` and the error looks unrelated. |
| Async fixtures + `TestClient` | ⭐⭐ Two event loops in two threads. "Attached to a different loop." Use `httpx.AsyncClient`. |
| Expecting `ASGITransport` to run startup | It doesn't. Use `LifespanManager` or a fixture. |
| Truncating tables between tests | Slow and schema-dependent. Use an outer transaction + rollback. |
| Session that can't commit in tests | `join_transaction_mode="create_savepoint"` lets the real commit path run and still roll back. |
| Patching `get_db` instead of overriding | Patching guesses an import path; `dependency_overrides` is the supported seam. |
| Forgetting to clear overrides | They're app-level and persist; one test then silently configures the next. |
| Faking your own services in API tests | If the service is faked, it isn't an integration test — make it a unit test. |
| Only asserting status codes | Assert the error body, the absent fields, and `Cache-Control`. |
| No query-count ceiling | An N+1 ships and is found by a customer. |
| `create_all` with migrations never executed | Add one CI job that runs `alembic upgrade head` and checks for an empty autogenerate diff. |
| SQLite in tests, Postgres in production | Different types and constraints — a different program. |

## Interview questions

**Q: `TestClient` vs `httpx.AsyncClient` — which and why?**

> `TestClient` is an httpx client over an ASGI transport, so there's no socket and no port — the
> request is a dict handed straight to the app. But it's a sync client driving an async app, so it
> runs an event loop in a separate thread. The moment you have async fixtures — an async engine, an
> `AsyncSession` — those objects get bound to the test's loop while the app runs on another, and you
> get "attached to a different loop" errors that are miserable to diagnose. So: sync app,
> `TestClient`; async app with an async database, `httpx.AsyncClient` with `ASGITransport`, because
> then everything shares one loop. The async client also lets me `await` inside the test — I can
> fire two requests with `asyncio.gather` and actually test the idempotency race rather than assume
> it.

**Q: Describe your database fixture.**

> A session-scoped engine against a real Postgres, and per test: open a connection, begin an outer
> transaction, bind a Session with `join_transaction_mode="create_savepoint"`, yield, then roll the
> outer transaction back. The savepoint mode is the point — my service calls `commit()` for real, so
> I'm testing the actual commit path, but it commits into a savepoint inside my outer transaction
> and the rollback still wipes it. Rollback rather than truncate, because rollback is proportional
> to what the test wrote rather than to the size of the schema. The app gets that same session via
> `dependency_overrides[get_db]`, which means my test can query the database directly and see rows
> the request wrote without them ever being committed.

**Q: What do you refuse to fake in an API test?**

> Anything inside my own deploy. Not the database — a fake repository has no unique constraints, no
> transactions and no query plans, so it hides the exact bugs I'm testing for. Not validation, not
> routing, not middleware, not my services — if a test needs the service faked, it's a unit test
> wearing an HTTP costume and should skip the HTTP. What I do fake is everything outside the deploy:
> the clock, third-party HTTP, randomness, and `get_current_user` in tests that are about something
> else — though that last one creates a debt, so I keep a small suite with no overrides at all that
> proves auth actually works.

**Q: How do you stop an N+1 from reaching production?**

> A query-count ceiling in the test suite. I attach a `before_cursor_execute` listener to the
> engine, hit the list endpoint with fifty seeded rows, and assert the count is at most three. It's
> a number, not a feeling — and it fails on the commit that introduces it, while the author still has
> the context, instead of being noticed months later as "the orders page got slow". It's the only
> automated defence, because an N+1 is invisible to a slow-query log: every one of those fifty
> queries is fast.

**Q: `create_all` or Alembic in the test suite?**

> `create_all` for the fast suite, because it's simpler and quicker. But that means the migrations
> are never executed by CI, and a broken migration ships. So I add one job that runs `alembic
> upgrade head` against an empty database and then asserts the resulting schema matches the models —
> an autogenerate that must produce an empty diff. That single job catches the most common team
> failure with Alembic: someone changed a model and forgot the migration.

## 🎙️ Articulation drill

**Two minutes: "How do you test a FastAPI service?"**

State the principle first — real stack, fake only what's outside the deploy — then make it concrete.
Client choice with the event-loop reason. The database fixture with the savepoint trick, and why
rollback beats truncate. `dependency_overrides` as the supported seam and the line between what you
override and what you never do. Then the assertions people skip: the error body, the fields that
must be *absent*, and the query-count ceiling. Close on the Alembic job — **`create_all` means your
migrations are never run by CI** — and on the honest note that if a test needs your own service
faked, it wanted to be a unit test.
