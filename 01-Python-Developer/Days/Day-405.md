# Day 405 📜

**P-405** · 📜 **Event sourcing** — the power, ⭐⭐ and the cost stated honestly

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: event sourcing stores the facts and derives the state — the power is that
> you can answer questions you had not thought of yet, and the cost is that you can never change your
> mind about what a fact means.**

---

# Part 1 — The idea, in one equation

```
⭐⭐ ***state = reduce(apply, events, initial)***

⭐ A normal system stores the ***result*** and throws away how it
⭐   got there:
⭐   ⭐ `UPDATE accounts SET balance = 340 WHERE id = 7`
⭐   ⭐⭐ THE PREVIOUS BALANCE IS GONE. THE REASON IS GONE. ⭐ You
⭐     recover them by inference from an audit table someone
⭐     remembered to write.

⭐ An event-sourced system stores the ***facts*** and computes
⭐   the result:
⭐   ⭐ `MoneyDeposited(account=7, cents=5000, at=…)`
⭐   ⭐ `PaymentTaken(account=7, cents=1600, order=…)`
⭐   ⭐⭐ THE BALANCE IS A FOLD OVER THOSE, AND THE HISTORY IS NOT
⭐     A SIDE-EFFECT — ***IT IS THE DATA.***

⭐ THE THREE NOUNS:
⭐   ⭐⭐ ***AGGREGATE*** — the consistency boundary. ⭐ One
⭐     aggregate = one stream = one lock = one transaction.
⭐     ⭐⭐ CHOOSING AGGREGATES ***IS*** THE DESIGN (DAY 399's
⭐     INVARIANTS, AGAIN).
⭐   ⭐ ***EVENT*** — an immutable, past-tense fact. ⭐⭐ NEVER A
⭐     COMMAND, NEVER A REQUEST (DAY 333).
⭐   ⭐ ***PROJECTION*** — a read model built by folding events
⭐     (Day 406).

⭐⭐ AND THE SENTENCE THAT KEEPS PEOPLE HONEST: ***IF YOU WOULD
⭐   NOT PUT IT IN A COMPANY'S PERMANENT RECORD, IT IS NOT AN
⭐   EVENT.***
```

---

# Part 2 — What it genuinely buys

```
⭐ ① ⭐⭐ ***AN AUDIT LOG THAT CANNOT DRIFT***, ⭐ because it is
⭐    the source of truth rather than a parallel write. ⭐ Every
⭐    audit table ever built has eventually disagreed with the
⭐    data it audits. ⭐⭐ THIS ONE STRUCTURALLY CANNOT.
⭐ ② ⭐ ***TEMPORAL QUERIES.*** ⭐ "What was this customer's
⭐    balance on 3 March?" is a fold up to a timestamp,
⭐    ⭐⭐ NOT AN ARCHAEOLOGICAL EXPEDITION.
⭐ ③ ⭐⭐ ***RETROACTIVE PROJECTIONS — THE BIGGEST ONE.***
⭐    ⭐ Someone asks for a report that needs data nobody thought
⭐    to store. ⭐ In a CRUD system the answer is "we can start
⭐    collecting that from today". ⭐⭐ HERE THE ANSWER IS "I CAN
⭐    BUILD IT OVER THE WHOLE HISTORY THIS AFTERNOON", ⭐ because
⭐    the raw facts were never discarded.
⭐ ④ ⭐ ***DEBUGGING BY REPLAY.*** ⭐ Reproduce a bug by folding
⭐    the exact event sequence that caused it. ⭐⭐ NO "CANNOT
⭐    REPRODUCE".
⭐ ⑤ ⭐ ***NATURAL FIT FOR CERTAIN DOMAINS*** — ⭐ accounting
⭐    (the ledger ***is*** an event log — Day 358), ⭐ anything
⭐    with undo, ⭐ anything collaborative, ⭐ anything regulated.
```

# Part 3 — ⭐⭐ The five costs, in the order they hurt

```
⭐⭐ ① ***EVENTS ARE PERMANENT, SO A MISTAKE IN THEIR MEANING IS
⭐    PERMANENT.***
⭐    ⭐ You cannot `ALTER TABLE` a fact. ⭐ If `OrderPlaced`
⭐      recorded a total that excluded tax and should have
⭐      included it, ⭐⭐ EVERY EVENT EVER WRITTEN IS NOW
⭐      AMBIGUOUS, AND EVERY FUTURE READER MUST KNOW ABOUT THE
⭐      DAY THE MEANING CHANGED — FOREVER.
⭐    ⭐⭐ ⇒ ***YOUR EVENT SCHEMA IS A PUBLIC API WITH NO
⭐      DEPRECATION PATH.*** ⭐ That is the real cost, and it is
⭐      the one people discover in year two.

⭐⭐ ② ***QUERYING IS HARD.*** ⭐ "All users in London" is not a
⭐    question an event store can answer. ⭐ Every query needs a
⭐    projection (Day 406), ⭐⭐ WHICH MEANS EVENTUAL CONSISTENCY
⭐    EVERYWHERE, WHICH MEANS EVERY SCREEN IN YOUR APPLICATION
⭐    INHERITS A LAG YOU MUST NOW EXPLAIN TO A PRODUCT MANAGER.

⭐⭐ ③ ***SNAPSHOTS BECOME MANDATORY.*** ⭐ Folding 200,000 events
⭐    per request is not viable. ⭐ So you snapshot every N
⭐    events. ⭐⭐ AND SNAPSHOTS ARE A ***CACHE OF A COMPUTATION***
⭐    — SO WHEN YOU FIX A BUG IN `apply()`, EVERY SNAPSHOT IS
⭐    WRONG AND MUST BE INVALIDATED. ⭐ Version your snapshots
⭐    with the code version that produced them, ⭐⭐ OR YOU WILL
⭐    SERVE STATE COMPUTED BY A BUG YOU ALREADY FIXED.

⭐⭐ ④ ***DELETING DATA IS STRUCTURALLY HARD.*** ⭐ "Erase this
⭐    person" against an append-only log is a contradiction.
⭐    ⭐⭐ ⇒ THE ANSWER IS ***CRYPTO-SHREDDING*** (DAY 395):
⭐      encrypt every personal field with a ***per-subject key***
⭐      held outside the log, ⭐ and on erasure ⭐⭐ DELETE THE KEY.
⭐      ⭐ The events remain — so the fold still works, the
⭐      counts still balance — ⭐⭐ AND THE PERSONAL DATA IS
⭐      UNRECOVERABLE EVERYWHERE AT ONCE, INCLUDING IN BACKUPS
⭐      AND REPLICAS YOU CANNOT ENUMERATE. ⭐ Design this on day
⭐      one; ⭐⭐ RETROFITTING IT IS NOT POSSIBLE.

⭐⭐ ⑤ ***THE TEAM MUST UNDERSTAND IT.*** ⭐ The commonest failure
⭐    of event sourcing is not technical: ⭐⭐ ONE ENTHUSIAST
⭐    INTRODUCES IT, LEAVES, AND THE REMAINING TEAM STARTS
⭐    `UPDATE`-ING THE PROJECTIONS DIRECTLY — ⭐ at which point you
⭐    have all the cost and none of the guarantee, ⭐⭐ AND THE
⭐    EVENT LOG IS NOW A LIE.
```

# Part 4 — ⭐⭐ Event versioning: the four techniques

```
⭐⭐ THE GOVERNING RULE: ***ADDITIVE CHANGES ONLY. A NEW MEANING
⭐   IS A NEW EVENT TYPE.***

⭐ ① ⭐ ***TOLERANT READER / WEAK SCHEMA.*** ⭐ Unknown fields
⭐    ignored, missing fields defaulted. ⭐⭐ COSTS NOTHING AND
⭐    HANDLES 80% OF CHANGES. ⭐ Do this from day one (Day 400's
⭐    protobuf rules give it to you for free).
⭐ ② ⭐⭐ ***UPCASTING ON READ.*** ⭐ A function
⭐    `v1 → v2 → v3` applied as events are loaded. ⭐ The store
⭐    keeps the original bytes; ⭐⭐ THE DOMAIN ONLY EVER SEES THE
⭐    LATEST SHAPE. ⭐ This is the workhorse.
⭐    ⭐ Cost: the upcaster chain only grows, ⭐⭐ AND IT IS CODE
⭐      YOU CAN NEVER DELETE.
⭐ ③ ⭐ ***MULTIPLE EVENT TYPES.*** ⭐ `OrderPlaced` and
⭐    `OrderPlacedV2` coexist; ⭐ `apply()` handles both forever.
⭐    ⭐⭐ HONEST AND UGLY, AND THE RIGHT ANSWER WHEN THE ***MEANING***
⭐    CHANGED RATHER THAN THE SHAPE.
⭐ ④ ⭐⭐ ***COPY-AND-TRANSFORM THE WHOLE STREAM*** — ⭐ the
⭐    nuclear option. ⭐ Write a new stream, transformed.
⭐    ⭐⭐ IT INVALIDATES EVERY CONSUMER'S POSITION, BREAKS EVERY
⭐    EXTERNAL REFERENCE TO AN EVENT ID, AND DESTROYS THE
⭐    PROPERTY YOU BOUGHT EVENT SOURCING FOR — NAMELY THAT THE
⭐    LOG IS THE UNALTERED TRUTH. ⭐ Reserve it for a genuine
⭐    disaster, ⭐⭐ AND EXPECT TO DO IT ONCE IN A CAREER.
```

# Part 5 — Concurrency: the one place it is *stronger* than a table

```
⭐⭐ ***OPTIMISTIC CONCURRENCY ON THE AGGREGATE VERSION.***
⭐   ⭐ Load the aggregate, note it is at version 14.
⭐   ⭐ Decide, produce new events.
⭐   ⭐ Append ***with `expected_version = 14`***.
⭐   ⭐⭐ IF SOMEONE ELSE APPENDED MEANWHILE, THE APPEND FAILS.
⭐     ⭐ Reload, re-decide, retry.

⭐⭐ AND THE MECHANISM IS ***ONE DATABASE INDEX***:
⭐   `UNIQUE (aggregate_id, version)`
⭐   ⭐ That single constraint is the entire optimistic-locking
⭐     implementation. ⭐⭐ NO LOCK SERVICE, NO TTL, NO FENCING
⭐     TOKEN, NO REDLOCK ARGUMENT (DAY 411) — ⭐ the database does
⭐     it, correctly, for free.

⭐⭐ ⇒ THIS IS THE UNDER-SOLD BENEFIT: ***AN EVENT-SOURCED
⭐   AGGREGATE HAS A STRONGER AND SIMPLER CONCURRENCY STORY THAN
⭐   A ROW YOU `UPDATE`***, ⭐ because "what did I base this
⭐   decision on" is explicit rather than implied.
```

# Part 6 — A Python implementation that is not a toy

```python
from dataclasses import dataclass
from typing import Sequence

# ⭐ Events: frozen, past-tense, ⭐⭐ AND VERSIONED IN THE NAME
@dataclass(frozen=True, slots=True)
class OrderPlaced:
    order_id: str; customer_id: str; total_cents: int   # ⭐⭐ INT

@dataclass(frozen=True, slots=True)
class OrderCancelled:
    order_id: str; reason: str

# ⭐ The aggregate: a fold plus decision functions.
class Order:
    __slots__ = ("id", "status", "total_cents", "version")

    @classmethod
    def rehydrate(cls, events: Sequence[object], version: int):
        o = cls.__new__(cls); o.version = version
        for e in events: o._apply(e)
        return o

    def _apply(self, e):                 # ⭐⭐ PURE. NO I/O. EVER.
        match e:
            case OrderPlaced():    self.id = e.order_id; self.status = "placed"
            case OrderCancelled(): self.status = "cancelled"

    def cancel(self, reason: str):       # ⭐ decide → new events
        if self.status == "cancelled":
            return []                    # ⭐⭐ IDEMPOTENT BY DESIGN
        if self.status == "shipped":
            raise DomainError("cannot cancel a shipped order")
        return [OrderCancelled(self.id, reason)]
```

```sql
-- ⭐⭐ THE STORE. ONE TABLE. THE UNIQUE INDEX IS THE WHOLE
-- ⭐   CONCURRENCY MECHANISM.
CREATE TABLE events (
  id             bigserial PRIMARY KEY,
  aggregate_id   uuid        NOT NULL,
  aggregate_type text        NOT NULL,
  version        int         NOT NULL,
  event_type     text        NOT NULL,
  payload        jsonb       NOT NULL,
  metadata       jsonb       NOT NULL,   -- ⭐⭐ trace id, actor,
                                         -- ⭐   causation, correlation
  occurred_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (aggregate_id, version)         -- ⭐⭐ OPTIMISTIC LOCK
);
CREATE INDEX ON events (aggregate_id, version);
```

```
⭐⭐ AND THE THREE THINGS THAT MAKE IT PRODUCTION-GRADE:
⭐   ⭐⭐ ① ***APPEND THE EVENTS AND THE OUTBOX ROW IN THE SAME
⭐      TRANSACTION*** (DAY 407). ⭐ Publishing is a consequence
⭐      of the append, never a second action.
⭐   ⭐ ② `metadata` carries `trace_id`, `causation_id` and
⭐      `correlation_id` — ⭐⭐ SO YOU CAN ASK "WHAT CAUSED THIS
⭐      EVENT?" AND GET AN ANSWER, WHICH IS HALF THE VALUE OF
⭐      THE WHOLE APPROACH.
⭐   ⭐⭐ ③ `_apply` IS ***PURE***. ⭐ No database calls, no clock,
⭐      no randomness, ⭐⭐ OR REPLAY PRODUCES A DIFFERENT ANSWER
⭐      THAN THE ORIGINAL RUN AND EVERY GUARANTEE COLLAPSES.
⭐      ⭐ Timestamps and ids are decided in the ***decide***
⭐      step and stored ***in*** the event.
```

# Part 7 — ⭐⭐ When not to event-source

```
⭐⭐ ***THE FAILURE MODE IS "EVENT-SOURCE THE WHOLE SYSTEM".***
⭐   ⭐ It is a technique for aggregates where ***history is the
⭐   product***, ⭐⭐ NOT AN ARCHITECTURE STYLE FOR AN APPLICATION.

⭐ ⇒ ⭐⭐ EVENT-SOURCE THE ONE OR TWO AGGREGATES WHERE HISTORY IS
⭐   GENUINELY THE VALUE: ⭐ money and ledgers, ⭐ an order
⭐   lifecycle, ⭐ anything regulated, ⭐ anything with undo.
⭐   ⭐⭐ USE PLAIN TABLES FOR EVERYTHING ELSE — ⭐ user profiles,
⭐   settings, catalogues, sessions. ⭐⭐ THEY CAN LIVE IN THE SAME
⭐   SERVICE AND THE SAME DATABASE. NOTHING IS INCONSISTENT ABOUT
⭐   THAT.

⭐⭐ AND THE SENTENCE THAT IS WORTH MORE THAN ENTHUSIASM IN AN
⭐   INTERVIEW: ***CRUD WITH A WELL-DESIGNED AUDIT TABLE GIVES
⭐   YOU 80% OF THE AUDIT VALUE FOR 5% OF THE COST.*** ⭐ If audit
⭐   is the only reason, ⭐⭐ TAKE THE 80%. ⭐ Event sourcing earns
⭐   its cost when you need ***retroactive projections***,
⭐   ***temporal queries*** or ***replay-based debugging*** —
⭐   ⭐⭐ AND IF YOU CANNOT NAME WHICH OF THOSE THREE, YOU ARE
⭐   BUYING PERMANENCE YOU DO NOT NEED.
```

# 💬 Interview

**1. ⭐⭐ "Sell me event sourcing, then talk me out of it."**
> ⭐ It buys an audit log that structurally cannot drift, temporal queries, replay-based debugging,
> and — the biggest one — ⭐⭐ **retroactive projections: when someone asks for a report needing data
> nobody thought to store, a CRUD system says "we can collect that from today" and an event-sourced
> one says "I can build it over the whole history this afternoon".** ⭐ Against it: ⭐⭐ **events are
> permanent, so a mistake in their meaning is permanent — your event schema is a public API with no
> deprecation path**, and that's what people discover in year two. ⭐ Querying needs projections, so
> every screen inherits a lag. ⭐ Snapshots become mandatory and are a cache of a computation, ⭐⭐ **so
> fixing a bug in `apply()` invalidates every snapshot.** ⭐ Deletion is structurally hard. ⭐⭐ **And the
> commonest failure isn't technical: one enthusiast introduces it, leaves, and the team starts
> UPDATE-ing the projections directly — at which point you have all the cost and the log is a lie.**

**2. ⭐⭐ "How do you handle GDPR erasure in an append-only log?"**
> ⭐ Crypto-shredding. ⭐⭐ **Encrypt every personal field with a per-subject key held outside the log,
> and on an erasure request delete the key. The events remain, so the fold still works and the counts
> still balance, and the personal data becomes unrecoverable everywhere at once — including in backups
> and replicas you can't enumerate.** ⭐ That's the same envelope-encryption property as KMS, applied
> per data subject. ⭐⭐ **And it has to be designed on day one, because retrofitting it isn't possible
> — you can't go back and encrypt facts that are already written in plaintext across every consumer's
> copy.**

**3. "How do you version events?"**
> ⭐ One governing rule: ⭐⭐ **additive changes only, and a new meaning is a new event type.** ⭐ Then
> four techniques in increasing severity: a tolerant reader that ignores unknown fields and defaults
> missing ones, which is free and handles most changes; ⭐⭐ **upcasting on read, where the store keeps
> the original bytes and a v1→v2→v3 chain runs at load time so the domain only sees the latest shape**
> — that's the workhorse, and the chain is code you can never delete; a second event type coexisting
> forever, which is honest and ugly and correct when the *meaning* changed; ⭐⭐ **and copy-and-transform
> of the whole stream, which invalidates every consumer's position and destroys the property you
> bought event sourcing for.** ⭐ That last one is a once-in-a-career move.

**4. ⭐⭐ "How does concurrency work?"**
> ⭐ Optimistic, on the aggregate version: load at version 14, decide, append with
> `expected_version=14`, and if someone else appended meanwhile the append fails and you reload and
> retry. ⭐⭐ **And the entire mechanism is one database index — `UNIQUE (aggregate_id, version)`. No
> lock service, no TTL, no fencing token, no Redlock argument; the database does it correctly for
> free.** ⭐ It's the under-sold benefit: ⭐⭐ **an event-sourced aggregate has a stronger and simpler
> concurrency story than a row you UPDATE, because what you based the decision on is explicit rather
> than implied.**

**5. "What makes an `apply` function wrong?"**
> ⭐ Any impurity. ⭐⭐ **No database calls, no clock, no randomness — because replay must produce
> exactly the same answer as the original run, and if `apply` reads `datetime.now()` it won't.** ⭐ Every
> timestamp, id and external value is decided in the *decide* step and stored *in* the event. ⭐ Once
> `apply` is pure, replay, snapshots and projections all work; ⭐⭐ **the moment it isn't, all three
> quietly produce different answers and you won't notice until you rebuild something.**

**6. ⭐⭐ "When wouldn't you event-source?"**
> ⭐ Almost everywhere. ⭐⭐ **The failure mode is event-sourcing the whole system — it's a technique for
> aggregates where history is the product, not an architecture style for an application.** ⭐ I'd
> event-source the ledger and the order lifecycle and use plain tables for profiles, settings and
> catalogues, in the same service and the same database. ⭐⭐ **And if audit is the only motivation, CRUD
> with a well-designed audit table gives you 80% of the value for 5% of the cost — take the 80%.**
> ⭐ Event sourcing earns its cost when you need retroactive projections, temporal queries or
> replay-based debugging, ⭐⭐ **and if you can't name which of those three, you're buying permanence
> you don't need.**
