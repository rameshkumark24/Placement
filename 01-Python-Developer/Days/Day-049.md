# Day 049

**L-049** · ⭐ `itertools` — the composable iteration toolkit

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every `itertools` function takes iterators and returns an iterator, so
> they compose into pipelines that use constant memory no matter how much data flows through.**
>
> ⭐ You do not need to memorise all of them. **You need to recognise the five or six shapes** —
> batching, windowing, grouping, flattening, taking-while — **so that you reach for the C-speed
> version instead of writing a loop with an index variable.**

---

# Part 1 — ⭐⭐ The ones you will actually use

```python
import itertools as it

# ⭐⭐ FLATTEN — one level, lazily
it.chain(a, b, c)                    # ⭐ concatenate iterables
it.chain.from_iterable(list_of_lists)    # ⭐⭐ flatten — the one people write a loop for

# ⭐⭐ SLICE an iterator (you cannot use [] on one — Day 046)
it.islice(gen, 10)                   # ⭐ first 10
it.islice(gen, 5, 15)                # ⭐ a window, without materialising
it.islice(gen, 0, None, 2)           # every other

# ⭐ RUNNING TOTALS
list(it.accumulate([1,2,3,4]))       # ⭐ [1, 3, 6, 10]
list(it.accumulate(prices, max))     # ⭐⭐ running maximum — any binary function
list(it.accumulate(xs, operator.mul))

# ⭐⭐ SLIDING WINDOW of two (3.10+)
list(it.pairwise([1,2,3,4]))         # ⭐⭐ [(1,2), (2,3), (3,4)] — deltas, comparisons

# ⭐⭐ BATCHING (3.12+) — the single most useful one for backend work
for batch in it.batched(rows, 500):  # ⭐ tuples of 500, last one shorter
    db.bulk_insert(batch)
```

⭐⭐ **`batched` is the shape you will use most often**, because bulk inserts, bulk API calls and
message-queue publishes all want fixed-size chunks from a lazy stream. **Before 3.12:**

```python
def batched(iterable, n):                       # ⭐ the standard recipe
    it_ = iter(iterable)
    while batch := tuple(it.islice(it_, n)):    # ⭐⭐ walrus (Day 040) earning its place
        yield batch
```

```python
# ⭐ CONDITIONAL TAKING — stop, or skip, based on a predicate
it.takewhile(lambda x: x < 100, sorted_stream)  # ⭐⭐ STOPS at the first failure — does not scan on
it.dropwhile(lambda x: x < 100, stream)         # ⭐ skips until the first failure, then yields all
it.filterfalse(is_valid, items)                 # ⭐ the inverse of filter
it.compress(data, selectors)                    # ⭐ pick by a parallel boolean iterable
it.zip_longest(a, b, fillvalue=None)            # ⭐⭐ zip that does NOT truncate (Day 034)
it.starmap(func, list_of_arg_tuples)            # ⭐ func(*args) for each tuple
```

⭐⭐ **`takewhile` on a sorted stream is a real optimisation, not a style choice** — it stops reading
at the first element that fails, so on a sorted 50 GB file you read only the prefix you need.

# Part 2 — ⭐⭐ `groupby`, and its trap

```python
data = [("a", 1), ("a", 2), ("b", 3), ("a", 4)]
for key, group in it.groupby(data, key=lambda x: x[0]):
    print(key, list(group))
# ⭐⭐ a [('a',1),('a',2)]
#    b [('b',3)]
#    a [('a',4)]        ⭐⭐ ← "a" AGAIN. It groups CONSECUTIVE runs, not all equal keys.
```

```
⭐⭐ THE TRAP: itertools.groupby IS NOT SQL's GROUP BY. It groups ADJACENT items only.
⭐   ⇒ ⭐⭐ YOU MUST SORT BY THE SAME KEY FIRST, or you get fragmented groups — silently.
⭐   ⇒ ⭐ that design is deliberate: it lets groupby work on an INFINITE or STREAMING source
⭐        in constant memory, which a true group-by cannot.
⭐   ⇒ ⭐⭐ if you want a real group-by and the data fits: defaultdict(list) (Day 038). It is
⭐        O(n) with no sort, and it does not have this failure mode.
```

⚠️ ⭐⭐ **The second `groupby` trap: the group iterator is invalidated when you advance.**

```python
groups = list(it.groupby(data, key=first))       # ⚠️ ⭐⭐ every group is now EMPTY
groups = [(k, list(g)) for k, g in it.groupby(data, key=first)]    # ⭐ materialise as you go
```

⭐ **The groups share the underlying iterator**, so moving to the next group consumes the previous
one — Day 046's exhaustion, in a place that looks safe. **`list(g)` inside the loop, always.**

```python
# ⭐⭐ WHERE groupby IS GENUINELY RIGHT — deduplicating CONSECUTIVE duplicates in a stream:
unique_runs = (k for k, _ in it.groupby(sensor_readings))   # ⭐ collapse repeated values
# ⭐ and: parsing a sorted log by day, without loading the file
```

# Part 3 — ⭐ Infinite and combinatoric

```python
it.count(10, 2)          # ⭐ 10, 12, 14, ... forever
it.cycle("abc")          # ⭐⭐ a, b, c, a, b, c, ... — ⚠️ it BUFFERS the whole input
it.repeat(None, 5)       # ⭐ five Nones; repeat(x) is infinite
```

⚠️ ⭐⭐ **An infinite iterator with no bound is a hang, not a crash.** `list(it.count())` never
returns and consumes all memory. **Always pair them with `islice`, `takewhile`, or `zip` against a
finite sequence** — `zip(it.count(), items)` is a hand-rolled `enumerate`, and it terminates because
`zip` stops at the shortest.

```python
it.product("ab", repeat=2)            # ⭐ aa ab ba bb — the nested-loop replacement
it.product(sizes, colours)            # ⭐⭐ every combination — cartesian product
it.permutations([1,2,3], 2)           # ⭐ ordered arrangements — n!/(n-k)!
it.combinations([1,2,3], 2)           # ⭐ (1,2) (1,3) (2,3) — unordered, no repeats
it.combinations_with_replacement([1,2], 2)
```

```
⭐⭐ THE COMPLEXITY WARNING YOU MUST SAY ALOUD IN AN INTERVIEW:
⭐   permutations(n)     ⇒ n!        — 10 items = 3.6 million; 13 items = 6 BILLION
⭐   combinations(n, k)  ⇒ C(n,k)
⭐   product(k, repeat=n) ⇒ kⁿ
⭐ ⇒ ⭐⭐ these are LAZY, so they never build the whole thing — ⚠️ but consuming one
⭐      in a loop is still exponential TIME. Laziness saves memory, never complexity.
```

⭐⭐ **"It's lazy, so memory is fine — but this is still O(n!) time" is exactly the sentence that
shows you understand what laziness does and does not buy.**

⚠️ ⭐ **`it.tee(gen, 2)`** duplicates an iterator, but **buffers everything one branch reads ahead of
the other** — if one branch is fully consumed first, `tee` has stored the entire stream. **It is not
a free re-iteration** (Day 046).

# Part 4 — ⭐ Composing, and the real recipes

```python
# ⭐⭐ A full pipeline — constant memory over a 50 GB file (Day 047):
lines   = open(path, encoding="utf-8")
parsed  = map(parse, lines)
errors  = filter(lambda r: r.level == "ERROR", parsed)
recent  = it.takewhile(lambda r: r.ts > cutoff, errors)   # ⭐ sorted ⇒ stop early
for batch in it.batched(recent, 500):                     # ⭐⭐ bulk write
    db.insert_many(batch)
```

| ⭐ The shape | ⭐⭐ The tool |
|---|---|
| ⭐ "In chunks of N" | ⭐⭐ `batched` / the `islice` recipe |
| "Compare each item to the next" | ⭐ `pairwise` |
| "Flatten a list of lists" | ⭐ `chain.from_iterable` |
| "First N of a stream" | ⭐ `islice` |
| ⭐ "Stop when the condition fails" (sorted data) | ⭐⭐ `takewhile` |
| "Running total / running max" | `accumulate` |
| "Collapse consecutive duplicates" | `groupby` |
| ⭐⭐ "Group all items by a key" | ⭐⭐ **`defaultdict(list)` — NOT `groupby`** |
| "Every combination of these options" | `product` |
| "Pad two unequal sequences" | `zip_longest` |

⭐ **`more-itertools`** (third-party) has `chunked`, `windowed`, `unique_everseen`, `first`,
`peekable`, `flatten` and about a hundred more. ⭐⭐ **`unique_everseen` and `windowed` are the two
worth knowing exist**, because they are the order-preserving dedupe (Day 036) and the general
sliding window that `pairwise` only does for n=2.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`groupby` without sorting first** | ⭐⭐ It groups adjacent runs. Fragmented groups, silently. |
| ⭐⭐ **`list(groupby(...))`** | ⭐⭐ Groups share the iterator — all empty. `list(g)` inside the loop. |
| Using `groupby` for a real group-by | ⭐ `defaultdict(list)` — O(n), no sort, no trap. |
| `list()` on an infinite iterator | ⭐ It hangs. Bound it with `islice`/`takewhile`/`zip`. |
| "It's lazy so it's cheap" | ⭐⭐ Laziness saves memory, never time complexity. |
| ⭐ `tee` as free re-iteration | ⭐⭐ It buffers the gap; can cost as much as a list. |
| Slicing an iterator with `[]` | ⭐ `islice`. |
| Hand-writing a batching loop with an index | ⭐ `batched`, or the four-line `islice` recipe. |
| `filter` where `takewhile` fits on sorted data | ⭐⭐ `filter` scans everything; `takewhile` stops. |
| `zip` where `zip_longest` was meant | ⭐ Silent truncation (Day 034). |

## Interview questions

**Q: What's the point of `itertools`?**
> Everything in it takes and returns iterators, so the functions compose into pipelines that hold one
> element at a time regardless of the input size. That's the same property as generators, but
> implemented in C, so the common shapes — chunking, windowing, flattening, taking-while — run at
> C speed instead of as a Python loop with an index variable. The practical value is recognising the
> shapes: once I see "in batches of 500" or "compare each item to the next", there's a named tool.

**Q: What's the trap with `groupby`?**
> Two of them. It groups *consecutive* runs, not all equal keys — so without sorting by the same key
> first, the same key appears in several groups and nothing warns you. That design is deliberate:
> it's what lets `groupby` work on an infinite stream in constant memory, which a real group-by
> can't. The second trap is that the group iterators share the underlying iterator, so advancing to
> the next group exhausts the previous one — `list(groupby(...))` gives you groups that are all
> empty. You materialise each group inside the loop. If I actually want SQL-style grouping and the
> data fits in memory, `defaultdict(list)` is O(n), needs no sort, and has neither failure mode.

**Q: How do you process a huge query result in batches of 500?**
> `itertools.batched` in 3.12, or the four-line recipe with `islice` and a walrus before that — pull
> `n` items off the iterator until you get an empty tuple. The important part is that the source
> stays lazy: the cursor yields rows one at a time, batching accumulates 500, the bulk insert happens,
> and the batch is released. Memory is 500 rows, not the result set, and it works the same on ten
> rows or ten million.

**Q: Is a lazy `permutations` cheap?**
> Cheap in memory, not in time. It never builds the full sequence, so memory is fine — but consuming
> it in a loop is still O(n!), and thirteen items is six billion tuples. Laziness changes the space
> complexity, never the time complexity, and that distinction is worth saying explicitly when a
> problem tempts you toward brute force.

**Q: When is `takewhile` better than `filter`?**
> On sorted data, where the predicate is monotonic. `filter` examines every element; `takewhile`
> stops at the first failure. On a sorted log file that's the difference between reading the whole
> file and reading only the prefix you need — a real optimisation that costs one word.

## 🎙️ Articulation drill

Record two minutes: **"Stream ten million rows from a database into an external API that accepts
batches of 500."**

⭐ Describe the pipeline as lazy end to end: **a server-side cursor yields rows one at a time,
transformation is a generator expression, batching is `itertools.batched`, and each batch is posted
and released.** Memory is 500 rows, not ten million, and it behaves identically at any scale.

⭐ Then the detail that shows production thinking: **the batch size is a trade** — larger batches mean
fewer round trips and a bigger retry blast radius, and if a batch fails you need to know whether the
API is idempotent (Day 010) before retrying it.

⭐⭐ **Then the caution worth volunteering:** *"the thing I'd check is whether the cursor is genuinely
server-side. Many drivers buffer the entire result set client-side by default, so the pipeline looks
lazy and the memory is spent before the first row arrives. The laziness of the Python code is
irrelevant if the layer beneath it is eager — and that's a general lesson about streaming, not a
database detail."*
