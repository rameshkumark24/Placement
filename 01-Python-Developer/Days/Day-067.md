# Day 067

**L-067** · ⭐ Race conditions in Python — `+=` is not atomic; what *is*, and why that is fragile

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the problem is not threads. The problem is shared mutable state — and
> threads merely make it visible.**
>
> ⭐ Today you will *see* the race in the bytecode, reproduce it deliberately, and then learn why the
> "atomic operations" list that people memorise is the wrong thing to rely on.

---

# Part 1 — ⭐⭐ Seeing the race

```python
import dis
def inc():
    global counter
    counter += 1

dis.dis(inc)
#   LOAD_GLOBAL   counter      ⭐⭐ read
#   LOAD_CONST    1
#   BINARY_OP     +=           ⭐⭐ compute
#   STORE_GLOBAL  counter      ⭐⭐ write
```

```
⭐⭐ THREE STEPS. THE GIL CAN BE RELEASED BETWEEN ANY TWO OF THEM (Day 065).

⭐   thread A: LOAD counter  ⇒ 41
⭐   ⭐⭐ ── switch ──
⭐   thread B: LOAD counter  ⇒ 41        ⭐ reads the SAME stale value
⭐   thread B: ADD, STORE    ⇒ 42
⭐   ⭐⭐ ── switch ──
⭐   thread A: ADD, STORE    ⇒ 42        ⭐⭐ B's increment is GONE
⭐
⭐ ⇒ ⭐⭐ A LOST UPDATE. Two increments, one result. This is a READ-MODIFY-WRITE race,
⭐      and it is the same shape as the database concurrency bug in Stage 5.
```

```python
# ⭐⭐ REPRODUCE IT — this is the ten-line demo to have in your fingers:
counter = 0
def worker():
    global counter
    for _ in range(100_000): counter += 1

ts = [Thread(target=worker) for _ in range(10)]
[t.start() for t in ts]; [t.join() for t in ts]
print(counter)          # ⭐⭐ NOT 1,000,000. And a DIFFERENT number every run.
```

⚠️ ⭐⭐ **"A different number every run" is the defining property of a race**, and it is why they are
so expensive: **the bug is not reproducible, it does not appear under a debugger (which changes the
timing), and it may pass ten thousand test runs before failing in production.**

⭐ **Provoke it deliberately when testing:** `sys.setswitchinterval(1e-6)` makes switches far more
frequent, turning a rare interleaving into a common one.

# Part 2 — ⭐⭐ What *is* atomic, and why that is a trap

```python
# ⭐ These are single bytecodes or C-level operations, so they complete without a switch:
lst.append(x)              # ⭐ atomic
lst.pop()                  # ⭐ atomic
d[k] = v                   # ⭐ atomic (for a plain key/value)
d.setdefault(k, v)         # ⭐ atomic
x = y                      # ⭐ a single STORE
some_list[i] = v           # ⭐ atomic
```

```python
# ⚠️ ⭐⭐ THESE ARE NOT, and each is a real bug shape:
counter += 1                          # ⭐⭐ read-modify-write
d[k] = d[k] + 1                       # ⭐⭐ same
if k not in d: d[k] = v               # ⭐⭐ CHECK-THEN-ACT — two threads both pass the check
if lst: item = lst.pop()              # ⭐⭐ same — the list can empty between the two
x = shared.value; shared.value = x+1  # ⭐ obviously
```

```
⭐⭐ WHY THE "ATOMIC LIST" IS THE WRONG THING TO MEMORISE — three reasons:
⭐   1. ⭐⭐ IT IS AN IMPLEMENTATION DETAIL. Nothing in the language spec promises it.
⭐        It has changed between CPython versions, and it does not hold on PyPy or Jython.
⭐   2. ⭐⭐ FREE-THREADED PYTHON CHANGES IT (Day 065). Per-object locks preserve some of it
⭐        and the guarantees are deliberately narrower.
⭐   3. ⭐⭐ IT IS FRAGILE UNDER EDITING. `d[k] = v` is atomic. The moment someone adds a
⭐        conditional or a computed value it silently is not, and the diff looks harmless.
⭐
⭐ ⇒ ⭐⭐ SO: use it to UNDERSTAND why a bug happens. Never as a design.
```

⭐⭐ **`itertools.count()` is the honourable exception worth knowing:** its `__next__` is implemented
in C and is atomic, so it is a genuinely safe shared counter — **and it is far clearer than a lock
around an integer.**

```python
from itertools import count
ids = count()
next(ids)                  # ⭐⭐ thread-safe, no lock, no contention
```

# Part 3 — ⭐ The other race shapes

```python
# ⭐⭐ 1. CHECK-THEN-ACT — the most common one in real code:
if user_id not in cache:              # ⭐⭐ both threads see "not in"
    cache[user_id] = expensive_load(user_id)   # ⭐ both do the expensive work
# ⭐ FIX: setdefault, or a lock, or accept the duplicate work if it is idempotent and cheap
cache.setdefault(user_id, expensive_load(user_id))   # ⚠️ still calls expensive_load twice!
# ⭐⭐ REAL FIX: a lock, or a library that does single-flight
```

⭐⭐ **That `setdefault` line is worth staring at:** it makes the *insert* atomic and does **not** stop
both threads calling `expensive_load` — because the argument is evaluated before the call. **This is
Day 038's "the default is built even when unused" trap, promoted to a concurrency bug.**

```python
# ⭐ 2. TOCTOU — the filesystem version (Day 060):
if os.path.exists(p): os.remove(p)    # ⚠️ another process can delete it in between
try: os.remove(p)                      # ⭐ EAFP has no window
except FileNotFoundError: pass

# ⭐ 3. LAZY INITIALISATION — two threads both build the singleton:
if _instance is None:
    _instance = build()                # ⭐⭐ both may build; one result is discarded
# ⭐ FIX: a module-level object (Day 053), or a lock with a double check

# ⭐⭐ 4. THE ITERATION RACE — mutation from another thread while you iterate:
for k in d: ...                        # ⭐⭐ RuntimeError: dictionary changed size (Day 035)
for k in list(d): ...                  # ⭐ snapshot first
```

⚠️ ⭐ **Composite operations on "thread-safe" collections are still races.** `queue.Queue` is
internally locked, but `if not q.empty(): q.get()` is a check-then-act with a window — **use
`q.get(timeout=...)` and catch `Empty` instead.**

# Part 4 — ⭐⭐ The fixes, ranked

```
⭐⭐ IN ORDER OF PREFERENCE — and notice that the best two remove the race rather than guard it:

⭐ 1. ⭐⭐ DON'T SHARE. Pass messages through a Queue (Day 066); give each thread its own
⭐      state with threading.local(); return results instead of mutating shared structures.
⭐ 2. ⭐⭐ MAKE IT IMMUTABLE. A frozen dataclass or a tuple cannot be raced on (Day 025).
⭐      ⇒ ⭐ replace the whole object atomically rather than mutating fields.
⭐ 3. ⭐ USE A LOCK, around the smallest possible region — and never across I/O (Day 066).
⭐ 4. ⭐ USE THE RIGHT PRIMITIVE: itertools.count for ids, Semaphore for limits,
⭐      Event for signalling, Queue for handoff.
⭐ 5. ⭐⭐ PUSH THE PROBLEM DOWN: an atomic INCR in Redis, or a database transaction with
⭐      the right isolation level — ⭐ which is the same race, solved by people who
⭐      specialise in it (Stage 5).
```

```python
# ⭐ The lock version, done properly:
lock = threading.Lock()
def inc():
    global counter
    with lock:                 # ⭐⭐ smallest possible region
        counter += 1
# ⚠️ ⭐ and note the cost: 10 threads now serialise on this line. A lock is
#    a correctness fix that reintroduces the sequential bottleneck you wanted to avoid.
```

⭐⭐ **Every lock is a small serial section, so Amdahl's law (Day 064) applies to it directly** — a
lock in a hot path can make the threaded version slower than the sequential one. ⭐ **Locking correctly
and locking usefully are different problems, and the second is why the "don't share" answer is
better.**

```
⭐⭐ TESTING FOR RACES — they are non-deterministic, so:
⭐   · ⭐ run the operation 10,000× in a loop with an ASSERTION on the invariant
⭐   · ⭐⭐ sys.setswitchinterval(1e-6) to force frequent switches
⭐   · run it on CI repeatedly — ⭐ a race that fails 1 in 1,000 will show up in 10,000 runs
⭐   · ⭐ ThreadSanitizer and the free-threaded build surface far more (Day 065)
⭐ ⇒ ⚠️ ⭐⭐ AND ACCEPT: a passing test does NOT prove the absence of a race. Only the
⭐      design does — which is the argument for (1) and (2) above.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"The GIL makes `+=` safe"** | ⭐⭐ Three bytecodes. It races. Day 065. |
| ⭐ Relying on the atomic-operations list | ⭐⭐ Implementation detail; fragile under editing. |
| `if k not in d: d[k] = ...` | ⭐ Check-then-act — both threads pass. |
| `setdefault(k, expensive())` | ⭐⭐ The argument is evaluated regardless. |
| `if not q.empty(): q.get()` | ⭐ A window between them. Use `get(timeout=)`. |
| `os.path.exists()` then act | ⭐ TOCTOU. EAFP. |
| Iterating a dict another thread mutates | ⭐ `RuntimeError`. Snapshot with `list()`. |
| A lock around a large region | ⭐⭐ Serialises everything — Amdahl. |
| Holding a lock across I/O | ⭐ Day 066. |
| Believing a passing test proves safety | ⭐⭐ Only the design does. |
| Debugging a race with a debugger | ⭐ It changes the timing and the bug vanishes. |

## Interview questions

**Q: Is `counter += 1` thread-safe in Python?**
> No. It compiles to load, add, store — three bytecodes — and the GIL can be released between any two
> of them, so two threads can both read the same value, both add one, and both write back: two
> increments, one result. Ten threads incrementing a hundred thousand times reliably produces less
> than a million, and a different number every run. That non-determinism is what makes races expensive:
> it isn't reproducible, it disappears under a debugger because the timing changes, and it can pass
> thousands of test runs before failing in production.

**Q: But some operations are atomic — can you rely on that?**
> You can understand bugs with it; you shouldn't design with it. `list.append` and `d[k] = v` are
> effectively atomic because they're single C-level operations, but nothing in the language spec
> promises that. It's varied between CPython versions, it doesn't hold on other implementations, and
> free-threaded Python deliberately narrows the guarantees. The worst property is fragility under
> editing: `d[k] = v` is atomic, and the moment someone makes the value computed or adds a condition
> it isn't, and the diff looks harmless. The one I'd genuinely use is `itertools.count`, whose
> `__next__` is atomic in C and is a clearer shared counter than a lock around an integer.

**Q: What's a check-then-act race?**
> Two operations that are individually safe but not safe together — `if key not in cache:` followed by
> populating it. Both threads see the key missing and both do the work. It's the most common shape in
> real code because it doesn't look like shared mutation. And the tempting fix is subtle:
> `cache.setdefault(k, expensive())` makes the *insert* atomic but still calls `expensive()` in both
> threads, because the argument is evaluated before the call — which is Day 038's "the default is
> built even when unused" trap promoted to a concurrency bug.

**Q: How do you fix races, in order of preference?**
> Don't share — pass messages through a queue, or give each thread its own state, so there's nothing
> concurrent to race on. Make it immutable — a frozen dataclass can't be raced on, and you replace the
> whole object rather than mutating fields. Then locks, around the smallest region, never across I/O.
> Then the right primitive for the job. And finally push it down: an atomic `INCR` in Redis or a
> database transaction is the same race solved by people who specialise in it. The first two remove
> the race; the rest guard it, and guarding is easier to get wrong.

**Q: What's the cost of locking?**
> Serialisation. Every lock is a small sequential section, so Amdahl's law applies directly — a lock in
> a hot path can make the threaded version slower than the single-threaded one, while still being
> correct. That's why "locking correctly" and "locking usefully" are different problems, and why the
> design answer of not sharing is better than the careful-locking answer.

**Q: How do you test for a race?**
> Stress it — run the operation thousands of times with an assertion on the invariant, and shorten
> `sys.setswitchinterval` to force frequent switches so a rare interleaving becomes common. Repeat it
> in CI, because a one-in-a-thousand failure shows up over ten thousand runs. But I'd be explicit that
> a passing test doesn't prove the absence of a race — it only failed to find one this time. The only
> thing that proves safety is the design.

## 🎙️ Articulation drill

Record two minutes: **"Ten threads increment a shared counter a hundred thousand times each. What do
you get, and why?"**

⭐ Answer with the number and then the mechanism: **less than a million, and a different number every
run.** `counter += 1` is load, add, store — **three bytecodes, and the GIL can be released between any
two of them**, so two threads read the same value, both add one, and one increment is lost.

⭐⭐ **Then correct the misconception, because this question is usually testing for it:** *"the GIL
doesn't help here. It guarantees one bytecode at a time, not one statement — it protects the
interpreter's own state, not mine."*

⭐ Then the fixes, ranked, and be clear which ones *remove* the problem: **don't share at all — a
queue, or per-thread state; or make the state immutable. Failing that, a lock around the smallest
region, or `itertools.count`, whose `__next__` is atomic in C.**

⭐⭐ **And close on the cost, which is the part that shows judgement:** *"a lock makes it correct and
reintroduces a serial section — Amdahl's law applies to it directly, so a lock in a hot path can make
the threaded version slower than the sequential one while still being right. That's why 'don't share'
beats 'lock carefully': one removes the race, the other manages it, and managing it is what people get
wrong."*
