# Day 155

**L-155** · **Deployment strategies** — rolling, blue-green, canary, and ⭐⭐ decoupling deploy from release

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: deploying is putting code on servers and releasing is exposing behaviour
> to users — and once you stop treating those as the same event, most deployment risk becomes a
> configuration change you can undo in one second instead of a rollout you have to reverse.**
>
> ⭐ Day 149 made a single deploy not drop requests. ⭐⭐ Today: how to make a *bad* deploy cheap, which
> is a different problem and the one that actually keeps you up at night.

# Part 1 — ⭐⭐ The three strategies, judged honestly

```
⭐⭐ ROLLING — replace pods a few at a time. ⭐ The Kubernetes default.
⭐   ⭐ + no extra infrastructure; ⭐ gradual
⭐   ⭐ − ⭐⭐ OLD AND NEW RUN SIMULTANEOUSLY for the whole rollout ⇒ every
⭐        schema and cache-key compatibility rule (Days 138, 143) applies
⭐   ⭐ − ⭐⭐ ROLLBACK IS ANOTHER ROLLING DEPLOY — minutes, not seconds
⭐   ⇒ ⭐ Right for most services, most of the time.
⭐
⭐⭐ BLUE-GREEN — two full environments; flip the router.
⭐   ⭐ + ⭐⭐ INSTANT ROLLBACK (flip back) — the whole point
⭐   ⭐ + you can smoke-test green with real infrastructure before any user
⭐        traffic reaches it
⭐   ⭐ − ⭐⭐ 2× COMPUTE during the switch
⭐   ⭐ − ⭐⭐ THE DATABASE IS **NOT** DUPLICATED. Blue and green share it, so
⭐        ⭐ the "instant rollback" is only instant for STATELESS changes.
⭐        ⭐⭐ If green ran a migration, flipping back gives you old code
⭐        against a new schema — ⭐ which is exactly why expand/contract
⭐        exists, and why blue-green does NOT remove that discipline.
⭐   ⭐ − ⭐ in-flight connections on blue are cut or must drain
⭐
⭐⭐ CANARY — send a small % of traffic to the new version, watch, increase.
⭐   ⭐ + ⭐⭐ THE ONLY STRATEGY THAT LIMITS BLAST RADIUS. A bad release harms
⭐        1% of users for 5 minutes rather than 100% for however long you take
⭐        to notice.
⭐   ⭐ + you get REAL production signal — real traffic shapes, real data
⭐   ⭐ − ⭐⭐ REQUIRES METRICS PER VERSION (Day 147) OR IT IS THEATRE. Without
⭐        a `version` label you cannot tell whether the canary is worse.
⭐   ⭐ − ⭐ two versions for longer ⇒ compatibility rules apply for longer
⭐   ⭐ − ⭐⭐ 1% OF TRAFFIC MAY BE TOO LITTLE TO DETECT ANYTHING. At 100 rps,
⭐        1% for 5 minutes is 300 requests — ⭐ not enough to see a 0.5% error
⭐        rate. ⭐⭐ The canary must run long enough to be statistically real,
⭐        and people almost never compute that.
```

```
⭐⭐ AND THE POINT THAT TIES THEM TOGETHER: EVERY ONE OF THESE HAS A WINDOW
⭐   WHERE TWO VERSIONS ARE LIVE. ⭐⭐ THERE IS NO STRATEGY THAT AVOIDS IT —
⭐   even blue-green, during the flip and during draining.
⭐   ⇒ ⭐⭐ THEREFORE BACKWARD COMPATIBILITY IS NOT A STRATEGY CHOICE. IT IS A
⭐        PERMANENT REQUIREMENT, and choosing blue-green because "then we
⭐        don't need expand/contract" is the most expensive mistake in this day.
```

# Part 2 — ⭐⭐ Decoupling deploy from release

```
⭐⭐ THE REFRAME THAT CHANGES EVERYTHING:

⭐   ⭐ DEPLOY  = the code is running on servers.       ⭐ A technical event.
⭐   ⭐ RELEASE = users experience the new behaviour.   ⭐ A product event.
⭐
⭐   ⭐⭐ IF THEY ARE THE SAME EVENT, THEN:
⭐        · turning a feature off requires a DEPLOY (Day 150 — ⭐ ten minutes
⭐          during the incident it exists for)
⭐        · you cannot ship half-finished work, so ⭐⭐ you keep long-lived
⭐          branches, which is Day 088's merge pain, permanently
⭐        · you cannot give it to 5% of users, or to internal staff first
⭐        · every release is all-or-nothing for everyone
⭐
⭐   ⭐⭐ IF THEY ARE SEPARATE (a flag), THEN:
⭐        · ⭐ code ships dark, continuously, in small pieces
⭐        · ⭐⭐ ROLLBACK IS A FLAG FLIP: ~1 SECOND, NO DEPLOY, NO BUILD
⭐        · ⭐ 1% → 10% → 100%, with the metrics watched at each step
⭐        · ⭐⭐ THE PERSON WHO TURNS IT ON DOES NOT HAVE TO BE AN ENGINEER
⭐
⭐   ⇒ ⭐⭐ THIS IS THE HIGHEST-LEVERAGE IDEA IN THE DAY, AND IT IS THE ANSWER
⭐        TO "how do you deploy safely?" ⭐ The safest deploy is one that
⭐        changes nothing users can see.
```

```python
# ⭐ flags are a DEPENDENCY (Day 132), so they are overridable and testable
def checkout(user: User, flags: Flags = Depends(get_flags)):
    if flags.enabled("new_pricing", user=user):     # ⭐⭐ per-user, evaluated per request
        return new_pricing(user)
    return old_pricing(user)
```

```
⭐⭐ THE FOUR RULES THAT KEEP FLAGS FROM BECOMING THE NEXT PROBLEM:
⭐  1. ⭐⭐ EVERY FLAG HAS AN OWNER AND AN EXPIRY DATE. ⭐ A flag is temporary
⭐       scaffolding. ⭐⭐ 200 permanent flags = 2²⁰⁰ possible configurations,
⭐       of which you test one. ⭐ Untested combinations are where the bugs go.
⭐  2. ⭐ EVALUATE ONCE PER REQUEST AND PASS THE RESULT DOWN. ⭐⭐ A flag that
⭐       changes MID-REQUEST gives you half of each code path — ⭐ a genuinely
⭐       baffling class of bug.
⭐  3. ⭐⭐ FAIL TO THE OLD BEHAVIOUR if the flag service is unreachable.
⭐       ⭐ The default must be the known-good path, always.
⭐  4. ⭐ STICKY BY USER, not random per request — ⭐⭐ hash the user id, so a
⭐       user's experience does not flicker between two designs on reload.
⭐
⭐ ⭐⭐ AND THE HONEST COST: A FLAG IS A BRANCH, AND EVERY BRANCH IS A PATH
⭐   THAT NEEDS A TEST. ⭐ Test both sides while the flag lives, and DELETE THE
⭐   FLAG AND THE DEAD PATH the week it reaches 100% — ⭐⭐ flag debt is real
⭐   debt, and it is the one people are worst at repaying.
```

# Part 3 — ⭐⭐ Making a canary actually mean something

```
⭐⭐ A CANARY WITHOUT AUTOMATED ANALYSIS IS A HUMAN STARING AT A DASHBOARD,
⭐   AND HUMANS ARE BAD AT THAT FOR TWENTY MINUTES.

⭐   ⭐ 1. deploy the canary with a ⭐⭐ `version` LABEL ON EVERY METRIC
⭐        (Day 147) and every log line (Day 146)
⭐   ⭐ 2. route 1–5% of traffic
⭐   ⭐ 3. ⭐⭐ COMPARE CANARY VS BASELINE ON THE SAME WINDOW — not against
⭐        yesterday. ⭐ Traffic shape varies by hour; a same-window comparison
⭐        controls for it automatically.
⭐   ⭐ 4. promote or roll back AUTOMATICALLY on the comparison

⭐⭐ WHAT TO COMPARE (and "errors" alone is not enough):
⭐   ⭐ error RATE (ratio, Day 147) · ⭐ p95 and p99 latency
⭐   ⭐⭐ CPU AND MEMORY PER REQUEST — ⭐ a memory leak shows here long before
⭐        it shows as an error, and it is the classic thing a short canary
⭐        misses entirely
⭐   ⭐⭐ QUERY COUNT PER REQUEST — ⭐ an N+1 (Day 136) is not an error and
⭐        not slow at 1% traffic; it becomes an outage at 100%
⭐   ⭐ BUSINESS METRICS — ⭐⭐ checkout completion, signup rate. ⭐ A release
⭐        that is technically perfect and drops conversion 20% is a bad
⭐        release, and NOTHING in your technical metrics will say so.

⭐⭐ THE THREE FAILURE MODES OF CANARIES, ALL OF WHICH LOOK LIKE SUCCESS:
⭐  1. ⭐⭐ TOO SHORT. Leaks, cache-fill effects, and cron-triggered paths need
⭐       time. ⭐ A 5-minute canary proves the process starts.
⭐  2. ⭐⭐ TOO SMALL TO BE SIGNIFICANT. 300 requests cannot distinguish a 0.5%
⭐       error rate from zero. ⭐ Compute the number you need before you start.
⭐  3. ⭐⭐ UNREPRESENTATIVE TRAFFIC. If routing is by IP hash, the canary may
⭐       see only one region, or only the customers whose integration polls
⭐       every second. ⭐ Randomise, and check the canary's traffic MIX.
```

# Part 4 — ⭐ The one-way doors

```
⭐⭐ SOME CHANGES CANNOT BE ROLLED BACK BY ANY DEPLOYMENT STRATEGY. RECOGNISE
⭐   THEM BEFORE SHIPPING, BECAUSE THE STRATEGY WILL NOT SAVE YOU:

⭐   ⭐⭐ A DESTRUCTIVE MIGRATION. `DROP COLUMN` — ⭐ the data is gone; rolling
⭐        back the code does not bring it back (Day 138).
⭐   ⭐⭐ A DATA BACKFILL that overwrites. ⭐ Keep the original column until you
⭐        are certain.
⭐   ⭐⭐ AN EXTERNAL SIDE EFFECT. Emails sent, payments captured, webhooks
⭐        delivered (Day 158). ⭐ You cannot un-send.
⭐   ⭐ A MESSAGE FORMAT CHANGE where old consumers cannot parse new messages
⭐        (Day 142) — ⭐⭐ the queue now holds messages nobody can read.
⭐   ⭐ AN API CONTRACT CHANGE clients have already adopted (Day 125).
⭐
⭐   ⇒ ⭐⭐ FOR THESE, THE STRATEGY IS *SEQUENCING*, NOT ROLLBACK:
⭐        expand/contract, dual-write, a shadow period, ⭐ and a deliberate
⭐        delay between "new code is live" and "old thing is removed".
⭐   ⇒ ⭐⭐ AND THE HABIT WORTH BUILDING: BEFORE EVERY DEPLOY, ASK "IF THIS IS
⭐        WRONG, WHAT IS MY UNDO?" ⭐ If the answer is not one sentence, you
⭐        are not ready to ship it.
```

```
⭐ THREE MORE TECHNIQUES WORTH NAMING:
⭐   ⭐⭐ DARK LAUNCH / SHADOW TRAFFIC — send a COPY of production requests to
⭐     the new version and ⭐ DISCARD ITS RESPONSES. ⭐⭐ You get real load and
⭐     real data with zero user risk. ⭐ Caveat: it must not write, or you
⭐     double every side effect — ⭐⭐ which is the mistake that makes shadow
⭐     traffic famous.
⭐   ⭐ RING DEPLOYMENT — internal staff → beta users → 1% → everyone.
⭐     ⭐⭐ Your own team as ring 0 is the cheapest canary that exists.
⭐   ⭐ ⭐⭐ ROLLBACK ≠ REVERT. Rolling back the DEPLOY (point at the old
⭐     digest) is instant. Reverting the COMMIT is a code change that goes
⭐     through CI. ⭐ Do the first immediately, the second calmly afterwards —
⭐     ⭐⭐ and people conflate them and spend twenty minutes writing a revert
⭐     PR while the site is down.
```

# Part 5 — ⭐ The deployment checklist

```
⭐⭐ BEFORE:
⭐   □ ⭐ artefact built once, tested, tagged by digest (Day 154)
⭐   □ ⭐⭐ migrations are EXPAND-ONLY and already applied (Day 138)
⭐   □ ⭐ new code works against the OLD schema, and old code against the NEW
⭐   □ ⭐ feature flag exists and defaults OFF
⭐   □ ⭐⭐ THE UNDO IS ONE SENTENCE, and someone has said it out loud
⭐   □ ⭐ not Friday 17:00 — ⭐⭐ not superstition: it is that the people who
⭐        understand the change must be available for the window in which it
⭐        fails
⭐
⭐⭐ DURING:
⭐   □ ⭐ watch error rate, p99, saturation — ⭐⭐ SPLIT BY VERSION
⭐   □ ⭐ watch the queue depth and oldest-message age (Day 147)
⭐   □ ⭐⭐ do not start a second change while the first is rolling — ⭐ two
⭐        changes in flight means you cannot attribute a regression to either
⭐
⭐⭐ AFTER:
⭐   □ ⭐ smoke tests passed automatically
⭐   □ ⭐⭐ WATCH FOR AT LEAST ONE FULL TRAFFIC CYCLE — ⭐ a nightly job, a
⭐        cache expiry, a token refresh, a Monday morning. ⭐⭐ "It's been fine
⭐        for ten minutes" is not evidence about the 3 a.m. batch.
⭐   □ ⭐ the contract migration (the DROP) is scheduled for LATER, separately
⭐   □ ⭐ flag ramp scheduled, flag deletion ticketed with a date
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Choosing blue-green to avoid backward compatibility | The database isn't duplicated. Two versions are always live somewhere. |
| Assuming blue-green rollback is instant for everything | Only for stateless changes. A migration on green makes the flip one-way. |
| A canary with no per-version metrics | Theatre. You can't tell whether the canary is worse. |
| A canary too short or too small | 300 requests can't detect a 0.5% error rate; five minutes can't detect a leak. |
| Canary compared against yesterday | Traffic shape varies by hour. Compare to the baseline over the same window. |
| Watching only errors on a canary | Memory per request and query count per request fail later and hurt more. |
| Ignoring business metrics | A technically perfect release that drops conversion 20% is a bad release. |
| Deploy and release as one event | Turning a feature off needs a deploy — during the incident it exists for. |
| Flags with no owner or expiry | 200 flags is 2²⁰⁰ configurations and you test one. |
| Evaluating a flag more than once per request | Half of each code path, and a baffling bug class. |
| Failing open to the new behaviour when the flag service is down | The default must be the known-good path. |
| Random rather than sticky flag assignment | A user's experience flickers between two designs on reload. |
| Shadow traffic that writes | Every side effect happens twice. |
| Confusing rollback with revert | Rollback is instant; a revert PR goes through CI. Do the first now. |
| No stated undo before deploying | If the undo isn't one sentence, the change isn't ready. |
| Two changes rolling at once | You can't attribute a regression to either. |
| Declaring success after ten minutes | You haven't seen the nightly job, the cache expiry or Monday morning. |

## Interview questions

**Q: Rolling, blue-green or canary?**

> Depends what you're optimising, and I'd say what each actually buys. Rolling is the default and is
> fine for most services, but rollback is another rolling deploy — minutes, not seconds. Blue-green
> buys instant rollback by flipping a router, and lets you smoke-test the new environment with real
> infrastructure before any user sees it; the costs are double compute and, importantly, that **the
> database is not duplicated** — so if green ran a migration, flipping back means old code against a
> new schema. That's why blue-green doesn't remove the need for expand/contract, and choosing it
> because "then we don't need that discipline" is the expensive mistake. Canary is the only one that
> limits blast radius: a bad release hurts one percent of users for five minutes instead of everyone
> until you notice. The thing they share is that every strategy has a window where two versions are
> live, so backward compatibility isn't a strategy choice, it's permanent.

**Q: What does "decouple deploy from release" mean and why does it matter?**

> Deploying is a technical event — the code is on servers. Releasing is a product event — users
> experience the new behaviour. If they're the same event, then turning a feature off requires a
> deploy, which takes ten minutes during exactly the incident it exists for; you can't ship
> half-finished work so you keep long-lived branches and inherit all the merge pain; and every
> release is all-or-nothing for everyone. Separate them with a flag and code ships dark and
> continuously, rollback becomes a one-second flag flip with no build, you can ramp one to ten to a
> hundred percent watching metrics, and the person who turns it on doesn't have to be an engineer.
> It's the highest-leverage idea here: the safest deploy is one that changes nothing users can see.

**Q: What's the cost of feature flags?**

> Every flag is a branch, so it doubles the paths that need testing, and they multiply — two hundred
> permanent flags is two-to-the-two-hundred possible configurations of which you test one, and the
> untested combinations are where the bugs live. So: every flag gets an owner and an expiry date, and
> gets deleted along with the dead path the week it hits a hundred percent. Three other rules —
> evaluate once per request and pass the result down, because a flag that changes mid-request gives
> you half of each code path; fail to the *old* behaviour if the flag service is unreachable; and
> make assignment sticky by hashing the user id, so someone's experience doesn't flicker between two
> designs when they reload.

**Q: Your canary looks fine after five minutes at 1%. Ship it?**

> Probably not, and for three separate reasons. Statistically: at a hundred requests per second, one
> percent for five minutes is about three hundred requests, which cannot distinguish a half-percent
> error rate from zero — I should compute the sample I need before I start. Temporally: five minutes
> proves the process starts. It doesn't cover a memory leak, cache-fill effects, the nightly batch,
> or a token refresh. And representatively: if routing is by IP hash the canary may be seeing one
> region, or only the customer whose integration polls every second. I'd also want to be comparing
> against the baseline over the *same* window rather than yesterday, and looking at memory and query
> count per request, not just errors — because an N+1 isn't an error and isn't slow at one percent
> traffic, and is an outage at a hundred.

**Q: What can't be rolled back?**

> Anything with an external or destructive effect. A dropped column — the data's gone and rolling
> back the code doesn't bring it back. An overwriting backfill. Emails sent, payments captured,
> webhooks delivered — you can't un-send. A message format change where old consumers can't parse
> what's in the queue. An API contract clients have already adopted. For all of these the strategy is
> sequencing rather than rollback: expand/contract, dual writes, a shadow period, and a deliberate
> gap between "new code is live" and "old thing is removed". The habit I'd build is asking, before
> every deploy, "if this is wrong, what's my undo?" — and if the answer isn't one sentence, it isn't
> ready to ship.

## Mini task

1. ⭐ Do a rolling deploy under load and measure the error rate through it. Then do it with a broken image and time your rollback.
2. ⭐⭐ Add a `version` label to every metric and log line. Confirm you can split error rate by version in one query.
3. ⭐⭐ Run a canary at 5%. Compute in advance how many requests you need to detect a 1% error rate, then check whether your window supplies them.
4. ⭐ Introduce a deliberate N+1 in the canary. Confirm it shows in query-count-per-request and not in errors or p99 at 5%.
5. ⭐⭐ Build a minimal flag service: sticky by user hash, defaults off, fails closed to old behaviour. Kill it and confirm the old path runs.
6. ⭐⭐ Evaluate a flag twice in one request and construct the half-and-half bug. Then evaluate once and pass it down.
7. ⭐ Set up shadow traffic to a second deployment with responses discarded. Verify it performs no writes.
8. ⭐⭐ Write the undo sentence for your last three deploys. For any that need more than one sentence, write the sequencing plan that would have.

## 🎙️ Articulation drill

**Two minutes: "How do you ship safely?"**

Open on the distinction — deploy versus release — because it reframes the question, and give the
consequence: rollback becomes a one-second flag flip instead of a rollout you have to reverse. Then
cover the strategies briefly and honestly, using blue-green's shared database to make the point that
**backward compatibility is permanent regardless of strategy**. Then canary, with the part most
people skip: it needs per-version metrics, a sample size you computed, a long enough window to catch
a leak, and a look at business metrics. Close on one-way doors — sent emails, dropped columns,
captured payments — and the habit that covers all of it: **before every deploy, say your undo out
loud; if it isn't one sentence, it isn't ready.**
