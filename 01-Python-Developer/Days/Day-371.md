# Day 371 🚀

**P-371** · 🚀 **Deployment strategies** — ⭐⭐ and the precondition nobody states

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every zero-downtime deployment strategy has exactly the same
> precondition — two versions of your code must be able to run simultaneously against one database
> and one set of queues — and if that is not true, rolling, blue-green and canary are all equally
> broken, they just fail in different-looking ways.**

---

# Part 1 — ⭐⭐ The precondition, stated properly

```
⭐⭐ DURING ***ANY*** GRADUAL DEPLOYMENT THERE IS A WINDOW —
⭐   seconds to hours — WHERE v1 AND v2 ARE BOTH SERVING.
⭐   ⇒ ⭐⭐ THEY SHARE: THE DATABASE, THE QUEUES, THE CACHE, THE
⭐     SESSION STORE, AND EACH OTHER'S IN-FLIGHT WORK.

⭐⭐ SO ***FIVE*** COMPATIBILITY REQUIREMENTS, AND MOST TEAMS
⭐   ONLY KNOW THE FIRST:
⭐   ① ⭐⭐ ***SCHEMA*** — v1 must work against v2's schema.
⭐      ⭐ Expand/contract (Day 283): add nullable, backfill,
⭐      dual-write, switch reads, ⭐ and only then drop —
⭐      ⭐⭐ IN A ***LATER RELEASE***, NOT A LATER STEP.
⭐   ② ⭐⭐ ***MESSAGE SCHEMA*** — v1 consumers will receive v2's
⭐      messages and vice versa. ⭐ Additive only (Day 333).
⭐      ⭐⭐ AND THE ONE PEOPLE MISS: A MESSAGE PUBLISHED BY v2
⭐      AND SAT IN A QUEUE FOR AN HOUR IS CONSUMED BY WHATEVER
⭐      IS RUNNING ***THEN***, WHICH MAY BE v1 AFTER A ROLLBACK.
⭐   ③ ⭐ ***CACHE*** — if the shape of a cached value changed,
⭐      ⭐⭐ v1 WILL DESERIALISE v2'S ENTRY AND CRASH. ⭐ Version
⭐      the cache key prefix; do not reuse it.
⭐   ④ ⭐⭐ ***SESSION / COOKIE FORMAT*** — a user logged in on
⭐      v2 lands on v1 on the next request.
⭐   ⑤ ⭐⭐ ***API CONTRACT*** — a browser loads v2's JavaScript
⭐      and then calls v1's API. ⭐ This is the frontend-specific
⭐      version and it is invisible in backend testing.

⭐⭐ ⇒ AND THE TEST THAT MAKES IT CONCRETE, WHICH ALMOST NOBODY
⭐   RUNS: ***DEPLOY v2 TO ONE REPLICA OF THREE AND RUN YOUR
⭐   INTEGRATION SUITE THROUGH THE LOAD BALANCER.*** ⭐ Requests
⭐   land on both versions at random.
⭐   ⇒ ⭐⭐ IF THAT PASSES, EVERY STRATEGY BELOW WORKS. IF IT
⭐     FAILS, NO STRATEGY BELOW WORKS AND YOU HAVE FOUND THE
⭐     REAL PROBLEM.
```

# Part 2 — ⭐ Recreate and rolling

```
⭐⭐ ***RECREATE*** — stop all, start all.
⭐   ⭐ ✔ Simple. ✔ ⭐⭐ NO COMPATIBILITY REQUIREMENT AT ALL,
⭐     because the versions never coexist.
⭐   ⭐ ✘ Downtime equal to shutdown + startup.
⭐   ⇒ ⭐⭐ AND IT IS THE ***CORRECT*** CHOICE SOMETIMES: a
⭐     migration that genuinely cannot be made backward-
⭐     compatible, ⭐ a singleton batch processor, ⭐ or an
⭐     internal tool where two minutes at 3 a.m. costs nothing.
⭐   ⇒ ⭐ Saying "I'd take the downtime here, and here is why" is
⭐     a stronger answer than contorting a schema change to
⭐     avoid it.

⭐⭐ ***ROLLING*** — replace instances a few at a time.
⭐   ⭐ ✔ No downtime, ⭐ no extra capacity beyond the surge.
⭐   ⭐ ✔ The default in Kubernetes and ECS.
⭐   ⭐ ✘ ⭐⭐ BOTH VERSIONS LIVE FOR THE WHOLE ROLLOUT — the
⭐     precondition is mandatory.
⭐   ⭐ ✘ ⭐⭐ ROLLBACK IS ANOTHER ROLLING UPDATE, SO IT TAKES
⭐     THE SAME TIME AS THE DEPLOY DID. ⭐ If your rollout takes
⭐     eight minutes, your worst-case exposure is eight minutes.

⭐⭐ THE TWO KNOBS THAT MATTER:
⭐   ⭐ `maxUnavailable` ⇒ ⭐⭐ HOW MUCH CAPACITY YOU LOSE DURING
⭐     THE ROLLOUT. ⭐ At `25%` with four replicas you run on
⭐     three — ⭐⭐ AND IF THREE CANNOT CARRY PEAK TRAFFIC, YOUR
⭐     DEPLOY IS A CAPACITY INCIDENT.
⭐   ⭐ `maxSurge` ⇒ how much extra you temporarily run. ⭐ Costs
⭐     money for minutes; ⭐⭐ USUALLY THE RIGHT KNOB TO OPEN AND
⭐     THE WRONG ONE TO IGNORE.
⭐   ⇒ ⭐ `maxUnavailable: 0, maxSurge: 25%` ⇒ ⭐⭐ NEVER BELOW
⭐     FULL CAPACITY, AT THE COST OF A LITTLE EXTRA COMPUTE.
⭐     ⭐ That is the setting most services should use and few do.

⭐⭐ AND THE THING THAT MAKES ROLLING WORK AT ALL: ⭐⭐ READINESS
⭐   PROBES. ⭐ Without them the orchestrator replaces the next
⭐   instance as soon as the previous ***process starts***,
⭐   ⭐⭐ NOT WHEN IT CAN SERVE — so a rollout of a broken image
⭐   proceeds happily to 100% and you have replaced every
⭐   working pod with a broken one.
```

# Part 3 — ⭐⭐ Blue-green

```
⭐⭐ TWO COMPLETE ENVIRONMENTS. ⭐ Blue serves; green is deployed
⭐   and tested; ⭐ the router switches; ⭐ blue stays warm as the
⭐   rollback.

⭐⭐ ✔ WHAT IT BUYS:
⭐   ⭐ ⭐⭐ INSTANT ROLLBACK — switch back. ⭐ Seconds, not
⭐     another rolling update. ⭐⭐ THIS IS THE ***ONLY*** REAL
⭐     REASON TO CHOOSE IT.
⭐   ⭐ Test the full environment before any user reaches it.
⭐   ⭐ The cutover is one atomic-ish operation.

⭐⭐ ✘ WHAT IT COSTS:
⭐   ⭐ ⭐⭐ DOUBLE THE INFRASTRUCTURE DURING THE SWITCH — and
⭐     for a large fleet that is a real bill.
⭐   ⭐ ⭐⭐ THE DATABASE IS ***NOT*** DUPLICATED. ⭐ Blue and
⭐     green share it, ⭐⭐ SO THE COMPATIBILITY PRECONDITION
⭐     APPLIES IN FULL — people believe blue-green exempts them
⭐     and it does not.
⭐   ⭐ ⭐⭐ IN-FLIGHT STATE IS LOST OR STRANDED: long-running
⭐     requests, WebSocket connections, and jobs a blue worker
⭐     had claimed.
⭐   ⭐ Warm caches on green are cold at cutover ⇒ ⭐ a latency
⭐     spike exactly at the moment of maximum attention.

⭐⭐ AND THE ROLLBACK CAVEAT THAT UNDOES THE MAIN BENEFIT:
⭐   ⭐ ⭐⭐ ONCE GREEN HAS WRITTEN DATA IN THE NEW FORMAT,
⭐     SWITCHING BACK TO BLUE MEANS BLUE MUST HANDLE IT.
⭐   ⇒ ⭐⭐ SO "INSTANT ROLLBACK" IS ONLY TRUE FOR THE ***CODE***.
⭐     ⭐ The data has already moved forward — which is Day 370's
⭐     rule appearing again and is the single most important
⭐     caveat to state.
```

# Part 4 — ⭐⭐ Canary

```
⭐⭐ ROUTE A SMALL FRACTION OF TRAFFIC TO v2, ⭐ compare
⭐   metrics, ⭐ increase or roll back.
⭐   ⭐ 1% → 5% → 25% → 50% → 100%, with a bake time at each.

⭐⭐ ✔ WHAT IT BUYS — ⭐ and it is the strongest property in this
⭐   day:
⭐   ⭐ ⭐⭐ A BAD DEPLOY AFFECTS 1% OF USERS INSTEAD OF 100%.
⭐   ⭐ ⭐⭐ AND IT IS THE ONLY STRATEGY THAT DETECTS PROBLEMS
⭐     ***TESTS CANNOT***: a slow query that only appears at
⭐     production data volume, a memory leak that takes twenty
⭐     minutes, a third party that behaves differently under
⭐     real load.

⭐⭐ ✘ WHAT IT COSTS:
⭐   ⭐ ⭐⭐ IT REQUIRES METRICS GOOD ENOUGH TO COMPARE TWO
⭐     POPULATIONS. ⭐ Without per-version labels on your
⭐     metrics, ⭐⭐ YOU CANNOT TELL WHETHER THE CANARY IS WORSE
⭐     — AND THEN YOU ARE JUST DEPLOYING SLOWLY. ⭐ This is the
⭐     precondition of the precondition.
⭐   ⭐ ⭐⭐ AT 1% OF TRAFFIC, A 1-IN-1000 BUG NEEDS 100,000
⭐     REQUESTS TO APPEAR ***ONCE***. ⭐ So a low-traffic service
⭐     cannot canary meaningfully at small percentages —
⭐     ⭐⭐ THE STATISTICS SIMPLY ARE NOT THERE, and pretending
⭐     otherwise is deployment theatre.
⭐   ⭐ Sticky routing matters: ⭐⭐ A USER BOUNCING BETWEEN
⭐     VERSIONS MID-FLOW SEES INCONSISTENT BEHAVIOUR. ⭐ Route by
⭐     a hash of the user id, not per request.

⭐⭐ WHAT TO COMPARE — ⭐ and "no errors" is not enough:
⭐   ⭐ Error rate, latency percentiles, ⭐ saturation (CPU,
⭐     memory, ⭐⭐ AND ***RESTART COUNT***, which catches an
⭐     OOMKill loop that error rate hides).
⭐   ⭐ ⭐⭐ AND ***BUSINESS*** METRICS: checkout completion,
⭐     signup rate. ⭐ A deploy that is technically perfect and
⭐     drops conversion by 8% is a bad deploy, ⭐⭐ AND ONLY THIS
⭐     CATEGORY OF METRIC EVER NOTICES.
⭐   ⭐ ⭐⭐ COMPARE CANARY AGAINST ***BASELINE RUNNING NOW***,
⭐     NOT AGAINST YESTERDAY — ⭐ or a Monday-morning traffic
⭐     shape reads as a regression.

⭐⭐ AND THE HONEST NOTE ON AUTOMATION: ⭐ Argo Rollouts, Flagger
⭐   and similar automate the analysis and the promotion.
⭐   ⭐⭐ THEY ARE EXCELLENT AND THEY ARE ALSO A SUBSTANTIAL
⭐   OPERATIONAL COMMITMENT — ⭐ a scripted percentage shift plus
⭐   a metrics query gets most of the value at a fraction of the
⭐   cost.
```

# Part 5 — ⭐⭐ Feature flags: separating deploy from release

```
⭐⭐ THE REFRAME THAT MATTERS MOST IN THIS DAY:
⭐   ***DEPLOYMENT MOVES CODE. RELEASE EXPOSES BEHAVIOUR. THEY
⭐      DO NOT HAVE TO HAPPEN TOGETHER.***
⭐   ⇒ ⭐⭐ WITH FLAGS, THE DEPLOY IS BORING — the new code is
⭐     present and inert — AND THE ***RELEASE*** IS A
⭐     CONFIGURATION CHANGE THAT TAKES EFFECT IN SECONDS AND
⭐     REVERSES IN SECONDS.
⭐   ⇒ ⭐⭐ AND THAT REVERSAL IS FASTER AND SAFER THAN ***ANY***
⭐     DEPLOYMENT STRATEGY, BECAUSE NO PROCESS RESTARTS AND NO
⭐     SCHEMA MOVES.

⭐⭐ WHAT FLAGS GIVE YOU:
⭐   ⭐ Kill switches for risky paths.
⭐   ⭐ Percentage rollout ⭐⭐ INDEPENDENT OF INFRASTRUCTURE —
⭐     you can canary a ***feature*** without canarying a
⭐     ***deployment***.
⭐   ⭐ Per-tenant or per-user targeting for a real beta.
⭐   ⭐ A/B experiments as a side effect.

⭐⭐ AND THE FOUR COSTS, STATED HONESTLY:
⭐   ① ⭐⭐ EVERY FLAG IS A BRANCH THAT LIVES FOREVER UNLESS
⭐      REMOVED (Day 368). ⭐ N flags is 2^N possible states,
⭐      ⭐⭐ AND YOU TEST TWO OF THEM.
⭐   ② ⭐ The evaluation service is now on your request path ⇒
⭐      ⭐⭐ IT NEEDS A LOCAL CACHE AND A SAFE DEFAULT, OR YOU
⭐      HAVE ADDED A SINGLE POINT OF FAILURE TO EVERY REQUEST
⭐      (Day 339's static stability).
⭐   ③ ⭐⭐ A FLAG READ IN A LOOP IS A LATENCY BUG — ⭐ evaluate
⭐      once per request, not per iteration.
⭐   ④ ⭐ Flags in tests multiply the matrix; ⭐⭐ TEST THE
⭐      ***ON*** PATH AND THE ***OFF*** PATH FOR ANYTHING THAT
⭐      MATTERS, AND ACCEPT YOU CANNOT TEST COMBINATIONS.

⭐⭐ ⇒ THE DISCIPLINE: ***EVERY FLAG HAS AN OWNER, A PURPOSE
⭐   AND AN EXPIRY DATE, AND A REPORT LISTS STALE ONES
⭐   WEEKLY.*** ⭐ Removing a flag is part of finishing the
⭐   feature, not a separate project nobody funds.
```

# Part 6 — ⭐ Choosing, with the honest decision rule

```
⭐⭐ THE DECISION TABLE:
⭐   ⭐ ***RECREATE*** ⇒ downtime is acceptable, ⭐ or the change
⭐     genuinely cannot be made backward-compatible.
⭐   ⭐ ⭐⭐ ***ROLLING*** ⇒ THE DEFAULT. ⭐ Costs nothing extra,
⭐     works everywhere, ⭐ and is sufficient for most services.
⭐   ⭐ ***BLUE-GREEN*** ⇒ when ***rollback speed*** is worth
⭐     double infrastructure. ⭐ Regulated environments, ⭐ big
⭐     releases, ⭐ services where a rolling rollback is too slow.
⭐   ⭐ ***CANARY*** ⇒ when you have ⭐⭐ ENOUGH TRAFFIC FOR
⭐     STATISTICS AND METRICS GOOD ENOUGH TO COMPARE. ⭐ High
⭐     blast radius, ⭐ user-facing changes.
⭐   ⭐ ⭐⭐ ***FLAGS*** ⇒ ORTHOGONAL. USE THEM WITH ALL OF THE
⭐     ABOVE.

⭐⭐ AND THE ANSWER THAT SCORES, BECAUSE IT INVERTS THE
⭐   QUESTION:
⭐   ***"THE STRATEGY MATTERS LESS THAN THE PRECONDITION. IF TWO
⭐      VERSIONS CANNOT COEXIST, ROLLING BREAKS IN A CONFUSING
⭐      WAY AND BLUE-GREEN BREAKS IN AN OBVIOUS ONE — BUT BOTH
⭐      BREAK. SO I'D SPEND THE FIRST EFFORT ON EXPAND/CONTRACT
⭐      MIGRATIONS, ADDITIVE MESSAGE SCHEMAS AND VERSIONED CACHE
⭐      KEYS, AND THEN ROLLING IS USUALLY ENOUGH."***

⭐⭐ AND THE THREE NUMBERS THAT ACTUALLY DECIDE IT:
⭐   ⭐ ⭐⭐ HOW LONG DOES A ROLLBACK TAKE? ⭐ If eight minutes is
⭐     too long, that is the blue-green argument.
⭐   ⭐ ⭐⭐ HOW MANY REQUESTS PER MINUTE? ⭐ Below a few thousand,
⭐     canary percentages are statistically meaningless.
⭐   ⭐ ⭐⭐ WHAT DOES A BAD MINUTE COST? ⭐ That number funds
⭐     everything else, and if nobody can state it, the answer
⭐     is rolling.
```

# Part 7 — ⭐⭐ The Python-specific deployment concerns

```
⭐⭐ ① ***BACKGROUND WORKERS DEPLOY TOO, AND DIFFERENTLY.***
⭐   ⭐ A Celery worker mid-task receives SIGTERM. ⭐ With
⭐     `acks_late`, the task is redelivered — ⭐⭐ TO A ***v2***
⭐     WORKER, WHICH MUST BE ABLE TO PROCESS A MESSAGE ***v1***
⭐     ENQUEUED.
⭐   ⇒ ⭐⭐ AND THE ORDERING RULE: ***DEPLOY CONSUMERS BEFORE
⭐     PRODUCERS.*** ⭐ New consumers must understand the new
⭐     message ***before*** anything emits it. ⭐ Doing it the
⭐     other way round puts messages nobody can parse into a
⭐     DLQ.

⭐⭐ ② ***SCHEDULED JOBS DURING A ROLLOUT.***
⭐   ⭐ A nightly job firing mid-deploy may run on v1 or v2, ⭐ or
⭐     ⭐⭐ TWICE, IF THE SCHEDULER'S LEASE IS HELD BY A POD THAT
⭐     GETS REPLACED. ⭐ Day 264's advisory lock is what makes
⭐     this safe, and this is the day it earns its keep.

⭐⭐ ③ ***CONNECTION POOLS AND CONNECTION COUNT.***
⭐   ⭐ ⭐⭐ DURING `maxSurge`, YOU HAVE 125% OF NORMAL PODS,
⭐     EACH WITH A FULL POOL — ⭐⭐ SO YOUR DATABASE SEES 125% OF
⭐     NORMAL CONNECTIONS AT EXACTLY THE MOMENT YOU ARE CHANGING
⭐     SOMETHING (Day 332's connection-count limit).
⭐   ⇒ ⭐ Size for the surge, not the steady state.

⭐⭐ ④ ***SLOW STARTUP INTERACTS BADLY WITH ROLLING.***
⭐   ⭐ A 30-second import time (Day 366) ⇒ ⭐⭐ A TEN-POD
⭐     ROLLOUT TAKES MINUTES, AND SO DOES THE ROLLBACK. ⭐ Cold
⭐     start is a deployment-safety property, not just a
⭐     performance one.
⭐   ⇒ ⭐ Use a ***startup probe*** so a slow boot is not
⭐     mistaken for a failure and restarted forever.

⭐⭐ ⑤ ***IN-PROCESS CACHES ARE PER-VERSION*** (Day 324).
⭐   ⭐ ⭐⭐ v1 AND v2 HAVE DIFFERENT WARM CACHES, SO USERS SEE
⭐     DIFFERENT ANSWERS DEPENDING ON WHICH POD THEY HIT — ⭐ and
⭐     it looks like a caching bug rather than a deployment one.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Assuming blue-green exempts you from compatibility | The database is shared. The precondition applies in full |
| ⭐⭐ "Instant rollback" with blue-green | True for code only. Green already wrote data forward |
| ⭐⭐ Rolling updates without readiness probes | A broken image rolls happily to 100%, replacing every working pod |
| ⭐ `maxUnavailable: 25%` on a service at capacity | Your deploy is a capacity incident |
| ⭐⭐ Canary without per-version metric labels | You can't tell if the canary is worse; you're just deploying slowly |
| ⭐⭐ Canary at 1% on a low-traffic service | A 1-in-1000 bug needs 100,000 requests to appear once. Deployment theatre |
| ⭐ Per-request canary routing | Users bounce between versions mid-flow and see inconsistency |
| ⭐ Comparing canary to yesterday's baseline | Monday-morning traffic reads as a regression |
| ⭐ Canary on technical metrics only | A deploy that drops conversion 8% is bad, and only business metrics notice |
| ⭐⭐ Flags with no owner or expiry | N flags is 2^N states and you test two |
| ⭐ A flag service with no local cache | You added a single point of failure to every request |
| ⭐⭐ Deploying producers before consumers | Messages nobody can parse go straight to the DLQ |
| ⭐ Ignoring worker deploys | A task enqueued by v1 gets redelivered to v2 mid-rollout |
| ⭐ Pool sizing for steady state | `maxSurge` gives you 125% of pods, each with a full pool |
| ⭐⭐ Treating slow startup as only a performance issue | It's a deployment-safety property: it sets your rollback time |

## Interview questions

**1. "Which deployment strategy would you choose?"**
> ⭐⭐ I'd invert the question first: **the strategy matters less than the precondition.** Every
> zero-downtime approach requires two versions to run simultaneously against one database and one set
> of queues — ⭐ and if that's not true, rolling breaks confusingly, blue-green breaks obviously, but
> both break. ⭐ So I'd spend the first effort on expand/contract migrations, additive message schemas
> and versioned cache keys, ⭐⭐ **and then rolling is usually enough.**

**2. "What exactly has to be compatible?"**
> ⭐ Five things, and most teams know one. Schema, via expand/contract. ⭐⭐ Message schema — **and the
> one people miss: a message published by v2 and sitting in a queue for an hour is consumed by whatever
> is running then, which may be v1 after a rollback.** ⭐ Cache value shape, or v1 deserialises v2's
> entry and crashes. Session and cookie format. ⭐ And the API contract, because a browser loads v2's
> JavaScript and then calls v1's API — which backend testing never sees. ⭐⭐ The test is **deploy v2 to
> one replica of three and run the integration suite through the load balancer.**

**3. "Blue-green gives instant rollback, right?"**
> ⭐ For the code. ⭐⭐ **Once green has written data in the new format, switching back means blue has to
> handle it** — the data has already moved forward. ⭐ And blue-green doesn't duplicate the database, so
> the compatibility requirement applies in full, which people believe it exempts them from. ⭐ Plus
> double infrastructure during the switch, stranded in-flight state and WebSockets, and a cold cache at
> cutover — a latency spike at the moment of maximum attention.

**4. "When is canary not worth it?"**
> ⭐⭐ Two cases. **Without per-version labels on your metrics you can't compare populations, so you're
> just deploying slowly** — that's the precondition of the precondition. ⭐⭐ And **at 1% of traffic, a
> one-in-a-thousand bug needs a hundred thousand requests to appear once**, so a low-traffic service
> can't canary meaningfully at small percentages — the statistics aren't there. ⭐ I'd also insist on
> business metrics, because a technically perfect deploy that drops conversion eight percent is a bad
> deploy and only that category notices.

**5. "How do feature flags change this?"**
> ⭐⭐ They separate deployment from release: **deployment moves code, release exposes behaviour, and
> they don't have to happen together.** ⭐ The deploy becomes boring — new code present and inert — and
> the release is a config change that reverses in seconds, ⭐⭐ **which is faster and safer than any
> deployment strategy, because no process restarts and no schema moves.** ⭐ The costs are real: every
> flag is a permanent branch, N flags is 2^N states, and the evaluation service is now on your request
> path so it needs a local cache and a safe default.

**6. "What's Python-specific about deployments?"**
> ⭐ Four things. ⭐⭐ **Workers deploy differently: deploy consumers before producers**, or messages
> nobody can parse land in the DLQ. ⭐ Scheduled jobs can run twice mid-rollout unless there's an
> advisory lock. ⭐ Connection pools — `maxSurge` means 125% of pods each with a full pool, so size for
> the surge. ⭐⭐ And **slow startup is a deployment-safety property, not a performance one**: thirty
> seconds of imports makes a ten-pod rollout minutes long, and the rollback exactly as long.

## 🎙️ Articulation drill

**Two minutes.** Lead by inverting the question: **every zero-downtime strategy has the same
precondition — two versions of your code must run simultaneously against one database and one set of
queues — and if that isn't true, rolling breaks confusingly and blue-green breaks obviously, but both
break.** Name the five compatibility requirements and dwell on the two people miss: **a message
published by v2 and sitting in a queue for an hour is consumed by whatever is running then, which may
be v1 after a rollback**, and a browser that loaded v2's JavaScript then calls v1's API, which backend
testing never sees. Give the test that settles it: **deploy v2 to one replica of three and run the
integration suite through the load balancer.** Then the strategies briefly: rolling as the default with
`maxUnavailable: 0` and surge, made safe by readiness probes — **without which a broken image rolls
happily to a hundred percent, replacing every working pod.** Blue-green for rollback speed only, ⭐ with
the caveat that **instant rollback is true for code and not for data, because green already wrote
forward.** Canary for blast radius, with two honest limits: **without per-version metric labels you're
just deploying slowly, and at one percent of traffic a one-in-a-thousand bug needs a hundred thousand
requests to appear once.** Close on the reframe that beats all of them: **deployment moves code,
release exposes behaviour — with a flag the deploy is boring and the reversal takes seconds, because
no process restarts and no schema moves.**
