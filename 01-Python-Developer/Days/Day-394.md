# Part 2 — ⭐⭐ The custom-metric trap, with the arithmetic

```
⭐ $0.30 per custom metric per month. ⭐ Sounds trivial.
⭐⭐ AND A "METRIC" IS ***A UNIQUE COMBINATION OF NAME PLUS
⭐   DIMENSION VALUES.*** ⭐ Which is Day 374's cardinality
⭐   lesson with an invoice attached.

⭐   `RequestLatency{endpoint, status, region, instance_id}`
⭐     ⭐ 50 endpoints × 5 statuses × 3 regions × 20 instances
⭐     ⭐⭐ = 15,000 METRICS = ***$4,500 / MONTH***
⭐     ⭐ …for one metric name, ⭐⭐ AND `instance_id` ALONE
⭐       MULTIPLIED IT BY TWENTY.

⭐⭐ ⇒ TWO RULES:
⭐   ⭐⭐ ① ***NEVER PUT AN UNBOUNDED OR HIGH-CARDINALITY VALUE IN
⭐      A DIMENSION.*** ⭐ Not instance id, not user id, not path
⭐      with an id in it, ⭐⭐ NOT REQUEST ID. ⭐ Same rule as
⭐      Prometheus labels; ⭐⭐ HERE IT IS ENFORCED BY YOUR
⭐      FINANCE DEPARTMENT.
⭐   ⭐ ② `PutMetricData` is also $0.01 per 1,000 calls — ⭐⭐ SO A
⭐      PER-REQUEST CALL IS BOTH A COST AND A LATENCY BUG (IT IS
⭐      A NETWORK ROUND TRIP ON YOUR HOT PATH).

⭐⭐ ***THE FIX IS EMF — EMBEDDED METRIC FORMAT — AND IT IS
⭐   UNDER-KNOWN.*** ⭐ You write ***one structured log line***;
⭐   CloudWatch extracts metrics from it automatically.
```

```python
# ⭐⭐ ONE LINE THAT IS SIMULTANEOUSLY A LOG EVENT AND A METRIC.
from aws_embedded_metrics import metric_scope

@metric_scope
def handle(order, metrics):
    metrics.set_namespace("Flagship")
    metrics.put_dimensions({"Service": "api", "Endpoint": "checkout"})
    metrics.put_metric("Latency", ms, "Milliseconds")
    # ⭐⭐ THE PAYOFF: THESE ARE ***PROPERTIES***, NOT DIMENSIONS.
    # ⭐   FULLY SEARCHABLE IN LOGS INSIGHTS, ⭐⭐ AND THEY COST
    # ⭐   NOTHING AS METRICS BECAUSE THEY ARE NOT METRICS.
    metrics.set_property("order_id", order.id)
    metrics.set_property("user_id", order.user_id)
    metrics.set_property("trace_id", current_trace_id())
```

```
⭐⭐ ⇒ THAT IS DAY 375's "ONE WIDE EVENT" AND DAY 374's
⭐   CARDINALITY RULE, ***RECONCILED***: ⭐ low-cardinality
⭐   dimensions become cheap metrics you can alarm on, ⭐⭐ AND
⭐   HIGH-CARDINALITY CONTEXT STAYS IN THE EVENT WHERE YOU CAN
⭐   SEARCH IT DURING AN INCIDENT. ⭐ One write. ⭐ No hot-path
⭐   API call.
```

# Part 3 — Logs: three prices, three levers

```
⭐ INGESTION .... ⭐⭐ $0.50/GB — ***THE BIG ONE.***
⭐ STORAGE ...... $0.03/GB-month.
⭐ INSIGHTS ..... ⭐ $0.005/GB ***scanned per query.***
⭐   ⭐⭐ SO A BADLY-SCOPED QUERY OVER 2 TB COSTS $10 — ⭐ and
⭐   during an incident, ⭐⭐ SOMEONE WILL RUN IT TWENTY TIMES.
⭐   ⭐ Always narrow the time range and the log group first.

⭐⭐ THE THREE LEVERS, IN ORDER OF RETURN:
⭐ ① ⭐⭐ ***RETENTION. THE DEFAULT IS "NEVER EXPIRE".*** ⭐ This
⭐    is the single commonest silent line on an AWS bill: ⭐ log
⭐    groups created in 2021 by a service that no longer exists,
⭐    ⭐⭐ STILL BILLING STORAGE EVERY MONTH FOREVER. ⭐ Set 30
⭐    days for app logs, 90 for audit, ⭐⭐ AND SET IT IN
⭐    TERRAFORM SO NEW GROUPS INHERIT IT.
⭐ ② ⭐ ***LOG CLASS.*** ⭐ Infrequent Access is ~50% cheaper to
⭐    ingest ⭐⭐ AND IS CORRECT FOR ANYTHING YOU ONLY READ DURING
⭐    AN INCIDENT — ⭐ debug logs, access logs, VPC flow logs.
⭐ ③ ⭐⭐ ***LOG LESS.*** ⭐ Day 375's economics: sample successes,
⭐    keep all errors. ⭐⭐ ONE WIDE EVENT PER UNIT OF WORK BEATS
⭐    FIFTEEN NARROW LINES ON EVERY AXIS — SIZE, COST, AND
⭐    USEFULNESS.

⭐ ⭐ At real volume: ⭐⭐ SHIP TO S3 AND QUERY WITH ATHENA. ⭐ Day
⭐   386's partitioning and Parquet rules apply, ⭐ and it is an
⭐   order of magnitude cheaper for logs you rarely read.
⭐   ⭐ Keep the last 7 days in CloudWatch for fast access; ⭐ keep
⭐   the year in S3.
```

# Part 4 — Alarms, and the default that hides a dead service

```
⭐⭐ ***`TreatMissingData` DEFAULTS TO `missing`, WHICH MEANS THE
⭐   ALARM DOES NOT CHANGE STATE.***
⭐   ⭐ So if your service stops publishing the metric entirely —
⭐     ⭐⭐ BECAUSE IT CRASHED, OR THE AGENT DIED, OR THE TASK
⭐     NEVER STARTED — ⭐⭐ THE ALARM SITS IN `OK` FOREVER.
⭐   ⭐⭐ ⇒ ***"NO DATA" READS AS "FINE", WHICH IS EXACTLY
⭐     BACKWARDS FOR AN AVAILABILITY ALARM.***
⭐   ⭐ Set `treat_missing_data = "breaching"` on anything whose
⭐     absence is itself bad. ⭐⭐ THIS IS A ONE-WORD FIX FOR A
⭐     WHOLE CLASS OF SILENT FAILURE.

⭐ THE OTHER PARAMETERS THAT MATTER:
⭐   ⭐ `M out of N` datapoints — ⭐⭐ THE CLOUDWATCH VERSION OF
⭐     DAY 374's "DO NOT PAGE ON ONE SPIKE".
⭐   ⭐ Period vs evaluation periods: ⭐⭐ TIME TO ALARM = PERIOD ×
⭐     EVALUATION PERIODS, ⭐ and people are surprised by five
⭐     minutes of silence before a page.
⭐   ⭐⭐ COMPOSITE ALARMS — ⭐ alarm on `(HighErrorRate AND
⭐     NOT DeployInProgress)`, or on a parent so that ten child
⭐     alarms produce ***one*** page. ⭐⭐ THIS IS DAY 374's
⭐     GROUPING AND INHIBITION, AS A CLOUDWATCH PRIMITIVE, AND
⭐     IT IS THE MAIN DEFENCE AGAINST ALERT FATIGUE HERE.
⭐   ⭐ Anomaly detection bands: ⭐ good for traffic-shaped
⭐     metrics, ⭐⭐ BAD FOR ANYTHING WITH A REAL THRESHOLD —
⭐     ⭐ an SLO is a number you chose, ⭐⭐ NOT A DEVIATION FROM
⭐     WHATEVER YOU HAPPENED TO BE DOING LAST WEEK.
⭐ ⭐ Alarm actions can do more than notify: ⭐ reboot, ⭐ scale,
⭐   ⭐⭐ OR TRIGGER AN ECS DEPLOYMENT ROLLBACK (DAY 390).
```

# Part 5 — X-Ray, and the honest position on it

```
⭐ WHAT IT IS: ⭐ AWS-native distributed tracing. ⭐ $5 per
⭐   million traces recorded. ⭐ Sampled by default (⭐ 1 req/s +
⭐   5% — ⭐⭐ WHICH MEANS YOUR RARE SLOW REQUEST IS PROBABLY NOT
⭐   IN THERE, ⭐ so raise the rate or use tail sampling).
⭐ ⭐ The service map is genuinely good: ⭐⭐ IT DRAWS YOUR
⭐   ARCHITECTURE FROM OBSERVED TRAFFIC, WHICH IS OFTEN THE
⭐   FIRST ACCURATE DIAGRAM A TEAM HAS EVER HAD.

⭐⭐ ***THE HONEST POSITION: INSTRUMENT WITH OPENTELEMETRY AND
⭐   EXPORT TO X-RAY VIA THE ADOT COLLECTOR.***
⭐   ⭐ You keep vendor neutrality (Day 376) ⭐ and lose nothing.
⭐   ⭐⭐ WRITING X-RAY SDK CALLS THROUGHOUT YOUR PYTHON CODE IS
⭐     BUYING LOCK-IN FOR NO BENEFIT — ⭐ and it is a decision
⭐     that is expensive to reverse later.

⭐⭐ AND DAY 376's LESSON IS UNCHANGED AND UNFORGIVING HERE:
⭐   ⭐⭐ ***PROPAGATION BREAKS AT THE QUEUE AND AT THE OUTBOX
⭐   ROW.*** ⭐ SQS carries the trace header only if you put it
⭐   in the message attributes yourself. ⭐⭐ IF YOU DO NOT, YOUR
⭐   TRACE ENDS AT `SendMessage` AND A SECOND, UNRELATED TRACE
⭐   BEGINS IN THE WORKER — ⭐ and the most valuable trace you
⭐   own (request → queue → worker → database) is the one you do
⭐   not have.
```

⭐ ⭐ Querying: ⭐ Athena over the trail bucket (cheap, ⭐ and you

# 💬 Interview

**1. ⭐⭐ "Our CloudWatch bill is bigger than our EC2 bill. Where do you look?"**
> ⭐ Three places. ⭐⭐ **Custom metrics first, because a metric is a unique combination of name and
> dimension values — so `latency` with an `instance_id` dimension across 50 endpoints, 5 statuses, 3
> regions and 20 instances is 15,000 metrics at $0.30 each, which is $4,500 a month from one metric
> name.** ⭐ Then log retention, ⭐⭐ **because the default is "never expire" and every account has log
> groups from services that no longer exist, still billing storage forever.** ⭐ Then whichever
> Insights product someone ticked, since those publish a lot of custom metrics on your behalf. ⭐ And
> the general rule: ⭐⭐ **5–15% of infrastructure spend is normal for observability; above 25% you're
> paying more to watch the system than to run it.**

**2. ⭐⭐ "How do you get high-cardinality context without paying for it?"**
> ⭐ Embedded Metric Format. ⭐⭐ **You write one structured log line and CloudWatch extracts metrics
> from it — the low-cardinality fields become dimensions you can alarm on, and everything
> high-cardinality goes in as properties, which are fully searchable in Logs Insights and cost nothing
> as metrics because they aren't metrics.** ⭐ That reconciles the two rules that seem to conflict:
> keep dimensions low-cardinality, and log one wide event with all the context. ⭐ One write, ⭐⭐ **and
> no `PutMetricData` call on the hot path — which is both a cost and a latency bug, since it's a
> network round trip inside your request.**

**3. ⭐⭐ "Your service crashed and no alarm fired. Why?"**
> ⭐ Almost certainly `TreatMissingData`. ⭐⭐ **It defaults to `missing`, which means the alarm doesn't
> change state — so if the service stops publishing the metric entirely because it crashed, the alarm
> sits in OK forever and "no data" reads as "fine".** ⭐ That's exactly backwards for an availability
> alarm. ⭐ Setting `treat_missing_data = "breaching"` on anything whose absence is itself bad is a
> one-word fix for a whole class of silent failure. ⭐ I'd also have a Synthetics canary, ⭐⭐ **because
> it's the only signal that survives the entire region being unhealthy.**

**4. "X-Ray or OpenTelemetry?"**
> ⭐⭐ **Instrument with OpenTelemetry and export to X-Ray through the ADOT collector.** ⭐ You get the
> service map and the AWS integration, and you keep vendor neutrality — ⭐⭐ **writing X-Ray SDK calls
> throughout the Python codebase is buying lock-in for no benefit, and it's expensive to reverse.**
> ⭐ I'd also raise the default sampling, which is one request a second plus 5%, ⭐⭐ **because that
> means the rare slow request you actually want is probably not in there** — tail sampling is the
> better answer. ⭐ And the propagation lesson holds unchanged: ⭐⭐ **SQS carries the trace context only
> if you put it in message attributes yourself, otherwise the trace ends at `SendMessage` and the most
> valuable trace you own — request to queue to worker to database — is the one you don't have.**

**5. "How would you set up CloudTrail?"**
> ⭐ An organization trail writing to a bucket in a separate log-archive account, with Object Lock and
> log file validation. ⭐⭐ **Separate account so a compromised credential in prod can't delete the
> evidence of what it did, and Object Lock so even root can't** — ⭐⭐ **an audit log the attacker can
> delete isn't an audit log, and that's the entire design requirement.** ⭐ Management events are free
> for the first copy so there's no excuse; ⭐⭐ **data events are charged per event and on a busy bucket
> S3 data events can cost more than the bucket**, so I'd enable those selectively by prefix on the
> buckets that matter.

**6. "Why does an incident make Logs Insights expensive?"**
> ⭐ Because it's charged at half a cent per gigabyte scanned per query, ⭐⭐ **so a badly-scoped query
> over two terabytes is ten dollars, and during an incident somebody will run it twenty times.**
> ⭐ Narrowing the time range and the log group first is a habit worth having. ⭐ At real volume I'd ship
> logs to S3 and query with Athena — ⭐⭐ **same partitioning and Parquet rules as any other S3 data,
> and an order of magnitude cheaper for logs you rarely read** — keeping the last week in CloudWatch
> for speed.

## 🎙️ Articulation drill

**Two minutes.** Frame it first: **nothing here replaces Prometheus, OTel and structured logs — it's
the same three signals with AWS billing attached. What's genuinely new is CloudTrail, which has no
open-source equivalent and isn't optional.** Then the money, with the arithmetic: **a CloudWatch
custom metric is a unique combination of name and dimension values, so putting `instance_id` on a
latency metric across 50 endpoints, 5 statuses and 3 regions is 15,000 metrics at thirty cents — $4,500
a month from one metric name.** Give the fix that people don't know: **Embedded Metric Format — one
structured log line, where low-cardinality fields become dimensions you can alarm on and everything
else becomes properties that are searchable and cost nothing.** That reconciles "keep cardinality low"
with "log one wide event". Then the alarm default that hides outages: **`TreatMissingData` defaults to
`missing`, so a service that crashes and stops publishing leaves its alarm in OK forever — no data
reads as fine, which is exactly backwards.** One word fixes it. On tracing: **instrument with OTel and
export to X-Ray through ADOT — the service map without the lock-in — and remember propagation breaks
at the queue unless you put the trace context in SQS message attributes yourself.** Close on
CloudTrail, because it's the one with a hard requirement: **an organization trail into a separate
log-archive account with Object Lock, because an audit log the attacker can delete is not an audit
log.** And the discipline: **observability at 5–15% of infra spend is normal; above 25% you're paying
more to watch the system than to run it.**
