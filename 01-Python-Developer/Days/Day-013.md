# Part 1 — ⭐ Rules, and how a value is chosen

```css
/* ⭐ selector { property: value; } — that is the entire syntax. */
.card h2 { font-size: 1.5rem; color: #222; }
```

```
⭐⭐ THE CASCADE — when several rules set the same property, the winner is decided in this order:

⭐ 1. ORIGIN + IMPORTANCE   author !important > author > user agent (the browser's defaults)
⭐ 2. ⭐⭐ SPECIFICITY        how precisely the selector identifies the element
⭐ 3. ⭐ SOURCE ORDER        last one wins
⭐
⭐ ⇒ ⭐⭐ "Cascading" is the C in CSS, and it is the whole design: many sources contribute,
⭐      one deterministic algorithm resolves them.
```

## ⭐⭐ Specificity, counted properly

```
⭐⭐ Count three numbers:  (IDs, CLASSES/attributes/pseudo-classes, ELEMENTS)   — compare left to right.

⭐   h2                      ⇒ (0,0,1)
⭐   .card h2                ⇒ (0,1,1)
⭐   .card .title            ⇒ (0,2,0)   ⭐ beats the above — a class outweighs any number of elements
⭐   #main .title            ⇒ (1,1,0)   ⭐⭐ an ID outweighs any number of classes
⭐   [type="text"]           ⇒ (0,1,0)
⭐   :hover                  ⇒ (0,1,0)
⭐   ::before                ⇒ (0,0,1)
⭐   *                       ⇒ (0,0,0)
⭐   inline style="..."      ⇒ ⭐⭐ beats all selectors
⭐   !important              ⇒ ⭐⭐ beats even that   ⚠️ and is almost always a symptom
```

⚠️ ⭐⭐ **`!important` is not a tool, it is a confession** — that you could not work out which rule
was winning. It also escalates: the next person needs `!important` too, and now nothing can be
overridden. **The professional fix is to lower specificity everywhere, not to raise it here.**

⭐ **Inheritance** is separate from the cascade: some properties (`color`, `font-family`,
`line-height`) inherit to descendants; most (`border`, `padding`, `display`) do not.

# Part 2 — ⭐⭐ The box model

```
⭐ EVERY element is a rectangle, made of four layers:

   ┌─────────── margin ────────────┐   ⭐ outside, transparent, ⭐⭐ COLLAPSES vertically
   │  ┌────────  border  ───────┐  │
   │  │  ┌─────  padding ────┐  │  │   ⭐ inside, takes the background
   │  │  │  ┌── content ──┐  │  │  │
   │  │  │  │   w × h     │  │  │  │
   │  │  │  └─────────────┘  │  │  │
   │  │  └───────────────────┘  │  │
   │  └─────────────────────────┘  │
   └───────────────────────────────┘
```

```css
/* ⭐⭐ THE DEFAULT THAT SURPRISES EVERYONE */
.a { width: 200px; padding: 20px; border: 5px solid; }
/* ⇒ ⭐⭐ actual rendered width = 200 + 40 + 10 = 250px.  `width` meant CONTENT width. */

/* ⭐⭐ THE FIX EVERY REAL PROJECT APPLIES, ONCE, AT THE TOP: */
*, *::before, *::after { box-sizing: border-box; }
/* ⇒ ⭐ now `width: 200px` means the BORDER BOX is 200px. Padding eats inward. */
```

⭐⭐ **`box-sizing: border-box` is the single most valuable line of CSS you will learn today**, and
"why is my 100%-width element wider than its parent" is nearly always this.

⭐ **Margin collapsing:** adjacent vertical margins merge into the **larger** of the two (not the
sum), and a parent with no border or padding "collapses" its child's top margin outward. Horizontal
margins never collapse. **It looks like a bug and is specified behaviour.**

# Part 3 — ⭐ Layout algorithms — pick the right one and CSS stops fighting

| ⭐ `display` | ⭐ Behaviour |
|---|---|
| `block` | full width, stacks vertically; `width`/`height` apply |
| ⭐ `inline` | flows in text; ⚠️ ⭐ **`width`/`height` ignored**, vertical margin ignored |
| `inline-block` | flows inline, but sizes like a block |
| ⭐⭐ `flex` | ⭐ **one-dimensional** layout — a row or a column |
| ⭐⭐ `grid` | ⭐ **two-dimensional** layout — rows *and* columns together |
| `none` | ⭐⭐ removed from the tree entirely (vs `visibility: hidden`, which reserves space) |

```css
/* ⭐⭐ FLEXBOX — 90% of the layout you will ever write */
.row {
  display: flex;
  justify-content: space-between;  /* ⭐ along the MAIN axis */
  align-items: center;             /* ⭐ along the CROSS axis */
  gap: 1rem;                       /* ⭐ spacing without margin hacks */
  flex-wrap: wrap;
}
.row > .grow { flex: 1; }          /* ⭐ take the remaining space */

/* ⭐ GRID — when you genuinely have both dimensions */
.layout {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));  /* ⭐⭐ responsive with no media query */
  gap: 1rem;
}
```

⭐⭐ **Flex for a row or a column; grid for a page.** Choosing wrong is the cause of most "CSS is
horrible" experiences — the older float- and table-based hacks exist only because neither of these
existed until recently.

## ⭐ Positioning, and the stacking rule that catches people

| `position` | ⭐ Meaning |
|---|---|
| `static` | default — in normal flow |
| `relative` | offset from where it *would* be; ⭐⭐ **still occupies its original space**, and becomes a containing block |
| ⭐ `absolute` | ⭐⭐ removed from flow; positioned relative to the **nearest positioned ancestor** |
| `fixed` | relative to the viewport |
| ⭐ `sticky` | relative until a scroll threshold, then fixed |

⚠️ ⭐⭐ **`z-index` only works on positioned elements, and only within a stacking context.** A child
with `z-index: 9999` cannot escape a parent that created a lower stacking context — which is why
"my modal is behind the header" happens, and why raising the number never fixes it.

# Part 4 — ⭐⭐ Selectors — the part you will use professionally forever

```css
h2                 /* element */
.lead              /* class */
#main              /* id */
.card h2           /* ⭐ DESCENDANT — h2 anywhere inside .card */
.card > h2         /* ⭐ CHILD — direct children only */
.a + .b            /* adjacent sibling */
a[href^="https"]   /* ⭐ attribute starts-with */
li:nth-child(2n)   /* every second */
tr:last-child
input:focus, a:hover
```

⭐⭐ **These are exactly the selectors you pass to BeautifulSoup's `.select()`, to Playwright's
`page.locator()`, and to Selenium.** Learning them is not a front-end detour — it is the query
language of every piece of browser automation and scraping you will write in Python.

```python
soup.select("article.post > h2 a[href^='/']")     # ⭐ same grammar, in Python
page.locator("form#login input[name='email']")    # ⭐ Playwright, same grammar
```

⭐ **Modern CSS worth knowing exists:** custom properties (`--brand: #06f; color: var(--brand)`) for
theming without a preprocessor, and `@media (max-width: 640px)` for responsive rules. ⭐⭐ **Mobile
first** — write the small-screen rules as the base and add complexity upward with `min-width`
queries; it produces less CSS and fewer overrides.

# Part 5 — C-09 · ⭐ HTTP on the wire

```
⭐⭐ HTTP/1.1 — TEXT, delimited. The parser reads until it finds things:
⭐   GET /x HTTP/1.1\r\n
⭐   Host: a.com\r\n
⭐   \r\n                      ⭐⭐ blank line ends the headers
⭐   <body — length from Content-Length, or chunked>
⭐   ⇒ ⭐ human readable, and ⭐⭐ ambiguous: two ways to frame a body is how
⭐      REQUEST SMUGGLING attacks exist (a front-end proxy and a back-end server
⭐      disagreeing about where one request ends and the next begins).

⭐⭐ HTTP/2 — BINARY FRAMES. Every frame:
⭐   ┌ length (24 bits) ┬ type (8) ┬ flags (8) ┬ stream id (31) ┬ payload ┐
⭐   types: HEADERS, DATA, SETTINGS, WINDOW_UPDATE, RST_STREAM, PING, GOAWAY
⭐   ⇒ ⭐⭐ explicit lengths and a stream id ⇒ no ambiguity, and interleaving becomes possible.

⭐⭐ HTTP/3 — the same frame idea, but carried by QUIC streams over UDP.
```

| | ⭐ Compression |
|---|---|
| HTTP/1.1 | ⭐ headers **not compressed at all** — full cookies on every request |
| ⭐ HTTP/2 | ⭐⭐ **HPACK** — a shared static + dynamic table; repeated headers become an index |
| ⭐ HTTP/3 | ⭐⭐ **QPACK** — HPACK re-designed so out-of-order delivery cannot corrupt the table |

⭐⭐ **Why QPACK had to exist:** HPACK's dynamic table assumes headers arrive in order — a decoder
must have seen entry *n* before entry *n+1* references it. QUIC delivers streams **independently and
out of order**, so QPACK splits the table updates onto their own stream and allows a decoder to
block only when it genuinely must. ⭐ **A nice example of a design that was correct at one layer
breaking when the layer beneath it changed its guarantees.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Forgetting `box-sizing: border-box`** | ⭐⭐ `width` means *content* width by default. Set it once, globally. |
| ⭐⭐ **Reaching for `!important`** | ⭐ It is a confession, and it escalates. Lower specificity instead. |
| Fighting specificity with more IDs | ⭐ Prefer flat, class-based selectors. |
| Setting `width` on an `inline` element | ⭐ Ignored. Use `inline-block` or `block`. |
| Expecting margins to add | ⭐ Vertical margins **collapse** to the larger. |
| ⭐ Raising `z-index` to fix stacking | ⭐⭐ It needs `position`, and cannot escape a parent stacking context. |
| Using grid for a single row | ⭐ Flex is the one-dimensional tool. |
| Floats for layout | ⭐ Obsolete — that is what flex and grid replaced. |
| `visibility: hidden` vs `display: none` | ⭐ The first still occupies space. |
| Desktop-first media queries | ⭐ Mobile-first produces fewer overrides. |
| Thinking HTTP/2 is "HTTP/1.1 but faster" | ⭐⭐ It is a different, binary wire format. |

## Interview questions

**Q: How does the browser decide which rule wins?**
> The cascade, in order: origin and importance first — `!important` author rules beat normal author
> rules, which beat user-agent defaults; then specificity, counted as IDs, then classes and
> attributes and pseudo-classes, then elements, compared left to right; then source order, where the
> last declaration wins. Inheritance is separate — it only supplies a value when nothing in the
> cascade set one.

**Q: What is the box model, and what does `box-sizing: border-box` change?**
> Every element renders as content, padding, border and margin. By default `width` sets the *content*
> width, so padding and border add to the rendered size — a 200px box with 20px padding occupies
> 240px, plus border. `border-box` makes `width` describe the border box instead, so padding grows
> inward. Essentially every project sets it globally, because the default makes composition
> arithmetic.

**Q: Flexbox or grid?**
> Flex for one dimension — a row or a column, with items sizing and distributing along it. Grid when
> I genuinely need both dimensions to be related, like a page layout where columns line up across
> rows. Most component-level layout is flex; page-level layout is grid.

**Q: Why doesn't `z-index: 9999` bring my modal to the front?**
> Two reasons. It only applies to positioned elements, so a `static` element ignores it entirely. And
> z-index is resolved *within a stacking context* — if an ancestor created one, via `position` plus a
> z-index, or `transform`, `opacity` below 1, or `filter`, then the child's z-index only orders it
> among its siblings inside that context. The fix is to move the modal out of that subtree — usually
> to a portal at the document root — not to raise the number.

**Q: Why does a backend engineer need CSS selectors?**
> Because they're the query language of the browser, and therefore of everything that automates one.
> BeautifulSoup's `select`, Playwright's locators and Selenium's CSS strategy all take the same
> grammar. Every scraper and every browser test I write is CSS selectors, whether or not I ever write
> a stylesheet.

**Q: What changed in HTTP/2's wire format, and why did HTTP/3 need QPACK?**
> HTTP/2 replaced delimited text with binary frames carrying an explicit length, type and stream id,
> which is what makes interleaving possible and removes the framing ambiguity that request smuggling
> exploits. HPACK compresses headers against a dynamic table shared by both sides — but that assumes
> ordered delivery, and QUIC delivers streams independently and out of order, so a reference could
> arrive before the entry it points at. QPACK restructures the table updates so that can't corrupt
> the decoder.

## 🎙️ Articulation drill

Record two minutes: **"Explain the cascade and specificity to a junior who just wrote
`!important` on nine rules."**

⭐ Start with the algorithm, because it is deterministic and knowable: origin and importance,
then specificity, then source order. ⭐ Then show the count on their own selectors, so they can see
*why* the losing rule lost. ⭐⭐ **Then the important part: `!important` does not solve the problem,
it removes your ability to solve it later** — the next override needs `!important` too, and now the
stylesheet has no ordering left to give. ⭐ The real fix is a flat, class-based selector style so
that source order is usually the deciding factor, which is the one you actually control.
