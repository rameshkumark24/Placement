# Part 1 — ⭐⭐ The six shapes

Every day in this stage was one of these. If you can state all six, you own the stage.

```
⭐⭐ ① STATE THAT EXISTS TWICE WILL DRIFT.
⭐   A count beside a list · a JS variable beside DOM text · a
⭐   client validation rule beside a server one · hand-written
⭐   types beside a spec · a client role check beside a server one.
⭐   ⇒ ⭐ ONE SOURCE OF TRUTH, EVERYTHING ELSE DERIVED OR GENERATED.
⭐   ⇒ Days 220, 225, 229, 236, 246

⭐⭐ ② IDENTITY, NOT EQUALITY, DRIVES THE FRAMEWORK.
⭐   {a:1} !== {a:1} explains: why mutation doesn't re-render, the
⭐   infinite effect loop, why memo misses, and why context
⭐   re-renders everything.
⭐   ⇒ Days 215, 223, 226, 231, 232

⭐⭐ ③ THE CLIENT IS A SUGGESTION.
⭐   Hidden buttons, client validation, and anything in the bundle
⭐   are UX and never security. ⭐ The endpoint is the boundary.
⭐   ⇒ Days 222, 229, 236, 243

⭐⭐ ④ THE DANGEROUS FAILURE DOES NOT RAISE.
⭐   fetch resolves on a 500 · a rejected promise nobody awaited ·
⭐   an index key moving a tick to another record · a stale cache
⭐   after a write · a leaked field nobody renders.
⭐   ⇒ Days 216, 217, 228, 230, 236

⭐⭐ ⑤ THE COST IS WHERE YOU ARE NOT LOOKING.
⭐   Your 40 ms is 1.4% of the wait. Bundle, waterfall, images and
⭐   fonts are the rest — ⭐ and none of it is in your server metrics.
⭐   ⇒ Days 220, 227, 241, 242

⭐⭐ ⑥ TWO VERSIONS ARE ALWAYS LIVE.
⭐   The open tab runs yesterday's bundle. ⭐ So deploys are rollouts,
⭐   API changes are migrations, and old clients must keep working.
⭐   ⇒ Days 245, 246
```

# Part 2 — The five proofs

You have passed when you can **do** these, not describe them.

- [ ] **⭐⭐ One real screen, four states.** Loading skeleton, error branched by status with a retry,
      **empty split into never-had-any and filtered-to-zero**, and success. Against **your own API**.
- [ ] **⭐⭐ The index-key corruption, demonstrated.** Tick a row, delete another, watch the tick move.
      Then fix it. You must be able to reproduce this on demand.
- [ ] **⭐ A generated client.** Rename a field on the server; the frontend build fails.
- [ ] **⭐⭐ The keyboard pass.** Tab the whole app with no mouse: everything reachable, focus always
      visible, modal traps and returns focus, first error focused on failed submit.
- [ ] **⭐⭐ A CSP that blocks your own XSS.** Inject a script through your own API, confirm it runs,
      add the CSP, confirm the bug still exists and the exploit no longer works.

```
⭐⭐ AND THE MEASUREMENT, WRITTEN DOWN:
⭐   LCP ___  INP ___  CLS ___  initial JS ___ KB
⭐   ⇒ ⭐ before and after ONE optimisation you chose,
⭐     ⭐⭐ WITH THE REASON YOU CHOSE THAT ONE.
```

# Part 4 — ⭐⭐ What this stage changed on the server

The real output of Stage 6 is not the UI. It is these, and they belong in your project defence.

| ⭐ Finding | Day |
|---|---|
| **An endpoint that needed four round trips to render one screen** | 214 |
| **A 422 that could not be attached to a field** | 217, 229 |
| **A response carrying fields nobody renders** — fixed with a `response_model` allow-list | 236 |
| **Authorization expressed as `permissions` per resource**, computed by the enforcing code | 236 |

## 🎙️ Articulation drill

⭐⭐ **Three minutes: "tell me about the frontend work."**

Open with the reason, not the stack. **I built the client for my own API, and the point was never to
become a frontend engineer — it was that an API whose UI I've never written is an API I've only half
designed.**

Give the evidence, as findings. **The first screen needed four round trips to render one view. Every
endpoint was individually correct and the API was wrong, and I couldn't have seen it from the server
side. My 422 was a nested blob I couldn't attach to an input, so I changed the contract to carry a
field name. I opened DevTools on my own app and found a response shipping fields I never rendered, so
the serialiser became an allow-list. And a double-click on Save made two orders, so the create endpoint
took an idempotency key.**

Show the systems thinking. **A few things generalised. The client is a suggestion — hidden buttons and
client validation are UX, and the endpoint is the only boundary, so the server now sends a permissions
object per resource computed by the same code that enforces it. Two versions are always live because of
open tabs, so a frontend deploy is a rollout and every API change is additive or a migration. And my
p99 of forty milliseconds was about one percent of what the user waited — the bundle and the request
waterfall were the rest, and neither was in my dashboards.**

Close with scope, deliberately. **I'm not a frontend specialist. I can build a competent, accessible,
secure UI for an API I wrote and defend every decision in it, and I test with the keyboard rather than
claiming a compliance level I haven't audited. What the stage actually produced was six changes to my
backend — which is why I'd do it again.**
