# Day 277 📡

**P-277** · 📡 **Real-time in the browser** — ⭐⭐ the tab that has been open since Tuesday

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a real-time connection is not a feature you add, it is a distributed
> system you now own in the browser — it will drop, it will miss messages while it was gone, and the
> tab will still be open three days later, so the design question is not "how do I connect" but "how
> do I resynchronise after being disconnected".**
>
> Today: ⭐ SSE vs WebSocket honestly, ⭐⭐ reconnect and the gap, and when polling wins.

---

# Part 1 — ⭐ The decision, honestly

| | **Polling** | ⭐⭐ **SSE** | **WebSocket** |
|---|---|---|---|
| Direction | ⭐ client pulls | ⭐ server → client | ⭐ both ways |
| Complexity | ⭐⭐ **almost none** | ⭐ low | ⭐⭐ highest |
| Reconnect | ⭐⭐ **n/a — it is just requests** | ⭐⭐ **automatic, with `Last-Event-ID`** | ⭐ you write it |
| Through proxies | ✅ | ⭐ mostly (needs no buffering) | ⭐⭐ needs an upgrade path |
| Auth | ⭐ normal | ⭐ cookies work | ⭐⭐ awkward — no custom headers |
| Scaling | ⭐ trivial | ⭐⭐ one connection per client held open | ⭐⭐ same, plus state |

```
⭐⭐ THE HONEST DEFAULT: ⭐ POLL UNTIL POLLING HURTS.

⭐   ⭐ A 5-SECOND POLL ON ONE ENDPOINT IS: no new protocol, no
⭐     reconnection logic, no sticky sessions, no proxy surprises,
⭐     and it survives every network event for free.
⭐   ⇒ ⭐⭐ FOR A FLAGSHIP PROJECT WITH ONE USER DEMOING IT, POLLING
⭐     IS OFTEN THE CORRECT ENGINEERING ANSWER — and saying so
⭐     is a stronger signal than reaching for WebSockets.

⭐   ⭐ USE SSE WHEN: server-push only, many clients, sub-second
⭐     matters. ⭐⭐ IT IS THE RIGHT ANSWER FAR MORE OFTEN THAN IT
⭐     IS CHOSEN, because people know WebSockets and forget SSE.
⭐   ⭐ USE WEBSOCKET WHEN: genuinely BIDIRECTIONAL and high
⭐     frequency — chat, collaborative editing, live cursors.
```

> ⭐ **You met this decision on Day 018 and again in Stage 7.** The frontend adds one fact that changes
> the balance: **SSE reconnects itself and replays from `Last-Event-ID`, and a WebSocket does neither
> unless you build it.** That is most of the work, and SSE gives it to you free.

# Part 2 — ⭐⭐ The gap is the whole problem

```
⭐⭐ THE FAILURE EVERY REAL-TIME UI HAS UNTIL SOMEONE FIXES IT

⭐   09:00 connected. Events flowing. ✅
⭐   ⭐ 09:04 laptop lid closes / wifi drops / phone changes network
⭐   09:31 ⭐ reconnects successfully ✅
⭐   ⇒ ⭐⭐ THE 27 MINUTES OF EVENTS THAT HAPPENED WHILE
⭐     DISCONNECTED ARE **GONE**. The connection is healthy.
⭐     The screen is WRONG. ⭐ NOTHING INDICATES THIS.

⭐⭐ ⇒ TWO FIXES, AND YOU NEED ONE OF THEM:
⭐   ① ⭐⭐ REFETCH ON RECONNECT — simplest and nearly always right.
⭐      The socket becomes a "something changed" HINT, and the
⭐      REST API remains the source of truth.
⭐   ② ⭐ REPLAY FROM A CURSOR — SSE's Last-Event-ID, or send your
⭐      own "since" on reconnect. Correct, more work, needs the
⭐      server to retain events.

⭐   ⇒ ⭐⭐ ① IS THE ONE TO BUILD. IT REUSES THE CACHE YOU ALREADY
⭐     HAVE (Day 228) AND CANNOT DRIFT.
```

```typescript
useEffect(() => {
  const es = new EventSource("/api/events");          // ⭐ cookies sent

  es.onopen = () => {
    setConnected(true);
    qc.invalidateQueries({ queryKey: keys.orders.all });  // ⭐⭐ CLOSE THE GAP
  };                                                      //    on EVERY open

  es.onmessage = (e) => {
    const evt = JSON.parse(e.data);
    qc.invalidateQueries({ queryKey: keys.orders.detail(evt.orderId) });
    //   ⭐⭐ INVALIDATE, DON'T PATCH — the event says WHAT changed,
    //      the API says WHAT IT IS NOW. One source of truth (Day 225).
  };

  es.onerror = () => setConnected(false);   // ⭐ EventSource retries itself
  return () => es.close();                  // ⭐⭐ CLEANUP (Day 226)
}, [qc]);
```

> ⭐⭐ **Invalidate, do not patch.** Applying `evt.newStatus` directly to the cache means your client is
> now *computing* state from a stream of deltas — and one missed message leaves it permanently wrong
> with no way to notice. **Treating the event as a hint keeps the server authoritative.**

# Part 3 — Reconnection and the visible state

```
⭐⭐ THE USER MUST BE ABLE TO TELL. ⭐ A stale screen that looks
⭐   live is worse than an obviously disconnected one.

⭐   · ⭐ A SMALL INDICATOR: "Live" / "Reconnecting…" / "Offline"
⭐   · ⭐⭐ ON RECONNECT: refetch, then the indicator returns to Live
⭐   · EXPONENTIAL BACKOFF + JITTER (Day 227) if you hand-roll it —
⭐     ⭐⭐ 10,000 CLIENTS RECONNECTING IN LOCKSTEP AFTER YOUR DEPLOY
⭐     IS A SELF-INFLICTED THUNDERING HERD
⭐   · ⭐ PAUSE WHEN HIDDEN: document.visibilityState === "hidden"
⭐     ⇒ ⭐⭐ A TAB OPEN SINCE TUESDAY SHOULD NOT HOLD A CONNECTION
⭐       AND POLL ALL WEEK. Reconnect + refetch on visible.
```

```typescript
// ⭐⭐ the four lines that stop a background tab costing you money
useEffect(() => {
  const onVis = () => {
    if (document.visibilityState === "visible") {
      qc.invalidateQueries();          // ⭐ catch up on return
    }
  };
  document.addEventListener("visibilitychange", onVis);
  return () => document.removeEventListener("visibilitychange", onVis);
}, [qc]);
```

| ⭐ Server-side, for SSE | |
|---|---|
| **Disable proxy buffering** | ⭐⭐ nginx `proxy_buffering off` — otherwise events are held and "real-time" arrives in bursts (Day 453) |
| **Heartbeat every ~20 s** | ⭐ A comment line keeps idle-timeout proxies from closing it |
| **`X-Accel-Buffering: no`** | ⭐ The header that fixes it when you cannot change nginx |
| **Worker model** | ⭐⭐ Each connection **holds a worker slot**. With sync workers, 20 open tabs can exhaust the pool (Day 453). |

# Part 4 — The multi-tab reality

```
⭐⭐ FIVE TABS = FIVE CONNECTIONS = 5× THE SERVER COST FOR ONE USER.
⭐   ⭐ Browsers cap ~6 connections per host on HTTP/1.1, so a
⭐     sixth tab can HANG WAITING — including for normal API calls.
⭐   ⇒ ⭐ HTTP/2 mostly removes the cap. ⭐⭐ BUT THE SERVER COST
⭐     IS REAL EITHER WAY.
⭐   ⇒ ⭐ FIXES: pause hidden tabs (above) — ⭐⭐ THE 90% FIX —
⭐     or a BroadcastChannel so one leader tab holds the connection
⭐     and fans out to the others.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how did you do real-time?"**

Start with the honest default, because reaching for WebSockets is the expected answer and the weaker
one. **I started with a five-second poll, and for a lot of applications that's where I'd stop — no new
protocol, no reconnection logic, no sticky sessions, and it survives every network event for free. I
moved to SSE because it's server-push only, which is what I actually needed, and it reconnects itself.
A WebSocket would have been bidirectional machinery I don't use.**

Then the real design problem. **A real-time connection isn't a feature, it's a distributed system in
the browser. It will drop. The failure everyone has is the gap: the laptop lid closes at nine, it
reconnects at half past, and the twenty-seven minutes of events in between are gone. The connection is
healthy and the screen is silently wrong.**

Then the fix, and why that shape. **On every open — not just the first — I invalidate the queries. The
event stream is a hint that something changed, and the REST API stays the source of truth. I invalidate
rather than patching the cache, because applying deltas means the client is computing state from a
stream, and one missed message leaves it permanently wrong with nothing to notice it.**

Close on the operational details. **There's a visible connection indicator, because a stale screen that
looks live is worse than an obviously disconnected one. Hidden tabs release the connection and catch up
on return — a tab open since Tuesday shouldn't hold a worker slot all week. And on the server side,
proxy buffering has to be off, or "real-time" arrives in bursts.**
