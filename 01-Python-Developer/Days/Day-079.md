# Day 079

**L-079** · ⭐ **The shell** — pipes, redirection, exit codes, expansion, and why quoting is the whole language

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the shell is a program that expands text into a list of words and then
> calls `fork` and `exec` — so every surprising behaviour is an expansion you did not expect, and every
> quoting rule is about stopping one.**
>
> ⭐ You already know the second half from Day 076: `shell=True` is dangerous *because* the shell
> expands. **Today is what it expands, and in what order.**

---

# Part 1 — ⭐⭐ What the shell actually does with a line

```
⭐⭐ YOU TYPE:   grep -n "$pattern" *.py | head -5
⭐
⭐   1. SPLIT into words on spaces
⭐   2. ⭐⭐ EXPAND each word (Part 4) ⇒ "$pattern" becomes its value; *.py becomes
⭐        a LIST OF FILENAMES — ⭐ the shell does this, NOT grep
⭐   3. set up the pipe: create a pipe pair, wire fd 1 of grep to fd 0 of head
⭐   4. ⭐ fork() twice ⇒ two child processes                        (Day 064)
⭐   5. ⭐⭐ exec() in each child ⇒ the process IMAGE is replaced by the program
⭐   6. wait() for the last one; ⭐ its exit status becomes $?
⭐
⭐⭐ ⇒ THE PROGRAM NEVER SEES YOUR TEXT. It receives argv — a list of strings that
⭐     the shell already finished mangling. ⭐⭐ THIS IS THE WHOLE MODEL.
```

⭐⭐ **This is exactly `subprocess`** (Day 076), which is why that day's rule now reads as a
consequence rather than a rule: **passing a list means step 2 never happens** — no expansion, so
nothing to inject. **`shell=True` re-enables the entire expansion machinery on a string you built.**

```python
subprocess.run(["grep", "-n", pattern, "app.py"])     # ⭐⭐ argv directly. No shell exists.
subprocess.run(f"grep -n {pattern} *.py", shell=True) # ⚠️ steps 1-2 run on YOUR string
```

⭐ **`echo *` is the demonstration worth doing once:** `echo` has no idea what a glob is. It prints the
filenames because **the shell had already replaced `*` before `echo` started.**

| ⭐ Fact | ⭐ Consequence |
|---|---|
| ⭐⭐ A child gets a **copy** of the environment | `export X=1` in a script cannot change your shell |
| ⭐⭐ `cd` must therefore be a **builtin** | a child `cd` would exit and leave you where you were |
| `type cmd` / `command -v` | ⭐ tells you builtin vs alias vs file — the first debugging step |

# Part 2 — ⭐⭐ Three file descriptors, and the ordering trap

```
⭐⭐ EVERY PROCESS STARTS WITH THREE OPEN FILES (Day 078: everything is a file):
⭐    0  stdin    ← keyboard, or a pipe, or a file
⭐    1  stdout   → ⭐⭐ THE RESULT. What the program was asked to produce.
⭐    2  stderr   → ⭐⭐ DIAGNOSTICS. Errors, progress, warnings.
⭐
⭐   ⇒ ⭐⭐ THE SPLIT EXISTS SO THAT  prog | other  KEEPS WORKING WHILE PROG COMPLAINS.
⭐        Errors must not contaminate the data. ⭐ This is why logging goes to stderr
⭐        by default (Day 076) and why `print()` — stdout — is the wrong tool in a service.
```

```bash
cmd > out.txt          # ⭐ stdout to a file (TRUNCATES)      ⚠️ >> appends
cmd 2> err.txt         # ⭐ stderr only
cmd > out 2>&1         # ⭐⭐ BOTH to out       ⭐ bash shorthand: cmd &> out
cmd 2>&1 > out         # ⚠️⚠️ NOT THE SAME — see below
cmd < in.txt           # ⭐ stdin from a file
cmd > /dev/null 2>&1   # ⭐ silence
cmd | tee log.txt      # ⭐⭐ see it AND save it — the one to remember
```

```
⭐⭐ WHY THE ORDER MATTERS — `2>&1` MEANS "MAKE fd 2 A COPY OF fd 1 *AS IT IS NOW*":
⭐
⭐   cmd > out 2>&1      1 → out ; then 2 → (copy of 1) = out      ⭐⭐ BOTH IN out ✔
⭐   cmd 2>&1 > out      2 → (copy of 1) = TERMINAL ; then 1 → out
⭐                       ⇒ ⭐⭐ stderr STILL GOES TO THE TERMINAL. ✗
⭐
⭐   ⇒ ⭐ read it as ASSIGNMENT, not as a declaration. It is a snapshot, left to right.
```

```
⭐⭐ THE PYTHON BUG THIS EXPLAINS — "MY DOCKER LOGS ARE EMPTY":
⭐   Python's stdout is LINE-buffered on a terminal and BLOCK-buffered (4-8 KB)
⭐   when it is a pipe or a file.  ⇒ ⭐⭐ `python app.py > log` or `docker logs`
⭐   shows NOTHING until 8 KB accumulates — or forever, if the process is killed.
⭐   ⇒ ⭐⭐ FIX: python -u   or   ENV PYTHONUNBUFFERED=1   in every Dockerfile.
⭐   ⇒ ⭐ and stderr is unbuffered, which is why the traceback appears but the
⭐        print() before it does not — ⭐⭐ making the logs actively misleading.
```

# Part 3 — ⭐⭐ Pipes and exit codes

```
⭐⭐ A PIPE IS AN IN-KERNEL BUFFER (~64 KB) WITH TWO ENDS.
⭐
⭐   producer ──write──▶ [ buffer ] ──read──▶ consumer
⭐
⭐   ⇒ ⭐⭐ BOTH PROCESSES RUN AT THE SAME TIME. A pipeline is CONCURRENCY, and
⭐        on a multi-core box it is genuine PARALLELISM (Day 065 — no GIL between
⭐        separate processes). ⭐ `cat huge | grep x` starts producing immediately;
⭐        it does not read the file first.
⭐   ⇒ ⭐⭐ BACKPRESSURE IS FREE: buffer full ⇒ the writer BLOCKS in write().
⭐        ⭐ You get flow control with no code, which is why streaming through a
⭐        pipeline uses constant memory — exactly a generator pipeline (Day 047).
⭐   ⇒ ⭐⭐ IF THE READER EXITS FIRST the writer gets SIGPIPE and dies.
⭐        ⭐ In Python that surfaces as BrokenPipeError:
⭐             python gen.py | head -5      ⇒ head exits at line 5 ⇒ traceback.
⭐        ⭐ It is not a bug in your program — it is the pipeline working.
```

```bash
$ grep -c ERROR app.log ; echo $?     # ⭐⭐ $? = exit status of the last command
# ⭐ 0 = SUCCESS. Non-zero = a failure, and the number often says which.
```

| Code | ⭐ Meaning |
|---|---|
| `0` | ⭐⭐ success — **zero is true here, unlike Python** |
| `1` | general failure |
| `2` | misuse / bad arguments |
| `126` / `127` | not executable / **not found** — ⭐ `127` is the typo one |
| ⭐⭐ `128+n` | ⭐⭐ **killed by signal n** — `137` = 128+9 = SIGKILL ⇒ often **OOM** (Day 081) |

```bash
a && b        # ⭐ run b only if a SUCCEEDED (exit 0)
a || b        # ⭐ run b only if a FAILED       ⭐ ruff check . || exit 1
a ; b         # ⭐ run both regardless
a & b         # ⭐ background a
$(cmd)        # ⭐⭐ command substitution — the OUTPUT becomes text
```

⚠️ ⭐⭐ **A pipeline's exit status is the status of the *last* command only.** So `false | true`
succeeds, and — the one that ships — **`python fetch.py | tee out.json` reports success even when
`fetch.py` crashed.** ⭐ Tomorrow's `set -o pipefail` (Day 083) is the fix; today the point is that
**the default is wrong and you have to opt out of it.**

⭐ **`sys.exit(1)` in Python is how you participate.** `sys.exit("message")` prints to stderr and exits
1; an uncaught exception exits 1 too. **A CLI that reports failure by printing and returning 0 is
unusable in a pipeline or in CI** — which is Day 060's error-handling design, on the process boundary.

# Part 4 — ⭐⭐ Expansion and quoting — the actual source of shell bugs

```
⭐⭐ THE ORDER, LEFT TO RIGHT, ONCE PER WORD:
⭐   1. brace          {a,b}.txt ⇒ a.txt b.txt
⭐   2. tilde          ~ ⇒ /home/you
⭐   3. parameter      $VAR  ${VAR:-default}  ${VAR:?error if unset}
⭐   4. command        $(date +%F)      ⭐ prefer over backticks — nests, readable
⭐   5. arithmetic     $(( 3 * 7 ))
⭐   6. ⭐⭐ WORD SPLITTING   ← ⭐⭐ THE DANGEROUS ONE. Splits on IFS (space/tab/newline).
⭐   7. ⭐ GLOBBING        *.py ⇒ filenames
⭐   8. quote removal
⭐
⭐⭐ ⇒ STEP 6 HAPPENS AFTER STEP 3. THAT IS THE ENTIRE PROBLEM:
⭐     file="my report.pdf" ;  rm $file    ⇒ expands, THEN splits ⇒ rm my report.pdf
⭐                                          ⇒ ⭐⭐ TWO ARGUMENTS. Deletes the wrong things.
⭐     ⇒ ⭐⭐ rm "$file"   ⇒ quoting SUPPRESSES step 6 ⇒ one argument. ✔
⭐     ⇒ ⭐⭐ THE RULE: QUOTE EVERY VARIABLE EXPANSION. Every one. No exceptions
⭐          worth learning, because the exceptions are the bugs.
```

| Quote | ⭐ Effect |
|---|---|
| `'single'` | ⭐⭐ **literal — nothing expands.** Use for regexes, passwords, `$` |
| `"double"` | ⭐ expands `$var`, `` `cmd` ``, `\` — ⭐⭐ **but suppresses splitting and globbing** |
| none | ⭐⭐ everything, including splitting and globbing |

```bash
grep '$100' file        # ⭐ literal $100     ·  grep "$pattern" file   ⭐ the variable
echo "$*"               # ⭐ all args as ONE string
echo "$@"               # ⭐⭐ all args as SEPARATE, correctly-quoted words ← the one you want
"${ARR[@]}"             # ⭐ same rule for arrays
```

```bash
# ⭐⭐ ENVIRONMENT — a shell variable is NOT an environment variable until exported:
NAME=value              # ⭐ shell-local. A child process cannot see it.
export NAME=value       # ⭐⭐ now it is in the environment ⇒ inherited by children
DEBUG=1 python app.py   # ⭐⭐ set for ONE command only — the cleanest form
env | sort              # ⭐ what a child will actually receive   · unset NAME
```

⭐⭐ **This is `os.environ` from the other side.** Python reads the environment its parent handed it,
**a copy made at exec time** — so `os.environ["X"] = "1"` affects *your* process and any child you
start afterwards, and can never affect the shell that started you. ⭐ `.env` files are read by a
library (`pydantic-settings`, Stage 4); **the shell knows nothing about them.**

⚠️ ⭐ **Secrets in the environment are visible** — `/proc/PID/environ` (Day 082), `ps eww`, and any
crash reporter that dumps the environment. **Better than a committed file, worse than a secrets
manager.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Unquoted `$var`** | ⭐⭐ Word splitting. **Quote every expansion.** |
| `cmd 2>&1 > file` | ⭐⭐ Wrong order — stderr still goes to the terminal. |
| ⭐ Expecting `\|` to check the first command | ⭐⭐ Only the **last** status counts. `pipefail`. |
| ⭐ Empty Docker/CI logs | ⭐⭐ Block buffering. `PYTHONUNBUFFERED=1`. |
| Treating exit 0 as false | ⭐⭐ **0 is success.** The inverse of Python truthiness. |
| ⭐ `BrokenPipeError` treated as a bug | ⭐ `head` closed the pipe. That is correct behaviour. |
| `NAME=x` then expecting a child to see it | ⭐ Not exported. |
| ⭐ A CLI that prints an error and exits 0 | ⭐⭐ Unusable in `&&`, in a pipeline, or in CI. |
| Backticks | ⭐ Use `$(...)` — nests and reads. |
| `for f in $(ls)` | ⭐⭐ Splits on spaces. Use a glob: `for f in *.py`. |
| ⭐ `echo` with user data | ⭐ Use `printf '%s\n'` — `echo` interprets flags and escapes. |

## Interview questions

**Q: What does the shell do between you pressing Enter and the program running?**
> It splits the line into words, expands each one — variables, command substitution, then word
> splitting and globbing — wires up any redirections and pipes, then forks and execs. The key point
> is that the program never sees what you typed: it receives `argv`, a list of strings the shell has
> already finished transforming. That's why `echo *` prints filenames even though `echo` has no idea
> what a glob is, and it's exactly why passing a list to `subprocess` is injection-proof — no shell
> means no expansion step to hijack.

**Q: Why quote variables in shell scripts?**
> Because word splitting happens *after* variable expansion. If `$file` contains "my report.pdf" then
> `rm $file` expands first and splits second, so `rm` receives two arguments and deletes the wrong
> things — or, with an unset variable, receives none and does something worse. Double quotes suppress
> splitting and globbing while still allowing expansion, which is almost always what you want. I treat
> it as unconditional: every expansion gets quoted, because the exceptions are exactly where the bugs
> are.

**Q: Why are your container logs empty until the app crashes?**
> Python line-buffers stdout when it's a terminal and block-buffers it — several kilobytes — when it's
> a pipe or a file, which is what Docker gives you. So `print` output sits in the buffer while stderr,
> which is unbuffered, comes through immediately. That makes the logs actively misleading: you see the
> traceback but not the messages that led up to it, and if the process is SIGKILLed the buffer is
> simply lost. The fix is `PYTHONUNBUFFERED=1` or `python -u`, and it belongs in every Dockerfile.

**Q: What's the difference between stdout and stderr, and why does it exist?**
> stdout is the program's result, stderr is its commentary. The split exists so that `prog | other`
> keeps working while `prog` complains — errors must never contaminate the data flowing down the
> pipeline. That's the reasoning behind logging going to stderr by default, and behind `print` being
> the wrong tool in a service: a diagnostic on stdout will one day end up parsed as data.

**Q: `python fetch.py | tee out.json` exits 0 but the JSON is empty. Why?**
> Because a pipeline's exit status is the status of its last command, and `tee` succeeded. The
> failure of `fetch.py` is discarded, so CI goes green over a broken artefact. `set -o pipefail` makes
> the pipeline report the first failing command instead, and it's part of the standard script header
> for exactly this reason. The related habit on the Python side is actually exiting non-zero —
> `sys.exit(1)` — because a CLI that prints an error and returns 0 can't be composed with anything.

## 🎙️ Articulation drill

Record two minutes: **"Why is passing a list to `subprocess` safer than `shell=True`?"** — the same
question as Day 076, **now answered from the mechanism instead of the rule.**

⭐ Start with what a shell is: **"the shell's job is to expand text into an argv list and then fork and
exec. Expansion is where variables, command substitution, word splitting and globbing happen — and
all of it happens before the program starts, so the program only ever sees a finished list of
strings."**

⭐⭐ **Then the conclusion falls out rather than being asserted:** *"so `shell=True` means my string
goes through the expansion machinery. A semicolon is a command separator, backticks are substitution,
`$(...)` runs something — none of that is escaping I can win by sanitising. Passing a list skips step
two entirely: there is no shell process, the arguments go straight to `execve`, so there is nothing to
parse and therefore nothing to inject."*

⭐ **Close by generalising, which is what makes it a senior answer:** *"it is the same principle as
parameterised SQL and template autoescaping — you do not sanitise data into code, you keep them in
separate channels. And the one place I do need a shell — a pipe or a glob — I usually do in Python
instead."*
