# Day 240 🩹

**P-240** · 🩹 **Error boundaries and empty states** — ⭐⭐ the white screen, and what boundaries miss

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an uncaught render error unmounts your entire application and leaves a
> blank white page — React does this deliberately, because a half-rendered UI can show wrong data —
> so a boundary is not a nicety, it is the difference between one broken widget and a dead app.**
>
> Today: the white screen, ⭐⭐ the four things boundaries do **not** catch, ⭐ where to place them,
> and empty states done properly.

---

# Part 1 — The white screen

```jsx
function OrderTotal({ order }) {
  return <p>{order.total.toFixed(2)}</p>;   // ⭐⭐ order.total is null
}                                            //    ⇒ TypeError ⇒ WHOLE APP GONE
```

```
⭐⭐ WHY REACT UNMOUNTS EVERYTHING

⭐   ⭐ A component that threw is in an UNKNOWN state. React's choice:
⭐     show NOTHING rather than show something POSSIBLY WRONG.
⭐   ⇒ ⭐⭐ FOR A BANKING APP THAT IS THE CORRECT CHOICE.
⭐     ⭐ For your dashboard it means one null field kills the page.
⭐   ⇒ ⭐⭐ SO THE BOUNDARY IS HOW YOU SCOPE THE BLAST RADIUS —
⭐     THE SAME DECISION AS DAY 456'S DEGRADATION LADDER.
```

```jsx
class ErrorBoundary extends React.Component {   // ⭐ must be a class, still
  state = { error: null };
  static getDerivedStateFromError(error) { return { error }; }
  componentDidCatch(error, info) {
    reportError(error, { componentStack: info.componentStack });  // ⭐ Day 279
  }
  render() {
    if (this.state.error) {
      return this.props.fallback ?? <ErrorPanel
        onRetry={() => this.setState({ error: null })} />;  // ⭐⭐ RETRY
    }
    return this.props.children;
  }
}
```

> ⭐ **The retry matters.** A boundary with no way back forces a full page reload, which loses
> everything the user typed. `reset` + refetch recovers from a transient failure in place.

# Part 2 — ⭐⭐ What boundaries do NOT catch

```
⭐⭐ THIS IS THE PART PEOPLE GET WRONG IN INTERVIEWS.

⭐   ❌ ① EVENT HANDLERS
⭐        onClick={() => { throw new Error() }}  ⇒ ⭐⭐ NOT CAUGHT.
⭐        ⭐ Use try/catch in the handler.
⭐   ❌ ② ASYNC CODE
⭐        setTimeout, promises, ⭐⭐ ANYTHING AFTER AN await ⇒ NOT CAUGHT.
⭐        ⭐ This is most of your real error surface.
⭐   ❌ ③ SERVER-SIDE RENDERING errors (different mechanism)
⭐   ❌ ④ ⭐⭐ ERRORS THROWN BY THE BOUNDARY'S **OWN** FALLBACK
⭐        ⇒ ⭐ that propagates UP, and if there is nothing above it,
⭐          you get the white screen anyway. KEEP FALLBACKS TRIVIAL.

⭐   ⇒ ⭐⭐ A BOUNDARY CATCHES **RENDER** ERRORS. THAT IS ALL.
⭐     ⇒ so you ALSO need: the Day 216 unhandledrejection listener,
⭐       window.onerror, and try/catch in handlers.
```

| ⭐ Error source | ⭐ Caught by |
|---|---|
| Render, lifecycle, constructor | ⭐⭐ Error boundary |
| Event handler | `try/catch` in the handler |
| Promise rejection | ⭐⭐ `unhandledrejection` listener |
| A query's fetch | ⭐ The query library's `isError` — **handled, not thrown** |
| Everything else | `window.onerror` |

# Part 3 — Where to put them

```
⭐⭐ THREE LEVELS. NOT ONE, NOT FIFTY.

⭐   ① ⭐ ROOT — the last resort. "Something went wrong, reload."
⭐        ⭐⭐ Its ONLY job is to never be blank.
⭐   ② ⭐⭐ PER ROUTE — a broken /reports must not kill /orders.
⭐        ⭐ Nested layouts (Day 233) give you this for free.
⭐   ③ ⭐ PER INDEPENDENT WIDGET — a dashboard where the revenue
⭐        chart fails but the other five panels still render.

⭐   ⇒ ⭐⭐ THE PLACEMENT QUESTION IS ALWAYS: "WHAT IS THE SMALLEST
⭐     THING THAT CAN FAIL WITHOUT MAKING THE REST USELESS?"
⭐     ⇒ ⭐ That is exactly the bulkhead reasoning from Stage 12.
```

| ⭐ Fallback should say | Not |
|---|---|
| ⭐⭐ What failed, in user terms — "Couldn't load revenue" | "Error" |
| ⭐ What they can do — **Retry**, go back, contact support | A dead end |
| ⭐ A reference id for support | ⭐⭐ A stack trace (which leaks internals and helps nobody) |

# Part 4 — ⭐⭐ The four states, finally

```
⭐⭐ EVERY DATA-DRIVEN SCREEN. NO EXCEPTIONS.

⭐ ① LOADING ⇒ ⭐ a SKELETON shaped like the content.
⭐    ⭐⭐ NOT a centred spinner that is replaced by content of a
⭐      different size — that is layout shift, and it is measured
⭐      (CLS, Day 241).
⭐    ⭐ Do not show it for <200 ms — a flash is worse than a wait.

⭐ ② ERROR ⇒ ⭐⭐ WHAT HAPPENED + WHAT TO DO. Branch on status:
⭐      401 ⇒ sign in again      403 ⇒ "you don't have access"
⭐      404 ⇒ "not found" + back  429 ⇒ "too many requests, retrying"
⭐      5xx ⇒ "our side — retry"  offline ⇒ "you appear to be offline"

⭐ ③ ⭐⭐ EMPTY ⇒ THE MOST-MISSED STATE, AND THE MOST NOTICED.
⭐    ⭐ SPLIT IT IN TWO — they need different words:
⭐      · ⭐⭐ NEVER HAD ANY ⇒ explain + THE ACTION THAT CREATES ONE
⭐        ("No orders yet" + [Create order])
⭐      · ⭐⭐ FILTERED TO ZERO ⇒ "No orders match 'xyz'" +
⭐        [Clear filters]  ⇒ ⭐ SHOWING "no orders yet" TO SOMEONE
⭐        WITH 500 ORDERS AND A BAD FILTER IS A REAL BUG.

⭐ ④ SUCCESS ⇒ the one everybody builds first.
```

> ⭐ **Two more that separate a real app from a demo:** *partial* success (Day 216's `allSettled` — some
> widgets loaded, one did not) and *stale* (showing cached data while refetching, with a subtle
> indicator rather than a spinner that hides working content).

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "what happens when a component throws?"**

State the behaviour and the reason, because the reason is the interesting half. **The whole app
unmounts and you get a blank white page. React does that deliberately — a component that threw is in an
unknown state, and showing nothing is safer than showing something possibly wrong. For a banking app
that's the correct default. For my dashboard it means one null field kills the page, so a boundary is
how I scope the blast radius.**

Then the limits, which is where most answers stop too early. **A boundary catches render errors and
nothing else. Not event handlers, not anything after an await, not errors thrown by its own fallback —
which propagate up and give you the white screen anyway, so fallbacks stay trivial. Async is most of my
real error surface, so I also need an unhandledrejection listener and try/catch in handlers. Saying
"error boundaries handle errors" is the answer that gets followed up.**

Then placement as a familiar principle. **Three levels: root so it's never blank, per route so a broken
reports page doesn't kill orders, and per independent widget on a dashboard. The question is always what
the smallest thing is that can fail without making the rest useless — which is bulkheading.**

Close on the state everyone forgets. **Every screen gets four states, and empty is the one that's
missed and the one reviewers notice. It has to be split in two: never had any, which needs the action
that creates one, versus filtered to zero, which needs a way to clear the filter. Showing "no orders
yet" to someone with five hundred orders and a bad filter is a real bug.**
