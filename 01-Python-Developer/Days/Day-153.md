# Day 153

**L-153** · **Rate limiting and quotas in production** — distributed counters, ⭐⭐ multi-tenant fairness, and the 429 contract

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a rate limit protects the *service* from a moment, a quota protects the
> *business* over a period, and abuse protection protects users from each other — three different

>

# Part 1 — ⭐⭐ Three different problems

```
⭐⭐ PEOPLE SAY "RATE LIMITING" AND MEAN ONE OF THREE THINGS. THEY HAVE
⭐   DIFFERENT WINDOWS, DIFFERENT KEYS, AND DIFFERENT RESPONSES:

⭐  1. ⭐ RATE LIMIT — protects CAPACITY. ⭐ "100 req/min per key."
⭐       ⭐ window: seconds/minutes · ⭐ response: ⭐⭐ 429 + `Retry-After`
⭐       ⭐ Enforced in a cheap, hot path. ⭐⭐ Resets constantly.
⭐
⭐  2. ⭐ QUOTA — protects REVENUE AND COST. ⭐ "1,000,000 API calls/month
⭐       on the Pro plan", "50 GB of storage".
⭐       ⭐ window: billing period · ⭐⭐ response: 402 or 403, NOT 429 —
⭐       ⭐ because `Retry-After` would be "18 days", which is not a retry,
⭐       it is an UPGRADE PROMPT. ⭐⭐ Using 429 here makes every client SDK
⭐       retry a request that can never succeed this month.
⭐
⭐  3. ⭐⭐ ABUSE / FAIRNESS — protects OTHER USERS. ⭐ "no single tenant may
⭐       consume more than 30% of the pool", "5 failed logins per account".
⭐       ⭐ window: adaptive · ⭐ response: 429, a CAPTCHA, or a slowdown.
⭐
⭐   ⇒ ⭐⭐ THE PRACTICAL CONSEQUENCE: THEY ARE DIFFERENT COUNTERS WITH
⭐        DIFFERENT KEYS, AND A REQUEST MAY PASS TWO AND FAIL THE THIRD.
⭐        ⭐ Trying to express a monthly quota as a rate limit gives you either
⭐        a 30-day Redis key (which cannot be reasoned about) or a wrong answer.
```

```
⭐⭐ AND THE KEY CHOICE, WHICH IS WHERE MOST DESIGNS GO WRONG:

⭐   ⭐ BY IP        — ⭐⭐ the default, and the WORST for authenticated APIs.
⭐        ⭐ One corporate NAT is 5,000 employees behind one IP; ⭐⭐ mobile
⭐        carriers rotate IPs per request; IPv6 gives an attacker a /64.
⭐        ⭐ Use it ONLY for unauthenticated endpoints, and by SUBNET for v6.
⭐   ⭐ BY API KEY / USER — ⭐⭐ correct for authenticated traffic. Stable,
⭐        attributable, and it survives NAT.
⭐   ⭐ BY TENANT    — ⭐ correct for B2B: the noisy neighbour is an org.
⭐   ⭐⭐ BY (KEY, ROUTE CLASS) — ⭐ the one people forget. A 100/min global
⭐        limit lets someone spend all of it on your most expensive endpoint.
⭐        ⭐⭐ Limit cheap reads generously and the expensive report endpoint
⭐        tightly — ⭐ the resource you are protecting is CPU, not requests.
⭐   ⇒ ⭐⭐ AND ALWAYS LIMIT LOGIN BY ACCOUNT ***AND*** BY IP (Day 140).
⭐        ⭐ Per-IP alone loses to a botnet; per-account alone lets one IP
⭐        spray ten thousand accounts.
```

# Part 2 — ⭐⭐ Distributed: making the counter atomic

```
⭐⭐ WHY THE Day 123 VERSION BREAKS AT TWO REPLICAS:
⭐   ⭐ each process has its own counter ⇒ ⭐⭐ N replicas = N × the limit.
⭐   ⭐ autoscaling then makes your limit a FUNCTION OF YOUR REPLICA COUNT —
⭐        ⭐ so it loosens exactly when you are under load.

⭐⭐ AND THE OBVIOUS REDIS FIX IS ALSO BROKEN:
⭐   ❌  n = redis.get(key)
⭐       if n < limit: redis.incr(key)        ⭐⭐ READ-MODIFY-WRITE ⇒ a RACE
⭐   ⭐ Day 067's race with Redis as the shared object. ⭐ Twelve replicas at
⭐     the boundary all read 99 and all increment.
⭐
⭐   ⇒ ⭐⭐ THE FIX IS THE SAME AS EVERY OTHER TIME: MAKE THE CHECK AND THE
⭐        INCREMENT ONE ATOMIC OPERATION. (Day 122's claim, Day 143's `NX`.)
```

```lua
-- ⭐⭐ SLIDING-WINDOW LOG, ATOMIC, IN ONE ROUND TRIP
local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)   -- ⭐ drop expired
local count = redis.call('ZCARD', key)
if count < limit then
  redis.call('ZADD', key, now, ARGV[4])                -- ⭐ unique member id
  redis.call('EXPIRE', key, window)                    -- ⭐⭐ ALWAYS set a TTL
  return {1, limit - count - 1}
end
return {0, 0}
```

```
⭐⭐ WHY LUA AND NOT A PIPELINE: ⭐ a Lua script runs ATOMICALLY on Redis's
⭐   single thread (Day 143) — ⭐⭐ nothing interleaves, and it is ONE round
⭐   trip instead of three. ⭐ At 10k rps, round trips are the cost.
⭐   ⚠ ⭐⭐ AND KEEP IT SHORT: a slow script blocks EVERY client, because
⭐     that single thread is also serving your cache.

⭐⭐ ALGORITHM CHOICE, RESTATED FOR PRODUCTION (Day 123's five, judged):
⭐   ⭐ FIXED WINDOW    — ⭐⭐ allows a 2× burst at the boundary. ⭐ Cheapest.
⭐        Fine when the limit is a rough guard rather than a guarantee.
⭐   ⭐ SLIDING LOG     — ⭐ exact, ⭐⭐ but O(n) MEMORY PER KEY: one ZSET
⭐        member per request. ⭐ At 10k/min per key that is real memory.
⭐   ⭐⭐ SLIDING COUNTER — ⭐ two fixed windows, weighted by overlap. ⭐⭐ O(1)
⭐        memory, ~99% accurate. ⭐ THE PRODUCTION DEFAULT — say this one.
⭐   ⭐⭐ TOKEN BUCKET   — ⭐ the only one that expresses "sustained rate PLUS a
⭐        burst allowance", which is what humans actually want. ⭐⭐ Two
⭐        numbers (rate, capacity), stored as (tokens, last_refill).
⭐        ⭐ Best for APIs with legitimate bursty clients.
```

# Part 3 — ⭐⭐ The 429 contract, and where the limit lives

```
⭐⭐ A RATE LIMIT WITHOUT HEADERS IS A GUESSING GAME. THE CONTRACT:

⭐   HTTP/1.1 429 Too Many Requests
⭐   Retry-After: 30                       ⭐⭐ SECONDS (or an HTTP date).
⭐                                            ⭐ WITHOUT THIS, WELL-BEHAVED
⭐                                            CLIENTS RETRY IMMEDIATELY and
⭐                                            you have built a retry storm
⭐                                            (Day 152) INTO YOUR OWN DESIGN.
⭐   RateLimit-Limit: 100                  ⭐ the ceiling
⭐   RateLimit-Remaining: 0                ⭐⭐ ON *EVERY* RESPONSE, not just
⭐                                            429s — so a client can slow down
⭐                                            BEFORE being blocked
⭐   RateLimit-Reset: 30                   ⭐ seconds until the window resets
⭐
⭐   ⭐ (`X-RateLimit-*` is the older de-facto spelling; the IETF draft drops
⭐     the `X-`. ⭐⭐ Pick one, document it, never change it — Day 125.)
⭐
⭐   ⇒ ⭐⭐ AND THE BODY IS A PROBLEM-DETAILS OBJECT WITH A MACHINE-READABLE
⭐        `code` (Day 120): `rate_limited` vs `quota_exceeded` are DIFFERENT
⭐        codes because they demand different client behaviour — ⭐ one waits,
⭐        one upgrades.
⭐
⭐⭐ 429 vs 503: ⭐ 429 means "YOU are over your limit". ⭐⭐ 503 means "the
⭐   SERVICE is overloaded" (Day 152's load shedding). ⭐ Different causes,
⭐   different fixes, and conflating them means a well-behaved client backs
⭐   off for a problem that is not theirs.
```

```
⭐⭐ WHERE TO ENFORCE — three layers, and you want more than one:
⭐  1. ⭐ EDGE (CDN / WAF / API gateway) — ⭐⭐ THE ONLY PLACE THAT PROTECTS
⭐       YOU FROM A FLOOD, because it rejects before the bytes reach your
⭐       network. ⭐ Coarse: per-IP, per-path.
⭐  2. ⭐ GATEWAY / INGRESS — per API key, still cheap, ⭐ shared across all
⭐       services behind it.
⭐  3. ⭐⭐ APPLICATION — the only place that knows PLAN, TENANT, ROUTE COST
⭐       and USER. ⭐ Necessarily the most expensive place, and the only one
⭐       that can express your business rules.
⭐   ⇒ ⭐⭐ APPLICATION-LEVEL LIMITING CANNOT SAVE YOU FROM A VOLUMETRIC
⭐        ATTACK — by the time you count the request you have already paid
⭐        for the TCP handshake, TLS, and a worker. ⭐ Say this explicitly;
⭐        it is the distinction between a business rule and a defence.
```

# Part 4 — ⭐⭐ Multi-tenant fairness, and the noisy neighbour

```
⭐⭐ THE PROBLEM PER-KEY LIMITS DO NOT SOLVE: EVERY TENANT IS WITHIN ITS
⭐   LIMIT AND THE SERVICE IS STILL DEGRADED.
⭐   ⭐ 500 tenants × 100 req/min each = 50,000/min. ⭐ You provisioned for
⭐     10,000 because ⭐⭐ NOT EVERYONE USES THEIR FULL LIMIT — which is true
⭐     until the day it is not. ⭐ Limits are per-tenant; capacity is global.

⭐⭐ THREE MECHANISMS, IN INCREASING SOPHISTICATION:

⭐  1. ⭐ A GLOBAL CONCURRENCY CAP PER TENANT (not just a rate):
⭐       ⭐⭐ "no tenant may hold more than 20 concurrent requests" — ⭐ this
⭐       is Day 152's BULKHEAD, keyed by tenant. ⭐⭐ It bounds resource
⭐       occupancy, which a rate limit does not: 10 requests/min that each
⭐       take 60 s is a bigger problem than 1,000 that take 5 ms.
⭐
⭐  2. ⭐⭐ FAIR QUEUING / WEIGHTED SHARES. Under contention, serve tenants
⭐       round-robin rather than first-come-first-served. ⭐ A tenant that
⭐       floods the queue then waits behind everyone else's FIRST request,
⭐       not ahead of it. ⭐⭐ This is what makes one runaway script not
⭐       everyone's outage.
⭐
⭐  3. ⭐⭐ WORK-BASED ACCOUNTING, NOT REQUEST-BASED. ⭐ Charge COST, not
⭐       count: a report is 100 units, a health check is 1. ⭐⭐ GitHub and
⭐       Stripe both do versions of this, and it is the answer that shows you
⭐       have thought past "requests per minute" — ⭐ because the resource you
⭐       are protecting was never requests.
⭐
⭐ ⭐⭐ AND: DIFFERENTIATE BY PLAN, BUT ALSO BY BEHAVIOUR. ⭐ A client that
⭐   consistently gets 429s and keeps hammering can be given a longer
⭐   `Retry-After` — ⭐⭐ ADAPTIVE penalties turn a limit into a feedback loop
⭐   rather than a wall it can lean on continuously.
```

# Part 5 — ⭐⭐ Failure modes: what happens when the limiter breaks

```
⭐⭐ THE QUESTION THAT SEPARATES A DESIGN FROM A LIBRARY CALL:
⭐   ⭐ "REDIS IS DOWN. DO YOU FAIL OPEN OR FAIL CLOSED?"

⭐   ⭐⭐ FAIL OPEN (allow everything)
⭐        ⭐ + your service stays up
⭐        ⭐ − ⭐⭐ NO PROTECTION AT THE EXACT MOMENT YOU ARE ALREADY DEGRADED
⭐   ⭐⭐ FAIL CLOSED (reject everything)
⭐        ⭐ + limits are never bypassed
⭐        ⭐ − ⭐⭐ A CACHE OUTAGE BECOMES A TOTAL OUTAGE. ⭐ You converted a
⭐          degradation into a catastrophe with a config choice.
⭐
⭐   ⇒ ⭐⭐ THE ANSWER: FAIL OPEN FOR CAPACITY LIMITS, FAIL CLOSED FOR SECURITY
⭐        LIMITS. ⭐ An ordinary API limit failing open costs you some load.
⭐        ⭐⭐ LOGIN ATTEMPTS FAILING OPEN COSTS YOU AN UNTHROTTLED BRUTE-FORCE
⭐        WINDOW — ⭐ so that one fails closed, and you accept that logins are
⭐        unavailable while Redis is.
⭐   ⇒ ⭐ AND ALWAYS: a per-process fallback limiter (Day 123's in-memory
⭐        version) when Redis is unreachable. ⭐⭐ N × limit is a bad limit and
⭐        an infinitely better one than no limit.

⭐⭐ FOUR MORE PRODUCTION DETAILS THAT ARE EACH A REAL INCIDENT:
⭐   ⭐ ⭐⭐ NEVER LET THE LIMITER ADD LATENCY TO THE HAPPY PATH. A limiter
⭐        with no `socket_timeout` (Day 152) means a hung Redis hangs EVERY
⭐        request — ⭐ the thing protecting you becomes the outage.
⭐   ⭐ ⭐⭐ ALWAYS SET A TTL ON EVERY LIMITER KEY. Millions of per-IP keys
⭐        with no expiry is Day 143's memory exhaustion, and `allkeys-lru`
⭐        then evicts your SESSIONS to make room for rate-limit counters.
⭐   ⭐ EXEMPT HEALTH CHECKS AND INTERNAL TRAFFIC — ⭐⭐ rate-limiting your own
⭐        probes causes Day 149's restart loop.
⭐   ⭐ ⭐⭐ SHIP IT IN "OBSERVE" MODE FIRST: count what WOULD have been
⭐        blocked, alert on it, and look at who it is. ⭐ Almost every first
⭐        rollout finds that the top blocked client is your own mobile app or
⭐        a partner integration — ⭐⭐ and finding that in a metric is much
⭐        cheaper than finding it in a support queue.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| One counter for rate limits, quotas and abuse | Three problems, three windows, three responses. |
| 429 for a monthly quota | `Retry-After: 18 days` makes SDKs retry forever. Use 402/403. |
| Limiting by IP on an authenticated API | One NAT is 5,000 employees; carriers rotate IPs; IPv6 gives an attacker a /64. |
| One global limit regardless of route | The whole budget gets spent on your most expensive endpoint. |
| Login limited by IP only (or account only) | IP-only loses to a botnet; account-only lets one IP spray 10,000 accounts. |
| In-process counters behind N replicas | Your effective limit becomes a function of your replica count. |
| `GET` then `INCR` in Redis | Read-modify-write race — every replica reads 99 at the boundary. |
| A long Lua script | It blocks Redis's single thread, and that thread serves your cache too. |
| Sliding log at high volume | O(n) memory per key. Use the sliding counter. |
| No `Retry-After` | Well-behaved clients retry immediately — a retry storm you designed in. |
| Rate-limit headers only on 429s | Clients can't slow down before being blocked. Send them always. |
| 429 and 503 used interchangeably | "You're over your limit" and "we're overloaded" need different client behaviour. |
| App-level limiting as flood protection | You've already paid for the handshake, TLS and a worker before you count. |
| Per-tenant limits with no global cap | 500 tenants within their limits can still exceed your capacity. |
| Rate without a concurrency cap | 10 slow requests can outweigh 1,000 fast ones. |
| Counting requests rather than cost | The resource you're protecting was never requests. |
| No TTL on limiter keys | Memory exhaustion, and LRU then evicts your sessions. |
| Fail-closed on ordinary limits | A cache outage becomes a total outage. |
| Fail-open on login limits | An unthrottled brute-force window at the worst moment. |
| No `socket_timeout` on the limiter's Redis | The protection becomes the outage. |
| Rate-limiting health checks | Probes fail and you get Day 149's restart loop. |
| Enforcing on day one without observing | Your top blocked client is usually your own mobile app. |

## Interview questions

**Q: What's the difference between a rate limit and a quota?**

> Window, purpose and response. A rate limit protects capacity over seconds or minutes and answers
> 429 with `Retry-After`. A quota protects revenue and cost over a billing period and should answer
> 402 or 403 — because if you return 429 for a monthly quota, `Retry-After` is eighteen days, and
> every client SDK will dutifully retry a request that cannot succeed this month. They're different
> counters with different keys, and a request can pass one and fail the other. There's a third thing
> people fold in too: abuse and fairness protection, which is about protecting users from each other
> rather than protecting the service.

**Q: How do you rate limit across twelve replicas?**

> The counter has to be shared, and the check and increment have to be one atomic operation.
> In-process counters mean N replicas gives N times the limit, which is worst when it matters most —
> autoscaling loosens your limit exactly under load. But the naive Redis version is also wrong: `GET`
> then compare then `INCR` is read-modify-write, so at the boundary every replica reads ninety-nine
> and increments. I'd use a Lua script, which runs atomically on Redis's single thread and does it in
> one round trip instead of three — keeping it short, because that thread is also serving my cache.
> Algorithm-wise I'd default to a sliding-window counter: two fixed windows weighted by overlap, O(1)
> memory and about ninety-nine percent accurate, versus a sliding log which is exact but stores a
> member per request. Token bucket if clients are legitimately bursty, because it's the only one that
> expresses a sustained rate plus a burst allowance.

**Q: Redis goes down. Does your rate limiter fail open or closed?**

> Depends what the limit is for, and I'd split it. Capacity limits fail open — an ordinary API limit
> failing open costs some load, whereas failing closed converts a cache outage into a total outage,
> which is turning a degradation into a catastrophe with a config choice. Security limits fail
> closed: login attempt limiting failing open gives an attacker an unthrottled brute-force window at
> exactly the moment you're distracted, so I accept that logins are unavailable while Redis is.
> Either way I keep a per-process in-memory fallback — N times the limit is a bad limit and an
> infinitely better one than no limit. And the limiter's Redis client needs a socket timeout, because
> otherwise a hung Redis hangs every request and the thing protecting you becomes the outage.

**Q: Every tenant is within their rate limit and the service is still degraded. What's wrong?**

> Limits are per-tenant and capacity is global. Five hundred tenants at a hundred a minute is fifty
> thousand a minute, and you provisioned for ten thousand on the assumption that not everyone uses
> their full allowance — which holds until it doesn't. Three things help. A concurrency cap per
> tenant as well as a rate, because ten requests that take a minute each occupy more of the service
> than a thousand that take five milliseconds, and a rate limit doesn't bound occupancy. Fair queuing
> under contention, so a tenant that floods the queue waits behind everyone else's first request
> rather than ahead of it. And accounting by cost rather than by request — a report is a hundred
> units, a health check is one — because the resource you're protecting was never requests.

**Q: Where do you enforce the limit?**

> In more than one place, because the layers protect against different things. The edge — CDN or WAF
> — is the only one that protects you from a flood, because it rejects before the bytes reach your
> network; it's coarse, per-IP and per-path. The gateway handles per-API-key limits cheaply across
> all services. And the application is the only layer that knows the plan, the tenant, the user and
> the cost of the route, so it's where business rules live. The important thing to say out loud is
> that application-level limiting can't save you from a volumetric attack — by the time you count the
> request you've already paid for the handshake, TLS and a worker. It's a business rule, not a
> defence.

## 🎙️ Articulation drill

**Two minutes: "Design rate limiting for our API."**

Separate the three problems first — capacity, billing, fairness — because most answers conflate them
and the separation is the insight. Pick a key and justify it, rejecting IP for authenticated traffic
with the NAT and IPv6 reasons. Then the distributed mechanics: one atomic Lua script, sliding-window
counter as the default, token bucket if clients are bursty. Then the client contract: headers on
every response so clients can slow down before they're blocked, `Retry-After` so you don't design a
retry storm into your own API, and distinct codes for limited versus quota-exceeded. Close on the two
questions that show operational experience: **what happens when Redis is down — fail open for
capacity, closed for security** — and **what happens when every tenant is within their limit and you
are still out of capacity**, which is where concurrency caps and cost-based accounting come in.
