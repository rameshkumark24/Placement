# Part 1 — ⭐ Which is which

| ⭐⭐ Immutable | ⭐⭐ Mutable |
|---|---|
| `int`, `float`, `complex`, `bool` | `list` |
| ⭐ `str` | ⭐ `dict` |
| ⭐ `tuple` | `set` |
| `frozenset` | `bytearray` |
| `bytes` | ⭐ **your classes, by default** |
| `range`, `None` | `collections.deque`, `defaultdict`, `Counter` |

```python
s = "hello"
s[0] = "H"        # ⭐⭐ TypeError — strings are immutable
s = "H" + s[1:]   # ⭐ this REBINDS s to a NEW string. The old one is unchanged.
```

⚠️ ⭐⭐ **The performance consequence you will meet in a DSA round:** because strings are immutable,
`s += x` in a loop builds a **new string every iteration** — copying everything each time, so
**O(n²)**. ⭐ **Build a list and `"".join(parts)`: O(n).** *(CPython has an optimisation that
sometimes rescues `s += x` when the refcount is exactly 1, which makes it worse — it is fast until it
silently is not.)*

```
⭐⭐ IMMUTABILITY IS SHALLOW. This is the part people miss:
⭐   t = (1, [2, 3])
⭐   ⇒ ⭐ the TUPLE cannot change which objects it holds
⭐   ⇒ ⭐⭐ but the LIST inside it can be mutated freely:  t[1].append(4)  ⇒ (1, [2, 3, 4])
```

```python
# ⭐⭐ THE BEST TRICK QUESTION IN PYTHON, and it teaches something real:
t = (1, [2, 3])
t[1] += [4]
# ⭐⭐ raises TypeError ... AND THE LIST IS ALREADY [2, 3, 4].
# ⭐ WHY: `+=` on a list calls __iadd__, which MUTATES IN PLACE and returns self —
#    then the statement tries `t[1] = result`, which the TUPLE rejects.
# ⇒ ⭐⭐ the mutation succeeded; the re-binding failed. Both halves of `+=` are visible.
```

# Part 2 — ⭐⭐ The mutable default argument

```python
def append_to(item, target=[]):      # ⚠️⚠️ ⭐⭐ THE BUG
    target.append(item)
    return target

append_to(1)     # [1]
append_to(2)     # ⭐⭐ [1, 2]  ← not a fresh list
append_to(3)     # ⭐⭐ [1, 2, 3]
```

```
⭐⭐ WHY — and this is a Day 024 consequence, not a special rule:
⭐   `def` is a STATEMENT that EXECUTES when the module is imported.
⭐   ⇒ the default expression `[]` is evaluated ONCE, at that moment,
⭐     and the resulting list is stored on the function object:
⭐        append_to.__defaults__   ⇒ ⭐⭐ ([1, 2, 3],)
⭐   ⇒ ⭐⭐ every call that omits the argument BINDS THE PARAMETER TO THAT SAME LIST.
```

```python
# ⭐⭐ THE FIX — and it is always the same fix:
def append_to(item, target=None):
    if target is None:               # ⭐⭐ `is None`, not `if not target` (Day 029)
        target = []                  # ⭐ a NEW list, per call
    target.append(item)
    return target
```

⚠️ ⭐⭐ **This is not only about lists.** `def f(cache={})`, `def f(when=datetime.now())` — the
timestamp is frozen at import time and every log line claims the process started now — and
`def f(conn=make_connection())` opens a connection at import. **Any mutable or
evaluated-once default is the same bug.**

⭐ **Where it is deliberate:** `def f(x, _cache={})` as a memo is an old idiom. ⭐⭐ **Do not use it** —
`functools.lru_cache` says the same thing and says it out loud.

# Part 3 — ⭐⭐ Copying: none, shallow, deep

```python
import copy
original = [[1, 2], [3, 4]]

alias   = original                 # ⭐⭐ NO COPY — one object, two names (Day 024)
shallow = original[:]              # ⭐ or list(original), copy.copy(original)
deep    = copy.deepcopy(original)  # ⭐⭐ recursive
```

```
⭐⭐ WHAT EACH ONE ACTUALLY DOES:

⭐ ALIAS:    name ──▶ [ ptr, ptr ] ──▶ [1,2]  [3,4]
⭐           ⇒ mutating anything is visible everywhere

⭐⭐ SHALLOW: a NEW outer list, ⭐⭐ THE SAME INNER OBJECTS
⭐           shallow ──▶ [ ptr, ptr ] ──┐
⭐           original ─▶ [ ptr, ptr ] ──┴──▶ ⭐⭐ [1,2] [3,4]   (shared!)
⭐           ⇒ shallow.append(...)   ⇒ original unaffected  ⭐ ✓
⭐           ⇒ ⭐⭐ shallow[0].append(9) ⇒ original CHANGES TOO  ⚠️

⭐ DEEP:     everything duplicated, recursively ⇒ fully independent
⭐           ⇒ ⭐ costs time and memory, and ⭐⭐ handles cycles correctly (it memoises by id)
```

```python
shallow[0].append(99)
original            # ⭐⭐ [[1, 2, 99], [3, 4]]  ← the "copy" was not deep enough
```

⭐⭐ **The rule: a shallow copy is enough only when the contents are immutable.** A list of ints, a
list of strings, a list of tuples-of-ints — shallow is correct and cheap. **A list of lists, a dict
of dicts, a list of your own objects — shallow is a bug waiting for a mutation.**

⚠️ ⭐ **`deepcopy` is not free and not always right:** it is slow, it will happily copy a database
session or an open file handle if one is reachable from your object, and it can pull in half your
object graph. ⭐⭐ **Often the better answer is not to copy at all — build a new object with the
values you want, or use immutable data.**

```python
d = {"a": [1]}
d.copy()                        # ⭐ shallow
{**d}                           # ⭐ shallow
copy.deepcopy(d)                # ⭐ deep
# ⭐ Custom classes control this with __copy__ and __deepcopy__.
```

# Part 4 — ⭐ Designing with mutability

```
⭐⭐ THE THREE RULES THAT PREVENT MOST OF THESE BUGS:

⭐ 1. ⭐⭐ DON'T MUTATE WHAT YOU DON'T OWN.  Arguments belong to the caller.
⭐ 2. ⭐⭐ DON'T HAND OUT YOUR INTERNALS.    Return a copy, a tuple, or a view.
⭐ 3. ⭐⭐ PREFER IMMUTABLE FOR ANYTHING SHARED. Config, constants, cache keys,
⭐         anything crossing a thread boundary (Stage 1's concurrency block).
```

```python
from dataclasses import dataclass, replace

@dataclass(frozen=True)          # ⭐⭐ immutable AND hashable (Day 029)
class Point:
    x: int
    y: int

p = Point(1, 2)
p.x = 5                          # ⭐ FrozenInstanceError
q = replace(p, x=5)              # ⭐⭐ the functional-update idiom: a NEW object
```

⭐⭐ **`@dataclass(frozen=True)` is the single best default for a value object in modern Python** —
you get `__init__`, `__repr__`, `__eq__`, `__hash__` and immutability from one line, and immutable
objects can be shared freely, used as dict keys, and cached without fear.

| ⭐ Situation | ⭐ Reach for |
|---|---|
| A value object (money, a point, a config) | ⭐⭐ `@dataclass(frozen=True)` |
| Something you must accumulate into | `list` / `dict`, kept local |
| A default argument | ⭐⭐ `None`, then build inside |
| A constant collection | `tuple` / `frozenset` |
| Copying a nested structure | ⭐ `deepcopy` — or rebuild it explicitly |
| Exposing internal state | ⭐ a copy, or a read-only view |

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Mutable default argument** | ⭐⭐ Evaluated once at `def` time. Use `None`. |
| Thinking only lists are affected | ⭐ Dicts, `datetime.now()`, connections — same bug. |
| ⭐ `s += x` in a loop | ⭐⭐ O(n²). Build a list and `join`. |
| Assuming a tuple is deeply immutable | ⭐⭐ It is shallow — mutable contents stay mutable. |
| ⭐ Assuming `[:]` is a real copy | ⭐⭐ Shallow. Inner objects are shared. |
| `deepcopy` by reflex | ⭐ Slow, and it copies things you never wanted copied. |
| Mutating an argument | ⭐ Caller's object. Return a new one. |
| Returning internal collections | ⭐ Copy, tuple, or a view. |
| Mutable objects as dict keys | ⭐⭐ Day 029 — the hash changes and the entry is lost. |
| Not knowing `frozen=True` exists | ⭐ It is the best default for a value object. |

## Interview questions

**Q: What does this print, and why?**
```python
def f(x, acc=[]): acc.append(x); return acc
print(f(1)); print(f(2))
```
> `[1]` then `[1, 2]`. The default is evaluated once, when the `def` statement runs at import time,
> and the resulting list is stored on the function object in `__defaults__`. Every call that omits
> the argument binds the parameter to that same list. It's not a special rule — it follows from
> defaults being ordinary expressions evaluated at definition time. The fix is `acc=None` and
> building the list inside, checking with `is None` rather than truthiness, because an empty list the
> caller passed deliberately is falsy.

**Q: Shallow vs deep copy?**
> A shallow copy creates a new container holding the same references, so the top level is
> independent and everything nested is shared — appending to the copy is safe, mutating an element
> of the copy is not. A deep copy recursively duplicates everything and handles cycles by memoising
> on object identity. Shallow is correct and cheap when the contents are immutable; the moment
> there's a nested list, dict or custom object, shallow is a bug waiting for someone to mutate it.
> I'd also say deep copying isn't automatically the safe choice — it's slow and it will cheerfully
> copy a database session if one is reachable.

**Q: `t = (1, [2, 3]); t[1] += [4]` — what happens?**
> It raises a `TypeError` *and* the list ends up as `[2, 3, 4]`. `+=` on a list calls `__iadd__`,
> which mutates in place and returns self; then the statement performs the assignment
> `t[1] = result`, which the tuple refuses. So the mutation succeeded and the rebinding failed. It's
> a nice demonstration that `+=` is two operations, and that tuple immutability is about which
> objects it holds, not about those objects.

**Q: Why is string concatenation in a loop a problem?**
> Strings are immutable, so `s += x` allocates a new string and copies the whole accumulated content
> each iteration — quadratic overall. Building a list and joining once is linear. CPython has an
> in-place optimisation when the refcount happens to be 1, which makes it worse rather than better:
> the code is fast until a stray reference makes it silently quadratic.

**Q: How do you stop callers from mutating your object's state?**
> Don't hand out the internals. Return a copy or a tuple from an accessor, and design value objects
> as frozen dataclasses so the question doesn't arise. Immutable objects can be shared freely, used
> as dictionary keys, cached, and passed between threads without a lock — which is why frozen is a
> good default and mutability should be the deliberate choice.

## 🎙️ Articulation drill

Record two minutes: **"Explain the mutable default argument bug — and then explain why it isn't a
quirk."**

⭐ The behaviour first: the default list is created once, when the `def` runs at import, and stored
on the function object — so every call that omits the argument shares it. ⭐ Demonstrate with
`f.__defaults__`, which makes it undeniable rather than folklore.

⭐⭐ **Then the part that shows understanding rather than memorisation:** *"It isn't a special rule.
Defaults are ordinary expressions, and `def` is a statement that executes once — so the value is
bound once, exactly like any other name. If defaults were re-evaluated per call, Python would need a
rule that expressions in that one position behave differently from everywhere else. The bug is the
price of consistency, and knowing that is why I also spot `datetime.now()` and `make_connection()` as
defaults, which are the same bug wearing different clothes."*
