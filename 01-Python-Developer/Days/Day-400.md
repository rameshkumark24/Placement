# Part 1 — What gRPC actually buys, in order

```
⭐ ① ⭐ HTTP/2 — ⭐ multiplexed streams over one connection, ⭐ so
⭐    no head-of-line blocking at the HTTP layer and no
⭐    connection-per-request.
⭐ ② ⭐ BINARY FRAMING — ⭐ smaller and much cheaper to parse than
⭐    JSON. ⭐⭐ FOR PYTHON THIS MATTERS MORE THAN FOR MOST
⭐    LANGUAGES: JSON PARSING IS PURE CPU ON THE GIL (DAY 065),
⭐    ⭐ and protobuf's parser is C.
⭐ ③ ⭐ FOUR CALL SHAPES — unary, server-streaming,
⭐    client-streaming, bidirectional.
⭐ ④ ⭐ CODE GENERATION FROM A SHARED SCHEMA — ⭐⭐ THE CONTRACT
⭐    IS A FILE IN A REPOSITORY, NOT A WIKI PAGE THAT DRIFTED.
⭐ ⑤ ⭐⭐ ***DEADLINE PROPAGATION AS A FIRST-CLASS CONCEPT.***
⭐    ⭐⭐ THIS IS THE ARGUMENT PEOPLE UNDER-SELL AND IT IS THE
⭐    STRONGEST ONE. ⭐ REST has no equivalent: you pass a
⭐    timeout, the server never learns it, and it happily
⭐    computes a result for a caller that left. ⭐ In gRPC the
⭐    deadline travels with the call and ***keeps travelling***
⭐    (Part 4).

⭐⭐ ⇒ AND THE HONEST FRAMING FOR THE WHOLE DAY: ***IF YOU ARE
⭐   NOT USING THE SCHEMA AND THE DEADLINE, YOU BOUGHT A BUILD
⭐   STEP.*** ⭐ Those two are the value. ⭐ Speed is a bonus,
⭐   ⭐⭐ AND IT IS RARELY THE REASON THAT SURVIVES SCRUTINY.
```

# Part 2 — ⭐⭐ The wire format, and the rules that derive from it

```
⭐ EVERY FIELD ON THE WIRE IS:
⭐   ⭐⭐ ***(field_number << 3) | wire_type***, THEN THE VALUE.
⭐   ⭐ Wire types: 0 varint (int32/64, bool, enum), 1 fixed64,
⭐     2 length-delimited (string, bytes, message, packed
⭐     repeated), 5 fixed32.

⭐⭐ ⇒ ***THE DECODER NEVER SEES A NAME. NAMES EXIST ONLY IN YOUR
⭐   GENERATED CODE.*** ⭐ Now derive every rule:

⭐ ✅ ***RENAMING A FIELD IS FREE ON THE WIRE.*** ⭐ It breaks
⭐   generated code (a compile/attribute error) but ⭐⭐ NO DATA IS
⭐   MISREAD. ⭐ It is a source-compatibility change, not a wire
⭐   one.
⭐ ❌ ⭐⭐ ***CHANGING A FIELD NUMBER IS A BREAKING CHANGE
⭐   DISGUISED AS A RENAME.*** ⭐ Old data has the old number; the
⭐   new code looks for a different one. ⭐ The field silently
⭐   becomes empty. ⭐⭐ NO ERROR ANYWHERE.
⭐ ☠️ ⭐⭐ ***REUSING A RETIRED NUMBER IS THE CATASTROPHIC ONE.***
⭐   ⭐ Field 4 was `is_admin` (bool). ⭐ You deleted it. ⭐ A year
⭐   later someone adds `retry_count` as field 4.
⭐   ⭐⭐ OLD DATA WITH `is_admin=true` NOW DECODES AS
⭐   `retry_count=1`. ⭐ Both are varints, so ⭐⭐ THE PARSE
⭐   SUCCEEDS AND THE MEANING IS WRONG. ⭐ ⇒ `reserved 4;` and
⭐   `reserved "is_admin";` ⭐⭐ EVERY TIME YOU DELETE. NO
⭐   EXCEPTIONS.
⭐ ✅ ADDING A FIELD IS SAFE. ⭐⭐ AND IN proto3 UNKNOWN FIELDS ARE
⭐   ***PRESERVED*** ON A ROUND TRIP (SINCE 3.5), ⭐ so an old
⭐   proxy that reads and re-writes a message does not strip the
⭐   new field — ⭐⭐ WHICH IS THE PROPERTY THAT MAKES THE NINTH
⭐   FALLACY (DAY 398) SURVIVABLE.
⭐ ⚠️ CHANGING A TYPE is safe only ***within a wire type***:
⭐   ⭐ int32 ↔ int64 ↔ uint32 ↔ uint64 ↔ bool ↔ enum are all
⭐     varint, ⭐⭐ SO THEY PARSE — BUT VALUES CAN TRUNCATE OR
⭐     SIGN-FLIP. ⭐ int32 → int64 is safe; int64 → int32 is not.
⭐   ⭐ string ↔ bytes is safe (both length-delimited, ⭐⭐ IF THE
⭐     BYTES ARE VALID UTF-8).
⭐ ⚠️ ⭐⭐ SINGULAR ↔ `repeated` OF THE SAME TYPE IS ***WIRE***
⭐   COMPATIBLE: ⭐ a reader expecting singular takes the last
⭐   value; ⭐ a reader expecting repeated sees a one-element
⭐   list. ⭐⭐ DEFINED, AND ALMOST CERTAINLY NOT WHAT YOU MEANT.
⭐ ⭐⭐ ENUMS: proto3 ENUMS ARE ***OPEN***. ⭐ An unknown value is
⭐   preserved as its number rather than rejected. ⭐⭐ ⇒ ALWAYS
⭐   DEFINE `FOO_UNSPECIFIED = 0;` ⭐ so "unset" and "the first
⭐   real value" are distinguishable, ⭐⭐ AND SO A NEW ENUM VALUE
⭐   FROM A NEWER PEER DOES NOT LOOK LIKE YOUR DEFAULT.
```

```protobuf
message Order {
  string id            = 1;
  int64  total_cents   = 2;   // ⭐⭐ MONEY IS AN INTEGER (Day 358)
  reserved 4;                 // ⭐⭐ WAS is_admin. NEVER REUSE.
  reserved "is_admin";
  Status status        = 5;
  optional string note = 6;   // ⭐ proto3 optional ⇒ presence
}
enum Status {
  STATUS_UNSPECIFIED = 0;     // ⭐⭐ ALWAYS. ALWAYS.
  STATUS_PENDING     = 1;
}
```

# Part 3 — Python specifics that cost people an afternoon

```
⭐ ① ⭐⭐ ***THE GENERATED IMPORT PROBLEM.*** ⭐ `protoc` emits
⭐    `import order_pb2 as order__pb2` — ⭐ an ***absolute***
⭐    import — ⭐⭐ SO PUTTING THE GENERATED FILES IN A PACKAGE
⭐    BREAKS THEM WITH `ModuleNotFoundError`.
⭐    ⭐ Fixes, best first: ⭐⭐ GENERATE WITH MATCHING PATHS
⭐      (`python -m grpc_tools.protoc -I. --python_out=.
⭐      --grpc_python_out=. proto/order.proto` ⭐ and import as
⭐      `proto.order_pb2`), ⭐ or use `betterproto`, ⭐ or
⭐      post-process the imports (⭐⭐ WHAT EVERYONE DOES AND
⭐      NOBODY ENJOYS).
⭐ ② ⭐ ***`.pyi` STUBS*** — pass `--pyi_out` ⭐⭐ OR mypy SEES
⭐    `Any` FOR YOUR ENTIRE API AND YOU HAVE LOST THE MAIN
⭐    BENEFIT OF THE SCHEMA IN A TYPED CODEBASE (DAY 061).
⭐ ③ ⭐⭐ ***CONCURRENCY: `grpc.server(ThreadPoolExecutor(N))` IS
⭐    THREADS.*** ⭐ So a CPU-bound handler still serialises on
⭐    the GIL and N does not help (Day 065). ⭐⭐ FOR I/O-BOUND
⭐    HANDLERS USE `grpc.aio` — ⭐ and note you cannot mix: an
⭐    `async def` handler on a sync server does not run.
⭐ ④ ⭐ ***`grpcio` IS A LARGE C EXTENSION*** — ⭐⭐ SLOW TO BUILD
⭐    FROM SOURCE AND A REAL SIZE ADDITION TO YOUR IMAGE.
⭐    ⭐ Check the arm64 wheel exists before you migrate
⭐    (Day 385).
⭐ ⑤ ⭐⭐ ***PROTOBUF PYTHON OBJECTS ARE NOT DATACLASSES.***
⭐    ⭐ No `__init__` kwargs validation you would recognise,
⭐    ⭐ default values instead of `None` (so `if msg.name:` is
⭐    ambiguous between "empty" and "unset" ⭐⭐ UNLESS THE FIELD
⭐    IS `optional`), ⭐ and mutation semantics that surprise
⭐    people. ⭐⭐ CONVERT AT THE BOUNDARY INTO YOUR OWN
⭐    PYDANTIC/DATACLASS MODELS ⭐ and keep protobuf types out of
⭐    your domain layer (Day 399).
```

# Part 4 — ⭐⭐ Deadlines, which is the feature you came for

```python
# ⭐ CLIENT: a deadline, not a timeout.
resp = stub.GetOrder(req, timeout=2.0)

# ⭐⭐ SERVER: it ARRIVED. This is what REST cannot do.
def GetOrder(self, request, context):
    remaining = context.time_remaining()      # ⭐ seconds left
    if remaining < 0.2:                       # ⭐⭐ NOT WORTH
        context.abort(grpc.StatusCode.DEADLINE_EXCEEDED, "no time")

    # ⭐⭐ AND PASS A ***REDUCED*** DEADLINE DOWNSTREAM:
    inner = pricing_stub.Quote(q, timeout=remaining - 0.1)

    if not context.is_active():               # ⭐⭐ CLIENT LEFT
        return                                # ⭐ stop working
```

```
⭐⭐ ***THE DEADLINE BUDGET.*** ⭐ The deadline is absolute, not a
⭐   per-hop duration — ⭐⭐ SO IT SHRINKS AS IT TRAVELS, AND A
⭐   LEAF AT DEPTH FOUR GETS WHATEVER IS LEFT. ⭐ That is
⭐   Day 398's decreasing-budget rule ⭐⭐ IMPLEMENTED BY THE
⭐   PROTOCOL INSTEAD OF BY DISCIPLINE, ⭐ which is why it
⭐   actually holds.

⭐⭐ AND THE HABIT WORTH BUILDING: ***CHECK `is_active()` BEFORE
⭐   EXPENSIVE WORK.*** ⭐ Otherwise you compute a result nobody
⭐   is waiting for, ⭐⭐ WHICH IS DAY 367's 499 IN gRPC FORM AND
⭐   IS PURE WASTE DURING EXACTLY THE OVERLOAD WHERE YOU CAN
⭐   LEAST AFFORD IT (DAY 336).
```

# Part 5 — The error model, and which codes may be retried

```
⭐ STATUS CODES THAT MATTER, AND THE RETRY DECISION:
⭐   ⭐ `UNAVAILABLE` ......... ⭐⭐ RETRYABLE. ⭐ The canonical
⭐     "could not reach it" — ⭐ the request did not run.
⭐   ⭐ `RESOURCE_EXHAUSTED` .. ⭐ retryable ***with backoff***
⭐     (Day 336). ⭐⭐ RETRYING IMMEDIATELY IS THE CASCADE.
⭐   ⭐⭐ `DEADLINE_EXCEEDED` .. ***NOT AUTOMATICALLY RETRYABLE.***
⭐     ⭐⭐ THIS IS DAY 398's OUTCOME ③: ⭐ the server may have done
⭐     the work and been slow to answer. ⭐⭐ RETRY ONLY IF THE
⭐     CALL IS IDEMPOTENT, AND SEND A KEY.
⭐   ⭐ `INTERNAL`, `UNKNOWN` .. ⭐ same unknown problem. ⭐ Do not
⭐     blind-retry.
⭐   ⭐ `INVALID_ARGUMENT`, `NOT_FOUND`, `PERMISSION_DENIED`,
⭐     `FAILED_PRECONDITION` — ⭐⭐ NEVER RETRY. ⭐ The answer will
⭐     not change.
⭐   ⭐ `ABORTED` .............. ⭐ a concurrency conflict —
⭐     ⭐⭐ RETRY AT A HIGHER LEVEL, AFTER RE-READING.

⭐ ⭐ Rich errors: `google.rpc.Status` with `details` carrying a
⭐   typed message ⭐⭐ — SO "WHICH FIELD WAS INVALID" IS
⭐   STRUCTURED, NOT A STRING YOUR CLIENT REGEXES.
⭐ ⭐ Retries live in the ***service config***, not in your code:
⭐   ⭐ `retryableStatusCodes`, `maxAttempts`, backoff.
⭐   ⭐⭐ AND SET A RETRY ***BUDGET*** (DAY 336) — PER-CALL RETRY
⭐   LIMITS DO NOT BOUND FLEET-WIDE AMPLIFICATION.
```

# Part 6 — Load balancing gRPC, which breaks the naive setup

```
⭐⭐ THE PROBLEM IS DAY 389's, SHARPENED: ⭐ gRPC opens ***one
⭐   long-lived HTTP/2 connection*** and multiplexes every call
⭐   onto it.
⭐   ⭐⭐ ⇒ AN L4 BALANCER (NLB) BALANCES ***CONNECTIONS***, SO ONE
⭐   CLIENT PINS TO ONE SERVER FOREVER. ⭐ You scale out and the
⭐   new pods receive nothing, ⭐⭐ WHILE THE ORIGINAL POD IS AT
⭐   100% AND THE FLEET GRAPH LOOKS FINE.

⭐ THREE FIXES:
⭐   ⭐ ① ***AN L7 BALANCER*** (ALB, Envoy) — ⭐ understands
⭐      HTTP/2 and balances ***streams***. ⭐ Simplest.
⭐   ⭐ ② ***CLIENT-SIDE BALANCING*** — ⭐ `dns:///service:50051`
⭐      with `round_robin`, ⭐⭐ SO THE CLIENT HOLDS A SUBCHANNEL
⭐      PER BACKEND. ⭐ Cheapest at scale, ⭐⭐ AND IT RE-RESOLVES,
⭐      WHICH IS THE ANSWER TO STAGE 11's "POOLS OUTLIVE DNS"
⭐      SHAPE.
⭐   ⭐ ③ A service mesh (Day 342) — ⭐ correct, and a lot of
⭐      machinery for the problem.
⭐ ⭐ Either way set keepalives (`keepalive_time_ms`), ⭐⭐ OR AN
⭐   IDLE CONNECTION IS SILENTLY REAPED BY A NAT OR AN ALB AND
⭐   YOUR NEXT CALL FAILS ONCE, PERIODICALLY, FOREVER.
```

⭐   gRPC.*** ⭐ Use `.proto` as the schema for your ***Kafka

⭐   HTTP/JSON at the edge. ⭐⭐ YOU GET THE EVOLUTION RULES AND

# 💬 Interview

**1. ⭐⭐ "What are the protobuf schema evolution rules?"**
> ⭐ I'd derive them rather than list them, because they all come from one fact: ⭐⭐ **the field number
> is the schema and the name is documentation — on the wire, each field is the number and a wire type,
> so the decoder never sees a name.** ⭐ From that: renaming is free on the wire and only breaks
> generated code; ⭐⭐ **changing a number is a breaking change disguised as a rename, and the field
> silently becomes empty with no error**; adding is safe, and proto3 preserves unknown fields on a
> round trip so an old proxy doesn't strip a new field. ⭐ Type changes are safe only within a wire
> type, so int32 to int64 is fine and the reverse truncates. ⭐⭐ **And the catastrophic one is reusing a
> retired number: field 4 was a bool `is_admin`, someone later adds an int `retry_count` as 4, and old
> data decodes as `retry_count=1` — both varints, so the parse succeeds and the meaning is wrong.**
> ⭐ Hence `reserved`, every time, no exceptions.

**2. ⭐⭐ "Why gRPC over REST?"**
> ⭐ Two reasons that survive scrutiny and one bonus. ⭐⭐ **The schema is a file in a repository rather
> than a wiki page that drifted, and the deadline is a first-class concept that propagates.** ⭐ REST
> has no equivalent of the second: you set a timeout, the server never learns it, and it happily
> computes a result for a caller that already left. ⭐⭐ **In gRPC the server can read `time_remaining()`,
> refuse work it can't finish, and pass a reduced deadline downstream — which makes the
> decreasing-timeout-budget rule enforced by the protocol instead of by discipline.** ⭐ Binary framing
> is the bonus, and it matters more in Python than most languages because JSON parsing is pure CPU on
> the GIL. ⭐⭐ **But I'd be honest: if you're not using the schema and the deadline, you bought a build
> step.**

**3. "Which gRPC errors do you retry?"**
> ⭐ `UNAVAILABLE` freely — the request didn't run. ⭐ `RESOURCE_EXHAUSTED` with backoff, because
> retrying immediately is the cascade. ⭐ Never `INVALID_ARGUMENT`, `NOT_FOUND` or `PERMISSION_DENIED`,
> since the answer won't change. ⭐⭐ **And the interesting one is `DEADLINE_EXCEEDED`, which is not
> automatically retryable — the server may have done the work and been slow to answer, so it's the
> unknown outcome. Retry it only if the call is idempotent, and send a key.** ⭐ I'd put the retry
> policy in the service config rather than in code, ⭐⭐ **with a retry budget, because per-call limits
> don't bound fleet-wide amplification.**

**4. ⭐⭐ "You scaled your gRPC service to ten pods and one is at 100% CPU. Why?"**
> ⭐ Connection pinning. ⭐⭐ **gRPC opens one long-lived HTTP/2 connection and multiplexes every call
> onto it, so an L4 balancer — which balances connections — pins each client to one server forever.
> The new pods get nothing while the original is saturated, and the fleet-average graph looks fine.**
> ⭐ Three fixes: an L7 balancer that understands HTTP/2 and balances streams; client-side balancing
> with `dns:///` and a round-robin policy, ⭐⭐ **which also re-resolves and so answers the
> pools-outlive-DNS problem**; or a mesh. ⭐ And keepalives either way, or an idle connection gets
> silently reaped by a NAT and the next call fails once, periodically, forever.

**5. "Anything specific about gRPC in Python?"**
> ⭐ Three things. ⭐⭐ **`grpc.server(ThreadPoolExecutor(N))` is threads, so a CPU-bound handler still
> serialises on the GIL and raising N doesn't help — `grpc.aio` is the answer for I/O-bound, and you
> can't mix the two.** ⭐ Generated files use absolute imports, so putting them in a package breaks with
> `ModuleNotFoundError` unless you generate with matching paths. ⭐⭐ **And I'd pass `--pyi_out`, because
> otherwise mypy sees `Any` for the entire API and you've lost the main benefit of having a schema in
> a typed codebase.** ⭐ I also convert protobuf messages into my own models at the boundary, ⭐⭐ **since
> protobuf objects have default values rather than `None`, so `if msg.name:` can't distinguish "empty"
> from "unset" unless the field is `optional`.**

**6. "When wouldn't you use gRPC?"**
> ⭐ Browser clients, where you need grpc-web plus a proxy — real infrastructure. ⭐ Public APIs, where
> curl-ability and the network tab are features. ⭐ And small teams, where the codegen step, the proto
> repository and the versioning discipline are an ongoing cost. ⭐⭐ **The middle path I'd raise is
> protobuf *without* gRPC: use `.proto` as the schema for your Kafka messages and events over plain
> JSON at the edge — you get the evolution rules and the registry, which is the part that prevents
> incompatible-version breakage, without committing to the transport.**
