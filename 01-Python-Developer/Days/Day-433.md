**P-433** · 🎯 **Hybrid search and reranking** — ⭐⭐ retrieve wide, rerank narrow

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: dense retrieval and keyword retrieval fail on opposite inputs, and a

# Part 1 — Where dense vectors lose, exactly

```
⭐ DAY 419 SAID SIMILARITY ≠ RELEVANCE. ⭐ Here are the four
⭐   query types where dense retrieval ***reliably*** loses to
⭐   1970s keyword search:

⭐ ① ***IDENTIFIERS.*** ⭐ "ticket PROJ-4821", "error E_1043",
⭐   "part number 7X-99B". ⭐⭐ AN EMBEDDING ENCODES THAT AS
⭐   "SOME KIND OF CODE" — ⭐ PROJ-4821 and PROJ-4822 are nearly
⭐   identical vectors, ⭐⭐ AND THEY ARE DIFFERENT TICKETS.

⭐ ② ***RARE AND NEW TERMS.*** ⭐ Your internal service names,
⭐   a person's surname, a product launched after the embedding
⭐   model was trained. ⭐⭐ THE MODEL HAS NO USEFUL
⭐   REPRESENTATION FOR A TOKEN IT NEVER SAW IN CONTEXT.

⭐ ③ ***EXACT-PHRASE INTENT.*** ⭐ The user is quoting. ⭐ They
⭐   want the document containing ***those words***, not the one
⭐   about the same topic.

⭐ ④ ***ACRONYMS AND JARGON COLLISIONS.*** ⭐ "PIP" is a Python
⭐   installer, a performance improvement plan, and a payment
⭐   protocol. ⭐⭐ THE VECTOR PICKS ONE MEANING — usually the
⭐   internet's, not yours.

⭐⭐ AND WHERE KEYWORD SEARCH LOSES, WHICH IS WHY YOU KEEP BOTH:
⭐   ⭐ "how do I get my money back" vs a document that says
⭐     ***"refund policy"*** — ⭐⭐ ZERO TERM OVERLAP, PERFECT
⭐     SEMANTIC MATCH.
⭐   ⭐ Paraphrase, synonyms, other languages, misspellings.

⭐⭐ ⇒ THESE ARE ***COMPLEMENTARY FAILURE MODES***, NOT COMPETING
⭐   ALGORITHMS. ⭐ That is the entire argument for hybrid, and it
⭐   is why hybrid gains do not shrink as embedding models get
⭐   better — ⭐⭐ NO AMOUNT OF SEMANTIC TRAINING MAKES A VECTOR
⭐   DISTINGUISH TICKET 4821 FROM 4822.
```

# Part 2 — BM25 in one honest paragraph

```
⭐ ***BM25*** ranks a document for a query by summing, over the
⭐   query terms it contains:
⭐   ⭐ ① how ***often*** the term appears here (with saturation
⭐     — the 20th occurrence adds almost nothing),
⭐   ⭐ ② how ***rare*** the term is corpus-wide (IDF — matching
⭐     "the" is worthless, matching "PROJ-4821" is decisive),
⭐   ⭐ ③ normalised by document ***length*** so long documents
⭐     do not win by accident.

⭐⭐ THAT IS IT. ⭐ No model, no GPU, no embedding, no reindex
⭐   when you change models, sub-millisecond, and ⭐⭐ IT BEATS
⭐   DENSE RETRIEVAL OUTRIGHT ON EVERY QUERY IN PART 1.

⭐ Postgres gives you a close cousin free: ⭐ `tsvector` + `gin`
⭐   + `ts_rank_cd`. ⭐⭐ NOT TRUE BM25 (no length normalisation
⭐   by default, weaker IDF) BUT GOOD ENOUGH THAT ADDING IT IS
⭐   USUALLY WORTH 5–15 POINTS OF RECALL FOR ONE INDEX.
⭐   ⭐ If you need real BM25 in Postgres: the `pg_search`/
⭐     `ParadeDB` extension. ⭐ Elsewhere: OpenSearch, Vespa.
```

# Part 3 — ⭐⭐ Reciprocal Rank Fusion, and why you must not add scores

```
⭐ YOU HAVE TWO RANKED LISTS. ⭐ THE OBVIOUS MOVE IS
⭐   `0.5 × cosine + 0.5 × bm25`. ⭐⭐ IT IS WRONG, FOR A REASON
⭐   WORTH BEING ABLE TO STATE:

⭐   ⭐ cosine similarity lives in a narrow band — ⭐ real corpora
⭐     cluster between 0.3 and 0.9 with tiny variance;
⭐   ⭐ BM25 is ***unbounded*** and corpus-dependent — ⭐ 2.1 on
⭐     one query, 47 on another;
⭐   ⭐⭐ THE TWO ARE NOT ON A COMMON SCALE AND THERE IS NO FIXED
⭐     NORMALISATION THAT MAKES THEM COMPARABLE, ⭐ because the
⭐     BM25 distribution shifts ***per query***.
⭐   ⭐ Min-max normalising per query is the usual patch, and it
⭐     ⭐⭐ MAKES A DOCUMENT'S SCORE DEPEND ON WHAT ***ELSE*** WAS
⭐     RETRIEVED — ⭐ so adding an unrelated document changes the
⭐     ranking of the top result.

⭐ ***RRF THROWS THE SCORES AWAY AND USES ONLY RANK:***
⭐
⭐          score(d) = Σ   1 / (k + rank_i(d)) ,  k ≈ 60
⭐                   lists i
⭐
⭐   ⭐ rank 1 → 1/61 = 0.0164 ⭐ rank 2 → 1/62 = 0.0161
⭐   ⭐ rank 10 → 1/70 = 0.0143 ⭐ rank 50 → 1/110 = 0.0091
⭐   ⭐⭐ THE k DAMPENS THE TOP: BEING #1 IN ONE LIST BEATS BEING
⭐     #3 IN ONE LIST, BUT BEING #3 IN ***BOTH*** BEATS BEING #1
⭐     IN ONE. ⭐ That is exactly the behaviour you want —
⭐     ⭐⭐ AGREEMENT ACROSS INDEPENDENT METHODS IS EVIDENCE.
⭐   ⭐ Scale-free, tuning-free, and it extends to n lists —
⭐     add a title index, a recency list, a graph walk; ⭐⭐ RRF
⭐     DOES NOT CARE.
```

```sql
-- ⭐⭐ HYBRID RETRIEVAL IN ONE POSTGRES STATEMENT.
-- Two CTEs, two indexes, one fusion. No extra service.
WITH dense AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
    FROM chunks_v4
   WHERE tenant_id = $3                      -- ⭐⭐ DAY 434
   ORDER BY embedding <=> $1
   LIMIT 50
),
sparse AS (
  SELECT id, ROW_NUMBER() OVER (
           ORDER BY ts_rank_cd(tsv, websearch_to_tsquery('english', $2)) DESC
         ) AS rank
    FROM chunks_v4
   WHERE tenant_id = $3
     AND tsv @@ websearch_to_tsquery('english', $2)
   ORDER BY ts_rank_cd(tsv, websearch_to_tsquery('english', $2)) DESC
   LIMIT 50
)
SELECT c.id, c.doc_id, c.heading_path, c.body,
       COALESCE(1.0 / (60 + d.rank), 0.0)
     + COALESCE(1.0 / (60 + s.rank), 0.0) AS rrf
  FROM chunks_v4 c
  LEFT JOIN dense  d ON d.id = c.id
  LEFT JOIN sparse s ON s.id = c.id
 WHERE d.id IS NOT NULL OR s.id IS NOT NULL
 ORDER BY rrf DESC
 LIMIT 50;                                    -- ⭐ wide. rerank next.
```

⭐ `websearch_to_tsquery` is the one to use — it accepts `"quoted phrases"`, `or`, and `-negation`
from real users without throwing on punctuation the way `to_tsquery` does.

# Part 4 — ⭐⭐ Reranking: the biggest single quality win

```
⭐ ***THE ARCHITECTURAL DIFFERENCE, WHICH IS THE WHOLE POINT.***

⭐ ***BI-ENCODER*** (your embedding model):
⭐   ⭐ encode(query) → vector ⭐ encode(passage) → vector
⭐   ⭐⭐ THE TWO NEVER MEET. ⭐ The passage was encoded months
⭐     ago with no idea what would be asked. ⭐ Comparison is a
⭐     dot product between two independent summaries.
⭐   ⭐ ⇒ precomputable, so it scales to 100M documents.

⭐ ***CROSS-ENCODER*** (the reranker):
⭐   ⭐ score(query ‖ passage) → one number, ⭐⭐ WITH FULL
⭐     ATTENTION ***BETWEEN*** THE QUERY AND THE PASSAGE TOKENS.
⭐   ⭐ It can see that "30 days" in the passage answers "how
⭐     long" in the query. ⭐⭐ A BI-ENCODER STRUCTURALLY CANNOT —
⭐     it compressed the passage before the question existed.
⭐   ⭐ ⇒ nothing is precomputable: ⭐⭐ N PASSAGES = N FORWARD
⭐     PASSES, ***PER QUERY***. ⭐ Over a corpus: impossible.
⭐     Over 50 candidates: ~100–300ms. ⭐ Affordable.

⭐⭐ ⇒ HENCE THE SHAPE OF EVERY SERIOUS PIPELINE:
⭐   ***RETRIEVE 50 CHEAPLY (RECALL), RERANK TO 8 EXPENSIVELY
⭐   (PRECISION), GENERATE.***
```

```
⭐ ***THE MEASURED LADDER*** — typical shape on a real corpus.
⭐   Your numbers will differ; ⭐⭐ THE ***ORDER*** RARELY DOES.

⭐  ┌────────────────────────────┬──────────┬────────────────┐
⭐  │ CONFIGURATION              │ RECALL@5 │ ADDED LATENCY  │
⭐  ├────────────────────────────┼──────────┼────────────────┤
⭐  │ dense only                 │  ~0.62   │ —              │
⭐  │ + contextual prefix (D430) │  ~0.75   │ ⭐⭐ ZERO        │
⭐  │ + hybrid RRF               │  ~0.82   │ ~15ms          │
⭐  │ + cross-encoder rerank     │  ~0.91   │ ~150ms         │
⭐  └────────────────────────────┴──────────┴────────────────┘

⭐⭐ NOTE WHICH ROW IS FREE. ⭐ The contextual prefix is a string
⭐   concatenation at ingest and it moves the number more than
⭐   the thing you would have paid for. ⭐⭐ DO THE FREE ROWS
⭐   FIRST. ⭐ That ordering ***is*** the seniority.
```

```python
from sentence_transformers import CrossEncoder

# ⭐ 300MB, CPU-viable at ~50 pairs in 150–300ms.
# ⭐⭐ LOAD IT ONCE AT PROCESS START — not per request.
_reranker = CrossEncoder("BAAI/bge-reranker-base", max_length=512)

def rerank(query: str, hits: list[Hit], *, top_n: int = 8) -> list[Hit]:
    if not hits:
        return []
    pairs = [(query, f"{h.heading_path}\n{h.body}") for h in hits]
    scores = _reranker.predict(pairs)          # ⭐ len(hits) forward passes
    ranked = sorted(zip(hits, scores), key=lambda t: -t[1])

    # ⭐⭐ THE PART PEOPLE OMIT: AN ABSOLUTE THRESHOLD.
    # ⭐ Reranking always returns SOMETHING — it is a sort, not a
    # judgement. ⭐⭐ IF THE BEST SCORE IS BELOW THE FLOOR, THE
    # CORPUS DOES NOT CONTAIN THE ANSWER, AND SENDING GARBAGE TO
    # THE MODEL IS HOW YOU GET A CONFIDENT WRONG ANSWER (D 422).
    kept = [h for h, s in ranked[:top_n] if s >= RERANK_FLOOR]
    return kept
```

```
⭐ ***YOUR THREE OPTIONS, HONESTLY:***
⭐   ⭐ `bge-reranker-base` / `-large` — ⭐ open, local, strong.
⭐     ⭐⭐ THE DEFAULT.
⭐   ⭐ Cohere Rerank — ⭐ excellent, an API call, ⭐⭐ SO IT IS A
⭐     NETWORK HOP AND A PER-QUERY COST ON THE CRITICAL PATH.
⭐   ⭐ ***LLM-as-reranker*** — ⭐ ask a small model to score
⭐     relevance. ⭐⭐ FLEXIBLE, 10–50× MORE EXPENSIVE AND SLOWER
⭐     THAN A PURPOSE-BUILT CROSS-ENCODER. ⭐ Only when you need
⭐     a criterion no reranker was trained on.
```

# Part 5 — Diversity, and the near-duplicate that eats your top-k

```
⭐ ***THE FAILURE:*** ⭐ your top 8 are eight chunks of the same
⭐   document saying the same thing, ⭐ because that document is
⭐   genuinely the most similar and overlap made near-copies.
⭐   ⭐⭐ YOU SPENT YOUR ENTIRE CONTEXT BUDGET ON ONE SOURCE, AND
⭐     A QUESTION WITH TWO SIDES ONLY HEARD ONE.

⭐ ***THREE FIXES, CHEAPEST FIRST:***
⭐   ⭐ ① ***CAP PER DOCUMENT.*** ⭐ At most 2–3 chunks from any
⭐     one `doc_id`. ⭐⭐ FOUR LINES OF PYTHON, SOLVES 80% OF IT.
⭐   ⭐ ② ***MMR*** (maximal marginal relevance) — greedily pick
⭐     the next chunk maximising `λ·relevance − (1−λ)·max
⭐     similarity to already-picked`. ⭐ λ ≈ 0.7.
⭐   ⭐ ③ ***DEDUPE BY CONTENT HASH*** — the same paragraph in
⭐     three documents. ⭐ Keep the newest (`updated_at`).

⭐⭐ AND THE ORDERING OF WHAT SURVIVES: ⭐ lost-in-the-middle
⭐   (Day 415) is real, ⭐⭐ SO PUT THE BEST CHUNK ***FIRST*** AND
⭐   THE SECOND-BEST ***LAST***, ⭐ and never present chunks in
⭐   database order. ⭐ Number them, so the model can cite by
⭐   index and you can verify the citation (Day 424).
```

# Part 6 — The retrieval function, assembled

```python
async def retrieve(
    question: str,
    *,
    tenant_id: str,                    # ⭐⭐ REQUIRED. DAY 434.
    k_wide: int = 50,
    k_final: int = 8,
    max_per_doc: int = 2,
    token_budget: int = 4_000,
) -> list[Hit]:
    qvec = await embed_query(question)                     # ⭐ Day 431

    hits = await store.hybrid_search(                      # ⭐ Part 3 SQL
        vector=qvec, text=question, tenant_id=tenant_id, k=k_wide,
    )
    if not hits:
        return []                                          # ⭐⭐ ABSTAIN. D 422.

    hits = rerank(question, hits, top_n=k_wide)            # ⭐ Part 4

    out, per_doc, spent = [], {}, 0
    for h in hits:                                         # ⭐ Part 5
        if per_doc.get(h.doc_id, 0) >= max_per_doc:
            continue
        if spent + h.token_count > token_budget:           # ⭐⭐ BUDGET IS
            continue                                       # ⭐ A CONSTRAINT,
        out.append(h)                                      # ⭐ NOT A HOPE
        per_doc[h.doc_id] = per_doc.get(h.doc_id, 0) + 1
        spent += h.token_count
        if len(out) >= k_final:
            break

    # ⭐⭐ LOST-IN-THE-MIDDLE: best first, second-best last.
    if len(out) > 2:
        out = [out[0]] + out[2:] + [out[1]]
    return out
```

```
⭐⭐ FIVE THINGS THAT FUNCTION DOES THAT A TUTORIAL'S DOES NOT:
⭐   ⭐ ① `tenant_id` cannot be omitted;
⭐   ⭐ ② it can return ***nothing***, and that is a valid,
⭐     designed outcome rather than an error;
⭐   ⭐ ③ the token budget is enforced, not assumed — ⭐⭐ SO A
⭐     SINGLE 3,000-TOKEN CHUNK CANNOT BLOW YOUR CONTEXT;
⭐   ⭐ ④ one document cannot own the whole context;
⭐   ⭐ ⑤ ordering is deliberate and adversarial to the known
⭐     positional weakness of the model.
```

# 💬 Interview

**1. "Why hybrid search? Aren't embeddings strictly better?"**

⭐ No — they fail on a specific, predictable class of query, and keyword search is *perfect* on exactly
that class. ⭐⭐ Identifiers are the clearest case: PROJ-4821 and PROJ-4822 have nearly identical
embeddings and are different tickets, so no amount of semantic training fixes that; the vector encodes
"some kind of code". ⭐ Same for rare internal terms the model never saw, exact-phrase intent when the
user is quoting, and acronym collisions where the vector picks the internet's meaning of "PIP" rather
than ours. ⭐⭐ And dense wins where keyword can't: "how do I get my money back" against a document
titled "refund policy" has zero term overlap. ⭐ They're complementary failure modes, which is why the
gain from hybrid hasn't shrunk as embedding models improved.

**2. "How do you combine the two result lists?"**

⭐ Reciprocal rank fusion — sum of 1/(60 + rank) across lists. ⭐⭐ The important part is *why not*
weighted score addition: cosine similarity sits in a narrow band around 0.3 to 0.9 while BM25 is
unbounded and its distribution shifts **per query**, so there's no fixed normalisation that makes them
comparable. ⭐ Min-max normalising per query is the usual patch and it introduces a worse bug — a
document's score starts depending on what else was retrieved, so adding an irrelevant result can reorder
your top hit. ⭐⭐ RRF throws the scores away and keeps only rank, so it's scale-free and tuning-free,
and the constant damps the top so that ranking third in *both* lists beats ranking first in one — which
is what you want, because agreement between independent methods is evidence.

**3. "Explain reranking and why it isn't just a better embedding model."**

⭐ It's an architectural difference, not a quality difference. ⭐⭐ A bi-encoder embeds the query and the
passage **independently** — the passage was compressed into a vector months before your question
existed, so the comparison is between two summaries that never met. ⭐ A cross-encoder takes the query
and the passage together in one forward pass with full attention between them, so it can see that "30
days" in the passage answers "how long" in the query. ⭐⭐ The cost is that nothing is precomputable: N
passages means N forward passes per query, so you can't run it over a corpus — but over fifty
candidates it's about 150 milliseconds. ⭐ That asymmetry is the entire reason the pipeline is shaped
retrieve-wide-then-rerank-narrow.

**4. "What did reranking actually buy you, and what did you do before it?"**

⭐ On our corpus, recall@5 went from about 0.82 to 0.91 for roughly 150 milliseconds. ⭐⭐ But the more
useful answer is what I did *first*: the contextual prefix at ingest moved us from 0.62 to 0.75 for
zero added latency and zero added cost, and hybrid added another 0.07 for fifteen milliseconds. ⭐ So
two-thirds of the total gain came from the free rows. ⭐⭐ Doing the paid optimisation before the free
one is the most common ordering mistake in this work — people buy a reranker before they've concatenated
a heading onto a chunk.

**5. "What's the danger with a reranker?"**

⭐⭐ It's a sort, not a judgement — it always returns something, even when the corpus contains nothing
relevant. ⭐ So without an absolute score floor you take the least-bad of fifty irrelevant chunks,
hand them to the model as authoritative context, and get a confident wrong answer with a citation
attached. ⭐⭐ I set a threshold and let the retriever return an empty list, because "we don't have
that" is a valid designed outcome — it's the abstention path, and it only works if retrieval can
actually produce nothing.

**6. "Your top 8 are eight chunks of the same document. Is that a bug?"**

⭐ Technically it's correct behaviour and practically it's a bug, because I've spent the whole context
budget on one source and a question with two sides only heard one. ⭐⭐ The cheap fix is a cap of two or
three chunks per `doc_id`, which is four lines and handles most of it. ⭐ Beyond that, MMR — greedily
pick the next chunk that maximises relevance minus similarity to what's already picked — and dedupe by
content hash for boilerplate that appears in several documents. ⭐⭐ And once I've chosen the survivors I
order them deliberately: best first, second-best last, because of lost-in-the-middle. ⭐ Never database
order.

**7. "What's on the critical path latency-wise?"**

⭐ Query embedding, roughly 5 to 60 milliseconds depending on local versus API; hybrid search in
Postgres, around 15; reranking fifty candidates, 150 to 300. ⭐⭐ So retrieval is 200 to 400
milliseconds against a generation that's usually two to five seconds — which is worth saying, because
people optimise retrieval latency while the model dominates. ⭐ The one I'd actually attack is the
embedding hop if it's an API, since that's on **every** query and it's a dependency that can be down
while the database is fine.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "how did you improve retrieval quality?"**

Start with measurement, because it licenses everything after it. **I had thirty questions with
known-correct documents and I scored recall@5 only — no generation involved, so nothing could confound
the signal. Dense-only was 0.62. That number is the point of the story.**

Then the free win. **The first thing I did cost nothing: prepending the document title and heading path
to each chunk before embedding. 0.62 to 0.75, no added latency, no added inference. Doing the paid
optimisation before the free one is the most common ordering mistake in this work.**

Then hybrid, with the mechanism. **Dense retrieval fails on a predictable class of query — identifiers,
where PROJ-4821 and PROJ-4822 have nearly identical vectors and are different tickets; rare internal
terms the model never saw; exact phrases when the user is quoting. Keyword search is perfect on exactly
those, and hopeless on "how do I get my money back" against a page titled "refund policy". Complementary
failure modes, so we run both. We fuse with reciprocal rank fusion rather than adding scores, because
cosine sits in a narrow band and BM25 is unbounded with a distribution that shifts per query — there's no
normalisation that makes them comparable, and the min-max patch makes a document's score depend on what
else was retrieved. RRF keeps only rank, so ranking third in both lists beats first in one, which is
right: agreement between independent methods is evidence. That took us to 0.82 for fifteen
milliseconds.**

Then reranking, framed architecturally. **The last step is a cross-encoder. The difference isn't
quality, it's when the query and the passage meet: an embedding model compressed the passage months
before the question existed, so it's comparing two independent summaries. A cross-encoder reads both
together with full attention, so it can see that "30 days" answers "how long". The price is that nothing
precomputes — N passages is N forward passes per query — so you can't run it over a corpus, but over
fifty candidates it's 150 milliseconds. 0.82 to 0.91.**

Close on the guardrail. **A reranker is a sort, not a judgement — it always returns something. So
there's an absolute score floor, and if nothing clears it the retriever returns an empty list and the
system says it doesn't know. Without that you hand the least-bad of fifty irrelevant chunks to the model
as authoritative context, and get a confident wrong answer with a citation on it.**
