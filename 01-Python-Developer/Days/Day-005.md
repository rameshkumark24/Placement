# Part 1 — ⭐ The client

```python
# client.py — speak HTTP by hand. No requests, no httpx.
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect(("example.com", 80))                       # ⭐⭐ THE CLIENT INITIATES. That is the definition.

request = (
    b"GET / HTTP/1.1\r\n"
    b"Host: example.com\r\n"                         # ⭐⭐ mandatory in HTTP/1.1 — see below
    b"Connection: close\r\n"
    b"\r\n"                                          # ⭐ the blank line ends the headers
)
s.sendall(request)

chunks = []
while True:
    data = s.recv(4096)                              # ⭐⭐ recv returns WHATEVER HAS ARRIVED, not the whole thing
    if not data:                                     # ⭐ empty bytes = the other side closed
        break
    chunks.append(data)
s.close()

print(b"".join(chunks).decode(errors="replace"))
```

| ⭐ What this teaches | |
|---|---|
| ⭐⭐ **`connect()` is what makes you the client** | ⭐ the server called `accept()`; you called `connect()` |
| ⭐⭐ **`recv()` is not "read the response"** | ⭐⭐ **it returns whatever bytes have arrived so far** — you must loop |
| ⭐⭐ **`Host:` is mandatory** | ⭐⭐ one IP hosts many sites; **this header is how the server knows which one** — it is why virtual hosting exists |
| ⭐ Empty `recv` means closed | ⭐ that is how you detect the end when there is no `Content-Length` |

⚠️ ⭐⭐ **The `recv` loop is the single most important line of today.** TCP is a *byte stream*, not a
message protocol — it does not preserve your message boundaries. **One `sendall` can arrive as three
`recv`s, and three `sendall`s can arrive as one.** Day 008 explains why; every protocol you ever use
has framing (a length prefix, a delimiter, or a terminator) precisely because of this.

# Part 2 — ⭐ Request/response as a model

| | |
|---|---|
| ⭐ **The client asks; the server answers.** | ⭐ one request, one response, initiated by the client |
| ⭐⭐ **The server cannot speak first.** | ⭐⭐ this is the limitation that everything else works around |

## ⭐⭐ What that limitation forces

| Need | Workaround | ⭐ Cost |
|---|---|---|
| ⭐ "Tell me when something happens" | ⭐ **polling** — ask every N seconds | ⭐⭐ mostly wasted requests; latency = the interval |
| ⭐ Faster notification | ⭐ **long polling** — the server holds the request open | ⭐ a held connection per client |
| ⭐ Server → client stream | ⭐ **SSE** | ⭐ one-directional |
| ⭐⭐ **Both directions, freely** | ⭐⭐ **WebSockets** (Day 017) | ⭐ a persistent connection to manage |

⭐ **Do the arithmetic once and it stays with you:** 10,000 users polling every 5 seconds is **2,000
requests per second**, and if nothing has changed, essentially all of them are waste. That number is
why Day 017 exists.

## ⭐ Statelessness — the property that made the web scale

```
⭐⭐ HTTP is STATELESS: every request must carry everything needed to serve it.
⭐   ⇒ ⭐ the server does not have to remember you between requests
⭐   ⇒ ⭐⭐ therefore ANY server in the fleet can answer ANY request
⭐   ⇒ ⭐⭐ therefore you can put ten servers behind a load balancer and add an eleventh
```

⚠️ **Note what statelessness does *not* mean.** It does not mean there is no state — it means the
state is not in the *server's memory*. It is in a cookie, a token, a database or a cache. **The
moment you keep session state in a Python process's memory, you have broken horizontal scaling**, and
you will meet that consequence again in Stage 9. Day 019 covers where state actually lives.

# Part 3 — C-04 · ⭐⭐ TCP: the handshake

```
⭐⭐ THE THREE-WAY HANDSHAKE — this happens before a single byte of your data moves:

   CLIENT                                      SERVER
     │  ── SYN,  seq=x ──────────────────────▶  │   ⭐ "I want to talk. My sequence starts at x."
     │  ◀───────────── SYN-ACK, seq=y, ack=x+1 │   ⭐ "OK. Mine starts at y. I got yours."
     │  ── ACK,  ack=y+1 ────────────────────▶  │   ⭐ "I got yours too."
     │                                          │
     │  ⭐⭐ NOW the connection is ESTABLISHED    │
```

| ⭐ Why three and not two | |
|---|---|
| ⭐⭐ **Both sides must agree on a starting sequence number** | ⭐⭐ and both must confirm the other's — that takes three messages |
| ⭐ Random initial sequence numbers | ⭐ a security measure — predictable ones allow connection hijacking |
| ⭐⭐ **The cost is one full round trip** | ⭐⭐ before any data. **Across continents that is ~130 ms of nothing** |

⭐⭐ **That last row is why connection reuse matters so much.** A new TCP connection costs a round
trip; adding TLS costs one or two more (Day 009). **This is the entire reason for HTTP keep-alive,
connection pools in your database driver, and HTTP/2 multiplexing** — and it is the same argument you
will make about connection pooling in Stage 5.

## ⭐ Sequence and acknowledgement numbers

```
⭐ Every byte is numbered. The ACK says "I have received everything up to N; send me N."
⭐ ⇒ ⭐⭐ CUMULATIVE acknowledgement. ⭐ An ACK for byte 5000 confirms every byte before it.
⭐ ⇒ ⭐ Anything unacknowledged after a timeout is retransmitted (Day 007's C-05).
⭐ ⇒ ⭐⭐ This is what "reliable" means in TCP: not "never lost", but "lost and re-sent, in order".
```

## ⭐ Teardown — and the state that will confuse you later

```
⭐ Closing takes FOUR messages, because each direction closes independently:
   FIN ──▶     ◀── ACK     ◀── FIN     ACK ──▶

⭐⭐ The side that closes FIRST enters TIME_WAIT for ~2× the maximum segment lifetime (~60s).
⭐ ⇒ ⭐⭐ WHY: so a delayed packet from this connection cannot be delivered to a NEW connection
⭐     that happens to reuse the same four-tuple.
⭐ ⇒ ⭐⭐ THIS IS WHY "address already in use" happens when nothing is running (Day 003).
⭐ ⇒ ⭐ And why `SO_REUSEADDR` exists, which is that line you have been typing since Day 003.
```

⭐ **Day 008 goes deeper into the state machine.** Today just connect the dots: the flag you have been
copying has a reason, and the reason is a correctness guarantee about delayed packets.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Treating `recv()` as "read the whole response"** | ⭐⭐ It returns what has arrived. TCP is a byte stream — you must loop and frame. |
| Assuming one `send` = one `recv` | ⭐ Message boundaries are not preserved. Ever. |
| Omitting the `Host` header in HTTP/1.1 | It is mandatory; virtual hosting depends on it. |
| ⭐ "Stateless means no state" | ⭐⭐ It means no state **in the server's memory** between requests. |
| Keeping session data in a Python process | ⭐⭐ Breaks horizontal scaling the moment you add a second worker. |
| Thinking the handshake is free | ⭐ One round trip before any data — 130 ms across continents. |
| "TCP guarantees delivery" | ⭐ It guarantees ordered delivery **or** an error. It cannot make a cut cable work. |
| Ignoring `TIME_WAIT` | It is the usual cause of a bind failure when nothing is running. |

## Interview questions

**Q: What makes something a client rather than a server?**
> Which side initiates. The server binds a port and waits in `accept()`; the client calls `connect()`.
> They are roles in a protocol rather than kinds of machine, and one program is usually both — a web
> API is a server to the browser and a client to Postgres, Redis and whatever else it calls. That
> matters because every timeout, retry and connection-pool decision applies to you in your client
> role.

**Q: Why do you need a loop around `recv()`?**
> Because TCP is a byte stream and does not preserve message boundaries. One `sendall` can arrive as
> several `recv` calls and several sends can coalesce into one read, so `recv` returns whatever has
> arrived so far. That is why every protocol on top of TCP has framing — HTTP uses `Content-Length` or
> chunked encoding, and hand-rolled protocols use a length prefix or a delimiter. Assuming one read
> gets the whole message is the classic beginner socket bug.

**Q: Why is HTTP stateless, and what did that buy?**
> Each request carries everything needed to serve it, so the server does not have to remember the
> client between requests. That means any server in a fleet can answer any request, which is what
> makes horizontal scaling and load balancing straightforward. It does not mean there is no state — it
> means the state lives in a cookie, a token, a cache or a database rather than in one process's
> memory. Putting session state in process memory is exactly how people accidentally break the
> property.

**Q: Why is the TCP handshake three messages?**
> Both sides need to choose an initial sequence number and have it acknowledged by the other. The
> client's SYN carries its number, the server's SYN-ACK carries its own and acknowledges the client's,
> and the client's ACK acknowledges the server's — three messages is the minimum for a mutual
> agreement. The practical consequence is that every new connection costs a full round trip before any
> data moves, which is the whole argument for keep-alive and connection pooling.

**Q: You restarted your server and got "address already in use". Why?**
> The previous listening socket is in `TIME_WAIT`. The side that closes first holds the tuple for
> roughly twice the maximum segment lifetime so that any delayed packet from the old connection cannot
> be delivered to a new connection reusing the same four-tuple. `SO_REUSEADDR` tells the kernel you
> accept that risk and want to bind anyway, which is why it is standard in every server example.
