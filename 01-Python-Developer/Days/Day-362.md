# Day 362 🧱

**P-362** · 🧱 **Images and layers** — the cache, ⭐⭐ the tag lie, and the secret you cannot delete

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an image is an ordered stack of immutable filesystem diffs, and the two
> consequences that matter are that layer order determines whether your builds take ten seconds or
> four minutes, and that deleting a file in a later layer does not remove it — so a secret committed
> in layer three is still in the image after `RUN rm` in layer four.**

---

# Part 1 — ⭐⭐ What a layer actually is

```
⭐⭐ EACH INSTRUCTION THAT CHANGES THE FILESYSTEM PRODUCES A
⭐   ***DIFF***: the set of files added, changed or deleted.
⭐   ⭐ `RUN`, `COPY`, `ADD` ⇒ a layer.
⭐   ⭐ `ENV`, `WORKDIR`, `USER`, `LABEL`, `EXPOSE`, `CMD` ⇒
⭐     ⭐⭐ METADATA ONLY, NO LAYER. ⭐ People assume these are
⭐     "free instructions to minimise" and they already are.

⭐⭐ AT RUNTIME, ***OVERLAYFS*** STACKS THEM READ-ONLY AND ADDS
⭐   ONE WRITABLE LAYER on top.
⭐   ⭐ Writing to an existing file ⇒ ⭐⭐ ***COPY-UP***: the
⭐     whole file is copied into the writable layer first.
⭐   ⇒ ⭐⭐ WHICH IS WHY APPENDING ONE LINE TO A 2 GB FILE INSIDE
⭐     A CONTAINER COSTS 2 GB OF DISK AND SEVERAL SECONDS. ⭐ It
⭐     is the single most surprising performance behaviour in
⭐     containers, and it explains "why is my container disk
⭐     filling up".

⭐⭐ DELETION IS THE PART THAT MATTERS MOST:
⭐   ⭐ `RUN rm /app/secret.pem` does ***not*** remove the bytes.
⭐   ⭐ ⭐⭐ IT WRITES A ***WHITEOUT*** MARKER IN THE NEW LAYER
⭐     THAT ***HIDES*** THE FILE. ⭐ The earlier layer still
⭐     contains it, unchanged, and it ships with the image.
⭐   ⇒ ⭐⭐ ANYONE WHO PULLS YOUR IMAGE CAN EXTRACT IT WITH
⭐     `docker save` AND `tar`, WITHOUT RUNNING ANYTHING.
⭐   ⇒ ⭐⭐ SO: ***A SECRET THAT HAS EVER EXISTED IN A LAYER IS
⭐     IN THE IMAGE FOREVER, AND MUST BE TREATED AS
⭐     COMPROMISED AND ROTATED.*** ⭐ Not "removed in the next
⭐     build" — ***rotated***.

⭐⭐ AND THE CONTENT-ADDRESSING THAT MAKES SHARING WORK:
⭐   ⭐ Each layer is identified by the digest of its contents,
⭐     ⭐ so two images sharing a base share those layers on disk
⭐     and in the registry — ⭐⭐ PULLING TEN IMAGES BUILT ON THE
⭐     SAME BASE DOWNLOADS THE BASE ONCE.
⭐   ⇒ ⭐ Which is a real argument for a ***standard base image
⭐     across your organisation***: it is not tidiness, it is
⭐     bandwidth, disk and pull latency on every node.
```

# Part 2 — ⭐⭐ The build cache, and the ordering rule

```
⭐⭐ THE RULE: ***A LAYER IS REUSED ONLY IF ITS INSTRUCTION
⭐   ***AND*** EVERY LAYER BEFORE IT ARE UNCHANGED.***
⭐   ⇒ ⭐⭐ SO ONE CHANGE INVALIDATES EVERYTHING BELOW IT. ⭐ The
⭐     cache is a prefix match, not a set.

⭐⭐ FOR `COPY`, "UNCHANGED" MEANS ⭐⭐ THE CHECKSUM OF THE
⭐   COPIED FILES — not the timestamp. ⭐ Which is why
⭐   `COPY . .` early is fatal: ⭐⭐ EDITING ***ANY*** FILE
⭐   INVALIDATES EVERY SUBSEQUENT LAYER, INCLUDING YOUR
⭐   DEPENDENCY INSTALL.

⭐⭐ ❌ THE DOCKERFILE EVERYONE WRITES FIRST:
```

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .                          # ❌ ⭐⭐ CACHE DIES HERE
RUN pip install -r requirements.txt   # ⭐ 90 s, EVERY BUILD
CMD ["uvicorn", "app.main:app"]
```

```dockerfile
# ✔ ⭐⭐ THE ORDERING THAT MATTERS — DEPENDENCIES BEFORE SOURCE
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .                  # ⭐ changes rarely
RUN pip install --no-cache-dir -r requirements.txt   # ⭐⭐ CACHED
COPY . .                                 # ⭐ changes constantly
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]
```

```
⭐⭐ THE PRINCIPLE, GENERALISED:
⭐   ***ORDER INSTRUCTIONS FROM LEAST-FREQUENTLY-CHANGED TO
⭐      MOST-FREQUENTLY-CHANGED.***
⭐   ⇒ ⭐ base → system packages → dependency manifest →
⭐     dependency install → application code.
⭐   ⇒ ⭐⭐ TYPICAL EFFECT ON A REAL PYTHON PROJECT: A 3–4 MINUTE
⭐     BUILD BECOMES 10–20 SECONDS ON EVERY CODE CHANGE. ⭐ It
⭐     is the highest-return two-line change in this stage.

⭐⭐ AND THE THREE CACHE KILLERS TO WATCH FOR:
⭐   ① ⭐⭐ NO `.dockerignore` ⇒ `COPY . .` INCLUDES `.git`,
⭐      `.venv`, `__pycache__`, `node_modules`, TEST FIXTURES.
⭐      ⇒ ⭐⭐ THE CACHE BREAKS ON EVERY COMMIT (because `.git`
⭐        changes), THE CONTEXT UPLOAD IS SLOW, ⭐⭐ AND `.env`
⭐        AND `.aws/credentials` GET BAKED IN. ⭐ It is a
⭐        performance fix and a security control at once.
⭐   ② ⭐ `RUN apt-get update` in its own layer ⇒ ⭐⭐ THE
⭐      PACKAGE INDEX IS CACHED AND GOES STALE, SO A LATER
⭐      `apt-get install` FAILS OR INSTALLS AN OLD VERSION.
⭐      ⭐ Always `apt-get update && apt-get install` in one
⭐      `RUN`.
⭐   ③ ⭐ Anything with a timestamp or a random value early in
⭐      the file — ⭐ a build-arg like `BUILD_DATE` placed near
⭐      the top ⭐⭐ INVALIDATES EVERYTHING BELOW IT ON EVERY
⭐      BUILD. ⭐ Put those `ARG`s and `LABEL`s ***last***.
```

# Part 3 — ⭐⭐ The tag lie

```
⭐⭐ ***A TAG IS A MUTABLE POINTER. A DIGEST IS THE IDENTITY.***

⭐⭐ THREE CONSEQUENCES, AND ALL THREE HAVE CAUSED REAL
⭐   INCIDENTS:
⭐   ① ⭐⭐ `FROM python:3.12-slim` DOES NOT MEAN THE SAME BYTES
⭐      TODAY AS LAST WEEK. ⭐ The tag is re-pointed on every
⭐      patch release.
⭐      ⇒ ⭐⭐ SO A BUILD THAT SUCCEEDED YESTERDAY CAN FAIL TODAY
⭐        WITH NO CHANGE TO YOUR CODE — and the diff is invisible
⭐        in git.
⭐   ② ⭐⭐ PUSHING `myapp:latest` TWICE MEANS TWO DIFFERENT
⭐      IMAGES WITH ONE NAME. ⭐ "Which version is in
⭐      production?" becomes unanswerable.
⭐   ③ ⭐ `imagePullPolicy: IfNotPresent` with a moving tag ⇒
⭐      ⭐⭐ DIFFERENT NODES RUN DIFFERENT CODE UNDER THE SAME
⭐      TAG, INDEFINITELY. ⭐ This is a genuinely horrible bug
⭐      to diagnose because both pods report the same version.

⭐⭐ THE DISCIPLINE:
⭐   ⭐ ⭐⭐ BUILD-TIME: PIN THE BASE BY DIGEST —
⭐     `FROM python:3.12-slim@sha256:abc…`. ⭐ Update it
⭐     deliberately, with a bot (Renovate/Dependabot) opening a
⭐     PR you review.
⭐   ⭐ ⭐⭐ DEPLOY-TIME: DEPLOY BY DIGEST, NEVER BY TAG. ⭐ Tags
⭐     are for humans; ⭐⭐ DIGESTS ARE FOR MACHINES.
⭐   ⭐ Tag with something meaningful ***as well***:
⭐     `myapp:1.4.2`, `myapp:git-a3f9c21`, ⭐⭐ AND NEVER RELY
⭐     ON `latest` FOR ANYTHING AUTOMATED.
⭐   ⇒ ⭐ This is Day 283's "promote the digest", ⭐⭐ AND THIS
⭐     IS THE DAY THAT EXPLAINS ***WHY*** THE DIGEST IS THE ONLY
⭐     THING THAT MEANS ANYTHING.

⭐⭐ AND ONE MORE THING A DIGEST BUYS: ⭐⭐ IMMUTABILITY IS A
⭐   SUPPLY-CHAIN CONTROL. ⭐ If an attacker compromises your
⭐   registry and re-points a tag, a digest-pinned deployment
⭐   ***does not change***. ⭐ A tag-based one silently does.
```

# Part 4 — ⭐⭐ Python-specific layering

```
⭐⭐ ① ***`--no-cache-dir` ON `pip install`.***
⭐   ⭐ pip caches downloaded wheels in `~/.cache/pip` — ⭐⭐ AND
⭐     THAT CACHE IS BAKED INTO THE LAYER. ⭐ Often 100–300 MB
⭐     of files you will never use again.
⭐   ⇒ ⭐ `--no-cache-dir`, ⭐⭐ OR BETTER, A BUILDKIT CACHE
⭐     MOUNT: `RUN --mount=type=cache,target=/root/.cache/pip
⭐     pip install -r requirements.txt` — ⭐⭐ WHICH KEEPS THE
⭐     CACHE ***BETWEEN BUILDS*** WITHOUT PUTTING IT ***IN THE
⭐     IMAGE***. ⭐ Best of both, and almost nobody uses it.

⭐⭐ ② ***PIN EVERYTHING, TRANSITIVELY.***
⭐   ⭐ `requirements.txt` with `fastapi` and no version ⇒
⭐     ⭐⭐ A DIFFERENT IMAGE EVERY BUILD, WHICH DEFEATS THE
⭐     ENTIRE POINT OF AN IMAGE.
⭐   ⇒ ⭐ Use a lockfile: `pip-compile` (pip-tools),
⭐     `uv pip compile`, `poetry.lock`, ⭐ with hashes
⭐     (`--generate-hashes`) so ⭐⭐ A COMPROMISED PACKAGE
⭐     VERSION CANNOT BE SUBSTITUTED.
⭐   ⇒ ⭐⭐ AND PIN THE ***BUILD TOOLS*** TOO: `pip`, `setuptools`
⭐     AND `wheel` VERSIONS AFFECT WHAT GETS BUILT.

⭐⭐ ③ ***THE `.pyc` QUESTION.***
⭐   ⭐ `PYTHONDONTWRITEBYTECODE=1` keeps `.pyc` out of the
⭐     image — ⭐⭐ AND THEN THE FIRST REQUEST AFTER EVERY START
⭐     PAYS THE COMPILE COST, AND WITH A READ-ONLY FILESYSTEM
⭐     IT PAYS IT ***EVERY TIME.***
⭐   ⇒ ⭐⭐ FOR A LONG-RUNNING SERVICE, DO THE OPPOSITE:
⭐     `RUN python -m compileall -q /app` AT BUILD TIME. ⭐ It
⭐     costs a few MB and removes cold-start compile latency
⭐     permanently. ⭐ For a short-lived job image, skip it.

⭐⭐ ④ ***VIRTUALENV IN A CONTAINER — YES OR NO?***
⭐   ⭐ In a single-stage image it is redundant: ⭐ the container
⭐     ***is*** the isolation.
⭐   ⭐ ⭐⭐ IN A MULTI-STAGE BUILD IT IS EXTREMELY USEFUL,
⭐     BECAUSE A VENV IS ***ONE DIRECTORY YOU CAN COPY*** —
⭐     `COPY --from=builder /opt/venv /opt/venv` ⭐ is far
⭐     cleaner than chasing site-packages across paths.
⭐   ⇒ ⭐ Day 363 uses exactly this.

⭐⭐ ⑤ ***`COPY --chown` INSTEAD OF `RUN chown -R`.***
⭐   ⭐ `RUN chown -R app /app` after a `COPY` ⇒ ⭐⭐ COPY-UP OF
⭐     EVERY FILE INTO A NEW LAYER, DOUBLING THAT CONTENT'S SIZE
⭐     IN THE IMAGE. ⭐ `COPY --chown=app:app . .` does it in one
⭐     layer, free.
```

# Part 5 — ⭐ Inspecting an image like an adversary

```
⭐⭐ THE COMMANDS, AND WHAT EACH REVEALS:
⭐   ⭐ `docker history --no-trunc <image>` ⇒ ⭐⭐ EVERY
⭐     INSTRUCTION AND ITS SIZE. ⭐ This is where you see the
⭐     400 MB layer you did not intend, ⭐⭐ AND WHERE A
⭐     `--build-arg` SECRET APPEARS IN PLAIN TEXT.
⭐   ⭐ `docker save img | tar -tv` ⇒ every file in every layer.
⭐   ⭐ `dive <image>` ⇒ ⭐ an interactive layer browser with a
⭐     wasted-space estimate. ⭐⭐ RUN IT ONCE ON YOUR OWN IMAGE
⭐     AND YOU WILL FIND SOMETHING.
⭐   ⭐ `docker inspect` ⇒ env, user, entrypoint, labels.
⭐     ⭐⭐ AND `ENV DB_PASSWORD=…` IS VISIBLE HERE TO ANYONE
⭐     WITH THE IMAGE.

⭐⭐ THE THREE PLACES SECRETS LEAK INTO IMAGES:
⭐   ① ⭐⭐ `ARG`/`--build-arg` ⇒ ***RECORDED IN THE IMAGE
⭐      HISTORY***. ⭐ People use this for private-repo tokens
⭐      constantly, and it is exactly as exposed as writing it
⭐      in the Dockerfile.
⭐   ② ⭐ `ENV` ⇒ visible in `inspect` and in every child
⭐      process's environment.
⭐   ③ ⭐ A file copied in and later `rm`-ed ⇒ Part 1.
⭐   ⇒ ⭐⭐ THE FIX FOR ALL THREE: ***BUILDKIT SECRET MOUNTS.***
⭐     `RUN --mount=type=secret,id=pip_token pip install …`
⭐     ⭐⭐ THE SECRET IS AVAILABLE DURING THAT `RUN` AND IS IN
⭐     ***NO LAYER***. ⭐ It is one line and it is the correct
⭐     answer.
⭐   ⇒ ⭐ And for runtime secrets: ⭐⭐ INJECT AT RUN TIME, NEVER
⭐     BAKE (Day 372).
```

# Part 6 — ⭐⭐ Base image choice

```
⭐⭐ THE FOUR OPTIONS FOR PYTHON, WITH THE HONEST SIZES:
⭐   ⭐ `python:3.12` ⇒ ~1 GB. ⭐ Everything, including compilers
⭐     you do not want in production.
⭐   ⭐ ⭐⭐ `python:3.12-slim` ⇒ ~150 MB. ⭐⭐ THE DEFAULT
⭐     ANSWER. Debian, glibc, manylinux wheels work.
⭐   ⭐ `python:3.12-alpine` ⇒ ~50 MB, ⭐⭐ AND A TRAP.
⭐   ⭐ `gcr.io/distroless/python3` ⇒ ⭐ small, no shell, no
⭐     package manager. ⭐⭐ EXCELLENT SECURITY POSTURE, HARDER
⭐     TO DEBUG (Day 361's `kubectl debug` is how).

⭐⭐ ***THE ALPINE TRAP, WHICH IS THE PYTHON-SPECIFIC ONE
⭐   INTERVIEWERS LIKE:***
⭐   ⭐ Alpine uses ***musl***, not glibc.
⭐   ⭐ ⭐⭐ PyPI's `manylinux` WHEELS ARE BUILT AGAINST glibc, SO
⭐     THEY DO NOT INSTALL. ⭐ pip falls back to building from
⭐     source.
⭐   ⇒ ⭐⭐ CONSEQUENCES: BUILD TIMES GO FROM 30 SECONDS TO
⭐     10–20 MINUTES; YOU MUST INSTALL gcc AND HEADERS, WHICH
⭐     ***ERASES THE SIZE SAVING***; AND SOME PACKAGES SIMPLY
⭐     FAIL.
⭐   ⇒ ⭐⭐ AND THE SUBTLE ONE: musl's MALLOC IS SLOWER UNDER
⭐     MULTITHREADED WORKLOADS, SO YOU CAN LOSE MEASURABLE
⭐     PERFORMANCE FOR A SMALLER IMAGE YOU DID NOT ACTUALLY GET.
⭐   ⇒ ⭐⭐ SO: ***USE `-slim`. ⭐ USE ALPINE ONLY IF YOUR
⭐     DEPENDENCIES ARE PURE PYTHON AND YOU HAVE MEASURED THE
⭐     BENEFIT.*** ⭐ (`musllinux` wheels exist now and coverage
⭐     is improving — ⭐ but "improving" is not "reliable".)

⭐⭐ AND THE OTHER SIZE QUESTION WORTH REFRAMING:
⭐   ⭐ ⭐⭐ IMAGE SIZE MATTERS LESS THAN PEOPLE THINK FOR
⭐     ***BANDWIDTH*** (layers are shared and cached) AND MORE
⭐     THAN THEY THINK FOR ***ATTACK SURFACE AND CVE NOISE***.
⭐   ⇒ ⭐ A 1 GB image with a shell, curl, gcc and a package
⭐     manager gives an attacker a toolkit ⭐⭐ AND GIVES YOU
⭐     TWO HUNDRED CVEs TO TRIAGE THAT HAVE NOTHING TO DO WITH
⭐     YOUR CODE.
```

# Part 7 — ⭐ Registry hygiene

```
⭐⭐ FIVE THINGS THAT ARE ALWAYS WORTH DOING:
⭐   ① ⭐⭐ IMMUTABLE TAGS ENABLED (ECR and most registries
⭐      support it) ⇒ a tag can never be re-pointed. ⭐ Removes
⭐      an entire class of "which build is this?" incident.
⭐   ② ⭐ A lifecycle policy: keep the last N, expire untagged
⭐      after X days. ⭐⭐ WITHOUT IT, REGISTRY STORAGE GROWS
⭐      FOREVER AND IT IS BILLED.
⭐   ③ ⭐ Scan on push (Day 363), ⭐ and fail the ***pipeline***
⭐      rather than emailing a report nobody reads.
⭐   ④ ⭐⭐ ONE REGISTRY PER ENVIRONMENT OR A CLEAR PROMOTION
⭐      PATH — ⭐ so "how did an unscanned image reach
⭐      production?" has a structural answer, not a policy one.
⭐   ⑤ ⭐ Sign images (cosign/Sigstore) and ⭐⭐ VERIFY AT ADMISSION
⭐      — ⭐ the point is not the signature, it is that the
⭐      cluster ***refuses*** anything unsigned, which turns a
⭐      policy into a mechanism.

⭐⭐ AND THE PRACTICE THAT PAYS FOR ITSELF:
⭐   ***AN SBOM PER IMAGE*** (syft/Trivy), stored as an artefact.
⭐   ⇒ ⭐⭐ WHEN THE NEXT log4shell-CLASS CVE LANDS, THE
⭐     QUESTION "WHICH OF OUR 200 IMAGES CONTAINS THIS
⭐     PACKAGE?" IS A GREP INSTEAD OF A WEEK. ⭐ That is the
⭐     entire justification, and it is enough.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ `COPY . .` before installing dependencies | Every code edit invalidates the dependency layer. 3-minute builds forever |
| ⭐⭐ Believing `RUN rm secret` removes it | It writes a whiteout. The bytes ship in the earlier layer — rotate the secret |
| ⭐⭐ Secrets via `--build-arg` | Recorded in `docker history` in plain text. Use BuildKit secret mounts |
| ⭐ Secrets in `ENV` | Visible in `docker inspect` and in every child process's environment |
| ⭐⭐ Deploying by tag | Tags are mutable. Two pushes of `latest` is two images with one name |
| ⭐ Unpinned base image | A build that worked yesterday fails today, with no diff in git |
| ⭐ `IfNotPresent` with a moving tag | Different nodes run different code under the same tag, indefinitely |
| ⭐⭐ No `.dockerignore` | Cache breaks every commit, context upload is slow, and `.env` gets baked in |
| ⭐ `apt-get update` in its own layer | The index is cached and goes stale; installs fail or fetch old versions |
| ⭐ `pip install` without `--no-cache-dir` | 100–300 MB of wheel cache baked into the layer |
| ⭐⭐ Alpine for a Python app with C extensions | musl means no manylinux wheels: 20-minute builds, and the size saving is erased |
| ⭐ `RUN chown -R` after `COPY` | Copies up every file into a new layer. Use `COPY --chown` |
| ⭐ Build args or labels near the top | A timestamp arg invalidates everything below it on every build |
| ⭐⭐ No registry lifecycle policy | Storage grows forever and it's billed |

## Interview questions

**1. "Your Docker build takes four minutes on every code change. Why?"**
> ⭐⭐ Almost certainly `COPY . .` before `pip install`. ⭐ **The cache is a prefix match — a layer is
> reused only if it and everything above it are unchanged — and for `COPY` "unchanged" means the
> checksum of the files**, so editing any file invalidates the dependency install. ⭐ Copy the
> requirements file first, install, then copy the source: ⭐⭐ **typically four minutes becomes fifteen
> seconds.** ⭐ And add a `.dockerignore`, or `.git` changes every commit and breaks it anyway.

**2. "You committed a private key into an image and removed it in the next line. Is it safe?"**
> ⭐⭐ No. **`RUN rm` writes a whiteout marker that hides the file; the bytes are still in the earlier
> layer and ship with the image**, extractable with `docker save` and `tar` without running anything.
> ⭐⭐ So the key must be treated as compromised and **rotated**, not removed. ⭐ The correct mechanism is
> a BuildKit secret mount — the secret exists during that `RUN` and lands in no layer.

**3. "Tag or digest?"**
> ⭐ Tags for humans, digests for machines. ⭐⭐ **A tag is a mutable pointer** — `python:3.12-slim` isn't
> the same bytes as last week, two pushes of `latest` is two images with one name, and
> `IfNotPresent` with a moving tag means different nodes run different code while reporting the same
> version. ⭐ So: pin the base by digest with a bot opening update PRs, deploy by digest, and enable
> immutable tags in the registry. ⭐⭐ It's also a supply-chain control — **if someone re-points a tag in
> your registry, a digest-pinned deployment doesn't change.**

**4. "Alpine or slim for Python?"**
> ⭐⭐ Slim, unless I've measured otherwise. **Alpine uses musl, and PyPI's manylinux wheels are built
> against glibc**, so anything with a C extension falls back to compiling from source: builds go from
> thirty seconds to fifteen minutes, you have to install gcc and headers, ⭐⭐ **which erases the size
> saving you came for.** ⭐ And musl's allocator is slower under multithreaded load. ⭐ musllinux wheels
> exist and coverage is improving, but improving isn't reliable.

**5. "Does image size matter?"**
> ⭐ Less than people think for bandwidth, since layers are shared and cached across images on a node —
> ⭐⭐ **and more than they think for attack surface and CVE noise.** ⭐ A gigabyte image with a shell,
> curl, gcc and a package manager hands an attacker a toolkit and hands you two hundred CVEs to triage
> that have nothing to do with your code. ⭐ That's the real argument for slim and distroless.

**6. "What Python-specific layering choices would you make?"**
> ⭐ `--no-cache-dir`, or better a BuildKit cache mount so the wheel cache persists **between** builds
> without landing **in** the image. ⭐ A lockfile with hashes, so a compromised version can't be
> substituted, and pinned build tools. ⭐⭐ `compileall` at build time for a long-running service —
> **otherwise with a read-only filesystem you pay the bytecode compile on every single start.** ⭐ And
> `COPY --chown` rather than `RUN chown -R`, which would copy up every file into a new layer.

## 🎙️ Articulation drill

**Two minutes.** Define a layer as a filesystem diff, then give the two consequences that matter. First
the cache: **it's a prefix match, so one change invalidates everything below it — which is why `COPY .
.` before installing dependencies means a four-minute build on every code edit, and reordering it to
requirements-then-install-then-source makes it fifteen seconds.** Add the `.dockerignore`, which is
simultaneously a performance fix and a security control, since without it `.git` changes every commit
and `.env` gets baked in. Then the deletion consequence, which is the one people get wrong: **`RUN rm`
writes a whiteout marker that hides the file — the bytes remain in the earlier layer and ship with the
image**, so a leaked secret has to be rotated, not removed. Name the three leak paths — build args
recorded in history, `ENV` visible in inspect, and copied-then-deleted files — and the single fix,
BuildKit secret mounts. Then the tag lie: **a tag is a mutable pointer and a digest is the identity**,
so pin the base by digest and deploy by digest, which also means a compromised registry re-pointing a
tag can't change what you run. Close on the Python-specific choice: **slim, not Alpine, because musl
means no manylinux wheels — builds go from thirty seconds to fifteen minutes and you install gcc,
