**L-113** · **Testing the framework** — a test client you write yourself, and ⭐⭐ one suite run against both adapters

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a test client is not a network client — it calls your application object
> directly, which is why an "integration test through the API" can cost a millisecond, and why
> Day 092's fat integration layer is affordable at all.**
>
> ⭐ Day 097 used `httpx.ASGITransport` as a given. **Today you write it**, and then you run one test
> suite against both your WSGI and ASGI adapters — which is Day 095's contract test, applied to your

# Part 1 — ⭐⭐ A WSGI test client, in twenty lines

```python
from io import BytesIO

class WSGIClient:
    def __init__(self, app): self.app = app

    def request(self, method, path, body=b"", headers=None, query=""):
        captured = {}
        def start_response(status, response_headers, exc_info=None):
            captured["status"] = int(status.split(" ", 1)[0])      # ⭐ "200 OK" -> 200
            captured["headers"] = response_headers

        environ = {                                                 # ⭐ Day 109's environ
            "REQUEST_METHOD": method,
            "PATH_INFO": path,
            "QUERY_STRING": query,
            "CONTENT_LENGTH": str(len(body)),
            "wsgi.input": BytesIO(body),                            # ⭐⭐ a file-like body
            "wsgi.url_scheme": "http",
            "SERVER_NAME": "testserver", "SERVER_PORT": "80",
        }
        for k, v in (headers or {}).items():
            environ["HTTP_" + k.upper().replace("-", "_")] = v      # ⭐ the mangling, deliberately

        chunks = self.app(environ, start_response)
        try:
            body_out = b"".join(chunks)
        finally:
            if hasattr(chunks, "close"): chunks.close()             # ⭐⭐ Day 109 — or `finally`
        return TestResponse(captured["status"], captured["headers"], body_out)   # ⭐ never runs
```

```
⭐⭐ NO SOCKET. NO PORT. NO SERVER. NO THREAD.
⭐   ⇒ ⭐⭐ THEREFORE: no port collisions in CI, no "wait for the server to be
⭐        ready" sleep, nothing left running when a test fails, and a full
⭐        request/response cycle in microseconds.
⭐   ⇒ ⭐⭐ AND IT EXERCISES EVERYTHING THAT MATTERS: routing, middleware order,
⭐        the adapter, error handling, headers. ⭐ The only thing it skips is the
⭐        socket layer — which you tested on Days 103-105, and which is not where
⭐        your bugs are.
⭐   ⇒ ⭐ note the `finally: close()`. Forget it and a streaming handler's
⭐        generator never runs its cleanup, so your test suite leaks database
⭐        cursors and you blame the pool.
```

# Part 2 — ⭐⭐ An ASGI test client — you drive the protocol

```python
class ASGIClient:
    def __init__(self, app): self.app = app

    async def request(self, method, path, body=b"", headers=None):
        scope = {"type": "http", "method": method, "path": path,
                 "headers": [(k.lower().encode(), v.encode())
                             for k, v in (headers or {}).items()],
                 "query_string": b"", "client": ("127.0.0.1", 12345)}

        sent, to_receive = [], [                                   # ⭐⭐ YOU are the server now
            {"type": "http.request", "body": body, "more_body": False},
        ]
        async def receive(): return to_receive.pop(0)
        async def send(message): sent.append(message)

        await self.app(scope, receive, send)

        start = next(m for m in sent if m["type"] == "http.response.start")
        body_out = b"".join(m.get("body", b"") for m in sent
                            if m["type"] == "http.response.body")   # ⭐ handles streaming
        return TestResponse(start["status"], start["headers"], body_out)
```

```
⭐⭐ WRITING THIS IS THE MOMENT ASGI STOPS BEING ABSTRACT: you are playing the
⭐   SERVER's half of Day 110's protocol. ⭐ You supply the scope, you answer
⭐   `receive`, you collect what the app `send`s.
⭐   ⇒ ⭐⭐ AND IT MAKES THE TESTS FOR STREAMING TRIVIAL — the response body is
⭐        just "every `http.response.body` message concatenated", so asserting on
⭐        the CHUNK BOUNDARIES is possible too, which no network client can do.
⭐   ⇒ ⭐ `httpx.ASGITransport` (Day 097) is precisely this, with a nicer API.
```

```python
async def lifespan(self):                        # ⭐⭐ test startup/shutdown too
    messages = [{"type": "lifespan.startup"}, {"type": "lifespan.shutdown"}]
    sent = []
    async def receive(): return messages.pop(0)
    async def send(m): sent.append(m)
    await self.app({"type": "lifespan"}, receive, send)
    assert sent[0]["type"] == "lifespan.startup.complete"     # ⭐ or .failed
```

⭐⭐ **Almost nobody tests lifespan, and it is where the "works locally, dies in production" bugs live**
— a pool that fails to build, a shutdown hook that hangs past the grace period (Day 081). ⭐ **Driving
it directly costs five lines.**

# Part 3 — ⭐ What to test in a framework

```python
@pytest.mark.parametrize("path, expected_status, expected_id", [    # ⭐ Day 094
    ("/users/42",     200, 42),
    ("/users/0",      200, 0),          # ⭐ boundary
    ("/users/abc",    404, None),       # ⭐⭐ the :int converter must NOT match
    ("/users/",       404, None),
    ("/users/42/",    404, None),       # ⭐ or 308, depending on your policy (Day 107)
])
def test_routing(client, path, expected_status, expected_id): ...

def test_wrong_method_is_405_with_allow(client):
    r = client.request("DELETE", "/users/42")
    assert r.status == 405                                   # ⭐⭐ NOT 404 (Day 107)
    assert "GET" in r.headers["Allow"]                       # ⭐ the header is the point

def test_middleware_runs_in_order(client):
    order = []
    # ⭐⭐ each middleware appends on the way IN and on the way OUT
    assert order == ["a_in", "b_in", "handler", "b_out", "a_out"]      # ⭐ the onion, asserted

def test_handler_exception_returns_500_and_server_survives(client):
    r = client.request("GET", "/boom")
    assert r.status == 500
    assert b"Traceback" not in r.body                        # ⭐⭐ Day 105's security rule
    assert client.request("GET", "/health").status == 200    # ⭐⭐ still alive
```

```
⭐⭐ THE FOUR TESTS THAT ARE ACTUALLY LOAD-BEARING, and note that each one
⭐   corresponds to a bug you deliberately caused earlier in the stage:
⭐   1. ⭐ ROUTING TABLE — including the negative cases. ⭐⭐ A converter that
⭐        matches too much (Day 107's `.+`) only shows up in a negative test.
⭐   2. ⭐⭐ 404 vs 405 — the distinction the whole router shape exists for.
⭐   3. ⭐⭐ MIDDLEWARE ORDER — asserted explicitly, because the onion is a
⭐        correctness property (Day 108) and nothing else will catch a reorder.
⭐   4. ⭐⭐ THE ERROR PATH — a 500, no traceback in the body, and THE NEXT
⭐        REQUEST STILL WORKS. ⭐ That last assertion is the one people omit and
⭐        it is the one that catches a handler killing the worker.
```

# Part 4 — ⭐⭐ One suite, both adapters

```python
@pytest.fixture(params=["wsgi", "asgi"])              # ⭐⭐ Day 095's contract test
def client(request, app):
    return WSGIClient(app) if request.param == "wsgi" else SyncASGIClient(app)

def test_json_endpoint_returns_the_same_thing(client):
    r = client.request("POST", "/orders", body=b'{"qty": 2}',
                       headers={"Content-Type": "application/json"})
    assert r.status == 201
    assert json.loads(r.body)["qty"] == 2
```

```
⭐⭐ EVERY TEST NOW RUNS TWICE, ONCE PER ADAPTER — and that is not tidiness, it
⭐   is the only thing that keeps the two implementations honest.
⭐   ⇒ ⭐⭐ IT CATCHES THE REAL DIVERGENCES: headers as `str` in one adapter and
⭐        `bytes` in the other (Days 109, 110); duplicate headers surviving ASGI
⭐        and being comma-joined by WSGI; a status set differently; a streaming
⭐        response chunked in one and buffered in the other.
⭐   ⇒ ⭐ this is EXACTLY Day 095's fake-versus-real contract test, applied to
⭐        two implementations of your own interface — ⭐⭐ and it is the technique
⭐        to reach for any time you have two things that must behave the same.
```

```python
from hypothesis import given, strategies as st       # ⭐ Day 098A

@given(st.integers(min_value=0, max_value=10**9))
def test_url_for_round_trips(app, user_id):
    path = app.router.url_for("get_user", user_id=user_id)   # ⭐ generate
    handler, params = app.router.resolve(path, "GET")         # ⭐ then resolve
    assert params["user_id"] == user_id                        # ⭐⭐ ROUND TRIP
```

⭐⭐ **A router is one of the best property-testing targets there is**, because it has a genuine
inverse: `url_for` and `resolve` must round-trip for every valid parameter. ⭐ **Hypothesis will find
the values that break your regex** — a zero, a very large integer, a name containing a slash or a
percent sign — **which is precisely the set you would not have thought to write by hand.**

# Part 5 — ⭐ The pyramid, for a framework

| ⭐ Level | ⭐ What it covers | ⭐ Cost |
|---|---|---|
| ⭐ Unit | the router alone, `Headers`, the parser (Day 104) | ⭐ microseconds |
| ⭐⭐ **Test client** | ⭐⭐ routing + middleware + adapter + errors together | ⭐ ~1 ms — **the fat layer** |
| ⭐ Real socket | your Day 106 server end to end | ⭐ ~10 ms — **a handful only** |

```
⭐⭐ AND THE HANDFUL OF SOCKET-LEVEL TESTS ARE NOT OPTIONAL, BECAUSE THEY COVER
⭐   THE ONE THING THE TEST CLIENT CANNOT: THE WIRE.
⭐   ⇒ ⭐ keep-alive across two requests on one connection (Day 105)
⭐   ⇒ ⭐⭐ Content-Length correctness — ⭐ the test client never notices a wrong
⭐        length, because it never parses the framing. ⭐⭐ THAT IS THE CLASSIC
⭐        BLIND SPOT of in-process testing, and it is worth knowing about it
⭐        rather than discovering it from a hanging browser.
⭐   ⇒ ⭐ a slow client, a client that disconnects mid-response, and a request
⭐        that exceeds your parser limits (Day 104)
⭐   ⇒ ⭐⭐ SO: hundreds of test-client tests, and about five socket tests that
⭐        exist purely to prove the bytes are right.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Starting a real server for every test | ⭐⭐ Call the app object. Microseconds, no ports, nothing left running. |
| ⭐ Forgetting `close()` on the WSGI iterable | ⭐ Streaming generators never clean up — leaked cursors. |
| Never testing lifespan | ⭐⭐ Where "works locally, dies in production" lives. Five lines. |
| ⭐ Only testing routes that exist | ⭐⭐ A too-greedy converter only appears in a negative test. |
| Not asserting 405 vs 404 | ⭐ The distinction the router's whole shape exists for. |
| ⭐⭐ **Not asserting middleware order** | ⭐⭐ Nothing else catches a reorder, and order is correctness. |
| Testing the error status but not survival | ⭐⭐ Assert the **next** request still works. |
| ⭐ One adapter tested | ⭐⭐ Run the suite against both — that is what keeps them honest. |
| ⭐ No socket tests at all | ⭐⭐ The test client never checks `Content-Length`. |
| Hand-writing router cases | ⭐ It has an inverse — property-test the round trip. |

## Interview questions

**Q: How do you test a web application without starting a server?**
> By calling the application object directly. For WSGI you build an `environ` dict, pass a
> `start_response` that captures the status and headers, and join the returned iterable. For ASGI you
> supply a scope, implement `receive` and `send` yourself, and collect the messages the app sends. No
> socket, no port, no thread — so no port collisions in CI, no waiting for a server to come up, and
> nothing left running when a test fails. And it exercises everything that matters: routing,
> middleware order, the adapter, error handling. That's what `httpx.ASGITransport` and Flask's test
> client are, and writing one makes the protocol concrete.

**Q: What does an in-process test client *not* cover?**
> The wire. It never parses framing, so it will happily pass with a wrong `Content-Length` — which is
> the bug that makes a browser hang forever. It also can't test keep-alive across two requests on one
> connection, a slow client, a client that disconnects mid-response, or the parser limits. So I'd keep
> hundreds of test-client tests and about five socket-level tests that exist purely to prove the bytes
> are right. Knowing that blind spot is better than discovering it from a hanging browser.

**Q: You have WSGI and ASGI adapters. How do you keep them consistent?**
> Parametrize the client fixture over both and run the entire suite twice. It's the same contract-test
> technique as testing a fake and a real implementation against one suite, and it catches the
> divergences that actually happen: headers as strings in one and bytes in the other, duplicate
> headers surviving ASGI but being comma-joined under WSGI, a status set differently, a response
> streamed in one and buffered in the other. Without it the two drift, and you find out from whichever
> one production uses.

**Q: What would you property-test in a framework?**
> The router, because it has a genuine inverse — `url_for` and `resolve` must round-trip for every
> valid parameter value. Hypothesis will find the values that break the regex: zero, very large
> integers, names with a slash or a percent sign, empty strings. Those are exactly the cases I
> wouldn't have written by hand, and a router is one of the best property-testing targets there is for
> that reason.

**Q: Which four framework tests are load-bearing?**
> The routing table including negative cases, because a converter that matches too much only shows up
> when you assert that something *doesn't* match. The 404-versus-405 distinction, which is what the
> router's shape exists for. Middleware order, asserted explicitly, because it's a correctness
> property and nothing else catches a reorder. And the error path — a 500, no traceback in the body,
> and crucially that the *next* request still succeeds. That last assertion is the one people omit,
> and it's the one that catches a handler taking down the worker.

## 🎙️ Articulation drill

Record two minutes: **"How do you test a web API quickly?"**

⭐ **Lead with the mechanism, because "use the test client" is the shallow answer:** **"in process —
you call the application object directly rather than going through a socket. For ASGI that means
supplying a scope, implementing `receive` and `send` yourself, and collecting the messages the app
sends back. It's about twenty lines, and it's what `httpx.ASGITransport` and Flask's test client
actually are."**

⭐⭐ **Then why it changes your test strategy rather than just your speed:** *"the point isn't
convenience, it's that a full request through routing, middleware, the adapter and error handling costs
a millisecond instead of ten. That's what makes a fat integration layer affordable — I'd rather have
three hundred tests going through the real stack than three hundred unit tests full of mocks, because
in a backend most bugs are at the seams. And no ports means no collisions in CI and nothing left
running when a test fails."*

⭐⭐ **Then the blind spot, unprompted, because that is what shows judgement:** *"what it doesn't cover
is the wire. It never parses framing, so a wrong `Content-Length` passes every in-process test and
then hangs a real browser. It can't test keep-alive, a slow client, or a disconnect mid-response. So I
keep a handful of socket-level tests that exist purely to prove the bytes are right — hundreds of fast
ones, about five slow ones."*

⭐ **Close on the technique that generalises:** *"and if there are two implementations that must agree
— a WSGI and an ASGI adapter, or a fake and a real repository — I parametrize the client fixture over
both and run one suite twice. That's the only thing that keeps them honest; otherwise they drift and
you find out from whichever one production uses."*
