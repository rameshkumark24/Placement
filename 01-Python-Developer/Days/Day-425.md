# Part 1 — Why unit tests do not work here

```
⭐ ⭐ A unit test asserts an exact output for an exact input.
⭐ ⭐⭐ THAT FAILS HERE FOR FOUR SEPARATE REASONS:
⭐   ⭐ ① The output varies between identical calls (Day 418).
⭐   ⭐ ② ⭐⭐ MANY DIFFERENT OUTPUTS ARE EQUALLY CORRECT. ⭐ Two
⭐      valid summaries share few tokens.
⭐   ⭐ ③ ⭐⭐ "CORRECT" IS OFTEN A JUDGEMENT, NOT AN EQUALITY.
⭐   ⭐ ④ The model changes underneath you (Day 420) ⭐ without a
⭐      version bump on your side.

⭐⭐ ⇒ SO THE UNIT OF VERIFICATION CHANGES: ***NOT "DOES THIS
⭐   INPUT PRODUCE THIS OUTPUT" BUT "ACROSS N REPRESENTATIVE
⭐   INPUTS, WHAT FRACTION MEET THE CRITERIA?"***
⭐   ⭐ A test is a boolean. ⭐⭐ AN EVAL IS A ***SCORE***, ⭐ and
⭐     scores are compared between versions rather than asserted.
⭐   ⭐⭐ ⇒ AND THAT MEANS THE CI GATE CHANGES SHAPE TOO: ⭐ not
⭐     "all tests pass" but ⭐⭐ ***"THE SCORE DID NOT DROP MORE
⭐     THAN X BELOW THE BASELINE"***.

⭐ ⭐⭐ AND THE THING THAT MAKES THIS URGENT RATHER THAN
⭐   THEORETICAL: ***WITHOUT EVALS YOU CANNOT SAFELY DO ANY OF
⭐   THE THINGS THIS STAGE TELLS YOU TO DO.*** ⭐ You cannot move
⭐   to a cheaper model (Day 421), ⭐ change a prompt (Day 422),
⭐   ⭐ swap providers (Day 458), ⭐ change chunking (Day 430) or
⭐   ⭐ ship a rollout (Day 459), ⭐⭐ BECAUSE YOU CANNOT SEE THE
⭐   EFFECT. ⭐ Evals are not a quality practice; ⭐⭐ THEY ARE THE
⭐   PRECONDITION FOR EVERY OPTIMISATION IN THIS STAGE.
```

# Part 2 — ⭐⭐ Build the first one in an afternoon

```
⭐⭐ ***THE MISTAKE IS WAITING UNTIL YOU CAN BUILD A GOOD ONE.***
⭐   ⭐ 30 examples beats zero by an enormous margin. ⭐ 200 is
⭐   plenty for most tasks. ⭐⭐ NOBODY NEEDS 10,000 TO START.

⭐ ***STEP 1 — COLLECT REAL INPUTS.***
⭐   ⭐ From production logs if you have them (Day 455), ⭐ from
⭐     the sales demo, ⭐ from support tickets.
⭐   ⭐⭐ NOT INVENTED ONES. ⭐ Invented inputs are all typical, and
⭐     ⭐⭐ TYPICAL IS THE CASE THAT ALREADY WORKS.

⭐ ***STEP 2 — ⭐⭐ DELIBERATELY SKEW TOWARD FAILURE.***
⭐   ⭐ A random sample is ~90% cases you already handle, ⭐⭐ SO IT
⭐     WASTES 90% OF YOUR SIGNAL. ⭐ Compose it as:
⭐   ⭐ ~40% typical (⭐⭐ REGRESSION PROTECTION)
⭐   ⭐ ~30% edge cases (empty, huge, malformed, multilingual)
⭐   ⭐ ~20% ⭐⭐ KNOWN PAST FAILURES — ***EVERY BUG BECOMES AN EVAL
⭐     CASE, FOREVER.*** ⭐ This is the discipline that compounds.
⭐   ⭐ ~10% adversarial (Day 446)

⭐ ***STEP 3 — WRITE THE EXPECTED OUTCOME.***
⭐   ⭐ For extraction/classification: ⭐⭐ THE EXACT ANSWER. ⭐ Easy.
⭐   ⭐ For generation: ⭐⭐ NOT AN EXPECTED STRING — ⭐ a list of
⭐     ***criteria***: "mentions the refund window", "does not
⭐     promise a specific date", "under 100 words".

⭐ ***STEP 4 — STORE IT AS DATA, IN THE REPO.***
⭐   ⭐ A JSONL file next to the code. ⭐⭐ VERSION-CONTROLLED,
⭐     REVIEWABLE IN A PR, DIFFABLE. ⭐ Not a spreadsheet, not a
⭐     SaaS you will lose access to.
```

```jsonl
{"id": "inv-007", "input": {"doc": "..."}, "expect": {"total_cents": 452900, "currency": "GBP"}, "tags": ["typical"]}
{"id": "inv-041", "input": {"doc": "..."}, "expect": {"total_cents": null}, "tags": ["edge", "no-total", "bug-2314"]}
{"id": "inv-052", "input": {"doc": "..."}, "expect": {"total_cents": 91200}, "tags": ["edge", "two-totals", "regression"]}
```

# Part 3 — ⭐⭐ The four grader types, cheapest first

```
⭐⭐ ① ***EXACT / STRUCTURAL MATCH*** — ⭐ free, instant,
⭐    deterministic.
⭐    ⭐ Classification labels, extracted values, valid JSON,
⭐      required keys present, a value in an enum.
⭐    ⭐⭐ USE THIS WHEREVER THE TASK ALLOWS IT, AND DESIGN TASKS SO
⭐      IT DOES. ⭐ A task with a checkable answer is a task you
⭐      can improve.

⭐⭐ ② ***PROGRAMMATIC ASSERTIONS*** — ⭐ free, and far more
⭐    powerful than people use.
⭐    ⭐ `len(out) < 500` · `"http" not in out` ·
⭐      `all(c in SOURCE for c in out.quotes)` ·
⭐      `json.loads(out)` succeeds · `sum(items) == total`
⭐    ⭐⭐ THE QUOTE-IN-SOURCE CHECK (DAY 424) IS A HALLUCINATION
⭐      METRIC THAT COSTS NOTHING AND MOST TEAMS DO NOT HAVE ONE.

⭐⭐ ③ ***SIMILARITY / OVERLAP*** — ⭐ cheap, and weak.
⭐    ⭐ Embedding cosine against a reference (Day 419), ⭐ ROUGE,
⭐      ⭐ F1 over extracted entities.
⭐    ⭐⭐ THE HONEST CAVEAT: A HIGH SIMILARITY SCORE DOES NOT MEAN
⭐      CORRECT — ⭐ Day 419's negation problem means a summary
⭐      saying the ***opposite*** scores high. ⭐⭐ USE AS A
⭐      REGRESSION TRIPWIRE, NEVER AS A QUALITY MEASURE.

⭐⭐ ④ ***LLM-AS-JUDGE*** — ⭐ expensive, slow, subjective, ⭐⭐ AND
⭐    THE ONLY OPTION FOR OPEN-ENDED GENERATION. ⭐ Day 426 does
⭐    it properly, including its failure modes.

⭐⭐ ⇒ ***THE RULE: PUSH AS MUCH AS POSSIBLE UP TO ① AND ②.***
⭐   ⭐ A team that ends up judging everything with an LLM has
⭐   usually defined its task too loosely — ⭐⭐ AND REDEFINING THE
⭐   TASK SO PART OF IT IS CHECKABLE (ADD A `quote` FIELD, ADD A
⭐   `category`, ADD A LENGTH BOUND) IS BETTER ENGINEERING THAN A
⭐   BETTER JUDGE.
```

# Part 4 — Running them

```python
# ⭐⭐ pytest RUNS THIS FINE. You do not need a framework to start.
import json, pathlib, pytest

CASES = [json.loads(l) for l in
         pathlib.Path("evals/invoice.jsonl").read_text().splitlines()]

@pytest.mark.eval          # ⭐⭐ MARKED, SO IT DOES NOT RUN ON
@pytest.mark.parametrize(  # ⭐   EVERY COMMIT (PART 5)
    "case", CASES, ids=lambda c: c["id"])
def test_invoice(case, results):
    out = extract(case["input"]["doc"])
    ok = grade(out, case["expect"])
    results.record(case["id"], ok, case["tags"])   # ⭐⭐ AGGREGATE
    # ⭐⭐ NOTE: NO `assert` ON THE INDIVIDUAL CASE. ⭐ One failure
    # ⭐   is not a build failure — ***the aggregate score is***.

def test_aggregate_score(results):
    score = results.pass_rate()
    baseline = float(pathlib.Path("evals/baseline.txt").read_text())
    assert score >= baseline - 0.02, (      # ⭐⭐ A 2% TOLERANCE
        f"eval score {score:.3f} vs baseline {baseline:.3f}")
```

```
⭐⭐ FOUR DECISIONS IN THAT FILE THAT PEOPLE GET WRONG:
⭐ ① ⭐⭐ ***THE GATE IS THE AGGREGATE, NOT THE INDIVIDUAL CASE.***
⭐    ⭐ Asserting per-case makes the suite permanently red and
⭐    ⭐⭐ THE TEAM STOPS LOOKING AT IT WITHIN A WEEK (DAY 374's
⭐    ALERT FATIGUE, IN CI).
⭐ ② ⭐⭐ ***A TOLERANCE BAND, BECAUSE THE SCORE IS NOISY.*** ⭐ Run
⭐    the baseline three times to find your natural variance,
⭐    ⭐ then set the band above it. ⭐⭐ A GATE TIGHTER THAN YOUR
⭐    NOISE IS A FLAKY TEST (DAY 368).
⭐ ③ ⭐ ***SCORE BY TAG, NOT JUST OVERALL.*** ⭐⭐ AN OVERALL 92%
⭐    HIDING 40% ON `multilingual` IS THE FINDING, ⭐ and the
⭐    aggregate will never show it.
⭐ ④ ⭐ ***RECORD THE OUTPUTS, NOT JUST THE SCORE.*** ⭐⭐ THE DIFF
⭐    BETWEEN RUNS IS WHERE YOU LEARN WHAT ACTUALLY CHANGED.
```

# Part 5 — Where they run, and what they cost

```
⭐ ⭐⭐ THEY COST REAL MONEY AND REAL MINUTES. ⭐ 200 cases × 2
⭐   calls × $0.01 = $4 a run, ⭐ and several minutes.
⭐   ⭐⭐ SO THE TIERING FROM DAY 368 APPLIES DIRECTLY:

⭐   ⭐ ***EVERY COMMIT*** — ⭐⭐ A 15-CASE SMOKE SET, DETERMINISTIC
⭐     GRADERS ONLY, UNDER 30 SECONDS. ⭐ Catches "the prompt
⭐     template broke" and "the schema no longer parses".
⭐   ⭐ ***EVERY PR THAT TOUCHES A PROMPT, SCHEMA, MODEL OR
⭐     RETRIEVAL CONFIG*** — ⭐⭐ THE FULL SUITE. ⭐ This is the gate
⭐     that matters, ⭐⭐ AND SCOPING IT BY PATH KEEPS IT AFFORDABLE.
⭐   ⭐ ***NIGHTLY*** — full suite plus LLM-judge graders, ⭐ against
⭐     production traffic samples.
⭐   ⭐ ***BEFORE ANY MODEL OR PROVIDER CHANGE*** — ⭐⭐ NON-
⭐     NEGOTIABLE (DAYS 417, 458).

⭐ ⭐⭐ AND THE PRACTICE THAT MAKES THE SUITE IMPROVE ITSELF:
⭐   ⭐⭐ ***EVERY PRODUCTION FAILURE BECOMES AN EVAL CASE, THE
⭐   SAME DAY.*** ⭐ A user reports a bad answer → the input goes
⭐   into the JSONL with the correct expectation → ⭐⭐ IT CAN
⭐   NEVER SILENTLY REGRESS AGAIN.
⭐   ⭐ That is exactly the regression-test discipline from
⭐     Day 095, ⭐⭐ AND IT IS THE SINGLE HABIT THAT SEPARATES A
⭐     TEAM WHOSE AI FEATURE IMPROVES FROM ONE WHOSE FEATURE
⭐     DRIFTS.
```

# Part 6 — What to measure beyond "correct"

```
⭐ ⭐⭐ A SINGLE PASS RATE HIDES TOO MUCH. ⭐ Track a small
⭐   dashboard per task:
⭐   ⭐ ***ACCURACY*** by tag
⭐   ⭐⭐ ***ABSTENTION RATE*** — ⭐ how often it says "I don't
⭐     know". ⭐⭐ A ***FALLING*** ABSTENTION RATE WITH FLAT
⭐     ACCURACY MEANS IT STARTED GUESSING, ⭐ and that is a
⭐     regression nothing else detects.
⭐   ⭐⭐ ***HALLUCINATION RATE*** — quotes not in source
⭐     (Day 424).
⭐   ⭐ ***FORMAT COMPLIANCE*** — schema-valid on first attempt
⭐     (Day 424's repair rate).
⭐   ⭐ ***COST AND p95 LATENCY*** per case (Day 421) — ⭐⭐ SO A
⭐     PROMPT CHANGE THAT ADDS 40% COST FOR 1% ACCURACY IS
⭐     VISIBLE AS A TRADE RATHER THAN A WIN.
⭐   ⭐⭐ ***REFUSAL RATE*** — ⭐ over-refusal is a real regression
⭐     when a safety filter tightens (Day 417).

⭐ ⭐⭐ AND THE HONEST LIMITATION TO STATE OUT LOUD: ***AN EVAL SET
⭐   MEASURES WHAT YOU THOUGHT TO PUT IN IT.*** ⭐ It will not
⭐   catch a failure mode you have not imagined.
⭐   ⭐ ⇒ Which is why it is fed by ***production failures***
⭐     (Part 5) rather than by imagination, ⭐⭐ AND WHY IT
⭐     COMPLEMENTS RATHER THAN REPLACES MONITORING AND HUMAN
⭐     REVIEW (DAY 455).
```

# 💬 Interview

**1. ⭐⭐ "How do you test an LLM feature?"**
> ⭐ Not with unit tests — ⭐⭐ **output varies between identical calls, many different outputs are
> equally correct, "correct" is often a judgement rather than an equality, and the model changes
> underneath you without a version bump on your side.** ⭐ So the unit of verification changes: ⭐⭐ **not
> "does this input produce this output" but "across N representative inputs, what fraction meet the
> criteria?" A test is a boolean; an eval is a score, compared between versions rather than asserted.**
> ⭐ And the CI gate changes shape with it — not "all tests pass" but "the score didn't drop more than
> two points below baseline".

**2. ⭐⭐ "How would you build an eval set from nothing?"**
> ⭐ In an afternoon, ⭐⭐ **because the mistake is waiting until you can build a good one — thirty
> examples beats zero by an enormous margin.** ⭐ Real inputs from production logs or support tickets,
> never invented ones, ⭐⭐ **because invented inputs are all typical and typical is the case that
> already works.** ⭐ Then deliberately skew toward failure: ⭐⭐ **a random sample is 90% cases you
> already handle, so it wastes 90% of your signal.** ⭐ Roughly 40% typical for regression protection,
> 30% edge cases, 20% known past failures and 10% adversarial. ⭐ Expected outcomes as exact answers
> where the task allows and as criteria lists where it doesn't. ⭐⭐ **And stored as JSONL in the repo —
> version-controlled, reviewable in a PR, diffable — not a spreadsheet or a SaaS you'll lose access
> to.**

**3. "What kinds of graders are there?"**
> ⭐ Four, cheapest first. ⭐⭐ **Exact and structural match — free, instant, deterministic — for labels,
> extracted values and schema validity. Programmatic assertions, which are far more powerful than
> people use: length bounds, no URLs, JSON parses, line items sum to the total, and the
> quote-in-source check, which is a hallucination metric that costs nothing and most teams don't
> have.** ⭐ Similarity, which is cheap and weak — ⭐⭐ **a summary saying the opposite scores high,
> because of the negation problem, so it's a regression tripwire and never a quality measure.** ⭐ And
> LLM-as-judge for open-ended generation. ⭐⭐ **The rule is to push as much as possible into the first
> two — a team judging everything with an LLM has usually defined its task too loosely, and redefining
> the task so part of it is checkable is better engineering than a better judge.**

**4. ⭐⭐ "How do you gate a PR on evals?"**
> ⭐ On the aggregate score against a baseline, with a tolerance band. ⭐ Three things people get wrong:
> ⭐⭐ **asserting per-case makes the suite permanently red and the team stops looking within a week —
> that's alert fatigue in CI. The tolerance band has to exceed your natural variance, so I run the
> baseline three times to measure the noise first, because a gate tighter than your noise is just a
> flaky test. And I score by tag as well as overall — an overall 92% hiding 40% on multilingual is the
> finding, and the aggregate will never show it.** ⭐ Tiered by cost: a fifteen-case deterministic smoke
> set on every commit, the full suite on any PR touching a prompt, schema, model or retrieval config,
> and judges nightly.

**5. ⭐⭐ "What makes an eval suite get better over time?"**
> ⭐⭐ **Every production failure becomes an eval case the same day.** ⭐ A user reports a bad answer, the
> input goes into the JSONL with the correct expectation, and it can never silently regress again.
> ⭐ It's the regression-test discipline applied to a probabilistic system, ⭐⭐ **and it's the single
> habit that separates a team whose AI feature improves from one whose feature drifts.**

**6. "What do you measure besides accuracy?"**
> ⭐⭐ **Abstention rate especially — a falling abstention rate with flat accuracy means the model
> started guessing, and nothing else detects that regression.** ⭐ Hallucination rate via quotes not in
> source. ⭐ Format compliance on first attempt, which is the repair rate. ⭐⭐ **Cost and p95 latency per
> case, so a prompt change that adds 40% cost for 1% accuracy shows up as a trade rather than a win.**
> ⭐ And refusal rate, since over-refusal is a real regression when a safety filter tightens. ⭐ I'd also
> state the limitation: ⭐⭐ **an eval set measures what you thought to put in it, so it complements
> monitoring and human review rather than replacing them.**
