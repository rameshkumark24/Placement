# Day 244 🧪

**P-244** · 🧪 **Testing the frontend** — ⭐⭐ behaviour, not implementation

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a frontend test is worth having only if it would fail for a reason a user
> would care about — which rules out testing that a component called `setState`, and rules in testing
> that clicking Save shows a confirmation and that a failed request shows a retry.**
>
> Today: ⭐ the pyramid corrected, testing behaviour, ⭐⭐ mocking at the network boundary, and the
> handful of E2E tests that earn their cost.

---

# Part 1 — The shape

```
⭐⭐ THE FRONTEND PYRAMID IS SQUATTER THAN THE BACKEND ONE

⭐   ⭐ E2E (Playwright) ......... 5–10 total ⇒ ⭐⭐ THE CRITICAL PATHS
⭐   ⭐⭐ COMPONENT/INTEGRATION ... THE BULK ⇒ ⭐ render a real tree,
⭐        (Testing Library)                   click real things
⭐   ⭐ UNIT ..................... only pure logic ⇒ formatters,
⭐        reducers, validators, date maths

⭐   ⇒ ⭐⭐ WHY SQUAT: A COMPONENT IN ISOLATION IS RARELY WHERE THE
⭐     BUG IS. Frontend bugs live in the WIRING — the wrong prop,
⭐     the missing state, the request that never fired. ⭐ Integration
⭐     tests exercise wiring; unit tests on components do not.
```

| ⭐ Worth testing | ⭐⭐ Theatre |
|---|---|
| The form submits and shows a confirmation | ⭐ That a `<Button>` renders its children |
| A failed request shows an error + retry | ⭐⭐ That `useState` was called |
| The empty state appears with zero results | Snapshot tests of whole pages |
| Validation blocks a bad email | ⭐ That a `className` is `"btn-primary"` |
| ⭐ Permissions hide the delete button | Anything only reachable via `.instance()` |

> ⭐⭐ **Snapshots deserve their own warning.** A whole-page snapshot fails on every legitimate change,
> so the reviewer's routine becomes "run `-u`, glance, commit" — which is a test that trains people to
> approve diffs without reading them. **Small, targeted snapshots of stable output only.**

# Part 2 — ⭐⭐ Query the way a user would

```jsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("shows an error and lets the user retry", async () => {
  server.use(http.post("/api/orders", () => HttpResponse.error()));
  render(<OrderForm />);

  await userEvent.type(screen.getByLabelText(/email/i), "a@b.com");
  await userEvent.click(screen.getByRole("button", { name: /save/i }));

  expect(await screen.findByRole("alert")).toHaveTextContent(/could not save/i);
  expect(screen.getByRole("button", { name: /retry/i })).toBeEnabled();
});
```

```
⭐⭐ THE QUERY PRIORITY — AND WHY IT IS ALSO AN ACCESSIBILITY TEST

⭐   ① ⭐⭐ getByRole      ⇒ how assistive tech finds it. USE THIS.
⭐   ② getByLabelText     ⇒ form fields
⭐   ③ getByText          ⇒ non-interactive content
⭐   ④ ⭐ getByTestId      ⇒ LAST RESORT. It tests nothing about
⭐        whether a user can find the element.

⭐   ⇒ ⭐⭐ IF YOU CANNOT SELECT IT BY ROLE, A SCREEN READER USER
⭐     PROBABLY CANNOT FIND IT EITHER (Day 239).
⭐     ⭐ YOUR TEST SUITE HAS JUST BECOME AN ACCESSIBILITY LINTER
⭐       FOR FREE. That is the strongest argument for this library.
```

| ⭐ Rule | |
|---|---|
| **`userEvent`, not `fireEvent`** | ⭐ It fires the *real* sequence — pointerdown, focus, keydown, input. `fireEvent.change` skips reality. |
| **`findBy*` for async** | ⭐⭐ Retries until it appears. `getBy*` fails instantly on anything async. |
| **Never assert on state** | ⭐ Assert on what is rendered. State is implementation. |
| **`await` everything from `userEvent`** | ⭐ It is async now; missing awaits cause flakes |

# Part 3 — ⭐⭐ Mock at the network, not the module

```javascript
// ❌ mocking the module — couples the test to your code's structure
vi.mock("./api", () => ({ getUsers: vi.fn(() => [{id:1}]) }));
// ⭐⭐ RENAME THE FUNCTION AND THE TEST STILL PASSES WHILE THE APP
//    IS BROKEN. It asserted a call, not a behaviour.

// ✅ MSW — intercept the HTTP request itself
const server = setupServer(
  http.get("/api/users", () => HttpResponse.json([{ id: 1, name: "Ada" }])),
);
```

| ⭐ Why the network boundary | |
|---|---|
| **Your code runs unchanged** | ⭐⭐ Wrapper, parsing, error mapping, retry — **all exercised**. Module mocks skip all of it. |
| **Refactors don't break tests** | ⭐ Rename anything internal; the HTTP contract is what you asserted |
| **Errors are realistic** | ⭐⭐ Return a real 500 with an HTML body and confirm Day 217's wrapper handles it |
| **Same handlers in dev** | ⭐ Develop against a backend that does not exist yet |

```javascript
// ⭐⭐ the tests that matter most are the failure ones
http.get("/api/users", () => new HttpResponse(null, { status: 500 }));
http.get("/api/users", () => HttpResponse.json({...}, { status: 403 }));
http.get("/api/users", async () => { await delay(5000); ... });  // ⭐ slow
http.get("/api/users", () => HttpResponse.error());              // ⭐ offline
```

> ⭐ **Most frontend suites test only the success path**, which is the path that already works. **The
> four handlers above are where the value is** — and they are the four states of Day 240.

# Part 4 — The E2E tests that earn their cost

```
⭐⭐ E2E IS EXPENSIVE: SLOW, FLAKY, AND IT FAILS FOR REASONS THAT
⭐   ARE NOT BUGS. ⭐ SO KEEP IT TO THE PATHS WHERE FAILURE IS
⭐   UNACCEPTABLE:

⭐   ① ⭐⭐ SIGN UP → LOG IN → LOG OUT
⭐   ② ⭐⭐ THE ONE WORKFLOW YOUR APP EXISTS FOR, END TO END
⭐   ③ ⭐ PAYMENT / anything irreversible
⭐   ④ ⭐ ONE PERMISSION TEST: the wrong user CANNOT reach the thing
⭐        (Day 236, now proved from the outside)

⭐   ⇒ ⭐⭐ 5–10 TESTS. ⭐ A 200-TEST E2E SUITE IS A SUITE PEOPLE
⭐     RE-RUN UNTIL IT PASSES, WHICH IS THE SAME AS HAVING NONE.
```

| ⭐ Flake control | |
|---|---|
| **Never `waitForTimeout`** | ⭐⭐ Wait for a *condition* — a visible element, a network response |
| **Reset state per test** | ⭐ A seeded DB or an API call, not "run them in order" |
| **Retry once in CI, zero locally** | ⭐ A test that needs three retries is telling you something |
| **⭐⭐ Trace on failure** | Playwright's trace viewer turns "flaky in CI" into a video you can watch |

## Today's build

1. Write three component tests using **role queries only**. ⭐⭐ Where you cannot find an element by role, **fix the component**, not the test.
2. ⭐ Set up MSW. Convert any module mocks to network handlers.
3. ⭐⭐ **Write the four failure handlers** — 500, 403, slow, offline — and test all four states.
4. ⭐ Try `fireEvent.change` on a controlled input, then `userEvent.type`. Note what the first one skips.
5. ⭐⭐ Write **one** E2E test for your critical path. Time it. **Then write the wrong-user permission test.**
6. ⭐ Add a `waitForTimeout`, watch it flake under CI load, replace it with a condition.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you test a frontend?"**

Give the filter first, because it explains everything else. **A test is worth having only if it would
fail for a reason a user cares about. That rules out asserting a component called setState or that a
button renders its children, and rules in that clicking Save shows a confirmation and that a failed
request shows a retry.**

Then the shape and why it differs from the backend. **The pyramid is squatter — mostly integration
tests that render a real tree and click real things, only a handful of end-to-end, and unit tests
reserved for pure logic. Frontend bugs live in the wiring: the wrong prop, the missing state, the
request that never fired. A component tested in isolation is rarely where the bug is.**

Then the technique with the free benefit. **I query by role, the way assistive technology does. If I
can't select an element by role, a screen reader user probably can't find it either — so the suite
becomes an accessibility linter for free. Test ids are a last resort because they test nothing about
whether a user can find the thing.**

Then mocking, which is where most suites go wrong. **I mock at the network with MSW, not the module.
A module mock means renaming a function leaves the test passing while the app is broken — it asserted
a call, not a behaviour. Intercepting HTTP means my wrapper, parsing, error mapping and retry all
actually run. And the handlers that matter are the failure ones: a 500 with an HTML body, a 403, a slow
response, and offline. Most suites test only the success path, which is the path that already works.**

Close on E2E discipline. **Five to ten tests on paths where failure is unacceptable — auth, the core
workflow, anything irreversible, and one proving the wrong user can't reach a protected thing. A
two-hundred-test E2E suite is one people re-run until it passes, which is the same as having none.**
