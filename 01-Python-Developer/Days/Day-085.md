# Day 085

**L-085** · ⭐ **The three trees** — the index, `add -p`, commit messages, and ⭐⭐ **what to do when you commit a secret**

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: Git has three copies of your project — the working tree, the index and
> HEAD — and every everyday command is a move between two of them, which is why one diagram replaces
> a dozen memorised incantations.**
>
> ⭐ And the part of today that will one day matter more than all the rest: **a committed secret is
> not removed by deleting it. Rotate first, rewrite second.**

# Part 1 — ⭐⭐ The three trees

```
⭐⭐            WORKING TREE          INDEX (staging)             HEAD
⭐              what you edit    │  what the NEXT commit    │  what the LAST
⭐              (real files)     │  will contain (.git/index)│  commit contained
⭐
⭐        ────── git add ──────▶
⭐        ◀──── git restore ────
⭐                                ───── git commit ─────▶
⭐        ◀────────── git restore --source=HEAD ──────────
⭐        ◀────────── git reset --hard (⚠️ all three) ─────
```

| ⭐ Command | ⭐⭐ Compares / moves |
|---|---|
| ⭐⭐ `git diff` | ⭐⭐ working tree **vs index** — *what I have not staged* |
| ⭐⭐ `git diff --staged` | ⭐⭐ index **vs HEAD** — ⭐ **what I am about to commit** |
| `git diff HEAD` | working tree vs HEAD — everything |
| `git status` | ⭐ a summary of both of the above at once |
| `git add f` | working tree → index |
| ⭐ `git restore f` | index → working tree (⚠️ **discards your edit**) |
| ⭐ `git restore --staged f` | HEAD → index (unstage; keeps your edit) |
| `git commit` | index → a new commit |

```
⭐⭐ WHY DOES THE INDEX EXIST AT ALL? THE QUESTION IS WORTH ANSWERING PROPERLY,
⭐   BECAUSE IT IS THE ONE THING GIT HAS THAT MOST TOOLS DO NOT:
⭐   ⇒ so that a COMMIT IS SOMETHING YOU COMPOSE, not "whatever is on disk right now".
⭐   ⇒ ⭐⭐ you fixed a bug and, along the way, renamed a variable and deleted a
⭐        stale comment. ⭐ Those are TWO changes. The index lets you commit them
⭐        as two commits — ⭐⭐ so that one can be reverted, reviewed, or bisected
⭐        without the other.
⭐   ⇒ ⭐ "the working tree is your desk, the index is the envelope, the commit is
⭐        posting it."
```

⭐⭐ **`git status` is the tool that reads this diagram back to you** — untracked, "changes not staged"
(working tree vs index) and "changes to be committed" (index vs HEAD) are literally the three columns.
⭐ Once you see that, `status` stops being noise.

# Part 2 — ⭐⭐ `git add -p`, and atomic commits

```bash
git add -p            # ⭐⭐ THE SINGLE HIGHEST-VALUE GIT COMMAND. Stage hunk by hunk.
# y stage · n skip · s SPLIT this hunk smaller · e EDIT it by hand · q quit
git add -p file.py    # ⭐ one file
git diff --staged     # ⭐⭐ ALWAYS. Read exactly what you are about to commit.
git commit            # ⭐ no -m ⇒ your editor ⇒ you write a real message
```

```
⭐⭐ WHAT `add -p` ACTUALLY BUYS YOU — THREE THINGS, AND THE THIRD IS THE REAL ONE:
⭐  1. ⭐ ATOMIC COMMITS: one logical change each.
⭐  2. ⭐ NO STRAY DEBUG LINES. print(), a commented-out block, a hardcoded
⭐       localhost URL — ⭐⭐ you see every hunk, so you cannot ship them by accident.
⭐  3. ⭐⭐ IT IS A SELF-REVIEW. You read your own diff before anyone else does,
⭐       and you WILL find something. ⭐ This is the cheapest quality gate in
⭐       existence and it costs about ninety seconds.
⭐
⭐⭐ ⇒ AND THE OPPOSITE HABIT IS THE CAUSE OF MOST ACCIDENTS: `git add .` commits
⭐     whatever happens to be lying around — .env, a 200 MB CSV, a private key,
⭐     someone else's half-finished edit. ⭐⭐ Almost every leaked-secret story
⭐     starts with `git add .`.
```

| ⭐ Atomic commit | ⭐ Why it pays, concretely |
|---|---|
| ⭐⭐ One logical change | ⭐⭐ `git revert` undoes exactly it, and nothing else |
| Builds and passes tests | ⭐⭐ **`git bisect` is only usable if every commit works** (Day 087) |
| Small | ⭐ reviewable — the review-quality curve collapses past a few hundred lines (Day 088) |
| ⭐ Explains itself | ⭐ `git log` becomes documentation you got for free |

⭐⭐ **The bisect argument is the one that converts people.** A commit that mixes a refactor with a bug
fix is a commit you cannot revert cleanly and cannot bisect through — **so the discipline pays off at
exactly the worst moment: 2 a.m., six months later, when someone is bisecting to find your bug.**

# Part 3 — ⭐ Commit messages that survive

```
⭐⭐ Add per-IP rate limiting to the login endpoint        ⭐ ≤50 chars, IMPERATIVE
                                                          ⭐ blank line — mandatory
Brute-force attempts were reaching the password hasher     ⭐⭐ WHY, not what.
directly, which made each attempt cost 100 ms of CPU.      ⭐ The diff already
                                                           says what.
Uses a fixed window in Redis rather than a token bucket
because we only need coarse protection here and the
window is far simpler to reason about under failure.       ⭐⭐ THE ALTERNATIVE
                                                           REJECTED, AND WHY.
Refs: #431
```

```
⭐⭐ THE RULE, AND ITS JUSTIFICATION:
⭐   THE DIFF SAYS WHAT CHANGED. ONLY THE MESSAGE CAN SAY WHY.
⭐   ⇒ ⭐⭐ "Fix bug" is a message that will cost someone an hour in two years.
⭐   ⇒ ⭐ IMPERATIVE MOOD ("Add", not "Added") because Git's own generated
⭐        messages are imperative — "Merge branch", "Revert commit" — so your
⭐        history reads consistently.
⭐   ⇒ ⭐⭐ THE TEST: if someone bisects to this commit at 2 a.m., does the message
⭐        tell them whether they have found the cause or just a nearby change?
```

| ⭐ Bad | ⭐ Why it fails |
|---|---|
| `fix` · `wip` · `updates` | ⭐ Carries no information at all |
| `Fixed the thing we discussed` | ⭐ The conversation is gone; the commit is forever |
| ⭐ A 400-line commit called `refactor` | ⭐⭐ Unreviewable, unrevertable, unbisectable |
| `Add validation` on a 12-file diff | ⭐ That is several commits wearing a trenchcoat |

⭐ **Conventional Commits** (`feat:`, `fix:`, `chore:`, `BREAKING CHANGE:`) is worth adopting **if** you
generate changelogs or version automatically. ⭐⭐ **Otherwise it is ceremony** — a clear imperative
subject and a *why* paragraph beat a well-prefixed empty message every time.

```bash
git commit --amend              # ⭐ fix the LAST commit — ⚠️ new hash (Day 084) ⇒ local only
git commit --amend --no-edit    # ⭐ "I forgot one line"
git commit --fixup <sha>        # ⭐⭐ marks a fix for a specific commit ⇒ auto-squashed (Day 086)
```

# Part 4 — ⭐ `.gitignore`, and the trap in it

```gitignore
# ⭐ Python
__pycache__/
*.py[cod]
.venv/
*.egg-info/

# ⭐⭐ Secrets and local config
.env
.env.*
!.env.example          # ⭐⭐ NEGATE — commit the TEMPLATE, never the file
*.pem
*.key

# ⭐ Tooling / data
.pytest_cache/
.mypy_cache/
.ruff_cache/
htmlcov/
.coverage
*.sqlite3
data/raw/
.DS_Store
.idea/
```

```
⚠️⚠️ ⭐⭐ THE TRAP THAT COSTS EVERYONE AN HOUR ONCE:
⭐   .gitignore ONLY AFFECTS UNTRACKED FILES.
⭐   ⇒ ⭐⭐ Once a file is TRACKED, adding it to .gitignore does NOTHING. Git keeps
⭐        committing your changes to it, and you will swear the file is being ignored.
⭐   ⇒ ⭐⭐ THE FIX:  git rm --cached .env    (removes it from the INDEX, keeps it
⭐        on disk) ⇒ then commit. ⭐ From then on it is untracked, so the ignore applies.
⭐   ⇒ ⚠️⚠️ AND NOTE: THAT DOES NOT REMOVE IT FROM HISTORY. See Part 5.
⭐
⭐ THREE PLACES IGNORES LIVE, and using the right one is a courtesy:
⭐   .gitignore              ⭐ committed — the project's rules (build output, .env)
⭐   .git/info/exclude       ⭐ local, uncommitted — ⭐⭐ YOUR scratch files
⭐   core.excludesFile       ⭐⭐ global — your EDITOR and OS junk (.idea/, .DS_Store)
⭐   ⇒ ⭐ your editor's directory does not belong in someone else's .gitignore.
```

```bash
git check-ignore -v path/to/file    # ⭐⭐ WHICH RULE is ignoring this? Ends the argument.
git status --ignored                # ⭐ what is being hidden from you
git add -f file                     # ⭐ force-add something ignored (rare, deliberate)
```

# Part 5 — ⭐⭐ You committed a secret. What now?

```
⭐⭐ FIRST, THE FACT THAT DECIDES EVERYTHING — AND IT COMES STRAIGHT FROM DAY 084:
⭐   THE BLOB IS CONTENT-ADDRESSED AND STILL REACHABLE FROM THE OLD COMMIT.
⭐   ⇒ ⭐⭐ DELETING THE FILE IN A NEW COMMIT REMOVES NOTHING. The secret is:
⭐        · in .git/objects on every machine that has ever cloned or pulled
⭐        · ⭐⭐ on GitHub's servers — reachable by SHA even after a force-push,
⭐          and cached in forks, PRs and the events API
⭐        · in CI caches, in backups, in anyone's editor history
⭐   ⇒ ⭐⭐ AND IF IT WAS PUSHED TO A PUBLIC REPO, ASSUME IT WAS SCRAPED WITHIN
⭐        MINUTES. Bots watch the public event firehose continuously. This is
⭐        not a hypothetical: leaked AWS keys are exploited in single-digit minutes.
```

```
⭐⭐ THE RESPONSE, IN THIS ORDER. THE ORDER IS THE ANSWER:
⭐
⭐ 1. ⭐⭐ ROTATE THE CREDENTIAL. NOW. BEFORE ANYTHING ELSE.
⭐      ⇒ ⭐⭐ THIS IS THE ONLY STEP THAT ACTUALLY MAKES YOU SAFE. Revoke the key,
⭐        issue a new one. ⭐ Every other step is tidying up.
⭐      ⇒ ⭐ if you only have time for one thing, this is the one thing.
⭐ 2. AUDIT: did anything use it? Check the provider's access logs for the window.
⭐ 3. REWRITE HISTORY, if the repo is private or the exposure was brief:
⭐      git filter-repo --path .env --invert-paths        ⭐ (or the BFG)
⭐      ⇒ ⭐⭐ this REWRITES EVERY COMMIT ⇒ every hash changes ⇒ force-push ⇒
⭐        ⭐ EVERY COLLABORATOR MUST RE-CLONE. It is disruptive, and it is
⭐        still worth doing. ⭐ Ask GitHub Support to purge cached views.
⭐ 4. ⭐ PREVENT: gitleaks / detect-secrets in pre-commit (Day 099), .env ignored
⭐      from the first commit, ⭐⭐ and stop using `git add .`.
⭐
⭐⭐ ⇒ THE INTERVIEW ANSWER IN ONE LINE: "rotate first, rewrite second — because
⭐     rewriting history does not un-leak a key that has already been read."
```

⭐⭐ **The design lesson, which is the part that generalises:** secrets should never have been in a
file the repo can see. **Environment variables** (Day 079), **a secrets manager**, or a
mounted secret — and `.env.example` committed with the *shape* and none of the values. ⭐ Stage 4's
`pydantic-settings` makes this the path of least resistance.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`git add .` reflexively** | ⭐⭐ `git add -p`. Almost every leak starts with `add .`. |
| Committing without reading the diff | ⭐ `git diff --staged` first. Ninety seconds. |
| ⭐ Adding a tracked file to `.gitignore` | ⭐⭐ Ignores only apply to **untracked** files. `git rm --cached`. |
| ⭐⭐ **Deleting a secret in a new commit** | ⭐⭐ It is still in history. **Rotate the credential.** |
| Rewriting history before rotating | ⭐⭐ Wrong order — the key may already have been read. |
| `-m "fix"` | ⭐ Costs someone an hour later. |
| ⭐ Describing *what* in the message | ⭐⭐ The diff says what. Say **why**. |
| Mixing a refactor and a fix | ⭐⭐ Unrevertable, and it poisons `bisect`. |
| ⭐ `.idea/` in the project `.gitignore` | ⭐ Your editor is your business — use the global one. |
| Committing `.env` | ⭐ Commit `.env.example` with the keys and no values. |
| `--amend` on a pushed commit | ⭐ New hash ⇒ force-push ⇒ only for your own branch. |

## Interview questions

**Q: What is the staging area for?**
> So a commit is something you compose rather than a snapshot of whatever's on disk. In practice you
> fix a bug and also rename a variable and delete a stale comment — that's two or three changes, and
> the index lets you commit them separately so each one can be reviewed, reverted or bisected
> independently. Concretely, `git diff` shows working tree against index, `git diff --staged` shows
> index against HEAD, and that second one is what I read before every commit.

**Q: Why do you use `git add -p`?**
> Three reasons, and the third is the real one. It produces atomic commits. It stops stray debug
> lines — a `print`, a commented block, a hardcoded localhost — from shipping, because I see every
> hunk. And it's a self-review: I read my own diff before a colleague does, and I nearly always find
> something. Ninety seconds, and it's the cheapest quality gate available. The habit it replaces,
> `git add .`, is how `.env` files and 200 MB CSVs get committed.

**Q: What makes a good commit message?**
> A short imperative subject, a blank line, then a body that explains *why* — because the diff already
> says what. I'd include the alternative I rejected and the reason, since that's the thing nobody can
> reconstruct later. My test is: if someone bisects to this commit at 2 a.m., does the message tell
> them whether they've found the cause or just a nearby change? "Fix bug" fails that test and will
> cost somebody an hour.

**Q: You've added `.env` to `.gitignore` but Git keeps showing it as modified.**
> Because `.gitignore` only applies to untracked files, and that one is already tracked. `git rm
> --cached .env` removes it from the index while leaving it on disk, and after that commit the ignore
> takes effect. The important follow-up is that this does *not* remove it from history — every past
> commit still contains the blob — so if it held real credentials, the actual response is to rotate
> them.

**Q: You've just pushed an AWS key to a public repo. Walk me through the next ten minutes.**
> Rotate the key first. Revoke it, issue a new one, and only then do anything else — because bots
> watch the public event firehose and leaked cloud keys get exploited within minutes, so a rewrite
> that takes me twenty minutes is twenty minutes too late. Then check the provider's access logs for
> that window to see whether it was used. Then rewrite history with `filter-repo` or the BFG and
> force-push, knowing that every collaborator has to re-clone and that GitHub may still serve the old
> object by SHA until support purges it. Then prevention: `gitleaks` in pre-commit, `.env` ignored
> from the first commit, and no more `git add .`. The one-line version is "rotate first, rewrite
> second" — rewriting history doesn't un-leak a key someone already read.

## Mini task

1. ⭐⭐ Edit a file, `git add` it, edit it again. **Run all three diffs** and predict each before you
   look.
2. ⭐⭐ Make two unrelated changes in one file and split them into two commits with `git add -p`,
   using `s` to split a hunk.
3. ⭐ Stage something, then `git restore --staged`. Then `git restore` and note what you lost.
4. ⭐⭐ Write a commit message with a real *why* paragraph including a rejected alternative. **Read it
   back a week later.**
5. ⭐ `git log --oneline -20` on a repo you use. **Count how many messages tell you why.**
6. ⭐⭐ Commit a file, then add it to `.gitignore`, then keep editing it. **Watch the ignore fail.**
   Fix with `git rm --cached`.
7. ⭐ `git check-ignore -v` on something that is being ignored unexpectedly.
8. ⭐ Move your editor's directory out of the project `.gitignore` and into `core.excludesFile`.
9. ⭐⭐ **In a throwaway repo:** commit a fake key, delete it in a later commit, then **find it again**
   with `git log --all -p -- secrets.txt` and `git cat-file -p <blob>`. **This is the demonstration
   that deletion does nothing.**
10. ⭐⭐ Remove it properly with `git filter-repo` and confirm the blob is gone.
11. ⭐ Add `gitleaks` (or `detect-secrets`) as a pre-commit hook and try to commit a fake key.

## 🎙️ Articulation drill

Record two minutes: **"You pushed a `.env` with a live database password to a public repo ten minutes
ago."**

⭐ **Lead with the order, because the order is the entire answer** — an interviewer is checking
whether you reach for the Git command or the rotation: **"the first thing is to rotate the credential.
Not clean the history — rotate. Revoke that password, issue a new one, deploy it. Everything else is
tidying up, and none of it makes me safe."**

⭐⭐ **Then justify it with the mechanism:** *"because the secret is already out. The blob is
content-addressed and reachable from the old commit, so it's in `.git/objects` on every clone, on
GitHub's servers where it can be fetched by SHA even after a force-push, and in any fork or CI cache.
And on a public repo it was almost certainly scraped already — bots watch the public event stream, and
leaked cloud keys get used within minutes. A history rewrite that takes me twenty minutes is twenty
minutes too late."*

⭐ **Then the rest, briefly:** *"check the provider's access logs for that window to see if it was
used. Then rewrite with `filter-repo` and force-push, accepting that everyone has to re-clone, and ask
support to purge the cached views. Then prevention — `gitleaks` in pre-commit, `.env` ignored from the
first commit, and stop using `git add .`, because that's how it happened."*

⭐⭐ **Close on the design point:** *"though the real fix is that the secret should never have been in
a file the repo can see. Environment variables or a secrets manager, and a committed `.env.example`
that has the keys and none of the values."*
