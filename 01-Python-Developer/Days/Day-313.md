# Part 2 — ⭐⭐ The interface is the design

```python
K = TypeVar("K"); V = TypeVar("V")

class EvictionPolicy(Protocol[K]):
    def record_access(self, key: K) -> None: ...
    def record_insert(self, key: K) -> None: ...
    def record_remove(self, key: K) -> None: ...
    def evict_candidate(self) -> K: ...      # ⭐⭐ raises if empty
```

```
⭐⭐ WHY THIS SPLIT IS THE WHOLE ANSWER:
⭐   ⭐ THE CACHE owns storage, capacity, TTL and locking.
⭐   ⭐ THE POLICY owns ***ONLY*** the ordering question:
⭐     "which key would you drop next?"
⭐   ⇒ ⭐⭐ LRU, LFU, FIFO AND RANDOM ARE NOW FOUR SMALL
⭐     CLASSES AND THE CACHE NEVER CHANGES. ⭐ That is the
⭐     difference between answering the question and answering
⭐     the interview.

⭐ ⭐ AND NOTE WHAT THE POLICY DOES ***NOT*** GET: the values.
⭐   ⭐⭐ IT SEES KEYS ONLY, SO IT CANNOT ACCIDENTALLY HOLD A
⭐   REFERENCE THAT PREVENTS GARBAGE COLLECTION — ⭐ a real
⭐   memory leak in cache implementations, and a good detail to
⭐   state.
```

# Part 3 — ⭐⭐ LRU: the data structure, and why

```
⭐⭐ REQUIREMENT: O(1) get, O(1) put, O(1) eviction.
⭐   ⭐ A dict alone ⇒ ⭐ O(1) lookup, ⭐⭐ NO ORDER.
⭐   ⭐ A list alone ⇒ ⭐ order, ⭐⭐ O(n) MOVE-TO-FRONT.
⭐   ⇒ ⭐⭐ HASH MAP → NODE, PLUS A DOUBLY-LINKED LIST.
⭐     ⭐ Doubly linked ***because*** you must unlink a node
⭐       found via the map, in O(1), which needs its
⭐       predecessor — ⭐⭐ THAT SENTENCE IS THE ENTIRE REASON,
⭐       AND IT IS THE ONE PEOPLE CANNOT GIVE.
⭐   ⭐ Sentinel head and tail nodes ⇒ ⭐ no null checks
⭐     anywhere, which removes most of the bugs.

⭐⭐ AND THE PYTHON REALITY, WHICH YOU SHOULD SAY OUT LOUD:
⭐   ⭐ `OrderedDict.move_to_end()` IS EXACTLY THIS, IN C.
⭐   ⭐ `functools.lru_cache` exists and is faster than anything
⭐     you will write.
⭐   ⇒ ⭐⭐ "IN PRODUCTION I WOULD USE `OrderedDict`; I'LL WRITE
⭐     THE LINKED LIST BECAUSE THAT IS WHAT IS BEING ASKED" —
⭐     ⭐ saying that scores, because it shows you know the
⭐       standard library and are not confusing an exercise with
⭐       engineering.
```

# Part 4 — ⭐⭐ 15–30: the code

```python
class LRUPolicy(Generic[K]):
    def __init__(self) -> None:
        self._od: OrderedDict[K, None] = OrderedDict()
    def record_access(self, key): self._od.move_to_end(key)
    def record_insert(self, key): self._od[key] = None
    def record_remove(self, key): self._od.pop(key, None)
    def evict_candidate(self) -> K:
        if not self._od: raise CacheEmpty()
        return next(iter(self._od))          # ⭐ oldest

@dataclass
class Entry(Generic[V]):
    value: V
    expires_at: float | None

class Cache(Generic[K, V]):
    def __init__(self, capacity: int, policy: EvictionPolicy[K],
                 clock: Callable[[], float] = time.monotonic):
        self._data: dict[K, Entry[V]] = {}
        self._cap, self._policy, self._clock = capacity, policy, clock
        self._lock = RLock()
        self.hits = self.misses = self.evictions = self.expired = 0

    def get(self, key: K) -> V:
        with self._lock:
            e = self._data.get(key)
            if e is None:
                self.misses += 1; raise KeyError(key)
            if e.expires_at is not None and self._clock() > e.expires_at:
                self._remove(key); self.expired += 1; self.misses += 1
                raise KeyError(key)          # ⭐⭐ LAZY EXPIRY
            self._policy.record_access(key)
            self.hits += 1
            return e.value

    def put(self, key: K, value: V, ttl: float | None = None) -> None:
        with self._lock:
            if key in self._data:
                self._data[key] = self._mk(value, ttl)
                self._policy.record_access(key); return
            while len(self._data) >= self._cap:      # ⭐⭐ while, not if
                victim = self._policy.evict_candidate()
                self._remove(victim); self.evictions += 1
            self._data[key] = self._mk(value, ttl)
            self._policy.record_insert(key)
```

```
⭐⭐ SIX SCORED DETAILS:
⭐   ⭐ `while len >= cap` NOT `if` — ⭐⭐ CAPACITY CAN SHRINK,
⭐     AND A BYTE-BASED CACHE MAY NEED SEVERAL EVICTIONS FOR ONE
⭐     LARGE ENTRY. ⭐ `if` is correct only for the exact
⭐     problem you were asked and wrong for the follow-up.
⭐   ⭐ ⭐⭐ LAZY EXPIRY ON READ, not a background sweeper —
⭐     ⭐ simpler, no thread, ⭐⭐ AND THE HONEST COST: EXPIRED
⭐     ENTRIES OCCUPY CAPACITY UNTIL TOUCHED. ⭐ Mention both.
⭐   ⭐ A CLOCK PASSED IN ⇒ TTL testable without sleeping.
⭐   ⭐ `get` RAISES rather than returning `None` — ⭐⭐
⭐     OTHERWISE A CACHED `None` IS INDISTINGUISHABLE FROM A
⭐     MISS, which is a real and much-hit bug.
⭐   ⭐ AN UPDATE COUNTS AS AN ACCESS, and does not evict.
⭐   ⭐ STATS AS FIELDS ⇒ ⭐ hit ratio is available, ⭐⭐ AND
⭐     YOU SHOULD ADD DAY 266'S CAVEAT UNPROMPTED: IT IS A
⭐     VANITY METRIC UNLESS YOU KNOW THE COST OF A MISS.
```

# Part 5 — ⭐⭐ 30–40: thread safety and the stampede

```
⭐⭐ ① THE LOCK. ⭐ One lock around the whole cache is correct
⭐     and coarse. ⭐⭐ FINER LOCKING IS NOT WORTH IT: the
⭐     critical section is a few dict operations, so contention
⭐     is low and sharding adds a consistency problem to save
⭐     nanoseconds. ⭐ Say that rather than defending "just a
⭐     lock" apologetically.
⭐   ⭐ `RLock` here is honest, because `get` may call `_remove`.

⭐⭐ ② ⭐⭐ THE STAMPEDE (Day 266) — THE ANSWER THAT SEPARATES
⭐     THIS FROM A DSA ANSWER:
⭐     ⭐ One hot key expires; 2,000 concurrent readers all miss
⭐       and all recompute. ⭐⭐ THE CACHE IS AT A 99.9% HIT
⭐       RATIO WHILE IT TAKES THE DATABASE DOWN.
⭐     ⇒ ⭐ `get_or_compute(key, loader)` with a ***per-key***
⭐       lock: one thread computes, the rest wait.
⭐     ⇒ ⭐⭐ AND THE PER-KEY LOCK DICTIONARY ITSELF NEEDS
⭐       CLEANING UP, or it becomes an unbounded map keyed by
⭐       every key ever requested — ⭐ a leak inside the fix.

⭐⭐ ③ THE THUNDERING HERD ON A COLD CACHE — ⭐ jitter on TTLs
⭐     so keys written together do not expire together.

⭐⭐ ④ MULTI-PROCESS (Day 310): ⭐⭐ THE LOCK PROTECTS NOTHING
⭐     ACROSS PROCESSES, AND EACH PROCESS HAS ITS OWN CACHE —
⭐     ⭐ N copies, N staleness windows, and no invalidation
⭐     (Day 266's `lru_cache` warning). ⭐ That is the point at
⭐     which the answer is Redis, and the design becomes a
⭐     network cache with different failure modes.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Coding immediately | You finish in ten minutes and face thirty-five you didn't prepare for. |
| One hardcoded eviction policy | Policy as an interface is the actual design question. |
| Giving the policy access to values | It only needs keys, and holding values prevents collection. |
| Not explaining *why* doubly linked | You must unlink a node found via the map in O(1), which needs its predecessor. |
| Pretending `OrderedDict` doesn't exist | Say you'd use it in production and write the list because that's the ask. |
| `if` instead of `while` when evicting | Wrong the moment capacity shrinks or entries have sizes. |
| A background expiry thread by default | Lazy expiry is simpler; state its cost instead of hiding it. |
| `time.time()` inside the cache | Pass a clock or TTL is untestable without sleeping. |
| `get` returning `None` | A cached `None` becomes indistinguishable from a miss. |
| No stats | Hits, misses, evictions and expiries are what make it operable. |
| Quoting hit ratio without cost-of-miss | It's a vanity metric (Day 266). |
| Apologising for one coarse lock | It's correct; the critical section is tiny and sharding buys nanoseconds. |
| No stampede answer | The cache takes the database down at a 99.9% hit ratio. |
| A per-key lock map that's never cleaned | A leak inside the fix. |
| Assuming the lock helps across processes | N processes means N caches and no invalidation. |
| LFU without ageing | Last week's hot key keeps its count forever. |

## Interview questions

**Q: What's actually being assessed here?**

> Not the hash map and linked list — everyone can write that in ten minutes, which is why finishing it
> fast leaves you with thirty-five minutes of questions you haven't prepared for. The design question
> is whether eviction is a pluggable policy, how TTL interacts with capacity, what happens under
> concurrency, and what the cache does to the system behind it. So my first question is whether the
> policy is fixed, because that decides whether this is one class or an interface with four
> implementations.

**Q: Why a doubly linked list?**

> Because eviction needs the least-recently-used node in O(1), and access needs to move an arbitrary
> node — found via the hash map — to the front, also in O(1). Unlinking a node in O(1) requires its
> predecessor, which is exactly what a singly linked list can't give you. That sentence is the whole
> justification, and it's the one candidates usually can't produce. In Python I'd say plainly that
> `OrderedDict.move_to_end` is this structure implemented in C, and I'd use it in production — I'm
> writing the list because it's what's being asked.

**Q: What's the most dangerous thing about a cache?**

> The stampede. One hot key expires, every concurrent reader misses simultaneously, and they all
> recompute — so the cache takes the database down at the precise moment its hit ratio reads 99.9%.
> The fix is `get_or_compute` with a per-key lock so one thread computes and the rest wait, plus
> jittered TTLs so keys written together don't expire together. And the fix has its own trap: the
> per-key lock dictionary needs cleaning up or it becomes an unbounded map keyed by every key ever
> requested.

**Q: Is one lock around the whole cache acceptable?**

> Yes, and I'd say it without apologising. The critical section is a few dictionary operations, so
> contention is low, and sharding the lock adds a consistency problem to save nanoseconds. What
> matters more is what the lock *doesn't* do: it's meaningless across processes, and each process has
> its own cache with its own staleness window and no way to invalidate the others. That's the point
> where the answer stops being an in-process cache and becomes Redis, with an entirely different set
> of failure modes.

## 🎙️ Articulation drill

**Two minutes.** Open by naming the trap: **everyone can write the map and linked list, which is why
it isn't what's being assessed** — finishing in ten minutes leaves thirty-five you haven't prepared
for. So the first question is whether eviction policy is pluggable, and the design is **a cache that
owns storage, capacity, TTL and locking, and a policy that only answers "which key would you drop
next?"** — so LRU, LFU and FIFO are four small classes and the cache never changes. Give the linked

predecessor** — and say you'd use `OrderedDict` in production. Then the details that separate answers:
**`while` not `if` when evicting**, a clock passed in, and `get` raising so a cached `None` isn't a
