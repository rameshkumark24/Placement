# Day 006

**L-006** · The Internet — packets, routers, ISPs, and how data physically moves

**Time:** 3 hrs · **Mode:** NEW

> **The internet is not a network. It is an agreement between about seventy thousand independent
> networks to forward each other's packets** — with no central authority, no global map, and no
> guarantee. Understanding that it is a *federation* rather than a *system* explains most of its
> behaviour, including its failures.

---

# Part 1 — ⭐⭐ Packet switching

## The choice that defined the internet

| | ⭐ Circuit switching (telephones) | ⭐⭐ Packet switching (internet) |
|---|---|---|
| Setup | ⭐ a dedicated path reserved end to end | ⭐⭐ **none — each packet is routed independently** |
| Capacity | guaranteed for the call | ⭐ shared, contended |
| ⭐ If a link fails | ⭐⭐ **the call drops** | ⭐⭐ **packets route around it** |
| Efficiency | ⭐ idle time is wasted capacity | ⭐⭐ **idle time is available to others** |
| Guarantees | strong | ⭐⭐ **none at the network layer** |

```
⭐⭐ THE CONSEQUENCE THAT SHAPES EVERYTHING ABOVE IT:
⭐   IP is BEST-EFFORT. Packets may be ⭐ lost · ⭐ duplicated · ⭐⭐ REORDERED · ⭐ delayed arbitrarily.
⭐ ⇒ ⭐⭐ The network makes NO promises. ⭐⭐ TCP builds reliability ON TOP of an unreliable network,
⭐   at the endpoints — which is the "end-to-end principle", and it is why the internet scaled.
```

⭐ **Why put reliability at the ends?** Because a network that guarantees nothing can be simple, cheap
and made of anyone's equipment. **Intelligence at the edges, dumb pipes in the middle** — that design
choice is why a startup can add a service to the internet without asking permission, and it is worth
knowing as an architectural principle, not just a networking fact.

## ⭐ What a packet actually contains

```
⭐ [ Ethernet ][ IP header ][ TCP header ][ your data ][ Eth trailer ]
              └ src IP     └ src port
                dst IP       dst port
                TTL          seq / ack
                protocol     flags, window
```

| ⭐ Field worth knowing | ⭐ Why |
|---|---|
| ⭐⭐ **TTL** (hop limit) | ⭐⭐ decremented at every router; **at zero the packet is dropped and an ICMP error returns** — this is exactly how `traceroute` works |
| Protocol | 6 = TCP, 17 = UDP, 1 = ICMP |
| ⭐ Total length | ⭐ bounded by the MTU (Day 002) |
| ⭐ Fragmentation flags | ⭐ splitting a packet that exceeds a link's MTU |

⭐⭐ **TTL exists to stop routing loops from filling the internet with immortal packets.** A
misconfiguration that sends packets in a circle would otherwise never end; TTL guarantees every packet
dies within 255 hops.

# Part 2 — ⭐ The journey of one packet

```
⭐ You type example.com in Chennai. The server is in Oregon.

   your laptop
      │  ⭐ WiFi frame to the router                       ~1 ms
   home router  ⭐⭐ (NAT rewrites your source — Day 004)
      │  ⭐ copper/fibre to the ISP
   ISP access network                                      ~5 ms
      │
   ⭐⭐ ISP core ── peering / transit ──▶ another ISP
      │
   ⭐⭐ SUBMARINE CABLE ──────────────────────────────────  ~120 ms  ⭐ the physics floor
      │
   destination ISP ──▶ datacentre edge router
      │
   ⭐ load balancer ──▶ ⭐ the server process ──▶ ⭐⭐ accept() returns (Day 004)
```

| ⭐ Layer of the internet | ⭐ What it is |
|---|---|
| **Tier 3** | your local ISP — buys transit from bigger networks |
| **Tier 2** | regional — mixes peering and paid transit |
| ⭐ **Tier 1** | ⭐⭐ **the global backbone — they peer with each other and pay nobody** |
| ⭐ **IXP** | ⭐ an internet exchange — where networks physically interconnect |
| ⭐⭐ **Peering vs transit** | ⭐⭐ peering = we swap traffic free; transit = I pay you to reach everyone |

⭐ **This is commercial, not technical, and it leaks into engineering.** Your latency to a service can
depend on a *business relationship* between two networks — which is one reason CDNs and edge locations
exist (Stage 9, Stage 11): they shorten the path *and* keep traffic off expensive transit.

## ⭐ BGP — how routes are actually decided

| | |
|---|---|
| ⭐ Each network (an **AS**) announces "I can reach these prefixes" | via BGP to its neighbours |
| ⭐ Neighbours propagate the announcement | ⭐ the global routing table is built from these announcements |
| ⭐⭐ **It is built on trust** | ⭐⭐ **historically almost no verification** |
| ⚠️ ⭐⭐ **Consequence** | ⭐⭐ a mis-announced prefix can black-hole or hijack traffic for a large part of the internet — this has happened repeatedly, sometimes by accident |

⭐ **You will not configure BGP.** You should know it exists, that it is why "the internet had an
outage" is a real sentence, and that route propagation takes minutes — which is why DNS-based failover
is slow (Stage 11) and why multi-region designs cost what they cost.

# Part 3 — ⭐ Measuring it yourself

```bash
ping -c 5 google.com          # ⭐ round-trip time and loss
traceroute google.com         # ⭐⭐ every hop, and where the latency jumps
mtr google.com                # ⭐ traceroute + ping, continuously — the best of the three
dig google.com                # ⭐ Day 007
curl -w "@-" -o /dev/null -s https://example.com <<'EOF'
   dns:      %{time_namelookup}s
   connect:  %{time_connect}s
   tls:      %{time_appconnect}s
   ttfb:     %{time_starttransfer}s
   total:    %{time_total}s
EOF
```

⭐⭐ **Run that last one and read the five numbers.** They decompose a single request into DNS, TCP
handshake, TLS handshake, server think-time and transfer. **That decomposition is how you diagnose
"the site is slow" for the rest of your career**, and it is available in one command.

| ⭐ If the big number is… | ⭐ …the problem is |
|---|---|
| `dns` | resolution — a slow or distant resolver (Day 007) |
| ⭐ `connect` | ⭐ network distance or packet loss — the handshake round trip |
| ⭐ `tls` | ⭐ certificate chain, or extra round trips (Day 009) |
| ⭐⭐ **`ttfb` minus `tls`** | ⭐⭐ **the server thinking — this is YOUR code, and usually the database** |
| ⭐ `total` minus `ttfb` | ⭐ payload size and bandwidth |

⚠️ ⭐ **`ping` measuring 5 ms while your API takes 800 ms tells you the network is innocent.** People
skip this and spend a day tuning the wrong layer. **Measure the decomposition first.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Thinking the internet guarantees delivery** | ⭐⭐ IP is best-effort. TCP adds reliability at the endpoints, not in the network. |
| Assuming packets take the same path | ⭐ Each is routed independently and can arrive out of order. |
| ⭐ "Latency is about bandwidth" | ⭐⭐ Latency is distance and hops; bandwidth is capacity. A fat pipe to Oregon is still 130 ms away. |
| Believing you can engineer away the physics floor | ⭐ You can only shorten the distance — which is what a CDN is. |
| Thinking routing is centrally planned | ⭐ BGP is a distributed announcement protocol built on trust. |
| Ignoring TTL | It is why traceroute works and why loops do not last forever. |
| Diagnosing slowness without decomposing it | ⭐⭐ `curl -w` gives you DNS/connect/TLS/TTFB in one command. |

## Interview questions

**Q: What does "best-effort delivery" mean, and why is the internet built that way?**
> IP makes no promise: packets can be lost, duplicated, reordered or delayed arbitrarily, and the
> network will not tell you. Reliability is added by TCP at the endpoints instead. That is the
> end-to-end principle, and it is why the internet scaled — a network that promises nothing can be
> simple, cheap and built from anyone's equipment, and new services can be added at the edges without
> anyone's permission.

**Q: Why is a request to another continent slow even on a fast connection?**
> Because latency is set by distance and hop count, not bandwidth. Light in fibre covers about two
> hundred thousand kilometres per second, so thirteen thousand kilometres is roughly sixty-five
> milliseconds each way before any equipment is involved — and TCP needs a round trip to connect, TLS
> needs one or two more. Adding bandwidth does not reduce any of that. The only real fix is to shorten
> the distance, which is exactly what a CDN or an edge location does.

**Q: How does traceroute work?**
> It exploits TTL. It sends packets with a hop limit of one, so the first router decrements it to zero,
> discards the packet and returns an ICMP time-exceeded message revealing its address. Then two, then
> three, and so on, mapping the path hop by hop. It is a nice example of a diagnostic built entirely
> out of a mechanism that exists for another reason — TTL is there to stop routing loops.

**Q: A user says your API is slow. What is your first command?**
> `curl -w` with a format string that prints DNS lookup, connect, TLS, time to first byte and total.
> That decomposes one request into five numbers and immediately tells you which layer to look at:
> slow DNS, slow handshake meaning distance or loss, slow TLS, slow time-to-first-byte meaning the
> server is thinking — usually the database — or a slow transfer meaning payload size. Without that
> decomposition people spend a day tuning the wrong layer.

## 🎙️ Articulation drill

Record two minutes: **"A user in Singapore says the app is slow, but it is fine for you in Chennai.
How do you investigate?"**

⭐ Do not start with the code. **Start by decomposing one request** — DNS, connect, TLS,
time-to-first-byte, transfer — because that single command tells you whether you are looking at a
network problem or an application problem.

⭐⭐ **Then name the two shapes it usually is:** if connect and TLS dominate, it is distance and the
answer is an edge location or a CDN, because you cannot beat the speed of light. If time-to-first-byte
dominates, the network is innocent and it is your code, almost always the database. **Knowing which
half of that fork you are in before touching anything is the whole skill.**
