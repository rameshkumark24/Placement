# Day 124

**L-124** · **Caching, content negotiation and compression** — ⭐⭐ the four places a response can be cached, and the one that leaks

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: caching is not one thing — a response can be stored in four different
> places with four different lifetimes and four different owners, and almost every caching bug is
> either "it is stale somewhere I forgot about" or "it is shared with someone it should not be".**
>
> ⭐ Day 102 gave you the headers. **Today is the system they control**, and the fastest possible
> response: the one you never generate.

# Part 1 — ⭐⭐ Four caches, four owners

```
⭐⭐ A RESPONSE CAN BE STORED IN FOUR PLACES, AND YOU CONTROL THEM DIFFERENTLY:
⭐
⭐   1. ⭐ THE BROWSER          private to one user · ⚠️ ⭐⭐ YOU CANNOT PURGE IT.
⭐        ⇒ ⭐⭐ once you send max-age=3600, that response is out of your hands
⭐          for an hour. ⭐ This is why long max-age needs versioned URLs.
⭐   2. ⭐⭐ A SHARED CACHE (CDN, nginx) shared by EVERYONE · ⭐ purgeable by API
⭐        ⇒ ⭐⭐ the one that leaks (Part 2)
⭐   3. ⭐ AN APPLICATION CACHE (Redis) yours · ⭐ fully controllable · ⭐⭐ and
⭐        the only one where you choose the key
⭐   4. ⭐ THE DATABASE'S OWN caches — buffer pool, query plans (Stage 5)
⭐
⭐ ⇒ ⭐⭐ THE FIRST QUESTION FOR ANY CACHING DECISION IS **WHICH ONE**, because
⭐     "cache it" means something different in each, and the invalidation story
⭐     ranges from "one API call" to "impossible".
```

```
⭐⭐ AND THE RULE THAT PREVENTS THE WORST OUTCOME: ANYTHING YOU CANNOT PURGE
⭐   MUST BE IMMUTABLE.
⭐   ⇒ ⭐ `/static/app.a3f9c1.js` with `max-age=31536000, immutable` is safe,
⭐        because the CONTENT HASH IS IN THE URL: a new build is a new URL, so
⭐        the old cached copy becomes irrelevant rather than wrong.
⭐   ⇒ ⚠️ ⭐⭐ `/static/app.js` with `max-age=31536000` IS A YEAR-LONG BUG YOU
⭐        CANNOT RECALL. ⭐ Users will hold a broken build until they clear their
⭐        cache, and no deploy will fix it.
⭐   ⇒ ⭐⭐ SO: LONG max-age REQUIRES A VERSIONED URL. Short max-age for
⭐        anything at a stable URL. ⭐ That single rule prevents most of the
⭐        career-limiting caching mistakes.
```

# Part 2 — ⭐⭐ The shared-cache leak

```
⚠️⚠️ ⭐⭐ A SHARED CACHE KEYS ON THE URL. IF `/api/me` IS CACHEABLE AND TWO USERS
⭐    REQUEST IT, THE SECOND RECEIVES THE FIRST USER'S DATA.
⭐    ⇒ ⭐ no bug in your handler, no bug in the CDN — ⭐⭐ the cache did exactly
⭐         what it was told, and you told it wrong.
⭐
⭐ ⭐⭐ THREE DEFENCES, AND YOU WANT THE FIRST TWO:
⭐  1. ⭐⭐ `Cache-Control: private` ⇒ ⭐ "browsers only; shared caches must not
⭐       store this." ⭐⭐ THE PRIMARY CONTROL.
⭐  2. ⭐⭐ `no-store` for anything with a token or payment data ⇒ nobody stores
⭐       it at all, not even the browser.
⭐  3. ⭐ `Vary: Authorization` ⇒ makes the header part of the cache key.
⭐       ⚠️ ⭐⭐ CORRECT AND FRAGILE: it depends on every intermediary honouring
⭐       it, and a cache with a low `Vary` cardinality limit may ignore it.
⭐  ⇒ ⭐⭐ SO: `private, no-store` BY DEFAULT ON EVERY AUTHENTICATED RESPONSE,
⭐       and opt INTO caching deliberately, per endpoint. ⭐ Default-cacheable
⭐       plus a remembered `Vary` is how the leak happens.
⭐  ⇒ ⭐ `Vary: Accept-Encoding` you almost always want anyway, or a cache can
⭐       serve gzipped bytes to a client that never asked for them.
```

```
⭐⭐ THE INVALIDATION PROBLEM, STATED HONESTLY: there are only three strategies,
⭐   and they trade the same axis.
⭐   1. ⭐ TTL — expire after N seconds. ⭐⭐ Simple, and it is STALE FOR UP TO N
⭐        SECONDS BY DESIGN. ⭐ Choose N by asking "how stale is acceptable", and
⭐        the answer is usually far higher than instinct suggests.
⭐   2. ⭐ EXPLICIT PURGE on write. ⭐⭐ Fresh, and you must find EVERY key
⭐        affected — ⭐ which is exactly Day 091's shotgun surgery, so one
⭐        forgotten key is permanently wrong data.
⭐   3. ⭐⭐ VERSIONED KEYS — put a version or `updated_at` in the cache key, so
⭐        a write makes the old key UNREACHABLE rather than requiring deletion.
⭐        ⭐⭐ The old entry simply ages out. ⭐ This is the most robust option
⭐        and the least used.
⭐   ⇒ ⭐⭐ "THERE ARE ONLY TWO HARD THINGS: CACHE INVALIDATION AND NAMING" IS
⭐        FUNNY BECAUSE OPTION 2 IS GENUINELY UNSOLVABLE AT SCALE. ⭐ Prefer 1
⭐        and 3, and reach for 2 only where correctness demands it.
```

# Part 3 — ⭐ `ETag`, `304`, and application caching

```python
def get_user(request, user_id: int):
    user = repo.get(user_id)
    etag = f'"{user.updated_at.timestamp()}-{user.id}"'          # ⭐ cheap and sufficient
    if request.headers.get("if-none-match") == etag:
        return Response(b"", status=304, headers=[("ETag", etag)])   # ⭐⭐ no body
    return JSONResponse(serialise(user), headers=[("ETag", etag),
                                                  ("Cache-Control", "private, max-age=60")])
```

```
⭐⭐ A 304 SAVES BANDWIDTH, NOT WORK — you still hit the database to compute the
⭐   ETag. ⭐ That is fine on mobile, where bytes are the expensive part, and it
⭐   is NOT a server-load optimisation.
⭐   ⇒ ⭐⭐ IF YOU WANT TO SAVE THE WORK, derive the ETag from something you
⭐        already have — a version column, a `updated_at` you cache in Redis —
⭐        so the 304 path never touches the main table.
⭐   ⇒ ⭐ and the ETag doubles as the concurrency token for `If-Match` (Day 102),
⭐        which is a second reason to derive it from a version rather than a hash
⭐        of the body.
```

```python
# ⭐⭐ APPLICATION CACHING — versioned keys, so no purge is needed:
def get_product(product_id: int):
    version = redis.get(f"product:{product_id}:v") or "0"
    key = f"product:{product_id}:{version}"                # ⭐⭐ version IS the invalidation
    if (hit := redis.get(key)) is not None:
        return json.loads(hit)
    product = repo.get(product_id)
    redis.setex(key, 3600, json.dumps(product))
    return product

def update_product(product_id, **changes):
    repo.update(product_id, **changes)
    redis.incr(f"product:{product_id}:v")                  # ⭐⭐ old key is now unreachable
```

⚠️ ⭐⭐ **Cache stampede** (or *dogpile*): a popular key expires and a thousand concurrent requests all
miss and all hit the database at once. ⭐ **Fixes:** a lock so one request refills while the others
wait or serve stale; `stale-while-revalidate` at the HTTP layer; or **jittered TTLs**, so a thousand
keys created together do not expire together — ⭐⭐ the same thundering-herd shape as Day 123's
`Retry-After`.

# Part 4 — ⭐ Content negotiation

```http
Accept: application/json, text/csv;q=0.8        ⭐ what the client WANTS, with preferences
Accept-Encoding: gzip, br                        ⭐ what it can DECODE
Accept-Language: en-GB, en;q=0.9                 ⭐ what it can READ
```

```
⭐⭐ THE SERVER PICKS, AND MUST SAY WHAT IT PICKED — `Content-Type`,
⭐   `Content-Encoding`, `Content-Language` — ⭐⭐ AND MUST SEND A MATCHING `Vary`,
⭐   or a shared cache will serve the wrong variant to the next client.
⭐   ⇒ ⭐ `q=` values are preferences, in 0–1. Highest wins; ties break by
⭐        specificity.
⭐   ⇒ ⭐ if you cannot satisfy the `Accept` header, `406 Not Acceptable` — ⭐⭐ or,
⭐        pragmatically, just return JSON, because a strict 406 breaks more
⭐        clients than it helps. ⭐ Decide, and document it.
⭐   ⇒ ⚠️ ⭐⭐ ALWAYS SEND A CHARSET on anything a browser renders. `text/html`
⭐        without one lets the browser SNIFF the encoding, and a UTF-7 sniffing
⭐        attack is a real historical XSS vector (Day 127).
```

```
⭐ FORMAT SELECTION — THREE OPTIONS, ONE RECOMMENDATION:
⭐   `Accept: text/csv`   ⭐ correct HTTP, ⚠️ ⭐ awkward to test and to link to
⭐   `/orders.csv`        ⭐⭐ pragmatic, cacheable, ⭐ a user can paste it in a
⭐                          browser — ⭐⭐ and it gets its own cache key for free
⭐   `?format=csv`        ⭐ same benefits, ⚠️ easy to forget in the `Vary`
⭐   ⇒ ⭐⭐ USE THE EXTENSION FOR HUMAN-FACING EXPORTS and content negotiation
⭐        for machine clients. ⭐ Purity loses to "a support engineer can paste
⭐        the URL into a browser".
```

# Part 5 — ⭐ Compression

```
⭐⭐ WHERE TO COMPRESS: NOT IN PYTHON. ⭐ nginx or the CDN does it in C, can
⭐   cache both variants, and does not occupy a worker (Day 111).
⭐   · ⭐ gzip     — universal, fast, good enough
⭐   · ⭐ brotli   — ~15-20% smaller, slower to compress ⇒ ⭐⭐ ideal for STATIC
⭐        assets compressed once at build time and served forever
⭐   · ⭐ zstd     — increasingly supported, excellent ratio-to-speed
⭐   ⇒ ⭐ do not compress below ~1 KB: the headers and CPU cost more than the
⭐        saving. ⭐ Do not compress already-compressed bytes — JPEG, PNG, MP4,
⭐        zip — ⭐⭐ you spend CPU to make them very slightly larger.
```

```
⚠️⚠️ ⭐⭐ AND THE ONE THAT SOUNDS EXOTIC AND IS NOT: BREACH.
⭐    IF A RESPONSE CONTAINS (a) A SECRET — a CSRF token, a session id — AND
⭐    (b) ATTACKER-CONTROLLED CONTENT, AND IS COMPRESSED, THEN THE **LENGTH** OF
⭐    THE RESPONSE LEAKS INFORMATION ABOUT THE SECRET.
⭐    ⇒ ⭐ compression replaces repeated strings, so if the attacker's injected
⭐         guess matches part of the secret, the response gets SHORTER. ⭐⭐ They
⭐         recover the token one character at a time, from response sizes alone.
⭐    ⇒ ⭐⭐ MITIGATIONS: do not put secrets in a compressed response body;
⭐         randomise the token per response (masking); or disable compression on
⭐         responses containing secrets.
⭐    ⇒ ⭐ it is why "just gzip everything" is not quite right, and it is worth
⭐         knowing as an example that ⭐⭐ A SIDE CHANNEL CAN LEAK THROUGH
⭐         SOMETHING AS INNOCUOUS AS A LENGTH.
```

```
⭐⭐ THE FASTEST RESPONSE IS THE ONE YOU NEVER GENERATE. IN ORDER OF VALUE:
⭐   1. ⭐⭐ a 304, or a CDN hit ⇒ you did nothing at all
⭐   2. ⭐ an application cache hit ⇒ no database
⭐   3. ⭐ a cheaper query ⇒ ⭐⭐ and this is usually the real fix (Day 100A)
⭐   4. ⭐ compression ⇒ fewer bytes for the same work
⭐   ⇒ ⚠️ ⭐⭐ AND THE WARNING: CACHING IS OFTEN USED TO HIDE A SLOW QUERY. ⭐ You
⭐        get a fast p50 and an appalling p99 whenever the cache misses, plus a
⭐        correctness risk you did not have before. ⭐⭐ FIX THE QUERY FIRST;
⭐        CACHE WHAT IS ALREADY FAST BUT FREQUENT.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Long `max-age` on a stable URL** | ⭐⭐ A year-long bug you cannot recall. Version the URL. |
| ⭐ Authenticated responses cacheable by default | ⭐⭐ A shared cache serves one user's data to another. |
| Relying on `Vary: Authorization` alone | ⭐ Correct and fragile. `private, no-store` by default. |
| ⭐ Purge-on-write as the main strategy | ⭐⭐ One forgotten key is permanently wrong. Prefer TTL or versioned keys. |
| Uniform TTLs | ⭐⭐ A thousand keys expire together — a stampede. Jitter them. |
| ⭐ No stampede protection on a hot key | ⭐ A thousand concurrent misses hit the database at once. |
| ⭐ Expecting a 304 to save server work | ⭐ It saves **bandwidth**; you still computed the ETag. |
| Negotiating without `Vary` | ⭐⭐ A cache serves the wrong variant. |
| ⭐ `text/html` with no charset | ⭐⭐ Encoding sniffing — a real XSS vector. |
| Compressing in Python | ⭐ nginx does it in C without occupying a worker. |
| Compressing JPEGs, or 200-byte bodies | ⭐ You spend CPU to gain nothing. |
| ⭐⭐ **Compressing a response with a secret and attacker input** | ⭐⭐ BREACH — the length leaks the secret. |
| ⭐ Caching to hide a slow query | ⭐⭐ Fast p50, appalling p99, plus a new correctness risk. |

## Interview questions

**Q: Where can a response be cached?**
> Four places with four owners. The browser, which is private to one user and which you *cannot
> purge* — once you've sent `max-age=3600` it's out of your hands for an hour. A shared cache like a
> CDN or reverse proxy, which is the one that leaks between users but is purgeable. Your own
> application cache in Redis, where you choose the key and control everything. And the database's
> internal caches. The first question for any caching decision is which one, because "cache it" means
> something different in each and the invalidation story ranges from one API call to impossible.

**Q: How can caching leak one user's data to another?**
> A shared cache keys on the URL. If `/api/me` is cacheable and two users request it, the second gets
> the first's response — and neither your handler nor the CDN has a bug; the cache did what it was
> told. `Vary: Authorization` makes the header part of the key and is the mechanically correct fix,
> but it depends on every intermediary honouring it. So I'd make authenticated responses
> `private, no-store` by default and opt into caching deliberately per endpoint. Default-cacheable
> plus a remembered `Vary` is exactly how this happens.

**Q: How do you invalidate a cache?**
> Three options and they trade the same axis. A TTL is simplest and is stale by design for up to N
> seconds — and the acceptable N is usually much larger than instinct suggests. Explicit purge on
> write is fresh but requires finding every affected key, which is shotgun surgery, so one forgotten
> key is permanently wrong data. Versioned keys are the most robust and least used: put a version in
> the key, and a write makes the old key unreachable rather than requiring deletion, so it just ages
> out. I'd prefer TTL and versioned keys, and use explicit purge only where correctness demands it.

**Q: What's a cache stampede?**
> A popular key expires and a thousand concurrent requests all miss and all hit the database at once —
> so the moment the cache is least useful is the moment the load is highest. Fixes are a lock so one
> request refills while others wait or serve stale, `stale-while-revalidate` at the HTTP layer, or
> jittered TTLs so keys created together don't expire together. That last one is the same
> thundering-herd shape as sending every client the same `Retry-After`.

**Q: Why is "just gzip everything" not quite right?**
> Two reasons. Small bodies and already-compressed formats cost CPU and gain nothing. And BREACH: if a
> response contains both a secret — a CSRF token, say — and attacker-controlled content, and it's
> compressed, then the response *length* leaks information about the secret, because compression
> shortens repeated strings. An attacker guesses a character at a time and watches the size. So you
> keep secrets out of compressed bodies, mask them per response, or disable compression on those
> responses. It's a good example of a side channel leaking through something as innocuous as a length.
