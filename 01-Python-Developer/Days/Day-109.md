# Day 109

**L-109** · **WSGI** — the whole specification in one page, and ⭐⭐ why it cannot do WebSockets

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: WSGI is one function signature — `app(environ, start_response)` returning
> an iterable of bytes — and that single agreement is why any Python web framework can run under any
> Python web server, which was not true before it existed.**
>
> ⭐ Day 105 gave you a server. Day 107–108 gave you a framework. **Today is the contract between
> them**, and it is small enough to hold in your head entirely.

# Part 1 — ⭐ The problem it solved

```
⭐⭐ BEFORE WSGI (2003), EVERY PYTHON WEB SERVER HAD ITS OWN API:
⭐   mod_python had one, FastCGI another, CGI a third.
⭐   ⇒ ⭐⭐ SO A FRAMEWORK HAD TO PICK A SERVER, AND A SERVER HAD TO PICK
⭐        FRAMEWORKS. An n × m problem, with most of the cells empty.
⭐
⭐ ⭐⭐ PEP 333 DEFINED ONE CALLABLE, AND THE n × m BECAME n + m:
⭐        ANY framework  ×  ANY server, ⭐ as long as both speak the callable.
⭐   ⇒ ⭐ that is the same "one interface, many implementations" argument as
⭐        Day 056's Protocol, and the same n×m → n+m arithmetic as Day 055's
⭐        composition. ⭐⭐ It is the most successful interface in Python's
⭐        history, and it is nine lines of specification.
```

# Part 2 — ⭐⭐ The entire specification

```python
def app(environ: dict, start_response: Callable) -> Iterable[bytes]:
    status = "200 OK"                                    # ⭐ a STRING, code and reason
    headers = [("Content-Type", "text/plain; charset=utf-8")]
    start_response(status, headers)                       # ⭐⭐ call it BEFORE returning
    return [b"hello from raw WSGI"]                       # ⭐⭐ an ITERABLE OF BYTES
```

```
⭐⭐ THAT IS ALL OF IT. THREE OBLIGATIONS ON THE APPLICATION:
⭐   1. accept exactly two arguments: `environ` and `start_response`
⭐   2. ⭐ call `start_response(status, headers)` before yielding any body
⭐   3. ⭐⭐ return an ITERABLE OF BYTES — not a string, not a dict, not one blob
⭐
⭐ ⭐⭐ AND ONE OBLIGATION ON THE SERVER: call the app, iterate the result, write
⭐   each chunk to the socket, and call `.close()` on the iterable if it has one.
```

| ⭐ `environ` key | ⭐ Meaning |
|---|---|
| `REQUEST_METHOD` | ⭐ `"GET"` |
| ⭐⭐ `PATH_INFO` | ⭐⭐ the path, **already percent-decoded** |
| `QUERY_STRING` | ⭐ raw, undecoded |
| ⭐ `CONTENT_LENGTH` / `CONTENT_TYPE` | ⚠️ ⭐ note: **no `HTTP_` prefix** — a CGI wart |
| ⭐⭐ `HTTP_*` | ⭐⭐ every other header: `X-Request-Id` ⇒ `HTTP_X_REQUEST_ID` |
| ⭐ `wsgi.input` | ⭐⭐ a **file-like object** for the body — you `.read(n)` it |
| `wsgi.url_scheme` | `"http"` / `"https"` |
| `wsgi.errors` | a stream for error output |
| `SERVER_NAME` / `SERVER_PORT` | ⭐ what to build absolute URLs from |

```
⭐⭐ THE HTTP_ MANGLING IS A REAL SOURCE OF BUGS, AND IT IS NOT REVERSIBLE:
⭐   `X-Request-Id` ⇒ upper-cased, dashes to underscores, `HTTP_` prefixed
⭐   ⇒ ⭐⭐ SO `X-Request-Id` AND `X_Request_Id` COLLIDE INTO THE SAME KEY.
⭐   ⇒ ⭐ and headers can repeat (Day 104) but environ is a flat dict — ⭐⭐ so
⭐        WSGI LOSES DUPLICATE HEADERS, joining them with commas. `Set-Cookie`
⭐        is a response header, so it escapes this, but the general point stands:
⭐        ⭐⭐ the CGI environ model is lossy, and ASGI fixed it (Day 110).
```

# Part 3 — ⭐ An adapter for your framework

```python
def wsgi_adapter(framework_app):
    """⭐⭐ Make Day 108's framework speak WSGI."""
    def application(environ, start_response):
        # ⭐ 1. environ ⇒ Request
        headers = Headers([
            (k[5:].replace("_", "-"), v) for k, v in environ.items() if k.startswith("HTTP_")
        ] + [(k.replace("_", "-"), environ[k]) for k in ("CONTENT_TYPE", "CONTENT_LENGTH")
             if k in environ])
        length = int(environ.get("CONTENT_LENGTH") or 0)
        body = environ["wsgi.input"].read(length) if length else b""   # ⭐⭐ read EXACTLY (Day 104)

        request = Request(environ["REQUEST_METHOD"], environ["PATH_INFO"],
                          parse_qs(environ.get("QUERY_STRING", "")), headers, body)

        # ⭐ 2. run the app
        response = framework_app(request)

        # ⭐ 3. Response ⇒ start_response + an iterable
        start_response(f"{response.status} {STATUS_TEXT[response.status]}",
                       response.headers + [("Content-Length", str(len(response.body)))])
        return [response.body]
    return application
```

```bash
gunicorn myapp:application -w 4 --bind 127.0.0.1:8000     # ⭐⭐ your framework, on a real server
```

```
⭐⭐ THAT IS THE PAYOFF OF THE WHOLE STAGE SO FAR: your own routing, your own
⭐   middleware, your own request objects — ⭐ now running under a production
⭐   server with worker processes, graceful reload and signal handling (Day 111),
⭐   because you implemented ONE FUNCTION SIGNATURE.
⭐   ⇒ ⭐⭐ AND THE REVERSE IS THE BETTER EXERCISE: make YOUR Day-106 server a
⭐        WSGI CONTAINER — parse the request, build environ, call `app`, iterate
⭐        the result. ⭐ Then run FLASK on it. When someone else's framework runs
⭐        unmodified on your server, you have understood the contract.
```

⚠️ ⭐ **`wsgi.input` must be read exactly `CONTENT_LENGTH` bytes.** ⭐⭐ Reading to EOF may block
forever on a keep-alive connection (Day 105) because the next request has not arrived yet — **the same
framing rule as Day 104, now expressed through a file-like object.**

# Part 4 — ⭐ Streaming and middleware in WSGI

```python
def streaming_app(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/csv")])
    def rows():                                    # ⭐⭐ a GENERATOR (Day 047)
        yield b"id,name\n"
        for row in query_all():
            yield f"{row.id},{row.name}\n".encode()
    return rows()                                  # ⭐ the server iterates it
```

```
⭐⭐ STREAMING IS FREE, AND IT IS THE CLEVEREST THING IN THE SPEC: "return an
⭐   ITERABLE" means a generator qualifies. ⇒ ⭐ constant memory for a 2 GB
⭐   export (Day 105), with no extra API at all.
⭐   ⇒ ⭐ if the iterable has `.close()`, the server MUST call it ⇒ so a
⭐        generator's `finally` runs (Day 047) and your database cursor closes
⭐        even if the client disconnects mid-download.
```

```python
def wsgi_timing_middleware(app):                   # ⭐ a WSGI app that wraps a WSGI app
    def middleware(environ, start_response):
        start = time.perf_counter()
        def wrapped_start_response(status, headers, exc_info=None):
            headers.append(("X-Response-Time",
                            f"{(time.perf_counter()-start)*1000:.1f}ms"))
            return start_response(status, headers, exc_info)
        return app(environ, wrapped_start_response)   # ⭐⭐ wrap start_response, not the return
    return middleware
```

⭐⭐ **Note what middleware has to do here: wrap `start_response`.** ⭐ You cannot modify the headers
after the fact, because the app calls `start_response` itself — **so a WSGI middleware that touches
response headers must intercept the callable**, which is clunky and is one of the things ASGI made
cleaner.

# Part 5 — ⭐⭐ Why WSGI cannot do WebSockets

```
⭐⭐ LOOK AT THE SIGNATURE AND DERIVE THE LIMITS — do not memorise them:
⭐        app(environ, start_response) -> Iterable[bytes]
⭐
⭐ 1. ⭐⭐ IT IS CALLED ONCE, WITH THE REQUEST ALREADY COMPLETE, AND RETURNS.
⭐      ⇒ ⭐⭐ THERE IS NO WAY TO RECEIVE MORE DATA AFTER THE CALL BEGINS.
⭐      ⇒ ⭐ a WebSocket (Day 017) is many messages in BOTH directions over one
⭐        connection ⇒ ⭐⭐ THERE IS NOWHERE IN THIS SIGNATURE TO PUT THEM.
⭐        No amount of cleverness adds it; the shape is wrong.
⭐
⭐ 2. ⭐⭐ IT IS A SYNCHRONOUS CALLABLE. There is no way for the app to yield
⭐      control back to the server while it waits.
⭐      ⇒ ⭐⭐ SO ONE WORKER = ONE REQUEST AT A TIME, always. Concurrency must
⭐        come from threads or processes (Day 106) — ⭐ an event loop cannot
⭐        help, because the app never gives the loop a chance to run.
⭐
⭐ 3. ⭐ NO LIFECYCLE HOOKS. There is no "the server is starting" or "the server
⭐      is stopping" ⇒ ⭐⭐ connection pools get built lazily on first request,
⭐      and graceful shutdown (Day 081) has nowhere to hook in.
⭐
⭐ 4. ⭐ SERVER-SENT EVENTS (Day 018) technically work — an infinite generator —
⭐      ⭐⭐ but each open stream OCCUPIES A WHOLE WORKER. 200 subscribers needs
⭐      200 threads.
⭐
⭐ ⇒ ⭐⭐ ASGI EXISTS TO FIX 1, 2 AND 3. THAT IS THE WHOLE MOTIVATION, and if you
⭐     can derive it from the signature you never need to remember it.
```

| | ⭐ WSGI | ⭐ ASGI (Day 110) |
|---|---|---|
| Callable | ⭐ sync, once | ⭐⭐ `async`, with `receive`/`send` |
| Request body | ⭐ a file-like object | ⭐ messages you `await` |
| ⭐⭐ WebSockets | ⭐⭐ **impossible** | ⭐ first-class |
| ⭐ Concurrency | ⭐ threads/processes only | ⭐⭐ event loop, plus threads/processes |
| Lifespan | ⭐ none | ⭐ startup/shutdown events |
| ⭐ Ecosystem | ⭐⭐ Django, Flask, huge and stable | ⭐ FastAPI, Starlette, Django async |

⭐ **WSGI is not obsolete.** ⭐⭐ Django and Flask still run on it, it is simpler to reason about, and
for a request/response API with a synchronous database driver **it is often the better choice** — a
sync worker cannot suffer Day 072's blocking-call catastrophe, because blocking is all it does.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Returning a `str` | ⭐⭐ An iterable of **bytes**. |
| Returning a single `bytes` object | ⭐ It is iterable — you will stream one byte at a time. Wrap it in a list. |
| ⭐ Calling `start_response` after yielding | ⭐ It must come first. |
| ⭐⭐ **Reading `wsgi.input` to EOF** | ⭐⭐ May block forever on keep-alive. Read exactly `CONTENT_LENGTH`. |
| Looking for `HTTP_CONTENT_TYPE` | ⭐ `CONTENT_TYPE` and `CONTENT_LENGTH` have no prefix. |
| ⭐ Expecting duplicate headers | ⭐⭐ `environ` is flat and lossy — they are comma-joined. |
| Modifying headers after the app returns | ⭐ Wrap `start_response`. |
| ⭐ Not calling `.close()` on the iterable | ⭐⭐ Generator `finally` never runs — leaked cursors. |
| ⭐ Expecting async to help under WSGI | ⭐⭐ The app never yields control. Threads or processes. |
| SSE under WSGI at scale | ⭐ One worker per open stream. |
| ⭐ Assuming WSGI is dead | ⭐ Django and Flask, and it cannot suffer the async blocking bug. |

## Interview questions

**Q: What is WSGI?**
> One function signature: a callable taking `environ` and `start_response` and returning an iterable
> of bytes. That's the whole specification. Before it, every Python web server had its own API, so
> frameworks were locked to servers — an n-by-m problem. WSGI turned it into n plus m: any framework
> runs on any server. It's the same "one interface, many implementations" argument as a Protocol, and
> it's probably the most successful interface in Python's history at about nine lines.

**Q: What's in `environ`?**
> CGI-style keys: `REQUEST_METHOD`, `PATH_INFO` — already percent-decoded — `QUERY_STRING`, and every
> header as `HTTP_` plus the upper-cased name with dashes turned into underscores, except
> `CONTENT_TYPE` and `CONTENT_LENGTH` which have no prefix, as a CGI wart. The body is `wsgi.input`, a
> file-like object you read exactly `CONTENT_LENGTH` bytes from — reading to EOF can block forever on
> a keep-alive connection because the next request hasn't arrived. The model is also lossy: environ is
> a flat dict, so duplicate headers get comma-joined and `X-Request-Id` collides with
> `X_Request_Id`. ASGI fixed that by keeping headers as a list of byte pairs.

**Q: How does streaming work in WSGI?**
> It falls out of "return an iterable" — a generator qualifies, so you yield chunks and the server
> writes each one, giving constant memory for a large export with no extra API. The detail worth
> knowing is that the server must call `.close()` on the iterable if it has one, which means the
> generator's `finally` runs and your database cursor gets closed even when the client disconnects
> mid-download.

**Q: Why can't WSGI do WebSockets?**
> You can derive it from the signature rather than remembering it. The callable is invoked once with
> the request already complete, and it returns — there's no channel to receive further data after the
> call begins. A WebSocket is many messages in both directions over one connection, and there is
> nowhere in that signature to put them. It's also synchronous, so the app can never yield control
> back to the server while waiting, which means one worker handles one request at a time and an event
> loop can't help. And there are no lifecycle hooks, so pools are built lazily and graceful shutdown
> has nowhere to attach. ASGI exists to fix exactly those three.

**Q: Is WSGI obsolete?**
> No. Django and Flask still run on it, it's much simpler to reason about, and for a request/response
> API with a synchronous database driver it's frequently the better choice — a sync worker physically
> cannot suffer the blocking-call-in-async catastrophe, because blocking is all it does. I'd reach for
> ASGI when I need WebSockets, server-sent events at scale, or genuinely high concurrency on I/O-bound
> work.

## 🎙️ Articulation drill

Record two minutes: **"What is WSGI, and why does ASGI exist?"**

⭐ **Give the spec first, because it is small enough to state completely:** **"WSGI is one function
signature — a callable taking `environ` and `start_response`, returning an iterable of bytes. That's
the entire specification. Its value is the arithmetic: before it, every server had its own API, so it
was n frameworks times m servers. WSGI made it n plus m."**

⭐⭐ **Then derive ASGI's existence from the signature rather than listing features:** *"and you can
read WSGI's limits straight off that signature. It's called once, with the request already complete,
and it returns — so there is no channel to receive more data after the call starts. A WebSocket is many
messages in both directions on one connection, and there's simply nowhere in that shape to put them.
It's also synchronous, so the app can never hand control back to the server while it waits, which means
one worker is one request and an event loop can't help. And there's no lifecycle hook, so connection
pools get built lazily and graceful shutdown has nowhere to attach."*

⭐⭐ **Then state ASGI as the fix, not as a replacement:** *"ASGI exists to fix exactly those three. It
makes the app an async callable with `receive` and `send` channels, so many messages can flow in both
directions, the app can await, and there's a lifespan scope for startup and shutdown."*

⭐ **Close on the honest position, because 'ASGI is better' is the shallow answer:** *"but WSGI isn't
obsolete. Django and Flask still run on it, it's far easier to reason about, and for a request/response
API with a synchronous driver it's often the better choice — a sync worker physically cannot suffer the
blocking-call-in-async problem, because blocking is all it does. I'd move to ASGI for WebSockets,
server-sent events at scale, or genuinely high-concurrency I/O."*
