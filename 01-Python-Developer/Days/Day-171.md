# Day 171

**L-171** · 🎸 **The Django ORM I** — ⭐⭐ lazy QuerySets, `select_related` vs `prefetch_related`, and when a query actually runs

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a QuerySet is a description of a query, not a query — nothing touches the
> database until something needs a row, and almost every Django performance surprise is a
> disagreement between where you *wrote* the query and where it *ran*.**
>
> ⭐ Day 136 taught the N+1 with SQLAlchemy. ⭐⭐ Django has the same problem with different tools and
> one extra hazard: **the query can be triggered from a template, by someone who is editing HTML.**

# Part 1 — ⭐⭐ Laziness, and the seven things that evaluate

```python
qs = Order.objects.filter(status="paid")      # ⭐ NO QUERY
qs = qs.exclude(total_cents=0)                # ⭐ NO QUERY — returns a NEW QuerySet
qs = qs.order_by("-created_at")               # ⭐ NO QUERY
print(qs.query)                               # ⭐ prints SQL — STILL no query
for o in qs:                                  # ⭐⭐ ***HERE***. One query.
    ...
```

```
⭐⭐ WHAT TRIGGERS EVALUATION — memorise this list, because every surprise is
⭐   on it:
⭐   ⭐ ITERATION · ⭐ `list(qs)` · ⭐ `bool(qs)` / `if qs:` · ⭐ `len(qs)`
⭐   ⭐ SLICING WITH A STEP (`qs[::2]`) — ⭐⭐ but `qs[:10]` does NOT; it adds
⭐        a `LIMIT` and stays lazy
⭐   ⭐ `repr(qs)` — ⭐⭐ WHICH MEANS THE DEBUGGER AND THE SHELL EVALUATE IT.
⭐        ⭐ Printing a QuerySet in a debugger runs the query, and people
⭐        conclude the wrong thing about where the slowness is.
⭐   ⭐ `pickle(qs)`, `qs.count()`, `qs.exists()`, `qs.first()`, `qs.get()`
⭐
⭐⭐ AND THE PART THAT COSTS PEOPLE REAL MONEY:
⭐   ⭐ `if qs:` LOADS EVERY ROW INTO MEMORY to decide truthiness.
⭐        ⇒ ⭐⭐ USE `qs.exists()` — it becomes `SELECT 1 ... LIMIT 1`.
⭐   ⭐ `len(qs)` LOADS EVERY ROW. ⇒ ⭐⭐ `qs.count()` becomes `SELECT COUNT(*)`.
⭐   ⭐ ⭐⭐ BUT THE REVERSE IS ALSO A TRAP: if you are ABOUT to iterate the
⭐        QuerySet anyway, ⭐ `count()` is a SECOND query, and `len()` on an
⭐        already-cached QuerySet is free. ⭐⭐ "Always use count()" is wrong
⭐        advice; the rule is **`exists()`/`count()` when you need only the
⭐        answer, `len()` when you already have the rows.**
```

```
⭐⭐ THE RESULT CACHE — the mechanism behind the two biggest confusions:
⭐   ⭐ evaluating a QuerySet CACHES the rows on that QuerySet object.
⭐        for o in qs: ...    # ⭐ query
⭐        for o in qs: ...    # ⭐⭐ NO query — cached
⭐   ⭐ BUT ANY NEW QUERYSET HAS NO CACHE:
⭐        Order.objects.filter(...)   # ⭐⭐ a NEW object every time ⇒ a new query
⭐        ⇒ ⭐ calling `Order.objects.filter(x)` in a loop is N queries even
⭐          though it "looks the same".
⭐   ⭐ ⭐⭐ AND SLICING A CACHED QUERYSET RE-QUERIES: `qs[:5]` after `list(qs)`
⭐        is a NEW QuerySet with a LIMIT — ⭐ it does not slice the cache.
⭐   ⇒ ⭐⭐ TWO NAMES, TWO OBJECTS, TWO QUERIES. THE VARIABLE IS THE CACHE.
```

# Part 2 — ⭐⭐ The N+1, and the two fixes

```python
# ⭐⭐ 1 + N + N QUERIES. Written by someone reasonable.
for order in Order.objects.filter(status="paid")[:50]:   # ⭐ 1
    print(order.user.email)                              # ⭐⭐ +50 (to-one)
    print(order.items.count())                           # ⭐⭐ +50 (to-many)
```

```
⭐⭐ THE TWO TOOLS, AND THE RULE DERIVED RATHER THAN MEMORISED:

⭐  ⭐⭐ `select_related("user")` — FOR TO-ONE (FK, OneToOne)
⭐     ⭐ becomes a SQL **JOIN**: one query, extra columns.
⭐     ⭐ CORRECT because a to-one join adds columns, ⭐⭐ NOT ROWS.
⭐
⭐  ⭐⭐ `prefetch_related("items")` — FOR TO-MANY (reverse FK, M2M)
⭐     ⭐ becomes a **SECOND QUERY** with `WHERE order_id IN (...)`, joined
⭐        in Python.
⭐     ⭐ CORRECT because joining a to-many MULTIPLIES ROWS: ⭐⭐ 50 orders ×
⭐        20 items = 1,000 rows, each carrying a full copy of the order —
⭐        ⭐ Day 136's fan-out, and it is a bandwidth and memory problem long
⭐        before it is a query-count problem.
⭐
⭐   ⇒ ⭐⭐ SO THE RULE IS NOT ARBITRARY: **JOIN WHEN IT ADDS COLUMNS,
⭐        SECOND-QUERY WHEN IT WOULD ADD ROWS.** ⭐ Same conclusion as
⭐        SQLAlchemy's `joinedload`/`selectinload`, reached the same way.
```

```python
# ⭐ 3 queries, regardless of page size
orders = (Order.objects
          .filter(status="paid")
          .select_related("user")                        # ⭐ join
          .prefetch_related("items")[:50])               # ⭐ +1 query

# ⭐⭐ AND THE ONE PEOPLE MISS — `.count()` on a prefetched relation STILL
#    QUERIES, because COUNT is SQL, not Python:
order.items.count()        # ⭐⭐ a query, EVEN WITH prefetch_related
len(order.items.all())     # ⭐ uses the prefetch cache — zero queries
# ⇒ ⭐⭐ THE ONE PLACE `len()` BEATS `count()`, and it reverses Part 1's
#      advice. ⭐ The rule underneath both: DO NOT ASK SQL A QUESTION YOU
#      ALREADY HAVE THE ANSWER TO IN MEMORY.
```

```
⭐⭐ `Prefetch()` — FOR WHEN THE PREFETCH ITSELF NEEDS FILTERING OR ORDERING:
⭐   .prefetch_related(
⭐       Prefetch("items",
⭐                queryset=Item.objects.filter(refunded=False).select_related("sku"),
⭐                to_attr="active_items")          # ⭐⭐ nested loading, controlled
⭐   )
⭐   ⇒ ⭐ WITHOUT `Prefetch`, `order.items.filter(refunded=False)` INSIDE THE
⭐        LOOP **IGNORES THE PREFETCH CACHE AND RE-QUERIES** — ⭐⭐ so you did
⭐        the prefetch AND the N+1. ⭐ That is the subtlest performance bug in
⭐        the Django ORM, because the code looks optimised.
```

# Part 3 — ⭐⭐ Fetching less: `only`, `defer`, `values`

```
⭐⭐ `select_related` FIXES QUERY COUNT. THESE FIX PAYLOAD — and payload is
⭐   what kills a list endpoint with a `TextField` on it.

⭐   ⭐ `.only("id", "status")`   → SELECT just those columns
⭐        ⭐⭐ ACCESSING ANY OTHER FIELD TRIGGERS A PER-ROW QUERY. ⭐ So `only()`
⭐        misused is a NEW N+1 — ⭐⭐ you optimised the first query and created
⭐        fifty more.
⭐   ⭐ `.defer("description")`  → everything EXCEPT. Same hazard, inverted.
⭐        ⭐ Use `defer` for one huge column; `only` when you genuinely need
⭐        three fields.
⭐   ⭐⭐ `.values("id", "status")`        → DICTS, not model instances
⭐   ⭐⭐ `.values_list("id", flat=True)`  → a flat list of scalars
⭐        ⭐ + ⭐⭐ NO MODEL INSTANTIATION AT ALL. For 100k rows this is often
⭐          a 5–10× win, because building model objects is the cost.
⭐        ⭐ − no methods, no properties, no `save()` — ⭐ and that is a
⭐          FEATURE for a read-only report: ⭐⭐ you cannot accidentally
⭐          trigger a relation, because there is nothing to trigger.
⭐
⭐   ⇒ ⭐⭐ THE DECISION: **NEED BEHAVIOUR ⇒ MODELS. NEED DATA ⇒ `values()`.**
⭐        ⭐ A report endpoint almost never needs behaviour, and Day 167's
⭐        report is exactly this shape.

⭐⭐ AND `.iterator()` FOR LARGE SCANS:
⭐   ⭐ a normal QuerySet loads EVERYTHING into the result cache ⇒ ⭐⭐ 2M rows
⭐        is 2M model objects in RAM, and your worker OOMs (Day 082's exit 137).
⭐   ⭐ `.iterator(chunk_size=2000)` streams with a server-side cursor and
⭐        ⭐⭐ KEEPS NO CACHE. ⭐ Which means iterating it twice re-queries —
⭐        that is the trade, and it is the right one for a batch job.
```

# Part 4 — ⭐ Making the invisible visible

```
⭐⭐ YOU CANNOT FIX WHAT YOU CANNOT SEE, AND DJANGO HIDES QUERIES BY DESIGN.
⭐   FOUR TOOLS, IN INCREASING ORDER OF WHEN THEY CATCH IT:

⭐  1. ⭐ `django-debug-toolbar` — ⭐⭐ shows query count, duplicates and SQL
⭐       per page. ⭐ Best first tool; ⭐⭐ development only, never production
⭐       (it holds queries in memory and exposes settings).
⭐  2. ⭐ `print(qs.query)` / `qs.explain()` — ⭐⭐ `explain()` is `EXPLAIN`,
⭐       and it is the one people forget exists.
⭐  3. ⭐⭐ `assertNumQueries(3)` IN TESTS — ⭐ Django ships Day 141's
⭐       query-count ceiling BUILT IN. ⭐⭐ There is no excuse not to have it:
⭐          with self.assertNumQueries(3):
⭐              self.client.get("/orders/")
⭐  4. ⭐ `nplusone` or `django-zen-queries` — ⭐⭐ RAISE on an unexpected
⭐       lazy load. ⭐ Day 136's `lazy="raise"`, as a library.
⭐
⭐   ⇒ ⭐⭐ AND THE ONE THAT ONLY DJANGO NEEDS: **TEMPLATES CAN QUERY.**
⭐        ⭐ `{% for item in order.items.all %}` inside a `{% for order %}`
⭐        loop is an N+1 written in HTML, ⭐⭐ invisible to anyone reading the
⭐        view. ⭐ `django-zen-queries` can mark a template render as
⭐        query-forbidden — which is the only real defence.
```

```python
# ⭐⭐ THE HABIT: EVERY LIST VIEW GETS A CEILING, AND IT IS A CONSTANT
class OrderListTests(TestCase):
    def test_list_is_not_n_plus_1(self):
        OrderFactory.create_batch(50)
        with self.assertNumQueries(4):          # ⭐⭐ a NUMBER, not a feeling
            self.client.get("/orders/")
```

# Part 5 — ⭐⭐ Managers and QuerySets: Django's repository

```python
class OrderQuerySet(models.QuerySet):
    def for_user(self, user):
        return self.filter(user=user)                      # ⭐⭐ scoping, ONE place
    def paid(self):
        return self.filter(status="paid")
    def with_details(self):
        return self.select_related("user").prefetch_related("items")   # ⭐ ONE place

class Order(models.Model):
    objects = OrderQuerySet.as_manager()                   # ⭐ chainable everywhere
    ...

# ⭐⭐ NOW THE VIEW READS AS DOMAIN LANGUAGE AND CANNOT FORGET EITHER RULE:
Order.objects.for_user(request.user).paid().with_details()[:50]
```

```
⭐⭐ WHY `QuerySet.as_manager()` RATHER THAN A CUSTOM `Manager`:
⭐   ⭐ manager methods are NOT CHAINABLE — `Order.objects.paid().for_user(u)`
⭐        only works if `paid()` returns a QuerySet with those methods on it.
⭐   ⇒ ⭐⭐ `as_manager()` puts every method on both. ⭐ It is the modern
⭐        idiom, and it is what makes this genuinely a repository rather than
⭐        a bag of helper functions.

⭐⭐ AND THE TENANCY QUESTION (Day 160), WHICH HAS A REAL DJANGO ANSWER:
⭐   ⭐ ❌ a default manager that always filters by tenant — ⭐⭐ tempting, and
⭐        it breaks the admin, breaks cascade deletes, and hides rows from
⭐        management commands in ways that are very hard to debug.
⭐   ⭐ ✅ ⭐⭐ AN EXPLICIT `.for_tenant(t)` THAT EVERY VIEW MUST CALL, plus
⭐        ⭐ POSTGRES RLS underneath (Day 160). ⭐⭐ The explicit call is
⭐        reviewable; RLS is the guarantee. ⭐ Same two-layer answer as your
⭐        capstone, in Django's idiom.

⭐⭐ THE THREE-LINE SUMMARY OF THIS DAY:
⭐   ⭐ A QUERYSET IS A DESCRIPTION. It runs when someone needs a row.
⭐   ⭐ `select_related` ADDS COLUMNS; `prefetch_related` AVOIDS ADDING ROWS.
⭐   ⭐⭐ PUT SCOPING AND LOADING IN A QUERYSET METHOD, AND ASSERT THE QUERY
⭐        COUNT — because in Django, the query you did not write is the one
⭐        that will hurt you.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `if qs:` to test for rows | Loads every row. `qs.exists()` is `SELECT 1 ... LIMIT 1`. |
| `len(qs)` for a count | Loads every row — unless you already have them cached, in which case it's free. |
| "Always use `count()`" | Wrong when you're about to iterate anyway — that's a second query. |
| `count()` on a prefetched relation | Still queries. `len(rel.all())` uses the cache. |
| Calling `Model.objects.filter(...)` in a loop | A new QuerySet each time, so a new query each time. The variable is the cache. |
| Expecting `qs[:5]` to slice a cached QuerySet | It's a new QuerySet with a `LIMIT` — it re-queries. |
| `select_related` on a to-many | Row multiplication — 50 orders × 20 items = 1,000 rows. |
| `prefetch_related` on a to-one | An unnecessary second query where a join adds only columns. |
| `.filter()` on a prefetched relation inside a loop | Ignores the prefetch cache and re-queries. Use `Prefetch(queryset=...)`. |
| `only()` then touching another field | A per-row query — you turned one N+1 into another. |
| Loading 2M rows without `.iterator()` | 2M model objects in RAM and an OOM kill. |
| Using models where you need data | `values_list` skips instantiation entirely and is often 5–10× faster. |
| No `assertNumQueries` | Django ships the query-count ceiling built in; there's no excuse. |
| Ignoring queries in templates | An N+1 authored by someone editing HTML, invisible from the view. |
| `django-debug-toolbar` in production | Holds queries in memory and exposes settings. |
| Custom `Manager` methods instead of `QuerySet.as_manager()` | Manager methods don't chain. |
| A default manager that filters by tenant | Breaks the admin, cascades and management commands in confusing ways. |

## Interview questions

**Q: When does a QuerySet hit the database?**

> When something needs an actual row: iteration, `list()`, `bool()`, `len()`, `repr()`, slicing with
> a step, and the terminal methods like `count()`, `exists()`, `get()`, `first()`. Filtering,
> excluding and ordering all return new QuerySets and query nothing — you can even print `qs.query`
> and see the SQL without running it. The one that catches people is `repr()`, because that means
> your debugger and shell evaluate a QuerySet just by displaying it, and people then draw the wrong
> conclusion about where the slowness is. And evaluation caches results *on that QuerySet object*, so
> iterating twice is one query — but calling `Model.objects.filter(...)` again is a brand-new object
> with an empty cache. The variable is the cache.

**Q: `select_related` or `prefetch_related`?**

> `select_related` for to-one — a foreign key or one-to-one — because it becomes a SQL join, and a
> to-one join adds *columns*, not rows. `prefetch_related` for to-many, because joining a to-many
> multiplies rows: fifty orders each with twenty items is a thousand rows, each carrying a full copy
> of the order. That's a bandwidth and memory problem before it's a query-count problem. So the rule
> isn't arbitrary — join when it adds columns, second-query when it would add rows. The subtle trap
> is that filtering a prefetched relation inside the loop ignores the prefetch cache and re-queries,
> so you've paid for the prefetch *and* got the N+1; that's what `Prefetch(queryset=...)` is for. And
> `count()` on a prefetched relation still hits the database, because `COUNT` is SQL — `len(rel.all())`
> uses the cache.

**Q: How do you stop an N+1 reaching production in Django?**

> `assertNumQueries` in the test suite, which is the query-count ceiling built into the framework —
> seed fifty rows, hit the list endpoint, assert at most four queries. It fails on the commit that
> introduces the regression, while the author still has context, and it's the only defence that
> works before production, because an N+1 is invisible to a slow-query log — every one of those fifty
> queries is fast. During development I'd use `django-debug-toolbar` for the duplicate-query view,
> and `django-zen-queries` or `nplusone` to make an unexpected lazy load raise, which is the
> equivalent of SQLAlchemy's `lazy="raise"`. The Django-specific hazard is that templates can query:
> a nested `{% for %}` over a relation is an N+1 written in HTML and invisible to anyone reading the
> view, so marking template rendering query-forbidden is the only real defence there.

**Q: When would you use `values_list` over model instances?**

> When I need data rather than behaviour. Model instantiation is a real cost — for a hundred thousand
> rows, `values_list(flat=True)` is often five to ten times faster, because it skips building objects
> entirely. And there's a safety benefit that matters more to me than the speed: a dict or a tuple
> has no relations, so you *cannot* accidentally trigger a lazy load from it. For a report endpoint,
> which almost never needs model behaviour, that's exactly what I want. For large scans I'd add
> `.iterator()`, since a normal QuerySet loads everything into its result cache and two million model
> objects will OOM the worker — the trade being that `.iterator()` keeps no cache, so iterating twice
> re-queries.

## 🎙️ Articulation drill

**Two minutes: "How do you handle the N+1 in Django?"**

Start with laziness, because everything follows from it — a QuerySet is a description, and the
question is always where it *ran* versus where it was written. Then derive the two tools from row
multiplication rather than reciting them, since deriving it shows you understand the cost model.
Name the two traps that make code *look* optimised while being slow: filtering a prefetched relation
inside the loop, and `count()` on a prefetch. Then the defence, and be concrete: `assertNumQueries`
is Django's built-in query ceiling and there is no excuse for not having one on every list view.
