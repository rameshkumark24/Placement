# Day 278 🎭

**P-278** · 🎭 **Optimistic updates** — ⭐⭐ where the UI lies, and how it confesses

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: an optimistic update is a deliberate lie told to the user for 200
> milliseconds, and it is only ethical when you can take it back exactly — which means the two places
> you must never be optimistic are the places where taking it back is impossible or where the user
> will act on the lie.**
>
> Today: ⭐ the pattern, ⭐⭐ exact rollback, the concurrent-mutation trap, and where to refuse.

---

# Part 1 — The pattern

```typescript
const mutation = useMutation({
  mutationFn: (patch) => client.PATCH("/orders/{id}", { body: patch }),

  onMutate: async (patch) => {
    await qc.cancelQueries({ queryKey: keys.orders.detail(id) });
    //    ⭐⭐ CANCEL FIRST — an in-flight GET can land AFTER your
    //       optimistic write and silently overwrite it (Day 217's race)

    const previous = qc.getQueryData(keys.orders.detail(id));  // ⭐ snapshot
    qc.setQueryData(keys.orders.detail(id), (old) => ({ ...old, ...patch }));
    return { previous };                    // ⭐⭐ handed to onError
  },

  onError: (_err, _patch, ctx) => {
    qc.setQueryData(keys.orders.detail(id), ctx.previous);   // ⭐⭐ EXACT UNDO
    toast.error("Couldn't save — your change was reverted");  // ⭐ TELL THEM
  },

  onSettled: () => {
    qc.invalidateQueries({ queryKey: keys.orders.detail(id) });
    //    ⭐⭐ ALWAYS refetch at the end — success OR failure.
    //       The server may have normalised, defaulted, or partly applied.
  },
});
```

| ⭐ Step | ⭐⭐ Why it is not optional |
|---|---|
| `cancelQueries` | ⭐⭐ Without it, an in-flight refetch overwrites your optimistic value and the UI "flickers back" |
| **Snapshot `previous`** | ⭐ Rollback must restore *exactly* what was there — not a guess, not a recomputation |
| **`onError` restores + tells** | ⭐⭐ A silent revert is worse than an error: the user watched it succeed and now it is gone |
| **`onSettled` invalidates** | ⭐ The server is authoritative. Your optimistic object was an approximation. |

# Part 2 — ⭐⭐ The concurrent-mutation trap

```
⭐⭐ TWO OPTIMISTIC UPDATES IN FLIGHT, ONE FAILS.

⭐   t0  value = A
⭐   t1  ⭐ mutation 1: A → B  (snapshot: A)
⭐   t2  ⭐ mutation 2: B → C  (snapshot: B)
⭐   t3  ⭐⭐ MUTATION 1 FAILS ⇒ rolls back to ITS snapshot: **A**
⭐   ⇒ ⭐⭐ THE SCREEN NOW SHOWS **A**, DISCARDING MUTATION 2's
⭐     CHANGE — WHICH IS STILL IN FLIGHT AND WILL SUCCEED.
⭐   ⇒ ⭐ FINAL STATE: SERVER SAYS C, UI SAID A, UNTIL SOMETHING
⭐     REFETCHES. ⭐⭐ NAIVE ROLLBACK IS ONLY CORRECT FOR ONE
⭐     MUTATION AT A TIME.
```

| ⭐ Fix | |
|---|---|
| **⭐⭐ Disable while pending** | Simplest, and correct. One in flight at a time per resource. **Do this.** |
| **Invalidate instead of restoring** | ⭐ On error, refetch rather than replaying a snapshot — slower, always right |
| **Track a mutation count** | ⭐ Only roll back if yours is the last outstanding one |

> ⭐ **This is the lost-update problem** you met in Stage 5 and again on Day 480 — **two writers, one
> value, and a rollback that does not know about the other writer.** Same shape, in a cache.

# Part 3 — ⭐⭐ Where you must never be optimistic

```
⭐⭐ TWO RULES. BOTH HAVE COST SOMEBODY MONEY.

⭐ ① ⭐⭐ NEVER OPTIMISTIC ON SOMETHING IRREVERSIBLE.
⭐    payments · refunds · sending an email · publishing ·
⭐    deleting without a recycle bin
⭐    ⇒ ⭐ "Payment sent ✅" that later reverts is not a UI glitch,
⭐      it is ⭐⭐ TELLING A USER SOMETHING FALSE ABOUT THEIR MONEY.
⭐    ⇒ ⭐ SHOW PENDING. WAIT FOR THE SERVER. (Day 275's 202.)

⭐ ② ⭐⭐ NEVER OPTIMISTIC WHEN THE USER WILL **ACT** ON THE LIE.
⭐    ⭐ "Invite sent" ⇒ they tell their colleague to check email.
⭐    ⭐ "Balance updated" ⇒ they make a decision on the number.
⭐    ⇒ ⭐⭐ THE 200 ms YOU SAVED IS WORTH LESS THAN THE ONE TIME
⭐      IT IS WRONG.

⭐ ✅ ⭐ OPTIMISTIC IS RIGHT FOR: a toggle, a like, reordering,
⭐    marking read, adding a tag — ⭐⭐ CHEAP, REVERSIBLE, AND THE
⭐    USER WILL SEE THE TRUTH IMMEDIATELY IF IT FAILS.
```

| ⭐ Better than optimistic, often | |
|---|---|
| **Pending state** | ⭐ Show the row greyed with a spinner. Honest, and nearly as fast to *feel*. |
| **⭐⭐ Undo** | Act for real, offer "Undo" for 8 s. **No lie at all**, and the user gets the same speed. |
| **Disable + spinner** | ⭐ For a single button, this is enough and costs nothing to reason about |

# Part 4 — Failing honestly

```
⭐⭐ WHEN THE ROLLBACK HAPPENS, THE USER MUST KNOW **WHAT** WAS LOST.

⭐   ❌ "Something went wrong"      ⇒ ⭐ lost WHAT?
⭐   ❌ ⭐⭐ SILENT REVERT           ⇒ THE WORST OPTION. They saw it
⭐      work. Now it is gone and they think they imagined it.
⭐   ✅ ⭐ "Couldn't update the status — reverted to Paid. [Retry]"
⭐      ⇒ names the field, names the value restored, offers the fix.

⭐   ⭐⭐ AND IF THE FAILURE WAS A 409 (someone else edited it):
⭐     ⭐ DO NOT SILENTLY OVERWRITE OR SILENTLY DISCARD.
⭐     "This changed while you were editing. [See their version]
⭐      [Keep mine]" ⇒ ⭐⭐ CONFLICT IS A UI STATE, NOT AN ERROR.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "do you use optimistic updates?"**

Define it honestly — the framing is the answer. **Selectively, and I describe it as what it is: a
deliberate lie told to the user for a couple of hundred milliseconds. It's only ethical when I can take
it back exactly, which means snapshotting the previous value rather than recomputing it, cancelling
in-flight queries first so a refetch doesn't overwrite my optimistic write, and always invalidating at
the end because the server is authoritative and my optimistic object was an approximation.**

Then the bug that shows you ran into it. **Naive rollback is only correct for one mutation at a time.
With two in flight, if the first fails it rolls back to its own snapshot and discards the second
change — which is still in flight and about to succeed. The UI ends up showing a value the server
disagrees with until something refetches. It's the lost-update problem in a cache, and I fixed it by
allowing one mutation per resource at a time.**

Then the boundary, which is the judgement part. **Two places I'm never optimistic. Anything
irreversible — payments, refunds, sending email — because "Payment sent" that later reverts isn't a UI
glitch, it's telling someone something false about their money. And anything the user will act on: if
"invite sent" makes them tell a colleague to check their inbox, the two hundred milliseconds I saved is
worth less than the one time it's wrong. Those get a pending state and wait for the server.**

Close on the alternative and the failure path. **Where I can, I prefer undo — act for real, offer to
reverse it for eight seconds. Same perceived speed, no lie at all. And when a rollback does happen the
user is told what was lost and what it reverted to, because a silent revert is the worst option
available: they watched it work, and now it's gone.**
