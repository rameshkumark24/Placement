# Day 046

**L-046** · ⭐ **Iterators and the iteration protocol** — `__iter__`/`__next__`, `StopIteration`

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an *iterable* can produce an iterator; an *iterator* is the thing being
> consumed, and it is used up exactly once.** Confusing the two is the source of every "why is my
> data empty the second time?" bug.
>
> ⭐ This is the protocol underneath `for`, comprehensions, `zip`, `sum`, unpacking, `in`, and
> tomorrow's generators — one small interface with an enormous surface area.

---

# Part 1 — ⭐⭐ What `for` actually does

```python
for x in thing:
    body(x)
```

```
⭐⭐ COMPILES TO ROUGHLY:
⭐   it = iter(thing)          ⇒ calls thing.__iter__()   ⭐ (or the old __getitem__ protocol)
⭐   while True:
⭐       try:    x = next(it)  ⇒ calls it.__next__()
⭐       except StopIteration: break
⭐       body(x)
⭐
⭐ ⇒ ⭐⭐ StopIteration IS NOT AN ERROR. It is the protocol's "I'm done" signal, implemented
⭐      as an exception — which is why `for` costs a little more than a C loop, and why
⭐      exception handling in CPython is optimised so heavily.
```

| ⭐ Term | ⭐⭐ Definition | ⭐ Test |
|---|---|---|
| ⭐⭐ **Iterable** | has `__iter__` — ⭐ *can produce* an iterator | `list`, `dict`, `str`, `set`, `range`, a file |
| ⭐⭐ **Iterator** | has `__next__` **and** `__iter__` returning `self` | ⭐ a generator, `zip(...)`, `map(...)`, `enumerate(...)` |

```python
lst = [1, 2, 3]
iter(lst) is lst             # ⭐⭐ False — a list is ITERABLE, not an iterator
it = iter(lst)
iter(it) is it               # ⭐⭐ True — an iterator returns ITSELF from __iter__
```

⭐⭐ **Every iterator is an iterable; not every iterable is an iterator.** ⭐ And the reason an
iterator must implement `__iter__` returning `self` is so it can be used directly in a `for` — which
is why you can write `for x in zip(a, b)` and also pass it to `list()`.

# Part 2 — ⭐⭐ Exhaustion: the bug this day exists for

```python
it = iter([1, 2, 3])
list(it)          # ⭐ [1, 2, 3]
list(it)          # ⭐⭐ [] — GONE. An iterator is consumed ONCE.

lst = [1, 2, 3]
list(lst); list(lst)          # ⭐ both give [1,2,3] — a list is re-iterable
```

```python
# ⚠️⚠️ ⭐⭐ THE PRODUCTION VERSION — and it does not raise:
rows = (parse(line) for line in f)     # ⭐ a generator (Day 047)
count = sum(1 for _ in rows)           # ⭐⭐ CONSUMES it
for r in rows:                         # ⭐⭐ runs ZERO times. No error. No warning.
    process(r)                         #    Your job silently processed nothing.
```

```
⭐⭐ THE FOUR PLACES THIS BITES:
⭐  1. counting, then iterating (above)
⭐  2. ⭐ zip(gen, gen) — ⭐⭐ BOTH names point at ONE iterator ⇒ you get (0,1),(2,3),(4,5)
⭐  3. checking `if not list(gen)` and then iterating it
⭐  4. ⭐⭐ passing the same generator to two functions
⭐
⭐ ⭐⭐ THE FIXES, in order of preference:
⭐   · materialise it once:  rows = list(gen)      ⇒ ⭐ if it fits in memory
⭐   · make the SOURCE re-iterable: a function returning a fresh generator each call
⭐   · itertools.tee(gen, 2)  ⇒ ⚠️ ⭐ buffers everything one branch reads ahead of the other
```

⭐⭐ **The middle option is the good one and it is under-used:**

```python
def rows():                        # ⭐⭐ call it again to get a fresh pass
    with open(path) as f:
        for line in f:
            yield parse(line)

sum(1 for _ in rows())             # ⭐ fresh
for r in rows(): ...               # ⭐ fresh again
```

# Part 3 — ⭐ Writing an iterator

```python
class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self):
        return CountdownIterator(self.n)      # ⭐⭐ a NEW iterator per for-loop ⇒ re-iterable

class CountdownIterator:
    def __init__(self, n): self.n = n
    def __iter__(self): return self           # ⭐ required
    def __next__(self):
        if self.n <= 0: raise StopIteration   # ⭐⭐ the protocol's terminator
        self.n -= 1
        return self.n + 1
```

⭐⭐ **The separation is the whole design lesson: the *collection* is iterable, the *cursor* is the
iterator.** ⚠️ **If `__iter__` returns `self`, the object can only be looped over once** — which is
correct for a stream and wrong for a collection. **Nearly every "my custom class only works in one
`for` loop" bug is this.**

```python
# ⭐ In practice you write it as a generator (Day 047) — one method, no second class:
class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self):
        for i in range(self.n, 0, -1):
            yield i                            # ⭐⭐ a fresh generator per call. Re-iterable, free.
```

⭐ **The legacy `__getitem__` protocol still works:** an object with `__getitem__` taking `0, 1, 2…`
and raising `IndexError` is iterable, because `iter()` falls back to it. **You will meet it in old
code; do not write it.**

```python
# ⭐ The two-argument iter() — genuinely useful and almost unknown:
for chunk in iter(lambda: f.read(4096), b""):     # ⭐⭐ call until it returns the SENTINEL
    process(chunk)
for line in iter(input, "quit"): ...
```

# Part 4 — ⭐ Consuming iterators well

```python
next(it)                     # ⭐ raises StopIteration when exhausted
next(it, default)            # ⭐⭐ returns default instead — use this in application code
list(it) / tuple(it) / set(it) / dict(it)
sum(it) / min(it) / max(it) / any(it) / all(it)      # ⭐ all take iterators, all are lazy-friendly
sorted(it)                   # ⭐ materialises internally — it must
enumerate(it, start=1)       # ⭐ lazy
zip(a, b, strict=True)       # ⭐ lazy (Day 034)
reversed(seq)                # ⚠️ ⭐ needs __reversed__ or len+__getitem__ — NOT any iterator
```

```
⭐⭐ any() AND all() SHORT-CIRCUIT, and combined with a generator that is a real optimisation:
⭐   any(is_bad(x) for x in huge)    ⇒ ⭐⭐ stops at the FIRST bad one; never builds a list
⭐   all(check(x) for x in huge)     ⇒ stops at the first failure
⭐ ⇒ ⭐ compare: any([is_bad(x) for x in huge]) ⇒ ⭐⭐ evaluates EVERY element first. Brackets matter.
```

⚠️ ⭐⭐ **`StopIteration` inside a generator is a `RuntimeError` (PEP 479).** If you call `next(it)`
inside a generator and it raises, the exception used to silently end your generator; since Python 3.7
it becomes `RuntimeError: generator raised StopIteration`. **Use `next(it, None)` and check, or catch
it explicitly.**

```python
# ⭐ Peeking without consuming — there is no built-in, so:
import itertools
first = next(it, None)
if first is not None:
    it = itertools.chain([first], it)      # ⭐⭐ push it back on the front
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Iterating an iterator twice** | ⭐⭐ Exhausted after one pass, silently. |
| ⭐ Confusing iterable and iterator | ⭐ One produces; one is consumed. |
| `zip(gen, gen)` | ⭐⭐ One iterator, pairs of consecutive items. |
| `__iter__` returning `self` on a collection | ⭐⭐ Makes it single-use. Return a new iterator. |
| Counting a generator then looping it | ⭐ Zero iterations, no error. |
| ⭐ `any([...])` instead of `any(...)` | ⭐⭐ The list is built first — no short-circuit. |
| `next(it)` with no default in app code | ⭐ `StopIteration` escapes as a confusing error. |
| `next()` inside a generator | ⭐⭐ PEP 479 turns it into `RuntimeError`. |
| Expecting `reversed()` on any iterator | ⭐ It needs a sequence or `__reversed__`. |
| Using `tee` casually | ⭐ It buffers the gap between branches. |

## Interview questions

**Q: What's the difference between an iterable and an iterator?**
> An iterable implements `__iter__` and can produce an iterator; an iterator implements `__next__`
> and also `__iter__` returning itself, and it holds the position. A list is iterable but not an
> iterator — `iter(lst) is lst` is False, and each `for` gets a fresh cursor, which is why you can
> loop over a list twice. A generator *is* an iterator, so it's consumed once and the second loop
> silently does nothing.

**Q: What does `for x in y` actually do?**
> Calls `iter(y)` once, then `next()` on the result repeatedly until `StopIteration` is raised, which
> it catches and treats as the end. So the terminator is an exception rather than a sentinel value —
> which is unusual, and it's part of why CPython optimises exception handling so heavily. It also
> means anything implementing those two methods works in a `for`, with no inheritance involved —
> Day 031's protocol point again.

**Q: You count the rows in a generator, then loop over it, and get nothing. Why?**
> Because counting consumed it. An iterator has one pass, and once it's exhausted every subsequent
> iteration yields nothing — with no error, which is the dangerous part. The options are to
> materialise it into a list if it fits, or better, to make the *source* re-iterable: write a
> function that returns a fresh generator each call, so `rows()` gives me a new pass every time.
> `itertools.tee` exists but it buffers whatever gap opens between the two branches, so it can use as
> much memory as the list would have.

**Q: How would you make a custom class iterable, and what's the trap?**
> Implement `__iter__`. The trap is returning `self` and putting `__next__` on the same object — that
> works, but it means the object can only be looped over once, because there's one shared position.
> That's correct for a stream and wrong for a collection. The clean version is for `__iter__` to be a
> generator function, so each call produces a fresh independent generator, and you get re-iterability
> for free with one method instead of two classes.

**Q: Why does `any(x for x in ...)` differ from `any([x for x in ...])`?**
> The brackets build the whole list first, so every element is evaluated before `any` sees anything.
> Without them it's a generator expression, and `any` short-circuits at the first true value. On a
> large or expensive sequence that's the difference between doing one unit of work and doing all of
> it — and it's two characters.

## 🎙️ Articulation drill

Record two minutes: **"A colleague's data pipeline silently processes zero rows. Debug it out
loud."**

⭐ Name the suspect immediately: **something consumed the iterator before the loop.** A `sum(1 for _
in rows)` to log the count, an `if not list(rows)` guard, or the same generator passed to two
functions — **all of which exhaust it, and none of which raise.** ⭐ The tell is that the failure is
silent: an exhausted iterator yields nothing and reports nothing.

⭐ Then the distinction that explains it: **a list is iterable, so every `for` gets a fresh cursor. A
generator *is* the cursor, so there is only one pass.**

⭐⭐ **Then the fix, and argue for the right one:** *"materialising with `list()` works if it fits, but
that throws away the reason the pipeline was a generator. The better fix is to make the source
re-iterable — a function that returns a fresh generator each call, so `rows()` gives a new pass every
time and the constant-memory property survives. `itertools.tee` is the option people reach for and
it quietly buffers everything one branch reads ahead of the other, so it can cost as much as the list
would have."*
