# Part 1 — ⭐ Replica sets, and the anomalies you already know

```
⭐   PRIMARY ──oplog──▶ SECONDARY ⭐ (replicates + can serve reads)
⭐           ──oplog──▶ SECONDARY
⭐   ⭐ The OPLOG is a capped collection of idempotent operations —
⭐     ⭐⭐ Postgres's WAL, at the logical level. Same idea, and the same
⭐     three jobs: recovery, replication, and change streams.
⭐   ⭐ Elections via Raft: a majority elects a new primary in ~10 s.
⭐   ⭐⭐ AN EVEN NUMBER OF VOTING MEMBERS IS A MISTAKE — 4 nodes
⭐     tolerate the same single failure as 3 and cost more. ⭐ Use an
⭐     arbiter only when you must, and know it holds no data.

⭐⭐ READ PREFERENCE — and every option below `primary` buys you Day
⭐   201's anomalies:
⭐   ⭐ primary (default) · primaryPreferred · secondary ·
⭐     secondaryPreferred · nearest
⭐   ⇒ ⭐⭐ READ-YOUR-WRITES, MONOTONIC READS AND CAUSAL VIOLATIONS ARE
⭐     ALL AVAILABLE HERE, IDENTICALLY. ⭐ Reading from a secondary is
⭐     the same consistency-model change it was in Postgres.
```

```javascript
// ⭐⭐ AND HERE MONGO GIVES YOU SOMETHING POSTGRES MAKES YOU BUILD:
with client.start_session(causal_consistency=True) as s:
    db.orders.insert_one({...}, session=s)
    db.orders.find_one({...}, session=s)   # ⭐⭐ GUARANTEED to see it,
                                           #    even from a secondary
// ⭐⭐ CAUSALLY CONSISTENT SESSIONS: the driver tracks a cluster time
//    and the server WAITS for the secondary to catch up.
//    ⇒ ⭐⭐ THIS IS DAY 201'S LSN-TOKEN SOLUTION, BUILT IN AND
//      AUTOMATIC. ⭐ It is a genuine, specific Mongo advantage and it
//      is worth naming when someone asks what Mongo does better.
//    ⭐ Cost: a read may WAIT, so it trades latency for correctness —
//      and it requires `readConcern: majority`.
```

# Part 2 — ⭐⭐ Write concern and read concern: tunable consistency, made explicit

```
⭐⭐ WRITE CONCERN — "when may the driver return?"
⭐   ⭐ w: 0          fire and forget. ⭐⭐ Not even an error is returned.
⭐   ⭐ w: 1          the primary has it. ⭐⭐ LOST ON FAILOVER.
⭐   ⭐⭐ w:"majority" a majority have it ⇒ ⭐⭐ IT SURVIVES AN ELECTION.
⭐        ⭐ Default since 5.0.
⭐   ⭐ j: true       flushed to the journal on those nodes (durability
⭐                    against power loss, not just process loss)
⭐   ⭐ wtimeout      ⭐⭐ AND THE TRAP: A `wtimeout` EXPIRY DOES ***NOT***
⭐        ROLL THE WRITE BACK. It tells you "I could not confirm" —
⭐        ⭐⭐ which is Day 166's `payment_unknown`, exactly: a timeout
⭐        means "I don't know", not "it failed".

⭐⭐ READ CONCERN — "what am I allowed to see?"
⭐   ⭐ local        whatever this node has, ⭐⭐ INCLUDING WRITES THAT
⭐                   MAY LATER BE ROLLED BACK BY AN ELECTION
⭐   ⭐ available    like local, no shard consistency check (fastest,
⭐                   loosest)
⭐   ⭐⭐ majority   only data acknowledged by a majority ⇒ ⭐⭐ IT
⭐                   CANNOT BE ROLLED BACK. ⭐ This is the one you want.
⭐   ⭐ linearizable strongest, ⭐⭐ primary only, and it WAITS. Slow;
⭐                   reserve for the rare read that must be definitive.
⭐   ⭐ snapshot     a consistent point-in-time view — used by
⭐                   transactions.

⭐ ⇒ ⭐⭐ THE PAIRING THAT MATTERS: `w:"majority"` + `readConcern:
⭐   "majority"` GIVES YOU READ-YOUR-WRITES ON THE PRIMARY AND NO
⭐   ROLLED-BACK READS. ⭐⭐ `w:1` + `local` — the old defaults — is what
⭐   produced every "MongoDB lost my data" story, and it was a
⭐   configuration, not a defect.
⭐ ⭐⭐ SAY THIS IN AN INTERVIEW: MongoDB's consistency is not weak, it
⭐   is TUNABLE — and the burden that puts on you is to know which
⭐   setting you have, which is exactly the burden of a Postgres
⭐   isolation level.
```

# Part 3 — ⭐ Multi-document transactions, honestly

```python
with client.start_session() as s:
    with s.start_transaction(
        read_concern=ReadConcern("snapshot"),
        write_concern=WriteConcern("majority"),
    ):
        db.accounts.update_one({"_id": a}, {"$inc": {"bal": -100}}, session=s)
        db.accounts.update_one({"_id": b}, {"$inc": {"bal":  100}}, session=s)
# ⭐ Snapshot isolation. ⭐⭐ Conflicts raise `TransientTransactionError`,
#   which means ⭐⭐ YOU NEED DAY 195'S RETRY LOOP — same shape, same two
#   mistakes to avoid (retry the whole logic; no side effects inside).
```

```
⭐⭐ THE COSTS, WHICH ARE THE REAL ARGUMENT:
⭐   ⭐ 60-SECOND DEFAULT LIMIT (`transactionLifetimeLimitSeconds`).
⭐     ⭐⭐ A bulk update of 400,000 documents (Day 211) will not fit.
⭐   ⭐ The snapshot is held in the WiredTiger cache ⇒ ⭐⭐ a long
⭐     transaction pressures memory for everyone. ⭐ Same shape as Day
⭐     194's xmin horizon: one long reader taxes the whole system.
⭐   ⭐⭐ ACROSS SHARDS IT IS A TWO-PHASE COMMIT — coordinator, prepare,
⭐     commit — with the latency and failure modes 2PC always has.
⭐   ⭐ Documents touched are locked, so contention behaves like any
⭐     other database's.

⭐⭐ THE HONEST POSITION:
⭐   ⭐ USE THEM for the genuinely rare cross-document operation — a
⭐     transfer, a two-collection state change — where you have already
⭐     concluded the alternative is worse.
⭐   ⭐⭐ IF YOU NEED THEM ON A HOT PATH, THAT IS A DESIGN SIGNAL: the
⭐     document model exists so that the aggregate you must change
⭐     atomically is ***ONE DOCUMENT***. ⭐⭐ A single-document update is
⭐     atomic for free — `$inc`, `$push`, `$set` on nested paths,
⭐     conditional updates with a filter — and that covers far more than
⭐     people expect once the schema is right.
⭐   ⇒ ⭐⭐ "WE ADDED TRANSACTIONS" IS OFTEN THE FIX FOR "WE MODELLED IT
⭐     AS TWO DOCUMENTS WHEN IT WAS ONE."
```

# Part 4 — ⭐⭐ Sharding, and the one decision you cannot take back

```
⭐   mongos (router) → config servers (metadata)
⭐                   → shard A [replica set] · shard B · shard C
⭐   ⭐ Data is split into CHUNKS by the SHARD KEY and balanced across
⭐     shards automatically.

⭐⭐ THE SHARD KEY MUST HAVE THREE PROPERTIES. MISSING ANY ONE IS FATAL:

⭐ ① ⭐⭐ HIGH CARDINALITY — the number of possible values bounds the
⭐    number of chunks. ⭐ `country` gives you ~195 chunks and no more,
⭐    ever, however much data you have.
⭐ ② ⭐⭐ LOW FREQUENCY — no single value may dominate. ⭐ If 60% of
⭐    documents share one tenant_id, that shard holds 60% of your data
⭐    and cannot be split further. ⭐⭐ A JUMBO CHUNK: too big to move,
⭐    too big to split, permanently unbalanced.
⭐ ③ ⭐⭐ NON-MONOTONIC — ⭐⭐ THE ONE PEOPLE GET WRONG. A key that
⭐    always increases (a timestamp, an ObjectId, an auto-increment)
⭐    means ⭐⭐ EVERY NEW WRITE GOES TO THE SAME "MAX" CHUNK ON THE SAME
⭐    SHARD. ⭐ You have N shards and one of them is doing all the
⭐    writing, permanently. ⭐⭐ SHARDING GAVE YOU NO WRITE SCALING AT
⭐    ALL, which is usually the reason you sharded.
⭐    ⇒ ⭐ Fix: HASHED sharding (`{_id: "hashed"}`) distributes evenly —
⭐      ⭐⭐ AT THE COST OF RANGE QUERIES, which now scatter to every
⭐      shard. ⭐ Or a COMPOUND key that leads with something
⭐      well-distributed: `{tenant_id: 1, created_at: 1}`.

⭐⭐ AND THE FOURTH PROPERTY, WHICH IS ABOUT READS:
⭐   ⭐ A query that INCLUDES the shard key is ***TARGETED*** — routed to
⭐     one shard.
⭐   ⭐⭐ A query WITHOUT it is ***SCATTER-GATHER*** — sent to EVERY
⭐     shard, results merged by mongos.
⭐   ⇒ ⭐⭐ SO THE SHARD KEY MUST APPEAR IN YOUR HOT QUERIES, or every
⭐     read costs the whole cluster. ⭐ This is Day 200's partition-key
⭐     rule, with a much higher penalty for getting it wrong.
⭐   ⭐⭐ AND: A UNIQUE INDEX ON A SHARDED COLLECTION MUST BE PREFIXED BY
⭐     THE SHARD KEY — ⭐ Day 200's constraint, verbatim, for the same
⭐     reason.
```

```
⭐⭐ WHEN DO YOU ACTUALLY NEED IT? BE SCEPTICAL:
⭐   ⭐ The working set no longer fits in one machine's RAM.
⭐   ⭐ Write throughput exceeds one primary (⭐⭐ and you have already
⭐     checked it is not an index or a schema problem).
⭐   ⭐ Data volume exceeds one machine's storage.
⭐   ⭐ A genuine geographic-residency requirement (zone sharding).
⭐   ⇒ ⭐⭐ MOST PEOPLE WHO SHARD DID NOT NEED TO. A single replica set
⭐     on modern hardware handles a very large amount, and sharding buys
⭐     you a router, config servers, cross-shard transactions as 2PC,
⭐     scatter-gather reads, a balancer, and a decision you cannot undo.
⭐   ⭐ Mongo 5.0+ can RESHARD — ⭐⭐ it rewrites the entire collection.
⭐     It makes the decision recoverable, not cheap. ⭐ Plan as though
⭐     it were permanent.
```

## Interview questions

**Q: Does MongoDB have transactions, and would you use them?**

> Yes, multi-document transactions since 4.0 on replica sets and 4.2 sharded, with snapshot isolation
> and a `TransientTransactionError` on conflict that needs the same retry loop as a Postgres
> serialization failure. So the old "Mongo has no transactions" line is years out of date. But the
> costs are the real argument: a sixty-second default limit, a snapshot held in the WiredTiger cache so
> a long transaction pressures memory for everyone — the same shape as a long reader pinning Postgres's
> xmin horizon — and across shards it's a two-phase commit with all the latency and failure modes 2PC
> carries. So I'd use them for the genuinely rare cross-document operation, and treat needing them on a
> hot path as a design signal: the document model exists precisely so that the thing you must change
> atomically is one document, and a single-document update is atomic for free, including `$inc`,
> `$push` and conditional updates. "We added transactions" is often the fix for "we modelled it as two
> documents when it was one."

**Q: How do you choose a shard key?**

> Three properties, and missing any one is fatal. High cardinality, because the number of distinct
> values bounds the number of chunks forever — sharding on country gives you about a hundred and
> ninety-five chunks no matter how much data you have. Low frequency, because if one value covers most
> documents that shard holds most of your data and can't be split, which is a jumbo chunk: too big to
> move, too big to split, permanently unbalanced. And non-monotonic, which is the one people get wrong:
> a timestamp or an ObjectId always increases, so every new write goes to the max chunk on one shard —
> you have N shards and one of them does all the writing, which means sharding bought you no write
> scaling at all, and write scaling is usually why you sharded. Hashed sharding fixes distribution at
> the cost of range queries scattering everywhere; a compound key leading with something
> well-distributed is often better. And the fourth consideration is reads: a query without the shard
> key is scatter-gather to every shard, so the key has to appear in your hot queries — which is the
> partition-key rule with a much higher penalty.

**Q: What's MongoDB's consistency model?**

> Tunable, which is the accurate word — not weak. Write concern says when the driver may return: `w:0`
> is fire-and-forget, `w:1` means the primary has it and it's lost on failover, and `w:"majority"`
> means it survives an election. Read concern says what you're allowed to see: `local` includes writes
> that could still be rolled back by an election, and `majority` cannot be rolled back. The pairing
> that matters is `w:"majority"` with `readConcern:"majority"`, which since 5.0 is roughly the default;
> the old `w:1` plus `local` is what produced every "MongoDB loses data" story, and that was a
> configuration rather than a defect. The one genuinely nice thing on top is causally consistent
> sessions — the driver carries a cluster time and the server makes a secondary catch up before
> answering, which is the LSN-token solution from Postgres replication built in and automatic. And the
> trap worth naming: a `wtimeout` expiring does *not* roll the write back, it means "I couldn't
> confirm", which is the third outcome you have to model.

**Q: When do you actually need sharding?**

> When the working set no longer fits in one machine's RAM, when write throughput genuinely exceeds one
> primary, when data volume exceeds one machine's storage, or when there's a real geographic residency
> requirement. And I'd be sceptical about the second one specifically, because most write-throughput
> problems turn out to be a missing index, an unbounded array causing document rewrites, or a schema
> that makes every update touch too much. What sharding buys you along with scale is a router, config
> servers, cross-shard transactions as two-phase commit, scatter-gather reads for anything missing the
> shard key, a balancer to operate, and a decision you can only undo by rewriting the entire
> collection. Resharding exists since 5.0, which makes the decision recoverable rather than cheap. So
> the honest summary is that a single replica set on modern hardware handles a great deal, and most
> people who sharded didn't need to.

**Q: You've spent twenty-eight days on databases. What's the single most transferable idea?**

> That almost none of it was about a vendor. The B-tree arithmetic is the same in Postgres and Mongo,
> and so is the composite index rule — Mongo documents it as ESR and Postgres people derive the same
> equality-sort-range ordering, because it follows from the structure rather than the product. Row
> multiplication is a double join in SQL, two `$unwind`s in an aggregation, and two `Count()`
> annotations in Django — one fact, three costumes. At-least-once is the only real delivery guarantee
> whether you use Streams, Kafka, SQS or `SKIP LOCKED`, so idempotency is the price of admission
> regardless. Snapshot-versus-current is a domain question that produces the same schema in a
> relational database and a document one. And every tuning conversation reduces to the same discipline:
> measure, find where the estimate and reality disagree, name the cause before proposing a fix. What
> changes between systems is which wrong thing is the default.
