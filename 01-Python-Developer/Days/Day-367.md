# Day 367 🔀

**P-367** · 🔀 **Nginx** — reverse proxy, TLS termination, and ⭐⭐ the slow client

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: Nginx is not in front of your Python app for speed — it is there to
> decouple client speed from worker occupancy, so that a phone on a train uploading at 5 KB/s cannot
> consume a worker for four minutes, and every other reason you will hear is a bonus on top of that
> one.**

---

# Part 1 — ⭐⭐ The slow client, with the arithmetic

```
⭐⭐ THE SCENARIO:
⭐   ⭐ A gunicorn ***sync*** worker serves exactly one
⭐     connection at a time.
⭐   ⭐ A client on a bad mobile connection sends a 1 MB request
⭐     body at 5 KB/s.
⭐   ⇒ ⭐⭐ THAT WORKER IS OCCUPIED FOR ***200 SECONDS***, DOING
⭐     ESSENTIALLY NOTHING.
⭐   ⭐ Four workers ⇒ ⭐⭐ FOUR SUCH CLIENTS TAKE THE SERVICE
⭐     DOWN AT 2% CPU. ⭐ Nothing on your dashboard looks wrong.
⭐   ⇒ ⭐ This is Slowloris arriving by accident, ⭐⭐ AND IT IS
⭐     ALSO A TRIVIAL DELIBERATE ATTACK.

⭐⭐ NGINX'S FIX: ***IT BUFFERS.***
⭐   ⭐ It accepts the request slowly, ⭐ into memory or a temp
⭐     file, ⭐⭐ AND HANDS A ***COMPLETE*** REQUEST TO GUNICORN
⭐     IN MICROSECONDS.
⭐   ⭐ Same on the way out: it takes the response instantly and
⭐     dribbles it to the client at whatever pace they manage.
⭐   ⇒ ⭐⭐ WORKER OCCUPANCY IS NOW PROPORTIONAL TO ***WORK
⭐     DONE***, NOT TO ***CLIENT BANDWIDTH.*** ⭐ That sentence
⭐     is the whole day.

⭐⭐ AND THE ASYNC NUANCE, WHICH IS WHERE PYTHON PEOPLE PUSH
⭐   BACK:
⭐   ⭐ ⭐⭐ AN ASYNC UVICORN WORKER IS ***MUCH*** LESS
⭐     VULNERABLE — a slow client is just a coroutine that is
⭐     awaiting, and thousands can wait concurrently.
⭐   ⇒ ⭐ So is Nginx pointless with async? ⭐⭐ NO, AND THE
⭐     HONEST REASONS ARE:
⭐     ⭐ ① Slow clients still consume file descriptors, memory
⭐       buffers and connection-limit slots.
⭐     ⭐ ② ⭐⭐ TLS TERMINATION AND HTTP/2 ARE CPU WORK YOU DO
⭐       NOT WANT ON THE GIL (Part 3).
⭐     ⭐ ③ Static files, compression, caching, rate limiting and
⭐       request-size limits are ⭐⭐ WORK THAT SHOULD NEVER
⭐       REACH PYTHON AT ALL.
⭐   ⇒ ⭐⭐ SO THE PRECISE ANSWER: ***WITH SYNC WORKERS, NGINX IS
⭐     A CORRECTNESS REQUIREMENT. WITH ASYNC WORKERS, IT IS AN
⭐     EFFICIENCY AND SECURITY LAYER.*** ⭐ Both are worth
⭐     having; only the first is urgent.
```

# Part 2 — ⭐⭐ A configuration worth understanding line by line

```nginx
upstream app {
    server api:8000;
    keepalive 32;                       # ⭐⭐ REUSE UPSTREAM CONNS
}

server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;  # ⭐⭐ RESUMPTION = 1-RTT
    ssl_session_tickets off;             # ⭐ forward secrecy

    client_max_body_size 10m;            # ⭐⭐ REJECT BEFORE PYTHON
    client_body_timeout  10s;            # ⭐⭐ THE SLOWLORIS FIX
    client_header_timeout 10s;

    location /static/ {
        alias /srv/static/;
        expires 1y;                      # ⭐ Day 327: hashed names
        add_header Cache-Control "public, immutable";
    }

    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;          # ⭐⭐ REQUIRED FOR KEEPALIVE
        proxy_set_header Connection "";  # ⭐⭐ …AND SO IS THIS

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;   # ⭐⭐ PART 4

        proxy_connect_timeout 2s;        # ⭐ decreasing inward
        proxy_send_timeout   30s;
        proxy_read_timeout   30s;
    }

    location /events {                   # ⭐ SSE (Day 269)
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_buffering off;             # ⭐⭐ OR EVENTS ARRIVE IN
        proxy_read_timeout 1h;           #   A CLUMP, MINUTES LATE
    }

    location /ws {                       # ⭐ WebSocket (Day 352)
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;   # ⭐⭐ REQUIRED
        proxy_set_header Connection "upgrade";    # ⭐⭐ REQUIRED
        proxy_read_timeout 3600s;                 # ⭐ idle sockets
    }
}
```

```
⭐⭐ THE SIX LINES THAT ARE ACTUALLY LOAD-BEARING:
⭐   ① ⭐⭐ `client_body_timeout` — ***THIS IS THE SLOW-CLIENT
⭐      DEFENCE.*** ⭐ Buffering helps; a timeout is what stops
⭐      an attacker holding ten thousand connections open.
⭐   ② ⭐⭐ `keepalive` + `proxy_http_version 1.1` + `Connection
⭐      ""` — ⭐ all three, or upstream keepalive silently does
⭐      not happen and you pay a TCP handshake per request.
⭐   ③ ⭐ `client_max_body_size` — ⭐⭐ A 2 GB UPLOAD IS REJECTED
⭐      AT THE EDGE INSTEAD OF BUFFERED THROUGH TO PYTHON.
⭐   ④ ⭐⭐ `proxy_buffering off` FOR SSE. ⭐ Without it, SSE
⭐      appears completely broken and the bug is invisible in
⭐      the application.
⭐   ⑤ ⭐⭐ THE `Upgrade`/`Connection` PAIR FOR WEBSOCKETS. ⭐ Miss
⭐      either and the handshake fails with a confusing 400.
⭐   ⑥ ⭐ Timeouts decreasing inward (Day 325).
```

# Part 3 — ⭐⭐ TLS termination, and why it belongs here

```
⭐⭐ THE COST OF TLS:
⭐   ⭐ A handshake is asymmetric crypto — ⭐ expensive.
⭐     ⭐ Symmetric encryption afterwards is cheap and usually
⭐     hardware-accelerated.
⭐   ⇒ ⭐⭐ SO THE COST IS DOMINATED BY ***NEW CONNECTIONS***,
⭐     NOT BY BYTES — which is why session resumption and
⭐     keepalive matter far more than cipher choice.

⭐⭐ WHY TERMINATE AT NGINX RATHER THAN IN PYTHON:
⭐   ⭐ ⭐⭐ TLS IN PYTHON RUNS ON THE GIL-BOUND PROCESS. ⭐ Nginx
⭐     does it in C, in an event loop, across all cores.
⭐   ⭐ ⭐⭐ CERTIFICATE ROTATION BECOMES A RELOAD (`nginx -s
⭐     reload`), NOT A DEPLOY. ⭐ That is the operational
⭐     argument and it is the one that matters day to day.
⭐   ⭐ One place to configure protocols and ciphers, ⭐ one
⭐     place to fix when a protocol is deprecated.
⭐   ⇒ ⭐ In cloud environments the ALB/CloudFront usually
⭐     terminates instead, ⭐⭐ AND THEN NGINX'S REMAINING JOBS
⭐     ARE BUFFERING, STATIC FILES AND LIMITS — which is still
⭐     enough to justify it.

⭐⭐ AND THE THREE HEADERS THAT MUST BE RIGHT:
⭐   ⭐ `Strict-Transport-Security` — ⭐⭐ WITH CARE: `preload`
⭐     AND A LONG `max-age` ARE EFFECTIVELY IRREVERSIBLE for
⭐     that domain. ⭐ Start with a short max-age.
⭐   ⭐ ⭐⭐ `X-Forwarded-Proto` — WITHOUT IT, YOUR APP THINKS
⭐     EVERY REQUEST IS PLAIN HTTP, SO IT BUILDS `http://`
⭐     REDIRECT URLS AND ⭐⭐ REFUSES TO SET `Secure` COOKIES,
⭐     WHICH SILENTLY DOWNGRADES YOUR SESSION SECURITY.
⭐   ⭐ HTTP→HTTPS redirect on port 80, ⭐ and nothing else on
⭐     port 80.
```

# Part 4 — ⭐⭐ The forwarded-headers trap

```
⭐⭐ THE PROBLEM: behind a proxy, ***every*** request appears to
⭐   come from the proxy's IP.
⭐   ⇒ ⭐ Your per-IP rate limit (Day 336) becomes a
⭐     ***global*** limit. ⭐ Your audit log records one address
⭐     forever. ⭐ Your geo logic sees one country.

⭐⭐ THE FIX HAS TWO HALVES AND PEOPLE DO ONE:
⭐   ① ⭐ Nginx sets `X-Forwarded-For` and `X-Forwarded-Proto`.
⭐   ② ⭐⭐ THE APP MUST BE TOLD TO ***TRUST*** THEM.
⭐      ⭐ `uvicorn --proxy-headers --forwarded-allow-ips=…`,
⭐      ⭐ or `ProxyHeadersMiddleware`, ⭐ or Django's
⭐        `SECURE_PROXY_SSL_HEADER` + `USE_X_FORWARDED_HOST`.
⭐   ⇒ ⭐⭐ WITHOUT ②, THE HEADERS ARE PRESENT AND IGNORED, AND
⭐     EVERYTHING LOOKS CORRECT UNTIL YOU CHECK.

⭐⭐ AND THE SECURITY HALF, WHICH IS THE PART THAT MATTERS:
⭐   ⭐ ⭐⭐ `X-Forwarded-For` IS CLIENT-SUPPLIED. ⭐ A client can
⭐     send `X-Forwarded-For: 1.2.3.4` and, if you trust it
⭐     blindly, ⭐⭐ THEY HAVE SPOOFED THEIR IP AND BYPASSED
⭐     EVERY PER-IP CONTROL YOU HAVE.
⭐   ⇒ ⭐ `$proxy_add_x_forwarded_for` ***appends*** the real
⭐     peer, ⭐⭐ SO THE ***LAST*** ENTRY IS TRUSTWORTHY AND THE
⭐     EARLIER ONES ARE NOT.
⭐   ⇒ ⭐⭐ SO: TRUST ONLY N ENTRIES FROM THE RIGHT, WHERE N IS
⭐     THE NUMBER OF PROXIES YOU CONTROL. ⭐ Set
⭐     `forwarded-allow-ips` to your proxy's address — ⭐⭐ NEVER
⭐     `*` IN PRODUCTION, WHICH IS THE DEFAULT PEOPLE COPY FROM
⭐     TUTORIALS.
⭐   ⇒ ⭐ And note `Forwarded:` (RFC 7239) is the standardised
⭐     version, ⭐ still less widely used.

⭐⭐ AND THE RELATED ONE: ⭐⭐ NGINX PASSES `Host` FROM THE
⭐   CLIENT. ⭐ If your app builds absolute URLs from `Host` and
⭐   does not validate it, ⭐⭐ AN ATTACKER CONTROLS THE LINK IN
⭐   YOUR PASSWORD-RESET EMAIL. ⭐ Validate `ALLOWED_HOSTS`
⭐   (Django does this by default; FastAPI needs
⭐   `TrustedHostMiddleware`).
```

# Part 5 — ⭐ What to push out of Python entirely

```
⭐⭐ EVERY REQUEST NGINX HANDLES IS A REQUEST YOUR GIL NEVER
⭐   SEES. ⭐ Five things belong here:

⭐⭐ ① ***STATIC FILES.*** ⭐ Nginx serves them with `sendfile`,
⭐      ⭐⭐ ZERO-COPY, AT ORDERS OF MAGNITUDE MORE THROUGHPUT
⭐      THAN WHITENOISE OR A PYTHON HANDLER. ⭐ (Whitenoise is
⭐      excellent when you have no proxy — ⭐ when you do, this
⭐      is better.)
⭐⭐ ② ***COMPRESSION.*** ⭐ `gzip on` with `gzip_types` for
⭐      JSON — ⭐⭐ AND `gzip_min_length 1000`, BECAUSE
⭐      COMPRESSING A 200-BYTE RESPONSE COSTS MORE THAN IT
⭐      SAVES.
⭐      ⇒ ⭐⭐ AND THE SECURITY NOTE: COMPRESSING A RESPONSE THAT
⭐        MIXES A SECRET WITH ATTACKER-CONTROLLED INPUT IS THE
⭐        BREACH/CRIME CLASS OF ATTACK. ⭐ Rare for APIs, worth
⭐        knowing.
⭐⭐ ③ ***RATE LIMITING AT THE EDGE.*** ⭐ `limit_req_zone` costs
⭐      almost nothing and ⭐⭐ REJECTS ABUSE BEFORE IT OCCUPIES A
⭐      PYTHON WORKER. ⭐ It complements, not replaces,
⭐      application-level limits (Day 347): ⭐ Nginx does per-IP
⭐      volumetrics, ⭐ the app does per-tenant and per-cost.
⭐⭐ ④ ***REQUEST SIZE AND HEADER LIMITS.***
⭐⭐ ⑤ ***CONNECTION LIMITS*** — `limit_conn` per IP, ⭐ which
⭐      is the other half of the slow-client defence.

⭐⭐ AND ONE THING THAT SHOULD ***NOT*** MOVE HERE:
⭐   ⭐ ⭐⭐ AUTHORISATION. ⭐ `auth_request` exists and is
⭐     tempting; ⭐⭐ ONLY THE SERVICE KNOWS WHETHER THIS USER
⭐     OWNS THIS ROW (Day 341). ⭐ Authentication at the edge is
⭐     fine; authorisation is not.
```

# Part 6 — ⭐⭐ Operating it: reloads, buffers and the errors you will see

```
⭐⭐ `nginx -s reload` IS GRACEFUL: ⭐ it starts new workers,
⭐   ⭐⭐ AND OLD WORKERS FINISH THEIR IN-FLIGHT REQUESTS BEFORE
⭐   EXITING. ⭐ Config changes and certificate rotation cost
⭐   zero downtime.
⭐   ⇒ ⭐⭐ ALWAYS `nginx -t` FIRST. ⭐ A bad config on reload is
⭐     refused (good); a bad config on ***start*** is an outage.

⭐⭐ THE FOUR ERRORS YOU WILL ACTUALLY SEE, AND WHAT EACH MEANS:
⭐   ⭐ ⭐⭐ ***502 BAD GATEWAY*** — nginx could not connect, or
⭐     the upstream died mid-response. ⭐ In a deploy, this is
⭐     almost always ⭐⭐ THE MISSING SLEEP BEFORE DRAINING
⭐     (Day 324): nginx still has the old pod in rotation.
⭐   ⭐ ⭐⭐ ***504 GATEWAY TIMEOUT*** — the upstream did not
⭐     answer within `proxy_read_timeout`. ⭐ Your app is slow,
⭐     ⭐⭐ AND IT IS ***STILL WORKING*** ON A REQUEST NOBODY
⭐     WILL RECEIVE (Day 336's deadline argument).
⭐   ⭐ ***413*** — body exceeded `client_max_body_size`.
⭐     ⭐⭐ AND IT IS OFTEN THE ***PROXY'S*** LIMIT, NOT YOURS,
⭐     WHICH IS WHY "MY 20 MB UPLOAD FAILS AND THE APP LOGS
⭐     NOTHING" IS SO CONFUSING.
⭐   ⭐ ***499*** — ⭐⭐ NGINX-SPECIFIC: THE CLIENT CLOSED THE
⭐     CONNECTION BEFORE A RESPONSE. ⭐ A rising 499 rate means
⭐     users are giving up, ⭐⭐ WHICH IS A LATENCY SIGNAL THAT
⭐     NEVER APPEARS IN YOUR APPLICATION'S ERROR RATE.

⭐⭐ AND TWO WARNINGS IN THE ERROR LOG THAT ARE REAL:
⭐   ⭐ `a client request body is buffered to a temporary file`
⭐     ⇒ ⭐ raise `client_body_buffer_size`, or accept the disk
⭐     I/O.
⭐   ⭐ `upstream sent too big header` ⇒ ⭐⭐ RAISE
⭐     `proxy_buffer_size`. ⭐ This is what a very large `Set-
⭐     Cookie` or a long JWT in a header produces, and it looks
⭐     like a random 502.
```

# Part 7 — ⭐ Nginx vs the alternatives

```
⭐⭐ ⭐ ***CADDY*** — automatic Let's Encrypt certificates, ⭐ far
⭐   simpler config, ⭐ sane defaults. ⭐⭐ FOR A SMALL SERVICE
⭐   THIS IS OFTEN THE BETTER ENGINEERING CHOICE, AND SAYING SO
⭐   IS NOT A WEAKNESS.
⭐⭐ ⭐ ***TRAEFIK*** — service discovery from Docker/Kubernetes
⭐   labels, ⭐ so routes appear as containers start. ⭐ Excellent
⭐   in Compose; ⭐ more moving parts.
⭐⭐ ⭐ ***ENVOY*** — the most capable, ⭐ the basis of most
⭐   meshes (Day 341), ⭐⭐ AND CONFIGURED BY A CONTROL PLANE
⭐   RATHER THAN BY HAND.
⭐⭐ ⭐ ***A CLOUD LOAD BALANCER*** — ALB/NLB does TLS, health
⭐   checks and routing. ⭐⭐ AND THEN YOU MAY NEED NO PROXY AT
⭐   ALL — ⭐ though an ALB does ***not*** buffer request bodies
⭐   the way Nginx does, ⭐⭐ SO WITH SYNC WORKERS YOU STILL WANT
⭐   ONE.
⭐⭐ ⭐ ***NOTHING*** — ⭐ uvicorn directly is fine for an
⭐   internal service behind an authenticated gateway with async
⭐   workers, ⭐⭐ AND SAYING "I WOULDN'T ADD ONE HERE" WITH THAT
⭐   REASONING IS A BETTER ANSWER THAN ADDING IT REFLEXIVELY.

⭐⭐ ⇒ THE JUDGEMENT SENTENCE: ***THE QUESTION IS NOT "WHICH
⭐   PROXY" BUT "WHAT MUST HAPPEN BEFORE A REQUEST REACHES
⭐   PYTHON" — TLS, BUFFERING, LIMITS, STATIC FILES — AND THEN
⭐   PICKING WHATEVER DOES THOSE WITH THE LEAST OPERATIONAL
⭐   SURFACE.***
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Exposing sync gunicorn directly to the internet | Four slow clients take the service down at 2% CPU |
| ⭐⭐ Buffering without `client_body_timeout` | Buffering helps; only the timeout stops ten thousand held connections |
| ⭐⭐ `keepalive` without `proxy_http_version 1.1` and `Connection ""` | Upstream keepalive silently doesn't happen; a handshake per request |
| ⭐⭐ `proxy_buffering` on for SSE | Events arrive in a clump minutes later, and the app looks broken |
| ⭐ Missing `Upgrade`/`Connection` for WebSockets | The handshake fails with a confusing 400 |
| ⭐⭐ Setting `X-Forwarded-*` but not trusting it in the app | The headers are present and ignored; everything looks fine until you check |
| ⭐⭐ `forwarded-allow-ips=*` | Any client can spoof their IP and bypass every per-IP control |
| ⭐ No `X-Forwarded-Proto` | The app builds `http://` redirects and refuses to set `Secure` cookies |
| ⭐ Trusting `Host` without an allow-list | An attacker controls the link in your password-reset email |
| ⭐⭐ Authorisation via `auth_request` | Only the service knows whether this user owns this row |
| ⭐ `gzip` on everything | Compressing a 200-byte response costs more than it saves |
| ⭐ HSTS with preload on day one | Effectively irreversible for that domain |
| ⭐ Reloading without `nginx -t` | A bad config on start is an outage |
| ⭐⭐ Ignoring 499s | Users are giving up, and it never appears in your app's error rate |

## Interview questions

**1. "Why is Nginx in front of your Python app?"**
> ⭐⭐ Not for speed — **to decouple client speed from worker occupancy.** ⭐ A sync gunicorn worker
> serves one connection at a time, so a client sending a megabyte at five kilobytes a second occupies
> it for two hundred seconds; **four such clients take the service down at 2% CPU**, and nothing on the
> dashboard looks wrong. ⭐ Nginx buffers the complete request and hands it over in microseconds, so
> occupancy tracks work done rather than client bandwidth.

**2. "Do you still need it with async workers?"**
> ⭐ Less urgently, and yes. ⭐⭐ **With sync workers it's a correctness requirement; with async workers
> it's an efficiency and security layer.** ⭐ Slow clients still consume file descriptors and buffers;
> TLS and HTTP/2 are CPU work you don't want on a GIL-bound process; and static files, compression,
> rate limiting and size limits are work that should never reach Python at all. ⭐ Behind a cloud load
> balancer that terminates TLS, those last three are still enough to justify it.

**3. "What breaks if you forget forwarded headers?"**
> ⭐ Three things, and the fix has two halves people usually half-do. ⭐ Per-IP rate limits become global
> because every request appears to come from the proxy; audit logs record one address; and without
> `X-Forwarded-Proto` the app thinks everything is HTTP, ⭐⭐ **so it builds `http://` redirects and
> refuses to set `Secure` cookies, silently downgrading session security.** ⭐⭐ And the security half:
> **`X-Forwarded-For` is client-supplied**, so trusting it blindly lets anyone spoof their IP — trust
> only the entries added by proxies you control, and never `forwarded-allow-ips=*`.

**4. "You're getting 502s during deploys."**
> ⭐⭐ Almost always the missing drain window: **the pod stopped accepting before the proxy stopped
> sending**, so requests arrive at a socket that's gone. ⭐ The fix is Day 324's sequence — fail
> readiness, sleep about five seconds so the balancer notices, *then* stop accepting. ⭐ Second
> candidate is an upstream header too large for `proxy_buffer_size`, which a long JWT or a big
> `Set-Cookie` produces and which presents as a random 502.

**5. "What would you push out of Python?"**
> ⭐ Static files with `sendfile`, which is zero-copy and orders of magnitude faster than a Python
> handler; compression above a minimum length; per-IP rate limiting and connection limits; and body
> size limits, ⭐⭐ **so a two-gigabyte upload is rejected at the edge rather than buffered through to
> your app.** ⭐ What I would *not* move is authorisation — `auth_request` is tempting, but only the
> service knows whether this user owns this row.

**6. "Nginx, Caddy, Traefik or nothing?"**
> ⭐⭐ The question isn't which proxy, it's **what must happen before a request reaches Python** — TLS,
> buffering, limits, static files — then pick whatever does those with the least operational surface.
> ⭐ Caddy for a small service, because automatic certificates and sane defaults are genuinely better
> engineering. ⭐ Traefik in Compose for label-based discovery. ⭐ And **nothing** is a real answer for an
> internal async service behind an authenticated gateway — ⭐⭐ though I'd note an ALB doesn't buffer
> request bodies the way Nginx does, so with sync workers you still want one.

## 🎙️ Articulation drill

**Two minutes.** Lead with the real reason, because most people give the wrong one: **Nginx isn't there
for speed, it's there to decouple client speed from worker occupancy.** Do the arithmetic out loud —
**a sync worker serves one connection at a time, so a client sending a megabyte at five kilobytes a
second holds it for two hundred seconds, and four of those take the service down at two percent CPU.**
Nginx buffers the complete request and hands it over in microseconds. Then be precise about async,
because that's the pushback: **with sync workers it's a correctness requirement; with async workers it's
an efficiency and security layer** — file descriptors, TLS off the GIL, and static files, compression
and limits that should never reach Python. Name the directive that actually does the work: **buffering
helps, but `client_body_timeout` is what stops an attacker holding ten thousand connections open.**
Then the trap that silently costs you security: **setting `X-Forwarded-*` isn't enough — the app has to
be told to trust them, and trusting them from anyone means any client can spoof their IP and bypass
every per-IP control**, so trust only the entries your own proxies added. Close on the operational
detail worth having: **a rising 499 rate means users are giving up, and it never shows up in your
application's error rate** — and on the judgement, which is that the question isn't which proxy but
what must happen before a request reaches Python.
