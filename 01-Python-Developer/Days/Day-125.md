# Day 125

**L-125** · **API versioning and evolution** — ⭐⭐ what actually counts as a breaking change

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: versioning is what you do when you have failed to evolve compatibly, so
> the useful skill is not choosing between URL and header versioning — it is knowing precisely which
> changes are safe, because most changes people version for did not need a version at all.**
>
> ⭐ Once someone else's code depends on your API, **you have lost the ability to change it freely**.
> Today is how to keep changing it anyway.

---

# Part 1 — ⭐⭐ Which changes break

```
⭐⭐ SAFE — ADDITIVE. A CORRECT CLIENT IGNORES WHAT IT DOES NOT KNOW:
⭐   ✔ adding a new endpoint
⭐   ✔ ⭐ adding an OPTIONAL request field (with a sensible default)
⭐   ✔ ⭐⭐ adding a field to a RESPONSE
⭐   ✔ adding a new value to an enum ⭐ …see the caveat below
⭐   ✔ adding a new error code ⭐ …ditto
⭐   ✔ relaxing a validation rule ⇒ ⭐ things that failed now succeed
⭐
⭐ ⚠️⚠️ BREAKING — SOMETHING THAT WORKED STOPS WORKING:
⭐   ✘ ⭐⭐ REMOVING OR RENAMING A FIELD ⇒ the single most common break
⭐   ✘ ⭐⭐ CHANGING A TYPE — `"42"` to `42`, or an id from int to uuid
⭐   ✘ ⭐ making an optional field required
⭐   ✘ ⭐ tightening validation ⇒ requests that worked now 422
⭐   ✘ ⭐⭐ CHANGING THE MEANING of a field while keeping its name and type —
⭐        `amount` in pounds becoming `amount` in pence. ⭐⭐ THE WORST ONE:
⭐        nothing fails, everything is silently wrong by a factor of 100.
⭐   ✘ ⭐ changing a status code, changing default sort order, changing an error
⭐        code
⭐   ✘ ⭐⭐ CHANGING A DEFAULT VALUE ⇒ a client that omitted the field gets
⭐        different behaviour without changing a line
```

```
⭐⭐ THE ENUM CAVEAT, AND IT DECIDES WHETHER "ADDITIVE" IS TRUE: ADDING AN ENUM
⭐   VALUE IS SAFE ONLY IF CLIENTS TOLERATE UNKNOWN VALUES.
⭐   ⇒ ⭐ a client with an exhaustive match — or a Pydantic model with a strict
⭐        `Literal` — ⭐⭐ CRASHES ON A VALUE THAT DID NOT EXIST WHEN IT WAS
⭐        WRITTEN. And a strongly-typed generated client is the most likely to.
⭐   ⇒ ⭐⭐ SO YOU MUST STATE THE RULE IN YOUR DOCUMENTATION: "clients MUST
⭐        tolerate unknown enum values and unknown fields." ⭐ Say it and adding
⭐        a value is minor; leave it unsaid and it is breaking, and you find out
⭐        from a customer.
⭐   ⇒ ⭐ this is Day 058's "closed in code, open in the database", now at the
⭐        API boundary — ⭐⭐ and it is why Day 119's `extra="forbid"` is a
⭐        versioning decision rather than purely a security one.
```

⭐⭐ **Renaming a field is the change people most often think is cosmetic.** ⭐ `user_name` →
`username` breaks every client, and the fix is not to version — **it is to add the new name, populate
both, deprecate the old, and remove it a year later** (Part 3).

# Part 2 — ⭐ Where the version goes

| ⭐ Scheme | ⭐ Example | |
|---|---|---|
| ⭐⭐ **URL path** | `/v1/orders` | ⭐⭐ obvious, cacheable, greppable, testable in a browser · ⚠️ ⭐ not "RESTful" (the resource did not change) |
| Custom header | `X-API-Version: 2` | ⭐ clean URLs · ⚠️ ⭐⭐ invisible in logs, hard to route, easy to forget |
| ⭐ Accept header | `Accept: application/vnd.acme.v2+json` | ⭐ theoretically correct · ⚠️ ⭐⭐ nobody enjoys it, and it breaks browser testing |
| Query parameter | `?version=2` | ⭐ easy · ⚠️ pollutes the cache key, easy to omit |
| ⭐ **Date-based** | `X-API-Version: 2026-08-18` | ⭐⭐ Stripe's model — see below |

```
⭐⭐ THE RECOMMENDATION, AND THE REASONING RATHER THAN THE FASHION:
⭐   USE THE URL PATH (`/v1/`) FOR MOST APIs.
⭐   ⇒ ⭐ it is visible in every log line, every trace, every bug report and
⭐        every `curl` someone pastes into a ticket. ⭐⭐ That operational
⭐        visibility beats theoretical purity, and versioning is an operational
⭐        problem.
⭐   ⇒ ⭐ your reverse proxy can route `/v1` and `/v2` to different deployments,
⭐        which is genuinely useful during a migration.
⭐   ⇒ ⚠️ ⭐ the purist objection — that `/v1/orders` and `/v2/orders` are the
⭐        same resource so the URL should not change — is correct and does not
⭐        matter.
⭐
⭐ ⭐⭐ AND VERSION AT THE COARSEST USEFUL LEVEL. `/v1` for the whole API, not
⭐   per endpoint: ⭐ per-endpoint versions produce a matrix nobody can reason
⭐   about, and a client that must remember `/v3/orders` with `/v1/users`.
```

```
⭐⭐ STRIPE'S DATE-BASED MODEL, BECAUSE IT IS THE MOST SOPHISTICATED ONE IN
⭐   COMMON USE:
⭐   · every account is PINNED to the API date it first integrated on
⭐   · new clients get the latest; existing ones keep their behaviour forever
⭐   · ⭐⭐ INTERNALLY, THE SERVER RUNS ONE CURRENT VERSION AND APPLIES A CHAIN OF
⭐        REQUEST/RESPONSE TRANSFORMERS to translate older versions into it
⭐   ⇒ ⭐⭐ THE KEY INSIGHT: there is ONE codebase and N SMALL TRANSFORMERS —
⭐        not N copies of the application. ⭐ Each transformer is a few lines
⭐        ("in versions before 2024-03-01, rename `amount_total` to `total`") and
⭐        is testable in isolation.
⭐   ⇒ ⚠️ ⭐ the cost is real and grows: every transformer is maintained forever,
⭐        and the chain must be applied in order. ⭐⭐ Worth it at Stripe's scale;
⭐        overkill for an internal API with three consumers.
```

# Part 3 — ⭐⭐ Evolve instead of versioning

```
⭐⭐ EXPAND / MIGRATE / CONTRACT — THE SAME PATTERN AS A DATABASE MIGRATION
⭐   (Day 021), APPLIED TO AN API. IT HANDLES ALMOST EVERY CHANGE WITHOUT A NEW
⭐   VERSION:
⭐
⭐   1. ⭐⭐ EXPAND  — add the new field ALONGSIDE the old. Populate BOTH.
⭐        ⇒ ⭐ nothing breaks; old and new clients both work.
⭐   2. ⭐⭐ MIGRATE — announce the deprecation, give a date, and MEASURE who is
⭐        still using the old field. ⭐ Contact them directly if you can.
⭐   3. ⭐ CONTRACT — remove the old field once usage is zero.
⭐
⭐ ⇒ ⭐⭐ STEP 2 IS THE ONE PEOPLE SKIP, AND IT IS THE ONLY ONE THAT MAKES STEP 3
⭐     SAFE. ⭐⭐ YOU CANNOT REMOVE WHAT YOU CANNOT MEASURE — so INSTRUMENT FIELD
⭐     USAGE: log which response fields each client actually reads (hard), or at
⭐     minimum which clients still SEND the old request field, and which API
⭐     version each key is on.
⭐ ⇒ ⭐ a rename becomes: add `username`, populate both, deprecate `user_name`,
⭐     remove it in a year. ⭐⭐ No version bump, no parallel codebase.
```

```http
Deprecation: Sat, 01 Nov 2026 00:00:00 GMT       ⭐ RFC 9745 — this endpoint is deprecated
Sunset: Sun, 01 Feb 2027 00:00:00 GMT            ⭐⭐ RFC 8594 — and it will STOP WORKING then
Link: <https://docs.acme.com/migrate-v2>; rel="deprecation"
Warning: 299 - "The `user_name` field is deprecated; use `username`."
```

```
⭐⭐ MACHINE-READABLE DEPRECATION IS WORTH MORE THAN A BLOG POST, BECAUSE IT
⭐   REACHES THE ONE PLACE THE DEVELOPER IS ACTUALLY LOOKING — their own logs.
⭐   ⇒ ⭐ a blog post reaches whoever reads your blog. ⭐⭐ A `Sunset` header
⭐        reaches every integration that logs response headers, and a client
⭐        library can surface it as a warning automatically.
⭐   ⇒ ⭐⭐ AND SET A REAL DATE. "Deprecated" with no sunset date is ignored
⭐        forever — ⭐ people migrate against deadlines, not against advice.
```

# Part 4 — ⭐ Running two versions

```
⭐⭐ THREE WAYS, AND THE THIRD IS ALMOST ALWAYS RIGHT:
⭐  1. ⚠️ ⭐⭐ TWO DEPLOYMENTS from two branches ⇒ ⭐ simple for a month, then
⭐       every bug fix and security patch must be applied twice, and they drift.
⭐       ⭐⭐ THE DRIFT IS THE KILLER: v1 quietly stops receiving fixes and
⭐       becomes the vulnerable one.
⭐  2. ⭐ TWO ROUTERS, ONE CODEBASE ⇒ `/v1` and `/v2` handlers over shared
⭐       services. ⭐⭐ Fine when the difference is only the wire format.
⭐  3. ⭐⭐ ONE CODEBASE + TRANSFORMERS (Stripe's model) ⇒ the current version is
⭐       the only implementation, and older versions are translations.
⭐       ⭐ Most maintainable; the transformers are pure functions and trivially
⭐       testable (Day 089).
⭐
⭐ ⇒ ⭐⭐ WHATEVER YOU CHOOSE: **THE DOMAIN LAYER MUST NOT KNOW ABOUT VERSIONS**
⭐     (Day 090). Versioning is a boundary concern — schemas and transformers at
⭐     the edge, one set of business rules underneath. ⭐ A version check inside
⭐     a service function is the beginning of two products.
```

```
⭐⭐ AND THE POLICY THAT MAKES ANY OF IT SUSTAINABLE — DECIDE IT BEFORE YOU
⭐   SHIP v2, NOT AFTER:
⭐   □ ⭐⭐ HOW MANY VERSIONS DO YOU SUPPORT AT ONCE? ⭐ Two. ⭐⭐ "Latest and
⭐       previous" is the only policy that stays bounded; anything else grows.
⭐   □ ⭐ FOR HOW LONG after a new version ships? 6-12 months, stated up front.
⭐   □ ⭐ WHO IS ON WHAT? ⭐⭐ You must be able to answer this per client. Track
⭐       the version per API key on every request.
⭐   □ ⭐ WHAT IS THE DEFAULT for a request with no version? ⭐⭐ THE OLDEST
⭐       SUPPORTED ONE, never "latest" — ⭐ defaulting to latest means your next
⭐       release silently breaks every unversioned client.
```

# Part 5 — ⭐ Contract testing

```python
# ⭐⭐ A GOLDEN-RESPONSE TEST — the cheapest protection against accidental breaks:
def test_v1_order_response_shape(client, snapshot):
    r = client.request("GET", "/v1/orders/1")
    assert json.loads(r.body) == snapshot          # ⭐ a committed fixture file
```

```
⭐⭐ WHY THIS IS WORTH MORE THAN A CONVENTION: ⭐ a snapshot test FAILS THE
⭐   MOMENT anyone adds, renames or retypes a field. ⭐⭐ The developer then has
⭐   to look at the diff and decide "is this additive or breaking?" — ⭐ which is
⭐   exactly the decision that otherwise gets made by accident at 6 p.m.
⭐   ⇒ ⭐ update the snapshot deliberately, in the same PR, so the diff is
⭐        REVIEWABLE (Day 100B). ⭐⭐ The reviewer sees the API change as a change
⭐        rather than as a side effect of a refactor.
⭐   ⇒ ⚠️ ⭐ snapshot tests rot if updated reflexively. ⭐⭐ The rule: a snapshot
⭐        change must be mentioned in the PR description.
```

```
⭐ THREE MORE CONTRACT MECHANISMS, IN ORDER OF EFFORT:
⭐   · ⭐ VALIDATE RESPONSES AGAINST YOUR OWN OPENAPI SPEC in tests (Day 126)
⭐        ⇒ the spec cannot drift from reality
⭐   · ⭐⭐ CONSUMER-DRIVEN CONTRACTS (Pact): each consumer publishes what it
⭐        actually uses, and your CI fails if you break any of them ⇒ ⭐⭐ this
⭐        is the only mechanism that tells you a change is safe BECAUSE NOBODY
⭐        USES THAT FIELD, rather than by guesswork
⭐   · ⭐ DIFF THE SPEC in CI (`oasdiff`) and fail on a breaking change
⭐   ⇒ ⭐⭐ AND NOTE THE SHAPE: this is Day 095's contract test again — one
⭐        assertion that two independently-changing things still agree.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Versioning for an additive change | ⭐⭐ Adding a response field is safe. Most versions were unnecessary. |
| ⭐⭐ **Renaming a field "cosmetically"** | ⭐⭐ It breaks every client. Add, populate both, deprecate, remove. |
| Changing a field's meaning | ⭐⭐ The worst break — nothing fails and everything is silently wrong. |
| ⭐ Changing a default value | ⭐ Clients that omitted the field get new behaviour with no change. |
| ⭐ Assuming enum additions are safe | ⭐⭐ Only if you documented that clients must tolerate unknown values. |
| Per-endpoint versions | ⭐ A matrix nobody can reason about. |
| ⭐ Defaulting an unversioned request to "latest" | ⭐⭐ Your next release silently breaks them. Default to oldest supported. |
| ⭐⭐ **Two branches for two versions** | ⭐⭐ They drift, and v1 stops getting security fixes. |
| Version checks in the domain layer | ⭐ Versioning is a boundary concern. |
| ⭐ Deprecating with no sunset date | ⭐⭐ People migrate against deadlines, not advice. |
| Removing a field without measuring usage | ⭐⭐ You cannot remove what you cannot measure. |
| ⭐ No contract test | ⭐ A breaking change ships as a side effect of a refactor. |
| Updating snapshots reflexively | ⭐ Require it to be mentioned in the PR description. |

## Interview questions

**Q: How do you version an API?**
> The more useful question is what actually breaks, because most changes people version for didn't
> need it. Adding an endpoint, an optional request field or a response field is safe — a correct
> client ignores what it doesn't know. Removing or renaming a field, changing a type, tightening
> validation, or changing a default all break. And the worst is changing a field's *meaning* while
> keeping its name and type — `amount` in pounds becoming pence — because nothing fails and everything
> is silently wrong by a factor of a hundred. When I do need a version I'd put it in the URL path,
> because it's visible in every log, trace, bug report and pasted `curl`, and versioning is an
> operational problem.

**Q: How do you rename a field without breaking anyone?**
> Expand, migrate, contract — the same pattern as a database migration. Add the new name alongside the
> old and populate both, so nothing breaks. Announce the deprecation with a real sunset date and
> measure who's still using the old one. Then remove it once usage is zero. The step people skip is
> the measuring, and it's the only one that makes removal safe — you can't remove what you can't
> measure. Done that way, a rename needs no version bump at all.

**Q: Is adding a value to an enum a breaking change?**
> It depends entirely on whether you told clients to tolerate unknown values. A client with an
> exhaustive match — or a generated client with a strict literal type — crashes on a value that didn't
> exist when it was written, and strongly-typed generated clients are the most likely to. So the rule
> has to be in the documentation: clients must tolerate unknown enum values and unknown fields. Say it
> and the addition is minor; leave it unsaid and it's breaking, and you find out from a customer.

**Q: How do you run two versions without maintaining two codebases?**
> Transformers. One current implementation, with request and response transformers translating older
> versions into it — which is Stripe's model. Each transformer is a few lines, "before this date,
> rename this field", and they're pure functions so they're trivially testable. The alternative,
> two branches, is simple for about a month and then every bug fix has to be applied twice and they
> drift — and the drift is the real danger, because the old version quietly stops receiving security
> fixes. Whatever the mechanism, the domain layer must not know about versions; it's a boundary
> concern, and a version check inside a service function is the beginning of two products.

**Q: How do you stop a breaking change shipping by accident?**
> A golden-response snapshot test, which fails the moment anyone adds, renames or retypes a field. The
> value isn't the assertion, it's that the developer then has to look at the diff and consciously
> decide whether it's additive or breaking — the decision that otherwise gets made by accident during
> a refactor. Updating the snapshot happens in the same PR so a reviewer sees the API change as a
> change. Beyond that, validating responses against your own OpenAPI spec so it can't drift, diffing
> the spec in CI, and for a real consumer base, consumer-driven contracts — which are the only
> mechanism that tells you a change is safe *because nobody uses that field* rather than by guesswork.

## Mini task

1. ⭐⭐ Classify ten recent changes to any API you have as additive or breaking. **Check whether any
   shipped as breaking without a version.**
2. ⭐⭐ Change a field's units without renaming it and **write down what a client would experience.**
3. ⭐ Add an enum value, then consume it with a strict Pydantic `Literal` client. **Watch it crash.**
4. ⭐⭐ Do a full expand/migrate/contract rename: add the new field, populate both, add `Deprecation`
   and `Sunset` headers, then remove it.
5. ⭐⭐ **Instrument usage**: log which clients still send the deprecated field, and build the query
   that tells you when it is safe to remove.
6. ⭐ Add `/v1` to your URLs and route `/v1` and `/v2` at nginx to two deployments.
7. ⭐⭐ Implement one request transformer and one response transformer for an older version. **Test
   them as pure functions with no HTTP.**
8. ⭐ Default an unversioned request to "latest", then ship a breaking change and **observe what you
   just did.** Change the default to oldest supported.
9. ⭐⭐ Add a golden-response snapshot test. **Rename a field and watch it fail.**
10. ⭐ Update the snapshot and confirm the diff is readable in a PR.
11. ⭐⭐ Write your versioning policy in four lines: how many versions, for how long, who is on what,
    what the default is. **Put it in an ADR** (Day 101).

## 🎙️ Articulation drill

Record two minutes: **"You need to rename a field in a public API. What do you do?"**

⭐ **Refuse the framing first, because the question contains the mistake:** **"I wouldn't rename it —
not as a single act. A rename removes a field, and that breaks every client that reads it. It's the
change people most often think is cosmetic, and it's the most common way an API breaks."**

⭐⭐ **Then the pattern, with the step that matters:** *"instead, expand, migrate, contract — the same
shape as a database migration. Add the new name alongside the old and populate both, so nothing breaks.
Announce the deprecation with `Deprecation` and `Sunset` headers and a real date, because people
migrate against deadlines, not against advice — and headers reach the one place a developer is
actually looking, which is their own logs. Then measure who's still using the old field and remove it
when usage is zero. That measuring step is the one people skip, and it's the only thing that makes
removal safe: you can't remove what you can't measure."*

⭐⭐ **Then broaden it, because the interesting claim is about versioning generally:** *"and I'd point
out that this needs no version bump at all. Most of the versions I've seen shipped were for changes
that were additive or could have been evolved this way. Versioning is what you do when you've failed to
evolve compatibly, so the useful skill is knowing precisely which changes break — and the one that
worries me most isn't removal, it's changing a field's *meaning* while keeping its name and type.
`amount` going from pounds to pence fails nothing and is silently wrong by a factor of a hundred."*

⭐ **Close on prevention:** *"to stop this happening by accident I'd have a golden-response snapshot
test. It fails the moment a field is added, renamed or retyped, which forces someone to consciously
decide whether the change is additive or breaking — instead of that decision being made accidentally
during a refactor at six o'clock."*
