# Day 440 🩹

**P-440** · 🩹 **When the agent is wrong** — ⭐⭐ score the trajectory, gate the action

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an agent that has failed is exactly as fluent as one that has succeeded, so
> you never learn the outcome from the agent — you learn it from an independent check, and everything
> irreversible waits behind a gate that the model is not permitted to open.**

# Part 1 — ⭐⭐ The doom loop, and why the model cannot see it

```
⭐ ***THE TRANSCRIPT:***
⭐   ⭐ step 3: `get_invoice(id="INV-2041")` → `not found`
⭐   ⭐ step 4: `get_invoice(id="INV-2041")` → `not found`
⭐   ⭐ step 5: `get_invoice(id="INV-2041")` → `not found`
⭐   ⭐ … until your step budget saves you.

⭐ ***WHY IT HAPPENS — AND IT IS NOT STUPIDITY:***
⭐   ⭐ each step is a fresh forward pass conditioned on a
⭐     transcript in which ⭐⭐ CALLING THAT TOOL WITH THOSE
⭐     ARGUMENTS IS THE MOST PLAUSIBLE NEXT ACTION;
⭐   ⭐ the failures ***are*** in the context, but they read as
⭐     ⭐⭐ EVIDENCE THAT THE ACTION IS WHAT ONE DOES HERE, ⭐ not
⭐     as evidence to stop;
⭐   ⭐ ⭐⭐ THE MODEL HAS NO MECHANISM FOR "I HAVE ALREADY TRIED
⭐     THIS" BEYOND WHAT THE TEXT SAYS — ⭐ there is no loop
⭐     counter, no memory, no frustration (Day 414).

⭐ ***THE FIX IS IN YOUR LOOP, NOT YOUR PROMPT.***
⭐   ⭐ ① hash `(tool_name, canonical_args)` per step;
⭐   ⭐ ② on the ***second*** identical call, ⭐ do not execute —
⭐     return an escalating message instead:
⭐     ⭐⭐ "YOU HAVE ALREADY CALLED get_invoice WITH THIS EXACT
⭐       ID AND IT RETURNED NOT-FOUND. DO NOT CALL IT AGAIN.
⭐       EITHER TRY `search_invoices` OR TELL THE USER THE
⭐       INVOICE DOES NOT EXIST."
⭐     ⭐ ⭐⭐ NOTE IT NAMES AN ALTERNATIVE ***AND*** AN EXIT.
⭐       ⭐ "Do not repeat" alone produces a paraphrased repeat.
⭐   ⭐ ③ on the third, ⭐⭐ ABORT THE RUN. ⭐ Do not negotiate.
⭐   ⭐ ④ log it as a metric — ⭐⭐ `repeat_call_rate` IS ONE OF
⭐     THE BEST HEALTH SIGNALS AN AGENT HAS, ⭐ and it moves the
⭐     moment a prompt or model changes.

⭐⭐ THE NEAR-MISS VARIANT, WHICH IS WORSE: ⭐ the arguments
⭐   change trivially each time — `"INV-2041"`, `"INV2041"`,
⭐   `"inv-2041"`. ⭐⭐ HASH ***CANONICALISED*** ARGS (lowercase,
⭐   strip, sort keys) OR YOU WILL NOT CATCH IT.
```

# Part 2 — ⭐⭐ The reversibility ladder

```
⭐ ***CLASSIFY EVERY TOOL. THE CLASS DECIDES THE CONTROL.***

⭐  ┌───┬───────────────────┬──────────────────────────────────┐
⭐  │ 0 │ ***READ***        │ ⭐ no gate. ⭐⭐ STILL SUBJECT TO   │
⭐  │   │ search, get       │ THE TENANT FILTER (D434) — READS  │
⭐  │   │                   │ ARE HOW DATA LEAVES.             │
⭐  ├───┼───────────────────┼──────────────────────────────────┤
⭐  │ 1 │ ***REVERSIBLE     │ ⭐ let it run. ⭐ Log for undo.    │
⭐  │   │ WRITE***          │ Draft, tag, internal note.       │
⭐  ├───┼───────────────────┼──────────────────────────────────┤
⭐  │ 2 │ ***COSTLY-TO-     │ ⭐ run, but ⭐⭐ RATE-LIMIT AND     │
⭐  │   │ REVERSE***        │ ALERT. ⭐ Status change, refund   │
⭐  │   │                   │ under £50, ticket reassignment.  │
⭐  ├───┼───────────────────┼──────────────────────────────────┤
⭐  │ 3 │ ***IRREVERSIBLE   │ ⭐⭐ HUMAN GATE. ALWAYS. ⭐ Email   │
⭐  │   │ / EXTERNALLY      │ sent, payment taken, record      │
⭐  │   │ VISIBLE***        │ deleted, message posted.         │
⭐  │   │                   │ ⭐⭐ "SORRY, IGNORE THAT EMAIL" IS │
⭐  │   │                   │ NOT AN UNDO — IT IS A SECOND     │
⭐  │   │                   │ EMAIL (D411).                    │
⭐  └───┴───────────────────┴──────────────────────────────────┘

⭐⭐ THE DESIGN RULE THAT MATTERS: ⭐ ***THE GATE IS ON THE
⭐   ACTION, NOT ON THE MODEL'S REQUEST TO ACT.***
⭐   ⭐ ❌ a system prompt saying "always ask before sending
⭐     email" — ⭐⭐ THAT IS A REQUEST TO A TEXT PREDICTOR AND IT
⭐     WILL BE HONOURED MOST OF THE TIME, WHICH IS THE WORST
⭐     POSSIBLE PROPERTY FOR A SECURITY CONTROL.
⭐   ⭐ ✅ `send_email.needs_approval = True`, enforced in the
⭐     loop, ⭐⭐ SO NO PROMPT — AND NO INJECTION (D446) — CAN
⭐     BYPASS IT.

⭐ ***AND MAKE THE APPROVAL MEANINGFUL:***
⭐   ⭐ show the ***rendered effect***, not the arguments: the
⭐     actual email body and recipient, not
⭐     `{"to":"…","tmpl":17}`;
⭐   ⭐ ⭐⭐ ONE GATE PER RUN, BATCHED — ⭐ five approvals in
⭐     ninety seconds trains the user to click yes, ⭐⭐ WHICH
⭐     CONVERTS YOUR CONTROL INTO A FORMALITY. ⭐ Approval
⭐     fatigue is a real failure mode of these systems.
```

# Part 3 — Partial completion, which is the hard case

```
⭐ THE AGENT DID 3 OF 5 STEPS AND FAILED. ⭐⭐ THE THREE ARE
⭐   DONE. THERE IS NO TRANSACTION AROUND AN AGENT RUN — ⭐ it
⭐   spans several systems, so ***you lost the I in ACID*** the
⭐   moment you added a second tool (Day 411).

⭐ ⇒ ***THIS IS A SAGA, AND YOU ALREADY KNOW THE SHAPE:***
⭐   ⭐ ① ***ORDER THE STEPS SO REVERSIBLE ONES COME FIRST*** and
⭐     the ***pivot*** — the first irreversible action — comes as
⭐     late as possible. ⭐⭐ EVERYTHING BEFORE THE PIVOT CAN BE
⭐     ABANDONED; NOTHING AFTER IT CAN.
⭐   ⭐ ② ***COMPENSATE, DO NOT UNDO.*** ⭐ A cancellation record,
⭐     a correction email, a reversal entry. ⭐⭐ IT IS A NEW
⭐     VISIBLE FACT AND THE USER MUST SEE IT.
⭐   ⭐ ③ ***REPORT WHAT HAPPENED, PRECISELY.*** ⭐ "I created the
⭐     ticket and notified the team; I could not update the
⭐     billing record, so ⭐⭐ THE TICKET EXISTS AND THE BILLING
⭐     IS UNCHANGED." ⭐ That sentence is the deliverable.

⭐⭐ AND THE ARCHITECTURAL DODGE THAT BEATS ALL OF IT: ⭐ where
⭐   you can, have the agent ***propose a plan*** and execute it
⭐   transactionally in your own code. ⭐⭐ THE MODEL DECIDES
⭐   ***WHAT***; A DETERMINISTIC EXECUTOR DECIDES ***HOW***, ⭐ and
⭐   the executor can validate the whole plan before performing
⭐   any of it. ⭐⭐ THIS IS THE SINGLE BIGGEST RELIABILITY WIN
⭐   AVAILABLE IN AGENT DESIGN AND IT IS UNDER-USED BECAUSE IT
⭐   LOOKS LESS LIKE AN AGENT.
```

# Part 4 — ⭐⭐ Never trust the agent's account of itself

```
⭐ ***THE FAILURE:*** ⭐ "I've updated the customer's address and
⭐   sent them a confirmation." ⭐⭐ NEITHER TOOL WAS EVER
⭐   CALLED. ⭐ The sentence is a plausible continuation of a
⭐   transcript in which those were the goals — ⭐⭐ THAT IS
⭐   ***EXACTLY*** WHAT NEXT-TOKEN PREDICTION PRODUCES (DAY 414),
⭐   and it is fluent, specific and completely false.

⭐ ⇒ ***THE COMPLETION SIGNAL MUST COME FROM YOUR CODE.***
⭐   ⭐ ① `success = "update_address" in executed_tools and
⭐     result.ok` — ⭐⭐ NOT FROM PARSING THE PROSE.
⭐   ⭐ ② the user-facing summary is ***rendered from the tool
⭐     log***, not from the model's final message. ⭐⭐ THE MODEL
⭐     WRITES THE EXPLANATION; ***YOUR CODE WRITES THE FACTS.***
⭐   ⭐ ③ for anything that matters, ***verify independently***:
⭐     re-read the record after writing it.

⭐⭐ THE SAME RULE, GENERALISED: ⭐ ***NEVER LET A
⭐   NON-DETERMINISTIC COMPONENT BE THE SOURCE OF TRUTH ABOUT
⭐   WHAT A DETERMINISTIC SYSTEM DID.*** ⭐ You have the tool log.
⭐   Use it.
```

# Part 5 — Trajectory evals: score the path

```
⭐ DAY 425 SCORED ***OUTPUTS***. ⭐⭐ AN AGENT'S OUTPUT CAN BE
⭐   RIGHT FOR TERRIBLE REASONS — ⭐ fourteen steps, six wrong
⭐   tools, £0.40 and a lucky recovery. ⭐⭐ IT WILL NOT RECOVER
⭐   NEXT TIME.

⭐ ***SCORE THE TRAJECTORY. FIVE METRICS:***
⭐   ⭐ ① ***TASK SUCCESS*** — verified by ***your code***
⭐     (Part 4), never by the model's claim.
⭐   ⭐ ② ***STEP COUNT*** vs the known-minimum for that task.
⭐     ⭐⭐ 3 WHEN 2 WOULD DO IS FINE; 11 IS A BUG.
⭐   ⭐ ③ ***FIRST-TOOL ACCURACY*** — ⭐ did it pick the right
⭐     tool first? ⭐⭐ THE SINGLE BEST PREDICTOR OF WHETHER YOUR
⭐     TOOL ***DESCRIPTIONS*** ARE THE PROBLEM (D438).
⭐   ⭐ ④ ***REPEAT-CALL RATE*** — Part 1.
⭐   ⭐ ⑤ ***COST AND p95 LATENCY PER TASK*** — ⭐⭐ GATED, NOT
⭐     REPORTED (D421).

⭐ ***AND THE ONE THAT CATCHES REAL DAMAGE:***
⭐   ⭐ ⭐⭐ ***UNAUTHORISED-ACTION COUNT MUST BE ZERO.*** ⭐ Seed
⭐     the corpus with injected instructions (Day 446) and assert
⭐     that no gated tool ever fires without approval.
⭐   ⭐⭐ HARD GATE, NO TOLERANCE BAND — ⭐ same class as Day
⭐     434's leak count. ⭐ A safety invariant is not a score.

⭐ ***THE EVAL SET IS THE TRAJECTORY, STORED:*** ⭐ record every
⭐   run's messages, tool calls, results and budget (Day 439's
⭐   store gave you this free). ⭐⭐ A FAILED PRODUCTION RUN IS A
⭐   REGRESSION TEST YOU CAN REPLAY, AND THE ONLY REASON MOST
⭐   TEAMS CANNOT IS THAT THEY LOGGED THE ANSWER AND NOT THE
⭐   PATH.
```

# 💬 Interview

**1. "Your agent calls the same failing tool five times. Why, and what do you do?"**

⭐ Because each step is a fresh forward pass conditioned on a transcript in which that call is the most
plausible next action, and the previous failures read as evidence that this is what one *does* here
rather than evidence to stop. ⭐⭐ There's no loop counter, no memory, no frustration — the model has no
mechanism for "I already tried this" beyond what the text literally says. ⭐ So the fix is in the loop,
not the prompt: I hash the tool name plus canonicalised arguments, and on a second identical call I
don't execute it — I return a message that names both an alternative and an exit, because "don't repeat
that" alone produces a paraphrased repeat. ⭐⭐ Third time, the run aborts. ⭐ And I track repeat-call
rate as a metric, because it's one of the best health signals an agent has and it moves the moment a
prompt or model changes.

**2. "How do you stop an agent doing something irreversible?"**

⭐ By classifying every tool on a reversibility ladder and putting the gate on the **action**, not on the
model's request to act. ⭐⭐ A system prompt saying "always ask before sending email" is a request to a
text predictor, and it'll be honoured most of the time — which is the worst possible property for a
security control. ⭐ Instead the tool is flagged `needs_approval` and the loop suspends the run, so no
prompt and no injection can bypass it. ⭐ Two details make it actually work: the approval shows the
**rendered effect** — the real email body and recipient, not a JSON blob — and gates are batched one per
run, because five approvals in ninety seconds trains the user to click yes and converts the control into
a formality.

**3. "The agent completed three of five steps and failed. Now what?"**

⭐ Those three happened. ⭐⭐ There's no transaction around an agent run — it spans several systems, so I
lost isolation the moment I added a second tool. ⭐ It's a saga: order the steps so reversible ones come
first and the pivot — the first irreversible action — is as late as possible, because everything before
it can be abandoned and nothing after it can. ⭐ Then compensate rather than undo: a cancellation record
or a correction email is a **new visible fact**, not an erasure. ⭐⭐ And report precisely — "the ticket
exists, the billing record is unchanged" is the deliverable. ⭐ Where I can, though, I dodge the whole
problem: have the model propose a plan and execute it transactionally in my own code, so the model
decides *what* and a deterministic executor decides *how* and can validate the entire plan before doing
any of it.

**4. "The agent says it updated the record. Did it?"**

⭐⭐ I don't know until I check my own tool log, and I never take its word for it. ⭐ "I've updated the
address and sent a confirmation" is a plausible continuation of a transcript in which those were the
goals — that's precisely what next-token prediction produces, and it's fluent, specific and can be
completely false. ⭐⭐ So the completion signal comes from my code: success is "this tool ran and
returned ok", and the user-facing summary is **rendered from the tool log**, not from the model's final
message. ⭐ The model writes the explanation; my code writes the facts. ⭐ For anything that matters I
re-read the record after writing it.

**5. "How do you evaluate an agent?"**

⭐ On the trajectory, not just the answer, because an agent's output can be right for terrible reasons —
fourteen steps, six wrong tools and a lucky recovery, which won't recur. ⭐⭐ Five metrics: task success
verified by my code; step count against the known minimum; first-tool accuracy, which is the best signal
for whether my tool **descriptions** are the problem; repeat-call rate; and cost and p95 latency per
task, gated rather than reported. ⭐⭐ Plus one hard gate with no tolerance band: unauthorised-action
count must be zero, tested by seeding documents with injected instructions and asserting no gated tool
ever fires. ⭐ A safety invariant isn't a score.

**6. "Where does the eval set come from?"**

⭐ Production trajectories, which I already store because the run is durable — the transcript, tool
calls, results and budget are persisted after every step for resumability. ⭐⭐ That means a failed
production run is a replayable regression test for free. ⭐ Most teams can't do this, and the reason is
always the same: they logged the answer and not the path. ⭐⭐ Once you have the path, "the agent got
worse this week" becomes a diff between two trajectories rather than an argument.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "how do you make an agent safe to run?"**

Open with the property that drives every decision. **An agent that failed is exactly as fluent as one
that succeeded. "I've updated the address and sent the confirmation" is a plausible continuation of a
transcript in which those were the goals — it's what next-token prediction produces, and it can be
entirely false. So I never learn the outcome from the agent. Success is "this tool ran and returned ok"
in my own log, and the user-facing summary is rendered from that log. The model writes the explanation;
my code writes the facts.**

Then the gates. **Every tool sits on a reversibility ladder: reads, reversible writes, costly-to-reverse,
and irreversible or externally visible. The rule is that the gate is on the action, not on the model's
request to act. A system prompt saying "always ask before sending email" is a request to a text
predictor, and it'll be honoured most of the time — the worst possible property for a security control.
So the tool is flagged and the loop suspends. And the approval shows the real email body, not a JSON
blob, and there's one batched gate per run, because five approvals in ninety seconds teaches the user to
click yes and turns the control into a formality.**

Then loops and partial failure. **The doom loop happens because each step is a fresh forward pass where
that call is still the most plausible action, and the failures in the context read as evidence that this
is what one does here. There's no loop counter and no frustration. So I hash the tool and canonicalised
arguments, and the second identical call doesn't execute — it gets a message naming an alternative and
an exit, because "don't repeat that" alone produces a paraphrased repeat. Third time the run aborts.
And when three of five steps completed, that's a saga: the pivot goes as late as possible, everything
before it can be abandoned, and after it I compensate rather than undo — a correction is a new visible
fact.**

Close on evaluation, because it's what makes it improvable. **I score the trajectory, not just the
answer, since an output can be right for terrible reasons — fourteen steps and a lucky recovery that
won't happen again. Task success verified by code, step count against a known minimum, first-tool
accuracy, repeat-call rate, cost and latency. Plus one hard gate with no tolerance band:
unauthorised-action count is zero, tested by seeding documents with injected instructions. And the eval
set writes itself, because runs are durable — the transcript is already persisted for resumability, so
every failed production run is a replayable regression test. Most teams can't do that because they
logged the answer and not the path.**
