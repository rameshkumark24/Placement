# Day 111

**L-111** · **Serving it in production** — Gunicorn, Uvicorn workers, nginx, and ⭐⭐ why the reverse proxy is protecting you

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a production Python deployment is three layers, and each exists for a
> reason you can now derive — a reverse proxy because a slow client must not occupy a worker, a process
> manager because the GIL means one process cannot use more than one core, and workers because that is
> where your code actually runs.**
>
> ⭐ Day 021 sketched this. **Days 065, 081 and 106 have since supplied every underlying fact**, so
> today it should feel like arithmetic rather than configuration.

# Part 1 — ⭐⭐ The three layers

```
⭐⭐ INTERNET
⭐      │
⭐      ▼
⭐   [ nginx / ALB ]      ⭐ TLS termination · ⭐⭐ BUFFERING SLOW CLIENTS ·
⭐      │                    static files · compression · request size limits
⭐      ▼
⭐   [ gunicorn ]         ⭐ the MASTER: forks workers, restarts them, handles
⭐      │  │  │  │           signals (Day 081), graceful reload
⭐      ▼  ▼  ▼  ▼
⭐   [ worker × 4 ]       ⭐⭐ where YOUR CODE RUNS. One per core, because the GIL
⭐                           means one process gets one core for bytecode (Day 065)
⭐
⭐ ⇒ ⭐⭐ EACH LAYER SOLVES A PROBLEM THE LAYER BELOW CANNOT. That is the whole
⭐     architecture, and if you can name the problem for each you never need to
⭐     memorise the diagram.
```

# Part 2 — ⭐⭐ Workers, and how many

```bash
# ⭐ SYNC (WSGI — Django, Flask):
gunicorn myapp:application -w 4 -k gthread --threads 8 --bind 0.0.0.0:8000

# ⭐⭐ ASYNC (ASGI — FastAPI, Starlette):
gunicorn myapp:app -w 4 -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:8000
# ⭐ or directly:  uvicorn myapp:app --workers 4
```

| Worker type | ⭐ Concurrency | ⭐ Use for |
|---|---|---|
| `sync` | ⭐ 1 request per worker | ⭐ CPU-bound, or absolute simplicity |
| ⭐ `gthread` | ⭐ threads per worker | ⭐⭐ **the normal WSGI choice** — I/O-bound Django/Flask |
| ⭐⭐ `UvicornWorker` | ⭐⭐ an event loop per worker | ⭐ ASGI apps (Day 110) |
| `gevent`/`eventlet` | monkey-patched coroutines | ⭐ legacy; ⚠️ surprising interactions |

```
⭐⭐ HOW MANY WORKERS — DERIVE IT, DO NOT COPY A FORMULA:
⭐
⭐  · ⭐⭐ THE FLOOR IS THE CORE COUNT, BECAUSE OF THE GIL (Day 065): one process
⭐      executes bytecode on one core at a time, so N cores need N processes to
⭐      be used at all.
⭐  · ⭐⭐ CPU-BOUND WORK ⇒ workers ≈ cores. More just adds context switching.
⭐  · ⭐ SYNC + I/O-BOUND ⇒ each worker is idle while waiting, so you can
⭐      oversubscribe: gunicorn's `2 × cores + 1` is a heuristic for exactly
⭐      this, ⭐⭐ and the real number comes from measurement (Day 100A), not
⭐      from the docs.
⭐  · ⭐⭐ ASYNC + I/O-BOUND ⇒ workers = cores IS ENOUGH, because each worker
⭐      already handles thousands of concurrent connections in one loop
⭐      (Day 106). ⭐ Adding more processes buys nothing but memory.
⭐
⭐ ⚠️ ⭐⭐ AND THE CONSTRAINT PEOPLE FORGET — MEMORY AND CONNECTIONS MULTIPLY:
⭐    · 4 workers × 400 MB RSS = 1.6 GB. ⭐⭐ In a 1 GB container that is an
⭐      OOMKill (Day 082) that looks like a random restart.
⭐    · ⭐⭐ 4 workers × a pool of 20 = 80 DATABASE CONNECTIONS FROM ONE POD.
⭐      ⭐ Multiply by pod count and you exhaust Postgres's `max_connections`,
⭐      which presents as "the database is down" and is really "we did
⭐      multiplication wrong".
```

# Part 3 — ⭐ Preload, restarts, and timeouts

```bash
gunicorn myapp:app \
  --workers 4 \
  --preload \                 # ⚠️⚠️ ⭐⭐ read the warning below
  --max-requests 1000 \       # ⭐ restart a worker after N requests
  --max-requests-jitter 100 \ # ⭐⭐ so they do not all restart at once
  --timeout 30 \              # ⭐⭐ KILL a worker stuck this long
  --graceful-timeout 30       # ⭐ how long to finish in-flight work (Day 081)
```

```
⚠️⚠️ ⭐⭐ `--preload` IS THE SETTING THAT LOOKS FREE AND IS NOT.
⭐    It imports your app ONCE in the master, then forks ⇒ ⭐ copy-on-write
⭐    shares the memory, which genuinely saves hundreds of MB.
⭐    ⇒ ⚠️ ⭐⭐ BUT ANYTHING CREATED BEFORE THE FORK IS SHARED BY THE CHILDREN:
⭐         · ⭐⭐ A DATABASE CONNECTION OR POOL CREATED AT IMPORT TIME IS NOW
⭐           SHARED BY FOUR PROCESSES ⇒ ⭐⭐ interleaved protocol traffic on one
⭐           socket ⇒ corrupted results and impossible-looking errors.
⭐         · ⭐ threads do not survive fork (Day 068) ⇒ a background thread
⭐           started at import exists in the master and in none of the workers.
⭐         · ⭐ random seeds and any cached state are shared.
⭐    ⇒ ⭐⭐ THE RULE: CREATE CONNECTIONS AND POOLS *AFTER* THE FORK — in
⭐         gunicorn's `post_fork` hook, or in ASGI's `lifespan.startup`
⭐         (Day 110), which is per-worker and is why lifespan is the cleaner
⭐         answer. ⭐ Day 027's `gc.freeze()` belongs here too.
```

| Setting | ⭐ What it really does |
|---|---|
| ⭐ `--max-requests` | ⭐⭐ **restarts workers periodically — a leak mitigation, not a fix** (Day 100A) |
| `--max-requests-jitter` | ⭐ without it, all workers restart simultaneously ⇒ a latency spike |
| ⭐⭐ `--timeout` | ⭐⭐ the master **SIGKILLs** a worker silent this long — ⚠️ ⭐ in-flight requests die |
| `--graceful-timeout` | ⭐ how long a worker may finish work after `SIGTERM` (Day 081) |
| ⭐ `HUP` | ⭐⭐ **graceful reload** — new workers, old ones drain. Zero-downtime config change |

⚠️ ⭐⭐ **`--timeout` is not a request timeout.** ⭐ It is a *worker liveness* check, and it kills the
whole worker — **taking every other in-flight request on that worker with it.** ⭐⭐ **An async worker
handling 500 connections loses all 500.** Set a real per-request timeout in your application, and keep
`--timeout` as a last resort well above it.

# Part 4 — ⭐⭐ Why nginx is not optional

```
⭐⭐ THE ARGUMENT THAT MATTERS, AND IT IS DAY 106'S CONCURRENCY MATHS:
⭐   A client on a train uploads 5 MB over 40 seconds.
⭐   ⇒ ⭐⭐ WITHOUT A PROXY: one of your four workers (or one thread) is occupied
⭐        for the whole 40 seconds, doing nothing but receiving bytes slowly.
⭐        ⭐ Twenty such clients and a four-worker sync deployment is DOWN —
⭐        ⭐⭐ this is slowloris (Day 103) achieved accidentally, by commuters.
⭐   ⇒ ⭐⭐ WITH nginx: it BUFFERS the whole request, then hands your worker a
⭐        complete request over a fast local socket, and buffers the response
⭐        back out. ⭐⭐ YOUR WORKER IS BUSY FOR MILLISECONDS INSTEAD OF SECONDS.
⭐   ⇒ ⭐ nginx can do this because it is the Day 106 `selectors` architecture in
⭐        C: thousands of slow connections cost it kilobytes each.
```

| ⭐ nginx also does | ⭐ Why not in Python |
|---|---|
| ⭐ TLS termination | ⭐ C, hardware acceleration, and one place to rotate certs |
| ⭐⭐ **Static files** | ⭐⭐ `sendfile()` — kernel to socket, **never entering your process** |
| Compression | ⭐ cheaper there, and it can vary by client |
| ⭐ Request size limits | ⭐⭐ rejects a 2 GB upload **before** it reaches you |
| Rate limiting | ⭐ crude but free, and it happens before your app wakes up |
| ⭐ Connection limits, timeouts | ⭐ every limit from Day 106, enforced outside your process |

```nginx
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host              $host;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;   # ⭐ the real client IP
    proxy_set_header X-Forwarded-Proto $scheme;                       # ⭐⭐ or you generate http:// URLs
    proxy_read_timeout 30s;
}
client_max_body_size 10m;                                             # ⭐ Day 104's limit, outside
```

⚠️ ⭐⭐ **`X-Forwarded-For` is client-controlled unless the proxy overwrites it.** ⭐ Trusting it
blindly means an attacker sets their own IP for your rate limiter and audit log — **trust only the
hop your proxy appended, and configure the framework's trusted-proxy list.** (Day 123 uses this.)

⭐⭐ **`X-Forwarded-Proto` matters more than it looks:** without it your app thinks it is on plain HTTP
and generates `http://` redirect URLs and non-`Secure` cookies — **behind a TLS proxy, that is a
downgrade you introduced yourself** (Day 019).

# Part 5 — ⭐ Health checks, and the deployment checklist

```python
@route("/healthz")                    # ⭐⭐ LIVENESS — "is the process wedged?"
def healthz(request):
    return JSONResponse({"status": "ok"})      # ⭐ NO dependency checks

@route("/readyz")                     # ⭐⭐ READINESS — "should I get traffic?"
def readyz(request):
    db.execute("SELECT 1")                     # ⭐ check dependencies HERE
    return JSONResponse({"status": "ready"})
```

```
⭐⭐ THE DISTINCTION IS OPERATIONALLY CRITICAL AND ROUTINELY GOT WRONG:
⭐   LIVENESS FAILS  ⇒ ⭐⭐ THE ORCHESTRATOR KILLS AND RESTARTS THE CONTAINER.
⭐   READINESS FAILS ⇒ ⭐ it is removed from the load balancer, and left running.
⭐
⭐   ⇒ ⚠️⚠️ ⭐⭐ SO PUTTING A DATABASE CHECK IN LIVENESS IS A DISASTER: the
⭐        database blips, EVERY pod fails liveness, EVERY pod is restarted
⭐        SIMULTANEOUSLY — ⭐⭐ turning a 10-second database hiccup into a
⭐        full outage plus a cold start, with no capacity left to recover.
⭐   ⇒ ⭐⭐ LIVENESS SHOULD ALMOST NEVER FAIL. It answers one question: is this
⭐        process so wedged that only a restart can help? ⭐ Readiness is where
⭐        dependencies belong, because losing traffic is recoverable.
```

```
⭐⭐ THE DEPLOYMENT CHECKLIST — every line is a day you have done:
⭐   □ ⭐ exec form in the Dockerfile, and a SIGTERM handler       (Day 081)
⭐   □ ⭐⭐ PYTHONUNBUFFERED=1, logs to stdout as JSON             (Days 079, 099A)
⭐   □ ⭐ settings built once at startup; fail fast on missing env (Days 090, 110)
⭐   □ ⭐⭐ pools created AFTER fork / in lifespan                  (Part 3)
⭐   □ ⭐ workers = cores (async) or measured (sync); ⭐⭐ RSS × workers < limit
⭐   □ ⭐⭐ workers × pool size × pods < the database's max_connections
⭐   □ ⭐ graceful-timeout > your slowest request; preStop sleep    (Day 081)
⭐   □ ⭐ liveness with no dependencies; readiness with them
⭐   □ ⭐⭐ a per-request timeout in the app, `--timeout` above it
⭐   □ ⭐ nginx: body size limit, read timeout, X-Forwarded-*       (Part 4)
⭐   □ ⭐ a non-root USER, read-only filesystem where possible      (Day 078)
⭐   □ ⭐⭐ /healthz, /readyz, and a request id on every response   (Day 099A)
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ One worker on a 4-core box | ⭐⭐ The GIL means you are using one core. |
| ⭐⭐ **Copying `2n+1` for an async app** | ⭐⭐ Async workers already do thousands each. Cores is enough. |
| Ignoring RSS × workers | ⭐⭐ OOMKill that looks like a random restart. |
| ⭐⭐ **Forgetting workers × pool × pods** | ⭐⭐ Exhausts `max_connections` — presents as "the DB is down". |
| ⭐ `--preload` with a pool created at import | ⭐⭐ Four processes share one socket. Corrupt results. |
| Threads started at import with `--preload` | ⭐ They do not survive fork. |
| ⭐ `--max-requests` with no jitter | ⭐ Every worker restarts at once. |
| Treating `--timeout` as a request timeout | ⭐⭐ It kills the **worker** — and all its other requests. |
| ⭐⭐ **No reverse proxy** | ⭐⭐ One slow client occupies a worker for the whole upload. |
| ⭐ Serving static files from Python | ⭐ nginx uses `sendfile()`; the bytes never enter your process. |
| Trusting `X-Forwarded-For` | ⭐⭐ Client-controlled. Spoofed IPs in your rate limiter and audit log. |
| ⭐ Missing `X-Forwarded-Proto` | ⭐ `http://` redirects and non-`Secure` cookies behind TLS. |
| ⭐⭐ **A DB check in liveness** | ⭐⭐ A DB blip restarts every pod simultaneously. |

## Interview questions

**Q: Walk me through a production Python deployment.**
> Three layers, each solving something the layer below can't. A reverse proxy for TLS, static files
> and — the important one — buffering slow clients, so a commuter on a train uploading five megabytes
> doesn't occupy one of my workers for forty seconds. A process manager, because the GIL means one
> process gets one core for bytecode, so N cores need N processes. And the workers, where my code
> runs, each either a thread pool for WSGI or an event loop for ASGI. If I can name the problem each
> layer solves, the configuration follows.

**Q: How many workers?**
> The floor is the core count, because of the GIL. For CPU-bound work that's also the ceiling — more
> just adds context switching. For sync I/O-bound work you can oversubscribe, and `2n+1` is a
> reasonable starting heuristic, but the real number comes from measurement. For async I/O-bound work,
> cores is enough, because each worker already handles thousands of concurrent connections in one
> loop, so extra processes buy nothing but memory. And the constraint people forget is that things
> multiply: four workers times 400 MB is 1.6 GB, which OOMKills in a 1 GB container, and four workers
> times a pool of twenty times the pod count can exhaust Postgres's `max_connections` — which presents
> as "the database is down" and is really arithmetic.

**Q: What's the catch with `--preload`?**
> It imports the app once in the master and forks, so copy-on-write shares the memory — a real saving.
> But anything created before the fork is shared by the children, and a database connection or pool
> created at import time is then shared by four processes writing to one socket, which gives you
> interleaved protocol traffic and impossible-looking errors. Threads don't survive fork either, so a
> background thread started at import exists in the master and in none of the workers. The rule is to
> create connections after the fork — gunicorn's `post_fork` hook, or ASGI's `lifespan.startup`, which
> is per-worker and is the cleaner answer.

**Q: Why do you need nginx in front?**
> Mainly to protect workers from slow clients. A client uploading over a slow connection occupies a
> worker for the entire transfer if it talks to you directly — twenty of those and a four-worker
> deployment is down, which is slowloris achieved accidentally by commuters. nginx buffers the whole
> request and hands over a complete one on a fast local socket, so the worker is busy for milliseconds
> instead of seconds. It can do that because it's the event-loop architecture in C, where thousands of
> slow connections cost kilobytes each. Beyond that: TLS, static files via `sendfile` so the bytes
> never enter my process, body size limits enforced before the request reaches me, and connection
> limits.

**Q: Liveness or readiness — where does the database check go?**
> Readiness, always. Liveness failing means the orchestrator kills and restarts the container, so a
> database check in liveness turns a ten-second database blip into every pod being restarted
> simultaneously — a full outage plus a cold start with no capacity left to recover. Liveness should
> almost never fail; it answers only "is this process so wedged that a restart is the only fix?"
> Readiness is where dependencies belong, because being removed from the load balancer is recoverable
> and being killed isn't.

## 🎙️ Articulation drill

Record two minutes: **"How would you deploy this API?"**

⭐ **Give the three layers with the reason for each, not the names:** **"a reverse proxy, a process
manager, and workers — and each one exists for a problem the layer below can't solve."**

⭐⭐ **Then the proxy, with the argument people don't expect:** *"the proxy is mostly there to buffer
slow clients. Someone on a train uploading five megabytes over forty seconds occupies one of my workers
for that entire time if they talk to me directly — twenty of those and a four-worker deployment is
down. That's slowloris, achieved accidentally by commuters. nginx buffers the whole request and hands
my worker a complete one over a fast local socket, so it's busy for milliseconds. It can afford to,
because it's the event-loop architecture in C where a slow connection costs kilobytes."*

⭐⭐ **Then the worker maths, derived:** *"worker count starts at the core count, because the GIL means
one process gets one core for bytecode. For async, cores is also enough — each worker already handles
thousands of connections in one loop, so extra processes buy only memory. And I'd check the two things
that multiply: RSS times workers against the container limit, or you get an OOMKill that looks like a
random restart; and workers times pool size times pods against the database's `max_connections`, which
otherwise presents as 'the database is down' when it's really arithmetic."*

⭐ **Close on two specifics that show operational experience:** *"pools get created after the fork —
in lifespan, not at import — because with `--preload` a pool built before forking is shared by four
processes writing to one socket. And the database check goes in readiness, never liveness: liveness
failing means the container is killed, so a database blip would restart every pod simultaneously and
turn ten seconds of degradation into a full outage with a cold start."*
