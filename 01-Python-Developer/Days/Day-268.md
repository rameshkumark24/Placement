# Day 268 🏗️

**P-268** · 🏗 **Real-time updates** — ⭐⭐ and the honest choice between SSE and WebSockets

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: the socket is a delivery optimisation, never a source of truth — because
> the one thing a browser connection can never guarantee you is that it was connected.**
>
> ⭐ The dispatcher board in `fieldwork` should update as technicians move. ⭐⭐ That requirement can
> be met four ways, and three of them are wrong for your traffic — so the first part of today is
> arithmetic, not architecture.

# Part 1 — ⭐⭐ Do you need it? The arithmetic first

```
⭐⭐ START HERE, BECAUSE IT USUALLY ENDS THE DISCUSSION:
⭐   500 open dashboards × 1 poll / 5 s = ⭐ 100 rps
⭐   ⇒ ⭐⭐ AND ~99% OF THOSE RESPONSES ARE "NOTHING CHANGED".

⭐   ⭐ 100 rps is not a problem. It is a cached endpoint and one
⭐     extra pod. ⭐⭐ IF YOUR DASHBOARD AUDIENCE IS 20 PEOPLE,
⭐     ***POLL***. It is one endpoint you already have, it is
⭐     cacheable (Day 266), it survives a reconnect for free,
⭐     and it introduces NO new failure modes.
⭐   ⭐ Add `If-None-Match` and most of those 100 rps become 304s
⭐     that cost you almost nothing.

⭐⭐ REAL-TIME EARNS ITS COST AT EXACTLY THREE THINGS:
⭐   ① ⭐ HIGH CONNECTION COUNTS, where polling × N is real load
⭐   ② ⭐ SUB-SECOND EXPECTATIONS (a live map, a chat)
⭐   ③ ⭐⭐ A MESSAGE RATE HIGH ENOUGH THAT POLLING WOULD MISS
⭐     EVENTS BETWEEN POLLS and the intermediate states matter
```

```
⭐⭐ THREE QUESTIONS THAT PICK THE TRANSPORT:
⭐   ① DIRECTION — server→client only? ⇒ ⭐⭐ SSE, and stop here.
⭐        ⭐ You already have a REST API for client→server. The
⭐          "bidirectional" requirement is usually imagined.
⭐   ② RATE — a few messages a second? ⇒ SSE is fine.
⭐        Hundreds per second per client? ⇒ WebSockets.
⭐   ③ CLIENTS — browsers only? ⇒ SSE. Native mobile, or a
⭐        binary protocol? ⇒ WebSockets.
```

# Part 2 — ⭐⭐ SSE: one HTTP response that never ends

```
⭐   HTTP/1.1 200 OK
⭐   Content-Type: text/event-stream
⭐   Cache-Control: no-cache
⭐   X-Accel-Buffering: no          ⭐⭐ SEE THE TRAPS BELOW
⭐
⭐   id: 1043
⭐   event: job.updated
⭐   data: {"id":"7f3…","status":"en_route"}
⭐   ⭐ (a blank line ends the event)
⭐
⭐   : ping                          ⭐ a comment = a heartbeat
```

```
⭐⭐ THE KILLER FEATURE IS NOT SIMPLICITY:
⭐   ***THE BROWSER RECONNECTS FOR YOU AND SENDS `Last-Event-ID`.***
⭐   ⇒ ⭐ A 30-second tunnel drop resumes exactly where it stopped,
⭐     with no client code at all.
⭐   ⇒ ⭐⭐ IF — AND ONLY IF — YOUR SERVER ACTUALLY READS THAT
⭐     HEADER AND REPLAYS FROM IT. ⭐ Ignore it and you have
⭐     built at-most-once delivery with extra ceremony, and the
⭐     gap is invisible in every test that doesn't drop a
⭐     connection.
```

```
⭐⭐ THREE THINGS THAT WILL BITE YOU, ALL OF THEM "WORKS LOCALLY":

⭐ ① ⭐⭐ PROXY BUFFERING. nginx buffers the response, so nothing
⭐     reaches the browser until the buffer fills or the request
⭐     ends — ⭐ which for a stream is NEVER.
⭐     ⇒ `proxy_buffering off` / `X-Accel-Buffering: no`.
⭐     ⭐⭐ Locally you had no proxy, so it worked perfectly, and
⭐       in staging it is silent rather than broken.

⭐ ② ⭐⭐ HTTP/1.1 ALLOWS SIX CONNECTIONS PER ORIGIN. One is now
⭐     permanently occupied by the stream. ⭐ Open the app in
⭐     seven tabs and the seventh HANGS — including its normal
⭐     API calls. ⇒ ⭐⭐ SSE EFFECTIVELY REQUIRES HTTP/2, where
⭐     streams are multiplexed over one connection.

⭐ ③ ⭐ IDLE TIMEOUTS. Load balancers close connections with no
⭐     traffic (ALB default 60 s). ⇒ a `: ping` comment every
⭐     15–30 s, which also lets the client detect a dead link.
```

```
⭐ ⭐ WHAT SSE CANNOT DO: client→server messages, binary frames,
⭐   and custom headers on the initial request from `EventSource`
⭐   — ⭐⭐ WHICH MEANS SSE HAS THE SAME BROWSER AUTH PROBLEM AS
⭐   WEBSOCKETS (Part 3), unless you authenticate with a cookie.
```

# Part 3 — ⭐⭐ WebSockets, and the auth trap

```
⭐⭐ THE TRAP, AND IT IS SPECIFIC TO BROWSERS:
⭐   `new WebSocket(url)` ⇒ ⭐⭐ YOU CANNOT SET HEADERS. There is
⭐   no `Authorization` on a browser WebSocket handshake. So:

⭐   ❌ wss://api.example.com/ws?token=eyJhbGciOi...
⭐   ⇒ ⭐⭐ THE ACCESS TOKEN IS NOW IN: the load balancer access
⭐     log · the proxy log · the APM trace · browser history ·
⭐     and any `Referer` the page later sends.
⭐   ⭐ Logs are retained for 90 days and read by more people
⭐     than your database is.

⭐⭐ THE PATTERN: A CONNECTION TICKET.
⭐   ① POST /ws-ticket with your NORMAL auth (Day 258)
⭐   ② server returns a single-use, 30-second, user-scoped ticket
⭐   ③ wss://…/ws?ticket=…  ⇒ server redeems it ONCE and drops it
⭐   ⇒ ⭐⭐ LEAKED INTO A LOG, IT IS WORTH THIRTY SECONDS AND ONE
⭐     USE — ⭐ which is the entire point.
```

```
⭐⭐ THE ONE ALMOST NOBODY CHECKS: CROSS-SITE WEBSOCKET HIJACKING.
⭐   ⭐ Cookies ARE sent on the WebSocket handshake.
⭐   ⭐⭐ AND THE SAME-ORIGIN POLICY DOES NOT APPLY TO WEBSOCKETS.
⭐   ⇒ ⭐⭐ ANY SITE CAN OPEN A SOCKET TO YOUR API WITH YOUR
⭐     USER'S COOKIES ATTACHED, AND READ EVERYTHING YOU PUSH.
⭐   ⇒ ⭐ YOU MUST VALIDATE THE `Origin` HEADER YOURSELF, on the
⭐     handshake. There is no framework default that does it.

⭐⭐ AND AUTHORISATION IS NOT A ONE-TIME EVENT ON A LONG SOCKET:
⭐   ⭐ the token expires 15 minutes in; the role is revoked;
⭐     the user is removed from the tenant
⭐   ⇒ ⭐⭐ A CONNECTION OPENED AT 09:00 MUST NOT STILL BE
⭐     RECEIVING A MANAGER'S EVENTS AT 17:00. ⭐ Enforce a max
⭐     connection lifetime, and re-check authorisation on
⭐     subscribe — not only on connect.
```

# Part 4 — ⭐⭐ Fan-out, and the rule that makes real-time safe

```
⭐⭐ THE PROBLEM THAT DOES NOT EXIST UNTIL REPLICA #2:
⭐   ⭐ Client X holds a socket on ⭐ PROCESS A.
⭐   ⭐ The event happens in ⭐ PROCESS C (a different pod, or a
⭐     Celery worker, or the outbox relay).
⭐   ⇒ ⭐⭐ PROCESS C HAS NO SOCKET FOR X. The message is never
⭐     delivered, ⭐⭐ AND NOTHING ERRORS ANYWHERE.
⭐   ⭐ Locally you had one process, so it was flawless.
```

```
⭐⭐ THE BUS: Redis Pub/Sub (Day 209). Every process subscribes;
⭐   any process publishes; each delivers to its own sockets.
⭐   ⇒ ⭐ This is also why you do NOT need sticky sessions — a
⭐     client can land on any pod.
⭐   ⇒ ⭐⭐ BUT PUB/SUB IS AT-MOST-ONCE: a subscriber that is
⭐     reconnecting misses everything published in that window,
⭐     with no record that it happened.
```

```
⭐⭐ SO — THE RULE, AND IT IS THE MOST IMPORTANT LINE OF THE DAY:
⭐   ***THE SOCKET IS AN OPTIMISATION. THE TRUTH IS THE DATABASE.***
⭐   ⇒ ⭐ Every push has a REST equivalent.
⭐   ⇒ ⭐ The client REFETCHES ON RECONNECT rather than assuming
⭐     it missed nothing.
⭐   ⇒ ⭐⭐ A DROPPED MESSAGE THEREFORE COSTS ***LATENCY, NOT
⭐     CORRECTNESS*** — which is what makes the whole feature
⭐     safe to build on an at-most-once bus.
⭐   ⇒ ⭐⭐ AND THE CONVERSE: IF LOSING A MESSAGE LOSES DATA, YOU
⭐     NEEDED A STREAM WITH ACKNOWLEDGEMENTS (Day 209), NOT A
⭐     SOCKET. ⭐ Notice that this is the same distinction as
⭐     Pub/Sub vs Streams, arriving from the other direction.
```

```
⭐⭐ TWO DESIGN RULES FOR WHAT YOU PUBLISH:
⭐   ⭐ PUBLISH IDs AND A TYPE, NOT PAYLOADS — same reasons as
⭐     Day 265, plus a new one: ⭐⭐ A PAYLOAD ON A CHANNEL
⭐     BYPASSES PER-USER AUTHORISATION, because the process
⭐     delivering it did not run your predicate (Day 259).
⭐   ⭐⭐ CHANNELS ARE SCOPED — `tenant:{id}:jobs`, never a global
⭐     `jobs` channel that every process filters afterwards.
⭐     ⭐ Filtering after fan-out means one tenant's events were
⭐       already in a process that will happily deliver them the
⭐       day someone edits that filter.
```

# Part 5 — ⭐⭐ Backpressure: one slow client, everyone's outage

```
⭐⭐ A TECHNICIAN ON A TRAIN. YOU PUSH 200 msg/s. THEY ACK 5.
⭐   ⇒ ⭐ TCP backs up. Your per-connection send buffer grows.
⭐   ⇒ ⭐⭐ AND IN MOST FRAMEWORKS THAT BUFFER IS UNBOUNDED BY
⭐     DEFAULT ⇒ ⭐⭐ ONE SLOW CLIENT OOMs THE PROCESS SERVING
⭐     FOUR THOUSAND OTHERS.

⭐⭐ SO EVERY PER-CONNECTION QUEUE IS BOUNDED, AND YOU CHOOSE
⭐   WHAT HAPPENS WHEN IT FILLS:
⭐   ⭐ COALESCE — keep only the LATEST state per entity.
⭐     ⇒ ⭐⭐ USUALLY CORRECT FOR DASHBOARDS: nobody needs the
⭐       intermediate values, they need the current one.
⭐   ⭐ DROP-OLDEST — acceptable for pure notifications.
⭐   ⭐⭐ DISCONNECT — the most honest option, because Part 4's
⭐     rule makes it safe: the client reconnects and refetches,
⭐     and is instantly correct again.
```

# Part 6 — ⭐⭐ Operating connections

```
⭐⭐ ① THE PROCESS MODEL IS NOT NEGOTIABLE.
⭐   ⭐ A sync worker holds one connection per thread. 5,000
⭐     connections is not achievable that way.
⭐   ⇒ ⭐⭐ THIS IS AN ASYNC WORKLOAD BY CONSTRUCTION — and
⭐     therefore ⭐⭐ ONE BLOCKING CALL IN A HANDLER STALLS EVERY
⭐     CONNECTION ON THAT PROCESS. ⭐ Exactly Day 258's argon2
⭐     lesson, with four thousand victims instead of a queue.

⭐⭐ ② SCALING IS DIFFERENT BECAUSE CONNECTIONS ARE STATE.
⭐   ⭐ Adding a pod does not relieve the loaded pod — existing
⭐     connections stay where they are. ⭐⭐ RELIEF ONLY ARRIVES
⭐     WHEN CLIENTS RECONNECT, which is the opposite of how a
⭐     stateless tier behaves and surprises people mid-incident.

⭐⭐ ③ THE DEPLOY IS A SELF-INFLICTED THUNDERING HERD.
⭐   ⭐ Every connection drops at once, and every client
⭐     reconnects in the same second ⇒ ⭐⭐ AND EACH RECONNECT
⭐     TRIGGERS A REFETCH (Part 4), so you get a connection
⭐     storm AND a REST storm together.
⭐   ⇒ ⭐ JITTERED EXPONENTIAL BACKOFF IN THE CLIENT — the same
⭐     lesson as Day 265's retries, on the other side of the wire.
⭐   ⇒ ⭐ Plus connection draining so a rollout is staggered.

⭐⭐ ④ WHAT TO GRAPH:
⭐   ⭐ open connections (per pod — an imbalance is normal and
⭐     tells you when the last deploy was)
⭐   ⭐ messages published vs delivered ⇒ ⭐⭐ THE GAP IS YOUR
⭐     REAL DELIVERY RATE, and it is never 100%
⭐   ⭐ disconnect reasons, and RECONNECT RATE — ⭐⭐ a spike in
⭐     reconnects is the earliest signal that you broke something
⭐   ⭐ per-connection buffer high-water marks
```

# Part 7 — ⭐ Testing it

```
⭐   ❌ time.sleep(2); assert received == [...]
⭐   ⇒ ⭐ Slow when it passes, flaky when it fails, and it fails
⭐     on a loaded CI box for no reason (Day 261).
⭐   ⭐⭐ WAIT ON THE EVENT WITH A DEADLINE:
⭐     msg = await asyncio.wait_for(client.receive(), timeout=2)

⭐⭐ AND TEST THE PATH THAT ACTUALLY HAS BUGS — THE RECONNECT:
⭐   ① connect, ② kill the connection server-side, ③ publish
⭐   three events while it is down, ④ let it reconnect,
⭐   ⑤ ⭐⭐ ASSERT THE CLIENT'S STATE MATCHES THE REST ENDPOINT.
⭐   ⇒ ⭐⭐ THAT ASSERTION IS PART 4'S RULE, EXPRESSED AS A TEST —
⭐     and it is the single most valuable test in this day.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Building real-time without the polling arithmetic | 500 dashboards at one poll per 5 s is 100 rps. Poll. |
| Choosing WebSockets for server→client-only updates | SSE, and you keep the browser's free reconnect. |
| Ignoring `Last-Event-ID` | You built at-most-once with extra ceremony, invisibly. |
| Forgetting proxy buffering | Nothing is delivered, and it worked locally because there was no proxy. |
| SSE over HTTP/1.1 | Six connections per origin; the seventh tab hangs, API calls included. |
| No heartbeat | Load balancers close idle connections at 60 s. |
| A token in the WebSocket query string | It lands in access logs, APM traces and browser history. |
| No `Origin` check on the handshake | Cross-site WebSocket hijacking — the same-origin policy doesn't apply. |
| Authorising only at connect | A socket opened at 09:00 still delivers a revoked manager's events at 17:00. |
| Delivering from the process that has the socket | With N pods the event usually happens elsewhere, and nothing errors. |
| Sticky sessions to "solve" fan-out | A bus solves it properly and keeps the tier replaceable. |
| Publishing payloads on a channel | The delivering process never ran your authorisation predicate. |
| A global channel filtered per process | One tenant's events are already in a process that may deliver them. |
| Treating the socket as the source of truth | Pub/Sub is at-most-once. Every push needs a REST equivalent. |
| Unbounded per-connection buffers | One client on a train OOMs the process serving four thousand. |
| Sync workers for connections | It's an async workload; one blocking call stalls every connection. |
| Expecting a new pod to relieve load | Connections are state; relief only comes on reconnect. |
| No client-side reconnect jitter | Every deploy is a connection storm plus a REST storm. |
| Graphing only connection count | Published-versus-delivered is the number that shows loss. |
| `sleep()` in real-time tests | Slow when passing, flaky when failing. Wait with a deadline. |

## Interview questions

**Q: SSE or WebSockets?**

> Usually neither, and I'd start with the arithmetic: five hundred dashboards polling every five
> seconds is a hundred requests a second, which is one cached endpoint. Real-time earns its cost at
> high connection counts, sub-second expectations, or a message rate where polling would miss events
> that matter. If I do need it, direction decides: server-to-client only means SSE, because it's plain
> HTTP and the browser reconnects for me with `Last-Event-ID` — which is the actual feature, not the
> simplicity. WebSockets when I need bidirectional, high rate, or binary. And SSE has real costs: it
> needs HTTP/2 or the sixth-connection limit hangs a tab, and it dies silently behind a buffering
> proxy.

**Q: How do you authenticate a browser WebSocket?**

> Not with a token in the query string, because that ends up in load balancer logs, APM traces and
> browser history, all of which are read by more people than the database is. Browsers can't set
> headers on a WebSocket, so I use a ticket: the client calls a normal authenticated endpoint, gets a
> single-use thirty-second user-scoped ticket, and connects with that — leaked, it's worth thirty
> seconds and one use. The one people miss is that cookies *are* sent on the handshake and the
> same-origin policy doesn't apply to WebSockets, so any site can open a socket to your API with your
> user's cookies attached. You have to validate `Origin` yourself.

**Q: A user is connected to pod A and the event happens in a Celery worker. How does it reach them?**

> Through a bus — Redis Pub/Sub on a tenant-scoped channel, with every pod subscribed. That's also
> why I don't need sticky sessions. But Pub/Sub is at-most-once: a subscriber that's reconnecting
> misses everything published in that window with no record. So the rule is that the socket is a
> delivery optimisation and the database is the truth — every push has a REST equivalent and the
> client refetches on reconnect, which makes a dropped message cost latency rather than correctness.
> If losing a message would lose data, I needed a stream with acknowledgements, not a socket.

**Q: What happens when one client is slow?**

> If the per-connection send buffer is unbounded — which is the default in most frameworks — one
> client on a bad connection grows a buffer until the process OOMs, and it takes down the four
> thousand other connections on that pod. So every per-connection queue is bounded and I choose the
> policy: coalescing to the latest state per entity is usually right for a dashboard, because nobody
> needs the intermediate values; otherwise drop-oldest, or just disconnect, which is honest and safe
> precisely because the client reconnects and refetches.

**Q: What breaks when you deploy?**

> Every connection drops at once and every client reconnects in the same second — and because each
> reconnect triggers a refetch, you get a connection storm and a REST storm simultaneously. The fix
> is jittered exponential backoff in the client, which is the same lesson as queue retries from the
> other side of the wire, plus connection draining to stagger the rollout. And the thing that
> surprises people mid-incident is that adding a pod doesn't relieve a loaded one, because
> connections are state — relief only arrives when clients reconnect.

## Today's build

1. ⭐⭐ Do the polling arithmetic for your real audience and write down why you are or aren't building this.
2. ⭐ Build the polling version first with an ETag, and measure the cost of a 304.
3. ⭐⭐ Implement SSE with event IDs, and implement `Last-Event-ID` replay on the server.
4. ⭐ Drop the connection for 30 seconds, publish three events, and prove all three arrive on resume.

## 🎙️ Articulation drill

**Three minutes: "Add live updates to the dispatch board."**

Start by doing the arithmetic out loud, because it demonstrates the instinct: **five hundred
dashboards polling every five seconds is a hundred requests a second, and ninety-nine percent of
those responses say nothing changed** — that's one cached endpoint, so if the audience is small, poll,
and you inherit no new failure modes. Then name the three conditions under which real-time actually
pays, and pick the transport on direction: server-to-client only means SSE, whose real feature is that
**the browser reconnects for you and sends `Last-Event-ID`** — provided you actually implement the
replay, or you've built at-most-once with extra ceremony. Mention the two operational traps that both
present as "works locally": proxy buffering and the six-connection limit. For WebSockets, lead with
auth, because it's the part people get wrong: **browsers can't set headers, so tokens end up in query
strings and then in access logs**, and the fix is a single-use thirty-second ticket — plus an `Origin`
check, because cookies travel on the handshake and the same-origin policy doesn't apply. Then fan-out:
with N pods the event usually happens somewhere else and nothing errors, so a bus — and since Pub/Sub
is at-most-once, **the socket is an optimisation and the database is the truth**, every push has a
REST equivalent, the client refetches on reconnect, and a lost message costs latency rather than
correctness. Close on the two operational realities: **one slow client with an unbounded buffer OOMs
the process serving four thousand**, and every deploy is a connection storm plus a refetch storm
unless the client backs off with jitter.
