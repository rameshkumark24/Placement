# Day 306 🧭

**P-306** · 🧭 **The modular monolith** — ⭐⭐ the architecture you should default to

**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: microservices are a deployment answer to an organisational problem — so
> if you cannot name the team boundary or the scaling boundary that forced the split, you have bought
> distributed systems failure modes and paid for them with nothing.**
>
> ⭐ Day 305 gave you bounded contexts. ⭐⭐ Today is where they live: modules with enforced
> boundaries inside one deployable, which is both the right default *and* the only architecture from
> which extracting a service is ever cheap.

---

# Part 1 — ⭐⭐ What a network call actually costs

```
⭐⭐ THE COMPARISON THAT SHOULD PRECEDE EVERY SPLIT DECISION:

⭐   ⭐ A FUNCTION CALL
⭐        ⭐ ~nanoseconds
⭐        ⭐ two outcomes: it returns, or it raises
⭐        ⭐⭐ CANNOT HALF-SUCCEED
⭐        ⭐ refactorable by a tool, typed end to end

⭐   ⭐ A NETWORK CALL
⭐        ⭐ ~milliseconds — ⭐ 10,000× slower, before load
⭐        ⭐⭐ THREE OUTCOMES: SUCCESS, FAILURE, ***AND THE
⭐          TIMEOUT THAT MEANS YOU DO NOT KNOW*** (Day 263)
⭐        ⭐ needs a timeout, a retry policy, idempotency, a
⭐          circuit breaker (Day 286)
⭐        ⭐⭐ AND THE CONTRACT IS NOW VERSIONED ACROSS A DEPLOY
⭐          BOUNDARY, so both sides must work during a rollout

⭐ ⇒ ⭐⭐ SO SPLITTING A SERVICE DOES NOT "DECOUPLE" ANYTHING.
⭐   ***IT CONVERTS EVERY IN-PROCESS CONSISTENCY GUARANTEE INTO
⭐      A DISTRIBUTED ONE.*** ⭐ Your transaction across two
⭐   modules becomes a saga; your invariant becomes eventual;
⭐   your stack trace becomes four log searches.
```

```
⭐⭐ AND THE COUPLING DOES NOT GO AWAY — IT CHANGES FORM
⭐   (Day 298):
⭐   ⭐ Before: a module imports another module's function.
⭐     ⭐ Refactorable, type-checked, breaks at CI.
⭐   ⭐ After: a service calls another service's HTTP endpoint.
⭐     ⭐⭐ SAME LOGICAL COUPLING, NOW INVISIBLE TO EVERY TOOL
⭐     YOU OWN, AND IT BREAKS IN PRODUCTION INSTEAD OF IN CI.
⭐   ⇒ ⭐⭐ "WE SPLIT IT SO THE TEAMS WOULDN'T BLOCK EACH
⭐     OTHER" IS A REAL REASON. ⭐ "We split it so the code
⭐     would be decoupled" is a misunderstanding of where
⭐     coupling lives.
```

# Part 2 — ⭐⭐ The three real reasons to split

```
⭐⭐ ① ***INDEPENDENT DEPLOY CADENCE, BLOCKED BY A SHARED
⭐     RELEASE.*** ⭐ Six teams, one pipeline, and a failing
⭐     test in payments blocks a search fix.
⭐     ⇒ ⭐⭐ THIS IS THE REAL DRIVER IN NEARLY EVERY HONEST
⭐       CASE, AND IT IS ***ORGANISATIONAL***.

⭐⭐ ② ***GENUINELY DIFFERENT RESOURCE PROFILES.*** ⭐ Video
⭐     transcoding needs 16 CPUs and no traffic; the API needs
⭐     many small instances. ⭐ Scaling them together is real
⭐     waste — ⭐⭐ THOUGH NOTE A SEPARATE ***WORKER*** OFTEN
⭐     SOLVES THIS WITHOUT A SEPARATE SERVICE (Day 284).

⭐⭐ ③ ***A HARD OWNERSHIP OR COMPLIANCE BOUNDARY.*** ⭐ Card
⭐     data in a smaller audited scope; a separate team with
⭐     separate on-call.

⭐⭐ AND THE REASONS THAT ARE NOT REASONS:
⭐   ⭐ ❌ "it's cleaner"           ⇒ Day 298
⭐   ⭐ ❌ "we might need to scale" ⇒ ⭐ you can split later,
⭐        and Part 6 says extraction from a good module is days
⭐   ⭐ ❌ "everyone does it"
⭐   ⭐ ❌ ⭐⭐ "SO WE CAN USE DIFFERENT LANGUAGES" ⇒ that is a
⭐        cost being described as a benefit
```

# Part 3 — ⭐⭐ The structure: slice first, layer inside

```
⭐⭐ DAY 299'S LIMIT WAS THAT LAYERS SLICE HORIZONTALLY WHILE
⭐   FEATURES ARE VERTICAL. ⭐ The fix is to do both, in the
⭐   right order:

⭐   app/
⭐     billing/          ⭐⭐ ← A BOUNDED CONTEXT (Day 305)
⭐       api.py          ⭐⭐ THE ONLY PUBLIC SURFACE
⭐       domain/
⭐       services/
⭐       repositories/
⭐       models.py       ⭐ its own tables
⭐     dispatch/
⭐       api.py
⭐       …
⭐     shared_kernel/    ⭐ Money, ids, clock — tiny and stable
⭐     platform/         ⭐ db session, config, logging

⭐ ⇒ ⭐⭐ THE TEST THAT THE SLICING IS RIGHT: A TYPICAL FEATURE
⭐   CHANGE TOUCHES ***ONE TOP-LEVEL DIRECTORY***. ⭐ If every
⭐   change still touches four, you renamed folders (Day 298 —
⭐   count the files).

⭐⭐ AND `api.py` IS THE WHOLE DISCIPLINE:
⭐   ⭐ It exposes functions and DTOs. ⭐⭐ NEVER ENTITIES,
⭐     NEVER ORM MODELS, NEVER A SESSION.
⭐   ⭐ It is the thing you would turn into HTTP if you ever
⭐     extracted the module — ⭐⭐ WHICH MAKES IT A REHEARSAL
⭐     FOR A SPLIT YOU MAY NEVER NEED, AT ALMOST NO COST.
```

# Part 4 — ⭐⭐ Enforcement, or it is just folders

```ini
[importlinter:contract:module-independence]
name = Contexts are independent
type = independent
modules =
    app.billing
    app.dispatch
    app.support

[importlinter:contract:public-api-only]
name = Cross-context imports go through api
type = forbidden
source_modules = app.dispatch
forbidden_modules =
    app.billing.domain
    app.billing.services
    app.billing.models        # ⭐⭐ api.py IS NOT LISTED — that is the point
```

```
⭐⭐ AND THE RULE THAT IS BROKEN MOST OFTEN, AND MATTERS MOST,
⭐   BECAUSE NO IMPORT LINTER CAN SEE IT:
⭐   ***A MODULE MAY NOT READ ANOTHER MODULE'S TABLES.***
⭐   ⭐ `dispatch` writes `SELECT … FROM billing_invoices` and
⭐     ⭐⭐ THERE IS NOT ONE IMPORT TO DETECT (Day 298).
⭐   ⇒ ⭐⭐ CONSEQUENCE: BILLING CAN NEVER CHANGE ITS SCHEMA
⭐     AGAIN, because it does not know who reads it — ⭐ which
⭐     is precisely the freedom the module boundary existed to
⭐     provide, now silently gone.
⭐   ⇒ ⭐ ENFORCE IT MECHANICALLY, since a linter cannot:
⭐     ⭐ table name prefixes per module (`billing_*`)
⭐     ⭐⭐ A TEST THAT GREPS EACH MODULE'S SQL AND MODELS FOR
⭐       ANOTHER MODULE'S PREFIX
⭐     ⭐ or, strongest, ⭐⭐ A POSTGRES SCHEMA PER MODULE WITH
⭐       A DB ROLE THAT CANNOT SELECT FROM THE OTHERS — the
⭐       database refusing is worth more than any convention.
```

# Part 5 — ⭐⭐ How modules talk

```
⭐⭐ TWO MECHANISMS, AND THE CHOICE IS THE SAME ONE AS DAY 305:

⭐ ① ⭐ DIRECT CALL TO `other.api`
⭐      ⭐ synchronous, typed, refactorable, ⭐⭐ AND IT CAN
⭐        SHARE A TRANSACTION IF YOU DECIDE IT SHOULD — which
⭐        is a capability you ***lose forever*** the moment you
⭐        split into services, and is the single most
⭐        underrated benefit of the monolith.
⭐      ⭐ Use when: you need the answer now, and consistency
⭐        matters.

⭐ ② ⭐ A DOMAIN EVENT (Day 305)
⭐      ⭐ asynchronous, no return value, ⭐ publisher does not
⭐        know the subscribers.
⭐      ⭐ Use when: the other module reacting is not your
⭐        concern, and eventual is acceptable.
⭐      ⭐⭐ IN-PROCESS DISPATCH IS FINE ***IF*** LOSS IS
⭐        ACCEPTABLE; OTHERWISE IT IS THE OUTBOX (Day 263) —
⭐        and this is exactly where people get it wrong, because
⭐        an in-process event bus feels like infrastructure and
⭐        delivers nothing.

⭐⭐ THE DIRECTION RULE THAT PREVENTS THE WORST TANGLE:
⭐   ⭐ Prefer ⭐⭐ EVENTS UPWARD AND CALLS DOWNWARD. ⭐ A
⭐     "lower" module (billing) should not call "upward" into
⭐     dispatch; it emits `InvoiceIssued` and dispatch listens.
⭐   ⇒ ⭐⭐ MUTUAL DIRECT CALLS BETWEEN TWO MODULES IS A CYCLE,
⭐     AND A CYCLE MEANS THEY ARE ***ONE MODULE*** THAT HAS
⭐     BEEN SPLIT ALONG THE WRONG SEAM. ⭐ The import linter
⭐     will tell you; believe it rather than adding an
⭐     exception.
```

# Part 6 — ⭐⭐ Extraction, and the paradox

```
⭐⭐ IF THE MODULE IS PROPERLY BOUNDED, EXTRACTING IT IS
⭐   MOSTLY MECHANICAL:
⭐   ① `api.py` becomes an HTTP (or gRPC) interface — ⭐ the
⭐        signatures already exist and already take DTOs
⭐   ② callers swap a direct call for a client that implements
⭐        the same protocol (Day 300)
⭐   ③ ⭐⭐ THE HARD PART, AND IT IS THE ONLY HARD PART:
⭐        ***ANY TRANSACTION THAT SPANNED BOTH MODULES MUST NOW
⭐        BECOME A SAGA WITH COMPENSATION*** — ⭐ which is
⭐        exactly the work Days 263 and 305 prepared you for.
⭐   ④ the tables move, and every cross-module read you allowed
⭐        becomes a migration you cannot do

⭐⭐ HENCE THE PARADOX, AND IT IS WORTH SAYING IN AN INTERVIEW:
⭐   ***A MODULE YOU COULD EXTRACT CHEAPLY IS USUALLY A MODULE
⭐      YOU DO NOT NEED TO EXTRACT*** — the boundary is already
⭐   doing its work. ⭐⭐ AND A MODULE YOU ***CANNOT*** EXTRACT
⭐   CHEAPLY IS ONE YOU MUST NOT EXTRACT, because the split
⭐   would spread a tangle across a network.
⭐   ⇒ ⭐ Which yields the practical rule: ⭐⭐ THE MODULAR
⭐     MONOLITH IS BOTH THE DESTINATION ***AND*** THE ONLY SANE
⭐     ROUTE TO MICROSERVICES. ⭐ Anyone starting with services
⭐     is guessing at boundaries with the highest-cost tool
⭐     available.
```

# Part 7 — ⭐ The honest costs

```
⭐   ⭐ ONE DEPLOY — ⭐ a bad change in any module can take the
⭐     whole thing down. ⭐⭐ MITIGATED BY THE SAME GATES YOU
⭐     ALREADY BUILT (Day 281) AND BY FEATURE FLAGS (Day 283),
⭐     NOT BY SPLITTING.
⭐   ⭐ ONE RUNTIME — ⭐⭐ A MEMORY LEAK OR AN EVENT-LOOP BLOCK
⭐     IN ONE MODULE AFFECTS ALL OF THEM (Day 258). ⭐ Real,
⭐     and the strongest argument in this list.
⭐   ⭐ ONE LANGUAGE AND ONE RUNTIME VERSION.
⭐   ⭐ DISCIPLINE IS REQUIRED FOREVER — ⭐⭐ THE BOUNDARY IS
⭐     ENFORCED BY A CONTRACT FILE THAT ANYONE CAN ADD AN
⭐     EXCEPTION TO. ⭐ A service boundary enforces itself
⭐     brutally; a module boundary needs a culture, ⭐ which is
⭐     why every exception added to that file deserves the same
⭐     scrutiny as an ADR.
⭐ ⇒ ⭐⭐ NAMING THESE COSTS IS WHAT MAKES THE RECOMMENDATION
⭐   CREDIBLE. ⭐ "Modular monolith, and here is what it costs
⭐   me" beats "monoliths are fine" by a wide margin.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Splitting for decoupling | It converts in-process guarantees into distributed ones; the coupling just becomes invisible. |
| Ignoring the third outcome | A network call can time out, which means you don't know. |
| "We might need to scale" | You can extract later — from a good module it's days. |
| "Different languages" as a benefit | That's a cost described as a benefit. |
| Layering before slicing | Every change still touches four directories; you renamed folders. |
| Exposing entities or ORM models from a module | `api.py` exposes functions and DTOs, or the boundary is decorative. |
| Relying on convention for module boundaries | Import-linter contracts, or it's just folders. |
| One module reading another's tables | No import exists to detect it, and the owner can never change its schema. |
| No mechanical table-ownership check | Prefixes and a grep test, or schemas and roles — a linter can't see SQL. |
| An in-process event bus for work that must happen | It feels like infrastructure and delivers nothing. Use the outbox. |
| Mutual direct calls between modules | That's a cycle: one module split along the wrong seam. |
| Adding a linter exception to resolve a cycle | Believe the tool; fix the seam. |
| Forgetting cross-module transactions on extraction | They become sagas with compensation — the only genuinely hard part. |
| Starting with microservices | Guessing at boundaries with the most expensive tool available. |
| Recommending a monolith without naming its costs | One runtime, one deploy, and discipline forever. |

## Interview questions

**Q: Monolith or microservices?**

> A modular monolith by default, and I'd justify it by what a split actually costs rather than by
> taste. A function call is nanoseconds with two outcomes and can't half-succeed; a network call is
> milliseconds with three outcomes, including the timeout that means you don't know — so splitting
> doesn't decouple anything, it converts every in-process consistency guarantee into a distributed
> one. Transactions become sagas, invariants become eventual, and a stack trace becomes four log
> searches. The coupling doesn't disappear either; it becomes invisible to every tool I own and breaks
> in production instead of CI.

**Q: So when would you split?**

> Three reasons. Independent deploy cadence blocked by a shared release — six teams, one pipeline, a
> failing payments test blocking a search fix — which is the honest driver in most real cases and is
> organisational rather than technical. Genuinely different resource profiles, though a separate
> worker process often solves that without a separate service. And a hard ownership or compliance
> boundary, like keeping card data in a smaller audited scope. What I wouldn't accept is "it's
> cleaner" or "we might need to scale", because extraction from a well-bounded module is a few days'
> work.

**Q: What does a modular monolith look like?**

> Sliced by bounded context first, layered inside each slice — so a typical feature change touches one
> top-level directory, and if it still touches four, I've renamed folders rather than restructured.
> Each module has an `api.py` that exposes functions and DTOs and never entities, ORM models or a
> session; that file is exactly what would become an HTTP interface if I ever extracted the module,
> so it's a rehearsal for a split I may never need at almost no cost. Plus a deliberately tiny shared
> kernel, because everything depends on it and every change there is fleet-wide.

**Q: How do you stop it becoming a big ball of mud?**

> Import-linter contracts in CI: modules independent, and cross-context imports only through `api`.
> But the rule that matters most is one no linter can see — a module may not read another module's
> tables. There's no import to detect when dispatch selects from `billing_invoices`, and the
> consequence is that billing can never change its schema again because it doesn't know who reads it,
> which is exactly the freedom the boundary existed to give. So I enforce it mechanically: table
> prefixes per module and a test that greps for foreign prefixes, or — strongest — a Postgres schema
> per module with a role that can't select from the others. The database refusing beats any
> convention.

**Q: What's the paradox of extraction?**

> That a module you could extract cheaply is usually one you don't need to extract, because the
> boundary is already doing its work — and a module you *can't* extract cheaply is one you mustn't,
> because you'd spread a tangle across a network. Which means the modular monolith is both the
> destination and the only sane route to microservices: anyone starting with services is guessing at
> boundaries using the most expensive tool available. And I'd name the costs of my own recommendation
> — one runtime, so a memory leak or a blocked event loop in one module affects all of them, one
> deploy, and a boundary enforced by a file anyone can add an exception to.

## Today's build

1. ⭐⭐ Draw your project's bounded contexts. Restructure the tree so each is a top-level module.
2. ⭐ Verify by tracing a feature change: it should touch one top-level directory.
3. ⭐⭐ Give each module an `api.py` exposing only functions and DTOs. Move everything else behind it.
4. ⭐⭐ Add independence and public-api-only contracts to import-linter. Fix every violation.
5. ⭐ Create `shared_kernel/` with Money, ids and the clock. Keep it under 200 lines.
6. ⭐⭐ Prefix each module's tables and write a test that greps for foreign prefixes in SQL and models.
7. ⭐⭐ Try the strong version: a Postgres schema per module with restricted roles. Note what breaks.
8. ⭐ Classify every cross-module interaction as a direct call or an event, and say why.
9. ⭐⭐ Find any in-process event carrying must-happen work and move it to the outbox.
10. ⭐⭐ Look for cycles between modules. For each, decide whether to invert to an event or merge them.
11. ⭐ Apply the events-upward / calls-downward rule and record any place it's violated.
12. ⭐⭐ Pick one module and write the extraction plan, including which transactions become sagas.
13. ⭐ Estimate the extraction in days, then decide honestly whether it's worth doing.
14. ⭐⭐ Write the ADR: modular monolith, the three signals that would change it, and the four costs you accept.

## 🎙️ Articulation drill

**Three minutes: "How would you structure a new system?"**

nanoseconds with two outcomes and a network call is milliseconds with three** — including the timeout
that means you don't know. So **splitting doesn't decouple anything; it converts every in-process

genuinely different resource profiles and hard compliance boundaries. Describe the structure —
