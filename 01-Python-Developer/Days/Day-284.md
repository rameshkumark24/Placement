# Day 284 🏗️

**P-284** · 🏗 **Infrastructure** — ⭐⭐ where it runs, and how it survives losing something

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: choose the smallest infrastructure that can demonstrate the properties
> you need to defend — because a hand-rolled Kubernetes cluster you cannot operate is worth less in
> an interview than a managed platform whose failure modes you can describe from memory.**
>
> ⭐ Day 283 can deploy. ⭐⭐ Today is what it deploys *onto*: reproducible, private by default,
> able to lose a component, backed up in a way you have actually restored, and costing an amount you
> can itemise.

# Part 1 — ⭐⭐ Sizing the ambition honestly

```
⭐⭐ THE TRAP: BUILDING A PLATFORM INSTEAD OF A PROJECT.
⭐   ⭐ EKS + Istio + ArgoCD + Kafka for an app with 40 users
⭐     ⇒ ⭐⭐ YOU WILL SPEND THE REMAINING WEEKS OPERATING IT
⭐       INSTEAD OF BUILDING, and you will still not be able to
⭐       answer "what happens when a node dies" — because you
⭐       never had enough traffic to find out.

⭐⭐ THE SELECTION RULE:
⭐   ***PICK THE SMALLEST THING THAT LETS YOU DEMONSTRATE THE
⭐      PROPERTY, AND KNOW ITS FAILURE MODES COLD.***
⭐   ⇒ ⭐ ECS Fargate, Cloud Run, App Runner, Fly, Render — any
⭐     of them lets you show: rolling deploys, health checks,
⭐     autoscaling, secrets, private networking, and an RDS
⭐     failover. ⭐⭐ THAT IS THE ENTIRE LIST OF THINGS ANYONE
⭐     WILL ASK YOU ABOUT.
⭐   ⇒ ⭐⭐ AND SAYING "I CHOSE FARGATE BECAUSE I DID NOT NEED
⭐     WHAT KUBERNETES COSTS TO OPERATE" IS A ***STRONGER***
⭐     ANSWER THAN A CLUSTER YOU CANNOT DEBUG. It is a sizing
⭐     judgement, and sizing judgement is what seniority is.
```

```
⭐ ⭐ THE FIVE WORKLOADS YOU ACTUALLY HAVE (from Days 253–270):
⭐   ⭐ the API           — scales on concurrency
⭐   ⭐ the worker pool   — scales on queue age (Day 265)
⭐   ⭐ the scheduler     — ⭐⭐ EXACTLY ONE (Day 264)
⭐   ⭐ the outbox relay  — one or few, idempotent (Day 263)
⭐   ⭐ migrations        — a one-shot task, run before release
⭐ ⇒ ⭐⭐ THEY ARE SEPARATE DEPLOYMENTS FROM THE SAME IMAGE,
⭐   with different commands, different scaling and different
⭐   alerts. ⭐ Running workers inside the API container is the
⭐   most common mistake here: a traffic spike then starves your
⭐   background work at exactly the moment it matters.
```

# Part 2 — ⭐⭐ Infrastructure as code, for one specific reason

```
⭐⭐ NOT "BEST PRACTICE". THE REASON IS A QUESTION:
⭐   ***IF THIS ACCOUNT WERE DELETED, COULD YOU REBUILD IT?***
⭐   ⇒ ⭐ If the answer needs your memory, you do not have
⭐     infrastructure — ⭐⭐ YOU HAVE A PET, and every future
⭐     change is a guess about what the console already contains.

⭐ ⭐ WHAT THIS BUYS THAT A README CANNOT:
⭐   ⭐ a diff before a change ⇒ ⭐⭐ `terraform plan` IS A CODE
⭐     REVIEW FOR PRODUCTION, and it is the only one you get
⭐   ⭐ drift detection — the console change someone made at
⭐     2 a.m. shows up as a plan diff
⭐   ⭐ an identical staging environment, which is what makes
⭐     Day 286's load numbers mean anything

⭐ ⭐ TWO PRACTICAL RULES:
⭐   ⭐ REMOTE STATE WITH LOCKING (S3 + DynamoDB, or the managed
⭐     backend). ⭐⭐ LOCAL STATE MEANS TWO APPLIES CAN RACE AND
⭐     CORRUPT IT, and state is not recoverable from the cloud.
⭐   ⭐⭐ STATE CONTAINS SECRETS IN PLAINTEXT — RDS passwords,
⭐     generated keys. ⭐ Encrypt the bucket, restrict it, and
⭐     never commit state to git.
```

# Part 3 — ⭐⭐ The network, which is the real security boundary

```
⭐⭐ THE SHAPE, AND EVERY LINE OF IT IS LOAD-BEARING:
⭐   ⭐ PUBLIC SUBNET   → the load balancer. Nothing else.
⭐   ⭐ PRIVATE SUBNET  → app tasks, workers
⭐   ⭐⭐ PRIVATE, NO INTERNET GATEWAY → Postgres, Redis
⭐   ⇒ ⭐⭐ THE DATABASE IS NOT REACHABLE FROM THE INTERNET, SO
⭐     A LEAKED PASSWORD IS NOT AN IMMEDIATE BREACH. ⭐ That is
⭐     the single highest-value line in this whole day.

⭐ ⭐ ACCESS FOR HUMANS: no bastion with an open SSH port —
⭐     ⭐⭐ SESSION MANAGER / IAM-AUTHENTICATED TUNNELS, which
⭐       are logged, revocable, and have no key to lose.

⭐ ⭐ SECURITY GROUPS ARE THE ACTUAL FIREWALL, and they should
⭐     REFERENCE EACH OTHER, not CIDRs:
⭐     ⭐ `db_sg` allows 5432 FROM `app_sg` — ⭐⭐ so scaling the
⭐       app changes nothing, and a new service must be granted
⭐       explicitly rather than inheriting a subnet range.
```

```
⭐⭐ AND THE ONE ALMOST NOBODY SETS — ***EGRESS***:
⭐   ⭐ Default: your app may connect to ANY host on the internet.
⭐   ⇒ ⭐⭐ WHICH IS WHAT TURNS AN SSRF OR A COMPROMISED
⭐     DEPENDENCY INTO EXFILTRATION. ⭐ The read of your database
⭐     is not the breach; ⭐⭐ THE OUTBOUND CONNECTION IS.
⭐   ⇒ ⭐ Restrict egress to what you actually call: the payment
⭐     provider, the object store (via a VPC endpoint), the mail
⭐     API. ⭐⭐ AND THE VPC ENDPOINT FOR S3 IS ALSO A COST FIX
⭐     (Part 6), so this is the rare control that pays for itself.
```

# Part 4 — ⭐⭐ What breaks when you lose one thing

> ⭐ Fill this in for **your** system, then **test the rows you can**. ⭐⭐ A row you have not
> tested is a prediction, and predictions in this table are wrong about a third of the time.

```
⭐⭐ | Lost            | Expected                     | Tested? |
⭐   | one API task    | LB removes it, no user impact| ⭐ yes  |
⭐   | one worker      | task redelivered once (D265) | ⭐ yes  |
⭐   | ⭐⭐ the scheduler | ⭐⭐ NOTHING RUNS. Silent.   | ⭐⭐ ?  |
⭐   | one AZ          | remaining AZs serve; RDS     |        |
⭐   |                 | fails over in 60–120 s       |        |
⭐   | the DB primary  | 60–120 s of write errors,    |        |
⭐   |                 | then recovery (D201)         |        |
⭐   | Redis           | cache misses (D266) — ⭐⭐ but |        |
⭐   |                 | if it is also your broker,   |        |
⭐   |                 | ⭐⭐ QUEUED WORK IS GONE      |        |
⭐   | object storage  | uploads fail; existing reads |        |
⭐   |                 | continue if signed (D267)    |        |

⭐⭐ THE TWO ROWS THAT USUALLY SURPRISE PEOPLE:
⭐   ⭐ THE SCHEDULER — it is a single instance BY DESIGN
⭐     (Day 264), so it is a single point of failure by design.
⭐     ⭐⭐ THAT IS ACCEPTABLE ***ONLY BECAUSE*** THE DEAD-MAN
⭐     ALERT EXISTS. Without it, you have an unmonitored SPOF.
⭐   ⭐ THE SHARED REDIS — the cache row and the broker row have
⭐     completely different severities, which is Day 265's
⭐     separate-instances rule arriving as an availability
⭐     argument rather than a configuration one.
```

# Part 5 — ⭐⭐ The database in production

```
⭐   ⭐ MANAGED, MULTI-AZ. ⭐⭐ Multi-AZ is not a read replica —
⭐     it is a synchronous standby for FAILOVER only. ⭐ You
⭐     cannot read from it, and people are surprised by that.
⭐   ⭐ Automated backups + PITR, and ⭐⭐ THE RETENTION WINDOW
⭐     IS A DECISION: 7 days means a corruption discovered on
⭐     day 8 is permanent (Day 200).
⭐   ⭐⭐ RESTORE ONCE, TIMED, AND WRITE THE NUMBER DOWN.
⭐     ⇒ ⭐⭐ AN UNTESTED BACKUP IS A BELIEF. And the number you
⭐       discover is your real RTO, which is usually 10× what
⭐       people assume — restoring 100 GB is not instant.
⭐   ⭐ Parameters from Day 202, not defaults.
⭐   ⭐ Connection limits: ⭐⭐ A `db.t4g.medium` GIVES YOU ABOUT
⭐     ***170*** CONNECTIONS. Your API pool × tasks + worker
⭐     concurrency (Day 265) will exceed that before you notice
⭐     ⇒ ⭐ PgBouncer in transaction mode, with Day 197's list
⭐       of the seven things it breaks stuck to the wall.
⭐   ⭐ Storage autoscaling ON — ⭐⭐ A FULL DISK IS A HARD STOP
⭐     WITH NO GRACEFUL DEGRADATION, and it is a completely
⭐     avoidable incident.
```

# Part 6 — ⭐⭐ Cost, as an engineering constraint

```
⭐⭐ THE THREE LINE ITEMS THAT SURPRISE EVERYONE:
⭐   ① ⭐⭐ THE NAT GATEWAY — ~$32/month PER AZ, plus per-GB
⭐     processing. ⭐ On a small project it is routinely the
⭐     LARGEST single item, and it exists so private tasks can
⭐     reach the internet.
⭐     ⇒ ⭐⭐ VPC ENDPOINTS FOR S3 AND ECR REMOVE MOST OF THE
⭐       TRAFFIC — the same control as Part 3's egress rule.
⭐   ② ⭐ LOGS — ingestion is charged per GB, and DEBUG logging
⭐     at 200 rps will out-cost your compute. Sample them.
⭐   ③ ⭐ IDLE ENVIRONMENTS — staging running 24/7 for a project
⭐     you touch at weekends. Schedule it down.

⭐⭐ AND THE REASON THIS IS ON A LEARNING ROADMAP AT ALL:
⭐   ***"IT COSTS ABOUT $70 A MONTH, AND HERE IS WHERE IT GOES"
⭐      IS AN ANSWER ALMOST NO CANDIDATE CAN GIVE.***
⭐   ⇒ ⭐ It proves you deployed it, kept it running, and looked
⭐     at the bill — which is three claims in one sentence.
⭐   ⭐ Tag every resource with the project so the bill is
⭐     itemised at all.
```

# Part 7 — ⭐ Environments and parity

```
⭐   ⭐ SAME IaC MODULES, different variables. ⭐⭐ NOT A SECOND
⭐     HAND-BUILT ENVIRONMENT — differences you did not intend
⭐     are exactly the ones that break the deploy.
⭐   ⭐⭐ STAGING NEEDS PRODUCTION-***SHAPED*** DATA VOLUMES.
⭐     ⇒ ⭐ 200 rows in staging means Day 281's query-count
⭐       ceilings and Day 286's load numbers measured nothing.
⭐     ⇒ ⭐⭐ ANONYMISED, NOT COPIED. A production dump in
⭐       staging is a data breach with extra steps: fewer
⭐       controls, more access, and it will be forgotten.
⭐   ⭐ A seed command that produces a realistic dataset in one
⭐     step, versioned with the code.
⭐   ⭐ Accept the differences you cannot afford (one AZ, smaller
⭐     instances) and ⭐⭐ WRITE THEM DOWN, so that when staging
⭐     behaves differently you look at the list instead of
⭐     debugging a ghost.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Building a platform for a project | You'll operate it instead of building, and still can't describe its failures. |
| Copying a big-company architecture | Sizing judgement is what seniority looks like. Choose small and defend it. |
| Running workers inside the API container | A traffic spike starves background work exactly when it matters. |
| Clicking infrastructure into existence | You have a pet. Every future change is a guess. |
| Local Terraform state | Two applies race and corrupt it, and it isn't recoverable. |
| Committing state to git | It contains database passwords in plaintext. |
| A publicly reachable database | A leaked password becomes an immediate breach. |
| A bastion with an open SSH port | Use IAM-authenticated sessions: logged, revocable, no key to lose. |
| Security groups referencing CIDRs | Reference other groups so scaling doesn't silently widen access. |
| Unrestricted egress | It's what turns an SSRF into exfiltration. The outbound connection is the breach. |
| An untested failure table | A third of your predictions are wrong. |
| An unmonitored single scheduler | A SPOF by design is fine *only* with the dead-man alert. |
| One Redis for cache and broker | Two rows in the failure table with completely different severities. |
| Expecting to read from a Multi-AZ standby | It's a failover target, not a replica. |
| An untested backup | A belief. Restore once, timed, and record your real RTO. |
| Ignoring instance connection limits | A `t4g.medium` gives ~170; your pools will exceed it. |
| Storage autoscaling off | A full disk is a hard stop with no degradation. |
| Not knowing what it costs | NAT gateways are routinely the biggest line item on small projects. |
| DEBUG logging at production rates | Log ingestion out-costs compute. |
| Staging with 200 rows | Your ceilings and load numbers measured nothing. |
| A production dump in staging | A data breach with fewer controls and more access. |

## Interview questions

**Q: Why not Kubernetes?**

> Because I didn't need what it costs to operate. The properties I have to demonstrate are rolling
> deploys, health checks, autoscaling, secrets management, private networking and a database failover
> — and a managed container platform gives me all of them while I spend my time on the application.
> I'd rather be able to describe my failure modes from memory than run a cluster I can't debug. If the
> constraints changed — multiple teams, custom scheduling, real multi-tenancy at the infrastructure
> layer — that's a different answer, and I can say what would move me.

**Q: Why is your infrastructure in code?**

> One question: if this account were deleted, could I rebuild it? If the answer needs my memory, I
> don't have infrastructure, I have a pet — and every future change is a guess about what the console
> already contains. Beyond that, `terraform plan` is the only code review production ever gets, drift
> from a 2 a.m. console change shows up as a diff, and staging is genuinely identical, which is what
> makes my load-test numbers mean anything.

**Q: What's your network layout?**

> Load balancer in the public subnet, app and workers private, database and Redis in a private subnet
> with no internet gateway — so the database isn't reachable from the internet and a leaked password
> isn't an immediate breach. Security groups reference each other rather than CIDR ranges, so scaling
> doesn't silently widen access. And the piece almost nobody sets is egress: by default my app can
> connect to any host on the internet, which is exactly what turns an SSRF or a compromised dependency
> into exfiltration. The read isn't the breach — the outbound connection is. Restricting it and adding
> a VPC endpoint for S3 also cuts the NAT bill, so it's one of the few controls that pays for itself.

**Q: What happens when you lose an availability zone?**

> Remaining tasks serve traffic and RDS fails over in roughly a minute to two, during which writes
> error and my retry logic matters. The two rows in that table that surprise people are the scheduler
> and Redis. The scheduler is a single instance by design, so it's a single point of failure by design
> — and that's acceptable only because there's a dead-man alert on it; without that it's an unmonitored
> SPOF. And Redis has two completely different severities depending on whether it's the cache or the
> broker, which is why they're separate instances.

**Q: What does it cost?**

> About seventy dollars a month, and I can break it down: the NAT gateway is the largest single item
> at around thirty per AZ plus per-gigabyte processing, then the database, then compute, then logs —
> and log ingestion will overtake compute if you leave DEBUG on at any real request rate. I added VPC
> endpoints for S3 and ECR to cut NAT traffic, and staging is scheduled down outside the hours I use
> it. Knowing that number is worth stating, because it proves I deployed it, kept it running, and
> actually looked at the bill.

## Today's build

1. ⭐⭐ Write down the smallest platform that demonstrates your six properties, and the sentence defending it.
2. ⭐ Split the five workloads into separate deployments from one image, with different commands and scaling rules.
3. ⭐⭐ Move everything into Terraform. Then destroy and recreate staging from scratch, timed.
4. ⭐ Move state to a remote backend with locking, encrypt it, and confirm it isn't in git.
5. ⭐⭐ Put the database in a subnet with no internet gateway and prove you cannot reach it from your laptop.
6. ⭐ Replace any bastion with IAM-authenticated session access.
7. ⭐⭐ Convert security group rules to reference groups rather than CIDRs.
8. ⭐⭐ Restrict egress to your known destinations. Then try to `curl` an arbitrary host from a task and confirm it fails.
9. ⭐ Add VPC endpoints for S3 and ECR, and compare NAT data-processing charges before and after.
10. ⭐⭐ Fill in the failure table for your system, then actually test at least four rows.
11. ⭐⭐ Trigger an RDS failover during a load test and record the exact error window.
12. ⭐⭐ Restore a backup to a new instance, timed. Write the number down as your RTO.
13. ⭐ Check your instance's connection limit against your total pool arithmetic. Add PgBouncer if it's close.
14. ⭐ Enable storage autoscaling and set a disk-usage alert well before the ceiling.
15. ⭐⭐ Tag everything, then read the bill and write the itemised breakdown into the README.
16. ⭐⭐ Build a seed command producing production-shaped volumes, and write down every intentional staging difference.

## 🎙️ Articulation drill

**Three minutes: "Where does it run?"**

Lead with the sizing judgement, because it is the answer: **choose the smallest infrastructure that
demonstrates the properties you need, and know its failure modes cold.** Say what those properties are
— rolling deploys, health checks, autoscaling, secrets, private networking, database failover — and
that a managed platform gives you all of them, so **"I didn't need what Kubernetes costs to operate"
is a stronger answer than a cluster you can't debug.** Then infrastructure as code, justified by one
question: if the account were deleted, could you rebuild it? If the answer needs your memory, it's a
pet — and `terraform plan` is the only code review production ever gets. Then the network, which is
where the security actually lives: **the database has no internet gateway, so a leaked password isn't
an immediate breach**, security groups reference each other, and the piece almost nobody sets is
egress — **unrestricted outbound is what turns an SSRF into exfiltration, because the read isn't the
breach, the outbound connection is.** Then the failure table, and pick the two rows that surprise
people: **the scheduler is a single point of failure by design, which is acceptable only because the
dead-man alert exists**, and Redis has two different severities depending on whether it's a cache or a
broker. Close with the two things almost nobody has: **a restore you actually timed, because an
untested backup is a belief**, and an itemised monthly cost — which proves in one sentence that you
deployed it, kept it running, and read the bill.
