# Part 1 — ⭐⭐ Review your own design as an adversary

```
⭐⭐ THE PROBLEM: YOU CANNOT REVIEW YOUR OWN DESIGN IN THE SAME FRAME OF
⭐   MIND THAT PRODUCED IT. So change the frame deliberately — put on a
⭐   role and ask that role's questions, out loud, in writing.

⭐ ① ⭐⭐ THE HOSTILE REVIEWER — "why is that not simpler?"
⭐    ⭐ Which entity could be deleted entirely? ⭐ Which endpoint exists
⭐      because it seemed symmetric rather than because someone needs it?
⭐    ⭐⭐ Which abstraction has exactly one implementation and always
⭐      will? (Day 139: a repository over one ORM is often ceremony.)
⭐ ② ⭐⭐ THE OPERATOR — "it is 3 a.m. and this is broken."
⭐    ⭐ How do I know which tenant is affected? ⭐ Which single query
⭐      tells me whether the outbox is draining? ⭐⭐ What is the
⭐      manual, safe way to retry one failed payment?
⭐ ③ ⭐⭐ THE ATTACKER — Part 2.
⭐ ④ ⭐ THE FUTURE MAINTAINER — "why is this like this?"
⭐    ⭐⭐ Every answer that is "I don't remember" is a missing ADR.
⭐ ⑤ ⭐⭐ THE PRODUCT OWNER — "can we add X?"
⭐    ⭐ Pick the most likely next feature (for `fieldwork`: recurring
⭐      jobs). ⭐⭐ Does your schema make it possible, hard, or
⭐      catastrophic? ⭐ You are not building it. You are checking you
⭐      did not accidentally forbid it.
```

```
⭐⭐ THE SIX QUESTIONS TO ANSWER IN WRITING TODAY:
⭐   ① What is the single most likely thing to go wrong in production,
⭐      and what will I see when it does?
⭐   ② ⭐⭐ Which decision would be most expensive to reverse in three
⭐      weeks? ⭐ Am I more confident in it than that cost warrants?
⭐   ③ What am I building because it is interesting rather than needed?
⭐   ④ ⭐⭐ Where is the tenant boundary enforced, and what happens if
⭐      exactly one query forgets? ⭐ If the answer is "a data leak",
⭐      the enforcement level is wrong (Part 3).
⭐   ⑤ Which endpoint will be slowest at 50k jobs, and why do I think so?
⭐   ⑥ ⭐⭐ If I had to cut 30% of scope on day 270, what goes — and can
⭐      I cut it cleanly, or is it entangled?
```

# Part 2 — ⭐⭐ The threat model, as a grid

```
⭐⭐ NOT "WE'LL USE HTTPS AND HASH PASSWORDS". A GRID: ACTOR × ASSET ×
⭐   WHAT THEY MIGHT TRY × WHAT STOPS IT × HOW IT IS PROVED.

⭐ | ACTOR        | TRIES TO                  | STOPPED BY      | PROVED |
⭐ | anon         | read any job              | auth dependency | test   |
⭐ | ⭐⭐ tenant A  | read tenant B's job by id | ⭐⭐ RLS + tenant | ⭐⭐ a  |
⭐ |   user       |                           | in WHERE ⇒ 404  | test   |
⭐ |              |                           |                 | FILE   |
⭐ | technician   | list all tenant jobs      | row filter in   | test   |
⭐ |              |                           | the LIST query  |        |
⭐ | technician   | complete an unassigned job| ⭐ command perm  | test   |
⭐ | ⭐⭐ customer  | change the signed link's  | ⭐⭐ signed token | test   |
⭐ |   (link)     | job id                    | binds the id    |        |
⭐ | any user     | escalate their own role   | role changes    | test   |
⭐ |              |                           | owner-only      |        |
⭐ | attacker     | brute-force login         | ⭐ per-account +  | test   |
⭐ |              |                           | per-IP limit,   |        |
⭐ |              |                           | ⭐⭐ FAIL CLOSED  |        |
⭐ | attacker     | enumerate valid emails    | ⭐⭐ identical    | test   |
⭐ |              | via reset/login timing    | response + time |        |
⭐ | attacker     | upload a 5 GB "photo"     | ⭐ presigned +   | test   |
⭐ |              | or an SVG with script     | type + size +   |        |
⭐ |              |                           | ⭐⭐ served from  |        |
⭐ |              |                           | a separate      |        |
⭐ |              |                           | origin          |        |
⭐ | ⭐⭐ attacker  | make the server fetch an  | ⭐⭐ SSRF: no     | test   |
⭐ |              | internal URL (webhooks,   | user-supplied   |        |
⭐ |              | image import)             | URLs fetched    |        |
⭐ | ⭐ insider    | read the audit trail out  | ⭐ append-only,  | review |
⭐ |              | of the DB                 | separate perms  |        |

⭐ ⇒ ⭐⭐ EVERY ROW IN THE "PROVED" COLUMN THAT SAYS "test" BECOMES A
⭐   TEST FUNCTION ON DAY 259, IN ***ONE FILE***, NAMED SO THAT ITS
⭐   ABSENCE IS OBVIOUS: `test_authorization_matrix.py`. ⭐ Day 165's
```

```
⭐⭐ AND THE THREE THAT ARE ALWAYS MISSED IN A PROJECT THIS SHAPE:
⭐   ① ⭐⭐ THE BACKGROUND JOB HAS NO USER, SO IT HAS NO TENANT FILTER.
⭐      ⭐ A worker that iterates "all jobs" is the one place your
⭐      tenant isolation does not apply — ⭐⭐ and it is where a bug
⭐      writes tenant A's data onto tenant B. ⭐ Decide today: workers
⭐      set the tenant explicitly per unit of work, with `SET LOCAL`.
⭐   ② ⭐⭐ THE REPORTING QUERY IS WRITTEN BY HAND AND BYPASSES THE ORM,
⭐      SO IT BYPASSES YOUR FILTER. ⭐ Day 269 is the day this bites.
⭐   ③ ⭐ THE SIGNED CUSTOMER LINK IS A BEARER TOKEN IN A URL — it lands
⭐      in logs, referrers and browser history. ⭐⭐ Short expiry, one
⭐      job, no write scope beyond acknowledging.
```

# Part 3 — ⭐⭐ Two decisions to make explicitly today

```
⭐⭐ ① THE TENANT ENFORCEMENT LEVEL (Day 160's four levels):
⭐   L1 ⭐ "every query includes tenant_id"  → ⭐⭐ one omission = a leak
⭐   L2 ⭐ a base repository/query helper    → ⭐ one bypass = a leak
⭐   L3 ⭐ a session-scoped default filter   → ⭐ raw SQL bypasses it
⭐   L4 ⭐⭐ POSTGRES ROW-LEVEL SECURITY      → ⭐⭐ NOTHING BYPASSES IT
⭐
⭐   ⭐⭐ CHOOSE L4, AND KNOW ITS TWO SILENT FAILURES (Day 160):
⭐     ⭐ RLS DOES NOT APPLY TO THE TABLE OWNER OR A SUPERUSER — so the
⭐       application must connect as a NON-OWNER role, or your policies
⭐       are decorative and every test passes.
⭐     ⭐⭐ `SET app.tenant_id` MUST BE `SET LOCAL` INSIDE THE
⭐       TRANSACTION — plain `SET` on a pooled connection leaks the
⭐       tenant to the next request (Day 197). ⭐⭐ THAT IS A
⭐       CROSS-TENANT DATA EXPOSURE CAUSED BY A CONNECTION POOL.
⭐   ⇒ ⭐ Write both facts into ADR-0004 so the next person cannot
⭐     undo them by accident.

⭐⭐ ② THE CAPACITY ESTIMATE — so "it doesn't scale" has a definition:
⭐   ⭐ 200 tenants · peak 40 concurrent dispatchers at 09:00
⭐   ⭐ ~6 requests per dispatcher-minute ⇒ ⭐ 4 rps sustained, say 40
⭐     rps peak with a 10× safety factor
⭐   ⭐⭐ LITTLE'S LAW (Day 156): 40 rps × 150 ms = ⭐⭐ 6 CONCURRENT
⭐     REQUESTS IN FLIGHT. ⭐ That is the whole system.
⭐   ⇒ ⭐⭐ SO: 2 app instances × 4 workers is generous, and the pool is
⭐     ~5 per worker, giving 40 connections — comfortably under
⭐     `max_connections` (Day 197). ⭐⭐ AND THE HONEST CONCLUSION: at
⭐     this scale NOTHING NEEDS SHARDING, CACHING OR A QUEUE FOR
⭐     THROUGHPUT REASONS. ⭐ Everything you build for those reasons,
⭐     you are building to LEARN, and saying so is more impressive than
⭐     pretending it was necessary.
⭐   ⭐ DATA: 50k jobs/year × 200 tenants ⇒ 10M jobs in year one, ~4 KB
⭐     each ⇒ ⭐ 40 GB. ⭐⭐ One Postgres instance. No partitioning
⭐     (Day 200's threshold), and knowing WHY you are not partitioning
⭐     is worth more than partitioning.
```

# Part 4 — ⭐ Five ADRs, each with a number in it

```
⭐⭐ AN ADR WITHOUT A NUMBER, A REJECTED ALTERNATIVE AND A CONSEQUENCE
⭐   IS A DIARY ENTRY. THE FORMAT:
⭐     CONTEXT (what forced a decision) · DECISION · ⭐⭐ ALTERNATIVES
⭐     CONSIDERED AND WHY REJECTED · CONSEQUENCES (including the bad
⭐     ones) · ⭐ A NUMBER

⭐   ADR-0001 ⭐ why this project (Day 248)
⭐   ADR-0002 ⭐ aggregate boundaries (Day 250)
⭐   ADR-0003 ⭐⭐ the overlap rule is an EXCLUDE constraint, not service
⭐              code — ⭐ rejected: advisory lock (serialises the whole
⭐              technician), SELECT-then-INSERT (a race), SERIALIZABLE
⭐              (needs a retry loop everywhere for one rule).
⭐              ⭐ CONSEQUENCE: requires `btree_gist`; the error surfaces
⭐              as an `IntegrityError` we must map to 409.
⭐   ADR-0004 ⭐⭐ tenant isolation via RLS at level 4 — ⭐ rejected:
⭐              schema-per-tenant (200 migrations), database-per-tenant
⭐              (200 connection pools). ⭐⭐ CONSEQUENCE: the app must
⭐              connect as a non-owner role, and every request must
⭐              `SET LOCAL` — both of which are load-bearing and easy to
⭐              undo accidentally.
⭐   ADR-0005 ⭐ cursor pagination with no total count — ⭐ rejected:
⭐              offset (linear cost, Day 193), exact count (a scan per
⭐              request). ⭐ CONSEQUENCE: no "jump to page N"; the UI
⭐              must be built for it, which is a Stage 6 constraint you
⭐              are imposing today.

⭐ ⭐⭐ THE TEST OF A GOOD ADR: SIX MONTHS LATER, SOMEONE WHO DISAGREES
⭐   WITH YOU SHOULD BE ABLE TO READ IT AND SAY "I SEE WHY YOU DID
⭐   THAT" — even while still disagreeing.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Reviewing your own design in the same frame that produced it | Adopt roles deliberately and write down each one's questions. |
| A threat model as prose about HTTPS and hashing | A grid: actor × attempt × control × proof. |
| Forgetting the background worker has no user | It's the one place tenant isolation doesn't apply by default. |
| Forgetting hand-written reporting SQL bypasses your filter | That's where the isolation you tested doesn't hold. |
| Choosing tenant isolation implicitly | Pick a level and write down its failure modes. |
| RLS with the app connecting as the table owner | Policies are silently skipped and every test passes. |
| Plain `SET app.tenant_id` on a pooled connection | The tenant leaks to the next request — cross-tenant exposure. |
| Skipping the capacity estimate | Then "it doesn't scale" has no definition and neither does "enough". |
| Pretending infrastructure was needed for throughput | At 40 rps it wasn't. Saying you built it to learn is stronger. |
| ADRs with no rejected alternatives | A diary entry, not a decision record. |
| ADRs with no stated bad consequences | Nobody believes a decision with only upsides. |
| Passing the gate on "I probably would" | The value of a gate is entirely in its refusal. |
| Not saying the design out loud | "And then somehow" is an unfinished decision, and you won't find it silently. |

## Interview questions

**Q: How do you review your own design?**

> By changing frame deliberately, because you can't review a design in the mind that produced it. I
> use five roles with their own questions: a hostile reviewer asking what could be deleted and which
> abstraction has exactly one implementation; an operator asking how they'd know which tenant is
> affected at three in the morning and what the safe manual retry is; an attacker, which is the threat
> model; a future maintainer, where every "I don't remember why" is a missing ADR; and a product owner
> asking whether the most likely next feature is possible, hard or catastrophic — not to build it, but
> to check I haven't accidentally forbidden it. Then six written questions, of which the sharpest is
> "which decision would be most expensive to reverse in three weeks, and am I more confident in it
> than that cost warrants?"

**Q: What's in your threat model?**

> A grid — actor, what they'd try, what stops it, and how that's proved — because prose about HTTPS
> and password hashing isn't a threat model. Rows include a tenant reading another tenant's record by
> id, a technician listing jobs they aren't assigned to, a customer editing the job id in their signed
> link, brute-forcing login, enumerating emails through reset timing, uploading an SVG with script,
> and making the server fetch an internal URL. The proof column is the important one: every row that
> says "test" becomes a function in a single file named so its absence is obvious. And I'd call out
> the three that are always missed in this shape of system — the background worker has no user and
> therefore no tenant filter by default, hand-written reporting SQL bypasses whatever filter the ORM
> applies, and a signed link is a bearer token in a URL that ends up in logs, referrers and history.

**Q: How do you enforce multi-tenancy?**

> Postgres row-level security, and I'd explain why rather than just naming it. There are four levels:
> remembering the filter in every query, a shared base query helper, a session-scoped default filter,
> and RLS. The first three all have the property that one omission or one piece of raw SQL is a
> cross-tenant leak, and in a codebase with reporting queries there will be raw SQL. RLS is the only
> level where nothing bypasses it — but it has two silent failure modes I'd write into an ADR because
> both are easy to undo by accident. It doesn't apply to the table owner or a superuser, so the
> application must connect as a non-owner role or the policies are decorative and every test still
> passes. And the tenant must be set with `SET LOCAL` inside the transaction, because a plain `SET` on
> a pooled connection persists onto whoever gets that connection next — which is cross-tenant data
> exposure caused by a connection pool.

**Q: What did your capacity estimate tell you?**

> That almost none of the infrastructure was needed for throughput, which I think is the more
> impressive thing to be able to say. Peak is forty concurrent dispatchers on a weekday morning, about
> forty requests a second with a generous safety factor, and Little's Law at a hundred and fifty
> milliseconds gives six concurrent requests in flight for the entire system. Two instances with four
> workers is comfortable, the connection count is around forty, and the data is roughly forty gigabytes
> in year one — one Postgres instance, well under the partitioning threshold. So the caching, the
> queue and the read models exist because I wanted to build and measure them, not because the load
> required them. Being explicit about that is better than implying necessity, because an interviewer
> who does the arithmetic will get there anyway, and knowing *why you aren't* partitioning is worth
> more than partitioning.

**Q: Why gate before writing code?**

> Because today is the last day changing my mind is free. Every decision on the list — the aggregate
> boundaries, the tenant enforcement level, the pagination style, the error shape — is an afternoon
> now and a migration plus a client-breaking change in three weeks. The gate's value is entirely in
> its refusal, so "mostly done" fails it; if I let myself pass on the basis that I probably would have
> got it right, I've just replaced a design review with optimism. The item I'd defend hardest is the
> non-document one: say the whole design out loud in ten minutes, because every place you find yourself
> saying "and then somehow" is an unfinished decision, and you will not find those silently.

## 🎙️ Articulation drill

**Ten minutes: present the whole design, out loud, to someone who will ask questions.**

Two minutes on the problem and the actors. Two on the domain: the aggregates, the state machine, and
**the invariant that fits in no aggregate and therefore lives in a constraint.** Two on the API: the
error shape, transitions as commands, and cursor pagination with the consequence you're imposing on
the UI. Two on security: the tenant enforcement level, its two traps, and the fact that the threat
model is a test file. Two on capacity: the arithmetic, ending in six concurrent requests — and the
honest sentence about what you're building to learn rather than because the load requires it.

Then write down every place you said **"and then somehow"**. Those are your unfinished decisions, and
they are the only reason to have done this out loud rather than on paper.
