# Part 1 — ⭐⭐ The hierarchy

```
⭐ BaseException
⭐  ├── ⭐⭐ SystemExit          — sys.exit()
⭐  ├── ⭐⭐ KeyboardInterrupt   — Ctrl-C
⭐  ├── GeneratorExit           — Day 047
⭐  └── ⭐⭐ Exception           ← ⭐⭐ EVERYTHING YOU SHOULD EVER CATCH
⭐       ├── ArithmeticError ── ZeroDivisionError, OverflowError
⭐       ├── LookupError ────── KeyError, IndexError
⭐       ├── OSError ────────── FileNotFoundError, PermissionError, ⭐ ConnectionError, TimeoutError
⭐       ├── ValueError ─────── UnicodeDecodeError (Day 037)
⭐       ├── TypeError, AttributeError, NameError
⭐       ├── RuntimeError ───── RecursionError
⭐       └── StopIteration (Day 046), StopAsyncIteration
```

```
⭐⭐ WHY THE SPLIT AT BaseException — this is the design, and it is a good one:
⭐   `except Exception:` does NOT catch Ctrl-C or sys.exit().
⭐   ⇒ ⭐⭐ so a retry loop wrapping `except Exception` stays interruptible, and a broad
⭐        handler cannot accidentally prevent your process from shutting down.
⭐   ⇒ ⭐⭐ THEREFORE: never write `except BaseException` or a bare `except:` — a bare
⭐        except catches BaseException, so Ctrl-C enters your handler and is swallowed.
```

⭐ **Picking the right built-in matters more than people think** — it is the first thing a reader
sees:

| ⭐ Situation | ⭐ Raise |
|---|---|
| Wrong **type** | `TypeError` |
| Right type, ⭐ **wrong value** | ⭐ `ValueError` |
| Missing dict key / index | `KeyError` / `IndexError` |
| ⭐ Not implemented **in this subclass** | ⭐ `NotImplementedError` |
| ⭐ Operation invalid **for the current state** | ⭐⭐ `RuntimeError`, or your own |
| Anything I/O, network, filesystem | `OSError` and its subclasses |

⚠️ ⭐ **`NotImplemented` (a value, Day 031) is not `NotImplementedError` (an exception).** Returning
the first from `__add__` lets Python try the reflected operation; raising the second says "a subclass
must implement this".

# Part 2 — ⭐⭐ Chaining: `raise ... from`

```python
try:
    row = db.fetch(user_id)
except psycopg.OperationalError as e:
    raise UserLookupFailed(user_id) from e     # ⭐⭐ EXPLICIT chaining
```

```
⭐⭐ THREE BEHAVIOURS, AND THE DIFFERENCE IS VISIBLE IN THE TRACEBACK:

⭐   raise New() from e     ⇒ __cause__ = e
⭐                            ⇒ ⭐ "The above exception was the DIRECT CAUSE of the following"
⭐   raise New()            ⇒ ⭐ __context__ = e, set AUTOMATICALLY inside an except block
⭐                            ⇒ "During handling of the above exception, ANOTHER occurred"
⭐   ⭐ raise New() from None ⇒ ⭐⭐ SUPPRESSES the chain entirely
⭐
⭐ ⇒ ⭐⭐ `from e` is the one you want when TRANSLATING an exception across a layer boundary:
⭐      the caller sees your domain error, and the traceback still holds the driver error
⭐      that actually caused it. Losing that is losing the only evidence you had.
```

⚠️ ⭐⭐ **`from None` is for one specific case: when the underlying error is noise that would mislead.**
A `KeyError` inside a config loader, re-raised as `ConfigMissing("DATABASE_URL")`, is clearer without
it. **Using `from None` to hide a real cause is destroying evidence.**

```python
# ⭐ Bare `raise` re-raises the CURRENT exception with its ORIGINAL traceback:
try:
    work()
except Exception:
    logger.exception("work failed")     # ⭐⭐ logs the full traceback
    raise                               # ⭐⭐ bare — NOT `raise e`, which resets nothing but reads worse

# ⭐ 3.11+: add context without wrapping
except ValueError as e:
    e.add_note(f"while parsing row {i}")
    raise
```

# Part 3 — ⭐ Custom exceptions

```python
# ⭐⭐ ONE BASE PER PACKAGE — so callers can catch everything from you, or nothing:
class BillingError(Exception):
    """Base for all billing errors."""

class InsufficientFunds(BillingError):
    def __init__(self, account_id: str, required: Decimal, available: Decimal):
        self.account_id = account_id            # ⭐⭐ CARRY THE DATA as attributes
        self.required = required
        self.available = available
        super().__init__(f"account {account_id}: need {required}, have {available}")

class PaymentDeclined(BillingError):
    def __init__(self, code: str):
        self.code = code                        # ⭐ so the caller can branch on code without parsing
        super().__init__(f"declined: {code}")
```

```
⭐⭐ THE THREE RULES:
⭐   1. ⭐ ONE base class per package/module ⇒ `except BillingError` is a meaningful boundary
⭐   2. ⭐⭐ CARRY STRUCTURED DATA on the exception — never make the caller parse the message
⭐   3. ⭐ still call super().__init__(message) so str(e) is useful and the repr is readable
⭐
⭐ ⚠️ ⭐ AND THE ANTI-RULE: do not build a forty-class hierarchy up front. Add one when a
⭐   caller genuinely needs to distinguish it. Exceptions are an API — every class you add
⭐   is one someone may start catching.
```

⭐⭐ **Rule 2 is the one people skip and regret:** `except PaymentDeclined as e: if "insufficient" in
str(e)` is a caller parsing your English. **An attribute is a contract; a message is not.**

⭐ **Inherit from a specific built-in when it genuinely is one** — `class ConfigError(ValueError)`
means existing `except ValueError` handlers still work. ⚠️ **But do not do it for convenience: it
makes your error catchable by handlers that were not thinking about you.**

# Part 4 — ⭐ `try/except/else/finally` and exception groups

```python
try:
    conn = connect()          # ⭐⭐ keep the try SMALL — only what can raise what you handle
except ConnectionError as e:
    raise ServiceUnavailable() from e
else:
    use(conn)                 # ⭐⭐ runs ONLY if no exception — keeps it OUT of the try
finally:
    cleanup()                 # ⭐ always
```

```
⭐⭐ WHY `else` EXISTS: it narrows the `try`. If `use(conn)` were inside the try and it
⭐   happened to raise ConnectionError, you would catch and mistranslate an error from
⭐   the wrong operation. ⇒ ⭐ the try block should contain the smallest thing that can fail.
```

⚠️ ⭐⭐ **`return` or `break` inside `finally` discards the in-flight exception**, silently:

```python
def f():
    try:
        raise ValueError("real problem")
    finally:
        return "fine"        # ⭐⭐ the ValueError VANISHES. f() returns "fine".
```

⭐ **Python 3.14 makes this a syntax warning**; until then it is a genuine trap. **Never `return`
from `finally`.**

```python
# ⭐ Exception groups (3.11+) — for CONCURRENT failures, where several things fail at once:
async with asyncio.TaskGroup() as tg:          # ⭐⭐ Day 071
    tg.create_task(a()); tg.create_task(b())
# ⇒ if both fail: ExceptionGroup with BOTH — not just the first

try:
    ...
except* ValueError as eg:      # ⭐⭐ `except*` handles the MATCHING subset of the group
    for e in eg.exceptions: ...
except* TypeError as eg:       # ⭐ this can ALSO run — both branches may fire
    ...
```

⭐⭐ **Exception groups exist because concurrency broke the old model:** with one call stack, one
exception is enough. **With five parallel tasks, three can fail for different reasons, and reporting
only the first loses the other two.** ⭐ You will meet this in Day 071's `TaskGroup`.

⭐ **Performance:** a `try` that does not raise is essentially free (zero-cost in 3.11+), which is
the mechanical basis of EAFP (Day 023). ⚠️ **Raising is expensive** — building the traceback costs
real time — **so exceptions are for exceptional paths, not for a loop's control flow.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Bare `except:`** | ⭐⭐ Catches `BaseException` — swallows Ctrl-C and `SystemExit`. |
| `except Exception` where a specific class fits | ⭐ Say what you can handle. |
| ⭐⭐ **Re-raising without `from`** | ⭐⭐ The traceback keeps the context, but the causal link is implicit. |
| ⭐ `from None` to hide a real cause | ⭐⭐ You destroyed the evidence. |
| Messages instead of attributes | ⭐⭐ Callers end up parsing your English. |
| A forty-class exception hierarchy | ⭐ Add one when a caller must distinguish it. |
| ⭐⭐ **`return` in `finally`** | ⭐⭐ Silently discards the in-flight exception. |
| A large `try` block | ⭐ Use `else`; the try holds only what can fail. |
| `raise e` instead of bare `raise` | ⭐ Bare `raise` is the idiom. |
| Exceptions for ordinary control flow | ⭐ Raising is expensive; `try` is not. |
| Ignoring failures after the first, concurrently | ⭐⭐ `ExceptionGroup` and `except*`. |

## Interview questions

**Q: Why does `except Exception` not catch `KeyboardInterrupt`?**
> Because `KeyboardInterrupt`, `SystemExit` and `GeneratorExit` inherit from `BaseException`, not from
> `Exception`. That split is deliberate: it means a broad handler — a retry loop, a worker's
> catch-all — stays interruptible and can't accidentally prevent the process from shutting down. It's
> also why a bare `except:` is wrong rather than merely lazy: bare except catches `BaseException`, so
> Ctrl-C enters your handler and gets swallowed.

**Q: What does `raise ... from` do?**
> Sets `__cause__`, which makes the causal link explicit in the traceback — "the above exception was
> the direct cause of the following". Without it, raising inside an `except` block still records the
> original as `__context__`, so the information isn't lost, but the relationship is implicit. I use
> `from e` whenever I translate an exception across a layer boundary: the caller sees my domain error,
> and the traceback still holds the driver error that actually caused it. `from None` suppresses the
> chain, which is right when the underlying error is misleading noise and wrong whenever it's the
> evidence.

**Q: How do you design a custom exception?**
> One base class per package, so callers can catch everything from my library or nothing. Structured
> data as attributes — the account id, the required amount, the decline code — because the alternative
> is the caller doing `if "insufficient" in str(e)`, which means parsing my English and breaking when I
> reword it. And I'd still pass a readable message to `super().__init__` so `str(e)` and the log line
> are useful. What I wouldn't do is design forty classes up front; each one is public API that someone
> may start catching, so I add one when a caller genuinely needs to distinguish it.

**Q: What's `else` on a `try` for?**
> Narrowing the `try` block. Code that runs only on success goes in `else` rather than inside the
> `try`, so an exception raised by *that* code isn't caught by a handler intended for the risky
> operation. Without it, a `ConnectionError` from using the connection would be caught and translated
> as though the connection failed — a wrong error, from the wrong operation, and very hard to spot.

**Q: What are exception groups for?**
> Concurrency. With one call stack, one exception is enough — but with five parallel tasks, three can
> fail for different reasons, and reporting only the first loses the rest. `ExceptionGroup` carries all
> of them, and `except*` handles the matching subset, so more than one handler can fire for the same
> group. It's what `asyncio.TaskGroup` raises, and it exists because structured concurrency needed an
> error model that the old one couldn't express.

**Q: Are exceptions expensive?**
> Setting up a `try` is essentially free — zero-cost in 3.11 and later, so the happy path pays nothing,
> which is the mechanical justification for EAFP. Actually raising is expensive, mostly from building
> the traceback. So exceptions belong on exceptional paths; using them as a loop's control flow is a
> real performance problem as well as a readability one.

## 🎙️ Articulation drill

Record two minutes: **"Design the exceptions for a payments module."**

⭐ Start with the shape: **one base — `BillingError` — so a caller can catch everything from this
module or nothing**, then a small number of specific subclasses added because a caller genuinely needs
to distinguish them: `InsufficientFunds`, `PaymentDeclined`, `ProviderUnavailable`.

⭐⭐ **Then the rule that matters most:** *"each one carries structured data as attributes — the
account id, the amounts, the decline code — because the alternative is the caller writing `if
'insufficient' in str(e)`, and that means my error message is now an API I can never reword. An
attribute is a contract; a message is documentation."*

⭐ Then translation across the boundary: **the driver's `OperationalError` becomes
`ProviderUnavailable` with `raise ... from e`, so the caller sees a domain error and the traceback
still holds the driver error that actually caused it.** ⭐⭐ **And the mapping to HTTP happens once, at
the edge: `InsufficientFunds` is a 409, `PaymentDeclined` is a 402, `ProviderUnavailable` is a 503 —
so the domain never imports anything web-shaped, and there is exactly one place that decides what the
outside world sees.**
