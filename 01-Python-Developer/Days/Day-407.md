> ⭐⭐ **The sentence to own: you cannot atomically write to your database and publish to a broker — and

# Part 1 — The dual-write problem, in four lines

```python
db.session.commit()          # ⭐ ① the state changed
broker.publish(event)        # ⭐⭐ ② CRASH HERE
```

```
⭐⭐ ⇒ THE ORDER WAS PLACED AND NOBODY WILL EVER BE TOLD.
⭐   ⭐ No email, no warehouse pick, no analytics row.
⭐   ⭐⭐ AND NOTHING ANYWHERE LOGS AN ERROR — ⭐ the transaction
⭐     committed successfully and the process died afterwards.

⭐ NOW REVERSE IT:
⭐   ⭐ `broker.publish(event)` then `db.commit()` — ⭐⭐ CRASH
⭐     BETWEEN, AND YOU HAVE PUBLISHED `OrderPlaced` FOR AN ORDER
⭐     THAT DOES NOT EXIST. ⭐ Downstream services act on a fact
⭐     that never happened, ⭐⭐ WHICH IS STRICTLY WORSE.

⭐⭐ ⇒ ***THERE IS NO ORDERING THAT WORKS.*** ⭐ And the obvious
⭐   escape — a distributed transaction across the database and
⭐   the broker — is not available: ⭐⭐ 2PC IS BLOCKING (DAY 341),
⭐   MOST BROKERS DO NOT SUPPORT XA, AND THE ONES THAT DO MAKE
⭐   YOUR AVAILABILITY THE ***PRODUCT*** OF BOTH SYSTEMS'
⭐   AVAILABILITY (DAY 399).

⭐⭐ ⇒ AND RETRYING THE PUBLISH IN A `finally` DOES NOT FIX IT
⭐   EITHER, ⭐ because the process can die during the retry.
⭐   ⭐⭐ ANY IN-MEMORY SOLUTION FAILS TO THE SAME CRASH. ⭐ The
⭐   fix must be ***durable***, ⭐⭐ AND THE ONLY DURABLE THING YOU
⭐   ALREADY HAVE IS THE DATABASE TRANSACTION.
```

# Part 2 — ⭐⭐ The outbox

```
⭐⭐ ***WRITE THE EVENT TO AN `outbox` TABLE ***IN THE SAME
⭐   TRANSACTION*** AS THE STATE CHANGE. A SEPARATE RELAY READS
⭐   THE TABLE AND PUBLISHES.***

⭐   BEGIN;
⭐     INSERT INTO orders ...;
⭐     INSERT INTO outbox (aggregate_id, type, payload, ...);
⭐   COMMIT;                    ⭐⭐ ← ATOMIC. BOTH OR NEITHER.

⭐⭐ ⇒ AND THAT IS THE WHOLE IDEA: ***THE ATOMICITY CAME FREE
⭐   FROM A TRANSACTION YOU ALREADY HAD.*** ⭐ You did not add a
⭐   coordinator, a protocol, or a new failure mode. ⭐⭐ YOU MOVED
⭐   THE PROBLEM INTO THE ONE PLACE THAT ALREADY SOLVES IT.

⭐ WHAT THE RELAY GUARANTEES, PRECISELY:
⭐   ⭐⭐ ***AT-LEAST-ONCE.*** ⭐ It publishes, then marks the row
⭐     done. ⭐ Crash between → ⭐⭐ IT PUBLISHES AGAIN ON RESTART.
⭐   ⭐⭐ ⇒ SO ***CONSUMERS MUST BE IDEMPOTENT.*** ⭐ Always. ⭐ There
⭐     is no configuration that removes this (Day 335), ⭐⭐ AND
⭐     ANY DESIGN THAT ASSUMES OTHERWISE IS BROKEN AND HAS NOT
⭐     NOTICED YET.
```

```sql
CREATE TABLE outbox (
  id             bigserial PRIMARY KEY,
  aggregate_id   uuid        NOT NULL,     -- ⭐⭐ THE ORDERING KEY
  event_type     text        NOT NULL,
  payload        jsonb       NOT NULL,
  trace_id       text,                     -- ⭐⭐ DAY 376's
                                           -- ⭐   FORGOTTEN HOP
  created_at     timestamptz NOT NULL DEFAULT now(),
  published_at   timestamptz                -- ⭐ NULL = pending
);
CREATE INDEX ON outbox (id) WHERE published_at IS NULL;
-- ⭐⭐ PARTIAL INDEX: THE POLLING QUERY STAYS FAST FOREVER EVEN
-- ⭐   WITH A HUNDRED MILLION PUBLISHED ROWS.
```

# Part 3 — ⭐⭐ The gap bug: the subtle failure nobody warns you about

```
⭐ THE NAIVE RELAY: ⭐ `SELECT ... WHERE id > :last_seen ORDER BY id`
⭐   ⭐ then remember the highest id you saw.

⭐⭐ AND HERE IS WHY THAT ***SILENTLY SKIPS ROWS***:
⭐ ① ⭐ Transaction A takes sequence value ***5***. ⭐ (Sequences
⭐    hand out numbers ***outside*** the transaction, at INSERT
⭐    time.)
⭐ ② ⭐ Transaction B takes sequence value ***6***.
⭐ ③ ⭐⭐ B COMMITS FIRST. ⭐ A is still running — a slow query, a
⭐    lock wait, a busy worker.
⭐ ④ ⭐ The relay polls, sees id 6, publishes it, ⭐⭐ AND STORES
⭐    `last_seen = 6`.
⭐ ⑤ ⭐ A commits. ⭐ Row 5 becomes visible.
⭐ ⑥ ⭐⭐ THE RELAY NEXT ASKS FOR `id > 6`. ***ROW 5 IS NEVER
⭐    PUBLISHED.*** ⭐ Ever. ⭐⭐ NO ERROR, NO GAP DETECTED, NO
⭐    ALARM.

⭐⭐ ⇒ THIS IS A REAL, COMMON, PRODUCTION DATA-LOSS BUG IN
⭐   HAND-ROLLED OUTBOXES, ⭐ and it only appears under
⭐   concurrency, ⭐⭐ SO IT NEVER SHOWS UP IN TESTING.

⭐⭐ THE FIXES, BEST FIRST:
⭐ ① ⭐⭐ ***DO NOT TRACK A CURSOR AT ALL. CLAIM AND DELETE.***
⭐    ⭐ `SELECT ... WHERE published_at IS NULL ... FOR UPDATE
⭐      SKIP LOCKED`, ⭐ publish, ⭐ then mark or delete ***in the
⭐      same transaction***. ⭐⭐ AN UNCOMMITTED ROW IS SIMPLY NOT
⭐      VISIBLE YET AND WILL BE PICKED UP ON THE NEXT POLL —
⭐      THE PROBLEM DISAPPEARS RATHER THAN BEING MANAGED.
⭐      ⭐⭐ THIS IS THE ANSWER. USE IT.
⭐ ② ⭐ ***LOGICAL DECODING / CDC*** (Part 5) — ⭐⭐ THE WAL IS IN
⭐    ***COMMIT*** ORDER, SO THE PROBLEM CANNOT ARISE.
⭐ ③ ⭐ Track `xmin`/snapshot boundaries — ⭐⭐ CORRECT AND FIDDLY.
⭐ ④ ⭐ Re-scan a trailing window (`id > last_seen - 1000`) with
⭐    a dedup set — ⭐⭐ A MITIGATION, NOT A FIX, ⭐ and it still
⭐    loses a row from a transaction that ran longer than the
⭐    window.
```

# Part 4 — The relay in Python

```python
CLAIM = text("""
    SELECT id, aggregate_id, event_type, payload, trace_id
      FROM outbox
     WHERE published_at IS NULL
     ORDER BY id
     LIMIT 200
       FOR UPDATE SKIP LOCKED        -- ⭐⭐ MANY RELAYS, NO
""")                                 -- ⭐   COORDINATION, NO LOCK

def relay_once() -> int:
    with engine.begin() as conn:              # ⭐⭐ ONE TXN
        rows = conn.execute(CLAIM).all()
        if not rows:
            return 0
        for r in rows:
            producer.produce(
                TOPIC,
                key=str(r.aggregate_id).encode(),   # ⭐⭐ ORDERING
                value=r.payload,                    # ⭐   PER AGG
                headers=[("trace_id", r.trace_id or ""),
                         ("event_id", str(r.id))],  # ⭐⭐ DEDUP KEY
            )
        producer.flush(10)                    # ⭐⭐ BEFORE MARKING
        conn.execute(text(
            "UPDATE outbox SET published_at = now() "
            "WHERE id = ANY(:ids)"), {"ids": [r.id for r in rows]})
    return len(rows)
```

```
⭐⭐ FOUR THINGS IN THAT FUNCTION THAT ARE NOT DECORATION:
⭐   ⭐⭐ ① `SKIP LOCKED` MEANS YOU CAN RUN SIX RELAY REPLICAS
⭐      WITH NO LEADER ELECTION AND NO DISTRIBUTED LOCK
⭐      (DAY 411). ⭐ Each claims a disjoint set. ⭐⭐ THE DATABASE
⭐      IS THE COORDINATOR AND IT IS ALREADY CORRECT.
⭐   ⭐⭐ ② `flush()` BEFORE THE `UPDATE`. ⭐ Otherwise you mark
⭐      rows published while they sit in librdkafka's buffer,
⭐      ⭐⭐ AND DAY 401's SILENT-DROP BUG BECOMES SILENT ***DATA
⭐      LOSS*** INSTEAD OF A LOST METRIC.
⭐   ⭐ ③ Key by `aggregate_id` — ⭐⭐ SAME AGGREGATE, SAME
⭐      PARTITION, SAME ORDER (DAY 401). ⭐ Global order is not
⭐      preserved and was never needed.
⭐   ⭐⭐ ④ `event_id` IN THE HEADER IS THE CONSUMER'S DEDUP KEY
⭐      (DAY 335), AND `trace_id` IS THE HOP EVERY TRACE LOSES
⭐      (DAY 376).

⭐ ⭐ Cleanup: ⭐⭐ DELETE PUBLISHED ROWS AFTER A DAY, OR PARTITION
⭐   BY DAY AND `DROP` THE PARTITION. ⭐ An outbox nobody prunes
⭐   becomes your largest table, ⭐⭐ AND ITS BLOAT SLOWS THE VERY
⭐   TRANSACTION THAT WRITES TO IT.
⭐ ⭐ The ORM trap: ⭐⭐ WRITING THE OUTBOX ROW AFTER
⭐   `session.commit()` IS THE DUAL-WRITE BUG REINTRODUCED INSIDE
⭐   YOUR ORM. ⭐ Use a `before_commit` hook or an explicit call
⭐   inside the unit of work, ⭐⭐ AND ADD A TEST THAT ASSERTS THE
⭐   TWO INSERTS SHARE A TRANSACTION.
```

# Part 5 — ⭐⭐ CDC and Debezium: the three things that bite

```
⭐ HOW IT WORKS ON POSTGRES: ⭐ a ***replication slot*** plus a
⭐   ***publication***. ⭐ Debezium reads the WAL through logical
⭐   decoding and emits a message per row change.
⭐   ⭐⭐ THE WAL IS IN COMMIT ORDER, SO PART 3's GAP BUG CANNOT
⭐   HAPPEN, ⭐ and there is no polling load on your tables.

⭐⭐ ① ***THE REPLICATION SLOT WILL FILL YOUR DISK AND STOP YOUR
⭐    DATABASE.*** ⭐ This is the number-one Debezium production
⭐    incident and it is not subtle.
⭐    ⭐ A slot guarantees Postgres retains WAL until the consumer
⭐      confirms it. ⭐⭐ SO IF DEBEZIUM IS DOWN — OR SLOW, OR
⭐      SOMEONE CREATED A SLOT FOR A TEST AND FORGOT IT — WAL
⭐      ACCUMULATES ***WITHOUT BOUND*** UNTIL THE VOLUME IS FULL,
⭐      AND A POSTGRES THAT CANNOT WRITE WAL CANNOT COMMIT
⭐      ANYTHING.
⭐    ⭐⭐ ⇒ ALARM ON `pg_replication_slots` LAG
⭐      (`pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)`),
⭐      ⭐⭐ SET `max_slot_wal_keep_size` SO POSTGRES WILL SACRIFICE
⭐      THE SLOT RATHER THAN ITSELF, ⭐ and audit for orphan slots
⭐      monthly.

⭐⭐ ② ***`REPLICA IDENTITY` DECIDES WHETHER YOU GET THE "BEFORE"
⭐    IMAGE.*** ⭐ By default Postgres writes only the primary key
⭐    for `UPDATE` and `DELETE`, ⭐⭐ SO YOUR CDC EVENT HAS THE NEW
⭐    ROW AND A `before` OF `null` — ⭐ and any consumer that
⭐    needs "what changed" or "what was the old value" cannot
⭐    work. ⭐ `REPLICA IDENTITY FULL` gives you it ⭐⭐ AND COSTS
⭐    WRITE THROUGHPUT AND WAL VOLUME ON EVERY UPDATE. ⭐ Choose
⭐    per table, deliberately.

⭐⭐ ③ ***SCHEMA CHANGES FLOW THROUGH AND BREAK CONSUMERS.***
⭐    ⭐ A column rename is a new field name in every downstream
⭐    message. ⭐⭐ WHICH IS DAY 398's NINTH FALLACY ARRIVING BY
⭐    WAY OF A MIGRATION SOMEBODY RAN ON A TUESDAY. ⭐ ⇒ a schema
⭐    registry with a compatibility mode (Day 401), ⭐ and CDC
⭐    output treated as a versioned contract.

⭐ ⭐ Also: ⭐⭐ THE INITIAL SNAPSHOT CAN TAKE HOURS AND HOLD LOCKS
⭐   OR SATURATE I/O ON A LARGE TABLE — ⭐ use incremental
⭐   snapshotting, ⭐ and do it in a maintenance window.
```

# Part 6 — ⭐⭐ Outbox or CDC-on-tables? The rule

```
⭐⭐ ***CDC ON YOUR BUSINESS TABLES MAKES YOUR DATABASE SCHEMA
⭐   YOUR PUBLIC API.***
⭐   ⭐ Rename a column and six downstream consumers break.
⭐   ⭐ Normalise a table and the event shape changes.
⭐   ⭐⭐ YOU HAVE COUPLED EVERY CONSUMER TO YOUR STORAGE DECISIONS
⭐     — WHICH IS EXACTLY THE SHARED-DATABASE ANTI-PATTERN OF
⭐     DAY 399, DELIVERED ASYNCHRONOUSLY SO IT IS HARDER TO SEE.

⭐⭐ ***THE OUTBOX GIVES YOU AN EXPLICIT, VERSIONED CONTRACT.***
⭐   ⭐ You choose the event shape. ⭐ You choose what is public.
⭐   ⭐ You refactor the schema freely.

⭐⭐ ⇒ THE RULE:
⭐   ⭐⭐ ***OUTBOX FOR EVENTS OTHER SERVICES CONSUME.***
⭐   ⭐⭐ ***CDC-ON-TABLES FOR REPLICATING DATA INTO SOMETHING YOU
⭐     OWN*** — ⭐ a warehouse, a search index, a cache, an
⭐     analytics lake. ⭐ There, schema coupling is fine because
⭐     both ends are yours and change together.
⭐   ⭐⭐ AND THE BEST OF BOTH: ***CDC ON THE OUTBOX TABLE.***
⭐     ⭐ The explicit contract of the outbox ⭐ plus the commit
⭐     ordering, low latency and zero polling of CDC.
⭐     ⭐⭐ DEBEZIUM SHIPS AN OUTBOX EVENT ROUTER FOR EXACTLY THIS,
⭐     AND IT IS THE MOST DEFENSIBLE ANSWER IN AN INTERVIEW.
```

# Part 7 — Where the outbox shows up everywhere else

```
⭐⭐ ONCE YOU SEE IT, THE PATTERN IS THE WHOLE STAGE:
⭐   ⭐ Day 402: ⭐ the consumer offset stored in ***the same
⭐     transaction*** as the projection write.
⭐   ⭐ Day 406: ⭐ the projection position in the same
⭐     transaction as its rows.
⭐   ⭐ Day 405: ⭐ the events and the outbox row in one append.
⭐   ⭐ Day 358: ⭐ the ledger entry and the idempotency key in
⭐     one commit.
⭐   ⭐ Day 335: ⭐ the dedup guard in the same transaction as the
⭐     effect.

⭐⭐ ⇒ ***ALL OF THEM ARE ONE MOVE: WHEN TWO THINGS MUST HAPPEN
⭐   TOGETHER AND ONLY ONE SYSTEM HAS TRANSACTIONS, PUT BOTH
⭐   THINGS IN THAT SYSTEM AND MAKE THE SECOND ONE A CONSEQUENCE
⭐   OF THE FIRST.***
⭐   ⭐ It is not a Kafka pattern, or a microservices pattern.
⭐   ⭐⭐ IT IS THE ONLY WAY TO GET ATOMICITY ACROSS A BOUNDARY
⭐     WITHOUT A DISTRIBUTED TRANSACTION, ⭐ and it is the single
⭐     most transferable idea in Stage 12.
```

# 💬 Interview

**1. ⭐⭐ "How do you publish an event when you save a record?"**
> ⭐ Not by publishing after the commit, because that's the dual-write problem: ⭐⭐ **crash between the
> commit and the publish and the order exists but nobody will ever be told — no email, no warehouse
> pick — and nothing logs an error, because the transaction succeeded and the process died
> afterwards.** ⭐ Reversing the order is worse: you publish an event for an order that doesn't exist.
> ⭐⭐ **There's no ordering that works, and a distributed transaction across the database and the broker
> isn't available — 2PC blocks, and it makes your availability the product of both systems'.** ⭐ So:
> the outbox. ⭐⭐ **Write the event to an outbox table in the same transaction as the state change, and
> a separate relay publishes it — the atomicity comes free from a transaction you already had.** ⭐ The
> relay is at-least-once, so consumers must be idempotent; no configuration removes that.

**2. ⭐⭐ "You've built an outbox with `WHERE id > last_seen`. What's wrong?"**
> ⭐ It silently skips rows. ⭐⭐ **Sequences hand out numbers at INSERT time, outside the transaction, so
> transaction A can take id 5 and transaction B can take id 6 and commit first. The relay sees 6,
> publishes it, stores last_seen=6 — and then A commits, row 5 becomes visible, and the relay is
> already asking for id > 6. Row 5 is never published, with no error and no gap detected.** ⭐ It only
> appears under concurrency, so it never shows up in testing. ⭐ The fix is to stop tracking a cursor:
> ⭐⭐ **`WHERE published_at IS NULL ... FOR UPDATE SKIP LOCKED`, publish, then mark in the same
> transaction — an uncommitted row simply isn't visible yet and gets picked up on the next poll, so
> the problem disappears rather than being managed.**

**3. "What does `SKIP LOCKED` buy you in the relay?"**
> ⭐⭐ **You can run six relay replicas with no leader election and no distributed lock — each claims a
> disjoint set, and the database is the coordinator.** ⭐ That's the theme from the locking day arriving
> early: ⭐⭐ **the best distributed lock is usually one you didn't need, because the database already
> does it correctly.** ⭐ And the other non-decorative detail is ⭐⭐ **flushing the producer before
> marking the rows published — otherwise you mark rows done while they're still in the client's
> buffer, and a silent drop becomes silent data loss.**

**4. ⭐⭐ "What breaks with Debezium in production?"**
> ⭐ Three things, and the first is severe. ⭐⭐ **A replication slot guarantees Postgres retains WAL
> until the consumer confirms it — so if Debezium is down, or slow, or someone made a slot for a test
> and forgot it, WAL accumulates without bound until the volume is full, and a Postgres that can't
> write WAL can't commit anything.** ⭐ So I alarm on slot lag and set `max_slot_wal_keep_size` so
> Postgres sacrifices the slot rather than itself. ⭐ Second, ⭐⭐ **`REPLICA IDENTITY` — by default only
> the primary key goes in the WAL for updates, so your CDC event has a `before` of null and any
> consumer needing "what changed" can't work**; `FULL` fixes it and costs write throughput. ⭐ Third,
> schema changes flow straight through to consumers, so CDC output needs a registry and a
> compatibility mode.

**5. ⭐⭐ "Outbox or CDC on the tables?"**
> ⭐ It depends who consumes it, and there's a clean rule. ⭐⭐ **CDC on business tables makes your
> database schema your public API — rename a column and six consumers break — which is the
> shared-database anti-pattern delivered asynchronously so it's harder to see.** ⭐ The outbox gives you
> an explicit, versioned contract where you choose what's public and can refactor storage freely.
> ⭐⭐ **So: outbox for events other services consume; CDC-on-tables for replicating into something you
> own, like a warehouse or a search index, where both ends change together.** ⭐ And the best answer is
> both: ⭐⭐ **CDC on the outbox table — the explicit contract plus commit ordering, low latency and no
> polling. Debezium ships an outbox event router for exactly that.**

**6. "Is the outbox a Kafka pattern?"**
> ⭐ No — it's the general move, and it shows up everywhere in this stage. ⭐⭐ **The consumer offset
> stored in the same transaction as the projection write; the projection position with its rows; the
> events and the outbox row in one append; the ledger entry and the idempotency key in one commit.
> They're all the same thing: when two things must happen together and only one system has
> transactions, put both in that system and make the second a consequence of the first.** ⭐ It's the
> only way to get atomicity across a boundary without a distributed transaction.

## 🎙️ Articulation drill

**Two minutes.** Open with the problem in four lines: **commit then publish, crash between, and the
order exists but nobody will ever be told — with no error anywhere, because the transaction succeeded
and the process died afterwards. Reverse it and you publish an event for an order that doesn't exist,
which is worse. There's no ordering that works, and 2PC across a database and a broker isn't
available.** Then the answer: **write the event to an outbox table in the same transaction as the
state change, and let a relay publish it — the atomicity comes free from a transaction you already
had, with no coordinator and no new failure mode.** Relay is at-least-once, so consumers are
idempotent. Then the bug that proves you've built one: **`WHERE id > last_seen` silently skips rows,
because sequence numbers are taken at INSERT time and a transaction that took a lower id can commit
later — the relay moves past it and that row is never published, with no error, and it only happens
under concurrency so testing never sees it.** Fix: **claim with `FOR UPDATE SKIP LOCKED` instead of
tracking a cursor, which also lets you run six relay replicas with no leader election because the
database is the coordinator.** Then CDC: **the replication slot is the one that stops your database —
Postgres retains WAL until the consumer confirms, so a stopped or forgotten slot fills the disk and a
Postgres that can't write WAL can't commit.** Give the rule: **outbox for events other services
consume, because CDC on business tables makes your schema your public API; CDC on tables for
replicating into something you own; and CDC on the outbox table for both.** Close on the generalisation:
**this isn't a Kafka pattern. When two things must happen together and only one system has
transactions, put both in that system and make the second a consequence of the first — and that's the
offset-in-the-same-transaction, the projection position, and the idempotency key too.**
