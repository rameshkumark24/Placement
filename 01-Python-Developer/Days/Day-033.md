# Part 1 — ⭐⭐ What a list is

```c
/* ⭐ CPython, Include/cpython/listobject.h */
typedef struct {
    PyObject_VAR_HEAD          /* ⭐ refcount, type, ⭐⭐ ob_size = the LENGTH you see */
    PyObject **ob_item;        /* ⭐⭐ a C array of POINTERS to objects */
    Py_ssize_t allocated;      /* ⭐⭐ CAPACITY — how many slots exist, ≥ ob_size */
} PyListObject;
```

```
⭐⭐ TWO SIZES, AND THE DIFFERENCE IS THE WHOLE DAY:
⭐   ob_size   = len(lst)      — how many elements you have
⭐   allocated = capacity      — how many slots are reserved
⭐   ⇒ ⭐⭐ append() writes into a spare slot and increments ob_size. NO allocation, usually.
⭐   ⇒ ⭐ when ob_size == allocated ⇒ REALLOCATE a bigger block and COPY the pointers.
```

⭐ **It is an array of pointers, so the elements can be any mix of types** — and that is exactly the
memory cost measured on Day 028. **`list` is not `array`; there is nothing contiguous about the
*objects*, only about the pointers to them.**

## ⭐⭐ Over-allocation, and why `append` is O(1) amortised

```python
import sys
lst = []
for i in range(10):
    lst.append(i)
    print(len(lst), sys.getsizeof(lst))
# ⭐ capacity grows: 0, 4, 8, 16, 25, 35, 46, 58, 72, 88, ...
```

```
⭐⭐ THE GROWTH RULE: new_allocated ≈ len + (len >> 3) + 6   ⇒ ⭐ roughly 1.125× plus a constant.
⭐   ⇒ ⭐ growth is GEOMETRIC (a constant FACTOR), which is what makes append amortised O(1):
⭐     n appends cost n cheap writes + a geometric series of copies ⇒ ⭐⭐ O(n) total ⇒ O(1) each.
⭐   ⇒ ⚠️ ⭐⭐ if it grew by a CONSTANT amount instead, n appends would cost O(n²).
⭐        That single design choice is why `append` in a loop is fine and `insert(0, …)` is not.
```

⭐ **Compare Java's `ArrayList` (1.5×) and C++'s `vector` (2×).** ⭐⭐ **CPython grows more slowly
because it optimises for memory over copy count** — a deliberate trade, and a good thing to notice
aloud: *"the growth factor is the trade between wasted memory and copy frequency."*

⚠️ ⭐ **Shrinking:** `pop()` from the end does *not* immediately release capacity — the list only
shrinks its allocation when it falls well below half. **A list that peaked at a million elements
keeps that memory until you rebind it.**

# Part 2 — ⭐⭐ The complexity table you must know cold

| Operation | ⭐ Cost | ⭐⭐ Why |
|---|---|---|
| `lst[i]` | ⭐ **O(1)** | pointer arithmetic |
| `lst[i] = x` | O(1) | |
| ⭐ `lst.append(x)` | ⭐⭐ **O(1) amortised** | spare capacity |
| `lst.pop()` | O(1) | from the end |
| ⭐⭐ **`lst.insert(0, x)`** | ⭐⭐ **O(n)** | ⭐ every later pointer shifts right (`memmove`) |
| ⭐⭐ **`lst.pop(0)`** | ⭐⭐ **O(n)** | ⭐ every later pointer shifts left |
| `lst.remove(x)` | O(n) | search, then shift |
| ⭐ `x in lst` | ⭐⭐ **O(n)** | ⭐ linear scan — **use a `set` (Day 036)** |
| `lst.index(x)` | O(n) | |
| `len(lst)` | ⭐ **O(1)** | `ob_size` is stored |
| `lst[a:b]` | O(b−a) | ⭐ builds a **new list** |
| ⭐ `lst.sort()` | O(n log n) | Timsort |
| `min` / `max` / `sum` | O(n) | |
| `lst.reverse()` | O(n) | in place |
| `lst * k` | O(nk) | ⚠️ ⭐ and Day 024's aliasing trap |

```python
# ⚠️⚠️ ⭐⭐ THE BFS BUG — the most common silent timeout in Python interviews:
queue = [start]
while queue:
    node = queue.pop(0)          # ⭐⭐ O(n) EVERY iteration ⇒ O(n²) overall
    ...

from collections import deque    # ⭐⭐ THE FIX
queue = deque([start])
node = queue.popleft()           # ⭐⭐ O(1) — a doubly linked list of blocks (Day 038)
```

⭐⭐ **Say the reason aloud in a round, not just the fix:** *"a list is a contiguous array, so
removing from the front shifts every remaining pointer — I'll use a `deque`, which is O(1) at both
ends."* **That sentence is worth more than the working code**, because it shows you chose rather than
remembered.

# Part 3 — ⭐ Sorting: Timsort

```python
lst.sort()                     # ⭐ IN PLACE, returns None
new = sorted(lst)              # ⭐ returns a NEW list, works on any iterable
lst.sort(key=lambda x: x.age)  # ⭐⭐ key computed ONCE per element (decorate-sort-undecorate)
lst.sort(key=lambda x: (-x.score, x.name))   # ⭐ Day 029's tuple-key trick
lst.sort(reverse=True)
```

```
⭐⭐ TIMSORT — invented for Python, then adopted by Java and Android:
⭐   · ⭐⭐ STABLE — equal elements keep their original order ⇒ multi-pass sorting works
⭐   · ⭐⭐ ADAPTIVE — it finds existing sorted RUNS and merges them
⭐        ⇒ ⭐ nearly-sorted data approaches O(n). Real data is often nearly sorted.
⭐   · worst case O(n log n), O(n) extra space
```

⚠️ ⭐⭐ **`lst.sort()` returns `None`.** `x = lst.sort()` binds `None` — it is a deliberate Python
convention that **in-place methods return `None`**, so you cannot accidentally chain and believe you
have a copy. ⭐ `sort`/`sorted`, `reverse`/`reversed`, `append`/`+` — **the standard library names
tell you which mutates.**

⭐ **`key` beats `cmp`:** the key function runs **once per element** (n calls), while a comparator
would run O(n log n) times. `functools.cmp_to_key` exists for the rare case you genuinely need
pairwise logic.

# Part 4 — ⭐ Idioms and traps

```python
# ⭐ Building lists
[x*2 for x in xs if x > 0]        # ⭐⭐ comprehension — faster than append in a loop
                                  #    (the loop and the append are done in C)
lst = [None] * n                  # ⭐ preallocate when you know the size
lst += other                      # ⭐⭐ __iadd__ ⇒ EXTENDS IN PLACE (like extend)
lst = lst + other                 # ⭐⭐ builds a NEW list — different object, and O(n+m)
```

```python
# ⚠️⚠️ ⭐⭐ NEVER MUTATE A LIST WHILE ITERATING IT:
for x in lst:
    if bad(x): lst.remove(x)      # ⭐⭐ SKIPS elements — the index advances past the shift
lst[:] = [x for x in lst if not bad(x)]   # ⭐⭐ CORRECT, and mutates in place for other holders
lst = [x for x in lst if not bad(x)]      # ⭐ also correct — but REBINDS (Day 024)
```

⭐⭐ **`lst[:] = ...` versus `lst = ...` is a real distinction, not style:** the first mutates the
object every other reference can see; the second rebinds only your name. **Which one you want depends
on whether anyone else holds that list.**

```python
# ⭐ Copying (Day 025)
shallow = lst[:]  /  list(lst)  /  lst.copy()      # ⭐ all shallow
import copy; deep = copy.deepcopy(lst)

# ⭐ Useful
lst.extend(other)          # ⭐ O(m); `append(other)` would nest it instead
lst.reverse()              # in place;  reversed(lst) is a lazy iterator
lst.count(x)               # O(n)
del lst[2]                 # O(n);  del lst[2:5] also works
lst.clear()
```

⭐ **When a list is the wrong structure:** membership testing (**`set`**), a queue (**`deque`**), a
priority queue (**`heapq`**), millions of numbers (**`array`**/NumPy), sorted insertion
(**`bisect`**) — all of which are Days 036–039.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`pop(0)` in a BFS loop** | ⭐⭐ O(n) each ⇒ O(n²). `deque.popleft()`. |
| ⭐⭐ **`x in lst` in a loop** | ⭐⭐ O(n) each. Build a `set` first. |
| Mutating while iterating | ⭐ Skips elements. Rebuild, or iterate a copy. |
| `x = lst.sort()` | ⭐⭐ Returns `None`. Use `sorted()`. |
| Expecting `sort` to be unstable | ⭐ Timsort is stable — rely on it for multi-pass. |
| ⭐ Confusing `lst[:] =` with `lst =` | ⭐⭐ Mutation vs rebinding — visible to others or not. |
| `append` where `extend` was meant | ⭐ You get a nested list. |
| `[[0]*n]*m` | ⭐⭐ Day 024 — one row, m references. |
| Expecting memory back after `pop` | ⭐ Capacity shrinks lazily. |
| Using a list as a priority queue | ⭐ `heapq` — O(log n) instead of O(n log n) per step. |

## Interview questions

**Q: What is a Python list, internally?**
> A dynamic array of pointers to objects, with a length and a separately tracked capacity. Appending
> writes into spare capacity and bumps the length; when capacity runs out it allocates a larger block
> — geometric growth, roughly 1.125× plus a constant — and copies the pointers. That geometric factor
> is what makes append amortised O(1): the copies form a geometric series, so n appends cost O(n)
> total. If it grew by a fixed amount instead, appending n items would be quadratic.

**Q: Why is `insert(0, x)` O(n)?**
> Because the elements are contiguous in memory. Inserting at the front means every existing pointer
> has to move one slot to the right — a `memmove` of the whole array. Same for `pop(0)`. It's the
> classic trap in BFS: a queue built on a list is quadratic, and a `deque` is O(1) at both ends
> because it's a doubly linked list of blocks.

**Q: What sorting algorithm does Python use, and why does it matter?**
> Timsort, which is stable and adaptive. Stability matters because it makes multi-pass sorting work —
> sort by the secondary key, then the primary, and ties keep their earlier order. Adaptivity matters
> because it detects already-sorted runs and merges them, so nearly-sorted input approaches linear,
> and real data is very often nearly sorted. Worst case is O(n log n) with O(n) extra space.

**Q: Why does `key` exist rather than a comparator?**
> Because the key function is called once per element — n calls — and then the sort compares the
> computed keys directly. A comparator would be invoked O(n log n) times, and in Python each of those
> is a full function call with the interpreter overhead that implies. It's decorate-sort-undecorate
> built into the language, and it's why `key=lambda x: (-x.score, x.name)` is the idiomatic way to
> sort on several fields.

**Q: What's the difference between `lst[:] = new` and `lst = new`?**
> The first mutates the existing list object in place, so every other reference to it sees the
> change. The second rebinds my local name to a different object and leaves everyone else pointing at
> the old one. Which I want depends on whether the list was handed to me — if a caller holds it,
> rebinding silently does nothing from their point of view.

## 🎙️ Articulation drill

Record two minutes: **"Why is `list.pop(0)` slow, and what would you use instead?"**

⭐ Start from the layout, because the layout *is* the answer: **a list is a contiguous array of
pointers, so removing the first element means shifting every remaining pointer down by one** — a
single `memmove`, but O(n) of them, and in a loop that is O(n²).

⭐ Then the fix and its mechanism: **a `deque` is a doubly linked list of fixed-size blocks, so both
ends are O(1)** — at the cost of O(n) random indexing, which a queue never needs.

⭐⭐ **Then close on the property that makes the other end fast, because it is the same idea seen from
the other side:** *"appending is cheap for exactly the opposite reason — the array is over-allocated,
and it grows by a constant factor, so the copies form a geometric series and amortise to O(1) per
append. Geometric growth at the back, linear shifting at the front. One data structure, two very
different answers depending on which end you touch."*
