# Day 098

**L-098** · 🧪 ⭐⭐ **Coverage vs mutation testing** — why 100% coverage proves almost nothing

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: coverage measures which lines were *executed*, not whether anything was
> *verified* — so it is an excellent way to find untested code and a terrible way to prove code is
> tested, and mutation testing is the tool that measures the thing coverage only appears to.**
>
> ⭐ This is a short, sharp day with one demonstration in it that changes how you read a coverage
> report for good.

---

# Part 1 — ⭐ What coverage actually measures

```bash
pytest --cov=myapp --cov-branch --cov-report=term-missing
```

```
Name                     Stmts   Miss Branch BrPart  Cover   Missing
------------------------------------------------------------------------
myapp/orders.py             84      3     22      2    95%   47, 61-62
myapp/pricing.py            40      0     14      0   100%
```

| ⭐ Kind | ⭐ Measures |
|---|---|
| Statement / line | ⭐ was this line executed |
| ⭐⭐ **Branch** | ⭐⭐ was **each outcome** of each condition taken |
| Path | every combination — ⭐ exponential, nobody uses it |

```python
def apply(order):
    if order.is_priority:          # ⭐ one test with is_priority=True:
        order.fee = 0              #    ⭐⭐ 100% LINE coverage, 50% BRANCH coverage
    return order                   #    ⭐ the False path was NEVER RUN
```

⭐⭐ **Always use `--cov-branch`.** ⭐ Line coverage on a codebase full of `if`s systematically
overstates how much you have tested, and the gap is largest exactly where the risk is — **in the
conditionals.**

# Part 2 — ⭐⭐ The demonstration

```python
# ⭐⭐ THIS TEST GIVES 100% COVERAGE OF apply_discount(). IT VERIFIES NOTHING.
def test_apply_discount():
    apply_discount(Order(total=Decimal("100")))     # ⚠️ NO ASSERTION AT ALL
```

```
⭐⭐ RUN IT. COVERAGE SAYS 100%. THE FUNCTION COULD RETURN ANYTHING — OR DELETE
⭐   YOUR DATABASE — AND THE TEST STILL PASSES.
⭐
⭐   ⇒ ⭐⭐ THEREFORE: COVERAGE MEASURES EXECUTION, NOT VERIFICATION. It answers
⭐        "did the test runner walk over this line", and nothing whatsoever about
⭐        whether the behaviour of that line is checked.
⭐   ⇒ ⭐⭐ SO USE IT AS A NEGATIVE SIGNAL, WHICH IS STRONG, AND NEVER AS A
⭐        POSITIVE ONE, WHICH IS WORTHLESS:
⭐        · 0% on a module   ⇒ ⭐⭐ DEFINITELY untested. Reliable, actionable.
⭐        · 100% on a module ⇒ ⭐⭐ tells you almost nothing.
⭐   ⇒ ⭐ THE ONLY QUESTION WORTH ASKING A COVERAGE REPORT: "what did we NOT
⭐        execute at all, and is any of it important?"
```

```
⭐⭐ AND THE TARGET-NUMBER TRAP — GOODHART'S LAW, IN A CI CONFIG:
⭐   "WHEN A MEASURE BECOMES A TARGET, IT CEASES TO BE A GOOD MEASURE."
⭐   Mandate 90% and you will reliably get:
⭐     · ⭐⭐ tests with no assertions, written to walk lines
⭐     · ⭐ tests of getters, __repr__ and dataclass constructors — ⭐⭐ high line
⭐       count, zero risk covered
⭐     · ⭐⭐ `# pragma: no cover` sprinkled on whatever is inconvenient
⭐     · the ERROR PATHS still untested, because they are the hard ones
⭐   ⇒ ⭐⭐ THE PERVERSITY: the number goes up while the SUITE GETS WORSE, because
⭐        every one of those tests is a maintenance cost that catches nothing.
```

⭐ **Better than a global threshold: a *diff* coverage gate.** ⭐⭐ "New and changed lines in this PR
must be covered" is enforceable, fair to legacy code, and it points the requirement at exactly the
code most likely to contain a fresh bug.

# Part 3 — ⭐⭐ Mutation testing

```
⭐⭐ THE IDEA, AND IT IS THE RIGHT QUESTION: DELIBERATELY BREAK YOUR CODE AND
⭐   CHECK WHETHER YOUR TESTS NOTICE.
⭐
⭐   1. make a small change to the source — ⭐ a MUTANT:
⭐        <  →  <=          +  →  -          ==  →  !=
⭐        True → False      return x → return None
⭐        delete a line     0 → 1
⭐   2. ⭐ run the test suite against the mutated code
⭐   3. ⭐⭐ TEST FAILS ⇒ the mutant is KILLED ✔  — your tests verify that line
⭐      ⭐⭐ TESTS PASS ⇒ the mutant SURVIVED ⚠️ — ⭐⭐ your tests EXECUTE that line
⭐         BUT DO NOT VERIFY IT
⭐   4. score = killed / total
⭐
⭐ ⇒ ⭐⭐ A SURVIVING MUTANT IS THE PRECISE THING COVERAGE CANNOT SEE. It is the
⭐     gap between "walked over" and "checked". ⭐ And every surviving mutant is
⭐     ACTIONABLE: it names the exact line and the exact change nobody tested.
```

```bash
pip install mutmut
mutmut run --paths-to-mutate src/myapp/pricing.py
mutmut results
mutmut show 14        # ⭐⭐ the exact diff nobody caught
```

```
⭐⭐ WHAT A SURVIVING MUTANT USUALLY MEANS, IN ORDER OF FREQUENCY:
⭐  1. ⭐⭐ A MISSING BOUNDARY TEST. `<` → `<=` survived because you tested 5 and
⭐       15 but never exactly 10. ⭐ Day 096's cycle 5, found automatically.
⭐  2. ⭐ AN ASSERTION THAT IS TOO WEAK — `assert result is not None` passes for
⭐       every wrong answer too.
⭐  3. ⭐⭐ GENUINELY DEAD CODE — the mutant survived because the line does not
⭐       matter. ⭐ Delete it. This is a real and pleasing outcome.
⭐  4. ⭐ AN EQUIVALENT MUTANT — the change genuinely does not alter behaviour
⭐       (`i += 1` vs `i = i + 1`). ⭐⭐ Unkillable, and the main source of noise.
```

```
⚠️ ⭐⭐ THE COST IS REAL AND IT DECIDES HOW YOU USE IT: the suite runs ONCE PER
⭐    MUTANT. A module with 300 mutants and a 20-second suite is over an hour.
⭐    ⇒ ⭐⭐ SO DO NOT RUN IT ON EVERYTHING, EVER. Run it on the code where a
⭐         silent wrong answer would be expensive — ⭐ pricing, tax, permissions,
⭐         rate limits, anything financial or security-related.
⭐    ⇒ ⭐ run it periodically (a weekly job, or before a release), not per-PR.
⭐    ⇒ ⭐⭐ AND TREAT THE OUTPUT AS A TODO LIST, NOT A SCORE. The value is the
⭐         individual surviving mutants, each of which names a real missing test.
⭐         A "mutation score target" would repeat exactly the coverage mistake.
```

# Part 4 — ⭐ The policy that actually works

```
⭐⭐ WHAT I WOULD PUT IN A REAL PROJECT, AND WHY EACH LINE IS THERE:
⭐
⭐  1. ⭐ `--cov-branch` always. Line coverage overstates, and it overstates most
⭐       where the risk is.
⭐  2. ⭐⭐ NO GLOBAL PERCENTAGE TARGET. Use coverage to FIND untested code, and
⭐       read the report as a list of files, not as a number.
⭐  3. ⭐⭐ A DIFF-COVERAGE GATE on PRs — new and changed lines must be covered.
⭐       ⭐ Fair to legacy, aimed at the freshest risk.
⭐  4. ⭐ A low absolute floor (say 60%) purely as a RATCHET against collapse.
⭐  5. ⭐⭐ MUTATION TESTING, PERIODICALLY, ON THE CRITICAL DOMAIN ONLY.
⭐  6. ⭐⭐ AND THE ONE THAT BEATS ALL FIVE: FOR EVERY BUG THAT REACHES
⭐       PRODUCTION, ADD THE FAILING TEST FIRST (Day 096). ⭐ Real incidents are
⭐       better at finding your blind spots than any tool, because they are drawn
⭐       from the actual distribution of what goes wrong.
```

⚠️ ⭐ **`# pragma: no cover` has exactly two honest uses:** an `if TYPE_CHECKING:` block (Day 090) and
a defensive branch that genuinely cannot be reached. ⭐⭐ **Everywhere else it is a number-management
tool**, and a code reviewer should treat a new one as a question.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Reading 100% as "tested"** | ⭐⭐ It means *executed*. A test with no assertions gets 100%. |
| Line coverage without `--cov-branch` | ⭐ Systematically overstates, worst at conditionals. |
| ⭐⭐ **Mandating 90%** | ⭐⭐ Goodhart — the number rises while the suite gets worse. |
| Tests of getters to raise the number | ⭐ Maintenance cost, zero risk covered. |
| ⭐ `# pragma: no cover` on anything awkward | ⭐ Two honest uses. Otherwise it is number management. |
| A global floor instead of diff coverage | ⭐⭐ Diff coverage aims at the freshest risk and is fair to legacy. |
| ⭐ Running mutation testing on the whole repo | ⭐⭐ Hours. Target the expensive-to-get-wrong modules. |
| Setting a mutation-score target | ⭐⭐ Repeats the coverage mistake. It is a TODO list. |
| ⭐ Ignoring surviving mutants | ⭐ Each one names a real missing test — usually a boundary. |
| Chasing equivalent mutants | ⭐ Unkillable by definition. Note and move on. |

## Interview questions

**Q: Your team has 95% coverage. What does that tell you?**
> That 95% of lines were executed by the suite. It tells me almost nothing about whether behaviour is
> verified — a test with no assertion at all gives 100% coverage of whatever it calls. So I treat
> coverage as a strong negative signal and a worthless positive one: a module at 0% is definitely
> untested and that's actionable, while a module at 100% could be covered by tests that assert
> nothing. The only question I ask a coverage report is "what did we never execute, and does any of it
> matter?"

**Q: Would you set a coverage target in CI?**
> Not a high global one. That's Goodhart's law in a config file: mandate 90% and you get tests with no
> assertions, tests of getters and `__repr__`, and `pragma: no cover` on anything inconvenient — the
> number goes up while the suite gets worse, because every one of those tests is a maintenance cost
> that catches nothing. What I would set is a diff-coverage gate, so new and changed lines in a PR
> must be covered. That's fair to legacy code and points the requirement at the code most likely to
> contain a fresh bug. Plus a low absolute floor as a ratchet against collapse.

**Q: What is mutation testing?**
> It makes small changes to your source — flipping `<` to `<=`, replacing a return with `None`,
> deleting a line — and reruns the suite against each mutant. If a test fails, the mutant is killed
> and that line is genuinely verified. If everything passes, the mutant survived, which means your
> tests execute that line but don't check it. That's precisely the gap coverage can't see, and it's
> the actual measure of test quality rather than test presence.

**Q: What does a surviving mutant usually mean?**
> Most often a missing boundary test — `<` became `<=` and survived because you tested 5 and 15 but
> never exactly 10. Sometimes an assertion that's too weak, like `assert result is not None`, which
> passes for every wrong answer. Sometimes genuinely dead code, which is a pleasing outcome because
> you delete it. And sometimes an equivalent mutant, where the change really doesn't alter behaviour —
> those are unkillable and are the main source of noise.

**Q: Why not run mutation testing everywhere?**
> Cost. The suite runs once per mutant, so a module with three hundred mutants and a twenty-second
> suite is over an hour. I'd run it periodically — weekly, or before a release — on the code where a
> silent wrong answer is expensive: pricing, tax, permissions, rate limits. And I'd treat the output as
> a TODO list of individual surviving mutants rather than a score, because setting a mutation-score
> target would repeat exactly the mistake we just made with coverage.

## Mini task

1. ⭐⭐ **Write a test with no assertions** and run coverage on it. **Look at the 100%.** Keep this
   demonstration; it is the one to show a colleague.
2. ⭐ Run your suite with and without `--cov-branch`. **Write down both numbers** and explain the gap.
3. ⭐⭐ Find your lowest-coverage module. Is it low-risk, or is it the scariest code you own?
4. ⭐ Find a `# pragma: no cover` in any project you can access. **Judge whether it is honest.**
5. ⭐⭐ Install `mutmut` and run it on **one small, important module.**
6. ⭐⭐ Take the first surviving mutant and **write the test that kills it.** Note what kind of gap it
   was.
7. ⭐ Find an equivalent mutant and explain why it cannot be killed.
8. ⭐⭐ Deliberately weaken a good assertion to `is not None` and **watch mutants start surviving.**
9. ⭐ Set up a diff-coverage check on a PR and see it fail for uncovered new lines.
10. ⭐⭐ Take the last real bug from your project. **Was the buggy line covered?** If yes, that is the
    whole lesson of today in one data point.

## 🎙️ Articulation drill

Record two minutes: **"We have 95% coverage. Are we well tested?"**

⭐ **Answer the actual question, not the flattering one:** **"it tells you 95% of lines were executed.
It doesn't tell you anything was checked."**

⭐⭐ **Then the demonstration, because it is unanswerable and takes ten seconds:** *"a test that calls a
function and asserts nothing at all gives you 100% coverage of that function. The function could
return the wrong value, or delete a table, and the test still passes. So coverage measures execution,
not verification — it's a strong negative signal and a worthless positive one. Zero percent on a module
means definitely untested and that's actionable. A hundred percent means almost nothing."*

⭐⭐ **Then the trap, named:** *"and I'd be wary of the number being a target, because that's Goodhart's
law. Mandate ninety percent and you predictably get tests with no assertions, tests of getters and
`__repr__`, and `pragma: no cover` on whatever's awkward — while the error paths, which are the hard
ones, stay untested. The metric goes up and the suite gets worse."*

⭐ **Then what you'd actually do:** *"branch coverage rather than line, because line coverage
overstates most exactly where the conditionals are. A diff-coverage gate so new and changed lines must
be covered — fair to legacy, aimed at the freshest risk. And for the code where a silent wrong answer
is expensive, pricing or permissions, I'd run mutation testing periodically. That flips `<` to `<=` and
checks whether any test notices, which is the thing coverage only appears to measure. Every surviving
mutant names a real missing test, usually a boundary."*

⭐⭐ **Close on the one that beats all of it:** *"though the highest-value practice isn't a tool at all
— for every bug that reaches production, write the failing test first. Real incidents find your blind
spots better than any metric, because they come from the actual distribution of what goes wrong."*
