> ⭐⭐ **The sentence to own: `parametrize` turns one test into many independent tests — so a failure

# Part 1 — ⭐⭐ `parametrize`

```python
import pytest

@pytest.mark.parametrize("amount, expected", [
    (Decimal("0"),   Decimal("0")),
    (Decimal("99"),  Decimal("99")),      # ⭐ boundary — just below
    (Decimal("100"), Decimal("90")),      # ⭐⭐ boundary — exactly at
    (Decimal("101"), Decimal("90.9")),
])
def test_discount(amount, expected):
    assert apply_discount(amount) == expected
```

```
⭐⭐ WHY NOT A LOOP INSIDE ONE TEST — THREE REASONS, AND THE FIRST IS DECISIVE:
⭐  1. ⭐⭐ FOUR SEPARATE TESTS ⇒ the failure line names the exact input:
⭐       test_discount[100-90] FAILED. ⭐ A loop gives you one failure and stops
⭐       at the first bad case, hiding the rest.
⭐  2. ⭐ EACH CASE GETS ITS OWN FIXTURES ⇒ no leakage between cases.
⭐  3. ⭐ you can select or skip ONE case: pytest -k "100-90"
⭐  ⇒ ⭐⭐ AND THE HABIT IT ENCOURAGES: parametrize makes adding a BOUNDARY CASE
⭐       a one-line change, so you actually add them. ⭐ Most bugs live at
⭐       boundaries — 0, 1, empty, exactly-at-the-limit, one-over, None.
```

```python
@pytest.mark.parametrize("value, expected", [
    pytest.param("", False, id="empty"),                       # ⭐⭐ readable ids
    pytest.param("a@b.com", True, id="simple"),
    pytest.param("a@b", False, id="no_tld",
                 marks=pytest.mark.xfail(reason="issue #212")), # ⭐ per-case marks
])
def test_is_valid_email(value, expected): ...

# ⭐⭐ STACKING = CARTESIAN PRODUCT — 2 × 3 = SIX tests:
@pytest.mark.parametrize("currency", ["GBP", "USD"])
@pytest.mark.parametrize("tier", ["free", "pro", "enterprise"])
def test_pricing(currency, tier): ...
```

⚠️ ⭐ **Stacking is easy to overdo.** Three stacked lists of five is 125 tests, most of them
meaningless combinations. ⭐⭐ **Parametrize the axis that actually varies the behaviour**; use an
explicit list of realistic tuples for the rest.

```python
# ⭐ INDIRECT — pass the parameter to a FIXTURE rather than the test:
@pytest.fixture
def client(request):
    return make_client(auth=request.param)          # ⭐ request.param

@pytest.mark.parametrize("client", ["admin", "anon"], indirect=True)
def test_access(client): ...
```

# Part 2 — ⭐ `pytest.raises`, and testing failure

```python
def test_refund_over_limit_is_rejected():
    with pytest.raises(RefundTooLarge) as exc_info:      # ⭐ the TYPE
        process_refund(Decimal("10000"))
    assert exc_info.value.limit == Decimal("500")        # ⭐ and the payload

def test_invalid_email_message():
    with pytest.raises(ValueError, match=r"invalid email: .*@"):   # ⭐⭐ match= is a REGEX search
        parse_email("nope@")
```

```
⭐⭐ TEST THE FAILURE PATHS. It is the half of the suite people skip, and it is
⭐   where Day 060's error design gets verified:
⭐   · ⭐ the right EXCEPTION TYPE — because callers catch by type
⭐   · ⭐⭐ the MESSAGE, when a human will read it — match= guards against a
⭐        refactor that silently degrades an error into "something went wrong"
⭐   · ⭐ that the operation had NO PARTIAL EFFECT (nothing was written)
⭐   ⚠️ ⭐ pytest.raises(Exception) is almost always too broad — it passes when
⭐      your code raises a TypeError from a typo, which is the opposite of a test.
```

⭐ **`pytest.warns(DeprecationWarning)`** for deprecations, and **`pytest.raises(ExceptionGroup)`** with
`exc_info.group_contains(...)` for `TaskGroup` failures (Day 071).

# Part 3 — ⭐⭐ Markers, and `monkeypatch`

```python
@pytest.mark.slow
def test_full_import(): ...

@pytest.mark.skip(reason="pending #431")
@pytest.mark.skipif(sys.platform == "win32", reason="POSIX signals")   # ⭐ (Day 081)
@pytest.mark.xfail(reason="known bug #212", strict=True)               # ⭐⭐ STRICT
```

```bash
pytest -m "not slow"        # ⭐⭐ the fast loop while developing
pytest -m "slow"            # ⭐ the nightly run
```

```
⭐⭐ xfail(strict=True) IS THE ONE WORTH KNOWING: a NON-strict xfail passes
⭐   silently if the bug gets fixed ⇒ ⭐⭐ you never learn that it was fixed, and
⭐   the marker rots there forever. ⭐ STRICT makes an unexpected PASS a FAILURE
⭐   ⇒ the suite tells you "issue #212 is fixed, delete this marker".
⭐ ⭐⭐ AND: set `--strict-markers` so a typo like @pytest.mark.slwo is an ERROR
⭐   rather than a silently-ignored decorator that skips nothing.
```

```python
def test_uses_configured_url(monkeypatch):
    monkeypatch.setenv("DATABASE_URL", "postgresql://test")   # ⭐ auto-undone
    monkeypatch.delenv("API_KEY", raising=False)
    monkeypatch.setattr(myapp.clock, "now", lambda: FIXED_TIME)   # ⭐⭐ patch an attribute
    monkeypatch.chdir(tmp_path)
    ...
    # ⭐⭐ EVERY CHANGE IS REVERSED AT THE END OF THE TEST, INCLUDING ON FAILURE.
```

```
⭐⭐ THE RULE THAT CAUSES MORE CONFUSION THAN ANY OTHER IN PYTHON TESTING —
⭐   PATCH WHERE IT IS *USED*, NOT WHERE IT IS *DEFINED*. And Day 074 explains it:
⭐
⭐     # myapp/orders.py
⭐     from myapp.clock import now          ⇒ ⭐⭐ this BINDS A NAME IN
⭐     def place(): return now()               myapp.orders' NAMESPACE.
⭐
⭐   ⇒ ⚠️ monkeypatch.setattr("myapp.clock.now", fake)   ⇒ ⭐⭐ DOES NOTHING.
⭐        myapp.orders.now still points at the ORIGINAL function object.
⭐   ⇒ ⭐⭐ monkeypatch.setattr("myapp.orders.now", fake) ⇒ ✔ works.
⭐   ⇒ ⭐ OR import the MODULE instead — `from myapp import clock` … `clock.now()`
⭐        ⇒ ⭐⭐ then the lookup happens at CALL time, so patching the module works
⭐        and the confusion disappears entirely. ⭐ That is a design fix, not a
⭐        testing trick, and it is why module imports age better (Day 074).
```

⭐ **`monkeypatch` over `unittest.mock.patch` for simple substitutions**: it is scoped to the test, it
undoes itself, and there is no decorator-argument ordering to get wrong. ⭐⭐ **Reach for `mock` when
you need to *assert on calls*** — which Day 095 argues you should want less often than you think.

# Part 4 — ⭐ `tmp_path`, `capsys`, `caplog`

```python
def test_writes_report(tmp_path):
    out = tmp_path / "report.csv"            # ⭐⭐ a fresh directory PER TEST
    write_report(out, rows)
    assert out.read_text(encoding="utf-8").startswith("id,name")   # ⭐ Day 076

def test_cli_prints_summary(capsys):
    main(["--summary"])
    captured = capsys.readouterr()           # ⭐ .out and .err
    assert "3 orders" in captured.out

def test_logs_a_warning_on_retry(caplog):
    with caplog.at_level(logging.WARNING):   # ⭐⭐ set the level, or you capture nothing
        fetch_with_retry(url)
    assert "retrying" in caplog.text
    assert caplog.records[0].levelno == logging.WARNING
```

```
⭐⭐ THE caplog TRAP, AND IT COMES STRAIGHT FROM DAY 076: caplog works by adding a
⭐   HANDLER at the ROOT. ⇒ if your app sets `logger.propagate = False` anywhere,
⭐   ⭐⭐ THOSE RECORDS NEVER REACH THE ROOT AND caplog SEES NOTHING — and the test
⭐   fails with an empty `caplog.text`, which looks like the code not logging.
⭐   ⇒ ⭐ and `caplog.set_level()` on the right LOGGER NAME, not just the level.
⭐
⭐ ⭐⭐ AND THE DESIGN QUESTION UNDERNEATH: should you assert on log output at all?
⭐   ⇒ ⭐ YES for logs that are a CONTRACT — an audit line, a security event, a
⭐        structured field your alerting queries.
⭐   ⇒ ⚠️ ⭐⭐ NO for incidental debug messages: that is testing implementation
⭐        (Day 092) and it will break on every reword.
```

# Part 5 — ⭐⭐ Configuration, and the flags you actually use

```toml
# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]                    # ⭐ do not scan the whole repo
addopts = "-ra --strict-markers --strict-config"   # ⭐⭐ see below
filterwarnings = ["error"]               # ⭐⭐ THE HIGH-VALUE ONE
markers = [
    "slow: takes more than a second",
    "integration: needs a database",
]
```

```
⭐⭐ THE THREE SETTINGS THAT CHANGE HOW MUCH A SUITE IS WORTH:
⭐  1. ⭐⭐ filterwarnings = ["error"] ⇒ A DEPRECATION WARNING BECOMES A TEST
⭐       FAILURE. ⇒ ⭐⭐ you find out about a breaking change in a dependency
⭐       MONTHS BEFORE the upgrade that removes it, instead of on the day it
⭐       breaks production. ⭐ Add per-warning ignores as needed; keep the default.
⭐  2. ⭐⭐ --strict-markers ⇒ a mistyped marker is an error, not a silent no-op.
⭐  3. ⭐ -ra ⇒ a summary of every skip/xfail with its reason ⇒ ⭐⭐ skipped tests
⭐       stay VISIBLE instead of quietly becoming permanent.
```

| ⭐ Flag | ⭐ Use |
|---|---|
| ⭐⭐ `-x` | stop at the first failure — **the debugging loop** |
| ⭐⭐ `--lf` / `--ff` | ⭐⭐ **last-failed only** / failed-first — the fastest inner loop there is |
| ⭐ `-k "order and not slow"` | select by name expression |
| `-q` / `-v` | quieter / per-test names |
| ⭐ `--durations=10` | ⭐⭐ **the ten slowest tests** — where your suite's time went |
| ⭐ `--pdb` | ⭐ drop into the debugger at the failure (Day 100) |
| `-s` | do not capture stdout |
| ⭐⭐ `-n auto` | ⭐ `pytest-xdist` — parallel across cores (Day 068) |
| ⭐ `-p no:randomly` | temporarily disable order randomisation |

```
⭐ THE PLUGINS WORTH INSTALLING ON DAY ONE:
⭐   pytest-cov         ⭐ coverage (Day 098)
⭐   pytest-xdist       ⭐⭐ -n auto ⇒ real parallelism; ⭐ also EXPOSES shared state
⭐   pytest-randomly    ⭐⭐ shuffles order ⇒ order dependence fails immediately (Day 092)
⭐   time-machine       ⭐ freeze the clock (faster than freezegun)
⭐   respx / responses  ⭐ stub HTTP at the transport layer (Day 097)
⭐   pytest-asyncio     ⭐ or anyio, for async tests (Day 097)
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Looping over cases inside one test** | ⭐⭐ `parametrize` — the failure names the input, and later cases still run. |
| Stacking three parametrize lists | ⭐ 125 tests, mostly meaningless. Parametrize the axis that matters. |
| ⭐ `pytest.raises(Exception)` | ⭐⭐ Passes on a `TypeError` from a typo. Be specific. |
| Not asserting the error message | ⭐ `match=` guards against errors degrading into "something went wrong". |
| ⭐ Non-strict `xfail` | ⭐⭐ Silently passes when fixed; the marker rots. `strict=True`. |
| No `--strict-markers` | ⭐ A typo'd marker silently does nothing. |
| ⭐⭐ **Patching where it is defined** | ⭐⭐ `from x import y` bound a name in *your* module. Patch there. |
| ⭐ Empty `caplog.text` | ⭐ `propagate = False` somewhere, or the level was never set. |
| Asserting on incidental log lines | ⭐⭐ Testing implementation — breaks on every reword. |
| Writing test files into the repo | ⭐ `tmp_path`. |
| ⭐ No `filterwarnings = error` | ⭐⭐ You find out about breaking changes on the day they break you. |
| Never running `--durations` | ⭐ You do not know where your suite's time goes. |

## Interview questions

**Q: Why `parametrize` rather than a loop inside the test?**
> Because it produces separate tests. The failure line names the exact input — `test_discount[100-90]`
> — and every other case still runs, where a loop stops at the first bad value and hides the rest.
> Each case also gets fresh fixtures, so there's no leakage, and you can select one case with `-k`.
> The habit it creates matters as much: adding a boundary case becomes a one-line change, so you
> actually add them, and most bugs live at boundaries — zero, one, empty, exactly at the limit, one
> over.

**Q: You patched a function and the test still calls the real one. Why?**
> Because `from myapp.clock import now` binds a name in the *importing* module's namespace, so
> patching `myapp.clock.now` leaves `myapp.orders.now` pointing at the original function object. You
> have to patch where it's used — `myapp.orders.now`. The better fix is a design one: import the
> module and call `clock.now()`, so the attribute lookup happens at call time and patching the module
> works. That's the same import mechanic behind circular imports, and it's a reason module-level
> imports age better than name imports.

**Q: What's `xfail(strict=True)` for?**
> A non-strict `xfail` passes silently once the underlying bug is fixed, so nobody ever learns it's
> fixed and the marker sits there forever pretending a working feature is broken. Strict makes an
> unexpected pass a failure, so the suite actively tells you "this is fixed, delete the marker". I'd
> pair it with `--strict-markers`, so a mistyped marker name is an error rather than a decorator that
> silently does nothing.

**Q: Name a pytest setting that most projects should have and most don't.**
> `filterwarnings = ["error"]`. It turns a `DeprecationWarning` into a test failure, which means you
> learn about a breaking change in a dependency months before the release that removes it, instead of
> on the day it takes production down. You can add targeted ignores for warnings you can't act on yet.
> The other two I'd always set are `--strict-markers` and `-ra`, because `-ra` keeps skipped and
> xfailed tests visible with their reasons instead of letting them quietly become permanent.

**Q: Should tests assert on log output?**
> Only when the log is a contract — an audit line, a security event, a structured field that alerting
> queries. Those are behaviour and deserve tests. Asserting on incidental debug messages is testing
> implementation, and it breaks on every reword for no benefit. The mechanical gotcha is that
> `caplog` attaches a handler at the root, so if anything in the app sets `propagate = False` the
> records never arrive and `caplog.text` is empty — which looks exactly like the code failing to log.

## 🎙️ Articulation drill

Record two minutes: **"You've joined a team whose test suite takes 25 minutes and everyone ignores
it. What do you do in the first week?"**

⭐ **Measure before changing anything:** **"first `--durations=25`, because suites are almost never
uniformly slow — usually a handful of tests dominate, and they're usually integration tests spinning
something up per test rather than per session."**

⭐⭐ **Then three concrete moves, cheapest first:** *"fixture scope is the usual win — a session-scoped
engine with a function-scoped transaction rolled back per test gives you a clean database without
paying the connection cost every time. Then `-n auto` with xdist for real parallelism across cores.
And `--lf` for the inner loop, so while I'm fixing something I'm only running what failed. Those three
usually take a suite from 'run it in CI and hope' to 'run it before every commit', and that shift is
where the value actually is — a test that fails seconds after I write the bug is worth ten that fail
twenty minutes later."*

⭐⭐ **Then the trust problem, which is the harder half:** *"but 'everyone ignores it' usually means
flaky, not just slow. I'd install `pytest-randomly` to expose order dependence immediately, and
quarantine the flakes with tickets rather than letting people re-run. Once the reflex is to re-run CI
instead of read the failure, real failures get re-run too, and the suite has stopped protecting
anything."*

⭐ **Close on the settings nobody sets:** *"and I'd add `filterwarnings = ["error"]`, `--strict-markers`
and `-ra` to the config. The first one is the highest-leverage line in a pytest config — it turns a
deprecation into a failure, so you learn about a breaking dependency change months early rather than
on the day it breaks production."*
