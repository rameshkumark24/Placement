# Day 480 💷

**P-480** · 💷 **LLD round 4 — a wallet** — ⭐⭐ the balance is derived, not stored

**Time:** 3 hrs · **Mode:** MOCK + DEBRIEF

> ⭐⭐ **The sentence to own: a wallet that stores a balance and updates it has no way to detect its own
> corruption — a double-entry ledger stores the movements instead, so the balance becomes a derived
> value and every error in the system becomes arithmetic that no longer sums to zero.**

# Part 1 — ⭐⭐ Money is never a float

```
⭐ ***THE FIRST THING TO SAY, BEFORE ANY DESIGN:***

⭐   >>> 0.1 + 0.2 == 0.3
⭐   False
⭐   >>> 0.1 + 0.2
⭐   0.30000000000000004

⭐ ⭐⭐ FLOATS ARE BINARY FRACTIONS. ⭐ 0.1 is not representable,
⭐   ⭐⭐ SO EVERY ADDITION ACCUMULATES ERROR, ⭐ and a system that
⭐   processes millions of transactions accumulates it into
⭐   something a regulator can see.

⭐ ***THE TWO ACCEPTABLE ANSWERS:***
⭐   ⭐ ① ⭐⭐ ***INTEGER MINOR UNITS*** — pence, cents, satoshi.
⭐     ⭐ `amount_pence: int`. ⭐⭐ EXACT, FAST, TRIVIAL TO STORE,
⭐     AND MY DEFAULT.
⭐     ⭐ ⭐⭐ THE CATCH: DIVISION. ⭐ Splitting 100p three ways is
⭐       33 + 33 + 34, ⭐⭐ AND ***WHO GETS THE EXTRA PENNY*** IS A
⭐       BUSINESS RULE YOU MUST ASK ABOUT, NOT A ROUNDING MODE
⭐       YOU PICK.
⭐   ⭐ ② ***`decimal.Decimal`*** — ⭐ base-10, exact for money,
⭐     ⭐ explicit rounding contexts. ⭐⭐ NECESSARY FOR INTEREST,
⭐     FX AND ANYTHING WITH FRACTIONAL RATES.
⭐     ⭐ ⭐⭐ ALWAYS CONSTRUCT FROM A ***STRING***: `Decimal("0.1")`.
⭐       ⭐ `Decimal(0.1)` inherits the float's error and is
⭐       ⭐⭐ THE MOST COMMON DECIMAL BUG THERE IS.

⭐ ***AND THE THING THAT IS NOT OPTIONAL: ⭐⭐ CURRENCY TRAVELS
⭐   WITH THE AMOUNT.***
⭐   ⭐ A bare `int` is a bug waiting to add pounds to euros.
⭐   ⭐ ⭐⭐ A `Money` VALUE OBJECT THAT ***REFUSES*** TO ADD
⭐     DIFFERENT CURRENCIES TURNS A CLASS OF FINANCIAL INCIDENT
⭐     INTO A `TypeError` AT THE POINT OF THE MISTAKE.
```

```python
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class Money:
    pence: int
    currency: str = "GBP"

    def __post_init__(self):
        if not isinstance(self.pence, int):     # ⭐⭐ NO FLOATS IN
            raise TypeError("money must be integer minor units")

    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:     # ⭐⭐ THE WHOLE POINT
            raise ValueError(f"{self.currency} + {other.currency}")
        return Money(self.pence + other.pence, self.currency)
```

# Part 2 — ⭐⭐ Double-entry: the balance is derived

```
⭐ ***THE DESIGN THAT FAILS:*** ⭐ a `balance` column, updated on
⭐   every transaction.
⭐   ⭐ ⭐⭐ IT WORKS PERFECTLY UNTIL IT DOESN'T, AND THEN IT IS
⭐     UNRECOVERABLE: ⭐ if the balance is wrong, ***you cannot
⭐     tell***, because there is nothing to check it against.
⭐   ⭐ ⭐⭐ NO HISTORY, NO AUDIT, NO ANSWER TO "WHY IS THIS
⭐     £4.20?"

⭐ ✅ ***DOUBLE-ENTRY: STORE THE ***MOVEMENTS***.***
⭐   ⭐ Every transaction writes ***two or more*** entries that
⭐     ⭐⭐ SUM TO EXACTLY ZERO.
⭐   ⭐ A transfer of £10 from Alice to Bob:
⭐     ⭐ `(txn_1, alice, -1000)` and `(txn_1, bob, +1000)`
⭐   ⭐ ⭐⭐ THE BALANCE IS `SELECT SUM(amount) WHERE account = ?`.

⭐ ***THE FOUR PROPERTIES THIS BUYS — SAY ALL FOUR:***
⭐   ⭐ ① ⭐⭐ ***ERRORS BECOME DETECTABLE.*** ⭐ The sum of ***all***
⭐     entries in the system must be zero. ⭐⭐ A NIGHTLY JOB THAT
⭐     CHECKS THIS FINDS BUGS THAT NO TEST WOULD — ⭐ it is the
⭐     single strongest argument for the pattern.
⭐   ⭐ ② ***complete audit trail*** — ⭐ every penny traceable to
⭐     a transaction, which is a regulatory requirement rather
⭐     than a nicety.
⭐   ⭐ ③ ⭐⭐ ***NO LOST UPDATES BY CONSTRUCTION*** — ⭐ entries are
⭐     ***inserts***, and two concurrent inserts do not overwrite
⭐     each other. ⭐⭐ THE READ-MODIFY-WRITE RACE SIMPLY DOES NOT
⭐     EXIST.
⭐   ⭐ ④ ***money is conserved*** — ⭐ you cannot create or
⭐     destroy value by accident, ⭐⭐ BECAUSE AN UNBALANCED
⭐     TRANSACTION IS REJECTED BY A CONSTRAINT.

⭐ ***AND THE COST, WHICH YOU MUST VOLUNTEER:***
⭐   ⭐ ⭐⭐ READING A BALANCE IS NOW AN AGGREGATION OVER MILLIONS
⭐     OF ROWS.
⭐   ⭐ ⇒ a ***materialised balance*** as a cached projection,
⭐     ⭐ updated in the same transaction, ⭐⭐ AND RECONCILED
⭐     NIGHTLY AGAINST THE SUM.
⭐   ⭐ ⭐⭐ THAT IS DERIVED STATE (D412): IT MUST BE REBUILDABLE,
⭐     AND YOU MUST HAVE REBUILT IT. ⭐ The reconciliation job is
⭐     not optional bookkeeping — ⭐⭐ IT IS THE MECHANISM THAT
⭐     MAKES PROPERTY ① REAL.
```

```sql
CREATE TABLE entries (
  id           bigserial PRIMARY KEY,
  txn_id       uuid        NOT NULL,        -- ⭐ groups the pair
  account_id   uuid        NOT NULL,
  amount_pence bigint      NOT NULL,        -- ⭐⭐ SIGNED
  currency     char(3)     NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON entries (account_id, id);
CREATE UNIQUE INDEX ON entries (txn_id, account_id);  -- ⭐⭐ IDEMPOTENCY

-- ⭐⭐ THE INVARIANT, ENFORCED RATHER THAN HOPED FOR:
-- every txn_id must sum to zero. Checked per-transaction in a
-- trigger or a constraint trigger, AND globally by the nightly
-- reconciliation.
```

# Part 3 — ⭐⭐ The transfer, and the ordered-lock deadlock

```
⭐ ***THE CLASSIC DEADLOCK, AND IT IS A GUARANTEED FOLLOW-UP:***
⭐   ⭐ Thread 1: transfer A → B. Locks A, then wants B.
⭐   ⭐ Thread 2: transfer B → A. Locks B, then wants A.
⭐   ⭐ ⭐⭐ NEITHER PROCEEDS. FOREVER.

⭐ ⭐⭐ THE FIX: ***ACQUIRE LOCKS IN A GLOBAL TOTAL ORDER.***
⭐   ⭐ Sort the two account ids and always lock the smaller
⭐     first, ⭐⭐ REGARDLESS OF THE DIRECTION OF THE TRANSFER.
⭐   ⭐ ⭐⭐ THEN A CYCLE IS ***STRUCTURALLY IMPOSSIBLE***, ⭐ because
⭐     a cycle requires two threads to disagree about ordering,
⭐     and they cannot.
⭐   ⭐ ⭐ This generalises: ***any*** deadlock caused by lock
⭐     ordering is fixed by imposing a total order, ⭐⭐ AND THE
⭐     ORDER JUST HAS TO BE CONSISTENT — IT DOES NOT HAVE TO BE
⭐     MEANINGFUL.

⭐ ***IN A DATABASE, THE SAME BUG WEARS A DIFFERENT HAT:***
⭐   ⭐ `SELECT … FOR UPDATE` on two rows in inconsistent order
⭐     deadlocks the same way. ⭐⭐ POSTGRES DETECTS IT AND KILLS
⭐     ONE TRANSACTION, ⭐ which is better than hanging —
⭐     ⭐⭐ BUT IT IS STILL AN ERROR YOUR CODE MUST RETRY, ⭐ so
⭐     order the `FOR UPDATE` by account id anyway.

⭐ ***AND THE BETTER ANSWER, WHICH IS TO NEED FEWER LOCKS:***
⭐   ⭐ ⭐⭐ WITH DOUBLE-ENTRY, THE ***WRITE*** NEEDS NO LOCK AT ALL
⭐     — ⭐ it is two inserts in one transaction.
⭐   ⭐ ⭐⭐ THE ONLY THING NEEDING SERIALISATION IS THE
⭐     ***SUFFICIENT-FUNDS CHECK***, ⭐ and even that is better
⭐     expressed as a constraint than as a lock (Part 4).
```

```python
import threading
from contextlib import ExitStack

_locks: dict[str, threading.Lock] = {}
_locks_guard = threading.Lock()

def _lock_for(account_id: str) -> threading.Lock:
    with _locks_guard:                       # ⭐ Day 479's pattern
        return _locks.setdefault(account_id, threading.Lock())

def transfer(src: str, dst: str, amount: Money, txn_id: str) -> None:
    if src == dst:
        raise ValueError("self-transfer")    # ⭐⭐ ASK ABOUT THIS CASE
    # ⭐⭐ THE ENTIRE DEADLOCK FIX IS THIS ONE `sorted` CALL.
    first, second = sorted((src, dst))
    with ExitStack() as stack:
        stack.enter_context(_lock_for(first))
        stack.enter_context(_lock_for(second))
        if balance_of(src) < amount:
            raise InsufficientFunds(src)
        append_entries(txn_id, [(src, -amount.pence),
                                (dst, +amount.pence)])
```

```
⭐ ⭐⭐ NOTE THE UNBOUNDED `_locks` DICT — ⭐ one lock per account
⭐   forever is a slow memory leak on a system with many accounts.
⭐   ⭐ ⭐⭐ SAY IT UNPROMPTED: ⭐ "this leaks a lock per account;
⭐     in production I'd use a fixed pool of N locks selected by
⭐     `hash(account) % N`, ⭐⭐ WHICH BOUNDS MEMORY AND ONLY COSTS
⭐     FALSE CONTENTION BETWEEN UNRELATED ACCOUNTS."
```

# Part 4 — ⭐⭐ Put correctness in the resource

```
⭐ ***THE SUFFICIENT-FUNDS CHECK IS CHECK-THEN-ACT*** (Day 479)
⭐   — ⭐ read the balance, decide, write.
⭐   ⭐ ⭐⭐ IN A SINGLE PROCESS, A LOCK FIXES IT. ⭐ Across
⭐     processes, ***an in-process lock is meaningless.***

⭐ ***THE ESCALATION, IN ORDER — AND EACH STEP MOVES CORRECTNESS
⭐   CLOSER TO THE DATA:***
⭐   ⭐ ① ***in-process lock*** — ⭐ one instance only.
⭐   ⭐ ② ***`SELECT … FOR UPDATE`*** on the account row —
⭐     ⭐⭐ PESSIMISTIC, CORRECT ACROSS PROCESSES, ⭐ serialises
⭐     that account.
⭐   ⭐ ③ ***optimistic — a `version` column*** with a conditional
⭐     update. ⭐⭐ BETTER UNDER LOW CONTENTION; ⭐ retry on
⭐     conflict.
⭐   ⭐ ④ ⭐⭐ ***A CHECK CONSTRAINT ON THE MATERIALISED BALANCE***
⭐     — `CHECK (balance_pence >= 0)`.
⭐     ⭐ ⭐⭐ NOW OVERDRAWING IS ***STRUCTURALLY IMPOSSIBLE***: THE
⭐       DATABASE REFUSES THE WRITE, WHATEVER YOUR APPLICATION
⭐       CODE BELIEVES. ⭐ Every bug, race and future refactor is
⭐       covered by one line of DDL.

⭐ ⭐⭐ ④ IS THE ANSWER THAT ENDS THE TOPIC: ⭐ ***correctness
⭐   lives in the resource, not in the coordinator*** (D412), and
⭐   a constraint has no false-negative rate the way a check does
⭐   (D448).

⭐ ***IDEMPOTENCY — THE SAME MOVE:***
⭐   ⭐ the client sends a `txn_id`; ⭐ the unique index on
⭐     `(txn_id, account_id)` makes a replay ***fail rather than
⭐     double-spend***.
⭐   ⭐ ⭐⭐ THE DATABASE DECIDES, NOT YOUR CONTROL FLOW — ⭐ so a
⭐     retry after a timeout is safe by construction, which is
⭐     Day 444's rule applied to money.
```

# 💬 Interview

**1. "Design a wallet."**

⭐ Before anything: money is integer minor units or `Decimal`, never a float, and currency travels with
the amount. ⭐⭐ Then the core decision — I wouldn't store a balance and update it. I'd store the
movements as a double-entry ledger where every transaction writes entries summing to zero, and the
balance becomes `SELECT SUM(amount)`. ⭐ The reason isn't elegance: ⭐⭐ a stored balance has no way to
detect its own corruption. If it's wrong, there's nothing to check it against. ⭐ With entries, the sum
of everything in the system must be zero, so a nightly reconciliation finds bugs no test would.

**2. "That's slow to read."**

⭐ It is, and I'd volunteer that rather than wait for it. ⭐⭐ Reading a balance becomes an aggregation
over millions of rows, so I'd keep a materialised balance updated in the same transaction as the entries.
⭐ But that's derived state, so it has to be rebuildable and reconciled — and the reconciliation job
isn't bookkeeping, it's the mechanism that makes the error-detection property real. ⭐⭐ If the
materialised balance ever disagrees with the sum, I have a bug *and* I know about it, which is the entire
point. ⭐ A system where those can silently diverge has given up the benefit.

**3. "Two simultaneous transfers between the same pair of accounts."**

⭐ That's the deadlock: one thread locks A then wants B, the other locks B then wants A. ⭐⭐ The fix is
acquiring locks in a global total order — sort the account ids and always take the smaller first,
regardless of transfer direction. ⭐ Then a cycle is structurally impossible, because a cycle requires two
threads to disagree about ordering and they can't. ⭐⭐ The order doesn't have to be meaningful, only
consistent. ⭐ Same bug appears in the database with `SELECT FOR UPDATE` on two rows — Postgres detects
it and kills one transaction rather than hanging, which is better, but it's still an error you have to
retry, so I'd order the `FOR UPDATE` by account id anyway.

**4. "Do you even need locks?"**

⭐ Less than you'd think, and that's the better answer. ⭐⭐ With double-entry the *write* needs no lock at
all — it's two inserts in one transaction, and concurrent inserts don't overwrite each other, so the
read-modify-write race simply doesn't exist. ⭐ The only thing needing serialisation is the
sufficient-funds check, which is check-then-act. ⭐⭐ And even that is better as a constraint than a
lock: `CHECK (balance_pence >= 0)` on the materialised balance makes overdrawing structurally impossible
regardless of what my application code believes. ⭐ One line of DDL covers every race, every bug, and
every future refactor — correctness in the resource rather than the coordinator.

**5. "The client retries a transfer after a timeout."**

⭐ The client sends a transaction id, and there's a unique index on `(txn_id, account_id)`. ⭐⭐ A replay
fails on the constraint rather than double-spending — the database decides, not my control flow. ⭐ Which
matters because the timeout case is exactly the one where I don't know whether the first attempt
succeeded. ⭐⭐ And the id has to come from the client at the point of intent, not be generated inside my
service, because a service-generated id would be different on each retry and the constraint would never
fire.

**6. "Split £100 three ways."**

⭐ 33, 33 and 34 pence over, and the interesting question is who gets the extra penny. ⭐⭐ That's a
business rule, not a rounding mode — it might be the first payee, the largest, the platform, or rotated
for fairness — and I'd ask rather than pick. ⭐ What I wouldn't do is use floats and let the error land
somewhere arbitrary. ⭐⭐ And whichever rule we choose, the remainder still has to appear as an entry, or
the transaction doesn't sum to zero and my invariant catches it — which is a nice demonstration that the
ledger enforces the thing I care about.

**7. "What did the four LLD rounds have in common?"**

⭐ Four shapes. ⭐⭐ Ask what varies and make only that pluggable — pricing in the parking lot, templates
in notifications, the loader in the cache, and in the wallet *nothing* varies, so I'd say that rather
than add abstraction. ⭐ Every round had a check-then-act hiding in it — spot allocation, dedup, cache
fill, sufficient funds — so I now go looking for it before the interviewer does. ⭐⭐ Push correctness
into the resource: a unique index, a conditional update, a check constraint. ⭐ And make the dangerous
thing impossible rather than remembered — frozen tickets, required idempotency keys, a `Money` type that
refuses mixed currencies, sorted lock acquisition.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "design a wallet."**

Open with the thing that must be said first. **"Two decisions before any structure. Money is integer
minor units or Decimal, never a float — 0.1 plus 0.2 isn't 0.3 in binary, and across millions of
transactions that error accumulates into something a regulator can see. And currency travels with the
amount in a value object that refuses to add GBP to EUR, which turns a class of financial incident into
a TypeError at the point of the mistake."**

Then the core design, argued from failure. **"I wouldn't store a balance and update it. I'd store the
movements — double entry, where every transaction writes entries summing to zero, and the balance is a
sum. The reason isn't elegance: a stored balance has no way to detect its own corruption. If it's wrong,
there's nothing to check it against. With entries, every transaction sums to zero and the whole system
sums to zero, so a nightly reconciliation finds bugs that no test would. You also get a complete audit
trail, and the read-modify-write race disappears entirely, because entries are inserts and concurrent
inserts don't overwrite each other."**

Then volunteer the cost. **"What it costs is read performance — a balance becomes an aggregation over
millions of rows. So I'd materialise the balance in the same transaction and reconcile it nightly against
the sum. That's derived state, so it has to be rebuildable, and the reconciliation isn't bookkeeping,
it's the mechanism that makes the error-detection property real."**

Close on concurrency, with the better answer last. **"The classic follow-up is two simultaneous transfers
between the same pair of accounts, which deadlocks — one locks A then wants B, the other the reverse. The
fix is one `sorted` call: acquire in a global total order, always the lower account id first, so a cycle
becomes structurally impossible. But the better answer is needing fewer locks. The write needs none. The
only thing requiring serialisation is the sufficient-funds check, and that's better as a check constraint
than a lock — one line of DDL that makes overdrawing impossible whatever my application code believes.
That's correctness in the resource rather than the coordinator."**
