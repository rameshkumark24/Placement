# Day 363 🏗️

**P-363** · 🏗️ **Multi-stage builds, image size, and scanning**

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a multi-stage build exists so the tools that *create* your artefact never
> ship with it — and for Python that means a build stage with a compiler producing a virtualenv, and a
> runtime stage that copies one directory and has no compiler, no package manager and often no shell
> at all.**

---

# Part 1 — ⭐⭐ The problem multi-stage solves

```
⭐⭐ A SINGLE-STAGE PYTHON IMAGE WITH ANY C EXTENSION CONTAINS:
⭐   ⭐ gcc, g++, make, ⭐ Python headers, ⭐ libpq-dev,
⭐     libjpeg-dev, libffi-dev, ⭐ the pip wheel cache, ⭐ apt
⭐     lists, ⭐ and your source tree including tests.
⭐   ⇒ ⭐⭐ 800 MB–1.2 GB, OF WHICH PERHAPS 200 MB IS NEEDED AT
⭐     RUNTIME.

⭐⭐ AND THE COST IS NOT MAINLY SIZE — ⭐ say all four:
⭐   ① ⭐⭐ ATTACK SURFACE: an attacker with execution now has a
⭐      compiler, a package manager and curl. ⭐ They can build
⭐      and fetch tooling ***in place***.
⭐   ② ⭐⭐ CVE NOISE: two hundred findings in packages your
⭐      application never calls. ⭐ The real one is buried, and
⭐      the team learns to ignore the report — ⭐⭐ WHICH IS THE
⭐      ACTUAL DAMAGE.
⭐   ③ ⭐ Pull latency on every new node and every scale-out.
⭐   ④ ⭐ Registry storage and transfer cost.

⭐⭐ THE SHAPE:
⭐   ⭐ ***STAGE 1 (builder)*** — has the compilers, produces an
⭐     artefact.
⭐   ⭐ ***STAGE 2 (runtime)*** — starts from a minimal base and
⭐     ⭐⭐ COPIES ***ONLY THE ARTEFACT***.
⭐   ⇒ ⭐⭐ ONLY THE FINAL STAGE'S LAYERS ARE IN THE SHIPPED
⭐     IMAGE. ⭐ Everything in the builder is discarded — ⭐⭐ AND
⭐     UNLIKE `RUN rm` (Day 362), IT IS GENUINELY GONE, BECAUSE
⭐     THOSE LAYERS ARE NEVER PART OF THE FINAL MANIFEST.
```

# Part 2 — ⭐⭐ The Python multi-stage build, done properly

```dockerfile
# syntax=docker/dockerfile:1.7
# ⭐⭐ STAGE 1 — BUILD. Compilers live here and die here.
FROM python:3.12-slim@sha256:... AS builder

ENV PIP_DISABLE_PIP_VERSION_CHECK=1 \
    PYTHONDONTWRITEBYTECODE=1

RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential libpq-dev \
    && rm -rf /var/lib/apt/lists/*        # ⭐ same RUN, or it's a layer

# ⭐⭐ A VENV IS ONE DIRECTORY — WHICH IS WHY IT IS THE RIGHT
# ⭐   ARTEFACT FOR A MULTI-STAGE BUILD.
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

COPY requirements.lock .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --require-hashes -r requirements.lock   # ⭐⭐ HASHES

# ⭐⭐ STAGE 2 — RUNTIME. No compiler. No package manager.
FROM python:3.12-slim@sha256:... AS runtime

RUN apt-get update && apt-get install -y --no-install-recommends \
        libpq5 \
    && rm -rf /var/lib/apt/lists/* \
    && useradd -u 10001 -m -s /usr/sbin/nologin app     # ⭐ numeric UID

COPY --from=builder /opt/venv /opt/venv                 # ⭐⭐ ONE COPY
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

WORKDIR /app
COPY --chown=10001:10001 app/ ./app/                    # ⭐ Day 362
RUN python -m compileall -q /app /opt/venv              # ⭐⭐ COLD START

USER 10001
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```
⭐⭐ THE FIVE DECISIONS IN THAT FILE, EACH WORTH STATING:
⭐   ① ⭐⭐ `libpq-dev` IN THE BUILDER, `libpq5` IN THE RUNTIME.
⭐      ⭐ The `-dev` package is headers for compiling; the
⭐      runtime needs only the shared library. ⭐⭐ GETTING THIS
⭐      PAIRING RIGHT IS MOST OF THE SIZE SAVING, AND MOST
⭐      PEOPLE COPY THE `-dev` PACKAGE INTO BOTH STAGES.
⭐   ② ⭐ The venv as the transfer unit — ⭐ one `COPY`, no
⭐      hunting through site-packages.
⭐   ③ ⭐⭐ `--require-hashes` ⇒ A SUBSTITUTED PACKAGE VERSION
⭐      FAILS THE BUILD RATHER THAN SHIPPING.
⭐   ④ ⭐ `compileall` in the runtime stage ⇒ Day 362's
⭐      cold-start point, ⭐⭐ AND IT MUST BE ***AFTER*** THE
⭐      SOURCE COPY.
⭐   ⑤ ⭐ Numeric `USER` last, so earlier `RUN`s can still write.

⭐⭐ AND THE BUG THIS SHAPE STILL HAS, WHICH IS WORTH KNOWING:
⭐   ⭐ ⭐⭐ THE VENV HARD-CODES THE PYTHON PATH IT WAS BUILT
⭐     WITH. ⭐ Builder and runtime must have the ***same***
⭐     Python minor version and the same base — ⭐⭐ OR THE VENV
⭐     POINTS AT AN INTERPRETER THAT DOES NOT EXIST, AND YOU GET
⭐     A CONFUSING FAILURE AT STARTUP. ⭐ Same base image, same
⭐     digest ideally.
```

# Part 3 — ⭐ Other stage patterns worth knowing

```
⭐⭐ ① ***A TEST STAGE THAT GATES THE BUILD.***
⭐   ⭐ `FROM builder AS test` → `RUN pytest -q`
⭐   ⇒ ⭐⭐ THE BUILD ***FAILS*** IF TESTS FAIL, AND THE TEST
⭐     DEPENDENCIES NEVER REACH THE RUNTIME IMAGE.
⭐   ⇒ ⭐ Caveat: ⭐⭐ WITH BUILDKIT, UNREFERENCED STAGES ARE
⭐     ***SKIPPED*** — so a test stage nothing depends on will
⭐     not run unless you `--target test` it explicitly in CI.
⭐     ⭐ That surprises people who think they have a gate.

⭐⭐ ② ***A DEV STAGE AND A PROD STAGE IN ONE FILE.***
⭐   ⭐ `--target dev` adds `pytest`, `ipdb`, `watchfiles`;
⭐     ⭐ `--target prod` does not.
⭐   ⇒ ⭐⭐ ONE DOCKERFILE, TWO IMAGES, AND ***THE SAME BASE AND
⭐     THE SAME DEPENDENCY RESOLUTION*** — which removes the
⭐     "works in dev" class of bug at its root.

⭐⭐ ③ ***COPYING FROM AN EXTERNAL IMAGE.***
⭐   ⭐ `COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv`
⭐   ⇒ ⭐ Grab one binary from a published image without
⭐     installing anything.

⭐⭐ ④ ***PARALLEL STAGES.*** ⭐ BuildKit builds independent
⭐   stages concurrently — ⭐⭐ SO A FRONTEND BUILD AND A PYTHON
⭐   DEPENDENCY INSTALL RUN AT THE SAME TIME AND THE BUILD IS AS
⭐   SLOW AS THE SLOWER ONE, NOT THEIR SUM.

⭐⭐ AND THE `uv` NOTE, BECAUSE IT IS CURRENT AND WORTH ONE
⭐   SENTENCE: ⭐⭐ `uv` RESOLVES AND INSTALLS PYTHON
⭐   DEPENDENCIES 10–100× FASTER THAN pip, ⭐ which turns a
⭐   90-second dependency layer into a few seconds on a cache
⭐   miss. ⭐ Mentioning it signals you have built images
⭐   recently.
```

# Part 4 — ⭐⭐ Distroless and the debugging trade

```
⭐⭐ ***DISTROLESS*** = the runtime and its shared libraries,
⭐   ⭐⭐ AND NOTHING ELSE. ⭐ No shell, no `apt`, no `curl`, no
⭐   `ls`, no package manager.

⭐⭐ WHAT IT BUYS:
⭐   ⭐ ⭐⭐ AN ATTACKER WITH CODE EXECUTION HAS NO SHELL TO
⭐     SPAWN AND NO TOOLS TO FETCH MORE. ⭐ It does not stop the
⭐     RCE; ⭐⭐ IT MAKES THE ***NEXT STEP*** MUCH HARDER, WHICH
⭐     IS WHAT DEFENCE IN DEPTH ACTUALLY MEANS.
⭐   ⭐ CVE counts drop by an order of magnitude, ⭐⭐ SO THE
⭐     REPORT BECOMES READABLE AND THEREFORE ACTUALLY READ.
⭐   ⭐ `nonroot` variants exist and should be the default.

⭐⭐ WHAT IT COSTS — ⭐ and be honest about all of it:
⭐   ⭐ ⭐⭐ NO `docker exec sh`. ⭐ Debugging needs `kubectl
⭐     debug` / `docker debug`, which attaches a ***separate***
⭐     container sharing the namespaces (Day 361). ⭐ It works
⭐     well and it is unfamiliar, so ⭐⭐ REHEARSE IT ***BEFORE***
⭐     AN INCIDENT, NOT DURING ONE.
⭐   ⭐ ⭐⭐ NO SHELL MEANS ENTRYPOINT SCRIPTS DO NOT WORK. ⭐ Any
⭐     `entrypoint.sh` doing migrations or env templating must
⭐     become Python, an init container, or a separate job.
⭐   ⭐ Healthchecks that shell out (`CMD curl …` in a
⭐     `HEALTHCHECK`) break — ⭐ use the orchestrator's HTTP
⭐     probe instead, which you should be doing anyway.
⭐   ⭐ ⭐⭐ AND FOR PYTHON SPECIFICALLY: DISTROLESS PYTHON PINS
⭐     A PYTHON VERSION YOU DO NOT CONTROL, WHICH CAN LAG. ⭐ A
⭐     common alternative is `-slim` with everything unnecessary
⭐     removed, ⭐ or Chainguard's Python images.

⭐⭐ ⇒ THE JUDGEMENT: ⭐⭐ DISTROLESS FOR ANYTHING
⭐   INTERNET-FACING OR HANDLING SENSITIVE DATA; `-slim` IS A
⭐   PERFECTLY DEFENSIBLE DEFAULT ELSEWHERE. ⭐ Saying "it
⭐   depends on whether the team can debug it at 3 a.m." is the
⭐   mature version of the answer.
```

# Part 5 — ⭐⭐ What a CVE report actually means

```
⭐⭐ RUN `trivy image myapp:1.4.2` AND YOU GET 180 FINDINGS.
⭐   ⭐⭐ MOST TEAMS' RESPONSE IS TO IGNORE THE REPORT, WHICH IS
⭐   THE WORST POSSIBLE OUTCOME. ⭐ The fix is triage, not
⭐   volume reduction alone.

⭐⭐ THE FOUR QUESTIONS PER FINDING:
⭐   ① ⭐⭐ IS THE VULNERABLE ***CODE PATH*** REACHABLE FROM MY
⭐      APPLICATION? ⭐ A CVE in a video codec in a library you
⭐      import for CSV parsing is not your emergency.
⭐   ② ⭐ Is it remotely triggerable, or does it need local
⭐      access I have already lost?
⭐   ③ ⭐ Is there a fix available? ⭐⭐ IF NOT, THE DECISION IS
⭐      MITIGATE-OR-ACCEPT, AND IT NEEDS AN OWNER AND A DATE.
⭐   ④ ⭐ What is the actual exposure — internet-facing, or an
⭐      internal batch job?

⭐⭐ THE POLICY THAT WORKS IN PRACTICE:
⭐   ⭐ ⭐⭐ FAIL THE BUILD ON ***CRITICAL AND HIGH WITH A FIX
⭐     AVAILABLE***. ⭐ That is actionable by definition: there
⭐     is a version to move to.
⭐   ⭐ Report medium and low; ⭐ do not block on them.
⭐   ⭐ ⭐⭐ ALLOW TIME-BOXED EXCEPTIONS WITH AN OWNER AND AN
⭐     EXPIRY DATE — ⭐ a `.trivyignore` entry with a date and a
⭐     name, ⭐⭐ AND A CHECK THAT FAILS WHEN AN EXCEPTION
⭐     EXPIRES. ⭐ Without the expiry, the ignore file becomes
⭐     the place findings go to die.
⭐   ⇒ ⭐⭐ AND THE STRUCTURAL POINT: ***MOST FINDINGS COME FROM
⭐     THE BASE IMAGE, NOT YOUR CODE.*** ⭐ So the highest-value
⭐     control is an automated base-image bump, ⭐ not a
⭐     per-finding argument.

⭐⭐ AND THE THREE SCANNER TYPES, BECAUSE THEY ANSWER DIFFERENT
⭐   QUESTIONS:
⭐   ⭐ ***IMAGE/OS + DEPENDENCY*** (Trivy, Grype) ⇒ known CVEs
⭐     in packages.
⭐   ⭐ ***SAST*** (bandit, semgrep, CodeQL) ⇒ patterns in
⭐     ***your*** code.
⭐   ⭐ ⭐⭐ ***SECRET SCANNING*** (gitleaks, trufflehog) ⇒ ⭐ and
⭐     this is the one that catches real incidents most often,
⭐     ⭐⭐ BECAUSE A LEAKED CREDENTIAL IS EXPLOITED IN MINUTES
⭐     AND NEEDS NO EXPLOIT AT ALL.
```

# Part 6 — ⭐ Getting the image small, in order of effect

```
⭐⭐ THE LEVERS, LARGEST FIRST:
⭐   ① ⭐⭐ MULTI-STAGE (drop the toolchain) ⇒ ⭐ typically
⭐      −400 to −700 MB. ⭐ Everything else is rounding after
⭐      this.
⭐   ② ⭐ `-slim` base rather than full ⇒ −850 MB.
⭐   ③ ⭐ `--no-install-recommends` + `rm -rf
⭐      /var/lib/apt/lists/*` ***in the same `RUN`*** ⇒
⭐      ⭐⭐ TENS OF MB, AND ONLY IF IT IS THE SAME `RUN` —
⭐      otherwise you added a layer instead of removing one.
⭐   ④ ⭐ pip cache mount instead of a baked cache ⇒ −100 to
⭐      −300 MB.
⭐   ⑤ ⭐ `.dockerignore` (tests, fixtures, `.git`, docs) ⇒
⭐      ⭐⭐ SOMETIMES HUNDREDS OF MB, AND IT IS FREE.
⭐   ⑥ ⭐ Distroless ⇒ a further −80 MB and most of the CVEs.

⭐⭐ AND THE ANTI-PATTERN THAT LOOKS CLEVER:
⭐   ⭐ ⭐⭐ CHAINING ***EVERYTHING*** INTO ONE ENORMOUS `RUN`
⭐     TO "MINIMISE LAYERS". ⭐ It does reduce layer count —
⭐     ⭐⭐ AND IT DESTROYS THE BUILD CACHE, SO EVERY BUILD
⭐     REDOES EVERYTHING.
⭐   ⇒ ⭐⭐ LAYER ***COUNT*** IS NOT A METRIC WORTH OPTIMISING.
⭐     LAYER ***CONTENT*** AND ***ORDER*** ARE. ⭐ Chain only
⭐     what must be atomic to avoid leaving artefacts behind
⭐     (apt update+install+clean).

⭐⭐ THE TARGET FOR A TYPICAL PYTHON API: ⭐⭐ 150–250 MB WITH
⭐   `-slim`, ⭐ 80–120 MB DISTROLESS. ⭐ If you are at 1 GB,
⭐   the toolchain is still in there.
```

# Part 7 — ⭐ Reproducibility, and how far to take it

```
⭐⭐ "REPRODUCIBLE" HAS DEGREES, AND KNOWING WHICH ONE YOU NEED
⭐   IS THE POINT:
⭐   ① ⭐ ***SAME DEPENDENCIES*** — a lockfile with hashes.
⭐        ⭐⭐ THIS IS THE ONE THAT MATTERS AND MOST TEAMS SKIP
⭐        IT.
⭐   ② ⭐ ***SAME BASE*** — pinned by digest.
⭐   ③ ⭐ ***SAME SYSTEM PACKAGES*** — pin apt versions, or
⭐        accept drift within a base image generation.
⭐   ④ ⭐⭐ ***BIT-IDENTICAL IMAGE*** — needs
⭐        `SOURCE_DATE_EPOCH`, deterministic ordering, no
⭐        timestamps. ⭐⭐ RARELY WORTH IT UNLESS YOU ARE
⭐        PUBLISHING SOFTWARE OTHERS VERIFY.
⭐   ⇒ ⭐⭐ SAY WHICH LEVEL YOU ARE AT AND WHY. ⭐ "Levels one and
⭐     two, because that removes the failure modes I actually
⭐     hit, and bit-identical would cost more than it returns"
⭐     is a complete answer.

⭐⭐ AND THE PROVENANCE LAYER ON TOP:
⭐   ⭐ ⭐⭐ BUILD ATTESTATION + SBOM + SIGNATURE ⇒ "this image
⭐     came from this commit, built by this pipeline, contains
⭐     these packages."
⭐   ⇒ ⭐ `docker buildx build --provenance=true --sbom=true`
⭐     is one flag pair, ⭐ and `cosign sign` is one command.
⭐   ⇒ ⭐⭐ THE VALUE IS NOT THE PAPERWORK — IT IS THAT
⭐     ADMISSION CONTROL CAN ***REFUSE*** ANYTHING UNSIGNED,
⭐     TURNING A POLICY INTO A MECHANISM (Day 362).
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Shipping the compiler in the runtime image | An attacker with execution can build and fetch tooling in place |
| ⭐⭐ `-dev` packages in the runtime stage | You need `libpq5`, not `libpq-dev`. This is most of the size saving |
| ⭐ Different Python versions in builder and runtime | The venv hard-codes its interpreter path and fails confusingly at startup |
| ⭐⭐ A test stage nothing references | BuildKit skips unreferenced stages. You think you have a gate and you don't |
| ⭐ `apt-get clean` in a separate `RUN` | You added a layer instead of removing content. Same `RUN`, always |
| ⭐⭐ Chaining everything into one giant `RUN` | Reduces layer count and destroys the cache. Count isn't the metric |
| ⭐⭐ Ignoring the CVE report because it has 180 findings | The worst outcome. Triage on reachability and fix-availability instead |
| ⭐ Blocking builds on every medium and low | The team routes around the gate within a week |
| ⭐⭐ A `.trivyignore` with no expiry or owner | It becomes the place findings go to die |
| ⭐ Distroless without rehearsing debugging | You discover you can't `exec` into it during an incident |
| ⭐ Entrypoint shell scripts with distroless | There's no shell. Migrations become an init container or a job |
| ⭐⭐ No lockfile with hashes | A substituted package version ships silently |
| ⭐ Chasing bit-identical reproducibility | Expensive, and rarely the failure mode you actually hit |

## Interview questions

**1. "Why multi-stage?"**
> ⭐⭐ So the tools that create the artefact never ship with it. ⭐ A single-stage Python image with any C
> extension carries gcc, headers, `-dev` packages and a wheel cache — around a gigabyte, of which maybe
> two hundred megabytes is needed at runtime. ⭐⭐ And the cost isn't mainly size: **an attacker with
> execution gets a compiler and a package manager, and you get two hundred CVEs in packages your code
> never calls, so the report stops being read.** ⭐ Only the final stage's layers ship, so unlike `RUN
> rm`, the builder's contents are genuinely gone.

**2. "What's the Python-specific structure?"**
> ⭐ A builder stage with `build-essential` and `-dev` packages that creates a **virtualenv**, ⭐⭐ because
> **a venv is one directory, which makes it the right transfer unit** — the runtime stage is a single
> `COPY --from=builder /opt/venv /opt/venv`. ⭐ Runtime gets `libpq5` rather than `libpq-dev`, a numeric
> non-root user, and `compileall` after the source copy. ⭐⭐ And the trap: **the venv hard-codes its
> interpreter path, so builder and runtime must be the same Python version and ideally the same base
> digest.**

**3. "Distroless — worth it?"**
> ⭐ For anything internet-facing or handling sensitive data, yes. ⭐⭐ **It doesn't stop an RCE; it makes
> the next step much harder** — no shell to spawn, no package manager to fetch tools — and CVE counts
> drop by an order of magnitude, so the report becomes readable and therefore read. ⭐ The costs are
> real: no `exec sh`, so debugging is `kubectl debug` attaching a separate container — ⭐⭐ **which works
> well and must be rehearsed before an incident, not during one** — and entrypoint shell scripts have
> to become init containers or Python.

**4. "Your scanner reports 180 vulnerabilities. What do you do?"**
> ⭐⭐ Not ignore it, which is what most teams do and is the worst outcome. ⭐ Triage on four questions:
> is the vulnerable code path reachable from my application, is it remotely triggerable, is there a fix
> available, and what's the actual exposure. ⭐⭐ Then a policy that's actionable by definition: **fail
> the build on critical and high with a fix available**, report the rest. ⭐ Time-boxed exceptions with
> an owner and an expiry, and a check that fails when one expires. ⭐⭐ And the structural fix: **most
> findings come from the base image, so an automated base bump beats per-finding argument.**

**5. "How do you get a Python image small?"**
> ⭐ In order of effect: multi-stage to drop the toolchain, which is four to seven hundred megabytes and
> makes everything else rounding; `-slim` rather than full; `--no-install-recommends` with the apt
> cleanup **in the same `RUN`**; a pip cache mount rather than a baked cache; a real `.dockerignore`;
> and distroless. ⭐⭐ And the anti-pattern: **chaining everything into one giant `RUN` to minimise layer
> count destroys the cache — layer count isn't a metric worth optimising, content and order are.**
> ⭐ Target is 150–250 MB slim; at a gigabyte, the toolchain is still in there.

**6. "How reproducible are your builds?"**
> ⭐ I'd name the level. ⭐⭐ **Same dependencies via a lockfile with hashes — which is the one that
> matters and most teams skip — and same base pinned by digest.** ⭐ System package pinning is a
> judgement call, and bit-identical builds need `SOURCE_DATE_EPOCH` and deterministic ordering, which
> is rarely worth it unless others verify your artefacts. ⭐ On top of that, provenance attestation, an
> SBOM and a signature — ⭐⭐ and the value isn't the paperwork, it's that **admission control can refuse
> anything unsigned, which turns a policy into a mechanism.**

## 🎙️ Articulation drill

**Two minutes.** State the purpose in one line: **a multi-stage build exists so the tools that create
your artefact never ship with it** — and unlike deleting files in a later layer, the builder's contents
are genuinely gone because those layers aren't in the final manifest. Give the Python shape: **a builder
with compilers and `-dev` headers producing a virtualenv, because a venv is one directory and therefore
the right transfer unit**, and a runtime stage that copies it and installs only the shared library —
`libpq5`, not `libpq-dev`, which is most of the size saving. Name the trap: **the venv hard-codes its
interpreter path, so builder and runtime must be the same Python.** Then reframe why size matters:
**it's not bandwidth, it's that an attacker with execution gets a compiler and a package manager, and
you get two hundred CVEs in code you never call — so the report stops being read, which is the real
damage.** On scanning, give a policy that's actionable by construction: **fail on critical and high
with a fix available, report the rest, allow time-boxed exceptions with an owner and an expiry** — and
note that most findings come from the base image, so an automated base bump beats arguing per finding.
Close on distroless with both halves: **it doesn't prevent an RCE, it makes the next step much harder**
— and it costs you `exec sh`, so you rehearse `kubectl debug` before the incident, not during it.
