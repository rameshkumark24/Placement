**P-254** · 🏗 **The domain layer** — ⭐⭐ the state machine as data, and tests that touch no database

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: the domain layer is the part of your system that would still be correct
> if you replaced Postgres with a filing cabinet — and the test of whether you built one is whether
> its test suite runs in under a second with no database, no network and no fixtures.**
>
> ⭐ Python makes this easier than most languages and therefore easier to skip. ⭐⭐ The pressure

# Part 1 — ⭐⭐ What belongs here, and the test for it

```
⭐⭐ IN THE DOMAIN:
⭐   ✅ ⭐ the state machine and its legal transitions
⭐   ✅ ⭐ invariants that are true regardless of storage
⭐   ✅ ⭐ value objects: Money, TimeWindow, Address
⭐   ✅ ⭐ calculations: an invoice total, a job's duration, a price
⭐   ✅ ⭐⭐ domain events: "what just became true"

⭐⭐ NOT IN THE DOMAIN:
⭐   ❌ ⭐ sessions, queries, `select()`, any SQLAlchemy import
⭐   ❌ ⭐ HTTP status codes, `Request`, `Depends`
⭐   ❌ ⭐ Celery, Redis, S3, the payment client
⭐   ❌ ⭐⭐ `datetime.now()` — ⭐⭐ TIME IS AN INPUT, NOT AN AMBIENT
⭐        FACT. A domain object that reads the clock cannot be tested at
⭐        a boundary, and every scheduling bug lives at a boundary.
⭐   ❌ ⭐ logging (⭐⭐ arguable, and the argument is worth having: a
⭐        domain that logs has an opinion about your observability stack)

⭐⭐ THE TEST, AND IT IS MECHANICAL: `import-linter` FAILS THE BUILD IF
⭐   `domain/` IMPORTS ANYTHING OUTWARD (Day 253). ⭐ If you cannot pass
⭐   it, the layer does not exist — you have a folder.
```

```
⭐⭐ THE HONEST OBJECTION, ANSWERED: "THIS IS OVER-ENGINEERING FOR A
⭐   CRUD APP." ⭐ Often true. ⭐⭐ HERE IS WHEN IT IS NOT:
⭐   ⭐ You have a state machine with more than four states. ✅
⭐   ⭐ The same rules are needed from THREE entry points — the API, a
⭐     background job, and a report. ✅
⭐   ⭐⭐ There is a rule you must be able to point at and say "that,
⭐     there, is the business rule" when someone asks. ✅
⭐   ⇒ ⭐⭐ IF ALL THREE ARE FALSE, PUT THE LOGIC IN THE SERVICE AND
⭐     MOVE ON. ⭐ Knowing when NOT to do this is worth as much as
⭐     knowing how.
```

# Part 2 — ⭐⭐ The state machine as data, not control flow

```python
# ⭐ domain/states.py
class JobState(StrEnum):
    DRAFT="draft"; SCHEDULED="scheduled"; DISPATCHED="dispatched"
    IN_PROGRESS="in_progress"; COMPLETED="completed"
    INVOICED="invoiced"; PAID="paid"; CANCELLED="cancelled"

class JobAction(StrEnum):
    SCHEDULE="schedule"; DISPATCH="dispatch"; START="start"
    COMPLETE="complete"; INVOICE="invoice"; PAY="pay"; CANCEL="cancel"

# ⭐⭐ ONE TABLE. NOT A CHAIN OF `if`s IN SIX MODULES.
TRANSITIONS: dict[tuple[JobState, JobAction], JobState] = {
    (JobState.DRAFT,       JobAction.SCHEDULE): JobState.SCHEDULED,
    (JobState.SCHEDULED,   JobAction.DISPATCH): JobState.DISPATCHED,
    (JobState.DISPATCHED,  JobAction.START):    JobState.IN_PROGRESS,
    (JobState.IN_PROGRESS, JobAction.COMPLETE): JobState.COMPLETED,
    (JobState.COMPLETED,   JobAction.INVOICE):  JobState.INVOICED,
    (JobState.INVOICED,    JobAction.PAY):      JobState.PAID,
    **{(s, JobAction.CANCEL): JobState.CANCELLED
       for s in (JobState.DRAFT, JobState.SCHEDULED, JobState.DISPATCHED)},
}
# ⭐⭐ `IN_PROGRESS` IS ABSENT FROM THE CANCEL SET, VISIBLY. That was
#    Day 249's `?`, and as data the answer is present rather than
#    implied by a missing `elif` nobody can find.

TERMINAL = {JobState.PAID, JobState.CANCELLED}
```

```
⭐⭐ FOUR THINGS THE TABLE GIVES YOU THAT `if`s DO NOT:
⭐  ① ⭐⭐ AN EXHAUSTIVE TEST FOR FREE — iterate every (state, action)
⭐     pair and assert allowed or rejected. ⭐ 8 × 7 = 56 cases, one
⭐     parametrised test, and a new state is a FAILING test rather than
⭐     a forgotten branch.
⭐  ② ⭐ THE API CAN PUBLISH IT — `GET /jobs/{id}` returns
⭐     `available_actions`, so the UI does not reimplement the machine
⭐     and then drift from it.
⭐  ③ ⭐ A DIAGRAM CAN BE GENERATED from it, which means the diagram
⭐     cannot be out of date.
⭐  ④ ⭐⭐ THE DATABASE CAN MIRROR IT — a `CHECK` on the status column,
⭐     so a bad `UPDATE` from psql cannot create a state your code has
⭐     never heard of.
```

```python
# ⭐ The behaviour, in one place:
@dataclass
class Job:
    id: JobId
    tenant_id: TenantId
    state: JobState
    work_items: list[WorkItem] = field(default_factory=list)

    def apply(self, action: JobAction, *, now: datetime) -> list[Event]:
        target = TRANSITIONS.get((self.state, action))
        if target is None:
            raise InvalidTransition(self.state, action)   # ⭐⭐ ONE place
        # ⭐⭐ GUARDS: rules that are legal-by-state and still forbidden
        if action is JobAction.INVOICE and not self.work_items:
            raise DomainError("cannot invoice a job with no work items")
        previous, self.state = self.state, target
        return [JobTransitioned(self.id, previous, target, at=now)]
        # ⭐⭐ `now` IS A PARAMETER. Time is an input (Part 1).
```

# Part 3 — ⭐ Value objects, and the two that earn their keep

```python
# ⭐⭐ MONEY. Day 041 and Day 187 said never a float; this is where you
#    make that structural rather than a habit.
@dataclass(frozen=True, slots=True)
class Money:
    cents: int
    def __post_init__(self):
        if self.cents < 0: raise ValueError("Money cannot be negative")
    def __add__(self, o: "Money") -> "Money": return Money(self.cents+o.cents)
    def __mul__(self, q: int) -> "Money":     return Money(self.cents*q)
# ⭐⭐ THE POINT IS NOT THE ARITHMETIC. IT IS THAT `total: Money` CANNOT
#    ACCIDENTALLY RECEIVE A FLOAT, A STRING, OR A QUANTITY — and that
#    `Money + int` is a TypeError at the point of the mistake rather
#    than a wrong invoice three weeks later.

# ⭐⭐ TIMEWINDOW. This one is load-bearing: it is the type your EXCLUDE
#    constraint enforces (Day 250), so the two must agree.
@dataclass(frozen=True, slots=True)
class TimeWindow:
    start: datetime
    end: datetime
    def __post_init__(self):
        if self.start.tzinfo is None or self.end.tzinfo is None:
            raise ValueError("naive datetimes are forbidden")  # ⭐⭐ Day 187
        if self.end <= self.start:
            raise ValueError("window must be positive")
    def overlaps(self, o: "TimeWindow") -> bool:
        return self.start < o.end and o.start < self.end   # ⭐ half-open
# ⭐⭐ WRITE `overlaps` EVEN THOUGH POSTGRES ENFORCES IT. Two reasons:
#    ⭐ the UI needs a fast client-side answer before submitting, and
#    ⭐⭐ your property test can assert that Python and Postgres agree —
#      which is how you find out that one of them treats the end bound
#      inclusively and the other does not.
```

```
⭐⭐ THE RULE FOR VALUE OBJECTS: `frozen=True`, VALIDATE IN
⭐   `__post_init__`, AND NO IDENTITY. ⭐ Two Money(500) are the same
⭐   money; two Jobs with the same fields are not the same job.
⭐ ⭐ `slots=True` because you will make millions of them in a report.
⭐ ⭐⭐ AND RESIST THE URGE TO MAKE EVERYTHING ONE. `Email`, `PhoneNumber`
⭐   and `Address` are usually fine as validated strings on the Pydantic
⭐   boundary. ⭐ Money and TimeWindow earn it because ARITHMETIC and
⭐   COMPARISON are where the bugs are.
```

# Part 4 — ⭐⭐ Where each invariant actually lives

```
⭐⭐ DAY 250'S TABLE, NOW WITH THE DOMAIN COLUMN FILLED IN — and the
⭐   important observation is HOW FEW ROWS SAY "DOMAIN ONLY".

⭐ | INVARIANT                  | DOMAIN | SERVICE | DATABASE |
⭐ | legal state transitions    | ⭐⭐ ✅  |         | ⭐ CHECK  |
⭐ | cannot invoice with no     | ⭐ ✅   |         |          |
⭐ |   work items               |        |         |          |
⭐ | money is never negative    | ⭐ ✅   |         | ⭐ CHECK  |
⭐ | window end > start         | ⭐ ✅   |         | ⭐ CHECK  |
⭐ | ⭐⭐ no overlapping          |        |         | ⭐⭐ EXCLUDE|
⭐ |   assignments              |        |         |          |
⭐ | one active assignment/job  |        |         | ⭐ partial|
⭐ |                            |        |         | unique   |
⭐ | tenant isolation           |        |         | ⭐⭐ RLS   |
⭐ | cannot invoice an          |        | ⭐ ✅    |          |
⭐ |   unfinished job           |        | (1 txn) |          |
⭐
⭐ ⇒ ⭐⭐ THE PATTERN: THE DOMAIN OWNS RULES ABOUT ***ONE OBJECT'S
⭐   INTERNAL CONSISTENCY***. Anything involving OTHER ROWS, other
⭐   users, or concurrency belongs to the database (Day 184 #2).
⭐ ⇒ ⭐⭐ AND THE DOUBLE-ENTRY ROWS ARE DELIBERATE: the domain gives a
⭐   good error message; the CHECK makes it TRUE. Day 187's Part 4,
⭐   applied to your own project.
```

# Part 5 — ⭐⭐ Domain events, and what they are not

```python
@dataclass(frozen=True, slots=True)
class JobTransitioned:
    job_id: JobId; from_state: JobState; to_state: JobState; at: datetime

@dataclass(frozen=True, slots=True)
class JobCompleted:
    job_id: JobId; work_item_ids: list[WorkItemId]; at: datetime
```

```
⭐⭐ THREE RULES, AND EACH ONE IS A BUG PREVENTED:
⭐  ① ⭐⭐ A DOMAIN EVENT IS A FACT IN THE PAST TENSE, NOT A COMMAND.
⭐     ⭐ `JobCompleted`, not `SendInvoiceEmail`. ⭐⭐ Day 161: an event
⭐       says what happened; a command says what to do. Naming an event
⭐       after its consequence welds one consumer into the domain
⭐       forever.
⭐  ② ⭐⭐ THE DOMAIN ***RETURNS*** EVENTS. IT DOES NOT PUBLISH THEM.
⭐     ⭐ Publishing needs I/O, and the domain has none. ⭐⭐ The SERVICE
⭐       takes the returned events and writes them to the OUTBOX in the
⭐       SAME TRANSACTION as the state change (Days 142, 166) — which is
⭐       the entire dual-write fix, and it only works because the domain
⭐       handed the events back instead of firing them.
⭐  ③ ⭐ AN EVENT CARRIES IDs AND FACTS, NOT ORM OBJECTS. ⭐⭐ It will be
⭐     serialised to JSON and read by a worker minutes later, possibly by
⭐     a NEWER version of the code (Day 161). Design it as a wire format.

⭐⭐ AND THE ANTI-PATTERN THIS REPLACES: A SIGNAL OR AN ORM HOOK
⭐   (`post_save`) THAT SENDS AN EMAIL. ⭐ Day 172 showed it is skipped
⭐   entirely by bulk operations; ⭐⭐ and even when it fires, it fires
⭐   BEFORE COMMIT, so a rollback sends an email about something that
⭐   never happened.
```

# Part 6 — ⭐ Testing the domain: fast, and without a database

```python
@pytest.mark.parametrize("state,action",
    [(s, a) for s in JobState for a in JobAction])
def test_transition_table_is_total(state, action):
    job = Job(id=JobId(1), tenant_id=TenantId(1), state=state)
    if (state, action) in TRANSITIONS:                 # ⭐⭐ 56 CASES
        assert job.apply(action, now=T0)               #    FROM ONE TEST
    else:
        with pytest.raises(InvalidTransition):
            job.apply(action, now=T0)
# ⭐⭐ ADDING A STATE MAKES THIS FAIL UNTIL YOU HAVE DECIDED EVERY
#    TRANSITION FOR IT. That is the property you want from a test.

@given(a=windows(), b=windows())
def test_overlap_matches_postgres(a, b, pg):
    assert a.overlaps(b) == pg.scalar(
        select(literal(a.as_range()).op("&&")(literal(b.as_range()))))
# ⭐⭐ THE ONE TEST HERE THAT TOUCHES A DATABASE, AND DELIBERATELY:
#    it asserts that your Python and your constraint agree about bounds.
#    ⭐ Everything else in `tests/unit/` runs with no I/O at all.
```

```
⭐⭐ THE TARGET: `pytest tests/unit/` COMPLETES IN UNDER A SECOND.
⭐   ⭐ No fixtures, no database, no `freezegun` (⭐⭐ because time is a
⭐     parameter — pass `now=T0` and the need disappears).
⭐   ⭐⭐ THIS IS THE PAYOFF FOR THE WHOLE LAYER: you will run these
⭐     hundreds of times a day, and a suite that takes 40 seconds is a
⭐     suite you run at the end.
⭐ ⭐ Property-based tests (`hypothesis`) fit the domain better than
⭐   anywhere else in the codebase, because it is pure: ⭐⭐ "an invoice
⭐   total always equals the sum of its lines" is a property, and
⭐   hypothesis will find the empty-list and overflow cases you would
⭐   not have written.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| A `domain/` folder that imports the session | Then it's a folder, not a layer. Enforce with `import-linter`. |
| `datetime.now()` inside the domain | Time is an input; otherwise boundary cases can't be tested. |
| Building a domain layer for a genuine CRUD app | If the three conditions are false, put it in the service and move on. |
| The state machine as scattered `if`s | The missing transition is invisible; as data it's obvious and testable. |
| No `CHECK` mirroring the state values | A bad `UPDATE` from psql creates a state your code has never heard of. |
| Money as a float, or as a bare int | A wrong invoice three weeks later instead of a TypeError at the mistake. |
| Naive datetimes anywhere | Reject them in `__post_init__`, not in a code review. |
| Not writing `overlaps` because Postgres enforces it | You lose the client-side check and the agreement test. |
| Making every string a value object | `Email` is fine as a validated field. Money and TimeWindow earn it. |
| Putting concurrency rules in the domain | Anything involving other rows or other actors belongs to the database. |
| Events named after their consequence | `SendInvoiceEmail` welds one consumer into the domain forever. |
| The domain publishing events | It has no I/O. It returns them; the service writes them to the outbox. |
| Events carrying ORM objects | They're a wire format read later by possibly newer code. |
| A `post_save` signal that sends email | Skipped by bulk ops, and it fires before commit. |
| A unit suite that needs a database | You'll run it at the end instead of hundreds of times a day. |

## Interview questions

**Q: What goes in your domain layer?**

> Rules that would still be true if you replaced Postgres with a filing cabinet: the state machine,
> invariants about a single object's internal consistency, value objects like Money and TimeWindow,
> calculations, and domain events. What's excluded is everything with I/O — sessions, HTTP, Celery,
> S3 — and one thing people don't expect: `datetime.now()`. Time is an input, not an ambient fact,
> because a domain object that reads the clock can't be tested at a boundary and every scheduling bug
> lives at a boundary. The test of whether the layer really exists is mechanical: `import-linter` in CI
> asserting the domain imports nothing outward. If that doesn't pass, you have a folder rather than a
> layer. And I'd say clearly when *not* to do this — if there's no real state machine, only one entry
> point, and no rule anyone would ask you to point at, put the logic in the service.

**Q: Why is the state machine a table rather than conditionals?**

> Four reasons, and the first is the one that convinces people. A table gives you an exhaustive test
> for free: iterate every state-action pair and assert allowed or rejected, which for eight states and
> seven actions is fifty-six cases from one parametrised test — and adding a state makes that test
> fail until you've decided every transition for it, which is exactly the property you want. Second,
> the API can publish `available_actions` so the UI doesn't reimplement the machine and drift from it.
> Third, a diagram can be generated from it, so the diagram can't be stale. Fourth, the database can
> mirror the allowed values in a `CHECK`, so a manual `UPDATE` can't create a state the code has never
> heard of. And practically, the missing transition is *visible* — in my table, `in_progress` is plainly
> absent from the cancel set, which is a decision someone made, whereas a missing `elif` is
> indistinguishable from an oversight.

**Q: Where do your business rules actually live?**

> Split, and the split has a principle rather than a preference: the domain owns rules about one
> object's internal consistency, and anything involving other rows, other actors or concurrency
> belongs to the database. So legal transitions, non-negative money and a positive time window are in
> the domain; no-overlapping-assignments, one-active-assignment-per-job and tenant isolation are an
> `EXCLUDE` constraint, a partial unique index and row-level security. Some rules appear twice on
> purpose — the domain gives a good error message, the constraint makes it true — because the domain
> check is bypassable by any code path that doesn't go through it, and there always is one: a data
> migration, a management command, a report. The artefact I'd point at is the invariants table with a
> column for where each rule is enforced and one for how it's proved, and the rule that if the
> enforcement column says "the service", I ask once more whether a constraint could do it.

**Q: How do domain events work in your design?**

> The domain *returns* events rather than publishing them, which sounds like a small distinction and
> is the whole thing. Publishing needs I/O and the domain has none, so `job.apply(...)` returns a list
> of facts and the service writes them to the outbox table in the same transaction as the state
> change. That's the dual-write fix — the state and the intent to notify commit atomically, and a
> relay delivers them afterwards with at-least-once semantics — and it only works because the domain
> handed the events back instead of firing them. Two naming rules go with it: an event is a past-tense
> fact, not a command, so `JobCompleted` rather than `SendInvoiceEmail`, because naming it after its
> consequence welds one consumer into the domain forever; and events carry ids and plain values rather
> than ORM objects, because they're a wire format read minutes later by possibly newer code. The
> pattern this replaces is an ORM signal that sends an email, which is skipped entirely by bulk
> operations and, when it does fire, fires before commit.

**Q: What does your test suite look like for this layer?**

> Fast and dependency-free — `tests/unit/` completes in under a second with no database, no fixtures
> and no clock mocking, because time is a parameter so `freezegun` is unnecessary. The two techniques
> that matter are parametrising over the whole transition table for exhaustiveness, and property-based
> tests with hypothesis, which fit the domain better than anywhere else precisely because it's pure —
> "an invoice total always equals the sum of its lines" is a property, and hypothesis finds the
> empty-list and overflow cases I wouldn't have written. There's exactly one test in that area that
> deliberately touches a database: asserting that my Python `overlaps` and Postgres's range overlap
> operator agree, because that's how you discover one of them treats a boundary inclusively and the
> other doesn't. The payoff for the whole layer is that speed: a forty-second suite is one you run at
> the end, and a one-second suite is one you run continuously.

## 🎙️ Articulation drill

**Two minutes: "Why do you have a domain layer?"**

Start with the test rather than the theory: **it would still be correct if you replaced Postgres with
a filing cabinet, and its tests run in under a second with no database.** Then say when you wouldn't
build one, because that's the credibility move — no real state machine, one entry point, no rule
anyone would ask you to point at, and it's ceremony. Then the state machine as data, with the reason
that lands: **fifty-six cases from one parametrised test, and adding a state makes it fail until every
transition is decided.** Then the split, as a principle: **the domain owns one object's internal
consistency; anything about other rows or other actors belongs to the database** — with the overlap
rule as the example that moved. Close on events: **the domain returns them, the service writes them to
the outbox in the same transaction** — which is the dual-write fix, and it only works because the
domain didn't fire them itself.
