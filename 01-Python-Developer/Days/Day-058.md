> ⭐⭐ **The sentence to own: a string literal used as a state name is an open set pretending to be a
> closed one — and every typo in it is a silent no-match rather than an error.**
>
> ⭐ Enums are the highest-value-per-effort change in most codebases: replacing `status == "shipped"`
> with `status is Status.SHIPPED` converts a class of silent bugs into import-time failures.

# Part 1 — ⭐⭐ `Enum`

```python
from enum import Enum, auto, unique

class Status(Enum):
    PENDING = "pending"
    SHIPPED = "shipped"
    CANCELLED = "cancelled"

Status.SHIPPED              # ⭐ <Status.SHIPPED: 'shipped'>
Status.SHIPPED.name         # ⭐ "SHIPPED"
Status.SHIPPED.value        # ⭐ "shipped"
Status("shipped")           # ⭐⭐ lookup BY VALUE — this is how you parse from a database
Status["SHIPPED"]           # ⭐ lookup by name
list(Status)                # ⭐⭐ iterable, in definition order
len(Status)                 # 3
```

```
⭐⭐ MEMBERS ARE SINGLETONS. There is exactly ONE Status.SHIPPED object per process.
⭐   ⇒ ⭐⭐ so compare with `is` — Status.SHIPPED is s. Identity, O(1), no __eq__ call.
⭐   ⇒ ⭐ they are hashable, so they work as dict keys and set members (Day 029)
⭐   ⇒ ⭐ built by EnumMeta, a metaclass (Day 053) — which is what turns class attributes
⭐        into member objects
```

```
⭐⭐ WHY THIS BEATS STRING LITERALS — four reasons, and the first is the big one:
⭐   1. ⭐⭐ A TYPO IS AN ERROR: Status.SHIPPPED ⇒ AttributeError, at import, immediately.
⭐        ⇒ `status == "shippped"` is a SILENT FALSE, forever, in one branch nobody tests.
⭐   2. ⭐ DISCOVERABILITY: list(Status) tells you every legal value. A string cannot.
⭐   3. ⭐⭐ EXHAUSTIVENESS: mypy can verify a match statement covers every member (Day 062)
⭐   4. ⭐ ONE PLACE to add a value, and one place to look for its meaning
```

```python
class Priority(Enum):
    LOW = auto()            # ⭐ 1, 2, 3 — when the value is arbitrary and never persisted
    MEDIUM = auto()
    HIGH = auto()

@unique                     # ⭐ forbid aliases — two names with the same value
class Colour(Enum):
    RED = 1
    CRIMSON = 1             # ⭐⭐ without @unique this is an ALIAS: Colour.CRIMSON is Colour.RED
```

⚠️ ⭐⭐ **`auto()` values must never be persisted.** They are positional, so inserting a member in the
middle silently renumbers everything after it — and your database now says `2` for something else.
**Persist explicit string values.**

# Part 2 — ⭐ `IntEnum`, `StrEnum`, and `Flag`

```python
from enum import IntEnum, StrEnum, Flag, auto

class HttpStatus(IntEnum):
    OK = 200
    NOT_FOUND = 404

HttpStatus.OK == 200        # ⭐⭐ True — IntEnum members ARE ints
json.dumps(HttpStatus.OK)   # ⭐ 200 — serialises without help

class Env(StrEnum):         # ⭐ 3.11+
    DEV = "dev"
    PROD = "prod"
Env.PROD == "prod"          # ⭐⭐ True — and f"{Env.PROD}" is "prod"
```

```
⭐⭐ THE TRADE, and you should state it rather than just picking one:
⭐   ✓ ⭐ interoperates with code and libraries that expect a raw int/str; serialises free
⭐   ✗ ⭐⭐ IT COMPARES EQUAL TO THE RAW VALUE ⇒ the type error you wanted to catch slips through:
⭐        `if status == 200` still works, and so does passing 404 where an enum was expected.
⭐   ⇒ ⭐⭐ SO: plain Enum by DEFAULT. IntEnum/StrEnum only where an external interface
⭐        genuinely demands the raw type.
```

⚠️ ⭐ **A plain `Enum` is not JSON-serialisable** — `json.dumps(Status.SHIPPED)` raises. **Serialise
`.value` explicitly, or use a `default=` function (Day 051's `singledispatch`), or Pydantic, which
handles enums natively.** ⭐⭐ **That one line of friction is worth paying for the type safety.**

```python
class Perm(Flag):
    READ = auto()           # ⭐ 1
    WRITE = auto()          # ⭐ 2
    ADMIN = auto()          # ⭐ 4

p = Perm.READ | Perm.WRITE  # ⭐⭐ a combination is still a Perm
Perm.WRITE in p             # ⭐ True
p & Perm.ADMIN              # ⭐ Perm(0) — falsy
```

⭐ **`Flag` is the right model for permission sets and feature bits** — it replaces a set of booleans
or a hand-rolled bitmask with something self-documenting.

```python
class Status(Enum):
    ...
    @property
    def is_terminal(self) -> bool:            # ⭐⭐ enums can have METHODS
        return self in {Status.SHIPPED, Status.CANCELLED}

    @classmethod
    def _missing_(cls, value):                # ⭐ called when lookup by value fails
        return cls(value.lower()) if isinstance(value, str) else None
```

⭐⭐ **Methods on enums are underused and excellent:** behaviour that switches on a status belongs
*on* the status. **It removes the `if/elif` chain and makes adding a member fail loudly if you forgot
to handle it.**

# Part 3 — ⭐ `TypedDict`

```python
from typing import TypedDict, NotRequired

class UserPayload(TypedDict):
    id: int
    email: str
    nickname: NotRequired[str]        # ⭐ 3.11+; or Required[...] with total=False

def handle(p: UserPayload) -> None:
    print(p["email"])                 # ⭐ mypy knows the key exists and its type
    print(p["emial"])                 # ⭐⭐ mypy ERROR: TypedDict has no key "emial"
```

```
⭐⭐ WHAT IT IS AND IS NOT:
⭐   ✓ ⭐ a STATIC description of a dict's shape — keys, types, optionality
⭐   ✓ ⭐⭐ the right tool for typing JSON you receive, **kwargs, or a legacy dict-based API
⭐   ✗ ⭐⭐ AT RUNTIME IT IS A PLAIN DICT. isinstance does not work. NOTHING IS VALIDATED.
⭐        ⇒ UserPayload(id="x") type-errors in mypy and runs fine.
⭐   ✗ no methods, no defaults, no coercion
```

⭐⭐ **So `TypedDict` types a dict; Pydantic *validates* one.** ⭐ Use `TypedDict` when the data must
stay a dict — an existing API you cannot change, a function taking `**kwargs`, a boundary where
converting to objects is not worth it — **and Pydantic when you actually need to know the data is
correct** (Day 057's boundary).

⭐ `total=False` makes every key optional; **`Required`/`NotRequired` per key is better**, because
whole-dict optionality is almost never what you mean.

# Part 4 — ⭐⭐ Choosing, and enums in a database

| ⭐ You have | ⭐⭐ Use |
|---|---|
| ⭐⭐ A **closed set of named values** | ⭐⭐ `Enum` |
| A closed set that must interop as int/str | ⭐ `IntEnum` / `StrEnum` — knowing the cost |
| A set of independent on/off options | ⭐ `Flag` |
| ⭐ A small immutable record, unpacked | `NamedTuple` (Day 034) |
| A record with behaviour | ⭐ `@dataclass` (Day 057) |
| ⭐⭐ The **shape of a dict** you must keep as a dict | ⭐⭐ `TypedDict` |
| ⭐⭐ **External data to validate** | ⭐⭐ **Pydantic** |

```
⭐⭐ ENUMS AND THE DATABASE — three rules learned the hard way:
⭐   1. ⭐⭐ STORE THE VALUE, NOT THE NAME, and make the value an explicit STRING.
⭐        ⇒ never auto(): inserting a member renumbers the rest and your rows now lie.
⭐   2. ⭐ PREFER A VARCHAR COLUMN over a native DB ENUM type — ⭐⭐ adding a value to a
⭐        Postgres enum is a migration with locking implications; adding a string is not.
⭐   3. ⭐⭐ HANDLE THE UNKNOWN VALUE. Old rows may hold values you have since removed, so
⭐        Status(row.status) can raise ValueError on data you cannot change.
⭐        ⇒ ⭐ that is what _missing_ is for, or an explicit fallback member.
```

⭐⭐ **Rule 3 is the one that causes a real 3am incident:** a member is renamed or deleted, the code
deploys, and every read of an old row raises. **Enums are a closed set in your code and an open set in
your database, because the database remembers what you used to believe.**

```python
# ⭐ The exhaustiveness payoff (Day 062 makes it check):
def label(s: Status) -> str:
    match s:
        case Status.PENDING: return "Waiting"
        case Status.SHIPPED: return "On its way"
        case Status.CANCELLED: return "Cancelled"
# ⭐⭐ add a member and mypy --strict flags this function as non-exhaustive.
#    ⇒ THAT is the property a string literal can never give you.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **String literals for a closed set** | ⭐⭐ A typo is a silent `False`; an enum typo is an error. |
| ⭐⭐ **Persisting `auto()` values** | ⭐⭐ Positional — inserting a member renumbers the rest. |
| Native DB enum column | ⭐ Adding a value is a migration. Prefer varchar. |
| Not handling removed values on read | ⭐⭐ Old rows raise `ValueError`. Use `_missing_`/a fallback. |
| ⭐ `IntEnum`/`StrEnum` by default | ⭐⭐ They compare equal to raw values — the check you wanted is gone. |
| Expecting `Enum` to be JSON-serialisable | ⭐ Serialise `.value`, or use Pydantic. |
| Aliases created by accident | ⭐ `@unique`. |
| ⭐ `if/elif` on an enum | ⭐⭐ Put the behaviour on the enum as a method or property. |
| ⭐ Expecting `TypedDict` to validate | ⭐⭐ Static only — at runtime it is a plain dict. |
| `isinstance(x, MyTypedDict)` | ⭐ Not supported. |
| `total=False` for one optional key | ⭐ `NotRequired` on that key. |

## Interview questions

**Q: Why use an enum rather than string constants?**
> Because a string is an open set pretending to be closed. `status == "shippped"` is a silent `False`
> that lives in whichever branch nobody tested; `Status.SHIPPPED` is an `AttributeError` at import. On
> top of that, members are singletons so comparison is identity, `list(Status)` documents every legal
> value, there's one place to add one, and mypy can verify a `match` covers every member — so adding a
> state makes the compiler tell you which functions forgot to handle it. That exhaustiveness check is
> the thing a string can never give you.

**Q: `Enum` or `IntEnum`/`StrEnum`?**
> Plain `Enum` by default. The mixin versions compare equal to their raw values, which is convenient
> for interop and serialisation and throws away the type safety you wanted — `if status == 200` still
> works, and passing a bare `404` where an enum was expected still passes. I'd use them only where an
> external interface genuinely demands the raw type. The cost of a plain enum is that it isn't
> JSON-serialisable, which is one line of `.value` or a serialiser function, and worth paying.

**Q: How do you store an enum in a database?**
> The value, explicitly a string, in a varchar column. Never `auto()`, because the values are
> positional and inserting a member in the middle renumbers everything after it — so existing rows
> silently mean something different. Varchar rather than a native Postgres enum, because adding a value
> to a database enum is a migration with locking implications while adding a string isn't. And I'd
> handle unknown values on read: old rows can hold members that have since been renamed or removed, so
> `Status(row.status)` raises on data I can't change. `_missing_` or an explicit fallback member covers
> it. The general point is that an enum is a closed set in code and an open set in the database,
> because the database remembers what you used to believe.

**Q: What's `TypedDict` for, and what doesn't it do?**
> It describes a dict's shape statically — which keys exist, their types, which are optional — so mypy
> catches a mistyped key and a wrong value type. It's the right tool when the data must remain a dict:
> a legacy API, a function's `**kwargs`, or a JSON payload I'm not converting to objects. What it
> doesn't do is exist at runtime — it's a plain dict, `isinstance` doesn't work, and nothing is
> validated. So `TypedDict` types a dict and Pydantic validates one, which puts it on the inside of the
> same boundary as dataclasses.

**Q: Would you put methods on an enum?**
> Yes, and it's underused. Behaviour that switches on a status belongs on the status — an `is_terminal`
> property, or a `label`. It removes the `if/elif` chain from the call sites and it puts the knowledge
> in one place, so adding a member draws attention to whatever didn't handle it. It's the same instinct
> as replacing a conditional with polymorphism, at a much lower cost.
