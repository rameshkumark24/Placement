# Day 061

**L-061** · ⭐⭐ **Type hints that earn their keep** — generics, `TypeVar`, variance, `Optional` vs `|`

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: type hints are documentation the computer checks — and their single
> biggest payoff is `None`-safety, because `AttributeError: 'NoneType' object has no attribute` is the
> most common runtime error in Python.**
>
> ⭐ Annotations are metadata (Day 042). Today is about writing ones that are worth checking, and
> knowing where the effort stops paying.

---

# Part 1 — ⭐ The vocabulary

```python
def f(xs: list[int], m: dict[str, float], t: tuple[int, str]) -> set[str]: ...
def g(x: int | None) -> str | None: ...        # ⭐⭐ 3.10+ — prefer this to Optional[int]
def h(cb: Callable[[int, str], bool]) -> None: ...
def k(xs: Sequence[int]) -> Iterable[str]: ... # ⭐⭐ ABSTRACT in, CONCRETE out — see below
```

```
⭐⭐ THE RULE THAT IMPROVES EVERY SIGNATURE YOU WRITE:
⭐   ⭐⭐ ACCEPT THE MOST ABSTRACT TYPE YOU CAN; RETURN THE MOST CONCRETE.
⭐   ⇒ ⭐ take Iterable[int] or Sequence[int], not list[int] — the caller may have a tuple,
⭐        a generator, or a range, and none of them should have to convert.
⭐   ⇒ ⭐ return list[str], not Iterable[str] — the caller can then index it and len() it.
⭐ ⇒ ⭐⭐ this is Postel's law (Day 010) restated as a type signature.
```

| ⭐ Construct | ⭐ Use |
|---|---|
| ⭐⭐ `X \| None` | ⭐ the modern `Optional[X]`. Same thing, better reading. |
| ⭐ `Any` | ⭐⭐ **"stop checking"** — see Day 062. Not "unknown". |
| `object` | ⭐⭐ "unknown, and I will narrow it" — ⭐ **the safe alternative to `Any`** |
| ⭐ `Literal["a", "b"]` | ⭐ a closed set of values (⭐⭐ an `Enum` is usually better — Day 058) |
| `Final` | rebinding is an error |
| ⭐ `ClassVar[int]` | ⭐ a class attribute, not a dataclass field (Day 057) |
| ⭐ `Never` / `NoReturn` | this function never returns — it always raises or exits |
| ⭐ `Annotated[int, Field(ge=0)]` | ⭐⭐ a type plus metadata — how Pydantic and FastAPI carry constraints |
| `Self` | ⭐ a method returning its own type — correct under subclassing |

⭐⭐ **`X | None` versus `Optional[X]` is not just style:** `Optional` reads as "this argument is
optional", which is wrong — **it means the value may be `None`**, which is a different claim from
having a default. **`| None` says exactly that.**

# Part 2 — ⭐⭐ Generics and `TypeVar`

```python
# ⚠️ ⭐ Without a TypeVar, the connection between input and output is lost:
def first(xs: list[Any]) -> Any: ...           # ⭐⭐ the caller learns nothing

from typing import TypeVar
T = TypeVar("T")
def first(xs: Sequence[T]) -> T | None:        # ⭐⭐ "returns the SAME type the sequence holds"
    return xs[0] if xs else None

first([1, 2, 3])          # ⭐ mypy knows: int | None
first(["a"])              # ⭐ str | None
```

```python
# ⭐ Python 3.12 syntax (PEP 695) — no TypeVar declaration needed:
def first[T](xs: Sequence[T]) -> T | None: ...
class Box[T]: ...
type Rows = list[dict[str, str]]              # ⭐ the `type` statement replaces TypeAlias
```

```python
# ⭐ BOUNDED and CONSTRAINED type variables:
N = TypeVar("N", bound=Number)                # ⭐ T must be a Number or a subclass
S = TypeVar("S", str, bytes)                  # ⭐⭐ EXACTLY str or bytes — not a union of them

# ⭐ Generic classes:
from typing import Generic
class Repository(Generic[T]):
    def get(self, id: int) -> T | None: ...
    def save(self, item: T) -> None: ...

repo: Repository[User] = SqlRepository()      # ⭐⭐ get() now returns User | None
```

⭐⭐ **A generic `Repository[T]` combined with a `Protocol` (Day 056) is the shape of a typed,
testable data layer**, and it is what Stage 3 will build: the service depends on
`Repository[User]`, the SQL implementation and the in-memory fake both satisfy it, and mypy checks
both.

# Part 3 — ⭐⭐ Variance — the part people cannot explain

```python
def total(xs: list[float]) -> float: ...
ints: list[int] = [1, 2, 3]
total(ints)              # ⭐⭐ mypy ERROR — and this looks wrong until you see why
```

```
⭐⭐ WHY IT IS AN ERROR, and this is the clearest explanation:
⭐   list is MUTABLE. If list[int] were accepted where list[float] is wanted, then:
⭐        def total(xs: list[float]): xs.append(3.14)      ⭐⭐ perfectly legal for list[float]
⭐   ⇒ ⭐⭐ your list[int] now contains a float. The type system just lied to you.
⭐   ⇒ ⭐ so ⭐⭐ MUTABLE containers are INVARIANT: list[int] is NOT a list[float].
⭐
⭐ ⭐⭐ Sequence IS covariant, because it is READ-ONLY — nothing can be appended:
⭐        def total(xs: Sequence[float]) -> float: ...
⭐        total(ints)          ⇒ ⭐⭐ FINE.
```

```
⭐⭐ THE THREE, WITH THE ONE-LINE INTUITION:
⭐   COVARIANT      (Sequence[T], tuple, frozenset) — ⭐ producers/read-only ⇒ subtypes OK
⭐   CONTRAVARIANT  (Callable ARGUMENTS)            — ⭐ consumers ⇒ SUPERtypes OK
⭐   ⭐⭐ INVARIANT   (list, dict, set)               — ⭐⭐ mutable ⇒ EXACT type only
⭐
⭐ ⇒ ⭐⭐ THE PRACTICAL FIX, and it is the same as Part 1's rule:
⭐      ACCEPT Sequence/Iterable/Mapping, not list/dict — and the variance problem
⭐      disappears, because read-only containers are covariant.
```

⭐⭐ **"Mutable containers are invariant because a function could put the wrong thing in" is the whole
answer**, and being able to give it — with the `append` example — is a genuine senior signal. ⭐ It is
also why `Callable[[Base], None]` accepts a function taking `Derived`... **no — the other way round: a
callback taking `Base` can be used where one taking `Derived` is expected**, because it handles more.

# Part 4 — ⭐ Typing what you actually write

```python
# ⭐⭐ DECORATORS — the reason ParamSpec exists (Day 044):
from typing import ParamSpec, TypeVar, Callable
P = ParamSpec("P"); R = TypeVar("R")

def retry(fn: Callable[P, R]) -> Callable[P, R]:      # ⭐⭐ preserves the FULL signature
    @wraps(fn)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        return fn(*args, **kwargs)
    return wrapper
# ⚠️ ⭐ without ParamSpec you write Callable[..., R] and mypy stops checking the arguments
#    of every decorated function — a decorator that silently disables type checking.
```

```python
# ⭐ FORWARD REFERENCES — a class referring to itself or to something defined later:
from __future__ import annotations          # ⭐⭐ makes ALL annotations strings — put it first
class Node:
    def children(self) -> list[Node]: ...   # ⭐ works, no quotes needed

from typing import TYPE_CHECKING
if TYPE_CHECKING:                            # ⭐⭐ import ONLY for typing — no runtime cost,
    from .models import User                 #    and it breaks import cycles (Day 074)
```

⚠️ ⭐ **`from __future__ import annotations` interacts badly with anything that *reads* annotations at
runtime** — Pydantic and FastAPI resolve them, and a type they cannot resolve becomes an error at
import. **It is fine in practice; just know it is why an obscure "cannot evaluate forward reference"
appears.**

```python
# ⭐ overload — one function, several precise signatures:
from typing import overload
@overload
def get(key: str) -> str | None: ...
@overload
def get(key: str, default: str) -> str: ...      # ⭐⭐ with a default it NEVER returns None
def get(key, default=None): ...                  # ⭐ the real implementation, unannotated
```

```
⭐⭐ WHERE THE EFFORT PAYS, IN ORDER:
⭐   1. ⭐⭐ PUBLIC FUNCTION SIGNATURES — the contract, and what a reader looks at first
⭐   2. ⭐⭐ ANYTHING THAT CAN BE None — this is where the bugs actually are
⭐   3. ⭐ dataclass/Pydantic models — types you were writing anyway (Day 057)
⭐   4. ⭐ collection element types — list[User] not list
⭐   ⇒ ⭐ and it stops paying on: local variables mypy can infer, short private helpers,
⭐        one-off scripts, and test bodies.
```

⚠️ ⭐⭐ **Over-annotating is a real failure mode.** A signature with four `TypeVar`s and a
`ParamSpec` that nobody can read is worse than `Any` — **the point is to communicate a contract, and
an unreadable one communicates nothing.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`list[X]` in a parameter** | ⭐⭐ `Sequence`/`Iterable` — abstract in, concrete out. |
| Not understanding the variance error | ⭐⭐ Mutable containers are invariant — a callee could append. |
| ⭐ `Any` to silence mypy | ⭐⭐ It disables checking and spreads (Day 062). Use `object` + narrowing. |
| `Optional[X]` for "has a default" | ⭐ It means "may be `None`". Use `X \| None`. |
| ⭐ `Callable[..., R]` on a decorator | ⭐⭐ `ParamSpec` — otherwise arguments stop being checked. |
| `Literal` where an `Enum` belongs | ⭐ Enum gives methods, iteration and exhaustiveness. |
| Runtime imports for typing only | ⭐ `TYPE_CHECKING` — no cost, breaks cycles. |
| Annotating every local | ⭐ mypy infers them; the noise costs readability. |
| A signature with five type variables | ⭐⭐ Unreadable is worse than untyped. |
| Assuming hints are enforced | ⭐ Day 042 — they are metadata. |

## Interview questions

**Q: What do type hints actually buy you?**
> Checked documentation, and the biggest single win is `None`-safety — `AttributeError: 'NoneType'
> object has no attribute` is the most common runtime error in Python, and a checker catches it
> statically. Beyond that, they're the fastest way to read an unfamiliar function, they make IDE
> completion and refactoring reliable, and libraries like Pydantic and FastAPI read them at runtime to
> generate validation and OpenAPI schemas. They aren't enforced by the language — they're metadata
> until something reads them.

**Q: Why does passing a `list[int]` to a function expecting `list[float]` fail?**
> Because `list` is mutable, so it's invariant. If it were allowed, the function could legally append a
> float to what the caller knows as a `list[int]`, and the caller's type is now a lie. Read-only
> containers don't have that problem — `Sequence` is covariant, so `Sequence[float]` happily accepts a
> `list[int]`. The practical consequence is a signature rule: accept `Sequence` or `Iterable` rather
> than `list`, which is more permissive for callers *and* makes the variance issue disappear.

**Q: What's a `TypeVar` for?**
> Expressing a relationship between types rather than a fixed type. `def first(xs: Sequence[T]) -> T |
> None` says the return is the same type the sequence holds, so calling it with a `list[int]` gives
> `int | None`. With `Any` in those positions the caller learns nothing, and everything downstream
> stops being checked. Bounded type variables constrain it further — `TypeVar("N", bound=Number)`.

**Q: How do you type a decorator?**
> With `ParamSpec` plus a `TypeVar` for the return: `Callable[P, R] -> Callable[P, R]`, and the wrapper
> takes `*args: P.args, **kwargs: P.kwargs`. Without it the usual signature is `Callable[..., R]`,
> which tells the checker to stop verifying arguments — so every decorated function loses argument
> checking silently. That's the type-level version of the `functools.wraps` problem from Day 044:
> a careless decorator quietly degrades everything it touches.

**Q: `Optional[X]` or `X | None`?**
> `X | None`, both for readability and for accuracy. `Optional` suggests "this argument is optional",
> which is a claim about defaults; what it actually means is that the value may be `None`. `X | None`
> says exactly that, and it's the modern syntax from 3.10.

**Q: Where do you stop annotating?**
> Public signatures always, anything nullable always, and model fields — those I was writing anyway.
> I stop at local variables the checker can infer, short private helpers, and test bodies. And I'd
> stop before a signature becomes unreadable: four type variables and a `ParamSpec` that nobody can
> parse communicates less than a plain one with a docstring. The goal is a contract someone can read,
> not maximum coverage.

## 🎙️ Articulation drill

Record two minutes: **"Why does mypy reject passing a `list[int]` where a `list[float]` is
expected?"**

⭐ Answer with the mechanism, not the vocabulary: **because `list` is mutable, so it is invariant.**
Then the demonstration, which is the part that makes it click: **a function declaring `list[float]` is
allowed to append a float — and if it were handed my `list[int]`, my list now contains a float and the
type I was relying on is a lie.** ⭐ The checker is preventing that, not being pedantic.

⭐ Then the contrast: **`Sequence` is covariant because it is read-only** — nothing can be put in, so
accepting a `list[int]` where `Sequence[float]` is expected is safe.

⭐⭐ **Then convert it into the rule you would actually apply:** *"which means the fix is the same
thing that makes the signature better anyway — accept `Sequence` or `Iterable` rather than `list`, and
return the concrete type. Abstract in, concrete out. It is more permissive for callers, it makes the
variance problem vanish, and it is the type-system version of being liberal in what you accept and
conservative in what you emit."*
