# Part 1 — The generics you will write

You will write about four. Everything else is library authorship.

```typescript
// ① identity over a container — ⭐ the api() wrapper from Day 217
async function api<T>(path: string, opts?: Options): Promise<T> { ... }
const users = await api<User[]>("/users");     // ⭐ users: User[]

// ② constrained — ⭐⭐ "anything with an id"
function byId<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find(i => i.id === id);         // ⭐ returns T, not a widened type
}

// ③ keyof — ⭐ sort by a real field name, checked
function sortBy<T, K extends keyof T>(items: T[], key: K): T[] {
  return [...items].sort((a, b) => (a[key] > b[key] ? 1 : -1));
}
sortBy(users, "name");    // ✅
sortBy(users, "nmae");    // ⭐⭐ compile error — the typo is caught

// ④ the built-ins — ⭐ used constantly, written never
type Draft = Partial<User>;              // all optional
type Card  = Pick<User, "id" | "name">;  // subset
type Safe  = Omit<User, "passwordHash">; // ⭐⭐ the one you actually want
```

| Python | TypeScript |
|---|---|
| `TypeVar("T")` | `<T>` |
| `TypeVar("T", bound=X)` | `<T extends X>` |
| — | ⭐⭐ `keyof T` — no clean Python equivalent, genuinely useful |

> ⭐ **`api<User[]>("/users")` is a lie you are choosing to tell.** Nothing verified the response is
> `User[]`; you asserted it. That is fine *only* if the boundary validates — Part 3. Say this out
> loud in an interview and you will sound like someone who has debugged it.

# Part 2 — Narrowing

```typescript
// ⭐ the four that work
if (typeof x === "string") ...          // primitives
if (x instanceof ApiError) ...          // classes
if ("email" in user) ...                // property presence
if (r.status === "success") ...         // ⭐⭐ discriminated union — the best one

// ⭐ the custom guard, for when the above cannot express it
function isUser(x: unknown): x is User {          // ⭐⭐ "x is User" = the guard
  return typeof x === "object" && x !== null
      && "id" in x && typeof (x as any).id === "string";
}
```

```
⭐⭐ THE TRAP: NARROWING IS FORGOTTEN ACROSS AN AWAIT OR A CALLBACK

⭐   if (user.email) {
⭐     await save();
⭐     send(user.email);   // ⭐⭐ STILL NARROWED here (user is const)
⭐   }

⭐   ⭐ BUT if `user` is a `let` reassigned anywhere, or a property
⭐   of a mutable object captured in a closure, TS conservatively
⭐   widens it back. ⇒ ⭐⭐ COPY TO A CONST:
⭐     const email = user.email;
⭐     if (!email) return;
⭐     ... email is string from here, unconditionally.
```

> ⭐ **`if (!x) return;` early is better than nesting.** It narrows for the whole remaining function
> and it is the same guard-clause discipline as Day 060.

# Part 3 — ⭐⭐ The validated boundary

This is the day's real content. Types are erased (Day 218), so a `User` annotation on a fetch response
is an assumption. **Validate where data enters, and only there.**

```typescript
import { z } from "zod";

// ⭐⭐ ONE definition produces BOTH the runtime check and the static type
const User = z.object({
  id: z.string().uuid(),
  name: z.string(),
  email: z.string().email().nullable(),    // ⭐ null from the wire (Day 215)
  role: z.enum(["admin", "user"]),
  createdAt: z.string().datetime(),
});
type User = z.infer<typeof User>;          // ⭐ the static type, derived

export async function getUsers(): Promise<User[]> {
  const raw = await api("/users");         // ⭐ unknown, honestly
  return z.array(User).parse(raw);         // ⭐⭐ THROWS if the API drifted
}
```

```
⭐⭐ WHERE TO VALIDATE, AND WHERE NOT TO

⭐   ✅ VALIDATE  · API responses          · URL params & query strings
⭐               · localStorage reads     · postMessage / websocket frames
⭐               · anything from a form    · env vars at startup
⭐   ❌ DON'T     · between your own components — ⭐⭐ THAT IS WHAT THE
⭐                 TYPES ARE FOR, and re-validating there is cargo cult.

⭐   ⇒ ⭐⭐ THE EXACT ARGUMENT FOR PYDANTIC AT YOUR FASTAPI EDGE.
⭐     Same shape, other end of the wire.
```

| ⭐ Why validate a response you wrote yourself | |
|---|---|
| **The server deploys separately** | ⭐⭐ The client running in a user's tab is an *old* client. Version skew is not hypothetical, it is Tuesday. |
| **The failure becomes loud** | A `ZodError` naming `users[3].email: expected string, got null` beats `undefined` on screen. ⭐ Day 455 again: make the quiet failure noisy. |
| **You get the type free** | ⭐ `z.infer` means one source, no drift between the checker and the annotation. |

> ⭐ **Cost, stated honestly:** a schema per response shape, a few KB of bundle, and parse time on
> large lists. **Worth it at the boundary, wasteful anywhere else.** On Day 246 you generate these
> from OpenAPI instead of writing them by hand, which removes most of the cost.

# Part 4 — The three errors that look terrifying

| ⭐ Error | What it actually means | Fix |
|---|---|---|
| `Type 'string \| undefined' is not assignable to type 'string'` | ⭐⭐ **The correct error.** Something may be absent and you assumed it isn't. | Narrow it. `if (!x) return;` — do **not** `!` it away. |
| `Property 'x' does not exist on type 'never'` | ⭐ You narrowed a union down to nothing — usually a `case` on a value that cannot occur, or an exhaustive switch you added a branch to. | Read the union; a branch is impossible or the discriminant is wrong. |
| `Types of property 'x' are incompatible... (100 lines)` | ⭐ Two big object types differ. **Read the LAST line first** — the nested leaf is the real mismatch. | Compare the two leaf types; ignore the wrapper noise. |

```typescript
// ⭐⭐ the non-null assertion is a lie to the compiler
const el = document.getElementById("root")!;   // ⭐ "trust me"
// ⇒ ⭐⭐ if it's null you get a runtime crash with NO type error.
// Use it only where you can prove it, and prefer a real check:
const el = document.getElementById("root");
if (!el) throw new Error("mount point #root missing");
```

> ⭐ **`!` and `as` are the two escape hatches, and both are you overruling the compiler.** Grep for
> them in review. Each one should have a comment saying why you are more certain than the checker.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you keep types honest when the data comes from outside?"**

State the principle first. **Types are erased, so they can only lie at the boundary — the place data
enters the program. Everywhere inside, the types are true because the compiler enforced them. So I
validate once at the edge and never again.**

Make it concrete with the tool and the payoff. **One Zod schema per response shape gives me the runtime
check and the static type from a single definition, so they can't drift. If the API changes, I get
`users[3].email: expected string, got null` instead of the word "undefined" rendered to a customer.
That's turning a quiet failure into a loud one, which is the same instinct I apply on the server.**

Then pre-empt the obvious objection, because it is the interesting part. **People ask why I'd validate a
response from an API I wrote myself. Because the server deploys separately — the client in a user's tab
is an old client, and version skew isn't hypothetical. And it's exactly the Pydantic argument at my
FastAPI edge, just the other end of the same wire.**

Close on cost. **It's a schema and a few KB, and it's only worth it at the boundary — re-validating
between my own components is cargo cult, that's what the types are for. On the flagship I generate the
schemas from the OpenAPI spec so I'm not hand-maintaining them at all.**
