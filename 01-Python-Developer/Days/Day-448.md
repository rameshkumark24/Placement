# Day 448 🚧

**P-448** · 🚧 **Guardrails** — ⭐⭐ a check is not a boundary

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a guardrail is a probabilistic check that reduces the rate of a bad
> outcome, so it belongs on top of deterministic controls and never instead of them — and the moment
> anyone treats one as a security boundary, you have swapped an engineering control for a statistic.**

---

# Part 1 — ⭐⭐ Check versus boundary

```
⭐ ***A BOUNDARY*** is something an attacker ***cannot*** cross,
⭐   by construction:
⭐   ⭐ a database role with no DELETE privilege;
⭐   ⭐ a tenant predicate inside the query (Day 434);
⭐   ⭐ a tool that requires human approval (Day 440);
⭐   ⭐ a network that has no route out (Day 446);
⭐   ⭐ ⭐⭐ THESE HAVE NO FALSE-NEGATIVE RATE. THAT IS THE
⭐     DEFINITION.

⭐ ***A CHECK*** is something that usually notices:
⭐   ⭐ a toxicity classifier, a PII detector, an
⭐     injection-heuristic model, an LLM judging policy
⭐     compliance;
⭐   ⭐ ⭐⭐ THESE HAVE A FALSE-NEGATIVE RATE, AND A FALSE
⭐     NEGATIVE ***IS*** A BYPASS.

⭐⭐ ⇒ THE ORDERING RULE, WHICH IS THE ENTIRE DAY:
⭐   ***BUILD THE BOUNDARIES FIRST. ADD CHECKS ON TOP TO REDUCE
⭐   THE RATE AND TO GIVE YOU TELEMETRY. NEVER SHIP A CHECK AS
⭐   THE ONLY THING BETWEEN AN ATTACKER AND MONEY.***

⭐ ***AND THE FAILURE THIS PREVENTS:*** ⭐ a team ships a
⭐   "guardrail layer", the security review passes because there
⭐   is a box on the diagram, ⭐⭐ AND THE ACTUAL CONTROL IS A
⭐   CLASSIFIER WITH AN UNMEASURED FALSE-NEGATIVE RATE ON
⭐   ADVERSARIAL INPUT — ⭐ which is the input distribution it
⭐   was least trained for.
```

# Part 2 — What to check, on each side

```
⭐ ***INPUT (before the model sees it):***
⭐   ⭐ ① ***PII detection*** — ⭐ do you want a card number in
⭐     your provider logs and your traces at all? (Day 450)
⭐   ⭐ ② ***topic / scope classification*** — ⭐ off-topic,
⭐     medical, legal, competitor. ⭐⭐ CHEAP AND OFTEN THE MOST
⭐     BUSINESS-RELEVANT ONE.
⭐   ⭐ ③ ***injection heuristics*** (Day 446) — ⭐ a speed bump,
⭐     labelled as one.
⭐   ⭐ ④ ***abuse and rate limiting*** — ⭐⭐ NOT A MODEL. A
⭐     COUNTER. ⭐ And it is the control that actually stops the
⭐     $40,000 weekend.
⭐   ⭐ ⑤ ***length caps*** — ⭐ free, exact, and a real DoS
⭐     control given quadratic attention (Day 416).

⭐ ***OUTPUT (before the user or the next system sees it):***
⭐   ⭐ ① ***PII / secret leakage*** — ⭐⭐ REGEX FOR CARD AND
⭐     ACCOUNT NUMBERS IS FREE AND EXACT; ⭐ names need a model.
⭐   ⭐ ② ***groundedness*** — ⭐ does every claim have a quote in
⭐     the context? (Days 424/435) ⭐⭐ THE ONE THAT MATTERS MOST
⭐     IN RAG, AND IT IS ***PROGRAMMATIC***.
⭐   ⭐ ③ ***policy compliance*** — no advice you are not
⭐     licensed to give, no promises about refunds.
⭐   ⭐ ④ ***safety / toxicity*** — ⭐ usually the provider's
⭐     moderation endpoint, which is cheap and fast.
⭐   ⭐ ⑤ ***schema and business validation*** (Days 424/447) —
⭐     ⭐⭐ DETERMINISTIC, SO IT GOES FIRST AND COSTS NOTHING.

⭐⭐ NOTICE HOW MANY OF THOSE ARE NOT MODELS. ⭐ Length caps,
⭐   rate limits, regexes, schema checks, quote verification —
⭐   ⭐⭐ ALL FREE, EXACT, AND WITH NO FALSE-POSITIVE DRIFT.
⭐   ⭐ ***DO ALL OF THOSE BEFORE YOU BUY A CLASSIFIER.***
```

# Part 3 — ⭐⭐ The economics nobody prices

```
⭐ ***EVERY MODEL-BASED GUARDRAIL IS A MODEL CALL.***

⭐ ***LATENCY:*** ⭐ input guard 200ms + generation 2,000ms +
⭐   output guard 300ms = ⭐⭐ 2,500ms. ⭐ You added 25% for
⭐   checks. ⭐ Two of each and you have added 50%.

⭐ ***COST:*** ⭐ the output guard reads ***the whole answer plus
⭐   the whole context*** to judge groundedness — ⭐⭐ THAT CAN BE
⭐   MORE TOKENS THAN THE GENERATION ITSELF. ⭐ A "cheap safety
⭐   layer" can quietly double your bill.

⭐ ***AND THE STREAMING CONTRADICTION, WHICH IS THE REAL DESIGN
⭐   PROBLEM:***
⭐   ⭐ ⭐⭐ YOU CANNOT CHECK AN ANSWER YOU HAVE ALREADY SHOWN.
⭐   ⭐ Three options, pick deliberately:
⭐     ⭐ ⓐ ***do not stream*** on high-risk paths — ⭐ slower,
⭐       correct;
⭐     ⭐ ⓑ ***stream, then retract*** — ⭐⭐ THE USER READ IT.
⭐       RETRACTION IS THEATRE FOR ANYTHING THAT MATTERS;
⭐     ⭐ ⓒ ⭐⭐ ***BUFFER-AND-CHECK IN CHUNKS*** — ⭐ hold ~200
⭐       tokens, check, release. ⭐ Adds one chunk of latency,
⭐       keeps most of the streaming feel. ⭐⭐ USUALLY THE RIGHT
⭐       ANSWER.

⭐ ***THREE WAYS TO BUY THE LATENCY BACK:***
⭐   ⭐ run input guards ***concurrently*** with retrieval, not
⭐     before it;
⭐   ⭐ ⭐⭐ USE SMALL PURPOSE-BUILT CLASSIFIERS (LLAMA GUARD, A
⭐     FINE-TUNED DISTILBERT) RATHER THAN A FRONTIER MODEL — ⭐ a
⭐     40ms local classifier versus a 400ms API call;
⭐   ⭐ ⭐⭐ ONLY GUARD WHAT MATTERS. ⭐ Read-only Q&A over public
⭐     docs does not need the same stack as a refund agent.
```

# Part 4 — ⭐⭐ False positives are the product's problem

```
⭐ ***A GUARDRAIL HAS TWO ERROR RATES AND TEAMS ONLY EVER
⭐   MEASURE ONE.***

⭐ ***FALSE NEGATIVE*** — the bad thing gets through.
⭐   ⭐⭐ THIS IS THE ONE EVERYONE TESTS, AND IT IS A ***BYPASS***.

⭐ ***FALSE POSITIVE*** — a legitimate request is blocked.
⭐   ⭐ 5% FP on a support bot = ⭐⭐ ONE IN TWENTY REAL USERS
⭐     BLOCKED, ⭐ and they do not file a bug — ⭐⭐ THEY STOP
⭐     USING IT.
⭐   ⭐ Worse, FPs are ***not*** uniformly distributed:
⭐     ⭐⭐ TOXICITY CLASSIFIERS FIRE MORE ON DIALECT, ON
⭐     NON-ENGLISH TEXT, AND ON DISCUSSIONS ***ABOUT*** HARM —
⭐     ⭐ so a medical or safeguarding product blocks exactly its
⭐       most important conversations.
⭐   ⭐⭐ ⇒ THAT IS A FAIRNESS PROBLEM, NOT ONLY A UX ONE, AND
⭐     IT IS THE THING TO RAISE IN A DESIGN REVIEW.

⭐ ⇒ ***THE GUARDRAIL NEEDS ITS OWN EVAL SET, WITH THREE
⭐   BUCKETS:***
⭐   ⭐ ① real attacks — ⭐ must be caught;
⭐   ⭐ ② benign traffic — ⭐ must pass;
⭐   ⭐ ③ ⭐⭐ ***BENIGN-BUT-SIMILAR*** — ⭐ "how do I stop someone
⭐     hacking my account?", "the invoice says my card was
⭐     charged 4111 1111 1111 1111". ⭐⭐ BUCKET ③ IS WHERE EVERY
⭐     GUARDRAIL EMBARRASSES ITSELF AND ALMOST NOBODY BUILDS IT.

⭐ ***AND THE REFUSAL UX, WHICH IS PART OF THE CONTROL:***
⭐   ⭐ say ***something specific***: "I can't help with payment
⭐     details here";
⭐   ⭐ ⭐⭐ ALWAYS OFFER AN ESCAPE HATCH TO A HUMAN;
⭐   ⭐ log it with a reason code so you can measure bucket ③ in
⭐     production. ⭐⭐ A BLOCK WITH NO REASON CODE IS AN
⭐     UNDEBUGGABLE PRODUCT COMPLAINT.
```

⭐  ① ⭐⭐ AUTHZ / TENANT / SESSION SCOPE      boundary   free
⭐  ② ⭐⭐ RATE + SPEND LIMITS                 boundary   free
⭐  ③ length caps, schema validation         boundary   free
⭐  ④ regex secrets/PAN, allowlists          boundary   free

⭐  ⑥ quote-in-source groundedness check     boundary   free
⭐  ─────────────────────────────────────────────────────────

⭐  ⑨ injection heuristics                   check   ~100ms

# 💬 Interview

**1. "How do you do guardrails?"**

⭐ I'd start by separating checks from boundaries, because the word gets used for both. ⭐⭐ A boundary is
something an attacker can't cross by construction — a role with no DELETE, a tenant predicate inside the
query, a tool requiring approval, a network with no route out. ⭐ Those have no false-negative rate;
that's the definition. ⭐ A check is something that usually notices — a toxicity classifier, a PII
detector, an LLM judging policy. ⭐⭐ Those have a false-negative rate, and a false negative *is* a
bypass. ⭐ So boundaries first, checks on top to reduce the rate and give me telemetry, and never a check
as the only thing between an attacker and money.

**2. "What would you build first?"**

⭐ The free, exact things, in order: authorisation and tenant scoping, rate and spend limits, length caps,
schema validation, regexes for card and account numbers, tool gates by reversibility, and the
quote-in-source groundedness check. ⭐⭐ Seven controls, all deterministic, all with no false positives,
and they stop the failures that actually cost money. ⭐ Only then do I add classifiers. ⭐⭐ Most teams
start with an LLM-as-judge policy layer because it demos well, and ship it on top of an application
where the model can still choose its own tenant.

**3. "What does a guardrail cost?"**

⭐ More than people budget. ⭐⭐ An input guard at 200 milliseconds plus generation at two seconds plus
an output guard at 300 is a 25% latency increase, and two of each makes it 50%. ⭐ On cost, an output
guard that checks groundedness reads the whole answer **plus the whole retrieved context**, which can
be more tokens than the generation itself — so a "cheap safety layer" quietly doubles the bill. ⭐⭐ I'd
buy it back three ways: run input guards concurrently with retrieval rather than before it, use small
purpose-built classifiers like Llama Guard or a fine-tuned encoder at 40 milliseconds locally instead of
a frontier model at 400, and only guard the paths that matter — read-only Q&A over public docs doesn't
need a refund agent's stack.

**4. "How do guardrails interact with streaming?"**

⭐⭐ Directly, and it's the real design problem: you can't check an answer you've already shown. ⭐ Three
options. ⭐ Don't stream on high-risk paths — slower and correct. ⭐⭐ Stream and retract, which is
theatre, because the user already read it. ⭐ Or buffer and check in chunks: hold about two hundred
tokens, check, release. ⭐⭐ That costs one chunk of latency and keeps most of the streaming feel, and
it's usually what I'd ship.

**5. "What's the failure mode of a guardrail?"**

⭐ False positives, and almost nobody measures them. ⭐⭐ A five percent false-positive rate on a support
bot means one in twenty real users is blocked, and they don't file a bug — they stop using the product.
⭐ And they're not uniformly distributed: toxicity classifiers fire more on dialect, on non-English text,
and on discussions *about* harm — so a medical or safeguarding product blocks exactly its most important
conversations. ⭐⭐ That's a fairness problem as much as a UX one, and it's the thing I'd raise in a
design review. ⭐ So the guardrail gets its own eval set with three buckets: real attacks that must be
caught, benign traffic that must pass, and benign-but-similar — "how do I stop someone hacking my
account?" ⭐⭐ Bucket three is where every guardrail embarrasses itself and almost nobody builds it.

**6. "A user gets blocked. What do they see?"**

⭐ Something specific and a way out. ⭐⭐ "I can't help with payment details here, but I can connect you
to someone who can" beats a generic refusal, because a vague block reads as a broken product rather than
a policy. ⭐ And every block is logged with a reason code, which is what lets me measure the
benign-but-similar bucket in production rather than guessing. ⭐⭐ A block with no reason code is an
undebuggable product complaint.

## 🎙️ Articulation drill
