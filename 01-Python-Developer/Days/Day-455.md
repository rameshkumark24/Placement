# Day 455 🔭

**P-455** · 🔭 **Observability without a correct answer** — ⭐⭐ everything returns 200 while broken

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every request succeeds, every latency is normal and every error rate is
> zero while the system quietly serves nonsense — so you stop monitoring failures and start monitoring
> distributions, because the only thing that reliably changes when quality drops is the shape of your
> data, not the status code.**

# Part 1 — ⭐⭐ Why your existing monitoring cannot see this

```
⭐ ***A NORMAL SERVICE FAILS LOUDLY.*** ⭐ A 500, a timeout, a
⭐   null, a constraint violation. ⭐⭐ THE SIGNAL AND THE FAILURE
⭐   ARE THE SAME EVENT.

⭐ ***THIS SYSTEM FAILS SILENTLY, AND HERE IS THE FULL LIST OF
⭐   WAYS — ⭐⭐ EVERY ONE RETURNS 200:***
⭐   ⭐ retrieval returns nothing and the model answers from
⭐     memory (Day 449);
⭐   ⭐ the permission filter is bypassed by a cache hit
⭐     (Day 454);
⭐   ⭐ a provider silently updates a model behind a stable name;
⭐   ⭐ ⭐⭐ THE VALIDATION REPAIR LOOP ABSORBS A QUALITY
⭐     REGRESSION AND REPORTS SUCCESS (DAY 424);
⭐   ⭐ an injected document changes the answer (Day 446);
⭐   ⭐ chunking changes and recall drops 15 points;
⭐   ⭐ ⭐⭐ THE ANSWER IS CONFIDENT, FLUENT, WELL-CITED AND
⭐     WRONG.

⭐ ⭐⭐ ⇒ ERROR RATE: 0%. p99: NORMAL. UPTIME: 100%.
⭐   ***AND THE PRODUCT IS BROKEN.***

⭐ ⇒ ***THE THREE THINGS YOU MONITOR INSTEAD:***
⭐   ⭐ ① ***DISTRIBUTIONS*** — because a change in behaviour
⭐     moves a distribution before anyone files a ticket;
⭐   ⭐ ② ***PROXIES FOR CORRECTNESS*** — abstention rate,
⭐     validation failures, retrieval scores;
⭐   ⭐ ③ ⭐⭐ ***USER BEHAVIOUR*** — ⭐ which is the only source of
⭐     truth you have about whether the answer was any good.

# Part 2 — The wide event

```
⭐ ***ONE STRUCTURED EVENT PER REQUEST, WITH EVERYTHING ON IT***
⭐   (Day 393). ⭐⭐ NOT FIFTEEN LOG LINES — ⭐ one row you can
⭐   group by, because ***every question you will ask is a
⭐   `GROUP BY` you did not anticipate.***
```

@dataclass(frozen=True, slots=True)
class LLMEvent:
    # ⭐ identity and correlation
    trace_id: str; run_id: str | None
    tenant_id: str; user_id_hash: str        # ⭐⭐ HASHED (D450)
    feature: str                             # ⭐⭐ COST ATTRIBUTION (D457)

    # ⭐⭐ WHICH SYSTEM PRODUCED THIS? — the reproducibility key
    config_hash: str; prompt_version: str
    model: str; index_version: str

    # ⭐ retrieval
    retrieved_doc_ids: list[str]             # ⭐⭐ AUDIT TRAIL (D434)
    retrieval_scores: list[float]
    rerank_top_score: float | None
    context_tokens: int
    abstained_retrieval: bool

    # ⭐ generation
    prompt_tokens: int; cached_tokens: int; completion_tokens: int
    finish_reason: str                       # ⭐⭐ "length" IS A BUG

    # ⭐⭐ QUALITY PROXIES — THE ROWS THAT ACTUALLY DETECT THINGS
    schema_valid: bool

    business_rules_failed: list[str]

# Part 3 — ⭐⭐ The eight metrics that actually detect problems

```
⭐ ① ⭐⭐ ***ABSTENTION RATE.*** ⭐ The single best health signal.
⭐   ⭐ ***UP*** → retrieval broke: an index rebuild failed, an
⭐     embedding model changed, a tenant's documents vanished.
⭐   ⭐ ***DOWN*** → ⭐⭐ WORSE, AND COUNTERINTUITIVE: ⭐ the model
⭐     got more eager to please. ⭐⭐ A PROVIDER UPDATE THAT MAKES
⭐     IT MORE HELPFUL MAKES IT ***LESS HONEST***, AND EVERY
⭐     OTHER METRIC IMPROVES WHILE THIS ONE FALLS (D417/449).

⭐ ② ⭐⭐ ***REPAIR ATTEMPT RATE.*** ⭐ Your repair loop absorbs
⭐   failures and reports success (Day 424). ⭐⭐ A REPAIR RATE
⭐   CLIMBING FROM 2% TO 9% IS A REGRESSION THAT IS ***INVISIBLE
⭐   IN EVERY OTHER METRIC***, ⭐ because the requests all
⭐   succeeded. ⭐ Alert on it.

⭐ ③ ***`finish_reason == "length"` RATE.*** ⭐⭐ A TRUNCATED
⭐   ANSWER IS A ***WRONG*** ANSWER THAT PARSES. ⭐ Should be near
⭐   zero; a rise means prompts or outputs grew.

⭐ ④ ⭐⭐ ***RETRIEVAL SCORE DISTRIBUTION.*** ⭐ Track p50 of the
⭐   top score. ⭐⭐ A SUDDEN SHIFT MEANS THE INDEX, THE EMBEDDING
⭐   MODEL OR THE QUERY PATH CHANGED — ⭐ and it moves ***before***
⭐   users complain. ⭐ Cheapest early warning you own.

⭐ ⑤ ⭐⭐ ***OUTPUT LENGTH DISTRIBUTION.*** ⭐ The most reliable
⭐   detector of a silent provider model update. ⭐⭐ THE MEAN
⭐   MOVES 20% OVERNIGHT AND NOBODY TOLD YOU. ⭐ Check it against
⭐   your `model` field to catch pinned-alias drift.

⭐ ⑥ ***CACHE HIT RATE + FALSE-HIT RATE*** (Day 454).

⭐ ⑦ ***REPEAT-CALL RATE*** (Day 440) — agent health.

⭐ ⑧ ***COST PER REQUEST, p50 AND p99, BY FEATURE AND TENANT.***
⭐   ⭐⭐ THE p99 IS THE ONE THAT MATTERS: ⭐ a p50 of $0.01 with
⭐     a p99 of $2.40 means a small number of requests are doing
⭐     something you did not design (Day 457).

⭐⭐ ALERT ON ***DISTRIBUTION SHIFT***, NOT ON THRESHOLDS. ⭐ You
⭐   do not know the right value of any of these. ⭐⭐ YOU DO KNOW
⭐   THAT LAST WEEK'S VALUE WAS ACCEPTABLE — ⭐ so compare
⭐   today's distribution against a trailing baseline, per
⭐   feature.
```

```

⭐   ⭐ ⭐⭐ 100% OF: FAILURES, VALIDATION FAILURES, REPAIRS,

# 💬 Interview

**1. "How do you monitor an LLM feature?"**

⭐ Not the way I'd monitor a normal service, because everything here returns 200. ⭐⭐ Retrieval can find
nothing and the model answers from memory; a cache hit can bypass the permission filter entirely; the
provider can swap the model behind a stable name; the repair loop can absorb a quality regression and
report success. ⭐ Error rate zero, p99 normal, uptime a hundred percent, product broken. ⭐⭐ So I
monitor three things instead: distributions, proxies for correctness, and user behaviour. ⭐ And I alert
on distribution *shift* rather than thresholds, because I don't know the right value of any of these
metrics — but I do know last week's value was acceptable.

**2. "What's the single best health signal?"**

⭐ Abstention rate, and it's interesting in both directions. ⭐⭐ Up means retrieval broke — an index
rebuild failed, an embedding model changed, a tenant's documents vanished. ⭐ Down is the
counterintuitive one and it's worse: the model got more eager to please. ⭐⭐ A provider update that makes
it more helpful makes it less honest, and every other metric improves while this one falls. ⭐ Second is
repair-attempt rate: my validation repair loop silently absorbs failures and reports success, so a
repair rate climbing from two percent to nine is a real regression that is invisible in every other
metric because all those requests succeeded.

**3. "How would you catch a provider silently changing the model?"**

⭐ Three ways, and I'd have all three. ⭐⭐ Output length distribution is the most reliable — the mean
moves twenty percent overnight and nobody told you, and it's free to compute. ⭐ Retrieval and rerank
score distributions catch the embedding-side equivalent. ⭐⭐ And the nightly eval against **production
config**, which is the only measurement in the whole stack that actually knows the correct answer.
⭐ Everything else is a proxy; that one is ground truth, and it's the reason the eval harness has to be
runnable outside CI.

**4. "Users say it's gotten worse. How do you check?"**

⭐ I don't ask the model and I don't rely on thumbs. ⭐⭐ Explicit feedback is one to three percent of
users, skewed to the furious and the delighted, and the most common failure — a plausible wrong answer —
gets a thumbs *up*, because the user can't tell either. ⭐ The signal I'd reach for is the rephrase: the
user asking the same thing again in different words within sixty seconds. ⭐⭐ That's a failed answer
detected automatically with no click, and it's trivially computable — embed consecutive questions in a
session and flag high similarity. ⭐ Escalation to a human right after an answer is the other
unambiguous one, and it's already sitting in the support system.

**5. "What do you log, and what can you keep?"**

⭐ One wide structured event per request with everything on it, because every question I'll want to ask
is a `GROUP BY` I didn't anticipate — config hash, prompt version, model, index version, retrieved doc
ids and scores, token counts including cached, finish reason, schema validity, repair attempts, business
rules failed, abstention flags, cost, per-stage latency. ⭐⭐ The test for the schema is whether I can
answer "why did we give *that* answer to *that* user last Tuesday" from one row. ⭐ Payloads are
different: I keep a hundred percent of failures, repairs, thumbs-down, rephrases, escalations, gated
actions and anything over a cost threshold, and one to five percent of successes stratified by feature
and tenant so small tenants aren't invisible. ⭐⭐ I sample the payload, never the event — the event is
small, carries no sensitive content, and is what the alerting runs on.

**6. "What's the relationship between observability and your eval set?"**

⭐ They're the same flywheel. ⭐⭐ Every rephrase and every escalation is a labelled eval case, arriving
pre-labelled with "this failed", and I already have the full trajectory because the run was durable for
resumability. ⭐ So I triage twenty a week into the eval set. ⭐⭐ After three months the eval set is made
of real failures, which is the one asset a competitor can't copy — they can copy the prompt in a minute.
⭐ The privacy caveat from earlier applies: I desensitise at capture time and keep the shape rather than
the specifics.
