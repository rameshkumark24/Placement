# Part 1 — The three questions

```
⭐⭐ ***SQS — "WHO DOES THIS WORK?"***
⭐   ⭐ A durable buffer of ***tasks*** for one consumer group.
⭐   ⭐ Pull-based. ⭐ Each message is processed once (by someone).
⭐   ⭐⭐ IT CARRIES ***COMMANDS*** (DAY 333): `SendWelcomeEmail`.
⭐   ⭐ The producer knows what should happen.

⭐⭐ ***SNS — "WHO SHOULD KNOW?"***
⭐   ⭐ Push fan-out to N subscribers. ⭐ Every subscriber gets a
⭐     copy. ⭐ No storage of its own.
⭐   ⭐⭐ IT CARRIES ***EVENTS***: `UserRegistered`.
⭐   ⭐ The producer does not know or care who is listening.

⭐⭐ ***EVENTBRIDGE — "WHAT HAPPENED?"***
⭐   ⭐ A router with ***content-based*** filtering on the message
⭐     ***body***, ⭐ a schema registry, ⭐ 20+ target types,
⭐     ⭐⭐ AND ARCHIVE-AND-REPLAY.
⭐   ⭐ Also events — ⭐⭐ BUT WITH ROUTING LOGIC THAT LIVES IN
⭐     INFRASTRUCTURE RATHER THAN IN CODE.

⭐⭐ ⇒ AND DAY 333's TEST STILL DECIDES IT IN ONE MOVE:
⭐   ⭐⭐ ***DELETE EVERY SUBSCRIBER. IS THE PRODUCER STILL
⭐   CORRECT?***
⭐   ⭐ Yes → it published an ***event*** → SNS or EventBridge.
⭐   ⭐⭐ NO ("THE EMAIL NEVER GETS SENT") → IT ISSUED A
⭐     ***COMMAND*** → SQS, ⭐ and pretending otherwise gives you
⭐     a distributed monolith with a message broker in it.
```

# Part 2 — SQS mechanics, and the lease people think is a lock

```
⭐ STANDARD: ⭐ at-least-once, ⭐ best-effort ordering,
⭐   ⭐⭐ ESSENTIALLY UNLIMITED THROUGHPUT. ⭐ The default.
⭐ FIFO: ⭐ ordering ***per MessageGroupId***, ⭐ deduplication
⭐   within a ***5-minute*** window, ⭐ 300 tps (3,000 batched).
⭐   ⭐⭐ AND THE CRUCIAL LIMIT: ***THE DEDUP WINDOW IS FIVE
⭐   MINUTES, SO FIFO IS NOT AN IDEMPOTENCY STRATEGY*** — ⭐ a
⭐   retry an hour later, or a human replay next Tuesday, sails
⭐   straight through (Day 335). ⭐⭐ YOU STILL NEED YOUR OWN
⭐   DEDUP KEY IN THE SAME TRANSACTION AS THE WRITE.

⭐⭐ ***VISIBILITY TIMEOUT IS A LEASE, NOT A LOCK.***
⭐   ⭐ Receive a message → it is hidden for N seconds → ⭐ you
⭐     delete it, or ⭐⭐ IT REAPPEARS FOR SOMEONE ELSE.
⭐   ⭐⭐ IF PROCESSING TAKES LONGER THAN THE TIMEOUT, THE MESSAGE
⭐     IS REDELIVERED ***WHILE YOU ARE STILL WORKING ON IT.***
⭐     ⭐ Two workers now do the same job. ⭐ Both succeed. ⭐⭐ THE
⭐     CUSTOMER IS CHARGED TWICE, AND NOTHING IN ANY LOG SAYS
⭐     "DUPLICATE".
⭐   ⭐⭐ ⇒ ***VISIBILITY TIMEOUT > p99 PROCESSING TIME***, ⭐ and
⭐     for genuinely long jobs, ⭐⭐ HEARTBEAT WITH
⭐     `change_message_visibility` RATHER THAN SETTING A HUGE
⭐     TIMEOUT — ⭐ because a huge timeout means a crashed worker's
⭐     message is stuck for that long too. ⭐⭐ THIS IS EXACTLY DAY
⭐     343's LEASE ARGUMENT, AND THE FENCING-TOKEN LESSON
⭐     APPLIES: ***THE LEASE IS NOT A CORRECTNESS GUARANTEE.***

⭐ ⭐⭐ ALWAYS LONG POLLING (`WaitTimeSeconds=20`). ⭐ Short polling
⭐   costs more ***and*** returns empty responses from a subset
⭐   of servers, ⭐⭐ SO A NON-EMPTY QUEUE CAN RETURN NOTHING —
⭐   which people debug for hours.
⭐ ⭐ DLQ with `maxReceiveCount` (5 is sane). ⭐⭐ AND THE PART
⭐   PEOPLE SKIP: ***BUILD THE REDRIVE.*** ⭐ A DLQ with no alarm
⭐   and no path back is a data-loss device with extra steps.
```

# Part 3 — ⭐⭐ The consumer loop, and the batch bug

```python
# ⭐⭐ THE BUG — and it is in a very large fraction of real
# ⭐   Python consumers.
msgs = sqs.receive_message(QueueUrl=Q, MaxNumberOfMessages=10,
                           WaitTimeSeconds=20).get("Messages", [])
for m in msgs:
    handle(m)                       # ⭐⭐ ONE OF THESE RAISES
sqs.delete_message_batch(...)       # ⭐⭐ NEVER RUNS
# ⇒ ⭐⭐ ALL TEN REDELIVER. THE NINE THAT SUCCEEDED ARE PROCESSED
# ⭐   AGAIN. ⭐ Five times. ⭐⭐ THEN NINE GOOD MESSAGES LAND IN THE
# ⭐   DLQ ALONGSIDE THE ONE POISON MESSAGE.
```

```python
# ⭐⭐ THE FIX — delete per message, as each one succeeds.
for m in msgs:
    try:
        handle(m)                                  # ⭐ idempotent
        sqs.delete_message(QueueUrl=Q,
                           ReceiptHandle=m["ReceiptHandle"])
    except Exception:
        log.exception("msg_failed", extra={
            "message_id": m["MessageId"],
            "receive_count": m["Attributes"]["ApproximateReceiveCount"],
        })
        # ⭐⭐ DO NOT DELETE. Let visibility timeout + DLQ work.

# ⭐⭐ AND ON LAMBDA, THE SAME BUG HAS A ONE-LINE FIX PEOPLE DO
# ⭐   NOT KNOW ABOUT — enable ReportBatchItemFailures and:
def handler(event, ctx):
    failed = []
    for r in event["Records"]:
        try: handle(r)
        except Exception: failed.append({"itemIdentifier": r["messageId"]})
    return {"batchItemFailures": failed}     # ⭐⭐ ONLY THESE RETRY
```

```
⭐⭐ AND THE THREE RULES THAT MAKE A CONSUMER PROFESSIONAL:
⭐   ⭐⭐ ① ***IDEMPOTENT HANDLER, WITH THE DEDUP KEY WRITTEN IN
⭐      THE SAME TRANSACTION AS THE EFFECT*** (DAY 335). ⭐ At-
⭐      least-once is the contract; ⭐⭐ IDEMPOTENCY IS HOW YOU
⭐      SURVIVE IT.
⭐   ⭐ ② Log `ApproximateReceiveCount` — ⭐⭐ IT IS THE FASTEST
⭐      SIGNAL THAT SOMETHING IS RETRYING FOREVER.
⭐   ⭐⭐ ③ ALARM ON ***`ApproximateAgeOfOldestMessage`***, NOT ON
⭐      QUEUE DEPTH. ⭐ Depth spikes harmlessly during a burst;
⭐      ⭐⭐ AGE RISING MEANS YOU ARE NOT KEEPING UP, AND IT IS THE
⭐      METRIC THAT MAPS TO A CUSTOMER WAITING (DAY 322's
⭐      LITTLE'S LAW).
```

# Part 4 — SNS, and the fan-out pattern that is the default answer

```
⭐ SNS: ⭐ topic → many subscriptions (SQS, Lambda, HTTPS, email,
⭐   SMS). ⭐⭐ FILTER POLICIES ON MESSAGE ***ATTRIBUTES*** SO
⭐   SUBSCRIBERS DO NOT RECEIVE-AND-DISCARD — ⭐ which is both a
⭐   cost and a coupling win.

⭐⭐ ***THE PATTERN: SNS → SQS PER CONSUMER.*** ⭐ Not SNS →
⭐   Lambda, and never SNS → your HTTP endpoint. ⭐ Because:
⭐   ⭐⭐ ① SNS HAS NO STORAGE. ⭐ If a subscriber is down, SNS
⭐      retries on a schedule and then ***gives up***. ⭐ An SQS
⭐      queue holds the message for up to 14 days,
⭐      ⭐⭐ SO A CONSUMER CAN BE DOWN FOR AN HOUR AND LOSE
⭐      NOTHING.
⭐   ⭐⭐ ② EACH CONSUMER GETS ITS OWN BUFFER, ITS OWN RETRY
⭐      BEHAVIOUR AND ITS OWN DLQ — ⭐ so a slow consumer cannot
⭐      affect a fast one. ⭐⭐ THAT IS A BULKHEAD (DAY 336).
⭐   ⭐ ③ You can replay from the queue, and inspect it.
⭐   ⭐⭐ ④ ADDING A CONSUMER IS A NEW SUBSCRIPTION AND ***ZERO
⭐      PRODUCER CHANGES.*** ⭐ Which is the entire point of
⭐      publishing an event.

⭐ ⭐ FIFO topics exist and pair only with FIFO queues.
⭐ ⭐ Subscription DLQs exist — ⭐⭐ SET THEM, OR A FAILED DELIVERY
⭐   IS SIMPLY GONE.
```

# Part 5 — EventBridge, and the feature that justifies it

```
⭐ THE BUS: ⭐ default bus (AWS service events — ⭐⭐ EC2 STATE
⭐   CHANGES, ECS TASK STOPS, CODEPIPELINE — ⭐ free and
⭐   immediately useful), ⭐ custom buses, ⭐ partner buses.

⭐ RULES MATCH ON THE ***BODY***, not on attributes:
```

```json
{
  "source": ["flagship.orders"],
  "detail-type": ["OrderPlaced"],
  "detail": {
    "total":   [{"numeric": [">", 500]}],
    "country": ["GB", "IE"],
    "tier":    [{"anything-but": "free"}]
  }
}
```

```
⭐⭐ ⇒ SO ROUTING LOGIC MOVES FROM YOUR CODE INTO
⭐   INFRASTRUCTURE. ⭐ That is genuinely good (⭐ a new consumer
⭐   for high-value UK orders needs no producer change and no
⭐   deploy) ⭐⭐ AND GENUINELY DANGEROUS: ***BUSINESS LOGIC IN A
⭐   RULE IS INVISIBLE TO YOUR TESTS, YOUR TYPE CHECKER AND YOUR
⭐   CODE REVIEW.*** ⭐ Keep rules coarse; ⭐ keep decisions in
⭐   code.

⭐⭐ ***AND THE FEATURE THAT ACTUALLY JUSTIFIES EVENTBRIDGE:
⭐   ARCHIVE AND REPLAY.***
⭐   ⭐ Archive every event on the bus for N days.
⭐   ⭐⭐ THEN REPLAY THREE DAYS OF HISTORY INTO A ***NEW***
⭐     CONSUMER.
⭐   ⭐⭐ ⇒ THAT IS DAY 359's SHAPE ⑦ — ***A DERIVED STORE THAT IS
⭐     REBUILDABLE*** — AVAILABLE AS A MANAGED FEATURE. ⭐ You can
⭐     add a read model, a search index or an analytics consumer
⭐     and backfill it from the bus ⭐⭐ WITHOUT WRITING A BACKFILL
⭐     JOB. ⭐ Nothing else in this trio can do it.
⭐   ⭐ (Caveat: ⭐⭐ REPLAY RE-DELIVERS, SO YOUR CONSUMERS MUST BE
⭐     IDEMPOTENT — ⭐ Day 335, once more.)

⭐ COST AND LIMITS: ⭐ $1 per million events, ⭐ rules free.
⭐   ⭐⭐ LATENCY IS HIGHER (OFTEN ~0.5 s, OCCASIONALLY SECONDS)
⭐   AND THERE IS ***NO ORDERING***. ⭐⭐ SO IT IS NOT A REQUEST-
⭐   PATH COMPONENT, AND ANYTHING ORDER-SENSITIVE DOES NOT
⭐   BELONG ON IT.
⭐ ⭐ EventBridge Pipes: source → filter → enrich → target,
⭐   ⭐⭐ WITH NO LAMBDA IN THE MIDDLE FOR SIMPLE CASES.
⭐ ⭐ Scheduler: ⭐⭐ THE MODERN CRON — ONE-OFF AND RECURRING,
⭐   TIMEZONE-AWARE, AT SCALE.
```

# Part 6 — The anti-pattern gallery

```
⭐ ① ⭐⭐ ***SQS USED FOR PUB/SUB.*** ⭐ Two consumers need the
⭐    message, so you make two queues and ⭐⭐ CHANGE THE PRODUCER
⭐    TO WRITE TO BOTH. ⭐ Now every new consumer is a producer
⭐    deploy. ⭐⭐ THAT IS DAY 333's DISTRIBUTED MONOLITH, AND IT
⭐    IS THE COMMONEST OF THESE MISTAKES. ⭐ Fix: SNS → SQS.
⭐ ② ⭐⭐ ***EVENTBRIDGE USED AS A WORK QUEUE.*** ⭐ No visibility
⭐    timeout, no per-message lease, ⭐ half-second latency,
⭐    ⭐⭐ AND NO BACKPRESSURE — ⭐ so a slow consumer just gets
⭐    more events thrown at it.
⭐ ③ ⭐ ***SNS STRAIGHT TO AN HTTP ENDPOINT.*** ⭐⭐ YOUR SERVICE
⭐    IS NOW A PUBLIC WEBHOOK RECEIVER WITH SNS's RETRY POLICY AS
⭐    YOUR ONLY BUFFER, ⭐ and a deploy loses messages.
⭐ ④ ⭐⭐ ***FIFO CHOSEN "TO BE SAFE".*** ⭐ 300 tps, a five-minute
⭐    dedup window that is not idempotency, ⭐⭐ AND ORDERING ONLY
⭐    WITHIN A GROUP ID — ⭐ so if everything shares one group id
⭐    you have serialised your entire pipeline. ⭐⭐ ASK WHAT
⭐    ***ACTUALLY*** NEEDS ORDER: ⭐ usually it is per-entity
⭐    ("this user's events"), ⭐⭐ WHICH IS A GROUP ID, NOT A
⭐    GLOBAL GUARANTEE (DAY 334).
⭐ ⑤ ⭐⭐ ***A 256 KB MESSAGE LIMIT DISCOVERED IN PRODUCTION.***
⭐    ⭐ Fix: ⭐⭐ THE ***CLAIM-CHECK*** PATTERN — PUT THE PAYLOAD IN
⭐    S3, PUT THE KEY IN THE MESSAGE. ⭐ The extended client does
⭐    it for you. ⭐⭐ AND IT IS BETTER DESIGN ANYWAY: MESSAGES
⭐    STAY SMALL, CHEAP AND READABLE IN A DLQ.
⭐ ⑥ ⭐ ***NO ALARM ON THE DLQ.*** ⭐⭐ MESSAGES ARRIVE, NOBODY
⭐    LOOKS, THE RETENTION EXPIRES, AND THE DATA IS GONE
⭐    SILENTLY.
```

# 💬 Interview

**1. ⭐⭐ "SQS, SNS or EventBridge?"**
> ⭐ They answer three different questions. ⭐⭐ **SQS answers "who does this work" — a durable buffer of
> commands for one consumer group. SNS answers "who should know" — push fan-out of events, where the
> producer doesn't care who's listening. EventBridge answers "what happened" — routing with
> content-based filters on the body, plus archive and replay.** ⭐ And the test that decides it in one
> move is the same one from event-driven design: ⭐⭐ **delete every subscriber and ask whether the
> producer is still correct.** ⭐ If yes it published an event; if the answer is "the email never gets
> sent", it issued a command and it belongs on a queue.

**2. ⭐⭐ "Explain visibility timeout."**
> ⭐ It's a lease, not a lock. ⭐ You receive a message, it's hidden for N seconds, and you either
> delete it or it comes back for someone else. ⭐⭐ **The failure is when processing takes longer than
> the timeout: the message is redelivered while you're still working on it, two workers do the same
> job, both succeed, and the customer is charged twice with nothing in any log saying "duplicate".**
> ⭐ So the timeout must exceed p99 processing time, ⭐⭐ **and for long jobs you heartbeat with
> `change_message_visibility` rather than setting a huge timeout — because a huge timeout also means a
> crashed worker's message is stuck for that long.** ⭐ It's the same lease argument as a distributed
> lock: ⭐⭐ **the lease is not a correctness guarantee, so the handler has to be idempotent.**

**3. ⭐⭐ "What's wrong with receiving ten messages and deleting the batch at the end?"**
> ⭐ One failure loses all ten. ⭐⭐ **The delete never runs, so all ten redeliver and the nine that
> succeeded get processed again — five times — and then nine good messages land in the DLQ next to the
> one poison message.** ⭐ The fix is deleting per message as each succeeds, ⭐⭐ **and on Lambda it's a
> one-line fix people don't know about: enable `ReportBatchItemFailures` and return the failed
> message ids, so only those retry.**

**4. "Why SNS to SQS rather than SNS to Lambda?"**
> ⭐⭐ **Because SNS has no storage.** ⭐ If a subscriber is down, SNS retries on a schedule and then
> gives up; ⭐⭐ **an SQS queue holds the message for up to fourteen days, so a consumer can be down for
> an hour and lose nothing.** ⭐ It also gives each consumer its own buffer, retry behaviour and DLQ,
> so a slow consumer can't affect a fast one — that's a bulkhead. ⭐ And you can inspect and replay
> from a queue. ⭐⭐ **Plus the point of the whole pattern: adding a consumer is a new subscription and
> zero producer changes.**

**5. "When is EventBridge worth it over SNS?"**
> ⭐ Two reasons. ⭐ Content-based filtering on the body means routing lives in infrastructure — a new
> consumer for high-value UK orders needs no producer change — ⭐⭐ **though I'd keep rules coarse,
> because business logic in a rule is invisible to my tests, my type checker and code review.** ⭐ And
> the one that actually justifies it: ⭐⭐ **archive and replay. You can add a read model or a search
> index and backfill it by replaying three days of history off the bus, with no backfill job** — which
> is the rebuildable-derived-store property as a managed feature, and nothing else in the trio does
> it. ⭐ The costs are half-second latency and no ordering, ⭐⭐ **so it's never a request-path
> component.**

**6. "Would you use FIFO queues?"**
> ⭐ Only with a specific reason, because people pick it "to be safe" and inherit real limits.
> ⭐⭐ **300 transactions a second, a five-minute deduplication window — which is not an idempotency
> strategy, since a retry an hour later or a human replay next Tuesday sails through — and ordering
> only within a message group.** ⭐ So if everything shares one group id you've serialised the entire
> pipeline. ⭐⭐ **The right question is what actually needs order, and it's almost always per-entity —
> this user's events — which is a group id, not a global guarantee.** ⭐ And regardless of FIFO, the
> dedup key goes in my own database in the same transaction as the effect.

## 🎙️ Articulation drill

**Two minutes.** Refuse the feature-list framing: **these three answer different questions — who does
this work, who should know, what happened.** SQS carries commands to one consumer group; SNS fans out
events to subscribers the producer doesn't know about; EventBridge routes on content and can replay.
**And the deciding test is one move: delete every subscriber and ask whether the producer is still
correct. If the answer is "the email never gets sent", it was a command and it belongs on a queue.**
Then the mechanic worth knowing properly: **visibility timeout is a lease, not a lock — if processing
outlives it the message is redelivered while you're still working, two workers do the same job, both
succeed, and the customer is charged twice with nothing in the logs saying duplicate.** So the timeout
exceeds p99, long jobs heartbeat rather than taking a huge timeout, **and the handler is idempotent
with the dedup key written in the same transaction as the effect — because at-least-once is the
contract.** Give the consumer bug: **receive ten, delete the batch at the end, one raises — all ten
redeliver, nine succeed again five times, and nine good messages end up in the DLQ next to the poison
one.** Then the pattern: **SNS to SQS per consumer, because SNS has no storage — a queue holds
