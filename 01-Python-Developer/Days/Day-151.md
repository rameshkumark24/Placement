**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a Dockerfile is a cache key expressed as a file — every line's cache is
> invalidated by the line above it, so the *order* of your instructions determines whether a
> one-character code change rebuilds in four seconds or four minutes.**

# Part 1 — ⭐⭐ Layers and the cache: the ordering rule

```
⭐⭐ EVERY INSTRUCTION CREATES A LAYER. A LAYER IS CACHED UNTIL ITS INPUTS
⭐   CHANGE — AND ⭐ ONCE ONE LAYER IS INVALIDATED, EVERY LAYER AFTER IT IS
⭐   REBUILT TOO. That cascade is the whole optimisation.

⭐   ❌ THE ORDER EVERYONE WRITES FIRST:
⭐        COPY . .                      ⭐⭐ invalidated by ANY file change
⭐        RUN pip install -r requirements.txt
⭐        ⇒ ⭐⭐ EVERY CODE CHANGE REINSTALLS EVERY DEPENDENCY. 3 minutes for
⭐          a typo fix, on every commit, for every developer, forever.
⭐
⭐   ✅ ⭐⭐ THE ORDER THAT FOLLOWS FROM THE RULE — LEAST-CHANGING FIRST:
⭐        COPY requirements.txt .       ⭐ changes weekly
⭐        RUN pip install -r requirements.txt   ⭐⭐ CACHED across code changes
⭐        COPY . .                      ⭐ changes hourly
⭐        ⇒ ⭐ code change = 4 seconds. ⭐⭐ Same image, same content, purely
⭐          a consequence of ordering.
⭐
⭐   ⇒ ⭐⭐ THE GENERAL RULE: SORT INSTRUCTIONS BY HOW OFTEN THEIR INPUTS
⭐        CHANGE, RAREST FIRST. ⭐ Everything else in this part is that rule
⭐        applied.
```

```dockerfile
# ⭐⭐ AND `.dockerignore` — the file people skip, with three real costs
# .git            ⭐⭐ often HUNDREDS OF MB, and it contains every secret you
#                    ever committed (Day 150)
# .venv           ⭐ a Linux image with your host's macOS/Windows binaries
# __pycache__     ⭐ stale .pyc, and it CHANGES CONSTANTLY ⇒ busts the cache
# .env            ⭐⭐ Day 150 — in the layer forever
# tests/, docs/   ⭐ size
```

> ⭐⭐ **Without `.dockerignore`, the build context — everything in the directory — is uploaded to the
> daemon on every build.** ⭐ A 400 MB `.git` directory means every build starts with a 400 MB
> transfer, and `COPY . .` then invalidates on files that have nothing to do with your app.

# Part 2 — ⭐⭐ Multi-stage: the compiler that must not ship

```dockerfile
# syntax=docker/dockerfile:1
# ─────────── stage 1: BUILD ───────────
FROM python:3.12-slim AS builder
ENV PIP_NO_CACHE_DIR=1 PIP_DISABLE_PIP_VERSION_CHECK=1
RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential libpq-dev \
    && rm -rf /var/lib/apt/lists/*        # ⭐⭐ SAME RUN — see the box below

WORKDIR /app
COPY requirements.txt .
RUN python -m venv /opt/venv && /opt/venv/bin/pip install -r requirements.txt

# ─────────── stage 2: RUNTIME ───────────
FROM python:3.12-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends libpq5 \
    && rm -rf /var/lib/apt/lists/*        # ⭐ the RUNTIME lib only, not -dev

COPY --from=builder /opt/venv /opt/venv   # ⭐⭐ ONLY the built artefact crosses
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

RUN useradd --create-home --uid 10001 app     # ⭐⭐ Part 4
WORKDIR /app
COPY --chown=app:app . .
USER app

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]   # ⭐⭐ EXEC FORM
```

```
⭐⭐ WHY MULTI-STAGE IS NOT JUST "SMALLER":
⭐   ⭐ `build-essential` is ~300 MB. ⭐⭐ IT IS A COMPILER AND A LINKER SITTING
⭐     IN YOUR PRODUCTION IMAGE. ⭐ An attacker with code execution can BUILD
⭐     things there — ⭐⭐ so removing it is a SECURITY improvement, not only a
⭐     size one. Say it that way.
⭐   ⭐ smaller images pull faster ⇒ ⭐⭐ faster scale-up, faster rollback.
⭐     ⭐ During an incident, image pull time is on your recovery path.
⭐   ⭐ fewer packages ⇒ fewer CVEs ⇒ ⭐ less scanner noise, and the alerts
⭐     that remain are real.

⭐⭐ THE `rm -rf /var/lib/apt/lists/*` DETAIL, BECAUSE IT IS A CLASSIC:
⭐   ⭐ it MUST be in the SAME `RUN` as the `apt-get install`.
⭐   ⭐⭐ A SEPARATE `RUN rm` DOES NOT SHRINK THE IMAGE — the files are already
⭐     committed in the previous layer, and a later layer only records a
⭐     DELETION MARKER. ⭐ Layers are additive; nothing is ever truly removed.
⭐   ⇒ ⭐⭐ IDENTICAL FACT TO Day 150's secret-in-a-layer AND Day 084's git
⭐     objects. ⭐ Three systems, one property: content-addressed history never
⭐     forgets.
```

# Part 3 — ⭐⭐ Reproducibility: the build that works on Tuesday and fails on Friday

```
⭐⭐ THREE SOURCES OF NON-DETERMINISM, ALL AVOIDABLE:

⭐  1. ⭐⭐ UNPINNED DEPENDENCIES. `fastapi` in requirements.txt means the
⭐       build resolves whatever exists TODAY. ⭐ Tuesday's image and Friday's
⭐       image are different programs from the same commit — ⭐⭐ which
⭐       destroys the one thing a commit hash is supposed to guarantee.
⭐       ⇒ ⭐ A LOCK FILE with hashes: `uv.lock`, `poetry.lock`, or
⭐         `pip-compile --generate-hashes`. ⭐⭐ Hashes also defend against a
⭐         compromised or re-uploaded package.
⭐
⭐  2. ⭐ FLOATING BASE IMAGES. `python:3.12-slim` moves. ⭐⭐ Pin by DIGEST
⭐       (`python:3.12-slim@sha256:...`) when you need real reproducibility,
⭐       ⭐ and update it deliberately — because pinning also means you stop
⭐       receiving security patches until you act.
⭐
⭐  3. ⭐ `apt-get install` WITHOUT VERSIONS. ⭐⭐ Same problem, one layer down.
⭐
⭐   ⇒ ⭐⭐ THE PRINCIPLE: A COMMIT HASH SHOULD DETERMINE AN IMAGE. If it does
⭐        not, then "we rolled back to the last good commit" ⭐ does not mean
⭐        you rolled back to the last good IMAGE — and your rollback can
⭐        contain a dependency that was never tested.
```

```dockerfile
# ⭐⭐ uv — worth knowing, because it is ~10× faster and cache-friendly
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev              # ⭐⭐ --frozen = FAIL if lock is stale
```

> ⭐ `--mount=type=cache` is a BuildKit cache that **persists across builds without becoming a
> layer** — ⭐⭐ so you get the speed of a warm package cache without shipping it. ⭐ And `--frozen`
> means a lockfile that does not match `pyproject.toml` fails the build rather than silently
> resolving something new, which is the whole point of having a lockfile.

# Part 4 — ⭐⭐ Runtime correctness: PID 1, users, and signals

```
⭐⭐ PID 1 — Day 083, and it is the single most consequential line in the file:

⭐   ❌ CMD uvicorn app.main:app          ⭐ SHELL FORM
⭐        ⇒ runs `/bin/sh -c "uvicorn ..."` ⇒ ⭐⭐ SH IS PID 1 AND DOES NOT
⭐          FORWARD SIGNALS ⇒ `docker stop` is ignored ⇒ 10 s wait ⇒ SIGKILL
⭐          ⇒ ⭐ every in-flight request truncated, every deploy (Day 149)
⭐   ✅ ⭐⭐ CMD ["uvicorn", "app.main:app"]   ⭐ EXEC FORM — uvicorn IS PID 1
⭐          and installs its own SIGTERM handler
⭐
⭐   ⭐⭐ AND IF YOUR PROCESS SPAWNS CHILDREN (gunicorn, Celery with prefork):
⭐        ⭐ add `tini` as PID 1. Not for signals — for ⭐⭐ ZOMBIE REAPING.
⭐        ⭐ PID 1 is responsible for reaping orphaned children; ⭐⭐ a Python
⭐        process at PID 1 does not, so zombies accumulate until you exhaust
⭐        the PID table. ⭐ Slow, silent, and baffling when it happens.
⭐        ENTRYPOINT ["/usr/bin/tini", "--"]
```

```
⭐⭐ NON-ROOT — and the reason that is NOT "best practice says so":
⭐   ⭐ containers share the HOST KERNEL (Day 078). ⭐⭐ Root in the container
⭐     is (by default) root on the host UID-wise — so a container escape, a
⭐     bad `--privileged`, or a writable host mount is game over.
⭐   ⭐ Day 079's concrete version: a root container writing to a mounted
⭐     volume creates ⭐⭐ ROOT-OWNED FILES ON THE HOST that your user cannot
⭐     delete. ⭐ Everyone meets this once.
⭐   ⇒ ⭐ `useradd --uid 10001` + `USER app`. ⭐⭐ Use a HIGH, EXPLICIT UID so
⭐     Kubernetes `runAsNonRoot` can verify it, and so it does not collide
⭐     with a host user.
⭐   ⚠ ⭐ Do `USER app` LATE — you need root for `apt-get` — ⭐⭐ and
⭐     `COPY --chown=app:app`, or your files are root-owned and unwritable.
⭐   ⭐ Ports < 1024 need root: ⭐⭐ bind 8000, not 80. The load balancer maps it.
```

```
⭐ FOUR ENV VARS THAT ARE ALL LOAD-BEARING:
⭐   ⭐⭐ PYTHONUNBUFFERED=1        — Day 079. Without it stdout is BLOCK-
⭐        buffered when not a TTY ⇒ ⭐ `docker logs` is EMPTY during the
⭐        incident, and your logs appear only after the crash. ⭐⭐ Or worse,
⭐        are lost with the buffer.
⭐   ⭐ PYTHONDONTWRITEBYTECODE=1  — no `.pyc` in a read-only filesystem
⭐   ⭐ PYTHONFAULTHANDLER=1       — ⭐⭐ a traceback on SIGSEGV/SIGABRT.
⭐        Otherwise a C-extension crash gives you a dead container and NOTHING.
⭐   ⭐ PIP_NO_CACHE_DIR=1         — do not ship pip's download cache
```

# Part 5 — ⭐ Base images, size, and what a healthcheck is for

```
⭐⭐ THE FOUR CHOICES, WITH THE ONE THAT IS A TRAP:
⭐   ⭐ python:3.12          ~1 GB   ⭐ full Debian. Only for debugging.
⭐   ⭐⭐ python:3.12-slim    ~150 MB ⭐⭐ THE DEFAULT ANSWER. Debian, glibc,
⭐        wheels work, `apt-get` available when you need it.
⭐   ⭐⭐ python:3.12-alpine  ~60 MB  ⭐⭐ THE TRAP. Alpine uses musl, not
⭐        glibc, so ⭐ MANY WHEELS DO NOT MATCH and pip COMPILES FROM SOURCE:
⭐        ⭐⭐ builds go from 30 s to 10 minutes, images can end up LARGER, and
⭐        you inherit musl's DNS and threading differences. ⭐ Known slower
⭐        for some workloads. ⭐⭐ Say "slim, not alpine, because musl breaks
⭐        the manylinux wheel ecosystem" — it is a strong signal.
⭐   ⭐ distroless / chainguard  ~50 MB  ⭐ no shell, no package manager.
⭐        ⭐⭐ Excellent security posture (no shell = far less useful RCE),
⭐        ⭐ and you cannot `exec` in to debug. ⭐ A real trade, not a free win.

⭐⭐ HEALTHCHECK IN THE DOCKERFILE:
⭐   ⭐ HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
⭐       CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8000/healthz')"
⭐   ⭐⭐ USEFUL FOR compose AND Swarm. ⭐ IGNORED BY KUBERNETES, which uses its
⭐     own probes (Day 149). ⭐⭐ Know which orchestrator reads it — people
⭐     debug a Dockerfile HEALTHCHECK for an hour before learning k8s never
⭐     looked at it.
```

```
⭐⭐ AND THE THREE THINGS THAT MAKE AN IMAGE OPERABLE, NOT JUST BUILDABLE:
⭐   ⭐ LABELS with the commit sha and build time — ⭐⭐ so "which code is this
⭐     running?" has an answer during an incident (Day 146's `version` field
⭐     comes from here).
⭐        LABEL org.opencontainers.image.revision=$GIT_SHA
⭐   ⭐ TAG BY IMMUTABLE SHA, NEVER DEPLOY `:latest` — ⭐⭐ `latest` means two
⭐     pods can run different code with the same tag, and a rollback has
⭐     nothing to roll back TO.
⭐   ⭐ SCAN IN CI (`trivy`, `grype`) and ⭐⭐ FAIL ON *FIXABLE* HIGH/CRITICAL
⭐     ONLY — ⭐ failing on unfixable CVEs teaches people to add `--exit-code
⭐     0`, and then the scan is decoration.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `COPY . .` before `pip install` | Every code change reinstalls every dependency. Copy the requirements file first. |
| No `.dockerignore` | Ships `.git` (and its secrets), the host `.venv`, and busts the cache on `__pycache__`. |
| `rm` in a separate `RUN` from the install | Layers are additive; the deletion is only a marker. Same `RUN`. |
| Build tools in the runtime image | ~300 MB, and a compiler in production is a security problem, not just a size one. |
| Unpinned dependencies | A commit hash no longer determines an image, so a rollback isn't a rollback. |
| Floating base image tag | Same problem one layer down. Pin by digest when reproducibility matters. |
| Shell-form `CMD` | `/bin/sh` becomes PID 1 and swallows SIGTERM — every deploy truncates requests. |
| No init when spawning children | PID 1 must reap; Python doesn't, so zombies accumulate until the PID table fills. |
| Running as root | Root in the container is root on the shared kernel, and it creates root-owned files on mounts. |
| `USER` before `apt-get` | The install fails; put `USER` late. |
| `COPY` without `--chown` after `USER` | Files are root-owned and your process can't write them. |
| Binding port 80 | Requires root. Bind 8000 and let the LB map it. |
| Missing `PYTHONUNBUFFERED` | `docker logs` is empty during the incident, and buffered lines can be lost entirely. |
| Alpine for a Python service | musl breaks manylinux wheels — slow builds, sometimes larger images, subtle runtime differences. |
| Expecting Kubernetes to use `HEALTHCHECK` | It doesn't. It uses its own probes. |
| Deploying `:latest` | Two pods can run different code under one tag, and rollback has no target. |
| Failing CI on unfixable CVEs | People disable the scan, and then it's decoration. |

## Interview questions

**Q: Your Docker build takes four minutes for a one-line code change. Why?**

> Layer ordering. A layer's cache is invalidated when its inputs change, and everything after an
> invalidated layer rebuilds too. If `COPY . .` comes before `pip install`, then any file change
> invalidates the copy, so the install rebuilds every time. Copying `requirements.txt` first and
> installing before copying the source means the dependency layer is keyed only on that file, so it
> stays cached across code changes and the rebuild is a few seconds. Same image, same content — pure
> ordering. The general rule is to sort instructions by how often their inputs change, rarest first.
> I'd also check `.dockerignore`, because without it the whole `.git` directory is uploaded as build
> context on every build and `COPY . .` invalidates on files that have nothing to do with the app.

**Q: Why multi-stage?**

> Because the toolchain needed to *build* the dependencies has no business being in the image that
> runs them. `build-essential` and `libpq-dev` are about three hundred megabytes, and more
> importantly they're a compiler and linker sitting in production — an attacker with code execution
> can build things there, so removing them is a security improvement, not just a size one. The
> practical benefits compound: smaller images pull faster, which matters because image pull time sits
> on your recovery path during an incident, and fewer packages means fewer CVEs and less scanner
> noise, so the alerts that remain are real.

**Q: You add `RUN rm -rf /var/lib/apt/lists/*` as its own line and the image doesn't shrink. Why?**

> Because layers are additive and immutable. The files were already committed in the previous layer;
> a later layer can only record a deletion marker, so the bytes are still in the image and still
> pulled. The removal has to happen in the same `RUN` as the install, so the layer is never created
> containing them. It's exactly the same property as a secret in a Docker layer or a secret in git
> history — content-addressed history doesn't forget, which is why in all three cases you have to
> prevent rather than clean up.

**Q: Why not Alpine? It's much smaller.**

> Because Alpine uses musl rather than glibc, and the Python wheel ecosystem is built around
> manylinux, which is glibc. So a lot of packages have no matching wheel and pip compiles from
> source — builds go from thirty seconds to ten minutes, and once you've installed the build
> toolchain the image can end up *larger* than slim. You also inherit musl's differences in DNS
> resolution and threading, which produce subtle bugs that don't reproduce anywhere else. My default
> is `python:3.12-slim`. If I genuinely need a minimal attack surface I'd go to distroless, and
> accept the real trade that there's no shell to exec into when debugging.

**Q: What are the runtime correctness issues in a Python Dockerfile?**

> Three. PID 1: shell-form `CMD` puts `/bin/sh` at PID 1 and it doesn't forward signals, so
> `docker stop` is ignored, you wait out the grace period, and SIGKILL truncates every in-flight
> request on every deploy. Exec form makes uvicorn PID 1 with its own handler; if the process spawns
> children I add `tini`, not for signals but for zombie reaping, since PID 1 is responsible for
> reaping orphans and Python doesn't. Non-root: containers share the host kernel, so root in the
> container is a much shorter path to root on the host, and concretely a root container writing to a
> mounted volume creates root-owned files nobody can delete. And `PYTHONUNBUFFERED`, because
> otherwise stdout is block-buffered when it isn't a TTY, so `docker logs` is empty exactly when
> you're looking at it during an incident.

## 🎙️ Articulation drill

**Two minutes: "Walk me through your Dockerfile."**

Go top to bottom and give the reason for each choice rather than the choice. Base image: slim, and
say why not alpine — musl versus the manylinux wheel ecosystem. Ordering: dependencies before source,
because a layer's cache dies with the layer above it. Multi-stage, framed as removing a compiler from
production rather than as saving megabytes. Then runtime correctness in three beats: exec-form `CMD`
so uvicorn is PID 1 and actually receives SIGTERM, a non-root high UID, and `PYTHONUNBUFFERED` so the
logs exist during the incident. Close on reproducibility — **a lockfile with hashes and a pinned base
digest, because otherwise a commit hash doesn't determine an image and your rollback isn't one.**
