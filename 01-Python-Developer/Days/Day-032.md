# Part 1 — ⭐⭐ What `x.y` actually does

```
⭐⭐ ATTRIBUTE LOOKUP ORDER — memorise this; it explains every surprise in this area:

⭐   x.y  ⇒ calls type(x).__getattribute__(x, "y"), which does:
⭐
⭐   1. ⭐⭐ search type(x).__mro__ for "y"
⭐        ⇒ if found AND it is a DATA DESCRIPTOR (has __set__ or __delete__)
⭐          ⇒ ⭐⭐ CALL ITS __get__ AND STOP.   ⭐ ← data descriptors WIN over the instance
⭐   2. ⭐ look in x.__dict__ ⇒ if found, return it
⭐   3. ⭐ back to the class: if it is a NON-DATA descriptor (only __get__) ⇒ call __get__
⭐        ⇒ else return the class attribute itself
⭐   4. ⭐⭐ nothing found ⇒ call type(x).__getattr__(x, "y") if it exists
⭐   5. ⇒ AttributeError
```

```
⭐⭐ THE TWO CONSEQUENCES THAT MATTER:
⭐   · ⭐⭐ a `property` (a DATA descriptor) CANNOT be shadowed by an instance attribute —
⭐     self.__dict__["y"] = 5 does not override it. That is step 1 beating step 2.
⭐   · ⭐ a plain function (a NON-data descriptor) CAN be shadowed per instance —
⭐     which is how monkey-patching one object's method works.
```

## ⭐ `__getattr__` vs `__getattribute__`

| | ⭐ `__getattr__` | ⭐⭐ `__getattribute__` |
|---|---|---|
| Called | ⭐ **only when normal lookup FAILED** | ⭐⭐ **on EVERY attribute access** |
| Risk | low | ⭐⭐ **infinite recursion, and it is easy** |
| Use for | ⭐ proxies, lazy attributes, nice errors | ⭐ almost never |

```python
class Config:
    def __init__(self, d): self._d = d
    def __getattr__(self, name):          # ⭐ only reached when normal lookup failed
        try: return self._d[name]
        except KeyError:
            raise AttributeError(name) from None    # ⭐⭐ raise AttributeError, not KeyError —
                                                    # hasattr() and getattr(default) depend on it

class Bad:
    def __getattribute__(self, name):
        return self.__dict__[name]        # ⚠️⚠️ ⭐⭐ `self.__dict__` is ITSELF an attribute access
                                          # ⇒ INFINITE RECURSION ⇒ RecursionError
        # ⭐ correct: return object.__getattribute__(self, name)
```

⚠️ ⭐⭐ **The `__getattr__` gotcha that costs an afternoon:** a class with `__getattr__` returning
something for *any* name makes `hasattr(x, anything)` return `True`, breaks `copy`, `pickle` and
`deepcopy` (which probe for `__deepcopy__`, `__reduce__`, `__getstate__`), and confuses debuggers.
**Always raise `AttributeError` for names you do not handle, and exclude dunders explicitly.**

# Part 2 — ⭐⭐ Descriptors

```python
class Positive:
    def __set_name__(self, owner, name):        # ⭐ called at class creation — you get your OWN name
        self.name = "_" + name
    def __get__(self, obj, objtype=None):
        if obj is None: return self             # ⭐⭐ accessed on the CLASS, not an instance
        return getattr(obj, self.name)
    def __set__(self, obj, value):              # ⭐⭐ having __set__ makes this a DATA descriptor
        if value <= 0: raise ValueError(f"{self.name} must be positive")
        setattr(obj, self.name, value)

class Account:
    balance = Positive()                        # ⭐ ONE descriptor object, on the CLASS
    def __init__(self, b): self.balance = b     # ⭐⭐ goes through __set__ — validated

Account(-5)        # ⭐ ValueError
```

| ⭐ Kind | ⭐ Defines | ⭐ Priority |
|---|---|---|
| ⭐⭐ **Data descriptor** | `__get__` + (`__set__` or `__delete__`) | ⭐⭐ **beats the instance dict** |
| ⭐ Non-data descriptor | `__get__` only | ⭐ instance dict wins |

⚠️ ⭐⭐ **The descriptor instance lives on the class, so it is shared by every instance** — which is
why `__set_name__` exists and why the value must be stored *on the object* (`obj.__dict__` or a
private name), never on `self`. **Storing state on the descriptor is the classic beginner bug: every
account shares one balance.**

# Part 3 — ⭐⭐ Everything you already use is a descriptor

```python
# ⭐ 1. property — a data descriptor, and this is the whole implementation in spirit:
class property_:
    def __init__(self, fget): self.fget = fget
    def __get__(self, obj, objtype=None):
        if obj is None: return self
        return self.fget(obj)
    def __set__(self, obj, value): raise AttributeError("read-only")

class Circle:
    def __init__(self, r): self.r = r
    @property
    def area(self): return 3.14159 * self.r ** 2      # ⭐ computed, accessed like an attribute
    @area.setter
    def area(self, v): self.r = (v / 3.14159) ** 0.5
```

```
⭐⭐ 2. FUNCTIONS ARE NON-DATA DESCRIPTORS. This is where BOUND METHODS come from:
⭐   Account.deposit          ⇒ ⭐ a plain function
⭐   account.deposit          ⇒ ⭐⭐ function.__get__(account, Account) ⇒ a BOUND METHOD
⭐   ⇒ ⭐⭐ THAT is how `self` gets passed. It is not magic and it is not syntax —
⭐        it is the descriptor protocol applied to functions.
⭐
⭐ 3. classmethod / staticmethod ⇒ descriptors that bind differently (or not at all)
⭐ 4. __slots__ (Day 028)        ⇒ each slot is a descriptor over fixed storage
⭐ 5. functools.cached_property  ⇒ ⭐⭐ a NON-data descriptor: computes once, then writes into
⭐                                  the instance dict — and step 2 of the lookup then wins forever
```

⭐⭐ **`cached_property` is the best illustration of why data vs non-data matters.** It defines only
`__get__`, so after the first access it stores the result in `self.__dict__` and the instance dict
takes priority on every subsequent access — **zero overhead thereafter, no cache dict, no
invalidation logic.** ⚠️ It needs a `__dict__`, so **it does not work with `__slots__`**.

```python
from functools import cached_property
class Report:
    @cached_property
    def rows(self):                      # ⭐ expensive query, run at most once per instance
        return db.fetch_all()
del report.rows                          # ⭐ invalidate by deleting from the instance dict
```

# Part 4 — ⭐ Where you meet this in real code

```python
# ⭐⭐ SQLAlchemy: `User.name` on the CLASS returns an expression object; on an INSTANCE it
#     returns the loaded value. That asymmetry is the `if obj is None: return self` branch.
session.query(User).filter(User.name == "ada")   # ⭐ builds SQL — class access
user.name                                        # ⭐ "ada" — instance access

# ⭐ Django's model fields, Pydantic's fields, and attrs all work the same way.
```

⭐⭐ **This also explains the N+1 problem's mechanism** (Stage 5): `order.customer` looks like an
attribute read, and it is a descriptor that **issues a SQL query**. In a loop over 100 orders that is
100 queries — **because attribute access in Python is a protocol, an innocuous-looking line can do
arbitrary work.**

```
⭐⭐ WHEN TO WRITE A DESCRIPTOR YOURSELF — the honest answer:
⭐   ✓ ⭐ the same validation/conversion logic repeated across many attributes and classes
⭐   ✓ ⭐ you are building a framework or an ORM-like API
⭐   ✗ ⭐⭐ one computed attribute        ⇒ use @property
⭐   ✗ ⭐⭐ one expensive computed value  ⇒ use @cached_property
⭐   ✗ ⭐⭐ validating request/config data ⇒ use PYDANTIC (Stage 3). Do not rebuild it.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`self.x` inside `__getattribute__`** | ⭐⭐ Infinite recursion. Use `object.__getattribute__`. |
| ⭐ Raising `KeyError` from `__getattr__` | ⭐⭐ `hasattr` and `getattr(default)` expect `AttributeError`. |
| `__getattr__` answering every name | ⭐ Breaks `copy`, `pickle` and debuggers. Exclude dunders. |
| ⭐⭐ Storing per-instance state on the descriptor | ⭐⭐ It lives on the class — every instance shares it. |
| Hand-writing the private name | ⭐ `__set_name__` gives it to you. |
| Forgetting `if obj is None: return self` | ⭐ Class-level access breaks. |
| Expecting a `property` to be shadowable | ⭐⭐ Data descriptors beat the instance dict. |
| `cached_property` with `__slots__` | ⭐ It needs `__dict__`. |
| Never invalidating a `cached_property` | ⭐ `del obj.attr`. |
| Writing descriptors for validation | ⭐⭐ Pydantic already does it, better. |

## Interview questions

**Q: What happens when you write `obj.attr`?**
> `__getattribute__` runs. It walks the type's MRO first: if it finds a data descriptor — something
> with `__set__` or `__delete__` as well as `__get__` — it calls `__get__` and stops, which is why a
> `property` can't be shadowed by an instance attribute. Otherwise it checks the instance `__dict__`.
> If that misses, it goes back to the class for a non-data descriptor or a plain attribute. And only
> if all of that fails does `__getattr__` get called, which is why `__getattr__` is the safe hook and
> `__getattribute__` is the dangerous one.

**Q: `__getattr__` versus `__getattribute__`?**
> `__getattr__` is a fallback, called only when normal lookup has already failed, so it's cheap and
> safe — good for proxies, lazy loading, or better error messages. `__getattribute__` intercepts
> every attribute access including the ones your own implementation makes, so a naive implementation
> that touches `self.anything` recurses infinitely; you have to delegate to
> `object.__getattribute__`. I've essentially never needed the second one.

**Q: What is a descriptor, and why should I care?**
> Any object that defines `__get__`, and optionally `__set__` or `__delete__`, placed as a class
> attribute. It lets attribute access run code. I should care because the things I use every day are
> descriptors: `property`, `classmethod`, `staticmethod`, `cached_property`, slots — and, crucially,
> plain functions, which is where bound methods come from. `obj.method` is
> `function.__get__(obj, type)` returning a bound method, which is how `self` gets supplied. It isn't
> syntax; it's the protocol.

**Q: Data versus non-data descriptor?**
> A data descriptor defines `__set__` or `__delete__` and takes priority over the instance
> dictionary; a non-data descriptor defines only `__get__` and loses to it. That difference is the
> whole design of `cached_property`: it's non-data, so on first access it computes the value and
> writes it into the instance dict, and every later access finds the instance dict first and skips
> the descriptor entirely. Zero overhead afterwards, and invalidation is just `del obj.attr`.

**Q: Where does this show up in libraries you use?**
> SQLAlchemy and Django models. `User.name` accessed on the class returns a query expression;
> accessed on an instance it returns the value — that asymmetry is the `if obj is None: return self`
> branch in `__get__`. It also explains the mechanism behind N+1 queries: `order.customer` looks like
> an attribute read but is a descriptor that issues SQL, so a loop over a hundred orders quietly runs
> a hundred queries. Attribute access in Python can do arbitrary work, and that's worth remembering
> when reading a hot loop.

**Q: Would you write one?**
> Rarely. For one computed attribute I'd use `property`; for an expensive one, `cached_property`; for
> validating incoming data, Pydantic — which is a much better-tested version of what I'd write. A
> hand-rolled descriptor earns its place when the same validation or conversion logic repeats across
> many attributes and classes, or when I'm building the framework rather than using one.
