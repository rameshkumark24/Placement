# Part 1 — ⭐⭐ The relay: from outbox row to queue

```python
# worker/relay.py — ⭐ runs continuously, or on a short schedule
def relay_once(db: Session, batch: int = 100) -> int:
    rows = db.scalars(
        select(Outbox).where(Outbox.published_at.is_(None))
        .order_by(Outbox.id).limit(batch)
        .with_for_update(skip_locked=True)          # ⭐⭐ THE line that allows N relays
    ).all()
    for row in rows:
        publish(row.topic, row.payload, headers=trace_headers())   # ⭐ Day 148 carrier
        row.published_at = now()
    db.commit()                                      # ⭐ marks the whole batch
    return len(rows)
```

```
⭐⭐ WHY `SKIP LOCKED` IS THE WHOLE TRICK:
⭐   ⭐ two relays start. Relay A locks rows 1–100. ⭐⭐ Relay B does NOT block
⭐     and does NOT see them — it takes 101–200. ⭐ Without `SKIP LOCKED`,
⭐     B waits for A and your relay is single-threaded by construction.
⭐   ⇒ ⭐⭐ SO THE RELAY SCALES HORIZONTALLY WITH NO COORDINATION AND NO LOCK
⭐     SERVICE. ⭐ That is a genuinely elegant property and worth naming.

⭐⭐ AND THE GUARANTEE THE RELAY ACTUALLY PROVIDES — be precise:
⭐   ⭐ it publishes, THEN marks. ⭐⭐ If it dies in between, the row is
⭐     unmarked and gets published AGAIN ⇒ ⭐ AT-LEAST-ONCE.
⭐   ⭐ marking first would be at-most-once ⇒ ⭐⭐ silent loss, which is worse.
⭐   ⇒ ⭐⭐ AT-LEAST-ONCE IS THE CORRECT CHOICE **BECAUSE** THE CONSUMER IS
⭐     IDEMPOTENT (Part 2). ⭐ Those two decisions are one decision, and you
⭐     should state them together.

⭐ ⭐⭐ MONITOR: OLDEST UNPUBLISHED OUTBOX ROW AGE (Day 147). ⭐ Not the count.
⭐   ⭐⭐ Count 3 with age two hours is a dead relay, and count alone cannot
⭐   tell you that. ⭐ Alert on age > 60 s.
```

# Part 2 — ⭐⭐ The worker, and the rule from Day 163 paying off

```python
# worker/tasks.py
@celery_app.task(bind=True, acks_late=True,                   # ⭐⭐ at-least-once
                 autoretry_for=(TransientError,),
                 retry_backoff=True, retry_jitter=True,       # ⭐ Day 142
                 retry_kwargs={"max_retries": 6},
                 time_limit=60, soft_time_limit=50)           # ⭐ or a slot is held forever
def send_order_confirmation(self, order_id: int, organiser_id: str, otel: dict) -> None:
    ctx = extract(otel)                                        # ⭐⭐ Day 148 — or orphan trace
    with tracer.start_as_current_span("send_order_confirmation", context=ctx):
        bind_contextvars(order_id=order_id, organiser_id=organiser_id)   # ⭐ Day 146
        with SessionLocal() as db:
            set_tenant(UUID(organiser_id))                     # ⭐⭐ Day 160 — re-establish
            updated = db.execute(
                update(Order)
                .where(Order.id == order_id, Order.confirmation_sent_at.is_(None))
                .values(confirmation_sent_at=now())
            ).rowcount
            if updated == 0:
                return                                          # ⭐⭐ already sent — idempotent
            db.commit()
            mailer.send(...)                                    # ⭐ flag-first: at-most-once
```

```
⭐⭐ THREE THINGS THIS TASK GETS RIGHT THAT ARE EASY TO GET WRONG:
⭐  1. ⭐⭐ IT TAKES AN ID, NOT AN OBJECT (Day 142). ⭐ An ORM object is not
⭐       JSON-serialisable, is stale by the time it runs, and is detached in a
⭐       process with no session.
⭐  2. ⭐⭐ IT CARRIES `organiser_id` AND `otel` EXPLICITLY. ⭐ The request is
⭐       gone: the `ContextVar` is gone and `SET LOCAL` ended with its
⭐       transaction. ⭐⭐ This is where tenant isolation and tracing are most
⭐       often lost, and both are one field in the payload.
⭐  3. ⭐⭐ THE SERVICE FUNCTIONS IT CALLS IMPORT NO FastAPI. ⭐ Day 163's CI
⭐       grep is what makes today free instead of a refactor — ⭐⭐ there is no
⭐       `Depends` here and nowhere for an `HTTPException` to go.

⭐⭐ AND THE HONEST TRADE IN `updated == 0` / FLAG-FIRST:
⭐   ⭐ set the flag, then send ⇒ ⭐⭐ a crash in between LOSES the email.
⭐   ⭐ send, then set the flag ⇒ ⭐⭐ a crash in between SENDS IT TWICE.
⭐   ⇒ ⭐ FOR EMAIL, THE DUPLICATE IS BETTER — so flag AFTER for email.
⭐   ⇒ ⭐⭐ FOR MONEY, NEITHER IS ACCEPTABLE, WHICH IS EXACTLY WHY PART 3
⭐        EXISTS. ⭐ Knowing which of your side effects tolerate which failure
⭐        is the actual engineering here.
```

# Part 3 — ⭐⭐ Payment: the call that can time out

```python
def capture_payment(db: Session, order: Order) -> None:
    idem = f"order-{order.id}-capture-v1"          # ⭐⭐ DERIVED, not random
    try:
        result = provider.charge(
            amount_cents=order.total_cents, currency=order.currency,
            idempotency_key=idem,                   # ⭐⭐ THE defence (Day 122, other side)
            timeout=httpx.Timeout(connect=2, read=10, write=5, pool=1),
        )
    except httpx.TimeoutException:
        order.status = "payment_unknown"            # ⭐⭐ NOT "failed". NOT "succeeded".
        db.commit()
        schedule_reconciliation(order.id)           # ⭐ Part 5
        raise PaymentPending(order.id)
    order.status = "paid" if result.captured else "payment_declined"
    db.commit()
```

```
⭐⭐ `payment_unknown` IS THE MOST IMPORTANT STATE IN THE SYSTEM, AND MOST
⭐   IMPLEMENTATIONS DO NOT HAVE IT:
⭐   ⭐ a timeout does not mean it failed. ⭐⭐ THE CHARGE MAY HAVE SUCCEEDED
⭐     AND THE RESPONSE WAS LOST. ⭐ Recording "failed" means you may release
⭐     inventory for a ticket the customer HAS PAID FOR.
⭐   ⇒ ⭐⭐ THREE OUTCOMES, NOT TWO (Day 152). ⭐ Model the third explicitly, or
⭐     your code will silently pick one of the wrong two.
⭐
⭐⭐ WHY THE IDEMPOTENCY KEY IS DERIVED FROM THE ORDER, NOT RANDOM:
⭐   ⭐ a random key on retry is a NEW charge. ⭐⭐ `order-812-capture-v1` is
⭐     the same on every attempt from every worker forever ⇒ ⭐ the provider
⭐     dedupes for you, which is the strongest idempotency available
⭐     (Day 142's strategy 3).
⭐   ⭐ the `-v1` suffix is deliberate: ⭐⭐ if you ever need to legitimately
⭐     re-charge the same order, you bump it rather than inventing a new
⭐     scheme under pressure.
⭐
⭐ ⭐⭐ AND: A CIRCUIT BREAKER AROUND THE PROVIDER (Day 152), OUTSIDE the
⭐   retry, ⭐ with the "what do we return when open?" answer decided in
⭐   advance: ⭐⭐ hold the order in `awaiting_payment`, keep the hold alive,
⭐   and tell the user to try again — ⭐ never silently release inventory.
```

# Part 4 — ⭐⭐ The inbound webhook: the provider's version of the truth

```python
@router.post("/webhooks/payments", include_in_schema=False)
async def payment_webhook(request: Request, db: Session = Depends(get_db)):
    raw = await request.body()                                   # ⭐⭐ RAW bytes first
    ts, sig = parse_sig(request.headers.get("x-provider-signature", ""))
    if abs(time.time() - ts) > 300:
        raise HTTPException(400, {"code": "stale_signature"})    # ⭐⭐ replay defence
    expected = hmac.new(SECRET, f"{ts}.".encode() + raw, sha256).hexdigest()
    if not hmac.compare_digest(expected, sig):                   # ⭐ constant time
        raise HTTPException(401, {"code": "bad_signature"})

    evt = ProviderEvent.model_validate_json(raw)                 # ⭐ parse AFTER verifying
    claimed = db.execute(
        insert(ProcessedEvent).values(id=evt.id)
        .on_conflict_do_nothing()
    ).rowcount
    if claimed == 0:
        return {"status": "duplicate"}                           # ⭐⭐ 200, not 409
    db.add(Outbox(topic="payment.event", payload=evt.model_dump()))
    db.commit()                                                   # ⭐ claim + enqueue, atomic
    return {"status": "accepted"}                                 # ⭐⭐ under 200 ms
```

```
⭐⭐ FIVE RULES, ALL OF WHICH THIS ENDPOINT OBEYS:
⭐  1. ⭐ VERIFY BEFORE PARSING. ⭐⭐ Signing covers raw bytes; re-serialised
⭐       JSON will not match.
⭐  2. ⭐⭐ THE TIMESTAMP IS INSIDE THE SIGNED STRING. A signature alone does
⭐       not stop replay — the replayed request is validly signed.
⭐  3. ⭐⭐ RESPOND FAST, PROCESS ASYNC. And the consequence: ⭐ YOUR 200 MEANS
⭐       "RECEIVED", so the provider will never retry — ⭐⭐ from here YOU own
⭐       the retry, which is why it goes through the outbox.
⭐  4. ⭐ DUPLICATES RETURN 200. ⭐⭐ A 409 makes them retry it more.
⭐  5. ⭐⭐ OUT-OF-ORDER IS ASSUMED. `payment.succeeded` can arrive before
⭐       your own capture call returns. ⭐ The handler must be a state machine,
⭐       not a sequence:
⭐         `awaiting_payment` → paid ✅
⭐         `payment_unknown`  → paid ✅  ⭐⭐ (this is the timeout, resolved)
⭐         `paid`             → paid ✅  ⭐ no-op
⭐         `refunded`         → paid ❌  ⭐⭐ ALERT — this is a real anomaly
⭐
⭐   ⇒ ⭐⭐ AND THE STRONGEST RULE (Day 158): TREAT THE WEBHOOK AS A
⭐        NOTIFICATION, NOT DATA. ⭐ On receipt, call the provider's API for
⭐        the CURRENT status. ⭐⭐ That makes ordering, duplication and payload
⭐        tampering irrelevant in one move — and for money, take it.
```

# Part 5 — ⭐⭐ Reconciliation, and outbound webhooks

```
⭐⭐ THE JOB THAT MAKES THE WHOLE DESIGN HONEST (Day 159):

⭐   every 5 minutes:
⭐     for order in orders where status = 'payment_unknown'
⭐                            and updated_at < now() - 2 min:
⭐         ⭐ ask the provider: what is the state of `order-{id}-capture-v1`?
⭐         ⭐ captured  ⇒ mark paid, issue tickets
⭐         ⭐ not found ⇒ ⭐⭐ the charge never happened. Release the hold.
⭐         ⭐ pending   ⇒ leave it; try again next run
⭐
⭐   ⇒ ⭐⭐ WITHOUT THIS JOB, `payment_unknown` IS A STATE ORDERS ENTER AND
⭐        NEVER LEAVE. ⭐ You have modelled the truth and then abandoned the
⭐        customer in it, which is worse than not modelling it.
⭐   ⇒ ⭐ AND IT NEEDS Day 159's DISCIPLINE: a watermark or a status filter
⭐        rather than a time window, ⭐⭐ dead-man monitoring because nobody is
⭐        waiting, and a metric for `count(payment_unknown)` — ⭐ which should
⭐        be near zero and is a leading indicator of a provider problem.
```

```python
# ⭐ OUTBOUND webhooks to organisers — Day 158, and it reuses the outbox
@celery_app.task(acks_late=True, autoretry_for=(DeliveryError,),
                 retry_backoff=True, retry_jitter=True, retry_kwargs={"max_retries": 9})
def deliver_webhook(self, delivery_id: int) -> None:
    d = load(delivery_id)
    if breaker_open(d.endpoint_id):                    # ⭐⭐ per-endpoint (Day 158)
        raise self.retry(countdown=3600)
    url = validated_public_url(d.endpoint.url)         # ⭐⭐ SSRF: resolved + IP-checked
    body = canonical_json(d.payload)
    sig = sign(body, d.endpoint.secret, ts=now())      # ⭐ HMAC over raw bytes
    r = httpx.post(url, content=body, headers={"X-Signature": sig},
                   timeout=10, follow_redirects=False) # ⭐⭐ no redirects — SSRF bypass
    if r.status_code // 100 != 2:
        raise DeliveryError(r.status_code)
    d.delivered_at = now()
```

```
⭐⭐ THE THREE THINGS THAT MAKE THIS PRODUCTION-GRADE RATHER THAN A DEMO:
⭐   ⭐ A DELIVERY LOG with every attempt, status and response time —
⭐        ⭐⭐ without it, "we never got it" is a conversation with no evidence.
⭐   ⭐ A REPLAY BUTTON — ⭐⭐ their endpoint was down for an hour and they need
⭐        those 400 events; without replay your only answer is "sorry".
⭐   ⭐ A PER-ENDPOINT BREAKER AND CONCURRENCY CAP — ⭐⭐ one dead organiser
⭐        integration must not consume your delivery fleet or delay everyone
⭐        else's events (Day 153's fairness, in your worker pool).
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `.delay()` after `commit()` instead of an outbox row | A crash between them loses the event with no record it existed. |
| Relay without `SKIP LOCKED` | A second relay blocks; you're single-threaded by construction. |
| Marking published before publishing | At-most-once — silent loss. Publish, then mark. |
| Monitoring outbox count rather than oldest-row age | Count 3 with age two hours is a dead relay. |
| Passing ORM objects to tasks | Not serialisable, stale by execution, detached in the worker. |
| Not carrying `organiser_id` in the payload | The job runs with no tenant or a default — where isolation is most often lost. |
| Not carrying the trace context | Every async job is an orphan trace, exactly where the hard bugs are. |
| A random idempotency key on retry | It's a brand-new charge. Derive it from the order. |
| Recording a payment timeout as "failed" | It may have succeeded. You'd release a ticket the customer paid for. |
| No `payment_unknown` state | Your code silently picks one of the two wrong answers. |
| `payment_unknown` with no reconciliation job | A state orders enter and never leave — worse than not modelling it. |
| Parsing the webhook before verifying it | Signing covers raw bytes; re-serialised JSON won't match. |
| Signature without a timestamp | A captured request replays forever, validly signed. |
| Processing the webhook inline | The provider times out and retries while you're still working. |
| 409 for a duplicate webhook | Makes them retry more. Return 200. |
| Handling webhooks as a sequence | `succeeded` can arrive before your capture returns. Write a state machine. |
| No alert on the impossible transition | `refunded → paid` is a genuine anomaly and should page someone. |
| Following redirects on outbound delivery | A 302 bypasses every SSRF check on the original URL. |
| No per-endpoint breaker | One dead integration consumes the delivery fleet forever. |
| No delivery log or replay | Every failure is a support conversation you can't win. |

## Interview questions

**Q: Walk me through what happens after a successful purchase.**

> The purchase transaction writes the order, decrements inventory, releases the hold and inserts an
> outbox row — all atomically, so there's no dual write. A relay polls the outbox with
> `FOR UPDATE SKIP LOCKED`, which is what lets me run several relays with no coordination — a second
> relay doesn't block, it just takes the next hundred rows. It publishes and then marks, which is
> at-least-once, and that's the correct choice *because* the consumer is idempotent; those two are
> really one decision. The worker takes an id, not an object, plus the organiser id and the trace
> context explicitly, because the request is gone — the ContextVar is gone and `SET LOCAL` ended with
> its transaction, and that's where tenant isolation and tracing are most often lost. And the service
> functions it calls import no FastAPI, which is why this was free rather than a refactor.

**Q: Your payment call times out. What state is the order in?**

> `payment_unknown` — not failed, not succeeded. That's the most important state in the system and
> most implementations don't have it. A timeout doesn't mean it didn't happen; the charge may have
> succeeded and the response was lost. If I record "failed" I might release inventory for a ticket
> the customer has paid for, and if I record "succeeded" I might issue a free ticket. So I model the
> third outcome explicitly, and then — this is the part that makes it honest — a reconciliation job
> every five minutes asks the provider about `order-812-capture-v1` and resolves it: captured means
> mark paid, not-found means the charge never happened so release the hold, pending means try again.
> Without that job, `payment_unknown` is a state orders enter and never leave, which is worse than
> not modelling it at all.

**Q: Why is the payment idempotency key derived rather than random?**

> Because a random key on a retry is a brand-new charge — which is exactly the double-charge I'm
> trying to prevent. `order-812-capture-v1` is identical on every attempt, from every worker,
> forever, so the provider dedupes for me. That's the strongest form of idempotency available,
> because the guarantee lives on the side that actually moves the money rather than in my own
> bookkeeping. The `-v1` suffix is deliberate too: if there's ever a legitimate reason to re-charge
> the same order, I bump the version rather than inventing a new scheme under pressure during an
> incident.

**Q: How do you handle the provider's webhook?**

> Verify the HMAC over the raw bytes before parsing, with the timestamp inside the signed string and
> a five-minute window — because a signature alone doesn't stop replay, since a replayed request is
> validly signed. Then claim the event id with an insert and `ON CONFLICT DO NOTHING`, return 200 for
> a duplicate rather than 409 since an error makes them retry more, write an outbox row, and return
> in under a couple of hundred milliseconds. And the consequence people miss: my 200 means
> "received", so the provider will never retry — from that point I own the retry, which is why it
> goes through my own durable path. The handler is a state machine rather than a sequence, because
> `payment.succeeded` can arrive before my own capture call returns, and `refunded → paid` is an
> impossible transition that should page someone rather than be silently applied. For money I'd also
> apply the strongest rule: treat the webhook as a notification and call the provider's API for
> current state, which makes ordering, duplication and tampering irrelevant in one move.

## 🎙️ Articulation drill

**Two minutes: "How do you make sure a customer is never charged twice?"**

Start with the honest framing — the moment money enters someone else's system you stop being
transactional, so the goal is making "I don't know" survivable. Then four mechanisms in order: an
idempotency key on your own endpoint claimed atomically, so a client retry returns the same order;
a *derived* key on the provider call, so their side dedupes across every worker and every retry
forever; a `payment_unknown` state, because a timeout is a third outcome and recording either of the
other two is a real failure with real money; and a reconciliation job, without which that state is
somewhere orders go and never leave. Close on the webhook rule that makes the rest robust: **treat
it as a notification and fetch current state, which makes ordering, duplication and tampering
irrelevant in one move.**
