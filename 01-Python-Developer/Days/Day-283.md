# Day 283 🔁

**P-283** · 🔁 **The pipeline** — ⭐⭐ build, verify, deploy, and roll back

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a deploy is only reversible if the migration is — which means the
> hardest part of shipping is not the pipeline, it is that for a few minutes old code and new code
> are running against the same database at the same time, on purpose.**
>
> ⭐ Day 282 produced one artefact. ⭐⭐ Today that artefact moves: verified once, promoted by
> digest, released in a way you can undo, with a schema that tolerates both versions of the code.

# Part 1 — ⭐⭐ Build once, promote the digest

```
⭐⭐ THE ANTI-PATTERN, AND IT LOOKS SO REASONABLE:
⭐   build → test → deploy staging
⭐   (approve) → ⭐⭐ BUILD AGAIN → deploy production

⭐ ⇒ ⭐⭐ YOU TESTED AN ARTEFACT YOU DID NOT SHIP.
⭐   ⭐ Between the two builds: the base tag moved, a transitive
⭐     wheel published a new patch, a lockfile-less dependency
⭐     resolved differently, the build cache was cold.
⭐   ⇒ ⭐ "It worked in staging" is now literally true and
⭐     completely useless.

⭐⭐ THE PIPELINE SHAPE THAT FIXES IT:
⭐   ① BUILD    → one image, tagged with the git SHA, pushed
⭐   ② VERIFY   → all gates (Day 281) run against ***THAT IMAGE***
⭐   ③ RELEASE  → ⭐⭐ `deploy sha256:abc…` TO STAGING
⭐   ④ PROMOTE  → ⭐⭐ THE SAME DIGEST TO PRODUCTION

⭐ ⇒ ⭐ Which is only possible because Day 282 kept configuration
⭐   out of the image. ⭐⭐ THE TWO RULES ARE ONE RULE.
```

```
⭐ ⭐ AND IT MAKES ROLLBACK EXACT: `deploy sha256:previous`.
⭐   ⭐⭐ NOT "REVERT THE COMMIT AND REBUILD", which takes eight
⭐     minutes you do not have and may not even reproduce.
```

# Part 2 — ⭐⭐ Three pipelines, because failures mean different things

```
⭐⭐ | Pipeline | Trigger | Budget | What a failure means |
⭐   | PR       | push to a PR | < 8 min | ⭐ this change is wrong |
⭐   | MAIN     | merge        | <25 min | ⭐ main is broken — stop |
⭐   | RELEASE  | tag/manual   | —       | ⭐ this promotion is off |

⭐ ⭐ PR: lint, types, unit, integration, patch coverage, auth
⭐     matrix, spec drift, migration check (Day 281)
⭐ ⭐ MAIN: build + push the image, full E2E against a deployed
⭐     staging, image scan, mutation testing, dependency audit
⭐ ⭐ RELEASE: promote the digest, run migrations, smoke test,
⭐     watch the canary window, be ready to roll back

⭐⭐ THE RULE THAT KEEPS IT HONEST:
⭐   ***THE PIPELINE IS THE ONLY WAY TO DEPLOY.***
⭐   ⇒ ⭐ A documented manual path means the pipeline is
⭐     OPTIONAL, and an optional pipeline rots — nobody notices
⭐     it broke, because the emergency path works.
⭐   ⇒ ⭐⭐ IF YOU NEED AN EMERGENCY PATH, IT IS THE SAME
⭐     PIPELINE WITH A FLAG, so it is exercised and logged.
```

# Part 3 — ⭐⭐ The five minutes when both versions are live

```
⭐⭐ THIS IS THE PART PEOPLE GET WRONG, AND IT IS NOT OPTIONAL —
⭐   IT IS WHAT A ROLLING DEPLOY ***IS***:
⭐   ⭐ t+0   3 pods on v1
⭐   ⭐ t+30  2 pods on v1, 1 pod on v2   ⭐⭐ BOTH SERVING
⭐   ⭐ t+90  0 pods on v1

⭐ ⇒ ⭐⭐ SO FOR NINETY SECONDS, ***OLD CODE AND NEW CODE ARE
⭐   RUNNING AGAINST THE SAME SCHEMA***. Plus: a queue full of
⭐   messages produced by v1 that v2 will consume (Day 265), and
⭐   in-flight requests started on v1 finishing on v1.
```

```
⭐⭐ WHICH MEANS THE ONE-STEP MIGRATION IS ALWAYS WRONG:
⭐   `ALTER TABLE jobs RENAME COLUMN notes TO description;`
⭐   ⇒ ⭐ Migration runs before v2 rolls out ⇒ ⭐⭐ EVERY v1 POD
⭐     500s ON `notes` UNTIL IT IS REPLACED.
⭐   ⇒ ⭐ Migration runs after ⇒ every v2 pod 500s on
⭐     `description` until it runs. ⭐⭐ THERE IS NO ORDERING
⭐     THAT WORKS. (The same shape as Day 263's dual write:
⭐     when no ordering is safe, change the design.)

⭐⭐ EXPAND / CONTRACT — ***THREE DEPLOYS***, AND EACH ONE IS
⭐   INDIVIDUALLY REVERSIBLE:
⭐   ⭐ ① EXPAND — add `description`, nullable. Deploy code that
⭐        WRITES BOTH and READS `notes`. ⭐ v1 is unaffected.
⭐   ⭐ ② MIGRATE + SWITCH — backfill in batches (Day 264), then
⭐        deploy code that READS `description`, still writing both.
⭐   ⭐ ③ CONTRACT — stop writing `notes`, deploy, then drop it.
⭐   ⇒ ⭐⭐ AT NO POINT DOES ANY LIVE VERSION DEPEND ON A COLUMN
⭐     THAT DOES NOT EXIST — and that sentence is the whole
⭐     technique.
```

```
⭐⭐ AND FOUR MIGRATION RULES THAT ARE ABOUT LOCKS, NOT SCHEMAS:
⭐   ⭐ `SET lock_timeout = '3s'` AT THE TOP OF EVERY MIGRATION.
⭐     ⇒ ⭐⭐ WITHOUT IT, A MIGRATION WAITING BEHIND A LONG READ
⭐       QUEUES EVERY SUBSEQUENT QUERY BEHIND ***ITSELF***
⭐       (Day 196) — ⭐ the deploy takes the site down while the
⭐       migration is still WAITING to start.
⭐   ⭐ Retry the statement rather than failing the deploy.
⭐   ⭐ `CREATE INDEX CONCURRENTLY`, outside a transaction, and
⭐     remember it can leave an INVALID index if it fails.
⭐   ⭐ `ADD CONSTRAINT … NOT VALID` then `VALIDATE` separately
⭐     (Day 187) — the second takes a weaker lock.
⭐   ⭐⭐ AND NEVER BACKFILL INSIDE THE MIGRATION. A migration
⭐     that updates 4M rows holds a transaction for forty minutes
⭐     (Day 264) while your deploy pipeline waits on it.
```

# Part 4 — ⭐⭐ Rollback, honestly

```
⭐⭐ THE ASYMMETRY NOBODY STATES OUT LOUD:
⭐   ⭐ CODE rolls back in seconds — it is a digest change.
⭐   ⭐⭐ DATA DOES NOT ROLL BACK AT ALL. Rows written by v2 in
⭐     the new shape are still there when v1 returns.
⭐   ⇒ ⭐⭐ SO "CAN WE ROLL BACK?" IS REALLY "DOES v1 STILL WORK
⭐     AGAINST THE SCHEMA AND DATA v2 LEFT BEHIND?" — and
⭐     expand/contract is precisely what makes the answer yes.

⭐ ⭐ THE PRACTICAL POSITION:
⭐   ⭐ ROLL BACK CODE, always, immediately, without discussion.
⭐   ⭐⭐ ROLL ***FORWARD*** FOR DATA. A `down` migration that
⭐     drops a column deletes the rows v2 wrote. ⭐ Which is why
⭐     Day 281 tests `downgrade` in CI on an empty database and
⭐     you still do not run it in production.
⭐   ⭐ Feature flags decouple the two: ⭐⭐ SHIP THE CODE DARK,
⭐     TURN IT ON SEPARATELY — then "rollback" is a config
⭐     change with no deploy at all, which is the fastest
⭐     mitigation available to you.
```

# Part 5 — ⭐ Release strategies, chosen by what you can measure

```
⭐ ⭐ ROLLING — the default. Cheap, no extra infrastructure,
⭐     and it is the reason Part 3 exists.
⭐ ⭐ BLUE / GREEN — two full environments, switch the router.
⭐     ⇒ ⭐ Instant rollback, double the cost, ⭐⭐ AND THE
⭐       DATABASE IS STILL SHARED, so Part 3 applies anyway.
⭐ ⭐ CANARY — 5% of traffic to v2, watch, then proceed.
⭐     ⇒ ⭐⭐ A CANARY WITH NO METRIC AND NO AUTOMATIC ABORT IS
⭐       JUST A SLOWER ROLLOUT. ⭐ Name the signal (error rate,
⭐       p99, a business metric), the window, and the threshold
⭐       BEFORE you start, or you will stare at a graph and
⭐       decide it looks fine.
⭐ ⇒ ⭐ For this project: rolling, plus feature flags. Say that,
⭐   and say why — you can explain a choice you sized correctly
⭐   far better than one you copied.
```

# Part 6 — ⭐⭐ CI is production, and it has your credentials

```
⭐⭐ THE THREAT MODEL PEOPLE SKIP: ***CI CAN DEPLOY, SO CI IS
⭐   THE MOST PRIVILEGED THING YOU OWN.***

⭐   ⭐ NO LONG-LIVED CLOUD KEYS. Use OIDC federation: the
⭐     provider mints a short-lived token scoped to this repo
⭐     and this environment. ⭐⭐ A leaked build log then costs
⭐     you fifteen minutes instead of everything.
⭐   ⭐⭐ PIN THIRD-PARTY ACTIONS BY COMMIT SHA, NOT BY TAG.
⭐     ⇒ ⭐ `uses: some/action@v3` is a MUTABLE POINTER. The
⭐       owner can move it, or lose their account, and
⭐       ⭐⭐ ARBITRARY CODE THEN RUNS WITH YOUR DEPLOY
⭐       CREDENTIALS. This has happened repeatedly, at scale.
⭐   ⭐ Secrets are per-ENVIRONMENT, with production behind a
⭐     required approval.
⭐   ⭐⭐ NEVER RUN UNTRUSTED CODE WITH SECRETS — a workflow
⭐     triggered by a fork's PR must not have access to them.
⭐   ⭐ Mask secrets in logs, and assume masking will fail once.
```

# Part 7 — ⭐ What makes a pipeline trustworthy

```
⭐   ⭐ DETERMINISTIC — a re-run of the same SHA does the same
⭐     thing. Lockfiles, pinned actions, pinned base digests.
⭐   ⭐ FAST ENOUGH TO OBEY (Day 281).
⭐   ⭐ IT TELLS YOU WHAT IT DID: which SHA, which digest, which
⭐     migrations, at what time — ⭐⭐ AND `/version` LETS YOU
⭐     CHECK WHAT IS ACTUALLY RUNNING RIGHT NOW, which is the
⭐     first question in every incident.
⭐   ⭐⭐ AND IT IS EXERCISED. ***A ROLLBACK PATH YOU HAVE NEVER
⭐     RUN IS NOT A ROLLBACK PATH — IT IS A PARAGRAPH.***
⭐     ⇒ ⭐ Roll back once a month on purpose, in staging, on a
⭐       normal Tuesday.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Rebuilding for each environment | You tested an artefact you didn't ship. Promote the digest. |
| Rollback by revert-and-rebuild | Eight minutes you don't have, and it may not reproduce. |
| One pipeline for everything | A PR failure and a main failure mean different things and need different budgets. |
| A documented manual deploy path | The pipeline becomes optional, and optional pipelines rot. |
| Ignoring that both versions run at once | It's what a rolling deploy *is*, not an edge case. |
| A one-step rename migration | No ordering works. Expand, migrate, contract. |
| No `lock_timeout` in migrations | A migration waiting behind a long read queues every query behind itself. |
| `CREATE INDEX` without `CONCURRENTLY` | Writes blocked for the duration on a large table. |
| `ADD CONSTRAINT` without `NOT VALID` | A full-table lock during validation. |
| Backfilling inside the migration | A forty-minute transaction with the deploy pipeline waiting on it. |
| Assuming data rolls back with code | Rows v2 wrote are still there when v1 returns. |
| Running `down` migrations in production | You delete the data the new version wrote. |
| No feature flags | Every mitigation requires a deploy. |
| A canary with no threshold or abort | A slower rollout, plus a graph you'll decide looks fine. |
| Long-lived cloud keys in CI | One leaked log is total compromise. Use OIDC. |
| Third-party actions pinned by tag | A mutable pointer running with your deploy credentials. |
| Secrets available to fork-triggered workflows | Untrusted code with your credentials. |
| No production approval step | The most privileged action you own has no gate. |
| Not exposing the running SHA | The first question in an incident becomes unanswerable. |
| Never rehearsing a rollback | It isn't a rollback path, it's a paragraph. |

## Interview questions

**Q: Walk me through your deploy.**

> One build produces one image, tagged by git SHA, and every gate runs against that image. That exact
> digest deploys to staging, and if it passes, the *same digest* is promoted to production — never a
> rebuild, because a rebuild means I tested an artefact I didn't ship: the base tag can move, a
> transitive wheel can publish a patch, and "it worked in staging" becomes literally true and useless.
> That also makes rollback exact — it's a digest change, not a revert-and-rebuild that takes eight
> minutes I don't have. It only works because configuration lives in the environment rather than in
> the image, so those two rules are really one rule.

**Q: What's hard about deploying a schema change?**

> That a rolling deploy means old and new code run against the same database simultaneously, on
> purpose, for a minute or two — plus a queue of messages produced by the old version that the new one
> will consume. So a one-step rename can't work in either order: migrate first and the old pods 500 on
> the missing column, migrate after and the new pods 500. It's the same shape as the dual write —
> when no ordering is safe, change the design. Expand/contract is three deploys, each individually
> reversible, and the property that matters is that at no point does any live version depend on a
> column that doesn't exist.

**Q: What do you do about migration locks?**

> Set `lock_timeout` at the top of every migration and retry, because a migration waiting behind a
> long-running read queues every subsequent query behind *itself* — so the site goes down while the
> migration hasn't even started. Then `CREATE INDEX CONCURRENTLY` outside a transaction, `ADD
> CONSTRAINT NOT VALID` followed by a separate `VALIDATE`, and never a backfill inside a migration,
> because that's a forty-minute transaction with the deploy pipeline waiting on it and autovacuum
> blocked behind it.

**Q: Can you roll back?**

> Code, yes, in seconds. Data, no — rows the new version wrote in the new shape are still there when
> the old version comes back. So the real question is whether the old code still works against the
> schema and data the new code left behind, and expand/contract is exactly what makes that answer yes.
> In practice: roll back code immediately and without discussion, roll *forward* for data, and never
> run a `down` migration in production, because dropping that column deletes what the new version
> wrote. Feature flags are the fastest mitigation of all, since shipping dark makes "rollback" a config
> change with no deploy.

**Q: How do you secure CI?**

> By treating it as the most privileged thing I own, because it can deploy. No long-lived cloud keys —
> OIDC federation so the token is short-lived and scoped to this repo and environment, which turns a
> leaked build log into a fifteen-minute problem. Third-party actions pinned by commit SHA rather than
> tag, because a tag is a mutable pointer and moving it runs arbitrary code with my deploy
> credentials — which has happened repeatedly at scale. Production secrets behind a required approval,
> and no secrets at all in workflows a fork can trigger.

## 🎙️ Articulation drill

**Three minutes: "How does code get to production?"**

Open with the artefact rule: **build once, verify that image, and promote the digest** — never rebuild
for production, because then you tested something you didn't ship, and it also makes rollback a digest
change rather than an eight-minute rebuild under pressure. Note that this only works because config
lives in the environment, so it's really one rule with Day 282. Then spend the bulk of the answer on
the hard part, because it's what separates people who have deployed from people who have read about
it: **a rolling deploy means old and new code run against the same schema simultaneously, on purpose**
— plus a queue of old-format messages. So a one-step rename fails in both orderings, which is the same
shape as the dual write: when no ordering is safe, change the design. Expand, migrate, contract, three
individually reversible deploys, and **the property is that no live version ever depends on a column
that doesn't exist.** Add the lock rules, especially `lock_timeout`, because **a migration waiting
behind a long read queues every query behind itself — the site goes down before the migration even
starts.** Then rollback, honestly: **code rolls back, data doesn't**, so the real question is whether
the old code survives what the new code wrote — and roll forward for data rather than running a `down`
migration that deletes it. Close on CI as the most privileged thing you own: OIDC instead of long-lived
keys, actions pinned by SHA because a tag is a mutable pointer that can run arbitrary code with your
deploy credentials, and **a rollback path you've never rehearsed is a paragraph, not a path.**
