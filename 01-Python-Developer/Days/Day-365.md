# Day 365 🧬

**P-365** · 🧬 **Docker Compose** — ⭐⭐ and the gap between dev and production

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: Compose is the best local development tool there is and a mediocre
> production runtime, and the value of knowing exactly where the two diverge is that it tells you
> which bugs your local environment can never find — which is a short, specific, memorisable list.**

---

# Part 1 — ⭐⭐ What Compose is genuinely excellent at

```
⭐⭐ ONE FILE, ONE COMMAND, AND A NEW ENGINEER IS PRODUCTIVE IN
⭐   TEN MINUTES INSTEAD OF TWO DAYS.
⭐   ⇒ ⭐⭐ THAT IS THE ENTIRE JUSTIFICATION, AND IT IS ENORMOUS.
⭐     ⭐ Onboarding cost is a real engineering cost and it is
⭐     almost never measured.

⭐⭐ THE FIVE THINGS IT DOES WELL:
⭐   ① ⭐ ***THE WHOLE DEPENDENCY SET*** — Postgres, Redis,
⭐        MinIO, Mailhog, Kafka — ⭐⭐ AT THE ***SAME VERSIONS AS
⭐        PRODUCTION***, which removes a genuine class of bug.
⭐   ② ⭐ ***A NETWORK WITH DNS*** so services find each other
⭐        by name (Day 364).
⭐   ③ ⭐ ***DECLARATIVE AND VERSIONED*** — the environment is
⭐        in git and reviewed like code.
⭐   ④ ⭐⭐ ***DISPOSABLE*** — `docker compose down -v` and you
⭐        are back to zero. ⭐ "My local database is in a weird
⭐        state" stops being a morning.
⭐   ⑤ ⭐⭐ ***CI USES THE SAME FILE***, so integration tests run
⭐        against real Postgres rather than SQLite — ⭐⭐ AND
⭐        TESTING AGAINST A DIFFERENT DATABASE THAN YOU DEPLOY
⭐        IS ONE OF THE MOST EXPENSIVE SHORTCUTS IN SOFTWARE.

⭐⭐ AND WHERE IT IS LEGITIMATELY FINE IN PRODUCTION:
⭐   ⭐ A single-node internal tool. ⭐ A side project. ⭐ A
⭐     demo. ⭐ A stateless service behind a load balancer where
⭐     the deploy is "pull and restart" and a minute of downtime
⭐     is acceptable.
⭐   ⇒ ⭐⭐ SAYING THIS IS IMPORTANT: "COMPOSE IN PRODUCTION IS
⭐     WRONG" IS DOGMA. ⭐ "Compose in production is fine until
⭐     you need zero-downtime deploys, multiple nodes, or
⭐     automatic restart on node failure" is an engineering
⭐     answer.
```

# Part 2 — ⭐ A Compose file worth copying

```yaml
services:
  api:
    build:
      context: .
      target: dev                    # ⭐ Day 363's multi-target
    command: uvicorn app.main:app --host 0.0.0.0 --reload
    volumes:
      - ./app:/app/app               # ⭐⭐ SOURCE ONLY, NOT /app
    environment:
      DATABASE_URL: postgresql+asyncpg://app:app@db:5432/app
      REDIS_URL: redis://cache:6379/0
      LOG_LEVEL: DEBUG
    ports: ["8000:8000"]
    depends_on:
      db: { condition: service_healthy }     # ⭐ Day 364
      cache: { condition: service_started }
    networks: [frontend, backend]

  db:
    image: postgres:16-alpine        # ⭐⭐ PIN THE MINOR VERSION
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app         # ⭐ dev only, and obviously so
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:                     # ⭐⭐ REQUIRED FOR THE CONDITION
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 2s
      timeout: 3s
      retries: 15
      start_period: 5s               # ⭐ don't count early failures
    networks: [backend]              # ⭐⭐ NO PORTS PUBLISHED

  cache:
    image: redis:7-alpine
    command: redis-server --save "" --appendonly no   # ⭐ dev: no disk
    networks: [backend]

volumes:
  pgdata:

networks:
  frontend:
  backend:
    internal: true                   # ⭐⭐ NO EXTERNAL ACCESS AT ALL
```

```
⭐⭐ THE SIX DECISIONS IN THAT FILE:
⭐   ① ⭐⭐ `internal: true` ON THE BACKEND NETWORK — the
⭐      database is unreachable from outside by ***topology***,
⭐      not by remembering not to publish a port.
⭐   ② ⭐ Mount `./app` rather than `.` — ⭐⭐ SO THE MOUNT DOES
⭐      NOT SHADOW THE INSTALLED PACKAGE (Day 364).
⭐   ③ ⭐ `service_healthy` with a real healthcheck and a
⭐      `start_period`.
⭐   ④ ⭐ Pinned minor versions — ⭐⭐ `postgres:16`, NOT
⭐      `postgres:latest`, WHICH WILL ONE DAY BE A MAJOR
⭐      UPGRADE THAT SILENTLY REFUSES TO START ON YOUR EXISTING
⭐      VOLUME.
⭐   ⑤ ⭐ Redis persistence disabled in dev — ⭐ faster, and
⭐      honest about being ephemeral.
⭐   ⑥ ⭐⭐ THE DEV PASSWORD IS OBVIOUSLY A DEV PASSWORD. ⭐ Never
⭐      a real-looking one, ⭐⭐ SO NOBODY EVER COPIES IT SOMEWHERE
⭐      IT MATTERS.

⭐⭐ AND THE OVERRIDE MECHANISM WORTH KNOWING:
⭐   ⭐ `compose.yaml` + `compose.override.yaml` (⭐ applied
⭐     automatically) ⭐ + `-f` for explicit stacks + `profiles:`
⭐     for optional services.
⭐   ⇒ ⭐⭐ SO THE HEAVY OPTIONAL PIECES (Kafka, Elasticsearch)
⭐     ARE BEHIND A PROFILE AND ARE NOT STARTED BY DEFAULT —
⭐     ⭐ which keeps `docker compose up` under a minute, and
⭐     that matters more for adoption than anything else in the
⭐     file.
```

# Part 3 — ⭐⭐ The gap: what dev can never find

```
⭐⭐ THIS IS THE PART TO MEMORISE. ⭐ Each item is a class of
⭐   production bug your laptop is structurally incapable of
⭐   reproducing.

⭐⭐ ① ***ONE REPLICA.*** ⭐ Every Day-324 bug is invisible:
⭐      module-level caches, in-process locks, per-replica
⭐      schedulers, sticky-session assumptions.
⭐      ⇒ ⭐⭐ FIX: `docker compose up --scale api=3` BEHIND
⭐        NGINX, AND RUN YOUR TESTS THROUGH IT. ⭐ It takes ten
⭐        minutes and finds real bugs.
⭐⭐ ② ***NO RESOURCE LIMITS.*** ⭐ Your laptop has 32 GB and
⭐      12 cores; ⭐⭐ PRODUCTION HAS 512 MB AND HALF A CPU. ⭐ You
⭐      will never see an OOMKill or CFS throttling locally.
⭐      ⇒ ⭐ FIX: set `deploy.resources.limits` in Compose to
⭐        ***production values***. ⭐⭐ MOST TEAMS NEVER DO THIS
⭐        AND IT IS FREE.
⭐⭐ ③ ***ZERO NETWORK LATENCY AND ZERO LOSS.*** ⭐ Everything is
⭐      on one bridge; ⭐⭐ N+1 QUERIES ARE INVISIBLE BECAUSE
⭐      EACH ROUND TRIP IS 0.05 ms INSTEAD OF 0.5 ms, AND
⭐      RETRIES NEVER FIRE.
⭐      ⇒ ⭐ FIX: `tc netem` or Toxiproxy to inject latency and
⭐        failures. ⭐⭐ ONE AFTERNOON, AND IT FINDS TIMEOUT AND
⭐        RETRY BUGS THAT OTHERWISE SHIP.
⭐⭐ ④ ***TINY DATA.*** ⭐ 50 rows. ⭐⭐ A MISSING INDEX IS
⭐      INVISIBLE AT 50 ROWS AND FATAL AT 5 MILLION — ⭐ and the
⭐      query plan is genuinely different, not just slower.
⭐      ⇒ ⭐ FIX: a seed script with realistic volume and
⭐        ***realistic skew*** (Day 329's Zipf distribution).
⭐⭐ ⑤ ***NO TLS, NO PROXY, NO REAL AUTH.*** ⭐ Forwarded
⭐      headers, cookie flags, CORS, redirect loops behind a
⭐      proxy — ⭐⭐ ALL FIRST ENCOUNTERED IN STAGING.
⭐      ⇒ ⭐ FIX: put Nginx in the Compose stack (Day 367). ⭐ It
⭐        is twenty lines.
⭐⭐ ⑥ ***NO DEPLOY.*** ⭐ Rolling updates, readiness gating,
⭐      graceful shutdown, migrations under load — ⭐⭐ COMPOSE
⭐      SIMPLY STOPS AND STARTS.
⭐      ⇒ ⭐ There is no good local fix. ⭐⭐ THIS IS WHY STAGING
⭐        MUST EXIST AND MUST BE SHAPED LIKE PRODUCTION.
⭐⭐ ⑦ ***NO CONCURRENCY OF CONSEQUENCE.*** ⭐ You click once;
⭐      production clicks a thousand times a second.
⭐      ⇒ ⭐ FIX: a load-test target in the Compose stack (k6,
⭐        Locust) that anyone can run.

⭐⭐ ⇒ AND THE HABIT WORTH FORMING: ***WHEN A PRODUCTION BUG
⭐   ESCAPES, ASK WHICH OF THESE SEVEN GAPS LET IT THROUGH, AND
⭐   CLOSE THAT ONE.*** ⭐ Over a year this converges on a local
⭐   environment that catches almost everything.
```

# Part 4 — ⭐⭐ Why Compose is not a production orchestrator

```
⭐⭐ THE FIVE MISSING CAPABILITIES, STATED AS CAPABILITIES
⭐   RATHER THAN AS "IT IS NOT KUBERNETES":
⭐   ① ⭐⭐ ***NO RESCHEDULING.*** ⭐ The node dies, the service
⭐      is gone. ⭐ Nothing moves it.
⭐   ② ⭐⭐ ***NO ROLLING UPDATE.*** ⭐ `compose up` stops the old
⭐      container and starts the new one. ⭐ Downtime per
⭐      service, every deploy.
⭐   ③ ⭐ ***NO READINESS GATING.*** ⭐ Traffic arrives before the
⭐      app is ready, ⭐⭐ AND NOTHING REMOVES A SICK INSTANCE
⭐      FROM ROTATION.
⭐   ④ ⭐ ***NO HORIZONTAL SCALING ACROSS MACHINES.*** ⭐ `--scale`
⭐      is one host's worth.
⭐   ⑤ ⭐ ***NO SECRET MANAGEMENT, NO RBAC, NO POLICY.***
⭐   ⇒ ⭐⭐ AND CRUCIALLY: ***RESTART POLICIES GET YOU FURTHER
⭐     THAN PEOPLE THINK.*** ⭐ `restart: unless-stopped` plus a
⭐     healthcheck plus systemd covers single-node availability
⭐     surprisingly well, ⭐⭐ WHICH IS WHY THE HONEST THRESHOLD
⭐     IS "MULTIPLE NODES OR ZERO-DOWNTIME DEPLOYS", NOT
⭐     "PRODUCTION".

⭐⭐ THE LADDER, WITH THE TRIGGER FOR EACH STEP:
⭐   ⭐ Compose on one VM ⇒ ⭐⭐ UNTIL you need zero-downtime
⭐     deploys or survive-node-failure.
⭐   ⭐ Compose + a load balancer + two VMs ⇒ ⭐ manual, works,
⭐     ⭐⭐ AND THE DEPLOY ORCHESTRATION IS NOW YOUR PROBLEM.
⭐   ⭐ ECS / Fargate / Cloud Run / App Runner ⇒ ⭐⭐ THE STEP
⭐     MOST TEAMS SHOULD TAKE, AND SKIP. ⭐ Rolling deploys,
⭐     health gating and autoscaling without a cluster to
⭐     operate.
⭐   ⭐ Kubernetes ⇒ ⭐ when you need the extension model, many
⭐     teams, or portability across environments (Days 377–378).
⭐   ⇒ ⭐⭐ NAMING THAT MIDDLE STEP IS THE SIGNAL. ⭐ Most
⭐     candidates jump from Compose to Kubernetes as though
⭐     nothing exists between them.
```

# Part 5 — ⭐ Compose in CI

```
⭐⭐ THE HIGHEST-VALUE USE AFTER LOCAL DEV: ⭐⭐ INTEGRATION
⭐   TESTS AGAINST ***REAL*** DEPENDENCIES.

⭐⭐ THE PATTERN:
⭐   ⭐ `docker compose -f compose.yaml -f compose.ci.yaml up -d
⭐     --wait` ⇒ ⭐⭐ `--wait` BLOCKS UNTIL HEALTHCHECKS PASS,
⭐     WHICH REMOVES EVERY `sleep 10` FROM YOUR PIPELINE.
⭐   ⭐ Run tests ⇒ `docker compose down -v` ⇒ ⭐⭐ ALWAYS IN A
⭐     CLEANUP STEP THAT RUNS ON FAILURE TOO, or your runners
⭐     leak volumes until the disk fills.

⭐⭐ THE FOUR CI-SPECIFIC ADJUSTMENTS:
⭐   ⭐ ⭐⭐ NO BIND MOUNTS — CI has no source tree to mount into
⭐     a running container in the same way. ⭐ Build the image
⭐     and use it.
⭐   ⭐ ⭐⭐ USE A PROJECT NAME (`-p ci-$RUN_ID`) SO PARALLEL
⭐     JOBS DO NOT COLLIDE ON NETWORK AND VOLUME NAMES. ⭐ This
⭐     is the bug that makes CI "flaky" in a way nobody can
⭐     reproduce.
⭐   ⭐ ⭐⭐ DO NOT PUBLISH PORTS IN CI — two parallel jobs both
⭐     binding 5432 is a guaranteed conflict. ⭐ Talk over the
⭐     Compose network instead.
⭐   ⭐ `tmpfs` for the database data directory ⇒ ⭐⭐ POSTGRES ON
⭐     tmpfs IS DRAMATICALLY FASTER AND YOU DO NOT CARE ABOUT
⭐     DURABILITY IN CI. ⭐ Add `fsync=off` too. ⭐ Often halves
⭐     integration-test time.

⭐⭐ AND THE ALTERNATIVE WORTH ONE SENTENCE: ⭐⭐ `testcontainers`
⭐   STARTS DEPENDENCIES FROM ***INSIDE*** YOUR TEST SUITE, ⭐ so
⭐   the same tests run identically locally and in CI with no
⭐   external orchestration. ⭐ It costs a little startup time
⭐   per session and removes an entire category of "works in CI
⭐   only" problems.
```

# Part 6 — ⭐ Compose ergonomics that make people actually use it

```
⭐⭐ THE DIFFERENCE BETWEEN A COMPOSE SETUP PEOPLE USE AND ONE
⭐   THEY WORK AROUND:
⭐   ⭐ ⭐⭐ `docker compose up` MUST BE UNDER A MINUTE ON A COLD
⭐     CACHE, AND UNDER TEN SECONDS ON A WARM ONE. ⭐ Above that,
⭐     people stop restarting it and start debugging stale
⭐     state.
⭐   ⭐ ⭐⭐ A `Makefile` OR `justfile` WITH FIVE TARGETS: `up`,
⭐     `down`, `test`, `logs`, `shell`. ⭐ Nobody should be
⭐     typing a twelve-flag `docker compose` command from
⭐     memory.
⭐   ⭐ ⭐⭐ SEED DATA THAT IS ***REALISTIC AND IDEMPOTENT***, so
⭐     `make seed` twice is safe.
⭐   ⭐ A `.env.example` committed, ⭐ `.env` gitignored, ⭐⭐ AND
⭐     A STARTUP CHECK THAT NAMES THE MISSING VARIABLE RATHER
⭐     THAN FAILING WITH A `KeyError`.
⭐   ⭐ ⭐⭐ HOT RELOAD THAT ACTUALLY WORKS — ⭐ and on macOS,
⭐     `--reload` over a bind mount uses polling and can burn a
⭐     whole core; ⭐ `watchfiles` with a narrowed watch path, or
⭐     Compose's `develop.watch` sync, fixes it.

⭐⭐ AND THE DOCUMENTATION LINE THAT PAYS FOR ITSELF:
⭐   ***A README SECTION THAT SAYS EXACTLY WHAT `make up` GIVES
⭐      YOU, WHAT IT DOES ***NOT*** GIVE YOU, AND WHICH TESTS
⭐      REQUIRE STAGING.***
⭐   ⇒ ⭐⭐ THAT SECOND CLAUSE IS PART 3'S LIST, AND WRITING IT
⭐     DOWN IS HOW A TEAM STOPS BEING SURPRISED BY IT.
```

# Part 7 — ⭐ Compose vs the alternatives, briefly

```
⭐⭐ ⭐ ***DEVCONTAINERS*** — Compose plus an editor
⭐   configuration, so the ***tooling*** also runs in the
⭐   container. ⭐⭐ REMOVES "WORKS WITH MY LOCAL PYTHON"
⭐   ENTIRELY, at the cost of a slower inner loop on
⭐   macOS/Windows.
⭐⭐ ⭐ ***TILT / SKAFFOLD*** — for teams already on Kubernetes:
⭐   develop against a real cluster with fast rebuilds.
⭐   ⭐⭐ WORTH IT ONLY IF PRODUCTION IS KUBERNETES AND THE GAP
⭐   IN PART 3 IS COSTING YOU.
⭐⭐ ⭐ ***NIX / DEVBOX*** — reproducible toolchains without
⭐   containers. ⭐ Excellent, steeper learning curve, ⭐⭐ AND IT
⭐   SOLVES THE ***TOOLING*** PROBLEM WHILE LEAVING THE
⭐   ***SERVICES*** PROBLEM, so it often pairs ***with***
⭐   Compose rather than replacing it.
⭐⭐ ⭐ ***JUST RUN IT LOCALLY*** — ⭐⭐ AND THIS IS A LEGITIMATE
⭐   ANSWER for a small team on one platform with two
⭐   dependencies. ⭐ Fastest inner loop by a distance.

⭐⭐ ⇒ THE JUDGEMENT: ***THE BEST LOCAL ENVIRONMENT IS THE ONE
⭐   THE TEAM ACTUALLY USES.*** ⭐ A perfect setup with a
⭐   three-minute startup loses to a decent one that starts in
⭐   ten seconds, ⭐⭐ BECAUSE THE SLOW ONE GETS BYPASSED AND
⭐   THEN THE DIVERGENCE YOU WERE PREVENTING HAPPENS ANYWAY.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Treating Compose dev as equivalent to production | Seven structural gaps mean whole classes of bug can't appear locally |
| ⭐⭐ Never testing with more than one replica | Every module-level cache and in-process lock bug stays invisible |
| ⭐⭐ No resource limits locally | You never see an OOMKill or throttling until production |
| ⭐ Tiny seed data | A missing index is invisible at 50 rows and the query plan is genuinely different |
| ⭐ `postgres:latest` | One day it's a major version that refuses to start on your existing volume |
| ⭐⭐ Publishing database ports in CI | Parallel jobs collide on 5432. Use the Compose network |
| ⭐⭐ No project name in CI | Parallel jobs collide on network and volume names — the unreproducible flake |
| ⭐ `sleep 10` instead of `--wait` | Slow and still racy. Healthchecks plus `--wait` |
| ⭐ No cleanup on failure | Runners leak volumes until the disk fills |
| ⭐ Bind-mounting `.` rather than the source directory | Shadows the installed package |
| ⭐⭐ Realistic-looking dev passwords | Someone copies one somewhere it matters |
| ⭐ A startup that takes three minutes | People stop restarting it and start debugging stale state |
| ⭐⭐ Jumping straight from Compose to Kubernetes | ECS/Fargate/Cloud Run is the step most teams should take and skip |

## Interview questions

**1. "Is Compose production-ready?"**
> ⭐ For a single-node internal tool or a stateless service where a minute of downtime is fine, yes —
> ⭐⭐ and **`restart: unless-stopped` plus healthchecks plus systemd covers single-node availability
> better than people expect.** ⭐ What it can't do is reschedule after node failure, roll updates
> without downtime, gate traffic on readiness, or scale across machines. ⭐⭐ So the honest threshold is
> **"multiple nodes or zero-downtime deploys", not "production"** — and the next step is usually
> ECS, Fargate or Cloud Run, not Kubernetes.

**2. "What can your local environment never catch?"**
> ⭐ Seven things, and I'd name them because it tells you where to invest: ⭐⭐ **one replica, so every
> module-level cache and in-process lock bug is invisible**; no resource limits, so no OOMKills or
> throttling; zero network latency, so N+1 queries and missing retries hide; tiny data, so a missing
> index doesn't show and the query plan is genuinely different; no TLS or proxy, so forwarded headers
> and cookie flags surface in staging; no rolling deploy; and no real concurrency. ⭐⭐ **Five of those
> seven have cheap local fixes** — scale to three behind Nginx, set production resource limits, inject
> latency with Toxiproxy, seed realistic volume and skew, and put Nginx in the stack.

**3. "How do you use Compose in CI?"**
> ⭐ Integration tests against real Postgres rather than SQLite, because ⭐⭐ **testing against a
> different database than you deploy is one of the most expensive shortcuts in software.** ⭐ Four
> adjustments: `--wait` so healthchecks replace every `sleep`; a unique project name per run,
> ⭐⭐ **because parallel jobs colliding on network and volume names is the flake nobody can
> reproduce**; no published ports; and the database on tmpfs with `fsync=off`, which often halves
> integration-test time.

**4. "Why isn't `depends_on` enough?"**
> ⭐ It waits for the container to start, not the service to be ready, so the app connects at second one
> and crashes. ⭐ `condition: service_healthy` with a real healthcheck and a `start_period` fixes it
> locally. ⭐⭐ But the real answer is retry-on-connect in the app, **because production has no
> `depends_on` and your database will restart underneath you** — ordering tools hide a missing retry.

**5. "What makes a local environment people actually use?"**
> ⭐⭐ Speed, above everything. **Under a minute cold, under ten seconds warm** — past that, people stop
> restarting it and start debugging stale state, and then the divergence you were preventing happens
> anyway. ⭐ Then five make targets so nobody types a twelve-flag command; idempotent realistic seed
> data; heavy optional services behind profiles; and ⭐⭐ **a README section saying what it does *not*
> give you**, which is that seven-item list, written down so the team stops being surprised by it.

**6. "Compose or testcontainers?"**
> ⭐ Compose for the human loop — you want the stack running while you work. ⭐⭐ Testcontainers for the
> test suite, because **dependencies start from inside the tests, so the same suite runs identically
> locally and in CI with no external orchestration** — which removes the "works in CI only" category
> entirely. ⭐ They're complementary, and I'd use both.

## 🎙️ Articulation drill

**Two minutes.** Give the value honestly: **Compose is the best local development tool there is** — one
file, one command, the whole dependency set at production versions, disposable, and versioned in git —
and its real justification is onboarding cost, which is a genuine engineering cost nobody measures.
Then the part that matters more: **knowing exactly where it stops resembling production tells you which
bugs your laptop is structurally incapable of finding.** Name them: one replica, so every in-process
cache and lock bug hides; no resource limits, so no OOMKills or throttling; zero network latency, so
N+1s and missing retries never surface; tiny data, so a missing index is invisible and the query plan
is genuinely different; no TLS or proxy; no rolling deploy; no real concurrency. ⭐ Then the useful
half: **five of those seven have cheap local fixes** — scale to three behind Nginx, set production
resource limits in the Compose file, inject latency with Toxiproxy, seed realistic volume and skew, and
put Nginx in the stack. On production use, refuse the dogma: **Compose plus restart policies plus
systemd covers single-node availability well, so the threshold is multiple nodes or zero-downtime
deploys** — and the step most teams should take and skip is ECS, Fargate or Cloud Run, not Kubernetes.
Close on adoption: **a perfect setup that takes three minutes loses to a decent one that takes ten
seconds, because the slow one gets bypassed and the divergence happens anyway.**
