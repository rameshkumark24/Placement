# Part 1 — ⭐⭐ `heapq` is a min-heap, and only a min-heap

```
⭐ ***THE THREE FACTS THAT MATTER:***
⭐   ⭐ ① ⭐⭐ `heapq` IS A ***MIN***-HEAP. THERE IS NO MAX-HEAP IN
⭐     THE STANDARD LIBRARY.
⭐     ⭐ ⇒ push `-x` and negate on the way out. ⭐⭐ SAY "I'M
⭐       NEGATING BECAUSE PYTHON ONLY GIVES ME A MIN-HEAP" — ⭐ it
⭐       reads as fluency rather than as a hack.
⭐   ⭐ ② ***it operates on an ordinary list, in place.*** ⭐ No
⭐     wrapper class. ⭐ `heapify(lst)` is ⭐⭐ O(n), NOT
⭐     O(n log n) — ⭐ worth knowing and worth saying.
⭐   ⭐ ③ ⭐⭐ ***TUPLES COMPARE ELEMENT-WISE***, ⭐ so
⭐     `(priority, item)` gives you a priority queue free —
⭐     ⭐⭐ AND IF `priority` TIES, PYTHON COMPARES `item`, WHICH
⭐     ***RAISES TypeError*** IF THE ITEM IS NOT ORDERABLE.
⭐     ⭐ ⇒ `(priority, counter, item)` with a monotonic counter.
⭐     ⭐ ⭐⭐ THIS IS A REAL BUG THAT APPEARS ONLY WHEN TWO
⭐       PRIORITIES TIE, WHICH IS WHY IT REACHES PRODUCTION.

⭐ ***THE FOUR OPERATIONS:***
⭐   ⭐ `heappush(h, x)` · `heappop(h)` — ⭐ O(log n)
⭐   ⭐ `h[0]` — ⭐⭐ PEEK, O(1)
⭐   ⭐ ⭐⭐ `heappushpop(h, x)` — ⭐ push then pop, ***one***
⭐     sift instead of two. ⭐ The top-k workhorse.
⭐   ⭐ `nlargest(k, it)` / `nsmallest(k, it)` — ⭐ fine, and
⭐     ⭐⭐ KNOW THAT THEY DEGRADE TO A SORT WHEN k IS NEAR n.
```

# Part 2 — ⭐⭐ Top-k: the counterintuitive heap

```
⭐ ***THE QUESTION:*** ⭐ k largest elements from n.
⭐ ***THE TRAP:*** ⭐ reach for a max-heap of everything. ⭐⭐ THAT
⭐   IS O(n) SPACE AND O(n log n) — ⭐ no better than sorting.

⭐ ⭐⭐ THE ANSWER: ***A ***MIN***-HEAP OF SIZE k.***
⭐   ⭐ Keep exactly k items. ⭐ The smallest of your current best
⭐     k sits at the root, ⭐⭐ SO IT IS EXACTLY THE ONE TO EVICT
⭐     WHEN SOMETHING BETTER ARRIVES.
⭐   ⭐ ⇒ ⭐⭐ O(n log k) TIME, O(k) SPACE.
⭐   ⭐ ⭐⭐ FOR k=10 OUT OF n=10,000,000 THAT IS THE DIFFERENCE
⭐     BETWEEN A STREAMING SOLUTION AND ONE THAT DOES NOT FIT IN
⭐     MEMORY. ⭐ Say that — it is the real-world justification.

⭐ ***THE SENTENCE TO SAY OUT LOUD:*** ⭐⭐ "I WANT A MIN-HEAP FOR
⭐   THE k ***LARGEST***, BECAUSE THE ROOT IS THE WEAKEST MEMBER
⭐   OF MY CURRENT BEST SET, AND THAT IS PRECISELY WHAT I WANT TO
⭐   THROW AWAY."
```

```python
import heapq

def k_largest(nums, k: int) -> list[int]:
    h = []
    for x in nums:                        # ⭐ works on a stream
        if len(h) < k:
            heapq.heappush(h, x)
        elif x > h[0]:                    # ⭐⭐ PEEK IS O(1)
            heapq.heappushpop(h, x)       # ⭐ one sift, not two
    return sorted(h, reverse=True)
# ⭐ O(n log k) time, O(k) space.

def top_k_frequent(nums, k: int) -> list[int]:
    from collections import Counter
    counts = Counter(nums)
    # ⭐⭐ AND THE ANSWER THAT BEATS THE HEAP: BUCKET SORT.
    # ⭐ A frequency is at most n, so index BY frequency —
    # ⭐⭐ O(n), AND WORTH OFFERING AS THE FOLLOW-UP.
    buckets = [[] for _ in range(len(nums) + 1)]
    for val, c in counts.items():
        buckets[c].append(val)
    out = []
    for c in range(len(buckets) - 1, 0, -1):
        out.extend(buckets[c])
        if len(out) >= k:
            return out[:k]
    return out
```

# Part 3 — ⭐⭐ Intervals: choose the sort key first

```
⭐ ***THE ENTIRE TOPIC IS ONE DECISION, AND IT IS ALWAYS THE
⭐   FIRST LINE OF CODE.***

⭐  ┌──────────────────────────┬───────────────────────────────┐
⭐  │ ***MERGE OVERLAPPING***  │ ⭐⭐ SORT BY ***START***        │
⭐  │ ***INSERT INTERVAL***    │ ⭐⭐ SORT BY ***START***        │
⭐  │ ***MEETING ROOMS I***    │ ⭐ sort by start, check adjacent│
⭐  │ ***MEETING ROOMS II***   │ ⭐⭐ SORT BY START + ***A       │
⭐  │ (min rooms needed)       │ MIN-HEAP OF END TIMES***       │
⭐  │ ***NON-OVERLAPPING***    │ ⭐⭐ SORT BY ***END*** — ⭐ THIS  │
⭐  │ (fewest removals)        │ IS THE ONE PEOPLE GET WRONG    │
⭐  └──────────────────────────┴───────────────────────────────┘

⭐ ⭐⭐ WHY "FEWEST REMOVALS" SORTS BY ***END*** — ⭐ and be ready
⭐   to prove this, because it is the classic follow-up:
⭐   ⭐ It is the ***activity-selection*** problem: keeping the
⭐     most intervals is the same as removing the fewest.
⭐   ⭐ ⭐⭐ THE GREEDY ARGUMENT: ⭐ always keep the interval that
⭐     ***finishes earliest***, because it leaves the maximum
⭐     remaining room for everything after it.
⭐   ⭐ ⭐⭐ THE EXCHANGE ARGUMENT: ⭐ take any optimal solution; if
⭐     its first interval does not finish earliest, swap it for
⭐     the one that does. ⭐⭐ THE SOLUTION IS STILL VALID AND NO
⭐     SMALLER — SO A GREEDY-BY-END SOLUTION IS OPTIMAL.
⭐   ⭐ ⭐⭐ SAYING THAT PROOF IN TWO SENTENCES IS THE HIGHEST-
⭐     VALUE THIRTY SECONDS IN THIS ENTIRE TOPIC.

⭐ ***AND THE EDGE CASE THAT MUST BE ASKED ABOUT, NOT ASSUMED:***
⭐   ⭐ ⭐⭐ DO `[1,2]` AND `[2,3]` OVERLAP? ⭐ It decides `<` versus
⭐     `<=` and it changes the answer. ⭐⭐ ASK; DO NOT GUESS.
```

```python
def merge(intervals: list[list[int]]) -> list[list[int]]:
    intervals.sort(key=lambda x: x[0])        # ⭐⭐ THE ALGORITHM
    out = []
    for start, end in intervals:
        if out and start <= out[-1][1]:       # ⭐ `<=` touching merges
            out[-1][1] = max(out[-1][1], end) # ⭐⭐ `max` — the next
        else:                                 # interval may be
            out.append([start, end])          # CONTAINED
    return out
# ⭐ O(n log n) — dominated by the sort, and say so.
```

```python
def min_meeting_rooms(intervals: list[list[int]]) -> int:
    if not intervals:
        return 0
    intervals.sort(key=lambda x: x[0])
    ends = []                                 # ⭐⭐ MIN-HEAP OF END TIMES
    for start, end in intervals:
        # ⭐ the earliest-finishing room is the only one worth
        # ⭐⭐ CHECKING — if IT hasn't freed up, none have.
        if ends and ends[0] <= start:
            heapq.heappop(ends)               # ⭐ reuse that room
        heapq.heappush(ends, end)
    return len(ends)                          # ⭐⭐ PEAK CONCURRENCY
```

```python
def erase_overlap(intervals: list[list[int]]) -> int:
    if not intervals:
        return 0
    intervals.sort(key=lambda x: x[1])        # ⭐⭐ BY *END*
    kept, last_end = 1, intervals[0][1]
    for start, end in intervals[1:]:
        if start >= last_end:                 # ⭐ no overlap
            kept += 1
            last_end = end
    return len(intervals) - kept
```

# Part 4 — The mock: four problems, 45 minutes

```
⭐ ***P1 (8 min) — MERGE INTERVALS.*** ⭐ Ask the touching-
⭐   endpoints question ***before*** coding.
⭐ ***P2 (12 min) — MEETING ROOMS II.*** ⭐ Then: ⭐⭐ "SOLVE IT
⭐   WITHOUT A HEAP" ⭐ (the sweep line).
⭐ ***P3 (15 min) — MERGE k SORTED LISTS.***
⭐ ***P4 (10 min) — MEDIAN FROM A DATA STREAM.*** ⭐⭐ THE
⭐   TWO-HEAP PROBLEM, AND THE BEST HEAP QUESTION THERE IS.
```

```python
# ⭐⭐ P2 FOLLOW-UP — THE SWEEP LINE. Often clearer than the heap.
def min_rooms_sweep(intervals) -> int:
    # ⭐ Forget intervals. There are only EVENTS on a timeline.
    events = []
    for s, e in intervals:
        events.append((s, 1))     # ⭐ a room is taken
        events.append((e, -1))    # ⭐ a room is freed
    # ⭐⭐ THE TIE-BREAK IS THE WHOLE PROBLEM: at the same time,
    # -1 sorts before +1, so a meeting ENDING frees a room for
    # one STARTING. Without this you over-count by one.
    events.sort()
    cur = best = 0
    for _, delta in events:
        cur += delta
        best = max(best, cur)
    return best
# ⭐ O(n log n), O(n) — and it generalises to any "peak
# ⭐⭐ CONCURRENCY" QUESTION, WHICH IS WHY IT IS WORTH KNOWING.
```

```python
# ⭐ P3 — k-way merge. The heap holds ONE item per list.
def merge_k_lists(lists: list[list[int]]) -> list[int]:
    h = []
    for i, lst in enumerate(lists):
        if lst:
            # ⭐⭐ (value, list index, element index) — the middle
            # field is the TIE-BREAKER from Part 1 ③.
            heapq.heappush(h, (lst[0], i, 0))
    out = []
    while h:
        val, i, j = heapq.heappop(h)
        out.append(val)
        if j + 1 < len(lists[i]):
            heapq.heappush(h, (lists[i][j + 1], i, j + 1))
    return out
# ⭐⭐ O(N log k) WHERE N IS TOTAL ELEMENTS — *not* O(N log N).
# ⭐ The heap only ever holds k items. That is the whole point.
```

```python
# ⭐⭐ P4 — TWO HEAPS FACING EACH OTHER.
class MedianFinder:
    def __init__(self):
        self.low = []    # ⭐⭐ MAX-heap (negated) — smaller half
        self.high = []   # ⭐ min-heap — larger half

    def add(self, num: int) -> None:
        # ⭐ push to low, then move low's largest into high —
        # ⭐⭐ THIS TWO-STEP KEEPS BOTH HEAPS ORDERED CORRECTLY
        # WITHOUT ANY BRANCHING ON VALUE.
        heapq.heappush(self.low, -num)
        heapq.heappush(self.high, -heapq.heappop(self.low))
        # ⭐ rebalance so low is never smaller than high
        if len(self.high) > len(self.low):
            heapq.heappush(self.low, -heapq.heappop(self.high))

    def median(self) -> float:
        if len(self.low) > len(self.high):
            return -self.low[0]
        return (-self.low[0] + self.high[0]) / 2
# ⭐ O(log n) insert, ⭐⭐ O(1) READ.
```

# 💬 Interview

**1. "Find the k largest elements."**

⭐ A min-heap of size k, which is the opposite of most people's instinct. ⭐⭐ The reasoning I'd say out
loud is that the root of a min-heap holding my current best k is the *weakest* member of that set — so
it's precisely the one to evict when something better arrives. ⭐ That gives O(n log k) time and O(k)
space, against O(n log n) and O(n) for sorting. ⭐⭐ For k=10 out of ten million that's the difference
between a streaming solution and one that doesn't fit in memory, which is the real justification rather
than the asymptotic one. ⭐ And I'd use `heappushpop` rather than push-then-pop, since it's one sift
instead of two.

**2. "Why does 'fewest removals' sort by end time?"**

⭐ Because it's activity selection in disguise — keeping the most intervals is the same as removing the
fewest. ⭐⭐ The greedy is: always keep the interval that finishes earliest, because it leaves the
maximum remaining room for everything after it. ⭐ And the proof is an exchange argument: take any
optimal solution; if its first interval doesn't finish earliest, swap in the one that does. ⭐⭐ The
solution is still valid and no smaller, so greedy-by-end is optimal. ⭐ That's the classic follow-up on
this topic, and being able to give the argument in two sentences is worth more than knowing the sort key.

**3. "Solve meeting rooms without a heap."**

⭐ A sweep line, and it's often clearer. ⭐⭐ Forget intervals entirely — there are only events on a
timeline: a start takes a room, an end frees one. Sort the events, walk them, track the running count,
keep the maximum. ⭐ The whole problem is the tie-break: at the same timestamp, an end must sort before a
start, so a meeting finishing frees a room for one beginning. ⭐⭐ Without that you over-count by one.
⭐ It generalises to any peak-concurrency question, which is why I'd offer it even when the heap version
works.

**4. "What goes wrong with heap tuples?"**

⭐ Tuples compare element-wise, so `(priority, item)` gives a priority queue for free — until two
priorities tie. ⭐⭐ Then Python compares the second element, and if that's a dict or a custom object
without ordering, it raises `TypeError`. ⭐ The fix is a monotonic counter in the middle:
`(priority, counter, item)`. ⭐⭐ What makes it nasty is that it only fires when two priorities are
exactly equal, so it passes every small test and shows up in production. ⭐ It's also why the k-way
merge carries a list index — that's serving as the tie-breaker, not just as bookkeeping.

**5. "Median from a data stream."**

⭐ Two heaps facing each other: a max-heap for the smaller half, a min-heap for the larger half.
⭐⭐ The median is either the top of the bigger heap or the average of both tops, so reads are O(1) and
inserts are O(log n). ⭐ The implementation detail worth showing is the two-step insert — push onto the
low heap, then move the low heap's largest into the high heap, then rebalance if high got bigger.
⭐⭐ That keeps both halves correctly ordered with no branching on value, which is where people introduce
bugs. ⭐ And since `heapq` has no max-heap, the low half stores negated values.

**6. "Top-k frequent elements — can you beat the heap?"**

⭐ Yes, with bucket sort, and I'd offer it as the follow-up. ⭐⭐ A frequency is at most n, so I can index
*by* frequency: build n+1 buckets, drop each value into the bucket for its count, then walk from the
highest bucket down until I have k. ⭐ That's O(n) rather than O(n log k). ⭐⭐ The heap version is still
the right answer if the values are streaming or if memory matters, so I'd present it as a trade rather
than as strictly better.

## 🎙️ Articulation drill

⭐⭐ **Two minutes, out loud: "find the k most frequent elements in a large stream."**

Start by clarifying what changes the approach. **"Two questions first: is this a stream or can I hold it
all in memory, and how does k compare to n? Those two decide the whole solution."**

Then the heap answer, with the counterintuitive part explained. **"If it's a stream, I count frequencies
and keep a *min*-heap of size k. That's deliberately the opposite of the instinct — I want a min-heap for
the k largest, because the root is the weakest member of my current best set, which is exactly what I
want to evict when something better arrives. O(n log k) time, O(k) space, and I'd use `heappushpop` so
it's one sift rather than two."**

Then give the real justification, not the asymptotic one. **"For k of ten out of ten million, that's the
difference between something that streams in constant memory and something that has to hold the whole
input. The big-O gap is small; the practical gap is whether it runs."**

Then offer the better answer as a trade. **"If I can hold it all, I'd beat the heap with bucket sort. A
frequency is at most n, so I index *by* frequency — n+1 buckets, drop each value into its count's bucket,
walk down from the top until I have k. That's O(n). I'd present it as a trade rather than as strictly
better, because the heap still wins when the data is streaming or memory is bounded."**

Close with the Python detail. **"One implementation note: if I put tuples in the heap, I add a monotonic
counter between the priority and the item. Otherwise two equal priorities make Python compare the items,
and if those aren't orderable it raises TypeError — which only happens on a tie, so it passes every small
test and fails in production."**
