# Day 352 💬

**P-352** · 💬 **Design 8 — the chat system** — ⭐⭐ routing to a connection

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: chat is the one design where the state is a TCP connection you cannot move,
> so the central problem is routing — given a user id, find the machine holding their socket — and
> every other hard part (ordering, delivery receipts, presence) follows from the fact that the socket
> is an optimisation and the database is the truth.**

# Part 1 — ⭐ 0–8: scope and numbers

```
⭐⭐ FUNCTIONAL:
⭐   ① 1:1 messaging. ② Group chat (up to ~500).
⭐   ③ ⭐ Delivery receipts: sent / delivered / read.
⭐   ④ ⭐ Presence (online / last seen). ⑤ Offline delivery
⭐        and history.
⭐   ⭐⭐ OUT: voice/video, end-to-end encryption (⭐ mention that
⭐     E2EE removes server-side search and multi-device history
⭐     sync, which is a ***product*** decision, not a technical
⭐     one), media (⭐ presigned URLs, Day 327).

⭐⭐ NON-FUNCTIONAL:
⭐   ⭐ 50 M DAU, ⭐⭐ ~10 M CONCURRENT CONNECTIONS at peak.
⭐   ⭐ 40 messages/user/day ⇒ 2 × 10^9/day = ⭐ 23,000/s;
⭐     peak ~70,000/s.
⭐   ⭐ ⭐⭐ DELIVERY p99 < 500 ms — perceptible; chat that feels
⭐     laggy feels broken.
⭐   ⭐ ⭐⭐ ORDERING WITHIN A CONVERSATION IS ***REQUIRED***.
⭐     ⭐ Across conversations, irrelevant.
⭐   ⭐ ⭐⭐ ZERO MESSAGE LOSS. ⭐ This is the one where "we
⭐     dropped a few" is unacceptable, which rules out
⭐     fire-and-forget anywhere in the path.

⭐⭐ THE CONNECTION ESTIMATE THAT SIZES THE FLEET:
⭐   ⭐ A tuned Python/asyncio server holds ~50k–100k idle
⭐     WebSockets per instance (⭐ memory-bound: ~10–30 KB per
⭐     connection of buffers and Python objects).
⭐   ⇒ ⭐⭐ 10 M CONCURRENT ÷ 100k = ***~100–200 GATEWAY
⭐     INSTANCES***, ⭐ and that is a fleet whose only job is
⭐     holding sockets.
⭐   ⇒ ⭐⭐ WHICH IS EXACTLY WHY THE GATEWAY IS A ***SEPARATE
⭐     SERVICE*** FROM THE CHAT LOGIC: IT SCALES ON CONNECTION
⭐     COUNT, NOT ON MESSAGE RATE, AND THOSE ARE DIFFERENT
⭐     NUMBERS.
```

# Part 2 — ⭐⭐ The routing problem

```
⭐⭐ THE CORE DIFFICULTY: ⭐ Alice's socket is on gateway-7.
⭐   Bob's is on gateway-93. ⭐⭐ BOB'S MESSAGE ARRIVES AT
⭐   GATEWAY-93 AND MUST REACH A SOCKET ON A DIFFERENT MACHINE.
⭐   ⇒ ⭐ You cannot move a TCP connection. ⭐⭐ THIS IS DAY
⭐     324'S ONE LEGITIMATE USE OF AFFINITY: ***THE STATE IS
⭐     THE CONNECTION.***

⭐⭐ ① ***THE SESSION REGISTRY*** — `user_id -> gateway_id`,
⭐   in Redis, ⭐⭐ WITH A TTL AND A HEARTBEAT.
⭐   ⭐ ⭐⭐ THE TTL IS ESSENTIAL: A GATEWAY THAT CRASHES NEVER
⭐     DEREGISTERS ITS USERS, SO WITHOUT EXPIRY YOU ROUTE
⭐     MESSAGES INTO A VOID FOREVER (Day 341).
⭐   ⭐ ⭐⭐ AND MULTI-DEVICE MEANS IT IS `user_id -> SET OF
⭐     (device_id, gateway_id)`, NOT A SINGLE VALUE. ⭐ Getting
⭐     that wrong means a phone login silently kills a desktop
⭐     session.

⭐⭐ ② ***DELIVERY*** — three options:
⭐   ⭐ (a) ⭐ DIRECT RPC gateway→gateway. ⭐ Lowest latency.
⭐     ⭐ ✘ N² connection mesh; ⭐⭐ AND A GATEWAY MUST HANDLE
⭐     THE RACE WHERE THE TARGET DISCONNECTS MID-SEND.
⭐   ⭐ (b) ⭐⭐ PUB/SUB PER GATEWAY — each gateway subscribes to
⭐     its own channel; senders publish to `gw:{id}`.
⭐     ⭐ ✔ Simple, no mesh, ⭐ scales with gateways not with
⭐     users. ⭐⭐ THE PRACTICAL DEFAULT.
⭐   ⭐ (c) ⭐ PUB/SUB PER ***USER*** — `user:{id}`.
⭐     ⭐ ✘ ⭐⭐ 10 MILLION SUBSCRIPTIONS. ⭐ Most brokers
⭐     struggle; ⭐ it is the intuitive design and the wrong one.
⭐   ⇒ ⭐ Choose (b), ⭐⭐ AND SAY WHY (c) IS TEMPTING AND
⭐     WRONG — that comparison is the signal.

⭐⭐ ③ ⭐⭐ AND THE RULE THAT MAKES ALL OF THIS SAFE:
⭐   ***PERSIST THE MESSAGE ***BEFORE*** ATTEMPTING DELIVERY.***
⭐   ⇒ ⭐ Day 269's line, and here it is load-bearing: ⭐⭐ THE
⭐     SOCKET IS AN OPTIMISATION; THE DATABASE IS THE TRUTH.
⭐   ⇒ ⭐ Registry stale? Gateway dead? Recipient offline?
⭐     ⭐⭐ ALL THREE COLLAPSE INTO ONE CASE: THE MESSAGE IS
⭐     STORED, AND THE CLIENT WILL FETCH IT ON RECONNECT.
```

# Part 3 — ⭐⭐ Ordering without a global clock

```
⭐⭐ THE PROBLEM: two participants send simultaneously from
⭐   different regions. ⭐ What order does everyone see?
⭐   ⭐ ⭐⭐ SERVER WALL-CLOCK TIMESTAMPS ARE WRONG: skew is
⭐     10–100 ms (Day 343), and two messages can carry
⭐     ***identical*** timestamps.
⭐   ⭐ ⭐⭐ CLIENT TIMESTAMPS ARE WORSE: THEY ARE ATTACKER-
⭐     CONTROLLED AND OFTEN JUST WRONG (a phone with the wrong
⭐     date puts messages in 2009).

⭐⭐ ✔ ***A PER-CONVERSATION SEQUENCE NUMBER.***
⭐   ⭐ The conversation is the ordering domain. ⭐ One writer
⭐     assigns `seq = last_seq + 1` atomically.
⭐   ⭐ ⭐⭐ HOW: SHARD BY `conversation_id` AND MAKE THE
⭐     ASSIGNMENT A CONDITIONAL WRITE ON THAT SHARD — ⭐ Redis
⭐     `INCR`, a Cassandra LWT, or a Postgres sequence per
⭐     conversation. ⭐ Day 310's check-and-act, once more.
⭐   ⇒ ⭐⭐ TOTAL ORDER ***WITHIN*** A CONVERSATION, WHICH IS
⭐     THE ONLY PLACE IT IS REQUIRED. ⭐ No global clock, no
⭐     consensus, no coordination between conversations.
⭐   ⇒ ⭐⭐ AND IT GIVES YOU GAP DETECTION FOR FREE: A CLIENT
⭐     THAT HAS seq 1,2,3,7 ***KNOWS*** IT MISSED 4–6 AND CAN
⭐     ASK FOR THEM — ⭐ which is how sync-on-reconnect works
⭐     without a full history fetch.

⭐⭐ AND THE `client_message_id`:
⭐   ⭐ The sender generates a UUID; ⭐⭐ THE SERVER TREATS IT AS
⭐     AN IDEMPOTENCY KEY. ⭐ A retry over a flaky mobile network
⭐     does not create a duplicate (Day 335).
⭐   ⇒ ⭐ It also lets the client match its optimistic local echo
⭐     to the server's acknowledgement, ⭐⭐ WHICH IS WHAT MAKES
⭐     THE UI FEEL INSTANT WITHOUT LYING.
```

# Part 4 — ⭐⭐ Storage: the access pattern is the model

```
⭐⭐ THE ACCESS PATTERNS, IN ORDER OF FREQUENCY:
⭐   ① "Last 50 messages in conversation C" ⇒ ⭐⭐ 95% OF READS.
⭐   ② "Messages after seq N" ⇒ reconnect sync.
⭐   ③ "My conversation list, ordered by recent activity."
⭐   ④ Search — ⭐ a separate derived index (Day 337).

⭐⭐ ⇒ SO: `messages` PARTITIONED BY `conversation_id`,
⭐   CLUSTERED BY `seq DESC`.
⭐   ⭐ ⭐⭐ ONE PARTITION READ SERVES 95% OF TRAFFIC. ⭐ That is
⭐     Day 332's single-table thinking, and it is why a
⭐     wide-column store fits this problem so naturally.
⭐   ⭐ ⭐⭐ AND THE WIDE-PARTITION RISK (Day 348): A GROUP WITH
⭐     10 MILLION MESSAGES IS ONE ENORMOUS PARTITION. ⭐ Bucket
⭐     by `(conversation_id, month)` so partitions stay bounded.

⭐⭐ VOLUME: 2 × 10^9 messages/day × ~500 B = ⭐ 1 TB/day
⭐   ⇒ ⭐⭐ 365 TB/YEAR. ⭐ Tier it: recent hot, older to cheaper
⭐   storage, ⭐ and ask whether you keep it forever at all —
⭐   ⭐⭐ RETENTION IS A PRODUCT AND LEGAL DECISION THAT CHANGES
⭐   THE COST BY AN ORDER OF MAGNITUDE.

⭐⭐ THE CONVERSATION LIST is a separate, small, ***mutable***
⭐   table: `(user_id, conversation_id, last_message_seq,
⭐   unread_count, last_activity)`.
⭐   ⇒ ⭐⭐ UPDATED ON EVERY MESSAGE, SO IT IS 2 × 10^9 UPDATES A
⭐     DAY × PARTICIPANTS — ⭐ often ***hotter than the message
⭐     write itself***, and the piece people forget to size.
```

# Part 5 — ⭐⭐ Group chat and receipts: the multipliers

```
⭐⭐ GROUP FAN-OUT: ⭐ one message to a 500-person group is 500
⭐   deliveries and 500 conversation-list updates.
⭐   ⇒ ⭐ At 70,000 messages/s with an average group of 10, that
⭐     is ⭐⭐ 700,000 DELIVERIES/S. ⭐ Day 351's fan-out, at chat
⭐     latency.
⭐   ⇒ ⭐ Store the message ***once*** per conversation
⭐     (⭐⭐ NOT ONCE PER RECIPIENT), and fan out only the
⭐     ***notification***. ⭐ Each client reads the conversation
⭐     partition.
⭐   ⇒ ⭐⭐ THAT ONE DECISION TURNS 500 WRITES INTO 1 WRITE PLUS
⭐     500 PUSHES, AND PUSHES ARE CHEAP.

⭐⭐ READ RECEIPTS — ⭐⭐ THE HIDDEN N² THAT SURPRISES PEOPLE:
⭐   ⭐ A 500-person group: each message read by 500 people
⭐     ⇒ ⭐⭐ 500 RECEIPT EVENTS PER MESSAGE, ***EACH FANNED OUT
⭐     TO 500 PEOPLE*** IF YOU SHOW PER-USER RECEIPTS.
⭐   ⇒ ⭐⭐ 250,000 EVENTS FOR ONE MESSAGE. ⭐ This is why real
⭐     products disable per-user read receipts above a group
⭐     size.
⭐   ⇒ FIXES: ⭐ receipts as a ***high-water mark***
⭐     (`user X has read up to seq N` — one row, updated, not
⭐     one row per message); ⭐ batch and debounce them; ⭐⭐ AND
⭐     SHOW ONLY A ***COUNT*** IN LARGE GROUPS.

⭐⭐ PRESENCE — ⭐ the same shape, worse:
⭐   ⭐ Naive: every status change pushed to every contact.
⭐     ⭐ 50 M users × 100 contacts ⇒ ⭐⭐ A BROADCAST STORM ON
⭐     EVERY MORNING COMMUTE.
⭐   ⇒ FIXES: ⭐⭐ ***SUBSCRIBE TO PRESENCE ONLY FOR CONTACTS
⭐     WHOSE CHAT IS CURRENTLY ON SCREEN*** — typically fewer
⭐     than ten. ⭐ Coarse granularity ("last seen recently"
⭐     rather than to the second), ⭐ heartbeat every 30 s with a
⭐     90 s TTL, ⭐ and debounce flapping.
⭐   ⇒ ⭐⭐ AND SAY THE PRODUCT POINT: PRESENCE IS THE MOST
⭐     EXPENSIVE LOW-VALUE FEATURE IN CHAT, AND ITS PRECISION
⭐     SHOULD BE NEGOTIATED DOWN.
```

# Part 6 — ⭐⭐ Connections, reconnects and offline

```
⭐⭐ THE GATEWAY'S JOB — ⭐ five things and nothing else:
⭐   ⭐ Authenticate at handshake — ⭐⭐ VIA A SHORT-LIVED TICKET
⭐     FETCHED OVER HTTP, NOT A TOKEN IN THE QUERY STRING
⭐     (Day 269): query strings land in access logs.
⭐   ⭐ ⭐⭐ VALIDATE `Origin` — WEBSOCKETS ARE NOT PROTECTED BY
⭐     THE SAME-ORIGIN POLICY, SO WITHOUT THIS ANY SITE CAN
⭐     OPEN AN AUTHENTICATED SOCKET AS YOUR USER (CSWSH).
⭐   ⭐ Register in the session registry; heartbeat.
⭐   ⭐ ⭐⭐ MAINTAIN A ***BOUNDED*** PER-CONNECTION SEND BUFFER
⭐     AND DISCONNECT SLOW CONSUMERS. ⭐ A phone on a dying
⭐     network that cannot drain will otherwise consume the
⭐     gateway's memory (Day 336).
⭐   ⭐ Forward inbound messages to the chat service.

⭐⭐ RECONNECT — ⭐⭐ THE MOST IMPORTANT CLIENT PROTOCOL, AND THE
⭐   PLACE THUNDERING HERDS COME FROM:
⭐   ⭐ Client stores the last `seq` it has per conversation.
⭐   ⭐ On reconnect: ⭐⭐ `SYNC {conversation: last_seq}` ⇒ the
⭐     server returns everything after. ⭐ No full history fetch,
⭐     no duplicates.
⭐   ⭐ ⭐⭐ EXPONENTIAL BACKOFF WITH JITTER ON RECONNECT — ⭐ a
⭐     gateway restart drops 100,000 clients that will otherwise
⭐     all reconnect in the same second, ⭐⭐ AND THE RECONNECT
⭐     STORM IS WORSE THAN THE OUTAGE THAT CAUSED IT (Day 339).

⭐⭐ OFFLINE DELIVERY:
⭐   ⭐ The message is stored regardless (Part 2's rule).
⭐   ⭐ ⭐⭐ IF THE REGISTRY SAYS "NOT CONNECTED", SEND A ***PUSH
⭐     NOTIFICATION*** (Day 350) INSTEAD — ⭐ and that is the
⭐     handoff between the two systems.
⭐   ⭐ On next connect, the sync protocol delivers everything —
⭐     ⭐⭐ SO OFFLINE DELIVERY NEEDS NO SEPARATE QUEUE. ⭐ The
⭐     conversation partition ***is*** the queue, and noticing
⭐     that is the elegant part.
```

# Part 7 — ⭐ Bottlenecks and the summary

```
⭐⭐ WHAT BREAKS:
⭐   ① ⭐⭐ GATEWAY MEMORY. ⭐ 10 M sockets × 20 KB = 200 GB of
⭐      buffers across the fleet. ⭐ Tune buffer sizes; it is the
⭐      dominant cost.
⭐   ② ⭐ Registry lookups: 70,000/s ⇒ Redis, ⭐⭐ AND CACHE THE
⭐      MAPPING LOCALLY FOR A FEW SECONDS ON THE SENDING
⭐      GATEWAY — chat is bursty within a conversation, so the
⭐      hit rate is high.
⭐   ③ ⭐⭐ THE CONVERSATION-LIST TABLE — the hottest write in
⭐      the system. ⭐ Batch the unread counters; ⭐ consider a
⭐      counter store rather than a row update.
⭐   ④ ⭐ A gateway restart ⇒ ⭐⭐ 100,000 SIMULTANEOUS
⭐      RECONNECTS AND SYNC REQUESTS. ⭐ Drain slowly, jitter,
⭐      and rate-limit sync.

⭐⭐ THE SUMMARY:
⭐   ***"The state is a TCP connection you can't move, so the
⭐      core problem is routing: a session registry mapping user
⭐      to gateway, with a TTL because a crashed gateway never
⭐      deregisters, and delivery by pub/sub per gateway rather
⭐      than per user — ten million subscriptions is the
⭐      intuitive design and the wrong one. Everything is
⭐      persisted before delivery is attempted, so stale
⭐      registry, dead gateway and offline recipient collapse
⭐      into one case. Ordering is a per-conversation sequence
⭐      number, which needs no global clock and gives gap
⭐      detection for free. Groups store once and fan out
⭐      notifications, and receipts are high-water marks,
⭐      because per-user receipts in a five-hundred-person group
⭐      is a quarter of a million events for one message."***
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Delivering before persisting | Any failure loses the message, and this is the one system where that's unacceptable |
| ⭐⭐ Pub/sub channel per user | Ten million subscriptions. Intuitive and wrong; per-gateway scales with the fleet |
| ⭐⭐ Session registry with no TTL | A crashed gateway never deregisters and you route into a void forever |
| ⭐ Registry as a single value per user | Multi-device breaks; a phone login silently kills the desktop |
| ⭐⭐ Ordering by server timestamp | 10–100 ms of skew, and collisions. Per-conversation sequence numbers |
| ⭐ Trusting client timestamps | Attacker-controlled, and phones with wrong dates put messages in 2009 |
| ⭐⭐ Storing a group message per recipient | 500 writes instead of one. Store once, fan out notifications |
| ⭐⭐ Per-user read receipts in large groups | 250,000 events for one message in a 500-person group |
| ⭐ Receipts as a row per message per user | High-water mark: one row, updated |
| ⭐⭐ Naive presence broadcast | A storm every morning. Subscribe only to visible contacts, and coarsen precision |
| ⭐ Token in the WebSocket query string | It lands in access logs. Short-lived ticket over HTTP |
| ⭐⭐ No `Origin` check | WebSockets aren't covered by same-origin. Any site opens a socket as your user |
| ⭐ Unbounded per-connection send buffer | One phone on a dying network eats the gateway's memory |
| ⭐ Reconnect without jittered backoff | 100,000 clients return in the same second; the storm beats the outage |
| ⭐ Unbounded conversation partitions | A group with 10 M messages is one enormous partition. Bucket by month |

## Interview questions

**1. "How does a message get from Alice to Bob?"**
> ⭐ Alice's socket is on one gateway, Bob's on another, and you can't move a TCP connection. ⭐ So: a
> session registry in Redis mapping user to gateway, **with a TTL and heartbeats, because a crashed
> gateway never deregisters itself.** ⭐⭐ Delivery via **pub/sub per gateway** — sender publishes to
> `gw:{id}` — because a channel per user is ten million subscriptions, which is the intuitive design
> and the wrong one. ⭐⭐ And the rule that makes it safe: **persist before attempting delivery**, so a
> stale registry, a dead gateway and an offline recipient are all the same case.

**2. "How do you order messages?"**
> ⭐⭐ A per-conversation sequence number, assigned by a conditional write on the conversation's shard.
> ⭐ Server timestamps have ten to a hundred milliseconds of skew and can collide; client timestamps are
> attacker-controlled and often just wrong. ⭐ The conversation is the ordering domain, which is the
> only place order is required — so no global clock and no consensus. ⭐⭐ **And it gives gap detection
> free: a client holding 1, 2, 3, 7 knows it missed 4 through 6 and can ask for exactly those**, which
> is how reconnect sync works without fetching history.

**3. "How do you model storage?"**
> ⭐ From the access pattern: ninety-five percent of reads are "last fifty messages in this
> conversation", so partition by conversation and cluster by sequence descending — **one partition read
> serves almost all traffic.** ⭐⭐ Then the risk: **a group with ten million messages is one enormous
> partition**, so bucket by conversation and month. ⭐ And the piece people forget to size: the
> conversation-list table, updated on every message per participant, ⭐⭐ **which is often a hotter
> write than the messages themselves.**

**4. "Read receipts in a 500-person group?"**
> ⭐⭐ That's a hidden N²: five hundred people reading each message, and if each receipt fans out to
> everyone that's **a quarter of a million events for one message.** ⭐ So: receipts as a high-water
> mark — one row per user per conversation saying "read up to seq N", updated rather than inserted —
> batched and debounced. ⭐ And above a group size, show a count rather than per-user receipts, which is
> exactly what real products do.

**5. "How does presence work without a storm?"**
> ⭐ Naively, every status change pushes to every contact — fifty million users times a hundred
> contacts, which storms every morning. ⭐⭐ Instead **subscribe to presence only for contacts whose
> chat is currently on screen**, usually fewer than ten; heartbeat every thirty seconds with a
> ninety-second TTL; coarsen to "recently" rather than to the second; and debounce flapping. ⭐⭐ And
> I'd make the product point: **presence is the most expensive low-value feature in chat, and its
> precision should be negotiated down.**

**6. "A gateway with 100,000 connections restarts. What happens?"**
> ⭐ All hundred thousand clients reconnect — ⭐⭐ **and if they don't back off with jitter, the
> reconnect storm is worse than the outage that caused it.** ⭐ Each then sends a sync with its last
> sequence per conversation, so the server returns only the delta, which is why there's no full history
> fetch and no duplicates. ⭐ I'd drain slowly on shutdown, rate-limit sync, and rely on the registry
> TTL to clear the stale mappings. ⭐ Messages that arrived meanwhile were persisted, so nothing is lost
> — the conversation partition *is* the offline queue.

## 🎙️ Articulation drill

**Two minutes.** Name the distinctive constraint first: **this is the one design where the state is a
TCP connection you cannot move**, so the central problem is routing — given a user id, find the machine
holding their socket. Give the registry with its two details that matter: **a TTL, because a crashed
gateway never deregisters and you'd route into a void forever**, and a set of devices rather than a
single value. Then delivery, and make the comparison: **pub/sub per gateway, not per user, because ten
million subscriptions is the intuitive design and the wrong one.** Then the rule that simplifies
everything: **persist before attempting delivery — the socket is an optimisation, the database is the
truth** — so a stale registry, a dead gateway and an offline recipient collapse into one case, and
offline delivery needs no separate queue because the conversation partition already is one. On ordering,
refuse both clocks and use **a per-conversation sequence number, which needs no global clock and gives
gap detection free: a client holding 1, 2, 3, 7 knows exactly what to ask for.** Close on the two
multipliers people miss: **a group message is stored once and fanned out as notifications, not written
five hundred times**, and **per-user read receipts in a five-hundred-person group is a quarter of a
million events for one message** — which is why receipts are high-water marks and why presence
precision should be negotiated down rather than engineered up.
