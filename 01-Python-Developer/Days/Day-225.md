# Day 225 🎯

**P-225** · 🎯 **State** — ⭐⭐ derived state is a bug, and the four questions

**Time:** 3 hrs · **Mode:** NEW · **⭐⭐ The highest-value day in the stage**

> ⭐⭐ **The sentence to own: anything you can compute from something else must not be stored, because
> two copies of the same fact will drift and nothing will tell you when — and the overwhelming
> majority of React bugs, including most of the ones people blame on effects, are two sources of
> truth for one fact.**
>
> Today: ⭐ the four questions, ⭐⭐ derived state, where state lives, and normalising it.

---

# Part 1 — ⭐⭐ Is it state at all?

```
⭐⭐ THE FOUR QUESTIONS. ASK THEM BEFORE EVERY useState.

⭐ ① ⭐ IS IT PASSED IN AS A PROP?          ⇒ not state.
⭐ ② ⭐⭐ CAN I COMPUTE IT FROM OTHER STATE
⭐      OR PROPS?                           ⇒ ⭐⭐ NOT STATE. COMPUTE IT.
⭐ ③ ⭐ DOES IT STAY THE SAME ACROSS RENDERS
⭐      AND NOBODY RE-RENDERS ON CHANGE?    ⇒ a ref, or a constant.
⭐ ④ ⭐⭐ DOES IT COME FROM THE SERVER?      ⇒ ⭐ SERVER CACHE, NOT
⭐                                             CLIENT STATE. Day 228.

⭐   ⇒ ⭐⭐ WHAT SURVIVES ALL FOUR IS ACTUAL STATE, AND IT IS ALWAYS
⭐     LESS THAN YOU EXPECTED. Most components need one or two pieces.
```

# Part 2 — Derived state, the bug

```jsx
// ❌ THE BUG. It is everywhere, and it always looks reasonable.
const [items, setItems] = useState([]);
const [count, setCount] = useState(0);          // ⭐⭐ DERIVED
const [hasItems, setHasItems] = useState(false); // ⭐⭐ DERIVED
const [total, setTotal] = useState(0);           // ⭐⭐ DERIVED

function add(item) {
  setItems([...items, item]);
  setCount(count + 1);
  setTotal(total + item.price);
  setHasItems(true);
  // ⭐⭐ FOUR WRITES THAT MUST ALL BE CORRECT, FOREVER, IN EVERY
  //    CODE PATH. remove() forgets one. The bulk import forgets two.
  //    ⇒ THE COUNT SAYS 5 AND THE LIST SHOWS 4. NOTHING ERRORS.
}
```

```jsx
// ✅ ONE source of truth. Everything else is computed on render.
const [items, setItems] = useState([]);
const count    = items.length;                              // ⭐ free
const hasItems = items.length > 0;
const total    = items.reduce((s, i) => s + i.price, 0);
// ⭐⭐ CANNOT DRIFT. There is nothing to keep in sync.
```

| ⭐ Objection | Answer |
|---|---|
| *"Recomputing every render is slow"* | ⭐⭐ It is a `.length` and a loop over ten items — nanoseconds. **Measure before you memoise** (Day 232). |
| *"But it's a big list"* | ⭐ Then `useMemo` the computation. Still **one** source of truth; you have cached a derivation, not stored a second fact. |
| *"I need it in a callback"* | ⭐ Compute it there. It is still derived. |

```
⭐⭐ THE FAMILY OF BUGS THIS ONE PRODUCES

⭐   · the badge count disagrees with the list
⭐   · "no results" shows while results are visible
⭐   · the total is right until you delete a row
⭐   · a filter is applied but the empty state never clears
⭐   ⇒ ⭐⭐ ALL THE SAME BUG. TWO COPIES OF ONE FACT.
⭐   ⇒ ⭐ AND IT IS THE SAME LESSON AS DAY 480'S DOUBLE-ENTRY LEDGER:
⭐     THE BALANCE IS DERIVED FROM THE ENTRIES, NEVER STORED
⭐     ALONGSIDE THEM.
```

### The special case: props → state

```jsx
// ❌ initialises ONCE, then ignores the prop forever
function Editor({ user }) {
  const [name, setName] = useState(user.name);   // ⭐⭐ STALE when user changes
```

| ⭐ What you actually wanted | Do this |
|---|---|
| A field that resets when the record changes | ⭐⭐ `<Editor key={user.id} …/>` — a changed key **remounts** and re-initialises. **The idiomatic fix.** |
| Genuinely uncontrolled after first load | ⭐ Keep it, and name it `initialName` so the intent is explicit |
| Fully controlled | ⭐ Lift the state to the parent; no local copy at all |

# Part 3 — Where state lives

```
⭐⭐ PUT IT AS LOW AS POSSIBLE. LIFT ONLY WHEN FORCED.

⭐   ① ⭐ ONE component uses it        ⇒ inside that component
⭐   ② ⭐ TWO SIBLINGS need it         ⇒ lift to their COMMON PARENT
⭐   ③ ⭐ Half the app needs it        ⇒ Context (Day 231) — ⭐ and it is
⭐                                        usually auth, theme, or locale
⭐   ④ ⭐⭐ IT CAME FROM THE SERVER      ⇒ ⭐⭐ NOT REACT STATE AT ALL.
⭐                                        A CACHE. Day 228.
⭐   ⑤ ⭐ It belongs in the URL         ⇒ ⭐⭐ THE URL. Filters, tabs,
⭐      (shareable, bookmarkable,          page number, search query.
⭐       survives refresh)                 Day 233.

⭐   ⇒ ⭐⭐ LIFTING TOO EARLY is the other half of the problem: state in
⭐     a root component re-renders the world and couples everything to it.
```

> ⭐ **The URL is state you keep forgetting you have.** A filtered list whose filter is in `useState`
> loses it on refresh and cannot be shared. In the URL it survives, is linkable, and gets back/forward
> for free. **Interviewers notice when a candidate reaches for the URL unprompted.**

# Part 4 — Shape it flat

```jsx
// ❌ nested — updating one item is a nightmare of spreads
const [state, setState] = useState({
  users: [{ id: "1", posts: [{ id: "a", comments: [...] }] }]
});

// ✅ normalised — ⭐ the same rule as a relational schema (Stage 5)
const [usersById, setUsersById] = useState({ "1": { id:"1", postIds:["a"] } });
const [postsById, setPostsById] = useState({ "a": { id:"a", commentIds:[] } });

// ⭐ updating one user, flat:
setUsersById(prev => ({ ...prev, [id]: { ...prev[id], name } }));
```

| ⭐ Rule | |
|---|---|
| **Flat over nested** | ⭐⭐ Deep updates need a spread per level, and one missed level mutates shared data. |
| **`id → object` maps, plus id arrays for order** | ⭐ O(1) lookup, and order is data you can change independently. |
| **Never duplicate an object into two places** | ⭐⭐ Store the id. Duplicates are the drift bug at a different scale. |
| **`useReducer` when transitions are the point** | ⭐ Several fields that change together, or a real state machine — the reducer *names* the transitions, which is what makes it worth it. |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you decide what belongs in state?"**

Lead with the rule and the reason. **Anything I can compute from something else doesn't get stored,
because two copies of one fact will drift and nothing tells me when. If I keep a list and a count, then
every code path has to update both forever — remove forgets one, the bulk import forgets two, and the
badge says five while the list shows four. No error, no crash. The count is just `items.length`,
computed on render, and then it can't drift.**

Connect it to something outside React, which shows it is a principle rather than a framework rule.
**It's the same reason a ledger derives the balance from the entries instead of storing it alongside
them. One source of truth, everything else computed.**

Then the questions, briefly. **Before every `useState` I ask: is it a prop, can I compute it, does
anything re-render when it changes, and did it come from the server? Server data isn't client state,
it's a cache with staleness — different problem, different tool. What survives all four is always less
than I expected.**

Close on placement, including the one people forget. **State goes as low as possible and gets lifted
only when forced, because state in a root component re-renders the world. And filters, tabs and search
queries belong in the URL, not in `useState` — that way they survive a refresh, they're shareable, and
back and forward work for free.**
