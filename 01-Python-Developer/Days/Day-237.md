# Day 237 🔀

**P-237** · 🔀 **CORS from the other side** — ⭐⭐ it protects other sites from you

**Time:** 3 hrs · **Mode:** RECALL → NEW

> ⭐⭐ **The sentence to own: CORS is not a defence for your API — it is the browser relaxing a rule it

# Part 1 — ⭐⭐ The correction

You learned CORS from the server on Day 020. Here is the part that is usually taught backwards.

```
⭐⭐ WHAT THE SAME-ORIGIN POLICY IS ACTUALLY FOR

⭐   You are logged into bank.com. You visit evil.com.
⭐   evil.com runs: fetch("https://bank.com/balance", {credentials:"include"})
⭐   ⭐ THE REQUEST IS SENT. ⭐⭐ THE COOKIE IS ATTACHED. THE SERVER
⭐     PROCESSES IT. ⭐ THE BROWSER THEN REFUSES TO LET evil.com
⭐     **READ THE RESPONSE**.

⭐   ⇒ ⭐⭐ SO CORS PROTECTS **bank.com's USER** FROM **evil.com's SCRIPT**.
⭐     IT DOES NOT PROTECT bank.com's API FROM ANYONE.
⭐   ⇒ ⭐⭐ AND NOTE: THE REQUEST STILL HAPPENED. IF IT WAS A
⭐     STATE-CHANGING GET, THE DAMAGE IS DONE AND CORS BLOCKED ONLY
⭐     THE READING OF THE RECEIPT. **THAT IS CSRF** (Day 235).
```

| ⭐ Belief | ⭐⭐ Reality |
|---|---|
| *"CORS secures my API"* | ⭐⭐ It does nothing against curl, Postman, a server, or any non-browser client |
| *"`*` is a vulnerability"* | ⭐ On a **public** API it is correct and normal. It is only wrong **with credentials** |
| *"A CORS error means my server rejected it"* | ⭐⭐ Usually your server **replied 200**. The *browser* hid the response from your JS |

> ⭐ **Read that last row again in DevTools.** The Network tab shows the request and often a 200. The
> Console shows a CORS error. Both are true — and knowing that saves you an hour of debugging a
> server that is working fine.

# Part 2 — Simple requests vs preflight

```
⭐⭐ A "SIMPLE" REQUEST GOES STRAIGHT OUT — no preflight:
⭐   · GET, HEAD, or POST
⭐   · AND only "safe" headers
⭐   · AND Content-Type is one of:
⭐       text/plain · multipart/form-data · application/x-www-form-urlencoded

⭐⭐ ANYTHING ELSE IS PREFLIGHTED — and this catches everyone:
⭐   ⭐⭐ Content-Type: application/json  ⇒ **NOT SIMPLE**
⭐   ⭐ Authorization: Bearer ...        ⇒ NOT SIMPLE
⭐   ⭐ any custom header (X-Request-Id) ⇒ NOT SIMPLE
⭐   ⇒ ⭐⭐ SO ESSENTIALLY EVERY REAL API CALL YOU MAKE IS PREFLIGHTED.
```

```http
OPTIONS /api/orders                       ⭐ the browser asks first
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization

⭐ the server must answer:
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400        ⭐⭐ CACHE IT — otherwise EVERY
                                     request pays a second round trip
```

> ⭐⭐ **`Max-Age` is a real performance setting.** Without it, every POST is two round trips. With it,
> one per day per origin. **This is a free latency win people leave on the floor.**

# Part 3 — ⭐⭐ The four errors, decoded

| ⭐ Console says | ⭐⭐ What it means | Fix |
|---|---|---|
| *"No `Access-Control-Allow-Origin` header"* | ⭐ The server did not answer the preflight, or answered without the header. **Often your OPTIONS route 404s or a middleware rejects it.** | Ensure OPTIONS is handled **before** auth middleware |
| *"…header has a value `*` that is not equal to the supplied origin"* | ⭐⭐ You sent `credentials: "include"` **and** the server returned `*`. **Forbidden combination.** | Echo the exact origin from an allow-list |
| *"Method PATCH is not allowed"* | The preflight response omitted it | Add it to `Allow-Methods` |
| *"Request header field x-tenant-id is not allowed"* | ⭐ Your custom header is not in `Allow-Headers` | Add it — ⭐ note it is **case-insensitive but must be listed** |

```python
# ⭐ FastAPI — the correct shape for a credentialed API
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],   # ⭐⭐ EXPLICIT LIST, never "*"
    allow_credentials=True,                      #    when credentials are on
    allow_methods=["GET","POST","PATCH","DELETE"],
    allow_headers=["content-type","authorization"],
    max_age=86400,                               # ⭐ cache the preflight
)
```

```
⭐⭐ THE ONE THAT IS ACTUALLY DANGEROUS

⭐   ❌ allow_origins = [request.headers["origin"]]   # "echo it back"
⭐      + allow_credentials = True
⭐   ⇒ ⭐⭐ THIS ALLOWS **EVERY** ORIGIN WITH COOKIES ATTACHED.
⭐     IT IS `*` WITH CREDENTIALS, WHICH THE SPEC FORBIDS, IMPLEMENTED
⭐     BY HAND. ⭐ ANY SITE CAN NOW READ YOUR API AS YOUR LOGGED-IN USER.
⭐   ⇒ ⭐ AN ALLOW-LIST, CHECKED, OR NOTHING.
```

> ⭐ **Regex origin matching is where this goes wrong quietly:** `.*\.example\.com` also matches
> `evil-example.com.attacker.net` if you forget to anchor it. **Anchor the pattern, or use exact
> strings.**

# Part 4 — Making it a non-problem

```
⭐⭐ THE BEST CORS CONFIG IS NO CROSS-ORIGIN AT ALL

⭐   ① ⭐⭐ SAME ORIGIN: serve the app and the API from one origin,
⭐      /api/* proxied to the backend.
⭐      ⇒ ⭐ NO CORS. NO PREFLIGHT. SameSite=Lax cookies just work.
⭐        NO Access-Control HEADERS TO GET WRONG.
⭐   ② dev proxy: Vite's server.proxy makes localhost:5173/api →
⭐      localhost:8000. ⭐ Dev matches prod, which kills a whole class
⭐      of "works in dev" bugs.
⭐   ③ ⭐ SUBDOMAINS (app. + api.) still need CORS, but they are
⭐      SAME-SITE, so cookies with SameSite=Lax work.
⭐   ④ genuinely different domains ⇒ ⭐⭐ CORS + SameSite=None; Secure
⭐      + A CSRF TOKEN. The most work, the most to get wrong.
```

> ⭐⭐ **Choosing same-origin deployment removes CORS, most CSRF exposure, and the `SameSite=None`
> requirement in one architectural decision.** That is a much better interview answer than any
> header configuration.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "explain CORS."**

Correct the usual framing first, because most candidates state it backwards. **CORS isn't a defence for
my API. It's the browser relaxing a rule it imposes on scripts. If I'm logged into my bank and visit a
malicious site, that site's fetch to the bank is still sent, the cookie is still attached, and the
server still processes it — the browser just refuses to let the script read the response. So it
protects the bank's user from the malicious page, not the bank's API from anyone. Curl is entirely
unaffected.**

Add the consequence, which is the useful half. **Because the request still happens, a state-changing
GET is already done and CORS only blocked reading the receipt. That's CSRF, and it's why SameSite and
an Origin check are separate controls.**

Then the debugging insight. **A CORS error usually means my server replied 200 and the browser hid it
from my JavaScript. The Network tab shows the request succeeding while the console shows an error, and
both are true — knowing that saves an hour of debugging a server that's working fine. And essentially
every real API call is preflighted, because `Content-Type: application/json` isn't a simple request.
Setting Max-Age matters: without it every POST is two round trips.**

Close on the architectural answer, which beats any header. **The best CORS config is no cross-origin at
all — serve the app and API from one origin with `/api` proxied. That removes CORS, most CSRF exposure,
and the SameSite=None requirement in a single decision. And it makes dev match prod, which kills a
whole class of "works locally" bugs.**
