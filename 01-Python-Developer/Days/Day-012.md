**L-012** · ⭐⭐ **What HTML actually is** — a document, a tree, the DOM · not a programming language

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: HTML is a serialised tree. The browser parses it into the DOM, and from
> that moment on the HTML is gone — the DOM is the truth.** Everything confusing about front-end
> work becomes simple once you hold that distinction.
>
> As a backend engineer you will spend your life **producing** HTML (Jinja2, Django templates) and
> **parsing** it (scraping, testing). Both jobs go badly if you think of it as text.

# Part 1 — ⭐⭐ Markup, not programming

```
⭐ HTML is a MARKUP language: it describes STRUCTURE and MEANING. It has:
⭐   ✗ no variables   ✗ no loops   ✗ no conditionals   ✗ no functions
⭐   ⇒ ⭐⭐ it cannot compute anything. It is a DESCRIPTION, not an instruction.

⭐ The three-way split you must never blur:
⭐   HTML       ⇒ ⭐ STRUCTURE and MEANING   ("this is a heading, this is a nav")
⭐   CSS        ⇒ ⭐ PRESENTATION            (Day 013)
⭐   JavaScript ⇒ ⭐ BEHAVIOUR               (Day 014)
```

⚠️ ⭐⭐ **"Is HTML a programming language?" is asked to see whether you understand categories.** The
answer is no, with the reason: it is not Turing-complete and expresses no computation. Say it
without embarrassment — this is not a trick, and hedging is the wrong signal.

# Part 2 — ⭐⭐ The tree, and the DOM

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Ada</title>
  </head>
  <body>
    <h1 id="title">Hello</h1>
    <p class="lead">World <a href="/next">next</a></p>
  </body>
</html>
```

```
⭐⭐ WHAT THE BROWSER BUILDS — a tree of NODES, not a string:

  Document
   └── html            (element, lang="en")
        ├── head
        │    ├── meta
        │    └── title ── "Ada"          ⭐ text node
        └── body
             ├── h1    (id="title") ── "Hello"
             └── p     (class="lead")
                  ├── "World "           ⭐ text node
                  └── a (href="/next") ── "next"
```

| ⭐ Term | ⭐ Meaning |
|---|---|
| ⭐ **HTML** | the **text** you sent over the wire |
| ⭐⭐ **DOM** | ⭐⭐ the **live in-memory tree** the browser built from it |
| ⭐ Node | anything in the tree — element, text, comment |
| ⭐ Element | a node from a tag |
| ⭐ Attribute | `id`, `class`, `href` — data on an element |

```
⭐⭐ THE DISTINCTION THAT ANSWERS A DOZEN FUTURE QUESTIONS:
⭐   "View source"  ⇒ ⭐ the HTML the SERVER SENT
⭐   DevTools "Elements" ⇒ ⭐⭐ the CURRENT DOM, including everything JS changed
⭐   ⇒ ⭐⭐ they differ on any dynamic page — and if you scrape with `requests`,
⭐        ⭐⭐ YOU GET THE FIRST ONE. That is why scraping a React site returns an empty div.
```

⚠️ ⭐⭐ **This is the single most common confusion in Python scraping.** `requests.get(url).text` is
the pre-JavaScript HTML. If the content is rendered client-side it is **not in there** — no parser
will find it. The options are: find the JSON API the page itself calls (usually best), or drive a
real browser (`playwright`). **Day 014 and Day 015 explain exactly why.**

## ⭐ The browser repairs your mistakes — and that is a trap

```html
<p>one<p>two          <!-- ⭐ no closing tags -->
<b><i>x</b></i>       <!-- ⭐ mis-nested -->
```

⭐⭐ **HTML parsing is defined to never fail.** The spec specifies error recovery precisely, so both
of those produce a valid DOM — just possibly not the one you meant. ⭐⭐ **Which means: your broken
HTML will "work", right up until the DOM the browser invented differs from the one your CSS selector
or your test assumed.**

# Part 3 — ⭐ Semantics, and why they are not decoration

```html
<!-- ⭐ Meaningless soup — renders identically, means nothing: -->
<div class="header"><div class="nav-thing">...</div></div>

<!-- ⭐⭐ Semantic — same pixels, real meaning: -->
<header><nav>...</nav></header>
<main><article><h1>...</h1><section>...</section></article></main>
<footer>...</footer>
```

| ⭐ Who reads the semantics | ⭐ What they do with them |
|---|---|
| ⭐⭐ **Screen readers** | ⭐⭐ "navigation landmark", "heading level 1" — **`div` says nothing** |
| Search engines | ⭐ what this page is *about* |
| ⭐ Reader modes, browsers | extract the article |
| ⭐ Other developers | the structure is self-documenting |

⭐⭐ **Accessibility is not optional and it is not charity — in many jurisdictions it is a legal
requirement**, and it is one of the few areas where doing the right thing costs you nothing but
choosing the correct tag name.

```html
<!-- ⭐⭐ THE RULE THAT COVERS 80% OF ACCESSIBILITY: use the element that means the thing. -->
<div onclick="submit()">Send</div>   <!-- ⚠️ ⭐⭐ not focusable, no keyboard, no role -->
<button onclick="submit()">Send</button>  <!-- ⭐ free: focus, Enter/Space, role, disabled -->
```

## ⭐ Forms — the part a backend engineer must know cold

```html
<form action="/login" method="POST">          <!-- ⭐⭐ THIS is the HTTP request being described -->
  <label for="email">Email</label>
  <input id="email" name="email" type="email" required>   <!-- ⭐⭐ `name` = the key you receive -->
  <input name="password" type="password">
  <button type="submit">Log in</button>
</form>
```

```
⭐⭐ WHAT ARRIVES AT YOUR PYTHON HANDLER:
⭐   POST /login HTTP/1.1
⭐   Content-Type: application/x-www-form-urlencoded      ⭐⭐ NOT JSON
⭐   email=ada%40example.com&password=hunter2
⭐
⭐ ⇒ ⭐⭐ `name` is the field key. No `name`, no data — the field is simply not sent.
⭐ ⇒ ⭐ method="GET" instead puts the fields in the QUERY STRING (Day 010: safe, idempotent).
⭐ ⇒ ⭐⭐ file uploads REQUIRE enctype="multipart/form-data".
⭐ ⇒ ⭐⭐ `required` / type="email" are CONVENIENCE, not validation —
⭐      ⚠️ anyone can POST directly with curl. VALIDATE ON THE SERVER. ALWAYS.
```

# Part 4 — ⭐⭐ HTML from Python: templates and the injection you will cause

```python
# ⚠️⚠️ ⭐⭐ NEVER build HTML by concatenating user input.
html = f"<p>Hello {name}</p>"        # ⭐⭐ name = "<script>fetch('/steal?c='+document.cookie)</script>"
```

```python
# ⭐ Jinja2 (Flask/FastAPI) and Django templates AUTOESCAPE by default:
from jinja2 import Environment
env = Environment(autoescape=True)                 # ⭐⭐ TRUE. Check this; it is False by default
env.from_string("<p>Hello {{ name }}</p>").render(name="<script>x</script>")
# ⇒ <p>Hello &lt;script&gt;x&lt;/script&gt;</p>    ⭐ rendered as TEXT, not executed
```

⚠️ ⭐⭐ **The two ways people defeat their own escaping:** calling `| safe` (Jinja) or
`mark_safe`/`{% autoescape off %}` (Django) on user data, and building HTML strings in Python and
injecting them into the template. **`| safe` on anything a user can influence is a stored XSS.**

⭐ **Parsing HTML in Python:** use a parser, never a regular expression.

```python
from bs4 import BeautifulSoup
soup = BeautifulSoup(html, "html.parser")     # ⭐ or "lxml" — faster, stricter
soup.select("article h2 a")                   # ⭐ CSS selectors — the same ones Day 013 teaches
```

⭐⭐ **"Why can't you parse HTML with a regex?"** Because HTML is a **nested, recursive** structure
with error recovery, and regular expressions cannot describe arbitrary nesting. **You will get 90% of
cases and be permanently broken on the rest.**

# Part 5 — C-08 · ⭐ DNS internals

⭐ Day 007 gave you the resolution path. Today: the mechanics you get asked about.

```
⭐⭐ RECURSIVE vs ITERATIVE — the distinction people fumble:

⭐ YOU ──"resolve api.example.com, and don't come back until you have it"──▶ RESOLVER
⭐                                                   ⭐⭐ that request is RECURSIVE
⭐
⭐ RESOLVER ──"who serves .com?"──▶ ROOT      ──▶ "ask these"    ⭐⭐ ITERATIVE
⭐           ──"who serves example.com?"──▶ TLD ──▶ "ask these"   ⭐⭐ ITERATIVE
⭐           ──"what is api.example.com?"──▶ AUTHORITATIVE ──▶ the answer
⭐
⭐ ⇒ ⭐⭐ Your client makes ONE recursive query; the resolver makes SEVERAL iterative ones.
⭐    ⇒ ⭐ Referrals, not forwarding — each server answers "not me, try there".
```

| ⭐ Record | ⭐ What it holds | ⭐ Note |
|---|---|---|
| `A` / `AAAA` | IPv4 / IPv6 address | |
| ⭐ `CNAME` | an **alias** to another name | ⚠️ ⭐⭐ **illegal at the apex** — `example.com` cannot be a CNAME |
| `MX` | mail servers + priority | |
| `TXT` | arbitrary text | ⭐ SPF, DKIM, domain-ownership proofs |
| `NS` | which servers are authoritative | |
| `SOA` | zone metadata, **default TTL** | |
| ⭐ `SRV` | service + port | ⭐ used by service discovery |
| ⭐ `PTR` | reverse lookup | ⭐ mail servers check this |

```
⭐⭐ WHY CNAME-AT-APEX BITES YOU ON YOUR FIRST DEPLOYMENT:
⭐   your host gives you   myapp-1234.herokudns.com
⭐   www.example.com ⇒ CNAME ⇒ fine.
⭐   example.com     ⇒ CNAME ⇒ ⭐⭐ ILLEGAL (the apex must also carry NS and SOA records,
⭐                              and a CNAME may not coexist with other records)
⭐   ⇒ ⭐ FIX: your DNS provider's non-standard "ALIAS"/"ANAME"/"flattened CNAME" record,
⭐        which resolves the target and serves an A record on the fly.
```

⭐ **TTL and propagation:** ⭐⭐ **"DNS propagation" is not a thing — nothing propagates.** Caches
expire. A record has a TTL; every resolver holds it that long and no notification exists. **So the
migration procedure is: lower the TTL to 60 s, wait for the *old* TTL to fully expire, change the
record, then raise the TTL again.** Skip step one and you wait a day.

⚠️ ⭐ **Negative caching is real:** an `NXDOMAIN` is cached too (per the SOA), which is why a
just-created record can appear broken for longer than you expect on a machine that already asked.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"HTML is a programming language"** | ⭐ No computation, no Turing-completeness. It is markup. |
| ⭐⭐ **Confusing view-source with the DOM** | ⭐⭐ One is what the server sent; one is live. Scraping gets the first. |
| ⭐ Parsing HTML with regex | ⭐⭐ Nesting is recursive; regex cannot express it. Use a parser. |
| `<div onclick>` instead of `<button>` | ⭐ Loses focus, keyboard, role — for nothing. |
| Trusting `required` / `type="email"` | ⚠️ ⭐⭐ Client-side only. Validate on the server. |
| Forgetting `name` on an input | ⭐⭐ The field is simply not submitted. |
| f-string HTML with user data | ⭐⭐ XSS. Use a template with autoescape. |
| ⭐ `\| safe` on user content | ⭐⭐ You have just disabled the protection. |
| Saying "DNS propagation" | ⭐ Caches expire; nothing propagates. Lower TTL first. |
| CNAME at the apex | ⭐ Illegal — use ALIAS/ANAME. |
| Forgetting negative caching | ⭐ `NXDOMAIN` is cached too. |

## Interview questions

**Q: What is the DOM, and how is it different from HTML?**
> HTML is the serialised text the server sends. The DOM is the live tree the browser builds from it
> in memory — nodes, elements, text, attributes — and it is what CSS matches against and what
> JavaScript mutates. After parsing, the HTML string is irrelevant; the DOM is the state. That's why
> view-source and the Elements panel disagree on any dynamic page.

**Q: Why does your scraper return an empty page for some sites?**
> Because `requests` performs one HTTP request and gives me the initial HTML. If the page renders its
> content in JavaScript, that content isn't in the response at all — it arrives from a later API call
> the browser makes. The right first move is to open the network tab and find that API, which is
> usually JSON and far easier to consume than HTML. If it's genuinely required, drive a real browser
> with Playwright and accept the cost.

**Q: Why not parse HTML with a regular expression?**
> Because HTML nests arbitrarily and regular languages can't describe arbitrary nesting. On top of
> that, real HTML is frequently malformed and browsers apply a specified error-recovery algorithm, so
> the tree isn't a mechanical function of the tags. A parser implements that algorithm; a regex
> implements my optimism.

**Q: How do you safely render user-supplied text into a page from Python?**
> Through a template engine with autoescaping on — Jinja2 with `autoescape=True`, or Django
> templates, which do it by default. The escaping has to happen at output time, in the template, not
> at input time, because the correct escaping depends on the context you're inserting into. And never
> mark user content safe: `| safe` and `mark_safe` disable exactly the protection you want.

**Q: Difference between a recursive and an iterative DNS query?**
> Recursive is what my machine sends to its resolver: "give me the final answer". Iterative is what
> the resolver then does: it asks the root, gets a referral to the TLD servers, asks those, gets a
> referral to the authoritative servers, and asks those. Each of those servers answers "not me, try
> here" rather than doing the work — so one recursive request produces several iterative ones.

**Q: You need to migrate a domain to a new host with no downtime. How?**
> Lower the record's TTL first — to 60 seconds — and then wait out the *old* TTL, because every
> resolver that already cached it will hold the old value for that long and there is no way to
> invalidate it. Once the old TTL has expired everywhere, change the record; clients pick it up
> within a minute. Then put the TTL back up. If the domain is at the apex I also can't use a CNAME,
> so I need the provider's ALIAS record.

## 🎙️ Articulation drill

Record two minutes: **"Explain HTML, and the difference between HTML and a server, to a
non-technical person."**

⭐ A server is a **program**, running on a machine, waiting for requests. ⭐ HTML is one of the
**things it can send back** — a description of a document: this is a heading, this is a link, this is
a form. ⭐⭐ **The browser reads that description and builds a live model of the document — the DOM —
and from then on it is the model that matters, not the text.** CSS styles that model, JavaScript
changes it.

⭐⭐ **The line that proves you understand the split:** *the server sends a description once; the
browser owns it from then on.*
