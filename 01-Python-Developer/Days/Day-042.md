# Part 1 — ⭐⭐ A function is an object with attributes

```python
def greet(name: str, punct: str = "!") -> str:
    """Say hello."""
    return f"Hello {name}{punct}"

greet.__name__          # ⭐ "greet"
greet.__qualname__      # ⭐ "greet" — or "Class.method" — used in tracebacks
greet.__doc__           # ⭐ "Say hello."
greet.__module__        # ⭐ where it was defined
greet.__defaults__      # ⭐⭐ ("!",) — Day 025's mutable-default bug lives here
greet.__annotations__   # ⭐⭐ {'name': str, 'punct': str, 'return': str}
greet.__code__          # ⭐ the compiled code object
greet.__code__.co_varnames, greet.__code__.co_argcount
greet.__dict__          # ⭐⭐ {} — YES, you can set arbitrary attributes on a function
```

```python
# ⭐ Function attributes are real, and libraries use them:
greet.call_count = 0            # ⭐⭐ perfectly legal
def route(path):
    def deco(fn):
        fn._route = path        # ⭐ tag the function; a registry scans for the tag later
        return fn
    return deco
```

```
⭐⭐ ANNOTATIONS ARE METADATA, NOT ENFORCEMENT. Say this precisely:
⭐   def f(x: int) -> str  ⇒ Python stores {"x": int, "return": str} and DOES NOTHING ELSE.
⭐   ⇒ ⭐⭐ f("not an int") runs happily. There is no runtime check. None.
⭐   ⇒ ⭐ the value comes from mypy (Day 062), from your IDE, and from libraries that READ
⭐        them at runtime — Pydantic, FastAPI and dataclasses all do exactly that.
```

⭐⭐ **"Python has type hints but is not type-checked at runtime" is a common interview probe**, and
the good answer names *who* consumes them: a static checker, an editor, and frameworks that
deliberately introspect `__annotations__` to generate validation, serialisation and documentation.

# Part 2 — ⭐ Introspection with `inspect`

```python
import inspect
sig = inspect.signature(greet)
sig                            # ⭐ (name: str, punct: str = '!') -> str
sig.parameters["punct"].default, sig.parameters["punct"].kind
inspect.getsource(greet)       # ⭐ the source text
inspect.isfunction / ismethod / isgenerator / iscoroutinefunction     # ⭐⭐ the last one matters a lot
```

⭐⭐ **`inspect.signature` is what FastAPI reads to build your API.** Your parameter names, types and
defaults *become* the query parameters, the request body schema and the OpenAPI docs — **which is why
Day 044's decorators must preserve the signature or the framework sees the wrapper's `(*args,
**kwargs)` instead of yours.**

⭐ **`iscoroutinefunction`** is how a framework decides whether to `await` your handler or run it in
a thread pool — the mechanism behind FastAPI accepting both `def` and `async def` routes (Day 072).

# Part 3 — ⭐ `lambda`

```python
square = lambda x: x ** 2      # ⚠️ ⭐⭐ PEP 8 says don't — use `def square(x): return x ** 2`
sorted(people, key=lambda p: p.age)          # ⭐ THIS is what lambda is for
filter(lambda x: x > 0, nums)
defaultdict(lambda: defaultdict(int))        # ⭐ a factory that takes no arguments
```

```
⭐⭐ WHAT A LAMBDA IS: an expression that evaluates to a function object. Nothing more.
⭐   · ⭐ ONE expression, no statements — no assignment, no `if` statement (the ternary is fine),
⭐     no `try`, no `return`
⭐   · ⭐⭐ __name__ is "<lambda>" ⇒ tracebacks and profiles are anonymous and useless
⭐ ⇒ ⭐⭐ SO: assigning a lambda to a name buys you nothing and COSTS you the name in the
⭐      traceback. Use it inline, where the function has no independent identity.
```

⭐ **Prefer `operator` to a trivial lambda** (Day 045): `key=operator.attrgetter("age")` is faster
than `key=lambda p: p.age`, because it avoids a Python-level call per element — **and in a sort of a
million items that is a measurable difference**, since `key` is called n times (Day 033).

# Part 4 — ⭐ Higher-order functions

```python
# ⭐ Functions as arguments
sorted(xs, key=len)
max(people, key=lambda p: p.score)
list(map(str.upper, words))
list(filter(None, items))            # ⭐⭐ `None` as the predicate ⇒ drop falsy values

# ⭐ Functions as return values (Day 043)
def multiplier(n):
    def inner(x): return x * n
    return inner

# ⭐⭐ Functions as data — the dispatch table (Days 023, 035)
OPS = {"+": operator.add, "-": operator.sub}
fn = OPS[token]
fn(a, b)
```

```
⭐⭐ map/filter VS COMPREHENSIONS — the real rule:
⭐   ✓ ⭐ map(str.upper, words)          — an EXISTING named function ⇒ map reads fine
⭐   ✗ ⭐⭐ map(lambda x: x*2, xs)        — ⭐⭐ [x*2 for x in xs] is clearer AND faster
⭐        (the lambda adds a Python-level call per element; the comprehension does not)
⭐   ✓ map/filter are LAZY in Python 3 ⇒ ⭐ good in a pipeline over a large stream
⭐ ⇒ ⭐ and `reduce` is in functools, not builtins, ⭐⭐ because Guido thought a loop was
⭐      almost always clearer. That opinion is usually right (Day 051).
```

⭐ **The three built-ins worth knowing here:** `any`/`all` (short-circuiting, and they take
generators, so `any(x > 5 for x in huge)` stops at the first hit), and `sorted`'s `key`.

```python
# ⭐ Callables are broader than functions (Day 031):
callable(len), callable(int), callable(MyClass), callable(instance_with_call)   # ⭐⭐ all True
```

⭐⭐ **A class is callable** — calling it constructs an instance. **So `int`, `list` and your own
classes are all valid values for `key=`, `defaultdict(...)`, and anywhere else a "factory" is
wanted**, with no lambda required.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Expecting annotations to be enforced** | ⭐⭐ Pure metadata. mypy, editors and frameworks read them. |
| ⭐ Assigning a lambda to a name | ⭐ Use `def` — you lose the name in every traceback. |
| `map(lambda ...)` where a comprehension fits | ⭐ Clearer and faster without the per-element call. |
| Trivial lambdas in `key=` | ⭐⭐ `operator.attrgetter`/`itemgetter` — n calls saved. |
| Forgetting `map`/`filter` are lazy | ⭐ They return iterators; `list()` them to see anything. |
| Assuming only `def` makes callables | ⭐ Classes, `partial`, and `__call__` objects too. |
| Ignoring `__wrapped__`/signature loss | ⭐⭐ Day 044 — it breaks FastAPI and docs tooling. |
| Setting attributes on a function and calling it hacky | ⭐ It is how many registries work. |

## Interview questions

**Q: What does `def` actually do?**
> Compiles the body into a code object, builds a function object around it with the defaults,
> annotations and closure attached, and binds it to a name in the current namespace. It's a statement
> that runs, not a declaration — which is why defaults are evaluated once at that moment, and why a
> `def` inside a function creates a new function object every call. And the resulting object is
> ordinary: I can store it in a dict, pass it, return it, and set attributes on it.

**Q: Are Python type hints enforced?**
> No. They're stored in `__annotations__` and otherwise ignored at runtime — `f("string")` on a
> function annotated `x: int` runs fine. Their value comes from three consumers: static checkers like
> mypy, editors, and libraries that deliberately read them at runtime. That last group is the
> interesting one — Pydantic, FastAPI and dataclasses all introspect annotations to generate
> validation, serialisation and OpenAPI schemas, so in those frameworks the hints do have runtime
> effect, just not from the language.

**Q: When is a lambda appropriate?**
> Inline, where the function has no independent identity — a `key=`, a small predicate, a
> zero-argument factory for `defaultdict`. Assigning one to a name is the case to avoid: it does
> exactly what `def` does but leaves `__name__` as `<lambda>`, so tracebacks and profiler output lose
> the name. And for trivial attribute or item access I'd reach for `operator.attrgetter` instead,
> since `key` is called once per element and that avoids a Python-level call each time.

**Q: `map`/`filter` or comprehensions?**
> A comprehension unless there's already a named function to apply. `map(str.upper, words)` reads
> well; `map(lambda x: x*2, xs)` is worse than the comprehension in both clarity and speed, because
> the lambda is a real function call per element while the comprehension's expression is inlined into
> the loop. The one thing `map` and `filter` have going for them is laziness, which matters in a
> pipeline over a large stream — though a generator expression gives me that too.

**Q: Why does `inspect.signature` matter in practice?**
> Because frameworks build behaviour from it. FastAPI reads my handler's parameters, types and
> defaults to generate query parameters, the request body model and the OpenAPI documentation. That's
> why a badly written decorator breaks things in a way that looks unrelated: if the wrapper doesn't
> preserve the signature, the framework sees `(*args, **kwargs)` and my endpoint loses all its
> parameters.

Record two minutes: **"What does it mean that functions are first-class in Python?"**

function can go in a dict, be passed as an argument, be returned from another function, and carry

being syntax you memorise and become the obvious thing to do with a higher-order function."*
