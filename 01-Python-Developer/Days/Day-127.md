**L-127** · 🔒 **Security I** — injection, XSS and SSRF, and ⭐⭐ the one principle underneath all three

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: injection of every kind is one mistake repeated — data crossing into a
> position where it is read as instructions — so the fix is never smarter escaping, it is a channel
> where code and data cannot be confused.**
>
> ⭐ You have already met this principle three times: parameterised SQL, `subprocess` with a list, and
> the algorithm pinned in a JWT. **Today it gets named**, and then applied to the three vulnerabilities
> that dominate real incidents.

# Part 1 — ⭐⭐ The principle

```
⭐⭐ EVERY INJECTION IS THE SAME SHAPE:
⭐        YOU BUILD A STRING THAT MIXES **CODE YOU WROTE** WITH **DATA THEY SENT**,
⭐        AND HAND IT TO AN INTERPRETER THAT CANNOT TELL THEM APART.
⭐
⭐   SQL      f"SELECT … WHERE name = '{name}'"   ⇒ the SQL parser
⭐   Shell    f"ping {host}"          shell=True   ⇒ the shell         (Days 076, 079)
⭐   HTML     f"<p>{comment}</p>"                  ⇒ the browser
⭐   LDAP · XPath · NoSQL · a template engine · a log line · a CSV opened in Excel
⭐
⭐ ⇒ ⭐⭐ THE FIX IS ALWAYS THE SAME AND IT IS NEVER ESCAPING: USE A CHANNEL
⭐     WHERE CODE AND DATA TRAVEL SEPARATELY.
⭐        SQL   ⇒ ⭐ bound parameters — the query goes one way, values another
⭐        Shell ⇒ ⭐ an argv LIST — no shell parses anything
⭐        HTML  ⇒ ⭐ a template engine that escapes by default
⭐   ⇒ ⭐⭐ ESCAPING IS THE FALLBACK, AND IT LOSES OVER TIME: every escaping
⭐        function is context-specific, and the contexts multiply (HTML body vs
⭐        attribute vs JavaScript vs URL vs CSS). ⭐ Someone eventually uses the
⭐        wrong one. ⭐⭐ A separate channel cannot be used wrongly.
```

# Part 2 — ⭐⭐ SQL injection

```python
# ⚠️⚠️ VULNERABLE
cur.execute(f"SELECT * FROM users WHERE email = '{email}'")
# ⇒ ⭐ email = "' OR '1'='1"          ⇒ every user
# ⇒ ⭐⭐ email = "'; DROP TABLE users--"  ⇒ …if the driver allows multiple statements

# ⭐⭐ SAFE — the query and the values never meet as text
cur.execute("SELECT * FROM users WHERE email = %s", (email,))
```

```
⭐⭐ WHY A BOUND PARAMETER IS SAFE, AND IT IS NOT "IT ESCAPES QUOTES": THE QUERY
⭐   IS PARSED AND PLANNED **BEFORE** THE VALUE IS SUPPLIED. The value never
⭐   passes through the SQL parser at all — ⭐⭐ so there is no syntax for it to
⭐   become. ⭐ It arrives as a typed value in the protocol, alongside a query
⭐   whose shape is already fixed.
⭐   ⇒ ⭐ that is also why it is often FASTER: the plan can be cached and reused
⭐        across values (Stage 5).
```

```python
# ⚠️ ⭐⭐ WHAT PARAMETERS CANNOT PROTECT — IDENTIFIERS (Day 121):
cur.execute(f"SELECT * FROM orders ORDER BY {sort_column}")     # ⚠️ injectable
# ⇒ ⭐⭐ YOU CANNOT BIND A COLUMN NAME, A TABLE NAME, OR A DIRECTION.
# ⭐ THE ONLY SAFE FORM IS AN ALLOWLIST:
SORTS = {"created_at": "created_at", "total": "total"}
column = SORTS.get(sort_column) or raise HTTPError(400, "invalid sort")
```

| ⭐ Also worth knowing | |
|---|---|
| ⭐ ORMs are safe **by default** | ⚠️ ⭐⭐ `session.execute(text(f"…{x}"))` and `.raw()` bypass it entirely |
| ⭐⭐ **Blind injection** | ⭐ no output — the attacker uses timing (`pg_sleep`) or boolean differences |
| ⭐ Second-order | ⭐⭐ stored safely, then interpolated later by a **different** query |
| ⭐ Least privilege | ⭐ the app's DB user should not own the schema — ⭐⭐ then `DROP TABLE` fails even if injected |
| ⭐ Error messages | ⭐⭐ a leaked constraint name is a free schema map (Day 120) |

# Part 3 — ⭐⭐ XSS

```
⭐⭐ THREE KINDS, AND THE THIRD NEVER TOUCHES YOUR SERVER:
⭐  1. ⭐ STORED    — a comment containing `<script>` is saved and served to
⭐       everyone. ⭐⭐ The worst: one payload, every visitor.
⭐  2. ⭐ REFLECTED — input echoed straight back (a search term, an error
⭐       message — ⭐ Days 119, 120's warning about echoing values).
⭐  3. ⭐⭐ DOM-BASED — the server is never involved: JavaScript reads
⭐       `location.hash` and writes it into `innerHTML`. ⭐ No server-side fix
⭐       exists, so a backend-only review misses it entirely.
```

```
⭐⭐ WHY IT IS THE MOST SERIOUS CLIENT-SIDE BUG: THE ATTACKER'S SCRIPT RUNS
⭐   INSIDE YOUR ORIGIN, AS THE VICTIM.
⭐   ⇒ ⭐ it can read anything the page can, act as the user, and — unless the
⭐        cookie is `HttpOnly` (Day 115) — ⭐⭐ TAKE THE SESSION AWAY AND USE IT
⭐        FROM ANYWHERE, FOREVER.
⭐   ⇒ ⭐⭐ AND IT DEFEATS EVERY CSRF DEFENCE, because the script can read your
⭐        token and make the request from the legitimate origin. ⭐ That is why
⭐        Day 115 said XSS is the more serious bug.
```

```python
# ⭐ DEFENCE 1 — CONTEXTUAL ESCAPING, BY DEFAULT:
env = Environment(autoescape=True)          # ⭐⭐ Jinja2: ON, and never turn it off
# ⚠️ `{{ comment | safe }}` and `Markup(...)` disable it — ⭐ treat both as
#    blocking review comments unless the value is provably server-generated.
```

```
⚠️ ⭐⭐ AND THE THING AUTOESCAPING DOES NOT COVER — CONTEXT:
⭐    `<div>{{ x }}</div>`            ⇒ ⭐ HTML escaping is correct
⭐    `<a href="{{ x }}">`            ⇒ ⭐⭐ `javascript:alert(1)` STILL RUNS —
⭐         HTML-escaping does nothing to a URL scheme. ⭐ Validate the scheme.
⭐    `<script>var a = {{ x }}</script>` ⇒ ⭐⭐ JS context — HTML escaping is the
⭐         WRONG escaper. Use `|tojson`, or better, do not put data in a script tag.
⭐    `<div onclick="{{ x }}">`       ⇒ ⭐ an event handler is JS context too
⭐   ⇒ ⭐⭐ FIVE CONTEXTS, FIVE ESCAPERS — WHICH IS EXACTLY WHY PART 1 SAYS
⭐        ESCAPING LOSES. ⭐ Prefer: never interpolate into an attribute or a
⭐        script; pass data via `data-` attributes or a JSON endpoint and let the
⭐        DOM API do the insertion.
```

```
⭐⭐ DEFENCE 2 — CONTENT SECURITY POLICY, WHICH IS THE ONLY DEFENCE THAT WORKS
⭐   *AFTER* YOU HAVE MADE A MISTAKE:
⭐     Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-r4nd0m';
⭐                              object-src 'none'; base-uri 'none'
⭐   ⇒ ⭐⭐ AN INJECTED `<script>` WITHOUT THE NONCE DOES NOT EXECUTE. ⭐ The bug
⭐        is still there; the exploit is not.
⭐   ⇒ ⚠️ ⭐ `'unsafe-inline'` in `script-src` disables essentially all of it —
⭐        ⭐⭐ and it is the most common way a CSP is present and worthless.
⭐   ⇒ ⭐ deploy with `Content-Security-Policy-Report-Only` first, collect
⭐        violations, then enforce.
⭐
⭐ ⭐ DEFENCE 3 — the supporting headers:
⭐     X-Content-Type-Options: nosniff        ⭐⭐ stop the browser guessing a type
⭐     Referrer-Policy: strict-origin-when-cross-origin
⭐     Strict-Transport-Security: max-age=31536000; includeSubDomains
⭐     Content-Type: text/html; charset=utf-8  ⭐⭐ always the charset (Day 124)
```

# Part 4 — ⭐⭐ SSRF

```python
# ⚠️⚠️ ⭐⭐ "FETCH THE IMAGE AT THIS URL" — one of the most dangerous features
#    you can build:
@app.route("/import", methods=["POST"])
def import_image(request, user):
    return httpx.get(request.json["url"]).content        # ⚠️⚠️ SSRF
```

```
⭐⭐ THE ATTACKER SUPPLIES A URL AND **YOUR SERVER** MAKES THE REQUEST — FROM
⭐   INSIDE YOUR NETWORK, WITH YOUR IDENTITY:
⭐   · ⭐ `http://localhost:6379` ⇒ your Redis, unauthenticated
⭐   · ⭐ `http://10.0.0.5/admin` ⇒ an internal service with no auth because
⭐        "it is only reachable internally"
⭐   · ⭐⭐ `http://169.254.169.254/latest/meta-data/iam/…` ⇒ THE CLOUD METADATA
⭐        SERVICE ⇒ ⭐⭐ TEMPORARY IAM CREDENTIALS FOR YOUR ROLE. ⭐ This is how
⭐        the Capital One breach happened, and it is still the first thing tried.
⭐   · ⭐ `file:///etc/passwd`, `gopher://`, `dict://` ⇒ other schemes entirely
⭐   ⇒ ⭐⭐ SSRF TURNS YOUR SERVER INTO THE ATTACKER'S PROXY, AND EVERY "TRUSTED
⭐        INTERNAL NETWORK" ASSUMPTION FAILS AT ONCE.
```

```
⭐⭐ DEFENCES, WEAKEST TO STRONGEST — AND NOTE THAT THE FIRST TWO ARE NOT ENOUGH:
⭐  1. ⚠️ ⭐ BLOCK-LIST HOSTNAMES ⇒ ⭐⭐ TRIVIALLY BYPASSED: `127.0.0.1` also
⭐       spells `2130706433`, `0177.0.0.1`, `[::1]`, `localtest.me`, and a
⭐       domain YOU control can simply RESOLVE to 127.0.0.1.
⭐  2. ⭐ ALLOW-LIST SCHEMES (`https` only) and PORTS ⇒ ⭐ necessary, insufficient.
⭐  3. ⭐⭐ RESOLVE THE HOSTNAME YOURSELF, CHECK THE **IP** AGAINST PRIVATE
⭐       RANGES, AND CONNECT TO THAT IP ⇒ ⭐⭐ this is the real fix, and the last
⭐       clause matters: resolving-then-connecting-by-name reintroduces
⭐       **DNS REBINDING**, where the second lookup returns 127.0.0.1.
⭐  4. ⭐ DISABLE REDIRECTS, or re-validate every hop — ⭐⭐ a permitted URL that
⭐       302s to the metadata service defeats a check done only on the input.
⭐  5. ⭐⭐ THE STRONGEST: FETCH FROM AN ISOLATED EGRESS PROXY with no route to
⭐       your internal network. ⭐ Then a bypass reaches nothing worth having.
⭐  ⇒ ⭐ plus: IMDSv2 on AWS (requires a header, so a plain GET fails), timeouts,
⭐       a response size limit, and never returning the raw body to the caller.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ f-strings in SQL | ⭐⭐ Bound parameters — the value never passes through the parser. |
| ⭐ Escaping quotes by hand | ⭐ Context-specific and it loses. Use a separate channel. |
| ⭐⭐ **Interpolating an identifier** | ⭐⭐ Parameters cannot bind column names. Allowlist. |
| `text(f"…")` inside an ORM | ⭐ You just bypassed the protection you were relying on. |
| ⭐ App DB user owns the schema | ⭐⭐ Least privilege makes `DROP TABLE` fail even if injected. |
| Turning off autoescaping | ⭐ `|safe` is a blocking review comment. |
| ⭐⭐ **Trusting autoescaping in an attribute or script** | ⭐⭐ Five contexts, five escapers. `javascript:` still runs in `href`. |
| `'unsafe-inline'` in CSP | ⭐⭐ The most common way a CSP is present and worthless. |
| No CSP at all | ⭐ The only defence that works after you have made a mistake. |
| ⭐⭐ **Fetching a user-supplied URL** | ⭐⭐ SSRF. Resolve, check the IP, connect to that IP, no redirects. |
| Blocking `localhost` by name | ⭐ `2130706433`, `[::1]`, or a domain you control pointing at 127.0.0.1. |
| Validating the URL but following redirects | ⭐ A 302 to the metadata service defeats it. |
| ⭐ Trusting the internal network | ⭐⭐ SSRF is exactly the assumption failing. |

## Interview questions

**Q: What is the common principle behind injection vulnerabilities?**
> Data reaching a position where it's read as instructions. You build a string mixing code you wrote
> with data they sent and hand it to an interpreter that can't tell them apart — and that's SQL
> injection, shell injection, XSS, LDAP, template injection, all of it. The fix is never smarter
> escaping, it's a channel where code and data travel separately: bound parameters, an argv list, a
> template engine that escapes by default. Escaping loses over time because it's context-specific and
> the contexts multiply — HTML body versus attribute versus JavaScript versus URL — so eventually
> someone uses the wrong one. A separate channel can't be used wrongly.

**Q: Why is a bound parameter safe? And when can't you use one?**
> Because the query is parsed and planned before the value is supplied, so the value never passes
> through the SQL parser and there's no syntax for it to become — it arrives as a typed value
> alongside a query whose shape is already fixed. That's also why it's often faster, since the plan can
> be cached. What you can't parameterise is an identifier: a column name, table name or sort direction.
> So `ORDER BY {user_input}` has to be an allowlist mapping the client's string to a column you
> control.

**Q: Why is XSS more serious than CSRF?**
> Because the attacker's script runs inside your origin as the victim. It can read anything the page
> can, act as the user, and — unless the session cookie is `HttpOnly` — take the credential away and
> use it from anywhere, indefinitely. It also defeats every CSRF defence, because the script can read
> the CSRF token and make the request from the legitimate origin. CSRF is a write-only attack that
> `SameSite` plus a token largely handles; XSS is total compromise of the page. And DOM-based XSS never
> touches the server at all, so a backend-only review misses it entirely.

**Q: What is SSRF and how do you defend against it?**
> Your server makes a request to a URL the attacker chose, from inside your network with your
> identity. The first thing tried is the cloud metadata service, which hands back temporary IAM
> credentials for your role — that's how the Capital One breach worked. Blocking hostnames doesn't
> work, because `127.0.0.1` also spells `2130706433` and `[::1]`, and an attacker's own domain can
> simply resolve to it. The real fix is to resolve the hostname yourself, check the resulting IP
> against private ranges, and connect to *that IP* — connecting by name after checking reintroduces DNS
> rebinding. Plus disabling redirects, because a permitted URL that 302s to the metadata service
> defeats a check done only on the input. Strongest of all is fetching through an isolated egress proxy
> with no route to internal services, so a bypass reaches nothing worth having.

**Q: What does a Content Security Policy buy you?**
> It's the only defence that works *after* you've made a mistake. With `script-src 'self'` and a nonce,
> an injected script tag simply doesn't execute — the bug is still there but the exploit isn't. The
> caveat is that `'unsafe-inline'` in `script-src` disables essentially all of it, and that's the most
> common way a CSP ends up present and worthless. I'd deploy in report-only mode first, collect
> violations, then enforce. And it doesn't excuse escaping — the point of defence in depth is that
> you'll make a mistake somewhere, and the second layer decides whether it becomes an incident.
