# Day 110

**L-110** · **ASGI** — `scope`, `receive`, `send`, and ⭐⭐ how one protocol covers HTTP, WebSockets and lifespan

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: ASGI replaces "one call in, one return out" with "a scope plus two async
> channels" — and because messages can flow in both directions for as long as the connection lives,
> HTTP, WebSockets, streaming and startup hooks all become the same protocol with a different scope
> type.**
>
> ⭐ Day 109 derived what WSGI cannot do. **Today is the shape that can**, and it is the interface
> FastAPI, Starlette and Django's async mode all speak.

---

# Part 1 — ⭐⭐ The signature, and why it is that shape

```python
async def app(scope: dict, receive: Callable, send: Callable) -> None:
    ...
```

| | ⭐ What it is |
|---|---|
| ⭐⭐ `scope` | ⭐ a dict describing **the connection** — type, path, headers, client. **Constant for its lifetime** |
| ⭐⭐ `receive` | ⭐⭐ `await receive()` ⇒ the **next incoming message**. Called as many times as you like |
| ⭐⭐ `send` | ⭐⭐ `await send(message)` ⇒ push a message **out**. Called as many times as you like |

```
⭐⭐ COMPARE THE TWO SHAPES AND EVERYTHING FOLLOWS:
⭐   WSGI:  app(environ, start_response) -> Iterable[bytes]
⭐          ⇒ ⭐ ONE call. ONE return. ⭐⭐ The conversation is over before you
⭐            can ask a question.
⭐   ASGI:  await app(scope, receive, send)
⭐          ⇒ ⭐⭐ A COROUTINE THAT LIVES AS LONG AS THE CONNECTION, with an
⭐            inbox and an outbox it may use in any order, any number of times.
⭐
⭐ ⇒ ⭐⭐ AND NOW ALL FOUR OF DAY 109'S LIMITS DISSOLVE AT ONCE:
⭐     · many inbound messages     ⇒ ⭐ WebSockets, streamed uploads
⭐     · many outbound messages    ⇒ ⭐ streaming responses, SSE
⭐     · it is a COROUTINE         ⇒ ⭐⭐ it can await, so one thread serves
⭐                                     thousands of connections (Day 106)
⭐     · a `lifespan` scope type   ⇒ ⭐ startup and shutdown hooks
⭐   ⇒ ⭐⭐ ONE DESIGN CHANGE, FOUR CAPABILITIES. That is why the spec is worth
⭐        understanding rather than memorising.
```

# Part 2 — ⭐ HTTP, by hand

```python
async def app(scope, receive, send):
    assert scope["type"] == "http"

    # ⭐ 1. READ THE BODY — it arrives as one or more messages
    body = b""
    while True:
        message = await receive()                     # ⭐⭐ {"type": "http.request", ...}
        body += message.get("body", b"")
        if not message.get("more_body", False):       # ⭐⭐ the framing flag
            break

    # ⭐ 2. SEND THE HEAD, THEN THE BODY — always in that order
    await send({
        "type": "http.response.start",
        "status": 200,
        "headers": [(b"content-type", b"application/json")],   # ⭐⭐ BYTES, and lowercase
    })
    await send({
        "type": "http.response.body",
        "body": json.dumps({"ok": True}).encode(),
    })
```

```
⭐⭐ THREE THINGS TO NOTICE, EACH DELIBERATE:
⭐  1. ⭐⭐ HEADERS ARE A LIST OF (bytes, bytes) PAIRS, NOT A DICT — ⭐ so
⭐       DUPLICATES SURVIVE and casing is not mangled. ⭐⭐ That is the direct fix
⭐       for Day 109's lossy `environ`, and it is why `Set-Cookie` works
⭐       correctly without a special case.
⭐  2. ⭐⭐ THE BODY ARRIVES IN PIECES, with `more_body` telling you whether to
⭐       keep asking. ⭐ You are doing Day 104's framing again — but the SERVER
⭐       has done the parsing, and hands you the pieces.
⭐  3. ⭐ `http.response.start` THEN `http.response.body`. ⭐⭐ Once you have sent
⭐       the start message THE STATUS IS FIXED (Day 105) — so validate before it.
```

```python
# ⭐⭐ STREAMING — just send more body messages:
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/csv")]})
    async for row in query_rows():                              # ⭐ Day 047, async
        await send({"type": "http.response.body",
                    "body": row.encode(), "more_body": True})   # ⭐⭐ more to come
    await send({"type": "http.response.body", "body": b""})     # ⭐ more_body defaults False ⇒ end
```

⭐ **`http.disconnect`** arrives from `receive()` when the client goes away mid-response. ⭐⭐ **Check
for it in a long stream** or you will happily generate a 2 GB export for a browser tab that closed
thirty seconds ago.

# Part 3 — ⭐ WebSockets and lifespan — the same protocol

```python
async def websocket_app(scope, receive, send):
    assert scope["type"] == "websocket"
    while True:
        message = await receive()
        if message["type"] == "websocket.connect":
            await send({"type": "websocket.accept"})            # ⭐ or .close to reject
        elif message["type"] == "websocket.receive":
            text = message.get("text") or message["bytes"].decode()
            await send({"type": "websocket.send", "text": f"echo: {text}"})
        elif message["type"] == "websocket.disconnect":
            break
```

```
⭐⭐ NOTHING NEW HAS BEEN ADDED. Same signature, same two channels — ⭐ only the
⭐   scope type and the message names differ. ⭐⭐ Day 017's upgrade handshake,
⭐   frame parsing and masking are all done by the SERVER; you get messages.
⭐   ⇒ ⭐⭐ THAT IS THE ELEGANCE OF THE DESIGN, and it is the answer to "why does
⭐        ASGI look like this" — one shape, three protocols.
⭐   ⇒ ⚠️ ⭐ AND THE PART THAT IS STILL YOURS: authenticate on `websocket.connect`
⭐        BEFORE accepting, and remember the browser cannot set headers on a
⭐        WebSocket ⇒ ⭐⭐ the token comes via a cookie, a subprotocol, or a first
⭐        message — not `Authorization` (Day 116).
```

```python
async def lifespan_app(scope, receive, send):
    assert scope["type"] == "lifespan"
    while True:
        message = await receive()
        if message["type"] == "lifespan.startup":
            try:
                app.state.pool = await create_pool()             # ⭐⭐ ONCE, at boot
            except Exception as e:
                await send({"type": "lifespan.startup.failed", "message": str(e)})
                return                                            # ⭐ the server refuses to start
            await send({"type": "lifespan.startup.complete"})
        elif message["type"] == "lifespan.shutdown":
            await app.state.pool.close()                          # ⭐⭐ drain (Day 081)
            await send({"type": "lifespan.shutdown.complete"})
            return
```

```
⭐⭐ LIFESPAN IS THE UNDERRATED HALF OF ASGI, AND IT MATTERS FOR TWO REASONS:
⭐  1. ⭐⭐ FAIL FAST. A bad database URL kills STARTUP rather than the first
⭐       request at 3 a.m. ⭐ Day 090's "a misconfigured process should die on
⭐       boot" is only implementable because this hook exists.
⭐  2. ⭐⭐ GRACEFUL SHUTDOWN (Day 081) HAS SOMEWHERE TO ATTACH: on SIGTERM the
⭐       server stops accepting, finishes in-flight requests, then fires
⭐       `lifespan.shutdown` so you can close the pool and flush. ⭐ Under WSGI
⭐       there is no such moment, which is why connections leak on redeploy.
```

# Part 4 — ⭐ ASGI middleware, and the wrapping trap

```python
def timing_middleware(app):
    async def middleware(scope, receive, send):
        if scope["type"] != "http":                # ⭐⭐ PASS THROUGH lifespan and websocket
            return await app(scope, receive, send)
        start = time.perf_counter()

        async def send_wrapper(message):           # ⭐⭐ wrap SEND to touch headers
            if message["type"] == "http.response.start":
                elapsed = (time.perf_counter() - start) * 1000
                message["headers"].append((b"x-response-time",
                                           f"{elapsed:.1f}ms".encode()))
            await send(message)

        await app(scope, receive, send_wrapper)
    return middleware
```

```
⭐⭐ TWO TRAPS, AND BOTH ARE COMMON IN REAL CODEBASES:
⭐
⭐  1. ⭐⭐ FORGETTING TO PASS THROUGH NON-HTTP SCOPES. A middleware that assumes
⭐       `scope["type"] == "http"` and mishandles `lifespan` ⇒ ⭐⭐ THE SERVER
⭐       HANGS AT STARTUP waiting for a `startup.complete` that never comes.
⭐       ⭐ The symptom — "uvicorn starts and then nothing" — looks nothing like
⭐       the cause.
⭐
⭐  2. ⭐⭐ CONSUMING `receive` WITHOUT REPLAYING IT (Day 108, now concrete). A
⭐       middleware that reads the body to log it must hand downstream a
⭐       `receive` that replays the buffered messages:
⭐
⭐         body = b""
⭐         while True:
⭐             m = await receive()
⭐             body += m.get("body", b"")
⭐             if not m.get("more_body"): break
⭐         async def replay():
⭐             return {"type": "http.request", "body": body, "more_body": False}
⭐         await app(scope, replay, send)
⭐       ⇒ ⚠️ ⭐ and you now hold the whole body in memory ⇒ cap it, and exempt
⭐         upload routes.
```

⭐ **`scope["state"]`** is the sanctioned per-connection scratch space for middleware to pass values
down — the ASGI equivalent of Day 108's `request.state`.

# Part 5 — ⭐⭐ The rule that has not changed

```
⭐⭐ ASGI GIVES YOU CONCURRENCY FOR WAITING AND NOTHING ELSE. DAY 072'S RULE IS
⭐   UNCHANGED AT THE PROTOCOL LEVEL, AND DAY 106 SHOWED YOU THE MECHANISM:
⭐
⭐   async def app(scope, receive, send):
⭐       rows = db.query("SELECT ...")      # ⚠️⚠️ ⭐⭐ A SYNCHRONOUS DRIVER
⭐   ⇒ ⭐⭐ THE EVENT LOOP IS BLOCKED ⇒ EVERY OTHER CONNECTION THIS WORKER OWNS
⭐        IS FROZEN, including the ones that are only waiting.
⭐   ⇒ ⭐ FIXES, in order of preference: an async driver (asyncpg, httpx) ·
⭐        `await asyncio.to_thread(...)` for a sync call you cannot replace ·
⭐        ⭐⭐ or use WSGI and threads, which is a legitimate answer (Day 109).
⭐
⭐ ⭐⭐ AND THE HONEST SUMMARY OF ASGI vs WSGI, WHICH IS NOT "ASGI IS BETTER":
⭐   ASGI is strictly MORE CAPABLE and strictly EASIER TO GET WRONG. ⭐ A sync
⭐   WSGI worker cannot commit the blocking-call catastrophe; an ASGI worker can,
⭐   and one library call does it. ⭐⭐ Choose ASGI when you need WebSockets, SSE
⭐   at scale, or high-concurrency I/O — and then take the async discipline
⭐   seriously, because it is not optional.
```

| ⭐ Feature | ⭐ WSGI | ⭐ ASGI |
|---|---|---|
| Headers | ⚠️ lossy flat dict | ⭐⭐ list of byte pairs — duplicates survive |
| Body | ⭐ a file-like object | ⭐ messages with `more_body` |
| WebSockets | ⭐ impossible | ⭐⭐ same protocol |
| Startup/shutdown | ⭐ none | ⭐⭐ `lifespan` |
| ⭐⭐ Blocking call | ⭐ costs one worker | ⭐⭐ **costs every connection on the worker** |
| Servers | gunicorn (sync/gthread) | ⭐ uvicorn, hypercorn, daphne |

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Headers as a dict of `str` | ⭐⭐ A list of `(bytes, bytes)` — lowercase, duplicates preserved. |
| One `receive()` for the body | ⭐ Loop until `more_body` is false. |
| Changing the status after `response.start` | ⭐⭐ It is already sent. Validate first (Day 105). |
| ⭐ Ignoring `http.disconnect` | ⭐ You generate a 2 GB export for a closed tab. |
| ⭐⭐ **Middleware not passing through `lifespan`** | ⭐⭐ The server hangs at startup, with an unrelated-looking symptom. |
| Consuming `receive` without replay | ⭐⭐ The handler sees an empty body. |
| ⭐ Buffering the body with no cap | ⭐ You re-created Day 104's memory problem. |
| Building the pool on first request | ⭐⭐ That is what `lifespan.startup` is for — fail at boot. |
| ⭐ Expecting `Authorization` on a WebSocket | ⭐ Browsers cannot set it. Cookie, subprotocol, or first message. |
| Accepting a WebSocket before authenticating | ⭐ Authenticate on `connect`, then accept. |
| ⭐⭐ **A sync driver in an ASGI app** | ⭐⭐ Freezes every connection the worker owns. |

## Interview questions

**Q: What is ASGI?**
> An async callable taking three things: `scope`, a dict describing the connection and constant for
> its lifetime; `receive`, which you await for the next inbound message; and `send`, for outbound
> messages. The key difference from WSGI is that it's a coroutine that lives as long as the
> connection, with an inbox and an outbox it can use in any order and any number of times — rather
> than one call in and one return out. That single change gives you streamed bodies, streamed
> responses, WebSockets and lifespan hooks, because all four are just different scope types and
> message names over the same shape.

**Q: How does a body arrive in ASGI?**
> As one or more `http.request` messages, each with a `body` and a `more_body` flag, so you loop until
> `more_body` is false. It's the same framing problem as parsing from a socket, except the server has
> done the parsing and hands you the pieces — which is what makes streamed uploads possible without
> buffering. On the way out it's `http.response.start` with status and headers, then one or more
> `http.response.body` messages. Once you've sent the start message the status is fixed, so anything
> that can fail has to happen before it.

**Q: Why are ASGI headers a list of byte pairs?**
> To fix WSGI's lossy model. `environ` is a flat dict of strings, so duplicate headers get comma-joined
> and the `HTTP_` mangling makes `X-Request-Id` and `X_Request_Id` collide. A list of lowercase byte
> pairs preserves duplicates and exact bytes, which is why `Set-Cookie` needs no special case.

**Q: What is lifespan for, and why does it matter?**
> Startup and shutdown events. Two reasons it matters. It lets you fail fast — a bad database URL
> kills the process at boot rather than surprising one user at 3 a.m. — and that's what makes "build
> settings once at startup" actually enforceable. And it gives graceful shutdown somewhere to attach:
> on SIGTERM the server stops accepting, finishes in-flight requests, then fires `lifespan.shutdown`
> so you can drain the pool and flush. WSGI has no such moment, which is why connections leak on
> every redeploy.

**Q: What's the most common ASGI middleware bug?**
> Not passing through non-HTTP scopes. A middleware that assumes `scope["type"] == "http"` and
> mishandles `lifespan` means the server never receives `startup.complete`, so it hangs at boot — and
> "uvicorn starts and then nothing happens" looks nothing like a middleware bug. The other one is
> consuming `receive` without replaying it: a middleware that reads the body to log or verify it
> leaves the handler with an empty body, and the endpoint reports a missing field on a request that
> obviously had one.

**Q: Is ASGI just better than WSGI?**
> It's strictly more capable and strictly easier to get wrong. A synchronous WSGI worker physically
> cannot commit the blocking-call catastrophe, because blocking is all it does — the cost is one
> worker. An ASGI worker can, and a single synchronous database call freezes every connection that
> worker owns, including the ones only waiting. So I'd choose ASGI for WebSockets, server-sent events
> at scale, or high-concurrency I/O, and then treat the async discipline as non-negotiable rather than
> a preference.
