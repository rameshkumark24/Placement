# Day 122

**L-122** · ⭐⭐ **Idempotency keys** — making a retried `POST` safe, end to end

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the client cannot tell a lost response from a failed request, so it will
> retry — and an idempotency key is the mechanism that lets the server recognise "I have already done
> this" and return the *original* answer rather than doing it again.**
>
> ⭐ Day 102 established that something always retries. **Today is the implementation**, and the two
> hard parts are the concurrent duplicate and deciding what counts as "the same request".

---

# Part 1 — ⭐ The failure it fixes

```
⭐⭐ THE SEQUENCE, WHICH HAPPENS EVERY DAY IN EVERY PAYMENT SYSTEM:
⭐   1. client POSTs /charges       ⇒ the server charges the card ✔
⭐   2. ⭐ the response is lost — a timeout, a dropped connection, a proxy hiccup
⭐   3. ⭐⭐ THE CLIENT SEES A TIMEOUT AND CANNOT DISTINGUISH:
⭐          (a) the request never arrived        ⇒ retrying is REQUIRED
⭐          (b) it arrived and the reply was lost ⇒ retrying is a DOUBLE CHARGE
⭐   4. ⭐ the client retries — because not retrying loses real orders
⭐   ⇒ ⭐⭐ SO SOMEBODY IS CHARGED TWICE, AND NO COMPONENT INVOLVED HAS A BUG.
⭐
⭐ ⇒ ⭐⭐ AND IT IS NOT ONLY THE CLIENT: a load balancer retries, a queue
⭐     redelivers, a user double-clicks, a mobile app resends on reconnect.
⭐     ⭐ You cannot remove retries. You can only make them safe.
```

```http
POST /charges
Idempotency-Key: 01J7ZK3M8QF4T6...          ⭐⭐ chosen by the CLIENT, once per intent
Content-Type: application/json

{"amount": "50.00", "currency": "GBP", "card": "tok_..."}
```

⭐⭐ **The key identifies the *intent*, not the attempt.** ⭐ The client generates it once when the
user presses the button and reuses it for **every retry of that same action** — so a fresh key on each
retry defeats the entire mechanism, and that is the most common client-side mistake.

# Part 2 — ⭐⭐ The server side

```python
def idempotent(handler):
    def wrapped(request, user):
        key = request.headers.get("idempotency-key")
        if key is None:
            return handler(request, user)                  # ⭐ or 400, if you require it

        fingerprint = sha256(request.body).hexdigest()      # ⭐⭐ Part 3
        scope = f"idem:{user.id}:{request.path}:{key}"      # ⭐⭐ scoped — see below

        record = store.get(scope)
        if record is not None:
            if record.fingerprint != fingerprint:
                raise HTTPError(422, "idempotency key reused with a different body")
            if record.status == "in_progress":
                raise HTTPError(409, "request already in progress",   # ⭐ Part 4
                                headers=[("Retry-After", "1")])
            return replay(record.response)                  # ⭐⭐ THE ORIGINAL RESPONSE

        if not store.claim(scope, fingerprint, ttl=24 * 3600):   # ⭐⭐ ATOMIC — Part 4
            raise HTTPError(409, "request already in progress")

        try:
            response = handler(request, user)
        except Exception:
            store.release(scope)                            # ⭐⭐ let a genuine retry through
            raise
        store.complete(scope, response)
        return response
    return wrapped
```

```
⭐⭐ THREE DESIGN POINTS IN THAT CODE:
⭐  1. ⭐⭐ SCOPE THE KEY BY USER **AND** ENDPOINT. A global key namespace means
⭐       one customer's key can collide with another's — ⭐ so user B sends a key
⭐       that happens to match and receives USER A'S RESPONSE. ⭐⭐ That is an
⭐       IDOR (Day 118) delivered through your idempotency layer.
⭐  2. ⭐⭐ RELEASE THE CLAIM ON FAILURE. If the handler raised a 500, the
⭐       operation did NOT happen, so a retry must be allowed to try again. ⭐ A
⭐       naive implementation that stores "in progress" forever turns one
⭐       transient failure into a permanently poisoned key.
⭐  3. ⭐ TTL of 24 hours (Stripe uses 24h). ⭐⭐ Long enough to cover any sane
⭐       retry window, short enough that the store does not grow forever.
```

⭐⭐ **What you store is the whole response — status, headers and body** — because a replay must be
*indistinguishable* from the original. ⭐ Returning `200 {"already_done": true}` is not idempotency; it
is a different response that the client now has to handle separately, which defeats the point.

# Part 3 — ⭐ Same key, different body

```
⭐⭐ WHAT IF A CLIENT SENDS THE SAME KEY WITH A DIFFERENT PAYLOAD?
⭐   · charge £50 with key K  ⇒ ✔
⭐   · charge £5,000 with key K ⇒ ⭐⭐ IF YOU REPLAY, YOU SILENTLY IGNORE A REAL
⭐        REQUEST AND TELL THEM IT SUCCEEDED. The £5,000 never happens and the
⭐        client believes it did.
⭐   ⇒ ⭐⭐ SO: FINGERPRINT THE REQUEST (hash the body, and the path) AND STORE
⭐        IT WITH THE KEY. A mismatch is a 422 — ⭐ it is a client bug, and
⭐        telling them loudly is far kinder than quietly discarding money.
⭐   ⇒ ⭐ hash the RAW BODY, before parsing, so key ordering and whitespace do
⭐        not matter... ⚠️ ⭐⭐ which also means a client that re-serialises its
⭐        JSON differently on retry gets a spurious 422. ⭐ Hash the PARSED,
⭐        canonicalised payload if your clients are not byte-stable.
```

```
⭐⭐ IDEMPOTENCY IS NOT CACHING, AND THE DIFFERENCE MATTERS:
⭐   A CACHE serves a stored response to ANYONE asking the same question, and it
⭐     is an optimisation — ⭐ correctness does not depend on it.
⭐   ⭐⭐ AN IDEMPOTENCY RECORD serves a stored response ONLY to the SAME CLIENT
⭐     REPEATING THE SAME INTENT, and ⭐⭐ CORRECTNESS DEPENDS ON IT — its job is
⭐     to prevent a second side effect, not to save work.
⭐   ⇒ ⭐ hence: scoped per user, keyed on an explicit client-supplied token,
⭐        short TTL, and it applies to WRITES — the opposite of a cache in every
⭐        respect (Day 124).
```

# Part 4 — ⭐⭐ The concurrent duplicate

```
⚠️⚠️ ⭐⭐ THE CASE A NAIVE "CHECK THEN INSERT" MISSES ENTIRELY: two identical
⭐    requests arrive AT THE SAME MOMENT, on two different workers.
⭐
⭐    worker A: store.get(K) ⇒ None          ⭐ nothing recorded yet
⭐    worker B: store.get(K) ⇒ None          ⭐⭐ ALSO nothing — A has not finished
⭐    worker A: charge the card ✔
⭐    worker B: charge the card ✔            ⭐⭐ DOUBLE CHARGE, DESPITE THE KEY
⭐
⭐    ⇒ ⭐⭐ THIS IS DAY 067'S RACE, ACROSS PROCESSES. The check and the claim
⭐         must be ONE ATOMIC OPERATION.
⭐    ⇒ ⭐⭐ REDIS:    SET key value NX EX 86400   ⇒ ⭐ "set if not exists",
⭐         atomic; the loser gets False and returns 409.
⭐    ⇒ ⭐⭐ POSTGRES: a UNIQUE constraint on the key and `INSERT … ON CONFLICT
⭐         DO NOTHING` ⇒ ⭐ the loser inserts zero rows. ⭐⭐ The database is doing
⭐         the compare-and-swap for you (Days 088, 102 — the same pattern again).
⭐    ⇒ ⭐ the loser returns 409 with `Retry-After: 1`, and the client retries
⭐         into the completed record a second later.
```

```
⭐⭐ AND THE DEEPER GUARANTEE — THE IDEMPOTENCY RECORD AND THE SIDE EFFECT MUST
⭐   AGREE. If you charge the card and then crash before storing the record, the
⭐   retry charges again.
⭐   ⇒ ⭐ IF THE SIDE EFFECT IS IN YOUR OWN DATABASE: write the record and the
⭐        row IN THE SAME TRANSACTION. ⭐⭐ Then they cannot disagree, and this is
⭐        the clean case.
⭐   ⇒ ⭐⭐ IF THE SIDE EFFECT IS EXTERNAL (a payment gateway), YOU CANNOT HAVE
⭐        ATOMICITY ACROSS TWO SYSTEMS. ⭐ So: write "in progress" WITH the
⭐        gateway's own idempotency key BEFORE calling, and reconcile afterwards.
⭐        ⭐⭐ Every serious payment API accepts an idempotency key precisely so
⭐        you can push the guarantee down to the system that owns the money.
⭐   ⇒ ⭐ this is Stage 9's distributed-transaction problem in miniature, and it
⭐        is worth recognising it as such.
```

# Part 5 — ⭐ Where it belongs, and what else buys it

```
⭐⭐ APPLY IT TO ANY ENDPOINT WITH A NON-IDEMPOTENT SIDE EFFECT:
⭐   ✔ payments, refunds, transfers      ✔ sending an email or an SMS
⭐   ✔ creating an order or a user       ✔ publishing to a queue
⭐   ✘ ⭐ GET, PUT, DELETE — ⭐⭐ already idempotent by definition (Day 102);
⭐       adding a key buys nothing.
⭐
⭐ ⭐⭐ AND THE CHEAPER ALTERNATIVES, WHICH ARE OFTEN BETTER:
⭐  1. ⭐⭐ A NATURAL UNIQUE CONSTRAINT. `UNIQUE(user_id, order_reference)` makes
⭐       the DUPLICATE IMPOSSIBLE rather than detected. ⭐ If your domain has a
⭐       natural key, use it — ⭐⭐ it is stronger, because it holds even for
⭐       writes that never went through your API.
⭐  2. ⭐ PUT WITH A CLIENT-CHOSEN ID (Day 102) — idempotent by construction,
⭐       no extra machinery.
⭐  3. ⭐ A STATE MACHINE: "only a PENDING order may be paid" ⇒ ⭐⭐ the second
⭐       attempt fails a state check rather than duplicating.
⭐   ⇒ ⭐⭐ REACH FOR AN IDEMPOTENCY KEY WHEN THERE IS NO NATURAL KEY AND THE
⭐        CLIENT MUST CHOOSE THE IDENTITY OF THE INTENT. ⭐ It is machinery;
⭐        prefer a constraint when one exists.
```

⭐ **Document it.** ⭐⭐ Clients must know the header name, that the key is per-intent and reused on
retry, the TTL, and what a `409` and a `422` mean — **an idempotency scheme nobody knows about is a
scheme nobody uses.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ A new key on each retry | ⭐⭐ The key identifies the **intent**. A fresh key defeats the whole mechanism. |
| ⭐⭐ **Check-then-insert** | ⭐⭐ Two workers both see "nothing" and both charge. Atomic claim: `SET NX` or `ON CONFLICT`. |
| ⭐ A global key namespace | ⭐⭐ Cross-user collision returns someone else's response — IDOR via idempotency. |
| Not fingerprinting the body | ⭐⭐ Same key, different amount ⇒ you silently discard a real request. |
| ⭐ Keeping "in progress" after a 500 | ⭐ A transient failure permanently poisons the key. |
| Returning `{"already_done": true}` | ⭐⭐ A replay must be indistinguishable from the original. |
| ⭐ Storing only the body | ⭐ Store status, headers and body. |
| ⭐⭐ **Record and side effect in different transactions** | ⭐⭐ Crash between them and the retry duplicates. |
| No TTL | ⭐ The store grows forever. |
| Adding keys to `PUT`/`DELETE` | ⭐ Already idempotent. |
| ⭐ Building this when a `UNIQUE` constraint would do | ⭐⭐ A constraint makes duplicates impossible, not merely detected. |
| Not documenting it | ⭐ Clients cannot use what they do not know about. |

## Interview questions

**Q: Why do you need idempotency keys?**
> Because a client can't distinguish a lost response from a failed request. It times out, and the
> request may have succeeded with only the reply lost — so retrying is either required or a double
> charge, and there's no way to tell which. And the client will retry, because not retrying loses real
> orders. So will the load balancer, the queue and the user's second click. You can't remove retries,
> only make them safe. A client-supplied key lets the server recognise a repeat of the same intent and
> replay the original response.

**Q: How do you implement one?**
> The client sends a key identifying the intent — generated once when the button is pressed and reused
> on every retry. The server scopes it by user and endpoint, fingerprints the request body, and
> atomically claims the key. If the claim succeeds it does the work and stores the full response —
> status, headers and body — so a replay is indistinguishable from the original. If the key already
> exists and is complete, it returns the stored response. If it exists with a different fingerprint,
> that's a 422, because the client is reusing a key for a different request and silently discarding it
> would be worse.

**Q: What's the concurrency problem?**
> Check-then-insert. Two identical requests hit two workers at the same instant, both look up the key,
> both see nothing because the first hasn't finished, and both do the work. That's the classic
> read-modify-write race across processes. The fix is making the check and the claim one atomic
> operation — `SET key NX EX` in Redis, or a unique constraint with `INSERT … ON CONFLICT DO NOTHING`
> in Postgres, where the database does the compare-and-swap for you. The loser returns 409 with
> `Retry-After` and picks up the completed record a second later.

**Q: How do you make sure the record and the side effect agree?**
> If the side effect is in my own database, I write the idempotency record and the row in the same
> transaction, so they can't disagree. If it's external — a payment gateway — I can't have atomicity
> across two systems, so I write "in progress" with the gateway's own idempotency key *before* calling
> it and reconcile afterwards. That's why every serious payment API accepts an idempotency key: it
> lets you push the guarantee down to the system that owns the money. It's a distributed-transaction
> problem in miniature.

**Q: When would you not use one?**
> When a natural unique constraint exists. `UNIQUE(user_id, order_reference)` makes the duplicate
> *impossible* rather than detected, and it holds even for writes that never went through my API —
> a migration, a background job, another service. Same for a PUT with a client-chosen id, which is
> idempotent by construction, or a state machine where only a pending order can be paid. Idempotency
> keys are machinery, and I'd reach for them when there's no natural key and the client has to choose
> the identity of the intent.

## 🎙️ Articulation drill

Record two minutes: **"How do you stop a payment endpoint charging twice?"**

⭐ **Start from why it happens without blaming anyone:** **"the client times out and genuinely cannot
tell whether the request never arrived or arrived and the response was lost. Retrying is either
necessary or a double charge, and there's no way to distinguish. And something will retry regardless —
the client library, the load balancer, the queue, the user's second click. So the goal isn't to prevent
retries, it's to make them safe."**

⭐⭐ **Then the mechanism, with the detail that shows implementation:** *"the client generates an
idempotency key once, when the user presses the button, and reuses it for every retry of that intent.
The server scopes it by user and endpoint — a global namespace means one customer's key can collide
with another's and return someone else's response, which is an IDOR through the idempotency layer. It
fingerprints the body, so the same key with a different amount is a 422 rather than silently discarding
a real request. And it stores the whole response, status and headers included, so a replay is
indistinguishable from the original."*

⭐⭐ **Then the concurrency, which is where naive implementations fail:** *"the case that breaks a
naive version is two identical requests arriving simultaneously on two workers. Both check, both see
nothing because the first hasn't finished, and both charge. The check and the claim have to be one
atomic operation — `SET NX` in Redis, or a unique constraint with `ON CONFLICT DO NOTHING`, letting the
database do the compare-and-swap. And the record and the side effect need to agree: same transaction if
the effect is in my database, and if it's an external gateway, I pass *their* idempotency key so the
guarantee lives with the system that owns the money."*

⭐ **Close on the simpler answer:** *"though before building any of that I'd look for a natural unique
constraint. `UNIQUE(user_id, reference)` makes the duplicate impossible rather than detected, and it
holds even for writes that never went through my API. Idempotency keys are for when there's no natural
key and the client has to choose the identity of the intent."*
