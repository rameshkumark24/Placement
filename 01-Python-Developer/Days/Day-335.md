# Day 335 🎯

**P-335** · 🎯 **Delivery semantics** — ⭐⭐ why exactly-once is a lie, and what to build instead

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: exactly-once *delivery* is impossible over an unreliable network, and
> saying so is not pedantry — it is the reason your design must be at-least-once delivery plus
> effectively-once *processing*, and the whole engineering problem is where you put the deduplication
> and whether it commits atomically with the work.**

---

# Part 1 — ⭐⭐ The impossibility, in four lines

```
⭐⭐ THE TWO-GENERALS PROBLEM, IN THE FORM THAT MATTERS:
⭐   ① Producer sends a message. ⭐ The network drops the ack.
⭐   ② ⭐⭐ THE PRODUCER CANNOT DISTINGUISH:
⭐        ⭐ (a) the message was lost, from
⭐        ⭐ (b) the message arrived and the ***ack*** was lost.
⭐   ③ ⭐ If it retries and (b) was true ⇒ ***duplicate***.
⭐   ④ ⭐ If it does not retry and (a) was true ⇒ ***loss***.
⭐   ⇒ ⭐⭐ THERE IS NO THIRD OPTION AND NO PROTOCOL CREATES ONE.
⭐     ⭐ Adding another ack just moves the same question one
⭐     hop further along. ⭐⭐ IT IS THE SAME INFORMATION LIMIT
⭐     AS DAY 330'S PROOF.

⭐⭐ ⇒ ***YOU MUST CHOOSE WHICH FAILURE YOU PREFER.*** And for
⭐   almost everything, ⭐⭐ DUPLICATES ARE PREFERABLE TO LOSS,
⭐   BECAUSE DUPLICATES CAN BE MADE HARMLESS AND LOSS CANNOT BE
⭐   MADE ANYTHING.
```

---

# Part 2 — ⭐ The three semantics, with their real costs

```
⭐⭐ ***AT-MOST-ONCE*** — send once, never retry. Commit before
⭐   processing.
⭐   ⭐ ✔ No duplicates. ✔ Simplest. ✔ Lowest latency.
⭐   ⭐ ✘ ⭐⭐ SILENT LOSS.
⭐   ⇒ ⭐ Legitimate for: metrics samples, presence pings,
⭐     telemetry where one missing point is invisible.
⭐   ⇒ ⭐⭐ AND NOTHING ELSE. If you cannot name why loss is
⭐     acceptable, it is not.

⭐⭐ ***AT-LEAST-ONCE*** — retry until acked. Commit after
⭐   processing.
⭐   ⭐ ✔ No loss. ⭐ ✘ Duplicates.
⭐   ⇒ ⭐⭐ THE DEFAULT FOR EVERYTHING THAT MATTERS, AND THE
⭐     BASIS OF EVERY REAL SYSTEM.

⭐⭐ ***"EXACTLY-ONCE"*** — ⭐⭐ AT-LEAST-ONCE DELIVERY PLUS
⭐   DEDUPLICATION, WEARING A BETTER NAME.
⭐   ⇒ ⭐ It is achievable as a ***processing*** property, never
⭐     as a ***delivery*** property.
⭐   ⇒ ⭐⭐ THE PRECISE TERM IS ***EFFECTIVELY-ONCE***, and using
⭐     it correctly in an interview is a genuine marker.
```

# Part 3 — ⭐⭐ What Kafka's exactly-once actually is

```
⭐⭐ KAFKA GIVES YOU TWO REAL THINGS, AND THEY ARE NARROWER
⭐   THAN THE MARKETING:
⭐   ① ⭐ ***IDEMPOTENT PRODUCER*** (`enable.idempotence=true`)
⭐        ⭐ Each producer gets a PID; each message a sequence
⭐          number per partition. ⭐ The broker rejects
⭐          duplicates from a retry.
⭐        ⇒ ⭐⭐ THIS ELIMINATES DUPLICATES CAUSED BY ***PRODUCER
⭐          RETRIES***. ⭐ It does not eliminate duplicates
⭐          caused by your application publishing twice — ⭐⭐ A
⭐          RESTARTED PROCESS GETS A NEW PID AND ITS
⭐          RE-PUBLISHED MESSAGE IS A NEW MESSAGE.
⭐   ② ⭐ ***TRANSACTIONS*** — atomically write to several
⭐        partitions ***and*** commit consumer offsets.
⭐        ⇒ ⭐⭐ THIS MAKES ***READ-PROCESS-WRITE WITHIN KAFKA***
⭐          ATOMIC. ⭐ Consume from A, produce to B, commit the
⭐          offset — all or nothing.
⭐        ⇒ ⭐ Consumers must set `isolation.level=
⭐          read_committed` or they see aborted messages.

⭐⭐ AND THE BOUNDARY THAT MATTERS MOST:
⭐   ***KAFKA'S TRANSACTION COVERS KAFKA. IT DOES NOT COVER
⭐      YOUR POSTGRES WRITE, YOUR STRIPE CHARGE, OR YOUR
⭐      EMAIL.***
⭐   ⇒ ⭐⭐ THE MOMENT THE SIDE EFFECT LEAVES KAFKA, YOU ARE
⭐     BACK TO AT-LEAST-ONCE AND YOU OWN THE DEDUPLICATION.
⭐   ⇒ ⭐ Which is exactly why the interesting engineering is
⭐     Part 4, not Part 3.
```

# Part 4 — ⭐⭐ Effectively-once, four ways

```
⭐⭐ ① ***NATURALLY IDEMPOTENT OPERATIONS*** — the best answer.
⭐   ⭐ `SET status = 'shipped'` is idempotent.
⭐     `INCREMENT attempts` is not.
⭐   ⭐ `UPDATE … WHERE status = 'pending'` ⇒ ⭐⭐ THE SECOND
⭐     DELIVERY UPDATES ZERO ROWS AND YOU KNOW IT (Day 264's
⭐     rule: ***drive side effects from what the write actually
⭐     changed***).
⭐   ⇒ ⭐⭐ REDESIGNING THE OPERATION TO BE IDEMPOTENT BEATS
⭐     EVERY DEDUPLICATION MECHANISM, BECAUSE IT HAS NO STATE
⭐     TO EXPIRE, LOSE OR OUTGROW.

⭐⭐ ② ***A DEDUPLICATION TABLE, IN THE SAME TRANSACTION.***
⭐   ⭐⭐ THE ATOMICITY IS THE ENTIRE POINT. If you record
⭐     "seen" and do the work in two transactions, you have
⭐     just moved the two-generals problem inside your own
⭐     process.
⭐   ⇒ ⭐ And it needs a retention policy, or it grows forever.

⭐⭐ ③ ***CONDITIONAL WRITES / OPTIMISTIC CONCURRENCY.***
⭐   ⭐ `UPDATE … WHERE version = :expected`. ⭐ Rowcount 0 ⇒
⭐     someone else did it. ⭐ Day 310's shape, again.

⭐⭐ ④ ***AN EXTERNAL IDEMPOTENCY KEY FOR THIRD PARTIES.***
⭐   ⭐ Stripe, PayPal and most payment APIs accept an
⭐     `Idempotency-Key` header. ⭐⭐ PASS A KEY DERIVED FROM
⭐     YOUR DOMAIN — `charge:{order_id}` — NOT A FRESH UUID,
⭐     ⭐ or a retry generates a new key and charges twice.
⭐   ⇒ ⭐⭐ THIS IS THE SINGLE HIGHEST-VALUE LINE OF CODE IN A
⭐     PAYMENT INTEGRATION.
```

```python
# ⭐⭐ ② DONE PROPERLY — ONE TRANSACTION, NOT TWO
async def handle(event: Event, session: AsyncSession) -> None:
    async with session.begin():                     # ⭐⭐ ONE TX
        seen = await session.execute(
            insert(ProcessedEvent)
            .values(event_id=event.id, at=utcnow())
            .on_conflict_do_nothing()               # ⭐ the guard
            .returning(ProcessedEvent.event_id)     # ⭐⭐ DAY 264
        )
        if seen.scalar_one_or_none() is None:
            return                                  # ⭐ duplicate
        await do_the_work(event, session)           # ⭐⭐ SAME TX
# ⭐⭐ IF do_the_work RAISES, THE GUARD ROLLS BACK TOO, SO THE
# ⭐   REDELIVERY IS PROCESSED. ⭐ Two transactions would have
# ⭐   marked it seen and then lost the work — ⭐⭐ WHICH IS
# ⭐   AT-MOST-ONCE, ACCIDENTALLY.
```

# Part 5 — ⭐⭐ The dual-write problem, and the outbox as the answer

```
⭐⭐ THE PROBLEM THAT UNDERLIES ALL OF THIS:
⭐   ⭐ `session.commit()` then `producer.send(...)`.
⭐   ⇒ ⭐⭐ THE PROCESS DIES BETWEEN THEM. THE DATABASE HAS THE
⭐     ORDER; NOBODY EVER HEARS ABOUT IT.
⭐   ⭐ Reverse the order and you publish an order that was
⭐     rolled back. ⭐⭐ BOTH ORDERS ARE WRONG. There is no
⭐     correct ordering of two independent commits.

⭐⭐ THE OUTBOX (Day 263, and this is the day it is proved):
⭐   ① ⭐ Write the business row ***and*** an `outbox` row in
⭐        ***one*** local transaction.
⭐   ② ⭐ A relay polls (or CDC tails the WAL) and publishes.
⭐   ③ ⭐ Marks the outbox row sent — ⭐⭐ AND IF IT CRASHES
⭐        BETWEEN PUBLISH AND MARK, IT PUBLISHES AGAIN.
⭐   ⇒ ⭐⭐ SO THE OUTBOX GIVES ***AT-LEAST-ONCE PUBLISHING***,
⭐     NOT EXACTLY-ONCE — ⭐⭐ AND SAYING THAT PLAINLY IS WHAT
⭐     SEPARATES SOMEONE WHO HAS BUILT ONE FROM SOMEONE WHO HAS
⭐     READ ABOUT IT.
⭐   ⇒ ⭐ The consumer's idempotency (Part 4) closes the loop.
⭐     ⭐⭐ THE TWO HALVES TOGETHER ARE THE WHOLE ANSWER; NEITHER
⭐     IS SUFFICIENT ALONE.

⭐⭐ AND THE MIRROR-IMAGE BUG ON THE CONSUMER SIDE:
⭐   ⭐ Process the message, then commit the offset ⇒ crash
⭐     between ⇒ reprocess. ⭐ Fine, ***if*** idempotent.
⭐   ⭐ ⭐⭐ THE ELEGANT VERSION: STORE THE CONSUMED OFFSET IN
⭐     ***YOUR OWN DATABASE***, IN THE SAME TRANSACTION AS THE
⭐     WORK. ⭐ Then the offset and the effect are atomic by
⭐     construction, and Kafka's offset store becomes a hint.
```

# Part 6 — ⭐ The deduplication window, and why it is finite

```
⭐⭐ YOU CANNOT REMEMBER EVERY MESSAGE FOREVER. ⭐ So every
⭐   dedup scheme has a ***window***, and you must know yours.

⭐⭐ HOW TO SIZE IT — THE HONEST CALCULATION:
⭐   ⭐ ***WINDOW > MAX POSSIBLE REDELIVERY DELAY.***
⭐   ⭐ Which is: retry policy (say 6 attempts, exponential to
⭐     1 h) + DLQ replay time + ⭐⭐ THE TIME A HUMAN MIGHT TAKE
⭐     TO REPLAY A TOPIC AFTER AN INCIDENT.
⭐   ⇒ ⭐ That last term is usually days, ⭐⭐ AND IT IS THE ONE
⭐     PEOPLE FORGET — so a 1-hour dedup window plus a
⭐     three-day replay equals duplicate charges.

⭐⭐ IMPLEMENTATIONS, AND WHEN EACH IS RIGHT:
⭐   ⭐ ***DB TABLE + INDEX ON `created_at`***, deleted by a
⭐     nightly job. ⭐⭐ THE DEFAULT — durable, queryable,
⭐     transactional with the work.
⭐   ⭐ ***REDIS `SET NX EX`*** — fast, ⭐⭐ AND NOT
⭐     TRANSACTIONAL WITH YOUR DATABASE, so a crash between the
⭐     two loses the work. ⭐ Fine for suppressing duplicate
⭐     ***notifications***, wrong for money.
⭐   ⭐ ***A UNIQUE CONSTRAINT ON A NATURAL KEY*** —
⭐     ⭐⭐ THE BEST OF ALL, BECAUSE THE DEDUP TABLE ***IS***
⭐     THE DATA. `UNIQUE(order_id, charge_attempt)` needs no
⭐     window and no cleanup at all.
⭐   ⭐ ***BLOOM FILTER*** — for enormous volume where a rare
⭐     false positive (dropping a legitimate message) is
⭐     acceptable. ⭐ Rarely is.
```

# Part 7 — ⭐ Saying it well, and the honest system statement

```
⭐⭐ THE ANSWER THAT SCORES, IN FIVE BEATS:
⭐   ① ⭐⭐ "EXACTLY-ONCE ***DELIVERY*** IS IMPOSSIBLE — the
⭐      sender can't distinguish a lost message from a lost
⭐      ack."
⭐   ② ⭐ "So I choose at-least-once delivery, because
⭐      duplicates can be made harmless and loss cannot."
⭐   ③ ⭐⭐ "AND I MAKE ***PROCESSING*** EFFECTIVELY-ONCE" — by
⭐      idempotent operations first, then a dedup guard in the
⭐      same transaction as the work.
⭐   ④ ⭐ "The publish side is the outbox, which is also
⭐      at-least-once — the two halves together are the
⭐      guarantee."
⭐   ⑤ ⭐⭐ "AND THE DEDUP WINDOW MUST EXCEED THE LONGEST
⭐      REDELIVERY PATH, WHICH INCLUDES A HUMAN REPLAYING A
⭐      TOPIC DAYS LATER."

⭐⭐ AND THE END-TO-END POINT WORTH MAKING LAST:
⭐   ***THE USER'S RETRY IS PART OF THE SYSTEM.*** ⭐ A
⭐   double-clicked button, a refreshed checkout page, a mobile
⭐   client retrying on a flaky connection — ⭐⭐ THESE PRODUCE
⭐   DUPLICATES THAT NO BROKER CONFIGURATION ANYWHERE CAN
⭐   PREVENT. ⭐ Which is why the idempotency key starts at the
⭐   HTTP boundary (Day 260), not at the queue.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Claiming exactly-once delivery | Impossible over an unreliable network. The claim itself signals inexperience |
| ⭐⭐ Believing Kafka transactions cover your database | They cover Kafka. The moment a side effect leaves, you own the dedup |
| ⭐⭐ Marking "seen" in a separate transaction from the work | You just built at-most-once by accident |
| ⭐ Using at-most-once without naming why loss is fine | If you can't justify losing it, you can't lose it |
| ⭐⭐ A fresh UUID as the third-party idempotency key | The retry gets a new key and charges twice. Derive it from the domain |
| ⭐ Assuming the outbox gives exactly-once | It gives at-least-once publishing. The consumer's dedup closes the loop |
| ⭐⭐ A dedup window shorter than the replay path | An incident replay days later re-executes everything |
| ⭐ Redis dedup for money | Not transactional with your database. Fine for notifications, wrong for charges |
| ⭐ Idempotency starting at the queue | The user's double-click already made a duplicate. It starts at the HTTP boundary |
| ⭐⭐ Incrementing counters in a consumer | `INCREMENT` is the canonical non-idempotent operation |
| ⭐ Forgetting `isolation.level=read_committed` | Consumers see aborted transactional messages |

## Interview questions

**1. "Can you guarantee exactly-once?"**
> ⭐⭐ Not delivery — **the sender cannot distinguish a lost message from a lost acknowledgement**, so
> it must either risk a duplicate or risk a loss, and no protocol creates a third option. ⭐ What I can
> guarantee is **effectively-once processing**: at-least-once delivery, because duplicates can be made
> harmless and loss can't, plus deduplication or naturally idempotent operations on the consumer side.

**2. "What does Kafka's exactly-once actually give you?"**
> ⭐ Two narrower things. The idempotent producer removes duplicates caused by **producer retries**
> using a PID and per-partition sequence numbers — ⭐⭐ but a restarted process gets a new PID, so an
> application that publishes twice still publishes twice. ⭐ And transactions make read-process-write
> **within Kafka** atomic, including offset commits. ⭐⭐ Neither covers my Postgres write or my Stripe
> charge, and that boundary is where the real engineering is.

**3. "How do you make a consumer idempotent?"**
> ⭐ First choice: make the operation naturally idempotent — `UPDATE … WHERE status = 'pending'` and
> drive the side effect from the rowcount, so the second delivery changes nothing and I know it.
> ⭐⭐ Otherwise a dedup guard **in the same transaction as the work** — an `ON CONFLICT DO NOTHING`
> insert with `RETURNING`, so if the work fails the guard rolls back too. ⭐ Two transactions would
> mark it seen and lose the work, which is at-most-once by accident.

**4. "Explain the dual-write problem."**
> ⭐ Commit the database then publish, and a crash between them means the order exists and nobody hears.
> Publish then commit, and you announce an order that rolled back. ⭐⭐ **There is no correct ordering
> of two independent commits.** ⭐ The outbox fixes it: business row and outbox row in one local
> transaction, a relay publishes and marks. ⭐⭐ And I'd say plainly that the outbox gives
> **at-least-once publishing, not exactly-once** — the consumer's idempotency is the other half, and
> neither half is sufficient alone.

**5. "How long do you keep deduplication records?"**
> ⭐ Longer than the longest possible redelivery path: the retry policy, plus DLQ replay, ⭐⭐ **plus
> the days a human might take to replay a topic after an incident** — that's the term people forget,
> and a one-hour window against a three-day replay means duplicate charges. ⭐ Best of all is a unique
> constraint on a natural key, because then the dedup table *is* the data and there's no window and no
> cleanup.

**6. "Where does idempotency start?"**
> ⭐⭐ At the HTTP boundary, not the queue — **the user's double-click, refreshed checkout page and
> retrying mobile client produce duplicates no broker setting can prevent.** ⭐ So the client sends an
> idempotency key, the API stores it with the result, and the same key returns the same response. ⭐ For
> third parties I derive the key from the domain — `charge:{order_id}` — never a fresh UUID, or the
> retry charges twice.

## 🎙️ Articulation drill

**Two minutes.** Start with the impossibility and be precise, because precision is the point:
**exactly-once delivery cannot exist, because the sender can't distinguish a lost message from a lost
acknowledgement** — retry and you may duplicate, don't and you may lose, and adding another ack just
moves the same question one hop. So choose: **duplicates, because duplicates can be made harmless and
loss cannot be made anything.** Then correct the vocabulary — **what's achievable is effectively-once
processing, not exactly-once delivery** — and say what Kafka really gives: an idempotent producer that
removes duplicates from producer retries, and transactions that make read-process-write atomic **within
Kafka**, which stops at your database. Then the engineering: idempotent operations first, because
redesigning the operation beats every dedup mechanism and has no state to expire; ⭐ otherwise **a dedup
guard in the same transaction as the work, because two transactions is at-most-once by accident.** Give
the dual-write problem and the outbox, and be honest about it: **the outbox is at-least-once publishing,
and the consumer's idempotency is the other half — neither is sufficient alone.** Close on the window —
**it must exceed the longest redelivery path, including a human replaying a topic three days after an
incident** — and on where this really starts: **the user's double-click, which no broker configuration
anywhere can prevent.**
