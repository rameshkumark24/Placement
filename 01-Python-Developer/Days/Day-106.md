# Day 106

**L-106** · ⭐⭐ **Concurrency for your server** — threads, a pool, and `selectors`: the day you build asyncio's engine by hand

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: your server handles one client at a time because `accept()` and `recv()`
> block — and there are exactly three ways out of that, which are threads, processes, and asking the
> kernel which sockets are ready. Everything else, `asyncio` included, is one of those three with
> better ergonomics.**
>
> ⭐ Day 016 said `asyncio` is `epoll` plus a loop. **Today you write that loop**, and the reason
> `async`/`await` exists becomes something you have felt rather than been told.

# Part 1 — ⭐ The problem, demonstrated

```python
def handle(request):
    time.sleep(2)                       # ⭐ stand-in for a database query
    return build_response(200, [], b"done")
```

```bash
$ time curl localhost:8000/ & time curl localhost:8000/ & wait
# ⭐ first:  2.0s
# ⭐⭐ second: 4.0s   ← it waited for the first to finish ENTIRELY
```

```
⭐⭐ WHY: THE ACCEPT LOOP IS SEQUENTIAL.
⭐   accept() → handle() → sendall() → back to accept()
⭐   ⇒ ⭐⭐ WHILE handle() IS RUNNING, NOBODY IS CALLING accept(). ⭐ New clients
⭐        sit in the kernel's backlog queue (Day 103) until it fills, and then
⭐        they are refused.
⭐   ⇒ ⭐⭐ AND NOTE: THOSE TWO SECONDS ARE SPENT WAITING, NOT COMPUTING. The CPU
⭐        is idle. ⭐ That is the whole opportunity, and it is why this is an
⭐        I/O-bound problem (Day 064) with three different solutions.
```

# Part 2 — ⭐ Thread per connection

```python
import threading

while True:
    conn, addr = server.accept()
    t = threading.Thread(target=handle_connection, args=(conn,), daemon=True)
    t.start()                                # ⭐⭐ back to accept() immediately
```

```
⭐⭐ IT WORKS, AND THE GIL IS NOT THE PROBLEM HERE (Day 065): recv, send and any
⭐   database driver RELEASE THE GIL while waiting on a syscall. ⭐ A hundred
⭐   threads blocked in recv use no CPU and genuinely overlap.
⭐
⭐ ⭐ WHERE IT BREAKS, IN ORDER OF WHICH BITES FIRST:
⭐   · ⭐⭐ MEMORY — ~8 MB of virtual stack per thread; ⭐ a few thousand threads
⭐        is real memory and real scheduler pressure.
⭐   · ⭐⭐ UNBOUNDED. One thread PER CONNECTION means an attacker chooses how
⭐        many threads you create ⇒ ⭐⭐ slowloris (Day 103) now exhausts THREADS
⭐        as well as sockets. ⭐ This is the decisive flaw, not the memory.
⭐   · context switching at high counts
⭐   · ⭐ shared state between threads is now YOUR problem (Days 066, 067)
⭐   ⇒ ⭐ fine to a few hundred concurrent connections. ⭐⭐ Not fine when the
⭐        connection count is chosen by strangers.
```

# Part 3 — ⭐⭐ A bounded thread pool

```python
from concurrent.futures import ThreadPoolExecutor       # ⭐ Day 069

with ThreadPoolExecutor(max_workers=32) as pool:
    while True:
        conn, addr = server.accept()
        pool.submit(handle_connection, conn)            # ⭐⭐ QUEUED if all 32 are busy
```

```
⭐⭐ ONE LINE, AND THE PROPERTY THAT MATTERS IS THE BOUND: MEMORY AND THREAD
⭐   COUNT ARE NOW YOURS TO CHOOSE, NOT THE ATTACKER'S.
⭐   ⇒ ⭐⭐ AND THE COST IS HEAD-OF-LINE BLOCKING: 32 slow requests occupy every
⭐        worker, and the 33rd client waits in the queue even if its request
⭐        would take a millisecond. ⭐ Under overload, latency for everyone
⭐        rises together.
⭐   ⇒ ⭐⭐ THAT IS THE CORRECT TRADE, and it is worth being able to say why:
⭐        BOUNDED DEGRADATION BEATS UNBOUNDED COLLAPSE. A queue that grows is
⭐        recoverable; a process that is OOM-killed is not.
⭐   ⇒ ⚠️ ⭐ BUT AN UNBOUNDED QUEUE JUST MOVES THE PROBLEM — memory grows, and
⭐        clients wait past their own timeouts for a response nobody wants
⭐        any more. ⭐⭐ SHED LOAD INSTEAD: cap the queue and return 503 with
⭐        Retry-After (Day 102). ⭐ Refusing fast is kinder than accepting slowly.
```

⭐ **This is what a WSGI server does** (Day 109): Gunicorn's `gthread` worker is exactly this shape —
a bounded pool per worker process, several worker processes, one listening socket shared via
`SO_REUSEPORT` (Day 103).

# Part 4 — ⭐⭐ `selectors` — one thread, thousands of connections

```python
import selectors, socket

sel = selectors.DefaultSelector()          # ⭐⭐ epoll on Linux, kqueue on BSD (Day 016)
server.setblocking(False)
sel.register(server, selectors.EVENT_READ, data=None)

conns: dict[socket.socket, ConnState] = {}

while True:
    events = sel.select(timeout=1)                     # ⭐⭐ BLOCKS UNTIL SOMETHING IS READY
    for key, mask in events:
        sock = key.fileobj
        if sock is server:                             # ⭐ a new client
            conn, addr = server.accept()
            conn.setblocking(False)
            conns[conn] = ConnState()
            sel.register(conn, selectors.EVENT_READ)
        else:                                          # ⭐ an existing client has data
            state = conns[sock]
            data = sock.recv(4096)                     # ⭐⭐ CANNOT BLOCK — it is READY
            if not data:
                sel.unregister(sock); sock.close(); del conns[sock]
                continue
            state.buf += data
            if state.has_complete_request():           # ⭐⭐ ← and here is the problem
                response = handle(state.take_request())
                sock.sendall(response)                 # ⚠️ see below
```

```
⭐⭐ THIS IS THE ENTIRE ARCHITECTURE OF asyncio, nginx, Node and Redis, and you
⭐   have just written it:
⭐   ONE THREAD · NON-BLOCKING SOCKETS · A CALL THAT SLEEPS UNTIL THE KERNEL SAYS
⭐   SOMETHING IS READY · A DISPATCH LOOP · AND PER-CONNECTION STATE HELD IN A DICT.
⭐   ⇒ ⭐⭐ 10,000 IDLE CONNECTIONS COST ONE DICT ENTRY AND ONE KERNEL REGISTRATION
⭐        EACH — no thread, no stack, ⭐ kilobytes rather than megabytes.
⭐   ⇒ ⭐⭐ AND NOW DAY 070'S SENTENCE IS SOMETHING YOU HAVE BUILT: "the loop is a
⭐        while-loop that spends its life inside select()".
```

```
⚠️⚠️ ⭐⭐ AND HERE IS WHY YOU DO NOT WANT TO WRITE SERVERS THIS WAY — THE TWO
⭐    PROBLEMS THAT MOTIVATE async/await ENTIRELY:
⭐
⭐  1. ⭐⭐ EVERY BLOCKING CALL IS BANNED. `handle()` doing a database query, or
⭐       `sock.sendall()` on a slow client, ⭐⭐ STOPS ALL 10,000 CONNECTIONS,
⭐       because there is one thread and it is inside your function.
⭐       ⇒ ⭐⭐ THIS IS DAY 072, ARRIVED AT FROM UNDERNEATH: the blocking call in
⭐         an `async def` is catastrophic for exactly this reason, and you can
⭐         now see the mechanism rather than recall the rule.
⭐
⭐  2. ⭐⭐ YOU MUST HAND-WRITE A STATE MACHINE. You cannot "read the headers,
⭐       then read the body" as a sequence — ⭐ each recv returns whenever the
⭐       kernel feels like it, so every connection needs an explicit state
⭐       (`READING_HEADERS`, `READING_BODY`, `WRITING`) and a partial buffer, and
⭐       your straight-line logic from Day 104 becomes a transition table.
⭐       ⇒ ⭐⭐ THAT IS THE PROBLEM async/await SOLVES, AND IT IS THE ONLY ONE:
⭐         `await` LETS YOU WRITE THE SEQUENTIAL VERSION AND HAVE THE COMPILER
⭐         BUILD THE STATE MACHINE FOR YOU. ⭐ The coroutine's suspended frame
⭐         IS the per-connection state (Day 048's generators).
⭐       ⇒ ⭐⭐ SO async IS NOT "FASTER THAN THREADS". IT IS THE SAME selectors
⭐         LOOP, WITH THE STATE MACHINE GENERATED RATHER THAN HAND-WRITTEN.
```

# Part 5 — ⭐ Choosing, and the fourth option

| Model | ⭐ Concurrency | ⭐ Memory/conn | ⭐ Fails when |
|---|---|---|---|
| Sequential | 1 | — | ⭐ immediately |
| ⭐ Thread per conn | ~hundreds | ⭐⭐ MBs | ⭐⭐ the client count is attacker-chosen |
| ⭐⭐ **Thread pool** | pool size | ⭐ MBs × pool | ⭐ head-of-line blocking under overload |
| ⭐ Process pool | cores | ⭐⭐ MBs × procs | ⭐ the same, plus IPC cost |
| ⭐⭐ **`selectors` / async** | ⭐⭐ thousands | ⭐⭐ **KBs** | ⭐⭐ **any blocking call** |

```
⭐⭐ THE FOURTH OPTION, AND IT IS WHAT PRODUCTION ACTUALLY DOES:
⭐   PROCESSES × THREADS, or PROCESSES × EVENT LOOPS.
⭐   ⇒ ⭐ N worker PROCESSES (one per core — Day 065's GIL means one process
⭐        cannot use more than one core for Python bytecode), each running
⭐        either a thread pool or an event loop, ⭐⭐ all sharing ONE listening
⭐        socket via SO_REUSEPORT so the kernel load-balances accepts.
⭐   ⇒ ⭐⭐ THAT IS EXACTLY gunicorn -w 4 -k uvicorn.workers.UvicornWorker
⭐        (Day 111): four processes for the cores, an event loop inside each
⭐        for the waiting. ⭐ Nothing else.
⭐
⭐ ⭐⭐ AND THE DECISION RULE, WHICH IS DAY 064'S, UNCHANGED:
⭐   MOSTLY WAITING ⇒ event loop (or threads). MOSTLY COMPUTING ⇒ processes.
⭐   ⭐ A web server is mostly waiting, which is why every one of them is
⭐   built this way.
```

```
⭐⭐ AND THE PART THAT IS NOT ABOUT MODELS AT ALL — LIMITS, IN EVERY MODEL:
⭐   · ⭐ a read timeout per connection            (Day 103 — slowloris)
⭐   · ⭐⭐ a cap on TOTAL concurrent connections   ⇒ refuse beyond it, do not queue forever
⭐   · ⭐ a cap per client IP                      ⇒ one laptop cannot fill the pool
⭐   · ⭐ a request timeout                        ⇒ a slow handler cannot hold a worker forever
⭐   · ⭐⭐ 503 + Retry-After WHEN SATURATED        ⇒ ⭐ shed load, do not collapse
⭐   ⇒ ⭐⭐ A SERVER WITHOUT THESE IS NOT "SIMPLE", IT IS UNBOUNDED — and every
⭐        one of these limits is something a stranger otherwise gets to choose
⭐        for you.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Doing work in the accept loop | ⭐⭐ Nobody is calling `accept()`; clients fill the backlog. |
| ⭐⭐ **Unbounded thread per connection** | ⭐⭐ The attacker chooses your thread count. |
| Blaming the GIL for a slow server | ⭐ It is released during I/O. This is a **waiting** problem. |
| ⭐ An unbounded work queue | ⭐⭐ Memory grows and clients wait past their own timeouts. Shed load. |
| ⭐⭐ **A blocking call in the `selectors` loop** | ⭐⭐ Stops all 10,000 connections. This is Day 072's mechanism. |
| Expecting straight-line code in an event loop | ⭐ You must hand-write a state machine — which is why `await` exists. |
| ⭐ "async is faster than threads" | ⭐⭐ Same loop; it generates the state machine. Faster **per connection in memory**. |
| Threads for CPU-bound handlers | ⭐ The GIL is real for bytecode. Use processes (Day 068). |
| ⭐ No connection cap or timeout | ⭐⭐ Unbounded, in every model. |
| Forgetting `setblocking(False)` | ⭐ One slow socket blocks the whole loop. |

## Interview questions

**Q: Your server handles one request at a time. What are the options?**
> Three, fundamentally. A thread per connection — simple, and the GIL isn't the problem because
> `recv` and database drivers release it while waiting, but it's unbounded, so an attacker chooses how
> many threads I create. A bounded pool — same model, but the memory ceiling is mine rather than
> theirs, at the cost of head-of-line blocking when every worker is busy. Or non-blocking sockets with
> `selectors`, which is one thread, thousands of connections, and kilobytes each instead of megabytes.
> In production it's usually a combination: worker processes for the cores, and inside each one either
> a thread pool or an event loop.

**Q: What does the `selectors` version teach you about asyncio?**
> That it *is* asyncio. One thread, non-blocking sockets, a call that sleeps until the kernel reports
> a socket ready, a dispatch loop, and per-connection state in a dict. Writing it makes two things
> obvious. First, why a blocking call is catastrophic — there's one thread, and if it's inside your
> function nothing else can be serviced, which is exactly the `async def` failure mode with the
> mechanism visible. Second, why `await` exists at all: with raw selectors you can't write "read the
> headers, then read the body" as a sequence, because each `recv` returns whenever the kernel feels
> like it — so every connection needs an explicit state machine and a partial buffer.
> `async`/`await` lets you write the sequential version and has the compiler build that state machine
> for you. The suspended coroutine frame *is* the per-connection state.

**Q: Is async faster than threads?**
> Not per request. It's the same event loop underneath, and for the same workload the throughput is
> comparable. What it buys is memory per connection — kilobytes rather than megabytes — so it scales
> to tens of thousands of mostly-idle connections, which is exactly the WebSocket and long-poll case.
> And it costs you the requirement that nothing in the path may block, which is a real constraint,
> because one badly-chosen library call takes out every connection the worker owns.

**Q: Under overload, what should your server do?**
> Shed load rather than queue indefinitely. An unbounded queue just moves the problem — memory grows,
> and clients end up waiting past their own timeouts for a response nobody wants any more, so you're
> doing work that will be thrown away. Cap the queue, and return 503 with `Retry-After` beyond it.
> Bounded degradation beats unbounded collapse: a queue that fills is recoverable, a process that gets
> OOM-killed isn't. And refusing fast is kinder to the client than accepting slowly.

**Q: What limits does every server need, regardless of model?**
> A read timeout per connection, a cap on total concurrent connections, a cap per client IP, a request
> timeout so a slow handler can't hold a worker forever, and a 503 with `Retry-After` when saturated.
> The framing I'd use is that every limit you don't set is a number a stranger gets to choose for you
> — how many threads you create, how much memory you allocate, how long you hold a socket. A server
> without them isn't simple, it's unbounded.

## 🎙️ Articulation drill

Record two minutes: **"Why does `asyncio` exist?"** — and answer it from having built the thing,
which almost nobody has.

⭐ **Start from the loop, not from the syntax:** **"underneath, an async server is one thread, a set
of non-blocking sockets, and a call — `epoll`, or `select` — that sleeps until the kernel says one of
them is ready. Then it dispatches. That's it, and you can write it in forty lines with the `selectors`
module."**

⭐⭐ **Then the reason `await` exists, which is the actual question:** *"and when you write it that
way, you immediately hit the problem async/await solves. You can't express 'read the headers, then read
the body' as a sequence, because each `recv` returns whenever the kernel feels like it — you might get
half the headers. So every connection needs an explicit state machine and a partial buffer, and your
straight-line parsing logic turns into a transition table. `await` lets you write the sequential
version and has the compiler build that state machine for you. The suspended coroutine frame *is* the
per-connection state."*

⭐⭐ **Then correct the usual misconception, unprompted:** *"which is why I'd push back on 'async is
faster than threads'. It's the same loop underneath, and per request the throughput is comparable.
What it buys is memory per connection — kilobytes instead of megabytes — so it scales to tens of
thousands of mostly-idle connections, which is the WebSocket case. And it costs you the rule that
nothing may block: one badly-chosen library call takes out every connection that worker owns, because
there's one thread and it's inside your function."*

⭐ **Close on what production actually does:** *"so real deployments use both layers — worker processes
for the cores, because the GIL means one process can't use more than one for bytecode, and an event
loop inside each for the waiting. `gunicorn -w 4 -k uvicorn.workers.UvicornWorker` is exactly that, and
nothing more."*
