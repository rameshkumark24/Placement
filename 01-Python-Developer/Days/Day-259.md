# Day 259 🏗️

**P-259** · 🔐 **Authorisation** — ⭐⭐ RBAC, ownership, tenancy, and the matrix as a test file

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: authorisation lives in the `WHERE` clause. A permission check that runs
> after the rows have been fetched protects a detail endpoint and silently does nothing on a list —
> which is how an API returns every tenant's data while every test passes.**
>
> ⭐ Day 258 established *who you are*. ⭐⭐ Today is three separate questions that people collapse
> into one, and the collapse is where every real breach in an application like this comes from.

# Part 1 — ⭐⭐ Three questions, three places

```
⭐⭐ ① WHO ARE YOU?            ⇒ ⭐ AUTHENTICATION (Day 258)
⭐      ⭐ a signature check. ⭐ Failure ⇒ 401.
⭐⭐ ② MAY SOMEONE OF YOUR ROLE DO THIS ***KIND*** OF THING?
⭐      ⇒ ⭐ RBAC, in a dependency. ⭐ "Technicians may not issue
⭐        invoices." ⭐ Failure ⇒ 403.
⭐      ⭐⭐ THIS CHECK DOES NOT LOOK AT ANY ROW.
⭐⭐ ③ MAY YOU DO IT TO ***THIS PARTICULAR RECORD***?
⭐      ⇒ ⭐⭐ THE QUERY. "A technician may complete a job ASSIGNED TO
⭐        THEM." ⭐ Failure ⇒ 404 (Day 118 — a 403 confirms the record
⭐        exists).
⭐      ⭐⭐ THIS CHECK ***IS*** A PREDICATE, AND IT MUST BE IN THE SAME
⭐        QUERY THAT FETCHES THE ROWS.

⭐ ⇒ ⭐⭐ THE COLLAPSE THAT CAUSES BREACHES: TREATING ③ AS IF IT WERE ②.
⭐   ⭐ `@require_role("technician")` on the list endpoint answers the
⭐     wrong question — it confirms the caller is a technician, and then
⭐     returns everyone's jobs.
⭐   ⭐ An object-permission hook answers ③ correctly on a DETAIL view
⭐     and ⭐⭐ IS NEVER CALLED ON A LIST (Day 176). ⭐ `GET /jobs/7`
⭐     returns 404 correctly; `GET /jobs` returns the whole table.
```

# Part 2 — ⭐ RBAC: roles, and how much machinery to build

```
⭐⭐ FOUR ROLES, HIERARCHICAL, IN A `CHECK`-CONSTRAINED COLUMN.
⭐   owner > dispatcher > technician ; customer is DISJOINT, not lower.
⭐   ⭐⭐ THAT LAST POINT MATTERS: a customer is not "a technician with
⭐     fewer rights", they are a different KIND of principal with a
⭐     different authentication path. ⭐ Modelling them on the same
⭐     ladder produces `if role == "customer"` special cases everywhere.

⭐⭐ ROLES-IN-CODE vs PERMISSIONS-IN-DATABASE — decide once, in an ADR:
⭐   ⭐ ROLES AS AN ENUM + a permission map in code:
⭐     ✅ ⭐ testable, greppable, versioned with the code, no query.
⭐     ❌ ⭐ a customer cannot define a custom role.
⭐   ⭐ PERMISSIONS AS ROWS (role_permissions table):
⭐     ✅ ⭐ custom roles, changeable without a deploy.
⭐     ❌ ⭐⭐ A QUERY (OR A CACHE) ON EVERY REQUEST, permissions that
⭐        can be edited into an inconsistent state, and ⭐⭐ AN
⭐        AUTHORISATION MODEL YOU CANNOT READ IN A CODE REVIEW.
⭐   ⇒ ⭐⭐ FOR THIS PROJECT: ROLES IN CODE. ⭐ Write ADR-0008 saying
⭐     so, and name the trigger that would change it ("a customer asks
⭐     for custom roles"), so the decision is revisitable rather than
⭐     accidental.
```

```python
PERMISSIONS: dict[Role, frozenset[Action]] = {
    Role.OWNER:      frozenset(Action),                    # ⭐ all
    Role.DISPATCHER: frozenset({Action.JOB_CREATE, Action.JOB_DISPATCH,
                                Action.JOB_CANCEL, Action.JOB_READ,
                                Action.REPORT_READ}),
    Role.TECHNICIAN: frozenset({Action.JOB_READ, Action.JOB_START,
                                Action.JOB_COMPLETE, Action.PHOTO_UPLOAD}),
    Role.CUSTOMER:   frozenset({Action.JOB_READ, Action.INVOICE_PAY}),
}
# ⭐⭐ NOTE THAT TECHNICIAN AND CUSTOMER BOTH HAVE `JOB_READ`. ⭐ The
#    role says WHICH ACTIONS; the query says WHICH ROWS. ⭐⭐ Those are
#    genuinely different questions and this table cannot answer the
#    second one — which is the entire point of Part 3.
```

# Part 3 — ⭐⭐ Question ③: the predicate, and the two places it must live

```python
# ⭐⭐ ONE FUNCTION, USED BY ***BOTH*** THE LIST AND THE DETAIL QUERY.
def visible_jobs(actor: Principal) -> ColumnElement[bool]:
    match actor.role:
        case Role.OWNER | Role.DISPATCHER:
            return true()                      # ⭐ RLS still scopes tenant
        case Role.TECHNICIAN:
            return jobs.c.id.in_(
                select(assignments.c.job_id)
                .where(assignments.c.technician_id == actor.id,
                       assignments.c.status != "cancelled"))
        case Role.CUSTOMER:
            return jobs.c.id == actor.scoped_job_id   # ⭐ signed link
```

```python
def list_jobs(s, actor, ...):
    return s.execute(select(...).where(visible_jobs(actor), *filters))

def get_job(s, actor, job_id):
    row = s.execute(select(...).where(jobs.c.id == job_id,
                                      visible_jobs(actor))).first()
    if row is None: raise NotFound()      # ⭐⭐ 404, NOT 403 — and note
    return row                            #    the code cannot tell the
                                          #    difference either, which
                                          #    is exactly right
```

```
⭐⭐ WHY ONE SHARED FUNCTION RATHER THAN TWO CHECKS:
⭐   ⭐ There is now exactly ONE definition of "which jobs may this actor
⭐     see", and both paths import it. ⭐⭐ THE LIST/DETAIL DIVERGENCE
⭐     BECOMES STRUCTURALLY IMPOSSIBLE rather than a thing you remember.
⭐   ⭐ New endpoint? It uses the same predicate or it does not compile
⭐     in review.
⭐   ⭐⭐ AND IT COMPOSES WITH RLS: RLS handles the TENANT boundary
⭐     (Part 4); this handles the WITHIN-TENANT row rules. ⭐ Two layers,
⭐     two questions, and neither one is doing the other's job.
```

# Part 4 — ⭐⭐ RLS in practice, and the two ways to make it useless

```sql
ALTER TABLE jobs ENABLE ROW LEVEL SECURITY;
ALTER TABLE jobs FORCE ROW LEVEL SECURITY;      -- ⭐⭐ SEE TRAP ①
CREATE POLICY tenant_isolation ON jobs
  USING      (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
-- ⭐⭐ `USING` FILTERS READS; `WITH CHECK` VALIDATES WRITES. ⭐ Omit
--    `WITH CHECK` and a tenant can INSERT rows belonging to another —
--    the reads are protected and the writes are not.
```

```
⭐⭐ TRAP ① — RLS DOES NOT APPLY TO THE TABLE OWNER OR A SUPERUSER.
⭐   ⭐ Your migrations create the tables, so the migration role owns
⭐     them. ⭐⭐ IF THE APPLICATION CONNECTS AS THAT SAME ROLE, EVERY
⭐     POLICY IS SILENTLY SKIPPED — and every test passes, because your
⭐     tests connect the same way.
⭐   ⇒ ⭐⭐ TWO ROLES: `fieldwork_migrate` (owner, used by Alembic only)
⭐     and `fieldwork_app` (non-owner, GRANTed DML). ⭐ `FORCE ROW LEVEL
⭐     SECURITY` additionally applies policies to the owner, which is a
⭐     good belt-and-braces default.
⭐   ⇒ ⭐⭐ AND THE TEST THAT PROVES IT: connect as `fieldwork_app`, set
⭐     tenant 1, and assert `SELECT count(*) FROM jobs` is less than the
⭐     true total. ⭐ If it equals the total, RLS is decorative.

⭐⭐ TRAP ② — `SET` vs `SET LOCAL` (Days 192, 197, 252).
⭐   ⭐ Plain `SET app.tenant_id = 7` persists on the CONNECTION.
⭐   ⇒ ⭐⭐ RETURNED TO THE POOL, THE NEXT REQUEST — POSSIBLY ANOTHER
⭐     TENANT'S — INHERITS IT. ⭐⭐ CROSS-TENANT DATA EXPOSURE CAUSED BY
⭐     A CONNECTION POOL, with no error anywhere.
⭐   ⇒ ⭐⭐ `SET LOCAL`, INSIDE A TRANSACTION, ALWAYS. It resets at
⭐     commit or rollback, which is precisely the behaviour you want.
⭐   ⇒ ⭐ And the test: request as tenant A, return the connection,
⭐     request as tenant B on the same connection, assert B sees only B.
```

```
⭐⭐ AND THE THIRD PLACE RLS DOES NOT PROTECT YOU — Day 252 named it and
⭐   here it becomes code: ⭐⭐ THE BACKGROUND WORKER HAS NO REQUEST AND
⭐   THEREFORE NO TENANT.
⭐   ⇒ ⭐ A worker that iterates "all pending jobs" must `SET LOCAL
⭐     app.tenant_id` PER UNIT OF WORK, from the job payload — not once
⭐     at start-up, and not "as a superuser because it's internal".
⭐   ⇒ ⭐⭐ AN OUTBOX RELAY IS THE WORST CASE: it legitimately reads
⭐     across tenants. ⭐ Give it its own role with its own narrow
⭐     policy, and make the handler set the tenant before doing anything
⭐     domain-shaped.
```

# Part 5 — ⭐⭐ The matrix as a test file

```python
# tests/test_authorization_matrix.py
# ⭐⭐ THIS FILE OVERRIDES NOTHING. Real tokens, real dependencies, real
#    database. Day 165's rule: stub the principal and you test the stub.

CASES = [
    # (role,        method, path,                     expected)
    ("technician",  "GET",  "/v1/jobs/{other_job}",   404),   # ⭐⭐ not 403
    ("technician",  "GET",  "/v1/jobs",               "only_assigned"),
    ("technician",  "POST", "/v1/jobs",               403),
    ("technician",  "POST", "/v1/invoices/{id}/issue",403),
    ("dispatcher",  "POST", "/v1/invoices/{id}/issue",403),
    ("dispatcher",  "POST", "/v1/jobs/{id}/dispatch", 200),
    ("customer",    "GET",  "/v1/jobs/{other_job}",   404),
    ("customer",    "POST", "/v1/jobs/{id}/complete", 403),
    ("owner",       "POST", "/v1/users/invite",       201),
    ("dispatcher",  "POST", "/v1/users/invite",       403),
    ("anon",        "GET",  "/v1/jobs",               401),
]

@pytest.mark.parametrize("role,method,path,expected", CASES)
def test_matrix(client, seeded, role, method, path, expected): ...

# ⭐⭐ AND THE ONE THAT MATTERS MOST — THE CROSS-TENANT FILE:
@pytest.mark.parametrize("path", ALL_RESOURCE_PATHS)
def test_tenant_b_cannot_touch_tenant_a(client, two_tenants, path):
    r = client.get(path.format(id=two_tenants.a_job_id),
                   headers=auth(two_tenants.b_user))
    assert r.status_code == 404                       # ⭐⭐ NEVER 200,
                                                      #    NEVER 403
```

```
⭐⭐ FOUR PROPERTIES THAT MAKE THIS FILE WORTH MORE THAN ITS LINE COUNT:
⭐  ① ⭐⭐ IT IS THE THREAT MODEL (Day 252), EXECUTABLE. Every ❌ in the
⭐     grid is a row here, so "did we implement the threat model?" is
⭐     answered by a test run.
⭐  ② ⭐ IT IS PARAMETRISED OVER PATHS FROM THE ROUTE TABLE, so a new
⭐     endpoint appears in the cross-tenant test automatically.
⭐  ③ ⭐⭐ IT ASSERTS 404 RATHER THAN 403 FOR OTHER TENANTS, which
⭐     encodes the information-leak decision as a test rather than a
⭐     convention.
⭐  ④ ⭐⭐ IT OVERRIDES NOTHING. ⭐ The moment it stubs `get_principal`,
⭐     it stops testing authorisation and starts testing your fixture.
```

# Part 6 — ⭐ The four escalations to test explicitly

```
⭐ ① ⭐⭐ ROLE ESCALATION BY MASS ASSIGNMENT (Day 257).
⭐    `PATCH /v1/users/me {"role": "owner"}` ⇒ ⭐⭐ the request schema
⭐    has no `role` field, so it is a 422 with `extra="forbid"`. ⭐ Test
⭐    it anyway — this is the single most common real escalation.
⭐ ② ⭐ IDOR ON A NESTED RESOURCE.
⭐    `GET /v1/jobs/{my_job}/photos/{their_photo}` ⇒ ⭐⭐ the photo query
⭐    must be scoped by BOTH the photo id AND the parent job, or a valid
⭐    parent laundering an invalid child works. ⭐ People check the
⭐    parent and then fetch the child by id alone.
⭐ ③ ⭐⭐ THE FORGOTTEN LIST FILTER — Part 1, and the reason Part 3 uses
⭐    one shared predicate.
⭐ ④ ⭐⭐ THE ADMIN OR INTERNAL ENDPOINT. `/internal/*`, `/admin/*`,
⭐    `/metrics`, the debug route someone added. ⭐⭐ These are the
⭐    routes that get registered without going through the normal
⭐    dependency, and the route-table test (Day 257) is what catches
⭐    them — ⭐ plus network-level restriction, because defence in depth
⭐    means `/metrics` is not reachable from the internet at all.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Treating "may they touch this row" as a role check | A role check on a list endpoint returns everyone's data. |
| An object-permission hook as your only row check | It's never called on list endpoints. |
| Different predicates in the list and detail queries | They diverge. Use one shared function. |
| 403 for another tenant's record | It confirms the record exists. 404. |
| Modelling the customer as a lower-privileged staff role | They're a different kind of principal; you'll get `if role == customer` everywhere. |
| Permissions in the database by default | A query per request and an authorisation model you can't read in review. |
| RLS with the app connecting as the table owner | Policies are silently skipped and every test still passes. |
| A policy with `USING` but no `WITH CHECK` | Reads are protected; a tenant can still insert into another. |
| Plain `SET app.tenant_id` | It persists on the pooled connection into the next tenant's request. |
| A worker that sets the tenant once at startup | It must be set per unit of work, from the payload. |
| Running the outbox relay as a superuser "because it's internal" | Give it a narrow role and set the tenant per event. |
| An authorisation test file that overrides dependencies | You tested your fixture. |
| Not testing the cross-tenant case on every path | The new endpoint is the one that leaks. |
| Fetching a nested resource by id alone | A valid parent launders an invalid child. |
| Assuming `/internal` and `/metrics` are safe | They're registered outside the normal dependency and reachable. |

## Interview questions

**Q: How do you do authorisation?**

> As three separate questions in three places, because collapsing them is where the breaches come
> from. Who you are is authentication — a signature check, 401 on failure. Whether someone of your role
> may do this *kind* of thing is RBAC in a dependency, and crucially that check looks at no rows at
> all — 403 on failure. And whether you may do it to *this particular record* is a predicate that has
> to be in the same query that fetches the rows, returning 404 rather than 403 because a 403 confirms
> the record exists. The failure mode I'd highlight is treating the third question as if it were the
> second: an object-permission hook answers it correctly on a detail endpoint and is never called on a
> list, so `GET /jobs/7` correctly returns 404 while `GET /jobs` returns the entire table — and every
> test for the detail view passes.

**Q: How do you prevent the list/detail divergence?**

> With one function that returns a SQL predicate, used by both queries. `visible_jobs(actor)` returns
> `true()` for owners and dispatchers, an `IN` subquery over assignments for technicians, and an
> equality on the scoped job id for a customer on a signed link. The list query filters by it; the
> detail query filters by it *and* the id, so a miss is indistinguishable from not existing — which is
> exactly the 404 semantics I want, and the code can't tell the difference either. The point isn't the
> function, it's that there is now exactly one definition of "which rows may this actor see", so
> divergence is structurally impossible rather than something I remember. It also composes with
> row-level security cleanly: RLS owns the tenant boundary, the predicate owns the within-tenant rules,
> and neither is doing the other's job.

**Q: What are the two ways RLS silently doesn't work?**

> First, it doesn't apply to the table owner or a superuser — and the migration role owns the tables it
> created, so if the application connects as that role every policy is skipped. The nasty part is that
> your tests connect the same way, so everything passes. The fix is two roles: a migration owner used
> only by Alembic, and a non-owner application role with DML grants, plus `FORCE ROW LEVEL SECURITY` as
> belt and braces. And a test that connects as the app role, sets a tenant, and asserts the row count is
> *less* than the true total — if it equals the total, RLS is decoration. Second, `SET` versus
> `SET LOCAL`: a plain `SET` persists on the connection, so when it goes back to the pool the next
> request — possibly another tenant's — inherits it. That's cross-tenant data exposure caused by a
> connection pool, with no error anywhere. `SET LOCAL` inside the transaction resets at commit, which
> is exactly the behaviour you want.

**Q: Where does RLS not protect you at all?**

> Background work, because there's no request and therefore no tenant. A worker that iterates all
> pending jobs has to set the tenant per unit of work from the job payload — not once at startup, and
> definitely not by connecting as a superuser on the grounds that it's internal, which is the shortcut
> people take. The hardest case is the outbox relay, because it legitimately reads across tenants: I'd
> give it its own database role with its own narrow policy, and require the handler to set the tenant
> before doing anything domain-shaped. The other place is hand-written reporting SQL, which bypasses
> whatever filter the ORM applies — RLS actually saves you there, which is one of the strongest
> arguments for choosing it over an application-level filter, because the reporting query is exactly
> where an application-level filter gets forgotten.

**Q: How do you know your authorisation is correct?**

> A single test file that is the threat model made executable. Every ❌ in the actor-by-action grid is a
> parametrised row asserting a status code, plus a cross-tenant test parametrised over every resource
> path from the route table, asserting 404 — never 200, and never 403. Four properties make it worth
> more than its line count: it answers "did we implement the threat model?" with a test run; it picks
> up new endpoints automatically because it's driven by the route table; it encodes the 404-not-403
> decision as a test rather than a convention; and it overrides nothing. That last one is the rule I'd
> state most firmly — the moment that file stubs the principal dependency, it stops testing
> authorisation and starts testing the fixture, which is the most comfortable way to have no coverage
> at all.

## 🎙️ Articulation drill

**Two minutes: "How is authorisation enforced in your system?"**

Lead with the three questions and insist on the separation, because the separation is the insight:
identity, then role-level capability which looks at no rows, then row-level permission which **is** a
predicate. Then the failure that makes it concrete: **an object-permission check protects the detail
endpoint and is never called on the list, so one returns 404 correctly while the other returns every
row** — and say how you make that impossible, with one shared predicate function used by both queries.
Then the tenant layer: RLS, because it's the only level nothing bypasses, including the hand-written
reporting SQL where an application filter always gets forgotten — and its two silent failures, the
owner role and plain `SET` on a pooled connection, both of which leave tests passing. Close on the
proof: **the threat model is a test file that overrides nothing**, parametrised over the route table so
new endpoints are covered automatically, asserting 404 rather than 403 for another tenant.
