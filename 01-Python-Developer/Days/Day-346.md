# Day 346 📋

**P-346** · 📋 **Design 2 — Pastebin** — ⭐⭐ where large content actually lives

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: Pastebin looks like the URL shortener with a bigger value, and the one
> difference changes everything — the payload is megabytes rather than bytes, so the content leaves
> the database entirely, and every remaining problem is about serving large private blobs cheaply
> without your API touching them.**

---

# Part 1 — ⭐ 0–8: scope, and the one number that matters

```
⭐⭐ FUNCTIONAL:
⭐   ① Create a paste (text, up to ~10 MB) ⇒ get a URL.
⭐   ② Read a paste by URL.
⭐   ③ ⭐ Expiry (10 min / 1 day / never), ⭐ visibility
⭐        (public / unlisted / private), ⭐ syntax highlighting.
⭐   ⭐⭐ OUT: accounts, editing, comments, forking, diffing.

⭐⭐ NON-FUNCTIONAL:
⭐   ⭐ 10 M pastes/day; read:write ≈ 10:1 (⭐⭐ MUCH LOWER THAN
⭐     THE SHORTENER — most pastes are read once or twice by
⭐     the person you sent them to, and this changes the caching
⭐     answer).
⭐   ⭐ ⭐⭐ AVERAGE PASTE SIZE ~10 KB, p99 ~1 MB, MAX 10 MB.
⭐   ⭐ Read p99 < 300 ms (a page load, not a redirect).

⭐⭐ THE ESTIMATE THAT DECIDES THE DESIGN:
⭐   ⭐ 10^7/day × 10 KB = ***100 GB/day***
⭐   ⇒ ⭐ 36 TB/year ⭐⭐ OF ***CONTENT***, versus roughly
⭐     10^7 × 200 B = 2 GB/day of ***metadata***.
⭐   ⇒ ⭐⭐ THE CONTENT IS 50× THE METADATA. ⭐ Two stores, and
⭐     now I can say why in one sentence instead of asserting
⭐     it.
⭐   ⭐ Writes: 10^7/10^5 = 100/s, peak 300/s. ⭐⭐ TINY.
⭐   ⭐ Reads: 1,000/s, peak 3,000/s.
⭐   ⭐ Bandwidth out: 3,000/s × 10 KB = ⭐ 30 MB/s ≈ 240 Mbps,
⭐     ⭐⭐ AND ~78 TB/MONTH OF EGRESS ⇒ ***~$7,000/MONTH AT
⭐     $0.09/GB*** (Day 327). ⭐ That is the biggest line on the
⭐     bill and the argument for a CDN, stated with a number.
```

# Part 2 — ⭐⭐ Where the content lives — the whole design decision

```
⭐⭐ ❌ IN POSTGRES AS `TEXT`:
⭐   ⭐ 36 TB/year in the primary. ⭐ Backups become enormous
⭐     and slow, ⭐ replication ships every byte to every
⭐     replica (Day 328), ⭐⭐ AND TOAST STORAGE MEANS A LARGE
⭐     VALUE IS OUT-OF-LINE ANYWAY — you get the cost without
⭐     the benefit.
⭐   ⭐ ⭐⭐ AND THE KILLER: A `SELECT *` THAT ACCIDENTALLY
⭐     INCLUDES THE CONTENT COLUMN WILL SATURATE YOUR
⭐     DATABASE'S NETWORK LINK.

⭐⭐ ✔ CONTENT IN OBJECT STORAGE, METADATA IN POSTGRES:
⭐   `pastes(key PK, s3_key, size, mime, syntax, visibility,
⭐           owner_id, expires_at, created_at, sha256, status)`
⭐   ⇒ ⭐⭐ DAY 327'S RULE: ***THE BYTES GO IN THE BUCKET, THE
⭐     ROW GOES IN THE DATABASE.***
⭐   ⇒ ⭐ Metadata is now ~2 GB/day — ⭐⭐ WHICH FITS ON ONE
⭐     POSTGRES FOR YEARS, so this design needs no sharding at
⭐     all. ⭐ Say that: it is the payoff.

⭐⭐ THE SIZE-BASED HYBRID WORTH PROPOSING:
⭐   ⭐ ⭐⭐ CONTENT UNDER ~4 KB GOES ***INLINE*** IN THE ROW.
⭐   ⇒ ⭐ A large fraction of pastes are small snippets, and
⭐     inline means ***one*** round trip instead of two —
⭐     ⭐⭐ CUTTING p50 LATENCY ROUGHLY IN HALF FOR THE COMMON
⭐     CASE.
⭐   ⇒ ⭐ Above the threshold, S3.
⭐   ⇒ ⭐⭐ THIS IS EXACTLY WHAT REAL SYSTEMS DO (it is why
⭐     Postgres has an inline/TOAST threshold at all), AND
⭐     PROPOSING IT UNPROMPTED IS A STRONG SIGNAL.
```

# Part 3 — ⭐⭐ The write path: never through your API

```
⭐⭐ FOR SMALL PASTES (< 1 MB) — ⭐ through the API is fine, and
⭐   simpler. ⭐ 300/s × 10 KB = 3 MB/s. Nothing.

⭐⭐ FOR LARGE PASTES — ⭐⭐ PRESIGNED PUT (Day 327):
⭐   ① Client asks for an upload slot with the declared size.
⭐   ② ⭐⭐ API AUTHORISES, INSERTS A `pending` ROW, RETURNS A
⭐      PRESIGNED URL WITH THE KEY, MAX SIZE, CONTENT-TYPE AND
⭐      EXPIRY ALL PINNED BY THE SERVER.
⭐   ③ Client PUTs directly to S3.
⭐   ④ ⭐ Storage event ⇒ worker validates and flips to `ready`.
⭐   ⑤ ⭐ Sweeper removes stale `pending` rows and orphan objects
⭐      in both directions.

⭐⭐ AND THE SIZE-LIMIT SUBTLETY THAT CATCHES PEOPLE:
⭐   ⭐ ⭐⭐ YOU CANNOT ENFORCE A SIZE LIMIT AFTER THE FACT — the
⭐     bytes are already stored and already billed.
⭐   ⇒ ⭐ Presigned ***POST*** policies support a
⭐     `content-length-range` condition; ⭐ presigned PUT can pin
⭐     an exact `ContentLength`. ⭐⭐ EITHER WAY, THE LIMIT MUST
⭐     BE IN THE SIGNATURE, NOT IN A CHECK YOU RUN AFTERWARDS.

⭐⭐ DEDUPLICATION — ⭐ and the honest analysis:
⭐   ⭐ Store by `sha256(content)` as the S3 key ⇒ identical
⭐     content stored once, N metadata rows pointing at it.
⭐   ⭐ ✔ Real savings: error logs and stack traces get pasted
⭐     repeatedly.
⭐   ⭐ ✘ ⭐⭐ DELETION BECOMES REFERENCE COUNTING, WHICH IS A
⭐     WHOLE CLASS OF BUG — and a wrong refcount either leaks
⭐     storage forever or deletes content someone else is still
⭐     reading.
⭐   ⭐ ✘ ⭐⭐ AND A PRIVACY PROBLEM PEOPLE MISS: IF I CAN TEST
⭐     WHETHER MY UPLOAD DEDUPLICATED (by timing, or by a
⭐     "this already exists" response), ⭐⭐ I CAN CONFIRM
⭐     SOMEONE ELSE PASTED A SPECIFIC SECRET.
⭐   ⇒ ⭐⭐ SO: DEDUPE ONLY WITHIN A PRIVACY BOUNDARY (per user,
⭐     or public-only), NEVER GLOBALLY ACROSS PRIVATE CONTENT —
⭐     ⭐ and say the reason, because it is the part that scores.
```

# Part 4 — ⭐⭐ The read path: serving private content through a CDN

```
⭐⭐ THE TENSION: ⭐ you want CDN caching for cost and latency
⭐   (Part 1's $7,000/month), ⭐⭐ BUT MOST PASTES ARE UNLISTED
⭐   OR PRIVATE AND MUST NOT BE PUBLICLY CACHEABLE (Day 327's
⭐   regional breach).

⭐⭐ THE ANSWER BY VISIBILITY — ⭐ three cases, three treatments:
⭐   ⭐ ***PUBLIC*** ⇒ CDN-cacheable with a long TTL, keyed on
⭐     the paste key. ⭐⭐ IMMUTABLE CONTENT MEANS `max-age=
⭐     31536000, immutable` IS SAFE — pastes are never edited,
⭐     which is the property that makes this free.
⭐   ⭐ ***UNLISTED*** ⇒ the key is unguessable (Day 345's key
⭐     space), ⭐ so it is cacheable ***by key*** — ⭐⭐ BUT SAY
⭐     THE CAVEAT OUT LOUD: UNGUESSABLE IS NOT AUTHORISATION,
⭐     IT IS A LINK NOBODY HAS LEAKED YET. ⭐ Fine for a
⭐     snippet, wrong for credentials.
⭐   ⭐ ***PRIVATE*** ⇒ ⭐⭐ SIGNED CDN URLS (Day 327). ⭐ The API
⭐     checks authorisation, then issues a short-lived signed
⭐     URL for the object. ⭐⭐ YOU GET EDGE CACHING ***AND***
⭐     AUTHORISATION, WHICH IS THE ONLY OPTION THAT GIVES BOTH.

⭐⭐ THE FLOW FOR A PRIVATE PASTE:
⭐   `GET /p/{key}` → API checks auth → 302 (or JSON) with a
⭐   ⭐ 5-minute signed CDN URL → the browser fetches bytes from
⭐   the edge.
⭐   ⇒ ⭐⭐ YOUR API HANDLED 200 BYTES; THE CDN SERVED 10 MB.
⭐   ⇒ ⭐ And the API response itself is `Cache-Control:
⭐     private, no-store`, because it contains a credential.
```

# Part 5 — ⭐⭐ Expiry, which is harder than it looks

```
⭐⭐ THREE MECHANISMS, AND YOU NEED MORE THAN ONE:
⭐   ① ⭐⭐ ***LAZY, AT READ TIME*** — `WHERE expires_at >
⭐      now()`. ⭐ Correctness never depends on a job running.
⭐      ⭐ Day 316's lesson, again.
⭐   ② ⭐ ***A SWEEPER*** deleting expired rows in batches
⭐      (Day 260) — for storage reclamation only.
⭐   ③ ⭐⭐ ***S3 LIFECYCLE RULES*** — but they only support
⭐      coarse age-based expiry, ⭐ so per-paste TTLs need the
⭐      sweeper to issue the deletes.

⭐⭐ THE THREE TRAPS:
⭐   ⭐ ⭐⭐ THE CDN STILL HAS IT. ⭐ An expired paste is served
⭐     from the edge for the rest of its TTL. ⭐ For "burn after
⭐     reading" that is a correctness failure, ⭐⭐ SO
⭐     SHORT-TTL PASTES MUST NOT BE CDN-CACHED AT ALL — the
⭐     expiry choice and the caching policy are coupled, and
⭐     noticing that is the point.
⭐   ⭐ ⭐⭐ "BURN AFTER READING" IS A DISTRIBUTED PROBLEM:
⭐     two concurrent readers both see it. ⭐ It needs a
⭐     conditional `UPDATE … WHERE read_count = 0 RETURNING`
⭐     (Day 310) — ⭐⭐ THE SAME CHECK-AND-ACT SHAPE, AT A
⭐     COMPLETELY DIFFERENT SCALE.
⭐   ⭐ Deletion is four places (Day 327): row, object, CDN,
⭐     and any search/preview derivative.

⭐⭐ AND THE COST NOTE: ⭐⭐ 10 M PASTES/DAY WITH A LIFECYCLE
⭐   MEANS 10 M `DELETE` CALLS TO S3 EVENTUALLY. ⭐ Deletes are
⭐   free but the ***LIST*** to find them is not; ⭐ prefix keys
⭐   by expiry date (`exp/2026-08-20/…`) so the sweeper deletes
⭐   by prefix instead of scanning.
```

# Part 6 — ⭐ Abuse, which is the real operational story

```
⭐⭐ A PASTE SERVICE IS FREE, ANONYMOUS, PUBLIC HOSTING. ⭐ It
⭐   will be used for:
⭐   ⭐ ⭐⭐ MALWARE PAYLOADS AND C2 CONFIGURATION — served from
⭐     your domain, which gets your domain blocklisted, ⭐⭐ AND
⭐     THAT TAKES DOWN LEGITIMATE USERS TOO.
⭐   ⭐ Leaked credential dumps ⇒ legal and disclosure
⭐     obligations.
⭐   ⭐ Phishing pages if you render HTML — ⭐⭐ SO YOU DO NOT
⭐     RENDER HTML. ⭐ Serve `text/plain` with
⭐     `X-Content-Type-Options: nosniff`, ⭐⭐ AND SERVE USER
⭐     CONTENT FROM A ***SEPARATE DOMAIN***, so a stored-XSS in
⭐     a preview cannot touch your session cookies.

⭐⭐ THE CONTROLS, CHEAPEST FIRST:
⭐   ⭐ Rate limit creation per IP and per key (Day 336).
⭐   ⭐ ⭐⭐ ASYNCHRONOUS SCANNING against threat feeds and
⭐     secret-detection regexes (AWS keys, private keys) — ⭐ and
⭐     a fast revoke path, which is why the read goes through
⭐     your API rather than a permanent public S3 URL.
⭐   ⭐ Size and rate caps per anonymous session.
⭐   ⭐ An abuse-report endpoint and a takedown queue with an
⭐     owner.

⭐⭐ ⇒ AND THE ARCHITECTURAL CONSEQUENCE WORTH STATING:
⭐   ***THE ABILITY TO REVOKE IS WHY THE READ PATH GOES THROUGH
⭐      AN AUTHORISATION CHECK RATHER THAN A PERMANENT PUBLIC
⭐      OBJECT URL*** — ⭐ the same reason Day 345 chose 302.
```

# Part 7 — ⭐ Bottlenecks, and the honest summary

```
⭐⭐ WHAT BREAKS FIRST:
⭐   ① ⭐⭐ EGRESS COST, NOT CAPACITY. ⭐ At 10× this is
⭐      $70,000/month before anything is slow. ⭐ CDN offload
⭐      and compression (⭐ text compresses ~5–10×, ⭐⭐ AND
⭐      STORING GZIPPED WITH `Content-Encoding: gzip` MEANS THE
⭐      CDN AND BROWSER HANDLE IT AND YOU PAY A FIFTH OF THE
⭐      EGRESS).
⭐   ② ⭐ S3 request rate on a hot prefix — ⭐ modern S3 scales
⭐      per prefix, ⭐⭐ SO KEY BY A HASH PREFIX RATHER THAN A
⭐      TIMESTAMP (Day 329's monotonic-key hotspot, again).
⭐   ③ ⭐ The metadata database — ⭐⭐ NOT FOR A LONG TIME. 2 GB
⭐      a day of metadata is years of runway on one node, and
⭐      saying "I would not shard this" is the correct answer.

⭐⭐ THE SUMMARY THAT LANDS:
⭐   ***"Pastebin is the shortener with one difference that
⭐      changes everything: the payload is 50× the metadata. So
⭐      content goes to object storage — small ones inline for
⭐      one round trip — the write path is presigned with the
⭐      size in the signature, and the read path is signed CDN
⭐      URLs so I get edge caching and authorisation together.
⭐      The database never sees a megabyte, so it never needs
⭐      sharding. My biggest line item is egress, not compute,
⭐      and my biggest operational problem is abuse."***
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Storing content in Postgres | 36 TB/year in the primary, replicated to every replica, and one `SELECT *` saturates the link |
| ⭐⭐ Uploading large pastes through the API | A worker per upload, double transfer, and ten pods means ten uploads |
| ⭐⭐ Enforcing size after upload | The bytes are stored and billed. The limit must be in the signature |
| ⭐⭐ Global deduplication of private content | Detectable dedup lets me confirm someone else pasted a specific secret |
| ⭐ Deduplication without refcounting | You either leak storage forever or delete content someone is still reading |
| ⭐⭐ Public CDN caching for unlisted pastes without saying the caveat | Unguessable is not authorisation; it's a link nobody has leaked yet |
| ⭐⭐ Caching a short-TTL paste at the edge | It outlives its expiry. Expiry policy and caching policy are coupled |
| ⭐ Burn-after-reading without a conditional update | Two concurrent readers both get it |
| ⭐ Rendering user content as HTML on your own domain | Stored XSS against your own session cookies. Separate domain, `nosniff`, `text/plain` |
| ⭐ Timestamp-prefixed S3 keys | All writes land on one prefix. Hash-prefix them |
| ⭐ Sharding the metadata database | 2 GB a day is years of runway. Saying "I wouldn't" is the right answer |
| ⭐ Forgetting compression | Text compresses 5–10×, and that's a direct 80% cut to your largest bill |

## Interview questions

**1. "How is this different from the URL shortener?"**
> ⭐⭐ One difference that changes everything: **the payload is about fifty times the metadata.** ⭐ Ten
> million pastes a day at ten kilobytes is a hundred gigabytes of content a day against two gigabytes
> of metadata — so content goes to object storage and the database stays small enough that ⭐⭐ **it
> never needs sharding at all**, which is the payoff. ⭐ The read:write ratio is also far lower, about
> ten to one, so caching matters less and egress matters more.

**2. "Where does the content go?"**
> ⭐ Object storage, with the row in Postgres. ⭐⭐ And I'd propose the hybrid: **content under about
> four kilobytes stored inline in the row**, because a large fraction of pastes are small snippets and
> inline means one round trip instead of two, roughly halving p50 for the common case. ⭐ Above the
> threshold, S3. ⭐ That's the same reasoning Postgres itself uses for its inline/TOAST threshold.

**3. "Would you deduplicate identical pastes?"**
> ⭐ Only carefully. ⭐ Content-addressed keys give real savings, because people paste the same stack
> traces repeatedly. ⭐⭐ But deletion becomes reference counting, and there's a privacy problem people
> miss: **if I can detect that my upload deduplicated, I can confirm someone else pasted a specific
> secret.** ⭐ So dedupe within a privacy boundary — per user, or public content only — never globally
> across private pastes.

**4. "How do you serve a private paste through a CDN?"**
> ⭐⭐ Signed CDN URLs — the only option that gives edge caching **and** authorisation. ⭐ The API checks
> the user may read it, then returns a five-minute signed URL, and the browser fetches ten megabytes
> from the edge while my API handled two hundred bytes. ⭐ The API response itself is `private,
> no-store`, because it contains a credential. ⭐ Public pastes get a long immutable TTL, which is free
> because pastes are never edited.

**5. "How does expiry work?"**
> ⭐ Lazily at read time first — `WHERE expires_at > now()` — so correctness never depends on a job
> running; a sweeper reclaims storage in batches; and S3 lifecycle for coarse ages. ⭐⭐ The trap worth
> naming: **the CDN still has it**, so an expired paste serves from the edge for the rest of its TTL —
> which means short-TTL pastes must not be edge-cached at all. ⭐ Expiry policy and caching policy are
> coupled. ⭐ And burn-after-reading needs a conditional update with `RETURNING`, or two concurrent
> readers both get it.

**6. "What's your biggest operational problem?"**
> ⭐⭐ Abuse, not scale. It's free anonymous hosting, so it will serve malware configs and credential
> dumps from my domain — ⭐⭐ **and a domain blocklisting takes down legitimate users too.** ⭐ So:
> creation rate limits, asynchronous scanning against threat feeds and secret-detection patterns, a
> takedown queue with an owner, `text/plain` with `nosniff` on a separate domain so a stored XSS can't
> reach my cookies. ⭐ And the architectural consequence: the read path goes through an authorisation
> check rather than a permanent public object URL, precisely so revocation works.

## 🎙️ Articulation drill

**Two minutes.** Open by naming the single difference from the shortener and letting it drive
everything: **the payload is about fifty times the metadata**, so content goes to object storage and
the database stays small enough that it never needs sharding — which is the payoff, and worth saying
plainly. Propose the hybrid unprompted: **inline under four kilobytes for one round trip, S3 above**,
which is exactly what Postgres itself does internally. On the write path, presigned uploads with the
key, type and **size pinned in the signature, because you cannot enforce a size limit after the bytes
are already stored and billed.** On dedup, give the benefit and then the objection that scores:
**detectable deduplication lets me confirm someone else pasted a specific secret**, so dedupe only
within a privacy boundary. On the read path, resolve the tension: **signed CDN URLs are the only option
that gives edge caching and authorisation together** — my API handles two hundred bytes while the CDN
serves ten megabytes. Then the coupling people miss: **an expired paste keeps serving from the edge, so
short-TTL pastes must not be cached there at all.** Close on the two things that actually run this
system: **egress is the biggest bill, and gzip cuts it by eighty percent** — and abuse is the biggest
operational problem, which is why the read path goes through an authorisation check rather than a
permanent public object URL.
