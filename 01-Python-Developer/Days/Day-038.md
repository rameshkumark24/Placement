# Part 1 — ⭐⭐ `deque` — the fix for Day 033

```python
from collections import deque

q = deque([1, 2, 3])
q.append(4);      q.pop()        # ⭐ right end — O(1)
q.appendleft(0);  q.popleft()    # ⭐⭐ LEFT END — O(1). This is the whole point.
q.extendleft([1,2])              # ⚠️ ⭐ inserts in REVERSE order — each goes to the front
q.rotate(1)                      # ⭐ rotate right; rotate(-1) left — O(k)
```

```
⭐⭐ HOW: a DOUBLY LINKED LIST OF FIXED-SIZE BLOCKS (64 pointers each).
⭐   ⇒ ⭐ O(1) at both ends, and better cache behaviour than a per-element linked list
⭐   ⇒ ⚠️ ⭐⭐ BUT: dq[i] IS O(n) — indexing walks the blocks.
⭐   ⇒ ⭐⭐ SO: deque for QUEUES and STACKS. list for RANDOM ACCESS. Never the other way round.
```

| | `list` | ⭐ `deque` |
|---|---|---|
| ⭐ append / pop right | O(1) | O(1) |
| ⭐⭐ **append / pop LEFT** | ⭐⭐ **O(n)** | ⭐⭐ **O(1)** |
| ⭐ random index | ⭐⭐ **O(1)** | ⭐⭐ **O(n)** |
| slicing | ⭐ yes | ⭐ **no** — `itertools.islice` |

```python
# ⭐⭐ THE RING BUFFER — maxlen is genuinely underused:
recent = deque(maxlen=100)
for line in stream:
    recent.append(line)          # ⭐⭐ pushes the OLDEST out automatically. Never grows.
```

⭐⭐ **`deque(maxlen=n)` is a bounded buffer in one argument** — the last N log lines, a sliding
window of the last N measurements, "keep the most recent 1,000 events for the error report". **It is
the fix for an entire family of unbounded-memory bugs (Day 028).**

⭐ **`deque` is also thread-safe for `append` and `popleft`** (the GIL makes those atomic), which
makes it a legitimate simple producer/consumer queue — though `queue.Queue` is the right answer once
you need blocking (Day 066).

# Part 2 — ⭐⭐ `defaultdict`

```python
from collections import defaultdict

groups = defaultdict(list)                # ⭐⭐ the factory is called on a MISSING key
for r in rows: groups[r.city].append(r)   # ⭐ no setdefault, no `if key not in`

counts = defaultdict(int)                 # ⭐ int() is 0
for w in words: counts[w] += 1

graph = defaultdict(list)                 # ⭐⭐ adjacency list — the DSA staple
for a, b in edges: graph[a].append(b); graph[b].append(a)

nested = defaultdict(lambda: defaultdict(int))    # ⭐ two levels
```

```
⭐⭐ VS setdefault:
⭐   d.setdefault(k, []).append(x)     ⇒ ⭐⭐ the [] is CONSTRUCTED ON EVERY CALL, used or not
⭐   defaultdict(list)[k].append(x)    ⇒ ⭐ constructed only when actually missing
⭐ ⇒ ⭐ same result, less garbage, and it reads better.
```

⚠️ ⭐⭐ **The trap: merely *reading* a missing key creates it.**

```python
d = defaultdict(list)
if d["nope"]:                  # ⭐⭐ this READ just inserted "nope": [] into the dict
    ...
len(d)                         # ⭐⭐ 1 — you now have a key you never meant to add

d.get("nope")                  # ⭐ None, and inserts NOTHING — use get() to probe
"nope" in d                    # ⭐ also safe
```

⭐⭐ **This causes real bugs in loops that check-then-use**, and worse, it makes a `defaultdict`
silently grow when you use it as a lookup table. **`.get()` to read, `[]` to accumulate.**

⭐ **The alternative:** subclass `dict` and define `__missing__`, which is exactly how `defaultdict`
works — the dict machinery calls `__missing__` when `__getitem__` fails.

# Part 3 — ⭐⭐ `Counter`

```python
from collections import Counter

c = Counter("mississippi")
c                      # Counter({'i': 4, 's': 4, 'p': 2, 'm': 1})
c.most_common(2)       # ⭐⭐ [('i', 4), ('s', 4)] — the reason this class exists
c["z"]                 # ⭐⭐ 0 — a missing key returns 0 and is NOT inserted (unlike defaultdict)
c.total()              # ⭐ 11 (3.10+)

# ⭐ Counter arithmetic — genuinely useful, and rarely known:
a, b = Counter("abc"), Counter("bcd")
a + b                  # ⭐ sums counts
a - b                  # ⭐⭐ subtracts, DROPPING zero and negative counts
a & b                  # ⭐ minimum of each — "what do both have"
a | b                  # maximum of each
+c                     # ⭐ strips non-positive entries
c.subtract(b)          # ⭐⭐ in place, and DOES allow negatives
```

```
⭐⭐ WHERE Counter REPLACES A LOOP:
⭐   "top 10 words / errors / endpoints"       ⇒ Counter(items).most_common(10)
⭐   ⭐⭐ "are these two strings anagrams?"       ⇒ Counter(a) == Counter(b)
⭐   "do I have enough of each ingredient?"    ⇒ ⭐ needed - have  (empty ⇒ yes)
⭐   "which items appear more than once?"      ⇒ [k for k,v in c.items() if v > 1]
```

⭐⭐ **`Counter(a) == Counter(b)` for anagrams is the answer that shows fluency**, and it is O(n)
against the O(n log n) of sorting both strings — worth saying out loud, because the sorted version is
what most people write first.

⚠️ ⭐ **`Counter` is a `dict` subclass**, so `most_common()` ties are broken by insertion order, not
by anything meaningful. **If ties matter, sort explicitly with a key.**

# Part 4 — ⭐ `OrderedDict`, `ChainMap`, and the rest

```python
from collections import OrderedDict, ChainMap
```

```
⭐⭐ "IS OrderedDict OBSOLETE NOW THAT dict IS ORDERED?" — a real interview question. NO:
⭐   1. ⭐⭐ move_to_end(key, last=True/False)  — dict has no equivalent
⭐   2. ⭐⭐ popitem(last=False)                — pop from the FRONT; dict only pops the end
⭐   3. ⭐⭐ EQUALITY IS ORDER-SENSITIVE:
⭐        OrderedDict(a=1,b=2) == OrderedDict(b=2,a=1)   ⇒ ⭐⭐ False
⭐        dict(a=1,b=2)        == dict(b=2,a=1)          ⇒ ⭐ True
⭐   ⇒ ⭐⭐ (1) and (2) are exactly what an LRU CACHE needs — a classic LLD question:
```

```python
class LRUCache:                                   # ⭐⭐ O(1) get and put
    def __init__(self, cap): self.cap = cap; self.d = OrderedDict()
    def get(self, k):
        if k not in self.d: return -1
        self.d.move_to_end(k)                     # ⭐ mark as recently used
        return self.d[k]
    def put(self, k, v):
        if k in self.d: self.d.move_to_end(k)
        self.d[k] = v
        if len(self.d) > self.cap:
            self.d.popitem(last=False)            # ⭐⭐ evict the LEAST recently used
```

⭐⭐ **Know that `functools.lru_cache` exists (Day 051) and that this is what it does inside** — but
be able to write it, because "implement an LRU cache" is one of the most-asked LLD warm-ups and the
`OrderedDict` version is six lines.

```python
# ⭐ ChainMap — layered lookup with NO copying:
config = ChainMap(cli_args, env_vars, file_config, DEFAULTS)
config["timeout"]        # ⭐⭐ first mapping that has the key wins — left to right
# ⇒ ⭐ writes go to the FIRST mapping only; the others are never touched.
```

⭐ **`ChainMap` is the configuration-precedence pattern in one object**, and unlike `{**a, **b}` it
does not copy, so later changes to the underlying dicts are visible.

| Also in the module | ⭐ For |
|---|---|
| `namedtuple` | Day 034 |
| `UserDict` / `UserList` / `UserString` | ⭐ subclassing safely — `dict` subclasses do **not** route everything through `__setitem__` |
| `collections.abc` | ⭐⭐ the protocols — `Iterable`, `Mapping`, `Sequence` (Day 056) |

⚠️ ⭐ **`class MyDict(dict)` is a common mistake:** `dict.update()` and `dict.__init__` do not call
your overridden `__setitem__`, so your invariant is bypassed. **`UserDict` wraps a real dict and
routes everything properly.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`list.pop(0)` for a queue** | ⭐⭐ `deque.popleft()` — O(1) (Day 033). |
| Indexing a `deque` in a loop | ⭐⭐ O(n) per index. Use a list for random access. |
| ⭐⭐ **Reading a missing key from a `defaultdict`** | ⭐⭐ It inserts it. Use `.get()` to probe. |
| `setdefault` with a costly default | ⭐ Built every call. `defaultdict`. |
| Counting with a manual `if k in d` | ⭐ `Counter`, or `defaultdict(int)`. |
| Sorting both strings for anagrams | ⭐⭐ `Counter(a) == Counter(b)` is O(n). |
| Relying on `most_common` tie order | ⭐ Insertion order. Sort explicitly. |
| ⭐ "`OrderedDict` is obsolete" | ⭐⭐ `move_to_end`, front `popitem`, order-sensitive equality. |
| Unbounded recent-items list | ⭐⭐ `deque(maxlen=n)`. |
| `class X(dict)` to customise | ⭐ `UserDict` — built-in methods bypass your overrides. |
| Merging config with `{**a, **b}` when you need live layers | ⭐ `ChainMap`. |

## Interview questions

**Q: When do you reach for a `deque`?**
> Whenever I need a queue or need to touch the front of a sequence. A list is a contiguous array, so
> `pop(0)` shifts every element and a BFS built on one is quadratic; a deque is a doubly linked list
> of blocks and is O(1) at both ends. The trade is random access — indexing a deque walks the blocks
> and is O(n) — so it's queues and stacks for deque, random access for list. I'd also mention
> `maxlen`, which turns it into a ring buffer in one argument and is a clean fix for "keep the last
> N" without unbounded growth.

**Q: `defaultdict` versus `setdefault`?**
> Same outcome, different cost and readability. `setdefault(k, [])` constructs the empty list on
> every call whether or not it's needed, and it reads awkwardly; `defaultdict(list)` only calls the
> factory on an actual miss. The trap with `defaultdict` is that merely reading a missing key inserts
> it, so a membership check written as `if d[k]:` silently grows the dict — I use `.get()` or `in` to
> probe and `[]` only when I intend to accumulate.

**Q: Is `OrderedDict` obsolete now that dicts keep insertion order?**
> No, for three reasons. It has `move_to_end`, which plain dicts don't. Its `popitem` can pop from
> the front, while a dict only pops the last item. And its equality is order-sensitive, so two
> `OrderedDict`s with the same pairs in different orders are unequal, whereas plain dicts compare
> equal. The first two are exactly what an LRU cache needs, which is why the six-line LRU
> implementation uses it — and that's what `functools.lru_cache` is doing internally.

**Q: How would you check whether two strings are anagrams?**
> `Counter(a) == Counter(b)`. It's O(n) and it reads as the definition of the problem. Sorting both
> and comparing is the version most people write and it's O(n log n) — fine, but worth knowing the
> better one, and worth saying which you chose and why.

**Q: What's `ChainMap` for?**
> Layered lookup without copying — CLI arguments over environment variables over a config file over
> defaults, in precedence order, resolved by the first mapping that has the key. Unlike merging with
> `{**a, **b}` it doesn't build a new dict, so it's cheap and it reflects later changes to the
> underlying mappings. It's the configuration-precedence pattern expressed as a data structure.

## 🎙️ Articulation drill

Record two minutes: **"Walk me through implementing an LRU cache."**

⭐ State the requirement first — **O(1) get and put, with eviction of the least recently used** — then
the classic answer: **a hash map for lookup plus a doubly linked list for recency**, and note that
`OrderedDict` is exactly that combination already, which is why the Python implementation is six
lines rather than sixty.

⭐ Then walk the two operations: **`get` moves the key to the end and returns it; `put` inserts,
moves to the end, and if the size exceeds capacity, `popitem(last=False)` removes the front — the
least recently used.**

⭐⭐ **Then the two things that turn a correct answer into a good one:** *"`functools.lru_cache` does
this for you, and I'd use it for memoising a function — but I'd bound `maxsize`, because an unbounded
cache keyed by user input is an unbounded, attacker-controlled dict. And if I were writing this from
scratch in an interview I'd say up front that plain dicts don't have `move_to_end` or a front
`popitem`, which is precisely why `OrderedDict` still exists after 3.7 made dicts ordered."*
