# Day 119

**L-119** · **Input validation at the boundary** — ⭐⭐ parse, don't validate; mass assignment; and `response_model` as a security control

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: validation is not a check you run on a dict — it is a conversion from
> untrusted input into a typed object that cannot be invalid, done once at the edge, so that every
> layer inside can simply trust what it receives.**
>
> ⭐ Day 057 drew the Pydantic boundary. **Today is what happens at it**, including the two things
> people never think of as validation: refusing unknown fields, and validating what you send *back*.

---

# Part 1 — ⭐⭐ Parse, don't validate

```python
# ⚠️ ⭐ "VALIDATE" — the check and the value stay separate, so nothing is proved:
def create_order(data: dict):
    if "email" not in data:              raise ValueError("email required")
    if "@" not in data["email"]:         raise ValueError("bad email")
    if data.get("qty", 0) <= 0:          raise ValueError("qty must be positive")
    ...                                  # ⭐⭐ and now `data` is STILL a dict[str, Any]

# ⭐⭐ "PARSE" — the check PRODUCES a value whose type carries the proof:
@dataclass(frozen=True)
class OrderRequest:
    email: Email                          # ⭐⭐ a type that CANNOT hold an invalid address
    qty: PositiveInt
    ship_to: Address

def create_order(req: OrderRequest): ...  # ⭐ nothing downstream can receive junk
```

```
⭐⭐ THE DIFFERENCE IS WHERE THE KNOWLEDGE LIVES:
⭐   VALIDATE ⇒ the knowledge "this was checked" lives in the READER'S HEAD, and
⭐              in the ORDER OF STATEMENTS. ⭐⭐ Three functions later, nobody
⭐              knows whether `data["email"]` was checked, so they check again —
⭐              or, worse, they don't.
⭐   PARSE    ⇒ ⭐⭐ THE KNOWLEDGE LIVES IN THE TYPE. A function taking `Email`
⭐              cannot be called with an unvalidated string, and mypy says so
⭐              (Day 062).
⭐   ⇒ ⭐⭐ "PARSE, DON'T VALIDATE" IS THE SHORT NAME FOR THIS, AND IT IS THE
⭐        SINGLE MOST USEFUL IDEA ON THE PAGE. ⭐ It is also exactly why
⭐        Day 057 put Pydantic at the edge and dataclasses inside: ⭐⭐ VALIDATE
⭐        ONCE, THEN TRUST — and the type is what carries the trust inward.
```

| ⭐ Layer | ⭐ Question | ⭐ Failure |
|---|---|---|
| ⭐ Syntactic | is it JSON? is `qty` an integer? | ⭐ `400` (Day 104) |
| ⭐⭐ Semantic | ⭐ is `qty` positive? is the date in the past? | ⭐⭐ `422` — well-formed, invalid |
| ⭐⭐ **Business** | ⭐⭐ does this user have enough credit? is the item in stock? | ⭐⭐ `409` — **not validation** |

```
⭐⭐ THE THIRD ROW IS THE ONE PEOPLE PUT IN THE WRONG PLACE, AND THE DISTINCTION
⭐   IS WORTH STATING PRECISELY:
⭐   VALIDATION says "THIS REQUEST IS WELL-FORMED" — it depends only on the
⭐     request, it is the same answer every time, and it belongs at the edge.
⭐   ⭐⭐ THE DOMAIN says "THIS REQUEST IS NOT ALLOWED RIGHT NOW" — it depends on
⭐     STATE, the answer changes minute to minute, and it belongs in the service
⭐     layer (Day 090).
⭐   ⇒ ⭐ "quantity must be positive" is validation. "we only have two left" is
⭐        a domain rule, and putting it in your Pydantic model drags the database
⭐        into your schema and makes it untestable.
```

# Part 2 — ⭐ Doing it, with and without a library

```python
from pydantic import BaseModel, Field, EmailStr, field_validator

class CreateOrder(BaseModel):
    model_config = {"extra": "forbid"}                    # ⭐⭐ Part 3 — the important line

    email: EmailStr
    qty: int = Field(gt=0, le=100)                        # ⭐ bounds, not just a type
    ship_to: str = Field(min_length=1, max_length=200)    # ⭐⭐ EVERY string needs a max
    coupon: str | None = None

    @field_validator("coupon")
    @classmethod
    def normalise(cls, v: str | None) -> str | None:
        return v.strip().upper() if v else None            # ⭐ normalise AT the boundary
```

```
⭐⭐ EVERY UNBOUNDED FIELD IS A DENIAL OF SERVICE, AND THIS IS DAY 104'S PARSER
⭐   LIMITS ONE LAYER UP:
⭐   · ⭐ a string with no `max_length` ⇒ a 10 MB name in your database, in every
⭐        log line, in every response
⭐   · ⭐⭐ a LIST with no `max_items` ⇒ `{"ids": [1,2,3, …×1,000,000]}` and your
⭐        handler does a million lookups
⭐   · ⭐⭐ NESTING DEPTH ⇒ `[[[[[…]]]]]` a thousand deep is a JSON BOMB: the
⭐        parser recurses and you get a RecursionError, or worse, quadratic work
⭐   · ⭐ an unbounded integer ⇒ `10**10000` is a valid Python int, and arithmetic
⭐        on it is not free (Day 041)
⭐   ⇒ ⭐⭐ BOUND EVERY FIELD. The default for anything attacker-supplied is a
⭐        limit, not "whatever they send".
```

⭐ **Coerce carefully.** ⭐⭐ Pydantic v2's strict-vs-lax mode matters: in lax mode `"5"` becomes `5`,
which is convenient for query strings and **surprising in a JSON body**. ⭐ Decide per boundary — lax
for query parameters, strict for JSON — and be explicit about it.

# Part 3 — ⭐⭐ Unknown fields, and mass assignment

```python
# ⚠️⚠️ ⭐⭐ THE VULNERABILITY, IN ONE LINE:
user = User(**request.json)                  # ⭐ "convenient"
db.save(user)

# ⇒ ⭐⭐ THE CLIENT SENDS {"email": "...", "is_admin": true} AND IS NOW AN ADMIN.
# ⇒ ⭐ or {"balance": 999999}, or {"user_id": 7}, or {"price": 0.01}.
```

```
⭐⭐ THAT IS **MASS ASSIGNMENT**, and it is the same class as IDOR (Day 118):
⭐   the code is authenticated, the endpoint is legitimate, ⭐⭐ AND THE BUG IS
⭐   THAT THE CLIENT GOT TO CHOOSE WHICH FIELDS TO SET.
⭐   ⇒ ⭐⭐ THE FIX IS AN EXPLICIT ALLOWLIST — which a parsed schema IS, for free:
⭐        the model has three fields, so exactly three fields can arrive.
⭐   ⇒ ⭐ NEVER `Model(**request.json)`. ⭐⭐ Always parse into a request schema,
⭐        then map its fields explicitly onto the entity.
⭐   ⇒ ⭐ and remember the mirror case: a PATCH that lets a client set
⭐        `user_id` reassigns someone else's record — mass assignment producing
⭐        an IDOR.
```

```
⭐⭐ `extra="forbid"` — REJECT UNKNOWN FIELDS. TWO REASONS, AND THE SECOND IS
⭐   THE ONE PEOPLE UNDERESTIMATE:
⭐  1. ⭐ SECURITY: it is the allowlist above, enforced by the parser.
⭐  2. ⭐⭐ IT CATCHES CLIENT TYPOS. A client sends `emailAddress` instead of
⭐       `email`; with `ignore`, the field is SILENTLY DROPPED and the request
⭐       succeeds with missing data. ⭐⭐ The bug surfaces days later as "the
⭐       emails are empty", and nobody suspects the request that returned 201.
⭐       ⭐ With `forbid`, the client gets a 422 naming the unknown field
⭐       immediately.
⭐   ⇒ ⚠️ ⭐ THE COST, AND IT IS REAL: `forbid` makes ADDING a field to a client
⭐        request a breaking change in the other direction — an old server
⭐        rejects a new client. ⭐⭐ For an internal API, forbid. For a public
⭐        API with clients you do not control, this is a versioning decision
⭐        (Day 125), and it belongs in an ADR (Day 101).
```

# Part 4 — ⭐⭐ Validating the *output*

```python
class UserOut(BaseModel):                     # ⭐⭐ an EXPLICIT output schema
    id: int
    email: str
    created_at: datetime
    # ⭐⭐ NOTE WHAT IS ABSENT: password_hash, internal_notes, is_deleted,
    #    stripe_customer_id, the whole rest of the row.

@app.route("/users/{id:int}", response_model=UserOut)     # ⭐ the response is FILTERED
def get_user(...): return db.get_user(id)                  # ⭐ returns the full ORM object
```

```
⭐⭐ AN OUTPUT SCHEMA IS A SECURITY CONTROL, AND IT IS THE MOST UNDER-RATED ONE
⭐   IN THIS WHOLE STAGE:
⭐   ⇒ ⭐⭐ WITHOUT IT, `return user` SERIALISES WHATEVER THE MODEL HAPPENS TO
⭐        HAVE. ⭐ Today that is fine. ⭐⭐ NEXT MONTH SOMEONE ADDS
⭐        `internal_risk_score` OR `password_reset_token` TO THE TABLE, AND YOUR
⭐        PUBLIC ENDPOINT STARTS RETURNING IT — with no code change to the
⭐        endpoint, no review of the endpoint, and no test failure.
⭐   ⇒ ⭐⭐ THE OUTPUT SCHEMA MAKES THE LEAK IMPOSSIBLE BY DEFAULT: a new column
⭐        is invisible until someone deliberately adds it to `UserOut` — which is
⭐        a reviewable line in a diff (Day 100B).
⭐   ⇒ ⭐ it is also the honest source for your OpenAPI response documentation
⭐        (Day 126), so the docs cannot drift from reality.
⭐   ⇒ ⭐⭐ THIS IS DAY 090'S LAYERING AT THE OUTBOUND EDGE: the ORM model is an
⭐        internal representation, and it should never be the wire format.
```

⚠️ ⭐ **The same applies to error bodies** (Day 120): an exception's `str()` can contain a row, a query
or a filename. ⭐⭐ **Shape the error too.**

# Part 5 — ⭐ The error response, and where validation runs

```json
{
  "code": "validation_error",
  "message": "Request validation failed",
  "request_id": "01J7…",
  "errors": [
    {"field": "qty",        "code": "greater_than", "message": "must be > 0"},
    {"field": "ship_to",    "code": "too_long",     "message": "max 200 characters"},
    {"field": "emailAddres","code": "unknown_field","message": "unexpected field"}
  ]
}
```

```
⭐⭐ FOUR RULES FOR VALIDATION ERRORS:
⭐  1. ⭐⭐ RETURN **ALL** ERRORS AT ONCE, not the first. ⭐ Otherwise the client
⭐       fixes one field, resubmits, and discovers the next — ⭐⭐ a five-round
⭐       trip for a form with five mistakes.
⭐  2. ⭐ A FIELD PATH, including nested ones: `items.0.qty`.
⭐  3. ⭐⭐ A MACHINE-READABLE `code` PER ERROR. ⭐ The client branches on the
⭐       code and displays the message; ⭐⭐ making clients regex your prose is
⭐       how you can never reword an error again (Day 120).
⭐  4. ⭐⭐ NEVER ECHO THE OFFENDING VALUE BACK UNFILTERED — that reflects
⭐       attacker-controlled content into a response (Day 127), and it can echo
⭐       a password straight into a log (Day 099A).
```

```
⭐⭐ AND WHERE VALIDATION SITS IN THE STACK (Days 090, 108):
⭐        transport limits  ⇒ ⭐ nginx body size, parser limits   (Days 104, 111)
⭐        ⭐⭐ SCHEMA PARSE  ⇒ at the route boundary — 400 / 422
⭐        ⭐ AUTHORISATION   ⇒ after parsing, before the domain     (Day 118)
⭐        ⭐⭐ DOMAIN RULES  ⇒ in the service, over typed objects — 409
⭐        database constraints ⇒ ⭐ the last line, and it must exist anyway
⭐   ⇒ ⭐⭐ THE DATABASE CONSTRAINT IS NOT REDUNDANT WITH THE SCHEMA. Application
⭐        validation stops the API path; ⭐ a migration, a script, a background
⭐        job or a second service does not go through your schema. ⭐⭐ NOT NULL,
⭐        UNIQUE and CHECK are the only rules that are actually enforced.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Checking a dict and passing the dict on | ⭐⭐ Parse into a type — then the proof travels with the value. |
| Business rules in the schema | ⭐ "Only two left" depends on state. That is the domain, and a 409. |
| ⭐⭐ **`Model(**request.json)`** | ⭐⭐ Mass assignment — the client picks the fields. Explicit mapping. |
| `extra="ignore"` | ⭐⭐ Silently drops a client's typo'd field; the bug surfaces days later. |
| ⭐ A string field with no `max_length` | ⭐ Every unbounded field is a DoS. |
| No list or nesting limits | ⭐⭐ A million-item list, or a JSON bomb. |
| ⭐⭐ **Returning the ORM object directly** | ⭐⭐ A new column silently joins your public API. Use an output schema. |
| First-error-only validation | ⭐ Five round trips for five mistakes. |
| Prose-only errors | ⭐ Clients regex your messages, and you can never reword them. |
| ⭐ Echoing the bad value back | ⭐ Reflects attacker content, and can log a password. |
| Trusting the schema instead of a constraint | ⭐⭐ Migrations and background jobs do not go through it. |
| ⭐ Lax coercion in a JSON body | ⭐ `"5"` becoming `5` is convenient in a query string and surprising in JSON. |

## Interview questions

**Q: What does "parse, don't validate" mean?**
> That validation should produce a value, not just a verdict. If I check a dict and pass the same dict
> onward, the knowledge that it was checked lives in the reader's head and in the order of statements
> — so three functions later nobody knows whether `data["email"]` was validated, and they either check
> again or don't. If I parse into a typed object, the type carries the proof: a function taking
> `Email` cannot be called with an unvalidated string, and the type checker enforces it. That's
> exactly why validation belongs at the edge and everything inside can just trust — validate once,
> then trust, with the type doing the carrying.

**Q: Where's the line between validation and business rules?**
> Validation says the request is well-formed and depends only on the request, so the answer is the
> same every time — "quantity must be positive". A business rule depends on state and the answer
> changes minute to minute — "we only have two left". The first belongs in the schema at the edge and
> returns 422; the second belongs in the service layer and returns 409. Putting stock levels in a
> Pydantic model drags the database into your schema and makes it untestable, which is the practical
> reason the line matters.

**Q: What is mass assignment?**
> Constructing a model straight from the request body — `User(**request.json)` — so the client
> chooses which fields get set. They send `is_admin: true`, or `balance`, or `user_id`, and you've
> written a privilege escalation. It's the same shape as IDOR: authenticated, legitimate endpoint, and
> the bug is that the client controls something they shouldn't. The fix is an explicit allowlist, and
> a parsed request schema is one for free — the model has three fields, so exactly three fields can
> arrive. Then map onto the entity explicitly rather than splatting.

**Q: Should unknown fields be rejected?**
> Usually yes, and the underrated reason isn't security. A client that sends `emailAddress` instead of
> `email` gets a 201 and silently missing data, and the bug surfaces days later as "the emails are
> empty" with nobody suspecting a request that succeeded. `forbid` turns that into an immediate 422
> naming the field. The cost is real though: it makes adding a field on the client a breaking change
> against an older server. For an internal API I'd forbid; for a public API with clients I don't
> control, it's a versioning decision and deserves an ADR.

**Q: Why is an output schema a security control?**
> Because without one, returning the ORM object serialises whatever the model happens to have today.
> Next month someone adds `internal_risk_score` or `password_reset_token` to the table and your public
> endpoint starts returning it — with no change to the endpoint, no review of the endpoint, and no
> failing test. An explicit output model makes that impossible by default: a new column is invisible
> until someone deliberately adds it, which is a reviewable line in a diff. It's also the honest
> source for your API documentation, so the docs can't drift.

## 🎙️ Articulation drill

Record two minutes: **"How do you handle input validation?"**

⭐ **Reframe it from checking to converting, in one sentence:** **"I don't think of validation as
running checks on a dict — I think of it as parsing untrusted input into a typed object that can't be
invalid. The difference matters because if I check a dict and pass the dict on, three functions later
nobody knows whether it was checked, so they either check again or they don't."**

⭐⭐ **Then the boundary, and the distinction people get wrong:** *"it happens once, at the edge, and
everything inside trusts the type. And I'd separate it from business rules: 'quantity must be positive'
depends only on the request and is a 422; 'we only have two left' depends on state, changes minute to
minute, and belongs in the service layer as a 409. Putting stock levels in a Pydantic model drags the
database into the schema and makes it untestable."*

⭐⭐ **Then the two things people don't think of as validation:** *"first, rejecting unknown fields —
partly because it's an allowlist against mass assignment, where a client sends `is_admin: true` and
escalates themselves, but mostly because it catches client typos. Send `emailAddress` instead of
`email` with 'ignore' and you get a 201 with silently missing data, and the bug shows up days later as
'the emails are empty'. Second, validating the *output*: without an explicit response model, someone
adds `password_reset_token` to the table next month and your public endpoint starts returning it, with
no code change and no failing test."*

⭐ **Close on the limits and the last line of defence:** *"and I'd bound every field — max lengths, max
list sizes, nesting depth — because every unbounded field is a denial of service. But I'd still keep
the database constraints, because migrations, background jobs and other services don't go through my
schema. `NOT NULL` and `UNIQUE` are the only rules actually enforced."*
