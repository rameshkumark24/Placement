# Day 194 ⭐

**L-194** · 🐘 **MVCC, vacuum and bloat** — ⭐⭐ why `UPDATE` writes a new row, and the bill that follows

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: in Postgres an `UPDATE` does not update anything. It writes a new row
> version and marks the old one dead — and every operational problem in this day is the invoice for
> that one design decision.**
>
> ⭐ You have already felt it four times without naming it: the `Heap Fetches` on an index-only scan
> (Day 189), the `dirtied` buffers on a `SELECT` (Day 191), why `count(*)` cannot be cached (Day 193),
> and why a table you only ever update keeps growing. ⭐⭐ Today it becomes one mechanism.

# Part 1 — ⭐⭐ There is no update

```
⭐⭐ EVERY TUPLE CARRIES A 23-BYTE HEADER (Day 186). The two fields that
⭐   matter today:
⭐     xmin — ⭐ the transaction id that CREATED this version
⭐     xmax — ⭐ the transaction id that DELETED it (0 = still live)

⭐   UPDATE orders SET status='paid' WHERE id=7;   -- ⭐ txid 5000
⭐
⭐   BEFORE:  [id=7 status='pending'  xmin=4000 xmax=0    ]
⭐   AFTER:   [id=7 status='pending'  xmin=4000 xmax=5000 ]  ⭐⭐ DEAD
⭐            [id=7 status='paid'     xmin=5000 xmax=0    ]  ⭐⭐ LIVE
⭐
⭐⭐ SO: AN UPDATE IS AN INSERT PLUS A TOMBSTONE. A DELETE IS JUST THE
⭐   TOMBSTONE. ⭐ The old version is still physically there.
```

```
⭐⭐ WHY BUILD IT THIS WAY? Because it buys the property the whole
⭐   database rests on:
⭐   ⇒ ⭐⭐ ***READERS NEVER BLOCK WRITERS. WRITERS NEVER BLOCK READERS.***
⭐   ⭐ A long report reading `orders` sees the versions that were live
⭐     when it started, while checkouts keep writing new ones. No locks,
⭐     no waiting, no reader ever seeing a half-finished transaction.
⭐
⭐⭐ AND THE ARCHITECTURAL CONTRAST WORTH KNOWING:
⭐   ⭐ Oracle and MySQL/InnoDB update IN PLACE and keep the OLD version
⭐     in a separate UNDO LOG. ⭐⭐ THEY PAY ON READS (reconstructing old
⭐     versions) AND ON `ORA-01555 snapshot too old`.
⭐   ⭐ Postgres keeps ALL versions in the TABLE. ⭐⭐ IT PAYS BY NEEDING
⭐     SOMEONE TO COME ALONG LATER AND CLEAN UP. That someone is VACUUM,
⭐     and the entire rest of this day is about it.
⭐   ⇒ ⭐ Neither is "better". ⭐⭐ Postgres traded a read-time cost for a
⭐     maintenance-time cost, which is a good trade right up until the
⭐     maintenance stops happening.
```

```
⭐⭐ THE SIX CONSEQUENCES, AND YOU HAVE MET FOUR OF THEM ALREADY:

⭐ ① ⭐⭐ THE TABLE GROWS WHEN YOU ONLY UPDATE. Update every row of a
⭐    10 GB table once ⇒ 20 GB on disk, 10 GB of it garbage.
⭐ ② ⭐⭐ EVERY INDEX MUST GET A NEW ENTRY — because the new version has
⭐    a new physical address (ctid). ⭐ Unless HOT applies (Part 5).
⭐ ③ ⭐⭐ `count(*)` CANNOT BE CACHED (Day 193 Q4). "How many rows?"
⭐    has no single answer — it depends on YOUR snapshot.
⭐ ④ ⭐⭐ AN INDEX CANNOT ANSWER VISIBILITY (Day 189). The index entry
⭐    does not know if the row is dead, so an index-only scan must
⭐    consult the visibility map — and `Heap Fetches` is what it costs
⭐    when that map is stale.
⭐ ⑤ ⭐⭐ A `SELECT` CAN DIRTY PAGES (Day 191's `dirtied=`). The first
⭐    reader after a commit sets HINT BITS on tuples, recording "this
⭐    xmin is known committed" so future readers skip the lookup.
⭐    ⭐ Which is why the FIRST query after a bulk load is often the
⭐      slowest, and why it writes.
⭐ ⑥ ⭐ A rolled-back transaction leaves dead tuples too. ⭐⭐ ROLLBACK IS
⭐    NOT FREE — it is instant, but it left rubbish behind.
```

# Part 2 — ⭐ Snapshots: what "your transaction sees"

```
⭐⭐ A SNAPSHOT IS THREE THINGS:
⭐     xmin — the oldest transaction still running
⭐     xmax — the next transaction id not yet assigned
⭐     xip  — ⭐ the list of in-progress transaction ids
⭐
⭐⭐ A TUPLE IS VISIBLE TO YOU IF:
⭐     its xmin committed BEFORE your snapshot, AND
⭐     its xmax is 0, or is a transaction that had NOT committed.
⭐
⭐ READ COMMITTED  ⇒ ⭐⭐ A NEW SNAPSHOT PER *STATEMENT*.
⭐ REPEATABLE READ ⇒ ⭐⭐ ONE SNAPSHOT FOR THE WHOLE *TRANSACTION*.
⭐   ⇒ ⭐ That one line is the entire difference, and tomorrow (Day 195)
⭐     is what follows from it.
```

```sql
-- ⭐ Watch it directly. Two psql sessions:
-- A:  BEGIN; SELECT txid_current();  -- ⭐ 5000
-- B:  UPDATE orders SET status='x' WHERE id=7; -- commits
-- A:  SELECT status FROM orders WHERE id=7;    -- ⭐⭐ READ COMMITTED
--                                              --   sees 'x'
--     -- ⭐⭐ under REPEATABLE READ it would still see the old value
SELECT xmin, xmax, ctid, * FROM orders WHERE id = 7;
-- ⭐⭐ `ctid` = (page, item). WATCH IT CHANGE ON EVERY UPDATE. That
--    moving address is exactly why every index must be rewritten.
```

# Part 3 — ⭐⭐ Bloat: the arithmetic, and how to measure it honestly

```
⭐⭐ BLOAT = DEAD TUPLES + FREE SPACE THAT VACUUM RECLAIMED BUT NEVER
⭐   RETURNED TO THE OPERATING SYSTEM.

⭐   ⭐⭐ THE SYMPTOM SET — recognise these as ONE disease:
⭐     ⭐ the table is 40 GB and `count(*)` says 12 million small rows
⭐     ⭐ a seq scan reads 5× the pages it should
⭐     ⭐ ⭐⭐ AN INDEX SCAN GOT SLOWER OVER MONTHS WITH NO CODE CHANGE
⭐     ⭐ shared buffers hold mostly dead rows, so your cache hit rate
⭐       fell and nobody changed anything
⭐     ⭐ a `VACUUM FULL` on staging "fixed it" and everyone moved on
```

```sql
-- ⭐ THE QUICK CHECK — dead vs live, per table:
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1)
         AS dead_pct,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;
-- ⭐⭐ OVER ~20% DEAD ON A BIG HOT TABLE IS WHERE YOU START LOOKING.

-- ⭐ THE ACCURATE CHECK (slow — it reads the table):
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstattuple('orders');       -- ⭐ exact
SELECT * FROM pgstattuple_approx('orders');-- ⭐⭐ sampled, use this one
-- ⭐ And for indexes: `pgstatindex('idx_name')` → `avg_leaf_density`.
--   ⭐⭐ Below ~50% means the index is carrying twice the pages it needs.
```

# Part 4 — ⭐⭐ VACUUM: what it does, what it does *not*, and why yours isn't running

```
⭐⭐ WHAT `VACUUM` DOES — four jobs, and only the first is famous:
⭐   ① marks dead tuple space REUSABLE by future inserts on that table
⭐   ② ⭐⭐ UPDATES THE VISIBILITY MAP ⇒ enables index-only scans
⭐        (Day 189's `Heap Fetches: 0`)
⭐   ③ ⭐⭐ FREEZES OLD TUPLES ⇒ prevents wraparound (Part 6)
⭐   ④ updates the free space map, and can update statistics if you say
⭐        `VACUUM ANALYZE`

⭐⭐ WHAT IT DOES ***NOT*** DO:
⭐   ⭐⭐ IT DOES NOT RETURN DISK TO THE OPERATING SYSTEM. Your 40 GB
⭐     table stays 40 GB; the space is reusable, not released.
⭐     ⭐ (Exception: trailing empty pages at the very end of the file.)

⭐⭐ `VACUUM FULL` DOES RETURN THE SPACE — by REWRITING THE ENTIRE TABLE.
⭐   ⭐⭐ IT TAKES AN ACCESS EXCLUSIVE LOCK FOR THE WHOLE REWRITE.
⭐     ⇒ ⭐⭐ ON A 200 GB TABLE THAT IS AN HOUR OF TOTAL OUTAGE, plus you
⭐       need 200 GB of free disk to do it. ⭐ Day 138's lock queue makes
⭐       it worse: everything piles up behind it.
⭐   ⇒ ⭐⭐ USE `pg_repack` INSTEAD — it does the same rewrite ONLINE,
⭐     using triggers and a swap, taking the exclusive lock only for a
⭐     moment at the end. ⭐ This is the answer expected of someone who
⭐     has actually operated a database.
```

```
⭐⭐ AUTOVACUUM, AND THE DEFAULT THAT BREAKS ON BIG TABLES:

⭐   TRIGGER = autovacuum_vacuum_threshold          (default 50)
⭐           + autovacuum_vacuum_scale_factor × n_live_tup  (default 0.2)
⭐
⭐   ⭐ 1,000-row table   ⇒ vacuum after ~250 dead rows.      Fine.
⭐   ⭐⭐ 100,000,000-ROW TABLE ⇒ VACUUM AFTER ***20 MILLION***
⭐      DEAD ROWS. ⭐⭐ SO YOUR BIGGEST, HOTTEST TABLE IS THE ONE
⭐      AUTOVACUUM VISITS LEAST OFTEN — exactly backwards.
⭐   ⇒ ⭐⭐ THE FIX IS PER-TABLE, AND IT BELONGS IN A MIGRATION:
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor  = 0.01,   -- ⭐ 1%
    autovacuum_vacuum_threshold     = 10000,
    autovacuum_analyze_scale_factor = 0.005,  -- ⭐ stats matter more
    autovacuum_vacuum_cost_delay    = 2       -- ⭐ let it work faster
);
```

```
⭐⭐ AND WHY IT IS TOO SLOW EVEN WHEN IT RUNS: THE COST LIMIT.
⭐   Autovacuum deliberately throttles itself: it accumulates "cost"
⭐   per page and SLEEPS when it hits `autovacuum_vacuum_cost_limit`
⭐   (default 200) — ⭐⭐ WHICH IS SHARED ACROSS ALL AUTOVACUUM WORKERS.
⭐   ⇒ ⭐⭐ ON MODERN HARDWARE THE DEFAULT IS ABSURDLY CONSERVATIVE — it
⭐     was tuned for spinning disks. Raising `cost_limit` to 1000–2000
⭐     and dropping `cost_delay` to 2 ms is one of the highest-value
⭐     changes on a busy database, and almost nobody makes it.
⭐   ⭐ Also raise `autovacuum_max_workers` only WITH the cost limit —
⭐     more workers sharing the same budget just makes each one slower.
```

# Part 5 — ⭐⭐ The three things that stop vacuum dead

```
⭐⭐ VACUUM CANNOT REMOVE A DEAD TUPLE IF ***ANY*** TRANSACTION MIGHT
⭐   STILL NEED TO SEE IT. That boundary is the ***xmin horizon***, and
⭐   it is set by the oldest thing holding a snapshot ANYWHERE.

⭐ ① ⭐⭐ A LONG-RUNNING OR IDLE-IN-TRANSACTION SESSION.
⭐    ⭐⭐ ONE FORGOTTEN `BEGIN;` IN A PSQL WINDOW, OR ONE SQLALCHEMY
⭐      SESSION LEFT OPEN BY A CRASHED WORKER, ⭐⭐ STOPS VACUUM FROM
⭐      CLEANING ***EVERY TABLE IN THE DATABASE***.
⭐    ⭐ Not that table. The database. For as long as it is open.
⭐    ⇒ ⭐⭐ THIS IS THE #1 CAUSE OF MYSTERIOUS BLOAT, AND IT IS ALMOST
⭐      ALWAYS AN APPLICATION BUG, NOT A DATABASE ONE.
⭐ ② ⭐⭐ A REPLICATION SLOT WITH NO CONSUMER. An inactive slot pins the
⭐    horizon forever AND retains WAL until the disk fills.
⭐    ⭐ The classic: a replica was decommissioned, the slot was not.
⭐ ③ ⭐ A PREPARED TRANSACTION (two-phase commit) nobody committed.
⭐    ⭐⭐ `max_prepared_transactions > 0` with a framework that crashed
⭐      mid-2PC. Check `pg_prepared_xacts`; it is almost always garbage.
```

```sql
-- ⭐⭐ THE THREE QUERIES TO RUN WHEN BLOAT MAKES NO SENSE:
SELECT pid, state, now() - xact_start AS txn_age, query
FROM pg_stat_activity
WHERE state IN ('idle in transaction','active')
  AND xact_start < now() - interval '5 minutes'
ORDER BY xact_start;                        -- ⭐ ①

SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
FROM pg_replication_slots;                  -- ⭐ ②  active=false is bad

SELECT * FROM pg_prepared_xacts;            -- ⭐ ③  should be empty
```

```
⭐⭐ THE APPLICATION-SIDE FIX, WHICH IS THE ONE THAT ACTUALLY WORKS:
⭐   ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
⭐   ⭐⭐ THIS IS NOT A HACK. It is a statement that no legitimate
⭐     transaction in an OLTP application stays open a minute doing
⭐     nothing. ⭐ Set `statement_timeout` too (Day 152's timeout
⭐     hierarchy, now at the database layer).
⭐   ⭐ In Python: the SQLAlchemy session that opened a transaction and
⭐     then called a slow HTTP API is Day 172's "never hold a
⭐     transaction across I/O" — ⭐⭐ and THIS is the cost you were being
⭐     warned about.
```

```
⭐⭐ HOT UPDATES AND FILLFACTOR — the way to make the whole problem
⭐   smaller instead of cleaning up after it:
⭐   ⭐ A HOT update writes the new version ON THE SAME PAGE and updates
⭐     NO indexes — the old tuple points at the new one.
⭐   ⭐ REQUIRES: ⭐⭐ no indexed column changed, AND free space on the
⭐     page.
⭐   ⇒ ⭐⭐ `ALTER TABLE orders SET (fillfactor = 85);` leaves 15% of
⭐     each page empty ON PURPOSE so updates can stay local. ⭐ For a
⭐     heavily-updated table this can cut index writes dramatically.
⭐   ⭐ Check it: `n_tup_hot_upd / n_tup_upd` in `pg_stat_user_tables`.
⭐     ⭐⭐ Below ~50% on an update-heavy table means you are paying for
⭐       index maintenance you could avoid — either by fillfactor or by
⭐       dropping the index on the column that keeps changing (Day 189).
```

# Part 6 — ⭐⭐ Transaction ID wraparound: the outage class with a name

```
⭐⭐ TRANSACTION IDS ARE 32-BIT. ~4.2 BILLION, AND POSTGRES USES HALF
⭐   THE SPACE IN EACH DIRECTION — so ~2 BILLION transactions of
⭐   headroom before "in the past" wraps around to "in the future" and
⭐   ⭐⭐ COMMITTED DATA WOULD SILENTLY BECOME INVISIBLE.

⭐ THE DEFENCE: ⭐ FREEZING. Vacuum stamps very old tuples as "visible to
⭐   everyone, forever", removing them from the xid comparison entirely.
⭐
⭐⭐ THE ESCALATION LADDER, WHICH YOU WILL SEE IN LOGS BEFORE YOU SEE AN
⭐   OUTAGE:
⭐   ⭐ ~200M xids old  → autovacuum starts an ANTI-WRAPAROUND VACUUM
⭐        ⭐⭐ WHICH WILL NOT BACK OFF. It ignores cost delays and it
⭐        CANNOT BE SKIPPED — ⭐ so a table you never vacuumed suddenly
⭐        gets a full scan at the worst possible moment.
⭐   ⭐ ~40M remaining  → `WARNING: database "x" must be vacuumed within
⭐        40000000 transactions` in every log line
⭐   ⭐ ~1M remaining   → ⭐⭐ ***THE DATABASE REFUSES ALL WRITES.***
⭐        Read-only. Single-user mode to recover. Hours of downtime.
⭐
⭐⭐ THIS IS THE OUTAGE THAT TOOK DOWN SENTRY AND MAILCHIMP PUBLICLY,
⭐   AND IT IS 100% PREVENTABLE BY ONE MONITORING QUERY:
SELECT datname, age(datfrozenxid) AS xid_age,
       round(100.0 * age(datfrozenxid) / 2000000000, 1) AS pct_to_wrap
FROM pg_database ORDER BY xid_age DESC;
-- ⭐⭐ ALERT AT 50%. INVESTIGATE AT 25%. ⭐ Put this in your Day 147
--    metrics as a gauge; it is the single most important database
--    gauge that most teams do not have.
-- ⭐ Per-table: age(relfrozenxid) from pg_class.
```

```
⭐⭐ WHAT ACTUALLY CAUSES IT — never "too many transactions". Always one
⭐   of the three blockers from Part 5, left alone for weeks. ⭐ Which
⭐   means the wraparound alert and the bloat investigation are the SAME
⭐   investigation.
⭐ ⭐ PG 14+ softens this: the failsafe disables cost delays automatically,
⭐   and `vacuum_failsafe_age` exists. ⭐⭐ It buys time; it does not
⭐   remove the need to watch the gauge.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Thinking `UPDATE` modifies a row | It writes a new version and tombstones the old. |
| Assuming `ROLLBACK` is free | Instant, but it left dead tuples behind. |
| Expecting `VACUUM` to shrink the file | It makes space reusable, not returned. |
| Running `VACUUM FULL` on a big live table | ACCESS EXCLUSIVE for the whole rewrite, plus double the disk. Use `pg_repack`. |
| Leaving autovacuum defaults on a 100M-row table | 0.2 scale factor means 20 million dead rows before it triggers. |
| Raising `autovacuum_max_workers` alone | They share one cost budget; each just gets slower. |
| Leaving `autovacuum_vacuum_cost_limit` at 200 | Tuned for spinning disks. 1000–2000 on modern storage. |
| Hunting bloat in the table when a session is idle in transaction | One open transaction stops vacuum for the entire database. |
| Leaving a replication slot after decommissioning a replica | It pins the xmin horizon and retains WAL until the disk fills. |
| Not setting `idle_in_transaction_session_timeout` | No OLTP transaction legitimately sits open for a minute. |
| Indexing a frequently-updated column | It disables HOT, so every update writes every index. |
| Ignoring `n_tup_hot_upd / n_tup_upd` | Below 50% on an update-heavy table means avoidable index writes. |
| Treating wraparound as a "too many transactions" problem | It's always a blocked vacuum left alone for weeks. |
| Having no `age(datfrozenxid)` alert | It's the most important database gauge most teams don't have. |

## Interview questions

**Q: What happens physically when you run an `UPDATE` in Postgres?**

> Nothing is updated. Postgres writes a new tuple with the new values, sets `xmin` to the current
> transaction id, and stamps `xmax` on the old version to mark when it died — so an `UPDATE` is an
> insert plus a tombstone and a `DELETE` is just the tombstone. That's multi-version concurrency
> control, and what it buys is the property the whole database rests on: readers never block writers
> and writers never block readers, because a long report just keeps reading the versions that were
> live when its snapshot was taken. The architectural contrast is worth stating — Oracle and InnoDB
> update in place and keep old versions in an undo log, so they pay at read time reconstructing them
> and they have "snapshot too old" errors. Postgres keeps every version in the table and pays by
> needing someone to clean up afterwards. That's a good trade right up until the cleanup stops
> happening, which is what vacuum, bloat and wraparound are all about.

**Q: What is bloat and how do you fix it?**

> Dead tuples plus space that vacuum reclaimed but never returned to the operating system. It shows up
> as a table far larger than its row count justifies, sequential scans reading several times the pages
> they should, index scans that got slower over months with no code change, and a cache hit rate that
> fell because shared buffers are full of dead rows. I'd measure with `pg_stat_user_tables` for a quick
> dead-tuple percentage and `pgstattuple_approx` for a real number, and `pgstatindex` for
> `avg_leaf_density` on the indexes. The fix depends on the cause. If autovacuum simply isn't keeping
> up, that's per-table settings — the default scale factor of 0.2 means a hundred-million-row table
> waits for twenty million dead rows, so your biggest, hottest table is the one autovacuum visits
> least, which is exactly backwards. If the space has to be returned, `VACUUM FULL` rewrites the table
> under an ACCESS EXCLUSIVE lock, which on a large table is an outage, so I'd use `pg_repack`, which
> does the same rewrite online and takes the exclusive lock only briefly at the end.

**Q: Autovacuum is running but bloat keeps growing. What's happening?**

> Something is pinning the xmin horizon, so vacuum is running and finding nothing it's allowed to
> remove — it can't reclaim a tuple that any transaction might still need to see. There are three
> causes and I'd check all three. First, a long-running or idle-in-transaction session: one forgotten
> `BEGIN` in a psql window, or a SQLAlchemy session left open by a crashed worker, blocks cleanup for
> *every table in the database*, not just the one it touched. That's the most common cause by a wide
> margin and it's an application bug, not a database one. Second, a replication slot with no consumer
> — usually a replica that was decommissioned while its slot wasn't — which pins the horizon and
> retains WAL until the disk fills. Third, an abandoned prepared transaction in `pg_prepared_xacts`.
> The durable fix for the first is `idle_in_transaction_session_timeout`, which isn't a hack: no
> legitimate OLTP transaction sits open for a minute doing nothing.

**Q: Explain transaction ID wraparound.**

> Transaction ids are 32-bit, and Postgres treats half the space as past and half as future, so
> there's about two billion transactions of headroom before old committed data would appear to be in
> the future and become invisible. The defence is freezing — vacuum stamps sufficiently old tuples as
> visible to everyone forever, taking them out of the comparison. The escalation is what makes it an
> operational story: around two hundred million transactions of age, autovacuum launches an
> anti-wraparound vacuum that ignores cost delays and can't be skipped, so a table you never vacuumed
> suddenly gets a full scan at the worst possible time; then warnings in every log line; and around a
> million remaining, the database refuses all writes and needs single-user mode to recover. It's taken
> down well-known companies publicly and it's entirely preventable with one gauge — `age(datfrozenxid)`
> as a percentage of two billion, alerting at fifty percent. And the cause is never "too many
> transactions", it's always one of the three vacuum blockers left alone for weeks, which means the
> wraparound alert and the bloat investigation are the same investigation.

**Q: What's a HOT update and why should I care?**

> A heap-only tuple update — Postgres writes the new version on the same page and updates no indexes
> at all, with the old tuple pointing forward to the new one. It requires two things: no indexed column
> changed, and free space on that page. That's why it connects two things I'd otherwise treat
> separately. It's the reason indexing a column that changes on every update, like `updated_at`, is
> expensive out of proportion to the index itself — it disables HOT for the whole table, so every
> update writes every index. And it's why `fillfactor` exists: setting it to 85 deliberately leaves
> fifteen percent of each page empty so updates can stay local, which on an update-heavy table cuts
> index write volume substantially. You can check whether you're getting it from
> `n_tup_hot_upd` over `n_tup_upd` in `pg_stat_user_tables`; well under half on a hot table means
> you're paying for index maintenance you could design away.

## Mini task

1. ⭐ `SELECT xmin, xmax, ctid, * FROM t WHERE id=1`, run three updates, and watch `ctid` and `xmin` change each time.
2. ⭐⭐ Update every row of a 1M-row table once and compare `pg_total_relation_size` before and after. Then `VACUUM` and compare again — confirm the file didn't shrink.
3. ⭐ `VACUUM FULL` it and confirm the file *did* shrink. Watch `pg_locks` from another session during the rewrite.
4. ⭐⭐ Open `BEGIN;` in one session and leave it. In another, update and vacuum a table repeatedly. Prove `n_dead_tup` never drops. Close the first session and vacuum again.
5. ⭐⭐ Do #4 from Python: open a SQLAlchemy session, run one query, don't commit, and sleep. Then find your own pid in `pg_stat_activity` as `idle in transaction`.
6. ⭐ Set `idle_in_transaction_session_timeout = '10s'` and reproduce #5. Read the error your application receives.
7. ⭐⭐ Compute the autovacuum trigger point for a table with 80M live rows at default settings. Then set per-table parameters and verify with `pg_stat_user_tables` that vacuums become frequent.
8. ⭐ Install `pgstattuple`, measure a bloated table exactly and approximately, and compare the runtimes.
9. ⭐⭐ Check `avg_leaf_density` on your capstone's busiest index. If under 50%, `REINDEX CONCURRENTLY` and re-measure.
10. ⭐⭐ Measure `n_tup_hot_upd / n_tup_upd` on an update-heavy table. Add an index on the updated column and re-measure. Then set `fillfactor = 85`, rewrite, and measure a third time.
11. ⭐ Run the `age(datfrozenxid)` query. Turn it into a Prometheus gauge in your capstone (Day 147).
12. ⭐⭐ Create a replication slot with no consumer, write for a while, and watch `pg_wal_lsn_diff` and `n_dead_tup` both grow. Drop the slot and confirm both recover.

## 🎙️ Articulation drill

**Two minutes: "Why does Postgres need vacuum?"**

Start with the mechanism, not the maintenance: an `UPDATE` writes a new row version and tombstones the
old one, which is what makes readers never block writers — and the price is that somebody has to clean
up the old versions later. Contrast with undo logs in one sentence so it's clearly a trade rather than
a flaw. Then the four jobs of vacuum, and make sure to say the one people don't know: it maintains the
visibility map, which is what makes index-only scans possible. Then the operational half, which is
where the experience shows. Give the autovacuum arithmetic — **a 0.2 scale factor means a
hundred-million-row table waits for twenty million dead rows, so the biggest hottest table is the one
it visits least** — and then the diagnosis people miss: if bloat grows while autovacuum runs, something
is pinning the xmin horizon, and **one idle-in-transaction session blocks cleanup for every table in
the database**. Close on wraparound: two billion transactions, the database goes read-only, it has taken
down real companies, and it's one gauge away from impossible.
