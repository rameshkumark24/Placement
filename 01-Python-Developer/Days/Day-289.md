# Day 289 🏗️

**P-289** · 🏗 **Two data models in one system** — ⭐⭐ and a decision you can reproduce in March

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a decision made on 20 May must still be explainable in November against
> the rules that were in force on 20 May — which means you store the inputs and the rule version with
> the decision, because recomputing it later answers a different question.**
>
> ⭐ Day 250 derived a domain model from invariants. ⭐⭐ Today there are *two* models with
> completely different rules — structured facts, and a versioned corpus — and the interesting failure
> is what happens to each when time passes.

# Part 1 — ⭐⭐ Two models, and why they don't merge

```
⭐⭐ | ⭐ THE FACTS                | ⭐ THE CORPUS              |
⭐   | applications, limits,      | policy documents, sections|
⭐   | thresholds, entities       | versions, effective dates |
⭐   | ⭐ relational, constrained  | ⭐ documents + chunks      |
⭐   | ⭐⭐ EXACT                   | ⭐⭐ RETRIEVED BY SIMILARITY|
⭐   | wrong = a bug              | ⭐ wrong = "not retrieved" |
⭐   | tested by assertion        | ⭐⭐ MEASURED BY recall@k   |

⭐⭐ THE MISTAKE THAT COSTS THE MOST: PUTTING THE FACTS IN THE
⭐   VECTOR STORE BECAUSE IT IS ALREADY THERE.
⭐   ⭐ "What is the leave limit for contractors?" then becomes a
⭐     SIMILARITY SEARCH over a sentence containing a number.
⭐   ⇒ ⭐⭐ SIMILARITY IS NOT LOOKUP. It returns the passage most
⭐     like your question, and a passage about the *previous*
⭐     limit, or a neighbouring category's limit, is extremely
⭐     similar. ⭐⭐ YOU WILL GET A NUMBER. IT WILL BE WRONG
⭐     ABOUT 8% OF THE TIME, AND YOU WILL NEVER FIND OUT WHICH 8%.
⭐   ⇒ ⭐ Numbers that decisions depend on live in COLUMNS.
```

# Part 2 — ⭐⭐ Effective dating, which is the whole facts model

```
⭐⭐ THE NAIVE TABLE, AND THE BUG IT GUARANTEES:
⭐   thresholds(category, max_days)          -- ⭐ one row per category
⭐   ⇒ ⭐ The policy changes on 1 June. You `UPDATE` the row.
⭐   ⇒ ⭐⭐ EVERY DECISION YOU EVER MADE BEFORE 1 JUNE NOW
⭐     EXPLAINS ITSELF WITH THE WRONG NUMBER.
⭐   ⭐ Day 187's snapshot-versus-current, arriving with legal
⭐     consequences instead of a wrong revenue chart.
```

```sql
CREATE TABLE thresholds (
  category     text        NOT NULL,
  max_days     int         NOT NULL,
  valid_from   date        NOT NULL,
  valid_to     date,                        -- ⭐ NULL = still in force
  during       daterange   GENERATED ALWAYS AS
                 (daterange(valid_from, valid_to)) STORED,
  EXCLUDE USING gist (category WITH =, during WITH &&)   -- ⭐⭐ Day 187
);
```

```
⭐⭐ THE `EXCLUDE` CONSTRAINT IS DOING REAL WORK: it makes
⭐   OVERLAPPING VERSIONS OF THE SAME RULE ***IMPOSSIBLE***.
⭐   ⇒ ⭐ Without it, two rows both claim to be in force on
⭐     3 June, your query returns two answers, and your code
⭐     silently takes the first — ⭐⭐ ORDERED BY WHATEVER THE
⭐     PLANNER FELT LIKE THAT DAY.

⭐⭐ AND THE QUERY IS NOW ALWAYS ASKED "AS OF" SOMETHING:
⭐   WHERE category = :c AND during @> :as_of_date
⭐   ⇒ ⭐ Which forces the question the whole day turns on:
⭐     ⭐⭐ ***AS OF WHEN DO YOU WANT THE ANSWER?***
```

```
⭐⭐ TWO TIME AXES, AND CONFLATING THEM IS THE CLASSIC ERROR:
⭐   ⭐ VALID TIME — when the rule was IN FORCE in the world
⭐   ⭐ TRANSACTION TIME — when your system KNEW about it
⭐   ⇒ ⭐⭐ THEY DIFFER WHENEVER SOMETHING IS BACKDATED, and
⭐     backdating always happens: a policy signed in July,
⭐     effective from April, entered in August.
⭐   ⇒ ⭐ "What did we decide?" is transaction time.
⭐     "What SHOULD we have decided?" is valid time.
⭐     ⭐⭐ AN AUDIT ASKS THE FIRST. A CORRECTION ASKS THE
⭐       SECOND. ⭐ You need both, and you need to know which
⭐       question you are answering.
```

# Part 3 — ⭐⭐ The decision record, which is the real product

```
⭐⭐ THE TEMPTING DESIGN: store the verdict, recompute the
⭐   explanation on demand.
⭐   ⇒ ⭐⭐ IT IS WRONG, AND IT IS WRONG IN A WAY THAT LOOKS
⭐     CORRECT FOR MONTHS: recomputation uses TODAY'S rules,
⭐     TODAY'S code, and TODAY'S corpus — so your explanation
⭐     drifts away from your verdict, silently, and the two
⭐     disagree exactly when someone finally reads them.
```

```
⭐⭐ STORE THE DECISION AS AN ***IMMUTABLE, SELF-CONTAINED
⭐   RECORD***:
⭐   ⭐ the INPUTS, exactly as supplied (a JSON snapshot)
⭐   ⭐ the `as_of` DATE used
⭐   ⭐⭐ the RULE-SET VERSION (a hash or version id)
⭐   ⭐ the OUTCOME and the reason codes
⭐   ⭐⭐ the FULL TRACE — which rules fired, in order (Day 290)
⭐   ⭐ the CITATIONS: document id + version + section, ⭐⭐ NOT
⭐     a chunk id, because chunks are re-created on reindex
⭐   ⭐ the code version, and the model + prompt version if a
⭐     model touched the explanation
⭐   ⇒ ⭐⭐ THE TEST OF THIS DESIGN, AND IT IS A REAL TEST YOU
⭐     WRITE: ***DELETE THE RULES TABLE, RESTORE A DECISION
⭐     FROM SIX MONTHS AGO, AND EXPLAIN IT.*** If you cannot,
⭐     the record is incomplete.
```

```
⭐ ⭐ AND IT MUST BE APPEND-ONLY. ⭐⭐ A CORRECTION IS A NEW
⭐   DECISION THAT SUPERSEDES THE OLD ONE, never an `UPDATE`.
⭐   ⇒ ⭐ Because the question is not only "what is right now"
⭐     but "what did we tell them, and when did we change our
⭐     mind" — ⭐⭐ AND AN `UPDATE` DESTROYS THE ONLY EVIDENCE
⭐     THAT THE SECOND QUESTION HAS AN ANSWER.
```

# Part 4 — ⭐⭐ The corpus model

```
⭐⭐ FOUR LEVELS, AND EACH EXISTS FOR A SPECIFIC REASON:
⭐   ⭐ DOCUMENT   — the stable thing a human names
⭐   ⭐ VERSION    — ⭐⭐ effective_from / effective_to, plus
⭐        `supersedes`. ⭐ A policy is not edited; it is REPLACED.
⭐   ⭐ SECTION    — the structural unit a citation points at
⭐        ⇒ ⭐⭐ CITATIONS POINT HERE. Stable across reindexing.
⭐   ⭐ CHUNK      — the retrieval unit (Day 292)
⭐        ⇒ ⭐⭐ DISPOSABLE BY DESIGN. Re-chunk whenever you
⭐          like; nothing durable may reference a chunk id.

⭐⭐ THE RULE THAT SAVES YOU A REWRITE:
⭐   ***CITE SECTIONS. CHUNKS ARE AN IMPLEMENTATION DETAIL.***
⭐   ⇒ ⭐ Change your chunk size in month three — a decision
⭐     that WILL happen (Day 292) — and every stored citation
⭐     pointing at a chunk id becomes a dangling reference.
```

```
⭐⭐ THE METADATA THAT DETERMINES WHETHER RETRIEVAL CAN WORK AT
⭐   ALL — decided now, because retrofitting it means reindexing:
⭐   ⭐ source, document version, effective range
⭐   ⭐ jurisdiction / applicability
⭐   ⭐⭐ ACCESS LEVEL
⭐   ⭐ content hash (Day 292's incremental ingestion)
```

# Part 5 — ⭐⭐ Access control, with the severity turned up

```
⭐⭐ DAY 269 SAID THE TENANT FILTER MUST BE ***IN*** THE QUERY.
⭐   ⭐ Here it is worse, and the reason is mechanical:
⭐   ⇒ ⭐⭐ A CHUNK RETRIEVED IS A CHUNK IN THE PROMPT IS A CHUNK
⭐     IN THE ANSWER. ⭐ There is no "we fetched it but didn't
⭐     show it". The moment an unauthorised passage enters the
⭐     context window, ⭐⭐ IT IS AVAILABLE TO BE PARAPHRASED,
⭐     SUMMARISED AND QUOTED — and it will be, because that is
⭐     precisely what the system is for.

⭐⭐ SO: FILTER ***BEFORE*** THE SEARCH, IN THE INDEX.
⭐   ⭐ Pre-filter on `access_level` and `jurisdiction`, then
⭐     search within the permitted set.
⭐   ⭐⭐ POST-FILTERING IS NOT A CONTROL — it is a redaction
⭐     after the disclosure, and it breaks `k` as well: you
⭐     asked for 10, you can show 3.
⭐   ⭐ Separate indexes or namespaces per access tier is the
⭐     stronger version, and worth it when the tiers are few.

⭐ ⭐ AND THE TEST, WHICH IS THE HIGHEST-VALUE ONE IN THIS
⭐   PROJECT: ⭐⭐ SEED A RESTRICTED DOCUMENT CONTAINING A
⭐   UNIQUE NONSENSE TOKEN, ASK 50 QUESTIONS AS AN
⭐   UNAUTHORISED USER, AND ASSERT THE TOKEN NEVER APPEARS IN
⭐   ANY ANSWER, ANY CITATION, OR ANY LOG.
```

# Part 6 — ⭐ Deletion, supersession and drift

```
⭐   ⭐ SUPERSEDED ≠ DELETED. ⭐⭐ THE OLD VERSION MUST REMAIN,
⭐     because a decision from April is explained by April's
⭐     text. ⭐ But it must be EXCLUDED from retrieval by
⭐     default, or you cite repealed policy with total
⭐     confidence — ⭐⭐ WHICH IS THE MOST DAMAGING SINGLE
⭐     FAILURE THIS SYSTEM HAS.
⭐   ⇒ ⭐ So retrieval always filters on the effective range,
⭐     and the `as_of` date flows from the question all the way
⭐     into the vector query. ⭐⭐ SAME PARAMETER, BOTH MODELS.

⭐   ⭐ ACTUAL DELETION (an erasure request, a document
⭐     published in error) reaches: the source, the chunks, the
⭐     VECTORS, the caches, and any provider-side logs (Day 267's
⭐     four deletes, now five).
⭐   ⭐⭐ EMBEDDING DRIFT: change the embedding model and every
⭐     vector in the store is in a different space.
⭐     ⇒ ⭐⭐ STORE THE MODEL ID ***WITH EVERY VECTOR***, refuse
⭐       to mix, and treat reindexing as a routine operation
⭐       with a runbook — ⭐ not as a project you dread.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Putting exact numbers in the vector store | Similarity is not lookup; you'll get a plausible neighbouring number. |
| `UPDATE`ing a threshold when policy changes | Every past decision now explains itself with the wrong number. |
| No exclusion constraint on validity ranges | Two rows in force at once, and your code takes whichever the planner returned first. |
| Querying without an `as_of` date | You answered a different question from the one asked. |
| Conflating valid time and transaction time | Audits and corrections need different axes, and backdating always happens. |
| Recomputing the explanation on demand | It drifts from the verdict silently and disagrees when someone finally reads it. |
| A decision record without the inputs | You cannot replay it, so you cannot backtest a rule change (Day 291). |
| Omitting the rule-set version | "Which rules decided this?" becomes unanswerable. |
| Mutable decision records | A correction is a new decision; an `UPDATE` destroys the only evidence you changed your mind. |
| Citing chunk ids | Reindexing turns every stored citation into a dangling reference. |
| Deciding metadata later | Retrofitting it means reindexing the corpus. |
| Post-filtering search results by access level | Redaction after disclosure, and it breaks `k`. |
| Leaving superseded documents in the retrievable set | You cite repealed policy with total confidence. |
| Deleting a document without its vectors | It is still retrievable, still quotable, still in the answer. |
| Mixing embedding models in one index | The vectors are in different spaces; store the model id with each. |
| Building a knowledge graph first | A second extraction pipeline with its own accuracy problem. |

## Interview questions

**Q: Why are there two data models?**

> Because exact facts and retrievable text have opposite properties. Thresholds and eligibility rules
> live in constrained relational columns where wrong means a bug and correctness is asserted; policy
> text lives in a versioned corpus where wrong means "not retrieved" and quality is measured by
> recall. The expensive mistake is putting the facts in the vector store because it's already there —
> then "what is the limit for contractors" becomes a similarity search, and a passage about the
> previous limit or a neighbouring category is extremely similar. You get a number, it's wrong some
> of the time, and you never learn which times.

**Q: How do you handle a policy change?**

> By never updating in place. Rules and document versions are effective-dated with a validity range,
> and an exclusion constraint makes overlapping versions of the same rule impossible — without that,
> two rows both claim to be in force and the code silently takes whichever came back first. Every
> query then carries an `as_of` date, which forces the right question: as of when do you want the
> answer? I'd also separate valid time from transaction time, because backdating always happens — a
> policy signed in July, effective from April, entered in August — and an audit asks what we decided
> while a correction asks what we should have decided.

**Q: Someone asks in November why something was declined in March. What do you show them?**

> A stored, immutable decision record: the inputs exactly as supplied, the `as_of` date, the rule-set
> version, the outcome and reason codes, the full trace of which rules fired in order, and citations
> to document sections with their versions. Not a recomputation — recomputing uses today's rules,
> today's code and today's corpus, so the explanation drifts away from the verdict silently and the
> two disagree precisely when someone finally reads them. The test I'd write is deliberately brutal:
> drop the rules table, restore a six-month-old decision, and explain it. If you can't, the record is
> incomplete.

**Q: Why cite sections rather than chunks?**

> Because chunks are disposable by design. I will change chunk size or strategy in month three —
> that's a near-certainty, not a risk — and every stored citation pointing at a chunk id becomes a
> dangling reference. Sections are the structural unit a human recognises and they survive
> reindexing, so citations point there and chunks stay an implementation detail nothing durable
> references.

**Q: How does document access control work?**

> Pre-filtered in the index, never after. The mechanical reason is that a chunk retrieved is a chunk
> in the prompt is a chunk in the answer — there's no "we fetched it but didn't show it", because
> paraphrasing retrieved text is exactly what the system does. So filtering afterwards is a redaction
> after the disclosure, and it also breaks `k`: you asked for ten and can show three. The test is to
> seed a restricted document containing a unique nonsense token and assert it never appears in any
> answer, citation or log across fifty unauthorised queries.

## 🎙️ Articulation drill

**Three minutes: "How is the data modelled?"**

Start with the split and why it isn't arbitrary: **exact facts and retrievable text have opposite
properties**, so thresholds live in constrained columns and policy text lives in a versioned corpus —
and name the expensive mistake, which is putting numbers in the vector store because it's already
there. **Similarity is not lookup**: a passage about last year's limit is extremely similar to one
about this year's, so you get a number that's wrong some of the time and you never learn which times.
Then effective dating, and give the constraint rather than the intention: validity ranges with an
exclusion constraint, **so two versions of the same rule cannot both be in force** — without it your
code takes whichever row the planner returned. Every query carries an `as_of` date, and mention both
time axes, because backdating always happens. Then the piece that makes it defensible: **an immutable
decision record storing the inputs, the rule-set version, the trace and section-level citations —
never a recomputation**, because recomputation uses today's rules and drifts away from the verdict
silently. Give the test: drop the rules table, restore a six-month-old decision, explain it. Close on
access control with its mechanical reason: **a chunk retrieved is a chunk in the prompt is a chunk in
the answer**, so the filter goes inside the search and the proof is a nonsense token in a restricted
document that must never appear in any answer, citation or log.
