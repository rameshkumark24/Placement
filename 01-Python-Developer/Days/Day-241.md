# Day 241 📊

**P-241** · 📊 **Frontend performance** — ⭐⭐ why your p99 said 40 ms and the user waited 3 seconds

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: your server metrics measure the part of the wait you are responsible for
> and not the part the user experiences — DNS, TLS, the HTML, the bundle, the parse, the render and a
> waterfall of dependent requests all happen outside your histogram, and together they are usually the
> majority of the time.**
>
> Today: ⭐ the three vitals that matter, ⭐⭐ the critical path, field vs lab data, and the budget.

---

# Part 1 — ⭐⭐ Where the three seconds went

```
⭐⭐ YOUR API: 40 ms. THE USER: 2.8 s. THE ACCOUNTING:

⭐   DNS + TCP + TLS ................  300 ms  ⭐ invisible to you
⭐   HTML (TTFB) ....................  150 ms
⭐   ⭐⭐ JS BUNDLE DOWNLOAD (600 KB) .. 1,200 ms  ⭐ ON 4G. THE BIG ONE.
⭐   ⭐ PARSE + EXECUTE ..............  400 ms  ⭐⭐ WORSE ON A CHEAP
⭐                                              PHONE THAN DOWNLOAD
⭐   React mount ....................  100 ms
⭐   ⭐ API CALL (your 40 ms) ........   40 ms  ⭐⭐ ← ALL YOU MEASURED
⭐   ⭐⭐ WATERFALL: 2 dependent calls .  400 ms
⭐   render + paint .................  200 ms
⭐                                    ─────────
⭐                                     ~2.8 s

⭐   ⇒ ⭐⭐ YOUR 40 ms IS **1.4%** OF THE WAIT.
⭐     ⭐ OPTIMISING IT TO 20 ms IS INVISIBLE. THE BUNDLE AND THE
⭐       WATERFALL ARE 57%.
```

> ⭐⭐ **This is Day 457's discipline applied to the client: find where the cost actually is before
> engineering against it.** The reason backend engineers under-invest here is that their dashboards
> are honest about their own layer and silent about every other one.

# Part 2 — The three vitals

| ⭐ Metric | Measures | Good | ⭐⭐ Usual cause when bad |
|---|---|---|---|
| **LCP** — Largest Contentful Paint | ⭐ When the main content appears | < 2.5 s | ⭐⭐ A huge unoptimised hero image, a slow TTFB, or render-blocking resources |
| **INP** — Interaction to Next Paint | ⭐⭐ Responsiveness to *every* interaction | < 200 ms | ⭐ Long tasks blocking the main thread — a big re-render, a heavy sort |
| **CLS** — Cumulative Layout Shift | ⭐ How much the page jumps | < 0.1 | ⭐⭐ Images with no dimensions, ads/banners injected late, **a spinner replaced by taller content** (Day 240) |

```
⭐⭐ THE ONE PEOPLE MISUNDERSTAND: INP.
⭐   It is not "load time". It is ⭐ EVERY CLICK, TAP AND KEYPRESS
⭐   FOR THE WHOLE SESSION, and it is reported at ~p98.
⭐   ⇒ ⭐⭐ ONE 800 ms INTERACTION IN A LONG SESSION FAILS THE PAGE,
⭐     EVEN IF EVERYTHING ELSE IS INSTANT. ⭐ It is a tail metric,
⭐     exactly like your p99 — and you already know tails matter more
⭐     than averages (Day 481).
```

| ⭐ Also worth watching | |
|---|---|
| **TTFB** | ⭐ Your server + network. **The only one your backend metrics see.** |
| **Total JS** | ⭐⭐ The lever you control most directly |
| **Long tasks (>50 ms)** | ⭐ Each one is a frozen UI window |

# Part 3 — ⭐⭐ The critical path

```
⭐⭐ WHAT BLOCKS THE FIRST PAINT — fix in this order

⭐ ① ⭐⭐ RENDER-BLOCKING RESOURCES
⭐    · <script> in <head> without defer  ⇒ ⭐ parsing STOPS
⭐    · every <link rel=stylesheet>       ⇒ ⭐⭐ CSS IS ALWAYS
⭐      RENDER-BLOCKING. Inline the critical bit, defer the rest.
⭐    · ⭐ @import inside CSS ⇒ a SERIAL request. Never.

⭐ ② ⭐⭐ THE WATERFALL (Day 227) — the biggest structural win
⭐    HTML → JS → API → API → image
⭐    ⇒ ⭐ EACH ARROW IS A FULL ROUND TRIP THAT COULD NOT START EARLIER.
⭐    ⇒ ⭐⭐ FIXES: <link rel=preload> for the bundle · route loaders ·
⭐      server rendering · <link rel=preconnect> to your API origin
⭐      (saves DNS+TLS, ~100–300 ms, one line)

⭐ ③ BUNDLE SIZE — route splitting (Day 233), tree-shaking (Day 222)
⭐ ④ ⭐ IMAGES AND FONTS — Day 242, usually the largest bytes
```

```html
<!-- ⭐ four lines that are nearly free -->
<link rel="preconnect" href="https://api.example.com">   <!-- ⭐⭐ DNS+TLS early -->
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">
<script src="/app.js" defer></script>                     <!-- ⭐ never blocks -->
<img src="..." width="800" height="400">                  <!-- ⭐⭐ kills CLS -->
```

# Part 4 — Field vs lab, and the budget

```
⭐⭐ THEY ANSWER DIFFERENT QUESTIONS. YOU NEED BOTH.

⭐   LAB (Lighthouse, DevTools)
⭐     ⭐ Reproducible, debuggable, one device you chose.
⭐     ⭐⭐ IT IS NOT YOUR USERS. A perfect Lighthouse score with bad
⭐       field data is normal and means your synthetic profile is
⭐       nothing like reality.
⭐   FIELD (RUM / web-vitals in prod)
⭐     ⭐⭐ REAL DEVICES, REAL NETWORKS, REAL P75. THE TRUTH.
⭐     ⭐ Harder to debug — you get a number without a stack.

⭐   ⇒ ⭐⭐ SAME SPLIT AS SYNTHETIC MONITORING VS PRODUCTION METRICS
⭐     IN STAGE 10. Lab tells you WHY, field tells you WHETHER.
```

```javascript
// ⭐ ship this on day one — it is ~1 KB
import { onLCP, onINP, onCLS } from "web-vitals";
[onLCP, onINP, onCLS].forEach(fn => fn(m => {
  navigator.sendBeacon("/rum", JSON.stringify({    // ⭐⭐ survives unload
    name: m.name, value: m.value, id: m.id, path: location.pathname,
  }));
}));
```

| ⭐⭐ The budget, enforced in CI | |
|---|---|
| Initial JS | ⭐ < 200 KB gzipped |
| LCP image | < 200 KB |
| Total requests to first paint | ⭐ < 20 |
| ⭐⭐ **Lighthouse CI fails the build** | **so growth is a decision someone made, not drift nobody saw** |

## Today's build

1. ⭐⭐ **Run Lighthouse on your app, mobile profile, 4G throttle.** Write down LCP, INP, CLS. **These are your before numbers.**
2. ⭐ Open the Network waterfall and **draw the dependency arrows on paper.** Count the sequential hops.
3. ⭐⭐ Add `preconnect` to your API origin. Re-measure. **One line, usually 100–300 ms.**
4. ⭐ Find your largest bundle chunk. Split one route out. Re-measure.
5. ⭐⭐ Remove `width`/`height` from an image and watch CLS spike. Put them back.
6. ⭐ Ship the web-vitals beacon. **Compare field p75 with your lab score** — expect them to disagree.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "your API is fast but the app feels slow — what do you do?"**

Do the accounting out loud. **First I stop looking at server metrics, because they measure the part I'm
responsible for rather than the part the user experiences. On a typical page my forty-millisecond API
call is about one percent of the wait. DNS, TLS and the HTML are three hundred milliseconds, the
JavaScript bundle is over a second on 4G, parsing it is another four hundred — worse than downloading on
a cheap phone — and then a waterfall of dependent requests. Optimising forty milliseconds to twenty is
invisible.**

Then what you measure instead. **LCP for when content appears, INP for responsiveness, CLS for
stability. INP is the one people misread — it's not load time, it's every interaction across the whole
session reported near p98, so one eight-hundred-millisecond interaction fails the page even if
everything else is instant. It's a tail metric, exactly like a p99.**

Then the fixes, in order of leverage. **The waterfall first, because it's structural — preconnect to the
API origin is one line and often saves a couple of hundred milliseconds, and moving fetches into route
loaders removes a round trip. Then bundle size via route splitting, then images and fonts, which are
usually the largest bytes.**

Close on measurement discipline. **Lab and field answer different questions — Lighthouse tells me why,
real-user monitoring tells me whether, and a perfect Lighthouse score with bad field data just means my
synthetic profile is nothing like my users. And the budget goes in CI, so bundle growth is a decision
somebody made rather than drift nobody noticed.**
