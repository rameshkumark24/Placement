# Part 1 — ⭐⭐ `is` vs `==`

```python
a = [1, 2, 3]
b = [1, 2, 3]
c = a

a == b     # ⭐ True  — same VALUE      ⇒ calls a.__eq__(b)
a is b     # ⭐⭐ False — different OBJECTS ⇒ compares id()
a is c     # True
```

| | ⭐ `is` | ⭐ `==` |
|---|---|---|
| Asks | ⭐⭐ same object? | ⭐⭐ same value? |
| Implemented as | ⭐ pointer comparison | ⭐ calls `__eq__` |
| Overridable | ⭐⭐ **never** | yes |
| Speed | ⭐ always O(1) | ⭐ whatever your `__eq__` costs |

```
⭐⭐ USE `is` FOR EXACTLY THESE:
⭐   x is None        ⭐⭐ ← ALWAYS. None is a singleton, and __eq__ can be overridden to lie.
⭐   x is True / False   ⭐ (rare — usually you just want truthiness)
⭐   x is some_sentinel  ⭐ your own MISSING = object()
⭐   x is y           ⭐ when you genuinely mean "the same object" (caching, identity maps)
⭐
⭐ ⚠️ ⭐⭐ NEVER for numbers or strings — Day 028 explained why it appears to work.
```

⭐⭐ **The sentinel pattern is worth having ready**, because `None` is sometimes a legitimate value:

```python
MISSING = object()                       # ⭐⭐ a unique object; equal to nothing else, ever
def get(d, key, default=MISSING):
    if default is MISSING:               # ⭐ distinguishes "no default given" from "default=None"
        return d[key]
    return d.get(key, default)
```

# Part 2 — ⭐⭐ Truthiness, and the bug you will write

```
⭐ `if x:` calls __bool__(x); if absent, __len__(x); if neither, TRUE.

⭐⭐ FALSY: False · None · 0 · 0.0 · 0j · Decimal(0) · "" · [] · () · {} · set() · range(0)
⭐         · ⭐ anything whose __len__ returns 0 or __bool__ returns False
⭐ ⭐⭐ TRUTHY: everything else — including "0", "False", [0], {0: None}, and any object by default
```

```python
# ⚠️⚠️ ⭐⭐ THE BUG. In production code, right now, somewhere:
def apply(discount=None):
    if not discount:            # ⚠️ ⭐⭐ TRUE for None AND for 0 AND for 0.0
        discount = DEFAULT      # ⭐⭐ a deliberate 0% discount is silently overwritten
```

```python
# ⭐⭐ THE FIX, and it is always the same:
    if discount is None:        # ⭐⭐ "not provided" — the ONLY thing you meant
        discount = DEFAULT
```

```
⭐⭐ THE RULE, AND IT IS WORTH SAYING VERBATIM IN A REVIEW:
⭐   ⭐⭐ `if not x` means "empty or zero or absent".
⭐   ⭐⭐ `if x is None` means "absent".
⭐   ⇒ if 0, 0.0, "" or [] are LEGITIMATE VALUES in your domain — and they nearly always are —
⭐     ⇒ ⭐⭐ these two are different programs.
⭐ ⇒ ⭐ affected in real code: quantities, prices, discounts, offsets, page numbers,
⭐      search queries, counts, and every optional API field.
```

⚠️ ⭐⭐ **The same bug in a web handler:** `if not request.query_params.get("page")` treats `page=0`
as missing. **And in FastAPI/Pydantic, "the client sent `null`" and "the client omitted the field"
are different states** — which is why Pydantic gives you `exclude_unset` and a `PydanticUndefined`
sentinel rather than reusing `None` for both.

⭐ **Custom truthiness** — define `__bool__` (or `__len__`) deliberately, and know that an object
with neither is always truthy, which is usually what you want:

```python
class Cart:
    def __len__(self): return len(self.items)     # ⭐ now `if cart:` means "has items"
```

# Part 3 — ⭐⭐ The `__eq__` / `__hash__` contract

```
⭐⭐ THE CONTRACT — three rules, and violating any one breaks dicts and sets:
⭐   1. ⭐⭐ a == b  ⇒  hash(a) == hash(b)          (the reverse need NOT hold — collisions are legal)
⭐   2. ⭐⭐ hash(x) MUST NOT CHANGE while x is in a dict or set
⭐   3. ⭐ __eq__ should be reflexive, symmetric, transitive
```

```
⭐⭐ WHY RULE 1: a dict finds a key by hashing to a BUCKET, then comparing with == inside it.
⭐   ⇒ ⭐⭐ if two equal objects hash differently they land in DIFFERENT BUCKETS
⭐        ⇒ the lookup never even reaches the comparison ⇒ ⭐⭐ your key is "not found"
⭐        while an equal key sits in the dict.
```

```python
# ⚠️ ⭐⭐ THE GOTCHA EVERY PYTHON DEVELOPER HITS ONCE:
class P:
    def __init__(self, x): self.x = x
    def __eq__(self, o): return self.x == o.x     # ⭐⭐ defining __eq__ sets __hash__ = None

{P(1)}      # ⭐⭐ TypeError: unhashable type: 'P'
```

⭐⭐ **This is deliberate, not an oversight.** If you change equality and keep the default
identity-based hash, rule 1 is broken: two equal objects would hash differently. **Python makes the
class unhashable rather than let you build a silently broken dict.**

```python
# ⭐ THE FIXES — pick one:
class P:
    def __eq__(self, o): return isinstance(o, P) and self.x == o.x
    def __hash__(self): return hash(self.x)       # ⭐ hash the SAME fields you compare

from dataclasses import dataclass
@dataclass(frozen=True)          # ⭐⭐ generates __eq__ AND a matching __hash__. Use this.
class P: x: int

@dataclass                       # ⭐ eq only ⇒ unhashable, and correctly so (it is mutable)
class Q: x: int
```

## ⚠️ ⭐⭐ Rule 2 — the silent one

```python
@dataclass(eq=True)
class Tag:
    name: str
    def __hash__(self): return hash(self.name)    # ⚠️ ⭐⭐ hashable AND mutable

t = Tag("a")
s = {t}
t.name = "b"          # ⭐⭐ the hash changed while it sat in the set
t in s                # ⭐⭐ False — it is in there, in the WRONG BUCKET, and unreachable.
s.remove(t)           # ⭐ KeyError. It is present and unfindable.
```

⭐⭐ **This is why the built-in mutable types are unhashable**: `list`, `dict` and `set` refuse to be
keys precisely so this cannot happen. ⭐ **The rule: hashable implies immutable-in-practice — hash
only fields that never change.**

⭐ **Useful details:** `hash(-1)` is `-2` (CPython uses −1 as an error signal); string hashing is
randomised per process by default (`PYTHONHASHSEED`) to defend against hash-collision DoS, **so a
`hash()` value must never be persisted or sent between processes**; and `hash(1) == hash(1.0) ==
hash(True)`, which is why `{1: "a", 1.0: "b", True: "c"}` is a **one-entry dict**.

# Part 4 — ⭐ Comparison, sorting, and `__lt__`

```python
from functools import total_ordering

@total_ordering                  # ⭐ define __eq__ and __lt__; get the other four free
class Version:
    def __init__(self, parts): self.parts = tuple(parts)
    def __eq__(self, o): return self.parts == o.parts
    def __lt__(self, o): return self.parts < o.parts
```

```python
sorted(items, key=lambda i: (i.priority, i.name))   # ⭐⭐ tuple keys sort lexicographically
sorted(items, key=lambda i: (-i.score, i.name))     # ⭐ descending on one field, ascending on another
```

⭐⭐ **`sorted` needs only `__lt__`** — it never uses `__gt__`. ⭐ **And Python 3 removed `__cmp__`
and arbitrary cross-type comparison**: `1 < "a"` is a `TypeError`, which was a deliberate choice to
turn a silent nonsense result into an error.

⭐ **`sort` is stable**, which is what makes multi-pass sorting work: sort by the secondary key first,
then by the primary, and ties keep the earlier order.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`if not x` meaning "not provided"** | ⭐⭐ `0`, `0.0`, `""`, `[]` are falsy. Use `is None`. |
| ⭐ `is` for numbers/strings | ⭐⭐ Works by accident (Day 028). Use `==`. |
| ⭐ `== None` | ⭐ `is None` — `__eq__` can be overridden to lie. |
| ⭐⭐ Defining `__eq__` without `__hash__` | ⭐ The class becomes unhashable — deliberately. |
| Hashing fields you then mutate | ⭐⭐ The object becomes unfindable in its own set. |
| Making a mutable class hashable | ⭐ That is why `list` is not a key. |
| Persisting `hash()` across processes | ⭐⭐ String hashing is randomised per process. |
| Forgetting `1 == 1.0 == True` | ⭐ Dict keys collapse into one entry. |
| Writing all six comparisons | ⭐ `@total_ordering`, or a `key=` tuple. |
| Expecting `sorted` to use `__gt__` | ⭐ It uses `__lt__` only. |

## Interview questions

**Q: `is` versus `==`?**
> `is` compares identity — are these the same object — and it's a pointer comparison that can't be
> overridden. `==` compares value by calling `__eq__`, which any class can define. I use `is` for
> `None`, for the booleans, and for my own sentinels, and `==` for everything else. Comparing numbers
> or strings with `is` appears to work because of the small-integer cache and literal interning,
> which makes it worse — it's a bug that passes its tests.

**Q: What's wrong with `if not value:` when checking whether an argument was provided?**
> It conflates "not provided" with "provided, and falsy" — zero, zero-point-zero, empty string, empty
> list. In a domain where a quantity of zero, a page offset of zero or an empty search string is
> legitimate, that silently rewrites the caller's intent. `if value is None` asks the question that
> was actually meant. It's the kind of bug that never fails in testing because nobody tests with
> zero.

**Q: Explain the `__eq__`/`__hash__` contract.**
> Equal objects must have equal hashes, and an object's hash must not change while it's in a hash
> container. The first is required because lookup hashes to a bucket and only then compares — so two
> equal objects with different hashes land in different buckets, and the dict never finds the key
> even though an equal one is present. The second is why mutable built-ins aren't hashable: mutating
> a key after insertion leaves it in the wrong bucket, so it's present, unfindable, and `remove`
> raises `KeyError`.

**Q: Why does defining `__eq__` make a class unhashable?**
> Because the default hash is identity-based, and once equality is value-based the two disagree — two
> equal objects would hash differently, violating the contract. Rather than let you build a
> quietly-broken dict, Python sets `__hash__` to `None`. The fix is either to define a hash over the
> same fields I compare, or to use `@dataclass(frozen=True)`, which generates both consistently and
> also makes mutation impossible, which is really the underlying requirement.

**Q: Anything unusual about hashing in CPython?**
> String hashing is randomised per process by default, as a defence against hash-collision denial of
> service, so a hash value is only meaningful within one process — never persist it or send it
> between processes. `hash(-1)` is `-2`, because −1 is reserved as an error signal in the C API. And
> `hash(1)`, `hash(1.0)` and `hash(True)` are all equal, which is why a dict literal with those three
> keys collapses to a single entry.

**Q: How do you sort by two fields, one descending?**
> A `key` function returning a tuple, negating the descending numeric field — `key=lambda x:
> (-x.score, x.name)`. For non-numeric descending fields I rely on `sort` being stable and do two
> passes, sorting by the secondary key first. And I'd define `__lt__` rather than all six
> comparisons, since `sorted` only uses `__lt__`, and use `@total_ordering` if the full set is
> genuinely needed.

## 🎙️ Articulation drill

Record two minutes: **"Explain the `__eq__` and `__hash__` contract, and what breaks without it."**

⭐ State the contract: **equal objects must hash equally, and the hash must not change while the
object is in a hash container.** ⭐ Then the mechanism, because the mechanism is the explanation: a
dict hashes to a bucket and only compares within that bucket, so two equal objects with different
hashes are never compared at all — the lookup fails while an equal key sits in the dict.

⭐⭐ **Then the second rule with its symptom, which is the memorable half:** *"if you mutate a field
that the hash is computed from, the object is now in the wrong bucket. `x in s` is False, `s.remove(x)`
raises `KeyError`, and the object is genuinely present and genuinely unreachable. That is exactly why
lists and dicts are not hashable — the language removes the possibility rather than trusting you.
Which is also why `@dataclass(frozen=True)` is the right default for anything that goes in a set: it
generates both methods consistently and removes mutation, which is the real requirement underneath
both rules."*
