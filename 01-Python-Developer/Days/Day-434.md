# Part 3 — ⭐⭐ Two structural traps

```
⭐⭐ TRAP ① — ***POST-FILTERING IS A SECURITY BUG, NOT A
⭐   PERFORMANCE CHOICE.***
⭐   ⭐ Day 432 framed it as "you might get zero results".
⭐   ⭐ The security framing is worse: ⭐⭐ POST-FILTERING MEANS
⭐     ANOTHER TENANT'S VECTORS ***WERE SEARCHED, SCORED AND
⭐     RETURNED INTO YOUR PROCESS MEMORY***, and the only thing
⭐     standing between them and the prompt is a line of your
⭐     application code.
⭐   ⭐ Every retry, every refactor, every "let's also try
⭐     without the filter to debug it" ⭐⭐ IS ONE TYPO FROM
⭐     DISCLOSURE.
⭐   ⭐⭐ ⇒ THE FILTER BELONGS ***INSIDE THE QUERY THE DATABASE
⭐     EXECUTES***, and ideally inside a policy the database
⭐     enforces whatever query you send (Part 4).

⭐⭐ TRAP ② — ***PERMISSIONS CHANGE. EMBEDDINGS DO NOT.***
⭐   ⭐ You copied a document's ACL into the index at ingest.
⭐   ⭐ On Tuesday somebody is removed from the group.
⭐   ⭐⭐ THE INDEX STILL SAYS THEY MAY READ IT, AND WILL UNTIL
⭐     THE NEXT REINDEX. ⭐ Your revocation did nothing.
⭐   ⭐ THE THREE HONEST OPTIONS:
⭐     ⭐ ⓐ ***resolve permissions at query time*** against the
⭐       live source — join, or fetch the user's group set and
⭐       pass it as the filter. ⭐⭐ CORRECT. COSTS A LOOKUP.
⭐     ⭐ ⓑ ***propagate changes into the index*** via the outbox
⭐       (Day 407) — ⭐ eventually consistent, ⭐⭐ AND YOU MUST
⭐       STATE THE WINDOW OUT LOUD: "revocation takes effect
⭐       within 30 seconds."
⭐     ⭐ ⓒ ***index-time ACLs with no propagation*** —
⭐       ⭐⭐ THIS IS THE ONE EVERYONE SHIPS AND IT IS BROKEN.
⭐   ⭐⭐ ⇒ SAME SHAPE AS DAY 412: THE INDEX IS ***DERIVED
⭐     STATE***, AND DERIVED SECURITY STATE GOES STALE EXACTLY
⭐     LIKE DERIVED BUSINESS STATE — ⭐ except the consequence is
⭐     a disclosure rather than a wrong dashboard.
```

# Part 4 — Making the filter impossible to forget

```
⭐ ***FOUR LAYERS. EACH ONE ALONE IS INSUFFICIENT.***

⭐ ① ***TYPES.*** ⭐ `tenant_id` is a required keyword-only
⭐   argument on every retrieval function (Day 432's protocol).
⭐   ⭐⭐ NO DEFAULT. NO `Optional`. NO `**filters` DICT — ⭐ a
⭐   dict makes omission a runtime possibility instead of a type
⭐   error, and dicts get built dynamically.

⭐ ② ***THE DATABASE.*** ⭐⭐ POSTGRES ROW-LEVEL SECURITY. ⭐ The
⭐   filter stops being something your code remembers and becomes
⭐   something the engine applies to every statement, including
⭐   the ad-hoc query you run while debugging at 2am.

⭐ ③ ***REQUEST CONTEXT.*** ⭐ The tenant comes from the
⭐   ***authenticated session***, never from the request body,
⭐   never from an LLM's tool arguments. ⭐⭐ IF AN AGENT CAN
⭐   CHOOSE ITS OWN `tenant_id`, PROMPT INJECTION (DAY 446) IS
⭐   NOW A DATA-EXFILTRATION PRIMITIVE, ⭐ and you built the
⭐   exploit yourself.

⭐ ④ ***TESTS AND ALARMS.*** ⭐ Part 6.
```

```sql
-- ⭐⭐ RLS: THE FILTER THE DATABASE APPLIES WHETHER OR NOT YOU
-- REMEMBERED IT.
ALTER TABLE chunks_v4 ENABLE ROW LEVEL SECURITY;
ALTER TABLE chunks_v4 FORCE ROW LEVEL SECURITY;   -- ⭐ also for the owner

CREATE POLICY tenant_isolation ON chunks_v4
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);

-- ⭐ per-request, inside the transaction, from the session:
SET LOCAL app.tenant_id = '…';
```

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def tenant_session(pool, *, tenant_id: str):
    """⭐⭐ THE ONLY WAY TO GET A CONNECTION. Enforced by review
    and by the fact that nothing else is exported."""
    async with pool.acquire() as conn:
        async with conn.transaction():
            # ⭐ SET LOCAL is transaction-scoped, so a pooled
            # ⭐⭐ CONNECTION CANNOT LEAK THE SETTING TO THE NEXT
            # REQUEST — the classic bug with SET (Day 385).
            await conn.execute(
                "SELECT set_config('app.tenant_id', $1, true)", tenant_id
            )
            yield conn
```

```
⭐⭐ WHY RLS IS WORTH THE SETUP, IN ONE SENTENCE: ⭐ it converts
⭐   "every engineer who ever writes a query must remember" into
⭐   ***"the engine will not return those rows"***, ⭐⭐ AND THAT
⭐   IS THE DIFFERENCE BETWEEN A CONVENTION AND A CONTROL.
```

# Part 5 — Document-level ACLs, the harder version

```
⭐ TENANT ISOLATION IS THE EASY HALF. ⭐ The hard half is
⭐   ***within*** a tenant: HR documents, board minutes, the
⭐   salary spreadsheet, a private Confluence space.

⭐ ***THE SHAPE THAT WORKS:*** ⭐ store an `acl` array of
⭐   principal ids on each chunk, resolve the ***user's***
⭐   principal set at query time, and filter with array overlap.
⭐
⭐   acl text[]  →  {'group:eng', 'group:all-staff', 'user:42'}
⭐   query       →  WHERE acl && $user_principals
⭐   ⭐ GIN index on `acl` so it composes with the ANN scan.

⭐⭐ THE THREE THINGS THAT MAKE IT HARD:
⭐   ⭐ ① ***GROUP EXPANSION IS RECURSIVE*** and lives in another
⭐     system (Okta, AD, Google Groups). ⭐ Resolving it per
⭐     query is a network hop — ⭐⭐ CACHE IT PER USER WITH A
⭐     SHORT TTL AND ***STATE THE REVOCATION WINDOW***.
⭐   ⭐ ② ***"DENY" RULES DO NOT COMPOSE WITH ARRAY OVERLAP.***
⭐     ⭐ Day 381's IAM lesson: explicit deny must beat allow.
⭐     ⭐⭐ IF YOUR SOURCE SYSTEM HAS DENIES, YOU CANNOT MODEL IT
⭐       AS A SET INTERSECTION AND MUST EVALUATE PER DOCUMENT.
⭐   ⭐ ③ ***THE SOURCE OF TRUTH MOVES.*** ⭐ A document changes
⭐     folder and inherits new permissions. ⭐⭐ NOTHING ABOUT
⭐     THE DOCUMENT'S ***TEXT*** CHANGED, SO YOUR CONTENT-HASH
⭐     CACHE (DAY 431) SKIPS IT AND THE OLD ACL SURVIVES.
⭐     ⭐⭐ ⇒ ACL UPDATES MUST BE A ***SEPARATE PATH*** FROM
⭐       CONTENT UPDATES. ⭐ This bug is very common and very
⭐       quiet.
```

# Part 6 — Deletion, caching, and proving it works

```
⭐ ***① DELETION IS NOT AUTOMATIC.***
⭐   ⭐ The user deletes a document. ⭐⭐ THE INDEX DOES NOT CARE.
⭐   ⭐ Under GDPR/DPA erasure this is a live compliance problem,
⭐     not a tidiness one.
⭐   ⭐ ⇒ delete by `doc_id` in the ***same transaction*** if the
⭐     index is in Postgres; ⭐⭐ VIA THE OUTBOX (DAY 407) IF IT
⭐     IS A SEPARATE SERVICE. ⭐ Never a best-effort call after
⭐     commit — that is the dual-write bug Stage 12 spent a day
⭐     on.
⭐   ⭐ ⭐⭐ AND DO NOT FORGET THE EMBEDDING CACHE, THE PROMPT
⭐     CACHE, AND YOUR OBSERVABILITY STORE — ⭐ deleted text
⭐     lives in traces (Day 455).

⭐ ***② THE CACHE KEY IS A SECURITY BOUNDARY.*** ⭐ Stage 11 said
⭐   this about CDNs; ⭐⭐ IT IS EXACTLY AS TRUE FOR A SEMANTIC
⭐   ANSWER CACHE. ⭐ Cache on the question text alone and user B
⭐   gets user A's answer built from documents B may not read.
⭐   ⭐⭐ ⇒ THE KEY MUST INCLUDE TENANT ***AND*** THE PRINCIPAL
⭐     SET (hashed), ⭐ which is also why per-user answer caches
⭐     have terrible hit rates. ⭐ That is a cost you accept, not
⭐     a bug you optimise away (Day 454).

⭐ ***③ PROVE IT. THREE ARTEFACTS:***
⭐   ⭐ ⓐ ***THE CANARY TEST.*** ⭐ Seed tenant B with a document
⭐     containing a unique nonsense token — `ZZQX-CANARY-7741`.
⭐     ⭐⭐ AS TENANT A, ASK EVERY QUESTION IN YOUR EVAL SET AND
⭐     ASSERT THE TOKEN NEVER APPEARS IN ANY RETRIEVED CHUNK OR
⭐     ANY ANSWER. ⭐ Run it in CI, every build.
⭐   ⭐ ⓑ ***THE CONSTRUCTOR TEST.*** ⭐ Assert that calling the
⭐     retriever without a tenant raises `TypeError`. ⭐⭐ IT IS
⭐     ONE LINE AND IT PINS THE INVARIANT AGAINST REFACTORS.
⭐   ⭐ ⓒ ***THE AUDIT LOG.*** ⭐⭐ LOG THE RETRIEVED `doc_id`s,
⭐     THE TENANT AND THE PRINCIPAL SET FOR EVERY QUERY. ⭐ This
⭐     is the only thing that lets you answer "what was
⭐     disclosed, and to whom?" ⭐⭐ WITHOUT IT, YOUR INCIDENT
⭐     REPORT IS A SHRUG, AND A SHRUG IS ASSUMED-WORST-CASE BY
⭐     EVERY REGULATOR.
```

```python
CANARY = "ZZQX-CANARY-7741"

@pytest.mark.parametrize("question", EVAL_QUESTIONS)
async def test_no_cross_tenant_leak(question, retriever):
    hits = await retriever.retrieve(question, tenant_id=TENANT_A)
    for h in hits:
        assert CANARY not in h.body, f"leak via chunk {h.chunk_id}"
        assert h.tenant_id == TENANT_A            # ⭐⭐ belt AND braces

async def test_tenant_is_not_optional(retriever):
    with pytest.raises(TypeError):
        await retriever.retrieve("anything")      # ⭐ no tenant_id
```

# 💬 Interview

**1. "How do you stop a RAG system leaking data between tenants?"**

⭐ I start by naming why it's harder than it sounds: ⭐⭐ a missing tenant filter in SQL shows 40,000
rows and someone notices in minutes, but a missing tenant filter in retrieval produces a fluent,
well-cited paragraph that looks exactly like a correct answer. ⭐ No exception, no error rate change, no
latency change. ⭐⭐ The generation step launders the data into original prose, so every signal you'd
normally monitor is silent. ⭐ So the defence is layered: tenant is a required keyword-only argument on
the retrieval interface so omitting it is a type error; Postgres row-level security so the engine
applies it whether or not my code remembered; the tenant comes from the authenticated session and never
from a request body or a tool argument; and a canary test in CI where tenant B holds a unique token and
every eval question asked as tenant A must never surface it.

**2. "Why is post-filtering a security issue and not just a performance one?"**

⭐ Because post-filtering means the other tenant's vectors were **searched, scored, and returned into my
process memory**, and the only thing between them and the prompt is one line of application code.
⭐⭐ Every refactor, every retry path, every "let me remove the filter to debug this" is one typo from
disclosure. ⭐ Pre-filtering means those rows were never candidates. ⭐⭐ Same output on the happy path,
completely different blast radius when something goes wrong — and in this domain you design for the
failure, because the failure is invisible.

**3. "Shared index with a filter, or an index per tenant?"**

⭐ I'd decide on the failure mode rather than the cost. ⭐⭐ With a shared index, a bug means disclosure;
with a namespace per tenant, a bug means an empty result. ⭐ One of those is a breach notification and
the other is a bug report. ⭐ So for regulated or competitively sensitive data with a modest tenant
count — say under a thousand — I'd buy the safe failure mode. ⭐⭐ Above that, per-index memory overhead
makes it impractical and you're back to a shared index, which is fine as long as you defend it in depth
with RLS and canaries rather than relying on everyone remembering a WHERE clause.

**4. "A user is removed from a group. What happens to your index?"**

⭐⭐ If I copied ACLs into the index at ingest — nothing. The index still says they can read it, and will
until the next reindex, so the revocation did nothing. ⭐ That's the trap: permissions change and
embeddings don't. ⭐ There are three honest options: resolve permissions at query time against the live
source, which is correct and costs a lookup; propagate changes through an outbox, which is eventually
consistent and requires you to **state the window out loud** — "revocation takes effect within thirty
seconds"; or index-time ACLs with no propagation, which is what most teams ship and is simply broken.
⭐⭐ It's the same shape as any derived state: it goes stale, except here the consequence is disclosure
rather than a wrong dashboard.

**5. "What's the subtle ACL bug you've seen?"**

⭐ A document moves folder and inherits new permissions. ⭐⭐ Nothing about its **text** changed, so the
content-hash cache correctly skips re-embedding it — and the old ACL rides along untouched. ⭐ The
document is now readable by people who shouldn't see it, and the pipeline behaved exactly as designed.
⭐⭐ The fix is that ACL updates have to be a separate path from content updates, keyed off permission
events rather than content hashes. ⭐ The general lesson is that the content hash proves the *text* is
unchanged, and I'd been using it to imply the *record* was unchanged.

**6. "How does caching interact with this?"**

⭐⭐ The cache key is a security boundary — the same rule as a CDN. ⭐ If I cache answers on question
text alone, user B asks the same question and gets user A's answer, assembled from documents B has no
right to see, and it's served instantly with no retrieval happening at all, so even a perfect permission
filter is bypassed. ⭐⭐ So the key includes the tenant and a hash of the user's principal set. ⭐ That
tanks the hit rate, and that's a cost I accept rather than a problem I optimise away — a semantic
answer cache with a global key is a data-leak machine with excellent metrics.

**7. "There's been a suspected leak. What can you tell the customer?"**

⭐ That depends entirely on whether I logged retrieved document ids, which is why I do. ⭐⭐ For every
query I log the tenant, the principal set, the retrieved doc ids and the config version — so I can
reconstruct exactly which documents entered which answers, and give a precise list of what was exposed
and to whom. ⭐ Without that log, the honest answer is "I don't know", ⭐⭐ and every regulator treats
"I don't know" as worst case. ⭐ The other thing I'd check is the observability store: prompts and
retrieved text end up in traces, so deleted or restricted content lives there too, which means retention
limits and redaction on that path as well.
