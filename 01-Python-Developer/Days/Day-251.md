# Day 251 🏗️

**P-251** · 🏗 **The API contract** — ⭐⭐ OpenAPI before any endpoint, and the auth matrix as a grid

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: FastAPI generates OpenAPI from your code, which is convenient and is
> the wrong direction for a project this size. Write the contract first, review it, then implement
> against it — because a spec derived from code can never disagree with the code, and disagreeing
> with the code is exactly what you want a spec to do.**
>
> ⭐ Every decision today is one that is cheap now and expensive in three weeks: the error shape, the
> pagination style, where idempotency lives, and who may see what.

# Part 1 — ⭐ Resources, and the four naming decisions

```
⭐⭐ RESOURCES ARE NOUNS. ACTIONS ARE HTTP METHODS — until they are not,
⭐   and knowing when is the skill.

⭐   GET    /v1/jobs?status=scheduled&cursor=…      ⭐ list
⭐   POST   /v1/jobs                                ⭐ create
⭐   GET    /v1/jobs/{id}                           ⭐ read
⭐   PATCH  /v1/jobs/{id}                           ⭐⭐ partial update.
⭐          ⭐ PUT means "replace entirely" and almost nobody means that
⭐   DELETE /v1/jobs/{id}                           ⭐ if it exists at all

⭐⭐ AND THE STATE TRANSITIONS, WHICH ARE ***NOT*** FIELD UPDATES:
⭐   ❌ PATCH /v1/jobs/{id} {"status": "dispatched"}
⭐      ⭐⭐ THIS IS THE MOST COMMON API DESIGN MISTAKE IN THIS PROJECT.
⭐        ⭐ It says "set a field" when the real operation is "perform a
⭐          transition, which has preconditions, side effects and its
⭐          own authorisation rule".
⭐        ⭐⭐ It also invites a client to set any status it likes, so
⭐          the validation has to reconstruct the state machine from a
⭐          diff — and every caller must know the state machine.
⭐   ✅ POST /v1/jobs/{id}/dispatch     {"technician_id":…, "window":…}
⭐      POST /v1/jobs/{id}/complete    {"work_items":[…]}
⭐      POST /v1/invoices/{id}/pay     {"payment_method_id":…}
⭐      ⭐⭐ EACH HAS ITS OWN REQUEST SHAPE, ITS OWN 409 CONDITIONS AND
⭐        ITS OWN PERMISSION. ⭐ That is not un-RESTful; a transition is
⭐        a resource-level command and REST has always allowed it.

⭐⭐ THE FOUR NAMING DECISIONS, MADE ONCE:
⭐   ⭐ plural nouns · ⭐ lowercase, hyphens not underscores in paths ·
⭐   ⭐ `snake_case` in JSON bodies (⭐⭐ pick one and never mix; Python
⭐     on both ends makes snake_case the honest choice) ·
⭐   ⭐⭐ `/v1/` in the path from the first commit — Day 161: adding a
⭐     version later means every existing client is "unversioned".
```

# Part 2 — ⭐⭐ The error contract: one shape, everywhere

```json
{
  "error": {
    "code": "assignment_conflict",
    "message": "Technician is already assigned 10:00–12:00.",
    "details": [{"field": "window", "issue": "overlaps assignment 8812"}],
    "request_id": "01J8ZQ..."
  }
}
```

```
⭐⭐ FIVE RULES, AND EACH PREVENTS A SPECIFIC FUTURE ARGUMENT:
⭐  ① ⭐⭐ `code` IS A STABLE MACHINE STRING. Clients branch on it.
⭐     ⭐ `message` is for humans and may be reworded any time —
⭐     ⭐⭐ SO NO CLIENT MAY EVER PARSE `message`, and saying so in the
⭐       contract is what makes that true.
⭐  ② `details` is for field-level validation, and is absent otherwise.
⭐  ③ ⭐⭐ `request_id` IS ON ***EVERY*** ERROR AND IN THE `x-request-id`
⭐     RESPONSE HEADER (Day 146). ⭐ It is what turns a support email
⭐     into a log query.
⭐  ④ ⭐⭐ NEVER LEAK INTERNALS. No stack traces, no SQL, no "user with
⭐     email X not found" (⭐ that is a user-enumeration oracle).
⭐  ⑤ ⭐ 5xx bodies say nothing but the code and the request id.

⭐⭐ THE STATUS CODE TABLE — decide it now, not per endpoint:
⭐   400 malformed syntax          ⭐ rarely; usually 422
⭐   401 no/invalid credentials    ⭐ + `WWW-Authenticate` (Day 140)
⭐   403 authenticated, not allowed ⭐⭐ ONLY when revealing existence is
⭐       acceptable
⭐   404 not found ***OR*** ⭐⭐ NOT YOURS — the default for anything
⭐       tenant-scoped (Day 118: a 403 confirms the record exists)
⭐   409 state conflict            ⭐ "job is not in a completable state"
⭐   410 gone                      ⭐ a resource that existed
⭐   422 semantically invalid      ⭐ the workhorse for validation
⭐   423 locked                    ⭐ optional; a 409 usually suffices
⭐   429 rate limited              ⭐⭐ ALWAYS with `Retry-After` (Day 208)
⭐   503 shedding / not ready      ⭐ with `Retry-After` too
```

# Part 3 — ⭐⭐ Pagination, filtering and the DoS surface

```
⭐⭐ CURSOR PAGINATION, FROM THE FIRST ENDPOINT (Days 176, 193):
⭐   GET /v1/jobs?limit=50&cursor=eyJjIjoiMjAyNi0…
⭐   { "data": [...], "next_cursor": "…", "has_more": true }
⭐
⭐   ⭐⭐ NO `total`. ⭐ It is a `count(*)` scan per request under MVCC
⭐     (Day 193 Q4), it is the slowest thing on the page, and it renders
⭐     a page number nobody uses. ⭐⭐ If a screen genuinely needs a
⭐     count, give it a SEPARATE, CAPPED endpoint returning "1000+".
⭐   ⭐ The cursor is an OPAQUE base64 of the sort key plus a tiebreaker
⭐     — ⭐⭐ opaque so you can change the sort without breaking clients,
⭐     and with a tiebreaker so equal timestamps cannot skip or repeat
⭐     a row (Day 193 Q3).
⭐   ⭐⭐ SIGN OR VALIDATE IT. An attacker-supplied cursor is
⭐     attacker-supplied SQL input; at minimum reject anything that does
⭐     not decode to the expected shape.
```

```
⭐⭐ FILTERING IS A DENIAL-OF-SERVICE SURFACE (Day 176). THE FOUR RULES:
⭐   ⭐ AN ALLOWLIST OF FILTERABLE FIELDS. Not "any column".
⭐   ⭐ AN ALLOWLIST OF SORT FIELDS, ⭐⭐ EACH BACKED BY AN INDEX. A
⭐     sortable field with no index is a full scan any client can
⭐     trigger.
⭐   ⭐ `limit` capped hard (⭐ 100) and defaulted (⭐ 25). ⭐⭐ Never
⭐     unbounded, and never "limit=0 means all".
⭐   ⭐⭐ FREE-TEXT SEARCH IS A SEPARATE PARAMETER WITH ITS OWN RATE
⭐     LIMIT AND MINIMUM LENGTH — Day 199. A two-character `q` across
⭐     every job is a scan you invited.
```

# Part 4 — ⭐⭐ Idempotency, and where it goes in the contract

```
⭐⭐ EVERY UNSAFE, NON-IDEMPOTENT ENDPOINT ACCEPTS `Idempotency-Key`.
⭐   POST /v1/jobs · POST /v1/jobs/{id}/dispatch · POST /invoices/{id}/pay

⭐⭐ THE CONTRACT MUST STATE ALL FOUR BEHAVIOURS, OR CLIENTS WILL GUESS:
⭐   ① first request with key K ⇒ process, store (status, body) under K
⭐   ② repeat with SAME key and SAME body ⇒ ⭐⭐ RETURN THE STORED
⭐      RESPONSE. Do not re-execute.
⭐   ③ ⭐⭐ repeat with SAME key and DIFFERENT body ⇒ ***422***
⭐      `idempotency_key_reuse`. ⭐ This is why Day 250 stored a request
⭐      hash. Without it, a client bug replays an unrelated response and
⭐      believes something happened that did not.
⭐   ④ ⭐ concurrent repeat while the first is still running ⇒ `409
⭐      request_in_progress` and let the client retry. ⭐⭐ Do NOT block
⭐      holding a connection.
⭐   ⭐ Keys expire (24 h) and that is documented.

⭐⭐ AND THE HALF PEOPLE FORGET: THE CLIENT SIDE. Document that the key
⭐   must be generated ***ONCE PER LOGICAL OPERATION*** and REUSED
⭐   ACROSS RETRIES. ⭐ A client that generates a fresh key per retry has
⭐   idempotency headers and no idempotency.
```

```
⭐ CONCURRENCY CONTROL ON UPDATES — the other half:
⭐   GET  /v1/jobs/{id}   → `ETag: "v7"`
⭐   PATCH /v1/jobs/{id}  with `If-Match: "v7"`
⭐        ⇒ ⭐⭐ 412 PRECONDITION FAILED if it changed underneath
⭐   ⭐ This is optimistic locking as an HTTP feature: it turns a silent
⭐     lost update (Day 195) into a visible 412 the UI can handle.
⭐   ⭐⭐ Decide now whether `If-Match` is REQUIRED or optional on PATCH.
⭐     Optional means it will not be sent.
```

# Part 5 — ⭐⭐ The auth matrix: a grid, not prose

```
⭐⭐ WRITE IT AS A TABLE. PROSE HIDES THE GAPS; A GRID SHOWS THE EMPTY
⭐   CELLS, AND THE EMPTY CELLS ARE THE BUGS.

⭐ | RESOURCE / ACTION      | owner | dispatcher | technician    |customer|
⭐ | job: list              | all   | all        | ⭐⭐ ASSIGNED  | ⭐ own |
⭐ |                        |       |            | ONLY          | 1 job  |
⭐ | job: read              | all   | all        | assigned only | own    |
⭐ | job: create            | ✅    | ✅          | ❌            | ❌     |
⭐ | job: dispatch          | ✅    | ✅          | ❌            | ❌     |
⭐ | job: start / complete  | ✅    | ❌          | ⭐ assigned    | ❌     |
⭐ | job: cancel            | ✅    | ✅          | ❌            | ❌     |
⭐ | photo: upload          | ✅    | ❌          | ⭐ assigned    | ❌     |
⭐ | invoice: read          | ✅    | ✅          | ❌            | ⭐ own |
⭐ | invoice: issue         | ✅    | ❌          | ❌            | ❌     |
⭐ | invoice: pay           | ✅    | ❌          | ❌            | ⭐ own |
⭐ | user: invite / disable | ✅    | ❌          | ❌            | ❌     |
⭐ | report: utilisation    | ✅    | ✅ (read)   | ❌            | ❌     |

⭐⭐ THE THREE THINGS THIS GRID FORCES YOU TO NOTICE:
⭐  ① ⭐⭐ "ASSIGNED ONLY" IS A ***ROW-LEVEL*** RULE, NOT A ROLE CHECK.
⭐     It cannot live in a decorator; it lives in the `WHERE` clause
⭐     (Day 184 #9) — ⭐ and therefore in the LIST query too, which is
⭐     exactly the bug Day 176 showed: an object-permission hook is
⭐     never called on a list.
⭐  ② ⭐ The customer is a different KIND of principal — no account, a
⭐     signed link, one job. ⭐⭐ Decide now whether that is a JWT with a
⭐     narrow scope or a separate signed-token path, because it changes
⭐     your dependency chain (Day 140).
⭐  ③ ⭐⭐ EVERY ❌ IS A TEST. Day 165's rule: the threat model becomes a
⭐     test file, and every cell in this grid is one assertion.
```

```
⭐ AND THE CONTRACT-LEVEL SECURITY DECISIONS, WRITTEN DOWN TODAY:
⭐   ⭐ access token 15 min · refresh 30 days, ROTATED, with reuse
⭐     detection revoking the family (Day 140/165)
⭐   ⭐ where the refresh token lives — ⭐⭐ httpOnly Secure SameSite
⭐     cookie for the browser, body for the mobile/API client; the
⭐     contract states both.
⭐   ⭐⭐ CORS: an explicit origin allowlist. ⭐ And the reminder from
⭐     Day 020 that CORS is not authorisation.
⭐   ⭐ Rate limits, per endpoint class, stated IN the contract so
⭐     clients can behave: auth 5/min, writes 60/min, reads 600/min,
⭐     search 20/min (Day 208).
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Generating the spec from the code | Then it can never disagree with the code, which is its job. |
| `PATCH {"status": "..."}` for transitions | A transition has preconditions, side effects and its own permission. |
| Mixing camelCase and snake_case | Pick one in the contract and never mix. |
| Adding `/v1/` later | Every existing client is then unversioned. |
| No stable machine-readable error `code` | Clients parse `message`, and you can never reword it. |
| A 403 for another tenant's record | It confirms the record exists. Use 404. |
| `total` on every list response | A `count(*)` scan per request to render a page number nobody uses. |
| A transparent, unvalidated cursor | It's attacker-supplied input, and it freezes your sort order. |
| A cursor with no tiebreaker | Equal timestamps skip or repeat rows at page boundaries. |
| Sortable fields with no index | A full scan any client can trigger. |
| Uncapped `limit` | Or `limit=0` meaning "all". |
| Idempotency without a request hash | A reused key with a different body replays the wrong response. |
| Blocking on a concurrent duplicate request | Return 409 rather than holding a connection. |
| Not documenting client-side key generation | A fresh key per retry is idempotency theatre. |
| Optional `If-Match` | It won't be sent. |
| An auth policy written as prose | The grid shows the empty cells, and the empty cells are the bugs. |
| Row-level rules expressed as role checks | They belong in the `WHERE` clause, including on list endpoints. |

## Interview questions

**Q: Why write the OpenAPI spec before the code?**

> Because a spec generated from code can never disagree with the code, and disagreeing with the code
> is the entire point of having one. Writing it first turns design questions into cheap decisions:
> what the error shape is, whether pagination is cursor or offset, which endpoints take idempotency
> keys, and what each actor may do. All of those are an afternoon now and a migration later. It also
> unblocks parallel work — the frontend can generate a client and mock a server on day one — and it
> gives you something to review. The counter-argument is that FastAPI's generated docs are excellent
> and the spec drifts from the code, which is fair; the answer is a CI check that the implemented
> routes match the spec, so drift is a build failure rather than a discovery.

**Q: How do you model a state transition in a REST API?**

> As a command sub-resource — `POST /jobs/{id}/dispatch` — not as `PATCH {"status": "dispatched"}`.
> The patch version says "set a field" when the real operation has preconditions, its own request
> shape, its own conflict conditions and its own permission. It also invites clients to set any status
> they like, so validation has to reconstruct the state machine from a diff, and every caller ends up
> needing to know the state machine. With a command endpoint, dispatch takes a technician and a window,
> returns 409 with `assignment_conflict` or `invalid_state_transition`, and is permitted for owners and
> dispatchers but not technicians — all of which is expressible in the contract. People sometimes
> object that it isn't RESTful; a transition is a resource-level command, and it's a much better fit
> than pretending state is just another field.

**Q: What's in your error contract?**

> A single shape everywhere: a stable machine-readable `code`, a human `message`, optional field-level
> `details`, and a `request_id` that's also in the response header. The two rules that matter are that
> clients branch on `code` and may never parse `message` — stating that in the contract is what lets
> me reword messages freely — and that the request id is on every error, because it's what turns a
> support email into a log query. On status codes I'd pre-decide the table rather than choose per
> endpoint, and the one worth calling out is using 404 rather than 403 for anything tenant-scoped: a
> 403 confirms the record exists, which is an information leak in a multi-tenant system. And 5xx
> bodies say nothing but a code and the request id — no stack traces, no SQL, and nothing that
> distinguishes "no such user" from "wrong password".

**Q: How does idempotency work in your API?**

> Every unsafe non-idempotent endpoint accepts an `Idempotency-Key`, and the contract specifies all
> four behaviours because clients will otherwise guess. First use processes and stores the status and
> body. A repeat with the same key and same body returns the stored response without re-executing. A
> repeat with the same key and a *different* body is a 422 — which is why the key table stores a hash
> of the request, and without it a client bug replays an unrelated response and believes something
> happened that didn't. And a concurrent duplicate while the first is in flight gets a 409 rather than
> blocking, because holding a connection open is how one client's retry storm consumes your pool. The
> half people forget is the client contract: the key must be generated once per logical operation and
> reused across retries — a fresh key per retry is idempotency theatre.

**Q: How do you document authorisation?**

> As a grid — actor by resource-action — because prose hides gaps and a table shows empty cells, and
> the empty cells are the bugs. Filling it in forces three realisations. First, that some rules aren't
> role checks at all: "a technician sees only assigned jobs" is row-level, so it belongs in the `WHERE`
> clause rather than a decorator, and crucially it has to be in the *list* query too — which is the
> exact bug where an object-permission hook is never called on a list endpoint and the detail view is
> correctly protected while the collection returns everything. Second, that the customer is a different
> kind of principal — no account, a signed link, one job — which changes the dependency chain and has
> to be decided rather than discovered. And third, that every ❌ in the grid is a test: the threat model
> becomes a test file, one assertion per cell.

## Today's build

1. ⭐ Write `openapi.yaml` by hand for the core resources. Lint it (`spectral` or `redocly`).
2. ⭐⭐ Model every state transition as a command sub-resource. List each one's 409 conditions.
3. ⭐ Fix the four naming decisions and apply them consistently. Put them in the spec description.
4. ⭐⭐ Define the error schema once and `$ref` it from every error response.
5. ⭐ Write the status-code table into the spec's description, including the 404-not-403 rule.
6. ⭐⭐ Define the cursor pagination envelope. Write down what the cursor encodes and how you validate it.
7. ⭐ Write the allowlists: filterable fields, sortable fields (each with its index), limit cap and default.
8. ⭐⭐ Document `Idempotency-Key` on every unsafe endpoint, with all four behaviours and the client-side rule.
9. ⭐ Add `ETag`/`If-Match` to updatable resources and decide required vs optional.
10. ⭐⭐ Write the full auth matrix. Mark every row-level rule distinctly from every role rule.
11. ⭐ Write the security section: token lifetimes, storage per client type, CORS allowlist, rate limits per endpoint class.
12. ⭐⭐ Generate a client from the spec and write one script that calls three endpoints against a mock. If the spec can't do that, it isn't finished.

## 🎙️ Articulation drill

**Two minutes: "Walk me through your API design."**

Don't list endpoints. Lead with the three decisions that were expensive to change: **transitions as
command sub-resources rather than status patches**, **cursor pagination with no total**, and **one error
shape with a stable code that clients branch on and a message they may never parse.** Give the reason
for each in a sentence — a transition has preconditions and its own permission; a total is a scan per
request to render a page number nobody reads; a stable code is what lets you reword messages forever.
Then the security half: 404 rather than 403 for tenant-scoped resources, because a 403 confirms
existence. Then close on the auth matrix and the sentence that shows you've been bitten: **"a
technician sees only assigned jobs" is a row-level rule, so it lives in the `WHERE` clause and it has
to be in the list query too — an object-permission hook is never called on a list.**
