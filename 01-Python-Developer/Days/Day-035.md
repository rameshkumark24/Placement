# Part 1 — ⭐⭐ Hash table, open addressing

```
⭐ THE BASIC MECHANISM:
⭐   1. i = hash(key) & (table_size - 1)      ⭐⭐ mask, not modulo — the table is a POWER OF TWO
⭐   2. look at slot i
⭐   3. empty ⇒ the key is not present
⭐      occupied ⇒ ⭐⭐ compare: `is` first (fast path), then `==`
⭐      different key ⇒ ⭐ COLLISION ⇒ PROBE for another slot
```

```
⭐⭐ COLLISION STRATEGY — and this is the part that distinguishes a good answer:

⭐ ⭐⭐ CHAINING (Java's HashMap): each slot holds a LINKED LIST of entries.
⭐    ⇒ simple, but ⭐ pointer chasing ⇒ cache misses, and per-node allocation.

⭐ ⭐⭐ OPEN ADDRESSING (Python): everything lives IN the table; on collision, probe elsewhere.
⭐    ⇒ ⭐ better cache locality — the probe sequence stays in the same memory region
⭐    ⇒ ⭐⭐ CPython's probe is not linear. It uses a PERTURBATION:
⭐         perturb = hash;  j = (5*j + 1 + perturb) & mask;  perturb >>= 5
⭐    ⇒ ⭐⭐ the HIGH bits of the hash are mixed in gradually, so keys that collide in the
⭐         low bits diverge quickly — while early probes stay cache-local.
```

⭐ **Deletion needs a tombstone.** You cannot simply blank a slot, because that would break a probe
sequence that passes through it — a later key would appear absent. **CPython writes a `DUMMY`
marker**, which is skipped on lookup but treated as free on insertion, and cleaned up on resize.

# Part 2 — ⭐⭐ The compact dict (3.6+) — and why order became a guarantee

```
⭐ OLD LAYOUT (≤3.5): ONE sparse array of (hash, key, value) — 24 bytes per SLOT,
⭐   ⇒ ⭐ and slots are mostly EMPTY (load factor ≤ 2/3), so most of that is wasted.

⭐⭐ COMPACT LAYOUT (3.6+): TWO arrays.

⭐   indices:  [ -1, 1, -1, -1, 0, -1, 2, -1 ]     ⭐⭐ sparse, but only SMALL INTEGERS
⭐                                                    (1, 2, 4 or 8 bytes, sized to the table)
⭐   entries:  [ (hash, "a", 1), (hash, "b", 2), (hash, "c", 3) ]   ⭐⭐ DENSE, IN INSERTION ORDER

⭐   ⇒ lookup: hash ⇒ index into `indices` ⇒ that gives a position in `entries`
⭐   ⇒ ⭐⭐ 20–25% LESS MEMORY, because the wasted sparse slots are now tiny ints
⭐   ⇒ ⭐⭐ AND ITERATION IS A LINEAR WALK OF `entries` — which is INSERTION ORDER, FOR FREE.
```

```
⭐⭐ SO: insertion order was a SIDE EFFECT of a MEMORY optimisation in 3.6,
⭐   and was made a LANGUAGE GUARANTEE in 3.7 once everyone had come to rely on it.
⭐   ⇒ ⭐ that is a genuinely nice piece of history and a great thing to say in an interview.
⭐   ⇒ ⚠️ ⭐⭐ NOTE: dicts are ORDERED, not SORTED. Two different claims.
```

⭐ **`PYTHONHASHSEED` randomisation (Day 029) does not affect iteration order any more** — order is
insertion order, independent of hashes. **Sets are still hash-ordered and unpredictable** (Day 036),
which is a distinction people get wrong.

## ⭐ Resizing

```
⭐⭐ WHEN: when used > 2/3 of the table ⇒ ⭐ grow to the next power of two ≥ used*3
⭐   ⇒ ⭐⭐ REHASH EVERYTHING — every key is reinserted into the new table.
⭐   ⇒ ⭐ so a single insert is O(1) AMORTISED, exactly like list.append (Day 033):
⭐        most are cheap, occasionally one is O(n), geometric growth amortises it.
⭐   ⇒ ⭐ 2/3 is the trade: higher load ⇒ less memory, more probing.
```

⭐ **Key-sharing dicts (PEP 412):** instances of the same class share **one** keys table, and each
instance stores only the values array. ⭐⭐ **That is why an ordinary object is not as expensive as
"a whole dict per instance" sounds** — though `__slots__` (Day 028) is still substantially smaller,
and adding attributes outside `__init__` breaks the sharing.

# Part 3 — ⭐ Complexity, and the operations worth knowing

| Operation | ⭐ Average | ⭐ Worst |
|---|---|---|
| `d[k]`, `k in d`, `d[k] = v`, `del d[k]` | ⭐⭐ **O(1)** | ⭐ O(n) — pathological collisions |
| `len(d)` | O(1) | |
| Iteration | O(n) | ⭐⭐ **in insertion order** |
| `d.keys()/.values()/.items()` | ⭐ O(1) — **views, not copies** | |
| `d1 \| d2` (3.9+) | O(n+m) | ⭐ new dict; right wins on conflict |
| `d.copy()` | O(n) | ⭐ shallow (Day 025) |

⚠️ ⭐⭐ **The worst case is a real attack, not a theoretical one:** if an attacker controls keys and
can predict the hash, they can force every key into one probe sequence and turn O(1) into O(n) —
**a hash-collision DoS.** ⭐ **That is why string hashing is randomised per process**, and why
`PYTHONHASHSEED` exists.

```python
# ⭐ The API worth having in your fingers:
d.get(k)                 # ⭐ None if missing — never raises
d.get(k, default)
d.setdefault(k, [])      # ⭐⭐ get, or insert-and-return — ⚠️ the default is BUILT even when unused
d.pop(k, default)
d.popitem()              # ⭐ LIFO — the LAST inserted pair (3.7+)
d.update(other)          # ⭐ or d |= other
{**a, **b}               # ⭐ merge; b wins
d.items()                # ⭐⭐ a VIEW — it reflects later changes to d
```

⚠️ ⭐⭐ **Views are live, and that is the point:**

```python
keys = d.keys()
d["new"] = 1
len(keys)                # ⭐⭐ already updated — it is a window, not a snapshot
list(d.keys())           # ⭐ take a snapshot when you need one
```

```python
# ⚠️⚠️ ⭐⭐ NEVER RESIZE A DICT WHILE ITERATING IT:
for k in d:
    if bad(k): del d[k]          # ⭐⭐ RuntimeError: dictionary changed size during iteration
for k in list(d):                # ⭐ snapshot the keys first
    if bad(k): del d[k]
d = {k: v for k, v in d.items() if not bad(k)}    # ⭐ or rebuild
```

⭐ **Changing a *value* during iteration is legal** — only inserting or deleting keys is not.
**Python raises here rather than silently skipping, unlike the list case (Day 033)** — because a
dict resize would invalidate the iterator's position entirely.

# Part 4 — ⭐⭐ Dicts are the language

```
⭐⭐ WHERE DICTS ARE ALREADY DOING THE WORK FOR YOU:
⭐   · module globals()          — a dict
⭐   · an instance's __dict__    — a dict (Day 023)
⭐   · a class's namespace       — a dict (a mappingproxy)
⭐   · **kwargs                  — a dict (Day 034)
⭐   · attribute lookup          — dict lookups along the MRO (Day 032)
⭐   · the interpreter's builtins — a dict
⭐ ⇒ ⭐⭐ THIS IS WHY DICT PERFORMANCE IS INTERPRETER PERFORMANCE, and why so much CPython
⭐      optimisation work (specialising adaptive interpreters, inline caches) is about
⭐      making these lookups cheaper.
```

```python
# ⭐⭐ THE DISPATCH IDIOM — replaces if/elif chains (and Day 023's registry):
HANDLERS = {"csv": parse_csv, "json": parse_json}
parser = HANDLERS[fmt]                    # ⭐ O(1), extensible, testable
parser(data)

# ⭐ Grouping and counting — before reaching for pandas
from collections import defaultdict, Counter
groups = defaultdict(list)
for r in rows: groups[r.city].append(r)
counts = Counter(words)                   # ⭐ Day 038

# ⭐ Memoisation is a dict (Day 051 makes it a decorator)
```

⚠️ ⭐ **`d.keys()` in a membership test is redundant:** `k in d` already tests keys, and it is the
faster and clearer form. ⭐⭐ **And `if k in d: d[k]` does two lookups where `d.get(k)` does one** —
minor, but in a hot loop it is free to get right.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"Python dicts use chaining"** | ⭐⭐ Open addressing with a perturbed probe. |
| Saying dicts are "sorted" | ⭐ **Ordered** — insertion order, not sorted order. |
| Thinking order was always guaranteed | ⭐ 3.6 side effect, 3.7 guarantee. Say the history. |
| ⭐⭐ **Adding/deleting keys while iterating** | ⭐⭐ `RuntimeError`. Iterate `list(d)`. |
| Treating `.items()` as a snapshot | ⭐ It is a live view. |
| `k in d.keys()` | ⭐ `k in d`. |
| `d[k]` with no `try` on possibly-missing keys | ⭐ `d.get(k, default)`. |
| `setdefault` with an expensive default | ⭐⭐ The default is evaluated even when unused. |
| Assuming O(1) always | ⭐ Adversarial keys can force O(n) — hence hash randomisation. |
| Unhashable keys | ⭐ Day 029 — lists and dicts cannot be keys. |

## Interview questions

**Q: How does a Python dict work?**
> It's a hash table using open addressing. The key's hash is masked against the table size — always a
> power of two — to pick a slot; on collision it probes using a perturbation scheme that folds in the
> high bits of the hash gradually, so early probes stay cache-local while keys that collide in the
> low bits diverge quickly. That's different from Java's HashMap, which chains a linked list per
> bucket; open addressing keeps everything in one array, which is much better for cache locality.
> Deletion writes a tombstone rather than clearing the slot, because clearing it would break probe
> sequences that pass through it.

**Q: Why do dicts preserve insertion order?**
> Because of the compact layout introduced in 3.6. Instead of one sparse array of entries, there are
> two: a sparse array of small integer indices, and a dense array of entries stored in insertion
> order. That was a memory optimisation — the wasted sparse slots became one-byte integers instead of
> 24-byte entries, saving 20 to 25% — and ordered iteration fell out of it, because iterating just
> walks the dense array. It was an implementation detail in 3.6 and became a language guarantee in
> 3.7. Worth being precise: dicts are ordered, not sorted, and sets are still unordered because they
> don't use that layout.

**Q: What's the complexity, and when does it degrade?**
> O(1) average for lookup, insert and delete; O(n) worst case when many keys collide into the same
> probe sequence. That's not purely theoretical — if an attacker controls the keys and can predict
> hashes, they can force the worst case deliberately, which is a denial-of-service. It's why CPython
> randomises string hashing per process, and why a hash value is only meaningful inside one process.

**Q: When does a dict resize, and what does that cost?**
> When it's more than two-thirds full. It allocates a table sized to the next power of two at least
> three times the number of used slots and reinserts every key, which is O(n). Individual inserts are
> therefore O(1) amortised, exactly like list append — geometric growth means the occasional
> expensive operation averages out. Two-thirds is the trade-off point between memory and probe
> length.

**Q: Why can't you delete keys while iterating?**
> Because insertion or deletion can trigger a resize, which rehashes everything and invalidates the
> iterator's position entirely. CPython detects it and raises `RuntimeError` rather than silently
> producing wrong results — which is better than the list case, where mutating during iteration just
> skips elements. Changing a value is fine; only changing the set of keys is a problem. The fix is to
> iterate over `list(d)` or rebuild with a comprehension.

**Q: Why does dict performance matter so much in Python specifically?**
> Because the language is built from dicts. Module globals, instance attributes, class namespaces,
> `**kwargs`, and every attribute lookup along the MRO are dict operations. Making dicts faster makes
> the interpreter faster, which is why so much CPython optimisation work — key-sharing dicts, inline
> caches, the specialising interpreter — is really about making these lookups cheaper.
