**P-435** · 📐 **RAG evaluation** — ⭐⭐ two failures, opposite fixes, so measure them apart

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a wrong answer in a RAG system has exactly two causes — retrieval didn't
> find it, or generation ignored it — and since the fixes point in opposite directions, an end-to-end

# Part 1 — ⭐⭐ Why end-to-end accuracy is the wrong first metric

```
⭐ YOUR SYSTEM SCORES 61%. ⭐ What do you change?

⭐   ⭐ chunk size? ⭐ embedding model? ⭐ k? ⭐ the reranker?
⭐   ⭐ the prompt? ⭐ the model? ⭐ the context ordering?
⭐   ⭐⭐ ONE NUMBER CANNOT DISTINGUISH SEVEN CAUSES, ⭐ so what
⭐     actually happens is you change three things at once, the
⭐     number moves by 4 points, and ⭐⭐ YOU HAVE LEARNED
⭐     NOTHING BECAUSE YOU CANNOT ATTRIBUTE THE MOVE.

⭐ ***SPLIT THE PIPELINE AT ITS SEAM:***
⭐
⭐   question ──► RETRIEVAL ──► context ──► GENERATION ──► answer
⭐                   │                          │
⭐              ⭐⭐ RECALL@k              ⭐⭐ FAITHFULNESS
⭐              "is the answer            "given this context,
⭐               in the context           did it answer
⭐               at all?"                  correctly and only
⭐                                         from the context?"

⭐⭐ AND THE RELATIONSHIP THAT MAKES IT A ***CEILING***:
⭐   ⭐ recall@k = 0.70 ⇒ ***30% OF QUESTIONS ARE UNANSWERABLE NO
⭐     MATTER WHAT PROMPT OR MODEL YOU USE.*** ⭐ Not "harder".
⭐     Unanswerable. ⭐ The information is not in the window.
⭐   ⭐⭐ ⇒ END-TO-END ACCURACY CAN NEVER EXCEED RECALL@k
⭐     (ignoring the model answering correctly from parametric
⭐     memory, which you should be ***suppressing***, not
⭐     harvesting).
⭐   ⭐⭐ ⇒ SO IF RECALL IS 0.70, PROMPT ENGINEERING IS THE WRONG
⭐     PROJECT. ⭐ People spend weeks there anyway.
```

# Part 2 — Building a gold set in an afternoon, without labellers

```
⭐ THE OBJECTION: ⭐ "we don't have labelled data."
⭐ ⭐⭐ YOU DO. ⭐ Your corpus ***is*** the labels, if you generate
⭐   backwards.

⭐ ***THE SYNTHETIC GOLD SET — 3 HOURS, ~150 CASES:***
⭐   ⭐ ① sample 150 chunks, stratified across documents and
⭐     document ***types*** (policy, FAQ, table, code) —
⭐     ⭐⭐ NOT UNIFORMLY, OR TABLES WILL BE UNDER-REPRESENTED
⭐     AND THEY ARE WHERE IT BREAKS;
⭐   ⭐ ② for each, ask a strong model: ⭐ "write a question this
⭐     passage answers, phrased the way a real user would type
⭐     it — ⭐⭐ DO NOT REUSE THE PASSAGE'S VOCABULARY";
⭐   ⭐ ③ ⭐⭐ THE CHUNK THAT PRODUCED THE QUESTION IS THE
⭐     KNOWN-CORRECT CHUNK. ⭐ That is your label, free.
⭐   ⭐ ④ ***HUMAN-REVIEW 20%*** — ⭐ delete the unanswerable, the
⭐     ambiguous and the trivially keyword-matched.

⭐⭐ THE THREE HONEST LIMITATIONS — SAY THEM BEFORE YOU ARE
⭐   ASKED:
⭐   ⭐ ⓐ ***SYNTHETIC QUESTIONS ARE TOO CLEAN.*** ⭐ Real users
⭐     type "refund??" and three words of context.
⭐   ⭐ ⓑ ***IT ONLY TESTS SINGLE-CHUNK ANSWERS.*** ⭐⭐ THE HARD
⭐     ONES NEED TWO CHUNKS AND YOUR GENERATOR WILL NEVER WRITE
⭐     THEM. ⭐ Add multi-hop cases by hand.
⭐   ⭐ ⓒ ***IT ENCODES YOUR CHUNKING.*** ⭐⭐ IF YOU RE-CHUNK, THE
⭐     "CORRECT CHUNK" IDS ARE STALE — ⭐ so label the
⭐     ***`doc_id` + a verbatim answer span***, not the chunk id.
⭐     ⭐⭐ THIS ONE DETAIL SAVES YOU REBUILDING THE SET.
⭐   ⭐ ⇒ so: ⭐⭐ SYNTHETIC FOR VOLUME, ***REAL PRODUCTION
⭐     QUESTIONS FOR TRUTH***. ⭐ Replace synthetic cases with
⭐     real ones as they arrive.

⭐⭐ AND THE SET THAT MATTERS MOST: ⭐ ***20 QUESTIONS THE CORPUS
⭐   GENUINELY CANNOT ANSWER.*** ⭐ Plausible, on-topic, and
⭐   simply absent. ⭐⭐ THE ONLY CORRECT BEHAVIOUR IS ABSTENTION
⭐   (DAY 422). ⭐ Most systems score near zero here and nobody
⭐   finds out until a customer does.
```

# Part 3 — Retrieval metrics, and which one to actually use

```
⭐ ***RECALL@k*** — of the questions, what fraction had a
⭐   correct chunk anywhere in the top k? ⭐⭐ THIS IS THE ONE.
⭐   ⭐ It is the ceiling. ⭐ Report it at your ***production k***
⭐     and at k=50 (pre-rerank) so you can see whether the loss
⭐     is in retrieval or in reranking.

⭐ ***PRECISION@k*** — what fraction of the k are relevant?
⭐   ⭐ Matters because irrelevant context costs tokens ***and***
⭐     distracts the model. ⭐⭐ SECONDARY: A USELESS CHUNK IS
⭐     CHEAP, A MISSING ONE IS FATAL.

⭐ ***MRR*** — 1/rank of the first correct hit, averaged.
⭐   ⭐ Useful when the user reads a result list.

⭐ ***NDCG@k*** — position-discounted with graded relevance.
⭐   ⭐⭐ THE RIGHT ACADEMIC ANSWER AND USUALLY OVERKILL: ⭐ it
⭐     needs graded labels you do not have.

⭐⭐ THE PRACTICAL SET: ⭐ ***RECALL@k AS THE GATE, MRR AS THE
⭐   TIEBREAK, PRECISION@k WATCHED FOR COST.***
```

```python
def recall_at_k(cases, retrieve, k: int) -> float:
    """⭐ cases: [(question, tenant, {gold_doc_ids})]"""
    hits = 0
    for q, tenant, gold in cases:
        got = {h.doc_id for h in retrieve(q, tenant_id=tenant, k_final=k)}
        hits += bool(got & gold)          # ⭐⭐ ANY gold doc counts
    return hits / len(cases)

def mrr(cases, retrieve, k: int) -> float:
    total = 0.0
    for q, tenant, gold in cases:
        for i, h in enumerate(retrieve(q, tenant_id=tenant, k_final=k), 1):
            if h.doc_id in gold:
                total += 1 / i
                break
    return total / len(cases)
```

```
⭐⭐ NOTE WHAT THESE FUNCTIONS DO ***NOT*** DO: ⭐ call an LLM.
⭐   ⭐ They are deterministic, run in seconds, cost nothing, and
⭐     can run on every commit.
⭐   ⭐⭐ THAT IS WHY YOU BUILD THEM FIRST — ⭐ retrieval evals
⭐     are ordinary software tests, and they are where most of
⭐     your improvement will come from.
```

# Part 4 — Generation metrics, with the important one first

```
⭐ ① ***FAITHFULNESS / GROUNDEDNESS*** — ⭐⭐ IS EVERY CLAIM IN
⭐   THE ANSWER SUPPORTED BY THE RETRIEVED CONTEXT? ⭐ This is
⭐   the hallucination metric and the one that matters most,
⭐   because ⭐⭐ AN UNFAITHFUL ANSWER IS INDISTINGUISHABLE FROM A
⭐   FAITHFUL ONE TO A USER.
⭐   ⭐ Two ways to measure, and use both:
⭐     ⭐ ⓐ ***PROGRAMMATIC (FREE, EXACT):*** ⭐ require a
⭐       verbatim `supporting_quote` per claim and assert it
⭐       appears in the context (Day 424). ⭐⭐ NO JUDGE, NO
⭐       AMBIGUITY, RUNS IN CI.
⭐     ⭐ ⓑ ***JUDGED (BROADER, NOISIER):*** ⭐ decompose the
⭐       answer into claims, ask a judge whether the context
⭐       entails each. ⭐⭐ DAY 426'S FOUR FAILURE MODES ALL
⭐       APPLY.

⭐ ② ***ANSWER CORRECTNESS*** — against a reference answer.
⭐   ⭐ Judged. ⭐⭐ NOT EXACT-MATCH — the model will phrase it
⭐     differently and be right.

⭐ ③ ***ANSWER RELEVANCE*** — did it answer ***the question
⭐   asked***, rather than something adjacent it found?

⭐ ④ ***CONTEXT UTILISATION*** — of the k chunks provided, how
⭐   many were actually used? ⭐⭐ LOW UTILISATION MEANS YOU ARE
⭐   PAYING FOR TOKENS THAT DO NOTHING — ⭐ lower k and save
⭐   money at equal quality.

⭐ ⑤ ⭐⭐ ***ABSTENTION RATE ON THE UNANSWERABLE SET.*** ⭐ The
⭐   single most diagnostic number in the whole harness. ⭐ It is
⭐   the only metric that goes ***down*** when you make the model
⭐   more eager to please, ⭐⭐ WHICH IS EXACTLY WHAT SYCOPHANCY
⭐   TUNING (DAY 417) DOES.
```

# 💬 Interview

**1. "How do you evaluate a RAG system?"**

⭐ Separately at each stage, because a wrong answer has two possible causes with opposite fixes:
retrieval didn't surface the information, or generation had it and didn't use it. ⭐⭐ An end-to-end
score tells me something is broken while actively hiding which — and the instinct is always to rewrite
the prompt, so if the real problem is recall you burn two weeks proving the prompt was never the issue.
⭐ So I measure recall@k on retrieval, which is deterministic, costs nothing and runs on every commit,
and faithfulness plus abstention on generation. ⭐⭐ The relationship that matters is that recall@k is a
**ceiling**: at 0.70, thirty percent of questions are unanswerable no matter what model or prompt I use,
because the information isn't in the window.

**2. "You have no labelled data. What now?"**

⭐ The corpus is the labels if you generate backwards. ⭐⭐ Sample 150 chunks stratified across document
*types* — not uniformly, or tables get under-represented and tables are where it breaks — ask a strong
model to write the question each passage answers in the words a real user would type, and the chunk that
produced it is the known-correct chunk. ⭐ Then human-review twenty percent to delete the ambiguous and
the trivially keyword-matched. ⭐⭐ Three hours. ⭐ One detail saves you rebuilding it: label the
`doc_id` and a verbatim answer span rather than the chunk id, because chunk ids become meaningless the
moment you change the chunker — and changing the chunker is exactly the experiment you're building this
to run.

**3. "What's wrong with synthetic eval questions?"**

⭐ Three things, and I'd say them before being asked. ⭐⭐ They're too clean — real users type "refund??"
and three words, not a well-formed sentence. ⭐ They only test single-chunk answers, because the
generator writes a question from one passage, so the hard multi-hop cases have to be added by hand.
⭐ And they encode your current chunking. ⭐⭐ So synthetic is for volume and real production questions
are for truth: every thumbs-down in production is a candidate eval case that's already labelled with
what went wrong, and after three months the set is made of real failures. ⭐ That set is a moat — a
competitor copies the prompt in a minute and can't copy that.

**4. "Recall is 0.68 and faithfulness is 0.94. What do you do?"**

⭐ I don't touch the prompt. ⭐⭐ Faithfulness at 0.94 says generation is doing its job — when the answer
is in the context, the model uses it. ⭐ The 32% gap is retrieval, so I work the retrieval ladder in
cost order: chunking first, because it's the ceiling and the fixes are free; then the contextual prefix;
then hybrid search; then a reranker; and only then a different embedding model, since that's a full
reindex. ⭐⭐ I'd also compare recall@50 against recall@8 — if recall@50 is 0.9 and recall@8 is 0.68,
retrieval found it and my reranker is dropping it, which is a completely different fix.

**5. "What's the most diagnostic single metric?"**

⭐⭐ Abstention rate on a set of questions the corpus genuinely can't answer. ⭐ Twenty plausible,
on-topic questions where the information simply isn't there, and the only correct behaviour is "I don't
have that." ⭐⭐ Most systems score near zero and nobody finds out until a customer does. ⭐ It's also
the only metric that goes **down** as you make the model more agreeable, which is exactly what
preference tuning does — so it catches a class of regression that every other metric rewards.

**6. "How do you measure hallucination without a judge?"**

⭐ Make the schema do it. ⭐⭐ Every extracted claim carries a verbatim `supporting_quote`, and I assert
programmatically that the quote appears in the retrieved context. ⭐ No judge, no ambiguity, no cost,
runs in CI. ⭐ It doesn't catch everything — a correct quote can support a wrong inference — so I also
run a judged claim-entailment metric, with the caveat that judges have their own failure modes and I've
measured human–human agreement first to know the ceiling. ⭐⭐ But the programmatic check catches the
large, embarrassing category — invented numbers and invented names — for free.

**7. "How does this run in CI without costing a fortune?"**

⭐ Three cadences. ⭐⭐ Retrieval metrics and the cross-tenant leak test on every commit — no LLM calls,
seconds, free, so there's no excuse not to have it. ⭐ The full suite including judged metrics on any PR
touching prompts, schemas or retrieval config: minutes and a few dollars. ⭐ And nightly against the
production config, which is what catches a provider silently updating a model behind a stable name.
⭐⭐ The gates differ in kind — the leak count is a hard zero with no tolerance band, because a security
invariant isn't a score, while recall gets a band above measured run-to-run noise so I'm not blocked by
sampling variance.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "how do you know your RAG system is any good?"**

Open with the decomposition, because it's the whole insight. **A wrong answer has exactly two causes:
retrieval didn't find the information, or generation had it and didn't use it. Those have opposite
fixes — one is chunking and search, the other is prompting and model choice — so an end-to-end score
tells me something is broken while hiding which. And the instinct on a bad answer is always to rewrite
the prompt, so if recall is the real problem you burn two weeks proving the prompt was never the issue.**

Then the ceiling. **Recall@k is measured first because it's a ceiling, not a metric. At 0.70, thirty
percent of questions are unanswerable regardless of model or prompt, because the information isn't in
the window. And recall evals are ordinary software tests — deterministic, no LLM calls, seconds, free —
so they run on every commit alongside the cross-tenant leak test.**

Then the gold set, with its limits stated up front. **We had no labelled data, so we generated
backwards: sample a hundred and fifty chunks stratified by document type, ask a model to write the
question each one answers in the words a user would type, and the source chunk is the label. Three
hours. We label the doc id and a verbatim answer span rather than the chunk id, because chunk ids die
the moment you change the chunker — which is precisely the experiment the harness exists to run. And
synthetic questions are too clean and only test single-chunk answers, so it's synthetic for volume and
real production questions for truth. Every thumbs-down is a candidate case that arrives pre-labelled
with what went wrong.**

Close on the two numbers that matter and the gate that isn't a score. **The most diagnostic thing we
have is twenty questions the corpus genuinely cannot answer, where the only correct behaviour is
abstention. Most systems score near zero there and find out from a customer. It's also the one metric
that goes down as a model gets more agreeable, so it catches regressions everything else rewards. And
faithfulness we measure for free: every claim carries a verbatim quote and we assert programmatically
that it appears in the context. The cross-tenant leak count is the one gate with no tolerance band —
it's zero or the build fails, because a security invariant isn't a score.**
