# Day 406 🔭

**P-406** · 🔭 **CQRS, read models and projection lag**

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: CQRS is the decision to stop pretending one model serves both writing and
> reading — and the entire price is a lag you must measure, expose and design around, because a lag
> you have not measured is not eventual consistency, it is a bug you have not found yet.**

---

# Part 1 — Three levels of commitment, and most teams need the first

```
⭐⭐ CQRS IS NOT ONE THING. IT IS A LADDER, AND PEOPLE JUMP TO
⭐   THE TOP RUNG BECAUSE THAT IS THE ONE IN THE BLOG POSTS.

⭐ ① ⭐⭐ ***SEPARATE MODELS, ONE DATABASE, ONE SERVICE.***
⭐    ⭐ Command handlers work with rich domain objects; ⭐ queries
⭐    are hand-written SQL returning flat read DTOs, ⭐⭐ BYPASSING
⭐    THE ORM AND THE DOMAIN ENTIRELY.
⭐    ⭐⭐ COST: ALMOST NOTHING. ⭐ No new infrastructure, no lag,
⭐    no consistency change. ⭐⭐ AND IT REMOVES THE SINGLE
⭐    BIGGEST SOURCE OF SLOW PYTHON ENDPOINTS: LOADING FIFTY
⭐    FULLY-HYDRATED ORM OBJECTS WITH THEIR RELATIONSHIPS TO
⭐    RENDER A TABLE OF FIVE COLUMNS (DAY 190).
⭐    ⭐⭐ ***THIS IS WHAT MOST TEAMS ACTUALLY NEED.***

⭐ ② ⭐ ***SEPARATE READ SCHEMA, SAME DATABASE.*** ⭐ Denormalised
⭐    tables or materialised views, updated in the same
⭐    transaction or by a trigger/refresh.
⭐    ⭐ Cost: a little duplication. ⭐⭐ STILL NO DISTRIBUTED LAG IF
⭐    YOU UPDATE IN-TRANSACTION.

⭐ ③ ⭐ ***SEPARATE READ STORE.*** ⭐ Elasticsearch, Redis, a
⭐    different database, updated asynchronously from events.
⭐    ⭐⭐ COST: A NEW DATASTORE TO OPERATE, A LAG, A REBUILD
⭐    PROCEDURE, AND A NEW CLASS OF BUG — ***DIVERGENCE***.

⭐⭐ ⇒ THE TEST BEFORE CLIMBING: ***NAME THE QUERY THAT IS SLOW
⭐   AND CANNOT BE MADE FAST WITH AN INDEX.*** ⭐ If you cannot
⭐   name it, you are at level 1 and that is correct.
⭐   ⭐⭐ "IT WOULD BE CLEANER" IS NOT A QUERY.
```

# Part 2 — Why the two models genuinely differ

```
⭐ THE WRITE MODEL IS NORMALISED ***TO PROTECT INVARIANTS***:
⭐   ⭐ one fact in one place, so it cannot be contradicted.
⭐ THE READ MODEL IS DENORMALISED ***TO ANSWER A QUESTION IN ONE
⭐   SEEK***: ⭐ everything the screen needs, in one row.

⭐⭐ AND THEY ARE IN DIRECT OPPOSITION: ***THE JOIN THAT MAKES
⭐   THE READ FAST IS THE DUPLICATION THAT MAKES THE WRITE
⭐   SLOW AND RISKY.*** ⭐ Day 359's shape ② — precompute versus
⭐   compute-on-read — ⭐⭐ AND CQRS IS SIMPLY THE DECISION TO STOP
⭐   COMPROMISING BETWEEN THEM IN ONE SCHEMA.

⭐ ⭐ The read model is ***disposable***. ⭐⭐ THAT IS ITS DEFINING
⭐   PROPERTY: IT CAN ALWAYS BE DELETED AND REBUILT FROM THE
⭐   SOURCE OF TRUTH. ⭐ The moment it holds a fact that exists
⭐   nowhere else — ⭐⭐ A COUNTER SOMEONE INCREMENTED DIRECTLY, A
⭐   FLAG AN ADMIN TOOL SET — ⭐⭐ IT IS NO LONGER A PROJECTION, IT
⭐   IS A SECOND SOURCE OF TRUTH, AND YOU HAVE LOST THE
⭐   PROPERTY YOU BUILT IT FOR (DAY 359 SHAPE ⑦).
```

# Part 3 — ⭐⭐ Projection lag, and the three fixes that work

```
⭐⭐ ***THE READ MODEL IS ALWAYS BEHIND. THE ONLY QUESTIONS ARE
⭐   BY HOW MUCH, AND WHAT THE USER SEES.***

⭐ THE FAILURE, WHICH IS ALWAYS THE SAME ONE: ⭐ user clicks
⭐   Save, ⭐ the command succeeds, ⭐ the UI redirects to the list,
⭐   ⭐⭐ THE LIST READS THE PROJECTION, ⭐ the projection is 300 ms
⭐   behind, ⭐⭐ AND THE USER'S OWN CHANGE IS NOT THERE. ⭐ They
⭐   click Save again. ⭐⭐ NOW YOU HAVE TWO.

⭐⭐ THE THREE FIXES, BEST FIRST:
⭐ ① ⭐⭐ ***RETURN THE NEW STATE FROM THE COMMAND.*** ⭐ The
⭐    handler already knows what it wrote. ⭐⭐ RETURN IT, AND THE
⭐    UI DOES NOT NEED TO RE-READ AT ALL.
⭐    ⭐⭐ THIS IS THE SIMPLEST FIX, IT REMOVES THE PROBLEM RATHER
⭐    THAN HIDING IT, AND IT IS THE ONE PEOPLE SKIP BECAUSE
⭐    "COMMANDS SHOULD RETURN VOID" IS A RULE SOMEBODY READ.
⭐    ⭐ Commands returning the affected entity is fine. ⭐ Do it.
⭐ ② ⭐ ***ROUTE THAT ONE READ TO THE WRITE MODEL.*** ⭐ The
⭐    "detail page immediately after save" read goes to the
⭐    source of truth; ⭐ every other read goes to the projection.
⭐    ⭐⭐ ONE ENDPOINT, NOT ALL OF THEM.
⭐ ③ ⭐⭐ ***A VERSION TOKEN — THE GENERAL ANSWER.*** ⭐ The command
⭐    returns the position it wrote at (an offset, an LSN, an
⭐    aggregate version). ⭐ The client sends it on the next read.
⭐    ⭐⭐ THE READ ENDPOINT WAITS — BOUNDED, SAY 500 ms — UNTIL
⭐    THE PROJECTION HAS REACHED THAT POSITION, THEN ANSWERS.
⭐    ⭐ If it times out, ⭐⭐ ANSWER ANYWAY AND SAY THE DATA MAY BE
⭐    STALE, ⭐ or fall back to the write model.
⭐    ⭐⭐ THAT IS DAY 329's ***READ-YOUR-WRITES SESSION
⭐    GUARANTEE***, IMPLEMENTED IN ABOUT THIRTY LINES.

⭐⭐ AND THE NON-NEGOTIABLE: ***PUBLISH `projection_lag_seconds`
⭐   AS A METRIC AND ALARM ON IT*** (DAY 394). ⭐ Lag in seconds,
⭐   not in events — ⭐⭐ BECAUSE "12,000 EVENTS BEHIND" IS
⭐   MEANINGLESS AND "FOUR MINUTES BEHIND" IS A DECISION.
⭐   ⭐ Compute it as `now − timestamp_of_last_processed_event`.
```

# Part 4 — Projections: three properties, non-negotiable

```
⭐ ① ⭐⭐ ***IDEMPOTENT.*** ⭐ Delivery is at-least-once (Days 402,
⭐    407), so every projection ***will*** see duplicates.
⭐    ⭐ `INSERT ... ON CONFLICT DO UPDATE` and absolute
⭐    assignments rather than increments — ⭐⭐ OR TRACK THE LAST
⭐    APPLIED VERSION PER ROW AND SKIP ANYTHING NOT NEWER, WHICH
⭐    IS THE ONLY WAY TO MAKE A COUNTER SAFE.
⭐ ② ⭐⭐ ***REBUILDABLE, AND YOU MUST HAVE REBUILT IT.***
⭐    ⭐ A rebuild procedure that has never been run is a
⭐    procedure that does not work (Day 379).
⭐ ③ ⭐ ***OWNS ITS OWN POSITION.*** ⭐ Each projection tracks
⭐    where it is, ⭐⭐ IN THE SAME TRANSACTION AS ITS WRITES
⭐    (DAY 402's PATTERN). ⭐ Then a crash cannot leave the data
⭐    and the position disagreeing, ⭐⭐ AND ONE SLOW PROJECTION
⭐    DOES NOT HOLD BACK ANY OTHER.

⭐⭐ ***THE REBUILD PROCEDURE*** — ⭐ Day 337's derived-index rule,
⭐   verbatim:
⭐   ① ⭐ Build `orders_read_v2` ***alongside*** v1.
⭐   ② ⭐ Replay from the beginning until it catches up.
⭐   ③ ⭐⭐ RUN BOTH IN PARALLEL AND ***MEASURE THE DIVERGENCE***
⭐      — ⭐ compare row counts and a sample of rows.
⭐      ⭐⭐ DO NOT ASSERT THAT IT MATCHES. MEASURE IT.
⭐   ④ ⭐ Swap the alias/view. ⭐ Keep v1 for a week.
⭐   ⑤ ⭐ Drop v1.
⭐   ⭐⭐ THE REBUILD IS THE SAFETY PROPERTY YOU BOUGHT. ⭐ Rehearse
⭐     it quarterly.
```

# Part 5 — When a projection hits a bad event

```
⭐ AN EVENT ARRIVES THAT THE PROJECTION CANNOT HANDLE — ⭐ a
⭐   missing field, a nonsense value, a division by zero.
⭐   ⭐⭐ THREE OPTIONS, AND THE COMMON CHOICE IS THE WRONG ONE:

⭐   ⭐ ① ***SKIP AND CARRY ON.*** ⭐⭐ TEMPTING, AND ALMOST ALWAYS
⭐      WRONG: THE PROJECTION IS NOW SILENTLY INCORRECT AND WILL
⭐      STAY THAT WAY UNTIL SOMEONE NOTICES A NUMBER LOOKS ODD IN
⭐      SIX WEEKS. ⭐ You have traded a loud failure for a quiet
⭐      lie.
⭐   ⭐ ② ***DEAD-LETTER IT AND CONTINUE.*** ⭐ Acceptable ***only
⭐      if*** the projection tolerates gaps ⭐ (a search index:
⭐      yes; ⭐⭐ A BALANCE: ABSOLUTELY NOT), ⭐ and only with an
⭐      alarm on the dead-letter count.
⭐   ⭐ ③ ⭐⭐ ***HALT.*** ⭐ Stop the projection, page. ⭐⭐ CORRECT
⭐      FOR ANY PROJECTION THAT MUST BE RIGHT — ⭐ and the alarm
⭐      is free, because it is the projection-lag alarm you
⭐      already have, ⭐⭐ RISING VERTICALLY.

⭐⭐ ⇒ AND THE RULE: ***A PROJECTION MAY BE LATE. IT MAY NOT BE
⭐   WRONG.*** ⭐ Lateness is visible and self-correcting;
⭐   ⭐⭐ WRONGNESS IS INVISIBLE AND PERMANENT.
```

# Part 6 — The Python projector

```python
# ⭐⭐ ONE PROCESS PER PROJECTION. Independent position,
# ⭐   independent failure, independent redeploy.
def run(projection: str, handlers: dict):
    while running:
        with engine.begin() as conn:                 # ⭐⭐ ONE TXN
            pos = conn.execute(text(
                "SELECT position FROM projection_state "
                "WHERE name=:n FOR UPDATE"),         # ⭐⭐ SINGLE
                {"n": projection}).scalar()          # ⭐ RUNNER

            rows = conn.execute(text(
                "SELECT id, event_type, payload, occurred_at "
                "FROM events WHERE id > :p ORDER BY id LIMIT 500"),
                {"p": pos}).all()
            if not rows:
                time.sleep(0.2); continue

            for r in rows:
                h = handlers.get(r.event_type)
                if h: h(conn, r.payload)             # ⭐⭐ SAME conn

            conn.execute(text(
                "UPDATE projection_state SET position=:p, "
                "last_event_at=:t WHERE name=:n"),
                {"p": rows[-1].id, "t": rows[-1].occurred_at,
                 "n": projection})
        # ⭐⭐ WRITES AND POSITION COMMIT TOGETHER. A CRASH REPLAYS
        # ⭐   THE BATCH — WHICH IS WHY HANDLERS ARE IDEMPOTENT.
        LAG.set((datetime.now(UTC) - rows[-1].occurred_at)
                .total_seconds())                    # ⭐⭐ SECONDS
```

```
⭐⭐ THREE NOTES THAT MATTER:
⭐   ⭐ `FOR UPDATE` on the state row means ⭐⭐ EXACTLY ONE RUNNER
⭐     PER PROJECTION EVEN WITH SIX REPLICAS — ⭐ a leader
⭐     election you get for free from the database (Day 411).
⭐   ⭐⭐ THE `ORDER BY id` POLL HAS THE ***GAP BUG***: A
⭐     TRANSACTION THAT TOOK ITS SEQUENCE VALUE EARLIER CAN
⭐     COMMIT LATER, SO A ROW WITH A ***LOWER*** id CAN APPEAR
⭐     ***AFTER*** YOU HAVE MOVED PAST IT. ⭐ Day 407 explains it
⭐     properly and gives the fixes; ⭐⭐ KNOW THAT IT EXISTS
⭐     BEFORE YOU SHIP THIS.
⭐   ⭐ For parallelism, partition by `aggregate_id` and run one
⭐     runner per partition — ⭐⭐ ORDER IS ONLY REQUIRED
⭐     ***WITHIN*** AN AGGREGATE (DAY 401's LESSON, AGAIN).
```

# Part 7 — When CQRS is wrong

```
⭐ ① ⭐⭐ ***WHEN YOUR READS AND WRITES HAVE THE SAME SHAPE***,
⭐    ⭐ which is most CRUD. ⭐ A form that edits one row and a
⭐    page that shows one row do not need two models.
⭐ ② ⭐ When the lag is unacceptable to the product and you have
⭐    not budgeted for the mitigations in Part 3.
⭐ ③ ⭐ When nobody will own the rebuild procedure.
⭐ ④ ⭐⭐ WHEN IT IS BEING ADOPTED BECAUSE IT APPEARS IN THE SAME
⭐    ARTICLES AS EVENT SOURCING. ⭐ They are ***independent***
⭐    choices: ⭐⭐ YOU CAN EVENT-SOURCE WITHOUT CQRS (FOLD ON
⭐    READ), AND YOU CAN DO CQRS OVER PLAIN TABLES WITH NO
⭐    EVENTS AT ALL. ⭐ Saying that clearly is a strong signal.

⭐ THE COST TALLY, SO YOU CAN PRICE IT: ⭐ two models, ⭐ a
⭐   projector to deploy and monitor, ⭐ a lag to explain, ⭐ a
⭐   rebuild procedure to rehearse, ⭐⭐ AND A NEW CLASS OF BUG
⭐   (DIVERGENCE) THAT NO TEST SUITE CATCHES BECAUSE IT ONLY
⭐   APPEARS AFTER MONTHS OF PRODUCTION EVENTS.
```

# 💬 Interview

**1. ⭐⭐ "What is CQRS and when do you need it?"**
> ⭐ It's the decision to stop pretending one model serves both writing and reading — ⭐⭐ **because the
> write model is normalised to protect invariants and the read model is denormalised to answer a
> question in one seek, and those are in direct opposition: the join that makes the read fast is the
> duplication that makes the write slow.** ⭐ But it's a ladder, not a thing. ⭐⭐ **Level one is
> separate models in one service and one database — command handlers use domain objects, queries are
> hand-written SQL returning flat DTOs — and it costs almost nothing while removing the biggest source
> of slow Python endpoints: hydrating fifty ORM objects with their relationships to render five
> columns.** ⭐ Level three is a separate read store with a lag and a rebuild procedure. ⭐⭐ **Most teams
> need level one and reach for level three. The test before climbing is: name the query that's slow
> and can't be fixed with an index.**

**2. ⭐⭐ "A user saves and doesn't see their change. What do you do?"**
> ⭐ Three fixes, best first. ⭐⭐ **Return the new state from the command — the handler already knows
> what it wrote, so the UI doesn't need to re-read at all.** ⭐ That removes the problem rather than
> hiding it, and people skip it because "commands should return void" is a rule somebody read. ⭐ Second,
> route that one read to the write model — the detail page immediately after save, not every endpoint.
> ⭐ Third, the general answer: ⭐⭐ **a version token. The command returns the position it wrote at, the
> client sends it on the next read, and the read endpoint waits — bounded, say 500 ms — until the
> projection reaches that position, then answers; on timeout it answers anyway and flags staleness.**
> ⭐ That's read-your-writes as a session guarantee, in about thirty lines.

**3. "How do you monitor a projection?"**
> ⭐⭐ **`projection_lag_seconds`, computed as now minus the timestamp of the last processed event —
> seconds, not events, because "12,000 events behind" is meaningless and "four minutes behind" is a
> decision.** ⭐ And that same metric is my alarm for the poison-event case, ⭐⭐ **because a halted
> projection shows up as lag rising vertically, which means I get the alert for free.**

**4. ⭐⭐ "A projection hits an event it can't handle. What happens?"**
> ⭐ Three options and the tempting one is wrong. ⭐⭐ **Skipping means the projection is now silently
> incorrect and stays that way until someone notices a number looks odd in six weeks — you've traded a
> loud failure for a quiet lie.** ⭐ Dead-lettering is acceptable only if the projection tolerates gaps
> — a search index yes, a balance absolutely not — and only with an alarm. ⭐⭐ **Halting is correct for
> anything that must be right.** ⭐ The rule I'd state is: ⭐⭐ **a projection may be late; it may not be
> wrong. Lateness is visible and self-correcting; wrongness is invisible and permanent.**

**5. "How do you rebuild a read model?"**
> ⭐ Build v2 alongside v1, replay from the beginning until it catches up, ⭐⭐ **run both in parallel
> and measure the divergence — compare counts and a sample of rows, don't assert that it matches** —
> then swap the alias and keep v1 for a week. ⭐ And I'd rehearse it quarterly, ⭐⭐ **because a rebuild
> procedure that's never been run is a procedure that doesn't work, and the rebuild is the entire
> safety property you bought.**

**6. ⭐⭐ "Do you need event sourcing to do CQRS?"**
> ⭐ No, and they get conflated because they appear in the same articles. ⭐⭐ **They're independent
> choices: you can event-source without CQRS by folding on read, and you can do CQRS over plain tables
> with no events at all — a denormalised read table maintained by triggers is CQRS.** ⭐ I'd also make
> sure the read model stays disposable: ⭐⭐ **the moment it holds a fact that exists nowhere else — a
> counter someone incremented directly, a flag an admin tool set — it stops being a projection and
> becomes a second source of truth, and you've lost the property you built it for.**

## 🎙️ Articulation drill

**Two minutes.** Define it as a decision, not a pattern: **CQRS is deciding to stop pretending one
model serves both reading and writing — the write model is normalised to protect invariants, the read
model is denormalised to answer a question in one seek, and the join that makes the read fast is the
duplication that makes the write slow.** Then immediately give the ladder, because that's where
judgement shows: **level one is separate models in one service and one database, which costs almost
nothing and removes the biggest source of slow Python endpoints; level three is a separate read store
with a lag, a rebuild procedure and a new class of bug. Most teams need one and reach for three — and
the test is to name the query that's slow and can't be fixed with an index.** Then the price:
**projection lag, and the failure is always the same — the user saves, the list reads a projection
that's 300 ms behind, their change isn't there, so they click Save again and now you have two.** Give
the fixes best-first: **return the new state from the command, which removes the problem rather than
hiding it; route that one read to the write model; or the general answer, a version token where the
command returns a position and the read waits, bounded, until the projection reaches it.** Then the
discipline: **publish lag in seconds and alarm on it; keep handlers idempotent because delivery is
at-least-once; update the position in the same transaction as the writes; and rebuild by running the
new projection alongside and measuring divergence rather than asserting it.** Close with the rule and
the correction: **a projection may be late, it may not be wrong — lateness is visible and
self-correcting, wrongness is invisible and permanent. And CQRS and event sourcing are independent
choices; a denormalised read table maintained by triggers is CQRS with no events at all.**
