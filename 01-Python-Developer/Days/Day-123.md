# Day 123

**L-123** · **Rate limiting** — five algorithms, ⭐⭐ and why the fixed window lets through twice the limit

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a rate limiter's job is not to be fair, it is to keep your service alive
> when someone — malicious or merely buggy — sends more traffic than you can serve, which means the
> important question is always "what happens at the boundary" rather than "what is the average".**
>
> ⭐ Day 096 built a fixed-window limiter test-first. **Today is why that algorithm is the weakest one,
> and what to use instead.**

# Part 1 — ⭐ Fixed window, and its boundary flaw

```python
def allow(key: str, limit: int, window: int) -> bool:
    bucket = f"rl:{key}:{int(time.time()) // window}"      # ⭐ the window number
    count = redis.incr(bucket)
    if count == 1:
        redis.expire(bucket, window)                        # ⭐ TTL on first hit
    return count <= limit
```

```
⭐⭐ SIMPLE, ONE ROUND TRIP, ALMOST NO MEMORY — AND IT LETS THROUGH TWICE THE
⭐   LIMIT AT EVERY BOUNDARY:
⭐
⭐   limit = 100 per minute
⭐   10:00:59  ⇒ 100 requests, all allowed   ⭐ (window "10:00")
⭐   10:01:00  ⇒ 100 requests, all allowed   ⭐⭐ (window "10:01" — a fresh counter)
⭐   ⇒ ⭐⭐ 200 REQUESTS IN TWO SECONDS, AND THE LIMITER SAYS BOTH MINUTES WERE
⭐        WITHIN LIMIT. ⭐ Every window boundary is a free burst of 2× the limit.
⭐
⭐ ⇒ ⭐⭐ AND IT IS NOT THEORETICAL: a client that retries on a 429 by waiting
⭐     "until the next minute" lands EXACTLY on the boundary — ⭐ so your worst
⭐     spike arrives from well-behaved clients synchronising, which is also why
⭐     `Retry-After` should carry JITTER (Part 5).
```

⭐ **Also note the TTL race:** if the process dies between `incr` and `expire`, the key lives forever
and that user is limited permanently. ⭐⭐ **Use `SET key 1 EX window NX` then `INCR`, or a Lua
script** — the same atomicity requirement as Day 122.

# Part 2 — ⭐ Sliding log and sliding window counter

```python
# ⭐ SLIDING LOG — exact, and expensive
def allow(key, limit, window):
    now = time.time()
    p = redis.pipeline()
    p.zremrangebyscore(key, 0, now - window)     # ⭐ drop entries older than the window
    p.zadd(key, {str(uuid4()): now})             # ⭐ record this request
    p.zcard(key)                                  # ⭐ how many in the window
    p.expire(key, window)
    return p.execute()[2] <= limit
```

```
⭐⭐ EXACTLY CORRECT — a true rolling window with no boundary effect. ⭐⭐ AND IT
⭐   STORES ONE ENTRY PER REQUEST: at 10,000 requests/minute across 50,000 users
⭐   that is a great deal of Redis memory for a counter.
⭐   ⇒ ⭐ use it where precision genuinely matters and volume is low — ⭐⭐ login
⭐        attempts (Day 114), password resets, expensive report generation.
⭐   ⇒ ⚠️ ⭐ not for general API traffic.
```

```
⭐⭐ SLIDING WINDOW COUNTER — THE PRACTICAL COMPROMISE, AND WHAT MOST PRODUCTION
⭐   LIMITERS ACTUALLY USE:
⭐   keep TWO fixed-window counters and interpolate:
⭐
⭐        estimate = current_count + previous_count × (fraction of the previous
⭐                                                     window still inside the
⭐                                                     rolling window)
⭐
⭐   ⭐ at 10:01:15 with a 60s window, 25% of the rolling window is still in the
⭐     10:00 window ⇒ estimate = current + 0.25 × previous
⭐   ⇒ ⭐⭐ TWO COUNTERS PER KEY, O(1) MEMORY, AND THE BOUNDARY BURST IS GONE.
⭐   ⇒ ⚠️ ⭐ it ASSUMES the previous window's traffic was evenly spread, so it can
⭐        be slightly off in both directions — ⭐⭐ which is an excellent trade
⭐        for a limit that is a policy choice anyway. ⭐ "100 per minute" was
⭐        never a precise physical constant.
```

# Part 3 — ⭐⭐ Token bucket — the one that allows bursts on purpose

```python
# ⭐⭐ TOKEN BUCKET: tokens refill at a steady rate; a request costs one token.
def allow(key, rate_per_sec, capacity):
    now = time.time()
    tokens, last = redis.hmget(key, "tokens", "last")        # ⭐ lazily refilled
    tokens = min(capacity, float(tokens or capacity) + (now - float(last or now)) * rate_per_sec)
    if tokens < 1:
        return False
    redis.hset(key, mapping={"tokens": tokens - 1, "last": now})   # ⭐⭐ must be ATOMIC — use Lua
    return True
```

```
⭐⭐ THE TWO PARAMETERS ARE THE POINT, AND THEY ARE INDEPENDENT:
⭐   RATE     ⇒ the SUSTAINED throughput you will allow  (tokens per second)
⭐   CAPACITY ⇒ ⭐⭐ THE BURST you will tolerate           (the bucket size)
⭐   ⇒ ⭐ rate 10/s with capacity 100 means: an idle client may fire 100 at once,
⭐        then settles to 10/s. ⭐⭐ THAT IS USUALLY WHAT YOU ACTUALLY WANT —
⭐        real clients are bursty (a page loads twelve resources at once) and a
⭐        strict 10/s would reject perfectly reasonable behaviour.
⭐   ⇒ ⭐⭐ THIS IS WHY TOKEN BUCKET IS THE DEFAULT IN API GATEWAYS: it separates
⭐        "how fast, on average" from "how much at once", and those are genuinely
⭐        two different policy decisions.
⭐   ⇒ ⭐ LEAKY BUCKET is the mirror image: requests queue and drain at a fixed
⭐        rate, SMOOTHING output rather than allowing bursts. ⭐⭐ Use it when the
⭐        thing downstream cannot take a spike — a third-party API with its own
⭐        limit, or a database you are protecting.
```

| Algorithm | ⭐ Memory | ⭐ Boundary burst | ⭐ Use |
|---|---|---|---|
| Fixed window | ⭐ O(1) | ⚠️ ⭐⭐ **2×** | ⭐ crude, cheap, rarely right |
| ⭐ Sliding log | ⚠️ O(n) | ⭐ none | ⭐⭐ login, resets — precision at low volume |
| ⭐⭐ **Sliding counter** | ⭐ O(1) | ⭐ negligible | ⭐⭐ **general API traffic** |
| ⭐⭐ **Token bucket** | ⭐ O(1) | ⭐ **deliberate** | ⭐⭐ **the default; burst-tolerant** |
| Leaky bucket | ⭐ O(1) | ⭐ none (smoothed) | ⭐ protecting a fragile downstream |

# Part 4 — ⭐⭐ What to limit, and by what

```
⭐⭐ "RATE LIMIT THE API" IS NOT A DESIGN. THE DIMENSION MATTERS MORE THAN THE
⭐   ALGORITHM:
⭐   · ⭐ PER USER / API KEY      ⇒ ⭐⭐ the fairest, and the only one that works
⭐        for authenticated traffic — ⭐ but useless before login.
⭐   · ⭐⭐ PER IP                ⇒ the only option for anonymous endpoints
⭐        ⚠️ ⭐ and it punishes shared NATs: a whole office, a university, or a
⭐        mobile carrier can look like one client. ⭐⭐ Set it generously, or
⭐        you will block real users while a distributed attacker spreads across
⭐        thousands of addresses and never trips it.
⭐   · ⭐ PER ENDPOINT           ⇒ ⭐⭐ `/login` and `/reports/export` deserve far
⭐        tighter limits than `/health`. A single global limit is always wrong
⭐        for something.
⭐   · ⭐⭐ PER COST             ⇒ charge a heavy endpoint more tokens. ⭐ A search
⭐        that scans a million rows should not cost the same as reading a cached
⭐        row — ⭐⭐ this is the model GraphQL APIs are forced into, and it is the
⭐        most honest one.
⭐   ⇒ ⭐⭐ IN PRACTICE YOU RUN SEVERAL AT ONCE: a generous per-IP limit, a
⭐        per-user limit, and tight per-endpoint limits on the expensive and
⭐        dangerous routes. ⭐ The first request to trip any of them is refused.
```

```
⚠️⚠️ ⭐⭐ AND THE ONE THAT BREAKS EVERYTHING BEHIND A PROXY (Day 111):
⭐    `request.client_ip` IS YOUR LOAD BALANCER'S IP. ⭐⭐ SO ONE LIMIT APPLIES
⭐    TO YOUR ENTIRE USER BASE, and the first busy minute rate-limits everybody.
⭐    ⇒ ⭐ you must read `X-Forwarded-For` — ⭐⭐ AND IT IS CLIENT-CONTROLLED, so
⭐         an attacker sets a random value per request and bypasses the limiter
⭐         entirely.
⭐    ⇒ ⭐⭐ THE CORRECT FORM: trust only the entries appended by YOUR OWN proxies.
⭐         Configure the trusted-proxy list and take the RIGHTMOST UNTRUSTED
⭐         address, ⭐ not the leftmost — the leftmost is whatever the client
⭐         wrote.
⭐    ⇒ ⭐ getting this wrong in either direction is a real, common bug: too
⭐         trusting and the limiter does nothing; not trusting at all and you
⭐         limit the whole world as one client.
```

# Part 5 — ⭐ The response, and where the limiter lives

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30                            ⭐⭐ MANDATORY — seconds, or a date
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30                        ⭐ seconds until the window resets
```

```
⭐⭐ SEND THE HEADERS ON **EVERY** RESPONSE, NOT ONLY ON A 429 — ⭐ then a
⭐   well-behaved client can slow down BEFORE it is refused, which is better for
⭐   both of you than a wall of rejections.
⭐   ⇒ ⭐⭐ AND `Retry-After` NEEDS JITTER. Tell a thousand clients to retry in
⭐        exactly 30 seconds and they all return at the same instant — ⭐⭐ you
⭐        have built a synchronised thundering herd out of your own rate limiter.
⭐        ⭐ Add a random spread, and require exponential backoff in your client
⭐        documentation.
⭐   ⇒ ⭐ 429 is the correct status; ⭐⭐ 503 with `Retry-After` is for "the whole
⭐        service is shedding load" (Day 106), which is a different message.
```

```
⭐⭐ WHERE TO PUT IT — AND THE ANSWER IS USUALLY "NOT IN PYTHON":
⭐   · ⭐⭐ AT THE EDGE (nginx, an API gateway, Cloudflare) ⇒ ⭐ the request never
⭐        reaches your worker, so a flood costs you nothing. ⭐⭐ THIS IS THE ONE
⭐        THAT PROTECTS YOU, because a limiter inside your app still requires a
⭐        worker, a Redis round trip and a response for every rejected request.
⭐   · ⭐ IN THE APPLICATION ⇒ ⭐ needed for per-user and per-cost limits, because
⭐        the edge does not know who you are or what a request costs.
⭐   ⇒ ⭐⭐ SO: A CRUDE, GENEROUS LIMIT AT THE EDGE FOR SURVIVAL, AND PRECISE
⭐        PER-USER LIMITS IN THE APP FOR FAIRNESS. ⭐ They are different jobs.
⭐   ⇒ ⚠️ ⭐⭐ AND THE LIMITER MUST NOT BECOME THE OUTAGE: if Redis is down, do
⭐        you FAIL OPEN (allow everything) or FAIL CLOSED (reject everything)?
⭐        ⭐⭐ For a rate limiter, FAIL OPEN — it is a protective measure, and
⭐        taking the whole service down to enforce a quota is a worse outcome
⭐        than briefly serving too much. ⭐ Decide it explicitly, log loudly, and
⭐        write it in the ADR (Day 101) — the opposite choice is right for an
⭐        authorisation check.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Fixed window in production** | ⭐⭐ 2× the limit at every boundary — and clients synchronise onto it. |
| `INCR` then `EXPIRE` non-atomically | ⭐ A crash between them limits that user forever. |
| ⭐ Sliding log for general traffic | ⭐ One entry per request. Use it for login only. |
| Non-atomic token-bucket update | ⭐⭐ Two workers both spend the same token. Use Lua. |
| ⭐⭐ **Limiting on the proxy's IP** | ⭐⭐ One limit for your entire user base. |
| Trusting `X-Forwarded-For` blindly | ⭐⭐ A random header per request bypasses the limiter. |
| ⭐ One global limit | ⭐ `/login` and `/health` do not deserve the same number. |
| Charging every endpoint one token | ⭐⭐ A million-row search costs the same as a cached read. |
| ⭐ 429 without `Retry-After` | ⭐ The client guesses. |
| ⭐⭐ **`Retry-After` with no jitter** | ⭐⭐ A synchronised thundering herd, built by you. |
| Headers only on 429 | ⭐ Clients cannot slow down before being refused. |
| ⭐ Only limiting in the app | ⭐⭐ A flood still costs a worker and a round trip each. |
| Failing closed when Redis is down | ⭐⭐ The limiter becomes the outage. |

## Interview questions

**Q: What's wrong with a fixed-window rate limiter?**
> The boundary. With a hundred per minute, a client can send a hundred at 10:00:59 and another hundred
> at 10:01:00 — two hundred requests in two seconds, and both minutes were within limit. So every
> window boundary is a free burst of twice the limit. It's worse than it sounds, because a client that
> handles a 429 by waiting for the next minute lands exactly on the boundary, so your biggest spike
> arrives from well-behaved clients synchronising. That's also why `Retry-After` needs jitter.

**Q: Which algorithm would you use?**
> Token bucket as the default, because its two parameters map onto two genuinely different policy
> decisions: the refill rate is sustained throughput, and the bucket size is the burst you'll tolerate.
> Real clients are bursty — a page loads twelve resources at once — so a strict per-second limit
> rejects reasonable behaviour. Sliding window counter is the good compromise when you want a simple
> "N per minute" without the boundary problem: two counters and an interpolation, O(1) memory. Sliding
> log where precision genuinely matters and volume is low, like login attempts. And leaky bucket when
> I'm protecting something downstream that can't take a spike.

**Q: What do you rate limit *by*?**
> Several dimensions at once, and the dimension matters more than the algorithm. Per user or API key
> is fairest but useless before login. Per IP is the only option for anonymous endpoints, and it needs
> to be generous because a whole office behind a NAT looks like one client — while a distributed
> attacker spreads across thousands of addresses and never trips it. Per endpoint, because `/login`
> and `/health` don't deserve the same number. And ideally per cost, charging expensive endpoints
> more tokens, because a search scanning a million rows shouldn't cost the same as a cached read.

**Q: What breaks rate limiting behind a load balancer?**
> The client IP is the load balancer's, so one limit applies to your entire user base and the first
> busy minute rate-limits everybody. You have to read `X-Forwarded-For` — but that's client-controlled,
> so an attacker sets a random value per request and bypasses the limiter completely. The correct form
> is to trust only the entries your own proxies appended: configure the trusted-proxy list and take
> the rightmost untrusted address, not the leftmost. Getting it wrong in either direction is a real
> bug — too trusting and the limiter does nothing, not trusting at all and you limit the world as one
> client.

**Q: If Redis is down, do you allow or reject?**
> Allow — fail open. A rate limiter is a protective measure, and taking the whole service down to
> enforce a quota is a worse outcome than briefly serving too much traffic. But I'd decide it
> explicitly rather than by accident, log loudly, and alarm on it, because now the protection is off.
> The opposite choice is right for an authorisation check, where failing open is a security incident —
> so it's worth being able to say why the two differ rather than having one reflex.
