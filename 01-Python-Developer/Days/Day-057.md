# Day 057

**L-057** · ⭐ `dataclasses` — `frozen`, `slots`, `field`, and exactly where Pydantic takes over

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `@dataclass` writes the boilerplate you were going to write. It does not
> validate anything — the type hints are still just annotations (Day 042).**
>
> ⭐ That single distinction is the whole ownership boundary of your Stage 3/4 architecture:
> **dataclasses for data you already trust, Pydantic for data crossing your boundary.**

---

# Part 1 — ⭐⭐ What you get

```python
from dataclasses import dataclass, field

@dataclass
class Order:
    id: int
    total: Decimal
    tags: list[str] = field(default_factory=list)     # ⭐⭐ Day 025's fix, built in
    note: str = ""
```

```
⭐⭐ GENERATED FOR YOU: __init__, __repr__, __eq__  — from the ANNOTATED class attributes.
⭐   ⇒ ⭐ __repr__ alone is worth it (Day 031: the highest-value-per-character method)
⭐   ⇒ ⭐⭐ ORDER MATTERS: fields with defaults must come AFTER fields without.
⭐        ⇒ ⚠️ and this breaks on inheritance — see kw_only in Part 3.
⭐   ⇒ ⭐ an annotation with NO value is a required field; a plain assignment with no
⭐        annotation is NOT a field at all (it stays an ordinary class attribute).
```

| ⭐ Option | ⭐ Effect |
|---|---|
| `eq=True` (default) | `__eq__` comparing all fields as a tuple |
| ⭐⭐ `frozen=True` | ⭐⭐ immutable **and hashable** (Days 025, 029) |
| ⭐ `order=True` | `__lt__`, `__le__`, `__gt__`, `__ge__` — ⭐ tuple comparison, so field order *is* sort order |
| ⭐⭐ `slots=True` (3.10+) | ⭐⭐ no `__dict__` — ~50% less memory (Day 028) |
| ⭐⭐ `kw_only=True` (3.10+) | ⭐⭐ every field keyword-only (Day 040) |
| `repr=False` | skip `__repr__` |
| `init=False` | you write `__init__` yourself |

```python
# ⭐⭐ THE COMBINATION I would default to for a value object:
@dataclass(frozen=True, slots=True)
class Point:
    x: float
    y: float
# ⇒ ⭐ __init__, __repr__, __eq__, __hash__, immutable, small. Six lines of nothing.
```

⚠️ ⭐ **`slots=True` and `frozen=True` together mean no `cached_property`** (Day 051 — it needs
`__dict__`) and no adding attributes. **That is usually what you want for a value object and never what
you want for a service.**

# Part 2 — ⭐⭐ `field()`

```python
@dataclass
class Job:
    name: str
    tags: list[str] = field(default_factory=list)   # ⭐⭐ a NEW list per instance
    created: datetime = field(default_factory=now)  # ⭐⭐ evaluated PER INSTANCE, not at import
    _cache: dict = field(default_factory=dict, repr=False, compare=False)
    id: str = field(init=False, default="")         # ⭐ not an __init__ parameter
    meta: dict = field(default_factory=dict, metadata={"sensitive": True})
```

| ⭐ `field(...)` argument | ⭐ Meaning |
|---|---|
| ⭐⭐ `default_factory` | ⭐⭐ a callable, called per instance — **the mutable-default fix** |
| `default` | a plain value (⚠️ ⭐ a mutable one raises `ValueError` — the language stops you) |
| ⭐ `init=False` | excluded from `__init__` — set it in `__post_init__` |
| `repr=False` | keep it out of the `__repr__` — ⭐ use for secrets and large blobs |
| ⭐ `compare=False` | excluded from `__eq__`/ordering — ⭐ use for caches, timestamps |
| `kw_only=True` | this field only, keyword-only |
| `metadata` | ⭐ an arbitrary dict — libraries read it; the language ignores it |

⭐⭐ **`ValueError: mutable default <class 'list'> for field tags is not allowed` is one of the nicest
error messages in Python** — the language recognised Day 025's bug and refuses to let you write it.
**`default_factory` exists for exactly that.**

```python
# ⭐ __post_init__ and InitVar — derived fields and construction-only arguments:
from dataclasses import InitVar

@dataclass
class Rect:
    width: float
    height: float
    scale: InitVar[float] = 1.0          # ⭐⭐ passed to __init__, NOT stored as a field
    area: float = field(init=False)

    def __post_init__(self, scale):      # ⭐ receives the InitVars
        self.width *= scale; self.height *= scale
        self.area = self.width * self.height
```

⚠️ ⭐ **In a `frozen=True` dataclass, `__post_init__` cannot assign** — use
`object.__setattr__(self, "area", ...)`, which is ugly enough to be a signal that the field probably
wants to be a `cached_property` or a plain method instead.

```python
from dataclasses import asdict, astuple, replace, fields
replace(order, total=Decimal("5"))       # ⭐⭐ the functional update (Day 025)
fields(Order)                            # ⭐ introspect — name, type, default, metadata
asdict(order)                            # ⚠️ ⭐⭐ RECURSIVE and DEEP-COPIES everything
```

⚠️ ⭐⭐ **`asdict` deep-copies**, so on a large nested structure it is expensive and it will happily
choke on anything unpicklable. **For serialisation, write it explicitly or use Pydantic's
`model_dump`.**

# Part 3 — ⭐ Inheritance, and the default-ordering problem

```python
@dataclass
class Base:
    name: str = "unnamed"          # ⭐ has a default

@dataclass
class Child(Base):
    id: int                        # ⚠️⚠️ ⭐⭐ TypeError: non-default argument 'id'
                                   #     follows default argument
```

```
⭐⭐ WHY: fields are collected base-first, so __init__ becomes (name="unnamed", id) —
⭐   which is not a legal signature.
⭐ ⭐⭐ THE FIX, and it is the reason kw_only exists:
```

```python
@dataclass(kw_only=True)          # ⭐⭐ order stops mattering entirely
class Base:
    name: str = "unnamed"

@dataclass(kw_only=True)
class Child(Base):
    id: int                       # ⭐ fine — Child(id=1) or Child(id=1, name="x")
```

⭐⭐ **`kw_only=True` on every dataclass is a defensible house style**, and Day 040's argument applies:
call sites become self-documenting, and you can add or reorder fields without breaking callers.
**Pydantic v2 is keyword-only by default for the same reason.**

# Part 4 — ⭐⭐ The boundary: dataclass vs Pydantic

```python
@dataclass
class User:
    id: int
    email: str

User(id="not-an-int", email=None)      # ⭐⭐ WORKS. No error. Annotations are not checks.
```

```python
from pydantic import BaseModel, EmailStr, Field

class User(BaseModel):
    id: int
    email: EmailStr
    age: int = Field(ge=0, le=150)

User(id="42", email="a@b.com", age=30)     # ⭐⭐ id COERCED to int 42
User(id="x", email="nope", age=-1)         # ⭐⭐ ValidationError listing ALL THREE problems
```

| | ⭐ `dataclass` | ⭐⭐ Pydantic |
|---|---|---|
| Validation | ⭐⭐ **none** | ⭐⭐ **yes, from the annotations** |
| Coercion | none | ⭐ `"42"` → `42` (configurable) |
| Speed | ⭐⭐ **faster** (stdlib, no validation) | ⭐ v2's core is Rust — fast, but not free |
| ⭐ JSON schema | no | ⭐⭐ yes — this is FastAPI's OpenAPI docs |
| Dependency | ⭐⭐ **stdlib** | third-party |
| Nested parsing | you do it | ⭐⭐ recursive, automatic |

```
⭐⭐ THE RULE, AND IT IS AN ARCHITECTURAL BOUNDARY, NOT A PREFERENCE:
⭐   ⭐⭐ PYDANTIC AT THE EDGE — HTTP request bodies, config files, message-queue payloads,
⭐        third-party API responses. ⇒ anything you did not create.
⭐   ⭐⭐ DATACLASSES INSIDE — your domain objects, already-validated values, internal
⭐        results, anything constructed by your own code.
⭐   ⇒ ⭐ validate ONCE, at the boundary (Day 023's EAFP note), and trust it afterwards.
⭐        Re-validating internally is cost with no benefit and it hides where the trust
⭐        boundary actually is.
```

⭐ **`pydantic.dataclasses.dataclass`** is the bridge — dataclass syntax with validation — and ⭐
**`attrs`** predates dataclasses, has validators and converters, and is still better for some cases.
**Know they exist; default to stdlib dataclasses plus Pydantic at the edge.**

⭐⭐ **When a plain class still wins:** the object has significant behaviour rather than data,
`__init__` does real work, or you need full control over construction. **`@dataclass` is for data with
a little behaviour, not behaviour with a little data.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Expecting a dataclass to validate** | ⭐⭐ Annotations are metadata. Nothing is checked. |
| Mutable `default=[]` | ⭐ `ValueError` — the language stops you. `default_factory`. |
| `datetime.now()` as a `default` | ⭐⭐ Frozen at import. `default_factory=now`. |
| Non-default field after a default in a subclass | ⭐⭐ `TypeError`. Use `kw_only=True`. |
| ⭐ `asdict` for serialisation | ⭐⭐ Deep-copies everything; slow and fragile. |
| Assigning in a frozen `__post_init__` | ⭐ Needs `object.__setattr__` — usually a design signal. |
| `slots=True` with `cached_property` | ⭐ Needs `__dict__` (Day 051). |
| `frozen=True` on a mutable domain object | ⭐ Then `replace()` everywhere — decide deliberately. |
| Pydantic for internal domain objects | ⭐⭐ Validate once at the edge; trust afterwards. |
| A dataclass for a behaviour-heavy class | ⭐ Data with some behaviour, not the reverse. |
| Plain assignment with no annotation | ⭐ Not a field — it stays a class attribute (Day 053). |

## Interview questions

**Q: What does `@dataclass` give you?**
> `__init__`, `__repr__` and `__eq__` generated from the annotated class attributes, plus optional
> ordering, immutability and slots. `__repr__` alone justifies it — every log line, debugger view and
> failing assertion is better for it. What it explicitly does *not* do is validate: the annotations are
> metadata, so `User(id="not an int")` constructs happily. That's the whole boundary with Pydantic.

**Q: Dataclass or Pydantic?**
> It's an architectural boundary rather than a preference. Pydantic at the edge — request bodies,
> config, queue payloads, third-party responses — anything I didn't create, because there I need
> parsing, coercion, structured errors and a JSON schema. Dataclasses inside, for domain objects and
> already-validated values, because they're stdlib, faster, and there's nothing left to validate. The
> principle is to validate once at the boundary and trust it afterwards; re-validating internally costs
> time and obscures where the trust boundary actually is.

**Q: What's `default_factory` for?**
> Per-instance mutable defaults. A plain `default=[]` would share one list across every instance, which
> is the mutable-default-argument bug one level up — and the language actually refuses it with a
> `ValueError` naming the field, which is one of the better error messages in Python.
> `default_factory=list` calls the factory per instance. It's also the right answer for
> `datetime.now`, which as a plain default would be frozen at import time.

**Q: Why does adding a required field to a dataclass subclass fail?**
> Because fields are collected base-first, so if the base has a default and the subclass adds a
> required field, the generated `__init__` has a non-default parameter after a default one, which isn't
> a legal signature. `kw_only=True` removes the problem entirely, since keyword-only parameters have no
> ordering constraint. I'd default to `kw_only=True` anyway — call sites become self-documenting and I
> can add or reorder fields without breaking callers, which is the same argument as keyword-only
> function arguments.

**Q: What does `frozen=True` buy?**
> Immutability, and therefore a generated `__hash__`, so the object can be a dict key or set member —
> which satisfies the hash contract trivially, because nothing can change while it's in the container.
> It also makes the object safe to share without defensive copies. The cost is that updates become
> `replace()` calls returning new objects, so it's a deliberate choice: right for value objects, wrong
> for something you mutate through its lifetime.

**Q: When is a plain class still the right answer?**
> When the type is behaviour with a little data rather than data with a little behaviour. If `__init__`
> does real work — opening connections, validating across fields, computing derived state — or if I
> need control over construction, the generated `__init__` is fighting me. `@dataclass` is for records;
> a service or an entity with a rich lifecycle is usually clearer as a normal class.

## 🎙️ Articulation drill

Record two minutes: **"When do you use a dataclass and when Pydantic?"**

⭐ Lead with the fact that decides it: **a dataclass does not validate anything. The annotations are
metadata, so `User(id="not an int")` constructs happily.** Pydantic reads the same annotations and
turns them into parsing, coercion, structured errors and a JSON schema.

⭐⭐ **Then state it as an architectural boundary rather than a preference:** *"Pydantic at the edge —
HTTP bodies, config, queue payloads, third-party responses; anything I did not create. Dataclasses
inside — domain objects and already-validated values. The principle is validate once at the boundary
and trust it afterwards; re-validating internally costs time and, worse, obscures where the trust
boundary actually is, so nobody can tell which data has been checked."*

⭐ Then the two defaults you would apply: **`kw_only=True` so field order never constrains callers, and
`frozen=True, slots=True` for value objects** — immutable, hashable, small, and safe to share.

⭐⭐ **Close on the limit:** *"and I'd stop using dataclasses when the type is behaviour with a little
data rather than data with a little behaviour — if `__init__` needs to do real work, the generated one
is fighting me."*
