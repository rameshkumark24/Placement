**L-138** · **Alembic** — autogenerate, and ⭐⭐ the migrations that lock a table until the site is down

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a migration is not "changing the schema" — it is changing the schema
> *while the old code is still running*. Every hard rule in this day falls out of that one sentence.**
>
> ⭐ You will spend most of today on two things Alembic cannot do for you: **deciding whether a
> migration is safe to run against a live table**, and **splitting an unsafe change into safe steps**.

# Part 1 — ⭐ The mechanism, quickly

```bash
alembic init -t async migrations          # ⭐ `-t async` if you did Day 137
alembic revision --autogenerate -m "add orders.status"
alembic upgrade head
alembic downgrade -1
alembic current                            # ⭐ what this database is at
alembic history --verbose
```

```python
# migrations/versions/8f2a1c_add_orders_status.py
revision      = "8f2a1c"
down_revision = "3b91de"        # ⭐⭐ THIS is what makes migrations a linked list, not a set

def upgrade() -> None:
    op.add_column("orders", sa.Column("status", sa.String(20), nullable=True))

def downgrade() -> None:
    op.drop_column("orders", "status")
```

```
⭐⭐ THE THREE FACTS THAT EXPLAIN EVERY ALEMBIC CONFUSION:

⭐  1. ⭐⭐ ALEMBIC STORES ONE ROW IN ONE TABLE: `alembic_version.version_num`.
⭐       That row is the ONLY thing that says where a database is. It is not
⭐       derived from the schema — ⭐ so a hand-edited schema and Alembic's
⭐       opinion of the schema can disagree silently, forever.
⭐
⭐  2. ⭐⭐ MIGRATIONS FORM A CHAIN VIA `down_revision`, NOT A SORT ORDER.
⭐       ⭐ Filenames and timestamps are decoration. Two developers branching
⭐       from the same `down_revision` produce ⭐⭐ TWO HEADS, and `upgrade head`
⭐       then fails with "Multiple head revisions". ⭐ Fix: `alembic merge`.
⭐
⭐  3. ⭐⭐ AUTOGENERATE DIFFS YOUR MODELS AGAINST THE DATABASE. It writes a
⭐       GUESS. ⭐ It is a first draft with a good hit rate — ⭐⭐ it is never
⭐       the final answer, and the rest of this day is why.
```

# Part 2 — ⭐⭐ What autogenerate misses, and what it gets actively wrong

```
⭐⭐ IT DOES NOT DETECT (silently produces nothing):
⭐   · ⭐ table or column RENAMES — ⭐⭐ it emits DROP + ADD, which is
⭐        "delete the data, then make an empty column". ⭐⭐ THIS IS THE ONE
⭐        THAT DESTROYS PRODUCTION DATA. Day 084's lesson again: a rename is
⭐        never detected, only inferred.
⭐   · ⭐ CHECK constraints, most server defaults, and column-type *changes*
⭐        that the dialect cannot compare (⭐ enable `compare_type=True`)
⭐   · ⭐ anything not attached to your metadata: views, triggers, functions,
⭐        partial indexes, extensions, ⭐ tables owned by another service
⭐
⭐⭐ IT DETECTS AND SHOULD NOT (produces spurious drops):
⭐   · ⭐⭐ tables it does not know about — including `alembic_version` in
⭐        other schemas, PostGIS's `spatial_ref_sys`, ⭐ another team's tables
⭐        in the same database. Autogenerate says "not in my models" and
⭐        writes `op.drop_table(...)`.
⭐   ⇒ ⭐⭐ FIX: `include_object` in `env.py`, and ⭐ READ EVERY GENERATED FILE
⭐        BEFORE COMMITTING IT. Treat it exactly like a `git add -p` hunk
⭐        (Day 086): you are reviewing a proposal, not accepting a fact.
```

```python
# migrations/env.py
def include_object(obj, name, type_, reflected, compare_to):
    if type_ == "table" and name in {"spatial_ref_sys", "celery_taskmeta"}:
        return False                      # ⭐ not ours — never drop it
    if type_ == "table" and obj.schema not in (None, "public"):
        return False
    return True

context.configure(
    connection=connection,
    target_metadata=target_metadata,
    include_object=include_object,
    compare_type=True,                    # ⭐ catch String(20) → String(40)
    compare_server_default=True,          # ⭐ noisy, but catches real drift
)
```

> ⭐⭐ **The rename procedure, since autogenerate cannot help you:** delete the generated
> DROP/ADD pair and write `op.alter_column("orders", "state", new_column_name="status")` by hand —
> **and read Part 4 before you decide even that is safe.**

# Part 3 — ⭐⭐ The lock: why a "one-second" migration takes the site down

```
⭐⭐ THE THING NOBODY TELLS YOU: `ALTER TABLE` TAKES AN ACCESS EXCLUSIVE LOCK.
⭐   That lock blocks ⭐ EVERY read and EVERY write on that table.
⭐
⭐   ⭐⭐ AND HERE IS THE PART THAT TURNS A FAST MIGRATION INTO AN OUTAGE:
⭐
⭐   ⭐ a long-running SELECT holds an ACCESS SHARE lock
⭐        ↓
⭐   ⭐ your ALTER queues behind it, waiting for ACCESS EXCLUSIVE
⭐        ↓
⭐   ⭐⭐ EVERY SUBSEQUENT QUERY QUEUES BEHIND *YOUR* ALTER — because lock
⭐        requests are a FIFO queue, and a pending exclusive lock blocks the
⭐        shared locks arriving after it.
⭐        ↓
⭐   ⭐⭐ ⇒ ONE 30-SECOND ANALYTICS QUERY + ONE INSTANT `ALTER` = A TOTAL
⭐        OUTAGE ON THAT TABLE FOR 30 SECONDS. The migration was never slow.
⭐        ⭐ IT WAS THE QUEUE BEHIND IT.
```

```python
# ⭐⭐ THE DEFENCE — put it at the top of every migration that alters a table:
def upgrade() -> None:
    op.execute("SET lock_timeout = '3s'")       # ⭐⭐ fail fast rather than pile up
    op.execute("SET statement_timeout = '30s'")
    op.add_column(...)
```

> ⭐⭐ **`lock_timeout` converts an outage into a failed deploy.** A failed deploy is a Slack
> message. An outage is an incident. **You want the Slack message.** Retry it at 3 a.m. when no
> analytics query is running — or better, kill the long query first.

```
⭐⭐ SAFE VS UNSAFE ON POSTGRES (memorise this table — it is asked directly):

⭐  SAFE — metadata-only, instant:
⭐   · ADD COLUMN nullable, no default            ⭐ always safe
⭐   · ADD COLUMN with a CONSTANT default          ⭐ PG 11+ only; PG ≤10 rewrote
⭐                                                    the whole table
⭐   · DROP COLUMN                                 ⭐ instant, but see Part 4
⭐   · RENAME column/table                         ⭐ instant, and BREAKS OLD CODE
⭐   · ADD INDEX **CONCURRENTLY**                  ⭐⭐ no write lock
⭐   · ADD CHECK ... NOT VALID, then VALIDATE      ⭐⭐ two steps, both cheap
⭐
⭐  UNSAFE — full table rewrite or long exclusive lock:
⭐   · ⭐⭐ ADD COLUMN ... NOT NULL (no default)    ⭐ fails outright if rows exist
⭐   · ⭐⭐ ALTER COLUMN TYPE (most)                ⭐ rewrites every row
⭐   · ⭐⭐ ADD INDEX (without CONCURRENTLY)        ⭐ blocks writes for the build
⭐   · ⭐⭐ ADD FOREIGN KEY (validating)            ⭐ locks BOTH tables
⭐   · ⭐⭐ SET NOT NULL on an existing column      ⭐ full scan under exclusive lock
⭐        (⭐ PG 12+ can skip the scan if a matching CHECK is already VALID)
```

```python
# ⭐⭐ CONCURRENT INDEX — and the one gotcha that makes it fail
def upgrade() -> None:
    with op.get_context().autocommit_block():        # ⭐⭐ REQUIRED
        op.create_index(
            "ix_orders_user_created", "orders", ["user_id", "created_at"],
            postgresql_concurrently=True,
        )
```

> ⭐⭐ **`CREATE INDEX CONCURRENTLY` cannot run inside a transaction**, and Alembic wraps every
> migration in one. `autocommit_block()` is the escape hatch. ⭐ **The consequence you must know:
> a concurrent index build that fails leaves an `INVALID` index behind** — it is not rolled back,
> because it was not in a transaction. Your `downgrade` must drop it, and your next `upgrade` must
> tolerate finding it (`IF NOT EXISTS`).

# Part 4 — ⭐⭐ Expand / contract: the pattern that makes any change safe

```
⭐⭐ THE PREMISE AGAIN: during a rolling deploy, OLD CODE AND NEW CODE RUN
⭐   AGAINST THE SAME DATABASE AT THE SAME TIME. (Day 111's rolling deploy.)
⭐   ⭐ So the schema must be readable by BOTH for the length of the deploy.
⭐
⭐⭐ THEREFORE: NEVER SHIP A SCHEMA CHANGE AND THE CODE THAT NEEDS IT IN THE
⭐   SAME RELEASE. Split it into three releases.

⭐   RENAME `orders.state` → `orders.status`, DONE SAFELY:

⭐   RELEASE 1 — EXPAND ⭐⭐ (migration only, no behaviour change)
⭐     · ADD COLUMN `status` (nullable)
⭐     · backfill in batches (Part 5)
⭐     · code writes BOTH columns, reads `state`
⭐        ⇒ ⭐ old code still works: `state` is still authoritative
⭐
⭐   RELEASE 2 — MIGRATE READS
⭐     · code reads `status`, still writes both
⭐        ⇒ ⭐ rollback to Release 1 is still safe — `state` is still current
⭐
⭐   RELEASE 3 — CONTRACT
⭐     · code stops touching `state`
⭐     · migration: DROP COLUMN `state`
⭐        ⇒ ⭐⭐ only now is the old column unreferenced by ANY running process
⭐
⭐   ⇒ ⭐⭐ THREE DEPLOYS INSTEAD OF ONE. That is the cost, and it is the
⭐        correct cost. ⭐ The one-deploy version has a window — usually 30 to
⭐        180 seconds — in which half your fleet writes to a column that no
⭐        longer exists, and every one of those requests 500s.
```

```
⭐⭐ THE SAME SHAPE COVERS EVERY DANGEROUS CHANGE:

⭐  ADD A NOT NULL COLUMN:
⭐    1. ADD COLUMN nullable, WITH a default   ⭐ (new rows are fine immediately)
⭐    2. backfill existing rows in batches
⭐    3. ⭐ ADD CHECK (col IS NOT NULL) NOT VALID  → VALIDATE CONSTRAINT
⭐    4. SET NOT NULL  ⭐ (PG 12+ sees the valid CHECK and skips the scan)
⭐
⭐  CHANGE A COLUMN TYPE:
⭐    ⭐ add a new column of the new type, dual-write, backfill, swap reads,
⭐      drop the old one. ⭐⭐ i.e. expand/contract — there is no in-place shortcut.
⭐
⭐  DROP A COLUMN:
⭐    ⭐⭐ deploy the code that stops SELECTing it FIRST. ⭐ Remember the ORM
⭐      selects every mapped column by default — ⭐⭐ so old code with the column
⭐      still on the model will `SELECT status` and get "column does not exist"
⭐      on EVERY query against that table, not just ones that use the field.
```

> ⭐⭐ **That last line is the single most common self-inflicted outage in ORM shops.** Dropping a
> column breaks *every* query for that model, because `SELECT *`-by-mapping is the ORM's default.
> ⭐ Remove the attribute from the model, deploy, **then** drop the column.

# Part 5 — ⭐ Data migrations, ordering, and the down-migration lie

```python
# ⭐⭐ BACKFILL IN BATCHES — never one statement over 40 million rows
def upgrade() -> None:
    conn = op.get_bind()
    while True:
        result = conn.execute(sa.text("""
            UPDATE orders SET status = state
            WHERE id IN (
                SELECT id FROM orders WHERE status IS NULL LIMIT 5000
            )
        """))
        if result.rowcount == 0:
            break
        # ⭐⭐ each batch is its own transaction → short locks, resumable,
        #    ⭐ and the WAL/undo log does not grow without bound
```

```
⭐⭐ THREE RULES FOR DATA MIGRATIONS:

⭐  1. ⭐⭐ NEVER IMPORT YOUR ORM MODELS INTO A MIGRATION.
⭐       ⭐ A migration is pinned to a moment in history; your models are on
⭐       `main`. ⭐⭐ In six months the model has a column this migration's
⭐       schema does not — and a fresh `alembic upgrade head` on a new
⭐       environment crashes on a migration that "worked fine when written".
⭐       ⇒ ⭐ Use `sa.text(...)` or a local `sa.table()/sa.column()` stub.
⭐
⭐  2. ⭐ For a large backfill, prefer a SEPARATE SCRIPT over a migration.
⭐       ⭐⭐ A four-hour migration blocks your deploy pipeline for four hours,
⭐       and a deploy that cannot roll forward is an outage waiting for a bug.
⭐
⭐  3. ⭐ Make it RESUMABLE and IDEMPOTENT (`WHERE status IS NULL` above does
⭐       both). ⭐⭐ It will be interrupted. Plan for the interruption.
```

```
⭐⭐ THE DOWN-MIGRATION LIE:

⭐   `downgrade()` implies you can go back. ⭐⭐ FOR SCHEMA, PARTLY. FOR DATA,
⭐   NO — `drop_column` deleted it, and the downgrade recreates an EMPTY column.
⭐
⭐   ⇒ ⭐⭐ THE HONEST POSITION: in production you ROLL FORWARD. You write a
⭐        new migration that undoes the change. ⭐ Downgrades are for local
⭐        development, where losing the data is free.
⭐   ⇒ ⭐ Still write `downgrade()` — ⭐⭐ but write it so that reviewing it
⭐        forces you to notice when a change is irreversible. That is its real
⭐        value: it is a THINKING TOOL, not a rollback plan.
```

```
⭐⭐ DEPLOY ORDERING — the rule, and its one exception:

⭐   ⭐ MIGRATE FIRST, THEN DEPLOY CODE. Because expand/contract guarantees
⭐     the new schema is backwards-compatible, the old code keeps working
⭐     against it. ⭐⭐ The reverse order has a window where new code hits an
⭐     old schema and 500s.
⭐   ⭐ EXCEPTION: the CONTRACT step (a drop) runs AFTER the code deploy —
⭐     ⭐⭐ because a drop is the one change that is deliberately NOT
⭐     backwards-compatible.
⭐   ⇒ ⭐⭐ SO: EXPAND BEFORE, CONTRACT AFTER.
⭐
⭐ ⭐ AND: run migrations as a ONE-OFF JOB, never in your app's startup or
⭐   lifespan (Day 133). ⭐⭐ Ten replicas booting simultaneously = ten
⭐   concurrent `alembic upgrade head`. Alembic locks `alembic_version`, so
⭐   nine of them block, then find nothing to do — ⭐ but your readiness
⭐   probe times out during the wait, and Kubernetes kills the pods mid-deploy.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Committing an autogenerated migration unread | ⭐⭐ It writes DROP + ADD for a rename. Review every generated file like a code diff. |
| Adding an index without `CONCURRENTLY` | Blocks all writes for the duration of the build. Use `autocommit_block()` + `postgresql_concurrently=True`. |
| `ADD COLUMN ... NOT NULL` on a populated table | Fails, or rewrites the table. Nullable → backfill → validate → SET NOT NULL. |
| Shipping the migration and the code that needs it together | ⭐⭐ Rolling deploys run both versions at once. Expand, deploy, contract. |
| Dropping a column while the model still maps it | Breaks **every** query for that model, not just ones using the field. |
| Importing ORM models inside a migration | Pins live code to historical schema; the migration breaks months later on a fresh database. |
| One `UPDATE` over 40M rows | Hours-long lock, huge WAL, unresumable. Batch it. |
| Running `alembic upgrade` in app startup | Ten replicas race; nine block; readiness probes fail. Use a one-off job. |
| Trusting `downgrade()` as a rollback plan | Data is gone. Roll forward with a new migration. |
| No `lock_timeout` | One slow query turns an instant `ALTER` into a total table outage. |

## Interview questions

**Q: Your migration is `ALTER TABLE orders ADD COLUMN status TEXT`. It took 40 seconds in production and the site went down. Why?**

> The `ALTER` itself was instant — adding a nullable column with no default is metadata-only on
> modern Postgres. What took 40 seconds was **waiting for the lock**. `ALTER TABLE` needs ACCESS
> EXCLUSIVE, and something already held a shared lock — a long analytics query, or an idle-in-
> transaction connection that read the table and never committed. My `ALTER` queued behind it.
> **And because lock requests are FIFO, every query that arrived after mine queued behind my
> pending exclusive lock** — so normal traffic was blocked too, even though it would have been
> compatible with the query that was actually running. The fix is `SET lock_timeout = '3s'` at the
> top of the migration: it turns a 40-second outage into a failed deploy I can retry.

**Q: How do you rename a column with zero downtime?**

> You don't rename it — the rename itself is instant, but it's instantly *incompatible* with the
> code currently running. I use expand/contract across three deploys. Release one adds the new
> column and makes the code write both while reading the old one; the old code is unaffected because
> the old column is still authoritative. Release two switches reads to the new column, still writing
> both — so a rollback to release one is still safe. Release three stops writing the old column and
> drops it. Three deploys instead of one, and no window where a running process references a column
> that doesn't exist.

**Q: Why shouldn't you import your SQLAlchemy models into a migration file?**

> Because a migration is pinned to a point in schema history and your models are always at HEAD.
> A migration that does `session.query(User)` today works; six months later, after `User` gains
> three columns from later migrations, running `alembic upgrade head` on a fresh database executes
> this old migration against a schema that doesn't have those columns yet, and it crashes. The
> symptom is brutal: migrations that "have always worked" fail only for new environments and new
> developers. I use `sa.text()` or a minimal `sa.table()/sa.column()` stub that describes the schema
> **as it is at that migration**.

**Q: `alembic upgrade head` fails with "Multiple head revisions". What happened?**

> Two branches each created a migration whose `down_revision` pointed at the same parent, so the
> chain forked. Migrations are a linked list, not a sorted set — filenames and timestamps mean
> nothing. I run `alembic heads` to see both, then `alembic merge -m "merge x and y" <rev1> <rev2>`,
> which creates an empty migration with two parents and rejoins the chain. The important part is
> checking whether the two migrations actually *conflict* — a merge revision reunites the graph but
> does not reconcile two people who both added a column named `status`.

**Q: Where in the deploy pipeline do migrations run?**

> As a separate one-off job that must succeed before the new code rolls out — never in application
> startup, because ten replicas booting at once means ten concurrent `alembic upgrade head`, nine of
> which block on the version-table lock long enough to fail their readiness probes. Ordering is
> expand-before, contract-after: additive migrations run before the code deploy so old code still
> works against the new schema, and drops run after the deploy, because a drop is the one change
> that's deliberately not backwards-compatible.

## 🎙️ Articulation drill

**Two minutes: "Walk me through adding a NOT NULL column to a table with 40 million rows, live."**

Say the premise first — old code and new code run simultaneously, so the schema must satisfy both.
Then the four steps with the reason for each: nullable-with-default so new rows are correct
immediately and the write is metadata-only; a batched, resumable backfill in its own transactions;
`CHECK ... NOT VALID` then `VALIDATE`, both of which take weak locks; and finally `SET NOT NULL`,
which Postgres 12+ short-circuits because the valid CHECK already proves it. Finish with
`lock_timeout`, and with the sentence that ties it together: **the migration was never the slow
part — the queue behind it was.**
