# Part 1 — ⭐ Index types, and the two that are genuinely different

```
⭐ SINGLE FIELD   db.orders.createIndex({customer_id: 1})
⭐ COMPOUND       db.orders.createIndex({customer_id: 1, status: 1,
⭐                                       created_at: -1})
⭐ ⭐⭐ MULTIKEY   — automatic on any array field. One index entry PER
⭐                  ARRAY ELEMENT.
⭐ TEXT           — one per collection, ⭐ crude next to Day 199's FTS
⭐ 2dsphere       — geospatial
⭐ HASHED         — for shard keys (Day 213)
⭐ WILDCARD       {"attributes.$**": 1} — ⭐ index unknown field names.
⭐                  ⭐⭐ For genuinely user-defined attributes. Expensive.
⭐ PARTIAL        partialFilterExpression: {status: "pending"}
⭐                  ⭐⭐ Day 190's partial index, identical reasoning:
⭐                  a queue of 400 pending inside 200M rows.
⭐ UNIQUE         ⭐ and `unique + partial` for Day 187's soft-delete case
⭐ ⭐⭐ TTL        db.sessions.createIndex({expires_at: 1},
⭐                                        {expireAfterSeconds: 0})
```

```
⭐⭐ THE TWO WORTH DWELLING ON:

⭐ ① ⭐⭐ TTL INDEXES — Postgres has no equivalent, and this is a real
⭐    convenience. A background thread deletes expired documents every
⭐    ~60 s.
⭐    ⭐⭐ THE THREE THINGS PEOPLE GET WRONG:
⭐      ⭐ DELETION IS NOT PROMPT. Up to a minute late, more under load.
⭐        ⇒ ⭐⭐ NEVER USE A TTL INDEX AS A SECURITY OR CORRECTNESS
⭐          BOUNDARY. Filter on `expires_at > now` in the query too; the
⭐          index is housekeeping, not enforcement.
⭐      ⭐ It only fires on a DATE field (or an array of dates — then
⭐        the EARLIEST wins).
⭐      ⭐⭐ On a large collection the deleter is a real write workload
⭐        with real IO. ⭐ It has caused replication lag incidents.

⭐ ② ⭐⭐ MULTIKEY, AND ITS RESTRICTION — the one that surprises people:
⭐    ⭐⭐ A COMPOUND INDEX MAY INCLUDE AT MOST ***ONE*** ARRAY FIELD.
⭐    ⭐ `{tags: 1, comments.author: 1}` where both are arrays ⇒ the
⭐      index cannot be built (or the insert fails if it exists).
⭐    ⭐ Why: the number of entries would be the CARTESIAN PRODUCT of
⭐      the two arrays. ⭐⭐ Day 192's row multiplication, appearing as
⭐      an index restriction — the same fact, third costume.
⭐    ⭐ Also: multikey indexes cannot provide a covered query, and a
⭐      sort on a multikey field has surprising semantics.
```

# Part 2 — ⭐⭐ ESR: the same rule, the same reason

```
⭐   db.orders.find({customer_id: "c:42", status: "paid",
⭐                   created_at: {$gte: cutoff}})
⭐            .sort({created_at: -1}).limit(20)

⭐⭐ MONGODB'S OWN DOCUMENTED RULE IS ***ESR***:
⭐   ⭐ EQUALITY first · ⭐ SORT next · ⭐ RANGE last
⭐   ⇒ ⭐⭐ {customer_id: 1, status: 1, created_at: -1}
⭐
⭐ ⭐⭐ IT IS DAY 190'S RULE, VERBATIM, FOR THE SAME REASON: an equality
⭐   narrows to one contiguous block of index entries in which the next
⭐   key is still sorted; a range scatters everything after it, so those
⭐   keys can only be applied as a filter.
⭐ ⇒ ⭐⭐ THAT IS THE STAGE-5 PAYOFF: you did not learn "how Postgres
⭐   indexes work". You learned how B-trees work, and MongoDB agrees
⭐   because physics does not have vendors.
```

```javascript
// ⭐⭐ READING THE PLAN — the three numbers, and the ratio that matters
db.orders.find({...}).sort({...}).explain("executionStats")

// winningPlan.stage: ⭐ COLLSCAN (bad) · IXSCAN (good)
//                    ⭐⭐ SORT  ⇒ NO INDEX SERVED THE SORT
//                    ⭐⭐ FETCH ⇒ it went to the documents
//                    ⭐ PROJECTION_COVERED ⇒ never touched them
// executionStats:
//   nReturned:            20
//   totalKeysExamined:    20        ⭐ index entries read
//   totalDocsExamined:    20        ⭐ documents fetched
//   executionTimeMillis:  1
```

```
⭐⭐ THE DIAGNOSTIC IS THE RATIO, AND IT IS `Rows Removed by Filter`
⭐   WEARING A DIFFERENT NAME (Day 191):
⭐   ⭐ keysExamined / nReturned ≈ 1   ✅ the index is precise
⭐   ⭐⭐ docsExamined ≫ nReturned      ❌ the index found candidates and
⭐        the SERVER filtered them — ⭐ a missing or badly-ordered key
⭐   ⭐⭐ docsExamined = 0              ⭐⭐ A COVERED QUERY. Nothing was
⭐        fetched; the index answered it entirely. ⭐ Requires: every
⭐        field in the filter, sort AND projection is in the index, and
⭐        `_id` is explicitly excluded.
⭐   ⭐⭐ A `SORT` STAGE WITH `hasSortStage: true` ⇒ AN IN-MEMORY SORT,
⭐        ⭐⭐ CAPPED AT 32 MB — beyond that the query ***FAILS***, it
⭐        does not spill. ⭐ Day 191's spill, but fatal instead of slow.
⭐   ⭐ `$hint` forces an index — ⭐⭐ a diagnostic, never a fix, exactly
⭐        like `enable_seqscan=off`.
```

# Part 3 — ⭐⭐ The aggregation pipeline, and the order that decides everything

```
⭐   [ {$match: …}, {$lookup: …}, {$unwind: …}, {$group: …},
⭐     {$sort: …}, {$limit: …}, {$project: …} ]
⭐   ⭐ Each stage consumes the previous stage's documents. ⭐⭐ It is
⭐     Day 047's generator pipeline, on a server.

⭐⭐ THE FOUR RULES, IN ORDER OF HOW MUCH THEY MATTER:

⭐ ① ⭐⭐ `$match` FIRST, AND AS EARLY AS POSSIBLE.
⭐    ⭐ Only a `$match` at the START can use an index. ⭐⭐ A `$match`
⭐      after a `$group` is filtering a materialised intermediate result
⭐      with no index at all.
⭐    ⭐ The optimiser does move some `$match`es earlier — ⭐⭐ but it
⭐      CANNOT move one past a `$group`, a `$unwind` that changes the
⭐      field, or most `$project`s. ⭐ Write the order you want.

⭐ ② ⭐⭐ `$sort` MUST BE INDEX-SERVED OR IT IS CAPPED AT 100 MB AND
⭐    ***ERRORS***. `allowDiskUse: true` lifts it to disk — ⭐⭐ but a
⭐    disk sort of ten million documents is not a fix, it is a symptom.
⭐    ⭐ `$sort` immediately before `$limit` is optimised into a top-k
⭐      scan, which is genuinely cheap. ⭐⭐ `$sort` then `$skip` then
⭐      `$limit` is Day 193's offset problem, unchanged.

⭐ ③ ⭐ `$project`/`$unset` EARLY to shrink documents — ⭐⭐ every later
⭐    stage carries whatever you did not drop, and the 100 MB limit is
⭐    per stage.

⭐ ④ ⭐⭐ `$limit` AS EARLY AS CORRECTNESS ALLOWS.
```

```
⭐⭐ `$lookup` — IT IS A LEFT OUTER JOIN, AND BOTH COMMON OPINIONS ABOUT
⭐   IT ARE WRONG:
⭐   ❌ "Mongo can't join." ⭐ It can, since 3.2.
⭐   ❌ "So joins are fine." ⭐⭐ It executes as a lookup PER INPUT
⭐      DOCUMENT against the foreign collection. ⭐⭐ THAT IS AN N+1
⭐      WITH A NICE SYNTAX — and unlike Postgres, THERE IS NO PLANNER
⭐      THAT WILL TURN IT INTO A HASH JOIN.
⭐   ⇒ ⭐⭐ THE RULES: `$match` HARD FIRST so few documents reach it;
⭐     ⭐⭐ THE FOREIGN FIELD MUST BE INDEXED (if it is not, you have
⭐     written N collection scans); and it cannot cross shards in the
⭐     general case.
⭐   ⇒ ⭐⭐ IF YOU FIND YOURSELF WRITING SEVERAL `$lookup`s, THAT IS THE
⭐     SCHEMA TELLING YOU DAY 211'S DECISION WAS WRONG — or that this
⭐     data wanted a relational database. ⭐ It is a legitimate signal,
⭐     not a failure.
```

```
⭐⭐ `$unwind` — ⭐⭐ IT IS ROW MULTIPLICATION (Day 192), EXPLICITLY.
⭐   One order with 3 items becomes 3 documents.
⭐   ⇒ ⭐⭐ SO A `$group` AFTER TWO `$unwind`s DOUBLE-COUNTS, EXACTLY AS
⭐     A DOUBLE JOIN DOES — ⭐ and it returns plausible numbers, so it
⭐     ships. ⭐ Day 192's rule survives: unwind ONE multi-valued path
⭐     per pipeline, or aggregate each in a `$facet` and combine.
⭐   ⭐ `preserveNullAndEmptyArrays: true` is the LEFT-JOIN equivalent —
⭐     ⭐⭐ without it, documents with an empty array VANISH from your
⭐     results, which is Day 192's `LEFT JOIN … WHERE` bug in a new
⭐     costume.
```

```javascript
// ⭐ The stages worth knowing beyond the basics:
{$facet: {byStatus: [...], byMonth: [...], total: [...]}}
// ⭐⭐ RUN SEVERAL SUB-PIPELINES OVER THE SAME INPUT IN ONE PASS —
//    this is how you compute faceted counts (Day 199's gap) in one
//    round trip. ⭐ Note each sub-pipeline is subject to the 100 MB cap.
{$bucket: {groupBy: "$price", boundaries: [0,100,500,1000]}}
{$setWindowFields: {...}}   // ⭐ 5.0+: window functions, i.e. rank,
                            //   running totals — SQL's, arriving late
{$merge: {into: "daily_rollup"}}  // ⭐⭐ WRITE THE RESULT TO A
                                  //    COLLECTION = a materialised
                                  //    view (Day 188), refreshed by a
                                  //    scheduled pipeline. ⭐ This is
                                  //    the answer to slow reporting.
```

# Part 4 — ⭐ In Python, and the habits that keep it sane

```python
pipeline = [
    {"$match": {"tenant_id": tid,                    # ⭐⭐ INDEXED, FIRST
                "created_at": {"$gte": start, "$lt": end}}},
    {"$unwind": "$items"},                           # ⭐ ONE unwind
    {"$group": {"_id": "$items.product_id",
                "revenue": {"$sum": {"$multiply": [
                    "$items.unit_price_cents", "$items.qty"]}},
                "units": {"$sum": "$items.qty"}}},
    {"$sort": {"revenue": -1}},
    {"$limit": 20},
]
cur = db.orders.aggregate(pipeline, allowDiskUse=False,  # ⭐⭐ start
                          maxTimeMS=10_000)              #    FALSE so a
                                                         #    bad pipeline
                                                         #    fails loudly
```

```
⭐⭐ FOUR HABITS:
⭐  ① ⭐⭐ `maxTimeMS` ON EVERY AGGREGATION. Without it one bad pipeline
⭐     runs until someone notices. ⭐ Day 152's timeout hierarchy, at the
⭐     last boundary that did not have one.
⭐  ② ⭐⭐ `allowDiskUse=False` BY DEFAULT — so exceeding 100 MB is a
⭐     loud failure in staging rather than a silent slowness in
⭐     production. Turn it on deliberately, per job.
⭐  ③ ⭐ Build pipelines as a list of named stage-functions, not one
⭐     200-line literal. ⭐⭐ A pipeline is code; it deserves tests.
⭐  ④ ⭐⭐ `explain()` EVERY AGGREGATION THAT SHIPS, and check the FIRST
⭐     stage used an index. ⭐ That single check catches most of them.

⭐⭐ AND THE OPERATIONAL TOOLS, WHICH MAP ONE-TO-ONE ONTO DAY 202:
⭐   ⭐ `db.currentOp()`            → `pg_stat_activity`
⭐   ⭐ `db.killOp(id)`             → `pg_cancel_backend`
⭐   ⭐⭐ the PROFILER (`db.setProfilingLevel(1, {slowms: 100})`)
⭐        → `log_min_duration_statement` + `pg_stat_statements`
⭐   ⭐ `$indexStats`               → `pg_stat_user_indexes` (find
⭐        unused indexes — ⭐⭐ same rule: wait a full business cycle
⭐        before dropping)
⭐   ⭐ Atlas Performance Advisor    → index suggestions from real
⭐        workload. ⭐ Genuinely good; still verify with `explain`.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Assuming Mongo indexing is a different subject | Same B-trees, same ESR rule, same physics. |
| A compound index with two array fields | Not allowed — the entry count would be the cartesian product. |
| Trusting a TTL index for a security boundary | Deletion is up to a minute late. Filter on the date too. |
| Ignoring TTL deletion as a write workload | It has caused replication-lag incidents on large collections. |
| Reading only `executionTimeMillis` | The ratio of keys and docs examined to returned is the diagnostic. |
| Not noticing a `SORT` stage | An in-memory sort capped at 32 MB — beyond that the query fails. |
| `$hint` as a fix | It's a diagnostic, like `enable_seqscan = off`. |
| `$match` after `$group` | It can't use an index; it filters a materialised intermediate. |
| Relying on the optimiser to move `$match` | It can't move past `$group` or most `$project`s. |
| `allowDiskUse: true` as the default | A ten-million-document disk sort is a symptom, not a fix. |
| `$sort` + `$skip` + `$limit` for deep pages | Same offset problem as SQL. Use a range on the sort key. |
| Treating `$lookup` as a free join | It's a per-document lookup with no planner to turn it into a hash join. |
| `$lookup` on an unindexed foreign field | You wrote N collection scans. |
| Several `$lookup`s in one pipeline | That's the schema telling you the embed/reference call was wrong. |
| Two `$unwind`s then a `$group` | Row multiplication — every aggregate is inflated, with plausible numbers. |
| `$unwind` without `preserveNullAndEmptyArrays` | Documents with empty arrays vanish silently. |
| No `maxTimeMS` | One bad pipeline runs until someone notices. |

## Interview questions

**Q: How do you design a compound index in MongoDB?**

> Equality, Sort, Range — MongoDB documents it as the ESR rule, and it's the same rule as Postgres for
> the same reason: an equality predicate narrows the index to one contiguous block in which the next
> key is still sorted, so it can narrow further, whereas a range scatters everything after it and those
> keys can only be applied as filters. For a query filtering on tenant and status, ranging on date and
> sorting by date, that's `{tenant: 1, status: 1, created_at: -1}`. I'd verify with
> `explain("executionStats")` and look at the ratio rather than the timing: keys examined over
> documents returned close to one means the index is precise, documents examined far above returned
> means the server is filtering after the fetch, and a `SORT` stage means no index served the ordering
> — which matters more here than in Postgres, because an in-memory sort is capped at 32 MB and the
> query *fails* rather than spilling.

**Q: What's `$lookup` and should you use it?**

> It's a left outer join, so "Mongo can't join" has been wrong since 3.2 — but "joins are fine now" is
> also wrong. It executes as a lookup per input document against the foreign collection, which is an
> N+1 with pleasant syntax, and unlike Postgres there's no planner that will decide to turn it into a
> hash join instead. So the rules are: `$match` hard first so very few documents reach the `$lookup`,
> and the foreign field must be indexed — if it isn't, you've written N collection scans. It also
> can't cross shards in the general case. The signal I'd pay attention to is the count: if a pipeline
> needs several `$lookup`s, that's the schema telling me the embed-versus-reference decision was wrong,
> or that this data wanted a relational database. That's useful information rather than a failure.

**Q: What does `$unwind` do to your aggregates?**

> It multiplies documents — one order with three items becomes three documents — which is exactly row
> multiplication from a SQL join. So two `$unwind`s followed by a `$group` double-counts in precisely
> the way a double join does, and just like there, it returns plausible numbers rather than an error,
> so it ships and someone notices months later that a dashboard is inflated. The rule survives
> unchanged: unwind at most one multi-valued path per pipeline, and if you need two, compute each in a
> `$facet` and combine. The other trap is that `$unwind` drops documents whose array is empty or
> missing unless you pass `preserveNullAndEmptyArrays` — which is the `LEFT JOIN` with a `WHERE` on the
> right table, in a new costume: the rows you were trying to preserve silently disappear.

**Q: When is a TTL index the right tool?**

> For housekeeping — expiring sessions, cached computations, event data past its retention window —
> where it saves you writing and operating a delete job, which is a genuine convenience Postgres has no
> equivalent for. Three caveats. Deletion isn't prompt: a background thread runs about once a minute
> and falls behind under load, so **a TTL index must never be a security or correctness boundary** —
> if an expired session must not be usable, the query filters on the expiry date too and the index is
> just cleanup. It only fires on a date field, and on an array of dates the earliest wins. And on a
> large collection the deleter is a real write workload with real IO, which has caused replication-lag
> incidents. So: excellent for hygiene, never for enforcement.

**Q: An aggregation is slow. What do you check?**

> First whether the pipeline starts with a `$match` that uses an index, because only a `$match` at the
> start can — and the optimiser will move some earlier for you but can't move one past a `$group` or
> most `$project`s, so I'd write the order I want rather than rely on it. Then `explain` for the same
> ratios as a find: keys and documents examined against returned. Then whether there's a blocking
> `$sort` that isn't index-served, since that's capped at 100 MB per stage and `allowDiskUse` turns a
> failure into a slow disk sort, which is a symptom rather than a fix. Then whether `$project` or
> `$unset` should come earlier, because every later stage carries whatever wasn't dropped and the
> memory cap is per stage. And I'd check for `$lookup` against an unindexed foreign field. Operationally
> the profiler with `slowms` set is the equivalent of `pg_stat_statements`, and `$indexStats` finds
> unused indexes with the same rule as Postgres — wait a full business cycle before dropping anything.

## 🎙️ Articulation drill

**Two minutes: "How do you make a MongoDB query fast?"**

Open by refusing to treat it as a new subject: **the indexes are B-trees, so the composite ordering
rule is the same one you already know — and MongoDB documents it under the same name, ESR.** Derive it
in one sentence so it's clear you understand rather than remember it. Then the diagnostic: not the
timing, but the ratio of keys and documents examined to documents returned, plus whether a `SORT`
stage appeared — and note the sharper edge here, that an in-memory sort past its cap *fails* rather
than spilling. Then the pipeline, where the only rule that really matters is **`$match` first, because
only a leading `$match` can use an index and the optimiser can't move one past a `$group`.** Then the
two traps that produce wrong answers rather than slow ones: **`$lookup` is a per-document lookup with
no planner to rescue it**, and **`$unwind` is row multiplication, so two of them plus a `$group` gives
you inflated numbers that look plausible.** Close on the honest signal: several `$lookup`s in a pipeline
means the schema decision was wrong, and that's information rather than a failure.
