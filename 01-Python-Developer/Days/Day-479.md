# Part 1 — ⭐⭐ What the GIL actually guarantees

```
⭐ ***THE BELIEF:*** ⭐ "Python has a GIL, so my dict is thread-
⭐   safe and I don't need locks."
⭐ ***THE TRUTH:*** ⭐⭐ ***INDIVIDUAL*** OPERATIONS ON BUILT-IN
⭐   TYPES ARE ATOMIC. ⭐ ***SEQUENCES*** OF THEM ARE NOT.

⭐ ✅ ***ATOMIC*** — will not interleave:
⭐   ⭐ `d[k] = v` · `d.get(k)` · `lst.append(x)` ·
⭐     `d.setdefault(k, v)` · `x = d.pop(k, None)`

⭐ ❌ ***NOT ATOMIC*** — a thread switch can land in the middle:
⭐   ⭐ ⭐⭐ `if k not in d: d[k] = compute()` ⭐ ← two operations
⭐   ⭐ ⭐⭐ `d[k] = d.get(k, 0) + 1` ⭐ ← read, add, write
⭐   ⭐ `if len(cache) > MAX: evict()` ⭐ ← check-then-act
⭐   ⭐ ⭐⭐ ANYTHING SPANNING A FUNCTION CALL, ⭐ because the
⭐     interpreter can switch threads at call boundaries

⭐ ⭐⭐ AND THE VERSION-SPECIFIC CAVEAT WORTH KNOWING IN 2026:
⭐   ⭐ Python 3.13+ ships an optional ***free-threaded*** build
⭐     with ***no GIL***. ⭐⭐ IN THAT BUILD, EVEN THE "ATOMIC"
⭐     COLUMN ABOVE NEEDS RE-CHECKING, ⭐ and code that
⭐     accidentally worked because of the GIL stops working.
⭐   ⭐ ⭐⭐ ⇒ THE ONLY DEFENSIBLE POSITION HAS ALWAYS BEEN:
⭐     ***DO NOT RELY ON THE GIL FOR CORRECTNESS.*** ⭐ Say that
⭐     sentence — it is right today and it stays right.

⭐ ***AND THE OTHER HALF, WHICH DECIDES YOUR ARCHITECTURE:***
⭐   ⭐ ⭐⭐ THE GIL MEANS THREADS DO NOT GIVE YOU CPU PARALLELISM.
⭐   ⭐ Threads are for ***I/O concurrency***; ⭐⭐ FOR CPU WORK
⭐     YOU NEED PROCESSES. ⭐ A "thread pool to speed up
⭐     computation" is a design smell in Python and an
⭐     interviewer will ask about it.
```

# Part 2 — The naive cache, and its three races

```python
# ⭐ THE VERSION EVERYONE WRITES FIRST.
class Cache:
    def __init__(self, load):
        self._d = {}
        self._load = load

    def get(self, key):
        if key not in self._d:        # ⭐⭐ ① CHECK
            self._d[key] = self._load(key)   # ⭐⭐ ② ACT
        return self._d[key]
```

```
⭐ ⭐⭐ THREE SEPARATE PROBLEMS, AND CANDIDATES USUALLY SEE ONE.

⭐ ① ⭐⭐ ***DUPLICATE WORK.*** ⭐ Two threads both see the key
⭐   missing and both call `_load`. ⭐ Wasteful, ⭐⭐ AND IF `_load`
⭐   HAS SIDE EFFECTS — INCREMENTING A COUNTER, CHARGING AN
⭐   API — IT IS A CORRECTNESS BUG, NOT A PERFORMANCE ONE.

⭐ ② ⭐⭐ ***THE STAMPEDE (THUNDERING HERD).*** ⭐ A popular key
⭐   expires. ⭐⭐ ONE THOUSAND IN-FLIGHT REQUESTS ALL MISS
⭐   SIMULTANEOUSLY AND ALL HIT THE DATABASE WITH THE ***SAME***
⭐   QUERY. ⭐ The database falls over, ⭐⭐ WHICH MAKES THE MISSES
⭐   SLOWER, WHICH MAKES MORE REQUESTS PILE UP. ⭐ This is a
⭐   feedback loop and it is how caches take down the system they
⭐   were added to protect.

⭐ ③ ***UNBOUNDED GROWTH.*** ⭐ No eviction ⇒ ⭐⭐ THIS IS NOT A
⭐   CACHE, IT IS A MEMORY LEAK WITH GOOD HIT RATES.

⭐ ⭐⭐ THE ORDER TO FIX THEM IN: ⭐ ③ first (bound it), ⭐ then ①
⭐   and ② together (single-flight), ⭐⭐ BECAUSE A CORRECT CACHE
⭐   THAT OOMs IS STILL AN OUTAGE.
```

# Part 3 — ⭐⭐ Single-flight: one loader per key

```
⭐ ***THE GOAL:*** ⭐ N concurrent misses on the same key ⇒
⭐   ⭐⭐ ***EXACTLY ONE*** LOAD, AND N-1 THREADS WAIT FOR IT.

⭐ ***THE WRONG FIX:*** ⭐ hold a global lock across `_load`.
⭐   ⭐ ⭐⭐ NOW EVERY MISS SERIALISES ***ALL*** TRAFFIC, INCLUDING
⭐     HITS ON UNRELATED KEYS, ⭐ and your cache is a global
⭐     bottleneck with a slow I/O call inside the critical
⭐     section. ⭐⭐ NEVER HOLD A LOCK ACROSS I/O.

⭐ ***THE RIGHT SHAPE — A ***FUTURE*** PER KEY:***
⭐   ⭐ under a short lock, either find an existing in-flight
⭐     future ⭐ or create one and mark yourself the loader;
⭐   ⭐ ⭐⭐ RELEASE THE LOCK, ***THEN*** DO THE SLOW WORK;
⭐   ⭐ everyone else waits on the future.
⭐   ⭐ ⭐⭐ THE LOCK PROTECTS THE ***BOOKKEEPING***, NOT THE
⭐     ***WORK***. ⭐ That sentence is the design.
```

```python
import threading
from concurrent.futures import Future
from collections import OrderedDict

class SingleFlightCache:
    def __init__(self, load, max_size: int = 1000):
        self._load = load
        self._max = max_size
        self._data: OrderedDict[str, object] = OrderedDict()
        self._inflight: dict[str, Future] = {}
        self._lock = threading.Lock()      # ⭐ guards bookkeeping only

    def get(self, key: str):
        with self._lock:
            if key in self._data:
                self._data.move_to_end(key)        # ⭐ LRU touch
                return self._data[key]
            fut = self._inflight.get(key)
            if fut is None:
                fut = Future()
                self._inflight[key] = fut
                leader = True                      # ⭐⭐ I LOAD
            else:
                leader = False                     # ⭐ I WAIT

        if not leader:
            return fut.result()        # ⭐⭐ NO LOCK HELD WHILE WAITING

        try:
            value = self._load(key)                # ⭐⭐ SLOW I/O,
        except Exception as e:                     #    LOCK RELEASED
            with self._lock:
                self._inflight.pop(key, None)
            fut.set_exception(e)       # ⭐⭐ WAITERS SEE THE ERROR —
            raise                      # never leave them hanging
        else:
            with self._lock:
                self._data[key] = value
                self._data.move_to_end(key)
                self._inflight.pop(key, None)
                while len(self._data) > self._max:
                    self._data.popitem(last=False)  # ⭐ evict oldest
            fut.set_result(value)
            return value
```

```
⭐ ⭐⭐ FIVE THINGS THAT CODE GETS RIGHT, AND EACH IS A RUBRIC ROW:
⭐   ⭐ ① the lock is held only around dict manipulation —
⭐     ⭐⭐ MICROSECONDS, NEVER I/O;
⭐   ⭐ ② ⭐⭐ THE EXCEPTION PATH REMOVES THE IN-FLIGHT ENTRY ***AND***
⭐     FAILS THE FUTURE — ⭐ forget either and every future caller
⭐     for that key blocks forever, ⭐⭐ WHICH IS THE WORST BUG ON
⭐     THIS PAGE;
⭐   ⭐ ③ `OrderedDict.move_to_end` + `popitem(last=False)` is
⭐     ⭐⭐ AN LRU IN TWO LINES;
⭐   ⭐ ④ eviction is `while`, not `if` — ⭐ the bound holds even
⭐     if `max` is lowered at runtime;
⭐   ⭐ ⑤ ⭐⭐ WAITERS BLOCK ON THE FUTURE, NOT ON THE LOCK, ⭐ so
⭐     unrelated keys are never delayed.
```

# Part 4 — TTL, and the stampede that survives single-flight

```
⭐ ***SINGLE-FLIGHT FIXES ***CONCURRENT*** MISSES ON ONE KEY. ⭐ It
⭐   does ***not*** fix these two:***

⭐ ① ⭐⭐ ***SYNCHRONISED EXPIRY.*** ⭐ Ten thousand keys written
⭐   at the same moment with the same TTL ⭐⭐ ALL EXPIRE AT THE
⭐   SAME MOMENT. ⭐ Single-flight collapses each key to one
⭐   load — ⭐⭐ AND YOU STILL GET TEN THOUSAND SIMULTANEOUS
⭐   LOADS.
⭐   ⭐ ⇒ ⭐⭐ ***JITTER THE TTL***: `ttl * random.uniform(0.8, 1.2)`.
⭐     ⭐ One line, and it is the fix nobody writes until after
⭐     the incident.

⭐ ② ⭐⭐ ***THE COLD-START HERD.*** ⭐ A deploy empties the cache;
⭐   every key is a miss at once. ⭐ ⇒ warm the top-N keys on
⭐   start, or ⭐⭐ ROLL DEPLOYS SO ONE FULL CACHE ALWAYS SURVIVES.

⭐ ***AND THE TWO REFINEMENTS WORTH NAMING:***
⭐   ⭐ ⭐⭐ ***SERVE-STALE-WHILE-REVALIDATING*** — ⭐ on expiry,
⭐     return the stale value ***immediately*** and refresh in
⭐     the background. ⭐⭐ NOBODY EVER WAITS, AND IT TURNS THE
⭐     CACHE INTO A FALLBACK TIER WHEN THE SOURCE IS DOWN
⭐     (D454/456).
⭐   ⭐ ⭐⭐ ***NEGATIVE CACHING*** — ⭐ cache "not found" too, with
⭐     a shorter TTL. ⭐⭐ OTHERWISE A MISSING KEY IS AN INFINITE
⭐     CACHE MISS AND AN ATTACKER CAN BYPASS YOUR CACHE ENTIRELY
⭐     BY REQUESTING KEYS THAT DO NOT EXIST.

⭐ ***EXPIRY MECHANISM — LAZY BEATS ACTIVE:***
⭐   ⭐ store `(value, expires_at)`, ⭐ check on read.
⭐   ⭐ ⭐⭐ NO SWEEPER THREAD, NO TIMER PER ENTRY, ⭐ and the LRU
⭐     bound already stops unbounded growth of dead entries.
⭐   ⭐ ⭐ Use `time.monotonic()`, not `time.time()` — ⭐⭐ THE WALL
⭐     CLOCK CAN JUMP BACKWARDS AND YOUR ENTRIES BECOME
⭐     IMMORTAL (D409).
```

# Part 5 — ⭐⭐ The asyncio version is a different program

```
⭐ ***THE QUESTION THEY WILL ASK:*** ⭐ "your service is async —
⭐   does this still work?"
⭐ ⭐⭐ ANSWER: NO, AND THE REASON MATTERS.

⭐ ① ⭐⭐ `threading.Lock` IN AN `async def` ***BLOCKS THE ENTIRE
⭐   EVENT LOOP***. ⭐ Every other coroutine — unrelated requests,
⭐   the health check — stops. ⭐⭐ ONE SLOW LOAD BECOMES A TOTAL
⭐   STALL (DAY 453).
⭐   ⭐ ⇒ ***`asyncio.Lock`***, which yields instead of blocking.
⭐ ② ⭐⭐ NEVER MIX THEM. ⭐ An `asyncio.Lock` is not thread-safe;
⭐   a `threading.Lock` is not loop-safe. ⭐ If you genuinely have
⭐   both worlds, ⭐⭐ THE ONLY SANE ANSWER IS A DEDICATED THREAD
⭐   POOL VIA `asyncio.to_thread`, WITH THE CACHE OWNED BY ONE
⭐   SIDE.
⭐ ③ ***the single-flight shape is unchanged*** — ⭐⭐ ONLY THE
⭐   PRIMITIVE CHANGES: ⭐ `asyncio.Future` and `await fut`
⭐   instead of `Future` and `fut.result()`.
⭐   ⭐ ⭐⭐ SAY THAT: THE ***ALGORITHM*** IS PORTABLE, THE
⭐     ***PRIMITIVES*** ARE NOT.

⭐ ***AND THE ANSWER THAT ENDS THE ROUND WELL:***
⭐   ⭐ ⭐⭐ "IF THIS IS MULTI-PROCESS OR MULTI-POD, AN IN-PROCESS
⭐     CACHE IS PER-INSTANCE BY DEFINITION — ⭐ ten pods means ten
⭐     caches and ten stampedes. ⭐⭐ SINGLE-FLIGHT THEN HAS TO BE
⭐     DISTRIBUTED: A SHORT-LIVED LOCK KEY IN REDIS, ⭐ with a
⭐     TTL so a dying pod cannot wedge the key forever — ⭐⭐ AND
⭐     AT THAT POINT I'D WANT TO KNOW WHETHER THE COMPLEXITY IS
⭐     WORTH IT VERSUS JUST ACCEPTING TEN LOADS."
```

# 💬 Interview

**1. "Is a Python dict thread-safe?"**

⭐ Individual operations are; sequences aren't, and that distinction is the whole topic. ⭐⭐ `d[k] = v`
and `d.get(k)` won't interleave, but `if k not in d: d[k] = compute()` is two operations with a thread
switch possible between them — that's check-then-act, and it's exactly as racy as it would be in C.
⭐ Anything spanning a function call is a switch point. ⭐⭐ I'd also add that I don't rely on the GIL for
correctness in any case, because 3.13 ships an optional free-threaded build where even the atomic column
needs re-checking — code that accidentally worked because of the GIL stops working there.

**2. "What's wrong with the naive cache?"**

⭐ Three things, and people usually see one. ⭐⭐ Duplicate work — two threads both miss and both load,
which is merely wasteful unless the loader has side effects, in which case it's a correctness bug.
⭐ The stampede: a popular key expires and a thousand in-flight requests all miss simultaneously and hit
the database with the same query. ⭐⭐ That's a feedback loop — the database slows, so misses take
longer, so more requests pile up — and it's how a cache takes down the system it was added to protect.
⭐ And unbounded growth, which makes it a memory leak with good hit rates. ⭐⭐ I'd fix the bound first,
because a correct cache that OOMs is still an outage.

**3. "Fix the stampede."**

⭐ Single-flight: N concurrent misses on a key produce exactly one load, and the others wait. ⭐⭐ The
wrong fix is holding a global lock across the load — that serialises all traffic including hits on
unrelated keys, and it puts slow I/O inside a critical section. ⭐ The right shape is a future per key:
under a short lock I either find an in-flight future or create one and become the loader; then I release
the lock and do the slow work; everyone else waits on the future. ⭐⭐ The lock protects the bookkeeping,
not the work. ⭐ That one sentence is the design.

**4. "What breaks in your single-flight implementation?"**

⭐ The exception path, and it's the bug I'd most want to be asked about. ⭐⭐ If the loader raises and I
only remove the in-flight entry without failing the future — or fail the future without removing the
entry — every caller waiting on it blocks forever. ⭐ A production hang with no error in any log, because
technically nothing failed. ⭐⭐ So both happen: pop the in-flight entry under the lock, set the exception
on the future, then re-raise. ⭐ Almost everyone writes the happy path correctly; that's the row that
separates people who've run one.

**5. "You've added single-flight. Is the stampede gone?"**

⭐ For concurrent misses on one key, yes. ⭐⭐ Two cases survive it. ⭐ Synchronised expiry: ten thousand
keys written at the same moment with the same TTL all expire together, so single-flight collapses each
key to one load and you still get ten thousand simultaneous loads. ⭐⭐ The fix is jittering the TTL —
multiply by a random factor between 0.8 and 1.2 — one line, and it's the thing nobody writes until after
the incident. ⭐ And cold start: a deploy empties the cache and everything misses at once, so you warm
the top keys or roll deploys so one full cache always survives. ⭐⭐ I'd also serve stale while
revalidating, which means nobody ever waits and the cache becomes a fallback tier when the source is
down.

**6. "Your service is async. Does this still work?"**

⭐ No, and the reason is the important part. ⭐⭐ A `threading.Lock` inside an `async def` blocks the
entire event loop — every other coroutine, including unrelated requests and the health check, stops.
One slow load becomes a total stall. ⭐ So it's `asyncio.Lock`, which yields rather than blocks. ⭐⭐ And
never mix them: an asyncio lock isn't thread-safe and a threading lock isn't loop-safe. ⭐ What's worth
saying is that the *algorithm* is unchanged — the single-flight shape is identical, only the primitives
differ, `asyncio.Future` and `await` instead of `Future` and `.result()`. ⭐⭐ The algorithm is portable;
the primitives are not.

**7. "You have ten pods."**

⭐ Then an in-process cache is per-instance by definition — ten pods means ten caches and ten stampedes,
so my single-flight guarantee is now per-pod rather than global. ⭐⭐ Making it global means a distributed
lock: a short-lived key in Redis with a TTL, so a pod dying mid-load can't wedge that key forever. ⭐ But
I'd want to ask whether that's worth it, because ten concurrent loads is often perfectly survivable and
a distributed lock adds a dependency, a failure mode, and the fencing problem. ⭐⭐ The honest answer is
that it depends on what the loader costs, and I'd rather measure that than assume.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "design a thread-safe cache with a loader."**

Start by naming the class of bug. **"A cache is a chain of check-then-act sequences, and that's the
whole difficulty. People assume the GIL protects them — it makes individual bytecodes atomic, so `d[k] =
v` is safe, but `if k not in d: d[k] = load()` is two operations with a switch point between them. It's
exactly as racy as it would be in C. And I don't rely on the GIL for correctness anyway, because the
free-threaded builds remove that accidental protection."**

Then enumerate the three problems. **"The naive version has three bugs and people usually see one.
Duplicate work — two threads both miss and both load, which is a correctness bug rather than a
performance one if the loader has side effects. The stampede — a hot key expires and a thousand in-flight
requests hit the database with the same query, which is a feedback loop, because the database slowing
down makes more requests pile up. And unbounded growth, which makes it a memory leak with good hit
rates. I'd bound it first, because a correct cache that OOMs is still an outage."**

Then the design, stated as a principle. **"The fix for the first two is single-flight: one load per key,
everyone else waits. The wrong way is holding a lock across the load, which serialises unrelated keys and
puts slow I/O in a critical section. The right way is a future per key — under a short lock I either find
an in-flight future or create one and become the loader, then release the lock before doing the work. The
lock protects the bookkeeping, not the work."**

Close on the bug that matters and the caveats. **"The part I'd be most careful about is the exception
path: if the loader raises, I must both remove the in-flight entry and fail the future. Do only one and
every future caller for that key blocks forever — a production hang with nothing in the logs. And
single-flight doesn't fix everything: ten thousand keys with the same TTL still expire together, so TTLs
get jittered. If the service is async, the algorithm is identical but the primitives aren't — a threading
lock in an async handler stalls the entire event loop. And across ten pods this is per-instance by
definition, so I'd ask whether ten concurrent loads is actually a problem before reaching for a
distributed lock."**
