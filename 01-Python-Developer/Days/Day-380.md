# Day 380 ☁️

**P-380** · ☁️ **The cloud model** — regions, AZs, shared responsibility, ⭐⭐ and the two planes

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the cloud is not someone else's computer, it is someone else's *API* — and
> almost every cloud failure mode you have not seen before comes from the fact that the API that
> changes things and the thing being changed fail independently, with the API failing more often.**

---

# Part 1 — What you are actually buying

```
⭐⭐ NOT SERVERS. ***AN API OVER CAPACITY, PLUS A HARD LINE OF
⭐   RESPONSIBILITY DRAWN THROUGH THE MIDDLE OF YOUR SYSTEM.***

⭐ The five things you rent, in order of how much of the
⭐ operational burden they remove:
⭐   ① ⭐ COMPUTE — a machine, or a fraction of one, or a
⭐      process invocation. ⭐ You still own the OS upward.
⭐   ② ⭐ STORAGE — durable bytes with an HTTP API, or a block
⭐      device. ⭐⭐ DURABILITY IS THEIRS. CORRECTNESS IS YOURS.
⭐   ③ ⭐ NETWORK — a software-defined network you configure by
⭐      API. ⭐⭐ FIREWALLS ARE NOW OBJECTS IN A DATABASE, NOT
⭐      DEVICES IN A RACK, ⭐ which is why they can be wrong in
⭐      ways a physical cable cannot.
⭐   ④ ⭐⭐ ***MANAGED STATE*** — a database, a cache, a queue,
⭐      where you buy *the operations* rather than the software.
⭐      ⭐ This is where most of the value is, ⭐⭐ AND WHERE MOST
⭐      OF THE LOCK-IN IS.
⭐   ⑤ ⭐⭐ ***THE CONTROL PLANE ITSELF*** — ⭐ the ability to
⭐      create and destroy all of the above in seconds, from
⭐      code. ⭐⭐ THIS IS THE ACTUAL PRODUCT. Everything else
⭐      existed before; ⭐ this is what changed.

⭐⭐ ⇒ AND THE CONSEQUENCE THAT ORGANISES THE WHOLE STAGE:
⭐   ***BECAUSE INFRASTRUCTURE IS NOW AN API CALL, IT IS NOW
⭐   SOFTWARE — SO IT GETS VERSIONED, REVIEWED AND TESTED
⭐   (DAY 379), AND IT CAN NOW FAIL THE WAY SOFTWARE FAILS.***
```

# Part 2 — Regions and availability zones, with the arithmetic

```
⭐⭐ ***A REGION IS AN INDEPENDENT FAILURE DOMAIN.*** ⭐ Separate
⭐   capacity, separate control plane, separate billing surface,
⭐   separate legal jurisdiction. ⭐⭐ SERVICES IN ONE REGION DO
⭐   NOT DEPEND ON ANOTHER — ⭐ that is the whole design goal.

⭐⭐ ***AN AZ IS ONE OR MORE DATA CENTRES WITH INDEPENDENT POWER,
⭐   COOLING AND NETWORK, INSIDE ONE REGION.*** ⭐ Far enough
⭐   apart to not share a flood or a substation, ⭐ close enough
⭐   to be a sub-millisecond network away.

⭐⭐ THE NUMBERS THAT DECIDE YOUR ARCHITECTURE:
⭐   ⭐ SAME AZ  ............ ~0.1 ms      ⭐ free
⭐   ⭐ CROSS-AZ ............ ~0.5–1 ms    ⭐⭐ $0.01/GB ***EACH
⭐     DIRECTION*** — ⭐ so a chatty service pair split across
⭐     AZs pays twice for every round trip
⭐   ⭐ CROSS-REGION ........ 60–100 ms+   ⭐ (us-east-1 ⇄
⭐     eu-west-1 ≈ 75 ms) ⭐⭐ AND $0.02/GB

⭐⭐ ⇒ THE RULE THAT FALLS OUT OF THOSE THREE LINES:
⭐   ⭐⭐ ***SYNCHRONOUS REPLICATION ACROSS AZs IS FINE.
⭐   SYNCHRONOUS REPLICATION ACROSS REGIONS IS NOT*** — ⭐ 75 ms
⭐   added to ***every write*** is not a tuning problem, it is a
⭐   different product. ⭐ Cross-region is asynchronous, which
⭐   means it has an RPO measured in seconds (Day 328).

⭐⭐ AND THE HONEST POSITION ON MULTI-REGION: ***IT COSTS 3–10×
⭐   AND MOST COMPANIES THAT BUILD IT DO NOT NEED IT.*** ⭐ You
⭐   need multi-***AZ***. ⭐ Multi-region is for a regulatory
⭐   requirement, a latency requirement on another continent, or
⭐   an RTO that survives a full regional event — ⭐⭐ AND IF YOU
⭐   CANNOT NAME WHICH OF THE THREE, YOU ARE BUYING COMPLEXITY.
```

# Part 3 — ⭐⭐ Control plane vs data plane

> **This is the most important idea in the stage.** It is also the one that separates people who have
> operated in the cloud from people who have deployed to it.

```
⭐⭐ ***THE CONTROL PLANE IS THE API THAT CREATES, MODIFIES AND
⭐   DESTROYS.*** ⭐ RunInstances. CreateBucket. UpdateService.
⭐   ModifyTargetGroup. ⭐ It is a distributed system with a
⭐   database behind it, and it is doing a lot of work.

⭐⭐ ***THE DATA PLANE IS THE THING THAT SERVES YOUR TRAFFIC.***
⭐   ⭐ The running instance. GET on an object. A packet crossing
⭐   a load balancer. ⭐ It is simpler, more replicated, and
⭐   deliberately built to keep running with no control plane at
⭐   all.

⭐⭐ ⇒ ***THEY FAIL INDEPENDENTLY, AND THE CONTROL PLANE FAILS
⭐   MORE OFTEN.*** ⭐ That single asymmetry produces four
⭐   consequences you will otherwise learn during an incident:

⭐ ① ⭐⭐ ***YOUR RECOVERY PLAN MAY DEPEND ON THE PLANE THAT IS
⭐    DOWN.*** ⭐ "We'll just scale out" is a control-plane call.
⭐    "We'll fail over to the other AZ" is a control-plane call.
⭐    ⭐⭐ DURING A LARGE REGIONAL EVENT, RUNNING INSTANCES OFTEN
⭐    KEEP SERVING WHILE NOTHING NEW CAN BE LAUNCHED — ⭐ so the
⭐    plan you rehearsed is the one thing unavailable.

⭐ ② ⭐⭐ ***STATIC STABILITY IS THE ANSWER*** (Day 336). ⭐ A
⭐    statically stable system survives a failure ***without
⭐    making any control-plane call.*** ⭐ Concretely: run N+1
⭐    across AZs so losing one AZ needs no scaling action; keep
⭐    the standby warm rather than creating it on demand;
⭐    ⭐⭐ PRE-PROVISION FOR THE FAILURE INSTEAD OF REACTING TO IT.
⭐    ⭐ It costs more. ⭐⭐ THAT COST IS THE PRODUCT.

⭐ ③ ⭐ DNS failover, autoscaling and certificate issuance are
⭐    ***all*** control-plane operations. ⭐⭐ SO IS EVERY
⭐    `boto3` CALL IN YOUR APPLICATION — ⭐ which is why an app
⭐    that calls `describe_instances` on the request path has a
⭐    hidden dependency on the least reliable part of AWS.

⭐ ④ ⭐⭐ ***NEVER PUT A CONTROL-PLANE CALL IN A HEALTH CHECK.***
⭐    ⭐ A health check that calls the AWS API turns a control-
⭐    plane slowdown into your service being marked unhealthy and
⭐    replaced — ⭐⭐ WHICH IS THE DEATH SPIRAL OF DAY 325 WITH A
⭐    CLOUD PROVIDER SUPPLYING THE PUSH.
```

# Part 5 — IaaS → PaaS → serverless, judged honestly

```
⭐⭐ IT IS ***NOT*** A LADDER OF SOPHISTICATION. ⭐ It is a
⭐   spectrum of ***how much surface is managed***, and each step
⭐   makes exactly the same trade:

⭐   ⭐⭐ ***EACH STEP UP REMOVES WORK YOU MUST DO AND ADDS
⭐   BEHAVIOUR YOU CANNOT CHANGE.***

⭐ EC2 ........... you own OS, patching, capacity, everything
⭐ ECS/Fargate ... you own the image and the config
⭐ Lambda ........ you own the function; ⭐⭐ AND YOU INHERIT A
⭐                 15-MINUTE CEILING AND A COLD START (Day 391)
⭐ RDS ........... you own the schema; ⭐⭐ AND YOU CANNOT INSTALL
⭐                 AN ARBITRARY EXTENSION OR TOUCH THE FILESYSTEM

⭐⭐ ⇒ THE THREE QUESTIONS TO ASK BEFORE ADOPTING ***ANY***
⭐   MANAGED SERVICE — ⭐ ask them out loud, in this order:
⭐   ① ⭐⭐ ***WHAT HAPPENS AT THE LIMIT?*** ⭐ Every managed
⭐      service has quotas. ⭐⭐ FIND THEM BEFORE PRODUCTION DOES.
⭐   ② ⭐⭐ ***WHAT DOES THE EXIT LOOK LIKE?*** ⭐ Not "will we
⭐      leave" — ⭐ "if we had to, what is the shape of the work?"
⭐      ⭐ SQS → any queue is a week. ⭐⭐ DYNAMODB SINGLE-TABLE →
⭐      A REWRITE (DAY 332).
⭐   ③ ⭐⭐ ***WHAT FAILURE MODE CAN I NO LONGER FIX MYSELF?***
⭐      ⭐ This is the one nobody asks, and it is the one that
⭐      matters at 3 a.m. ⭐⭐ WITH RDS YOU CANNOT `strace` THE
⭐      PROCESS. YOUR ONLY MOVE IS A SUPPORT TICKET — ⭐ so buy
⭐      the support plan, or accept the RTO.
```

# Part 6 — How cloud billing actually works (the preview)

```
⭐⭐ THREE MECHANISMS PRODUCE ~90% OF EVERY BILL:
⭐   ① ⭐⭐ ***PROVISIONED CAPACITY, CHARGED WHETHER USED OR
⭐      NOT.*** ⭐ An idle instance costs the same as a busy one.
⭐      ⭐⭐ UTILISATION IS THEREFORE A FIRST-CLASS ENGINEERING
⭐      METRIC (DAY 396).
⭐   ② ⭐⭐ ***DATA MOVEMENT, ASYMMETRICALLY.*** ⭐ In is free.
⭐      ⭐⭐ OUT TO THE INTERNET IS ~$0.09/GB. CROSS-AZ IS $0.01/GB
⭐      IN ***EACH*** DIRECTION. ⭐ This is why an architecture
⭐      diagram is also a cost diagram — ⭐⭐ EVERY ARROW THAT
⭐      CROSSES A BOUNDARY HAS A PRICE.
⭐   ③ ⭐ ***API CALLS.*** ⭐ Per request, per million. ⭐⭐ A
⭐      PYTHON LOOP IS A BILLING EVENT GENERATOR (DAY 386).

⭐⭐ ⇒ AND THE ONE-LINE MODEL TO KEEP: ***YOU PAY FOR TIME,
⭐   DISTANCE AND COUNT.*** ⭐ How long it exists, how far the
⭐   bytes travel, how many times you ask.
```

# 💬 Interview

**1. "What's the difference between a region and an availability zone, and why do I care?"**
> ⭐ A region is an independent failure domain with its own control plane; an AZ is an isolated data
> centre within it. ⭐⭐ **The reason to care is the latency: cross-AZ is under a millisecond so
> synchronous replication across AZs is free architecturally, while cross-region is 60–100 ms so
> replication there must be asynchronous — which means an RPO greater than zero.** ⭐ So multi-AZ buys
> you zero-data-loss survival of a data-centre failure, and multi-region buys you survival of a
> regional event at the cost of accepting data loss on failover. ⭐ Different products, and people
> conflate them.

**2. ⭐⭐ "What is the control plane, and why does it matter operationally?"**
> ⭐ The control plane is the API that creates and changes resources; the data plane is what serves
> traffic. ⭐⭐ **They fail independently and the control plane fails more often — so the operational
> rule is that your failure response must not depend on it.** ⭐ Concretely: during a large event your
> running instances typically keep serving but you cannot launch new ones, ⭐⭐ **so "we'll scale out"
> and "we'll fail over" are both plans that need the thing that's broken.** ⭐ The answer is static
> stability: run N+1 across AZs, keep standbys warm, pre-provision for the failure rather than
> reacting to it. ⭐ And never call the cloud API from a health check.

**3. "Where does the shared responsibility line actually sit for a Python web app?"**
> ⭐ They own the hypervisor, the physical network, disk durability and running the managed services.
> ⭐⭐ **I own every IAM policy, every security group, whether the bucket is public, my base image's
> CVEs, my dependencies, my schema and my data's correctness.** ⭐ The formulation I use is: durability
> is theirs, availability is shared, ⭐⭐ **correctness is entirely mine — S3's eleven nines protect
> against a disk dying, not against my code deleting the object**, which is exactly why backups,
> versioning and a copy in a separate account still exist.

**4. "When would you not use a managed service?"**
> ⭐ When one of three questions has a bad answer. ⭐⭐ **What happens at the limit** — every managed
> service has quotas, and finding them in production is expensive. ⭐⭐ **What does the exit look like**
> — not whether we'd leave, but the shape of the work if we had to; SQS is a week, a DynamoDB
> single-table design is a rewrite. ⭐⭐ **And what failure mode can I no longer fix myself** — with RDS
> I can't strace the process, so my only move is a support ticket, and that has to be acceptable in my
> RTO. ⭐ If all three are fine, take the managed service; the operations you're buying are real.

**5. "Is multi-region worth it?"**
> ⭐ Usually not, and I'd want to hear which of three drivers applies: a regulatory data-residency
> requirement, a latency requirement on another continent, or an RTO that must survive a full regional
> outage. ⭐⭐ **If none of those is nameable, we're buying 3–10× the cost and complexity for a risk
> that multi-AZ already covers.** ⭐ And multi-region isn't a switch — it forces asynchronous
> replication, which means accepting data loss on failover, ⭐⭐ **so it changes the product's
> consistency guarantees, not just its topology.**

**6. "What's the first thing you do in a new AWS account?"**
> ⭐ A budget alarm. ⭐ Then MFA on root and stop using root, separate accounts per environment under
> Organizations, CloudTrail into an account nobody deploys to, ⭐⭐ **and a tagging convention from the
> very first resource, because retrofitting tags is a project and without them cost attribution is
> impossible.**

## 🎙️ Articulation drill

**Two minutes.** Open with the reframe: **the cloud isn't someone else's computer, it's someone else's
API — infrastructure became software, which is why it gets versioned and reviewed, and also why it can
now fail the way software fails.** Then the idea that carries the stage: **there are two planes.** The
control plane creates and changes things; the data plane serves traffic; **they fail independently and
the control plane fails more often** — so during a large regional event your running instances usually
keep serving while nothing new can launch, **which means "we'll scale out" and "we'll fail over" are
both plans that depend on the broken thing.** The answer is static stability: N+1 across AZs,
standbys warm, **pre-provision for the failure instead of reacting to it**, and never put an AWS API
call in a health check. Then give the geography with numbers: **cross-AZ is under a millisecond so
synchronous replication is free; cross-region is 60–100 ms, so replication there is asynchronous and
your RPO stops being zero** — which is why multi-AZ is the default and multi-region needs a named
driver. Close on responsibility, sharply: **durability is theirs, availability is shared, correctness
is entirely mine — eleven nines protect the bytes from a dying disk, not from my code deleting them.**
