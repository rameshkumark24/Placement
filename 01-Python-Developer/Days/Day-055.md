# Day 055

**L-055** · ⭐ Composition over inheritance · mixins · when multiple inheritance is defensible

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: inheritance says "I am a kind of that". Composition says "I use one of
> those". Most code that inherits actually only wanted the second one.**
>
> ⭐ This is a design day, and it is the one that shows up in LLD rounds (Stage 8) more than any
> other Stage 1 topic. **"Would you use inheritance here?" is a question you should be able to answer
> with a reason, not a preference.**

# Part 1 — ⭐⭐ Why inheritance gets over-used

```
⭐⭐ IT LOOKS LIKE THE CHEAPEST WAY TO REUSE CODE — one word, and you have all the methods.
⭐   ⇒ ⚠️ ⭐⭐ but it is the TIGHTEST COUPLING the language offers:
⭐        · the subclass depends on the base's INTERNALS, not just its public interface
⭐        · ⭐ it is decided at CLASS-DEFINITION time and cannot vary at runtime
⭐        · ⭐⭐ it is TRANSITIVE — you inherit everything, including what you did not want
⭐        · you get ONE parent chain, forever
```

```python
# ⚠️ ⭐⭐ THE FRAGILE BASE CLASS — the canonical demonstration:
class Counter(dict):
    def __setitem__(self, k, v):
        print("set", k)
        super().__setitem__(k, v)

c = Counter()
c["a"] = 1        # ⭐ "set a"
c.update({"b": 2})    # ⭐⭐ NOTHING PRINTS — dict.update does not go through __setitem__
```

⭐⭐ **You inherited the *implementation*, and the implementation has internal paths you cannot see.**
⭐ The composition version cannot have this bug:

```python
class Counter:
    def __init__(self): self._d = {}
    def __setitem__(self, k, v):
        print("set", k)
        self._d[k] = v
    def update(self, other):
        for k, v in other.items(): self[k] = v     # ⭐⭐ YOU control every path in
    def __getitem__(self, k): return self._d[k]
```

⭐ **This is why `collections.UserDict` exists** (Day 038) — it wraps a real dict and routes every
operation through your overrides. **Inherit from `UserDict`, not from `dict`.**

# Part 2 — ⭐⭐ The test

```
⭐⭐ THREE QUESTIONS, IN ORDER:

⭐ 1. ⭐⭐ IS-A or HAS-A?
⭐      "a SavingsAccount IS-A Account"        ⇒ inheritance is plausible
⭐      "an Order HAS-A discount policy"       ⇒ ⭐⭐ composition
⭐      "a Service HAS-A logger"               ⇒ composition (⚠️ and yet people write LoggerMixin)
⭐
⭐ 2. ⭐⭐ LISKOV: anywhere the base works, does the subclass work?
⭐      an override that narrows its input, widens its exceptions, or does nothing
⭐      ⇒ ⭐⭐ NOT A SUBTYPE. The inheritance is lying and callers will be surprised.
⭐
⭐ 3. ⭐ CAN IT CHANGE AT RUNTIME, or vary per instance?
⭐      ⇒ ⭐⭐ inheritance CANNOT. Composition can — you just pass a different object.
```

```python
# ⚠️ ⭐⭐ THE COMBINATORIAL EXPLOSION — the strongest single argument:
class Report: ...
class PdfReport(Report): ...
class CsvReport(Report): ...
class EmailedPdfReport(PdfReport): ...
class EmailedCsvReport(CsvReport): ...
class ScheduledEmailedPdfReport(EmailedPdfReport): ...
# ⭐⭐ 3 formats × 2 deliveries × 2 schedules = 12 CLASSES. Add one format ⇒ 4 more.
```

```python
# ⭐⭐ COMPOSITION — three small objects, and every combination is free:
@dataclass
class Report:
    formatter: Formatter          # ⭐ Pdf / Csv / Json
    delivery: Delivery            # ⭐ Email / S3 / Download
    schedule: Schedule | None = None
    def run(self, data):
        self.delivery.send(self.formatter.render(data))
# ⭐⭐ 3 + 3 + 2 = 8 small classes ⇒ 18 combinations, none of them written.
# ⇒ ⭐ and a new format is ONE class, testable on its own.
```

⭐⭐ **"n × m classes becomes n + m classes" is the sentence to have ready in an LLD round.** **This is
also exactly the Strategy pattern**, and it is the single most useful design pattern in a Python
codebase — because in Python a strategy can be a plain function, not a class.

# Part 3 — ⭐ Composition in practice

```python
# ⭐ 1. DELEGATION — hold the object, forward what you need
class Order:
    def __init__(self, repo, pricer, notifier):
        self._repo, self._pricer, self._notifier = repo, pricer, notifier
    def place(self):
        total = self._pricer.total(self.items)      # ⭐ delegate
        self._repo.save(self); self._notifier.sent(self)

# ⭐⭐ 2. DEPENDENCY INJECTION — pass collaborators in, do not construct them
class Service:
    def __init__(self, db):        # ⭐⭐ testable: pass a fake
        self.db = db
# ⚠️ vs  self.db = Database()      # ⭐⭐ untestable: hardcoded, needs a real DB in every test

# ⭐ 3. STRATEGY AS A FUNCTION — Python does not need a class for this
def apply_discount(order, policy=lambda o: 0):
    return order.total - policy(order)

# ⭐ 4. __getattr__ FORWARDING — for a wrapper with a wide surface (Day 032)
class Proxy:
    def __init__(self, inner): self._inner = inner
    def __getattr__(self, name): return getattr(self._inner, name)
```

⭐⭐ **Dependency injection is the practical payoff and it is worth naming as such:** the reason to
compose is not tidiness, it is that **the collaborators become substitutable, so the class is testable
without a database, a network, or a clock.** ⭐ Stage 4's FastAPI `Depends` is this idea with framework
support, and Stage 8 will assume it.

⚠️ ⭐ **Composition's costs, stated honestly:** more classes, more indirection, and boilerplate
forwarding methods. **A three-line subclass is sometimes genuinely the right answer** — the argument
is against inheritance as a *default*, not against it entirely.

# Part 4 — ⭐⭐ Mixins, and when multiple inheritance is defensible

```
⭐⭐ A GOOD MIXIN — all four, or it is not a mixin:
⭐   1. ⭐ ONE concern (serialisation, comparison, timestamps)
⭐   2. ⭐⭐ NO STATE of its own, or state named to avoid collision (Day 053's __x)
⭐   3. ⭐⭐ NO __init__ — or a cooperative one that forwards **kwargs (Day 054)
⭐   4. ⭐ depends only on a DOCUMENTED interface of the class it is mixed into
```

```python
# ⭐ A defensible mixin:
class ComparableByKey:
    def _key(self): raise NotImplementedError      # ⭐⭐ the documented requirement
    def __eq__(self, o): return self._key() == o._key()
    def __lt__(self, o): return self._key() < o._key()

class Version(ComparableByKey):
    def _key(self): return self.parts
```

```
⭐⭐ WHEN MULTIPLE INHERITANCE IS DEFENSIBLE — the short list:
⭐   ✓ ⭐ ABCs / Protocols declaring an interface (Day 056) — no implementation to conflict
⭐   ✓ ⭐⭐ small stateless mixins, at most two or three
⭐   ✓ a framework that documents it (Django's class-based views)
⭐   ✗ ⭐⭐ two bases that both have real state and real __init__ ⇒ ⭐⭐ that is where the
⭐        silent-truncation bug of Day 054 lives
```

⚠️ ⭐⭐ **Django's class-based views are the honest cautionary tale.** They are a real, working,
widely-used design — and `ListView` has around eight ancestors, so **answering "where does
`get_queryset` come from?" requires reading the MRO.** That cost is why the community built
`django-vanilla-views` and why function-based views never died. **Cite it as evidence, not as
mockery: it works, and the readability price is real.**

⭐ **Inheritance depth as a metric:** more than **two or three** levels of your own classes is a smell.
**Each level is another place a reader must look to answer "what does this method do?"**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Inheriting for code reuse** | ⭐⭐ Composition. Inheritance is for is-a. |
| ⭐ Subclassing `dict`/`list` for invariants | ⭐⭐ Internal paths bypass you. `UserDict`, or wrap. |
| ⭐⭐ **A class per feature combination** | ⭐⭐ n×m classes. Compose: n+m. |
| Overriding a method to do nothing | ⭐ LSP violation — not a subtype. |
| Constructing collaborators inside `__init__` | ⭐⭐ Untestable. Inject them. |
| `LoggerMixin` for a logger | ⭐ That is has-a. Hold a logger. |
| A mixin with its own `__init__` and state | ⭐⭐ Day 054's truncation bug waits there. |
| Four or more levels of your own classes | ⭐ Each level is another place to look. |
| Assuming composition is free | ⭐ More classes, more forwarding. Sometimes a subclass wins. |
| Writing a Strategy class where a function fits | ⭐ In Python the strategy can be a function. |

## Interview questions

**Q: Composition or inheritance?**
> Composition by default; inheritance when the relationship is genuinely is-a and satisfies
> substitutability. The reason isn't taste — inheritance is the tightest coupling available, because
> the subclass depends on the base's internals rather than its interface, it's fixed at class
> definition so it can't vary per instance, and it's transitive so you get everything including what
> you didn't want. Composition gives me one clear seam per collaborator, which is also the seam I test
> through.

**Q: Give me a concrete case where inheritance goes wrong.**
> Subclassing `dict` to add a validating `__setitem__`. It works for `d[k] = v` and silently doesn't
> for `update()`, because `dict.update` is implemented in C and doesn't route through `__setitem__`. So
> the invariant holds on one path and not another, which is the fragile base class problem in
> miniature: I inherited an implementation with internal paths I can't see. Wrapping a dict — or using
> `collections.UserDict`, which exists for exactly this — means every path goes through my code.

**Q: What's the strongest argument for composition?**
> Combinatorial explosion. Three report formats, two delivery methods and two schedules is twelve
> classes as a hierarchy, and adding one format adds four more. As composition it's three formatters,
> three deliveries and two schedules — eight small classes covering eighteen combinations, none of
> which anyone wrote. The general form is that n×m classes becomes n+m, each testable on its own.
> That's the Strategy pattern, and in Python a strategy can be a plain function rather than a class.

**Q: What makes a good mixin?**
> One concern, no state of its own, no `__init__` — or a cooperative one that forwards `**kwargs` —
> and a dependency only on a documented interface of whatever it's mixed into. A comparison mixin that
> requires the class to provide a `_key` method is fine. A mixin with its own state and its own
> `__init__` is where Day 054's silent truncation bug lives: if any class in the chain forgets its
> `super()` call, the mixins after it never initialise and nothing raises.

**Q: When is multiple inheritance defensible?**
> ABCs and Protocols declaring an interface, since there's no implementation to conflict; two or three
> small stateless mixins; and frameworks that document the pattern. Django's class-based views are the
> honest example — they work and are widely used, and `ListView` has around eight ancestors, so
> answering "where does `get_queryset` come from" means reading the MRO. That readability cost is real
> enough that the community built simpler alternatives. I'd cite it as evidence rather than as a
> criticism: it's a legitimate design with a price.

**Q: Is composition ever the wrong choice?**
> Yes — it costs more classes, more indirection, and forwarding methods that do nothing but delegate.
> If a subclass genuinely is a specialisation and it's three lines, inheritance is clearer. The
> argument is against inheritance as the *default*, not against inheritance.

## 🎙️ Articulation drill

Record two minutes: **"You have twelve report classes. Refactor them."**

⭐ Diagnose before designing: **twelve classes is three formats times two deliveries times two
schedules — the hierarchy is encoding a cross-product, and adding one format adds four classes.** That
is the tell.

⭐ Then the redesign: **one `Report` holding a formatter, a delivery and an optional schedule.** Three
plus three plus two is eight small classes, covering eighteen combinations that nobody has to write,
and each piece is testable alone. **n × m becomes n + m.**

⭐⭐ **Then the second benefit, which is the one that matters in practice:** *"it also gives me the
seam I test through. Composition means the collaborators are passed in, so I can substitute a fake
formatter or a fake delivery and test the orchestration without a network or a filesystem. That's the
real reason to prefer it — inheritance gives me reuse, composition gives me substitutability, and
substitutability is what makes code testable."*

⭐ Concede the limit: **if a subclass genuinely is a specialisation and it is three lines, inherit** —
the argument is against inheritance as the default, not against inheritance.
