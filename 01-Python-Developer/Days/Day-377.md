# Part 1 — ⭐⭐ The one idea

```
⭐⭐ ***YOU DO NOT TELL KUBERNETES WHAT TO DO. YOU TELL IT WHAT
⭐   YOU WANT, AND A CONTROLLER LOOPS FOREVER TRYING TO MAKE IT
⭐   TRUE.***

⭐⭐ THE LOOP, WHICH IS THE ENTIRE SYSTEM:
⭐   ⭐ ① OBSERVE actual state. ⭐ ② COMPARE to desired.
⭐   ⭐ ③ ACT to reduce the difference. ⭐ ④ REPEAT, FOREVER.

⭐⭐ FIVE CONSEQUENCES, AND THEY EXPLAIN ALMOST EVERY
⭐   KUBERNETES BEHAVIOUR THAT CONFUSES PEOPLE:
⭐   ① ⭐⭐ `kubectl apply` RETURNS IMMEDIATELY AND ***NOTHING
⭐      HAS HAPPENED YET.*** ⭐ You wrote a record; a controller
⭐      will notice. ⭐⭐ HENCE `kubectl rollout status` — WITHOUT
⭐      IT YOUR PIPELINE GOES GREEN BEFORE THE DEPLOY EXISTS
⭐      (Day 370).
⭐   ② ⭐⭐ IT IS SELF-HEALING BY CONSTRUCTION. ⭐ Delete a pod
⭐      and one reappears — ⭐ not because deletion is blocked,
⭐      but because a controller noticed a difference.
⭐   ③ ⭐⭐ IT IS ***EVENTUALLY*** CONSISTENT. ⭐ There is no
⭐      moment of "done"; there is only convergence, ⭐ which
⭐      may take seconds or may never complete.
⭐   ④ ⭐⭐ MANUAL CHANGES ARE UNDONE. ⭐ `kubectl scale` then a
⭐      pipeline `apply` and you are back where you started —
⭐      ⭐⭐ WHICH IS WHY GITOPS EXISTS AND WHY "IT KEEPS
⭐      REVERTING MY CHANGE" IS THE SYSTEM WORKING.
⭐   ⑤ ⭐ Failure is a ***state***, not an exception. ⭐ A pod
⭐      that cannot schedule sits `Pending` forever, ⭐⭐ AND
⭐      NOTHING WILL EVER TELL YOU UNLESS YOU LOOK OR ALERT.

⭐⭐ AND THE ARCHITECTURAL SHAPE, MINIMALLY:
⭐   ⭐ ***API SERVER*** — the only thing that talks to `etcd`;
⭐     everything else talks to it.
⭐   ⭐ ***etcd*** — the store. ⭐⭐ RAFT (Day 343) — SO EVERY
⭐     DEPLOY YOU HAVE EVER DONE WENT THROUGH A CONSENSUS
⭐     PROTOCOL.
⭐   ⭐ ***SCHEDULER*** — assigns pods to nodes.
⭐   ⭐ ***CONTROLLER MANAGER*** — the loops.
⭐   ⭐ ***KUBELET*** — on each node, makes reality match what
⭐     was assigned.
⭐   ⇒ ⭐⭐ AND THE PROPERTY WORTH SAYING: THE CONTROL PLANE CAN
⭐     BE ***COMPLETELY DOWN*** AND RUNNING PODS KEEP SERVING.
⭐     ⭐ You lose the ability to ***change*** things, not to
⭐     ***run*** them — ⭐ which is Day 339's static stability,
⭐     built in.
```

# Part 2 — ⭐⭐ The four objects

```
⭐⭐ ① ***POD*** — one or more containers sharing a network
⭐   namespace and volumes.
⭐   ⭐ ⭐⭐ CONTAINERS IN A POD REACH EACH OTHER ON `localhost`
⭐     (Day 361) — that is what makes sidecars work.
⭐   ⭐ ⭐⭐ THE UNIT OF SCHEDULING AND THE UNIT OF FAILURE.
⭐   ⇒ ⭐⭐ AND YOU NEVER CREATE ONE DIRECTLY: A BARE POD IS NOT
⭐     RESCHEDULED IF ITS NODE DIES. ⭐ It is what a controller
⭐     creates on your behalf.

⭐⭐ ② ***DEPLOYMENT*** — desired state for a stateless
⭐   application.
⭐   ⭐ It manages ***ReplicaSets***; ⭐ each ReplicaSet manages
⭐     Pods. ⭐⭐ THE INDIRECTION EXISTS SO A ROLLOUT CAN RUN TWO
⭐     REPLICASETS AT ONCE AND SO ROLLBACK IS "SCALE THE OLD ONE
⭐     BACK UP" — ⭐ which is why `kubectl rollout undo` is fast.
⭐   ⭐ Owns replicas, the pod template, and the update strategy
⭐     (Day 371).

⭐⭐ ③ ***SERVICE*** — a stable name and virtual IP in front of
⭐   a changing set of pods.
⭐   ⭐ ⭐⭐ IT SELECTS PODS BY ***LABEL***, AND ONLY ***READY***
⭐     PODS ARE INCLUDED. ⭐ That is the mechanism behind
⭐     Day 371's rolling safety.
⭐   ⭐ `ClusterIP` (internal), `NodePort`, `LoadBalancer`,
⭐     ⭐ `ExternalName`.
⭐   ⇒ ⭐⭐ AND THE TWO THINGS THAT SURPRISE PEOPLE: THE VIRTUAL
⭐     IP IS IMPLEMENTED BY iptables/IPVS RULES ON EVERY NODE
⭐     (there is no proxy process in the path), ⭐⭐ AND
⭐     LOAD-BALANCING IS ***PER CONNECTION***, SO A LONG-LIVED
⭐     HTTP/2 OR gRPC CONNECTION PINS TO ONE POD (Day 325).

⭐⭐ ④ ***CONFIGMAP / SECRET*** — configuration and credentials,
⭐   injected as env or files (Days 364, 372).
⭐   ⭐ ⭐⭐ AND THE BEHAVIOUR PEOPLE ASSUME WRONGLY: EDITING A
⭐     CONFIGMAP DOES ***NOT*** RESTART PODS. ⭐ Mounted files
⭐     update eventually; ⭐⭐ ENVIRONMENT VARIABLES ***NEVER***
⭐     UPDATE. ⭐ Roll the deployment, ⭐ or hash the config into
⭐     an annotation so a change forces a rollout — ⭐ which is
⭐     the standard trick.

⭐⭐ ⇒ THAT IS 90% OF WHAT MOST APPLICATIONS NEED. ⭐ Ingress,
⭐   Job, CronJob, StatefulSet and HPA cover most of the rest —
⭐   ⭐⭐ AND THE HONEST NOTE: ***IF YOU FIND YOURSELF NEEDING
⭐   MORE THAN A DOZEN OBJECT KINDS, ASK WHETHER THE COMPLEXITY
⭐   IS COMING FROM YOUR PROBLEM OR FROM YOUR PLATFORM.***
```

# Part 3 — ⭐⭐ A Deployment worth copying

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api }
spec:
  replicas: 3
  strategy:
    rollingUpdate: { maxUnavailable: 0, maxSurge: 1 }   # ⭐⭐ Day 371
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api, version: "1.4.2" }            # ⭐ for metrics
      annotations:
        checksum/config: "{{ sha256 .Values.config }}"  # ⭐⭐ FORCES ROLL
    spec:
      terminationGracePeriodSeconds: 45                 # ⭐⭐ > DRAIN+p99
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001                                # ⭐ numeric (361)
        fsGroup: 10001                                  # ⭐ volume perms
      containers:
        - name: api
          image: ghcr.io/org/api@sha256:abc...          # ⭐⭐ DIGEST (362)
          ports: [{ containerPort: 8000 }]
          env:
            - name: WEB_CONCURRENCY                     # ⭐⭐ Day 361
              value: "2"
          envFrom:
            - secretRef: { name: api-secrets }
          resources:
            requests: { cpu: "250m", memory: "256Mi" }  # ⭐ scheduling
            limits:   {              memory: "512Mi" }  # ⭐⭐ NO CPU LIMIT
          startupProbe:                                 # ⭐⭐ SLOW BOOT
            httpGet: { path: /livez, port: 8000 }
            failureThreshold: 30
            periodSeconds: 2
          readinessProbe:                               # ⭐ traffic gate
            httpGet: { path: /readyz, port: 8000 }
            periodSeconds: 5
          livenessProbe:                                # ⭐⭐ NO DEPS
            httpGet: { path: /livez, port: 8000 }
            periodSeconds: 10
            failureThreshold: 3
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true                # ⭐ Day 361
            capabilities: { drop: ["ALL"] }
          volumeMounts:
            - { name: tmp, mountPath: /tmp }
      volumes:
        - name: tmp
          emptyDir: {}                                  # ⭐ scratch space
```

```
⭐⭐ THE SIX DECISIONS THAT MATTER:
⭐   ① ⭐⭐ IMAGE BY DIGEST — ⭐ so `IfNotPresent` cannot serve a
⭐      different build under the same tag (Day 362).
⭐   ② ⭐⭐ `maxUnavailable: 0` — never below full capacity.
⭐   ③ ⭐⭐ THE CONFIG CHECKSUM ANNOTATION — ⭐ the standard way
⭐      to make a ConfigMap change actually roll the pods.
⭐   ④ ⭐⭐ MEMORY LIMIT BUT ***NO CPU LIMIT*** (Day 361) —
⭐      ⭐ requests guarantee the floor; a CPU limit adds
⭐      throttling that usually costs more latency than it
⭐      protects. ⭐⭐ MEMORY IS NOT COMPRESSIBLE, SO ITS LIMIT
⭐      IS REQUIRED.
⭐   ⑤ ⭐⭐ THREE DISTINCT PROBES: startup for slow boot,
⭐      readiness for traffic, liveness with ***no
⭐      dependencies*** (Day 325).
⭐   ⑥ ⭐ Grace period exceeding drain + p99 + cleanup (Day 366).
```

# Part 4 — ⭐⭐ Probes, precisely

```
⭐⭐ THREE PROBES, THREE QUESTIONS, AND CONFUSING THEM CAUSES
⭐   OUTAGES:
⭐   ⭐ ***STARTUP*** — "has it finished booting?" ⇒ ⭐⭐ WHILE IT
⭐     RUNS, THE OTHER TWO ARE DISABLED. ⭐ This is how a
⭐     30-second Python import time (Day 366) avoids being
⭐     mistaken for a failure and restarted forever.
⭐   ⭐ ***READINESS*** — "should traffic come here now?" ⇒
⭐     ⭐⭐ FAILING REMOVES THE POD FROM THE SERVICE. ⭐ It does
⭐     ***not*** restart anything, which is exactly why
⭐     dependency checks belong here.
⭐   ⭐ ***LIVENESS*** — "is this process wedged?" ⇒ ⭐⭐ FAILING
⭐     ***RESTARTS THE CONTAINER***.

⭐⭐ THE RULE THAT PREVENTS THE CLASSIC OUTAGE:
⭐   ***A LIVENESS PROBE MUST NEVER CHECK A DEPENDENCY.***
⭐   ⇒ ⭐ A 30-second database blip restarts ***every pod
⭐     simultaneously***, ⭐⭐ GIVING YOU A COLD CACHE, A
⭐     RECONNECTION STAMPEDE, AND A TWENTY-MINUTE OUTAGE GROWN
⭐     FROM A THIRTY-SECOND ONE — ⭐ and the post-mortem blames
⭐     the database.

⭐⭐ AND THE FOUR SUBTLETIES:
⭐   ① ⭐⭐ THE PROBE IS EXECUTED BY THE ***KUBELET***, NOT
⭐      THROUGH THE SERVICE. ⭐ So it bypasses your ingress and
⭐      your auth — ⭐ which is why probe endpoints must be
⭐      cheap and must not require credentials.
⭐   ② ⭐⭐ A PROBE THAT QUEUES BEHIND USER TRAFFIC REPORTS
⭐      "DEAD" WHEN THE POD IS MERELY BUSY (Day 325's death
⭐      spiral). ⭐ In a saturated gunicorn pool, `/livez` waits
⭐      in the same queue as everything else.
⭐   ③ ⭐ `failureThreshold` × `periodSeconds` is your actual
⭐      detection time. ⭐⭐ 3 × 10 s MEANS UP TO THIRTY SECONDS
⭐      OF TRAFFIC TO A DEAD POD BEFORE READINESS NOTICES.
⭐   ④ ⭐⭐ READINESS MUST FAIL ***IMMEDIATELY*** ON SIGTERM AND
⭐      LIVENESS MUST NOT (Day 324) — ⭐ and then sleep ~5 s so
⭐      the endpoints actually propagate, ⭐⭐ BECAUSE ENDPOINT
⭐      UPDATES ARE EVENTUALLY CONSISTENT ACROSS EVERY NODE'S
⭐      iptables RULES, AND THAT PROPAGATION IS WHERE DEPLOY-TIME
⭐      502s COME FROM.
```

# Part 5 — ⭐ Networking and Services

```
⭐⭐ THE FLAT NETWORK MODEL: ⭐ every pod gets an IP, ⭐ and every
⭐   pod can reach every other pod ***without NAT***.
⭐   ⇒ ⭐⭐ WHICH MEANS ***THERE IS NO NETWORK ISOLATION BY
⭐     DEFAULT.*** ⭐ Any pod can reach your database pod.
⭐   ⇒ ⭐ `NetworkPolicy` is opt-in, ⭐⭐ AND IT REQUIRES A CNI
⭐     THAT IMPLEMENTS IT — ⭐ applying one with a CNI that
⭐     ignores it gives you a policy that silently does nothing,
⭐     which is worse than none.

⭐⭐ DNS:
⭐   ⭐ `svc-name.namespace.svc.cluster.local`, ⭐ shortened to
⭐     `svc-name` within a namespace.
⭐   ⭐ ⭐⭐ AND THE `ndots:5` TRAP (Day 364): AN EXTERNAL
⭐     LOOKUP LIKE `api.stripe.com` IS TRIED WITH ***FIVE SEARCH
⭐     SUFFIXES FIRST***, so every external call costs several
⭐     failed DNS queries. ⭐ A trailing dot or a custom
⭐     `dnsConfig` fixes it, ⭐⭐ AND IT IS A REAL, COMMONLY-MISSED
⭐     LATENCY SOURCE.

⭐⭐ THE TWO SERVICE BEHAVIOURS TO KNOW:
⭐   ⭐ ⭐⭐ PER-CONNECTION LOAD BALANCING ⇒ ⭐ HTTP/1 with
⭐     keepalive and gRPC both pin to one pod. ⭐ For gRPC you
⭐     need client-side balancing or a mesh (Day 341).
⭐   ⭐ ***HEADLESS SERVICES*** (`clusterIP: None`) return pod
⭐     IPs directly ⇒ ⭐⭐ WHICH IS HOW CLIENTS THAT DO THEIR OWN
⭐     BALANCING, AND STATEFULSETS, WORK.

⭐⭐ AND `INGRESS`: ⭐ HTTP routing into the cluster, implemented
⭐   by a controller (nginx-ingress, Traefik) that is itself a
⭐   pod. ⭐⭐ EVERY DAY-367 CONCERN — BUFFERING, TIMEOUTS,
⭐   FORWARDED HEADERS, BODY LIMITS — APPLIES, AND IS CONFIGURED
⭐   THROUGH ANNOTATIONS THAT DIFFER PER CONTROLLER.
```

# Part 6 — ⭐⭐ Debugging when something will not start

```
⭐⭐ THE SEQUENCE, AND IT ALMOST ALWAYS ENDS AT STEP 2:
⭐   ① ⭐ `kubectl get pods` ⇒ the status column.
⭐   ② ⭐⭐ `kubectl describe pod X` ⇒ ***READ THE EVENTS AT THE
⭐      BOTTOM.*** ⭐ Ninety percent of answers are there and
⭐      most people never scroll down.
⭐   ③ ⭐ `kubectl logs X --previous` ⇒ ⭐⭐ THE `--previous` FLAG
⭐      IS THE POINT: IT SHOWS THE ***CRASHED*** CONTAINER'S
⭐      OUTPUT, WHICH IS THE ONE YOU WANT.
⭐   ④ ⭐ `kubectl exec -it X -- sh`, ⭐ or `kubectl debug` for a
⭐      distroless image (Day 363).
⭐   ⑤ ⭐ `kubectl get events --sort-by=.lastTimestamp`.

⭐⭐ THE STATUSES, DECODED:
⭐   ⭐ ⭐⭐ `Pending` ⇒ NOT SCHEDULED. ⭐ Insufficient CPU or
⭐     memory on any node, ⭐ an unsatisfiable node selector or
⭐     taint, ⭐ or an unbound PVC. ⭐⭐ `describe` SAYS EXACTLY
⭐     WHICH.
⭐   ⭐ `ImagePullBackOff` ⇒ wrong name, ⭐ wrong registry, ⭐ or
⭐     a missing `imagePullSecret`.
⭐   ⭐ ⭐⭐ `CrashLoopBackOff` ⇒ THE CONTAINER KEEPS EXITING.
⭐     ⭐ Check exit code: ⭐⭐ 137 = OOMKILLED (Day 361); ⭐ 1 =
⭐     your application; ⭐ 143 = SIGTERM handled.
⭐     ⇒ ⭐⭐ AND THE BACKOFF IS EXPONENTIAL TO FIVE MINUTES,
⭐       SO A FIX CAN APPEAR NOT TO WORK FOR MINUTES.
⭐   ⭐ ⭐⭐ `Running` BUT `0/1 READY` ⇒ THE READINESS PROBE IS
⭐     FAILING. ⭐ The app is up and something it depends on is
⭐     not — ⭐ this is the status that most often means "the
⭐     probe is wrong" rather than "the app is broken".
⭐   ⭐ `Terminating` for a long time ⇒ ⭐⭐ THE PROCESS IS NOT
⭐     HANDLING SIGTERM (Day 361), OR A FINALIZER IS STUCK.

⭐⭐ AND THE FOUR THINGS WORTH CHECKING BEFORE ANYTHING ELSE:
⭐   ⭐ Did the image digest actually change?
⭐   ⭐ ⭐⭐ DOES THE SERVICE'S SELECTOR MATCH THE POD'S LABELS?
⭐     ⭐ A typo gives you a Service with zero endpoints and a
⭐     perfectly healthy pod nobody can reach.
⭐   ⭐ `kubectl get endpoints svc-name` ⇒ ⭐⭐ EMPTY MEANS NO
⭐     ***READY*** POD MATCHES.
⭐   ⭐ Is the ConfigMap or Secret it references actually
⭐     present in ***this namespace***?
```

# Part 7 — ⭐ When Kubernetes is the wrong answer

```
⭐⭐ WHAT IT GENUINELY GIVES YOU:
⭐   ⭐ Self-healing, ⭐ rolling deploys with health gating,
⭐   ⭐ service discovery, ⭐ autoscaling, ⭐ bin-packing across
⭐   nodes, ⭐ and ⭐⭐ A COMMON VOCABULARY THAT MEANS A NEW
⭐   ENGINEER ALREADY KNOWS HOW YOUR DEPLOYMENTS WORK.

⭐⭐ WHAT IT COSTS — ⭐ all five, honestly:
⭐   ① ⭐⭐ A CONTROL PLANE TO RUN OR PAY FOR, AND UPGRADE ON
⭐      SOMEONE ELSE'S SCHEDULE (roughly three releases a year,
⭐      with a deprecation window).
⭐   ② ⭐⭐ A LARGE CONCEPTUAL SURFACE. ⭐ Debugging now spans
⭐      your app, the CNI, the ingress controller, the CSI
⭐      driver and the scheduler.
⭐   ③ ⭐ YAML, and the templating layer you will add on top of
⭐      it, and the drift between them.
⭐   ④ ⭐⭐ A NEW CLASS OF FAILURE THAT IS NOT YOUR CODE — ⭐ and
⭐      often not your team's expertise either.
⭐   ⑤ ⭐ Cost: ⭐⭐ SMALL CLUSTERS ARE POOR VALUE. ⭐ Control
⭐      plane plus system pods plus reserved capacity is a real
⭐      floor before you run anything.

⭐⭐ THE THRESHOLD, STATED HONESTLY:
⭐   ⭐ ⭐⭐ ONE OR TWO SERVICES, ONE TEAM ⇒ ***ECS/FARGATE,
⭐     CLOUD RUN, APP RUNNER, OR A VM WITH SYSTEMD.*** ⭐ You get
⭐     rolling deploys and health checks without a cluster.
⭐   ⭐ ⭐⭐ MANY SERVICES, MULTIPLE TEAMS, A PLATFORM NEED, OR A
⭐     REQUIREMENT TO RUN THE SAME THING IN SEVERAL ENVIRONMENTS
⭐     ⇒ KUBERNETES EARNS ITS COST.
⭐   ⇒ ⭐⭐ AND THE HONEST MIDDLE: MANY TEAMS ADOPT IT FOR THE
⭐     ECOSYSTEM — CERT-MANAGER, EXTERNAL-DNS, ARGO, OPERATORS —
⭐     RATHER THAN FOR SCALE, ⭐ and that is a legitimate reason
⭐     as long as it is named as the reason.

⭐⭐ ⇒ THE INTERVIEW POSITION: ***"I CAN OPERATE IT, AND I WOULD
⭐   ASK WHETHER WE NEED IT."*** ⭐ Both halves. ⭐⭐ ENTHUSIASM
⭐   WITHOUT THE SECOND HALF READS AS INEXPERIENCE.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Expecting `kubectl apply` to mean "deployed" | It writes a record. Without `rollout status`, your pipeline goes green before anything happened |
| ⭐⭐ Liveness probes that check dependencies | A 30-second blip restarts every pod, turning a degradation into a twenty-minute outage |
| ⭐ No startup probe with slow Python imports | A slow boot is mistaken for a failure and restarted forever |
| ⭐ Readiness that doesn't fail on SIGTERM | Traffic keeps arriving during shutdown. And you still need the ~5 s propagation sleep |
| ⭐⭐ Deploying by tag | `IfNotPresent` can serve a different build under the same tag across nodes |
| ⭐⭐ CPU limits on latency-sensitive services | Throttling costs more than bursting protects. Requests guarantee the floor |
| ⭐ No memory limit | Memory isn't compressible; without a limit the node's OOM killer chooses for you |
| ⭐⭐ Expecting a ConfigMap edit to restart pods | Files update eventually; env vars never. Use a config checksum annotation |
| ⭐ Assuming network isolation | The pod network is flat by default. NetworkPolicy is opt-in and needs a CNI that implements it |
| ⭐⭐ Ignoring `ndots:5` | Every external DNS lookup costs several failed queries first |
| ⭐ Expecting Services to balance gRPC | Per-connection balancing pins long-lived connections to one pod |
| ⭐⭐ Not reading the events in `describe` | Ninety percent of "won't start" answers are there and nobody scrolls down |
| ⭐ `kubectl logs` without `--previous` on a crash loop | You're reading the container that hasn't failed yet |
| ⭐ Service selector that doesn't match pod labels | Zero endpoints and a perfectly healthy pod nobody can reach |
| ⭐⭐ Adopting Kubernetes for two services | Control plane, system pods and reserved capacity before you run anything |

## Interview questions

**1. "Explain Kubernetes in one idea."**
> ⭐⭐ **Declarative state plus reconciliation loops: you record what you want, and controllers loop
> forever making actual state match.** ⭐ Everything else follows — `apply` returns instantly because
> nothing has happened yet, it self-heals because a controller notices a difference, it's eventually
> consistent so there's no moment of "done", ⭐⭐ and **manual changes get undone, which is why "it keeps
> reverting my change" is the system working correctly.**

**2. "What are the three probes and how do they differ?"**
> ⭐ Startup asks "has it booted", and while it runs the other two are disabled — ⭐⭐ **which is how a
> thirty-second Python import time avoids being mistaken for a failure and restarted forever.**
> ⭐ Readiness asks "should traffic come here", and failing removes the pod from the Service without
> restarting it — so dependency checks belong there. ⭐ Liveness asks "is it wedged", and failing
> restarts. ⭐⭐ **Liveness must never check a dependency: a thirty-second database blip would restart
> every pod at once, giving you a cold cache and a reconnection stampede.**

**3. "Why do you get 502s during a deploy?"**
> ⭐⭐ Because **endpoint updates are eventually consistent across every node's iptables rules**, so
> after a pod stops accepting there's a window where traffic is still routed to it. ⭐ The fix is
> Day 324's sequence: fail readiness immediately on SIGTERM, sleep about five seconds so the removal
> propagates, then drain. ⭐ And the grace period must exceed that sleep plus your p99 plus cleanup, or
> you're SIGKILLed mid-request.

**4. "A pod is `Running` but `0/1 Ready`. What's happening?"**
> ⭐ The readiness probe is failing — the process is up and something it checks isn't. ⭐⭐ **It's the
> status that most often means the probe is wrong rather than the app being broken**: it checks a
> dependency that's briefly unavailable, or it queues behind user traffic in a saturated worker pool
> and reports dead when the pod is merely busy. ⭐ I'd check `kubectl describe` events first, then hit
> the probe endpoint directly from inside the pod.

**5. "What surprises people about Services?"**
> ⭐ Two things. ⭐⭐ **The virtual IP is iptables or IPVS rules on every node — there's no proxy process
> in the path** — which is why there's nothing to look at when it misbehaves. ⭐⭐ And **balancing is
> per-connection, so a long-lived HTTP/2 or gRPC connection pins to one pod**, which is the "why is one
> pod hot" problem and needs client-side balancing or a mesh. ⭐ Plus the flat network: any pod can
> reach any pod, so isolation is opt-in via NetworkPolicy, and only if your CNI implements it.

**6. "When would you not use Kubernetes?"**
> ⭐ One or two services with one team — ⭐⭐ **ECS, Fargate, Cloud Run or a VM with systemd gives you
> rolling deploys and health gating without a control plane to run, upgrade on someone else's schedule,
> and debug.** ⭐ Small clusters are poor value: control plane, system pods and reserved capacity are a
> real floor before you run anything. ⭐⭐ The honest middle is that **many teams adopt it for the
> ecosystem — cert-manager, external-dns, Argo — rather than for scale, and that's legitimate as long
> as it's named as the reason.** ⭐ My position is: I can operate it, and I'd ask whether we need it.

## Today's build

```
⭐ ① Deploy the flagship to kind or minikube with the Part 3
⭐    manifest. ⭐⭐ BY DIGEST, WITH ALL THREE PROBES.
⭐ ② ⭐⭐ DELETE A POD AND WATCH IT COME BACK. Then scale by
⭐    hand and re-`apply` to watch your change be undone.
⭐ ③ ⭐⭐ BREAK THE LIVENESS PROBE DELIBERATELY BY POINTING IT
⭐    AT A DEPENDENCY, THEN STOP THE DATABASE. Watch every pod
⭐    restart. That is the outage, in miniature.
⭐ ④ Remove `maxUnavailable: 0` and deploy under load.
⭐    ⭐⭐ MEASURE THE ERROR RATE DIFFERENCE.
⭐ ⑤ ⭐⭐ REPRODUCE THE DEPLOY-502: DEPLOY WITHOUT THE DRAIN
```

## 🎙️ Articulation drill

**Two minutes.** Give the one idea and let everything follow from it: **you declare desired state and
controllers loop forever making actual state match** — which is why `apply` returns instantly while
nothing has happened yet, why deleting a pod brings one back, why there's no moment of "done", and
**why manual changes get undone, which is the system working rather than failing.** Add the property
worth knowing: **the control plane can be entirely down and running pods keep serving — you lose the
ability to change things, not to run them.** Then the four objects — pod, deployment, service, config —
and the two behaviours that surprise people: **a Service's virtual IP is iptables rules on every node
with no proxy in the path, and balancing is per-connection, so gRPC pins to one pod.** Then probes,
precisely, because confusing them causes outages: **startup disables the others so a slow Python boot
isn't restarted forever; readiness removes you from the Service without restarting; liveness restarts —
and must never check a dependency, or a thirty-second database blip restarts every pod at once and
turns a degradation into a twenty-minute outage.** Give the deploy-502 explanation, because it's the
most useful thing here: **endpoint removal is eventually consistent across every node, so you fail
readiness, sleep five seconds, then drain.** Close on judgement: **I can operate it, and I'd ask whether
we need it** — one or two services should be Fargate or Cloud Run, and many teams adopt it for the
ecosystem rather than for scale, which is fine as long as that's named as the reason.
