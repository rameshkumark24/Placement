# Part 1 — ⭐ The session, and the id

```python
import secrets

def create_session(user_id: int) -> str:
    sid = secrets.token_urlsafe(32)                  # ⭐⭐ 256 bits from a CSPRNG
    redis.setex(f"sess:{sid}", ABSOLUTE_TIMEOUT,
                json.dumps({"user_id": user_id, "created": time.time()}))
    return sid
```

```
⭐⭐ WHY `secrets` AND NOT `random` — and this is a real, exploited bug class:
⭐   `random` is a MERSENNE TWISTER. It is fast, statistically excellent, and
⭐   ⭐⭐ COMPLETELY PREDICTABLE: observe 624 outputs and you can reconstruct the
⭐   internal state and predict every future value.
⭐   ⇒ ⭐⭐ SO A SESSION ID FROM `random` MEANS AN ATTACKER WHO COLLECTS ENOUGH
⭐        IDS — by registering accounts repeatedly — CAN PREDICT OTHER PEOPLE'S.
⭐   ⇒ ⭐ `secrets` uses the OS CSPRNG (`/dev/urandom`, Day 078). ⭐⭐ Use it for
⭐        session ids, tokens, reset links, API keys, CSRF tokens — anything an
⭐        adversary must not guess.
⭐   ⇒ ⭐ 32 bytes is far more than needed and costs nothing. Do not economise.
```

| ⭐ Store what where | |
|---|---|
| ⭐⭐ In the cookie | ⭐ **only the id.** Opaque, meaningless, unguessable |
| ⭐ In Redis/the DB | ⭐ user id, created-at, last-seen, IP, user agent, roles |
| ⚠️ Never in the session | ⭐⭐ large objects, or anything you would not re-fetch — **the session is a cache with a very confusing invalidation story** |

⭐⭐ **The single genuine advantage of server-side sessions over JWT (Day 116): logout works.**
⭐ `redis.delete(f"sess:{sid}")` and the credential is dead everywhere, immediately — **which is
exactly what a signed token cannot do.**

```
⭐ TWO TIMEOUTS, AND YOU WANT BOTH:
⭐   IDLE (sliding)    30 min of inactivity ⇒ expire. ⭐ Refresh the TTL on use.
⭐   ⭐⭐ ABSOLUTE      12-24 hours regardless of activity ⇒ ⭐ so a stolen
⭐                       session cannot be kept alive forever by the thief.
⭐   ⇒ ⭐ sliding-only is the common mistake: an attacker with a stolen id just
⭐        keeps using it and it never expires.
```

# Part 2 — ⭐⭐ Cookie attributes, and what each defends

```http
Set-Cookie: sid=xK3f...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

| ⭐ Attribute | ⭐⭐ What it stops |
|---|---|
| ⭐⭐ `HttpOnly` | ⭐⭐ **JavaScript cannot read it** ⇒ an XSS bug cannot exfiltrate the session |
| ⭐⭐ `Secure` | ⭐ never sent over plain HTTP ⇒ no network capture |
| ⭐⭐ `SameSite=Lax` | ⭐⭐ **not sent on cross-site POSTs** ⇒ most CSRF, gone |
| `SameSite=Strict` | ⭐ not sent on *any* cross-site request — ⚠️ breaks arriving from an email link |
| ⭐ `SameSite=None` | ⭐⭐ requires `Secure`; only for genuine cross-site use — ⚠️ **CSRF is fully back** |
| `Path=/` · `Domain` | ⭐ scope — ⚠️ ⭐⭐ setting `Domain=.example.com` shares the cookie with **every** subdomain |
| `Max-Age` / `Expires` | ⭐ persistent vs session cookie |
| ⭐ `__Host-` prefix | ⭐⭐ the browser **enforces** `Secure`, `Path=/` and no `Domain` |

```
⭐⭐ `HttpOnly` IS THE ONE THAT MATTERS MOST, AND THE REASONING IS WORTH SAYING:
⭐   it does not prevent XSS. ⭐⭐ IT LIMITS WHAT AN XSS BUG CAN DO. With it, a
⭐   successful XSS can act as the user in that page; without it, the attacker
⭐   takes the session id away and acts as the user FOREVER, FROM ANYWHERE.
⭐   ⇒ ⭐⭐ THAT IS THE ARGUMENT AGAINST STORING A TOKEN IN localStorage (Day 116)
⭐        IN ONE SENTENCE: localStorage is readable by any script on the page.
⭐
⭐ ⚠️ ⭐⭐ AND THE SUBDOMAIN TRAP: `Domain=.example.com` sends your session cookie
⭐    to blog.example.com, status.example.com, and whatever marketing spun up
⭐    last week on a shared host. ⭐ ONE compromised subdomain — or one that
⭐    simply logs request headers — ⭐⭐ AND EVERY SESSION IS EXPOSED. Scope
⭐    cookies as narrowly as they will go.
```

# Part 3 — ⭐⭐ Session fixation

```
⭐⭐ THE ATTACK, AND IT IS THE ONE PEOPLE MISS BECAUSE IT NEEDS NO THEFT:
⭐   1. the attacker obtains a valid session id — usually by just VISITING your
⭐      site and being issued one for their anonymous session.
⭐   2. ⭐ they get the victim to use THAT id: a link with `?sid=...` if you are
⭐      careless, a cookie set from a compromised subdomain (Part 2), or an XSS
⭐      on any page in scope.
⭐   3. ⭐⭐ THE VICTIM LOGS IN. Your server marks THAT SESSION as authenticated.
⭐   4. ⭐⭐ THE ATTACKER NOW HOLDS AN AUTHENTICATED SESSION ID — one they have
⭐      known all along. ⭐ They never stole anything.
⭐
⭐ ⇒ ⭐⭐ THE FIX IS ONE LINE, AND IT IS ROUTINELY OMITTED:
⭐     ISSUE A BRAND-NEW SESSION ID ON LOGIN, AND DELETE THE OLD ONE.
```

```python
def login(request, email, password):
    user = authenticate(email, password)              # ⭐ Day 114
    if user is None:
        raise HTTPError(401, "Invalid email or password")

    old_sid = request.cookies.get("sid")
    if old_sid:
        redis.delete(f"sess:{old_sid}")               # ⭐⭐ kill the pre-login session
    sid = create_session(user.id)                     # ⭐⭐ a NEW, unknown id

    response = JSONResponse({"ok": True})
    response.set_cookie("sid", sid, httponly=True, secure=True,
                        samesite="Lax", path="/", max_age=ABSOLUTE_TIMEOUT)
    return response
```

```
⭐⭐ AND ROTATE ON EVERY PRIVILEGE CHANGE, NOT JUST LOGIN:
⭐   · elevation to admin · a password change · enabling or disabling MFA
⭐   ⇒ ⭐⭐ A PASSWORD CHANGE SHOULD ALSO INVALIDATE EVERY OTHER SESSION FOR THAT
⭐        USER. ⭐ That is the whole point of "change your password" after a
⭐        compromise — ⭐⭐ if the attacker's session survives it, the advice you
⭐        gave the user was useless.
⭐   ⇒ ⭐ store sessions under a per-user set (`user:42:sessions`) so you can
⭐        enumerate and revoke them — and so you can offer "log out everywhere",
⭐        which users genuinely want.
```

# Part 4 — ⭐⭐ CSRF — the browser is the attacker

```
⭐⭐ THE ROOT CAUSE, AND IT IS NOT A BUG IN YOUR CODE: THE BROWSER ATTACHES
⭐   COOKIES FOR example.com TO *ANY* REQUEST TO example.com, NO MATTER WHICH
⭐   SITE CAUSED IT.
⭐
⭐   evil.com serves:
⭐       <form action="https://bank.com/transfer" method="POST">
⭐         <input name="to" value="attacker"><input name="amount" value="10000">
⭐       </form>
⭐       <script>document.forms[0].submit()</script>
⭐   ⇒ ⭐⭐ THE VICTIM'S BROWSER SENDS IT WITH THEIR bank.com SESSION COOKIE
⭐        ATTACHED. ⭐ Your server sees a perfectly authenticated request.
⭐   ⇒ ⭐⭐ NOTE WHAT THE ATTACKER CANNOT DO: READ THE RESPONSE (the same-origin
⭐        policy stops that, Day 020). ⭐ CSRF is a WRITE attack — it makes you
⭐        DO something, it does not let them SEE anything.
```

| ⭐ Defence | ⭐ How it works |
|---|---|
| ⭐⭐ **`SameSite=Lax`** | ⭐⭐ the browser refuses to attach the cookie to cross-site POSTs — **covers most of it, for free** |
| ⭐ Synchroniser token | ⭐ a random token in the session **and** in the form; compare on submit |
| ⭐ Double-submit cookie | ⭐⭐ token in a **JS-readable** cookie *and* in a header; compare — needs no server state |
| ⭐ Origin/Referer check | ⭐ reject when `Origin` is not yours — ⚠️ can be absent |
| ⭐⭐ Custom header (`X-Requested-With`) | ⭐⭐ a form **cannot** set headers; only JS can, and JS is bound by CORS |

```
⭐⭐ WHY SameSite IS NOT THE WHOLE ANSWER, EVEN THOUGH IT IS MOST OF IT:
⭐   · ⭐ `Lax` STILL SENDS THE COOKIE ON TOP-LEVEL GET NAVIGATION ⇒ ⭐⭐ any
⭐        state-changing GET endpoint is still exploitable. ⭐ Which is really an
⭐        argument for Day 102: GET must be SAFE. If `GET /delete?id=5` exists,
⭐        SameSite will not save you.
⭐   · ⭐ SUBDOMAINS ARE SAME-SITE ⇒ a compromised subdomain bypasses it entirely.
⭐   · ⭐ browser defaults vary, and older clients ignore it.
⭐   ⇒ ⭐⭐ SO: SameSite=Lax AS THE BASELINE, PLUS A TOKEN ON ANY GENUINELY
⭐        DANGEROUS ACTION. ⭐ Defence in depth, and the token is cheap.
```

```python
# ⭐⭐ THE DOUBLE-SUBMIT PATTERN — stateless, and the usual choice for an SPA:
csrf = secrets.token_urlsafe(32)
response.set_cookie("csrf", csrf, httponly=False,      # ⭐⭐ JS MUST read this one
                    secure=True, samesite="Lax")

# ⭐ the client echoes it back in a header on every unsafe request:
if request.method not in ("GET", "HEAD", "OPTIONS"):
    if not secrets.compare_digest(request.headers.get("x-csrf-token", ""),
                                  request.cookies.get("csrf", "")):   # ⭐ Day 114
        raise HTTPError(403, "CSRF token mismatch")
```

```
⭐⭐ WHY DOUBLE-SUBMIT WORKS: evil.com CAN cause the browser to SEND your
⭐   cookies, but it CANNOT READ THEM (same-origin policy) — ⭐⭐ so it cannot
⭐   produce the matching header. ⭐ The defence rests entirely on "can send" and
⭐   "can read" being different permissions, which is the same distinction that
⭐   makes CSRF a write-only attack in the first place.
⭐   ⇒ ⚠️ ⭐ IT DOES ASSUME NO XSS and no attacker-controlled subdomain writing
⭐        cookies for your domain. ⭐⭐ Under XSS, every CSRF defence fails —
⭐        which is why XSS is the more serious bug (Day 127).
```

# Part 5 — ⭐ Sessions vs tokens, decided

| | ⭐⭐ Server session | ⭐ JWT (Day 116) |
|---|---|---|
| ⭐⭐ Revocation | ⭐⭐ **instant — delete the row** | ⚠️ ⭐⭐ **impossible until expiry** |
| State | ⭐ a store, and it must be available | ⭐ none — until you add a denylist |
| Size on the wire | ⭐ ~40 bytes | ⭐ 300–800 bytes, **on every request** |
| Cross-domain | ⭐ awkward | ⭐ easy |
| ⭐ Read cost | ⭐ a Redis hit per request | ⭐ signature verification only |
| ⭐⭐ Logout everywhere | ⭐ trivial | ⭐⭐ needs the state you were avoiding |

```
⭐⭐ THE POSITION WORTH DEFENDING: FOR A NORMAL WEB APPLICATION WITH ONE
⭐   BACKEND, USE SERVER-SIDE SESSIONS.
⭐   ⇒ ⭐ Redis is one dependency you very likely already have, a lookup is
⭐        sub-millisecond, and ⭐⭐ REVOCATION ACTUALLY WORKS — which you will
⭐        need the first time an account is compromised or an employee leaves.
⭐   ⇒ ⭐⭐ "STATELESS" IS THE WRONG THING TO OPTIMISE FOR IN A SYSTEM THAT
⭐        ALREADY HAS A DATABASE ON EVERY REQUEST. ⭐ You are not avoiding state;
⭐        you are avoiding one cheap lookup and paying for it with revocation.
⭐   ⇒ ⭐ JWTs earn their place for service-to-service calls, short-lived
⭐        access tokens in front of a refresh token (Day 117), and genuinely
⭐        cross-domain or multi-party situations.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ `random` for a session id | ⭐⭐ Predictable — 624 outputs reveal the state. `secrets`. |
| Session data in the cookie | ⭐ Only the opaque id. |
| ⭐ Sliding timeout only | ⭐⭐ A stolen session never expires. Add an absolute one. |
| ⭐⭐ **No `HttpOnly`** | ⭐⭐ An XSS bug becomes permanent account takeover. |
| No `Secure` | ⭐ Sent in cleartext on any accidental HTTP request. |
| ⭐ `Domain=.example.com` | ⭐⭐ Every subdomain sees your session cookie. |
| ⭐⭐ **Not rotating the session id on login** | ⭐⭐ Session fixation — the attacker never has to steal anything. |
| Password change leaving other sessions alive | ⭐⭐ Then "change your password" was useless advice. |
| ⭐ Relying on `SameSite` alone | ⭐ Top-level GET still sends it; subdomains are same-site. |
| ⭐ A state-changing `GET` | ⭐⭐ Defeats `SameSite=Lax` entirely. GET must be safe. |
| ⭐ CSRF token compared with `==` | ⭐ `secrets.compare_digest`. |
| ⭐ `HttpOnly` on the CSRF cookie | ⭐ Double-submit needs JS to read it. |
| Choosing JWT to be "stateless" | ⭐⭐ You already hit a database. You traded away revocation. |

## Interview questions

**Q: How do you implement a session?**
> An unguessable random id from `secrets.token_urlsafe(32)` in a cookie, with the state in Redis under
> that key. The cookie gets `HttpOnly`, `Secure`, `SameSite=Lax` and the narrowest `Path` and `Domain`
> that work. Two timeouts — a sliding idle timeout and an absolute one, because sliding-only means a
> stolen session can be kept alive forever. And the id gets regenerated on login. `secrets` rather
> than `random` matters because `random` is a Mersenne Twister: observe enough outputs and you can
> predict all future ones, and an attacker can generate outputs by registering accounts.

**Q: What is session fixation?**
> The attacker gets a valid session id — usually just by visiting the site — then gets the victim to
> use that same id, through a URL parameter, a cookie set from a compromised subdomain, or XSS. The
> victim logs in, the server marks *that* session as authenticated, and the attacker is now holding an
> authenticated session they've known all along. They never stole anything. The fix is one line that's
> routinely missing: issue a brand-new session id on login and delete the old one. I'd rotate on any
> privilege change too, and a password change should invalidate every other session for that user —
> otherwise "change your password after a breach" is useless advice, because the attacker's session
> survives it.

**Q: What is CSRF, and why does it happen?**
> The browser attaches cookies for your domain to any request to your domain, regardless of which site
> caused it. So a form on evil.com posting to bank.com arrives with the victim's session cookie
> attached and looks perfectly authenticated. The important limit is that the attacker can't read the
> response — the same-origin policy stops that — so CSRF is a write attack: it makes you do something,
> it doesn't let them see anything.

**Q: How do you defend against it?**
> `SameSite=Lax` as the baseline, which stops the browser attaching the cookie to cross-site POSTs and
> covers most of it for free. But not all of it: `Lax` still sends the cookie on top-level GET
> navigation, so any state-changing GET endpoint remains exploitable — which is really an argument for
> keeping GET safe. And subdomains count as same-site, so a compromised subdomain bypasses it. So I'd
> add a token on genuinely dangerous actions: double-submit for an SPA, where a JS-readable cookie is
> echoed back in a header. That works because evil.com can cause your cookies to be *sent* but can't
> *read* them, so it can't produce the matching header. Under XSS every CSRF defence fails, which is
> why XSS is the more serious bug.

**Q: Sessions or JWTs?**
> Server-side sessions for a normal web app with one backend. Redis is a dependency you probably
> already have, a lookup is sub-millisecond, and revocation actually works — which you need the first
> time an account is compromised or someone leaves. "Stateless" is the wrong thing to optimise for in
> a system that already hits a database on every request: you're not avoiding state, you're avoiding
> one cheap lookup and paying for it with the ability to log anyone out. JWTs earn their place for
> service-to-service calls, short-lived access tokens in front of a refresh token, and genuinely
> cross-domain situations.

## 🎙️ Articulation drill

Record two minutes: **"How does session-based authentication work, and what can go wrong?"**

⭐ **Give the mechanism in one sentence, then the two properties it rests on:** **"an unguessable
random id in a cookie, with the state on the server. Its whole security comes down to two things: the
id can't be guessed, and it can't be used by a site the user didn't intend to talk to."**

⭐⭐ **Then the four things that go wrong, in order of how often they're missed:** *"first, generating
the id with `random` instead of `secrets` — `random` is a Mersenne Twister, so enough observed outputs
reveal the state, and an attacker can generate outputs by registering accounts. Second, the cookie
attributes: `HttpOnly` doesn't prevent XSS, it limits what an XSS bug can *do* — without it the
attacker takes the session away and is you, forever, from anywhere. Third, and the one people miss
entirely, session fixation: if you don't issue a new id on login, an attacker can plant an id they
already know, wait for the victim to log in, and be authenticated without stealing anything. That's a
one-line fix that's routinely absent."*

⭐⭐ **Then CSRF, explained by cause rather than by name:** *"and fourth, CSRF — which isn't a bug in my
code at all. The browser attaches my cookies to any request to my domain no matter who caused it, so a
form on evil.com posting to my API arrives perfectly authenticated. The limit worth knowing is that
they can't read the response, so it's a write attack. `SameSite=Lax` covers most of it for free, but
not top-level GET navigation — which is really an argument for keeping GET safe — and subdomains count
as same-site. So I'd add a double-submit token on dangerous actions, which works because evil.com can
cause my cookies to be sent but can't read them."*

⭐ **Close on the comparison, with a position:** *"and I'd default to server-side sessions over JWTs
for a normal web app, because revocation actually works. 'Stateless' isn't worth optimising for in a
system that already hits a database every request — you're trading the ability to log someone out for
one sub-millisecond lookup."*
