# Day 096

**L-096** · 🧪 **TDD** — red, green, refactor on a real rate limiter, and ⭐ **where it does not help**

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the value of writing the test first is not discipline — it is that a test
> you have watched fail is the only kind you know actually tests something, and that the awkwardness
> of writing it is design feedback arriving before the code exists rather than after.**
>
> ⭐ Today is one worked example done properly, and then an honest account of the limits. **Both
> halves matter in an interview**: people who claim TDD always applies are trusted about as much as
> people who have never tried it.

---

# Part 1 — ⭐ The cycle, and what each step is *for*

```
⭐⭐ RED    → GREEN    → REFACTOR   → repeat
⭐
⭐ 🔴 RED      Write a failing test. ⭐⭐ RUN IT AND WATCH IT FAIL.
⭐             ⇒ ⭐⭐ THIS IS THE STEP PEOPLE SKIP, AND IT IS THE POINT: a test
⭐               that has never failed proves NOTHING. It may be asserting on the
⭐               wrong object, silently skipped (Day 093), or passing for a reason
⭐               unrelated to your code. ⭐ Seeing red is how you test the test.
⭐             ⇒ ⭐ and read the failure MESSAGE — if it is unclear now, it will
⭐               be unclear at 2 a.m. in CI.
⭐
⭐ 🟢 GREEN    Make it pass by ⭐⭐ the simplest thing that could work. Hardcode if
⭐             that is genuinely simplest. ⭐ Ugly is fine here — you are proving
⭐             the test can go green, and the next test will remove the hardcode.
⭐
⭐ 🔵 REFACTOR ⭐⭐ NOW clean it up, with the test as a net (Day 091). ⭐ This is
⭐             the step that gets dropped under deadline, ⭐⭐ and dropping it is
⭐             what turns TDD into "writing tests first and living with the mess".
```

⭐⭐ **The cycle is short — minutes, not hours.** ⭐ If you have been red for twenty minutes, the step
was too big: delete it, take a smaller one.

# Part 2 — ⭐⭐ Building a rate limiter, test first

**The requirement:** *at most N requests per key per window; the window is fixed and resets.*

```python
# 🔴 CYCLE 1 — the first test. It does not compile, and that is correct.
def test_first_request_is_allowed():
    limiter = RateLimiter(limit=2, window_seconds=60)
    assert limiter.allow("user:1") is True
```

```
⭐⭐ NOTE WHAT THAT TEST ALREADY DID BEFORE ANY CODE EXISTS — this is the part
⭐   people mean by "TDD is a design activity":
⭐   · ⭐ it named the class and the method
⭐   · ⭐⭐ it decided the SIGNATURE: allow(key) -> bool. Not `check()` raising an
⭐        exception, not `hit()` returning a count. ⭐ You chose by writing the
⭐        CALL SITE first, which is the only place the ergonomics are visible.
⭐   · ⭐ it decided the constructor takes limit and window, not a config object
```

```python
# 🟢 GREEN — the simplest thing. Deliberately, obviously incomplete.
class RateLimiter:
    def __init__(self, limit, window_seconds):
        self.limit = limit
    def allow(self, key): return True
```

```python
# 🔴 CYCLE 2 — force it to count.
def test_requests_over_the_limit_are_denied():
    limiter = RateLimiter(limit=2, window_seconds=60)
    assert limiter.allow("user:1") is True
    assert limiter.allow("user:1") is True
    assert limiter.allow("user:1") is False        # ⭐ the third one

# 🟢
class RateLimiter:
    def __init__(self, limit, window_seconds):
        self.limit = limit
        self.count = 0
    def allow(self, key):
        self.count += 1
        return self.count <= self.limit
```

```python
# 🔴 CYCLE 3 — keys must be independent. THIS test kills the shared counter.
def test_keys_are_counted_separately():
    limiter = RateLimiter(limit=1, window_seconds=60)
    assert limiter.allow("user:1") is True
    assert limiter.allow("user:2") is True         # ⭐⭐ a DIFFERENT key

# 🟢
        self.counts: dict[str, int] = defaultdict(int)      # ⭐ Day 038
    def allow(self, key):
        self.counts[key] += 1
        return self.counts[key] <= self.limit
```

```python
# 🔴 CYCLE 4 — ⭐⭐ THE ONE THAT DRIVES THE DESIGN. The window must expire.
def test_the_window_resets():
    limiter = RateLimiter(limit=1, window_seconds=60)
    assert limiter.allow("user:1") is True
    assert limiter.allow("user:1") is False
    # ⚠️ ⭐⭐ …and now what? time.sleep(60) IS NOT A TEST (Day 092).
```

```
⭐⭐ THIS IS THE MOMENT TDD EARNS ITS KEEP. The test is HARD TO WRITE, and Day 089
⭐   already told you what that means: THE DECISION AND THE I/O ARE TANGLED. The
⭐   I/O here is the CLOCK.
⭐   ⇒ ⭐⭐ THE FIX IS A DESIGN CHANGE, ARRIVED AT FROM THE TEST: INJECT THE CLOCK.
⭐   ⇒ ⭐ and notice you would probably NOT have thought of that writing code
⭐        first — you would have called time.monotonic() inline, and discovered
⭐        the problem later, while trying to test it, with the code already written.
```

```python
# 🟢 the design the test asked for:
class RateLimiter:
    def __init__(self, limit, window_seconds, clock=time.monotonic):   # ⭐⭐ INJECTED
        self.limit, self.window = limit, window_seconds
        self.clock = clock
        self.buckets: dict[str, tuple[float, int]] = {}     # key -> (window_start, count)

    def allow(self, key: str) -> bool:
        now = self.clock()
        start, count = self.buckets.get(key, (now, 0))
        if now - start >= self.window:                       # ⭐ window expired
            start, count = now, 0
        if count >= self.limit:
            return False
        self.buckets[key] = (start, count + 1)
        return True

# ⭐⭐ AND THE TEST IS NOW INSTANT, DETERMINISTIC AND OBVIOUS:
def test_the_window_resets():
    fake_time = 1000.0
    limiter = RateLimiter(limit=1, window_seconds=60, clock=lambda: fake_time)
    assert limiter.allow("user:1") is True
    assert limiter.allow("user:1") is False
    fake_time += 61                                           # ⭐⭐ time travel, for free
    assert limiter.allow("user:1") is True
```

```python
# 🔴 CYCLE 5 — the BOUNDARY, which is where the bugs are (Day 094):
@pytest.mark.parametrize("elapsed, expected", [
    (0,    False),      # same instant
    (59.9, False),      # ⭐ just inside
    (60.0, True),       # ⭐⭐ EXACTLY at the boundary — is it >= or > ?
    (60.1, True),
])
def test_window_boundary(elapsed, expected): ...
```

⭐⭐ **Cycle 5 is where a real bug lives, and TDD found it by asking a question you have to answer:**
*is the window inclusive or exclusive?* ⭐ **You cannot write that test without deciding**, and the
decision then exists in the suite as documentation.

```
🔵 ⭐⭐ REFACTOR — and now the payoff, because the tests describe BEHAVIOUR
⭐    (Day 092), not the dict:
⭐    · swap the fixed window for a SLIDING window ⇒ ⭐⭐ every test above still
⭐      applies unchanged except the boundary case, which is exactly the case
⭐      whose semantics you deliberately changed.
⭐    · move the state into Redis for multiple workers (Day 068) ⇒ ⭐ the same
⭐      tests run against a fake and against real Redis — Day 095's contract test.
⭐    ⇒ ⭐⭐ THAT is what "tests let you change the code" means, concretely.
```

# Part 3 — ⭐⭐ The one TDD practice that is never wrong

```
⭐⭐ THE BUG-FIX WORKFLOW. Even people who dislike TDD do this, and you should
⭐   do it every single time:
⭐   1. ⭐⭐ REPRODUCE the bug — in a TEST, not by hand.
⭐   2. ⭐ WATCH IT FAIL. ⭐⭐ This proves you have actually reproduced the reported
⭐        problem and not something adjacent — which is the most common way a
⭐        "fix" ships without fixing anything.
⭐   3. FIX the code.
⭐   4. ⭐ Watch it pass.
⭐   ⇒ ⭐⭐ AND NOW THE BUG CAN NEVER SILENTLY RETURN. A regression test written
⭐        at the moment of a real failure is the highest-value test in any suite,
⭐        because it is the only one you KNOW corresponds to something that
⭐        genuinely went wrong.
⭐   ⇒ ⭐ it also gives your PR (Day 088) its best possible description: the
⭐        failing test IS the explanation of the bug.
```

# Part 4 — ⭐ Where TDD helps, and where it does not

| ⭐ TDD is strong | ⭐ Why |
|---|---|
| ⭐⭐ **Bug fixes** | ⭐⭐ The test *is* the reproduction. Never skip this. |
| Well-understood logic with a clear contract | ⭐ Rate limiters, parsers, pricing, state machines |
| ⭐ Algorithmic work | ⭐ Boundaries surface as tests rather than as incidents |
| ⭐⭐ Anything with tricky edge cases | ⭐⭐ Writing the case forces you to *decide* the semantics |
| Refactoring legacy code | ⭐ Characterisation tests first (Day 091) |

| ⚠️ TDD is weak | ⭐ Why |
|---|---|
| ⭐⭐ **Exploratory work / spikes** | ⭐⭐ You cannot test-drive a design you have not discovered. **Spike, then delete it, then TDD.** |
| UI and layout | ⭐ "Looks right" is not an assertion |
| ⭐ Integration-shaped glue | ⭐ Little logic; one integration test is worth more than ten unit tests |
| ⭐ A thin CRUD endpoint | ⭐⭐ The test would restate the framework |

```
⭐⭐ TAKE THE CRITICISM SERIOUSLY — "TEST-INDUCED DESIGN DAMAGE" (DHH):
⭐   the claim is that TDD pressures you toward indirection — interfaces,
⭐   injection and layers introduced ONLY so the code can be mocked — and that
⭐   the result is a codebase optimised for its tests rather than for readers.
⭐
⭐   ⭐⭐ AND IT IS A FAIR CRITICISM OF SOMETHING REAL. My answer:
⭐   ⇒ ⭐⭐ most of that damage is MOCK overuse, not TDD (Day 095). Injecting a
⭐        CLOCK improved the rate limiter for everyone — it is now deterministic
⭐        and reusable. Injecting a `UserServiceFactoryProvider` so a mock can be
⭐        slotted in improves nothing.
⭐   ⇒ ⭐ THE TEST TO APPLY: does this seam make the code better for a READER, or
⭐        only for a TEST? ⭐⭐ If only for a test, the design pressure was
⭐        misread — and that is the honest, non-defensive answer.
```

⭐ **Two schools, briefly.** *London/outside-in* starts at the boundary and mocks collaborators,
discovering interfaces as it goes. *Chicago/inside-out* starts with the domain and uses real objects,
mocking only genuine I/O. ⭐⭐ **Chicago produces fewer mocks and more durable tests** — which is
consistent with everything Day 095 argued — **but outside-in is genuinely better when the shape of the
API is the thing you are trying to discover.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Not watching the test fail** | ⭐⭐ A test that has never failed proves nothing. |
| ⭐ Skipping refactor | ⭐ That is "tests first, then live with the mess". |
| Writing five tests before any code | ⭐ One at a time; each should drive one change. |
| ⭐ Steps too big | ⭐ Twenty minutes red ⇒ delete and take a smaller step. |
| ⭐ `time.sleep` to test expiry | ⭐⭐ Inject the clock — the design change the test is asking for. |
| ⭐⭐ Ignoring "this is hard to test" | ⭐⭐ That is design feedback, not an obstacle. |
| Fixing a bug without a failing test first | ⭐⭐ You cannot prove you reproduced it. |
| ⭐ TDD on an exploratory spike | ⭐ Spike, **delete the spike**, then TDD. |
| Introducing an interface only for mocking | ⭐⭐ Does the seam help a reader? If not, drop it. |
| ⭐ Claiming TDD always applies | ⭐ Reads as inexperience. |

## Interview questions

**Q: Walk me through the TDD cycle and say what each step is for.**
> Red, green, refactor. The red step is the one people skip and it's the whole point — you write the
> test and *watch it fail*, because a test that's never failed proves nothing. It might be asserting
> on the wrong object, or silently not collected, or passing for a reason unrelated to your code.
> Seeing red is how you test the test. Green is the simplest thing that could work, hardcoding if
> that's genuinely simplest, because the next test will remove the hardcode. Refactor is where you
> clean it up with the tests as a net — and dropping that step is what turns TDD into writing tests
> first and living with the mess.

**Q: Give me a concrete case where writing the test first changed the design.**
> Building a rate limiter. The first three tests were straightforward, and then I needed to test that
> the window resets — and there's no acceptable way to write that against a real clock, because
> `sleep(60)` isn't a test. That awkwardness is design feedback: the decision and the I/O are tangled.
> The fix is to inject the clock, and the test becomes instant and deterministic — you just advance a
> variable. Writing the code first, I'd have called `time.monotonic()` inline and only discovered the
> problem later, with the code already written and harder to change. And the injected clock is better
> for everyone, not just for tests: it makes the limiter deterministic and reusable.

**Q: Do you always practise TDD?**
> No, and I'd distrust anyone who says they do. It's strongest where there's a clear contract and real
> logic — parsers, pricing, rate limiters, state machines — and especially anywhere with tricky edge
> cases, because writing the boundary case forces you to *decide* the semantics rather than discover
> them in production. It's weak on exploratory work, because you can't test-drive a design you haven't
> found yet; there I'd spike, throw the spike away, then TDD the real thing. It's also weak on UI and
> on thin CRUD glue where the test would just restate the framework. The one place I'd never skip it
> is bug fixes.

**Q: Why write the test first for a bug fix specifically?**
> Because watching it fail proves I've actually reproduced the reported problem rather than something
> adjacent — which is the most common way a "fix" ships without fixing anything. Then the fix turns it
> green, and the bug can't silently return. A regression test written at the moment of a real failure
> is the highest-value test in a suite, because it's the only kind I *know* corresponds to something
> that genuinely went wrong. It also makes the PR self-explanatory: the failing test is the
> description of the bug.

**Q: What do you make of "test-induced design damage"?**
> It's a fair criticism of something real. TDD can push people toward indirection that exists only so
> the code can be mocked, and then the codebase is optimised for its tests rather than for readers.
> My response is that most of that damage is mock overuse rather than TDD itself. Injecting a clock
> made my rate limiter better for everyone. Introducing a factory-provider so a mock can be slotted in
> improves nothing. The test I apply is whether the seam makes the code better for a reader or only
> for a test — and if it's only for a test, I misread the design pressure.

## Mini task

1. ⭐⭐ **Build the rate limiter from scratch, test-first, all five cycles.** Do not read ahead; write
   each test before the code.
2. ⭐⭐ At cycle 4, **try to write the expiry test with `time.sleep` first.** Time it. Then inject the
   clock and time it again.
3. ⭐⭐ Deliberately break one test's assertion so it passes trivially (`assert True`) and notice you
   would not have caught it without watching red.
4. ⭐ Add the boundary parametrization and **decide** whether the window is inclusive. Write the
   decision into a test name.
5. ⭐⭐ **Refactor to a sliding window** with the tests as your net. Note which single test changed and
   why that is the correct one.
6. ⭐⭐ Move the state into Redis behind a `Protocol` (Day 095) and run the same tests against a fake
   and the real thing.
7. ⭐⭐ Take a real bug from your own project. **Write the failing test first**, watch it fail, then fix
   it.
8. ⭐ Take a spike you wrote exploratively. **Delete it** and rebuild it test-first. Compare the
   designs honestly.
9. ⭐⭐ Find a seam in your code that exists only for mocking. **Decide whether it helps a reader**, and
   remove it if not.
10. ⭐ Do one small feature outside-in (mock collaborators) and one inside-out (real objects). **Say
    which tests you would rather own in a year.**
