# Day 045

**L-045** · `classmethod`, `staticmethod`, `classmethod` factories, `functools.partial`, `operator`

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `classmethod` exists so a method can produce *the right subclass*, and
> `partial` exists so you can fix arguments without writing a lambda you cannot pickle.**
>
> ⭐ Both are descriptors (Day 032) and both are small. **The alternative-constructor pattern from
> Part 2 is the one that will show up in your own code every week.**

---

# Part 1 — ⭐ The three method kinds

```python
class Order:
    tax_rate = 0.2                       # ⭐ class attribute

    def total(self):                     # ⭐ INSTANCE method — gets the instance
        return self.subtotal * (1 + self.tax_rate)

    @classmethod
    def from_row(cls, row):              # ⭐⭐ gets the CLASS
        return cls(subtotal=row["subtotal"])

    @staticmethod
    def is_valid_currency(code):         # ⭐ gets NOTHING — a plain function in a namespace
        return code in {"GBP", "USD", "EUR"}
```

| | ⭐ Receives | ⭐ Use for |
|---|---|---|
| instance method | `self` | ⭐ behaviour of one object |
| ⭐⭐ `classmethod` | ⭐⭐ `cls` | ⭐⭐ **alternative constructors**, class-level state, factories |
| `staticmethod` | nothing | ⭐ a helper that *belongs* with the class but needs neither |

```
⭐⭐ WHY cls MATTERS — this is the entire argument for classmethod:
⭐   class PriorityOrder(Order): ...
⭐   PriorityOrder.from_row(row)   ⇒ ⭐⭐ cls IS PriorityOrder ⇒ you get a PriorityOrder back.
⭐   ⇒ ⭐⭐ hardcoding `return Order(...)` would return the WRONG CLASS for every subclass,
⭐        silently, and only in the subclass's tests if you wrote any.
```

⭐ **Both are descriptors** (Day 032): `classmethod.__get__` binds `cls`, `staticmethod.__get__`
binds nothing and returns the plain function. **That is all they are** — which is why they must sit
outermost in a decorator stack (Day 044): they change what the attribute *is*, so anything applied
after them wraps a descriptor rather than a function.

⚠️ ⭐ **`staticmethod` is often a smell.** If it needs neither the instance nor the class, ask whether
it should be a module-level function. **It is justified when the grouping genuinely aids discovery
(`Order.is_valid_currency`) or when subclasses might override it** — otherwise a module function is
simpler and easier to test.

# Part 2 — ⭐⭐ The alternative-constructor pattern

```python
class User:
    def __init__(self, id: int, email: str, created: datetime):
        self.id, self.email, self.created = id, email, created

    @classmethod
    def from_row(cls, row) -> "User":            # ⭐⭐ database
        return cls(row["id"], row["email"], row["created_at"])

    @classmethod
    def from_json(cls, s: str) -> "User":        # ⭐ API payload
        d = json.loads(s)
        return cls(d["id"], d["email"], datetime.fromisoformat(d["created"]))

    @classmethod
    def anonymous(cls) -> "User":                # ⭐ a named special case
        return cls(0, "", datetime.min)
```

```
⭐⭐ WHY THIS IS THE RIGHT SHAPE:
⭐   · ⭐⭐ __init__ stays ONE simple thing — it takes real values and assigns them
⭐   · each entry point is NAMED, so the call site reads as documentation
⭐   · ⭐ no `if isinstance(arg, dict) elif isinstance(arg, str)` inside __init__ —
⭐     which is the alternative, and it is how constructors become unmaintainable
⭐   · ⭐ subclasses inherit every constructor for free, correctly typed
⭐
⭐ ⭐⭐ THE RULE: __init__ takes VALUES. classmethods take REPRESENTATIONS.
```

⭐ **You have already seen these:** `dict.fromkeys` (Day 036), `datetime.fromisoformat`,
`datetime.now`, `Path.cwd`, `int.from_bytes`. **The standard library uses this pattern everywhere,
which is a good argument that it is the idiom rather than a preference.**

⭐ **`__new__` vs `__init__`** gets its own day (Day 053), but the short version: **`__new__` creates
the object and `__init__` initialises it** — you need `__new__` only for immutable types and
singletons, and an alternative constructor is almost always the answer instead.

# Part 3 — ⭐⭐ `functools.partial`

```python
from functools import partial

def connect(host, port, timeout=30): ...

local = partial(connect, "localhost")          # ⭐ fixes the FIRST positional
local(5432)                                    # ⇒ connect("localhost", 5432)

quick = partial(connect, timeout=1)            # ⭐ fixes a keyword (still overridable)
quick("db", 5432, timeout=5)                   # ⭐ 5 wins — later keywords override
```

```
⭐⭐ partial VS lambda — three real differences, not style:
⭐   1. ⭐⭐ PICKLABLE. partial over a module-level function crosses a process boundary;
⭐        a lambda or closure does not (Day 043) ⇒ multiprocessing, Celery, ProcessPoolExecutor.
⭐   2. ⭐⭐ NO LATE BINDING. partial(f, i) captures i's VALUE NOW —
⭐        ⇒ ⭐⭐ so it is immune to Day 030's loop trap, by construction.
⭐   3. ⭐ INTROSPECTABLE: p.func, p.args, p.keywords. A lambda is opaque.
```

```python
# ⭐⭐ THE LOOP TRAP, SOLVED BY CONSTRUCTION:
handlers = [lambda: print(i) for i in range(3)]          # ⚠️ prints 2, 2, 2
handlers = [partial(print, i) for i in range(3)]         # ⭐⭐ prints 0, 1, 2
```

```python
# ⭐ Where partial genuinely earns its place:
pool.map(partial(process, config=cfg), items)      # ⭐⭐ picklable ⇒ works with processes
sorted(rows, key=partial(get_field, "created"))
json.dumps = partial(json.dumps, default=str)      # ⭐ pre-configuring a library function
callback = partial(self.on_done, request_id)       # ⭐ binding context to a callback
```

⭐ **`functools.partialmethod`** does the same inside a class body, which is a neat way to define
`set_active = partialmethod(_set_state, True)`.

⚠️ ⭐ **`partial` fixes arguments left to right**, so you cannot skip one. If you need to fix a later
positional, pass it by keyword or use a small `def` — **and at that point a named function is
usually clearer anyway.**

# Part 4 — ⭐ The `operator` module

```python
import operator as op
from operator import itemgetter, attrgetter, methodcaller

sorted(people, key=attrgetter("age"))              # ⭐⭐ instead of lambda p: p.age
sorted(rows,   key=itemgetter(1))                  # ⭐ instead of lambda r: r[1]
sorted(people, key=attrgetter("last", "first"))    # ⭐⭐ multiple ⇒ a TUPLE key, for free
sorted(strs,   key=methodcaller("lower"))
max(d.items(), key=itemgetter(1))                  # ⭐ the highest-value entry in a dict

functools.reduce(op.add, nums)                     # ⭐ instead of lambda a,b: a+b
OPS = {"+": op.add, "-": op.sub, "*": op.mul}      # ⭐ the dispatch table again
```

```
⭐⭐ WHY IT IS NOT JUST STYLE:
⭐   `key=` is called ONCE PER ELEMENT (Day 033) ⇒ n Python-level function calls for a lambda.
⭐   ⇒ ⭐ itemgetter/attrgetter are implemented in C ⇒ measurably faster on large sorts
⭐   ⇒ ⭐⭐ and attrgetter("last", "first") builds the tuple key for you — the multi-field
⭐        sort idiom (Day 029) with no lambda at all.
```

⭐ **`operator` also gives you the in-place forms** (`op.iadd`) and the comparison functions
(`op.lt`, `op.eq`), which is what `functools.cmp_to_key` and various sorting utilities are built on.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Hardcoding the class in a factory** | ⭐⭐ Use `cls` — subclasses get the wrong type otherwise. |
| ⭐ Overloading `__init__` with isinstance branches | ⭐⭐ Named classmethods take representations. |
| `staticmethod` for everything stateless | ⭐ Often a module function is simpler. |
| `classmethod`/`staticmethod` not outermost | ⭐⭐ They change what the attribute is (Day 044). |
| ⭐ Lambda where `partial` belongs | ⭐⭐ Not picklable; late binding; opaque. |
| Lambdas in a loop building callbacks | ⭐⭐ `partial` captures the value by construction. |
| ⭐ `key=lambda x: x.field` on a big sort | ⭐ `attrgetter` — n calls in C rather than Python. |
| Writing a multi-field lambda key | ⭐ `attrgetter("a", "b")` returns the tuple. |
| Expecting `partial` to skip arguments | ⭐ Left to right, or use keywords. |

## Interview questions

**Q: `classmethod` versus `staticmethod`?**
> A classmethod receives the class as its first argument, a staticmethod receives nothing. The reason
> that difference matters is subclassing: a classmethod factory that does `return cls(...)`
> automatically produces the right subclass, whereas hardcoding the class name silently returns the
> base type for every subclass. Staticmethod is really just a namespacing tool — if the function
> needs neither the instance nor the class, I'd usually ask whether it should be a module-level
> function instead, unless the grouping genuinely helps discovery or subclasses might override it.

**Q: What's the alternative-constructor pattern?**
> Keeping `__init__` simple — it takes real values and assigns them — and adding named classmethods
> for each way an object can be built: `from_row`, `from_json`, `from_bytes`. It avoids the
> alternative, which is an `__init__` full of `isinstance` branches trying to guess what it was
> handed, and it makes call sites self-documenting. The standard library uses it constantly —
> `dict.fromkeys`, `datetime.fromisoformat`, `int.from_bytes` — so it's the idiom rather than a
> preference. The rule I'd give is: `__init__` takes values, classmethods take representations.

**Q: `partial` or a lambda?**
> Three reasons for `partial`. It's picklable when it wraps a module-level function, so it can cross
> a process boundary — lambdas and closures can't, which is the `Can't pickle local object` error
> people hit with `multiprocessing` and Celery. It binds argument values immediately rather than
> capturing a variable, so it's immune to the loop-variable trap by construction. And it's
> introspectable — `.func`, `.args`, `.keywords` — where a lambda is opaque in a traceback.

**Q: Why use `operator.attrgetter` instead of a lambda?**
> Because `key` is called once per element, so on a large sort it's n Python-level function calls,
> and `attrgetter` is implemented in C. It also handles the multi-field case directly:
> `attrgetter("last", "first")` returns a tuple, which is exactly the idiom for sorting by several
> fields, without writing the lambda at all. It's one of the few micro-optimisations that also makes
> the code clearer.

**Q: Where does the decorator order matter with these?**
> `classmethod` and `staticmethod` have to be outermost. They're descriptors that change what the
> class attribute *is*, so if another decorator is applied after them, it receives a descriptor
> object rather than a function and the wrapper breaks in a confusing way. Same underlying reason as
> Day 032: attribute access is a protocol, and those two participate in it.

## 🎙️ Articulation drill

Record two minutes: **"How do you design a class that can be built from a database row, a JSON
payload, or plain values?"**

⭐ Answer with the shape, not the code: **`__init__` takes real values and does nothing clever — no
`isinstance` branching, no guessing what it was handed.** Then **one named classmethod per
representation**: `from_row`, `from_json`, and any named special case like `anonymous()`.

⭐ Then the reason that is not just tidiness: **each is written with `cls(...)`, so every subclass
inherits every constructor and gets its own type back.** Hardcoding the class name is the bug —
silent, and only visible in subclass tests.

⭐⭐ **Then close by placing it, because that is what makes it an argument rather than a habit:**
*"this is the standard library's own pattern — `dict.fromkeys`, `datetime.fromisoformat`,
`int.from_bytes` — and it scales, because the day a fourth input format arrives you add a method
instead of another branch to a constructor that already has three. The one place I'd move off it is
external data, where I want Pydantic doing the parsing and validation rather than a classmethod doing
it by hand."*
