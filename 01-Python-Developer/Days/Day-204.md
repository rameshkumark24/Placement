# Part 1 — ⭐ Strings: four different tools with one name

```
⭐ ① A BLOB — the cache value from Day 143.
⭐    SET user:42 '{"…"}' EX 300 NX
⭐    ⭐⭐ THE OPTIONS MATTER MORE THAN THE COMMAND:
⭐      `NX` set only if absent · `XX` only if present
⭐      `EX s` / `PX ms` TTL · `KEEPTTL` keep the existing TTL
⭐      `GET` return the OLD value ⭐⭐ (7.0+: an atomic get-and-set)
⭐    ⭐⭐ `SET k v EX 300 NX` IS AN ATOMIC "CREATE-IF-ABSENT WITH
⭐      EXPIRY" — ⭐ it is Day 207's lock, and it is one command.
⭐    ⭐⭐ AND THE BUG: `SET k v` WITHOUT `KEEPTTL` ***CLEARS THE TTL***.
⭐      A cache entry silently becomes immortal. ⭐ Extremely common.

⭐ ② A COUNTER — `INCR` / `INCRBY` / `DECRBY` / `INCRBYFLOAT`
⭐    ⭐⭐ ATOMIC, NO LOCK, NO READ-MODIFY-WRITE. Day 195's lost update
⭐      cannot occur. ⭐ `INCR` on a missing key starts at 0.
⭐    ⭐ The pattern: `INCR` then, if the reply is 1, `EXPIRE` — ⭐⭐ two
⭐      commands, and Day 208 makes it one Lua script for a reason.

⭐ ③ A BITMAP — Part 6.
⭐ ④ ⭐ RAW BYTES — up to 512 MB. ⭐⭐ Which you should read as "do not":
⭐    a 10 MB value is 10 MB copied through a single-threaded server.
```

# Part 2 — ⭐ Hashes, lists, sets

```
⭐⭐ HASH — a field→value map under one key.
⭐   HSET user:42 name "Priya" visits 0
⭐   ⭐⭐ HINCRBY user:42 visits 1   ← ATOMIC FIELD INCREMENT. This is
⭐     the reason to choose a hash over a JSON string: ⭐ you can update
⭐     ONE FIELD without read-modify-write, and without rewriting the
⭐     whole value (Day 198's amplification problem, in miniature).
⭐   ⭐ HSETNX · HDEL · HRANDFIELD · ⭐ 7.4+: HEXPIRE per-field TTL
⭐   ⭐⭐ MEMORY: 100 fields in ONE HASH ≈ ***1/5*** THE MEMORY of 100
⭐     separate keys (Part 8). ⭐ Every key has ~50–100 bytes of
⭐     overhead; hash fields share it.
⭐   ⭐⭐ AND THE LIMIT: NO TTL PER KEY-SET, no expiry on a field before
⭐     7.4, and `HGETALL` on a huge hash is Day 203's banned list.

⭐⭐ LIST — a linked list. Push/pop at both ends, O(1).
⭐   LPUSH q job1 · RPOP q          ⭐ a queue
⭐   BRPOP q 5                      ⭐⭐ BLOCKING pop — no polling
⭐   LPUSH recent x · LTRIM recent 0 99   ⭐⭐ A CAPPED "LAST 100" LIST
⭐        IN TWO COMMANDS. ⭐ Activity feeds, recent searches, last-N
⭐        logs. ⭐ LTRIM is O(removed), so trimming often is cheap.
⭐   ⭐⭐ THE WARNING: A LIST IS ***NOT*** A RELIABLE QUEUE. `RPOP`
⭐     removes the job; if the worker dies, ⭐⭐ THE JOB IS GONE. There
⭐     is no ack.
⭐     ⇒ ⭐ `BLMOVE q processing LEFT RIGHT 5` — atomically move to a
⭐       processing list, do the work, then remove it. ⭐⭐ Plus a
⭐       reaper for jobs stuck in `processing`. ⭐ Or use Streams
⭐       (Day 209), which have this built in.

⭐⭐ SET — unordered, unique. O(1) add/remove/membership.
⭐   ⭐⭐ `SADD seen:day event123` RETURNS 1 IF NEW, 0 IF PRESENT.
⭐     ⇒ ⭐⭐ THAT IS AN ATOMIC IDEMPOTENCY CHECK IN ONE COMMAND —
⭐       Day 184's invariant #6, for the price of one round trip. ⭐ Use
⭐       it for webhook dedup, at-least-once consumers, "already sent".
⭐   ⭐ SINTER / SUNION / SDIFF — set algebra server-side. "Mutual
⭐     followers" is one command. ⭐⭐ SINTER is O(N×M); on big sets use
⭐     `SINTERCARD` (7.0+) with a `LIMIT` if you only need a count.
⭐   ⭐ SPOP (random remove), SRANDMEMBER (random peek) — sampling,
⭐     raffles, work stealing.
```

# Part 3 — ⭐⭐ The sorted set: the most useful structure in Redis

```
⭐⭐ A SET WHERE EVERY MEMBER HAS A `score` (float), KEPT IN SCORE ORDER.
⭐   Skip list + hash map ⇒ ⭐ O(log n) insert, O(log n) rank lookup,
⭐   O(log n + m) range scan. ⭐⭐ AND *THE SCORE CAN MEAN ANYTHING* —
⭐   which is why one structure covers five unrelated problems.

⭐ ① ⭐ LEADERBOARD — score = points
⭐    ZADD lb 4200 priya · ZINCRBY lb 50 priya
⭐    ZREVRANGE lb 0 9 WITHSCORES     ⭐ top 10, O(log n + 10)
⭐    ⭐⭐ ZREVRANK lb priya           ⭐⭐ "YOU ARE #4,812 OF 2,000,000"
⭐      — ⭐ in microseconds. In SQL that is a window function over the
⭐      whole table.
⭐    ⭐ `ZADD lb GT 4200 priya` — ⭐⭐ only update if GREATER. High
⭐      scores never go backwards, with no read.

⭐ ② ⭐⭐ DELAYED / SCHEDULED JOBS — score = run-at timestamp
⭐    ZADD due 1755400000 job:91
⭐    ZRANGEBYSCORE due -inf <now> LIMIT 0 100   ⭐ what is ready
⭐    ⭐⭐ Day 159's scheduler, without a cron. ⭐ Pop atomically with
⭐      `ZPOPMIN`, or Lua for range-and-remove.

⭐ ③ ⭐⭐ SLIDING-WINDOW RATE LIMIT — score = request timestamp
⭐    ZREMRANGEBYSCORE k -inf <now-60s>   ⭐ drop what left the window
⭐    ZCARD k                             ⭐ how many remain
⭐    ⇒ ⭐ Day 208 builds this properly, in Lua, in one round trip.

⭐ ④ ⭐ PRIORITY QUEUE — score = priority. `ZPOPMIN` / `BZPOPMIN`.

⭐ ⑤ ⭐⭐ A SECONDARY INDEX — score = a numeric attribute (price, age,
⭐    created_at). ⭐ `ZRANGEBYSCORE products:by_price 100 500`.
⭐    ⭐⭐ AND WITH ALL SCORES EQUAL, `ZRANGEBYLEX` GIVES YOU
⭐      LEXICOGRAPHIC RANGES — autocomplete prefixes, in O(log n).
```

```
⭐⭐ THE COST, STATED HONESTLY: a sorted set is the most memory-hungry
⭐   structure here — roughly 60–100 bytes per member beyond the data,
⭐   because of the skip list. ⭐ A 10M-member leaderboard is ~1 GB.
⭐   ⇒ ⭐ Cap it (`ZREMRANGEBYRANK lb 0 -1000001` keeps the top million),
⭐     or shard by segment.
```

# Part 4 — ⭐⭐ Bitmaps and HyperLogLog: two arithmetic tricks

```
⭐⭐ BITMAP — a string used as an array of bits, offset = user id.
⭐   SETBIT dau:2026-08-19 42 1      ⭐ user 42 was active
⭐   BITCOUNT dau:2026-08-19         ⭐⭐ HOW MANY DAUs — one command
⭐   BITOP AND out dau:d1 dau:d2     ⭐⭐ ACTIVE ON BOTH DAYS
⭐   BITOP OR  wau dau:d1 … dau:d7   ⭐ weekly actives
⭐
⭐   ⭐⭐ THE ARITHMETIC THAT SELLS IT:
⭐     100,000,000 users ÷ 8 bits = ⭐⭐ 12.5 MB PER DAY.
⭐     ⭐ A year of daily-actives = 4.5 GB, and every retention question
⭐       ("came back on day 7") is a `BITOP` away.
⭐     ⭐ The equivalent SQL table is 100M rows per day.
⭐   ⭐⭐ THE CONDITION: IDS MUST BE DENSE SMALL INTEGERS. Sparse ids
⭐     (or UUIDs) waste the whole array — ⭐ user id 4,000,000,000
⭐     allocates 500 MB by itself. ⭐⭐ Map to a dense sequence first,
⭐     or use HyperLogLog.

⭐⭐ HYPERLOGLOG — probabilistic cardinality.
⭐   PFADD visitors:today user:9182   ⭐ any string, any cardinality
⭐   PFCOUNT visitors:today           ⭐ estimated distinct count
⭐   PFMERGE month visitors:d1 … d30  ⭐⭐ union, then count — CORRECT,
⭐                                       not the sum of the parts
⭐   ⭐⭐ 12 KB PER COUNTER. FIXED. FOR ANY CARDINALITY, UP TO 2^64.
⭐     ⭐ Standard error 0.81%.
⭐   ⭐ vs a SET of 10M ids: ⭐⭐ ~400 MB → 12 KB. THIRTY THOUSAND
⭐     TIMES SMALLER.
⭐   ⭐⭐ THE TRADE, AND YOU MUST SAY IT OUT LOUD: YOU CAN NEVER ASK
⭐     "IS USER X IN THERE?" — there are no members, only an estimate.
⭐     ⭐ Right for analytics counts. Wrong for anything you must act on
⭐       per user.
```

```
⭐ GEOSPATIAL — GEOADD / GEOSEARCH BYRADIUS. ⭐⭐ It IS a sorted set
⭐   whose score is a geohash, which is why `ZRANGE` works on it and why
⭐   its cost profile is the sorted set's.
⭐ STREAMS — an append-only log with consumer groups. ⭐ Day 209.
```

# Part 5 — ⭐⭐ Encodings: why small collections are nearly free

```sql
redis> RPUSH mylist a b c
redis> OBJECT ENCODING mylist       -- ⭐ "listpack"
redis> RPUSH mylist … (200 items)
redis> OBJECT ENCODING mylist       -- ⭐⭐ "quicklist" — IT CONVERTED
```

```
⭐⭐ REDIS STORES SMALL COLLECTIONS AS A ***FLAT PACKED ARRAY***, and
⭐   only converts to the "real" structure past a threshold.

⭐   TYPE        SMALL              LARGE        THRESHOLD (default)
⭐   hash        listpack           hashtable    128 entries / 64 B
⭐   list        listpack           quicklist    128 / 64
⭐   set (ints)  ⭐ intset          hashtable    512 entries
⭐   set (other) listpack           hashtable    128 / 64
⭐   zset        listpack           skiplist     128 / 64
⭐   string      ⭐ embstr (≤44 B)  raw          44 bytes

⭐⭐ THE TRADE: THE PACKED FORM IS O(n) — ⭐ BUT n ≤ 128, IT IS
⭐   CONTIGUOUS, AND IT FITS IN CACHE LINES, SO IT IS ***FASTER*** THAN
⭐   A HASH TABLE AS WELL AS SMALLER.
⭐   ⭐⭐ MEMORY: a 100-field listpack hash ≈ 1/5 to 1/10 the memory of
⭐     the hashtable form, and ~1/5 that of 100 separate keys.

⭐⭐ THE DESIGN CONSEQUENCE — the "hash bucketing" trick:
⭐   ❌ 10,000,000 keys `user:42:visits` → ~1 GB of key overhead alone
⭐   ✅ 100,000 hashes of 100 fields each, `users:{id/100}` → ⭐⭐ ~5×
⭐     LESS MEMORY, same access pattern, one extra division in your
⭐     code. ⭐ Instagram published this; it is still the best-known
⭐     Redis memory optimisation.
⭐   ⭐⭐ AND THE TRAP: ONE OVERSIZED COLLECTION CONVERTS ***PERMANENTLY
⭐     AND SILENTLY***. It never converts back, even after you delete
⭐     items. ⭐ Check with `OBJECT ENCODING` in a test, not in your head.
```

# Part 6 — ⭐ Choosing, and naming

```
⭐⭐ THE DECISION TABLE — read it as "what is the QUESTION?"

⭐   "get/set a blob"                       → STRING
⭐   "increment a number atomically"         → STRING (INCR)
⭐   "update one field of an object"         → HASH
⭐   "have I seen this before?"              → ⭐⭐ SET (SADD == 1)
⭐   "who is in both groups?"                → SET (SINTER)
⭐   "the last N things"                     → LIST (LPUSH + LTRIM)
⭐   "a queue"                               → ⭐ LIST if losses are ok,
⭐                                              ⭐⭐ STREAM if not
⭐   "rank, top-N, or a range by a number"   → ⭐⭐ SORTED SET
⭐   "what is due now?"                      → ⭐⭐ SORTED SET (score=ts)
⭐   "how many distinct, roughly?"           → HYPERLOGLOG
⭐   "which of 100M flags are set?"          → BITMAP
⭐   "an event log many consumers read"      → STREAM
```

```
⭐⭐ KEY NAMING IS AN API (Day 143, restated because it matters here):
⭐   `app:v2:tenant:{tid}:user:{uid}:profile`
⭐   ⭐ COLON-DELIMITED HIERARCHY — so `SCAN MATCH` and RedisInsight
⭐     group it, and so a human can read a `MONITOR` dump.
⭐   ⭐⭐ A VERSION SEGMENT — ⭐⭐ changing the serialisation format
⭐     becomes a deploy, not a migration: bump `v2`→`v3` and the old
⭐     keys expire on their own.
⭐   ⭐ THE TENANT IN THE KEY — Day 160's isolation, at the cache layer.
⭐   ⭐⭐ AND `{braces}` MATTER IN CLUSTER MODE: only the part inside
⭐     braces is hashed, so `{tid}` in every key of one tenant keeps
⭐     them on one node — ⭐ which is what makes a multi-key command or
⭐     a Lua script legal at all.
```

```python
# ⭐ In Python, with the two habits that keep this maintainable:
class Keys:                                    # ⭐⭐ ONE place, not 30
    V = "v2"
    @staticmethod
    def profile(tid: int, uid: int) -> str:
        return f"app:{Keys.V}:t:{{{tid}}}:user:{uid}:profile"

with r.pipeline(transaction=False) as p:       # ⭐ Day 203
    p.hincrby(Keys.profile(t, u), "visits", 1)
    p.expire(Keys.profile(t, u), 86400)        # ⭐⭐ EVERY key gets a
    p.execute()                                #    TTL, or you have
                                               #    built a memory leak
# ⭐⭐ THE RULE WORTH ENFORCING IN REVIEW: ***EVERY WRITE SETS A TTL OR
#    IS EXPLICITLY JUSTIFIED IN A COMMENT.*** Unbounded key growth is
#    the most common way a Redis "cache" becomes a production incident.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Using only `GET`/`SET` | You've paid for a data structure server and installed a hash map. |
| `SET k v` on an existing key with a TTL | It clears the TTL. Use `KEEPTTL`. |
| Read-modify-write for a counter | `INCR` is atomic; the lost update can't happen. |
| A JSON string where a hash belongs | You rewrite the whole value to change one field. |
| 10 million individual keys | ~50–100 bytes of overhead each. Bucket into hashes. |
| Treating a list as a reliable queue | `RPOP` has no ack; a dead worker loses the job. Use `BLMOVE` or a Stream. |
| Polling a list with `RPOP` in a loop | `BRPOP` blocks server-side. |
| Doing "have I seen this?" with `SISMEMBER` then `SADD` | `SADD`'s return value already answers it, atomically. |
| `SINTER` on two huge sets | O(N×M). `SINTERCARD` with a limit if you only need a count. |
| Not knowing sorted sets solve five different problems | Score = points, timestamp, priority, attribute, or window position. |
| Uncapped leaderboards | ~60–100 bytes per member; ten million members is a gigabyte. |
| Bitmaps with sparse or UUID ids | One id of four billion allocates 500 MB. |
| Expecting HyperLogLog to answer membership | There are no members, only an estimate. |
| Summing per-day `PFCOUNT`s for a month | `PFMERGE` then count — the union is not the sum. |
| Assuming a converted encoding converts back | It's permanent and silent. Verify with `OBJECT ENCODING`. |
| Keys without a version segment | A format change becomes a migration instead of a deploy. |
| Writing a key with no TTL and no justification | That's how a cache becomes a memory-exhaustion incident. |

## Interview questions

**Q: When would you use a sorted set?**

> More often than anything else in Redis, because the score can mean five different things. Points, and
> you get a leaderboard with `ZREVRANGE` for the top ten and `ZREVRANK` for "you are number four
> thousand of two million" in microseconds — which in SQL is a window function over the whole table. A
> timestamp, and you get scheduled or delayed jobs: everything due is `ZRANGEBYSCORE` up to now. A
> request time, and you get a sliding-window rate limiter by trimming everything outside the window and
> counting what's left. A priority, and `ZPOPMIN` gives you a priority queue with a blocking variant. Or
> any numeric attribute, and you have a secondary index with range queries — and with equal scores,
> `ZRANGEBYLEX` gives lexicographic ranges, which is how you do prefix autocomplete. The cost to state
> honestly is memory: sixty to a hundred bytes per member for the skip list, so a ten-million-member
> leaderboard is about a gigabyte and needs capping.

**Q: You need to count unique visitors per day for a hundred million users. How?**

> Two options with very different trade-offs, and which one depends on whether you'll ever need to ask
> about an individual. If ids are dense integers and you need per-user answers, a bitmap — one bit per
> user, so twelve and a half megabytes per day for a hundred million users, `BITCOUNT` for the total,
> and `BITOP AND` across two days answers "came back the next day", which is a retention question
> answered with one command. The condition is that ids have to be dense; a user id of four billion
> allocates five hundred megabytes on its own, so UUIDs are out unless you map to a dense sequence.
> If you only need the count, HyperLogLog: twelve kilobytes fixed, for any cardinality, with a 0.81%
> standard error, and `PFMERGE` gives you a correct monthly union rather than the sum of daily counts.
> Versus a set of ten million ids at roughly four hundred megabytes, that's thirty thousand times
> smaller. The trade you must say out loud is that HyperLogLog has no members — you can never ask
> whether a specific user is in there.

**Q: How do you deduplicate at-least-once webhook deliveries with Redis?**

> `SADD seen:<window> <event_id>` and check the return value: one means it's new, zero means you've
> already processed it. That's an atomic test-and-set in a single command and a single round trip,
> which is exactly the idempotency guarantee you need for at-least-once delivery. The details that
> matter are the key design and the TTL: I'd bucket by day or hour so the set is bounded and expires
> on its own rather than growing forever, and I'd make sure the TTL is comfortably longer than the
> provider's retry window. The thing I'd flag is that this is a *cache-grade* guarantee — if Redis is
> flushed or fails over with unsaved state, dedup entries vanish and you'd reprocess. So for money it
> backs a database unique constraint rather than replacing one, with Redis as the fast path.

**Q: What's the biggest memory optimisation in Redis?**

> Bucketing many keys into fewer hashes. Every key carries somewhere between fifty and a hundred bytes
> of overhead for the dictionary entry, the object header and the expiry entry, so ten million
> individual keys is about a gigabyte before any of your data. If you store the same data as a hundred
> thousand hashes of a hundred fields each — keyed by `id / 100` — Redis keeps each small hash in a
> *listpack*, a flat packed array, and the memory drops by roughly five times. The counterintuitive
> part is that the packed form is O(n) and still faster, because n is capped at a hundred and
> twenty-eight and the data is contiguous and cache-friendly. The trap is that once a collection
> exceeds the threshold it converts to a hash table permanently and silently, and it never converts
> back even if you delete elements — so you verify with `OBJECT ENCODING` in a test rather than
> assuming.

**Q: Is a Redis list a good queue?**

> For work you can afford to lose, yes — `LPUSH` and `BRPOP` give you a blocking queue in two commands
> with no broker to run. But `RPOP` removes the job the moment it's handed out, so if the worker dies
> mid-job it's gone with no error and no record: there is no acknowledgement. The intermediate fix is
> `BLMOVE`, which atomically moves the job to a processing list, and then you delete it after success
> and run a reaper for anything stuck there too long — which is you reimplementing a visibility
> timeout. Past that point I'd use Redis Streams with consumer groups, where acknowledgement, pending
> entries and claiming stalled work are built in. And it's worth comparing against the Postgres queue
> with `SKIP LOCKED`, which for moderate volumes is genuinely better because it's transactional with
> the rest of your data and it's one fewer system.

## 🎙️ Articulation drill

**Two minutes: "What's actually in Redis besides `GET` and `SET`?"**

Open with the framing: if you only use strings, you installed a distributed hash map and paid for a
data structure server. Then give the shape of every win — the operation runs next to the data, so a
question that would be a forty-megabyte transfer is two hundred bytes. Spend most of your time on
sorted sets, because they're the answer to the most problems: **one structure, five meanings of the
score** — points for a leaderboard, timestamp for delayed jobs, request time for a sliding-window rate
limit, priority for a queue, and any attribute for a range index — and mention `ZREVRANK` giving you
"you're number four thousand of two million" in microseconds. Then the two arithmetic tricks, because
the numbers land: **a hundred million users' daily actives in twelve and a half megabytes with a
bitmap**, and **twelve kilobytes for any cardinality with HyperLogLog, at the cost of never being able
to ask about one user.** Close on the memory design point — every key costs fifty to a hundred bytes of
overhead, so bucketing millions of keys into hashes cuts memory around fivefold — and the rule you'd
enforce in review: every write sets a TTL or justifies itself.
