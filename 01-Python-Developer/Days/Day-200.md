# Day 200

**L-200** · 🐘 **Partitioning** — ⭐⭐ splitting a table without splitting the application

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: partitioning is a *maintenance* feature that sometimes speeds up
> queries — not a query-speed feature that happens to help maintenance. People adopt it for the
> second reason, are disappointed, and never discover the first.**
>
> ⭐ The headline number: deleting 500 million old rows with `DELETE` takes hours, writes hundreds of
> gigabytes of WAL, bloats the table, and triggers a vacuum storm. ⭐⭐ `DROP TABLE events_2024_01`
> takes **milliseconds** and returns the disk immediately. That is the feature.

---

# Part 1 — ⭐⭐ What it actually buys you, ranked honestly

```
⭐⭐ ① RETENTION AND ARCHIVAL — ⭐⭐ THE REAL REASON. Instant, no WAL, no
⭐    bloat, disk returned to the OS at once. ⭐ `DETACH` first if you
⭐    want to keep the data offline.
⭐⭐ ② MAINTENANCE THAT FITS IN A WINDOW — vacuum, ANALYZE, REINDEX and
⭐    `CREATE INDEX` all operate PER PARTITION. ⭐⭐ A 4 TB table cannot
⭐    be reindexed; forty 100 GB partitions can, one per night.
⭐    ⭐ And autovacuum's scale factor (Day 194) now applies to a 100 GB
⭐      table instead of a 4 TB one — ⭐⭐ so it actually runs.
⭐⭐ ③ SMALLER, HOTTER INDEXES — each partition has its own B-tree.
⭐    ⭐ The current month's index fits in shared buffers; the 2019 one
⭐      is never touched.
⭐⭐ ④ BULK LOAD AND EXPIRY BY SWAP — load into a detached table, index
⭐    it, `ATTACH` it. ⭐ No lock on the live data during the work.
⭐⭐ ⑤ QUERY SPEED VIA PRUNING — ⭐⭐ REAL, BUT USUALLY THE SMALLEST WIN.
⭐    ⭐ A good index already skips the rows a partition would skip.
⭐      Pruning helps most when it eliminates whole INDEXES from
⭐      consideration, or when the query is a large scan of one month.
⭐
⭐ ⇒ ⭐⭐ IF YOUR ONLY REASON IS ⑤, YOU PROBABLY WANT AN INDEX (Day 190)
⭐   OR A BRIN, NOT A PARTITIONED TABLE.
```

```
⭐⭐ AND THE THRESHOLD, STATED AS A NUMBER SO YOU DO NOT ADOPT IT EARLY:
⭐   ⭐ Under ~100 GB, or under ~100M rows: ⭐⭐ DO NOT PARTITION. Use
⭐     indexes, partial indexes, BRIN, and a batched archival job.
⭐   ⭐ Above that, ⭐⭐ AND with a natural partition key that appears in
⭐     almost every query, ⭐ AND with a retention policy: partition.
⭐   ⭐⭐ "WE MIGHT NEED IT LATER" IS NOT A REASON. It constrains your
⭐     primary key (Part 4) from day one.
```

# Part 2 — ⭐ The three strategies

```sql
-- ⭐⭐ RANGE — ~90% of real cases. Time series, events, logs, orders.
CREATE TABLE events (
    id          bigint GENERATED ALWAYS AS IDENTITY,
    tenant_id   int  NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload     jsonb NOT NULL,
    PRIMARY KEY (id, occurred_at)        -- ⭐⭐ SEE PART 4. NOT (id).
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_08 PARTITION OF events
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');   -- ⭐ [from, to)
CREATE TABLE events_default PARTITION OF events DEFAULT; -- ⭐⭐ Part 5

-- ⭐ LIST — a small, stable set: region, tenant tier, event type.
... PARTITION BY LIST (region);
CREATE TABLE events_eu PARTITION OF events FOR VALUES IN ('de','fr','es');

-- ⭐ HASH — even spread with no natural ranges. ⭐⭐ Gives you ② and ③
--   from Part 1 but NOT ① — you cannot drop "old" data from a hash
--   partition, because "old" is not a partition.
... PARTITION BY HASH (tenant_id);
CREATE TABLE events_h0 PARTITION OF events
    FOR VALUES WITH (MODULUS 8, REMAINDER 0);

-- ⭐ SUB-PARTITIONING: range by month, then list by region. ⭐⭐ Legal,
--   and it multiplies your partition count — which is Part 4 ④.
```

# Part 3 — ⭐⭐ Pruning: the rule that decides whether any of this helps

```sql
-- ✅ PRUNED: the partition key is in the WHERE clause
SELECT * FROM events WHERE occurred_at >= '2026-08-01' AND tenant_id = 7;
-- ⭐ EXPLAIN shows ONE partition scanned.

-- ❌ NOT PRUNED: no partition key
SELECT * FROM events WHERE tenant_id = 7;
-- ⭐⭐ EVERY PARTITION IS SCANNED. With 60 monthly partitions you now do
--    60 index scans instead of 1. ⭐⭐ THIS QUERY IS ***SLOWER*** THAN
--    IT WAS BEFORE YOU PARTITIONED.

-- ❌ NOT PRUNED: a function on the partition key (Day 189 ①, again)
WHERE date_trunc('month', occurred_at) = '2026-08-01'
-- ✅ WHERE occurred_at >= '2026-08-01' AND occurred_at < '2026-09-01'
```

```
⭐⭐ SO THE ADOPTION TEST IS ONE QUESTION:
⭐   ***"DOES ALMOST EVERY QUERY FILTER ON THE PARTITION KEY?"***
⭐   ⭐ No ⇒ ⭐⭐ PARTITIONING WILL MAKE YOUR READS WORSE. Choose a
⭐     different key, or do not partition.

⭐ TWO KINDS OF PRUNING, and the second is easy to miss:
⭐   ⭐ PLAN-TIME — the value is a constant. Shows as fewer child nodes.
⭐   ⭐⭐ RUN-TIME — the value is a PARAMETER (`$1`) or comes from the
⭐     outer side of a nested loop. ⭐ `EXPLAIN` alone shows ALL
⭐     partitions; only ⭐⭐ `EXPLAIN ANALYZE` reveals
⭐     `Partitions removed: 59`. ⭐ People panic at the plan and the
⭐     runtime behaviour is fine. Check both.
⭐   ⭐ `enable_partition_pruning` is on by default; if pruning is not
⭐     happening, the cause is your predicate, not a setting.
```

# Part 4 — ⭐⭐ The four things that quietly stop working

## ⭐⭐ ① Every unique constraint must contain the partition key

```sql
PRIMARY KEY (id)                  -- ❌ ⭐⭐ REJECTED on a partitioned
                                  --   table
PRIMARY KEY (id, occurred_at)     -- ✅ ⭐ the partition key is included
-- ⭐ WHY: a unique index is per-partition. Postgres cannot enforce
--   global uniqueness without checking every partition on every insert.
```

```
⭐⭐ AND HERE ARE THE FOUR CONSEQUENCES, WHICH ARE THE REAL COST:
⭐  ⓐ ⭐⭐ YOUR PRIMARY KEY IS NOW COMPOSITE. Every URL, every API
⭐     response, every foreign key and every ORM assumption that "the id
⭐     identifies the row" must change — ⭐ or you accept that `id` is
⭐     unique only by convention (a sequence still generates unique
⭐     values; ⭐⭐ THE DATABASE JUST NO LONGER GUARANTEES IT).
⭐  ⓑ ⭐⭐ `UNIQUE (email)` IS IMPOSSIBLE unless email is the partition
⭐     key. ⭐ If you need a global unique constraint, that table cannot
⭐     be partitioned on something else. Full stop.
⭐  ⓒ ⭐ Day 187's partial unique index for soft deletes, and Day 195's
⭐     "one active per user" — ⭐⭐ both need re-examining, because both
⭐     are unique indexes.
⭐  ⓓ ⭐⭐ AN IDEMPOTENCY KEY (Day 184 #6) IS A UNIQUE CONSTRAINT. If it
⭐     is on a partitioned table, either the key includes the partition
⭐     column or your idempotency guarantee is per-partition — ⭐ which
⭐     is a silent correctness hole, not a limitation.
```

## ⭐ ② Cross-partition updates

```
⭐   UPDATE events SET occurred_at = '2026-09-05' WHERE id = 1;
⭐   ⭐ PG 11+ handles it — ⭐⭐ AS A DELETE FROM ONE PARTITION AND AN
⭐     INSERT INTO ANOTHER. ⭐ Which means: a new ctid, all indexes
⭐     rewritten, `BEFORE UPDATE` triggers on one table and `BEFORE
⭐     INSERT` on the other, and any concurrent `SELECT … FOR UPDATE`
⭐     can raise. ⭐⭐ DESIGN SO THE PARTITION KEY IS IMMUTABLE —
⭐     `occurred_at` should never change anyway.
```

## ⭐ ③ Foreign keys, in both directions

```
⭐   ⭐ A PARTITIONED TABLE REFERENCING another table: ✅ fine.
⭐   ⭐ ANOTHER TABLE REFERENCING a partitioned table: ✅ since PG 12 —
⭐     ⭐⭐ but it must reference the FULL composite key, so your child
⭐     table needs both columns too. ⭐ That propagates the design cost
⭐     outward, which is why event/log tables (nothing references them)
⭐     are the natural candidates and core entities usually are not.
```

## ⭐⭐ ④ Too many partitions

```
⭐   ⭐ Planning must consider every partition it cannot prune at plan
⭐     time; locks are taken per partition; `pg_class` grows.
⭐   ⭐⭐ THE PRACTICAL CEILING: a few hundred is comfortable, a few
⭐     thousand is where planning time and lock overhead become visible,
⭐     and tens of thousands is a different kind of outage — ⭐ where a
⭐     0.2 ms query has 40 ms of planning in front of it.
⭐   ⇒ ⭐⭐ DAILY PARTITIONS × 5 YEARS = 1,825. ⭐ Monthly, with older
⭐     ones detached and archived, is almost always the right shape.
⭐   ⭐ `plan_cache_mode = force_custom_plan` sometimes helps with
⭐     prepared statements over many partitions; ⭐⭐ fewer partitions
⭐     helps more.
```

# Part 5 — ⭐⭐ Operating it (this is where the outages are)

```
⭐⭐ THE CLASSIC OUTAGE, AND IT HAS HAPPENED TO EVERYONE WHO PARTITIONS
⭐   BY HAND:
⭐   ⭐ It is 00:00 on the 1st. No partition exists for the new month.
⭐   ⭐⭐ EVERY INSERT FAILS:
⭐        ERROR: no partition of relation "events" found for row
⭐   ⭐ Your ingestion is down, at midnight, on a date change, which is
⭐     the least-staffed moment there is.

⭐⭐ THE TWO DEFENCES, AND YOU WANT BOTH:
⭐  ① ⭐⭐ A DEFAULT PARTITION — inserts land somewhere instead of
⭐     failing. ⭐⭐ BUT IT IS A SAFETY NET, NOT A HOME: attaching a new
⭐     partition later requires SCANNING THE DEFAULT PARTITION to prove
⭐     no row belongs in the new range, ⭐ and that scan takes ACCESS
⭐     EXCLUSIVE. So a big default partition makes the fix expensive.
⭐     ⇒ ⭐⭐ ALERT ON `count(*) FROM events_default > 0`. Non-zero
⭐       means something is already wrong.
⭐  ② ⭐⭐ AUTOMATION THAT RUNS AHEAD — create partitions 3–6 MONTHS in
⭐     advance, and ⭐⭐ ALERT IF THE FURTHEST-FUTURE PARTITION IS LESS
⭐     THAN 30 DAYS AWAY. ⭐ The alert is the actual control; the cron
⭐     job is just what usually satisfies it.
⭐     ⭐ `pg_partman` does creation + retention properly. Use it unless
⭐       you enjoy writing this.
```

```sql
-- ⭐ Retention, the whole point:
ALTER TABLE events DETACH PARTITION events_2024_01 CONCURRENTLY; -- ⭐ 14+
-- ⭐ now it is an ordinary table: COPY it to object storage, then
DROP TABLE events_2024_01;                    -- ⭐⭐ milliseconds

-- ⭐⭐ ATTACHING WITHOUT A LOCK STORM — the trick worth knowing:
--   `ATTACH PARTITION` normally SCANS the table to prove every row fits
--   the range, holding ACCESS EXCLUSIVE on the parent (Day 196's queue).
CREATE TABLE events_2026_09 (LIKE events INCLUDING ALL);
ALTER TABLE events_2026_09 ADD CONSTRAINT ck_range CHECK (
    occurred_at >= '2026-09-01' AND occurred_at < '2026-10-01');  -- ⭐
-- ⭐ load and index it here, at your leisure
ALTER TABLE events ATTACH PARTITION events_2026_09
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
-- ⭐⭐ POSTGRES SEES THE MATCHING CHECK CONSTRAINT AND ***SKIPS THE
--    SCAN***. The lock is held for milliseconds instead of minutes.
```

```
⭐⭐ CONVERTING AN EXISTING 2 TB TABLE — there is no `ALTER TABLE …
⭐   PARTITION BY`. The two honest paths:
⭐  ⓐ ⭐ NEW TABLE + BACKFILL + SWAP: create `events_new` partitioned,
⭐     dual-write (Day 155's expand/contract), backfill in batches,
⭐     verify counts, rename inside one transaction. ⭐⭐ Slow, safe,
⭐     and reversible at every step.
⭐  ⓑ ⭐⭐ ATTACH THE OLD TABLE AS PARTITION ZERO: create the parent,
⭐     `ATTACH` the entire existing table as the "everything before now"
⭐     partition, and let new partitions take over going forward.
⭐     ⭐ Fast, and you never split the history — ⭐⭐ which means you
⭐     never get retention benefits for the old data. Often fine.
⭐  ⭐ Either way the composite-key change (Part 4 ①) is the hard part,
⭐    and it is an application change, not a database one.
```

```python
# ⭐ SQLAlchemy — the parent is declarative, the partitions are not:
class Event(Base):
    __tablename__ = "events"
    __table_args__ = (
        PrimaryKeyConstraint("id", "occurred_at"),          # ⭐⭐ composite
        {"postgresql_partition_by": "RANGE (occurred_at)"},
    )
# ⭐⭐ THE GOOD NEWS: ORDINARY QUERIES NEED NO CHANGES AT ALL. You
#    SELECT, INSERT and UPDATE against `events` and Postgres routes.
# ⭐ Partition DDL goes in migrations (or pg_partman), not in models.
# ⭐⭐ Django has no native support — `django-postgres-extra`, or manage
#    partitions with raw SQL migrations and leave the model alone.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Partitioning for query speed | It's a maintenance feature. A good index usually does more for reads. |
| Partitioning a 20 GB table | Under ~100 GB, use indexes, BRIN and a batched archival job. |
| Choosing a key that isn't in most `WHERE` clauses | Every query scans every partition — slower than before. |
| A function on the partition key in the predicate | Kills pruning, exactly like it kills index use. |
| Panicking at `EXPLAIN` showing all partitions | Run-time pruning only appears in `EXPLAIN ANALYZE` as `Partitions removed`. |
| Expecting `PRIMARY KEY (id)` to work | Every unique constraint must contain the partition key. |
| Forgetting that an idempotency key is a unique constraint | It becomes per-partition — a silent correctness hole. |
| Letting the partition key be mutable | A cross-partition update is a delete plus an insert. |
| Partitioning a core entity other tables reference | The composite key propagates to every child. Event tables are the natural fit. |
| Daily partitions kept for years | Thousands of partitions turn a 0.2 ms query into 40 ms of planning. |
| Creating partitions by hand | It fails at midnight on the 1st, when nobody is awake. |
| Treating the default partition as a solution | Attaching a new partition then requires scanning it under ACCESS EXCLUSIVE. |
| No alert on furthest-future partition age | The cron job isn't the control; the alert is. |
| `ATTACH PARTITION` without a matching CHECK first | It scans the table holding ACCESS EXCLUSIVE on the parent. |
| Looking for `ALTER TABLE … PARTITION BY` | It doesn't exist. Backfill-and-swap, or attach the old table as one partition. |

## Interview questions

**Q: Why would you partition a table?**

> Mostly for maintenance, not for speed, and that reframing is the whole answer. Retention is the big
> one: deleting five hundred million old rows takes hours, writes hundreds of gigabytes of WAL, bloats
> the table and triggers a vacuum storm, whereas dropping a partition takes milliseconds and returns
> the disk immediately. Then maintenance that fits in a window — vacuum, `ANALYZE`, `REINDEX` and
> index builds all work per partition, so a four-terabyte table that can't be reindexed becomes forty
> hundred-gigabyte ones that can, one a night. And autovacuum's scale factor now applies to the smaller
> table, so it actually triggers. Smaller hot indexes are third, and bulk load by attach is fourth.
> Query pruning is real but usually the smallest win, because a good index already skips the same rows
> — so if pruning is the only reason, I'd add an index or a BRIN instead and not take on the costs.

**Q: What's the biggest design constraint partitioning imposes?**

> Every unique constraint, including the primary key, must contain the partition key — because a
> unique index is per-partition and Postgres can't enforce global uniqueness without checking every
> partition on every insert. So `PRIMARY KEY (id)` becomes `PRIMARY KEY (id, occurred_at)`, and that
> ripples outward: any table referencing it needs both columns, every ORM assumption that the id
> identifies the row has to be revisited, and a genuinely global `UNIQUE (email)` is simply impossible
> unless email is the partition key. The one people miss is that an idempotency key is a unique
> constraint, so on a partitioned table your idempotency guarantee silently becomes per-partition —
> that's a correctness hole rather than an inconvenience. It's also why event and log tables are the
> natural candidates: nothing references them, so the composite key costs almost nothing.

**Q: How do you avoid the midnight-on-the-first outage?**

> Two defences, and you want both. A default partition so inserts land somewhere instead of failing
> with "no partition found for row" — but it's a safety net, not a home, because attaching a proper
> partition later requires scanning the default to prove no row belongs in the new range, and that scan
> holds ACCESS EXCLUSIVE on the parent. So I'd alert on the default partition being non-empty at all,
> since any row in it means something's already wrong. And automation that creates partitions three to
> six months ahead — `pg_partman` rather than hand-rolled — with the actual control being an alert when
> the furthest-future partition is less than thirty days away. The cron job isn't the safeguard; the
> alert that the cron job has stopped working is.

**Q: How do you attach a partition without locking the table?**

> Create the table standalone, add a `CHECK` constraint matching exactly the range you're going to
> attach it with, load and index it at your leisure, and then run `ATTACH PARTITION`. Postgres sees the
> matching check constraint, knows every row must satisfy the range, and skips the validation scan — so
> the ACCESS EXCLUSIVE lock on the parent is held for milliseconds instead of minutes. Without that
> constraint it scans the whole table while holding the lock, and from the lock-queue lesson that means
> every query arriving during the scan queues behind it. On the detach side, `DETACH PARTITION
> CONCURRENTLY` since PG 14 avoids the equivalent problem. I'd still set `lock_timeout` around either
> operation.

**Q: Can you partition an existing two-terabyte table in place?**

> No — there's no `ALTER TABLE ... PARTITION BY`, and that surprises people. There are two honest
> paths. Create a new partitioned table, dual-write to both, backfill in batches, verify counts, and
> swap names inside one transaction — slow, safe, reversible at every step, and it's the expand-contract
> pattern applied to a whole table. Or create the partitioned parent and attach the *existing* table as
> a single "everything before now" partition, letting new partitions take over going forward — which is
> fast and never splits the history, at the price of never getting retention benefits for the old data,
> which is often perfectly acceptable. Either way the hard part isn't the data movement, it's the
> composite primary key, and that's an application change rather than a database one.

## 🎙️ Articulation drill

**Two minutes: "When and how would you partition a table?"**

Open by correcting the usual reason: **it's a maintenance feature, not a query-speed feature** — and
give the number, deleting five hundred million rows takes hours and bloats the table while dropping a
partition takes milliseconds. Add the second maintenance win, that vacuum and reindex become
per-partition so a table too big to maintain becomes forty that aren't. Then the adoption test in one
sentence: does almost every query filter on the partition key? — because if not, you've turned one
index scan into sixty and made reads worse. Then the cost that changes designs: **every unique
constraint must contain the partition key, so your primary key becomes composite and an idempotency
key silently becomes per-partition**, which is why event and log tables are the natural candidates.
Close on operations, because that's where the incidents are: **it fails at midnight on the first when
nobody made next month's partition**, so you want automation running months ahead *and* an alert on the
furthest-future partition, plus a default partition as a net you also alert on.
