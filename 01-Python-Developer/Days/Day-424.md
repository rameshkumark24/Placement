# Day 424 🧾

**P-424** · 🧾 **Structured output as schema design** — ⭐⭐ the schema is part of the prompt

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: your schema is not a container the answer gets poured into afterwards — it
> is read by the model before it generates, so the shape of the schema changes the content of the
> answer, and a schema that forbids uncertainty manufactures confident fabrication.**

---

# Part 1 — The mechanism, restated

```
⭐ ⭐ Day 420 gave the three mechanisms. ⭐⭐ THE ONE THAT MATTERS
⭐   IS CONSTRAINED DECODING: ⭐ at each step the provider masks
⭐   the token distribution so only tokens that keep the JSON
⭐   schema-valid can be sampled (Day 418).
⭐   ⭐⭐ ⇒ SO VALIDITY IS ENFORCED AT THE SAMPLER, NOT REQUESTED
⭐     IN THE PROMPT. ⭐ It cannot fail.

⭐⭐ AND THE CONSEQUENCE PEOPLE DO NOT EXPECT: ***THE SCHEMA IS
⭐   ALSO SENT TO THE MODEL AS TEXT.***
⭐   ⭐ Field names, descriptions, enum values and required-ness
⭐     are all ***in the context***, ⭐⭐ SO THEY ARE PROMPT
⭐     TOKENS THAT CONDITION THE ANSWER.
⭐   ⭐⭐ ⇒ WHICH MEANS: ***RENAMING A FIELD FROM `val` TO
⭐     `total_amount_in_pence` CHANGES THE ANSWER.*** ⭐ Not the
⭐     parsing — ⭐⭐ THE ANSWER. ⭐ The schema is documentation the
⭐     model reads, and it is the cheapest prompt engineering
⭐     available because you were writing it anyway.
```

# Part 2 — ⭐⭐ Six schema design rules

```
⭐⭐ ① ***NAME FIELDS AS INSTRUCTIONS.***
⭐    ⭐ ❌ `date` → ✅ `invoice_date_iso8601`
⭐    ⭐ ❌ `amount` → ✅ `total_cents_excluding_tax`
⭐    ⭐⭐ THE NAME IS FREE PROMPT SPACE AND IT IS RIGHT NEXT TO
⭐      WHERE THE VALUE IS GENERATED.

⭐⭐ ② ***USE `description` — IT IS THE HIGHEST-LEVERAGE FIELD IN
⭐    THE WHOLE SCHEMA.*** ⭐ Pydantic's `Field(description=...)`
⭐    is emitted into the JSON Schema and read by the model.
⭐    ⭐ That is where the edge cases go: ⭐⭐ "IF SEVERAL TOTALS
⭐      APPEAR, USE THE ONE LABELLED 'AMOUNT DUE'."

⭐⭐ ③ ***CONSTRAIN THE VALUE SPACE.*** ⭐ `Literal` and `Enum`
⭐    beat `str` every time. ⭐⭐ A FREE-TEXT `category` FIELD WILL
⭐    EVENTUALLY CONTAIN "Bug ", "bugs", "BUG" AND "possible
⭐    bug" — ⭐ an enum makes those unsampleable.
⭐    ⭐ Same for `ge`, `le`, `pattern`, `max_length`.

⭐⭐ ④ ***KEEP IT FLAT.*** ⭐ Deep nesting degrades quality
⭐    measurably — ⭐⭐ THE MODEL MUST TRACK BRACKET STATE ACROSS
⭐    HUNDREDS OF TOKENS WHILE ALSO DOING THE TASK. ⭐ Two shallow
⭐    calls beat one deeply-nested schema.

⭐⭐ ⑤ ***ORDER FIELDS IN THE ORDER YOU WANT THEM THOUGHT
⭐    ABOUT.*** ⭐ JSON is generated left to right, ⭐⭐ SO EVERY
⭐    FIELD IS CONDITIONED ON THE ONES BEFORE IT. ⭐ Reasoning
⭐    before conclusion (Day 423). ⭐ Evidence before verdict.
⭐    ⭐ Quote before classification.

⭐⭐ ⑥ ***ALWAYS PROVIDE AN ABSTENTION PATH*** — ⭐ and this is the
⭐    day's most important rule:
⭐    ⭐ `Optional[str] = None`, ⭐ an `"unknown"` enum member, ⭐ or
⭐      a `found: bool`.
⭐    ⭐⭐ A SCHEMA WITH `invoice_number: str` (REQUIRED) ON A
⭐      DOCUMENT THAT HAS NO INVOICE NUMBER ***FORCES*** THE MODEL
⭐      TO EMIT A STRING. ⭐ Constrained decoding guarantees it
⭐      will. ⭐⭐ SO IT INVENTS ONE — AND YOU CAUSED THAT
⭐      HALLUCINATION WITH A TYPE ANNOTATION.
⭐    ⭐⭐ ⇒ ***REQUIRED FIELDS MANUFACTURE FABRICATION. THIS IS
⭐      THE SINGLE MOST COUNTERINTUITIVE FACT IN THIS DAY.***
```

# Part 3 — A schema that does real work

```python
from typing import Literal, Optional
from pydantic import BaseModel, Field

class LineItem(BaseModel):
    description: str
    quantity: int = Field(ge=1)
    unit_price_cents: int = Field(ge=0)   # ⭐⭐ MONEY IS INTEGER

class InvoiceExtraction(BaseModel):
    # ⭐⭐ ① EVIDENCE FIRST — conditions everything after it, and
    # ⭐    gives you a free hallucination check (Part 5).
    supporting_quote: str = Field(
        description="Verbatim text from the document containing "
                    "the total. Copy exactly, do not paraphrase.")

    # ⭐⭐ ② THEN THE EXTRACTION, WITH ABSTENTION EVERYWHERE
    invoice_number: Optional[str] = Field(
        None, description="The invoice number as printed. "
                          "null if the document has none.")
    invoice_date_iso8601: Optional[str] = Field(
        None, pattern=r"^\d{4}-\d{2}-\d{2}$",
        description="null if no date is present. Do not guess "
                    "from the filename or today's date.")
    total_cents: Optional[int] = Field(
        None, ge=0,
        description="Total amount due in the smallest currency "
                    "unit. If several totals appear, use the one "
                    "labelled 'Amount Due'. null if unclear.")
    currency: Optional[Literal["GBP", "EUR", "USD", "INR"]] = None
    line_items: list[LineItem] = []

    # ⭐⭐ ③ AND THE FIELD THAT MAKES IT OPERABLE
    confidence: Literal["high", "medium", "low"] = Field(
        description="low if the document is a scan, is partly "
                    "illegible, or does not appear to be an invoice.")
```

```
⭐⭐ WHAT EACH DECISION BUYS:
⭐   ⭐ `supporting_quote` first → ⭐⭐ EVIDENCE-BEFORE-CONCLUSION
⭐     ***AND*** A PROGRAMMATIC CHECK.
⭐   ⭐ `Optional` everywhere → ⭐⭐ ABSTENTION IS EXPRESSIBLE, SO
⭐     FABRICATION IS NOT FORCED.
⭐   ⭐ `pattern` on the date → ⭐ the sampler cannot emit
⭐     "March 3rd".
⭐   ⭐ `description` carrying the tie-break rule → ⭐⭐ THE EDGE
⭐     CASE LIVES NEXT TO THE FIELD RATHER THAN IN A PARAGRAPH
⭐     3,000 TOKENS EARLIER.
⭐   ⭐ `Literal` currency → ⭐ no "pounds", no "£".
⭐   ⭐⭐ `confidence` → ***A ROUTING SIGNAL***: low goes to a
⭐     human or to the strong model (Day 421). ⭐ It is
⭐     self-reported and imperfect, ⭐⭐ AND IT IS STILL FAR BETTER
⭐     THAN NOTHING, AND IT COSTS THREE TOKENS.
```

# Part 4 — ⭐⭐ Validation is a layered defence

```
⭐ ***LAYER 1 — SYNTAX.*** ⭐ Constrained decoding. ⭐⭐ FREE AND
⭐   GUARANTEED. ⭐ Use it wherever the provider offers it.
⭐ ***LAYER 2 — SCHEMA.*** ⭐ Pydantic types, enums, ranges,
⭐   patterns. ⭐⭐ ALSO ENFORCED AT THE SAMPLER WHERE SUPPORTED,
⭐   AND RE-VALIDATED BY YOU ON RECEIPT ANYWAY — ⭐ because you do
⭐   not trust a provider's guarantee with your data integrity.
⭐ ***LAYER 3 — ⭐⭐ BUSINESS RULES. THE ONE THAT ACTUALLY
⭐   CATCHES ERRORS.***
⭐   ⭐ `sum(line_items) == total` ⭐ ← catches arithmetic
⭐     (Day 414)
⭐   ⭐ `invoice_date <= today`
⭐   ⭐⭐ `supporting_quote in source_document` ⭐ ← ***CATCHES
⭐     HALLUCINATION, IN ONE LINE, DETERMINISTICALLY***
⭐   ⭐ `currency` consistent with the vendor's country
⭐   ⭐⭐ THESE ARE ORDINARY PYTHON. NO MODEL INVOLVED. ⭐ They are
⭐     the highest-value validation you will write and they are
⭐     invisible in every tutorial.
⭐ ***LAYER 4 — CROSS-REFERENCE.*** ⭐ Does this invoice number
⭐   exist? ⭐ Does this vendor? ⭐⭐ A DATABASE LOOKUP BEATS ANY
⭐   AMOUNT OF PROMPTING.

⭐⭐ ⇒ ***SCHEMA-VALID IS NOT CORRECT*** (DAY 420). ⭐ Layers 1–2
⭐   guarantee you can parse it. ⭐⭐ LAYERS 3–4 ARE THE ONLY ONES
⭐   THAT TELL YOU IT IS ***TRUE***, ⭐ and they are where the
⭐   engineering is.
```

# Part 5 — The repair loop, and why it should rarely run

```python
async def extract(doc: str, attempts: int = 2) -> InvoiceExtraction:
    msgs = [{"role": "user", "content": PROMPT.render(doc=doc)}]
    for i in range(attempts):
        result = await complete_structured(
            task="invoice_extract", messages=msgs,
            schema=InvoiceExtraction)
        errs = business_rules(result, doc)      # ⭐ LAYER 3
        if not errs:
            return result
        REPAIR_ATTEMPTS.labels(task="invoice_extract").inc()
        # ⭐⭐ FEED THE ***SPECIFIC*** FAILURE BACK. "It's wrong" is
        # ⭐   useless; "line items sum to 4200 but total says
        # ⭐   4500" is actionable.
        msgs += [
            {"role": "assistant", "content": result.model_dump_json()},
            {"role": "user", "content":
             f"These checks failed: {errs}. Correct them. "
             f"If a value cannot be determined, use null."},
        ]
    REPAIR_EXHAUSTED.labels(task="invoice_extract").inc()
    raise ExtractionFailed(errs)   # ⭐⭐ FAIL LOUDLY. DO NOT
                                   # ⭐   RETURN THE BAD RESULT.
```

```
⭐⭐ AND FOUR RULES ABOUT REPAIR THAT MATTER MORE THAN THE CODE:
⭐ ① ⭐⭐ ***ALARM ON THE REPAIR RATE, NOT JUST THE FAILURE
⭐    RATE.*** ⭐ A repair loop is a ***silent quality
⭐    degradation absorber*** — ⭐⭐ IT WILL HIDE A PROMPT
⭐    REGRESSION PERFECTLY WHILE DOUBLING YOUR COST AND LATENCY.
⭐    ⭐ If repairs go from 2% to 30%, ⭐⭐ SOMETHING CHANGED AND
⭐    YOUR ERROR RATE WILL NOT SHOW IT.
⭐ ② ⭐ ***CAP AT TWO ATTEMPTS.*** ⭐⭐ IF IT CANNOT FIX IT TWICE IT
⭐    WILL NOT FIX IT ON THE FIFTH, ⭐ and you are paying 5× for a
⭐    failure.
⭐ ③ ⭐⭐ ***MOST REPAIRS ARE A SCHEMA BUG, NOT A MODEL BUG.***
⭐    ⭐ A high repair rate on one field usually means that field
⭐    has no abstention path (Part 2 ⑥) or an ambiguous
⭐    description. ⭐⭐ FIX THE SCHEMA, DELETE THE REPAIR.
⭐ ④ ⭐ ***NEVER RETURN AN UNVALIDATED RESULT ON EXHAUSTION.***
⭐    ⭐⭐ FAILING IS RECOVERABLE; SILENTLY WRITING A FABRICATED
⭐    INVOICE TOTAL INTO YOUR LEDGER IS NOT (DAY 414).
```

# Part 6 — Extraction patterns worth knowing

```
⭐ ① ⭐⭐ ***EXTRACT WITH SPANS, NOT VALUES.*** ⭐ Ask for the
⭐    verbatim text ***and*** the parsed value. ⭐ Then check the
⭐    span exists in the source. ⭐⭐ THIS TURNS HALLUCINATION FROM
⭐    AN UNMEASURABLE WORRY INTO A BOOLEAN, AND IT IS THE SINGLE
⭐    BEST TECHNIQUE IN THIS DAY.
⭐ ② ⭐ ***ONE PASS PER FIELD GROUP*** for hard documents.
⭐    ⭐⭐ SEPARATE CALLS FOR HEADER FIELDS AND LINE ITEMS BEAT ONE
⭐    CALL DOING BOTH (DAY 423).
⭐ ③ ⭐ ***NORMALISE IN CODE, NOT IN THE PROMPT.*** ⭐ Ask for the
⭐    date as it appears; ⭐⭐ PARSE IT WITH `dateutil`. ⭐ Do not
⭐    ask the model to do timezone arithmetic — ⭐⭐ IT IS
⭐    ARITHMETIC (DAY 414).
⭐ ④ ⭐ ***RETURN A LIST, NOT A SINGLE ITEM***, when zero or many
⭐    are possible. ⭐⭐ AN EMPTY LIST IS A CLEAN "NOT FOUND"; ⭐ a
⭐    required object is not.
⭐ ⑤ ⭐⭐ ***PUT THE PAGE OR CHUNK ID IN THE OUTPUT.*** ⭐ Then a
⭐    human reviewing a low-confidence extraction can go straight
⭐    to the source, ⭐⭐ AND YOUR REVIEW TOOL COSTS AN AFTERNOON
⭐    INSTEAD OF BEING IMPOSSIBLE.
```

# 💬 Interview

**1. ⭐⭐ "Does the schema affect the answer, or just the parsing?"**
> ⭐ Both — and people only expect the second. ⭐⭐ **The schema is sent to the model as text: field
> names, descriptions, enum values and required-ness are all prompt tokens that condition the answer.
> So renaming a field from `val` to `total_amount_in_pence` changes the answer, not just the
> parsing.** ⭐ Which makes the schema the cheapest prompt engineering available, ⭐⭐ **because you were
> writing it anyway** — the field name is free prompt space sitting right next to where the value gets
> generated, and `description` is the highest-leverage field in the whole thing, because that's where
> the tie-break rules go.

**2. ⭐⭐ "How can a schema cause hallucination?"**
> ⭐ By forbidding uncertainty. ⭐⭐ **If `invoice_number: str` is required and the document has no
> invoice number, constrained decoding *guarantees* the model emits a string — so it invents one. You
> caused that fabrication with a type annotation.** ⭐ So every field that might genuinely be absent
> gets an abstention path: `Optional` with a null default, an `unknown` enum member, or a `found`
> boolean. ⭐⭐ **Required fields manufacture fabrication, and that's the most counterintuitive fact
> here.**

**3. "Give me your schema design rules."**
> ⭐ Six. ⭐⭐ **Name fields as instructions, because the name is free prompt space. Use `description` for
> the edge cases, so the rule lives next to the field rather than in a paragraph 3,000 tokens earlier.
> Constrain the value space — `Literal` and `Enum` beat `str`, because a free-text category field will
> eventually contain "Bug ", "bugs", "BUG" and "possible bug". Keep it flat, because deep nesting
> makes the model track bracket state across hundreds of tokens while also doing the task. Order
> fields in the order you want them thought about, since JSON generates left to right and every field
> is conditioned on the ones before it. And always provide an abstention path.**

**4. ⭐⭐ "Structured output guarantees valid JSON. Are you done?"**
> ⭐ No — ⭐⭐ **schema-valid is not correct.** ⭐ Layers one and two, constrained decoding and Pydantic
> types, guarantee I can parse it. ⭐⭐ **Layers three and four are the only ones that tell me it's true:
> business rules — do the line items sum to the total, is the date not in the future, and crucially
> does the supporting quote actually appear in the source document, which catches hallucination in one
> line deterministically — and cross-reference, does this vendor exist in our database.** ⭐ Those are
> ordinary Python with no model involved, ⭐⭐ **they're the highest-value validation you'll write, and
> they're invisible in every tutorial.**

**5. ⭐⭐ "How do you handle a response that fails validation?"**
> ⭐ A repair loop that feeds the *specific* failure back — ⭐⭐ **"it's wrong" is useless, "line items
> sum to 4200 but the total says 4500" is actionable** — capped at two attempts, ⭐⭐ **because if it
> can't fix it twice it won't fix it on the fifth and you're paying 5× for a failure.** ⭐ Four rules
> matter more than the code: ⭐⭐ **alarm on the repair *rate*, because a repair loop is a silent quality
> degradation absorber — it'll hide a prompt regression perfectly while doubling your cost and
> latency, and your error rate won't move. Most repairs are a schema bug rather than a model bug — a
> high repair rate on one field usually means that field has no abstention path, so fix the schema and
> delete the repair. And never return an unvalidated result on exhaustion: failing is recoverable,
> silently writing a fabricated invoice total into your ledger is not.**

**6. "Best extraction technique you know?"**
> ⭐⭐ **Extract spans, not just values — ask for the verbatim text alongside the parsed value, then
> check programmatically that the span exists in the source.** ⭐ That turns hallucination from an
> unmeasurable worry into a boolean. ⭐ After that: ⭐⭐ **normalise in code rather than in the prompt —
> ask for the date as it appears and parse it with `dateutil`, because timezone arithmetic is
> arithmetic and that's the thing models are structurally bad at.** ⭐ And put the page or chunk id in
> the output, ⭐⭐ **so a human reviewing a low-confidence extraction goes straight to the source and your
> review tool costs an afternoon instead of being impossible.**
