```python
class TicketType(Base):
    __tablename__ = "ticket_types"

    event_id: Mapped[int] = mapped_column(ForeignKey("events.id"), index=True)

        CheckConstraint("quantity_sold <= quantity_total", name="ck_no_oversell"),  # ⭐⭐
        CheckConstraint("quantity_sold >= 0", name="ck_sold_nonneg"),
```

```
⭐⭐ WHY `organiser_id` IS ON A CHILD TABLE THAT COULD JOIN TO GET IT:
⭐   ⭐ RLS (Day 160) needs the tenant column ON THE TABLE the policy protects
⭐     — ⭐⭐ a policy cannot join. ⭐ So the tenant is denormalised onto every
⭐     tenant-scoped table, and that is deliberate, not sloppy.
⭐   ⭐⭐ AND THE CONSEQUENCE YOU MUST HANDLE: A DENORMALISED COLUMN CAN GO
⭐     WRONG. ⭐ Add a composite foreign key or a trigger so a `ticket_type`
⭐     cannot point at an event belonging to a different organiser —
⭐     ⭐⭐ otherwise you have built a tenant-crossing bug into the schema.

⭐⭐ THE MIGRATION (Day 138) — three habits from the first one:
⭐   ⭐ READ the autogenerated file before committing. Every time.
⭐   ⭐ `SET lock_timeout = '3s'` at the top of any migration touching a
⭐     populated table — ⭐⭐ start the habit while the tables are empty and it
⭐     costs nothing.
⭐   ⭐⭐ CHECK CONSTRAINTS ARE ADDED `NOT VALID` THEN `VALIDATE` once there is
⭐     data. ⭐ Today the tables are empty so it does not matter — ⭐⭐ which is
⭐     exactly why today is when you learn the pattern.
```

# Part 2 — ⭐⭐ The hold: a reservation that replaces a lock

```python
# services/holds.py            ⭐⭐ imports nothing from fastapi
HOLD_TTL = timedelta(minutes=10)

def create_hold(db: Session, *, user_id: int, ticket_type_id: int, qty: int) -> Hold:
    if qty < 1 or qty > MAX_PER_ORDER:
        raise InvalidQuantity(qty)                            # ⭐ domain error, not HTTP

    tt = db.execute(                                          # ⭐⭐ THE LOCK
        select(TicketType).where(TicketType.id == ticket_type_id).with_for_update()
    ).scalar_one_or_none()
    if tt is None:
        raise NotFound("ticket_type", ticket_type_id)

    expire_stale_holds(db, ticket_type_id)                    # ⭐⭐ Part 3
    if tt.quantity_sold + held_qty(db, ticket_type_id) + qty > tt.quantity_total:
        raise SoldOut(ticket_type_id)                         # ⭐ code: sold_out

    hold = Hold(user_id=user_id, ticket_type_id=ticket_type_id, qty=qty,
                expires_at=now() + HOLD_TTL)
    db.add(hold)
    db.commit()                                               # ⭐⭐ lock released HERE
    return hold
```

```
⭐⭐ FOUR THINGS TO NOTICE, EACH ONE A DELIBERATE DECISION:

⭐  1. ⭐⭐ THE LOCK IS HELD FOR MICROSECONDS AND NEVER ACROSS I/O. ⭐ No HTTP
⭐       call, no email, no cache write inside this transaction (Day 135).
⭐       ⭐⭐ That single discipline is what keeps the on-sale spike from
⭐       serialising into a queue behind one row.
⭐  2. ⭐⭐ AVAILABLE = total − sold − ACTIVE HOLDS. ⭐ Holds must count, or two
⭐       people hold the same last ticket and one of them fails at payment —
⭐       ⭐ which is a worse experience than "sold out" and looks like a bug.
⭐  3. ⭐ `with_for_update()` ON THE `ticket_types` ROW SERIALISES BUYERS OF
⭐       THE SAME TICKET TYPE, and only them. ⭐⭐ Different events do not
⭐       contend at all. ⭐ That is the contention you accepted in ADR-003, and
⭐       Day 168 will measure it.
⭐  4. ⭐⭐ THE SERVICE RAISES DOMAIN ERRORS. `SoldOut`, not `HTTPException`.
⭐       ⭐ The API layer maps them to codes (Day 120); ⭐⭐ the worker on Day
⭐       166 calls the same function and maps them differently.
```

```
⭐⭐ AND THE ALTERNATIVE YOU SHOULD BE ABLE TO ARGUE AGAINST:
⭐   ⭐ "Just use `UPDATE ticket_types SET quantity_sold = quantity_sold + 1
⭐      WHERE id = :id AND quantity_sold + 1 <= quantity_total` and check
⭐      rowcount." ⭐⭐ THIS IS ACTUALLY EXCELLENT — an atomic conditional
⭐      update, no explicit lock, one statement.
⭐   ⇒ ⭐ USE IT FOR THE PURCHASE. ⭐⭐ It does not work for the HOLD, because a
⭐      hold must consider rows in another table, so you need the lock to make
⭐      the read-and-decide atomic.
⭐   ⇒ ⭐⭐ BEING ABLE TO SAY *BOTH* — "conditional update where the state is
⭐      one row, explicit lock where the decision spans tables" — IS THE
⭐      ANSWER THAT SEPARATES PEOPLE HERE.
```

# Part 3 — ⭐⭐ Expiry: the state that must clean itself up

```
⭐⭐ A HOLD THAT NEVER EXPIRES IS INVENTORY PERMANENTLY DESTROYED. ⭐ THREE
⭐   PLACES IT CAN BE RELEASED, AND YOU WANT TWO OF THEM:

⭐  1. ⭐⭐ LAZILY, ON READ — `expire_stale_holds()` inside the locked section.
⭐       ⭐ + always correct at the moment it matters; ⭐⭐ no scheduler needed
⭐         for correctness, only for tidiness
⭐       ⭐ − the row lingers until someone asks
⭐  2. ⭐ A SCHEDULED SWEEP (Day 159) every minute.
⭐       ⭐ + keeps the table small and metrics honest
⭐       ⭐ − ⭐⭐ IT IS NOT THE CORRECTNESS MECHANISM. If you rely on it, then
⭐         a scheduler outage oversells... or undersells, silently.
⭐  3. ⭐ A PARTIAL INDEX + `WHERE expires_at > now()` in every query.
⭐       ⭐⭐ Cleanest of all: nothing to expire, because expiry is COMPUTED.
⭐
⭐   ⇒ ⭐⭐ DO (3) FOR CORRECTNESS AND (2) FOR HYGIENE. ⭐ Day 159's point,
⭐        earned: THE BEST SCHEDULED JOB IS THE ONE YOU DELETED — ⭐⭐ a sweep
⭐        for expired things is usually a missing `expires_at` and a WHERE
⭐        clause. ⭐ Here the sweep survives only to stop the table growing.
```

```sql
-- ⭐ the index that makes the computed version fast
CREATE INDEX ix_holds_active ON holds (ticket_type_id)
  WHERE released_at IS NULL;              -- ⭐⭐ partial: only rows that can matter
```

# Part 4 — ⭐⭐ Purchase: idempotent, atomic, and testable

```python
# services/orders.py
def place_order(db: Session, *, user_id: int, hold_id: int, idem_key: str) -> Order:
    # ⭐⭐ 1. CLAIM THE IDEMPOTENCY KEY ATOMICALLY (Day 122)
    claimed = db.execute(
        insert(Order).values(user_id=user_id, idempotency_key=idem_key,
                             status="pending", hold_id=hold_id)
        .on_conflict_do_nothing(index_elements=["idempotency_key"])
        .returning(Order.id)
    ).scalar_one_or_none()
    if claimed is None:                                   # ⭐ someone already claimed it
        existing = db.scalar(select(Order).where(Order.idempotency_key == idem_key))
        if existing.user_id != user_id:                   # ⭐⭐ key reuse across users
            raise IdempotencyConflict()
        return existing                                    # ⭐ SAME response, no new charge

    # ⭐⭐ 2. CONSUME THE HOLD AND DECREMENT — one atomic conditional update
    hold = db.execute(
        select(Hold).where(Hold.id == hold_id, Hold.user_id == user_id,
                           Hold.released_at.is_(None), Hold.expires_at > now())
        .with_for_update()
    ).scalar_one_or_none()
    if hold is None:
        raise HoldExpired(hold_id)                        # ⭐ code: hold_expired

    updated = db.execute(
        update(TicketType)
        .where(TicketType.id == hold.ticket_type_id,
               TicketType.quantity_sold + hold.qty <= TicketType.quantity_total)  # ⭐⭐
        .values(quantity_sold=TicketType.quantity_sold + hold.qty)
    ).rowcount
    if updated == 0:
        raise SoldOut(hold.ticket_type_id)                # ⭐ the CHECK would have too

    hold.released_at = now()
    order = db.get(Order, claimed)
    order.status = "awaiting_payment"
    db.add(Outbox(topic="order.created", payload={"order_id": order.id}))   # ⭐⭐ Day 142
    db.commit()                                            # ⭐⭐ ONE transaction, all of it
    return order
```

```
⭐⭐ WHAT MAKES THIS FUNCTION CORRECT — say each of these out loud:
⭐   ⭐ THE IDEMPOTENCY CLAIM IS AN INSERT WITH A UNIQUE CONSTRAINT, not a
⭐        SELECT-then-INSERT. ⭐⭐ Two concurrent retries: the database picks a
⭐        winner. ⭐ Day 122's rule — the claim must be the same operation as
⭐        the check.
⭐   ⭐⭐ THE DECREMENT IS A CONDITIONAL UPDATE. Even with no lock at all, it
⭐        cannot oversell — ⭐ the predicate is evaluated by the database at
⭐        write time.
⭐   ⭐ THE `CHECK` CONSTRAINT IS A THIRD LINE OF DEFENCE. ⭐⭐ Lock, predicate,
⭐        constraint. ⭐ Any two can be wrong and you still do not oversell.
⭐   ⭐⭐ THE OUTBOX ROW IS IN THE SAME TRANSACTION AS THE ORDER. ⭐ No dual
⭐        write (Day 142). Either both exist or neither does.
⭐   ⭐ ONE `commit()`, IN THE SERVICE (Day 139). ⭐⭐ Not in the repository,
⭐        not in `get_db`.
```

# Part 5 — ⭐⭐ The test that is the point of today

```python
def test_no_oversell_under_concurrency(engine, seeded_ticket_type):   # ⭐ 10 tickets
    """⭐⭐ 200 threads, 10 tickets. Exactly 10 succeed. Always."""
    results = []
    def buy(i: int):
        with Session(engine) as s:                       # ⭐⭐ REAL sessions, real commits
            try:
                hold = create_hold(s, user_id=i, ticket_type_id=TT, qty=1)
                place_order(s, user_id=i, hold_id=hold.id, idem_key=f"k{i}")
                results.append("ok")
            except (SoldOut, HoldExpired):
                results.append("sold_out")

    with ThreadPoolExecutor(max_workers=50) as ex:
        list(ex.map(buy, range(200)))

    assert results.count("ok") == 10                     # ⭐⭐ EXACTLY. Not "at most".
    with Session(engine) as s:
        tt = s.get(TicketType, TT)
        assert tt.quantity_sold == 10
        assert s.scalar(select(func.count(Ticket.id))) == 10   # ⭐ and no phantom tickets
```

```
⭐⭐ WHY THIS TEST CANNOT USE THE SAVEPOINT FIXTURE (Day 141): every thread
⭐   needs its OWN transaction that really commits, or there is nothing to
⭐   race. ⭐ So this one test gets a real database it truncates afterwards —
⭐   ⭐⭐ and knowing WHICH tests need that and which do not is itself the skill.

⭐⭐ THE OTHER FIVE TESTS THAT MATTER TODAY:
⭐  1. ⭐⭐ RETRIED PURCHASE CHARGES ONCE — same idempotency key twice
⭐       concurrently ⇒ ⭐ one order, one decrement, both callers get the SAME
⭐       order id.
⭐  2. ⭐ AN EXPIRED HOLD CANNOT BE PURCHASED (freeze the clock — Day 133's
⭐       seam is what makes this one line instead of a `sleep(600)`).
⭐  3. ⭐⭐ RELEASING A HOLD RETURNS INVENTORY — hold 10, expire them, and
⭐       confirm 10 are purchasable again.
⭐  4. ⭐ THE OUTBOX ROW EXISTS IFF THE ORDER DOES — force a failure after the
⭐       outbox insert and assert neither survives.
⭐  5. ⭐⭐ TRY TO BREAK THE CONSTRAINT DIRECTLY: `UPDATE ticket_types SET
⭐       quantity_sold = 999` in raw SQL ⇒ ⭐ the database must refuse.
⭐       ⭐⭐ That test proves the guarantee is not in your code.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Testing the purchase path only sequentially | The oversell bug only appears under concurrency. |
| Using the savepoint fixture for the race test | Nothing commits, so nothing races. That test needs real transactions. |
| Asserting "at most 10 sold" | Assert *exactly* 10 — undersell is also a bug. |
| Holding the lock across the payment call | One slow provider serialises every buyer for that event. |
| Available = total − sold, ignoring holds | Two people hold the last ticket; one fails at payment and it looks like a bug. |
| `SELECT` then `INSERT` for idempotency | Two retries both pass the check. The claim must be the check. |
| Idempotency key not scoped to the user | One user replays another's key and reads their order. |
| Decrementing without a conditional predicate | The lock becomes the only defence, and defences should be layered. |
| No `CHECK` constraint | You've put the guarantee somewhere a bug can reach. |
| Enqueueing the confirmation instead of writing an outbox row | Dual write — the order exists and nothing was sent. |
| Committing in the repository | Two calls in one operation become two transactions. |
| `HTTPException` in a service | Day 166's worker calls the same function with nowhere to raise it. |
| Relying on the sweep job for hold expiry | A scheduler outage silently changes your inventory maths. |
| A full index where a partial index fits | Every released hold is indexed forever. |
| Denormalised `organiser_id` with no integrity check | A ticket type pointing at another organiser's event — a tenant crossing built into the schema. |

## Interview questions

**Q: Two people buy the last ticket at the same moment. What happens?**

> Exactly one succeeds, and there are three independent mechanisms making that true. The hold takes
> `SELECT ... FOR UPDATE` on the ticket-type row, so buyers of the *same* ticket type serialise while
> buyers of different events don't contend at all. The purchase decrements with a conditional
> update — `WHERE quantity_sold + qty <= quantity_total` — which the database evaluates at write
> time, so even with no lock it can't oversell; I check `rowcount` and raise sold-out on zero. And
> there's a `CHECK (quantity_sold <= quantity_total)` constraint, so any two of those can be wrong
> and the database still refuses. The point of layering is that my lock can have a bug and my
> constraint cannot. And critically, the lock is held for microseconds and never across the payment
> call — that's what the hold exists for.

**Q: Why a hold rather than locking through the payment?**

> Because payment takes ten to thirty seconds against a third party, and holding a row lock across
> network I/O means one slow provider blocks every buyer for that event behind a single row. A hold
> is a short-lived reservation that replaces a long lock: it makes the inventory decision atomically
> in microseconds, records the reservation with an expiry, and releases the lock. Availability is
> then total minus sold minus active holds — holds have to count, or two people hold the same last
> ticket and one fails at payment, which is a worse experience than "sold out" and looks like a bug.

**Q: How do expired holds get released?**

> Ideally they don't need releasing — expiry is computed rather than swept. Every query filters
> `expires_at > now() AND released_at IS NULL`, backed by a partial index, so an expired hold stops
> counting the instant it expires with nothing having to run. I do also have a sweep job, but only
> for hygiene — to stop the table growing — explicitly not for correctness. That distinction matters:
> if the sweep is the correctness mechanism, then a scheduler outage silently changes my inventory
> maths in one direction or the other, and nothing reports it. It's the general point that a nightly
> job sweeping for expired things is usually a missing timestamp column and a `WHERE` clause.

**Q: How do you know the concurrency is actually correct?**

> A test that runs two hundred threads against ten tickets with real sessions and real commits, and
> asserts exactly ten succeed — exactly, not at most, because underselling is also a bug. That one
> can't use my normal savepoint fixture, since nothing commits there so nothing races; it gets a real
> database it truncates afterwards, and knowing which tests need that is part of the skill. Alongside
> it: a test that fires the same idempotency key twice concurrently and asserts one order with both
> callers getting the same id; a frozen-clock test that an expired hold can't be purchased; a test
> that releasing holds returns inventory; and one that tries to violate the `CHECK` constraint with
> raw SQL, which proves the guarantee doesn't live in my code.

## 🎙️ Articulation drill

**Two minutes: "How do you prevent overselling?"**

Give the three layers and say explicitly why you want all three — the lock can have a bug, the
constraint cannot. Then the piece that shows real experience: the lock is held for microseconds and
never across the payment call, which is what the hold exists for, and holds must count toward
availability or a buyer fails at payment instead of seeing "sold out". Mention the conditional update
and be able to argue both sides — one row, use the predicate; a decision spanning tables, take the
lock. Then close on evidence rather than assertion: **two hundred threads, ten tickets, exactly ten
succeed, run twenty times — because a concurrency test that passes nineteen times out of twenty has
failed.**
