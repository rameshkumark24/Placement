# Part 2 — ⭐⭐ The audit lens: what do you know now?

```
⭐⭐ DO NOT "READ THROUGH IT AND SEE WHAT LOOKS WRONG."
⭐   ⭐ You wrote it, so reading it reconstructs your original
⭐     intention and everything looks fine (Day 262).
⭐   ⇒ ⭐⭐ INSTEAD, AUDIT IT ***ONE STAGE AT A TIME***, ASKING
⭐     A SPECIFIC QUESTION YOU COULD NOT HAVE ASKED IN MARCH:

⭐   ⭐ STAGE 5 — ⭐⭐ WHICH QUERY IS THE WORST, AND WHY? Run
⭐        `EXPLAIN (ANALYZE, BUFFERS)` on the five busiest
⭐        (Day 191). Are the FKs indexed (Day 189)?
⭐   ⭐ STAGE 5 — ⭐⭐ WHAT HAPPENS WITH TWO CONCURRENT BUYERS
⭐        OF THE LAST TICKET? (Days 195–196.)
⭐   ⭐ STAGE 5 — is anything `timestamp` that should be
⭐        `timestamptz`? Any `NOT IN` on a nullable column?
⭐   ⭐ STAGE 7 — where is the transaction boundary, and is
⭐        there a network call inside it (Day 256)?
⭐   ⭐ STAGE 7 — ⭐⭐ IS THERE A DUAL WRITE? (Day 263.)
⭐   ⭐ STAGE 7 — can a request be retried safely (idempotency)?
⭐   ⭐ STAGE 7 — does any scheduled job exist, and would you
⭐        know if it stopped (Day 264)?
⭐   ⭐ STAGE 7 — does a response schema exist, or does it
⭐        serialise the model (Day 257)?
⭐   ⭐ STAGE 7 — is authorisation in the `WHERE` clause, or
⭐        applied after (Day 259)?

⭐ ⇒ ⭐⭐ NINE QUESTIONS, EACH ANSWERED WITH EVIDENCE FROM THE
⭐   RUNNING SYSTEM. ⭐ That is an audit. "It could be cleaner"
⭐   is not.
```

# Part 3 — ⭐⭐ The findings register

```
⭐⭐ ONE ROW PER FINDING. FOUR COLUMNS, AND THE FOURTH IS THE
⭐   ONE THAT MAKES IT ENGINEERING RATHER THAN COMPLAINING:
⭐   | Finding | Evidence | Severity | ⭐⭐ COST TO FIX |

⭐⭐ WHAT YOU WILL ALMOST CERTAINLY FIND IN `ticketed`:
⭐   ⭐⭐ CRITICAL — ***THE OVERSELL RACE.*** You wrote
⭐     `SELECT quantity_remaining … ` then `UPDATE … SET
⭐     quantity_remaining = :n - 1`. ⭐ Two buyers read 1, both
⭐     write 0, ⭐⭐ AND YOU SOLD THE SAME SEAT TWICE. Your
⭐     tests passed because they were sequential.
⭐   ⭐⭐ CRITICAL — no idempotency on the purchase endpoint, so
⭐     a retry or a double-click is a second order.
⭐   ⭐ HIGH — a dual write: the order commits, then the email
⭐     is sent. Crash in between ⇒ silent (Day 263).
⭐   ⭐ HIGH — the order line stores a `ticket_type_id` and the
⭐     receipt joins to the CURRENT price ⇒ ⭐⭐ EDITING A
⭐     PRICE REWRITES OLD RECEIPTS (Day 187).
⭐   ⭐ MEDIUM — unindexed foreign keys; the event listing is
⭐     an N+1; `SELECT *` on a TOASTed description column.
⭐   ⭐ MEDIUM — `timestamp` instead of `timestamptz`.
⭐   ⭐ MEDIUM — offset pagination on the orders list.
⭐   ⭐ LOW — the ORM model is the response schema, so a new
⭐     internal column would leak (Day 257).
⭐   ⭐ LOW — no `/version`, no structured logs, no request id.

⭐ ⇒ ⭐⭐ THE REGISTER IS A DELIVERABLE ON ITS OWN. ⭐ Even the
⭐   findings you never fix are evidence that you can find them,
⭐   ⭐⭐ AND THAT IS THE SKILL BEING ASSESSED.
```

# Part 4 — ⭐⭐ Characterisation tests come first

```
⭐⭐ THE RULE THAT MAKES ALL OF THIS SAFE, AND IT IS THE MOST
⭐   VALUABLE TECHNIQUE ON THIS DAY:
⭐   ***YOU CANNOT SAFELY CHANGE CODE WITH NO TESTS. SO BEFORE
⭐      YOU FIX ANYTHING, WRITE TESTS THAT PIN THE CURRENT
⭐      BEHAVIOUR — ***INCLUDING THE BEHAVIOUR YOU THINK IS
⭐      WRONG***.

⭐   ⭐ A characterisation test does not assert what SHOULD
⭐     happen. ⭐⭐ IT ASSERTS WHAT ***DOES*** HAPPEN, so that
⭐     any change becomes visible as a diff rather than as a
⭐     surprise in production.
⭐   ⭐ Write one, run it, and if it fails, ⭐⭐ CHANGE THE
⭐     TEST TO MATCH REALITY — you are recording, not judging.
⭐   ⇒ ⭐ Then, when you fix the bug, ⭐⭐ THE CHARACTERISATION
⭐     TEST FAILS, AND YOU UPDATE IT ***DELIBERATELY***, IN THE
⭐     SAME COMMIT AS THE FIX. ⭐ That commit is now a precise
⭐     record of a behaviour change.

⭐⭐ AND FOR THE OVERSELL BUG SPECIFICALLY, THE FIRST TEST IS
⭐   THE ONE THAT PROVES THE BUG EXISTS:
⭐   ⭐ 50 threads, one ticket left, real Postgres (Day 261) —
⭐     ⭐⭐ ASSERT THAT MORE THAN ONE SUCCEEDS. ⭐ It will.
⭐   ⇒ ⭐⭐ A FAILING-BY-DESIGN TEST THAT DEMONSTRATES A REAL
⭐     PRODUCTION BUG IS THE SINGLE MOST PERSUASIVE ARTEFACT
⭐     YOU CAN PUT IN A PULL REQUEST.
```

# Part 5 — ⭐⭐ The three fixes worth doing, each with its proof

```
⭐⭐ ① THE OVERSELL RACE — ***FIX IT IN THE DATABASE***
⭐   ⭐ ❌ NOT with a Python lock (one process only), not with
⭐     `SELECT FOR UPDATE` alone (correct but serialises), and
⭐     ⭐⭐ NOT WITH A CHECK IN THE SERVICE (that is where the
⭐     bug already is).
⭐   ⭐ ✅ An atomic conditional write, plus a constraint:
⭐        UPDATE ticket_types
⭐           SET quantity_sold = quantity_sold + :n
⭐         WHERE id = :id
⭐           AND quantity_sold + :n <= quantity_total;
⭐        -- ⭐⭐ plus CHECK (quantity_sold <= quantity_total)
⭐   ⇒ ⭐⭐ ROWS AFFECTED = 0 MEANS SOLD OUT (Day 264's rule:
⭐     drive the outcome from what the write CHANGED).
⭐   ⇒ ⭐ THE CHECK CONSTRAINT IS THE POINT: it makes the bug
⭐     ⭐⭐ IMPOSSIBLE RATHER THAN UNLIKELY, including from a
⭐     migration, a script, or the next endpoint someone adds.
⭐   ⭐ PROOF: the 50-thread test now asserts exactly one
⭐     success — and you flip the assertion in the same commit.

⭐⭐ ② IDEMPOTENCY ON PURCHASE
⭐   ⭐ A client-supplied key, a unique index, and the stored
⭐     response returned on a repeat (Day 260).
⭐   ⭐ PROOF: two identical concurrent requests ⇒ one order,
⭐     two identical responses.

⭐⭐ ③ THE DUAL WRITE ⇒ THE OUTBOX (Day 263)
⭐   ⭐ The order row and the `OrderPlaced` row commit together;
⭐     a relay sends the email.
⭐   ⭐ PROOF: kill the process between commit and send, and
⭐     assert the email is still sent after restart.

⭐ ⇒ ⭐⭐ NOTE WHAT ALL THREE HAVE IN COMMON: EACH IS A SMALL,
⭐   LOCAL CHANGE WITH A TEST THAT DEMONSTRATES THE PROBLEM AND
⭐   THEN DEMONSTRATES THE FIX. ⭐ None of them required
⭐   rewriting anything.
```

# Part 6 — ⭐⭐ What you deliberately do not fix

```
⭐⭐ THE HARD PART OF AN AUDIT IS STOPPING.
⭐   ⭐ You now know enough to find fifty things. ⭐ Fixing all
⭐     of them is a rewrite wearing a disguise, and it takes
⭐     three weeks and produces a system with NEW bugs and no
⭐     characterisation tests for them.

⭐⭐ THE TRIAGE RULE:
⭐   ⭐ CRITICAL (data loss, money, security) ⇒ fix now.
⭐   ⭐ HIGH (silent failure, wrong data) ⇒ fix now.
⭐   ⭐⭐ MEDIUM (performance at a scale you do not have) ⇒
⭐     ***WRITE IT DOWN WITH THE TRIGGER*** — "the events list
⭐     is an N+1; it is fine at 40 events and needs fixing
⭐     before 500."
⭐   ⭐ LOW (style, ergonomics) ⇒ fix opportunistically, when
⭐     you are already in that file.

⭐ ⇒ ⭐⭐ "I FOUND IT, I MEASURED IT, AND I DECIDED NOT TO FIX
⭐   IT YET — HERE IS THE TRIGGER THAT WOULD CHANGE THAT" IS A
⭐   ***STRONGER*** ANSWER THAN HAVING FIXED IT. ⭐ It shows
⭐   you can hold a known problem without either panicking or
⭐   forgetting.
```

# Part 7 — ⭐ Shipping a fix to a running system

```
⭐   ⭐ EVERY CHANGE HERE IS A ***MIGRATION AGAINST LIVE DATA***
⭐     (Day 283), which is why the fixes are ordered:
⭐     ① ⭐⭐ ADD THE CHECK CONSTRAINT `NOT VALID` FIRST, then
⭐        `VALIDATE` — ⭐⭐ AND IF VALIDATION FAILS, YOU HAVE
⭐        JUST DISCOVERED THAT YOU ***ALREADY*** OVERSOLD
⭐        SOMETHING, which is a finding in its own right and
⭐        needs a data fix before the code fix.
⭐     ② the atomic UPDATE is backward-compatible — old code
⭐        and new code can run together (Day 283).
⭐     ③ the outbox table is additive; the relay is a new
⭐        process; nothing existing changes.
⭐   ⭐ And a backfill, if you need one, is a job — never part
⭐     of the migration (Day 264).

⭐ ⇒ ⭐⭐ NOTICE THAT THE ***ORDER*** OF THE FIXES WAS DECIDED
⭐   BY DEPLOYABILITY, NOT BY SEVERITY. ⭐ That distinction is
⭐   most of what "experienced" means here.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| "I'd rewrite it" | The answer of someone who has never kept a system running. |
| Contempt for your own old code | It was written by someone without your context — the permanent condition of all code. |
| Reading it to see what looks wrong | You wrote it; reading reconstructs the intention and it all looks fine. |
| Auditing without evidence | "It could be cleaner" isn't a finding. Run `EXPLAIN`, run the race. |
| A findings list with no cost column | That's complaining, not engineering. |
| Changing code before writing tests | You have no way to see what you broke. |
| Characterisation tests asserting what *should* happen | They record what does happen, including the bug. |
| Fixing the race in the service layer | That's where the bug already is. Put it in the database. |
| `SELECT FOR UPDATE` as the only fix | Correct but serialises; an atomic conditional write is better. |
| No `CHECK` constraint | The bug stays possible from a script, a migration, or the next endpoint. |
| Fixing everything you found | A rewrite in disguise, with new bugs and no characterisation tests. |
| Fixing mediums with no trigger recorded | You'll rediscover it in a year, at scale, under pressure. |
| Ordering fixes by severity alone | Order by deployability; some fixes enable others. |
| Adding a constraint without `NOT VALID` first | And if validation fails, you just found existing bad data. |
| Backfilling inside a migration | It's a job (Day 264). |
| Not writing the audit up | The comparison is the only artefact that shows change over time. |

## Interview questions

**Q: You inherit a system with a serious bug. What's your first move?**

> Write a test that demonstrates it, before touching any code. For the oversell bug in my ticketing
> project that's fifty threads against one remaining ticket on real Postgres, asserting that more than
> one succeeds — a failing-by-design test that proves a real production bug, which is the most
> persuasive thing you can put in a pull request. More generally I write characterisation tests first:
> tests that pin what the code *does*, including the behaviour I think is wrong, so that any change
> shows up as a deliberate diff rather than a surprise. Then when I fix it, the characterisation test
> fails and I update it in the same commit, which makes that commit an exact record of a behaviour
> change.

**Q: How did you find the problems?**

> Not by reading it, because I wrote it — reading reconstructs my original intention and everything
> looks reasonable. I audited it one topic at a time with questions I couldn't have asked when I built
> it: run `EXPLAIN ANALYZE` on the five busiest queries, check whether foreign keys are indexed, ask
> what happens with two concurrent buyers of the last ticket, look for a dual write, ask whether a
> retry is safe, and ask whether I'd know if a scheduled job stopped. Nine specific questions, each
> answered with evidence from the running system. "It could be cleaner" isn't a finding.

**Q: What did you fix, and what did you leave?**

> I fixed three things: the oversell race, with an atomic conditional update plus a check constraint
> so it's impossible rather than unlikely; idempotency on the purchase endpoint; and the dual write
> between the order and the confirmation email, using an outbox. Each one is small, local, and has a
> test that demonstrates the problem and then the fix. I left the N+1 on the event listing, the offset
> pagination and a handful of type issues — recorded with triggers, like "fine at forty events, needs
> fixing before five hundred". Fixing all fifty things I found would have been a rewrite in disguise,
> with new bugs and no characterisation tests for them.

**Q: Why is the check constraint the important part of that fix?**

> Because the atomic update fixes the code path I know about, and the constraint fixes every path,
> including the migration someone writes next year, an admin script, and the second purchase endpoint
> somebody adds for a partner integration. It moves the guarantee from "this function is careful" to
> "this state cannot exist". And adding it taught me something extra: I added it `NOT VALID` and then
> validated, and if validation had failed that would itself have been a finding — evidence that I'd
> already oversold something and needed a data fix before a code fix.

## 🎙️ Articulation drill

**Three minutes: "Tell me about a time you improved code you didn't write."**

Use the framing first, because it sets the register: **"I'd rewrite it" is the answer of someone who
has never had to keep a system running.** Describe the situation honestly — a system you built before
you knew what you know now, which is the permanent condition of all code, including today's. Then the
method: **you can't find bugs by reading, because reading reconstructs the intention**, so you audit
one topic at a time with specific questions — the worst query by `EXPLAIN`, unindexed foreign keys,
two concurrent buyers of the last ticket, a dual write, whether a retry is safe, whether you'd know if
a job stopped. Then the technique that makes changing it safe: **characterisation tests that pin what
the code does, including the behaviour you think is wrong** — and for the race, a fifty-thread test
that asserts more than one purchase succeeds, which is a failing-by-design test proving a real
production bug. Describe the fix and put the emphasis in the right place: the atomic conditional
update fixes the path you know about, **but the `CHECK` constraint makes the bug impossible rather
than unlikely** — including from a script or the next endpoint someone adds. Close on triage, because
that's the senior part: **you now know enough to find fifty things, and fixing all of them is a rewrite
in disguise** — so criticals and highs get fixed, mediums get written down with a trigger, and "I found
it, measured it, and chose to wait" is a stronger answer than a heroic weekend.
