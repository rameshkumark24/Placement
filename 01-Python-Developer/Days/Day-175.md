# Day 175

**L-175** · 🎸 **Django REST Framework I** — ⭐⭐ serializers, and why they are not Pydantic models

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a Pydantic model parses input into a typed object and stops; a DRF
> serializer parses, validates against the database, and then *writes* — so it is three
> responsibilities in one class, and every DRF pain you will ever have comes from that.**
>
> ⭐ Day 131 said parse, don't validate, and keep three models per resource. ⭐⭐ DRF's design predates
> that consensus and makes the opposite bet. **Understanding the bet is how you use DRF well.**

---

# Part 1 — ⭐⭐ Serializer vs Pydantic model

```python
# ⭐ PYDANTIC (Day 131) — parse in, parse out, two classes, no database
class OrderIn(BaseModel):
    ticket_type_id: int
    qty: int = Field(gt=0, le=10)

class OrderOut(BaseModel):
    id: int
    status: str
    total_cents: int

# ⭐ DRF — one class, both directions, and it saves
class OrderSerializer(serializers.ModelSerializer):
    class Meta:
        model = Order
        fields = ["id", "ticket_type", "qty", "status", "total_cents"]
        read_only_fields = ["id", "status", "total_cents"]     # ⭐⭐ Part 2
```

```
⭐⭐ THE FOUR DIFFERENCES THAT MATTER IN PRACTICE:

⭐  1. ⭐⭐ DIRECTION. Pydantic: input and output are DIFFERENT CLASSES. DRF:
⭐       ONE class does both, split by `read_only` / `write_only`.
⭐       ⭐ + less duplication · ⭐⭐ − the input contract and the output
⭐       contract are entangled, so ⭐ adding an output field can accidentally
⭐       make it writable (Part 2's mass-assignment hazard).
⭐
⭐  2. ⭐⭐ IT WRITES. `serializer.save()` calls `.create()` or `.update()`.
⭐       ⭐ Pydantic never touches a database. ⭐⭐ This is DRF's single biggest
⭐       design decision: PERSISTENCE IS IN THE SERIALIZER.
⭐
⭐  3. ⭐⭐ VALIDATION CAN QUERY. `UniqueValidator` runs a SELECT.
⭐       `PrimaryKeyRelatedField` runs a SELECT to resolve an id into an
⭐       object. ⭐ Pydantic validators must not hit a database (Day 131);
⭐       ⭐⭐ DRF validators routinely do — which is genuinely convenient and
⭐       is also why a serializer with ten related fields runs ten queries.
⭐
⭐  4. ⭐ PERFORMANCE. Pydantic v2 executes in Rust; ⭐⭐ DRF serializers are
⭐       pure Python and are frequently the bottleneck on a large list
⭐       response. ⭐ For a 10,000-row export, serialization can exceed the
⭐       query time — ⭐⭐ `.values()` + a manual dict is often 5–10× faster,
⭐       and that is a legitimate optimisation, not a hack.
⭐
⭐   ⇒ ⭐⭐ THE SUMMARY TO SAY: **DRF SERIALIZERS ARE FORMS FOR APIs.** ⭐ That
⭐        is their lineage — they descend from `ModelForm`, not from a parsing
⭐        library — and every design choice follows from it.
```

# Part 2 — ⭐⭐ `ModelSerializer`, and its two dangerous conveniences

```
⭐⭐ DANGER 1 — `fields = "__all__"`. NEVER USE IT.
⭐   ⭐ it serialises every field, ⭐⭐ INCLUDING ONES ADDED LATER BY SOMEONE
⭐        ELSE. ⭐ Add `internal_notes` or `password_hash` to the model, and it
⭐        appears in your API response, with no code change and no review of
⭐        the API.
⭐   ⇒ ⭐⭐ Day 119: THE OUTPUT SCHEMA IS A SECURITY CONTROL. `__all__` deletes
⭐        the control. ⭐ List fields explicitly, always, and let the diff be
⭐        the review.
⭐
⭐⭐ DANGER 2 — WRITABLE BY DEFAULT ⇒ MASS ASSIGNMENT (Day 119).
⭐   ⭐ every listed field is WRITABLE unless marked otherwise.
⭐   ⭐⭐ So `PATCH /orders/1 {"status": "paid", "total_cents": 0}` SUCCEEDS
⭐        unless you remembered `read_only_fields`.
⭐   ⇒ ⭐⭐ AND THE ONE THAT IS AN ACTUAL BREACH: `organiser` or `user` as a
⭐        writable field ⇒ ⭐ a client sets `{"user": 42}` and creates an order
⭐        for someone else. ⭐⭐ Server-owned fields are `read_only`, and the
⭐        real value comes from `request.user`:
⭐          def perform_create(self, serializer):
⭐              serializer.save(user=self.request.user)   # ⭐⭐ never from input
⭐
⭐   ⇒ ⭐⭐ THE HABIT: START FROM `read_only_fields` CONTAINING EVERYTHING
⭐        SERVER-OWNED, AND WRITE THE EXPLICIT FIELD LIST. ⭐ Two lines that
⭐        remove an entire vulnerability class.
```

```python
# ⭐⭐ THE THREE-SERIALIZER SHAPE — Day 131's rule, in DRF
class OrderCreateSerializer(serializers.ModelSerializer):
    class Meta:
        model = Order
        fields = ["ticket_type", "qty"]          # ⭐⭐ no id, no user, no status
class OrderUpdateSerializer(serializers.ModelSerializer):
    class Meta:
        model = Order
        fields = ["qty"]                          # ⭐ what may actually change
class OrderReadSerializer(serializers.ModelSerializer):
    user = UserBriefSerializer(read_only=True)
    class Meta:
        model = Order
        fields = ["id", "user", "qty", "status", "total_cents", "created_at"]

# ⭐ and select by action, which is the DRF idiom
def get_serializer_class(self):
    return {"create": OrderCreateSerializer,
            "update": OrderUpdateSerializer,
            "partial_update": OrderUpdateSerializer}.get(self.action, OrderReadSerializer)
```

> ⭐⭐ **The differences between those three classes are the value, exactly as in Day 131.** ⭐ Create
> has no `id` and no `user` — that's mass assignment closed. Update has only what may change. Read
> omits nothing you want but includes nothing you didn't choose.

# Part 3 — ⭐⭐ Validation: four levels, and where each belongs

```python
class OrderCreateSerializer(serializers.ModelSerializer):
    qty = serializers.IntegerField(min_value=1, max_value=10)     # ⭐ 1. FIELD

    def validate_qty(self, value):                                # ⭐ 2. ONE FIELD
        if value % 2 and self.context["request"].user.is_restricted:
            raise serializers.ValidationError("odd quantities not allowed")
        return value

    def validate(self, attrs):                                    # ⭐⭐ 3. CROSS-FIELD
        if attrs["ticket_type"].event.has_ended:
            raise serializers.ValidationError({"ticket_type": "event has ended"})
        return attrs

    class Meta:
        validators = [UniqueTogetherValidator(                    # ⭐ 4. OBJECT-LEVEL
            queryset=Order.objects.all(), fields=["user", "ticket_type"])]
```

```
⭐⭐ THE RULES THAT KEEP THIS FROM BECOMING A MESS:

⭐  1. ⭐⭐ `validate_<field>` RECEIVES **ONE** FIELD. If you need two, you need
⭐       `validate()` — ⭐ and reaching for `self.initial_data` inside a
⭐       single-field validator is the anti-pattern, because it is UNVALIDATED
⭐       raw input.
⭐  2. ⭐ RAISE `serializers.ValidationError`, never `HTTPException`, never a
⭐       bare `ValueError`. ⭐⭐ Only the first produces a 400 with your field
⭐       structure; the others become a 500.
⭐  3. ⭐⭐ `validate()` MAY QUERY, AND THAT IS THE TRAP. ⭐ "Is this ticket
⭐       still available?" in a validator is a CHECK, and by the time
⭐       `.save()` runs the answer may have changed — ⭐⭐ TOCTOU. ⭐ Business
⭐       invariants under concurrency belong in the SERVICE, inside the
⭐       transaction (Day 164), with a conditional update or a lock.
⭐       ⭐⭐ A validator can say "sold out" politely; only the service can
⭐       guarantee it.
⭐  4. ⭐ ⭐⭐ VALIDATION IS SKIPPED ENTIRELY IF YOU CALL `Model.objects.create()`
⭐       DIRECTLY. ⭐ Day 172: `save()` does not validate. ⭐⭐ So a management
⭐       command, a signal or a migration bypasses every rule above — which is
⭐       why real invariants belong in `Meta.constraints`.

⭐⭐ AND THE ERROR SHAPE (Day 120): DRF'S DEFAULT IS
⭐        `{"qty": ["Ensure this value is >= 1."], "non_field_errors": [...]}`
⭐   ⭐ Field-keyed, which is good for forms. ⭐⭐ But it has NO machine-readable
⭐        `code` at the top level, and `non_field_errors` is a magic string.
⭐   ⇒ ⭐ Write a CUSTOM `EXCEPTION_HANDLER` that wraps every response in one
⭐        shape with a stable `code`, ⭐⭐ exactly as you overrode
⭐        `RequestValidationError` in FastAPI (Day 130). ⭐ One shape, one
⭐        place, decided once.
```

# Part 4 — ⭐⭐ Nested serializers: the famous pain

```python
class OrderReadSerializer(serializers.ModelSerializer):
    items = ItemSerializer(many=True, read_only=True)    # ⭐ READ: easy and fine
```

```
⭐⭐ READING NESTED DATA IS TRIVIAL. **WRITING IT IS NOT SUPPORTED**, and DRF
⭐   says so explicitly: ⭐ a nested serializer is `read_only` unless you write
⭐   `.create()` and `.update()` yourself.

⭐   ⭐⭐ WHY DRF REFUSES — and the reasons are good ones:
⭐    ⭐ what does `PATCH {"items": [...]}` MEAN? ⭐⭐ Replace all? Merge by id?
⭐         Delete the omitted ones? ⭐ There is no correct default, and each
⭐         answer is a different API.
⭐    ⭐ nested writes need ONE transaction across several models ⇒ ⭐⭐ a
⭐         serializer is now orchestrating a multi-table operation, which is
⭐         a service's job.
⭐    ⭐ partial updates of nested collections are genuinely ambiguous in REST.
⭐
⭐   ⇒ ⭐⭐ THE THREE ANSWERS, BEST FIRST:
⭐    1. ⭐⭐ **DON'T.** Make the nested thing its own endpoint:
⭐         `POST /orders/{id}/items/`. ⭐ Simpler, obvious semantics,
⭐         separately permissioned, ⭐⭐ and it is what most good APIs do.
⭐    2. ⭐ Write `.create()` yourself, ⭐⭐ delegating to a service function
⭐         wrapped in `atomic` — ⭐ the serializer parses, the service writes.
⭐    3. ⭐ `drf-writable-nested` — ⭐⭐ it works and it makes the ambiguity
⭐         implicit, which is the thing you were trying to avoid.
```

```python
# ⭐ if you must: the serializer PARSES, the service WRITES
class OrderCreateSerializer(serializers.Serializer):     # ⭐⭐ plain, not Model-
    ticket_type_id = serializers.IntegerField()
    qty = serializers.IntegerField(min_value=1, max_value=10)

    def create(self, validated_data):
        return place_order(user=self.context["request"].user, **validated_data)
        # ⭐⭐ one call into a service that owns the transaction (Day 164)
```

> ⭐⭐ **This is the shape to prefer for anything non-trivial: a plain `Serializer` for parsing, and a
> service function for the operation.** ⭐ You keep DRF's validation and browsable API, and you keep
> your transaction boundary where Day 139 put it — which is the best of both designs.

# Part 5 — ⭐ ViewSets, routers, and the N+1 that ships by default

```python
class OrderViewSet(viewsets.ModelViewSet):
    permission_classes = [IsAuthenticated]
    def get_queryset(self):
        return (Order.objects
                .for_user(self.request.user)              # ⭐⭐ scoping, Day 118
                .select_related("user")                   # ⭐⭐ Day 171
                .prefetch_related("items"))
    def perform_create(self, serializer):
        serializer.save(user=self.request.user)           # ⭐ never from input

router = DefaultRouter()
router.register("orders", OrderViewSet)          # ⭐ list/create/retrieve/update/destroy
```

```
⭐⭐ WHAT A ROUTER GIVES YOU — and it is a lot:
⭐   ⭐ five URLs with correct methods and 405s · ⭐ consistent naming ·
⭐        ⭐ `@action(detail=True)` for custom routes · ⭐⭐ a browsable API that
⭐        is genuinely useful for exploring an API by hand.

⭐⭐ AND THE FOUR THINGS THAT GO WRONG:
⭐  1. ⭐⭐ **THE DEFAULT `queryset` IS AN N+1 WAITING TO SHIP.** ⭐ A
⭐       `ModelViewSet` with `queryset = Order.objects.all()` and a serializer
⭐       with any nested field is 1+N by construction. ⭐⭐ It works in
⭐       development with 5 rows and dies at 500 — ⭐ EVERY loading strategy
⭐       must be in `get_queryset`, and every list endpoint needs
⭐       `assertNumQueries` (Day 171).
⭐  2. ⭐⭐ **`get_queryset` IS THE ONLY PLACE TENANT SCOPING BELONGS.** ⭐ Not
⭐       `get_object`, not a permission class. ⭐⭐ If the queryset is scoped,
⭐       then a wrong id is a 404 rather than a 403 (Day 118), and there is no
⭐       code path that can return another user's row. ⭐ Object permissions
⭐       are a second layer, not the first.
⭐  3. ⭐ ⭐⭐ `ModelViewSet` GIVES YOU `DELETE` WHETHER YOU WANTED IT OR NOT.
⭐       ⭐ Registering a viewset publishes five endpoints; ⭐⭐ if destroy is
⭐       not part of your API, use `ReadOnlyModelViewSet` or compose the
⭐       mixins you actually want. ⭐ "It was in the default" is how a
⭐       destructive endpoint ships unnoticed.
⭐  4. ⭐ PAGINATION IS OFF BY DEFAULT. ⭐⭐ `Order.objects.all()` with no
⭐       `DEFAULT_PAGINATION_CLASS` returns every row, forever. ⭐ Set it
⭐       globally, with a `max_page_size` (Day 121).
⭐
⭐   ⇒ ⭐⭐ THE ONE-LINE SUMMARY OF DRF: **IT IS EXCELLENT WHEN YOUR API IS
⭐        YOUR MODELS, AND IT FIGHTS YOU WHEN IT IS NOT.** ⭐ For a
⭐        model-shaped CRUD API it is faster than anything else. ⭐⭐ For an
⭐        operation-shaped API — `place_order`, `refund`, `capture` — use
⭐        `APIView` or `@action` with a plain serializer and a service, and
⭐        stop trying to make a resource out of a verb.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `fields = "__all__"` | A field someone adds later appears in your API with no review. |
| Relying on `ModelSerializer` defaults for writability | Everything listed is writable — including `user`, which is a breach. |
| Trusting `user` or `organiser` from input | Server-owned fields are `read_only`; set them in `perform_create` from `request.user`. |
| One serializer for create, update and read | The differences between them are the security value. |
| `self.initial_data` inside `validate_<field>` | That's unvalidated raw input. Use `validate()`. |
| Raising `HTTPException` or `ValueError` in a validator | Only `ValidationError` becomes a 400; the others are 500s. |
| Enforcing a concurrency invariant in `validate()` | TOCTOU — the answer can change before `save()`. That belongs in the service transaction. |
| Assuming validators run on `Model.objects.create()` | They don't. Real invariants go in `Meta.constraints`. |
| Accepting DRF's default error shape | No top-level machine-readable code. Write a custom exception handler. |
| Trying to make nested writes work | DRF refuses for good reasons. Use a sub-resource endpoint or a service. |
| `queryset = Model.objects.all()` on a ViewSet | An N+1 by construction — fine at 5 rows, fatal at 500. |
| Scoping tenants in `get_object` or a permission class | It belongs in `get_queryset`, so a wrong id is a 404 and no path can leak. |
| Registering `ModelViewSet` without thinking about `destroy` | You just published a delete endpoint nobody reviewed. |
| No default pagination | `all()` returns every row, forever. |
| Serializing 10,000 rows with a `ModelSerializer` | Pure Python and often the bottleneck. `values()` plus dicts is 5–10× faster. |
| Forcing an operation into a resource | `place_order` is a verb. Use `APIView`/`@action` with a service. |

## Interview questions

**Q: How is a DRF serializer different from a Pydantic model?**

> A Pydantic model parses input into a typed object and stops. A DRF serializer parses, validates —
> often by querying the database — and then *writes*, because `serializer.save()` calls `create` or
> `update`. So it's three responsibilities in one class, and it handles both directions with
> `read_only`/`write_only` rather than having separate input and output classes. Its lineage explains
> it: serializers descend from `ModelForm`, not from a parsing library — they're forms for APIs.
> That's convenient, and the costs are real: the input and output contracts are entangled, so adding
> an output field can accidentally make it writable; a serializer with several related fields runs a
> query per field; and it's pure Python, so on a large list response serialization can exceed the
> query time, which is why `values()` plus manual dicts is a legitimate optimisation.

**Q: What's dangerous about `ModelSerializer`?**

> Two defaults. `fields = "__all__"` means a field someone adds to the model six months later appears
> in your API response with no code change and no review — and the output schema is a security
> control, so that deletes the control. And everything listed is *writable* unless marked otherwise,
> which is mass assignment: a client can PATCH `status` or `total_cents`, and worse, if `user` or
> `organiser` is writable they can create an order belonging to someone else. So: explicit field
> lists always, `read_only_fields` containing everything server-owned, and the actual owner set in
> `perform_create` from `request.user` rather than from input. I'd also use three serializers per
> resource selected by action, because the differences between create, update and read are exactly
> where that security value lives.

**Q: Why can't you do nested writes in DRF?**

> Because there's no correct default and DRF declines to invent one. What does `PATCH {"items":
> [...]}` mean — replace everything, merge by id, delete what's omitted? Each answer is a different
> API. And a nested write needs one transaction across several models, which makes the serializer an
> orchestrator of a multi-table operation, which is a service's job. My preferred answer is not to:
> make it a sub-resource, `POST /orders/{id}/items/`, which has obvious semantics and can be
> permissioned separately. If it has to be one call, I use a plain `Serializer` for parsing and
> delegate to a service function wrapped in `atomic` — the serializer parses, the service writes.
> That keeps DRF's validation and browsable API while putting the transaction boundary where it
> belongs.

**Q: Where does tenant scoping go in a ViewSet?**

> `get_queryset`, and nowhere else. If the queryset is scoped, then retrieve, update and destroy all
> derive from it, so a wrong id returns 404 rather than 403 — which also avoids confirming the object
> exists — and there is no code path that can return another user's row, because the query can't
> express it. Doing it in `get_object` or in a permission class is fetch-then-check, which is correct
> until someone adds a second call site. Object-level permissions are a legitimate second layer, but
> they're not the first. And `get_queryset` is also where the loading strategy lives, because a
> `ModelViewSet` with `queryset = Model.objects.all()` and any nested serializer field is an N+1 by
> construction — it works with five rows in development and dies at five hundred.

**Q: When is DRF the wrong tool?**

> When your API isn't shaped like your models. DRF is excellent for model-shaped CRUD — faster than
> anything else I've used — because ViewSets and routers give you five correct endpoints, pagination,
> filtering and a browsable API almost for free. But for operation-shaped endpoints — `place_order`,
> `refund`, `capture` — you end up fighting it, because those are verbs and DRF wants resources. In
> those cases I use `APIView` or an `@action` with a plain `Serializer` for parsing and a service
> function for the work, which keeps the parts of DRF that help and drops the resource abstraction
> that doesn't fit.

## 🎙️ Articulation drill

**Two minutes: "How do DRF serializers compare to what you used in FastAPI?"**

Lead with the structural difference rather than syntax — a serializer parses, validates against the
database, *and writes*, so it's three jobs in one class, and its ancestor is `ModelForm` rather than
a parsing library. Then the two defaults that are security-relevant: `__all__` deletes your output
control, and everything is writable, which is mass assignment and becomes a breach the moment `user`
is in the list. Give the three-serializer shape as the fix and say the differences between them *are*
the value. Then nested writes — DRF refuses for good reasons, and the good answer is a sub-resource
or a plain serializer delegating to a service. Close on the honest verdict: **DRF is excellent when
your API is your models and it fights you when it isn't**, and name the N+1 that a default ViewSet
queryset ships with.
