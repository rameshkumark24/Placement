# Day 224 🧱

**P-224** · 🧱 **Components and props** — ⭐⭐ composition, and the twelve-boolean component

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a component that has grown twelve boolean props is a component that
> should have been given `children` instead — configuration scales linearly with the callers you

# Part 1 — Props are a function signature

```tsx
type Props = {
  user: User;
  onSelect: (id: string) => void;     // ⭐ handlers are just props
  variant?: "primary" | "ghost";      // ⭐⭐ union, not string
  children?: React.ReactNode;         // ⭐ anything renderable
};

function UserCard({ user, onSelect, variant = "primary", children }: Props) {
  return (
    <article onClick={() => onSelect(user.id)} data-variant={variant}>
      <h3>{user.name}</h3>
      {children}                       {/* ⭐⭐ the extension point */}
    </article>
  );
}
```

| ⭐ Rule | Why |
|---|---|
| **Props are read-only** | ⭐⭐ Mutating a prop is the impurity of Day 223. The owner of the data owns the update. |
| **Name handlers `onX`, implementations `handleX`** | ⭐ Consistency the whole ecosystem shares. |
| **Prefer unions over booleans** | ⭐⭐ `variant="ghost"` beats `isGhost` — see Part 3. |
| **Destructure in the signature** | ⭐ It *is* the documentation, and defaults live there. |

> ⭐ **A component is a function whose return value happens to be a UI description.** Every design
> instinct from Stage 8 applies unchanged: small surface, one responsibility, no hidden coupling.

# Part 2 — Composition

```jsx
// ❌ CONFIGURATION — the component must anticipate every caller
<Card title="X" showFooter footerText="Y" headerIcon={<I/>} bordered dense />

// ✅ COMPOSITION — the caller supplies the parts
<Card>
  <Card.Header icon={<I/>}>X</Card.Header>
  <Card.Body>…</Card.Body>
  <Card.Footer>Y</Card.Footer>
</Card>
```

| ⭐ Pattern | Use for |
|---|---|
| **`children`** | ⭐⭐ The default answer. If a prop's value is *JSX*, it probably wanted to be `children`. |
| **Slots** (named `ReactNode` props) | ⭐ Two or more holes: `<Layout sidebar={<Nav/>} main={<Page/>} />` |
| **Compound components** | ⭐ A family sharing implicit state — `Tabs`/`Tab`, `Card.Header` |
| **Render prop / function child** | ⭐ The parent owns state, the caller owns markup: `<Query>{({data}) => …}</Query>` |
| **⭐⭐ Custom hook** | **Share *logic*, not markup.** Usually the right answer when you were about to add a prop. |

```jsx
// ⭐⭐ the move that prevents most prop explosions:
//    lift the LOGIC into a hook, leave the MARKUP to the caller
function useSelection(items) {
  const [selected, setSelected] = useState(new Set());
  const toggle = (id) => setSelected(s => {
    const next = new Set(s);            // ⭐ new reference (Day 223)
    next.has(id) ? next.delete(id) : next.add(id);
    return next;
  });
  return { selected, toggle, clear: () => setSelected(new Set()) };
}
// ⇒ ⭐ any list can now be selectable without ANY new props on the list.
```

# Part 3 — ⭐⭐ The boolean explosion

```
⭐⭐ HOW EVERY SHARED COMPONENT DIES

⭐   <Button primary />
⭐   <Button primary large />
⭐   <Button primary large loading />
⭐   <Button primary large loading iconOnly />
⭐   ... six months later:
⭐   <Button primary secondary danger large small loading disabled
⭐           iconOnly fullWidth rounded elevated compact />

⭐⭐ 12 BOOLEANS = 4,096 COMBINATIONS.
⭐   ⭐ You have tested about six of them.
⭐   ⭐⭐ MOST ARE MUTUALLY EXCLUSIVE AND NOTHING SAYS SO:
⭐     primary + secondary + danger — what renders? Whatever the
⭐     last if-branch happened to be. THE TYPE SYSTEM PERMITTED IT.

⭐ ✅ THE FIX — make illegal states unrepresentable (Stage 8, again)
⭐   variant: "primary" | "secondary" | "danger"    ⭐⭐ pick exactly one
⭐   size:    "sm" | "md" | "lg"
⭐   state:   "idle" | "loading" | "disabled"
⭐   ⇒ 3 props, 27 valid combinations, ⭐ ZERO CONTRADICTORY ONES,
⭐     and the compiler rejects the nonsense.
```

| ⭐ Smell | Fix |
|---|---|
| Two booleans that cannot both be true | ⭐⭐ One union |
| A prop only used to pass through to a child | ⭐ Pass the child instead (`children`/slot) |
| A prop named `render…` or `…Component` | ⭐ Probably wanted `children` |
| More than ~7 props | ⭐ Split the component, or it is doing two jobs |
| A boolean that turns a *whole section* on | ⭐⭐ That section is a slot |

# Part 4 — Where to split

```
⭐⭐ SPLIT WHEN — real reasons only

⭐   ① ⭐ IT IS REUSED. The only unarguable reason.
⭐   ② ⭐⭐ IT HAS ITS OWN STATE that the parent does not care about.
⭐      (an open/closed accordion inside a page — the page should
⭐      not re-render because a panel toggled)
⭐   ③ ⭐ IT IS A NAMED CONCEPT in the domain — <InvoiceRow> reads
⭐      better than 40 lines of nested divs
⭐   ④ ⭐ IT NEEDS ITS OWN TEST or its own loading boundary

⭐⭐ DO NOT SPLIT BECAUSE:
⭐   · "the file is long" — ⭐ a 200-line component used once is FINE,
⭐     and eight one-use components in eight files is WORSE to read
⭐   · "best practice"
⭐   · ⭐⭐ premature reuse — abstracting the SECOND time you need it
⭐     is right; abstracting the FIRST time invents the wrong seam.
```

> ⭐⭐ **The prop-drilling threshold.** Passing a prop through 2 levels is fine. Through 5 levels of
> components that do not use it is a smell — but the fix is usually **composition** (pass the element
> down, not the data) rather than Context (Day 231). Reach for Context third, not first.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you keep shared components from rotting?"**

Name the failure mode first, because everyone recognises it. **Every shared component dies the same
way: it accumulates booleans. Primary, then large, then loading, then iconOnly — six months later
there are twelve, which is four thousand combinations of which I've tested about six. And the real
problem isn't the count, it's that most are mutually exclusive and nothing says so. Primary plus danger
is meaningless, and whatever renders is whichever if-branch happened to come last.**

Then the fix, tied to a principle you already hold. **Replace booleans with unions — variant, size,
state. Three props, twenty-seven valid combinations, zero contradictory ones, and the compiler rejects
the nonsense. It's making illegal states unrepresentable, which is the same thing I do when modelling a
domain.**

Then the deeper move. **Configuration scales with the callers you anticipated; composition scales with
the ones you didn't. If a prop's value is JSX, it wanted to be children. If a boolean turns a whole
section on, that section is a slot. And when I'm about to add a prop for behaviour rather than
appearance, the answer is usually a custom hook — share the logic, let the caller own the markup.**

Close on restraint. **I split when something is genuinely reused, has its own state, or is a named
domain concept. Not because a file got long — a two-hundred-line component used once is fine, and eight
single-use components across eight files is harder to read, not easier.**
