# Part 1 — ⭐ The four levels, and where Postgres differs from the textbook

```
⭐⭐ THE SQL STANDARD DEFINES LEVELS BY WHAT THEY FORBID:

⭐   LEVEL             DIRTY  NON-REPEAT  PHANTOM  ⭐⭐ WRITE SKEW
⭐   READ UNCOMMITTED   yes      yes        yes         yes
⭐   READ COMMITTED     no       yes        yes         yes
⭐   REPEATABLE READ    no       no        (yes)        yes   ⭐⭐ ← the
⭐   SERIALIZABLE       no       no         no          NO       one
⭐                                                              people
⭐                                                              miss

⭐⭐ WHAT POSTGRES ACTUALLY DOES — three differences worth stating:
⭐  ① ⭐⭐ THERE IS NO READ UNCOMMITTED. Asking for it gives you READ
⭐     COMMITTED. ⭐ MVCC means an uncommitted version is simply not
⭐     visible; ⭐⭐ POSTGRES CANNOT PRODUCE A DIRTY READ EVEN IF YOU
⭐     WANT ONE.
⭐  ② ⭐⭐ POSTGRES'S REPEATABLE READ ALSO PREVENTS PHANTOM READS —
⭐     it is a true SNAPSHOT ISOLATION, stronger than the standard
⭐     requires. ⭐ (This is why the table says "(yes)".)
⭐  ③ ⭐⭐ POSTGRES'S SERIALIZABLE IS *SSI* — Serializable Snapshot
⭐     Isolation. It does NOT use two-phase locking; it runs at snapshot
⭐     isolation speed and ABORTS transactions that would have produced
⭐     a non-serialisable outcome. ⭐ Optimistic, not pessimistic.
```

```
⭐⭐ AND THE ONE THAT DOES *NOT* APPEAR IN THE STANDARD'S TABLE AT ALL:
⭐   ***WRITE SKEW*** — ⭐⭐ REPEATABLE READ DOES NOT PREVENT IT, AND
⭐   ALMOST EVERYONE BELIEVES IT DOES. Part 4 is entirely about it.
```

# Part 2 — ⭐⭐ Reproduce them. Two windows, right now.

## ⭐ Anomaly 1 — non-repeatable read (same row, two answers)

```sql
-- A: BEGIN;                                    -- READ COMMITTED
-- A: SELECT balance FROM accounts WHERE id=1;  -- ⭐ 1000
-- B: UPDATE accounts SET balance=500 WHERE id=1; COMMIT;
-- A: SELECT balance FROM accounts WHERE id=1;  -- ⭐⭐ 500 ← CHANGED
-- ⇒ ⭐⭐ TWO READS IN ONE TRANSACTION, TWO ANSWERS.
-- ⭐ Repeat with `BEGIN ISOLATION LEVEL REPEATABLE READ;` ⇒ still 1000.
```

## ⭐ Anomaly 2 — phantom read (same query, new rows)

```sql
-- A: BEGIN;
-- A: SELECT count(*) FROM orders WHERE tenant_id=7;  -- ⭐ 40
-- B: INSERT INTO orders (tenant_id, ...) VALUES (7, ...); COMMIT;
-- A: SELECT count(*) FROM orders WHERE tenant_id=7;  -- ⭐⭐ 41
-- ⇒ ⭐ A row appeared that matches a query you already ran.
-- ⭐⭐ POSTGRES'S REPEATABLE READ PREVENTS THIS. The standard's does not.
```

## ⭐⭐ Anomaly 3 — read skew (two rows, inconsistent with each other)

```sql
-- ⭐⭐ THE ONE THAT MAKES REPORTS WRONG, AND NOBODY REPRODUCES IT.
-- A: BEGIN;
-- A: SELECT balance FROM accounts WHERE id=1;   -- ⭐ 1000
-- B: BEGIN; UPDATE accounts SET balance=900 WHERE id=1;
--           UPDATE accounts SET balance=1100 WHERE id=2; COMMIT;
-- A: SELECT balance FROM accounts WHERE id=2;   -- ⭐⭐ 1100
-- ⇒ ⭐⭐ A SAW 1000 AND 1100. TOTAL = 2100. THE TOTAL WAS *NEVER* 2100
--   AT ANY INSTANT. ⭐ Your reconciliation report is off by 100 and
--   nothing in the log is wrong.
-- ⇒ ⭐⭐ THIS IS THE REASON ANY MULTI-STATEMENT REPORT SHOULD RUN AT
--   REPEATABLE READ. One line, and the class of bug disappears.
```

## ⭐⭐ Anomaly 4 — the lost update (this one costs money)

```sql
-- ⭐⭐ THE READ-MODIFY-WRITE, WHICH IS WHAT AN ORM ENCOURAGES YOU TO DO.
-- A: BEGIN; SELECT quantity FROM stock WHERE id=1;   -- ⭐ 10
-- B: BEGIN; SELECT quantity FROM stock WHERE id=1;   -- ⭐ 10
-- A: UPDATE stock SET quantity=9 WHERE id=1; COMMIT;
-- B: UPDATE stock SET quantity=9 WHERE id=1; COMMIT;
-- ⇒ ⭐⭐ TWO SALES. ONE DECREMENT. THE SECOND SALE VANISHED.
--   ⭐ No error, no lock wait, no log line. Postgres did exactly what
--     both transactions asked.

-- ⭐⭐ THE FOUR FIXES, AND YOU MUST BE ABLE TO RANK THEM:
-- ① ⭐⭐ ATOMIC CONDITIONAL UPDATE — best when expressible.
UPDATE stock SET quantity = quantity - 1
WHERE id = 1 AND quantity >= 1;      -- ⭐ check rowcount! 0 ⇒ sold out
-- ⭐ No lock you wrote, no race, one statement. Day 164's oversell fix.
-- ② ⭐ PESSIMISTIC LOCK — when you must read, decide, then write.
SELECT quantity FROM stock WHERE id=1 FOR UPDATE;    -- ⭐ B now waits
-- ③ ⭐ OPTIMISTIC / VERSION COLUMN — when the gap includes user think
--    time (a web form). `WHERE id=1 AND version=7`, rowcount 0 ⇒ 409.
-- ④ ⭐⭐ REPEATABLE READ — B gets `ERROR: could not serialize access
--    due to concurrent update` and must RETRY. ⭐ Correct, but you have
--    converted a silent bug into a visible failure you must handle.
```

```
⭐⭐ AND THE SUBTLETY THAT SURPRISES EVERYONE, ABOUT READ COMMITTED:
⭐   UPDATE stock SET quantity = quantity - 1 WHERE id=1 AND quantity>=1;
⭐   ⭐ Run concurrently, B BLOCKS on A's row lock. When A commits, B
⭐     does NOT proceed with its old snapshot — ⭐⭐ IT RE-READS THE NEW
⭐     ROW VERSION AND RE-EVALUATES THE `WHERE` CLAUSE.
⭐   ⇒ ⭐⭐ THIS IS WHY THE CONDITIONAL UPDATE IS SAFE EVEN AT READ
⭐     COMMITTED, AND WHY SELECT-THEN-UPDATE IS NOT.
⭐   ⭐⭐ IT IS ALSO WHY READ COMMITTED CAN PRODUCE A RESULT THAT MATCHES
⭐     NO SINGLE SNAPSHOT — the SELECT part of a statement uses one
⭐     snapshot and the blocked UPDATE re-checks against a newer row.
⭐     ⭐ Strange, documented, and the reason serious money code does not
⭐       rely on subtle READ COMMITTED behaviour.
```

# Part 3 — ⭐ REPEATABLE READ, and the retry loop that is not optional

```
⭐ ONE SNAPSHOT FOR THE WHOLE TRANSACTION. ⭐⭐ ALL FOUR CONSEQUENCES:
⭐   ✅ non-repeatable reads gone · ✅ phantoms gone · ✅ read skew gone
⭐   ⭐⭐ ❗ AND: IF YOU UPDATE A ROW SOMEONE ELSE CHANGED SINCE YOUR
⭐      SNAPSHOT, POSTGRES ABORTS YOU:
⭐        ERROR: could not serialize access due to concurrent update
⭐        SQLSTATE 40001
⭐   ⇒ ⭐⭐ 40001 IS NOT A BUG. IT IS THE FEATURE. It means "I refused to
⭐     let you write a wrong answer." ⭐ Your job is to try again.
```

```python
# ⭐⭐ THE RETRY DECORATOR, AND THE THING PEOPLE GET WRONG ABOUT IT
from psycopg import errors
import random, time

def with_retry(fn, attempts=5):
    for i in range(attempts):
        try:
            with SessionLocal.begin() as session:        # ⭐ NEW txn
                return fn(session)                       # ⭐⭐ ALL of it
        except (errors.SerializationFailure,
                errors.DeadlockDetected) as e:           # ⭐ 40001/40P01
            if i == attempts - 1:
                raise
            time.sleep((0.05 * 2**i) * (0.5 + random.random()))  # ⭐ Day 152
    # ⭐⭐ THE MISTAKE: RETRYING ONLY THE COMMIT.
    #    The whole transaction read a snapshot that is now known wrong,
    #    so ⭐⭐ EVERY DECISION IT MADE MUST BE RECOMPUTED. Re-run the
    #    BUSINESS LOGIC, not the write.
    # ⭐⭐ AND THE SECOND MISTAKE: side effects inside `fn`. If it sent an
    #    email or charged a card, a retry does it twice. ⭐ Emit to the
    #    OUTBOX inside the transaction (Day 142) and let the relay send
    #    once. The retry then costs nothing but CPU.
```

```python
# ⭐ Setting the level in SQLAlchemy — three scopes:
engine = create_engine(url, isolation_level="REPEATABLE READ")   # ⭐ all
conn = engine.connect().execution_options(
    isolation_level="SERIALIZABLE")                              # ⭐ one
session.connection(execution_options={"isolation_level":
    "REPEATABLE READ"})                                          # ⭐ per
# ⭐⭐ IT MUST BE SET BEFORE THE FIRST STATEMENT OF THE TRANSACTION.
#    `SET TRANSACTION ISOLATION LEVEL` after a query raises.
```

# Part 4 — ⭐⭐ Write skew: the anomaly REPEATABLE READ does not stop

```sql
-- ⭐⭐ THE RULE: "AT LEAST ONE DOCTOR MUST BE ON CALL."
-- ⭐ Alice and Bob are both on call. Both want to go off call.

-- A: BEGIN ISOLATION LEVEL REPEATABLE READ;
-- A: SELECT count(*) FROM doctors WHERE on_call=true;    -- ⭐ 2, fine
-- B: BEGIN ISOLATION LEVEL REPEATABLE READ;
-- B: SELECT count(*) FROM doctors WHERE on_call=true;    -- ⭐ 2, fine
-- A: UPDATE doctors SET on_call=false WHERE name='Alice'; COMMIT;
-- B: UPDATE doctors SET on_call=false WHERE name='Bob';   COMMIT;
-- ⇒ ⭐⭐ NOBODY IS ON CALL. BOTH TRANSACTIONS COMMITTED. NO ERROR.

-- ⭐⭐ WHY REPEATABLE READ CANNOT SEE IT: THEY WROTE ***DIFFERENT
--    ROWS***. There is no write-write conflict to detect. Each read a
--    consistent snapshot and each write was legal in isolation.
-- ⭐⭐ THE SHAPE, SO YOU RECOGNISE IT ELSEWHERE:
--    read a set → decide → write a DIFFERENT row that changes that set.
-- ⭐ Other instances of the same shape, all real:
--    ⭐ two bookings for the same room (Day 187's EXCLUDE constraint)
--    ⭐ two withdrawals against a combined balance across two accounts
--    ⭐ two users claiming the last seat in different rows
--    ⭐ ⭐⭐ ANY "COUNT THEN INSERT IF UNDER LIMIT" — which is most
--      quota, rate-limit and capacity code people write.
```

```
⭐⭐ THE THREE FIXES, RANKED BY WHAT THEY COST:

⭐ ① ⭐⭐ A CONSTRAINT — put the invariant where a bug cannot reach it.
⭐    EXCLUDE for overlaps; a partial unique index for "one active";
⭐    a CHECK on a counter column. ⭐ Free at runtime, and it cannot be
⭐    bypassed by any code path (Day 187 Part 4). ⭐⭐ ALWAYS TRY FIRST.
⭐ ② ⭐ MATERIALISE THE CONFLICT — give the transactions a row to fight
⭐    over. `SELECT ... FROM shifts WHERE id=$today FOR UPDATE` before
⭐    deciding. ⭐⭐ Now there IS a write-write conflict, and any level
⭐    detects it. ⭐ Cost: you serialised the whole shift.
⭐ ③ ⭐⭐ SERIALIZABLE — Postgres tracks the read *predicate* (an SIREAD
⭐    lock) and aborts the second committer with 40001. ⭐ Correct,
⭐    general, and needs the retry loop from Part 3.
```

```
⭐⭐ SERIALIZABLE (SSI), HONESTLY:
⭐   ⭐ COST: predicate-lock tracking memory, and ⭐⭐ FALSE POSITIVES —
⭐     it will sometimes abort a transaction that would actually have
⭐     been fine. That is the price of not using locks.
⭐   ⭐ ⭐⭐ ON A READ-ONLY TRANSACTION, DECLARE IT: `BEGIN TRANSACTION
⭐     ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;` — it waits
⭐     for a safe snapshot and then ⭐⭐ CAN NEVER BE ABORTED. Perfect
⭐     for the nightly reconciliation report.
⭐   ⭐⭐ AND THE OPERATIONAL TRAP: ***EVERY*** TRANSACTION THAT
⭐     PARTICIPATES MUST BE SERIALIZABLE. One READ COMMITTED writer
⭐     ignores the whole scheme and the guarantee is gone. ⭐ It is a
⭐     property of the SYSTEM, not of one transaction.
⭐   ⭐ Throughput: fine at low conflict rates; ⭐⭐ collapses under high
⭐     contention because aborts and retries multiply. Measure it.
```

# Part 5 — ⭐ What to actually do

```
⭐⭐ THE DECISION, AS A SHORT LIST:

⭐ ① DEFAULT: READ COMMITTED — ⭐ it is the right default, and Postgres
⭐    ships it for a reason. ⭐⭐ BUT WRITE YOUR MUTATIONS SO IT IS
⭐    ENOUGH: conditional `UPDATE ... WHERE` with a rowcount check, or
⭐    `FOR UPDATE` when you must read-then-write.
⭐ ② ⭐⭐ ANY MULTI-STATEMENT REPORT OR EXPORT: REPEATABLE READ. One
⭐    line, kills read skew, and a read-only transaction can never hit
⭐    40001. ⭐ There is no reason not to.
⭐ ③ ⭐⭐ A GENUINE MULTI-ROW INVARIANT (write skew shape): a CONSTRAINT
⭐    if you can express it; SERIALIZABLE + retries if you cannot.
⭐ ④ NEVER: raise the level and skip the retry loop. ⭐⭐ You have traded
⭐    a rare wrong answer for a frequent 500.

⭐⭐ AND THE INVARIANT FROM DAY 184, WHICH THIS DAY IS THE PROOF OF:
⭐   ⭐⭐ "PUT THE GUARANTEE WHERE A BUG CANNOT REACH IT." An isolation
⭐   level is a guarantee you must remember to ask for, in every code
⭐   path, forever. A constraint is one you cannot forget.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Treating isolation level as a performance dial | It's a list of specific wrong answers you're accepting. |
| Asking for READ UNCOMMITTED | Postgres gives you READ COMMITTED. MVCC can't produce a dirty read. |
| Believing REPEATABLE READ prevents write skew | It doesn't — the transactions write different rows. |
| Raising the level without a retry loop | You converted a rare wrong answer into a frequent 500. |
| Retrying only the commit | The whole snapshot is invalid; re-run the business logic. |
| Side effects inside a retried transaction | A retry charges the card twice. Emit to the outbox instead. |
| `SELECT` then `UPDATE` at READ COMMITTED | Classic lost update. Use a conditional update or `FOR UPDATE`. |
| Ignoring the rowcount from a conditional update | Zero rows means the condition failed — that's your business answer. |
| Setting the isolation level mid-transaction | It must be set before the first statement. |
| Assuming SERIALIZABLE protects you if one writer is READ COMMITTED | It's a property of the system; one non-participant voids it. |
| Running a long report at READ COMMITTED | Read skew: a total that was never true at any instant. |
| Not using `READ ONLY DEFERRABLE` for a serializable report | It waits for a safe snapshot and can then never be aborted. |
| Expecting SERIALIZABLE to scale under high contention | Aborts and retries multiply. Measure it. |

## Interview questions

**Q: What isolation level does your application use, and why?**

> READ COMMITTED, because it's Postgres's default and it's the right default — but the honest answer
> is that the level alone doesn't make anything safe, so the real work is writing mutations that are
> correct at that level. That means conditional updates with a rowcount check —
> `UPDATE stock SET quantity = quantity - 1 WHERE id = $1 AND quantity >= 1` — rather than reading a
> value into Python, deciding, and writing it back, which is the classic lost update. Where I do
> deviate: any multi-statement report or export runs at REPEATABLE READ, because at READ COMMITTED you
> get read skew — you read account one before another transaction moves money and account two
> afterwards, so your total was never true at any instant, and nothing in any log looks wrong. It's one
> line and a whole class of bug disappears, and a read-only transaction can't hit a serialization
> failure, so there's no downside.

**Q: What's write skew and why doesn't REPEATABLE READ prevent it?**

> Two transactions read the same set, each decides something based on it, and each writes a *different*
> row in a way that invalidates the other's decision. The canonical case is two doctors both on call,
> both checking that at least one other person is on call, both going off — and the invariant is
> violated with both transactions committed and no error. REPEATABLE READ can't detect it because it
> looks for write-write conflicts and there aren't any: they touched different rows, and each snapshot
> was internally consistent. The shape is worth memorising because it's everywhere — count then insert
> if under limit, which is most quota, capacity and booking code. The fixes in order are: express it as
> a constraint if you can, since an `EXCLUDE` constraint or a partial unique index puts the guarantee
> somewhere no code path can bypass; materialise the conflict by locking a shared parent row so there
> *is* a write-write conflict; or SERIALIZABLE, which tracks the read predicate and aborts the second
> committer — with a retry loop, which isn't optional.

**Q: What does `could not serialize access` mean and how do you handle it?**

> SQLSTATE 40001 — Postgres refused to let a transaction commit a result that couldn't have happened in
> any serial order. It's the feature working, not a bug, and the handling is a retry with exponential
> backoff and jitter, capped at a few attempts. Two things people get wrong. First, they retry only the
> commit, which is meaningless: the whole transaction read a snapshot that's now known to be wrong, so
> every decision it made has to be recomputed — you re-run the business logic in a fresh transaction.
> Second, side effects. If the transaction sent an email or called a payment API, retrying does it
> twice, so anything external has to go through the outbox inside the transaction and be sent once by
> the relay — which is the same pattern as the dual-write problem. Once that's true, a retry costs
> nothing but CPU. And I'd emit a metric on retry counts, because a rising retry rate is the early
> warning that contention is becoming a scaling problem.

**Q: Can you get a lost update at READ COMMITTED with a single `UPDATE` statement?**

> No, and the reason is a genuinely surprising piece of Postgres behaviour. If two sessions run
> `UPDATE stock SET quantity = quantity - 1 WHERE id = 1 AND quantity >= 1` concurrently, the second
> blocks on the first's row lock — and when the first commits, the second doesn't proceed with its
> original snapshot. It re-reads the new row version and re-evaluates the `WHERE` clause against it.
> So the condition is checked against the committed value and the decrement is safe. That's exactly why
> the conditional update is the best fix for a lost update and why select-then-update isn't: the gap
> between the read and the write is where the race lives, and a single statement has no gap. The same
> mechanism is also why READ COMMITTED can produce a result that corresponds to no single snapshot,
> which is documented and slightly unsettling — it's a reason not to build money logic on subtle
> READ COMMITTED behaviour when a constraint would do.

**Q: When would you use SERIALIZABLE?**

> When there's a genuine multi-row invariant I can't express as a constraint. Postgres's SERIALIZABLE
> is SSI — optimistic, not two-phase locking — so it runs at snapshot-isolation speed and aborts
> transactions that would have produced a non-serialisable outcome, which means the cost lands as
> retries rather than as waiting. Three caveats I'd state up front. It has false positives, aborting
> transactions that would actually have been fine, which is the price of not locking. It's a property
> of the whole system: one READ COMMITTED writer touching the same data voids the guarantee, so it's
> all-or-nothing across the code paths involved. And it degrades under high contention because aborts
> and retries multiply, so it needs measuring rather than assuming. The one place I'd use it without
> hesitation is a read-only reconciliation report declared `SERIALIZABLE READ ONLY DEFERRABLE`, which
> waits for a safe snapshot and can then never be aborted.

## 🎙️ Articulation drill

wrong answers you're agreeing to accept, so if you can't name them you defaulted rather than chose.
