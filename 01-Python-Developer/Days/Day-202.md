# Part 1 — ⭐ Setting it up, and what normalisation means

```ini
# postgresql.conf — ⭐⭐ requires a RESTART (it is a preload library)
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.max = 10000      # ⭐ distinct queries tracked
pg_stat_statements.track = top      # ⭐ 'all' also counts statements
                                    #   inside functions/procedures
pg_stat_statements.track_utility = off  # ⭐ skip DDL noise
pg_stat_statements.track_planning = off # ⭐⭐ ON adds real overhead;
                                        #   turn it on temporarily when
                                        #   you suspect planning time
                                        #   (Day 200's partitions!)
```

```sql
CREATE EXTENSION pg_stat_statements;
```

```
⭐⭐ NORMALISATION IS THE WHOLE TRICK, AND IT HAS ONE SHARP EDGE:
⭐   SELECT * FROM orders WHERE id = 42
⭐   SELECT * FROM orders WHERE id = 91
⭐   ⇒ ⭐ ONE ENTRY: `SELECT * FROM orders WHERE id = $1`, calls = 2.
⭐
⭐   ⭐⭐ THE EDGE: THE STATS ARE FOR THE ***TEXT***, NOT THE ***PLAN***.
⭐     One entry can hide two completely different plans — a fast one
⭐     for a small tenant and a catastrophic one for your largest.
⭐   ⇒ ⭐⭐ WHICH IS WHY `stddev_exec_time` IS THE MOST UNDERUSED COLUMN
⭐     IN THE VIEW. High mean = uniformly slow. ⭐⭐ HIGH STDDEV WITH A
⭐     LOW MEAN = SOMETIMES CATASTROPHIC, and that is the query causing
⭐     your p99 while your p50 looks perfect.
⭐   ⭐ Also: `IN ($1,$2,$3)` and `IN ($1,$2,$3,$4)` were separate
⭐     entries before PG 14. ⭐ On 14+ they merge, which finally makes
⭐     ORM-generated `IN` lists readable.
```

# Part 2 — ⭐⭐ The six queries that find everything

```sql
-- ⭐⭐ ① BY TOTAL TIME. If you run one query today, run this one.
SELECT round(total_exec_time::numeric/1000,1) AS total_s,
       calls,
       round(mean_exec_time::numeric,2)   AS mean_ms,
       round(stddev_exec_time::numeric,2) AS stddev_ms,
       round(100*total_exec_time/sum(total_exec_time) OVER (),1) AS pct,
       left(query, 90)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
-- ⭐⭐ THE SHAPE YOU ALMOST ALWAYS SEE: the #1 entry is 2 ms and runs
--    4,000,000 times. ⭐ Nobody complained. It is 40% of your database.
--    ⭐⭐ THAT IS THE N+1 (Day 193, Query 6). It is invisible in every
--      slow-query log ever configured.

-- ⭐⭐ ② BY VARIANCE — the p99 hunter
SELECT calls, round(mean_exec_time::numeric,2) mean,
       round(stddev_exec_time::numeric,2) sd,
       round(max_exec_time::numeric,2) max_ms, left(query,90)
FROM pg_stat_statements
WHERE calls > 100 AND stddev_exec_time > 2 * mean_exec_time
ORDER BY stddev_exec_time DESC LIMIT 20;
-- ⭐⭐ CAUSES, IN ORDER OF LIKELIHOOD: parameter skew (one huge
--    tenant), lock waits (Day 196), cache cold vs warm (Day 186), or
--    plan instability.

-- ⭐ ③ BY IO — who is evicting everyone else's cache
SELECT calls, shared_blks_read, shared_blks_hit,
       round(100.0*shared_blks_hit/NULLIF(shared_blks_hit+shared_blks_read,0),1)
         AS hit_pct,
       pg_size_pretty(shared_blks_read*8192::bigint) AS read_bytes,
       left(query,80)
FROM pg_stat_statements ORDER BY shared_blks_read DESC LIMIT 20;

-- ⭐⭐ ④ BY SPILLS — Day 191's `work_mem` problem, ranked
SELECT calls, temp_blks_written, left(query,90)
FROM pg_stat_statements WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC LIMIT 20;

-- ⭐⭐ ⑤ BY WAL — who is causing your checkpoints and replication lag
SELECT calls, pg_size_pretty(wal_bytes::bigint) AS wal, left(query,90)
FROM pg_stat_statements ORDER BY wal_bytes DESC LIMIT 20;
-- ⭐ PG 13+. ⭐⭐ Finds the jsonb write amplification from Day 198
--   immediately, and the `UPDATE` that touches an over-indexed table.

-- ⭐ ⑥ ROWS PER CALL — the "we fetch 40,000 rows to show 20" detector
SELECT calls, rows, rows/NULLIF(calls,0) AS rows_per_call, left(query,80)
FROM pg_stat_statements
WHERE calls > 50 ORDER BY rows/NULLIF(calls,0) DESC NULLS LAST LIMIT 20;
```

```
⭐⭐ THE METHODOLOGY, WHICH MATTERS MORE THAN THE QUERIES:
⭐   ⭐ The counters are CUMULATIVE SINCE THE LAST RESET. ⭐⭐ SO YOUR
⭐     TOP ENTRY MAY BE A MIGRATION YOU RAN IN MARCH.
⭐   ⇒ ⭐⭐ SNAPSHOT AND DIFF:
⭐        SELECT pg_stat_statements_reset();   -- ⭐ or snapshot the view
⭐        …run the workload / wait one hour…
⭐        …snapshot again, subtract…
⭐   ⭐ In production, do not reset — ⭐⭐ store hourly snapshots into a
⭐     table and diff. Then you can answer "what changed after the
⭐     Tuesday deploy?", which is the question you will actually be
⭐     asked. ⭐ pgwatch2 / pganalyze do this for you.
```

# Part 3 — ⭐⭐ Wait events: where the time actually goes

```sql
-- ⭐⭐ pg_stat_statements TELLS YOU *WHICH* QUERY. WAIT EVENTS TELL YOU
--    *WHY*. Sample this every second and aggregate:
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity WHERE state = 'active'
GROUP BY 1,2 ORDER BY 3 DESC;
```

```
⭐⭐ READING THE RESULT — each type means a different fix:
⭐   ⭐ NULL / (none)  ⇒ ⭐⭐ ON CPU. Fix the query or add cores.
⭐   ⭐ IO             ⇒ reading data. ⭐ More RAM, better indexes,
⭐        faster storage. `DataFileRead` dominating = Day 186's problem.
⭐   ⭐⭐ Lock          ⇒ ***ROW OR TABLE LOCKS***. Day 196. ⭐ No amount
⭐        of index tuning helps; this is a concurrency design problem.
⭐   ⭐⭐ LWLock        ⇒ internal contention. `WALWrite`, `BufferMapping`,
⭐        ⭐ `LockManager` (often: too many partitions or too many
⭐        connections). ⭐⭐ Usually means "too much concurrency", and
⭐        the fix is a SMALLER pool (Day 197), not a bigger one.
⭐   ⭐ Client         ⇒ ⭐⭐ WAITING FOR ***YOUR APPLICATION***.
⭐        `ClientRead` dominating means the database is idle waiting for
⭐        you — ⭐ the bottleneck is not the database at all. ⭐⭐ This
⭐        single observation ends a lot of arguments.
⭐   ⭐ IPC / Timeout / Extension ⇒ parallel workers, sleeps, extensions.
⭐   ⇒ ⭐ `pg_wait_sampling` samples this continuously so you do not
⭐     have to poll. ⭐⭐ Worth installing before you need it.
```

# Part 4 — ⭐ The settings that matter, derived not copied

```
⭐⭐ TWELVE SETTINGS. IN ORDER. EACH WITH ITS DERIVATION.

⭐ MEMORY
⭐  1. shared_buffers = 25% RAM        ⭐ Day 186. Not 80%.
⭐  2. effective_cache_size = 60% RAM  ⭐⭐ ALLOCATES NOTHING; it is the
⭐       planner's belief about caching, and it decides index vs seq
⭐       scan more often than anything else you will touch.
⭐  3. work_mem — ⭐⭐ DERIVE IT: RAM×0.25 ÷ (max_connections × ~2 sorts).
⭐       ⭐ 64 GB, 100 conns ⇒ ~40 MB is generous. ⭐⭐ Raise it PER
⭐       QUERY with `SET LOCAL`, never globally to fix one report.
⭐  4. maintenance_work_mem = 1–2 GB   ⭐ used by VACUUM, CREATE INDEX,
⭐       ALTER TABLE. ⭐⭐ Raising this makes index builds and vacuum
⭐       DRAMATICALLY faster and costs nothing at steady state.
⭐       ⭐ `autovacuum_work_mem` separately if you have many workers.

⭐ PLANNER
⭐  5. ⭐⭐ random_page_cost = 1.1 ON SSD/NVMe (default 4.0).
⭐       ⭐⭐ THE DEFAULT ASSUMES A SPINNING DISK WHERE A RANDOM READ IS
⭐       4× A SEQUENTIAL ONE. On SSD it is ~1.1. ⭐⭐ LEAVING IT AT 4
⭐       MAKES POSTGRES SYSTEMATICALLY AVOID INDEXES IT SHOULD USE —
⭐       Day 189's reason ④, caused by a config file.
⭐  6. effective_io_concurrency = 200 on NVMe (default 1) ⭐ enables
⭐       prefetch for bitmap heap scans.
⭐  7. default_statistics_target = 100, raise to 500–1000 per column on
⭐       skewed columns. ⭐ Day 189 ⑥.
⭐  8. ⭐⭐ jit = off FOR OLTP. JIT compilation can add 100+ ms to a
⭐       query that runs in 5 ms, because the planner overestimated cost
⭐       and decided compiling was worth it. ⭐⭐ A classic "why did this
⭐       endpoint get slower on PG 12" mystery.

⭐ WRITE PATH
⭐  9. max_wal_size = 8–16 GB          ⭐ Day 186's checkpoint sawtooth.
⭐ 10. checkpoint_completion_target = 0.9
⭐ 11. wal_compression = on            ⭐ cheap; cuts full-page writes.

⭐ MAINTENANCE
⭐ 12. ⭐⭐ autovacuum_vacuum_cost_limit = 1000–2000 and per-table scale
⭐       factors on your big tables. ⭐ Day 194. ⭐⭐ THE HIGHEST-VALUE
⭐       CHANGE ON MOST BUSY DATABASES AND ALMOST NOBODY MAKES IT.

⭐ ⭐⭐ AND THE META-RULE: CHANGE ONE THING, MEASURE, WRITE DOWN WHY.
⭐   A postgresql.conf full of settings nobody can justify is worse than
⭐   the defaults, because now you cannot reason about anything.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Ranking `pg_stat_statements` by mean time | Rank by total. Frequency usually beats duration. |
| Ignoring `stddev_exec_time` | High stddev with low mean is exactly what makes your p99. |
| Reading cumulative counters | They include March's migration. Snapshot and diff. |
| Resetting stats in production to "get clean numbers" | You destroyed the history. Store snapshots instead. |
| Assuming one entry means one plan | It's normalised by text; two tenants can get two plans. |
| `track_planning = on` permanently | Real overhead. Turn it on to answer a question, then off. |
| Only looking at query stats | Wait events tell you *why*. `ClientRead` means it isn't the database. |
| Treating high LWLock waits as "needs more capacity" | Usually too much concurrency — a smaller pool. |
| Leaving `random_page_cost = 4` on SSD | Postgres systematically avoids indexes it should use. |
| Raising `work_mem` globally | Per sort, per connection. Derive it, then `SET LOCAL` per query. |
| Ignoring `maintenance_work_mem` | It makes vacuum and index builds dramatically faster for free. |
| Leaving `jit = on` for OLTP | It can add 100 ms to a 5 ms query. |
| Changing five settings at once | You now know nothing. One change, measured, written down. |
| Claiming a tuning win with no before number | A claim, not a proof. |

## Interview questions

**Q: How do you find what to optimise in a database you've never seen?**

> `pg_stat_statements`, sorted by total execution time rather than mean — and I'd say why, because it's
> the thing people get backwards. A four-millisecond query run two million times costs more than a
> nine-second nightly report, and it's usually top of the list with nobody having ever complained about
> it. That's typically the N+1, which is structurally invisible in any slow-query log because every
> individual execution is fast. Then I'd look at variance: high `stddev_exec_time` with a low mean is
> what makes your p99, and it usually means parameter skew — one enormous tenant getting a different
> plan through the same normalised query text. Then IO, temp blocks for spills, and WAL bytes to find
> write amplification. And I'd snapshot and diff rather than read cumulative counters, because those
> include the migration someone ran in March.

**Q: Query stats say query X is the worst. What else do you look at?**

> Wait events, because query stats say *which* and wait events say *why*. Sampling
> `pg_stat_activity` for active backends and grouping by `wait_event_type` tells you whether time is
> going to CPU, IO, locks, internal LWLock contention, or the client. Each points at a different fix
> and three of them can't be fixed by tuning the query. `Lock` means it's a concurrency design problem
> — no index helps. Heavy `LWLock` usually means too much concurrency, and the fix is a *smaller*
> connection pool, not a bigger one, which is counterintuitive enough that people do the opposite.
> And `ClientRead` dominating means the database is sitting idle waiting for the application, so the
> bottleneck isn't the database at all — that single observation ends a lot of arguments. I'd install
> `pg_wait_sampling` so this is continuous rather than something I poll during an incident.

**Q: Which Postgres settings would you change from the defaults, and why?**

> I'd give a short list with derivations rather than a config file. `shared_buffers` at about a quarter
> of RAM, and `effective_cache_size` at around sixty percent — that second one allocates nothing but
> tells the planner how much caching to assume, and it decides index versus sequential scan more often
> than anything else. `work_mem` derived from RAM divided by max connections times a couple of sorts,
> then raised per query with `SET LOCAL` rather than globally. `maintenance_work_mem` up to a gigabyte
> or two, because it makes vacuum and index builds dramatically faster and costs nothing at steady
> state. The one I'd emphasise is `random_page_cost`: the default of 4 assumes a spinning disk where a
> random read costs four times a sequential one, and on SSD it's closer to 1.1 — leaving it at the
> default makes Postgres systematically avoid indexes it should use, which is a "why isn't my index
> used" problem caused by a config file. `jit = off` for OLTP. And autovacuum cost limits plus
> per-table scale factors, which is the highest-value change on most busy databases and almost nobody
> makes it.

**Q: You changed a setting and things got faster. How confident are you?**

> Not very, until I've done three things. Established a baseline over a full workload cycle rather than
> a few minutes, because a database that was mid-checkpoint or had a cold cache will flatter or
> punish any change. Changed exactly one thing, so the attribution is real. And reverted it to confirm
> the improvement disappears — that's the step people skip, and it's the one that catches coincidences
> like an unrelated deploy or a batch job finishing. In a tuning report the most credible section is
> the list of changes I made and reverted because they didn't help, precisely because it shows the
> measurements were real rather than confirmatory. A config file full of settings nobody can justify is
> worse than the defaults, because you can no longer reason about anything.

**Q: Walk me through your first hour on a database that's "slow".**

> Five things in order. `pg_stat_activity` for anything blocked or long-running, using
> `pg_blocking_pids` — because if it's a lock queue, nothing else matters and it needs fixing now.
> Wait events sampled for a minute, to know whether I'm looking at CPU, IO, locks or the client.
> `pg_stat_statements` by total time, diffed against an earlier snapshot if one exists, to find the
> workload's actual shape. `pg_stat_user_tables` for dead tuples and last autovacuum, and
> `age(datfrozenxid)`, because bloat and wraparound explain a lot of gradual degradation. And the
> checkpoint and bgwriter stats for a write-path problem. Then, and only then, `EXPLAIN (ANALYZE,
> BUFFERS)` on the top one or two queries. The reason for that order is that four of those five can
> make every query slow, and if I start with `EXPLAIN` I'll tune a query that was never the problem.
