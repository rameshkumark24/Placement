# Part 1 — ⭐ The tree, and why there are no drive letters

```
/           ⭐ the single root. Everything is under it, including other disks.
├── bin usr/bin      programs
├── etc              ⭐⭐ configuration. Text files. /etc/hosts, /etc/passwd
├── var              ⭐ things that change: /var/log ⭐⭐, /var/lib, /var/tmp
├── home/you         your files
├── tmp              ⭐ world-writable, cleared on reboot, ⚠️ NOT private
├── opt srv          third-party / served data
├── proc             ⭐⭐ NOT ON DISK — the kernel, presented as files (Day 082)
├── dev              devices as files — /dev/null, /dev/urandom (Day 015)
└── mnt media        ⭐ where other disks are ATTACHED
```

⭐⭐ **There is no `D:`.** A second disk is *mounted* — grafted onto a directory — so a path never
tells you which device it lives on. **`df -h .` tells you.** This matters more than it sounds:

```
⭐⭐ WHY THE MOUNT MODEL SHOWS UP IN YOUR CODE:
⭐   · Day 076's atomic write (tmp + replace) ⭐⭐ is only atomic ON THE SAME FILESYSTEM.
⭐     Writing to /tmp and replacing onto /var/lib is a COPY, not a rename ⇒ not atomic.
⭐     ⇒ ⭐⭐ always create the temp file in the DESTINATION DIRECTORY.
⭐   · a container's writable layer and a mounted volume are different filesystems.
⭐   · "no space left on device" is per-filesystem — ⭐ df -h, and check INODES too:
⭐     df -i. A million tiny cache files can exhaust inodes with the disk half empty.
```

| ⭐ Navigation | |
|---|---|
| `pwd` · `cd -` | where am I · **back to the previous directory** |
| `ls -lah` | long, all, human sizes — ⭐ the one to memorise |
| `ls -lt` / `-ltr` | by time / **oldest last** — ⭐ what changed |
| `du -sh *` \| `sort -h` | ⭐⭐ **what is eating the disk** |
| `tree -L 2` · `stat f` | shape · every fact about one file |

⭐ **A leading `.` is not a filetype, it is a naming convention** that `ls` hides. `.env`, `.git`,
`.venv` are ordinary. ⚠️ **`cp -r src/* dest/` silently skips them; `cp -r src/. dest/` does not.**

# Part 2 — ⭐⭐ Permissions, and the one bit everyone misreads

```
$ ls -l app.py
-rw-r--r--  1 ramesh  devs  1240 Aug 14 10:02 app.py
│└┬┘└┬┘└┬┘     └──┬─┘  └─┬┘
│ │  │  │         │      └── ⭐ GROUP
│ │  │  └─ other  └───────── ⭐ OWNER (user)
│ │  └──── group
│ └─────── ⭐ owner:  r w -
└───────── type: - file · d directory · l symlink · s socket
```

| Bit | ⭐ On a **file** | ⭐⭐ On a **directory** |
|---|---|---|
| `r` (4) | read the contents | ⭐ **list the names** inside |
| `w` (2) | modify the contents | ⭐⭐ **create / delete / rename entries** |
| `x` (1) | execute it | ⭐⭐ **TRAVERSE it — enter, and reach anything inside** |

```
⭐⭐ THE MISREAD THAT COSTS AN HOUR, DERIVED:
⭐   x ON A DIRECTORY IS NOT "EXECUTE", IT IS "MAY PASS THROUGH".
⭐   ⇒ ⭐⭐ a file that is world-readable (rw-r--r--) is still UNREACHABLE if any
⭐        directory on its path lacks x for you. The error is on the DIRECTORY,
⭐        but Python reports it on the FILE ⇒ you stare at the wrong thing.
⭐   ⇒ ⭐⭐ and the mirror image: DELETING a file needs w ON THE DIRECTORY,
⭐        not on the file. ⚠️ You can delete a file you cannot read.
⭐        (A read-only file in a writable directory is deletable. That surprises people.)
⭐   ⇒ ⭐ namei -l /var/lib/app/data.db  ⇒ prints the permissions of EVERY component.
```

```bash
chmod 640 secrets.env      # ⭐⭐ rw- r-- ---  · owner writes, group reads, world nothing
chmod u+x deploy.sh        # ⭐ symbolic form — safer, it is a diff not a replacement
chmod 755 dir/             # ⭐ the normal directory: everyone may traverse and list
chown -R app:app /srv/app  # ⭐ owner:group
umask                      # ⭐⭐ bits SUBTRACTED from new files. 022 ⇒ files 644, dirs 755
```

⚠️ ⭐⭐ **`chmod 777` is never the fix.** It is the thing you type when you do not yet know which of
the three identities is failing — and it leaves a directory any process on the box can write to.
**Find out who the process is (Part 3), then grant that identity the minimum.**

⭐ **Two special bits worth recognising rather than using:** `setuid` (`rwsr-xr-x`, run as the file's
owner — this is how `sudo` and `ping` work, and why they are audited so heavily) and the **sticky
bit** on `/tmp` (`drwxrwxrwt`, meaning *anyone may create, but only the owner may delete* — without
it, any user could delete anyone's temp files).

# Part 3 — ⭐⭐ Users, and why your container writes root-owned files

```
⭐⭐ A USER IS A NUMBER. The name is a lookup in /etc/passwd for humans.
⭐   id            ⇒ uid=1000(ramesh) gid=1000(ramesh) groups=1000,27(sudo),999(docker)
⭐   ⇒ ⭐⭐ THE KERNEL ONLY EVER COMPARES NUMBERS.
```

```
⭐⭐ THE CONSEQUENCE THAT BITES EVERY DOCKER USER, DERIVED FROM THAT ONE FACT:
⭐   1. a container has its own /etc/passwd, but shares the HOST KERNEL.
⭐   2. by default the process inside runs as uid 0 (root).
⭐   3. a bind-mounted directory is the SAME filesystem as the host's.
⭐   ⇒ ⭐⭐ files your container writes are owned by uid 0 ON YOUR MACHINE
⭐        ⇒ you cannot delete them without sudo. Everyone hits this once.
⭐   ⇒ ⭐⭐ THE FIX, and the security fix, are the same one: run as a non-root user.
⭐        Dockerfile:  RUN useradd -u 1000 -m app   then   USER app
⭐   ⇒ ⭐⭐ AND NOW THE MIRROR BUG: uid 1000 inside must be able to write the volume
⭐        ⇒ PermissionError on startup ⇒ chown the volume, or match the host uid.
⭐        ⭐ This is the single most common "works locally, fails in the container".
```

| ⭐ Command | |
|---|---|
| `whoami` · `id` | ⭐⭐ **who is this process** — the first question, always |
| `sudo -u app python app.py` | ⭐ reproduce the service's identity *exactly* |
| `getent passwd app` | does the user exist at all |
| `groups you` | ⭐ group membership is why `docker` works without `sudo` |

⚠️ ⭐ **`sudo pip install` is the classic self-inflicted wound.** It writes into the system Python that
the OS itself depends on. **Virtualenvs and `uv` exist so that you never need root to install a
library** (Day 075) — if you are typing `sudo` to install a Python package, the environment is wrong,
not the permissions.

⭐ **Environment does not survive `sudo` by default**, which is why a script works for you and fails
under `sudo` with a missing variable — `sudo -E` preserves it, and a service manager (Day 081) is the
correct answer rather than either.

# Part 4 — ⭐ Links, and what `rm` actually removes

```
⭐⭐ A FILE IS AN INODE (the data + metadata). A DIRECTORY ENTRY IS A NAME POINTING AT IT.
⭐
⭐   ln  target  hard      ⭐ a SECOND NAME for the same inode. Same device only.
⭐   ln -s target soft     ⭐⭐ a small file CONTAINING A PATH. Can cross devices, can dangle.
⭐
⭐   ⇒ ⭐⭐ rm DOES NOT DELETE A FILE. It removes a NAME (unlink) and decrements a
⭐        link count. The data goes when the count hits zero AND no process has it open.
⭐   ⇒ ⭐⭐ THEREFORE: deleting a 40 GB log that a running process still holds open
⭐        FREES NOTHING. df stays full; du no longer sees it. ⭐ You must restart the
⭐        process, or truncate: `: > /var/log/app.log`. (Day 082 finds the holder.)
⭐   ⇒ ⭐ and it is EXACTLY reference counting (Day 026), implemented by the kernel.
```

| | Hard link | ⭐ Symlink |
|---|---|---|
| Crosses filesystems | ✗ | ⭐ ✓ |
| Survives deleting the target | ✓ | ⚠️ ✗ — dangles |
| To a directory | ✗ | ✓ |
| `ls -l` shows | nothing special | ⭐ `link -> /path/to/target` |

⭐ **You already depend on symlinks:** `.venv/bin/python` is one, pointing at the real interpreter —
which is why `python -V` inside a venv reports the right version, and why copying a `.venv` between
machines produces something broken rather than something portable.

```python
from pathlib import Path
p = Path("link")
p.is_symlink()        # ⭐ is it a link
p.readlink()          # ⭐ where does it point (may not exist)
p.resolve()           # ⭐⭐ follow everything ⇒ the real absolute path
p.stat()              # ⭐ follows the link · p.lstat() ⇒ the link ITSELF
```

⚠️ ⭐⭐ **A security note you will be asked about:** if a user supplies a filename, `Path(base) /
user_input` can escape the directory — via `../..`, or via a symlink pointing outside. **Resolve
first, then check containment**, and never trust the string:

```python
target = (base / user_input).resolve()
if not target.is_relative_to(base.resolve()):    # ⭐⭐ 3.9+ — the whole check
    raise ValueError("path traversal")
```

# Part 5 — D-01 · ⭐⭐ Why databases exist

⭐ The database block runs alongside Stage 2 (D-01…D-08) so that Stage 5 is revision, not discovery.
**It starts here because you now know what a file is.**

```
⭐⭐ SUPPOSE YOU STORE ORDERS IN orders.json AND JUST WRITE IT.
⭐   It works. On one machine, with one process, and no crashes. Then:

⭐ 1. CONCURRENCY  two workers (Day 068) read, modify, write ⇒ ⭐⭐ the LAST ONE
⭐                 WINS and the other's order VANISHES. It is Day 067's race,
⭐                 with a file instead of an integer.
⭐ 2. ATOMICITY    "debit A, credit B" is two writes. ⭐⭐ Crash between them and
⭐                 money has evaporated. Day 076's tmp+replace saves ONE file —
⭐                 ⭐⭐ it does not compose across two.
⭐ 3. QUERYING     "orders over £100 last Tuesday" ⇒ read ALL of it into RAM and
⭐                 loop. ⭐ O(n) forever, and at 8 GB it stops fitting.
⭐ 4. INTEGRITY    nothing stops an order referencing customer 999 who does not
⭐                 exist, or a negative quantity, or a duplicate id.
⭐ 5. DURABILITY   ⭐⭐ write() returns before the data is on the disk. Power cut ⇒
⭐                 the file is fine but the last minute is gone, silently.
⭐ 6. ACCESS       two machines cannot share it at all.

⭐⭐ ⇒ A DBMS IS NOT "A PLACE TO PUT DATA". It is the answer to those six, and you
⭐     will be asked to name them. ⭐ Every one has a name: isolation, atomicity,
⭐     the query planner, constraints, durability (fsync + WAL), and the network layer.
```

| ⭐ Layer of a DBMS | ⭐ What it does |
|---|---|
| Client / connection | ⭐ speaks a wire protocol over TCP (Day 008) |
| ⭐ **Parser + planner** | ⭐⭐ turns *what you want* into *how to get it* — the reason SQL is declarative |
| Executor | runs the plan |
| ⭐ **Transaction + lock manager** | ⭐⭐ makes concurrent work behave as if it were serial |
| ⭐ **Storage + buffer pool** | pages, B-trees, caching hot pages in RAM |
| ⭐ **WAL / recovery** | ⭐⭐ write the intent *before* the change ⇒ crash recovery |

⭐⭐ **The single sentence for D-01:** *"a database is a file, plus concurrency control, plus a query
planner, plus crash recovery — and you should reach for one the moment more than one thing writes."*

⭐ **And the honest counterweight:** SQLite is a real database in a single file and is in the standard
library (Day 076). *"Just use a file"* is rarely right; *"just use SQLite"* very often is.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`chmod 777` to fix an error** | ⭐⭐ Find *which identity* fails (`id`), grant the minimum. |
| Reading `x` on a directory as "execute" | ⭐⭐ It means **traverse**. No `x` ⇒ nothing inside is reachable. |
| ⭐ Expecting file perms to control deletion | ⭐⭐ Deletion needs `w` on the **directory**. |
| Temp file in `/tmp`, replace into `/var` | ⭐⭐ Different filesystem ⇒ a copy ⇒ **not atomic**. |
| ⭐ Deleting a big log to free space | ⭐⭐ Frees nothing while a process holds it open. Truncate or restart. |
| `sudo pip install` | ⭐ Breaks the system Python. Use a venv / `uv`. |
| ⭐ Container writing root-owned files | ⭐⭐ Add a `USER`; chown the volume. |
| `cp -r src/* dst` | ⭐ Skips dotfiles. Use `src/.` |
| Trusting a user-supplied path | ⭐⭐ `resolve()` then `is_relative_to()`. |
| ⭐ "Disk full" but `df` shows space | ⭐ Check inodes: `df -i`. |
| Copying a `.venv` between machines | ⭐ It is full of symlinks and absolute paths. Recreate it. |

## Interview questions

**Q: A file is `rw-r--r--` and owned by someone else. Your service can't read it. Why might that be?**
> The likely cause isn't the file at all — it's a directory on the path missing the execute bit for
> that identity. `x` on a directory means "may traverse", so if any component of `/var/lib/app/data`
> lacks it, nothing underneath is reachable no matter how open the file's own permissions are. Python
> reports the error against the file, which sends people to the wrong place. `namei -l` on the full
> path shows every component's permissions at once. And the first thing I'd check is `id` for the
> process's actual user, because "my service" usually runs as someone other than me.

**Q: Why do files created inside a Docker container end up owned by root on your machine?**
> Because a container shares the host kernel, and the kernel only compares UID numbers. By default
> the process inside runs as UID 0, a bind mount is the same filesystem as the host's, so the files
> land with owner UID 0 — which on the host is root. The fix is also the security fix: create a user
> in the image and add `USER`. Then you get the mirror problem, where that UID can't write the mounted
> volume, and you resolve it by chowning the volume or matching the host UID. It's the most common
> shape of "works locally, fails in the container".

**Q: You deleted a 40 GB log file and the disk is still full. Explain.**
> `rm` doesn't delete a file, it removes a name and decrements the inode's link count. The space is
> reclaimed when the count reaches zero *and* no process still has the file open — and the process
> that was writing that log still has it open, so the inode survives with no name. `du` can't see it
> any more but `df` still counts it, which is exactly the symptom. `lsof | grep deleted` finds the
> holder. Either restart it, or truncate the file in place with `: > file`, which keeps the same inode
> and drops the contents.

**Q: Why do databases exist? Answer as if I'd said "just write a JSON file".**
> A file gives you storage and nothing else. It gives you no concurrency control, so two writers
> lose each other's work — the same race as `+=` across threads, at file scale. No atomicity across
> more than one write, so a crash halfway through "debit and credit" destroys money. No query engine,
> so every question is a full scan in your process's memory. No constraints, so nothing stops an order
> pointing at a customer that doesn't exist. And no durability guarantee, because `write` returns long
> before the bytes are on the platter. A DBMS is a file plus solutions to those five, and the moment
> more than one thing writes, you need them. Though I'd add that "use SQLite" is often the right size
> of answer — it's a genuine transactional database in the standard library.

## 🎙️ Articulation drill

Record two minutes: **"Our API works on my laptop and throws `PermissionError` in staging."**

⭐ Do not guess. **Say the diagnostic order out loud**, because that is what is being assessed:
**"first, who is the process — `id`, or the `USER` in the Dockerfile — because it is almost never the
same identity as mine. Second, which path exactly, and `namei -l` on it, because the failure is
usually a missing traverse bit on a parent directory rather than anything about the file. Third, is it
a mounted volume, because then the owner was decided by whatever wrote it first."**

⭐⭐ **Then the sentence that shows you understand rather than remember:** *"and the fix is never
`chmod 777` — that is what you type when you have not yet identified the identity. Once you know the
UID, you grant that UID the minimum: chown the volume, or bake the user into the image so the same UID
owns it in both places."*

⭐ **Close with the trade-off**, since interviewers like to hear the cost: *"running as non-root is
also the security control — a compromised process that is uid 0 with a bind mount owns the host's
files, and one that is uid 1000 does not."*
