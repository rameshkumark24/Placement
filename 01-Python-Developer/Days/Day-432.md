# Day 432 🗄️

**P-432** · 🗄️ **Vector databases, decided honestly** — ⭐⭐ start with the Postgres you already run

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a vector database sells you one thing — approximate nearest-neighbour
> search — and "approximate" means you traded recall for latency, so the only honest way to choose one
> is to know what recall you gave up and what it bought.**

---

# Part 1 — What you are actually buying

```
⭐ STRIP THE MARKETING AND A VECTOR DATABASE IS ***THREE***
⭐   THINGS:
⭐   ⭐ ① an ***ANN index*** — sub-linear search over vectors
⭐   ⭐ ② ***metadata filtering*** that composes with ①
⭐   ⭐ ③ the ordinary database boring parts: persistence,
⭐     replication, backups, concurrent writes

⭐⭐ NOTE WHICH OF THOSE YOUR EXISTING POSTGRES ALREADY DOES
⭐   PERFECTLY. ⭐ It is ② and ③. ⭐ pgvector adds ①.

⭐ ***AND NOTE THE SCALE AT WHICH ① MATTERS AT ALL:***
⭐   ⭐ exact search over 100k × 768-dim vectors in NumPy:
⭐     ⭐⭐ ~30–60ms ON ONE CORE. ⭐ Entirely fine.
⭐   ⭐ 1M vectors: ~400ms — ⭐ borderline.
⭐   ⭐ 10M vectors: ~4s — ⭐⭐ NOW YOU NEED AN INDEX.
⭐   ⭐⭐ ⇒ SO "DO I NEED A VECTOR DATABASE?" IS REALLY "DO I
⭐     HAVE MORE THAN ABOUT A MILLION VECTORS, OR MORE THAN A
⭐     FEW QUERIES PER SECOND?" ⭐ Most internal tools have
⭐     neither and adopt one anyway.
```

# Part 2 — ⭐⭐ ANN means you chose to be wrong sometimes

```
⭐ EXACT SEARCH SCANS EVERYTHING: ⭐ O(n), 100% recall, always
⭐   correct. ⭐ ANN skips most of the space using a graph or a
⭐   partitioning, ⭐⭐ AND THEREFORE ***MISSES SOME TRUE NEAREST
⭐   NEIGHBOURS***. ⭐ That is not a bug report, it is the deal.

⭐ ***RECALL IS A DIAL, AND IT HAS A DEFAULT YOU DID NOT SET.***
⭐   ⭐⭐ MOST TEAMS RUN AT 85–95% RECALL WITHOUT KNOWING THE
⭐     NUMBER. ⭐ 5–15% of your true top-k silently absent.
⭐   ⭐ Combined with Day 430's ceiling, ⭐⭐ THAT COMPOUNDS: A
⭐     CHUNK THAT EXISTS, EMBEDS WELL, AND IS STILL NEVER
⭐     RETURNED.

⭐ ***HNSW*** — a navigable small-world graph. The knobs:
⭐   ⭐ `m` — edges per node. ⭐ Higher = better recall, more RAM,
⭐     slower build. ⭐ 16 is a fine default.
⭐   ⭐ `ef_construction` — build-time candidate list. ⭐ Higher =
⭐     better graph, much slower build. ⭐ 64–200.
⭐   ⭐ ⭐⭐ `ef_search` — QUERY-TIME CANDIDATE LIST. ***THIS IS
⭐     THE RECALL/LATENCY DIAL AND IT IS TUNABLE PER QUERY.***
⭐     ⭐ Raise it for a high-stakes query, lower it for a
⭐       typeahead. ⭐ Must be ≥ k.

⭐ ***IVFFlat*** — cluster into `lists`, search `probes` of them.
⭐   ⭐ Builds far faster, uses less RAM, ⭐⭐ WORSE RECALL AT THE
⭐     SAME LATENCY. ⭐ And a trap: ⭐⭐ IT MUST BE BUILT ***AFTER***
⭐     THE DATA EXISTS — building it on an empty table gives you
⭐     garbage clusters that never recover.

⭐⭐ ⇒ HNSW UNLESS BUILD TIME OR MEMORY FORCES OTHERWISE.
```

```
⭐ ***MEASURE YOUR RECALL. IT IS TWENTY LINES.***
⭐   ⭐ take 200 random queries
⭐   ⭐ compute exact top-10 by brute force (you can afford this
⭐     offline, once)
⭐   ⭐ run the same queries through the ANN index
⭐   ⭐⭐ RECALL = |ANN ∩ EXACT| / 10, AVERAGED.
⭐   ⭐ If it is below ~0.95, raise `ef_search` and re-measure
⭐     the latency you paid for it.
⭐   ⭐⭐ NOBODY DOES THIS. IT TAKES AN HOUR AND IT IS A REAL
⭐     DIFFERENTIATOR IN AN INTERVIEW.
```

# Part 3 — ⭐⭐ Pre-filter vs post-filter: the one that decides everything

```
⭐ THE QUERY YOU ACTUALLY RUN IS NEVER PURE SIMILARITY. ⭐ It is
⭐   ***"nearest 8 WHERE tenant_id = :t AND deleted_at IS NULL"***.
⭐   ⭐⭐ HOW THE ENGINE COMBINES THOSE DECIDES CORRECTNESS.

⭐ ① ***POST-FILTER*** — ANN first, then drop non-matching rows.
⭐   ⭐ Ask for 8, get 8 by distance, filter → ⭐⭐ YOU MIGHT
⭐     RETURN ***ZERO***. ⭐ If tenant T is 0.1% of the corpus,
⭐     the top 8 globally almost certainly contain none of T's.
⭐   ⭐ The naive patch is "over-fetch 1000 then filter", which
⭐     ⭐⭐ MAKES RESULT COUNT DEPEND ON HOW POPULAR YOUR TENANT
⭐     IS — ⭐ a small tenant silently gets worse retrieval than a
⭐     big one, forever, with no error.

⭐ ② ***PRE-FILTER*** — restrict the candidate set, then search.
⭐   ⭐ Correct result count, ⭐ but a naive implementation
⭐     degenerates to a full scan of the subset ⭐⭐ AND THROWS
⭐     AWAY THE INDEX.

⭐ ③ ***FILTERED ANN*** — the filter is evaluated ***during***
⭐   graph traversal. ⭐⭐ THIS IS THE FEATURE THAT ACTUALLY
⭐   DISTINGUISHES SERIOUS VECTOR DATABASES. ⭐ Qdrant and
⭐   Weaviate do it natively; ⭐ pgvector does it via the planner
⭐   plus `iterative scan` (0.8+), which mostly works and
⭐   occasionally does not.

⭐⭐ WHY THIS IS TOMORROW'S SECURITY LESSON TOO: ⭐ if your
⭐   permission filter is a post-filter, then "returns nothing"
⭐   and "returns another tenant's data" are the two failure
⭐   modes of the same code path (Day 434).
```

# Part 4 — pgvector, concretely

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks_v4 (
  id            bigserial PRIMARY KEY,
  doc_id        uuid        NOT NULL,
  tenant_id     uuid        NOT NULL,          -- ⭐⭐ DAY 434
  heading_path  text        NOT NULL,
  body          text        NOT NULL,
  ordinal       int         NOT NULL,
  token_count   int         NOT NULL,
  content_hash  text        NOT NULL,
  updated_at    timestamptz NOT NULL DEFAULT now(),
  embedding     vector(768) NOT NULL,
  -- ⭐ Day 433 needs this column; build it now, not later.
  tsv           tsvector GENERATED ALWAYS AS
                  (to_tsvector('english', heading_path || ' ' || body)) STORED
);

-- ⭐ vector_cosine_ops because we normalise (Day 431).
-- ⭐⭐ IF YOUR VECTORS ARE NORMALISED, INNER PRODUCT IS FASTER
-- AND EQUIVALENT: vector_ip_ops.
CREATE INDEX ON chunks_v4
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 100);

CREATE INDEX ON chunks_v4 (tenant_id);
CREATE INDEX ON chunks_v4 (doc_id);            -- ⭐ deletion path
CREATE INDEX ON chunks_v4 USING gin (tsv);     -- ⭐ Day 433
CREATE UNIQUE INDEX ON chunks_v4 (doc_id, ordinal);  -- ⭐ idempotent upsert
```

```sql
-- ⭐ The query. Note the operator and the ORDER BY shape —
-- ⭐⭐ THE INDEX IS ONLY USED FOR `ORDER BY <col> <=> $1 LIMIT n`.
-- Any other ordering, any expression, and it silently seq-scans.
SET LOCAL hnsw.ef_search = 100;                -- ⭐ the recall dial

SELECT id, doc_id, heading_path, body,
       1 - (embedding <=> $1) AS score          -- ⭐ <=> is cosine DISTANCE
  FROM chunks_v4
 WHERE tenant_id = $2                           -- ⭐⭐ NON-NEGOTIABLE
 ORDER BY embedding <=> $1
 LIMIT 50;
```

```
⭐⭐ THE FOUR pgvector TRAPS, IN THE ORDER THEY WILL BITE YOU:

⭐ ① ***`<=>` IS DISTANCE, NOT SIMILARITY.*** ⭐ Smaller is
⭐   better. ⭐⭐ SORTING DESC GIVES YOU THE ***WORST*** MATCHES
⭐   AND LOOKS PLAUSIBLE ENOUGH TO SHIP. ⭐ Operators: `<=>`
⭐   cosine, `<#>` negative inner product, `<->` L2.

⭐ ② ***THE INDEX QUIETLY GOES UNUSED.*** ⭐ Wrap the ORDER BY
⭐   in a subquery, add a different sort key, or use a different
⭐   operator class than the index was built with, ⭐⭐ AND YOU
⭐   GET A SEQUENTIAL SCAN OVER EVERY ROW WITH CORRECT RESULTS
⭐   AND 400× THE LATENCY. ⭐ `EXPLAIN ANALYZE` is not optional
⭐   here — ⭐⭐ RUN IT ONCE AND ***ASSERT ON THE PLAN IN A
⭐   TEST***.

⭐ ③ ***SELECTIVE FILTER + HNSW = TOO FEW ROWS.*** ⭐ Part 3.
⭐   ⭐ pgvector 0.8's `hnsw.iterative_scan = relaxed_order`
⭐     fixes most of it; ⭐⭐ ON OLDER VERSIONS, PARTITION BY
⭐     TENANT OR OVER-FETCH AND ACCEPT THE ARITHMETIC.

⭐ ④ ***BUILD TIME AND `maintenance_work_mem`.*** ⭐ An HNSW
⭐   build that does not fit in memory falls back to an on-disk
⭐   path that is ***orders of magnitude*** slower. ⭐⭐ SET IT
⭐   HIGH FOR THE BUILD, AND BUILD `CONCURRENTLY` IF THE TABLE
⭐   IS LIVE.
```

# Part 6 — ⭐⭐ When you actually outgrow Postgres

```
⭐ ***THE FOUR REAL TRIGGERS*** — ⭐ not one of them is "it feels
⭐   more professional":

⭐ ① ***SCALE.*** ⭐ Past roughly 10–50M vectors the HNSW index
⭐   stops fitting comfortably in RAM alongside your OLTP working
⭐   set, ⭐⭐ AND NOW YOUR VECTOR SEARCH IS EVICTING YOUR
⭐   APPLICATION'S BUFFER CACHE. ⭐ That is a real, measurable
⭐   production incident and it looks like "the app got slow".

⭐ ② ***FILTERED SEARCH AT HIGH QPS*** with highly selective
⭐   filters — Part 3. ⭐ Purpose-built engines are genuinely
⭐   better here.

⭐ ③ ***YOU NEED TO SCALE THE INDEX INDEPENDENTLY*** of the
⭐   database — different hardware, different replica count.

⭐ ④ ***OPERATIONAL ISOLATION.*** ⭐⭐ YOU DO NOT WANT A REINDEX
⭐   TO BE ABLE TO TAKE DOWN CHECKOUT. ⭐ This one is a real
⭐   architectural argument and it arrives earlier than ①.

⭐ ***AND THE THING THAT MAKES THE MOVE CHEAP:*** ⭐ put a
⭐   protocol in front on day one. ⭐⭐ IT IS TWENTY LINES AND IT
⭐   TURNS A MIGRATION INTO A NEW CLASS.
```

```python
from typing import Protocol, Sequence
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class Hit:
    chunk_id: str
    doc_id: str
    score: float
    heading_path: str
    body: str

class VectorStore(Protocol):
    async def upsert(self, rows: Sequence["ChunkRow"]) -> None: ...

    async def search(
        self,
        vector: Sequence[float],
        *,
        tenant_id: str,          # ⭐⭐ REQUIRED. KEYWORD-ONLY. NO DEFAULT.
        k: int = 50,
        ef_search: int | None = None,
    ) -> list[Hit]: ...

    async def delete_document(self, *, tenant_id: str, doc_id: str) -> int: ...
```

```
⭐⭐ NOTE THE THREE DESIGN DECISIONS IN THAT PROTOCOL:
⭐   ⭐ `tenant_id` is required and keyword-only, ⭐⭐ SO A
⭐     PERMISSION LEAK IS A ***TYPE ERROR*** AND NOT A CODE
⭐     REVIEW MISS (Day 434);
⭐   ⭐ `ef_search` is exposed, ⭐ because recall is a per-query
⭐     decision, not a global constant;
⭐   ⭐ `delete_document` exists at all — ⭐⭐ MOST WRAPPERS
⭐     FORGET DELETION UNTIL LEGAL ASKS.
```

# 💬 Interview

**1. "Which vector database did you choose and why?"**

⭐ pgvector, because the honest answer to "do I need a vector database" was no. ⭐⭐ We had about 300,000
chunks and single-digit queries per second — exact search over that in NumPy is under a hundred
milliseconds, and Postgres with HNSW is a couple of milliseconds. ⭐ What I got for free was the part
that's actually hard: the chunk row and the document row commit in the **same transaction**, so I can
never have an indexed chunk for a document that failed to save; backups, replication and point-in-time
recovery already existed; and I can join retrieval results to permission tables. ⭐⭐ I'd move to Qdrant
when one of four things becomes true — tens of millions of vectors, filtered search at high QPS,
needing to scale the index independently, or operational isolation so a reindex can't affect checkout.
⭐ To keep that cheap I put a `VectorStore` protocol in front from day one.

**2. "What does 'approximate' cost you?"**

⭐ Recall, and most teams never measure it. ⭐⭐ Typical defaults land you at 85 to 95% — so 5 to 15% of
your true top-k is silently missing, on top of whatever chunking already lost. ⭐ Measuring it is about
twenty lines: take 200 queries, compute exact top-10 by brute force offline, run the same queries
through the ANN index, and report the intersection size over 10. ⭐⭐ In HNSW the dial is `ef_search`,
and the useful property is that it's **per query** — you can run a high-stakes compliance lookup at
`ef_search=400` and a typeahead at 40. ⭐ I'd avoid IVFFlat unless build time forces it, and if I did
use it I'd remember it must be built after the data exists, because building it on an empty table gives
you clusters that never recover.

**3. "Explain pre-filter versus post-filter."**

⭐ It's the difference between "nearest 8, then keep the ones for this tenant" and "among this tenant's
rows, the nearest 8". ⭐⭐ Post-filtering breaks in a way that's specific and nasty: if a tenant is 0.1%
of the corpus, the global top-8 almost certainly contains none of theirs, so you return zero results.
⭐ The reflex fix — over-fetch a thousand and filter — makes result quality a function of how popular
your tenant is, so small tenants silently get worse retrieval forever with no error. ⭐⭐ What you
actually want is the filter evaluated *during* graph traversal, which is the feature that genuinely
separates purpose-built vector databases. ⭐ In pgvector that's the planner plus iterative scan in 0.8;
on older versions you partition by tenant.

**4. "What's the pgvector bug that cost you the most time?"**

⭐ The index silently not being used. ⭐⭐ pgvector only uses the HNSW index for the exact shape
`ORDER BY column <operator> $1 LIMIT n` — wrap it in a subquery, add a secondary sort key, or use an
operator that doesn't match the index's operator class, and you get a sequential scan over every row.
⭐ The results are **correct**, which is why it survives review; it's just 400 times slower. ⭐⭐ Now I
run `EXPLAIN` in a test and assert the plan contains an index scan, because it's the kind of regression
that arrives with an unrelated refactor. ⭐ The other one is `<=>` being a *distance*: sorting
descending gives you the worst matches and the output still looks plausible.

**5. "Someone proposes FAISS in production. What do you say?"**

⭐ That FAISS is a library, not a database, and the distinction is the whole conversation. ⭐⭐ It has no
persistence you didn't write, no metadata filtering, no concurrent writes, and deletion is effectively
a rebuild. ⭐ So the moment you need "this tenant only", or "the process restarted", or "the user deleted
that document", you're writing a database — badly. ⭐ It's excellent as an embedded index inside
something else, which is exactly how several vector databases use it.

**6. "How do you handle deleting a document?"**

⭐ It has to be a first-class operation, which is why `delete_document` is on my store protocol rather
than something I'd bolt on. ⭐⭐ The index is derived state, so deleting from the source of truth does
nothing to it — that's how systems end up serving content that legally no longer exists. ⭐ In Postgres
I get this nearly free: the delete happens in the same transaction as the source delete, keyed by
`doc_id`, which is exactly why I insisted on carrying `doc_id` on every chunk at ingest. ⭐⭐ With a
separate vector service it's a distributed-systems problem, and the correct shape is the outbox from
Day 407, not a best-effort call after commit.

## 🎙️ Articulation drill

⭐⭐ **Two minutes, out loud: "how did you choose your vector store?"**

Open by refusing the framing, politely. **The question I asked first wasn't which vector database — it
was whether I needed one. Strip the marketing and you're buying approximate nearest-neighbour search;
metadata filtering, persistence and backups are things my Postgres already does. And exact search over
a hundred thousand vectors is tens of milliseconds in NumPy, so below about a million vectors and a few
queries a second, the index isn't the bottleneck and adopting a second datastore is pure operational
cost.**

Then what pgvector bought that isn't on any comparison chart. **The chunk and the document row commit
in the same transaction, so I can't have an indexed chunk for a document that failed to save. Deletion
is a foreign key away, which matters because the index is derived state and deleting from the source
does nothing to it — that's how systems keep serving content that legally no longer exists. And backups
and PITR already existed.**

Then show you know what you gave up. **Approximate means recall, and most teams never measure theirs —
defaults put you at eighty-five to ninety-five percent, so a tenth of your true top-k is silently
missing on top of whatever chunking already lost. I measured it against brute force on two hundred
queries and swept `ef_search` to pick an operating point, and the useful part is that it's per-query, so
a compliance lookup runs at four hundred and a typeahead runs at forty.**

Close on the two scars, because they're specific. **First, pgvector only uses the HNSW index for exactly
`ORDER BY column <=> $1 LIMIT n` — wrap it in a subquery and you get a sequential scan with correct
results and four hundred times the latency, which is why I assert on the query plan in a test. Second,
post-filtering. If a tenant is a tenth of a percent of the corpus, the global top-eight contains none of
their rows and you return nothing; over-fetching a thousand doesn't fix it, it just makes retrieval
quality depend on how big your tenant is. That's why the filter is inside the query and the tenant is a
required argument on the store interface — which is tomorrow's subject, because that same code path is
how these systems leak data.**
