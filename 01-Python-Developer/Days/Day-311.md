# Part 3 — ⭐⭐ 10–15 minutes: the flow, aloud

```
⭐   ⭐ car arrives → ⭐ allocation strategy picks a free spot
⭐     that FITS → ⭐⭐ SPOT IS OCCUPIED ATOMICALLY → ticket
⭐     issued → … → ⭐ ticket presented → duration computed →
⭐     pricing strategy returns Money → spot freed → ticket
⭐     closed

⭐⭐ TWO DESIGN DECISIONS SURFACE HERE, AND THEY ARE THE ONLY
⭐   TWO THAT MATTER:

⭐ ① ⭐⭐ WHO OWNS "IS THIS SPOT FREE?"
⭐     ⭐ Option A: `ParkingLot` holds a set of free spots.
⭐          ⇒ ⭐ O(1) allocation, ⭐⭐ AND THE OCCUPANCY TRUTH
⭐            NOW LIVES IN TWO PLACES (the set and the spot),
⭐            which must be kept consistent — a second invariant
⭐            created to optimise the first.
⭐     ⭐ Option B: `Spot` owns its own occupancy.
⭐          ⇒ ⭐⭐ ONE SOURCE OF TRUTH, ONE PLACE TO LOCK, AND
⭐            THE INVARIANT IS ***INSIDE THE THING IT
⭐            CONSTRAINS*** (Day 302). ⭐ Allocation is a scan.
⭐     ⇒ ⭐⭐ CHOOSE B, AND SAY WHY: correctness first, and the
⭐       index is an optimisation you add ***with*** a
⭐       consistency story, not instead of one. ⭐ Then mention
⭐       A as the scaling answer — that sequence is the signal.

⭐ ② ⭐ ALLOCATION IS A ***STRATEGY***, NOT AN `if` CHAIN,
⭐     because question ③ said types are fixed but the *rule*
⭐     (nearest, cheapest, level-balanced) is exactly what
⭐     changes. ⭐⭐ THE ABSTRACTION GOES ON THE AXIS THAT
⭐     VARIES (Day 298).
```

# Part 4 — ⭐⭐ 15–30 minutes: the core

```python
class SpotSize(IntEnum):                    # ⭐ Int so it orders
    MOTORCYCLE = 1; COMPACT = 2; LARGE = 3

FITS: dict[VehicleType, list[SpotSize]] = { # ⭐⭐ DATA, NOT ifs
    VehicleType.MOTORCYCLE: [SpotSize.MOTORCYCLE, SpotSize.COMPACT,
                             SpotSize.LARGE],
    VehicleType.CAR:        [SpotSize.COMPACT, SpotSize.LARGE],
    VehicleType.TRUCK:      [SpotSize.LARGE],
}

@dataclass
class Spot:
    id: SpotId
    floor: int
    size: SpotSize
    _occupied_by: Plate | None = None
    _lock: Lock = field(default_factory=Lock, repr=False)

    def try_occupy(self, plate: Plate) -> bool:   # ⭐⭐ CHECK+ACT, ONE OP
        with self._lock:
            if self._occupied_by is not None:
                return False
            self._occupied_by = plate
            return True

    def release(self) -> None:
        with self._lock:
            self._occupied_by = None

class AllocationStrategy(Protocol):          # ⭐ Day 300
    def choose(self, spots: Sequence[Spot],
               vehicle: Vehicle) -> Spot | None: ...

class NearestFirst:
    def choose(self, spots, vehicle):
        allowed = FITS[vehicle.type]
        candidates = [s for s in spots
                      if s.size in allowed and s.is_free]
        return min(candidates, key=lambda s: (s.floor, s.id),
                   default=None)
```

```python
class ParkingLot:                            # ⭐⭐ THE AGGREGATE ROOT
    def park(self, vehicle: Vehicle) -> Ticket:
        for _ in range(MAX_RETRIES):         # ⭐⭐ SEE PART 5
            spot = self._allocation.choose(self._spots, vehicle)
            if spot is None:
                raise LotFull(vehicle.type)
            if spot.try_occupy(vehicle.plate):
                return self._tickets.issue(spot, vehicle, self._clock.now())
        raise LotFull(vehicle.type)          # ⭐ lost every retry
```

```
⭐⭐ FIVE THINGS IN THAT CODE THAT ARE BEING SCORED:
⭐   ⭐ `FITS` AS DATA — ⭐⭐ a motorcycle fitting a large spot
⭐     is a business rule, and as a dict it is one line to
⭐     change and trivially testable. As nested `if`s it is a
⭐     refactor.
⭐   ⭐ `try_occupy` RETURNS A BOOL — ⭐⭐ CHECK AND ACT AS ONE
⭐     OPERATION (Day 310), not two.
⭐   ⭐ ⭐⭐ THE RETRY LOOP — the strategy chose a spot, someone
⭐     else took it, so you choose again. ⭐ Most candidates
⭐     never notice this window exists.
⭐   ⭐ `LotFull` AS AN EXCEPTION, not `None`.
⭐   ⭐ A CLOCK PASSED IN (Day 303) — ⭐ so pricing is testable
⭐     without sleeping.
```

# Part 5 — ⭐⭐ 30–40 minutes: the race, properly

```
⭐⭐ THE QUESTION: "TWO CARS ARRIVE AT DIFFERENT ENTRANCES AND
⭐   THERE IS ONE SPOT LEFT."

⭐   ⭐ THE SHARED MUTABLE STATE: `Spot._occupied_by`.
⭐   ⭐ THE INVARIANT: at most one vehicle per spot.
⭐   ⭐ THE MECHANISM: ⭐⭐ THE PER-SPOT LOCK MAKES CHECK+ACT
⭐        ATOMIC, SO EXACTLY ONE `try_occupy` RETURNS `True`.
⭐        ⭐ Per-spot rather than one global lock, ⭐⭐ SO TWO
⭐        CARS TAKING ***DIFFERENT*** SPOTS DO NOT CONTEND — a
⭐        global lock would be correct and would serialise the
⭐        entire lot.
⭐   ⭐ THE LOSER RETRIES and gets a different spot, ⭐ or
⭐        exhausts retries and gets `LotFull`.

⭐⭐ AND THEN, UNPROMPTED (Day 310's high-value sentence):
⭐   ⭐ "This is correct in one process. ⭐⭐ WITH TWO SERVERS
⭐     THERE ARE TWO LOCKS AND THE INVARIANT IS GONE — the code
⭐     is unchanged and the tests still pass."
⭐   ⭐ ⭐⭐ THE FIX IS TO MOVE THE INVARIANT INTO THE DATABASE:
⭐        UPDATE spots SET occupied_by = :plate
⭐         WHERE id = :id AND occupied_by IS NULL;
⭐        -- ⭐⭐ rowcount 1 = won, 0 = lost. NO LOCK NEEDED.
⭐     ⭐ Plus a partial unique index so a plate cannot occupy
⭐       two spots — ⭐⭐ THE ***SECOND HALF*** OF THE INVARIANT,
⭐       WHICH ALMOST NOBODY IMPLEMENTS: the per-spot lock says
⭐       nothing about one car being in two spots.
```

```
⭐ ⭐ THE TEST YOU OFFER (Day 310): ⭐⭐ 50 THREADS, ONE FREE
⭐   SPOT, ***ASSERT EXACTLY ONE*** SUCCESS AND 49 `LotFull`.
⭐   ⭐ Not `<= 1`, which passes when everything fails.
```

# Part 6 — ⭐ Pricing, and the second strategy

```python
class PricingStrategy(Protocol):
    def price(self, ticket: Ticket, now: datetime) -> Money: ...

class HourlyByType:
    RATES = {VehicleType.MOTORCYCLE: 20,     # ⭐ paise/minor units
             VehicleType.CAR: 40, VehicleType.TRUCK: 80}
    def price(self, ticket, now):
        minutes = (now - ticket.entry_time).total_seconds() / 60
        hours = ceil(minutes / 60)           # ⭐⭐ PART HOURS ROUND UP
        return Money(hours * self.RATES[ticket.vehicle_type], INR)
```

```
⭐   ⭐ `Money` (Day 304), never a float.
⭐   ⭐⭐ ROUNDING IS A ***BUSINESS RULE***, NOT AN
⭐     IMPLEMENTATION DETAIL — ⭐ "do part hours round up?" is
⭐     a question to ask, and ⭐⭐ ASKING IT SCORES BECAUSE IT
⭐     IS EXACTLY THE KIND OF THING THAT GETS DISCOVERED IN
⭐     PRODUCTION BY A COMPLAINT.
⭐   ⭐ A free grace period, a daily maximum and weekend rates
⭐     all become ⭐⭐ NEW STRATEGIES, NOT `if`s — which is the
⭐     payoff of having asked question ④ in Part 1.
```

# Part 7 — ⭐⭐ The extensions they will ask for

```
⭐⭐ ① "ADD EV CHARGING SPOTS."
⭐   ⭐ ❌ A new `SpotSize` ⇒ ⭐⭐ WRONG AXIS. Charging is not
⭐        a size; a large spot may or may not charge.
⭐   ⭐ ✅ ⭐⭐ A ***CAPABILITY SET*** ON `Spot` (`{EV_CHARGER}`)
⭐        AND A REQUIREMENT SET ON `Vehicle`. ⭐ `FITS` becomes
⭐        size-fit AND capability-superset — ⭐⭐ AND NOTHING
⭐        ELSE IN THE DESIGN CHANGES, which is the answer they
⭐        are testing for.

⭐⭐ ② "ADD RESERVATIONS."
⭐   ⭐ ⭐⭐ THIS BREAKS THE MODEL, AND SAYING SO IS CORRECT:
⭐     occupancy becomes ***time-ranged***, so a spot is not
⭐     free/occupied but has intervals — ⭐ which is Day 250's
⭐     `EXCLUDE USING gist` problem exactly. ⭐⭐ NAMING THAT
⭐     CONNECTION IS THE STRONGEST POSSIBLE ANSWER HERE.

⭐⭐ ③ "MULTIPLE LOTS."
⭐   ⭐ `ParkingLot` is already the aggregate root, ⭐ so it is
⭐     a collection plus a lot id on `Spot`. ⭐⭐ AND THE REAL
⭐     ANSWER: THE PER-SPOT LOCK IS NOW DEFINITELY WRONG,
⭐     because multiple lots means multiple servers.

⭐⭐ ④ "THE DISPLAY BOARD SHOWS FREE SPOTS PER FLOOR."
⭐   ⭐ ⭐⭐ A READ, SO IT DOES NOT GO THROUGH THE AGGREGATE
⭐     (Day 301). ⭐ A counter or a query, and it may be stale
⭐     by a second — ⭐ which is a decision to state, not a
⭐     defect.

⭐ ⇒ ⭐⭐ CLOSE (Day 308): three tests you'd write first, one
⭐   thing you'd change with more time, ⭐⭐ AND WHAT BREAKS AT
⭐   100×: "the allocation scan is O(spots) per arrival —
⭐   fine at 500 spots, and at 50,000 I'd add a per-(floor,size)
⭐   free set ***with*** the consistency story I skipped in
⭐   Part 3."
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Modelling `Colour`, `Gate`, `DisplayBoard` | You run out of time before the part being assessed. |
| Not asking about concurrency | It's the whole problem, and asking early signals you know it. |
| A strategy interface with no varying requirement | Gold-plating unless you asked and got a yes. |
| Vehicle-to-spot fitting as nested `if`s | It's a business rule; make it data. |
| `is_free` then `occupy` as two calls | Check-then-act — the bug this problem exists to test. |
| One global lock | Correct and it serialises the entire lot. Lock per spot. |
| No retry after losing a spot | The strategy chose it, someone else took it; most candidates never see this window. |
| Returning `None` when full | `LotFull` says what happened. |
| Occupancy tracked in both a set and the spot | Two sources of truth, and a second invariant to protect the first. |
| `datetime.now()` inside pricing | Pass a clock, or you can't test without sleeping. |
| Floats for money | Use minor units in a `Money` value object. |
| Not asking about rounding | Part hours are a business rule discovered in production by complaint. |
| Treating an in-process lock as the final answer | Two servers means two locks and no invariant, with tests still passing. |
| Only enforcing one half of the invariant | A per-spot lock says nothing about one car in two spots. |
| Making EV charging a size | Wrong axis. Capabilities and requirements. |
| Treating reservations as a small change | Occupancy becomes time-ranged, which is the overlap-constraint problem. |
| Routing the display board through the aggregate | It's a read; staleness is a stated decision. |
| `assert successes <= 1` | Passes when everything fails. Assert exactly one. |

## Interview questions

**Q: Walk me through your parking lot design.**

> Five classes: `ParkingLot` as the aggregate root, `Spot`, `Vehicle`, `Ticket`, plus two protocols
> for allocation and pricing. Sizes and vehicle types are enums, the fit rules are a dict rather than
> nested conditionals because that's a business rule, and entrances, exits and the display board
> aren't modelled — they're where the API gets called from, or reads over occupancy. The invariant I'm
> protecting is at most one vehicle per spot and a vehicle in at most one spot, and everything
> interesting in the design exists to hold that sentence.

**Q: Who owns whether a spot is free?**

> The spot itself, and I'd explain the alternative I rejected. The lot could hold a set of free spots,
> which gives O(1) allocation — but then occupancy lives in two places that must be kept consistent,
> so I've created a second invariant in order to optimise the first. Putting it on the spot gives one
> source of truth, one place to lock, and the invariant inside the thing it constrains. The free-set
> index is the scaling answer, and I'd add it *with* a consistency story rather than instead of one.

**Q: Two cars arrive at once and there's one spot left.**

> The shared mutable state is the spot's occupancy; the invariant is one vehicle per spot; the
> mechanism is a per-spot lock making check-and-act atomic, so exactly one `try_occupy` returns true.
> Per-spot rather than global, so two cars taking different spots don't contend — a global lock would
> be correct and would serialise the whole lot. The loser retries and gets a different spot, which is
> a window most designs don't notice: the strategy chose a spot and someone else took it between
> choosing and occupying.

**Q: What changes with two servers?**

> The lock stops working, and silently — there are now two locks, the code is unchanged, and the tests
> still pass. So the invariant moves into the database: a conditional update setting `occupied_by`
> where it's currently null, with the affected-row count as the answer, and no application lock at
> all. Plus a partial unique index on the plate, because that's the half of the invariant almost
> nobody implements — a per-spot lock says nothing about one car occupying two spots. And the test is
> fifty threads against one free spot asserting exactly one success, not at most one, because `<= 1`
> passes when a bug rejects everything.

**Q: Add EV charging spots.**

> Not as a new size — charging isn't a size, and a large spot may or may not have a charger, so that's
> the wrong axis. A capability set on the spot and a requirement set on the vehicle, with the fit check
> becoming size-fit plus capability-superset. Nothing else in the design changes, which is what the
> question is really testing. The extension that *does* break the model is reservations: occupancy
> becomes time-ranged rather than a boolean, so a spot has intervals — which is exactly the
> non-overlapping constraint problem, and in Postgres it's an `EXCLUDE USING gist` on a range.

## 🎙️ Articulation drill

**Three minutes: the full parking lot walkthrough.**

Thirty seconds of scope: five classes, two protocols, **entrances and the display board deliberately
not modelled**, and the invariant stated up front — at most one vehicle per spot, and a vehicle in at
most one spot. Sixty seconds on the two decisions that matter. **Who owns occupancy**: the spot, not a
free-set in the lot, because a set means occupancy lives in two places and I've created a second
invariant to optimise the first — with the index as the scaling answer that comes *with* a consistency
story. And **allocation as a strategy while sizes stay an enum**, because the abstraction goes on the
axis that varies. Sixty seconds on the race, using the four-sentence form: shared state is the spot's
occupancy, the invariant is one vehicle per spot, the mechanism is a per-spot lock making check-and-act
one operation — **per-spot rather than global, so two cars taking different spots don't contend** — and
the loser retries, which is a window most designs never notice. Then the sentence that separates this
from a textbook answer: **with two servers there are two locks and the invariant is gone, silently,
with the tests still passing** — so it becomes a conditional `UPDATE` whose rowcount is the answer,
plus a partial unique index on the plate, **which is the half of the invariant almost nobody
implements.** Close with thirty seconds of extensions: EV charging is a capability, not a size;
reservations make occupancy time-ranged, which is the overlap-constraint problem; and the allocation
scan is O(spots), fine at 500 and worth indexing at 50,000.
