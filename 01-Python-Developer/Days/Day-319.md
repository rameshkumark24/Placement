# Part 2 — ⭐⭐ Snakes and Ladders, small on purpose

```python
@dataclass(frozen=True)
class Board:
    size: int = 100
    jumps: Mapping[int, int] = field(default_factory=dict)  # ⭐ snakes AND ladders

    def move(self, frm: int, roll: int) -> int:
        target = frm + roll
        if target > self.size:
            return frm                      # ⭐⭐ OVERSHOOT: a RULE, ask for it
        return self.jumps.get(target, target)
```

```
⭐⭐ FOUR DECISIONS, EACH DELIBERATE:
⭐   ⭐ SNAKES AND LADDERS ARE ***ONE*** DICT. ⭐⭐ THEY DIFFER
⭐     ONLY IN WHETHER THE DESTINATION IS HIGHER — ⭐ two classes
⭐     for that is the over-engineering being tested.
⭐   ⭐ THE DIE IS INJECTED (Day 303) ⇒ ⭐⭐ THE GAME IS
⭐     TESTABLE AND REPRODUCIBLE. ⭐ A `random` call inside the
⭐     game is the single most common testability failure here.
⭐   ⭐ OVERSHOOT IS A ***RULE VARIANT*** — ask. ⭐ Some
⭐     versions bounce back, some stay. ⭐⭐ ASKING SHOWS YOU
⭐     KNOW RULES ARE REQUIREMENTS.
⭐   ⭐ CHAINED JUMPS: ⭐ if a ladder lands on a snake, do you
⭐     follow it? ⭐⭐ ONE `get` OR A `while` LOOP — AND A
⭐     `while` NEEDS CYCLE DETECTION, so ask rather than assume.
⭐ ⇒ ⭐ Total: ~40 lines. ⭐⭐ SPEND THE REMAINING TIME ON
⭐   CHESS, AND SAY THAT YOU ARE.
```

# Part 3 — ⭐⭐ Chess: the fact that reorganises everything

```
⭐⭐ ***A MOVE IS LEGAL ONLY IF, AFTER MAKING IT, YOUR OWN KING
⭐   IS NOT ATTACKED.***
⭐   ⇒ ⭐ So legality cannot be answered by the piece. ⭐⭐ A
⭐     BISHOP DOES NOT KNOW WHETHER MOVING EXPOSES THE KING, AND
⭐     IT CANNOT KNOW WITHOUT SEEING THE WHOLE BOARD AFTER THE
⭐     MOVE.

⭐⭐ HENCE THE TWO-LAYER SPLIT, WHICH IS THE ANSWER:
⭐   ⭐ ⭐⭐ LAYER 1 — ***PSEUDO-LEGAL MOVES***: what this piece
⭐        can do given occupancy. ⭐ Owned by the piece. Pure.
⭐   ⭐ ⭐⭐ LAYER 2 — ***LEGAL MOVES***: pseudo-legal moves
⭐        filtered by simulating each one and rejecting those
⭐        that leave your king attacked. ⭐ Owned by the game.
⭐   ⇒ ⭐⭐ CHECK, CHECKMATE, STALEMATE AND PINS ALL FALL OUT OF
⭐     THIS FOR FREE, AND THAT IS THE PAYOFF:
⭐     ⭐ CHECK = your king is attacked
⭐     ⭐ CHECKMATE = in check ***and*** no legal moves
⭐     ⭐ STALEMATE = not in check ***and*** no legal moves
⭐     ⭐⭐ A PIN NEEDS NO CODE AT ALL — the pinned piece's
⭐       moves simply fail the filter.
⭐   ⇒ ⭐ Candidates who try to detect pins directly write a
⭐     hundred lines that this design deletes.
```

```python
def legal_moves(self, colour: Colour) -> list[Move]:
    out = []
    for mv in self._pseudo_legal(colour):
        undo = self._apply(mv)              # ⭐⭐ MAKE
        if not self._is_attacked(self._king_square(colour), colour.other):
            out.append(mv)
        self._undo(undo)                    # ⭐⭐ UNMAKE
    return out
```

```
⭐⭐ MAKE/UNMAKE RATHER THAN COPYING THE BOARD:
⭐   ⭐ Copying a board per candidate move is ~40 copies per
⭐     position — ⭐ correct, and it is the right first version.
⭐   ⭐⭐ MAKE/UNMAKE IS THE REAL ANSWER, AND IT ***REQUIRES***
⭐     THE UNDO RECORD PART 5 NEEDS ANYWAY — so the performance
⭐     answer and the undo feature are the same object.
⭐   ⇒ ⭐ Say both, and say which you would write first.
```

# Part 4 — ⭐⭐ Pieces, and the three rules that break the model

```
⭐⭐ PIECES: ⭐ a `Piece` protocol with `pseudo_moves(board, sq)`.
⭐   ⭐ Sliding pieces (bishop, rook, queen) share a direction
⭐     walk; knights and kings are offset lists. ⭐⭐ SO IT IS
⭐     TWO ALGORITHMS AND A TABLE OF DIRECTIONS, NOT SIX
⭐     UNRELATED CLASSES.

⭐⭐ AND THE THREE RULES THAT DO NOT FIT "A PIECE MOVES":
⭐   ① ⭐⭐ CASTLING — involves TWO pieces, depends on
⭐        ***history*** (neither has moved), and on three squares
⭐        not being attacked. ⭐ It belongs to the game, not the
⭐        king.
⭐   ② ⭐⭐ EN PASSANT — depends on the ***previous move only***,
⭐        ⭐ so the board state alone is insufficient. ⭐⭐ THIS
⭐        IS THE ONE THAT PROVES YOU NEED MORE THAN PIECE
⭐        POSITIONS IN YOUR STATE.
⭐   ③ ⭐ PROMOTION — a move that ***replaces*** a piece, so
⭐        `Move` needs a `promotion` field and undo must restore
⭐        the pawn.

⭐ ⇒ ⭐⭐ THEREFORE GAME STATE IS NOT JUST THE BOARD:
⭐   ⭐ piece placement · side to move · castling rights ·
⭐     en-passant square · halfmove clock · fullmove number
⭐   ⇒ ⭐⭐ WHICH IS EXACTLY FEN. ⭐ Naming FEN and saying "the
⭐     standard notation already enumerates the state you need"
⭐     is a strong, cheap signal — ⭐ and it gives you draw
⭐     detection (fifty-move, threefold repetition) for free,
⭐     because repetition compares these fields, not the pieces
⭐     alone.
```

# Part 5 — ⭐⭐ Move, undo, and why the record is the design

```python
@dataclass(frozen=True)
class Move:
    frm: Square; to: Square
    promotion: PieceType | None = None      # ⭐ ③

@dataclass                                   # ⭐⭐ EVERYTHING NEEDED TO REVERSE
class Undo:
    move: Move
    captured: Piece | None                  # ⭐ incl. en-passant victim
    captured_square: Square                 # ⭐⭐ NOT ALWAYS move.to
    prev_castling: CastlingRights
    prev_ep_square: Square | None
    prev_halfmove: int
```

```
⭐⭐ THREE OBSERVATIONS THAT SCORE:
⭐   ⭐ ⭐⭐ `captured_square` IS SEPARATE FROM `move.to` — ⭐ en
⭐     passant captures a pawn that is not on the destination.
⭐     ⭐⭐ FORGETTING THIS IS THE CLASSIC UNDO BUG, and it
⭐     appears only in one rare position.
⭐   ⭐ ⭐⭐ UNDO MUST RESTORE ***RIGHTS***, NOT JUST PIECES.
⭐     ⭐ Moving a rook back does not restore castling rights,
⭐     because those were lost by the move having happened.
⭐   ⭐ ⭐⭐ THE UNDO STACK ***IS*** THE GAME HISTORY — so undo,
⭐     move-list, replay, threefold repetition and PGN export are
⭐     one data structure. ⭐ One record, five features.
```

# Part 6 — ⭐ The rest, and the extensions

```
⭐   ⭐ ⭐⭐ SEPARATE ***RULES*** FROM ***GAME***: `Rules` is
⭐     pure functions over a position; `Game` holds history,
⭐     clocks and players. ⭐ Then a variant (Chess960,
⭐     three-check) is a different `Rules`, ⭐ and an engine can
⭐     use `Rules` without a `Game` at all.
⭐   ⭐ PERFORMANCE, if asked: ⭐ bitboards, ⭐⭐ AND THE HONEST
⭐     ANSWER — "not until profiling says so; the design above
⭐     supports it because `Rules` is already isolated."
⭐   ⭐ TIMERS ⇒ ⭐ a clock per player, decremented on move,
⭐     with time itself injected (Day 254).
⭐   ⭐ ⭐⭐ TWO PLAYERS OVER A NETWORK ⇒ this stops being an LLD
⭐     problem: the server is authoritative, the client's board is
⭐     a cache, and every move is validated server-side —
⭐     ⭐ because a client that computes legality is a client that
⭐     can cheat (Day 294's rule: ***the output of something you
⭐     do not control is untrusted input***).
⭐ ⇒ ⭐ CLOSE: three tests (legal-move counts by perft depth,
⭐   en-passant undo, stalemate detection); one change
⭐   (make/unmake instead of copying); ⭐⭐ AT 100×: it is a
⭐   single-game problem — the scale question is thousands of
⭐   concurrent games, which is a stateless-server question.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Over-engineering Snakes and Ladders | It's forty lines; the question is testing whether you know that. |
| Separate Snake and Ladder classes | They differ only in direction of the destination. |
| `random` inside the game | The game becomes untestable and irreproducible. |
| Assuming the overshoot rule | It's a variant; asking shows rules are requirements. |
| Putting legality in the piece | A bishop can't know whether moving exposes the king. |
| Detecting pins directly | They fall out of the make-test-unmake filter for free. |
| Copying the board per candidate move | Correct first, but make/unmake needs the undo record you already want. |
| Six unrelated piece classes | Two algorithms — sliding and offsets — plus a direction table. |
| Modelling only piece positions | En passant depends on the previous move; castling on history. |
| Not knowing FEN | It enumerates exactly the state you need, and gives repetition detection. |
| Undo restoring only pieces | Castling rights and the en-passant square must be restored too. |
| Assuming the captured square is `move.to` | En passant captures elsewhere — the classic undo bug. |
| Keeping undo separate from history | One record gives undo, replay, repetition and export. |
| Reaching for bitboards unprompted | Not until profiling; say the design supports it. |
| Client-side legality in a networked game | The client can cheat; the server is authoritative. |

## Interview questions

**Q: What's the hard part of chess?**

> That a move's legality depends on the position it creates — you can't know if a move is legal until
> you've made it and checked whether your own king is attacked. That single fact reorganises the
> design into two layers: pseudo-legal moves, which the piece owns and are pure given occupancy, and
> legal moves, which the game owns by simulating each candidate and rejecting the ones that leave the
> king in check. The payoff is that check, checkmate, stalemate and pins all fall out for free — a
> pinned piece needs no code at all, its moves simply fail the filter. Candidates who try to detect
> pins directly write a hundred lines this design deletes.

**Q: How do you model game state?**

> Not as piece positions, because two rules break that. En passant depends on the previous move only,
> so the board alone is insufficient, and castling depends on whether pieces have ever moved. So the
> state is placement, side to move, castling rights, the en-passant square, the halfmove clock and the
> move number — which is exactly FEN, and I'd say so, because the standard notation already enumerates
> the state you need. It also gives you threefold repetition and the fifty-move rule for free, since
> repetition compares those fields rather than the pieces alone.

**Q: How do you implement undo?**

> With a record that captures everything needed to reverse the move: the move, the captured piece
> *and the square it was captured on* — separate, because en passant captures a pawn that isn't on the
> destination, and conflating them is the classic undo bug that only shows up in one rare position —
> plus the previous castling rights, en-passant square and halfmove clock, because moving a rook back
> doesn't restore rights that were lost by the move having happened. And that undo stack *is* the game
> history, so undo, move list, replay, repetition detection and PGN export are all one data structure.

**Q: And Snakes and Ladders?**

> Deliberately small: a frozen board with one dict of jumps, because snakes and ladders differ only in
> whether the destination is higher, an injected die so the game is reproducible and testable, and a
> loop. About forty lines. I'd ask two rule questions — what happens on an overshoot, and whether
> chained jumps are followed, since a chain needs cycle detection — and then say I'm spending the rest
> of the time on chess. The question is really testing whether I'll build a `MoveValidator` hierarchy
> for a game that has no legality question at all.
