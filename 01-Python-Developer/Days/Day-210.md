# Day 210

**L-210** · 🍃 **MongoDB and the document model** — ⭐⭐ what it is genuinely good at, and the bar it must clear

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: in SQL you model the *data* and then write queries against it. In
> MongoDB you model the *queries* and then store data shaped to fit them. Everything good and
> everything painful about MongoDB follows from that one inversion.**
>
> ⭐⭐ **And the consequence nobody says out loud: a genuinely new access pattern is a migration.**
>
> ⭐ You also need the honest comparison, because Day 198 already gave you a document store inside
> Postgres. ⭐⭐ The question is never "documents or rows" — it is "does this need a **second
> database**?"

# Part 1 — ⭐ What it actually is

```
⭐   DATABASE → COLLECTION → DOCUMENT (BSON)
⭐   ⭐ BSON = binary JSON, plus real types JSON lacks: ⭐⭐ ObjectId,
⭐     Date, Decimal128 (⭐ money — Day 187's rule survives here),
⭐     Binary, and 64-bit ints.
⭐   ⭐ `_id` is mandatory, unique, indexed, and immutable. ⭐⭐ Default
⭐     is an ObjectId: 4-byte timestamp + 5-byte random + 3-byte counter
⭐     ⇒ ⭐ roughly time-ordered, which makes it a decent shard key
⭐     candidate in exactly one respect and a bad one in another
⭐     (Day 213).

⭐⭐ WHAT "SCHEMALESS" MEANS IN PRACTICE — Day 198's argument, again:
⭐   ⭐ The database enforces nothing by default. ⭐⭐ SO THE SCHEMA
⭐     MOVES INTO YOUR APPLICATION, and if you do not write it down
⭐     there, it exists only as an average of what six services happen
⭐     to do.
⭐   ⭐⭐ AND MONGO HAS HAD `$jsonSchema` VALIDATORS SINCE 3.6 — required
⭐     fields, types, ranges, enums, `additionalProperties: false`.
⭐     ⭐ Almost nobody uses them, which is a choice, not a limitation.
⭐   ⇒ ⭐⭐ THE HONEST POSITION: "SCHEMALESS" IS REALLY "SCHEMA ON READ,
⭐     ENFORCED BY YOU". ⭐ Write it in Pydantic AND in a validator.
```

```
⭐⭐ FIVE THINGS THAT CHANGED AND PEOPLE STILL GET WRONG:
⭐  ① ⭐⭐ MULTI-DOCUMENT TRANSACTIONS EXIST (4.0 replica sets, 4.2
⭐     sharded). ⭐ "Mongo has no transactions" is six years out of date
⭐     — ⭐⭐ but Day 213 gives the cost, and the cost is the reason the
⭐     old advice still half-applies.
⭐  ② ⭐ DOCUMENT-LEVEL CONCURRENCY since WiredTiger (3.0). The
⭐     database-level lock people remember is long gone.
⭐  ③ ⭐⭐ `w: "majority"` IS THE DEFAULT WRITE CONCERN SINCE 5.0. The
⭐     old `w: 1` default — acknowledged by one node, lost on failover —
⭐     is the source of most "Mongo lost my data" stories, and it was a
⭐     DEFAULT, not a bug.
⭐  ④ ⭐ Jepsen found real issues in 3.x/4.x and most were fixed;
⭐     ⭐⭐ the durable lesson is not "Mongo is unsafe" but "READ YOUR
⭐     WRITE AND READ CONCERNS, BECAUSE THEY ARE TUNABLE AND THE
⭐     DEFAULTS ARE A CHOICE SOMEONE MADE FOR YOU."
⭐  ⑤ ⭐ `$lookup` exists. It is a left outer join. ⭐⭐ So "Mongo can't
⭐     join" is wrong, and "so joins are fine now" is also wrong
⭐     (Day 212).
```

```
⭐⭐ THE HARD LIMIT THAT SHAPES EVERY SCHEMA: ***16 MB PER DOCUMENT.***
⭐   ⭐ It is not a number you should ever approach — ⭐⭐ performance
⭐     degrades badly long before it, because a growing document is
⭐     rewritten and every index entry follows it.
⭐   ⇒ ⭐⭐ IT IS REALLY A DESIGN CONSTRAINT IN DISGUISE: ***NOTHING
⭐     UNBOUNDED MAY BE EMBEDDED.*** Day 211 is that sentence, expanded.
```

# Part 2 — ⭐⭐ The inversion: modelling queries, not data

```
⭐⭐ THE SAME PRODUCT, TWO PHILOSOPHIES:

⭐ POSTGRES: ⭐ normalise, then JOIN at read time.
⭐   orders · order_items · products · addresses
⭐   ⇒ ⭐ ONE FACT LIVES IN ONE PLACE. ⭐⭐ ANY question is answerable
⭐     with a query you have not thought of yet.
⭐   ⇒ ⭐ Cost: reads assemble the aggregate every time.

⭐ MONGODB: ⭐⭐ store the AGGREGATE as it is READ.
⭐   { _id, customer: {...}, items: [...], shipping: {...}, total }
⭐   ⇒ ⭐⭐ ONE READ. ONE DISK LOCATION. NO JOIN. ⭐ This is genuinely
⭐     fast and genuinely simpler for that access pattern.
⭐   ⇒ ⭐⭐ COST: THE SHAPE ENCODES AN ASSUMPTION ABOUT HOW IT WILL BE
⭐     READ. ⭐ A question that cuts across the aggregate — "total
⭐     revenue per product across all orders" — is now an aggregation
⭐     pipeline over every order, or a second collection you maintain.

⭐ ⇒ ⭐⭐ THE TEST BEFORE YOU CHOOSE: ***"CAN I LIST MY ACCESS PATTERNS,
⭐   AND AM I CONFIDENT THEY WILL NOT CHANGE?"***
⭐   ⭐ Confident ⇒ the document model will serve you very well.
⭐   ⭐⭐ Not confident ⇒ you are choosing a schema optimised for
⭐     queries you have not discovered, and normalisation is exactly the
⭐     hedge against that. ⭐ That is the whole trade, and it is a
⭐     judgement about your product, not about databases.
```

# Part 3 — ⭐⭐ Where it genuinely wins, and where it is a mistake

```
⭐⭐ IT GENUINELY WINS WHEN:
⭐  ✅ ⭐⭐ THE SHAPE VARIES PER RECORD AND THE VARIATION IS THE POINT —
⭐     a product catalogue where a laptop and a novel share almost no
⭐     attributes. ⭐ In SQL this is 200 nullable columns, EAV, or a
⭐     JSONB column (which is the same answer in a different building).
⭐  ✅ ⭐ A DEEP HIERARCHY IS ALWAYS READ AS ONE UNIT — a CMS page with
⭐     nested blocks, a form definition, a configuration tree. ⭐⭐ The
⭐     SQL version is four tables and a recursive CTE for something that
⭐     is conceptually one object.
⭐  ✅ ⭐ HIGH-VOLUME WRITES WITH SIMPLE ACCESS — events, telemetry,
⭐     logs, sessions — ⭐⭐ especially with the bucket pattern
⭐     (Day 211) and a TTL index (Day 212), which together do
⭐     time-series retention in about six lines.
⭐  ✅ ⭐⭐ SHARDING IS A FIRST-CLASS FEATURE. If you genuinely need
⭐     horizontal write scale-out, Mongo has it built in and Postgres
⭐     needs Citus or application-level sharding. ⭐ This is a real
⭐     advantage and it is the one people cite least.
⭐  ✅ ⭐ Rapid early-stage iteration where the model is genuinely
⭐     unsettled. ⭐⭐ Honest, and it expires: the flexibility you enjoy
⭐     in month 2 is the six historical shapes you handle in year 2.

⭐⭐ IT IS A MISTAKE WHEN:
⭐  ❌ ⭐⭐ THE DATA IS DEEPLY RELATIONAL. Many-to-many with attributes
⭐     on the relationship is the clearest case — ⭐ students, courses,
⭐     enrolments with grades. ⭐⭐ Every document model of that is
⭐     worse than the two-line SQL one.
⭐  ❌ ⭐⭐ AD-HOC QUERYING AND REPORTING MATTER. Analysts write SQL.
⭐     They do not write aggregation pipelines, and every BI tool speaks
⭐     SQL first.
⭐  ❌ ⭐⭐ YOU HAVE CROSS-ENTITY INVARIANTS. Day 187's `EXCLUDE`
⭐     constraint, Day 195's write skew, Day 164's oversell — ⭐⭐ THE
⭐     CONSTRAINTS THAT MAKE THOSE IMPOSSIBLE DO NOT EXIST HERE. You
⭐     get uniqueness and `$jsonSchema`, and that is all.
⭐  ❌ ⭐ Your team knows SQL and does not know Mongo. ⭐⭐ Day 183's
⭐     tiebreak, and it is a legitimate one.
⭐  ❌ ⭐⭐ YOU CHOSE IT TO AVOID MIGRATIONS. Day 198's finding transfers
⭐     exactly: you did not avoid the migration, you deferred it into
⭐     every read path, forever.
```

# Part 4 — ⭐⭐ The comparison you must actually make: Mongo vs Postgres JSONB

```
⭐⭐ POSTGRES ALREADY HAS DOCUMENTS (Day 198). SO THE REAL QUESTION IS
⭐   NOT "DOCUMENTS OR ROWS" — IT IS ***"DOES THIS NEED A SECOND
⭐   DATABASE?"***

⭐   WHAT POSTGRES JSONB GIVES YOU THAT MONGO DOES NOT:
⭐    ⭐⭐ RELATIONAL DATA IN THE SAME TRANSACTION AS DOCUMENT DATA.
⭐      ⭐ The order is rows with constraints; the provider payload is
⭐        jsonb; one commit covers both.
⭐    ⭐ Real constraints, real foreign keys, real joins, a mature
⭐      planner, SQL for analysts, one thing to operate and back up.
⭐    ⭐⭐ And "documents" stops being an architecture decision and
⭐      becomes a column type.

⭐   WHAT MONGO GIVES YOU THAT POSTGRES JSONB DOES NOT:
⭐    ⭐⭐ BUILT-IN SHARDING AND A MATURE HORIZONTAL STORY.
⭐    ⭐⭐ CAUSAL-CONSISTENCY SESSIONS — read-your-writes across
⭐      replicas as a client-side setting (Day 213). ⭐ Day 201 made you
⭐      build that by hand.
⭐    ⭐ Per-document write concerns, TTL indexes, change streams, and
⭐      an aggregation framework designed for nested data.
⭐    ⭐ Operationally simpler failover and elections out of the box.

⭐ ⇒ ⭐⭐ THE HONEST BAR: ***ADD MONGO WHEN THE DOCUMENT MODEL IS THE
⭐   DOMINANT PATTERN FOR THE WHOLE SERVICE — NOT FOR ONE COLUMN'S
⭐   WORTH OF FLEXIBILITY.*** ⭐ "We need a flexible field" is a JSONB
⭐   column. "Everything we store is a variably-shaped aggregate we
⭐   fetch by id, and we expect to shard" is MongoDB.
⭐ ⭐⭐ AND POLYGLOT PERSISTENCE HAS A PRICE YOU ALREADY KNOW: two
⭐   datastores means the dual-write problem (Day 142), two backup and
⭐   restore stories, two failure modes, two on-call runbooks.
```

# Part 5 — ⭐ In Python

```python
from pymongo import MongoClient, ASCENDING
from pymongo.write_concern import WriteConcern
from pymongo.read_concern import ReadConcern

client = MongoClient(
    "mongodb://h1,h2,h3/?replicaSet=rs0",
    w="majority",                    # ⭐⭐ SET IT EXPLICITLY even though
    journal=True,                    #    5.0+ defaults to it — the next
    readConcernLevel="majority",     #    person should not have to
    retryWrites=True,                #    check the server version
    serverSelectionTimeoutMS=3000,   # ⭐ Day 152, at every boundary
    connectTimeoutMS=3000,
    socketTimeoutMS=10000,
)
db = client.shop
```

```python
# ⭐⭐ WRITE THE SCHEMA DOWN TWICE — in code, and in the database.
class OrderItem(BaseModel):
    sku: str
    name: str                       # ⭐⭐ SNAPSHOT, not a reference —
    unit_price_cents: int           #    Day 188's rule is unchanged by
    qty: int = Field(ge=1)          #    the storage engine

class Order(BaseModel):
    schema_version: int = 2         # ⭐⭐ NON-NEGOTIABLE. Day 198.
    customer_id: str
    items: list[OrderItem]
    status: Literal["pending","paid","shipped","cancelled"]
    created_at: datetime            # ⭐ tz-aware UTC. Day 187.

db.create_collection("orders", validator={"$jsonSchema": {
    "bsonType": "object",
    "required": ["schema_version", "customer_id", "items", "status"],
    "properties": {
        "schema_version": {"bsonType": "int"},
        "status": {"enum": ["pending","paid","shipped","cancelled"]},
        "items": {"bsonType": "array", "minItems": 1},
    },
}}, validationLevel="strict", validationAction="error")
# ⭐⭐ `validationAction: "warn"` LOGS AND ACCEPTS — useful for adopting
#    validation on an existing collection, ⭐ and useless as a permanent
#    setting, because nobody reads the log.
```

```
⭐⭐ THE SCHEMA-VERSION FIELD IS THE SINGLE HIGHEST-VALUE HABIT HERE.
⭐   ⭐ Without it: readers guess the shape from which keys are present,
⭐     and that guess is spread across every service.
⭐   ⭐ With it: one `migrate_v1_to_v2(doc)` function at the boundary, a
⭐     background backfill, and a metric counting documents still at v1.
⭐   ⭐⭐ THAT METRIC REACHING ZERO IS THE ONLY WAY A SCHEMA MIGRATION
⭐     EVER *FINISHES* IN A SCHEMALESS DATABASE.
⭐ ⭐ Async: `motor` mirrors pymongo. ODMs (`beanie`, `mongoengine`) are
⭐   optional; ⭐⭐ Pydantic plus raw pymongo is a perfectly professional
⭐   choice and keeps query locality (Day 139).
```

## Common mistakes

| Mistake | Correction |
|---|---|
| "MongoDB is SQL but web scale" | It's a different data model with a different trade, not a faster one. |
| Believing schemaless means no schema | It means schema on read, enforced by you. Write it in Pydantic *and* a validator. |
| Not using `$jsonSchema` validators | They've existed since 3.6. Not using them is a choice. |
| "Mongo has no transactions" | Multi-document since 4.0. The cost is the real argument, not their absence. |
| Leaving write/read concerns unset | They're tunable, and the defaults are somebody's choice. Set them explicitly. |
| Designing near the 16 MB limit | Performance degrades long before it. It's really "embed nothing unbounded". |
| Choosing Mongo for one flexible field | That's a JSONB column, not a second database. |
| Choosing Mongo to avoid migrations | You deferred the migration into every read path, forever. |
| Modelling many-to-many-with-attributes as documents | Every document version is worse than the SQL one. |
| Ignoring that analysts and BI tools speak SQL | Ad-hoc reporting is a genuine reason not to choose it. |
| Adding Mongo alongside Postgres casually | Two datastores is the dual-write problem plus two of every runbook. |
| No `schema_version` field | Nothing can ever tell you a migration has finished. |
| Leaving `validationAction: "warn"` permanently | Nobody reads the log. |

## Interview questions

**Q: When would you choose MongoDB over Postgres?**

> When the document model is the dominant pattern for the whole service, not for one field. Concretely:
> the shape varies genuinely per record and the variation is the point — a catalogue where a laptop and
> a novel share almost no attributes; a deep hierarchy always read as one unit, like a CMS page with
> nested blocks, where the SQL version is four tables and a recursive CTE for one conceptual object;
> high-volume writes with simple access patterns; or a real need for built-in horizontal sharding,
> which is Mongo's most underrated genuine advantage since Postgres needs Citus or application-level
> sharding for that. What I'd push back on is the common reason people actually give — "we need a
> flexible field" — because Postgres JSONB is a document store you already have, in the same
> transaction as your relational data, with real constraints and joins and one thing to operate. So
> the question isn't documents versus rows, it's whether this needs a *second database*, and that bar
> is higher than people treat it.

**Q: What's the fundamental difference in how you design a schema?**

> In SQL you model the data and then write queries against it; in Mongo you model the queries and then
> store data shaped to fit. That inversion explains everything downstream. Storing the aggregate as
> it's read gives you one read, one location, no join — genuinely fast and genuinely simpler for that
> access pattern. The cost is that the shape encodes an assumption about how it will be read, so a
> question that cuts across the aggregate becomes an aggregation over every document or a second
> collection you maintain by hand. Which gives you the test to apply before choosing: can I list my
> access patterns, and am I confident they won't change? If yes, the document model serves you very
> well. If no, you're optimising for queries you haven't discovered, and normalisation is precisely the
> hedge against that. It's a judgement about how settled your product is, not about which database is
> better.

**Q: Is "MongoDB loses data" a fair criticism?**

> It was fair about a specific default rather than the database. The old `w: 1` write concern
> acknowledged a write once the primary had it, so a failover before replication lost acknowledged
> writes — and that was the default, which is why so many teams hit it without doing anything wrong.
> Jepsen found real issues in the 3.x and 4.x era, most of which were fixed, and since 5.0 the default
> is `w: "majority"`. So the accurate version today is that Mongo's consistency is *tunable*, and the
> durable lesson is to read your write and read concerns rather than inherit them — which is the same
> lesson as knowing your Postgres isolation level. I'd still set them explicitly in the connection
> string even where the default is now correct, so the next person doesn't have to check the server
> version to know what guarantee they have.

**Q: What does the 16 MB document limit actually mean for design?**

> It's a design constraint wearing a limit's clothing: nothing unbounded may be embedded. You should
> never approach 16 MB, because performance degrades badly long before it — a growing document gets
> rewritten and every index entry has to follow it, so an array that grows per event turns each write
> into a rewrite of everything before it. So the limit isn't really a ceiling you plan around, it's the
> enforcement mechanism for the embedding rule: embed things that are bounded and read together,
> reference things that grow. That's tomorrow's entire subject, and it's the decision that determines
> your queries, your write patterns and your consistency story — which is why getting it wrong is
> expensive to reverse.

**Q: How do you handle schema evolution in a schemaless database?**

> With a `schema_version` field on every document, and it's non-negotiable. Without it, readers infer
> the shape from which keys happen to be present, and that inference gets duplicated across every
> service that touches the collection — which is how a collection ends up with six shapes and no
> document saying which. With it, you get one migration function at the read boundary, a background
> backfill, and a metric counting documents still on the old version. That last piece matters most:
> **that metric reaching zero is the only way a schema migration ever finishes in a schemaless
> database** — otherwise you keep the compatibility code forever because nobody can prove it's safe to
> delete. Alongside that I'd add a `$jsonSchema` validator, because the alternative is that the only
> enforcement lives in whichever service happens to write correctly.

## 🎙️ Articulation drill

**Two minutes: "Would you use MongoDB?"**

Lead with the inversion, because it's the thing most people can't articulate: **in SQL you model the
data and query it; in Mongo you model the queries and store data to fit** — so a genuinely new access
pattern is a migration. Then the test that follows: can you list your access patterns and are you
confident they won't change? Give two or three cases where it genuinely wins, and make sure sharding
is one of them, since it's the real advantage people cite least. Then make the move that shows
judgement: **Postgres already has documents, so the question isn't documents versus rows, it's whether
this needs a second database** — and one flexible field is a JSONB column, not an architecture.
Mention the price of polyglot persistence: the dual-write problem and two of every runbook. Close on
the operational habit that matters regardless of which you choose: **a `schema_version` field, because
that metric reaching zero is the only way a migration ever finishes in a schemaless database.**
