# Day 062

**L-062** · ⭐ **mypy in strict mode** — what it catches, what it cannot, `Any` as a defect

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `Any` does not mean "unknown". It means "stop checking" — and it
> propagates, silently, through every expression it touches.**
>
> ⭐ Gradual typing is the reason Python could adopt types at all, and it is also the reason a
> half-typed codebase gives false confidence. **Today is about knowing exactly what your checker does
> and does not guarantee.**

---

# Part 1 — ⭐ Running it

```toml
# pyproject.toml
[tool.mypy]
python_version = "3.12"
strict = true                          # ⭐⭐ turn it all on
warn_unreachable = true                # ⭐ not in strict — but you want it
show_error_codes = true

[[tool.mypy.overrides]]                # ⭐ third-party packages with no stubs
module = ["untyped_lib.*"]
ignore_missing_imports = true
```

```
⭐⭐ WHAT `strict = true` ACTUALLY TURNS ON — the ones that matter:
⭐   disallow_untyped_defs      ⇒ ⭐⭐ every function must be annotated
⭐   disallow_any_generics      ⇒ ⭐ `list` alone is an error; write `list[int]`
⭐   ⭐⭐ no_implicit_optional    ⇒ `def f(x: int = None)` is an error — it must be `int | None`
⭐   warn_return_any            ⇒ ⭐⭐ returning an Any from a typed function is flagged
⭐   warn_unused_ignores        ⇒ a `# type: ignore` that no longer suppresses anything
⭐   strict_equality            ⇒ ⭐ comparing types that can never be equal
⭐   disallow_untyped_calls     ⇒ typed code cannot call untyped code unnoticed
```

⭐⭐ **`no_implicit_optional` alone justifies strict mode.** `def f(x: int = None)` used to be
accepted, which meant a signature that lied about its own default — **and every `None`-related bug
starts with a signature that lied.**

```python
reveal_type(x)          # ⭐⭐ mypy prints the inferred type. Not a runtime function — a mypy directive.
reveal_locals()
```

⭐ **`reveal_type` is the debugger for types**, and it is how you find out where an `Any` entered.

# Part 2 — ⭐⭐ What it catches

| ⭐ Catch | ⭐ Example |
|---|---|
| ⭐⭐ **`None` where a value was assumed** | `user.name` when `user: User \| None` |
| Wrong argument type | `f("3")` where `f(x: int)` |
| ⭐ Missing return on a path | a branch that falls off the end of a `-> str` function |
| ⭐ Wrong return type | returning `None` from `-> str` |
| ⭐⭐ **Unsafe override** | ⭐⭐ a subclass narrowing a parameter type — **an LSP violation** (Day 055) |
| ⭐⭐ Non-exhaustive `match` | adding an enum member (Day 058) |
| ⭐ Unreachable code | with `warn_unreachable` — often reveals a real logic bug |
| Typos in attributes | `obj.emial` |
| Comparing incomparable types | `"1" == 1` with `strict_equality` |

```python
# ⭐⭐ THE BIGGEST WIN — None-safety, and mypy forces the narrowing:
def greet(user: User | None) -> str:
    return user.name                 # ⭐⭐ error: Item "None" has no attribute "name"

def greet(user: User | None) -> str:
    if user is None:                 # ⭐ NARROWING — mypy now knows the type in each branch
        return "hello, stranger"
    return user.name                 # ⭐ here `user` is User
```

```python
# ⭐⭐ EXHAUSTIVENESS — the property that makes enums worth it (Day 058):
from typing import assert_never

def label(s: Status) -> str:
    match s:
        case Status.PENDING:   return "Waiting"
        case Status.SHIPPED:   return "On its way"
        case _ as unreachable:
            assert_never(unreachable)   # ⭐⭐ add a member ⇒ mypy fails HERE, at compile time
```

⭐⭐ **`assert_never` is the highest-value five characters in this file:** it converts "someone must
remember to update every switch" into a build error listing exactly which ones were forgotten.

⭐ **The narrowing tools:** `isinstance`, `is None`, `assert`, `in` on a `Literal`, and — for your own
predicates — `TypeIs` (3.13) / `TypeGuard`:

```python
from typing import TypeIs
def is_user(x: object) -> TypeIs[User]:      # ⭐⭐ tells mypy what a True result means
    return isinstance(x, User)
```

# Part 3 — ⭐⭐ What it cannot catch

```
⭐⭐ THE HONEST LIST, AND YOU SHOULD BE ABLE TO GIVE IT:

⭐ 1. ⭐⭐ ANYTHING AT THE BOUNDARY. json.loads() returns Any. A DB row is Any.
⭐      os.environ is str. A YAML file is Any.
⭐      ⇒ ⭐⭐ mypy verifies your BELIEF about that data, never the data.
⭐      ⇒ ⭐⭐ THIS IS WHY PYDANTIC EXISTS (Day 057) — it checks at runtime what mypy
⭐           can only assume. Types INSIDE, validation AT THE EDGE.
⭐ 2. ⭐ Any propagation — one Any and everything downstream is unchecked
⭐ 3. ⭐ Runtime monkey-patching, setattr, dynamic attributes
⭐ 4. ⭐ Missing or wrong third-party stubs — a stub can simply be incorrect
⭐ 5. ⭐⭐ LOGIC. A correctly typed function can compute the wrong answer. Types are not tests.
```

```python
data = json.loads(body)          # ⭐⭐ Any
user_id = data["user"]["id"]     # ⭐⭐ Any — mypy checks NOTHING here
send_email(user_id)              # ⭐⭐ accepted, whatever send_email expects. It could be a dict.
```

⭐⭐ **That three-line example is the whole argument for validating at the boundary.** ⭐ Strict mode
helps: `disallow_any_expr` is too aggressive for most codebases, but **`warn_return_any` catches the
common case of an `Any` escaping a typed function.**

## ⭐⭐ `Any` is a defect

```
⭐⭐ Any is not "I do not know the type". It is "DO NOT CHECK THIS OR ANYTHING IT TOUCHES."
⭐   x: Any
⭐   y = x.foo().bar[0]      ⇒ ⭐⭐ y is Any. No error. The infection spreads silently.
⭐
⭐ ⭐⭐ THE ALTERNATIVE: `object`.
⭐   object means "unknown" — and mypy then REFUSES every operation until you narrow it.
⭐   ⇒ ⭐ `object` makes you prove what it is; `Any` lets you assume.
```

⭐ **Treat `Any` like a `# TODO`:** acceptable at a boundary you have not typed yet, never as a way to
make an error go away. **`disallow_any_explicit` exists if you want the stricter position.**

```python
# ⭐⭐ IGNORES — always with a code, always with a reason:
result = legacy_call()   # type: ignore[no-any-return]  # legacy_lib has no stubs; see #1234
# ⚠️ ⭐ a bare `# type: ignore` suppresses EVERY error on that line, including future ones.
```

⭐ **`warn_unused_ignores` (on in strict) tells you when an ignore is no longer needed** — which
matters, because a stale ignore is silently hiding whatever error appears there next.

# Part 4 — ⭐ Adopting it on real code

```
⭐⭐ THE RATCHET — never "annotate everything" as one task; it does not finish:
⭐   1. add mypy to CI with NO strict flags. Fix what it finds. ⇒ ⭐ a green baseline.
⭐   2. ⭐⭐ turn strict on for ONE module — usually the newest, or the domain layer:
⭐        [[tool.mypy.overrides]] module = ["myapp.domain.*"] strict = true
⭐   3. ⭐ require full annotations for NEW and MODIFIED code in review
⭐   4. ⭐⭐ widen module by module. ⇒ the checked fraction only ever goes UP.
⭐   ⇒ ⭐ and put it in CI. ⭐⭐ A type checker nobody runs is a comment.
```

| ⭐ Tool | ⭐ Note |
|---|---|
| ⭐ **mypy** | the reference implementation; the strictest ecosystem support |
| ⭐ **pyright / Pylance** | ⭐⭐ much faster, better inference, and what VS Code runs — ⭐ they disagree occasionally |
| ⭐ **Ruff** | not a type checker, but it catches a neighbouring class of bug, and it is instant |
| `typeshed` | the stub repository for the stdlib and popular packages |
| `py.typed` | ⭐ the marker file your own package needs so consumers see your types |

⚠️ ⭐ **mypy is slow on a large codebase** — use the cache, and run it on changed files locally with a
full run in CI. **`dmypy` (the daemon) makes the local loop tolerable.**

```
⭐⭐ THE HONEST POSITION TO HOLD IN AN INTERVIEW:
⭐   "Type hints have paid for themselves on every codebase I have used them on, mostly through
⭐    None-safety and safe refactoring. ⭐⭐ But gradual typing means a single `Any` at the boundary
⭐    undermines everything downstream of it — so I validate external data with Pydantic and treat
⭐    mypy as checking my beliefs, not my inputs. ⭐ And types are not tests: a perfectly typed
⭐    function can still compute the wrong answer."
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`Any` to silence an error** | ⭐⭐ It disables checking downstream. Use `object` and narrow. |
| Thinking `Any` means "unknown" | ⭐ That is `object`. `Any` means "stop checking". |
| ⭐ Bare `# type: ignore` | ⭐⭐ Suppresses future errors too. Always `[code]` + a reason. |
| Leaving stale ignores | ⭐ `warn_unused_ignores` finds them. |
| ⭐⭐ **Trusting mypy on external data** | ⭐⭐ `json.loads` is `Any`. Validate with Pydantic. |
| `def f(x: int = None)` | ⭐ Implicit optional — strict rejects it, correctly. |
| Annotating everything in one sprint | ⭐ Ratchet module by module. |
| Not running it in CI | ⭐⭐ A checker nobody runs is a comment. |
| Believing types replace tests | ⭐ A typed function can still be wrong. |
| Skipping `assert_never` | ⭐⭐ It is what makes enum exhaustiveness a build error. |
| No `py.typed` in your own package | ⭐ Consumers get none of your annotations. |

## Interview questions

**Q: What does mypy actually catch?**
> Mostly `None`-safety, which is the largest single category of runtime error in Python — it forces me
> to narrow a `User | None` before using it. Beyond that: wrong argument and return types, missing
> returns on a branch, unsafe overrides where a subclass narrows a parameter — which is a Liskov
> violation the language itself would never mention — and, with `assert_never`, non-exhaustive matches,
> so adding an enum member becomes a build error listing every switch that forgot it.

**Q: What can it not catch?**
> Anything at the boundary. `json.loads` returns `Any`, database rows are `Any`, environment variables
> are strings, YAML is `Any` — so mypy verifies my *beliefs* about incoming data, never the data
> itself. That's precisely why Pydantic exists: types inside, validation at the edge. It also can't
> follow monkey-patching or dynamic attributes, it trusts third-party stubs that may be wrong, and it
> says nothing about logic — a perfectly typed function can compute the wrong answer. Types are not
> tests.

**Q: Why is `Any` a problem?**
> Because it doesn't mean "unknown", it means "stop checking" — and it propagates. Anything derived
> from an `Any` is also `Any`, so a single one at a boundary silently disables checking for everything
> downstream, with no error anywhere. The alternative when I genuinely don't know a type is `object`,
> which means unknown: mypy then refuses every operation until I narrow it with `isinstance`. `object`
> makes me prove what it is; `Any` lets me assume.

**Q: How would you introduce mypy to an existing codebase?**
> As a ratchet, never as a project. Add it to CI with no strict flags and fix whatever it finds to get
> a green baseline. Then turn strict on for one module — usually the domain layer or the newest code —
> using per-module overrides, and require annotations for new and modified code in review. Then widen
> module by module, so the checked fraction only ever goes up. "Annotate everything" as a single task
> never finishes and blocks everything else meanwhile.

**Q: How do you handle a `# type: ignore`?**
> Always with an error code and a reason — `# type: ignore[no-any-return]  # lib has no stubs, see
> #1234`. A bare ignore suppresses every error on that line, including ones introduced later, so it's a
> permanent blind spot. `warn_unused_ignores` is on in strict mode, which tells me when one is no
> longer needed — worth having, because a stale ignore is quietly hiding whatever error appears there
> next.

**Q: Are type hints worth it?**
> Yes, and I'd give the honest version. They've paid for themselves mostly through `None`-safety and
> through making refactoring safe — renaming across a large codebase stops being an act of faith. The
> costs are real: annotation effort, CI time, occasional fights with a checker over something you know
> is fine, and a false sense of security if you forget that one `Any` at a boundary undermines
> everything after it. So: strict typing inside, runtime validation at the edge, and tests for the
> logic.

## 🎙️ Articulation drill

Record two minutes: **"Is static typing worth it in Python?"**

⭐ Say yes, then justify with the specific win rather than the general one: **`None`-safety.**
`AttributeError: 'NoneType' object has no attribute` is the most common runtime error in Python, and a
checker turns it into a build failure that also forces the narrowing to be written. ⭐ Then the second
real payoff: **refactoring stops being an act of faith** — renaming or changing a signature across a
large codebase becomes verifiable.

⭐⭐ **Then the limit, stated as an architectural consequence rather than a caveat:** *"gradual typing
means one `Any` undermines everything downstream, and `Any` is exactly what you get at every boundary —
`json.loads`, a database row, an environment variable. So mypy is checking my beliefs about incoming
data, never the data. That is why the design is types inside and Pydantic at the edge: the checker
guarantees internal consistency, and validation guarantees the input matches what I claimed."*

⭐ Close on the honest boundary: **types are not tests.** A perfectly typed function can compute the
wrong answer, and no amount of strictness will say so.
