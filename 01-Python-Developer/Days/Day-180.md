# Day 180

**L-180** · 🎸 **Testing Django** — ⭐⭐ `TestCase` vs `TransactionTestCase`, factories, and the suite that stays fast

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `TestCase` wraps every test in a transaction it rolls back, which is why
> it is fast and also why your `on_commit` callbacks never fire, your `select_for_update` proves
> nothing, and your concurrency test cannot race.**
>
> ⭐ Day 141 built this discipline for FastAPI. ⭐⭐ Django ships most of it — including the query-count
> ceiling — and has three specific traps that cause tests to pass while production breaks.

---

# Part 1 — ⭐⭐ The three base classes, and when each is required

```
⭐⭐ `SimpleTestCase`
⭐   ⭐ NO DATABASE ACCESS AT ALL — it raises if you touch one.
⭐   ⇒ ⭐ perfect for pure logic, template rendering, form validation.
⭐   ⇒ ⭐⭐ AND USE IT DELIBERATELY: the ban is a design signal. If a "unit"
⭐        test needs a database, ⭐ ask whether the logic should be pure.
⭐
⭐⭐ `TestCase`  ⭐ ← the default, and correct for ~95% of tests
⭐   ⭐ wraps each test in a TRANSACTION and ROLLS BACK.
⭐   ⭐ + ⭐⭐ FAST (a rollback is O(what you wrote), not O(schema)) and
⭐        perfectly isolated. ⭐ Day 141's savepoint fixture, built in.
⭐   ⭐ + `setUpTestData` runs ONCE PER CLASS inside an outer transaction —
⭐        ⭐⭐ shared fixtures with no cross-test contamination.
⭐   ⭐ − ⭐⭐ THE THREE THINGS IT BREAKS — Part 2.
⭐
⭐⭐ `TransactionTestCase`
⭐   ⭐ real commits; TRUNCATES tables afterwards.
⭐   ⭐ + ⭐⭐ REQUIRED for `on_commit`, real concurrency, and anything that
⭐        depends on committed state.
⭐   ⭐ − ⭐⭐ 10–100× SLOWER, ⭐ and it resets sequences and wipes data other
⭐        tests may have expected. ⭐ Use it sparingly and deliberately.
⭐
⭐   ⇒ ⭐⭐ THE RULE: `TestCase` BY DEFAULT; `TransactionTestCase` ONLY WHERE
⭐        COMMIT SEMANTICS ARE THE THING UNDER TEST. ⭐ Knowing WHICH tests
⭐        need it is the skill (Day 164 said the same about the savepoint
⭐        fixture).
```

# Part 2 — ⭐⭐ The three things `TestCase` silently breaks

```
⭐⭐ TRAP 1 — `transaction.on_commit` CALLBACKS NEVER RUN.
⭐   ⭐ the outer transaction never commits, so the hook never fires.
⭐   ⇒ ⭐⭐ EVERY `.delay()` YOU WIRED WITH `on_commit` (Day 179) IS
⭐        SILENTLY UNTESTED. ⭐ The test passes; no task is ever enqueued.
⭐   ⇒ ⭐ FIX: `with self.captureOnCommitCallbacks(execute=True) as cbs:` —
⭐        ⭐⭐ then ASSERT `len(cbs) == 1`, so you are testing that the
⭐        callback was REGISTERED, not just that nothing exploded.
⭐
⭐⭐ TRAP 2 — `select_for_update` PROVES NOTHING.
⭐   ⭐ there is only one connection and one transaction, ⭐⭐ so there is
⭐        nothing to lock against. ⭐ The test passes whether or not your
⭐        locking is correct.
⭐   ⇒ ⭐⭐ AND WORSE ON SQLite, WHICH IGNORES `select_for_update` ENTIRELY
⭐        (Day 172). ⭐ A green suite is compatible with a completely broken
⭐        concurrency design.
⭐   ⇒ ⭐ FIX: `TransactionTestCase` + real threads + Postgres (Part 3).
⭐
⭐⭐ TRAP 3 — YOUR CONCURRENCY TEST CANNOT RACE.
⭐   ⭐ threads inside a `TestCase` see a different connection with no view of
⭐        the uncommitted outer transaction ⇒ ⭐⭐ they see an EMPTY DATABASE.
⭐   ⇒ ⭐ Day 164's 200-thread oversell test MUST be a `TransactionTestCase`.
⭐
⭐⭐ AND THE FOURTH, WHICH IS NOT A TRAP BUT A GOTCHA:
⭐   ⭐ `TestCase` DOES NOT reset the CACHE, and a `locmem` cache persists
⭐        across tests in a process ⇒ ⭐⭐ order-dependent failures that look
⭐        like flakiness (Day 154). ⭐ Use `@override_settings` with a dummy
⭐        cache, or clear it in `setUp`.
```

# Part 3 — ⭐ pytest-django, and the fixtures worth having

```python
# ⭐ pytest-django is the better runner: fixtures, parametrize, plugins (Day 093)
@pytest.mark.django_db                       # ⭐ = TestCase (rolled back)
def test_creates_order(client, user):
    ...

@pytest.mark.django_db(transaction=True)     # ⭐⭐ = TransactionTestCase
def test_no_oversell_under_concurrency(): ...

@pytest.fixture
def api(client, user):
    client.force_login(user)                 # ⭐ skips the password hash — fast
    return client
```

```
⭐⭐ THE FLAGS THAT MATTER:
⭐   ⭐ `--reuse-db` ⇒ ⭐⭐ skip `migrate` on every run. ⭐ On a project with 300
⭐        migrations this is often 30–60 seconds PER RUN, and it is the single
⭐        biggest local speed win. ⭐ `--create-db` when the schema changes.
⭐   ⭐ `-n auto` (xdist) ⇒ ⭐⭐ needs ONE DATABASE PER WORKER. pytest-django
⭐        does this automatically; ⭐ without it you get "flakes" that are
⭐        genuine races (Day 154).
⭐   ⭐ ⭐⭐ `--no-migrations` (or `django_test_migrations`) BUILDS THE SCHEMA
⭐        DIRECTLY FROM MODELS. ⭐ Much faster — ⭐⭐ AND IT MEANS YOUR
⭐        MIGRATIONS ARE NEVER EXECUTED BY YOUR TEST SUITE, so a broken one
⭐        ships. ⭐ Day 141's answer applies: use it for the fast suite AND run
⭐        a separate CI job that migrates a fresh database and asserts
⭐        `makemigrations --check` is clean (Day 173).

⭐⭐ FIXTURES: FACTORIES, NOT JSON.
⭐   ⭐ ❌ `fixtures = ["orders.json"]` — ⭐⭐ a static dump that rots with your
⭐        schema, is loaded per test, and makes every test depend on data it
⭐        did not ask for. ⭐ You cannot see what the test needs.
⭐   ⭐ ✅ ⭐⭐ `factory_boy` — each test declares exactly the data it needs:
⭐          order = OrderFactory(status="paid", qty=2)
⭐        ⇒ ⭐ the test is readable in isolation, ⭐⭐ and adding a model field
⭐          does not break 200 tests.
⭐   ⭐ ⭐⭐ `setUpTestData` FOR EXPENSIVE SHARED OBJECTS — ⭐ once per class,
⭐        inside a transaction. ⭐⭐ BUT: objects are re-fetched per test in
⭐        modern Django; if you mutate a class attribute directly you will
⭐        still leak state. ⭐ Day 093's scope trap, in Django's clothes.
```

# Part 4 — ⭐⭐ What to actually assert

```python
class OrderAPITests(TestCase):
    def test_list_is_scoped_and_not_n_plus_1(self):
        OrderFactory.create_batch(50, user=self.other_user)
        mine = OrderFactory.create_batch(3, user=self.user)
        self.client.force_login(self.user)
        with self.assertNumQueries(4):                  # ⭐⭐ Day 141, built in
            r = self.client.get("/api/v1/orders/")
        assert {o["id"] for o in r.json()["results"]} == {o.id for o in mine}
        #  ⭐⭐ ONE test asserting BOTH isolation and query count — Day 176's
        #     `has_object_permission`-not-called-on-list bug dies here.
```

```
⭐⭐ THE SEVEN ASSERTIONS THAT CATCH REAL BUGS IN DJANGO SPECIFICALLY:
⭐  1. ⭐⭐ `assertNumQueries` ON EVERY LIST VIEW. ⭐ Django ships the ceiling;
⭐       there is no excuse. ⭐⭐ And it catches the ViewSet default-queryset
⭐       N+1 (Day 175) on the commit that introduces it.
⭐  2. ⭐⭐ CROSS-USER AND CROSS-TENANT ACCESS RETURNS 404 — ⭐ for LIST as
⭐       well as detail (Day 176).
⭐  3. ⭐ ABSENT FIELDS: `assert "password" not in r.content.decode()`.
⭐       ⭐⭐ Catches `fields = "__all__"` the day someone adds a column
⭐       (Day 175).
⭐  4. ⭐⭐ `assertTemplateUsed` + query count for server-rendered pages —
⭐       ⭐ the template N+1 (Day 171) has no other automated defence.
⭐  5. ⭐ `on_commit` CALLBACKS REGISTERED, via `captureOnCommitCallbacks`.
⭐  6. ⭐⭐ MIGRATIONS: `makemigrations --check --dry-run` as a TEST or a CI
⭐       step (Day 173).
⭐  7. ⭐⭐ THE ROUTE-PERMISSION SWEEP (Day 140): walk the URLconf and assert
⭐       every view is authenticated or on an explicit public list. ⭐ In DRF,
⭐       assert no view uses `AllowAny` outside that list.

⭐⭐ AND THE MOCKING RULES (Day 141), UNCHANGED:
⭐   ⭐ ✅ mock the CLOCK (`freezegun`), third-party HTTP (`responses`),
⭐        payment providers, email (`django.core.mail.outbox` is built in and
⭐        excellent).
⭐   ⭐ ❌ ⭐⭐ NEVER MOCK THE ORM. ⭐ A mocked QuerySet has no constraints, no
⭐        transactions, no ordering and no query count — ⭐⭐ it hides exactly
⭐        the bugs you are testing for (Day 139's fake-repository trap).
⭐   ⭐ ❌ ⭐⭐ AND NEVER USE SQLite WHEN YOU DEPLOY ON POSTGRES. ⭐ Different
⭐        types, different constraint enforcement, no `select_for_update`, no
⭐        RLS, different NULL ordering. ⭐⭐ You are testing a different program.
```

# Part 5 — ⭐ Keeping it fast

```
⭐⭐ A DJANGO SUITE GETS SLOW IN FOUR PREDICTABLE PLACES. FIX IN THIS ORDER:

⭐  1. ⭐⭐ MIGRATIONS ON EVERY RUN. `--reuse-db` locally; ⭐ build the schema
⭐       directly in CI with a separate migration job. ⭐⭐ Usually the single
⭐       biggest win, and usually 30–60 s per run.
⭐  2. ⭐⭐ `TransactionTestCase` USED CASUALLY. ⭐ Each one truncates every
⭐       table. ⭐⭐ Grep for it; every instance should have a comment saying
⭐       why.
⭐  3. ⭐ PASSWORD HASHING IN FIXTURES. ⭐⭐ argon2 is ~200 ms BY DESIGN
⭐       (Day 140), and a suite creating 500 users spends 100 seconds
⭐       hashing. ⭐ Override to `MD5PasswordHasher` in test settings — ⭐⭐ this
⭐       is safe precisely because it is the one place slow hashing has no
⭐       security value.
⭐  4. ⭐ FIXTURE OVER-CREATION — ⭐⭐ `SubFactory` chains that build an
⭐       organiser, an event and five ticket types for a test about one field.
⭐       ⭐ Use `build()` (unsaved) where you do not need a row.
⭐
⭐   ⇒ ⭐⭐ AND MEASURE FIRST (Day 100A): `pytest --durations=20`. ⭐ Write down
⭐        your guess for the slowest test BEFORE looking. ⭐⭐ It is almost
⭐        never what you expected, and that is the point of measuring.

⭐⭐ THE TEST-SETTINGS BLOCK WORTH COPYING:
⭐   ⭐ `PASSWORD_HASHERS = ["django.contrib.auth.hashers.MD5PasswordHasher"]`
⭐   ⭐ `CACHES = {"default": {"BACKEND": "...DummyCache"}}` ⭐⭐ or a locmem
⭐        cache leaks between tests
⭐   ⭐ `EMAIL_BACKEND = "...locmem.EmailBackend"` ⭐ then assert on
⭐        `mail.outbox`
⭐   ⭐ `CELERY_TASK_ALWAYS_EAGER = True` — ⭐⭐ CONVENIENT AND DISHONEST: it
⭐        runs tasks INLINE and SYNCHRONOUSLY, so ⭐ serialisation errors,
⭐        retries, `acks_late` and the transaction boundary are all untested.
⭐        ⇒ ⭐⭐ Use it for convenience, and keep a SMALL suite with a REAL
⭐          broker for the tasks that matter (Day 141's override debt).
⭐   ⭐ `DEBUG = False` in tests — ⭐⭐ or you never exercise your 500 handler
⭐        or your `ALLOWED_HOSTS` behaviour.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Expecting `on_commit` callbacks under `TestCase` | The outer transaction never commits. Every `.delay()` is silently untested. |
| Testing `select_for_update` under `TestCase` | One connection, nothing to lock against. The test passes either way. |
| A concurrency test under `TestCase` | Threads see a different connection and an empty database. |
| SQLite for tests, Postgres in production | No `select_for_update`, no RLS, different types and constraint enforcement. |
| `TransactionTestCase` used casually | It truncates every table — 10–100× slower. Every use needs a stated reason. |
| A `locmem` cache in tests | State leaks across tests as order-dependent "flakiness". |
| JSON fixture files | They rot with the schema, and every test depends on data it didn't ask for. |
| Mutating `setUpTestData` class attributes | State leaks between tests — the scope trap in Django's clothes. |
| `--no-migrations` with no compensating job | Your migrations are never executed by CI, so a broken one ships. |
| `-n auto` without a database per worker | Genuine races that look like flakes. |
| Mocking the ORM | No constraints, no transactions, no query counts — it hides what you're testing for. |
| No `assertNumQueries` | Django ships the query ceiling; the ViewSet N+1 will otherwise reach production. |
| Only testing cross-user access on detail views | `has_object_permission` isn't called on `list` — that's where the leak is. |
| argon2 hashing in tests | 200 ms per user by design; override to MD5 in test settings. |
| `CELERY_TASK_ALWAYS_EAGER` as the only task testing | Runs inline and synchronously — serialisation, retries and boundaries untested. |
| `DEBUG=True` in tests | You never exercise your 500 handler or `ALLOWED_HOSTS`. |
| Optimising the suite before `--durations` | It's never the test you guessed. |

## Interview questions

**Q: What's the difference between `TestCase` and `TransactionTestCase`?**

> `TestCase` wraps each test in a transaction and rolls it back, which makes it fast — a rollback is
> proportional to what the test wrote rather than to the schema — and perfectly isolated. That's the
> right default for about ninety-five percent of tests. `TransactionTestCase` commits for real and
> truncates tables afterwards, which is ten to a hundred times slower. The reason to know the
> difference is that `TestCase` silently breaks three things: `on_commit` callbacks never fire
> because the outer transaction never commits, so every `.delay()` you wired through `on_commit` is
> untested and the test still passes; `select_for_update` proves nothing because there's one
> connection and nothing to lock against; and a threaded concurrency test can't race, because the
> threads get a different connection and see an empty database. So anything where commit semantics
> are the thing under test needs `TransactionTestCase`, and knowing which tests those are is the
> skill.

**Q: How do you test that a background task gets enqueued?**

> With `captureOnCommitCallbacks(execute=True)`, and I assert on the *number* of callbacks captured,
> not just that nothing exploded — because the failure mode is silence. Under a plain `TestCase` the
> callback simply never runs, so a test asserting "no exception" passes on code that enqueues
> nothing. For the task itself, `CELERY_TASK_ALWAYS_EAGER` is convenient and dishonest: it runs the
> task inline and synchronously, so argument serialisation, retries, `acks_late` and the transaction
> boundary are all untested. I'd use it for the bulk of tests and keep a small suite against a real
> broker for the tasks that actually matter — same debt-and-repayment shape as overriding auth in
> most tests and keeping one suite that overrides nothing.

**Q: What would you assert in a DRF list-endpoint test?**

> Three things in one test. That the response contains only *my* rows and none of the other user's —
> and specifically for `list`, not just detail, because `has_object_permission` isn't called on list,
> so that's exactly where isolation leaks while every detail test passes. That the query count is
> bounded, with `assertNumQueries`, which catches the ViewSet default-queryset N+1 on the commit that
> introduces it — and Django ships that assertion, so there's no excuse. And that fields which
> shouldn't be there aren't, by checking the raw response body for things like `password`, which
> catches `fields = "__all__"` the day somebody adds a column to the model.

**Q: Your Django suite takes twelve minutes. What do you do?**

> Run `pytest --durations=20` first and write down my guess beforehand, because it's never the test I
> expected. Then in order: migrations on every run, which `--reuse-db` fixes locally and is often
> thirty to sixty seconds a run on a mature project; casual `TransactionTestCase` use, which
> truncates every table — I'd grep for it and require a comment justifying each one; password hashing
> in fixtures, since argon2 is two hundred milliseconds by design and a suite creating five hundred
> users spends a minute and a half hashing, so I override to MD5 in test settings, which is safe
> precisely because that's the one context where slow hashing has no security value; and
> over-eager `SubFactory` chains building an organiser and five ticket types for a test about one
> field. If I go as far as `--no-migrations` for speed, I add a separate CI job that migrates a fresh
> database and runs `makemigrations --check`, or my migrations are never executed by CI at all.

## 🎙️ Articulation drill

**Two minutes: "How do you test a Django application?"**

Lead with the mechanic that explains everything else — `TestCase` rolls back a transaction, which is
why it's fast and why three specific things silently stop working. Name all three, and make the
`on_commit` one concrete: every task you wired through it is untested and the test still passes,
which is the worst kind of green. Then say which tests need `TransactionTestCase` and note that
knowing *which* is the skill. Cover factories over fixture files, and the assertions that are Django
specific — `assertNumQueries` on every list view, and list-endpoint isolation rather than only
detail, because that's where DRF's permission model leaks. Close on speed with the ordering and one
concrete number: **argon2 is two hundred milliseconds by design, so a suite creating five hundred
users spends ninety seconds hashing — and overriding to MD5 is safe precisely because that's the one
place slow hashing buys nothing.**
