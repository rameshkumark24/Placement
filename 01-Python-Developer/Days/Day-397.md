# Part 4 — ⭐⭐ The five proofs

> Day 379's rule, applied to AWS: **these are demonstrations, not claims.** Anyone can say "it's
> highly available". These produce a number, a timestamp or a graph.

```
⭐⭐ ① ***KILL AN ENTIRE AVAILABILITY ZONE.*** ⭐ Not a task —
⭐    an AZ. ⭐ Drain the subnets or stop every task in one.
⭐    ⭐⭐ THE PROOF: THE SERVICE STAYS UP AND ERROR RATE STAYS
⭐    INSIDE THE SLO. ⭐ What this actually tests is whether you
⭐    left a ***single-AZ dependency*** hiding in a multi-AZ
⭐    design — ⭐⭐ ONE NAT GATEWAY, ONE CACHE NODE, ONE SUBNET
⭐    THAT ONLY EXISTS IN AZ-A (383, 388).

⭐⭐ ② ***FORCE AN RDS FAILOVER UNDER LOAD.*** ⭐ "Reboot with
⭐    failover" while a load test runs.
⭐    ⭐⭐ THE PROOF: THE NUMBER OF SECONDS WRITE ERRORS PERSIST —
⭐    BEFORE YOUR POOL SETTINGS AND AFTER. ⭐ Two numbers.
⭐    ⭐⭐ IF THE "AFTER" IS NOT DRAMATICALLY SMALLER, YOU HAVE NOT
⭐    UNDERSTOOD DAY 387.

⭐⭐ ③ ***RESTORE FROM POINT-IN-TIME AND TIME THE WHOLE
⭐    SEQUENCE.*** ⭐ Restore, repoint the application, serve real
⭐    traffic. ⭐⭐ THE PROOF: ONE NUMBER, WHICH IS YOUR RTO —
⭐    NOT THE ONE IN THE RUNBOOK (387).

⭐⭐ ④ ***SHOW COST PER 1,000 REQUESTS, AND SHOW IT FALLING.***
⭐    ⭐ Make one change — the S3 endpoint, Graviton, a Savings
⭐    Plan — ⭐⭐ AND SHOW THE ***UNIT*** COST BEFORE AND AFTER.
⭐    ⭐ Total cost is not the proof; ⭐⭐ THE DENOMINATOR IS THE
⭐    PROOF (396).

⭐⭐ ⑤ ***ALARM → TRACE → LOG LINE IN UNDER FIVE MINUTES.***
⭐    ⭐ Break something deliberately at the ***worker***, not the
⭐    API, ⭐⭐ SO THE TRACE MUST SURVIVE THE QUEUE HOP. ⭐ Start a
⭐    stopwatch at the page. ⭐⭐ THE PROOF IS THE ELAPSED TIME
⭐    (394, 376).
```

# Part 5 — ⭐⭐ The six shapes this stage keeps producing

> Day 359 gave eight design shapes. **Stage 11 has six, and every one appeared at least three times.**
> Learn them as the transferable content; the service names are not the lesson.

```
⭐⭐ ① ***THE TWO PLANES.*** ⭐ The API that changes things and
⭐    the thing that serves traffic fail independently, and the
⭐    control plane fails more. ⭐⭐ ⇒ YOUR RECOVERY MUST NOT NEED
⭐    IT. ⭐ (380 · 389's scale-out latency · 392's DNS failover)

⭐⭐ ② ***POOLS OUTLIVE DNS.*** ⭐ Every failover in AWS is a name
⭐    repoint, and every connection pool holds a socket that
⭐    never re-resolves. ⭐⭐ ⇒ BOUND CONNECTION LIFETIME, AND MAKE
⭐    WRONGNESS LOUD. ⭐ (387 · 388 · 390 · 392)

⭐⭐ ③ ***SMALL THINGS BURST, AND BURSTING ENDS.*** ⭐ t-family
⭐    CPU, EBS bandwidth, S3 prefix splitting, Aurora ACUs.
⭐    ⭐⭐ ⇒ THE GRAPH LOOKS HEALTHY WHILE THE CREDIT BALANCE
⭐    APPROACHES ZERO, SO ALARM ON THE BALANCE. ⭐ (385 · 386 ·
⭐    388)

⭐⭐ ④ ***THE CACHE KEY IS A SECURITY BOUNDARY.*** ⭐ Whatever
⭐    defines "the same request" defines who may see whose data.
⭐    ⭐⭐ ⇒ ANY INPUT THAT CHANGES THE RESPONSE IS IN THE KEY OR
⭐    IS NOT FORWARDED. ⭐ (392 · 386's presigned URLs · 388)

⭐⭐ ⑤ ***THE MANAGED SERVICE'S LIMIT IS STILL YOUR LIMIT.***
⭐    ⭐ RDS still has `max_connections`; Redis is still
⭐    single-threaded; Lambda still exhausts your database;
⭐    Fargate still caps `stopTimeout`. ⭐⭐ ⇒ THE ABSTRACTION
⭐    HIDES THE KNOB, NOT THE PHYSICS. ⭐ (385 · 387 · 388 · 391)

⭐⭐ ⑥ ***EVERY ARROW THAT CROSSES A BOUNDARY HAS A PRICE.***
⭐    ⭐ AZ, region, internet, NAT, KMS, per-request API.
⭐    ⭐⭐ ⇒ AN ARCHITECTURE DIAGRAM IS ALSO A COST DIAGRAM, AND
⭐    YOU SHOULD BE ABLE TO READ IT BOTH WAYS. ⭐ (380 · 383 ·
⭐    386 · 395 · 396)
```

## 🎙️ Articulation drill — the stage close

**Three minutes.** Open with what the stage was actually about: **not services — the fact that in the
cloud every architectural decision is simultaneously a latency decision, an availability decision and
a bill, and being able to give all three numbers for the same diagram is the difference.** Then give
the six shapes as the transferable content. **The two planes: the API that changes things fails more
often than the thing serving traffic, so recovery must not need it — which is why we're
pre-provisioned N+1 rather than reactively scaled.** **Pools outlive DNS: every AWS failover is a name
repoint, and every connection pool holds a socket that never re-resolves — which is why a database
that recovered in thirty seconds left the app broken for forty minutes, and why we bound connection
lifetime and make wrongness loud instead of silent.** **Small things burst and bursting ends: t-family
CPU, EBS bandwidth, S3 prefix splitting — and the graph looks healthy while the credit balance heads
to zero, so we alarm on the balance.** **The cache key is a security boundary, because whatever
defines "the same request" defines who sees whose data.** **The managed service's limit is still your
limit — RDS still has max_connections, Redis is still single-threaded, Lambda still exhausts your
database; the abstraction hides the knob, not the physics.** **And every arrow crossing a boundary has
a price, so an architecture diagram is also a cost diagram.** Then close on proof rather than claim:
**I killed an AZ under load and stayed inside the SLO; a forced failover costs eleven seconds of write
errors instead of forty minutes; my RTO is the number I measured on a real restore including
repointing the app; and cost per thousand requests is down thirty-one percent since March.** Finish
with the honest line: **most of that came from a gateway endpoint and an instance family, not from
clever code — and knowing which lever is worth the week is the actual skill.**
