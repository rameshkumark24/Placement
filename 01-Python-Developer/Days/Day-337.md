# Day 337 🔎

**P-337** · 🔎 **Search and inverted indexes** — ⭐⭐ keeping a derived index honest

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a search index is a derived, eventually-consistent, rebuildable copy of
> your data optimised for a completely different question — and every serious search incident comes
> not from relevance but from the index quietly disagreeing with the database and nobody noticing
> for three weeks.**

---

# Part 1 — ⭐⭐ Why a database index is the wrong shape

```
⭐⭐ A B-TREE ANSWERS: "GIVE ME ROWS WHERE column = / < / >".
⭐⭐ SEARCH ASKS: "GIVE ME DOCUMENTS ***ABOUT*** X, BEST FIRST."
⭐   ⇒ ⭐ Different question, different structure.

⭐⭐ `LIKE '%term%'` IS NOT SEARCH — FIVE REASONS, ALL FATAL:
⭐   ① ⭐⭐ NO INDEX CAN SERVE A LEADING WILDCARD. Full scan.
⭐   ② ⭐ No stemming: "running" doesn't match "run".
⭐   ③ ⭐ No relevance: 10,000 rows in arbitrary order.
⭐   ④ ⭐ No multi-term logic, no phrase, no proximity.
⭐   ⑤ ⭐ No typo tolerance, no synonyms.

⭐⭐ ***THE INVERTED INDEX*** — one idea, and it is the whole
⭐   field:
⭐     "python"  → [doc1, doc7, doc9]
⭐     "async"   → [doc7, doc12]
⭐   ⇒ ⭐ Query "python async" ⇒ ***intersect the posting
⭐     lists*** ⇒ [doc7].
⭐   ⇒ ⭐⭐ THE COST IS PROPORTIONAL TO THE NUMBER OF MATCHING
⭐     DOCUMENTS, NOT TO THE CORPUS SIZE. ⭐ That is why it
⭐     scales, and it is the sentence to say.

⭐⭐ THE ANALYSIS PIPELINE — ⭐⭐ WHERE ALL SEARCH BUGS LIVE:
⭐   ⭐ tokenise → lowercase → remove stopwords → stem/lemmatise
⭐     → (n-grams, synonyms, ASCII-folding)
⭐   ⇒ ⭐⭐ THE INDEXER AND THE QUERY MUST USE ***THE SAME***
⭐     ANALYSER. ⭐ Index with stemming and query without and
⭐     you get zero results for a document that obviously
⭐     matches — ⭐⭐ AND THE SYSTEM REPORTS NO ERROR AT ALL.
```

# Part 2 — ⭐⭐ Relevance: BM25, in words you can defend

```
⭐⭐ THREE INTUITIONS, AND YOU ONLY NEED THESE THREE:
⭐   ① ⭐ ***TERM FREQUENCY*** — a document mentioning "python"
⭐        eight times is more about Python than one mentioning
⭐        it once. ⭐⭐ BUT WITH ***DIMINISHING RETURNS***:
⭐        the 40th mention adds almost nothing, and TF-IDF's
⭐        failure to saturate is exactly what BM25 fixed.
⭐   ② ⭐⭐ ***INVERSE DOCUMENT FREQUENCY*** — a term appearing
⭐        in every document carries no information. ⭐ "the" is
⭐        worthless; "kubernetes" is decisive.
⭐   ③ ⭐ ***LENGTH NORMALISATION*** — a 50-word doc with three
⭐        mentions beats a 5,000-word doc with three mentions.

⭐⭐ ⇒ BM25 IS THOSE THREE WITH TWO TUNING KNOBS (k1 for
⭐   saturation, b for length normalisation). ⭐⭐ THAT IS A
⭐   COMPLETE, CORRECT ANSWER — nobody needs the formula.

⭐⭐ AND THE THING THAT MATTERS MORE THAN THE ALGORITHM:
⭐   ***RELEVANCE IS TEXT SCORE ***PLUS*** BUSINESS SIGNAL.***
⭐   ⭐ Recency, popularity, in-stock, rating, personalisation,
⭐     ⭐ paid placement.
⭐   ⇒ ⭐⭐ A PURE BM25 PRODUCT SEARCH RETURNS THE PERFECT MATCH
⭐     THAT HAS BEEN OUT OF STOCK FOR A YEAR. ⭐ Saying this
⭐     shows you have thought about search as a ***product***,
⭐     not as a library.
⭐   ⇒ ⭐ Day 293's hybrid retrieval and reranking are the same
⭐     idea in the retrieval-augmented setting.
```

# Part 3 — ⭐⭐ The four things users call "search"

```
⭐⭐ ① ***LOOKUP*** — "order #12345", an exact SKU, an email.
⭐      ⇒ ⭐⭐ THIS IS A DATABASE QUERY. ⭐ Sending it to
⭐        Elasticsearch is a common and expensive mistake:
⭐        you get eventual consistency and fuzziness where the
⭐        user wanted an exact, immediate answer.
⭐⭐ ② ***FILTER/FACET*** — "red, size 9, under ₹5000".
⭐      ⇒ ⭐ Structured. ⭐ Postgres does this well; a search
⭐        engine does it well ***and*** gives you facet counts
⭐        cheaply, which is the actual reason to use one here.
⭐⭐ ③ ***FULL-TEXT*** — "waterproof jacket for hiking".
⭐      ⇒ ⭐ The inverted index. ⭐ This is search.
⭐⭐ ④ ***SEMANTIC*** — "something to keep me dry on a hill".
⭐      ⇒ ⭐ Embeddings + ANN (Day 292–293).

⭐⭐ THE POINT: ***ASK WHICH ONE BEFORE YOU DESIGN ANYTHING.***
⭐   ⇒ ⭐⭐ HALF THE "WE NEED ELASTICSEARCH" REQUESTS ARE ① OR
⭐     ②, AND ARE BETTER SERVED BY AN INDEX YOU ALREADY HAVE.
```

# Part 4 — ⭐⭐ Postgres full-text: how far it goes

```
⭐⭐ IT GOES FURTHER THAN PEOPLE THINK — ⭐ comfortably to a few
⭐   million documents with modest query rates.

⭐   ⭐ `to_tsvector('english', title || ' ' || body)` stored in
⭐     a ***generated column***, with a ⭐ GIN index.
⭐   ⭐ `websearch_to_tsquery` — ⭐⭐ HANDLES USER SYNTAX
⭐     ("quoted phrases", -exclusions) WITHOUT THROWING ON
⭐     MALFORMED INPUT, unlike `to_tsquery`. ⭐ Use this one.
⭐   ⭐ `setweight(..., 'A')` for the title, `'B'` for the body
⭐     ⇒ crude but real field boosting.
⭐   ⭐ `pg_trgm` for typo tolerance and `LIKE '%x%'` support.

⭐⭐ THE TRAP THAT SURPRISES EVERYONE (Day 268, and it is worth
⭐   repeating because it is the #1 Postgres FTS performance
⭐   bug):
⭐   ***`ORDER BY ts_rank(...) LIMIT 20` CANNOT USE THE INDEX
⭐      FOR THE ORDERING.***
⭐   ⇒ ⭐ The GIN index finds the matching set; ⭐⭐ THEN EVERY
⭐     MATCH IS SCORED AND SORTED. ⭐ A query matching 400,000
⭐     rows scores 400,000 rows to show you twenty.
⭐   ⇒ ⭐ FIXES: narrow first with a selective filter; ⭐ use
⭐     `ts_rank_cd` only on a pre-limited candidate set; ⭐ or
⭐     accept it and cache.
⭐   ⇒ ⭐⭐ THIS IS ALSO THE MOMENT THE "JUST USE POSTGRES"
⭐     ARGUMENT ACTUALLY BREAKS, AND KNOWING ***WHERE*** IT
⭐     BREAKS IS WHAT MAKES THE ARGUMENT CREDIBLE.

⭐⭐ WHEN TO MOVE TO ELASTICSEARCH/OPENSEARCH:
⭐   ⭐ Tens of millions of documents, or high query rates.
⭐   ⭐ Faceting over large result sets.
⭐   ⭐ Complex relevance tuning, synonyms, per-field analysers.
⭐   ⭐ ⭐⭐ SEARCH LOAD THAT MUST NOT COMPETE WITH TRANSACTIONAL
⭐     LOAD — often the real reason, and a legitimate one.
```

# Part 5 — ⭐⭐ The derived-index rule, which is the actual lesson

```
⭐⭐ ***THE SEARCH INDEX IS NEVER A SYSTEM OF RECORD.*** ⭐ It
⭐   is a projection. ⭐ Three consequences, and all three must
⭐   be true or you have a second source of truth (Day 332):

⭐⭐ ① ***IT MUST BE FULLY REBUILDABLE FROM THE DATABASE, BY A
⭐      COMMAND YOU HAVE RUN THIS QUARTER.***
⭐   ⇒ ⭐ Not "in principle". ⭐⭐ THE REBUILD IS YOUR DISASTER
⭐     RECOVERY, YOUR SCHEMA MIGRATION AND YOUR BUG-FIX
⭐     MECHANISM, ALL AT ONCE.
⭐   ⇒ ⭐ Which means it must run without downtime ⇒ ⭐⭐ INDEX
⭐     TO A NEW INDEX, THEN ATOMICALLY SWAP AN ALIAS. ⭐ Never
⭐     reindex in place.

⭐⭐ ② ***UPDATES FLOW ONE WAY, THROUGH A DURABLE PATH.***
⭐   ⭐ ❌ `db.commit(); es.index(doc)` ⇒ ⭐⭐ DAY 335'S DUAL
⭐     WRITE. The crash between them is permanent divergence,
⭐     and it is ***silent***.
⭐   ⭐ ✔ ⭐⭐ OUTBOX (Day 263) OR CDC. ⭐ At-least-once, plus an
⭐     idempotent indexer (`_id` = the row's primary key, so
⭐     re-indexing is an overwrite).
⭐   ⭐ ✔ ⭐ Version the document with the row's `updated_at` or
⭐     a monotonic version and use `external_gte` versioning —
⭐     ⭐⭐ SO AN OUT-OF-ORDER REDELIVERY CANNOT OVERWRITE A
⭐     NEWER DOCUMENT WITH AN OLDER ONE.

⭐⭐ ③ ***DIVERGENCE MUST BE DETECTED, NOT ASSUMED ABSENT.***
⭐   ⭐ A nightly reconciler: count by bucket, compare, ⭐ sample
⭐     N documents and diff them field by field.
⭐   ⇒ ⭐⭐ EXPORT `search_index_divergence` AS A METRIC AND
⭐     ALERT ON IT. ⭐ Without this, your index has been wrong
⭐     since the deploy three weeks ago and the only person who
⭐     knows is a customer who stopped using search.
```

```python
# ⭐⭐ THE ZERO-DOWNTIME REBUILD, WHICH IS THE WHOLE OPERATIONAL
# ⭐   STORY IN SIX LINES
new = f"products-{int(time.time())}"
await es.indices.create(index=new, mappings=MAPPINGS)     # ⭐ new shape
await bulk_index_everything(into=new)                     # ⭐ from the DB
await verify_counts(new)                                  # ⭐⭐ GATE
await es.indices.update_aliases(actions=[                 # ⭐⭐ ATOMIC
    {"remove": {"index": "products-*", "alias": "products"}},
    {"add":    {"index": new,          "alias": "products"}},
])
# ⭐ The app only ever talks to the alias `products`.
# ⭐⭐ MAPPING CHANGES, ANALYSER CHANGES AND CORRUPTION ALL HAVE
# ⭐   THE SAME FIX, AND IT IS THIS ONE.
```

# Part 6 — ⭐ Sharding, replicas, and the near-real-time gap

```
⭐⭐ ELASTICSEARCH'S MODEL, MINIMALLY:
⭐   ⭐ An index has ***primary shards*** (fixed at creation —
⭐     ⭐⭐ HENCE THE ALIAS PATTERN, WHICH IS ALSO HOW YOU
⭐     CHANGE SHARD COUNT) and ***replica shards*** (readable,
⭐     changeable).
⭐   ⭐ A query fans out to every shard, each returns its top K,
⭐     ⭐ and the coordinator merges.
⭐   ⇒ ⭐⭐ SO A SEARCH IS AS SLOW AS ITS SLOWEST SHARD (Day 322
⭐     again), ⭐ and more shards is not automatically faster.
⭐   ⇒ ⭐ Rule of thumb: shards of 10–50 GB, and ⭐⭐ FEWER
⭐     SHARDS THAN PEOPLE INSTINCTIVELY CREATE.

⭐⭐ ***NEAR REAL TIME*** — the thing that generates support
⭐   tickets:
⭐   ⭐ A document is searchable only after a ***refresh***,
⭐     by default every 1 second.
⭐   ⇒ ⭐⭐ SO "I SAVED IT AND IT'S NOT IN SEARCH" IS NORMAL
⭐     BEHAVIOUR, NOT A BUG. ⭐ And with an outbox in the path,
⭐     the real gap is seconds, not one.
⭐   ⇒ ⭐ FIX FOR THE USER, NOT FOR THE INDEX: ⭐⭐ AFTER A
⭐     WRITE, SHOW THE USER'S OWN ITEM FROM THE DATABASE AND
⭐     MERGE IT INTO THE RESULTS. ⭐ That is Day 331's
⭐     read-your-writes, applied to search — ⭐⭐ AND IT IS THE
⭐     ONLY FIX THAT DOESN'T DESTROY INDEXING THROUGHPUT.
⭐   ⇒ ⭐ (`refresh=wait_for` exists and is a throughput
⭐     disaster if used per write. Bulk indexing should set
⭐     `refresh_interval=-1` and restore it afterwards.)
```

# Part 7 — ⭐ Measuring search, so "relevance" stops being an opinion

```
⭐⭐ THE OFFLINE METRICS:
⭐   ⭐ ***RECALL@K*** — did the right document appear at all?
⭐     ⭐⭐ A HARD CEILING: nothing downstream can rescue a
⭐     document that was never retrieved (Day 293).
⭐   ⭐ ***PRECISION@K*** / ***MRR*** (how high was the first
⭐     good result) / ***nDCG*** (graded relevance, position-
⭐     weighted).
⭐   ⇒ ⭐ You need ~100 labelled queries. ⭐⭐ THAT IS AN
⭐     AFTERNOON, AND ALMOST NOBODY DOES IT, WHICH IS WHY
⭐     SEARCH QUALITY ARGUMENTS ARE USUALLY VIBES.

⭐⭐ THE ONLINE METRICS THAT MATTER MORE:
⭐   ⭐ ⭐⭐ ZERO-RESULT RATE — the single best search metric.
⭐     ⭐ It is a direct measure of failure, it needs no
⭐     labels, and the top zero-result queries are a
⭐     prioritised backlog handed to you for free.
⭐   ⭐ Click-through position, query reformulation rate
⭐     (⭐ a user searching again in 10 s ***failed***),
⭐     abandonment, and search→conversion.

⭐⭐ AND THE OPERATIONAL METRICS: ⭐ index lag (write → visible),
⭐   ⭐⭐ DIVERGENCE COUNT, query p99, and rebuild duration —
⭐   ⭐ because rebuild duration is your recovery time.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Different analysers at index and query time | Obvious matches return nothing, and the system reports no error |
| ⭐⭐ Dual-writing DB then Elasticsearch | The crash between them is permanent, silent divergence. Outbox or CDC |
| ⭐⭐ No rebuild command you've actually run | The index is a second system of record you created by accident |
| ⭐ Reindexing in place | No rollback and downtime. New index plus an atomic alias swap |
| ⭐ No version on the document | An out-of-order redelivery overwrites new data with old |
| ⭐⭐ Never reconciling | Your index has been wrong for three weeks and only a departed customer knows |
| ⭐⭐ `ORDER BY ts_rank` on a broad match | The GIN index can't order; you score 400,000 rows to show 20 |
| ⭐ Sending exact lookups to a search engine | Eventual consistency and fuzziness where the user wanted an exact immediate answer |
| ⭐ Pure BM25 for product search | You'll rank a perfect match that's been out of stock for a year |
| ⭐ Treating the refresh gap as a bug | It's by design. Fix it in the UI with read-your-writes, not with `refresh=wait_for` per write |
| ⭐ Too many shards | Every query fans out to all of them and waits for the slowest |
| ⭐⭐ No zero-result-rate metric | The cheapest, label-free measure of search failure, and a free backlog |

## Interview questions

**1. "Why not `LIKE '%term%'`?"**
> ⭐ No index can serve a leading wildcard, so it's a full scan; and there's no stemming, no relevance
> ordering, no phrase or proximity, no typo tolerance. ⭐⭐ The right structure is an inverted index —
> term to posting list, intersect the lists — **and the reason it scales is that cost is proportional
> to the number of matching documents, not to the corpus size.**

**2. "Explain relevance ranking."**
> ⭐ BM25, and I'd give it as three intuitions rather than a formula: term frequency **with diminishing
> returns**, inverse document frequency so common words carry no information, and length
> normalisation. ⭐⭐ Then the part that matters more: **relevance is text score plus business signal**
> — recency, popularity, stock, rating. Pure BM25 on a product catalogue happily ranks the perfect
> match that's been out of stock for a year.

**3. "How do you keep the index in sync?"**
> ⭐⭐ It's a derived store, so three rules. **Fully rebuildable by a command I've actually run this
> quarter**, into a new index with an atomic alias swap — that one procedure covers disaster recovery,
> mapping changes and bug fixes. ⭐ Updates flow one way through an outbox or CDC, never a dual write,
> with an idempotent indexer keyed on the row id and external versioning so a late redelivery can't
> overwrite newer data. ⭐⭐ And divergence gets **detected, not assumed absent** — a nightly reconciler
> exporting a divergence metric, because otherwise the index has been wrong since a deploy three weeks
> ago.

**4. "When does Postgres full-text stop being enough?"**
> ⭐ A few million documents at modest query rates is comfortable. ⭐⭐ Where it actually breaks is
> ranking: **`ORDER BY ts_rank` can't use the GIN index for ordering, so a query matching four hundred
> thousand rows scores four hundred thousand to return twenty.** ⭐ Beyond that: faceting over large
> result sets, per-field analysers and synonyms, and — often the real reason — wanting search load off
> the transactional database.

**5. "A user saves a product and it isn't in search. Bug?"**
> ⭐ No — near-real-time is the design: documents become searchable at the next refresh, a second by
> default, and with an outbox in the path the real gap is a few seconds. ⭐⭐ The fix is in the UI, not
> the index: **after a write, show the user's own item from the database and merge it into results** —
> read-your-writes applied to search. ⭐ Forcing a refresh per write destroys indexing throughput.

**6. "How do you know your search is good?"**
> ⭐ Offline: a hundred labelled queries giving recall@k, MRR and nDCG — recall is a hard ceiling,
> since nothing downstream rescues a document that was never retrieved. ⭐⭐ Online, and more useful:
> **zero-result rate, which is a direct measure of failure that needs no labels and hands you a
> prioritised backlog** — plus reformulation rate, since a user searching again within ten seconds has
> told you the first attempt failed. ⭐ Operationally: index lag, divergence count, and rebuild
> duration, because rebuild duration *is* my recovery time.

## 🎙️ Articulation drill

**Two minutes.** Start with the shape mismatch: **a B-tree answers "which rows equal this", search asks
"which documents are about this, best first"** — and the inverted index is the answer because its cost
scales with the number of matches, not with the corpus. Mention where the bugs actually live: **the
analyser, because indexing with stemming and querying without returns nothing and reports no error.**
Give relevance as three intuitions — saturating term frequency, inverse document frequency, length
normalisation — then immediately say the more important thing: **relevance is text score plus business
signal**, or you rank the perfect match that's been out of stock for a year. Then the real lesson,
which is operational: **a search index is a derived, rebuildable projection, never a system of record**
— so it must be rebuildable by a command you've run recently, into a new index with an atomic alias
swap; updates must flow one way through an outbox rather than a dual write, versioned so a late
redelivery can't overwrite newer data; **and divergence must be detected rather than assumed absent,
because otherwise your index has been wrong since a deploy three weeks ago and the only person who
knows is a customer who stopped using search.** Close on measurement: recall as the hard ceiling
offline, **and zero-result rate online, which costs nothing, needs no labels and hands you a
prioritised backlog.**
