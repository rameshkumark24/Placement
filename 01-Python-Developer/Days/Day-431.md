# Part 3 — ⭐⭐ The prefixes, and the asymmetry nobody mentions

```
⭐ MANY MODELS ARE TRAINED ***ASYMMETRICALLY***: ⭐ queries and
⭐   passages are embedded with different instruction prefixes,
⭐   because a question and its answer are ***not*** similar
⭐   texts (Day 419's core point).

⭐   ⭐ E5 / BGE:    "query: …"  vs  "passage: …"
⭐   ⭐ Cohere:      input_type="search_query"
⭐                          vs  input_type="search_document"
⭐   ⭐ Instructor:  an explicit task instruction string

⭐⭐ IF YOU OMIT THEM, NOTHING FAILS. ⭐ No exception, no warning,
⭐   no log line. ⭐⭐ YOU JUST LOSE 5–15 POINTS OF RECALL AND
⭐   NEVER KNOW. ⭐ This is the single most common silent bug in
⭐   hand-rolled RAG.

⭐⭐ AND THE MIRROR-IMAGE BUG, WHICH IS WORSE: ⭐ using the
⭐   ***query*** prefix at ingest time. ⭐⭐ NOW EVERY VECTOR IN
⭐   YOUR INDEX IS WRONG AND THE ONLY FIX IS A FULL REINDEX.
⭐   ⭐⭐ ⇒ SO PUT THE PREFIX INSIDE ONE FUNCTION THAT NOTHING
⭐     ELSE MAY BYPASS. ⭐ Two public functions, never one with a
⭐     boolean flag — a flag gets defaulted wrong exactly once
⭐     and you pay for it with a reindex.
```

```python
from typing import Literal

_MODEL = "BAAI/bge-base-en-v1.5"
_QUERY_PREFIX   = "Represent this sentence for searching relevant passages: "
_PASSAGE_PREFIX = ""          # ⭐ bge asymmetry: queries only

async def embed_passages(texts: list[str]) -> list[list[float]]:
    """⭐⭐ INGEST PATH. The ONLY way chunk vectors are made."""
    return await _embed([_PASSAGE_PREFIX + t for t in texts])

async def embed_query(text: str) -> list[float]:
    """⭐⭐ QUERY PATH. The ONLY way a question is embedded."""
    return (await _embed([_QUERY_PREFIX + text]))[0]
```

# Part 4 — ⭐⭐ The content-hash cache: where the wasted money is

```
⭐ THE PATTERN EVERY TEAM SHIPS FIRST: ⭐ a nightly job that
⭐   re-embeds the entire corpus because "it might have changed".

⭐   ⭐ 400,000 chunks × 500 tokens = 200M tokens
⭐   ⭐ at $0.02/M (small model) = $4/night = ***$120/month***
⭐   ⭐ at $0.13/M (large model) = $26/night = ***$780/month***
⭐   ⭐⭐ TO RE-COMPUTE VECTORS THAT ARE BIT-IDENTICAL, ⭐ plus
⭐     hours of wall-clock and a rate limit you now have to
⭐     engineer around.

⭐ ***THE FIX IS THE `content_hash` FROM DAY 430.***
⭐   ⭐ Hash exactly the string you embed (prefix included).
⭐   ⭐ On ingest: SELECT the hashes you already have, embed only
⭐     the misses. ⭐⭐ TYPICAL NIGHTLY CHANGE RATE ON A REAL
⭐     CORPUS IS 0.5–3%, ⭐ so this is a 30–200× reduction.
⭐   ⭐ ⭐⭐ AND IT MAKES INGESTION ***IDEMPOTENT*** (Stage 12) —
⭐     re-running a failed job is free and safe.

⭐⭐ THE HASH MUST INCLUDE THE MODEL NAME AND THE PREFIX
⭐   VERSION. ⭐ Otherwise the day you change models, every hash
⭐   still matches and ***the cache serves you stale vectors from
⭐   the old model***, silently, forever.
```

```python
import hashlib, asyncio

def embed_key(text: str, model: str, prefix_version: str) -> str:
    h = hashlib.sha256()
    h.update(model.encode()); h.update(b"\x00")
    h.update(prefix_version.encode()); h.update(b"\x00")
    h.update(text.encode())
    return h.hexdigest()

async def embed_with_cache(chunks, model, prefix_version, store, batch=128):
    keys = [embed_key(c.embed_text, model, prefix_version) for c in chunks]
    have = await store.get_many(keys)                    # ⭐ dict key -> vector
    todo = [(k, c) for k, c in zip(keys, chunks) if k not in have]

    sem = asyncio.Semaphore(4)                           # ⭐ respect the rate limit
    async def run(group):
        async with sem:
            vecs = await embed_passages([c.embed_text for _, c in group])
            await store.put_many({k: v for (k, _), v in zip(group, vecs)})
            return {k: v for (k, _), v in zip(group, vecs)}

    results = await asyncio.gather(*[
        run(todo[i:i + batch]) for i in range(0, len(todo), batch)
    ])
    for r in results:
        have.update(r)
    # ⭐⭐ REPORT THE HIT RATE — it is your single best ingestion
    # health metric. A sudden drop to 0% means someone changed
    # the chunker or the prefix.
    print(f"embedded {len(todo)}/{len(chunks)} "
          f"({100 * (1 - len(todo) / max(len(chunks), 1)):.1f}% cache hit)")
    return [have[k] for k in keys]
```

# Part 5 — Storage arithmetic, and the quantisation you will need

```
⭐ ***THE NUMBER PEOPLE GET WRONG BY 10×.***
⭐   ⭐ 1,000,000 chunks × 1536 dims × 4 bytes (float32)
⭐     = ***6.1 GB*** of raw vectors.
⭐   ⭐⭐ AND THE HNSW INDEX ON TOP IS ROUGHLY ANOTHER 1.5–2×,
⭐     ⭐ so budget ***~15 GB*** — ⭐⭐ AND HNSW WANTS TO BE IN RAM.
⭐   ⭐ That is a machine decision, not a table decision.

⭐ ***THE THREE LEVERS, IN ORDER OF WHAT THEY COST YOU:***
⭐   ⭐ ① ***MATRYOSHKA TRUNCATION.*** ⭐ Models trained this way
⭐     (OpenAI v3, Nomic) pack the most information into the
⭐     first dimensions, so you can ***slice the vector***:
⭐     1536 → 512 dims = 3× smaller, ⭐⭐ TYPICALLY 1–3 POINTS OF
⭐     RECALL. ⭐ Renormalise after slicing.
⭐   ⭐ ② ***int8 QUANTISATION.*** ⭐ 4× smaller, ⭐ ~1 point.
⭐     Supported natively by pgvector (`halfvec`, and int8 via
⭐     extensions), Qdrant, Weaviate.
⭐   ⭐ ③ ***BINARY QUANTISATION.*** ⭐⭐ 32× SMALLER — 6.1GB →
⭐     192MB — ⭐ Hamming distance instead of cosine. ⭐ Loses
⭐     real accuracy alone; ⭐⭐ THE PATTERN THAT WORKS IS
⭐     BINARY-FOR-SHORTLIST THEN ***RESCORE THE TOP 200 WITH THE
⭐     FULL VECTORS***. ⭐ Near-full quality at a fraction of RAM.

⭐⭐ DO NOT DO ANY OF THIS UNTIL SIZE IS A REAL PROBLEM. ⭐ Under
⭐   ~2M vectors, float32 in Postgres is simpler and fine.
```

# Part 6 — ⭐⭐ The reindex, and why it is an alias swap

```
⭐ ***THE THINGS THAT FORCE A FULL REINDEX:***
⭐   ⭐ changing embedding model (obviously)
⭐   ⭐ changing model ***version*** — ⭐⭐ PROVIDERS UPDATE
⭐     MODELS BEHIND A STABLE NAME; ⭐ a "v3" snapshot change can
⭐     shift vectors enough to matter
⭐   ⭐ changing the prefix, dimension, or normalisation
⭐   ⭐⭐ CHANGING THE ***CHUNKER*** (DAY 430) — ⭐ people forget
⭐     this one; new boundaries mean new text means new vectors
⭐   ⭐ changing the contextual prefix content

⭐ ***THE WRONG WAY*** (which is what happens by default):
⭐   ⭐ UPDATE the vectors in place, in a loop, over 6 hours.
⭐   ⭐⭐ FOR THOSE 6 HOURS YOUR INDEX IS ***HALF ONE MODEL AND
⭐     HALF ANOTHER***. ⭐ Cosine distance between vectors from
⭐     two different models is ***meaningless***, not merely
⭐     worse — ⭐⭐ SO RANKING IS RANDOM FOR EVERY QUERY THAT
⭐     TOUCHES BOTH HALVES, AND NOTHING ERRORS.

⭐ ***THE RIGHT WAY — THE SAME SHAPE AS A DATABASE MIGRATION:***
⭐   ⭐ ① build into a ***new*** table/collection:
⭐     `chunks_v4_bge_1024`
⭐   ⭐ ② keep writing new documents to ***both*** while it
⭐     builds (dual-write) ⭐ or replay from the source of truth
⭐     afterwards
⭐   ⭐ ③ run the eval (Day 435) against the new index
⭐     ⭐⭐ BEFORE ANY TRAFFIC SEES IT
⭐   ⭐ ④ flip a ***single config value*** — the alias — to point
⭐     reads at v4
⭐   ⭐ ⑤ keep v3 for a week. ⭐⭐ ROLLBACK IS FLIPPING THE ALIAS
⭐     BACK, NOT A SIX-HOUR REBUILD.
⭐   ⭐ ⑥ drop v3.

⭐⭐ THIS IS DAY 412 RESTATED: ⭐ the index is derived state, and
⭐   ***you do not own derived state until you have rebuilt it
⭐   from scratch at least once, on purpose, with a stopwatch.***
⭐   ⭐ Know your full-rebuild time. ⭐⭐ IT IS AN SLA NUMBER: IT
⭐   IS YOUR WORST-CASE RECOVERY TIME IF THE INDEX IS LOST.
```

```python
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class IndexVersion:
    """⭐⭐ THE ALIAS. One object, one place, one flip."""
    table: str            # "chunks_v4_bge_1024"
    model: str            # "BAAI/bge-base-en-v1.5"
    dims: int             # 768
    prefix_version: str   # "p2"
    chunker_version: str  # "structure-v3"
    # ⭐ Day 427 taught this: config gets a content hash so a
    # log line can prove which pipeline produced an answer.

ACTIVE = IndexVersion("chunks_v4_bge_768", "BAAI/bge-base-en-v1.5",
                      768, "p2", "structure-v3")
```

# 💬 Interview

**1. "How did you choose your embedding model?"**

⭐ I used MTEB to build a shortlist of three and then ignored it. ⭐⭐ The top models there are within a
point of each other averaged over fifty tasks that aren't mine, and the public sets get trained on. ⭐ So
I embedded my own corpus with all three and scored recall@5 on thirty real questions — about forty
minutes of work. ⭐⭐ The cheapest model came within two points of the most expensive, so I took the
cheap one. ⭐ The thing I checked before any of that was max sequence length: a lot of models truncate
at 512 tokens **silently**, so a 900-token chunk quietly loses its tail and that content becomes
unsearchable with no error anywhere.

**2. "What's the most common silent bug in a hand-rolled RAG pipeline?"**

⭐⭐ Missing or mismatched query/passage prefixes. ⭐ Models like E5 and BGE are trained asymmetrically —
queries get one instruction prefix, passages get another — because a question and its answer aren't
similar texts. ⭐⭐ Omit them and nothing fails: no exception, no warning, you just lose five to fifteen
points of recall permanently. ⭐ The nastier variant is using the *query* prefix at ingest, which makes
every vector in your index wrong and costs a full reindex to fix. ⭐⭐ So I expose two functions,
`embed_query` and `embed_passages`, and never a single function with a boolean — a flag gets defaulted
wrong exactly once.

**3. "How do you keep ingestion cheap?"**

⭐ A content-hash cache. ⭐⭐ The default implementation everyone ships is a nightly job that re-embeds
the whole corpus, which for 400,000 chunks is a couple of hundred million tokens a night to recompute
vectors that are bit-identical. ⭐ I hash exactly the string I embed and skip anything I've already
done. ⭐⭐ Real corpora change 0.5 to 3% a night, so it's a 30 to 200× reduction, and the useful
side-effect is that ingestion becomes idempotent, so re-running a failed job is free. ⭐⭐ The critical
detail is that the hash includes the model name and prefix version — otherwise the day you change models
every hash still matches and the cache serves you stale vectors from the old model, silently, forever.

**4. "You need to change embedding models. Walk me through it."**

⭐ It's a database migration, not a config change. ⭐⭐ The failure mode if you do it in place is
specific and bad: for the six hours the backfill runs, half your index is one model and half is
another, and cosine distance between vectors from different models isn't *worse*, it's **meaningless** —
so ranking is effectively random for any query spanning both halves, and nothing errors. ⭐ So: build
into a new table, dual-write new documents to both, run the eval against the new index before any
traffic sees it, then flip one alias value to move reads. ⭐⭐ Keep the old index for a week, because
rollback should be flipping the alias back, not a six-hour rebuild.

**5. "What triggers a reindex besides changing the model?"**

⭐ Changing the prefix, the dimension, the normalisation — and the one people forget, ⭐⭐ **changing the
chunker**. ⭐ New boundaries mean new text means new vectors, so a chunking improvement is as much of a
migration as a model swap. ⭐ Also silent provider updates behind a stable model name. ⭐⭐ That's why my
index version object carries model, dims, prefix version and chunker version together — if any of them
changes, it's a new index, and the config hash in the logs tells me which pipeline produced any given
answer.

**6. "1 million chunks. What does storage look like?"**

⭐ At 1536 dimensions in float32 that's about 6 GB of raw vectors, and an HNSW index adds roughly
another 1.5 to 2×, so budget around 15 GB — ⭐⭐ and HNSW wants to be resident in RAM, so it's a machine
sizing decision, not a table decision. ⭐ If that's a problem I'd reach for Matryoshka truncation first —
models like OpenAI's v3 pack the most information into the leading dimensions, so slicing 1536 to 512
is 3× smaller for one to three points of recall. ⭐⭐ Beyond that, binary quantisation is 32× smaller,
which alone loses real accuracy, but binary-for-shortlist then rescoring the top 200 with full vectors
gets most of it back. ⭐ Under about 2 million vectors I wouldn't do any of it — float32 in Postgres is
simpler and fine.

**7. "Local model or API?"**

⭐ Depends on which constraint is real. ⭐ If data can't leave the network, it's decided — local, and
that's usually the whole reason. ⭐⭐ Otherwise the axis people under-weight is query latency: the
embedding call is on the critical path of every single search, so a 60ms API hop is 60ms on every query
forever, plus a dependency that can be down while your database is healthy. ⭐ A local 384 or 768-dim
model does that in single-digit milliseconds in-process. ⭐⭐ The hybrid worth knowing — API for bulk
ingest, local for queries — is only valid if it's literally the same model on both sides; mixing them
is the meaningless-distance bug again.

## 🎙️ Articulation drill

⭐⭐ **Two minutes, out loud: "how do you manage embeddings in production?"**

Start with the framing that makes the rest inevitable. **An embedding model isn't a dependency you
upgrade — every vector in the index was produced by one specific model, and a vector from a different
model isn't worse, it's meaningless. So picking a model means taking on a reindex problem, and the job
is making that reindex boring.**

Then the operational spine, in three beats. **We chose by measuring, not by leaderboard — MTEB gave us
a shortlist of three, then we scored recall@5 on our own thirty questions and took the cheapest within
noise. Before any of that we checked max sequence length, because a lot of models truncate at 512 tokens
silently and your chunk tails just stop being searchable. Then we split embedding into two functions,
query and passage, with no boolean flag, because those models are trained asymmetrically and getting the
prefix wrong costs you ten points of recall with no error anywhere — and getting it wrong at ingest
costs a full reindex.**

Then the cost line, which is where the money actually is. **Ingestion is cached by a hash of the exact
string we embed, including model name and prefix version. Real corpora change under three percent a
night, so that's a thirty to two-hundred-times reduction on the nightly job, and it makes ingestion
idempotent so a failed run is free to retry. The hash has to include the model, or the day you switch
models every key still matches and the cache serves you old-model vectors forever.**

Close on the migration, because it's the senior part. **Changing the model — or the prefix, or the
chunker — is a database migration. In place, you spend six hours with half the index in one space and
half in another and ranking effectively random, with nothing erroring. So we build into a new table,
dual-write, run the eval against it before any traffic sees it, and flip a single alias. Rollback is
flipping it back. And we've done a full rebuild with a stopwatch on purpose, because the index is
derived state, and the rebuild time is our worst-case recovery time if we lose it.**
