# Part 1 — ⭐⭐ Four different features called "search"

```
⭐⭐ BEFORE ANY TECHNOLOGY: WHICH OF THESE IS THE USER DOING?

⭐ ① ⭐ EXACT LOOKUP — "find job JOB-2291"
⭐      ⇒ ⭐⭐ THAT IS AN INDEX, NOT SEARCH. A unique b-tree and
⭐        one page read (Day 189). No engine involved.

⭐ ② ⭐ PREFIX / TYPEAHEAD — "hend…" ⇒ "Henderson"
⭐      ⇒ ⭐ A prefix index, or trigram. Budget: under 100 ms,
⭐        because it fires on every keystroke.

⭐ ③ ⭐ FULL TEXT over notes, descriptions, documents
⭐      ⇒ ⭐ tsvector + GIN, stemming, ranking (Day 199).

⭐ ④ ⭐⭐ FACETED FILTER + SORT — "open jobs, priority high,
⭐      region south, sorted by SLA deadline"
⭐      ⇒ ⭐⭐ THAT IS SQL WITH THE RIGHT COMPOSITE INDEX (Day 190).
⭐        ⭐ IT IS NOT SEARCH AT ALL.

⭐ ⇒ ⭐⭐ AND ④ IS WHAT MOST "WE NEED ELASTICSEARCH" REQUESTS
⭐   ACTUALLY ARE. ⭐ Asking which of the four is happening is
⭐   the single highest-leverage question in this whole area,
⭐   and it takes one sentence.
```

# Part 2 — ⭐⭐ Postgres full text, and the honest threshold for leaving

```sql
ALTER TABLE jobs ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (
      setweight(to_tsvector('english', coalesce(title,'')),       'A') ||
      setweight(to_tsvector('english', coalesce(description,'')), 'B')
  ) STORED;                                   -- ⭐ maintained by Postgres

CREATE INDEX jobs_tsv_idx ON jobs USING GIN (tsv);

SELECT id, title
  FROM jobs
 WHERE tenant_id = :tid
   AND tsv @@ websearch_to_tsquery('english', :q)   -- ⭐⭐ Day 199
 ORDER BY ts_rank(tsv, websearch_to_tsquery('english', :q)) DESC
 LIMIT 20;
```

```
⭐⭐ THE TRAP IN THE LINE YOU JUST WROTE:
⭐   ***`ORDER BY ts_rank` DOES NOT USE THE INDEX.***
⭐   ⇒ ⭐ The GIN index finds the matching set. ⭐⭐ THEN EVERY
⭐     MATCH IS SCORED AND SORTED. ⭐ So a query matching 400,000
⭐     rows costs 400,000 rank computations to return 20 —
⭐   ⇒ ⭐⭐ RANKING COST SCALES WITH THE MATCH SET, NOT WITH THE
⭐     LIMIT. ⭐ Which is why a search engine's "cheap ranking"
⭐     is genuinely a feature, and why your common-word queries
⭐     are the slow ones while your rare-word queries are fast —
⭐     the exact opposite of most people's intuition.
```

```
⭐ ⭐ TRIGRAM for typos and for `ILIKE '%foo%'`, which is
⭐   otherwise an unavoidable sequential scan (Day 189 —
⭐   a leading wildcard is not sargable):
⭐     CREATE EXTENSION pg_trgm;
⭐     CREATE INDEX ON customers USING GIN (name gin_trgm_ops);

⭐⭐ THE HONEST BAR FOR A SEARCH ENGINE — ALL FOUR OF THESE ARE
⭐   REAL REASONS, AND "IT WOULD BE FASTER" IS NOT ONE:
⭐   ① per-field relevance tuning that you must iterate on
⭐   ② facet AGGREGATIONS at scale ("142 open, 38 closed")
⭐   ③ tens of millions of documents
⭐   ④ ⭐ cross-entity search — one box searching jobs AND
⭐      customers AND documents together

⭐⭐ AND THE PRICE, WHICH IS ALWAYS UNDERSTATED (Day 199):
⭐   ⭐⭐ A DUAL WRITE AND A REINDEX PIPELINE — you now own
⭐     consistency between two stores FOREVER, plus a "search is
⭐     stale" support category, plus a reindex procedure you must
⭐     rehearse before you need it. ⭐ Route the writes through
⭐     the outbox (Day 263) or accept silent drift.
```

# Part 3 — ⭐⭐ The tenant filter that must be inside the query

```python
# ❌ THE ONE THAT LOOKS FINE IN REVIEW
results = search_index.query(q)                       # ⭐ ALL tenants
return [r for r in results if r.tenant_id == tid][:20]
```

```
⭐⭐ TWO BUGS, AND THE SECOND IS THE SERIOUS ONE:
⭐   ① ⭐ PAGE 1 NOW HAS 3 RESULTS. Or zero, while the engine
⭐     happily reports 900 hits — because you filtered AFTER
⭐     the limit and pagination is now meaningless.
⭐   ② ⭐⭐ YOU READ TWENTY OTHER TENANTS' ROWS INTO YOUR PROCESS,
⭐     INTO YOUR LOGS, AND INTO YOUR APM TRACE. ⭐ The list
⭐     comprehension is not a filter — ⭐⭐ IT IS A REDACTION,
⭐     AND IT HAPPENS AFTER THE DISCLOSURE.

⭐⭐ THE FILTER GOES WHERE THE INDEX CAN USE IT:
⭐   WHERE tenant_id = :tid AND tsv @@ websearch_to_tsquery(...)
⭐   ⇒ ⭐ Same shared predicate as Day 259 — search is not exempt
⭐     from the authorisation rule just because it is "read-only".
⭐   ⇒ ⭐⭐ IN AN EXTERNAL ENGINE: an index per tenant, or a
⭐     filter clause applied BY THE ENGINE — never in your code.
```

# Part 4 — ⭐⭐ Reporting: three architectures

```
⭐⭐ WHY A REPORT IS DIFFERENT IN KIND, NOT IN DEGREE:
⭐   ⭐ ONE analytical query can read more pages than your entire
⭐     OLTP workload does in an hour —
⭐   ⇒ ⭐⭐ AND IT EVICTS YOUR HOT DATA FROM SHARED BUFFERS WHILE
⭐     DOING IT (Day 186).
⭐   ⇒ ⭐⭐ SO THE REPORT DOES NOT MERELY RUN SLOWLY. IT MAKES
⭐     EVERY OTHER ENDPOINT SLOW, for minutes after it finishes,
⭐     because the cache has to warm back up.
```

```
⭐⭐ ① A READ REPLICA (Day 201) — the cheapest correct answer.
⭐   ⭐ Route reporting sessions to the replica. Done.
⭐   ⭐⭐ TWO GOTCHAS, BOTH FROM DAY 201:
⭐     ⭐ REPLICATION LAG ⇒ the report disagrees with the screen
⭐       the user just came from. ⭐⭐ "I closed that job ten
⭐       seconds ago and the report says it's open" is a support
⭐       ticket you will get. ⭐ Show the data timestamp.
⭐     ⭐⭐ A LONG QUERY ON A REPLICA IS EITHER CANCELLED
⭐       (conflict with recovery) OR — with `hot_standby_feedback`
⭐       ON — ⭐⭐ IT HOLDS BACK VACUUM ON THE ***PRIMARY***.
⭐       ⭐ Which means your read-only reporting query bloats the
⭐         write database. Exactly the Day 194 mechanism, at a
⭐         distance, and it catches everybody once.

⭐⭐ ② MATERIALIZED VIEWS — precomputed, refreshed on a schedule.
⭐   ⭐ REFRESH MATERIALIZED VIEW ***CONCURRENTLY*** — and
⭐   ⭐⭐ IT REQUIRES A UNIQUE INDEX ON THE VIEW. Without
⭐     CONCURRENTLY the refresh takes an ACCESS EXCLUSIVE lock,
⭐     and ⭐⭐ EVERY READER QUEUES BEHIND IT (Day 196) — a
⭐     "read-only dashboard" that stalls the whole board for 40 s
⭐     every ten minutes.
⭐   ⭐ Freshness = the refresh interval. ⭐⭐ PUT THAT NUMBER IN
⭐     THE UI. "As of 14:05" prevents an entire class of ticket.

⭐⭐ ③ INCREMENTAL ROLLUP TABLES — maintained by a job (Day 264)
⭐   or from the outbox (Day 263).
⭐   ⭐ The only option that scales to near-real-time, and the
⭐     only one that forces you to solve late data (Part 5).
⭐   ⭐⭐ THE RULE THAT KEEPS IT HONEST: ***IF YOU CANNOT REBUILD
⭐     THE ROLLUP FROM THE SOURCE, IT IS NOT A CACHE — IT IS A
⭐     SECOND SOURCE OF TRUTH*** (Day 266), and it will drift,
⭐     and you will have no way to prove it did.
```

# Part 5 — ⭐⭐ Buckets, time zones and late data

```
⭐⭐ THE TIME ZONE LANDMINE:
⭐   date_trunc('day', occurred_at)     -- ⭐⭐ THIS IS UTC
⭐   ⇒ ⭐ Your Chennai tenant's "Monday" ends at 05:30 on Monday
⭐     morning UTC. ⭐⭐ EVERY DAILY NUMBER YOU SHOW THEM IS
⭐     SPLIT ACROSS TWO OF YOUR BUCKETS, and none of them match
⭐     what they counted by hand.
⭐   ⭐ Store `timestamptz` (Day 187), aggregate with
⭐     `date_trunc('day', occurred_at AT TIME ZONE :tenant_tz)`.
⭐   ⇒ ⭐⭐ AND THE CONSEQUENCE PEOPLE MISS: WITH DST, A "DAY" IS
⭐     SOMETIMES 23 OR 25 HOURS. Any rollup that assumes 24
⭐     double-counts or drops an hour, twice a year, in the
⭐     direction nobody checks.

⭐⭐ LATE DATA — an event arrives for a bucket you already sealed:
⭐   ⭐ a mobile client syncs after two days offline
⭐   ⭐ a provider webhook is retried (Day 263)
⭐   ⇒ ⭐ TWO STRATEGIES:
⭐     ⭐⭐ RECOMPUTE A TRAILING WINDOW — rebuild the last 7 days
⭐       every night. ⭐ Simple, self-healing, and right far more
⭐       often than people expect.
⭐     ⭐ IDEMPOTENT UPSERTS keyed by (bucket, dimensions), so
⭐       re-applying an event is safe (Day 264's guard, again).
⭐   ⇒ ⭐⭐ WHAT YOU MUST NOT DO IS `+= 1` ON DELIVERY, because
⭐     at-least-once (Day 265) then means your totals drift
⭐     upward forever with no way to detect it.
```

# Part 6 — ⭐⭐ Exports without an OOM

```python
rows = session.scalars(select(Job).where(...)).all()   # ⭐⭐ 400,000
return Response(to_csv(rows), media_type="text/csv")
```

```
⭐⭐ WHAT THAT COSTS: 400k ORM objects ≈ ⭐ 2–4 GB OF RSS, one
⭐   worker held for three minutes, a proxy that gives up at 60 s,
⭐   ⭐⭐ AND THEN THE USER CLICKS THE BUTTON AGAIN — so you are
⭐   now doing it twice, concurrently, on the same pod.

⭐⭐ THREE FIXES, IN ORDER, AND THE THIRD IS THE REAL ONE:
⭐   ① ⭐ A SERVER-SIDE CURSOR / `yield_per` (Day 188) so rows
⭐     stream instead of materialising.
⭐   ② ⭐ A STREAMING RESPONSE so bytes leave as they are produced.
⭐   ③ ⭐⭐ AN EXPORT IS A JOB, NOT A REQUEST (Days 264–265):
⭐     enqueue ⇒ write to storage ⇒ hand back a presigned link
⭐     (Day 267) ⇒ notify.
⭐     ⇒ ⭐ It survives a disconnect, it can be retried, it does
⭐       not hold a worker, and it is auditable.
⭐   ⭐ THE CROSSOVER: a few thousand rows ⇒ stream it inline.
⭐     Above that ⇒ make it a job. ⭐ Say the number in the ADR.
```

```
⭐⭐ AND THE ONE NOBODY EXPECTS — CSV INJECTION:
⭐   ⭐ A cell beginning `=`, `+`, `-` or `@` is a FORMULA in
⭐     Excel and Sheets. ⭐⭐ A CUSTOMER NAMES THEIR SITE
⭐     `=cmd|'/c calc'!A1` AND YOUR EXPORT EXECUTES IT ON YOUR
⭐     ACCOUNTANT'S LAPTOP.
⭐   ⇒ ⭐ Prefix such cells with `'`, or quote and escape them.
⭐     ⭐⭐ THIS IS STORED XSS'S COUSIN, AND IT LEAVES YOUR
⭐       SYSTEM ENTIRELY BEFORE IT FIRES.
```

# Part 7 — ⭐⭐ The numbers that are quietly wrong

```
⭐⭐ ① `COUNT(*)` FOR "1,234,567 RESULTS"
⭐   ⭐ It scans the entire filtered set to render a number that
⭐     nobody clicks past page 3 of. ⇒ ⭐ Cursor pagination with
⭐     no total (Day 260), a capped count (`LIMIT 1001` ⇒
⭐     "1000+"), or the planner's estimate for a fuzzy figure.

⭐⭐ ② `count(distinct user_id)` AT SCALE ⇒ HyperLogLog (Day 204),
⭐   12 KB and 0.81% error. ⭐ State the error bar in the UI or
⭐   someone will reconcile it against an exact number and file
⭐   a bug.

⭐⭐ ③ SOFT-DELETED ROWS IN REPORTS (Day 187) — ⭐ every report
⭐   is wrong unless every report remembers the filter, and one
⭐   forgotten `WHERE deleted_at IS NULL` in a rollup is
⭐   invisible until someone compares two screens.

⭐⭐ ④ THE ONE THAT ENDS TRUST — SNAPSHOT vs CURRENT (Day 187):
⭐   ⭐ revenue computed by joining orders to the CURRENT product
⭐     price ⇒ ⭐⭐ LAST YEAR'S REVENUE CHANGES WHENEVER SOMEONE
⭐     EDITS A PRICE TODAY.
⭐   ⇒ ⭐⭐ A FINANCE REPORT THAT CHANGES WHEN NOBODY CHANGED ANY
⭐     ORDERS IS THE BUG THAT ENDS TRUST IN THE WHOLE SYSTEM —
⭐     not in the report. ⭐ The order line stores the price it
⭐     was sold at, and the report reads that.

⭐⭐ ⑤ MONEY — sum in integer minor units, round ONCE at the end
⭐   (Day 254). ⭐ A report that misses the ledger by a few paise
⭐   is a data-model bug, not a display bug, and rounding it
⭐   away hides the model error permanently.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Reaching for a search engine before asking which feature it is | Most "search" requests are faceted filtering — that's a composite index. |
| Expecting `ORDER BY ts_rank` to use the index | Ranking cost scales with the match set, so common words are the slow ones. |
| `ILIKE '%x%'` without trigram | A leading wildcard isn't sargable; it's a sequential scan every time. |
| Adopting Elasticsearch for speed alone | The price is a dual write and a reindex pipeline you own forever. |
| Filtering search results in Python | Broken pagination *and* other tenants' rows in your process and logs. |
| Running reports on the primary | One report evicts hot data from shared buffers and slows everything for minutes. |
| Forgetting replica lag in reports | "I closed that ten seconds ago" tickets. Show the data timestamp. |
| Long replica queries with `hot_standby_feedback` on | Your read-only report bloats the write primary. |
| `REFRESH MATERIALIZED VIEW` without `CONCURRENTLY` | An ACCESS EXCLUSIVE lock; every reader queues behind the refresh. |
| `CONCURRENTLY` without a unique index on the view | It simply won't run. |
| Not showing the freshness timestamp | Users reconcile a stale view against a live screen and file bugs. |
| A rollup that can't be rebuilt from source | It's a second source of truth, and it will drift undetectably. |
| `date_trunc` in UTC for tenant-facing days | Every daily number is split across two buckets for non-UTC tenants. |
| Assuming a day is 24 hours | DST makes it 23 or 25 twice a year, in the direction nobody checks. |
| `+= 1` on event delivery | At-least-once means totals drift upward forever. |
| No plan for late data | Recompute a trailing window, or upsert idempotently. |
| `.all()` for an export | Gigabytes of RSS, a held worker, a proxy timeout, and the user clicks again. |
| A large export as a synchronous request | It's a job: storage, presigned link, notification. |
| Unescaped leading `=` in CSV cells | Formula injection that executes on the recipient's machine. |
| `COUNT(*)` for a result total | A full scan of the filtered set for a number nobody uses. |
| Joining to current prices for historical revenue | Last year's revenue changes when someone edits a price today. |

## Interview questions

**Q: The product wants search. What do you do first?**

> Ask which of four things they mean, because they have different answers. Exact lookup is a unique
> index. Typeahead is a prefix or trigram index with a hundred-millisecond budget. Full text is
> tsvector and GIN. And faceted filtering with sorting is plain SQL with the right composite index —
> which is what most "we need Elasticsearch" requests turn out to be. Getting that question in early
> is worth more than any implementation detail, because the wrong answer here is a system you operate
> for years.

**Q: When does Postgres full-text search stop being enough?**

> When I need per-field relevance tuning I'll actually iterate on, facet aggregations at scale, tens
> of millions of documents, or cross-entity search in one box. Not "when it's slow", because the
> usual slowness is a specific known thing: `ORDER BY ts_rank` doesn't use the index, so ranking cost
> scales with the size of the match set rather than the limit — which is why common-word queries are
> the slow ones. And I'd state the price out loud: an engine means a dual write and a reindex
> pipeline, so I own consistency between two stores forever, and I'd route the writes through the
> outbox rather than hoping.

**Q: What's wrong with filtering search results by tenant in Python?**

> Two things. Pagination breaks immediately — you ask for twenty and show three while the engine
> reports nine hundred hits — and, more seriously, you've already read other tenants' rows into your
> process, your logs and your APM trace. That list comprehension isn't a filter, it's a redaction
> applied after the disclosure. The filter has to be in the query where the index can use it, or in
> the engine's own filter clause, and it should be the same shared predicate the rest of the app uses.

**Q: Where do reports run?**

> Not on the primary, because one analytical query can read more pages than an hour of OLTP traffic
> and evicts the hot set from shared buffers while doing it — so it doesn't just run slowly, it makes
> everything else slow for minutes afterwards. A read replica is the cheapest correct answer, with
> two caveats: lag means the report can disagree with the screen the user just left, so I show the
> data timestamp; and a long query on a replica either gets cancelled or, with `hot_standby_feedback`
> on, holds back vacuum on the primary — which is the surprising one, a read-only report bloating the
> write database. Beyond that, materialized views refreshed concurrently, or incremental rollups if
> it needs to be near-real-time.

**Q: A finance report changed and nobody changed any orders. What happened?**

> Almost certainly the report joins order lines to the current product price instead of the price
> stored on the line at the time of sale. So editing a price today rewrites last year's revenue. It's
> the snapshot-versus-current distinction, and it's the bug that ends trust in the entire system
> rather than in one screen, because the user's conclusion is that the numbers are made up. The fix
> is in the data model — the line stores what it was sold for — not in the report.

## 🎙️ Articulation drill

**Three minutes: "Search and reporting for a multi-tenant SaaS."**

Open with the classification, because it saves the most money: **there are four features called
search** — exact lookup, typeahead, full text, and faceted filtering — and the last one is what most
Elasticsearch requests actually are, which makes it a composite index rather than a system to
operate. For full text, Postgres with a generated tsvector column and GIN, and name the specific
limit rather than a vague one: **`ORDER BY ts_rank` doesn't use the index, so ranking cost scales with
the match set — common words are the slow queries, not the rare ones.** Give the four honest reasons
to leave, and the price: a dual write and a reindex pipeline, routed through the outbox or it drifts
silently. Then the security point, in one line: **filtering search results in Python isn't a filter,
it's a redaction after the disclosure**, and it breaks pagination as a bonus. Move to reporting with
the reason it's different in kind: **one analytical query can evict your hot set from shared buffers,
so it doesn't run slowly, it makes everything else slow.** Replica first, with the two caveats —
lag disagreeing with the screen the user just left, and `hot_standby_feedback` letting a read-only
query bloat the write primary. Then materialized views with `CONCURRENTLY` and the unique index it
requires, and rollups with the honesty rule: **if you can't rebuild it from source it isn't a cache,
it's a second source of truth.** Close on correctness: time zones and the 23-hour day, idempotent
upserts because at-least-once makes `+= 1` drift forever, exports as jobs rather than requests, and
**the finance report that changes when nobody changed any orders — which is a data-model bug, and the
one that ends trust in the whole system rather than one screen.**
