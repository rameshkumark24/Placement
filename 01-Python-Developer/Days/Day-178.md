# Day 178

**L-178** · 🎸 **Django async** — ⭐⭐ what actually works, what silently doesn't, and why the ORM is the whole story

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: Django's async support is real at the view layer and shallow at the ORM
> layer — `async` methods exist, but they are a thread-pool wrapper around synchronous code, so you
> get the syntax of concurrency without most of its benefit.**
>
> ⭐ Day 134 said the dangerous combination is blocking code inside `async def`. ⭐⭐ Django makes that
> combination *the default outcome*, and then protects you from it with an exception you have to
> learn to read.

# Part 1 — ⭐ What genuinely works

```python
# ⭐ async views: real, since 3.1
async def event_list(request):
    async with httpx.AsyncClient() as c:                 # ⭐⭐ THE actual use case
        weather, rates = await asyncio.gather(
            c.get("https://weather.example/api"),
            c.get("https://rates.example/api"),
        )
    return JsonResponse({"weather": weather.json(), "rates": rates.json()})
```

```
⭐⭐ THE LIST OF THINGS THAT ARE GENUINELY ASYNC IN MODERN DJANGO:
⭐   ⭐ ASYNC VIEWS — run on the event loop under an ASGI server. ✅
⭐   ⭐ ASYNC MIDDLEWARE — ⭐⭐ but ONE sync middleware in the chain forces a
⭐        thread-pool hop for EVERY request through it (Part 3).
⭐   ⭐ ASYNC TESTS, `AsyncClient`, async signal receivers. ✅
⭐   ⭐ THE CACHE API (`acache.aget`), sessions, and `aauthenticate`. ✅
⭐   ⭐ `StreamingHttpResponse` with an async generator ⇒ ⭐⭐ SSE (Day 144)
⭐        works properly. ✅
⭐   ⭐ ASGI + Channels for WebSockets. ✅
⭐
⭐⭐ AND THE ONE THAT DECIDES EVERYTHING: **THE ORM.**
⭐   ⭐ `await Order.objects.aget(pk=1)`, `async for o in qs`, `.acreate()`,
⭐        `.asave()`, `.acount()` — ⭐⭐ THESE ALL EXIST AND THEY ALL WORK.
⭐   ⭐ ⭐⭐ AND THEY ARE `sync_to_async` WRAPPERS AROUND THE SYNCHRONOUS ORM.
⭐        ⭐ The database driver is still `psycopg`, blocking, in a thread.
⭐   ⇒ ⭐⭐ SO: THE SYNTAX IS ASYNC. THE CONCURRENCY IS A THREAD POOL. ⭐ You
⭐        do not get the "one loop, thousands of connections" property that
⭐        made async worth choosing in Day 137.
⭐   ⇒ ⭐ Compare with SQLAlchemy + `asyncpg` (Day 137), which is genuinely
⭐        non-blocking to the socket. ⭐⭐ That is the honest gap, and stating
⭐        it precisely is the interview answer.
```

# Part 2 — ⭐⭐ `SynchronousOnlyOperation`, and what it protects

```python
async def bad_view(request):
    order = Order.objects.get(pk=1)      # ⭐⭐ SynchronousOnlyOperation
    return JsonResponse({...})
```

```
⭐⭐ WHY DJANGO RAISES INSTEAD OF JUST WORKING — and this is a good design:
⭐   ⭐ a synchronous ORM call on the event loop would BLOCK THE LOOP ⇒
⭐        ⭐⭐ every other request on that worker stalls (Day 134's 50-second
⭐        regression). ⭐ Django refuses rather than let you ship that.
⭐   ⇒ ⭐⭐ THIS IS `lazy="raise"` FOR CONCURRENCY (Day 136): make the wrong
⭐        thing IMPOSSIBLE rather than merely slow. ⭐ Give Django credit for
⭐        it — most frameworks let you do the slow thing silently.

⭐⭐ THE THREE FIXES, AND THEY ARE NOT EQUIVALENT:
⭐   ⭐ `await Order.objects.aget(pk=1)`         ⭐ correct, and it is a
⭐        thread-pool call under the hood
⭐   ⭐ `await sync_to_async(f)()`               ⭐ for your own sync code
⭐   ⭐ ⭐⭐ MAKE THE VIEW SYNC (`def`)            ⭐ often the RIGHT answer —
⭐        see Part 5

⭐⭐ AND THE TRAP THAT PRODUCES IT WHEN YOU THOUGHT YOU WERE SAFE:
⭐   ⭐ `await Order.objects.aget(pk=1)` succeeds ⇒ you have an `Order`.
⭐   ⭐ then `order.user.email` ⇒ ⭐⭐ **`SynchronousOnlyOperation`** — because
⭐        a lazy relation load is an IMPLICIT synchronous query.
⭐   ⇒ ⭐⭐ EXACTLY Day 137's greenlet lesson, in a different framework: **in
⭐        async code, lazy loading cannot work, because attribute access is
⭐        not an await point.** ⭐ The fix is the same: `select_related` /
⭐        `prefetch_related` eagerly, always.
⭐   ⇒ ⭐ AND THE FAILURE MODE IS BETTER THAN SQLAlchemy'S SYNC BEHAVIOUR:
⭐        ⭐⭐ a silent N+1 becomes a loud exception. ⭐ Async is stricter, and
⭐        the strictness is the feature.
```

```
⭐⭐ `sync_to_async` HAS TWO MODES AND THE DEFAULT IS THE SLOW ONE:
⭐   ⭐ `thread_sensitive=True` (DEFAULT) ⇒ ⭐⭐ ALL such calls run in ONE
⭐        SHARED THREAD, serialised. ⭐ Necessary because Django's ORM uses
⭐        thread-local connections and transactions.
⭐        ⇒ ⭐⭐ SO TEN CONCURRENT `sync_to_async` ORM CALLS RUN **ONE AT A
⭐          TIME**. ⭐ Your `asyncio.gather` over five queries is sequential.
⭐   ⭐ `thread_sensitive=False` ⇒ a real thread pool, ⭐⭐ and NOT SAFE for
⭐        the ORM inside a transaction.
⭐   ⇒ ⭐⭐ THIS IS THE SINGLE MOST IMPORTANT PERFORMANCE FACT ABOUT ASYNC
⭐        DJANGO, AND IT IS ALMOST NEVER MENTIONED. ⭐ It is why "I made my
⭐        views async and nothing got faster" is the normal outcome.
```

# Part 3 — ⭐⭐ The mixing cost

```
⭐⭐ EVERY BOUNDARY CROSSING COSTS A THREAD HOP, AND DJANGO INSERTS THEM
⭐   AUTOMATICALLY WHEREVER YOU MIX:

⭐   ⭐ ASGI server → async middleware → async view      ⭐ 0 hops ✅
⭐   ⭐ ASGI server → SYNC middleware → async view       ⭐⭐ 2 hops (in, out)
⭐   ⭐ ASGI server → async view → `sync_to_async` ORM   ⭐ 1 hop per call
⭐   ⭐ WSGI server → async view                          ⭐⭐ Django runs an
⭐        event loop PER REQUEST — ⭐ strictly worse than a sync view
⭐
⭐   ⇒ ⭐⭐ ONE SYNC MIDDLEWARE IN THE CHAIN FORCES ADAPTATION FOR EVERY
⭐        REQUEST PASSING THROUGH IT. ⭐ And most third-party middleware is
⭐        still sync — ⭐⭐ so a single package can erase the benefit of every
⭐        async view you wrote, invisibly.
⭐   ⇒ ⭐ Django tells you: `async_capable` / `sync_capable` flags on
⭐        middleware classes. ⭐⭐ Audit your `MIDDLEWARE` list before believing
⭐        any async benchmark of your own app.

⭐⭐ AND THE ONE THAT BITES IN MANAGEMENT COMMANDS AND SCRIPTS:
⭐   ⭐ `async_to_sync(f)()` runs an async function from sync code.
⭐   ⭐ ⭐⭐ CALLING IT INSIDE AN ALREADY-RUNNING EVENT LOOP DEADLOCKS OR
⭐        RAISES. ⭐ It creates or reuses a loop, and nesting is not supported.
⭐   ⇒ ⭐ Know which side of the boundary you are on before you reach for
⭐        either adapter — ⭐⭐ that confusion is most of the pain people
⭐        attribute to "async Django is broken".
```

# Part 4 — ⭐ Channels, and when async Django is actually right

```
⭐⭐ CHANNELS — WebSockets in Django (Day 144's problem, Django's answer):
⭐   ⭐ `AsyncWebsocketConsumer` for the socket
⭐   ⭐ ⭐⭐ A CHANNEL LAYER (Redis) FOR FAN-OUT — ⭐ which is EXACTLY the
⭐        architecture Day 144 derived: process-local sockets, shared bus for
⭐        crossing between workers. ⭐⭐ Channels ships it.
⭐   ⭐ groups = rooms; `group_send` publishes.
⭐   ⇒ ⭐ AND THE SAME CAVEATS APPLY UNCHANGED: ⭐⭐ the Redis channel layer is
⭐        not durable (Day 144), so anything you promised to deliver is
⭐        persisted first and resynced on reconnect; ⭐ backpressure,
⭐        heartbeats and reconnect jitter are still yours.
⭐   ⇒ ⭐⭐ Channels is a genuine reason to run Django on ASGI, and it is the
⭐        most common one.

⭐⭐ THE FOUR CASES WHERE ASYNC DJANGO PAYS:
⭐  1. ⭐⭐ WEBSOCKETS / SSE — long-lived connections. ⭐ A thread per
⭐       connection does not scale; an event loop does. ⭐⭐ The clearest win.
⭐  2. ⭐⭐ FAN-OUT TO SLOW THIRD PARTIES — five HTTP calls with
⭐       `asyncio.gather` in one view. ⭐ Genuinely faster, ⭐⭐ and it works
⭐       because `httpx` is really async even though the ORM is not.
⭐  3. ⭐ STREAMING RESPONSES — LLM tokens, large exports.
⭐  4. ⭐ VERY HIGH-CONCURRENCY, LOW-CPU proxying.
⭐
⭐⭐ AND THE CASE THAT IS **NOT** ON THE LIST: A NORMAL CRUD API.
⭐   ⭐ if your view is `query → serialise → return`, ⭐⭐ THE ORM CALL IS THE
⭐        WHOLE REQUEST, and it is a thread-pool call either way.
⭐   ⇒ ⭐⭐ ASYNC ADDS THREAD HOPS AND A `SynchronousOnlyOperation` HAZARD AND
⭐        SUBTRACTS NOTHING. ⭐ Day 134's conclusion holds: a consistently sync
⭐        service beats an inconsistently async one, and the worst outcome is
⭐        the half-migration.
```

# Part 5 — ⭐⭐ The honest recommendation

```
⭐⭐ WHAT I WOULD ACTUALLY DO, AND WHY:

⭐   ⭐ ✅ SYNC VIEWS + MORE GUNICORN WORKERS for CRUD. ⭐⭐ Day 156's Little's
⭐        Law: if you need 640 rps and each request is 50 ms, you need 32
⭐        concurrent slots — ⭐ workers and threads give you those, and the
⭐        code stays simple and debuggable.
⭐   ⭐ ✅ ASYNC VIEWS for the specific endpoints that fan out to slow
⭐        third parties. ⭐⭐ Mixing is FINE at the view level — Django
⭐        supports per-view choice, ⭐ which is a genuine advantage over
⭐        all-or-nothing frameworks.
⭐   ⭐ ✅ CHANNELS on ASGI for WebSockets, as its own deployment.
⭐   ⭐ ❌ ⭐⭐ DO NOT REWRITE A WORKING SYNC CODEBASE TO ASYNC EXPECTING
⭐        THROUGHPUT. ⭐ The ORM is the bottleneck and it will not become
⭐        non-blocking by you adding `await`.

⭐⭐ AND THE MEASUREMENT DISCIPLINE (Day 156), because this is exactly where
⭐   people believe a benchmark they should not:
⭐   ⭐ measure with an OPEN model, with a REALISTIC MIX, ⭐⭐ and check the
⭐        MIDDLEWARE for sync entries before believing any number.
⭐   ⭐ ⭐⭐ WATCH EVENT-LOOP LAG (Day 147). ⭐ In async Django it is the single
⭐        best detector of a synchronous call that slipped through — and one
⭐        slipping through is the normal case, not the exception.

⭐⭐ THE FIVE-LINE SUMMARY:
⭐   ⭐ Async views are real; the async ORM is a thread-pool façade.
⭐   ⭐⭐ `sync_to_async` defaults to ONE SHARED THREAD, so concurrent ORM
⭐        calls serialise — which is why nothing gets faster.
⭐   ⭐ Lazy relation access raises in async code, which is Day 137's lesson
⭐        and is a FEATURE.
⭐   ⭐ One sync middleware taxes every request through it.
⭐   ⭐⭐ Use async for sockets, streaming and third-party fan-out. Use sync
⭐        for CRUD, and add workers.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Expecting async views to speed up a CRUD API | The ORM call is the whole request and it's a thread-pool call either way. |
| Assuming Django's `a*` ORM methods are non-blocking | They're `sync_to_async` wrappers around the synchronous ORM. |
| Not knowing `sync_to_async` defaults to one shared thread | Concurrent ORM calls serialise, so `gather` over five queries is sequential. |
| `thread_sensitive=False` around ORM calls in a transaction | Unsafe — Django's connections and transactions are thread-local. |
| Touching a relation on an object fetched with `aget` | `SynchronousOnlyOperation` — a lazy load is an implicit sync query. |
| Treating that exception as an obstacle | It's `lazy="raise"` for concurrency; it stops you shipping a blocked event loop. |
| One sync middleware in an otherwise async stack | Two thread hops for every request through it — it can erase the whole benefit. |
| Async views under a WSGI server | Django runs an event loop per request — strictly worse than a sync view. |
| `async_to_sync` inside a running loop | Deadlock or exception. Know which side of the boundary you're on. |
| Assuming the Channels Redis layer is durable | It isn't. Persist first, resync on reconnect. |
| Rewriting a working sync codebase for throughput | The ORM is the bottleneck and `await` won't change that. |
| Believing an async benchmark without auditing `MIDDLEWARE` | A single sync package invalidates it. |
| No event-loop lag metric in async Django | It's the best detector of a synchronous call slipping through, and one always does. |

## Interview questions

**Q: Is Django async?**

> At the view layer, genuinely yes — async views, middleware, tests, the cache API, streaming
> responses, and Channels for WebSockets all work properly under ASGI. At the ORM layer, no in the
> way that matters: `aget`, `acreate` and `async for` all exist and all work, but they're
> `sync_to_async` wrappers around the synchronous ORM, so the driver is still blocking and the
> concurrency is a thread pool. So you get the syntax of async without the property that made async
> worth choosing — one loop handling thousands of connections. That's the honest gap against
> SQLAlchemy with `asyncpg`, which is non-blocking all the way to the socket.

**Q: Someone makes all their views async and nothing gets faster. Why?**

> Most likely `sync_to_async`'s default. It runs with `thread_sensitive=True`, which means every such
> call executes in *one shared thread*, serialised — necessary because Django's connections and
> transactions are thread-local. So ten concurrent ORM calls run one at a time, and an
> `asyncio.gather` over five queries is effectively sequential. That's the single most important
> performance fact about async Django and it's almost never mentioned. The second cause is
> middleware: one sync middleware in the chain forces a thread-pool hop in and out for every request
> through it, and most third-party middleware is still sync — so a single package can erase the
> benefit of every async view, invisibly. I'd audit the `async_capable` flags before believing any
> benchmark.

**Q: You `await Order.objects.aget(pk=1)` and then read `order.user.email`. What happens?**

> `SynchronousOnlyOperation`. The `aget` worked, but crossing the relation is an implicit
> synchronous query, and attribute access isn't an await point so there's nowhere to suspend. It's
> exactly the greenlet-bridge lesson from async SQLAlchemy in a different framework: in async code,
> lazy loading cannot work. The fix is the same — eager load with `select_related` or
> `prefetch_related`. And I'd point out that this is *better* than the sync behaviour: the identical
> code is a silent N+1 in sync Django and a loud exception in async, so async is stricter, and the
> strictness is the feature. Django refusing rather than silently blocking the event loop is a good
> design decision.

**Q: When would you actually use async Django?**

> Four cases. WebSockets or SSE, where a thread per connection doesn't scale and an event loop does —
> that's the clearest win and the most common reason to run ASGI, via Channels. Fan-out to slow third
> parties, where `asyncio.gather` over five HTTP calls is genuinely faster because `httpx` really is
> async even though the ORM isn't. Streaming responses, like LLM tokens or large exports. And
> high-concurrency low-CPU proxying. What's *not* on the list is a normal CRUD API: if the view is
> query, serialise, return, then the ORM call is the whole request and it's a thread-pool call either
> way, so async adds thread hops and a `SynchronousOnlyOperation` hazard and subtracts nothing.
> Django lets you choose per view, which is a real advantage — so I'd keep sync views and add
> workers, and make async the exception where it earns its place.

## 🎙️ Articulation drill

**Two minutes: "Should we move our Django app to async?"**

Split the answer at the ORM, because that's where the truth lives: views are genuinely async, the ORM
is a thread-pool façade with async syntax, so you don't get the property that made async worth
choosing. Then give the two mechanical reasons nothing gets faster — `sync_to_async` defaults to one
shared thread so concurrent ORM calls serialise, and one sync middleware taxes every request through
it. Say what async *does* buy: sockets, streaming, and third-party fan-out, because `httpx` really is
async. Then give the recommendation and its arithmetic: **sync views plus enough workers to satisfy
Little's Law, with async reserved for the endpoints that fan out** — and note that Django letting you
choose per view is a genuine advantage. Close on Day 134's rule: a consistently sync service beats an
inconsistently async one, and the worst outcome is the half-migration.
