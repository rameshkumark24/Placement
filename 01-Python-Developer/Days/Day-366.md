# Part 2 — ⭐ The target Dockerfile, assembled from Days 361–364

```dockerfile
# syntax=docker/dockerfile:1.7
ARG PYTHON_IMAGE=python:3.12-slim@sha256:...      # ⭐ pinned (362)

# ───────── builder ─────────
FROM ${PYTHON_IMAGE} AS builder
ENV PIP_DISABLE_PIP_VERSION_CHECK=1 PYTHONDONTWRITEBYTECODE=1
RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential libpq-dev && rm -rf /var/lib/apt/lists/*
RUN python -m venv /opt/venv                      # ⭐ 363: one directory
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.lock .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --require-hashes -r requirements.lock

# ───────── test (run explicitly in CI with --target test) ─────────
FROM builder AS test
COPY . .
RUN pip install --require-hashes -r requirements-dev.lock
RUN pytest -q && ruff check . && mypy app

# ───────── runtime ─────────
FROM ${PYTHON_IMAGE} AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
        libpq5 && rm -rf /var/lib/apt/lists/* \
    && useradd -u 10001 -m -s /usr/sbin/nologin app
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONHASHSEED=random
WORKDIR /app
COPY --chown=10001:10001 app/ ./app/
COPY --chown=10001:10001 alembic/ ./alembic/ alembic.ini ./
RUN python -m compileall -q /app /opt/venv        # ⭐⭐ 362: cold start
USER 10001
EXPOSE 8000
STOPSIGNAL SIGTERM
CMD ["python", "-m", "gunicorn", "app.main:app", \
     "-k", "uvicorn.workers.UvicornWorker", \
     "-c", "gunicorn.conf.py"]                    # ⭐ config in a file
```

```
⭐⭐ FOUR THINGS TO NOTICE:
⭐   ① ⭐⭐ EXEC FORM `CMD`, SO SIGTERM REACHES THE PROCESS
⭐      (Day 361). ⭐ Non-negotiable.
⭐   ② ⭐ Migrations copied in but ***not run*** here — Part 5.
⭐   ③ ⭐⭐ GUNICORN CONFIG IN A FILE, NOT FLAGS — ⭐ so worker
⭐      count can be computed from the cgroup rather than
⭐      hard-coded (Part 3).
⭐   ④ ⭐ `PYTHONHASHSEED=random` is the default; ⭐⭐ SETTING IT
⭐      EXPLICITLY DOCUMENTS THAT YOU DID NOT PIN IT, WHICH
⭐      MATTERS BECAUSE SOME "REPRODUCIBLE BUILD" GUIDES
⭐      SUGGEST PINNING IT AND THAT WEAKENS HASH-DoS
⭐      PROTECTION.
```

# Part 3 — ⭐⭐ The gunicorn config that respects the container

```python
# gunicorn.conf.py — ⭐⭐ EVERY VALUE HERE IS A DECISION
import os, multiprocessing

def _cgroup_cpus() -> float:
    try:                                        # ⭐⭐ cgroup v2
        quota, period = open("/sys/fs/cgroup/cpu.max").read().split()
        if quota != "max":
            return int(quota) / int(period)
    except FileNotFoundError:
        pass
    return float(len(os.sched_getaffinity(0)))  # ⭐ better than cpu_count

# ⭐⭐ EXPLICIT ENV WINS. THE DETECTION IS A FALLBACK, NOT A
# ⭐   CLEVERNESS CONTEST (Day 361).
workers = int(os.getenv("WEB_CONCURRENCY", max(2, round(_cgroup_cpus() * 2))))

worker_class = "uvicorn.workers.UvicornWorker"
bind = "0.0.0.0:8000"                    # ⭐⭐ NOT 127.0.0.1 (Day 364)

timeout = 60                             # ⭐ worker hard kill
graceful_timeout = 30                    # ⭐⭐ MUST EXCEED YOUR p99
keepalive = 5                            # ⭐ behind a proxy: match it

max_requests = 2000                      # ⭐⭐ Day 361: RSS never falls
max_requests_jitter = 200                # ⭐⭐ OR ALL WORKERS RECYCLE
                                         #   AT THE SAME MOMENT

preload_app = False                      # ⭐ Part 4 — read carefully
accesslog = "-"                          # ⭐ stdout (Day 375)
errorlog = "-"
logger_class = "app.logging.JSONLogger"  # ⭐ structured (Day 285)
```

```
⭐⭐ THE WORKER-COUNT ARITHMETIC, DONE HONESTLY:
⭐   ⭐ ***ASYNC WORKERS (uvicorn)***: each handles many
⭐     concurrent I/O-bound requests, ⭐⭐ BUT STILL ONLY ONE
⭐     CPU'S WORTH OF WORK. ⭐ So workers ≈ CPUs available,
⭐     ⭐ ×2 if your handlers are heavily I/O-bound and the CPU
⭐     is often idle.
⭐   ⭐ ⭐⭐ `2 × CPU + 1` IS THE ***SYNC*** WORKER RECIPE AND IT
⭐     IS WRONG FOR ASYNC WORKERS — it is memory you spend for
⭐     concurrency the event loop already gives you.
⭐   ⭐ ⭐⭐ AND THE MEMORY CHECK THAT DECIDES IT: workers ×
⭐     per-worker RSS MUST FIT INSIDE THE LIMIT WITH HEADROOM.
⭐     ⭐ At 150 MB per worker and a 512 MB limit, ⭐⭐ THREE
⭐     WORKERS IS YOUR CEILING NO MATTER WHAT THE CPU MATH SAYS.
⭐   ⇒ ⭐⭐ SO THE REAL RULE IS: ***COMPUTE FROM CPU, THEN CAP BY
⭐     MEMORY, THEN VERIFY BY MEASUREMENT.***
```

# Part 4 — ⭐⭐ Cold start, and what actually costs the seconds

```
⭐⭐ WHERE A PYTHON SERVICE'S STARTUP TIME GOES — ⭐ measure with
⭐   `python -X importtime -m app.main 2>&1 | sort -k2 -rn | head`:
⭐   ⭐ ⭐⭐ IMPORTS DOMINATE. ⭐ `pandas` ~1.5 s, `sqlalchemy`
⭐     ~0.4 s, `boto3` ~0.8 s, `torch` several seconds.
⭐   ⭐ Bytecode compilation on first import — ⭐⭐ ELIMINATED BY
⭐     `compileall` AT BUILD TIME (Day 362), and this is the
⭐     single easiest second to remove.
⭐   ⭐ Connection pool warm-up, ⭐ config fetch, ⭐ migration
⭐     check.

⭐⭐ THE FOUR FIXES, IN ORDER OF EFFECT:
⭐   ① ⭐⭐ `compileall` AT BUILD TIME. ⭐ Free, and mandatory
⭐      with a read-only filesystem.
⭐   ② ⭐⭐ LAZY-IMPORT THE HEAVY, RARELY-USED THINGS. ⭐ `boto3`
⭐      imported inside the one function that uses S3 rather
⭐      than at module scope ⭐⭐ SAVES ITS FULL COST ON EVERY
⭐      START AND EVERY WORKER.
⭐   ③ ⭐ Do not connect to everything at import time — ⭐⭐ THAT
⭐      IS ALSO DAY 303'S RULE ABOUT `pytest --collect-only`
⭐      OPENING A DATABASE. ⭐ Connect in `lifespan`.
⭐   ④ ⭐ Trim dependencies. ⭐⭐ IF YOU IMPORT `pandas` TO PARSE
⭐      ONE CSV, THAT IS 1.5 SECONDS AND ~150 MB PER WORKER FOR
⭐      SOMETHING `csv` DOES.

⭐⭐ AND `preload_app`, WHICH IS A GENUINE TRADE:
⭐   ⭐ ✔ ON: imports happen ***once*** in the master, then
⭐     fork ⇒ ⭐⭐ FASTER START AND INITIALLY SHARED MEMORY.
⭐   ⭐ ✘ ⭐⭐ AND COPY-ON-WRITE SHARING ERODES, BECAUSE CPython
⭐     REFCOUNTS TOUCH OBJECT HEADERS AND DIRTY THE PAGES
⭐     (Day 361). ⭐ The saving is real for the first minutes and
⭐     not permanent.
⭐   ⭐ ✘ ⭐⭐ AND THE REAL DANGER: ***ANYTHING CREATED BEFORE
⭐     THE FORK IS SHARED ACROSS WORKERS.*** ⭐ A database
⭐     connection, an `httpx.AsyncClient`, or an asyncio loop
⭐     created at import time ⭐⭐ WILL BE INHERITED BY EVERY
⭐     WORKER AND WILL CORRUPT IN WAYS THAT LOOK LIKE RANDOM
⭐     PRODUCTION CORRUPTION.
⭐   ⇒ ⭐⭐ SO: `preload_app = False` UNLESS YOU HAVE VERIFIED
⭐     NOTHING STATEFUL IS CREATED AT IMPORT TIME. ⭐ It is a
⭐     performance optimisation with a correctness precondition.
```

# Part 5 — ⭐⭐ Migrations: where they run, and where they must not

```
⭐⭐ ❌ ***IN THE ENTRYPOINT.*** ⭐ `alembic upgrade head &&
⭐   gunicorn …`
⭐   ⇒ ⭐⭐ THREE REPLICAS START ⇒ THREE CONCURRENT MIGRATIONS.
⭐     ⭐ Alembic takes a lock so you probably survive, ⭐⭐ BUT
⭐     TWO REPLICAS NOW WAIT ON THE LOCK AND FAIL THEIR STARTUP
⭐     PROBE, AND THE ORCHESTRATOR RESTARTS THEM. ⭐ A restart
⭐     loop that resolves itself eventually and terrifies
⭐     everyone.
⭐   ⇒ ⭐ And on rollback: ⭐⭐ THE OLD IMAGE'S ENTRYPOINT
⭐     MIGRATES ***DOWN***, WHICH IS HOW YOU LOSE DATA DURING AN
⭐     INCIDENT.

⭐⭐ ✔ ***A SEPARATE, ONE-SHOT STEP THAT RUNS BEFORE THE
⭐   ROLLOUT.***
⭐   ⭐ A Kubernetes Job / ECS task / pipeline step, ⭐ using the
⭐     ***same image***, with a different command.
⭐   ⇒ ⭐⭐ ONE RUNNER, DETERMINISTIC ORDER, AND A FAILURE STOPS
⭐     THE DEPLOY INSTEAD OF HALF-DEPLOYING.
⭐   ⭐ ⭐⭐ AND IT ONLY WORKS BECAUSE OF EXPAND/CONTRACT
⭐     (Day 283): THE MIGRATION MUST BE COMPATIBLE WITH THE
⭐     ***OLD*** CODE THAT IS STILL RUNNING WHILE IT APPLIES.
⭐   ⇒ ⭐ Which is why the rule is: ⭐⭐ ***ADDITIVE MIGRATIONS
⭐     BEFORE THE ROLLOUT, DESTRUCTIVE ONES A RELEASE LATER.***

⭐⭐ AND THE PYTHON DETAIL: ⭐⭐ ALEMBIC'S `env.py` OFTEN IMPORTS
⭐   YOUR APPLICATION MODELS, WHICH IMPORTS YOUR SETTINGS, WHICH
⭐   REQUIRES EVERY ENV VAR. ⭐ So the migration job needs the
⭐   full config, ⭐⭐ OR IT FAILS WITH A VALIDATION ERROR THAT
⭐   LOOKS NOTHING LIKE A DATABASE PROBLEM.
```

# Part 6 — ⭐⭐ Graceful shutdown, verified rather than assumed

```
⭐⭐ THE FULL CHAIN — ⭐ five links, and one broken link makes
⭐   the rest pointless:
⭐   ① ⭐ Orchestrator sends SIGTERM to PID 1.
⭐   ② ⭐⭐ IT ARRIVES — exec form, no shell wrapper (Day 361).
⭐   ③ ⭐⭐ READINESS FAILS IMMEDIATELY, LIVENESS DOES NOT
⭐      (Day 325). ⭐ Then sleep ~5 s so the load balancer
⭐      notices.
⭐   ④ ⭐ Gunicorn stops accepting, finishes in-flight requests
⭐      up to `graceful_timeout`.
⭐   ⑤ ⭐ Pools closed, metrics flushed, exit 0.
⭐   ⇒ ⭐⭐ AND THE GRACE PERIOD (`stop_grace_period` /
⭐     `terminationGracePeriodSeconds`) MUST EXCEED ③+④+⑤ ⭐ or
⭐     the orchestrator SIGKILLs you mid-request and you have
⭐     built an elaborate mechanism that never completes.

⭐⭐ THE TEST THAT PROVES IT — ⭐⭐ AND "WE HANDLE SIGTERM" IS
⭐   WORTHLESS WITHOUT IT:
⭐   ⭐ Start a request that takes 10 seconds.
⭐   ⭐ `docker kill --signal=TERM <id>` one second in.
⭐   ⭐ ⭐⭐ ASSERT THE REQUEST RETURNS 200 AND THE CONTAINER
⭐     EXITS 0 AFTERWARDS.
⭐   ⇒ ⭐ Exit 143 = SIGTERM handled. ⭐⭐ EXIT 137 = YOU WERE
⭐     KILLED, AND THE CHAIN IS BROKEN SOMEWHERE.
⭐   ⇒ ⭐⭐ PUT THIS IN CI. ⭐ It is fifteen lines and it protects
⭐     a property that silently regresses whenever someone edits
⭐     the Dockerfile.

⭐⭐ AND THE ONE PEOPLE FORGET: ⭐⭐ BACKGROUND WORKERS NEED THE
⭐   SAME TREATMENT. ⭐ A Celery worker killed mid-task with
⭐   `acks_late` will redeliver — ⭐ which is fine ***if*** the
⭐   task is idempotent (Day 335), ⭐⭐ AND IS DATA CORRUPTION IF
⭐   IT IS NOT.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Claiming improvements without a baseline | You cannot say anything specific, which is the only thing worth saying |
| ⭐ Measuring throughput on a laptop's 12 cores | Fiction. Measure under production resource limits |
| ⭐⭐ `2 × CPU + 1` workers with async workers | That's the sync recipe. You're spending memory for concurrency the loop already provides |
| ⭐⭐ Worker count that ignores the memory limit | At 150 MB/worker in 512 MB, three is your ceiling regardless of CPU math |
| ⭐ `max_requests` without jitter | All workers recycle at the same moment |
| ⭐⭐ `preload_app = True` with connections created at import | Every worker inherits the same socket and you get corruption that looks random |
| ⭐⭐ Migrations in the entrypoint | Three replicas race, two fail their probe, and rollback migrates *down* |
| ⭐ Forgetting Alembic's `env.py` imports your settings | The migration job fails with a config error that looks nothing like a database problem |
| ⭐⭐ "We handle SIGTERM" with no test | It silently regresses the next time someone edits the Dockerfile |
| ⭐ Grace period shorter than drain + p99 + cleanup | You're SIGKILLed mid-request and the whole mechanism never completes |
| ⭐ Importing `pandas` to parse one CSV | 1.5 s of startup and ~150 MB per worker for something `csv` does |
| ⭐ Ignoring background workers in the shutdown story | A non-idempotent task killed mid-flight is corruption, not a redelivery |
| ⭐⭐ A results table with no unchanged rows | Suspicious. The honest number is the credible one |

## Interview questions

**1. "Walk me through containerising a Python service."**
> ⭐⭐ I'd start by measuring, because otherwise I can't claim anything: **image size, cold build, warm
> build after a one-line change, cold start to ready, idle and loaded RSS, throughput, and graceful
> shutdown time.** ⭐ Then multi-stage with a venv as the transfer artefact, dependencies before source
> for the cache, `compileall` at build time, a numeric non-root user, exec-form `CMD`. ⭐ Then re-measure
> and write both columns down. ⭐⭐ On my service that was **1.1 GB to 190 MB, a three-and-a-half minute
> warm build to fourteen seconds, and fourteen-second cold start to two.**

**2. "How many gunicorn workers?"**
> ⭐ Compute from the CPU **quota**, not `os.cpu_count()` — ⭐⭐ and note that **`2 × CPU + 1` is the
> sync-worker recipe and it's wrong for async workers**, where each already handles many concurrent
> requests on one core. ⭐⭐ Then cap by memory: **at 150 MB per worker with a 512 MB limit, three is the
> ceiling no matter what the CPU maths says.** ⭐ Then verify by measurement, and make it an env var so
> it's explicit rather than a detection contest.

**3. "Where do migrations run?"**
> ⭐⭐ Not in the entrypoint. **Three replicas starting means three concurrent migrations — Alembic's
> lock saves correctness, but two replicas then wait, fail their startup probe and get restarted**, so
> you get a restart loop that resolves itself and terrifies everyone. ⭐⭐ And on rollback, **the old
> image's entrypoint migrates *down*, which is how you lose data during an incident.** ⭐ So: a separate
> one-shot job using the same image with a different command, before the rollout — which only works
> because migrations are expand/contract and compatible with the code still running.

**4. "How do you know graceful shutdown works?"**
> ⭐⭐ There's a CI test, because "we handle SIGTERM" without one is worthless — **it silently regresses
> the next time someone edits the Dockerfile.** ⭐ Start a ten-second request, send SIGTERM one second
> in, assert the request returns 200 and the container exits 0. ⭐ Exit 143 means handled; ⭐⭐ **exit 137
> means you were killed and the chain is broken somewhere** — usually shell-form `CMD`, or a grace
> period shorter than the drain sleep plus p99 plus cleanup.

**5. "Why is your cold start 14 seconds?"**
> ⭐ Almost always imports. ⭐⭐ `python -X importtime` sorted by cost usually shows one or two
> dependencies dominating — **`pandas` is about a second and a half, `boto3` nearly one.** ⭐ Fixes in
> order: `compileall` at build time, which is free and mandatory with a read-only filesystem;
> lazy-import heavy rarely-used libraries inside the function that needs them; don't connect to
> anything at import time; and question dependencies — ⭐⭐ **importing pandas to parse one CSV costs a
> second and a half of startup and 150 MB per worker for something the stdlib does.**

**6. "Would you use `preload_app`?"**
> ⭐ Only after verifying a precondition. ⭐ It imports once in the master then forks, so startup is
> faster and memory is initially shared — ⭐⭐ though **the sharing erodes, because CPython's refcounts
> dirty the shared pages.** ⭐⭐ The real danger is correctness: **anything stateful created before the
> fork — a database connection, an HTTP client, an event loop — is inherited by every worker and
> corrupts in ways that look like random production failures.** ⭐ So it's a performance optimisation
> with a correctness precondition, and off by default.

## 🎙️ Articulation drill

**Two minutes.** Lead with the discipline, because it's what makes the rest credible: **measure seven
things before you change anything — image size, cold and warm build, cold start to ready, idle and
loaded memory, throughput, and graceful shutdown — three runs, median, under production resource
limits, or the throughput number is fiction.** Then the changes and what each buys: multi-stage with a
venv as the transfer artefact removes the toolchain; dependencies before source turns a three-minute
warm build into fifteen seconds; **`compileall` at build time plus lazy-importing your two most
expensive libraries is usually most of the cold-start win** — and you find those with `python -X
importtime`, not by guessing. On workers: compute from the CPU quota rather than `cpu_count`, **cap by
memory, because at a hundred and fifty megabytes a worker in a five-hundred-megabyte limit, three is
the ceiling regardless of CPU maths**, and make it an env var. Then the two operational points. **Migrations
never in the entrypoint** — three replicas race, two fail their probes and restart, and on rollback the
old image migrates *down*. And **graceful shutdown needs a CI test**, because "we handle SIGTERM"
silently regresses the moment someone edits the Dockerfile: ten-second request, SIGTERM at one second,
assert 200 and exit 0. Close by saying the table out loud, **including a row that didn't improve** —
"throughput was unchanged because the bottleneck was the database" is a stronger claim than a uniform
list of wins.
