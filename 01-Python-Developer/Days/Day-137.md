# Day 137

**L-137** · **Async SQLAlchemy** — the greenlet bridge, and ⭐⭐ why lazy loading stops working entirely

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: async SQLAlchemy is the same library with an awaitable façade, and the
> one behavioural difference that matters is that lazy loading no longer works — because a lazy load is
> implicit I/O, and implicit I/O cannot be awaited.**
>
> ⭐ Day 134 said to migrate the driver before the routes. **This is that driver**, and it turns
> Day 136's advice from good practice into a hard requirement.

---

# Part 1 — ⭐ The setup

```python
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession

engine = create_async_engine(
    "postgresql+asyncpg://user:pass@host/db",        # ⭐⭐ the DRIVER changes, not the URL scheme
    pool_size=10, max_overflow=5, pool_pre_ping=True,
)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)   # ⭐ Day 135

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with SessionLocal() as session:                           # ⭐ Day 132
        yield session
```

```python
async def list_orders(db: AsyncSession, user_id: int) -> list[Order]:
    stmt = select(Order).where(Order.user_id == user_id).options(selectinload(Order.items))
    result = await db.scalars(stmt)                  # ⭐⭐ `await` — the only visible change
    return result.all()                               # ⭐ `.all()` is NOT awaited
```

```
⭐⭐ WHAT CHANGES, AND IT IS LESS THAN PEOPLE EXPECT:
⭐   · ⭐ `create_async_engine`, `AsyncSession`, `async_sessionmaker`
⭐   · ⭐ `await db.execute(...)` / `await db.scalars(...)` / `await db.get(...)`
⭐   · ⭐ `await db.commit()`, `await db.flush()`, `await db.refresh(obj)`
⭐   · ⭐⭐ THE QUERY LANGUAGE IS IDENTICAL. `select()`, `where`, `join`,
⭐        `options` — all unchanged. ⭐ That is deliberate: 2.0's unified API
⭐        exists precisely so sync and async share one query syntax.
⭐   ⇒ ⭐ `asyncpg` for Postgres, `aiomysql`/`asyncmy` for MySQL, `aiosqlite`
⭐        for SQLite. ⭐⭐ `psycopg` (v3) speaks both, which makes it the easiest
⭐        migration path.
```

# Part 2 — ⭐⭐ The greenlet bridge

```
⭐⭐ SQLALCHEMY'S CORE IS SYNCHRONOUS AND ALWAYS HAS BEEN. THE ASYNC API IS NOT A
⭐   REWRITE — IT IS A BRIDGE BUILT ON `greenlet`.
⭐
⭐   ⭐ your `await db.execute(...)`
⭐        ↓ ⭐⭐ runs the SYNCHRONOUS SQLAlchemy machinery inside a greenlet
⭐        ↓ when that machinery needs the network, the greenlet SUSPENDS
⭐        ↓ ⭐ control returns to the event loop, which awaits the real I/O
⭐        ↓ the result comes back; the greenlet RESUMES exactly where it stopped
⭐
⭐   ⇒ ⭐⭐ SO THE ORM'S UNIT OF WORK, IDENTITY MAP AND FLUSH LOGIC ARE THE SAME
⭐        CODE — ⭐ which is why behaviour matches sync so closely, and why the
⭐        migration is mostly mechanical.
⭐   ⇒ ⭐⭐ AND IT EXPLAINS THE ONE RULE: THE BRIDGE ONLY WORKS AT POINTS YOU
⭐        `await`. ⭐ Attribute access is not one of those points, so any I/O
⭐        triggered by an attribute has no way to suspend — and that is Part 3.
⭐   ⇒ ⭐ it also explains `greenlet_spawn has not been called` — ⭐⭐ the error
⭐        you get when SQLAlchemy needs to do I/O outside the bridge. Its
⭐        meaning is always the same: **something tried to lazy-load.**
```

# Part 3 — ⭐⭐ Lazy loading is gone

```python
orders = (await db.scalars(select(Order))).all()
for order in orders:
    print(order.user.email)          # ⚠️⚠️ MissingGreenlet / greenlet_spawn error
```

```
⭐⭐ IN SYNC SQLALCHEMY THAT WAS AN N+1 (Day 136) — SLOW BUT WORKING. ⭐⭐ IN
⭐   ASYNC IT IS AN **EXCEPTION**, because there is no way to await inside an
⭐   attribute access.
⭐   ⇒ ⭐⭐ WHICH IS, HONESTLY, AN IMPROVEMENT: the async version turns a silent
⭐        performance bug into a loud failure. ⭐ It is `lazy="raise"` (Day 136)
⭐        enforced by physics rather than by configuration.
⭐   ⇒ ⭐⭐ THEREFORE: **EVERY RELATIONSHIP YOU INTEND TO USE MUST BE EAGERLY
⭐        LOADED AT QUERY TIME.** `selectinload` for collections, `joinedload`
⭐        for to-one (Day 136's rule, now mandatory).
⭐   ⇒ ⭐ the escape hatch: `await db.refresh(obj, ["items"])`, or
⭐        `await obj.awaitable_attrs.items` — ⭐⭐ both are per-object, so using
⭐        them in a loop is the N+1 you were trying to avoid. ⭐ They are for
⭐        one-off cases, not for lists.
```

```
⚠️⚠️ ⭐⭐ THE OTHER PLACE THIS BITES, AND IT IS THE ONE PEOPLE DEBUG FOR HOURS:
⭐    **SERIALISATION**. A Pydantic `response_model` with a nested `items: list[ItemOut]`
⭐    touches `order.items` DURING SERIALISATION — ⭐ which happens AFTER your
⭐    repository returned, outside any await point you control.
⭐    ⇒ ⭐⭐ SO THE ERROR APPEARS IN THE FRAMEWORK, WITH A TRACEBACK THROUGH
⭐         PYDANTIC, AND NOTHING POINTS AT THE QUERY THAT FORGOT `selectinload`.
⭐    ⇒ ⭐⭐ THE FIX IS THE STRUCTURAL ONE FROM DAY 135: DO NOT RETURN ORM
⭐         OBJECTS. Convert to a Pydantic model INSIDE the repository, while the
⭐         session is alive and you know what was loaded. ⭐ Then serialisation
⭐         cannot touch the database, by construction.
⭐    ⇒ ⭐ and `expire_on_commit=False` is not optional here (Day 135) — with it
⭐         on, every attribute after commit is a lazy load, so every response is
⭐         this error.
```

# Part 4 — ⭐ Concurrency, and what a session is not

```python
# ⚠️⚠️ ⭐⭐ WRONG — one session, used concurrently:
async def get_dashboard(db: AsyncSession, user_id: int):
    orders, invoices = await asyncio.gather(          # ⭐ Day 071
        repo.list_orders(db, user_id),
        repo.list_invoices(db, user_id),              # ⚠️⚠️ SAME SESSION
    )
```

```
⭐⭐ AN `AsyncSession` IS **NOT** CONCURRENCY-SAFE. It holds one connection and
⭐   one transaction, and two coroutines using it at once interleave statements
⭐   on the same connection.
⭐   ⇒ ⭐ SQLAlchemy detects the common cases and raises
⭐        `InvalidRequestError: This session is provisioning a new connection…`
⭐        — ⭐⭐ but do not rely on the detection; the guarantee is the rule, not
⭐        the error.
⭐   ⇒ ⭐⭐ IT IS DAY 067'S SHARED-MUTABLE-STATE RACE, with a database connection
⭐        as the shared object.
⭐
⭐ ⭐ THE FIXES, IN ORDER OF PREFERENCE:
⭐   1. ⭐⭐ DO NOT GATHER — run them sequentially. ⭐ Two 5 ms queries is 10 ms;
⭐        that is almost never the bottleneck, and Day 070 warns against
⭐        reaching for concurrency reflexively.
⭐   2. ⭐ ONE QUERY instead of two, if they are related (a join, or a single
⭐        `IN`).
⭐   3. ⭐⭐ A SESSION PER TASK if you genuinely need parallel queries:
⭐        `async with SessionLocal() as s: ...` inside each coroutine —
⭐        ⭐ and accept that they are then separate transactions, so they do not
⭐        see each other's uncommitted work.
```

⚠️ ⭐⭐ **`AsyncSession` is also not usable across tasks or after the request ends** — ⭐ so a
`BackgroundTasks` job (Day 130) or an `asyncio.create_task` (Day 071) that captures the request's
session is using something about to be closed. **Open a new session inside the task.**

# Part 5 — ⭐ Migrating, and testing

```
⭐⭐ THE ORDER FROM DAY 134, MADE CONCRETE — DRIVER FIRST, ROUTES LAST:
⭐  1. ⭐ ADD ASYNC ALONGSIDE. Both engines can coexist against one database.
⭐  2. ⭐⭐ FIX EVERY LAZY LOAD **FIRST**, while still synchronous: set
⭐       `lazy="raise"` (Day 136) and make the sync suite pass. ⭐⭐ That is the
⭐       whole migration, done in the environment where failures are cheap.
⭐  3. ⭐ CONVERT THE REPOSITORY LAYER — `await`, and return Pydantic models.
⭐  4. ⭐ CONVERT SERVICES, then routes to `async def`.
⭐  5. ⭐ delete the sync engine.
⭐  ⇒ ⭐⭐ DOING IT IN THE OTHER ORDER — ROUTES FIRST — GIVES YOU `async def`
⭐       ROUTES CALLING A SYNC DRIVER, WHICH IS DAY 134'S 50× REGRESSION ON
⭐       EVERY ENDPOINT. ⭐ The order is not a preference.
```

```python
# ⭐ TESTING (Days 097, 132)
@pytest_asyncio.fixture
async def db_session(async_engine):
    conn = await async_engine.connect()
    trans = await conn.begin()
    session = AsyncSession(bind=conn, join_transaction_mode="create_savepoint")
    yield session
    await session.close()
    await trans.rollback()                      # ⭐⭐ everything the test did is undone
    await conn.close()
```

```
⭐⭐ THE SAME TRANSACTION-ROLLBACK PATTERN AS DAY 097, WITH TWO ASYNC-SPECIFIC
⭐   TRAPS:
⭐   · ⭐⭐ EVENT-LOOP SCOPE. A session-scoped async fixture on a function-scoped
⭐        loop gives *"attached to a different loop"* (Day 097). ⭐ Match the
⭐        scopes, or use `anyio`/`asyncio_mode = "auto"` and one loop.
⭐   · ⭐ THE ENGINE MUST BE DISPOSED, or the suite hangs at exit holding
⭐        connections.
⭐   ⇒ ⭐⭐ AND THE TEST THAT MATTERS MOST HERE: THE QUERY-COUNT ASSERTION FROM
⭐        DAY 136. ⭐ In async, a missing `selectinload` is an exception rather
⭐        than a slow response — ⭐⭐ so your tests catch it, which is the one
⭐        genuine ergonomic win of the async ORM.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Expecting lazy loading to work** | ⭐⭐ It cannot — attribute access has no await point. Eager-load everything. |
| Misreading `greenlet_spawn has not been called` | ⭐ It always means: something tried to lazy-load. |
| ⭐⭐ **A nested `response_model` without `selectinload`** | ⭐⭐ Fails during serialisation, with a traceback through Pydantic. |
| ⭐ Returning ORM objects from the repository | ⭐⭐ Convert to Pydantic inside, while the session is alive. |
| `expire_on_commit=True` | ⭐ Every post-commit attribute is a lazy load ⇒ every response errors. |
| ⭐⭐ **`gather` over one session** | ⭐⭐ Not concurrency-safe. Sequential, one query, or a session per task. |
| Using the request's session in a background task | ⭐ It is about to close. Open a new one. |
| ⭐⭐ **Converting routes before the driver** | ⭐⭐ Async routes over a sync driver — Day 134's 50× regression. |
| Session-scoped async fixture, function-scoped loop | ⭐ "Attached to a different loop". |
| ⭐ `awaitable_attrs` in a loop | ⭐ That is the N+1 you were avoiding. |
| Not disposing the engine in tests | ⭐ The suite hangs at exit. |

## Interview questions

**Q: How does async SQLAlchemy work?**
> It's the same synchronous library with an awaitable façade built on greenlets. Your `await
> db.execute()` runs the ordinary SQLAlchemy machinery inside a greenlet; when that machinery needs
> the network the greenlet suspends, control returns to the event loop, the real I/O is awaited, and
> the greenlet resumes exactly where it stopped. So the unit of work, identity map and flush logic are
> the same code, which is why behaviour matches sync so closely and the migration is mostly mechanical.
> It also explains the one rule: the bridge only works at points you `await`.

**Q: What's the one behavioural difference that matters?**
> Lazy loading doesn't work. Accessing `order.user` on an unloaded relationship raises rather than
> issuing a query, because attribute access has no await point — implicit I/O can't be suspended. So
> every relationship you intend to use has to be eagerly loaded at query time. And I'd argue that's an
> improvement: in sync SQLAlchemy the same code is an N+1, slow but working, and in async it's a loud
> failure. It's `lazy="raise"` enforced by physics rather than configuration.

**Q: Where does that bite hardest?**
> Serialisation. A Pydantic response model with a nested list touches the relationship *during*
> serialisation, which happens after your repository returned and outside any await point you control
> — so the error surfaces in the framework with a traceback through Pydantic, and nothing points at
> the query that forgot `selectinload`. The structural fix is not to return ORM objects at all:
> convert to a Pydantic model inside the repository while the session is alive and you know what was
> loaded. Then serialisation can't touch the database by construction. And `expire_on_commit=False`
> stops being optional, because otherwise every attribute after commit is a lazy load.

**Q: Can you run two queries concurrently on one session?**
> No — an `AsyncSession` holds one connection and one transaction, so two coroutines using it
> interleave statements on the same connection. SQLAlchemy detects the common cases and raises, but
> the rule is the guarantee, not the error. It's the shared-mutable-state race with a database
> connection as the shared object. My first answer is usually not to gather at all — two five-
> millisecond queries is ten milliseconds and almost never the bottleneck — or to combine them into
> one query. If I genuinely need parallelism, a session per task, accepting that they're then separate
> transactions.

**Q: How would you migrate a sync codebase to async?**
> Driver first, routes last, and the order isn't a preference. The most valuable step is second: set
> `lazy="raise"` and fix every lazy load *while still synchronous*, so the failures happen in an
> environment where they're cheap. That's effectively the whole migration. Then convert the repository
> layer to `await` and have it return Pydantic models, then services, then routes. Doing it the other
> way round gives you async routes over a synchronous driver, which is a fifty-times regression on
> every endpoint with no error message.

## 🎙️ Articulation drill

Record two minutes: **"What changes when you move SQLAlchemy to async?"**
