# Part 1 — ⭐⭐ Process vs thread

⭐ Day 003 gave you the process: an address space the hardware isolates. **A thread is a scheduling
unit *inside* one.**

```
⭐⭐ ONE PROCESS, THREE THREADS:

  ┌──────────────── PROCESS (one address space) ────────────────┐
  │  ⭐⭐ SHARED:  heap · globals · module objects · file        │
  │              descriptors · loaded code · open sockets        │
  │  ┌─────────┐  ┌─────────┐  ┌─────────┐                       │
  │  │ THREAD 1│  │ THREAD 2│  │ THREAD 3│                       │
  │  │ ⭐ stack │  │ stack   │  │ stack   │  ⭐ PER-THREAD:        │
  │  │ regs    │  │ regs    │  │ regs    │  stack, registers,     │
  │  │ PC      │  │ PC      │  │ PC      │  program counter,      │
  │  └─────────┘  └─────────┘  └─────────┘  thread-local storage  │
  └──────────────────────────────────────────────────────────────┘
```

| | ⭐ Process | ⭐ Thread |
|---|---|---|
| ⭐⭐ Memory | ⭐⭐ **isolated** — hardware-enforced | ⭐⭐ **shared** — no protection at all |
| Creation cost | high (~ms) | ⭐ low (~µs) |
| Context switch | expensive — ⭐ TLB flush, cold cache | ⭐ cheaper — same address space |
| Communication | ⭐ pipes, sockets, shared memory (⭐⭐ serialise) | ⭐⭐ just read the variable |
| ⭐ A crash | kills one process | ⭐⭐ **kills the whole process** |
| ⭐⭐ Races | impossible by construction | ⭐⭐ **the default** |

```
⭐⭐ THE TRADE, IN ONE LINE: threads are cheap and dangerous; processes are expensive and safe.
⭐   ⇒ ⭐ shared memory is the *feature* of threads and the *entire* source of their bugs.
```

⭐ **A thread's 8 MB stack is virtual, not resident** — it is reserved address space, and only the
pages you touch become real memory. **So "10,000 threads = 80 GB" is wrong; the real limits are
scheduler overhead and kernel structures.** ⚠️ **But thousands of threads is still the wrong design,
and Day 070 explains what to do instead.**

# Part 2 — ⭐⭐ Preemptive scheduling — why races exist

```
⭐⭐ THE OS SCHEDULER CAN SUSPEND A THREAD AT ALMOST ANY MACHINE INSTRUCTION:
⭐   · its time slice expired (a timer interrupt — typically every few milliseconds)
⭐   · it blocked on I/O
⭐   · a higher-priority thread became runnable
⭐   · it called a blocking syscall
⭐
⭐ ⇒ ⭐⭐ YOU DO NOT CONTROL WHERE THE SWITCH HAPPENS. That single fact is why a race
⭐      condition is possible at all (Day 067), and why "it works on my machine" is
⭐      meaningless for concurrent code — the interleaving differs every run.
```

```
⭐⭐ THE CONTRAST THAT DEFINES THE WHOLE BLOCK:

⭐   PREEMPTIVE (threads)   ⇒ the OS switches whenever it likes
⭐                          ⇒ ⭐⭐ you must LOCK anything shared
⭐   COOPERATIVE (asyncio)  ⇒ ⭐⭐ switches happen ONLY at `await`
⭐                          ⇒ ⭐⭐ between two awaits, your code is ATOMIC — no lock needed
⭐                          ⇒ ⚠️ ⭐⭐ and if you never await, NOTHING else ever runs (Day 072)
```

⭐⭐ **That contrast is worth memorising as a pair**, because it explains both models' greatest
strength and greatest weakness in one sentence each. **Cooperative scheduling trades "races
everywhere" for "one bad citizen stops everything".**

⭐ **A blocked thread costs no CPU.** When a thread waits on a socket the kernel moves it to a wait
queue and schedules something else — it is not spinning. **What it costs is the thread itself: the
stack, the kernel structure, and a slot in the scheduler.**

# Part 3 — ⭐⭐ CPU-bound vs I/O-bound

```
⭐⭐ THE TAXONOMY THAT DECIDES YOUR ENTIRE DESIGN. Measure this before choosing anything.

⭐ ⭐⭐ I/O-BOUND — the program is WAITING: network, disk, database, another service.
⭐    CPU usage is low; wall-clock time is dominated by round trips.
⭐    ⇒ ⭐⭐ you do not need more CPUs. You need to STOP BLOCKING while you wait.
⭐    ⇒ ⭐ threads work. ⭐⭐ asyncio works better and far more cheaply.
⭐
⭐ ⭐⭐ CPU-BOUND — the program is COMPUTING: parsing, maths, compression, image work.
⭐    One core is pinned at 100%.
⭐    ⇒ ⭐⭐ you need actual PARALLELISM ⇒ ⭐⭐ PROCESSES (Day 068), because of the GIL.
⭐    ⇒ ⭐ or move the loop out of Python entirely — NumPy, a C extension (Day 028).
```

```python
# ⭐⭐ HOW TO TELL, in ten seconds, without guessing:
import time
t0 = time.perf_counter(); c0 = time.process_time()
work()
wall = time.perf_counter() - t0        # ⭐ total elapsed
cpu  = time.process_time() - c0        # ⭐⭐ CPU actually consumed

# ⭐⭐ cpu / wall ≈ 1.0  ⇒ CPU-BOUND — it was computing the whole time
# ⭐⭐ cpu / wall ≈ 0.05 ⇒ I/O-BOUND — it spent 95% of the time waiting
```

⭐⭐ **That five-line measurement is the most useful thing on this page.** ⚠️ **Almost every wrong
concurrency decision starts with guessing this** — reaching for `multiprocessing` on an I/O-bound
workload adds serialisation cost and process overhead to something that was only ever waiting.

⭐ **A third category exists and gets missed: memory-bound** — the CPU is busy but stalled on cache
misses (Day 001). **More cores do not help; a better data layout does.**

# Part 4 — ⭐ The decision table, and what limits you

| ⭐ Workload | ⭐⭐ Use | ⭐ Why |
|---|---|---|
| ⭐⭐ Many network calls | ⭐⭐ **`asyncio`** | thousands of waits, one thread (Day 070) |
| A few blocking calls, sync library | ⭐ `ThreadPoolExecutor` | the GIL is released during I/O (Day 065) |
| ⭐⭐ Heavy computation | ⭐⭐ **`ProcessPoolExecutor`** | real cores (Day 068) |
| Numeric arrays | ⭐ NumPy | the loop leaves Python entirely |
| Mixed | ⭐ processes **containing** an event loop | ⭐⭐ this is `gunicorn -w 4 -k uvicorn` (Day 021) |

```
⭐⭐ AMDAHL'S LAW, IN THE ONLY FORM YOU NEED:
⭐   if 10% of the work is inherently SERIAL, then ⭐⭐ infinite cores gives you at most 10× —
⭐   never more. ⇒ ⭐ the serial fraction, not the core count, is your ceiling.
⭐   ⇒ ⭐⭐ so profile before parallelising: speeding up something that is 5% of runtime
⭐        cannot give you more than 5%, no matter how well you do it.
```

⭐ **Know your machine:** `os.cpu_count()` reports logical cores (hyperthreading inflates it —
⭐⭐ **two hyperthreads share one execution unit, so they help I/O-ish workloads and roughly nothing
for pure compute**). ⚠️ **In a container, `os.cpu_count()` reports the *host's* cores, not your CPU
limit** — which is why a pod with a 1-core limit happily starts 16 workers and thrashes. **Use
`os.process_cpu_count()` (3.13+) or read the cgroup quota.**

⭐⭐ **The shape you will actually deploy** (Day 021, restated now that you know why): **processes for
CPU parallelism because the GIL blocks threads, and an event loop inside each process for I/O
concurrency because waiting needs no CPU.** They solve different problems and compose.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Guessing CPU-bound vs I/O-bound** | ⭐⭐ Measure `process_time / perf_counter`. |
| Using processes for I/O | ⭐ Pure overhead — it was only waiting. |
| Using threads for computation | ⭐⭐ The GIL means no parallelism (Day 065). |
| Confusing concurrency and parallelism | ⭐ Structure vs execution. |
| Assuming a blocked thread burns CPU | ⭐ It is in a kernel wait queue. |
| ⭐ "8 MB per thread" | ⭐ Virtual reservation; only touched pages are resident. |
| Thousands of threads | ⭐⭐ Scheduler overhead. Use an event loop. |
| ⭐ `os.cpu_count()` in a container | ⭐⭐ Reports host cores, not your quota. |
| Parallelising before profiling | ⭐ Amdahl: the serial fraction is the ceiling. |
| Expecting hyperthreads to double compute | ⭐ They share execution units. |

## Interview questions

**Q: Concurrency or parallelism?**
> Concurrency is a structural property — the program is dealing with several things at once, and they
> may interleave on one core. Parallelism is an execution property — several things genuinely running
> simultaneously on different cores. Python gives excellent concurrency and, because of the GIL, no
> thread parallelism, which is why the language's answer splits: threads or asyncio for waiting,
> processes for computing.

**Q: What's shared between threads and what isn't?**
> Everything in the address space is shared — the heap, globals, module objects, file descriptors,
> open sockets. Each thread has its own stack, registers and program counter, plus thread-local
> storage if you ask for it. That sharing is the whole point of threads and the entire source of their
> bugs: there's no hardware protection between them, so two threads touching the same object is the
> default rather than the exception.

**Q: Why do race conditions exist at all?**
> Because scheduling is preemptive — the OS can suspend a thread at almost any machine instruction,
> on a timer interrupt, and you don't control where. So the interleaving differs every run, which is
> also why "it works on my machine" means nothing for concurrent code. The contrast is asyncio, which
> is cooperative: switches happen only at an `await`, so code between two awaits is atomic and needs
> no lock. That trades "races everywhere" for "one bad citizen stops everything".

**Q: How do you decide which concurrency model to use?**
> By measuring, not guessing. `time.process_time()` divided by `time.perf_counter()` over the workload
> gives the CPU-to-wall ratio: near 1 means CPU-bound, so I need real parallelism and therefore
> processes; near zero means it spent its time waiting, so I need to stop blocking — asyncio, or
> threads if the library is synchronous. Almost every wrong concurrency decision I've seen started
> with someone assuming which one it was, and reaching for `multiprocessing` on a workload that was
> only ever waiting on a network.

**Q: What does a blocked thread cost?**
> No CPU — the kernel moves it to a wait queue and runs something else. What it costs is the thread:
> a stack, a kernel structure and a scheduler slot. That's why threads scale to hundreds and not to
> tens of thousands, and why an event loop wins for high-concurrency I/O: ten thousand waiting
> connections are ten thousand file descriptors and one thread, rather than ten thousand threads.

**Q: Anything to watch with `os.cpu_count()`?**
> Two things. It counts logical cores, so hyperthreading inflates it — two hyperthreads share
> execution units, so they help interleaved or memory-stalled work and give roughly nothing for pure
> compute. And in a container it reports the *host's* cores rather than the cgroup limit, so a pod
> capped at one CPU will cheerfully start sixteen workers and thrash. `os.process_cpu_count()` in 3.13
> respects the affinity mask, or you read the cgroup quota directly.

## 🎙️ Articulation drill

Record two minutes: **"A job takes 40 minutes. How do you make it faster?"**

⭐ Refuse to answer until you have measured, and say what you would measure: **the ratio of
`process_time` to `perf_counter`.** Near 1 means it computed for 40 minutes; near zero means it waited
for 38 of them. **These want opposite solutions, and guessing wrong makes it slower.**

⭐ If I/O-bound: **the fix is to stop blocking, not to add CPUs** — asyncio if the libraries support
it, a thread pool if they are synchronous. If CPU-bound: **processes, because the GIL means threads
give no parallelism** — or better, move the loop out of Python into NumPy or a C extension, which
often beats parallelising it.

⭐⭐ **Then the discipline that comes before either:** *"and I'd profile first, because Amdahl's law
says the serial fraction is the ceiling — if the part I can parallelise is 30% of the runtime, perfect
parallelism gets me 30% and no more. The most common outcome of profiling a slow job is that it was
one unindexed query or one N+1, and no amount of concurrency would have helped."*
