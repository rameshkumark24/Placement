**L-156** · **Load testing and capacity** — ⭐⭐ coordinated omission, the knee, and why your numbers are wrong

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: most load tests measure the *tool's* patience rather than the *server's*
> capacity — because a client that waits for a response before sending the next request cannot
> generate the load that breaks you, and it hides the exact latency you were trying to find.**

> three ways the measurement lies to you.

# Part 1 — ⭐⭐ Open vs closed: the distinction almost nobody makes

```
⭐⭐ CLOSED MODEL — N virtual users, each in a loop:
⭐        send → wait for response → think → send
⭐   ⇒ ⭐⭐ THE OFFERED LOAD IS A CONSEQUENCE OF YOUR SERVER'S SPEED.
⭐        ⭐ If the server slows down, the load generator AUTOMATICALLY SLOWS
⭐        DOWN TOO. ⭐⭐ You cannot overload it. The system self-regulates, and
⭐        that is precisely the property you did NOT want in a load test.
⭐   ⇒ ⭐ This is what `hey -c 50`, `ab -c`, and a default JMeter thread group
⭐        give you.
⭐
⭐⭐ OPEN MODEL — arrivals at a FIXED RATE, regardless of responses:
⭐        1,000 requests/sec arrive, whether or not the previous ones finished
⭐   ⇒ ⭐⭐ QUEUES BUILD. Concurrency RISES when the server slows. ⭐ This is
⭐        how real traffic behaves: your users do not wait for each other.
⭐   ⇒ ⭐ `k6` (`constant-arrival-rate`), `vegeta -rate=1000`, Locust with a
⭐        constant-throughput shape.
⭐
⭐   ⇒ ⭐⭐ WHY IT MATTERS, CONCRETELY: with 50 closed users, if p50 doubles
⭐        from 20 ms to 40 ms, your throughput HALVES and everything still
⭐        "looks fine" — ⭐ no queue, no errors, no saturation.
⭐        ⭐⭐ IN PRODUCTION, TRAFFIC DOES NOT HALVE WHEN YOU GET SLOWER. The
⭐        queue grows, latency compounds, and you fall over.
⭐   ⇒ ⭐⭐ SO: A CLOSED-MODEL TEST CANNOT REPRODUCE THE FAILURE MODE YOU CARE
⭐        ABOUT. Use it to find per-request cost; ⭐ use OPEN to find capacity.
```

# Part 2 — ⭐⭐ Coordinated omission: why your p99 is a fantasy

```
⭐⭐ THE MOST IMPORTANT MEASUREMENT BUG IN PERFORMANCE WORK, AND IT HAS A
⭐   NAME BECAUSE IT IS EVERYWHERE:

⭐   ⭐ your tool intends to send one request every 10 ms.
⭐   ⭐ request #500 hits a 2-SECOND GC pause / lock / failover.
⭐        ↓
⭐   ⭐⭐ A CLOSED-MODEL TOOL SIMPLY DOES NOT SEND THE 200 REQUESTS THAT
⭐        SHOULD HAVE ARRIVED DURING THOSE 2 SECONDS. It was blocked.
⭐        ↓
⭐   ⭐ it records: 1 slow request (2,000 ms), then resumes.
⭐   ⭐⭐ IT SHOULD HAVE RECORDED 200 REQUESTS WITH LATENCIES OF 2000, 1990,
⭐        1980 … 10 ms — because a real user who arrived at t+1s WAITED 1s.
⭐        ↓
⭐   ⇒ ⭐⭐ THE 199 WORST MEASUREMENTS WERE SILENTLY OMITTED. ⭐ Your p99 says
⭐        45 ms. ⭐⭐ THE REAL p99 IS OVER A SECOND. ⭐ Not slightly wrong —
⭐        wrong by an order of magnitude, and wrong in the direction that
⭐        makes you confident.

⭐⭐ THE FIXES:
⭐   ⭐ USE AN OPEN-MODEL TOOL. Arrivals are scheduled independently, so a
⭐        stall produces exactly the queue of late requests real users produce.
⭐   ⭐⭐ MEASURE LATENCY FROM *INTENDED* SEND TIME, not actual send time.
⭐        ⭐ `wrk2`, `k6` and `vegeta` do this; `ab` and `hey` do not.
⭐   ⭐ ⭐⭐ AND CROSS-CHECK AGAINST YOUR SERVER-SIDE HISTOGRAM (Day 147) —
⭐        ⭐ but note the server's histogram has its OWN blind spot: it does
⭐        not include time spent queued in the kernel accept backlog before
⭐        your process saw the request. ⭐⭐ THE CLIENT'S NUMBER IS THE TRUTH;
⭐        the server's number tells you which part is yours.
```

# Part 3 — ⭐⭐ Finding the knee, and Little's Law

```
⭐⭐ DON'T ASK "CAN IT HANDLE 1,000 rps?" ASK "WHERE DOES IT BREAK, AND WHAT
⭐   BREAKS FIRST?" ⭐ RAMP THE ARRIVAL RATE AND PLOT THREE LINES:

⭐   throughput │        ┌────────────  ⭐⭐ FLAT: saturated
⭐   (completed)│      ╱                    ⭐ (or FALLING: thrashing)
⭐              │    ╱
⭐              │  ╱
⭐              └────────────────────  offered load →
⭐                        ▲
⭐   latency    │         │        ╱⭐⭐ HOCKEY STICK
⭐              │         │      ╱
⭐              │─────────┴────╱
⭐              └────────────────────
⭐                      ⭐⭐ THE KNEE
⭐
⭐   ⇒ ⭐⭐ THE KNEE IS YOUR CAPACITY. Past it, throughput stops rising and
⭐        ONLY LATENCY GROWS — ⭐ you are converting extra load purely into
⭐        queueing (Day 147's saturation).
⭐   ⇒ ⭐⭐ OPERATE AT ~50–70% OF THE KNEE. ⭐ Not 95%: you need headroom for
⭐        traffic spikes, for a node dying and shifting its load onto you, and
⭐        for the deploy that temporarily runs at reduced capacity.
⭐   ⇒ ⭐⭐ AND IF THROUGHPUT *FALLS* PAST THE KNEE, YOU HAVE A CONGESTION
⭐        COLLAPSE — context switching, lock contention, retries (Day 152), or
⭐        GC. ⭐ That is the shape that turns into an outage rather than
⭐        slowness, and it is why load shedding exists.
```

```
⭐⭐ LITTLE'S LAW — L = λ × W. Learn it; it is three variables and it answers
⭐   half of all capacity questions without a test:
⭐        ⭐ L = concurrent requests in the system
⭐        ⭐ λ = arrival rate (rps)
⭐        ⭐ W = average time in the system (seconds)
⭐
⭐   ⭐ "500 rps, 200 ms average" ⇒ L = 500 × 0.2 = ⭐⭐ 100 CONCURRENT
⭐     REQUESTS. ⭐ So you need ≥100 workers/connections — ⭐⭐ 40 threads
⭐     (Day 134) IS ALREADY THE BOTTLENECK, and you can know that before
⭐     running anything.
⭐   ⭐⭐ AND RUN IT BACKWARDS, WHICH IS THE MORE USEFUL DIRECTION:
⭐     "I have 4 workers × 8 threads = 32 slots, and my p50 is 50 ms"
⭐     ⇒ λ = 32 / 0.05 = ⭐⭐ 640 rps MAXIMUM. ⭐ No test needed; if you need
⭐     2,000 rps, no amount of tuning gets you there — ⭐⭐ you need more slots
⭐     or a faster handler, and the law tells you WHICH, and by how much.
```

# Part 4 — ⭐⭐ Making the test resemble reality

```
⭐⭐ FIVE WAYS A LOAD TEST FLATTERS YOU, EACH WORTH MORE THAN THE TOOL CHOICE:

⭐  1. ⭐⭐ ONE ENDPOINT AT A TIME. Real traffic is a MIX, and mixes contend
⭐       for the same pool, the same CPU, the same locks. ⭐ Model the real
⭐       distribution (from your access logs, Day 080's pipeline).
⭐  2. ⭐⭐ THE SAME USER / THE SAME ROW. ⭐ Everything hits ONE cache entry and
⭐       ONE database page ⇒ ⭐⭐ a 100% cache hit rate you will never see, and
⭐       no lock contention because there is nothing to contend WITH. ⭐ Or the
⭐       opposite: all writes to one row, which is 100% contention.
⭐       ⇒ ⭐ RANDOMISE OVER A REALISTIC KEY DISTRIBUTION — ⭐⭐ and real
⭐         distributions are Zipfian (a few very hot keys), not uniform.
⭐  3. ⭐⭐ AN EMPTY DATABASE. 1,000 rows: every query is an index-free seq
⭐       scan that is FAST. ⭐ 50 million rows: a different query plan
⭐       entirely. ⭐⭐ A load test on a small dataset tests a different program.
⭐  4. ⭐ COLD VS WARM. ⭐⭐ Discard the first 30–60 seconds: JIT-less Python
⭐       still has import costs, empty connection pools, empty caches, and
⭐       an unwarmed page cache. ⭐ Then run long enough to see the leak.
⭐  5. ⭐⭐ NO THINK TIME AND NO CONNECTION CHURN. Real clients open new TLS
⭐       connections, abandon requests, and pause. ⭐ A single reused keep-alive
⭐       connection skips handshakes that cost real CPU.
⭐
⭐ ⭐⭐ AND THE ONE THAT INVALIDATES EVERYTHING: DO NOT LOAD-TEST FROM YOUR
⭐   LAPTOP. ⭐ You will measure your home upload bandwidth, your NAT's
⭐   connection table, and your own CPU spent generating load. ⭐⭐ WATCH THE
⭐   GENERATOR'S OWN CPU — if it is above ~70%, YOU ARE MEASURING THE
⭐   GENERATOR. ⭐ That single check invalidates a surprising number of
⭐   published numbers.
```

# Part 5 — ⭐ Four kinds of test, and reading the result

```
⭐⭐ THEY ANSWER DIFFERENT QUESTIONS. RUN THE RIGHT ONE:
⭐   ⭐ SMOKE     — 1–5 users, 1 min. ⭐ "Does it work at all?" Runs in CI.
⭐   ⭐ LOAD      — expected peak, 10–30 min. ⭐ "Do we meet the SLO?"
⭐   ⭐⭐ STRESS   — ramp until it breaks. ⭐ "Where is the knee, and what
⭐        breaks first?" ⭐⭐ AND — the half people skip — "DOES IT RECOVER
⭐        WHEN THE LOAD STOPS?" ⭐ A system that stays down after the load
⭐        ends is metastable (Day 152), and that is the most valuable finding
⭐        a stress test can produce.
⭐   ⭐ SOAK      — moderate load, ⭐⭐ 4–24 HOURS. ⭐ "Do we leak?" ⭐⭐ THE ONLY
⭐        TEST THAT FINDS MEMORY LEAKS, connection leaks, unbounded caches,
⭐        disk fill, and file-descriptor exhaustion — ⭐ and it is the one
⭐        nobody runs.
⭐   ⭐ SPIKE     — 0 → peak in seconds. ⭐ "What does autoscaling do?"
⭐        ⭐⭐ Usually: it is too slow, and you need pre-provisioning.

⭐⭐ WHEN IT IS SLOW, DIAGNOSE IN THIS ORDER (Day 082's ladder, at fleet level):
⭐  1. ⭐⭐ IS THE GENERATOR THE BOTTLENECK? Check its CPU first, always.
⭐  2. ⭐ IS IT SATURATION OR SPEED? ⭐⭐ Rising queue/pool-wait with flat CPU
⭐       = you are BLOCKED, not busy. ⭐ Rising CPU = you are busy.
⭐  3. ⭐ WHICH RESOURCE? app CPU · DB CPU · pool exhaustion · event-loop lag
⭐       (Day 147) · network.
⭐  4. ⭐⭐ READ A TRACE (Day 148) at low load and at high load and COMPARE.
⭐       ⭐ The span that grew is the answer, and it is usually not the one
⭐       you expected.
⭐  5. ⭐ ONLY NOW profile the code (Day 100A).
⭐
⭐   ⇒ ⭐⭐ THE MOST COMMON REAL ANSWER, BY A LARGE MARGIN: THE DATABASE
⭐        CONNECTION POOL. ⭐ 4 workers × pool_size 5 = 20 connections total;
⭐        Little's Law says you needed 100. ⭐⭐ The application is idle, the
⭐        database is idle, and every request is waiting for a connection —
⭐        ⭐ which looks exactly like "the database is slow" in a trace, and
⭐        is not.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Closed-model tool for a capacity test | The generator slows down when the server does. You cannot overload it. |
| Trusting p99 from `ab`/`hey` | Coordinated omission — the worst measurements are the ones never taken. |
| Measuring from actual rather than intended send time | Same bug, stated precisely. |
| Only trusting the server-side histogram | It excludes time queued in the accept backlog. The client's number is the truth. |
| Asking "can it do 1,000 rps?" | Ask where the knee is and what breaks first. |
| Operating at 95% of the knee | No headroom for spikes, a lost node, or a reduced-capacity deploy. |
| Ignoring falling throughput past the knee | That's congestion collapse — an outage shape, not a slowness shape. |
| Testing one endpoint | Real mixes contend for the same pool, CPU and locks. |
| Same user, same row every request | 100% cache hit rate you'll never see, or 100% contention you don't have. |
| Uniform key distribution | Real access is Zipfian — a few very hot keys. |
| Load testing against a small dataset | Different query plans; you're testing a different program. |
| Including the cold first minute | Empty pools, empty caches, import costs. Discard the warm-up. |
| One reused keep-alive connection | Skips TLS handshakes that cost real CPU. |
| Load testing from a laptop | You measure your uplink and NAT table. |
| Not watching the generator's CPU | Above ~70% you're measuring the generator, not the server. |
| Never running a soak test | The only test that finds leaks — and the one nobody runs. |
| Stress test with no recovery phase | The most valuable finding is whether it recovers when load stops. |
| Profiling code before checking saturation | The usual answer is pool exhaustion, and no profiler will show it. |

## Interview questions

**Q: What's the difference between an open and a closed load model, and why does it matter?**

> In a closed model you have N virtual users each looping send-wait-think, so the offered load is a
> consequence of the server's speed — if the server slows down, the generator automatically slows
> down too, which means you literally cannot overload it. That's the self-regulating property you
> specifically don't want in a load test. In an open model, arrivals happen at a fixed rate
> regardless of whether previous requests completed, so queues build and concurrency rises when the
> server slows — which is how real traffic behaves, because users don't wait for each other. The
> concrete consequence: with fifty closed users, if p50 doubles then throughput just halves and
> everything looks calm — no queue, no errors. In production traffic doesn't halve when you get
> slower; the queue grows and you fall over. So a closed test can't reproduce the failure mode you
> care about.

**Q: What's coordinated omission?**

> The most important measurement bug in performance work. Suppose your tool intends to send a request
> every ten milliseconds, and one request hits a two-second stall — a GC pause, a lock, a failover. A
> closed-model tool was blocked, so it simply never sends the two hundred requests that should have
> arrived during those two seconds. It records one slow request and moves on. But a real user
> arriving one second into that stall waited one second, so the correct recording is two hundred
> requests at two thousand, one thousand nine hundred and ninety, and so on down. The hundred and
> ninety-nine worst measurements were silently omitted. Your p99 reads forty-five milliseconds and
> the true p99 is over a second — wrong by an order of magnitude, and wrong in the direction that
> makes you confident. The fix is an open-model tool that measures from *intended* send time: `wrk2`,
> `k6`, `vegeta` do; `ab` and `hey` don't.

**Q: You need 2,000 rps. How do you know if your service can do it without running a test?**

> Little's Law: concurrency equals arrival rate times time in the system. Run it backwards. If I have
> four workers with eight threads each, that's thirty-two concurrent slots, and if my p50 is fifty
> milliseconds then my ceiling is thirty-two divided by 0.05, which is six hundred and forty requests
> per second. So two thousand is not reachable by tuning — I need more slots or a faster handler, and
> the law tells me which and by how much. It's three variables and it answers most capacity questions
> before you've written a script. It's also how you catch the classic misconfiguration: five hundred
> rps at two hundred milliseconds needs a hundred concurrent slots, so a forty-thread pool is already
> the bottleneck.

**Q: Your load test looks great and production falls over at the same rate. What was wrong with the test?**

> Probably several things, and I'd check them in this order. Was the model closed — because then I
> never actually applied the load. Was I testing one endpoint, when real traffic is a mix contending
> for the same pool and locks. Was every request hitting the same user and the same row, which gives
> a hundred percent cache hit rate I'll never see in production, or the opposite, total lock
> contention on one row. Was the database small — a thousand rows means every query is a fast
> sequential scan and the planner makes completely different choices at fifty million. Did I include
> the cold first minute, or run long enough to see a leak. And the one that invalidates everything:
> was the generator's own CPU above seventy percent, in which case I measured the generator.

**Q: Latency rises under load but CPU is flat. What does that tell you?**

> That I'm blocked, not busy — which is a saturation problem rather than a speed problem, so
> profiling the code would waste an afternoon. Something is queueing: most commonly the database
> connection pool. Four workers with a pool size of five is twenty connections, and Little's Law may
> say I needed a hundred, so requests sit waiting for a connection while both the application and the
> database are idle. In a trace that looks exactly like "the database is slow" and isn't, which is
> why I instrument acquire time separately. The other candidates are event-loop lag from a blocking
> call, a semaphore, or a lock. The fast way to confirm is to compare a trace at low load with one at
> high load — the span that grew is the answer.

## Mini task

1. ⭐ Run the same test with `hey -c 50` and with `k6` at a constant arrival rate. Compare reported p99.
2. ⭐⭐ Add a deliberate 2-second stall every 500 requests. Compare p99 from both tools. That difference is coordinated omission.
3. ⭐⭐ Ramp arrival rate and plot throughput and latency together. Mark the knee. Compute 60% of it and write that number down as your capacity.
4. ⭐ Apply Little's Law to your current worker and pool config. Predict your ceiling, then measure it. Compare.
5. ⭐⭐ Run one test against 1,000 rows and one against 5 million. Compare p99 and `EXPLAIN` output for the same query.
6. ⭐⭐ Run the same load against a single user id, then against a Zipfian distribution. Compare cache hit rate and p99.
7. ⭐ Watch the generator's CPU during a test. Push until it exceeds 70% and note how the reported numbers change.
8. ⭐⭐ Run a 4-hour soak at 50% of the knee. Plot RSS and open file descriptors. Find something.
9. ⭐⭐ Stress past the knee, then drop the load to zero and watch whether it recovers on its own.

## 🎙️ Articulation drill

**Two minutes: "How would you load test this service?"**

Start by rejecting the naive framing — not "can it do 1,000 rps" but "where is the knee and what
breaks first" — and say you'd operate at half to two-thirds of it for headroom. Then the measurement
correctness points, because they're what separate a real answer: open model, not closed, with the
reason that a closed generator slows down when the server does; and coordinated omission, explained
with the stall example, because it makes p99 wrong by an order of magnitude in the flattering
direction. Then realism: a traffic mix, a Zipfian key distribution, a production-sized dataset, and a
warm-up you discard. Mention Little's Law as the thing that answers half of it without a test. Close
on the two tests nobody runs — **a soak, which is the only thing that finds leaks, and a stress test
with a recovery phase, which tells you whether you're metastable.**
