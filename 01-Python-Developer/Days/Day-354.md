# Day 354 📂

**P-354** · 📂 **Design 10 — file storage and sync** — ⭐⭐ chunking, delta sync, and conflicts

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: Dropbox-style sync is a distributed-state-machine problem wearing a
> file-manager costume — the storage is easy, and the hard parts are transferring only what changed,
> and deciding what happens when two devices edited the same file offline, which is a question the
> system is not allowed to answer silently.**

# Part 1 — ⭐ 0–8: scope and numbers

```
⭐⭐ FUNCTIONAL:
⭐   ① Upload/download files. ② ⭐⭐ SYNC ACROSS DEVICES.
⭐   ③ ⭐ Version history and restore. ④ ⭐ Sharing.
⭐   ⑤ ⭐ Offline edits reconciled on reconnect.
⭐   ⭐⭐ OUT: real-time collaborative editing (⭐ that is
⭐     operational transforms or CRDTs — ***a different
⭐     problem***, because it merges ***within*** a document
⭐     rather than choosing between versions), previews, search.

⭐⭐ NON-FUNCTIONAL:
⭐   ⭐ 100 M users, 50 GB each ⇒ ⭐ 5 EB nominal.
⭐   ⭐ ⭐⭐ AND THE NUMBER THAT CHANGES THAT: DEDUPLICATION
⭐     TYPICALLY REMOVES 50–90% OF STORED BYTES, because
⭐     everyone has the same installers, PDFs and shared
⭐     documents. ⭐ So "5 exabytes" is the ***pre***-dedup
⭐     figure and saying that shows you know what dominates.
⭐   ⭐ ⭐⭐ SYNC LATENCY < 5 s FOR A SMALL CHANGE.
⭐   ⭐ ⭐⭐ ZERO DATA LOSS — INCLUDING NEVER SILENTLY LOSING THE
⭐     LOSING SIDE OF A CONFLICT. ⭐ This is the requirement that
⭐     drives Part 5.

⭐⭐ ⇒ AND THE OBSERVATION THAT SHAPES EVERYTHING:
⭐   ***MOST EDITS CHANGE A TINY FRACTION OF A FILE.*** ⭐ Save a
⭐   50 MB presentation after moving one slide ⇒ ⭐⭐ RE-UPLOADING
⭐   50 MB FOR A 200 KB CHANGE IS THE ENTIRE PROBLEM, AND
⭐   CHUNKING IS THE ENTIRE ANSWER.
```

# Part 2 — ⭐⭐ Chunking, and why the boundaries matter

```
⭐⭐ ***FILES ARE STORED AS A LIST OF CHUNK HASHES, NOT AS
⭐   BYTES.***
⭐   `file_version(id, path, size, chunk_list=[h1,h2,…], mtime)`
⭐   `chunks(hash PK, size, storage_key, refcount)`
⭐   ⇒ ⭐⭐ THE FILE BECOMES A ***RECIPE***; THE CHUNKS ARE THE
⭐     INGREDIENTS, AND THEY ARE SHARED GLOBALLY.

⭐⭐ ① ***FIXED-SIZE CHUNKING*** (4 MB blocks).
⭐   ⭐ ✔ Trivial. ⭐ ✘ ⭐⭐ INSERTING ONE BYTE AT THE START
⭐     SHIFTS ***EVERY*** SUBSEQUENT BOUNDARY, SO EVERY CHUNK
⭐     HASH CHANGES AND YOU RE-UPLOAD THE WHOLE FILE.
⭐   ⇒ ⭐ Fine for append-only files and media; ⭐⭐ USELESS FOR
⭐     DOCUMENTS, WHICH ARE THE CASE THAT MATTERS.

⭐⭐ ② ⭐⭐ ***CONTENT-DEFINED CHUNKING*** (rolling hash / Rabin
⭐   fingerprint) — the real answer.
⭐   ⭐ Slide a window over the bytes; ⭐⭐ CUT WHERE THE ROLLING
⭐     HASH MATCHES A PATTERN (e.g. low 13 bits are zero).
⭐   ⇒ ⭐⭐ BOUNDARIES ARE DETERMINED BY ***CONTENT***, NOT BY
⭐     POSITION — SO INSERTING A BYTE CHANGES ***ONE*** CHUNK
⭐     AND EVERY OTHER BOUNDARY IS UNMOVED.
⭐   ⭐ Target ~1–4 MB average, with min and max bounds
⭐     (⭐⭐ THE MAX MATTERS: WITHOUT IT, PATHOLOGICAL DATA
⭐     PRODUCES ONE ENORMOUS CHUNK).
⭐   ⇒ ⭐⭐ THIS IS THE SINGLE MOST IMPORTANT IDEA IN THE
⭐     DESIGN, AND MOST CANDIDATES DESCRIBE FIXED CHUNKS AND
⭐     STOP.

⭐⭐ THE UPLOAD PROTOCOL THAT FALLS OUT:
⭐   ① Client chunks locally, computes hashes.
⭐   ② ⭐⭐ ASKS THE SERVER: "WHICH OF THESE 40 HASHES DO YOU
⭐      ALREADY HAVE?"
⭐   ③ Uploads only the missing ones (presigned, Day 327).
⭐   ④ Commits a new version with the full chunk list.
⭐   ⇒ ⭐⭐ EDIT ONE SLIDE IN A 50 MB DECK ⇒ ***ONE CHUNK
⭐     UPLOADED.*** ⭐ That is the product.
```

# Part 3 — ⭐⭐ Deduplication and its dangers

```
⭐⭐ THE WIN: chunks keyed by hash ⇒ ⭐ the same installer stored
⭐   once for a million users. ⭐⭐ 50–90% STORAGE REDUCTION.

⭐⭐ THE DANGER ①  — ***THE DEDUP SIDE CHANNEL*** (Day 346, and
⭐   here it is far more serious):
⭐   ⭐ If the client can detect that a chunk already exists
⭐     (upload finishes instantly), ⭐⭐ IT CAN TEST WHETHER ***A
⭐     SPECIFIC FILE EXISTS ANYWHERE IN THE SYSTEM.***
⭐   ⇒ ⭐⭐ AND WORSE — THE HISTORICAL ATTACK: IF POSSESSING THE
⭐     ***HASH*** IS ENOUGH TO CLAIM A CHUNK, SOMEONE WITH ONLY
⭐     THE HASH CAN ***DOWNLOAD*** CONTENT THEY NEVER HAD.
⭐   ⇒ FIXES: ⭐ dedupe ***server-side only*** (client always
⭐     uploads, server discards duplicates) — ⭐ costs bandwidth,
⭐     kills the attack; ⭐ or dedupe within a trust boundary
⭐     (per user, per team); ⭐⭐ OR REQUIRE A PROOF OF POSSESSION
⭐     OF THE ACTUAL BYTES, NOT JUST THE HASH.

⭐⭐ THE DANGER ② — ***REFERENCE COUNTING.***
⭐   ⭐ Deleting a file must not delete chunks another file uses.
⭐   ⇒ ⭐⭐ REFCOUNTS ARE RACY: DECREMENT TO ZERO, AND BEFORE
⭐     YOU DELETE, A NEW UPLOAD REFERENCES THAT CHUNK.
⭐   ⇒ ⭐⭐ THE SAFE ANSWER: ***NEVER DELETE ON REFCOUNT ZERO.***
⭐     Mark it, and have a periodic mark-and-sweep GC delete
⭐     only chunks unreferenced for N days.
⭐   ⇒ ⭐ It is garbage collection, and it should be as
⭐     conservative as one: ⭐⭐ THE COST OF KEEPING A DEAD CHUNK
⭐     IS PENNIES; THE COST OF DELETING A LIVE ONE IS SOMEONE'S
⭐     FILE.

⭐⭐ AND ENCRYPTION VS DEDUP — ⭐ the honest tension:
⭐   ⭐ Per-user encryption keys ⇒ ⭐⭐ IDENTICAL PLAINTEXT
⭐     PRODUCES DIFFERENT CIPHERTEXT ⇒ ***NO CROSS-USER
⭐     DEDUPLICATION AT ALL.***
⭐   ⇒ ⭐ Convergent encryption (key derived from content) keeps
⭐     dedup, ⭐⭐ AND REINTRODUCES THE CONFIRMATION ATTACK.
⭐   ⇒ ⭐⭐ THERE IS NO FREE ANSWER — IT IS A DELIBERATE CHOICE
⭐     BETWEEN COST AND PRIVACY, AND NAMING IT AS SUCH IS THE
⭐     SCORING MOVE.
```

# Part 4 — ⭐⭐ The sync protocol

```
⭐⭐ THE CORE IDEA: ***EACH USER'S NAMESPACE HAS A MONOTONIC
⭐   CURSOR / JOURNAL POSITION. A CLIENT ASKS "WHAT HAS CHANGED
⭐   SINCE CURSOR X?"***
⭐   ⇒ ⭐⭐ THIS IS THE SAME SHAPE AS DAY 352'S PER-CONVERSATION
⭐     SEQUENCE AND DAY 334'S LOG OFFSET. ⭐ Three appearances,
⭐     one idea: a per-scope monotonic position makes
⭐     "catch me up" a range query.

⭐⭐ THE COMPONENTS:
⭐   ⭐ ***METADATA SERVICE*** — the journal of file versions.
⭐     ⭐⭐ THE SYSTEM OF RECORD.
⭐   ⭐ ***BLOCK SERVICE*** — chunk storage.
⭐   ⭐ ***NOTIFICATION SERVICE*** — a long-poll or WebSocket
⭐     that says only "something changed, come and ask".
⭐     ⭐⭐ NOTE WHAT IT DOES ***NOT*** DO: IT DOES NOT CARRY THE
⭐     CHANGE. ⭐ That makes it stateless, cheap, and safe to
⭐     lose — ⭐⭐ AND IT MEANS A DROPPED NOTIFICATION COSTS A
⭐     POLL, NOT A LOST FILE.
⭐   ⭐ ***CLIENT*** — a local watcher and a local database of
⭐     known state.

⭐⭐ THE UPLOAD FLOW:
⭐   ⭐ Watch ⇒ debounce (⭐⭐ EDITORS WRITE FILES 5–10 TIMES
⭐     DURING ONE SAVE; SYNCING EACH IS 10× THE WORK AND A
⭐     GUARANTEED CONFLICT STORM) ⇒ chunk ⇒ ask-which-missing ⇒
⭐     upload ⇒ commit version ⇒ ⭐ others notified.

⭐⭐ THE DOWNLOAD FLOW:
⭐   ⭐ Notified ⇒ `GET /delta?cursor=X` ⇒ ⭐⭐ FETCH ONLY THE
⭐     CHUNKS NOT ALREADY ON DISK (they may already be present
⭐     from another file!) ⇒ reassemble ⇒ ⭐⭐ ATOMIC RENAME INTO
⭐     PLACE, NEVER A PARTIAL WRITE OVER THE USER'S FILE.
⭐   ⇒ ⭐ Then advance the cursor. ⭐⭐ ADVANCING BEFORE THE
⭐     RENAME LOSES THE UPDATE ON A CRASH.
```

# Part 5 — ⭐⭐ Conflicts: the part you are not allowed to guess

```
⭐⭐ THE SCENARIO: two devices edit the same file while offline.
⭐   Both reconnect.

⭐⭐ THE OPTIONS, AND WHY MOST ARE WRONG:
⭐   ⭐ ❌ ***LAST WRITE WINS*** — ⭐⭐ SILENTLY DESTROYS
⭐     SOMEBODY'S WORK, AND CLOCK SKEW MEANS "LAST" MAY BE THE
⭐     EARLIER EDIT (Day 343).
⭐   ⭐ ❌ ***AUTOMATIC MERGE*** — impossible for binary files,
⭐     and wrong even for text without semantics.
⭐   ⭐ ✔ ⭐⭐ ***KEEP BOTH.*** `report.docx` and
⭐     `report (Alice's conflicted copy 2026-08-20).docx`.
⭐   ⇒ ⭐⭐ IT LOOKS UNSOPHISTICATED AND IT IS EXACTLY RIGHT:
⭐     ***THE SYSTEM CANNOT KNOW WHICH EDIT MATTERS, SO IT MUST
⭐     NOT CHOOSE — IT PRESERVES BOTH AND SURFACES THE
⭐     DECISION.*** ⭐ Dropbox, Google Drive and OneDrive all do
⭐     this, and it is the answer to give.

⭐⭐ HOW YOU ***DETECT*** IT — ⭐ and this is where candidates
⭐   are weak:
⭐   ⭐ ⭐⭐ EVERY UPLOAD CARRIES THE ***PARENT VERSION*** IT WAS
⭐     BASED ON.
⭐   ⭐ Server accepts only if the parent is still the current
⭐     version ⇒ ⭐⭐ A CONDITIONAL WRITE (Day 310) — otherwise
⭐     it is a conflict.
⭐   ⇒ ⭐⭐ THIS IS OPTIMISTIC CONCURRENCY CONTROL, AND IT IS THE
⭐     SAME `WHERE version = :expected` PATTERN AT A DIFFERENT
⭐     SCALE. ⭐ Naming it that way is what makes it sound like
⭐     understanding rather than a Dropbox anecdote.

⭐⭐ AND FOUR CASES PEOPLE FORGET ENTIRELY:
⭐   ⭐ ⭐⭐ EDIT VS DELETE ⇒ keep the edit, resurrect the file.
⭐     ⭐ Deleting is cheap to redo; recreating lost work is not.
⭐   ⭐ ⭐⭐ TWO DEVICES CREATE ***DIFFERENT*** FILES AT THE SAME
⭐     PATH ⇒ same conflict handling.
⭐   ⭐ ⭐⭐ CASE SENSITIVITY: `Report.txt` and `report.txt`
⭐     coexist on Linux and collide on macOS/Windows.
⭐     ⭐ Normalise and detect at commit time.
⭐   ⭐ ⭐⭐ A DIRECTORY MOVE WITH 10,000 FILES INSIDE ⇒ ⭐ if you
⭐     model it as 10,000 deletes and 10,000 creates, every
⭐     client re-downloads everything. ⭐⭐ MODEL MOVE AS A
⭐     FIRST-CLASS OPERATION, OR A DRAG-AND-DROP COSTS A
⭐     TERABYTE OF EGRESS.
```

# Part 6 — ⭐ Sharing, versions and the metadata scale

```
⭐⭐ SHARING: ⭐ a shared folder appears in N namespaces.
⭐   ⭐ ⭐⭐ THE NAIVE MODEL — COPY THE JOURNAL ENTRIES INTO EACH
⭐     MEMBER'S NAMESPACE — MEANS A 100-PERSON SHARED FOLDER
⭐     FANS OUT EVERY CHANGE 100 TIMES. ⭐ Day 351, again.
⭐   ⇒ ⭐⭐ BETTER: THE SHARED FOLDER IS ITS ***OWN*** NAMESPACE
⭐     WITH ITS OWN CURSOR, AND EACH CLIENT SYNCS THE
⭐     NAMESPACES IT IS A MEMBER OF. ⭐ One journal, N readers —
⭐     ⭐ pull rather than push, which is Day 351's hybrid,
⭐     arriving from a different direction.
⭐   ⭐ Permissions checked at read; ⭐⭐ REVOCATION MUST INVALIDATE
⭐     ANY ISSUED PRESIGNED URLS, WHICH IS WHY THEIR EXPIRY IS
⭐     MINUTES.

⭐⭐ VERSION HISTORY: ⭐ every commit is a new version row with
⭐   a chunk list.
⭐   ⇒ ⭐⭐ HISTORY IS ALMOST FREE, BECAUSE UNCHANGED CHUNKS ARE
⭐     SHARED BETWEEN VERSIONS — ⭐ 100 versions of a document
⭐     that changed a paragraph each time costs ~100 small
⭐     chunks, not 100 full copies. ⭐ That is a lovely
⭐     consequence of Part 2 and worth pointing out.
⭐   ⭐ Retention policy per plan; ⭐ pruning old versions is
⭐     just dropping version rows and letting GC handle chunks.

⭐⭐ METADATA SCALE — ⭐⭐ THE PART PEOPLE UNDERESTIMATE:
⭐   ⭐ 100 M users × 10,000 files × 5 versions =
⭐     ⭐⭐ 5 × 10^12 VERSION ROWS.
⭐   ⇒ ⭐⭐ THE ***METADATA*** IS THE HARD DATABASE PROBLEM HERE,
⭐     NOT THE BYTES. ⭐ Shard by `user_id`/`namespace_id` (which
⭐     keeps a namespace's journal on one shard — ⭐ exactly Day
⭐     329's "keep the unit of work together").
```

# Part 7 — ⭐ Bottlenecks and the summary

```
⭐⭐ WHAT BREAKS:
⭐   ① ⭐⭐ METADATA WRITE VOLUME — every save is a journal
⭐      entry. ⭐ Debounce hard on the client; ⭐⭐ THE CLIENT IS
⭐      PART OF YOUR CAPACITY PLAN.
⭐   ② ⭐ The notification fan-out for large shared folders ⇒
⭐      namespaces, ⭐ and coalesce notifications (one per
⭐      namespace per second is plenty).
⭐   ③ ⭐⭐ CHUNK GC AT EXABYTE SCALE — a mark-and-sweep over
⭐      trillions of chunks cannot be one pass. ⭐ Partition by
⭐      hash prefix and sweep continuously.
⭐   ④ ⭐ The "which chunks do you have" call ⇒ ⭐⭐ BATCH IT
⭐      (one call for 40 hashes, not 40 calls) and put a Bloom
⭐      filter in front.

⭐⭐ THE SUMMARY:
⭐   ***"Storage is easy; the design is transfer and conflicts.
⭐      Files are recipes of content-defined chunks, so editing
⭐      one slide in a fifty-megabyte deck uploads one chunk —
⭐      and content-defined boundaries are what make that true,
⭐      because fixed chunks shift on a single inserted byte.
⭐      Sync is a per-namespace monotonic cursor, so catching up
⭐      is a range query, and the notification channel carries
⭐      no data, only 'come and ask'. Conflicts are detected by
⭐      requiring the parent version — optimistic concurrency —
⭐      and resolved by keeping both copies, because the system
⭐      genuinely cannot know which edit mattered and must not
⭐      choose. The two things I'd watch are dedup as a privacy
⭐      side channel and chunk GC, which should be conservative,
⭐      because keeping a dead chunk costs pennies and deleting
⭐      a live one costs somebody's file."***
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Fixed-size chunking | One inserted byte shifts every boundary and you re-upload the whole file |
| ⭐ No max chunk size | Pathological data produces one enormous chunk |
| ⭐⭐ Client-side dedup by hash alone | A confirmation side channel, and historically a way to download content you never had |
| ⭐⭐ Deleting chunks at refcount zero | Racy. Mark and sweep conservatively — a dead chunk costs pennies, a live one costs a file |
| ⭐⭐ Last-write-wins on conflict | Silently destroys work, and clock skew means "last" may be earlier |
| ⭐ Automatic merge | Impossible for binaries, wrong for text without semantics |
| ⭐⭐ No parent version on upload | You cannot detect a conflict at all. It's optimistic concurrency, and it's mandatory |
| ⭐ Resolving edit-vs-delete as delete | Deleting is cheap to redo; recreating lost work isn't |
| ⭐⭐ Modelling a directory move as N deletes and N creates | A drag-and-drop costs a terabyte of egress |
| ⭐ Syncing every editor write | Editors save 5–10 times per save. Debounce, or you get a conflict storm |
| ⭐⭐ Copying journal entries into every member's namespace | A 100-person folder fans out 100×. Shared folders are their own namespace |
| ⭐ Advancing the cursor before the atomic rename | A crash loses the update silently |
| ⭐ Underestimating metadata | Trillions of version rows. Metadata is the hard database problem, not the bytes |

## Interview questions

**1. "How do you avoid re-uploading a whole file?"**
> ⭐⭐ Content-defined chunking. Files are stored as a list of chunk hashes — a recipe — and boundaries
> are chosen by a **rolling hash over the content rather than by byte position**, ⭐⭐ so **inserting a
> byte changes one chunk instead of shifting every boundary.** ⭐ Then the client asks which of its
> forty hashes the server already has and uploads only the missing ones. ⭐ Editing one slide in a
> fifty-megabyte deck becomes one chunk uploaded.

**2. "Two devices edit the same file offline. What happens?"**
> ⭐ Detection first: **every upload carries the parent version it was based on, and the server accepts
> only if that's still current** — optimistic concurrency, the same conditional-write pattern as
> anywhere else. ⭐⭐ Resolution: **keep both.** ⭐ Last-write-wins silently destroys work and clock skew
> makes "last" unreliable; automatic merge is impossible for binaries. ⭐⭐ **The system cannot know
> which edit mattered, so it must not choose — it preserves both and surfaces the decision**, which is
> what every real product does.

**3. "What's dangerous about deduplication here?"**
> ⭐⭐ It's a side channel. If a client can tell that a chunk already exists — the upload finishes
> instantly — **it can test whether a specific file exists anywhere in the system.** ⭐⭐ And
> historically worse: if possessing the *hash* is enough to claim a chunk, someone with only the hash
> can download content they never had. ⭐ So: server-side dedup only, or dedup within a trust boundary,
> or a proof of possession of the actual bytes. ⭐ And there's a real tension with per-user encryption —
> it kills cross-user dedup entirely, and convergent encryption brings the attack back.

**4. "How does sync actually work?"**
> ⭐ Each namespace has a monotonic journal cursor, so a client asks "what changed since X" and gets a
> range — ⭐⭐ **the same shape as a chat sequence number or a log offset.** ⭐ The notification channel
> says only "something changed, come and ask" — **it carries no data, which makes it cheap, stateless
> and safe to lose: a dropped notification costs a poll, not a file.** ⭐ And the client debounces hard,
> because editors write a file five to ten times during one save.

**5. "How do you delete a chunk safely?"**
> ⭐⭐ You don't delete on refcount zero — that's racy, because a new upload can reference the chunk
> between the decrement and the delete. ⭐ Mark it and run a conservative mark-and-sweep that deletes
> only chunks unreferenced for some days, partitioned by hash prefix and swept continuously at this
> scale. ⭐⭐ **Keeping a dead chunk costs pennies; deleting a live one costs somebody's file** — so the
> GC is deliberately biased.

**6. "Someone drags a folder with 10,000 files into another folder."**
> ⭐⭐ If a move is modelled as ten thousand deletes and ten thousand creates, **every client
> re-downloads everything, and a drag-and-drop costs a terabyte of egress.** ⭐ So move has to be a
> first-class journal operation that clients apply locally by renaming. ⭐ Same family of problem as
> case-sensitivity collisions between platforms, which have to be normalised and detected at commit
> time rather than discovered by a client that can't create the file.

## 🎙️ Articulation drill

**Two minutes.** Open with the reframing: **storage is the easy part; the design is transfer and
conflicts.** Give the observation that drives everything — **most edits change a tiny fraction of a
file** — and then the mechanism: files are recipes of chunk hashes, and **the boundaries must be
content-defined, because with fixed chunks a single inserted byte shifts every boundary and you
re-upload the whole file.** Content-defined means one chunk changes and the rest are untouched, so
editing a slide in a fifty-megabyte deck uploads one chunk. Then sync: **a per-namespace monotonic
cursor, so catching up is a range query** — the same shape as a chat sequence or a log offset — and a
notification channel that carries no data, only "come and ask", which makes a dropped notification cost
a poll rather than a file. Then conflicts, in two halves. Detection: **every upload carries its parent
version and the server accepts only if that's still current — optimistic concurrency.** Resolution:
**keep both copies, because the system genuinely cannot know which edit mattered and must not choose** —
which looks unsophisticated and is exactly right. Close on the two things that quietly matter:
**deduplication is a privacy side channel, since detectable dedup confirms a specific file exists
somewhere in the system**, and **chunk GC must be conservative, because a dead chunk costs pennies and
a live one costs somebody's file.**
