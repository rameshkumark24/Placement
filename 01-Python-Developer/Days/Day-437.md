# Part 2 — ⭐⭐ The four invariants, and the test that pins each

```
⭐⭐ ① ***YOU CANNOT RETRIEVE WITHOUT A TENANT.***
⭐   ⭐ Keyword-only, required, no `Optional`, no filter dict.
⭐   ⭐ TEST: `pytest.raises(TypeError)` on a call without it.
⭐   ⭐ ⭐⭐ PLUS THE CANARY: TENANT B HOLDS A UNIQUE TOKEN IN A
⭐     TOPICALLY IDENTICAL DOCUMENT; ASKING AS A MUST NEVER
⭐     SURFACE IT. RUNS ON EVERY COMMIT.
⭐   ⭐ PLUS RLS, so removing the WHERE clause still passes.

⭐⭐ ② ***IT MAY RETURN NOTHING, AND THAT IS A DESIGNED
⭐   OUTCOME.***
⭐   ⭐ Reranker floor, not just a sort (D433).
⭐   ⭐ TEST: a question your corpus cannot answer returns
⭐     `hits == []` and `abstained is True`.
⭐   ⭐ ⭐⭐ WITHOUT THIS, THE ABSTENTION PATH IN THE PROMPT
⭐     (D422) IS DECORATION — the model always gets *something*
⭐     that looks authoritative.

⭐⭐ ③ ***THE TOKEN BUDGET IS ENFORCED.***
⭐   ⭐ TEST: seed one 3,000-token chunk and assert
⭐     `context_tokens <= budget`.
⭐   ⭐ ⭐⭐ A BUDGET YOU DO NOT ENFORCE IS A BILL YOU DISCOVER
⭐     LATER (D421).

⭐⭐ ④ ***RECALL IS MEASURED AND GATED.***
⭐   ⭐ recall@k in CI on every commit — no LLM calls, free.
⭐   ⭐ TEST: the gate fails the build when recall drops more
⭐     than the tolerance band below the last release.
⭐   ⭐ ⭐⭐ AN UNMEASURED PIPELINE CANNOT BE CHANGED, WHICH MEANS
⭐     IT CANNOT BE IMPROVED OR MADE CHEAPER (D425).
```

# Part 4 — ⭐⭐ The six shapes of retrieval

```
⭐⭐ ① ***RETRIEVAL IS AN ECONOMIC ARGUMENT, NOT AN
⭐   ARCHITECTURAL PREFERENCE.*** (D429)
⭐   ⭐ 43× cheaper, 10× faster to first token, ***and*** more
⭐     accurate because of lost-in-the-middle. ⭐⭐ IT IS NOT A
⭐     COMPROMISE. ⭐ And below ~50k tokens of corpus it loses to
⭐     a cached prompt, which is a real answer, not a cop-out.

⭐⭐ ② ***CHUNKING IS THE CEILING.*** (D430)
⭐   ⭐ Everything downstream can only ***reorder*** what
⭐     chunking produced. ⭐⭐ NO RERANKER RECOVERS INFORMATION NO
⭐     CHUNK CONTAINS. ⭐ One object is doing two jobs that want
⭐     opposite sizes — small to search, large to read — and
⭐     every serious technique separates those two units.

⭐⭐ ③ ***THE FREE OPTIMISATIONS BEAT THE PAID ONES, SO DO THEM
⭐   FIRST.*** (D430/433/436)
⭐   ⭐ Heading-path prefix: +0.10–0.15 for a string
⭐     concatenation. ⭐ Hybrid: +0.05–0.08 for one index.
⭐   ⭐⭐ TWO-THIRDS OF THE TOTAL GAIN ARRIVES BEFORE YOU SPEND A
⭐     PENNY. ⭐ Ordering the work correctly ***is*** the skill.

⭐⭐ ④ ***THE INDEX IS DERIVED STATE.*** (D431/432/434 ← D412)
⭐   ⭐ Changing the model, the prefix or ***the chunker*** is a
⭐     migration with an alias swap, because a half-migrated
⭐     index has ***meaningless*** distances, not merely worse
⭐     ones. ⭐ Deletion is not automatic. ⭐ Permissions go stale.
⭐   ⭐⭐ YOU DO NOT OWN DERIVED STATE UNTIL YOU HAVE REBUILT IT
⭐     ON PURPOSE, WITH A STOPWATCH.

⭐⭐ ⑤ ***THE PERMISSION FILTER IS A CORRECTNESS INVARIANT AND
⭐   ITS FAILURE IS SILENT.*** (D434)
⭐   ⭐ Generation ***launders*** leaked data into fluent original
⭐     prose, so row counts, error rates and latency all stay
⭐     normal. ⭐⭐ THEREFORE: TENANT FROM THE SESSION NEVER THE
⭐     MODEL, FILTER INSIDE THE QUERY NEVER AFTER IT, RLS
⭐     UNDERNEATH, A CANARY IN CI, AND RETRIEVED DOC IDS LOGGED —
⭐     BECAUSE "I DON'T KNOW WHAT WAS DISCLOSED" IS READ AS
⭐     WORST-CASE BY EVERYONE WHO MATTERS.

⭐⭐ ⑥ ***SOME QUESTIONS ARE NOT RETRIEVAL QUESTIONS.*** (D436)
⭐   ⭐ Counts, sums, superlatives, recency, diffs. ⭐⭐ TOP-k
⭐     RETURNS EIGHT DOCUMENTS WHEN THE ANSWER NEEDS FOUR
⭐     THOUSAND ROWS, AND THE FABRICATED NUMBER ARRIVES FLUENT,
⭐     SPECIFIC AND WITH A CITATION. ⭐ Route them to SQL — and
⭐     show the SQL, because it is the only citation an aggregate
⭐     answer can have.
```

# 💬 Interview

**1. "Walk me through your retrieval architecture."**

⭐ One service, one public method, four invariants that live in that method so the next feature can't
bypass them. ⭐ A question comes in with a tenant and a principal set taken from the authenticated
session. ⭐⭐ If it's multi-turn it gets rewritten to a standalone query and we log the rewrite. ⭐ Then
it's routed — a third of our questions turn out to be aggregations, and those go to a validated
text-to-SQL path rather than the index. ⭐ Lookup questions get embedded through an API that enforces
the query prefix, then hybrid dense-plus-keyword search with the tenant and ACL predicates **inside**
the SQL, fifty candidates fused by RRF, cross-encoder reranked to eight with an absolute floor, capped
per document, expanded to parent sections, budget-enforced, and ordered best-first-second-last for
lost-in-the-middle. ⭐⭐ The result object carries the doc ids, the scores and the config hash, because
that's what makes it auditable and evaluable.

**2. "What are the four invariants and why those four?"**

⭐ You cannot retrieve without a tenant — it's keyword-only and required, so omitting it is a type error
rather than a review miss, and there's a canary test in CI plus RLS underneath. ⭐ It may return
nothing — the reranker has an absolute floor, because without that the abstention path in the prompt is
decoration; the model always gets something authoritative-looking. ⭐ The token budget is enforced, not
assumed, because a budget you don't enforce is a bill you find later. ⭐⭐ And recall is measured and
gated on every commit, because an unmeasured pipeline can't be changed — which means it can't be
improved *or* made cheaper. ⭐ Those four are the ones where the failure is silent, which is exactly why
they need to be structural.

**3. "What's the single biggest lever you found?"**

⭐⭐ Prepending the heading path to the chunk text before embedding. ⭐ Ten to fifteen points of recall
for a string concatenation and no extra inference. ⭐ It works because a chunk full of pronouns embeds
near nothing — "it must be renewed within 30 days" is equally close to every renewal rule in the corpus,
and the prefix puts the missing subject back into the vector. ⭐⭐ The wider lesson is the ordering:
two-thirds of our total gain arrived before we spent a penny, and the most common mistake in this field
is buying a reranker before concatenating a heading onto a chunk.

**4. "What can your system not do?"**

⭐ Recall@8 is 0.91, so about nine percent of questions have no correct chunk in the window and no
prompt fixes those. ⭐ It can't answer aggregations — those route to SQL, and I show the user the
generated query because it's the only citation an aggregate can have. ⭐⭐ Permission revocation takes
up to thirty seconds because ACL changes propagate through an outbox, and I state that window rather
than pretending it's instant. ⭐ Multi-hop questions spanning three documents are weak; we handle two by
decomposition and stop there. ⭐⭐ And full rebuild is 38 minutes, which is our worst-case recovery time
if we lose the index. ⭐ All of that is in the README, because being able to state your limits precisely
is more convincing than claiming you don't have any.

**5. "How do you know none of it regressed?"**

⭐ Retrieval metrics and the cross-tenant canary run on every commit — deterministic, no LLM calls,
seconds, free. ⭐ The full suite including judged faithfulness runs on any PR touching prompts, schemas
or retrieval config. ⭐ And a nightly run against the production config, which is what catches a
provider silently updating a model behind a stable name. ⭐⭐ The gates differ in kind on purpose: recall
gets a tolerance band above measured run-to-run noise, and the leak count is a hard zero with no band at
all, because a security invariant is not a score.

**6. "If you started again, what would you do differently?"**

⭐ I'd build the eval set before the index rather than after. ⭐⭐ We spent our first two weeks tuning
chunk sizes by reading output and arguing, and the moment we had thirty labelled questions the answer
was obvious in ninety minutes — and it wasn't the size, it was the splitting strategy. ⭐ I'd also label
`doc_id` plus an answer span from the start instead of chunk ids, because chunk ids become meaningless
the moment you re-chunk, which is precisely the experiment the harness exists to run. ⭐⭐ And I'd add
the twenty unanswerable questions on day one — our baseline abstention rate was 0.15, and nobody would
have found that out until a customer did.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: "tell me about the retrieval system you built."**

Lead with the contract, not the components. **Retrieval isn't a library we call, it's a service with
four invariants. You can't retrieve without a tenant — it's a required keyword-only argument, so
forgetting it is a type error, and there's row-level security underneath and a canary test in CI. It's
allowed to return nothing, because the reranker has an absolute floor rather than just a sort order —
without that, the abstention path in the prompt is decoration, since the model always gets something
authoritative-looking. The token budget is enforced, not assumed. And recall is measured and gated on
every commit, because a pipeline you can't measure is one you can't change.**

Then the numbers, because they carry the story. **Dense-only recall@5 was 0.62. Prepending the heading
path before embedding took it to 0.75 for free. Hybrid search with reciprocal rank fusion took it to
0.82 for fifteen milliseconds. A cross-encoder reranker took it to 0.91 for a hundred and fifty. So
two-thirds of the gain arrived before we spent anything — and getting that ordering right is most of the
skill. We tried HyDE, measured it flat, and deleted it.**

Then the part most people never mention. **Recall@8 is 0.91, which means nine percent of questions are
unanswerable no matter what prompt we write. Knowing that stopped us tuning prompts for a problem
prompts can't touch. And about a third of the questions users actually asked were aggregations — counts,
totals, "which is largest" — which a vector index can't answer at all: top-k returns eight documents
when the answer needs four thousand rows, and the fabricated number arrives fluent, specific and with a
citation. So there's a router, and those go to validated text-to-SQL over a read-only view, with the
generated SQL shown to the user.**

Close on the security invariant and the proof. **The one that keeps me honest is that a retrieval leak
is silent. A missing tenant filter in SQL shows forty thousand rows and someone notices in minutes — the
same bug in retrieval produces a fluent, well-cited paragraph built from another customer's data, with
no exception, no error-rate change and no latency change, because generation launders it into original
prose. So: tenant from the session, never the model. Filter inside the query, never after it. RLS
underneath. Retrieved doc ids logged, so I can answer "what was disclosed and to whom" — and "I don't
know" is read as worst case by everyone who matters. We proved it by deleting the tenant predicate in a
branch: the canary failed in CI in forty seconds, and with RLS enabled it didn't leak at all. That's
what defence in depth means, and I've got the two CI runs.**
