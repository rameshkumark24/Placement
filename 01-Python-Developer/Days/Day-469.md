# Day 469 🔬

**P-469** · 🔬 **The failure interrogation** — ⭐⭐ what breaks first, and how you would know

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every deep dive ends the same way — what breaks, at what scale, how would
> you know, and what would you do next — and the candidates who separate are the ones who answer with a
> named component and a metric rather than with a new architecture.**

---

# Part 1 — ⭐⭐ "What breaks at 10×?" is four questions

```
⭐ ***THE WEAK ANSWER:*** ⭐ "We'd add caching and horizontal
⭐   scaling." ⭐⭐ THIS IS A LIST OF WORDS. ⭐ It works for any
⭐   system, which is exactly why it scores nothing.

⭐ ***THE FOUR QUESTIONS HIDING INSIDE IT:***
⭐   ⭐ ① ⭐⭐ ***WHICH COMPONENT BREAKS ***FIRST***?*** ⭐ Name one.
⭐     ⭐⭐ NAMING ONE IS THE WHOLE SIGNAL — ⭐ it proves you have
⭐     a model of where the pressure is, rather than a list of
⭐     scaling techniques.
⭐   ⭐ ② ***AT WHAT NUMBER?*** ⭐ A rough figure with reasoning
⭐     beats a precise one you cannot derive.
⭐   ⭐ ③ ⭐⭐ ***HOW WOULD YOU KNOW?*** ⭐ Which metric moves, and
⭐     ***before*** or ***after*** users notice? ⭐⭐ THIS IS THE
⭐     QUESTION MOST CANDIDATES HAVE NO ANSWER TO AT ALL.
⭐   ⭐ ④ ***WHAT DO YOU DO, AND WHAT DOES THAT COST?***

⭐ ***THE STRONG ANSWER, SAME SYSTEM:***
⭐   ⭐ ⭐⭐ "TOKENS PER MINUTE BREAKS FIRST, AND EARLIER THAN
⭐     PEOPLE EXPECT. ⭐ We're at 6,500 tokens a request, so a
⭐     200k TPM tier is thirty requests a minute — half a request
⭐     per second — ⭐⭐ AND OUR RPM LIMIT OF 5,000 IS COMPLETELY
⭐     IRRELEVANT. ⭐ I'd know from 429 rate and from queue wait
⭐     time, which moves before latency does. ⭐⭐ THE FIX IS
⭐     SEPARATE KEYS PER WORKLOAD CLASS AND MOVING BATCH WORK TO
⭐     THE BATCH API — ⭐ that's a separate quota pool and half
⭐     the price. ⭐ Quota increases have a lead time of days to
⭐     weeks, so that's a planning item, not an incident
⭐     response."

⭐ ⭐⭐ NOTE WHAT MAKES IT STRONG: ⭐ one named component, an
⭐   arithmetic derivation, a leading indicator, a fix with a
⭐   cost, ⭐⭐ AND A CONSTRAINT THAT CANNOT BE SOLVED IN THE
⭐   MOMENT. ⭐ That last clause is what an operator sounds like.
```

# Part 3 — ⭐⭐ "How would you know?" is the real question

```
⭐ ***FOR EVERY FAILURE, YOU NEED THREE THINGS:***
⭐   ⭐ ① ***THE LEADING INDICATOR*** — what moves ***before***
⭐     users notice;
⭐   ⭐ ② ***THE ALARM*** — the threshold or shift you actually
⭐     alert on;
⭐   ⭐ ③ ⭐⭐ ***THE SILENT CASE*** — the failure with ***no***
⭐     indicator, and what you built to make it visible.

⭐ ③ ***IS THE ONE THAT WINS ROUNDS***, and this stage handed you
⭐   four of them:
⭐   ⭐ ⭐⭐ A CROSS-TENANT LEAK ⭐ — no exception, no error rate,
⭐     no latency change. ⭐ ⇒ a canary test in CI, and retrieved
⭐     doc ids logged so the question "what was disclosed and to
⭐     whom" is answerable at all.
⭐   ⭐ ⭐⭐ THE REPAIR LOOP ABSORBING A REGRESSION ⭐ — every
⭐     request succeeds. ⭐ ⇒ alert on repair rate, not error
⭐     rate.
⭐   ⭐ ⭐⭐ A PROVIDER SWAPPING THE MODEL UNDER A STABLE NAME ⭐ —
⭐     you deployed nothing. ⭐ ⇒ output-length distribution, and
⭐     the nightly eval against production config.
⭐   ⭐ ⭐⭐ A CACHE HIT BYPASSING THE PERMISSION FILTER ⭐ — the
⭐     code path never ran. ⭐ ⇒ tenant and principal hash in the
⭐     key, and a false-hit rate measured by shadow-running 1%.

⭐ ⭐⭐ THE GENERAL FORM, WORTH SAYING OUT LOUD: ⭐ ***"THE
⭐   FAILURES I WORRY ABOUT MOST ARE THE ONES THAT RETURN 200."***
⭐   ⭐ Everything that throws will be noticed by somebody.
```

# 💬 Interview

**1. "What breaks first at ten times the traffic?"**

⭐ Tokens per minute, and earlier than people expect. ⭐⭐ We're at about 6,500 tokens a request, so a
200,000 TPM tier gives thirty requests a minute — half a request per second — while the RPM limit of
five thousand is completely irrelevant. ⭐ I'd know from the 429 rate and from queue wait time, which
moves before latency does. ⭐⭐ The fix is separate API keys per workload class so a background job can't
starve interactive traffic, and moving deferrable work to the batch API — a separate quota pool at half
the price. ⭐ And the part that isn't an incident response: quota increases have a lead time of days to
weeks, so that has to be a planning item.

**2. "How would you know something's wrong?"**

⭐ For most failures there's a leading indicator, and I'd name the metric rather than say "monitoring".
⭐⭐ But the failures I actually worry about are the ones that return 200. ⭐ A cross-tenant leak produces
no exception, no error-rate change and no latency change — so there's nothing to alert on, and the fix
had to be a test that *constructs* the failure and runs on every commit. ⭐⭐ The repair loop absorbing a
quality regression is the same shape: every request succeeds, so I alert on repair rate rather than error
rate. ⭐ A provider swapping the model under a stable name means I deployed nothing and behaviour moved,
so output-length distribution and a nightly eval against production config. ⭐⭐ Everything that throws
will be noticed by somebody; the silent ones need something built.

**3. "What would you do with another month?"**

⭐ Three things, ranked, with the reason for the order. ⭐⭐ First, multi-hop retrieval — it's about sixty
percent of my remaining failures, so it's the only change that moves the ceiling. ⭐ Second, taking the
embedding API hop out of the query path: sixty milliseconds on every request forever, and it's a
dependency that can be down while my database is healthy. ⭐ Third, ACL propagation from thirty seconds
to real-time — nobody's asked for it, and it's the thing I'd be least comfortable defending in a
security review. ⭐⭐ And what I wouldn't do is fine-tune: the gap is retrieval, not form, so it'd cost
weeks and buy nothing.

**4. "Isn't this over-engineered?"**

⭐ Partly, and I'd rather say which parts than defend all of it. ⭐⭐ The eval harness was over-engineered
for the first month and essential by the third — I'd build it again on day one, knowing that. ⭐ The
reranker I'd call justified: nine points of recall for a hundred and fifty milliseconds. ⭐⭐ The
multi-agent experiment genuinely was over-engineering, which is why it isn't in the system — one agent
with six good tools measured better and cost a third as much.

**5. "This doesn't seem that hard."**

⭐ Most of it wasn't, and I wouldn't defend the difficulty of the whole system. ⭐⭐ The genuinely hard
part was that a permission leak produces a perfect-looking answer — fluent, well-cited, and built from
another customer's data — so there's no error, no latency change, nothing to alert on. ⭐ The generation
step launders the evidence. ⭐⭐ Which means the fix couldn't be monitoring; it had to be a test that
constructs the failure, plus row-level security so the database enforces the boundary regardless of my
code. ⭐ Getting that right took longer than all the retrieval quality work combined.

**6. "Why should I believe your numbers?"**

⭐ Because of the method, and I can show you the artefact. ⭐⭐ Thirty questions with known-correct
sources, generated backwards from chunks and human-reviewed; labelled by doc id and answer span rather
than chunk id, so re-chunking doesn't invalidate the set; scored recall-only with no generation involved,
so nothing else can confound it. ⭐ The sweep across forty configurations is a plot I can pull up, and
the harness runs in CI. ⭐⭐ If any of that sounds thin, the honest answer is that thirty cases is a small
set and the confidence interval is wide — which is why I treat a two-point difference as noise rather
than a result.

## 🎙️ Articulation drill

⭐⭐ **Three minutes, out loud: the failure interrogation, end to end.**

Start with the ordered answer, not a list of techniques. **"At ten times the traffic, the first thing to
break is the token-per-minute quota, and much earlier than people expect. We're at six and a half
thousand tokens a request, so a two-hundred-thousand TPM tier is thirty requests a minute — half a
request per second — and our RPM limit of five thousand is irrelevant. I'd see it in the 429 rate and in
queue wait time, which moves before latency does. The fix is separate keys per workload class and moving
batch work to the batch API, which is a separate pool at half the price. And quota increases take days
to weeks, so it's a planning item rather than something I can fix during an incident."**

Then go where they haven't asked. **"At ten times the tenants, something different breaks: filter
selectivity. As each tenant's share of the corpus shrinks, approximate search gets worse for them
specifically — so my smallest customers degrade first, and they degrade silently, because they assume
it was always like that. That's the failure mode I'd want to instrument before it happens rather than
after."**

Then the class of failure that defines the system. **"The failures I actually worry about are the ones
that return 200. A cross-tenant leak has no exception, no error-rate change and no latency change,
because generation launders the data into fluent prose. The repair loop absorbing a quality regression
looks like a hundred percent success. A provider swapping the model under a stable name means I deployed
nothing and behaviour moved. None of those can be alerted on with normal monitoring — each one needed
something built: a canary test that constructs the leak, an alarm on repair rate, and output-length
distribution plus a nightly eval against production config."**

Close on the ranked month, ending with a rejection. **"With another month: multi-hop retrieval first,
because it's sixty percent of my remaining failures and the only thing that moves the ceiling. Then
taking the embedding hop off the query path — sixty milliseconds on every request forever, and a
dependency that can be down while the database is fine. Then ACL propagation from thirty seconds to
real-time, which nobody has asked for and is the thing I'd least like to defend in a security review.
And I wouldn't fine-tune. The gap is retrieval, not form."**
