# Day 026

**L-026** · ⭐⭐ **Reference counting** — `sys.getrefcount`, deterministic destruction, and its costs

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: CPython frees an object the instant its reference count hits zero — not
> "eventually", not "at the next GC pause". Immediately, on the line that dropped the last
> reference.**
>
> ⭐ That property is genuinely nice, and it has three consequences most Python developers cannot
> name: it is why `__del__` is unreliable, it is why forked workers use far more memory than you
> expect, and it is **half the reason the GIL exists at all** (Day 065).

---

# Part 1 — ⭐⭐ How it works

```
⭐ Every object's header carries ob_refcnt (Day 023). CPython adjusts it constantly:

⭐   INCREF when:  a name is bound · appended to a container · passed to a function
⭐                 · captured by a closure · stored as an attribute
⭐   DECREF when:  a name is rebound or deleted · a container is destroyed
⭐                 · a function returns (its locals go) · a scope ends
⭐
⭐ ⇒ ⭐⭐ DECREF to 0  ⇒  tp_dealloc runs IMMEDIATELY  ⇒  memory returned to the allocator
⭐                       ⇒ ⭐ and every object it referenced is DECREF'd in turn (a cascade)
```

```python
import sys
a = []
sys.getrefcount(a)     # ⭐⭐ 2, not 1 — the argument passed to getrefcount is itself a reference
b = a
sys.getrefcount(a)     # 3
del b
sys.getrefcount(a)     # 2
```

⭐ **The off-by-one is the standard gotcha:** `getrefcount` receives the object as an argument, which
is itself a temporary reference. **Always read it as "n − 1".**

```python
class Noisy:
    def __del__(self): print("freed")

x = Noisy()
x = None          # ⭐⭐ prints "freed" RIGHT HERE. Not later. Deterministically.
```

```
⭐⭐ CONTRAST WITH A TRACING GC (Java, Go, JavaScript):
⭐   there, an unreachable object is freed at some UNSPECIFIED later time, during a GC cycle.
⭐   ⇒ ⭐ you get: no refcount overhead, no cycle problem, but ⭐⭐ PAUSES and nondeterminism.
⭐ ⭐⭐ CPython chose the opposite trade: deterministic and immediate, at a constant running cost.
```

# Part 2 — ⭐⭐ The three consequences

## ⭐ 1. `__del__` is not a destructor — do not use it for cleanup

```python
class Conn:
    def __del__(self):
        self.sock.close()      # ⚠️⚠️ ⭐⭐ DO NOT RELY ON THIS
```

```
⭐⭐ WHY __del__ IS UNRELIABLE, and each reason is independently fatal:
⭐  1. ⭐⭐ It is a CPYTHON IMPLEMENTATION DETAIL. PyPy and Jython use tracing GC —
⭐     ⇒ your file/socket closes "eventually", or at interpreter exit, or never.
⭐  2. ⭐ A REFERENCE CYCLE delays it until the cyclic collector runs (Day 027).
⭐  3. ⭐ An exception inside __del__ is IGNORED (printed to stderr, swallowed).
⭐  4. ⭐ At interpreter shutdown, module globals may already be None ⇒ AttributeError.
⭐  5. ⭐⭐ A traceback stored anywhere keeps every local in every frame alive — including yours.
⭐
⭐ ⇒ ⭐⭐ THE ANSWER IS ALWAYS `with`. Context managers close on EVERY path, including exceptions.
⭐   ⇒ ⭐⭐ and this is exactly Day 008's CLOSE_WAIT bug, arriving from the language side.
```

⭐⭐ **The line to say in an interview: "`__del__` is a finaliser, not a destructor — the only
guaranteed cleanup in Python is a context manager."** ⭐ Use `__del__` at most as a *warning* — log
that something was not closed properly — never as the mechanism.

## ⭐⭐ 2. Fork and copy-on-write — the memory bug in every worker pool

```
⭐⭐ THE SETUP: gunicorn --preload, or Celery, or multiprocessing fork.
⭐   The parent loads a 2 GB model / lookup table, then forks 8 workers.
⭐   ⇒ ⭐ the OS uses COPY-ON-WRITE: the pages are SHARED until someone writes.
⭐   ⇒ ⭐⭐ EXPECTED: 2 GB total.  ACTUAL: creeping toward 16 GB.
⭐
⭐⭐ WHY: ⭐⭐ merely READING a Python object INCREFs it — which WRITES to the object header —
⭐        which is a write to that memory page — ⭐⭐ which triggers a copy-on-write copy.
⭐   ⇒ ⭐⭐ TOUCHING an object copies its page. Reading is a write, in CPython.
```

⭐ **The mitigation:** `gc.freeze()` after loading and before forking (it moves existing objects to a
permanent generation so the cyclic collector does not touch their headers either), keeping large data
in `numpy`/`array`/`mmap` buffers where the *payload* has no per-element refcount, or simply not
sharing via fork. ⭐⭐ **The point for you is to recognise the symptom: worker memory that grows to
N × the parent's, with no leak in your code.**

## ⭐ 3. It is half of why the GIL exists

```
⭐⭐ ob_refcnt is a plain integer, incremented and decremented on EVERY object touch.
⭐   ⇒ with real thread parallelism, two threads INCREF the same object simultaneously
⭐     ⇒ ⭐⭐ a lost update ⇒ the count is too low ⇒ ⭐⭐ the object is freed while in use
⭐     ⇒ use-after-free — a crash, or silent corruption.
⭐   ⇒ making every refcount atomic would cost ~2× on single-threaded code.
⭐   ⇒ ⭐⭐ THE GIL is the cheap answer: one lock, so refcounts never race. (Day 065.)
```

⭐⭐ **This is the answer that separates a real GIL explanation from the memorised one.** "The GIL
exists because reference counting is not thread-safe and making it atomic would slow down the
common case" — ⭐ and Python 3.13's free-threaded build is precisely the project of making that
trade differently (biased reference counting and deferred counting), which is why it is hard and why
it took twenty years.

# Part 3 — ⭐ `weakref` — referring without owning

```python
import weakref

class Node: pass
n = Node()
r = weakref.ref(n)        # ⭐⭐ does NOT increment the refcount
r()                       # the object
del n
r()                       # ⭐⭐ None — the object died, the weakref knows
```

| ⭐ Use `weakref` for | ⭐ Why |
|---|---|
| ⭐⭐ **Caches** | ⭐ `WeakValueDictionary` — entries vanish when nothing else needs them |
| ⭐ Back-pointers (child → parent) | ⭐⭐ breaks the cycle, so refcounting alone can free the tree |
| Observers / callbacks | a listener should not keep the subject alive |

⭐ **Not everything is weak-referenceable** — `list`, `dict`, `int` and `str` are not, because they
have no slot for it. Your own classes are, unless they use `__slots__` without `__weakref__`
(Day 028).

# Part 4 — ⭐ Seeing it, and finding leaks

```python
import sys, gc, tracemalloc

sys.getrefcount(obj)              # ⭐ remember: minus one
gc.get_referrers(obj)             # ⭐⭐ WHO is keeping this alive — the leak-hunting tool
gc.get_referents(obj)             # ⭐ what it points at

tracemalloc.start()
snap1 = tracemalloc.take_snapshot()
...                               # ⭐ run the suspect work
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:10]:
    print(stat)                   # ⭐⭐ allocation growth BY SOURCE LINE
```

```
⭐⭐ "MY PYTHON SERVICE LEAKS MEMORY" — the four real causes, in order of frequency:
⭐  1. ⭐⭐ AN UNBOUNDED CACHE OR LIST that only grows (a dict keyed by request id, a global list)
⭐  2. ⭐ A REFERENCE CYCLE with heavy contents (Day 027 handles it — but late, and in bursts)
⭐  3. ⭐⭐ A LOGGED/STORED TRACEBACK — it holds every frame, and every frame's locals
⭐  4. ⭐ A C EXTENSION with a genuine refcount bug (rare, and not yours to fix)
⭐
⭐ ⇒ ⭐⭐ NOTE: (1) is not a leak in the GC sense at all — the objects ARE reachable.
⭐      ⇒ ⭐⭐ "Python has a GC so I cannot leak" is false. You can always leak by REMEMBERING.
```

⚠️ ⭐ **Freed memory does not always return to the OS.** CPython's allocator keeps arenas of small
objects; RSS can stay high after the objects are gone. **A flat-but-high RSS after a spike is normal;
a monotonically rising one is your bug.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Cleanup in `__del__`** | ⭐⭐ Unreliable on five counts. Use `with`. |
| Reading `getrefcount` literally | ⭐ Subtract one for the call's own reference. |
| Assuming refcounting is the whole GC | ⭐ Cycles need the collector (Day 027). |
| ⭐ Expecting fork+COW to save memory | ⭐⭐ Reading INCREFs, which writes the page, which copies it. |
| Thinking a GC prevents leaks | ⭐⭐ An unbounded cache is reachable and unbounded. |
| Not knowing why the GIL exists | ⭐⭐ Non-atomic refcounts are half the reason. |
| Expecting RSS to drop after `del` | ⭐ The allocator keeps arenas. |
| Strong references in a cache | ⭐ `WeakValueDictionary` for identity caches. |
| Storing exception objects | ⭐⭐ They pin every frame and every local. |

## Interview questions

**Q: How does CPython manage memory?**
> Primarily reference counting: every object header carries a count, which is incremented when a
> reference is created and decremented when one goes away, and the object is deallocated the moment
> it reaches zero. That's deterministic — the memory is freed on the exact line that drops the last
> reference, not at some later collection. On top of that there's a generational cyclic collector,
> because refcounting alone can't free reference cycles.

**Q: What's the trade-off versus a tracing collector?**
> Reference counting gives immediate, predictable destruction and no pause times, at the cost of
> touching a counter on every single object operation — which is real overhead, prevents naive
> multithreading, and can't handle cycles. Tracing collectors have no per-operation cost and handle
> cycles naturally, but free objects at unpredictable times and introduce pauses. CPython took the
> deterministic side and then bolted a cycle collector on for the case refcounting can't cover.

**Q: Why shouldn't you use `__del__` to close resources?**
> Because none of its guarantees are strong enough. It's an implementation detail of CPython — on
> PyPy the object is collected whenever the tracing GC runs. A reference cycle delays it until the
> cyclic collector runs. Exceptions inside it are swallowed. At interpreter shutdown the globals it
> needs may already be gone. And anything that captures a traceback keeps the object alive
> indefinitely. Context managers close on every path including exceptions, which is why `with` is the
> answer — and it's the same discipline that prevents sockets piling up in `CLOSE_WAIT`.

**Q: You fork eight workers after loading a 2GB model and memory goes to 16GB. Why?**
> Copy-on-write doesn't help, because reading a Python object increments its reference count, and
> that's a write into the object header — so touching the shared pages copies them. Within minutes
> each worker has privately copied most of what it walks over. Mitigations are `gc.freeze()` before
> forking, keeping the bulk data in NumPy arrays or memory-mapped buffers where the payload has no
> per-element refcounts, or not sharing by fork at all.

**Q: How is reference counting related to the GIL?**
> Reference counts are ordinary non-atomic integers updated on every object access. With true thread
> parallelism two threads could increment the same counter concurrently and lose an update, which
> eventually frees a live object — a use-after-free. Making every refcount atomic would roughly
> double the cost of single-threaded code, so CPython took a single global lock instead. That's why
> removing the GIL is so hard, and what the free-threaded build in 3.13 is actually solving.

**Q: How would you investigate a service whose memory grows steadily?**
> `tracemalloc` with two snapshots compared by line, which attributes allocation growth to source
> lines. Then `gc.get_referrers` on a sample of the growing objects to find out what's holding them.
> In practice the answer is usually not a GC failure at all — it's an unbounded cache, a global list,
> or stored exception objects pinning frames. Everything reachable is by definition not garbage, so
> "we have a garbage collector" doesn't protect you from remembering too much.
