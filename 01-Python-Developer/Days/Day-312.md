# Part 2 — ⭐⭐ 5–10: entities, and the two request types

```
⭐⭐ NOUNS ⇒ elevator · floor · request · button · door ·
⭐   direction · controller
⭐   ⭐ `Floor` ⇒ ⭐ an `int`. Not a class.
⭐   ⭐ `Button` ⇒ ⭐⭐ NOT MODELLED — it is where a request
⭐        comes from, like an entrance (Day 311).
⭐   ⭐ `Door` ⇒ ⭐ a state on the car, not an object.
⭐   ⭐ `Direction` ⇒ enum {UP, DOWN, IDLE}

⭐⭐ THE DISTINCTION THAT CARRIES THE DESIGN:
⭐   ⭐ ⭐⭐ HALL REQUEST — (floor, direction). "Someone at
⭐        floor 7 wants to go DOWN." ⭐⭐ ANY CAR CAN SERVE IT,
⭐        so it belongs to the ***SYSTEM***.
⭐   ⭐ ⭐⭐ CAR REQUEST — (car, floor). "Someone inside car 2
⭐        pressed 12." ⭐ Only that car can serve it, so it
⭐        belongs to the ***CAR***.
⭐   ⇒ ⭐⭐ CONFLATING THEM IS THE COMMONEST MODELLING ERROR
⭐     HERE, AND IT MAKES SCHEDULING IMPOSSIBLE TO EXPRESS —
⭐     because you cannot reassign a request that was never
⭐     system-owned.

⭐⭐ WHAT SURVIVES: `ElevatorCar` · `HallRequest` ·
⭐   `Controller` · `SchedulingStrategy` (Protocol)
```

# Part 3 — ⭐⭐ Who is in charge

```
⭐⭐ TWO ARCHITECTURES. NAME BOTH, PICK ONE, SAY WHY:

⭐ ⓐ ⭐ CENTRAL CONTROLLER — owns all hall requests, assigns
⭐      them to cars; cars are state machines that move.
⭐      ⭐ + one place to change scheduling, easy to test
⭐      ⭐ − the controller knows every car's internals
⭐ ⓑ ⭐ BIDDING — the controller broadcasts a hall request; each
⭐      car returns a COST; lowest cost wins.
⭐      ⭐⭐ + THE CAR OWNS ITS OWN COST FUNCTION, WHICH IS THE
⭐        ONLY THING THAT KNOWS ITS DIRECTION, LOAD AND QUEUE —
⭐        so no state leaks to the controller.
⭐      ⭐ − harder to reason about globally

⭐ ⇒ ⭐⭐ CHOOSE ⓑ AND SAY THE REASON: the information needed to
⭐   score a request lives ***in the car***, so ⓐ forces the
⭐   controller to reach inside every car — ⭐ which is Day 302's
⭐   anaemic-domain failure, in a scheduler.
⭐   ⭐ And it is the same shape as a load balancer asking
⭐     backends for their queue depth rather than guessing.
```

# Part 4 — ⭐⭐ 10–30: the state machine and the code

```
⭐⭐ THE CAR IS A STATE MACHINE (Days 254, 309):
⭐   IDLE ──assign──► MOVING_UP / MOVING_DOWN
⭐   MOVING ──arrive──► DOORS_OPEN ──timeout──► IDLE or MOVING
⭐   ⭐⭐ ILLEGAL: MOVING_UP → MOVING_DOWN WITHOUT STOPPING.
⭐     ⭐ Draw it and that transition's absence is the design.
```

```python
class Direction(Enum): UP = 1; DOWN = -1; IDLE = 0

@dataclass
class ElevatorCar:
    id: int
    floor: int = 0
    direction: Direction = Direction.IDLE
    _stops: set[int] = field(default_factory=set)   # ⭐ a SET: dedupe free

    def cost_for(self, req: HallRequest) -> float | None:
        """⭐⭐ None = CANNOT SERVE. Not a huge number —
           'cannot' and 'expensive' are different answers."""
        d = abs(self.floor - req.floor)
        if self.direction is Direction.IDLE:
            return d
        moving_toward = (req.floor - self.floor) * self.direction.value > 0
        if moving_toward and req.direction is self.direction:
            return d                       # ⭐⭐ ON THE WAY: cheapest
        return d + len(self._stops) * 2     # ⭐ must finish current sweep

    def add_stop(self, floor: int) -> None:
        self._stops.add(floor)
        if self.direction is Direction.IDLE:
            self.direction = (Direction.UP if floor > self.floor
                              else Direction.DOWN if floor < self.floor
                              else Direction.IDLE)

    def step(self) -> None:                 # ⭐ one tick
        if not self._stops:
            self.direction = Direction.IDLE; return
        if self.floor in self._stops:
            self._stops.discard(self.floor); self._open_doors(); return
        self.floor += self.direction.value
```

```python
class Controller:
    def request(self, req: HallRequest) -> ElevatorCar:
        bids = [(c.cost_for(req), c) for c in self._cars]
        viable = [(cost, c) for cost, c in bids if cost is not None]
        if not viable:
            raise NoCarAvailable(req)       # ⭐ not None (Day 308)
        cost, car = min(viable, key=lambda b: (b[0], b[1].id))  # ⭐⭐ TIEBREAK
        car.add_stop(req.floor)
        return car
```

```
⭐⭐ FOUR SCORED DETAILS:
⭐   ⭐ `cost_for` RETURNING `None` FOR "CANNOT" — ⭐ a
⭐     maintenance-mode car returning 999999 gets picked when
⭐     every car is busy.
⭐   ⭐ ⭐⭐ THE TIEBREAK ON `car.id` — without it, `min` picks
⭐     by dict order and the simulation is not reproducible,
⭐     which makes every test flaky (Day 261).
⭐   ⭐ A `set` OF STOPS — pressing 7 twice is one stop, free.
⭐   ⭐ `step()` AS ONE TICK — ⭐⭐ TIME IS AN INPUT (Day 254),
⭐     so the whole system is testable with no sleeping.
```

# Part 5 — ⭐⭐ 30–40: the hard parts

```
⭐⭐ ① STARVATION. ⭐ Floor 15 keeps losing bids because cars
⭐     stay busy in the lobby. ⭐⭐ NOTHING IN THE COST FUNCTION
⭐     PREVENTS A REQUEST WAITING FOREVER.
⭐   ⇒ ⭐ Age the request: `cost -= waiting_seconds * k`, ⭐⭐ OR
⭐     A HARD RULE — any request older than N seconds is assigned
⭐     to the next free car regardless of cost. ⭐ Naming
⭐     starvation unprompted is a strong signal.

⭐⭐ ② REASSIGNMENT. ⭐ A car is assigned, then breaks down or a
⭐     closer car frees up. ⭐⭐ BECAUSE HALL REQUESTS ARE
⭐     SYSTEM-OWNED (Part 2), REASSIGNMENT IS POSSIBLE — ⭐ if
⭐     you had put them in the car, it would not be.

⭐⭐ ③ CONCURRENCY (Day 310). ⭐ Shared mutable state is
⭐     `_stops` and the pending-request set. ⭐ Invariant: a
⭐     hall request is assigned to exactly one car.
⭐   ⇒ ⭐⭐ THE CLEAN ANSWER IS NOT A LOCK: ***MAKE THE
⭐     CONTROLLER A SINGLE CONSUMER OF A REQUEST QUEUE***
⭐     (Day 310) — one thread makes all assignments, cars only
⭐     execute. ⭐ No shared mutation, so no lock.
⭐   ⇒ ⭐ At multi-process scale the queue becomes a real queue
⭐     and assignment becomes a conditional UPDATE.

⭐⭐ ④ DIRECTION IS PART OF THE REQUEST. ⭐ Someone at floor 7
⭐     going DOWN should not be picked up by a car going UP —
⭐     ⭐⭐ THE COST FUNCTION ALREADY ENCODES THIS, AND
⭐     CANDIDATES WHO MODELLED A HALL REQUEST AS JUST A FLOOR
⭐     CANNOT EXPRESS IT AT ALL.
```

# Part 6 — ⭐ Extensions they ask

```
⭐   ⭐ "EXPRESS ELEVATOR, FLOORS 10–15 ONLY" ⇒ ⭐ `cost_for`
⭐     returns `None` outside its range. ⭐⭐ NOTHING ELSE
⭐     CHANGES — which is the payoff of returning `None`.
⭐   ⭐ "FIRE MODE" ⇒ ⭐ a car state, plus the controller
⭐     excluding it. ⭐ A state machine transition, not a flag.
⭐   ⭐ "WEIGHT LIMIT" ⇒ `cost_for` returns `None` when full.
⭐   ⭐ "PRIORITISE THE LOBBY IN THE MORNING" ⇒ ⭐⭐ A DIFFERENT
⭐     `SchedulingStrategy`, chosen by time — ⭐ the strategy
⭐     interface earning its keep, ⭐ but only because question
⭐     ② said we optimise wait time.
⭐ ⇒ ⭐ CLOSE: three tests (starvation, reassignment,
⭐   reproducibility); one change (age-based priority); ⭐⭐ AT
⭐   100×: bidding is O(cars) per request and fine, but the
⭐   single-consumer controller becomes the bottleneck — shard
⭐   by building.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Not asking one car or several | One is a state machine, several is a scheduling problem. |
| Conflating hall and car requests | Hall requests are system-owned; conflating them makes reassignment impossible. |
| Modelling `Button`, `Door`, `Floor` as classes | A request source, a state, and an int. |
| A central controller reading car internals | The cost information lives in the car — that's the anaemic domain in a scheduler. |
| Returning a huge number for "cannot serve" | It gets picked when everything is busy. Return `None`. |
| No tiebreak in `min` | The simulation isn't reproducible and every test is flaky. |
| A list of stops | A set dedupes a double press for free. |
| Real time instead of a `step()` tick | You can't test without sleeping. |
| No starvation handling | Nothing in a cost function stops a request waiting forever. |
| Ignoring request direction | A car going up shouldn't collect someone going down. |
| Reaching for locks | One controller consuming a queue means no shared mutation at all. |
| An express car handled with an `if` in the controller | It's `None` from `cost_for`, and nothing else changes. |

## Interview questions

**Q: What's the core design decision?**

> Who's in charge. Either a central controller that assigns hall requests to cars, or cars that bid a
> cost and the cheapest wins. I choose bidding, because the information needed to score a request —
> direction, current queue, load, whether the floor is even reachable — lives inside the car. A
> central scheduler has to reach into every car to get it, which is the anaemic domain problem showing
> up in a scheduler. It's the same shape as a load balancer asking backends for their queue depth
> rather than guessing.

**Q: Why separate hall and car requests?**

> Because they have different owners. A hall request — floor seven, going down — can be served by any
> car, so it belongs to the system and can be reassigned if a car breaks down or a closer one frees
> up. A car request is a button pressed inside one car and only that car can serve it. Candidates who
> model a single `Request` type can't express reassignment at all, and they usually also drop the
> direction, which means a car going up will happily collect someone who wants to go down.

**Q: What stops a floor being starved?**

> Nothing in the cost function, which is the point — a purely cost-minimising scheduler will let the
> top floor wait indefinitely while cars stay busy near the lobby. So either age the request,
> subtracting from its cost as it waits, or add a hard rule that any request older than a threshold
> goes to the next free car regardless of cost. I'd mention it unprompted, because starvation is the
> failure mode this problem is really testing for.

**Q: Two requests arrive simultaneously.**

> The shared mutable state is the pending request set and each car's stops; the invariant is that a
> hall request is assigned to exactly one car. Rather than locking, I'd make the controller a single
> consumer of a request queue — one thread makes all assignments and cars only execute them — so
> there's no shared mutation to protect. At multi-process scale that queue becomes a real queue and
> assignment becomes a conditional update whose rowcount decides the winner.

## 🎙️ Articulation drill

**Two minutes.** Lead with the decision: **who is in charge** — central control or bidding — and pick
bidding because **the information needed to score a request lives inside the car**, so a central
scheduler has to reach into every car's internals. Then the modelling point that most candidates miss:
**hall requests and car requests have different owners**, which is what makes reassignment possible
and what preserves direction. Show the state machine, note that `MOVING_UP → MOVING_DOWN` doesn't
exist, and mention `step()` so time is an input. Then the failure mode this problem is really about:
**a cost-minimising scheduler starves the top floor**, fixed by ageing requests or a hard deadline.
Close on concurrency without a lock — **one controller consuming a queue, cars only executing** — and
on the express car being a `None` from `cost_for` with nothing else changing.
