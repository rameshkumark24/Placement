# Part 1 — ⭐⭐ `heapq`

```python
import heapq

h = []
heapq.heappush(h, 5); heapq.heappush(h, 1)   # ⭐ O(log n)
heapq.heappop(h)                             # ⭐⭐ 1 — the SMALLEST. O(log n)
h[0]                                         # ⭐ peek — O(1)
heapq.heapify(lst)                           # ⭐⭐ in place, O(n) — NOT O(n log n)
heapq.heappushpop(h, x)                      # ⭐ push then pop — cheaper than doing both
heapq.heapreplace(h, x)                      # ⭐ pop then push
heapq.nlargest(k, it, key=...)               # ⭐ O(n log k)
heapq.merge(*sorted_iterables)               # ⭐⭐ LAZY merge of sorted streams — constant memory
```

```
⭐⭐ IT IS A BINARY HEAP IN A PLAIN LIST — no node objects, no pointers:
⭐   children of i are at 2i+1 and 2i+2; the parent of i is at (i-1)//2
⭐   the invariant is only h[i] <= h[2i+1], h[2i+2]  ⇒ ⭐⭐ the list is NOT sorted, only heapified.
⭐   ⇒ ⭐ printing a heap looks wrong. It is not. Only h[0] is guaranteed.
⭐
⭐⭐ heapify IS O(n), and this surprises people: the bottom half of the array are leaves and
⭐   need no work, and the sift-down cost falls geometrically as you go up. Worth saying.
```

⚠️ ⭐⭐ **`heapq` is a MIN-heap only. There is no `maxheap` parameter.**

```python
# ⭐⭐ THE THREE MAX-HEAP OPTIONS — say which you chose and why:
heapq.heappush(h, -x)          # ⭐⭐ negate on the way in, negate on the way out. Numbers only.
heapq._heapify_max(lst)        # ⚠️ ⭐ private. Do not.
heapq.nlargest(k, items)       # ⭐ when you only need the top k, not a live heap
```

## ⭐⭐ The two patterns worth memorising

```python
# ⭐⭐ PATTERN 1 — "k largest": a MIN-heap of size k. Counter-intuitive, and the point of the problem.
h = []
for x in stream:
    heapq.heappush(h, x)
    if len(h) > k: heapq.heappop(h)     # ⭐⭐ evict the SMALLEST ⇒ h holds the k largest
# ⇒ ⭐ O(n log k) time, O(k) memory ⇒ works on a stream you cannot fit in RAM.

# ⭐⭐ PATTERN 2 — priority queue with a tie-breaker:
import itertools
counter = itertools.count()
heapq.heappush(pq, (priority, next(counter), task))    # ⭐⭐ the counter is NOT optional
```

⚠️ ⭐⭐ **The tie-breaker is the trap.** Heap entries are compared as tuples, so when two priorities
are equal Python compares the *next* element — and if that is your task object, you get
`TypeError: '<' not supported between instances of 'Task' and 'Task'`. **It only fails when
priorities collide, so it passes your test and crashes in production.** A monotonic counter also
gives you FIFO ordering within a priority, which is usually what you wanted anyway.

⭐ **Where heaps are the right answer:** top-k, merging sorted streams, Dijkstra and A*, task
schedulers, rate limiters, "next event" simulation, and median maintenance (two heaps).

# Part 2 — ⭐ `bisect`

```python
import bisect
a = [1, 3, 3, 5, 7]

bisect.bisect_left(a, 3)     # ⭐ 1 — the FIRST position where 3 could go
bisect.bisect_right(a, 3)    # ⭐ 3 — the LAST such position  (alias: bisect)
bisect.insort(a, 4)          # ⭐⭐ insert keeping sorted order
bisect.bisect_left(a, x, key=attrgetter("age"))   # ⭐ 3.10+
```

```
⭐⭐ THE MENTAL MODEL: bisect_left  ⇒ "how many elements are strictly LESS than x"
⭐                    bisect_right ⇒ "how many elements are ≤ x"
⭐   ⇒ ⭐⭐ count of x   = bisect_right(a,x) - bisect_left(a,x)
⭐   ⇒ ⭐ contains x    = i < len(a) and a[bisect_left(a,x)] == x
⭐   ⇒ ⭐⭐ "first element ≥ x" = a[bisect_left(a, x)]   ⇒ THE LOWER-BOUND QUERY
```

⚠️ ⭐⭐ **`insort` is O(n), not O(log n).** The *search* is logarithmic; the *insertion* shifts every
later element (Day 033). **So maintaining a sorted list by repeated `insort` is O(n²)** — for many
insertions, sort once at the end, or use a heap, or reach for `sortedcontainers`
(third-party, but the standard answer for a genuinely sorted mutable structure).

```python
# ⭐ The classic non-obvious use — bucketing by threshold:
GRADES = "FDCBA"
BREAKS = [60, 70, 80, 90]
GRADES[bisect.bisect(BREAKS, score)]      # ⭐⭐ no if/elif chain, O(log n)
```

⭐⭐ **`bisect` is also how you do weighted random selection**: build a cumulative-weight list once,
then `bisect` a uniform random number into it — O(log n) per draw instead of O(n).

# Part 3 — ⭐ `array`, and the numeric ladder

```python
from array import array
a = array("q", range(1_000_000))   # ⭐⭐ 8 MB contiguous — vs ~36 MB for a list (Day 028)
a[0]; a.append(5); a.tobytes()
```

| Typecode | Type |
|---|---|
| `b`/`B` | signed/unsigned char |
| `i`/`I` | int (2 or 4 bytes) |
| ⭐ `q`/`Q` | ⭐ signed/unsigned long long (8 bytes) |
| `f`/`d` | float / double |

```
⭐⭐ THE LADDER — pick the lowest rung that solves your problem:
⭐   list            ⇒ anything, any type            — ⭐ pointers, 28 B per int
⭐   array           ⇒ ⭐ millions of same-type numbers, contiguous, stdlib, no dependency
⭐   ⭐⭐ numpy        ⇒ ⭐⭐ arrays + VECTORISED C OPERATIONS ⇒ the real win (Day 028)
⭐   ⭐ memoryview    ⇒ a ZERO-COPY view over a buffer — slice bytes without copying them
⭐   bytes/bytearray ⇒ raw binary
```

⚠️ ⭐ **`array` gives you the memory win but *not* the speed win** — iterating it in Python still
boxes each element into an `int` object. **NumPy is where the loop itself moves into C**, which is
the point Day 028 made and the reason `array` is a niche tool while NumPy is an ecosystem.

⭐ **`memoryview` is worth knowing for backend work:** `data[1024:]` on a large `bytes` copies;
`memoryview(data)[1024:]` does not. **In a protocol parser or file processor that is the difference
between linear and quadratic memory traffic.**

# Part 4 — ⭐ Choosing the structure

| ⭐ The question | ⭐⭐ The structure | ⭐ Cost |
|---|---|---|
| "Have I seen this?" | ⭐⭐ `set` | O(1) |
| "What is the value for this key?" | `dict` | O(1) |
| "Queue / stack" | ⭐⭐ `deque` | O(1) both ends |
| ⭐⭐ **"Smallest / largest, repeatedly"** | ⭐⭐ **`heapq`** | O(log n) |
| ⭐ "Top k of a huge stream" | ⭐⭐ min-heap of size k | O(n log k), O(k) memory |
| "Where does x belong in sorted data?" | ⭐ `bisect` | O(log n) |
| "Which bucket does x fall in?" | `bisect` on breakpoints | O(log n) |
| "How many times?" | `Counter` | O(n) |
| "Millions of numbers" | `array` / NumPy | memory, then speed |
| "Sorted, and mutated often" | ⭐ `sortedcontainers` | O(log n) insert |

⭐⭐ **In an interview, name the structure and its cost before you write anything** — "this is a
top-k problem, so a min-heap of size k, O(n log k) time and O(k) space" is worth more than the
implementation, and it is Day 466's protocol applied to a data-structure choice.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Expecting a max-heap** | ⭐⭐ `heapq` is min-only. Negate, or `nlargest`. |
| ⭐⭐ **No tie-breaker in a priority queue** | ⭐⭐ `TypeError` when priorities collide — passes tests, fails live. |
| Assuming a heap is sorted | ⭐ Only `h[0]` is guaranteed. |
| Thinking `heapify` is O(n log n) | ⭐ It is O(n). |
| Using a max-heap of size k for "k largest" | ⭐⭐ You want a **min**-heap of size k. |
| Sorting to get the top 10 of a million | ⭐ `nlargest` — O(n log k). |
| ⭐ `insort` in a loop | ⭐⭐ O(n) per insert ⇒ O(n²). |
| `bisect` on an unsorted list | ⭐ Silent nonsense — it assumes sorted. |
| Confusing `bisect_left`/`right` | ⭐ Less-than vs less-or-equal. |
| Expecting `array` to be fast | ⭐⭐ Memory win only. NumPy for speed. |
| Slicing large `bytes` repeatedly | ⭐ `memoryview` — zero copy. |

## Interview questions

**Q: How do you find the top k elements of a very large stream?**
> A min-heap of size k. Push each element; if the heap exceeds k, pop the smallest. The heap then
> holds the k largest seen so far, and the root is the current cut-off. That's O(n log k) time and —
> more importantly — O(k) memory, so it works on a stream that doesn't fit in RAM. The
> counter-intuitive part is that "k largest" wants a *min*-heap, because the thing you need cheap
> access to is the smallest of your current best, so you can evict it.

**Q: What does `heapq` actually give you?**
> A binary heap stored in a plain list, using index arithmetic rather than node objects — children at
> 2i+1 and 2i+2. The invariant is only parent ≤ children, so the list isn't sorted and printing it
> looks wrong; only element zero is guaranteed. Push and pop are O(log n), peek is O(1), and
> `heapify` is O(n) rather than O(n log n), because the bottom half are leaves and the sift-down cost
> falls geometrically as you move up.

**Q: What's the trap with a priority queue in Python?**
> Ties. Entries are compared as tuples, so when two priorities are equal Python moves on to the next
> element — and if that's your task object, it raises `TypeError` because the object has no ordering.
> The nasty part is that it only fails when priorities collide, so it passes tests and breaks in
> production. Pushing `(priority, next(counter), item)` with a monotonic counter fixes it and gives
> FIFO ordering within a priority, which is usually the intended behaviour anyway.

**Q: When would you use `bisect`?**
> Any question about position in sorted data: does this exist, how many are less than x, what's the
> first element at or above x, which bucket does this value fall in. That last one replaces an
> if/elif chain of thresholds with an O(log n) lookup, and it's also how weighted random selection
> works — bisect a uniform random number into a cumulative-weight array. The caveat is `insort`: the
> search is logarithmic but the insertion shifts the array, so it's O(n), and maintaining a sorted
> list by repeated insort is quadratic.

**Q: `list`, `array` or NumPy?**
> A list for anything heterogeneous — it's an array of pointers, about 28 bytes per integer plus the
> pointer. `array` when I have millions of same-typed numbers and want them contiguous with no
> dependency, which is a memory win of roughly four times but not a speed win, because iterating it
> in Python still boxes every element. NumPy when I want the loop itself in C — that's where the
> order-of-magnitude comes from, and it's the same principle as every Python performance fix: move
> the loop out of the interpreter.

## 🎙️ Articulation drill

Record two minutes: **"Find the 100 most frequent words in a 50 GB log file."**

⭐ Two phases, and name the constraint before the algorithm: **the file does not fit in memory, so I
stream it.** ⭐ Counting is a `Counter` — or a plain dict — **which is bounded by the number of
*distinct* words, not by the file size, so that part fits even when the file does not.**

⭐ Then the selection: **`Counter.most_common(100)`, which internally is `heapq.nlargest` — a
min-heap of size 100, O(n log k) with O(k) memory** rather than sorting all distinct words at
O(n log n).

⭐⭐ **Then the follow-up you should raise yourself, because it is the real interview:** *"if the
distinct vocabulary also doesn't fit — say it's URLs or user IDs rather than English words — then the
counting phase is the problem, not the selection. At that point it's either a shard-and-merge job, or
a probabilistic structure like count-min sketch where I trade exactness for bounded memory. Naming
that boundary is more useful than the code."*
