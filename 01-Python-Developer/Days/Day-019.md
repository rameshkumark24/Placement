# Day 019

**L-019** · ⭐⭐ **Where state lives** — cookies, sessions, localStorage, sessionStorage, tokens
**C-13** · Network debugging — `ping`, `traceroute`, `dig`, `ss`, `curl -v`, `tcpdump`

**Time:** 3 hrs · **Mode:** NEW

> HTTP is stateless (Days 010, 016). So how does a site remember you are logged in?
>
> ⭐⭐ **The sentence to own: the client carries an identifier on every request, and the only design
> question is what that identifier means — a pointer to state on the server, or the state itself.**
> Every authentication scheme you will ever meet is one of those two, and each has one dominant
> weakness.

---

# Part 1 — ⭐⭐ Cookies

```http
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

⭐⭐ **A cookie is a string the server asks the browser to store and send back automatically on every
request to that domain.** That automatic resend is the whole feature — and the whole vulnerability
(CSRF, Part 4).

| ⭐ Attribute | ⭐⭐ What it does | ⭐⭐ Why it matters |
|---|---|---|
| ⭐⭐ **`HttpOnly`** | ⭐⭐ JavaScript **cannot read it** | ⭐⭐ **an XSS cannot steal the session** |
| ⭐⭐ **`Secure`** | HTTPS only | never sent in the clear |
| ⭐⭐ **`SameSite`** | ⭐ `Strict` / `Lax` / `None` | ⭐⭐ **the primary CSRF defence** |
| `Domain` / `Path` | scope | ⚠️ `Domain=.example.com` shares with **every** subdomain |
| `Max-Age` / `Expires` | lifetime | no expiry ⇒ session cookie, dies with the browser |

```
⭐⭐ SameSite, precisely:
⭐   Strict ⇒ never sent on ANY cross-site request ⇒ ⭐ following a link from email logs you out
⭐   ⭐⭐ Lax  ⇒ sent on top-level GET navigations only ⇒ ⭐⭐ THE MODERN DEFAULT, and it kills
⭐             classic CSRF, because a cross-site POST carries no cookie
⭐   None   ⇒ always sent ⇒ ⚠️ ⭐ REQUIRES Secure. This is what third-party cookies needed.
```

# Part 2 — ⭐⭐ The two designs

```
⭐⭐ (A) SERVER-SIDE SESSIONS — the cookie is a POINTER.
⭐   cookie: session=abc123  ──▶  Redis: "abc123" → {user_id: 5, roles: [...]}
⭐   ⭐ pro: ⭐⭐ REVOCATION IS INSTANT — delete the key and they are logged out. Now.
⭐   ⭐ pro: the client learns nothing; you can store as much as you like
⭐   ⭐ con: ⭐ a lookup per request, and a store you must run and keep available

⭐⭐ (B) TOKENS (JWT) — the cookie/header IS the state.
⭐   header.payload.signature — base64, ⭐⭐ SIGNED, NOT ENCRYPTED
⭐   ⭐ pro: ⭐ no lookup, no shared store ⇒ any service can verify it independently
⭐   ⭐ con: ⭐⭐ YOU CANNOT REVOKE IT. It is valid until it expires. That is the whole trade.
```

```python
# ⭐⭐ THE THING PEOPLE GET WRONG ABOUT JWTs: the payload is PUBLIC.
import base64, json
payload = json.loads(base64.urlsafe_b64decode(token.split(".")[1] + "=="))
# ⭐⭐ Anyone holding the token reads this. Signing proves it was not CHANGED.
# ⇒ ⚠️ ⭐⭐ NEVER put anything secret in a JWT.
```

```
⭐⭐ THE REVOCATION PROBLEM, AND THE STANDARD ANSWER:
⭐   User is banned at 10:00. Their JWT expires at 10:30.
⭐   ⇒ ⭐⭐ they remain fully authenticated for 30 minutes. There is no way to stop them.
⭐
⭐ ⭐⭐ THE FIX EVERYONE CONVERGES ON — and it is worth noticing what it is:
⭐   · SHORT-lived access token (5–15 min), kept in memory
⭐   · LONG-lived REFRESH token (days), ⭐⭐ stored server-side and therefore REVOCABLE
⭐   · refresh rotation: each use invalidates the old one ⇒ reuse detection
⭐ ⇒ ⭐⭐ NOTE WHAT HAPPENED: you reintroduced a server-side session for the refresh token.
⭐      ⇒ ⭐⭐ "stateless auth" ends up stateful at exactly the point where it must be.
```

⚠️ ⭐⭐ **The `alg: none` attack** — early JWT libraries honoured an algorithm field of `"none"` and
accepted an unsigned token. ⭐⭐ **Always specify the expected algorithm when verifying**
(`jwt.decode(token, key, algorithms=["HS256"])`) and never let the token choose. **A related attack
substitutes HS256 for RS256 so the public key is used as an HMAC secret.**

| | ⭐ Sessions | ⭐ JWT |
|---|---|---|
| ⭐⭐ **Revocation** | ⭐⭐ **instant** | ⭐⭐ **impossible until expiry** |
| Lookup per request | yes | no |
| Works across services | needs a shared store | ⭐ yes, with the public key |
| Size on the wire | tiny | ⭐ 300 B–1 KB, **every request** |
| ⭐ Right default for | ⭐⭐ **a normal web app** | ⭐ service-to-service, many APIs, mobile |

⭐⭐ **Say the default out loud in an interview: for one web application, a server-side session in
Redis with an `HttpOnly` cookie is simpler and strictly safer than a JWT.** JWTs won on fashion, not
on fit. The moment you need instant logout, "log out all devices", or a ban that takes effect *now*,
sessions already had it and JWTs need machinery.

# Part 3 — ⭐ Browser storage, and where a token must not go

| | ⭐ Sent automatically? | ⭐⭐ Readable by JS? | Lifetime |
|---|---|---|---|
| ⭐⭐ **Cookie (`HttpOnly`)** | ⭐ **yes** | ⭐⭐ **NO** | `Max-Age` |
| Cookie (normal) | yes | yes | `Max-Age` |
| ⭐ `localStorage` | ⭐ no | ⭐⭐ **yes** | forever |
| `sessionStorage` | no | ⭐ yes | that tab |
| In-memory JS variable | no | yes | ⭐ until reload |

```
⭐⭐ "WHERE DO I STORE THE JWT?" — the question, and the honest answer:

⭐ localStorage ⇒ ⚠️ ⭐⭐ ANY XSS reads it and exfiltrates it in one line.
⭐              ⇒ ⭐ but immune to CSRF, because nothing sends it automatically.
⭐ HttpOnly cookie ⇒ ⭐⭐ XSS cannot read it
⭐              ⇒ ⚠️ ⭐ but it IS sent automatically ⇒ CSRF applies ⇒ needs SameSite (+ a token)

⭐⭐ THE ANSWER THAT IS ACTUALLY RIGHT:
⭐   access token in MEMORY (a JS variable — dies on reload, unreadable after the tab closes)
⭐   refresh token in an ⭐⭐ HttpOnly, Secure, SameSite=Lax COOKIE
⭐   ⇒ ⭐⭐ XSS cannot steal the refresh token; CSRF cannot use it, because refreshing
⭐        requires a POST that SameSite blocks cross-site.
```

⭐⭐ **And the framing that matters more than the choice: if you have XSS, you have lost.** An
attacker running JavaScript on your origin can simply *use* the session — issue requests as the user
— whether or not they can read the token. **`HttpOnly` raises the cost; it does not save you.** The
real defence is Day 012's output escaping.

# Part 4 — ⭐ CSRF, in one page

```
⭐⭐ THE ATTACK — and it depends ENTIRELY on cookies being sent automatically:
⭐   1. You are logged into bank.com. Your session cookie sits in the browser.
⭐   2. You visit evil.com, which contains:
⭐        <form action="https://bank.com/transfer" method="POST" id="f">
⭐          <input name="to" value="attacker"><input name="amount" value="10000">
⭐        </form><script>f.submit()</script>
⭐   3. ⭐⭐ The browser sends your cookie. bank.com sees a fully authenticated request.
⭐
⭐⭐ NOTE: the attacker never READS anything (the same-origin policy stops that — Day 020).
⭐   ⇒ ⭐⭐ CSRF is about CAUSING ACTIONS, not stealing data. That distinction is the exam answer.
```

| ⭐ Defence | ⭐ How |
|---|---|
| ⭐⭐ **`SameSite=Lax`** | ⭐⭐ browser refuses to send the cookie on a cross-site POST — **kills the classic attack** |
| ⭐ CSRF token | a random value in the form, checked server-side — ⭐ the attacker cannot read it |
| ⭐ Double-submit cookie | same value in a cookie and a header; ⭐ JS can set the header, a form cannot |
| ⭐⭐ Check `Origin`/`Referer` | cheap, effective for state-changing requests |
| ⭐ Not authenticating by cookie | ⭐⭐ an `Authorization` header is never sent automatically ⇒ **no CSRF** |

⭐⭐ **The last row is why pure API + bearer-token architectures do not have a CSRF problem** — and
also why they have an XSS-storage problem instead. **You are choosing which attack to defend
against, not escaping both.**

# Part 5 — C-13 · ⭐⭐ The debugging toolkit

| ⭐ Tool | ⭐ Answers |
|---|---|
| ⭐ `ping host` | is it reachable, and what is the RTT (Day 006) |
| ⭐ `traceroute host` | ⭐ where does the path break or slow down |
| ⭐⭐ `dig +trace name` | ⭐ the full DNS resolution (Days 007, 012) |
| ⭐⭐ `ss -tan` | ⭐⭐ connection states — **`CLOSE_WAIT` first** (Day 008) |
| ⭐⭐ `curl -v` / `-w` | ⭐⭐ the whole exchange, and **the latency breakdown** |
| ⭐ `openssl s_client` | the certificate chain (Day 009) |
| ⭐ `tcpdump -A port 8000` | ⭐ the actual bytes — the last resort that never lies |
| ⭐ `lsof -i :8000` | what is holding the port |
| `nc -zv host port` | is the port open at all |

```bash
# ⭐⭐ THE ONE COMMAND TO MEMORISE — "the site is slow", decomposed:
curl -w "dns:%{time_namelookup} conn:%{time_connect} tls:%{time_appconnect} \
ttfb:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s https://example.com
```

| ⭐ Big number | ⭐⭐ Blame |
|---|---|
| `dns` | resolver / TTL (Day 007) |
| `conn` | network path or the TCP handshake (Day 008) |
| `tls` | certificate chain / handshake (Day 009) |
| ⭐⭐ `ttfb` | ⭐⭐ **your application, or its database** — this is the number you own |
| `total − ttfb` | payload size or bandwidth |

```
⭐⭐ THE DIAGNOSTIC ORDER THAT SEPARATES A SENIOR ANSWER FROM A GUESS:
⭐   1. Is it DNS?        dig
⭐   2. Is it reachable?  ping / nc / traceroute
⭐   3. Is it TLS?        openssl s_client
⭐   4. ⭐⭐ Is it my app?  curl -w ⇒ ttfb   ⭐ ← usually yes, and you should say so first
⭐   5. Is it sockets?    ss -tan  ⇒ CLOSE_WAIT, TIME_WAIT
⭐   6. ⭐ Still lost?      tcpdump. The bytes do not have opinions.
⭐
⭐⭐ AND THE RULE FROM DAY 004 THAT ANSWERS HALF OF THESE:
⭐   ⭐⭐ TIMEOUT  ⇒ the packet was DROPPED (firewall, security group, wrong route)
⭐   ⭐⭐ REFUSED  ⇒ you REACHED the machine and nothing is listening on that port
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **JWT in `localStorage`** | ⭐⭐ Any XSS exfiltrates it. Memory + `HttpOnly` refresh cookie. |
| ⭐⭐ **Putting secrets in a JWT** | ⭐⭐ Signed, not encrypted. The payload is public. |
| Expecting to revoke a JWT | ⭐ You cannot. Short expiry + a revocable refresh token. |
| Session cookie without `HttpOnly` | ⭐⭐ One XSS and the session is gone. |
| Missing `Secure` / `SameSite` | ⭐ Plaintext transmission; CSRF. |
| ⭐ Not pinning the JWT algorithm | ⭐⭐ `alg: none` and RS256→HS256 confusion. |
| Sessions in a process dict | ⭐⭐ Day 016 — dies with multiple workers. Redis. |
| Thinking CSRF steals data | ⭐ It causes actions. Same-origin policy blocks reading. |
| "HttpOnly means XSS is fine" | ⭐⭐ XSS can act as the user regardless. |
| Guessing at "the site is slow" | ⭐⭐ `curl -w` decomposes it in one command. |
| Confusing timeout and refused | ⭐⭐ Dropped vs reached. Different investigations. |

## Interview questions

**Q: How does a stateless protocol support logged-in users?**
> The client re-presents an identifier on every request, normally in a cookie. The design question is
> what the identifier *is*: a pointer to state held server-side, or the state itself, signed. Sessions
> are the first; JWTs are the second. Everything else — where to store it, how to revoke it — follows
> from that choice.

**Q: Sessions or JWTs?**
> For a single web application, sessions — a random id in an `HttpOnly`, `Secure`, `SameSite=Lax`
> cookie, with the data in Redis. It's simpler, the client learns nothing, and revocation is instant,
> which matters the moment you need "log out all devices" or a ban that takes effect now. JWTs earn
> their place when many independent services must verify without a shared store, or for mobile and
> third-party API clients. And I'd point out that the standard JWT setup — short access token plus a
> long refresh token stored server-side — has quietly reintroduced a session for the refresh token,
> because revocation genuinely requires state.

**Q: Where do you store a JWT in a browser?**
> Access token in memory, refresh token in an `HttpOnly` cookie. `localStorage` is readable by any
> script on the origin, so an XSS exfiltrates it in one line and it persists forever. `HttpOnly`
> keeps the refresh token out of JavaScript's reach, and `SameSite=Lax` stops a cross-site POST from
> using it. The honest caveat is that if I have XSS, the attacker can just make requests as the user
> — `HttpOnly` raises the cost, it doesn't save me.

**Q: What is CSRF and what stops it?**
> An attacker's page causes the browser to send a state-changing request to my site, and the browser
> attaches the session cookie automatically, so it arrives fully authenticated. The attacker never
> reads the response — the same-origin policy prevents that — so it's about causing actions, not
> stealing data. `SameSite=Lax` is the primary defence now, because the browser simply won't attach
> the cookie to a cross-site POST; a CSRF token or an `Origin` check backs it up. APIs that
> authenticate with an `Authorization` header aren't vulnerable at all, because nothing is sent
> automatically.

**Q: `HttpOnly`, `Secure`, `SameSite` — what does each buy?**
> `HttpOnly` puts the cookie out of JavaScript's reach, so XSS can't read the session. `Secure`
> restricts it to HTTPS, so it never crosses the network in the clear. `SameSite` controls whether
> it's attached to cross-site requests: `Lax` sends it on top-level GET navigations only, which kills
> classic CSRF while keeping ordinary links working.

**Q: "The site is slow." What do you run?**
> `curl -w` with the timing breakdown — DNS, connect, TLS, time-to-first-byte, total — because it
> attributes the delay to a layer in one command. A large TTFB with everything else small means it's
> my application or its database, which is usually the answer and is worth saying first rather than
> blaming the network. Then `dig` if DNS was slow, `openssl s_client` if the handshake was, and
> `ss -tan` on the server to check the connection states — a growing `CLOSE_WAIT` is a leaked socket
> and diagnoses itself.

## 🎙️ Articulation drill

Record two minutes: **"Design authentication for a web app with a mobile client."**

⭐ Split it, and say why: **the web app uses a server-side session in an `HttpOnly`, `Secure`,
`SameSite=Lax` cookie**, because it is simpler, the browser handles it, and revocation is instant.
⭐⭐ **The mobile client uses a short-lived access token plus a rotating refresh token stored
server-side**, because there is no cookie jar and no CSRF surface — and because rotation gives you
reuse detection, which is how you notice a stolen refresh token at all.

⭐⭐ **Then the sentence that makes it a senior answer:** *"Note that the refresh token is server-side
state, so the 'stateless' design is stateful exactly where it has to be — revocation is not
achievable without state, and anyone who claims otherwise has not been asked to ban a user yet."*
