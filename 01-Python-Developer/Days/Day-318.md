# Part 1 — ⭐⭐ The logging framework: three axes

```
⭐⭐ THE MISTAKE: ONE `Logger` CLASS WITH `if level >= …`,
⭐   `if destination == "file"`, and a format string.
⭐   ⇒ ⭐ Adding a destination touches the same class as adding
⭐     a format, which touches the same class as filtering.

⭐⭐ THREE AXES, AND EACH VARIES INDEPENDENTLY — WHICH IS WHY
⭐   EACH IS ITS OWN INTERFACE:
⭐   ⭐ ⭐⭐ WHERE — Handler (console, file, syslog, HTTP)
⭐   ⭐ ⭐⭐ HOW    — Formatter (plain, JSON, key-value)
⭐   ⭐ ⭐⭐ WHETHER — Filter (by level, by module, by sampling)

⭐   ⇒ ⭐ You can write a JSON formatter and a syslog handler
⭐     independently, and combine them without either knowing
⭐     about the other. ⭐⭐ THAT IS THE TEST OF WHETHER THE
⭐     AXES ARE REALLY SEPARATE: ***CAN THEY BE WRITTEN BY TWO
⭐     PEOPLE WHO NEVER SPEAK?***

⭐ ⭐ AND SAY THE OBVIOUS THING: ⭐⭐ THIS IS EXACTLY PYTHON'S
⭐   `logging` MODULE — Logger, Handler, Formatter, Filter. ⭐
⭐   Recognising that the standard library already solved this,
⭐   and that you would use it, is a stronger answer than
⭐   reinventing it silently.
```

```python
@dataclass(frozen=True)
class Record:                     # ⭐⭐ A VALUE OBJECT (Day 304)
    level: Level
    message: str
    ts: float
    logger: str
    context: Mapping[str, Any]    # ⭐ structured fields (Day 285)

class Handler(Protocol):
    def emit(self, record: Record, text: str) -> None: ...
class Formatter(Protocol):
    def format(self, record: Record) -> str: ...
class Filter(Protocol):
    def allows(self, record: Record) -> bool: ...
```

# Part 2 — ⭐⭐ The four details that separate answers

```
⭐⭐ ① ***LEVEL CHECK BEFORE MESSAGE CONSTRUCTION.***
⭐   ⭐ `log.debug(f"user {expensive()}")` ⭐⭐ EVALUATES THE
⭐     f-STRING EVEN WHEN DEBUG IS OFF. ⭐ In a hot loop that is
⭐     the whole cost of logging you thought you disabled.
⭐   ⇒ ⭐ Lazy: `log.debug("user %s", user_id)`, formatted only
⭐     if the record survives filtering.

⭐⭐ ② ***A HANDLER MUST NEVER RAISE INTO THE APPLICATION.***
⭐   ⭐ Disk full, syslog down, HTTP endpoint 500.
⭐   ⇒ ⭐⭐ LOGGING FAILING MUST NOT TAKE DOWN THE THING IT IS
⭐     OBSERVING. ⭐ Swallow, count, and report the failure
⭐     through a different channel.

⭐⭐ ③ ***A NETWORK HANDLER MUST BE ASYNCHRONOUS AND BOUNDED.***
⭐   ⭐ A synchronous HTTP log handler adds its latency to every
⭐     request — ⭐⭐ AND WHEN THE LOG SERVICE IS SLOW, YOUR API
⭐     IS SLOW, WHICH IS AN OUTAGE CAUSED ENTIRELY BY
⭐     OBSERVABILITY.
⭐   ⇒ ⭐ A bounded queue plus a worker thread, ⭐⭐ AND A DROP
⭐     POLICY WHEN FULL, PLUS A COUNTER OF DROPPED RECORDS —
⭐     because an unbounded log queue is a memory leak with a
⭐     schedule (Day 268's backpressure lesson).

⭐⭐ ④ ***THREAD SAFETY AT THE HANDLER, NOT THE LOGGER.***
⭐   ⭐ Two threads writing to one file interleave mid-line.
⭐   ⇒ ⭐ Lock inside `emit`, keep it short.
```

# Part 3 — ⭐⭐ The notification service: the real design

```
⭐⭐ NOUNS ⇒ user · notification · channel · template ·
⭐   preference · schedule
⭐   ⭐ CHANNELS: email, SMS, push, in-app — ⭐ obviously a
⭐        strategy interface; ⭐⭐ AND THIS IS THE PART EVERYONE
⭐        BUILDS, WHICH IS WHY IT IS NOT WHAT DISTINGUISHES YOU.

⭐⭐ THE FOUR THINGS THAT ACTUALLY MATTER:
⭐   ① ⭐⭐ PREFERENCES AND CONSENT — per user, per category,
⭐        per channel. ⭐⭐ AND ***OPT-OUT IS A HARD RULE, NOT A
⭐        FILTER***: it is checked at send time, not at
⭐        composition time, because a notification queued three
⭐        days ago must respect an unsubscribe from yesterday.
⭐   ② ⭐⭐ DEDUPLICATION AND RATE LIMITING PER USER — ⭐ the
⭐        thing that stops a retry storm from sending forty
⭐        emails. ⭐ An idempotency key per (user, event) and a
⭐        per-user limiter (Day 314).
⭐   ③ ⭐ TEMPLATES WITH LOCALISATION — versioned, ⭐⭐ AND
⭐        RENDERED AT ***SEND*** TIME FROM AN ID PLUS DATA, NOT
⭐        STORED AS RENDERED TEXT (Day 265's IDs-not-objects).
⭐   ④ ⭐⭐ DELIVERY IS AT-LEAST-ONCE AND FALLIBLE — every
⭐        channel is a third-party call with three outcomes
⭐        (Day 263).
```

```python
class Channel(Protocol):
    name: str
    def send(self, to: Recipient, rendered: Rendered) -> DeliveryResult: ...
    def supports(self, recipient: Recipient) -> bool: ...   # ⭐ no phone → no SMS

@dataclass(frozen=True)
class NotificationRequest:
    user_id: UserId
    category: Category                  # ⭐⭐ THE UNIT OF CONSENT
    template_id: TemplateId
    data: Mapping[str, Any]
    idempotency_key: str                # ⭐⭐ (user, event), NOT a uuid4
```

```
⭐⭐ THE `idempotency_key` DETAIL IS THE ONE PEOPLE MISS:
⭐   ⭐ A freshly generated UUID per attempt ⭐⭐ MAKES THE KEY
⭐     USELESS — the retry has a different key and sends again.
⭐   ⇒ ⭐ It must be derived from the ***event***:
⭐     `f"{user_id}:{event_id}:{channel}"` (Day 265).
```

# Part 4 — ⭐⭐ The pipeline, in the order that matters

```
⭐⭐ REQUEST → ① DEDUPE → ② CONSENT → ③ RATE LIMIT →
⭐   ④ CHANNEL SELECTION → ⑤ RENDER → ⑥ SEND → ⑦ RECORD

⭐   ⭐ ⭐⭐ ORDER IS CORRECTNESS, NOT STYLE:
⭐     ⭐ Dedupe first — cheapest, and it stops everything else.
⭐     ⭐⭐ CONSENT ***BEFORE*** RENDER — rendering a template
⭐       for someone who unsubscribed wastes work and, if you
⭐       render with personal data, ⭐⭐ COPIES PII INTO A LOG
⭐       AND A QUEUE FOR A MESSAGE THAT MUST NOT BE SENT.
⭐     ⭐ Rate limit before send, not after.
⭐     ⭐ Record after send — including failures.

⭐⭐ CHANNEL SELECTION WITH FALLBACK, AND THE TRAP:
⭐   ⭐ "Push, and if it fails, SMS." ⇒ ⭐⭐ WHAT COUNTS AS
⭐     FAILURE? A rejected token is a real failure; ⭐⭐ A
⭐     TIMEOUT IS ***UNKNOWN***, AND FALLING BACK ON UNKNOWN
⭐     SENDS THE USER TWO NOTIFICATIONS (Day 263).
⭐   ⇒ ⭐ So: fall back only on ***definite*** failure, and treat
⭐     unknown as sent-pending with reconciliation via the
⭐     provider's delivery webhook.
```

# Part 5 — ⭐⭐ Extension without imagination

```
⭐⭐ THE QUESTION BOTH PROBLEMS ARE REALLY ASKING: HOW DO YOU
⭐   MAKE IT EXTENSIBLE WITHOUT GOLD-PLATING (Day 308)?

⭐⭐ THE RULE (Day 298): ***AN INTERFACE PER AXIS THAT HAS
⭐   ALREADY VARIED, OR THAT THE REQUIREMENTS SAY WILL.***
⭐   ⭐ Channels ⇒ ⭐ yes: there are already four.
⭐   ⭐ Templates ⇒ ⭐ yes: localisation was stated.
⭐   ⭐⭐ A PLUGGABLE "DELIVERY STRATEGY ENGINE" ⇒ ***NO.***
⭐     ⭐ Nobody asked, there is one implementation, and it is a
⭐       cost with no purchase.
⭐   ⇒ ⭐⭐ AND SAY THE REJECTION OUT LOUD: "I'M ***NOT***
⭐     ABSTRACTING SCHEDULING, BECAUSE THERE IS ONE RULE AND I'D
⭐     RATHER ADD THE INTERFACE WHEN THERE ARE TWO." ⭐ A
⭐     declined abstraction, stated, scores higher than a built
⭐     one.

⭐ ⭐ THE OTHER HALF: ⭐⭐ EXTENSION POINTS COST NOTHING WHEN
⭐   THEY ARE ***DATA***. ⭐ A new notification category is a
⭐   row, not a class. ⭐ A new log level is a value. ⭐⭐ PREFER
⭐   THE AXIS THAT EXTENDS BY CONFIGURATION OVER THE ONE THAT
⭐   EXTENDS BY SUBCLASSING.
```

# Part 6 — ⭐ Operations, and the close

```
⭐   ⭐ ⭐⭐ SENDING IS ASYNC WORK (Day 265): the API accepts and
⭐     enqueues; a worker sends. ⭐ A synchronous send makes your
⭐     signup endpoint as slow and as available as your email
⭐     provider.
⭐   ⭐ THE ENQUEUE GOES THROUGH THE OUTBOX (Day 263) — ⭐⭐ "WE
⭐     CREATED THE ORDER BUT DIDN'T SEND THE EMAIL" IS THE
⭐     CANONICAL DUAL-WRITE FAILURE.
⭐   ⭐ ⭐⭐ QUIET HOURS AND BATCHING are product requirements
⭐     that look like scheduling: "no push before 8 a.m. in the
⭐     user's timezone" ⇒ ⭐ timezone lives on the user, and a
⭐     delayed message is a `run_after`, not a sleeping thread.
⭐   ⭐ METRICS: sent, delivered, bounced, opted-out, ⭐⭐ AND
⭐     PER-CHANNEL FAILURE RATE — ⭐ a bounce rate spike is a
⭐     deliverability incident, and nobody notices without the
⭐     graph.
⭐ ⇒ ⭐ CLOSE: three tests (consent checked at send time,
⭐   dedupe under concurrent retries, fallback not triggered by
⭐   a timeout); one change (delivery webhooks); ⭐⭐ AT 100×:
⭐   fan-out to a million users is a scheduling problem — chunk
⭐   it, and never load a million recipients into memory.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| One logger class with `if` branches | Where, how and whether vary independently; three interfaces. |
| Not recognising Python's `logging` | Say you'd use it; reinventing it silently is the weaker answer. |
| f-strings in log calls | The message is built even when the level is off. |
| A handler that raises | Logging failing must not take down what it observes. |
| A synchronous network log handler | Your API becomes as slow as your log service. |
| An unbounded log queue | A memory leak with a schedule. Bound it and count drops. |
| Locking the logger rather than the handler | The interleaving happens at the write. |
| Building only the channel abstraction | That's the part everyone builds; consent, dedupe and templates are the design. |
| Checking consent at composition time | A message queued three days ago must respect yesterday's unsubscribe. |
| A random idempotency key | The retry gets a different key and sends again. |
| Storing rendered text | Render at send time from a template id plus data. |
| Rendering before checking consent | Wasted work, and PII copied into logs and queues for a message that mustn't be sent. |
| Falling back on a timeout | Unknown isn't failure; the user gets two notifications. |
| Abstracting scheduling with one rule | A declined abstraction, stated, scores higher than a built one. |
| Sending synchronously | Signup becomes as available as your email provider. |
| Enqueuing outside the outbox | The canonical dual-write failure. |
| No per-channel failure metrics | A bounce spike is a deliverability incident nobody notices. |

## Interview questions

**Q: Design a logging framework.**

> Three interfaces, because three things vary independently: a handler for *where*, a formatter for
> *how*, and a filter for *whether*. The test that they're genuinely separate axes is whether two
> people who never speak could write a JSON formatter and a syslog handler and have them combine. And
> I'd say up front that this is exactly Python's `logging` module and I'd use it — recognising that
> the standard library solved this is a better answer than reinventing it quietly. The details that
> separate answers are lazy message construction, so an f-string isn't evaluated when the level is
> off; handlers that never raise into the application, because logging failing mustn't take down what
> it observes; and network handlers being asynchronous with a *bounded* queue and a drop counter,
> since an unbounded log queue is a memory leak with a schedule.

**Q: What's the real design in a notification service?**

> Not the channel abstraction — that's the part everyone builds. It's consent, deduplication,
> templating and delivery uncertainty. Consent is per user, per category, per channel, and it's
> checked at *send* time rather than composition time, because a message queued three days ago has to
> respect an unsubscribe from yesterday. Deduplication needs an idempotency key derived from the event
> rather than freshly generated, or a retry gets a different key and sends again. Templates are
> rendered at send time from an id plus data, not stored as rendered text. And every channel is a
> third-party call with three outcomes.

**Q: Why does pipeline order matter?**

> Because it's correctness, not style. Dedupe first because it's cheapest and stops everything else.
> Consent *before* rendering — otherwise you do the work for someone who unsubscribed, and if the
> template contains personal data you've copied PII into a log and a queue for a message that must not
> be sent. Rate limit before send. Record after, including failures. The fallback logic has the same
> shape of trap: falling back from push to SMS on a *timeout* sends the user two notifications,
> because a timeout isn't a failure, it's the absence of information — so fall back only on definite
> failure.

**Q: How do you decide what to make extensible?**

> An interface per axis that has already varied or that the requirements say will. Channels, yes —
> there are four. Templates with localisation, yes, it was stated. A pluggable delivery-strategy
> engine, no: nobody asked, there's one implementation, and it's a cost with no purchase. I'd say the
> rejection out loud, because a declined abstraction with a reason scores higher than a built one.
> And I'd prefer axes that extend by data over axes that extend by subclassing — a new notification
> category should be a row, not a class.
