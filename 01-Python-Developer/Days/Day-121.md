# Day 121

**L-121** · **Pagination** — offset vs ⭐⭐ keyset, why page 10,000 is slow, and the drift that duplicates rows

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: offset pagination has two independent defects — it gets slower the deeper
> you go, and it silently skips and duplicates rows when the data changes underneath — and keyset
> pagination fixes both by asking "what comes after *this row*" instead of "what comes after *this
> many rows*".**
>
> ⭐ It is the most common API design question there is, and **the drift problem is the half most
> people have never thought about**, because it is invisible in testing.

---

# Part 1 — ⭐ Offset, and its first defect

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 0;      -- ⭐ page 1
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 200000; -- ⭐⭐ page 10,001
```

```
⭐⭐ THE DATABASE CANNOT SKIP ROWS IT HAS NOT PRODUCED. To answer OFFSET 200000
⭐   it must produce 200,020 rows in order AND THROW AWAY 200,000 OF THEM.
⭐   ⇒ ⭐⭐ SO THE COST IS O(offset + limit), NOT O(limit). ⭐ Page 1 is a
⭐        millisecond; page 10,001 is seconds, on the same query and the same
⭐        index.
⭐   ⇒ ⭐ and it is the deep pages that get hit by crawlers, scrapers and
⭐        anyone exporting your catalogue in a loop — ⭐⭐ so the expensive case
⭐        is the ADVERSARIAL case, which makes it a denial-of-service vector as
⭐        well as a performance problem.
⭐   ⇒ ⭐ `EXPLAIN ANALYZE` shows it plainly: rows removed by the offset appear
⭐        in the plan, and the timing scales with them (Stage 5).
```

# Part 2 — ⭐⭐ The second defect: drift

```
⭐⭐ THE ONE PEOPLE HAVE NEVER CONSIDERED, BECAUSE IT NEVER HAPPENS ON A STATIC
⭐   TEST DATABASE. Sorted newest-first:
⭐
⭐   [ A B C D E F G H … ]     ⭐ the client reads page 1 = rows 1-3 = A B C
⭐   ⇒ ⭐⭐ A NEW ROW `Z` ARRIVES AND SORTS FIRST:
⭐   [ Z A B C D E F G H … ]   ⭐ the client asks for OFFSET 3 = C D E
⭐   ⇒ ⭐⭐ **C IS RETURNED TWICE, AND NOTHING IS MISSING** — this time.
⭐
⭐   ⇒ ⭐⭐ AND A DELETION DOES THE OPPOSITE: remove a row from page 1 and
⭐        everything shifts UP by one, so ⭐⭐ ONE ROW IS SKIPPED ENTIRELY AND
⭐        THE CLIENT NEVER SEES IT.
⭐
⭐ ⇒ ⭐⭐ THAT IS THE SERIOUS ONE. A DUPLICATE IS COSMETIC; A SILENTLY SKIPPED
⭐     ROW IS DATA LOSS — and it is invisible: no error, no warning, and the
⭐     client has no way to know. ⭐ If the paginated job is "export every order
⭐     to the warehouse", you now have a warehouse missing rows nobody can name.
⭐ ⇒ ⭐ it also gets WORSE with high write rates and with slower clients, which
⭐     is precisely the production condition your tests do not have.
```

# Part 3 — ⭐⭐ Keyset (cursor) pagination

```sql
-- ⭐ page 1
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20;

-- ⭐⭐ page 2: "give me what comes after THIS ROW"
SELECT * FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)      -- ⭐⭐ ROW COMPARISON
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

```
⭐⭐ WHY THIS FIXES BOTH DEFECTS AT ONCE:
⭐   · ⭐⭐ COST: with an index on `(created_at DESC, id DESC)` the database
⭐        SEEKS DIRECTLY to the key and reads 20 rows. ⭐ O(limit), and page
⭐        10,001 costs exactly what page 1 costs.
⭐   · ⭐⭐ DRIFT: the position is a ROW, not a COUNT. Insert a thousand rows at
⭐        the top and "everything after row C" is still everything after row C.
⭐        ⭐ Nothing is skipped, nothing repeats.
⭐
⭐ ⭐⭐ THE TIE-BREAKER IS NOT OPTIONAL, AND THIS IS THE DETAIL PEOPLE MISS:
⭐   sorting by `created_at` alone, with two rows sharing a timestamp, means the
⭐   database may order them differently between queries (a relation is a SET —
⭐   Day 081) ⇒ ⭐⭐ ONE OF THEM IS SKIPPED OR REPEATED AT THE PAGE BOUNDARY.
⭐   ⇒ ⭐⭐ SO THE SORT KEY MUST BE UNIQUE. Append the primary key, and use a ROW
⭐        COMPARISON `(a, b) < (?, ?)` rather than `a < ? OR (a = ? AND b < ?)` —
⭐        ⭐ the row form is correct, readable, and index-friendly in Postgres.
⭐   ⇒ ⭐ the index must match the ORDER BY exactly, direction included, or the
⭐        planner sorts and you have lost the benefit.
```

```python
import base64, json

def encode_cursor(row) -> str:                    # ⭐⭐ OPAQUE, by design
    return base64.urlsafe_b64encode(
        json.dumps({"created_at": row.created_at.isoformat(), "id": row.id}).encode()
    ).decode().rstrip("=")

# ⇒ "eyJjcmVhdGVkX2F0IjoiMjAyNi0wOC0xOFQxMDoxMiIsImlkIjo0Mn0"
```

```
⭐⭐ MAKE THE CURSOR OPAQUE, FOR THREE REASONS — AND NOTE THAT BASE64 IS NOT
⭐   SECURITY (Day 116), IT IS A SIGNAL:
⭐  1. ⭐ CLIENTS STOP CONSTRUCTING THEM by hand, so you can change the sort key
⭐       or add a field without breaking anyone.
⭐  2. ⭐ it does not look like a document id, so nobody tries to guess one.
⭐  3. ⚠️ ⭐⭐ AND IF THE CURSOR ENCODES ANYTHING SENSITIVE — an internal id, a
⭐       score, another tenant's boundary — ⭐⭐ SIGN IT WITH AN HMAC (Day 116)
⭐       AND VERIFY. ⭐ Otherwise a client can edit the decoded values and page
⭐       from a position you never offered, which is IDOR through a cursor
⭐       (Day 118).
```

# Part 4 — ⭐ What keyset costs you

| | ⭐ Offset | ⭐⭐ Keyset |
|---|---|---|
| Deep pages | ⚠️ ⭐ O(offset) | ⭐⭐ **O(limit)** |
| Drift | ⚠️ ⭐⭐ skips and duplicates | ⭐⭐ **stable** |
| ⭐ "Jump to page 500" | ⭐ ✔ | ⚠️ ⭐⭐ **✗ — the big loss** |
| ⭐ Total count | ⭐ easy (and expensive) | ⭐ awkward |
| Backwards paging | ✔ | ⭐ ✔, with a reversed comparison |
| Arbitrary sort order | ✔ | ⭐ needs an index per sort key |

```
⭐⭐ SO WHEN IS OFFSET STILL RIGHT? SAY THIS, BECAUSE "ALWAYS USE CURSORS" IS
⭐   THE SHALLOW ANSWER:
⭐   ✔ ⭐ AN ADMIN TABLE OVER A SMALL, SLOWLY-CHANGING SET where numbered pages
⭐       are the point and the total row count is genuinely wanted.
⭐   ✔ ⭐ any result set with a hard cap — search results limited to 1,000, say.
⭐   ✘ ⭐⭐ AN INFINITE FEED, AN EXPORT, A SYNC JOB, OR ANYTHING WITH WRITES
⭐       ARRIVING WHILE YOU PAGE. ⭐ Those are exactly the drift cases.
⭐   ⇒ ⭐⭐ AND THE HYBRID EVERYONE ACTUALLY SHIPS: offset for the first N pages
⭐        (so the UI can show page numbers), with a HARD CAP on depth —
⭐        `OFFSET > 10000 ⇒ 400, use a cursor`. ⭐ It keeps the UX and removes
⭐        the denial-of-service tail.
```

```
⚠️⚠️ ⭐⭐ THE TOTAL COUNT IS ITS OWN PROBLEM, AND IT IS OFTEN THE REAL COST:
⭐    `SELECT COUNT(*) FROM orders WHERE …` on ten million rows SCANS THEM ALL,
⭐    ⭐ every page, ⭐⭐ and it is frequently slower than the page query itself.
⭐    ⇒ ⭐ ASK WHETHER YOU NEED IT. "Showing 20 of 4,281,004" is rarely acted on.
⭐    ⇒ ⭐⭐ CHEAPER ANSWERS, in order: return `has_more` by fetching LIMIT+1 and
⭐         discarding the extra ⭐ (one row, exact, free); an ESTIMATE from
⭐         `pg_class.reltuples`; a cached count; or a count only on page 1.
⭐    ⇒ ⭐ `LIMIT n+1` is the single best trick here: you learn whether another
⭐         page exists without a second query.
```

# Part 5 — ⭐ The API surface

```json
GET /orders?limit=20&cursor=eyJjcmVh…

{
  "items": [ … 20 … ],
  "next_cursor": "eyJjcmVhdGVkX2F0Ijoi…",     // ⭐⭐ null when there is no more
  "has_more": true
}
```

```
⭐⭐ THE RULES FOR THE SURFACE:
⭐   □ ⭐ DEFAULT the limit (20) and CAP it (100). ⭐⭐ `?limit=1000000` is an
⭐       unbounded field (Day 119) and therefore a DoS.
⭐   □ ⭐⭐ `next_cursor: null` MEANS THE END. ⭐ Do not make the client compare
⭐       `len(items) < limit`, which is wrong on the boundary where the last page
⭐       happens to be exactly full.
⭐   □ ⭐ also send a `Link: <…>; rel="next"` header if you want to be idiomatic.
⭐   □ ⭐⭐ VALIDATE THE CURSOR and return `400 invalid_cursor` (Day 120) — never
⭐       a 500 from a base64 error.
⭐
⭐ ⚠️⚠️ ⭐⭐ AND THE SORTING TRAP, WHICH IS A SQL INJECTION ROUTE:
⭐    `?sort=created_at` ⇒ `ORDER BY {sort}` ⇒ ⭐⭐ YOU CANNOT PARAMETERISE AN
⭐    IDENTIFIER. A bound parameter works for VALUES, not for column names, so
⭐    people interpolate — and `?sort=id; DROP TABLE orders--` follows.
⭐    ⇒ ⭐⭐ THE ONLY SAFE FORM IS AN ALLOWLIST: map the client's string to a
⭐         column you control. `SORTS = {"created_at": Order.created_at, …}`,
⭐         and anything not in it is a 400. ⭐ Which also forces you to notice
⭐         that each allowed sort needs its own index and its own cursor shape.
```

⭐ **Idempotency of pages.** ⭐⭐ Fetching the same cursor twice must return the same rows — so a cursor
must never encode "where I got to" as server-side state. **It is a position in the data, and the client
owns it**; that is what makes retries safe (Day 102).

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Assuming `OFFSET` skips cheaply | ⭐⭐ It produces and discards. O(offset). |
| ⭐⭐ **Not knowing about drift** | ⭐⭐ Inserts duplicate rows; deletes **skip** them, silently. |
| Sorting by a non-unique column | ⭐⭐ Rows are skipped or repeated at page boundaries. Add the PK. |
| ⭐ `a < ? OR (a = ? AND b < ?)` | ⭐ Use a row comparison — correct and index-friendly. |
| An index that does not match `ORDER BY` | ⭐ The planner sorts, and keyset buys nothing. |
| ⭐ A transparent, editable cursor | ⭐⭐ Clients construct them; sensitive ones need an HMAC. |
| ⭐⭐ **`COUNT(*)` on every page** | ⭐⭐ Often slower than the page itself. `LIMIT n+1`, or an estimate. |
| No cap on `limit` | ⭐ `?limit=1000000`. |
| Client infers the end from `len(items)` | ⭐ Wrong when the last page is exactly full. Send `next_cursor: null`. |
| ⭐ 500 on a malformed cursor | ⭐ `400 invalid_cursor`. |
| ⭐⭐ **Interpolating `?sort` into `ORDER BY`** | ⭐⭐ SQL injection — identifiers cannot be parameterised. Allowlist. |
| "Always use cursors" | ⭐ Offset is fine for shallow, capped, admin-style listings. |

## Interview questions

**Q: How would you paginate an API?**
> Keyset for anything that's a feed, an export or a sync — "give me what comes after this row" rather
> than "skip this many". The query filters on a row comparison against the last row's sort key and
> takes a limit, with an index matching the sort order exactly, so the cost is O(limit) and page ten
> thousand costs what page one costs. The cursor is opaque, base64 of the key values, so clients don't
> construct them and I can change the sort key later. Offset is still fine for a shallow admin table
> where numbered pages are the point — but I'd cap the depth, because deep offsets are both slow and
> exactly what crawlers hit.

**Q: What's wrong with offset pagination, beyond speed?**
> Drift, and it's the defect most people have never considered because it never happens on a static
> test database. If a row is inserted while you're paging, everything shifts down and you see a row
> twice. If a row is deleted, everything shifts up and **a row is skipped entirely** — silently, with
> no error, and the client has no way to know. The duplicate is cosmetic; the skip is data loss. If
> the paginated job is "export every order to the warehouse", you end up with a warehouse missing rows
> nobody can name. Keyset fixes it because the position is a row rather than a count, so inserting a
> thousand rows above you changes nothing about "what comes after row C".

**Q: Why does a keyset cursor need a tie-breaker?**
> Because the sort key has to be unique. If you sort by `created_at` alone and two rows share a
> timestamp, the database is free to order them differently between queries — a relation is a set, so
> there's no inherent order for equal keys — and one of them gets skipped or repeated at the page
> boundary. So you append the primary key and compare the tuple: `(created_at, id) < (?, ?)`. The row
> comparison form is also more readable than the expanded OR version and Postgres can use the index
> for it.

**Q: How do you return a total count?**
> Ideally I don't. `COUNT(*)` on a large filtered set scans everything and is often slower than the
> page query itself, and "showing 20 of 4,281,004" is rarely acted on. The cheap alternative is
> fetching `LIMIT n+1` and discarding the extra row, which tells you exactly whether another page
> exists for the cost of one row. Beyond that, an estimate from the planner's statistics, or a cached
> count, or a count only on page one. If a product genuinely needs an exact total on every page, that's
> a requirement worth pushing back on with the query plan in hand.

**Q: A client sends `?sort=created_at`. What do you have to be careful about?**
> That you can't parameterise an identifier — bound parameters work for values, not column names — so
> the temptation is to interpolate the string into `ORDER BY`, and that's SQL injection. The only safe
> form is an allowlist mapping the client's string to a column object I control, with anything else
> returning 400. That constraint is useful in itself, because it forces you to notice that every
> allowed sort needs its own index and its own cursor shape, which is the real cost of offering
> arbitrary sorting.
