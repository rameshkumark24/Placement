# Part 1 — ⭐ The three tiers, and how to choose between them

```
⭐⭐ THE CHOICE IS DECIDED BY ONE QUESTION: WHAT HAPPENS IF THE PROCESS DIES
⭐   ONE MILLISECOND AFTER THE RESPONSE IS SENT?

⭐  1. ⭐ `BackgroundTasks` — same process, after the response.
⭐       ⭐⭐ LOST ON RESTART. No retry, no visibility, no metrics, and it
⭐       shares the worker's CPU and its threadpool (Day 134).
⭐       ⇒ ⭐ RIGHT FOR: audit log lines, cache warming, a metrics ping.
⭐         ⭐⭐ i.e. things nobody will ever ask about.
⭐
⭐  2. ⭐⭐ A REAL QUEUE (Celery / RQ / Dramatiq / arq).
⭐       ⭐ Durable, retried, observable, and runs in a SEPARATE process you
⭐       can scale and deploy independently.
⭐       ⇒ ⭐ RIGHT FOR: email, payments, report generation, third-party calls,
⭐         anything slow, ⭐⭐ anything a user would notice missing.
⭐
⭐  3. ⭐ THE DATABASE AS THE QUEUE (a `jobs` table + `SELECT ... FOR UPDATE
⭐       SKIP LOCKED`). ⭐⭐ Underrated. ⭐ One less system to run, transactional
⭐       with your data (Part 5 — this is a big deal), and Postgres handles
⭐       thousands/sec comfortably.
⭐       ⇒ ⭐ RIGHT UNTIL you need fan-out, priorities and high throughput.
⭐
⭐   ⇒ ⭐⭐ THE LINE, IN ONE SENTENCE: "WOULD A USER OR AN AUDITOR EVER ASK
⭐        WHY IT DIDN'T HAPPEN?" ⭐ If yes, it does not belong in
⭐        `BackgroundTasks`.
```

```python
# ⭐ THE ANTI-PATTERN THAT SHIPS CONSTANTLY:
@router.post("/orders")
def create(body: OrderIn, tasks: BackgroundTasks):
    order = svc.place(body)
    tasks.add_task(send_confirmation_email, order.id)   # ⭐⭐ silently lost on deploy
    return order
# ⇒ ⭐ deploys happen daily. Every deploy drops the emails in flight (Day 083),
#    ⭐⭐ and there is NOTHING in your logs to tell you it happened.
```

# Part 2 — ⭐ Celery's moving parts

```python
# app/worker.py
celery_app = Celery("app", broker=settings.redis_url, backend=settings.redis_url)

@celery_app.task(
    bind=True,
    autoretry_for=(HTTPError, OperationalError),
    retry_backoff=True,           # ⭐ exponential
    retry_jitter=True,            # ⭐⭐ NOT OPTIONAL — see the box
    retry_kwargs={"max_retries": 5},
    acks_late=True,               # ⭐⭐ Part 3
)
def send_confirmation_email(self, order_id: int) -> None:      # ⭐⭐ AN ID, NOT AN OBJECT
    with SessionLocal() as db:                                  # ⭐ its own session
        order = db.get(Order, order_id)
        if order is None or order.email_sent_at:                # ⭐⭐ idempotency guard
            return
        mailer.send(order.email, render(order))
        order.email_sent_at = now(); db.commit()
```

```
⭐⭐ THE BROKER IS NOT THE RESULT BACKEND — people conflate these constantly:
⭐   ⭐ BROKER: the queue. Where messages wait for a worker. (Redis/RabbitMQ)
⭐   ⭐ RESULT BACKEND: where return values and states are stored.
⭐   ⇒ ⭐⭐ IF YOU NEVER READ THE RESULT, TURN THE BACKEND OFF. Leaving it on
⭐        writes a row per task forever, ⭐ and unbounded result growth is a
⭐        classic "Redis ran out of memory at 3 a.m." postmortem.
⭐   ⇒ ⭐⭐ AND NEVER `.get()` A RESULT INSIDE A REQUEST — that is a synchronous
⭐        call wearing a queue's clothes. You now have the latency of the task
⭐        PLUS the queue, and a deadlock risk if the worker is saturated.

⭐⭐ PASS AN ID, NEVER AN OBJECT. THREE REASONS, ALL FATAL:
⭐   1. ⭐ arguments are SERIALISED (JSON) — ⭐⭐ an ORM object is not
⭐        JSON-serialisable, and if you make it so via pickle you have
⭐        Day 128's RCE-by-design on your queue
⭐   2. ⭐⭐ THE DATA IS STALE THE MOMENT IT IS ENQUEUED. The task may run
⭐        five minutes later, after three updates. ⭐ Sending an email with the
⭐        old address is a data bug with no exception attached.
⭐   3. ⭐ a detached ORM object (Day 135) will raise or lazy-load in a
⭐        process with no session
```

```
⭐⭐ WHY JITTER IS MANDATORY, NOT A NICETY:
⭐   ⭐ a third-party API returns 503. 4,000 queued tasks all fail.
⭐   ⭐ pure exponential backoff → ⭐⭐ ALL 4,000 RETRY AT EXACTLY t+2s,
⭐        THEN ALL AT t+4s, THEN t+8s.
⭐   ⇒ ⭐⭐ YOU HAVE BUILT A SYNCHRONISED DDoS ON A SERVICE THAT IS ALREADY
⭐        FAILING, and you keep it down. ⭐ Jitter spreads the herd. Same
⭐        principle as Day 143's cache-TTL jitter, and worth naming as such.
```

# Part 3 — ⭐⭐ At-least-once, and the guarantee you don't get

```
⭐⭐ THE THREE DELIVERY SEMANTICS, AND WHY ONLY ONE IS REAL:

⭐  AT-MOST-ONCE  — ack on receipt, then work. ⭐ Worker dies mid-task ⇒ the
⭐    message is gone. ⭐⭐ Silent data loss. (Celery's DEFAULT: `acks_late=False`.)
⭐  AT-LEAST-ONCE — work, then ack. ⭐ Worker dies mid-task ⇒ the message is
⭐    redelivered ⇒ ⭐⭐ THE TASK RUNS TWICE. (`acks_late=True`.)
⭐  EXACTLY-ONCE  — ⭐⭐ DOES NOT EXIST across a process boundary. The ack and
⭐    the side effect are two separate operations on two separate systems, and
⭐    the process can die between them. ⭐ Nothing removes that window.
⭐
⭐   ⇒ ⭐⭐ SO YOU CHOOSE: LOSE MESSAGES, OR RUN THEM TWICE.
⭐        ⭐ CHOOSE TWICE (`acks_late=True`) AND MAKE THE TASK IDEMPOTENT.
⭐        ⭐⭐ "Exactly-once processing" is achieved by at-least-once delivery
⭐        PLUS an idempotent consumer — never by the queue alone. ⭐ Say it
⭐        that way; it is the sentence that separates people who have run a
⭐        queue from people who have read about one.
```

```
⭐⭐ THE COST OF `acks_late=True`, WHICH YOU MUST ALSO KNOW:
⭐   ⭐ a task that reliably CRASHES the worker (OOM, segfault) is redelivered
⭐     to another worker, which also dies ⇒ ⭐⭐ THE POISON PILL: one bad
⭐     message can take down your entire worker fleet in a loop.
⭐   ⇒ ⭐ DEFENCE: `max_retries`, a hard `time_limit`, and ⭐⭐ A DEAD-LETTER
⭐     QUEUE. After N failures the message moves to a DLQ instead of being
⭐     retried forever.
⭐   ⇒ ⭐⭐ AND SOMEONE MUST WATCH THE DLQ. An unmonitored DLQ is `/dev/null`
⭐     with extra steps — ⭐ alert on `depth > 0`, not on a dashboard nobody opens.
```

```python
# ⭐⭐ THE THREE IDEMPOTENCY STRATEGIES — pick per task, and know which you used
# 1. ⭐ NATURALLY IDEMPOTENT: SET a value rather than increment it
order.status = "paid"                       # ⭐ safe twice
order.retry_count += 1                      # ⭐⭐ NOT safe twice

# 2. ⭐⭐ A GUARD FLAG, checked and set in the SAME transaction
updated = db.execute(
    update(Order).where(Order.id == oid, Order.email_sent_at.is_(None))
                 .values(email_sent_at=now())
).rowcount
if updated == 0:
    return                                   # ⭐ someone else already did it
mailer.send(...)                             # ⭐ note: still a window — see below

# 3. ⭐ AN IDEMPOTENCY KEY ON THE DOWNSTREAM CALL (Day 122, from the other side)
stripe.charge(..., idempotency_key=f"order-{oid}-capture")   # ⭐⭐ the strongest one
```

> ⭐⭐ **Strategy 2 has a window and you should say so out loud:** the flag is set, then the process
> dies before the email sends — the email is lost. ⭐ Flag-before means *at-most-once* for the side
> effect; flag-after means *at-least-once*. **You are choosing between a missing email and a
> duplicate email**, and for email the duplicate is usually correct. ⭐⭐ For a payment, neither is
> acceptable — which is exactly why strategy 3 exists, and why every payment API has an idempotency
> key.

# Part 4 — ⭐ Running it: queues, timeouts, deployment

```
⭐⭐ SEPARATE QUEUES BY LATENCY CLASS, NOT BY FEATURE:
⭐   ⭐ celery -A app worker -Q fast -c 8      ⭐ emails, webhooks, notifications
⭐   ⭐ celery -A app worker -Q slow -c 2      ⭐ report generation, imports
⭐   ⇒ ⭐⭐ WHY: on ONE queue, a hundred 10-minute reports occupy every worker
⭐        and the password-reset email waits 40 minutes behind them.
⭐        ⭐ HEAD-OF-LINE BLOCKING — Day 105's pipelining problem, at the job
⭐        level. ⭐ Feature-based queues do not fix it; latency-based ones do.

⭐⭐ FOUR SETTINGS THAT PREVENT REAL INCIDENTS:
⭐   · `task_time_limit` / `task_soft_time_limit` — ⭐⭐ WITHOUT THESE, ONE
⭐        HUNG HTTP CALL HOLDS A WORKER SLOT FOREVER. ⭐ Soft raises an
⭐        exception you can catch and clean up after; hard kills the process.
⭐        ⭐ Day 103: a request with no timeout is a resource leak with a
⭐        respectable name.
⭐   · `worker_prefetch_multiplier = 1` for long tasks — ⭐⭐ the default
⭐        prefetches a BATCH per worker, so 100 jobs get grabbed by one worker
⭐        while three others sit idle. ⭐ The classic "why is only one worker
⭐        busy" question.
⭐   · `worker_max_tasks_per_child` — ⭐ recycles processes; a blunt but
⭐        effective answer to a slow leak (Day 070).
⭐   · ⭐ concurrency model: `prefork` for CPU (Day 068's processes),
⭐        `gevent`/`eventlet`/`threads` for I/O-bound fan-out.

⭐⭐ DEPLOYING WORKERS — the bit that bites:
⭐   ⭐ workers must get SIGTERM and FINISH the current task before exiting
⭐     (warm shutdown, Day 083). ⭐⭐ Your stop grace period must therefore
⭐     exceed your longest task, or SIGKILL truncates work mid-flight.
⭐   ⭐⭐ AND: OLD WORKERS CONSUME NEW MESSAGES DURING A ROLLING DEPLOY. So a
⭐     task signature change is a BREAKING CHANGE across versions — ⭐ add new
⭐     kwargs with defaults, never remove or reorder positional args. ⭐⭐ It is
⭐     Day 138's expand/contract, applied to a message format.
```

# Part 5 — ⭐⭐ The dual-write problem, and the outbox

```
⭐⭐ THE BUG THAT IS IN ALMOST EVERY CODEBASE AND ALMOST NEVER NOTICED:

⭐   def place_order(...):
⭐       db.add(order)
⭐       db.commit()                         # ⭐ system A
⭐       send_email.delay(order.id)          # ⭐ system B
⭐
⭐   ⭐⭐ TWO SYSTEMS, TWO WRITES, NO SHARED TRANSACTION. Both orderings fail:
⭐
⭐   ⭐ COMMIT THEN ENQUEUE → the process dies in between, or Redis is down.
⭐        ⇒ ⭐⭐ ORDER EXISTS, EMAIL NEVER SENT. Silent.
⭐   ⭐ ENQUEUE THEN COMMIT → ⭐⭐ WORSE, AND THIS ONE IS COMMON: the worker is
⭐        fast and picks the job up BEFORE your transaction commits.
⭐        ⇒ ⭐⭐ `db.get(Order, id)` RETURNS `None`. The task fails, retries,
⭐        and by then the row exists — ⭐ so it "works", intermittently, and
⭐        your logs fill with mystery `None` errors. ⭐⭐ Then one day the
⭐        transaction ROLLS BACK and you have emailed a customer about an
⭐        order that does not exist.
```

```
⭐⭐ THE FIX, IN THREE ESCALATING LEVELS:

⭐  LEVEL 1 — ⭐ ENQUEUE AFTER COMMIT, NEVER INSIDE THE TRANSACTION.
⭐    ⭐ SQLAlchemy: `event.listen(session, "after_commit", ...)`.
⭐    ⇒ ⭐⭐ Removes the "row doesn't exist yet" bug and the phantom-email bug.
⭐      ⭐ Still loses the message if the process dies between the two.
⭐      ⭐⭐ GOOD ENOUGH FOR EMAIL. NOT FOR MONEY.
⭐
⭐  LEVEL 2 — ⭐⭐ THE TRANSACTIONAL OUTBOX. The one to name in an interview:
⭐    ⭐ INSERT the job into an `outbox` table IN THE SAME TRANSACTION as the
⭐      order. ⭐⭐ One transaction, one system, atomic by construction.
⭐    ⭐ A relay process polls the outbox and publishes to the broker:
⭐        SELECT * FROM outbox WHERE published_at IS NULL
⭐        ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED   ⭐⭐ SKIP LOCKED is
⭐                                          what makes multiple relays safe
⭐    ⇒ ⭐⭐ THE ORDER AND THE INTENT-TO-SEND COMMIT OR ROLL BACK TOGETHER.
⭐      ⭐ Delivery is now at-least-once (the relay may publish then die before
⭐      marking) — ⭐⭐ which is fine, because Part 3 already made the consumer
⭐      idempotent.
⭐
⭐  LEVEL 3 — ⭐ CDC: read the database's replication log (Debezium) instead of
⭐    polling. ⭐ Same guarantee, no polling, much more infrastructure.
⭐    ⭐⭐ Know the name; do not reach for it first.
```

```python
# ⭐⭐ THE OUTBOX, MINIMALLY — and note it is ~20 lines, not a framework
def place_order(db: Session, ...) -> Order:
    order = Order(...)
    db.add(order)
    db.add(Outbox(topic="order.placed", payload={"order_id": order.id}))   # ⭐⭐ same txn
    db.commit()                                    # ⭐ both, or neither
    return order
```

> ⭐⭐ **This is the same shape as Day 122's idempotency claim: make the two things that must agree
> be one atomic write.** ⭐ Whenever you find yourself writing to two systems in a row and hoping,
> the answer is almost always "make one of them a row in the other one's transaction".

## Common mistakes

| Mistake | Correction |
|---|---|
| `BackgroundTasks` for email or payments | Same process, lost on deploy, no retry, no trace. Use a real queue. |
| Passing an ORM object to a task | Not JSON-serialisable; stale by the time it runs; detached in the worker. Pass the id. |
| Leaving `acks_late=False` (the default) | At-most-once: a worker crash silently drops the job. |
| Assuming exactly-once delivery | ⭐⭐ Impossible across a process boundary. At-least-once + an idempotent consumer. |
| Exponential backoff without jitter | 4,000 tasks retry in lockstep and keep the failing service down. |
| No `max_retries` / no DLQ | A poison-pill message loops through your whole fleet. |
| A DLQ nobody monitors | `/dev/null` with extra steps. Alert on depth > 0. |
| One queue for everything | Long jobs block short ones — head-of-line blocking at the job level. |
| No `task_time_limit` | One hung HTTP call holds a worker slot forever. |
| Default `prefetch_multiplier` on long tasks | One worker grabs the batch; the others idle. |
| `.get()` on a task result inside a request | A synchronous call wearing a queue's clothes. |
| Result backend on when results are never read | Unbounded growth until Redis OOMs. |
| `.delay()` before `commit()` | The worker sees no row — or worse, the transaction rolls back and the email is a lie. |
| `.delay()` after `commit()` and calling it safe | Better, but still loses the message if the process dies between. Outbox for anything that matters. |
| Removing or reordering task arguments | Old workers consume new messages during a rolling deploy. Add kwargs with defaults. |

## Interview questions

**Q: When is `BackgroundTasks` enough, and when isn't it?**

> It runs in the same process after the response is sent, so it dies with the process — no retry, no
> durability, no visibility, and it competes with request handling for the same CPU and threadpool.
> That's fine for audit lines, cache warming, or a metrics ping. My test is: would a user or an
> auditor ever ask why it didn't happen? If yes, it needs a real queue — because deploys happen
> daily, every deploy drops whatever's in flight, and nothing in your logs will tell you.

**Q: Does your queue guarantee exactly-once delivery?**

> No queue does, across a process boundary. The ack and the side effect are two operations on two
> systems, and the process can die in the gap. So you choose: ack early and lose messages when a
> worker crashes, or ack late and sometimes run a task twice. I choose ack-late and make consumers
> idempotent — exactly-once *processing* is at-least-once delivery plus an idempotent consumer,
> never the queue on its own. The cost of ack-late is the poison pill: a message that reliably
> crashes the worker gets redelivered and crashes the next one, so it needs `max_retries`, a hard
> time limit, and a dead-letter queue that someone actually monitors.

**Q: `place_order` commits, then calls `send_email.delay(order.id)`. What's wrong?**

> Two writes to two systems with no shared transaction — the dual-write problem. In that order, if
> the process dies or Redis is unreachable between them, the order exists and the email never sends,
> silently. If you flip the order and enqueue first, it's worse: workers are fast, so the task often
> picks up the id before your transaction commits and `db.get` returns `None` — which "works" after
> a retry, so it hides as intermittent noise — and if the transaction ever rolls back, you've
> emailed a customer about an order that doesn't exist. The minimum fix is to enqueue on
> `after_commit`. The real fix is a transactional outbox: insert the job row in the same transaction
> as the order, and have a relay poll it with `FOR UPDATE SKIP LOCKED` and publish. Then the data
> and the intent commit or roll back together, and the relay's at-least-once publishing is fine
> because the consumer is already idempotent.

**Q: Why is jitter on retry backoff not optional?**

> Because failures are correlated. When a third-party API returns 503, it isn't one task failing,
> it's every queued task failing at once. Pure exponential backoff retries all of them at exactly
> t+2, then t+4, then t+8 — a synchronised thundering herd aimed at a service that's already
> struggling, which keeps it down and extends your own outage. Jitter spreads the retries across the
> window. Same reasoning as adding jitter to cache TTLs.

**Q: Only one of your four Celery workers seems busy. Why?**

> Almost always prefetch. The default `worker_prefetch_multiplier` makes each worker reserve a batch
> of messages up front, which is a good optimisation for tasks measured in milliseconds and a
> disaster for tasks measured in minutes — one worker grabs a hundred jobs and the others find an
> empty queue. Set it to 1 for long tasks. The related issue is queue design: long and short jobs on
> one queue means head-of-line blocking, so a password-reset email waits behind a hundred report
> generations. Split queues by latency class, not by feature.

## 🎙️ Articulation drill

**Two minutes: "How would you send a confirmation email after an order?"**

Start by rejecting the obvious version and say what breaks — `BackgroundTasks` dies with the
process, and deploys are daily. Move to a queue, then immediately raise the thing most people miss:
enqueueing and committing are two writes to two systems. Give both bad orderings and say which is
worse and why. Land on the outbox — one transaction, a relay with `SKIP LOCKED` — and note it's
about twenty lines, not a framework. Then close the loop: the relay is at-least-once, which is fine
**because you already made the consumer idempotent** — since at-least-once is the only guarantee
that exists.
