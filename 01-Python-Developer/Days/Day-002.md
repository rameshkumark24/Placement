# Part 1 — L-002 · From source to execution

## The problem

The CPU understands exactly one thing: machine code — binary instructions for *its* instruction set.
You write text. Something has to bridge that gap, and there are two classic strategies plus the
hybrid that Python actually uses.

## The two classic strategies

| | **Compiler** | **Interpreter** |
|---|---|---|
| When translation happens | ⭐ **once, ahead of time** | ⭐ **every time, as it runs** |
| Output | a machine-code executable | nothing — it just does the work |
| Startup | slow build, fast start | no build, slower execution |
| Errors | many caught before running | found when that line runs |
| Portability | ⭐ one binary per platform | ⭐ one source file runs anywhere the interpreter does |
| Examples | C, C++, Rust, Go | classic BASIC, shell |

```
COMPILED (C):
  hello.c ──[compiler]──▶ hello.o ──[linker]──▶ ./hello ──[CPU runs it directly]

INTERPRETED (naive):
  script.sh ──[shell reads line 1, does it, reads line 2, does it, ...]
```

⚠️ **Neither box describes Python, Java, C#, or most languages you will use.** They are all hybrids,
and the hybrid is the interesting part.

## ⭐⭐ Where Python actually sits

```
⭐⭐ THE REAL PIPELINE:

  app.py  ──[1. LEXER + PARSER]──▶  AST
                                     │
          ──[2. COMPILER]───────────▶ ⭐⭐ BYTECODE  (.pyc, cached in __pycache__)
                                     │
          ──[3. ⭐⭐ CPython VM]──────▶ a C loop that executes bytecode, one op at a time
                                     │
          ──[4. the CPU]────────────▶ machine code — ⭐ of the INTERPRETER, not of your program
```

| Step | What happens | You can see it |
|---|---|---|
| 1. Parse | text → abstract syntax tree | `ast.parse()`, `ast.dump()` |
| 2. **Compile** | AST → **bytecode** | ⭐⭐ `dis.dis(func)` |
| 3. Cache | bytecode written to `__pycache__/*.pyc` | ⭐ look in the folder |
| 4. Execute | the **CPython evaluation loop** runs the bytecode | Day 073 |

> **⭐⭐ So the honest sentence is: "Python is compiled to bytecode, which is then executed by a
> virtual machine written in C."** That is one sentence, it is correct, and almost nobody says it.
> Say it in an interview and the next question will be a better one.

## Why this matters — four consequences you will meet

| Consequence | Where you meet it |
|---|---|
| ⭐⭐ **Syntax errors are found before *any* code runs** | ⭐ compile step; a typo on line 400 stops line 1 |
| ⭐⭐ **Type errors are NOT** — they surface at execution | ⭐ this is why mypy exists (Day 062) |
| ⭐ **`__pycache__` exists to skip re-parsing** | ⭐ delete it and startup gets slower, once |
| ⭐⭐ **The "slowness" is the VM loop, not the parsing** | ⭐⭐ Day 073 — and it is why NumPy and C extensions are fast |

## ⭐ The comparison people actually want

| | **C** | **Java** | ⭐⭐ **Python** |
|---|---|---|---|
| Compiled to | machine code | JVM bytecode | ⭐ CPython bytecode |
| Executed by | the CPU | the JVM, **with a JIT that produces machine code** | ⭐⭐ the CPython VM, **no JIT in the default build** |
| Typical speed vs C | 1× | 1–2× after warm-up | ⭐⭐ **10–100×** |
| Why | — | JIT compiles hot paths to native code | ⭐⭐ every operation goes through the interpreter loop and dynamic dispatch |

⚠️ **Do not memorise "Python is slow" — memorise *where* it is slow.** The interpreter overhead is
per-bytecode-operation. So a tight Python loop over ten million items is slow, and the *same* work
inside NumPy or a database is not, because the loop moved into C. **That distinction is the entire
performance strategy for Python backends**, and it comes back in Stage 5 and Stage 9.

> ⭐ **Worth knowing:** other implementations make different choices — **PyPy** has a JIT and is often
> several times faster; **Cython** compiles annotated Python to C. CPython 3.11+ added a
> "specialising adaptive interpreter" that closes some of the gap, and 3.13+ ships an experimental
> JIT. When someone says "Python", they almost always mean CPython.

## Type this yourself

```python
# day002.py — see the bytecode with your own eyes.
import dis

def add_one(x):
    return x + 1

print("=== BYTECODE ===")
dis.dis(add_one)
```

Run it. You will see something close to:

```
  LOAD_FAST     0 (x)      ← push the local x onto the stack
  LOAD_CONST    1 (1)      ← push the constant 1
  BINARY_OP     0 (+)      ← pop two, add, push result
  RETURN_VALUE             ← pop and return
```

**Read those four lines carefully.** That is a *stack machine*: values are pushed and popped rather
than held in named registers. Every one of those instructions is a case in a giant `switch` inside
the C evaluation loop.

Now do the experiment that makes the cost visible:

```python
import dis, time

def loop_python(n):
    total = 0
    for i in range(n):
        total += i
    return total

print(f"instructions per iteration: roughly {len(list(dis.get_instructions(loop_python)))}")

start = time.perf_counter()
loop_python(10_000_000)
print(f"pure Python loop: {(time.perf_counter()-start)*1000:.0f} ms")

start = time.perf_counter()
sum(range(10_000_000))          # the same arithmetic, but the loop is in C
print(f"builtin sum():    {(time.perf_counter()-start)*1000:.0f} ms")
```

⭐⭐ **The two numbers are the lesson of the day.** Identical arithmetic. The difference is entirely
whether the *loop* runs in the interpreter or in C. Write both numbers down — you will quote this
ratio for the rest of the roadmap.

And prove the caching claim:

```bash
# In a folder with a module you import:
ls __pycache__/          # you will see module.cpython-312.pyc
rm -rf __pycache__/      # delete it
# run again — it is regenerated. Time both runs.
```

⚠️ **Note what `__pycache__` does NOT do:** it caches the *compile* step only. Your program still
runs through the interpreter loop every time. **Deleting it costs you milliseconds at startup, not
runtime.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"Python is an interpreted language"** | ⭐⭐ It is compiled to bytecode, which is then interpreted by a VM. Say the full sentence. |
| "Python has no compile step, so there are no compile errors" | ⭐ Syntax errors are raised at compile time, before any of your code runs. Type errors are not. |
| Thinking `.pyc` files make Python faster to *run* | They skip parsing at import. Execution speed is unchanged. |
| "Python is slow" with no qualifier | ⭐⭐ The interpreter loop is slow per operation. Move the loop into C — NumPy, the database, a builtin — and the same work is fast. |
| Assuming CPython is the only Python | PyPy has a JIT; Cython compiles to C. CPython is the default, not the definition. |
| Believing bytecode is portable machine code | It is portable, but only to a Python VM of a compatible version — `.pyc` files are version-specific. |

## Interview questions

**Q: Is Python compiled or interpreted?**
> Both, and the precise version is: source is compiled to bytecode, and the bytecode is executed by a
> virtual machine written in C. The compile step is why a syntax error anywhere in a file stops it
> from running at all, and the cached bytecode lives in `__pycache__`. What Python does *not* do by
> default is compile to native machine code — there is no JIT in standard CPython, which is the main
> reason it is an order of magnitude slower than C for tight loops.

**Q: Why is Python slower than Java or C?**
> The overhead is per bytecode operation. Every operation goes through the interpreter loop and does
> dynamic type dispatch, because the types are not known ahead of time. Java's JIT compiles hot paths
> to native machine code after warm-up, so it converges towards C; CPython's default build has no JIT,
> so it does not. The practical consequence is that you make Python fast by moving the loop out of
> Python — into NumPy, into the database, into a C extension — rather than by micro-optimising the
> Python.

**Q: What is in a `.pyc` file, and what does it buy you?**
> The compiled bytecode for a module, plus a header recording the source's modification time and
> size so it can be invalidated. It saves the parse-and-compile step on subsequent imports, which
> matters for startup time on large applications. It does not change execution speed at all.

**Q: If Python compiles, why do type errors only appear at runtime?**
> Because the compiler only checks syntax and produces bytecode; it does no type analysis, since
> names are bound at runtime and any name can hold any type. That is exactly the gap static type
> checkers fill — mypy reads your annotations and does the analysis the compiler does not, before you
> ship. It is a separate tool by design, not part of the runtime.

# Part 2 — C-02 · Physical and data link layers

## Layer 1 — Physical

The physical layer moves **bits** as signals: voltage on copper, light in fibre, radio in WiFi. It
has no idea what the bits mean. Its entire job is "get a 1 to the other end and have it still be a 1".

| Medium | Typical | Note |
|---|---|---|
| Copper (Cat 6) | 1–10 Gbps, ~100 m | cheap, susceptible to interference |
| Fibre | 10–400 Gbps, kilometres | ⭐ **light in glass — this is what an undersea cable is** |
| WiFi | shared, variable | ⭐ half-duplex and contended — the reason your latency varies |

⭐ **Latency has a floor set by physics.** Light in fibre travels ~200,000 km/s. India to US is
~13,000 km, so ~65 ms one way, ~130 ms round trip, **before any equipment touches it.** No amount of
engineering removes that, which is why CDNs exist (Stage 9) and why "just put the server closer" is a
real architectural decision.

## Layer 2 — Data Link

The link layer's job: **get a frame to the next device on this physical segment.** It introduces:

| Concept | What it is |
|---|---|
| **Frame** | the link layer's unit — header + payload + trailer (with a checksum) |
| ⭐⭐ **MAC address** | a 48-bit hardware address, e.g. `a4:83:e7:2f:11:9c` — **burned into the NIC** |
| **Switch** | forwards frames by MAC, learning which MAC is on which port |
| ⭐ **MTU** | maximum frame payload — typically **1500 bytes** on Ethernet |

```
⭐⭐ MAC vs IP — the distinction that must be automatic:
   MAC address  ⇒ "the next device on this cable/segment"   ⇒ CHANGES at every hop
   IP address   ⇒ "the final machine, anywhere on earth"    ⇒ STAYS THE SAME end to end
```

## ⭐ ARP — the translation nobody sees

You know the destination IP. To send a frame you need a destination *MAC*. ARP bridges the two:

```
1. Host A wants to send to 192.168.1.7 and does not know its MAC.
2. A BROADCASTS to the whole segment: "who has 192.168.1.7?"
3. The owner replies with its MAC.
4. A caches it in the ARP table (arp -a) and sends the frame.
```

⚠️ **Because ARP has no authentication, anyone on the segment can answer.** That is **ARP spoofing** —
the basis of local man-in-the-middle attacks, and one of several reasons TLS exists (Day 009): you
should assume the network is hostile rather than assume the network is correct.

## ⭐ MTU, and why it matters to you

The MTU is ~1500 bytes. Anything larger must be split. TCP handles this by choosing a segment size
that fits (Day 008), which is why **a 1 MB JSON response is not one packet — it is roughly 700 of
them**, each with its own headers and each subject to loss and retransmission.

> ⭐ **Carry this forward:** it is the physical reason that chatty APIs, oversized payloads and N+1
> queries cost more than their byte count suggests. The overhead is per packet, not per byte.

---

## Common mistakes

| Mistake | Correction |
|---|---|
| Confusing MAC with IP | MAC is the next hop on this segment and changes every hop; IP is the destination machine and does not. |
| Thinking a switch routes | A switch forwards by MAC within one network. A router forwards by IP between networks. |
| Assuming ARP is secure | It has no authentication at all. Any host on the segment can claim any IP. |
| "Fibre is faster because the signal is faster" | Speed of propagation is similar; fibre wins on bandwidth, distance and immunity to interference. |
| Ignoring the MTU | A large response is hundreds of packets, each with per-packet overhead and loss risk. |

---

## Interview questions

**Q: Difference between a MAC address and an IP address?**
> A MAC address identifies a network interface on a local segment and is used to deliver a frame to
> the next device — it changes at every hop. An IP address identifies the destination machine across
> networks and stays constant end to end. Both are needed because they answer different questions:
> where finally, and where next.

**Q: What is ARP and what is its security weakness?**
> ARP maps an IP address on the local network to a MAC address by broadcasting a request and caching
> the reply. It has no authentication, so any host on the segment can answer for any IP — that is ARP
> spoofing, and it enables local man-in-the-middle attacks. It is one of the reasons you encrypt at a
> higher layer rather than trusting the network.

**Q: What is the MTU and why should an application developer care?**
> The maximum payload a link-layer frame can carry, typically 1500 bytes on Ethernet. It matters
> because a large response is split into hundreds of packets, each carrying its own headers and each
> individually subject to loss and retransmission — so the cost of a payload is not linear in its
> size, and chatty protocols pay per packet.
