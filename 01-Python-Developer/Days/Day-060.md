# Day 060

**L-060** · ⭐ Error handling design — EAFP vs LBYL, what to catch, what to never catch

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: catch an exception only if you can do something about it. Everything
> else belongs at the boundary, where there is exactly one handler and it knows what the outside
> world should see.**
>
> ⭐ Day 059 was the mechanics. **This is the day that decides whether your service is debuggable.**

---

# Part 1 — ⭐⭐ The two categories

```
⭐⭐ EVERY ERROR IS ONE OF TWO THINGS, AND THEY WANT OPPOSITE TREATMENT:

⭐ 1. ⭐⭐ EXPECTED — part of the domain. It WILL happen in normal operation.
⭐      user not found · insufficient funds · invalid input · the upstream is down
⭐      ⇒ ⭐ handle it. It has a defined outcome: a 404, a 409, a retry, a queued job.
⭐      ⇒ ⭐⭐ it is NOT a bug, so it must not page anyone.
⭐
⭐ 2. ⭐⭐ UNEXPECTED — a bug. A None where there should not be one. A KeyError in your own dict.
⭐      ⇒ ⭐⭐ DO NOT HANDLE IT. Let it reach the boundary, return 500, log with the traceback,
⭐        and ALERT. The correct response is to fix the code.
⭐      ⇒ ⭐ catching it hides the bug and produces a service that is "up" and wrong.
```

⭐⭐ **Almost every bad error-handling decision is treating category 2 as category 1** — a broad
`except Exception` that logs and continues, turning a crash into silent corruption. **A crash is
information. Silence is not.**

⚠️ ⭐⭐ **The worst line in Python:**

```python
try:
    process(order)
except Exception:
    pass                    # ⭐⭐ the order is not processed. Nobody knows. Ever.
```

```python
# ⭐ Barely better, and still wrong:
except Exception as e:
    logger.error(f"failed: {e}")     # ⚠️ ⭐⭐ NO TRACEBACK — you logged the symptom
                                     #     and threw away the only evidence of the cause
# ⭐⭐ If you must log:
except Exception:
    logger.exception("processing order %s failed", order.id)   # ⭐ full traceback + context
    raise                                                      # ⭐⭐ and let it propagate
```

⭐⭐ **`logger.exception` rather than `logger.error(str(e))` is one of the highest-value habits on this
page.** `str(e)` on a `KeyError` is just `'user_id'` — **no file, no line, no call chain.**

# Part 2 — ⭐⭐ Where to catch

```
⭐⭐ ONE HANDLER PER ENTRY POINT. Not one per function.

⭐   HTTP request  ⇒ ⭐ a middleware / exception handler ⇒ maps domain errors to status codes
⭐   Queue consumer ⇒ ⭐ one handler ⇒ ack, retry, or dead-letter
⭐   CLI command   ⇒ ⭐ one handler ⇒ a message and an exit code
⭐   Scheduled job ⇒ ⭐ one handler ⇒ log, alert, exit non-zero
⭐
⭐ ⇒ ⭐⭐ EVERYTHING IN BETWEEN EITHER HANDLES SOMETHING SPECIFIC OR LETS IT THROUGH.
```

```python
# ⭐⭐ FastAPI — the whole error policy in one place (Days 010, 059):
@app.exception_handler(BillingError)
async def billing_handler(request, exc: BillingError):
    match exc:
        case InsufficientFunds():   status = 409
        case PaymentDeclined():     status = 402
        case ProviderUnavailable(): status = 503
    return JSONResponse({"code": type(exc).__name__, "detail": str(exc)}, status_code=status)
```

⭐⭐ **This is why the domain raises domain exceptions and never `HTTPException`.** ⭐ The business
logic has no idea HTTP exists, it is testable without a web framework, and **the mapping from domain
failure to status code lives in exactly one file** — which is also where you enforce that a 4xx never
pages anyone and a 5xx always does (Day 010).

## ⭐ Translate at layer boundaries

```python
# ⭐⭐ The repository turns driver errors into domain errors — and nothing above it
#    ever imports psycopg:
class UserRepo:
    def get(self, user_id) -> User:
        try:
            row = self._db.fetchone(SQL, user_id)
        except psycopg.OperationalError as e:
            raise RepositoryUnavailable() from e     # ⭐ Day 059
        if row is None:
            raise UserNotFound(user_id)              # ⭐⭐ a domain fact, not a driver fact
        return User.from_row(row)
```

⭐⭐ **Without translation, your HTTP layer ends up catching `psycopg.OperationalError`** — and now
swapping the database means editing the web layer. **Exception types leak across layers exactly like
imports do, and they are easier to miss.**

# Part 3 — ⭐ EAFP, LBYL, and what to *never* catch

```python
# ⭐ EAFP — the Python default (Day 023)
try:
    return cache[key]
except KeyError:
    return compute(key)

# ⭐ LBYL — correct here, because "missing" is not exceptional and the check is cheap:
if key in cache: ...
```

```
⭐⭐ THE HONEST RULE, since both are fine:
⭐   EAFP when the failure is genuinely UNLIKELY  ⇒ the happy path pays nothing (Day 059)
⭐   EAFP when a CHECK CAN GO STALE               ⇒ ⭐⭐ os.path.exists() then open() is a RACE;
⭐                                                   the file can vanish in between (TOCTOU)
⭐   LBYL when failure is COMMON and the check is cheap ⇒ raising is the expensive part
⭐   LBYL when the check is CLEARER               ⇒ readability is a real argument
```

```
⭐⭐ NEVER CATCH:
⭐   ✗ bare `except:`                    ⇒ swallows Ctrl-C and SystemExit (Day 059)
⭐   ✗ `except Exception: pass`          ⇒ ⭐⭐ the worst two lines in Python
⭐   ✗ ⭐ anything you cannot act on      ⇒ let it reach the boundary
⭐   ✗ ⭐⭐ inside a loop, to "keep going" ⇒ unless you COUNT the failures and report them,
⭐        a batch job that skips broken rows silently is a data-loss incident in slow motion
⭐   ✗ ⭐ around a whole function         ⇒ you cannot tell WHICH call failed
```

```python
# ⭐⭐ THE ONE LEGITIMATE "keep going" SHAPE — because it is accountable:
failures = []
for row in rows:
    try:
        process(row)
    except RowError as e:                     # ⭐ SPECIFIC
        failures.append((row.id, e))          # ⭐⭐ recorded, not swallowed
if failures:
    logger.error("%d of %d rows failed", len(failures), len(rows))
    raise BatchPartiallyFailed(failures)      # ⭐⭐ someone finds out
```

# Part 4 — ⭐ Retries, timeouts, and failing fast

```
⭐⭐ RETRY ONLY WHEN ALL THREE HOLD (Days 010, 044):
⭐   1. the error is TRANSIENT — a timeout, a 503, a connection reset
⭐      ⇒ ⭐⭐ retrying a 400 or a ValidationError is pure waste, forever
⭐   2. ⭐⭐ the operation is IDEMPOTENT, or you send an idempotency key
⭐      ⇒ ⭐⭐ a retried POST double-charges the customer
⭐   3. there is a BOUND — a max attempt count and a total deadline
⭐
⭐ ⭐⭐ AND: exponential backoff WITH JITTER. Without jitter, every client that failed
⭐   at the same moment retries at the same moment — a thundering herd (Stage 12).
```

```python
# ⭐⭐ EVERY NETWORK CALL HAS A TIMEOUT. No exceptions.
httpx.get(url, timeout=5.0)          # ⭐ default in httpx is 5s; in `requests` it is NONE
requests.get(url, timeout=5)         # ⚠️ ⭐⭐ without this, a hung server holds your worker FOREVER
```

⚠️ ⭐⭐ **`requests` has no default timeout, and this is one of the most common production hangs in
Python.** ⭐ A worker blocked on a socket read never returns, the pool exhausts, and the service stops
responding — **presenting as "the app is down" with no error and no traceback anywhere.**

```
⭐⭐ FAIL FAST AT STARTUP (Day 021): validate config, check required env vars, and let the
⭐   process REFUSE TO START rather than discovering at the first request.
⭐   ⇒ ⭐ a deploy that fails is an incident lasting seconds; a service that starts and
⭐     serves errors is an incident lasting until someone notices.
```

| ⭐ Anti-pattern | ⭐ Instead |
|---|---|
| `except Exception: pass` | ⭐⭐ Let it propagate. |
| ⭐ Log-and-re-raise at every level | ⭐⭐ Log **once**, at the boundary — otherwise one error prints five times |
| Returning `None` on failure | ⭐ Raise, or return an explicit `Result`. `None` gets ignored. |
| ⭐ Catching to convert to a bool | ⭐ You destroyed the reason |
| ⭐⭐ A default that hides a failure | ⭐ `config.get("timeout", 30)` where a missing key is a bug |
| Retrying everything | ⭐ Transient + idempotent + bounded |
| A `try` around 40 lines | ⭐ You cannot tell what failed |

⭐⭐ **"Log once, at the boundary" is worth stating in a review:** a chain of five functions each
logging and re-raising produces five entries for one failure, which makes the log unreadable and the
alert count meaningless. **Add *context* on the way up with `add_note` or by translating; log at the
top.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`except Exception: pass`** | ⭐⭐ Silent failure. The worst two lines in Python. |
| ⭐⭐ **`logger.error(str(e))`** | ⭐⭐ No traceback. `logger.exception`. |
| Treating bugs as expected errors | ⭐ Let them crash, alert, and get fixed. |
| Catching in every function | ⭐ One handler per entry point. |
| Raising `HTTPException` from the domain | ⭐⭐ Domain errors; map once at the edge. |
| Letting driver exceptions cross layers | ⭐ Translate with `from`. |
| ⭐ `os.path.exists()` then `open()` | ⭐⭐ TOCTOU race. Just open it. |
| Skipping bad rows silently | ⭐⭐ Count them and fail the batch. |
| ⭐⭐ **A request with no timeout** | ⭐⭐ A hung server holds the worker forever. |
| Retrying non-idempotent operations | ⭐ Double-charges. Idempotency key. |
| Backoff with no jitter | ⭐ Thundering herd. |
| Log-and-re-raise at each level | ⭐ Five log lines, one failure. |

## Interview questions

**Q: When should you catch an exception?**
> Only when I can do something about it — retry, fall back, translate it for a caller, or produce a
> defined outcome like a 404. Everything else belongs at the boundary. The distinction underneath is
> between expected errors, which are part of the domain and have a defined response, and unexpected
> ones, which are bugs: those should propagate, return a 500, log with the traceback and alert,
> because the correct fix is to change the code. Almost every bad decision here is treating a bug as
> an expected error, which turns a crash into silent wrongness — and a crash is information.

**Q: What's wrong with `except Exception as e: logger.error(str(e))`?**
> Two things. It has no traceback — `str(e)` on a `KeyError` is just the key name, with no file, line
> or call chain — so you've logged the symptom and discarded the only evidence of the cause.
> `logger.exception` inside an except block records the whole traceback. And it swallows: unless it
> re-raises, the caller believes the operation succeeded. If I'm catching to add context, I log once
> and re-raise; if I can't act on it, I don't catch it at all.

**Q: Where do you put error handling in a web service?**
> One handler per entry point. The domain raises domain exceptions and never imports anything
> web-shaped, the repository translates driver errors into domain errors with `raise ... from`, and a
> single exception handler at the HTTP boundary maps domain errors to status codes. That gives me one
> file where the whole error policy lives — including the rule that 4xx never pages anyone and 5xx
> always does — and a domain layer I can test without a web framework. Without the translation step,
> the HTTP layer ends up catching `psycopg.OperationalError`, and swapping the database means editing
> the web layer.

**Q: EAFP or LBYL?**
> EAFP when the failure is genuinely unlikely, since a `try` that doesn't raise costs nothing, and
> always when a check could go stale — `os.path.exists` followed by `open` is a time-of-check
> to time-of-use race, and the file can disappear in between. LBYL when failure is common, because
> raising is the expensive part, or when the check is simply clearer. Both are fine; the wrong move is
> picking one dogmatically.

**Q: When is it acceptable to keep going after an error in a loop?**
> When the failures are counted and reported. Catching a specific exception per row, collecting the
> failures, and then raising or alerting with the count at the end is accountable. Catching broadly and
> continuing is a data-loss incident in slow motion: the job reports success, the rows are missing, and
> nobody finds out until a reconciliation months later. The test is whether someone learns that it
> happened.

**Q: What's the most common production hang you've seen in Python?**
> A network call with no timeout. `requests` has no default, so a hung server holds the worker
> indefinitely; the pool exhausts, and the service stops responding with no error and no traceback
> anywhere — it presents as "the app is down". Every outbound call gets an explicit timeout, and
> retries only when the error is transient, the operation is idempotent, and the attempts are bounded
> — with jitter on the backoff, or every client that failed together retries together.

## 🎙️ Articulation drill

Record two minutes: **"How do you structure error handling in a backend service?"**

⭐ Lead with the classification, because everything follows from it: **expected errors are part of the
domain and have a defined outcome; unexpected ones are bugs and must be allowed to crash, log with a
traceback, and alert.** Treating the second as the first is how a service ends up "up" and wrong.

⭐ Then the layering: **domain code raises domain exceptions and never imports anything web-shaped;
the repository translates driver errors with `raise ... from`, so nothing above it knows which
database you use; and one exception handler at the entry point maps domain errors to status codes.**
One file holds the whole policy, including which failures page someone.

⭐⭐ **Then the two operational rules that separate this from a textbook answer:** *"log once, at the
boundary — a chain of functions each logging and re-raising gives five entries for one failure and
makes both the log and the alert count meaningless; add context on the way up instead. And every
outbound call gets an explicit timeout, because `requests` has no default and a hung upstream holds a
worker forever — the pool exhausts and the service stops responding with no error anywhere, which
presents as 'the app is down' and is the hardest kind of incident to diagnose."*
