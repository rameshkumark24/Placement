> ⭐⭐ **The sentence to own: Kafka gives you a log with a cursor; RabbitMQ gives you a broker that

# Part 1 — The AMQP model, and where the difference lives

```
⭐   producer → ⭐⭐ EXCHANGE → (binding) → QUEUE → consumer

⭐⭐ ***THE PRODUCER NEVER NAMES A QUEUE. IT PUBLISHES TO AN
⭐   EXCHANGE WITH A ROUTING KEY, AND THE ***BROKER*** DECIDES
⭐   WHERE IT GOES.*** ⭐ That single indirection is the
⭐   fundamental difference from Kafka, where routing is the
⭐   consumer's problem and the producer just picks a partition.

⭐ FOUR EXCHANGE TYPES:
⭐   ⭐ `direct` — routing key must match the binding key exactly.
⭐   ⭐⭐ `topic` — WILDCARD PATTERNS: `order.*.eu`,
⭐     `payment.#`. ⭐ The one you will actually use.
⭐   ⭐ `fanout` — every bound queue gets a copy. ⭐ Ignores the
⭐     key.
⭐   ⭐ `headers` — match on header values. ⭐ Rare.

⭐⭐ ⇒ AND THE CONSEQUENCE THAT MATTERS ARCHITECTURALLY: ***ADDING
⭐   A CONSUMER IS A NEW QUEUE AND A NEW BINDING — A BROKER-SIDE
⭐   OPERATION WITH NO PRODUCER CHANGE AND NO DEPLOY.*** ⭐ Which
⭐   is the property Day 393 wanted from SNS→SQS, ⭐⭐ AVAILABLE
⭐   HERE AS ONE COMPONENT RATHER THAN TWO.
```

# Part 2 — ⭐⭐ Per-message acknowledgement, and the four things it buys

```
⭐ IN KAFKA THE CURSOR IS A ***NUMBER***, SO PROGRESS IS
⭐   INHERENTLY ORDERED AND ALL-OR-NOTHING.
⭐⭐ IN RABBITMQ THE BROKER TRACKS ***EACH MESSAGE*** — delivered,
⭐   acked, nacked, redelivered. ⭐ That costs memory and
⭐   throughput. ⭐⭐ AND IT BUYS FOUR THINGS KAFKA STRUCTURALLY
⭐   CANNOT DO:

⭐ ① ⭐⭐ ***A SINGLE MESSAGE CAN FAIL AND RETRY ALONE.***
⭐    ⭐ `basic_nack(requeue=True)` and only that message comes
⭐    back. ⭐⭐ IN KAFKA A POISON MESSAGE EITHER BLOCKS ITS
⭐    PARTITION OR YOU COMMIT PAST IT AND LOSE IT — ⭐ there is no
⭐    third behaviour. ⭐⭐ THIS IS THE BIGGEST PRACTICAL
⭐    DIFFERENCE AND IT DECIDES MOST REAL CHOICES.

⭐ ② ⭐⭐ ***REAL PER-CONSUMER BACKPRESSURE VIA PREFETCH.***
⭐    ⭐ `basic_qos(prefetch_count=N)` — ⭐⭐ THE BROKER WILL NOT
⭐    SEND YOU AN N+1-TH UNACKED MESSAGE. ⭐ So a slow consumer
⭐    automatically receives less work and a fast one receives
⭐    more, ⭐⭐ WITH NO COORDINATION AND NO REBALANCE (DAY 336's
⭐    BACKPRESSURE, PROVIDED BY THE BROKER).

⭐ ③ ⭐⭐ ***DELAY AND SCHEDULED DELIVERY.*** ⭐ Via the
⭐    delayed-message plugin, ⭐ or the classic TTL + dead-letter
⭐    trick (Part 6). ⭐⭐ KAFKA HAS NO ANSWER FOR "RETRY THIS IN
⭐    FIVE MINUTES" AT ALL — ⭐ people build a whole extra topic
⭐    per delay tier and a scheduler, ⭐⭐ AND IT IS ALWAYS UGLY.

⭐ ④ ⭐ ***PRIORITY QUEUES.*** ⭐ `x-max-priority`. ⭐⭐ USE
⭐    SPARINGLY — ⭐ priority inversion and starvation are real —
⭐    ⭐ but it exists, and in Kafka it does not.

⭐⭐ ⇒ AND WHAT YOU GIVE UP, SO THE COMPARISON IS FAIR:
⭐   ⭐⭐ NO REPLAY (AN ACKED MESSAGE IS ***GONE***), ⭐ no second
⭐   independent consumer of the same history, ⭐ throughput an
⭐   order of magnitude lower, ⭐⭐ AND ORDERING ONLY WITHIN A
⭐   QUEUE WITH ONE CONSUMER — ⭐ two consumers on one queue
⭐   process concurrently and out of order.
```

# Part 3 — ⭐⭐ The decision, in one table

| Need | Answer |
|---|---|
| Retry one message without touching others | ⭐⭐ **RabbitMQ / SQS** |
| Delay, backoff, scheduled delivery | ⭐⭐ **RabbitMQ / SQS** |
| Priority | ⭐ RabbitMQ |
| Broker-side routing to many queues | ⭐ RabbitMQ |
| Per-consumer backpressure | ⭐ RabbitMQ |
| **Replay history** | ⭐⭐ **Kafka** |
| **Several independent consumers of one stream** | ⭐⭐ **Kafka** |
| Ordered per-key history | ⭐⭐ **Kafka** |
| >100k msg/s sustained | ⭐⭐ **Kafka** |
| A topic as a source of truth / rebuildable state | ⭐⭐ **Kafka (compacted)** |
| 100 msg/s and no operations team | ⭐⭐ **SQS** |

```
⭐⭐ ⇒ AND THE ANSWER TO "WE NEED BOTH", WHICH IS COMMON AND IS
⭐   NOT A FAILURE: ***THE EVENT LOG IS KAFKA AND THE WORK QUEUE
⭐   IS RABBITMQ OR SQS.*** ⭐ Events describe what happened and
⭐   must be replayable; ⭐ tasks describe what to do and need
⭐   per-message retry. ⭐⭐ THOSE ARE DIFFERENT PROBLEMS AND
⭐   DAY 393's COMMANDS-VS-EVENTS DISTINCTION IS EXACTLY THE LINE
⭐   BETWEEN THEM. ⭐ Two brokers is a legitimate architecture
⭐   ⭐⭐ IF YOU CAN SAY WHICH ONE CARRIES WHICH, IN ONE SENTENCE.
```

# Part 4 — Durability: four things, and three of four loses data

```
⭐⭐ ***ALL FOUR ARE REQUIRED. ANY THREE SILENTLY LOSES
⭐   MESSAGES.***
⭐ ① ⭐ `durable=True` on the exchange
⭐ ② ⭐ `durable=True` on the queue
⭐ ③ ⭐ `delivery_mode=2` (persistent) on the ***message***
⭐    ⭐⭐ — A PERSISTENT MESSAGE IN A NON-DURABLE QUEUE DIES WITH
⭐    THE BROKER, AND A TRANSIENT MESSAGE IN A DURABLE QUEUE DIES
⭐    TOO. ⭐ People set one and believe they set both.
⭐ ④ ⭐⭐ ***PUBLISHER CONFIRMS*** (`confirm_delivery()`) — ⭐ or
⭐    `basic_publish` returns immediately and you have no idea
⭐    whether the broker took it. ⭐⭐ SAME SHAPE AS DAY 401's
⭐    MISSING `flush()`.

⭐ QUEUE TYPES:
⭐   ⭐⭐ ***QUORUM QUEUES*** — ⭐ Raft-replicated (Day 410!),
⭐     ⭐⭐ THE MODERN DEFAULT FOR ANYTHING THAT MATTERS. ⭐ Survive
⭐     a broker loss with a majority. ⭐ Higher memory and lower
⭐     throughput than classic. ⭐⭐ ACCEPT THAT.
⭐   ⭐ ***CLASSIC MIRRORED QUEUES*** — ⭐⭐ DEPRECATED. ⭐ If you
⭐     have them, migrate.
⭐   ⭐ ***STREAMS*** — RabbitMQ's Kafka-like append-only type.
⭐     ⭐ Worth knowing it exists; ⭐⭐ IF YOU NEED IT, ASK WHETHER
⭐     YOU NEEDED KAFKA.

⭐⭐ AND THE FAILURE MODE PEOPLE ACTUALLY HIT: ***A CLASSIC QUEUE
⭐   HOLDS MESSAGES IN MEMORY.*** ⭐ A consumer outage during a
⭐   traffic peak fills the queue, ⭐⭐ THE BROKER HITS ITS MEMORY
⭐   HIGH WATERMARK, AND IT BLOCKS ***ALL PUBLISHERS ACROSS EVERY
⭐   QUEUE***. ⭐ One stuck consumer takes down publishing for
⭐   unrelated services. ⭐⭐ ⇒ LAZY MODE / QUORUM QUEUES, A
⭐   `x-max-length` LIMIT WITH AN OVERFLOW POLICY, AND AN ALARM
⭐   ON QUEUE DEPTH ***AND*** ON BROKER MEMORY.
```

# Part 5 — ⭐⭐ Python: pika's trap, and Celery's dangerous defaults

```
⭐⭐ ***`pika` IS NOT THREAD-SAFE.*** ⭐ A `BlockingConnection` and
⭐   its channels must be used from ***one*** thread. ⭐ Sharing
⭐   one across a thread pool produces frame corruption,
⭐   ⭐⭐ WHICH PRESENTS AS RANDOM `StreamLostError` AND
⭐   `UnexpectedFrameError` THAT LOOK LIKE NETWORK PROBLEMS AND
⭐   ARE NOT. ⭐ ⇒ one connection per thread, ⭐ or
⭐   `add_callback_threadsafe`, ⭐⭐ OR USE `aio-pika` AND STOP
⭐   THINKING ABOUT IT.
⭐ ⭐ And heartbeats: ⭐⭐ A LONG BLOCKING HANDLER STOPS pika
⭐   SERVING HEARTBEATS, THE BROKER DECIDES YOU ARE DEAD AND
⭐   CLOSES THE CONNECTION, ⭐ and the message is redelivered
⭐   while you are still processing it — ⭐⭐ WHICH IS EXACTLY
⭐   DAY 393's VISIBILITY-TIMEOUT FAILURE IN A DIFFERENT BROKER.
```

```python
# ⭐⭐ CELERY: THE FIVE SETTINGS TO CHANGE ON DAY ONE.
# ⭐   The defaults are optimised for a demo, not for a system
# ⭐   that must not lose work.
app.conf.update(
    task_acks_late=True,              # ⭐⭐ DEFAULT False = THE
        # ⭐ MESSAGE IS ACKED ***BEFORE*** YOUR TASK RUNS, SO A
        # ⭐ WORKER CRASH LOSES IT ENTIRELY, SILENTLY.
    task_reject_on_worker_lost=True,  # ⭐⭐ REQUIRED PARTNER OF
        # ⭐ acks_late, or a killed worker's task is still lost.
    worker_prefetch_multiplier=1,     # ⭐⭐ DEFAULT 4 × concurrency
        # ⭐ ⇒ ONE WORKER GRABS 16 TASKS AND SITS ON THEM WHILE
        # ⭐ IDLE WORKERS WAIT — head-of-line blocking (Day 336).
    broker_transport_options={"visibility_timeout": 3600},
        # ⭐⭐ SQS/REDIS BROKERS ONLY — MUST EXCEED YOUR LONGEST
        # ⭐ TASK OR IT REDELIVERS MID-EXECUTION.
    result_expires=3600,              # ⭐⭐ DEFAULT KEEPS RESULTS
        # ⭐ FOR A DAY; A REDIS RESULT BACKEND GROWS UNTIL IT OOMs.
    task_time_limit=300,              # ⭐ hard kill
    task_soft_time_limit=270,         # ⭐⭐ RAISES SoftTimeLimitExceeded
        # ⭐ SO YOU CAN CLEAN UP — Day 378's SIGTERM, in Celery.
)
```

```
⭐⭐ AND THE HONEST ASSESSMENT OF CELERY, BECAUSE YOU WILL BE
⭐   ASKED: ⭐ it is the default Python task queue, it works, it
⭐   has a decade of production behind it. ⭐⭐ ITS DEFAULTS ARE
⭐   DANGEROUS, ITS REDIS TRANSPORT IS NOT A REAL BROKER (NO
⭐   PUBLISHER CONFIRMS, VISIBILITY-TIMEOUT SEMANTICS BOLTED ON),

# Part 6 — The delayed-retry pattern, which is the reason to reach for RabbitMQ

```
⭐⭐ ***THE DLX + TTL TRICK.*** ⭐ This is the pattern that makes
⭐   exponential backoff possible without a scheduler:

⭐   ┌──────────────┐  nack/reject   ┌────────────────────┐
⭐   │ work.queue   │ ─────────────► │ retry.5s           │
⭐   │              │                │ x-message-ttl=5000 │
⭐   │              │ ◄───────────── │ x-dead-letter-     │
⭐   └──────────────┘  ⭐⭐ ON TTL     │   exchange=work    │
⭐                     ⭐⭐ EXPIRY     └────────────────────┘

⭐ ⭐ A rejected message dead-letters into `retry.5s`, ⭐ which has
⭐   ***no consumer*** — ⭐⭐ SO IT SIMPLY SITS THERE UNTIL ITS TTL
⭐   EXPIRES, ⭐ at which point it dead-letters ***back*** into the
⭐   work exchange. ⭐⭐ A DELAY, IMPLEMENTED WITH TWO QUEUE
⭐   ARGUMENTS AND NO CODE.
⭐ ⭐ Chain `retry.5s → retry.30s → retry.5m → parked` for
⭐   exponential backoff, ⭐⭐ AND USE A HEADER TO COUNT ATTEMPTS
⭐   SO YOU CAN STOP.
⭐ ⭐⭐ ONE TRAP: ***TTL EXPIRY IS CHECKED AT THE HEAD OF THE
⭐   QUEUE ONLY.*** ⭐ A message with a 5-second TTL behind one
⭐   with a 5-minute TTL waits five minutes. ⭐⭐ ⇒ ONE QUEUE PER
⭐   DELAY TIER, NOT PER-MESSAGE TTLs.
```

# Part 7 — Operating it

```
⭐ ⭐⭐ ***RABBITMQ SCALES UP, NOT OUT, FOR A SINGLE QUEUE.***
⭐   ⭐ Clustering spreads ***different*** queues across nodes and
⭐   replicates them; ⭐⭐ IT DOES NOT SHARD ONE QUEUE. ⭐ If one
⭐   queue is your bottleneck, the answer is more queues (shard
⭐   by key yourself) ⭐⭐ OR IT IS KAFKA.
⭐ ⭐ Network partitions: ⭐⭐ `cluster_partition_handling =
⭐   pause_minority` IS THE RIGHT SETTING. ⭐ The default
⭐   (`ignore`) permits split brain and you reconcile by hand
⭐   (Day 412).
⭐ ⭐ Monitor: ⭐ `messages_ready`, ⭐⭐ `messages_unacknowledged`
⭐   (A LARGE NUMBER MEANS CONSUMERS TOOK WORK AND ARE NOT
⭐   FINISHING), ⭐ consumer count, ⭐ broker memory and disk
⭐   watermarks, ⭐ redelivery rate.
⭐ ⭐⭐ AND THE MANAGED OPTION IS USUALLY RIGHT: ⭐ Amazon MQ or
⭐   CloudAMQP. ⭐⭐ SAME QUESTION AS EVERY DAY IN STAGE 11 —

# 💬 Interview

**1. ⭐⭐ "Kafka or RabbitMQ?"**
> ⭐ One question decides it: ⭐⭐ **do you need per-message behaviour, or replayable history?** ⭐ Per
> message — retry one message without touching the others, delay it five minutes, prioritise it,
> apply backpressure per consumer — that's RabbitMQ or SQS. ⭐ Replay, several independent consumers of
> the same stream, ordered per-key history, or throughput a broker can't reach — that's Kafka.
> ⭐⭐ **And the biggest practical difference is the first one: in Kafka a poison message either blocks
> its partition or you commit past it and lose it, and there is no third behaviour.** ⭐ "We need both"
> is common and isn't a failure: ⭐⭐ **the event log is Kafka and the work queue is RabbitMQ or SQS —
> events describe what happened and must be replayable, tasks describe what to do and need per-message
> retry.**

**2. "What does RabbitMQ's per-message tracking actually buy?"**
> ⭐ Four things Kafka structurally can't do. ⭐⭐ **Single-message nack and requeue. Real backpressure
> through prefetch, where the broker won't send you an N+1-th unacked message, so a slow consumer
> automatically gets less work with no rebalance. Delayed and scheduled delivery. And priority.**
> ⭐ Kafka has no answer to "retry this in five minutes" at all — ⭐⭐ **people end up building a topic
> per delay tier plus a scheduler, and it's always ugly.** ⭐ What you give up is real too: no replay,
> no second independent consumer of the same history, an order of magnitude less throughput, and
> ordering only within a queue served by one consumer.

**3. ⭐⭐ "How do you make RabbitMQ durable?"**
> ⭐ Four things, and any three silently loses messages: ⭐⭐ **a durable exchange, a durable queue,
> `delivery_mode=2` on the message itself, and publisher confirms.** ⭐ People set the queue durable and
> believe they've set the message persistent — ⭐⭐ **a persistent message in a non-durable queue dies
> with the broker, and so does a transient message in a durable one.** ⭐ And without publisher confirms
> `basic_publish` returns immediately with no idea whether the broker took it, which is the same shape
> as Kafka's missing `flush()`. ⭐ For queue type I'd use quorum queues — ⭐⭐ **they're Raft-replicated
> and the modern default; classic mirrored queues are deprecated.**

**4. ⭐⭐ "One consumer stopped and publishing broke for unrelated services. Explain."**
> ⭐ That's the classic-queue memory failure. ⭐⭐ **A classic queue holds messages in memory, so a
> consumer outage during a peak fills it, the broker hits its memory high watermark, and it blocks all
> publishers across every queue** — one stuck consumer takes down publishing for services that have
> nothing to do with it. ⭐ The fixes are quorum or lazy queues so messages go to disk, ⭐⭐ **an
> `x-max-length` with an overflow policy so a queue is bounded, and alarms on both queue depth and
> broker memory** — because the depth alarm alone won't tell you you're about to block everyone.

**5. ⭐⭐ "What would you change about Celery's defaults?"**
> ⭐ Five things on day one. ⭐⭐ **`task_acks_late=True`, because the default acks the message before
> your task runs, so a worker crash loses the task entirely and silently** — with
> `task_reject_on_worker_lost=True` as its required partner. ⭐⭐ **`worker_prefetch_multiplier=1`,
> because the default of four times concurrency means one worker grabs sixteen tasks and sits on them
> while other workers idle** — head-of-line blocking. ⭐ `result_expires`, or a Redis result backend
> grows until it OOMs. ⭐ And a soft time limit as well as a hard one, so the task can clean up. ⭐⭐ **My
> honest assessment is that Celery works and has a decade of production behind it, but its defaults
> are dangerous and its Redis transport isn't a real broker** — `dramatiq` has better defaults, and
> anything with multi-step state wants Temporal.

**6. "How do you do exponential backoff in RabbitMQ?"**
> ⭐⭐ **A chain of TTL queues with dead-letter exchanges.** ⭐ A rejected message dead-letters into a
> `retry.5s` queue that has no consumer, so it just sits there until its TTL expires, at which point
> it dead-letters back into the work exchange. ⭐⭐ **A delay implemented with two queue arguments and no
> code.** ⭐ Chain 5s → 30s → 5m → parked, and count attempts in a header so you can stop. ⭐ One trap:
> ⭐⭐ **TTL expiry is only checked at the head of the queue, so a five-second message behind a
> five-minute one waits five minutes — which means one queue per delay tier, never per-message TTLs.**
