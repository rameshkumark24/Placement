# Day 231 🌍

**P-231** · 🌍 **Context** — ⭐⭐ a dependency injection mechanism, not a state manager

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: Context solves *delivery* — getting a value to a deep component without
> threading it through every layer — and solves nothing about *storage*, so putting frequently
> changing state in it re-renders every consumer in the tree and turns a local update into an
> application-wide one.**
>
> Today: what it is for, ⭐ the composition fix you should try first, ⭐⭐ the re-render problem, and
> the split-context pattern.

---

# Part 1 — What it is for

```jsx
const ThemeContext = createContext<Theme>("light");

<ThemeContext.Provider value={theme}>
  <App />                       {/* ⭐ any depth below can read it */}
</ThemeContext.Provider>

function DeepButton() {
  const theme = useContext(ThemeContext);   // ⭐ no props threaded
}
```

```
⭐⭐ THE HONEST LIST OF WHAT BELONGS IN CONTEXT

⭐   ✅ ⭐ THE CURRENT USER / SESSION      (changes ~never)
⭐   ✅ theme, locale, timezone            (changes ~never)
⭐   ✅ a router                           (the library provides it)
⭐   ✅ ⭐ A QUERY CLIENT / DI CONTAINER    (a stable object)
⭐   ✅ a feature-flag set                  (changes ~never)

⭐   ❌ ⭐⭐ FORM STATE          ⇒ it changes per keystroke
⭐   ❌ ⭐⭐ SERVER DATA         ⇒ that is a cache (Day 228)
⭐   ❌ "the selected row"      ⇒ ⭐ lift to the common parent
⭐   ❌ everything, to avoid props ⇒ ⭐⭐ THAT IS A GLOBAL VARIABLE
⭐                                  WITH EXTRA STEPS

⭐   ⇒ ⭐⭐ THE PATTERN: CONTEXT IS FOR THINGS THAT ARE **WIDE AND SLOW**.
⭐     Wide and FAST is the failure. Narrow and fast is just useState.
```

---

# Part 2 — ⭐ Try composition first

```jsx
// ❌ prop drilling — the problem
<Page user={user}><Sidebar user={user}><Nav user={user}><Avatar user={user}/>

// ✅ FIX 1 — pass the ELEMENT, not the data. ⭐⭐ TRY THIS FIRST.
<Page sidebar={<Sidebar nav={<Nav avatar={<Avatar user={user} />} />} />} />
//    ⭐ Sidebar and Nav no longer know `user` exists at all.

// ✅ FIX 2 — children
<Layout><Avatar user={user} /></Layout>

// ✅ FIX 3 — Context, when the value is genuinely global AND stable
```

> ⭐⭐ **Most prop drilling is a composition problem wearing a Context-shaped hat.** The middle
> components did not need the data — they needed to *render something* they were not given. Reaching
> for Context first makes every intermediate component implicitly coupled to a global, which is
> exactly what you were trying to avoid.

# Part 3 — ⭐⭐ The re-render problem

```jsx
// ❌ THE BUG THAT MAKES PEOPLE SAY "CONTEXT IS SLOW"
<AppContext.Provider value={{ user, theme, cart, setCart }}>
//                          ⭐⭐ NEW OBJECT LITERAL EVERY RENDER
```

```
⭐⭐ WHY THIS IS EXPENSIVE

⭐   ① ⭐ the provider re-renders (any state change above it)
⭐   ② ⭐⭐ value IS A NEW OBJECT ⇒ Object.is says CHANGED
⭐   ③ ⭐⭐ **EVERY** useContext CONSUMER RE-RENDERS.
⭐      ⭐ React.memo DOES NOT SAVE THEM — context bypasses memo
⭐        entirely, because the dependency is not a prop.
⭐   ⇒ ⭐⭐ ONE CART UPDATE RE-RENDERS EVERY COMPONENT THAT READS
⭐     THEME. They are unrelated. Nothing tells you.

⭐   ⇒ ⭐ IT IS DAY 215'S {a:1} !== {a:1} FOR THE THIRD TIME —
⭐     dependency arrays, memo, and now context.
```

| ⭐ Fix | |
|---|---|
| **Memoise the value** | ⭐ `useMemo(() => ({user, theme}), [user, theme])` — necessary, not sufficient |
| **⭐⭐ Split the contexts** | One per concern. Theme consumers do not re-render on a cart change. **The real fix.** |
| **⭐⭐ Split state from setters** | `CartStateContext` + `CartDispatchContext`. Dispatch is **stable forever**, so components that only *write* never re-render. **The highest-value split.** |
| Put server data in a query cache | ⭐ It was never context's job (Day 228) |

```jsx
// ⭐⭐ the pattern worth memorising
const StateCtx = createContext(null);
const DispatchCtx = createContext(null);      // ⭐ stable, never changes

export function CartProvider({ children }) {
  const [state, dispatch] = useReducer(reducer, initial);
  return (
    <DispatchCtx.Provider value={dispatch}>
      <StateCtx.Provider value={state}>{children}</StateCtx.Provider>
    </DispatchCtx.Provider>
  );
}
// ⇒ ⭐⭐ an "Add to cart" button reads ONLY dispatch ⇒ it NEVER re-renders.
```

# Part 4 — The provider you should actually write

```jsx
const AuthContext = createContext(undefined);   // ⭐⭐ undefined, deliberately

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (ctx === undefined) {                      // ⭐⭐ THE GUARD
    throw new Error("useAuth must be used inside <AuthProvider>");
  }
  return ctx;
}
```

| ⭐ Rule | Why |
|---|---|
| **Default `undefined` + throw** | ⭐⭐ A sensible default silently gives you a logged-out user when the provider is missing — **a bug that renders**. Throwing is loud and correct. |
| **Export the hook, not the context** | ⭐ You keep the freedom to change the implementation, and consumers cannot `useContext` it raw. |
| **One provider per concern** | ⭐ Composable, testable, and each has its own re-render blast radius |
| **Type it** | ⭐ `createContext<AuthValue \| undefined>(undefined)` |

> ⭐ **When people say "we needed Redux/Zustand", the honest reason is usually one of three:** the
> value changes often and is read widely (split the context), the data is server state (use the
> cache), or transitions are complex (use `useReducer`). **A store is legitimate — but reach for it
> fourth, and be able to say which of the three it solves.**

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "when do you use Context?"**

Define it precisely, because the common definition is wrong. **Context solves delivery, not storage.
It gets a value to a deep component without threading it through every layer. It does nothing about
how state is managed — so the rule is that context is for things that are wide and slow: the session,
theme, locale, a query client. Wide and fast is the failure mode.**

Then the failure with its mechanism. **If the provider's value is an object literal, it's a new object
every render, so `Object.is` says it changed and every consumer re-renders — and `React.memo` doesn't
save them, because context bypasses memo entirely. One cart update re-renders every component that
reads theme. They're unrelated, and nothing tells you. That's the same identity comparison that drives
dependency arrays and memo — it's the third time the same fact shows up.**

Then the fixes in priority order. **Split contexts by concern, and split state from dispatch — dispatch
is stable forever, so a button that only writes never re-renders at all. That's the highest-value
split and it's usually what people were about to add a state library for.**

Close on what you try first. **Most prop drilling is a composition problem in disguise. The middle
components didn't need the data, they needed to render something they weren't given — so passing the
element down instead of the data fixes it without coupling every layer to a global. I reach for Context
third, and for a store fourth, and I can say which specific problem the store solves.**
