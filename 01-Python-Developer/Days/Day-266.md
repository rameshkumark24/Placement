# Day 266 ⚡

**P-266** · ⚡ **Caching, measured** — ⭐⭐ not assumed, and not on a hit ratio

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a cache is a second source of truth that you have promised to keep in
> sync, and you made that promise in exchange for a number — so if you cannot state the number, you
> have paid the whole price and bought nothing.**
>
> ⭐ Day 205 gave you the Redis mechanics. ⭐⭐ Today is the engineering decision: whether, where,
> keyed how, invalidated how, and — the part almost everyone skips — proved by what measurement.

# Part 1 — ⭐⭐ What a cache costs before it gives you anything

```
⭐⭐ FOUR COSTS, PAID ON DAY ONE:
⭐   ① ⭐⭐ A SECOND SOURCE OF TRUTH. Every bug report now carries a
⭐     new question — "was it cached?" — and the answer differs
⭐     between your laptop and production. ⭐ Debugging time goes
⭐     up permanently, for every engineer, forever.
⭐   ② ⭐ A SECOND FAILURE MODE. Redis is down, or slow, and your
⭐     p99 now contains a network hop that existed to save time.
⭐   ③ ⭐⭐ A CORRECTNESS SURFACE. Every cache bug is a stale-data
⭐     bug, and the worst class is CROSS-USER (Part 3) — which is
⭐     not a performance regression, it is a breach.
⭐   ④ ⭐ Memory, money, and an eviction policy you now own.

⭐ ⇒ ⭐⭐ SO THE FIRST QUESTION IS NEVER "WHAT SHOULD I CACHE".
⭐   IT IS ***"WHAT IS p99 NOW, AND WHAT WOULD IT BE?"*** (Day 202.)
```

```
⭐⭐ AND THREE THINGS TO DO FIRST, BECAUSE THEY COST NO CORRECTNESS:
⭐   ⭐ THE INDEX — a missing one turns 2 ms into 900 ms (Day 189)
⭐   ⭐ THE N+1 — 200 queries in a loop is not a caching problem
⭐     (Day 255); ⭐⭐ CACHING IT MEANS CACHING 200 QUERIES
⭐   ⭐ THE PAYLOAD — you serialise 90 fields, the UI shows 6

⭐ ⇒ ⭐⭐ A CACHE PUT IN FRONT OF AN N+1 IS THE MOST EXPENSIVE
⭐   MISTAKE IN THIS DAY: it works, so nobody fixes the N+1, and
⭐   the first cold cache after a restart takes the site down —
⭐   at which point the fix is an outage-time fix.
```

# Part 2 — ⭐⭐ Four places to put it

```
⭐⭐ NEAREST THE USER FIRST:

⭐ ① ⭐ CDN / HTTP           static assets, genuinely public GETs
⭐      + costs you nothing to operate
⭐      − ⭐ invalidation is minutes, and shared caches are
⭐        DANGEROUS for anything authenticated (Part 6)

⭐ ② ⭐⭐ APPLICATION (Redis)  computed values, rendered fragments,
⭐      expensive aggregates
⭐      + full control, shared across processes, explicit TTL
⭐      − ⭐ you own every single invalidation

⭐ ③ ⭐ QUERY RESULT         one expensive query's rows
⭐      + narrow and easy to reason about
⭐      − ⭐⭐ OFTEN THE WRONG LAYER: you skipped the database and
⭐        still pay ORM hydration, serialisation, and every other
⭐        query on the request

⭐ ④ ⭐ IN-PROCESS (`lru_cache`)  config, tiny reference tables
⭐      + nanoseconds, no network
⭐      − ⭐⭐ N PROCESSES ⇒ N COPIES ⇒ N STALENESS WINDOWS, AND
⭐        NO WAY TO INVALIDATE. ⭐ Only for data that changes on
⭐        deploy. ⭐⭐ A feature flag in an `lru_cache` is a flag
⭐        you cannot turn off during the incident it caused.
```

```
⭐⭐ THE RULE: CACHE AS FAR ***UP*** AS CORRECTNESS ALLOWS.
⭐   ⭐ Caching the rendered response skips the query, the ORM,
⭐     the mapping and the serialisation. ⭐ Caching the query
⭐     result skips one of those four.
⭐   ⇒ ⭐⭐ AND "AS CORRECTNESS ALLOWS" IS THE WHOLE CONSTRAINT,
⭐     because the further up you go, the more of the request's
⭐     identity is baked into the value — which is Part 3.
```

# Part 3 — ⭐⭐ The key is a security boundary

```
⭐⭐ THE RULE, AND IT IS NOT A PERFORMANCE RULE:
⭐   ***THE KEY MUST CONTAIN EVERY INPUT THAT CHANGES THE VALUE.***

⭐   ❌ f"jobs:list:page:{page}"
⭐   ⭐⭐ MISSING: tenant_id · the caller's role · their filters ·
⭐     the sort order · the serialiser version.
⭐   ⇒ ⭐⭐ A TECHNICIAN AT TENANT B IS SERVED TENANT A'S JOB LIST.
⭐     ⭐ And your authorisation code (Day 259) is perfectly
⭐       correct — ⭐⭐ IT WAS NEVER CALLED, BECAUSE THE CACHE
⭐       ANSWERED ABOVE IT.
⭐   ⇒ ⭐⭐ THIS IS THE SINGLE MOST DAMAGING CACHE BUG THERE IS,
⭐     and it is always a missing key component, never a Redis
⭐     problem.

⭐   ⭐ v1:t{tenant}:u{role}:jobs:{filters_hash}:{cursor}
```

```
⭐⭐ THE COROLLARY, WORTH SAYING OUT LOUD IN A REVIEW:
⭐   ***CACHE BELOW AUTHORISATION, OR PUT IDENTITY IN THE KEY.
⭐      NEVER NEITHER.***
⭐   ⇒ ⭐ Below: run the auth check, then cache the expensive
⭐     computation that follows. Safe by construction.
⭐   ⇒ ⭐ Above: faster, but the key now carries identity, and
⭐     ⭐⭐ EVERY FUTURE FIELD THAT AFFECTS VISIBILITY MUST BE
⭐     REMEMBERED BY THE NEXT PERSON WHO EDITS THAT ENDPOINT.
```

```
⭐⭐ THE ONE PEOPLE MISS: A PERMISSION CHANGE INVALIDATES NOTHING.
⭐   ⭐ You revoke a user's admin role. ⭐⭐ THEIR CACHED ADMIN
⭐     VIEW IS SERVED FOR ANOTHER 300 SECONDS.
⭐   ⇒ ⭐ FIX: a `perm_version` integer per user (or per tenant),
⭐     bumped on any role or membership change, ⭐⭐ AND INCLUDED
⭐     IN THE KEY. The bump invalidates everything for that user
⭐     at once, atomically, without enumerating a single key.
⭐   ⭐ Same trick for deploys: a `v1:` prefix you bump when the
⭐     SHAPE of a cached value changes — because ⭐⭐ YOU CANNOT
⭐     INVALIDATE A SHAPE CHANGE, and the old entries will
⭐     deserialise into the new code and produce nonsense.
```

# Part 4 — ⭐⭐ Invalidation, which is where the bugs live

```
⭐⭐ FOUR RULES, IN ORDER OF HOW OFTEN THEY ARE BROKEN:

⭐ ① ⭐⭐ DELETE, DO NOT UPDATE (Day 205).
⭐      ⭐ Two writers who both SET race, and the loser's value
⭐        survives with a full TTL. ⭐⭐ Two writers who both DEL
⭐        cannot lose: the next reader recomputes from the
⭐        database, which is by definition current.

⭐ ② ⭐⭐ EVERY ENTRY GETS A TTL — INCLUDING ONES YOU DELETE
⭐      EXPLICITLY. ⭐ The TTL is not the invalidation strategy;
⭐      ⭐⭐ IT IS THE BOUND ON THE LIFETIME OF THE INVALIDATION
⭐      YOU FORGOT TO WRITE. ⭐ Without it, one missed `DEL` is a
⭐      permanently wrong value.

⭐ ③ ⭐ CACHE-ASIDE, NOT WRITE-THROUGH, for OLTP: the write path
⭐      stays simple, and a cache outage degrades reads instead
⭐      of failing writes.

⭐ ④ ⭐⭐ FOR DERIVED AND AGGREGATE VALUES, PREFER A SHORT TTL
⭐      OVER A COMPLETE INVALIDATION GRAPH. ⭐ "Jobs completed
⭐      this week per technician" is touched by a dozen writers.
⭐      ⭐⭐ A 60-SECOND TTL IS CORRECT-ENOUGH AND CANNOT ROT;
⭐      A DEPENDENCY GRAPH IS EXACT ON THE DAY YOU WRITE IT AND
⭐      WRONG WITHIN TWO SPRINTS.
```

```
⭐⭐ AND THE ONE YOU MUST NEVER SOLVE WITH A TTL:
⭐   ***ANYTHING THE USER JUST CHANGED THEMSELVES.***
⭐   ⭐ They edit their name, hit save, and see the old one.
⭐   ⇒ ⭐⭐ THIS DESTROYS TRUST IN THE ENTIRE PRODUCT, not just
⭐     in that screen — because the user's conclusion is "it
⭐     didn't save", and their next action is to save again.
⭐   ⇒ ⭐ Targeted `DEL` on the write path, and accept the miss.
⭐     ⭐⭐ Read-your-own-writes is a correctness requirement,
⭐       not a nicety. (Same lesson as replica lag, Day 201.)
```

# Part 5 — ⭐⭐ The stampede, which arrives at 99.9% hit rate

```
⭐⭐ 3,000 rps ON ONE KEY. TTL 60 s. REBUILD TAKES 900 ms.
⭐   t = 60.000   the key expires
⭐   t = 60.001   ⭐⭐ ~2,700 REQUESTS MISS AND ALL START REBUILDING
⭐   ⇒ 2,700 concurrent copies of your most expensive query.

⭐ ⇒ ⭐⭐ THE DATABASE FALLS OVER AT THE PRECISE MOMENT THE CACHE
⭐   WAS WORKING PERFECTLY — ⭐ and the hit-ratio panel shows
⭐   99.9%, so the dashboard tells you the cache is fine while
⭐   the cache is what is killing you.
```

```
⭐⭐ THREE FIXES:
⭐   ① ⭐ A PER-KEY LOCK (`SET NX`, Day 207): one rebuilder, the
⭐     rest wait or serve stale. ⭐⭐ Inherits every lock caveat
⭐     from Day 207 — TTL, ownership, the rebuilder that dies.
⭐   ② ⭐ PROBABILISTIC EARLY EXPIRY / XFetch (Day 205): each
⭐     reader independently decides to refresh slightly early,
⭐     with probability rising as expiry approaches ⇒ ⭐⭐ ONE
⭐     REQUEST REBUILDS BEFORE ANYONE MISSES.
⭐   ③ ⭐⭐ STALE-WHILE-REVALIDATE: store `{value, fresh_until}`
⭐     with a much longer Redis TTL. Past `fresh_until`, SERVE
⭐     THE STALE VALUE IMMEDIATELY and refresh in the background.
⭐     ⇒ ⭐⭐ NOBODY EVER WAITS FOR A REBUILD. The best default
⭐       when slightly-stale is acceptable, which is most of the
⭐       time on read-heavy pages.
⭐   ⭐ Plus: JITTER THE TTL (`60 s ± 10%`) so keys written in the
⭐     same second do not expire in the same second.
```

```
⭐⭐ AND THE ONE JITTER CANNOT HELP: THE COLD START.
⭐   ⭐ Redis restarts, or someone runs FLUSHALL, or you fail over
⭐     ⇒ ⭐⭐ EVERY KEY MISSES AT ONCE.
⭐   ⇒ ⭐⭐ WHICH MEANS THE REAL QUESTION IS PART 7'S LAST ONE:
⭐     ***CAN YOUR SERVICE SURVIVE AN EMPTY CACHE?*** If it
⭐     cannot, the cache is not an optimisation — ⭐⭐ IT IS A
⭐     LOAD-BEARING WALL, and you have a single point of failure
⭐     that nobody has written down.
```

# Part 6 — ⭐⭐ HTTP caching, and the one-line breach

```
⭐⭐ THE WORST CACHE BUG IN THIS ENTIRE DAY, IN ONE LINE:
⭐   a shared cache (CDN, or nginx `proxy_cache`) in front of an
⭐   authenticated endpoint, ⭐⭐ WITHOUT `Vary: Authorization`
⭐   AND WITHOUT `Cache-Control: private`.
⭐   ⇒ ⭐⭐ USER A'S RESPONSE IS SERVED TO USER B. At the edge.
⭐     Before a single line of your code runs.
⭐   ⇒ ⭐ And it is invisible in every test you own, because
⭐     your tests do not go through the CDN.

⭐⭐ THE RULE: AUTHENTICATED RESPONSES ARE `private`. ALWAYS.
⭐   Cache-Control: private, no-store   (or `max-age=0, must-revalidate`)
⭐   ⇒ ⭐ If you genuinely want them shared, the cache must key on
⭐     identity — ⭐⭐ WHICH MEANS THE HIT RATE IS ~0 AND YOU DID
⭐     NOT WANT IT SHARED AFTER ALL.
```

```
⭐⭐ ETags — WHAT THEY ACTUALLY SAVE:
⭐   ⭐ `If-None-Match` ⇒ 304 ⇒ ⭐ YOU SAVE THE BANDWIDTH AND THE
⭐     CLIENT'S PARSE. ⭐⭐ YOU DO NOT SAVE THE WORK — unless the
⭐     ETag can be computed WITHOUT doing the work.
⭐   ⇒ ⭐⭐ SO A STRONG ETag DERIVED FROM `max(updated_at)` OR A
⭐     VERSION COUNTER IS WORTH REAL MONEY; ⭐ AN ETag COMPUTED
⭐     BY HASHING THE RENDERED RESPONSE SAVES BYTES ONLY.
⭐   ⭐ On a mobile client polling a list every 10 s, bytes-only
⭐     is still a win worth taking.
```

# Part 7 — ⭐⭐ Measuring it honestly

```
⭐⭐ THE HIT RATIO IS A VANITY METRIC (Day 205 — and it is worth
⭐   repeating because it is on every dashboard ever built):
⭐   ⭐ 99% hits on a 2 ms query ⇒ you saved ⭐ 2 ms
⭐   ⭐ 60% hits on a 900 ms query ⇒ you saved ⭐⭐ 540 ms/request
⭐ ⇒ ⭐⭐ THE NUMBER IS ***TIME SAVED × REQUEST RATE***, and the
⭐   only way to get it is to measure BOTH PATHS.
```

```
⭐⭐ THE EXPERIMENT, AND IT TAKES TWENTY MINUTES:
⭐   ① Feature-flag the cache OFF. Load-test. Record p50/p95/p99
⭐     and the database's queries-per-second.
⭐   ② Flag it ON. Same load, same duration, same data.
⭐   ③ ⭐ Record THREE deltas, not one:
⭐       ⭐ latency at p95 and p99 (⭐⭐ NOT the mean — the mean
⭐         is dominated by hits and tells you nothing about the
⭐         experience of a miss)
⭐       ⭐ origin load: DB queries/sec before ÷ after
⭐       ⭐⭐ THE COLD NUMBER: throughput at 0% hit rate, which is
⭐         your capacity on the Tuesday after a Redis failover
⭐   ④ ⭐⭐ WRITE THE THREE NUMBERS INTO THE ADR (Day 252). A cache
⭐     with no recorded before-and-after is a cache nobody can
⭐     ever justify removing.
```

```
⭐ WHAT TO GRAPH AFTERWARDS:
⭐   ⭐ hit ratio BY KEY PREFIX (aggregate hides the one prefix
⭐     that is at 4% and doing nothing but consuming memory)
⭐   ⭐ endpoint p99 with a hit/miss dimension
⭐   ⭐ Redis: memory, evicted_keys, latency, connections
⭐   ⭐⭐ EVICTIONS > 0 ON A CACHE INSTANCE IS NORMAL. ⭐⭐
⭐     EVICTIONS > 0 ON THE BROKER INSTANCE IS DATA LOSS (Day 265).
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Caching before profiling | You paid four costs for an unknown gain. Measure p99 first. |
| Caching in front of an N+1 | You cached 200 queries and guaranteed the cold start is an outage. |
| Caching a query result when the response is cacheable | Cache as far up as correctness allows. |
| `lru_cache` for anything runtime-mutable | N processes, N stale copies, no way to invalidate during the incident. |
| A key missing `tenant_id` | Cross-tenant data disclosure, with correct authorisation code that never ran. |
| A key missing the caller's role | The admin view served to a customer. |
| No `perm_version` in the key | Revoking a role does nothing until the TTL expires. |
| No version prefix | A shape change deserialises old entries into new code. |
| `SET` on invalidation | Two racing writers, and the loser's value survives with a full TTL. Use `DEL`. |
| An entry with no TTL | One missed invalidation is permanently wrong instead of briefly wrong. |
| Building an invalidation graph for aggregates | Exact the day you write it, wrong two sprints later. Short TTL. |
| TTL as the fix for read-your-own-writes | "It didn't save" is the conclusion, and trust in the product goes with it. |
| Uniform TTLs | Keys written together expire together. Jitter them. |
| No stampede protection | The database dies at 99.9% hit rate, and the dashboard says everything is fine. |
| Assuming jitter covers a cold start | A flush or failover misses every key at once. That's what the lock is for. |
| An authenticated response without `private` | A shared cache serves one user's response to another. |
| Believing an ETag saves work | It saves bytes, unless it can be computed without doing the work. |
| Reporting the hit ratio as the result | 99% of a 2 ms query is 2 ms. Report time saved × rate. |
| Comparing means | The mean is dominated by hits and hides the miss experience. |
| Never measuring the 0%-hit path | That's your real capacity, and you'll discover it during an incident. |

## Interview questions

**Q: When do you add a cache?**

> After I've measured, and after the three free fixes: the missing index, the N+1, and the payload.
> Caching in front of an N+1 is the one I actively watch for, because it works — so nobody fixes the
> N+1 — and then the first cold cache after a restart takes the site down, when the fix has to happen
> under incident pressure. And I'd state the costs, because they're paid on day one regardless of the
> benefit: a second source of truth that makes every future bug harder to diagnose, a second failure
> mode, a correctness surface whose worst case is cross-user, and memory to operate.

**Q: What goes in a cache key?**

> Every input that changes the value — and I treat that as a security rule, not a performance one.
> The one people miss is tenant and role: a key like `jobs:list:page:2` serves one tenant's data to
> another, and the authorisation code is perfectly correct because it was never called, since the
> cache answered above it. So either cache below authorisation, or put identity in the key, never
> neither. Plus a per-user `perm_version` bumped on role changes, otherwise revoking admin does
> nothing for five minutes, and a version prefix, because a change to the value's *shape* can't be
> invalidated — old entries deserialise into new code.

**Q: Why delete rather than update on a write?**

> Two writers who both `SET` race, and the loser's value can survive for a full TTL — it's newer in
> Redis and older in reality. Two writers who both `DEL` can't lose, because the next reader
> recomputes from the database. And every entry still gets a TTL even when I invalidate explicitly:
> the TTL isn't the strategy, it's the bound on how long the invalidation I forgot to write stays
> wrong.

**Q: What's a cache stampede and how do you handle it?**

> One hot key expires, and every in-flight request misses simultaneously and rebuilds — three
> thousand requests a second against a nine-hundred-millisecond query is roughly twenty-seven hundred
> concurrent copies of your most expensive work. The database falls over at the exact moment the
> cache was working perfectly, and the hit-ratio graph reads 99.9%. Fixes: jitter TTLs so keys don't
> expire together, then either a per-key rebuild lock, probabilistic early expiry, or
> stale-while-revalidate, which I'd default to because nobody ever waits for a rebuild. None of that
> helps a cold start after a failover, though, which is why I always measure throughput at a zero
> percent hit rate.

**Q: How do you know the cache is worth it?**

> By having the number. I flag it off, load-test, record p95, p99 and database QPS; flag it on and do
> it again; then report time saved times request rate rather than the hit ratio, because ninety-nine
> percent of a two-millisecond query is two milliseconds. The third number is the important one:
> throughput at zero percent hits. If the service can't survive an empty cache, the cache isn't an
> optimisation — it's a load-bearing wall and an undocumented single point of failure. And all three
> numbers go in the ADR, because a cache with no recorded before-and-after is one nobody can ever
> justify removing.

## Today's build

1. ⭐⭐ Profile your three slowest endpoints (Day 202). Fix any index, N+1 or payload problem *before* caching anything.
2. ⭐ Pick exactly one endpoint to cache and write down the predicted saving before you measure.
3. ⭐⭐ Load-test with the cache flagged off. Record p50/p95/p99 and database QPS.
4. ⭐ Implement cache-aside with an explicit key builder function — not string formatting at the call site.
5. ⭐⭐ Write the cross-tenant test: seed two tenants, request as A, then as B, assert B never sees A's rows.
6. ⭐⭐ Deliberately drop `tenant_id` from the key and confirm the test fails. Keep that test forever.
7. ⭐ Add `perm_version` to the key. Revoke a role and assert the next response reflects it immediately.
8. ⭐ Add a `v1:` prefix. Change a serialiser field, bump to `v2:`, and confirm old entries are ignored.
9. ⭐⭐ Invalidate with `SET` and reproduce the lost-update race with two concurrent writers. Switch to `DEL`.
10. ⭐ Remove the TTL from one key, break its invalidation, and observe how long it stays wrong.
11. ⭐⭐ Load-test one hot key with a uniform TTL and watch the stampede in the database's QPS graph.
12. ⭐⭐ Implement stale-while-revalidate with jittered TTLs and re-run the same test.
13. ⭐ `FLUSHALL` under load. Record whether the service stays up, and at what latency.
14. ⭐⭐ Measure throughput at 0% hit rate and write it in the ADR as your real capacity.
15. ⭐ Add `Cache-Control: private` to every authenticated response and write a test asserting it.
16. ⭐ Graph hit ratio by key prefix. Delete any prefix below 20% — it is pure memory cost.

## 🎙️ Articulation drill

**Three minutes: "Talk me through caching in your system."**

Start with the price, because it establishes that this was a decision: **a cache is a second source of
truth you've promised to keep in sync** — every future bug gains the question "was it cached?", you
own a new failure mode, and the worst-case correctness bug is cross-user. So before caching anything,
the index, the N+1 and the payload, and call out that **a cache in front of an N+1 works, which is
why it's dangerous** — nobody fixes the N+1 and the first cold start is an outage. Then the key, and
give it as a security rule: it must contain every input that changes the value, and the one people
miss is tenant and role, where **the authorisation code is perfectly correct and simply never ran
because the cache answered above it.** Mention `perm_version` for revocations and a version prefix
for shape changes. Then invalidation in one line — delete, never update, because two racing `SET`s
leave the loser's value alive for a full TTL — and **the TTL as a bound on the lifetime of the
invalidation you forgot**, with one exception you never solve that way: read-your-own-writes, because
the user's conclusion is "it didn't save". Then the stampede: one hot key expires and three thousand
requests rebuild at once, **so the database dies at the exact moment the cache is at 99.9%** — jitter
plus stale-while-revalidate. Close on measurement: report **time saved times rate, not the hit
ratio**, and the number that decides your architecture is throughput at zero percent hits, because
**if the service can't survive an empty cache the cache is a load-bearing wall, not an optimisation.**
