# Day 051

**L-051** · `functools` — `lru_cache`, `cached_property`, `reduce`, `singledispatch`

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `@lru_cache` is a dict keyed by the argument tuple that lives for the
> lifetime of the process — so every one of its failure modes is a fact about a dict you forgot you
> created.**
>
> ⭐ Today has one marquee item: **`@lru_cache` on a method is a memory leak**, and it is common,

# Part 1 — ⭐⭐ `lru_cache`

```python
from functools import lru_cache, cache

@lru_cache(maxsize=128)                 # ⭐ bounded, LRU eviction (Day 038's OrderedDict)
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)

fib(100)                                # ⭐⭐ instant — without the cache this is exponential
fib.cache_info()                        # ⭐ CacheInfo(hits=98, misses=101, maxsize=128, currsize=101)
fib.cache_clear()
fib.__wrapped__(10)                     # ⭐ call the undecorated original (Day 044)

@cache                                  # ⭐ 3.9+ — shorthand for lru_cache(maxsize=None)
def lookup(k): ...                      # ⚠️ ⭐⭐ UNBOUNDED
```

```
⭐⭐ HOW IT WORKS — and every trap follows from this one sentence:
⭐   a DICT, keyed by (args, kwargs-as-a-tuple), stored ON THE FUNCTION OBJECT,
⭐   living for the lifetime of the process, with an LRU eviction list if maxsize is set.
```

| ⚠️ Trap | ⭐ Consequence |
|---|---|
| ⭐ Arguments must be **hashable** | a `list` or `dict` argument ⇒ `TypeError` (Day 029) |
| ⭐⭐ `maxsize=None` on user input | ⭐⭐ an unbounded, attacker-controlled dict (Day 028) |
| ⭐ `f(1)` vs `f(x=1)` | ⭐⭐ **different cache entries** — same call, two misses |
| ⭐ Mutable return values | ⭐⭐ **every caller shares one object**; one mutation corrupts all |
| Not thread-safe end to end | two threads may both compute on a miss (⭐ the result is correct) |
| Time-dependent functions | a cached "now" is frozen forever |

⚠️ ⭐⭐ **The mutable-return trap is worth its own line**, because it looks like a caching problem and
is really Day 024:

```python
@cache
def get_config(env): return {"debug": False}     # ⭐⭐ ONE dict, handed to everyone
cfg = get_config("prod"); cfg["debug"] = True    # ⭐⭐ now EVERY caller sees debug=True. Forever.
```

⭐ **Cache functions that return immutable values**, or return a copy — **or better, cache the
expensive computation and let the caller build its own object.**

# Part 2 — ⭐⭐ `lru_cache` on a method is a leak

```python
class Report:
    @lru_cache(maxsize=None)             # ⚠️⚠️ ⭐⭐ THE LEAK
    def compute(self, key):
        return heavy(self.data, key)
```

```
⭐⭐ WHY: the cache lives on the FUNCTION, which lives on the CLASS — one cache for ALL instances.
⭐   The key includes `self`. ⇒ ⭐⭐ the cache holds a STRONG REFERENCE to every instance
⭐     it has ever been called on.
⭐   ⇒ ⭐⭐ NO Report OBJECT IS EVER GARBAGE COLLECTED. Not one. For the life of the process.
⭐   ⇒ ⭐ in a web service where each request builds one, that is an unbounded leak that
⭐     `tracemalloc` blames on the wrong line (Day 026).
```

```python
# ⭐⭐ THE FIXES — in order of preference:
class Report:
    @cached_property                     # ⭐⭐ per INSTANCE, no arguments, dies with the object
    def summary(self): return heavy(self.data)

    def compute(self, key):              # ⭐ per instance, with arguments
        return self._compute_cached(key)
    @cached_property
    def _compute_cached(self):
        return lru_cache(maxsize=32)(lambda key: heavy(self.data, key))

# ⭐ or: make it a module-level function taking only hashable values
@lru_cache(maxsize=1024)
def compute(data_id: str, key: str): ...
```

⭐⭐ **`functools.cached_property`** (Day 032) is the right tool for the no-argument case: it is a
**non-data descriptor** that computes once and writes the result into the instance `__dict__`, so
every later access finds the instance dict first. **Per instance, zero overhead afterwards, freed
with the object, and invalidated with `del obj.attr`.** ⚠️ It needs a `__dict__`, so it does not work
with `__slots__` (Day 028).

# Part 3 — ⭐ `singledispatch`

```python
from functools import singledispatch, singledispatchmethod

@singledispatch
def serialise(obj):                      # ⭐ the fallback
    raise TypeError(f"cannot serialise {type(obj)}")

@serialise.register
def _(obj: datetime) -> str:             # ⭐⭐ dispatches on the ANNOTATION (Day 042)
    return obj.isoformat()

@serialise.register
def _(obj: Decimal) -> str:              # ⭐ Day 041 — this is the JSON fix
    return str(obj)

@serialise.register(list)                # ⭐ or register the type explicitly
def _(obj): return [serialise(x) for x in obj]
```

```
⭐⭐ WHAT IT REPLACES: an isinstance ladder that every new type must be added to.
⭐   ⇒ ⭐ dispatch is by the FIRST argument's type, following the MRO (Day 054),
⭐        so registering a base class covers its subclasses.
⭐   ⇒ ⭐⭐ AND it is OPEN: a different module can register a handler for its own type
⭐        without touching your function. That is the real argument for it.
```

⭐ **`singledispatchmethod`** does the same for methods, dispatching on the *second* argument (after
`self`). ⚠️ **There is no multiple dispatch** — only the first argument is considered — and dispatch
happens per call, so it is slightly slower than a direct call.

⭐⭐ **Where you have already met this pattern:** `json.dumps(..., default=serialise)` is exactly
this, and a `@singledispatch` serialiser is the clean answer to Day 041's `Decimal`-over-JSON
problem.

# Part 4 — ⭐ `reduce`, and the rest

```python
from functools import reduce
import operator as op

reduce(op.add, nums)                     # ⭐ sum(nums) — use sum
reduce(op.or_, list_of_sets)             # ⭐⭐ union of many sets — genuinely good
reduce(op.or_, list_of_dicts)            # ⭐ merge many dicts (3.9+)
reduce(lambda a, b: a | b, sets, set())  # ⭐ with an initial value — safe on an empty input
```

```
⭐⭐ WHY reduce IS IN functools AND NOT BUILTINS: Guido's view was that a loop is almost always
⭐   clearer, and he was right. ⇒ ⭐ use it only when the operation is a NAMED BINARY function
⭐   and the intent is genuinely "fold this sequence into one value".
⭐   ⇒ ⭐⭐ reduce(lambda a,b: ..., xs) with a multi-line lambda is always worse than a loop.
```

⚠️ ⭐ **`reduce` on an empty sequence with no initial value raises `TypeError`** — pass the identity
value (`0`, `set()`, `{}`) and the edge case disappears.

```python
# ⭐ Choosing a cache — the table that matters in a service:
```

| ⭐ Need | ⭐⭐ Tool |
|---|---|
| Pure function, hashable args, bounded | ⭐⭐ `@lru_cache(maxsize=N)` |
| Per-instance, no arguments | ⭐⭐ `@cached_property` |
| ⭐ Needs to **expire** | ⚠️ ⭐⭐ **neither** — `lru_cache` has no TTL. Use `cachetools.TTLCache` |
| ⭐ Shared across processes/machines | ⭐⭐ **Redis** — a local cache is per worker (Day 021) |
| Cached and invalidated on write | your own layer — Stage 5 |

⚠️ ⭐⭐ **`lru_cache` has no TTL and no invalidation.** In a service with four workers you have four
caches with no coordination, and a value cached at startup is served until restart. **That is fine
for pure computation and wrong for anything derived from the database** — which is the mistake to
name in an interview.

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`lru_cache` on a method** | ⭐⭐ Keys on `self` ⇒ no instance is ever freed. |
| ⭐⭐ **`maxsize=None` on user input** | ⭐⭐ Unbounded, attacker-controlled dict. |
| Caching a mutable return value | ⭐⭐ All callers share one object. |
| Caching DB-derived values | ⭐ No TTL, no invalidation, per worker. |
| Expecting `f(1)` and `f(x=1)` to share | ⭐ Different keys. |
| Unhashable arguments | ⭐ `TypeError` — convert to a tuple. |
| ⭐ `cached_property` with `__slots__` | ⭐ Needs `__dict__`. |
| Never invalidating a `cached_property` | ⭐ `del obj.attr`. |
| `reduce` with a multi-line lambda | ⭐ A loop is clearer. |
| `reduce` on a possibly-empty sequence | ⭐ Pass an initial value. |
| An `isinstance` ladder in a library | ⭐⭐ `singledispatch` — others can extend it. |

## Interview questions

**Q: How does `lru_cache` work?**
> It's a dictionary keyed by the arguments, stored on the function object, with an LRU eviction order
> when `maxsize` is set. Every one of its gotchas comes from that: arguments must be hashable;
> `f(1)` and `f(x=1)` are different keys because the key includes how you called it; the cache lives
> for the process lifetime, so there's no expiry; and it's per process, so four workers means four
> independent caches with no coordination.

**Q: What's wrong with `@lru_cache` on a method?**
> The cache lives on the function, which lives on the class, so it's shared across all instances —
> and `self` is part of the key. That means the cache holds a strong reference to every instance it
> has ever been called with, so no object of that class is ever collected. In a web service that
> builds one per request, that's an unbounded leak, and it's hard to find because `tracemalloc`
> attributes the memory to wherever the objects were created rather than to the decorator holding
> them. For a no-argument case I'd use `cached_property`, which is per instance and dies with the
> object; otherwise a module-level cached function taking only hashable values.

**Q: What's `cached_property` doing that a `property` plus a cache isn't?**
> It's a non-data descriptor, so it only participates in attribute lookup until the first access —
> it computes the value and writes it into the instance `__dict__`, and from then on the instance
> dict wins because it's checked before non-data descriptors. So there's zero overhead afterwards, no
> separate cache dict to manage, the value is freed with the object, and invalidation is just
> `del obj.attr`. The catch is that it needs an instance `__dict__`, so it doesn't work with
> `__slots__`.

**Q: When would you use `singledispatch`?**
> When I'd otherwise write an `isinstance` ladder that grows every time a type is added — a
> serialiser is the canonical case. The real advantage over the ladder isn't tidiness, it's openness:
> another module can register a handler for its own type without modifying my function, and dispatch
> follows the MRO so registering a base class covers its subclasses. The limits are that it dispatches
> on the first argument only — no multiple dispatch — and there's a small per-call cost.

**Q: Is `lru_cache` an appropriate cache for a web service?**
> For pure computation, yes — parsing, formatting, expensive maths on hashable inputs. For anything
> derived from the database, no: it has no TTL and no invalidation, so a value cached at startup is
> served until the process restarts, and with several workers each has its own copy, so they'll
> disagree. That's Redis's job. The version of this mistake I'd watch for is caching a permissions or
> feature-flag lookup — it works in testing and then a change doesn't take effect until deploy.

## 🎙️ Articulation drill

Record two minutes: **"Your service's memory grows steadily and restarts fix it. Where do you
look?"**

⭐ Start with the general shape from Day 026: **this is almost never a garbage-collection failure —
it is something reachable that only grows.** So the question is what is holding references.

⭐⭐ **Then name this day's specific candidate, because it is the one people miss:** *"`@lru_cache` on
a method. The cache lives on the class, and `self` is part of the key, so it holds a strong reference
to every instance it has ever been called with — and in a service that creates one per request, no
instance is ever collected. It looks like an object leak with no owner, and `tracemalloc` points at
where the objects were constructed rather than at the decorator retaining them."*

⭐ Then the other usual suspects in order: an unbounded `@cache` keyed by user input, a module-level
dict or list that only grows, and stored exception objects pinning frames.

⭐⭐ **Close on the fix and the principle:** *"`cached_property` for the per-instance case, because it
dies with the object; a module-level cached function taking only hashable values otherwise; and a
`maxsize` on anything keyed by input I do not control. The general rule is that any cache without a
bound and a lifetime is a leak with a nicer name."*
