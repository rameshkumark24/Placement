**L-009** · ⭐⭐ **TLS / HTTPS** — what encryption actually protects, certificates, the handshake

# Part 1 — ⭐⭐ What TLS actually gives you

| ⭐ Property | ⭐ Meaning | ⭐⭐ Without it |
|---|---|---|
| ⭐ **Confidentiality** | nobody on the path can read the bytes | the café wifi reads your password |
| ⭐ **Integrity** | nobody on the path can change the bytes | the ISP injects ads into your page |
| ⭐⭐ **Authentication** | ⭐⭐ **you are talking to who you think you are** | ⭐⭐ you encrypt beautifully — to an attacker |

⭐⭐ **The third one is the one people forget, and it is the one that matters most.** Encryption
without authentication is worthless: a man in the middle simply terminates your TLS, reads
everything, and opens his own TLS to the real server. **That is exactly what `verify=False` turns
on** (Part 4).

```
⭐⭐ WHAT TLS DOES NOT DO — say all of these out loud:
⭐   ✗ It does not protect data AT REST      — your database is still plaintext (Stage 5, Stage 11 KMS)
⭐   ✗ It does not protect data IN THE SERVER — after decryption it is a normal Python str/bytes
⭐   ✗ It does not hide WHO you talked to    — the domain leaks via DNS and SNI
⭐   ✗ It does not hide HOW MUCH you sent    — packet sizes and timing leak
⭐   ✗ It does not make your app secure      — an SQL injection over HTTPS is still an SQL injection
```

⚠️ ⭐⭐ **"We use HTTPS so we're secure" is a red flag in an interview.** HTTPS secures one hop.
Every logging call, every `print()`, every exception traceback that includes a request body is a
plaintext copy of what TLS just spent a handshake protecting.

# Part 2 — ⭐ Symmetric and asymmetric, and why you need both

| | ⭐ Symmetric (AES) | ⭐ Asymmetric (RSA / ECDHE) |
|---|---|---|
| Keys | ⭐ one shared secret | a public/private **pair** |
| Speed | ⭐⭐ **fast** — hardware accelerated | ⭐⭐ **slow** — 100–1000× |
| Problem | ⭐⭐ **how do both sides get the key?** | solves exactly that |

```
⭐⭐ THE WHOLE DESIGN IN ONE LINE:
⭐   use the SLOW asymmetric crypto ONCE, to agree on a fast symmetric key,
⭐   then use the FAST symmetric key for all the actual data.
⭐ ⇒ ⭐⭐ that agreement step is the HANDSHAKE.
```

## ⭐⭐ Forward secrecy — the part worth understanding

```
⭐ OLD (RSA key exchange, now removed):
⭐   client picks the session key, encrypts it with the server's PUBLIC key, sends it.
⭐   ⇒ ⭐⭐ an attacker who RECORDS traffic today and STEALS the private key in 2030
⭐        can decrypt everything they recorded. Retroactively.

⭐⭐ MODERN (ECDHE — the E is "ephemeral"):
⭐   both sides derive a shared secret from throwaway key pairs; the shared secret
⭐   is NEVER SENT, and both sides DELETE the ephemeral keys afterwards.
⭐   ⇒ ⭐⭐ stealing the server's private key later reveals NOTHING about past sessions.
⭐   ⇒ ⭐ the private key is now used only to SIGN (prove identity), not to encrypt.
```

⭐⭐ **"What is forward secrecy and why does ECDHE provide it?"** is a clean senior-signal question,
and the answer is above: the session secret is derived, never transmitted, and the ephemeral keys are
discarded.

# Part 3 — ⭐⭐ The handshake, and its cost

```
⭐⭐ TLS 1.3 — ONE round trip (1-RTT):

  CLIENT                                                SERVER
    │ ── ClientHello ─────────────────────────────────────▶ │
    │    · TLS versions I support                           │
    │    · cipher suites I support                          │
    │    · ⭐ SNI: "api.example.com"  ⚠️ SENT IN PLAINTEXT   │
    │    · ⭐ my ephemeral public key (a guess at the group) │
    │                                                       │
    │ ◀───────────────────────────── ServerHello ────────── │
    │    · chosen cipher, server's ephemeral public key     │
    │    · ⭐⭐ CERTIFICATE  (+ chain)                        │
    │    · ⭐ signature proving it holds the private key     │
    │                                                       │
    │ ⭐⭐ both sides now COMPUTE the same shared secret       │
    │ ── Finished ────────────────────────────────────────▶ │
    │ ◀───────────────────────────────────── Finished ───── │
    │ ═══════════ ⭐ encrypted application data ═══════════ │
```

| ⭐ Version | Round trips before data | ⭐ Note |
|---|---|---|
| TLS 1.2 | ⭐ **2** | plus 1 for TCP ⇒ **3 RTT before a single byte of HTTP** |
| ⭐⭐ **TLS 1.3** | ⭐⭐ **1** | plus 1 for TCP ⇒ 2 RTT. Also **removed** RSA key exchange and all the broken ciphers |
| ⭐ TLS 1.3 **0-RTT** | 0 (resumption) | ⚠️ ⭐⭐ **replayable** — never use it for non-idempotent requests |

⭐⭐ **The cost is the point.** At 100 ms RTT, TLS 1.2 costs ~300 ms before your Python code sees the
request line. **That is the fourth independent argument for connection reuse** — after the handshake
(Day 005), the warm congestion window (Day 008), and the DNS lookup (Day 007).

```python
# ⭐⭐ Reusing a client reuses the TCP connection AND the TLS session.
# ⭐ Wrong — a fresh TCP + TLS handshake per call:
import httpx
for url in urls:
    httpx.get(url)                     # ⚠️ new connection every time

# ⭐⭐ Right — one pool, connections kept alive:
with httpx.Client() as client:         # ⭐ or requests.Session()
    for url in urls:
        client.get(url)
```

⚠️ ⭐⭐ **Module-level `requests.get(...)` / `httpx.get(...)` in a loop is the single most common
performance bug in Python service code.** It is invisible in development and adds hundreds of
milliseconds per call in production. Stage 3 makes the client a dependency you inject once.

# Part 4 — ⭐⭐ Certificates and the chain of trust

```
⭐⭐ A certificate is a SIGNED CLAIM: "the holder of this public key owns api.example.com",
⭐   signed by someone. The signature is what makes it worth anything.

⭐ THE CHAIN:
⭐   ROOT CA          (self-signed; ⭐⭐ shipped INSIDE your OS and inside Python's certifi)
⭐     └─ signs ─▶ INTERMEDIATE CA
⭐                   └─ signs ─▶ ⭐ api.example.com   ← the leaf your server presents

⭐⭐ Verification walks UP the chain until it reaches something already trusted.
⭐   ⇒ ⭐⭐ TRUST IS NOT IN THE CERTIFICATE. It is in the ROOT STORE ON YOUR MACHINE.
```

## ⭐ What the client checks — all of it, every time

| # | ⭐ Check | ⭐ Failure you will actually see |
|---|---|---|
| 1 | signature chain reaches a trusted root | `unable to get local issuer certificate` |
| 2 | ⭐ not expired | `certificate has expired` — ⭐⭐ the classic 3am outage |
| 3 | ⭐⭐ **hostname matches CN/SAN** | `Hostname mismatch` |
| 4 | not revoked (CRL / OCSP) | rarely enforced strictly |

⭐⭐ **Check 3 is the one that makes TLS meaningful.** An attacker can obtain a perfectly valid
certificate — *for their own domain*. Hostname verification is what stops them presenting it for
yours.

## ⭐⭐ Python's own certificate traps

```python
import ssl, certifi, httpx

# ⭐ Python does NOT use the OS trust store on macOS/Windows the way you expect —
# ⭐ it uses `certifi`, a bundle shipped as a pip package.
print(certifi.where())      # ⭐⭐ the file that decides what your program trusts

ctx = ssl.create_default_context()          # ⭐ verification ON, hostname check ON
ctx = ssl.create_default_context(cafile="corp-root.pem")   # ⭐ add a corporate root, properly
```

```python
# ⚠️⚠️ ⭐⭐ THE SIN. Every one of these DISABLES AUTHENTICATION ENTIRELY:
httpx.get(url, verify=False)
requests.get(url, verify=False)
ssl._create_unverified_context()
ctx.check_hostname = False; ctx.verify_mode = ssl.CERT_NONE
```

⚠️ ⭐⭐ **`verify=False` does not "skip a warning". It converts TLS from *secure* to *encrypted to
whoever answered*.** You still get a green padlock's worth of encryption — to the attacker. It is
the most common insecure line in Python codebases, it usually enters as a temporary fix for a
corporate proxy, and it never gets removed.

⭐⭐ **The correct fix for a corporate MITM proxy** is to add the proxy's root to the trust bundle:
`export SSL_CERT_FILE=/path/corp-root.pem` or `REQUESTS_CA_BUNDLE=...`. **Trust the extra root
explicitly; never disable the check.**

# Part 5 — ⭐ Where TLS terminates

```
⭐ COMMON PRODUCTION SHAPE:

  browser ══ TLS ══▶ [ CDN ] ══ TLS ══▶ [ Load balancer ] ──plain HTTP──▶ [ your uvicorn worker ]
                                          ⭐⭐ TERMINATION POINT              ⭐ sees http://, not https://

⭐⭐ CONSEQUENCES YOU WILL HIT:
⭐  · your app builds redirect URLs as http:// ⇒ ⭐⭐ redirect loops
⭐  · request.client.host is the LOAD BALANCER's IP, not the user's
⭐  · ⭐⭐ FIX: trust X-Forwarded-Proto / X-Forwarded-For — uvicorn --proxy-headers,
⭐        and ⚠️ ONLY when the proxy is trusted, because a client can forge those headers.
```

⭐ **Let's Encrypt made certificates free and automated** (90-day certs, ACME, `certbot`). ⭐⭐ **If
a certificate expiry ever takes your service down, the failure was not the certificate — it was that
renewal was manual.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **"HTTPS means we're secure"** | ⭐⭐ It secures one hop. Your logs, DB and code are still plaintext. |
| ⭐⭐ **`verify=False`** | ⭐⭐ Disables authentication — MITM becomes trivial. Add the root instead. |
| Thinking TLS encrypts with the certificate | ⭐ The cert authenticates; a derived symmetric key encrypts. |
| Believing the private key is used to encrypt data | ⭐ In TLS 1.3 it only **signs**. ECDHE derives the secret. |
| Assuming the domain is hidden | ⭐ SNI and DNS leak it. Only the *content* is hidden. |
| Not knowing where TLS terminates | ⭐⭐ Causes redirect loops and wrong client IPs. |
| Treating cert expiry as bad luck | ⭐⭐ It is missing automation. |
| Using 0-RTT for everything | ⚠️ It is replayable — idempotent GETs only. |
| Assuming Python uses the OS trust store | ⭐ It commonly uses `certifi`. Know where your roots come from. |

## Interview questions

**Q: What does HTTPS actually protect?**
> The connection between two endpoints — confidentiality, integrity, and crucially authentication of
> the server. It protects nothing at rest and nothing inside either process. Once my handler runs,
> the body is an ordinary `bytes` object; if I log it, I have just written the plaintext to disk. And
> it doesn't hide who I talked to, because the hostname is in DNS and in the SNI field in the clear.

**Q: Walk me through the handshake.**
> ClientHello with supported versions, cipher suites, the SNI hostname and an ephemeral public key.
> ServerHello with the chosen cipher, the server's ephemeral key, and the certificate chain plus a
> signature proving it holds the matching private key. Both sides derive the same shared secret from
> the ephemeral pairs — it is never transmitted — then Finished messages, and everything after that
> is symmetric. TLS 1.3 does that in one round trip on top of TCP's one.

**Q: Why both symmetric and asymmetric crypto?**
> Asymmetric solves key distribution but is orders of magnitude slower. Symmetric is fast but assumes
> a shared secret. So you use the expensive mechanism exactly once, to establish the cheap one.

**Q: What is forward secrecy?**
> Session keys are derived from ephemeral key pairs that are discarded afterwards, so an attacker who
> records traffic now and compromises the server's private key years later still cannot decrypt it.
> The old RSA key exchange lacked this, which is why TLS 1.3 removed it entirely.

**Q: A colleague adds `verify=False` because the request fails behind the corporate proxy. Response?**
> That turns off certificate verification, which is the authentication half of TLS — we would be
> encrypting to whoever answers, which is precisely the attack TLS exists to stop. The proxy is doing
> MITM with its own root, so the fix is to trust that root explicitly via `SSL_CERT_FILE` or a custom
> `SSLContext`. It's a one-line change either way; only one of them is safe.

**Q: Your app redirects to `http://` behind a load balancer. Why?**
> TLS terminated at the balancer, so the app sees a plain HTTP request and builds absolute URLs from
> that. The balancer records the original scheme in `X-Forwarded-Proto`; the app has to be told to
> trust it — `--proxy-headers` for uvicorn — and only because the balancer is trusted, since a client
> can send that header too.
