# Part 1 — ⭐ Redis is a data-structure server, and that is the point

```
⭐⭐ PEOPLE LEARN REDIS AS "GET/SET WITH A TTL" AND STOP. ⭐ The value is that
⭐   the operations are ATOMIC SERVER-SIDE, so a structure replaces a lock:

⭐   STRING   GET/SET/INCR       ⭐ counters, ⭐⭐ INCR is atomic ⇒ rate limits
⭐                                  without read-modify-write (Day 123)
⭐   HASH     HSET/HGETALL       ⭐ an object; update ONE field without
⭐                                  rewriting the whole JSON blob
⭐   LIST     LPUSH/BRPOP        ⭐⭐ a queue with a BLOCKING pop — no polling
⭐   SET      SADD/SISMEMBER     ⭐ dedupe, "have I seen this id?"
⭐   ZSET     ZADD/ZRANGEBYSCORE ⭐⭐ leaderboards, ⭐ and the sliding-window
⭐                                  rate limiter from Day 123 IS a ZSET
⭐   STREAM   XADD/XREADGROUP    ⭐⭐ a real log with CONSUMER GROUPS and acks —
⭐                                  i.e. Day 142's queue, without Celery
⭐   TTL      EXPIRE / SET ... EX ⭐⭐ per-key expiry is the feature the others
⭐                                  do not have
⭐
⭐   ⇒ ⭐⭐ THE MENTAL MODEL: it is single-threaded for commands, so ⭐ EVERY
⭐        COMMAND IS ATOMIC BY CONSTRUCTION. ⭐⭐ That is why `INCR` needs no
⭐        lock — and why ⭐ ONE SLOW COMMAND BLOCKS EVERY CLIENT
⭐        (`KEYS *` on a million keys is the classic outage; use `SCAN`).
```

```python
r = redis.asyncio.Redis.from_url(settings.redis_url, decode_responses=True)

async def get_user_cached(uid: int) -> dict:
    key = f"user:v2:{uid}"                              # ⭐⭐ `v2` — see Part 4
    if (raw := await r.get(key)) is not None:
        return json.loads(raw)                          # ⭐ HIT
    user = await repo.get(uid)                          # ⭐ MISS → source of truth
    await r.set(key, json.dumps(user), ex=300)          # ⭐⭐ ALWAYS AN `ex`
    return user
```

> ⭐⭐ **A `set` without `ex` is a memory leak with a business excuse.** ⭐ Make "every write has a
> TTL" a review rule; the exceptions (a config flag, a feature toggle) should be rare enough to
> notice.

# Part 2 — ⭐⭐ The four patterns, and the two that are wrong more often than they look

```
⭐⭐ CACHE-ASIDE (lazy loading) — the default, and what you wrote above.
⭐   ⭐ read: check cache → miss → read DB → populate → return
⭐   ⭐ write: ⭐⭐ WRITE DB, THEN **DELETE** THE KEY. Delete, not update.
⭐   ⇒ ⭐⭐ WHY DELETE RATHER THAN UPDATE — this is asked, and it is subtle:
⭐        two concurrent writers that both UPDATE the cache can interleave so
⭐        the cache ends up holding the OLDER value permanently. ⭐ Deleting
⭐        makes the next read re-derive from the truth. ⭐⭐ A cache that
⭐        stores a value it computed itself is a second source of truth.
⭐
⭐  WRITE-THROUGH — write cache and DB together. ⭐ Consistent-ish, ⭐⭐ but it
⭐    is the dual-write problem from Day 142 again: two systems, no shared
⭐    transaction. ⭐ It also caches things nobody will read.
⭐
⭐  WRITE-BEHIND — write cache, flush to DB later. ⭐⭐ FAST AND DANGEROUS:
⭐    Redis restarts, acknowledged writes are gone. ⭐ Only for data you can
⭐    afford to lose (view counts), and say that out loud when you choose it.
⭐
⭐  ⭐⭐ REFRESH-AHEAD / early recompute — refresh a hot key BEFORE it expires.
⭐    ⭐ The clean answer to the stampede (Part 3) for a small number of known
⭐    hot keys.
```

```
⭐⭐ AND THE ORDERING RULE THAT CATCHES EVERYONE:

⭐   ❌ delete cache → write DB
⭐        ⭐ another request reads between the two, gets the OLD row, and
⭐        ⭐⭐ REPOPULATES THE CACHE WITH STALE DATA — which now lives until TTL.
⭐   ✅ ⭐⭐ WRITE DB → DELETE CACHE.
⭐        ⭐ The window still exists (a reader that loaded the old value before
⭐        your write may set it after your delete), ⭐⭐ but it is now
⭐        microseconds instead of the duration of your database write.
⭐   ⇒ ⭐ If you need better than that: delete AFTER commit, and for the
⭐        paranoid case delete TWICE (immediately and after ~500 ms) —
⭐        ⭐⭐ "delayed double delete". ⭐ Know it exists; needing it is a
⭐        signal that the data should not be cached.
```

# Part 3 — ⭐⭐ The stampede, and the single-flight lock

```
⭐⭐ THE FAILURE MODE THAT TAKES DATABASES DOWN AT ROUND NUMBERS:

⭐   ⭐ one popular key. TTL 300 s. 5,000 req/s.
⭐   ⭐ at t=300 the key expires.
⭐   ⭐⭐ 5,000 REQUESTS MISS SIMULTANEOUSLY AND ALL RUN THE SAME EXPENSIVE
⭐        QUERY. The database, sized for ~0 of these, gets 5,000.
⭐        ⇒ ⭐ it slows → the query takes longer → more requests pile in →
⭐        ⭐⭐ THE CACHE NEVER GETS POPULATED BECAUSE NOTHING FINISHES.
⭐   ⇒ ⭐ ALSO CALLED: dogpile, thundering herd, cache stampede.

⭐⭐ AND ITS BIG BROTHER — SYNCHRONISED EXPIRY:
⭐   ⭐ you warm 10,000 keys at deploy with `ex=3600`. ⭐⭐ ONE HOUR LATER THEY
⭐        ALL EXPIRE IN THE SAME SECOND. ⭐ Your traffic graph shows a cliff
⭐        every hour, on the hour, and nobody can explain it.
⭐   ⇒ ⭐⭐ FIX: `ex = 3600 + random.randint(0, 600)`. ⭐ TTL JITTER — the same
⭐        fix as Day 142's retry jitter, for the same reason: ⭐⭐ correlated
⭐        timing is the bug, not the load.
```

```python
# ⭐⭐ SINGLE-FLIGHT: exactly one caller recomputes, the rest wait or serve stale
async def get_or_compute(key: str, ttl: int, compute):
    if (raw := await r.get(key)) is not None:
        return json.loads(raw)

    lock_key = f"lock:{key}"
    got = await r.set(lock_key, "1", nx=True, ex=10)      # ⭐⭐ NX = atomic claim (Day 122)
    if got:
        try:
            value = await compute()                       # ⭐ ONE caller pays the cost
            await r.set(key, json.dumps(value), ex=ttl + random.randint(0, ttl // 10))
            return value
        finally:
            await r.delete(lock_key)                      # ⭐ always release
    else:
        await asyncio.sleep(0.05)                          # ⭐ others wait briefly
        if (raw := await r.get(key)) is not None:
            return json.loads(raw)
        return await compute()                             # ⭐⭐ FALL BACK — never hang
```

```
⭐⭐ THREE THINGS TO NOTICE IN THAT CODE, EACH ASKED SEPARATELY:
⭐   1. ⭐⭐ `nx=True, ex=10` IS THE WHOLE LOCK. `nx` makes it an atomic
⭐        compare-and-set; `ex` guarantees release even if the holder dies —
⭐        ⭐ a lock without a TTL is a deadlock waiting for a crash.
⭐   2. ⭐⭐ THE LOSER FALLS BACK TO COMPUTING. A waiter that loops forever
⭐        turns a slow query into a hung request. ⭐ Degrade, don't block.
⭐   3. ⭐ TTL JITTER IS APPLIED AT WRITE TIME, so the herd never re-forms.
⭐
⭐ ⭐⭐ THE STRONGER PATTERN — STALE-WHILE-REVALIDATE: store `{value,
⭐   expires_at}` with a LONGER Redis TTL than the logical one. On a logical
⭐   miss, ⭐ SERVE THE STALE VALUE IMMEDIATELY and refresh in the background.
⭐   ⇒ ⭐⭐ p99 stops depending on your slowest query at all. Same idea as
⭐        Day 124's HTTP `stale-while-revalidate` — ⭐ one concept, two layers.
```

# Part 4 — ⭐⭐ Invalidation, keys, and what must never be cached

```
⭐⭐ THE KEY IS AN API. DESIGN IT ON PURPOSE:

⭐   ⭐ `user:v2:{id}`               ⭐⭐ A VERSION SEGMENT. When the shape of
⭐                                    the cached value changes, BUMP IT.
⭐     ⇒ ⭐⭐ WHY THIS MATTERS ENORMOUSLY: during a rolling deploy (Day 138),
⭐        old and new code share the cache. New code writes a value with a new
⭐        field; ⭐ old code reads it and crashes on the unexpected shape — or
⭐        worse, ⭐⭐ old code writes the OLD shape and new code reads it and
⭐        KeyErrors. ⭐ A version segment makes the two caches disjoint, and
⭐        the old keys expire on their own.
⭐   ⭐ ⭐⭐ INCLUDE EVERY INPUT THAT CHANGES THE VALUE — user, locale, tenant,
⭐        feature flags. ⭐ A key missing an input serves one user's data to
⭐        another. ⭐⭐ That is Day 124's `Vary` bug, in your own process.
⭐   ⭐ never cache under a key you cannot enumerate or rebuild.

⭐⭐ INVALIDATION, IN INCREASING ORDER OF HONESTY:
⭐   1. ⭐ TTL ONLY. ⭐⭐ The most underrated answer. "Wrong for at most 60
⭐        seconds" is a specification, and it needs no invalidation code at
⭐        all. ⭐ Reach for this first and say the number out loud.
⭐   2. ⭐ EXPLICIT DELETE ON WRITE. Correct, and ⭐⭐ the maintenance burden is
⭐        real: every new write path must remember every key it invalidates.
⭐   3. ⭐ VERSION/GENERATION KEYS — bump `user:{id}:gen` and include it in
⭐        every dependent key. ⭐⭐ Invalidates a whole FAMILY with one INCR,
⭐        with no key enumeration.
⭐   4. ⭐ EVENT-DRIVEN — invalidate from the outbox (Day 142). ⭐ Correct
⭐        across services; ⭐⭐ now your cache has an eventual-consistency
⭐        window you must document.
⭐   ⇒ ⭐⭐ AND `KEYS user:*` IS NOT AN OPTION. It is O(n) on a single-threaded
⭐        server: it blocks every client. Use `SCAN`, or design keys so you
⭐        never need to search.
```

```
⭐⭐ WHAT MUST NEVER GO IN A SHARED CACHE — say these unprompted:
⭐   · ⭐⭐ ANYTHING KEYED WITHOUT THE USER ID that varies per user.
⭐        ⭐ Day 124's leak, and now it is YOUR bug, not a CDN's.
⭐   · ⭐ auth decisions with a TTL longer than you would accept for a ban
⭐        (Day 140 — a cached `is_active` outlives the revocation)
⭐   · ⭐ money balances read for a decision — ⭐⭐ cache the DISPLAY, read the
⭐        TRUTH before you debit
⭐   · ⭐ anything you cannot afford to be stale by the TTL. ⭐⭐ If the answer
⭐        to "how long may this be wrong?" is "never", THE ANSWER IS NOT A CACHE.
```

# Part 5 — ⭐⭐ Redis is not your database

```
⭐⭐ WHAT YOU MUST KNOW BEFORE STORING ANYTHING YOU CANNOT LOSE:

⭐  PERSISTENCE:
⭐   ⭐ RDB  — periodic snapshot. ⭐⭐ A crash loses everything since the last
⭐             one, which may be minutes.
⭐   ⭐ AOF  — append-only log. `everysec` (default) ⭐⭐ LOSES UP TO ONE SECOND.
⭐             `always` is durable and much slower.
⭐   ⇒ ⭐⭐ SO EVEN "PERSISTENT" REDIS ACKNOWLEDGES WRITES IT MAY LOSE. That is
⭐        a deliberate trade for speed, and it is the right trade — ⭐ for a
⭐        cache.
⭐
⭐  REPLICATION:
⭐   ⭐⭐ ASYNCHRONOUS. A primary acks your write, then dies before replicating;
⭐        ⭐ the replica is promoted and ⭐⭐ YOUR ACKNOWLEDGED WRITE NEVER
⭐        EXISTED. ⭐ No configuration removes this — it is the design.
⭐
⭐  EVICTION (`maxmemory-policy`) — ⭐⭐ THE ONE PEOPLE GET BITTEN BY:
⭐   ⭐ `noeviction` (default): ⭐⭐ writes start FAILING when memory is full.
⭐        Your cache becomes a source of errors.
⭐   ⭐ `allkeys-lru`: ⭐⭐ ANY KEY MAY VANISH AT ANY MOMENT, TTL OR NOT.
⭐   ⇒ ⭐⭐ THEREFORE: IF YOU RUN `allkeys-lru` — the right policy for a cache —
⭐        THEN YOUR SESSIONS, YOUR RATE-LIMIT COUNTERS AND YOUR CELERY QUEUE
⭐        CAN BE EVICTED. ⭐ Sessions vanish = everyone logged out. Queue
⭐        evicted = ⭐⭐ jobs silently deleted.
⭐   ⇒ ⭐⭐ SO: SEPARATE INSTANCES (or at minimum separate databases) FOR
⭐        CACHE VS QUEUE VS SESSIONS. ⭐ Different durability requirements
⭐        must not share an eviction policy. ⭐⭐ THIS IS THE ANSWER TO
⭐        "why do you run three Redises?"
```

```
⭐⭐ DISTRIBUTED LOCKS — the honest version, because this is a favourite:
⭐   ⭐ `SET key val NX EX 30` is a lock. ⭐⭐ Release by comparing a UNIQUE
⭐     TOKEN in a Lua script — because `if get(k)==mine: delete(k)` in Python
⭐     is a read-modify-write, and ⭐ you can delete a lock that expired and
⭐     was re-acquired by someone else.
⭐   ⭐⭐ AND THE LIMIT: a lock has a TTL, so a holder that PAUSES (GC, a slow
⭐     disk, a stopped VM) can lose the lock WITHOUT KNOWING, and two holders
⭐     run at once. ⭐ Redlock does not remove this; it is contested precisely
⭐     here.
⭐   ⇒ ⭐⭐ SO A REDIS LOCK IS AN EFFICIENCY LOCK, NOT A CORRECTNESS LOCK.
⭐        ⭐ Use it to avoid duplicate work. For correctness, use the database:
⭐        a unique constraint, `SELECT ... FOR UPDATE` (Day 135), or a fencing
⭐        token the resource checks. ⭐⭐ That distinction is the whole answer.
```

```lua
-- ⭐ safe release: compare-and-delete, atomically
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `SET` with no TTL | A memory leak with a business excuse. Every write gets an `ex`. |
| Updating the cache on write instead of deleting | Interleaved writers can leave the older value cached permanently. Delete. |
| Delete cache, then write DB | A reader in between repopulates stale data for a full TTL. Write, **then** delete. |
| Identical TTLs on bulk-warmed keys | They all expire in the same second. Add jitter. |
| No single-flight on an expensive key | 5,000 simultaneous misses hit the DB and nothing ever finishes. |
| A lock with no TTL | A crashed holder deadlocks it forever. `NX EX` always. |
| Waiters that block indefinitely | Degrade to computing. A slow query must not become a hung request. |
| Cache key missing an input (user, tenant, locale) | You serve one user's data to another — Day 124's leak, in your own process. |
| No version segment in the key | Rolling deploys make old and new code read each other's shapes. |
| `KEYS pattern` in production | O(n) on a single-threaded server — it blocks every client. Use `SCAN`. |
| Sessions/queues on the same instance as `allkeys-lru` cache | Evicted sessions log everyone out; evicted jobs vanish. Separate instances. |
| `noeviction` on a cache | Writes fail when full; the cache becomes an error source. |
| Treating a Redis lock as a correctness guarantee | It's an efficiency lock. Correctness lives in the database. |
| Assuming replicated Redis can't lose an acked write | Replication is asynchronous. It can. |

## Interview questions

**Q: On write, do you update the cache or delete the key?**

> Delete. Two concurrent writers that both update can interleave — writer A reads and computes,
> writer B reads, computes and sets, then A sets its older value — and the cache holds stale data
> until the TTL, with no error anywhere. Deleting means the next read re-derives from the source of
> truth, so there's only ever one place a value is authored. And the ordering matters as much as the
> choice: write the database first, then delete. If you delete first, a concurrent reader loads the
> old row and repopulates the cache for a full TTL; doing it after shrinks that window from the
> length of your write to microseconds.

**Q: A cached homepage query expires and your database falls over. What happened and how do you fix it?**

> A cache stampede. One hot key expires and every in-flight request misses simultaneously, so
> instead of one expensive query you get five thousand, and because the database slows down under
> that load nothing completes and nothing repopulates the cache — it's self-sustaining. Two fixes.
> Single-flight: the first caller takes a Redis lock with `SET NX EX` and recomputes, others wait
> briefly and then fall back to computing rather than blocking forever. And stale-while-revalidate,
> which I prefer: store the value with a longer Redis TTL than its logical freshness, serve stale
> immediately on a logical miss and refresh in the background, so p99 stops depending on the slowest
> query. Separately I'd jitter the TTLs, because 10,000 keys warmed at deploy with the same TTL
> expire in the same second forever after.

**Q: Why would you run more than one Redis instance?**

> Because eviction policy is per-instance and different data has different durability requirements.
> A cache wants `allkeys-lru` — under memory pressure, throw anything away. But if sessions,
> rate-limit counters and the Celery queue share that instance, then under pressure Redis silently
> evicts sessions, which logs everyone out, and evicts queued messages, which deletes jobs with no
> error anywhere. The alternative default, `noeviction`, is worse in a different way: writes start
> failing and your cache becomes a source of 500s. So: separate instances, or at minimum separate
> the durable data out.

**Q: Is a Redis lock safe?**

> Safe enough to prevent duplicate work; not safe enough to protect correctness. Two problems. You
> must release with a Lua compare-and-delete against a unique token, or you'll delete a lock that
> expired and was re-acquired by someone else. And more fundamentally, the lock has a TTL, so a
> holder that pauses — GC, a slow disk, a suspended VM — can lose the lock without knowing, and two
> processes run the critical section at once. Redlock doesn't fix that; it's exactly what the
> critique targets. So I use a Redis lock as an efficiency optimisation, and for anything where
> double execution is *incorrect* I use the database: a unique constraint, `SELECT ... FOR UPDATE`,
> or a fencing token that the resource itself validates.

**Q: How do you decide what to cache?**

> By asking how long the value may be wrong. If the answer is a number — sixty seconds, five minutes
> — that number is the TTL and I often need no invalidation code at all, which is the most
> underrated option. If the answer is "never", it isn't cacheable, and that covers auth decisions
> and any balance read to authorise a debit: cache the display value, read the truth before you take
> money. Then I ask who may read it, which decides whether the user id belongs in the key — a key
> missing an input that varies the value serves one user's data to another.

## 🎙️ Articulation drill

**Two minutes: "Add caching to this slow endpoint."**

Start with the two questions — how long may it be wrong, and who may read it — and turn the first
answer into a TTL and the second into the key. Say cache-aside, write-then-delete, and why delete
rather than update. Then raise the stampede before you're asked, because that's the failure this
design has, and give both answers: single-flight with `NX EX` and a fallback, or
stale-while-revalidate if p99 matters. Mention TTL jitter and say it's the same fix as retry jitter.
Close on the boundary: **this instance is `allkeys-lru`, so nothing that must survive lives here** —
sessions, queues and counters get their own.
