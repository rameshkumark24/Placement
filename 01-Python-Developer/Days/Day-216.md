# Part 1 — The model you already have

```
⭐⭐ PYTHON (Day 070)              ⭐⭐ JAVASCRIPT
⭐  one thread                     one thread
⭐  an event loop                  ⭐ THE SAME EVENT LOOP IDEA
⭐  coroutine suspends at await    ⭐ function suspends at await
⭐  asyncio.gather()               Promise.all()
⭐  asyncio.create_task()          ⭐ calling an async fn (it starts NOW)
⭐  a blocking call stalls all     ⭐⭐ A BLOCKING LOOP STALLS ALL —
⭐    (Day 072)                        AND FREEZES THE SCREEN TOO

⭐⭐ THE ONE STRUCTURAL DIFFERENCE:
⭐   Python: async def f() -> calling it gives you a coroutine that
⭐           ⭐ HAS NOT STARTED. Nothing runs until awaited/scheduled.
⭐   JS:     async function f() -> calling it ⭐⭐ STARTS RUNNING
⭐           IMMEDIATELY and hands you a Promise for the result.
⭐   ⇒ ⭐⭐ IN JS, "FIRE AND FORGET" IS THE DEFAULT, NOT AN OPT-IN.
⭐     That single difference produces the failure in Part 4.
```

| ⭐ Concept | Python | JavaScript |
|---|---|---|
| The awaitable | coroutine / `Task` / `Future` | **Promise** — pending → fulfilled \| rejected |
| Start concurrently | `asyncio.create_task(f())` | ⭐ `const p = f()` — already started |
| Wait for all | `asyncio.gather(*ts)` | `Promise.all([...])` |
| All, keep failures | `gather(..., return_exceptions=True)` | ⭐⭐ `Promise.allSettled([...])` |
| First to finish | `asyncio.wait(FIRST_COMPLETED)` | `Promise.race([...])` |
| First to **succeed** | — | ⭐ `Promise.any([...])` |
| Timeout | `asyncio.timeout()` | `AbortSignal.timeout(ms)` — Day 227 |
| Structured concurrency | `TaskGroup` (Day 071) | ⭐ **none** — you supply the discipline |

# Part 2 — ⭐⭐ The same mistake you already learned once

```javascript
// ❌ SEQUENTIAL — 4 requests × 200 ms = 800 ms
for (const id of ids) {
  const user = await fetchUser(id);       // ⭐⭐ each waits for the last
  users.push(user);
}

// ✅ CONCURRENT — 200 ms
const users = await Promise.all(ids.map(id => fetchUser(id)));
```

> ⭐⭐ **This is byte-for-byte the Day 070 lesson.** `await` in a loop is sequential in both languages,
> and in both it is the most common async performance bug. The tell is identical: **your latency is
> `n × one_request` and it scales linearly with a number you did not intend to make a multiplier.**

```
⭐⭐ AND THE SAME CAVEAT: Promise.all IS UNBOUNDED.

⭐   ids.map(fetchUser)  with 5,000 ids
⭐   ⇒ ⭐⭐ 5,000 SIMULTANEOUS REQUESTS. The browser caps ~6 per host
⭐     so they queue — but you have also just DDoSed your own API
⭐     and made every response's latency terrible.

⭐   ⇒ ⭐ BOUND THE FAN-OUT. Same fix as Day 071:
⭐     batch it, or use a small concurrency limiter.
```

### The failure semantics differ, and it matters

| | Behaviour |
|---|---|
| `Promise.all` | ⭐⭐ **Rejects on the first failure.** You get one error and **lose the successful results.** The others keep running — they are not cancelled. |
| `Promise.allSettled` | ⭐ Never rejects. Returns `{status, value}` / `{status, reason}` per item. **Use this whenever partial success is meaningful.** |

```javascript
// ⭐⭐ dashboard: three widgets, one API each. One failing must not blank the page.
const [users, orders, stats] = await Promise.allSettled([
  fetchUsers(), fetchOrders(), fetchStats(),
]);
if (users.status === "fulfilled") render(users.value);
else showWidgetError("users", users.reason);   // ⭐ the other two still rendered
```

> ⭐ **The design question, not the API question:** *is partial success meaningful to the user?* On a
> dashboard, yes — `allSettled`. On a checkout where all three must succeed, no — `all`, and fail
> loudly. Choosing correctly is a design decision you should say out loud.

# Part 3 — Microtasks, and why your `console.log` order surprises you

```
⭐⭐ ONE TICK OF THE LOOP

⭐   1. run one macrotask   (a click, a timer, an I/O callback)
⭐   2. ⭐⭐ DRAIN THE ENTIRE MICROTASK QUEUE  (every .then / await
⭐      continuation — including ones queued while draining)
⭐   3. render if needed
⭐   4. next macrotask

⭐   ⇒ ⭐⭐ PROMISES ALWAYS BEAT setTimeout(0). Always.
⭐   ⇒ ⭐ AN INFINITE MICROTASK CHAIN STARVES RENDERING COMPLETELY —
⭐     the tab freezes and no timer ever fires again.
```

```javascript
console.log("1");
setTimeout(() => console.log("2"), 0);      // macrotask
Promise.resolve().then(() => console.log("3"));  // microtask
console.log("4");
// ⭐⭐ 1, 4, 3, 2
```

> ⭐ **Why a backend engineer should care.** It is the same priority-inversion shape as Day 458's eval
> job starving user traffic: a queue that is always drained fully before the next thing gets a turn
> will starve that next thing if you can keep feeding it. Here the starved thing is *the screen*.

# Part 4 — ⭐⭐ The failure Python does not have

Because calling an async function starts it, you can create a promise, never await it, and have its
failure disappear.

```javascript
// ❌ nothing awaits this. If it rejects, the app carries on as if fine.
saveDraft(doc);

// ⭐⭐ the user believes it saved. It did not. There is no error anywhere
//    in your UI — only an "Unhandled Promise Rejection" in the console
//    that nobody has open in production.
```

| ⭐ Fix | |
|---|---|
| **`await` it** | If the result matters, await it. Obvious and usually right. |
| **`.catch()` it explicitly** | ⭐ `saveDraft(doc).catch(reportError)` — deliberate fire-and-forget, failure still reported. |
| **⭐⭐ A global handler** | `window.addEventListener("unhandledrejection", reportError)` — the net that catches what you missed. **Wire this on day one of any real app** (Day 279). |
| **`void` for intent** | ⭐ `void saveDraft(doc).catch(log)` — signals "deliberately not awaited" to readers and linters. |

```
⭐⭐ THE PARALLEL YOU ALREADY KNOW
⭐   Python Day 069: an exception inside a Future that nobody
⭐   calls .result() on ⭐ VANISHES SILENTLY.
⭐   ⇒ ⭐⭐ SAME BUG, SAME SHAPE, DIFFERENT LANGUAGE:
⭐     AN ERROR NOBODY IS WAITING FOR IS AN ERROR NOBODY SEES.
⭐   ⇒ and it is the Day 455 lesson again — the dangerous failure
⭐     does not raise.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "explain JavaScript's concurrency model."**

Anchor it to what you already know, because that is the senior move. **It's the same model as Python's
asyncio — one thread, an event loop, cooperative suspension at `await`. So the same bugs transfer:
`await` in a loop is sequential, and if my latency is n times one request, that's the tell. `Promise.all`
is `gather`.**

Then name the real difference, because it is the part that produces a distinct failure. **Calling an
async function in JavaScript starts it immediately and hands you a promise — a Python coroutine hasn't
started until you await it. So fire-and-forget is the default rather than an opt-in, and a promise
nobody awaited can reject and vanish. The user sees a save that silently didn't happen, and the only
trace is an unhandled rejection in a console nobody has open in production. That's the same shape as a
Python Future whose result is never read — an error nobody is waiting for is an error nobody sees.**

Close on the choice that shows design thinking. **`Promise.all` rejects on first failure and throws away
the successes, `allSettled` gives you every outcome. Which one you want isn't an API question, it's
whether partial success means anything to the user — on a dashboard it does, on a checkout it doesn't.**
