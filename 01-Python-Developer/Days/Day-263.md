# Part 1 — ⭐⭐ The dual write, stated concretely

```
⭐   with uow:
⭐       invoice.mark_paid()          # ⭐ Postgres
⭐       uow.commit()
⭐   notify_customer(invoice)         # ⭐⭐ a second system

⭐⭐ FOUR THINGS CAN HAPPEN, AND TWO OF THEM ARE BUGS YOU CANNOT SEE:
⭐   ① both succeed                                     ✅
⭐   ② the commit fails ⇒ nothing happened              ✅
⭐   ③ ⭐⭐ the commit SUCCEEDS and the notify FAILS ⇒ paid, silent
⭐   ④ ⭐⭐ the process DIES between them ⇒ same, and no log line
⭐   ⇒ ⭐⭐ THERE IS NO ORDERING THAT FIXES THIS. Notify first and you
⭐     notify about payments that never commit. ⭐ Two systems, one
⭐     operation, no atomicity — ⭐⭐ AND WRAPPING IT IN `try/except`
⭐     MAKES IT WORSE, because now the failure is swallowed.

⭐⭐ THE FIX IS TO MAKE IT ***ONE*** WRITE:
⭐   with uow:
⭐       invoice.mark_paid()
⭐       uow.outbox.add(InvoicePaid(...))   # ⭐⭐ SAME TRANSACTION
⭐       uow.commit()                       # ⭐ atomic: both or neither
⭐   ⭐ A separate relay reads the outbox and does the second system.
⭐   ⇒ ⭐⭐ YOU HAVE NOT ELIMINATED THE PROBLEM — YOU HAVE MOVED IT TO A
⭐     PLACE WHERE ***RETRYING IS SAFE***, which is the whole trick.
```

# Part 2 — ⭐⭐ The relay

```sql
-- ⭐⭐ THE CLAIM QUERY. Day 196's `SKIP LOCKED`, doing real work.
WITH claimed AS (
    SELECT id FROM outbox
    WHERE processed_at IS NULL
      AND next_attempt_at <= now()          -- ⭐ backoff lives in a column
    ORDER BY id                             -- ⭐⭐ id order = commit order
    FOR UPDATE SKIP LOCKED                  -- ⭐⭐ N relays, no coordination
    LIMIT 50
)
UPDATE outbox o SET attempts = attempts + 1, claimed_at = now()
FROM claimed c WHERE o.id = c.id
RETURNING o.*;
```

```
⭐⭐ SIX DESIGN POINTS, EACH OF WHICH IS A BUG IF YOU SKIP IT:
⭐  ① ⭐⭐ `SKIP LOCKED` MEANS YOU CAN RUN TEN RELAYS WITH NO LEADER
⭐     ELECTION AND NO LOCK. ⭐ Each takes different rows. That is the
⭐     entire concurrency design.
⭐  ② ⭐⭐ CLAIM AND DELIVER IN ***SEPARATE*** TRANSACTIONS. The claim
⭐     commits, then the HTTP call happens with no transaction open
⭐     (Day 256). ⭐ Holding one across the call is the mistake the
⭐     outbox existed to prevent.
⭐  ③ ⭐ `attempts` INCREMENTS ON CLAIM, NOT ON FAILURE — ⭐⭐ so a relay
⭐     that dies mid-delivery still counts the attempt, and a poison
⭐     message cannot loop forever by crashing the process each time.
⭐  ④ ⭐ ORDER BY `id` GIVES YOU COMMIT ORDER, which is the only order
⭐     that means anything. ⭐⭐ AND IT IS NOT A GUARANTEE ACROSS
⭐     RELAYS — ten workers deliver concurrently, so ⭐⭐ ORDER IS
⭐     BEST-EFFORT AND YOUR CONSUMERS MUST NOT DEPEND ON IT (Day 161).
⭐     ⭐ If one stream genuinely needs order, add a partition key and
⭐     one relay per key.
⭐  ⑤ ⭐⭐ DELETE OR ARCHIVE PROCESSED ROWS. An outbox table that only
⭐     grows makes the partial index grow and the claim query slow —
⭐     ⭐ a nightly `DELETE ... WHERE processed_at < now() - 7 days`, in
⭐     batches.
⭐  ⑥ ⭐⭐ THE PARTIAL INDEX IS THE PERFORMANCE STORY:
⭐     `CREATE INDEX ON outbox (id) WHERE processed_at IS NULL` — ⭐ it
⭐     stays tiny forever because rows LEAVE it when processed (Day 190).
```

```python
def relay_once(session_factory, publisher, now) -> int:
    with session_factory() as s:                 # ⭐ TXN 1: claim
        rows = s.execute(CLAIM_SQL).all(); s.commit()
    for row in rows:
        try:
            publisher.publish(row)               # ⭐⭐ NO TRANSACTION
        except PermanentError:
            _dead_letter(row); continue
        except Exception:
            _schedule_retry(row, now); continue  # ⭐ TXN 3
        _mark_done(row, now)                     # ⭐ TXN 2
    return len(rows)
```

# Part 3 — ⭐⭐ At-least-once, and the consumer's obligation

```
⭐⭐ THE RELAY CAN ALWAYS DELIVER TWICE — THERE IS NO DESIGN THAT
⭐   PREVENTS IT. ⭐ The call succeeds and the process dies before
⭐   `_mark_done`; the row is reclaimed; it is delivered again.
⭐   ⇒ ⭐⭐ TO GET EXACTLY-ONCE ACKNOWLEDGEMENT YOU WOULD NEED AN ATOMIC
⭐     COMMIT ACROSS YOUR DATABASE AND THEIRS, WHICH IS THE PROBLEM YOU
⭐     STARTED WITH. ⭐ At-least-once is not a compromise; it is the
⭐     ceiling.
⭐   ⇒ ⭐⭐ THEREFORE: EVERY CONSUMER IS IDEMPOTENT. That is the price
⭐     of admission (Day 184 #6), and it is non-negotiable.

⭐⭐ THREE WAYS TO MAKE A CONSUMER IDEMPOTENT, IN ORDER OF PREFERENCE:
⭐  ① ⭐⭐ A NATURALLY IDEMPOTENT OPERATION — `SET status='paid'` rather
⭐     than `balance = balance + x`. ⭐ Free, and always try this first.
⭐  ② ⭐⭐ A DERIVED IDEMPOTENCY KEY the third party enforces.
⭐     ⭐ `key = sha256(f"{event_id}")` sent as Stripe's
⭐       `Idempotency-Key`. ⭐⭐ DERIVED, NOT RANDOM — a random key
⭐       regenerated on retry is idempotency theatre (Day 251).
⭐  ③ ⭐ A `processed_events(event_id)` TABLE with a unique index, on
⭐     the consumer side. ⭐⭐ Insert-and-check in the same transaction
⭐     as the effect, or the check is a race.
```

# Part 4 — ⭐⭐ The third outcome

```python
try:
    result = payments.charge(amount, idempotency_key=key, timeout=10)
except httpx.TimeoutException:
    order.status = "payment_unknown"      # ⭐⭐ NOT failed. NOT succeeded.
    session.commit()
    schedule_reconciliation(order.id)     # ⭐ Part 5
    raise PaymentPending(order.id)        # ⭐ the API returns 202
```

```
⭐⭐ WHY THIS IS THE MOST IMPORTANT STATE IN THE SYSTEM:
⭐   ⭐ A timeout means the request MAY have arrived, MAY have been
⭐     processed, and the RESPONSE may have been lost. ⭐⭐ THE CARD MAY
⭐     BE CHARGED.
⭐   ⭐ Treat it as FAILED ⇒ ⭐⭐ you retry, the derived key saves you
⭐     (if you used one) or you double-charge (if you did not) — and you
⭐     tell the customer their payment failed while their statement says
⭐     otherwise.
⭐   ⭐ Treat it as SUCCEEDED ⇒ ⭐⭐ you ship goods nobody paid for.
⭐   ⇒ ⭐⭐ THE THIRD STATE IS NOT DEFENSIVE PROGRAMMING. IT IS THE ONLY
⭐     HONEST MODEL OF WHAT YOU KNOW.

⭐⭐ AND THE RULE THAT GENERALISES BEYOND PAYMENTS:
⭐   ⭐⭐ ***ANY WRITE TO A SYSTEM YOU DO NOT CONTROL HAS THREE
⭐     OUTCOMES, NOT TWO.*** ⭐ Sending an email, creating a user in a
⭐     CRM, uploading to S3, calling your own other service. ⭐⭐ Most
⭐     of the time the third outcome is cheap to resolve; for money it is
⭐     the difference between an incident and a scandal.
```

# Part 5 — ⭐ Reconciliation: the job nobody writes

```
⭐⭐ EVERY `payment_unknown` MUST BE RESOLVED BY ASKING THE PROVIDER —
⭐   NOT BY GUESSING, AND NOT BY A HUMAN LOOKING AT A DASHBOARD.

⭐   every 5 min:
⭐     for order in payment_unknown older than 60 s:
⭐         ⭐ ask the provider by YOUR idempotency key / reference
⭐         ⭐ found + succeeded ⇒ transition to paid, emit InvoicePaid
⭐         ⭐ found + failed    ⇒ transition to failed, release the hold
⭐         ⭐ not found         ⇒ ⭐⭐ THE CHARGE NEVER ARRIVED. Safe to
⭐              retry with the SAME derived key.
⭐         ⭐⭐ still unknown after 24 h ⇒ ALERT A HUMAN. ⭐ Some
⭐              fraction always needs one, and pretending otherwise is
⭐              how it silently stays unresolved for a month.

⭐ ⭐⭐ THE THREE THINGS THAT MAKE THIS WORK:
⭐   ⭐ YOU MUST HAVE SENT A REFERENCE YOU CAN LOOK UP BY. ⭐⭐ If you
⭐     did not attach your own id to the charge, reconciliation is
⭐     impossible and the state is permanent. ⭐ Decide this on the day
⭐     you write the client, not the day you need it.
⭐   ⭐ THE JOB IS IDEMPOTENT AND BOUNDED (Day 159): a watermark, a
⭐     batch limit, and a `SKIP LOCKED` claim so two instances are safe.
⭐   ⭐⭐ A GAUGE OF `payment_unknown` COUNT AND AGE. ⭐⭐ IF THE OLDEST
⭐     UNRESOLVED ROW IS GROWING, RECONCILIATION IS BROKEN — and that
⭐     is the only signal you will get.
```

# Part 6 — ⭐⭐ Inbound webhooks, failures, and the four metrics

```
⭐⭐ INBOUND IS A STATE MACHINE, NOT A SEQUENCE (Day 158):
⭐   ⭐ Verify the HMAC over the ***RAW BYTES***, before parsing —
⭐     ⭐⭐ re-serialising JSON changes the bytes and the signature fails
⭐     for reasons nobody can find. ⭐ `compare_digest`, and a timestamp
⭐     check to bound replay.
⭐   ⭐⭐ THEY ARRIVE OUT OF ORDER. `payment.succeeded` can arrive before
⭐     `payment.created`. ⭐ Do not assume; look at the current state and
⭐     decide whether this event is a legal transition.
⭐   ⭐ THEY ARRIVE TWICE. Dedupe by the provider's event id in a table
⭐     with a unique index.
⭐   ⭐⭐ RETURN 200 QUICKLY AND DO THE WORK ASYNCHRONOUSLY. ⭐ Your 200
⭐     means "received", not "processed" — ⭐⭐ and a slow handler means
⭐     the provider retries, which means duplicates you then have to
⭐     dedupe anyway.

⭐⭐ FAILURE HANDLING — three categories, three responses:
⭐   ⭐ TRANSIENT (timeout, 5xx, connection reset) ⇒ retry with
⭐     exponential backoff AND ⭐⭐ JITTER (Day 152 — without jitter,
⭐     everything that failed together retries together).
⭐   ⭐ PERMANENT (400, 422, "customer does not exist") ⇒ ⭐⭐ DO NOT
⭐     RETRY. Dead-letter immediately; retrying a 422 forever is pure
⭐     waste and it hides the bug.
⭐   ⭐⭐ POISON (fails every time for an unknown reason) ⇒ after N
⭐     attempts, dead-letter with the full payload and the last error.
⭐     ⭐ A DLQ nobody looks at is a DLQ that does not exist — so it
⭐       gets an alert on non-zero, not a dashboard.

⭐⭐ THE FOUR METRICS. WITHOUT THESE THE WHOLE MECHANISM IS INVISIBLE:
⭐   ① ⭐⭐ OUTBOX BACKLOG (unprocessed count) — ⭐ rising means the
⭐        relay is down or slower than production. ⭐⭐ THE SINGLE MOST
⭐        IMPORTANT NUMBER HERE.
⭐   ② ⭐⭐ OLDEST UNPROCESSED AGE — ⭐ a backlog of 50 that is 3 seconds
⭐        old is healthy; a backlog of 5 that is 40 minutes old is a
⭐        stuck poison message.
⭐   ③ ⭐ DELIVERY LATENCY p95, and the attempt distribution.
⭐   ④ ⭐ DLQ DEPTH — alert on > 0.
⭐   ⭐⭐ AND A DEAD-MAN CHECK: alert if the relay has processed NOTHING
⭐     for five minutes during business hours. ⭐ Day 159: alert on
⭐     absence, because a relay that silently stopped produces no errors
⭐     at all.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Reordering the two writes to fix the dual write | No ordering fixes it. Make it one write plus a relay. |
| `try/except` around the second write | Now the failure is swallowed as well as unatomic. |
| Holding the transaction across the delivery call | That's the mistake the outbox existed to prevent. |
| Incrementing attempts on failure rather than on claim | A crash-looping poison message never counts an attempt. |
| Depending on outbox ordering | Ten relays deliver concurrently. Best-effort, unless you partition. |
| An outbox table that only grows | The claim query and the partial index degrade. Archive in batches. |
| A full index instead of a partial one | The point is that rows *leave* the index when processed. |
| Aiming for exactly-once delivery | It requires the atomic cross-system commit you started without. |
| A random idempotency key regenerated per retry | Idempotency theatre. Derive it from the event id. |
| Treating a timeout as a failure | You double-charge, or tell the customer it failed while their statement disagrees. |
| Treating a timeout as a success | You ship goods nobody paid for. |
| No reconciliation job | The unknown state is permanent and nobody notices. |
| Not sending your own reference on the charge | Reconciliation becomes impossible after the fact. |
| No alert when unknowns age past a day | Some fraction always needs a human; without the alert it stays unresolved for a month. |
| Verifying the webhook signature after parsing | Re-serialisation changes the bytes and the signature fails inexplicably. |
| Assuming webhooks arrive in order | They don't. Check whether the event is a legal transition from current state. |
| Doing the work before returning 200 | The provider retries, and you get duplicates anyway. |
| Retrying a permanent 422 | Pure waste, and it hides the bug. |
| A DLQ with no alert | A DLQ nobody looks at doesn't exist. |
| Monitoring backlog but not oldest age | A small stuck backlog looks healthy. |
| No dead-man check on the relay | A relay that stopped produces no errors at all. |

## Interview questions

**Q: What's the dual-write problem and how do you solve it?**

> Committing to your database and then calling a second system is two writes with no atomicity, and
> there's no ordering that fixes it: commit-then-notify loses notifications when the process dies in
> between; notify-then-commit notifies about things that never commit. Wrapping it in `try/except`
> makes it worse, because now the failure is swallowed too. The fix is to make it one write — the state
> change and an outbox row in the same transaction, so they're atomic — and then a separate relay reads
> the outbox and performs the external call. The honest framing is that this doesn't eliminate the
> problem, it moves it to a place where retrying is safe, which is the whole trick. Delivery is
> at-least-once, so every consumer has to be idempotent, and that's the ceiling rather than a
> compromise: exactly-once acknowledgement would need an atomic commit across two systems, which is
> the thing you didn't have.

**Q: Walk me through the relay.**

> A claim query using `SELECT ... FOR UPDATE SKIP LOCKED` over unprocessed rows ordered by id, limited
> to a batch — which means I can run ten relays with no leader election and no distributed lock,
> because each takes different rows. The claim commits in its own transaction, then the external call
> happens with no transaction open, then the result is recorded in another. Three details matter:
> attempts increment on *claim* rather than on failure, so a relay that dies mid-delivery still counts
> the attempt and a poison message can't loop forever by crashing the process; the index is partial on
> `processed_at IS NULL`, so it stays tiny forever because rows leave it when processed; and processed
> rows get archived in batches, or the table growth eventually degrades the claim. On ordering: id
> order is commit order, but with concurrent relays that's best-effort, so consumers must not depend on
> it — and if one stream genuinely needs ordering, it gets a partition key and a single relay per key.

**Q: What is `payment_unknown` and why does it exist?**

> Because a timeout is not a failure — it's the absence of information. The request may have arrived,
> may have been processed, and the response may have been lost, which means the card may be charged.
> If you model that as failed, you retry: with a derived idempotency key you're saved, without one you
> double-charge, and either way you've told the customer their payment failed while their statement
> says otherwise. If you model it as succeeded, you ship goods nobody paid for. So the third state
> isn't defensive programming, it's the only honest model of what you actually know. And it generalises
> beyond payments: every write to a system you don't control has three outcomes, not two — emails, CRM
> records, S3 uploads, calls to your own other services. Usually the third one is cheap to resolve;
> for money it's the difference between an incident and a scandal.

**Q: What resolves an unknown state?**

> A reconciliation job, not a human and not a guess. Every few minutes it takes payments that have been
> unknown for more than a minute and asks the provider by *your* reference: succeeded means transition
> to paid and emit the event, failed means release the hold, and not found means the charge never
> arrived so it's safe to retry with the same derived key. Three things make it work. You must have
> sent a reference you can look up by — if you didn't attach your own id to the charge, reconciliation
> is impossible after the fact and the state is permanent, so that's a decision made when you write
> the client, not when you need it. The job is idempotent and bounded, with a watermark and a
> `SKIP LOCKED` claim so two instances are safe. And there's a gauge on the count and the *age* of
> unresolved rows, with an alert past twenty-four hours — because some fraction always needs a human,
> and pretending otherwise is how it stays unresolved for a month.

**Q: How do you know the outbox is working?**

> Four metrics and a dead-man check. Backlog — the count of unprocessed rows — which is the single most
> important number, because a rising backlog means the relay is down or slower than production. Oldest
> unprocessed age, which is the one people skip and which catches the case that backlog can't: fifty
> rows three seconds old is healthy, five rows forty minutes old is a stuck poison message. Delivery
> latency and the attempt distribution. And dead-letter depth with an alert on greater than zero,
> because a DLQ nobody looks at doesn't exist. The dead-man check is the important addition: alert if
> the relay has processed *nothing* for five minutes during business hours, because a relay that
> silently stopped produces no errors at all — you can only detect it by the absence of success.

## 🎙️ Articulation drill

**Three minutes: "How do you make sure a payment and its notification can't diverge?"**

Start with the problem stated as four outcomes, and name the two that are invisible: the commit
succeeds and the second write doesn't, and the process dies in between. Say that no ordering fixes it
and that catching the exception makes it worse. Then the fix in one sentence — one transaction
containing the state change and the outbox row — and be honest about what it achieves: **it doesn't
eliminate the problem, it moves it somewhere retrying is safe.** Then at-least-once as the ceiling, and
therefore idempotent consumers as the price of admission. Then spend a full minute on the third
outcome, because it's the part that separates people who have shipped payments from people who
haven't: **a timeout is not a failure, it's the absence of information — treat it as failed and you
double-charge, treat it as succeeded and you ship for free.** Close on the two operational facts:
reconciliation is impossible unless you attached your own reference when you made the charge, and a
relay that silently stops produces no errors, so you alert on the absence of success.
