# Day 399 🧩

**P-399** · 🧩 **Decomposition** — by domain not layer, ⭐⭐ and sync vs async as an availability decision

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the unit of decomposition is the set of things that must change together
> and stay consistent together — and the test is not "does this feel like a separate concern", it is
> "can this team deploy on a Friday afternoon without asking anyone."**

---

# Part 1 — The three wrong axes, and why each fails

```
⭐⭐ ① ***BY LAYER.*** ⭐ `api-service`, `business-service`,
⭐    `data-service`.
⭐    ⭐⭐ WHY IT FAILS: EVERY FEATURE TOUCHES ALL THREE. ⭐ So
⭐    every change is a three-repository, three-deploy,
⭐    ordered-rollout operation. ⭐⭐ YOU HAVE NOT DECOMPOSED
⭐    ANYTHING — YOU HAVE DISTRIBUTED YOUR FUNCTION CALL STACK
⭐    AND PUT A NETWORK BETWEEN THE FRAMES.

⭐⭐ ② ***BY ENTITY.*** ⭐ `user-service`, `order-service`,
⭐    `product-service`. ⭐ Looks like domain modelling.
⭐    ⭐⭐ WHY IT FAILS: EVERY REAL OPERATION IS NOW A CROSS-SERVICE
⭐    JOIN. ⭐ "Show this user's orders with product names" is
⭐    three calls and an in-memory join ⭐⭐ THAT THE DATABASE USED
⭐    TO DO FOR FREE AND BETTER. ⭐ Entities are nouns; ⭐⭐ SERVICES
⭐    SHOULD BE ***CAPABILITIES***.

⭐⭐ ③ ***BY TECHNOLOGY.*** ⭐ "The Python service and the Go
⭐    service." ⭐⭐ THAT IS A STAFFING ARTEFACT, NOT A BOUNDARY,
⭐    ⭐ and it moves whenever someone leaves.

⭐⭐ ⇒ ***THE RIGHT AXIS IS A BOUNDED CONTEXT AROUND AN
⭐   INVARIANT.*** ⭐ Ask: ⭐⭐ ***WHAT DATA MUST BE
⭐   TRANSACTIONALLY CONSISTENT WITH WHAT?*** ⭐ That set cannot
⭐   be split without turning a transaction into a saga
⭐   (Day 408) — ⭐⭐ SO THE INVARIANTS DRAW THE LINES, AND
⭐   EVERYTHING ELSE IS PREFERENCE. ⭐ It is Day 330's sharding
⭐   question asked about services instead of rows.
```

# Part 2 — The four tests, in order

```
⭐ ① ⭐⭐ ***DEPLOYMENT INDEPENDENCE.*** ⭐ Can you release this
⭐    alone, at any time, without coordinating? ⭐⭐ AND THE
⭐    EVIDENCE IS NOT AN OPINION — IT IS `git log`: ⭐ how often do
⭐    commits touch both repositories in the same PR? ⭐⭐ IF THE
⭐    ANSWER IS "USUALLY", THEY ARE ONE SERVICE PRETENDING TO BE
⭐    TWO (DAY 340).

⭐ ② ⭐⭐ ***DATA OWNERSHIP: EXACTLY ONE WRITER PER TABLE.***
⭐    ⭐ Always. ⭐⭐ TWO SERVICES WRITING ONE TABLE IS THE SINGLE
⭐    WORST MARKER OF A DISTRIBUTED MONOLITH, ⭐ because now
⭐    neither can change the schema and both must deploy
⭐    together forever. ⭐ Reads across the line go through an
⭐    API or a replicated read model (Day 406), ⭐⭐ NEVER THROUGH
⭐    THE OTHER SERVICE'S DATABASE.

⭐ ③ ⭐⭐ ***FAILURE ISOLATION.*** ⭐ If this service is down, what
⭐    still works? ⭐⭐ IF THE HONEST ANSWER IS "NOTHING", YOU HAVE
⭐    ADDED LATENCY AND FAILURE MODES AND BOUGHT NO ISOLATION.
⭐    ⭐ This is the test that catches the "we did microservices"
⭐    architecture that is strictly worse than the monolith.

⭐ ④ ⭐ ***TEAM OWNERSHIP.*** ⭐ Conway's law is not a warning,
⭐    ⭐⭐ IT IS A FORECAST: YOUR ARCHITECTURE WILL COME TO MATCH
⭐    YOUR COMMUNICATION STRUCTURE WHETHER YOU DESIGN IT OR NOT.
⭐    ⭐ A service with no owning team decays.
```

# Part 3 — ⭐⭐ Sync vs async is an availability decision, with arithmetic

```
⭐⭐ THE ARITHMETIC NOBODY DOES, AND IT SETTLES THE ARGUMENT:

⭐ A ***synchronous*** chain of N services, each at 99.9%:
⭐   ⭐ 1 service ....... 99.9%   → 43 min/month down
⭐   ⭐ 3 services ...... 99.7%   → 2.2 hours
⭐   ⭐⭐ 5 SERVICES ..... 99.5%   → ***3.6 HOURS***
⭐   ⭐ 10 services ..... 99.0%   → 7.2 hours

⭐⭐ ⇒ ***EVERY SYNCHRONOUS DEPENDENCY MULTIPLIES YOUR DOWNTIME.
⭐   EVERY ASYNCHRONOUS ONE DOES NOT.*** ⭐ An async dependency
⭐   being down means work queues up; ⭐ a sync dependency being
⭐   down means ***you*** are down. ⭐⭐ THAT IS THE WHOLE
⭐   DIFFERENCE AND IT IS AN AVAILABILITY DIFFERENCE, NOT A
⭐   PERFORMANCE ONE.

⭐⭐ THE RULE THAT FALLS OUT: ***SYNCHRONOUS WHEN YOU NEED THE
⭐   ANSWER TO RESPOND. ASYNCHRONOUS WHEN YOU NEED THE WORK
⭐   DONE.***
⭐   ⭐ "Is this card valid?" → ⭐ sync. ⭐ You cannot answer
⭐     without it.
⭐   ⭐ "Send the receipt email" → ⭐⭐ ASYNC. ⭐ The user does not
⭐     wait, and the email service being down must not fail the
⭐     order.
⭐   ⭐ "Update the search index" → ⭐⭐ ASYNC, ALWAYS.

⭐⭐ AND THE REFRAME THAT MAKES IT DECIDABLE IN ONE QUESTION:
⭐   ⭐⭐ ***IS THIS A QUERY OR A COMMAND?*** ⭐ A query needs an
⭐   answer now, so it is synchronous. ⭐⭐ A COMMAND USUALLY DOES
⭐   NOT, AND MAKING IT SYNCHRONOUS IS A CHOICE YOU SHOULD HAVE
⭐   TO JUSTIFY (DAY 333).

⭐ ⭐ Mitigations when sync is genuinely required: ⭐ a cache with
⭐   `stale-if-error` semantics, ⭐ a default answer, ⭐⭐ AND —
⭐   THE BEST ONE — ***DEGRADE RATHER THAN FAIL***: ⭐ if the
⭐   recommendation service is down, show the popular list, ⭐⭐ AND
⭐   THAT IS A PRODUCT DECISION YOU MUST GO AND GET.
```

# Part 4 — The sequence that actually works

```
⭐ ① ⭐⭐ ***MODULAR MONOLITH FIRST.*** ⭐ One deployable, one
⭐    database, ⭐ but real internal module boundaries with
⭐    enforced import rules (Part 5).
⭐ ② ⭐ Let the boundaries move for six months while you are
⭐    still learning the domain. ⭐⭐ MOVING A PACKAGE IS AN
⭐    AFTERNOON; MOVING A SERVICE BOUNDARY IS A QUARTER.
⭐ ③ ⭐⭐ EXTRACT WHEN THERE IS A ***REASON***, AND THE REASONS
⭐    ARE A SHORT LIST:
⭐    ⭐ ① different scaling profile (the image processor needs
⭐      GPUs; the API does not)
⭐    ⭐ ② different team, with a real coordination cost you can
⭐      point at
⭐    ⭐ ③ different runtime or language requirement
⭐    ⭐ ④ different compliance or blast-radius boundary
⭐    ⭐ ⑤ different release cadence you can demonstrate
⭐    ⭐⭐ "IT WOULD BE CLEANER" IS NOT ON THE LIST.

⭐⭐ ⇒ AND THE SENTENCE THAT REFRAMES THE WHOLE DEBATE:
⭐   ⭐⭐ ***EXTRACTING A SERVICE FROM A WELL-MODULARISED MONOLITH
⭐   IS A WEEK. EXTRACTING ONE FROM A BALL OF MUD IS A YEAR.***
⭐   ⭐ So the modularisation ***is*** the work, ⭐⭐ AND THE
⭐   EXTRACTION IS THE EASY PART YOU MAY NEVER NEED TO DO.
⭐   ⭐ Which means "monolith first" is not a compromise —
⭐   ⭐⭐ IT IS THE CHEAPEST PATH TO MICROSERVICES ***AND*** THE
⭐   CHEAPEST PATH TO NOT NEEDING THEM.
```

# Part 5 — Enforcing boundaries in Python, which is harder than in Java

```
⭐⭐ PYTHON HAS NO `package-private`. ⭐ Any module can import any
⭐   other module. ⭐⭐ SO A BOUNDARY THAT IS ONLY A CONVENTION WILL
⭐   BE VIOLATED WITHIN A MONTH, BY SOMEONE IN A HURRY, AT 6 P.M.

⭐⭐ ⇒ ***THE ANSWER IS `import-linter` WITH LAYERED CONTRACTS IN
⭐   CI.*** ⭐ It turns architecture into a test that fails.
```

```ini
# .importlinter
[importlinter]
root_package = flagship

[importlinter:contract:layers]
name = Domain layers
type = layers
layers =
    flagship.web
    flagship.application
    flagship.domain
# ⭐⭐ domain CANNOT IMPORT application OR web. ENFORCED, NOT HOPED.

[importlinter:contract:contexts]
name = Bounded contexts are independent
type = independence
modules =
    flagship.billing
    flagship.catalog
    flagship.shipping
# ⭐⭐ NONE OF THESE MAY IMPORT ANOTHER — they talk through
# ⭐   flagship.contracts only. ⭐⭐ THIS IS THE SERVICE BOUNDARY,
# ⭐   ENFORCED BEFORE THE SERVICES EXIST.
```

```
⭐ AND THE THREE SUPPORTING CONVENTIONS:
⭐   ⭐ `_internal` sub-packages for anything not part of the
⭐     module's contract.
⭐   ⭐ An explicit `contracts` package holding the DTOs and
⭐     events each context publishes — ⭐⭐ WHICH BECOMES YOUR
⭐     PROTO FILES OR EVENT SCHEMAS VERBATIM ON THE DAY YOU
⭐     EXTRACT (DAY 400, DAY 405).
⭐   ⭐⭐ ONE MODULE OWNS ITS TABLES. ⭐ Enforce it with a
⭐     lint rule on model imports, ⭐ or with separate
⭐     schemas and separate database roles — ⭐⭐ WHICH IS THE
⭐     VERSION THAT ACTUALLY HOLDS, BECAUSE POSTGRES ENFORCES IT
⭐     AND POSTGRES DOES NOT GET TIRED AT 6 P.M.
```

# Part 6 — The distributed monolith checklist

```
⭐⭐ SEVEN SYMPTOMS. ***THREE OR MORE AND YOU HAVE ONE.***
⭐ ☐ ① Releases must go out in a specific order.
⭐ ☐ ② A shared database, ⭐⭐ OR TWO SERVICES WRITING ONE TABLE.
⭐ ☐ ③ A shared library that every service must upgrade in
⭐      lockstep. ⭐⭐ (A UTILITY LIBRARY IS FINE. A SHARED
⭐      ***DOMAIN MODEL*** IS THE COUPLING.)
⭐ ☐ ④ A change to one service routinely requires a change to
⭐      another in the same PR. ⭐⭐ CHECK `git log`.
⭐ ☐ ⑤ You cannot run one service locally without running six.
⭐ ☐ ⑥ ⭐⭐ ONE SERVICE BEING DOWN TAKES EVERYTHING DOWN.
⭐ ☐ ⑦ There is an integration environment that must be booked.

⭐⭐ ⇒ AND THE HONEST CONCLUSION IF YOU TICK FOUR: ***YOU HAVE
⭐   PAID EVERY COST OF MICROSERVICES AND BOUGHT NONE OF THE
⭐   BENEFITS.*** ⭐ The right move is usually to ***merge***
⭐   services back, ⭐⭐ WHICH IS A LEGITIMATE AND UNDER-USED
⭐   ARCHITECTURAL DECISION, ⭐ and one that is much easier to
⭐   defend than people expect.
```

# 💬 Interview

**1. ⭐⭐ "How do you decide service boundaries?"**
> ⭐ By invariants, not by nouns. ⭐⭐ **The question is what data must be transactionally consistent
> with what, because that set can't be split without turning a transaction into a saga** — so the
> invariants draw the lines and everything else is preference. ⭐ The two axes people reach for both
> fail: ⭐⭐ **by layer means every feature touches all three services, so you've distributed your
> function call stack; by entity means every real operation is a cross-service join the database used
> to do for free and better.** ⭐ Then I'd apply four tests: deployment independence — ⭐⭐ **and the
> evidence is `git log`, not an opinion: if commits routinely touch both repos in one PR, they're one
> service pretending to be two** — one writer per table, failure isolation, and team ownership.

**2. ⭐⭐ "Synchronous or asynchronous?"**
> ⭐ It's an availability decision, and the arithmetic settles it. ⭐⭐ **A synchronous chain of five
> services at 99.9% each is 99.5%, which is 3.6 hours a month — every synchronous dependency
> multiplies your downtime and every asynchronous one doesn't.** ⭐ An async dependency being down
> means work queues; a sync one being down means you are down. ⭐ So: ⭐⭐ **synchronous when you need
> the answer to respond, asynchronous when you need the work done.** ⭐ "Is this card valid" is sync;
> "send the receipt" and "update the search index" are async. ⭐⭐ **And the one-question version is: is
> this a query or a command? A command being synchronous is a choice you should have to justify.**

**3. "Monolith or microservices for a new product?"**
> ⭐ Modular monolith, and not as a compromise. ⭐⭐ **Extracting a service from a well-modularised
> monolith is a week; extracting one from a ball of mud is a year — so the modularisation is the work
> and the extraction is the easy part you may never need.** ⭐ Monolith-first is simultaneously the
> cheapest path to microservices and the cheapest path to not needing them. ⭐ I'd extract when there's
> a reason from a short list: ⭐⭐ **different scaling profile, different team with a demonstrable
> coordination cost, different runtime, different compliance boundary, or a different release cadence
> I can point at. "It would be cleaner" isn't on the list.**

**4. ⭐⭐ "How do you enforce module boundaries in Python?"**
> ⭐ With a tool, because Python has no package-private and any module can import any other — ⭐⭐ **so a
> boundary that's only a convention gets violated within a month by someone in a hurry at six
> o'clock.** ⭐ I use `import-linter` in CI with two kinds of contract: a layers contract so the domain
> can't import the web layer, and an independence contract so bounded contexts can't import each
> other, only a shared `contracts` package. ⭐⭐ **That `contracts` package becomes your proto files or
> event schemas verbatim on the day you extract.** ⭐ And for data ownership I'd go further than lint:
> ⭐⭐ **separate schemas and separate database roles, because Postgres enforces it and Postgres doesn't
> get tired at six o'clock.**

**5. "How do you know you've built a distributed monolith?"**
> ⭐ Seven symptoms, and three is enough: releases must go out in order; a shared database or two
> writers on one table; a shared domain library upgraded in lockstep; changes routinely spanning repos
> in one PR; you can't run one service without six; ⭐⭐ **one service being down takes everything
> down**; and a bookable integration environment. ⭐⭐ **If you tick four, you've paid every cost of
> microservices and bought none of the benefits — and the right move is usually to merge services back
> together**, which is a legitimate and under-used decision.

**6. "What's the worst decomposition mistake?"**
> ⭐⭐ **Two services writing the same table.** ⭐ It's the single worst marker, because now neither can
> change the schema and both must deploy together forever — ⭐⭐ **you have all the operational cost of
> two services and the coupling of one**, and it's usually invisible on the architecture diagram
> because the diagram draws the services, not the writes.

## 🎙️ Articulation drill

**Two minutes.** Open on the axis: **the unit of decomposition is the set of things that must change
together and stay consistent together — so the question is what data must be transactionally
consistent with what, because that set can't be split without turning a transaction into a saga.**
Dispose of the two wrong axes fast: **by layer distributes your function call stack and puts a network
between the frames; by entity turns every operation into a cross-service join the database did for
free and better.** Then the tests, leading with the one that has evidence: **can you deploy alone —
and `git log` answers that, not an opinion. One writer per table, always. If this service is down what
still works, because if the answer is nothing you've bought latency and failure modes and no
isolation.** Then the arithmetic that settles sync versus async: **five synchronous services at 99.9%
each is 99.5%, which is 3.6 hours a month — every synchronous dependency multiplies your downtime and
every asynchronous one doesn't. So: sync when you need the answer to respond, async when you need the
work done.** Close on sequencing and on Python: **extracting a service from a well-modularised
monolith is a week; from a ball of mud it's a year — so the modularisation is the work, which makes
monolith-first the cheapest path to microservices and to not needing them. And in Python that
modularisation has to be enforced by `import-linter` in CI plus separate database schemas, because
Python has no package-private and a convention gets violated within a month.**
