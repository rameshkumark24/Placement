# Day 454 🗃️

**P-454** · 🗃️ **Caching** — ⭐⭐ four layers, four keys, and one that quietly serves wrong answers

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: three of the four caching layers are ordinary engineering with ordinary
> keys, and the fourth — semantic caching — decides that two different questions are the same question,
> which means its failure mode is not a stale answer but a confidently wrong one that no error rate will
> ever show you.**

---

# Part 1 — The four layers, ranked by return

```
⭐ ① ⭐⭐ ***PROVIDER PROMPT CACHE*** (Day 415)
⭐   ⭐ KEY: ***the byte-exact prefix***. Server-side. ~5min TTL.
⭐   ⭐ SAVES: ~90% on cached input tokens.
⭐   ⭐ HIT RATE: ⭐⭐ VERY HIGH IF YOU ORDER THE PROMPT
⭐     CORRECTLY — stable content first, variable last.
⭐   ⭐ ⭐⭐ THE BIGGEST WIN IN THE WHOLE DAY, AND IT IS NOT A
⭐     CACHE YOU BUILD — ⭐ it is a cache you ***enable by
⭐     ordering***, which is why it gets skipped.

⭐ ② ***COMPONENT CACHES*** — ⭐ embeddings by content hash
⭐   (Day 431), rerank scores, tool results, retrieval results.
⭐   ⭐ KEY: content hash + model version.
⭐   ⭐ ⭐⭐ BORING, EXACT, HIGH HIT RATE, ZERO CORRECTNESS RISK.
⭐     ⭐ Do these before anything clever.

⭐ ③ ***EXACT-MATCH RESPONSE CACHE***
⭐   ⭐ KEY: `hash(config_hash + messages + tenant + principals)`
⭐   ⭐ HIT RATE: ⭐ near zero for open chat; ⭐⭐ 30–70% FOR
⭐     BATCH EXTRACTION, CLASSIFICATION AND ROUTING PIPELINES,
⭐     ⭐ where the same input genuinely recurs.
⭐   ⭐ ⭐⭐ SAFE, BECAUSE IDENTICAL INPUT MEANS IDENTICAL INPUT.

⭐ ④ ⭐⭐ ***SEMANTIC CACHE*** — ⭐ embed the query, serve a
⭐   previous answer if similarity > threshold.
⭐   ⭐ HIT RATE: ⭐ genuinely high.
⭐   ⭐ ⭐⭐ AND IT IS THE ONLY LAYER THAT CAN RETURN A ***WRONG
⭐     ANSWER***. ⭐ Part 3.

⭐ ⭐⭐ THE ORDER MATTERS: ⭐ ① and ② are free and safe and most
⭐   teams skip straight to ④ because it demos as "90% cheaper".
```

# Part 2 — ⭐⭐ The cache key is a security boundary

```
⭐ ***STAGE 11 SAID THIS ABOUT CDNs. DAY 434 SAID IT ABOUT
⭐   RETRIEVAL. IT IS MOST DANGEROUS HERE.***

⭐ ***THE BUG:*** ⭐ cache on question text alone.
⭐   ⭐ User A (finance) asks "what's our Q3 margin?" → answered
⭐     from finance documents, cached.
⭐   ⭐ User B (intern) asks the same words → ⭐⭐ SERVED
⭐     INSTANTLY, FROM CACHE, WITH ***NO RETRIEVAL RUNNING AT
⭐     ALL***.
⭐   ⭐ ⭐⭐ SO YOUR PERFECT PERMISSION FILTER IS BYPASSED — NOT
⭐     DEFEATED, ***BYPASSED*** — BECAUSE THE CODE PATH
⭐     CONTAINING IT NEVER EXECUTED. ⭐ No error, no log line, no
⭐     latency signal. ⭐ It looks like a cache ***win***.

⭐ ⇒ ***THE KEY MUST CONTAIN, EVERY TIME:***
⭐   ⭐ `tenant_id`
⭐   ⭐ ⭐⭐ A HASH OF THE PRINCIPAL SET ⭐ (the user's groups)
⭐   ⭐ `config_hash` — prompt version + schema + model +
⭐     temperature + retrieval params (Day 427)
⭐   ⭐ the index version (Day 431)

⭐ ⭐⭐ AND ACCEPT WHAT THAT COSTS: ⭐ per-principal keys mean a
⭐   much lower hit rate. ⭐⭐ THAT IS A PRICE, NOT A BUG TO
⭐   OPTIMISE AWAY. ⭐ A shared answer cache with a global key is
⭐   a data-leak machine with excellent metrics.

⭐ ***THE FREE BONUS:*** ⭐ `config_hash` in the key gives you
⭐   ***invalidation for nothing*** — ⭐⭐ CHANGE THE PROMPT AND
⭐   EVERY STALE ANSWER BECOMES UNREACHABLE INSTANTLY, ⭐ with no
⭐   purge job to write or get wrong.
```

# Part 3 — ⭐⭐ Why semantic caching is dangerous

```
⭐ ***IT ASSERTS THAT TWO DIFFERENT STRINGS ARE THE SAME
⭐   QUESTION. ⭐⭐ DAY 419 ALREADY TOLD YOU EMBEDDINGS ARE BAD AT
⭐   EXACTLY THE DISTINCTIONS THAT MATTER.***

⭐ ⭐⭐ ALL OF THESE PAIRS SIT ABOVE 0.95 COSINE SIMILARITY AND
⭐   HAVE ***DIFFERENT CORRECT ANSWERS***:
⭐   ⭐ "How do I cancel my subscription?"
⭐     vs "How do I cancel my subscription ***renewal***?"
⭐   ⭐ "Is the API rate limit 100 or 1000?"
⭐     vs "Is the API rate limit 1000 or 10000?"
⭐   ⭐ ⭐⭐ "CAN I EXPENSE THIS?" vs "CAN I ***NOT*** EXPENSE
⭐     THIS?" ⭐ — negation is nearly invisible to an embedding.
⭐   ⭐ ⭐⭐ "STATUS OF INVOICE 4471" vs "STATUS OF INVOICE 4472"
⭐     ⭐ — identifiers barely move the vector (Day 433).
⭐   ⭐ "What's the refund policy?" asked in ***March*** vs
⭐     ***November*** — ⭐ same words, the policy changed.

⭐ ⇒ ***THE FAILURE MODE:*** ⭐⭐ NOT A STALE ANSWER. A ***WRONG
⭐   ANSWER, SERVED FASTER AND MORE CONFIDENTLY THAN A CORRECT
⭐   ONE, WITH NO ERROR ANYWHERE.*** ⭐ And the cheaper and
⭐   faster it gets, the better your dashboards look.

⭐ ***HOW TO USE IT WITHOUT LOSING:***
⭐   ⭐ ① ⭐⭐ TUNE THE THRESHOLD AGAINST AN EVAL SET, NOT BY
⭐     INTUITION. ⭐ Build pairs that ***should*** hit and pairs
⭐     that ***must not*** — ⭐⭐ THE SECOND SET IS DAY 448'S
⭐     "BENIGN-BUT-SIMILAR" BUCKET AND IT IS THE ONLY THING THAT
⭐     TELLS YOU YOUR THRESHOLD.
⭐   ⭐ ② ***NORMALISE FIRST*** — lowercase, strip punctuation,
⭐     and ⭐⭐ EXTRACT IDENTIFIERS AND NUMBERS INTO THE KEY
⭐     ***EXACTLY***. ⭐ "invoice 4471" and "invoice 4472" then
⭐     cannot collide, ⭐⭐ WHICH REMOVES THE ENTIRE WORST
⭐     CATEGORY FOR ABOUT TEN LINES OF CODE.
⭐   ⭐ ③ ***SCOPE IT TO STABLE, LOW-STAKES, HIGH-VOLUME
⭐     QUESTIONS*** — ⭐ FAQ and policy lookups. ⭐⭐ NEVER
⭐     ACCOUNT-SPECIFIC, NEVER NUMERIC, NEVER TRANSACTIONAL.
⭐   ⭐ ④ ***SHORT TTLs*** — hours, not weeks.
⭐   ⭐ ⑤ ⭐⭐ CONSIDER SERVING IT AS A ***SUGGESTION***: ⭐ "others
⭐     asked something similar — is this what you meant?"
⭐     ⭐⭐ ALL OF THE SAVING, NONE OF THE FALSE-CONFIDENCE RISK.
```

# Part 4 — Invalidation, which is the part with no error message

```
⭐ ***THE DOCUMENT CHANGES. THE CACHED ANSWER DOES NOT.***
⭐   ⭐⭐ NOTHING ERRORS. NOTHING ALERTS. ⭐ Your users are simply
⭐     told last month's policy, quickly.

⭐ ***FOUR MECHANISMS, WEAKEST TO STRONGEST:***
⭐   ⭐ ① ***TTL*** — ⭐ crude and honest. ⭐⭐ CHOOSE IT FROM HOW
⭐     FAST THE UNDERLYING CONTENT CHANGES, NOT FROM YOUR
⭐     DESIRED HIT RATE. ⭐ Writing that sentence down forces the
⭐     right conversation.
⭐   ⭐ ② ***VERSIONED KEYS*** — ⭐ `config_hash` and index
⭐     version in the key. ⭐⭐ FREE, INSTANT, TOTAL. ⭐ Covers
⭐     every prompt, model and pipeline change.
⭐   ⭐ ③ ⭐⭐ ***DOC-ID TAGGING*** — ⭐ record which `doc_id`s
⭐     produced each cached answer ⭐ (you already log them for
⭐     the Day 434 audit trail, ⭐⭐ SO THIS IS FREE), ⭐ and evict
⭐     by tag when a document changes.
⭐   ⭐ ④ ***EVENT-DRIVEN*** — ⭐ ingestion emits a
⭐     `document.updated` event through the outbox (Day 407);
⭐     the cache subscribes and evicts by tag.
⭐     ⭐⭐ CORRECT, AND IT IS A REAL DISTRIBUTED-SYSTEMS
⭐     COMPONENT — DO NOT BUILD IT UNTIL ② AND ③ ARE NOT ENOUGH.

⭐ ***AND THE THING THAT MAKES TTLs DEFENSIBLE:***
⭐   ⭐ ⭐⭐ `stale-if-error` (STAGE 11). ⭐ A stale answer served
⭐     during a provider outage, ***clearly labelled with its
⭐     age***, is far better than an error page. ⭐ It converts
⭐     your cache into a fallback tier (Day 456).
```

# Part 5 — The two metrics nobody has

```
⭐ ***EVERYONE REPORTS HIT RATE. IT IS THE LEAST USEFUL OF THE
⭐   THREE.***

⭐ ① ***HIT RATE*** — ⭐ the cost story. ⭐ Fine.
⭐ ② ⭐⭐ ***FALSE-HIT RATE*** — ⭐ of semantic hits, what fraction
⭐   returned an answer that was ***wrong for the new
⭐   question***?
⭐   ⭐ MEASURE IT: ⭐⭐ SHADOW-RUN A SAMPLE OF HITS — ⭐ serve the
⭐     cached answer, ***also*** generate fresh in the
⭐     background, ⭐⭐ AND COMPARE. ⭐ 1% of traffic is enough,
⭐     and it costs almost nothing.
⭐   ⭐ ⭐⭐ THIS IS THE NUMBER THAT TELLS YOU WHETHER YOUR
⭐     THRESHOLD IS SANE, AND ALMOST NO ONE COLLECTS IT.
⭐ ③ ⭐⭐ ***STALENESS RATE*** — ⭐ of hits, what fraction was
⭐   produced before the underlying document last changed?
⭐   ⭐ ⭐⭐ COMPUTABLE EXACTLY FROM THE doc_id TAGS AND
⭐     `updated_at`. ⭐ No sampling, no judgement, no cost.

⭐ ***THE COST ARITHMETIC, TO KEEP IT HONEST:***
⭐   ⭐ 100k requests/day at $0.012 = ⭐ $1,200/day
⭐   ⭐ prompt caching alone (layer ①): ⭐⭐ −40–60%
⭐   ⭐ component caches (②): −10%
⭐   ⭐ exact match at 20% (③): −20% of what remains
⭐   ⭐ semantic at 30% (④): ⭐ −30% more…
⭐   ⭐ ⭐⭐ …AT A FALSE-HIT RATE YOU HAVE NOT MEASURED. ⭐ Layer ④
⭐     is the smallest saving and the only correctness risk, ⭐⭐
⭐     WHICH IS THE ENTIRE ARGUMENT OF THIS DAY.
```

# 💬 Interview

**1. "How do you cache an LLM feature?"**

⭐ Four layers with four different keys, and I'd do them in return order rather than in the order they
sound clever. ⭐⭐ First the provider's prompt cache, which isn't a cache I build — it's one I enable by
ordering the prompt stable-content-first, and it's a ninety percent discount on repeated input tokens.
⭐ Then component caches: embeddings by content hash, rerank scores, tool results — boring, exact, high
hit rate, zero correctness risk. ⭐ Then an exact-match response cache, which is near-useless for open
chat and thirty to seventy percent for extraction and classification pipelines where the same input
genuinely recurs. ⭐⭐ And only then semantic caching, which is the smallest saving and the only layer
that can return a wrong answer.

**2. "What has to be in the cache key?"**

⭐ Tenant, a hash of the user's principal set, the config hash, and the index version. ⭐⭐ The security
part is the one people miss: if you cache on question text alone, user B asks the same words as user A
and gets served instantly from cache with **no retrieval running at all** — so the permission filter
isn't defeated, it's bypassed, because the code path containing it never executed. ⭐ No error, no log
line, no latency signal; it looks like a cache win. ⭐⭐ Per-principal keys tank the hit rate, and that's
a price rather than a bug to optimise away. ⭐ The config hash is a free bonus: change the prompt and
every stale answer becomes unreachable instantly, with no purge job to write or get wrong.

**3. "What's wrong with semantic caching?"**

⭐ It asserts that two different strings are the same question, using embeddings — which are specifically
bad at the distinctions that matter. ⭐⭐ "How do I cancel my subscription" and "how do I cancel my
subscription renewal" are above 0.95 similarity with different answers. Negation is nearly invisible, so
"can I expense this" and "can I *not* expense this" collide. Identifiers barely move the vector, so
invoice 4471 and 4472 are the same query. ⭐ And the same words asked in March and November hit
different versions of a policy. ⭐⭐ So the failure mode isn't a stale answer, it's a wrong answer served
faster and more confidently than a correct one, with no error anywhere — and the better it performs, the
better your dashboards look.

**4. "Would you use it anyway?"**

⭐ Narrowly, and with two changes. ⭐⭐ First, normalise and extract identifiers and numbers into the key
**exactly**, so "invoice 4471" and "invoice 4472" can't collide — that's about ten lines and it removes
the worst category outright. ⭐ Second, tune the threshold against an eval set with pairs that *should*
hit and pairs that *must not*, which is the same benign-but-similar bucket I build for guardrails.
⭐ Then scope it to stable, low-stakes, high-volume questions — FAQ and policy lookups, never
account-specific, never numeric, never transactional — with short TTLs. ⭐⭐ And the option I'd push
hardest: serve it as a *suggestion* rather than an answer — "others asked something similar, is this
what you meant?" ⭐ All of the saving, none of the false-confidence risk.

**5. "How do you invalidate?"**

⭐ Four mechanisms and I'd stop as early as I could. ⭐ TTL, chosen from how fast the underlying content
changes rather than from the hit rate I'd like — writing that sentence down forces the right
conversation. ⭐⭐ Versioned keys, which are free and total for any prompt, model or pipeline change.
⭐ Doc-id tagging, where I record which documents produced each answer and evict by tag — and that's free
for me because I already log retrieved doc ids for the audit trail. ⭐⭐ And event-driven eviction
through the outbox, which is correct and is a real distributed-systems component, so I wouldn't build it
until tagging wasn't enough. ⭐ I'd also add `stale-if-error`, which turns the cache into a fallback tier
during a provider outage — a stale answer clearly labelled with its age beats an error page.

**6. "What do you measure?"**

⭐ Three things, and hit rate is the least useful. ⭐⭐ False-hit rate: of semantic hits, what fraction
returned an answer wrong for the new question — measured by shadow-running one percent of hits, serving
the cached answer while generating fresh in the background and comparing. ⭐ That's the number that
tells you whether the threshold is sane, and almost nobody collects it. ⭐⭐ And staleness rate: of hits,
what fraction was produced before the underlying document last changed — computable exactly from doc-id
tags and timestamps, no sampling and no judgement. ⭐ Hit rate only tells me the cost story, and the cost
story is the one thing that was never in doubt.

## 🎙️ Articulation drill

⭐⭐ **Two minutes, out loud: "how do you cache this?"**

Start by splitting the word, because four things are hiding inside it. **There are four layers with four
different keys. The provider's prompt cache, which I don't build — I enable it by ordering the prompt
stable-first, and it's a ninety percent discount on repeated input. Component caches for embeddings,
rerank scores and tool results, keyed by content hash: boring, exact, no correctness risk. An
exact-match response cache, near-useless for chat and thirty to seventy percent for extraction
pipelines. And semantic caching, which is the smallest saving and the only one that can return a wrong
answer. Most teams skip straight to the fourth because it demos as ninety percent cheaper.**

Then the security point, because it's the one that ends careers. **The cache key is a security boundary.
If I key on question text alone, a second user asks the same words and gets served instantly with no
retrieval running at all — so the permission filter isn't defeated, it's bypassed, because the code path
containing it never executed. No error, no log line, and it looks like a cache win. So the key carries
tenant, a hash of the principal set, the config hash and the index version. That tanks the hit rate, and
that's a price, not a bug.**

Then why semantic caching earns its warning. **It asserts two different strings are the same question,
using embeddings — which are specifically bad at exactly those distinctions. "Cancel my subscription"
and "cancel my subscription renewal" are above 0.95 with different answers. Negation is invisible.
Invoice 4471 and 4472 are the same vector. So the failure mode isn't staleness, it's a wrong answer
served faster and more confidently than a correct one, with nothing erroring — and the better it
performs, the better the dashboard looks. I'd use it narrowly: extract identifiers and numbers into the
key exactly, tune the threshold against pairs that must *not* collide, scope it to stable low-stakes
questions, and seriously consider serving the hit as a suggestion rather than an answer.**

Close on measurement. **Everyone reports hit rate, which is the least useful of the three. False-hit
rate — of semantic hits, how many were wrong for the new question — I get by shadow-running one percent
of hits and comparing against a fresh generation. Staleness rate — how many hits predate the last change
to their source documents — is exactly computable from doc-id tags, which I already have because I log
retrieved doc ids for the audit trail. Hit rate only tells me the cost story, and the cost story was
never the thing in doubt.**
