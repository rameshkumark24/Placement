# Part 1 — ⭐ `int` — arbitrary precision

```python
2 ** 1000                    # ⭐⭐ exact. No overflow. Ever.
import sys; sys.getsizeof(2**1000)     # ⭐ 160 bytes — it GREW (Day 023)
```

```
⭐⭐ WHAT THIS REMOVES: an entire category of problem.
⭐   · no int overflow, no "use a long", no wraparound bugs
⭐   · factorials, fibonacci, cryptographic maths — all exact, no special library
⭐ ⇒ ⭐⭐ SAY THIS IN A DSA ROUND when a problem is clearly testing for overflow.
⭐      "In Python integers are arbitrary precision, so the overflow case the problem is
⭐       probing for doesn't exist — in C I'd need a 64-bit check here."
⭐
⭐ ⚠️ ⭐ THE COST: big ints are SLOWER (schoolbook multiplication above a threshold), and
⭐   Python 3.11+ LIMITS int↔str conversion to 4300 digits by default — because converting
⭐   a huge int to a string is QUADRATIC and was a real DoS vector.
```

⭐ **Integer division has a sign rule people get wrong:**

```python
7 // 2      # 3
-7 // 2     # ⭐⭐ -4  — floor division rounds toward NEGATIVE INFINITY, not toward zero
int(-7/2)   # ⭐ -3  — int() TRUNCATES toward zero
-7 % 2      # ⭐⭐ 1   — the result takes the sign of the DIVISOR (unlike C, where it is -1)
divmod(-7, 2)   # (-4, 1)
```

⭐⭐ **`%` following the divisor's sign is genuinely useful:** `i % n` is always in `[0, n)`, so
circular-buffer and grid-wrapping indices need no correction — **the C idiom `((i % n) + n) % n` is
unnecessary in Python.** ⚠️ But it means a port of C code will differ on negative operands.

# Part 2 — ⭐⭐ Floats, and why `0.1 + 0.2` is not `0.3`

```python
0.1 + 0.2            # ⭐⭐ 0.30000000000000004
0.1 + 0.2 == 0.3     # ⭐⭐ False
from decimal import Decimal
Decimal(0.1)         # ⭐⭐ 0.1000000000000000055511151231257827021181583404541015625
```

```
⭐⭐ WHY: a float is IEEE-754 binary64 — sign, 11-bit exponent, 52-bit mantissa.
⭐   ⇒ it stores  m × 2^e.  ⭐⭐ 0.1 IS NOT REPRESENTABLE as any finite binary fraction,
⭐     exactly as 1/3 is not representable as a finite DECIMAL fraction.
⭐   ⇒ so 0.1 becomes the nearest binary64 value, which is very slightly more than 0.1.
⭐   ⇒ ⭐⭐ THE ERROR IS IN THE LITERAL, not in the addition. The addition was correct.
⭐
⭐ ⭐⭐ ~15–17 significant decimal digits. Anything beyond that is noise.
```

⭐⭐ **"The error is in the literal" is the sentence that shows understanding** — most people describe
this as "floating-point addition is inaccurate", which misplaces the fault.

```python
# ⭐ COMPARING FLOATS:
a == b                                    # ⚠️ ⭐⭐ almost always wrong
import math
math.isclose(a, b, rel_tol=1e-9)          # ⭐⭐ relative — the right default
math.isclose(a, 0.0, abs_tol=1e-12)       # ⭐ near zero you NEED abs_tol; rel_tol is useless there
```

```python
# ⭐ Other float behaviour worth knowing:
float("nan") == float("nan")   # ⭐⭐ False — NaN is not equal to ITSELF (IEEE-754 says so)
math.isnan(x)                  # ⭐ the only correct test
[float("nan")].__contains__(float("nan"))   # ⭐ True — `in` checks identity first!
math.inf; -math.inf; 1/0       # ⭐ ZeroDivisionError — Python raises rather than giving inf
round(2.5)                     # ⭐⭐ 2 — BANKER'S ROUNDING (round-half-to-EVEN)
round(3.5)                     # ⭐⭐ 4
sum([0.1]*10)                  # ⭐ 0.9999999999999999
math.fsum([0.1]*10)            # ⭐⭐ 1.0 — exact summation, worth it for long float sums
```

⚠️ ⭐⭐ **Banker's rounding surprises everyone once.** `round(0.5)` is `0`, `round(1.5)` is `2`. It is
deliberate — always rounding half up biases sums upward over many values — but it is **not** what a
finance spec usually says, so **specify the rounding mode explicitly with `Decimal` when it
matters.**

⭐ **The NaN-in-a-list result is a nice detail:** `in` and `==` on containers compare identity before
equality (Day 029's fast path), so a NaN *is* found in a list containing that same NaN object, while
`nan == nan` is False. **Two reasonable rules producing a contradictory-looking result.**

# Part 3 — ⭐⭐ `Decimal` — and the money rule

```python
from decimal import Decimal, getcontext, ROUND_HALF_UP

Decimal("0.1") + Decimal("0.2") == Decimal("0.3")     # ⭐⭐ True
Decimal(0.1)                                          # ⚠️ ⭐⭐ WRONG — the float error is already in
Decimal("0.1")                                        # ⭐⭐ RIGHT — construct from a STRING
```

```
⭐⭐ THE MONEY RULE, and the reason for it:
⭐   money is DECIMAL by definition — the rules are written in decimal, so representation
⭐   error is not a rounding detail, it is a WRONG NUMBER in an audit.
⭐   ⇒ ⭐⭐ over a million transactions, float error accumulates into a real discrepancy
⭐        that someone has to reconcile, and cannot.
⭐
⭐ ⭐⭐ TWO ACCEPTABLE ANSWERS, AND ONE WRONG ONE:
⭐   ✓ ⭐ Decimal, with an explicit context and rounding mode
⭐   ✓ ⭐⭐ INTEGER MINOR UNITS — store cents as an int. Simple, exact, fast, and it
⭐        serialises to JSON without argument. ⭐ Many payment systems do exactly this.
⭐   ✗ ⭐⭐ float. Ever. For anything a human will reconcile.
```

```python
getcontext().prec = 28
getcontext().rounding = ROUND_HALF_UP           # ⭐⭐ NOT the default — the default is HALF_EVEN
price = Decimal("19.99")
(price * 3).quantize(Decimal("0.01"))           # ⭐⭐ quantize = round to a fixed number of places
```

| ⭐ Concern | ⭐ Note |
|---|---|
| Speed | ⭐ `Decimal` is ~10–100× slower than float — irrelevant for transactions, fatal in a tight numeric loop |
| ⭐⭐ Database | ⭐⭐ `NUMERIC`/`DECIMAL`, never `FLOAT` — SQLAlchemy maps `Numeric` to `Decimal` |
| ⭐⭐ JSON | ⚠️ ⭐⭐ **JSON has no decimal type** — `json.dumps(Decimal)` raises; serialise as a **string**, or as integer minor units. Never as a float |
| Mixing | ⭐ `Decimal + float` raises `TypeError` — deliberately |
| Pydantic | ⭐ supports `Decimal` with `max_digits`/`decimal_places` |

⚠️ ⭐⭐ **The JSON boundary is where most Decimal discipline is lost.** A service that keeps `Decimal`
internally and emits `19.99` as a JSON float has handed the problem to every consumer. **Emit
`"19.99"` as a string, or `1999` with a stated currency and exponent.**

```python
from fractions import Fraction
Fraction(1, 3) + Fraction(1, 6)      # ⭐ Fraction(1, 2) — EXACT rational arithmetic
Fraction("0.1")                       # Fraction(1, 10)
```

⭐ **`Fraction` is exact for ratios** and the right tool for probability, unit conversion, or anything
where repeated division must not drift — **but denominators grow, so it is not for long
accumulations.**

# Part 4 — ⭐ Choosing

| ⭐ You have | ⭐⭐ Use |
|---|---|
| Counting, indexing, IDs | ⭐ `int` |
| ⭐⭐ **Money, tax, invoices** | ⭐⭐ **`Decimal` or integer minor units** |
| Measurements, science, ML | ⭐ `float` — the error is smaller than your measurement error |
| Exact ratios | `Fraction` |
| Millions of numbers, arithmetic in bulk | ⭐ NumPy (`float64`) — Days 028, 039 |
| Bit manipulation | `int` — `&`, `\|`, `^`, `<<`, `>>`, `bit_count()` |

```python
# ⭐ Bit operations, for the DSA track:
x & 1              # ⭐ odd?
x >> 1             # ⭐ halve (floor)
x & (x - 1)        # ⭐⭐ clears the lowest set bit — the Brian Kernighan popcount trick
x & -x             # ⭐ isolates the lowest set bit
bin(x); x.bit_length(); x.bit_count()      # ⭐ 3.10+
```

⭐⭐ **`float` is not "wrong" — it is right for measurements.** A sensor reading has more error in the
sensor than in the float. **The rule is about *exactness by definition*: money, counts and identifiers
are defined exactly, and measurements are not.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Floats for money** | ⭐⭐ `Decimal` or integer minor units. |
| ⭐⭐ **`Decimal(0.1)`** | ⭐⭐ The float error is already baked in. `Decimal("0.1")`. |
| `a == b` on floats | ⭐ `math.isclose`, with `abs_tol` near zero. |
| ⭐ Saying "float addition is inaccurate" | ⭐⭐ The error is in the literal; the addition was exact. |
| Expecting `round(2.5) == 3` | ⭐ Banker's rounding. Specify the mode with `Decimal`. |
| `x == float("nan")` | ⭐⭐ NaN is unequal to itself. `math.isnan`. |
| ⭐ Serialising `Decimal` as a JSON float | ⭐⭐ Use a string, or integer minor units. |
| `FLOAT` column for currency | ⭐ `NUMERIC`/`DECIMAL`. |
| `int(-7/2)` where `-7 // 2` was meant | ⭐ Truncation vs floor — they differ on negatives. |
| Porting `((i % n) + n) % n` from C | ⭐ Unnecessary — Python's `%` follows the divisor. |
| `sum()` on many floats | ⭐ `math.fsum` when accuracy matters. |
| `Decimal` in a tight numeric loop | ⭐ 10–100× slower. Use float or NumPy there. |

## Interview questions

**Q: Why is `0.1 + 0.2 != 0.3`?**
> Because floats are IEEE-754 binary, and 0.1 has no finite binary representation — exactly as one
> third has no finite decimal representation. So the literal `0.1` is already the nearest binary64
> value, slightly above 0.1, and the same for 0.2. The addition is performed exactly on those stored
> values; the discrepancy was in the literals, not the arithmetic. That distinction matters, because
> it tells you no amount of careful adding will fix it — you have to change the representation.

**Q: How do you store money?**
> `Decimal`, or integers in minor units — cents — never a float. Money is defined in decimal, so
> binary representation error isn't a rounding nuisance, it's a wrong number in a ledger, and it
> accumulates across transactions into something a human has to reconcile and can't. With `Decimal`
> I'd set the rounding mode explicitly rather than relying on the default, which is half-even.
> Integer minor units are the simpler answer where it fits: exact, fast, and unambiguous over JSON.
> And in the database it's `NUMERIC`, never `FLOAT`.

**Q: What's the trap at the JSON boundary?**
> JSON has no decimal type. `json.dumps` refuses a `Decimal` outright, and the tempting fix is
> `float(d)`, which throws away the exactness you were protecting and hands the problem to every
> consumer. The right options are to emit the value as a string — `"19.99"` — or as an integer minor
> unit with a stated currency and exponent. It's the point where most Decimal discipline in a
> codebase quietly leaks away.

**Q: Anything surprising about `round`?**
> It's banker's rounding — half to even — so `round(0.5)` is 0 and `round(1.5)` is 2. That's
> statistically better because always rounding half up biases sums upward, but it's usually not what a
> finance specification says. When the rounding rule is part of the requirements I'd use
> `Decimal.quantize` with an explicit mode rather than the built-in.

**Q: What does arbitrary-precision `int` give you, and does it cost anything?**
> Exactness with no overflow, which removes a whole category of problem — no wraparound bugs, no
> needing a bignum library for factorials or cryptographic maths. It's worth naming in a coding round
> when the problem is clearly probing for overflow, because in C that check would be required. The
> cost is speed on very large values, and Python 3.11 added a 4300-digit limit on int-to-string
> conversion, because that conversion is quadratic and was being used as a denial-of-service vector.

**Q: `-7 // 2` and `-7 % 2`?**
> `-4` and `1`. Floor division rounds toward negative infinity rather than toward zero, and the
> modulus takes the sign of the divisor, so `i % n` is always in `[0, n)`. That's genuinely useful —
> circular indices need no correction, unlike C where you write `((i % n) + n) % n`. It's also the
> thing to check first when porting numeric code from C, since the two languages disagree on
> negatives.
