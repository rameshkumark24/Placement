# Day 158

**L-158** · **Webhooks** — signing, replay, ⭐⭐ and delivering to endpoints that lie to you

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a webhook is an HTTP request you make to a server you do not control,
> operated by someone who will point their URL at localhost, return 200 before doing the work, and
> then ask why they missed an event — so the whole design is about surviving a receiver you cannot
> fix.**
>
> ⭐ Day 142 built durable background work, Day 122 built idempotency, Day 152 built retries.
> ⭐⭐ A webhook is those three things pointed at a stranger, plus two problems they do not have:
> **authenticating a message rather than a caller, and being the source of a request you did not
> initiate.**

# Part 1 — ⭐⭐ Sending: the delivery pipeline

```
⭐⭐ THE NAIVE VERSION, AND EVERY WAY IT FAILS:

⭐   def order_placed(order):
⭐       db.commit()
⭐       httpx.post(customer.webhook_url, json=payload)     # ⭐⭐ four bugs
⭐
⭐   1. ⭐⭐ IN THE REQUEST PATH. Their slow endpoint is now YOUR latency, and
⭐        their outage is your outage (Day 152's cascade).
⭐   2. ⭐ NO RETRY. A 500 on their side means the event is gone forever.
⭐   3. ⭐⭐ DUAL WRITE (Day 142). Commit succeeded, POST failed ⇒ silent loss.
⭐   4. ⭐⭐ SSRF. `webhook_url` IS ATTACKER-CONTROLLED — see Part 4.

⭐⭐ THE SHAPE THAT WORKS:
⭐   commit ──> outbox row (same txn) ──> relay ──> queue ──> delivery worker
⭐                                                              │
⭐                                            ┌─────────────────┴──────────┐
⭐                                            ▼                            ▼
⭐                                    2xx: mark delivered      non-2xx/timeout:
⭐                                                             schedule retry
⭐                                                             with backoff+jitter
⭐   ⇒ ⭐⭐ THE OUTBOX (Day 142) IS NOT OPTIONAL HERE. An event you promised to
⭐        deliver, lost because the process died between commit and enqueue,
⭐        is a support ticket you cannot answer — ⭐ you have no record that
⭐        the event ever existed.
```

```
⭐⭐ THE RETRY SCHEDULE — publish it, because it is part of your API contract:
⭐   ⭐ typical: 0s, 10s, 1m, 5m, 30m, 2h, 6h, 12h, 24h ⇒ ~3 days
⭐   ⭐ exponential with FULL JITTER (Day 142) — ⭐⭐ because when a receiver
⭐        comes back up, EVERY queued event for them retries at once and you
⭐        knock them straight back down.
⭐   ⭐⭐ AND A PER-ENDPOINT CIRCUIT BREAKER (Day 152): after N consecutive
⭐        failures, DISABLE the endpoint, stop attempting, and EMAIL THE
⭐        OWNER. ⭐ Otherwise one dead customer integration consumes your
⭐        delivery workers forever, and the queue for everyone else grows
⭐        behind it — ⭐⭐ head-of-line blocking with an external cause.
⭐   ⭐ ⭐⭐ SEPARATE QUEUES OR A CONCURRENCY CAP **PER RECEIVER**. One
⭐        customer with 100,000 events must not starve everyone else — this is
⭐        Day 153's fairness problem, in your delivery fleet.
```

# Part 2 — ⭐⭐ Signing: authenticating a message, not a caller

```
⭐⭐ THE RECEIVER'S PROBLEM: ANYONE CAN POST TO THEIR PUBLIC URL. ⭐ They need
⭐   to know the request came from you, and TLS alone does not tell them that
⭐   — ⭐⭐ TLS authenticates the SERVER to the CLIENT, which is the wrong
⭐   direction here.

⭐   ⭐⭐ HMAC OVER THE RAW BODY, WITH A TIMESTAMP:
⭐        signed = f"{timestamp}.{raw_body}"
⭐        sig    = hmac.new(secret, signed.encode(), sha256).hexdigest()
⭐        header: `X-Signature: t=1735689600,v1=5257a8...`
⭐
⭐⭐ THE FIVE DETAILS, EACH OF WHICH IS A REAL VULNERABILITY IF SKIPPED:
⭐  1. ⭐⭐ SIGN THE **RAW BYTES**, AND VERIFY THE **RAW BYTES**. ⭐ Not the
⭐       parsed-and-re-serialised JSON: key order, whitespace and unicode
⭐       escaping all differ ⇒ ⭐⭐ signature mismatches that are impossible to
⭐       debug. ⭐ In FastAPI: `await request.body()`, and parse afterwards.
⭐  2. ⭐⭐ INCLUDE A TIMESTAMP **IN THE SIGNED STRING** AND REJECT OLD ONES
⭐       (±5 min). ⭐ Without it, a captured request is REPLAYABLE FOREVER —
⭐       ⭐⭐ and a signature is not a defence against replay, because the
⭐       replayed request has a perfectly valid signature.
⭐  3. ⭐⭐ `hmac.compare_digest`, NEVER `==`. ⭐ String comparison
⭐       short-circuits on the first differing byte ⇒ a timing oracle that
⭐       leaks the signature byte by byte (Day 114).
⭐  4. ⭐ SEND **MULTIPLE SIGNATURES** DURING KEY ROTATION: `v1=old,v1=new`.
⭐       ⭐⭐ Day 150's overlap window — receivers cannot all rotate at once,
⭐       and a rotation without overlap breaks every integration.
⭐  5. ⭐⭐ HMAC, NOT "A SECRET IN A HEADER". ⭐ A bearer-style shared secret
⭐       is leaked by any receiver who logs headers (Day 146), and it does not
⭐       bind to the body — ⭐⭐ so it cannot detect tampering at all.
```

```python
# ⭐⭐ RECEIVING — the correct order of operations
@router.post("/webhooks/acme")
async def receive(request: Request):
    raw = await request.body()                                  # ⭐⭐ RAW, first
    ts, sig = parse_sig_header(request.headers.get("x-signature", ""))
    if abs(time.time() - ts) > 300:
        raise HTTPException(400, {"code": "timestamp_out_of_range"})   # ⭐ replay
    expected = hmac.new(SECRET, f"{ts}.".encode() + raw, sha256).hexdigest()
    if not hmac.compare_digest(expected, sig):                  # ⭐⭐ constant time
        raise HTTPException(401, {"code": "bad_signature"})

    event = Event.model_validate_json(raw)                      # ⭐ parse AFTER
    if not claim_event(event.id):                               # ⭐⭐ Day 122
        return {"status": "duplicate"}                          # ⭐ 200, not an error
    enqueue_processing(event.id)                                # ⭐⭐ Part 3
    return {"status": "accepted"}
```

# Part 3 — ⭐⭐ Receiving: the three rules that survive contact with reality

```
⭐⭐ RULE 1 — RESPOND 2xx FAST, PROCESS LATER.
⭐   ⭐ Senders time out in 3–10 seconds. ⭐⭐ If you process inline and take
⭐     12 seconds, THEY RETRY — and now you are processing the same event
⭐     twice, concurrently, while the first one is still running.
⭐   ⇒ ⭐ VERIFY, PERSIST, ENQUEUE, RETURN 200. ⭐⭐ Target under 200 ms.
⭐   ⇒ ⭐⭐ AND THE CONSEQUENCE PEOPLE MISS: A 200 NOW MEANS "RECEIVED", NOT
⭐        "SUCCEEDED". ⭐ If your async processing then fails, the sender will
⭐        never retry — ⭐⭐ so YOU own the retry from that point on. Your
⭐        queue's retry (Day 142) is not optional; it is the replacement for
⭐        theirs.
⭐
⭐⭐ RULE 2 — ASSUME DUPLICATES, ALWAYS.
⭐   ⭐ Every sender is at-least-once (Day 142). ⭐⭐ You WILL get the same
⭐     event twice — network retries, their bug, their replay tool.
⭐   ⇒ ⭐ Store `event_id` with a UNIQUE constraint and claim it atomically
⭐     BEFORE processing. ⭐⭐ Return 200 for a duplicate, not 409: an error
⭐     makes them retry it MORE.
⭐
⭐⭐ RULE 3 — ASSUME OUT-OF-ORDER.
⭐   ⭐ `subscription.updated` can arrive BEFORE `subscription.created`.
⭐     ⭐⭐ Parallel delivery workers and retries destroy ordering, and no
⭐     sender guarantees it across events.
⭐   ⇒ ⭐⭐ TWO DEFENCES: (a) events carry a VERSION or `occurred_at`, and you
⭐     ignore anything older than what you have stored — ⭐ the same
⭐     last-write-wins rule as any distributed system; (b) ⭐⭐ TREAT THE
⭐     WEBHOOK AS A **NOTIFICATION, NOT A DATA SOURCE**: on receipt, call
⭐     their API to fetch the CURRENT state.
⭐   ⇒ ⭐⭐ (b) IS THE ANSWER TO GIVE. It makes ordering, duplication and
⭐     tampering irrelevant in one move, at the cost of one API call. ⭐ Use it
⭐     for anything that matters, especially money.
```

```
⭐⭐ AND THE RULE BEHIND ALL THREE — SAY THIS: WEBHOOKS ARE A LATENCY
⭐   OPTIMISATION OVER POLLING, NOT A SOURCE OF TRUTH.
⭐   ⇒ ⭐ SO ALWAYS HAVE A RECONCILIATION JOB: nightly, poll their API for
⭐        anything you may have missed. ⭐⭐ Every serious integration has one,
⭐        because delivery WILL fail eventually — your endpoint was down for
⭐        four hours, their retries expired, and nothing in either system knows.
```

# Part 4 — ⭐⭐ SSRF: the vulnerability that is unique to sending

```
⭐⭐ THE USER GIVES YOU A URL AND YOU MAKE A REQUEST TO IT. ⭐ THAT IS THE
⭐   TEXTBOOK DEFINITION OF SERVER-SIDE REQUEST FORGERY (Day 127), and a
⭐   webhook feature is an SSRF feature with a business justification.

⭐   ⭐ `http://169.254.169.254/latest/meta-data/iam/...`
⭐        ⇒ ⭐⭐ CLOUD INSTANCE CREDENTIALS. This is the Capital One breach
⭐          shape, and it is one HTTP request.
⭐   ⭐ `http://localhost:6379/` ⇒ ⭐ your Redis. `http://10.0.1.5:5432` ⇒ your
⭐        database. ⭐⭐ Your firewall does not help: the request originates
⭐        INSIDE your network.
⭐   ⭐ `file:///etc/passwd` ⇒ ⭐ if the client follows non-HTTP schemes.

⭐⭐ THE DEFENCES, AND WHY THE OBVIOUS ONE IS INSUFFICIENT:
⭐  1. ⭐ HTTPS ONLY, port 443, ⭐ no credentials in the URL.
⭐  2. ⭐ RESOLVE THE HOSTNAME AND BLOCK PRIVATE RANGES — 127/8, 10/8,
⭐       172.16/12, 192.168/16, 169.254/16, ::1, fc00::/7.
⭐  3. ⭐⭐ AND HERE IS WHY (2) ALONE IS NOT ENOUGH — **DNS REBINDING**:
⭐       ⭐ you resolve `evil.com` → 1.2.3.4 (public, allowed) ✓
⭐       ⭐ TTL 0; you then CONNECT, and the SECOND resolution returns
⭐          127.0.0.1. ⭐⭐ THE CHECK AND THE USE WERE TWO DIFFERENT LOOKUPS —
⭐          a TOCTOU race (Day 067's shape, over DNS).
⭐       ⇒ ⭐⭐ FIX: resolve ONCE, validate the IP, and CONNECT TO THAT IP
⭐          (with the `Host` header set). ⭐ Or route all outbound webhook
⭐          traffic through a dedicated egress proxy that enforces the policy.
⭐  4. ⭐⭐ DO NOT FOLLOW REDIRECTS — ⭐ or a 302 to `169.254.169.254` bypasses
⭐       every check you did on the original URL.
⭐  5. ⭐⭐ RETURN NOTHING TO THE USER. Do not show the response body, headers
⭐       or precise timing in your delivery log — ⭐ that turns a blind SSRF
⭐       into a full read primitive.
⭐  6. ⭐ VERIFY OWNERSHIP: send a challenge to the URL and require the
⭐       response before enabling it. ⭐⭐ Stops your service being used to
⭐       DDoS a third party by pointing 10,000 webhooks at them.
⭐
⭐   ⇒ ⭐⭐ ARCHITECTURALLY, THE BEST ANSWER: DELIVER FROM AN ISOLATED WORKER
⭐        POOL WITH NO INTERNAL NETWORK ACCESS AND NO INSTANCE ROLE. ⭐ Then
⭐        SSRF reaches nothing worth reaching — ⭐⭐ Day 152's bulkhead, applied
⭐        to blast radius rather than to capacity.
```

# Part 5 — ⭐ Making it operable

```
⭐⭐ WHAT AN INTEGRATOR ACTUALLY NEEDS FROM YOU — and this is what separates
⭐   a webhook feature from a webhook PRODUCT:
⭐   ⭐ A DELIVERY LOG: every attempt, status code, response time, ⭐ and the
⭐        exact payload sent. ⭐⭐ Without it, every failure is a support
⭐        conversation with no evidence on either side.
⭐   ⭐⭐ A MANUAL REPLAY BUTTON. ⭐ Their endpoint was broken for an hour;
⭐        they fixed it; they need those 400 events. ⭐⭐ Without replay, your
⭐        only answer is "sorry" — and their data is permanently wrong.
⭐   ⭐ A TEST/PING EVENT they can trigger from your dashboard.
⭐   ⭐ VERSIONED EVENT SCHEMAS (Day 125) — ⭐⭐ adding a field is safe;
⭐        removing or retyping one breaks every receiver silently, ⭐ because
⭐        they parse with whatever they wrote a year ago and you will never
⭐        see the exception.
⭐   ⭐⭐ A SMALL, STABLE PAYLOAD: ids, type, timestamp, version — ⭐ and a
⭐        `data` object that is explicitly documented as best-effort. ⭐⭐ This
⭐        also nudges them toward Rule 3(b): fetch the current state.

⭐⭐ WHAT TO MONITOR (Day 147), because delivery is a queue and queues lie:
⭐   ⭐ delivery success rate PER ENDPOINT ⭐ (globally it is always ~99%,
⭐        which hides one customer at 0%)
⭐   ⭐⭐ OLDEST UNDELIVERED EVENT AGE — ⭐ not queue depth. Depth 12 with age
⭐        nine hours is a stuck receiver, and depth alone cannot say so.
⭐   ⭐ endpoints currently disabled by the breaker
⭐   ⭐ p95 receiver response time ⭐⭐ (a receiver creeping toward your timeout
⭐        is a future incident you can see coming)
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Sending the webhook in the request path | Their latency becomes yours and their outage becomes yours. |
| POST after commit with no outbox | The event is lost with no record it ever existed. |
| Retries without jitter | Every queued event for a recovering receiver fires at once and re-kills them. |
| No per-endpoint circuit breaker | One dead integration consumes your delivery workers forever. |
| One shared delivery queue | A customer with 100,000 events starves everyone else. |
| Signing the re-serialised JSON | Key order and whitespace differ — undebuggable mismatches. Sign raw bytes. |
| No timestamp in the signature | A captured request is replayable forever, with a valid signature. |
| `==` for signature comparison | A timing oracle. Use `hmac.compare_digest`. |
| Rotating the signing key with no overlap | Breaks every integration at once. Send both signatures. |
| A shared secret in a header instead of HMAC | Leaked by any receiver that logs headers, and doesn't bind to the body. |
| Processing inline before responding | They time out and retry while you're still working. |
| Treating your 200 as "succeeded" | It means "received" — the sender will never retry, so you own it now. |
| 409 for a duplicate event | Makes them retry more. Return 200. |
| Assuming event order | Retries and parallel workers destroy it. Use versions, or fetch current state. |
| Treating webhooks as a source of truth | They're a latency optimisation over polling. Reconcile nightly. |
| No SSRF validation on the URL | The metadata endpoint is one request away. |
| Validating the hostname then connecting by name | DNS rebinding — check and use are two lookups. Connect to the validated IP. |
| Following redirects | A 302 bypasses every check on the original URL. |
| Showing the response body in the delivery log | Turns a blind SSRF into a read primitive. |
| No delivery log or replay button | Every failure is a support conversation you can't win. |
| Monitoring queue depth rather than oldest event age | Depth 12 with age nine hours is a stuck receiver. |

## Interview questions

**Q: Design webhook delivery.**

> Never in the request path — their slowness becomes my latency and their outage becomes my outage.
> The event goes into an outbox row in the same transaction as the business write, because otherwise
> a crash between commit and enqueue loses an event with no record that it existed, and that's a
> support ticket I can't answer. A relay publishes to a queue, delivery workers POST with a
> timeout, and non-2xx or timeout schedules a retry on a published schedule — exponential with full
> jitter, because when a receiver recovers, every queued event for them fires at once and knocks them
> straight back down. Then two things people skip: a per-endpoint circuit breaker that disables a
> dead integration and emails the owner, so one broken customer doesn't consume my delivery fleet
> forever; and a per-receiver concurrency cap, so a customer with a hundred thousand events doesn't
> starve everyone else.

**Q: How do you let the receiver verify a webhook is really from you?**

> HMAC over the raw body with a timestamp included in the signed string. Five details matter. Sign and
> verify the *raw bytes*, not parsed-and-re-serialised JSON, because key order and whitespace differ
> and you get mismatches nobody can debug. Include the timestamp in the signed payload and reject
> anything outside about five minutes, because a signature is no defence against replay — a replayed
> request has a perfectly valid signature. Compare with `hmac.compare_digest`, never `==`, because
> string comparison short-circuits and leaks the signature byte by byte through timing. Send both old
> and new signatures during rotation, since receivers can't all rotate simultaneously. And HMAC
> rather than a shared secret in a header, because a bearer secret is leaked by any receiver who logs
> headers and doesn't bind to the body at all, so it can't detect tampering.

**Q: You're receiving webhooks. What are your rules?**

> Respond 2xx fast and process asynchronously — senders time out in a few seconds, so inline
> processing means they retry while I'm still working on the first copy. Verify, persist, enqueue,
> return, under a couple of hundred milliseconds. The consequence people miss is that my 200 means
> "received", not "succeeded", so if my async processing fails the sender will never retry — I own
> the retry from that point. Second, assume duplicates: every sender is at-least-once, so I claim the
> event id atomically before processing and return 200 for a duplicate, not 409, because an error
> makes them retry more. Third, assume out-of-order — updated can arrive before created — so events
> carry a version and I ignore stale ones. Though the real answer to ordering is to treat the webhook
> as a notification rather than a data source and call their API for current state, which makes
> ordering, duplication and tampering irrelevant in one move.

**Q: A user can set their own webhook URL. What's the security concern?**

> That's SSRF by design — a webhook feature is an SSRF feature with a business justification. They
> can point it at the cloud metadata endpoint and get instance credentials, which is the Capital One
> shape and is one HTTP request; or at internal Redis or Postgres, and my firewall doesn't help
> because the request originates inside the network. Defences: HTTPS and port 443 only; resolve and
> block private ranges; don't follow redirects, or a 302 bypasses every check on the original URL;
> and don't return the response body or precise timing to the user, or a blind SSRF becomes a read
> primitive. The subtle one is DNS rebinding — I resolve the host, it's public, I allow it, then the
> connection does a *second* lookup that returns 127.0.0.1. Check and use are two different lookups,
> so I resolve once, validate the IP, and connect to that IP with the `Host` header set. The best
> structural answer is delivering from an isolated worker pool with no internal network access and no
> instance role, so SSRF reaches nothing worth reaching.

**Q: A customer says they never received an event. What do you need to have built?**

> A delivery log with every attempt, its status code, response time and the exact payload sent —
> without it the conversation has no evidence on either side. A manual replay button, because their
> endpoint was down for an hour and they now need those four hundred events, and without replay my
> only answer is "sorry" while their data stays permanently wrong. Monitoring per endpoint rather
> than globally, since the global success rate is always about ninety-nine percent and hides the one
> customer at zero. And oldest-undelivered-event age rather than queue depth, because depth twelve
> with age nine hours is a stuck receiver and depth alone can't tell you that. Plus a reconciliation
> job on their side and mine, because webhooks are a latency optimisation over polling, not a source
> of truth, and delivery will eventually fail in a way neither system notices.

## 🎙️ Articulation drill

**Two minutes: "Design our webhook system."**

Split it into sending and receiving, and say the framing first: a webhook is a request to a server
you don't control, operated by someone who will misconfigure it. Sending: outbox in the same
transaction, queue, workers, published retry schedule with jitter, per-endpoint breaker and
concurrency cap. Signing: HMAC over raw bytes with a timestamp in the signed string, constant-time
compare, overlapping keys during rotation — and say why each one is a vulnerability if skipped.
Receiving: fast 2xx then async, with the consequence that your 200 means received so you own the
retry; idempotency by event id; and out-of-order handled by fetching current state rather than
trusting the payload. Then raise SSRF unprompted, because a webhook URL field is an SSRF feature —
mention rebinding and the isolated egress pool. Close on operability: **a delivery log and a replay
button, because delivery will fail and without replay your only answer is "sorry".**
