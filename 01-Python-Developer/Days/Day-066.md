# Part 1 — ⭐ Threads, and the contrast with Day 003

```python
import threading

counter = 0                      # ⭐⭐ ONE variable, shared by every thread

def work(n):
    global counter
    counter += n

ts = [threading.Thread(target=work, args=(1,)) for _ in range(5)]
for t in ts: t.start()           # ⭐ start() runs it; ⚠️ run() would just call it inline
for t in ts: t.join()            # ⭐⭐ WAIT for completion — without this, main may exit first
print(counter)                   # ⭐ 5 — the same variable, unlike Day 003's processes
```

```
⭐⭐ THE CONTRAST WORTH HOLDING (Day 003, Day 064):
⭐   multiprocessing ⇒ the child's `counter` was a COPY. The parent never saw the change.
⭐   threading       ⇒ ⭐⭐ it is THE SAME OBJECT. Every thread sees every write.
⭐   ⇒ ⭐ that is the feature, and Day 067 is the bill.
```

⚠️ ⭐⭐ **Daemon threads are a trap.** `Thread(daemon=True)` does not keep the process alive — **and
when the process exits, daemon threads are killed abruptly: no `finally`, no context-manager exit, no
flush.** ⭐ A daemon thread writing a file can leave it truncated. **Use them only for genuinely
disposable background work, and prefer an explicit shutdown `Event`.**

```
⭐⭐ YOU CANNOT KILL A THREAD IN PYTHON. There is no Thread.terminate().
⭐   ⇒ ⭐⭐ so every long-running thread must be written to be ASKED to stop:
```

```python
stop = threading.Event()

def worker():
    while not stop.is_set():                 # ⭐⭐ check the flag
        item = get_work(timeout=1)           # ⭐ a TIMEOUT, so it can notice the flag
        if item: process(item)

t = threading.Thread(target=worker); t.start()
...
stop.set(); t.join(timeout=10)               # ⭐ ask, then wait with a bound
```

⭐⭐ **"A thread that blocks forever cannot be stopped" is the design constraint** — so every blocking
call inside a worker loop needs a timeout, or your shutdown hangs and something eventually SIGKILLs
the process mid-write.

# Part 2 — ⭐⭐ When threading genuinely helps

```python
# ⭐⭐ THE NUMBER THAT MAKES THE CASE — 50 HTTP requests, ~200 ms each:
#   sequential           ⇒ ~10 s
#   ThreadPoolExecutor   ⇒ ⭐⭐ ~0.4 s      (the GIL is released during the socket wait — Day 065)
#   ProcessPoolExecutor  ⇒ ⭐ ~1.5 s        (process startup + pickling, for no benefit)
#   asyncio              ⇒ ⭐ ~0.3 s, one thread, far less memory (Day 070)
```

| ⭐ Threads are right for | ⭐ Why |
|---|---|
| ⭐⭐ Blocking I/O with a **synchronous** library | ⭐⭐ `requests`, `psycopg2`, `boto3` — no async version, or not worth rewriting |
| Waiting on a subprocess | the wait releases the GIL |
| ⭐ NumPy / hashlib / compression | ⭐ those release the GIL in C (Day 065) |
| Keeping a UI or a heartbeat responsive | a background loop |
| ⭐ A handful (tens) of concurrent operations | ⭐⭐ above ~hundreds, use asyncio |

```
⭐⭐ THREADS vs ASYNCIO — the honest comparison, because both are correct answers:
⭐   THREADS  ✓ work with ANY blocking library, unchanged  ⭐⭐ ← the decisive advantage
⭐            ✓ no colour problem — no async/await to spread through your codebase
⭐            ✗ ⭐ ~8 KB–1 MB of real overhead each; hundreds is fine, ten thousand is not
⭐            ✗ ⭐⭐ PREEMPTIVE ⇒ races everywhere ⇒ locks
⭐   ASYNCIO  ✓ ⭐⭐ tens of thousands of connections, one thread
⭐            ✓ ⭐ COOPERATIVE ⇒ no preemption between awaits ⇒ far fewer races
⭐            ✗ ⭐⭐ needs async-aware libraries top to bottom, or it is worse than useless
```

⭐⭐ **The decisive practical point: threads work with the library you already have.** ⭐ If your
database driver is synchronous, a thread pool gives you concurrency today and asyncio gives you a
rewrite.

# Part 3 — ⭐⭐ Locks and the primitives

```python
lock = threading.Lock()
with lock:                          # ⭐⭐ ALWAYS a context manager — released on exception (Day 052)
    counter += 1

rlock = threading.RLock()           # ⭐⭐ REENTRANT — the SAME thread may acquire it again
```

```
⭐⭐ WHY RLock EXISTS — a real and common shape:
⭐   class Account:
⭐       def withdraw(self):  with self._lock: ...; self._log()
⭐       def _log(self):      with self._lock: ...      ⭐⭐ ← a plain Lock DEADLOCKS HERE
⭐   ⇒ ⭐ one method holding the lock calls another that also takes it.
⭐   ⇒ ⭐⭐ RLock counts acquisitions by the owning thread and releases at zero.
⭐   ⇒ ⚠️ ⭐ but needing RLock is often a sign the locking is at the wrong granularity.
```

| ⭐ Primitive | ⭐ For |
|---|---|
| ⭐⭐ `Lock` | mutual exclusion — one thread in the critical section |
| ⭐ `RLock` | ⭐ the same thread re-entering |
| ⭐⭐ `Event` | ⭐⭐ one-way signalling — **shutdown, ready, done** |
| `Condition` | wait until a predicate holds, with notification |
| ⭐ `Semaphore(n)` | ⭐⭐ **limit concurrency** — n at a time (a connection pool, a rate limit) |
| `Barrier(n)` | all n threads wait for each other |
| ⭐ `local()` | per-thread storage — no sharing, no lock |

```python
# ⚠️⚠️ ⭐⭐ DEADLOCK — two locks, two threads, opposite order:
def a(): 
    with lock1:
        with lock2: ...          # ⭐ thread A holds 1, wants 2
def b():
    with lock2:
        with lock1: ...          # ⭐⭐ thread B holds 2, wants 1 ⇒ BOTH WAIT FOREVER
```

```
⭐⭐ THE THREE PRACTICAL DEFENCES:
⭐   1. ⭐⭐ A GLOBAL LOCK ORDER — always acquire in the same order (e.g. by id()).
⭐        ⇒ this alone eliminates the cycle, which is one of deadlock's four conditions.
⭐   2. ⭐ TIMEOUTS: lock.acquire(timeout=5) ⇒ fail loudly instead of hanging forever
⭐   3. ⭐⭐ HOLD ONE LOCK AT A TIME — ⭐⭐ and NEVER do I/O while holding a lock:
⭐        a network call inside a critical section holds it for the network's latency,
⭐        which serialises every other thread behind a timeout you do not control.
```

⭐⭐ **"Never hold a lock across I/O" is the rule that prevents most real lock incidents.** ⭐ A
deadlock hangs and gets found; **a lock held across a slow HTTP call quietly serialises your whole
service and looks like "the app is slow".**

# Part 4 — ⭐⭐ `queue.Queue` — the design that avoids the problem

```python
from queue import Queue

q = Queue(maxsize=100)                   # ⭐⭐ BOUNDED ⇒ backpressure, not unbounded memory

def producer():
    for item in source():
        q.put(item)                      # ⭐ blocks when full — that is the feature
    for _ in workers: q.put(None)        # ⭐ one sentinel per consumer

def consumer():
    while (item := q.get()) is not None:  # ⭐ Day 040's walrus
        try:
            process(item)
        finally:
            q.task_done()                # ⭐ needed for q.join()
```

```
⭐⭐ WHY THIS IS THE RIGHT DEFAULT:
⭐   · ⭐⭐ Queue is ALREADY THREAD-SAFE — internally locked. You write no locks at all.
⭐   · ⭐⭐ the design changes: threads no longer SHARE state, they PASS OWNERSHIP.
⭐        ⇒ an item belongs to exactly one thread at a time ⇒ ⭐⭐ no race is possible
⭐   · ⭐ maxsize gives BACKPRESSURE: a slow consumer slows the producer instead of
⭐        letting the queue grow until the process is OOM-killed (Day 028)
⭐ ⇒ ⭐⭐ "Don't communicate by sharing memory; share memory by communicating." (Go's motto,
⭐      and it is the best advice in concurrency regardless of language.)
```

⚠️ ⭐ **`q.get()` with no timeout blocks forever** — which is exactly the un-killable thread from
Part 1. **Use `q.get(timeout=1)` in a loop that also checks a shutdown `Event`, or the sentinel
pattern above.**

```python
threading.local()          # ⭐ per-thread state — a DB connection per thread, a request id
                           # ⭐⭐ this is how frameworks give you "the current request"
```

⭐ **`threading.local()` is worth knowing because it is how synchronous frameworks implement
request-scoped globals** — ⚠️ **and why those globals break under asyncio, where many tasks share one
thread** (Day 070 uses `contextvars` instead).

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Sharing mutable state and locking carefully** | ⭐⭐ Pass messages with `Queue` — no lock to get wrong. |
| ⭐ `daemon=True` for real work | ⭐⭐ Killed abruptly — no `finally`, no flush. |
| Expecting to kill a thread | ⭐⭐ You cannot. Use an `Event` and timeouts. |
| A blocking call with no timeout in a worker | ⭐ Shutdown hangs forever. |
| `lock.acquire()` without `with` | ⭐⭐ An exception leaks the lock and deadlocks everyone. |
| ⭐⭐ **Holding a lock across I/O** | ⭐⭐ Serialises the service for the network's latency. |
| Two locks in inconsistent order | ⭐ Deadlock. Impose a global order. |
| An unbounded `Queue` | ⭐ No backpressure — memory grows until OOM. |
| `t.run()` instead of `t.start()` | ⭐ Runs inline in the current thread. |
| Forgetting `join()` | ⭐ Main may exit first. |
| Threads for CPU work | ⭐⭐ The GIL (Day 065). |
| Thousands of threads | ⭐ Use asyncio (Day 070). |

## Interview questions

**Q: When are threads the right choice in Python?**
> Blocking I/O with a synchronous library — `requests`, `psycopg2`, `boto3`. The GIL is released during
> the syscall, so fifty threads waiting on fifty sockets is genuine concurrency, and fifty requests at
> 200ms each go from ten seconds to under one. The decisive practical advantage over asyncio is that
> threads work with the library I already have: if my driver is synchronous, a thread pool gives me
> concurrency today and asyncio gives me a rewrite. The limit is scale — hundreds of threads is fine,
> tens of thousands is not, and that's where the event loop wins.

**Q: How do you stop a thread?**
> You ask it. There's no `Thread.terminate()`, so a long-running thread has to be written to check a
> `threading.Event` and every blocking call inside it needs a timeout — otherwise it can't notice the
> flag and shutdown hangs until something SIGKILLs the process, possibly mid-write. Daemon threads
> look like a shortcut and aren't: they're killed abruptly at interpreter exit, so no `finally` runs
> and no buffer is flushed.

**Q: `Lock` or `RLock`?**
> `Lock` unless the same thread needs to reacquire — which happens when one method holding the lock
> calls another that also takes it, and a plain `Lock` deadlocks against itself there. `RLock` counts
> acquisitions by the owning thread. But needing it is usually a signal that the locking is at the
> wrong granularity, so I'd look at whether the inner method should assume the lock is held rather
> than take it.

**Q: How do you avoid deadlock?**
> Three things. Impose a global acquisition order so a cycle can't form — that's one of the four
> Coffman conditions removed. Use timeouts, so a failure is loud rather than a hang. And hold one lock
> at a time. The rule I'd emphasise is never holding a lock across I/O: a deadlock hangs and gets
> found, but a lock held across a slow HTTP call silently serialises the whole service behind a
> timeout you don't control, and it presents as "the app is slow" with nothing obviously wrong.

**Q: What's the better design than locking?**
> Not sharing. A `queue.Queue` is already thread-safe internally, so producers and consumers pass
> ownership of items rather than sharing state — an item belongs to exactly one thread at a time, and
> no race is possible because there's nothing concurrent to race on. A bounded queue also gives
> backpressure: a slow consumer slows the producer rather than letting the queue grow until the
> process is OOM-killed. It's Go's "don't communicate by sharing memory; share memory by
> communicating", and it's the best advice in concurrency regardless of language.

**Q: What is `threading.local()` for?**
> Per-thread state with no sharing and therefore no locking — a database connection per thread, or a
> request id. It's how synchronous frameworks implement request-scoped globals like "the current
> request". Worth knowing that it breaks under asyncio, where thousands of tasks share one thread, so
> the async equivalent is `contextvars`.

## 🎙️ Articulation drill

Record two minutes: **"Design a worker that processes jobs from a queue, with a clean shutdown."**

⭐ Structure first: **a bounded `queue.Queue`, a pool of worker threads, and no shared mutable state —
threads take ownership of an item rather than sharing one.** Note that `Queue` is internally locked,
so **there are no locks in my code at all**, which removes the entire category of bug rather than
managing it.

⭐ Then backpressure: **`maxsize` means a slow consumer slows the producer**, rather than letting the
queue grow until the process is OOM-killed — which is the failure mode of every unbounded queue.

⭐⭐ **Then shutdown, because it is the part people get wrong:** *"you cannot kill a thread in Python,
so the workers have to be asked. A `threading.Event` flag, and — the bit that matters — every blocking
call inside the loop needs a timeout, because a worker blocked forever in `q.get()` can never notice
the flag. Without that, shutdown hangs, the orchestrator waits out its grace period, and something
SIGKILLs the process possibly mid-write. And I would not use daemon threads to dodge this: they're
killed abruptly at exit, so no `finally` runs and nothing is flushed."*
