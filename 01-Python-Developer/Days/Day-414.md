# Day 414 🧠

**P-414** · 🧠 **What an LLM actually is** — ⭐⭐ next-token prediction, and every consequence

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an LLM is a function from a token sequence to a probability distribution
> over the next token, sampled in a loop — and every surprising thing about building with one, from
> hallucination to cost to latency to prompt injection, is a direct consequence of that single
> sentence rather than a bug someone will fix.**

# Part 1 — The mechanism, in one loop

```
⭐ GIVEN A SEQUENCE OF TOKENS, THE MODEL OUTPUTS ***A
⭐   PROBABILITY FOR EVERY TOKEN IN ITS VOCABULARY*** (~50k–200k
⭐   entries) AS THE NEXT ONE.

⭐   "The capital of France is" →
⭐      " Paris"  0.94
⭐      " the"    0.02
⭐      " a"      0.01
⭐      …

⭐ ⭐ You (or the sampler) pick one. ⭐ Append it. ⭐⭐ RUN THE
⭐   ***WHOLE THING*** AGAIN. ⭐ Repeat until a stop token or a
⭐   length limit.

⭐⭐ ***THAT IS THE ENTIRE ALGORITHM. THERE IS NO SECOND
⭐   MECHANISM.***
⭐   ⭐ No lookup table. ⭐ No database. ⭐ No plan formed before it
⭐   starts writing. ⭐⭐ NO INTERNAL STATE CARRIED BETWEEN YOUR
⭐   API CALLS.

⭐⭐ AND THE FIRST ENGINEERING CONSEQUENCE, WHICH IS THE ONE
⭐   PEOPLE FEEL FIRST: ***GENERATION IS SEQUENTIAL, SO LATENCY
⭐   IS LINEAR IN ***OUTPUT*** LENGTH AND ROUGHLY CONSTANT IN
⭐   ***INPUT*** LENGTH.***
⭐   ⭐ Input is processed in one parallel pass (the "prefill").
⭐   ⭐⭐ OUTPUT IS PRODUCED ONE TOKEN AT A TIME (THE "DECODE"),
⭐     EACH REQUIRING A FULL FORWARD PASS.
⭐   ⭐⭐ ⇒ SO ***ASKING FOR A SHORTER ANSWER IS THE SINGLE MOST
⭐     EFFECTIVE LATENCY OPTIMISATION AVAILABLE TO YOU***, ⭐ and
⭐     sending a longer prompt is much cheaper in time than
⭐     receiving a longer answer. ⭐⭐ MOST PEOPLE OPTIMISE THE
⭐     WRONG ONE.
```

# Part 2 — ⭐⭐ Six consequences you must hold simultaneously

```
⭐⭐ ① ***IT HAS NO MEMORY.*** ⭐ Not "a short memory" —
⭐    ***none***. ⭐ Every API call is stateless. ⭐⭐ A "CONVERSATION"
⭐    IS YOU RESENDING THE ENTIRE HISTORY EVERY SINGLE TIME.
⭐    ⭐⭐ ⇒ WHICH IS WHY A LONG CHAT GETS SLOWER AND MORE
⭐      EXPENSIVE WITH EVERY TURN, QUADRATICALLY IN TOTAL COST —
⭐      ⭐ turn 50 resends turns 1–49. ⭐⭐ MEMORY IS ***YOUR***
⭐      ENGINEERING PROBLEM (DAY 443).

⭐⭐ ② ***IT CANNOT LOOK ANYTHING UP.*** ⭐ It has no access to
⭐    your database, the internet, the current date, or its own
⭐    training corpus. ⭐⭐ IT HAS ONLY WHAT IS IN THE CONTEXT
⭐    WINDOW RIGHT NOW PLUS WHAT ITS WEIGHTS ENCODE.
⭐    ⭐ ⇒ That is the entire argument for RAG (Day 429) and for
⭐      tools (Day 438).

⭐⭐ ③ ***"IT LIED TO ME" IS A CATEGORY ERROR.*** ⭐ Lying
⭐    requires knowing the truth and choosing otherwise.
⭐    ⭐⭐ THE MODEL PRODUCED THE MOST PLAUSIBLE CONTINUATION. ⭐ A
⭐    fabricated citation is plausible ***in form*** — the right
⭐    shape, a real-sounding journal, a well-formed DOI —
⭐    ⭐⭐ WHICH IS EXACTLY WHAT IT WAS OPTIMISED TO PRODUCE.
⭐    ⭐ Day 449 does the mechanics.

⭐⭐ ④ ***FLUENCY AND CORRECTNESS ARE INDEPENDENT VARIABLES.***
⭐    ⭐ There is no internal "confidence" that leaks into the
⭐    wording. ⭐⭐ A CONFIDENT WRONG ANSWER AND A CONFIDENT RIGHT
⭐    ANSWER ARE PRODUCED BY THE SAME PROCESS AND READ
⭐    IDENTICALLY — ⭐ so ***your users cannot tell***, and neither
⭐    can you, without checking. ⭐⭐ THIS IS THE SINGLE MOST
⭐    DANGEROUS PROPERTY OF THE TECHNOLOGY.

⭐⭐ ⑤ ***IT IS NON-DETERMINISTIC BY DEFAULT*** (Day 418) — ⭐ and
⭐    even at `temperature=0` it is only ***mostly***
⭐    reproducible, because floating-point non-associativity in
⭐    batched GPU kernels means the same input can produce
⭐    different logits depending on what else was in the batch.
⭐    ⭐⭐ ⇒ SO "TEMPERATURE 0 MAKES IT DETERMINISTIC" IS FALSE,
⭐      AND ANY TEST THAT ASSERTS AN EXACT STRING WILL FLAKE
⭐      (DAY 425).

⭐⭐ ⑥ ***THE INSTRUCTIONS AND THE DATA ARRIVE ON THE SAME
⭐    CHANNEL.*** ⭐ There is no `parameterised query` for
⭐    prompts. ⭐ The system prompt, the user's message and a
⭐    retrieved document are all just tokens in one sequence,
⭐    ⭐⭐ AND THE MODEL HAS NO RELIABLE WAY TO TELL WHICH ONE IT
⭐    IS SUPPOSED TO OBEY. ⭐ Hold that thought until Day 446;
⭐    ⭐⭐ IT IS THE MOST IMPORTANT SECURITY FACT IN THE STAGE.
```

# Part 3 — What "reasoning models" actually changed

```
⭐ ⭐⭐ THEY DID NOT ADD A SECOND MECHANISM. ⭐ A reasoning model
⭐   (o-series, Claude with extended thinking, DeepSeek-R1) is
⭐   still doing next-token prediction — ⭐⭐ IT HAS SIMPLY BEEN
⭐   TRAINED TO SPEND MANY TOKENS ON ***SCRATCH WORK*** BEFORE
⭐   COMMITTING TO AN ANSWER.

⭐ WHY THAT HELPS AT ALL: ⭐ each token is one forward pass, so
⭐   ⭐⭐ MORE TOKENS = MORE COMPUTE SPENT ON THE PROBLEM. ⭐ A
⭐   model that must answer immediately has one pass' worth of
⭐   computation; ⭐ one that writes 2,000 tokens of working has
⭐   2,000. ⭐⭐ "THINKING" IS LITERALLY BUYING COMPUTE WITH
⭐   TOKENS.

⭐ ⇒ THE ENGINEERING CONSEQUENCES ARE ALL PRACTICAL:
⭐   ⭐⭐ ① YOU PAY FOR THE THINKING TOKENS, ⭐ often at output
⭐      rates, ⭐⭐ AND YOU USUALLY DO NOT GET TO SEE THEM.
⭐   ⭐⭐ ② LATENCY GOES FROM SECONDS TO ***TENS OF SECONDS***, ⭐ so
⭐      a reasoning model on a synchronous request path is
⭐      usually a design error. ⭐⭐ MAKE IT ASYNCHRONOUS
⭐      (DAY 399).
⭐   ⭐ ③ It genuinely helps on multi-step logic, maths and
⭐      planning — ⭐⭐ AND IS PURE WASTE ON EXTRACTION,
⭐      CLASSIFICATION, FORMATTING AND SUMMARISATION, ⭐ which is
⭐      most of what production systems actually do.
⭐   ⭐⭐ ⇒ ***ROUTE BY TASK, NOT BY PRESTIGE*** (DAY 457).
```

# Part 4 — The vocabulary you need to not sound naive

```
⭐ ***TOKEN*** — ⭐ a sub-word unit. ⭐ Day 415.
⭐ ***CONTEXT WINDOW*** — ⭐ the maximum tokens of input + output
⭐   in one call. ⭐⭐ A HARD ARCHITECTURAL LIMIT, NOT A QUOTA.
⭐ ***PARAMETERS*** — ⭐ the learned weights. ⭐⭐ MORE PARAMETERS ≈
⭐   MORE CAPABILITY AND MORE COST PER TOKEN, ⭐ and the
⭐   relationship is not linear in either direction.
⭐ ***PROMPT / COMPLETION*** — ⭐ input / output. ⭐⭐ PRICED
⭐   DIFFERENTLY: OUTPUT IS TYPICALLY 3–5× THE PRICE OF INPUT.
⭐ ***SYSTEM / USER / ASSISTANT*** — ⭐ message roles. ⭐⭐ THEY ARE
⭐   A CONVENTION ENCODED AS SPECIAL TOKENS, ***NOT A SECURITY
⭐   BOUNDARY*** (Day 446).
⭐ ***TEMPERATURE, top-p*** — ⭐ sampling controls. ⭐ Day 418.
⭐ ***BASE vs INSTRUCT vs CHAT*** — ⭐ a base model completes
⭐   text; ⭐⭐ AN INSTRUCT/CHAT MODEL HAS BEEN FINE-TUNED TO
⭐   FOLLOW INSTRUCTIONS (DAY 417). ⭐ You almost always want the
⭐   latter.
⭐ ***EMBEDDING*** — ⭐ a vector representing meaning. ⭐ Day 419.
⭐ ***RAG*** — ⭐ retrieve, then generate. ⭐ Day 429.
⭐ ***TOOL / FUNCTION CALLING*** — ⭐ the model emits a structured
⭐   request for ***you*** to execute. ⭐⭐ IT NEVER EXECUTES
⭐   ANYTHING ITSELF (DAY 438).
⭐ ***HALLUCINATION*** — ⭐ confident fabrication. ⭐ Day 449.
```

# Part 5 — The first honest Python call

```python
# ⭐⭐ EVERY LESSON FROM STAGE 12 APPLIES TO THIS ONE CALL.
from openai import OpenAI
import httpx

client = OpenAI(
    timeout=httpx.Timeout(60.0, connect=5.0),   # ⭐⭐ DAY 398:
        # ⭐ NEVER UNBOUNDED. And 60 s is not paranoid — a long
        # ⭐ generation genuinely takes that long.
    max_retries=0,   # ⭐⭐ DISABLE THE SDK'S RETRIES AND OWN THEM
)                    # ⭐   YOURSELF, WITH A BUDGET (DAY 336).

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "You extract structured data."},
        {"role": "user", "content": text},
    ],
    max_tokens=500,          # ⭐⭐ A COST AND LATENCY CEILING.
        # ⭐ NEVER OMIT THIS. Without it, one pathological input
        # ⭐ can generate until the context window ends and bill
        # ⭐ you for all of it.
    temperature=0,           # ⭐ Day 418
)

print(resp.usage.prompt_tokens, resp.usage.completion_tokens)
# ⭐⭐ LOG `usage` ON ***EVERY*** CALL FROM DAY ONE. It is your
# ⭐   only cost signal, and retrofitting it means a month of
# ⭐   blind spend (Days 421, 457).
```

```

⭐   IMPLEMENTATIONS:
⭐   ⭐ ① No timeout → ⭐⭐ A HUNG CALL HOLDS A gunicorn WORKER
⭐      FOREVER (DAY 384).
```

# Part 6 — What this technology is genuinely good and bad at

```
⭐ ⭐⭐ GOOD AT — ⭐ and these are the shapes worth building:
⭐   ⭐ Transformation: ⭐⭐ TEXT IN A KNOWN FORM → TEXT IN
⭐     ANOTHER FORM. ⭐ Summarise, translate, rewrite, reformat,
⭐     extract to JSON. ⭐⭐ THE MOST RELIABLE CATEGORY BY FAR,
⭐     because the answer is ***in the input***.
⭐   ⭐ Classification and routing with a fixed label set.
⭐   ⭐ Drafting where a human reviews before it matters.
⭐   ⭐ Natural-language interfaces over structured systems
⭐     (Day 438).
⭐   ⭐ Semantic search (Day 419).

⭐ ⭐⭐ BAD AT — ⭐ and no amount of prompting fixes these:
⭐   ⭐⭐ ***FACTS IT WAS NOT GIVEN.*** ⭐ Use retrieval, not the
⭐     weights.
⭐   ⭐⭐ ***ARITHMETIC AND COUNTING.*** ⭐ It predicts the *shape*
⭐     of a number. ⭐ Give it a calculator tool.
⭐   ⭐ Anything requiring a guarantee. ⭐⭐ THERE IS NO
⭐     "ALWAYS" AVAILABLE.
⭐   ⭐ Long chains of exact reasoning without checks.
⭐   ⭐⭐ ***BEING THE FINAL AUTHORITY ON ANYTHING IRREVERSIBLE.***

⭐⭐ ⇒ THE DESIGN RULE THAT FALLS OUT OF THAT TABLE, AND IT IS
⭐   THE ONE SENTENCE TO CARRY INTO EVERY DESIGN REVIEW:
⭐   ⭐⭐ ***PUT THE MODEL WHERE A WRONG ANSWER IS RECOVERABLE.***
⭐   ⭐ Drafting an email a human sends: yes. ⭐ Deciding a refund
⭐   with no review: no. ⭐⭐ AND IF THE ANSWER MUST BE RIGHT,
⭐   THE MODEL PROPOSES AND SOMETHING ***DETERMINISTIC***
⭐   DISPOSES — ⭐ a schema validator, a permission check, a
⭐   database constraint, a human.
```

# 💬 Interview

**1. ⭐⭐ "What is an LLM, mechanically?"**
> ⭐ A function from a token sequence to a probability distribution over the next token, sampled in a
> loop — ⭐⭐ **you pick a token, append it, and run the whole model again.** ⭐ That's the entire
> algorithm; there's no lookup table, no plan formed before it starts writing, and no state carried
> between API calls. ⭐ And most of the engineering follows directly: ⭐⭐ **input is processed in one
> parallel pass while output is produced one token at a time, so latency is linear in output length
> and roughly flat in input length — which means asking for a shorter answer is the single most
> effective latency optimisation available, and most people optimise the prompt instead.**

**2. ⭐⭐ "Why does it hallucinate?"**
> ⭐ Because it was trained to produce the most plausible continuation, and ⭐⭐ **a fabricated citation
> is plausible in form — the right shape, a real-sounding journal, a well-formed DOI — which is
> exactly what it was optimised to produce.** ⭐ "It lied" is a category error; lying requires knowing
> the truth and choosing otherwise. ⭐ The dangerous part isn't the error rate, it's that ⭐⭐ **fluency
> and correctness are independent variables — a confident wrong answer and a confident right one come
> from the same process and read identically, so users can't tell and neither can you without
> checking.**

**3. "Does the model remember our conversation?"**
> ⭐⭐ **No — not a short memory, none. Every call is stateless, and a "conversation" is you resending
> the entire history each time.** ⭐ Which is why a long chat gets slower and more expensive every
> turn — turn fifty resends turns one through forty-nine, ⭐⭐ **so total cost over a conversation grows
> quadratically.** ⭐ Memory is my engineering problem, not a model feature: summarisation, a rolling
> window, or retrieval over past turns.

**4. ⭐⭐ "Is `temperature=0` deterministic?"**
> ⭐ No — it's *mostly* reproducible, which is not the same thing. ⭐⭐ **Floating-point addition isn't
> associative, and on batched GPU kernels the order of operations depends on what else was in the
> batch, so the same input can produce slightly different logits and occasionally a different token.**
> ⭐ The practical consequence is that ⭐⭐ **any test asserting an exact output string will flake**, which
> is why this stage replaces unit tests with evals.

**5. "What did reasoning models change?"**
> ⭐⭐ **Nothing about the mechanism — they're still doing next-token prediction. They've been trained
> to spend many tokens on scratch work before answering.** ⭐ That helps because each token is one
> forward pass, ⭐⭐ **so "thinking" is literally buying compute with tokens.** ⭐ Three engineering
> consequences: you pay for thinking tokens, often at output rates and usually without seeing them;
> latency goes to tens of seconds, ⭐⭐ **so putting one on a synchronous request path is usually a
> design error**; and they help on multi-step logic and are pure waste on extraction, classification
> and summarisation — which is most of what production systems do. ⭐ Route by task, not by prestige.

**6. ⭐⭐ "Where should the model sit in a system?"**
> ⭐⭐ **Where a wrong answer is recoverable.** ⭐ Drafting an email a human sends, yes; deciding a refund
> with no review, no. ⭐ And when the answer has to be right, ⭐⭐ **the model proposes and something
> deterministic disposes — a schema validator, a permission check, a database constraint, or a
> person.** ⭐ It's genuinely reliable at transformation, where the answer is already in the input:
> summarise, reformat, extract to JSON, classify into a fixed label set. ⭐⭐ **It's structurally bad at
> facts it wasn't given and at arithmetic, because it predicts the shape of a number — so those get
> retrieval and a calculator tool, not a better prompt.**

## 🎙️ Articulation drill

**Two minutes.** Define it mechanically and refuse the mysticism: **an LLM is a function from a token
sequence to a probability distribution over the next token, sampled in a loop — pick a token, append
it, run the whole model again. There's no lookup table and no plan formed before it starts writing.**
Then derive the engineering from it. **Latency is linear in output and flat in input, because input is
one parallel pass and output is one forward pass per token — so asking for a shorter answer beats
shortening the prompt.** **It has no memory at all, so a conversation is you resending the whole
history, and cost over a long chat grows quadratically.** **It can't look anything up, which is the
entire argument for retrieval and tools.** Then the two facts that shape the design: **fluency and
correctness are independent variables — a confident wrong answer reads exactly like a confident right
one, so nobody can tell without checking.** And **the instructions and the data arrive on the same
channel; there's no parameterised query for prompts, which is what makes injection unfixable by
prompting.** Close on placement: **put the model where a wrong answer is recoverable, and when the
answer must be right, the model proposes and something deterministic disposes — a validator, a
permission check, a constraint, or a human.** And frame the stage: **an LLM app is a distributed system
with a non-deterministic, expensive, untrusted component in the middle, so everything from Stages 9 to
12 applies unchanged — plus four new problems: you can't unit-test it, the trust boundary moved, cost
is per-request and variable, and confidence tells you nothing.**
