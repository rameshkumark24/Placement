# Part 1 — The tree and the API

```
⭐⭐ THE DOM IS NOT YOUR HTML. It is a LIVE TREE the browser built
⭐   from your HTML and then kept mutating. View source shows the
⭐   HTML you sent; DevTools shows the DOM as it is NOW.
⭐   ⇒ ⭐ they differ the moment any JS runs, which confuses everyone once.
```

```javascript
document.querySelector(".item")          // ⭐ first match, or null
document.querySelectorAll(".item")       // ⭐ STATIC NodeList — a snapshot
document.getElementsByClassName("item")  // ⭐⭐ LIVE collection — mutates
                                         //    while you iterate it. Avoid.

el.textContent = "safe";                 // ⭐⭐ ALWAYS THIS
el.innerHTML   = userInput;              // ⭐⭐ XSS. Day 243. Never with user data.

el.classList.add("active");              // ⭐ not el.className = — that clobbers
el.dataset.userId                        // reads data-user-id
```

| ⭐ Task | The call |
|---|---|
| Create | `document.createElement("div")` |
| Insert | `parent.append(child)` — ⭐ takes strings *and* nodes, unlike `appendChild` |
| Remove | `el.remove()` |
| Attribute vs property | ⭐⭐ `el.getAttribute("value")` is the *initial* HTML; `el.value` is the *current* state. **They diverge as soon as the user types**, and that surprise is the root of half of all form bugs. |

# Part 2 — Events

```javascript
button.addEventListener("click", (e) => {
  e.preventDefault();     // ⭐ stop the default (form submit, link nav)
  e.stopPropagation();    // ⭐ stop bubbling — use sparingly, it hides bugs
});
```

```
⭐⭐ THE THREE PHASES — and only bubbling matters day to day

⭐   CAPTURE   window -> ... -> target   (addEventListener(..., true))
⭐   TARGET    the element itself
⭐   BUBBLE    target -> ... -> window   ⭐ THE DEFAULT

⭐⭐ ⇒ DELEGATION: put ONE listener on the container, not 500 on rows.
⭐   list.addEventListener("click", e => {
⭐     const row = e.target.closest("[data-id]");   // ⭐ closest() is the trick
⭐     if (!row) return;
⭐     open(row.dataset.id);
⭐   });
⭐   ⇒ ⭐ works for rows added LATER — no re-binding after a re-render.
⭐     React uses exactly this internally.
```

| ⭐ Trap | |
|---|---|
| **Listeners keep objects alive** | ⭐⭐ Every `addEventListener` on `window`/`document` that is never removed is a leak, and it holds the whole closure. `AbortController` removes a batch at once: `addEventListener(ev, fn, { signal })`. |
| **`e.target` vs `e.currentTarget`** | ⭐ `target` is what was actually clicked (possibly a child `<span>`); `currentTarget` is what you attached to. Delegation needs `target` + `closest()`. |
| **Passive listeners** | ⭐ `{ passive: true }` on `scroll`/`touchmove` — tells the browser you will not `preventDefault`, so it need not wait for you before scrolling. |

# Part 3 — ⭐⭐ Layout thrashing, the cost model nobody mentions

```
⭐⭐ THE BROWSER BATCHES YOUR WRITES. IT CANNOT BATCH YOUR READS.

⭐   You set 5 styles ⇒ the browser queues them, plans to lay out ONCE.
⭐   ⭐⭐ THEN YOU READ el.offsetHeight — and the browser must FLUSH
⭐     everything queued and recompute layout SYNCHRONOUSLY to answer.
⭐     That is a FORCED REFLOW.

⭐   ❌ for (const el of rows) {
⭐        el.style.height = (el.offsetHeight + 10) + "px";
⭐      }              ⭐⭐ READ-WRITE-READ-WRITE ⇒ N FORCED REFLOWS
⭐                     ⇒ 500 rows can take SECONDS.

⭐   ✅ const hs = rows.map(el => el.offsetHeight);   // ⭐ READ ALL
⭐      rows.forEach((el,i) => el.style.height = hs[i]+10+"px"); // WRITE ALL
⭐                     ⭐⭐ ONE REFLOW. 100× faster, same output.
```

| ⭐ Forces a reflow when read | |
|---|---|
| `offsetTop/Left/Width/Height`, `clientWidth/Height`, `scrollTop/Height` | `getComputedStyle()`, `getBoundingClientRect()`, `el.focus()` |

> ⭐⭐ **This is the same lesson as N+1 queries.** Interleaving cheap operations with a synchronising
> one turns a batch into a loop of round trips. You already know the fix — **do all the reads, then
> all the writes** — because it is *"fetch the set, then process"* wearing a different hat.

# Part 4 — ⭐⭐ Why frameworks exist

Not because the DOM API is verbose. Because of these.

| ⭐ The real problem | What the DOM gives you |
|---|---|
| **State lives in two places** | ⭐⭐ Your JS variable *and* the DOM text both hold "the count". They drift, and nothing tells you. **This is the killer.** |
| **Every update is a manual diff** | You must work out *which* of 40 elements changed and touch exactly those. |
| **Event handlers must be rebound** | Re-render the list, lose the listeners (unless you delegate). |
| **No composition** | ⭐ There is no unit called "a component" — only functions that happen to make elements. |

```
⭐⭐ THE FRAMEWORK'S ONE PROMISE

⭐   ❌ IMPERATIVE:  "the count changed, so find #count and set its text,
⭐                    and toggle the badge, and update aria-label..."
⭐   ✅ DECLARATIVE: "here is what the screen looks like FOR THIS STATE."
⭐                   ⭐⭐ THE FRAMEWORK WORKS OUT THE MINIMAL CHANGES.

⭐   ⇒ ⭐⭐ ONE SOURCE OF TRUTH. The DOM becomes a PROJECTION of state,
⭐     never a place state is stored. Drift becomes impossible rather
⭐     than merely unlikely.
```

> ⭐ **When you genuinely do not need one:** a static page, a form that posts normally, a page with
> three interactions. Vanilla JS plus delegation is smaller, faster and has no build step. **Knowing
> this is a stronger answer than defaulting to React**, and interviewers ask it precisely because most
> candidates cannot say when the framework is the wrong call.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "why do we use React instead of just the DOM?"**

Reject the shallow answer first — it signals you have thought about it. **It isn't that the DOM API is
verbose; `querySelector` and `append` are fine. The real problem is that state ends up living in two
places. My JavaScript variable holds the count and the DOM text holds the count, and nothing keeps
them in sync — they drift, and there's no error when they do.**

Then the promise, in one sentence. **A framework makes the DOM a projection of state rather than a
place state is stored. I describe what the screen looks like for a given state, and it works out the
minimal changes. Drift becomes impossible instead of merely unlikely.**

Add the cost model, because it shows you understand the layer underneath. **The DOM has a hidden cost:
the browser batches writes but can't batch reads, so reading `offsetHeight` forces it to flush and
recompute layout synchronously. Interleaving reads and writes over five hundred rows turned a
millisecond of work into seconds — it's N+1 queries wearing a different hat, and the fix is the same:
all the reads, then all the writes.**

Close by naming when not to. **For a static page or a form that posts normally, vanilla plus event
delegation is smaller and faster and has no build step. The framework earns its place when there's
enough state that keeping it in sync by hand becomes the job.**
