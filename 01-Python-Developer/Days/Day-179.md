# Part 1 — ⭐⭐ Settings that survive four environments

```
⭐⭐ THREE LAYOUTS, AND THE THIRD IS THE ONE TO USE:

⭐  1. ⭐ ONE `settings.py` WITH `if DEBUG:` BRANCHES.
⭐       ⭐⭐ Day 150's trap: the code path you test is not the code path you
⭐       run. ⭐ Production's branch is exercised for the first time in
⭐       production, by users.
⭐  2. ⭐ `settings/base.py` + `dev.py` + `prod.py`, selected by
⭐       `DJANGO_SETTINGS_MODULE`.
⭐       ⭐ + explicit; ⭐⭐ − prod.py itself is never imported in CI unless you
⭐       make it, so a typo there is found at deploy time.
⭐  3. ⭐⭐ ONE `settings.py`, EVERY DIFFERENCE AS A **VALIDATED
⭐       ENVIRONMENT VALUE**. ⭐ Day 150's rule: a config VALUE, not an
⭐       environment CHECK.
⭐       ⇒ ⭐⭐ Then staging can run the production configuration, and there
⭐         is one code path everywhere.
```

```python
# ⭐ settings.py — pydantic-settings inside Django (Day 150)
class Env(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="APP_", extra="forbid")  # ⭐⭐ typo = boot fail
    environment: Literal["local", "ci", "staging", "production"]
    secret_key: SecretStr
    database_url: PostgresDsn
    redis_url: RedisDsn
    allowed_hosts: list[str]
    debug: bool = False
    email_backend: Literal["console", "smtp"] = "console"   # ⭐⭐ a VALUE, not a branch

env = Env()                                # ⭐ raises at import ⇒ the pod cannot boot
DEBUG = env.debug
SECRET_KEY = env.secret_key.get_secret_value()
ALLOWED_HOSTS = env.allowed_hosts

assert not (env.environment == "production" and DEBUG), "DEBUG in production"   # ⭐⭐
```

```
⭐⭐ THE FIVE SETTINGS THAT ARE SECURITY CONTROLS, NOT PREFERENCES:
⭐   ⭐ `DEBUG=False` — ⭐⭐ True renders every local variable, including
⭐        `settings`, to whoever triggers an error (Day 170).
⭐   ⭐ `ALLOWED_HOSTS` — ⭐⭐ wrong ⇒ Host-header poisoning of password-reset
⭐        links; empty with DEBUG=False ⇒ everything 400s (a good failure).
⭐   ⭐ `SECRET_KEY` — signs sessions and reset tokens. ⭐⭐ Rotating it logs
⭐        everyone out and invalidates outstanding reset links; ⭐ Django
⭐        supports `SECRET_KEY_FALLBACKS` so you can rotate with an overlap
⭐        window (Day 150's rotation rule, built in).
⭐   ⭐ `SESSION_COOKIE_SECURE` / `CSRF_COOKIE_SECURE` — ⭐⭐ NOT on by default.
⭐   ⭐ `SECURE_PROXY_SSL_HEADER` — ⭐⭐ REQUIRED behind a TLS-terminating
⭐        proxy, or Django thinks every request is HTTP and your redirects and
⭐        `secure` cookies misbehave. ⭐ AND it must only be trusted if the
⭐        proxy STRIPS the header from client input — ⭐⭐ otherwise a client
⭐        sets `X-Forwarded-Proto: https` and defeats `SECURE_SSL_REDIRECT`.
⭐
⭐   ⇒ ⭐⭐ `python manage.py check --deploy` AUDITS ALL OF THESE. ⭐ Put it in
⭐        CI as a failing check, not as a thing you occasionally run.
```

# Part 2 — ⭐⭐ Static and media files: the extra problem

```
⭐⭐ FASTAPI SERVICES USUALLY HAVE NO STATIC FILES. DJANGO ALWAYS DOES —
⭐   THE ADMIN ALONE SHIPS CSS, JS AND FONTS.

⭐   ⭐⭐ **STATIC** = files YOU ship (admin CSS, your JS). Collected at build.
⭐   ⭐⭐ **MEDIA**  = files USERS upload (Day 145). ⭐ Completely different
⭐        lifecycle, completely different security posture, ⭐⭐ and conflating
⭐        them is the classic beginner error.

⭐⭐ THE THREE RULES:
⭐  1. ⭐⭐ `collectstatic` RUNS AT **BUILD TIME**, INTO THE IMAGE. ⭐ Not at
⭐       boot — ⭐⭐ ten replicas each writing the same files to a shared
⭐       volume is a race, and it is slow on every restart.
⭐  2. ⭐⭐ `DEBUG=False` STOPS DJANGO SERVING STATIC FILES ENTIRELY. ⭐ The
⭐       classic "my admin has no CSS in production". ⭐⭐ Django's static
⭐       serving is a DEVELOPMENT convenience and is explicitly not for
⭐       production. ⭐ Use WhiteNoise (in-process, fine to a real scale) or a
⭐       CDN in front of object storage.
⭐  3. ⭐⭐ **NEVER SERVE `MEDIA_ROOT` FROM YOUR APP DOMAIN.** ⭐ Day 145: a
⭐       user-uploaded HTML file served from your origin is stored XSS with
⭐       your session cookie. ⭐⭐ Separate origin, `Content-Disposition:
⭐       attachment`, `X-Content-Type-Options: nosniff`, and a content type
⭐       YOU determined.

⭐ ⭐⭐ AND USE A **HASHED** STATIC STORAGE
⭐   (`ManifestStaticFilesStorage`): filenames become
⭐   `app.a1b2c3.css`, so you can cache them forever and a deploy busts the
⭐   cache automatically. ⭐ Without it you are choosing between stale assets
⭐   and no caching. ⭐⭐ It also fails the build if a referenced file is
⭐   missing, which is a free correctness check.
```

```python
# ⭐ media via S3 (Day 145) — presigned, not proxied
DEFAULT_FILE_STORAGE = "storages.backends.s3boto3.S3Boto3Storage"
AWS_S3_FILE_OVERWRITE = False        # ⭐⭐ or two users' uploads collide by name
AWS_DEFAULT_ACL = None               # ⭐⭐ never public-read
AWS_QUERYSTRING_AUTH = True          # ⭐ presigned URLs, short expiry
```

# Part 3 — ⭐ The process model

```bash
gunicorn config.wsgi:application \
  --workers 4 \                    # ⭐ ≈ cores (Day 111) — the GIL is still the GIL
  --threads 4 \                    # ⭐⭐ gthread: I/O-bound Django benefits
  --worker-class gthread \
  --timeout 30 \                   # ⭐⭐ MUST exceed your slowest request or it SIGKILLs
  --graceful-timeout 30 \          # ⭐ Day 149 — time to finish in flight
  --max-requests 2000 \
  --max-requests-jitter 200 \      # ⭐⭐ or every worker recycles at once
  --access-logfile - --error-logfile -   # ⭐ stdout (Day 146)
```

```
⭐⭐ FIVE THINGS THAT ARE DJANGO-SPECIFIC OR EASILY GOT WRONG:
⭐  1. ⭐⭐ CONNECTION MATH (Day 156's Little's Law): workers × threads ×
⭐       `CONN_MAX_AGE` connections. ⭐ 4 × 4 = 16 potential connections per
⭐       pod; ⭐⭐ 10 pods = 160 > Postgres `max_connections` of 100 ⇒ THE
⭐       DATABASE STARTS REFUSING CONNECTIONS, which is a worse outage than
⭐       being slow. ⭐ Use PgBouncer in transaction mode past that point.
⭐  2. ⭐⭐ `CONN_MAX_AGE` — ⭐ Django's default is 0: **a new connection per
⭐       request**, which is a TCP handshake plus TLS plus auth per request.
⭐       ⭐⭐ Set it to 60. ⭐ But with PgBouncer in transaction mode, set it
⭐       back to 0 — ⭐⭐ persistent connections defeat the pooler entirely.
⭐  3. ⭐ `CONN_HEALTH_CHECKS = True` — ⭐⭐ or a persistent connection killed
⭐       by a failover is handed to a request and errors once per worker.
⭐  4. ⭐⭐ EXEC-FORM `CMD` AND PID 1 (Days 083, 149, 151) — unchanged, and
⭐       still the thing that makes every deploy truncate in-flight requests.
⭐  5. ⭐ `--timeout` KILLS THE WORKER WITH SIGKILL. ⭐⭐ It is a watchdog, not
⭐       a request timeout — the request has already consumed the time. ⭐ Real
⭐       timeouts go on the database (`statement_timeout`) and on outbound
⭐       calls (Day 152).
```

# Part 4 — ⭐⭐ Celery, wired the Django way

```python
# config/celery.py
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")
app = Celery("ticketed")
app.config_from_object("django.conf:settings", namespace="CELERY")
app.autodiscover_tasks()                       # ⭐ finds tasks.py in every app
```

```python
@shared_task(bind=True, acks_late=True, retry_backoff=True, retry_jitter=True,
             max_retries=6, time_limit=60, soft_time_limit=50)
def send_confirmation(self, order_id: int, organiser_id: str) -> None:
    #  ⭐⭐ @shared_task, not @app.task — reusable across projects, no import cycle
    with transaction.atomic():
        updated = Order.objects.filter(
            id=order_id, confirmation_sent_at__isnull=True
        ).update(confirmation_sent_at=timezone.now())     # ⭐⭐ idempotency claim
        if not updated:
            return
    mailer.send(...)
```

```
⭐⭐ THE FOUR DJANGO-SPECIFIC CELERY RULES:
⭐  1. ⭐⭐ **ENQUEUE WITH `transaction.on_commit`** (Day 172), ALWAYS:
⭐          transaction.on_commit(lambda: send_confirmation.delay(order.id, org_id))
⭐       ⇒ ⭐ without it the worker reads before your commit and gets
⭐         `DoesNotExist` — ⭐⭐ which "works" after a retry, so it hides as
⭐         intermittent noise until a rollback emails a real customer about an
⭐         order that never existed.
⭐  2. ⭐⭐ PASS IDS AND THE TENANT, NEVER MODEL INSTANCES (Days 142, 160).
⭐       ⭐ A model instance is not JSON-serialisable, is stale by execution,
⭐       and ⭐⭐ the worker has no request, so tenant context is gone unless
⭐       you pass it.
⭐  3. ⭐ WORKERS NEED THE SAME SETTINGS AND THE SAME IMAGE — ⭐⭐ deploy them
⭐       from the SAME digest as the web tier (Day 154), or a task signature
⭐       change means old workers consume new messages.
⭐  4. ⭐⭐ `django-celery-beat` PUTS THE SCHEDULE IN THE DATABASE, so it is
⭐       editable in the admin. ⭐ Nice, ⭐⭐ and it makes the schedule
⭐       UNVERSIONED — someone changes a cron expression in production with no
⭐       code review and no audit beyond `LogEntry` (Day 177). ⭐ Decide
⭐       deliberately; a file-based schedule is reviewable.
⭐   ⇒ ⭐ And Day 159 still applies in full: dead-man monitoring, an
⭐        idempotency key per period, and no reliance on beat for correctness.
```

# Part 5 — ⭐ The deployment checklist

```
⭐⭐ WORK THIS BEFORE THE FIRST REAL USER. Each line is one earlier day.
⭐
⭐  ⭐ CONFIG
⭐   □ `check --deploy` passes IN CI · □ `DEBUG=False` asserted at boot
⭐   □ `ALLOWED_HOSTS` set · □ `SECURE_PROXY_SSL_HEADER` set AND the proxy
⭐        strips the client's version
⭐   □ ⭐⭐ secrets from the environment, `SecretStr`, never in the image
⭐
⭐  ⭐ DATABASE
⭐   □ ⭐⭐ migrations as a JOB, never at container start (Days 138, 173)
⭐   □ `CONN_MAX_AGE` set consistently with your pooler
⭐   □ ⭐⭐ workers × threads × pods < `max_connections`
⭐   □ `statement_timeout` and `lock_timeout` set
⭐
⭐  ⭐ PROCESS
⭐   □ exec-form CMD; ⭐⭐ `docker stop` exits in under a second
⭐   □ `preStop` sleep > LB propagation (Day 149)
⭐   □ grace period > longest request AND > longest Celery task
⭐   □ ⭐ `/healthz` checks NOTHING; `/readyz` checks `SELECT 1`, cached
⭐
⭐  ⭐ ASSETS
⭐   □ `collectstatic` at BUILD · □ hashed storage · □ WhiteNoise or CDN
⭐   □ ⭐⭐ media on a separate origin, `attachment`, `nosniff`
⭐
⭐  ⭐ OBSERVABILITY (Days 146–148)
⭐   □ JSON logs to stdout with request id, trace id and VERSION
⭐   □ ⭐⭐ `PYTHONUNBUFFERED=1` — or `docker logs` is empty during the incident
⭐   □ metrics with a version label · □ traces joined by `trace_id`
⭐   □ ⭐⭐ five alerts, one of them on ABSENCE
⭐
⭐  ⭐ THE FIVE-MINUTE PROOFS
⭐   □ ⭐⭐ deploy under load ⇒ ZERO 5xx
⭐   □ ⭐⭐ roll back under load, TIMED (under 60 s)
⭐   □ stop the database ⇒ your error shape, `/readyz` 503, `/healthz` 200
⭐   □ ⭐ kill a Celery worker mid-task ⇒ redelivered, no double effect
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `if DEBUG:` branches for environment differences | The path you test isn't the path you run. Use validated config values. |
| `settings.py` with raw `os.environ` | No validation; a typo'd name is an unused module attribute nothing reports. |
| Never running `check --deploy` | It audits exactly the settings that are security controls. Put it in CI. |
| Missing `SECURE_PROXY_SSL_HEADER` behind a TLS proxy | Django thinks everything is HTTP; redirects and secure cookies misbehave. |
| Trusting `X-Forwarded-Proto` the proxy doesn't strip | A client sets it and defeats `SECURE_SSL_REDIRECT`. |
| `collectstatic` at container start | Ten replicas race on a shared volume, and every restart is slow. |
| Expecting Django to serve static with `DEBUG=False` | It won't. That's the "admin has no CSS" bug. Use WhiteNoise or a CDN. |
| Serving user uploads from your app origin | An uploaded HTML file is stored XSS with your session cookie. |
| Unhashed static storage | Choose between stale assets and no caching. Use `ManifestStaticFilesStorage`. |
| `AWS_DEFAULT_ACL` left public-read | Every upload is world-readable. |
| Ignoring workers × threads × pods vs `max_connections` | The database refuses connections — worse than being slow. |
| Leaving `CONN_MAX_AGE = 0` | A TCP handshake, TLS and auth on every request. |
| `CONN_MAX_AGE > 0` behind PgBouncer transaction mode | Persistent connections defeat the pooler entirely. |
| No `CONN_HEALTH_CHECKS` | A connection killed by failover errors once per worker. |
| Treating gunicorn `--timeout` as a request timeout | It's a SIGKILL watchdog; the time is already spent. Timeouts go on the DB and outbound calls. |
| `--max-requests` without jitter | Every worker recycles simultaneously. |
| `.delay()` without `on_commit` | The worker reads before commit — intermittent `DoesNotExist`, then a real one. |
| Passing model instances to tasks | Not serialisable, stale, and the tenant context is gone. |
| Workers deployed from a different image than the web tier | Old workers consume new messages during a rollout. |
| `django-celery-beat` without a decision | The schedule becomes unversioned and unreviewable. |

## Interview questions

**Q: How do you structure Django settings for four environments?**

> One `settings.py`, with every difference as a validated environment *value* rather than an
> environment check. `if DEBUG:` branches mean the code path I test isn't the code path I run — the
> production branch is exercised for the first time in production, by users. Split settings modules
> are better but have a subtler version of the same problem: `prod.py` is never imported in CI unless
> you make it, so a typo there is found at deploy time. So I put `pydantic-settings` inside
> `settings.py` with `extra="forbid"` and required fields, which makes a missing or misspelled
> variable a boot failure — and a pod that can't boot gets rolled back automatically, whereas a pod
> that boots and 500s later is an incident. Then boot-time assertions for the things that are
> security controls, and `check --deploy` as a failing check in CI rather than something you
> occasionally run.

**Q: What's different about deploying Django versus a FastAPI service?**

> Mostly the names are different and the rules are identical — but there's one genuinely extra
> problem: static files. A FastAPI service often has none; Django always does, because the admin
> ships CSS and JavaScript. Three rules there. `collectstatic` runs at build time into the image, not
> at boot, because ten replicas writing the same files to a shared volume is a race and slow on every
> restart. `DEBUG=False` stops Django serving static files entirely, which is the classic "my admin
> has no CSS in production" — that serving is explicitly a development convenience, so you need
> WhiteNoise or a CDN. And media — user uploads — is a completely different thing with a different
> security posture: never served from your app origin, because an uploaded HTML file there is stored
> XSS with your session cookie.

**Q: How do you size gunicorn and the connection pool?**

> Little's Law first: if I need six hundred requests per second and p50 is fifty milliseconds, I need
> about thirty concurrent slots, which is workers times threads. Then the constraint people miss —
> workers times threads times pods is my potential connection count, and if that exceeds Postgres's
> `max_connections`, the database starts *refusing* connections, which is a much worse outage than
> being slow. Four workers, four threads, ten pods is a hundred and sixty against a default of a
> hundred. Past that I put PgBouncer in transaction mode in front. And there's a coupling: Django's
> `CONN_MAX_AGE` defaults to zero, meaning a new connection per request with a handshake and auth
> each time, so I'd set it to sixty — unless I'm behind PgBouncer in transaction mode, where
> persistent connections defeat the pooler and it goes back to zero. I'd also set
> `CONN_HEALTH_CHECKS`, or a connection killed by a failover errors once per worker.

**Q: How do you wire Celery into Django correctly?**

> `@shared_task` rather than `@app.task` to avoid import cycles, `autodiscover_tasks`, and settings
> under a `CELERY` namespace. Then four rules. Always enqueue with `transaction.on_commit` — without
> it the worker reads before your commit and gets `DoesNotExist`, which "works" after a retry so it
> hides as intermittent noise until a rollback emails a real customer about an order that never
> existed. Pass ids and the tenant id, never model instances, because instances aren't serialisable,
> are stale by execution time, and the worker has no request so tenant context is gone. Deploy
> workers from the same image digest as the web tier, or old workers consume new messages during a
> rollout. And I'd think twice about `django-celery-beat`: putting the schedule in the database makes
> it editable in the admin, which also makes it unversioned and unreviewable — someone can change a
> cron expression in production with no code review.

## 🎙️ Articulation drill

**Two minutes: "Walk me through deploying a Django app."**

Say up front that most of it is framework-agnostic and name the parts that aren't. Settings as
validated values with a boot failure on anything missing, and `check --deploy` as a CI gate. Then
static files as the genuinely extra problem, with the three rules and the security one stated
sharply — user uploads never from your app origin, because that's stored XSS with your session
cookie. Then the process model, and lead with the arithmetic rather than the flags: workers times
threads times pods against `max_connections`, because exceeding it means the database refuses
connections, which is worse than slow. Celery in one line — `on_commit`, ids not instances, same
image digest. Close on the proofs rather than the config: **deploy under load with zero 5xx, and a
rollback you have actually timed.**
