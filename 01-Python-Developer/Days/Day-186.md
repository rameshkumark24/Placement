# Part 1 — ⭐ The process model, and why `max_connections` is a memory number

```
⭐⭐ POSTGRES IS NOT ONE PROGRAM. It is a family of processes.

⭐   postmaster ──────────── the supervisor. Listens on 5432. Forks.
⭐     ├── backend (you)      ⭐⭐ ONE OS PROCESS PER CONNECTION.
⭐     ├── backend (you)
⭐     ├── backend (them)
⭐     ├── background writer  ⭐ trickles dirty pages out to disk
⭐     ├── checkpointer       ⭐ Part 5
⭐     ├── WAL writer         ⭐ Part 4
⭐     ├── autovacuum launcher ⭐ Day 194
⭐     └── stats collector
⭐
⭐⭐ ONE PROCESS PER CONNECTION. Not a thread. Not a coroutine. A fork().
```

```
⭐⭐ WHY THAT ONE DESIGN DECISION EXPLAINS SO MUCH:

⭐   ⭐ A CONNECTION IS EXPENSIVE TO CREATE. fork() + backend startup ≈
⭐        1–3 ms of pure overhead. ⇒ ⭐⭐ this is WHY connection pools exist.
⭐        Not as an optimisation — as the difference between a working
⭐        service and one that spends its life forking.
⭐
⭐   ⭐ A CONNECTION IS EXPENSIVE TO *KEEP*. Each backend has its own
⭐        `work_mem` allowance, its own catalogue cache, its own plan cache.
⭐        ⭐⭐ BUDGET ~5–10 MB OF PRIVATE MEMORY PER IDLE CONNECTION, and far
⭐        more under a sort.
⭐        ⇒ ⭐⭐ `max_connections = 1000` IS NOT A CONFIGURATION, IT IS A
⭐          PROMISE TO ALLOCATE SEVERAL GIGABYTES YOU DO NOT HAVE.
⭐
⭐   ⭐ A CRASHING BACKEND CANNOT CORRUPT ANOTHER — separate address
⭐        spaces. ⭐⭐ But it CAN take the whole cluster down: Postgres
⭐        responds to a backend crash by restarting *everything*, because
⭐        it cannot know what shared memory the dead process was mutating.
⭐
⭐   ⭐ ⭐⭐ CONTEXT SWITCHING IS REAL. 500 active backends on 8 cores is not
⭐        "500 concurrent queries", it is 8 concurrent queries and 492
⭐        processes fighting for the runqueue. Throughput goes DOWN.
```

```
⭐⭐ THE ARITHMETIC FROM DAY 179, NOW WITH ITS REASON:

⭐   8 gunicorn workers × pool_size 5 × 3 app instances = 120 connections
⭐   + Celery: 4 workers × pool 5 × 2 instances               = 40
⭐   + your psql, the metrics exporter, the migration job     ≈ 10
⭐   ─────────────────────────────────────────────────────────────
⭐                                                            = 170
⭐   ⭐⭐ AND `max_connections` DEFAULTS TO 100.
⭐   ⇒ ⭐⭐ THE 101st IS NOT SLOW. IT IS *REFUSED*:
⭐        FATAL: sorry, too many clients already
⭐   ⭐ Which surfaces in your app as a 500 at boot, during the deploy,
⭐     when every instance opens its pool at once.
```

> ⭐⭐ **The rule: raise `max_connections` and you buy refusals-turn-into-thrashing. The real fix is a
> transaction pooler (PgBouncer) in front, so 1,000 client connections share 25 server backends.**
> ⭐ Day 197 does this properly.

# Part 2 — ⭐⭐ The page: the unit everything is measured in

```
⭐⭐ POSTGRES DOES NOT READ ROWS. IT READS 8 KB PAGES.

⭐   ┌──────────────────────────────── 8192 bytes ─────────┐
⭐   │ PageHeader (24 B)                                   │
⭐   │ ItemId array →→→ (4 B each, one per tuple)          │
⭐   │                                                     │
⭐   │              ← free space →                         │
⭐   │                                                     │
⭐   │ ←←← tuples grow up from the bottom                  │
⭐   │ [tuple 3][tuple 2][tuple 1]                         │
⭐   │ special space (index pages use this)                │
⭐   └─────────────────────────────────────────────────────┘
⭐
⭐⭐ CONSEQUENCE 1: reading ONE row reads 8 KB. There is no smaller read.
⭐⭐ CONSEQUENCE 2: rows on the SAME page are effectively free once one of
⭐     them is fetched. ⇒ ⭐⭐ THIS IS THE ENTIRE BASIS OF "CLUSTERING" AND
⭐     OF WHY INDEX *ORDER* MATTERS (Day 190).
⭐⭐ CONSEQUENCE 3: a row cannot exceed a page ⇒ big values go to TOAST.
```

```
⭐⭐ A TUPLE IS BIGGER THAN YOU THINK. Per row:
⭐   23 bytes of tuple header (xmin, xmax, ctid, flags…) ⭐ Day 194 needs
⭐        every one of these
⭐   + padding to 8-byte alignment
⭐   + a null bitmap if any column is nullable
⭐   + your data, also individually aligned
⭐
⭐   ⭐⭐ SO COLUMN ORDER CHANGES TABLE SIZE. Really:
⭐        (bool, bigint, bool, bigint, bool)  → 40 bytes/row  ⭐ padding
⭐        (bigint, bigint, bool, bool, bool)  → 27 → 32 bytes ⭐ same data
⭐   ⭐ ~20% on a billion-row table. ⭐⭐ Order columns widest-first when the
⭐     table is huge; ignore this entirely when it is not. Knowing WHEN a
⭐     micro-fact applies is the skill.
```

```
⭐⭐ TOAST — The Oversized-Attribute Storage Technique.
⭐   ⭐ A value over ~2 KB is compressed, and if still large, sliced into
⭐     chunks in a hidden side table.
⭐   ⭐⭐ THE PRACTICAL CONSEQUENCE NOBODY IS TAUGHT:
⭐        `SELECT id, name FROM articles`     → never touches TOAST 🚀
⭐        `SELECT * FROM articles`            → detoasts EVERY body 🐌
⭐   ⇒ ⭐⭐ `SELECT *` IS NOT "SLIGHTLY WASTEFUL" ON A TABLE WITH A LARGE
⭐     TEXT OR JSONB COLUMN. It is a second table scan and a decompression
⭐     pass. ⭐ This is the concrete, physical reason behind the advice you
⭐     have been given since Day 135 as a style rule.
⭐   ⭐ In SQLAlchemy: `deferred()` / `load_only()` are TOAST controls.
```

# Part 3 — ⭐⭐ Shared buffers, and why a timing without a cache state is meaningless

```
⭐⭐ THE READ PATH — three places a page can be:

⭐   your query
⭐     ↓ needs page 4,712 of table `orders`
⭐   ┌─────────────────────────┐
⭐   │ SHARED BUFFERS          │  ⭐ Postgres's own cache, in shared memory
⭐   │ (shared_buffers = 4GB)  │  ⭐⭐ HIT → ~100 ns. Nothing to see here.
⭐   └─────────────────────────┘
⭐     ↓ miss → read()
⭐   ┌─────────────────────────┐
⭐   │ OS PAGE CACHE           │  ⭐ the kernel's cache of the same file
⭐   │                         │  ⭐⭐ HIT → ~10 µs. Postgres calls this a
⭐   └─────────────────────────┘     "read" and CANNOT TELL IT FROM DISK.
⭐     ↓ miss
⭐   ┌─────────────────────────┐
⭐   │ DISK                    │  ⭐ NVMe ~100 µs · ⭐⭐ EBS gp3 ~1 ms
⭐   └─────────────────────────┘  ⭐⭐ network storage is 10× worse and it
⭐                                  is what you have in the cloud
```

```python
# ⭐⭐ THE MEASUREMENT THAT MAKES TIMINGS MEAN SOMETHING
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;

#  Buffers: shared hit=3 read=1841        ⭐⭐ ← THE LINE THAT MATTERS
#           ^^^^^^^^^  ^^^^^^^^^
#           in Postgres  NOT in Postgres (may still be in OS cache)

# ⭐ 1841 × 8 KB = 14 MB read to answer one user's orders.
# ⭐⭐ RUN IT AGAIN: shared hit=1844 read=0 → now 40× faster, SAME QUERY.
#    ⇒ ⭐⭐ "IT'S FAST NOW" AFTER A SECOND RUN MEANS NOTHING. YOU MEASURED
#      THE CACHE, NOT THE QUERY.
```

> ⭐⭐ **This is the single most common self-deception in database work: running a query twice,
> seeing 8 ms, and concluding it is fine — when the first run against a cold cache, which is what
> your users get at 3 a.m. after a failover, takes 900 ms.** ⭐ Always report `BUFFERS`, always say
> whether it was warm.

```
⭐⭐ SIZING, briefly, because two numbers do 90% of the work:
⭐   ⭐ shared_buffers ≈ 25% of RAM. ⭐⭐ NOT 80% — the OS page cache is
⭐        doing real work too, and doubling up wastes memory on two copies
⭐        of the same page ("double buffering").
⭐   ⭐ effective_cache_size ≈ 50–75% of RAM. ⭐⭐ THIS ONE ALLOCATES
⭐        NOTHING. It is a HINT TO THE PLANNER about how much caching to
⭐        assume — and it is the setting that most often decides whether
⭐        you get an index scan or a sequential scan (Day 189).
⭐   ⭐ ⭐⭐ A DEFAULT `shared_buffers` OF 128 MB IS STILL SHIPPED BY MANY
⭐        DISTRIBUTIONS. Check yours before you tune a single query.
```

# Part 4 — ⭐⭐ WAL: what "committed" actually costs

```
⭐⭐ THE NAIVE MENTAL MODEL: COMMIT → write the row to the table file.
⭐⭐ THE TRUTH:               COMMIT → write a WAL RECORD, fsync IT, return.
⭐                            The table file is updated LATER, lazily.

⭐   INSERT:
⭐     1. find/pin a page in shared buffers, add the tuple  ⭐ memory only
⭐     2. append a WAL record describing the change         ⭐ WAL buffer
⭐     3. mark the page DIRTY                               ⭐ memory only
⭐   COMMIT:
⭐     4. ⭐⭐ fsync THE WAL UP TO THIS POINT. ← the durability moment
⭐     5. return "COMMIT" to the client
⭐   LATER:
⭐     6. background writer / checkpointer writes the dirty page out
```

```
⭐⭐ WHY WRITE-AHEAD AT ALL? Because a crash between two 8 KB page writes
⭐   leaves the file inconsistent, and there is no way to know which half
⭐   landed. ⭐ The WAL is SEQUENTIAL, APPEND-ONLY, and REPLAYABLE:
⭐   ⇒ ⭐⭐ RECOVERY = "REPLAY THE WAL FROM THE LAST CHECKPOINT."
⭐   ⇒ ⭐⭐ AND THE SAME MECHANISM, SHIPPED ELSEWHERE, IS REPLICATION
⭐     (Day 201) AND POINT-IN-TIME RECOVERY. One log, three features.
```

```
⭐⭐ THE NUMBER THAT CHANGES HOW YOU WRITE CODE:
⭐   ⭐ AN fsync IS ~0.5–5 ms AND IT DOES NOT GET FASTER WITH A BIGGER
⭐     TRANSACTION.
⭐
⭐   1000 INSERTs, autocommit  → 1000 fsyncs → ~3 s   🐌
⭐   1000 INSERTs, one txn     →    1 fsync  → ~30 ms 🚀   ⭐⭐ 100×
⭐   1000 rows, one INSERT     →    1 fsync  → ~8 ms
⭐   COPY                      →    1 fsync  → ~3 ms
⭐
⭐   ⇒ ⭐⭐ THIS IS *WHY* `bulk_insert_mappings`, `executemany` AND
⭐     `bulk_create` ARE FAST. Not "less Python overhead" — FEWER fsyncs.
⭐     ⭐ You used them on Day 172 knowing they were faster. Now you know
⭐     the unit: disk flushes, not function calls.
```

```
⭐⭐ synchronous_commit — THE ONE DURABILITY DIAL, STATED HONESTLY:
⭐   ⭐ `on`  (default): COMMIT returns after the WAL is on disk.
⭐        ⇒ if the machine loses power, ⭐⭐ YOU LOSE NOTHING.
⭐   ⭐ `off`: COMMIT returns immediately; WAL is flushed within ~200 ms.
⭐        ⇒ ⭐⭐ ON A CRASH YOU LOSE THE LAST ~200 ms OF COMMITTED
⭐          TRANSACTIONS — ⭐ BUT THE DATABASE IS NOT CORRUPTED. That
⭐          distinction is the whole point: it is a DURABILITY trade, not
⭐          an INTEGRITY trade.
⭐   ⇒ ⭐⭐ IT CAN BE SET PER TRANSACTION. So: `on` for payments, `off` for
⭐     the analytics-events table. ⭐ Almost nobody knows this, and it is
⭐     the correct answer to "our event ingestion is fsync-bound".
```

```
⭐ full_page_writes: after a checkpoint, the FIRST change to a page writes
⭐   the ENTIRE 8 KB page into the WAL, not just the delta — insurance
⭐   against a torn page. ⭐⭐ CONSEQUENCE: WAL VOLUME SPIKES IMMEDIATELY
⭐   AFTER EVERY CHECKPOINT, so shortening `checkpoint_timeout` to "spread
⭐   the load" can multiply your WAL and make things worse. ⭐ A very
⭐   common tuning mistake, made with good intentions.
```

# Part 5 — ⭐ Checkpoints, and the sawtooth in your p99

```
⭐⭐ A CHECKPOINT IS: "flush every dirty page, then record that the WAL
⭐   before this point is no longer needed for recovery."

⭐   Triggered by: ⭐ `checkpoint_timeout` (default 5 min) — time
⭐                 ⭐ `max_wal_size` (default 1 GB) — volume
⭐                 ⭐ an explicit CHECKPOINT, a shutdown, a base backup

⭐⭐ THE SYMPTOM, WHICH YOU WILL SEE ON A GRAPH LONG BEFORE YOU KNOW WHY:
⭐   p99 latency ─────╮   ╭────╮   ╭────╮   ╭────
⭐                    ╰───╯    ╰───╯    ╰───╯
⭐                    ⭐⭐ a spike every ~5 minutes, in a service whose
⭐                       traffic is perfectly flat.
⭐   ⇒ ⭐ Checkpoint dumps a gigabyte of dirty pages at the disk; every
⭐     query competes with it for IO.
⭐
⭐⭐ THE FIX IS COUNTER-INTUITIVE: make checkpoints LESS frequent and
⭐   SMOOTHER, not more frequent.
⭐   ⭐ `checkpoint_completion_target = 0.9` → spread the writes over 90%
⭐        of the interval instead of dumping them. ⭐ Default since PG 14.
⭐   ⭐ `max_wal_size` LARGER (e.g. 8 GB) → fewer, and full-page-write
⭐        volume drops. ⭐⭐ The cost is a longer crash recovery. That is
⭐        the actual trade: RECOVERY TIME vs STEADY-STATE SMOOTHNESS.
⭐   ⭐ Watch `pg_stat_bgwriter`: ⭐⭐ `checkpoints_req` MUCH LARGER THAN
⭐        `checkpoints_timed` MEANS YOUR `max_wal_size` IS TOO SMALL.
⭐        One query, one verdict.
```

# Part 6 — ⭐ Where your Python actually sits

```python
# ⭐⭐ psycopg3 speaks the Postgres wire protocol directly. No ODBC, no
#    JDBC-equivalent. Your driver IS the client.

# ⭐ SIMPLE QUERY PROTOCOL:    one string → parse, plan, execute, return
# ⭐ EXTENDED QUERY PROTOCOL:  Parse → Bind → Execute
#      ⇒ ⭐⭐ THIS IS WHY PARAMETERISED QUERIES ARE INJECTION-PROOF.
#        The SQL text and the parameter values travel in SEPARATE
#        PROTOCOL MESSAGES. There is no string to escape, because there
#        is no string. ⭐ Not "escaping done well" — a different channel.
```

```python
# ⭐⭐ THE MEMORY TRAP YOU HAVE ALREADY HIT WITHOUT NAMING IT
cur.execute("SELECT * FROM events")          # ⭐⭐ 40M rows
rows = cur.fetchall()                        # ⭐⭐ ALL OF IT. IN RAM. OOM.

# ⭐ AND EVEN THIS DOES NOT HELP BY DEFAULT:
for row in cur:                              # ⭐⭐ the CLIENT already
    ...                                      #    buffered everything

# ⭐⭐ THE FIX: A SERVER-SIDE CURSOR. Named cursor ⇒ the server keeps the
#    result set and streams it in batches.
with conn.cursor(name="stream") as cur:      # psycopg3: server-side
    cur.itersize = 2000
    for row in cur.execute("SELECT * FROM events"):
        ...                                  # ⭐ constant memory

# ⭐ SQLAlchemy's spelling of the same thing:
for row in session.execute(stmt).yield_per(1000):   # ⭐⭐ and it also
    ...                                             #    stops the ORM
                                                    #    identity map
                                                    #    from retaining
                                                    #    every object
```

```
⭐⭐ PREPARED STATEMENTS, AND THE TRAP THAT BITES EVERY PGBOUNCER USER:
⭐   ⭐ psycopg3 auto-prepares a statement after it is seen 5 times.
⭐        ⇒ parse+plan happens once, not per execution.
⭐   ⭐⭐ A PREPARED STATEMENT LIVES IN *THAT BACKEND'S* SESSION STATE.
⭐   ⇒ ⭐⭐ PUT PGBOUNCER IN TRANSACTION MODE IN FRONT AND THE NEXT
⭐     EXECUTE LANDS ON A DIFFERENT BACKEND:
⭐        ERROR: prepared statement "_pg3_0" does not exist
⭐   ⭐ Fix: `prepare_threshold=None`, or pgbouncer session mode, or
⭐     `max_prepared_statements` on newer pgbouncer.
⭐   ⭐⭐ THE GENERAL RULE THIS INSTANCE TEACHES: A TRANSACTION POOLER
⭐     BREAKS EVERYTHING THAT IS SESSION STATE — prepared statements,
⭐     `SET`, advisory locks (Day 159!), `LISTEN/NOTIFY`, temp tables.
⭐     ⭐ Remember this on Day 197; it is the whole content of that day.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Raising `max_connections` to fix "too many clients" | Each connection is a process with private memory. Pool, or put PgBouncer in front. |
| Treating a connection as cheap | It is a `fork()` plus ~5–10 MB. This is why pools exist. |
| Assuming more connections = more throughput | Past core count, throughput drops from context switching. |
| Timing a query on the second run | You measured the buffer cache. Report `BUFFERS`, state warm or cold. |
| `shared_buffers` at 80% of RAM | Double-buffers with the OS cache. ~25% is the starting point. |
| Ignoring `effective_cache_size` | It allocates nothing but often decides index scan vs seq scan. |
| `SELECT *` on a table with a large text/JSONB column | Forces detoasting of every row — a second read pass plus decompression. |
| Believing COMMIT writes the table file | COMMIT writes and fsyncs the *WAL*. Pages are flushed later. |
| Inserting 1,000 rows in autocommit | 1,000 fsyncs. One transaction is ~100× faster. |
| Thinking `synchronous_commit=off` risks corruption | It risks losing the last ~200 ms. Integrity is unaffected. |
| Shortening `checkpoint_timeout` to smooth IO | More checkpoints means more full-page writes and more WAL. Do the opposite. |
| Ignoring `checkpoints_req` vs `checkpoints_timed` | `req` dominating means `max_wal_size` is too small. |
| `fetchall()` on a large result | Buffers everything client-side. Use a named/server-side cursor or `yield_per`. |
| Using prepared statements through PgBouncer transaction mode | The statement lives in one backend's session. So do `SET`, advisory locks and `LISTEN`. |

## Interview questions

**Q: What actually happens when you run `COMMIT`?**

> The change was already applied to a page in shared buffers and described in a WAL record. `COMMIT`
> writes a commit record and then `fsync`s the WAL up to that point — and *that* is the durability
> moment; the table file itself is written later by the checkpointer or background writer. Two things
> follow from that. First, durability costs one disk flush of about half a millisecond to a few
> milliseconds, and it doesn't get cheaper with a larger transaction, which is the real reason batch
> inserts are a hundred times faster than autocommit inserts — you're paying one fsync instead of a
> thousand, not saving Python overhead. Second, recovery is just "replay the WAL from the last
> checkpoint", and once you have a replayable log of every change, streaming it to another machine
> gives you replication and keeping it around gives you point-in-time recovery. One mechanism, three
> features.

**Q: Why do connection pools matter so much for Postgres specifically?**

> Because a Postgres connection is an operating-system process, not a thread. Creating one costs a
> `fork` plus backend startup, and keeping one idle costs several megabytes of private memory for its
> catalogue cache, plan cache and `work_mem` allowance. So connections are expensive to create *and*
> expensive to hold, which is a worse combination than most databases. That's why the arithmetic
> matters: workers times pool size times instances, plus Celery, plus your own psql, has to stay
> under `max_connections` — and exceeding it isn't slowness, it's `FATAL: sorry, too many clients`,
> a hard refusal that usually shows up during a deploy when every instance opens its pool at once.
> Raising `max_connections` trades refusals for thrashing, because past core count you have more
> processes fighting for the runqueue rather than more work getting done. The real answer above a few
> hundred clients is a transaction pooler like PgBouncer, so a thousand client connections share
> twenty-five backends.

**Q: A query takes 900 ms the first time and 8 ms after that. What do you conclude?**

> Almost nothing yet, and that's the point. The second run measured the buffer cache, not the query.
> I'd run `EXPLAIN (ANALYZE, BUFFERS)` and read the `shared hit` versus `read` numbers: if it's
> reading two thousand blocks cold, that's sixteen megabytes of IO to answer one request, and on
> network-attached cloud storage where a read is closer to a millisecond than a hundred microseconds,
> that's exactly the 900 ms. Then the question becomes whether the cold path matters — and it does,
> because it's what your users get after a failover, after a deploy that restarted the database, or
> for any data outside the working set. The habit I'd want on the team is that nobody reports a query
> timing without saying whether the cache was warm.

**Q: You see a latency spike every five minutes on a service with flat traffic. Where do you look?**

> Checkpoints. Five minutes is `checkpoint_timeout`'s default, and a checkpoint flushes every dirty
> page, so queries compete with a burst of write IO. I'd confirm with `pg_stat_bgwriter` and
> `log_checkpoints`. The fix is counter-intuitive: make checkpoints less frequent and smoother, not
> more frequent — `checkpoint_completion_target` near 0.9 to spread the writes across the interval,
> and a larger `max_wal_size`. More frequent checkpoints actively make it worse, because the first
> write to a page after a checkpoint puts the whole 8 KB page into the WAL, so shortening the interval
> multiplies WAL volume. The cost of the fix is a longer crash recovery, and that's the honest trade
> to state: recovery time against steady-state smoothness.

**Q: Why is a parameterised query immune to SQL injection?**

> Because with the extended query protocol the SQL text and the parameter values are separate
> protocol messages. The server parses and plans the statement with placeholders, then binds values
> into it — the values are never part of a string that gets parsed as SQL, so there is nothing to
> escape. That's a stronger guarantee than careful escaping: escaping can be got wrong, and a
> separate channel can't. It also explains where the protection stops. The moment you build the SQL
> text yourself — f-strings into `text()`, `RawSQL`, a dynamic table name — you're back in the single
> channel and the guarantee is gone, which is why identifiers can't be parameterised and have to be
> validated against an allowlist instead.

## 🎙️ Articulation drill

**Two minutes: "What happens inside Postgres when I run a query?"**

Lead with the process model, because it explains the operational world you already live in: one OS
process per connection, which is why pools exist and why `max_connections` is a memory budget rather
than a preference. Then the page — 8 KB, the unit of everything, and the reason `SELECT *` on a table
with a big text column is a second read pass. Then the three cache layers, and land the discipline
point: **a timing without a cache state is not a measurement**, so report `BUFFERS` and say whether it
was warm. Then the write path, and the sentence that pays for the whole day: commit doesn't write your
table, it fsyncs the WAL — which is why batching is a hundred times faster and why the same log gives
you replication and PITR for free. Close on checkpoints and the counter-intuitive fix, because it's the
kind of thing that separates people who have run a database from people who have read about one.
