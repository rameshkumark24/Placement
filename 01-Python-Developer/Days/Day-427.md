**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a prompt is the highest-leverage, least-governed artefact in your system —
> it changes behaviour more than most code changes, it is edited by people who do not open a pull

# Part 1 — Why this is a governance problem, not a tooling one

```
⭐ ⭐⭐ A PROMPT CHANGE CAN CHANGE EVERY OUTPUT YOUR PRODUCT
⭐   PRODUCES. ⭐ And in most teams it:
⭐   ⭐ is edited in a web UI or a database row,
⭐   ⭐ by someone who is not an engineer,
⭐   ⭐ with no review,
⭐   ⭐ no test,
⭐   ⭐ no version identifier on the request,
⭐   ⭐⭐ AND NO WAY TO ANSWER "WHAT CHANGED AT 14:32?"

⭐⭐ ⇒ WHICH IS PRECISELY DAY 372's FINDING: ***CONFIG CAUSES A
⭐   LARGE SHARE OF MAJOR OUTAGES BECAUSE IT BYPASSES REVIEW,
⭐   TESTS, CANARIES AND ROLLBACK.*** ⭐ A prompt is config with
⭐   more leverage than any config you have ever shipped.

⭐ ⭐⭐ AND THE HONEST TENSION, WHICH IS WHY THIS IS HARD: ⭐ the
⭐   people best at writing prompts — support leads, domain
⭐   experts, product managers — ⭐⭐ ARE OFTEN NOT THE PEOPLE
⭐   COMFORTABLE OPENING A PR. ⭐ So "put it in git" is correct
⭐   and insufficient; ⭐⭐ THE REAL ANSWER IS A PATH THAT IS
⭐   ***BOTH*** GOVERNED AND ACCESSIBLE (PART 5).
```

# Part 2 — ⭐⭐ The minimum viable discipline

```
⭐ ① ⭐⭐ ***PROMPTS LIVE IN VERSION CONTROL***, ⭐ as files, ⭐ with
⭐    typed inputs (Day 423's `StrictUndefined`).
⭐ ② ⭐⭐ ***EVERY PROMPT HAS A VERSION IDENTIFIER***, ⭐ and it
⭐    travels on the request and into the logs, the trace and
⭐    the metrics (Day 420).
⭐    ⭐⭐ WITHOUT THIS YOU CANNOT ATTRIBUTE A QUALITY CHANGE TO
⭐    ANYTHING, AND EVERY INCIDENT REVIEW ENDS IN A SHRUG.
⭐ ③ ⭐ ***A CHANGE REQUIRES AN EVAL RUN*** (Day 425).
⭐ ④ ⭐ ***A CHANGE IS REVIEWED*** by someone other than the
⭐    author.
⭐ ⑤ ⭐⭐ ***A CHANGE IS ROLLED OUT, NOT SWITCHED*** (PART 4).
⭐ ⑥ ⭐⭐ ***A CHANGE EMITS A DEPLOY MARKER*** TO MONITORING
⭐    (DAY 372) — ⭐ so "quality dropped at 14:32" and "prompt
⭐    v11 shipped at 14:31" are visibly adjacent on one graph.

⭐⭐ ⇒ AND THE SIMPLEST VERSION OF THE WHOLE THING: ***THE PROMPT
⭐   FILE'S CONTENT HASH IS THE VERSION.*** ⭐ No registry, no
⭐   database, no manual bump anyone can forget. ⭐⭐ IT CANNOT
⭐   DRIFT FROM WHAT ACTUALLY RAN, WHICH IS THE ONE PROPERTY THAT
⭐   MATTERS.
```

```python
from pathlib import Path
import hashlib, functools

@functools.cache
def load_prompt(name: str) -> tuple[str, str]:
    text = Path(f"prompts/{name}.jinja").read_text(encoding="utf-8")
    version = hashlib.sha256(text.encode()).hexdigest()[:12]
    return text, version          # ⭐⭐ VERSION ***DERIVED***, NEVER
                                  # ⭐   HAND-MAINTAINED

template, prompt_version = load_prompt("invoice_extract")
result = await complete(task="invoice_extract",
                        messages=render(template, doc=doc),
                        prompt_version=prompt_version)   # ⭐⭐ LOGGED
```

# Part 3 — What "a prompt" actually includes

```
⭐⭐ THE VERSION MUST COVER EVERYTHING THAT CHANGES BEHAVIOUR, OR
⭐   IT IS A FALSE COMFORT:
⭐   ⭐ the template text
⭐   ⭐ the few-shot examples (Day 423)
⭐   ⭐⭐ THE OUTPUT SCHEMA (DAY 424 — ***IT IS PART OF THE
⭐     PROMPT***, and people version the text and not the schema)
⭐   ⭐ the model name ***and*** the resolved snapshot (Day 420)
⭐   ⭐ temperature, top-p, max_tokens (Day 418)
⭐   ⭐ the retrieval config — k, chunk size, reranker
⭐     (Days 430, 433)
⭐   ⭐ the tool definitions (Day 438)

⭐⭐ ⇒ SO VERSION THE ***CONFIGURATION OBJECT***, NOT THE STRING.
⭐   ⭐ One `TaskConfig` per task, hashed as a whole.
⭐   ⭐⭐ OTHERWISE SOMEONE CHANGES `k` FROM 5 TO 10, QUALITY
⭐     MOVES, THE PROMPT VERSION IS UNCHANGED, AND YOU SPEND A
⭐     DAY LOOKING IN THE WRONG PLACE.
```

```python
@dataclass(frozen=True, slots=True)
class TaskConfig:
    prompt: str
    schema_name: str
    model: str
    temperature: float
    max_tokens: int
    retrieval_k: int
    reranker: str | None
    examples: tuple[str, ...]

    @property
    def version(self) -> str:      # ⭐⭐ ONE HASH OVER EVERYTHING
        return hashlib.sha256(
            repr(astuple(self)).encode()).hexdigest()[:12]
```

# Part 4 — ⭐⭐ Rolling out a prompt change

```
⭐⭐ ***A PROMPT CHANGE IS A DEPLOY, SO IT GETS DAY 371's
⭐   TREATMENT.***

⭐ ① ⭐ ***OFFLINE EVAL*** — the gate (Day 425). ⭐⭐ NECESSARY AND
⭐    NOT SUFFICIENT: ⭐ your eval set is not your traffic
⭐    distribution.
⭐ ② ⭐⭐ ***SHADOW*** — ⭐ run the new prompt on real traffic,
⭐    ***do not serve it***, log both outputs. ⭐⭐ THE HIGHEST-VALUE
⭐    AND LEAST-USED STEP: ⭐ it costs money and zero risk, and it
⭐    tells you how the change behaves on inputs your eval set
⭐    never imagined.
⭐ ③ ⭐ ***CANARY*** — 5% of traffic, ⭐⭐ WITH THE VERSION AS A
⭐    DIMENSION ON EVERY METRIC. ⭐ Watch quality proxies, not
⭐    just errors (Part 6).
⭐ ④ ⭐ ***RAMP*** — 25%, 50%, 100%, with time to observe at each.
⭐ ⑤ ⭐⭐ ***ROLLBACK IS A CONFIG CHANGE, NOT A DEPLOY*** — ⭐ point
⭐    the pointer at the previous version. ⭐⭐ SECONDS.

⭐⭐ AND THE THREE THINGS THAT MAKE A PROMPT CANARY DIFFERENT
⭐   FROM A CODE CANARY, WHICH IS THE PART PEOPLE GET WRONG:
⭐   ⭐⭐ ① ***THE FAILURE IS USUALLY NOT AN ERROR.*** ⭐ Error rate
⭐      and latency both look fine while the answers get worse.
⭐      ⭐⭐ SO YOUR CANARY MUST WATCH ***QUALITY PROXIES***, ⭐ or
⭐      it is watching the wrong graph entirely.
⭐   ⭐⭐ ② ***THE SIGNAL IS SLOW.*** ⭐ Thumbs-down rates need
⭐      hundreds of samples. ⭐⭐ A FIVE-MINUTE CANARY TELLS YOU
⭐      NOTHING; ⭐ plan hours or a day.
⭐   ⭐ ③ ⭐⭐ USERS IN THE CANARY GET A DIFFERENT PRODUCT
⭐      ***PERSONALITY***. ⭐ For a conversational feature, hold a
⭐      user on one version for their whole session — ⭐⭐ SWITCHING
⭐      MID-CONVERSATION IS VISIBLE AND UNSETTLING.
```

# Part 5 — Letting non-engineers edit safely

```
⭐ ⭐⭐ THE TENSION FROM PART 1, RESOLVED. ⭐ Three options,
⭐   strongest first:

⭐ ① ⭐⭐ ***A GIT-BACKED UI.*** ⭐ The editor writes to a branch and
⭐    opens a PR. ⭐⭐ NON-ENGINEERS GET A TEXTBOX; ENGINEERS GET
⭐    REVIEW, HISTORY, EVALS AND ROLLBACK. ⭐ Best of both, and
⭐    genuinely not much work if you use the GitHub API.
⭐ ② ⭐ ***A PROMPT REGISTRY WITH DISCIPLINE*** — a database
⭐    table, ⭐⭐ BUT WITH AN IMMUTABLE VERSION PER EDIT, A
⭐    REQUIRED EVAL RUN BEFORE ACTIVATION, AN APPROVAL STEP, AND
⭐    AN AUDIT LOG. ⭐ Several hosted tools do this.
⭐    ⭐⭐ THE RISK: THE DISCIPLINE IS OPTIONAL IN MOST TOOLS, AND
⭐    OPTIONAL DISCIPLINE IS ABSENT DISCIPLINE UNDER DEADLINE.
⭐ ③ ⭐ ***A STAGING ENVIRONMENT ANYONE CAN EDIT FREELY***, ⭐ with
⭐    promotion to production as the governed step. ⭐⭐ SIMPLE,
⭐    AND IT KEEPS THE FAST FEEDBACK LOOP THAT MAKES PROMPT
⭐    ITERATION WORK AT ALL.

⭐⭐ ⇒ AND THE NON-NEGOTIABLE UNDERNEATH ALL THREE: ***PRODUCTION
⭐   PROMPTS ARE IMMUTABLE AND ADDRESSED BY VERSION.*** ⭐ You
⭐   never edit the live one. ⭐⭐ YOU PUBLISH A NEW VERSION AND
⭐   MOVE A POINTER — ⭐ which is content-addressing (Day 392) and
⭐   it makes rollback free.
```

# Part 6 — ⭐⭐ Watching quality in production

```
⭐ ⭐⭐ THE PROBLEM: YOU HAVE NO GROUND TRUTH IN PRODUCTION.
⭐   ⭐ So you watch ***proxies***, and the art is picking ones
⭐   that move before your users complain.

⭐ ① ⭐⭐ ***ABSTENTION RATE*** — ⭐ how often it says "I don't
⭐    know". ⭐⭐ THE BEST SINGLE PROXY THERE IS, ⭐ because it moves
⭐    in both directions meaningfully: ⭐ a ***drop*** means it
⭐    started guessing; ⭐ a ***spike*** means retrieval broke.
⭐ ② ⭐ ***SCHEMA-VALID ON FIRST ATTEMPT*** (Day 424's repair
⭐    rate) — ⭐⭐ MOVES IMMEDIATELY AND COSTS NOTHING TO MEASURE.
⭐ ③ ⭐ ***OUTPUT LENGTH DISTRIBUTION*** — ⭐⭐ A SUDDEN SHIFT
⭐    ALMOST ALWAYS MEANS BEHAVIOUR CHANGED, ⭐ and it is the
⭐    earliest signal of a silent model update (Day 420).
⭐ ④ ⭐ ***TOOL-CALL RATE*** (Day 438), ⭐ ***retry rate***,
⭐    ⭐ ***refusal rate***.
⭐ ⑤ ⭐ ***USER SIGNALS*** — thumbs, regenerate clicks,
⭐    ⭐⭐ CONVERSATION ABANDONMENT, ⭐ escalation to a human.
⭐    ⭐⭐ THE REGENERATE CLICK IS THE MOST HONEST ONE YOU HAVE:
⭐    IT COSTS THE USER NOTHING TO EXPRESS AND MEANS "THAT WAS
⭐    NOT GOOD ENOUGH".
⭐ ⑥ ⭐ ***COST AND TOKEN DISTRIBUTIONS*** per version (Day 421).

⭐ ⭐⭐ AND THE ONE THAT CATCHES WHAT NOTHING ELSE DOES: ***RUN
⭐   YOUR EVAL SET AGAINST PRODUCTION CONFIG NIGHTLY.*** ⭐ Same
⭐   prompt, same model alias, same retrieval index.
⭐   ⭐⭐ IT CATCHES THE THING NO CANARY CAN: THE PROVIDER SILENTLY
⭐   MOVING YOUR MODEL SNAPSHOT UNDER A STABLE ALIAS, ⭐ or your
⭐   retrieval index drifting as documents are added (Day 435).
⭐   ⭐ Nothing you deployed changed, ⭐⭐ AND THE PRODUCT GOT
⭐   WORSE — ⭐ that failure is invisible without this.
```

# 💬 Interview

**1. ⭐⭐ "How do you manage prompts?"**
> ⭐ As versioned artefacts, because ⭐⭐ **a prompt is the highest-leverage, least-governed thing in the
> system — it changes behaviour more than most code changes, and in most teams it's edited in a web UI
> by someone who doesn't open a PR, with no review, no test and no version on the request.** ⭐ That's
> exactly the config-is-the-riskiest-change problem: ⭐⭐ **config causes a large share of major outages
> because it bypasses review, tests, canaries and rollback — and a prompt is config with more leverage
> than any config I've shipped.** ⭐ Minimum discipline: in version control, a version identifier on
> every request and in the logs, an eval run to change it, review by someone else, a ramped rollout,
> and a deploy marker on the monitoring graph.

**2. ⭐⭐ "How do you version a prompt?"**
> ⭐⭐ **By hashing the content, so the version is derived rather than hand-maintained — it can't drift
> from what actually ran, which is the one property that matters.** ⭐ But I'd version the whole
> configuration object, not the string: ⭐⭐ **the template, the few-shot examples, the output schema —
> which is part of the prompt and which people forget to version — the model name and its resolved
> snapshot, the sampling parameters, the retrieval config, and the tool definitions.** ⭐ Otherwise
> ⭐⭐ **someone changes `k` from 5 to 10, quality moves, the prompt version is unchanged, and you spend
> a day looking in the wrong place.**

**3. ⭐⭐ "How is a prompt canary different from a code canary?"**
> ⭐ Three ways, and they all catch people out. ⭐⭐ **The failure usually isn't an error — error rate and
> latency both look fine while the answers get worse, so the canary has to watch quality proxies or
> it's watching the wrong graph entirely.** ⭐⭐ **The signal is slow: thumbs-down rates need hundreds of
> samples, so a five-minute canary tells you nothing and you should plan for hours.** ⭐ And ⭐⭐ **users
> in the canary get a different product personality, so for a conversational feature you pin a user to
> one version for their whole session — switching mid-conversation is visible and unsettling.** ⭐ I'd
> also add the step people skip: ⭐⭐ **shadow first — run the new prompt on real traffic without
> serving it and log both. It costs money and zero risk, and it tells you how the change behaves on
> inputs your eval set never imagined.**

**4. "Non-engineers want to edit prompts. What do you do?"**
> ⭐ Take it seriously rather than refusing, ⭐⭐ **because the people best at writing prompts — support
> leads, domain experts — are often not comfortable opening a PR, so "put it in git" is correct and
> insufficient.** ⭐ Best option is ⭐⭐ **a git-backed UI: the editor writes to a branch and opens a PR,
> so non-engineers get a textbox and engineers get review, history, evals and rollback** — and it's not
> much work with the GitHub API. ⭐ Or a registry with an enforced eval-and-approval step, ⭐⭐ **though
> the risk there is that the discipline is optional in most tools, and optional discipline is absent
> discipline under deadline.** ⭐ Or free editing in staging with a governed promotion. ⭐⭐ **The
> non-negotiable underneath all three is that production prompts are immutable and addressed by
> version — you never edit the live one, you publish a new version and move a pointer, which makes
> rollback free.**

**5. ⭐⭐ "How do you know quality dropped in production, with no ground truth?"**
> ⭐ Proxies, chosen to move before users complain. ⭐⭐ **Abstention rate is the best single one, because
> it's meaningful in both directions — a drop means the model started guessing, a spike means
> retrieval broke.** ⭐ Schema-valid-on-first-attempt moves immediately and costs nothing. ⭐⭐ **Output
> length distribution, where a sudden shift almost always means behaviour changed — it's the earliest
> signal of a silent model update.** ⭐ Retry, refusal and tool-call rates. ⭐ User signals, ⭐⭐ **where
> the regenerate click is the most honest one you have: it costs the user nothing to express and means
> "that wasn't good enough".**

**6. ⭐⭐ "What catches a regression you didn't cause?"**
> ⭐⭐ **Running the eval set against production config nightly — same prompt, same model alias, same
> retrieval index.** ⭐ That catches the two things no canary can: ⭐⭐ **the provider silently moving your
> model snapshot under a stable alias, and your retrieval index drifting as documents are added.**
> ⭐ Nothing you deployed changed and the product got worse — ⭐⭐ **and that failure is completely
> invisible without a nightly run.**

## 🎙️ Articulation drill

**Two minutes.** Frame the risk: **a prompt is the highest-leverage, least-governed artefact in the
system — it changes behaviour more than most code changes, and it's typically edited in a web UI by
someone who doesn't open a PR, with no review, no test, and no version on the request. That's exactly
why config causes a disproportionate share of outages: it bypasses review, tests, canaries and
rollback.** Then the discipline, concretely: **prompts in version control, with the version derived
from a content hash so it can't drift from what ran — and version the whole configuration object, not
the string. The schema is part of the prompt, and so are the model snapshot, the sampling parameters
and the retrieval config; otherwise someone changes `k` from 5 to 10, quality moves, the prompt
version is unchanged, and you look in the wrong place for a day.** Then rollout, with the differences
that catch people: **shadow first — real traffic, not served, both outputs logged; that's the
highest-value and least-used step. Then canary, and know that the failure usually isn't an error, so
watching error rate and latency means watching the wrong graph. The signal is slow, so plan hours not
minutes. And pin users to one version for a session, because switching personality mid-conversation is
unsettling.** Resolve the human tension honestly: **the best prompt writers often aren't engineers, so
"put it in git" is correct and insufficient — a git-backed UI gives them a textbox and gives you
review, history and rollback. The non-negotiable is that production prompts are immutable and
addressed by version; you publish and move a pointer.** Close on the blind spot: **run your eval set
against production config nightly, because that's the only thing that catches a provider silently
moving your model snapshot or your retrieval index drifting — nothing you deployed changed and the
product got worse.**
