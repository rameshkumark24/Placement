# Part 1 — ⭐ Seeing processes

```bash
ps aux | head                # ⭐ every process: USER PID %CPU %MEM RSS STAT COMMAND
ps -ef --forest              # ⭐⭐ the TREE — who started whom
pgrep -af uvicorn            # ⭐⭐ find by name, with the full command line
top / htop                   # ⭐ live · ⭐ press `1` for per-core, `M` to sort by memory
ps -o pid,ppid,rss,etime,cmd -p 4242    # ⭐ exactly the columns you want
```

| ⭐ Column | ⭐ Meaning |
|---|---|
| `PID` / `PPID` | ⭐ this process / **its parent** |
| ⭐⭐ `RSS` | ⭐⭐ **resident memory — real RAM.** The number the OOM killer looks at |
| `VSZ` | virtual size — ⭐ mostly meaningless, includes unbacked mappings |
| ⭐ `STAT` | `R` running · `S` sleeping · ⭐⭐ `D` **uninterruptible I/O** · `Z` zombie · `T` stopped |
| `%CPU` | ⭐ over 100 % ⇒ more than one core ⇒ **more than one process or true parallelism** |

```
⭐⭐ TWO STATES WORTH RECOGNISING INSTANTLY:
⭐   Z (zombie)  ⇒ the process EXITED but nobody read its exit status. It holds a PID
⭐                 and nothing else. ⭐ The parent must wait(); ⭐⭐ if the parent is
⭐                 gone, init/PID 1 adopts it and reaps it. ⭐⭐ Thousands of zombies
⭐                 ⇒ A BUG IN THE PARENT, not in the children.
⭐   D           ⇒ blocked in the kernel on I/O and ⭐⭐ CANNOT BE KILLED, not even -9.
⭐                 ⭐ Usually a stuck disk or NFS mount. If `kill -9` "does nothing",
⭐                 look at STAT before you look at your code.
```

⭐⭐ **Orphan vs zombie is a real interview question.** An **orphan** is alive with a dead parent — it
gets re-parented to PID 1 and is fine. A **zombie** is dead with a live parent that never called
`wait()` — it is a leak. ⭐ In Python, `subprocess.Popen` without `wait()`/`communicate()` creates
zombies; `subprocess.run` cannot, because it waits.

# Part 2 — ⭐⭐ Signals

```
⭐⭐ A SIGNAL IS AN INTERRUPT DELIVERED TO A PROCESS. Each has a DEFAULT ACTION,
⭐   and most can be caught, blocked or ignored — ⭐⭐ except two, which cannot.
```

| Signal | # | ⭐ Sent by | Default | ⭐ Catchable |
|---|---|---|---|---|
| ⭐⭐ `SIGTERM` | 15 | ⭐⭐ `kill`, `docker stop`, k8s, systemd | terminate | ⭐⭐ **YES — the polite one** |
| ⭐ `SIGINT` | 2 | ⭐ Ctrl-C | terminate | ⭐⭐ YES — **Python turns it into `KeyboardInterrupt`** |
| ⭐⭐ `SIGKILL` | 9 | ⭐ `kill -9`, the **OOM killer**, docker's timeout | die | ⭐⭐ **NO. Never.** |
| `SIGSTOP` | 19 | `kill -STOP`, Ctrl-Z | pause | ⭐ NO |
| `SIGHUP` | 1 | terminal closed | terminate | ⭐ YES — **conventionally "reload config"** |
| `SIGPIPE` | 13 | ⭐ writing to a closed pipe (Day 079) | terminate | YES |
| `SIGCHLD` | 17 | a child exited | ignore | YES — ⭐ how you reap |
| `SIGSEGV` | 11 | your C extension | core dump | ⭐ (do not) |

```
⭐⭐ THE ONLY TWO THAT MATTER TODAY, AND THE WHOLE DIFFERENCE:
⭐   SIGTERM  ⇒ "please stop"     ⇒ ⭐⭐ YOU GET TO RUN CODE. Finish in-flight work,
⭐                                   flush, close the DB pool, deregister, exit.
⭐   SIGKILL  ⇒ "you are stopped" ⇒ ⭐⭐ THE KERNEL REMOVES YOU. No handler, no
⭐                                   flush, no finally, no atexit, no __del__ (Day 026).
⭐                                   ⭐ Buffered stdout is LOST (Day 079).
⭐
⭐   ⇒ ⭐⭐ EVERY SHUTDOWN SYSTEM IS THE SAME TWO-STEP: send TERM, wait a grace
⭐        period, then send KILL. ⭐ docker stop: 10s. Kubernetes: 30s.
⭐        systemd: 90s. ⭐⭐ ALL OF YOUR SHUTDOWN WORK MUST FIT IN THAT WINDOW.
```

```python
import signal, sys

shutting_down = False

def handle(signum, frame):
    global shutting_down
    shutting_down = True                 # ⭐⭐ SET A FLAG. Do the work in the main loop.

signal.signal(signal.SIGTERM, handle)    # ⭐⭐ SIGINT too, so Ctrl-C behaves the same
signal.signal(signal.SIGINT, handle)
```

```
⭐⭐ THREE FACTS ABOUT PYTHON SIGNAL HANDLERS, EACH OF WHICH CAUSES A BUG:
⭐  1. ⭐⭐ ONLY THE MAIN THREAD RECEIVES SIGNALS.       (Day 066)
⭐       ⇒ a worker thread blocked in a queue.get() will not be interrupted;
⭐         ⭐ this is why Ctrl-C sometimes appears to "do nothing" — the main
⭐         thread is join()-ing and the handler never gets to run.
⭐  2. ⭐⭐ THE HANDLER RUNS BETWEEN BYTECODES.           (Days 067, 073)
⭐       ⇒ the C-level signal handler only sets a flag; the interpreter checks it
⭐         at the next instruction boundary. ⭐⭐ SO A LONG C CALL (a big regex,
⭐         numpy, time.sleep in some builds) DELAYS DELIVERY.
⭐  3. ⭐ DO ALMOST NOTHING IN THE HANDLER. Set a flag. ⭐⭐ Logging or acquiring a
⭐       lock inside a handler can deadlock, because you may have interrupted code
⭐       that already holds that lock.
```

⭐ **`KeyboardInterrupt` is not special** — it is Python's default SIGINT handler raising an exception
into the main thread. ⭐⭐ **Which is why `except Exception:` does not catch it**: it inherits from
`BaseException` (Day 059), *precisely so* that a broad handler cannot swallow your Ctrl-C.

# Part 3 — ⭐⭐ Graceful shutdown, derived

```
⭐⭐ WHAT HAPPENS ON EVERY DEPLOY, IN ORDER:
⭐   1. the orchestrator decides to replace your pod/container
⭐   2. ⭐ it removes you from the load balancer                    ⟵ ⭐⭐ ASYNCHRONOUS
⭐   3. it sends SIGTERM to PID 1
⭐   4. it waits (10s docker / 30s k8s)
⭐   5. ⭐⭐ SIGKILL
⭐
⭐⭐ ⇒ AND NOW THE THREE WAYS THIS DROPS REQUESTS — each has a different fix:
⭐
⭐   A. ⭐⭐ YOU IGNORE SIGTERM ⇒ everything in flight dies at step 5.
⭐   B. ⭐⭐ YOU EXIT INSTANTLY ⇒ the requests you were holding get a connection reset.
⭐   C. ⭐⭐ STEPS 2 AND 3 RACE ⇒ the LB still sends you traffic for a second or two
⭐        AFTER the TERM. ⭐ Exiting immediately means those arrive at a closed port.
⭐        ⭐⭐ THE FIX IS COUNTERINTUITIVE: on SIGTERM, SLEEP a few seconds while
⭐        STILL SERVING, then drain. (k8s: a preStop hook.) ⭐ The bug is not in
⭐        your code — it is that deregistration is eventually consistent.
⭐
⭐⭐ ⇒ CORRECT SHUTDOWN, IN ORDER:
⭐     stop accepting NEW connections → keep serving IN-FLIGHT ones → wait, with a
⭐     TIMEOUT SHORTER THAN THE GRACE PERIOD → close the DB pool → flush logs → exit 0.
```

```
⭐⭐ THE CONTAINER BUG THAT MAKES ALL OF THIS MOOT — AND IT IS EVERYWHERE:
⭐
⭐   Dockerfile:  CMD python app.py            ⭐ "shell form"
⭐   ⇒ ⭐⭐ this runs  /bin/sh -c "python app.py"  ⇒ SH IS PID 1, python is its child.
⭐   ⇒ ⭐⭐ sh DOES NOT FORWARD SIGNALS ⇒ your handler is never called ⇒ SIGKILL, always.
⭐   ⇒ ⭐⭐ FIX:  CMD ["python", "app.py"]      ⭐ exec form. Your process IS PID 1.
⭐
⭐⭐ AND THE SECOND HALF, WHICH SURPRISES EVEN PEOPLE WHO KNOW THE FIRST:
⭐   ⭐⭐ PID 1 DOES NOT GET DEFAULT SIGNAL ACTIONS. The kernel only delivers a
⭐   signal to PID 1 if it has INSTALLED A HANDLER for it.
⭐   ⇒ ⭐⭐ Python installs one for SIGINT, and NOT for SIGTERM.
⭐   ⇒ ⭐⭐ THEREFORE A PLAIN PYTHON PROCESS AS PID 1 IGNORES SIGTERM ENTIRELY,
⭐        and every `docker stop` takes the full 10 seconds and ends in SIGKILL.
⭐   ⇒ ⭐ THE TELL: your stop is always exactly 10 (or 30) seconds. That is never
⭐        a coincidence — ⭐⭐ it is the grace period, timing out.
⭐   ⇒ ⭐ Fixes: install the handler (above), or run under an init (`tini`,
⭐        `docker run --init`) that reaps and forwards properly.
```

⭐ **Gunicorn and Uvicorn already do this correctly** (Day 021): the master catches `SIGTERM`, stops
accepting, waits for workers, and kills them at `--graceful-timeout`. ⭐⭐ **Your job is to (a) use the
exec form, (b) make the grace period longer than your slowest request, and (c) not do anything in a
`finally` that takes longer than the window.**

```
⭐⭐ THE PART EVERY SERVICE GETS WRONG — WHAT ELSE MUST STOP:
⭐   · ⭐⭐ a Celery worker mid-task ⇒ acknowledge-late, so an unfinished task is REDELIVERED
⭐   · a consumer loop ⇒ finish the current message, do not commit the offset for the next
⭐   · ⭐ a cron-style background task (Day 071) ⇒ cancel and AWAIT it, or you lose the write
⭐   · ⭐⭐ IN-MEMORY STATE IS GONE. Anything you were "about to write" is lost.
⭐        ⇒ ⭐⭐ which is the real lesson: SHUTDOWN SAFETY IS A DESIGN PROPERTY.
⭐          An idempotent, restartable task survives SIGKILL; a clever one does not.
```

# Part 4 — ⭐ systemd, briefly

```ini
# /etc/systemd/system/myapi.service
[Unit]
Description=My API
After=network.target

[Service]
User=app                                  # ⭐⭐ NOT root (Day 078)
WorkingDirectory=/srv/app
Environment=PYTHONUNBUFFERED=1            # ⭐⭐ Day 079 — or your logs are empty
EnvironmentFile=/etc/myapi.env            # ⭐ secrets, mode 600
ExecStart=/srv/app/.venv/bin/gunicorn -k uvicorn.workers.UvicornWorker app:app
Restart=on-failure                        # ⭐ not `always` — see below
RestartSec=5
TimeoutStopSec=30                         # ⭐⭐ YOUR grace period. TERM, then KILL.

[Install]
WantedBy=multi-user.target
```

| ⭐ Command | |
|---|---|
| `systemctl status myapi` | ⭐ state, PID, last log lines — **the first command** |
| `systemctl restart / reload` | ⭐ restart · send `SIGHUP` |
| `journalctl -u myapi -f` | ⭐⭐ follow the logs (Day 080's `tail -f`, with structure) |
| `journalctl -u myapi --since "10 min ago" -p err` | ⭐ time-boxed, errors only |

⚠️ ⭐ **`Restart=always` on a service that crashes at startup is a crash loop that hides the bug** —
`on-failure` plus `RestartSec` gives you a service that recovers from a real fault but stops shouting
when it is fundamentally broken. ⭐⭐ **And note the shape is identical to Kubernetes**: a supervisor,
a restart policy, a grace period, and a log stream. **Learn it once here where you can see all the
pieces.**

# Part 5 — D-02 · ⭐⭐ The relational model

```
⭐⭐ A RELATION IS A SET OF TUPLES OVER A SET OF ATTRIBUTES, EACH DRAWN FROM A DOMAIN.
⭐
⭐   attribute  = a named column        domain = its type + allowed values
⭐   tuple      = one row               relation = the whole set
⭐
⭐   ⇒ ⭐⭐ "SET" IS THE LOAD-BEARING WORD, AND TWO THINGS FOLLOW FROM IT:
⭐      1. ⭐⭐ NO ORDER. There is no "first row". ⭐ Which is why a query without
⭐         ORDER BY may return rows in a different order tomorrow — and why
⭐         relying on it is a real bug, not pedantry.
⭐      2. ⭐ NO DUPLICATES — in the MODEL. ⚠️ SQL tables are BAGS and DO allow
⭐         duplicates, ⭐⭐ which is the single biggest gap between the theory
⭐         and the product, and the reason SELECT DISTINCT exists at all.
```

| ⭐ Key | ⭐ Definition |
|---|---|
| Superkey | any attribute set that uniquely identifies a tuple |
| ⭐ **Candidate key** | ⭐ a **minimal** superkey — remove any attribute and uniqueness breaks |
| ⭐⭐ **Primary key** | ⭐ the candidate key you *chose*. **Not special — chosen** |
| Alternate key | the candidate keys you did not choose (still `UNIQUE`) |
| ⭐⭐ **Foreign key** | an attribute referencing another relation's key ⇒ ⭐⭐ **referential integrity** |
| ⭐ Composite key | a key made of more than one attribute — ⭐ normal in join tables |

```
⭐⭐ NATURAL vs SURROGATE — a real design argument, and a favourite interview question:
⭐   NATURAL   (email, ISBN, national id)   ⭐ meaningful · ⚠️ ⭐⭐ CHANGES. People
⭐                                            change email addresses ⇒ you must
⭐                                            cascade the change through every FK.
⭐   SURROGATE (an id you invent)           ⭐⭐ stable and meaningless — which is
⭐                                            exactly the point: nothing about the
⭐                                            world can invalidate it.
⭐   ⇒ ⭐⭐ THE ANSWER: surrogate primary key, PLUS a UNIQUE constraint on the
⭐        natural key. You get stable references AND the integrity rule.
⭐   ⇒ ⭐ Day 058's enum lesson is the same shape: closed in code, open in the database.
```

```
⭐⭐ NULL IS NOT A VALUE — IT IS "UNKNOWN", AND IT MAKES SQL THREE-VALUED:
⭐   NULL = NULL      ⇒ ⭐⭐ NULL (not TRUE!)      ⇒ use IS NULL
⭐   NULL <> 5        ⇒ NULL
⭐   WHERE x = NULL   ⇒ ⭐⭐ MATCHES NOTHING, EVER, and does not error
⭐   COUNT(col)       ⇒ ⭐ SKIPS NULLs · COUNT(*) does not
⭐   ⇒ ⭐⭐ THIS IS Optional[T] FROM DAY 061, ENFORCED BY THE ENGINE — and NOT NULL
⭐        is the constraint that removes the whole class of problem. ⭐ Default to
⭐        NOT NULL and justify every nullable column.
```

⭐⭐ **The sentence for D-02:** *"a relation is a set of tuples, so there is no row order and no
positional access; a key is a promise of uniqueness that the engine enforces; and NULL means unknown,
which makes comparisons three-valued and is why `= NULL` silently matches nothing."*

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **`CMD python app.py` in a Dockerfile** | ⭐⭐ Shell form ⇒ `sh` is PID 1 ⇒ signals are never forwarded. |
| ⭐ Assuming Python handles `SIGTERM` | ⭐⭐ It does not. As PID 1 it is **ignored entirely**. |
| Doing real work in a signal handler | ⭐⭐ Set a flag. Logging there can deadlock. |
| ⭐ Expecting a worker thread to see Ctrl-C | ⭐ **Main thread only.** |
| `except Exception` to catch Ctrl-C | ⭐ `KeyboardInterrupt` is a `BaseException` — deliberately. |
| Exiting immediately on `SIGTERM` | ⭐⭐ Deregistration races. Serve for a moment, *then* drain. |
| Shutdown work longer than the grace period | ⭐⭐ It ends in `SIGKILL` anyway. |
| ⭐ "`kill -9` does nothing" | ⭐ Check `STAT` — `D` is uninterruptible. |
| `Popen` without `wait()` | ⭐ Zombies. |
| `Restart=always` on a startup crash | ⭐ A crash loop that hides the cause. |
| ⭐⭐ Relying on row order without `ORDER BY` | ⭐⭐ A relation is a **set**. |
| `WHERE x = NULL` | ⭐⭐ Matches nothing. `IS NULL`. |
| Natural key as the primary key | ⭐ Surrogate PK + `UNIQUE` on the natural key. |

## Interview questions

**Q: What happens between `docker stop` and your process dying?**
> It sends `SIGTERM` to PID 1, waits ten seconds, then sends `SIGKILL`. `SIGTERM` is catchable, so
> that window is your only chance to run code — stop accepting new connections, finish the in-flight
> requests, close the pool, flush, exit zero. `SIGKILL` can't be caught, so nothing runs: no
> `finally`, no `atexit`, and buffered stdout is lost. Two container-specific traps sit on top. If
> the Dockerfile uses the shell form, `/bin/sh` is PID 1 and doesn't forward signals, so your handler
> never fires. And PID 1 only receives signals it has installed a handler for — Python installs one
> for `SIGINT` but not `SIGTERM`, so a plain Python process as PID 1 ignores it outright. The tell is
> that every stop takes exactly ten seconds, which is never a coincidence.

**Q: Your deploy drops a handful of requests every time. Where do you look?**
> Three candidates, in order. First, whether `SIGTERM` reaches the app at all — shell form, or no
> handler. Second, whether shutdown is graceful or immediate: exiting the moment you get the signal
> resets the connections you're already holding. Third, and this is the one people miss, the race
> between load balancer deregistration and the signal — those two are asynchronous, so traffic can
> arrive for a second or two after `SIGTERM`. The counterintuitive fix is to sleep briefly while still
> serving before draining, which in Kubernetes is a `preStop` hook. The failure isn't in my code; it's
> that deregistration is eventually consistent.

**Q: Orphan versus zombie.**
> An orphan is a live process whose parent died — the kernel re-parents it to PID 1 and it carries on
> fine. A zombie is a dead process whose parent is still alive but never called `wait()`, so the exit
> status is still queued. It holds nothing but a PID entry. Thousands of zombies means a bug in the
> parent, not in the children — in Python that's `Popen` without `wait` or `communicate`. It's also
> why containers want a real init: PID 1 has to reap adopted children, and a Python app as PID 1
> doesn't.

**Q: Why can't you catch `SIGKILL`?**
> Because it's the guarantee that a process can always be removed. If it were catchable, a buggy or
> malicious program could refuse to die, and the operator would have nothing left. `SIGSTOP` is
> uncatchable for the same reason. The design consequence is that shutdown safety can't rest on
> cleanup code — anything that must survive a hard kill has to be idempotent and restartable, because
> `SIGKILL`, a power cut, and an OOM kill are the same event from your process's point of view.

**Q: What does it mean that a relation is a set?**
> That there's no inherent row order and no duplicate tuples. The order point is practical: a query
> without `ORDER BY` can return rows in a different order tomorrow because the planner changed, so
> relying on the observed order is a real bug. The duplicate point is where theory and SQL diverge —
> tables are bags, they do allow duplicates, and that's why `SELECT DISTINCT` needs to exist at all.

## 🎙️ Articulation drill

Record two minutes: **"Every deploy, a few users get a 502. Walk me through it."**

⭐ **Name the shape first, because it tells the interviewer you have seen this before:** **"a 502
during a deploy is almost always shutdown, not startup — the old instance is being replaced and
something in that sequence is abrupt."**

⭐⭐ **Then the three candidates, in order, with the mechanism for each:** *"first, does SIGTERM even
reach the app — if the Dockerfile uses the shell form then `sh` is PID 1 and doesn't forward signals,
and even with the exec form, PID 1 only receives signals it has installed a handler for, and Python
installs one for SIGINT but not SIGTERM. The tell is a stop that always takes exactly the grace period.
Second, is shutdown graceful — exiting the instant the signal arrives resets every connection I'm
currently holding. Third, the deregistration race: removing me from the load balancer and signalling
me are asynchronous, so traffic keeps arriving for a second or two after TERM."*

⭐⭐ **Then the fix, including the counterintuitive one:** *"handle SIGTERM, stop accepting, drain
in-flight work with a timeout shorter than the grace period — and on SIGTERM, sleep a few seconds while
still serving before draining, because that's the only way to cover the deregistration lag."*

⭐ **Close on the design point, which is the part that generalises:** *"and I'd treat graceful
shutdown as a best-effort optimisation rather than a guarantee. SIGKILL, an OOM kill and a power cut
are the same event from the process's point of view, so anything that must not be lost has to be
idempotent and restartable — the cleanup code is a courtesy, not a correctness argument."*
