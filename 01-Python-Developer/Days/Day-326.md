# Part 2 — ⭐⭐ The four failure modes, named

```
⭐⭐ ① CACHE STAMPEDE (dogpile / thundering herd)
⭐   ⭐ A hot key expires. 5,000 concurrent requests miss.
⭐     ⭐⭐ ALL 5,000 GO TO THE DATABASE AT ONCE.
⭐   ⭐ Day 313's arithmetic: at a 99.9% hit ratio, ⭐⭐ THE 0.1%
⭐     IS STILL A HUNDRED-FOLD SPIKE ON THE ORIGIN, AND THE
⭐     ORIGIN WAS SIZED FOR THE 0.1%.
⭐   ⇒ FIXES, IN ORDER OF PREFERENCE:
⭐      ⭐ (a) ⭐⭐ PROBABILISTIC EARLY EXPIRY (XFetch) — refresh
⭐          before expiry with rising probability. ⭐ No locks,
⭐          no coordination, ~6 lines. ⭐⭐ THE BEST ANSWER AND
⭐          ALMOST NOBODY GIVES IT.
⭐      ⭐ (b) A per-key lock: one refresher, others serve stale.
⭐      ⭐ (c) ⭐ TTL JITTER — ⭐⭐ MANDATORY REGARDLESS, or a
⭐          bulk warm-up expires 10,000 keys in the same second.

⭐⭐ ② CACHE PENETRATION
⭐   ⭐ Requests for keys that ***do not exist***. Every one
⭐     misses, every one hits the database. ⭐ Trivially
⭐     weaponised: `GET /user/<random>` in a loop.
⭐   ⇒ ⭐⭐ CACHE THE NEGATIVE RESULT, with a short TTL. ⭐ Plus
⭐     a Bloom filter if the key space is huge (Day 348).
⭐   ⇒ ⭐⭐ THIS IS WHY DAY 313 SAID `get` MUST RAISE RATHER
⭐     THAN RETURN `None` — you cannot cache "absent" in an API
⭐     that cannot express it.

⭐⭐ ③ CACHE AVALANCHE
⭐   ⭐ Many keys expire simultaneously, ***or the cache node
⭐     restarts empty***. ⭐⭐ 100% MISS RATE INSTANTLY.
⭐   ⇒ ⭐ Jitter, staggered warm-up, ⭐⭐ AND THE HONEST TEST:
⭐     ***CAN YOUR ORIGIN SURVIVE A COLD CACHE?*** If not, the
⭐     cache is not an optimisation — ⭐⭐ IT IS LOAD-BEARING
⭐     INFRASTRUCTURE AND MUST BE HA, BACKED UP AND ALERTED ON
⭐     LIKE A DATABASE. ⭐ Day 267's "0%-hit throughput is your
⭐     real capacity", now with a name.

⭐⭐ ④ HOT KEY
⭐   ⭐ One key gets 40% of traffic (a celebrity, a flash-sale
⭐     product). ⭐⭐ SHARDING DOESN'T HELP: ONE KEY IS ONE
⭐     SHARD. That node melts while the others idle.
⭐   ⇒ ⭐ (a) ⭐⭐ NEAR-CACHE IT IN-PROCESS with a 1–5 s TTL —
⭐          the one legitimate use of Day 324's forbidden dict.
⭐   ⇒ ⭐ (b) Key splitting: `post:42#0..9`, write all, read one
⭐          at random.
⭐   ⇒ ⭐ (c) Replicate the key across nodes.
```

```python
# ⭐⭐ PROBABILISTIC EARLY EXPIRY — THE WHOLE STAMPEDE FIX
def should_refresh(delta: float, ttl_left: float,
                   beta: float = 1.0) -> bool:
    """delta = how long the last recompute took."""
    return ttl_left <= 0 or (
        delta * beta * -math.log(random.random()) >= ttl_left
    )
# ⭐ Expensive values (large delta) refresh earlier.
# ⭐ Cheap values refresh right at expiry.
# ⭐⭐ AND ONLY ONE CALLER IN EXPECTATION CROSSES THE LINE FIRST,
# ⭐   WITH NO LOCK AND NO SHARED STATE AT ALL.
```

# Part 3 — ⭐⭐ Consistent hashing, derived

```
⭐⭐ THE NAIVE SCHEME: node = hash(key) % N.
⭐   ⭐ N goes 4 → 5.
⭐   ⇒ ⭐⭐ EVERY KEY WHOSE hash % 5 ≠ hash % 4 MOVES.
⭐     ⭐⭐ THAT IS ROUGHLY 80% OF THEM, AND FOR A CACHE IT
⭐       MEANS A NEAR-TOTAL MISS RATE — ⭐ i.e. an avalanche
⭐       (mode ③) triggered ***by scaling up***.
⭐   ⇒ ⭐ Add a node to survive load; take the origin down.

⭐⭐ THE FIX: PUT NODES AND KEYS ON THE ***SAME*** RING.
⭐   ① Hash each node ID to a point on a ring [0, 2^32).
⭐   ② Hash each key to a point on the same ring.
⭐   ③ ⭐ The key belongs to the ***first node clockwise***.
⭐   ⇒ ⭐⭐ ADD A NODE AND ONLY THE KEYS BETWEEN IT AND ITS
⭐     PREDECESSOR MOVE — ***K/N KEYS, NOT ALL OF THEM.***
⭐   ⇒ ⭐ 4 → 5 nodes now moves ~20%, not 80%.
```

```
⭐⭐ THE PROBLEM WITH THE PLAIN RING, WHICH IS THE ACTUAL
⭐   INTERVIEW QUESTION:
⭐   ⭐ 4 random points on a ring are ***not*** evenly spaced.
⭐     One node can own 45% of the ring.
⭐   ⭐ And when a node dies, ⭐⭐ ITS ***ENTIRE*** SHARE GOES TO
⭐     EXACTLY ONE NEIGHBOUR — which then dies too. ⭐ A ring
⭐     with no virtual nodes has a built-in cascade.

⭐⭐ THE FIX — ***VIRTUAL NODES***: place each physical node at
⭐   100–200 points on the ring.
⭐   ⇒ ⭐ Load evens out (law of large numbers).
⭐   ⇒ ⭐⭐ AND A DEAD NODE'S LOAD SPREADS ACROSS ***ALL***
⭐     SURVIVORS, NOT ONE. ⭐ That is the property that matters,
⭐     and the one candidates omit.
⭐   ⇒ ⭐ Bonus: weights fall out free — a 2× machine gets 2×
⭐     the virtual nodes.
```

```python
# ⭐ 25 lines. Type it; the bisect is the whole idea.
class HashRing:
    def __init__(self, nodes: list[str], vnodes: int = 150):
        self._ring: dict[int, str] = {}
        self._keys: list[int] = []
        self._vnodes = vnodes
        for n in nodes:
            self.add(n)

    def _hash(self, s: str) -> int:
        return int.from_bytes(hashlib.md5(s.encode()).digest()[:4], "big")

    def add(self, node: str) -> None:
        for i in range(self._vnodes):              # ⭐⭐ THE FIX
            h = self._hash(f"{node}#{i}")
            self._ring[h] = node
            bisect.insort(self._keys, h)

    def remove(self, node: str) -> None:
        for i in range(self._vnodes):
            h = self._hash(f"{node}#{i}")
            del self._ring[h]
            self._keys.remove(h)

    def get(self, key: str) -> str:
        if not self._keys:
            raise LookupError("empty ring")
        h = self._hash(key)
        i = bisect.bisect(self._keys, h) % len(self._keys)  # ⭐ wrap
        return self._ring[self._keys[i]]
```

```
⭐⭐ WHERE YOU HAVE ALREADY MET THIS WITHOUT NOTICING:
⭐   ⭐ Redis Cluster — 16,384 fixed ***hash slots***, which is
⭐     the same idea with a fixed vnode count. ⭐ Slots move,
⭐     keys don't rehash.
⭐   ⭐ Cassandra/DynamoDB partitioning · Memcached clients ·
⭐     Envoy's ring-hash · CDN origin selection.
⭐   ⇒ ⭐⭐ SAY "REDIS CLUSTER'S 16,384 SLOTS ARE CONSISTENT
⭐     HASHING WITH A FIXED VNODE COUNT" AND YOU HAVE SHOWN YOU
⭐     UNDERSTAND IT RATHER THAN MEMORISED IT.

⭐⭐ AND THE MODERN ALTERNATIVE WORTH ONE SENTENCE:
⭐   ⭐ ***RENDEZVOUS (HIGHEST-RANDOM-WEIGHT) HASHING*** —
⭐     score = hash(key + node) for every node, pick the max.
⭐   ⇒ ⭐ Perfect distribution, no vnodes, no ring; O(N) per
⭐     lookup, which is fine for small N. ⭐⭐ NAMING IT IS A
⭐     GENUINE DIFFERENTIATOR.
```

# Part 4 — ⭐⭐ Invalidation: the two hard problems, one of which is this

```
⭐⭐ THE PATTERNS — AND THE ONE THAT IS ALWAYS RIGHT:
⭐   ⭐ CACHE-ASIDE (lazy) — app reads cache, misses, loads,
⭐     writes cache. ⭐⭐ THE DEFAULT. Use it unless you have a
⭐     specific reason not to.
⭐   ⭐ READ-THROUGH — the cache loads for you. Same semantics,
⭐     less app code, more magic.
⭐   ⭐ WRITE-THROUGH — write cache + DB synchronously.
⭐     ⭐ Consistent, slower writes.
⭐   ⭐ WRITE-BEHIND — write cache, flush later. ⭐⭐ FAST AND
⭐     LOSES DATA ON CRASH. Almost never right for a system of
⭐     record.
⭐   ⭐ WRITE-AROUND — write DB only, let reads populate.
⭐     ⭐ Good for write-heavy data that is rarely read.

⭐⭐ THE RULE FROM DAY 267, RESTATED AND STILL THE ANSWER:
⭐   ***DELETE THE KEY ON WRITE. DO NOT UPDATE IT.***
⭐   ⇒ ⭐ Updating races: two writers, two computed values, the
⭐     older one lands last, ⭐⭐ AND IT STICKS UNTIL TTL.
⭐   ⇒ ⭐ Deleting is idempotent, order-insensitive, and the
⭐     worst case is one extra miss.

⭐⭐ EVEN DELETE HAS A RACE — SAY IT UNPROMPTED:
⭐   ⭐ Reader misses, loads v1 from DB… stalls.
⭐   ⭐ Writer writes v2, deletes the key.
⭐   ⭐ Reader wakes and writes ***v1*** into the cache.
⭐   ⇒ ⭐⭐ STALE FOREVER (until TTL).
⭐   ⇒ FIXES: ⭐ (a) a TTL always, so "forever" is bounded —
⭐     ⭐⭐ THE TTL IS NOT THE FRESHNESS POLICY, IT IS THE BOUND
⭐     ON A BUG YOU HAVE NOT FOUND YET; ⭐ (b) delayed
⭐     double-delete; ⭐ (c) version-stamped values, refuse to
⭐     write an older version.
```

# Part 5 — ⭐ Eviction, memory, and the Redis flags people misconfigure

```
⭐⭐ EVICTION POLICIES THAT MATTER:
⭐   ⭐ `allkeys-lru` — general caching. ⭐⭐ THE DEFAULT YOU
⭐     ALMOST ALWAYS WANT.
⭐   ⭐ `allkeys-lfu` — better when popularity is stable; ⭐ LRU
⭐     is fooled by a one-off scan, LFU is not.
⭐   ⭐ `volatile-*` — only evicts keys with a TTL.
⭐   ⭐ ⭐⭐ `noeviction` — ***THE DEFAULT IN REDIS***, and it
⭐     means ⭐⭐ WRITES START FAILING WHEN MEMORY FILLS.
⭐     ⇒ ⭐ If you use Redis as a cache and never set
⭐       `maxmemory-policy`, you have built a cache that
⭐       returns errors instead of evicting. ⭐⭐ CHECK THIS ON
⭐       EVERY REDIS YOU INHERIT.

⭐⭐ TWO MORE THAT BITE:
⭐   ⭐ ⭐⭐ SESSIONS AND CACHE IN THE SAME REDIS ⇒ eviction logs
⭐     users out. ⭐ Separate instances, or separate databases
⭐     with different policies.
⭐   ⭐ ⭐⭐ `KEYS *` IN PRODUCTION BLOCKS THE ENTIRE SERVER —
⭐     Redis is single-threaded for commands. ⭐ Use `SCAN`.
⭐     ⭐ The same is true of a large `DEL`; use `UNLINK`.

⭐⭐ AND THE MEASUREMENT THAT MATTERS MORE THAN HIT RATIO
⭐   (Day 267): ***TIME SAVED PER SECOND = hits/s × latency
⭐   saved.*** ⭐ A 60% hit ratio on a 900 ms query beats a 99%
⭐   hit ratio on a 2 ms one, ⭐⭐ AND THE SECOND CACHE IS
⭐   PROBABLY COSTING YOU MORE IN COMPLEXITY THAN IT SAVES.
```

# Part 6 — ⭐⭐ The multi-layer cache, and coherence

```
⭐⭐ THE REAL SHAPE IN A BUSY SERVICE:
⭐   ⭐ L1: in-process dict, TTL 1–5 s, tiny.
⭐   ⭐ L2: Redis, TTL minutes.
⭐   ⭐ L3: the database.

⭐⭐ WHY L1 IS WORTH IT DESPITE DAY 324:
⭐   ⭐ It removes a 0.5 ms network hop and, more importantly,
⭐     ⭐⭐ IT IS THE ONLY REAL DEFENCE AGAINST A HOT KEY.
⭐   ⭐ 40% of traffic on one key × 30 pods ⇒ ⭐ with a 2-second
⭐     L1, that key sees at most 30 Redis reads per 2 seconds
⭐     instead of 40,000.

⭐⭐ AND ITS PRICE, STATED HONESTLY:
⭐   ⭐⭐ L1 IS INCOHERENT BY CONSTRUCTION. ⭐ Deleting the Redis
⭐     key does ***not*** clear thirty local dicts.
⭐   ⇒ ⭐⭐ SO THE RULE IS: ***L1 TTL IS YOUR STALENESS BUDGET,
⭐     AND IT MUST BE SHORT ENOUGH THAT NOBODY CARES.***
⭐   ⇒ ⭐ If you find yourself wanting to invalidate L1 across
⭐     pods, you need a pub/sub invalidation channel — ⭐⭐ AND
⭐     AT THAT POINT ASK WHETHER THE 0.5 ms WAS WORTH IT.
⭐     ⭐ Usually: only for the hot key, never for everything.
```

# Part 7 — ⭐ Answering "would you add a cache?" well

```
⭐⭐ THE FOUR QUESTIONS, IN ORDER (Day 267, now with scale):
⭐   ① ⭐⭐ "WHAT IS THE READ:WRITE RATIO?" ⭐ Below ~10:1 a
⭐        cache is often not worth it.
⭐   ② ⭐ "HOW STALE MAY THIS BE, IN SECONDS?" ⭐⭐ IF THE ANSWER
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ `hash(key) % N` for cache sharding | Adding one node moves ~80% of keys. Scaling up causes the outage |
| ⭐⭐ Consistent hashing without virtual nodes | Uneven load, and a dead node dumps its entire share on one neighbour |
| ⭐⭐ No TTL because "we invalidate correctly" | The delete race makes stale permanent. TTL is the bound on the bug you haven't found |
| ⭐ Updating the cache on write | Two writers race and the older value sticks. Delete instead |
| ⭐⭐ No TTL jitter | A bulk warm-up expires ten thousand keys in the same second |
| ⭐ Not caching negative results | `GET /user/<random>` in a loop becomes a free DDoS on your database |
| ⭐⭐ Redis left on `noeviction` | The default. Your cache returns errors instead of evicting |
| ⭐ Sessions and cache in one Redis | Eviction logs users out |
| ⭐⭐ `KEYS *` in production | Blocks the single command thread for the whole server |
| ⭐ Believing sharding solves a hot key | One key is one shard. Only a near-cache or key-splitting helps |
| ⭐⭐ Treating a load-bearing cache as optional | If a cold cache takes you down, it needs HA and alerting like a database |

## Interview questions

**1. "Explain consistent hashing and why it exists."**
> ⭐⭐ Modulo hashing moves ~80% of keys when N changes, so adding a node to survive load causes a
> near-total cache miss and takes the origin down. ⭐ Consistent hashing puts nodes and keys on one
> ring and assigns each key to the next node clockwise, so only K/N keys move. ⭐⭐ Then the part that
> matters: **without virtual nodes the distribution is lumpy and a dead node's entire share lands on
> one neighbour**, which cascades — 150 vnodes per node fixes both, and gives you weighting for free.
> ⭐ Redis Cluster's 16,384 slots are this with a fixed vnode count.

**2. "Your cache node restarts empty at peak. What happens?"**
> ⭐⭐ That's an avalanche, and the honest answer starts with a question I should have asked at design
> time: **can the origin serve 100% of traffic?** ⭐ If yes, we're degraded and we ramp back up with
> staggered warming and jittered TTLs. ⭐⭐ If no, then the cache was never an optimisation — it's
> load-bearing infrastructure, and it needs replication, failover, alerting and a warm-up procedure
> like any database.

**3. "How do you prevent a stampede?"**
> ⭐ Jitter the TTLs always — that's free and prevents synchronised expiry. ⭐⭐ Then probabilistic
> early expiry: refresh before the TTL with a probability that rises as expiry approaches, scaled by
> how expensive the recompute was. **No locks, no coordination, about six lines, and in expectation
> only one caller crosses the line first.** ⭐ A per-key lock with serve-stale is the fallback when you
> need a hard guarantee.

**4. "Update the cache or delete it?"**
> ⭐ Delete. Updating races — two writers compute two values and the older one can land last and stick
> until TTL. ⭐ Deleting is idempotent and order-insensitive, and costs at most one extra miss.
> ⭐⭐ And even delete races with a slow reader that repopulates a stale value, **which is exactly why
> a TTL is mandatory even with perfect invalidation** — it bounds a bug you haven't found.

**5. "One key is 40% of your traffic. What do you do?"**
> ⭐⭐ Sharding cannot help, because one key is one shard — that node melts while the rest idle. ⭐ The
> real fix is a short-TTL in-process near-cache: thirty pods with a two-second L1 turn forty thousand
> reads a second into fifteen. ⭐ Key splitting across ten suffixes is the alternative when the value
> must stay in Redis. ⭐⭐ And I'd say the price out loud: the near-cache is incoherent by
> construction, so its TTL is my staleness budget.

**6. "When would you not add a cache?"**
> ⭐ When the read:write ratio is under about ten to one; when the tolerated staleness is zero, because
> then I want a replica or an index, not a cache; ⭐⭐ and when the query is already 2 ms, because
> **time saved per second is hits times latency saved — a 60% hit ratio on a 900 ms query beats 99% on
> a 2 ms one**, and the second cache costs more complexity than it returns.

## 🎙️ Articulation drill

**Two minutes.** Open with what a cache actually is: **a second copy of the truth with no owner**, so
every serious question about it is about disagreement, disappearance, or everything expiring at once.
Name the four failure modes fast — stampede, penetration, avalanche, hot key — and give the two
answers most candidates miss: **probabilistic early expiry, which beats the stampede with six lines
and no lock**, and **negative caching, without which a loop over random IDs is a free denial of
service on your database.** Then derive consistent hashing rather than reciting it: **modulo hashing
moves eighty percent of keys when you add a node, so scaling up to survive load is what takes the
origin down** — a ring moves K over N instead, and virtual nodes are the part that matters, because
without them the load is lumpy and a dead node dumps its whole share on one neighbour. Say that
Redis Cluster's sixteen thousand slots are the same idea with a fixed vnode count. Close on
invalidation: **delete, never update; and keep a TTL even with perfect invalidation, because the TTL
isn't the freshness policy — it's the bound on the bug you haven't found yet.** And on the question
that reframes everything: **what happens when the cache is empty? If the answer is "we go down", it
was never an optimisation.**
