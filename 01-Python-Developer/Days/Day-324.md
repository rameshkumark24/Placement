# Day 324 ↔️

**P-324** · ↔️ **Vertical vs horizontal scaling** — ⭐⭐ and what "stateless" really means

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: "stateless" does not mean the service has no state — it means no request
> depends on state held in the process that happens to serve it, and the whole art is finding the
> four kinds of state you forgot you had.**

---

# Part 1 — ⭐⭐ Vertical first, and the reason nobody says it

```
⭐⭐ VERTICAL: a bigger box. HORIZONTAL: more boxes.

⭐⭐ THE ADVICE THAT SOUNDS UNAMBITIOUS AND IS CORRECT:
⭐   ***SCALE VERTICALLY UNTIL IT HURTS, THEN HORIZONTALLY.***
⭐   ⭐ A 128-core, 2 TB-RAM machine is a real, rentable thing.
⭐   ⭐ It costs less than the engineers who would otherwise
⭐     spend six months sharding.
⭐   ⇒ ⭐⭐ MOST SYSTEMS THAT "NEEDED TO SCALE OUT" NEEDED AN
⭐     INDEX (Day 195).

⭐⭐ VERTICAL'S FOUR HARD LIMITS — KNOW ALL FOUR:
⭐   ① ⭐ A CEILING EXISTS. You run out of biggest-box.
⭐   ② ⭐⭐ COST GOES SUPERLINEAR. 2× the cores is often 3–4×
⭐        the price near the top of the range.
⭐   ③ ⭐⭐ IT IS ONE FAILURE DOMAIN. ⭐ No amount of RAM gives
⭐        you availability. ⭐⭐ THIS, NOT THROUGHPUT, IS THE
⭐        REAL REASON MOST SYSTEMS GO HORIZONTAL.
⭐   ④ ⭐ RESIZING IS A RESTART. Downtime, or a failover.

⭐⭐ HORIZONTAL'S HIDDEN PRICE, STATED HONESTLY:
⭐   ⭐ Coordination, consistency, partial failure, deploys that
⭐     span versions, and ⭐⭐ EVERY IN-PROCESS ASSUMPTION YOU
⭐     EVER MADE BECOMING FALSE.
⭐   ⇒ ⭐ Day 310's in-process lock. Day 313's cache. Day 314's
⭐     counter. ⭐⭐ ALL THREE SILENTLY BREAK AT N=2.
```

# Part 2 — ⭐⭐ Scale cube: the three axes

```
⭐⭐ X-AXIS — ***CLONING***. N identical copies behind a load
⭐   balancer. ⭐ Cheapest, most common, requires statelessness.
⭐   ⇒ ⭐ Scales ***request volume***. Does nothing for data size.

⭐⭐ Y-AXIS — ***FUNCTIONAL DECOMPOSITION***. Split by verb:
⭐   auth service, search service, billing service.
⭐   ⇒ ⭐ Scales ***team count*** and lets components scale
⭐     independently. ⭐⭐ Day 340 argues about the cost.

⭐⭐ Z-AXIS — ***DATA PARTITIONING***. Same code, different
⭐   slice of the data. ⭐ This is sharding (Day 329).
⭐   ⇒ ⭐⭐ THE ONLY AXIS THAT SCALES ***DATA SIZE AND WRITE
⭐     THROUGHPUT***, and the only one that is genuinely hard.

⭐⭐ THE ORDER TO REACH FOR THEM: ***X, THEN Z, THEN Y.***
⭐   ⇒ ⭐⭐ MOST TEAMS DO Y FIRST BECAUSE IT IS THE ONE WITH THE
⭐     EXCITING NAME, AND THEN DISCOVER THEY HAVE FIVE SERVICES
⭐     THAT ALL SHARE ONE OVERLOADED DATABASE — ⭐ which is Day
⭐     340's distributed monolith, born on day one.
```

# Part 3 — ⭐⭐ "Stateless" — the four kinds of state you forgot

```
⭐⭐ THE DEFINITION: ***NO REQUEST DEPENDS ON STATE HELD IN THE
⭐   PROCESS THAT HAPPENS TO SERVE IT.***
⭐   ⇒ ⭐ The service absolutely has state. It lives in Postgres,
⭐     Redis, S3 — ⭐⭐ SOMEWHERE ALL REPLICAS CAN SEE IT.
⭐   ⇒ ⭐⭐ THE TEST: ***KILL ANY POD MID-TRAFFIC. IF NO USER
⭐     NOTICES ANYTHING BEYOND ONE RETRY, YOU ARE STATELESS.***
```

```
⭐⭐ THE FOUR THAT HIDE — ALL FOUR ARE PYTHON-FLAVOURED:

⭐⭐ ① IN-MEMORY SESSIONS.
⭐   ⭐ `SESSION_ENGINE = 'django.contrib.sessions.backends.cache'`
⭐     with a per-process LocMem cache ⇒ ⭐⭐ LOG IN, GET POD A;
⭐     NEXT REQUEST HITS POD B; LOGGED OUT.
⭐   ⇒ ⭐ Fix: signed cookies (stateless) or Redis (shared).
⭐   ⇒ ⭐⭐ AND NOT "STICKY SESSIONS" — see Part 4.

⭐⭐ ② MODULE-LEVEL MUTABLE STATE. ⭐ The Python special.
⭐   ⭐ `_cache = {}` at module scope. `COUNTER = 0`.
⭐     `@lru_cache` on something that should be shared.
⭐   ⇒ ⭐⭐ EACH GUNICORN WORKER HAS ITS OWN COPY. With 4 workers
⭐     × 3 pods you have ***TWELVE DIVERGENT CACHES***, and a
⭐     `cache_clear()` endpoint clears exactly one of them.
⭐   ⇒ ⭐⭐ THIS IS THE #1 CAUSE OF "IT ONLY REPRODUCES SOMETIMES
⭐     IN PRODUCTION" IN PYTHON SERVICES.

⭐⭐ ③ LOCAL FILESYSTEM.
⭐   ⭐ Uploads to `/app/media`, exports to `/tmp`, a SQLite
⭐     file, a lock file.
⭐   ⇒ ⭐ The user uploads to pod A and downloads from pod B:
⭐     404. ⭐⭐ Fix: object storage (Day 327).

⭐⭐ ④ SCHEDULERS AND BACKGROUND LOOPS.
⭐   ⭐ `APScheduler` started in `startup`, or a `while True`
⭐     task, or `@app.on_event("startup")` doing work.
⭐   ⇒ ⭐⭐ THREE REPLICAS ⇒ THE NIGHTLY EMAIL GOES OUT THREE
⭐     TIMES. ⭐ Day 264's advisory lock exists precisely for
⭐     this, and this is the day it stops being an abstraction.
```

```python
# ⭐⭐ THE BUG, IN THE FORM YOU WILL ACTUALLY MEET IT
_rates: dict[str, Decimal] = {}                 # ❌ per-process

@app.get("/convert")
async def convert(amount: Decimal, ccy: str) -> Decimal:
    if ccy not in _rates:                       # ⭐ warms once…
        _rates[ccy] = await fetch_rate(ccy)     # ⭐ …per worker
    return amount * _rates[ccy]                 # ⭐⭐ AND NEVER
                                                #   EXPIRES, SO
                                                #   POD A AND POD
                                                #   B QUOTE
                                                #   DIFFERENT
                                                #   PRICES FOR
                                                #   DAYS
```

```python
# ⭐⭐ THE FIX IS NOT "ADD A TTL" — IT IS "MOVE IT OUT"
async def get_rate(ccy: str) -> Decimal:
    if (hit := await redis.get(f"rate:{ccy}")) is not None:
        return Decimal(hit)
    rate = await fetch_rate(ccy)
    await redis.set(f"rate:{ccy}", str(rate), ex=300)  # ⭐ shared
    return rate
# ⭐ A per-process cache is still fine — as a *second* layer with
# ⭐ a short TTL in front of Redis (Day 326's near-cache).
# ⭐⭐ WHAT IS NEVER FINE IS A PER-PROCESS CACHE AS THE ***ONLY***
# ⭐   COPY OF SOMETHING THAT MUST AGREE ACROSS REPLICAS.
```

# Part 4 — ⭐⭐ Sticky sessions: what they cost

```
⭐⭐ STICKY (SESSION AFFINITY): the LB pins a client to one
⭐   backend by cookie or IP hash.
⭐   ⇒ ⭐ It makes in-process state "work". ⭐⭐ IT IS A DEBT,
⭐     NOT A SOLUTION.

⭐⭐ WHAT IT BREAKS — FIVE THINGS, AND SAY THEM IN THIS ORDER:
⭐   ① ⭐⭐ DEPLOYS LOG EVERYONE OUT. Rolling restart ⇒ every
⭐        pinned session dies.
⭐   ② ⭐ SCALING OUT DOESN'T REBALANCE. New pods get only new
⭐        sessions; old pods stay hot for hours.
⭐   ③ ⭐ A LOST POD LOSES REAL USER DATA, not just a retry.
⭐   ④ ⭐ IP hashing collapses behind corporate NAT and mobile
⭐        carriers — ⭐⭐ 4,000 USERS BEHIND ONE IP ALL LAND ON
⭐        ONE POD.
⭐   ⑤ ⭐ Autoscaling down becomes user-visible.

⭐⭐ WHERE IT IS LEGITIMATE — ONE PLACE, AND ONLY ONE:
⭐   ***WHEN THE STATE IS THE CONNECTION ITSELF.***
⭐   ⭐ A WebSocket is pinned by physics (Day 269, Day 352). You
⭐     do not "share" a TCP socket; you route ***to*** it.
⭐   ⇒ ⭐⭐ WHICH IS WHY DAY 269 SAID "THE SOCKET IS AN
⭐     OPTIMISATION, THE DATABASE IS THE TRUTH" — the pin is
⭐     acceptable exactly because losing it costs a reconnect
⭐     and nothing else.
```

# Part 5 — ⭐ The stateful tier, which never goes away

```
⭐⭐ YOU CAN MAKE THE APP TIER STATELESS. ⭐⭐ YOU CANNOT MAKE
⭐   THE DATA TIER STATELESS. ⭐ You have only moved the problem,
⭐   deliberately, to one place where it can be solved once.
⭐   ⇒ ⭐⭐ THAT SENTENCE IS THE WHOLE POINT OF THIS DAY. Stages
⭐     328–332 are that one place.

⭐⭐ SO THE ARCHITECTURE EVERYONE CONVERGES ON:
⭐   ⭐ Stateless app tier   ⇒ scale by cloning (X)
⭐   ⭐ Stateful data tier   ⇒ scale by replication (328) and
⭐     partitioning (329)
⭐   ⭐ Shared session/cache ⇒ Redis
⭐   ⭐ Shared blobs         ⇒ object storage
⭐   ⭐ Shared work          ⇒ a queue with one consumer per item

⭐⭐ AND THE COROLLARY WORTH SAYING ALOUD IN AN INTERVIEW:
⭐   ***"STATELESS" IS NOT A VIRTUE, IT IS A TRADE: YOU PAY A
⭐      NETWORK HOP ON EVERY REQUEST TO BUY THE ABILITY TO KILL
⭐      ANY BOX AT ANY TIME.***
⭐   ⇒ ⭐ At 0.5 ms per hop (Day 323) that trade is nearly always
⭐     worth it — ⭐⭐ AND KNOWING THE PRICE IS WHAT MAKES IT A
⭐     DECISION RATHER THAN A SLOGAN.
```

# Part 6 — ⭐⭐ Graceful shutdown: statelessness in practice

```
⭐⭐ BEING STATELESS ONLY PAYS OFF IF KILLING A POD IS CHEAP.
⭐   ⭐ It is not, by default.

⭐⭐ THE SEQUENCE THAT MAKES IT CHEAP — ALL FIVE STEPS:
⭐   ① ⭐ SIGTERM arrives (⭐⭐ EXEC-FORM CMD ONLY — Day 282).
⭐   ② ⭐⭐ READINESS FAILS IMMEDIATELY, LIVENESS DOES NOT. The
⭐        LB stops sending new work; the pod stays alive.
⭐   ③ ⭐⭐ SLEEP ~5 SECONDS BEFORE CLOSING ANYTHING. ⭐ The LB
⭐        needs time to notice. ⭐⭐ SKIPPING THIS IS THE #1
⭐        CAUSE OF 502s DURING DEPLOYS, AND IT LOOKS LIKE A
⭐        RANDOM NETWORK PROBLEM FOREVER.
⭐   ④ ⭐ Finish in-flight requests, up to a timeout.
⭐   ⑤ ⭐ Close pools, flush metrics/logs, exit 0.
⭐   ⇒ ⭐ The grace period must exceed step ③ + your p99 +
⭐     step ⑤, or the orchestrator SIGKILLs you mid-request.
```

```python
# ⭐ FastAPI lifespan — the shape, not the ceremony
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.ready = True
    yield                                    # ⭐ serving
    app.state.ready = False                  # ⭐⭐ ② readiness off
    await asyncio.sleep(5)                   # ⭐⭐ ③ LB catch-up
    await engine.dispose()                   # ⭐ ⑤

@app.get("/readyz")
async def readyz():
    if not app.state.ready:
        raise HTTPException(503)             # ⭐ drain signal
    return {"ok": True}
```

# Part 7 — ⭐ Auditing your own service in fifteen minutes

```
⭐⭐ RUN THESE FIVE GREPS. EACH ONE FINDS A REAL BUG.
⭐   ① `grep -rn "^[A-Z_]* = \[\]\|^[A-Z_]* = {}" app/`
⭐        ⇒ module-level mutable state
⭐   ② `grep -rn "lru_cache\|@cache" app/`
⭐        ⇒ per-process memoisation — ⭐⭐ ASK OF EACH: "MUST
⭐          ALL REPLICAS AGREE ON THIS?"
⭐   ③ `grep -rn "open(\|Path(\|/tmp" app/`
⭐        ⇒ local filesystem
⭐   ④ `grep -rn "APScheduler\|BackgroundTasks\|on_event" app/`
⭐        ⇒ per-replica schedulers
⭐   ⑤ `grep -rn "threading.Lock\|asyncio.Lock" app/`
⭐        ⇒ ⭐⭐ EVERY ONE OF THESE IS A CORRECTNESS CLAIM THAT
⭐          IS FALSE AT TWO REPLICAS UNLESS IT GUARDS ONLY
⭐          PROCESS-LOCAL RESOURCES (Day 310).

⭐⭐ THEN THE ONE TEST THAT PROVES IT:
⭐   ***RUN TWO REPLICAS. SEND ALTERNATE REQUESTS TO EACH.
⭐      ASSERT THE SESSION, THE COUNTER AND THE CACHE ALL AGREE.***
⭐   ⇒ ⭐ `docker compose up --scale api=2` and a twenty-line
⭐     script. ⭐⭐ THIS TEST HAS FOUND A BUG IN EVERY SERVICE
⭐     I HAVE EVER POINTED IT AT.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ "Stateless means no state" | It means no state *in the serving process*. The state moved; it didn't vanish |
| ⭐⭐ Module-level `dict` as a cache | One copy per worker per pod. Twelve divergent caches, and `cache_clear()` clears one |
| ⭐ `@lru_cache` on user-visible data | Same bug with a decorator on it. Fine for pure functions, wrong for shared truth |
| ⭐⭐ Sticky sessions as the fix | Deploys log everyone out and scaling out doesn't rebalance. It's a debt |
| ⭐ IP-hash affinity | Corporate NAT puts thousands of users on one pod |
| ⭐⭐ Scheduler in the app process | N replicas send the nightly email N times. Advisory lock or a real scheduler |
| ⭐ Local filesystem for uploads | Upload to pod A, download from pod B, 404 |
| ⭐⭐ No sleep before draining | The LB is still routing to you. This is where deploy 502s come from |
| ⭐ Going horizontal before indexing | Most "we need to scale out" is a missing index |
| ⭐⭐ Functional split (Y) first | Five services on one database is a distributed monolith on day one |

## Interview questions

**1. "What does stateless mean?"**
> ⭐⭐ No request depends on state held in the process that happens to serve it. The service has plenty
> of state — it lives where every replica can see it. ⭐ The test is operational, not architectural:
> **kill any pod mid-traffic and no user notices beyond one retry.** ⭐ And it's a trade, not a virtue —
> you pay a network hop per request to buy the right to kill any box at any time.

**2. "Vertical or horizontal — which first?"**
> ⭐ Vertical until it hurts. A 128-core box is cheap next to six months of sharding work, and most
> "we need to scale out" turns out to be a missing index. ⭐⭐ But the reason people eventually go
> horizontal usually isn't throughput — **it's that one box is one failure domain, and no amount of
> RAM buys availability.**

**3. "Your app works on one pod and breaks on three. Where do you look?"**
> ⭐ Four places, in this order: module-level mutable state and `lru_cache`; sessions in a local cache;
> the local filesystem; and anything scheduled at startup. ⭐⭐ In Python the first is the most common
> by a distance, because a module-level dict is invisible — it doesn't look like infrastructure, it
> looks like a variable.

**4. "When are sticky sessions acceptable?"**
> ⭐⭐ When the state *is* the connection — a WebSocket, an SSE stream. You can't share a TCP socket,
> so you route to it. ⭐ Anywhere else it's a debt: deploys log everyone out, scaling out doesn't
> rebalance, and losing a pod loses user data instead of costing a retry.

**5. "Walk me through a graceful shutdown."**
> ⭐ SIGTERM must actually reach the process — exec-form `CMD`, not shell form. ⭐⭐ Then **fail
> readiness but not liveness, sleep five seconds so the load balancer notices**, drain in-flight
> requests to a timeout, close pools, exit zero. ⭐ Skipping the sleep is where deploy-time 502s come
> from, and they look like a random network problem for months.

**6. "Explain the scale cube."**
> ⭐ X is cloning — scales request volume, needs statelessness. Z is partitioning — the only axis that
> scales data size and write throughput, and the only genuinely hard one. Y is functional split —
> scales teams. ⭐⭐ Reach for them X, then Z, then Y; **teams that do Y first end up with five
> services sharing one overloaded database, which is all of the cost and none of the benefit.**

## 🎙️ Articulation drill

**Two minutes.** Lead with the definition people get wrong: **stateless doesn't mean no state, it means
no request depends on state in the process that happens to serve it** — the state moved somewhere all
replicas can see, and the test is operational: kill any pod mid-traffic and nobody notices beyond a
retry. Then the four hiding places, with the Python one first, because it's the one that bites: **a
module-level dict is one cache per worker per pod, so four workers on three pods is twelve divergent
caches and your clear-cache endpoint clears one of them** — then sessions in local memory, the local
filesystem, and schedulers started in the app process that send the nightly email once per replica.
Say plainly why sticky sessions aren't the fix: **deploys log everyone out, scaling out doesn't
rebalance, and IP hashing puts an entire office on one pod** — and name the one place they're
legitimate, which is when the state *is* the connection, because you can't share a socket. Close on
the honest framing: **stateless is a trade, not a virtue — half a millisecond a request to buy the
right to kill any box at any time** — and on the fact that you can't make the data tier stateless at
all, you've just moved the problem to one place where it gets solved once.
