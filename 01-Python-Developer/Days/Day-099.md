# Day 099

**L-099** · ⭐⭐ **Ruff, mypy and pre-commit** — the automated reviewer, so humans review design

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every class of problem a machine can find should be found by a machine
> before a human looks — not because the machine is smarter, but because human review attention is the
> scarcest resource on a team and it should be spent on design and correctness, never on a missing
> import or a trailing space.**
>
> ⭐ Day 088 said not to request review on red CI. **Today is building the CI that makes that
> meaningful**, and it is roughly two hours of setup that pays back every week thereafter.

# Part 1 — ⭐⭐ Ruff — lint and format, in one fast tool

```toml
# pyproject.toml
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = [
    "E", "W",   # ⭐ pycodestyle
    "F",        # ⭐⭐ pyflakes — undefined names, unused imports. REAL BUGS.
    "I",        # ⭐ isort — import ordering, automatically fixed
    "UP",       # ⭐ pyupgrade — modernise syntax for your target version
    "B",        # ⭐⭐ bugbear — see below. The highest-value set.
    "SIM",      # simplify
    "C4",       # comprehensions
    "RUF",      # ruff's own
]
ignore = ["E501"]        # ⭐ line length — the formatter owns this

[tool.ruff.lint.per-file-ignores]
"tests/*" = ["S101"]     # ⭐ assert is the point of a test
```

```bash
ruff check . --fix        # ⭐ lint, and fix what is mechanically fixable
ruff format .             # ⭐⭐ format (Black-compatible)
```

```
⭐⭐ FLAKE8-BUGBEAR ("B") IS THE SET THAT EARNS ITS PLACE, BECAUSE IT FINDS BUGS
⭐   RATHER THAN STYLE — AND YOU HAVE MET EVERY ONE OF THESE ALREADY:
⭐   B006  ⭐⭐ MUTABLE DEFAULT ARGUMENT                          ⇒ Day 025
⭐   B008  a function call in a default argument                 ⇒ Day 025
⭐   B023  ⭐⭐ a loop variable captured by a closure              ⇒ Days 030, 043
⭐   B904  `raise` inside `except` without `from`                ⇒ Day 059
⭐   B905  `zip()` without `strict=`  ⭐ silently truncates       ⇒ Day 049
⭐   B017  `pytest.raises(Exception)`                            ⇒ Day 094
⭐   ⇒ ⭐⭐ THAT IS FIVE REAL BUG CLASSES FROM STAGE 1, CAUGHT AUTOMATICALLY, ON
⭐        EVERY SAVE, FOREVER. ⭐ This is the argument for a linter in one line.
```

```
⭐⭐ WHY FORMATTING SHOULD BE AUTOMATED AND THEN NEVER DISCUSSED AGAIN:
⭐   the point is NOT that the tool's choices are better than yours. ⭐⭐ IT IS
⭐   THAT THE ARGUMENT HAS A RECURRING COST AND ZERO VALUE. Automating it
⭐   converts a permanent low-grade social cost into nothing at all.
⭐   ⇒ ⭐⭐ AND THE UNDER-RATED BENEFIT: consistent formatting makes DIFFS
⭐        MEANINGFUL. Without it, a PR contains reformatting noise and the
⭐        reviewer cannot see the actual change (Day 088).
⭐   ⇒ ⭐ do the big reformat as ONE commit, then add its SHA to
⭐        .git-blame-ignore-revs so `git blame` (Day 087) skips it forever.
```

# Part 2 — ⭐ mypy, adopted gradually

```toml
[tool.mypy]
python_version = "3.12"
strict = true                       # ⭐⭐ the goal (Day 062)
warn_unreachable = true
show_error_codes = true

[[tool.mypy.overrides]]             # ⭐⭐ THE ESCAPE HATCH THAT MAKES ADOPTION POSSIBLE
module = ["myapp.legacy.*"]
disallow_untyped_defs = false

[[tool.mypy.overrides]]
module = ["untyped_third_party.*"]
ignore_missing_imports = true       # ⭐ a library with no stubs
```

```
⭐⭐ THE ADOPTION STRATEGY THAT ACTUALLY WORKS ON AN EXISTING CODEBASE — because
⭐   "turn on strict everywhere" produces 4,000 errors and gets reverted:
⭐   1. ⭐⭐ TURN STRICT ON GLOBALLY, then add per-module overrides RELAXING it
⭐        for the existing mess. ⭐⭐ NOTE THE DIRECTION: new modules are strict
⭐        BY DEFAULT and the exceptions are an explicit, visible, shrinking list.
⭐        ⭐ The opposite arrangement never converges, because nobody opts in.
⭐   2. ⭐ delete one override per week. It is a ratchet.
⭐   3. ⭐⭐ CI FAILS ON ANY NEW ERROR. That is the whole mechanism.
⭐   4. ⭐ every `# type: ignore` carries an error code and a reason
⭐        (`# type: ignore[arg-type]  # lib stubs are wrong, see #812`)
⭐        ⇒ ⭐ `warn_unused_ignores` then deletes them when they stop being needed.
```

⭐⭐ **`Any` is a defect, not a placeholder** (Day 062) — and `disallow_any_explicit` makes that
enforceable where you are ready for it. ⭐ **Type stubs**: `types-requests`, `pandas-stubs` and
friends go in your dev dependencies (Day 075).

# Part 3 — ⭐⭐ pre-commit

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-merge-conflict          # ⭐ conflict markers (Day 087)
      - id: check-added-large-files       # ⭐⭐ Day 084 — a binary is in history FOREVER
        args: [--maxkb=500]
      - id: detect-private-key            # ⭐⭐ Day 085

  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.0
    hooks:
      - id: gitleaks                      # ⭐⭐ THE SECRET SCANNER (Day 085)
```

```bash
pre-commit install          # ⭐ wires it into .git/hooks (Day 084)
pre-commit run --all-files  # ⭐⭐ the first run, and what CI runs
pre-commit autoupdate       # ⭐ bump the pinned revs
```

```
⭐⭐ THE TWO HOOKS THAT ARE NOT ABOUT STYLE AT ALL, AND ARE THE REASON TO INSTALL
⭐   PRE-COMMIT EVEN IF YOU DISLIKE HOOKS:
⭐   · ⭐⭐ GITLEAKS / detect-private-key ⇒ ⭐⭐ Day 085 showed that a committed
⭐        secret is not removable — you rotate, you do not clean. ⭐ THE ONLY
⭐        REAL DEFENCE IS NEVER COMMITTING IT, and this is that defence.
⭐   · ⭐⭐ check-added-large-files ⇒ Day 084: a 200 MB CSV is in the object
⭐        database forever, on every clone, for every future colleague.
⭐   ⇒ ⭐ both prevent PERMANENT damage. Everything else in the file merely
⭐        prevents annoyance.
```

```
⭐⭐ THE RULE ABOUT WHERE THE GATE REALLY IS — and it is the point people miss:
⭐   PRE-COMMIT IS A FAST, LOCAL, ADVISORY GATE. ⭐⭐ IT IS NOT AUTHORITATIVE,
⭐   BECAUSE `git commit --no-verify` EXISTS and people use it at 6 p.m.
⭐   ⇒ ⭐⭐ THEREFORE CI MUST RUN THE SAME CHECKS — `pre-commit run --all-files`
⭐        — AND THAT IS THE REQUIRED CHECK ON THE BRANCH (Day 088).
⭐   ⇒ ⭐ pre-commit's job is to give you the answer in 2 seconds instead of 4
⭐        minutes. ⭐⭐ CI's job is to make it true.
⭐   ⇒ ⚠️ ⭐ AND KEEP IT FAST. A pre-commit that takes 40 seconds gets bypassed,
⭐        and a bypassed hook protects nobody. ⭐⭐ Put mypy and the test suite
⭐        in CI, not in the commit hook.
```

# Part 4 — ⭐ The pipeline, and the honest limit

```yaml
# .github/workflows/ci.yml — the shape, not the syntax
jobs:
  quality:                       # ⭐ ~30 seconds
    - uses: astral-sh/setup-uv
    - run: uv sync --frozen      # ⭐⭐ --frozen: fail if the lockfile is stale (Day 075)
    - run: pre-commit run --all-files
    - run: mypy src

  test:                          # ⭐ runs in parallel with quality
    - run: pytest -m "not integration" -n auto --cov --cov-branch

  integration:                   # ⭐ needs services
    services: [postgres, redis]
    - run: pytest -m integration   # ⭐ (Day 097)
```

```
⭐⭐ FOUR PROPERTIES OF A PIPELINE PEOPLE TRUST:
⭐  1. ⭐⭐ FAST FEEDBACK FIRST. Lint and types before the slow tests, so a typo
⭐       fails in 30 seconds rather than 12 minutes.
⭐  2. ⭐ PARALLEL where possible; ⭐ cache the dependency install.
⭐  3. ⭐⭐ THE SAME COMMANDS LOCALLY AND IN CI. ⭐⭐ "It passes on my machine" is
⭐       almost always a DIFFERENT COMMAND, not a different machine — a `make
⭐       check` target that CI also runs removes the whole category.
⭐  4. ⭐⭐ REQUIRED CHECKS ON THE PROTECTED BRANCH (Day 088), or none of it is
⭐       enforced.
⭐  ⇒ ⭐ and `uv sync --frozen` in CI is the line that makes Day 075's lockfile
⭐       mean something: without it, CI can silently resolve different versions.
```

```
⭐⭐ THE HONEST LIMIT, AND SAY IT — IT IS WHAT KEEPS TOOLING IN PROPORTION:
⭐   NONE OF THIS MAKES CODE GOOD. A perfectly formatted, fully typed,
⭐   lint-clean function can be the wrong abstraction solving the wrong problem.
⭐   ⇒ ⭐⭐ WHAT TOOLING DOES IS REMOVE THE NOISE FLOOR, SO THAT REVIEW IS ABOUT
⭐        SUBSTANCE. ⭐ A reviewer who spends attention on import order has none
⭐        left for "this endpoint is not idempotent" or "this lock is held across
⭐        a network call" — ⭐⭐ and those are the comments only a human can make.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Debating formatting | ⭐⭐ Automate it. Recurring cost, zero value. |
| ⭐ Only enabling `E`/`W` | ⭐⭐ `F` and `B` find **real bugs** — mutable defaults, closure capture, `raise` without `from`. |
| A reformat mixed into a feature PR | ⭐ Reviewer cannot see the change. Separate commit + `.git-blame-ignore-revs`. |
| ⭐⭐ **Turning on strict mypy everywhere at once** | ⭐⭐ 4,000 errors, reverted by Friday. Strict globally, relax per module. |
| Relaxed by default, strict opt-in | ⭐ Never converges — nobody opts in. |
| ⭐ Bare `# type: ignore` | ⭐ Error code and reason, plus `warn_unused_ignores`. |
| ⭐⭐ **Relying on pre-commit alone** | ⭐⭐ `--no-verify` exists. CI must run the same checks. |
| A 40-second pre-commit | ⭐ It gets bypassed. Keep mypy and tests in CI. |
| No secret scanner | ⭐⭐ A committed secret cannot be removed — only never committed. |
| Slow tests before lint in CI | ⭐ A typo should fail in 30 seconds. |
| ⭐ `uv sync` without `--frozen` in CI | ⭐⭐ The lockfile stops meaning anything. |
| Thinking green CI means good code | ⭐⭐ It means the noise is gone. Design is still a human job. |

## Interview questions

**Q: What's in your Python tooling setup?**
> Ruff for lint and formatting, mypy for types, pre-commit to run the fast checks locally, and CI
> running the same commands as the authority. On Ruff I'd enable more than the default: `F` from
> pyflakes catches undefined names and unused imports, and bugbear catches genuine bug classes —
> mutable default arguments, loop variables captured by closures, `raise` inside `except` without
> `from`, `zip` without `strict`. Those are five real bugs found automatically on every save, which
> is the whole argument for a linter in one sentence.

**Q: How would you introduce mypy to a large untyped codebase?**
> Strict globally, then per-module overrides relaxing it for the existing mess — and the direction
> matters. That way new modules are strict by default and the exceptions are an explicit, visible,
> shrinking list. The opposite arrangement, relaxed by default with strict opt-in, never converges
> because nobody opts in. Then CI fails on any new error, so it's a ratchet, and you delete an
> override a week. I'd also require every `# type: ignore` to carry an error code and a reason, with
> `warn_unused_ignores` on so they get removed when they stop being needed.

**Q: Why not rely on pre-commit alone?**
> Because `git commit --no-verify` exists and people use it when they're in a hurry, so local hooks
> are advisory by construction. Pre-commit's job is to give you the answer in two seconds instead of
> four minutes; CI's job is to make it actually true, running the same `pre-commit run --all-files`
> as a required check on the protected branch. The related discipline is keeping the hook fast — a
> forty-second pre-commit gets bypassed, and a bypassed hook protects nobody, so mypy and the test
> suite belong in CI rather than the commit hook.

**Q: Which pre-commit hooks matter most?**
> The two that prevent permanent damage rather than annoyance: a secret scanner like gitleaks, and
> `check-added-large-files`. A committed secret can't be removed — you rotate the credential, you
> don't clean history — so the only real defence is never committing it. And a 200 MB CSV is in the
> object database forever, on every clone, for every future colleague. Everything else in that file
> just saves people from trailing whitespace.

**Q: Does good tooling make code good?**
> No, and I'd say so plainly. A perfectly formatted, fully typed, lint-clean function can still be
> the wrong abstraction solving the wrong problem. What tooling does is remove the noise floor so that
> review is about substance — a reviewer spending attention on import order has none left for "this
> endpoint isn't idempotent" or "this lock is held across a network call", and those are the comments
> only a human can make.

## 🎙️ Articulation drill

Record two minutes: **"What would you set up in the first week on a project with no tooling?"**
