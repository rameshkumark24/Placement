# Day 301 🏛️

**P-301** · 🏛️ **The repository pattern, done properly** — ⭐⭐ and where an ORM isn't one

**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: a repository whose methods are `get`, `save` and `filter(**kwargs)` is
> not a repository — it is your ORM with a different import path and one more file, and it has cost
> you something while abstracting nothing.**
>
> ⭐ This is the most-cargo-culted pattern in backend development. ⭐⭐ Today: the three
> justifications that are real, the two that aren't, and the read path that should bypass it entirely.

---

# Part 1 — ⭐⭐ What it is, and the version that isn't

```
⭐⭐ MARTIN FOWLER'S DEFINITION IS PRECISE AND USUALLY IGNORED:
⭐   ***A REPOSITORY MEDIATES BETWEEN THE DOMAIN AND DATA
⭐      MAPPING, ACTING LIKE AN ***IN-MEMORY COLLECTION*** OF
⭐      AGGREGATES.***
⭐   ⇒ ⭐ Two words carry the weight:
⭐     ⭐⭐ "COLLECTION" — you add to it, remove from it, and
⭐       ask it for things. ⭐ You do not tell it HOW to fetch.
⭐     ⭐⭐ "AGGREGATES" — it deals in whole consistency
⭐       boundaries (Day 250), not in rows and not in columns.

⭐⭐ THE VERSION EVERYONE WRITES, WHICH IS NOT THIS:
⭐   class OrderRepository:
⭐       def get(self, id): return session.get(Order, id)
⭐       def save(self, o): session.add(o)
⭐       def filter(self, **kw): return session.query(Order)\
⭐                                      .filter_by(**kw)
⭐   ⇒ ⭐ `get` and `save` add nothing over the session.
⭐   ⇒ ⭐⭐ AND `filter(**kwargs)` IS THE ONE THAT KILLS IT:
⭐     ***IT LETS THE CALLER SPECIFY THE QUERY***, so every
⭐     query is still written at the call site — ⭐⭐ WHICH WAS
⭐     THE ENTIRE PROBLEM THE PATTERN EXISTS TO SOLVE. You
⭐     built a pass-through and named it an abstraction.
```

# Part 2 — ⭐⭐ The three justifications that are real

```
⭐⭐ ① QUERY LOCALITY — ⭐ and this is the big one (Day 255).
⭐   ⭐ Without a repository, `filter(status="pending")` appears
⭐     in eleven places. ⭐⭐ THE DAY YOU ADD SOFT DELETE, OR
⭐     TENANCY, OR AN ARCHIVED FLAG, YOU MUST FIND ALL ELEVEN —
⭐     AND YOU WILL FIND TEN.
⭐   ⇒ ⭐ With one, `pending_for_tenant(tenant_id)` exists once.
⭐     ⭐⭐ ONE PLACE TO ADD THE FILTER, ONE PLACE TO FIX THE
⭐     N+1, ONE PLACE THAT NAMES THE INDEX IT RELIES ON.

⭐⭐ ② A NAMED, TESTABLE DOMAIN BOUNDARY
⭐   ⭐ `orders.awaiting_technician_assignment()` says what the
⭐     business means. ⭐ `filter(status=3, assigned_to=None)`
⭐     says what the table looks like — ⭐⭐ AND THE SECOND ONE
⭐     GOES STALE SILENTLY WHEN THE MEANING OF STATUS 3 CHANGES.

⭐⭐ ③ CONTROLLING THE LOADING STRATEGY
⭐   ⭐⭐ THE CALLER CANNOT KNOW whether it needs eager loading;
⭐     the repository method does, because it knows what it
⭐     returns. ⭐ `with_lines()` uses `selectinload`;
⭐     `summary()` doesn't. ⭐⭐ THAT IS WHERE THE N+1 GETS
⭐     DECIDED (Day 255), AND IT CANNOT BE DECIDED AT THE CALL
⭐     SITE WITHOUT LEAKING PERSISTENCE INTO THE SERVICE.
```

```
⭐⭐ AND THE TWO JUSTIFICATIONS THAT ARE NOT REAL:
⭐   ⭐ ❌ "SO WE CAN SWAP THE DATABASE." ⭐⭐ YOU CANNOT
⭐     (Day 300). ⭐ Your transactions, constraints, `EXCLUDE`
⭐     and `SKIP LOCKED` are semantics, not syntax.
⭐   ⭐ ❌ "SO WE CAN MOCK IT IN TESTS." ⭐⭐ A FAKE REPOSITORY
⭐     HAS NO CONSTRAINTS, NO TRANSACTIONS, NO CONCURRENCY AND
⭐     NO N+1 (Day 261) — so tests against it pass while every
⭐     guarantee you actually made goes unverified. ⭐ Test
⭐     against Postgres.
```

# Part 3 — ⭐⭐ Repository vs the things it is confused with

```
⭐⭐ | PATTERN | DEALS IN | WHO KNOWS SQL | INTERFACE SHAPE |
⭐   | REPOSITORY | ⭐ aggregates | ⭐ it does | ⭐⭐ COLLECTION-
⭐        LIKE, DOMAIN-NAMED |
⭐   | DAO        | ⭐ tables/rows | it does | CRUD per table |
⭐   | DATA MAPPER| objects ↔ rows | it does | ⭐ mapping, not
⭐        querying (this is what SQLAlchemy's ORM ***is***) |
⭐   | ACTIVE RECORD | ⭐ a row that saves itself | ⭐⭐ THE
⭐        OBJECT DOES | `order.save()` (Django) |

⭐⭐ SO, PRECISELY:
⭐   ⭐ A SQLAlchemy `Session` IS NOT A REPOSITORY. ⭐ It is a
⭐     Unit of Work plus an Identity Map. ⭐⭐ USEFUL, AND A
⭐     DIFFERENT PATTERN — it manages the transaction and object
⭐     identity; it does not express domain queries.
⭐   ⭐ Django's `Model.objects` IS NOT A REPOSITORY. ⭐ It is
⭐     an Active Record manager. ⭐⭐ AND A CUSTOM `Manager`
⭐     WITH DOMAIN-NAMED QUERYSET METHODS IS ***DJANGO'S
⭐     IDIOMATIC ANSWER TO THE SAME PROBLEM*** — it gives you
⭐     query locality without a new layer.
⭐   ⇒ ⭐⭐ WHICH MEANS: IN DJANGO, A REPOSITORY LAYER IS OFTEN
⭐     FIGHTING THE FRAMEWORK'S GRAIN FOR A BENEFIT A CUSTOM
⭐     MANAGER ALREADY GIVES YOU (Day 183). ⭐ Saying that out
⭐     loud is worth more than reciting the pattern.
```

# Part 4 — ⭐⭐ Designing the interface

```
⭐⭐ FIVE RULES, AND THE FIRST TWO DO MOST OF THE WORK:

⭐ ① ⭐⭐ RETURN AGGREGATES OR DOMAIN OBJECTS. ***NEVER RETURN
⭐     A QUERY OBJECT.*** ⭐ Returning a `Query` or a lazy
⭐     `QuerySet` means the caller composes the query, executes
⭐     it wherever it likes, and ⭐⭐ THE LOCALITY YOU BUILT
⭐     THE LAYER FOR IS GONE — ⭐ plus the query now runs
⭐     outside the transaction you thought it was in.

⭐ ② ⭐⭐ NO `filter(**kwargs)` PASSTHROUGH. ⭐ Every method is
⭐     named for a domain question. ⭐⭐ IF YOU CANNOT NAME IT,
⭐     YOU DO NOT YET UNDERSTAND THE QUERY — which is a finding,
⭐     not an inconvenience.

⭐ ③ ⭐ ONE REPOSITORY ***PER AGGREGATE***, NOT PER TABLE.
⭐     ⭐⭐ `OrderRepository` OWNS `order_lines` TOO, because
⭐     they are one consistency boundary and a line has no
⭐     independent life (Day 250). ⭐ An `OrderLineRepository`
⭐     is a sign your aggregates are actually tables.

⭐ ④ ⭐ THE UNIT OF WORK OWNS THE TRANSACTION, NOT THE
⭐     REPOSITORY. ⭐⭐ A REPOSITORY THAT COMMITS MAKES IT
⭐     IMPOSSIBLE TO PUT TWO OPERATIONS IN ONE TRANSACTION —
⭐     which is the single most damaging design error in this
⭐     whole pattern (Day 256).

⭐ ⑤ ⭐ EXPRESS SEARCH CRITERIA AS A ***DOMAIN OBJECT***, not
⭐     as fifteen optional keyword arguments:
⭐     ⭐ `find(JobSearch(tenant, status, region, due_before))`
⭐     ⇒ ⭐⭐ THE CRITERIA OBJECT IS TESTABLE, VALIDATABLE,
⭐       AND — IMPORTANTLY — ***BOUNDED***: it is the allowlist
⭐       from Day 260, expressed as a type.
```

# Part 5 — ⭐⭐ The read path bypasses it, and that is correct

```
⭐⭐ THE TENSION EVERY REAL PROJECT HITS:
⭐   ⭐ A dashboard needs: job count by status, the technician's
⭐     name, the customer's city, and last week's total —
⭐     ⭐⭐ ACROSS FOUR AGGREGATES, AS A SINGLE GROUPED QUERY.
⭐   ⇒ ⭐ Loading four aggregates to compute it is absurd: it is
⭐     a thousand objects hydrated to produce twelve numbers.
⭐   ⇒ ⭐⭐ AND THIS IS WHERE PEOPLE ADD `filter(**kwargs)` AND
⭐     DESTROY THE PATTERN — because the pattern genuinely does
⭐     not fit, and they conclude the pattern is wrong rather
⭐     than that the ***CASE*** is different.

⭐⭐ THE ANSWER IS TO SPLIT THE PATHS (Day 255 — CQRS-lite):
⭐   ⭐ THE WRITE PATH goes through repositories, loads whole
⭐     aggregates, and enforces invariants.
⭐   ⭐⭐ THE READ PATH IS A SEPARATE `queries/` MODULE THAT
⭐     WRITES SQL AND RETURNS ***DTOs OR ROWS***, NOT DOMAIN
⭐     OBJECTS. ⭐ It may join anything. It never mutates.
⭐   ⇒ ⭐⭐ THIS IS NOT A COMPROMISE OR A LEAK — IT IS THE
⭐     RECOGNITION THAT READS AND WRITES HAVE DIFFERENT
⭐     CONSISTENCY REQUIREMENTS. ⭐ A read needs no invariant
⭐     enforced, because it changes nothing.
⭐   ⇒ ⭐ And it keeps the repository small enough to stay
⭐     honest, which is the practical benefit.
```

# Part 6 — ⭐ Testing it

```
⭐   ⭐⭐ TEST REPOSITORIES AGAINST REAL POSTGRES (Day 261).
⭐     ⭐ They exist to encapsulate SQL; ⭐⭐ TESTING THEM
⭐       WITHOUT SQL TESTS NOTHING AT ALL.
⭐   ⭐ Assert on QUERY COUNT as well as results (Day 255) —
⭐     ⭐⭐ THE REPOSITORY IS EXACTLY WHERE AN N+1 IS INTRODUCED
⭐     AND EXACTLY WHERE IT SHOULD BE CAUGHT.
⭐   ⭐ A FAKE repository is legitimate for ⭐ testing a service
⭐     ORCHESTRATION in isolation — sequence, error handling,
⭐     what gets called. ⭐⭐ IT IS NOT LEGITIMATE FOR TESTING
⭐     ANYTHING THAT DEPENDS ON A CONSTRAINT, A TRANSACTION OR
⭐     A RACE, WHICH IS MOST OF WHAT YOU CARE ABOUT.
⭐   ⭐⭐ AND THE TRAP: A FAKE THAT USES A DICT HAS ***NO
⭐     UNIQUE CONSTRAINT***, so the duplicate-order test passes
⭐     against the fake and fails in production.
```

# Part 7 — ⭐⭐ So should you use one?

```
⭐⭐ USE ONE WHEN:
⭐   ⭐ you have real aggregates with invariants (Day 250)
⭐   ⭐ the same query appears in several services
⭐   ⭐ you keep introducing N+1s in the same places
⭐   ⭐ your domain is pure and must stay ORM-free (Day 300)

⭐⭐ DO ***NOT*** WHEN:
⭐   ⭐ the app is CRUD — ⭐ the ORM already is your data layer
⭐   ⭐ you are in Django and a custom `Manager` gives you the
⭐     same locality with no new layer
⭐   ⭐ every method would be a one-line pass-through
⭐   ⭐⭐ THE ONLY REASON YOU CAN GIVE IS "TO SWAP THE
⭐     DATABASE" OR "TO MOCK IT" — ⭐ both of which are false
⭐     (Part 2), and a pattern held up by two false reasons
⭐     will be removed by the first person who thinks about it.

⭐ ⇒ ⭐⭐ THE INTERVIEW-GRADE ANSWER: ***"I USE ONE FOR THE
⭐   WRITE PATH BECAUSE OF QUERY LOCALITY AND LOADING
⭐   STRATEGY, AND I BYPASS IT FOR READS. I DON'T CLAIM IT
⭐   LETS ME SWAP DATABASES, BECAUSE IT DOESN'T."***
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `get`/`save` wrappers over the session | That's the session with a different import path. |
| A `filter(**kwargs)` passthrough | The caller writes the query, which was the problem you were solving. |
| Returning a `Query` or `QuerySet` | Locality gone, and the query runs outside the transaction you assumed. |
| "So we can swap the database" | You can't; the coupling is semantic. |
| "So we can mock it" | A fake has no constraints, transactions or races — the things you care about. |
| One repository per table | One per aggregate. `OrderLineRepository` means your aggregates are tables. |
| A repository that commits | Two operations can no longer share a transaction. |
| Fifteen optional keyword filters | A criteria object is testable, bounded, and is your allowlist as a type. |
| Loading aggregates to build a dashboard | A thousand objects hydrated for twelve numbers. |
| Adding `filter()` to serve reads | The case is different; split the path instead. |
| Confusing a Session with a repository | It's a Unit of Work plus Identity Map. |
| Adding a repository layer to Django | A custom `Manager` gives the same locality without a new layer. |
| Testing repositories against fakes | They exist to encapsulate SQL; testing without SQL tests nothing. |
| No query-count assertions | The repository is exactly where N+1s are born. |
| A dict-based fake | No unique constraint, so the duplicate test passes and production fails. |

## Interview questions

**Q: What is a repository, and what isn't one?**

> A collection-like interface for aggregates: you add, remove and ask it for things in domain terms,
> and it decides how to fetch them. What isn't one is a class with `get`, `save` and a
> `filter(**kwargs)` passthrough — that's the session with an extra import path, and the `filter`
> method in particular destroys the point, because the caller is still writing the query at the call
> site, which was the problem the pattern exists to solve. A SQLAlchemy `Session` isn't a repository
> either; it's a Unit of Work plus an Identity Map, which is a different and also useful pattern.

**Q: Why do you use one?**

> Three reasons, and I'd be careful to give only the real ones. Query locality: without it,
> `filter(status="pending")` lives in eleven places, and the day I add tenancy or soft delete I have
> to find all eleven and I'll find ten. A named domain boundary, so the method says
> `awaiting_technician_assignment` rather than `status=3, assigned_to=None`, which goes stale silently
> when the meaning of status 3 changes. And control of the loading strategy — the caller can't know
> whether eager loading is needed, but the method does, and that's where N+1s get decided.

**Q: And the reasons you don't give?**

> Swapping the database, and mocking. You can't swap it — transactions, constraints, `EXCLUDE` and
> `SKIP LOCKED` are semantic coupling that no interface hides. And a fake repository has no
> constraints, no transactions, no concurrency and no N+1, so a suite that runs against it verifies
> that my Python parses while every guarantee I actually made goes untested. A dict-based fake doesn't
> even have a unique constraint, so the duplicate-order test passes and production fails.

**Q: How do you handle a dashboard that spans four aggregates?**

> It doesn't go through repositories. Loading four aggregates to produce twelve numbers means
> hydrating a thousand objects for nothing, and this is exactly where people add a `filter()`
> passthrough and destroy the pattern — because the pattern genuinely doesn't fit and they conclude
> it's wrong rather than that the case is different. So I split the paths: writes go through
> repositories and load whole aggregates so invariants can be enforced; reads go through a separate
> queries module that writes SQL and returns DTOs. A read needs no invariant enforced because it
> changes nothing, and keeping reads out keeps the repository small enough to stay honest.

**Q: Would you use one in Django?**

> Usually not, and I'd say why rather than treating it as a rule. Django's ORM is Active Record, so a
> repository layer fights the grain — and a custom `Manager` with domain-named `QuerySet` methods
> gives me the same query locality and the same loading-strategy control without adding a layer.
> Fighting a framework's grain is a real cost, and the benefit here is already available idiomatically.

## Today's build

1. ⭐⭐ Audit every repository method in the flagship. Delete any that is a one-line pass-through.
2. ⭐⭐ Find and remove any `filter(**kwargs)` or `QuerySet`-returning method.
3. ⭐ Rename every remaining method to a domain question. List the ones you couldn't name.
4. ⭐⭐ For each unnameable method, work out what the query actually means — that's the finding.
5. ⭐ Check you have one repository per aggregate, not per table. Merge any that are per-table.
6. ⭐⭐ Confirm no repository commits. Move any commit into the Unit of Work.
7. ⭐ Replace a multi-keyword search method with a criteria object, and validate it.
8. ⭐⭐ Add query-count assertions to your three busiest repository methods.
9. ⭐⭐ Create `queries/` for the read path, move the dashboard query into it, and measure the object count before and after.
10. ⭐ Add a test asserting nothing in `queries/` performs a write.
11. ⭐⭐ Take one dict-based fake, write a test that should fail on a unique constraint, and watch it pass.
12. ⭐ Rewrite that test against real Postgres and watch it fail correctly.
13. ⭐⭐ Write the ADR: the three reasons you use repositories, the two you reject, and the read-path split.

## 🎙️ Articulation drill

**Two minutes: "Do you use the repository pattern?"**

Answer with a position rather than a definition: **for the write path, yes, and I bypass it for
reads.** Give the three real justifications — **query locality, because otherwise `status="pending"`
lives in eleven places and the day you add tenancy you find ten of them**; a domain-named boundary
that doesn't go stale like `status=3`; and control of the loading strategy, since the caller can't
know whether it needs eager loading but the method does, and that's where N+1s are decided. Then
volunteer the reasons you *don't* give, because that's what shows you've thought about it: **not to
swap the database, because the coupling is semantic — transactions, constraints, `SKIP LOCKED` — and
not to mock it, because a fake has no constraints and no races**, so those tests verify that your
Python parses. Name what disqualifies an implementation: **`get`, `save` and `filter(**kwargs)` is the
session with a different import path**, and returning a `QuerySet` hands the query back to the caller.
Then the tension and its resolution: a dashboard spanning four aggregates doesn't fit, and **that's
where people add `filter()` and destroy the pattern** — so split the paths, writes through
repositories and reads through a queries module returning DTOs, **which isn't a compromise, it's
recognising that a read enforces no invariant because it changes nothing.** Close with the honest
Django note: there, a custom manager gives the same locality without a new layer.
