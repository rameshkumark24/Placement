# Day 258 🏗️

**P-258** · 🔐 **Authentication** — ⭐⭐ refresh rotation, reuse detection, and the four traps in login

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: rotation without reuse detection is not a security feature, it is
> bookkeeping. The value is entirely in what happens when an old refresh token is presented — because
> that is the only observable evidence you will ever get that a token was stolen.**
>
> ⭐ Login is four lines of code and four separate traps, and one of them turns your login endpoint
> into a denial-of-service surface for the whole API.

# Part 1 — ⭐⭐ Passwords, and the trap that takes down the API

```python
from argon2 import PasswordHasher
ph = PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4)
# ⭐ argon2id, ~150–250 ms by design. ⭐⭐ THE SLOWNESS IS THE FEATURE:
#   it is what makes an offline attack on a stolen hash expensive.

@router.post("/login")
def login(body: LoginRequest, ...):          # ⭐⭐ NOTE: `def`, NOT
    ...                                      #    `async def` (Day 134)
```

```
⭐⭐ THE TRAP, AND IT IS THE SHARPEST ONE IN THE PROJECT:
⭐   ⭐ `async def login(...)` with a 200 ms CPU-bound hash inside
⭐     ⇒ ⭐⭐ IT BLOCKS THE EVENT LOOP FOR 200 ms.
⭐   ⇒ ⭐⭐ 20 LOGIN ATTEMPTS PER SECOND AND YOUR ***ENTIRE API*** —
⭐     every tenant, every endpoint — SERVES NOTHING. ⭐ Credential
⭐     stuffing becomes a whole-service outage, and your dashboards show
⭐     one worker pegged with no slow query anywhere.
⭐   ⇒ ⭐ `def` puts it on the threadpool. ⭐⭐ Or `await
⭐     run_in_threadpool(ph.verify, ...)` if the handler must be async
⭐     for other reasons. ⭐ Either way, DECIDE IT AND WRITE IT DOWN.

⭐⭐ AND THE OPERATIONAL HALF PEOPLE SKIP: `ph.check_needs_rehash(hash)`
⭐   ON EVERY SUCCESSFUL LOGIN. ⭐ Parameters get raised over time; this
⭐   is how existing users migrate to stronger ones without a reset
⭐   email. ⭐⭐ Store the algorithm parameters IN the hash string (argon2
⭐   does), or you can never change them.
```

# Part 2 — ⭐⭐ The four traps in the login endpoint

```
⭐ ① ⭐⭐ USER ENUMERATION VIA RESPONSE
⭐    ❌ "no account with that email" vs "incorrect password"
⭐    ⇒ ⭐⭐ ONE MESSAGE, ONE CODE, FOR BOTH: `invalid_credentials`.
⭐    ⭐ Same for password reset: ⭐⭐ "if that address exists we have
⭐      sent a link" — ALWAYS, including when it does not.

⭐ ② ⭐⭐ USER ENUMERATION VIA TIMING
⭐    ⭐ Unknown email ⇒ you skip the 200 ms hash ⇒ ⭐⭐ THE RESPONSE IS
⭐      MEASURABLY FASTER, and an attacker enumerates your user base with
⭐      a stopwatch.
⭐    ⇒ ⭐⭐ HASH A DUMMY PASSWORD ANYWAY when the user is not found.
⭐      ⭐ Keep one pre-computed dummy hash and verify against it.

⭐ ③ ⭐⭐ ACCOUNT LOCKOUT IS A DENIAL-OF-SERVICE ON YOUR OWN USERS
⭐    ⭐ "Lock after 5 failures" ⇒ ⭐⭐ ANYONE CAN LOCK ANY ACCOUNT BY
⭐      TYPING FIVE WRONG PASSWORDS. Lock the CEO out on demand.
⭐    ⇒ ⭐⭐ RATE LIMIT INSTEAD, ON TWO DIMENSIONS: per account (slow the
⭐      targeted attack) AND per IP (slow the broad one) — ⭐ with
⭐      exponential delay rather than a hard lock, so a real user's sixth
⭐      attempt succeeds a few seconds later.
⭐    ⭐ If you must lock, lock with an automatic expiry and notify.

⭐ ④ ⭐⭐ FAIL CLOSED (Day 208). If the rate limiter's Redis is down, the
⭐    LOGIN limiter FAILS CLOSED. ⭐ An unlimited brute-force window is
⭐    worse than a login outage, and it is precisely the window an
⭐    attacker waits for.
```

# Part 3 — ⭐ The tokens

```
⭐⭐ TWO TOKENS, AND THE REASON IS A TRADE BETWEEN TWO BAD OPTIONS:
⭐   ⭐ ACCESS TOKEN — ⭐ 15 min, ⭐⭐ STATELESS, verified by signature
⭐     with NO database hit. ⭐ Short because it cannot be revoked.
⭐   ⭐ REFRESH TOKEN — ⭐ 30 days, ⭐⭐ STATEFUL: a row in the database.
⭐     ⭐ Revocable, rotatable, and the thing that makes logout mean
⭐       something.
⭐   ⇒ ⭐⭐ THE WHOLE DESIGN IS: FAST CHECKS ON EVERY REQUEST, WITH A
⭐     BOUNDED WINDOW OF NON-REVOCABILITY. ⭐ 15 minutes is the size of
⭐     the hole you are accepting; say that number out loud when asked.
```

```python
# ⭐ Access token claims — and what must NOT be in there
{
  "sub": "user:8812", "tenant": "t:7", "role": "dispatcher",
  "iat": ..., "exp": ..., "jti": "...",     # ⭐ jti for the denylist
  "iss": "fieldwork", "aud": "fieldwork-api",  # ⭐⭐ VERIFY BOTH
}
# ⭐⭐ NOT IN THERE: email, name, anything that changes, anything
#    private. ⭐ A JWT is SIGNED, NOT ENCRYPTED — it is base64, and
#    anyone holding it can read every claim. ⭐⭐ People put PII in
#    tokens constantly and it ends up in logs and browser storage.
```

```
⭐⭐ RS256 OVER HS256, AND THE REASON IS ORGANISATIONAL:
⭐   ⭐ HS256 is symmetric ⇒ ⭐⭐ EVERY SERVICE THAT VERIFIES A TOKEN CAN
⭐     ALSO MINT ONE. ⭐ Fine with one service, wrong the moment there
⭐     are two.
⭐   ⭐ RS256: the auth service holds the private key; everything else
⭐     verifies with the public key, published at a JWKS endpoint.
⭐   ⭐⭐ INCLUDE `kid` IN THE HEADER FROM DAY ONE. Without it, rotating
⭐     a signing key means invalidating every live token simultaneously;
⭐     with it, you publish both keys, sign with the new one, and retire
⭐     the old after one access-token lifetime.
⭐ ⭐⭐ AND VERIFY `iss`, `aud`, `exp` AND THE ALGORITHM. ⭐ `algorithms=
⭐   ["RS256"]` explicitly — the `alg: none` and "HS256 signed with the
⭐   public key" attacks both exist because libraries once trusted the
⭐   header.
```

# Part 4 — ⭐⭐ Rotation and reuse detection: the centrepiece

```
⭐⭐ ROTATION: EVERY USE OF A REFRESH TOKEN ISSUES A NEW ONE AND
⭐   INVALIDATES THE OLD. So a stolen refresh token is only useful until
⭐   the real user next refreshes.

⭐⭐ REUSE DETECTION: WHAT HAPPENS WHEN THE ***OLD*** ONE IS PRESENTED.
⭐   ⭐ A token that has already been rotated is being presented by
⭐     SOMEBODY. ⭐⭐ There are exactly two explanations, and both
⭐     justify the same response:
⭐       ⭐ the attacker used it first and the user just tried, or
⭐       ⭐ the user used it first and the attacker just tried.
⭐   ⇒ ⭐⭐ EITHER WAY, ***ONE OF THEM IS AN ATTACKER, AND YOU CANNOT
⭐     TELL WHICH.*** ⇒ REVOKE THE ENTIRE FAMILY. Everyone re-logs in.
⭐   ⇒ ⭐⭐ THIS IS THE ONLY MOMENT IN YOUR SYSTEM THAT PRODUCES
⭐     EVIDENCE OF TOKEN THEFT. Without it, rotation is bookkeeping.
```

```python
# ⭐ The table: a lineage, not a token list
refresh_tokens(
    id            uuid pk,
    family_id     uuid not null,        # ⭐⭐ one login session
    user_id       ..., tenant_id ...,
    token_hash    text not null,        # ⭐⭐ HASH IT. A database dump
                                        #    must not be a session dump.
    parent_id     uuid null,            # ⭐ the chain
    expires_at    timestamptz not null,
    used_at       timestamptz null,     # ⭐⭐ non-null ⇒ ALREADY ROTATED
    revoked_at    timestamptz null,
    user_agent    text, ip inet         # ⭐ for the "someone signed in"
)                                       #   email, not for enforcement
CREATE UNIQUE INDEX ON refresh_tokens (token_hash);
CREATE INDEX ON refresh_tokens (family_id) WHERE revoked_at IS NULL;
```

```python
def refresh(uow, raw_token: str, now):
    with uow:
        row = uow.tokens.get_for_update_by_hash(sha256(raw_token))
        if row is None or row.expires_at < now:
            raise InvalidCredentials()
        if row.revoked_at is not None or row.used_at is not None:
            # ⭐⭐ REUSE. This is the whole feature.
            uow.tokens.revoke_family(row.family_id, now)      # ⭐⭐ ALL
            uow.outbox.add(SuspiciousTokenReuse(row.user_id, now))
            uow.commit()
            raise InvalidCredentials()      # ⭐⭐ SAME ERROR AS ANY
                                            #    OTHER FAILURE — never
                                            #    tell the attacker they
                                            #    tripped a detection
        row.used_at = now                   # ⭐ mark rotated
        new = uow.tokens.issue(family_id=row.family_id, parent=row.id, ...)
        uow.commit()
        return access_token(row.user_id), new.raw
```

```
⭐⭐ FOUR DETAILS THAT DECIDE WHETHER THIS ACTUALLY WORKS:
⭐  ① ⭐⭐ `get_for_update` — TWO CONCURRENT REFRESHES WITH THE SAME
⭐     TOKEN MUST NOT BOTH SUCCEED. ⭐ Without the row lock, a
⭐     double-tapped page issues two families and the detection never
⭐     fires. ⭐ Day 195's lost update, in your auth system.
⭐  ② ⭐⭐ HASH THE TOKEN AT REST. Otherwise a read-only SQL injection
⭐     or a leaked backup is a full session takeover for everyone.
⭐  ③ ⭐⭐ RETURN THE SAME ERROR ON REUSE. Telling the attacker they
⭐     tripped a detection tells them to be more careful.
⭐  ④ ⭐ THE REVOCATION IS THE ALERT. Emit an event; email the user
⭐     ("you were signed out for security"); count it as a metric.
⭐     ⭐⭐ A security control nobody observes is a control nobody knows
⭐     failed.

⭐ ⭐ AND THE HONEST GAP: A LEGITIMATE RACE CAN TRIGGER IT — two tabs
⭐   refreshing simultaneously, or a mobile client retrying after a
⭐   network blip. ⭐⭐ Mitigate with a short GRACE WINDOW (accept a
⭐   just-rotated token for ~10 seconds and return the SAME new token),
⭐   ⭐ and measure your false-positive rate before you widen it.
```

# Part 5 — ⭐ Storage, logout, and the flows around the edges

```
⭐⭐ WHERE THE REFRESH TOKEN LIVES — decide per client, and the browser
⭐   answer is not the API answer:
⭐   ⭐ BROWSER: ⭐⭐ httpOnly + Secure + SameSite=Lax cookie, scoped to
⭐     the refresh path. ⭐ `httpOnly` means XSS cannot read it — which
⭐     is the entire point, since `localStorage` is readable by any
⭐     script you ever load. ⭐⭐ AND BECAUSE IT IS A COOKIE, THE REFRESH
⭐     ENDPOINT NOW NEEDS CSRF PROTECTION (Day 174) — `SameSite=Lax`
⭐     plus a double-submit token.
⭐   ⭐ MOBILE / API CLIENT: response body, stored in the keychain.
⭐   ⭐⭐ NEVER `localStorage`. Say why in one sentence: any script on
⭐     the page can read it, including one from a compromised dependency.

⭐⭐ LOGOUT — and being honest about what it cannot do:
⭐   ⭐ Revoke the refresh family and clear the cookie. ⭐⭐ THE ACCESS
⭐     TOKEN REMAINS VALID UNTIL IT EXPIRES, because it is stateless.
⭐   ⇒ ⭐ That is the 15-minute hole, and it is a deliberate trade.
⭐   ⇒ ⭐⭐ IF YOU CANNOT ACCEPT IT: a `jti` denylist in Redis with a
⭐     TTL equal to the token lifetime — ⭐ which costs a Redis lookup on
⭐     EVERY request and reintroduces the statefulness JWTs were chosen
⭐     to avoid. ⭐⭐ Know the trade; do not pretend logout is instant.
⭐   ⭐ "Log out everywhere" = revoke all families for the user. Easy,
⭐     and users expect it.

⭐⭐ THE THREE SIDE FLOWS, EACH WITH ITS TRAP:
⭐   ⭐ EMAIL VERIFICATION — single-use token, expires, ⭐⭐ and it must
⭐     not be a JWT you cannot revoke.
⭐   ⭐ PASSWORD RESET — ⭐⭐ single-use, short-lived, HASHED at rest,
⭐     ⭐⭐ AND IT REVOKES EVERY REFRESH FAMILY ON USE. ⭐ A reset that
⭐     leaves the attacker's session alive achieves nothing.
⭐   ⭐ EMAIL CHANGE — ⭐⭐ confirm at the NEW address AND notify the OLD
⭐     one. ⭐ Without the notification, an attacker who gets a session
⭐     silently takes ownership of the account.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `async def` on a login handler that hashes | 200 ms of blocked event loop; 20 attempts/sec takes down the whole API. |
| No `check_needs_rehash` | Parameters can never be raised for existing users. |
| Different messages for unknown user and wrong password | User enumeration. |
| Skipping the hash when the user isn't found | Timing enumeration — a stopwatch reveals your user base. |
| Account lockout after N failures | Anyone can lock any account on demand. |
| Failing open on the login rate limiter | That's the window an attacker waits for. |
| PII in the JWT | It's signed, not encrypted, and it ends up in logs and storage. |
| HS256 across multiple services | Anything that can verify can also mint. |
| No `kid` in the header | Key rotation invalidates every live token at once. |
| Not pinning `algorithms=` on verify | `alg: none` and public-key-as-HMAC attacks. |
| Rotation without reuse detection | Bookkeeping. The value is entirely in the reuse branch. |
| Refresh without `SELECT FOR UPDATE` | Two concurrent refreshes both succeed and detection never fires. |
| Storing refresh tokens in plaintext | A leaked backup is a session dump. |
| A distinct error on reuse | You told the attacker they tripped a detection. |
| Revoking a family with no alert | A control nobody observes is a control nobody knows failed. |
| Refresh token in `localStorage` | Any script on the page can read it. |
| Cookie refresh with no CSRF protection | You traded XSS exposure for CSRF exposure. |
| Claiming logout is instant | The access token lives until it expires — state the number. |
| A password reset that doesn't revoke sessions | The attacker's session survives the reset. |
| Changing an email without notifying the old address | Silent account takeover. |

## Interview questions

**Q: Walk me through your login endpoint.**

> It's a `def`, not an `async def`, because argon2 takes a couple of hundred milliseconds of CPU by
> design and putting that on the event loop means twenty attempts a second serves nothing for the whole
> API — credential stuffing becomes a total outage with no slow query anywhere to explain it. Then four
> traps. Identical response for unknown user and wrong password, or you've built an enumeration oracle.
> Hash a dummy password when the user isn't found, or the timing difference is the same oracle with a
> stopwatch. Rate limit rather than lock accounts, on both the account and the IP, because "lock after
> five failures" means anyone can lock anyone out on demand. And that limiter fails *closed* if Redis
> is down, unlike a capacity limiter, because an unlimited brute-force window is worse than a login
> outage and it's exactly the window an attacker waits for. On success I also call
> `check_needs_rehash`, which is how existing users migrate to stronger parameters without a reset
> email.

**Q: Explain refresh token rotation and reuse detection.**

> Rotation means every use of a refresh token issues a new one and invalidates the old, so a stolen
> token is only useful until the real user next refreshes. That alone is bookkeeping. The value is in
> reuse detection — what happens when an already-rotated token is presented. There are exactly two
> explanations: the attacker used it first and the user has just tried, or the user used it first and
> the attacker has just tried. Either way one of them is an attacker and you can't tell which, so you
> revoke the whole family and everyone re-authenticates. That's the only moment in the system that
> produces observable evidence a token was stolen. Four implementation details decide whether it works:
> the lookup takes a row lock, or two concurrent refreshes both succeed and detection never fires;
> tokens are hashed at rest, so a leaked backup isn't a session dump; the reuse response is the same
> generic error, so you don't tell the attacker they tripped a detection; and the revocation emits an
> event and a metric, because a control nobody observes is a control nobody knows failed.

**Q: What are the downsides of that design?**

> Two honest ones. First, false positives: two browser tabs refreshing simultaneously or a mobile
> client retrying after a network blip can legitimately present a rotated token, and the user gets
> logged out for no reason. The mitigation is a short grace window — accept a token rotated within
> about ten seconds and return the same new token rather than issuing another — and measuring the
> false-positive rate before widening it. Second, logout isn't instant. Revoking the family kills
> refreshing, but the access token is stateless and stays valid until it expires, so there's a
> fifteen-minute window I'm explicitly accepting. If that's unacceptable, a `jti` denylist in Redis
> closes it at the cost of a lookup on every single request, which reintroduces exactly the statefulness
> JWTs were chosen to avoid. I'd rather state the number than pretend.

**Q: Where do you store tokens on the client?**

> Depends on the client, and the browser answer isn't the API answer. In a browser, the refresh token
> goes in an httpOnly, Secure, SameSite cookie scoped to the refresh path — httpOnly is the point,
> because it means cross-site scripting can't read it, whereas `localStorage` is readable by any script
> on the page including one from a compromised dependency. But choosing a cookie means the refresh
> endpoint now needs CSRF protection, because cookies are sent automatically — so `SameSite=Lax` plus a
> double-submit token. That's the trade being made explicitly: XSS exposure for CSRF exposure, and CSRF
> has better standard defences. For a mobile or API client the token comes back in the body and lives
> in the keychain. The access token can sit in memory in both cases, since it's short-lived and
> re-obtainable.

**Q: What do the password reset and email change flows need that people forget?**

> Reset tokens have to be single-use, short-lived and hashed at rest like any other credential — and
> the one people forget is that **using a reset must revoke every refresh family**, because a reset that
> leaves the attacker's existing session alive achieves nothing. The user changes their password,
> feels safe, and the attacker is still logged in. Email change needs confirmation at the *new*
> address and notification to the *old* one — without the notification, someone who obtains a session
> can silently move the account to their own address and the real owner has no signal at all. And the
> reset response must be identical whether the address exists or not, which means it's also the flow
> where people accidentally reintroduce enumeration after fixing it on login.

## 🎙️ Articulation drill

**Three minutes: "How does authentication work in your system?"**

Start with the login endpoint's four traps, because they're concrete and most people name at most one:
identical messages, dummy hashing for timing, rate limiting rather than lockout, and failing closed.
Lead with the `def`-versus-`async def` point, because it's the one that turns a security concern into
an availability incident — **two hundred milliseconds of hashing on the event loop means twenty
attempts a second serves nothing for the entire API.** Then the two-token design and the fifteen-minute
hole stated as a number. Then spend most of your time on rotation and reuse detection, and make the
distinction explicit: **rotation alone is bookkeeping; the value is entirely in what happens when an
old token is presented, because that's the only evidence of theft you'll ever get** — two explanations,
both meaning someone is an attacker, so revoke the family. Close with the honest costs: false positives
from two tabs, and logout that isn't instant unless you pay for a denylist on every request.
