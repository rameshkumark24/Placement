# Day 300 🏛️

**P-300** · 🏛️ **Clean & hexagonal architecture** — ⭐⭐ ports, adapters, and the dependency rule

**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: the whole idea is who owns the interface. If the interface lives next to
> the implementation, you have a helper class; if it lives next to the code that *uses* it, you have
> inverted the dependency — and everything else in clean architecture is a consequence of that one
> move.**
>
> ⭐ Day 299 pointed dependencies one way. ⭐⭐ Today they point *inward*, which is a stronger claim,
> and Python makes it cheaper to honour than Java does — which is itself the lesson.

---

# Part 1 — ⭐⭐ The dependency rule, stated precisely

```
⭐⭐ ***SOURCE-CODE DEPENDENCIES POINT INWARD. ALWAYS.***
⭐   ⭐ `domain/` imports nothing from anywhere else.
⭐   ⭐ `services/` imports `domain/`.
⭐   ⭐ `infrastructure/` imports `domain/` and `services/`.
⭐   ⭐ ⭐⭐ NOTHING INSIDE IMPORTS ANYTHING OUTSIDE, EVER.

⭐⭐ AND THE PART PEOPLE MISREAD: ***CONTROL*** FLOWS OUTWARD
⭐   ALL THE TIME.
⭐   ⭐ A service calls a payment provider at runtime — of
⭐     course it does. ⭐⭐ WHAT IT DOES NOT DO IS ***IMPORT***
⭐     THE STRIPE CLIENT.
⭐   ⇒ ⭐ It calls a `PaymentPort` that `domain/` or
⭐     `services/` defines, and something at the edge supplies
⭐     the implementation. ⭐⭐ THE CALL GOES OUT; THE
⭐     DEPENDENCY POINTS IN. That inversion is the entire trick,
⭐     and it has one name: DEPENDENCY INVERSION.
```

# Part 2 — ⭐⭐ Ports and adapters: ownership is the idea

```
⭐⭐ A ***PORT*** IS AN INTERFACE OWNED BY THE INSIDE.
⭐   ⭐ It is expressed in the domain's vocabulary, not the
⭐     vendor's: ⭐⭐ `charge(amount, reference) -> ChargeResult`,
⭐     ***NOT*** `create_payment_intent(...)`.
⭐   ⭐ It contains exactly what the domain needs. ⭐⭐ IF IT
⭐     MIRRORS THE VENDOR'S API, YOU HAVE NOT ABSTRACTED
⭐     ANYTHING — YOU HAVE RENAMED IT, AND THE SECOND VENDOR
⭐     WILL NOT FIT.

⭐⭐ AN ***ADAPTER*** IMPLEMENTS IT ON THE OUTSIDE.
⭐   ⭐ `StripeAdapter`, `PostgresOrderRepository`,
⭐     `SESEmailSender`. ⭐ Vendor vocabulary lives here and
⭐     nowhere else.

⭐⭐ THE MISTAKE THAT MAKES THE WHOLE THING POINTLESS:
⭐   ⭐ Putting `PaymentPort` in `infrastructure/payments/`,
⭐     next to `StripeAdapter`, "because they belong together".
⭐   ⇒ ⭐⭐ NOW THE SERVICE IMPORTS FROM `infrastructure/` TO
⭐     GET THE INTERFACE. ⭐ The dependency arrow points
⭐     outward again, the file count went up, and ⭐⭐ YOU HAVE
⭐     PAID EVERY COST OF THE PATTERN AND RECEIVED NONE OF ITS
⭐     BENEFIT.
⭐   ⇒ ⭐ THE PORT LIVES WITH ITS CONSUMER. Always. That single
⭐     placement decision is the difference between hexagonal
⭐     architecture and a folder of interfaces.
```

# Part 3 — ⭐⭐ Why this is cheaper in Python

```
⭐⭐ IN JAVA, A PORT IS AN `interface`, AND THE ADAPTER MUST
⭐   `implements` IT — ⭐ a NAME-BASED, COMPILE-TIME contract.
⭐   ⭐ So the adapter must import the port. ⭐⭐ THE ARROW IS
⭐     STILL CORRECT (outside → inside), but every adapter is
⭐     welded to the interface's identity.

⭐⭐ IN PYTHON, `typing.Protocol` IS ***STRUCTURAL***:
```

```python
# app/services/ports.py          ⭐⭐ OWNED BY THE INSIDE
class PaymentPort(Protocol):
    def charge(self, amount: Money, reference: str) -> ChargeResult: ...

# app/infrastructure/stripe_adapter.py
class StripeAdapter:              # ⭐⭐ IMPORTS NOTHING FROM THE PORT
    def charge(self, amount: Money, reference: str) -> ChargeResult:
        ...
```

```
⭐⭐ NOTICE WHAT IS ABSENT: THE ADAPTER DOES NOT SUBCLASS,
⭐   DOES NOT REGISTER, AND DOES NOT IMPORT THE PORT AT ALL.
⭐   ⭐ `mypy` verifies at the composition root that what you
⭐     passed satisfies the protocol.
⭐   ⇒ ⭐⭐ SO THE DEPENDENCY IS ***ZERO*** IN BOTH DIRECTIONS
⭐     AT IMPORT TIME, AND STILL TYPE-CHECKED. ⭐ Java cannot
⭐     express that, which is why hexagonal architecture feels
⭐     heavier there — and why importing Java's ceremony
⭐     wholesale into Python is a mistake people make.
⭐   ⭐ Use an ABC only when you want runtime enforcement or a
⭐     shared implementation. ⭐⭐ FOR A BOUNDARY, `Protocol`
⭐     IS BOTH LIGHTER AND STRICTLY MORE DECOUPLED.
```

# Part 4 — ⭐⭐ What actually gets easier — and what doesn't

```
⭐⭐ THE HONEST LIST OF BENEFITS:
⭐   ⭐ ① ⭐⭐ TESTS WITHOUT MOCKS. A `FakePaymentPort` is
⭐        fifteen lines, it is deterministic, and it can
⭐        simulate a TIMEOUT — ⭐ which is the case that
⭐        matters (Day 263) and the case a real sandbox will
⭐        not reproduce on demand.
⭐   ⭐ ② ⭐⭐ THE DOMAIN IS READABLE. `domain/` describes the
⭐        business and nothing else — no session, no HTTP, no
⭐        vendor. ⭐ This is the benefit people undersell, and
⭐        it is the one you feel every single day.
⭐   ⭐ ③ SWAPPING A PROVIDER — ⭐ real, but rarer than the
⭐        pattern's marketing suggests.

⭐⭐ AND THE HONEST LIST OF NON-BENEFITS:
⭐   ⭐ ❌ "YOU COULD SWAP POSTGRES FOR MONGO." ⭐⭐ NO. Your
⭐     transactions, constraints, `EXCLUDE`, `SKIP LOCKED` and
⭐     query patterns are Postgres decisions that live in your
⭐     DOMAIN's assumptions (Days 187, 196). ⭐ The interface
⭐     is not the coupling; ⭐⭐ THE SEMANTICS ARE.
⭐   ⭐ ❌ "IT MAKES CHANGES CHEAPER." ⭐ Only along the axis
⭐     you abstracted (Day 298). ⭐⭐ IT MAKES CHANGES ***ON
⭐     OTHER AXES SLIGHTLY MORE EXPENSIVE***, because there is
⭐     one more file between you and the thing.
⭐   ⭐ ❌ "IT'S OBJECTIVELY BETTER." ⭐ It is a trade you make
⭐     on purpose, per boundary.
```

# Part 5 — ⭐⭐ The cost, and the place people quit

```
⭐⭐ THE FULL PATTERN SAYS: `domain/Order` AND `orm/OrderModel`
⭐   ARE DIFFERENT CLASSES, WITH A MAPPER BETWEEN THEM.
⭐   ⭐ THE BENEFIT: the domain is genuinely persistence-free;
⭐     you can restructure tables without touching rules.
⭐   ⭐⭐ THE COST, AND IT IS REAL: every field appears three
⭐     times (domain, ORM, schema), every new field is three
⭐     edits, and ⭐⭐ THE MAPPER IS PURE OVERHEAD THAT
⭐     EVERYONE RESENTS AT 6 P.M.
⭐   ⇒ ⭐⭐ SO IT IS THE FIRST THING ABANDONED UNDER DEADLINE,
⭐     AND ONCE ABANDONED PARTIALLY, YOU HAVE THE COSTS OF BOTH
⭐     APPROACHES AND THE BENEFITS OF NEITHER. ⭐ That
⭐     half-state is worse than either pure choice.

⭐⭐ THE PRAGMATIC POSITION — AND IT IS WHAT YOUR FLAGSHIP DID
⭐   (Days 254–256), SO SAY SO:
⭐   ⭐ `domain/` IS PURE: entities, value objects, the state
⭐     machine, the calculations. ⭐⭐ NO ORM IMPORTS. ENFORCED
⭐     BY DAY 299'S CONTRACT.
⭐   ⭐ Persistence uses ⭐ SQLAlchemy imperative mapping, so
⭐     the ORM maps ***TO*** the domain class rather than
⭐     replacing it — ⭐⭐ WHICH BUYS PURITY WITHOUT A HAND-
⭐     WRITTEN MAPPER, and is the specific Python affordance
⭐     that makes this affordable.
⭐   ⭐ Read models are separate and may be plain rows
⭐     (Day 255) — ⭐ they are not domain objects and pretending
⭐     otherwise costs you the N+1 you spent a day fixing.
⭐   ⇒ ⭐⭐ THAT IS A DEFENSIBLE MIDDLE, AND "I APPLIED THE
⭐     DEPENDENCY RULE AND DECLINED THE MAPPER, HERE IS WHY"
⭐     IS A BETTER INTERVIEW ANSWER THAN EITHER PURITY OR
⭐     IGNORANCE.
```

# Part 6 — ⭐⭐ The tests that prove it

```
⭐⭐ ① THE ONE-LINE CI CHECK (Day 299) — ⭐ `domain/` may not
⭐     import `sqlalchemy`, `fastapi`, `redis`, `httpx`.
⭐     ⇒ ⭐⭐ THIS IS THE ENTIRE PATTERN, MECHANISED.

⭐⭐ ② THE DELETION TEST — ⭐⭐ CAN YOU DELETE THE WEB
⭐     FRAMEWORK AND STILL RUN THE DOMAIN AND SERVICE TESTS?
⭐     ⭐ If yes, the boundary is real. ⭐ If the answer is "the
⭐       tests import `TestClient`", your services are
⭐       HTTP-shaped and you found out cheaply.

⭐⭐ ③ THE SECOND-ADAPTER TEST — ⭐ write a second
⭐     implementation of one port (in-memory, or a second
⭐     vendor's sandbox). ⭐⭐ IF THE PORT NEEDS CHANGING TO
⭐     ACCOMMODATE IT, THE PORT WAS THE FIRST VENDOR'S API
⭐     WEARING A DIFFERENT NAME. ⭐ That is the sharpest test
⭐     on this page and it takes an hour.

⭐⭐ ④ THE SPEED TEST — ⭐ domain tests should run in
⭐     milliseconds with no fixtures. ⭐⭐ IF THEY NEED A
⭐     DATABASE, THEY ARE NOT DOMAIN TESTS AND THAT DIRECTORY
⭐     IS NOT A DOMAIN.
```

# Part 7 — ⭐ When not to do this

```
⭐   ⭐ CRUD WITH NO RULES — ⭐⭐ THERE IS NO "INSIDE" TO
⭐     PROTECT. ⭐ Ports around a system whose only logic is
⭐     validation is pure ceremony.
⭐   ⭐ ONE IMPLEMENTATION, FOREVER, WITH NO TESTING BENEFIT —
⭐     ⭐ e.g. a port around your own logging.
⭐   ⭐ A SCRIPT, A SPIKE, A PROTOTYPE.
⭐   ⭐⭐ AND THE JUDGEMENT THAT MATTERS: APPLY IT ***PER
⭐     BOUNDARY***, NOT PER PROJECT. ⭐ Ports for payments,
⭐     email and search — where fakes make tests possible and
⭐     vendors genuinely change. ⭐⭐ NO PORT FOR THE DATABASE,
⭐     because you are never swapping it and the repository
⭐     already gives you the seam you actually use.
⭐   ⇒ ⭐ Being able to say ***which*** boundaries got ports
⭐     and which didn't, with a reason for each, is the whole
⭐     skill. ⭐⭐ UNIFORM APPLICATION IS A SIGN THAT NO
⭐     DECISION WAS MADE.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Thinking the dependency rule forbids outward calls | Control flows outward; only *imports* point inward. |
| Putting the port next to the adapter | Then the inside imports the outside and you've paid for nothing. |
| A port that mirrors the vendor's API | You renamed it. The second vendor won't fit. |
| Using ABCs everywhere | `Protocol` is structural: zero import coupling in both directions. |
| Importing Java's ceremony wholesale | Python's structural typing makes the same idea much cheaper. |
| Claiming you could swap Postgres | Your transactions, constraints and `SKIP LOCKED` are semantic coupling. |
| Believing abstraction makes all change cheaper | Only along the abstracted axis; other axes get slightly worse. |
| A hand-written domain/ORM mapper under deadline | It's the first thing abandoned, and the half-state is worse than either choice. |
| Treating read models as domain objects | They're rows; pretending otherwise reintroduces the N+1. |
| Domain tests that need a database | Then it isn't a domain. |
| Only one adapter, ever | Write a second one as a test — if the port must change, it wasn't a port. |
| Applying ports uniformly | Uniform application means no decision was made. Choose per boundary. |
| Ports around CRUD with no rules | There's no inside to protect. |

## Interview questions

**Q: State the dependency rule and the thing people get wrong about it.**

> Source-code dependencies point inward: the domain imports nothing, services import the domain,
> infrastructure imports both, and nothing inside ever imports anything outside. What people misread
> is that control flows outward constantly — a service obviously calls a payment provider at runtime.
> It just doesn't *import* the Stripe client. It calls a port defined on the inside, and something at
> the edge supplies the implementation. The call goes out and the dependency points in, which is
> dependency inversion, and everything else follows from it.

**Q: What's the single most common mistake with ports and adapters?**

> Putting the interface next to the implementation, in the infrastructure package, because they feel
> related. That reverses the arrow — the service now imports from infrastructure to get the interface
> — so you've added a file, added indirection, and inverted nothing. The port lives with its consumer,
> always. The second mistake is a port that mirrors the vendor's API: if it says
> `create_payment_intent` rather than `charge`, you renamed the SDK, and you'll discover it the moment
> a second provider doesn't fit that shape.

**Q: Does Python change anything here?**

> Yes, and it's one of the few places where Python is genuinely structurally better. In Java a port is
> an interface the adapter must `implements`, so the adapter imports the port. In Python `Protocol` is
> structural, so the adapter subclasses nothing, registers nothing and imports nothing — and mypy
> still verifies at the composition root that what I passed satisfies the protocol. That's zero import
> coupling in both directions with full type checking, which Java can't express. It also means
> importing Java's ceremony wholesale is a mistake; ABCs are for runtime enforcement or shared
> implementation, not for boundaries.

**Q: What does it actually buy you?**

> Two things reliably and one occasionally. Tests without mocks — a fake payment port is fifteen lines
> and can simulate a timeout on demand, which is the case that matters and the one a vendor sandbox
> won't reproduce. A readable domain, which people undersell and which you feel every day. And
> provider swapping, which is real but rarer than the marketing suggests. What it does *not* buy is
> swapping your database: transactions, constraints, `EXCLUDE` and `SKIP LOCKED` are semantic coupling
> that no interface hides. The interface isn't the coupling — the semantics are.

**Q: Did you apply it everywhere?**

> No, and I'd argue uniform application is a sign no decision was made. Ports for payments, email and
> search, where fakes make testing possible and vendors genuinely change. No port for the database,
> because I'm not swapping it and the repository already gives me the seam I actually use. And I
> declined the hand-written domain-to-ORM mapper: I kept `domain/` pure and enforced it with an
> import-linter contract, but used imperative mapping so the ORM maps *to* my domain class rather than
> replacing it. That's the honest middle — and the half-abandoned mapper is worse than either pure
> position, because you pay both costs and get neither benefit.

## 🎙️ Articulation drill

**Two minutes: "Explain hexagonal architecture."**

inward, but control flows outward all the time** — a service calls Stripe at runtime; it just doesn't
import Stripe. It calls a port the inside owns, and the edge supplies the implementation. Then name
the thing that actually decides whether you've done it: **ownership of the interface.** If the port
sits next to the adapter in the infrastructure package, the arrow reverses and you've added a file and
