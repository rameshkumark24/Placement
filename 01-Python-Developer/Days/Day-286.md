# Day 286 💥

**P-286** · 💥 **Load testing** — ⭐⭐ and breaking it on purpose

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: a load test without a hypothesis is a benchmark, and benchmarks are
> marketing — the output you want is not a big number, it is the identity of the first thing that
> breaks and the throughput at which it breaks.**
>
> ⭐ Day 168's capstone found one knee. ⭐⭐ Today is the full version: a workload shaped like
> reality, the measurement trap that makes most published numbers meaningless, four bottlenecks
> found in order, and the cascade where entirely healthy pods take each other down.

# Part 1 — ⭐⭐ What the test is for

```
⭐⭐ THREE LEGITIMATE GOALS. "HOW FAST IS IT" IS NOT ONE:
⭐   ① ⭐⭐ FIND THE FIRST BOTTLENECK AND NAME IT. There is
⭐     always exactly one at a time, and the entire value of the
⭐     exercise is learning which one and why.
⭐   ② ⭐ ESTABLISH A CAPACITY NUMBER you can plan and autoscale
⭐     against.
⭐   ③ ⭐ VERIFY BEHAVIOUR UNDER STRESS — does it degrade, or
⭐     does it collapse? ⭐⭐ THOSE ARE DIFFERENT OUTCOMES AND
⭐     ONLY ONE IS ACCEPTABLE.

⭐⭐ AND THE HYPOTHESIS, WRITTEN BEFORE YOU RUN ANYTHING:
⭐   ⭐ "I predict we saturate at ~120 rps, and the first limit
⭐     will be the database connection pool."
⭐   ⇒ ⭐⭐ THE VALUE IS IN BEING WRONG. A prediction you got
⭐     right teaches you nothing you did not already know; a
⭐     prediction you got wrong is the whole reason to run it.
```

# Part 2 — ⭐⭐ The measurement trap that invalidates most load tests

```
⭐⭐ CLOSED-LOOP (the default in JMeter, Locust, Gatling with
⭐   fixed users): ⭐ N virtual users, each sends a request,
⭐   WAITS FOR THE RESPONSE, then sends the next.

⭐   ⇒ ⭐⭐ WHEN YOUR SERVER GETS SLOWER, THE LOAD OFFERED
⭐     ***DROPS***. The test backs off in exact proportion to
⭐     your degradation.
⭐   ⇒ ⭐⭐ SO THE QUEUE NEVER GROWS, LATENCY LOOKS ALMOST FLAT,
⭐     AND YOU CONCLUDE THE SYSTEM IS FINE — right up to the
⭐     point where it collapses with no warning on the graph.
⭐   ⭐ Real users do not do this. ⭐⭐ REAL ARRIVALS ARE
⭐     INDEPENDENT OF YOUR RESPONSE TIME.

⭐⭐ OPEN-LOOP: a fixed ARRIVAL RATE, regardless of responses.
⭐   ⭐ k6 `constant-arrival-rate` · Vegeta · Locust with a
⭐     rate-based shape.
⭐   ⇒ ⭐ Now a slowdown causes a QUEUE, exactly as in production,
⭐     and ⭐⭐ THE LATENCY CLIFF APPEARS WHERE IT ACTUALLY IS.
```

```
⭐⭐ THE SAME PROBLEM AGAIN, WITH A NAME: ***COORDINATED
⭐   OMISSION.*** ⭐ If the tool pauses while the server stalls,
⭐   the requests that WOULD have been sent during the stall are
⭐   never sent — ⭐⭐ AND THOSE ARE PRECISELY THE SLOW ONES.
⭐   ⇒ ⭐ Your p99 is computed from a sample that systematically
⭐     excludes the worst experiences. ⭐⭐ IT IS NOT SLIGHTLY
⭐     OPTIMISTIC. IT CAN BE WRONG BY AN ORDER OF MAGNITUDE.
```

# Part 3 — ⭐⭐ Designing a workload that resembles reality

```
⭐⭐ FOUR THINGS TO GET RIGHT, IN ORDER OF HOW OFTEN THEY ARE
⭐   GOT WRONG:

⭐ ① ⭐⭐ DATA VOLUME. 500 rows in the test database means every
⭐     query is an index-only scan of a table that fits in cache
⭐     ⇒ ⭐⭐ YOU MEASURED NOTHING (Day 284). Seed to production
⭐     shape: millions of rows, realistic tenant skew.
⭐ ② ⭐⭐ TENANT SKEW. Uniform random tenants is the one
⭐     distribution that never occurs. ⭐ Real systems have one
⭐     tenant with 60% of the data, and ⭐⭐ THAT TENANT IS
⭐     WHERE YOUR MISSING INDEX LIVES.
⭐ ③ ⭐ THE MIX. 90/10 read/write is not the same system as
⭐     50/50 — different locks, different bloat, different cache
⭐     behaviour. Take the ratio from your real endpoints.
⭐ ④ ⭐ CACHE STATE. ⭐⭐ RUN IT BOTH WAYS: warm (steady state)
⭐     and cold (after a restart, Day 266). ⭐ The cold number is
⭐     your true capacity, because that is the state you are in
⭐     during an incident.

⭐ ⭐ AND: ramp up, hold for a REAL duration (10+ min), and
⭐   watch for the slow degradations — ⭐⭐ MEMORY GROWTH, POOL
⭐   CREEP AND TABLE BLOAT DO NOT APPEAR IN A 60-SECOND RUN.
```

# Part 4 — ⭐⭐ The number you report

```
⭐   ❌ "It does 3,000 requests per second."
⭐   ⭐⭐ AT WHAT LATENCY? WITH WHAT ERROR RATE? ON WHAT DATA?
⭐     ⭐ A number without those three is not a measurement.

⭐⭐ THE HONEST FORM:
⭐   ***"IT SUSTAINS 140 rps WITH p99 UNDER 400 ms AND A 0%
⭐      ERROR RATE. AT 180 rps p99 GOES TO 2.4 s BECAUSE THE
⭐      CONNECTION POOL SATURATES."***
⭐   ⇒ ⭐ That single sentence contains: the capacity, the SLO,
⭐     the failure point, AND the mechanism. ⭐⭐ IT IS THE
⭐     SENTENCE THE WHOLE DAY EXISTS TO PRODUCE.

⭐⭐ AND YOU FIND IT BY LOOKING FOR THE KNEE:
⭐   rps    p50    p99    errors
⭐    50    18ms   45ms   0
⭐   100    21ms   80ms   0
⭐   140    28ms  390ms   0      ⭐⭐ ← the SLO edge
⭐   180    95ms  2400ms  0      ⭐ queueing, not work
⭐   220   800ms  9800ms  3.1%   ⭐⭐ collapse
⭐ ⇒ ⭐⭐ NOTE THAT p50 BARELY MOVES UNTIL THE END. ⭐ Watching
⭐   the average would have shown you nothing at all (Day 285).
```

# Part 5 — ⭐⭐ The four bottlenecks, found in order

```
⭐⭐ THEY ALWAYS ARRIVE IN THIS ORDER, AND EACH HAS A SIGNAL
⭐   THAT IDENTIFIES IT WITHOUT GUESSING:

⭐ ① ⭐ APP CPU — ⭐⭐ usually JSON serialisation or something
⭐     synchronous on the event loop (Day 258's argon2, again).
⭐     ⭐ SIGNAL: CPU at 100%, database nearly idle.
⭐ ② ⭐⭐ THE CONNECTION POOL — the commonest by far.
⭐     ⭐ SIGNAL: app CPU low, database CPU low, ⭐⭐ AND TIME
⭐       SPENT ***WAITING TO CHECK OUT A CONNECTION***. Nothing
⭐       is busy and everything is slow — which is the signature.
⭐     ⭐ FIX: it is rarely "raise the pool" (Day 197 — Little's
⭐       Law gave 20, not 400). It is a slow query holding a
⭐       connection, or a network call inside a transaction
⭐       (Day 256).
⭐ ③ ⭐ THE DATABASE — ⭐ SIGNAL: `pg_stat_statements` by TOTAL
⭐     time, plus wait events (Day 203). ⭐⭐ `ClientRead` HIGH
⭐     MEANS IT IS NOT THE DATABASE AT ALL.
⭐ ④ ⭐ AN EXTERNAL PROVIDER — ⭐ SIGNAL: your spans show 40 ms
⭐     of you and 380 ms of them (Day 285).
⭐     ⭐⭐ AND THIS IS THE ONE YOU CANNOT FIX BY SCALING —
⭐       only by timeouts, budgets and circuit breakers.
```

# Part 6 — ⭐⭐ The cascade: healthy pods killing each other

```
⭐⭐ THE FAILURE THAT ONLY APPEARS UNDER LOAD, IN SIX STEPS:
⭐   ① a dependency slows down; requests hold connections longer
⭐   ② the pool saturates; request latency climbs
⭐   ③ ⭐ THE READINESS PROBE TIMES OUT (it queues behind real
⭐     traffic, or worse, it checks the database — Day 282)
⭐   ④ ⭐⭐ THE POD IS REMOVED FROM THE LOAD BALANCER
⭐   ⑤ ⭐⭐ ITS TRAFFIC IS REDISTRIBUTED TO THE REMAINING PODS,
⭐     WHICH ARE ALREADY AT THE LIMIT
⭐   ⑥ ⭐⭐ THEY FAIL THEIR PROBES TOO ⇒ ***THE ENTIRE FLEET
⭐     GOES DOWN, ONE POD AT A TIME, WHILE EVERY POD IS
⭐     PERFECTLY HEALTHY.***
⭐   ⇒ ⭐ Add client retries on top and the offered load
⭐     TRIPLES exactly when you can least afford it.
```

```
⭐⭐ THE FOUR DEFENCES, CHEAPEST FIRST:
⭐   ① ⭐⭐ TIMEOUTS ON EVERYTHING. ⭐ The single highest-value
⭐     line of code in this entire day, and the default in most
⭐     HTTP clients is NO TIMEOUT AT ALL. ⭐⭐ AN UNBOUNDED WAIT
⭐     TURNS A SLOW DEPENDENCY INTO YOUR OUTAGE.
⭐   ② ⭐ RETRY BUDGETS + JITTER (Day 265) — and ⭐⭐ NEVER
⭐     RETRY AT MORE THAN ONE LAYER. Three layers each retrying
⭐     three times is 27 requests for one user action.
⭐   ③ ⭐ CIRCUIT BREAKER on the provider: fail fast while it is
⭐     broken, so you free the workers instead of queueing on it.
⭐   ④ ⭐⭐ LOAD SHEDDING — above a concurrency limit, return 429
⭐     IMMEDIATELY. ⭐ Serving 80% of traffic well beats serving
⭐     100% of it at a 30-second latency, and ⭐⭐ SHEDDING IS
⭐     THE ONLY DEFENCE THAT WORKS WHEN THE OVERLOAD IS REAL
⭐     RATHER THAN A BUG.
⭐   ⭐ Plus: readiness must be CHEAP and must not check
⭐     dependencies (Day 282).
```

# Part 7 — ⭐ Chaos, proportionate, and the capacity conclusions

```
⭐ ⭐ FIVE EXPERIMENTS, EACH RUN ***DURING*** A LOAD TEST —
⭐   which is the point, since all of them are fine when idle:
⭐   ① kill a pod            ⇒ ⭐ brief errors, then rebalance
⭐   ② fail over the database⇒ ⭐ 60–120 s of write errors, then
⭐        recovery WITHOUT a restart (Day 284)
⭐   ③ ⭐⭐ ADD 300 ms TO THE PROVIDER ⇒ do your timeouts and
⭐        breaker hold, or does the pool drain?
⭐   ④ stop Redis           ⇒ ⭐ cache misses only — unless it is
⭐        also your broker (Day 265)
⭐   ⑤ ⭐ revoke a credential ⇒ does it fail loudly, or silently
⭐        stop doing background work?
```

```
⭐⭐ AND THE AUTOSCALING CONCLUSION, WHICH FOLLOWS FROM THE
⭐   NUMBERS RATHER THAN FROM A TUTORIAL:
⭐   ⭐ ❌ SCALE THE API ON CPU. ⭐⭐ AN I/O-BOUND SERVICE
⭐     SATURATES ITS POOL AT 30% CPU AND NEVER TRIGGERS.
⭐   ⭐ ✅ scale on CONCURRENCY (in-flight requests) or on rps
⭐     per task, derived from the knee you just measured.
⭐   ⭐ ✅ ⭐⭐ SCALE WORKERS ON OLDEST-MESSAGE AGE (Day 265),
⭐     never on queue depth — depth 5,000 draining is fine and
⭐     depth 5 stuck is an outage.
⭐   ⭐ And set MAXIMUMS from Day 284's connection arithmetic:
⭐     ⭐⭐ AN AUTOSCALER WITH NO CEILING WILL HAPPILY SCALE
⭐     UNTIL IT EXHAUSTS `max_connections` AND TAKES THE
⭐     DATABASE DOWN — turning a traffic spike into an outage
⭐     via the mechanism you installed to prevent one.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Load testing without a hypothesis | It's a benchmark. The value is in being wrong about a prediction. |
| A closed-loop tool with fixed users | Load drops as you slow down, so the queue never grows and the cliff hides. |
| Ignoring coordinated omission | Your p99 excludes exactly the slow requests. It can be wrong by 10×. |
| Testing against 500 rows | Everything fits in cache; you measured nothing. |
| Uniform tenant distribution | The one distribution that never occurs, and skew is where your missing index lives. |
| A 60-second run | Memory growth, pool creep and bloat need ten minutes to show. |
| Only testing warm | The cold number is your capacity during an incident. |
| Reporting max rps | A number with no latency, error rate or data size isn't a measurement. |
| Watching the average | p50 barely moves until collapse. |
| Assuming the database is the bottleneck | Low CPU everywhere plus connection-wait time is a pool problem. |
| Raising the pool to fix pool saturation | Little's Law gave 20, not 400. Find the query holding it. |
| A readiness probe that checks the database | Step three of the cascade. |
| No client timeouts | The default is unbounded, and it turns a slow dependency into your outage. |
| Retrying at three layers | 27 requests for one user action, arriving when you're already overloaded. |
| No load shedding | The only defence that works when the overload is real rather than a bug. |
| Autoscaling the API on CPU | An I/O-bound service saturates its pool at 30% CPU and never scales. |
| Autoscaling workers on queue depth | Depth is not the signal. Oldest-message age is. |
| No autoscaler ceiling | It scales until `max_connections` is exhausted and takes the database with it. |
| Chaos experiments while idle | All of them pass when idle. Run them under load. |

## Interview questions

**Q: How do you load test?**

> With a hypothesis first — I write down where I think it saturates and what the first limit will be,
> because the value is in being wrong. Then an open-loop tool with a fixed arrival rate, which matters
> more than it sounds: a closed-loop test with fixed virtual users backs off exactly in proportion to
> your degradation, so the queue never grows, latency looks flat, and the system appears fine right up
> to the point it collapses. That's coordinated omission — the requests that would have been sent
> during a stall are never sent, and those are precisely the slow ones, so p99 can be wrong by an
> order of magnitude.

**Q: What do you report?**

> Not max rps. Something like "it sustains 140 requests a second with p99 under 400 milliseconds and
> no errors; at 180 the p99 goes to 2.4 seconds because the connection pool saturates." That one
> sentence has the capacity, the SLO, the failure point and the mechanism, and it's what the whole
> exercise exists to produce. I'd also point out that p50 barely moves until the very end, which is
> why watching averages tells you nothing.

**Q: You're slow and nothing is busy. What is it?**

> Almost always the connection pool. That's the signature: app CPU low, database CPU low, and time
> spent waiting to check out a connection — nothing is busy and everything is slow. And the fix is
> usually not raising the pool, because Little's Law gives you a small number, not a large one. It's
> finding what's holding connections: a slow query, or a network call inside a transaction, which is
> the rule about never doing I/O inside a transaction paying off.

**Q: Describe a failure that only appears under load.**

> The readiness cascade. A dependency slows, the pool saturates, latency climbs, and the readiness
> probe times out — either because it queues behind real traffic or because it checks the database.
> The pod leaves the load balancer, its traffic is redistributed to pods already at the limit, they
> fail their probes too, and the whole fleet goes down one pod at a time while every pod is perfectly
> healthy. Client retries triple the offered load exactly when you can least afford it. The defences
> in order: timeouts on everything — the default in most HTTP clients is unbounded, which turns a slow
> dependency into your outage — retry budgets with jitter and never retrying at more than one layer, a
> circuit breaker, and load shedding, which is the only one that helps when the overload is real
> rather than a bug.

**Q: What do you autoscale on?**

> Not CPU for the API, because an I/O-bound service saturates its connection pool at around thirty
> percent CPU and never triggers. Concurrency, or requests per second per task, with the target derived
> from the knee I measured. Workers scale on oldest-message age rather than queue depth, since depth
> five thousand and draining is healthy while depth five and stuck is an outage. And there's a maximum
> derived from the database connection arithmetic — an autoscaler with no ceiling will scale until it
> exhausts `max_connections` and takes the database down, turning a traffic spike into an outage via
> the mechanism installed to prevent one.

## Today's build

1. ⭐⭐ Write your hypothesis: the saturation point and the first bottleneck. Seal it before running anything.
2. ⭐ Seed the environment to production shape with realistic tenant skew.
3. ⭐⭐ Run the same scenario closed-loop and open-loop. Put the two latency curves side by side.
4. ⭐ Take the read/write mix from your real endpoint distribution, not from a guess.
5. ⭐⭐ Run the ladder and build the rps/p50/p99/error table. Identify the knee.
6. ⭐ Repeat with a cold cache and record that number separately as your true capacity.
7. ⭐⭐ Identify the first bottleneck by signal, not by guess. Write down which of the four it was and whether you predicted it.
8. ⭐ Fix exactly one thing, re-run, and record the new knee.
9. ⭐⭐ Instrument connection-checkout wait time. Confirm you can see pool saturation directly.
10. ⭐⭐ Reproduce the cascade: add provider latency under load and watch pods fail readiness in sequence.
11. ⭐⭐ Add timeouts everywhere. Find every HTTP client call with no timeout — there will be some.
12. ⭐ Add a circuit breaker on the provider and re-run the latency injection.
13. ⭐⭐ Implement load shedding with a concurrency limit returning 429, and show throughput holding as offered load rises.
14. ⭐ Run all five chaos experiments during a load test, and record what actually happened versus what you expected.
15. ⭐⭐ Set autoscaling on concurrency for the API and oldest-message age for workers, with maximums from your connection arithmetic.
16. ⭐ Write the capacity paragraph into the README, in the honest form from Part 4.

## 🎙️ Articulation drill

**Three minutes: "Tell me about load testing your service."**

Start by rejecting the usual output: **a load test without a hypothesis is a benchmark, and I don't
want a big number — I want the identity of the first thing that breaks and the throughput at which it
breaks.** Then the methodological point that invalidates most published numbers, because it shows you
have actually thought about measurement: **a closed-loop tool backs off in exact proportion to your
degradation**, so the queue never grows, latency looks flat, and the collapse arrives with no warning
on the graph — that's coordinated omission, and it excludes precisely the slow requests, so p99 can be
wrong by an order of magnitude. Say what you fix: open-loop arrival rate, production-shaped data with
realistic tenant skew, a real mix, and both warm and cold cache — **the cold number is your capacity
during an incident.** Then report it in the honest form: **140 rps at p99 under 400 ms with no errors,
degrading at 180 because the pool saturates** — capacity, SLO, failure point and mechanism in one
sentence. Give the four bottlenecks in order and the signature of the most common: **everything slow
and nothing busy is the connection pool**, and the fix is finding what holds connections, not raising
the number. Then the cascade, because it's the failure that only exists under load: **a readiness probe
times out, the pod leaves the load balancer, its traffic lands on pods already at the limit, and the
whole fleet dies one pod at a time while every pod is healthy.** Defences: timeouts everywhere — the
default is unbounded — retry budgets at one layer only, a circuit breaker, and load shedding, which is
the only one that helps when the overload is genuine. Close on autoscaling derived from your own
numbers: **not CPU, because an I/O-bound service saturates its pool at thirty percent CPU**, workers on
message age, and a ceiling — or the autoscaler exhausts `max_connections` and takes the database down.
