# Part 1 — ⭐ Four patterns, and why you will use one of them

```
⭐⭐ ① CACHE-ASIDE (LAZY LOADING) — ⭐⭐ THE ONE YOU WILL USE.
⭐    read:  cache.get → hit? return : (db.read → cache.set → return)
⭐    write: db.write → ⭐⭐ cache.DELETE
⭐    ✅ ⭐ The cache never needs to know how to load anything. ⭐ Only
⭐       requested data is cached. ⭐ A cache outage degrades to slow,
⭐       not broken.
⭐    ❌ ⭐ Every first read is a miss. ⭐ The load logic is duplicated
⭐       wherever you cache, which is why you wrap it (Part 6).

⭐ ② READ-THROUGH — the cache library owns the loader.
⭐    ⭐ Same behaviour, better encapsulation. ⭐⭐ In Python this is
⭐      just cache-aside inside a decorator; there is no distinct
⭐      product to buy.

⭐ ③ WRITE-THROUGH — write to cache AND db, synchronously.
⭐    ✅ ⭐ The cache is never stale. ❌ ⭐⭐ EVERY WRITE IS SLOWER, AND
⭐      YOU HAVE JUST CREATED DAY 142'S DUAL-WRITE PROBLEM: two systems,
⭐      one operation, no atomicity. ⭐ Rarely worth it.

⭐ ④ WRITE-BEHIND (WRITE-BACK) — write to cache, flush to db later.
⭐    ✅ ⭐ Very fast writes, absorbs bursts.
⭐    ❌ ⭐⭐ THE CACHE IS NOW YOUR SYSTEM OF RECORD FOR A WINDOW, WITH
⭐      DAY 205'S DURABILITY CEILING. ⭐ Legitimate for metrics and
⭐      view counters. ⭐⭐ Never for anything you would be asked about
⭐      in a support ticket.

⭐ ⑤ REFRESH-AHEAD — proactively refresh before expiry.
⭐    ⭐ Only pays for a small, known-hot key set. ⭐⭐ Part 4's
⭐      probabilistic version is the same idea, done adaptively.
```

# Part 2 — ⭐⭐ Invalidation: delete, don't update — with the proof

```
⭐⭐ WHY "UPDATE THE CACHE" IS WRONG. Two writers, one key:

⭐   T1: db.write(A)                    ⭐ A is committed
⭐   T2: db.write(B)                    ⭐ B is committed — B is TRUTH
⭐   T2: cache.set(B)                   ⭐ cache = B ✅
⭐   T1: cache.set(A)                   ⭐⭐ cache = A ❌ FOREVER WRONG
⭐   ⇒ ⭐⭐ A THREAD SCHEDULING ACCIDENT LEFT THE CACHE PERMANENTLY
⭐     DISAGREEING WITH THE DATABASE. No error. No TTL will help if the
⭐     TTL is long.

⭐   ⭐⭐ WITH `DELETE`, THE SAME INTERLEAVING IS HARMLESS: both delete,
⭐     the next read repopulates from the database, and the database
⭐     already has the correct value. ⭐⭐ DELETE IS IDEMPOTENT AND
⭐     ORDER-INDEPENDENT. THAT IS THE ENTIRE ARGUMENT.
```

```
⭐⭐ AND THE ORDER: ***WRITE THE DATABASE, THEN DELETE THE CACHE.***
⭐   ⭐ Delete-then-write leaves a window where a concurrent reader
⭐     repopulates the cache with the OLD value and it sticks.
⭐   ⭐⭐ THE RACE YOU CANNOT FULLY REMOVE, STATED HONESTLY:
⭐        reader: cache miss, db.read → old value  ⭐ (slow reader)
⭐        writer: db.write(new); cache.delete()
⭐        reader: cache.set(old)                   ⭐⭐ STALE, PERSISTED
⭐   ⇒ ⭐ It requires a reader to be descheduled across a whole write.
⭐     Rare — ⭐⭐ AND THIS IS EXACTLY WHY EVERY ENTRY HAS A TTL.
⭐   ⇒ ⭐⭐ THE TTL IS NOT MEMORY MANAGEMENT. IT IS THE UPPER BOUND ON
⭐     HOW LONG A BUG IN YOUR INVALIDATION CAN LIE TO A USER.
⭐   ⭐ If you truly cannot tolerate it: delete after commit AND again
⭐     after a short delay ("delayed double delete"), or use versioned
⭐     keys — ⭐ `user:42:v{updated_at_epoch}` — where a write makes the
⭐     old key unreachable rather than wrong.
```

```
⭐⭐ TTL DESIGN — three rules:
⭐   ⭐ CHOOSE IT FROM THE BUSINESS: "how stale may this be?" is a
⭐     product question with an actual answer. ⭐⭐ 300 seconds because
⭐     someone typed it is not a decision.
⭐   ⭐⭐ ALWAYS ADD JITTER. 10,000 keys written during a deploy with a
⭐     600 s TTL all expire in the same second ⇒ ⭐⭐ A SYNCHRONISED
⭐     STAMPEDE YOU BUILT YOURSELF. `ttl = base + random(0, base*0.1)`.
⭐   ⭐ SLIDING TTL (refresh on read) suits sessions; ⭐⭐ it is wrong
⭐     for data that must eventually reflect reality, because a popular
⭐     key never expires and therefore never self-heals.
```

# Part 3 — ⭐⭐ The stampede, and three real defences

```
⭐⭐ ONE HOT KEY EXPIRES. 500 CONCURRENT REQUESTS MISS. 500 IDENTICAL
⭐   EXPENSIVE QUERIES HIT THE DATABASE AT ONCE. ⭐ The database slows,
⭐   requests queue, timeouts fire, retries double the load (Day 152).
⭐   ⭐⭐ THE CACHE CAUSED THE OUTAGE.
```

```python
# ⭐ ① SINGLE-FLIGHT — only one caller recomputes; the rest wait.
def get_or_compute(key, ttl, compute):
    v = r.get(key)
    if v is not None:
        return deserialize(v)
    lock = f"lock:{key}"
    if r.set(lock, TOKEN, nx=True, ex=10):        # ⭐⭐ I am the one
        try:
            v = compute()
            r.set(key, serialize(v), ex=jitter(ttl))
            return v
        finally:
            release_lock(lock, TOKEN)             # ⭐ Day 207, properly
    # ⭐ someone else is computing
    for _ in range(50):
        time.sleep(0.02)
        v = r.get(key)
        if v is not None:
            return deserialize(v)
    return compute()   # ⭐⭐ FALL BACK. NEVER WAIT FOREVER for a lock
                       #    holder that may have died.
```

```python
# ⭐⭐ ② PROBABILISTIC EARLY EXPIRY (XFetch) — no lock, no waiting.
#    Each reader independently decides to refresh EARLY, with a
#    probability that rises as expiry approaches.
#    ⭐⭐ ⇒ ONE UNLUCKY READER REFRESHES WHILE THE KEY IS STILL VALID,
#      SO NOBODY EVER EXPERIENCES A MISS.
def get_xfetch(key, ttl, compute, beta=1.0):
    v, delta, expiry = read_with_meta(key)        # ⭐ store compute cost
    if v is None or time.time() - delta*beta*math.log(random.random()) >= expiry:
        start = time.time()
        v = compute()
        delta = time.time() - start               # ⭐⭐ expensive keys
        write_with_meta(key, v, delta, ttl)       #    refresh earlier
    return v
# ⭐ Elegant, lock-free, and it self-tunes: the more expensive the
#   recompute, the earlier it starts. ⭐⭐ The paper is "Optimal
#   Probabilistic Cache Stampede Prevention" — worth naming.
```

```
⭐⭐ ③ STALE-WHILE-REVALIDATE — serve the old value, refresh in the
⭐   background. ⭐ Store `{value, hard_expiry}` with a LONGER Redis TTL
⭐   than your logical one:
⭐     logical expiry passed but hard TTL alive ⇒ ⭐⭐ RETURN THE STALE
⭐     VALUE IMMEDIATELY and enqueue a refresh.
⭐   ⇒ ⭐⭐ NO USER EVER WAITS FOR A RECOMPUTE. The cost is that
⭐     everyone may see data one refresh-cycle old.
⭐   ⭐ This is the same idea as the HTTP header (Day 010) — and it is
⭐     the right default for dashboards, feeds and anything read far
⭐     more than it changes.
```

# Part 4 — ⭐⭐ Eviction: eight policies, and the one that isn't

```
⭐   maxmemory 4gb
⭐   maxmemory-policy allkeys-lru
⭐   maxmemory-samples 5

⭐⭐ THE EIGHT:
⭐   ⭐⭐ noeviction     — ⭐⭐ THE DEFAULT. Writes FAIL with OOM when
⭐        full. ⭐ Correct for a queue or a lock store. ⭐⭐ CATASTROPHIC
⭐        FOR A CACHE, and it is what you get if you never set this.
⭐   ⭐ allkeys-lru      — evict least-recently-used, from ALL keys.
⭐        ⭐⭐ THE RIGHT DEFAULT FOR A CACHE.
⭐   ⭐ allkeys-lfu      — least-FREQUENTLY-used (4.0+).
⭐        ⭐⭐ BETTER WHEN A SCAN OR A BOT SWEEPS THROUGH COLD KEYS: LRU
⭐        would evict your genuinely hot keys in favour of things touched
⭐        once. ⭐ LFU counters DECAY (`lfu-decay-time`), so yesterday's
⭐        hot key does not stay resident forever.
⭐   ⭐ allkeys-random   — surprisingly not-terrible, and cheap.
⭐   ⭐⭐ volatile-lru / -lfu / -random / -ttl — ⭐⭐ ONLY CONSIDER KEYS
⭐        THAT HAVE A TTL.
⭐        ⇒ ⭐⭐ ***IF NO KEY HAS A TTL, `volatile-*` BEHAVES EXACTLY
⭐          LIKE `noeviction` AND YOUR WRITES START FAILING.*** ⭐ This
⭐          is the single most common Redis misconfiguration: people
⭐          pick `volatile-lru` because it sounds safer, then cache
⭐          something without a TTL, and are baffled by OOM errors on a
⭐          half-empty instance.
⭐   ⇒ ⭐ `volatile-*` is right ONLY when one instance mixes cache
⭐     (with TTLs) and persistent data (without) — ⭐⭐ AND MIXING THEM
⭐     IS ITSELF THE MISTAKE (Day 181). Separate instances.
```

```
⭐⭐ LRU IS APPROXIMATE, AND THAT IS DELIBERATE:
⭐   ⭐ True LRU needs a linked list of every key — memory and pointer
⭐     chasing. ⭐ Redis instead SAMPLES `maxmemory-samples` keys and
⭐     evicts the oldest of those.
⭐   ⭐ 5 (default) is ~good; 10 is very close to true LRU at slightly
⭐     more CPU. ⭐⭐ This is a fine trade and worth being able to
⭐     explain: an approximation that costs nothing beats an exact
⭐     answer that costs a pointer per key.
⭐   ⭐⭐ AND EVICTION HAPPENS ON THE COMMAND PATH — a write that
⭐     triggers eviction pays for it. ⭐ Sudden `evicted_keys` growth
⭐     shows up as a latency change, not as an error.
```

# Part 5 — ⭐⭐ Measuring: the metric that matters and the one that lies

```sql
redis> INFO stats
--  keyspace_hits:  9,412,003
--  keyspace_misses:  187,441       ⭐ hit ratio = 98.0%
--  evicted_keys: 1,204,882         ⭐⭐ ← LOOK HERE
--  expired_keys: 8,120,441
```

```
⭐⭐ THE HIT RATIO IS NOT THE POINT.
⭐   ⭐ TIME SAVED = hits × (cost_of_miss − cost_of_hit)
⭐   ⭐ 99% hits × 2 ms saved  = ⭐ a rounding error
⭐   ⭐ 60% hits × 900 ms saved = ⭐⭐ THE REASON THE SERVICE IS UP
⭐   ⇒ ⭐⭐ INSTRUMENT ***BOTH PATHS*** (Day 147): a counter labelled
⭐     hit/miss, and a histogram of the MISS path's cost. ⭐ Then you
⭐     can state the cache's value in seconds per minute, which is a
⭐     number a manager can act on.

⭐⭐ AND THE TWO NUMBERS THAT DIAGNOSE A SICK CACHE:
⭐   ⭐⭐ `evicted_keys` RISING ⇒ THE WORKING SET NO LONGER FITS. Your
⭐     hit ratio will fall gradually and nothing will look broken.
⭐     ⇒ ⭐ more memory, shorter TTLs, smaller values, or accept it.
⭐   ⭐ `expired_keys ≫ evicted_keys` ⇒ healthy: entries are aging out
⭐     rather than being forced out.
⭐   ⭐⭐ A HIT RATIO THAT IS TOO ***HIGH*** (99.9%) ON A LARGE CACHE IS
⭐     ALSO A SIGNAL — ⭐ you may be caching things nobody re-reads, or
⭐     your TTLs are so long you are serving stale data.
```

```
⭐⭐ THE FIVE ANTI-PATTERNS, EACH WITH THE DAY THAT NAMED IT:
⭐   ① ⭐⭐ CACHING PER-USER DATA UNDER A SHARED KEY — Bob gets Alice's
⭐      dashboard. ⭐ Day 181. The identity must be IN the key.
⭐   ② ⭐ CACHING TO AVOID FIXING A QUERY — Day 181's step 6: now you
⭐      have a slow query AND a staleness bug.
⭐   ③ ⭐ NO TTL AND NO BOUND — Day 204: the cache becomes a memory
⭐      exhaustion incident.
⭐   ④ ⭐⭐ NOT CACHING MISSES ("negative caching"). If `GET /user/999999`
⭐      is a miss, every one of a million bogus requests reaches your
⭐      database. ⭐⭐ CACHE THE ABSENCE, with a SHORT TTL — it is a
⭐      real DoS vector and a two-line fix. ⭐ (A Bloom filter is the
⭐      scaled-up version.)
⭐   ⑤ ⭐ CACHING ERRORS. A 500 cached for 5 minutes turns a blip into
⭐      an outage. ⭐⭐ Cache successes and deliberate absences; never
⭐      cache a failure.
```

# Part 6 — ⭐ In Python, and the multi-level question

```python
# ⭐ Cache-aside as a decorator, with everything above applied:
def cached(key_fn, ttl=300, negative_ttl=30):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            key = key_fn(*a, **kw)                 # ⭐ versioned, tenant
            raw = r.get(key)                       #   scoped (Day 204)
            if raw is not None:
                obj = json.loads(raw)
                return None if obj is SENTINEL_MISS else obj
            val = fn(*a, **kw)
            r.set(key,
                  json.dumps(SENTINEL_MISS if val is None else val),
                  ex=jitter(negative_ttl if val is None else ttl))
            return val                             # ⭐⭐ ④ negative
        return wrapper                             #    caching, built in
    return deco
```

```
⭐⭐ SERIALISATION — one decision, three consequences:
⭐   ⭐ `json`   — portable, debuggable in `redis-cli`, slowest. ⭐⭐ THE
⭐        DEFAULT, and the right one until measured otherwise.
⭐   ⭐ `msgpack`/`orjson` — 2–5× faster and smaller. ⭐ Worth it on a
⭐        hot path.
⭐   ⭐⭐ `pickle` — ⭐⭐ ***NEVER.*** `pickle.loads` on data from Redis
⭐        is REMOTE CODE EXECUTION if anything can write to Redis — a
⭐        compromised service, an exposed port, a shared instance, a
⭐        key-collision from another team. ⭐⭐ "It is internal" is not
⭐        a security boundary. This is a genuine, exploited CVE class.
```

```
⭐⭐ TWO-LEVEL CACHING (in-process L1 + Redis L2):
⭐   ⭐ L1 removes the 0.2 ms round trip and is worth it for tiny,
⭐     extremely hot values — feature flags, config, tenant settings.
⭐   ⭐⭐ THE PROBLEM IS INVALIDATION: you cannot delete a key inside 30
⭐     other processes. ⭐ THREE ANSWERS:
⭐       ⭐ a very short L1 TTL (5–30 s) — ⭐⭐ crude, sufficient, and
⭐         what most teams should do;
⭐       ⭐ Redis PUB/SUB invalidation broadcast (Day 209) — ⭐ note it
⭐         is fire-and-forget, so a disconnected process misses it;
⭐       ⭐⭐ RESP3 CLIENT-SIDE CACHING (`CLIENT TRACKING`) — Redis
⭐         itself tells your client when a key it cached changed. ⭐ The
⭐         correct mechanism, and still under-adopted.
⭐   ⇒ ⭐⭐ DO NOT ADD L1 UNTIL YOU HAVE MEASURED THAT THE ROUND TRIP IS
⭐     THE PROBLEM. You are trading a correctness guarantee for 0.2 ms.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Updating the cache on write | Two writers can interleave and leave it permanently wrong. Delete. |
| Deleting before writing the database | A concurrent reader repopulates the old value and it sticks. |
| Treating TTL as memory management | It's the upper bound on how long an invalidation bug can lie. |
| Uniform TTLs | Everything written during a deploy expires in the same second. Jitter. |
| Sliding TTL on data that must reflect reality | A popular key never expires and never self-heals. |
| No stampede protection on an expensive key | 500 concurrent misses become 500 identical queries. |
| Waiting forever for the single-flight lock holder | It may have died. Bound the wait and fall back. |
| Leaving `maxmemory-policy` at the default | `noeviction` means a full cache returns write errors. |
| Choosing `volatile-lru` because it sounds safer | With no TTLs it behaves exactly like `noeviction`. |
| Mixing cache and persistent data in one instance | That's what forces the `volatile-*` mistake. Separate instances. |
| Reporting hit ratio as the cache's value | Value is hits × time saved. 99% on a 2 ms query is nothing. |
| Ignoring `evicted_keys` | Rising evictions mean the working set no longer fits; the decay is silent. |
| Not caching misses | A million lookups of a non-existent id all reach the database. |
| Caching errors | A cached 500 turns a blip into an outage. |
| `pickle` as the cache serialiser | Deserialising attacker-controlled data is remote code execution. |
| Adding an in-process L1 before measuring | You traded a correctness guarantee for 0.2 ms. |

## Interview questions

**Q: How do you invalidate a cache?**

> By deleting, never updating, and after the database write rather than before. The reason to delete is
> a concurrency proof rather than a preference: if two writers both update the cache, they can commit
> in one order and write the cache in the other, leaving it permanently disagreeing with the database
> with no error anywhere. Delete is idempotent and order-independent, so the same interleaving is
> harmless — the next read repopulates from the source of truth. Doing it after the write matters
> because delete-then-write leaves a window where a reader repopulates the old value. There's still a
> residual race — a slow reader that read before the write can set a stale value after the delete —
> and rather than pretend it away, that's exactly why every entry gets a TTL: **the TTL is the upper
> bound on how long a bug in your invalidation can lie to a user.** If I genuinely can't tolerate even
> that, versioned keys make the old entry unreachable rather than wrong.

**Q: A cached key expires and your database falls over. What happened and how do you prevent it?**

> A cache stampede. One hot key expires, hundreds of concurrent requests all miss, and they all issue
> the same expensive query simultaneously — the database slows, requests queue, timeouts fire, and
> retries double the load. The cache caused the outage. Three defences. Single-flight: the first caller
> takes a short lock and recomputes while the others poll briefly — with the important detail that the
> waiters bound their wait and fall back to computing, because the lock holder may have died.
> Probabilistic early expiry, where each reader independently decides to refresh early with a
> probability that rises as expiry approaches and scales with how expensive the recompute was, so one
> unlucky reader refreshes while the value is still valid and nobody ever experiences a miss — that's
> lock-free and self-tuning. And stale-while-revalidate: keep a longer Redis TTL than your logical one
> and serve the stale value immediately while refreshing in the background, so no user ever waits.
> Underneath all three, jittered TTLs, because uniform TTLs create synchronised expiry that you built
> yourself during a deploy.

**Q: Which eviction policy would you choose?**

> `allkeys-lru` for a general cache, or `allkeys-lfu` if the access pattern includes scans or crawlers
> that sweep through cold keys — LRU would evict genuinely hot data in favour of things touched once,
> and LFU's decaying counters handle that while still letting yesterday's hot key age out. The critical
> thing is not to leave the default, because `noeviction` means a full instance starts returning write
> errors instead of making room, which is right for a queue or a lock store and catastrophic for a
> cache. And the trap I'd flag is `volatile-lru`: people pick it because it sounds safer, but it only
> considers keys that have a TTL, so if anything is cached without one — and eventually something will
> be — it degrades to `noeviction` and you get OOM errors on a half-empty instance. It's only right
> when one instance deliberately mixes cache and persistent data, and mixing them is itself the mistake.
> I'd also mention that Redis's LRU is approximate by design, sampling a handful of keys rather than
> maintaining a full list, which is a good trade to be able to explain.

**Q: How do you know whether your cache is worth having?**

> Not from the hit ratio, which is a vanity metric — ninety-nine percent hits on a two-millisecond
> query saves nothing, while sixty percent on a two-second query is the reason the service is up. So I
> instrument both paths: a counter labelled hit or miss, and a histogram of the miss path's cost. Then
> the cache's value is hits times time saved, which I can state in seconds of database time removed per
> minute — a number someone can act on. Alongside that, two health signals. Rising `evicted_keys` means
> the working set no longer fits, and the consequence is a hit ratio that decays gradually with nothing
> looking broken. And a suspiciously high ratio on a large cache is also worth investigating: either
> you're caching things nobody re-reads, or the TTLs are long enough that you're mostly serving stale
> data.

**Q: Would you add an in-process cache in front of Redis?**

> Only after measuring that the round trip is genuinely the problem, and only for small, extremely hot,
> slow-changing values — feature flags, tenant config, that class of thing. The reason for the caution
> is that you're trading a correctness guarantee for about two tenths of a millisecond: you can delete
> a key in Redis, but you can't delete it inside thirty other processes. There are three ways to handle
> that. A very short L1 TTL of five to thirty seconds, which is crude, sufficient, and what most teams
> should do. A pub/sub invalidation broadcast, which is fire-and-forget so a briefly disconnected
> process silently misses it. Or RESP3 client-side caching with `CLIENT TRACKING`, where Redis itself
> tells your client when a key it has cached has changed — that's the correct mechanism and it's still
> under-adopted. I'd also refuse `pickle` as the serialiser at any level, because deserialising data
> from a shared store is remote code execution if anything can write to it, and "it's internal" isn't a
> security boundary.

## 🎙️ Articulation drill

**Two minutes: "How do you cache correctly?"**

Lead with cache-aside and why the alternatives mostly aren't worth it — write-through recreates the
dual-write problem, write-behind makes the cache your system of record with a one-second durability
ceiling. Then the invalidation rule *with its proof*, because that's what separates a rule from
understanding: **delete rather than update, because two writers can commit in one order and write the
cache in the other, and delete is idempotent and order-independent.** Then the honest residual race,
and land the reframe: **the TTL isn't memory management, it's the upper bound on how long an
invalidation bug can lie to a user.** Then the stampede in one sentence with your preferred defence.
