# Day 389 ⚖️

**P-389** · ⚖️ **ELB and Auto Scaling** — health checks, draining, ⭐⭐ and the 502 nobody can reproduce

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the load balancer's health check is the only opinion that matters about
> whether your service is alive, and the intermittent 502 nobody can reproduce is almost always two
> timeouts disagreeing — the balancer thinks a connection is good for sixty seconds and gunicorn
> closes it after two.**

---

# Part 1 — Which balancer, and why

```
⭐ ALB (LAYER 7) — ⭐ speaks HTTP. ⭐ The default.
⭐   ⭐ Routes on host, path, header, method, query.
⭐   ⭐ Terminates TLS. ⭐ Integrates WAF and Cognito/OIDC auth.
⭐   ⭐ Emits per-request access logs and target response times.
⭐   ⭐⭐ AND IT LOAD-BALANCES ***PER REQUEST***, WHICH IS THE
⭐     REASON YOU WANT IT: ⭐ a keep-alive connection's requests
⭐     still spread across targets.

⭐ NLB (LAYER 4) — ⭐ TCP/UDP/TLS. ⭐ Microsecond latency,
⭐   ⭐ static IPs, ⭐ preserves the source IP natively, ⭐ handles
⭐   millions of connections.
⭐   ⭐⭐ AND THE REASON THAT MATTERS TO YOU: ***IT BALANCES
⭐     CONNECTIONS, NOT REQUESTS*** — ⭐ which is Day 324's
⭐     connection-pinning problem. ⭐⭐ A gRPC OR WEBSOCKET CLIENT
⭐     THAT OPENS ONE LONG-LIVED CONNECTION STAYS ON ONE TARGET
⭐     FOREVER, ⭐ so a new target gets no traffic. ⭐⭐ FOR gRPC,
⭐     USE THE ALB (IT SPEAKS HTTP/2 AND BALANCES STREAMS) OR
⭐     BALANCE CLIENT-SIDE.

⭐ ⭐ GWLB — for inline security appliances. ⭐ You will not need
⭐   it.
⭐ ⭐⭐ CLASSIC ELB — LEGACY. IF YOU HAVE ONE, MIGRATING IS A
⭐   GOOD AFTERNOON.
```

# Part 2 — Health checks are a decision, not a default

```
⭐ THE FIVE PARAMETERS, AND WHAT EACH ONE BUYS:
⭐   ⭐ `interval` (default 30 s)
⭐   ⭐ `timeout` (5 s) — ⭐⭐ MUST BE < INTERVAL
⭐   ⭐ `unhealthy_threshold` (2)
⭐   ⭐ `healthy_threshold` (5 for ALB)
⭐   ⭐ `matcher` (200)

⭐⭐ THE TWO NUMBERS THAT ACTUALLY MATTER, AND NOBODY COMPUTES
⭐   THEM:
⭐   ⭐⭐ ***TIME TO EJECT A DEAD TARGET = interval ×
⭐     unhealthy_threshold*** = 30 × 2 = ***60 SECONDS.***
⭐     ⭐ For a whole minute, a fraction of your traffic goes to a
⭐     dead process. ⭐⭐ SET 10 s × 2 = 20 s AND THE OUTAGE IS
⭐     A THIRD AS LONG, FOR THE PRICE OF THREE TIMES THE HEALTH-
⭐     CHECK TRAFFIC — ⭐ which is nothing.
⭐   ⭐⭐ ***TIME TO RETURN = interval × healthy_threshold***
⭐     = 30 × 5 = ***150 SECONDS.*** ⭐ This is why a new task
⭐     seems to take forever to receive traffic, ⭐⭐ AND WHY YOUR
⭐     DEPLOY IS SLOWER THAN YOU EXPECT.

⭐⭐ AND THE RULE FROM DAY 377, RESTATED BECAUSE IT IS THE ONE
⭐   PEOPLE VIOLATE: ***THE HEALTH-CHECK ENDPOINT MUST NOT TOUCH
⭐   ANY DEPENDENCY.***
⭐   ⭐ `/healthz` returns 200 if the process can serve. ⭐ Full
⭐     stop. ⭐ No database, no Redis, no downstream call.
⭐   ⭐⭐ IF `/healthz` CHECKS POSTGRES, A DATABASE BLIP MARKS
⭐     ***EVERY*** TARGET UNHEALTHY SIMULTANEOUSLY, THE ALB
⭐     REMOVES ALL OF THEM, ⭐ AND A RECOVERABLE 20-SECOND
⭐     DATABASE EVENT BECOMES A TOTAL OUTAGE THAT OUTLIVES IT.
⭐   ⭐ (Panic mode — ⭐⭐ WHEN ALL TARGETS ARE UNHEALTHY THE ALB
⭐     SENDS TO ALL OF THEM ANYWAY — ⭐ mitigates this, and you
⭐     should not rely on being saved by it. ⭐ Day 325.)
⭐   ⭐ Keep a ***separate*** `/readyz` that does check
⭐     dependencies, ⭐⭐ AND POINT MONITORING AT IT RATHER THAN
⭐     THE LOAD BALANCER.
```

# Part 3 — ⭐⭐ The 502 nobody can reproduce

> The best single fact in this day. It explains a class of bug that teams live with for months.

```
⭐ THE SETUP, AND EVERY PART OF IT IS A DEFAULT:
⭐   ⭐ ALB `idle_timeout` = ***60 seconds***
⭐   ⭐⭐ gunicorn `--keep-alive` = ***2 SECONDS***

⭐ THE RACE, STEP BY STEP:
⭐ ① ⭐ ALB opens a keep-alive connection to your target and
⭐    proxies a request.
⭐ ② ⭐ Response sent. ⭐ ALB keeps the connection, believing it
⭐    is good for 60 s.
⭐ ③ ⭐⭐ TWO SECONDS LATER, GUNICORN CLOSES IT.
⭐ ④ ⭐⭐ AT THAT EXACT MOMENT THE ALB SENDS THE NEXT REQUEST ONTO
⭐    THE CLOSING SOCKET.
⭐ ⑤ ⭐ It receives a FIN instead of a response.
⭐ ⑥ ⭐⭐ THE CLIENT GETS `502 Bad Gateway`.

⭐⭐ WHY IT IS UNREPRODUCIBLE: ⭐ it needs the request to arrive
⭐   inside the microseconds-wide window between the backend
⭐   deciding to close and the ALB learning about it. ⭐⭐ SO IT IS
⭐   A TINY, RANDOM PERCENTAGE — 0.01% — ⭐ it rises with traffic,
⭐   ⭐ it never happens in staging, ⭐⭐ AND YOUR APPLICATION LOGS
⭐   SHOW ***NOTHING AT ALL***, BECAUSE THE REQUEST NEVER REACHED
⭐   YOUR CODE.

⭐⭐ ⇒ THE RULE: ***THE BACKEND'S KEEP-ALIVE TIMEOUT MUST BE
⭐   STRICTLY GREATER THAN THE LOAD BALANCER'S IDLE TIMEOUT.***
⭐   ⭐⭐ THE BALANCER MUST ALWAYS BE THE ONE THAT CLOSES, BECAUSE
⭐   ONLY THE BALANCER KNOWS WHETHER A REQUEST IS IN FLIGHT.
⭐   ⭐ ALB idle 60 → ⭐⭐ `gunicorn --keep-alive 75`
⭐   ⭐ Nginx in front → `keepalive_timeout 75s;`
⭐   ⭐ Uvicorn → `--timeout-keep-alive 75`

⭐⭐ AND THE REST OF THE STATUS-CODE VOCABULARY, WHICH TELLS YOU
⭐   WHERE TO LOOK BEFORE YOU LOOK:
⭐   ⭐ ***502*** — ⭐⭐ TARGET CLOSED THE CONNECTION OR SENT
⭐     SOMETHING MALFORMED. ⭐ Keep-alive race, ⭐ or a worker that
⭐     died mid-response (an OOM kill — Day 361).
⭐   ⭐ ***504*** — ⭐⭐ TARGET DID NOT RESPOND WITHIN THE IDLE
⭐     TIMEOUT. ⭐ Your code is slow. ⭐ A real application problem.
⭐   ⭐ ***503*** — ⭐⭐ NO HEALTHY TARGETS. ⭐ Look at the health
⭐     check, not the app.
⭐   ⭐ ***460*** — ⭐ the ***client*** disconnected before you
⭐     answered (Day 367's 499, in ALB dialect).
⭐   ⭐ ***`TargetConnectionErrorCount`*** — ⭐⭐ THE METRIC THAT
⭐     PROVES THE KEEP-ALIVE RACE. ⭐ Alarm on it.
```

# Part 4 — Draining, and the three timeouts that must be ordered

```
⭐ DEREGISTRATION DELAY (default ***300 s***) is the window in
⭐   which the ALB stops sending ***new*** requests but lets
⭐   in-flight ones finish.

⭐⭐ AND HERE IS THE SYNTHESIS — ***THREE SYSTEMS, ONE ORDERING,
⭐   AND VIOLATING IT DROPS REQUESTS***:

⭐   ⭐⭐ ***p99 REQUEST DURATION < DEREGISTRATION DELAY <
⭐     CONTAINER STOP TIMEOUT***

⭐   ⭐ If deregistration delay < request duration → ⭐⭐ THE ALB
⭐     GIVES UP AND THE CONNECTION IS CUT MID-RESPONSE.
⭐   ⭐ If stop timeout < deregistration delay → ⭐⭐ ECS SIGKILLS
⭐     THE TASK WHILE IT IS STILL DRAINING, ⭐ which is the same
⭐     dropped request arriving from the other direction.
⭐   ⭐⭐ AND ON FARGATE `stopTimeout` IS CAPPED AT 120 SECONDS
⭐     (DAY 390) — ⭐ so that cap is also a ceiling on your
⭐     longest request, ⭐⭐ WHICH IS A DESIGN CONSTRAINT PEOPLE
⭐     MEET BY ACCIDENT.

⭐ ⭐ Sensible set for a web API: ⭐ p99 = 2 s, ⭐ deregistration
⭐   delay = 30 s, ⭐ stopTimeout = 60 s, ⭐⭐ AND gunicorn's
⭐   `--graceful-timeout 30`.
⭐ ⭐ 300 s of deregistration delay is not "safe" — ⭐⭐ IT MAKES
⭐   EVERY DEPLOY FIVE MINUTES LONGER PER BATCH AND HIDES THE
⭐   FACT THAT YOUR APP IGNORES SIGTERM (DAY 378).
```

# Part 5 — Auto Scaling, and the four minutes you do not have

```
⭐ THE POLICIES:
⭐   ⭐⭐ ***TARGET TRACKING*** — "keep metric X at Y". ⭐ The
⭐     default choice. ⭐ It creates and manages the alarms.
⭐   ⭐ ***STEP SCALING*** — explicit thresholds. ⭐ For when you
⭐     need asymmetric behaviour (out fast, in slow).
⭐   ⭐⭐ ***SCHEDULED*** — ⭐⭐ THE MOST UNDER-USED AND OFTEN THE
⭐     BEST. ⭐ If your traffic has a shape you can predict, ⭐⭐ SCALE
⭐     ***BEFORE*** THE SPIKE INSTEAD OF REACTING TO IT — ⭐ which
⭐     is static stability (Day 380) applied to capacity.

⭐⭐ AND THE METRIC: ***`ALBRequestCountPerTarget` IS USUALLY
⭐   RIGHT FOR A PYTHON WEB TIER, AND CPU IS USUALLY WRONG***
⭐   (Day 378) — ⭐ because an I/O-bound service saturates its
⭐   worker pool at 30% CPU, ⭐⭐ SO CPU-BASED SCALING NEVER FIRES
⭐   WHILE EVERY REQUEST QUEUES.

⭐⭐ NOW THE ARITHMETIC NOBODY DOES — ***HOW LONG FROM SPIKE TO
⭐   CAPACITY?***
⭐   ⭐ metric published to CloudWatch ......... up to 60 s
⭐   ⭐ alarm evaluation period ................ 60 s
⭐   ⭐ instance launch / task placement ....... 30–180 s
⭐   ⭐ image pull + app boot + warm-up ........ 30–90 s
⭐   ⭐ health checks pass (Part 2!) ........... 30–150 s
⭐   ⭐⭐ ═══════════════════════════════════════════════════
⭐   ⭐⭐ TOTAL: ***THREE TO SEVEN MINUTES.***

⭐⭐ ⇒ ***YOU CANNOT AUTOSCALE OUT OF A THIRTY-SECOND SPIKE.***
⭐   ⭐ There are exactly three real options, and autoscaling is
⭐   not one of them:
⭐   ⭐ ① ⭐⭐ BE PRE-PROVISIONED (headroom costs money — DAY 380)
⭐   ⭐ ② ⭐⭐ SHED LOAD GRACEFULLY (DAY 335)
⭐   ⭐ ③ ⭐ queue the work and answer asynchronously
⭐   ⭐⭐ AUTOSCALING HANDLES THE ***TREND***, NOT THE ***SPIKE***.
⭐   ⭐ Say that sentence in an interview.
```

# Part 6 — Two ASG traps

```
⭐ ① ⭐⭐ ***HEALTH CHECK TYPE DEFAULTS TO `EC2`, NOT `ELB`.***
⭐    ⭐ An EC2 health check only asks whether the ***instance***
⭐    is running. ⭐⭐ SO AN INSTANCE WHOSE PYTHON PROCESS IS DEAD,
⭐    WEDGED OR OOM-LOOPING PASSES FOREVER — ⭐ the ALB stops
⭐    sending it traffic, ⭐⭐ AND THE ASG NEVER REPLACES IT. ⭐ You
⭐    run permanently degraded and the ASG reports 100% healthy.
⭐    ⭐⭐ SET `health_check_type = "ELB"`. ⭐ One line.
⭐ ② ⭐ ***COOLDOWN AND WARM-UP.*** ⭐ Without an instance warm-up
⭐    period, ⭐⭐ THE ASG COUNTS A BOOTING INSTANCE'S 0%
⭐    UTILISATION IN THE AVERAGE, CONCLUDES IT NEEDS MORE, AND
⭐    LAUNCHES AGAIN — ⭐ overshooting to double what you needed,
⭐    ⭐ then scaling in hard, ⭐⭐ THEN OSCILLATING. ⭐ Set the
⭐    warm-up to your real boot time, ⭐ which you measured on
⭐    Day 366.

⭐ ⭐⭐ AND ONE LOAD-BALANCER DEFAULT WORTH KNOWING: ⭐ cross-zone
⭐   balancing is ***on*** for ALB and ***off*** for NLB.
⭐   ⭐⭐ WITH IT OFF AND UNEVEN TARGET COUNTS PER AZ, A ZONE WITH
⭐   ONE TARGET RECEIVES THE SAME SHARE AS A ZONE WITH FIVE —
⭐   ⭐ so that one target gets five times the load and looks like
⭐   "a slow instance". ⭐ (On NLB, enabling it also adds
⭐   cross-AZ data charges. ⭐⭐ THE TRADE IS REAL BUT THE
⭐   IMBALANCE IS USUALLY WORSE.)

⭐ ⭐ Sticky sessions: ⭐⭐ A SMELL, NOT A FEATURE (DAY 323). ⭐ It
⭐   means state lives in a process, so scale-in loses sessions
⭐   and load never balances evenly. ⭐ Fix the state.
```

# 💬 Interview

**1. ⭐⭐ "We get about 0.01% 502s. No pattern, can't reproduce, nothing in the app logs."**
> ⭐ That combination is the keep-alive race, and the absent logs are the clue: ⭐⭐ **the request never
> reached the application.** ⭐ The ALB's idle timeout defaults to 60 seconds and gunicorn's keep-alive
> defaults to 2, ⭐⭐ **so the balancer holds a connection it believes is good while the backend closes
> it, and occasionally a request goes onto the closing socket and gets a FIN instead of a response.**
> ⭐ It needs a microsecond-wide window, so it's a tiny random percentage that scales with traffic and
> never shows up in staging. ⭐⭐ **The rule is that the backend's keep-alive must be strictly greater
> than the balancer's idle timeout — the balancer has to be the one that closes, because only it knows
> whether a request is in flight.** ⭐ ALB 60, gunicorn `--keep-alive 75`. ⭐ And I'd alarm on
> `TargetConnectionErrorCount`, which is the metric that proves it.

**2. "What should a health check endpoint do?"**
> ⭐⭐ **Nothing that touches a dependency.** ⭐ It returns 200 if the process can serve requests.
> ⭐⭐ **If `/healthz` checks Postgres, a twenty-second database blip marks every target unhealthy at
> once, the balancer removes all of them, and a recoverable event becomes a total outage that outlives
> its cause.** ⭐ I keep a separate `/readyz` that does check dependencies and point monitoring at that
> instead. ⭐ And I'd tune the timing deliberately: ⭐⭐ **time to eject a dead target is interval times
> unhealthy threshold — 30 by 2 is a full minute of traffic going to a dead process — so I use 10 by 2
> and pay three times the health-check traffic, which is nothing.**

**3. ⭐⭐ "What's the ordering constraint when a task shuts down?"**
> ⭐ Three systems have to agree: ⭐⭐ **p99 request duration < deregistration delay < container stop
> timeout.** ⭐ If deregistration delay is shorter than a request, the balancer cuts connections
> mid-response; ⭐⭐ **if stop timeout is shorter than deregistration delay, the orchestrator SIGKILLs
> the task while it's still draining — same dropped request from the other direction.** ⭐ And on
> Fargate `stopTimeout` caps at 120 seconds, ⭐⭐ **so that cap is also a ceiling on your longest
> request** — a design constraint people meet by accident. ⭐ I'd also say the default 300-second
> deregistration delay isn't "safe": it makes every deploy batch five minutes longer and hides the
> fact that the app ignores SIGTERM.

**4. ⭐⭐ "Can autoscaling handle a traffic spike?"**
> ⭐ No, and the arithmetic is the answer. ⭐⭐ **Metric publication up to 60 seconds, alarm evaluation
> 60, launch or placement 30 to 180, image pull and boot 30 to 90, health checks 30 to 150 — three to
> seven minutes from spike to serving capacity.** ⭐ So a thirty-second spike is over before the first
> new task is healthy. ⭐⭐ **Autoscaling handles the trend, not the spike.** ⭐ For spikes there are
> three real options: be pre-provisioned and pay for headroom, shed load gracefully, or queue the work
> and answer asynchronously. ⭐ And if the shape is predictable at all, ⭐⭐ **scheduled scaling is the
> most under-used policy — scaling before the spike instead of reacting to it is just static
> stability applied to capacity.**

**5. "What metric would you scale a Python web service on?"**
> ⭐⭐ **Request count per target, not CPU** — an I/O-bound Python service saturates its worker pool at
> maybe 30% CPU, ⭐⭐ **so CPU-based scaling never fires while every request queues.** ⭐ Requests per
> target maps directly to the thing that actually runs out, which is workers. ⭐ Queue depth for a
> worker fleet. ⭐ And I'd set an instance warm-up equal to my measured boot time, ⭐⭐ **because
> otherwise the ASG averages in a booting instance's 0% utilisation, concludes it needs more, and
> oscillates.**

**6. "Any default you always change on an ASG?"**
> ⭐⭐ **The health check type — it defaults to `EC2`, which only asks whether the instance is
> running.** ⭐ So an instance whose Python process is dead or wedged passes forever: the ALB stops
> sending it traffic and the ASG never replaces it, ⭐⭐ **so you run permanently degraded while the ASG
> reports 100% healthy.** ⭐ Setting it to `ELB` is one line.

## 🎙️ Articulation drill

**Two minutes.** Lead with the best story: **an intermittent 502 at 0.01%, no pattern, nothing in the
application logs — and the empty logs are the clue, because the request never reached the app.** The
ALB's idle timeout is 60 seconds and gunicorn's keep-alive is 2, **so the balancer holds a connection
it believes is good while the backend closes it, and occasionally sends a request onto the closing
socket and gets a FIN.** Rule: **the backend's keep-alive must exceed the balancer's idle timeout,
because only the balancer knows whether a request is in flight.** Then the health check, with the
arithmetic: **time to eject a dead target is interval times unhealthy threshold, so the defaults leave
traffic hitting a dead process for a full minute — and the endpoint must touch no dependency, because
a `/healthz` that checks Postgres turns a twenty-second database blip into a total outage that
outlives it.** Then the ordering that ties three systems together: **p99 request duration <
deregistration delay < stop timeout — and Fargate caps stop timeout at 120 seconds, so that's also a
ceiling on your longest request.** Close on scaling, with the number: **metric publication, alarm
evaluation, launch, boot, health checks — three to seven minutes from spike to capacity. So
autoscaling handles the trend, not the spike; for spikes you're pre-provisioned, you shed load, or you
queue the work.** And two defaults I always change: **scale on request-count-per-target rather than
CPU, because an I/O-bound Python service saturates its workers at 30% CPU; and set the ASG health
check to ELB, or an instance whose process is dead passes forever and you run degraded while the ASG
reports healthy.**
