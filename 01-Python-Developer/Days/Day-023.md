# Part 1 — ⭐⭐ What an object actually is

```c
/* ⭐ CPython, Include/object.h — every object in the language starts with this: */
typedef struct _object {
    Py_ssize_t ob_refcnt;        /* ⭐⭐ how many names/containers point at me (Day 026) */
    PyTypeObject *ob_type;       /* ⭐⭐ what I am — a POINTER to another object          */
} PyObject;
```

```
⭐⭐ THE THREE PROPERTIES EVERY OBJECT HAS, AND THEY ARE THE WHOLE MODEL:

⭐   IDENTITY  — its address. Never changes. ⇒ ⭐ id(x)      ⇒ tested with `is`
⭐   TYPE      — never changes. ⇒ ⭐ type(x)                 ⇒ decides what it can do
⭐   VALUE     — ⭐⭐ may or may not change ⇒ MUTABLE vs IMMUTABLE (Day 025)
```

```python
x = 42
type(x)          # <class 'int'>      ⭐ 42 is a heap object with a header
id(x)            # 140234...          ⭐ its address in CPython
x.bit_length()   # 6                  ⭐⭐ an INTEGER HAS METHODS. There is no primitive int.
(42).__add__(3)  # 45                 ⭐⭐ `+` is a method call (Day 031)
```

⭐⭐ **Compare Java, and say this comparison out loud in an interview:** Java has `int` (a machine
word, on the stack, no methods) *and* `Integer` (a heap object). ⭐⭐ **Python has only the second
kind.** There is no unboxed integer anywhere in the language.

```
⭐⭐ THE COST, AND IT IS THE FIRST HALF OF "WHY IS PYTHON SLOW" (Day 002):
⭐   a C int      = 8 bytes, in a register
⭐   a Python int = ⭐⭐ 28 bytes on the heap: refcount + type pointer + size + digits
⭐   ⇒ ⭐⭐ `a + b` is not an ADD instruction. It is: look up type(a), find __add__,
⭐        call it, ALLOCATE a new object for the result, adjust refcounts.
⭐   ⇒ ⭐ THAT is the 10–100× (Day 001's array.array experiment, now explained).
```

# Part 2 — ⭐⭐ Classes are objects too

```python
def f(): pass
class C: pass

type(42)      # <class 'int'>
type(int)     # ⭐⭐ <class 'type'>     ← int is an INSTANCE of type
type(C)       # ⭐ <class 'type'>
type(type)    # ⭐⭐ <class 'type'>     ← type is an instance of ITSELF. The recursion bottoms out here.
type(f)       # <class 'function'>
type(len)     # <class 'builtin_function_or_method'>
import os; type(os)   # ⭐ <class 'module'>
```

```
⭐⭐ SO: A CLASS IS AN OBJECT — an instance of `type`.
⭐   ⇒ it can be assigned to a name, put in a list, passed to a function, returned from one
⭐   ⇒ ⭐ this is why registries and factories in Python need no reflection API (contrast Java)
```

```python
# ⭐ Classes as data — completely ordinary Python:
HANDLERS = {"csv": CsvParser, "json": JsonParser}     # ⭐⭐ the CLASSES are the values
parser = HANDLERS[fmt]()                              # ⭐ look up, then call

# ⭐ type() with three arguments CREATES a class at runtime — this is what `class` compiles to:
Point = type("Point", (object,), {"x": 0, "y": 0})
```

⭐ **Metaclasses** are just "the type of a class", and you will almost never write one — ⭐⭐ **but you
use them constantly**: Django models, SQLAlchemy's declarative base and Pydantic's `BaseModel` all
use a metaclass to inspect the class body at definition time and build machinery from it. **Stage 1's OOP block
(053–063) covers writing one; today you only need to know what it *is*.**

# Part 3 — ⭐⭐ `type()` vs `isinstance()`, and duck typing

```python
type(x) == int              # ⚠️ ⭐ exact type only — a subclass FAILS
isinstance(x, int)          # ⭐⭐ x or any subclass ⇒ USE THIS
isinstance(x, (int, float)) # ⭐ a tuple of options
issubclass(bool, int)       # ⭐⭐ True! bool IS a subclass of int in Python.
True + True                 # ⭐⭐ 2. This is not a joke, and it is occasionally useful.
```

⚠️ ⭐⭐ **`isinstance(x, int)` is `True` for `True`.** Real consequence: a function validating an "id"
accepts `True` as the id `1`. Combined with Day 029's truthiness rules this produces a genuinely
confusing bug class.

```
⭐⭐ BUT THE PYTHONIC DEFAULT IS TO CHECK NEITHER — ⭐ DUCK TYPING:
⭐   "If it walks like a duck and quacks like a duck, it is a duck."
⭐   ⇒ ⭐ don't ask WHAT it is; ⭐⭐ just call the method and let it fail if it cannot
⭐   ⇒ ⭐ EAFP — "Easier to Ask Forgiveness than Permission" — is the Python idiom:
```

```python
# ⭐ LBYL — Look Before You Leap (the Java/C instinct):
if isinstance(f, File) and f.readable(): data = f.read()

# ⭐⭐ EAFP — the Python instinct, and it is not just style:
try:
    data = f.read()
except AttributeError:
    ...
# ⭐⭐ WHY IT IS BETTER: the LBYL check can be TRUE and the call still fail —
#     the state can change between the check and the use (a real race in threaded code).
#     ⇒ ⭐ and the happy path costs nothing: a try block that does not raise is ~free.
```

⭐ **Where explicit checks are still right:** at your system's *boundary* — parsing user input, an
API request body, a config file. ⭐⭐ **Inside your own code, trust the caller; at the edge, validate
everything** (which is what Pydantic will do for you in Stage 3).

# Part 4 — ⭐ Introspection, and the namespace as a dict

```python
dir(x)                 # ⭐ every attribute name
x.__dict__             # ⭐⭐ an instance's attributes — AN ORDINARY DICT
C.__dict__             # ⭐ the class's attributes — a mappingproxy (read-only view)
C.__mro__              # ⭐ method resolution order (Day 054)
callable(x)            # ⭐ has __call__ (Day 031)
getattr(x, "name", default)   # ⭐⭐ dynamic attribute access by string
hasattr(x, "read")     # ⭐ implemented as getattr in a try/except
vars(), globals(), locals()   # ⭐⭐ namespaces — also dicts (Day 030)
```

```
⭐⭐ THE REALISATION THAT MAKES PYTHON CLICK:
⭐   an object's attributes are a DICT.  a module's globals are a DICT.
⭐   a class's body is a DICT.           a function's locals are (conceptually) a DICT.
⭐   ⇒ ⭐⭐ "attribute access" is dictionary lookup with rules layered on top (Day 032)
⭐   ⇒ ⭐ which is why Python is so dynamic — and ⭐⭐ why each instance costs a whole dict
⭐        of memory until you use __slots__ (Day 028).
```

```python
import sys
sys.getsizeof(42)          # ⭐ 28
sys.getsizeof(0)           # ⭐ 24 — zero digits
sys.getsizeof(2**1000)     # ⭐⭐ 160 — Python ints are ARBITRARY PRECISION, so they GROW
sys.getsizeof("")          # 49
sys.getsizeof([])          # 56 — ⚠️ ⭐ and that EXCLUDES the objects it points at (Day 028)
```

⭐⭐ **Arbitrary-precision integers are worth naming in a DSA round:** there is no overflow in
Python, so an entire category of problem — "detect integer overflow", "use a long" — simply does not
exist. **Say that you noticed; it shows you know what the problem was testing for.**

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Thinking `int`/`float` are primitives** | ⭐⭐ Heap objects with headers and methods. There are no primitives. |
| ⭐ `type(x) == int` | ⭐⭐ Fails for subclasses. `isinstance`. |
| Forgetting `bool` is an `int` | ⭐⭐ `isinstance(True, int)` is `True`; `True + True == 2`. |
| Type-checking everywhere | ⭐ Duck typing inside; validate at the boundary. |
| ⭐ LBYL by reflex | ⭐⭐ EAFP is idiomatic *and* race-free. |
| Treating classes as special | ⭐ They are objects — store them, pass them, return them. |
| ⭐ Trusting `sys.getsizeof` on a container | ⭐⭐ It excludes referenced objects. |
| Expecting integer overflow | ⭐ Arbitrary precision. Mention it in a round. |
| Confusing `id()` with a hash | ⭐ `id` is the address; `hash` is a value-based digest (Day 029). |

## Interview questions

**Q: What does "everything is an object" actually mean in Python?**
> That every value is a heap-allocated structure with a reference count and a pointer to its type —
> there's no unboxed primitive anywhere. An integer has methods; a function is an object you can pass
> around; a class is an instance of `type`; a module is an object. The practical consequences are
> that anything can be stored, passed or returned uniformly, and that arithmetic is expensive,
> because `a + b` means a type lookup, a method call and a fresh allocation rather than a machine
> instruction.

**Q: `type()` or `isinstance()`?**
> `isinstance`, because it respects subclasses — `type(x) == int` rejects anything derived from
> `int`, which breaks polymorphism. But the more Python answer is usually neither: duck typing plus
> EAFP, where I attempt the operation and handle the exception, because the check-then-use pattern
> can be invalidated between the check and the use, and the happy path costs nothing. I'd keep
> explicit validation at the system boundary, where the input isn't mine.

**Q: What is `type` itself?**
> A class, and an instance of itself — `type(type) is type`. It's the default metaclass, the thing
> that constructs classes. Calling it with three arguments builds a class at runtime, which is
> exactly what the `class` statement compiles to. I rarely write metaclasses, but I use them
> constantly: Django models, SQLAlchemy's declarative base and Pydantic all inspect the class body at
> definition time through one.

**Q: Why is Python slow at arithmetic?**
> Because there's no primitive to be fast with. Adding two integers means dereferencing both objects,
> looking up the type, dispatching to `__add__`, allocating a new 28-byte object for the result, and
> updating reference counts — per operation, and interpreted per bytecode with no JIT. That's the
> constant factor behind the 10-to-100× difference, and it's why the strategy is to push the loop
> into C: NumPy stores unboxed machine integers contiguously and loops over them in compiled code.

**Q: Anything surprising about `bool`?**
> It's a subclass of `int`, so `True` is `1` and `isinstance(True, int)` is `True`. That matters when
> validating input — a function that accepts an integer id will silently accept `True` as `1`. It's
> also why `sum([True, False, True])` is a legitimate way to count matches.

## 🎙️ Articulation drill

Record two minutes: **"What does it mean that everything in Python is an object?"**

⭐ Start concrete: **there is no primitive integer.** `42` is a heap allocation with a reference
count, a type pointer, and methods you can call. ⭐ Then widen: functions, classes, modules and
`type` itself are all objects, which is why registries, decorators and dependency injection need no
special machinery in Python.

⭐⭐ **Then name both sides, because that is what makes it an engineering answer rather than a
recitation:** *"the uniformity is why the language is so flexible — and the same uniformity is the
constant factor that makes it slow, because every arithmetic operation is a type lookup, a method
dispatch and an allocation. That is exactly why the fix for slow Python is to move the loop into C
rather than to micro-optimise the Python."*
