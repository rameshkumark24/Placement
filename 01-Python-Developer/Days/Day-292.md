# Day 292 🔎

**P-292** · 🔎 **The RAG pipeline I** — ⭐⭐ ingestion, chunking, and the decisions that decide quality

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: if the right passage is not retrieved, nothing downstream can save you —
> no prompt, no model, no temperature. Which means the quality of this system is decided almost
> entirely by work you do before a model is ever called.**
>
> ⭐ Retrieval-augmented generation is a retrieval problem wearing a generation costume. ⭐⭐ Today
> is the unglamorous half where the quality actually comes from: parsing, chunking, metadata, and
> the ancestry a chunk needs to be findable at all.

# Part 1 — ⭐⭐ Where quality comes from

```
⭐⭐ THE PIPELINE, WITH WHERE THE QUALITY IS DECIDED:
⭐   PARSE ──► CLEAN ──► CHUNK ──► ENRICH ──► EMBED ──► INDEX
⭐   ⭐⭐ ~30%     ~10%    ⭐⭐ ~30%   ⭐ ~20%    ~10%    —

⭐   ⇒ ⭐⭐ NOTE WHAT IS ***NOT*** ON THIS LIST: THE MODEL, THE
⭐     PROMPT, AND THE TEMPERATURE. ⭐ They matter for how the
⭐     answer reads. ⭐⭐ THEY CANNOT PRODUCE A FACT THAT WAS
⭐     NEVER RETRIEVED.

⭐⭐ THE MENTAL MODEL THAT KEEPS YOU HONEST:
⭐   ***RETRIEVAL IS THE SYSTEM. THE MODEL IS A FORMATTER WITH
⭐      A GOOD VOCABULARY.***
⭐   ⇒ ⭐ Every hour spent on prompt wording before recall@k is
⭐     measured (Day 293) is an hour spent decorating a
⭐     conclusion you have not yet made correct.
```

# Part 2 — ⭐⭐ Parsing, which caps everything downstream

```
⭐⭐ THE UNDERRATED STAGE, BECAUSE ITS FAILURES ARE INVISIBLE:
⭐   ⭐ A PDF IS A ***LAYOUT*** FORMAT, NOT A DOCUMENT FORMAT.
⭐     It records glyph positions. ⭐⭐ THERE IS NO "PARAGRAPH"
⭐     IN A PDF — reading order is inferred, and inference fails
⭐     on two columns, sidebars and footnotes.
⭐   ⭐⭐ TABLES ARE DESTROYED BY DEFAULT. A limits table becomes
⭐     `Contractor 3 6 12 Permanent 6 12 24` — ⭐⭐ WHICH IS
⭐     WORSE THAN MISSING, because it is retrievable, plausible,
⭐     and unaligned with any column heading.
⭐   ⭐ HEADERS AND FOOTERS repeat on every page, so ⭐⭐ THE
⭐     COMPANY NAME AND "PAGE 4 OF 27" APPEAR IN EVERY CHUNK,
⭐     diluting every embedding by a constant.
⭐   ⭐ OCR quality is a HARD CEILING: a 92%-accurate scan means
⭐     roughly one wrong character per line, forever, in the
⭐     text you will cite.

⭐⭐ SO: INSPECT THE PARSED TEXT WITH YOUR OWN EYES, FOR TWENTY
⭐   DOCUMENTS, BEFORE BUILDING ANYTHING ELSE.
⭐   ⇒ ⭐⭐ THIS IS THE SINGLE HIGHEST-VALUE HOUR IN THE WHOLE
⭐     PIPELINE, and it is the one everybody skips, because it
⭐     feels like not-programming.
⭐   ⭐ Prefer structured sources when they exist — HTML, XML,
⭐     Markdown, an API — ⭐ a well-formed HTML policy page is
⭐     worth ten PDFs.
⭐   ⭐ Extract tables SEPARATELY and store them as tables.
⭐     ⭐⭐ AND IF A TABLE CONTAINS NUMBERS DECISIONS DEPEND ON,
⭐     IT BELONGS IN THE FACTS MODEL (Day 289), NOT THE CORPUS.
```

# Part 3 — ⭐⭐ Chunking

```
⭐⭐ FOUR STRATEGIES, AND ONE OF THEM IS RIGHT FOR POLICY:
⭐   ① ⭐ FIXED SIZE (500 tokens, 50 overlap) — ⭐⭐ SPLITS
⭐     MID-SENTENCE AND MID-TABLE. The baseline everyone starts
⭐     with and nobody should keep.
⭐   ② ⭐ RECURSIVE — split on paragraphs, then sentences, then
⭐     characters, until it fits. A reasonable default.
⭐   ③ ⭐⭐ STRUCTURAL — split on HEADINGS. ⭐ For policy
⭐     documents this is the answer, because ⭐⭐ A SECTION
⭐     BOUNDARY ***IS*** A MEANING BOUNDARY — someone already
⭐     did the semantic segmentation for you, by hand, and
⭐     printed it in bold.
⭐   ④ ⭐ SEMANTIC — split where embedding similarity between
⭐     adjacent sentences drops. ⭐ Clever, slow, and rarely
⭐     beats ③ on documents that HAVE structure.

⭐⭐ THE SIZE TRADE-OFF, STATED PROPERLY:
⭐   ⭐ SMALL chunks ⇒ precise embeddings, high precision,
⭐     ⭐⭐ AND THE ANSWER IS OFTEN SPLIT ACROSS TWO OF THEM.
⭐   ⭐ LARGE chunks ⇒ context survives, ⭐⭐ BUT THE EMBEDDING
⭐     IS AN AVERAGE OF EVERYTHING IN IT, so a chunk about six
⭐     topics is strongly similar to nothing at all.
⭐   ⇒ ⭐ Start at a section, cap at ~800 tokens, split long
⭐     sections recursively, overlap ~15%.
⭐   ⇒ ⭐⭐ AND THEN ***MEASURE IT*** (Day 293). Chunk size is
⭐     an empirical parameter, not a matter of taste, and it is
⭐     the first thing you should tune once you have a number.
```

# Part 4 — ⭐⭐ The ancestry every chunk must carry

```
⭐⭐ THE FAILURE THAT LOOKS LIKE A MODEL PROBLEM:
⭐   ⭐ A chunk reads, in its entirety:
⭐        "The maximum is 14 days in the first quarter."
⭐   ⇒ ⭐ It does not contain: which policy, which category of
⭐     worker, which jurisdiction, or which year.
⭐   ⇒ ⭐⭐ SO IT IS NEARLY UNRETRIEVABLE — nothing in the user's
⭐     question is lexically or semantically near it — AND IF IT
⭐     ***IS*** RETRIEVED, IT IS DANGEROUS, because it is a
⭐     number with no scope that a model will happily attach to
⭐     whatever the user asked about.

⭐⭐ THE FIX, AND IT IS ONE OF THE HIGHEST-VALUE CHANGES IN THIS
⭐   ENTIRE PIPELINE: ***PREPEND THE ANCESTRY TO THE EMBEDDED
⭐   TEXT.***
⭐   ⭐ Leave Policy 2026 (effective 2026-01-01, India) ›
⭐     Section 4: Contractors › 4.2 Leave entitlement
⭐     ───
⭐     The maximum is 14 days in the first quarter.
⭐   ⇒ ⭐ Now it matches "contractor leave India 2026", it is
⭐     self-describing when it lands in a prompt, and the model
⭐     cannot silently mis-scope it.
⭐   ⇒ ⭐⭐ THIS ONE CHANGE ROUTINELY MOVES recall@10 BY MORE
⭐     THAN SWITCHING EMBEDDING MODELS DOES, AND IT COSTS
⭐     TWENTY LINES.

⭐ ⭐ RELATED, AND CHEAP: store a WINDOW (the neighbouring
⭐   chunks) separately, retrieve on the small chunk, ⭐⭐ AND
⭐   SEND THE WINDOW TO THE MODEL. ⭐ You get small-chunk
⭐   precision with large-chunk context — the trade-off in
⭐   Part 3 partly dissolved.
```

# Part 5 — ⭐⭐ Metadata, decided now because retrofitting means reindexing

```
⭐   ⭐ document_id · version · section_path
⭐   ⭐⭐ effective_from / effective_to — ⭐ so the `as_of` date
⭐     (Day 289) can filter retrieval. ⭐⭐ WITHOUT THIS YOU
⭐     WILL CITE REPEALED POLICY, CONFIDENTLY.
⭐   ⭐⭐ access_level — ⭐ pre-filtered, never post-filtered
⭐     (Day 289 Part 5)
⭐   ⭐ jurisdiction / applicability
⭐   ⭐ content_hash — Part 7's incremental ingestion
⭐   ⭐ embedding_model_id — ⭐⭐ vectors from two models are in
⭐     different spaces and must never be compared
⭐   ⭐ ingested_at, parser_version — ⭐ so you can find every
⭐     chunk produced by the parser you have just discovered was
⭐     mangling tables

⭐ ⇒ ⭐⭐ FILTER ***BEFORE*** THE SEARCH, NOT AFTER. ⭐ Post-
⭐   filtering breaks `k` (you asked for 10 and can show 3) and,
⭐   for access level, is a redaction after the disclosure.
```

# Part 6 — ⭐ Embeddings, practically

```
⭐   ⭐ WHAT THEY ARE, OPERATIONALLY: a function from text to a
⭐     vector where "similar meaning" ≈ "close together" — under
⭐     ⭐⭐ THAT MODEL'S NOTION OF SIMILAR, WHICH IS NOT YOURS.
⭐     ⭐ Two clauses that are opposites are often very close,
⭐       because embeddings are weak at negation. ⭐⭐ THIS IS
⭐       WHY LEXICAL SEARCH DOES NOT GO AWAY (Day 293).
⭐   ⭐ Dimensions trade quality against memory and speed;
⭐     ⭐ normalise vectors and use cosine, consistently.
⭐   ⭐ Batch, and cache by content hash — ⭐⭐ RE-EMBEDDING AN
⭐     UNCHANGED CHUNK IS PURE COST, and on a 200-document
⭐     corpus it is most of your bill.
⭐   ⭐⭐ THE RE-EMBEDDING OBLIGATION: changing model ⇒
⭐     REINDEXING EVERYTHING. ⭐ So make reindex a routine job
⭐     with a runbook and a measured duration (Day 289), not an
⭐     event you dread — ⭐⭐ BECAUSE THE ALTERNATIVE IS BEING
⭐     UNABLE TO ADOPT A BETTER MODEL FOR THE LIFE OF THE
⭐     SYSTEM.
```

# Part 7 — ⭐⭐ Ingestion as an operable pipeline

```
⭐⭐ IT IS A JOB (Day 264), NOT A SCRIPT, AND IT NEEDS THE SAME
⭐   PROPERTIES:
⭐   ⭐ IDEMPOTENT — re-running produces the same index. ⭐ Key
⭐     chunks deterministically: (document_version, section_path,
⭐     chunk_index).
⭐   ⭐⭐ INCREMENTAL — content hash per source; unchanged
⭐     documents are skipped entirely. ⭐ Full re-ingest of 200
⭐     documents takes minutes and real money; incremental takes
⭐     seconds.
⭐   ⭐ RESUMABLE — chunked commits (Day 264), so a failure at
⭐     document 180 does not restart at 1.
⭐   ⭐⭐ DELETION IS PART OF INGESTION. A superseded or removed
⭐     document must have its chunks and VECTORS removed, or it
⭐     stays retrievable forever. ⭐ Reconcile: index count vs
⭐     source count, nightly (Day 270), and ⭐⭐ ALERT ON DRIFT —
⭐     a vector with no source document is a citation waiting to
⭐     be wrong.
⭐   ⭐ OBSERVABLE — documents processed, chunks produced,
⭐     ⭐⭐ CHUNKS ***SKIPPED*** AND WHY (a parse failure that
⭐     silently drops 30 documents is exactly the kind of
⭐     silence Day 270 exists to catch).
⭐   ⭐ VERSIONED — the parser and chunker have versions stored
⭐     on the chunk, so "which chunks need reprocessing?" is a
⭐     query rather than a guess.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Tuning prompts before measuring retrieval | No prompt recovers a passage that was never retrieved. |
| Not reading the parsed text yourself | The highest-value hour in the pipeline, and the one everyone skips. |
| Treating PDF as a document format | It records glyph positions; reading order is inferred and often wrong. |
| Letting tables flow into prose | Worse than missing: retrievable, plausible, and detached from its headings. |
| Leaving headers and footers in | Every chunk is diluted by the same constant text. |
| Numbers from tables left in the corpus | If a decision depends on it, it belongs in columns (Day 289). |
| Fixed-size chunking on structured documents | Section boundaries are meaning boundaries someone already marked. |
| Chunks too large | The embedding averages six topics and is similar to nothing. |
| Chunks too small | The answer splits across two of them. Retrieve small, send a window. |
| Chunks with no ancestry | "The maximum is 14 days" is unretrievable and dangerous if retrieved. |
| Treating chunk size as taste | It's an empirical parameter and the first thing to tune. |
| Deciding metadata later | Retrofitting means reindexing the whole corpus. |
| No effective dates on chunks | You will cite repealed policy, confidently. |
| Post-filtering by access level | Breaks `k`, and it's a redaction after disclosure. |
| Mixing embedding models in one index | Different vector spaces; store the model id and refuse to compare. |
| Re-embedding unchanged chunks | Pure cost, and most of your bill on a small corpus. |
| Treating reindex as a project | Then you can never adopt a better model. Make it routine with a runbook. |
| Ingestion as a script | It needs to be idempotent, incremental, resumable and observable. |
| Not deleting vectors on supersession | The old policy stays retrievable forever. |
| Not counting skipped documents | A parse failure that drops 30 documents is exactly the silent failure. |

## Interview questions

**Q: Where does RAG quality actually come from?**

> Ingestion, overwhelmingly — parsing and chunking are most of it, metadata is much of the rest, and
> the model and prompt are almost none of it. The framing I use is that retrieval is the system and
> the model is a formatter with a good vocabulary: if the right passage isn't retrieved, no prompt or
> temperature recovers it. So I don't touch prompt wording until recall@k is measured, because before
> that I'd just be decorating a conclusion I hadn't made correct yet.

**Q: What's hard about parsing policy documents?**

> That its failures are invisible downstream. A PDF is a layout format — it stores glyph positions,
> so there's no such thing as a paragraph and reading order is inferred, which breaks on columns and
> sidebars. Tables are the dangerous one: a limits table flattens into a row of numbers next to a row
> of categories, which is worse than missing because it's retrievable and plausible and no longer
> aligned with its headings. Headers and footers repeat into every chunk and dilute every embedding.
> So I read the parsed text of twenty documents by hand before building anything, prefer structured
> sources where they exist, extract tables separately — and if a table holds numbers a decision
> depends on, it goes in the relational model, not the corpus.

**Q: How do you chunk?**

> On structure, because in a policy document a section boundary is a meaning boundary that someone
> already marked by hand. Sections as the unit, capped around 800 tokens with long ones split
> recursively and a modest overlap. The trade-off is real in both directions: small chunks give
> precise embeddings but split answers across two of them, large chunks preserve context but average
> six topics into one vector that's strongly similar to nothing. The way out is to retrieve on the
> small chunk and send the surrounding window to the model. And chunk size is empirical — it's the
> first thing I tune once I have an eval number.

**Q: What's the single highest-value change you made to ingestion?**

> Prepending each chunk's ancestry to its embedded text — document title, effective date,
> jurisdiction, and the section path. Before that, a chunk reading "the maximum is 14 days in the
> first quarter" was nearly unretrievable, because nothing in a user's question is close to it, and
> actively dangerous if it *was* retrieved, since it's a number with no scope that a model will attach
> to whatever was asked. That change moved recall@10 more than switching embedding models did, and it
> was about twenty lines.

**Q: How does ingestion run?**

> As a job with the same properties as any other background work: idempotent, with chunks keyed
> deterministically so a re-run rebuilds the same index; incremental via content hashing, because
> re-embedding unchanged chunks is pure cost and most of the bill on a small corpus; resumable with
> chunked commits; and observable — including the count of documents *skipped* and why, since a parse
> failure that silently drops thirty documents is exactly the kind of silence that never raises an
> error. Deletion is part of it: a superseded document's vectors must go, or it stays retrievable
> forever, and I reconcile index count against source count nightly and alert on drift.

## 🎙️ Articulation drill

**Three minutes: "Walk me through your RAG ingestion."**

Lead with where quality comes from, because it reorders everything: **parsing and chunking are most of
it, and the model, the prompt and the temperature are none of it** — retrieval is the system and the
model is a formatter, so no prompt recovers a passage that wasn't retrieved. Then parsing, and be
specific rather than general: **a PDF is a layout format with no paragraphs**, reading order is
inferred, headers repeat into every chunk, and **a flattened limits table is worse than a missing one
because it's retrievable, plausible and detached from its headings.** Say that you read twenty parsed
documents by hand, and that it's the highest-value hour in the pipeline precisely because it feels
like not-programming. Then chunking on structure, because **a section boundary is a meaning boundary
somebody already marked**, with the size trade-off stated both ways and resolved by retrieving small
and sending a window. Then the change worth naming: **prepending ancestry to the embedded text moved
recall@10 more than switching embedding models did, for twenty lines** — because "the maximum is 14
days" has no scope, so it's unfindable and dangerous if found. Close on ingestion as a job rather than
a script: idempotent, incremental by content hash, resumable, **with deletion as part of it so a
superseded policy doesn't stay retrievable forever**, and a skipped-document count, because a parse
failure that silently drops thirty documents raises no error at all.
