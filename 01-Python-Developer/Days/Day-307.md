# Part 1 — ⭐⭐ Measure first, or you cannot claim anything

```
⭐⭐ FOUR NUMBERS, TAKEN NOW, WRITTEN DOWN:

⭐ ① ⭐ IMPORT-LINTER VIOLATIONS (Days 299, 306)
⭐      ⭐ Add the contracts, run it, ⭐⭐ AND DO NOT FIX
⭐        ANYTHING YET. The count is your baseline.

⭐ ② ⭐⭐ DOMAIN TEST SUITE DURATION
⭐      ⭐ `pytest tests/domain --durations=0`. ⭐⭐ IF IT IS
⭐        NOT SUB-SECOND, RULES ARE STILL IN SERVICES AND THE
⭐        DIRECTORY NAME IS ASPIRATIONAL (Day 300).

⭐ ③ ⭐ `mock.patch` COUNT (Day 303)
⭐      ⭐ `grep -rc "mock.patch\|monkeypatch" tests/ | ...`
⭐      ⭐⭐ EACH ONE IS A DEPENDENCY THAT WAS NOT INJECTED.

⭐ ④ ⭐⭐ FILES TOUCHED BY A STANDARD CHANGE (Day 298)
⭐      ⭐ Pick one: "add an optional `reference` field to a job,
⭐        settable at creation, visible in the API and
⭐        searchable." ⭐ Do it on a scratch branch and COUNT
⭐        THE FILES. ⭐⭐ THEN THROW THE BRANCH AWAY.
⭐      ⇒ ⭐⭐ THIS IS THE ONLY NUMBER THAT MEASURES WHAT
⭐        ARCHITECTURE IS ***FOR***. The other three are proxies.
```

```
⭐ ⇒ ⭐⭐ AND WRITE THE PREDICTION: which number do you expect
⭐   to improve most? ⭐ Being wrong is the point (Day 286) —
⭐   people consistently predict ④ improves and it usually
⭐   moves least, because layering does not reduce the number
⭐   of places a field must be declared.
```

# Part 2 — ⭐⭐ Two rules that make refactoring safe

```
⭐⭐ RULE ①: ***REFACTOR UNDER TEST.***
⭐   ⭐ A refactoring is by definition a change that does not
⭐     alter behaviour — ⭐⭐ AND THE ONLY WAY TO KNOW THAT IS
⭐     A TEST THAT WOULD NOTICE.
⭐   ⭐ If the area has no tests, write characterisation tests
⭐     FIRST (Day 296), pinning current behaviour including the
⭐     parts you think are wrong.

⭐⭐ RULE ②: ***ONE REFACTORING PER COMMIT, AND NEVER MIXED
⭐   WITH A BEHAVIOUR CHANGE.***
⭐   ⭐ A commit that moves 40 files AND fixes a bug is
⭐     unreviewable and unbisectable. ⭐⭐ WHEN SOMETHING
⭐     BREAKS IN THREE WEEKS, `git bisect` LANDS ON A COMMIT
⭐     WITH 400 CHANGED LINES AND TELLS YOU NOTHING.
⭐   ⇒ ⭐ Separate commits mean bisect lands on "extracted Money
⭐     value object" — ⭐⭐ WHICH IS AN ANSWER, NOT A STARTING
⭐     POINT.
⭐   ⭐ And the corollary people ignore: ⭐⭐ IF YOU NOTICE A
⭐     BUG WHILE REFACTORING, ***WRITE IT DOWN AND FIX IT IN A
⭐     SEPARATE COMMIT AFTERWARDS.*** ⭐ Fixing it inline is how
⭐     a refactor becomes unreviewable.
```

# Part 3 — ⭐⭐ The order, which matters more than the principles

```
⭐⭐ DO THEM IN THIS SEQUENCE. EACH STEP MAKES THE NEXT ONE
⭐   SAFER, AND DOING THEM OUT OF ORDER IS WHY REFACTORS STALL:

⭐ ① ⭐⭐ ADD THE CONTRACTS, FIX NOTHING. ⭐ You now have a
⭐      failing check and a list. ⭐ Everything after this is
⭐      "make the list shorter", which is a task with an end.

⭐ ② ⭐ EXTRACT VALUE OBJECTS (Day 304).
⭐      ⭐⭐ LOWEST RISK, HIGHEST READABILITY, AND IT TOUCHES
⭐        SIGNATURES EVERYWHERE — ⭐ so doing it first means
⭐        later steps move already-clean signatures.
⭐      ⭐ `Money`, `JobId`, `TenantId`, `DateRange`.

⭐ ③ ⭐⭐ MOVE RULES INTO ENTITIES (Days 302, 304).
⭐      ⭐ Guided by the duplicated-`if` grep. ⭐ One rule per
⭐        commit, with the service call replaced by one line.

⭐ ④ ⭐ FIX PORT OWNERSHIP (Day 300) — move interfaces next to
⭐      their consumers, convert ABCs to `Protocol`.

⭐ ⑤ ⭐ SPLIT THE GOD SERVICE (Day 299) — ⭐ by the tables each
⭐      method touches, not by name.

⭐ ⑥ ⭐⭐ INTRODUCE THE COMPOSITION ROOT (Day 303) — ⭐ last,
⭐      because it is easiest once dependencies are already
⭐      parameters. ⭐⭐ DOING IT FIRST MEANS WIRING CODE YOU
⭐      ARE ABOUT TO RESTRUCTURE.

⭐ ⑦ ⭐ ONLY THEN: MODULE BOUNDARIES (Day 306), if the project
⭐      is big enough to have contexts at all.

⭐ ⇒ ⭐⭐ NOTE THAT ② AND ③ ARE ***BOTTOM-UP*** AND ⑥ AND ⑦ ARE
⭐   ***TOP-DOWN***. ⭐ Bottom-up first, because value objects
⭐   and entity methods are correct regardless of what the
⭐   top-level structure turns out to be — ⭐⭐ SO THEY ARE
⭐   NEVER WASTED WORK, WHICH IS EXACTLY WHAT YOU WANT FROM THE
⭐   FIRST HALF OF A REFACTOR YOU MIGHT NOT FINISH.
```

# Part 4 — ⭐⭐ Worked: one rule, moved

```python
# ⭐ BEFORE — in three services, with one of them subtly different
if job.status != "in_progress":
    raise HTTPException(400, "Job is not in progress")
if completed_at < job.started_at:
    raise HTTPException(400, "Bad completion time")
job.status = "completed"; job.completed_at = completed_at
```

```
⭐⭐ THE COMMIT SEQUENCE — FIVE COMMITS, EACH GREEN:
⭐   ① ⭐ Write a domain test for `Job.complete()`. ⭐⭐ IT
⭐        FAILS: the method does not exist. ⭐ Good — the test
⭐        is now the specification.
⭐   ② ⭐ Add `Job.complete(at)` raising domain exceptions.
⭐        Tests pass. ⭐ Nothing calls it yet.
⭐   ③ ⭐ Change service A to call it. ⭐⭐ ITS TESTS STILL
⭐        PASS ONLY IF THE EXCEPTION MAPPING WORKS (Day 257) —
⭐        which is the moment you discover whether you have one
⭐        exception handler or three ad-hoc `try` blocks.
⭐   ④ ⭐ Change services B and C. ⭐⭐ ONE OF THEM WILL HAVE A
⭐        SUBTLY DIFFERENT RULE — ⭐ and that discrepancy is
⭐        the most valuable finding of the day, because ⭐⭐ IT
⭐        IS EITHER A BUG YOU HAVE BEEN SHIPPING OR A DOMAIN
⭐        RULE NOBODY WROTE DOWN. ⭐ Ask, don't guess.
⭐   ⑤ ⭐ Delete the duplicated checks.

⭐ ⇒ ⭐⭐ FIVE COMMITS, EACH INDIVIDUALLY REVERSIBLE, EACH
⭐   REVIEWABLE IN UNDER A MINUTE. ⭐ The same work as one
⭐   40-file commit, and a completely different risk profile.
```

# Part 5 — ⭐⭐ The five ways this goes wrong

```
⭐⭐ ① THE BIG-BANG BRANCH. ⭐ Two weeks of restructuring on
⭐     `refactor/clean-arch`. ⭐⭐ MAIN MOVES, THE MERGE
⭐     BECOMES A PROJECT, AND THE BRANCH IS ABANDONED — taking
⭐     the good work with it. ⭐ Merge daily, or it is not a
⭐     refactor, it is a rewrite with optimistic branding.

⭐⭐ ② "WHILE I'M HERE." ⭐ You are extracting Money and you
⭐     notice the tax calculation is wrong. ⭐⭐ WRITE IT DOWN.
⭐     ⭐ A refactor that also changes three behaviours cannot
⭐     be verified by "the tests still pass", because the tests
⭐     changed too.

⭐⭐ ③ RENAMING ACROSS A PUBLISHED BOUNDARY. ⭐ Renaming an
⭐     internal class is free. ⭐⭐ RENAMING A JSON FIELD, A
⭐     QUEUE MESSAGE KEY OR A DATABASE COLUMN IS A MIGRATION
⭐     WITH A ROLLOUT (Day 283) — ⭐ and doing it inside a
⭐     "pure refactor" commit is how a refactor causes an
⭐     incident and poisons the practice for a year.

⭐⭐ ④ ABSTRACTING WHAT DOES NOT VARY. ⭐ You now know the
⭐     patterns, so everything looks like it needs a port.
⭐     ⭐⭐ ONE IMPLEMENTATION BEHIND AN INTERFACE IS A COST
⭐     WITH NO PURCHASE (Day 298).

⭐⭐ ⑤ REFACTORING CODE THAT NEVER CHANGES. ⭐ The CSV importer
⭐     written 14 months ago, untouched since, working.
⭐     ⭐⭐ CLEAN CODE IS AN INVESTMENT IN ***FUTURE CHANGE***.
⭐     Code with no future change has no return on that
⭐     investment — ⭐ and touching it converts zero risk into
⭐     some risk for no benefit. ⭐ Check the git log before
⭐     you open a file.
```

# Part 6 — ⭐⭐ The stopping rule

```
⭐⭐ ***REFACTOR UNTIL THE NEXT CHANGE IS EASY. THEN STOP.***
⭐   ⭐ Not "until it matches the diagram in the book."
⭐   ⭐⭐ NOT UNTIL EVERY CONTRACT PASSES — some violations are
⭐     correct and should be recorded as exceptions with
⭐     reasons, which is a decision, not a defeat.

⭐ ⭐ THE CONCRETE TEST: RE-RUN MEASUREMENT ④.
⭐   ⭐ Do the same change request on a fresh scratch branch and
⭐     count the files again.
⭐   ⇒ ⭐⭐ IF IT DID NOT MOVE, YOU IMPROVED READABILITY AND
⭐     TESTABILITY BUT NOT CHANGE COST — ⭐ which is a real
⭐     result and should be reported honestly, not dressed up.
⭐   ⇒ ⭐ And often the honest finding is that ⭐⭐ THE FILE
⭐     COUNT IS IRREDUCIBLE: a new field genuinely must appear
⭐     in a migration, a model, a domain object, two schemas and
⭐     a test. ⭐ Six files is not a design failure; it is what
⭐     the change costs — ⭐⭐ AND KNOWING THAT STOPS YOU
⭐     CHASING IT WITH ABSTRACTIONS THAT MAKE EVERYTHING ELSE
⭐     WORSE.
```

# Part 7 — ⭐ The write-up

```
⭐   ⭐ AN ADR WITH FOUR SECTIONS:
⭐     ⭐ WHAT CHANGED — the six steps, with commit ranges
⭐     ⭐ THE NUMBERS — before and after, all four, ⭐ including
⭐       the one that did not move
⭐     ⭐⭐ WHAT I DELIBERATELY DID NOT DO — the CSV importer,

⭐     ⭐ WHAT I GOT WRONG — ⭐⭐ the prediction from Part 1,
⭐       and what the real answer turned out to be

⭐ ⇒ ⭐⭐ THAT LAST SECTION IS WHY THIS DAY IS WORTH DOING.
⭐   ⭐ "I refactored it to clean architecture" is a claim
⭐     anyone can make. ⭐⭐ "I MEASURED FOUR THINGS, THREE
⭐     IMPROVED, ONE DIDN'T, AND HERE IS WHY I NOW THINK THE
⭐     FOURTH IS IRREDUCIBLE" IS EVIDENCE OF ENGINEERING.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Refactoring without a baseline | A refactor with no number is an opinion. |
| Only measuring proxies | Files-touched-by-a-change is the one that measures what architecture is for. |
| No prediction | Being wrong is the point, and people are usually wrong about which number moves. |
| Refactoring untested code | A refactoring is a change that preserves behaviour; you need something that would notice. |
| Mixing a refactor with a bug fix | Unreviewable, and `git bisect` lands on 400 lines and tells you nothing. |
| Fixing a bug you notice mid-refactor | Write it down; fix it in its own commit. |
| Starting top-down | You'd wire code you're about to restructure. |
| Composition root first | It's easiest last, once dependencies are already parameters. |
| Doing the module split early | Only after value objects, entity rules and ports are settled. |
| A two-week refactor branch | Main moves, the merge becomes a project, the work is abandoned. |
| "While I'm here" | The tests changed too, so "tests still pass" proves nothing. |
| Renaming a JSON field or column in a refactor commit | That's a migration with a rollout, and it poisons the practice. |
| Adding ports to everything | One implementation behind an interface is a cost with no purchase. |
| Refactoring code that never changes | Clean code is an investment in future change; check the git log first. |
| Refactoring until it matches a book diagram | Stop when the next change is easy. |
| Treating remaining violations as failure | Some are correct; record them as exceptions with reasons. |
| Hiding the number that didn't move | That's the honest finding, and often it's irreducible. |

## Interview questions

**Q: How do you approach a refactor?**

> With measurements taken before I start, because a refactor with no number is an opinion. I record
> four: import-linter violations, domain test suite duration, `mock.patch` count, and — the only one
> that measures what architecture is actually for — the number of files touched by a standard change
> request, done on a scratch branch that I then throw away. I also write a prediction about which will
> improve most, and I'm often wrong: people expect the files-touched number to drop, and it usually
> moves least, because layering doesn't reduce the number of places a field must be declared.

**Q: What order do you do the work in?**

> Bottom-up first, top-down last, and the order matters more than the principles. Add the contracts
> and fix nothing, so I have a list and the task has an end. Then value objects, which are the lowest
> risk and touch signatures everywhere, so later steps move already-clean code. Then rules into
> entities, one per commit. Then port ownership, then splitting the god service, then the composition
> root — last, because it's easy once dependencies are already parameters, and doing it first means
> wiring code I'm about to restructure. The reason for bottom-up first is that value objects and
> entity methods are correct regardless of how the top-level structure ends up, so they're never
> wasted work on a refactor I might not finish.

**Q: How do you keep it safe?**

> Two rules. Refactor under test — and if the area has none, characterisation tests first, pinning
> current behaviour including the parts I think are wrong. And one refactoring per commit, never mixed
> with a behaviour change, because when something breaks three weeks later `git bisect` landing on
> "extracted Money value object" is an answer, whereas landing on a 400-line commit that moved forty
> files and fixed a bug is a starting point. If I notice a bug while refactoring, I write it down and
> fix it separately.

**Q: What did you find that you didn't expect?**

> When I moved a completion rule out of three services into the entity, one of the three had a subtly
> different version of it. That discrepancy was the most valuable thing I found all day, because it's
> either a bug I'd been shipping or a domain rule nobody wrote down — and the only way to tell is to
> ask rather than guess. That's a general property of consolidating duplicated logic: the duplicates
> are never quite identical, and the difference is information.

**Q: When do you stop?**

> When the next change is easy — not when it matches a diagram, and not when every contract passes,
> because some violations are correct and get recorded as exceptions with reasons. The concrete test
> is re-running the files-touched measurement. In my case it barely moved, and the honest conclusion
> was that the count is irreducible: a new field genuinely has to appear in a migration, a model, a
> domain object, two schemas and a test. Six files isn't a design failure, it's what the change costs
> — and knowing that stopped me chasing it with abstractions that would have made everything else
> worse.

## 🎙️ Articulation drill

**Two minutes: "Tell me about a refactor you did."**

Start with the discipline rather than the outcome: **a refactor with no number is an opinion**, so
four measurements first — contract violations, domain test duration, `mock.patch` count, and files
touched by a standard change request, which is the only one that measures what architecture is for.
Say you wrote a prediction and were wrong, because that's the interesting part. Then the order, and
why it's the order: **bottom-up first — value objects, then rules into entities — because those are
correct regardless of how the top-level structure ends up**, so they're never wasted if you don't
finish; composition root and module boundaries last, since wiring code you're about to restructure is
pure waste. Give the safety rules: refactor under test, with characterisation tests first if there
aren't any, and **one refactoring per commit, never mixed with a bug fix — because bisect landing on
"extracted Money" is an answer and bisect landing on 400 lines is a starting point.** Then the finding
worth telling: **consolidating a rule from three services revealed that one of them was subtly
different**, which is either a bug you've been shipping or an unwritten rule — and you ask rather than
guess. Close on stopping honestly: **refactor until the next change is easy, then stop**, and report
the number that didn't move — in my case files-touched, because a new field genuinely has to appear in
six places, and knowing that stops you chasing it with abstractions that make everything else worse.
