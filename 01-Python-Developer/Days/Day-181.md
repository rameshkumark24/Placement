# Part 1 — ⭐ Finding it: the toolbar, silk, and the ceiling

```
⭐⭐ THREE TOOLS, AND THEY CATCH THINGS AT DIFFERENT TIMES:

⭐  1. ⭐⭐ `django-debug-toolbar` — DEVELOPMENT. ⭐ Query count, duplicate
⭐       queries, SQL with `EXPLAIN`, template render time, cache hits.
⭐       ⭐⭐ THE "DUPLICATE QUERIES" PANEL IS THE N+1 DETECTOR — ⭐ it shows
⭐       "47 similar queries" and that number is the bug.
⭐       ⚠ ⭐⭐ NEVER IN PRODUCTION: it holds every query in memory and exposes
⭐         your settings.
⭐  2. ⭐ `django-silk` — ⭐⭐ works in a real environment (staging), records
⭐       per-request query and profile data, and can be sampled. ⭐ The middle
⭐       ground when the toolbar is not an option.
⭐  3. ⭐⭐ `assertNumQueries` — CI. ⭐ The only one that catches a regression
⭐       BEFORE it ships, on the commit that caused it (Days 141, 180).
⭐
⭐   ⇒ ⭐⭐ AND IN PRODUCTION: `py-spy` (Day 157) AND TRACES (Day 148),
⭐        unchanged. ⭐ Django adds no new answer there — ⭐⭐ the wide
⭐        `db.acquire` span still means your pool, not the database.

⭐⭐ THE DJANGO-SPECIFIC SLOW PATHS, IN ROUGH ORDER OF HOW OFTEN THEY ARE THE
⭐   ANSWER:
⭐   ⭐ THE N+1 (Day 171) — ⭐⭐ including from a TEMPLATE, which no profiler
⭐        attributes to the view.
⭐   ⭐ ⭐⭐ SERIALIZATION. DRF serializers are pure Python (Day 175); on a
⭐        large list they can exceed the query time. ⭐ `.values()` + dicts is
⭐        often 5–10× faster and is a legitimate fix.
⭐   ⭐ ⭐⭐ MODEL INSTANTIATION. 100k rows means 100k objects. ⭐ `values_list`
⭐        or `.iterator()`.
⭐   ⭐ THE PAGINATOR'S `COUNT(*)` on a huge table, on every page.
⭐   ⭐ ⭐⭐ MIDDLEWARE THAT TOUCHES `request.user` (Day 174) — a lazy object,
⭐        so one log line adds a query to EVERY request including `/healthz`.
⭐   ⭐ TEMPLATE RENDERING with many small includes (the toolbar shows it).
```

# Part 2 — ⭐⭐ The four cache levels

```
⭐⭐ FROM COARSEST TO FINEST. ⭐ The finer you go, the more control and the
⭐   more code:

⭐  1. ⭐ PER-SITE (`UpdateCacheMiddleware` + `FetchFromCacheMiddleware`)
⭐       ⭐⭐ CACHES EVERY ANONYMOUS GET. ⭐ Blunt, and see Part 3 — this is
⭐       where the leak lives.
⭐  2. ⭐ PER-VIEW (`@cache_page(60)`)
⭐       ⭐⭐ Same hazard, narrower blast radius.
⭐  3. ⭐⭐ TEMPLATE FRAGMENT (`{% cache 300 sidebar request.user.id %}`)
⭐       ⭐ Excellent for an expensive widget on an otherwise dynamic page.
⭐       ⭐⭐ NOTE THE `request.user.id` VARY ARGUMENT — ⭐ every varying input
⭐       must be in that list, and forgetting one is the leak again.
⭐  4. ⭐⭐ LOW-LEVEL (`cache.get` / `cache.set`) — ⭐ Day 143's cache-aside,
⭐       and ⭐⭐ THE ONE TO REACH FOR BY DEFAULT, because you control the key,
⭐       the TTL and the invalidation explicitly.
```

```python
# ⭐ low-level, with every Day 143 rule applied
def get_event(event_id: int) -> dict:
    key = f"event:v2:{event_id}"                    # ⭐⭐ v2 — rolling deploys share a cache
    if (hit := cache.get(key)) is not None:
        return hit
    data = EventSerializer(Event.objects.get(pk=event_id)).data
    cache.set(key, data, 60 + random.randint(0, 20))   # ⭐⭐ TTL + JITTER
    return data

def update_event(event_id: int, **fields) -> None:
    Event.objects.filter(pk=event_id).update(**fields)
    transaction.on_commit(lambda: cache.delete(f"event:v2:{event_id}"))
    #  ⭐⭐ WRITE DB → DELETE KEY, AFTER COMMIT. ⭐ Delete, not update; after,
    #     not before (Day 143). ⭐⭐ `on_commit` because a rolled-back write
    #     must not invalidate a correct cache entry.
```

```
⭐ THE BACKENDS, JUDGED:
⭐   ⭐ `LocMemCache` — ⭐⭐ PER PROCESS. Four workers means four caches with
⭐        four different answers, ⭐ and it silently makes any distributed
⭐        reasoning wrong. ⭐⭐ Development only. (Day 176: this is also why
⭐        DRF throttling is meaningless with it.)
⭐   ⭐ `RedisCache` — ⭐⭐ the answer. ⭐ Set a `socket_timeout` (Day 152) or a
⭐        hung Redis hangs every request — ⭐⭐ the cache becomes the outage.
⭐   ⭐ `DatabaseCache` — ⭐ works, ⭐⭐ and it puts load on the thing you were
⭐        trying to protect.
⭐   ⭐ ⭐⭐ AND THE EVICTION POINT FROM Day 143: if this Redis is `allkeys-lru`,
⭐        DO NOT ALSO PUT SESSIONS, RATE-LIMIT COUNTERS OR THE CELERY BROKER
⭐        ON IT. ⭐ Evicted sessions log everyone out; evicted jobs vanish.
```

# Part 3 — ⭐⭐ The per-view cache leak

```
⭐⭐ THE MISTAKE THAT SERVES ONE USER'S PAGE TO ANOTHER:

⭐   @cache_page(60)
⭐   def dashboard(request):
⭐       return render(request, "dash.html", {"orders": request.user.orders.all()})
⭐
⭐   ⭐⭐ `cache_page` KEYS ON THE **URL** (plus headers named in `Vary`).
⭐   ⇒ ⭐ Alice loads `/dashboard/`. ⭐⭐ Bob loads `/dashboard/` and GETS
⭐        ALICE'S ORDERS. ⭐ For sixty seconds. With no error anywhere.
⭐   ⇒ ⭐⭐ THIS IS Day 124'S SHARED-CACHE LEAK, INSIDE YOUR OWN APPLICATION.

⭐⭐ THE THREE THINGS THAT MAKE IT SURVIVABLE, AND YOU NEED ALL THREE:
⭐  1. ⭐⭐ **NEVER PER-VIEW-CACHE AN AUTHENTICATED VIEW.** ⭐ The blanket rule
⭐       is the safe one, and it costs almost nothing because authenticated
⭐       pages are usually the personalised ones.
⭐  2. ⭐ `@vary_on_cookie` / `@vary_on_headers("Cookie")` ⇒ ⭐⭐ keys per
⭐       session. ⭐ Correct, and the hit rate collapses to roughly zero, so
⭐       you have paid for a cache that does nothing.
⭐  3. ⭐⭐ USE THE **LOW-LEVEL** CACHE WITH THE USER OR TENANT IN THE KEY.
⭐       ⭐ Explicit, correct, and it caches the expensive PART rather than the
⭐       whole response.
⭐
⭐   ⇒ ⭐⭐ AND THE SAME TRAP AT LEVEL 3: `{% cache 300 sidebar %}` WITH NO
⭐        VARY ARGUMENT IS ONE FRAGMENT SHARED BY EVERY USER. ⭐ Add
⭐        `request.user.id`, the tenant, the locale, and any feature flag —
⭐        ⭐⭐ every input that changes the output must be in the key
⭐        (Day 143's rule, exactly).
⭐
⭐⭐ AND FOR ANY RESPONSE THAT IS PER-USER, WHETHER YOU CACHE IT OR NOT:
⭐   ⭐ `Cache-Control: private, no-store` (Day 124) — ⭐⭐ because a CDN or a
⭐        corporate proxy will otherwise cache it for you, and you will not
⭐        find out from your own logs.
```

# Part 4 — ⭐ Indexes and the database side

```python
class Order(models.Model):
    class Meta:
        indexes = [
            models.Index(fields=["user", "-created_at"]),        # ⭐ the list query
            models.Index(fields=["status"], name="ix_pending",
                         condition=Q(status="pending")),          # ⭐⭐ PARTIAL
        ]
        constraints = [
            models.CheckConstraint(check=Q(qty__gt=0), name="ck_qty_positive"),
            models.UniqueConstraint(fields=["idempotency_key"], name="uq_idem"),
        ]
```

```
⭐⭐ FIVE INDEXING FACTS THAT MATTER FOR AN APPLICATION DEVELOPER:
⭐  1. ⭐⭐ `db_index=True` IS FINE FOR ONE COLUMN AND USELESS FOR A COMPOSITE
⭐       QUERY. ⭐ `WHERE user=? ORDER BY created_at DESC` wants ONE index on
⭐       `(user, -created_at)`, ⭐⭐ not two separate indexes.
⭐  2. ⭐⭐ COLUMN ORDER MATTERS: EQUALITY FIRST, THEN RANGE/SORT. ⭐ An index
⭐       on `(created_at, user)` does not serve that query well.
⭐  3. ⭐ A PARTIAL INDEX (`condition=`) is tiny and fast when you always
⭐       filter on a state — ⭐⭐ Day 164's active-holds index exactly.
⭐  4. ⭐⭐ EVERY INDEX SLOWS WRITES AND COSTS DISK. ⭐ Index what you query,
⭐        not what you have. ⭐⭐ And unused indexes are real: check
⭐        `pg_stat_user_indexes` for `idx_scan = 0`.
⭐  5. ⭐⭐ `ForeignKey` CREATES AN INDEX AUTOMATICALLY; ⭐ a plain
⭐        `ForeignKey(db_index=False)` on a big table makes cascade deletes
⭐        and reverse lookups scan.
⭐
⭐   ⇒ ⭐⭐ AND `qs.explain()` (Day 171) IS HOW YOU CHECK, ⭐ not intuition.
⭐        `explain(analyze=True)` gives real timings and row estimates —
⭐        ⭐⭐ and a wildly wrong row estimate usually means stale statistics,
⭐        not a missing index.
```

```
⭐⭐ THREE MORE DATABASE-SIDE WINS:
⭐   ⭐ `bulk_create` / `bulk_update` — ⭐ 1 query instead of N, ⭐⭐ with
⭐        Day 172's warning: they skip `save()`, signals and validation.
⭐   ⭐ `update()` WITH `F()` — ⭐⭐ arithmetic in the database, no read.
⭐   ⭐ `Subquery`/`OuterRef` for correlated values — ⭐⭐ avoids the double-
⭐        `Count` join multiplication bug (Day 172) and keeps it to one query.
```

# Part 5 — ⭐⭐ The order of operations

```
⭐⭐ WHEN A DJANGO PAGE IS SLOW, WORK THIS ORDER. ⭐ It is Day 157's ladder
⭐   with Django's specifics filled in:

⭐  1. ⭐⭐ MEASURE. Toolbar in development, silk in staging, a trace in
⭐       production. ⭐ Never guess — ⭐⭐ and check whether latency is up with
⭐       CPU FLAT, which means blocked rather than busy.
⭐  2. ⭐⭐ COUNT THE QUERIES. ⭐ If it is more than about five for one page,
⭐       stop here — it is an N+1 and nothing else matters yet.
⭐  3. ⭐ FIX THE LOADING: `select_related` for to-one, `prefetch_related`
⭐       for to-many, `Prefetch` when it needs filtering. ⭐⭐ Then set an
⭐       `assertNumQueries` ceiling so it cannot come back.
⭐  4. ⭐ FETCH LESS: `only`/`defer` carefully, `values()` for reports,
⭐       `iterator()` for scans.
⭐  5. ⭐ INDEX WHAT YOU FILTER AND SORT ON. ⭐ Verify with `explain`.
⭐  6. ⭐⭐ CACHE — LOW-LEVEL, WITH EVERY VARYING INPUT IN THE KEY, a TTL you
⭐       can defend, and jitter.
⭐  7. ⭐ MOVE IT OFF THE REQUEST PATH — Celery (Day 142).
⭐  8. ⭐ MORE WORKERS — ⭐⭐ and only after checking `max_connections`
⭐       (Day 179).
⭐
⭐   ⇒ ⭐⭐ THE POINT OF THE ORDER: STEPS 2–3 ARE FREE AND USUALLY WORTH 10×.
⭐        ⭐ Step 6 is where people start, and it adds a consistency problem
⭐        to a performance problem — ⭐⭐ CACHING A SLOW QUERY MEANS YOU NOW
⭐        HAVE A SLOW QUERY **AND** A STALENESS BUG.

⭐⭐ AND THE HONEST CLOSING POINT: THE FASTEST CACHE IS THE ONE YOU DID NOT
⭐   NEED. ⭐ A page doing 4 queries against indexed columns and returning
⭐   50 rows does not need caching at any realistic scale. ⭐⭐ Most Django
⭐   performance work is deleting queries, not adding infrastructure.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| `django-debug-toolbar` enabled in production | It holds every query in memory and exposes your settings. |
| Guessing instead of reading the duplicate-queries panel | That "47 similar queries" number *is* the bug. |
| `@cache_page` on an authenticated view | It keys on the URL — Bob gets Alice's dashboard for 60 seconds. |
| `vary_on_cookie` as the fix | Correct, and the hit rate collapses to zero, so you've paid for nothing. |
| `{% cache %}` with no vary arguments | One fragment shared by every user. |
| Any per-user response without `private, no-store` | A CDN or corporate proxy caches it and you never find out. |
| `LocMemCache` in production | Per process — four workers, four caches, four answers. |
| No `socket_timeout` on the cache Redis | A hung cache hangs every request; the protection becomes the outage. |
| Cache Redis shared with sessions and the broker under LRU | Evicted sessions log everyone out; evicted jobs vanish. |
| Updating the cache on write | Interleaved writers can leave the older value cached. Delete. |
| Deleting the key before the DB write, or before commit | A reader repopulates stale data; a rollback invalidates a correct entry. |
| Identical TTLs on bulk-warmed keys | They all expire in the same second. Add jitter. |
| No version segment in the key | Rolling deploys make old and new code read each other's shapes. |
| Two `db_index=True` columns for a composite query | You want one index on the pair, in the right order. |
| Composite index with the sort column first | Equality first, then range or sort. |
| Indexing everything | Every index slows writes; check `pg_stat_user_indexes` for unused ones. |
| Caching before fixing the query count | You now have a slow query *and* a staleness bug. |

## Interview questions

**Q: Your Django page is slow. What's your order of work?**

> Measure first — toolbar in development, silk in staging, a trace in production — and check whether
> latency is up while CPU is flat, because that means blocked rather than busy and eliminates half
> the search. Then count queries: if one page issues more than about five, I stop there, because it's
> an N+1 and nothing else matters yet. Fix the loading strategy, then lock it in with
> `assertNumQueries`. Then fetch less — `values()` for reports, `iterator()` for scans, since model
> instantiation is a real cost. Then index what I filter and sort on, verified with `explain` rather
> than intuition. *Then* cache, and only at the low level. The reason the order matters is that steps
> two and three are free and usually worth ten times, whereas caching is where people start — and
> caching a slow query means you now have a slow query *and* a staleness bug.

**Q: What's wrong with `@cache_page` on a dashboard?**

> It keys on the URL plus whatever's in `Vary`, not on the user. So Alice loads `/dashboard/`, it
> goes in the cache, and Bob loads `/dashboard/` and gets Alice's orders — for sixty seconds, with no
> error anywhere. It's the shared-cache leak from HTTP caching, except now it's inside my own
> application. Three responses: never per-view-cache an authenticated view, which is the blanket rule
> and costs almost nothing since authenticated pages are the personalised ones; `vary_on_cookie`,
> which is correct and collapses the hit rate to roughly zero so you've paid for a cache that does
> nothing; or the low-level cache with the user or tenant in the key, which is what I'd actually do,
> because it caches the expensive *part* rather than the whole response. And any per-user response
> gets `Cache-Control: private, no-store` whether I cache it or not, because otherwise a CDN or a
> corporate proxy will cache it for me and I won't find out from my own logs.

**Q: How do you decide what to index?**

> From the queries, not from the model. A query like `WHERE user = ? ORDER BY created_at DESC` wants
> one composite index on `(user, -created_at)`, not two separate single-column indexes — and the
> order matters: equality columns first, then the range or sort column. If I always filter on a state
> — say only unreleased holds — a partial index with a `condition` is much smaller and faster. Then I
> verify with `qs.explain(analyze=True)` rather than assuming, and if the row estimate is wildly
> wrong that's usually stale statistics rather than a missing index. And I'd remember the cost side:
> every index slows writes and takes disk, so I check `pg_stat_user_indexes` for indexes with zero
> scans, which on a mature project always finds some.

**Q: Which cache backend, and what's the operational risk?**

> Redis, with a socket timeout — because without one a hung Redis hangs every request and the thing
> protecting you becomes the outage. `LocMemCache` is development-only: it's per process, so four
> workers means four caches giving four different answers, which also silently invalidates any
> distributed reasoning, including DRF's throttling. The operational risk beyond that is eviction
> policy: if that Redis runs `allkeys-lru`, which is right for a cache, then it must not also hold
> sessions, rate-limit counters or the Celery broker — because under memory pressure Redis will
> silently evict sessions, logging everyone out, and evict queued jobs, deleting work with no error
> anywhere. Different durability requirements shouldn't share an eviction policy.

## 🎙️ Articulation drill

**Two minutes: "How do you make a Django page fast?"**

less, index, *then* cache. Say why caching is sixth with the line that lands — caching a slow query
means you have a slow query and a staleness bug. Then cover the four cache levels and spend your time
on the hazard: `cache_page` keys on the URL, so Bob gets Alice's dashboard, which is the HTTP
shared-cache leak inside your own app. Give the three responses and pick one. Mention the operational
side — Redis with a socket timeout, and never sharing an LRU instance with sessions or the broker.

page doing four indexed queries doesn't need a cache at any realistic scale.**
