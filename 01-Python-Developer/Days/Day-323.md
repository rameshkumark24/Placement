# Day 323 🧮

**P-323** · 🧮 **Back-of-the-envelope estimation** — ⭐⭐ the numbers that decide the architecture

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: estimation is not a maths test, it is how you find the one number that
> makes a whole branch of the design impossible — and the only estimates worth doing are the ones
> whose answer changes what you build.**

---

# Part 1 — ⭐⭐ Why this day exists

```
⭐⭐ THE FAILURE MODE IT PREVENTS:
⭐   ⭐ Candidate designs a beautiful sharded, replicated,
⭐     Kafka-backed system. ⭐⭐ THE ACTUAL LOAD IS 40 REQUESTS
⭐     PER SECOND AND 300 GB. ⭐ One Postgres box would do it.
⭐   ⭐ Or the reverse: candidate says "we'll just store it in
⭐     Postgres" and the number is ⭐⭐ 4 PETABYTES A YEAR.

⭐⭐ SO THE PURPOSE IS NOT PRECISION. IT IS ***ELIMINATION***.
⭐   ⇒ ⭐⭐ AN ESTIMATE IS USEFUL EXACTLY WHEN IT RULES SOMETHING
⭐     OUT. If both answers lead to the same design, ⭐ SKIP THE
⭐     ARITHMETIC AND SAY SO — that is a senior move, not a lazy
⭐     one: *"I don't need to size this; at any plausible number
⭐     it fits on one node."*

⭐⭐ AND THE TOLERANCE: ***RIGHT TO WITHIN 10×.*** Nobody cares
⭐   if it is 40 TB or 60 TB. Everybody cares if it is 40 TB or
⭐   40 PB, because those are different companies.
```

# Part 2 — ⭐⭐ The numbers you memorise — and only these

```
⭐⭐ TIME (Jeff Dean's latency numbers, rounded to what you can
⭐   actually recall under pressure):
⭐   ⭐ L1 cache reference               ~1 ns
⭐   ⭐ Main memory reference            ~100 ns
⭐   ⭐ ***Python dict lookup***         ~50–100 ns
⭐   ⭐ Compress 1 KB                    ~1–10 µs
⭐   ⭐ SSD random read                  ~100 µs   (0.1 ms)
⭐   ⭐ Read 1 MB sequentially from SSD  ~200 µs
⭐   ⭐ ***Round trip within a datacentre  ~0.5 ms***
⭐   ⭐ Disk (spinning) seek             ~10 ms
⭐   ⭐ ***Round trip CA ⇄ Netherlands  ~150 ms***

⭐⭐ THE THREE THAT ACTUALLY DECIDE DESIGNS:
⭐   ① ⭐⭐ MEMORY IS ~1000× FASTER THAN SSD, SSD ~100× FASTER
⭐        THAN A SPINNING SEEK.
⭐   ② ⭐⭐ A DATACENTRE ROUND TRIP IS 0.5 ms — ⭐ SO 200 OF THEM
⭐        IS 100 ms, ⭐⭐ WHICH IS WHY N+1 IS A LATENCY BUG BEFORE
⭐        IT IS A DATABASE BUG (Day 197, Day 266).
⭐   ③ ⭐⭐ CROSS-CONTINENT IS 150 ms AND ***NO ENGINEERING FIXES
⭐        THE SPEED OF LIGHT.*** You can only move the data
⭐        closer (Day 327) or stop needing the round trip.
```

```
⭐⭐ SIZE — THE POWERS OF TWO, IN DECIMAL:
⭐   2^10 = thousand (KB)   2^20 = million (MB)
⭐   2^30 = billion (GB)    2^40 = trillion (TB)   2^50 = PB

⭐⭐ TYPICAL ROW / OBJECT SIZES — USE THESE, STATE THEM ALOUD:
⭐   ⭐ UUID 16 B · int8 8 B · timestamp 8 B
⭐   ⭐ A "normal" relational row with 10 columns  ⇒ ***~200 B***
⭐   ⭐ Plus indexes, bloat, alignment ⇒ ⭐⭐ MULTIPLY BY 2–3.
⭐   ⭐ A tweet-sized text            ⇒ ~300 B
⭐   ⭐ A JSON event with context     ⇒ ~1 KB
⭐   ⭐ A thumbnail                   ⇒ ~20 KB
⭐   ⭐ A photo                       ⇒ ~2 MB
⭐   ⭐ A minute of 1080p video       ⇒ ~50 MB

⭐⭐ TIME UNITS YOU WILL NEED EVERY SINGLE TIME:
⭐   ⭐ ***1 day ≈ 86,400 s ≈ 10^5 s***   (round it, always)
⭐   ⭐ 1 month ≈ 2.5 × 10^6 s
⭐   ⭐ 1 year  ≈ 3 × 10^7 s
⭐   ⇒ ⭐⭐ "1 MILLION EVENTS/DAY" = ***~12 PER SECOND***. Say
⭐     that instantly and the room relaxes.
```

# Part 3 — ⭐⭐ The method, in five steps

```
⭐⭐ ① ROUND EVERYTHING TO ONE SIGNIFICANT FIGURE, IMMEDIATELY.
⭐      "347 million users" ⇒ 300 million. ⭐ Do it out loud so
⭐      the interviewer knows it is deliberate.
⭐   ② ⭐⭐ WORK IN POWERS OF TEN. Track the exponent; the
⭐      mantissa is noise.
⭐   ③ ⭐ CONVERT DAILY TO PER-SECOND EARLY (÷ 10^5).
⭐   ④ ⭐⭐ APPLY A PEAK FACTOR AND SAY THE NUMBER. Peak/average
⭐      is ***2–3× for a global product, 5–10× for a regional
⭐      one, and 1000× for a flash sale*** (Day 356).
⭐      ⇒ ⭐⭐ FORGETTING PEAK IS THE MOST COMMON ESTIMATION
⭐        ERROR IN INTERVIEWS, AND IT IS THE ONE THAT TAKES
⭐        REAL SYSTEMS DOWN.
⭐   ⑤ ⭐ STATE THE ASSUMPTION THAT DOMINATES THE ANSWER, AND
⭐      HOW WRONG IT COULD BE.
```

```
⭐⭐ THE FIVE QUANTITIES WORTH COMPUTING, IN THIS ORDER:
⭐   ① ⭐⭐ QPS — reads and writes ***separately***.
⭐        ⇒ ⭐ The read:write ratio is the most design-relevant
⭐          number in the whole exercise. 100:1 means cache
⭐          and replicas. 1:1 means you have a write problem.
⭐   ② ⭐ STORAGE — per day, and at 5 years.
⭐   ③ ⭐ BANDWIDTH — bytes/s in and out. ⭐⭐ EGRESS IS THE BILL
⭐        (Day 353).
⭐   ④ ⭐ MEMORY — what fraction of the working set fits in RAM?
⭐   ⑤ ⭐⭐ MACHINES — the sanity check that catches everything
⭐        else: "that's 4 servers" vs "that's 40,000 servers".
```

# Part 4 — ⭐⭐ Worked example: the URL shortener (previewing Day 345)

```
⭐⭐ GIVEN: 100 million new URLs/day. Read:write = 100:1.
⭐   Store for 10 years.

⭐⭐ WRITES: 10^8 / 10^5 s = ***1,000 writes/s***.
⭐   ⭐ Peak ×3 ⇒ ***3,000 writes/s***.

⭐⭐ READS: 100 × 1,000 = ***100,000 reads/s***; peak 300,000/s.
⭐   ⇒ ⭐⭐ THIS SINGLE RATIO DECIDES THE ARCHITECTURE: the read
⭐     path must be a cache, and the write path can be boring.

⭐⭐ STORAGE: 500 B/record × 10^8/day = 50 GB/day
⭐   ⇒ × 365 × 10 = ⭐ 180 TB over ten years.
⭐   ⇒ ⭐⭐ 180 TB DOES NOT FIT ON ONE NODE COMFORTABLY ⇒
⭐     ***SHARDING IS REQUIRED, AND NOW I CAN SAY WHY.***

⭐⭐ MEMORY FOR THE CACHE: 20% of reads hit 80% of traffic.
⭐   ⭐ Cache the hot day: 10^8 × 0.2 × 500 B = ***10 GB***.
⭐   ⇒ ⭐⭐ 10 GB FITS IN ONE REDIS NODE. ⭐ That is a $200/month
⭐     answer to a 300,000 reads/s problem, ⭐⭐ AND SAYING SO
⭐     IS THE MOMENT THE INTERVIEW TURNS.

⭐⭐ BANDWIDTH: 300,000 reads/s × 500 B = 150 MB/s = 1.2 Gbps.
⭐   ⇒ ⭐ Fine. One 10 Gb NIC, or a CDN in front.
```

```
⭐⭐ WHAT THOSE SIX LINES BOUGHT:
⭐   ⭐ "Sharded storage"  — justified by 180 TB.
⭐   ⭐ "Cache in front"   — justified by 100:1.
⭐   ⭐ "One Redis node"   — justified by 10 GB.
⭐   ⇒ ⭐⭐ EVERY BOX ON THE DIAGRAM NOW HAS A NUMBER ATTACHED,
⭐     WHICH IS THE DIFFERENCE BETWEEN A DESIGN AND A DRAWING.
```

# Part 5 — ⭐ A second worked example, where the answer is "don't"

```
⭐⭐ GIVEN: an internal HR tool. 5,000 employees. Each loads
⭐   ~20 pages a day.

⭐⭐ QPS: 5,000 × 20 = 10^5 requests/day = ***1 req/s***.
⭐   ⭐ Peak ×10 (everyone at 9 a.m.) ⇒ ***10 req/s***.
⭐⭐ STORAGE: 5,000 employees × 50 KB of records = ***250 MB***.

⭐⭐ CONCLUSION, STATED PLAINLY:
⭐   ***ONE APPLICATION SERVER, ONE POSTGRES, DAILY BACKUPS.
⭐      NO CACHE, NO QUEUE, NO SHARDING, NO KUBERNETES.***
⭐   ⇒ ⭐⭐ THE ESTIMATE'S ENTIRE VALUE WAS TO LET YOU SAY "NO"
⭐     WITH A NUMBER BEHIND IT — ⭐ which is Day 286's
⭐     smallest-infrastructure rule, arrived at arithmetically.
⭐   ⇒ ⭐⭐ INTERVIEWERS PLANT THESE. A candidate who shards a
⭐     250 MB database has failed a judgement test, not a
⭐     knowledge test.
```

# Part 6 — ⭐⭐ The Python-specific numbers you should also know

```
⭐⭐ BECAUSE YOU WILL BE ASKED "CAN PYTHON DO THIS?":
⭐   ⭐ A FastAPI async handler doing one DB query:
⭐     ⭐ ~2,000–5,000 req/s per core for trivial work
⭐     ⭐ ~500–1,500 req/s per core realistically (auth, ORM,
⭐        serialisation, validation)
⭐   ⭐ A gunicorn ***sync*** worker = ⭐⭐ ONE CONCURRENT REQUEST.
⭐     ⭐ Concurrency = workers. Day 322's L is your worker count.
⭐   ⭐ A uvicorn ***async*** worker = thousands of concurrent
⭐     ***waiting*** requests, ⭐⭐ BUT STILL ONE CPU'S WORTH OF
⭐     WORK (the GIL, Day 065).
⭐   ⇒ ⭐⭐ SO: I/O-BOUND ⇒ ASYNC SCALES BEAUTIFULLY.
⭐     ⭐⭐ CPU-BOUND ⇒ ASYNC BUYS YOU NOTHING; you need
⭐       processes, and past that, another language for that
⭐       one component. ⭐ Say the second half out loud —
⭐       ⭐⭐ ADMITTING WHERE PYTHON STOPS IS WHAT MAKES THE
⭐       FIRST HALF CREDIBLE.

⭐⭐ TWO MORE, FOR THE SAME REASON:
⭐   ⭐ `json.dumps` of a 1 KB dict ⇒ ~5–10 µs. At 10,000 rps
⭐     that is 5–10% of a core — ⭐ visible, not fatal, and
⭐     `orjson` removes most of it.
⭐   ⭐ Pydantic v2 validation of a 20-field model ⇒ ~2–5 µs.
⭐     ⭐⭐ v1 WAS 10–20× SLOWER, which is why the rewrite
⭐       mattered and why "Pydantic is slow" is stale advice.
```

# Part 7 — ⭐ Saying it out loud without losing the room

```
⭐⭐ THE SCRIPT:
⭐   ⭐ "Let me size this before I draw anything — two minutes."
⭐   ⭐ "A hundred million a day is about a thousand a second,
⭐      call it three thousand at peak."
⭐   ⭐ "Five hundred bytes a record gives fifty gigs a day,
⭐      which is a hundred and eighty terabytes over ten years —
⭐      ⭐⭐ so this is sharded, and that's why."
⭐   ⭐ "The read:write ratio is a hundred to one, ⭐⭐ so the
⭐      read path is a cache and the write path can be dull."
⭐   ⭐ "If the ratio is actually ten to one, ⭐ the cache still
⭐      helps but I'd size the primary differently."

⭐⭐ THREE RULES FOR THE DELIVERY:
⭐   ① ⭐ WRITE THE NUMBERS WHERE THEY CAN BE SEEN. You will
⭐        refer back to them at minute 35.
⭐   ② ⭐⭐ NEVER SILENTLY COMPUTE. A wrong number said aloud
⭐        gets corrected in five seconds; a wrong number in your
⭐        head poisons the next twenty minutes.
⭐   ③ ⭐⭐ STOP AT THE FIRST NUMBER THAT DECIDES SOMETHING, AND
⭐        SAY WHAT IT DECIDED. Estimation with no conclusion is
⭐        just arithmetic performed at an interviewer.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Estimating without concluding | The number exists to rule something out. State what it ruled out or don't compute it |
| ⭐⭐ Forgetting the peak factor | Systems die at peak, not at average. 3× global, 10× regional, 1000× flash sale |
| ⭐ Carrying three significant figures | You are not more accurate for it, and you are slower and more error-prone |
| ⭐⭐ One QPS number for reads and writes | The read:write ratio is the single most design-relevant output |
| ⭐ Ignoring index and bloat overhead | Real storage is 2–3× the raw row size. Say the multiplier aloud |
| ⭐⭐ Sharding a 250 MB database | A judgement failure. The estimate existed to prevent exactly this |
| ⭐ Forgetting `1 day ≈ 10^5 s` | You will do this conversion six times per interview |
| ⭐ Claiming Python does 50k rps/core | It does not. Overclaiming once costs you the whole round's credibility |
| ⭐⭐ Computing silently | A number in your head that's wrong compounds for twenty minutes |
| ⭐ Sizing storage but never memory | "Does the hot set fit in RAM?" is often the cheapest answer available |

## Interview questions

**1. "Estimate the storage for Twitter's tweets for five years."**
> ⭐ 500 M tweets/day, ~300 B of text plus ~200 B metadata ⇒ 250 GB/day of text. ⭐ Index and
> replication ×3 ⇒ ~750 GB/day ⇒ ~1.4 PB over five years — ⭐⭐ and the important line: *media is a
> different order of magnitude entirely and belongs in object storage, not the database.* ⭐ 10% of
> tweets with a 2 MB image is 100 TB/day, ⭐⭐ which is 200× the text and decides the whole design.

**2. "How many servers for 100k requests/second in Python?"**
> ⭐ At a realistic 1,000 rps per core for a real handler, that's 100 cores; at 8 cores per box, ⭐ ~13
> machines at 100% — ⭐⭐ so ~30–40 with headroom for the utilisation curve and failure domains.
> ⭐ Then the honest follow-up: *if that number is uncomfortable, the fix isn't a different language,
> it's a cache, because at 100:1 reads most of those requests should never reach Python at all.*

**3. "One million events a day. How many per second?"**
> ⭐⭐ About twelve. ⭐ And I'd say immediately that twelve per second is a single-process problem —
> no queue, no Kafka, no partitioning — ⭐⭐ so the interesting question isn't throughput, it's what
> happens when the consumer is down for six hours, which is a backlog question, not a scale one.

**4. "When would you skip the estimation?"**
> ⭐⭐ When both plausible answers lead to the same design. ⭐ If it's clearly one node's worth of data
> at any believable number, I'll say *"I'm not sizing this, it fits"* and spend the minutes on the
> part that's actually hard. ⭐ Estimation is a filter, not a ritual.

**5. "Your estimate is off by 10×. Does it matter?"**
> ⭐ Usually no — that's the tolerance the method is designed for. ⭐⭐ It matters when 10× crosses an
> architectural boundary: fits-in-RAM to doesn't, one-node to sharded, one-region to multi-region.
> ⭐ So I name the boundary my number is nearest to, and say how much slack there is before I'd
> redesign.

**6. "Why do you separate reads from writes first?"**
> ⭐⭐ Because they scale by completely different mechanisms. Reads scale with caches, replicas and
> CDNs — all cheap and all eventually consistent. ⭐ Writes scale with sharding, which is expensive
> and changes your data model. ⭐⭐ A 100:1 ratio means the hard problem is small; a 1:1 ratio means
> the hard problem is the whole system.

## 🎙️ Articulation drill

**Two minutes.** Start with purpose, not method: **an estimate is worth doing only when its answer
rules something out** — if every plausible number leads to the same design, say so and move on, which
is a judgement call, not a shortcut. Then the tolerance: **right to within ten times**, one significant
figure, powers of ten, and everything said out loud so a wrong number gets corrected in five seconds
rather than poisoning twenty minutes. Give the three constants that actually decide things: **a day is
ten to the fifth seconds, a datacentre round trip is half a millisecond, and cross-continent is a
hundred and fifty and no engineering fixes the speed of light.** Then walk the shortener in six lines —
**a hundred million a day is a thousand a second, three at peak; five hundred bytes gives a hundred and
eighty terabytes over ten years, so this is sharded; and a hundred-to-one read ratio with a ten-gigabyte
hot set means one Redis node answers three hundred thousand reads a second.** Close on the peak factor,
because it's the one people skip and the one that takes systems down — **and on the discipline of
ending every number with the words "so this means", because arithmetic without a conclusion is just
arithmetic performed at an interviewer.**
