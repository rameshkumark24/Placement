# Part 1 — ⭐⭐ The graph, and what makes it different from Alembic

```bash
python manage.py makemigrations orders
python manage.py migrate
python manage.py showmigrations              # ⭐ what is applied, per app
python manage.py sqlmigrate orders 0007      # ⭐⭐ SHOW ME THE SQL — use this always
python manage.py migrate orders 0006         # ⭐ migrate backwards
```

```
⭐⭐ THE STRUCTURAL DIFFERENCES FROM ALEMBIC, AND THEY MATTER:

⭐  1. ⭐⭐ MIGRATIONS ARE **PER APP**, AND THE GRAPH SPANS APPS VIA
⭐       `dependencies = [("users", "0004_...")]`.
⭐       ⭐ Alembic has ONE linear chain; ⭐⭐ Django has a DIRECTED ACYCLIC
⭐       GRAPH across apps. ⭐ That is genuinely better for a modular
⭐       codebase — ⭐⭐ and it means "which migration runs first" is answered
⭐       by dependencies, not by filename or timestamp.
⭐  2. ⭐⭐ THE AUTODETECTOR READS YOUR **MODELS**, NOT THE DATABASE. Alembic
⭐       diffs models against a live schema; ⭐ Django diffs models against
⭐       the accumulated STATE of previous migrations.
⭐       ⇒ ⭐⭐ CONSEQUENCE: `makemigrations` NEEDS NO DATABASE CONNECTION, and
⭐         it is more accurate — it knows a `CharField` became a `TextField`,
⭐         which Alembic's type comparison often cannot.
⭐       ⇒ ⭐⭐ AND THE COST: THE MIGRATION FILES **ARE** THE SOURCE OF TRUTH
⭐         FOR STATE. ⭐ Delete them and Django believes the tables do not
⭐         exist. ⭐⭐ Hand-edit the database without a migration and Django
⭐         will never know — the divergence is permanent and silent.
⭐  3. ⭐⭐ DJANGO **ASKS YOU** ABOUT RENAMES: "Did you rename order.state to
⭐       order.status? [y/N]". ⭐ Alembic silently writes DROP + ADD (Day 138).
⭐       ⇒ ⭐⭐ THIS IS A REAL, MEANINGFUL SAFETY IMPROVEMENT — ⭐ and it only
⭐         works interactively. ⭐⭐ In CI with `--noinput` it answers NO, and
⭐         you get the data-destroying DROP + ADD after all.
⭐  4. ⭐ TWO BRANCHES CREATING `0008_*` gives you ⭐⭐ CONFLICTING MIGRATIONS.
⭐       ⭐ `makemigrations --merge` writes a merge node — ⭐ same shape as
⭐       `alembic merge`, and the same caveat: it rejoins the graph, ⭐⭐ it
⭐       does not reconcile two people who both added a `status` column.
```

# Part 2 — ⭐⭐ Reading what it actually does

```
⭐⭐ THE SINGLE MOST VALUABLE HABIT IN THIS DAY:
⭐        `python manage.py sqlmigrate orders 0007`
⭐   ⇒ ⭐ prints the exact SQL, without running it.
⭐   ⇒ ⭐⭐ RUN IT BEFORE EVERY MIGRATION THAT TOUCHES A POPULATED TABLE. ⭐ The
⭐        Python operation names hide enormous differences in cost.

⭐⭐ THE OPERATIONS THAT LOOK IDENTICAL AND ARE NOT (Day 138's table, in
⭐   Django's vocabulary):

⭐   `AddField(null=True)`               ⭐ metadata only. Instant. ✅
⭐   `AddField(default=X)`               ⭐ PG 11+: instant. ⭐⭐ PG ≤10: FULL
⭐                                          TABLE REWRITE.
⭐   `AddField(null=False, default=X)`   ⭐⭐ Django asks for a one-off default
⭐                                          and writes it as ADD + UPDATE +
⭐                                          ALTER — ⭐ THREE statements, one
⭐                                          of which scans the table.
⭐   `AlterField` CharField→TextField    ⭐⭐ on Postgres often instant;
⭐                                          ⭐ on MySQL a full rewrite. ⭐⭐ The
⭐                                          same migration file, wildly
⭐                                          different cost per backend.
⭐   `AddIndex`                          ⭐⭐ LOCKS WRITES for the build ⇒ see
⭐                                          Part 3
⭐   `AddConstraint` (FK / CHECK)        ⭐⭐ validates the whole table under
⭐                                          a lock
⭐   `RemoveField`                       ⭐ instant, ⭐⭐ and it breaks every
⭐                                          running query for that model
⭐                                          (Day 138)
⭐
⭐   ⇒ ⭐⭐ AND THE DJANGO-SPECIFIC LANDMINE: **`AlterField` ON A FIELD WITH
⭐        `db_index=True` OR `unique=True` CAN DROP AND RECREATE THE INDEX.**
⭐        ⭐ `sqlmigrate` shows it; the operation name does not.
```

```python
# ⭐⭐ SET A LOCK TIMEOUT — Day 138's fix, in Django form
class Migration(migrations.Migration):
    operations = [
        migrations.RunSQL("SET lock_timeout = '3s';", reverse_sql=migrations.RunSQL.noop),
        migrations.AddField(...),
    ]
    # ⇒ ⭐⭐ turns "one slow query queued ahead of us takes the site down for
    #      30 seconds" into "the deploy failed, retry it". ⭐ You want the
    #      Slack message, not the incident.
```

# Part 3 — ⭐⭐ Zero downtime: the same three releases

```
⭐⭐ THE PREMISE IS UNCHANGED FROM Day 138: DURING A ROLLING DEPLOY, OLD AND
⭐   NEW CODE RUN AGAINST THE SAME DATABASE. ⭐ So expand/contract still
⭐   applies, and Django adds one hazard of its own:

⭐   ⭐⭐ THE DJANGO-SPECIFIC ONE: THE ORM SELECTS **EVERY** CONCRETE FIELD ON
⭐        THE MODEL BY DEFAULT. ⭐ So the instant you `RemoveField`, any pod
⭐        still running the old code issues `SELECT ..., state, ...` and gets
⭐        ⭐⭐ "column does not exist" ON EVERY QUERY FOR THAT MODEL — not just
⭐        the ones that use the field. ⭐ One dropped column, and every
⭐        endpoint touching that table 500s.
⭐
⭐⭐ THE RENAME, DONE SAFELY — THREE RELEASES:
⭐   ⭐ R1 EXPAND:   `AddField status` (nullable) · backfill in batches ·
⭐        code writes BOTH, reads `state`
⭐   ⭐ R2 MIGRATE:  code reads `status`, still writes both ⭐ (rollback safe)
⭐   ⭐ R3 CONTRACT: code stops touching `state` · `RemoveField state`
⭐   ⇒ ⭐⭐ AND NOTE: DJANGO'S `RenameField` IS **ONE** OPERATION AND IS
⭐        THEREFORE **NOT** ZERO-DOWNTIME. ⭐ It is instant and correct for the
⭐        SCHEMA and immediately wrong for the code still running. ⭐⭐ The nice
⭐        rename detection is a data-safety feature, NOT a deployment one —
⭐        and conflating the two is the mistake this section exists to prevent.

⭐⭐ SEPARATING STATE FROM SCHEMA — the tool that makes multi-release changes
⭐   possible, and the one most people have never used:
⭐   ⭐ `SeparateDatabaseAndState` lets you tell Django "the model changed"
⭐        WITHOUT running DDL, or run DDL without changing model state.
⭐   ⇒ ⭐⭐ THIS IS HOW YOU DO A RENAME AS EXPAND/CONTRACT: add the new column
⭐        for real, then in a later release tell Django's state that the field
⭐        moved, with no DDL at all.
⭐   ⇒ ⭐ Also how you adopt a table that already exists, and how you make a
⭐        concurrent index (below) known to the autodetector.
```

```python
# ⭐⭐ CONCURRENT INDEX — Day 138's rule, and Django has it natively
class Migration(migrations.Migration):
    atomic = False                          # ⭐⭐ REQUIRED — CIC can't run in a txn
    operations = [
        migrations.AddIndexConcurrently(     # ⭐ django.contrib.postgres.operations
            model_name="order",
            index=models.Index(fields=["user", "created_at"], name="ix_order_user_created"),
        ),
    ]
```

```
⭐⭐ THREE THINGS ABOUT THAT:
⭐   ⭐ `atomic = False` is mandatory — ⭐⭐ Django wraps migrations in a
⭐        transaction and `CREATE INDEX CONCURRENTLY` cannot run inside one.
⭐   ⭐ ⭐⭐ A FAILED CONCURRENT BUILD LEAVES AN `INVALID` INDEX BEHIND, because
⭐        there was no transaction to roll back. ⭐ Your migration must
⭐        tolerate finding it on a rerun.
⭐   ⭐ ⭐⭐ WITH `atomic = False`, A MID-MIGRATION FAILURE LEAVES THE MIGRATION
⭐        HALF-APPLIED AND UNRECORDED. ⭐ Keep non-atomic migrations to ONE
⭐        operation each — that is the discipline that makes them recoverable.
```

# Part 4 — ⭐⭐ Data migrations, and the rule that breaks people

```python
def backfill(apps, schema_editor):
    Order = apps.get_model("orders", "Order")     # ⭐⭐ HISTORICAL model. NOT an import.
    while True:
        ids = list(Order.objects.filter(status_new__isnull=True)
                   .values_list("id", flat=True)[:5000])       # ⭐ batched
        if not ids:
            break
        Order.objects.filter(id__in=ids).update(status_new=F("status"))
        # ⭐⭐ each batch its own transaction ⇒ short locks, resumable

class Migration(migrations.Migration):
    atomic = False                                 # ⭐ so batches really commit
    operations = [migrations.RunPython(backfill, migrations.RunPython.noop)]
```

```
⭐⭐ `apps.get_model()` IS THE RULE, AND IT IS THE SAME LESSON AS Day 138 WITH
⭐   A BETTER MECHANISM:
⭐   ⭐ `from orders.models import Order` imports the model AS IT IS TODAY —
⭐        with three fields added by LATER migrations.
⭐   ⇒ ⭐⭐ RUN `migrate` ON A FRESH DATABASE AND THIS MIGRATION EXECUTES
⭐        AGAINST A SCHEMA THAT DOES NOT HAVE THOSE COLUMNS YET ⇒ CRASH.
⭐   ⇒ ⭐ THE SYMPTOM IS BRUTAL: a migration that "has always worked" fails
⭐        ONLY for new environments and new developers, ⭐⭐ months after it was
⭐        written, and the person debugging it did not write it.
⭐   ⇒ ⭐⭐ `apps.get_model()` GIVES YOU THE MODEL **AS IT WAS AT THAT POINT IN
⭐        THE GRAPH.** ⭐ This is genuinely nicer than Alembic's answer (hand-
⭐        written `sa.table()` stubs) — Django reconstructs it for you.
⭐
⭐⭐ AND WHAT THE HISTORICAL MODEL DOES **NOT** GIVE YOU — the second half of
⭐   the rule, and people miss it:
⭐   ⭐ ❌ custom managers (unless `use_in_migrations = True`)
⭐   ⭐ ❌ custom `save()`, ❌ signals, ❌ `@property`, ❌ model methods
⭐   ⇒ ⭐⭐ IT IS A PLAIN DATA SHELL. ⭐ If your backfill needs business logic,
⭐        COPY THE LOGIC INTO THE MIGRATION — ⭐⭐ do not import it, because
⭐        importing it re-creates exactly the version-skew bug you just fixed.
⭐        ⭐ Duplication is correct here; it is a snapshot, not a dependency.
```

```
⭐⭐ THREE MORE RULES FOR DATA MIGRATIONS:
⭐   ⭐ ALWAYS PROVIDE A REVERSE — `RunPython.noop` if it is genuinely
⭐        irreversible. ⭐⭐ Without one, `migrate` backwards is impossible for
⭐        everyone forever, including in development.
⭐   ⭐ ⭐⭐ FOR A BIG BACKFILL, PREFER A MANAGEMENT COMMAND OVER A MIGRATION.
⭐        ⭐ A four-hour migration blocks your deploy pipeline for four hours,
⭐        and a pipeline that cannot roll forward is an outage waiting for a
⭐        bug. ⭐⭐ Ship the schema change; run the backfill separately.
⭐   ⭐ MAKE IT RESUMABLE AND IDEMPOTENT (`WHERE ... IS NULL` above does
⭐        both). ⭐⭐ It will be interrupted.
```

# Part 5 — ⭐ Squashing, CI, and the operational rules

```
⭐⭐ SQUASHING — worth doing at ~200 migrations, and it has a real cost:
⭐   ⭐ `squashmigrations orders 0001 0187` ⇒ one replacement migration with a
⭐        `replaces = [...]` list, so both old and new deployments work.
⭐   ⭐ + a fresh `migrate` (⭐⭐ every CI run, every new developer) gets much
⭐        faster; ⭐ the graph becomes readable again.
⭐   ⭐ − ⭐⭐ `RunPython` OPERATIONS ARE NOT SQUASHED — they are carried
⭐        through, ⭐ and often need manual removal.
⭐   ⭐ − ⭐⭐ YOU MUST NOT DELETE THE OLD FILES UNTIL EVERY ENVIRONMENT HAS
⭐        PASSED THE SQUASH POINT. ⭐ Delete early and an old environment can
⭐        never migrate forward again.

⭐⭐ THE FOUR CI CHECKS — the first is the one that catches the real bug:
⭐  1. ⭐⭐ `makemigrations --check --dry-run` ⇒ FAILS IF A MODEL CHANGED
⭐       WITHOUT A MIGRATION. ⭐ This is Django's `alembic check` (Day 141) and
⭐       it is one line. ⭐⭐ It catches the most common team failure with
⭐       migrations, and most projects do not have it.
⭐  2. ⭐ `migrate` on an EMPTY database in CI ⇒ ⭐⭐ catches the
⭐       `apps.get_model` violation from Part 4, which only appears on fresh
⭐       databases.
⭐  3. ⭐ `migrate` then `migrate <app> zero` then `migrate` again ⇒ proves
⭐       reversibility, at least for schema.
⭐  4. ⭐ a linter (`django-migration-linter`) that flags unsafe operations —
⭐       ⭐⭐ `AddField(null=False)` on a big table, `RemoveField`, `AlterField`
⭐       type changes.

⭐⭐ AND THE OPERATIONAL RULES, UNCHANGED FROM Day 138:
⭐   ⭐ RUN MIGRATIONS AS A SEPARATE JOB, ⭐⭐ NEVER IN CONTAINER STARTUP —
⭐        ten replicas booting means ten concurrent `migrate`; ⭐ Django takes
⭐        an advisory lock so nine of them WAIT, and ⭐⭐ your readiness probe
⭐        times out during the wait and Kubernetes kills the pods mid-deploy.
⭐   ⭐ EXPAND BEFORE THE CODE DEPLOY, CONTRACT AFTER.
⭐   ⭐ ⭐⭐ `--fake` AND `--fake-initial` ARE FOOTGUNS. ⭐ They mark a migration
⭐        applied WITHOUT running it. ⭐⭐ Legitimate exactly twice: adopting an
⭐        existing database, and recovering from a manual fix. ⭐ Every other
⭐        use is you lying to Django, and Django will believe you forever.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Committing a generated migration unread | Run `sqlmigrate` — the operation name hides the cost. |
| `makemigrations --noinput` in CI | It answers "no" to the rename question and writes a data-destroying DROP + ADD. |
| Deleting migration files to "clean up" | They *are* the state. Django will believe the tables don't exist. |
| Hand-editing the database | The divergence from Django's state is permanent and silent. |
| Assuming `RenameField` is zero-downtime | It's instant and immediately wrong for the code still running. Expand/contract. |
| `RemoveField` before the code stops selecting it | Breaks *every* query for that model, not just ones using the field. |
| `AddIndex` on a large table | Locks writes for the build. Use `AddIndexConcurrently` with `atomic = False`. |
| Multiple operations in a non-atomic migration | A mid-way failure leaves it half-applied and unrecorded. |
| No `lock_timeout` | One slow query queued ahead turns an instant `ALTER` into an outage. |
| Importing models in a `RunPython` | It breaks months later, only on fresh databases, for someone who didn't write it. |
| Expecting custom `save()` or signals in a historical model | It's a plain data shell. Copy the logic in; don't import it. |
| No reverse on `RunPython` | Nobody can migrate backwards, ever, including locally. |
| A four-hour backfill inside a migration | Blocks the deploy pipeline. Ship the schema, run the backfill separately. |
| Deleting squashed migrations too early | An environment behind the squash point can never migrate forward. |
| No `makemigrations --check` in CI | The most common team failure ships — a model changed with no migration. |
| Migrations in container startup | Nine replicas wait on the advisory lock and fail their readiness probes. |
| `--fake` as a routine fix | You're lying to Django, and it will believe you forever. |

## Interview questions

**Q: How do Django migrations differ from Alembic?**

> Three real differences. Django's are per-app with cross-app dependencies, so the graph is a DAG
> rather than one linear chain — better for a modular codebase, and it means ordering comes from
> declared dependencies rather than filenames. The autodetector diffs your models against the
> accumulated state of previous migrations rather than against a live database, so `makemigrations`
> needs no connection and is more accurate about things like a `CharField` becoming a `TextField`.
> The cost of that is that the migration files *are* the source of truth for state — delete them and
> Django believes the tables don't exist, and hand-edit the database and Django will never know. And
> Django asks whether a rename is a rename, which is a genuine safety improvement over Alembic
> silently writing DROP plus ADD — except that it only works interactively, so `--noinput` in CI
> answers no and you get the destructive version anyway.

**Q: Is `RenameField` zero-downtime?**

> No, and this is the trap the nice rename detection creates. It's a single instant operation and
> it's correct for the schema, but it's immediately *wrong* for the code still running — during a
> rolling deploy the old pods are still selecting the old column name. Rename detection is a
> data-safety feature, not a deployment feature, and conflating them is the mistake. Zero-downtime
> renames are still three releases: add the new column and dual-write, switch reads, then remove the
> old one. What makes it worse in Django specifically is that the ORM selects every concrete field on
> the model by default, so the moment you `RemoveField`, old pods get "column does not exist" on
> *every* query for that model, not just ones touching the field. The tool that makes the multi-step
> version clean is `SeparateDatabaseAndState`, which lets you change model state without DDL or run
> DDL without changing state.

**Q: What's the rule for data migrations?**

> `apps.get_model()`, never a direct import. A direct import gets the model as it is *today*, with
> fields added by later migrations, so running `migrate` on a fresh database executes this old
> migration against a schema that doesn't have those columns yet and it crashes. The symptom is
> nasty: a migration that has always worked fails only for new environments and new developers,
> months later, and whoever debugs it didn't write it. `apps.get_model` reconstructs the model as it
> was at that point in the graph, which is genuinely nicer than Alembic's hand-written table stubs.
> The half people miss is that a historical model has no custom manager, no custom `save()`, no
> signals and no methods — it's a plain data shell. So if the backfill needs business logic, copy it
> into the migration rather than importing it, because importing recreates the exact version-skew bug
> you were avoiding. And batch it, make it resumable, and for anything large prefer a management
> command so a four-hour backfill isn't blocking the deploy pipeline.

**Q: What would you put in CI for migrations?**

> Four things. `makemigrations --check --dry-run`, which fails if a model changed without a
> migration — that's one line and it catches the most common team failure, and most projects don't
> have it. `migrate` on an empty database, which is what catches the `apps.get_model` violation,
> since that only ever fails on fresh databases. Migrating forward, back to zero, and forward again,
> to prove reversibility for schema at least. And a migration linter that flags unsafe operations
> like a non-nullable `AddField` on a big table. Operationally, migrations run as a separate job that
> must succeed before the code rolls out — never in container startup, because ten replicas booting
> means ten concurrent `migrate`, Django's advisory lock makes nine of them wait, and their readiness
> probes time out while they wait, so Kubernetes kills pods mid-deploy.

## 🎙️ Articulation drill

**Two minutes: "How do you ship a schema change safely in Django?"**

Open with the premise, because everything follows from it: during a rolling deploy, old and new code
share one database. Then say the Django-specific sharpener — the ORM selects every concrete field, so
dropping a column breaks every query for that model rather than only the ones using it. Walk the
three releases. Give credit where it's due: Django asks about renames, which Alembic doesn't — then
immediately name the two limits, that it only works interactively and that a rename being safe for
*data* doesn't make it safe for *deployment*. Cover `apps.get_model` with the failure story, since
that's the one that bites six months later. Close on the two operational lines that show experience:
**`makemigrations --check` in CI, and migrations as a job rather than at container startup, because
ten replicas racing the advisory lock fail their readiness probes.**
