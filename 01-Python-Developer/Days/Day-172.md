# Part 1 — ⭐⭐ Autocommit, `atomic`, and where the boundary belongs

```
⭐⭐ THE DEFAULT NOBODY TELLS YOU: **DJANGO IS IN AUTOCOMMIT MODE.**
⭐   ⭐ `order.save()` ⇒ BEGIN, UPDATE, COMMIT. Immediately.
⭐   ⇒ ⭐⭐ SO THIS IS **NOT ATOMIC**, AND IT READS AS IF IT IS:
⭐        order.status = "paid";  order.save()          # ⭐ committed
⭐        ticket.issue();         ticket.save()         # ⭐⭐ raises
⭐        ⇒ ⭐ ORDER IS PAID. NO TICKET EXISTS. ⭐⭐ Money taken, nothing
⭐          delivered — the exact state Day 166 called the worst one.

⭐⭐ `transaction.atomic` IS THE FIX, AND IT HAS THREE FORMS:
⭐   ⭐ decorator on a view or service function     ⭐⭐ ← prefer this
⭐   ⭐ `with transaction.atomic():` block
⭐   ⭐ `ATOMIC_REQUESTS = True` in settings — ⭐⭐ WRAPS EVERY REQUEST.
⭐        ⭐ + impossible to forget; ⭐⭐ − holds a transaction open for the
⭐        WHOLE request INCLUDING any HTTP call in it (Day 135's rule broken
⭐        globally), and a slow view now holds a connection AND a transaction.
⭐        ⇒ ⭐ Reasonable for a small CRUD app; ⭐⭐ wrong for anything that
⭐          calls a third party.

⭐⭐ WHERE THE BOUNDARY BELONGS — the same answer as Day 139:
⭐   ⭐ ❌ NOT per-`save()`     ⇒ nothing is atomic
⭐   ⭐ ❌ NOT the whole request ⇒ locks held across I/O
⭐   ⭐ ✅ ⭐⭐ THE SERVICE FUNCTION — it is the thing that knows what "the
⭐        operation" means, and it is where the rollback is meaningful.
```

```
⭐⭐ NESTED `atomic` IS A SAVEPOINT, NOT A TRANSACTION — and this produces the
⭐   single most confusing Django error:
⭐   ⭐ inner `atomic` block raises and is CAUGHT by you ⇒ ⭐ savepoint rolls
⭐        back, outer continues. ⭐⭐ Correct and useful.
⭐   ⭐ BUT: ⭐⭐ IF A **DATABASE** ERROR ESCAPES AN INNER BLOCK AND YOU CATCH
⭐        IT WITHOUT AN INNER `atomic`, THE WHOLE TRANSACTION IS POISONED:
⭐          try:  Thing.objects.create(...)      # ⭐ IntegrityError
⭐          except IntegrityError: pass          # ⭐⭐ "handled"
⭐          Other.objects.create(...)            # ⭐⭐ TransactionManagementError
⭐        ⇒ ⭐ Postgres marks the transaction as ABORTED; ⭐⭐ every subsequent
⭐          statement fails until rollback.
⭐   ⇒ ⭐⭐ RULE: **CATCHING A DATABASE ERROR REQUIRES ITS OWN `atomic` BLOCK.**
⭐        ⭐ That one rule prevents an entire genre of bug report.
```

```python
# ⭐⭐ `on_commit` — Day 142's dual-write fix, built in and correct
@transaction.atomic
def place_order(user, hold_id, idem_key):
    order = _create_order(...)
    transaction.on_commit(lambda: send_confirmation.delay(order.id))   # ⭐⭐ AFTER commit
    return order
```

```
⭐⭐ WHY `on_commit` MATTERS MORE THAN IT LOOKS (Day 142):
⭐   ⭐ `send_confirmation.delay(order.id)` INSIDE the transaction ⇒ ⭐⭐ the
⭐        worker is fast and reads the id BEFORE your commit ⇒ `DoesNotExist`.
⭐        ⭐ It "works" after a retry, so it hides as intermittent noise —
⭐        ⭐⭐ and one day the transaction rolls back and you have emailed a
⭐        customer about an order that does not exist.
⭐   ⇒ ⭐ `on_commit` runs only if the transaction commits. ⭐⭐ Still not an
⭐        outbox — a crash between commit and enqueue still loses it — but it
⭐        is the correct floor, and it is one line.
⭐   ⚠ ⭐ In tests, `on_commit` callbacks do NOT run under `TestCase` (which
⭐        wraps each test in a rolled-back transaction). ⭐⭐ Use
⭐        `captureOnCommitCallbacks()` or `TransactionTestCase`, or your
⭐        emails are silently untested.
```

# Part 2 — ⭐⭐ `F()`: doing arithmetic in the database

```python
# ⭐⭐ RACE. Two requests read 5, both write 6. One sale vanishes.
tt = TicketType.objects.get(pk=1)
tt.quantity_sold += 1                      # ⭐ read-modify-write in PYTHON
tt.save()

# ⭐⭐ NO RACE. The database does the arithmetic.
TicketType.objects.filter(pk=1).update(quantity_sold=F("quantity_sold") + 1)
#  ⇒ UPDATE ... SET quantity_sold = quantity_sold + 1 WHERE id = 1
```

```
⭐⭐ `F()` REFERENCES A COLUMN **ON THE SERVER**. THREE CONSEQUENCES:
⭐  1. ⭐⭐ NO LOST UPDATE — the read and the write are one statement, so
⭐       there is nothing to interleave. ⭐ Day 067's race, removed by
⭐       construction rather than by locking.
⭐  2. ⭐ ONE QUERY INSTEAD OF TWO (no SELECT needed).
⭐  3. ⭐⭐ AND THE CONDITIONAL FORM IS THE OVERSELL FIX FROM Day 164, IN
⭐       DJANGO:
⭐          updated = (TicketType.objects
⭐                     .filter(pk=1, quantity_sold__lt=F("quantity_total"))
⭐                     .update(quantity_sold=F("quantity_sold") + 1))
⭐          if updated == 0: raise SoldOut()
⭐       ⇒ ⭐⭐ ATOMIC CHECK-AND-SET IN ONE STATEMENT, NO LOCK REQUIRED.

⭐⭐ THE TWO GOTCHAS:
⭐   ⭐ AFTER `save()` WITH AN `F()`, THE PYTHON ATTRIBUTE HOLDS A
⭐        `CombinedExpression`, NOT A NUMBER — ⭐⭐ printing it gives you an
⭐        object, and using it in arithmetic compounds the expression.
⭐        ⭐ Call `obj.refresh_from_db()` if you need the value.
⭐   ⭐ ⭐⭐ `.update()` DOES NOT CALL `save()`, DOES NOT FIRE SIGNALS, AND
⭐        DOES NOT UPDATE `auto_now` FIELDS. ⭐ Your `updated_at` silently
⭐        stops changing — which is Part 4's theme.
```

# Part 3 — ⭐⭐ `select_for_update`, and the Django-specific traps

```python
@transaction.atomic                                   # ⭐⭐ REQUIRED — see below
def create_hold(user, ticket_type_id, qty):
    tt = (TicketType.objects
          .select_for_update()                        # ⭐ row lock until commit
          .get(pk=ticket_type_id))
    if available(tt) < qty:
        raise SoldOut()
    Hold.objects.create(...)                          # ⭐ lock released at commit
```

```
⭐⭐ FOUR TRAPS, AND THE FIRST ONE IS SILENT:
⭐  1. ⭐⭐ `select_for_update()` OUTSIDE `atomic` RAISES
⭐       `TransactionManagementError` on Postgres — ⭐ good. ⭐⭐ BUT ON MYSQL
⭐       IN AUTOCOMMIT IT SIMPLY LOCKS AND IMMEDIATELY RELEASES, so you get
⭐       NO ERROR AND NO LOCK. ⭐ A test suite on SQLite tells you nothing
⭐       either — ⭐⭐ SQLite ignores it entirely.
⭐       ⇒ ⭐ THIS IS WHY DAY 139 SAID: TEST ON THE DATABASE YOU DEPLOY ON.
⭐  2. ⭐⭐ IT IS LAZY LIKE EVERYTHING ELSE. `qs = ...select_for_update()`
⭐       LOCKS NOTHING until evaluated. ⭐ The lock happens at `get()` /
⭐       iteration, not at the line that reads like it locks.
⭐  3. ⭐ `select_for_update(nowait=True)` raises instead of waiting;
⭐       `skip_locked=True` skips locked rows — ⭐⭐ which is exactly Day 166's
⭐       relay pattern, and Django has it natively:
⭐          Outbox.objects.filter(published_at=None).select_for_update(skip_locked=True)[:100]
⭐  4. ⭐⭐ `select_for_update()` WITH `select_related()` LOCKS THE JOINED
⭐       ROWS TOO. ⭐ You wanted one row and locked the user table as well.
⭐       ⭐⭐ Use `of=("self",)` to lock only the primary table — ⭐ an
⭐       unexpectedly common source of contention.

⭐⭐ AND THE RULE FROM Day 164 STILL APPLIES, LOUDER: **NO I/O INSIDE THE
⭐   LOCKED BLOCK.** ⭐ With `ATOMIC_REQUESTS = True` this is easy to violate
⭐   without noticing, because the transaction boundary is invisible in the
⭐   code — ⭐⭐ it is in your settings file.
```

```
⭐⭐ ISOLATION LEVELS, BRIEFLY, BECAUSE IT IS ASKED:
⭐   ⭐ Postgres default: READ COMMITTED. ⭐⭐ Each STATEMENT sees a fresh
⭐        snapshot — so two reads in one transaction can disagree.
⭐   ⭐ `select_for_update` gives you back the guarantee you need for
⭐        read-then-write, ⭐⭐ or use the conditional `F()` update and need no
⭐        lock at all.
⭐   ⭐ SERIALIZABLE is available and correct, ⭐⭐ and it means your code MUST
⭐        handle serialisation failures with a retry loop. ⭐ Most teams choose
⭐        explicit locking over that; know that both are legitimate.
```

# Part 4 — ⭐⭐ Bulk operations: fast, and they skip everything

```python
Order.objects.bulk_create(orders, batch_size=1000)         # ⭐ 1 query per batch
Order.objects.bulk_update(orders, ["status"], batch_size=1000)
Order.objects.filter(status="pending").update(status="cancelled")   # ⭐ 1 query
Order.objects.filter(created__lt=cutoff).delete()          # ⭐⭐ NOT one query — see below
```

```
⭐⭐ THE TABLE THAT PREVENTS A WHOLE GENRE OF SILENT BUG:

⭐   OPERATION            save()?  signals?  auto_now?  validation?  cascades?
⭐   ─────────────────────────────────────────────────────────────────────────
⭐   `obj.save()`           ✅       ✅        ✅         ❌ (never)     n/a
⭐   `bulk_create`          ❌       ❌        ⭐ partial   ❌           n/a
⭐   `bulk_update`          ❌       ❌        ❌         ❌           n/a
⭐   `queryset.update()`    ❌       ❌        ❌         ❌           n/a
⭐   `queryset.delete()`    ❌   ⭐ YES (per obj) n/a      n/a       ⭐⭐ YES
⭐
⭐   ⇒ ⭐⭐ THE BUG: BUSINESS LOGIC IN `save()` OR IN A SIGNAL (Day 170) IS
⭐        **SILENTLY SKIPPED** THE DAY SOMEONE REPLACES A LOOP WITH
⭐        `bulk_create`. ⭐ No error. No log. ⭐⭐ The PR looks like a pure
⭐        performance improvement, and it changes behaviour.
⭐   ⇒ ⭐ THAT IS THE STRONGEST ARGUMENT FOR Day 170's RULE: put business
⭐        logic in explicit service functions, never in `save()` or a signal.
⭐
⭐⭐ AND `delete()` IS THE INVERSE SURPRISE — it is NOT one query:
⭐   ⭐ Django FETCHES the rows to run cascades and send signals ⇒ ⭐⭐ deleting
⭐        1M rows loads 1M objects into memory and can OOM you.
⭐   ⇒ ⭐ Batch it, or use `_raw_delete()` when you are certain there are no
⭐        cascades or signals — ⭐⭐ and note that `on_delete=models.CASCADE` is
⭐        enforced BY DJANGO IN PYTHON, not by the database, unless you also
⭐        have a DB-level constraint. ⭐ `DB_CASCADE` is not the default.
```

```
⭐⭐ AND THE ONE THAT SURPRISES EVERYONE: **`Model.save()` DOES NOT VALIDATE.**
⭐   ⭐ `full_clean()` runs validators; `save()` does not call it.
⭐   ⇒ ⭐⭐ `max_length=10` IS NOT ENFORCED BY `save()` — ⭐ it is enforced by
⭐        the database column, if the backend bothers (⭐⭐ MySQL may truncate,
⭐        SQLite ignores it entirely).
⭐   ⇒ ⭐ Validation lives in FORMS and DRF SERIALIZERS (Day 175), which is a
⭐        deliberate design choice and a genuine gap: ⭐⭐ anything writing
⭐        directly to the model — a management command, a migration, a
⭐        signal — bypasses every validator you wrote.
⭐   ⇒ ⭐⭐ SO PUT REAL INVARIANTS IN THE DATABASE: `CheckConstraint`,
⭐        `UniqueConstraint` in `Meta.constraints`. ⭐ Day 162's rule again —
⭐        put the guarantee where a bug cannot reach it.
```

# Part 5 — ⭐ Aggregation, and the escape hatches

```python
# ⭐ annotate = per-row; aggregate = one number for the whole queryset
Event.objects.annotate(sold=Count("tickets")).filter(sold__gt=100)
Order.objects.filter(status="paid").aggregate(total=Sum("total_cents"))

# ⭐⭐ THE CLASSIC BUG: TWO ANNOTATIONS OVER DIFFERENT MULTI-VALUED RELATIONS
Event.objects.annotate(n_tickets=Count("tickets"), n_orders=Count("orders"))
#  ⇒ ⭐⭐ BOTH NUMBERS ARE WRONG — the joins multiply, so each count is
#     inflated by the other's cardinality. ⭐ It returns numbers, so nobody
#     notices. ⭐⭐ FIX: `Count("tickets", distinct=True)`, or subqueries.
```

```
⭐⭐ THE ESCAPE HATCHES, IN ORDER OF WHEN TO REACH FOR THEM:
⭐  1. ⭐ `annotate` + `Subquery`/`OuterRef` — ⭐⭐ solves most "I need a
⭐       correlated value" cases without leaving the ORM.
⭐  2. ⭐ `.extra()` — ⭐⭐ deprecated. Do not.
⭐  3. ⭐ `Model.objects.raw("SELECT ...")` — returns model instances.
⭐       ⭐⭐ Parameterise: `raw("... WHERE id = %s", [uid])`. ⭐ String
⭐       formatting here is SQL injection (Day 127), and the ORM's protection
⭐       ends the moment you leave it.
⭐  4. ⭐⭐ `connection.cursor()` — full SQL. ⭐ For reports and bulk DDL this
⭐       is the right tool, ⭐⭐ and you own the parameterisation and the
⭐       tenant filter entirely. ⭐ RLS (Day 160) is what makes this safe.
⭐
⭐   ⇒ ⭐⭐ AND THE ORM'S REAL INJECTION HOLE: `.extra()`, `raw()`, and
⭐        `RawSQL()` — everything else parameterises for you. ⭐ Grep for those
⭐        three in any review.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Assuming multi-step views are atomic | Django is in autocommit — each `save()` is its own transaction. |
| `ATOMIC_REQUESTS = True` with third-party calls | Holds a transaction open across network I/O for the whole request. |
| Catching a database error without an inner `atomic` | The transaction is poisoned; every later statement raises. |
| `.delay()` inside the transaction | The worker reads before commit and gets `DoesNotExist`. Use `on_commit`. |
| Expecting `on_commit` callbacks to run under `TestCase` | They don't. Use `captureOnCommitCallbacks`. |
| `obj.field += 1; obj.save()` | Read-modify-write race. Use `F()`. |
| Reading an attribute after saving with `F()` | It's a `CombinedExpression`, not a number. `refresh_from_db()`. |
| `select_for_update()` outside `atomic` | Errors on Postgres, silently does nothing on MySQL autocommit, ignored by SQLite. |
| Testing locking on SQLite | It ignores `select_for_update` entirely — you've proven nothing. |
| `select_for_update` + `select_related` | Locks the joined tables too. Use `of=("self",)`. |
| Expecting the lock at the line that declares it | QuerySets are lazy; the lock happens on evaluation. |
| Business logic in `save()` or a signal | Silently skipped by `bulk_create`, `bulk_update` and `queryset.update()`. |
| Assuming `queryset.delete()` is one query | It fetches rows for cascades and signals — 1M rows can OOM you. |
| Assuming `save()` validates | It doesn't. `full_clean()` does, and nothing calls it for you. |
| Relying on `max_length` for integrity | Enforced by the column if the backend bothers. Use `Meta.constraints`. |
| Two `Count()` annotations over different relations | Joins multiply; both numbers are silently wrong. Use `distinct=True` or subqueries. |
| String formatting inside `raw()` or `RawSQL()` | SQL injection — the ORM's protection stops where you leave it. |

## Interview questions

**Q: Is a Django view atomic by default?**

> No — Django runs in autocommit, so every `save()` is its own transaction that commits immediately.
> That means a view doing two saves reads as one operation and is two, so if the second raises, the
> first is already committed: the order is marked paid and no ticket exists. The fix is
> `transaction.atomic`, and I'd put it on the service function rather than per-save or per-request.
> `ATOMIC_REQUESTS = True` is tempting because it's impossible to forget, but it holds a transaction
> open for the entire request including any third-party HTTP call, which breaks the rule about never
> holding locks across I/O — and worse, the boundary is then invisible in the code, it's in your
> settings file. Nested `atomic` is a savepoint rather than a transaction, and the related trap is
> that catching a database error without its own inner `atomic` block poisons the whole transaction:
> Postgres marks it aborted and every subsequent statement fails.

**Q: How do you increment a counter safely?**

> `F()`, which references the column on the server, so it compiles to `SET quantity_sold =
> quantity_sold + 1` — the read and the write are one statement, so there's nothing to interleave.
> The Python version, read then modify then save, is a classic lost update: two requests read five,
> both write six, one sale vanishes. And the conditional form is how I'd solve overselling in
> Django — `filter(pk=1, quantity_sold__lt=F("quantity_total")).update(...)` and check the returned
> rowcount. That's an atomic check-and-set in one statement with no lock at all. Two gotchas: after
> saving with an `F()`, the Python attribute holds an expression object rather than a number, so
> `refresh_from_db()` if you need the value; and `.update()` doesn't call `save()`, so `auto_now`
> fields silently stop updating.

**Q: What's dangerous about `bulk_create`?**

> It's fast because it skips almost everything: no `save()`, no signals, no validation, and largely
> no `auto_now`. So if there's business logic in a `save()` override or in a `post_save` signal, it
> silently stops happening the day someone replaces a loop with `bulk_create` — no error, no log, and
> the pull request looks like a pure performance improvement while it changes behaviour. That's the
> strongest practical argument for keeping business logic in explicit service functions rather than
> in `save()` or signals. The inverse surprise is `queryset.delete()`, which is *not* one query —
> Django fetches the rows to run cascades and fire signals, so deleting a million rows loads a
> million objects into memory. And cascades are enforced by Django in Python, not by the database,
> unless you've also added a database-level constraint.

**Q: Does `save()` validate?**

> No, and it surprises everyone. `full_clean()` runs validators and nothing calls it for you —
> validation lives in forms and DRF serializers, which is a deliberate design choice and a real gap:
> a management command, a data migration or a signal writing directly to the model bypasses every
> validator you wrote. `max_length` isn't enforced by `save()` either; it's enforced by the column,
> if the backend bothers — MySQL may truncate and SQLite ignores it. So for anything that's a genuine
> invariant, I put a `CheckConstraint` or `UniqueConstraint` in `Meta.constraints`, which is the same
> principle as the capstone: put the guarantee where a bug can't reach it.

**Q: What's wrong with `annotate(a=Count("x"), b=Count("y"))`?**

> Both numbers are wrong. Each `Count` becomes a join, and joining two multi-valued relations
> multiplies rows, so each count is inflated by the other's cardinality. What makes it nasty is that
> it returns plausible numbers rather than raising, so it ships and someone notices months later that
> a dashboard is inflated. The fix is `distinct=True` on each count, or restructuring as subqueries
> with `Subquery`/`OuterRef`, which is generally the better answer because it doesn't rely on
> deduplicating a cartesian product.

## 🎙️ Articulation drill

**Two minutes: "How does Django handle transactions and concurrency?"**

Lead with the default, because it's the thing people assume wrongly: autocommit, so a multi-step view
is not atomic no matter how it reads. Then where the boundary belongs and why `ATOMIC_REQUESTS` is
the tempting wrong answer — it makes the boundary invisible and holds it across I/O. Then concurrency
with `F()`, derived: the read and the write become one statement, so there's nothing to interleave,
and the conditional form is a check-and-set that needs no lock. Mention `select_for_update` and the
trap that it silently does nothing on SQLite, which is why you test on the database you deploy on.
Close on the bulk-operations table, because it's the highest-value thing here: **`bulk_create` skips
`save()`, signals and validation, so business logic in either of those silently disappears in a pull
request that looks like a pure optimisation.**
