# Part 1 — ⭐⭐ The aggregate is a contention boundary

```
⭐⭐ THE DEFINITION PEOPLE LEARN: "a cluster of related objects
⭐   treated as a unit."
⭐   ⇒ ⭐ True, and it leads straight to the wrong design,
⭐     because "related" is unbounded — ⭐⭐ EVERYTHING IS
⭐     RELATED TO EVERYTHING, SO THE RULE GIVES NO GUIDANCE.

⭐⭐ THE DEFINITION THAT DECIDES ANYTHING:
⭐   ***AN AGGREGATE IS THE UNIT OF CONSISTENCY AND THEREFORE
⭐      THE UNIT OF CONTENTION.*** ⭐ One aggregate, one
⭐   transaction, one lock, one conflict domain.

⭐⭐ WHICH TURNS THE MODELLING QUESTION INTO A CONCURRENCY
⭐   QUESTION: ***WHAT MUST BE TRUE AT THE INSTANT A
⭐   TRANSACTION COMMITS?***
⭐   ⭐ "An order's total equals the sum of its lines" ⇒ ⭐⭐
⭐     MUST HOLD ALWAYS ⇒ lines are INSIDE the Order aggregate.
⭐   ⭐ "A customer's lifetime spend reflects their orders" ⇒
⭐     ⭐ must it be exact at commit time? ⭐⭐ NO — nobody can
⭐     tell if it is four seconds stale ⇒ SEPARATE AGGREGATE,
⭐     updated eventually.
⭐   ⇒ ⭐⭐ AND THAT SECOND ANSWER IS A ***DECISION***, NOT A
⭐     COMPROMISE. ⭐ Saying "this is eventually consistent, and
⭐     here is the window" is engineering; ⭐⭐ PUTTING IT IN
⭐     THE SAME TRANSACTION ***BY ACCIDENT*** IS HOW YOU END UP
⭐     LOCKING A CUSTOMER ROW ON EVERY ORDER LINE INSERT.
```

```
⭐⭐ THE TWO SIZING FAILURES, WITH THEIR SYMPTOMS:
⭐   ⭐ ⭐⭐ TOO BIG ⇒ CONTENTION. `Venue` containing every
⭐        booking means ⭐ two people booking different rooms on
⭐        different days serialise against each other. ⭐⭐ THE
⭐        SYMPTOM IS 40001 SERIALISATION FAILURES (Day 195) OR
⭐        LOCK WAITS THAT MAKE NO SENSE TO ANYONE READING THE
⭐        DOMAIN MODEL.
⭐   ⭐ TOO SMALL ⇒ ⭐ INVARIANTS UNENFORCEABLE. If `OrderLine`
⭐        is its own aggregate, nothing can guarantee the total
⭐        — ⭐⭐ AND YOU WILL DISCOVER THIS AS A SUPPORT TICKET
⭐        ABOUT A WRONG INVOICE, NOT AS AN EXCEPTION.
⭐   ⇒ ⭐ Bias SMALL. ⭐⭐ CONTENTION IS THE HARDER PROBLEM TO
⭐     FIX LATER, AND A MISSING INVARIANT CAN BE PUSHED INTO A
⭐     DATABASE CONSTRAINT (Day 250).
```

# Part 2 — ⭐⭐ Reference other aggregates by ID

```python
# ❌ class Order:
#        customer: Customer        # ⭐ a whole other aggregate
#    → order.customer.credit_limit -= amount        # ⭐⭐ AND NOW…

# ⭐⭐ class Order:
#        customer_id: CustomerId   # ⭐ an ID, and nothing more
```

```
⭐⭐ WHY THIS ONE RULE MATTERS MORE THAN IT LOOKS:
⭐   ① ⭐⭐ IF YOU CAN NAVIGATE TO IT, YOU CAN MUTATE IT — and
⭐     the moment you do, ***TWO AGGREGATES ARE IN ONE
⭐     TRANSACTION***, so you now lock customer rows on order
⭐     writes and have invented a contention hotspot with no
⭐     code that looks wrong.
⭐   ② ⭐ IT MAKES THE BOUNDARY VISIBLE. `customer_id` says "you
⭐     must go and load that separately, deliberately."
⭐   ③ ⭐⭐ AND IN PYTHON THE ORM MAKES THE VIOLATION INVISIBLE:
⭐     `order.customer` LOOKS LIKE AN ATTRIBUTE ACCESS AND IS A
⭐     QUERY (Day 299) — ⭐ so the design rule and the N+1 rule
⭐     turn out to be the same rule seen from two directions.

⭐ ⭐ THE OBJECTION, AND ITS ANSWER: "but then I need the
⭐   customer's name for the order screen."
⭐   ⇒ ⭐⭐ THAT IS A ***READ***, AND READS DO NOT GO THROUGH
⭐     AGGREGATES (Day 301). ⭐ The query module joins whatever
⭐     it likes and returns a DTO. ⭐⭐ THE AGGREGATE RULE
⭐     CONSTRAINS ***WRITES***, WHERE INVARIANTS LIVE.
```

# Part 3 — ⭐⭐ Domain events

```
⭐⭐ WHAT ONE IS, PRECISELY:
⭐   ⭐ A ***FACT THAT HAPPENED***. Past tense. Immutable.
⭐     `JobCompleted(job_id, at, by)`.
⭐   ⭐ It carries what a consumer needs to react, ⭐ and it is
⭐     named in the domain's language (Day 304).
⭐   ⭐⭐ AND IT IS NOT A COMMAND: `SendInvoiceEmail` IS AN
⭐     INSTRUCTION TO ONE HANDLER; `JobCompleted` IS A FACT ANY
⭐     NUMBER OF HANDLERS MAY CARE ABOUT — ⭐⭐ WHICH MEANS THE
⭐     PUBLISHER MUST NOT KNOW WHO IS LISTENING. The moment it
⭐     does, you have a command with an event's name.

⭐⭐ THE THING THAT DECIDES THE MECHANISM: ***WHAT HAPPENS IF
⭐   THE HANDLER FAILS?***
⭐   ⭐ ⭐⭐ IF THE WORK ***MUST*** HAPPEN ⇒ THE OUTBOX
⭐     (Day 263). Same transaction, at-least-once delivery,
⭐     idempotent consumer. ⭐ Emails, invoices, notifying
⭐     another system.
⭐   ⭐ IF IT IS ONLY DECOUPLING IN-PROCESS LOGIC and losing it
⭐     is acceptable ⇒ ⭐ a synchronous in-transaction handler
⭐     is fine and much simpler.
⭐   ⇒ ⭐⭐ THE FAILURE IS PICKING A SYNCHRONOUS HANDLER FOR
⭐     WORK THAT MUST HAPPEN — because it works in every test,
⭐     and loses the email exactly when the process dies.
```

```
⭐ ⭐ WHERE EVENTS ARE RAISED: ⭐⭐ THE ENTITY RECORDS THEM;
⭐   THE SERVICE COLLECTS AND DISPATCHES THEM.
⭐     job.complete(at)          # ⭐ appends JobCompleted to
⭐                               #   job.events
⭐     uow.outbox.add_all(job.pull_events())
⭐     uow.commit()
⭐   ⇒ ⭐ The domain stays pure (Day 300) — ⭐⭐ IT DESCRIBES
⭐     WHAT HAPPENED, AND KNOWS NOTHING ABOUT DELIVERY.
```

# Part 4 — ⭐⭐ Eventual consistency as a deliberate choice

```
⭐⭐ WHEN TWO AGGREGATES MUST BOTH CHANGE, YOU HAVE EXACTLY
⭐   THREE OPTIONS, AND THEY SHOULD BE STATED IN THIS ORDER:
⭐   ① ⭐ MERGE THEM into one aggregate ⇒ ⭐ strong consistency,
⭐        ⭐⭐ AND CONTENTION (Part 1).
⭐   ② ⭐⭐ EVENT + EVENTUAL CONSISTENCY ⇒ commit the first,
⭐        emit an event, the second follows within seconds.
⭐   ③ ⭐ A DATABASE CONSTRAINT spanning both ⇒ ⭐⭐ THE
⭐        UNDERRATED OPTION. An `EXCLUDE` or a FK does not care
⭐        about your aggregate boundaries (Day 250) and gives
⭐        you strong consistency ***without*** a big aggregate.

⭐⭐ AND IF YOU CHOOSE ②, YOU OWE ONE ANSWER:
⭐   ***WHAT DO WE DO IF THE SECOND STEP NEVER SUCCEEDS?***
⭐   ⭐ Retry forever (Day 265)? ⭐ Compensate — reverse the
⭐     first? ⭐ Flag for a human?
⭐   ⇒ ⭐⭐ THIS IS A ***BUSINESS*** QUESTION, NOT A TECHNICAL
⭐     ONE, and it is the single most useful question to bring
⭐     to a domain expert. ⭐ "If the payment succeeds and we
⭐     can't allocate stock, do we refund automatically or call
⭐     the customer?" ⭐⭐ THEY HAVE AN OPINION. NOBODY HAS
⭐     EVER ASKED THEM.
```

# Part 5 — ⭐⭐ Bounded contexts

```
⭐⭐ THE OBSERVATION FROM DAY 304, FOLLOWED THROUGH: THE SAME
⭐   WORD MEANS DIFFERENT THINGS TO DIFFERENT TEAMS.
⭐   ⇒ ⭐ THE WRONG FIX: one canonical `Customer` with every
⭐     field every team needs.
⭐   ⇒ ⭐⭐ WHAT THAT PRODUCES: A CLASS WITH FORTY FIELDS, MOST
⭐     OF THEM NULL FOR MOST USES, WHICH CHANGES FOR THREE
⭐     UNRELATED REASONS AND WHOSE VALIDATION RULES CONTRADICT
⭐     EACH OTHER. ⭐ It serves nobody and blocks everybody.

⭐⭐ THE RIGHT FIX: DIFFERENT MODELS, EXPLICITLY.
⭐   ⭐ BILLING's Customer   — tax id, billing address, payment
⭐        method, credit terms
⭐   ⭐ DISPATCH's Customer  — site address, access notes,
⭐        contact phone
⭐   ⭐ SUPPORT's Customer   — tier, open tickets, history
⭐   ⇒ ⭐⭐ THREE CLASSES, THREE MODULES, ONE SHARED
⭐     ***IDENTIFIER***. ⭐ Each is small, each changes for one
⭐     reason, and each can be validated by rules that are
⭐     actually true in its context.
⭐   ⇒ ⭐ "But it's the same customer!" ⭐⭐ YES — AND `CustomerId`
⭐     IS THE THING THEY SHARE. THE ***MODEL*** IS NOT SHARED,
⭐     BECAUSE THE MEANING ISN'T.
```

# Part 6 — ⭐ Context mapping: how contexts relate

```
⭐   ⭐ SHARED KERNEL — a small module both depend on (Money,
⭐        identifiers). ⭐⭐ KEEP IT TINY AND STABLE: everything
⭐        depends on it, so every change is a fleet-wide change.
⭐   ⭐ CUSTOMER / SUPPLIER — downstream's needs influence
⭐        upstream's interface. ⭐ Requires the teams to talk.
⭐   ⭐ CONFORMIST — you take their model as-is because you have
⭐        no leverage. ⭐ Common with vendors and legacy systems.
⭐   ⭐⭐ ANTICORRUPTION LAYER — you translate their model into
⭐        yours at the boundary, so their vocabulary never
⭐        enters your domain.
⭐        ⇒ ⭐⭐ AND YOU HAVE ALREADY BUILT ONE: the payment
⭐          adapter (Day 300) that turns Stripe's
⭐          `PaymentIntent` into your `ChargeResult` ***is***
⭐          an anticorruption layer. ⭐ Naming it is worth
⭐          something in an interview, because it shows the
⭐          pattern was a decision rather than an accident.
```

# Part 7 — ⭐⭐ Where the seam goes inside one codebase

```
⭐⭐ CONTEXTS ARE MODULES, NOT SERVICES (Day 306).
⭐   ⭐ `billing/`, `dispatch/`, `support/`, each with its own
⭐     domain, services and repositories.
⭐   ⭐ Each publishes a small public interface; everything else
⭐     is private.
⭐   ⭐⭐ AND THE RULE THAT IS BROKEN MOST OFTEN AND MATTERS
⭐     MOST: ***A MODULE MAY NOT READ ANOTHER MODULE'S
⭐     TABLES.*** ⭐ Not "should not" — ⭐⭐ IF DISPATCH JOINS
⭐     TO `billing_invoices`, THE BOUNDARY IS DECORATIVE, AND
⭐     BILLING CAN NEVER CHANGE ITS SCHEMA AGAIN (Day 298).

⭐ ⭐ CROSS-CONTEXT COMMUNICATION, IN ORDER OF PREFERENCE:
⭐   ⭐ a direct call to the other module's PUBLIC INTERFACE —
⭐     ⭐ synchronous, same process, and it can share a
⭐     transaction if you decide it should
⭐   ⭐ a DOMAIN EVENT — ⭐ decoupled, asynchronous, no return
⭐     value, and the publisher does not know who listens
⭐   ⭐⭐ NEVER A SHARED TABLE, AND NEVER AN IMPORT OF ANOTHER
⭐     CONTEXT'S ENTITIES — ⭐ importing `billing.Invoice` into
⭐     dispatch means dispatch now breaks when billing renames a
⭐     field, which is precisely what the context existed to
⭐     prevent.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| "A cluster of related objects" as the sizing rule | Everything is related; the rule gives no guidance. |
| Sizing aggregates by data relationships | Size by what must be true at commit time. |
| Aggregates that are too big | Two people booking different rooms serialise against each other. |
| Aggregates too small to hold an invariant | You find out via a support ticket, not an exception. |
| Object references between aggregates | If you can navigate it you can mutate it, and now two are in one transaction. |
| Forgetting the ORM hides this | `order.customer` looks like an attribute and is a query. |
| Enlarging an aggregate to serve a screen | That's a read; reads bypass aggregates entirely. |
| Events that are really commands | If the publisher knows who listens, it's a command with an event's name. |
| Synchronous handlers for work that must happen | Works in every test; loses the email when the process dies. |
| Raising events from the service | The entity records what happened; the service dispatches. |
| Eventual consistency by accident | Say the window out loud, or you've made a decision without knowing. |
| No answer for a failed second step | It's a business question, and nobody has ever asked the expert. |
| Forgetting a constraint can span aggregates | Strong consistency without a big aggregate — the underrated option. |
| One canonical model for every team | Forty fields, mostly null, changing for three unrelated reasons. |
| Sharing the model instead of the identifier | They share a `CustomerId`; the meaning isn't shared. |
| A large shared kernel | Everything depends on it, so every change is fleet-wide. |
| One module reading another's tables | The boundary is decorative and the owner can never change its schema. |
| Importing another context's entities | You break when they rename a field — exactly what the context prevented. |

## Interview questions

**Q: How do you decide aggregate boundaries?**

> By asking what must be true at the instant a transaction commits — because an aggregate is the unit
> of consistency and therefore the unit of contention. "The order total equals the sum of its lines"
> must always hold, so lines live inside the order. "Customer lifetime spend reflects their orders"
> doesn't need to be exact at commit time — nobody can tell if it's four seconds stale — so that's a
> separate aggregate updated eventually. And I'd stress that the second answer is a decision rather
> than a compromise: eventual consistency stated with a window is engineering, whereas putting it in
> the same transaction by accident means you're locking a customer row on every order line insert.

**Q: Why reference other aggregates by ID?**

> Because if you can navigate to it, you can mutate it — and the moment you do, two aggregates are in
> one transaction and you've created a contention hotspot with no code that looks wrong. An ID makes
> the boundary visible: it says you must load that separately and deliberately. In Python this matters
> more than in some languages, because the ORM makes the violation invisible — `order.customer` looks
> like attribute access and is a query. So the aggregate rule and the N+1 rule turn out to be the same
> rule from two directions. The usual objection is needing the customer's name on a screen, and that's
> a read: reads bypass aggregates and return DTOs.

**Q: What's a domain event and how do you deliver it?**

> A fact that happened — past tense, immutable, named in the domain's language, and crucially the
> publisher doesn't know who listens. If it did, it'd be a command wearing an event's name. Delivery
> is decided by one question: what happens if the handler fails? If the work must happen — an invoice,
> a notification to another system — it goes in the outbox, in the same transaction, with an
> idempotent consumer. If it's only decoupling in-process logic and losing it is acceptable, a
> synchronous handler is fine. The failure is choosing synchronous for work that must happen, because
> it passes every test and loses the email exactly when the process dies.

**Q: Two aggregates must both change. What are the options?**

> Three, and I'd name them in order. Merge them, which gives strong consistency and contention. Or an
> event with eventual consistency, in which case I owe one answer: what do we do if the second step
> never succeeds — retry, compensate, or flag for a human? That's a business question, and it's the
> most useful thing to bring to a domain expert, because they have an opinion and nobody has ever
> asked them. Or — the underrated one — a database constraint spanning both, since an `EXCLUDE` or a
> foreign key doesn't care about my aggregate boundaries and gives strong consistency without a big
> aggregate.

**Q: What's a bounded context, practically?**

> Recognition that the same word means different things to different teams, so you build different
> models rather than one canonical class. Billing's customer has a tax id and credit terms; dispatch's
> has a site address and access notes; support's has a tier and ticket history. One canonical
> `Customer` gives you forty fields that are mostly null, contradictory validation rules, and a class
> that changes for three unrelated reasons. Three models sharing a `CustomerId` gives you three small
> things that each change for one reason. Inside one codebase those are modules, with the hardest rule
> being that a module may not read another module's tables — otherwise the boundary is decorative and
> the owner can never change its schema again.

## 🎙️ Articulation drill

**Three minutes: "How do you decide what belongs together?"**

Start by rejecting the usual rule: **"a cluster of related objects" gives no guidance, because
everything is related.** The definition that decides anything is that **an aggregate is the unit of
consistency and therefore the unit of contention** — so the modelling question is really a concurrency
question: what must be true at the instant a transaction commits? Give both examples, and stress that
choosing eventual consistency is a decision with a stated window, **not a compromise — whereas getting
it by accident means locking a customer row on every order line insert.** Then references by ID, with
the reason that matters: **if you can navigate it you can mutate it**, and in Python the ORM hides
that completely, since `order.customer` looks like an attribute and is a query — so the aggregate rule
and the N+1 rule are the same rule from two directions. Handle the objection: needing a name on a
screen is a read, and reads bypass aggregates. Then domain events: a past-tense fact where **the
publisher doesn't know who listens**, with delivery decided by "what if the handler fails?" — outbox
for must-happen, synchronous for decoupling, and the failure being synchronous for must-happen because
it passes every test. Close on bounded contexts: **one canonical `Customer` gives you forty mostly-null
fields and contradictory validation**, while three context-specific models sharing an id each change
for one reason — and inside a monolith the hardest rule is that a module may not read another's
tables, or the boundary is decorative.
