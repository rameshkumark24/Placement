# Day 341 🚪

**P-341** · 🚪 **API gateway, service discovery, and the service mesh**

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a gateway handles concerns that belong to every *external* request, a mesh
> handles concerns that belong to every *internal* call, and both exist for exactly one reason — to
> stop the same cross-cutting logic being reimplemented, inconsistently, in every service by every
> team.**

---

# Part 1 — ⭐⭐ What belongs in a gateway, and what never does

```
⭐⭐ THE GATEWAY IS THE SINGLE ENTRY POINT FOR EXTERNAL TRAFFIC.

⭐⭐ ✔ WHAT BELONGS THERE — ALL CROSS-CUTTING, ALL EXTERNAL:
⭐   ⭐ TLS termination, HTTP/2 and HTTP/3.
⭐   ⭐ ⭐⭐ AUTHENTICATION — verify the JWT signature ***once***,
⭐     at the edge, and pass identity inward as trusted headers.
⭐   ⭐ Rate limiting and quotas (Day 336).
⭐   ⭐ Routing by path/host/header, and canary by header.
⭐   ⭐ Request/response size limits, timeouts.
⭐   ⭐ CORS, compression, WAF, IP allow-lists.
⭐   ⭐ Access logging and a request id, ⭐⭐ INJECTED HERE SO
⭐     EVERY SERVICE SHARES ONE (Day 338).

⭐⭐ ✘ WHAT MUST NOT BE THERE — AND THIS IS THE SCORED HALF:
⭐   ⭐ ⭐⭐ BUSINESS LOGIC OF ANY KIND. ⭐ The moment the gateway
⭐     knows that an order over ₹10,000 needs approval, ⭐⭐ YOU
⭐     HAVE A DISTRIBUTED GOD OBJECT THAT EVERY TEAM MUST EDIT
⭐     AND NOBODY CAN TEST.
⭐   ⭐ ⭐⭐ AUTHORISATION DECISIONS. ⭐ Authentication (who you
⭐     are) at the gateway; ⭐⭐ AUTHORISATION (what you may do)
⭐     IN THE SERVICE, because only the service knows whether
⭐     this user owns this row. ⭐ Day 259's rule, at
⭐     infrastructure scale.
⭐   ⭐ ⭐⭐ RESPONSE AGGREGATION ACROSS SERVICES, unless it is an
⭐     explicit BFF (Part 2) — otherwise the gateway silently
⭐     becomes a service with no repo and no tests.
⭐   ⭐ Data transformation that hides a service's real contract.

⭐⭐ THE RULE: ***IF CHANGING A BUSINESS REQUIREMENT MEANS
⭐   EDITING GATEWAY CONFIG, THE LOGIC IS IN THE WRONG PLACE.***

⭐⭐ AND THE TRUST BOUNDARY THAT MUST BE SAID OUT LOUD:
⭐   ⭐ Passing identity as `X-User-Id` works ***only*** if
⭐     services cannot be reached except through the gateway.
⭐   ⇒ ⭐⭐ OTHERWISE ANYONE INSIDE THE NETWORK SETS THAT HEADER
⭐     AND BECOMES ANYONE. ⭐ Network policy, mTLS, or forward
⭐     the original token and verify again — ⭐⭐ AND THE
⭐     GATEWAY MUST ***STRIP*** INBOUND `X-User-*` HEADERS FROM
⭐     CLIENTS, WHICH IS ONE LINE THAT PEOPLE FORGET.
```

# Part 2 — ⭐ BFF: one gateway per client, and why

```
⭐⭐ THE PROBLEM: web needs 40 fields, mobile needs 8 on a slow
⭐   network, the partner API needs a stable versioned contract.
⭐   ⇒ ⭐ One shared gateway serving all three ends up as a
⭐     compromise that serves none well, ⭐⭐ AND EVERY CHANGE
⭐     REQUIRES AGREEMENT FROM THREE CLIENT TEAMS.

⭐⭐ ***BACKEND FOR FRONTEND***: one thin service per client
⭐   type, ⭐⭐ OWNED BY THAT CLIENT'S TEAM.
⭐   ⭐ ✔ Mobile team changes its BFF without asking anyone.
⭐   ⭐ ✔ Aggregation and trimming happen server-side, on a fast
⭐     network, ⭐ instead of over the mobile link.
⭐   ⭐ ✘ N BFFs to run and secure; ⭐ duplicated logic between
⭐     them, which is ⭐⭐ ACCEPTABLE DUPLICATION — the
⭐     alternative is coupling three client teams together.

⭐⭐ AND THE ALTERNATIVE WORTH ONE SENTENCE: ⭐ GraphQL solves
⭐   the same over-fetching problem by letting the client choose
⭐   fields — ⭐⭐ AT THE COST OF QUERY-COST CONTROL (depth
⭐   limits, complexity budgets, persisted queries) AND CACHING,
⭐   ⭐ because every distinct query is a distinct cache key.
```

# Part 3 — ⭐⭐ Service discovery: three approaches

```
⭐⭐ THE PROBLEM: service A must call service B, whose pods
⭐   change IP every deploy.

⭐⭐ ① ***DNS*** — `orders.internal` resolves to the current set.
⭐   ⭐ ✔ Universal, zero libraries, language-agnostic.
⭐   ⭐ ✘ ⭐⭐ CACHING. ⭐ Resolvers, and ***your own runtime***,
⭐     cache records past their TTL. ⭐ A removed pod keeps
⭐     receiving traffic. ⭐⭐ AND THE PYTHON-SPECIFIC VERSION:
⭐     `httpx`/`requests` WITH A CONNECTION POOL WILL HOLD AN
⭐     ESTABLISHED CONNECTION TO A DEAD IP INDEFINITELY,
⭐     BECAUSE IT NEVER RE-RESOLVES. ⭐ Bound connection
⭐     lifetime, and don't rely on DNS TTL alone.
⭐   ⇒ ⭐ Kubernetes Services are this, ⭐ with kube-proxy doing
⭐     the balancing so the DNS record is stable.

⭐⭐ ② ***CLIENT-SIDE DISCOVERY*** — the client queries a
⭐   registry (Consul, Eureka) and picks an instance itself.
⭐   ⭐ ✔ One fewer hop; ⭐ the client can do smart balancing
⭐     (least-request, ⭐ power-of-two — Day 325).
⭐   ⭐ ✘ ⭐⭐ A CLIENT LIBRARY PER LANGUAGE, AND EVERY SERVICE
⭐     NOW EMBEDS DISCOVERY, RETRY AND BALANCING LOGIC THAT
⭐     MUST BE UPGRADED IN LOCKSTEP. ⭐ This is precisely the
⭐     pain the mesh was invented to remove.

⭐⭐ ③ ***SERVER-SIDE DISCOVERY*** — the client calls a stable
⭐   address; something else routes.
⭐   ⭐ ✔ Clients stay dumb. ⭐ ✘ One more hop and one more
⭐     component.
⭐   ⇒ ⭐ Kubernetes + a mesh sidecar is this.

⭐⭐ AND THE PART THAT IS ACTUALLY HARD:
⭐   ***HEALTH AND DEREGISTRATION.*** ⭐ A crashed instance never
⭐   deregisters itself. ⭐⭐ SO THE REGISTRY NEEDS ACTIVE HEALTH
⭐   CHECKING OR LEASES WITH RENEWAL — AND YOU ARE BACK TO DAY
⭐   325'S QUESTION OF DISTINGUISHING SLOW FROM DEAD.
```

# Part 4 — ⭐⭐ The service mesh: what it does and what it costs

```
⭐⭐ THE IDEA: a ***sidecar proxy*** (Envoy) beside every pod
⭐   intercepts all inbound and outbound traffic.
⭐   ⭐ ***DATA PLANE*** = the sidecars. ⭐ ***CONTROL PLANE*** =
⭐     the thing configuring them (Istio, Linkerd).

⭐⭐ WHAT YOU GET, ***WITHOUT CHANGING APPLICATION CODE***:
⭐   ⭐ mTLS between every service, with automatic certificate
⭐     rotation — ⭐⭐ OFTEN THE SINGLE BEST REASON, BECAUSE
⭐     DOING THIS BY HAND IN TEN SERVICES IS MISERABLE.
⭐   ⭐ Retries, timeouts, circuit breaking, outlier ejection
⭐     (Day 339) — ⭐⭐ CONFIGURED CENTRALLY, IDENTICAL
⭐     EVERYWHERE.
⭐   ⭐ Load balancing that understands HTTP/2 and gRPC (Day 325).
⭐   ⭐ ⭐⭐ TRAFFIC SPLITTING FOR CANARIES BY PERCENTAGE OR
⭐     HEADER, with no deploy.
⭐   ⭐ Uniform metrics, traces and access logs for every hop —
⭐     ⭐ a golden-signals dashboard for free.
⭐   ⭐ Fault injection: ⭐⭐ ADD 500 ms OR 5% ERRORS TO ONE
⭐     DEPENDENCY TO TEST DAY 339'S DEFENCES, WITHOUT TOUCHING
⭐     CODE.

⭐⭐ WHAT IT COSTS — SAY ALL FIVE:
⭐   ① ⭐ A sidecar per pod: ~50–150 MB RAM, ~0.5–1 ms per hop.
⭐        ⭐⭐ DOUBLE YOUR POD COUNT AND ADD TWO HOPS PER CALL.
⭐   ② ⭐⭐ A COMPLEX, CRITICAL CONTROL PLANE. ⭐ When it
⭐        misbehaves, ***everything*** misbehaves, and the
⭐        failure is in a layer your team may not understand.
⭐   ③ ⭐ A steep operational learning curve; ⭐ Istio's config
⭐        surface is genuinely large.
⭐   ④ ⭐⭐ DEBUGGING NOW HAS A LAYER THAT IS INVISIBLE FROM
⭐        YOUR CODE. ⭐ "Why did I get a 503 when the service is
⭐        healthy?" is a mesh question, and it is a new class
⭐        of question.
⭐   ⑤ ⭐ Startup ordering: ⭐⭐ THE APP CAN START BEFORE THE
⭐        SIDECAR IS READY AND ITS FIRST OUTBOUND CALLS FAIL —
⭐        a classic and confusing bug.

⭐⭐ THE HONEST THRESHOLD:
⭐   ***YOU NEED A MESH WHEN YOU HAVE ENOUGH SERVICES, IN
⭐      ENOUGH LANGUAGES, THAT MAINTAINING RESILIENCE AND mTLS
⭐      IN LIBRARIES HAS BECOME THE BOTTLENECK.***
⭐   ⇒ ⭐ Roughly: ⭐⭐ UNDER ~10 SERVICES IN ONE LANGUAGE, USE A
⭐     SHARED LIBRARY AND SKIP IT. ⭐ Say this plainly — it is
⭐     the mature answer, and "we'd add a service mesh" as a
⭐     reflex is a red flag.
```

# Part 5 — ⭐ Where each cross-cutting concern actually goes

```
⭐⭐ THE TABLE WORTH MEMORISING — ⭐ it answers half the
⭐   follow-up questions in this area:

⭐   CONCERN                      WHERE
⭐   ────────────────────────────────────────────────────────
⭐   TLS to the client            gateway
⭐   ⭐⭐ mTLS service-to-service   mesh (or a shared library)
⭐   Authentication               ⭐⭐ GATEWAY (verify once)
⭐   ⭐⭐ AUTHORISATION             ⭐⭐ THE SERVICE. ALWAYS.
⭐   Rate limiting (per client)   gateway
⭐   Rate limiting (per tenant,
⭐     per feature)               ⭐ the service
⭐   Retries / timeouts / breakers ⭐ mesh, or library
⭐   ⭐⭐ IDEMPOTENCY               ⭐⭐ THE SERVICE. Nothing else
⭐                                 knows what "the same
⭐                                 operation" means.
⭐   Tracing propagation          ⭐ mesh injects; ⭐⭐ THE APP
⭐                                 MUST STILL PROPAGATE ACROSS
⭐                                 QUEUES (Day 338)
⭐   Canary routing               gateway or mesh
⭐   Schema validation            the service
⭐   Business rules               ⭐⭐ THE SERVICE, NON-NEGOTIABLE

⭐⭐ THE PATTERN IN THAT TABLE: ***INFRASTRUCTURE HANDLES WHAT
⭐   IS TRUE OF ***EVERY*** REQUEST; THE SERVICE HANDLES
⭐   ANYTHING THAT REQUIRES KNOWING WHAT THE REQUEST ***MEANS***.***
```

# Part 6 — ⭐⭐ The gateway as a single point of failure

```
⭐⭐ EVERYTHING GOES THROUGH IT, SO:
⭐   ⭐ It must be replicated, multi-AZ, and autoscaled ahead of
⭐     traffic, not behind it.
⭐   ⭐ ⭐⭐ IT MUST NOT DEPEND ON ANY SERVICE IT FRONTS. ⭐ A
⭐     gateway that calls an auth service synchronously on every
⭐     request has made that service's availability the ceiling
⭐     for ***everything***. ⭐ Verify JWTs locally with a cached
⭐     JWKS, ⭐⭐ AND CACHE THE KEYS WITH A LONG STALE-IF-ERROR
⭐     WINDOW so a JWKS outage doesn't log everyone out.
⭐   ⭐ ⭐⭐ ITS CONFIGURATION IS A DEPLOY. ⭐ It needs review,
⭐     staging, canaries and instant rollback — ⭐⭐ A BAD ROUTE
⭐     REGEX IS A TOTAL OUTAGE, AND IT IS THE MOST COMMON
⭐     GATEWAY INCIDENT BY A LARGE MARGIN.
⭐   ⭐ ⭐⭐ ITS OWN TIMEOUTS MUST BE THE LONGEST IN THE SYSTEM
⭐     (Day 325's decreasing-inward rule, from the top).

⭐⭐ AND THE DEGRADED MODE WORTH DESIGNING:
⭐   ***WHAT DOES THE GATEWAY DO WHEN ITS RATE-LIMIT STORE IS
⭐      DOWN?*** ⭐ Fail open and risk overload, or fail closed
⭐   and cause an outage? ⭐⭐ THE ANSWER IS PER-ROUTE, AND
⭐   DECIDING IT IN ADVANCE IS THE DIFFERENCE BETWEEN AN
⭐   ENGINEER AND A CONFIGURATION.
```

# Part 7 — ⭐ What you need when you have three services

```
⭐⭐ THE ANSWER MOST CANDIDATES CANNOT GIVE, AND IT SCORES:
⭐   ⭐ ***THREE SERVICES, ONE LANGUAGE, ONE TEAM?***
⭐   ⇒ ⭐⭐ NO MESH. NO REGISTRY. NO BFF.
⭐   ⭐ Kubernetes Services (DNS) for discovery.
⭐   ⭐ One ingress/ALB for TLS, routing and per-key rate
⭐     limiting.
⭐   ⭐ ⭐⭐ A SMALL SHARED HTTP CLIENT LIBRARY carrying
⭐     timeouts, retries, a breaker and trace propagation
⭐     (Day 339's `Dependency` wrapper — ⭐ you already wrote
⭐     it).
⭐   ⭐ NetworkPolicy so services can only be reached through
⭐     the ingress.
⭐   ⇒ ⭐⭐ THAT IS ~100 LINES AND A YAML FILE, AND IT COVERS
⭐     EVERYTHING A MESH WOULD HAVE GIVEN YOU AT THIS SIZE.

⭐⭐ AND THE TRIGGER FOR EACH UPGRADE — ⭐ name the trigger,
⭐   not the tool:
⭐   ⭐ A second language ⇒ ⭐⭐ the shared library stops being
⭐     shared ⇒ consider a mesh.
⭐   ⭐ A compliance requirement for encryption in transit
⭐     everywhere ⇒ mesh (mTLS).
⭐   ⭐ Multiple client types with divergent needs ⇒ BFFs.
⭐   ⭐ Teams needing traffic control without deploys ⇒ mesh.
⭐   ⇒ ⭐⭐ "WE'D ADD X WHEN Y HAPPENS" IS A SENIOR ANSWER.
⭐     "WE'D ADD X" IS NOT.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ Business logic in the gateway | A distributed god object every team edits and nobody can test |
| ⭐⭐ Authorisation at the gateway | Only the service knows whether this user owns this row |
| ⭐⭐ Trusting `X-User-Id` without a network boundary | Anyone inside the network becomes anyone. And strip inbound `X-User-*` |
| ⭐ Gateway calling a service it fronts, synchronously | That service's availability becomes the ceiling for everything |
| ⭐⭐ Gateway config with no review or rollback | A bad route regex is a total outage — the most common gateway incident |
| ⭐ Relying on DNS TTL for failover | Resolvers and your own pooled connections keep talking to dead IPs |
| ⭐ Client-side discovery in three languages | Three libraries carrying retry and balancing logic, upgraded in lockstep |
| ⭐⭐ A mesh for five services in one language | Doubled pod count, a critical control plane, and a shared library would have done it |
| ⭐ Forgetting sidecar startup ordering | The app's first outbound calls fail before the sidecar is ready |
| ⭐ Assuming the mesh propagates trace context across queues | It handles hops it can see. The queue isn't one |
| ⭐ No decision for a failed rate-limit store | Fail open or closed is a per-route business decision, made in advance |

## Interview questions

**1. "What belongs in an API gateway?"**
> ⭐ Cross-cutting concerns for external traffic: TLS, authentication verified once, rate limiting,
> routing, size limits, CORS, WAF, and injecting the request id everyone will share. ⭐⭐ What must
> never be there: **business logic, and authorisation** — authentication is who you are and belongs at
> the edge, authorisation is what you may do and only the service knows whether this user owns this
> row. ⭐ My rule: if changing a business requirement means editing gateway config, the logic is in the
> wrong place.

**2. "You pass identity as a header. What's the risk?"**
> ⭐⭐ It only works if services are unreachable except through the gateway — **otherwise anyone inside
> the network sets `X-User-Id` and becomes anyone.** ⭐ So: network policy or mTLS, and the gateway must
> strip inbound `X-User-*` headers from clients, which is one line people routinely forget. ⭐ The
> stronger alternative is forwarding the original token and verifying signature at each service.

**3. "Do you need a service mesh?"**
> ⭐ Probably not, and I'd say when I would. ⭐⭐ **Under about ten services in one language, a shared
> HTTP client library with timeouts, retries, a breaker and trace propagation covers everything a mesh
> gives you** — and costs no sidecars, no control plane and no new class of debugging question. ⭐ The
> triggers to adopt one are a second language, so the shared library stops being shared; a compliance
> requirement for mTLS everywhere; or teams needing traffic control without deploys. ⭐⭐ "We'd add it
> when X happens" is the answer; "we'd add it" isn't.

**4. "What does a mesh actually cost?"**
> ⭐ Fifty to a hundred and fifty megabytes and about a millisecond per hop per sidecar — you double
> pod count and add two hops per call. ⭐⭐ A complex control plane whose misbehaviour makes
> **everything** misbehave, in a layer your team may not understand. ⭐ A steep learning curve, a new
> debugging surface — "why a 503 when the service is healthy" is now a mesh question — ⭐ and sidecar
> startup ordering, where the app's first outbound calls fail before the proxy is ready.

**5. "How does service discovery work in Kubernetes, and what's the trap?"**
> ⭐ A Service gives a stable DNS name and virtual IP; kube-proxy balances to the current endpoints, so
> pods can change freely. ⭐⭐ The trap is caching, and the Python version is specific: **an `httpx` or
> `requests` connection pool holds an established connection to a dead IP indefinitely, because it never
> re-resolves.** ⭐ So bound connection lifetime rather than relying on DNS TTL. ⭐ And the genuinely
> hard part of any discovery system is deregistration — a crashed instance never removes itself, so you
> need active checks or renewable leases, and you're back to distinguishing slow from dead.

**6. "Where do retries belong — mesh or application?"**
> ⭐ Mechanism in the mesh or a shared library, **policy from the service** — because only the service
> knows whether an operation is idempotent. ⭐⭐ And critically, retries must exist at **exactly one
> layer**: mesh retries plus SDK retries plus gateway retries is Day 339's twenty-seven requests. ⭐ If
> the mesh does them, I turn the library's off explicitly, and I still own idempotency, because nothing
> below the service knows what "the same operation" means.

## 🎙️ Articulation drill

**Two minutes.** Give the division first: **a gateway handles what's true of every external request, a
mesh handles what's true of every internal call**, and both exist so the same cross-cutting logic isn't
reimplemented inconsistently by every team. Then the line people get wrong: **authentication at the
gateway, authorisation in the service**, because only the service knows whether this user owns this
row — and no business logic at the edge, because the moment the gateway knows an order over ten
thousand needs approval, it's a distributed god object every team edits and nobody tests. Add the
security detail: **passing identity as a header is only safe if services are unreachable except through
the gateway, and the gateway must strip inbound `X-User-*` from clients.** On discovery, name the
Python-specific trap: **a pooled HTTP client holds a connection to a dead IP indefinitely because it
never re-resolves**, so bound connection lifetime rather than trusting DNS TTL. Then the mesh, priced
honestly: mTLS with rotation, uniform resilience config, canary traffic splitting and free
golden-signals — against doubled pod count, a critical control plane whose failure breaks everything,
and a debugging layer invisible from your code. Close with the answer that shows judgement: **three
services in one language need no mesh, no registry and no BFF — Kubernetes DNS, one ingress, a hundred
lines of shared HTTP client, and a network policy** — and name the triggers for each upgrade, because
"we'd add it when X happens" is a senior answer and "we'd add it" isn't.
