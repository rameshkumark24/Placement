# Part 1 — ⭐⭐ What it actually is

```python
@admin.register(Order)
class OrderAdmin(admin.ModelAdmin):
    list_display = ("id", "user", "status", "total_display", "created_at")
    list_filter = ("status", "created_at")
    search_fields = ("id", "user__email")
    date_hierarchy = "created_at"
    readonly_fields = ("total_cents", "created_at")     # ⭐⭐ Part 3
    list_select_related = ("user",)                     # ⭐⭐ Part 2 — the N+1

    @admin.display(description="Total")
    def total_display(self, obj):
        return f"£{obj.total_cents / 100:,.2f}"
```

```
⭐⭐ TWENTY LINES BUY YOU: a searchable, filterable, paginated, sortable CRUD
⭐   interface with permissions, an audit log, bulk actions, inline related
⭐   editing, a date drill-down and CSV-friendly display.
⭐   ⇒ ⭐⭐ IN FASTAPI THAT IS A FRONT-END PROJECT. ⭐ Two to six weeks,
⭐        depending on how honest you are being.

⭐⭐ AND WHAT IT IS **NOT**, WHICH IS THE WHOLE DAY:
⭐   ⭐⭐ IT IS NOT A CUSTOMER-FACING UI. It exposes your schema, not your
⭐        product — field names, foreign keys, internal statuses.
⭐   ⭐⭐ IT IS NOT SAFE BY DEFAULT FOR NON-ENGINEERS. `is_staff` plus a
⭐        permission is enough to edit rows directly.
⭐   ⭐⭐ **IT BYPASSES YOUR SERVICE LAYER ENTIRELY.** ⭐ It calls
⭐        `ModelForm.save()`, which calls `Model.save()`. So:
⭐        ⭐ no `place_order()`, no transaction boundary you designed, ⭐⭐ no
⭐        inventory decrement, no outbox row, no idempotency, no audit event.
⭐        ⇒ ⭐⭐ SETTING `order.status = "paid"` IN THE ADMIN MARKS AN ORDER
⭐          PAID WITHOUT CHARGING ANYONE OR ISSUING A TICKET. ⭐ Everything
⭐          downstream then believes it.
⭐   ⇒ ⭐⭐ THE ADMIN EDITS THE **DATABASE**, NOT YOUR **DOMAIN**. That
⭐        sentence is the one to carry into the rest of this day.
```

```
⭐ IT DOES run `ModelForm` validation — ⭐⭐ which means `full_clean()` DOES get
⭐   called here, unlike `Model.objects.create()` (Day 172). ⭐ So field
⭐   validators and `clean()` methods apply. ⭐⭐ Your DRF serializer validation
⭐   does not, and neither does anything in a service.
```

# Part 2 — ⭐⭐ The admin will be your slowest page

```
⭐⭐ THE ADMIN IS AN N+1 GENERATOR BY DESIGN (Day 171), AND IT HAS FIVE
⭐   SEPARATE SOURCES:

⭐  1. ⭐⭐ `list_display` WITH A FOREIGN KEY → one query PER ROW.
⭐       ⭐ 100 rows × 3 FKs = 300 queries for one page.
⭐       ⇒ ⭐ `list_select_related = ("user", "event")`.
⭐  2. ⭐⭐ A METHOD IN `list_display` THAT TOUCHES A RELATION → same, and
⭐       `list_select_related` does NOT cover it automatically. ⭐ Override
⭐       `get_queryset()` and add the loading there.
⭐  3. ⭐⭐ A ForeignKey EDIT WIDGET RENDERS **EVERY** RELATED ROW IN A
⭐       `<select>`. ⭐ 500,000 users = 500,000 `<option>` tags = ⭐⭐ a
⭐       multi-megabyte page that times out. ⭐ THE FIX IS `raw_id_fields` or
⭐       `autocomplete_fields`, and it is not optional past a few thousand rows.
⭐  4. ⭐ `list_filter` ON AN UNINDEXED OR HIGH-CARDINALITY COLUMN → ⭐⭐ Django
⭐       runs a `DISTINCT` over the whole table to build the filter sidebar.
⭐  5. ⭐⭐ THE PAGINATOR'S `COUNT(*)` on a 50M-row table is seconds, on every
⭐       page load. ⭐ Override with an estimated count
⭐       (`show_full_result_count = False` helps).
⭐
⭐   ⇒ ⭐⭐ AND HERE IS WHY IT MATTERS MORE THAN IT SOUNDS: THE ADMIN RUNS
⭐        AGAINST YOUR **PRODUCTION DATABASE**, USUALLY ON THE **SAME
⭐        WORKERS** AS YOUR API. ⭐ A support agent opening a 500,000-option
⭐        select box can exhaust your connection pool and take down your
⭐        customer-facing API (Days 152, 168).
⭐   ⇒ ⭐⭐ THAT IS THE ARGUMENT FOR **RUNNING THE ADMIN ON A SEPARATE
⭐        DEPLOYMENT** with its own pool and its own workers — Day 152's
⭐        bulkhead, and the single best operational decision you can make here.
```

```python
class OrderAdmin(admin.ModelAdmin):
    list_select_related = ("user", "event")
    raw_id_fields = ("user",)                 # ⭐⭐ or autocomplete_fields
    show_full_result_count = False            # ⭐ skip the expensive COUNT
    list_per_page = 50

    def get_queryset(self, request):
        return super().get_queryset(request).select_related("user", "event")
```

# Part 3 — ⭐⭐ Making it safe

```
⭐⭐ THE FOUR CONTROLS, IN ORDER OF HOW OFTEN THEY ARE MISSING:

⭐  1. ⭐⭐ `readonly_fields` FOR EVERYTHING SERVER-OWNED. ⭐ `total_cents`,
⭐       `status`, `created_at`, `idempotency_key`, `quantity_sold`.
⭐       ⇒ ⭐⭐ This is Day 175's mass-assignment problem again, ⭐ except the
⭐         attacker is your own colleague and the form is fully trusted.
⭐  2. ⭐⭐ REMOVE DELETE UNLESS YOU MEAN IT. `has_delete_permission` →
⭐       `False`. ⭐ A cascade delete from the admin can remove ten thousand
⭐       related rows with one click and a confirmation page that ⭐⭐ lists
⭐       them, which people scroll past.
⭐  3. ⭐⭐ DANGEROUS TRANSITIONS BECOME **ACTIONS**, NOT FIELD EDITS:
⭐          @admin.action(description="Refund selected orders")
⭐          def refund(modeladmin, request, queryset):
⭐              for order in queryset:
⭐                  refund_order(order.id, actor=request.user)   # ⭐⭐ THE SERVICE
⭐       ⇒ ⭐⭐ NOW THE ADMIN GOES THROUGH YOUR DOMAIN: the transaction, the
⭐         outbox, the audit, the provider call. ⭐ And `status` stays
⭐         read-only, so the ONLY way to refund is the correct way.
⭐       ⇒ ⭐ THIS IS THE SINGLE HIGHEST-VALUE PATTERN IN THIS DAY.
⭐  4. ⭐ PERMISSIONS PER MODEL, NOT `is_superuser` FOR EVERYONE. ⭐⭐ Django
⭐       gives you add/change/delete/view per model and Groups to bundle
⭐       them — ⭐ `view` alone is a genuinely useful read-only support role
⭐       and almost nobody uses it.

⭐⭐ AND THE ONES PEOPLE FORGET ENTIRELY:
⭐   ⭐ ⭐⭐ MOVE IT OFF `/admin/`. ⭐ Not security by obscurity as a defence —
⭐        ⭐⭐ it is a 99% reduction in automated credential-stuffing traffic,
⭐        which is a real operational benefit. ⭐ Combine with an IP allow-list
⭐        or requiring a VPN, which IS a real control.
⭐   ⭐ ⭐⭐ MFA ON EVERY ADMIN ACCOUNT (`django-otp`). ⭐ An admin account is a
⭐        full database editor; a password alone is not a proportionate
⭐        control for that.
⭐   ⭐ `is_staff` IS NOT `is_superuser` — ⭐⭐ `is_superuser` bypasses EVERY
⭐        permission check, including ones you wrote. ⭐ Two people, maximum.
⭐   ⭐ ⭐⭐ CHECK WHAT `search_fields` DOES: `search_fields = ("user__email",)`
⭐        on 10M rows is an unindexed `LIKE '%…%'` JOIN — ⭐ Day 176's DoS,
⭐        now behind a login, ⭐⭐ and triggered by a support agent doing their
⭐        job.
```

# Part 4 — ⭐⭐ Audit: what you get and what you don't

```
⭐⭐ `LogEntry` — DJANGO LOGS ADMIN CHANGES AUTOMATICALLY, AND ITS LIMITS
⭐   MATTER:
⭐   ⭐ ✅ who, when, which object, add/change/delete, ⭐ and a change message
⭐        listing WHICH FIELDS changed.
⭐   ⭐ ❌ ⭐⭐ NOT THE OLD AND NEW **VALUES**. ⭐ "changed status" — from what,
⭐        to what? Not recorded.
⭐   ⭐ ❌ ⭐⭐ NOTHING OUTSIDE THE ADMIN. Your API, your services, your
⭐        management commands and your shell are all invisible to it.
⭐   ⭐ ❌ ⭐⭐ BULK ACTIONS OFTEN LOG NOTHING — a `queryset.update()` in a
⭐        custom action bypasses `save()` and `LogEntry` alike (Day 172).
⭐   ⇒ ⭐⭐ SO: `LogEntry` IS A CONVENIENCE, NOT A COMPLIANCE ARTEFACT.
⭐        ⭐ If you need a real trail, use `django-simple-history` or write
⭐        domain events (Day 161) from your SERVICES — ⭐⭐ which is another
⭐        reason to route dangerous admin operations through actions that call
⭐        services.

⭐⭐ AND THE QUESTION THAT COMES UP IN EVERY SUPPORT DISCUSSION:
⭐   ⭐ "CAN SUPPORT SEE CUSTOMER DATA IN THE ADMIN?"
⭐   ⇒ ⭐⭐ THE ADMIN HAS NO CONCEPT OF TENANCY. ⭐ A staff user with `view`
⭐        permission on `Order` sees EVERY organiser's orders (Day 160).
⭐   ⇒ ⭐ To scope it, override `get_queryset(self, request)` per ModelAdmin —
⭐        ⭐⭐ and be aware that Postgres RLS will NOT save you here if the
⭐        admin connects with a role that has `BYPASSRLS` or is the table
⭐        owner (Day 160's `FORCE`). ⭐ Check that explicitly.
⭐   ⇒ ⭐⭐ AND PII: the admin is where support staff read customer emails,
⭐        addresses and payment metadata all day. ⭐ That is a legitimate use
⭐        AND a data-protection surface — ⭐⭐ mask what they do not need
⭐        (`readonly_fields` with a masked display method), and log the reads
⭐        if you are regulated.
```

# Part 5 — ⭐ When to say no

```
⭐⭐ THE ADMIN IS THE RIGHT ANSWER WHEN:
⭐   ⭐ the users are ENGINEERS or trusted internal staff
⭐   ⭐ the operations are genuinely CRUD ("fix this typo", "look this up")
⭐   ⭐ the product is EARLY and a back-office would otherwise not exist
⭐   ⭐ ⭐⭐ it is a READ-ONLY support console — ⭐ `view` permission only, which
⭐        is a huge amount of value at almost zero risk

⭐⭐ IT IS THE WRONG ANSWER WHEN:
⭐   ⭐ ⭐⭐ THE OPERATION IS A BUSINESS PROCESS. "Refund", "cancel event",
⭐        "issue replacement" — ⭐ those have preconditions, side effects and
⭐        an audit requirement. ⭐⭐ They are services with a button, not fields
⭐        with an edit box.
⭐   ⭐ THE USERS ARE NON-TECHNICAL AND HIGH-VOLUME. ⭐⭐ The admin exposes your
⭐        schema; a support agent should see a CUSTOMER, not a row in
⭐        `auth_user` joined to four tables. ⭐ The mismatch causes real
⭐        mistakes, and they are your mistakes.
⭐   ⭐ ⭐⭐ YOU NEED APPROVALS, FOUR-EYES, OR SOFT DELETES. ⭐ The admin has no
⭐        workflow model at all.
⭐   ⭐ THE TABLES ARE HUGE — ⭐ see Part 2; it degrades badly and it degrades
⭐        against production.
⭐
⭐   ⇒ ⭐⭐ THE PROGRESSION MOST PRODUCTS FOLLOW, AND IT IS THE RIGHT ONE:
⭐        ⭐ 1. admin as the whole back-office (months 0–12)
⭐        ⭐ 2. admin locked down: read-only + actions that call services
⭐        ⭐ 3. a purpose-built internal tool for the top five workflows,
⭐             ⭐⭐ with the admin retained for engineers only
⭐   ⇒ ⭐⭐ AND THE DECISION RULE: **IF A NON-ENGINEER PERFORMS IT MORE THAN
⭐        ONCE A DAY, IT WANTS A PURPOSE-BUILT SCREEN.** ⭐ Everything else can
⭐        stay in the admin, forever, and that is fine.

⭐⭐ THE FIVE-LINE SUMMARY:
⭐   ⭐ The admin edits the DATABASE, not your DOMAIN.
⭐   ⭐ Route anything dangerous through an ACTION that calls a SERVICE.
⭐   ⭐ `readonly_fields` for everything server-owned; no delete by default.
⭐   ⭐⭐ It is an N+1 machine pointed at production — `list_select_related`,
⭐        `raw_id_fields`, and ideally its own deployment.
⭐   ⭐ `LogEntry` is a convenience, not an audit trail.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Treating the admin as a customer-facing UI | It exposes your schema, not your product. |
| Editing `status` or `total_cents` directly | It bypasses your service — an order becomes paid with no charge and no ticket. |
| No `readonly_fields` | Mass assignment where the form is fully trusted and the actor is a colleague. |
| Leaving delete enabled | One click cascades through ten thousand related rows. |
| `is_superuser` for the whole team | It bypasses every permission check, including ones you wrote. |
| Never using `view`-only permissions | A read-only support console is enormous value at nearly zero risk. |
| `list_display` with FKs and no `list_select_related` | One query per row per FK — 300 queries for one page. |
| A `list_display` method touching a relation | Not covered by `list_select_related`. Override `get_queryset`. |
| Default FK widgets on large tables | Every related row rendered as an `<option>`. Use `raw_id_fields`. |
| `list_filter` on a high-cardinality column | A `DISTINCT` over the whole table to build the sidebar. |
| Admin sharing workers and pool with the API | A support agent's slow page can exhaust the pool and take down customers. |
| `search_fields` across an unindexed join | An authenticated full-table scan triggered by someone doing their job. |
| Trusting `LogEntry` as an audit trail | No old/new values, nothing outside the admin, and bulk actions often log nothing. |
| Assuming the admin respects tenancy | It has no concept of it. Override `get_queryset` per ModelAdmin. |
| Assuming RLS protects the admin | Not if the admin's role is the table owner or has `BYPASSRLS`. |
| Leaving it on `/admin/` with no MFA | It's a full database editor behind one password. |
| Modelling a business process as field edits | Refunds and cancellations are services with a button. |

## Interview questions

**Q: What's the biggest risk with the Django admin?**

> That it edits the database rather than your domain. It goes through `ModelForm.save()` to
> `Model.save()`, so it completely bypasses your service layer: no transaction boundary you designed,
> no inventory decrement, no outbox row, no idempotency, no audit event. So a support agent setting
> `status = "paid"` marks an order paid without anyone being charged and without a ticket being
> issued — and every downstream system believes it. The fix is structural rather than procedural:
> make server-owned fields `readonly_fields` so that transition is impossible through a form, and
> expose the operation as an admin *action* that calls the same service function the API calls. Then
> the admin goes through your domain, gets the transaction and the audit, and there's only one way to
> refund an order. That pattern is the highest-value thing in this topic.

**Q: Why might the admin take down your API?**

> Because it's an N+1 generator pointed at your production database, usually running on the same
> workers and the same connection pool as your customer traffic. `list_display` with foreign keys is
> a query per row per FK; a foreign key edit widget renders *every* related row as an `<option>`, so
> half a million users is a multi-megabyte page; `list_filter` on a high-cardinality column runs a
> `DISTINCT` across the whole table; and the paginator's `COUNT(*)` on a fifty-million-row table is
> seconds on every page load. So a support agent opening one page can exhaust the pool and take down
> the API. Mitigations are `list_select_related`, `raw_id_fields` or `autocomplete_fields`, and
> `show_full_result_count = False` — but the best operational decision is running the admin as a
> separate deployment with its own pool, which is just a bulkhead.

**Q: Is `LogEntry` an audit trail?**

> It's a convenience, not a compliance artefact, and the gaps matter. It records who, when, which
> object and which fields changed — but not the old and new *values*, so "changed status" doesn't
> tell you from what to what. It records nothing outside the admin, so your API, services, management
> commands and shell sessions are invisible. And bulk actions frequently log nothing at all, because
> a `queryset.update()` bypasses `save()` and `LogEntry` alike. If I need a real trail I'd use
> `django-simple-history` or emit domain events from the services — which is another argument for
> routing dangerous admin operations through actions that call services, since then the audit happens
> in one place regardless of who triggered it.

**Q: When would you build an internal tool instead?**

> My rule is that if a non-engineer performs an operation more than once a day, it wants a
> purpose-built screen. The admin is right for engineers, for genuinely CRUD operations, for an early
> product where the alternative is no back-office at all, and — the underrated case — as a read-only
> support console with `view` permission only, which is a huge amount of value at almost zero risk.
> It's wrong when the operation is a business process with preconditions and side effects, when you
> need approvals or four-eyes or soft deletes since it has no workflow model, and when the users are
> non-technical and high-volume — because the admin shows a row in `auth_user` joined to four tables
> where a support agent needs to see a *customer*, and that mismatch causes real mistakes that are
> ultimately mine.

**Q: Does the admin respect multi-tenancy?**

> No — it has no concept of tenancy at all. A staff user with `view` on `Order` sees every
> organiser's orders. Scoping requires overriding `get_queryset` on each `ModelAdmin`, and the trap
> is assuming row-level security covers you: RLS won't help if the admin connects with the table
> owner's role or a role with `BYPASSRLS`, which is exactly why `FORCE ROW LEVEL SECURITY` exists and
> why you check it explicitly rather than assume. There's also a data-protection dimension —
> the admin is where support staff read customer emails and payment metadata all day, which is
> legitimate and is also a surface, so I'd mask what they don't need with a read-only display method
> and log reads if we're regulated.

## 🎙️ Articulation drill

**Two minutes: "How do you use the Django admin responsibly?"**

Start by giving it real credit — twenty lines for a permissioned, searchable, audited back-office is
weeks of work in any other stack, and it's the strongest single argument for choosing Django. Then
the sentence that reframes it: **it edits the database, not your domain**, so it bypasses your
services, and a status field edited directly marks an order paid with nobody charged. Give the fix as
a pattern rather than a warning: server-owned fields read-only, and dangerous transitions become
actions that call the same service the API calls. Then the operational point that shows you've run
one — it's an N+1 machine pointed at production on the same pool as your customers, so
`list_select_related`, `raw_id_fields`, and ideally its own deployment. Close on the limits:
`LogEntry` isn't an audit trail, the admin has no concept of tenancy, and **if a non-engineer does
it more than once a day, it wants a purpose-built screen.**
