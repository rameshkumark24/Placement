# Day 310 ⚡

**P-310** · ⚡ **Concurrency in LLD** — ⭐⭐ the question that ends most interviews

**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: name the shared mutable state, name the invariant that must hold across
> it, then pick the cheapest mechanism that holds it — and if there is no shared mutable state, say
> so, because "there is no concurrency problem here, and here is why" is a complete answer.**
>
> ⭐ "What if two users do this at the same time?" is asked in almost every LLD interview. ⭐⭐ Most
> candidates have designed as if single-threaded and have no framework for answering it.

---

# Part 1 — ⭐⭐ The three questions, in order

```
⭐⭐ ① ***WHAT IS THE SHARED MUTABLE STATE?***
⭐   ⭐ Not "is this thread-safe" — ⭐⭐ WHAT SPECIFICALLY IS
⭐     BOTH SHARED AND MUTATED? ⭐ A spot's occupancy. A
⭐     counter. A cached dict. A file handle.
⭐   ⇒ ⭐⭐ IF THE ANSWER IS "NOTHING", YOU ARE DONE, AND
⭐     SAYING SO CONFIDENTLY IS A ***STRONG*** ANSWER. ⭐ Most
⭐     candidates reach for a lock reflexively, which signals
⭐     that they cannot tell the difference.

⭐⭐ ② ***WHAT INVARIANT MUST HOLD ACROSS IT?***
⭐   ⭐ "At most one vehicle per spot." "The count never exceeds
⭐     capacity." ⭐⭐ THE INVARIANT IS WHAT YOU ARE
⭐     PROTECTING — not the variable.
⭐   ⇒ ⭐ Stating it makes the next step mechanical, because the
⭐     mechanism is chosen to hold ***that sentence***.

⭐⭐ ③ ***WHAT IS THE CHEAPEST MECHANISM THAT HOLDS IT?***
⭐   ⭐ And "cheapest" means least contention and least
⭐     coordination — ⭐⭐ NOT LEAST TYPING. Part 2 is the
⭐     ordered menu.
```

---

# Part 2 — ⭐⭐ The four options, in order of preference

```
⭐⭐ ① ***DON'T SHARE.*** ⭐ Per-request state, per-thread
⭐     objects, a copy instead of a reference.
⭐   ⇒ ⭐ A pure function has no concurrency problem, ever.
⭐   ⭐⭐ THE BEST CONCURRENCY DESIGN IS THE ONE WHERE THE
⭐     QUESTION DOES NOT ARISE, and a surprising amount of
⭐     "thread safety" work is repairing sharing that was never
⭐     necessary.

⭐⭐ ② ***IMMUTABILITY.*** ⭐ A frozen dataclass (Day 304) can
⭐     be read by any number of threads forever, with no lock,
⭐     no reasoning and no bugs.
⭐   ⇒ ⭐ Mutation becomes "replace the reference", which is a
⭐     single atomic assignment.

⭐⭐ ③ ***A SINGLE ATOMIC OPERATION.*** ⭐ Compare-and-swap; a
⭐     conditional `UPDATE … WHERE status = 'free'` (Day 296);
⭐     `INSERT` relying on a unique constraint.
⭐   ⇒ ⭐⭐ THE DATABASE OPTION IS THE ONE PEOPLE FORGET IN LLD
⭐     INTERVIEWS, AND IT IS USUALLY THE RIGHT ANSWER for
⭐     anything persistent: ⭐ no lock in your code at all, and
⭐     it works across processes for free.

⭐⭐ ④ ***A LOCK*** — ⭐ last, because it is the only option
⭐     that introduces contention, deadlock and priority
⭐     problems.
⭐   ⇒ ⭐ And when you do use one: ⭐⭐ HOLD IT FOR THE
⭐     SHORTEST POSSIBLE TIME, AND ***NEVER*** ACROSS I/O.
⭐     ⭐ A lock held across a network call is Day 256's rule in
⭐       a smaller room.
```

# Part 3 — ⭐⭐ Python specifics interviewers probe

```
⭐⭐ THE GIL — WHAT IT DOES AND DOES NOT DO:
⭐   ⭐ It ensures only one thread executes Python bytecode at
⭐     a time. ⭐⭐ IT DOES ***NOT*** MAKE YOUR CODE THREAD-SAFE.
⭐   ⭐ `counter += 1` is LOAD, ADD, STORE — ⭐⭐ THREE
⭐     BYTECODES, AND A THREAD SWITCH CAN HAPPEN BETWEEN THEM,
⭐     SO INCREMENTS ARE LOST. ⭐ This is the single most
⭐     common misconception, and it is worth being able to say
⭐     crisply.
⭐   ⭐ `list.append()` ***is*** atomic, because it is one
⭐     bytecode into C code that does not release the GIL —
⭐     ⭐ so a list is a safe queue-ish thing and a counter is
⭐     not, which surprises people.
⭐   ⇒ ⭐⭐ RELYING ON WHICH OPERATIONS HAPPEN TO BE ATOMIC IS
⭐     A BAD BET ANYWAY: it is CPython-specific, it changes,
⭐     and ⭐⭐ FREE-THREADED PYTHON REMOVES THE GUARANTEE
⭐     ENTIRELY.

⭐⭐ SO WHICH CONCURRENCY MODEL:
⭐   ⭐ THREADS — ⭐ good for I/O-bound work; the GIL is
⭐        released during I/O, so they genuinely overlap.
⭐   ⭐ PROCESSES — ⭐ for CPU-bound work; no shared memory, so
⭐        the concurrency problem becomes an IPC problem.
⭐   ⭐⭐ asyncio — SINGLE-THREADED, and ⭐⭐ THE INTERLEAVING
⭐        POINTS ARE ***ONLY*** AT `await`. ⭐ Which makes
⭐        reasoning dramatically easier: between two `await`s
⭐        nothing else runs, so a check-then-act with no `await`
⭐        between the check and the act is atomic.
⭐        ⇒ ⭐⭐ AND THE CORRESPONDING TRAP: ***PUT AN `await`
⭐          BETWEEN THE CHECK AND THE ACT AND THE RACE IS
⭐          BACK***, which is exactly how async races are
⭐          introduced — by someone adding a perfectly
⭐          reasonable `await` to existing code.
```

# Part 4 — ⭐ The lock catalogue

```
⭐   ⭐ `Lock` — ⭐ the default. One holder.
⭐   ⭐ `RLock` — re-entrant. ⭐⭐ NEEDING ONE IS USUALLY A
⭐        DESIGN SMELL: it means a locked method calls another
⭐        locked method, so your locking boundary is drawn in
⭐        two places at once.
⭐   ⭐ `Semaphore(n)` — ⭐ a bounded resource: N connections,
⭐        N concurrent uploads. ⭐ The right tool for rate and
⭐        capacity, and under-used.
⭐   ⭐ `Condition` — ⭐ wait until a state is reached. ⭐⭐
⭐        ALWAYS `while not condition: wait()`, NEVER `if` —
⭐        because a wakeup does not guarantee the condition
⭐        still holds when you get the lock back.
⭐   ⭐ `Event` — a one-shot flag; simple and often enough.
⭐   ⭐⭐ `queue.Queue` — ⭐⭐ THE ONE THAT REPLACES MOST LOCKS.
⭐        ⭐ Hand work between threads instead of sharing state,
⭐        and the locking is somebody else's problem, correctly
⭐        implemented. ⭐ In an interview, "I'd use a queue and
⭐        avoid the shared structure entirely" is a strong answer.
```

# Part 5 — ⭐⭐ The four classic bugs, named

```
⭐⭐ ① CHECK-THEN-ACT — ⭐ the parking lot's last spot.
⭐     if spot.is_free:        # ⭐⭐ thread B checks HERE
⭐         spot.occupy(car)    # ⭐ both proceed
⭐   ⇒ ⭐ FIX: make the check and the act ONE operation —
⭐     ⭐⭐ `if spot.try_occupy(car):` returning a bool, backed
⭐     by a lock, a CAS, or a conditional UPDATE.
⭐   ⇒ ⭐⭐ THIS IS THE SAME BUG AS THE OVERSELL (Day 296), THE
⭐     DOUBLE BOOKING (Day 250) AND THE IDEMPOTENCY RACE
⭐     (Day 260). ⭐ Recognising it as one bug in four costumes
⭐     is most of what this day is for.

⭐⭐ ② LOST UPDATE — ⭐ read 5, both add 1, write 6, one
⭐     increment vanished.
⭐   ⇒ ⭐ FIX: atomic increment, or `UPDATE … SET n = n + 1`
⭐     which does the arithmetic in the database.

⭐⭐ ③ DEADLOCK — ⭐ A holds spot lock and wants ticket lock;
⭐     B holds ticket and wants spot.
⭐   ⇒ ⭐⭐ FIX: A GLOBAL LOCK ORDER, STATED AND DOCUMENTED —
⭐     "always acquire in id order". ⭐ Same fix as Day 196's
⭐     database deadlocks, which is not a coincidence.
⭐   ⇒ ⭐ And timeouts, so a deadlock degrades into an error
⭐     rather than a hang.

⭐⭐ ④ THE DOUBLE-CHECKED LOCK PEOPLE WRITE WRONGLY:
⭐     if self._x is None:
⭐         with self._lock:
⭐             self._x = expensive()   # ⭐⭐ NO SECOND CHECK
⭐   ⇒ ⭐ Two threads both pass the outer check, both build it.
⭐     ⭐⭐ THE SECOND CHECK ***INSIDE*** THE LOCK IS THE ENTIRE
⭐     POINT OF THE PATTERN, AND IT IS THE PART THAT GETS
⭐     OMITTED. ⭐ In Python, prefer `functools.cache` or a
⭐     module-level constant and skip the pattern.
```

# Part 6 — ⭐⭐ The moment an in-process lock becomes wrong

```
⭐⭐ THE TRANSITION THAT SEPARATES LLD FROM SYSTEM DESIGN, AND
⭐   INTERVIEWERS PROBE IT DELIBERATELY:
⭐   ⭐ Your `threading.Lock` protects the invariant perfectly
⭐     — ⭐⭐ IN ***ONE PROCESS***.
⭐   ⭐ You run two replicas (Day 284). ⭐⭐ THERE ARE NOW TWO
⭐     LOCKS, EACH PERFECTLY PROTECTING NOTHING.
⭐   ⇒ ⭐ And the failure is silent: the code is unchanged, the
⭐     tests still pass, ⭐⭐ AND THE BUG APPEARS ONLY UNDER
⭐     PRODUCTION CONCURRENCY ON MORE THAN ONE MACHINE.

⭐⭐ THE THREE ANSWERS, IN ORDER:
⭐   ① ⭐⭐ PUSH THE INVARIANT INTO THE DATABASE — a unique
⭐        constraint, an `EXCLUDE` (Day 250), or a conditional
⭐        `UPDATE` whose affected-row count is the answer.
⭐        ⇒ ⭐⭐ ALWAYS PREFER THIS. It is correct across any
⭐          number of processes, it survives a restart, and it
⭐          cannot be bypassed by a script.
⭐   ② ⭐ `SELECT … FOR UPDATE` on the row — ⭐ correct, and it
⭐        serialises access to that row, which is sometimes what
⭐        you want and sometimes a bottleneck (Day 196).
⭐   ③ ⭐ A DISTRIBUTED LOCK (Day 207) — ⭐⭐ THE LAST RESORT,
⭐        and say why: it needs a TTL, it needs fencing tokens,
⭐        and ***the token protects the release, not the
⭐        critical section***. ⭐ Reaching for Redis first, when
⭐        a unique constraint would do, is the mistake.

⭐ ⇒ ⭐⭐ SAYING THIS UNPROMPTED — "THIS LOCK IS CORRECT IN ONE
⭐   PROCESS; IF WE RUN TWO, I'D MOVE THE INVARIANT INTO A
⭐   CONSTRAINT" — IS ONE OF THE HIGHEST-VALUE SENTENCES IN AN
⭐   LLD INTERVIEW, because it shows you know where the design
⭐   stops being local.
```

# Part 7 — ⭐ Answering it live

```
⭐   ⭐ THE SCRIPT, IN FOUR SENTENCES:
⭐     ① ⭐ "The shared mutable state is X."
⭐     ② ⭐ "The invariant is Y."
⭐     ③ ⭐ "The cheapest mechanism that holds it is Z, because…"
⭐     ④ ⭐⭐ "AT MULTI-PROCESS SCALE THAT BECOMES W."
⭐   ⇒ ⭐ Four sentences, thirty seconds, ⭐⭐ AND IT IS A
⭐     COMPLETE ANSWER TO A QUESTION MOST CANDIDATES ANSWER
⭐     WITH "I'D ADD A LOCK".

⭐   ⭐ AND THE TEST YOU OFFER TO WRITE: ⭐⭐ N THREADS, ONE
⭐     RESOURCE, ***ASSERT EXACTLY ONE SUCCEEDS*** (Day 261).
⭐     ⭐ Not "at most one" — ⭐⭐ `<= 1` PASSES WHEN A BUG
⭐     REJECTS EVERYTHING, which is the assertion mistake that
⭐     hides a real defect.
⭐   ⭐ Offering that test unprompted is worth more than the
⭐     mechanism you chose.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Reaching for a lock reflexively | First ask what is shared and mutated; sometimes the answer is nothing. |
| Protecting a variable instead of an invariant | The invariant is what you're holding; state it and the mechanism follows. |
| "Cheapest" meaning least typing | It means least contention and coordination. |
| Believing the GIL makes code thread-safe | `counter += 1` is three bytecodes and loses increments. |
| Relying on which operations are atomic | CPython-specific, changeable, and free-threaded Python removes it. |
| Threads for CPU-bound work | The GIL serialises bytecode; use processes. |
| Assuming async removes races | Every `await` is an interleaving point; adding one between check and act restores the race. |
| Reaching for `RLock` | It usually means your locking boundary is drawn in two places. |
| `if` instead of `while` around `Condition.wait()` | A wakeup doesn't guarantee the condition still holds. |
| Sharing a structure when a queue would do | Hand work over instead; the locking becomes someone else's, correctly done. |
| Not recognising check-then-act | It's the oversell, the double booking and the idempotency race in one. |
| Read-modify-write in Python | Do the arithmetic in the database: `SET n = n + 1`. |
| No global lock ordering | Deadlock, and it's the same fix as database deadlocks. |
| Holding a lock across I/O | The same rule as never calling a network inside a transaction. |
| Double-checked locking with no second check | The second check is the entire pattern. |
| An in-process lock in a multi-process system | Two locks, each protecting nothing, and the tests still pass. |
| A distributed lock as the first answer | Prefer a constraint; a distributed lock needs TTLs and fencing. |
| `assert count <= 1` in a race test | It passes when a bug rejects everything. Assert exactly one. |

## Interview questions

**Q: What if two users do this at the same time?**

> I'd answer in four sentences. The shared mutable state is the spot's occupancy. The invariant is at
> most one vehicle per spot. The cheapest mechanism that holds it is making the check and the act one
> operation — `try_occupy()` returning a boolean, backed by a conditional update whose affected-row
> count is the answer. And at multi-process scale that becomes a database constraint rather than an
> in-process lock. That last sentence is the one I'd make sure to say, because it's where the design
> stops being local.

**Q: Does the GIL make Python thread-safe?**

> No, and this is the most common misconception. It guarantees one thread executes bytecode at a time,
> which is not the same as making your operations atomic — `counter += 1` is a load, an add and a
> store, and a thread switch between them loses increments. Some operations happen to be atomic,
> like `list.append`, because they're a single bytecode into C, but relying on that is a bad bet:
> it's CPython-specific, it changes between versions, and free-threaded Python removes the guarantee
> entirely. So threads for I/O-bound work, processes for CPU-bound, and explicit synchronisation
> either way.

**Q: Does asyncio avoid all this?**

> It makes it much easier to reason about, because it's single-threaded and the only interleaving
> points are `await` expressions — so a check-then-act with no `await` between the check and the act
> is genuinely atomic. But that's also the trap: the race comes back the moment someone adds a
> perfectly reasonable `await` between them, which is exactly how async races get introduced. And it
> does nothing at all for multi-process concurrency, so any invariant that must hold across replicas
> still needs the database.

**Q: You've used a `threading.Lock`. What happens when we run two replicas?**

> There are now two locks, each perfectly protecting nothing — and the failure is silent, because the
> code is unchanged and the tests still pass; it only appears under production concurrency across
> machines. Three answers in order: push the invariant into the database as a unique constraint, an
> `EXCLUDE` constraint or a conditional update, which is correct for any number of processes and can't
> be bypassed by a script; `SELECT FOR UPDATE` on the row if I genuinely need to serialise access to
> it; and a distributed lock only as a last resort, with the caveat that it needs a TTL and fencing
> tokens, because the token protects the release rather than the critical section.

**Q: How would you test it?**

> N threads contending for one resource, asserting that *exactly* one succeeds — not "at most one",
> because `<= 1` passes when a bug rejects everything, which is the assertion mistake that hides a
> real defect. Against real Postgres if the invariant lives in the database, because SQLite ignores
> `FOR UPDATE` and has no `EXCLUDE`, so the test would pass and prove nothing. Offering that test
> unprompted is usually worth more than the mechanism I picked.

## 🎙️ Articulation drill

**Two minutes: "How do you handle concurrency in a design?"**

Give the framework first, because it's what most candidates lack: **name the shared mutable state,
name the invariant over it, pick the cheapest mechanism that holds it, then say what changes at
multi-process scale.** Note that if there's no shared mutable state, saying so confidently is a
complete answer — reaching for a lock reflexively signals you can't tell the difference. Then the
menu in order: **don't share, be immutable, use one atomic operation, and only then a lock** — and
flag the option people forget in interviews, which is the database: a conditional `UPDATE` whose
affected-row count is the answer needs no lock in your code and works across processes for free. Cover
the Python specifics crisply: **the GIL doesn't make you thread-safe, because `counter += 1` is three
bytecodes**, and relying on which operations happen to be atomic is CPython-specific and disappears
with free-threading. For asyncio, **the only interleaving points are `await`s, which makes reasoning
easy — and the trap is that adding a reasonable `await` between a check and an act restores the
race.** Name check-then-act as one bug in four costumes: the oversell, the double booking, the
idempotency race. Close on the transition that separates LLD from system design: **at two replicas
your lock becomes two locks, each protecting nothing, and the tests still pass** — so push the
invariant into a constraint, and offer the test that asserts *exactly* one success, because `<= 1`
passes when a bug rejects everything.
