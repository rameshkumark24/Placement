# Part 1 — ⭐ What replication is actually for

```
⭐⭐ FOUR REASONS, AND THEY WANT DIFFERENT SETUPS:
⭐   ① ⭐ READ SCALING — N replicas, N× read capacity.
⭐        ⇒ ⭐⭐ AND NOT WRITE CAPACITY. Every replica applies
⭐          ***every*** write. ⭐⭐ TEN REPLICAS DO NOT GIVE YOU
⭐          MORE WRITE THROUGHPUT; THEY GIVE YOU TEN COPIES OF
⭐          THE SAME WRITE LOAD. ⭐ That is Day 329's job.
⭐   ② ⭐⭐ HIGH AVAILABILITY — a standby to promote.
⭐   ③ ⭐ GEOGRAPHY — a replica near the user (Day 323's 150 ms).
⭐   ④ ⭐ ISOLATION — run analytics somewhere that cannot hurt
⭐        the primary. ⭐ (Careful: Day 265's `hot_standby_
⭐        feedback` makes long replica queries bloat the
⭐        ***primary***.)

⭐⭐ AND WHAT IT IS NOT FOR: ⭐⭐ A REPLICA IS NOT A BACKUP.
⭐   ⭐ `DELETE FROM orders;` replicates in milliseconds.
⭐   ⭐ A dropped table replicates. Corruption replicates.
⭐   ⇒ ⭐⭐ REPLICATION PROTECTS AGAINST HARDWARE FAILURE. ONLY
⭐     POINT-IN-TIME BACKUPS PROTECT AGAINST ***PEOPLE***.
```

# Part 2 — ⭐⭐ Three topologies

```
⭐⭐ ① SINGLE-LEADER (primary/replica) — ⭐⭐ USE THIS.
⭐   ⭐ All writes to one node; replicas are read-only.
⭐   ⭐ ✔ No write conflicts, ever. The hard problem is deleted
⭐     rather than solved.
⭐   ⭐ ✘ The leader is a write bottleneck and a failover event.
⭐   ⇒ ⭐ Postgres, MySQL, MongoDB, Redis, and ~95% of systems
⭐     you will ever build.

⭐⭐ ② MULTI-LEADER — writes accepted in several regions.
⭐   ⭐ ✔ Local write latency, survives a region.
⭐   ⭐ ✘ ⭐⭐ WRITE CONFLICTS ARE NOW ***YOUR*** PROBLEM, and
⭐     there is no correct generic answer — LWW loses data,
⭐     CRDTs constrain your data model, manual merge needs a
⭐     human.
⭐   ⇒ ⭐ Legitimate for: offline-capable clients, calendars,
⭐     collaborative editing (Day 354). ⭐⭐ NOT FOR MONEY.

⭐⭐ ③ LEADERLESS (Dynamo-style) — client writes to N, waits
⭐   for W acks; reads query R.
⭐   ⭐ ⭐⭐ IF W + R > N, A READ SET AND A WRITE SET MUST
⭐     OVERLAP, SO A READ SEES THE LATEST WRITE. That is the
⭐     whole quorum idea, in one line.
⭐   ⭐ N=3, W=2, R=2 is the canonical setting.
⭐   ⭐ ✘ Needs read repair, anti-entropy, and version vectors
⭐     to detect concurrent writes.
⭐   ⇒ ⭐ Cassandra, DynamoDB, Riak. ⭐ Day 348 builds one.
⭐   ⇒ ⭐⭐ AND THE CAVEAT MOST PEOPLE MISS: W+R>N DOES ***NOT***
⭐     GIVE LINEARIZABILITY. ⭐ Concurrent writes, sloppy quorums
⭐     and hinted handoff all break it — ⭐ it gives you a good
⭐     chance of freshness, not a guarantee.
```

# Part 3 — ⭐⭐ Sync vs async, and the write you lose

```
⭐⭐ ASYNCHRONOUS: leader commits, acks the client, ships the
⭐   log afterwards.
⭐   ⭐ ✔ Fast writes. ✔ A slow replica cannot stall you.
⭐   ⭐ ✘ ⭐⭐ IF THE LEADER DIES BEFORE SHIPPING, THOSE
⭐     COMMITTED, ACKNOWLEDGED WRITES ARE ***GONE***.
⭐   ⇒ ⭐⭐ THE USER SAW "PAYMENT CONFIRMED". THE NEW LEADER HAS
⭐     NO RECORD OF IT. ⭐ Nothing errored. Nothing alerted.

⭐⭐ SYNCHRONOUS: leader waits for replica ack before committing.
⭐   ⭐ ✔ No data loss on failover.
⭐   ⭐ ✘ ⭐⭐ EVERY WRITE NOW PAYS A NETWORK ROUND TRIP, ***AND
⭐     IF THE REPLICA IS DOWN, WRITES BLOCK.*** ⭐ You made
⭐     durability better and availability worse. That is not a
⭐     bug, it is the trade (Day 330).

⭐⭐ SEMI-SYNCHRONOUS — ⭐⭐ THE ANSWER IN PRACTICE:
⭐   ⭐ One synchronous replica, the rest async.
⭐   ⭐ Postgres: `synchronous_standby_names = 'ANY 1 (r1, r2)'`
⭐     with `synchronous_commit = on`.
⭐   ⇒ ⭐ Survives one node loss with zero data loss, and does
⭐     not block if a *particular* replica is down.

⭐⭐ THE KNOB WORTH KNOWING BY NAME:
⭐   ⭐ `synchronous_commit = off` on the ***primary*** means
⭐     ⭐⭐ THE COMMIT RETURNS BEFORE THE LOCAL WAL IS FSYNCED.
⭐     ⭐ You can lose a few hundred ms of committed transactions
⭐     on a crash — ⭐⭐ WITH NO REPLICATION INVOLVED AT ALL.
⭐   ⇒ ⭐ Legitimate for a metrics table. ⭐⭐ NEVER FOR A LEDGER.
⭐   ⇒ ⭐ And it is a per-transaction setting, ⭐⭐ WHICH IS THE
⭐     GOOD ANSWER: fast and lossy for events, durable for money,
⭐     in the same database.
```

# Part 4 — ⭐⭐ The three anomalies — the heart of the day

```
⭐⭐ ANOMALY ① — ***READ-YOUR-OWN-WRITES*** (read-after-write)
⭐   ⭐ User edits their profile ⇒ write to leader.
⭐   ⭐ Page reloads ⇒ read hits a replica 200 ms behind.
⭐   ⇒ ⭐⭐ THE USER SEES THEIR OLD NAME AND CONCLUDES THE SAVE
⭐     FAILED. ⭐ They press save again. Now you have two.
⭐   ⇒ FIXES, WORST TO BEST:
⭐      ⭐ (a) Read from the leader for 30 s after any write —
⭐          crude, effective, ⭐ and it works.
⭐      ⭐ (b) Read from the leader for ***that user's own***
⭐          data only.
⭐      ⭐ (c) ⭐⭐ TOKEN-BASED: the write returns the leader's
⭐          LSN; the client sends it back; the replica waits
⭐          until it has applied ≥ that LSN.
⭐          ⇒ ⭐⭐ THIS IS THE PROPER ANSWER AND IT IS EXACTLY
⭐            HOW DYNAMODB'S ConsistentRead AND POSTGRES'S
⭐            `pg_wal_lsn_diff` PLUMBING ARE USED IN PRACTICE.

⭐⭐ ANOMALY ② — ***MONOTONIC READS***
⭐   ⭐ Read 1 hits replica A (fresh): comment appears.
⭐   ⭐ Read 2 hits replica B (stale): comment gone.
⭐   ⇒ ⭐⭐ THE USER WATCHES TIME RUN BACKWARDS. ⭐ This is more
⭐     alarming to users than plain staleness, and it is caused
⭐     purely by ***load balancing across replicas.***
⭐   ⇒ ⭐ FIX: pin a user to one replica (hash their id) — ⭐ and
⭐     note the Day 324 caveat: this pin must be re-derivable,
⭐     not a sticky session.

⭐⭐ ANOMALY ③ — ***CONSISTENT PREFIX READS***
⭐   ⭐ A asks "how far are you?"; B replies "about a mile".
⭐   ⭐ A reader sees B's reply ***before*** A's question.
⭐   ⇒ ⭐⭐ CAUSALITY VIOLATED. ⭐ Happens when related writes
⭐     land on different partitions replicating at different
⭐     speeds — ⭐⭐ SO IT IS A ***SHARDING*** ANOMALY THAT SHOWS
⭐     UP AS A REPLICATION ONE.
⭐   ⇒ ⭐ FIX: keep causally related writes in one partition
⭐     (same conversation ⇒ same shard), or carry causal
⭐     metadata.
```

```python
# ⭐⭐ (a) IN PRACTICE — THE 30-SECOND LEADER STICKINESS
async def get_session(user_id: str) -> AsyncSession:
    if await redis.exists(f"wrote:{user_id}"):   # ⭐ set on write
        return leader_session()                  # ⭐⭐ ANOMALY ① GONE
    return replica_session(pick=hash(user_id))   # ⭐⭐ ANOMALY ② GONE
# ⭐ Two lines, both anomalies, and it is honest about being a
# ⭐ heuristic — the LSN token version is the rigorous one.
```

# Part 5 — ⭐⭐ Replication lag: measuring the right thing

```
⭐⭐ TWO KINDS OF LAG, AND PEOPLE MONITOR THE WRONG ONE:
⭐   ⭐ ***BYTE LAG*** — how much WAL is unapplied.
⭐     `pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)`
⭐     ⇒ ⭐ Useful, but 40 MB means nothing to a human.
⭐   ⭐ ⭐⭐ ***TIME LAG*** — how old is the newest applied
⭐     transaction. `now() - pg_last_xact_replay_timestamp()`
⭐     ⇒ ⭐⭐ THIS IS THE ONE THAT MAPS TO USER EXPERIENCE, AND
⭐       THE ONE YOUR SLO SHOULD USE (Day 322's freshness SLI).

⭐⭐ THE TRAP: ⭐⭐ ON AN IDLE PRIMARY, TIME LAG GROWS EVEN
⭐   THOUGH THE REPLICA IS PERFECTLY CAUGHT UP — there is simply
⭐   no newer transaction. ⭐ Alert on time lag ***only when the
⭐   primary is writing***, or you page at 4 a.m. every Sunday.

⭐⭐ WHY LAG SPIKES — FOUR CAUSES, IN ORDER OF FREQUENCY:
⭐   ① ⭐⭐ A LONG-RUNNING QUERY ON THE REPLICA BLOCKS REPLAY.
⭐        ⭐ Replay needs a lock the analytics query holds.
⭐        ⇒ ⭐ `max_standby_streaming_delay` decides who wins:
⭐          cancel the query, or let lag grow.
⭐   ② ⭐ A bulk write on the primary (a migration, a backfill).
⭐        ⇒ ⭐ Day 260's batching is a replication-lag control,
⭐          not just a lock-duration one.
⭐   ③ ⭐⭐ SINGLE-THREADED REPLAY. ⭐ The primary writes with 32
⭐        concurrent connections; the replica may replay with
⭐        far less parallelism. ⭐⭐ SO A REPLICA CAN FALL BEHIND
⭐        WHILE HAVING IDLE CPU.
⭐   ④ ⭐ Network saturation, or a slow replica disk.
```

# Part 6 — ⭐⭐ Failover: five steps and four ways it goes wrong

```
⭐⭐ THE STEPS:
⭐   ① Detect the leader is dead (⭐ timeout — ⭐⭐ AND YOU
⭐      CANNOT DISTINGUISH "DEAD" FROM "SLOW", WHICH IS DAY 330
⭐      AND DAY 343 IN A SENTENCE).
⭐   ② Choose a new leader — ⭐ the most up-to-date replica.
⭐   ③ Reconfigure clients to write to it.
⭐   ④ Reconfigure the other replicas to follow it.
⭐   ⑤ Handle the old leader when it returns.

⭐⭐ FAILURE ① — ***LOST WRITES.*** Async replication + the
⭐   promoted replica was behind ⇒ acknowledged writes vanish.
⭐   ⇒ ⭐⭐ AND WORSE: WHEN THE OLD LEADER RETURNS AND IS
⭐     REJOINED, ITS EXTRA WRITES ARE USUALLY ***DISCARDED*** —
⭐     silently. ⭐ GitHub's well-known incident was this shape:
⭐     discarded primary-key ranges that had already been handed
⭐     to users, so IDs then collided.

⭐⭐ FAILURE ② — ***SPLIT BRAIN.*** The old leader did not know
⭐   it was replaced and keeps accepting writes.
⭐   ⇒ ⭐⭐ TWO PRIMARIES, DIVERGENT DATA, AND A MANUAL MERGE
⭐     THAT NOBODY WANTS TO DO.
⭐   ⇒ ⭐ FIX: fencing (STONITH), a lease with an expiry, or a
⭐     fencing token (Day 343). ⭐⭐ THE PRINCIPLE: ***THE OLD
⭐     LEADER MUST BE MADE UNABLE TO WRITE, NOT MERELY ASKED
⭐     TO STOP.***

⭐⭐ FAILURE ③ — ***TIMEOUT TUNING IS A GENUINE DILEMMA.***
⭐   ⭐ Too short ⇒ a GC pause or a network blip triggers an
⭐     unnecessary failover, ⭐⭐ AND FAILOVERS THEMSELVES CAUSE
⭐     OUTAGES.
⭐   ⭐ Too long ⇒ you are down while you wait.
⭐   ⇒ ⭐ There is no correct value; there is only a choice you
⭐     should be able to defend.

⭐⭐ FAILURE ④ — ***THE CLIENTS DON'T FIND OUT.*** ⭐ DNS TTLs,
⭐   cached connections, a pool full of sockets to a dead host.
⭐   ⇒ ⭐⭐ THIS IS THE ONE THAT ACTUALLY BITES PYTHON SERVICES:
⭐     SQLAlchemy holds pooled connections to the old primary
⭐     and keeps handing them out. ⭐ You need `pool_pre_ping=
⭐     True`, a sane `pool_recycle`, and ⭐⭐ TO POINT AT A
⭐     FAILOVER ENDPOINT RATHER THAN AN INSTANCE ADDRESS.
⭐     ⭐ Day 385 has the DNS-caching version of this trap.
```

# Part 7 — ⭐ Routing reads and writes in a Python app

```
⭐⭐ THE ROUTING RULES, IN PRIORITY ORDER:
⭐   ① ⭐⭐ ANY TRANSACTION CONTAINING A WRITE ⇒ LEADER, WHOLE.
⭐        ⭐ Never split a transaction across nodes.
⭐   ② ⭐⭐ ANY READ THAT A WRITE DEPENDS ON ⇒ LEADER. ⭐ The
⭐        check-then-act read (Day 310) on a replica is a
⭐        correctness bug wearing a performance costume.
⭐   ③ ⭐ Read-your-own-writes window ⇒ leader (Part 4).
⭐   ④ ⭐ Everything else ⇒ replica.
⭐   ⑤ ⭐ Reports and exports ⇒ a ***dedicated*** replica, so a
⭐        20-minute query cannot lag the one serving users.

⭐⭐ AND THE ARCHITECTURAL POINT WORTH MAKING ALOUD:
⭐   ***ROUTING BELONGS AT THE SESSION FACTORY, NOT SPRINKLED
⭐      THROUGH REPOSITORIES.*** ⭐ One place decides; the
⭐   repositories (Day 301) never know. ⭐⭐ IF YOUR ANSWER TO
⭐   "WHICH DB DOES THIS QUERY USE?" REQUIRES READING FIFTY
⭐   FILES, THE DESIGN IS WRONG.
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ "Replicas scale writes" | Every replica applies every write. Read capacity only. Sharding is the write answer |
| ⭐⭐ Treating a replica as a backup | `DROP TABLE` replicates in milliseconds. Only PITR protects against people |
| ⭐⭐ Async replication with a promoted stale replica | Acknowledged writes vanish, and the old leader's extras get discarded on rejoin |
| ⭐ Fully synchronous replication | One replica down means all writes block. You traded availability for durability by accident |
| ⭐⭐ Reading a check-then-act value from a replica | A correctness bug dressed as a performance win |
| ⭐ Alerting on byte lag | 40 MB means nothing. Time lag maps to user experience |
| ⭐ Alerting on time lag from an idle primary | Lag grows because nothing is happening. You'll page every Sunday |
| ⭐⭐ No fencing on failover | Split brain. The old leader must be *unable* to write, not asked to stop |
| ⭐ Connecting to an instance address | The pool keeps handing out sockets to a dead primary. Failover endpoint + `pool_pre_ping` |
| ⭐ Read routing scattered across repositories | Nobody can answer which node a query used |
| ⭐⭐ Assuming W+R>N gives linearizability | It gives a good chance of freshness. Concurrent writes and sloppy quorums break it |

## Interview questions

**1. "You added five read replicas and writes are still slow. Why?"**
> ⭐⭐ Because replication doesn't scale writes — every replica applies every write, so I've created
> five copies of the same write load plus the WAL shipping to pay for. ⭐ Read replicas fix read
> capacity. ⭐⭐ Write throughput is a partitioning problem, which is tomorrow — **and before I shard
> anything I'd check whether the writes are slow because of an index, a lock, or a fsync setting,
> because usually they are.**

**2. "Name the anomalies a read replica introduces."**
> ⭐ Three. **Read-your-own-writes** — you save your profile and the reload shows the old name, so
> users save twice. **Monotonic reads** — successive reads hit different replicas and the user watches
> time run backwards, which alarms people more than plain staleness. ⭐⭐ And **consistent prefix** — a
> reply appears before the question, which is really a sharding anomaly showing up as a replication
> one, because the two writes live on partitions replicating at different speeds.

**3. "How do you fix read-your-own-writes?"**
> ⭐ Crudely and effectively: route that user to the leader for thirty seconds after any write, keyed
> in Redis. ⭐⭐ Properly: the write returns the leader's LSN, the client carries it, and the replica
> waits until it has replayed at least that far — **that's the token approach, and it's what
> DynamoDB's consistent read is doing conceptually.** ⭐ The middle option is leader reads for that
> user's own data only.

**4. "Sync or async replication?"**
> ⭐ Semi-synchronous — one synchronous standby, the rest async. ⭐⭐ Fully async loses acknowledged
> writes on failover; fully synchronous means one dead replica blocks every write, **which is trading
> availability for durability without meaning to.** ⭐ And in Postgres I'd note that
> `synchronous_commit` is per-transaction, so the ledger can be durable and the metrics table can be
> fast in the same database.

**5. "Walk me through what goes wrong during failover."**
> ⭐ Detection can't distinguish dead from slow, so the timeout is a genuine dilemma — too short and a
> GC pause triggers a failover, and failovers cause outages. ⭐⭐ Then lost writes if the promoted
> replica was behind, **and the nastier version where the old leader rejoins and its extra writes are
> discarded silently** — that's the GitHub incident shape, where already-issued IDs got reused. ⭐ Then
> split brain if the old leader isn't fenced. ⭐⭐ And the one that actually bites Python services:
> the connection pool keeps handing out sockets to the dead primary, so you need `pool_pre_ping` and a
> failover endpoint rather than an instance address.

**6. "Explain W + R > N."**
> ⭐ In a leaderless system you write to N replicas and wait for W acks, and read from R. If W plus R
> exceeds N, any read set and any write set must overlap by at least one node, so a read sees the
> latest write. ⭐ N=3, W=2, R=2 is canonical. ⭐⭐ And the caveat worth saying: **this is not
> linearizability** — concurrent writes, sloppy quorums and hinted handoff all break it. It buys you a
> high probability of freshness, not a guarantee.

## 🎙️ Articulation drill

**Two minutes.** Open by pricing it: **replication buys read capacity and survivability, and charges
in staleness** — and be explicit that it does not buy write throughput, because every replica applies
every write. Say the backup line early: **a replica is not a backup, because `DROP TABLE` replicates
in milliseconds** — replication protects against hardware, only point-in-time backups protect against
people. Then the three anomalies by name and by symptom: **read-your-own-writes, where the user saves
twice because the reload showed the old value; monotonic reads, where load balancing makes the user
watch time run backwards; and consistent prefix, where a reply arrives before the question** — and
note the third is really a sharding problem in disguise. Give the fixes in both flavours: the thirty-
second leader window that works, and the LSN token that's rigorous. Then failover, and be specific
about all four ways it hurts: **you can't distinguish dead from slow, so the timeout is a real
dilemma; async promotion loses acknowledged writes and silently discards the old leader's extras when
it rejoins; an unfenced old leader gives you split brain; and the clients often never find out,
because the connection pool is still handing out sockets to a dead host.** Close on the routing rule:
**any transaction containing a write goes to the leader whole, and any read a write depends on goes
to the leader too** — the second one is a correctness bug wearing a performance costume.
