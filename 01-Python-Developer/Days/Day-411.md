# Day 411 🔒

**P-411** · 🔒 **Distributed locking, leader election** and ⭐⭐ **the fencing token**

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a distributed lock does not give you mutual exclusion — it gives you
> mutual exclusion *most of the time*, and the difference is only visible in the case that matters, so
> the correctness must live in the resource rather than in the lock.**

# Part 1 — The four-step failure, and why "that won't happen" is wrong

```
⭐ ① ⭐ Client A acquires `lock:job-42` with a 30-second TTL.
⭐ ② ⭐⭐ A ***PAUSES FOR 40 SECONDS.***
⭐ ③ ⭐ The lock expires. ⭐ Client B acquires it, legitimately.
⭐ ④ ⭐⭐ A RESUMES — ***STILL BELIEVING IT HOLDS THE LOCK*** —
⭐    AND WRITES.
⭐ ⭐⭐ ⇒ ***BOTH WROTE. NEITHER GOT AN ERROR. NOTHING ANYWHERE
⭐   LOGGED A PROBLEM.***

⭐⭐ AND THE OBJECTION IS ALWAYS "A 40-SECOND PAUSE WON'T
⭐   HAPPEN". ⭐ Here is why it will, and several of these are
⭐   Python-specific:
⭐   ⭐ ① ***CFS THROTTLING*** (Day 361) — ⭐⭐ A CONTAINER OVER ITS
⭐      CPU QUOTA IS DESCHEDULED FOR THE REST OF THE 100 ms
⭐      PERIOD, REPEATEDLY. ⭐ Hundreds of milliseconds to seconds
⭐      of wall-clock stall, ⭐⭐ AND YOUR PROCESS CANNOT TELL.
⭐   ⭐ ② ***MEMORY PRESSURE / SWAP*** — page faults on a host
⭐      under pressure stall for seconds.
⭐   ⭐ ③ ***A `fork()` IN A LARGE-MEMORY PROCESS*** — ⭐⭐ COPYING
⭐      PAGE TABLES FOR A 6 GB PROCESS TAKES REAL TIME, ⭐ and
⭐      `multiprocessing` and gunicorn's preload do this.
⭐   ⭐ ④ ***A SLOW SYSCALL OR A BLOCKING C EXTENSION*** holding
⭐      the GIL.
⭐   ⭐ ⑤ ***VM LIVE MIGRATION*** — the hypervisor pauses you.
⭐   ⭐ ⑥ ***A STOP-THE-WORLD GC*** — smaller in CPython than in
⭐      the JVM, ⭐⭐ BUT A LARGE `gc.collect()` ON A BIG OBJECT
⭐      GRAPH IS NOT FREE.
⭐   ⭐ ⑦ ⭐⭐ AND THE ONE THAT ACTUALLY HAPPENS: ***THE NETWORK
⭐      CALL THAT RENEWS THE LOCK TIMED OUT*** — ⭐ so A is
⭐      running fine and simply ***lost the argument about
⭐      whether it still holds the lock***, which it will never
⭐      find out.

⭐⭐ ⇒ AND NOTE THE DEEPER POINT (DAY 409): ***THE TTL IS
⭐   MEASURED ON THE LOCK SERVICE'S CLOCK AND THE WORK IS DONE ON
⭐   YOURS.*** ⭐ Two clocks, no bound on their skew. ⭐⭐ SO EVEN
⭐   WITHOUT A PAUSE, "I STILL HAVE 10 SECONDS LEFT" IS AN
⭐   UNVERIFIABLE CLAIM.
```

# Part 2 — ⭐⭐ The fencing token

```
⭐⭐ ***THE LOCK SERVICE RETURNS A MONOTONICALLY INCREASING
⭐   NUMBER WITH EVERY GRANT. EVERY WRITE CARRIES ITS TOKEN. THE
⭐   STORAGE REJECTS ANY TOKEN LOWER THAN THE HIGHEST IT HAS
⭐   SEEN.***

⭐   ⭐ A acquires → token ***33***
⭐   ⭐ A pauses.
⭐   ⭐ B acquires → token ***34***, writes. ⭐⭐ STORAGE RECORDS 34.
⭐   ⭐ A resumes and writes with token 33.
⭐   ⭐⭐ ***STORAGE: 33 < 34 → REJECTED.***

⭐⭐ ⇒ AND SEE WHAT MOVED: ***THE CORRECTNESS IS NOW IN THE
⭐   RESOURCE, NOT IN THE LOCK.*** ⭐ The lock became an
⭐   optimisation — it stops two workers doing the work
⭐   simultaneously and wasting effort — ⭐⭐ WHILE THE ***SAFETY***
⭐   PROPERTY IS ENFORCED BY THE ONE COMPONENT THAT CANNOT BE
⭐   FOOLED BY A PAUSE, BECAUSE IT IS THE ONE DOING THE WRITE.

⭐ WHERE THE TOKEN COMES FROM: ⭐ ZooKeeper's `zxid`, ⭐ etcd's
⭐   revision / lease id, ⭐⭐ RAFT'S TERM NUMBER (DAY 410 — WHICH
⭐   IS EXACTLY WHY CONSENSUS SYSTEMS MAKE GOOD LOCK SERVICES),
⭐   ⭐ or a Postgres sequence.

⭐⭐ AND THE HONEST LIMITATION, WHICH MOST WRITE-UPS OMIT:
⭐   ⭐⭐ ***THIS REQUIRES YOUR STORAGE TO SUPPORT IT.***
⭐   ⭐ A version column and `WHERE version < :token`. ⭐ A
⭐     conditional write. ⭐ A compare-and-swap.
⭐   ⭐⭐ IF YOUR SINK IS A THIRD-PARTY HTTP API WITH NO
⭐     CONDITIONAL WRITE, YOU ***CANNOT*** FENCE IT — ⭐ and you
⭐     should stop pretending the lock makes it safe. ⭐⭐ MAKE THE
⭐     OPERATION IDEMPOTENT INSTEAD (PART 4), ⭐ or accept the
⭐     risk explicitly and write it down.
```

# Part 3 — Redlock, and the position to hold

```
⭐ THE CLAIM: ⭐ acquire the same lock on N independent Redis
⭐   masters; ⭐ a majority within a bounded time = held.
⭐ ⭐ Kleppmann's critique: ⭐⭐ IT DEPENDS ON BOUNDED CLOCK DRIFT
⭐   AND BOUNDED PAUSES — NEITHER OF WHICH HOLDS (PART 1) —
⭐   ⭐⭐ AND IT PROVIDES NO FENCING TOKEN, SO IT CANNOT FIX THE
⭐   PART-1 FAILURE EVEN IN PRINCIPLE.
⭐ ⭐ Antirez's response: the assumptions are reasonable for the
⭐   efficiency use case.
⭐ ⭐⭐ AND BOTH ARE RIGHT, BECAUSE THEY ARE ANSWERING DIFFERENT
⭐   QUESTIONS.

⭐⭐ ⇒ ***THE POSITION TO HOLD, AND IT SETTLES EVERY VERSION OF
⭐   THIS ARGUMENT:***
⭐   ⭐⭐ ***A REDIS LOCK IS AN EFFICIENCY OPTIMISATION — "DO NOT
⭐   DO THIS EXPENSIVE WORK TWICE". IT IS NEVER A CORRECTNESS
⭐   MECHANISM.***
⭐   ⭐ If a duplicate execution is merely ***wasteful***, a
⭐     single-instance Redis lock is fine and Redlock is
⭐     unnecessary complexity.
⭐   ⭐⭐ IF A DUPLICATE EXECUTION IS ***INCORRECT***, YOU NEED
⭐     EITHER A CONSENSUS SYSTEM WITH A FENCING TOKEN, OR — FAR
⭐     BETTER — AN OPERATION THAT DOES NOT CARE (PART 4).
⭐   ⭐ Saying exactly that is the answer; ⭐⭐ TAKING A SIDE IN THE
⭐     REDLOCK ARGUMENT IS NOT.
```

# Part 4 — ⭐⭐ Four ways to not need the lock, ranked

```
⭐⭐ ***THE BEST DISTRIBUTED LOCK IS THE ONE YOU DID NOT NEED.***

⭐ ① ⭐⭐ ***MAKE THE OPERATION IDEMPOTENT*** (DAY 335). ⭐ Then
⭐    two executions produce one effect and the lock stops being
⭐    a safety device. ⭐⭐ THIS IS THE ANSWER ROUGHLY HALF THE
⭐    TIME AND IT IS THE FIRST THING TO REACH FOR.

⭐ ② ⭐⭐ ***USE THE DATABASE'S OWN LOCKING — AND ESPECIALLY A
⭐    UNIQUE CONSTRAINT.***
⭐    ⭐⭐ A UNIQUE CONSTRAINT IS A DISTRIBUTED LOCK THAT IS
⭐    ACTUALLY CORRECT, COSTS NOTHING, AND CANNOT EXPIRE. ⭐ This
⭐    is the answer almost nobody gives.
⭐    ⭐ "Run this job once per day across twelve replicas":
⭐      `INSERT INTO job_runs (job, run_date) VALUES (...)`
⭐      with `UNIQUE (job, run_date)`. ⭐⭐ ELEVEN REPLICAS GET AN
⭐      INTEGRITY ERROR AND GO BACK TO SLEEP. ⭐ No TTL, no
⭐      renewal, no clock, no token — ⭐⭐ AND IT IS CORRECT UNDER
⭐      ARBITRARY PAUSES, WHICH NO TTL LOCK IS.
⭐    ⭐ Also: `SELECT ... FOR UPDATE`, ⭐⭐ AND `FOR UPDATE SKIP
⭐      LOCKED` FOR WORK CLAIMING (DAY 407) — ⭐ which gives you
⭐      N workers with no coordination at all.

⭐ ③ ⭐ ***PARTITION THE WORK SO ONLY ONE WORKER CAN OWN A
⭐    KEY.*** ⭐ A Kafka partition (Day 402), ⭐ consistent hashing
⭐    (Day 326), ⭐ a shard assignment. ⭐⭐ THE EXCLUSIVITY BECOMES
⭐    STRUCTURAL RATHER THAN ENFORCED.

⭐ ④ ⭐ ***OPTIMISTIC CONCURRENCY*** — ⭐ `UPDATE ... WHERE
⭐    version = :expected`. ⭐⭐ ZERO ROWS UPDATED MEANS SOMEONE
⭐    ELSE WENT FIRST: RELOAD AND RETRY (DAY 405).

⭐⭐ ⇒ ***A DISTRIBUTED LOCK IS WHAT YOU USE WHEN NONE OF THOSE
⭐   FOUR APPLIES — AND THAT IS RARER THAN PEOPLE THINK.***
⭐   ⭐ The legitimate case: ⭐⭐ COORDINATING A SIDE EFFECT ON A
⭐   SYSTEM WITH NO CONDITIONAL WRITE AND NO IDEMPOTENCY — ⭐ a
⭐   legacy SOAP API, ⭐ a file on a shared filesystem, ⭐ an
⭐   expensive third-party call you are billed for.
```

# Part 5 — Leader election, and the same rule again

```
⭐ WHAT IT IS FOR: ⭐ a singleton — ⭐ a scheduler, ⭐ a compactor,
⭐   ⭐ a migration runner, ⭐ a cron across N replicas.

⭐ HOW, IN DESCENDING ORDER OF HOW MUCH YOU SHOULD LIKE IT:
⭐ ① ⭐⭐ ***KUBERNETES `Lease` OBJECTS*** — ⭐ the mechanism
⭐    `kube-controller-manager` uses for itself. ⭐⭐ IF YOU ARE ON
⭐    KUBERNETES YOU ALREADY HAVE A CORRECT, etcd-BACKED LEADER
⭐    ELECTION AND SHOULD USE IT RATHER THAN INVENTING ONE.
⭐ ② ⭐ ***etcd*** lease + campaign, ⭐ or ⭐ ***ZooKeeper***
⭐    ephemeral sequential nodes.
⭐ ③ ⭐⭐ ***A DATABASE ROW WITH A LEASE COLUMN*** — ⭐ boring, and
⭐    correct enough for most singletons, ⭐ especially with
⭐    `FOR UPDATE` (Day 406's projector runner).
⭐ ④ ⭐ Redis — ⭐⭐ SAME CAVEAT AS PART 3.

⭐⭐ AND THE RULE FROM PART 2 APPLIES UNCHANGED TO LEADERS:
⭐   ⭐⭐ ***THE LEADER'S WRITES MUST CARRY ITS TERM OR LEASE
⭐   NUMBER, AND THE RESOURCE MUST REJECT AN OLD ONE.***
⭐   ⭐ A deposed leader that has not noticed is exactly Part 1's
⭐     paused client, ⭐⭐ AND "I AM THE LEADER" IS A BELIEF, NOT A
⭐     FACT (DAY 410's STALE-READ PROBLEM).
⭐ ⭐ Also: ⭐⭐ THE LEADER MUST ***STOP WORKING*** WHEN IT LOSES
⭐   THE LEASE, NOT MERELY DECLINE TO RENEW IT. ⭐ Wire the
⭐   lease-loss callback to cancel in-flight work, ⭐⭐ OR YOU HAVE
⭐   TWO LEADERS FOR THE DURATION OF ONE JOB.
```

# Part 6 — Python implementations, with the traps

```python
# ⭐⭐ ① REDIS LOCK — the release MUST be atomic and ownership-
# ⭐    checked, or you release SOMEONE ELSE'S lock.
RELEASE = """
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
"""                                   # ⭐⭐ Lua = ATOMIC
token = str(uuid4())
if r.set("lock:job", token, nx=True, ex=30):      # ⭐ NX + EX
    try:
        do_work(fencing_token=r.incr("lock:job:seq"))   # ⭐⭐ FENCE
    finally:
        r.eval(RELEASE, 1, "lock:job", token)     # ⭐⭐ NEVER
                                                  # ⭐   PLAIN DEL
# ⭐⭐ A PLAIN `del` AFTER YOUR TTL EXPIRED DELETES THE ***NEXT***
# ⭐   HOLDER'S LOCK — and now there is no lock at all.
```

```python
# ⭐⭐ ② POSTGRES ADVISORY LOCKS — and the pooling trap.
#    ❌ pg_try_advisory_lock  → SESSION-scoped.
#       ⭐⭐ WITH A CONNECTION POOL, THE CONNECTION GOES BACK TO
#       ⭐   THE POOL ***STILL HOLDING THE LOCK***, AND THE NEXT
#       ⭐   UNRELATED REQUEST INHERITS IT. Then nobody can ever
#       ⭐   acquire it again until that connection is recycled.
#    ✅ pg_advisory_xact_lock → TRANSACTION-scoped.
#       ⭐⭐ RELEASED AUTOMATICALLY ON COMMIT OR ROLLBACK. USE THIS.
with engine.begin() as conn:
    got = conn.execute(text(
        "SELECT pg_try_advisory_xact_lock(:k)"), {"k": key}).scalar()
    if got:
        ...   # ⭐⭐ AND IT IS RELEASED WHEN THE BLOCK EXITS,
              # ⭐   INCLUDING ON A CRASH, BECAUSE THE CONNECTION DIES.
```

```
⭐⭐ ③ AND THE ONE THAT ACTUALLY SOLVES "RUN THIS ONCE A DAY":
⭐   `INSERT INTO job_runs (job_name, run_date) VALUES (:j, :d)`
⭐   with `UNIQUE (job_name, run_date)`.
⭐   ⭐ Catch `IntegrityError` → someone else has it → return.
⭐   ⭐⭐ NO TTL. NO RENEWAL. NO CLOCK. NO TOKEN. CORRECT UNDER
⭐   ARBITRARY PAUSES. ⭐ And it leaves an audit row you can query.
⭐   ⭐⭐ IF YOU GIVE ONE ANSWER IN AN INTERVIEW ABOUT SCHEDULED
⭐   JOBS, GIVE THIS ONE.
```

# Part 7 — "Run this exactly once a day across N replicas"

```
⭐ THE FOUR ANSWERS, WITH THEIR HONEST TRADES:
⭐ ① ⭐⭐ ***UNIQUE CONSTRAINT ON (job, date).*** ⭐ Correct,
⭐    trivial, auditable. ⭐⭐ THE DEFAULT ANSWER.
⭐    ⭐ Trade: if the winner crashes mid-job, ⭐⭐ NOBODY RETRIES —
⭐    so add a `status` and `heartbeat_at` column and let a
⭐    stale row be reclaimed. ⭐ Now it is a lease again, ⭐⭐ AND
⭐    THE FENCING RULE RETURNS.
⭐ ② ⭐ ***A REAL SCHEDULER OUTSIDE THE APP*** — ⭐ Kubernetes
⭐    CronJob, EventBridge Scheduler (Day 393), Airflow.
⭐    ⭐⭐ THE JOB IS NOT RUNNING IN ALL N REPLICAS BECAUSE IT IS
⭐    NOT IN THE APP AT ALL. ⭐ Often the right answer, ⭐⭐ AND IT
⭐    MOVES THE SINGLETON PROBLEM TO SOMEONE WHOSE JOB IT IS.
⭐ ③ ⭐ ***LEADER ELECTION*** — one replica is the scheduler.
⭐    ⭐ Correct, and now you operate a leader election.
⭐ ④ ⭐ ***MAKE THE JOB IDEMPOTENT AND LET ALL N RUN IT.***
⭐    ⭐⭐ SOUNDS WASTEFUL, IS SOMETIMES CORRECT, AND HAS ZERO
⭐    COORDINATION — ⭐ if the job is a `MERGE` or an upsert
⭐    sweep, twelve replicas doing it produces one result.

⭐⭐ ⇒ AND THE ORDER TO PROPOSE THEM IN AN INTERVIEW: ***④, ①,
⭐   ②, THEN ③.*** ⭐ Reaching for the lock first is the signal
⭐   that separates people who have read about distributed locks
⭐   from people who have debugged one.
```

# 💬 Interview

**1. ⭐⭐ "Is a Redis lock safe?"**
> ⭐ It's safe *most of the time*, and the difference is only visible in the case that matters.
> ⭐⭐ **A acquires with a 30-second TTL, pauses for 40, the lock expires, B acquires legitimately, and
> A resumes still believing it holds the lock and writes. Both wrote, neither got an error, nothing
> logged a problem.** ⭐ And the "a 40-second pause won't happen" objection is wrong: ⭐⭐ **CFS
> throttling deschedules a container over its CPU quota repeatedly, a `fork()` in a six-gigabyte
> process takes real time, a VM live-migrates, and — the one that actually happens — the network call
> that renews the lock times out, so A is running fine and simply lost the argument about whether it
> still holds the lock.** ⭐ There's also a clock problem underneath: ⭐⭐ **the TTL is measured on the
> lock service's clock and the work happens on yours, so "I still have ten seconds" is an unverifiable
> claim.**

**2. ⭐⭐ "So what's the fix?"**
> ⭐ A fencing token. ⭐⭐ **The lock service returns a monotonically increasing number with every grant,
> every write carries it, and the storage rejects any token lower than the highest it has seen.** ⭐ A
> gets 33, pauses; B gets 34 and writes; A resumes and writes with 33 and is rejected. ⭐⭐ **What's
> moved is that correctness now lives in the resource rather than in the lock — the lock becomes an
> optimisation that stops duplicate work, while the safety property is enforced by the one component
> that can't be fooled by a pause, because it's the one doing the write.** ⭐ And the honest limitation
> most write-ups omit: ⭐⭐ **this requires storage that supports a conditional write. If your sink is a
> third-party HTTP API with no conditional write, you cannot fence it — so stop pretending the lock
> makes it safe and make the operation idempotent instead.**

**3. "What's your position on Redlock?"**
> ⭐ That both sides of the argument are right because they're answering different questions, and the
> useful statement is upstream of it: ⭐⭐ **a Redis lock is an efficiency optimisation — don't do this
> expensive work twice — and never a correctness mechanism.** ⭐ If a duplicate execution is merely
> wasteful, a single-instance lock is fine and Redlock is unnecessary complexity. ⭐⭐ **If a duplicate
> execution is incorrect, you need a consensus system with a fencing token, or far better an operation
> that doesn't care.** ⭐ Taking a side in the Redlock debate isn't the answer; saying which of those two
> situations you're in is.

**4. ⭐⭐ "How would you run a job exactly once a day across twelve replicas?"**
> ⭐ I'd propose four options in a specific order, and the order is the point. ⭐⭐ **First: make the job
> idempotent and let all twelve run it — it sounds wasteful and it's sometimes exactly right, with
> zero coordination, if the job is an upsert sweep.** ⭐⭐ **Second: a unique constraint on (job, date).
> Eleven replicas get an integrity error and go back to sleep — no TTL, no renewal, no clock, no
> token, correct under arbitrary pauses, and it leaves an audit row.** ⭐ Third: a real scheduler
> outside the app — a CronJob or EventBridge — which moves the singleton problem to someone whose job
> it is. ⭐ Fourth, and last, leader election. ⭐⭐ **Reaching for a distributed lock first is the signal
> that separates people who've read about them from people who've debugged one.**

**5. ⭐⭐ "When do you actually need a distributed lock?"**
> ⭐ When none of four cheaper things applies. ⭐⭐ **Make it idempotent — that's the answer about half
> the time. Use the database's own locking, and specifically a unique constraint, which is a
> distributed lock that's actually correct, costs nothing and cannot expire. Partition the work so
> exclusivity is structural — a Kafka partition, a shard. Or use optimistic concurrency on a version
> column.** ⭐ The genuine remaining case is ⭐⭐ **coordinating a side effect on a system with no
> conditional write and no idempotency — a legacy API, a file on a shared filesystem, an expensive
> third-party call** — and even then the lock is reducing waste, not guaranteeing safety.

**6. "Any Python-specific traps here?"**
> ⭐ Two. ⭐⭐ **A Redis lock must be released with a Lua script that checks ownership — a plain `del`
> after your TTL has already expired deletes the *next* holder's lock, and now there's no lock at
> all.** ⭐ And ⭐⭐ **`pg_try_advisory_lock` is session-scoped, so with a connection pool the connection
> goes back to the pool still holding the lock and the next unrelated request inherits it — nobody can
> acquire it again until that connection is recycled. Use `pg_advisory_xact_lock`, which is
> transaction-scoped and releases on commit, rollback or a dropped connection.**

## 🎙️ Articulation drill

**Two minutes.** Lead with the failure, told as four steps: **A acquires with a 30-second TTL, pauses
for 40, the lock expires, B acquires legitimately, A resumes still believing it holds the lock and
writes. Both wrote, neither errored, nothing logged.** Kill the objection immediately: **CFS throttling
deschedules a container repeatedly, a fork in a large process takes real time, a VM live-migrates —
and the one that actually happens is that the renewal call timed out, so A is running fine and just
lost the argument about whether it holds the lock.** Add the clock point: **the TTL is on the lock
service's clock and the work is on yours, so "I have ten seconds left" is unverifiable.** Then the fix
and what it means: **a fencing token — a monotonically increasing number with every grant, carried on
every write, with the storage rejecting anything lower than the highest it's seen. The correctness has
moved into the resource; the lock is now just an optimisation that stops duplicate work.** State the
limitation honestly: **this needs storage that supports a conditional write, so a third-party API with
no conditional write cannot be fenced and you should stop pretending the lock makes it safe.** Then
give the position that settles the Redlock argument: **a Redis lock is an efficiency optimisation,
never a correctness mechanism — if duplicates are merely wasteful it's fine, if duplicates are
incorrect you need a fencing token or an operation that doesn't care.** Close on the answer that shows
experience: **the best distributed lock is the one you didn't need. Make it idempotent; use a unique
constraint, which is a distributed lock that's actually correct, costs nothing and cannot expire;
partition the work so exclusivity is structural; or use optimistic concurrency. For "run this once a
day across twelve replicas", a unique constraint on job and date beats every lock — eleven replicas
get an integrity error and go back to sleep.**
