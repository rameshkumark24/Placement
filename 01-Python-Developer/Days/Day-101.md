# Part 1 — ⭐ Documentation that stays true

```
⭐⭐ THE ONE LAW OF DOCUMENTATION: THE CLOSER IT LIVES TO THE CODE, THE LONGER
⭐   IT STAYS TRUE.
⭐
⭐   ⭐⭐ A TEST          ⇒ FAILS when it drifts        ⇒ never wrong (Day 092)
⭐   ⭐ A TYPE HINT      ⇒ mypy catches drift          ⇒ rarely wrong (Day 062)
⭐   ⭐ A DOCSTRING      ⇒ reviewed with the diff      ⇒ sometimes wrong
⭐   ⭐ A README         ⇒ updated when someone notices ⇒ often stale
⭐   ⚠️ A WIKI PAGE      ⇒ nobody sees it in a PR      ⇒ ⭐⭐ USUALLY WRONG, AND
⭐                                                        CONFIDENTLY SO
⭐   ⇒ ⭐⭐ SO WRITE THE THING AS FAR DOWN THAT LIST AS IT WILL GO. ⭐ A test is
⭐        better documentation than a paragraph, because it cannot lie.
⭐   ⇒ ⚠️ ⭐⭐ AND A CONFIDENTLY WRONG DOCUMENT IS WORSE THAN NONE — it costs
⭐        someone a day and teaches the team not to trust any of it.
```

| ⭐ Artefact | ⭐ Its one job | ⭐ Its test |
|---|---|---|
| ⭐⭐ **README** | ⭐ get a new person running | ⭐⭐ **a new joiner runs it in 15 min without asking anyone** |
| Docstring | the contract (args, returns, **raises**) | ⭐ a caller needs nothing else (Day 089) |
| ⭐⭐ **ADR** | ⭐⭐ **why** — the thing nobody can reconstruct | ⭐ answers "why on earth is it like this?" |
| ⭐ **Runbook** | what to do at 3 a.m. | ⭐⭐ a tired stranger can follow it |
| Diagram | the shape | ⭐ text-based (Mermaid) **in the repo**, or it rots |

⭐⭐ **A README's only job is the first fifteen minutes.** ⭐ What is this, how do I run it, how do I
test it, how do I deploy it — in that order, with commands that can be pasted. ⭐⭐ **Architecture
essays belong elsewhere; a README that opens with a philosophy section is one nobody scrolls past.**

⭐ **Keep diagrams in the repo as text** (Mermaid in Markdown, or PlantUML). ⭐⭐ **A PNG exported from
a drawing tool is stale within a month and cannot be diffed** — a text diagram changes in the same PR
as the code, and a reviewer can see it change.

# Part 2 — ⭐⭐ ADRs

```markdown
# ADR-014: Use Redis for rate limiting rather than Postgres

**Status:** Accepted · 2026-08-18 · Supersedes ADR-009
**Context**
  We must limit login attempts per IP. We already run Postgres; Redis
  would be a new component to operate. Expected 2k writes/sec at peak,
  and the counter has no long-term value.
**Decision**
  Use Redis with a fixed-window counter and TTL expiry.
**Consequences**
  + A counter write no longer touches the primary database.
  + TTL expiry is built in; no cleanup job.
  − ⭐ A new component to run, monitor and back up (we accept: no durability needed).
  − ⭐⭐ If Redis is down, we fail OPEN — we log it and allow the request.
    This is a deliberate availability-over-enforcement choice.
**Alternatives considered**
  Postgres table: rejected — 2k writes/sec of throwaway rows on the primary,
  plus a cleanup job. In-memory per process: rejected — wrong counts behind
  multiple workers (Day 068).
```

```
⭐⭐ WHY ADRs, IN ONE ARGUMENT: THE CODE SHOWS WHAT YOU DID. THE TESTS SHOW WHAT
⭐   IT MUST DO. ⭐⭐ NOTHING IN THE REPOSITORY SHOWS WHAT YOU CONSIDERED AND
⭐   REJECTED — and that is the expensive thing to lose.
⭐   ⇒ ⭐⭐ WITHOUT IT, IN A YEAR SOMEONE SAYS "WHY IS THIS NOT IN POSTGRES?" AND
⭐        EITHER RE-DERIVES YOUR REASONING OVER A WEEK, OR "SIMPLIFIES" IT AND
⭐        REDISCOVERS THE ORIGINAL PROBLEM IN PRODUCTION.
⭐   ⇒ ⭐ it is exactly Day 085's commit message — "the diff says what, the
⭐        message says why" — at architectural scale.
⭐
⭐ ⭐⭐ THE RULES THAT MAKE THEM WORK:
⭐   · ⭐ write one for anything EXPENSIVE TO REVERSE: a datastore, a framework,
⭐     an auth model, a public API shape, a language. ⭐⭐ Not for "we used a dict".
⭐   · ⭐⭐ IMMUTABLE. You do not EDIT an accepted ADR — you write a new one that
⭐     SUPERSEDES it. ⭐ The history of decisions IS the value; an edited ADR
⭐     erases the fact that you once thought otherwise, and why you changed.
⭐   · ⭐⭐ THE CONSEQUENCES SECTION MUST CONTAIN THE COSTS. An ADR with only
⭐     benefits is advocacy, and nobody believes it. ⭐ The minus lines are what
⭐     make it credible — and they are what a future reader is checking against.
⭐   · ⭐ keep them in the repo: `docs/adr/0014-redis-rate-limiting.md`
⭐   · ⭐ one page. If it needs five, the decision is not yet made.
```

```markdown
<!-- ⭐⭐ A RUNBOOK — write it while CALM, use it while panicking -->
## Alert: `api_5xx_rate > 2%`
**Means:** more than 2% of responses are 5xx over 5 minutes.
**Check, in order:**
1. Recent deploys — `gh run list --limit 5`. ⭐ Most incidents are the last deploy.
2. `journalctl -u api --since "15 min ago" -p err` ⭐ (Day 081)
3. Database connections: `SELECT count(*) FROM pg_stat_activity;` — pool exhaustion?
4. `py-spy dump --pid $(pgrep -f uvicorn | head -1)` ⭐⭐ before restarting (Day 082)
**Mitigations:** roll back the last deploy (fastest, usually right) · scale out ·
disable feature flag `new_pricing`.
**Escalate to:** #payments-oncall if it involves charges.
```

⭐⭐ **The most valuable line in any runbook is "most incidents are the last deploy".** ⭐ It is true,
it is checkable in ten seconds, and it is the first thing a panicking person forgets.

# Part 3 — 🚪 ⭐⭐ The six answers

⭐ **Record each. Two minutes. No notes.** Same rules as Day 077 — **the gate is not "do you know
this", it is "can you say it under mild pressure without hedging."**

```
⭐⭐ 1. "WHY DOES REBASING CHANGE COMMIT HASHES?"                  (Day 084)
⭐   · a commit's hash covers its PARENT's hash ⇒ history is a hash chain
⭐   · ⇒ ⭐⭐ rebase BUILDS NEW COMMITS and moves a pointer; the originals survive
⭐   · ⇒ ⭐⭐ therefore force-push exists, therefore the reflog can rescue you,
⭐     and ⭐⭐ therefore deleting a leaked secret in a new commit removes NOTHING

⭐⭐ 2. "A PRODUCTION SERVICE IS HUNG. GO."                        (Days 082, 100)
⭐   · ⭐⭐ DO NOT RESTART — capture first; it takes two minutes
⭐   · ⭐ CPU near 100% ⇒ it is computing ⇒ py-spy top
⭐   · ⭐ CPU near 0%   ⇒ it is waiting   ⇒ strace ⇒ lsof the fd ⇒ ⭐⭐ AND THE
⭐     REAL FINDING IS THE MISSING TIMEOUT
⭐   · ⭐ futex forever ⇒ deadlock ⇒ py-spy dump shows all threads

⭐⭐ 3. "WHAT IS YOUR TESTING STRATEGY?"                           (Days 092, 095)
⭐   · the suite exists so I can CHANGE the code, not to prove correctness
⭐   · ⭐ many fast unit tests on real logic, a fat integration layer, few e2e
⭐   · ⭐⭐ behaviour not implementation — IF A PURE REFACTOR BREAKS IT, THE TEST
⭐     WAS WRONG
⭐   · ⭐⭐ fakes over mocks; five mocks is a measurement of the design

⭐⭐ 4. "WE HAVE 95% COVERAGE. ARE WE WELL TESTED?"                (Day 098)
⭐   · ⭐⭐ a test with NO ASSERTIONS gives 100% ⇒ coverage measures EXECUTION
⭐   · ⇒ strong negative signal, worthless positive one
⭐   · ⭐ a target makes it worse (Goodhart) ⇒ diff coverage, and mutation
⭐     testing on the code where a wrong answer is expensive

⭐⭐ 5. "WHAT DO YOU LOOK FOR IN A REVIEW?"                        (Day 100B)
⭐   · why → design → correctness → tests → readability → nits, and STOP EARLY
⭐   · ⭐⭐ "what happens if this is called twice?"
⭐   · ⭐ timeouts, N+1, blocking call in async, a lock across I/O, PII in logs
⭐   · ⭐⭐ and would the test FAIL if the code were wrong?

⭐⭐ 6. "HOW DO YOU FIND THE COMMIT THAT BROKE IT?"                (Days 087, 100)
⭐   · reproduce it as a test first — ⭐ then `git bisect run pytest -x`
⭐   · ⭐ 1,000 commits = 10 tests; exit 125 skips unbuildable commits
⭐   · ⭐⭐ and the honest limit: bisect needs every commit to build, which is
⭐     the real argument for atomic commits
```
