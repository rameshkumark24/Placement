# Part 1 — ⭐⭐ Reading bytecode

```python
import dis
def add(a, b):
    return a + b

dis.dis(add)
#   RESUME
#   LOAD_FAST   a          ⭐ locals are an ARRAY index — fast
#   LOAD_FAST   b
#   BINARY_OP   +          ⭐⭐ type lookup ⇒ __add__ ⇒ allocate a result (Day 023)
#   RETURN_VALUE
```

```
⭐⭐ THE THREE LOAD INSTRUCTIONS, AND THEIR COST ORDER — this is a real optimisation:
⭐   LOAD_FAST    ⇒ a LOCAL   — an index into an array on the frame.  ⭐⭐ fastest
⭐   LOAD_GLOBAL  ⇒ a MODULE global or builtin — ⭐ a DICT LOOKUP (Day 035), possibly two
⭐                  (module dict, then builtins dict)
⭐   LOAD_ATTR    ⇒ obj.attr — ⭐⭐ the whole protocol from Day 032
⭐
⭐ ⇒ ⭐⭐ WHICH IS WHY the classic hot-loop trick works:
⭐        append = result.append      ⇒ ⭐ hoist the attribute lookup OUT of the loop
⭐        for x in xs: append(x)      ⇒ ⭐ LOAD_FAST instead of LOAD_FAST + LOAD_ATTR
⭐   ⇒ ⚠️ ⭐ and why it matters far less since 3.11's inline caches. Measure before doing it.
```

```python
dis.dis(compile(src, "<s>", "exec"))     # ⭐ any source
f.__code__.co_consts, co_names, co_varnames, co_flags     # ⭐ what the compiler produced
dis.show_code(f)                          # ⭐ a readable summary
```

⭐⭐ **`dis` is a debugging tool, not trivia.** ⭐ It is how you answer "is this comprehension actually
faster?" (Day 050), "why is `+=` not atomic?" (Day 067), and "did the compiler fold that constant?"
(Day 028) — **without guessing.**

# Part 2 — ⭐ Frames, and the cost of a call

```
⭐⭐ EVERY CALL PUSHES A FRAME OBJECT: locals array, value stack, the code object,
⭐   a back-pointer to the caller, and the instruction pointer.
⭐   ⇒ ⭐ a traceback is that chain, walked (Day 059)
⭐   ⇒ ⭐ a generator's frame is HEAP-allocated and survives between yields (Day 047)
⭐   ⇒ ⭐⭐ storing an exception keeps its traceback ⇒ every frame ⇒ every local (Day 026)
⭐
⭐ ⭐⭐ A PYTHON FUNCTION CALL COSTS ROUGHLY 50–100 ns — ~50× a C function call.
⭐   ⇒ ⭐⭐ which is why a lambda inside `key=` matters on a million-element sort (Day 045),
⭐        and why "extract this three-line helper" is free everywhere except a hot loop.
```

⭐ **3.11's "zero-cost" exceptions** mean a `try` block that does not raise costs nothing at runtime —
the handler information moved to a side table. **That is the mechanical basis for EAFP** (Days 023,
059). ⚠️ **Raising still costs**, because the traceback must be built.

```python
import sys
sys.setrecursionlimit(3000)      # ⚠️ ⭐ the limit protects the C stack — raise it and you
                                 #    trade a clean RecursionError for a SEGFAULT
```

⭐⭐ **The recursion limit of 1000 is a real constraint in a DSA round** (the DSA track says so): **a
DFS over 10⁵ nodes will blow the stack.** ⭐ **Convert to an explicit stack and a `while` loop** — the
right answer — rather than raising the limit.

# Part 3 — ⭐⭐ Where the time actually goes

```
⭐⭐ THE PER-OPERATION TAX, and the fix follows from the list:
⭐   1. ⭐ DISPATCH        — decode a bytecode, jump to its handler
⭐   2. ⭐⭐ TYPE LOOKUP    — a + b must find __add__ on type(a) at runtime
⭐   3. ⭐⭐ ALLOCATION     — the result is a new heap object with a header (Day 023)
⭐   4. ⭐ REFCOUNTING     — every touch writes to the header (Day 026)
⭐   5. ⭐⭐ POINTER CHASING — a list is pointers to scattered objects ⇒ cache misses (Day 028)
⭐
⭐ ⇒ ⭐⭐ THE CONCLUSION: none of these gets much cheaper. So the fix is ALWAYS to do
⭐      FEWER Python-level operations — not to make each one faster.
```

| ⭐ Strategy | ⭐ Effect |
|---|---|
| ⭐⭐ **Move the loop into C** | ⭐⭐ NumPy, `str.join`, `sum`, `sorted` — 10–100× |
| ⭐ Better algorithm | ⭐⭐ a `set` instead of a list (Day 036) beats any micro-optimisation |
| ⭐ Fewer allocations | reuse buffers, generators instead of lists (Day 047) |
| ⭐ Fewer attribute lookups | hoist out of hot loops — ⭐ small, and smaller since 3.11 |
| ⭐⭐ Do not do it in Python | ⭐ a C extension, Cython, Rust via PyO3, or the database |

```python
# ⭐⭐ PROFILE FIRST. Always. The order that wastes least time:
python -X importtime -c "import myapp"     # ⭐⭐ startup cost, per import
python -m cProfile -s cumtime app.py       # ⭐ which FUNCTIONS
# then: py-spy top --pid <pid>             # ⭐⭐ a RUNNING process, no code changes, sampling
#       py-spy dump --pid <pid>            # ⭐⭐ every thread's stack — finds a HANG
import timeit; timeit.timeit(stmt, number=100000)     # ⭐ micro-benchmarks
```

⭐⭐ **`py-spy` is the one to remember.** It attaches to a running production process with no
instrumentation and no restart, and **`py-spy dump` prints every thread's stack — which is how you
diagnose a hung worker** (Day 060's missing timeout, or Day 072's blocked loop).

⚠️ ⭐⭐ **Never optimise without measuring, and Amdahl says why** (Day 064): making a function 10×
faster when it is 5% of runtime buys you 4.5%. **The profiler almost always points somewhere you did
not expect — usually a query, not a loop.**

# Part 4 — ⭐ What is getting faster

```
⭐ 3.11 — the "Faster CPython" release, ~25% overall:
⭐   · ⭐⭐ SPECIALISING ADAPTIVE INTERPRETER — a bytecode that has seen only ints
⭐        REWRITES ITSELF into an int-specific version, skipping the generic dispatch.
⭐        ⇒ ⭐ this is why type-stable code is now measurably faster than polymorphic code.
⭐   · ⭐ INLINE CACHES for attribute and global lookups (Part 1's hoisting matters less)
⭐   · ⭐ cheaper frames, lazy creation; ⭐⭐ zero-cost exceptions
⭐ 3.12/3.13 — more specialisation, ⭐ per-interpreter GIL (Day 065), ⭐⭐ an experimental JIT
⭐ 3.13+     — ⭐⭐ the free-threaded build (Day 065)
```

⭐⭐ **The specialising interpreter has a practical consequence worth knowing:** a function whose
argument is *always* an `int` runs faster than one that sometimes gets a `float` — **because the
first specialises and stays specialised, and the second de-optimises.** ⭐ It is a small effect and it
rewards type-stable code, which you were writing anyway (Day 061).

```
⭐⭐ THE HONEST PERFORMANCE POSITION FOR AN INTERVIEW:
⭐   "Python is 10–100× slower than C for tight loops, and that is almost never what makes
⭐    a service slow. ⭐⭐ In every backend I have profiled, the time was in a query, an N+1,
⭐    a missing index, or a network round trip — not in the interpreter. ⭐ When the
⭐    interpreter genuinely is the bottleneck, the fix is to move the loop out of Python
⭐    rather than to micro-optimise it."
```

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐⭐ **Optimising without profiling** | ⭐⭐ Amdahl — the profiler points somewhere unexpected. |
| Micro-optimising Python operations | ⭐ Do *fewer* operations; move the loop to C. |
| ⭐ Hoisting lookups everywhere | ⭐ Small, and smaller since 3.11's inline caches. |
| Raising the recursion limit | ⭐⭐ You trade `RecursionError` for a segfault. Iterate. |
| ⭐ Treating `dis` as trivia | ⭐⭐ It answers "is this actually faster" without guessing. |
| Assuming `try` is expensive | ⭐ Zero-cost when it does not raise (3.11+). |
| Storing exception objects | ⭐ Pins every frame and local (Day 026). |
| Ignoring import time | ⭐ `-X importtime` — startup is latency for a Lambda or a CLI. |
| Not knowing `py-spy` | ⭐⭐ Attaches to a live process; `dump` diagnoses a hang. |
| "Python is slow" as an explanation | ⭐⭐ Usually the database. Measure. |

## Interview questions

**Q: Why is Python slow?**
> Not for one reason — because every operation carries a fixed tax. Decoding and dispatching a
> bytecode, looking up the type to find `__add__`, allocating a heap object for the result, updating
> reference counts, and chasing pointers to scattered objects instead of walking contiguous memory.
> None of those gets dramatically cheaper, which is why the fix is always to perform *fewer*
> Python-level operations rather than to make each faster — moving the loop into C via NumPy or `join`
> or `sorted`, or choosing a better algorithm.

**Q: What's `dis` for, practically?**
> Answering questions without guessing. It shows why `counter += 1` isn't atomic — load, add, store —
> which is Day 067's race; whether a comprehension really compiles differently from a loop; whether
> the compiler folded a constant. And it makes the three load instructions visible: locals are an
> array index, globals are a dictionary lookup, and attributes go through the full descriptor
> protocol. That cost order is what the classic hoisting trick exploits, though inline caches in 3.11
> made it much less significant.

**Q: How do you approach a slow Python service?**
> Profile before touching anything, because Amdahl's law means making a function ten times faster when
> it's five percent of runtime buys four and a half percent. `cProfile` for which functions, `-X
> importtime` if startup matters, and `py-spy` for a running process — it attaches without
> instrumentation or a restart, and `py-spy dump` prints every thread's stack, which is how you
> diagnose a hung worker. In practice the profiler nearly always points at a query, an N+1 or a
> network round trip rather than at the interpreter.

**Q: What changed in 3.11?**
> The specialising adaptive interpreter, mainly. A bytecode that has only ever seen integers rewrites
> itself into an integer-specific version, skipping the generic type dispatch — so type-stable code is
> now measurably faster than polymorphic code, which is a nice alignment with writing well-typed code
> anyway. Plus inline caches for attribute and global lookups, cheaper lazily-created frames, and
> zero-cost exceptions, which means a `try` block that doesn't raise costs nothing at runtime. That
> last one is the mechanical justification for EAFP being idiomatic.

**Q: What about the recursion limit?**
> It defaults to 1000 and it exists to protect the C stack — CPython frames consume real C stack, so
> without the limit deep recursion segfaults instead of raising. Raising it trades a clean
> `RecursionError` for a crash, so the right answer for a deep traversal is to convert it to an
> explicit stack and a `while` loop. It's a genuine constraint in coding rounds: a recursive DFS over
> a hundred thousand nodes will hit it.

**Q: Is Python fast enough?**
> For almost every backend, yes — and I'd be specific about why. The interpreter is ten to a hundred
> times slower than C on tight loops, and that is essentially never what makes a service slow; the
> time is in the database, in serialisation, or on the network. When the interpreter genuinely is the
> bottleneck, the answer is to get the loop out of Python — NumPy, a C extension, or pushing the work
> into the database — rather than to micro-optimise the Python.

## 🎙️ Articulation drill

Record two minutes: **"Your API endpoint takes 800 ms. Walk me through making it faster."**

⭐ Refuse to guess: **profile first**, and say why with numbers — Amdahl means a tenfold improvement to
something that is 5% of the time buys 4.5%. ⭐ `cProfile` for which functions, and `py-spy` if it is
already in production, because it attaches to a live process with no restart and no instrumentation.

⭐⭐ **Then state the expectation, because it is usually right and it shows you have done this:** *"in
every backend I have profiled the time was not in the interpreter. It was a query without an index, an
N+1 from a lazy relationship, or a serial chain of network calls that should have been concurrent. The
first thing I would look at is the query count for the request, not the Python."*

⭐ Then, if the interpreter genuinely is the bottleneck: **do fewer Python-level operations rather than
faster ones** — move the loop into C with NumPy or `join`, fix the algorithm (a `set` instead of a
list beats any micro-optimisation), or push the work into the database. ⭐⭐ **And if it is genuinely
slow work that the user does not need to wait for, it belongs on a queue with a 202** — which is a
latency fix that costs no CPU at all.
