# Part 1 — A role is not a user

```
⭐⭐ ***A ROLE IS A SET OF PERMISSIONS PLUS A DOCUMENT SAYING WHO
⭐   IS ALLOWED TO BECOME IT.*** ⭐ Nobody logs in as a role. ⭐ You
⭐   ***assume*** it, and what you get back is a temporary
⭐   credential with an expiry.

⭐⭐ THE TWO HALVES EVERYONE CONFLATES — ⭐ and conflating them is
⭐   why the bug looks like a permissions bug when it is not:

⭐   ⭐⭐ ① ***THE TRUST POLICY ANSWERS "WHO MAY ASSUME ME".***
⭐        ⭐ It is a resource policy that lives on the role.
⭐        ⭐⭐ IF THIS IS WRONG YOU GET AccessDenied ON
⭐        `sts:AssumeRole` — ⭐ before any of your permissions
⭐        are consulted at all.
⭐   ⭐⭐ ② ***THE PERMISSION POLICY ANSWERS "WHAT MAY I DO".***
⭐        ⭐ If this is wrong you assume the role fine and then
⭐        fail on the actual call.

⭐⭐ ⇒ SO THE FIRST DIAGNOSTIC QUESTION IS ALWAYS: ***DID THE
⭐   ASSUME SUCCEED?*** ⭐ `get_caller_identity` answers it in one
⭐   line, ⭐⭐ AND IT SPLITS THE PROBLEM SPACE IN HALF.

⭐ WHY ROLES RATHER THAN USERS, IN ONE LINE EACH:
⭐   ⭐ Credentials ***expire by construction*** — ⭐⭐ SO A LEAK
⭐     HAS A DEADLINE.
⭐   ⭐ No secret exists to be committed to git.
⭐   ⭐ The assume is logged in CloudTrail with a session name —
⭐     ⭐⭐ SO "WHICH HUMAN DID THIS" SURVIVES SHARED ROLES.
⭐   ⭐ Permissions change without redeploying anything.
⭐   ⭐⭐ AND ROTATION BECOMES A NON-QUESTION, WHICH IS THE WHOLE
⭐     POINT OF DAY 372.
```

# Part 2 — STS mechanics

```
⭐ sts:AssumeRole RETURNS ***THREE*** FIELDS:
⭐   AccessKeyId  ⭐ SecretAccessKey  ⭐⭐ ***SessionToken***
⭐   ⭐⭐ THE THIRD IS THE ONE PEOPLE FORGET WHEN COPYING
⭐   CREDENTIALS BY HAND, ⭐ and it produces the maddening
⭐   `InvalidClientTokenId` — ⭐⭐ AN ERROR THAT SOUNDS LIKE A
⭐   WRONG KEY AND IS ACTUALLY A MISSING THIRD FIELD.

⭐ DURATION: ⭐ 15 min – 12 h, capped by the role's
⭐   MaxSessionDuration. ⭐⭐ EXCEPT ROLE CHAINING (ASSUMING A ROLE
⭐   ***FROM*** A ROLE), WHICH IS HARD-CAPPED AT ONE HOUR AND
⭐   CANNOT BE RAISED — ⭐ a real constraint for long jobs.

⭐ THE FOUR CALLS WORTH KNOWING:
⭐   ⭐ AssumeRole ................ same or cross account
⭐   ⭐ AssumeRoleWithWebIdentity . ⭐⭐ OIDC — GITHUB ACTIONS,
⭐     EKS SERVICE ACCOUNTS, MOBILE APPS
⭐   ⭐ AssumeRoleWithSAML ........ corporate SSO
⭐   ⭐ GetCallerIdentity ......... ⭐⭐ FREE, NEVER DENIED,
⭐     ALWAYS YOUR FIRST DEBUGGING CALL

⭐ TWO OPTIONS ON AssumeRole THAT EARN THEIR KEYSTROKES:
⭐   ⭐⭐ `RoleSessionName` — ⭐ appears in every CloudTrail event
⭐     as `assumed-role/Name/SESSION`. ⭐⭐ PUT THE HUMAN OR THE
⭐     JOB ID IN IT, ⭐ or your audit trail says "the app" for
⭐     everything.
⭐   ⭐⭐ `Policy` (a session policy) — ⭐ an ***additional***
⭐     ceiling for this session only. ⭐⭐ THE CORRECT TOOL FOR
⭐     "THIS BATCH JOB USES THE APP ROLE BUT MUST ONLY TOUCH ONE
⭐     PREFIX": ⭐ narrow at assume time instead of creating a
⭐     seventh role.
```

# Part 3 — ⭐⭐ IMDS, and the SSRF that reads your credentials

```
⭐⭐ HOW `boto3` GETS CREDENTIALS ON EC2 WITH NO CONFIG AT ALL:
⭐   ⭐ It calls the ***instance metadata service*** at the
⭐     link-local address ***169.254.169.254***, ⭐ which returns
⭐     the instance role's temporary credentials.

⭐⭐ IMDSv1 IS A PLAIN UNAUTHENTICATED GET. ⭐ Which means:
⭐   ⭐⭐ ***ANY SERVER-SIDE REQUEST FORGERY IN YOUR PYTHON APP
⭐   READS YOUR AWS CREDENTIALS.***

⭐   requests.get(user_supplied_url)          ⭐⭐ ← THE BUG
⭐   → http://169.254.169.254/latest/meta-data/iam/
⭐       security-credentials/app-role
⭐   → {"AccessKeyId": ..., "SecretAccessKey": ...,
⭐      "Token": ...}                          ⭐⭐ ← GAME OVER

⭐ ⭐⭐ THIS IS THE SHAPE OF THE LARGEST CLOUD BREACHES ON RECORD.
⭐   ⭐ Not an AWS flaw — ⭐⭐ AN APPLICATION FLAW WITH AN
⭐   EXTRAORDINARY PAYOFF, ⭐ because the metadata endpoint turns
⭐   "fetch a URL for me" into "hand me the account".

⭐⭐ IMDSv2 CLOSES IT, ⭐ and it costs nothing:
⭐   ⭐ You must first ***PUT*** to get a token, sending a
⭐     `X-aws-ec2-metadata-token-ttl-seconds` header.
⭐   ⭐⭐ A NAIVE SSRF CANNOT DO A PUT WITH A CUSTOM HEADER.
⭐   ⭐ The token response has ⭐⭐ TTL/HOP LIMIT 1 BY DEFAULT, SO
⭐     THE RESPONSE CANNOT BE PROXIED ONWARD — ⭐ which also stops
⭐     a container reaching the ***host's*** credentials.

⭐⭐ ⇒ SET `HttpTokens: required` ON EVERY INSTANCE AND EVERY
⭐   LAUNCH TEMPLATE. ⭐ One Terraform line. ⭐⭐ IT REMOVES AN
⭐   ENTIRE CLASS OF BREACH AND HAS NO DOWNSIDE — MODERN boto3
⭐   USES v2 AUTOMATICALLY.

⭐ AND DEFENCE IN DEPTH ON THE APPLICATION SIDE (Day 302):
⭐   ⭐ Never fetch a user-supplied URL without an allow-list.
⭐   ⭐⭐ RESOLVE THE HOST AND REJECT PRIVATE/LINK-LOCAL RANGES
⭐     ***AFTER*** RESOLUTION — ⭐ a DNS name can point at
⭐     169.254.169.254, ⭐⭐ AND CHECKING THE STRING IS NOT
⭐     CHECKING THE DESTINATION.
```

# Part 4 — ⭐⭐ The credential ladder, ranked by rotation speed

```
⭐⭐ RANKED WORST TO BEST BY THE ONLY QUESTION THAT MATTERS
⭐   (DAY 372): ***HOW FAST CAN I INVALIDATE THIS?***

⭐ ⑥ ⭐⭐ STATIC KEY IN SOURCE ......... rotate: ***NEVER***
⭐      ⭐ It is in the git history forever (Day 362).
⭐ ⑤ ⭐ STATIC KEY IN ENV VAR ......... rotate: hours + a deploy
⭐      ⭐ Plus every trap in Day 372 Part 1.
⭐ ④ ⭐ STATIC KEY IN A SECRETS MANAGER  rotate: minutes
⭐      ⭐⭐ BETTER, BUT THE KEY STILL EXISTS AND STILL LEAKS.
⭐ ③ ⭐ EC2 INSTANCE ROLE ............. rotate: ***automatic***
⭐      ⭐⭐ BUT SHARED BY EVERY PROCESS ON THE BOX.
⭐ ② ⭐⭐ ***ECS TASK ROLE / EKS IRSA*** . rotate: automatic
⭐      ⭐⭐ AND SCOPED PER CONTAINER — SO ONE COMPROMISED SIDECAR
⭐      DOES NOT INHERIT THE APP'S PERMISSIONS. ⭐ This is the
⭐      right answer for the flagship.
⭐ ① ⭐⭐ ***OIDC FEDERATION*** ......... ⭐⭐ THERE IS NO AWS
⭐      CREDENTIAL AT ALL. ⭐ CI proves its identity to AWS with a
⭐      short-lived token it did not store. ⭐⭐ NOTHING TO LEAK,
⭐      NOTHING TO ROTATE, NOTHING TO FIND IN A LOG.

⭐⭐ ⇒ THE POSITION TO HOLD: ***A LONG-LIVED IAM USER ACCESS KEY
⭐   IS A DESIGN SMELL IN 2020s AWS.*** ⭐ There are a few
⭐   legitimate cases — a third-party SaaS with no OIDC support,
⭐   a legacy on-prem job — ⭐⭐ AND EACH SHOULD BE A NAMED,
⭐   REVIEWED EXCEPTION WITH AN EXPIRY DATE, NOT THE DEFAULT.
```

# Part 5 — OIDC in practice, and the wildcard that undoes it

```json
{
  "Effect": "Allow",
  "Principal": {"Federated": "arn:aws:iam::111:oidc-provider/token.actions.githubusercontent.com"},
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:acme/flagship:ref:refs/heads/main"
    }
  }
}
```

```
⭐⭐ AND THE FAILURE, WHICH IS DAY 369's WILDCARD TRAP IN AWS
⭐   FORM — ⭐ it looks like a small convenience:

⭐   "sub": "repo:acme/*"            ⭐⭐ ← EVERY REPO IN THE ORG
⭐   "sub": "repo:acme/flagship:*"   ⭐⭐ ← EVERY BRANCH, INCLUDING
⭐                                       ONE A CONTRIBUTOR PUSHES

⭐⭐ ⇒ ***PIN THE FULL SUBJECT: ORG, REPO, AND REF OR
⭐   ENVIRONMENT.*** ⭐ Use a GitHub ***environment*** with
⭐   required reviewers and condition on
⭐   `repo:acme/flagship:environment:production` — ⭐⭐ WHICH
⭐   MAKES THE HUMAN APPROVAL PART OF THE IAM CONDITION RATHER
⭐   THAN A CONVENTION IN A YAML FILE.
⭐ ⭐ Use `StringEquals` on `sub`, ⭐⭐ NOT `StringLike`. ⭐ If you
⭐   see `StringLike` on a subject, read it very carefully.
```

# Part 6 — Accounts as the real boundary

```
⭐⭐ ***THE STRONGEST ISOLATION BOUNDARY IN AWS IS AN ACCOUNT,
⭐   NOT A POLICY.*** ⭐ Stronger than IAM, stronger than tags,
⭐   stronger than naming conventions — ⭐ because it is also a
⭐   quota boundary, a billing boundary, ⭐⭐ AND A BLAST-RADIUS
⭐   BOUNDARY THAT SURVIVES A MISTAKE IN A POLICY.

⭐ THE LAYOUT THAT IS SIMPLY THE DEFAULT ANSWER:
⭐   ⭐ management (org only, nothing deployed)
⭐   ⭐ log-archive  ⭐⭐ CLOUDTRAIL HERE, WRITE-ONLY FROM OTHERS
⭐   ⭐ shared-services (ECR, DNS)
⭐   ⭐ dev · staging · ***prod***

⭐ HOW WORK CROSSES THE LINE: ⭐ a role in prod whose trust
⭐   policy names a role in the CI account, ⭐⭐ WITH AN
⭐   `sts:ExternalId` FOR THIRD PARTIES (THE CONFUSED-DEPUTY
⭐   FIX) — ⭐ and that is the whole mechanism.

⭐⭐ THIS IS DAY 379's BLAST-RADIUS LAYERING, ONE LEVEL UP:
⭐   ⭐ Terraform state layered so a daily change cannot touch
⭐     the irreplaceable thing;
⭐   ⭐⭐ ACCOUNTS LAYERED SO A CREDENTIAL CANNOT.
```

# Part 7 — The Python trap: credentials that expire mid-job

```python
# ⭐⭐ THE BUG — and it is extremely common in Celery workers,
# ⭐ because it only fails after the process has been up an hour
# ⭐ and therefore never in dev.
resp = boto3.client("sts").assume_role(
    RoleArn=ROLE, RoleSessionName="worker")
c = resp["Credentials"]                      # ⭐ a plain dict
s3 = boto3.client("s3",
    aws_access_key_id=c["AccessKeyId"],      # ⭐⭐ FROZEN
    aws_secret_access_key=c["SecretAccessKey"],
    aws_session_token=c["SessionToken"])
# ⭐⭐ ⇒ AT T+60 MIN: ExpiredToken ON EVERY CALL, FOREVER,
# ⭐   BECAUSE botocore CANNOT REFRESH LITERAL KEYS YOU PASSED
# ⭐   IN. ⭐ The worker looks alive and does nothing.
```

```python
# ⭐⭐ THE FIX — let botocore own the refresh. Two options.

# ⭐ (a) Best: don't assume anything. Use the task role directly.
s3 = boto3.client("s3")          # ⭐⭐ REFRESHES FOREVER

# ⭐ (b) When you genuinely must assume another account's role:
from botocore.credentials import DeferredRefreshableCredentials
import botocore.session

def _refresh():
    c = boto3.client("sts").assume_role(
        RoleArn=ROLE, RoleSessionName=f"worker-{os.getpid()}",
        DurationSeconds=3600)["Credentials"]
    return {"access_key": c["AccessKeyId"],
            "secret_key": c["SecretAccessKey"],
            "token":      c["SessionToken"],
            "expiry_time": c["Expiration"].isoformat()}

bs = botocore.session.get_session()
bs._credentials = DeferredRefreshableCredentials(
    refresh_using=_refresh, method="sts-assume-role")
session = boto3.Session(botocore_session=bs)   # ⭐⭐ SELF-HEALING

# ⭐⭐ AND THE SIMPLEST VERSION OF (b) IF YOU CONTROL THE CONFIG:
# ⭐ put role_arn + credential_source in ~/.aws/config and just
# ⭐ call boto3.Session(profile_name=...) — botocore does all of
# ⭐ the above for you. ⭐⭐ PREFER THIS.
```

```
⭐⭐ AND TWO SMALLER PYTHON NOTES THAT SAVE REAL TIME:
⭐   ⭐⭐ ***CREATE THE CLIENT ONCE, NOT PER REQUEST.*** ⭐ Client
⭐     construction parses JSON service models and is ~100 ms;
⭐     ⭐⭐ DOING IT PER REQUEST IS A LATENCY BUG PEOPLE BLAME ON
⭐     THE NETWORK. ⭐ Module-level client, or a cached factory.
⭐   ⭐ `boto3.client` is ***not*** documented thread-safe to
⭐     create concurrently; ⭐⭐ CREATE IN THE MAIN THREAD, SHARE
⭐     THE CLIENT ACROSS THREADS (that part is fine), ⭐ and give
⭐     each thread pool a `Config(max_pool_connections=N)` that
⭐     matches its size ⭐⭐ OR YOU WILL SILENTLY SERIALISE ON A
⭐     TEN-CONNECTION POOL (DAY 386).
```

# 💬 Interview

**1. "What's the difference between a role and a user?"**
> ⭐ A user is a long-lived identity with a password or an access key. ⭐⭐ **A role is a set of
> permissions plus a trust policy saying who may become it, and assuming it produces credentials that
> expire.** ⭐ The practical difference is that a leaked role session has a deadline and a leaked
> access key doesn't. ⭐ And roles split into two documents people conflate: ⭐⭐ **the trust policy
> answers "who may assume me", the permission policy answers "what may I do" — so my first diagnostic
> is always whether the assume succeeded**, which `get_caller_identity` answers in one line and which
> cuts the problem space in half.

**2. ⭐⭐ "Explain IMDSv2 and why it exists."**
> ⭐ IMDS is the link-local endpoint at 169.254.169.254 that hands an instance its role credentials —
> it's how boto3 works with no configuration. ⭐⭐ **In v1 it's a plain unauthenticated GET, so any SSRF
> in the application reads the AWS credentials: `requests.get(user_url)` pointed at the metadata
> endpoint returns keys.** ⭐ That's the shape of the largest cloud breaches on record, and it's an
> application flaw with an extraordinary payoff rather than an AWS flaw. ⭐⭐ **v2 requires a PUT with a
> custom header to obtain a token, which a naive SSRF can't do, and the default hop limit of 1 stops
> the response being proxied — which also prevents a container reaching the host's credentials.**
> ⭐ Requiring v2 is one line, has no downside because modern SDKs use it automatically, and removes a
> whole class.

**3. "How should CI authenticate to AWS?"**
> ⭐⭐ **OIDC, so there is no AWS credential at all** — the pipeline proves its identity with a
> short-lived token it never stored, which means nothing to leak and nothing to rotate. ⭐ The role's
> trust policy conditions on the provider, the audience and the subject, ⭐⭐ **and the subject must be
> pinned fully — org, repo and ref.** ⭐ `repo:acme/*` grants every repo in the org; `repo:acme/app:*`
> grants every branch including one a contributor pushes. ⭐ Best is conditioning on a GitHub
> environment with required reviewers, ⭐⭐ **which makes the human approval part of the IAM condition
> rather than a convention in a YAML file** — and `StringEquals`, never `StringLike`.

**4. "Rank the ways an application can hold AWS credentials."**
> ⭐ By rotation speed, worst first: ⭐⭐ **a key in source can never be rotated because it's in the git
> history forever**; a key in an env var takes hours and a deploy; a key in a secrets manager takes
> minutes but still exists; an instance role rotates automatically but is shared by every process on
> the box; ⭐⭐ **an ECS task role or EKS IRSA rotates automatically and is scoped per container, so a
> compromised sidecar doesn't inherit the app's permissions**; and OIDC federation is best because
> there's no stored credential at all. ⭐ My position is that a long-lived IAM user key is a design
> smell — there are legitimate exceptions like a SaaS with no OIDC support, ⭐⭐ **but each should be a
> named exception with an expiry date, not the default.**

**5. ⭐⭐ "Our Celery workers get ExpiredToken after an hour. Why?"**
> ⭐ Almost certainly someone called `assume_role`, took the credentials dict, and passed the three
> literal strings into `boto3.client(...)`. ⭐⭐ **botocore can refresh credentials it resolved itself,
> but it cannot refresh literal keys you handed it — so at the one-hour expiry every call fails
> forever and the worker looks alive while doing nothing.** ⭐ It never reproduces in dev because dev
> processes don't live an hour. ⭐ The fix is to let botocore own the refresh: use the task role
> directly if you can, ⭐⭐ **or put `role_arn` and `credential_source` in the AWS config file and use a
> profile, which gives you refreshable credentials for free** — hand-rolling `DeferredRefreshableCredentials`
> is the third option, not the first.

**6. "Why separate AWS accounts per environment?"**
> ⭐⭐ **Because an account is a stronger boundary than any policy** — it's simultaneously a blast
> radius, a quota boundary and a billing boundary, and it survives a mistake in an IAM policy in a way
> that tags and naming conventions don't. ⭐ It's the same argument as layering Terraform state so a
> daily change can't touch the irreplaceable thing, one level up. ⭐ Crossing the line is a role in
> prod trusting a role in CI, ⭐⭐ **with an ExternalId for third parties to close the confused-deputy
> problem.**

## 🎙️ Articulation drill

**Two minutes.** Frame it as a single arc: **every AWS security improvement of the last decade is a
different way of not having a long-lived access key** — because the only question that matters about a
credential is how fast you can invalidate it. Then the ladder: **key in source can never be rotated
because git remembers; key in env is hours and a deploy; key in a manager is minutes but still exists;
instance role rotates automatically but every process on the box shares it; task role rotates and is
scoped per container; OIDC has no stored credential at all.** Give the mechanism briefly — **a role is
permissions plus a trust policy, and the trust policy failing looks like a permissions bug, so
`get_caller_identity` is always my first call.** Then the security story that proves depth: **IMDSv1
is an unauthenticated GET, so any SSRF in the app reads the instance's AWS credentials — that's the
shape of the biggest cloud breaches, and it's an app flaw with an enormous payoff. v2 needs a PUT with
a custom header, which a naive SSRF can't do, and hop limit 1 stops it being proxied out of a
container.** One line, no downside. Then the CI half: **OIDC with the subject pinned to org, repo and
ref — `repo:acme/*` grants the whole org, and conditioning on a GitHub environment makes human
approval part of the IAM condition.** Close with the Python one nobody expects: **workers that die
after exactly an hour because someone passed literal STS keys into a client botocore can't refresh.**
