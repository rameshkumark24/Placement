# Part 1 — ⭐ The API you are aiming for

```python
from myframework import App, JSONResponse

app = App()

@app.middleware
def timing(next_handler): ...                    # ⭐ Day 108

@app.on_startup                                   # ⭐ Day 110's lifespan
async def connect_db(): app.state.pool = await create_pool()

@app.route("/users/{user_id:int}", methods=["GET"])     # ⭐ Day 107
def get_user(request, user_id: int):                    # ⭐⭐ path param INJECTED by name
    return JSONResponse({"id": user_id})

@app.exception_handler(NotFound)                  # ⭐ Part 3
def handle_not_found(request, exc):
    return JSONResponse({"error": str(exc)}, 404)
```

```
⭐⭐ DESIGN THE PUBLIC API FIRST, BEFORE THE INTERNALS. ⭐ It is Day 096's first
⭐   test all over again: writing the CALL SITE is the only place the ergonomics
⭐   are visible, and it decides the internals rather than the other way round.
⭐   ⇒ ⭐ note the decision already made above: handlers receive path params AS
⭐        NAMED ARGUMENTS, not by digging in `request.params`. ⭐⭐ That single
⭐        choice is what forces Part 4's signature inspection to exist.
```

# Part 2 — ⭐ The `App` object

```python
class App:
    def __init__(self):
        self.router = Router()
        self.middlewares: list = []
        self.exception_handlers: dict[type, Callable] = {}
        self.startup_hooks: list = []
        self.shutdown_hooks: list = []
        self.state = SimpleNamespace()
        self._handler = None                      # ⭐ built once, at startup

    def route(self, path, methods=("GET",), name=None):
        def decorator(fn):
            self.router.add(path, fn, methods=set(methods), name=name or fn.__name__)
            return fn                             # ⭐⭐ return the FUNCTION, not a wrapper
        return decorator

    def build(self):
        """⭐⭐ Compose ONCE, at startup — not per request."""
        self.router.validate()                    # ⭐ Part 3
        handler = self._dispatch
        for mw in reversed(self.middlewares):     # ⭐ Day 108
            handler = mw(handler)
        self._handler = handler
```

```
⭐⭐ TWO DECISIONS WORTH DEFENDING:
⭐  1. ⭐⭐ `route` RETURNS THE ORIGINAL FUNCTION, not a wrapper. ⭐ So the
⭐       handler stays directly callable and directly testable — ⭐⭐ you can unit
⭐       test `get_user(request, 42)` with no framework at all. ⭐ Flask and
⭐       FastAPI both do this, and it is why their handlers are ordinary
⭐       functions (Day 044's `wraps` discussion, avoided entirely by not
⭐       wrapping).
⭐  2. ⭐⭐ COMPOSE THE CHAIN ONCE IN `build()`. ⭐ Rebuilding the middleware
⭐       onion per request is pure waste, and it is a real mistake in
⭐       hand-rolled frameworks (Day 100A: do less work).
```

# Part 3 — ⭐⭐ Fail at startup, not at 3 a.m.

```python
def validate(self):                               # ⭐ Router.validate
    seen_names, compiled = set(), []
    for route in self.routes:
        if route.name in seen_names:
            raise ConfigError(f"duplicate route name {route.name!r}")   # ⭐ breaks url_for
        seen_names.add(route.name)
        for earlier in compiled:                  # ⭐⭐ Day 107's ordering trap, automated
            if earlier.pattern.match(route.example_path()) and \
               earlier.methods & route.methods:
                raise ConfigError(
                    f"{route.template!r} is unreachable — {earlier.template!r} "
                    f"matches it first. Declare static routes before dynamic ones."
                )
        compiled.append(route)
```

```
⭐⭐ THIS IS THE HIGHEST-VALUE TWENTY LINES IN THE FRAMEWORK, AND ALMOST NO
⭐   HAND-ROLLED FRAMEWORK HAS IT. Day 107's trap — `/users/{name}` shadowing
⭐   `/users/me` — is silent, presents as an auth bug, and costs hours.
⭐   ⇒ ⭐⭐ A STARTUP `ConfigError` WITH THE FIX IN THE MESSAGE CONVERTS THAT
⭐        INTO A BOOT FAILURE, which is Day 090's principle applied to routing:
⭐        A MISCONFIGURED PROCESS SHOULD DIE LOUDLY AT BOOT.
⭐   ⇒ ⭐ other things worth validating at startup: a handler whose signature
⭐        requires a parameter no route can supply; a middleware that is not
⭐        callable; a duplicate `(path, method)` pair.
```

```python
def _handle_exception(self, request, exc):
    for cls in type(exc).__mro__:                 # ⭐⭐ Day 054's MRO, doing real work
        if cls in self.exception_handlers:
            return self.exception_handlers[cls](request, exc)
    raise
```

⭐⭐ **Walking the MRO is what makes `@app.exception_handler(HTTPError)` catch every subclass** — so
you register one handler for a family and specific ones where you need them, and the *most specific*
registered handler wins because `__mro__` is ordered nearest-first (Day 054). ⭐ **This is exactly how
FastAPI's exception handlers work.**

# Part 4 — ⭐⭐ Dependency injection, demystified

```python
import inspect

def _call_handler(self, fn, request, path_params: dict):
    sig = inspect.signature(fn)                          # ⭐ Day 042's introspection
    kwargs = {}
    for name, param in sig.parameters.items():
        if name == "request":
            kwargs[name] = request
        elif name in path_params:
            kwargs[name] = path_params[name]             # ⭐ already converted (Day 107)
        elif name in self.dependencies:
            kwargs[name] = self.dependencies[name](request)   # ⭐⭐ e.g. `user`, `db`
        elif param.default is not inspect.Parameter.empty:
            continue                                     # ⭐ optional — let the default apply
        else:
            raise ConfigError(f"{fn.__name__}: cannot supply {name!r}")   # ⭐⭐ at STARTUP
    return fn(**kwargs)
```

```
⭐⭐ THAT IS THE WHOLE SECRET OF `Depends`, AND IT IS FIFTEEN LINES:
⭐   READ THE SIGNATURE, RESOLVE EACH PARAMETER BY NAME OR TYPE, CALL THE
⭐   FUNCTION. ⭐ FastAPI adds type-based resolution, caching within a request,
⭐   `yield` dependencies for teardown (Day 052's context manager), and
⭐   sub-dependency graphs — ⭐⭐ but the mechanism is exactly this.
⭐   ⇒ ⭐⭐ AND IT IS ALSO pytest's FIXTURE MECHANISM (Day 093). Same idea, same
⭐        introspection, different vocabulary. ⭐ Recognising that they are one
⭐        pattern is worth more than knowing either API.
⭐   ⇒ ⭐⭐ THE VALIDATION BELONGS AT STARTUP: walk every registered handler's
⭐        signature in `build()` and raise if anything is unsatisfiable. ⭐ A
⭐        typo in a parameter name should be a boot failure, not a 500 on the
⭐        one route nobody tested.
```

# Part 5 — ⭐ The adapters, and what you left out

```python
class App:
    def __call__(self, environ, start_response):          # ⭐ WSGI (Day 109)
        return wsgi_adapter(self._handler)(environ, start_response)

    async def asgi(self, scope, receive, send):           # ⭐ ASGI (Day 110)
        if scope["type"] == "lifespan":
            return await self._lifespan(receive, send)
        ...
```

⭐⭐ **The adapters are thin because the framework core knows nothing about either protocol** — it
takes a `Request` and returns a `Response`. ⭐ **That is Day 090's layering, arrived at from the
inside:** the domain of a framework is routing and dispatch, and the protocol is an edge concern.

```
⭐⭐ WHAT YOU DELIBERATELY DID NOT BUILD — and naming the omissions is itself
⭐   the exercise:
⭐   · ⭐ REQUEST VALIDATION (Day 119) — you take `dict`s and trust them
⭐   · ⭐ SESSIONS, auth, CSRF (Days 114-118)
⭐   · ⭐ OpenAPI generation (Day 126) — ⭐⭐ though note it is now POSSIBLE,
⭐        because routes are data (Day 107) and signatures are inspectable
⭐   · ⭐ background tasks, WebSocket routing, templating, a CLI, static files
⭐   · ⭐⭐ TWENTY YEARS OF EDGE CASES: unicode paths, multipart uploads, HTTP/2,

```

⭐⭐ THE HONEST REFLECTION, AND IT IS THE POINT OF THE WHOLE STAGE:

## Common mistakes

| Mistake | Correction |
|---|---|
| ⭐ Building the middleware chain per request | ⭐ Compose once in `build()`. |
| ⭐ `route` returning a wrapper | ⭐⭐ Return the function — handlers stay directly testable. |
| ⭐⭐ **No startup validation** | ⭐⭐ Unreachable routes and unsatisfiable signatures should be boot failures. |
| Exception handlers matched by exact type | ⭐ Walk the MRO so a base class catches subclasses. |
| ⭐ Protocol details leaking into the core | ⭐ Core takes a `Request`, returns a `Response`. Adapters stay thin. |
| Digging path params out of `request.params` | ⭐⭐ Inject by name — visible in the signature (Days 089, 108). |
| ⭐ Silent failure when a parameter cannot be supplied | ⭐ `ConfigError` at startup with the fix in the message. |
| Concluding frameworks are trivial | ⭐⭐ 300 lines vs 7,000 is edge cases and ecosystem, not cleverness. |

## Interview questions

**Q: What actually is a web framework?**
> A router, a middleware chain, request and response objects, an exception registry, and an adapter to
> a server protocol. I built one — it's about three hundred lines and it runs under both gunicorn and
> uvicorn. The reason that's worth doing isn't that you'd ship it: Flask is seven thousand lines and
> the difference is edge cases, an extension system and twenty years of bug reports. It's that
> afterwards you know which parts of a request are HTTP and which parts are the framework, which is
> exactly the seam interviews probe.

**Q: How does FastAPI's `Depends` work?**
> Signature inspection. It reads the handler's parameters and resolves each one — from path
> parameters, query parameters, the body, or a registered dependency — then calls the function with
> keyword arguments. That's about fifteen lines in its simplest form; FastAPI adds type-based
> resolution, per-request caching, `yield` dependencies for teardown, and sub-dependency graphs. The
> nice recognition is that it's the same mechanism as pytest fixtures: same introspection, same
> resolve-by-name, different vocabulary.

**Q: What would you validate at application startup?**
> Anything that would otherwise be a 500 on the one route nobody tested. Unreachable routes — where an
> earlier dynamic pattern shadows a later static one, which is silent and presents as an auth bug.
> Duplicate route names, because they break reverse routing. Handlers whose signature asks for
> something no route can supply. And config, which is the same principle from a different angle: a
> misconfigured process should die loudly at boot rather than surprising one user at 3 a.m. It's about
> twenty lines and almost no hand-rolled framework has it.

**Q: Why does your exception handler walk the MRO?**
> So registering a handler for a base class catches its subclasses. You register one handler for
> `HTTPError` and it covers the whole family, and a more specific registration wins because `__mro__`
> is ordered nearest-first. Without it you'd need an entry per concrete exception type and the
> registry would drift out of date the first time someone adds a subclass. It's the same lookup
> FastAPI does.
