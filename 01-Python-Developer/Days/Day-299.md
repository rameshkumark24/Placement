# Day 299 🏛️

**P-299** · 🏛️ **Layered architecture** — ⭐⭐ and the four ways it rots

**Time:** 3 hrs · **Mode:** LEARN + BUILD

> ⭐⭐ **The sentence to own: a layer boundary that is not enforced by a tool is a boundary that
> exists in the README and nowhere else — because every violation of it is locally rational, done
> under time pressure, by someone who intends to clean it up.**
>
> ⭐ Layers are the default architecture, and they work. ⭐⭐ Today is why they work, the four
> specific ways they decay, and the twelve lines of CI configuration that stop all four.

---

# Part 1 — ⭐⭐ What layers actually buy

```
⭐   ⭐ web/          ⇒ HTTP: routes, schemas, status codes
⭐   ⭐ services/     ⇒ use cases: orchestration, transactions
⭐   ⭐ domain/       ⇒ rules, entities, invariants
⭐   ⭐ infrastructure/ ⇒ ORM, clients, queues, cache

⭐⭐ AND ONE RULE: ***DEPENDENCIES POINT ONE WAY.***

⭐⭐ WHAT THAT BUYS, STATED AS CHANGE COSTS (Day 298):
⭐   ⭐ THE MOST COMMON CHANGE — a new endpoint — ⭐⭐ TOUCHES
⭐     ONE LAYER. ⭐ That is the entire everyday value.
⭐   ⭐ THE MOST DANGEROUS CHANGE — a domain rule — ⭐⭐ IS
⭐     VISIBLE, because it happens in a directory whose diffs
⭐     people read differently.
⭐   ⭐ AND THE MOST FREQUENT ***QUESTION*** — "where does this
⭐     code go?" — ⭐ has a default answer, which is worth more
⭐     than it sounds: ⭐⭐ AN ARCHITECTURE THAT ANSWERS THAT
⭐     QUESTION CONSISTENTLY BEATS A BETTER ONE THAT DOESN'T.

⭐ ⇒ ⭐ Layers are unfashionable and almost always correct.
⭐   ⭐⭐ THE FASHIONABLE ALTERNATIVES MOSTLY ADD A DIMENSION
⭐   (features, contexts) WITHOUT REMOVING THIS ONE.
```

# Part 2 — ⭐⭐ Rot ①: the leaky model

```
⭐⭐ THE SYMPTOM: AN ORM OBJECT CROSSES INTO THE WEB LAYER.
⭐   ⭐ `return order` from a route, or an ORM instance handed
⭐     to a template.
⭐   ⇒ ⭐⭐ NOW THE PRESENTATION LAYER CAN TRIGGER A QUERY.
⭐     ⭐ A template renders `order.customer.name` and issues
⭐       SQL — ⭐⭐ AFTER THE SERVICE LAYER RETURNED, AFTER THE
⭐       TRANSACTION CLOSED, AND IN A LOOP.
⭐   ⇒ ⭐ This is the Django lesson (Day 171) and the
⭐     DetachedInstanceError in SQLAlchemy, and both are the
⭐     same architectural fact: ⭐⭐ THE BOUNDARY WAS CROSSED BY
⭐     AN OBJECT THAT CARRIES A DATABASE CONNECTION WITH IT.

⭐⭐ WHY IT IS RANKED FIRST: it does not look like a violation.
⭐   ⭐ There is no import of `infrastructure` in the route.
⭐     ⭐⭐ THE COUPLING TRAVELLED INSIDE THE RETURN VALUE —
⭐     exactly Day 298's point about import graphs.

⭐ ⇒ ⭐ THE FIX IS ALREADY IN YOUR FLAGSHIP: the service
⭐   returns a DTO or a response schema (Day 257), never an
⭐   entity. ⭐⭐ AND THE TEST IS MECHANICAL: assert that the
⭐   objects a service returns have no lazy attributes and no
⭐   session — ⭐ or simply expire the session before
⭐   serialising and see what explodes.
```

# Part 3 — ⭐⭐ Rot ②: the anaemic domain

```
⭐⭐ THE SYMPTOM: entities are data bags; every rule lives in
⭐   a service.
⭐   ⭐ `class Order:` with fifteen fields and no methods.
⭐   ⭐ `OrderService.cancel()` is 180 lines and contains the
⭐     entire state machine.

⭐⭐ THE DIAGNOSTIC THAT IS FASTER THAN READING:
⭐   ***GREP FOR THE SAME VALIDATION IN MORE THAN ONE PLACE.***
⭐   ⭐ If `if order.status != "pending"` appears in four
⭐     services, ⭐⭐ THE RULE HAS NO HOME, SO IT HAS FOUR —
⭐     and one of them is already out of date. ⭐ (You cannot
⭐     tell which without reading all four, which is the cost.)

⭐ ⇒ ⭐ THE FIX IS NOT "MOVE EVERYTHING INTO THE ENTITY".
⭐   ⭐⭐ IT IS THE DAY 302 TEST, ARRIVING EARLY: ***WOULD THIS
⭐     RULE STILL EXIST IF THE APPLICATION WERE A PAPER FORM?***
⭐   ⭐ "An order can only be cancelled while pending" ⇒ yes ⇒
⭐     ⭐⭐ DOMAIN. It goes in `Order.cancel()`, which raises.
⭐   ⭐ "Cancelling sends an email and refunds via Stripe" ⇒
⭐     no ⇒ ⭐ APPLICATION. It stays in the service.

⭐⭐ AND THE HONEST COUNTERPOINT, BECAUSE THIS IS OVER-APPLIED:
⭐   ⭐ A CRUD table with no rules ⭐⭐ SHOULD HAVE AN ANAEMIC
⭐     MODEL. ⭐ Inventing behaviour for `Country` so it isn't
⭐     "anaemic" is ceremony. ⭐⭐ THE SMELL IS AN ANAEMIC
⭐     MODEL FOR SOMETHING THAT HAS REAL RULES — not anaemia
⭐     itself.
```

---

# Part 4 — ⭐⭐ Rot ③: the shortcut that skips a layer

```
⭐⭐ THE SYMPTOM: A ROUTE IMPORTS A REPOSITORY DIRECTLY.
⭐   ⭐ `@app.get("/health/orders")` needs one count. ⭐ Writing
⭐     a service method for it is three files of ceremony for
⭐     one query. ⭐⭐ SO YOU SKIP IT — AND YOU ARE RIGHT, THIS
⭐     ONE TIME.

⭐⭐ THE PROBLEM IS NOT THIS CALL. IT IS THAT THE RULE IS NOW
⭐   "SOMETIMES", AND ⭐⭐ "SOMETIMES" IS NOT A RULE — IT IS A
⭐   JUDGEMENT CALL MADE BY EVERY FUTURE DEVELOPER UNDER
⭐   DEADLINE, INCLUDING THE ONE WHO NEEDS A TRANSACTION.
⭐   ⇒ ⭐ Six months later a route opens a transaction, calls
⭐     three repositories, and there is no service anywhere —
⭐     ⭐⭐ SO THE TRANSACTION BOUNDARY IS IN THE WEB LAYER,
⭐     WHICH IS EXACTLY THE FAILURE DAY 256 EXISTS TO PREVENT.

⭐⭐ THE TWO HONEST RESOLUTIONS — PICK ONE AND WRITE IT DOWN:
⭐   ⭐ ① STRICT: routes only ever call services. ⭐ Accept the
⭐        three-line pass-through methods as the price.
⭐   ⭐ ② ⭐⭐ EXPLICIT READ PATH: routes may use a `queries/`
⭐        module for READS ONLY — no writes, no transactions —
⭐        which is CQRS-lite (Day 255) and is a ***stated***
⭐        exception rather than an eroded rule.
⭐   ⇒ ⭐⭐ WHAT YOU MAY NOT DO IS LEAVE IT UNDECIDED, because
⭐     an unstated exception is indistinguishable from decay.
```

---

# Part 5 — ⭐⭐ Rot ④: the god service

```
⭐⭐ THE SYMPTOM: `UserService` HAS FORTY METHODS AND IS
⭐   IMPORTED BY EVERYTHING.
⭐   ⭐ It grew because "it's about users", ⭐ which is a
⭐     categorisation, ⭐⭐ NOT A COHESION ARGUMENT (Day 298).

⭐⭐ THE MEASUREMENT THAT SETTLES IT: FOR EACH METHOD, WHICH
⭐   FIELDS AND TABLES DOES IT TOUCH?
⭐   ⭐ registration, login, password reset  → credentials
⭐   ⭐ profile update, avatar               → profile
⭐   ⭐ team invitations, role changes       → membership
⭐   ⇒ ⭐⭐ THREE DISJOINT CLUSTERS SHARING A CLASS NAME AND
⭐     NOTHING ELSE. ⭐ Split them, and every import gets
⭐     narrower and more honest.

⭐ ⭐ AND THE SECOND-ORDER COST, WHICH IS THE ONE PEOPLE FEEL:
⭐   ⭐⭐ A GOD SERVICE MAKES EVERY TEST SLOW, because
⭐   constructing it requires every dependency it has ever
⭐   needed — ⭐ so a test of password reset instantiates the
⭐   billing client. ⭐⭐ TEST SETUP PAIN IS A DESIGN SIGNAL,
⭐   and it is usually the first one you get.
```

# Part 6 — ⭐⭐ Making the layering a build failure

```
⭐⭐ ALL FOUR ROTS SHARE ONE PROPERTY: EACH INDIVIDUAL
⭐   VIOLATION IS REASONABLE. ⭐ So conventions do not hold
⭐   them, code review does not catch them (the reviewer is
⭐   also under deadline), and documentation does not stop them.
⭐   ⇒ ⭐⭐ ONLY A TOOL DOES.
```

```ini
# .importlinter        ⭐⭐ RUNS IN CI, FAILS THE BUILD
[importlinter]
root_package = app

[importlinter:contract:layers]
name = Layered architecture
type = layers
layers =
    app.web
    app.services
    app.domain            # ⭐⭐ domain may import NOTHING below

[importlinter:contract:domain-purity]
name = Domain imports no infrastructure
type = forbidden
source_modules = app.domain
forbidden_modules =
    app.infrastructure
    sqlalchemy
    fastapi
    redis
```

```
⭐⭐ THE SECOND CONTRACT IS THE VALUABLE ONE, AND IT IS ONE
⭐   LINE: ***`domain/` MAY NOT IMPORT `sqlalchemy` OR
⭐   `fastapi`.*** ⭐ That single rule prevents rot ① and most
⭐   of rot ②, mechanically, forever — ⭐⭐ AND IT FAILS ON THE
⭐   PULL REQUEST RATHER THAN IN A CODE REVIEW SIX MONTHS AFTER
⭐   THE PERSON WHO CARED ABOUT IT LEFT.

⭐ ⭐ ADD TWO MORE CHECKS WHILE YOU ARE THERE:
⭐   ⭐ a test asserting no route imports a repository (rot ③)
⭐   ⭐ a lint rule capping service module size — ⭐ crude, and
⭐     it catches rot ④ months before anyone notices.
```

# Part 7 — ⭐ When layers are the wrong shape

```
⭐   ⭐ A GENUINELY CRUD APPLICATION — ⭐⭐ LAYERS ADD FOUR
⭐     FILES PER TABLE AND PREVENT NOTHING, because there are
⭐     no rules to protect. ⭐ Django's grain is right there,
⭐     and fighting it is the actual mistake (Day 183).
⭐   ⭐ A SCRIPT OR A ONE-OFF PIPELINE — ⭐ ceremony with no
⭐     lifetime to amortise it over.
⭐   ⭐⭐ AND THE REAL LIMIT: LAYERS SLICE HORIZONTALLY, BUT
⭐     ***FEATURES ARE VERTICAL.*** ⭐ A new feature touches
⭐     all four layers, so a large system ends up with four
⭐     enormous directories and no locality — ⭐⭐ WHICH IS
⭐     EXACTLY THE PROBLEM THE MODULAR MONOLITH SOLVES BY
⭐     SLICING BY FEATURE ***FIRST*** AND LAYERING ***INSIDE***
⭐     EACH SLICE (Day 306).
⭐   ⇒ ⭐ So layers are right, and they are not the last word —
⭐     ⭐ which is a better position than either "layers are
⭐       obsolete" or "layers are all you need".
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Treating layering as a convention | Every violation is locally rational; only a tool holds the line. |
| Returning ORM objects from a service | The presentation layer can now trigger queries, after the transaction closed. |
| Assuming no import means no coupling | The coupling travelled inside the return value. |
| All logic in services | The same validation ends up in four places, and one is already stale. |
| Forcing behaviour onto every entity | A CRUD table should be anaemic; the smell is anaemia where rules exist. |
| A route calling a repository "just this once" | The rule becomes "sometimes", which is a judgement call under deadline. |
| Leaving the read-path exception unstated | An unstated exception is indistinguishable from decay. |
| Transactions in the web layer | The exact failure the service layer exists to prevent. |
| Grouping a service by noun | "It's about users" is a category, not cohesion. |
| Ignoring painful test setup | It's usually the first design signal you get. |
| Relying on code review to catch layer violations | The reviewer is under the same deadline. |
| No `domain/` purity contract | One line prevents rot ① and most of rot ② forever. |
| Layers on a genuinely CRUD app | Four files per table protecting no rules. |
| Assuming layers scale to a large system | Features are vertical; layers are horizontal. That's what the modular monolith fixes. |

## Interview questions

**Q: Why layers?**

> Because of what they do to change costs. The most common change — a new endpoint — touches one
> layer, and the most dangerous change — a domain rule — happens in a directory whose diffs people
> read more carefully. And there's an underrated third benefit: they answer "where does this code
> go?" consistently, and an architecture that answers that question the same way every time beats a
> theoretically better one that doesn't. They're unfashionable and almost always correct; most of the
> fashionable alternatives add a second dimension without removing this one.

**Q: How do layered architectures decay?**

> Four ways, and each individual violation is reasonable, which is why conventions don't hold them.
> The leaky model: an ORM object crosses into the web layer, so a template triggers a query after the
> transaction closed — and there's no import to see, because the coupling travelled inside the return
> value. The anaemic domain: rules live in services, so the same validation appears in four places and
> one of them is stale. The layer-skipping shortcut: a route calls a repository once, which is right
> that time, but now the rule is "sometimes", and six months later a transaction is running in the web
> layer. And the god service: forty methods grouped by noun rather than by cohesion, whose first
> visible symptom is that testing password reset instantiates the billing client.

**Q: How do you stop that?**

> With a tool, because it's the only thing that works. Import-linter contracts in CI: a layers
> contract for the direction of dependencies, and — the valuable one — a forbidden-import contract
> saying `domain/` may not import `sqlalchemy` or `fastapi`. That single line prevents the leaky
> model and most of the anaemic domain, mechanically, and it fails on the pull request rather than in
> a review six months after the person who cared about it left. Plus a test asserting no route imports
> a repository, and a crude size cap on service modules that catches the god service early.

**Q: Where do layers stop working?**

> They slice horizontally while features are vertical. Every new feature touches all four layers, so a
> large system ends up with four enormous directories and no locality — a change to billing is spread
> across four places that also contain everything else. That's the problem the modular monolith solves
> by slicing by feature first and layering inside each slice. I'd also say layers are wrong for a
> genuinely CRUD application, where they add four files per table and protect no rules — that's where
> Django's grain is right and fighting it is the mistake.

## Today's build

1. ⭐⭐ Add import-linter to the flagship with a layers contract and a `domain/` purity contract. Fix every violation it finds.
2. ⭐ Count the violations. That number is your honest layering score.
3. ⭐⭐ Expire the session before serialisation and see what breaks. Fix by returning DTOs.
4. ⭐ Grep for the same status or state validation in more than one service.
5. ⭐⭐ Move one such rule into the entity and make the service call it. Delete the duplicates.
6. ⭐ Find an anaemic model that *should* be anaemic and leave it. Write down why.
7. ⭐⭐ List every route that imports a repository. Decide strict or explicit-read-path, and write the decision down.
8. ⭐⭐ If you choose the read path, create `queries/` and add a test asserting it never opens a transaction.
9. ⭐ Find your largest service. For every method, list the tables it touches.
10. ⭐⭐ Split it along the clusters you find, and note how the imports narrow.
11. ⭐ Measure test setup time before and after the split.
12. ⭐⭐ Add a CI test asserting no route imports a repository, and a size cap on service modules.
13. ⭐ Apply the same contracts to `clearline`. Note which rot it has that the flagship doesn't.
14. ⭐⭐ Write down which of your projects would be better as vertical slices, and why.

## 🎙️ Articulation drill

**Two minutes: "Talk me through your project's structure."**

Give the layers and the one rule, then justify them by change cost rather than by tidiness: **the most
common change touches one layer, the most dangerous change happens somewhere people read diffs
carefully, and "where does this code go?" gets the same answer every time** — which is worth more than
it sounds. Then show you know how it fails, because that's the part that distinguishes experience:
**four rots, each of which is individually reasonable.** An ORM object crossing into the web layer, so
a template queries after the transaction closed — **and there's no import to see, because the coupling
travelled inside the return value.** Logic drifting into services until the same validation exists in
four places. A route calling a repository once, correctly, **which turns the rule into "sometimes" —
and six months later the transaction boundary is in the web layer.** And a service grouped by noun
whose first symptom is that testing password reset instantiates the billing client. Then the
conclusion that follows from "each violation is reasonable": **conventions and code review cannot hold
this, so it's a build failure** — import-linter contracts in CI, with the highest-value line being that
`domain/` may not import `sqlalchemy` or `fastapi`. Close honestly: **layers slice horizontally and
features are vertical**, which is why a large system eventually needs vertical slices with layers
inside them.
