# Part 2 — ⭐⭐ Ledger, not balances

```
⭐⭐ THE TEMPTING DESIGN: `User.balance_with(other) -> Money`,
⭐   updated on every expense.
⭐   ⇒ ⭐ ① Two concurrent expenses ⇒ lost update (Day 310).
⭐   ⇒ ⭐ ② Editing an expense means ***reversing*** its effect
⭐        on a number, and one bug is permanent drift.
⭐   ⇒ ⭐⭐ ③ AND THE FATAL ONE: "WHY DO I OWE ₹340?" HAS NO
⭐        ANSWER. ⭐ The number is correct or it is not, and
⭐        nobody — including you — can tell which.

⭐⭐ THE LEDGER DESIGN:
⭐   ⭐ `Expense` — who paid, total, split type, ⭐ IMMUTABLE
⭐   ⭐ `Share` — (expense_id, user_id, amount) ⭐ IMMUTABLE
⭐   ⭐ ⭐⭐ BALANCE = SUM OVER SHARES. ***DERIVED, NEVER
⭐        STORED.***
⭐   ⇒ ⭐ An edit is a ***new*** expense superseding the old
⭐     (Day 289), or a reversal plus a replacement.
⭐   ⇒ ⭐⭐ "WHY DO I OWE ₹340?" IS NOW A QUERY THAT RETURNS
⭐     SEVEN ROWS WITH DATES AND DESCRIPTIONS — which is the
⭐     product, not an implementation detail.

⭐ ⭐ AND THE PERFORMANCE OBJECTION, ANSWERED PROPERLY:
⭐   ⭐ Summing every share for an active group is slow.
⭐   ⇒ ⭐⭐ CACHE THE BALANCE AS A ***MATERIALISED ROLLUP***
⭐     (Day 269), with the rule that it must be rebuildable
⭐     from the ledger at any time — ⭐ so it is a cache, not a
⭐     source of truth, and a reconciliation job proves it.
```

# Part 3 — ⭐⭐ The penny problem

```
⭐⭐ ₹100 SPLIT THREE WAYS. ⭐ Naively: 33.33 each = ₹99.99.
⭐   ⭐⭐ ONE PAISA HAS VANISHED, AND OVER A YEAR OF EXPENSES
⭐   THE GROUP'S BALANCES NO LONGER SUM TO ZERO — which is the
⭐   bug report "the numbers don't add up", filed by everyone.

⭐⭐ THE INVARIANT THAT MUST HOLD FOR EVERY SINGLE EXPENSE:
⭐   ***THE SHARES SUM ***EXACTLY*** TO THE TOTAL.***
```

```python
def allocate(total: int, weights: list[int]) -> list[int]:
    """⭐ total in minor units. Largest-remainder allocation."""
    w = sum(weights)
    base = [total * x // w for x in weights]        # ⭐ floor division
    remainder = total - sum(base)                    # ⭐⭐ 0..len-1 paise
    order = sorted(range(len(weights)),
                   key=lambda i: (-(total * weights[i] % w), i))  # ⭐ tiebreak
    for i in order[:remainder]:
        base[i] += 1
    return base                                      # ⭐⭐ SUMS EXACTLY
```

```
⭐⭐ FOUR THINGS TO SAY ABOUT THIS:
⭐   ⭐ INTEGER MINOR UNITS THROUGHOUT (Day 304). ⭐ No floats,
⭐     anywhere, ever.
⭐   ⭐ ⭐⭐ THE LEFTOVER PAISE GO TO THE LARGEST REMAINDERS —
⭐     the fairest deterministic rule.
⭐   ⭐ ⭐⭐ THE TIEBREAK ON INDEX MAKES IT ***DETERMINISTIC***:
⭐     the same expense allocated twice gives the same answer,
⭐     which matters because an edit re-allocates and users
⭐     would otherwise see a paisa move for no reason.
⭐   ⭐ ⭐⭐ AND THE PROPERTY TEST THAT IS WORTH MORE THAN THE
⭐     FUNCTION: ***FOR ANY TOTAL AND ANY WEIGHTS, THE PARTS SUM
⭐     TO THE TOTAL AND DIFFER BY AT MOST ONE MINOR UNIT.***
⭐     ⭐ Offer to write it unprompted.
```

# Part 4 — ⭐⭐ 15–30: the model

```python
class SplitStrategy(Protocol):
    def shares(self, total: Money, participants: Sequence[UserId],
               spec: Any) -> dict[UserId, Money]: ...

class EqualSplit:
    def shares(self, total, participants, spec=None):
        amounts = allocate(total.minor_units, [1] * len(participants))
        return {u: Money(a, total.currency)
                for u, a in zip(participants, amounts)}

class ExactSplit:
    def shares(self, total, participants, spec: dict[UserId, int]):
        if sum(spec.values()) != total.minor_units:      # ⭐⭐ VALIDATE
            raise SharesDoNotSumToTotal(sum(spec.values()),
                                        total.minor_units)
        return {u: Money(v, total.currency) for u, v in spec.items()}

@dataclass(frozen=True)                                   # ⭐⭐ IMMUTABLE
class Expense:
    id: ExpenseId
    group_id: GroupId
    paid_by: UserId
    total: Money
    shares: Mapping[UserId, Money]
    created_at: datetime
    superseded_by: ExpenseId | None = None

    def __post_init__(self):
        if sum(s.minor_units for s in self.shares.values()) \
                != self.total.minor_units:
            raise SharesDoNotSumToTotal(...)              # ⭐⭐ THE INVARIANT,
                                                          #   ENFORCED AT BIRTH
```

```
⭐⭐ THE `__post_init__` CHECK IS THE MOST IMPORTANT LINE HERE:
⭐   ⭐ It makes an unbalanced expense ***UNCONSTRUCTIBLE***
⭐     (Day 304), so no strategy, import, migration or admin
⭐     script can create one.
⭐   ⇒ ⭐ And the database mirrors it: ⭐⭐ A CONSTRAINT OR A
⭐     TRIGGER, because the same reasoning as Day 311 applies —
⭐     the class protects the code path you know about.
```

# Part 5 — ⭐⭐ 30–40: settlement and simplification

```
⭐⭐ BALANCES ARE A DIRECTED GRAPH: A owes B ₹300, B owes C
⭐   ₹300, C owes A ₹100.
⭐   ⭐ Literal settlement = 3 payments.
⭐   ⭐⭐ NET EACH PERSON FIRST: A −200, B 0, C +200
⭐        ⇒ ⭐ ONE PAYMENT: A → C ₹200.

⭐⭐ THE ALGORITHM (greedy, and be honest about it):
⭐   ① net every user to a single balance
⭐   ② two heaps: creditors and debtors
⭐   ③ repeatedly match the largest debtor to the largest
⭐      creditor for `min(|d|, c)`
⭐   ⇒ ⭐ Yields at most ***n − 1*** transfers.
⭐   ⇒ ⭐⭐ AND SAY THIS: MINIMISING THE NUMBER OF TRANSFERS
⭐     EXACTLY IS NP-HARD (it is subset-sum in disguise), SO
⭐     THIS IS A GREEDY HEURISTIC — ⭐ near-optimal in practice,
⭐     and knowing which problem you are approximating is the
⭐     senior answer. ⭐ Do not claim optimality.

⭐⭐ AND THE PRODUCT WARNING PEOPLE MISS:
⭐   ⭐ Simplification ⭐⭐ CREATES DEBTS BETWEEN PEOPLE WHO
⭐     NEVER TRANSACTED. ⭐ "Why do I owe Priya? I've never
⭐     bought her anything."
⭐   ⇒ ⭐⭐ SO IT IS OPT-IN, AND THE UI MUST SHOW THE ***PATH***.
⭐     ⭐ Which is only possible because Part 2 kept the ledger.
```

# Part 6 — ⭐ Concurrency and the rest

```
⭐   ⭐ ⭐⭐ CONCURRENCY IS ALMOST ABSENT BY DESIGN, AND THAT IS
⭐     THE POINT: appending immutable rows has no shared mutable
⭐     state (Day 310). ⭐ Two people adding expenses at once
⭐     simply both append.
⭐   ⇒ ⭐ The only race is ⭐⭐ SETTLEMENT AGAINST A CHANGING
⭐     LEDGER: you compute "A owes C ₹200", someone adds an
⭐     expense, and the settlement is stale.
⭐   ⇒ ⭐ Fix: a settlement records the ledger version it was
⭐     computed from, ⭐⭐ AND IS ITSELF A LEDGER ENTRY — so it
⭐     nets out rather than overwriting anything.
⭐   ⭐ MULTI-CURRENCY: ⭐⭐ STORE THE RATE AND THE DATE ON THE
⭐     EXPENSE. ⭐ Converting at read time means last year's
⭐     dinner changes price today (Day 269).
⭐   ⭐ DELETION: ⭐ a reversing entry, never a `DELETE` —
⭐     ⭐⭐ AND "WHO DELETED WHAT" IS A FEATURE IN A SHARED
⭐     FINANCIAL APP, not an audit nicety.
⭐ ⇒ ⭐ CLOSE: three tests (allocation property test, balance
⭐   derivation after an edit, settlement nets to zero); one
⭐   change (rollup with reconciliation); ⭐⭐ AT 100×: a group
⭐   with 50,000 expenses makes derivation slow — that is when
⭐   the rollup stops being optional.
```

## Common mistakes

| Mistake | Correction |
|---|---|
| Storing balances | Lost updates, permanent drift after an edit, and "why do I owe this?" has no answer. |
| Treating the rollup as truth | It's a cache; it must be rebuildable from the ledger and reconciled. |
| Mutable expenses | An edit becomes arithmetic on a number instead of a new immutable fact. |
| Floats for money | The paisa vanishes and balances stop summing to zero. |
| Naive division for splits | ₹100 three ways loses a paisa every time. |
| Non-deterministic remainder allocation | Re-editing moves a paisa between users for no reason. |
| Not validating exact splits | An expense whose shares don't sum to the total is a permanent inconsistency. |
| The invariant only in the service | Make it unconstructible, and mirror it in the database. |
| Claiming optimal settlement | Exact minimisation is NP-hard; this is a greedy heuristic. |
| Simplification on by default | It creates debts between people who never transacted. |
| Converting currency at read time | Last year's dinner changes price today. |
| Deleting expenses | A reversing entry; deletion history is a feature here. |
| Ignoring stale settlements | Record the ledger version, and make settlement a ledger entry. |

## Interview questions

**Q: Where do balances live?**

> Nowhere — they're derived. Expenses and shares are immutable rows, and a balance is a sum over them.
> Storing balances gives you three problems: concurrent expenses lose updates, an edit becomes
> arithmetic on a running total where one bug is permanent drift, and — the one that matters most —
> "why do I owe three hundred and forty rupees?" has no answer. With a ledger it's a query returning
> seven rows with dates and descriptions, which is the product rather than an implementation detail.
> If derivation gets slow I add a materialised rollup, with the rule that it's rebuildable from the
> ledger and reconciled, so it stays a cache and not a second source of truth.

**Q: Split a hundred rupees three ways.**

> Not 33.33 each, because that's 99.99 and the paisa is gone — repeat that across a year and the
> group's balances stop summing to zero, which is the bug report everyone files. I work in integer
> minor units and use largest-remainder allocation: floor divide, then distribute the leftover paise
> to the largest remainders, with a tiebreak on index so it's deterministic — because an edit
> re-allocates, and without determinism a paisa moves between people for no visible reason. And I'd
> offer the property test, which is worth more than the function: for any total and any weights, the
> parts sum exactly to the total and differ by at most one minor unit.

**Q: How do you minimise the number of settlement payments?**

> Net every person to a single balance, then greedily match the largest debtor to the largest
> creditor, which gives at most n − 1 transfers. And I'd be explicit that exact minimisation is
> NP-hard — it's subset-sum in disguise — so this is a heuristic that's near-optimal in practice.
> Claiming optimality is the trap. There's also a product consequence people miss: simplification
> creates debts between people who never transacted, so it's opt-in and the UI has to show the path —
> which is only possible because the ledger was kept.

**Q: What's the concurrency story?**

> Almost absent, and that's a design outcome rather than luck: appending immutable rows has no shared
> mutable state, so two people adding expenses simultaneously just both append. The only real race is
> settlement against a changing ledger — you compute that A owes C two hundred, someone adds an
> expense, and the settlement is stale. So a settlement records the ledger version it was computed
> from, and is itself a ledger entry, which means it nets out rather than overwriting anything.

## 🎙️ Articulation drill

**Two minutes.** Lead with the structural decision: **this is a ledger, not a balance sheet** —
immutable expenses and shares, balances derived. Give the three reasons, ending on the one that
matters: **"why do I owe ₹340?" has no answer if you stored a number**, and it's seven rows with dates
if you kept the ledger. Handle the performance objection with a rollup that must be rebuildable and
reconciled. Then the penny problem: **₹100 three ways is 99.99, and over a year balances stop summing
to zero** — integer minor units, largest-remainder allocation, and a deterministic tiebreak because an
edit re-allocates and a paisa shouldn't move for no reason. Offer the property test. Say where the
invariant lives: **unconstructible in `__post_init__` and mirrored as a database constraint**, because
the class only protects the path you know about. Then settlement: net everyone, greedily match largest
debtor to largest creditor for at most n−1 transfers, **and say that exact minimisation is NP-hard so
this is a heuristic** — plus the product warning that simplification creates debts between people who
never transacted. Close on concurrency being almost absent by design, because appending immutable rows
shares no mutable state.
