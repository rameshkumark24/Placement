# Day 378 ☸️

**P-378** · ☸️ **Kubernetes II** — graceful shutdown, disruption budgets, ⭐⭐ and when it is overkill

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: pods are killed constantly and on purpose — by deploys, autoscaling, node
> upgrades, spot reclamation and the scheduler rebalancing — so the only question that matters is

# Part 1 — ⭐⭐ Pod termination, every step

```
⭐⭐ THE FULL SEQUENCE, AND ***TWO THINGS HAPPEN IN PARALLEL***
⭐   — which is the fact everything else depends on:
⭐   ① ⭐ The pod is marked `Terminating`.
⭐   ② ⭐⭐ ***IN PARALLEL***: (a) THE ENDPOINT CONTROLLER REMOVES
⭐      IT FROM THE SERVICE, AND (b) THE KUBELET RUNS `preStop`
⭐      THEN SENDS SIGTERM.
⭐   ⇒ ⭐⭐ THEY ARE NOT ORDERED. ⭐ Endpoint removal must
⭐      propagate to every node's iptables/IPVS rules, to the
⭐      ingress controller, and to any client-side balancer —
⭐      ⭐⭐ AND THAT PROPAGATION TAKES HUNDREDS OF MILLISECONDS
⭐      TO SECONDS, WHILE SIGTERM ARRIVES IMMEDIATELY.
⭐   ③ ⭐ The process should drain.
⭐   ④ ⭐⭐ AFTER `terminationGracePeriodSeconds`: SIGKILL. ⭐ No
⭐      further negotiation.

⭐⭐ ⇒ SO THE RACE IS: ***TRAFFIC IS STILL BEING ROUTED TO YOU
⭐   AFTER YOU HAVE BEEN TOLD TO STOP.*** ⭐ If you stop
⭐   accepting immediately, those requests get connection
⭐   refused — ⭐⭐ WHICH IS EXACTLY WHERE DEPLOY-TIME 502s COME
⭐   FROM, AND WHY THEY LOOK LIKE A RANDOM NETWORK PROBLEM FOR
⭐   MONTHS.

⭐⭐ THE FIX, AND IT IS FIVE LINES:
⭐   ⭐ ⭐⭐ A `preStop` HOOK THAT SLEEPS 5–10 SECONDS.
⭐   ⇒ ⭐ SIGTERM is delayed until the hook finishes, ⭐ so the
⭐     pod keeps serving normally while endpoint removal
⭐     propagates.
⭐   ⇒ ⭐⭐ AND IT WORKS EVEN FOR APPLICATIONS THAT HANDLE
⭐     SIGTERM BADLY, WHICH IS WHY IT IS THE MOST RELIABLE FIX
⭐     RATHER THAN THE MOST ELEGANT ONE.
```

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "10"]      # ⭐⭐ ENDPOINT PROPAGATION WINDOW
terminationGracePeriodSeconds: 45   # ⭐ 10 (preStop) + p99 + cleanup
```

```
⭐⭐ AND THE APPLICATION'S HALF (Days 324, 366):
⭐   ⭐ Exec-form `CMD` so SIGTERM arrives at all (Day 361).
⭐   ⭐ On SIGTERM: ⭐⭐ FAIL READINESS, ***NOT*** LIVENESS.
⭐   ⭐ Finish in-flight requests up to a bound.
⭐   ⭐ Close pools, flush telemetry, exit 0.
⭐   ⇒ ⭐⭐ VERIFY IT: EXIT 143 IS SIGTERM HANDLED; EXIT 137 IS
⭐     SIGKILL AND MEANS THE CHAIN IS BROKEN SOMEWHERE.
```

# Part 2 — ⭐⭐ Voluntary vs involuntary disruption

```
⭐⭐ THE DISTINCTION THAT ORGANISES EVERYTHING:
⭐   ⭐ ***INVOLUNTARY*** — node hardware failure, kernel panic,
⭐     ⭐ an OOMKill, ⭐ a spot instance reclaimed with two
⭐     minutes' notice.
⭐     ⇒ ⭐⭐ NOTHING CAN PREVENT THESE. ⭐ You survive them with
⭐       replicas and spreading.
⭐   ⭐ ***VOLUNTARY*** — a node drained for an upgrade, ⭐ a
⭐     cluster autoscaler removing an underused node, ⭐ a
⭐     rebalance.
⭐     ⇒ ⭐⭐ THESE ***CAN*** BE CONTROLLED, AND THAT IS WHAT A
⭐       `PodDisruptionBudget` IS FOR.

⭐⭐ ***PodDisruptionBudget***: "at most one of my pods may be
⭐   voluntarily evicted at a time", or "at least two must
⭐   remain available".
⭐   ⇒ ⭐⭐ WITHOUT ONE, A NODE-POOL UPGRADE CAN DRAIN THREE
⭐     NODES AND TAKE ***ALL THREE*** OF YOUR REPLICAS DOWN
⭐     SIMULTANEOUSLY — ⭐ and the cluster is behaving correctly.
⭐   ⇒ ⭐ `minAvailable: 2` with `replicas: 3` is the usual
⭐     shape.

⭐⭐ AND THE TWO TRAPS THAT MAKE PDBs BACKFIRE:
⭐   ① ⭐⭐ `minAvailable` EQUAL TO `replicas` ⇒ ***NOTHING CAN
⭐      EVER BE EVICTED***, so node drains hang forever and
⭐      cluster upgrades stall. ⭐ Someone eventually deletes the
⭐      PDB under pressure, ⭐⭐ AND THEN YOU HAVE NO PROTECTION
⭐      AT ALL.
⭐   ② ⭐⭐ A PDB WITH A SINGLE REPLICA IS MEANINGLESS: ⭐ either
⭐      it blocks all maintenance or it permits total
⭐      unavailability. ⭐⭐ THE REAL FIX FOR A SINGLE-REPLICA
⭐      SERVICE IS A SECOND REPLICA, NOT A BUDGET.

⭐⭐ AND SPREADING, WHICH IS THE OTHER HALF:
⭐   ⭐ ⭐⭐ THREE REPLICAS ON ***ONE NODE*** SURVIVE NOTHING.
⭐   ⇒ ⭐ `topologySpreadConstraints` across nodes and
⭐     availability zones, ⭐ with `whenUnsatisfiable:
⭐     ScheduleAnyway` unless you genuinely prefer `Pending`
⭐     pods to imperfect placement — ⭐⭐ AND `DoNotSchedule` ON A
⭐     SMALL CLUSTER IS HOW YOU GET PODS THAT NEVER START.
```

# Part 3 — ⭐⭐ Autoscaling, and what to scale on

```
⭐⭐ THREE AUTOSCALERS, THREE JOBS:
⭐   ⭐ ***HPA*** — more pods.
⭐   ⭐ ***VPA*** — bigger pods. ⭐⭐ AND IT RESTARTS PODS TO
⭐     APPLY, SO IT CONFLICTS WITH HPA ON THE SAME METRIC. ⭐ Use
⭐     VPA in ***recommendation*** mode to size requests
⭐     correctly, which is its most valuable use.
⭐   ⭐ ***CLUSTER AUTOSCALER / KARPENTER*** — more nodes,
⭐     ⭐⭐ WITHOUT WHICH HPA SCALES INTO `Pending` PODS AND
⭐     NOTHING IMPROVES.

⭐⭐ ⭐⭐ WHY CPU IS THE WRONG METRIC FOR A PYTHON WEB SERVICE
⭐   — ⭐ and this pays off Day 287:
⭐   ⭐ An I/O-bound async service can be at ⭐⭐ 30% CPU AND
⭐     COMPLETELY SATURATED, because it is waiting on the
⭐     database, not computing.
⭐   ⭐ ⭐⭐ CPU RISES ***AFTER*** LATENCY DOES, SO YOU SCALE
⭐     AFTER USERS ARE ALREADY SUFFERING.
⭐   ⭐ ⭐⭐ AND WITH A CPU ***LIMIT*** SET, THROTTLING KEEPS
⭐     REPORTED CPU BELOW THE TARGET WHILE LATENCY EXPLODES
⭐     (Day 361) — ⭐ so the autoscaler sees a healthy number and
⭐     does nothing.

⭐⭐ WHAT TO SCALE ON INSTEAD, BEST FIRST:
⭐   ① ⭐⭐ ***REQUESTS PER SECOND PER POD*** — ⭐ directly
⭐      proportional to what arrives, and it leads latency.
⭐   ② ⭐⭐ ***IN-FLIGHT REQUESTS PER POD*** — ⭐ Little's Law's L
⭐      (Day 322), which is the truest measure of business.
⭐   ③ ⭐⭐ ***QUEUE AGE*** for workers — ⭐ not depth, ⭐ and it
⭐      is the metric that maps to a user's wait (Days 262, 373).
⭐   ④ ⭐ Latency itself — ⭐⭐ AND CAREFULLY, BECAUSE SCALING ON
⭐      LATENCY CAN AMPLIFY A ***DEPENDENCY*** PROBLEM: more
⭐      pods, more connections, a slower database, more latency.
⭐   ⇒ ⭐ All of these need `custom.metrics.k8s.io` (Prometheus
⭐     Adapter or KEDA). ⭐⭐ KEDA IS USUALLY THE PRACTICAL ANSWER
⭐     FOR QUEUE-DRIVEN WORKLOADS AND SCALES TO ZERO.

⭐⭐ AND THE FOUR THINGS THAT MAKE AUTOSCALING BEHAVE:
⭐   ⭐ ⭐⭐ STABILISATION WINDOWS — ⭐ scale up fast (0–30 s),
⭐     ⭐ scale down slowly (5+ minutes). ⭐⭐ ASYMMETRY IS THE
⭐     WHOLE POINT: THE COST OF BEING TOO SMALL IS AN OUTAGE;
⭐     THE COST OF BEING TOO BIG IS PENNIES.
⭐   ⭐ ⭐⭐ SLOW STARTUP DEFEATS AUTOSCALING. ⭐ A 30-second boot
⭐     (Day 366) means new capacity arrives after the spike is
⭐     over — ⭐ cold start is a ***scalability*** property.
⭐   ⭐ `minReplicas ≥ 2`, always — ⭐⭐ ONE REPLICA HAS NO
⭐     ROLLING DEPLOY AND NO DISRUPTION TOLERANCE.
⭐   ⭐ ⭐⭐ AND THE CEILING NOBODY CHECKS: SCALING PODS SCALES
⭐     ***DATABASE CONNECTIONS*** (Day 332). ⭐ Thirty pods × a
⭐     pool of ten is three hundred connections; ⭐⭐ AN HPA MAX
⭐     THAT EXCEEDS YOUR DATABASE'S CAPACITY MEANS AUTOSCALING
⭐     ***CAUSES*** THE OUTAGE.
```

# Part 4 — ⭐ Jobs, CronJobs and StatefulSets

```
⭐⭐ ***JOB*** — run to completion.
⭐   ⭐ ⭐⭐ THE MIGRATION RUNNER (Day 366): SAME IMAGE, DIFFERENT
⭐     COMMAND, RUN BEFORE THE ROLLOUT.
⭐   ⭐ `backoffLimit`, ⭐ `activeDeadlineSeconds`, ⭐⭐ AND
⭐     `ttlSecondsAfterFinished` — WITHOUT THE LAST ONE,
⭐     COMPLETED JOBS ACCUMULATE FOREVER AND CLUTTER EVERY
⭐     `kubectl get`.

⭐⭐ ***CRONJOB*** — a Job on a schedule.
⭐   ⭐ ⭐⭐ `concurrencyPolicy: Forbid` OR YOU GET OVERLAPPING
⭐     RUNS WHEN ONE TAKES LONGER THAN THE INTERVAL — ⭐ which is
⭐     the most common CronJob incident.
⭐   ⭐ ⭐⭐ `startingDeadlineSeconds` — ⭐ if the controller was
⭐     down, missed runs pile up and then all fire at once. ⭐ Set
⭐     it, or a control-plane blip becomes a thundering herd.
⭐   ⭐ ⭐⭐ AND IT IS ***AT-LEAST-ONCE***: A RUN CAN BE MISSED OR
⭐     DUPLICATED, SO THE JOB MUST BE IDEMPOTENT (Day 335) —
⭐     ⭐ the same requirement as everything else in this
⭐     curriculum, arriving again.
⭐   ⭐ ⭐⭐ AND ALERT ON ***ABSENCE*** (Days 264, 338): "THE
⭐     NIGHTLY JOB DID NOT REPORT SUCCESS BY 06:00" IS THE ONLY
⭐     ALERT THAT CATCHES A CRONJOB THAT SILENTLY STOPPED.

⭐⭐ ***STATEFULSET*** — stable identity, stable storage,
⭐   ordered rollout.
⭐   ⭐ `db-0`, `db-1` keep their names and their volumes across
⭐     restarts, ⭐ and get a headless Service for direct
⭐     addressing.
⭐   ⇒ ⭐⭐ AND THE HONEST POSITION: ***A STATEFULSET GIVES YOU
⭐     IDENTITY AND STORAGE, NOT A DATABASE.*** ⭐ Backup,
⭐     restore, failover and version upgrades are still entirely
⭐     yours — ⭐⭐ WHICH IS WHY AN OPERATOR (CloudNativePG,
⭐     Strimzi) OR A MANAGED SERVICE IS USUALLY THE RIGHT
⭐     ANSWER, AND WHY "WE RUN POSTGRES IN A STATEFULSET" SHOULD
⭐     BE FOLLOWED BY "AND HERE IS OUR TESTED RESTORE".
```

# Part 5 — ⭐⭐ The failures that are not your code

```
⭐⭐ THIS IS THE SECTION THAT MAKES KUBERNETES FEEL DIFFERENT
⭐   FROM EVERYTHING BEFORE IT.

⭐⭐ ① ***NODE PRESSURE AND EVICTION.***
⭐   ⭐ A node runs low on memory or disk ⇒ ⭐⭐ THE KUBELET
⭐     EVICTS PODS, CHOOSING BY ***QoS CLASS***.
⭐   ⭐ `BestEffort` (no requests) goes first; ⭐ `Burstable`
⭐     (requests < limits) next; ⭐⭐ `Guaranteed` (requests ==
⭐     limits) LAST.
⭐   ⇒ ⭐⭐ SO SETTING REQUESTS EQUAL TO LIMITS IS A ***SURVIVAL
⭐     STRATEGY***, NOT JUST A SIZING ONE — ⭐ and a pod with no
⭐     requests at all is the first thing thrown overboard.

⭐⭐ ② ***THE NOISY NEIGHBOUR.***
⭐   ⭐ Another team's pod saturates the node's disk or network.
⭐   ⇒ ⭐⭐ YOUR LATENCY DEGRADES AND ***NOTHING IN YOUR
⭐     SERVICE'S METRICS EXPLAINS IT***. ⭐ You need node-level
⭐     metrics to even see it, and most teams don't have them
⭐     on a dashboard.

⭐⭐ ③ ***DNS.***
⭐   ⭐ ⭐⭐ CoreDNS IS A SHARED, CENTRAL DEPENDENCY OF EVERY POD.
⭐     ⭐ If it is slow, ***everything*** is slow, ⭐ and it
⭐     presents as random latency across unrelated services.
⭐   ⇒ ⭐ Combined with `ndots:5` (Day 377), ⭐⭐ DNS IS THE
⭐     SINGLE MOST COMMON SOURCE OF MYSTERIOUS KUBERNETES
⭐     LATENCY. ⭐ NodeLocal DNSCache is the standard fix.

⭐⭐ ④ ***IMAGE PULL STORMS.***
⭐   ⭐ Scaling twenty pods of a 1 GB image onto fresh nodes ⇒
⭐     ⭐⭐ TWENTY GIGABYTES PULLED, AND THE REGISTRY OR THE
⭐     NETWORK BECOMES THE BOTTLENECK EXACTLY WHEN YOU NEEDED
⭐     CAPACITY. ⭐ Day 363's small image is a scaling property.

⭐⭐ ⑤ ***CONTROL-PLANE AND WEBHOOK FAILURES.***
⭐   ⭐ ⭐⭐ A FAILING ***ADMISSION WEBHOOK*** WITH
⭐     `failurePolicy: Fail` BLOCKS ***ALL*** POD CREATION IN
⭐     THE CLUSTER. ⭐ Nothing can start, including the webhook's
⭐     own replacement. ⭐⭐ IT IS THE MOST SPECTACULAR
⭐     SELF-INFLICTED KUBERNETES OUTAGE THERE IS.

⭐⭐ ⑥ ***ROLLING UPDATES THAT NEVER FINISH.***
⭐   ⭐ New pods never become ready ⇒ ⭐⭐ THE ROLLOUT STALLS
⭐     HALFWAY AND ***BOTH VERSIONS SERVE INDEFINITELY.*** ⭐ With
⭐     `maxUnavailable: 0` the old ones are still up, so nothing
⭐     alerts — ⭐⭐ AND YOU DISCOVER IT HOURS LATER. ⭐ Set
⭐     `progressDeadlineSeconds` and alert on it.

⭐⭐ ⇒ THE THEME: ***YOUR SERVICE'S HEALTH NOW DEPENDS ON
⭐   COMPONENTS YOU DO NOT OWN AND MAY NOT MONITOR.*** ⭐ Which
⭐   is the real cost of the platform, and the honest answer to
⭐   "what's hard about Kubernetes?"
```

# Part 6 — ⭐ Resource requests: the numbers that decide everything

```
⭐⭐ ***REQUESTS*** DRIVE SCHEDULING AND QoS. ⭐⭐ ***LIMITS***
⭐   DRIVE ENFORCEMENT.
⭐   ⭐ The scheduler packs nodes by ***requests***, ⭐ and it
⭐     never looks at actual usage.
⭐   ⇒ ⭐⭐ SO REQUESTS THAT ARE TOO HIGH WASTE MONEY ON EMPTY
⭐     NODES, AND REQUESTS THAT ARE TOO LOW OVERCOMMIT THE NODE
⭐     AND CAUSE EVICTIONS UNDER LOAD.

⭐⭐ HOW TO SET THEM HONESTLY:
⭐   ⭐ ***CPU REQUEST*** = observed p50–p75 usage. ⭐⭐ NO CPU
⭐     LIMIT for latency-sensitive services (Days 361, 377).
⭐   ⭐ ***MEMORY REQUEST*** = observed p95.
⭐   ⭐ ⭐⭐ ***MEMORY LIMIT*** = 1.5–2× the observed peak, ⭐ and
⭐     ***set it***, because memory is not compressible: without
⭐     a limit the node's OOM killer chooses a victim, ⭐⭐ AND IT
⭐     MAY NOT CHOOSE YOU.
⭐   ⇒ ⭐ VPA in recommendation mode does this measurement for
⭐     you and is the least-known genuinely useful feature here.

⭐⭐ AND THE PYTHON ARITHMETIC (Day 366):
⭐   ⭐ Interpreter + imports: 60–120 MB (⭐ 300 MB+ with
⭐     numpy/pandas).
⭐   ⭐ ⭐⭐ × WORKER COUNT, WITH COPY-ON-WRITE SHARING THAT
⭐     ERODES WITHIN HOURS.
⭐   ⇒ ⭐⭐ 2 WORKERS × 200 MB + HEADROOM ⇒ REQUEST 256Mi,
⭐     LIMIT 512Mi. ⭐ And `WEB_CONCURRENCY` must be set to match
⭐     the limit, ⭐⭐ NOT DERIVED FROM `os.cpu_count()`.

⭐⭐ ⇒ AND THE CLUSTER-LEVEL CONSEQUENCE WORTH KNOWING:
⭐   ***OVERCOMMITTING CPU IS NORMAL AND FINE — CPU IS
⭐      COMPRESSIBLE. OVERCOMMITTING MEMORY IS HOW NODES DIE.***
```

## Common mistakes

| Mistake | Why it's wrong |
|---|---|
| ⭐⭐ No `preStop` sleep | Endpoint removal and SIGTERM race, and traffic still arrives after you stop. That's the deploy 502 |
| ⭐ Grace period shorter than preStop + p99 + cleanup | SIGKILL mid-request, and the whole drain mechanism never completes |
| ⭐⭐ No PodDisruptionBudget | A node-pool upgrade can drain three nodes and take all three replicas at once |
| ⭐⭐ `minAvailable` equal to `replicas` | Nothing can ever be evicted; drains hang and someone deletes the PDB under pressure |
| ⭐ A PDB on a single-replica service | Meaningless. The fix is a second replica |
| ⭐ Three replicas on one node | Survives nothing. Spread across nodes and zones |
| ⭐⭐ Autoscaling on CPU for an I/O-bound Python service | 30% CPU while saturated, and CPU rises *after* latency |
| ⭐⭐ CPU limits plus CPU-based HPA | Throttling holds reported CPU below target while latency explodes |
| ⭐ Symmetric scale-up and scale-down | Too small is an outage; too big is pennies. Scale up fast, down slowly |
| ⭐⭐ HPA max above your database's connection capacity | Autoscaling *causes* the outage |
| ⭐ Slow startup with autoscaling | New capacity arrives after the spike is over |
| ⭐ CronJob without `concurrencyPolicy: Forbid` | Overlapping runs when one exceeds the interval |
| ⭐ CronJob without `startingDeadlineSeconds` | A control-plane blip makes every missed run fire at once |
| ⭐⭐ No absence alert on scheduled jobs | A CronJob that silently stops is invisible to every threshold alert |
| ⭐ Job without `ttlSecondsAfterFinished` | Completed Jobs accumulate forever |
| ⭐⭐ Assuming a StatefulSet gives you a database | It gives identity and storage. Backup, restore, failover and upgrades are still yours |
| ⭐ No requests set at all | `BestEffort` QoS — the first pod evicted under node pressure |
| ⭐⭐ Admission webhook with `failurePolicy: Fail` and no exclusions | It can block all pod creation, including its own replacement |
| ⭐ No `progressDeadlineSeconds` | A stalled rollout serves both versions indefinitely and nothing alerts |

## Interview questions

**1. "Walk me through what happens when a pod is deleted."**
> ⭐ It's marked `Terminating`, and then ⭐⭐ **two things happen in parallel and are not ordered:
> endpoint removal starts propagating, and the kubelet runs `preStop` then sends SIGTERM.** ⭐ Endpoint
> removal has to reach every node's iptables rules and the ingress controller, which takes hundreds of
> milliseconds to seconds, while SIGTERM is instant — ⭐⭐ **so traffic is still being routed to you
> after you've been told to stop, and that's exactly where deploy-time 502s come from.** ⭐ The fix is a
> `preStop` sleep of five to ten seconds, which works even for apps that handle SIGTERM badly.

**2. "What's a PodDisruptionBudget for?"**
> ⭐ Voluntary disruptions only — node drains, cluster autoscaler removals, rebalances. ⭐⭐ **Without
> one, a node-pool upgrade can drain three nodes and take all three of your replicas down
> simultaneously, and the cluster is behaving correctly.** ⭐ `minAvailable: 2` with three replicas.
> ⭐⭐ And the trap: **setting `minAvailable` equal to `replicas` means nothing can ever be evicted, so
> drains hang, cluster upgrades stall, and eventually someone deletes the PDB under pressure — leaving
> you with no protection at all.**

**3. "What would you autoscale on?"**
> ⭐⭐ Not CPU. **An I/O-bound async Python service can be at thirty percent CPU and completely
> saturated, because it's waiting on the database** — and CPU rises *after* latency, so you scale after
> users are already suffering. ⭐⭐ Worse, **with a CPU limit set, throttling holds reported CPU below
> the target while latency explodes**, so the autoscaler sees a healthy number. ⭐ I'd scale on requests
> per second per pod or in-flight requests, which is Little's Law's L, and on queue *age* for workers.
> ⭐⭐ Plus the ceiling nobody checks: **scaling pods scales database connections, so an HPA max above
> your database's capacity means autoscaling causes the outage.**

**4. "What fails in Kubernetes that isn't your code?"**
> ⭐ Node pressure evicting by QoS class — ⭐⭐ **so requests equal to limits is a survival strategy, and
> a pod with no requests is the first thing thrown overboard.** ⭐ Noisy neighbours, where your latency
> degrades and nothing in your metrics explains it. ⭐⭐ **DNS, which is the single most common source of
> mysterious latency**, because CoreDNS is a shared dependency of every pod and `ndots:5` multiplies
> every external lookup. ⭐ Image pull storms, which is why a small image is a scaling property. ⭐⭐ And
> the spectacular one: **an admission webhook with `failurePolicy: Fail` blocking all pod creation,
> including its own replacement.**

**5. "How do you set resource requests?"**
> ⭐ Requests drive scheduling and QoS; limits drive enforcement — ⭐⭐ and **the scheduler packs by
> requests and never looks at actual usage**, so too high wastes money on empty nodes and too low
> overcommits and causes evictions. ⭐ CPU request at observed p50–p75 with no CPU limit; memory request
> at p95; memory limit at 1.5–2× peak, ⭐⭐ **and you must set it, because memory isn't compressible —
> without a limit the node's OOM killer chooses, and it may not choose you.** ⭐ VPA in recommendation
> mode does the measurement.

**6. "Would you run Postgres in a StatefulSet?"**
> ⭐⭐ A StatefulSet gives you stable identity and stable storage — **it does not give you a database.**
> ⭐ Backup, tested restore, failover and version upgrades are all still yours. ⭐ So either an operator
> like CloudNativePG that implements those, or a managed service. ⭐⭐ And if someone says "we run
> Postgres in a StatefulSet", the follow-up question is **"show me your last tested restore"** — because
> that's the part the StatefulSet didn't solve.

## Today's build

```
⭐ ① Add a `preStop` sleep and a grace period. ⭐⭐ THEN DEPLOY
```

## 🎙️ Articulation drill

**Two minutes.** Start from the premise: **pods are killed constantly and on purpose**, so the only
question is whether the application treats termination as normal. Explain the race precisely, because
it's the most useful thing here: **on deletion, endpoint removal and SIGTERM happen in parallel and are
not ordered — removal has to propagate to every node's iptables rules and the ingress, which takes
seconds, while SIGTERM is instant.** So traffic still arrives after you've been told to stop, which is
where deploy 502s come from, ⭐ and the fix is a five-to-ten-second `preStop` sleep, **which works even
for applications that handle SIGTERM badly.** Then disruptions: **involuntary ones you survive with
replicas and spreading; voluntary ones you control with a disruption budget** — without which a
node-pool upgrade drains three nodes and takes all three replicas, correctly. Name the trap: **min-
available equal to replicas means nothing can ever be evicted, drains hang, and someone deletes the PDB
under pressure.** Then autoscaling: **not CPU, because an I/O-bound Python service can be thirty
percent CPU and completely saturated, and with a CPU limit throttling holds the number below target
while latency explodes** — scale on requests per second, in-flight count, or queue age, scale up fast
and down slowly, ⭐ **and check that your HPA max times your pool size doesn't exceed the database's
connection limit, or autoscaling causes the outage.** Close on the honest position: **I can operate it,
and I'd ask whether we need it** — and on the observation that the platform rewards applications that
were already stateless, idempotent and handled SIGTERM.
