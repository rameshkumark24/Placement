# Day 339

**L-339** · Resilience patterns — the anatomy of a cascading failure

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Almost every large outage has the same shape: one dependency slows down, retries multiply the
> load, a shared thread pool fills, and services that never touched the failing thing start
> failing.**
>
> Day 181 configured Resilience4j in one service. Today is the systemic view — **why each pattern
> exists, which one actually matters, and the property that makes a system survive a dependency
> failure without reacting at all.**

---

# Part 1 — ⭐⭐ The anatomy of a cascade

```
⭐ 1. Recommendation service slows: 50 ms → 5 s.
⭐ 2. Callers have no timeout, so requests occupy threads for 5 s instead of 50 ms.
⭐ 3. ⭐ Little's Law (Day 322): L = λ × W. W went up 100×, so concurrency went up 100×.
⭐ 4. The thread pool fills. ⭐⭐ Requests that never call recommendations now queue.
⭐ 5. Clients time out and RETRY → ⭐⭐ arrival rate triples.
⭐ 6. Health checks time out → ⭐ instances are removed → the rest take more load (Day 325).
⭐ 7. ⭐⭐ TOTAL OUTAGE — caused by an optional feature being slow.
```

| ⭐ Step | ⭐ The pattern that stops it |
|---|---|
| 2 | ⭐⭐ **Timeouts** |
| 4 | ⭐ **Bulkheads** — recommendations get their own pool |
| 5 | ⭐ **Retry budgets and jitter** (Day 325) |
| 6 | ⭐ **Shallow liveness + a removal cap** (Day 325) |
| all | ⭐ **Circuit breaker** — stop calling it at all |
| — | ⭐⭐ **A fallback: the page renders without recommendations** |

> **⭐ The framing to carry: resilience is about containment, not prevention. Dependencies will fail.
> The design question is whether their failure is confined to the feature they serve.**

# Part 2 — ⭐ The patterns, ranked

## ⭐⭐ 1. Timeouts — the one that matters most

> **⭐ Every network call has a timeout. If you set nothing else today, set these.** A call without a
> timeout is a promise to wait forever for a machine that may never answer.

| ⭐ Rule | |
|---|---|
| ⭐ **Connect and read timeouts, both** | Day 154 — four timeouts, all of them |
| ⭐ **Derive from the SLO, do not guess** | ⭐ if your SLO is 500 ms, a 30 s downstream timeout is decorative |
| ⭐⭐ **Attempts × timeout + backoff must fit the budget** | ⭐⭐ **compute it; 3 retries × 5 s does not fit a 2 s SLO** |
| ⭐ Better still: deadlines | Day 336 — the propagated version |

## ⭐ 2. Retries — necessary and dangerous

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐ **Idempotent operations only** | a retried charge is a second charge (Day 335) |
| ⭐ **Never on a timeout** | ⭐ the original may still be running |
| ⭐⭐ **Exponential backoff WITH jitter** | ⭐⭐ **without jitter every client retries in the same millisecond** |
| ⭐ **A fleet-wide budget, not a per-call count** | ⭐ e.g. retries ≤ 10% of requests |
| ⭐ Never retry at multiple layers | ⭐ **3 × 3 × 3 = 27 calls from one request** |

> **⭐ Layered retries are the amplifier people miss.** Client retries 3×, gateway retries 3×, service
> retries 3× — **one user action becomes 27 requests at a struggling downstream.** Retry at exactly
> one layer, and say which.

## ⭐ 3. Circuit breakers

```
⭐ CLOSED ──failures exceed threshold──► OPEN ──after a wait──► HALF-OPEN
⭐    ▲                                   │                          │
⭐    └─── probe succeeds ────────────────┴──── probe fails ─────────┘
⭐         ⭐ OPEN = fail INSTANTLY, without calling
```

| ⭐ It buys | |
|---|---|
| ⭐ **Fail fast** — no thread held for a dependency that is down | |
| ⭐ **Relief for the downstream** — ⭐ **it cannot recover while you keep hammering it** | |
| A place to put the fallback | |

⚠️ **Three configuration traps:**

1. ⭐ **`ignoreExceptions` for business failures.** A 404 or a validation rejection is a *correct*
   response. **Counting it as a failure opens the breaker on a healthy dependency** (Day 181).
2. ⭐ **Half-open must admit only a few probes.** Letting all traffic through on the first success is
   a stampede at a service that has just come back — **and it closes the breaker again immediately.**
3. ⭐ **The breaker is per dependency per instance.** With 50 instances, the downstream still sees 50
   probe requests during half-open. **Size the probe count accordingly.**

## ⭐ 4. Bulkheads

> **⭐ Separate resource pools per dependency, so one slow thing cannot consume every thread.** The
> name is from ship compartments — **a hull breach floods one compartment, not the vessel.**

```
⭐ payments   → its own pool of 20   ⭐ critical
⭐ recommendations → its own pool of 5 ⭐ optional — cannot starve payments
⭐ search     → its own pool of 10
```

**⭐ The cheap version is a semaphore**, not a thread pool: cap concurrent in-flight calls per
dependency. **No extra threads, most of the isolation.**

## ⭐ 5. Fallbacks — and what makes one good

| ⭐ Good fallback | ⭐ Bad fallback |
|---|---|
| ⭐ **Stale cached data, labelled as such** | ⭐ an empty list that looks like "no results" |
| ⭐ A reduced feature ("recommendations unavailable") | ⭐ **`null`, which crashes three layers up** |
| ⭐ A queued write, applied later | ⭐ a default that is silently wrong (`price = 0`) |
| ⭐ **A clear, honest error** | ⭐ retrying inside the fallback |

> **⭐ The test: would this fallback be indistinguishable from a correct answer?** If yes, it is
> dangerous — **an empty search result and a broken search index look identical to the user, and to
> your metrics.** A fallback must be observable.

# Part 3 — ⭐⭐ Graceful degradation as a design decision

**⭐ Do this exercise for real — it is a table an interviewer will find impressive because almost
nobody has one.**

| Feature | Dependency | ⭐ If it fails |
|---|---|---|
| ⭐ **Checkout** | payments | ⭐⭐ **fail — never fake a payment** |
| ⭐ Browse catalogue | database | ⭐ **serve from cache, stale, with a banner** |
| ⭐ **Recommendations** | ML service | ⭐ **hide the section entirely** |
| Reviews | review service | ⭐ show "unavailable"; the page still works |
| ⭐ Search | search cluster | ⭐ **fall back to a database `LIKE` query, degraded** |
| Analytics | events pipeline | ⭐ **drop silently — never affect the user** |

> **⭐ The point: degradation is decided per feature, in advance, and written down.** A system that
> has not decided **degrades by whichever component happens to fail first**, which is the same as not
> deciding at all.

⚠️ **And the discipline: a critical path should have as few dependencies as possible.** The strongest
resilience move is not a pattern — **it is noticing that checkout calls seven services and reducing
it to three.**

## ⭐⭐ Static stability — the idea worth stealing

> **⭐ A system is statically stable if it keeps working during a dependency failure using state it
> already has, rather than by reacting to the failure.**

| ⭐ Reactive | ⭐ Statically stable |
|---|---|
| Detect the failure, then fail over | ⭐ **already running in both places; nothing to detect** |
| Fetch config on startup | ⭐ **config already on disk; a config-service outage changes nothing** |
| Scale up when a zone dies | ⭐ **already provisioned for N−1 zones** |
| Look up routing on each request | ⭐ cached routing that keeps working when the lookup is down |

**⭐ Why it matters: reacting requires the control plane to work at exactly the moment things are
broken**, which is when it is least likely to. **A design that needs nothing to happen during a
failure has removed a whole class of failure** — and naming static stability in an interview is a
strong signal, because it shifts the conversation from patterns to properties.

# Part 4 — ⭐ Proving it

| ⭐ Requirement | |
|---|---|
| ⭐⭐ **Chaos-test every degradation row** | ⭐⭐ **an untested fallback is a hypothesis** (Day 286) |
| ⭐ Measure time-to-detect | how long before you knew? |
| ⭐ **Verify the blast radius** | ⭐ did anything unrelated break? That is the actual test |
| ⭐ Test the breaker's recovery | half-open storms only appear under load |
| ⭐ **Load-test with a dependency slow, not down** | ⭐⭐ **slow is far worse than down, and is rarely tested** |

> **⭐ "Slow is worse than down" deserves a sentence of its own.** A dependency returning connection
> refused fails in a millisecond and your fallback runs. **A dependency answering in 30 seconds holds
> your threads, fills your pools and takes you with it** — which is precisely the Part 1 cascade.
> **Test the slow case; almost nobody does.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Any network call with no timeout | ⭐⭐ **the root of nearly every cascade** |
| ⭐ Timeouts not derived from the SLO | 30 s downstream behind a 500 ms promise |
| ⭐⭐ Retries at three layers | ⭐⭐ **one request becomes 27** |
| ⭐ Retries without jitter | synchronised retry storms |
| Retrying non-idempotent calls | duplicate side effects |
| ⭐ Counting business failures as breaker failures | ⭐ the breaker opens on a healthy dependency |
| ⭐ Half-open admitting all traffic | ⭐ stampede; the breaker reopens instantly |
| ⭐ One shared pool for all dependencies | ⭐ **one slow call starves everything** |
| ⭐ **A fallback indistinguishable from success** | ⭐⭐ **empty results look like "nothing found"** |
| `null` fallbacks | a crash three layers up |
| ⭐ No written degradation matrix | ⭐ the system degrades by accident |
| ⭐ Seven dependencies on the critical path | ⭐ **availability multiplies down** |
| ⭐ Never testing the *slow* case | the realistic and worse failure, untested |

## Interview questions

**Q: Walk me through a cascading failure.**
A dependency slows from fifty milliseconds to five seconds. Callers without timeouts hold threads a
hundred times longer, so by Little's Law concurrency rises a hundredfold and the shared pool fills —
now requests that never touch that dependency are queuing. Clients time out and retry, tripling
arrival rate. Health checks time out, instances get removed, and the survivors take more load. An
optional feature has produced a total outage.

**Q: Which resilience pattern matters most?**
Timeouts, by a distance. Every other pattern assumes the call eventually returns. Without a timeout a
thread is committed indefinitely to a machine that may never answer, and that is the first step in
every cascade. And they should be derived from the SLO, with attempts times timeout plus backoff
computed to fit inside it rather than guessed.

**Q: What is wrong with retries?**
They multiply load on a system that is already failing, which is exactly the wrong moment. So:
idempotent operations only, never on a timeout since the original may still be running, exponential
backoff with jitter or every client retries in the same millisecond, and a fleet-wide budget rather
than a per-call count. The one people miss is layering — client, gateway and service each retrying
three times turns one action into twenty-seven requests.

**Q: What makes a good fallback?**
That it is distinguishable from success. Stale cached data with a banner, a hidden section, an
explicit "unavailable" — all fine. An empty list is dangerous, because a broken search index and
"nothing matched" look identical to both the user and your metrics. And never null, and never a
silently wrong default like a zero price.

**Q: What is static stability?**
Continuing to work during a failure using state you already have, rather than reacting. Running in
both zones already rather than failing over, config already on disk rather than fetched, capacity
already provisioned for N minus one. It matters because reacting requires the control plane to
function at exactly the moment things are broken, which is when it is least likely to — so a design
that requires nothing to happen during a failure removes a whole class of failure.

**Q: How do you know any of it works?**
Chaos testing every row of the degradation matrix, and specifically testing the dependency being
*slow* rather than down. Down is easy — it fails in a millisecond and the fallback runs. Slow is what
produces the cascade, and it is the case almost nobody tests. I measure time to detect and, more
importantly, blast radius: did anything unrelated break?

## Mini task

1. **Audit every outbound call for a timeout.** Any without one is your next incident.
2. ⭐ **Compute** attempts × timeout + backoff for each dependency and compare with your SLO. Fix
   what does not fit.
3. ⭐⭐ **Reproduce the cascade**: make one optional dependency take 5 s under load with no timeout,
   and watch unrelated endpoints fail. **Then add a timeout and repeat.**
4. Add a **bulkhead** (a semaphore per dependency) and re-run. **Confirm the blast radius is now one
   feature.**
5. ⭐ Configure a breaker, then **send business 404s** and watch it open on a healthy dependency.
   Add `ignoreExceptions` and confirm.
6. ⭐ Under load, let a dependency recover and **watch the half-open stampede.** Limit probes.
7. ⭐ Add retries at three layers deliberately and **count actual downstream requests per user
   action.**
8. ⭐⭐ **Write the degradation matrix** for your flagship — every feature, its dependencies, and the
   behaviour on failure. **Then chaos-test every row.**
9. ⭐ Test one dependency **down** and then **slow.** Record which is worse and by how much.
10. ⭐ Find one critical path and **count its dependencies.** Multiply their availabilities. **Remove
    one.**

## 🎙️ Articulation drill

**Three minutes:** *"One of your dependencies starts taking 5 seconds instead of 50 milliseconds.
What happens?"*

**⭐ The complete answer tells the cascade with Little's Law in it** — concurrency rises a
hundredfold, the shared pool fills, unrelated requests queue, retries triple the load, health checks
remove instances — **then names the containment in order: timeout, bulkhead, breaker, fallback, and a
degradation decision made in advance.**

easy — it fails in a millisecond and the fallback runs."**
