# Day 182

**L-182** · Structured logging, MDC, and tracing — making an incident answerable

**Time:** 3 hrs · **Mode:** NEW

> filter and its `finally`. Day 143 exposed metrics. Today assembles the full picture in Spring —

# Part 1 — JSON logs, and the configuration

```xml
<dependency>
  <groupId>net.logstash.logback</groupId>
  <artifactId>logstash-logback-encoder</artifactId>
</dependency>
```

```xml
<!-- logback-spring.xml  — ⭐ "-spring" so Spring's profile support works -->
<configuration>
  <springProfile name="local">
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
      <encoder><pattern>%d{HH:mm:ss} %-5level [%X{correlationId}] %logger{20} - %msg%n</pattern></encoder>
    </appender>
    <root level="INFO"><appender-ref ref="CONSOLE"/></root>
  </springProfile>

  <springProfile name="prod">
    <appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
      <queueSize>2048</queueSize>
      <discardingThreshold>0</discardingThreshold>   <!-- ⭐ don't silently drop WARN/ERROR -->
      <neverBlock>true</neverBlock>                  <!-- ⭐⭐ see below -->
      <appender-ref ref="JSON"/>
    </appender>
    <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
      <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <includeMdcKeyName>correlationId</includeMdcKeyName>
        <includeMdcKeyName>userId</includeMdcKeyName>
        <includeMdcKeyName>tenantId</includeMdcKeyName>
        <customFields>{"service":"orders","env":"${ENVIRONMENT}"}</customFields>
      </encoder>
    </appender>
    <root level="INFO"><appender-ref ref="ASYNC"/></root>
  </springProfile>
</configuration>
```

**⭐ Human-readable locally, JSON in production.** Reading JSON in a terminal during development is
miserable; grepping unstructured text in a log aggregator at 3 a.m. is worse. `<springProfile>` gives
you both.

**⭐ `neverBlock=true` is the setting that prevents an outage.** With an async appender and a full
queue, the default behaviour is to **block the application thread** until there is room. So a slow or
unreachable log destination stops your service — logging, of all things, becomes the outage. Dropping
log lines under extreme load is the correct trade.

**⭐ Log to stdout, not to a file.** Day 129A's container rule: the platform collects stdout. A file
inside a container needs rotation, disk management, and a sidecar, and it disappears when the pod
does.

## ⭐ Structured events, not sentences

```java
// ❌ unqueryable
log.info("Order " + orderId + " placed by " + userId + " for " + total);

// ✅ structured — every field is a searchable dimension
log.atInfo()
   .setMessage("order_placed")                                  // ⭐ a stable EVENT NAME
   .addKeyValue("orderId", orderId)
   .addKeyValue("customerId", customerId)
   .addKeyValue("total", total)
   .addKeyValue("itemCount", items.size())
   .log();
```

**⭐ The message should be a stable event name, never an interpolated sentence.** `order_placed` can
be counted, grouped and alerted on; `"Order 8842 placed by 17"` requires a regular expression that
breaks the day someone rewords the message.

The SLF4J 2 fluent API is the modern form; `StructuredArguments.kv()` works on the older API.

# Part 2 — MDC, and the four fields worth having

```java
// Day 151's filter, extended
MDC.put("correlationId", correlationId);
MDC.put("tenantId", tenantContext.get());          // Day 176
MDC.put("userId", currentUserId());                // ⭐ after authentication
MDC.put("clientVersion", req.getHeader("X-Client-Version"));
try { chain.doFilter(req, res); } finally { MDC.clear(); }     // ⭐⭐ non-negotiable
```

**⭐ Every log line in the request now carries all four automatically**, without a single call site
mentioning them. That is the entire value of the MDC: context without ceremony.

| Field | The question it answers |
|---|---|
| ⭐ `correlationId` | **show me everything that happened in this one request** |
| `userId` | is this one user or everyone? |
| `tenantId` | is this one tenant? — the first question in a SaaS incident |
| `clientVersion` | ⭐ did the mobile release yesterday cause this? |

**⭐ `MDC.clear()` in a `finally` is the rule that appears in Day 066A, Day 151, Day 176 and Day 177.**
Same `ThreadLocal` fact each time; here the consequence is logs attributed to the wrong user, which
is worse than no logs during an investigation.

**And it does not cross threads** — Day 177's `TaskDecorator` is required for `@Async`, and reactive
code needs the Micrometer context propagation library.

# Part 3 — Tracing, which is where correlation IDs end up

```xml
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-tracing-bridge-otel</artifactId></dependency>
<dependency><groupId>io.opentelemetry</groupId><artifactId>opentelemetry-exporter-otlp</artifactId></dependency>
```

```yaml
management.tracing.sampling.probability: 0.1      # ⭐ 10% — see below
logging.pattern.level: "%5p [${spring.application.name},%X{traceId:-},%X{spanId:-}]"
```

**Micrometer Tracing does automatically what Day 127's correlation ID did by hand**, and more:

- **W3C `traceparent` propagated** on every outgoing `RestClient`/`WebClient` call (Day 154);
- **`traceId` and `spanId` in the MDC**, so logs and traces join on one key;
- **spans for HTTP, JDBC, and messaging**, giving you a waterfall of where the time actually went.

**⭐ The difference from correlation IDs is what you can *see*.** A correlation ID lets you gather the
log lines. A trace shows you that the endpoint took 800 ms, of which 640 ms was one database query —
without anyone having instrumented that query.

## ⭐ Sampling, and the setting that ruins it

**100% sampling is expensive** — storage, network, and per-span overhead. 10% is a common default.

**⭐ But naive sampling drops the traces you need.** The interesting requests are the slow ones and the
failing ones, and at 10% you have a 90% chance the one your customer complained about is gone.

**Tail-based sampling** — implemented in the OpenTelemetry Collector, not in your application —
decides *after* the trace completes: keep everything that errored or exceeded a latency threshold,
sample the rest. **If you take one thing from this section, it is that sampling should be
error-and-latency-biased, not uniform.**

## Correlating the three signals

```
Metric  → "p99 latency on /api/orders jumped at 14:32"        (Day 143)
   ↓ exemplar or time window
Trace   → "one span dominates: SELECT ... FROM orders"
   ↓ traceId
Logs    → the exact requests, with userId and tenantId
```

**⭐ That path — metric to trace to log — is what "observable" means in practice.** Each signal answers
a different question: metrics say *something is wrong*, traces say *where*, logs say *what exactly*.
A system with only one of the three leaves you guessing at the other two questions.

# Part 4 — What to log, what never to log, and cost

## ⭐ The four things every request should produce

1. **One access log line per request** — method, path template, status, duration, correlation id.
   ⭐ **Path template, not the raw path** — `/orders/{id}`, or the field has unbounded cardinality
   (Day 143's rule, applied to logs).
2. **Business events at INFO** — `order_placed`, `payment_captured`, `refund_issued`. These are what
   you reconstruct a customer's history from.
3. **Errors with full context** at ERROR, once — see below.
4. **Nothing else at INFO.** Debug detail is at DEBUG, switchable per package at runtime via
   `/actuator/loggers` (Day 143).

## ⭐ Log an exception once

```java
// ❌ the same failure appears four times at four levels
catch (Exception e) { log.error("failed in repository", e); throw e; }
catch (Exception e) { log.error("failed in service", e);    throw e; }
```

**Log where you handle, not where you catch-and-rethrow.** Duplicated stack traces triple your log
bill and make an incident harder to read, because the same event looks like four events. Day 149's
catch-all handler is usually the right and only place.

## ⭐ Never log

| Never | Note |
|---|---|
| Passwords, tokens, API keys | including in a body-logging filter (Day 151) |
| ⭐ Full request/response bodies | PII, and enormous. Log named fields |
| Card numbers, national IDs, health data | ⭐ regulatory, not stylistic |
| Full email addresses | hash or mask if you need to correlate |
| ⭐ Anything from an unvalidated header | log injection (Day 151) |

**Add a scrubbing layer, because someone will do it anyway:**

```java
public class SensitiveDataConverter extends MessageConverter {
    private static final Pattern TOKEN = Pattern.compile("(?i)(bearer\\s+)[A-Za-z0-9._-]+");
    @Override public String convert(ILoggingEvent event) {
        return TOKEN.matcher(super.convert(event)).replaceAll("$1***");     // ⭐ defence in depth
    }
}
```

## Cost, which is a real engineering constraint

**A busy service can generate hundreds of gigabytes a day, and log storage is billed by volume.**
Three controls:

| Control | Effect |
|---|---|
| ⭐ **INFO in production, never DEBUG** | the largest single lever |
| Sampling high-volume events | log 1% of health-check accesses |
| ⭐ **Short retention for INFO, long for ERROR and audit** | 7 days vs 1 year |

**⭐ And the anti-pattern: DEBUG logging left on in production "just in case".** It costs a fortune,
it slows the application (string construction on every call), and it buries the lines that matter.
`/actuator/loggers` lets you raise a level for ten minutes during an incident — which is strictly
better.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Unstructured interpolated messages | unqueryable; regexes break on rewording |
| Message text as the event identity | cannot count or alert on it |
| ⭐ No `MDC.clear()` in a `finally` | logs attributed to the wrong user |
| Async appender without `neverBlock` | a slow log sink blocks the application |
| `discardingThreshold` default | silently drops WARN and ERROR under load |
| Logging to a file in a container | rotation, disk, and it dies with the pod |
| Raw paths in access logs | unbounded cardinality |
| Logging an exception at every layer | triple cost, confusing incidents |
| ⭐ Secrets or full bodies in logs | breach and regulatory exposure |
| Unvalidated header values logged | log injection |
| DEBUG in production | cost, latency, noise |
| Uniform 10% sampling | the traces you need are the ones dropped |
| Metrics without traces, or traces without logs | two of the three questions unanswerable |

## Interview questions

**Q: How do you make a service debuggable in production?**
Three correlated signals. Structured JSON logs to stdout with a correlation or trace id in the MDC,
so one request's lines can be gathered; metrics for RED and USE so you know something is wrong; and
distributed traces so you know *where* the time went. The path is metric to trace to log, and each
answers a question the others cannot.

**Q: Why structured logging rather than formatted messages?**
Because fields become queryable dimensions. `order_placed` with a `total` field can be counted,
grouped and alerted on; an interpolated sentence needs a regular expression that breaks the moment
someone rewords it.

**Q: What is the trap with an async appender?**
By default a full queue blocks the application thread, so a slow log destination becomes an outage.
`neverBlock=true` drops lines instead, and `discardingThreshold=0` stops it silently discarding
warnings and errors first.

**Q: How do you control logging cost?**
INFO in production with per-package DEBUG raised temporarily through Actuator during an incident,
sampling for high-volume routine events, and tiered retention — a week for INFO, a year for errors
and audit events.

**Q: What is wrong with 10% sampling?**
It is uniform, so the slow and failing requests you actually need are dropped 90% of the time.
Tail-based sampling in the collector keeps every error and every slow trace and samples the rest.

## 🎙️ Articulation drill

Two minutes: **"How do you make a service observable?"**

Three signals and what each answers — metrics say something is wrong, traces say where, logs say what
exactly — and the path between them is what makes an incident tractable. Structured JSON to stdout,
correlation and trace ids in the MDC, cleared in a `finally` because the thread is pooled. Then two
details that show you have run this in production: async appenders must be configured not to block,
or your log sink becomes your outage; and sampling must be biased toward errors and slow requests,
because uniform sampling drops exactly the traces you need.
