# Part 1 — ⭐ `pg_stat_statements`, and the ranking that matters

```
shared_preload_libraries = 'pg_stat_statements'    -- ⭐ requires a restart
pg_stat_statements.max = 10000
pg_stat_statements.track = top
```
```sql
create extension pg_stat_statements;
```

**⭐ It normalises queries** — `where id = 42` and `where id = 99` become one entry with `$1` — and
accumulates statistics per normalised query.

```sql
-- ⭐⭐ THE query. Total time, not average.
select round(total_exec_time::numeric/1000, 1) as total_sec,
       calls,
       round(mean_exec_time::numeric, 2)       as mean_ms,
       round(100.0*total_exec_time/sum(total_exec_time) over (), 1) as pct_of_total,
       rows,
       round(100.0*shared_blks_hit/nullif(shared_blks_hit+shared_blks_read,0),1) as hit_pct,
       left(query, 90) as query
from pg_stat_statements
order by total_exec_time desc                    -- ⭐⭐ THIS ordering
limit 20;
```

**⭐ Order by `total_exec_time`, not `mean_exec_time`. This is the whole insight of the day.**

| Query | Mean | Calls | ⭐ Total |
|---|---|---|---|
| Monthly report | ⭐ 8,000 ms | 30 | 240 s |
| ⭐ **Order lookup** | ⭐ **2 ms** | ⭐ **40,000,000** | ⭐⭐ **80,000 s** |

**⭐ The 2 ms query is 300× more expensive than the 8-second one**, and nobody has ever complained
about it. **Shaving it to 1 ms saves more than eliminating the report entirely.**

**⭐ That is the counter-intuitive result that makes this tool valuable**: the slowest query is
usually not the most important one, and human complaints select for latency rather than cost.

## The other useful orderings

```sql
order by calls desc                          -- ⭐ is anything being called far more than expected?
order by shared_blks_read desc               -- ⭐ what is hitting disk?
order by (total_exec_time/nullif(calls,0)) desc  -- worst average — for user experience
order by stddev_exec_time desc               -- ⭐ inconsistent — a plan flipping, or lock waits
order by rows/nullif(calls,0) desc           -- ⭐ returning huge result sets — a missing LIMIT
```

**⭐ Sorting by `calls` catches the N+1** (Day 160): a simple query with forty million calls when
there are two hundred thousand page views is your application looping. **`pg_stat_statements` is
often how an N+1 is *discovered*, long before anyone reads the Java.**

**⭐ High `stddev_exec_time` is the underused one.** A query with a mean of 5 ms and a standard
deviation of 800 ms is sometimes taking a second — a plan flip (Day 192), a lock wait (Day 196), or
a cold cache. Averages hide it entirely.

```sql
select pg_stat_statements_reset();     -- ⭐ reset, run a known workload, measure that window
```

# Part 2 — The other views, and what each answers

```sql
-- ⭐ Tables: is anything being sequentially scanned constantly?
select relname, seq_scan, seq_tup_read, idx_scan,
       seq_tup_read / nullif(seq_scan,0) as avg_rows_per_seq_scan
from pg_stat_user_tables
where seq_scan > 0 order by seq_tup_read desc limit 20;

-- ⭐ Indexes: which are never used? (Day 189)
select relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
from pg_stat_user_indexes where idx_scan < 50 order by pg_relation_size(indexrelid) desc;

-- ⭐ Cache hit ratio per table (Day 186)
select relname,
       round(100.0*heap_blks_hit/nullif(heap_blks_hit+heap_blks_read,0),2) as hit_pct
from pg_statio_user_tables order by heap_blks_read desc limit 20;

-- ⭐ Dead tuples and vacuum health (Day 194)
select relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
from pg_stat_user_tables order by n_dead_tup desc limit 20;

-- ⭐ What is waiting right now (Day 196)
select wait_event_type, wait_event, count(*), max(now()-query_start) as longest
from pg_stat_activity where state='active' group by 1,2 order by 3 desc;
```

**⭐ `seq_tup_read / seq_scan` is a sharp diagnostic**: a table with 400,000 sequential scans each
reading 5 rows is a **missing index being scanned constantly**, and it will not show up as a slow
query because each scan is fast.

**⭐ And `wait_event` in `pg_stat_activity` tells you what the database is *waiting on*, not what it
is running**, which is a different and often more useful question:

| `wait_event_type` | Means |
|---|---|
| ⭐ `Lock` | ⭐ blocked by another transaction (Day 196) |
| ⭐ `IO` | reading from disk — cache too small, or a bad plan |
| `LWLock` | internal contention — often buffer or WAL |
| `Client` | ⭐ **waiting on the application** — `idle in transaction` (Day 194) |

# Part 3 — ⭐ The settings that actually matter

**⭐ Configuration is the last resort, after queries, indexes and statistics.** But a handful of
defaults are genuinely wrong on modern hardware.

| Setting | Default | ⭐ Set to | Why |
|---|---|---|---|
| `shared_buffers` | 128MB | ⭐ **25% of RAM** | Day 186 |
| ⭐ `effective_cache_size` | 4GB | ⭐ **~75% of RAM** | ⭐ tells the planner index scans are cheap |
| ⭐ `random_page_cost` | ⭐ **4.0** | ⭐ **1.1 on SSD** | Day 192 — the 1990s default |
| `work_mem` | 4MB | ⭐ per workload, per session | Day 191 — **not globally** |
| `maintenance_work_mem` | 64MB | ⭐ 1–2GB | faster vacuum and index builds |
| ⭐ `max_wal_size` | 1GB | ⭐ 4–16GB on write-heavy | Day 186's checkpoint spikes |
| `checkpoint_completion_target` | 0.9 | 0.9 | already correct |
| `default_statistics_target` | 100 | ⭐ 500 on skewed columns | Day 189's estimates |
| ⭐ `idle_in_transaction_session_timeout` | ⭐ **off** | ⭐ **5min** | ⭐ Day 194's failure 1 |
| `statement_timeout` | off | ⭐ per role | bound runaway queries |
| ⭐ `lock_timeout` | off | ⭐ **in every migration** | Day 196's outage |
| `log_min_duration_statement` | off | ⭐ 1s | see slow queries |
| ⭐ `log_lock_waits` | off | ⭐ **on** | Day 196 |
| `autovacuum_vacuum_cost_limit` | 200 | ⭐ 1000+ | Day 194 — throttled for old disks |

**⭐ If you change only three things: `random_page_cost` on SSD, `effective_cache_size`, and
`idle_in_transaction_session_timeout`.** The first two stop the planner systematically avoiding
indexes; the third prevents a class of outage.

**⭐ And the meta-rule: change one setting, measure, keep or revert.** A configuration file full of
values copied from blog posts, none of which were measured on your workload, is worse than the
defaults — because now nobody knows which ones matter.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Ordering by mean time | you optimise the report and ignore the 40M-call query |
| Ignoring `calls` | the N+1 is invisible |
| Ignoring `stddev` | intermittent slowness averages away |
| ⭐ Tuning settings before queries | the smallest lever, pulled first |
| Copying settings from blogs | a config nobody can justify |
| Changing several at once | you learn nothing (Day 099) |
| ⭐ `work_mem` globally | per operation per connection |
| Not resetting statistics before a test | you measure history, not the change |
| ⭐ Not setting `idle_in_transaction_session_timeout` | Day 194's failure 1 stays open |
| Not reading `wait_event` | you see what runs, not what is stuck |

## Interview questions

**Q: How do you find what to optimise in an unfamiliar database?**
`pg_stat_statements` ordered by **total** execution time, not mean — because a 2 ms query called
forty million times costs far more than an eight-second monthly report, and nobody has ever
complained about it. Then `calls` to find N+1 patterns, `stddev` for intermittent problems,
`pg_stat_user_tables` for constant sequential scans, and `pg_stat_activity`'s `wait_event` for what
is stuck right now.

**Q: Which PostgreSQL defaults are wrong?**
`random_page_cost` at 4.0 assumes spinning disks and makes the planner avoid indexes on SSDs.
`effective_cache_size` at 4GB understates available cache, with the same effect.
`idle_in_transaction_session_timeout` is off, so one abandoned session blocks vacuuming database-wide.
And `shared_buffers` at 128MB is a starting default rather than a production one.

**Q: Where does configuration sit in your optimisation order?**
Last. Not issuing the query, rewriting it, and fixing statistics all come first, then indexes, then
settings. A handful of defaults are genuinely wrong on modern hardware, but a config file full of
unmeasured values copied from articles is worse than the defaults, because nobody knows which ones
matter.

**Q: What does `stddev_exec_time` tell you?**
That a query is inconsistent — a mean of 5 ms with a standard deviation of 800 ms means it sometimes
takes a second. That points at a plan flip, a lock wait, or a cold cache, and averages hide it
completely.

## Mini task

**The block gate is the task.** Additionally:

1. Enable `pg_stat_statements`. Run a mixed workload. **Order by mean, then by total. Compare the two
   top-tens** — they will barely overlap. That contrast is the day.
2. Deliberately create an N+1 from an application. **Find it in `pg_stat_statements` by `calls`
   alone**, without looking at the code.
3. Find a query with high `stddev`. Work out why.
4. `pg_stat_statements_reset()`, run one known workload, and attribute cost precisely.
5. Find the table with the highest `seq_tup_read / seq_scan`. Index it. Re-measure.
6. Set `random_page_cost` to 4 then 1.1. **Find one query whose plan changes**, and measure both.
7. Change one setting at a time from the table, measuring after each. **Keep only what moved a
   number**, and write down why.
8. Leave a session `idle in transaction`. Find it via `wait_event_type = 'Client'` and via
   `pg_stat_activity`. Then set the timeout.
