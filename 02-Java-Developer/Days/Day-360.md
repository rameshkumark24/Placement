# Day 360

**L-360** · Why containers — and what they are not

**Time:** 3 hrs · **Mode:** NEW

> **⭐ A container is not a lightweight virtual machine. It is an ordinary Linux process that has
> been lied to about what it can see.**
>
> Getting that right on day one prevents a dozen later confusions — why containers start in
> milliseconds, why they cannot run a different kernel, why "it's isolated" is only partly true,
> and why the real benefit is not isolation at all.

---

# Part 1 — ⭐ The problem containers actually solve

| ⭐ Symptom | ⭐ Cause |
|---|---|
| ⭐ **"Works on my machine"** | ⭐ different JDK patch level, OS libraries, locale, timezone data, CA certificates |
| ⭐ **Environment drift** | ⭐⭐ staging was configured by hand in 2022 and nobody remembers how |
| ⭐ A dependency upgrade breaks another app | one host, shared system libraries |
| Slow onboarding | "install these fourteen things in this order" |
| ⭐ **Deploys that differ from tests** | ⭐ you tested one thing and shipped another |

**⭐ The answers before containers, and why each fell short:**

| Approach | ⭐ Gave you | ⭐ Cost |
|---|---|---|
| ⭐ **Virtual machines** | ⭐ real isolation | ⭐⭐ **gigabytes, minutes to boot, a full OS to patch per app** |
| ⭐ **Config management** (Ansible, Chef) | repeatable setup | ⭐⭐ **convergent, not immutable — it fixes drift rather than preventing it** |
| ⭐ **Fat jars** (Day 144) | your code and its Java deps | ⭐ **not the JVM, not the OS libs, not the certs** |

> **⭐ The fat jar is the interesting near-miss for a Java engineer.** It packages everything *above*
> the JVM. **A container packages the JVM itself, plus glibc, plus the CA trust store, plus the
> timezone database** — and those are exactly the things that differ between your laptop and
> production.

# Part 2 — ⭐⭐ What a container actually is

```
⭐ VIRTUAL MACHINE                    ⭐ CONTAINER
⭐  ┌──────────────┐                   ┌──────────────┐
⭐  │ app          │                   │ app          │  ⭐ just a process
⭐  │ libs         │                   │ libs         │
⭐  │ ⭐ GUEST KERNEL│                   └──────┬───────┘
⭐  ├──────────────┤                          │
⭐  │ hypervisor   │                   ⭐ SHARED HOST KERNEL
⭐  ├──────────────┤                   ├──────────────┤
⭐  │ host kernel  │                   │ host kernel  │
⭐  └──────────────┘                   └──────────────┘
```

| | ⭐ VM | ⭐ Container |
|---|---|---|
| ⭐ **What runs** | ⭐ a whole operating system | ⭐⭐ **one process tree on the host kernel** |
| ⭐ **Start time** | ⭐ 30 s – minutes (a boot) | ⭐⭐ **milliseconds — it is `fork`+`exec`** |
| Size | GBs | ⭐ tens to hundreds of MB |
| Density per host | tens | ⭐ hundreds to thousands |
| ⭐ **Isolation strength** | ⭐⭐ **strong — separate kernel** | ⭐⭐ **weaker — a shared kernel is a shared attack surface** |
| ⭐ Can run another OS kernel | ⭐ yes | ⭐⭐ **no — Linux containers need a Linux kernel** |

⚠️ **"Docker on Mac and Windows runs a Linux VM."** Containers are a Linux kernel feature; on other
hosts there is a hidden virtual machine doing the work. **That is why file I/O across a bind mount is
slow on a Mac** — it crosses a VM boundary.

## ⭐⭐ The real benefit is the immutable artefact

> **⭐ Isolation is what containers *use*. The reason to adopt them is that the image is a single,
> content-addressed, immutable artefact — the same bytes in CI, staging and production.**

| ⭐ Consequence | |
|---|---|
| ⭐⭐ **The same SHA runs everywhere** | ⭐ Day 287's checklist item 1, made structural |
| ⭐ **A rollback is a pointer change** | ⭐ the previous image still exists |
| ⭐ **Config comes from outside** | 12-factor (Day 142, Day 373) |
| ⭐ The build is the boundary | ⭐ **nothing is "configured" after the image exists** |
| ⭐ **Drift is impossible** | ⭐⭐ you cannot patch a running container into a different image |

**⭐ Say this in an interview: "I use containers for the immutable artefact, not the isolation."** It
is the accurate reason, and it distinguishes you from someone repeating a marketing line.

# Part 3 — ⭐ What containers do NOT give you

| ⭐ Myth | ⭐ Reality |
|---|---|
| ⭐⭐ "Containers are secure by default" | ⭐⭐ **a shared kernel means a kernel exploit escapes the container.** Root inside is often root outside without extra hardening |
| ⭐ "Containers make apps scalable" | ⭐ they make *deployment* uniform; **your database is still the bottleneck** (Day 324) |
| ⭐ "Containers replace VMs" | ⭐ for multi-tenant untrusted workloads, **VMs are still the boundary** |
| ⭐ **"Stateless is easy, so state is too"** | ⭐⭐ **stateful containers need volumes, backups and careful scheduling — the hard part is unchanged** |
| "It fixes dependency hell" | ⭐ it *contains* it — you still upgrade base images and CVEs |
| ⭐ "Smaller is always better" | ⭐ Alpine's musl libc has caused real JVM issues (Day 363) |

⚠️ **The security point deserves emphasis because it is commonly overstated in the other
direction.** Containers are a **strong operational boundary and a weak security boundary.** Running
untrusted code needs more — user namespaces, seccomp, gVisor, or an actual VM. **Knowing that is the
difference between using containers and trusting them.**

# Part 4 — ⭐ The Java engineer's view, and when not to bother

**⭐ You already ship one artefact. What does the container add?**

| ⭐ Added to the image | ⭐ Why it matters |
|---|---|
| ⭐ **The exact JVM build** | ⭐ a JIT or GC change between patch releases is a real behaviour change |
| ⭐ **glibc / OS libraries** | native dependencies, DNS resolution behaviour |
| ⭐ **CA certificate bundle** | ⭐⭐ an outbound TLS call failing only in production is usually this |
| ⭐ Timezone database | ⭐ date handling that differs by host |
| Locale data | string comparison and formatting |
| ⭐ **The startup command** | ⭐ flags, memory settings, and the signal handling that makes shutdown graceful (Day 361) |

⚠️ **And the container changes JVM behaviour**, which is why Day 361 exists: the JVM must be told to
read cgroup limits rather than host resources, **or it sizes the heap for a 64 GB machine inside a
512 MB container and gets killed** (Day 144).

## ⭐ When containers are not the answer

| Situation | ⭐ Better |
|---|---|
| ⭐ A single desktop tool or CLI | ⭐ just ship the binary or jar |
| ⭐ **One app, one server, no team** | ⭐ a systemd unit is genuinely simpler |
| ⭐ Heavy GPU / kernel-module workloads | ⭐ possible, but the plumbing outweighs the gain |
| ⭐ **Untrusted multi-tenant code** | ⭐⭐ VMs or sandboxed runtimes |
| A database you have not planned storage for | ⭐ **a managed service beats a stateful container you have not thought through** |

> **⭐ The honest position: containers buy you a reproducible artefact and a uniform deployment
> interface. If you have neither a team nor multiple environments, you are paying for something you
> do not yet need** — and saying that is a stronger answer than reflexive adoption.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Calling a container a lightweight VM | ⭐ **it explains none of the actual behaviour** |
| ⭐⭐ Treating containers as a security boundary | ⭐⭐ **shared kernel; a kernel bug escapes** |
| ⭐ Adopting them for "scalability" | the database did not move |
| ⭐ **Building different images per environment** | ⭐⭐ you lost the one benefit that mattered |
| ⭐ Configuring a running container | ⭐ drift returns, and the image is now a lie |
| Expecting other-OS kernels to work | Linux containers need Linux |
| ⭐ Ignoring the JVM's cgroup awareness | ⭐ **heap sized for the host → OOMKill** |
| Containerising a database with no volume plan | data loss on the first restart |
| Assuming smaller base images are strictly better | musl has broken JVM workloads |

## Interview questions

**Q: What is a container?**
A normal Linux process whose view of the system has been restricted — namespaces limit what it can
see, cgroups limit what it can use, and a layered filesystem gives it its own root. It is not a
virtual machine: there is no guest kernel and no boot, which is why it starts in milliseconds and
why it cannot run a different operating system's kernel.

**Q: Why use them, then?**
For the immutable artefact rather than the isolation. The image is content-addressed, so the exact
same bytes run in CI, staging and production; rollback is a pointer change; configuration comes from
outside; and drift becomes impossible because you cannot patch a running container into a different
image. Isolation is the mechanism; reproducibility is the reason.

**Q: Are containers secure?**
They are a strong operational boundary and a weak security boundary. The kernel is shared, so a
kernel vulnerability escapes the container, and by default root inside can be close to root outside.
For untrusted multi-tenant workloads I would use VMs or a sandboxed runtime; for my own services I
would still drop capabilities, run non-root and use seccomp, but I would not claim isolation
equivalent to a VM.

**Q: You already build a fat jar. What does a container add?**
Everything below the jar: the exact JVM build, glibc, the CA certificate bundle, timezone and locale
data, and the startup command with its flags and signal handling. Those are precisely the things that
differ between a laptop and production — an outbound TLS failure that only happens in production is
almost always the certificate bundle.

**Q: When would you not containerise?**
A single application on a single server with no team — a systemd unit is genuinely simpler and I
would say so. Also desktop tools, and untrusted multi-tenant code, where I want a real VM boundary.
Containers buy a reproducible artefact and a uniform deployment interface; if you have one
environment and one person, you are paying for something you do not yet need.

## Mini task

1. **Time a VM boot against a container start** for equivalent workloads. Record both numbers.
2. ⭐ Run `docker run --rm alpine ps aux` and then `ps aux` on the host. **Find your container's
   process on the host** — prove it is an ordinary process.
3. ⭐ Run a container and `docker exec` into it; check `uname -r` **inside and outside.** Confirm the
   kernel is identical.
4. ⭐ **List every environmental thing your app depends on** — JVM version, locale, timezone, CA
   certs, native libs. **That list is what the image is for.**
5. Deliberately build **two images from the same source with different base images** and find a
   behavioural difference (TLS, locale, or date formatting).
6. ⭐ Run your Spring Boot app with `-m 512m` and **no** JVM container flags. **Reproduce the
   OOMKill.** (Day 361 fixes it.)
7. Write one paragraph: *"why we containerise, in one sentence, and what it does not buy us."*

## 🎙️ Articulation drill

**Two minutes:** *"Explain containers to a senior engineer who has never used them."*

**⭐ The marker: you never say "lightweight VM".** *"It is a process with a restricted view — three
kernel features and a layered filesystem. Which is why it starts instantly and why it shares your
kernel, for better and worse."*

**⭐ Then the second marker: you name the immutable artefact as the reason, not isolation.** Anyone
can recite the benefits list; **saying which benefit you actually adopted them for is what sounds
like experience.**
