# Day 135

**L-135** · Component scanning — how Spring finds your beans

**Time:** 3 hrs · **Mode:** NEW

> How the container discovers what to manage. The mechanism is short; the consequence is not —
> **your package structure is a wiring decision**, and getting it wrong produces the single most
> common Spring startup failure.

---

# Part 1 — What `@SpringBootApplication` actually is

```java
@SpringBootApplication
public class DemoApplication { … }
```

```java
@SpringBootConfiguration     // = @Configuration — this class declares beans
@EnableAutoConfiguration     // ⭐ Boot's auto-configuration (Day 140)
@ComponentScan               // ⭐ scan THIS package and everything below it
public @interface SpringBootApplication { }
```

**Three annotations in one**, and the third decides everything today: **`@ComponentScan` with no
arguments scans the package of the annotated class, recursively downward.**

## ⭐ The failure everyone hits once

```
com.acme.app
  └── DemoApplication.java          @SpringBootApplication  → scans com.acme.app.**

com.acme.services
  └── OrderService.java             @Service                → ❌ NEVER FOUND
```

```
Parameter 0 of constructor in com.acme.app.OrderController required a bean of type
'com.acme.services.OrderService' that could not be found.
```

**The service is annotated, compiled and on the classpath — and Spring never looks at it**, because
it is not under the main class's package.

```
✅ com.acme                      ← main class HERE
     ├── app / config
     ├── order    (controller, service, repository)
     └── payment
```

> **Put the main class in the root package.** Everything else lives beneath it, and scanning is
> automatic. This is the single most common Spring startup problem and it is entirely a package-
> layout question.

# Part 2 — Controlling the scan

```java
@ComponentScan(basePackages = {"com.acme.order", "com.acme.payment"})

@ComponentScan(basePackageClasses = {OrderMarker.class, PaymentMarker.class})   // ⭐ refactor-safe

@ComponentScan(
    basePackages = "com.acme",
    excludeFilters = @Filter(type = ASSIGNABLE_TYPE, classes = LegacyService.class))

@ComponentScan(
    includeFilters = @Filter(type = ANNOTATION, classes = MyCustomStereotype.class),
    useDefaultFilters = false)                    // ⭐ ONLY the include filter applies
```

**`basePackageClasses` over `basePackages`.** A `String` package name is not checked by the compiler,
so a rename or a package move silently breaks the scan; a class reference is followed by refactoring
tools and fails to compile if it moves.

The convention is a marker interface per module:

```java
package com.acme.order;
public interface OrderModule { }        // empty — exists only to name the package
```

## Scanning cost

**Scanning reads bytecode for every class under the base packages** to check for annotations. Broad
scanning is a real startup cost:

```java
@ComponentScan("com")              // 💀 scans every class in every "com.*" dependency
```

For a large application, narrowing the scan is one of the more effective startup optimisations. Boot
3's AOT processing removes it entirely for native images (Day 185B) by resolving components at build
time.

## `@Component` versus `@Bean` — where each is discovered

```java
// Discovered by SCANNING
@Service class OrderService { }

// Discovered by being DECLARED in a @Configuration class
@Configuration
class AppConfig {
    @Bean ObjectMapper objectMapper() { … }        // Day 132
}
```

**`@Configuration` classes are themselves found by scanning**, and then their `@Bean` methods are
processed. So a `@Configuration` class outside the scanned packages is as invisible as any other
component.

# Part 3 — Structuring a codebase

The choice that shapes everything else.

## ❌ By layer (technical)

```
com.acme
  ├── controller/   OrderController, CustomerController, PaymentController
  ├── service/      OrderService, CustomerService, PaymentService
  ├── repository/   OrderRepository, CustomerRepository, PaymentRepository
  └── model/        Order, Customer, Payment
```

**Familiar and wrong at scale**, for a specific reason: **one change touches four packages**. Adding
a field to an order means edits in `controller`, `service`, `repository` and `model` — Day 096's
**Shotgun Surgery** smell, institutionalised by the directory structure.

It also makes everything public: `OrderService` must be public for `OrderController` in another
package to use it, so **there is no way to keep anything internal to a feature**.

## ✅ By feature (package-by-feature)

```
com.acme
  ├── order/
  │     ├── OrderController.java        public
  │     ├── OrderService.java           ⭐ package-private
  │     ├── OrderRepository.java        ⭐ package-private
  │     └── Order.java
  ├── payment/
  │     ├── PaymentController.java
  │     └── PaymentService.java
  └── shared/
```

Three benefits, and the second is the one that matters most:

**High cohesion.** Everything about orders is in one place; a change touches one package.

**⭐ Real encapsulation.** `OrderService` can be **package-private**, so nothing outside
`com.acme.order` can use it — the compiler enforces the module boundary. **Spring instantiates and
injects package-private beans perfectly well**, because it uses reflection.

**A natural service boundary.** If `order` later becomes its own service, the package moves whole.

```java
package com.acme.order;

@Service
class OrderService { }                        // ⭐ no `public` — deliberately invisible outside

@RestController
public class OrderController {                 // public: it is the entry point
    OrderController(OrderService service) { … } // same package, so it can see it
}
```

**Package-private services are underused and free.** They turn "please do not call this from another
feature" from a code-review comment into a compile error.

## Communication between features

```java
// ❌ order depends on the internals of payment
class OrderService { OrderService(PaymentService payments) { … } }   // needs PaymentService public

// ✅ order depends on an interface it owns — Day 091's DIP
package com.acme.order;
public interface PaymentPort { Receipt charge(Money amount); }        // OWNED BY order

package com.acme.payment;
@Component class PaymentAdapter implements PaymentPort { }            // implemented by payment

// ✅ or fully decoupled, via an event (Day 133)
events.publishEvent(new OrderPlaced(order.id()));
```

**The interface belongs to the consumer, not the provider.** That is what makes the dependency arrow
point inward (Day 091) and is the basis of hexagonal architecture, which Stage 8 develops.

# Part 4 — Conditional registration

```java
@Component
@ConditionalOnProperty(name = "features.new-pricing", havingValue = "true")
class NewPricingService implements PricingService { }

@Component
@ConditionalOnMissingBean(PricingService.class)          // ⭐ a default that yields
class DefaultPricingService implements PricingService { }
```

| Condition | Registers when |
|---|---|
| `@ConditionalOnProperty` | A property has a given value |
| `@ConditionalOnClass` | A class is on the classpath ⭐ |
| `@ConditionalOnMissingClass` | It is not |
| `@ConditionalOnBean` / `@ConditionalOnMissingBean` | Another bean is present or absent ⭐ |
| `@ConditionalOnWebApplication` | It is a web application |
| `@Conditional(MyCondition.class)` | Your own logic |

**`@ConditionalOnMissingBean` is the mechanism behind every "define your own and Spring backs off"
behaviour** — it is how auto-configuration provides a default `ObjectMapper`, `DataSource` or
`PasswordEncoder` that you can override simply by declaring your own (Day 140).

⚠️ **Ordering matters and is subtle.** `@ConditionalOnMissingBean` is evaluated when the definition is
processed, so it only reliably sees beans registered *earlier*. In your own configuration this
produces order-dependent behaviour; auto-configuration is explicitly ordered to run *after* user
configuration, which is why the pattern works there and is fragile in application code.

**Prefer `@ConditionalOnProperty` for feature flags** — explicit, greppable, and it does not depend
on evaluation order.

⚠️ **Conditions are evaluated once, at startup.** A property changed at runtime does not add or remove
a bean. For a runtime toggle you need a feature-flag check inside the method (Day 088), not a
condition on the bean.

# Part 5 — Debugging the scan

```bash
java -jar app.jar --debug        # ⭐ the CONDITIONS EVALUATION REPORT (Day 130)
```

```
Positive matches:
-----------------
   DataSourceAutoConfiguration matched:
      - @ConditionalOnClass found required classes 'javax.sql.DataSource'

Negative matches:
-----------------
   RedisAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class
           'org.springframework.data.redis.core.RedisOperations'
```

**That report answers "why is this bean not here?" definitively**, and it is the correct first move
for any "bean not found" or "unexpected bean" problem.

```java
// list everything the container actually has
Arrays.stream(ctx.getBeanDefinitionNames()).sorted().forEach(System.out::println);

// find every implementation of an interface
ctx.getBeansOfType(PaymentGateway.class).forEach((name, bean) ->
        System.out.println(name + " → " + bean.getClass()));
```

```properties
logging.level.org.springframework.context.annotation=DEBUG   # what is being scanned
```

## When scanning is not enough

```java
@Import(SecurityConfig.class)                     // pull in a specific @Configuration
@Import(MyRegistrar.class)                        // ImportBeanDefinitionRegistrar — programmatic
@ImportResource("classpath:legacy-beans.xml")     // legacy XML
```

**`ImportBeanDefinitionRegistrar` registers definitions programmatically**, and it is how Spring Data
creates a repository bean for every interface you declare — there is no class to scan, so the
definitions are generated (Day 132's "definitions are data" paying off).

**`@Enable*` annotations are all `@Import` in disguise:**

```java
@EnableAsync      → @Import(AsyncConfigurationSelector.class)
@EnableCaching    → @Import(CachingConfigurationSelector.class)
@EnableWebSecurity → @Import(...)
```

Recognising that removes the last of the mystery: an `@Enable*` annotation imports a configuration
class that registers the post-processors that create the proxies.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Main class not in the root package | Beans silently not found — the classic startup failure |
| `basePackages` as strings | A rename or move breaks the scan with no compile error |
| Scanning `"com"` or `"org"` | Scans every dependency; slow startup |
| Package-by-layer at scale | Shotgun surgery; nothing can be package-private |
| Everything public | No module boundaries; any feature can call any internal |
| One feature depending on another's service | Coupling; the interface belongs to the consumer |
| `@ConditionalOnMissingBean` in application config | Order-dependent and fragile |
| Expecting conditions to re-evaluate at runtime | They run once, at startup |
| Not using `--debug` for a missing bean | Guessing instead of reading the report |
| `@Configuration` class outside the scanned packages | As invisible as any other component |

## Interview questions

**Q: How does Spring find your beans?**
`@ComponentScan` — included in `@SpringBootApplication` — scans the annotated class's package and
everything beneath it, reading bytecode for stereotype annotations and registering a `BeanDefinition`
for each. `@Configuration` classes are found the same way, and then their `@Bean` methods are
processed.

**Q: A bean is not being found. What is the most likely cause?**
It is outside the main class's package tree. The main class should be in the root package so
everything else is beneath it. `--debug` prints the conditions report, which settles it.

**Q: What is `@SpringBootApplication` composed of?**
`@SpringBootConfiguration`, `@EnableAutoConfiguration` and `@ComponentScan`.

**Q: Package by layer or by feature?**
By feature. Package-by-layer means one logical change touches four packages — shotgun surgery — and
forces everything to be public. Package-by-feature gives high cohesion, lets services be
package-private so the compiler enforces module boundaries, and produces a natural extraction
boundary if the feature becomes its own service.

**Q: Can Spring inject a package-private bean?**
Yes — it uses reflection. That is what makes package-private services practical, and it turns "do not
call this from another feature" into a compile error.

**Q: How should one feature call another?**
Through an interface owned by the *consumer*, implemented by the provider — so the dependency points
inward — or fully decoupled through an application event.

**Q: What is `@ConditionalOnMissingBean` for?**
It is the mechanism behind "declare your own and Spring backs off" — auto-configuration provides a
default only if you have not defined one. It is order-sensitive, which is fine in auto-configuration
(explicitly ordered after user config) and fragile in application code.

**Q: How do you find out why a bean was or was not created?**
Run with `--debug` and read the conditions evaluation report: positive matches, negative matches, and
the exact condition that decided each.

## Mini task

1. Move a `@Service` outside the main class's package and read the startup failure. Move it back.
2. Restructure a project from package-by-layer to package-by-feature. Then make every service
   package-private and fix whatever breaks — the compile errors are the coupling you had.
3. Make one feature depend on another's service, then refactor to a consumer-owned interface. Confirm
   the provider's class can become package-private.
4. Replace a `basePackages` string with `basePackageClasses` and a marker interface. Rename the
   package and confirm one form breaks and the other does not.
5. Scan `"com"` deliberately and measure the startup difference.
6. Write a `@ConditionalOnProperty` feature flag and toggle it across restarts. Then try changing the
   property at runtime and confirm nothing happens.
7. Write a `@ConditionalOnMissingBean` default, declare your own bean, and confirm the default backs
   off. Then move your declaration and observe the order sensitivity.
8. Run `--debug` and find three negative matches. For each, name the missing class or property.
9. Print every bean of one interface type with `getBeansOfType` and note the proxy class names.
10. Write a custom `@Conditional` that registers a bean only when an environment variable is present.

## 🎙️ Articulation drill

Two minutes: **"How would you structure a Spring Boot codebase?"**

Main class in the root package so scanning covers everything; packages by feature rather than by
layer, because one change should touch one package; services package-private so the compiler enforces
feature boundaries; and cross-feature calls through an interface the consumer owns, or an event.
Close with the practical point that `--debug` answers every "why is this bean here or not here"
question — knowing where to look is what stops the framework feeling like magic.
