# Part 1 — L-067 · Explicit locks

## The five things `synchronized` cannot do

```java
ReentrantLock lock = new ReentrantLock();

lock.lock();
try { criticalSection(); }
finally { lock.unlock(); }        // ← YOU must write this. Always. In finally.
```

That extra ceremony buys:

| Capability | Method | Why it matters |
|---|---|---|
| **Try without blocking** | `tryLock()` | Do something else instead of waiting |
| **Time out** | `tryLock(50, MILLISECONDS)` | **Deadlock recovery** — bail and retry |
| **Be interruptible** | `lockInterruptibly()` | A blocked thread can be cancelled |
| **Fairness** | `new ReentrantLock(true)` | FIFO — prevents starvation |
| **Non-block-structured** | lock in one method, unlock in another | Hand-over-hand locking |
| **Multiple wait sets** | `newCondition()` | Wake *only* producers, or *only* consumers |
| **Introspection** | `getHoldCount`, `getQueueLength`, `isLocked` | Monitoring and diagnostics |

The timeout row is the one to remember: **`tryLock` with a timeout turns a deadlock from a permanent
hang into a recoverable failure** (Day 071).

The forgotten `unlock()` is the tax. Where `synchronized` releases on exception automatically
(Day 066's generated exception table), `ReentrantLock` does not — so a missing `finally` means the
lock is held forever and every other thread blocks permanently.

## Fairness, and why it is usually wrong

```java
new ReentrantLock()       // barging: whoever is running may jump the queue
new ReentrantLock(true)   // fair: strict FIFO by arrival
```

Non-fair (the default) lets a thread that happens to be running acquire an available lock even
though others are queued. That sounds unjust; it is dramatically faster, because handing the lock to
an already-running thread avoids a park/unpark pair (a context switch, ~1–10 µs).

Fair locks can be **an order of magnitude slower** in throughput. Use fairness only when starvation
is an observed problem — a long-running thread repeatedly losing to short ones. `synchronized` is
always non-fair, with no option.

## `ReadWriteLock`

```java
ReadWriteLock rw = new ReentrantReadWriteLock();

rw.readLock().lock();      // many readers concurrently
try { return cache.get(k); } finally { rw.readLock().unlock(); }

rw.writeLock().lock();     // exclusive: no readers, no other writer
try { cache.put(k, v); } finally { rw.writeLock().unlock(); }
```

The invariant: **N readers or 1 writer, never both.** It pays off only when reads massively
outnumber writes *and* the critical section is long enough to matter — the bookkeeping is more
expensive than a plain lock, so a read-write lock over a two-nanosecond map lookup is a net loss.
Measure before adopting.

Two behaviours to know:

- **Downgrade is legal** (acquire write, acquire read, release write), **upgrade is not** (read →
  write deadlocks, because the writer waits for readers to leave and you are one of them).
- **Writer starvation** is possible under a continuous stream of readers unless you construct it
  fair.

`StampedLock` (Java 8) adds **optimistic reads**: take a stamp, read without any lock at all,
then validate the stamp and fall back to a real read lock if a write intervened. It is faster still
but not reentrant and easy to misuse — know the name and the idea.

```java
long stamp = sl.tryOptimisticRead();
int x = this.x, y = this.y;                 // no lock held
if (!sl.validate(stamp)) {                  // a writer came through
    stamp = sl.readLock();
    try { x = this.x; y = this.y; } finally { sl.unlockRead(stamp); }
}
```

## `wait` / `notify` — the primitive underneath everything

```java
synchronized (lock) {
    while (!condition) {       // ← WHILE, never if
        lock.wait();           // releases the monitor and sleeps
    }
    doWork();
}

synchronized (lock) {
    condition = true;
    lock.notifyAll();          // wakes waiters; they re-acquire before returning
}
```

Four rules, each of which is a classic bug when broken:

**1. You must hold the monitor.** `wait`/`notify` outside `synchronized` throws
`IllegalMonitorStateException`. This is the JVM enforcing that the check-and-wait is atomic.

**2. `wait()` releases the lock.** That is the whole point — otherwise nobody could ever change the
condition. `sleep()` does *not* release it, which is the difference the interview asks about.

**3. Always wait in a `while` loop, never an `if`.** Three reasons: *spurious wakeups* are permitted
by the specification and do occur; `notifyAll` wakes everyone, so another thread may have consumed
the condition before you re-acquire; and re-checking is free. An `if` here is a real bug that
appears under load and never in testing.

**4. Prefer `notifyAll` to `notify`.** `notify` wakes one arbitrary waiter. If waiters are waiting
for *different* conditions on the same monitor — producers and consumers on one lock — you can wake
the wrong one, which returns to waiting, and the thread that could have made progress is never
woken. That is a **lost wakeup**, and the system hangs with no error. `notify` is safe only when all
waiters are interchangeable and each notify enables exactly one.

## `Condition` — the fix for that last problem

`Condition` gives you **multiple wait sets on one lock**, which is exactly what `wait`/`notify`
lacks:

```java
public class BoundedBuffer<E> {
    private final Object[] items;
    private int count, putIdx, takeIdx;

    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedBuffer(int capacity) { items = new Object[capacity]; }

    public void put(E x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();      // producers wait here
            items[putIdx] = x;
            putIdx = (putIdx + 1) % items.length;
            count++;
            notEmpty.signal();                                  // wake ONE consumer
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public E take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();                // consumers wait here
            E x = (E) items[takeIdx];
            items[takeIdx] = null;
            takeIdx = (takeIdx + 1) % items.length;
            count--;
            notFull.signal();                                   // wake ONE producer
        } finally { lock.unlock(); }
    }

    public int size() { lock.lock(); try { return count; } finally { lock.unlock(); } }
}
```

**Type this one by hand.** It is a Stage 1 exit-gate item — *"live-code a thread-safe bounded
blocking queue"* — and it is asked constantly. Every line is deliberate:

- Separate conditions mean `signal()` is safe: a producer signalling `notEmpty` cannot accidentally
  wake another producer, so no lost wakeup and no wasted context switch.
- `await()` in a `while` loop, for the same reasons as `wait()`.
- `lock()` outside the `try`, `unlock()` in the `finally`. If `lock()` were inside the `try`, an
  exception on acquisition would take you to a `finally` that unlocks a lock you never held.
- The circular buffer means no allocation and no shifting.
- `items[takeIdx] = null` prevents the array retaining a dead reference — Day 027's leak pattern.

The `Condition` API mirrors `Object`'s but renamed to avoid confusion: `await`/`signal`/`signalAll`
instead of `wait`/`notify`/`notifyAll`. It also offers `awaitNanos`, `awaitUntil` and
`awaitUninterruptibly`, none of which `Object` has.

In production you would of course just use `ArrayBlockingQueue` — which is implemented **exactly
like the code above**, and now you know why.

## AQS — the thing all of these are built on

`ReentrantLock`, `ReentrantReadWriteLock`, `Semaphore`, `CountDownLatch` and
`ArrayBlockingQueue`'s internals all sit on **`AbstractQueuedSynchronizer`**. It maintains:

- a single **`volatile int state`** whose meaning each subclass defines — hold count for a lock,
  permits for a semaphore, remaining count for a latch;
- a **CLH-style FIFO queue** of waiting threads, parked via `LockSupport.park`/`unpark`.

A subclass implements `tryAcquire`/`tryRelease` in terms of a CAS on `state` (Day 068), and AQS
handles all the queueing, parking and cancellation. Knowing this one sentence lets you answer "how
is `ReentrantLock` implemented?" — *a CAS on a volatile state word plus an AQS wait queue* — which
is a notably strong answer.

## Choosing

```
Do you need timeout, interruptibility, fairness, or multiple conditions?
  ├── no  → synchronized          (simpler, auto-release, JIT-optimised)
  └── yes → ReentrantLock
Reads vastly outnumber writes AND the section is long?
  └── ReentrantReadWriteLock, or StampedLock if you can accept the constraints
Is there a ready-made concurrent collection?
  └── use it — ConcurrentHashMap, ArrayBlockingQueue (almost always the right answer)
```

The last branch is the real advice. **Doug Lea already wrote your data structure and it is more
correct than the one you are about to write.**

# Part 2 — B-14 · Why `epoll` matters

Day 064 introduced multiplexing. This is why it is *the* foundational primitive of modern servers.

## The same loop, five names

```
       ┌──────────────────────────────────────────┐
       │  while (true) {                          │
       │      events = epoll_wait(epfd, ...);     │  ← one thread blocks here
       │      for (e : events) handle(e);         │  ← callbacks must never block
       │  }                                       │
       └──────────────────────────────────────────┘
```

| System | Name for it | Underneath |
|---|---|---|
| Node.js | the event loop (libuv) | `epoll` / `kqueue` / IOCP |
| nginx | worker processes | `epoll` |
| Redis | single-threaded event loop | `epoll` |
| Netty / WebFlux / Vert.x | `EventLoopGroup` | Java `Selector` → `epoll` |
| Python asyncio, Go netpoller, Rust tokio | selector / netpoller / reactor | `epoll` |

**Redis is the clearest proof of the idea.** It is famously single-threaded for command execution
and still serves hundreds of thousands of operations per second — because every operation is
in-memory microseconds and the network waiting is handled by `epoll`. Concurrency and parallelism
are different things (Day 064): Redis is highly concurrent with one core of parallelism.

## Level-triggered vs edge-triggered

```
epoll_ctl(..., EPOLLIN)              level-triggered  (default)
epoll_ctl(..., EPOLLIN | EPOLLET)    edge-triggered
```

- **Level-triggered**: report readiness as long as data remains unread. Forgiving — read some now,
  the rest next iteration.
- **Edge-triggered**: report only the *transition* from not-ready to ready. Fewer wakeups, but you
  **must drain the socket until `EWOULDBLOCK`**, or the remaining bytes are never reported and that
  connection silently hangs forever.

Java's `Selector` is level-triggered. Netty uses edge-triggered on its native Linux transport, which
is one reason it is faster and also why writing correct edge-triggered code by hand is a bad idea.

## The rule the whole architecture rests on

> **Never block inside an event-loop callback.**

One `Thread.sleep`, one synchronous JDBC call, one `.block()` on a reactive chain, and **every
connection assigned to that loop stalls**. Not just the current request — all of them. This is the
defining hazard of async programming and the reason async codebases need discipline that blocking
ones do not.

The escape hatch is to hand blocking work to a separate pool (`Schedulers.boundedElastic()` in
Reactor, `libuv`'s thread pool in Node) — which reintroduces exactly the threads you were avoiding,
for the operations that genuinely need them.

**That trade-off is what Day 072 dissolves.** Virtual threads let you write blocking-style code
where the *runtime* performs the multiplexing: when a virtual thread blocks on I/O, it unmounts from
its carrier thread and the carrier goes on to run something else. You get `epoll` scaling with
sequential code, ordinary stack traces, and debuggers that work.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `unlock()` not in `finally` | Lock held forever on exception; total stall |
| `lock()` inside the `try` | `finally` unlocks a lock you never acquired |
| `if` instead of `while` around `wait`/`await` | Spurious wakeup or stolen condition ⇒ corrupt state |
| `notify` with heterogeneous waiters | Lost wakeup; silent hang |
| `wait`/`notify` outside `synchronized` | `IllegalMonitorStateException` |
| Fair locks by default | Throughput collapse |
| Read-write lock on a short section | Slower than a plain lock |
| Attempting a read → write upgrade | Deadlock |
| Blocking inside an event-loop callback | Every connection on that loop stalls |
| Edge-triggered without draining | Connection hangs with data pending |

## Interview questions

**Q: `ReentrantLock` vs `synchronized`?**
Same semantics plus `tryLock`, timeouts, interruptibility, fairness, non-block-structured locking
and multiple conditions — at the cost of a manual `unlock()` in a `finally`. Use `synchronized`
unless you need one of those.

**Q: Why must `wait` be in a `while` loop?**
Spurious wakeups are allowed, and with `notifyAll` another thread may consume the condition before
you re-acquire the monitor. The condition must be re-checked after waking.

**Q: `wait` vs `sleep`?**
`wait` releases the monitor and needs a notification (or timeout) to resume; `sleep` holds every
lock it has and resumes on time. `wait` is on `Object` and requires the monitor; `sleep` is static
on `Thread`.

**Q: `notify` vs `notifyAll`?**
`notify` wakes one arbitrary waiter — safe only when all waiters are interchangeable. Otherwise it
risks a lost wakeup. `notifyAll` is safe but wakes everyone; `Condition.signal` with separate
conditions gives you both safety and precision.

**Q: How is `ReentrantLock` implemented?**
On `AbstractQueuedSynchronizer`: a `volatile int state` manipulated by CAS, plus a FIFO queue of
parked threads.

**Q: Why is Redis fast if it is single-threaded?**
Because it is I/O-bound, not CPU-bound, and `epoll` lets one thread wait on hundreds of thousands of
sockets. Every command is an in-memory operation measured in microseconds.
