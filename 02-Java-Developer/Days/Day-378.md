# Day 378

**L-378** · Kubernetes II — graceful shutdown, disruption budgets, and when it is overkill

**Time:** 3 hrs · **Mode:** NEW

> **⭐ The hardest thing to get right in Kubernetes is not deploying — it is stopping.**
>
> Endpoint removal is asynchronous, so a pod that receives SIGTERM is still being sent traffic. **The
> fix is a sleep, and the fact that the correct answer is a sleep tells you something honest about
> the platform.**

---

# Part 1 — ⭐⭐ The shutdown sequence, and the race in it

```
⭐ You delete a pod. TWO THINGS HAPPEN IN PARALLEL — and nothing coordinates them:
⭐
⭐   ⭐ A) kubelet: preStop hook → SIGTERM → wait terminationGracePeriodSeconds → SIGKILL
⭐   ⭐ B) endpoint controller: remove from Endpoints → kube-proxy/ingress on EVERY node updates
⭐
⭐ ⭐⭐ (B) TAKES SECONDS. (A) STARTS IMMEDIATELY.
⭐ ⇒ ⭐⭐ traffic still arrives at a pod that is already shutting down ⇒ ⭐⭐ 502s during every deploy
```

| ⭐ The fix, all four parts required | |
|---|---|
| ⭐⭐ **`preStop: sleep 5–15s`** | ⭐⭐ **do nothing, and keep serving, while endpoint removal propagates** |
| ⭐ **exec-form entrypoint** | so the JVM actually receives SIGTERM (Day 361) |
| ⭐ **`server.shutdown=graceful`** | stop accepting, finish in-flight (Day 143) |
| ⭐⭐ **`terminationGracePeriodSeconds` > sleep + drain** | ⭐⭐ **or SIGKILL lands mid-drain** |

```yaml
⭐ lifecycle:
⭐   preStop: { exec: { command: ["sh","-c","sleep 10"] } }
⭐ terminationGracePeriodSeconds: 60      ⭐ 10 (sleep) + 30 (drain) + headroom
```

> **⭐ The counter-intuitive part worth saying out loud: the `preStop` sleep does nothing at all — and
> that is the point.** It exists purely to keep the pod serving while every node's proxy learns it
> should stop routing there. **Removing it is the single most common cause of 502s on deploy**, and
> the symptom is intermittent errors nobody can reproduce.

⚠️ **The pod also stops being ready before it stops serving, which is correct.** Readiness failing
speeds endpoint removal; **the sleep covers the propagation delay that remains.**

# Part 2 — ⭐⭐ Disruption: the budget that saves you

```
⭐ A node is drained for an upgrade. ⭐⭐ Kubernetes will happily evict EVERY pod of your Deployment
⭐ if they all happen to be on that node — ⭐⭐ unless you tell it not to.
```

```yaml
⭐ apiVersion: policy/v1
⭐ kind: PodDisruptionBudget
⭐ spec:
⭐   minAvailable: 2                   ⭐ or maxUnavailable: 1
⭐   selector: { matchLabels: { app: orders } }
```

| ⭐ PDB protects against | ⭐ It does NOT protect against |
|---|---|
| ⭐ node drains and cluster upgrades | ⭐⭐ **a node crashing — that is not a voluntary disruption** |
| ⭐ **Descheduler and autoscaler evictions** | your own rolling update (that has its own settings) |

⚠️ **A PDB with `minAvailable` equal to your replica count blocks node drains entirely** — the
cluster upgrade stalls and someone eventually forces it. **Set it below your replica count, and pair
it with anti-affinity so replicas are not all on one node in the first place.**

```yaml
⭐ topologySpreadConstraints:            ⭐ spread replicas across nodes and zones
⭐ - maxSkew: 1
⭐   topologyKey: topology.kubernetes.io/zone
⭐   whenUnsatisfiable: ScheduleAnyway   ⭐⭐ DoNotSchedule can leave pods Pending forever
```

> **⭐ Three replicas on one node is not three replicas** — it is one failure domain wearing a
> replica count. **Spread constraints plus a PDB are what make the number mean something.**

# Part 3 — ⭐ Scaling, state, and access

## ⭐ HPA, and why CPU is usually the wrong metric

```yaml
⭐ metrics:
⭐ - type: Pods
⭐   pods: { metric: { name: http_requests_per_second }, target: { averageValue: "100" } }
```

| ⭐ Metric | ⭐ Verdict |
|---|---|
| ⭐ CPU | ⭐⭐ **an I/O-bound JVM saturates on threads and pools while CPU looks idle** (Day 324) |
| ⭐ **Requests per second** | ⭐ a good proxy for load |
| ⭐⭐ **Queue depth / concurrency** | ⭐⭐ **closest to actual saturation** |
| ⭐ Latency | ⭐ scales after users are already suffering — a lagging signal |

⚠️ **And Day 324's fleet arithmetic applies: HPA scaling to 50 pods × 20 connections is 1,000
connections at a database sized for 200.** **Set `maxReplicas` from the connection budget, not from
optimism** — and remember the JVM's cold start means new pods are slow for the first thirty seconds.

## ⭐ StatefulSets and the database question

| StatefulSet gives | ⭐ Note |
|---|---|
| Stable network identity (`db-0`, `db-1`) | required for clustered software |
| Stable per-pod storage | a PVC per replica |
| Ordered start and stop | |

> **⭐ Running a production database on Kubernetes is a decision, not a default.** It is entirely
> possible with an operator, and **for most teams a managed database is the better trade**: you are
> not adding storage, backup, failover and version upgrades to a platform you are still learning.
> **Say the trade rather than a slogan in either direction.**

## ⭐ Security defaults that are wrong

| ⭐ Default | ⭐ Fix |
|---|---|
| ⭐⭐ **All pods can talk to all pods** | ⭐⭐ **NetworkPolicy — and until you add one, there is no segmentation** |
| ⭐ Default ServiceAccount is mounted | ⭐ `automountServiceAccountToken: false` unless needed |
| ⭐ Containers may run as root | ⭐ `runAsNonRoot`, `readOnlyRootFilesystem`, drop capabilities (Day 361) |
| ⭐ Secrets are base64 | encryption at rest + RBAC (Day 372) |
| No quotas | ⭐ ResourceQuota and LimitRange per namespace |

⚠️ **NetworkPolicy is the one people are most surprised by.** A fresh cluster is a flat network:
**any compromised pod can reach your database directly.** And policies are additive-deny — **until a
policy selects a pod, everything is allowed**, which means partial adoption gives partial protection
in a way that is easy to misread.

## ⭐ Templating

| Tool | ⭐ Trade |
|---|---|
| ⭐ **Helm** | ⭐ packaging, releases, third-party charts — **templated YAML with all that implies** |
| ⭐ **Kustomize** | ⭐ overlays, no templating language — **simpler for your own apps** |
| ⭐ Both | ⭐ common: Helm for third-party, Kustomize for your own |

# Part 4 — ⭐⭐ When Kubernetes is overkill

```
⭐ The real question is not "can we run it?" ⭐⭐ It is "who operates it at 3am, and for how many services?"
```

| ⭐ You probably do NOT need it | ⭐ You probably do |
|---|---|
| ⭐ **Fewer than ~5 services** | ⭐ dozens of services, several teams |
| ⭐ **One or two environments** | many environments, frequent deploys |
| ⭐⭐ **No platform capacity** | ⭐ someone owns the platform |
| ⭐ Traffic one VM handles comfortably | ⭐ genuine autoscaling needs |
| ⭐ **A small team shipping product** | ⭐⭐ **the org problem Kubernetes solves is real for you** (Day 340) |

| ⭐ The honest alternatives | |
|---|---|
| ⭐ **A managed PaaS** (Cloud Run, App Runner, Fly, Heroku-likes) | ⭐⭐ containers, autoscaling, TLS, deploys — **almost no operations** |
| ⭐ ECS/Fargate | containers without a control plane to run |
| ⭐ **Compose on one VM + systemd** | ⭐ Day 365 — genuinely fine for a small system |
| A load balancer and three VMs | ⭐ boring, reliable, cheap to reason about |

⚠️ **The costs are real and usually under-counted: an API you must learn, upgrades every few months,
CNI and ingress and storage decisions, RBAC, a whole new debugging vocabulary, and an on-call surface
that now includes the platform.** **Managed control planes remove some of that; they do not remove
the operational learning curve.**

> **⭐ The position to hold: Kubernetes is excellent and I would use it where the organisational
> problem is real. For a team of six with four services, a managed platform ships the same product
> with a fraction of the operational surface — and choosing that is engineering judgement, not
> ignorance.** It is Day 340's argument, one layer down.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **No `preStop` sleep** | ⭐⭐ **502s on every deploy, unreproducible** |
| ⭐ Grace period shorter than sleep + drain | SIGKILL mid-drain |
| ⭐ Shell-form entrypoint | SIGTERM never reaches the JVM (Day 361) |
| ⭐⭐ **No PodDisruptionBudget** | ⭐⭐ a node drain can take every replica |
| ⭐ `minAvailable` equal to replicas | blocks cluster upgrades entirely |
| ⭐ **No spread constraints** | ⭐ three replicas on one node is one failure domain |
| `DoNotSchedule` with tight skew | pods Pending forever |
| ⭐ **HPA on CPU for an I/O-bound app** | ⭐ never triggers until everything is timing out |
| ⭐ `maxReplicas` not derived from the connection budget | scaling the app kills the database (Day 324) |
| ⭐ **No NetworkPolicy** | ⭐⭐ flat network — any pod reaches the database |
| ⭐ Default ServiceAccount token mounted | needless credential in every pod |
| ⭐ A database on Kubernetes by default | a decision made by omission |
| ⭐⭐ **Kubernetes for four services and six people** | ⭐ platform work displacing product work |

## Interview questions

**Q: Why do you get 502s during a rolling deploy?**
Because endpoint removal is asynchronous. When a pod is deleted, the kubelet starts the shutdown
sequence immediately while the endpoint controller and every node's proxy take seconds to stop
routing to it — so traffic arrives at a pod that is already terminating. The fix is a `preStop` sleep
of five to fifteen seconds that does nothing except keep serving while that propagates, plus an
exec-form entrypoint so the JVM gets SIGTERM, graceful shutdown in the app, and a termination grace
period longer than the sleep plus the drain.

**Q: What does a PodDisruptionBudget protect against?**
Voluntary disruptions — node drains, cluster upgrades, descheduler and autoscaler evictions. Without
one, draining a node can evict every replica if they all happen to be on it. It does not protect
against a node crashing, which is involuntary. And `minAvailable` has to be below the replica count
or you block cluster upgrades entirely, so I pair it with topology spread constraints, because three
replicas on one node is one failure domain rather than three.

**Q: What would you autoscale on?**
Not CPU, usually. An I/O-bound JVM saturates on threads and connection pools while CPU looks idle, so
a CPU-based HPA never triggers until everything is already timing out. Requests per second or
in-flight concurrency is much closer to real saturation. And `maxReplicas` comes from the fleet-wide
database connection budget rather than from optimism — scaling to fifty pods at twenty connections
each is a thousand connections against a database sized for two hundred.

**Q: Would you run your database on Kubernetes?**
It is a decision, not a default. Operators make it genuinely possible, but it adds storage, backup,
failover and version upgrades to a platform the team is often still learning. For most teams a
managed database is the better trade, and I would rather spend the operational budget on the
application. I would run it on Kubernetes where there is a platform team and a specific reason.

**Q: When is Kubernetes the wrong choice?**
When you do not have the organisational problem it solves. For a team of six with four services and
two environments, the costs are real — an API to learn, upgrades every few months, CNI, ingress,
storage and RBAC decisions, and an on-call surface that now includes the platform. A managed
container platform ships the same product with a fraction of that. I would use Kubernetes where there
are dozens of services and several teams, and I would call choosing otherwise judgement rather than
ignorance.

## Mini task

1. ⭐⭐ **Remove the `preStop` sleep** and run a rolling deploy under load. **Count the 502s.** Add the
   sleep and repeat. **Record both numbers.**
2. ⭐ Set the grace period **below** sleep + drain and **watch SIGKILL land mid-request.**
3. ⭐⭐ Deploy three replicas without spread constraints, **check whether they are on one node**, then
   drain it and watch the service disappear.
4. ⭐ Add a **PDB** and repeat the drain. Then set `minAvailable` to the full replica count and
   **confirm the drain blocks.**
5. ⭐ Add **topology spread constraints** and verify placement across zones.
6. ⭐⭐ Configure an **HPA on CPU** for an I/O-bound workload and **demonstrate that it never
   triggers** while latency collapses. Switch to a concurrency metric.
7. ⭐ Compute your **fleet connection budget** and set `maxReplicas` from it (Day 324).
8. ⭐⭐ In a test namespace, **exec into an unrelated pod and connect to your database directly.** Add
   a **NetworkPolicy** and confirm it is refused.
9. ⭐ Set `automountServiceAccountToken: false` and find what breaks.
10. ⭐ Add `runAsNonRoot`, `readOnlyRootFilesystem` and dropped capabilities. **Fix what breaks.**
11. ⭐ Write down honestly: **how many services, how many people, who is on call for the platform.**
    **Then decide whether Kubernetes is the right choice for your flagship** — and write the reason.

## 🎙️ Articulation drill

**Three minutes:** *"Every deploy produces a handful of 502s. Nobody can reproduce it."*

**⭐ The full diagnosis: endpoint removal is asynchronous, so the pod is terminating while proxies on
other nodes still route to it.** Then the fix in four parts — **`preStop` sleep, exec-form entrypoint,
graceful shutdown, and a grace period longer than sleep plus drain** — and the note that the sleep
deliberately does nothing.

**⭐ Then the second half most people miss: check the disruption budget and spread constraints**, and
**test it under load rather than assuming**, because a handful of 502s on an idle cluster is invisible
and on a busy one is an incident. **Naming the measurement is what turns this from a recited fix into
a verified one.**
