# Day 370 🏗️

**L-370** · A real pipeline — lint → test → build → scan → deploy

**Time:** 3+ hrs · **Mode:** BUILD

> **⭐ Day 368 gave the principles. Today you build the actual pipeline for your flagship, with
> timings, and treat it as a product that has users, an SLO and an owner.**
>
> The measure of success is not that it exists. It is that **PR feedback arrives in under ten
> minutes, the artefact promoted to production is the one that was tested, and a rollback has been
> timed.**

---

# Part 1 — ⭐ The shape

```yaml
⭐ on: [pull_request, push(main)]

⭐ verify        ⭐ ~2 min   format · lint · compile · unit tests · ⭐ fails fast
⭐ build         ⭐ ~2 min   ⭐⭐ ONE image, tagged by SHA, pushed. Everything downstream uses it.
⭐ ├─ integration ~3 min    Testcontainers against the built image (Day 184)
⭐ ├─ scan        ~1 min    Trivy + dependency scan (Day 363)   ⭐ parallel with integration
⭐ └─ contract    ~1 min    OpenAPI diff (Day 153)
⭐ staging       ⭐ ~2 min   ⭐ deploy the DIGEST · migrate · smoke test
⭐ production    ⭐ manual   ⭐ same digest · approval gate · canary · verify · promote
```

| ⭐ Property | ⭐ Why |
|---|---|
| ⭐⭐ **PR feedback < 10 min** | ⭐ past that, people stop waiting and start batching (Day 368) |
| ⭐⭐ **One artefact, promoted** | ⭐⭐ **staging tested exactly what production runs** |
| ⭐ Parallel where independent | scanning need not wait for integration tests |
| ⭐ **Every stage re-runnable** | no manual steps, no local dependencies |
| ⭐ Traceable to a commit | SHA in the tag, the OCI labels and `build-info` (Day 362) |

# Part 2 — ⭐ What runs where

| ⭐ Trigger | ⭐ Runs | ⭐ Why |
|---|---|---|
| ⭐ **Every PR** | lint, unit, build, integration, scan, contract | ⭐ the gate before merge |
| ⭐ **Merge to main** | ⭐ all of the above **+ deploy to staging + smoke** | staging always reflects main |
| ⭐ **Manual / tag** | production | ⭐ a human decides *when*, not *whether it works* |
| ⭐ **Nightly** | ⭐ e2e, performance, ⭐ **a rescan of deployed images** (Day 363) | too slow or too broad for a PR |
| ⭐ Weekly | ⭐ **a restore drill** (Day 284) | the only proof a backup works |

> **⭐ The nightly rescan is the one teams forget.** Nothing in your image changed, but the CVE
> database did — **so the artefact that passed on Monday can be critical on Friday**, and only a
> scheduled scan of what is actually deployed will tell you.

⚠️ **Do not run end-to-end tests on every PR.** They are slow, they are the flakiest tests you own
(Day 368), and blocking every merge on them is how a team learns to ignore red builds. **Run them
after merge and on a schedule, and treat a failure as an incident rather than a merge blocker.**

# Part 3 — ⭐⭐ Migrations, deploys, and rollback

## ⭐ Migrations run separately from the application

```
⭐ ✗ the app runs Flyway at startup
⭐   ⇒ ⭐ during a rolling deploy, several instances race to migrate
⭐   ⇒ ⭐⭐ a failed migration becomes a crash-looping deploy, not a clear error
⭐
⭐ ✓ ⭐⭐ a migration JOB runs first, once, and must succeed before any instance starts
⭐   ⇒ ⭐ Flyway's lock makes it safe, but the FAILURE MODE is what matters:
⭐      a job that fails is a red pipeline step, not a mysterious restart loop
```

| ⭐ Requirement | |
|---|---|
| ⭐⭐ **Expand/contract, always** | ⭐⭐ **old and new code run simultaneously during any rolling deploy** (Day 166) |
| ⭐ **CI checks compatibility** | ⭐ run the previous version's tests against the new schema |
| ⭐ Migrations are forward-only | ⭐⭐ **a down migration that drops a column loses data — roll forward instead** |
| Long migrations run out of band | `lock_timeout` in every migration (Day 196) |

## ⭐ Deploy, verify, and roll back automatically

```
⭐ 1. deploy the digest to a small slice (canary — Day 371)
⭐ 2. ⭐ SMOKE TEST: health, one real read, one real write, ⭐ and the deployed SHA matches
⭐ 3. ⭐⭐ WATCH for 5 minutes: error rate, p99, ⭐ SLO burn rate (Day 338)
⭐ 4. ⭐ breach ⇒ ⭐⭐ AUTOMATIC ROLLBACK to the previous digest. No human in the loop.
⭐ 5. clean ⇒ promote to 100%
```

> **⭐ Step 2's last clause is small and valuable: assert that the running instance reports the SHA
> you just deployed.** It catches a deploy that silently did nothing — an image that failed to pull,
> a config pointing at the wrong tag — **which otherwise looks exactly like a successful deploy.**

⚠️ **A rollback you have not timed is not a rollback** (Day 283). **Practise it, record the number,
and put it in the runbook** — during an incident nobody wants to discover the procedure for the first
time.

# Part 4 — ⭐ The pipeline is a product

| ⭐ It has | ⭐ Meaning |
|---|---|
| ⭐ **Users** | the team — and they will route around it if it is slow or flaky |
| ⭐⭐ **An SLO** | ⭐ **PR feedback under 10 minutes; green builds over 95%** |
| ⭐ **An owner** | ⭐ someone fixes it when it breaks, rather than everyone re-running |
| ⭐ Metrics | duration by stage, failure rate, **flake rate**, queue time |
| ⭐ **A cost** | ⭐ CI minutes are real money — cancel superseded runs (Day 369) |

```
⭐ MEASURE, weekly:
⭐   ⭐ p50 / p95 PR feedback time        ⭐ over 10 min → fix it
⭐   ⭐⭐ % of runs failing for non-code reasons  ⭐⭐ the flake rate — over 2% is a crisis
⭐   ⭐ deploy frequency, lead time, change failure rate, MTTR   (DORA — Day 368)
⭐   ⭐ CI minutes per week, and per merged PR
```

## ⭐ The improvements that pay

| ⭐ Move | ⭐ Typical effect |
|---|---|
| ⭐⭐ Cache dependencies with proper restore-keys | ⭐ minutes per run (Day 369) |
| ⭐⭐ **Registry-backed Docker layer cache** | ⭐ image builds from 3 min to under 1 |
| ⭐ Split slow tests into a parallel job | wall-clock, not total, is what people feel |
| ⭐ **Cancel superseded runs** | ⭐ pure waste removed |
| ⭐ Fail fast ordering | ⭐ a lint error found at 30 s, not 8 min |
| Run integration tests against the built image | you test the artefact, not the source |

⚠️ **Optimise wall-clock time, not total compute.** Three jobs of two minutes in parallel feel like
two minutes; **one job of six minutes feels like six**, even though the second uses less CI time.
**The team experiences latency, and latency is what changes behaviour.**

## ✅ Done when

- [ ] ⭐ **PR feedback measured and under 10 minutes** (p95)
- [ ] ⭐ **One artefact built, promoted by digest** — verified byte-identical in both environments
- [ ] ⭐ Migrations run as a separate job, **expand/contract, forward-only**
- [ ] ⭐ **Smoke tests assert the deployed SHA**
- [ ] ⭐⭐ **An automatic rollback triggered by a metric breach** — and demonstrated
- [ ] ⭐ **Rollback timed and written in the runbook**
- [ ] ⭐ Nightly image rescan and a weekly restore drill scheduled
- [ ] ⭐ **Flake rate measured**, with quarantined tests owned

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Rebuilding for production | ⭐⭐ **you shipped a different artefact than you tested** |
| ⭐ Migrations at application startup | ⭐ racing instances; a crash loop instead of a clear failure |
| ⭐ **Down migrations** | data loss — roll forward |
| ⭐ E2E tests blocking every PR | ⭐⭐ the flakiest tests as a merge gate |
| ⭐ No SHA assertion in smoke tests | ⭐ a no-op deploy looks successful |
| ⭐ **Rollback never practised** | ⭐ discovered during the incident |
| ⭐ No automatic rollback trigger | a human must notice first |
| ⭐ **Optimising total compute** | the team feels wall-clock |
| Ignoring flake rate | trust erodes silently (Day 368) |
| No nightly rescan | the CVE database moved; you did not |
| Manual steps anywhere | not re-runnable, not auditable |

## Interview questions

**Q: Walk me through your pipeline.**
Verify runs first — format, lint, compile, unit tests — because the cheapest thing that can reject a
change should run first. Then the image is built once and tagged by commit SHA, and every later stage
consumes that artefact: integration tests and scanning in parallel, then a staging deploy of that
digest with migrations as a separate job, then production promoting the same digest behind an
approval gate. PR feedback is under ten minutes at p95, and I measure that.

**Q: Why not run migrations from the application?**
Because during a rolling deploy several instances start at once and race, and more importantly the
failure mode is wrong — a failed migration becomes a crash-looping deployment instead of a clearly
red pipeline step. A separate job that must succeed first gives a precise error. Migrations are also
expand/contract and forward-only, because old and new code run simultaneously during the rollout and
a down migration that drops a column loses data.

**Q: How do you know a deploy worked?**
Smoke tests that do a real read and a real write, plus an assertion that the running instance reports
the SHA I just deployed — that last one catches a deploy that silently did nothing, like an image
that failed to pull, which otherwise looks identical to success. Then five minutes of watching error
rate, latency and SLO burn rate, with an automatic rollback to the previous digest if any of them
breaches.

**Q: What do you measure about the pipeline itself?**
It is a product with users, so it gets an SLO: PR feedback under ten minutes, green builds above
ninety-five percent. I track duration by stage, queue time, DORA metrics, and above all the flake
rate — the fraction of runs failing for non-code reasons. Above about two percent that is a crisis,
because people start reflexively re-running and the pipeline stops meaning anything.

**Q: Your builds are slow. What do you do first?**
Measure where the time goes by stage, then optimise wall-clock rather than total compute — three
two-minute parallel jobs feel like two minutes even though they cost more CI time, because the team
experiences latency. Concretely: dependency caching with proper restore-keys, a registry-backed
Docker layer cache, splitting the slow test suite into a parallel job, and cancelling superseded runs
so three pushes do not run three full pipelines.

## Mini task

1. **Build the full pipeline** for your flagship with all the stages above.
2. ⭐ **Measure p95 PR feedback time.** If it is over ten minutes, optimise until it is not, and
   record before and after.
3. ⭐⭐ **Verify the promoted digest** is byte-identical between staging and production. If it is not,
   that is your finding.
4. ⭐ Move migrations to a separate job. **Make one fail deliberately** and confirm you get a clear
   red step rather than a restart loop.
5. ⭐ Add a **SHA assertion** to smoke tests. Then deploy a tag that does not exist and **confirm the
   smoke test catches the no-op.**
6. ⭐⭐ Implement **automatic rollback on error-rate breach.** Deploy a deliberately broken build and
   **watch it roll back with no human involved. Time it.**
7. ⭐ **Time a manual rollback** and write the number in the runbook.
8. ⭐ Run the suite 50 times on unchanged code and **compute your flake rate** (Day 368).
9. Add the **nightly rescan** and a **weekly restore drill**.
10. ⭐ Record **CI minutes per merged PR** before and after adding caching and run cancellation.

## 🎙️ Articulation drill

**Three minutes:** *"A bug reaches production. Walk me back through how it got there and what should
have caught it."*

**⭐ The strong answer walks the pipeline as a series of gates and names which one should have caught
it** — a unit test, an integration test against the real database, a contract check, a smoke test, or
the canary's metric watch. **Then the honest part: if none of them could have, say so and name what
you would add.**

**⭐ And close on recovery rather than prevention:** *"it reached production, the canary's error rate
breached and it rolled back automatically in ninety seconds — that number matters more than the
number of gates, because we will always ship some bugs."* **That is Day 368's MTTR argument, made
concrete.**
