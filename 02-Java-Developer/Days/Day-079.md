# Part 1 — L-079 · The shell

## What the shell actually does

For every command line, the shell:

1. **Expands** it — variables, globs, braces, command substitution, tilde.
2. **Splits** the result into words (on `$IFS`).
3. **Forks** a child process and **`exec`s** the program (Day 029's B-03).
4. **Waits**, then records the exit status in `$?`.

That order matters, and understanding it explains most surprises. `echo *.txt` prints filenames
because **the shell** expanded the glob before `echo` ever ran — `echo` never sees a `*`. And
`rm $file` breaks on a filename with a space because word-splitting happens *after* expansion, which
is precisely why you write `rm "$file"`.

## The three standard streams

Every process starts with three descriptors (Day 004, Day 063):

```
0  stdin    input
1  stdout   normal output       ← data
2  stderr   errors and progress ← diagnostics
```

**The split exists so you can pipe data without piping diagnostics.** `curl` writes the downloaded
body to stdout and its progress bar to stderr, so `curl url | jq` works.

```bash
cmd > out.txt            # stdout to file (truncate)
cmd >> out.txt           # append
cmd 2> err.txt           # stderr to file
cmd > out.txt 2>&1       # both to the same file  ← ORDER MATTERS
cmd 2>&1 > out.txt       # ✗ stderr to the OLD stdout (terminal), stdout to the file
cmd &> out.txt           # both (bash shorthand)
cmd > /dev/null 2>&1     # discard everything
cmd < input.txt          # stdin from file
cmd <<< "a string"       # here-string
cmd <<EOF                # here-document
line one
line two
EOF
```

The `2>&1` ordering is the classic interview trap. `2>&1` means "make fd 2 a **copy of whatever fd 1
currently is**". Put it before the redirect and fd 1 is still the terminal, so stderr goes to the
terminal — the opposite of what you wanted. **Redirections are applied left to right.**

## Pipes

```bash
cat access.log | grep ERROR | awk '{print $7}' | sort | uniq -c | sort -rn | head
```

A pipe connects the left command's stdout to the right command's stdin through a kernel buffer
(typically 64 KB). **Every stage runs concurrently** — this is not sequential batch processing.
When the buffer fills, the writer blocks: that is **backpressure**, exactly Day 070's bounded queue,
implemented by the kernel.

Consequences worth knowing:

```bash
grep ERROR huge.log | head -5     # grep gets SIGPIPE and stops early — it does NOT scan the rest
set -o pipefail                   # ← without this, a pipeline's status is the LAST command's only
echo "${PIPESTATUS[@]}"           # bash: every stage's exit code
```

**Without `pipefail`, `false | true` succeeds.** In a deploy script that means a failed build piped
into a formatter reports success. This is one of the highest-value one-liners in shell scripting.

And the subshell trap:

```bash
count=0
cat file | while read line; do count=$((count+1)); done
echo $count      # 0 — the while ran in a SUBSHELL; its variables died with it

while read line; do count=$((count+1)); done < file
echo $count      # correct
```

Each pipeline stage runs in its own process, so assignments inside it are invisible afterwards. Use
input redirection or process substitution instead.

```bash
diff <(sort a.txt) <(sort b.txt)      # process substitution — each becomes a /dev/fd/N
```

## Exit codes

```bash
cmd; echo $?          # 0 = success, 1–255 = failure
```

| Code | Meaning |
|---|---|
| 0 | success — **the only success value** |
| 1 | general error |
| 2 | misuse of builtins |
| 126 | found but not executable |
| 127 | **command not found** |
| 130 | terminated by Ctrl-C (128 + SIGINT 2) |
| 137 | killed by SIGKILL (128+9) — **usually the OOM killer or a container memory limit** |
| 143 | SIGTERM (128+15) — a normal container stop |

**137 and 143 are worth memorising.** A container that exits 137 was almost certainly killed for
exceeding its memory limit, and people spend hours looking for a Java exception that does not exist
because the JVM was killed by the kernel, not by itself.

```bash
cmd1 && cmd2      # run cmd2 only if cmd1 succeeded
cmd1 || cmd2      # run cmd2 only if cmd1 FAILED
cmd1 ; cmd2       # run both regardless
cmd1 && cmd2 || echo "failed"    # ⚠️ fires if cmd2 fails too
```

## Variables and environment

```bash
name="ram"              # shell variable — this process only. NO SPACES around =
export PATH="$PATH:/opt/tools/bin"   # exported → inherited by children
echo "$name"            # quote. Always.
echo "${name}s"         # braces when the name touches other characters
unset name
env | sort              # the exported environment
```

**A child cannot change its parent's environment.** That is why `cd` must be a shell *builtin* and
not a program, and why a script that sets variables needs `source script.sh` (or `. script.sh`) to
affect your current shell rather than a subshell.

Expansion forms that repay learning:

```bash
${VAR:-default}      # use default if unset/empty (does not assign)
${VAR:=default}      # assign the default too
${VAR:?message}      # ERROR OUT if unset  ← use in scripts for required config
${VAR:+alt}          # alt only if VAR is set
${#VAR}              # length
${VAR#prefix}  ${VAR##prefix}   # strip shortest / longest prefix
${VAR%suffix}  ${VAR%%suffix}   # strip shortest / longest suffix
${VAR/old/new} ${VAR//old/new}  # replace first / all
${VAR^^} ${VAR,,}               # upper / lower
```

```bash
f="/var/log/app.2026-08-14.log"
echo "${f##*/}"     # app.2026-08-14.log   (basename)
echo "${f%/*}"      # /var/log             (dirname)
echo "${f%%.*}"     # /var/log/app
```

`${DB_PASSWORD:?DB_PASSWORD is required}` is the one to adopt: a script that fails immediately with
a clear message beats one that connects to the wrong database with an empty password.

## Quoting — the rule

| Form | Expands `$VAR` | Expands `*` | Use for |
|---|---|---|---|
| `"double"` | ✅ | ❌ | **the default** |
| `'single'` | ❌ | ❌ | literal text, regexes, awk programs |
| bare | ✅ | ✅ | almost never |

> **Quote every variable expansion unless you have a specific reason not to.**

```bash
file="my report.txt"
rm $file        # ✗ tries to remove "my" and "report.txt"
rm "$file"      # ✅

"$@"            # ✅ each argument preserved separately
"$*"            # all arguments as ONE string
$@              # ✗ re-split on whitespace
```

`"$@"` versus `$@` is the difference between a wrapper script that works and one that mangles every
argument containing a space.

## Job control and history

```bash
cmd &            # background
jobs             # list
fg %1  /  bg %1
Ctrl-Z           # suspend
nohup cmd &      # survives logout
disown -h %1
```

For anything long-running on a remote host, use `tmux` or `screen` — an SSH disconnect sends
`SIGHUP` and kills your job, and "the deploy died because my laptop slept" is a real and avoidable
incident.

```bash
Ctrl-R           # reverse search history  ← the single biggest speed gain
!!               # last command      (sudo !!)
!$               # last argument of the previous command
Ctrl-A / Ctrl-E  # start / end of line
Ctrl-W / Ctrl-U  # delete word back / to start
```

## Code to type

```bash
# 1. redirection order
ls /nonexistent > out.txt 2>&1;  cat out.txt        # error captured
ls /nonexistent 2>&1 > out2.txt; cat out2.txt       # empty — error went to the terminal

# 2. pipefail
false | true; echo "without pipefail: $?"
set -o pipefail
false | true; echo "with pipefail:    $?"
set +o pipefail

# 3. the subshell trap
printf 'a\nb\nc\n' > lines.txt
n=0; cat lines.txt | while read -r l; do n=$((n+1)); done; echo "piped:      $n"
n=0; while read -r l; do n=$((n+1)); done < lines.txt;   echo "redirected: $n"

# 4. expansion
f="/var/log/app.2026-08-14.log"
echo "base=${f##*/} dir=${f%/*} noext=${f%.log}"
echo "${MISSING:-fallback}"
( set -u; echo "${REQUIRED:?REQUIRED must be set}" ) || echo "failed as intended"

# 5. quoting
touch "a file.txt"
for x in *.txt; do echo "[$x]"; done         # correct: glob results are not re-split
v="a file.txt"; ls $v ; ls "$v"

# 6. a real pipeline
printf '%s\n' 200 404 200 500 404 404 | sort | uniq -c | sort -rn
```

Run each and predict the output first. **Sections 1, 2 and 3 are the three that catch experienced
people**, and all three appear in production scripts.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Unquoted `$var` | Breaks on spaces; glob injection |
| `2>&1` before the redirect | stderr still goes to the terminal |
| No `pipefail` | A failing pipeline reports success |
| Assignments inside a piped `while` | Lost in the subshell |
| `name = value` with spaces | Shell tries to run `name` |
| `$@` unquoted | Arguments containing spaces are split |
| Expecting a child to change the parent's env | Needs `source` |
| Parsing `ls` output | Breaks on any unusual filename |
| Long jobs over SSH without tmux | Killed by `SIGHUP` on disconnect |
| Ignoring exit code 137 | Miss the OOM kill entirely |

## Interview questions

**Q: Difference between `>` and `2>&1`, and why does order matter?**
`>` redirects stdout; `2>&1` makes stderr a duplicate of stdout's *current* target. Redirections
apply left to right, so `2>&1 > file` sends stderr to the terminal and stdout to the file.

**Q: What is a pipe, mechanically?**
A kernel buffer connecting one process's stdout to another's stdin. Both run concurrently, and the
writer blocks when the buffer is full — backpressure.

**Q: Why does `count` stay 0 after a piped `while` loop?**
Each pipeline stage runs in a subshell, so its variable changes are lost. Use redirection or process
substitution.

**Q: What does exit code 137 mean?**
128 + 9: killed by SIGKILL, which in a container almost always means the memory limit was exceeded —
the OOM killer, not an application error.

**Q: When do you use single vs double quotes?**
Double for the default, since you usually want variable expansion without globbing. Single for
literal text — regexes and awk programs — where `$` must not be interpreted.

**Q: What is `set -o pipefail` for?**
Without it a pipeline's exit status is the last command's, so a failure upstream is invisible. It
makes the pipeline fail if any stage fails.
