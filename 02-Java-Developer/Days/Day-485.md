# Part 1 — ⭐ The round: a distributed job scheduler

> **Design a system that lets services schedule jobs — one-off at a future time, or recurring on a cron
> expression — and runs them reliably at scale.**

## ⭐ 0–10 — requirements and estimation

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| ⭐ schedule one-off and recurring jobs | ⭐⭐ **execution within ~1s of the scheduled time** |
| ⭐ cancel / reschedule | ⭐⭐ **a job must not be silently skipped** |
| ⭐ retry on failure, with a DLQ | ⭐⭐ **at-least-once — say this explicitly at minute 5** |
| ⭐ visibility: what ran, when, with what outcome | ⭐ multi-tenant: one tenant cannot starve another |
| ⭐ Out of scope: job code hosting, dependency DAGs | ⭐ (both are large enough to be their own systems) |

```
⭐ 100M scheduled jobs · ⭐ peak 50,000 executions/sec ⭐⭐ (cron is spiky — everyone picks :00)
⭐ ⇒ ⭐⭐ WHAT THE NUMBERS DECIDED:
⭐   ⭐⭐ THE SPIKE IS THE PROBLEM, not the average. ⭐⭐ Midnight and the top of every hour dominate.
⭐   ⇒ ⭐ so: a queue to absorb it (Day 393), ⭐⭐ and jitter/spreading for jobs that tolerate it
⭐   ⭐ 100M rows ⇒ partitioned storage; ⭐⭐ the due-jobs query must be an INDEXED RANGE SCAN, never a table scan
```

## ⭐⭐ 10–25 — the design

```
⭐ API → ⭐ job store (partitioned by ⭐⭐ due_time bucket) → ⭐⭐ pollers → ⭐ execution queue → ⭐ workers
⭐                                                          ↘ ⭐ retry topics → ⭐ DLQ + alarm
⭐
⭐ ⭐⭐ THE CORE QUERY: SELECT jobs WHERE due_time <= now AND status = 'PENDING' LIMIT n
⭐   ⇒ ⭐⭐ index on (status, due_time) — ⭐ and bucket by minute so the scan is bounded
⭐   ⇒ ⭐⭐ MANY POLLERS RUN THIS SIMULTANEOUSLY. ⭐⭐ That is the whole problem.
```

```sql
-- ⭐⭐ THE CLAIM: the same atomic conditional update as every other round in this roadmap
UPDATE jobs
   SET status = 'CLAIMED', claimed_by = :worker, lease_until = now() + interval '5 minutes'
 WHERE id = :id
   AND (status = 'PENDING'
        OR (status = 'CLAIMED' AND lease_until < now()));   -- ⭐⭐ reclaim an expired lease
-- ⭐⭐ rowsAffected = 1 ⇒ it is yours. 0 ⇒ someone else has it. ⭐ No lock service required.
```

| ⭐⭐ Why a lease rather than a lock | |
|---|---|
| ⭐⭐ **A worker that dies mid-job must not block the job forever** | ⭐⭐ the lease expires and another worker reclaims |
| ⭐⭐ **A worker that PAUSES may resume and run it twice** | ⭐⭐ **which is why the job must be idempotent — Day 411's fencing problem** |
| ⭐ Long jobs | ⭐ heartbeat to extend the lease (`ChangeMessageVisibility`, again — Day 393) |
| ⭐ Alternative | ⭐ `SELECT ... FOR UPDATE SKIP LOCKED` — same idea, database-native |

> **⭐⭐ Say the sentence explicitly: "this is at-least-once, so the contract is that submitted jobs must
> be idempotent, and I would put that in the API documentation rather than pretend otherwise."** Exactly
> once would require the job's side effect to be transactional with the scheduler's state, **which is the
> dual-write problem, and it is not solvable across a network** (Day 407).

# Part 2 — ⭐⭐ The deep dive: the four hard cases (25–38)

| ⭐ Case | ⭐⭐ The answer |
|---|---|
| ⭐⭐ **The system was down at the job's due time** | ⭐⭐ **catch-up policy is a per-job setting**: run it late, skip it, or run once regardless of how many were missed. **Ask which — "run all 400 missed hourly jobs at once" is rarely what anyone wants** |
| ⭐⭐ **The thundering herd at :00** | ⭐⭐ a queue absorbs it; **plus optional jitter within a window for jobs that declare themselves flexible** |
| ⭐⭐ **A recurring job's next run** | ⭐⭐ **compute it after the current run completes, not before** — otherwise a long-running job schedules overlapping executions. **And decide explicitly whether overlap is allowed** |
| ⭐⭐ **One tenant floods the system** | ⭐⭐ per-tenant rate limits and **fair queuing** — a shared queue means one tenant's ten thousand jobs delay everyone's |

```
⭐⭐ THE CATCH-UP QUESTION IS THE BEST ONE IN THE ROUND, because it has no correct answer:
⭐   an hourly job, the system is down for 18 hours.
⭐   ⇒ ⭐ run all 18 now?  ⭐ run one and skip 17?  ⭐ skip all and resume?
⭐   ⇒ ⭐⭐ Every one is right for some job and catastrophic for another —
⭐     a report can skip, ⭐⭐ a billing run absolutely cannot.
⭐ ⇒ ⭐⭐ SO IT IS A PER-JOB POLICY, declared at scheduling time. ⭐ Reaching for that is the answer.
```

| ⭐ Timezones and DST — the detail that shows care | |
|---|---|
| ⭐⭐ **Store the cron with its timezone, not a UTC instant** | ⭐⭐ "2am daily in Europe/London" is not a fixed UTC time |
| ⭐⭐ **DST spring forward** | ⭐⭐ **2:30am does not exist on that day** — run it, skip it, or shift it? Ask |
| ⭐ DST fall back | ⭐⭐ **2:30am happens twice** — must not run twice |
| ⭐ The rule | ⭐ compute the next occurrence with a real timezone library, and **test both DST transitions** |

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Promising exactly-once execution** | ⭐⭐ not available — say at-least-once and require idempotency |
| ⭐ Designing for the average rate | ⭐⭐ cron is spiky; :00 dominates |
| ⭐ A table scan for due jobs | ⭐⭐ an indexed range scan on (status, due_time) |
| ⭐⭐ **A lock instead of a lease** | ⭐⭐ a dead worker blocks the job forever |
| ⭐ No lease reclamation clause | ⭐ jobs stuck in CLAIMED |
| ⭐ No heartbeat for long jobs | ⭐ the lease expires mid-execution and it runs twice |
| ⭐⭐ **No catch-up policy** | ⭐⭐ 18 hours of missed billing runs, all at once |
| ⭐ Computing the next run before execution | ⭐⭐ overlapping executions of a slow job |
| ⭐ Cron stored as a UTC instant | ⭐⭐ DST breaks it twice a year |
| ⭐ Not testing both DST transitions | ⭐ one day is missing and one happens twice |
| ⭐ A shared queue across tenants | ⭐⭐ one tenant delays everyone |
| Aggregating rounds but not reading by row | the diagnosis lives in the rows |

## Interview questions

**Q: Can you guarantee a job runs exactly once?**
No, and I would say so at minute five rather than let it become a discovered problem. Exactly-once would
require the job's side effect to be transactional with the scheduler's own state, and those are separate
systems across a network — the dual-write problem. So the contract is at-least-once with an idempotency
requirement on submitted jobs, documented in the API. A worker that pauses long enough for its lease to
expire and then resumes will run the job twice, and no amount of coordination prevents that; making the
job idempotent does.

**Q: How do multiple pollers avoid running the same job?**
An atomic conditional update: set the job to claimed with a lease expiry, where the status is pending or
the status is claimed and the lease has already expired. Rows-affected is the arbiter — one means it is
yours, zero means someone else won. It needs no lock service, the lease means a dead worker's job is
reclaimed automatically rather than stuck forever, and long jobs heartbeat to extend it.
`SELECT FOR UPDATE SKIP LOCKED` is the database-native version of the same idea. It is the same mechanism
as a parking spot claim, a seat hold and an SQS visibility timeout.

**Q: The system was down for eighteen hours. What happens to an hourly job?**
That is a policy question rather than a technical one, and reaching for that is the answer. Running all
eighteen now, running one and skipping seventeen, and skipping everything are each correct for some jobs
and catastrophic for others — a report can be skipped, a billing run absolutely cannot. So catch-up
behaviour is a per-job setting declared at scheduling time, with a sensible default and a documented
maximum backlog. It is the best question in this design because it has no universally right answer.

**Q: How do you handle cron and daylight saving?**
Store the cron expression with its timezone rather than a computed UTC instant, because "2am daily in
London" is not a fixed UTC time. Then both transitions need an explicit decision: in spring the 2:30
occurrence does not exist that day, so does it run early, late, or not at all; and in autumn it happens
twice, so it must not run twice. I compute the next occurrence with a real timezone library and I test
both transitions specifically, because those are the two days a year the scheduler is wrong and nobody
notices until a report is missing.

**Q: What did five design rounds teach you about yourself?**
That my weakest row was the deep dive — I was going deep on the part I knew best rather than the part
that was hard, which is a comfortable habit that produces a mediocre round. The fix is mechanical: ask
which direction they want, and pick the component where the interesting failure lives. The other thing
the aggregate showed is a mechanism that appeared in four of the five designs — a limited resource
claimed by an atomic conditional update and held with an expiry. Parking spot, seat hold, visibility
timeout, job lease. Recognising it in a new problem is worth more than any individual design.
