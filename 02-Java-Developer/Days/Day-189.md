# Part 1 — The structure, and what a lookup costs

```
                     ┌──── root page ────┐
                     │  ..500..  ..900.. │        ⭐ ~1 page read
                     └───┬────────┬──────┘
             ┌───────────┘        └──────────┐
    ┌─ internal ─┐                    ┌─ internal ─┐   ⭐ 1 page read
    │ 100 300 480│                    │ 950 1200   │
    └──┬─────────┘                    └────────────┘
       ▼
  ┌─ leaf ──────────────────────────┐               ⭐ 1 page read
  │ 101→ctid  102→ctid  103→ctid ...│──► next leaf  ⭐ leaves are linked — range scans are cheap
  └─────────────────────────────────┘
       │
       ▼ ⭐ then a HEAP fetch to get the row — one MORE page read
```

**⭐ The number that matters: a B-tree on 100 million rows is about 4 levels deep.** Each level is one
8KB page read, so finding a row is ~4 page reads plus one heap fetch — five, against 12 million pages
for a sequential scan. **That ratio, not "indexes are fast", is the actual argument.**

**⭐ And the heap fetch is why index-only scans matter.** If every column the query needs is *in the
index*, PostgreSQL can skip the heap entirely:

```sql
create index ix_orders_customer_total on orders (customer_id) include (total);   -- ⭐ INCLUDE
select total from orders where customer_id = 42;    -- ⭐ index-only scan, no heap read
```

`INCLUDE` stores extra columns in the leaf without making them part of the search key — D-11's
covering index, with PostgreSQL's syntax.

⚠️ **Index-only scans still consult the visibility map** (Day 186's MVCC: the index does not know
whether a tuple is visible to you). **If a table is not vacuumed, index-only scans degrade into heap
fetches anyway** — which is a direct, surprising link from Day 194's vacuum to today's performance.

# Part 2 — ⭐⭐ The eight reasons your index is ignored

**Run `EXPLAIN` (Day 191) and see `Seq Scan` where you expected `Index Scan`. Here is the full list.**

### ⭐ 1. A function on the indexed column

```sql
create index ix_users_email on users (email);
select * from users where lower(email) = 'a@b.com';        -- ❌ Seq Scan
```

**The index stores `email`, the query asks about `lower(email)` — a different value.** The planner
cannot know they relate.

```sql
create index ix_users_email_lower on users (lower(email));  -- ⭐ expression index
```

**⭐ This is the most common cause in real applications**, and it appears in several disguises:

```sql
where date(created_at) = '2026-08-14'          -- ❌ function on the column
where created_at >= '2026-08-14'                -- ⭐ and < the next day — SARGABLE
  and created_at <  '2026-08-15'

where cast(id as text) = '42'                   -- ❌
where extract(year from placed_at) = 2026       -- ❌
where placed_at >= '2026-01-01' and placed_at < '2027-01-01'   -- ⭐
```

**The word is *sargable* — Search ARGument ABLE.** ⭐ **The rule: keep the indexed column bare on
one side of the comparison.**

### ⭐ 2. A type mismatch

```sql
-- id is bigint
where id = '42'                    -- ✅ fine, literal is coerced
where varchar_col = 42             -- ⚠️ may force a cast on the COLUMN → no index
```

**A cast applied to the column is case 1 in disguise.** This bites hardest with JDBC when the
parameter type does not match the column type — `setString` against a `bigint`, for instance.

### ⭐ 3. Leading wildcard

```sql
where name like '%smith%'          -- ❌ a B-tree is ordered by prefix — useless
where name like 'smith%'           -- ⭐ prefix search DOES use the index
```

Day 163b flagged this as a DoS vector. The fix is a **trigram index** (Day 190) or full-text search
(Day 199).

### ⭐ 4. Low selectivity — the index is *correctly* ignored

```sql
where status = 'ACTIVE'            -- ⭐ if 95% of rows are ACTIVE
```

**⭐ Reading 95% of a table via an index is slower than a sequential scan**, because the index adds
random I/O on top of reading nearly everything anyway. **The planner is right and your index is not
useful for this query.**

The fix is not to force the index — it is a **partial index** (Day 190):

```sql
create index ix_orders_pending on orders (placed_at) where status = 'PENDING';   -- ⭐ 0.1% of rows
```

### ⭐ 5. The table is small

Under a few hundred pages, a sequential scan is simply faster. **The planner is correct; ignore it.**
This is why testing index behaviour on 100 rows tells you nothing — a trap that catches people
constantly.

### ⭐ 6. Stale statistics

```sql
analyze orders;                                     -- ⭐ recompute
select last_analyze, last_autoanalyze, n_live_tup, n_dead_tup
from pg_stat_user_tables where relname = 'orders';  -- ⭐ when did it last run?
```

**⭐ The planner chooses by estimated cost, and the estimate comes from statistics.** After a bulk
load, statistics describe the old table — so the planner may believe a 50-million-row table has 1,000
rows and pick a plan that is catastrophic. **After any bulk load, `ANALYZE`.** Day 191 shows how to
spot this in a plan.

### ⭐ 7. Wrong column order in a composite index

**Day 190's subject, and it is the second most common cause after case 1.** An index on
`(status, created_at)` cannot serve a query filtering only on `created_at`.

### ⭐ 8. `OR` across different columns

```sql
where email = :e or phone = :p     -- ⚠️ often cannot use either index efficiently
```

PostgreSQL may manage a `BitmapOr` if both columns are indexed, but frequently does not. **A `UNION
ALL` of two indexed queries is often dramatically faster** — an ugly rewrite with a real payoff.

# Part 3 — ⭐ Reading the evidence, not guessing

```sql
explain (analyze, buffers) select * from orders where customer_id = 42;
```

```
Index Scan using ix_orders_customer on orders  (cost=0.43..8.45 rows=1 width=64)
                                               (actual time=0.021..0.023 rows=1 loops=1)
  Index Cond: (customer_id = 42)
  Buffers: shared hit=4
```

**⭐ The single most diagnostic thing in a plan is `rows` estimated versus `rows` actual.** An
estimate of 1 against an actual of 400,000 means the planner was working from bad information — case
6 — and **every downstream decision in that plan is built on the wrong number.** Day 191 covers this
properly.

## Is the index being used at all?

```sql
select relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
from pg_stat_user_indexes
order by idx_scan asc;                              -- ⭐ zero-scan indexes at the top
```

**⭐ Run this on any real database and you will find indexes with `idx_scan = 0`** — created for a
query that changed, or copied from a tutorial. **They are not free:**

| Cost of an unused index | Detail |
|---|---|
| ⭐ **Every `INSERT`/`UPDATE`/`DELETE` maintains it** | Day 186 — write amplification |
| Disk space | often larger than you expect |
| ⭐ **Memory** | it competes for `shared_buffers` |
| Vacuum time | more to clean (Day 194) |
| ⭐ **Planning time** | more paths for the planner to consider |

**Drop them** — after confirming across a full business cycle, since a monthly report's index looks
unused for 29 days.

## ⭐ Building indexes on a live table

```sql
create index concurrently ix_orders_status on orders (status);    -- ⭐ Day 166
```

Without `concurrently`, `CREATE INDEX` blocks **every write** for the duration — minutes on a large
table. With it, two table scans and the possibility of an **invalid index** if it fails, which must
then be dropped manually:

```sql
select indexrelid::regclass from pg_index where not indisvalid;   -- ⭐ find the wreckage
```

# Part 4 — Where the practice differs from the theory

## ⭐ Indexes are not free on writes

An `INSERT` into a table with eight indexes does **nine** write operations. Day 186's no-in-place-update
rule makes it worse: an `UPDATE` that moves the tuple to a new page must update every index — unless
it qualifies as a **HOT update** (same page, no indexed column changed).

**⭐ The practical rule: index for the queries you actually run, and delete the rest.** "Add an index
just in case" is a permanent tax on every write.

```sql
alter table orders set (fillfactor = 85);     -- ⭐ leave room on each page for HOT updates
```

## The foreign key index PostgreSQL does not create

**⭐ PostgreSQL indexes the primary key automatically. It does *not* index foreign keys.** So:

- `where customer_id = ?` — the most common query in your application — has no index;
- ⭐ **deleting a parent row scans the child table** to check the constraint, and takes a lock while
  it does.

**Index every foreign key you filter or join on.** This one omission is behind a surprising share of
slow application queries.

## Index size, and when it stops fitting

```sql
select indexrelname, pg_size_pretty(pg_relation_size(indexrelid))
from pg_stat_user_indexes where relname = 'orders' order by 2 desc;
```

**⭐ An index that no longer fits in `shared_buffers` starts hitting disk on every level descent**, and
performance falls off a cliff rather than degrading smoothly. This is when partial indexes (Day 190)
stop being an optimisation and become necessary.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ A function on the indexed column | the most common cause of an ignored index |
| `date(created_at) = ...` | use a half-open range instead |
| Type mismatch forcing a cast on the column | case 1 in disguise |
| Leading wildcard `like` | B-trees are prefix-ordered |
| Indexing a low-selectivity column | the planner is right to ignore it; use a partial index |
| Testing index behaviour on 100 rows | small tables always seq-scan |
| ⭐ No `ANALYZE` after a bulk load | the planner works from a fiction |
| Forcing an index because "it should be faster" | the planner is usually right; find out *why* |
| ⭐ Not indexing foreign keys | slow joins, and parent deletes scan the child |
| Keeping unused indexes | write amplification, memory, planning time |
| `CREATE INDEX` without `concurrently` | writes blocked for minutes |
| Leaving an invalid index after a failed build | never used, still maintained |
| "Add an index just in case" | a permanent tax on writes |

## Interview questions

**Q: You added an index and the query is still slow. Walk me through diagnosing it.**
`EXPLAIN (ANALYZE, BUFFERS)` first. If it is a sequential scan, the causes in likelihood order are: a
function or cast applied to the column making the predicate non-sargable; wrong leading column in a
composite index; low selectivity, where the planner is correct and I need a partial index; stale
statistics after a bulk load; or the table being too small to matter. The estimated-versus-actual row
count usually tells me which.

**Q: What is sargability?**
Whether a predicate can use an index. The column has to appear bare on one side — `where
date(created_at) = x` cannot use an index on `created_at`, but `where created_at >= x and created_at
< y` can. Same result, completely different plan.

**Q: What does an index cost?**
Write amplification — every insert and update maintains it, and because PostgreSQL never updates in
place, a non-HOT update touches every index on the table. Plus disk, buffer memory it competes for,
vacuum time, and planning time. So I index for queries I actually run and drop the ones with zero
scans.

**Q: What does PostgreSQL not index automatically?**
Foreign keys. The primary key gets an index, the foreign key does not — so the most common query in
an application has no index, and deleting a parent row scans the child table to check the constraint.

**Q: What is an index-only scan, and when does it not work?**
When the index contains every column the query needs, the heap fetch is skipped. But visibility still
has to be checked against the visibility map, so on a poorly vacuumed table it degrades back into
heap fetches.

## Mini task

**Use one million rows for all of these. Small tables prove nothing.**

1. Generate 1M orders. `EXPLAIN ANALYZE` a query on an unindexed column. Add the index. Compare
   times and `Buffers`.
2. **Reproduce all eight ignore-cases**, one at a time, and confirm each with `EXPLAIN`. Fix each.
3. Write `where date(placed_at) = '2026-08-14'`. Then the range version. **Compare the plans.**
4. Build an expression index on `lower(email)` and confirm the plan changes.
5. Add a covering index with `INCLUDE`. Confirm `Index Only Scan` and `Heap Fetches: 0`.
6. Delete 50% of the rows, do **not** vacuum, and re-run the index-only scan. **Watch `Heap Fetches`
   climb.** Then `vacuum` and re-run.
7. Time 100k inserts on a table with 0, 3 and 8 indexes. **Plot it.**
8. Create a foreign key with no index. Time deleting a parent row. Add the index and repeat.
9. `CREATE INDEX` without `concurrently` on the 1M-row table while running concurrent inserts.
   **Watch them block.** Then with `concurrently`.
10. Query `pg_stat_user_indexes` for `idx_scan = 0` and justify every index you have.

## 🎙️ Articulation drill

Three minutes: **"An index exists and the query is still slow. What do you do?"**

Do not list causes — describe a process. `EXPLAIN (ANALYZE, BUFFERS)`, then check estimated versus
actual rows first, because a large divergence means every later decision in the plan was made on bad
information. Then walk the causes in likelihood order, and be explicit that two of them mean the
planner is *right*: low selectivity and a small table. Close on the reframe that separates people —
the goal is not to make PostgreSQL use your index, it is to find out why it decided not to.
