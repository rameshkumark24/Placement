# Part 1 — ⭐ The four legitimate reasons to denormalize

**Normalization's guarantee is that a fact is stored once, so it cannot disagree with itself.**
Denormalizing gives that up, so it needs a justification stronger than "joins are slow" — which is
usually false on an indexed join of reasonable size.

### ⭐ 1. A historical value that must not change

```sql
create table order_items (
    order_id    bigint not null references orders(id),
    product_id  bigint not null references products(id),
    quantity    integer not null check (quantity > 0),
    unit_price  numeric(19,4) not null,     -- ⭐ COPIED from products at order time
    product_name text not null              -- ⭐ COPIED — the name at the time of sale
);
```

**⭐ This is not denormalization at all — it is a different fact.** `products.price` is *the current
price*; `order_items.unit_price` is *the price this customer paid*. Joining to `products` for a
receipt means last year's invoices silently change when someone edits a price, which is a legal and
accounting problem, not a performance one.

**The test: does this value describe the entity, or does it describe an event?** Event values are
copied, always.

### 2. A counter that would be an expensive aggregate

```sql
alter table posts add column comment_count integer not null default 0;
```

**Justified when the count is read constantly and `count(*)` is expensive.** The cost is that it can
drift, so it needs either a trigger or a periodic reconciliation job — and **the reconciliation job
is not optional**, because it will drift eventually.

⭐ **Try the alternatives first**: an index-only `count(*)` on a well-indexed foreign key is often
fast enough, and a materialized view (Part 3) is cheaper to keep honest.

### 3. A read model for a genuinely different access pattern

Reports, dashboards and search have different shapes from transactional writes. **Solve it with a
materialized view or a separate read table**, not by compromising the write schema.

### 4. Wide rows on an append-only table

An events or audit table nobody joins to has no integrity to protect. Flat is fine.

# Part 2 — The patterns normalization has no opinion on

## ⭐ Soft deletes — and the honest case against them

```sql
alter table users add column deleted_at timestamptz;
```

**⭐ The costs are real and people underestimate them:**

- **Every query needs `where deleted_at is null`** — and the one that forgets is a bug that shows
  deleted data to users. This is the same shape as Day 176's missing tenant filter.
- **Unique constraints break** — Day 187's partial index is mandatory, not optional.
- **Foreign keys stop protecting you.** A live order can reference a "deleted" customer, so the
  constraint is satisfied and the data is wrong.
- **The table grows forever.**

| Alternative | When |
|---|---|
| ⭐ **Hard delete + an archive table** | ⭐ **usually better.** Live tables stay clean; history is complete |
| `status` column with a real state machine | when "deleted" is one of several states — clearer intent |
| Soft delete | ⭐ when undelete is a genuine product feature |

**⭐ If you do use soft deletes, use a view:**

```sql
create view active_users as select * from users where deleted_at is null;   -- ⭐ default to safe
```

Then application code queries `active_users` and the filter cannot be forgotten. Same principle as
Day 176: **make the safe thing the default, not the thing you must remember.**

## Audit history — three shapes

| Approach | Verdict |
|---|---|
| `created_at`/`updated_at`/`by` columns | ⭐ minimum viable, but only the latest state (Day 165) |
| A shadow `_history` table via trigger | ⭐ **complete — a trigger cannot be bypassed by a bulk update** |
| ⭐ **An append-only event table** | ⭐ **best when the business narrative matters** (Day 165) |

**⭐ The trigger version's advantage is precisely Day 162's hole**: `@PreUpdate` and Envers are
listener-based and bulk SQL bypasses them. A database trigger does not care who wrote the row.

```sql
create trigger orders_audit after insert or update or delete on orders
    for each row execute function record_history();     -- ⭐ catches every writer
```

## ⭐ Hierarchies — four options, and the two that are usually right

| Model | Read a subtree | Move a subtree | Verdict |
|---|---|---|---|
| **Adjacency list** (`parent_id`) | ⭐ recursive CTE (D-10) | ⭐ one update | ⭐ **the default** |
| **Path enumeration** (`'/1/7/22/'`) | ⭐ one `like` query | rewrite the subtree | ⭐ good for shallow, read-heavy trees |
| Nested sets | one range query | ⭐ ❌ rewrites half the table | avoid |
| Closure table | one join | O(depth) rows per node | deep trees with heavy subtree reads |

```sql
with recursive subtree as (                                   -- ⭐ D-10, in production
    select id, parent_id, name, 1 as depth from categories where id = :root
    union all
    select c.id, c.parent_id, c.name, s.depth + 1
    from categories c join subtree s on c.parent_id = s.id
)
select * from subtree;
```

**⭐ Adjacency list plus a recursive CTE is the right answer for almost every application tree**, and
`ltree` is PostgreSQL's built-in path type if you want indexed path queries. Nested sets look elegant
in articles and are miserable in production because every insert renumbers.

## Multi-tenancy in the schema — Day 176, from below

```sql
tenant_id bigint not null references tenants(id),
...
create index ix_orders_tenant_placed on orders (tenant_id, placed_at desc);   -- ⭐ tenant_id FIRST
```

**⭐ `tenant_id` leads every composite index**, because every query filters on it (Day 190's
leftmost-prefix rule). And RLS (Day 176) sits on top — the schema decision and the security control
are the same decision viewed from two layers.

## EAV — and why to resist it

```sql
-- ❌ the entity-attribute-value table
create table attributes (entity_id bigint, key text, value text);
```

**You have given up types, constraints, indexes and readable queries** to avoid writing a migration.
Every query becomes a self-join per attribute.

**⭐ Use `jsonb` instead** (Day 198): typed enough, indexable with GIN, and queryable. **Or just add
the column** — a migration is cheap (Day 166) and a typed column is worth far more than the migration
costs.

# Part 3 — Views, materialized views, and generated columns

```sql
-- ⭐ Materialized view: computed once, stored, refreshed on demand
create materialized view daily_revenue as
select date_trunc('day', placed_at) as day, sum(total) as revenue, count(*) as orders
from orders where status <> 'CANCELLED'
group by 1;

create unique index on daily_revenue (day);        -- ⭐⭐ REQUIRED for concurrent refresh

refresh materialized view concurrently daily_revenue;   -- ⭐ does not block readers
```

**⭐ `concurrently` requires a unique index and it is the difference between a usable materialized
view and one that locks your dashboard during every refresh.** Without it, `refresh` takes an
`ACCESS EXCLUSIVE` lock and every reader blocks.

**The honest trade:** a materialized view is stale between refreshes. That is fine for a daily
revenue chart and wrong for a current account balance. **Pick the refresh interval from the staleness
the consumer can tolerate** — the same reasoning as Day 168's cache TTLs.

```sql
-- ⭐ Generated column: always correct, computed on write, indexable
alter table users add column email_lower text generated always as (lower(email)) stored;
create index on users (email_lower);
```

**Generated columns cannot drift**, because the database computes them. Excellent for normalized
search keys, extracted `jsonb` fields (Day 198) and derived flags — anywhere you would otherwise be
tempted to maintain a duplicate value in application code.

## ⭐ Part 4 — The design review checklist

Run this against any schema before it ships.

| # | Question |
|---|---|
| 1 | Is every table in **3NF**, and is each deviation deliberate and documented? |
| 2 | ⭐ Does every **event** copy the values it depends on rather than joining for them? |
| 3 | Is there a **foreign key** for every relationship, with a deliberate `on delete`? |
| 4 | ⭐ Does a **check constraint** encode every state-machine invariant? |
| 5 | Is every column `not null` unless absence is meaningful? |
| 6 | ⭐ Is every timestamp `timestamptz`, and every money value `numeric`? |
| 7 | ⭐ Does every query pattern have an index, with the **leading column** correct? (Day 190) |
| 8 | If soft-deleting: **partial unique indexes and a view**? |
| 9 | ⭐ Is `tenant_id` first in every composite index, with RLS on? |
| 10 | Is anything unbounded — a growing array, an unpartitioned events table? (Day 200) |
| 11 | ⭐ Can this schema be **migrated with expand/contract**? (Day 166) |
| 12 | Would the *write* path and the *report* path prefer different shapes — and if so, is the report a materialized view? |

**⭐ Item 11 is the one people never ask at design time**, and it is when it is cheapest to fix. A
column that will obviously need splitting, or a type that will obviously need widening, is far easier
to get right before there are 200 million rows in it.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Denormalizing "because joins are slow" | usually false on an indexed join; you gave up consistency for nothing |
| ⭐ Joining to `products` for a historical price | last year's invoices change when a price is edited |
| Counters with no reconciliation job | drift is certain, not possible |
| ⭐ Soft deletes without partial unique indexes | emails can never be reused |
| Soft deletes without a view | one forgotten filter shows deleted data |
| Relying on FKs with soft deletes | live rows reference "deleted" parents |
| Audit via application listeners only | bulk SQL bypasses it (Day 162) |
| Nested sets | every insert renumbers half the table |
| EAV | no types, no constraints, unreadable queries |
| Materialized view without a unique index | `refresh` blocks every reader |
| ⭐ `tenant_id` not first in composite indexes | every tenant-scoped query loses the index |
| Maintaining a derived value in application code | use a generated column |

## Interview questions

**Q: When do you denormalize?**
Four cases. A value that describes an *event* rather than an entity — a price paid is not the current
price, so it is copied, and that is not really denormalization. An expensive counter read constantly,
with a reconciliation job because it will drift. A genuinely different read pattern, solved with a
materialized view rather than by compromising the write schema. And append-only tables with no
integrity to protect.

**Q: Soft deletes — yes or no?**
Usually no. They break unique constraints unless you use partial indexes, they neuter foreign keys
because live rows can reference deleted parents, they grow forever, and every query that forgets the
filter is a data-exposure bug. I prefer a hard delete with an archive table, unless undelete is a
real product feature — and if I do soft-delete, I query through a view so the filter cannot be
forgotten.

**Q: How do you model a category tree?**
Adjacency list with a recursive CTE for almost everything — one column, cheap moves, and PostgreSQL
handles the recursion. Path enumeration or `ltree` for shallow read-heavy trees. Not nested sets:
reads are elegant and every insert renumbers half the table.

**Q: How do you keep a derived value correct?**
A generated column where the database computes it, so it cannot drift. A materialized view where the
computation is an aggregate, refreshed concurrently with a unique index so it does not block readers.
Application-maintained duplicates are the option I avoid, because they drift silently.

1. Design an e-commerce schema: customers, products, orders, order_items, addresses. Apply all 12

   three times** and compare readability.

   Day 162's listeners would not have.

## 🎙️ Articulation drill

Two minutes: **"How do you approach schema design?"**

Normalize by default, because the guarantee is that a fact cannot disagree with itself — then name
the deviations you allow and why. Lead with the event-versus-entity distinction, since copying a paid
price into the order line is the case people misclassify as denormalization. Constraints encoding
state-machine invariants. Indexes designed alongside the queries, with the tenant column leading.
Close on the question nobody asks at design time: can this schema be changed with expand/contract
later — because the answer is cheap now and expensive at 200 million rows.
