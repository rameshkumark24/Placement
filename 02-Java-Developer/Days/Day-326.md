# Day 326 ⭐

**L-326** · ⭐ Caching at scale — the four failure modes and consistent hashing

**Time:** 3 hrs · **Mode:** NEW

> **⭐ A cache is the highest-leverage component in any system and the one that fails in the most
> interesting ways.**
>
> Day 206 covered patterns and eviction on one Redis instance. Today is the distributed version:
> **what breaks when the cache is a cluster, why `hash(key) % N` is a catastrophe, and the four
> failure modes every interviewer probes.**

---

# Part 1 — ⭐ The hierarchy, and where to cache

```
⭐ Browser        ── free, but you cannot invalidate it. TTL carefully.
⭐ CDN edge       ── ⭐ absorbs the most traffic for the least money (Day 327)
⭐ API gateway    ── shared, coarse-grained
⭐ In-process     ── ⭐ fastest (nanoseconds), ⭐ but N copies that can disagree (Day 324)
⭐ Distributed    ── ⭐ Redis/Memcached — one truth, ~0.5 ms away
⭐ Database       ── the buffer pool you already have (Day 186)
```

> **⭐ The rule: cache as close to the user as the correctness allows.** Each layer up is an order of
> magnitude cheaper and faster — **and an order of magnitude harder to invalidate.**

| ⭐ Ask before adding a cache | |
|---|---|
| ⭐ **What is the read:write ratio?** | ⭐ below ~10:1 a cache mostly adds invalidation work |
| ⭐ **How stale can this be?** | ⭐ **the answer is almost never "not at all"** — get a number |
| ⭐ **What is the hit rate going to be?** | ⭐ **below ~80% you added a hop for little gain** |
| ⭐ What happens when it is empty? | ⭐ **if the answer is "we fall over", the cache is load-bearing** |

⚠️ **A load-bearing cache is an availability risk, not an optimisation.** If the database cannot serve
the traffic at a 0% hit rate, **a cache restart is an outage** — and that must be a stated, accepted
decision with a warm-up plan, not a surprise.

# Part 2 — ⭐⭐ The four failure modes

## ⭐ 1. Thundering herd / stampede

```
⭐ A hot key expires. 5,000 concurrent requests miss simultaneously.
⭐ ⇒ 5,000 identical database queries, and the database dies.
```

| ⭐ Fix | ⭐ Note |
|---|---|
| ⭐ **Per-key in-flight future** | ⭐ one loader, the rest await it (Day 313) |
| ⭐ **A short lock with a "someone is loading" marker** | across processes — cheap and effective |
| ⭐⭐ **Probabilistic early expiry** | ⭐⭐ **refresh with rising probability as the TTL approaches — no stampede ever forms** |
| Never expire; refresh in background | best hit rate; risks unbounded staleness on failure |

## ⭐ 2. Hot key

```
⭐ One celebrity's profile is 40% of all reads.
⭐ ⇒ ⭐ ONE cache node takes 40% of the traffic, and consistent hashing does NOT help —
⭐    the key hashes to one place by definition.
```

| ⭐ Fix | ⭐ Note |
|---|---|
| ⭐ **Local cache in front of the distributed one** | ⭐ **the standard answer — a 1-second in-process TTL removes almost all of it** |
| ⭐ Key splitting — `celeb:1#0..9`, read one at random | ⭐ N-way replication of one key |
| ⭐ Client-side request coalescing | fewer round trips |

> **⭐ Say it explicitly: consistent hashing solves rebalancing, not hotspots.** Candidates routinely
> offer it as the answer to a hot key, and it is precisely the wrong tool.

## ⭐ 3. Cache penetration — keys that do not exist

```
⭐ An attacker requests /user/999999999 repeatedly.
⭐ ⇒ Always a miss. Always hits the database. ⭐ The cache is bypassed by design.
```

| ⭐ Fix | ⭐ Note |
|---|---|
| ⭐ **Cache the negative result** | ⭐ a short TTL — 30 s is usually enough |
| ⭐ **A Bloom filter of existing keys** | ⭐⭐ **definitively answers "no" in memory; false positives only ever cost a lookup** |
| Validate the key format first | rejects obvious nonsense at the edge |

## ⭐ 4. Cache avalanche — mass simultaneous expiry

```
⭐ Warm 100,000 keys at deploy with the same 1-hour TTL.
⭐ ⇒ ⭐ One hour later they ALL expire in the same second.
```

| ⭐ Fix | ⭐ Note |
|---|---|
| ⭐⭐ **Jitter every TTL** | ⭐⭐ **`ttl = base + random(0, base/4)` — one line, removes the whole class** |
| Stagger warm-up | |
| ⭐ And the other avalanche: **the cache cluster restarts** | ⭐ **a request-rate limit to the database as a backstop** |

> **⭐ TTL jitter is the cheapest reliability win in this entire stage** — one line of code, and it
> eliminates a failure mode that takes down real systems.

# Part 3 — ⭐⭐ Consistent hashing

## ⭐ Why modulo fails

```
⭐ 4 cache nodes. key → hash(key) % 4.
⭐ Add a fifth node → hash(key) % 5.

⭐ Key "user:1234"  hash 9,999,999
⭐   % 4 = 3        ⭐ node 3
⭐   % 5 = 4        ⭐ node 4      ⇒ ⭐ MOVED

⭐⭐ Fraction of keys that move: (N-1)/N ≈ 80% at N=5.
⭐⭐ ⇒ Adding one node invalidates almost the entire cache at once, and every miss hits the database.
```

> **⭐ The failure is not "some remapping". It is that a routine capacity increase becomes a
> full-cache-miss event — which is an outage on any load-bearing cache.**

## ⭐ The ring

```
⭐ Hash space as a circle, 0 → 2^32.
⭐ Place NODES on it by hash(node). Place KEYS on it by hash(key).
⭐ A key belongs to the FIRST node CLOCKWISE from it.

        0 ─────────────────────────► 2^32
        │    A          B      C        │
        │  k1 k2      k3     k4  k5     │
        ⭐  k1,k2 → B    k3 → C    k4,k5 → A (wrapping)

⭐ Add node D between A and B:  ⭐ only keys between A and D move. ⭐ ~1/N of them.
⭐ Remove a node:               ⭐ only its keys move, to the next node clockwise.
```

| ⭐ Property | ⭐ Value |
|---|---|
| ⭐ **Keys moved when adding a node** | ⭐⭐ **~1/N instead of ~(N−1)/N** |
| Lookup cost | O(log N) — a sorted structure over the ring |
| ⭐ Who is affected | ⭐ **only the neighbouring node's range** |

## ⭐⭐ Virtual nodes — the part that is always asked

**⭐ With one point per node the ring is badly uneven**, because random placement is lumpy: **three
nodes can easily end up owning 55% / 30% / 15%.** And removing a node dumps its *entire* range onto
one neighbour.

```java
// ⭐ Each physical node gets ~150 points on the ring
for (int i = 0; i < 150; i++)
    ring.put(hash(node.id() + "#" + i), node);   // ⭐ TreeMap<Long, Node>

Node nodeFor(String key) {
    var entry = ring.ceilingEntry(hash(key));    // ⭐ first clockwise
    return entry != null ? entry.getValue() : ring.firstEntry().getValue();  // ⭐ wrap
}
```

| ⭐ Virtual nodes | ⭐ Load imbalance |
|---|---|
| 1 | ⭐ **very poor — often 2–3× between nodes** |
| 10 | noticeable |
| ⭐ **100–200** | ⭐⭐ **within a few percent — the standard choice** |

**⭐ Two more benefits worth naming:** removing a node spreads its keys across **many** neighbours
rather than one, and **weighting is free** — a machine with twice the memory gets twice the virtual
nodes.

⚠️ **Rendezvous (highest random weight) hashing is the simpler alternative:** for each key, compute
`hash(key, node)` for every node and pick the maximum. **No ring, no virtual nodes, naturally
balanced, trivially weighted** — at O(N) per lookup, which is fine for tens of nodes. **Mentioning it
signals you know consistent hashing is not the only answer.**

**⭐ Where it is actually used:** Memcached client libraries, Redis Cluster (via 16,384 fixed hash
slots, which is the pre-split idea from Day 329), Dynamo/Cassandra, CDN edge selection, and
consistent-hash load balancing (Day 325).

# Part 4 — ⭐ Invalidation, and the two hard cases

| Strategy | ⭐ Trade |
|---|---|
| ⭐ **TTL only** | ⭐ **simplest, always correct eventually — bounded staleness** |
| ⭐ Explicit delete on write | ⭐ fresher; **fails if the delete is lost** — so keep a TTL as a backstop |
| ⭐ **Versioned keys** — `user:123:v7` | ⭐⭐ **no invalidation at all; the old key just ages out** |
| Write-through | cache and store updated together; only helps if re-read soon |

⚠️ **Two writers, one cache — the classic race:**

```
⭐ A reads DB (v1) → B writes DB (v2) → B deletes cache → A writes v1 into cache
⭐ ⇒ ⭐⭐ The cache now holds v1 FOREVER (until TTL).
```

**⭐ Fixes:** delete after the write **and again after a short delay** (delayed double delete),
**versioned keys** (the old version is simply never read again), or a **short TTL as a backstop**.
**Always keep a TTL — an invalidation-only cache has no recovery from a lost delete.**

> **⭐ And the deeper point to state: a cache is a second copy of your data, so it introduces a
> consistency problem you did not previously have.** Choosing a staleness budget explicitly is the
> engineering decision; hoping deletes always arrive is not.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ `hash(key) % N` | ⭐⭐ **adding a node invalidates ~80% of the cache** |
| ⭐ Consistent hashing with no virtual nodes | ⭐ 2–3× load imbalance; removal dumps on one neighbour |
| ⭐ Offering consistent hashing for a hot key | ⭐ **wrong tool — the key hashes to one node by definition** |
| ⭐ **Identical TTLs everywhere** | ⭐⭐ **synchronised expiry — avalanche** |
| ⭐ No negative caching | ⭐ missing keys bypass the cache entirely |
| No stampede protection on hot keys | thousands of identical queries |
| ⭐ Invalidation with no TTL backstop | ⭐ **one lost delete = permanently stale** |
| ⭐ Ignoring the read/write interleaving race | a stale value pinned until TTL |
| ⭐ **A cache the database cannot survive without** | ⭐ **a restart becomes an outage** |
| In-process caches with correctness assumptions | N instances disagree (Day 324) |
| Caching below ~10:1 read:write | invalidation costs more than it saves |

## Interview questions

**Q: Why not `hash(key) % N`?**
Because changing N remaps almost everything — going from four nodes to five moves about eighty
percent of the keys. That is not a rebalancing inconvenience, it is a full cache miss event, and on a
load-bearing cache it takes the database down. Consistent hashing moves roughly one over N instead,
and only the neighbouring range is affected.

**Q: What are virtual nodes and why do you need them?**
Each physical node is placed at many points on the ring — typically a hundred or two — because random
placement with one point each is lumpy, giving two or three times the load imbalance. Virtual nodes
also mean a removed node's keys spread across many neighbours instead of landing entirely on one, and
weighting comes free: a bigger machine gets more points.

**Q: One key is forty percent of your traffic. What do you do?**
Not consistent hashing — that key hashes to one node by definition, so it does not help at all. A
small in-process cache in front of the distributed one solves it: even a one-second TTL removes
almost all of the traffic for a key that hot. If I need more, I split the key into N replicas and
read one at random.

**Q: Give me the cache failure modes.**
Stampede — a hot key expires and thousands of requests miss at once, fixed by single-flight loading
or probabilistic early refresh. Hot key — one key dominates, fixed with a local cache or key
splitting. Penetration — requests for keys that do not exist bypass the cache, fixed by caching
negatives or a Bloom filter. Avalanche — everything expires simultaneously because it was warmed
together with the same TTL, fixed by jittering every TTL, which is one line of code and the cheapest
reliability win available.

**Q: How do you invalidate?**
TTL always, as the backstop, plus explicit deletes on write for freshness. Better still, versioned
keys, so there is no invalidation at all — the new version is a new key and the old one ages out.
That also sidesteps the classic race where a reader loads an old value, a writer updates and deletes,
and the reader then writes the stale value back, pinning it until the TTL. An invalidation-only cache
has no recovery from a single lost delete.

## 🎙️ Articulation drill

**Three minutes:** *"Your cache hit rate just dropped from 95% to 40% and the database is
struggling. What happened?"*

**⭐ The strong answer works through causes in likelihood order**: a cache node was added or lost
(and if it is modulo-hashed, that alone explains everything) · mass expiry from synchronised TTLs ·
a deploy that changed the key format, invalidating everything at once · a shift in traffic to
uncached keys · **or someone flushed it.**

**⭐ Then the operational half**: is the database survivable at 0% hit rate, is there a request limit
protecting it, and how do you warm back up. **Naming "is this cache load-bearing?" is the question
that separates a diagnosis from a guess.**
