# Day 234 🖥️

**J-234** · 🖥️ **Rendering strategies** — ⭐⭐ the question that picks one

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: every rendering strategy is answering one question — *when* does the HTML
> get built, and *where* — and the correct answer per route follows from two facts you already know
> about your data: how often it changes, and whether it is the same for everyone.**
>
> Today: the five strategies, ⭐ hydration and its cost, ⭐⭐ the decision table, and server components.

---

# Part 1 — The five, in one table

| | ⭐ HTML built | Where | ⭐ Good for | ⭐⭐ The cost |
|---|---|---|---|---|
| **CSR** | In the browser, after JS loads | Client | Dashboards behind a login | ⭐⭐ Blank screen until JS parses. Bad SEO, bad on slow phones. |
| **SSR** | Per request | Server | Personalised, always-fresh | ⭐ Server CPU per request; ⭐ this is Thymeleaf, structurally |
| **SSG** | At build time | Build | Docs, marketing | ⭐⭐ Stale until you rebuild |
| **ISR** | Build, then re-built in the background on a timer | Build + server | Catalogues | ⭐ Users may see stale content within the window |
| **RSC** | ⭐ On the server, streamed, **no JS shipped for those components** | Server | ⭐⭐ Data-heavy pages | ⭐ New model; a hard client/server boundary |

```
⭐⭐ THE TWO QUESTIONS THAT DECIDE IT

⭐   ① ⭐ IS THIS PAGE THE SAME FOR EVERYONE?
⭐        YES ⇒ SSG or ISR (⭐⭐ cache it at the CDN, serve in 20 ms)
⭐        NO  ⇒ SSR or CSR
⭐   ② ⭐ HOW STALE CAN IT BE?
⭐        forever ⇒ SSG   ·  minutes ⇒ ISR
⭐        seconds ⇒ SSR   ·  live    ⇒ CSR + polling/websocket

⭐   ⇒ ⭐⭐ IT IS A CACHE-FRESHNESS DECISION, NOT A FRAMEWORK
⭐     PREFERENCE — the same call you make with @Cacheable and a TTL.
⭐   ⇒ ⭐ AND IT IS PER-ROUTE. A marketing page and a dashboard in
⭐     one app should NOT use the same strategy.
```

# Part 2 — ⭐ Hydration, and what it actually costs

```
⭐⭐ SSR IS TWO PHASES, AND PEOPLE COUNT ONLY THE FIRST

⭐   ① server sends HTML ⇒ ⭐ USER SEES CONTENT FAST ✅
⭐      (⭐ so far this is exactly Thymeleaf)
⭐   ② ⭐⭐ THE BROWSER DOWNLOADS THE JS AND **RE-RUNS EVERY
⭐      COMPONENT** to attach event listeners.
⭐      ⇒ ⭐ THE PAGE IS **VISIBLE BUT NOT INTERACTIVE** IN BETWEEN.

⭐   ⇒ ⭐⭐ THE UNCANNY VALLEY: the button is on screen and clicking
⭐     it does NOTHING. Users click three times, then rage-click.
⭐   ⇒ ⭐⭐ THAT SECOND PHASE IS THE PRICE REACT CHARGES THAT
⭐     THYMELEAF DOES NOT. SSR improves PERCEIVED load and can make
⭐     time-to-interactive WORSE, because you ship HTML *and* JS.
```

| ⭐ Hydration mismatch | ⭐⭐ A real, common bug |
|---|---|
| `new Date()` / `Math.random()` in render | ⭐⭐ Server and client disagree ⇒ React **discards the server HTML** and re-renders |
| `window` / `localStorage` during render | ⭐ Crashes on the server — it does not exist there |
| Content that depends on the user, rendered statically | ⭐⭐ The wrong name, cached at the CDN, **shown to a different user** |

> ⭐⭐ **That last row is a security incident shape**, not a rendering bug. Anything user-specific must
> never be produced by a route a shared cache can store — **the same rule as never putting a
> per-user response behind a shared `@Cacheable` key.**

# Part 3 — Server components

```jsx
// ⭐ SERVER COMPONENT (the default in the App Router)
async function OrderList() {
  const orders = await db.query("SELECT ...");   // ⭐⭐ runs on the SERVER
  return <ul>{orders.map(o => <li key={o.id}>{o.total}</li>)}</ul>;
}
// ⇒ ⭐⭐ ZERO JAVASCRIPT SHIPPED for this component.
//    ⭐ It cannot use useState, useEffect, or onClick.

"use client";                              // ⭐ opt back in, explicitly
function AddButton() {                     // ⭐ ships JS, can hold state
  const [busy, setBusy] = useState(false);
  return <button onClick={...}>Add</button>;
}
```

| ⭐ Server component | ⭐ Client component |
|---|---|
| ✅ Query a database, read a secret, use a big library free | ✅ `useState`, effects, handlers, browser APIs |
| ❌ No state, no effects, no `onClick` | ❌ ⭐⭐ **Everything it imports ships to the browser** |
| ⭐⭐ Bundle cost: **zero** | ⭐ Bundle cost: itself + its whole import tree |

```
⭐⭐ THE RULE THAT KEEPS THIS SANE
⭐   PUSH "use client" AS FAR DOWN THE TREE AS POSSIBLE.
⭐   ⭐ A "use client" at the top of a page makes the ENTIRE PAGE a
⭐     client component and you have gained nothing.
⭐   ⇒ ⭐⭐ SERVER COMPONENTS RENDER CLIENT ONES AS children, so the
⭐     interactive LEAVES ship JS and the data-heavy TRUNK does not.
```

> ⭐⭐ **The security note that matters most.** A server component can read secrets and query the
> database — which means **a mistaken `"use client"` on a file that touches a secret ships that secret
> to the browser** (Day 222). ⭐ It is the annotation-driven equivalent of accidentally putting a
> `@Value("${db.password}")` field on a DTO that gets serialised. Guard it with a `server-only` import.

# Part 4 — Streaming

```jsx
<Suspense fallback={<Skeleton />}>
  <SlowRecommendations />        {/* ⭐⭐ streams in when ready */}
</Suspense>
```

> ⭐ **Streaming removes the "slowest query decides the whole page" problem.** The shell and fast
> content arrive immediately; slow sections fill in. **This is Day 456's degradation ladder as a
> rendering feature** — the page is useful before it is complete.

```
⭐⭐ WHAT TO PICK, FOR THE FLAGSHIP YOU ARE BUILDING
⭐   marketing / landing   ⇒ SSG    (same for everyone, rarely changes)
⭐   docs                  ⇒ SSG
⭐   public catalogue      ⇒ ISR    (same for everyone, changes hourly)
⭐   ⭐ THE DASHBOARD       ⇒ ⭐⭐ CSR OR RSC BEHIND AUTH — per-user,
⭐                            so it CANNOT be shared-cached
⭐   an admin panel        ⇒ CSR    (SEO irrelevant, always fresh)
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you choose a rendering strategy?"**

Reframe it as something familiar. **Every strategy answers one question: when is the HTML built, and
where. I pick per route from two facts — is this page the same for everyone, and how stale can it be.
Same for everyone and rarely changing is static, cached at the CDN. Per-user is server- or
client-rendered, because it can't be shared-cached. It's a cache-freshness decision, the same call I
make with `@Cacheable` and a TTL.**

Then the cost people skip, using the comparison your audience knows. **SSR looks like Thymeleaf for the
first phase — the server sends HTML and content appears fast. Then the browser downloads the JS and
re-runs every component to attach handlers, and in between the page is visible but not interactive. The
button is there and clicking does nothing. That second phase is the price React charges that Thymeleaf
doesn't, and it means SSR can improve perceived load while making time-to-interactive worse.**

Then the security answer. **A personalised page rendered by a route a shared cache can store is an
incident — you serve one user's name to another. That's the same mistake as putting a per-user response
behind a shared cache key.**

Close on server components. **They ship zero JavaScript and can query the database directly, so the
data-heavy trunk costs nothing and only the interactive leaves ship code. The discipline is pushing
`"use client"` as far down as possible. And because server components can read secrets, a mistaken
`"use client"` ships one to the browser — the equivalent of putting an injected password field on a DTO
that gets serialised.**
