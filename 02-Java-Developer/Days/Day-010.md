# Part 1 — L-010 · HTTP anatomy

## The shape

HTTP is **text**, in a strict shape. Both requests and responses follow the same four-part
structure:

```
   ┌─────────────────────────────────────────┐
   │  Start line                             │   ← the only part that differs
   ├─────────────────────────────────────────┤
   │  Headers (one per line, Key: Value)     │
   │  ...                                    │
   ├─────────────────────────────────────────┤
   │  (blank line)                           │   ← CRLF CRLF — headers end here
   ├─────────────────────────────────────────┤
   │  Body (optional)                        │
   └─────────────────────────────────────────┘
```

```http
GET /users/42?fields=name HTTP/1.1          ← request line: METHOD PATH VERSION
Host: api.example.com                       ← headers
Accept: application/json
Authorization: Bearer eyJhbGc...
                                            ← blank line
                                            ← no body on a GET
```

```http
HTTP/1.1 200 OK                             ← status line: VERSION CODE REASON
Content-Type: application/json              ← headers
Content-Length: 47
Cache-Control: max-age=300
                                            ← blank line
{"id":42,"name":"Ramesh"}                   ← body
```

**That blank line is load-bearing.** It's the only thing telling the parser where headers stop. Omit
it and the receiver waits forever — which is exactly what you'd have seen on Day 004 if you'd broken
your response.

## Methods — and the two properties that actually matter

| Method | Purpose | Safe? | Idempotent? | Body? |
|---|---|---|---|---|
| `GET` | Retrieve | ✅ | ✅ | No |
| `HEAD` | Headers only, no body | ✅ | ✅ | No |
| `OPTIONS` | What's allowed here (CORS preflight) | ✅ | ✅ | No |
| `POST` | Create / process | ❌ | ❌ | Yes |
| `PUT` | Replace entirely | ❌ | ✅ | Yes |
| `PATCH` | Partial update | ❌ | ❌ | Yes |
| `DELETE` | Remove | ❌ | ✅ | Rarely |

**Safe** = does not change server state. **Idempotent** = doing it N times has the same effect as
doing it once.

**These two properties are not trivia — they decide real behaviour:**

- Browsers, proxies and CDNs **cache** safe methods. They will not cache a POST.
- Clients, load balancers and libraries **automatically retry** idempotent methods on network
  failure. They will not auto-retry a POST — because a retried POST might create a second order.
- A crawler follows `GET` links freely. If you put "delete" behind a `GET`, a crawler will delete
  your data. This has happened to real companies.

**Why is `DELETE` idempotent when the second call returns 404?** Because idempotence is about the
*resulting state*, not the response code. After one DELETE the resource is gone; after five it's
still gone. State is identical.

**Why isn't `POST` idempotent, and what do you do about it?** Two identical POSTs create two
resources. The fix is the **idempotency key** — you've already met it in
[`03-Web-Developer/05-API-Safety.md`](../../03-Web-Developer/05-API-Safety.md) as "the double-charge
killer". Now you know it exists because POST lacks a property the protocol gives PUT for free.
Full treatment on Day 123.

## Status codes

Learn the **families** first — then you can reason about any code you've never seen.

| Family | Meaning | The one-line rule |
|---|---|---|
| **1xx** | Informational | Rare. `101 Switching Protocols` = the WebSocket upgrade (Day 017) |
| **2xx** | Success | It worked |
| **3xx** | Redirection | Look elsewhere |
| **4xx** | Client error | **You** sent something wrong. Don't retry unchanged. |
| **5xx** | Server error | **I** broke. Retrying may work. |

**The 4xx/5xx split is the one that matters**, and it's the reason your retry rule from
[Phase 05](../../03-Web-Developer/05-API-Safety.md#4-retry-storms) says *never retry 4xx except 429*.
A 400 will be 400 forever — the request itself is malformed. A 503 might succeed in two seconds.

### The codes you'll actually use

| Code | When |
|---|---|
| `200 OK` | Success with a body |
| `201 Created` | Resource created — include a `Location` header |
| `204 No Content` | Success, deliberately no body (typical for DELETE) |
| `301` / `308` | Permanent redirect — **browsers cache this aggressively and it's painful to undo** |
| `302` / `307` | Temporary redirect |
| `304 Not Modified` | Your cached copy is still good (see conditional requests below) |
| `400 Bad Request` | Malformed syntax or failed validation |
| `401 Unauthorized` | **Not authenticated** — you haven't proven who you are |
| `403 Forbidden` | **Authenticated but not allowed** — I know who you are, you can't do this |
| `404 Not Found` | No such resource — *or* deliberately hiding one you don't own |
| `405 Method Not Allowed` | Wrong verb for this path |
| `409 Conflict` | State conflict — duplicate, or a version mismatch |
| `422 Unprocessable Entity` | Syntactically fine, semantically invalid |
| `429 Too Many Requests` | Rate limited — **send `Retry-After`** |
| `500 Internal Server Error` | Unhandled exception. Your fault. |
| `502 Bad Gateway` | Upstream returned garbage |
| `503 Service Unavailable` | Temporarily down / overloaded |
| `504 Gateway Timeout` | Upstream didn't answer in time |

**401 vs 403 is asked constantly.** 401 = "I don't know who you are" (authentication). 403 = "I know
who you are and the answer is no" (authorization). The names are historically confusing —
"Unauthorized" actually means unauthenticated.

**And the security nuance you already know from Phase 06:** for a resource the user doesn't own,
return **404, not 403** — a 403 confirms the resource exists, which leaks information. That's the
IDOR-hardening rule, and it's a deliberate deviation from the pure semantics above.

## Headers worth knowing now

### Request

| Header | Purpose |
|---|---|
| `Host` | **Mandatory in 1.1.** Which site — one IP serves many domains via virtual hosting |
| `Accept` | What content types I can handle |
| `Content-Type` | What I'm sending in the body |
| `Authorization` | `Bearer <token>` or `Basic <base64>` |
| `User-Agent` | Client identification |
| `Cookie` | Cookies for this domain |
| `If-None-Match` / `If-Modified-Since` | Conditional request — "only if it changed" |
| `Origin` | Set by the browser on cross-origin requests — the input to CORS (Day 020) |

**`Host` is why virtual hosting works.** One IP, one port, hundreds of sites — the server reads
`Host` to decide which one you meant. It's also why TLS needs SNI (Day 009): the certificate must be
chosen *before* the encrypted `Host` header can be read.

### Response

| Header | Purpose |
|---|---|
| `Content-Type` | MIME type of the body |
| `Content-Length` | Body size in bytes — how the client knows when to stop reading |
| `Cache-Control` | `max-age`, `no-cache`, `no-store`, `private`, `immutable` |
| `ETag` | Version identifier for conditional requests |
| `Location` | Where to go (with 3xx) or what was created (with 201) |
| `Set-Cookie` | Set a cookie — with `HttpOnly`, `Secure`, `SameSite` |
| `Retry-After` | With 429/503 — when to try again |
| `Access-Control-Allow-Origin` | CORS (Day 020) |
| Security headers | CSP, HSTS, X-Frame-Options, X-Content-Type-Options |

### Conditional requests — the mechanism behind 304

```
   First request:
     GET /logo.png
     ← 200 OK, ETag: "abc123", Cache-Control: max-age=3600

   After the cache expires:
     GET /logo.png
     If-None-Match: "abc123"
     ← 304 Not Modified          ← no body! Just a few bytes.
```

**The client keeps its cached copy and the server sends no body.** This is how a browser revalidates
a 2 MB image for the cost of a few hundred bytes. It's also why hashed filenames plus
`Cache-Control: immutable` is even better — no revalidation request at all.

## Statelessness

**HTTP is stateless: every request is independent, and the server remembers nothing between them.**

That's why every authenticated request must carry its own proof — a cookie or an `Authorization`
header. The server does not "know you're logged in"; it re-establishes that on every single request.

**This is not a limitation, it's the design that lets the web scale.** Any server can handle any
request, so you can put ten servers behind a load balancer and route freely. The moment a server
holds session state in memory, you need sticky sessions and you've broken horizontal scaling.

Statelessness is why JWTs are attractive (self-contained proof, no server lookup — Day 114) and why
session stores go in Redis rather than in the app (Day 113). Same principle you'll see again as
"stateless services scale horizontally" on Day 324.

## Type this yourself

Extend your Day 004 server into a real router.

```java
import java.io.*;
import java.net.*;

public class HttpAnatomy {
    public static void main(String[] args) throws IOException {
        ServerSocket server = new ServerSocket(8080);
        System.out.println("http://localhost:8080");

        while (true) {
            try (Socket client = server.accept()) {
                BufferedReader in = new BufferedReader(
                        new InputStreamReader(client.getInputStream()));

                String requestLine = in.readLine();
                if (requestLine == null) continue;
                System.out.println("\n>>> " + requestLine);

                String[] parts = requestLine.split(" ");
                String method = parts[0];
                String path   = parts[1];

                String header;
                while ((header = in.readLine()) != null && !header.isEmpty()) {
                    System.out.println("    " + header);
                }

                String status, body, type = "application/json";

                if (path.equals("/") && method.equals("GET")) {
                    status = "200 OK";
                    body = "{\"message\":\"hello\"}";
                } else if (path.equals("/created") && method.equals("POST")) {
                    status = "201 Created";
                    body = "{\"id\":42}";
                } else if (path.equals("/nobody")) {
                    status = "204 No Content";
                    body = "";
                } else if (path.equals("/teapot")) {
                    status = "418 I'm a teapot";
                    body = "{\"error\":\"short and stout\"}";
                } else if (path.equals("/boom")) {
                    status = "500 Internal Server Error";
                    body = "{\"error\":\"something broke\"}";
                } else if (!method.equals("GET") && !method.equals("POST")) {
                    status = "405 Method Not Allowed";
                    body = "{\"error\":\"method not allowed\"}";
                } else {
                    status = "404 Not Found";
                    body = "{\"error\":\"not found\"}";
                }

                OutputStream out = client.getOutputStream();
                StringBuilder r = new StringBuilder();
                r.append("HTTP/1.1 ").append(status).append("\r\n");
                r.append("Content-Type: ").append(type).append("\r\n");
                r.append("Content-Length: ").append(body.getBytes().length).append("\r\n");
                if (status.startsWith("201")) r.append("Location: /users/42\r\n");
                r.append("Connection: close\r\n");
                r.append("\r\n").append(body);

                out.write(r.toString().getBytes());
                out.flush();
            }
        }
    }
}
```

Then exercise it and **read the raw exchange every time**:

```bash
curl -v http://localhost:8080/
curl -v -X POST http://localhost:8080/created
curl -v http://localhost:8080/nobody
curl -v http://localhost:8080/teapot
curl -v -X DELETE http://localhost:8080/
curl -v http://localhost:8080/missing
curl -I http://localhost:8080/          # HEAD — headers only
```

**Two deliberate experiments:**

1. Send `204 No Content` **with** a body. Watch clients get confused — 204 promises no body, so the
   bytes are interpreted as the start of the next response.
2. Set `Content-Length` to a number larger than the body. The client hangs waiting for bytes that
   never come. **That's the header doing its job.**

## Common mistakes

| Mistake | Correction |
|---|---|
| Using `GET` for actions that change state | Crawlers and prefetchers will trigger them. Use POST/PUT/DELETE. |
| Returning `200` with an error in the body | Clients and monitoring rely on status codes. Use the right one. |
| Confusing 401 and 403 | 401 = not authenticated. 403 = authenticated, not permitted. |
| `PATCH` treated as idempotent | It generally isn't (e.g. "increment by 1"). `PUT` is. |
| Forgetting `Content-Length` or chunked encoding | The client can't tell where the body ends. |
| Assuming HTTP remembers you | It's stateless. Every request carries its own credentials. |
| 500 for a validation failure | Validation failure is 400/422 — the client's fault, not yours. |

## Interview questions

**Q: What's the difference between PUT and POST?**
> PUT replaces a resource at a known URI and is idempotent — repeating it leaves the same state.
> POST submits data to be processed, typically creating a resource whose URI the server chooses, and
> is not idempotent, so repeating it may create duplicates.

**Q: What does idempotent mean and why does it matter?**
> Performing the operation multiple times has the same effect as performing it once. It matters
> because it determines whether a client, proxy or load balancer can safely retry after a network
> failure. Non-idempotent operations need idempotency keys to be retried safely.

**Q: 401 vs 403?**
> 401 means unauthenticated — no valid credentials were supplied, and the client should authenticate.
> 403 means authenticated but not permitted. In practice, for resources a user doesn't own, many APIs
> deliberately return 404 instead of 403 so as not to reveal that the resource exists.

**Q: Why is HTTP stateless, and what does that buy you?**
> Each request is independent and carries everything needed to serve it. It means any server can
> handle any request, which is what allows horizontal scaling behind a load balancer without sticky
> sessions. The cost is that authentication must be re-established on every request.

**Q: What is a conditional request?**
> The client sends `If-None-Match` with a previously received ETag, or `If-Modified-Since`. If the
> resource is unchanged the server replies `304 Not Modified` with no body, so the client reuses its
> cached copy at a fraction of the bandwidth.

**Q: Why must `Host` be present in HTTP/1.1?**
> Virtual hosting — one IP address serves many domains, so the server needs the requested hostname to
> select the right site. It's also why TLS needs SNI, since the certificate must be chosen before the
> encrypted Host header is readable.

# Part 2 — C-07 · UDP

## What UDP is

**IP plus ports, and nothing else.** An 8-byte header: source port, destination port, length,
checksum. That's the entire protocol.

| | TCP | UDP |
|---|---|---|
| Header | 20 bytes | **8 bytes** |
| Handshake | 3-way, 1 RTT | **None — send immediately** |
| Reliable | Yes | No |
| Ordered | Yes | No |
| Congestion control | Yes | **No** |
| Message boundaries | No (byte stream) | **Yes (datagrams)** |

## What you lose, and why you'd want to

You lose reliability and ordering. You gain:

1. **No handshake** — first packet carries data. Saves a full RTT (140 ms across continents).
2. **No head-of-line blocking** — TCP delivers in order, so one lost packet stalls everything behind
   it even if it already arrived. UDP hands each datagram up as it lands.
3. **Message boundaries preserved** — you send one datagram, the receiver reads exactly one. TCP is
   a byte stream, so you must frame messages yourself.
4. **You control the tradeoffs** — implement exactly the reliability you need, and no more.

**The decision rule:** use UDP when **late data is worthless**.

| Use case | Why UDP |
|---|---|
| **DNS** | One small query, one small reply. A handshake would triple the cost. Retry if no answer. |
| **Voice/video calls** | A packet from 300 ms ago is useless — you've played past that audio. Drop it. |
| **Gaming** | Position updates supersede each other. The newest matters; old ones don't. |
| **Metrics (StatsD)** | Losing one datapoint is fine. Blocking your app on metrics is not. |
| **QUIC / HTTP/3** | Reliability rebuilt in userspace, *per stream*, avoiding TCP's head-of-line blocking (Day 011) |

**That last row is the important one.** HTTP/3 runs over UDP not because it wants unreliability, but
because TCP's ordering guarantee is applied to the whole connection, and HTTP/3 needs it per stream.
It was easier to rebuild reliability on UDP than to change TCP — which is ossified in middleboxes
worldwide and effectively unchangeable.

## Type this yourself

```java
import java.net.*;

public class UdpDemo {
    public static void main(String[] args) throws Exception {
        // Receiver
        new Thread(() -> {
            try (DatagramSocket socket = new DatagramSocket(9999)) {
                byte[] buf = new byte[1024];
                while (true) {
                    DatagramPacket p = new DatagramPacket(buf, buf.length);
                    socket.receive(p);                       // blocks
                    System.out.println("Got: " + new String(p.getData(), 0, p.getLength())
                            + "  from " + p.getSocketAddress());
                }
            } catch (Exception e) { e.printStackTrace(); }
        }).start();

        Thread.sleep(500);

        // Sender — no connect(), no handshake, just send
        try (DatagramSocket socket = new DatagramSocket()) {
            for (int i = 1; i <= 5; i++) {
                byte[] data = ("message " + i).getBytes();
                socket.send(new DatagramPacket(data, data.length,
                        InetAddress.getByName("localhost"), 9999));
            }
        }
        Thread.sleep(1000);
        System.exit(0);
    }
}
```

**Compare this to your TCP client from Day 005.** No `connect()`. No handshake. No stream. Each
`send()` is one self-contained datagram, and each `receive()` gets exactly one. Notice you never
learn whether any of them arrived.

## Interview questions

**Q: When would you use UDP over TCP?**
> When latency matters more than completeness and late data is worthless — real-time voice and video,
> gaming, DNS lookups, metrics. Also when you want to implement your own reliability semantics, which
> is what QUIC does.

**Q: What is head-of-line blocking?**
> TCP guarantees in-order delivery, so if one segment is lost, all subsequent segments are held in
> the receive buffer until it's retransmitted — even though they've already arrived. UDP has no such
> constraint, and HTTP/3 uses it to avoid the problem per stream.

**Q: Why does DNS use UDP?**
> Queries and responses are small and fit in one datagram, and a TCP handshake would triple the cost
> of a single lookup. If no reply arrives the client simply retries. DNS falls back to TCP for
> responses over 512 bytes and for zone transfers.
