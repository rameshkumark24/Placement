# Day 152

**L-152** · Pagination with `Pageable` — and where Spring's default is wrong

**Time:** 3 hrs · **Mode:** NEW

> Day 107 proved that offset pagination degrades — `OFFSET 100000` makes the database read and
> discard 100,000 rows — and that it is **incorrect** under concurrent writes, because rows shift
> between pages so a user sees duplicates and misses records entirely. Day 108 added the allow-list
> rule for sorting and filtering.
>
> Spring Data's `Pageable` is offset pagination with a convenient wrapper. Today is using it well,
> knowing exactly when it stops being adequate, and implementing Day 107's keyset alternative — which
> Spring does *not* give you.

---

# Part 1 — `Pageable`, and the three costs hidden in one line

```java
@GetMapping
Page<OrderResponse> list(@PageableDefault(size = 20, sort = "placedAt",
                                          direction = Sort.Direction.DESC) Pageable pageable) {
    return orders.findAll(pageable).map(OrderResponse::from);
}
```

`?page=2&size=20&sort=placedAt,desc` binds automatically — `PageableHandlerMethodArgumentResolver`
at Day 145's step 4.

**The three things this line quietly decides:**

### ⭐ 1. `Page` runs a second `COUNT(*)` query

```sql
select * from orders order by placed_at desc limit 20 offset 40;
select count(*) from orders;                    -- ⭐ on every single request
```

On a large table with a `WHERE` clause the count is frequently **slower than the data query** — it
must scan every matching row to produce a number nobody reads past "showing 1–20 of many".

```java
Slice<OrderResponse> list(Pageable p)   // ⭐ no count. Knows only "is there a next page?"
List<OrderResponse>  list(Pageable p)   // no count, no metadata
Page<OrderResponse>  list(Pageable p)   // count query every time
```

**Use `Slice` for infinite scroll and mobile feeds** — they need "load more", not a total. Reserve
`Page` for admin tables that genuinely render "Page 3 of 47".

### ⭐ 2. The unbounded `size` parameter

`?size=100000` is a request for 100,000 rows. Day 147's serialization cost plus Day 144's heap
pressure equals one URL that takes the service down — and it needs no authentication beyond whatever
the endpoint already required.

```yaml
spring.data.web.pageable.max-page-size: 100        # ⭐ set this on day one
spring.data.web.pageable.default-page-size: 20
spring.data.web.pageable.one-indexed-parameters: false
```

Boot caps at 2000 by default, which is far too high to be a safety net.

### ⭐ 3. `sort` is a raw property name from the client

`?sort=customer.creditCard.number,asc` — Spring Data will happily build that path. Day 108's rule
applies verbatim: **allow-list the sortable fields.**

```java
private static final Set<String> SORTABLE = Set.of("placedAt", "total", "status");

Pageable safe(Pageable p) {
    Sort sort = Sort.by(p.getSort().stream()
            .filter(o -> SORTABLE.contains(o.getProperty()))     // ⭐ silently drop unknown
            .toList());
    return PageRequest.of(p.getPageNumber(), Math.min(p.getPageSize(), 100),
                          sort.isEmpty() ? Sort.by(DESC, "placedAt") : sort);
}
```

Sorting by a field the client should not know exists is an **information leak even without seeing the
value** — sort by `internalRiskScore` twice and you have ordered every customer by their risk score.
That is Day 108's subtler point, and it is why "they can only sort, not select" is not a defence.

# Part 2 — ⭐ Deterministic ordering, the bug nobody expects

```java
Pageable p = PageRequest.of(0, 20, Sort.by(DESC, "status"));    // ⚠️ 8 distinct statuses
```

Twelve thousand orders, eight statuses, sorted by status. **Rows with equal sort keys have no defined
order.** The database may return them differently between the page-1 query and the page-2 query — and
under a parallel scan or after a plan change, it will.

Result: some orders appear on both pages, others on neither. The user is looking at an incomplete
list and has no way to tell.

**The fix is one line and it is mandatory:**

```java
Sort.by(DESC, "status").and(Sort.by(DESC, "id"))        // ⭐ always break ties on a unique column
```

**Every paginated query must end its sort with a unique column.** This is true of offset pagination
and keyset pagination alike, it costs nothing, and its absence produces a bug that is nearly
impossible to reproduce on a test dataset — which is exactly why it survives to production.

# Part 3 — Keyset pagination, which Spring does not give you

Day 107's argument, restated with numbers: `OFFSET 100000 LIMIT 20` reads 100,020 rows and throws
away 100,000. Keyset reads 20.

```
GET /api/orders?limit=20
GET /api/orders?limit=20&after=eyJwbGFjZWRBdCI6IjIwMjYtMDgtMTRUMTA6MjM6NDVaIiwiaWQiOiI3ZjNhIn0
```

```java
@GetMapping
CursorPage<OrderResponse> list(@RequestParam(required = false) String after,
                               @RequestParam(defaultValue = "20") @Max(100) int limit) {

    Cursor c = after == null ? null : Cursor.decode(after);      // ⭐ validate on decode

    List<Order> rows = c == null
            ? repo.firstPage(limit + 1)                          // ⭐ +1 to detect "hasNext"
            : repo.after(c.placedAt(), c.id(), limit + 1);

    boolean hasNext = rows.size() > limit;
    if (hasNext) rows = rows.subList(0, limit);

    String next = hasNext ? Cursor.of(rows.getLast()).encode() : null;
    return new CursorPage<>(rows.stream().map(OrderResponse::from).toList(), next);
}
```

```java
@Query("""
    select o from Order o
    where (o.placedAt < :placedAt)
       or (o.placedAt = :placedAt and o.id < :id)      ⭐ the tie-break, in the WHERE clause
    order by o.placedAt desc, o.id desc
""")
List<Order> after(@Param("placedAt") Instant placedAt, @Param("id") UUID id, int limit);
```

**Three implementation notes that matter:**

- **Fetch `limit + 1`.** It is how you know whether a next page exists without a count query. Trim
  before returning.
- **The `WHERE` must mirror the `ORDER BY` exactly**, including the tie-break column and direction.
  Mismatch them and rows are skipped — silently.
- **Row-value syntax is cleaner where supported:** `where (o.placedAt, o.id) < (:placedAt, :id)`.
  PostgreSQL supports it and can use a composite index directly; JPQL does not, so it needs a native
  query.

## The cursor must be opaque *and* validated

**Opaque** — base64 of a JSON object — because a readable cursor becomes a contract clients depend
on, and then you cannot change the sort without breaking them (Day 109).

**Validated** — because a base64 cursor is user input that goes straight into query parameters. It is
not injection if you bind it properly, but a malformed cursor must produce a **400 with a clear
message**, not a 500 from a parse exception. And if the cursor encodes fields the client should not
control, sign it with an HMAC (Day 115b).

## Choosing between them, honestly

| | Offset (`Pageable`) | Keyset (cursor) |
|---|---|---|
| Jump to page 47 | ✅ | ❌ **impossible by design** |
| Total count | ✅ | ❌ (or a separate, cached estimate) |
| Deep pages | ❌ degrades linearly | ✅ constant |
| Stable under writes | ❌ duplicates and gaps | ✅ |
| Client complexity | trivial | must carry the cursor |
| Spring support | built in | hand-rolled |

**The rule:** offset for admin tables and anything with page numbers in the UI; keyset for feeds,
infinite scroll, exports, and any API a third party will iterate. If a public API allows deep
pagination with offsets, someone will eventually iterate it to page 50,000 and you will discover it
from a database alert.

**And the pragmatic hybrid worth naming in an interview:** offer offset pagination but cap it —
`if (page > 500) throw new BadRequestException("use cursor pagination beyond page 500")`. Most UIs
never exceed page 10, and the cap turns an availability risk into a documented limit.

# Part 4 — The response envelope, and the N+1 that pagination hides

```java
public record CursorPage<T>(List<T> items, String nextCursor) {}
```

Day 103's advice — **wrap collections in an object, never return a bare JSON array.** A bare array
cannot gain a field without breaking clients, and a top-level array is the classic JSON hijacking
shape. `Page<T>`'s default serialization is also worth a warning: Boot 3 logs that serializing
`PageImpl` directly is unstable across versions, and the recommendation is your own DTO or
`PagedModel`. **Do not let Spring's internal page structure become your public contract.**

## ⭐ Pagination plus a lazy relationship is the N+1 trap

```java
Page<Order> page = repo.findAll(pageable);       // 1 query
page.map(OrderResponse::from);                    // ⭐ each `from` touches o.getItems() → 20 more
```

Twenty rows, twenty-one queries. It never shows up in local testing with three rows.

**And the fix people reach for makes it worse:**

```java
@Query("select o from Order o join fetch o.items")     // ❌ with Pageable
List<Order> findAllWithItems(Pageable pageable);
```

```
HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
```

Hibernate **loads every matching row into memory** and paginates the list in Java. Your `LIMIT 20`
became a full table load. The warning is easy to miss in a busy log, and the endpoint works perfectly
until the table grows.

**The correct answers**, in order of preference:

1. ⭐ **Project directly into the DTO** — `select new OrderResponse(o.id, o.total, …)`. No entity, no
   collection, no N+1. Day 147's argument, and the reason it is the best mapping strategy for reads.
2. **`@EntityGraph`** on the repository method for `@ManyToOne` relationships, which join cleanly.
3. **Two queries** — page the IDs, then fetch the collections for those IDs in one `IN` query.
4. **`@BatchSize(size = 25)`** on the collection — turns N queries into `N/25`, a mitigation rather
   than a fix.

Day 160 covers all of this properly. What matters today is recognising that **pagination is where the
N+1 becomes expensive**, because you have promised the client a bounded response and are issuing an
unbounded number of queries to produce it.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ No unique tie-break in the sort | duplicated and skipped rows; unreproducible locally |
| `Page` everywhere | a count query per request, often the slowest part |
| No `max-page-size` | `?size=100000` is a one-URL outage |
| Client-controlled `sort` property | Day 108 — sorting leaks values you never returned |
| Deep offsets on a public API | someone will iterate to page 50,000 |
| Readable cursor | becomes a contract you cannot change |
| Cursor parse failure → 500 | should be a 400 |
| `WHERE` not mirroring `ORDER BY` in keyset | rows silently skipped |
| Bare JSON array response | unextendable; hijacking shape |
| Serializing `PageImpl` as the public contract | unstable across Spring versions |
| ⭐ `join fetch` with `Pageable` on a collection | in-memory pagination — the whole table |
| Mapping entities per row in a page | N+1, invisible on small datasets |

## Interview questions

**Q: What is wrong with offset pagination?**
Two things. Performance — `OFFSET 100000` makes the database read and discard 100,000 rows, so cost
grows with page depth. And correctness — under concurrent inserts and deletes rows shift between
pages, so the user sees duplicates and misses records. Keyset pagination fixes both by asking "give
me rows after this key" instead of "skip this many".

**Q: What does `Page` cost that `Slice` doesn't?**
A second `COUNT(*)` query on every request, which on a large filtered table is often slower than the
data query. `Slice` fetches one extra row to determine `hasNext`. I use `Page` only when the UI
actually renders a total.

**Q: Why must every paginated sort end on a unique column?**
Because rows with equal sort keys have no defined order, so the database may order them differently
between page requests — producing duplicates and gaps. It is a one-line fix and an almost
unreproducible bug.

**Q: You paginate 20 orders and get 21 queries. What happened, and what is the fix?**
A lazy collection touched during mapping. The fix is to project into the DTO in the query so the
entity is never loaded. Notably, adding `join fetch` with a `Pageable` makes it worse — Hibernate
paginates in memory and loads every matching row.

## Mini task

1. Insert 200k orders. Time `?page=0&size=20` and `?page=9000&size=20`. Watch the degradation.
2. Switch `Page` to `Slice`. Turn on `spring.jpa.show-sql` and confirm the count query disappears.
   Time both.
3. Sort by a low-cardinality column with no tie-break. Fetch pages 1 and 2 repeatedly under
   concurrent inserts. **Find a duplicate.** Add the tie-break and confirm it stops.
4. Request `?size=50000`. Then set `max-page-size: 100` and confirm the cap.
5. Request `?sort=id,asc&sort=customer.email,asc`. Confirm it works. Add the allow-list.
6. Implement the keyset endpoint with an opaque cursor. Compare page-9000-equivalent latency against
   offset.
7. Feed it a corrupt cursor. Turn the 500 into a 400.
8. Map a page of orders with a lazy `items` collection and count the queries. Fix it with a
   projection. Then try `join fetch` + `Pageable` and **find the `HHH90003004` warning in the log**.

## 🎙️ Articulation drill

Two minutes: **"How do you paginate an API?"**

State the two failures of offset pagination — cost grows with depth, and concurrent writes shift rows
so users see duplicates and gaps. Then say what you actually ship: `Slice` rather than `Page` to
avoid a count query per request, a hard cap on page size, an allow-list on sort fields because
sorting leaks values, and always a unique tie-break column. For feeds and public iteration, keyset
with an opaque validated cursor. Close on the detail that shows production experience: pagination is
where an N+1 becomes expensive, and `join fetch` with `Pageable` silently paginates in memory.
