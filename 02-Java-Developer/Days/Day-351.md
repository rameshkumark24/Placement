# Day 351 ⭐

**L-351** · ⭐ Design 7 — the news feed

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ The most-asked system design question, and it has exactly one interesting decision: do you do
> the work when someone writes, or when someone reads?**
>
> Both answers are wrong at the extremes, **the right answer is a hybrid, and the thing that forces
> the hybrid is a single multiplication you can do in ten seconds.**

---

# Part 1 — ⭐ Requirements and the number that decides everything

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| Post (text + media reference) | ⭐⭐ **feed read: p99 < 200 ms — it is the app's home screen** |
| Follow / unfollow | ⭐ **feed may be seconds stale** — post visibility is not transactional |
| ⭐ **Read a feed of followed users' posts** | ⭐ **monotonic reads** — a feed must never go backwards (Day 331) |
| Paginate infinitely | availability: reads 99.99%, writes 99.9% |
| Ranking (chronological, then ranked) | ⭐ read:write ≈ 50–100:1 |

```
⭐ ESTIMATE (Day 323)
⭐   300M DAU · 2 posts/day · 100 feed views/day
⭐   ⭐ Posts:  600M/day ⇒ ~7,000/s ⇒ peak ~20,000/s
⭐   ⭐ Reads:  30B/day  ⇒ ~350,000/s ⇒ peak ~1M/s
⭐   ⭐ Average followers: 200
⭐   ⇒ ⭐⭐ FAN-OUT ON WRITE: 7,000 × 200 = 1.4M feed writes/s   (workable)
⭐   ⇒ ⭐⭐ ONE CELEBRITY with 100M followers = 100M writes for ONE post  (not workable)
```

> **⭐ That last line is the entire design, and you can reach it in ten seconds.** Say it out loud
> early — **it is what makes everything afterwards look like a derivation rather than a recollection.**

---

# Part 2 — ⭐⭐ The deep dive: fan-out on write vs read

## ⭐ The two pure strategies

```
⭐ FAN-OUT ON WRITE (push)               ⭐ FAN-OUT ON READ (pull)
⭐  post ⇒ append the post id to          ⭐  post ⇒ store once
⭐  EVERY follower's precomputed feed     ⭐  read ⇒ query the N people you follow,
⭐                                        ⭐         merge their recent posts, sort
⭐  ⭐ READ = one range read. Fast.        ⭐  ⭐ READ = N queries + a merge. Slow.
⭐  ⭐ WRITE = O(followers). Expensive.    ⭐  ⭐ WRITE = O(1). Cheap.
```

| | ⭐ On write | ⭐ On read |
|---|---|---|
| ⭐ **Read latency** | ⭐⭐ **~10 ms — one lookup** | ⭐ 100–500 ms — a scatter-gather |
| ⭐ **Write cost** | ⭐ O(followers) — **catastrophic for celebrities** | ⭐ O(1) |
| Storage | ⭐ every post duplicated per follower | one copy |
| ⭐ **Wasted work** | ⭐⭐ **fanned out to inactive users who never read** | none |
| Freshness | ⭐ eventual — the fan-out takes time | ⭐ always current |
| Deletion / edit | ⭐ must chase every copy | trivial |

**⭐ Two failures, one at each extreme:**

- ⭐⭐ **Write is unusable for celebrities.** 100M writes for one post means a post takes minutes to
  appear and one user can saturate the fan-out pipeline.
- ⭐⭐ **Read is unusable at the read rate.** One million feed reads a second, each fanning out to 200
  authors, is **200 million queries a second.** Impossible.

## ⭐⭐ The hybrid — and its precise rule

```
⭐ Users with < ~10,000 followers  ⇒ ⭐ FAN-OUT ON WRITE (the vast majority of posts)
⭐ Users with ≥ ~10,000 followers  ⇒ ⭐ FAN-OUT ON READ  (a tiny number of accounts)

⭐ READ PATH:
⭐   1. read the precomputed feed          ⭐ one range read
⭐   2. ⭐ query the few celebrities you follow directly  ⭐ typically 0–20 of them
⭐   3. merge, rank, return
```

| ⭐ Why the rule works | |
|---|---|
| ⭐⭐ **99.9% of posts fan out cheaply** | ⭐ the average user has 200 followers |
| ⭐⭐ **The expensive accounts are read-time** | ⭐ **and there are very few of them, so the merge is small** |
| The threshold is tunable | ⭐ raise it when fan-out capacity is spare, lower it under load |
| ⭐ It degrades gracefully | ⭐ **under pressure, move more accounts to pull** |

⚠️ **Two refinements worth naming.** **Do not fan out to inactive users** — if someone has not opened
the app in 30 days, generate their feed on read instead; **for a large service that removes a huge
share of the fan-out with no user-visible cost.** And **fan-out is asynchronous**: the post is
acknowledged immediately, a queue does the distribution, **so a slow fan-out delays visibility, not
the post.**

# Part 3 — ⭐ Storage and the read path

| Data | ⭐ Store | ⭐ Why |
|---|---|---|
| ⭐ Posts | ⭐ KV or wide-column, partitioned by `postId` | write-once, read by id |
| ⭐ **Feeds** | ⭐⭐ **Redis list/sorted-set per user, capped at ~1,000 entries** | ⭐ 1M reads/s cannot touch a database |
| ⭐ Social graph | ⭐ KV: `followers(userId)`, `following(userId)` | ⭐ **the follower list is read on every post — cache it hard** |
| Media | ⭐ object storage + CDN (Day 327) | never in the feed |

```
⭐ FEED ENTRY: just the post id (+ a rank score). ⭐ NOT the post body.
⭐ ⇒ ⭐ 1,000 ids × 8 B = 8 KB per user. 300M users = 2.4 TB — ⭐ shardable across a Redis fleet.
⭐ ⇒ ⭐ Hydration (id → post) is a batched multi-get from the post store, cached hard.
```

> **⭐ Storing ids rather than bodies is the decision that makes the storage tractable**, and it has a
> second benefit: **an edited or deleted post is fixed in one place**, because the feed only ever
> held a pointer.

## ⭐ Pagination — cursor, never offset

```
⭐ ✗ ?offset=200   ⭐⭐ items shift as new posts arrive ⇒ duplicates and skips (Day 107)
⭐ ✓ ?cursor=<score>_<postId>   ⭐ stable under insertion, and O(1) to resume
```

## ⭐ Ranking — say the pipeline, do not design an ML system

```
⭐ 1. CANDIDATE GENERATION  ⭐ the merged feed, a few hundred items
⭐ 2. FEATURE LOOKUP        ⭐ recency, affinity, engagement rate, media type
⭐ 3. SCORING               ⭐ a model, applied to a few hundred candidates — not to everything
⭐ 4. FILTERING             ⭐ blocked, muted, already-seen, diversity caps
```

**⭐ The point to make: ranking scores hundreds of candidates, not millions of posts.** Candidate
generation is what makes it affordable — **and it is why the feed structure exists at all.**

⚠️ **"Already seen" is a real requirement with a real cost:** it needs per-user state of recently
shown ids — **a bounded set with a TTL, not a growing list.**

# Part 4 — ⭐ The awkward cases, and what breaks

| ⭐ Case | ⭐ Answer |
|---|---|
| ⭐⭐ **A new follow** | ⭐⭐ **backfill their recent posts into your feed asynchronously** — or accept that new content only appears going forward |
| ⭐ **Unfollow** | ⭐ do **not** scrub the feed — filter at read time; scrubbing is expensive and rarely worth it |
| ⭐ **Delete a post** | ⭐ tombstone at read (hydration returns nothing) — **do not chase millions of feed copies** |
| ⭐ Edit a post | ⭐ **free** — the feed holds an id |
| ⭐ **A user follows 5,000 accounts** | the merge is bigger; **cap the celebrities queried, or precompute more aggressively** |
| ⭐ **Cold start** | no follows ⇒ a global/trending feed |
| ⭐ Inactive returning user | ⭐ their feed was never fanned out — generate on read, then resume push |

| ⭐ Breaks first | ⭐ Mitigation |
|---|---|
| ⭐⭐ **Celebrity fan-out** | ⭐⭐ **the hybrid threshold — this is the design** |
| ⭐ Feed store hot shards | ⭐ shard by userId; a hot *user* is rare (unlike a hot *post*) |
| ⭐ **Hydration load on the post store** | ⭐ heavy caching; a hot post is read by millions (Day 326's hot key) |
| Fan-out queue backlog | ⭐ **posts appear late — alert on queue lag, and shed to pull mode** |
| Follower-list reads | cache the follower list; it is read on every post |

```
⭐ MONITOR: feed read p99 · ⭐ fan-out queue lag (= post visibility delay) · hydration cache hit rate
⭐          ⭐ posts/min (business metric) · % of feeds served in hybrid mode
⭐ CUT:     ranking (start chronological), stories, notifications, search
⭐ AT 10×:  ⭐ lower the celebrity threshold; more Redis shards. ⭐ The shape does not change.
```

---

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Pure fan-out on write | ⭐⭐ **one celebrity post = 100M writes** |
| ⭐⭐ Pure fan-out on read | ⭐⭐ **1M reads/s × 200 authors = impossible** |
| ⭐ Not deriving the hybrid from the numbers | it looks memorised |
| ⭐ Fanning out synchronously | ⭐ posting waits for distribution |
| ⭐ Fanning out to inactive users | ⭐ most of the work, wasted |
| ⭐ **Storing post bodies in feeds** | storage explodes; edits and deletes become fan-out chases |
| ⭐ Offset pagination | ⭐ duplicates and skips as new posts arrive |
| ⭐ **Chasing deletes through every feed** | ⭐ filter at hydration instead |
| Scrubbing feeds on unfollow | expensive; filter at read |
| ⭐ Ranking every post rather than candidates | ⭐ it is a scoring pipeline over hundreds |
| No unbounded-set control on "already seen" | per-user state grows forever |
| Ignoring cold start | a new user sees an empty app |

## Interview questions

**Q: Fan-out on write or on read?**
Both, split by follower count, and the numbers force it. At seven thousand posts a second and two
hundred average followers, fan-out on write is about 1.4 million feed writes a second, which is
workable. But one account with a hundred million followers is a hundred million writes for a single
post, which is not. Meanwhile pure fan-out on read is a million feed requests a second each querying
two hundred authors — two hundred million queries a second. So: push for normal accounts, pull for
the few large ones, merged at read time.

**Q: Where do you set the threshold?**
Around ten thousand followers, and it is a tuning knob rather than a constant. It is also the
system's pressure valve — under fan-out load I lower it so more accounts become read-time, which
trades a slightly slower read for a much cheaper write. I would also skip fan-out for users inactive
for thirty days and generate their feed on read, which removes a large share of the work with no
visible cost.

**Q: What is in a feed entry?**
A post id and a score, not the body. That keeps a thousand-entry feed at about eight kilobytes per
user, so the whole feed store fits across a Redis fleet, and it makes edits free and deletes cheap —
the feed holds a pointer, so a removed post simply hydrates to nothing rather than requiring me to
chase millions of copies.

**Q: A user deletes a post that was fanned out to a million feeds.**
Nothing chases it. Hydration is a batch lookup from the post store, so a deleted post returns nothing
and is filtered out at read time. The same applies to unfollows — filtering at read is far cheaper
than scrubbing feeds, and the feed self-corrects as entries age out of the cap.

**Q: How does ranking fit?**
As a pipeline over candidates, not over the corpus. The merged feed produces a few hundred
candidates, features are looked up, a model scores those few hundred, and filters remove blocked,
muted, already-seen and over-represented items. The important framing is that candidate generation is
what makes ranking affordable — you never score millions of posts, which is exactly why the feed
structure exists.

## Mini task

1. **Run the 45-minute framework**, timed, with **fan-out as the deep dive.** Derive the hybrid from
   the arithmetic out loud.
2. ⭐ Implement **both pure strategies** over a synthetic graph (300k users, power-law followers).
   **Measure write amplification and read latency for each.**
3. ⭐⭐ Add a celebrity with 100k followers and **watch pure push fall over.** Implement the hybrid and
   re-measure.
4. ⭐ Tune the threshold from 1,000 to 100,000 and **plot write volume against read latency.** Find
   your knee.
5. ⭐ Skip fan-out for users inactive 30 days and **measure the fan-out volume removed.**
6. Implement **cursor pagination** and prove it is stable while new posts arrive. Then use offset and
   **reproduce duplicates and skips.**

   to nothing.
8. ⭐ Make one post go viral and **measure hydration load on the post store.** Add a hot-key cache
   (Day 326) and re-measure.
9. ⭐ Implement a **new-follow backfill** and measure how long it takes to appear.
10. Add a bounded **already-seen set** with a TTL and confirm per-user state stays bounded.
