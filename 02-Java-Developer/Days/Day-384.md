# Day 384

**L-384** · VPC II — security groups, NACLs, endpoints, and debugging connectivity

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ A security group is stateful and can reference another security group. A network ACL is
> stateless and can only see addresses. Those two sentences explain why one of them is your primary
> control and the other is a blunt instrument you rarely need.**
>
> Today: SG-referencing-SG as the only firewall rule that survives autoscaling, **the ephemeral-port bug
> that is 90% of NACL incidents**, VPC endpoints as both a security and a cost decision, and **an
> ordered checklist for "it cannot connect".**

# Part 1 — ⭐⭐ Security groups vs NACLs

| | ⭐⭐ Security group | ⭐⭐ Network ACL |
|---|---|---|
| ⭐ Attached to | ⭐ an **ENI** (instance, task, RDS, endpoint) | ⭐ a **subnet** |
| ⭐⭐ **State** | ⭐⭐ **stateful — the return path is automatic** | ⭐⭐ **stateless — you must allow BOTH directions** |
| ⭐ Rules | ⭐⭐ **allow only** — no deny exists | ⭐ allow **and** deny |
| Evaluation | ⭐ all rules, any match wins | ⭐ **numbered order, first match wins** |
| ⭐⭐ **Can reference** | ⭐⭐ **another security group** | ⭐ CIDR only |
| Default | deny inbound, allow all outbound | default NACL allows everything |
| ⭐ Use it for | ⭐⭐ **everything** | ⭐ a coarse subnet-wide deny |

## ⭐⭐ The rule that matters: reference the group, not the range

```
⭐⭐ WRONG — brittle, and wrong the moment anything scales or moves AZ:
⭐   sg-database   inbound  5432  from  10.0.2.0/24

⭐⭐ RIGHT — intent expressed directly, correct forever:
⭐   sg-database   inbound  5432  from  sg-application
⭐ ⇒ ⭐⭐ "the database accepts Postgres from the application, whatever its IP is,
⭐        however many there are, in whichever AZ."
```

> **⭐⭐ SG-to-SG references are the single best practice in AWS networking.** They survive autoscaling,
> AZ changes, subnet resizing and re-deploys **without any rule ever being edited** — and they read as
> the architecture, so a reviewer can see the intended call graph in the security groups alone.

⚠️ **The corollary is a chain, and it is worth writing out:** `sg-alb` allows 443 from the internet ·
`sg-app` allows 8080 **from `sg-alb`** · `sg-db` allows 5432 **from `sg-app`**. **Nothing anywhere names
an IP address, and the internet can reach exactly one of the three.**

## ⭐⭐ Why NACLs bite: statelessness

```
⭐ Inbound rule 100:  ALLOW tcp 443 from 0.0.0.0/0     ⭐ request arrives — fine
⭐ Outbound: ⭐⭐ nothing allowing 1024-65535 to 0.0.0.0/0
⭐ ⇒ ⭐⭐ THE RESPONSE IS DROPPED. The client sees a timeout, not a refusal.
⭐ ⇒ ⭐⭐ Because NACLs are stateless, the RETURN traffic on EPHEMERAL PORTS must be allowed explicitly.
```

| ⭐ When a NACL genuinely earns its place | |
|---|---|
| ⭐ Block a specific hostile CIDR subnet-wide | ⭐⭐ SGs have no deny — this is the real use case |
| ⭐ Defence in depth on an isolated data subnet | a second, independent layer |
| A compliance requirement naming subnet-level controls | it exists; satisfy it and move on |

> **⭐ Default position: leave NACLs open and do all your work in security groups.** A NACL you added
> "for safety" that nobody documented will cost someone four hours in eighteen months. **If you do add
> deny rules, write the ephemeral-port allow at the same time, in the same commit.**

# Part 2 — ⭐⭐ VPC endpoints: private, and cheaper

| Type | ⭐ Services | ⭐⭐ Cost | ⭐ Mechanism |
|---|---|---|---|
| ⭐⭐ **Gateway endpoint** | ⭐⭐ **S3, DynamoDB only** | ⭐⭐ **FREE** | ⭐ a route table entry (a prefix list) |
| ⭐ **Interface endpoint** (PrivateLink) | ⭐ ~everything else — ECR, SQS, KMS, Secrets Manager, STS… | ⭐ **~$0.01/hr per AZ + ~$0.01/GB** | ⭐ an ENI in your subnet, private DNS |

```
⭐⭐ Without endpoints:  ECS task → NAT gateway → internet → S3
⭐   ⇒ ⭐ billed as NAT hours + ⭐⭐ NAT DATA PROCESSING per GB, and it leaves your network

⭐⭐ With a gateway endpoint: ECS task → (route table) → S3
⭐   ⇒ ⭐⭐ FREE, ⭐ never leaves the AWS network, ⭐ and works with NO internet route at all
```

> **⭐⭐ Adding the S3 gateway endpoint is a five-minute change with a permanent bill reduction, and it is
> missing from most accounts.** Say it in an interview and it lands, because it is specific, cheap and
> real (Day 396).

| ⭐ The endpoints worth adding for a container workload | |
|---|---|
| ⭐⭐ **S3 (gateway)** | ⭐⭐ **free** — and ECR image *layers* live in S3 |
| ⭐ `ecr.api` + `ecr.dkr` (interface) | ⭐ image pulls without NAT |
| ⭐ `logs` (interface) | CloudWatch Logs can be very high volume |
| ⭐ `secretsmanager`, `kms`, `sts` | ⭐ so credentials never traverse the internet |

⚠️ **Interface endpoints are not free and there are dozens of them — do not add them all reflexively.**
Three AZs × $0.01/hr ≈ $22/month **each**. Add the ones your traffic actually justifies; **measure
first** (Day 396). And note the security upside is real independently of cost: **an endpoint policy can
restrict which buckets are reachable at all**, which is a genuine data-exfiltration control.

# Part 3 — ⭐⭐ The connectivity debugging checklist

```
⭐⭐ "It cannot connect." ⭐ Work the list IN THIS ORDER. Do not skip. Do not guess.

⭐ 1. ⭐⭐ Is the app LISTENING?          ss -lntp — and on 0.0.0.0, ⭐⭐ not 127.0.0.1
⭐ 2. ⭐ ROUTE TABLE                      is there a path? ⭐ is this subnet on the table you think?
⭐ 3. ⭐⭐ SECURITY GROUP — destination    inbound allows the source SG on that port?
⭐ 4. ⭐ SECURITY GROUP — source          outbound allows it? (default allows all — but check)
⭐ 5. ⭐⭐ NACL — both subnets, BOTH ways  ⭐⭐ ephemeral ports on the return path
⭐ 6. ⭐ DNS                              does the name resolve, and ⭐⭐ to a PRIVATE address?
⭐ 7. Host firewall                       iptables/firewalld inside the instance
⭐ 8. ⭐ The service itself                is RDS actually available? is the task running?
```

| ⭐ The symptom tells you where to look | |
|---|---|
| ⭐⭐ **Connection TIMEOUT** | ⭐⭐ **something is silently dropping — SG, NACL or routing** |
| ⭐⭐ **Connection REFUSED** | ⭐⭐ **you reached the host; nothing is listening on that port** |
| ⭐ DNS resolution failure | ⭐ DNS settings, private hosted zone, or endpoint private DNS |
| ⭐ TLS handshake failure | you connected — it is certificates, not networking |
| ⭐ Works from one AZ only | ⭐⭐ a per-AZ route table or a missing endpoint ENI |

> **⭐⭐ "Timeout means dropped, refused means reached" saves more debugging time than any other single
> fact in this stage.** A refusal is *good news*: the network is fine and the problem is the process.

## ⭐ The tools, in order of usefulness

| Tool | ⭐ What it gives |
|---|---|
| ⭐⭐ **Reachability Analyzer** | ⭐⭐ **evaluates the actual config and names the blocking component** — no traffic sent |
| ⭐ **VPC Flow Logs** | ⭐ `ACCEPT`/`REJECT` per flow — **REJECT tells you an SG or NACL dropped it** |
| ⭐ SSM Session Manager | ⭐ a shell on a private instance with **no bastion, no port 22, no key** |
| `nc -zv` / `curl -v` | the two-second first test |
| Network Access Analyzer | proves nothing *unintended* is reachable |

⚠️ **Flow logs do not tell you which rule rejected the packet, only that it was rejected** — and NACL
rejections and SG rejections look identical. **Reachability Analyzer is the one that names the
component**, and it is the tool most people do not know exists.

# Part 4 — ⭐ Reaching private things as a human

| Option | ⭐ Verdict |
|---|---|
| ⭐⭐ **SSM Session Manager** | ⭐⭐ **the answer** — IAM-authorised, CloudTrail-audited, no inbound port, no key |
| ⭐ **SSM port forwarding** | ⭐ tunnel to RDS from your laptop **without a bastion** |
| ⭐ Bastion host | ⭐ a permanent internet-facing SSH box you must patch — **legacy** |
| VPN / Client VPN | fine for broad access; more moving parts |
| ⭐ Making RDS publicly accessible | ⭐⭐ **never** |

```bash
# ⭐⭐ Reach a private RDS from your laptop with no bastion and no open port:
aws ssm start-session --target i-0abc \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["mydb.xxxx.rds.amazonaws.com"],"portNumber":["5432"],"localPortNumber":["5432"]}'
```

> **⭐ This one command retires the bastion host.** Access is granted by IAM (revocable instantly),
> every session is in CloudTrail with the commands recorded if you enable logging, **and there is no
> port 22 open to the internet anywhere.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **CIDR-based SG rules instead of SG references** | ⭐⭐ breaks on scaling, AZ change or resubnetting |
| ⭐ Expecting a deny rule in a security group | ⭐ they are allow-only by design |
| ⭐⭐ **NACL deny without ephemeral-port allow** | ⭐⭐ silent one-way traffic; ~90% of NACL incidents |
| ⭐ Using NACLs as the primary control | ⭐ stateless and address-blind — use SGs |
| ⭐⭐ **No S3 gateway endpoint** | ⭐⭐ free money left on the table, and traffic leaves the network |
| ⭐ Adding every interface endpoint | ⭐ ~$22/month each across three AZs |
| ⭐ App bound to `127.0.0.1` in a container | ⭐⭐ refused, and you will blame the network for an hour |
| ⭐⭐ Guessing instead of working the checklist | ⭐ hours lost on step 5 when step 1 was the answer |
| ⭐ Not distinguishing timeout from refused | ⭐⭐ the fastest diagnostic in the stage, unused |
| ⭐ Reading flow logs expecting rule detail | they say REJECT, not which rule |
| ⭐⭐ **A bastion host in 2026** | ⭐⭐ SSM Session Manager replaced it |
| RDS marked publicly accessible "temporarily" | it stays that way, and it is scanned within minutes |

## Interview questions

**Q: Security group or network ACL — when do you use which?**
Security groups for essentially everything. They are stateful, so the return path is automatic, they
attach to the network interface rather than the subnet, and crucially they can reference another
security group. Network ACLs are stateless, subnet-level and can only see addresses, so they earn their
place in exactly one situation — a coarse deny across a whole subnet, since security groups have no deny
at all. My default is open NACLs and all the real work in security groups.

**Q: Why reference a security group rather than a CIDR?**
Because it expresses the intent instead of a snapshot. "The database accepts Postgres from the
application security group" stays true when the application scales from two tasks to fifty, moves
availability zone, or the subnets get resized — no rule is ever edited. It also makes the security
groups readable as the architecture: internet to the load balancer group, load balancer group to the
application group, application group to the database group, with no IP address named anywhere.

**Q: Someone added a NACL deny rule and now a service intermittently times out. What happened?**
Almost certainly the ephemeral port return path. NACLs are stateless, so allowing inbound 443 does not
allow the response out — the outbound rules must permit the high ports the client used. The symptom is a
timeout rather than a refusal, and it often looks intermittent because only some flows land on affected
subnets. The rule I keep is that if you add a deny to a NACL you write the ephemeral allow in the same
commit.

**Q: What is a VPC endpoint and why would you add one?**
It lets resources reach AWS services without traversing the internet. Gateway endpoints — S3 and
DynamoDB only — are route table entries and are free, so they remove that traffic from your NAT gateway
data processing charges entirely, which for a container workload pulling images is often the single
largest quick win on the bill. Interface endpoints put an ENI in your subnet for other services and cost
about a cent per hour per zone plus per gigabyte, so those are added deliberately. There is a security
argument too: an endpoint policy can restrict which buckets are reachable at all, which is a real
exfiltration control.

**Q: Walk me through debugging "the app cannot reach the database".**
In order, and without guessing. Is the process listening, and on `0.0.0.0` rather than loopback. Is
there a route, and is this subnet actually attached to the route table I think it is rather than the
main one. Does the database's security group allow the port from the application's security group. Does
the NACL allow both directions including ephemeral ports. Does the name resolve, and to a private
address — if it resolves publicly, DNS hostnames are disabled on the VPC. Before any of that, though, I
read the symptom: a timeout means something dropped the packet, a refusal means I reached the host and
nothing is listening. And Reachability Analyzer will name the blocking component without sending a
packet.

## Mini task

1. ⭐⭐ Rewrite every CIDR-based rule in your VPC as an **SG-to-SG reference.** Confirm the chain
   internet → ALB → app → db.
2. ⭐ Try to add a **deny** rule to a security group. Understand why you cannot.
3. ⭐⭐ Add a NACL deny **without** the ephemeral allow. **Reproduce the timeout**, then fix it.
4. ⭐ From a private instance, `curl` S3 and record it going via NAT. **Add the gateway endpoint** and
   confirm it now works with the NAT route removed.
5. ⭐ Add an **endpoint policy** restricting the S3 endpoint to one bucket. Prove another bucket fails.
6. ⭐⭐ Deliberately create a **timeout** and a **connection refused** and confirm you can tell them apart
   from the symptom alone.
7. ⭐⭐ Run **Reachability Analyzer** on a broken path and read which component it names.
8. ⭐ Enable **VPC Flow Logs**, find a `REJECT`, and note that it does not tell you which rule.
9. ⭐⭐ Connect to a private instance with **SSM Session Manager** — no bastion, no key, port 22 closed.
10. ⭐⭐ **Port-forward to your private RDS** through SSM and connect a local SQL client to it.

## 🎙️ Articulation drill

**Two minutes:** *"How do you control traffic inside a VPC?"*

**⭐ Lead with the design, not the feature list: security groups do all the work, and every rule
references another security group rather than an address range** — so the rules read as the call graph
and survive every scaling event without an edit. **NACLs stay open unless there is a specific coarse
deny to make, because they are stateless and the ephemeral-port mistake produces silent one-way
traffic.**

**⭐ Then close with the endpoint, because it is where security and cost agree: an S3 gateway endpoint is
free, keeps the traffic off the NAT gateway and inside the AWS network, and its endpoint policy can
limit which buckets are reachable at all.**
