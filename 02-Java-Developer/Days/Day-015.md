# Part 1 — L-015 · The rendering pipeline

## The whole pipeline

Days 012, 013 and 014 gave you the three inputs. This is where they meet.

```
  bytes ──▶ characters ──▶ tokens ──▶ nodes ──▶ ┌─────────┐
                                                │   DOM   │
                                                └────┬────┘
                                                     │
  CSS bytes ──▶ ... ──▶ ┌────────┐                   │
                        │ CSSOM  │───────────────────┤
                        └────────┘                   │
                                                     ▼
                                            ┌────────────────┐
                                            │  RENDER TREE   │  visible nodes + styles
                                            └───────┬────────┘
                                                    │
                                            ┌───────▼────────┐
                                            │     LAYOUT     │  geometry: where + how big
                                            │   ("reflow")   │
                                            └───────┬────────┘
                                                    │
                                            ┌───────▼────────┐
                                            │     PAINT      │  fill pixels into layers
                                            └───────┬────────┘
                                                    │
                                            ┌───────▼────────┐
                                            │   COMPOSITE    │  assemble layers (GPU)
                                            └────────────────┘
```

### 1. Parse HTML → DOM

Incremental — the browser builds and displays as bytes arrive, rather than waiting for the whole
document. It also repairs malformed markup as it goes (Day 012).

### 2. Parse CSS → CSSOM

Same idea, different tree: a tree of style rules with the cascade already resolved.

**CSS is render-blocking.** The browser will not paint until the CSSOM is complete — otherwise you'd
see a flash of unstyled content, then a jarring restyle. **This is why `<link rel="stylesheet">`
belongs in `<head>`**: start the download as early as possible, because nothing paints until it lands.

### 3. Render tree

DOM + CSSOM combined, containing **only what will be painted**.

Note the important distinction:

| | In the render tree? |
|---|---|
| `display: none` | **No** — not in the tree at all |
| `visibility: hidden` | **Yes** — occupies space, just not drawn |
| `opacity: 0` | **Yes** — occupies space, drawn transparently |
| `<head>`, `<script>` | No — never rendered |

This is why `display: none` and `visibility: hidden` behave differently in layout, and it's a
standard interview question.

### 4. Layout (reflow) — the expensive one

Compute the exact position and size of every box. Everything until now was abstract; this produces
coordinates.

**Layout is expensive because it cascades.** Change one element's width and every sibling and
descendant may need recomputing.

### 5. Paint

Fill in pixels — text, colours, borders, shadows, images — into one or more layers.

### 6. Composite

Assemble the layers, on the GPU. Cheap, and it's why the next section matters so much.

## The performance rule that follows

**Not all CSS changes cost the same.** Which stage a change triggers determines its cost:

| You change | Triggers | Cost |
|---|---|---|
| `width`, `height`, `top`, `left`, `margin`, `padding`, `font-size` | **Layout** → paint → composite | 💸💸💸 Expensive |
| `color`, `background`, `box-shadow`, `border-radius` | Paint → composite | 💸💸 Moderate |
| **`transform`, `opacity`** | **Composite only** | 💸 Cheap — GPU, off the main thread |

**This is the single most actionable thing on this page:**

```css
/* 💀 Animates layout on every frame. Janky. */
@keyframes slide-bad { from { left: 0; }  to { left: 300px; } }

/* ✅ Composite only. Smooth 60fps, runs on the compositor thread. */
@keyframes slide-good { from { transform: translateX(0); } to { transform: translateX(300px); } }
```

You already have "animate `transform` and `opacity` only" as a rule in
[`03-Web-Developer/02-Design-System.md`](../../03-Web-Developer/02-Design-System.md) and
[`04-App-Developer/02-Design-System.md`](../../04-App-Developer/02-Design-System.md). **This is why.**
`transform` skips layout *and* paint entirely and can run on the compositor thread — which means it
still animates smoothly even while the main JS thread is busy (Day 014).

## Layout thrashing — the JS trap

```js
// 💀 Forces a synchronous layout on EVERY iteration
for (const el of elements) {
  el.style.width = el.offsetWidth + 10 + 'px';
}
```

The browser batches style changes and flushes layout once, when it can. But **reading a geometric
property forces an immediate flush** so it can give you a correct answer. Write-then-read in a loop
forces layout every iteration — this is *layout thrashing*, or *forced synchronous layout*.

```js
// ✅ Batch reads, then batch writes
const widths = elements.map(el => el.offsetWidth);      // all reads
elements.forEach((el, i) => el.style.width = widths[i] + 10 + 'px');  // all writes
```

**Properties that force a flush:** `offsetTop/Left/Width/Height`, `clientTop/Left/Width/Height`,
`scrollTop/Left/Width/Height`, `getComputedStyle()`, `getBoundingClientRect()`.

## Where scripts block

```html
<script src="a.js"></script>              <!-- BLOCKS parsing: fetch, execute, resume -->
<script src="b.js" async></script>        <!-- fetch in parallel, execute ASAP, order not guaranteed -->
<script src="c.js" defer></script>        <!-- fetch in parallel, execute after parsing, IN ORDER -->
```

```
   Blocking:  ──parse──[ fetch ][ exec ]──parse──▶
   async:     ──parse────────────────────▶
                    [ fetch ][exec]           ← interrupts whenever it lands
   defer:     ──parse────────────────────▶ [exec]
                    [ fetch ]                 ← waits for parsing to finish
```

**Default to `defer`.** Use `async` only for independent scripts like analytics. A plain `<script>`
in `<head>` stalls the entire parse — and the reason is historical: the script might call
`document.write` and change what's being parsed.

## Core Web Vitals, mapped to the pipeline

| Metric | Measures | Pipeline stage |
|---|---|---|
| **LCP** < 2.5s | When the largest element paints | Parse → layout → paint |
| **CLS** < 0.1 | Unexpected layout shifts | Layout, re-running late |
| **INP** < 200ms | Responsiveness to input | Main thread availability (Day 014) |

**CLS is caused by layout running late** — an image without `width`/`height` reserves no space, so
everything jumps when it loads. **INP is a Day 014 problem** — a busy main thread can't respond. And
now both items on your performance checklist have a mechanism behind them.

## Type this yourself

```html
<!DOCTYPE html>
<html><head><style>
  .box { width: 100px; height: 100px; background: crimson; margin: 10px; }
  @keyframes bad  { from { margin-left: 0; }              to { margin-left: 400px; } }
  @keyframes good { from { transform: translateX(0); }    to { transform: translateX(400px); } }
  .bad  { animation: bad  2s infinite alternate; }
  .good { animation: good 2s infinite alternate; background: seagreen; }
</style></head>
<body>
  <div class="box bad"></div>
  <div class="box good"></div>
  <button id="thrash">Layout thrash (200 elements)</button>
  <button id="batch">Batched (200 elements)</button>
  <div id="host"></div>

<script>
  const host = document.getElementById('host');
  for (let i = 0; i < 200; i++) {
    const d = document.createElement('div');
    d.textContent = 'row ' + i;
    d.style.width = '100px';
    host.appendChild(d);
  }
  const rows = [...host.children];

  document.getElementById('thrash').onclick = () => {
    const t = performance.now();
    for (const el of rows) el.style.width = el.offsetWidth + 1 + 'px';   // read+write interleaved
    console.log('thrash:', (performance.now() - t).toFixed(1), 'ms');
  };

  document.getElementById('batch').onclick = () => {
    const t = performance.now();
    const widths = rows.map(el => el.offsetWidth);                       // all reads
    rows.forEach((el, i) => el.style.width = widths[i] + 1 + 'px');      // all writes
    console.log('batch: ', (performance.now() - t).toFixed(1), 'ms');
  };
</script>
</body></html>
```

**Three experiments:**

1. **Devtools → Performance → record 3 seconds.** Look at the flame chart. The `margin-left`
   animation shows purple **Layout** bars every frame; the `transform` one doesn't. That's the cost
   difference, visible.
2. **Click both buttons and compare the console timings.** Same work, often 5–20× different. That's
   layout thrashing measured on your own machine.
3. **Devtools → Rendering panel → tick "Paint flashing" and "Layout Shift Regions".** Green flashes
   show repaints. Watch which animation causes them.

## Common mistakes

| Mistake | Correction |
|---|---|
| Animating `left`/`top`/`width` | Triggers layout every frame. Use `transform`. |
| Reading geometry inside a write loop | Forces synchronous layout each iteration. Batch reads, then writes. |
| Plain `<script>` in `<head>` | Blocks parsing. Use `defer`. |
| Stylesheets at the end of `<body>` | CSS is render-blocking; late CSS delays first paint. Put it in `<head>`. |
| Images without dimensions | Content jumps when they load — that's CLS. |
| Confusing `display:none` and `visibility:hidden` | The first is absent from the render tree; the second occupies space. |

## Interview questions

**Q: Walk me through what the browser does between receiving HTML and showing pixels.**
> It parses HTML into the DOM incrementally and CSS into the CSSOM, combines them into a render tree
> of visible nodes with computed styles, runs layout to compute geometry, paints pixels into layers,
> and composites those layers on the GPU.

**Q: Why is `transform` cheaper to animate than `left`?**
> `left` changes geometry, so it forces layout, then paint, then composite, every frame. `transform`
> only affects compositing, so layout and paint are skipped and the work can happen on the compositor
> thread — meaning it stays smooth even when the main thread is busy.

**Q: What is layout thrashing?**
> Interleaving DOM writes with reads of geometric properties. Writes are normally batched and flushed
> once, but reading a property like `offsetWidth` forces an immediate synchronous layout so the value
> is correct. In a loop, this recomputes layout on every iteration. The fix is to batch all reads
> first, then all writes.

**Q: `async` vs `defer`?**
> Both download in parallel with parsing. `async` executes as soon as it downloads, interrupting the
> parse, with no ordering guarantee. `defer` executes after parsing completes, in document order.
> `defer` is the sensible default; `async` suits independent scripts like analytics.

**Q: Why is CSS render-blocking?**
> Painting before the CSSOM is complete would show unstyled content and then restyle it. The browser
> blocks the first paint until CSS is parsed, which is why stylesheets belong in `<head>`.

# Part 2 — C-10 · Cryptographic primitives

*Day 009 covered TLS. This is the layer underneath: the three operations, and which to reach for.
Day 112 (password storage) and Day 114 (JWT) both depend on getting this distinction right.*

## The three operations — never confuse them

| | Purpose | Reversible? | Key |
|---|---|---|---|
| **Hashing** | Fingerprint data | **No** — one-way | None |
| **Encryption** | Hide data | **Yes**, with the key | Symmetric or asymmetric |
| **Signing** | Prove origin + integrity | N/A — verify only | Private signs, public verifies |

**The most common security error in the world is using the wrong one.** "We encrypt passwords" is
wrong — encryption is reversible, so a breached key exposes every password. Passwords are **hashed**.

## Hashing

Arbitrary input → fixed-size output. Deterministic, one-way, avalanche (one bit in flips ~half the
bits out), collision-resistant.

```
  SHA-256("hello")  → 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
  SHA-256("hellp")  → 7d8f2b6c...    ← completely different
```

**Two different jobs, two different families — and this is the distinction that matters:**

| Purpose | Algorithm | Property wanted |
|---|---|---|
| Integrity / fingerprint | SHA-256, SHA-3, BLAKE3 | **Fast** |
| **Password storage** | **bcrypt, argon2, scrypt** | **Deliberately slow** |

**Why passwords need a slow hash:** SHA-256 does billions of hashes per second on a GPU. A breached
SHA-256 password database is cracked in hours. bcrypt with a work factor of 12 takes ~250 ms per
hash — imperceptible at login, catastrophic for an attacker trying billions.

- **Salt** — a unique random value per password, stored alongside it. Defeats rainbow tables and
  ensures two users with the same password get different hashes.
- **Pepper** — a secret value applied to all passwords, stored separately from the database. A
  database-only breach then yields nothing.
- **Work factor** — the cost knob. Raise it as hardware gets faster.

**Never use MD5 or SHA-1** — both are broken for collision resistance. And never use a fast hash for
passwords, even with a salt.

This is Day 112, and it's on your security checklist as "passwords hashed with bcrypt/argon2 — never
plain, never MD5/SHA1". Now you know why each half of that sentence is there.

## Encryption

| | Symmetric | Asymmetric |
|---|---|---|
| Keys | One shared | Public + private |
| Speed | Fast | ~1000× slower |
| Example | AES-256-GCM | RSA, ECC |
| Problem solved | Bulk data | Key distribution, identity |

**Always prefer authenticated encryption (AEAD)** — AES-GCM or ChaCha20-Poly1305. Plain AES-CBC
encrypts but doesn't detect tampering; an attacker can flip bits in the ciphertext and you'd never
know. AEAD gives confidentiality *and* integrity in one primitive.

## MACs and signatures

Both prove integrity and origin. The difference is who can verify.

| | HMAC | Digital signature |
|---|---|---|
| Key | One shared secret | Private signs, public verifies |
| Who can verify | Only those with the secret | **Anyone** |
| Non-repudiation | No — either party could have made it | **Yes** — only the private key holder could |
| Speed | Fast | Slow |
| Example | HMAC-SHA256 | RSA-PSS, ECDSA, Ed25519 |

### This is exactly the JWT question (Day 114)

```
   HS256  = HMAC-SHA256      → one shared secret. Anyone who can VERIFY can also FORGE.
   RS256  = RSA signature    → private key signs; anyone with the public key can verify only.
```

**When does the difference matter?** If one service issues tokens and five services verify them:
with HS256 all six hold the same secret, so any one of them — or anyone who breaches any one of them
— can mint tokens. With RS256 only the issuer holds the private key. **That's the answer to "HS256
or RS256?" and it's a good one.**

And the `alg: none` attack: early JWT libraries honoured an `alg` header of `none` and skipped
verification entirely, so an attacker could strip the signature and be trusted. Never let the token
choose its own algorithm — pin it server-side.

## Random numbers

```java
new Random()                    // ❌ predictable — NEVER for security
new SecureRandom()              // ✅ cryptographically secure
```

```js
Math.random()                                  // ❌ never for security
crypto.getRandomValues(new Uint8Array(32))     // ✅
```

Session tokens, password reset tokens, salts, idempotency keys — all need CSPRNG. A predictable
reset token means anyone can take over an account.

## Type this yourself

```java
import java.security.*;
import javax.crypto.*;
import javax.crypto.spec.*;
import java.util.*;

public class CryptoPrimitives {
    public static void main(String[] args) throws Exception {
        // 1. Hashing — one-way, deterministic, avalanche
        MessageDigest sha = MessageDigest.getInstance("SHA-256");
        System.out.println("hello -> " + hex(sha.digest("hello".getBytes())));
        sha.reset();
        System.out.println("hellp -> " + hex(sha.digest("hellp".getBytes())));
        System.out.println("(one letter changed, completely different output)\n");

        // 2. HMAC — needs the secret to verify OR to forge
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec("shared-secret".getBytes(), "HmacSHA256"));
        System.out.println("HMAC  -> " + hex(mac.doFinal("message".getBytes())) + "\n");

        // 3. Signature — private signs, public verifies, only the holder can sign
        KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
        kpg.initialize(2048);
        KeyPair kp = kpg.generateKeyPair();

        Signature signer = Signature.getInstance("SHA256withRSA");
        signer.initSign(kp.getPrivate());
        signer.update("message".getBytes());
        byte[] sig = signer.sign();

        Signature verifier = Signature.getInstance("SHA256withRSA");
        verifier.initVerify(kp.getPublic());     // public key — verify only
        verifier.update("message".getBytes());
        System.out.println("Signature valid: " + verifier.verify(sig));

        verifier.initVerify(kp.getPublic());
        verifier.update("tampered".getBytes());
        System.out.println("Tampered valid:  " + verifier.verify(sig));

        // 4. Secure randomness
        byte[] token = new byte[32];
        SecureRandom.getInstanceStrong().nextBytes(token);
        System.out.println("\nToken: " + Base64.getUrlEncoder().withoutPadding().encodeToString(token));
    }

    static String hex(byte[] b) {
        StringBuilder sb = new StringBuilder();
        for (byte x : b) sb.append(String.format("%02x", x));
        return sb.toString();
    }
}
```

**Notice what you proved:** the public key verifies but cannot sign. That asymmetry is the entire
basis of certificates (Day 009) and RS256 JWTs (Day 114).

## Interview questions

**Q: Should passwords be encrypted or hashed?**
> Hashed, with a deliberately slow algorithm — bcrypt, scrypt or argon2 — plus a unique per-password
> salt. Encryption is reversible, so compromising the key exposes every password. Hashing is one-way,
> and slowness makes brute-forcing a stolen database impractical.

**Q: Why not SHA-256 for passwords?**
> It's designed to be fast — billions of hashes per second on a GPU — which is exactly what an
> attacker wants. Password hashes need a tunable work factor so verification is fast enough for one
> login and prohibitively slow for a brute-force attempt.

**Q: HMAC vs digital signature?**
> HMAC uses one shared secret, so anyone who can verify can also forge, and it provides no
> non-repudiation. A digital signature uses a private key to sign and a public key to verify, so
> anyone can verify while only the key holder can sign.

**Q: HS256 or RS256 for a JWT?**
> HS256 is simpler and faster, and is fine when the same service issues and verifies. If multiple
> services verify tokens, RS256 is better — they only need the public key, so a compromise of a
> verifying service can't mint tokens. Also, always pin the algorithm server-side rather than trusting
> the token's `alg` header.

**Q: What is a salt and what does it defend against?**
> A unique random value stored with each password hash. It ensures identical passwords hash
> differently and defeats precomputed rainbow tables, forcing an attacker to crack each password
> individually.
