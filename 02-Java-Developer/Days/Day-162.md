# Day 162

**L-162** · The persistence context — dirty checking, the entity lifecycle, and flush order

**Time:** 3 hrs · **Mode:** NEW

> **The mechanism day of the Data block**, and the counterpart to Day 132. Once you can name the four
> entity states and say when a flush happens, then "why did my change get saved when I never called
> `save()`?", "why did my change *not* get saved?", "why did the update run before the insert?" and
> "why does my bulk update leave stale objects?" all resolve to the same picture.
>
> The persistence context is a **first-level cache with automatic change detection**, and almost
> every JPA surprise is one of those two properties doing exactly what it promised.

# Part 1 — The four states

```
                 new Order()
                      │
                 ┌────▼─────┐  persist()   ┌───────────┐   flush/commit
                 │ TRANSIENT ├─────────────►│  MANAGED  ├───────────────► DB
                 └──────────┘               └─────┬─────┘
                                    detach() /    │    remove()
                                    close() /     │
                                    clear()       │
                                  ┌───────────┐   │   ┌──────────┐
                                  │ DETACHED  │◄──┘   │ REMOVED  │
                                  └─────┬─────┘       └──────────┘
                                        │  merge()  → returns a MANAGED copy
                                        └──────────────────────►
```

| State | Meaning |
|---|---|
| **Transient** | a new object. No id, unknown to Hibernate |
| ⭐ **Managed** | in the persistence context. **Changes are tracked and written automatically** |
| **Detached** | was managed; the context closed. Changes are *not* tracked |
| **Removed** | marked for deletion at flush |

## ⭐ The behaviour that surprises everyone

```java
@Transactional
public void applyDiscount(Long orderId) {
    Order order = repo.findById(orderId).orElseThrow();
    order.setTotal(order.getTotal().multiply(new BigDecimal("0.9")));
    // ⭐ no save(). No update(). Nothing.
}                                       // → UPDATE orders SET total = ? WHERE id = ?
```

**The UPDATE runs anyway**, because the entity is *managed*. On commit, Hibernate compares the object
against the snapshot it took at load time and writes the difference. That is **dirty checking**, and
it is the ORM's most valuable feature and its most surprising one.

**The corollary is more dangerous:**

```java
@Transactional
public OrderResponse get(Long id) {
    Order order = repo.findById(id).orElseThrow();
    order.setStatus(OrderStatus.VIEWED);       // ⚠️ "just for the response"
    return OrderResponse.from(order);
}                                               // ⭐ that is now PERSISTED
```

**Any mutation of a managed entity inside a transaction is a database write.** A field set for
display, a normalisation "just for this response", a `setX` inside a mapper — all of them hit the
database. Every accidental-data-modification bug in JPA is this one.

**`readOnly = true` is the guard**, and it earns its place here as much as in Day 156: Hibernate sets
the flush mode to `MANUAL` and skips dirty checking entirely, so an accidental mutation is silently
discarded rather than persisted.

# Part 2 — Flush, and why order matters

**A flush writes pending changes to the database; a commit ends the transaction.** They are not the
same, and the gap between them is where several bugs live.

**Hibernate flushes automatically at three moments:**

1. **before a query** that overlaps unflushed changes — so your query sees your own writes;
2. **on commit**;
3. when you call `flush()`.

## ⭐ The write order is fixed, and it is not your call order

Hibernate orders statements at flush by **operation type**, not by the sequence in which you wrote
the code:

```
1. inserts
2. updates
3. collection deletions
4. collection inserts
5. deletions          ⭐ last
```

```java
@Transactional
public void replace(Long id, Order replacement) {
    repo.delete(existing);            // you wrote delete first
    repo.save(replacement);           // then insert
}                                     // ⭐ Hibernate runs the INSERT first → unique constraint violation
```

**You expected delete-then-insert; you got insert-then-delete, and a constraint violation on a value
that was about to be free.** The fix is an explicit `flush()` between them — which is the one
legitimate everyday use of manual flushing.

## `persist` vs `merge` vs `save`

| Call | Behaviour |
|---|---|
| `persist(e)` | transient → managed. **Makes the passed object managed.** Fails on a detached entity |
| `merge(e)` | ⭐ **copies state into a managed instance and returns it.** The argument stays detached |
| Spring Data `save(e)` | `persist` if the id is null, otherwise `merge` |

**⭐ The `merge` trap:**

```java
Order detached = ...;
em.merge(detached);
detached.setStatus(SHIPPED);           // ❌ modifies the DETACHED object — not saved

Order managed = em.merge(detached);    // ⭐ use the RETURN VALUE
managed.setStatus(SHIPPED);            // ✅ tracked
```

**Always use `save()`'s return value.** The one you passed in may not be the managed one, and the
resulting bug — a change that silently does not persist — is indistinguishable from the Day 159
owning-side bug at first glance.

**And `merge` costs a SELECT**: to copy state into a managed instance, Hibernate must load the
current row first. Updating 1,000 detached entities via `merge` is 1,000 selects plus 1,000 updates.
Loading them managed and mutating them is 1 select plus batched updates.

# Part 3 — The first-level cache, and its two sharp edges

**The persistence context is a `Map<EntityKey, Object>` scoped to the transaction.**

```java
Order a = repo.findById(1L).get();     // ⭐ SELECT
Order b = repo.findById(1L).get();     // ⭐ no SELECT — served from the context
assert a == b;                         // ⭐⭐ reference equality, guaranteed
```

**`a == b` is a real guarantee**: within one persistence context there is exactly one object per
database row. This is what makes dirty checking coherent, and it is why Day 158's `equals` discussion
matters less inside a transaction than across one.

### ⭐ Edge 1 — it grows without bound

Every entity you load stays until the transaction ends. A batch job touching 500,000 rows in one
transaction holds 500,000 entities **plus 500,000 snapshots**. Then `OutOfMemoryError`.

```java
if (++count % 500 == 0) { em.flush(); em.clear(); }     // ⭐ Day 161's line, explained
```

`flush()` writes pending changes; `clear()` detaches everything and releases it. **Both are needed** —
`clear()` alone discards unwritten changes silently.

### ⭐ Edge 2 — bulk operations bypass it entirely

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)     // ⭐ both
@Query("update Order o set o.status = :new where o.status = :old")
int bulkUpdate(@Param("new") OrderStatus n, @Param("old") OrderStatus o);
```

**A bulk JPQL update goes straight to the database.** It does not update entities already in the
persistence context, and it does not fire lifecycle callbacks or `@Version` increments.

```java
Order order = repo.findById(1L).get();          // status = PENDING, now managed
repo.bulkUpdate(SHIPPED, PENDING);              // ⭐ database row is now SHIPPED
order.getStatus();                              // ⭐⭐ still PENDING — stale
order.setTotal(newTotal);                       // ⭐ dirty check writes ALL fields, including
                                                //   status = PENDING — silently reverting the bulk update
```

**The last line is the real damage**: a stale managed entity writes its stale field values back. That
is why `clearAutomatically = true` matters, and why `flushAutomatically = true` matters too — without
it, pending changes flush *after* the bulk statement and overwrite it.

**And note `@Version` is not incremented by a bulk update**, so optimistic locking (Day 165) is
bypassed for those rows. Bulk operations are the right tool for large data changes and they are
outside the ORM's guarantees; use them deliberately.

# Part 4 — Lifecycle callbacks, and where they must not be used

```java
@Entity
public class Order {
    @PrePersist  void onCreate() { this.placedAt = Instant.now(); }
    @PreUpdate   void onUpdate() { this.updatedAt = Instant.now(); }
    @PostLoad    void afterLoad() { this.displayTotal = total.setScale(2); }
}
```

| Callback | Fires |
|---|---|
| `@PrePersist` / `@PostPersist` | around insert |
| `@PreUpdate` / `@PostUpdate` | around update — ⭐ **only if something is dirty** |
| `@PreRemove` / `@PostRemove` | around delete |
| `@PostLoad` | after load |

**Three rules, each with a real failure behind it:**

1. ⭐ **No database access inside a callback.** You are inside Hibernate's flush; issuing a query
   triggers a nested flush and the behaviour is undefined — in practice, a `ConcurrentModificationException`
   or a silent loss.
2. ⭐ **No external calls.** An email sent from `@PostPersist` is sent even if the transaction then
   rolls back. Day 124's dual-write, again — and Day 133's `@TransactionalEventListener(AFTER_COMMIT)`
   is the correct tool.
3. **Callbacks do not fire for bulk operations or native SQL.** Auditing that depends on `@PreUpdate`
   silently has holes wherever bulk statements are used. Day 165's auditing uses this machinery, so
   the hole is worth knowing about.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Mutating a managed entity "just for the response" | it is a database write |
| No `readOnly = true` on reads | accidental mutations persist; dirty checking runs on every row |
| Expecting `flush()` to commit | it writes; the transaction is still open and can roll back |
| Assuming statement order matches call order | insert-before-delete constraint violations |
| Ignoring `merge`'s return value | changes silently not saved |
| `merge` in a loop | one SELECT per entity |
| Loading 500k entities in one transaction | OOM from entities plus snapshots |
| `clear()` without `flush()` | pending changes discarded silently |
| Bulk update without `clearAutomatically` | stale entities overwrite the bulk change on next flush |
| Expecting `@Version` to increment on a bulk update | optimistic locking bypassed |
| Querying inside a lifecycle callback | undefined behaviour mid-flush |
| Sending email from `@PostPersist` | fires even if the transaction rolls back |
| Auditing only via callbacks | bulk and native operations leave no audit trail |

## Interview questions

**Q: Why does an entity change persist without calling `save()`?**
Because the entity is managed and Hibernate snapshots every field at load. At flush it compares
object to snapshot and writes the difference. The dangerous corollary is that *any* mutation inside a
transaction is a write, including one made "just for the response" — which is why read paths get
`readOnly = true`.

**Q: `persist` vs `merge`?**
`persist` makes the passed transient object managed. `merge` copies state into a managed instance and
**returns it** — the argument stays detached, so ignoring the return value means changes silently do
not save. `merge` also costs a select per entity, so bulk updates via `merge` are slow.

**Q: What does a bulk JPQL update not do?**
It does not update entities already in the persistence context, does not fire lifecycle callbacks,
and does not increment `@Version`. A stale managed entity can then write its old field values back
over the bulk change, so `clearAutomatically` and `flushAutomatically` are both required.

**Q: You delete then insert and get a unique constraint violation. Why?**
Hibernate orders statements by operation type at flush — inserts first, deletes last — regardless of
call order. An explicit `flush()` between them enforces the order you intended.

1. Load an entity in `@Transactional`, mutate it, call nothing, and confirm the UPDATE in the SQL log.
2. Add `readOnly = true` and repeat. Confirm no UPDATE.
3. `findById` the same id twice; confirm one SELECT and `a == b`.
4. Delete then save a row with the same unique value. Get the violation. Insert `em.flush()` between.
5. `merge` a detached entity, mutate the *argument*, commit. Confirm nothing saved. Use the return
   value instead.
6. Update 1,000 detached entities via `merge`; count selects. Then load and mutate them managed;
   count again.
7. Load 200,000 entities in one transaction and watch the heap. Add `flush()`/`clear()` every 500.
8. Load an entity, run a bulk update on it, then mutate one other field and commit. **Read the
   database and find your bulk update reverted.** Add `clearAutomatically = true`.

## 🎙️ Articulation drill

Two minutes: **"What is the persistence context?"**

A transaction-scoped first-level cache with automatic change detection — one object per row, and a
snapshot per object. Then derive the consequences rather than listing them: changes save without
`save()` because of dirty checking, which means an accidental mutation is a write, which is why reads
are `readOnly`. It grows unbounded, which is why a batch job must flush and clear. And bulk updates
bypass it entirely, which is why a stale managed entity can silently overwrite one. Close on the flush
ordering, because inserts-before-deletes catches almost everyone once.
