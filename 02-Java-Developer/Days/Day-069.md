# Part 1 — L-069 · Executors

## The abstraction

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

Future<Integer> f = pool.submit(() -> expensive());     // Callable → Future
Integer result = f.get();                                // blocks until done

pool.shutdown();                                         // no new tasks; finish existing
pool.awaitTermination(30, TimeUnit.SECONDS);
```

The point is **decoupling task submission from thread management**. You describe *what* to run; the
pool decides *where* and *when*. That gives you thread reuse (no creation cost per task), a bound on
concurrency, a queue for backpressure, and a lifecycle you can shut down cleanly.

## `ThreadPoolExecutor` — the seven parameters

Every `Executors.newXxx()` factory is a preset of one constructor. Learn the constructor and the
factories become obvious:

```java
new ThreadPoolExecutor(
    corePoolSize,        // threads kept alive even when idle
    maximumPoolSize,     // hard ceiling
    keepAliveTime, unit, // how long an above-core idle thread survives
    workQueue,           // where tasks wait
    threadFactory,       // naming, daemon status, uncaught handler
    rejectedExecutionHandler);
```

**The submission algorithm is the thing to memorise**, because it is counter-intuitive and it is
asked constantly:

```
task arrives
   │
   ├─ threads < corePoolSize?          → create a new thread. (Even if others are idle.)
   │
   ├─ else: can the QUEUE accept it?   → enqueue it.
   │
   ├─ else: threads < maximumPoolSize? → create a new thread.
   │
   └─ else                             → REJECT (RejectedExecutionHandler)
```

> **The queue fills before the pool grows past core.**

That ordering is the source of the single most common production surprise: with an **unbounded**
queue, the queue can *never* be full, so `maximumPoolSize` is **dead configuration** — the pool
never exceeds core size no matter what you set. `newFixedThreadPool` is exactly this: core = max,
unbounded `LinkedBlockingQueue`. And that unbounded queue is also an `OutOfMemoryError` waiting to
happen, because it will absorb tasks until the heap is gone.

## The factory presets, and which are traps

| Factory | core / max | queue | Verdict |
|---|---|---|---|
| `newFixedThreadPool(n)` | n / n | unbounded | ⚠️ queue can OOM |
| `newSingleThreadExecutor()` | 1 / 1 | unbounded | ⚠️ same, but serial execution is often exactly right |
| `newCachedThreadPool()` | 0 / **`Integer.MAX_VALUE`** | `SynchronousQueue` (holds nothing) | 💀 unbounded *threads* |
| `newScheduledThreadPool(n)` | n / max | delayed queue | fine for scheduling |
| `newVirtualThreadPerTaskExecutor()` | — | — | Java 21; Day 072 |

`newCachedThreadPool` deserves the skull. Its queue holds zero elements, so by the algorithm above
every task that finds no idle thread creates a new one — without limit. A traffic spike creates
thousands of threads and the JVM dies with `OutOfMemoryError: unable to create native thread`.

**Write the constructor yourself:**

```java
ExecutorService pool = new ThreadPoolExecutor(
        8, 16,
        60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),                 // BOUNDED — backpressure
        new ThreadFactoryBuilder().setNameFormat("orders-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy());     // push back on the submitter
```

Two of those choices are load-bearing.

**A bounded queue is backpressure.** When it fills, the system must say "no" — and saying no loudly
(a 503, a rejection) is infinitely better than absorbing work you cannot do and dying later with a
heap dump nobody can read.

**Name your threads.** `pool-1-thread-3` tells you nothing in a thread dump at 3 AM; `orders-3`
tells you which subsystem is stuck. This costs one line and repays it the first time you debug a
hang.

The four rejection policies:

| Policy | Behaviour |
|---|---|
| `AbortPolicy` (default) | throws `RejectedExecutionException` |
| `CallerRunsPolicy` | the **submitting thread** runs the task — natural throttling |
| `DiscardPolicy` | silently drops it 💀 |
| `DiscardOldestPolicy` | drops the oldest queued task 💀 |

`CallerRunsPolicy` is the elegant one: the submitter is now busy executing, so it stops submitting,
and the pressure propagates upstream by itself. The two discard policies lose work silently — use
only where the work is genuinely disposable, like a metrics sample.

## Sizing a pool — arithmetic, not folklore

**CPU-bound work:**

```
threads ≈ number of cores        (+1 to cover the occasional page fault)
```

More threads than cores does not create more CPU; it creates context switches (Day 033's B-04).

**I/O-bound work** — Brian Goetz's formula:

```
threads = cores × targetUtilisation × (1 + waitTime / serviceTime)
```

Worked example: 8 cores, 90% target, a call that waits 100 ms on the network and burns 5 ms of CPU:

```
8 × 0.9 × (1 + 100/5) = 8 × 0.9 × 21 ≈ 151 threads
```

That number surprises people, and it is the honest answer for a blocking I/O workload: threads spend
95% of their life asleep, so you need many of them to keep 8 cores busy. It is also **the argument
for virtual threads** — 151 platform threads cost ~151 MB of stack and a busy scheduler, while
151,000 virtual threads cost almost nothing (Day 072).

**Separate pools for separate workloads.** One pool for CPU work, one per external dependency. If
the payment provider gets slow, it should exhaust *its* pool, not starve your entire application —
this is the **bulkhead** pattern, and it is the same reasoning as separating an event loop from a
blocking scheduler (Day 067's B-14).

## `Future` and its limits

```java
Future<Integer> f = pool.submit(() -> compute());
if (!f.isDone()) { /* … */ }
Integer v = f.get(5, TimeUnit.SECONDS);      // ALWAYS use the timeout overload
f.cancel(true);                              // true = interrupt if running
```

`Future` has four problems, and every one of them is why `CompletableFuture` exists:

1. **`get()` blocks.** There is no callback — you can only wait, which defeats the purpose.
2. **No composition.** You cannot say "when this finishes, do that" without blocking first.
3. **No combination.** Waiting for two futures means blocking on each in turn.
4. **No manual completion.** You cannot wrap a callback-based API in one.

Also note `get()` wraps any task exception in an `ExecutionException`; the real cause is in
`getCause()`. And **an exception thrown by a task submitted with `submit()` is swallowed until
someone calls `get()`** — a task can fail silently forever if you ignore the returned `Future`. Use
`execute()` with an `UncaughtExceptionHandler`, or always inspect the future.

## `CompletableFuture`

```java
CompletableFuture
    .supplyAsync(() -> fetchUser(id), pool)              // ALWAYS pass your own executor
    .thenApply(User::email)                              // transform          (map)
    .thenCompose(email -> lookupPrefs(email))            // chain another CF   (flatMap)
    .thenCombine(fetchOrders(id), Summary::new)          // join two
    .exceptionally(ex -> Summary.empty())                // recover
    .thenAccept(this::render)                            // consume
    .orTimeout(2, TimeUnit.SECONDS);                     // Java 9+
```

Two things to fix in your head immediately.

**`thenApply` vs `thenCompose` is `map` vs `flatMap`** (Day 059). If your function returns a plain
value, `thenApply`. If it returns another `CompletableFuture`, `thenCompose` — otherwise you get
`CompletableFuture<CompletableFuture<T>>` and the nesting compounds.

**Always pass an executor.** Without one, `supplyAsync` and every `*Async` method use the
`ForkJoinPool.commonPool()`, whose parallelism is `cores - 1`. On a 2-core container that is **one
thread**, shared with every parallel stream in the JVM (Day 060). One blocking call in there stalls
everything unrelated. This is the same common-pool hazard, now on the async side.

The `*Async` suffix controls *where* the continuation runs: `thenApply` may run on the completing
thread (or the caller, if already complete); `thenApplyAsync` always hands off to the executor.

## Composition patterns worth memorising

```java
// Fan-out then join — the canonical parallel-fetch shape
List<CompletableFuture<Item>> futures = ids.stream()
        .map(id -> CompletableFuture.supplyAsync(() -> fetch(id), pool))
        .toList();                                        // ← materialise FIRST: starts them all

CompletableFuture<Void> all = CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]));

List<Item> items = all.thenApply(v ->
        futures.stream().map(CompletableFuture::join).toList()).join();
```

The `.toList()` is not stylistic. Streams are lazy (Day 059) — without materialising, the futures are
created and joined one at a time and you have written a sequential program that looks parallel. That
is a genuine and very common bug.

```java
// First one wins (hedged request)
CompletableFuture.anyOf(primary, replica).thenAccept(this::use);

// Timeout with a fallback value
cf.completeOnTimeout(FALLBACK, 500, TimeUnit.MILLISECONDS);

// Handle both outcomes in one place
cf.handle((value, ex) -> ex != null ? fallback(ex) : value);
```

`allOf` returns `CompletableFuture<Void>` — it signals completion, it does not collect results; you
still join each future afterwards (they are complete by then, so `join` does not block).
`exceptionally` handles only the failure path; `handle` sees both; `whenComplete` observes both
without changing the value.

## Code to type

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.stream.*;

public class PoolDemo {

    public static void main(String[] args) throws Exception {
        // 1. The submission algorithm, made visible
        ThreadPoolExecutor p = new ThreadPoolExecutor(
                2, 4, 1, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(2),
                r -> { Thread t = new Thread(r); t.setName("demo-" + t.getId()); return t; },
                new ThreadPoolExecutor.AbortPolicy());

        for (int i = 1; i <= 8; i++) {
            final int n = i;
            try {
                p.submit(() -> {
                    System.out.printf("task %d on %s%n", n, Thread.currentThread().getName());
                    try { Thread.sleep(500); } catch (InterruptedException ignored) {}
                });
                System.out.printf("submitted %d  pool=%d queue=%d%n",
                        n, p.getPoolSize(), p.getQueue().size());
            } catch (RejectedExecutionException e) {
                System.out.printf("task %d REJECTED (pool=%d queue=%d)%n",
                        n, p.getPoolSize(), p.getQueue().size());
            }
        }
        p.shutdown();
        p.awaitTermination(10, TimeUnit.SECONDS);

        // 2. Sequential vs parallel fetch
        ExecutorService io = Executors.newFixedThreadPool(10);
        List<Integer> ids = IntStream.rangeClosed(1, 10).boxed().toList();

        long t0 = System.currentTimeMillis();
        ids.forEach(PoolDemo::fetch);
        System.out.println("sequential: " + (System.currentTimeMillis() - t0) + " ms");

        t0 = System.currentTimeMillis();
        List<CompletableFuture<String>> fs = ids.stream()
                .map(id -> CompletableFuture.supplyAsync(() -> fetch(id), io))
                .toList();                                     // materialise!
        CompletableFuture.allOf(fs.toArray(new CompletableFuture[0])).join();
        System.out.println("parallel:   " + (System.currentTimeMillis() - t0) + " ms");

        // 3. Composition and failure
        CompletableFuture<String> cf = CompletableFuture
                .supplyAsync(() -> { throw new IllegalStateException("boom"); }, io)
                .thenApply(s -> s + " never runs")
                .exceptionally(ex -> "recovered from " + ex.getCause().getMessage());
        System.out.println(cf.join());

        // 4. Silent failure with submit()
        Future<?> ignored = io.submit(() -> { throw new RuntimeException("nobody sees me"); });
        Thread.sleep(200);
        System.out.println("still here — the exception is trapped in the Future");

        io.shutdown();
    }

    static String fetch(int id) {
        try { Thread.sleep(300); } catch (InterruptedException ignored) {}
        return "item-" + id;
    }
}
```

Predict section 1 before running: **with core 2, queue 2 and max 4, which task number is the first
to be rejected?** Trace the algorithm — 2 threads, then 2 queued, then 2 more threads, so tasks 1–6
are accepted and task 7 is the first rejection. Watching the printed pool/queue sizes confirm your
trace is the exercise.

Section 2 should show ~3000 ms versus ~300 ms. Section 4 is the silent-failure demonstration —
remember it.

## Shutdown, done properly

```java
pool.shutdown();                                   // stop accepting; let queued tasks finish
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    List<Runnable> dropped = pool.shutdownNow();   // interrupt running tasks
    log.warn("{} tasks never started", dropped.size());
    if (!pool.awaitTermination(10, TimeUnit.SECONDS))
        log.error("pool did not terminate");
}
```

`shutdownNow()` **interrupts** running threads — which only works if your tasks handle interruption
correctly (Day 064). A task that swallows `InterruptedException` (Day 062) will ignore
`shutdownNow` entirely and your JVM will not exit. That is the chain of three days paying off in one
line.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `newCachedThreadPool` under load | Unbounded threads; native OOM |
| Unbounded queue | Heap OOM; `maximumPoolSize` is ignored |
| Expecting the pool to grow before the queue fills | Wrong mental model; wrong sizing |
| Unnamed threads | Unreadable thread dumps |
| No executor passed to `supplyAsync` | Runs on the shared common pool |
| `thenApply` where `thenCompose` belongs | Nested futures |
| Not materialising the stream before `allOf` | Sequential execution disguised as parallel |
| `get()` without a timeout | Indefinite hang |
| Ignoring the `Future` from `submit` | Exceptions vanish |
| One pool for everything | One slow dependency starves the whole app |
| Never shutting down | JVM will not exit (non-daemon threads) |

## Interview questions

**Q: Walk me through what `ThreadPoolExecutor` does when a task is submitted.**
Below core size, create a thread even if others are idle. Otherwise try to queue. If the queue is
full and we are below max, create a thread. Otherwise reject. The key consequence is that an
unbounded queue makes `maximumPoolSize` meaningless.

**Q: How do you size a thread pool?**
CPU-bound: about the core count. I/O-bound: `cores × utilisation × (1 + wait/service)`, which for a
100 ms call with 5 ms of CPU on 8 cores is roughly 150. Then measure, and use separate pools per
dependency.

**Q: Why is `newFixedThreadPool` risky?**
Its unbounded queue absorbs work indefinitely, so overload becomes an `OutOfMemoryError` instead of
a rejection. A bounded queue plus `CallerRunsPolicy` gives you backpressure.

**Q: `Future` vs `CompletableFuture`?**
`Future` only blocks. `CompletableFuture` composes — transform, chain, combine, recover, time out —
and can be completed manually, which lets you adapt callback APIs.

**Q: `thenApply` vs `thenCompose`?**
`map` vs `flatMap`. Use `thenCompose` when the function itself returns a `CompletableFuture`.

**Q: What is the common-pool hazard?**
`*Async` methods and parallel streams default to `ForkJoinPool.commonPool()` with `cores - 1`
threads, shared JVM-wide. One blocking task there stalls unrelated work; on a small container it can
be a single thread.

**Q: How do you shut a pool down?**
`shutdown()`, `awaitTermination`, then `shutdownNow()` if needed — and `shutdownNow` only works if
tasks respond to interruption.

Two minutes: **"How would you configure a thread pool for a service that calls a slow external
API?"**

Bounded queue, explicit core/max, the sizing formula with real numbers, a dedicated pool for that
dependency, `CallerRunsPolicy` or an explicit rejection mapped to 503, named threads, and a proper
shutdown sequence. Every element is a decision you can defend — that is what makes it senior.
