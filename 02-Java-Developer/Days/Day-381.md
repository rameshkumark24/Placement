# Day 381

**L-381** · IAM I — policies, evaluation logic and least privilege

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ IAM is not a permissions system with a deny list. It is a system where everything is denied
> and you are building the one narrow path that is allowed.**
>
> Today: the five-line policy anatomy, **the evaluation order that decides every single API call**, why
> SCPs and permission boundaries grant nothing, and **`iam:PassRole` — the privilege escalation that is
> in almost every over-permissive account.**

---

# Part 1 — ⭐ Anatomy of a policy

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ReadAppUploads",
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::my-app-uploads",
      "arn:aws:s3:::my-app-uploads/*"
    ],
    "Condition": { "StringEquals": { "aws:PrincipalOrgID": "o-abc123" } }
  }]
}
```

| ⭐ Element | ⭐ Question it answers |
|---|---|
| ⭐ **Effect** | ⭐ Allow or **Deny** |
| ⭐ **Action** | ⭐ which API calls — `service:Operation` |
| ⭐⭐ **Resource** | ⭐⭐ **which ARNs** — the part people wildcard out of fatigue |
| ⭐⭐ **Condition** | ⭐⭐ **under what circumstances** — the most under-used and most powerful element |
| Principal | ⭐ *only* in resource-based policies — who is being allowed |

⚠️ **Note the two ARNs for one bucket.** `arn:aws:s3:::bucket` is the bucket itself (for `ListBucket`);
`arn:aws:s3:::bucket/*` is the objects (for `GetObject`). **Listing a bucket and reading its objects are
different resources, and getting this wrong is the single most common S3 policy bug.**

## ⭐ Conditions are where least privilege actually lives

| ⭐ Condition key | ⭐ What it buys |
|---|---|
| ⭐⭐ `aws:PrincipalOrgID` | ⭐⭐ **only principals in my organisation** — kills most cross-account leaks |
| ⭐ `aws:SourceIp` / `aws:SourceVpce` | only from my network or my VPC endpoint |
| ⭐⭐ `aws:SecureTransport` | ⭐ **deny plain HTTP** — a one-line hardening every bucket should have |
| ⭐ `aws:RequestTag` / `aws:ResourceTag` | ⭐ tag-based access control (ABAC) |
| ⭐ `aws:MultiFactorAuthPresent` | ⭐⭐ require MFA for destructive actions |
| `s3:x-amz-server-side-encryption` | refuse unencrypted uploads |

> **⭐ A policy with `Resource: "*"` and a tight `Condition` is often far safer than a policy with a
> specific ARN and no condition** — because the condition constrains *who and from where*, which is
> what an attacker actually changes.

# Part 2 — ⭐⭐ The evaluation logic

```
⭐ For EVERY API call, in this order:

⭐ 1. ⭐⭐ Is there an EXPLICIT DENY anywhere?      ⇒ ⭐⭐ DENY. Nothing overrides this. Ever.
⭐ 2. Do the SCPs allow it?                        ⇒ if not, DENY  (org ceiling)
⭐ 3. Does a resource-based policy allow it?       ⇒ if yes, ALLOW (cross-account: needed)
⭐ 4. Does the permission boundary allow it?       ⇒ if not, DENY  (identity ceiling)
⭐ 5. Does a session policy allow it?              ⇒ if not, DENY  (assume-role ceiling)
⭐ 6. Does an identity-based policy allow it?      ⇒ if yes, ALLOW
⭐ 7. ⭐⭐ Otherwise                                 ⇒ ⭐⭐ IMPLICIT DENY (the default)
```

| ⭐ The three rules that survive the detail | |
|---|---|
| ⭐⭐ **Deny by default** | ⭐ no policy = no access |
| ⭐⭐ **Explicit Deny always wins** | ⭐⭐ **it cannot be overridden by any Allow, at any level** |
| ⭐⭐ **Access requires an Allow with no Deny** | ⭐ and, for cross-account, **an Allow on *both* sides** |

## ⭐⭐ Ceilings grant nothing

| Mechanism | ⭐ What it does | ⭐⭐ What it does NOT do |
|---|---|---|
| ⭐⭐ **SCP** (Organizations) | ⭐ caps what *anyone* in the account may do | ⭐⭐ **grants nothing** — an SCP allowing `s3:*` gives no one access |
| ⭐⭐ **Permission boundary** | ⭐ caps what a *principal* may do | ⭐⭐ grants nothing |
| ⭐ **Session policy** | caps a *specific assumed session* | grants nothing |
| ⭐ **Identity / resource policy** | ⭐⭐ **the only things that grant** | — |

> **⭐⭐ "The SCP allows it but I still get denied" is the most common AWS confusion of all.** SCPs are a
> ceiling. **Effective permissions are the *intersection* of every ceiling with the union of the
> grants.** Draw it once as overlapping circles and it never confuses you again.

⚠️ **The most valuable SCP in existence is three lines: deny leaving the organisation, deny disabling
CloudTrail, deny deleting the security tooling.** It applies to the account root user too — **the only
mechanism in AWS that can constrain root.**

# Part 3 — ⭐ Identity-based vs resource-based

| | ⭐ Identity-based | ⭐ Resource-based |
|---|---|---|
| Attached to | ⭐ a user, group or **role** | ⭐ the resource — bucket, queue, KMS key, Lambda |
| Has a `Principal` | ⭐ no (it *is* the principal) | ⭐⭐ **yes — required** |
| ⭐ Same account | either side alone is enough | either side alone is enough |
| ⭐⭐ **Cross account** | ⭐⭐ **NOT enough alone** | ⭐⭐ **BOTH sides must allow** |
| Services that support it | — | ⭐ S3, SQS, SNS, KMS, Lambda, Secrets Manager, ECR |

```
⭐⭐ Cross-account access, stated once and correctly:
⭐   Account A's role must ALLOW  s3:GetObject on B's bucket   (identity policy in A)
⭐   Account B's bucket must ALLOW A's role as Principal        (resource policy in B)
⭐   ⇒ ⭐⭐ Either one missing = denied. This is by design: both owners must consent.
```

⚠️ **KMS is the exception that catches everyone: the key policy is authoritative.** A key with no
statement granting the account's IAM has *no* access **even for an administrator**, and a key policy
that locks everyone out is genuinely unrecoverable without support (Day 395).

# Part 4 — ⭐⭐ `iam:PassRole`, and the escalation nobody audits

```
⭐ To launch an EC2 instance with a role attached, you need:
⭐   ec2:RunInstances      ⭐ AND ⭐⭐ iam:PassRole on that role

⭐⭐ SO: a developer with  ec2:RunInstances  +  iam:PassRole on "*"
⭐⭐    can launch an instance carrying the ADMIN role,
⭐⭐    SSH into it, and read its credentials from the metadata service.
⭐⭐ ⇒ ⭐⭐ They are now an administrator. No admin policy was ever attached to them.
```

| ⭐ Where `PassRole` hides | |
|---|---|
| ⭐ EC2 instance profiles | ⭐⭐ the classic path above |
| ⭐ **Lambda function roles** | ⭐⭐ create a function with the admin role, invoke it, done |
| ⭐ ECS task roles | same shape (Day 390) |
| CodeBuild / Glue / SageMaker | every service that "acts on your behalf" |

> **⭐⭐ The fix is one condition:** constrain `iam:PassRole` by resource to specific roles, or by
> `iam:PassedToService`:

```json
{ "Effect": "Allow", "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-task-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "ecs-tasks.amazonaws.com" } } }
```

⚠️ **Other quiet escalation paths worth knowing by name:** `iam:CreatePolicyVersion` (rewrite a policy
you are attached to), `iam:AttachUserPolicy` (attach admin to yourself), `lambda:UpdateFunctionCode` on
a privileged function, and `sts:AssumeRole` with a sloppy trust policy. **"Who can become an
administrator?" is a different and much better question than "who is an administrator?"**

# Part 5 — ⭐ Getting to least privilege without going insane

| ⭐ Step | ⭐ How |
|---|---|
| ⭐ 1. Start broad in dev | `PowerUserAccess` while you find the shape |
| ⭐⭐ 2. **Read CloudTrail** | ⭐⭐ **the actual API calls made — this is the ground truth** |
| ⭐⭐ 3. **`iam:GenerateServicePolicy` / Access Analyzer policy generation** | ⭐⭐ generates a policy *from* CloudTrail |
| ⭐ 4. Apply, run the test suite, fix denials | ⭐ each denial is a real requirement |
| ⭐ 5. **Access Analyzer — unused access** | ⭐ finds permissions granted and never used |
| ⭐ 6. **Access Analyzer — external access** | ⭐⭐ finds resources reachable from outside the account |

> **⭐ Least privilege written by hand from imagination is always wrong in both directions** — too broad
> where you guessed, too narrow where you forgot. **Generate it from observed calls, then review the
> diff.** That is a repeatable process rather than a virtue.

⚠️ **`*:*` in a "temporary" policy is permanent.** Nothing forces its removal, nothing alerts on it, and
it will be there in three years. **If you must use it, put an explicit expiry condition in it:**
`{"DateLessThan": {"aws:CurrentTime": "2026-09-01T00:00:00Z"}}` — **a policy that expires itself.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ `Resource: "*"` everywhere | ⭐⭐ the wildcard people stop noticing |
| ⭐ Forgetting the bucket **and** `bucket/*` ARNs | ⭐ list works, get fails (or vice versa) |
| ⭐⭐ **Believing an SCP grants access** | ⭐⭐ ceilings grant nothing — intersection, not union |
| ⭐ Expecting an Allow to beat a Deny | ⭐⭐ **explicit Deny is absolute** |
| ⭐⭐ **Cross-account with only one side configured** | ⭐⭐ both owners must consent — by design |
| ⭐ Assuming admins can use any KMS key | ⭐⭐ the key policy is authoritative |
| ⭐⭐ **Unconstrained `iam:PassRole`** | ⭐⭐ silent path to administrator |
| ⭐ Auditing "who is admin" but not "who can become admin" | ⭐ misses every escalation path |
| ⭐ Hand-writing least privilege from imagination | ⭐ wrong in both directions — generate from CloudTrail |
| ⭐ Temporary `*:*` policies | nothing ever removes them |
| No conditions on any policy | the cheapest hardening, unused |

## Interview questions

**Q: Walk me through how AWS decides whether an API call is allowed.**
Everything is denied by default. AWS collects every applicable policy and checks for an explicit Deny
first — if one exists anywhere, the call is denied and nothing can override it. Then the ceilings apply:
service control policies, permission boundaries and session policies must all permit the action, but
none of them grant anything. Finally an Allow must exist in either an identity-based policy or a
resource-based policy. So the effective permission is the intersection of every ceiling with the union
of the grants, minus any explicit deny.

**Q: An SCP allows `s3:*` but the developer gets access denied. Why?**
Because an SCP is a ceiling, not a grant. It defines the maximum any principal in that account may do;
it never gives anyone anything. The developer still needs an identity-based policy actually allowing the
S3 action. This is probably the most common IAM misunderstanding, and the mental model that fixes it is
overlapping circles: ceilings intersect, grants union.

**Q: What is `iam:PassRole` and why does it matter?**
Passing a role to a service — attaching an instance profile, setting a Lambda's execution role — is a
separate permission from creating the resource. If someone has `RunInstances` plus unconstrained
`PassRole`, they can launch an instance carrying the administrator role and read its credentials from
the metadata service. They have become an administrator without any admin policy ever being attached to
them. The fix is to scope PassRole by resource ARN and by `iam:PassedToService`. More generally, the
question to audit is not "who is an administrator" but "who can become one".

**Q: How do you grant another account access to your S3 bucket?**
Both sides must allow it. Your bucket policy names their role as the principal, and their identity
policy allows the S3 action against your bucket's ARN. Either side alone is not sufficient, which is
deliberate — both resource owners have to consent. I would also add an `aws:PrincipalOrgID` condition if
they are inside the same organisation, and prefer a role they assume over a long-lived credential.

**Q: How do you actually get to least privilege?**
Not by writing it from imagination, because that is wrong in both directions. Start broad in a
development account, let the workload run, then generate a policy from the CloudTrail record of the
calls it actually made — IAM Access Analyzer does this directly. Apply it, run the test suite, and treat
each denial as a discovered requirement. Then use Access Analyzer's unused-access findings to keep it
tight over time. It turns least privilege from a virtue into a repeatable process.

## Mini task

1. ⭐ Write a policy that allows reading exactly one S3 prefix. **Include both ARN forms** and prove list
   and get each work.
2. ⭐ Use the **IAM policy simulator** on it — for an allowed action and a denied one.
3. ⭐⭐ Add an explicit **Deny** that overlaps an Allow. Confirm the Deny wins.
4. ⭐ Add `aws:SecureTransport: false` deny to a bucket policy and **verify plain HTTP is refused.**
5. ⭐⭐ Set up an **SCP that denies a region** you do not use. Confirm an admin in the account is now
   blocked there — **including root.**
6. ⭐⭐ Attach a **permission boundary** to a test user and prove that adding an admin policy to that user
   changes nothing.
7. ⭐⭐ Find every principal in your account with `iam:PassRole` unconstrained. **Fix each one with
   `iam:PassedToService`.**
8. ⭐ Run **Access Analyzer** (external access) and explain every finding it reports.
9. ⭐⭐ Generate a policy **from CloudTrail** for one of your workloads. Diff it against what you would
   have written by hand.
10. ⭐ Write a policy with a **self-expiry date condition** and verify it stops working after the date
    (use a date one minute out).

## 🎙️ Articulation drill

**Two minutes:** *"How does IAM decide?"*

**⭐ Three sentences carry it: everything is denied by default; an explicit Deny beats every Allow; and
access needs a grant from an identity or resource policy that survives every ceiling above it.**

**⭐ Then the sentence that shows you have operated it, not read about it: "the mistake I look for first
is unconstrained `iam:PassRole`, because that is how someone with no admin policy becomes an
administrator — and the audit question is who *can become* admin, not who *is* admin."**
