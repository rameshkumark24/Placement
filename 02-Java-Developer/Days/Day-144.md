# Part 1 — DevTools, and the one thing about it that matters in production

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-devtools</artifactId>
  <optional>true</optional>          <!-- ⭐ -->
</dependency>
```

What it gives you: automatic restart on classpath change (fast, because it uses **two class loaders**
— one for jars that never change, one for your classes that it throws away and recreates), a
LiveReload server, and development-friendly property defaults (template caching off, `H2` console on,
more verbose logging on conditions).

**The restart trick is worth understanding**, because it is the same class-loader reasoning as
Day 077: your application classes are loaded by a disposable `RestartClassLoader`; the base loader
holds the unchanging library jars. Restart discards and rebuilds only the cheap half, which is why it
is a second rather than the twenty a full restart costs.

**The production question:** DevTools disables itself when it detects it is running from a fully
packaged jar, so leaking it is not the catastrophe it once was. But `<optional>true</optional>` still
matters: without it, DevTools becomes a **transitive dependency of anything that depends on your
module**, which is Day 073's transitive-resolution problem doing something you never intended. Mark
it optional, and use `spring-boot-devtools` never in a library.

**The setting you actually want in dev:**
```yaml
spring.devtools.restart.poll-interval: 2s
spring.devtools.restart.quiet-period:  1s
```
Without a quiet period the restart fires mid-compile, on a half-written class set, and you get a
confusing failure that resolves itself on the next save.

# Part 2 — ⭐ What is actually inside a fat jar

```
app.jar
├── META-INF/MANIFEST.MF
│     Main-Class: org.springframework.boot.loader.launch.JarLauncher    ← ⭐ not yours
│     Start-Class: com.acme.orders.OrdersApplication                    ← ⭐ yours
├── org/springframework/boot/loader/...      ← the launcher, ~40 classes, unpacked
├── BOOT-INF/
│   ├── classes/                             ← your compiled code and resources
│   ├── lib/                                 ← every dependency jar, **nested**
│   └── classpath.idx
```

**`java -jar app.jar` runs `JarLauncher`, not your main method.** The launcher builds a class loader
that can read jars *nested inside* a jar — something the standard JVM class loader cannot do, because
the `java -jar` classpath model has no concept of a jar within a jar — then reflectively invokes
`Start-Class`.

Three consequences that come up in real work:

| Fact | Consequence |
|---|---|
| Your classes are under `BOOT-INF/classes`, not the jar root | **a fat jar cannot be used as a dependency of another project.** Maven will resolve it and find no classes where it expects them |
| Nested jars need `LaunchedClassLoader` | tools that inspect a jar naively (some scanners, some agents) see nothing |
| `Main-Class` is the launcher | `java -cp app.jar com.acme.Something` does not work as you expect |

**The fix for the dependency case** is the one people search for after an hour of confusion:

```xml
<plugin>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <classifier>exec</classifier>       <!-- ⭐ fat jar becomes app-exec.jar -->
  </configuration>
</plugin>
```

Now `app.jar` is a normal, usable library jar and `app-exec.jar` is the runnable one. Better still:
do not depend on an application module at all — extract the shared code into a library module
(Day 141), which is what the coupling was telling you.

# Part 3 — Layered jars, and the Docker build that stops being slow

Day 129B's rule: **order layers from least to most frequently changed.** A naive Boot Dockerfile
violates it completely:

```dockerfile
# ❌ every code change invalidates a 60 MB layer
FROM eclipse-temurin:21-jre
COPY target/app.jar app.jar
ENTRYPOINT ["java","-jar","/app.jar"]
```

The jar is one file. Your dependencies — which change monthly — and your classes — which change every
commit — are inside it together. Change one line of Java and Docker re-uploads 60 MB, every build,
forever.

**Boot solves this with layered jars, on by default since 2.4:**

```bash
java -Djarmode=tools -jar app.jar list-layers
# dependencies
# spring-boot-loader
# snapshot-dependencies
# application            ← ⭐ only this changes on a normal commit
```

```dockerfile
# ---- extract ----
FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY target/app.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --launcher

# ---- runtime ----
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/app/dependencies/          ./
COPY --from=builder /app/app/spring-boot-loader/    ./
COPY --from=builder /app/app/snapshot-dependencies/ ./
COPY --from=builder /app/app/application/           ./
USER 1000:1000
ENTRYPOINT ["java","org.springframework.boot.loader.launch.JarLauncher"]
```

**The effect:** a code-only change rebuilds and re-pushes the last layer — typically **under a
megabyte** instead of sixty. Across a team pushing thirty times a day this is the difference between
CI that feels instant and CI that does not.

Note `ENTRYPOINT` invokes `JarLauncher` directly on the exploded layout — no jar, no unpacking at
startup, marginally faster boot.

> **Boot 3.3+ note:** `-Djarmode=tools extract` replaces the older
> `-Djarmode=layertools extract`. The old form still appears in most blog posts and in a lot of
> copied Dockerfiles; if you see `layertools` it is either an old Boot or an old article.

## Buildpacks — the zero-Dockerfile option

```bash
./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=acme/orders:1.4.0
```

Produces an OCI image with **no Dockerfile at all**: layered automatically, non-root user, a
memory-calculating entrypoint that sets heap from the container limit (Day 129B's whole problem,
solved by default), and a generated SBOM (Day 100A). It is a genuinely good default for a team that
does not want to own Dockerfile maintenance.

**What you give up:** control. A custom base image, a distroless runtime, or an OS package your app
needs are all easier with a Dockerfile. Rule of thumb — buildpacks until you have a specific reason,
then a layered Dockerfile.

## Container ergonomics you should set regardless

```dockerfile
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError \
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps"
```

| Flag | Why |
|---|---|
| `MaxRAMPercentage=75` | Day 129B — the JVM must size its heap from the *container* limit, leaving room for metaspace, thread stacks and native memory |
| `ExitOnOutOfMemoryError` | ⭐ an OOM leaves the JVM in an undefined state. Dying lets the orchestrator replace the pod; limping along corrupts data |
| `HeapDumpOnOutOfMemoryError` | Day 076 — you get exactly one chance to capture the evidence, and it is at the moment of failure |
| `-XX:HeapDumpPath` on a mounted volume | otherwise the dump dies with the container that produced it |

# Part 4 — Startup time, and the honest version of the AOT story

| Technique | Startup | Cost |
|---|---|---|
| Baseline Boot 3 on JVM | 2–4 s | — |
| Lazy initialization (`spring.main.lazy-initialization=true`) | ~40% faster | ⭐ **failures move from startup to first request.** Day 133's argument, inverted — a bad bean now fails a customer, not a deploy. Dev only |
| CDS (`-XX:SharedArchiveFile`) | 20–35% faster | build step; low risk; **the best effort/reward on the list** |
| Spring AOT (`spring-boot-maven-plugin` `process-aot`) | 15–30% faster | build complexity; no reflection surprises yet |
| **GraalVM native image** | **~50 ms** | slow builds (minutes), no runtime reflection without hints, no agents, no dynamic proxies without registration, larger memory during build |

**The honest framing for an interview:** native images are transformative for functions and CLIs
where a cold start is on the request path, and they are a significant operational commitment for a
long-running service, where a 3-second start amortised over a week of uptime buys you almost nothing.
Day 185B covers this properly. **CDS is the technique most teams should actually adopt** — it is a
build flag, it is boring, and it works.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| `COPY target/app.jar` with no layering | every commit re-pushes the whole image |
| Depending on a fat jar from another module | classes are under `BOOT-INF/`; resolution silently finds nothing |
| DevTools without `<optional>true</optional>` | leaks transitively into every consumer |
| No `MaxRAMPercentage` | JVM sizes heap from host RAM, gets OOM-killed (Day 129B) |
| No `ExitOnOutOfMemoryError` | a half-dead JVM keeps serving and keeps corrupting |
| Heap dump path inside the container | dump is destroyed with the container |
| `lazy-initialization` in production | wiring failures become customer-facing 500s |
| Running as root in the image | container escape becomes root on the node |
| Copying `layertools` from a blog into Boot 3.3+ | build fails, or worse, silently uses an old path |

## Interview questions

**Q: What is inside a Spring Boot fat jar?**
Your code in `BOOT-INF/classes`, dependencies as nested jars in `BOOT-INF/lib`, and Boot's launcher at
the root. `Main-Class` is `JarLauncher`, not your class; it installs a class loader that can read
nested jars and then invokes `Start-Class`. That is also why a fat jar is useless as a dependency.

**Q: Why layer the jar in Docker?**
Because layers cache by content and dependencies change far less often than application code.
Extracting into four layers means a normal commit re-pushes under a megabyte instead of the whole
jar.

**Q: Which JVM flags do you always set in a container?**
`MaxRAMPercentage` so the heap is derived from the container limit, `ExitOnOutOfMemoryError` so a
broken JVM is replaced instead of limping, and `HeapDumpOnOutOfMemoryError` with a path on a mounted
volume so the evidence survives the pod.

**Q: Would you use GraalVM native images?**
For serverless or a CLI, yes — cold start is on the request path. For a long-running service, usually
not: the build and reflection constraints are a real cost, and CDS gives a meaningful fraction of the
benefit for a build flag.

## Mini task

1. Build your jar. `unzip -l target/app.jar | head -30` and find `BOOT-INF/` and the manifest. Read
   `MANIFEST.MF` — confirm `Main-Class` is `JarLauncher`.
2. `java -Djarmode=tools -jar target/app.jar list-layers`.
3. Write the naive Dockerfile. Build. Change one line of Java. Rebuild. **Note the layer size pushed.**
4. Write the layered Dockerfile. Repeat. Compare.
5. Run with `-m 512m` and no `MaxRAMPercentage`; print `Runtime.maxMemory()`. Add the flag and repeat.
6. `./mvnw spring-boot:build-image`, then `docker inspect` the result — note the non-root user.
7. Try to add your app jar as a dependency of a second module. Watch it fail. Add `<classifier>exec</classifier>` and watch it work.

## 🎙️ Articulation drill

Two minutes: **"How do you package and ship a Spring Boot service?"**

Layered fat jar extracted into four Docker layers so a code change pushes a megabyte, not sixty. A JRE
base, non-root user, `MaxRAMPercentage` so the heap follows the container limit, `ExitOnOutOfMemory`
plus a dump path on a volume. Buildpacks if the team does not want to own a Dockerfile. Then place
native images honestly: worth it when cold start is on the request path, not worth the reflection and
build constraints for a service that starts once and runs for a week.
