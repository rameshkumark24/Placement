# Part 1 — The default layout, and what each piece actually is

```
my-service/
├── pom.xml                       ← or build.gradle
├── mvnw, mvnw.cmd                ← the wrapper: pins the build tool version
├── .mvn/wrapper/                 ← wrapper metadata
├── src/
│   ├── main/
│   │   ├── java/com/acme/orders/
│   │   │   └── OrdersApplication.java     ← ⭐ the main class
│   │   └── resources/
│   │       ├── application.yml
│   │       ├── static/                    ← served at / by default
│   │       ├── templates/                 ← Thymeleaf etc.
│   │       └── db/migration/              ← Flyway (Day 166)
│   └── test/
│       ├── java/com/acme/orders/
│       └── resources/
│           └── application-test.yml
└── target/                       ← build output, gitignored
```

**The Maven wrapper is not optional ceremony.** `./mvnw` downloads and uses a *pinned* Maven version.
Without it, your build depends on whatever Maven the developer or the CI image happens to have, which
is the same class of problem Day 073 described for dependency versions: reproducibility depends on
pinning every input, not most of them. Commit `mvnw`, `mvnw.cmd` and `.mvn/`.

## ⭐ The main class position rule

```java
package com.acme.orders;          // ⭐ this package matters

@SpringBootApplication
public class OrdersApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrdersApplication.class, args);
    }
}
```

Day 135 established the mechanism: `@SpringBootApplication` includes `@ComponentScan` with **no
`basePackages`**, so it defaults to *the package of the annotated class*, and scans downward.

Consequences, all of which are real bugs people hit:

| You do this | What happens |
|---|---|
| Main class in `com.acme.orders` | scans `com.acme.orders.**` — correct |
| Main class in the **default package** (no `package` line) | scans **the entire classpath**, including every library. Startup slows to a crawl or fails outright |
| Main class in `com.acme.orders.config` | your `com.acme.orders.web` beans are never found. `NoSuchBeanDefinitionException` at startup |
| Second module at `com.acme.shared` | invisible. Needs `@ComponentScan` widening or its own `@AutoConfiguration` |

**Rule:** the main class lives in the *root* package of your application, and nothing else lives
beside it except perhaps a top-level `config` package.

## What `@SpringBootApplication` actually is

It is one annotation standing in for three, which Day 140 partly covered:

```java
@Configuration              // this class may declare @Bean methods
@EnableAutoConfiguration    // ⭐ Day 140's mechanism
@ComponentScan              // Day 135's mechanism, rooted here
public @interface SpringBootApplication { }
```

Knowing the decomposition is an interview staple, but it also matters practically: when you need to
exclude an auto-configuration you put it on this annotation, and when you need to scan a sibling
package you replace the composed annotation with the three separately rather than fighting it.

# Part 2 — Package by feature, concretely

Day 135 made the argument. Here is what the two layouts look like for the same service.

**Layer-first — the default most tutorials teach:**

```
com.acme.orders/
├── controller/   OrderController, PaymentController, ShipmentController, UserController
├── service/      OrderService, PaymentService, ShipmentService, UserService
├── repository/   OrderRepository, PaymentRepository, ShipmentRepository, UserRepository
├── model/        Order, Payment, Shipment, User
└── dto/          OrderDto, CreateOrderRequest, PaymentDto, ...
```

**Feature-first:**

```
com.acme.orders/
├── OrdersApplication.java
├── order/        OrderController, OrderService, OrderRepository, Order,
│                 CreateOrderRequest, OrderResponse
├── payment/      PaymentController, PaymentService, PaymentRepository, Payment, ...
├── shipment/     ...
├── user/         ...
├── shared/       error handling, correlation-ID filter, clock, config properties
└── config/       SecurityConfig, JacksonConfig, OpenApiConfig
```

**The test that decides it:** "add a field to an order." Layer-first, you edit four packages. That is
Day 096's **shotgun surgery** in its purest form. Feature-first, you edit one directory and the diff
reads as one coherent change.

## The point most people miss: visibility becomes enforceable

Feature-first packages let you use Java's package-private default as a real boundary:

```java
// com.acme.orders.order
@Service
class OrderService {                    // ⭐ package-private — no `public`
    Order place(CreateOrderRequest r) { ... }
}
```

**Spring injects package-private beans without complaint** — it uses reflection, not the compiler's
access rules. So the only classes that can call `OrderService` are the ones in `order/`. Payment code
that wants an order must go through whatever `order/` chose to make `public`. The compiler now
enforces your architecture, and it does so with zero tooling.

Under layer-first this is impossible: `OrderService` must be `public` for the controller in the
`controller` package to see it, and once it is `public` everything sees it.

**What stays public:** the controller (Spring MVC needs it in practice for proxying and for clear
mapping), the entity if other features reference it, and any deliberately exported facade.

## The `shared/` package and how it rots

`shared` is necessary and it is also where discipline dies. Two rules keep it usable:

1. **`shared` may not import any feature package.** If `shared/EmailSender` imports
   `order.Order`, it is not shared — it is order code in the wrong place. This is checkable with
   ArchUnit in about four lines.
2. **Two features using a thing is not sufficient reason to move it there.** Three is a reasonable
   threshold; below that, duplicate it. Day 092's DRY caveat applies directly — premature sharing
   couples features that only *look* alike.

# Part 3 — Multi-module, and when it is worth it

```
my-service/
├── pom.xml                    ← packaging: pom, <modules>
├── domain/                    ← entities, domain services. No Spring Web, no JPA
├── application/               ← use cases, ports (interfaces)
├── infrastructure/            ← JPA adapters, HTTP clients, messaging
└── bootstrap/                 ← @SpringBootApplication, config, the fat jar
```

**What you gain:** the compiler enforces direction. `domain` cannot import `infrastructure` because
`domain/pom.xml` does not declare it. This is Day 091's **DIP** made structural rather than aspirational
— you cannot accidentally violate it in a hurried Friday commit.

**What you pay:** slower IDE indexing, slower builds, a `pom.xml` per module, and the constant
question "which module does this go in?" for every new class. For a team of three on one deployable,
that cost usually exceeds the benefit.

**Honest recommendation:** single module, package-by-feature, with an ArchUnit test enforcing the
same rules the module boundary would have enforced. You get the direction guarantee at a fraction of
the cost, and you can split into modules later when the package structure has already proven itself.

```java
@Test
void domainDoesNotDependOnSpring() {
    noClasses().that().resideInAPackage("..domain..")
        .should().dependOnClassesThat().resideInAPackage("org.springframework..")
        .check(new ClassFileImporter().importPackages("com.acme"));
}
```

# Part 4 — Resources, and the classpath facts worth knowing

**`src/main/resources` becomes the root of the classpath.** So `application.yml` is
`classpath:application.yml`, and `db/migration/V1__init.sql` is `classpath:db/migration/V1__init.sql`.
This is why Day 076's `ClassLoader.getResourceAsStream("db/migration/V1__init.sql")` works with no
leading slash and `getClass().getResourceAsStream()` needs one — the same distinction, arriving in a
Boot project.

| Directory | Behaviour |
|---|---|
| `resources/static/` | served at `/` — `static/logo.png` → `GET /logo.png` |
| `resources/public/`, `resources/META-INF/resources/` | same, different precedence |
| `resources/templates/` | template engine root, never served directly |
| `resources/db/migration/` | Flyway's default (Day 166) |
| `resources/banner.txt` | replaces the startup banner |

**`src/test/resources/application.yml` completely replaces the main one during tests** — it does not
merge. This surprises people constantly. If you want to override two properties in tests, do not
create a test `application.yml`; use `application-test.yml` with `@ActiveProfiles("test")`, which
*layers* on top (Day 142), or `@TestPropertySource`.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Main class in a sub-package | half your beans silently unscanned; error is `NoSuchBeanDefinition`, which points nowhere near the cause |
| Main class in the default package | scans every jar on the classpath |
| Layer-first packaging by default | every feature change is a four-package diff (Day 096) |
| Everything `public` | the package boundary is decorative |
| `shared` importing feature packages | a cycle in the architecture, invisible until you try to extract a module |
| Test `application.yml` in `src/test/resources` | replaces rather than overrides main config; mystery failures |
| Not committing `mvnw` | build depends on the developer's machine |
| Multi-module for a three-person team | pays module-boundary cost, uses none of it |

## Interview questions

**Q: What does `@SpringBootApplication` actually do?**
It composes `@Configuration`, `@EnableAutoConfiguration` and `@ComponentScan`. The scan is rooted at
the annotated class's package, which is why the main class's location is a structural decision and
not a formality.

**Q: Layered or feature packages?**
Feature, and the reason is change locality — the unit of change is a feature, so it should be the
unit of packaging; layer-first makes every change shotgun surgery. Feature packaging also lets me
keep services package-private, which turns the boundary into something the compiler enforces.

**Q: When would you split into Maven modules?**
When I want the *compiler* to enforce dependency direction and a single team no longer owns the whole
thing. Before that I get most of the guarantee from an ArchUnit test at a fraction of the build cost.

**Q: Why is a `application.yml` in `src/test/resources` a trap?**
Because it replaces the main file rather than merging with it, so every property not restated is
lost. Use a `test` profile instead, which layers.

## Mini task

1. Create a Boot project (`start.spring.io`, Web + Validation) with the main class in
   `com.acme.orders`.
2. Add `order/OrderController` and `order/OrderService`. Make **`OrderService` package-private.**
   Confirm it starts and injects.
3. Add `payment/PaymentService` and try to call `OrderService` from it. **Watch it fail to compile.**
   That compiler error is the lesson.
4. Now move the main class to `com.acme.orders.config` and restart. Read the failure. Move it back.
5. Add the ArchUnit test above and make it pass.
6. Put a `logging.level.root=DEBUG` in `src/test/resources/application.yml`, run a test, and observe
   that your main config's other properties are now gone.

## 🎙️ Articulation drill

Two minutes: **"How do you structure a Spring Boot service?"**

Root package for the main class because the component scan is rooted there. Package by feature, not
by layer, because the unit of change is a feature. Services package-private so the compiler enforces
the boundary. A thin `shared` that never imports features. Single module with an ArchUnit rule
instead of a multi-module build until team size justifies it. Then name the trade-off you accepted:
feature packaging makes cross-cutting layer changes — like swapping the persistence technology —
slightly harder to sweep, and you took that trade knowingly.
