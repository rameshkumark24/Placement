> What happens *after* the password check succeeds. HTTP is stateless (Day 010), so every subsequent

# Part 1 — How a session works

```
1. POST /login  { email, password }
2. Server verifies (Day 112), creates a session:
       sessionId = SecureRandom(32 bytes) → base64
       store[sessionId] = { userId, roles, createdAt, lastSeen, ip, userAgent }
3. Set-Cookie: SID=<sessionId>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1800
4. Every later request: the browser sends the cookie automatically
5. Server looks up store[sessionId] → the principal
```

**The cookie contains no information — only a random pointer.** That single property is what makes
sessions fundamentally different from tokens (tomorrow), and it is where most of their advantages
come from:

- The client cannot read, modify or forge the contents; there is nothing to read.
- The server can **change or revoke the session instantly** — delete the entry and the next request
  is unauthenticated.
- Session data can be large without inflating every request.

The cost is equally direct: **the server holds state**, so the store must be shared across instances,
must be fast, and is a component that can fail.

## Session id requirements

```java
byte[] bytes = new byte[32];                       // ≥128 bits of entropy
SecureRandom.getInstanceStrong().nextBytes(bytes); // NEVER java.util.Random
String sid = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
```

| Rule | Why |
|---|---|
| ≥128 bits of entropy | Brute-forcing a session id must be infeasible |
| `SecureRandom` | `Random` is a seeded LCG — observe a few outputs, predict the rest |
| **Regenerate on privilege change** | ⭐ **session fixation** — see below |
| Invalidate on logout, server-side | A client-side-only logout is not a logout |
| Absolute + idle timeout | Bound the window |

## ⭐ Session fixation

The attack that makes "regenerate the id on login" non-negotiable:

```
1. Attacker obtains a valid pre-login session id: SID=abc123
2. Attacker induces the victim to use it   (a link with ?SID=abc123, or an injected cookie)
3. Victim logs in — the server AUTHENTICATES THE EXISTING SESSION abc123
4. Attacker now uses abc123, which is authenticated as the victim
```

```java
// ✅ the fix — one line, and it must be there
request.changeSessionId();                          // Servlet 3.1+
// or: copy attributes to a NEW session and invalidate the old one
```

**Regenerate on every privilege escalation**, not only login — after MFA completion, after a role
change, after a password change.

# Part 2 — Cookie flags

Every flag prevents a specific attack. Know each one and its attack.

```http
Set-Cookie: SID=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1800
```

| Flag | Prevents |
|---|---|
| **`HttpOnly`** | JavaScript reading the cookie → **XSS cannot steal the session** |
| **`Secure`** | Transmission over plain HTTP → network interception |
| **`SameSite`** | The cookie being sent on cross-site requests → **CSRF** |
| `Path` | Scope creep to unrelated paths |
| `Domain` | ⚠️ Setting it *widens* scope to subdomains — omit unless needed |
| `Max-Age` / `Expires` | Unbounded lifetime |
| `__Host-` prefix | Enforces `Secure`, `Path=/`, and **no `Domain`** — subdomain injection |

## `HttpOnly` is the argument that decides tokens-vs-sessions

> **A session cookie with `HttpOnly` cannot be read by JavaScript. A JWT in `localStorage` can be
> read by any script that runs on your page.**

That is the whole XSS argument, and it is the strongest single point in favour of cookies. If an
attacker achieves XSS, `localStorage` tokens are exfiltrated in one line; an `HttpOnly` cookie
cannot be. (XSS still lets the attacker *act as the user* by making requests — but they cannot steal
a long-lived credential and use it elsewhere, later, from their own machine.)

## `SameSite`, precisely

| Value | Behaviour |
|---|---|
| `Strict` | Never sent cross-site — **including on a normal link from another site**, so the user appears logged out when arriving from Google |
| **`Lax`** | Sent on top-level **`GET`** navigations only. **The modern default.** |
| `None` | Always sent — **requires `Secure`**. For genuine cross-site APIs. |

`Lax` blocks the classic CSRF because a cross-site `POST` carries no cookie. **It is not complete
protection**: a state-changing `GET` is still vulnerable (Day 102's rule again), and `Lax` is applied
inconsistently by older browsers. **Keep CSRF tokens for state-changing operations** — defence in
depth (Day 119).

The `__Host-` prefix is under-used and free:

```http
Set-Cookie: __Host-SID=abc123; Secure; Path=/; SameSite=Lax; HttpOnly
```

The browser *refuses* to accept it unless `Secure` is set, `Path=/`, and there is no `Domain` — which
means a compromised or attacker-controlled subdomain cannot overwrite your session cookie. That
subdomain-injection attack is otherwise very hard to defend against.

# Part 3 — Where sessions live

| Store | Pros | Cons |
|---|---|---|
| **In-memory** | Fastest, trivial | ❌ Lost on restart; **breaks with more than one instance** |
| **Sticky sessions** (LB affinity) | Keeps in-memory viable | ❌ Uneven load; losing an instance logs users out; blocks rolling deploys |
| **Redis** ✅ | Fast (sub-ms), TTL built in, shared, survives restarts | One more component to operate |
| **Database** | Durable, queryable, no new component | Slower; a write on every request unless you throttle `lastSeen` |
| **Client-side (signed cookie)** | No server state | Size limit (~4 KB), and **revocation becomes hard** — this is JWT's trade-off |

**Redis is the standard answer**, and the reason is that it maps exactly onto the requirement:
key-value lookup by a random id, with a TTL that expires the session automatically.

```java
// Spring Session — this is genuinely all of it
@EnableRedisHttpSession(maxInactiveIntervalInSeconds = 1800)
public class SessionConfig { }
```

Two operational points worth knowing: **the session store is a single point of failure** — plan for
Redis being unavailable (fail closed, and decide whether that means logged-out or an error page). And
**writing `lastSeen` on every request** turns a read-mostly store into write-heavy; throttle it to
once a minute.

## Timeouts

```
Idle timeout:      30 min banking · 2 h general · 30 days "remember me"
Absolute timeout:  8–24 h regardless of activity
```

Both, not one. An idle timeout alone means a session refreshed by a background poll never expires.

"Remember me" should be a **separate long-lived token** that grants a *new* session on use — not a
30-day session — so a stolen remember-me token is detectable and revocable independently.

# Part 4 — Sessions vs tokens, honestly

Tomorrow is JWT. Today's framing, so tomorrow is a comparison rather than an enthusiasm:

| | Session (cookie) | JWT (stateless) |
|---|---|---|
| Server state | ✅ required | ❌ none |
| **Instant revocation** | ✅ **delete the row** | ❌ **valid until expiry** |
| Scales horizontally | ✅ with a shared store | ✅ trivially |
| XSS exposure | ✅ `HttpOnly` protects it | ❌ readable in `localStorage` |
| CSRF exposure | ❌ needs `SameSite` + tokens | ✅ if sent in a header |
| Payload size on the wire | ~40 bytes | 200–1000+ bytes, **every request** |
| Cross-domain / mobile | Awkward | ✅ natural |
| Data freshness | ✅ always current | ❌ stale until the token expires |
| Extra infrastructure | Redis | none |

> **The default choice for a browser application with a single backend is a session cookie.** It is
> simpler, revocable, and immune to token theft via XSS.
>
> **Tokens win for:** mobile and third-party clients, cross-domain APIs, service-to-service calls,
> and genuinely stateless architectures where a shared store is undesirable.

The industry drifted to JWT-for-everything around 2015 and has been drifting back since — largely
because **revocation is not optional in practice**. "Log out all devices", "this account was
compromised", "this user was fired" are ordinary requirements, and a stateless token cannot satisfy
them without reintroducing exactly the server-side state it was meant to eliminate.

Say that in an interview and it lands, because it is the considered position rather than the
fashionable one.

# Part 5 — D-12 · Query processing

**What happens between typing SQL and getting rows.** Day 078's D-01 named the components; this is
the pipeline.

```
SQL text
   ▼
1. PARSE       syntax → an abstract syntax tree.  Syntax errors here.
   ▼
2. ANALYSE     resolve names against the catalog: do the tables and columns exist?
   ▼           types checked, views expanded, permissions verified
3. REWRITE     apply rules — view substitution, some subquery flattening
   ▼
4. PLAN        ⭐ the optimiser: enumerate plans, ESTIMATE COST, pick the cheapest
   ▼
5. EXECUTE     run the chosen plan, pulling rows through the operator tree
```

**Step 4 is where all the interesting behaviour lives.**

## Cost-based optimisation

The optimiser does not know how long anything will take. It **estimates**, using:

- **Table statistics** — row counts, and per-column histograms, distinct-value counts and null
  fractions. Collected by `ANALYZE`, and **out of date by default**.
- **Cost constants** — the planner's model of relative expense (`seq_page_cost = 1.0`,
  `random_page_cost = 4.0`, `cpu_tuple_cost = 0.01`).

```
cost ≈ (pages read × page cost) + (rows processed × cpu cost)
```

**`random_page_cost = 4.0` is a 1990s spinning-disk assumption.** On SSDs random reads are nearly as
cheap as sequential, so leaving it at 4 makes the planner systematically avoid index scans it should
use. **Setting it to 1.1 on SSD-backed systems is one of the highest-value one-line tuning changes
available**, and it is a good thing to know in an interview.

## Selectivity, and where plans go wrong

The planner's central estimate: **how many rows will this predicate return?**

```sql
WHERE status = 'PAID'
-- histogram says 'PAID' is 60% of rows → 600,000 of 1,000,000 → sequential scan
WHERE id = 42
-- unique → 1 row → index scan
```

Estimates go wrong in predictable ways, and each has a fix:

| Cause | Symptom | Fix |
|---|---|---|
| **Stale statistics** | Estimated 1,000, actual 900,000 | `ANALYZE` |
| **Correlated columns** | `city='Chennai' AND state='TN'` treated as independent → wild underestimate | Extended statistics (`CREATE STATISTICS`) |
| **Skewed data** | 99% of rows share one value | Increase the histogram target |
| **Functions the planner cannot see through** | Default guess of 0.5% selectivity | Expression index; extended stats |
| **Parameter sniffing** | A plan cached for one parameter value is terrible for another | Prepared-statement plan choice; `plan_cache_mode` |

**The independence assumption is the most common cause of a catastrophically wrong plan.** The
planner multiplies selectivities: if 5% of rows are in Chennai and 8% are in Tamil Nadu, it estimates
0.4% — when the real answer is 5%, because every Chennai row is in Tamil Nadu. A 12× underestimate is
enough to pick a nested loop that should have been a hash join.

```sql
CREATE STATISTICS city_state (dependencies) ON city, state FROM addresses;
ANALYZE addresses;
```

## Join order — the combinatorial part

Day 100 flagged it; here is why it is hard. n tables have up to n! join orders, so:

- PostgreSQL uses **dynamic programming** up to `geqo_threshold` (default 12 tables),
- and switches to a **genetic algorithm** beyond that — meaning above 12 joined tables **the plan is
  not guaranteed to be good, or even stable between runs**.

That is a concrete design consequence: a 20-table join is not just slow, it is *unpredictable*.

## Reading `EXPLAIN` properly

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) SELECT …;
```

```
Nested Loop  (cost=0.29..8.34 rows=1 width=64) (actual time=0.021..0.089 rows=1523 loops=1)
             ↑ESTIMATED cost & rows                ↑ACTUAL time & rows
  Buffers: shared hit=45 read=1203
           ↑ from cache      ↑ from disk
```

The reading order and what to look for:

1. **Read inside-out, bottom-up.** The most indented node runs first.
2. **`cost=A..B`** — A is startup cost (before the first row), B is total. A `LIMIT` cares about A;
   a full scan cares about B.
3. ⭐ **Compare `rows=` estimated with `actual rows=`.** A divergence over ~10× is the single most
   informative signal in the output and almost always means bad statistics.
4. **`loops=`** — actual time is *per loop*. A node showing 0.5 ms with `loops=10000` took 5 seconds.
   **This is the most misread number in `EXPLAIN` output.**
5. **`Buffers: read=`** high means cache misses — either the working set exceeds `shared_buffers` or
   the query touches too much data.
6. **`Rows Removed by Filter:`** large means the predicate is not in the index (Day 110).

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) …          -- machine-readable
```

Paste the output into `explain.dalibo.com` or `explain.depesz.com` — both highlight the divergences
and the expensive nodes automatically, which is far faster than reading a 200-line plan by hand.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Not regenerating the session id on login | **Session fixation** |
| Missing `HttpOnly` | XSS steals the session |
| Missing `Secure` | Session id sent over plain HTTP |
| No `SameSite` | CSRF |
| Setting `Domain` unnecessarily | Cookie shared with every subdomain |
| `Random` for session ids | Predictable — sessions can be guessed |
| In-memory sessions behind a load balancer | Random logouts |
| Client-side-only logout | The session remains valid server-side |
| Idle timeout with no absolute timeout | A polling tab never expires |
| Writing `lastSeen` on every request | Read-mostly store becomes write-heavy |
| Choosing JWT to avoid Redis, then needing revocation | Redis reintroduced, plus token complexity |
| Never running `ANALYZE` | Plans chosen from wrong row counts |
| `random_page_cost=4` on SSDs | The planner avoids indexes it should use |
| Ignoring `loops=` in `EXPLAIN` | Off by four orders of magnitude on the cost |

## Interview questions

**Q: How does session-based auth work?**
The server creates a random session id, stores the principal against it, and sets it as an
`HttpOnly; Secure; SameSite` cookie. The cookie carries no data — only a pointer — so the client
cannot read or forge it and the server can revoke instantly by deleting the entry.

**Q: What is session fixation and how do you prevent it?**
An attacker plants a known session id on the victim before login; the server then authenticates that
existing session, which the attacker also holds. Prevent it by regenerating the session id on login
and on every privilege change.

**Q: Explain each cookie flag.**
`HttpOnly` stops JavaScript reading it, defeating XSS theft. `Secure` prevents transmission over
HTTP. `SameSite` controls cross-site sending, mitigating CSRF. `__Host-` forces `Secure`, `Path=/`
and no `Domain`, preventing a subdomain from overwriting the cookie.

**Q: Sessions or JWT?**
Sessions for a browser application with one backend: revocable instantly, `HttpOnly` protects against
XSS theft, small on the wire. Tokens for mobile, cross-domain and service-to-service. The decisive
factor is usually revocation — "log out everywhere" and "this account is compromised" are ordinary
requirements a stateless token cannot meet without reintroducing server state.

**Q: Where do you store sessions and why?**
Redis — key-value lookup by random id with a built-in TTL is exactly the access pattern, it is shared
across instances, and it survives restarts. In-memory breaks with more than one instance; sticky
sessions block rolling deploys.

**Q: Walk me through what happens when you run a query.**
Parse to an AST, analyse against the catalog for names, types and permissions, rewrite (view
expansion), plan — the cost-based optimiser estimates using table statistics and cost constants and
picks the cheapest plan — then execute the operator tree.

**Q: A query suddenly got slow with no code change. Why?**
Almost always the plan changed because statistics went stale or data volume crossed a threshold.
Check estimated versus actual rows in `EXPLAIN ANALYZE` and run `ANALYZE`. Correlated columns are the
other common cause — the planner assumes independence and can underestimate by an order of magnitude.

**Q: What is the most misread number in an `EXPLAIN` plan?**
`loops`. Actual time is reported per loop, so a node at 0.5 ms with `loops=10000` consumed five
seconds.

## Mini task

1. Build session login with a plain HTTP server: `SecureRandom` id, an in-memory map, and the full
   cookie flag set. Inspect the cookie in devtools.
2. Demonstrate session fixation: capture a pre-login session id, log in, and confirm the same id is
   still valid. Then add `changeSessionId()` and confirm the attack fails.
3. Remove `HttpOnly` and read the cookie from the console. Put it back.
4. Set `SameSite=Lax` and build a cross-site form `POST` that fails, then a cross-site `GET` that
   succeeds — demonstrating why `Lax` is not complete CSRF protection.
5. Move the session store to Redis with a TTL. Kill the app, restart it, and confirm the session
   survives.
6. Run two app instances behind a load balancer with in-memory sessions and observe random logouts.
7. Implement both an idle and an absolute timeout, and prove a polling client cannot extend past the
   absolute one.
8. Take a slow query. Run `EXPLAIN (ANALYZE, BUFFERS)`, find the node with the largest
   estimated-vs-actual divergence, run `ANALYZE`, and compare plans.
9. Build correlated columns (`city`, `state`) over 500,000 rows, observe the underestimate, then add
   extended statistics and observe the corrected estimate.
10. Set `random_page_cost` to 1.1 and re-plan a query that was doing a sequential scan.

## 🎙️ Articulation drill

Two minutes: **"Sessions or JWTs — which would you choose and why?"**

Do not answer with a preference. Give the trade-off table's decisive rows — revocation, XSS exposure,
wire size, and where state lives — then the recommendation with its context: sessions for a browser
app with one backend, tokens for mobile and service-to-service. Close on revocation as the factor
that usually decides it, because "log out everywhere" is a requirement almost every product
eventually has.
