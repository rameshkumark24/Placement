# Day 160 ⭐

**L-160** · Lazy vs eager, the N+1 problem, and `LazyInitializationException`

**Time:** 3+ hrs · **Mode:** NEW · **Marquee day**

> **The most consequential day in the Data block, and the most commonly asked JPA interview question
> in existence.** N+1 is not an exotic edge case — it is the *default behaviour* of an ORM used
> naively, and it is why "we added JPA and the app got slow" is a story every Java developer has
> heard.
>
> Day 157 named the root cause: **object code navigates one reference at a time; SQL wants the whole
> shape in one round trip.** Today is that gap, in full, with every failure mode it produces.

# Part 1 — The problem, in numbers

```java
@Transactional(readOnly = true)
public List<OrderSummary> recentOrders() {
    List<Order> orders = repo.findTop100ByOrderByPlacedAtDesc();     // ⭐ 1 query
    return orders.stream()
        .map(o -> new OrderSummary(o.getId(),
                                   o.getCustomer().getName(),        // ⭐ +1 query each
                                   o.getItems().size()))             // ⭐ +1 query each
        .toList();
}
```

```
select * from orders order by placed_at desc limit 100;    -- 1
select * from customers where id = ?;                      -- ×100
select * from order_items where order_id = ?;              -- ×100
                                                    ⭐ 201 queries
```

**Each query is fast — 0.5 ms.** The problem is the round trips: 201 × 1 ms network latency ≈ **200 ms
of pure waiting**, for data one query could have returned in 3 ms. On a cloud database across an
availability zone, latency is higher and the endpoint takes over a second.

**And this is why it survives to production:** with 5 test rows it is 11 queries and 4 ms. Nothing
is slow. It scales linearly with data volume, so it appears gradually and correlates with growth
rather than with any deploy.

## The three ways it hides

1. **`open-in-view: true`** (Day 139) — the lazy loads fire during **JSON serialization**, after your
   service method returned. A profiler pointed at the service shows nothing.
2. **A `toString()` that touches a relationship** — one `log.debug("{}", order)` in a loop and you
   have an N+1 that only exists when debug logging is on.
3. **Mapping in a stream** — as above; the `.map()` looks like pure in-memory work.

## Detecting it, which is the actual skill

```java
@Test
void recentOrdersIssuesOneQuery() {
    SQLStatementCountValidator.reset();
    service.recentOrders();
    SQLStatementCountValidator.assertSelectCount(1);       // ⭐ db-util library
}
```

**Asserting the query count in a test is the only durable fix.** Any other approach — code review,
vigilance, a runbook — decays. A test fails the build the day someone adds a `getCustomer()` call
inside a loop, which is exactly when it is cheap to fix.

In development, `datasource-proxy` (Day 157) logs the per-transaction query count. In production,
Day 143's `hikaricp_connections_acquire` and the query metrics tell you a pool is churning. **But
the test is the control.**

# Part 2 — Why eager fetching is not the fix

The instinct is to set `fetch = EAGER`. It replaces one problem with three worse ones.

### ⭐ 1 — Eager is transitive and unbounded

```java
class Order    { @ManyToOne(fetch = EAGER) Customer customer; }
class Customer { @ManyToOne(fetch = EAGER) Organisation org; @OneToMany(fetch = EAGER) List<Address> addresses; }
class Organisation { @OneToMany(fetch = EAGER) List<Department> departments; }
```

`repo.findById(orderId)` now loads the order, the customer, the organisation, every department and
every address — **on every query, forever, whether you need them or not.** You cannot turn it off at
the call site. `LAZY` is a decision you can override per query; `EAGER` is one you cannot.

### ⭐ 2 — Eager cannot be undone, but lazy can be overridden

This is the asymmetry that settles the argument:

- `LAZY` + `join fetch` when needed = exactly what you want, per query.
- `EAGER` + "just this once, don't" = **impossible.** There is no `@Query` hint that makes an eager
  association lazy.

**So `LAZY` everywhere is the only strategy that leaves you options.**

### ⭐ 3 — Eager makes `findAll` catastrophic

An eager `@OneToMany` on a `findAll` over 1,000 orders issues 1,001 queries — the N+1 you were trying
to avoid, now unavoidable — or produces a cartesian product join returning 50,000 rows to build
1,000 objects.

**The verdict:**

> **`fetch = LAZY` on every association, always. Then fetch what you need, per query, explicitly.**

```java
@ManyToOne(fetch = FetchType.LAZY)  @JoinColumn(name = "customer_id") private Customer customer;
@OneToOne(fetch = FetchType.LAZY,  optional = false)                 private Invoice invoice;
@OneToMany(mappedBy = "order")   /* lazy by default */               private List<OrderItem> items;
```

# Part 3 — `LazyInitializationException`, and why it is a *good* exception

```
org.hibernate.LazyInitializationException:
    could not initialize proxy [com.acme.Customer#42] - no Session
```

**What it means:** you touched a lazy association after the persistence context closed. The proxy
holds an id and a reference to a session; the session is gone; it cannot load.

**Where it happens:** in the controller or during serialization, once `open-in-view: false`.

## ⭐ The four "fixes", ranked — and the ranking is the point

| Fix | Verdict |
|---|---|
| **1. Fetch what you need in the query** (`join fetch`, entity graph, projection) | ⭐⭐ **the correct answer.** State the shape you need up front |
| **2. Map to a DTO inside the transaction** | ⭐ correct. The boundary is explicit |
| 3. `open-in-view: true` | ❌ **hides it.** The N+1 still happens, now during serialization, holding a connection |
| 4. `fetch = EAGER` | ❌ makes it global and permanent |
| 5. `Hibernate.initialize()` in a loop | ❌ that *is* the N+1, written by hand |

**And the framing that matters:**

> **`LazyInitializationException` is not a bug to suppress. It is Hibernate telling you that you
> asked for data you did not fetch — a design question surfacing at exactly the right moment.**

With `open-in-view: false` it fails loudly in a test. With `true` it succeeds and costs you 200
queries in production. **The exception is the cheaper outcome**, which is why Day 157 said turning
that setting off surfaces bugs rather than causing them.

# Part 4 — Fixing it: the four techniques

### 1. `join fetch` — for a single collection

```java
@Query("select distinct o from Order o join fetch o.items where o.placedAt > :since")
List<Order> findRecentWithItems(@Param("since") Instant since);
```

**One query.** Three caveats:

- **`distinct` is needed** because joining a collection multiplies parent rows. In Hibernate 6 the
  duplicates are removed in memory automatically, but the *database* still returns the multiplied
  rows — so the network cost is real either way.
- ⭐ **Two collection `join fetch`es produce a cartesian product.** 10 items × 5 payments = 50 rows
  per order. Hibernate 6 throws `MultipleBagFetchException` for two `List`s; with `Set`s it silently
  builds the product. **One collection per query, maximum.**
- ⭐ **Never with `Pageable`** — Day 152's in-memory pagination. Turn on
  `fail_on_pagination_over_collection_fetch` (Day 157) so it throws.

### 2. `@EntityGraph` — declarative, and composable with derived queries

```java
@EntityGraph(attributePaths = {"customer", "items"})
List<Order> findByStatus(OrderStatus status);
```

Cleaner than JPQL for `@ManyToOne`s, and it works on Spring Data's derived query methods. Same
collection constraint applies.

### 3. ⭐ `@BatchSize` — the fix that scales to the whole application

```java
@OneToMany(mappedBy = "order")
@BatchSize(size = 25)                              // ⭐ Hibernate-specific
private List<OrderItem> items;
```

```sql
select * from order_items where order_id in (?,?,?, ... 25 ids);
```

**100 queries become 4.** It does not eliminate the extra queries; it makes their count sublinear.

**Set a global default and forget it:**

```yaml
spring.jpa.properties.hibernate.default_batch_fetch_size: 25
```

**This one line is the highest-value-per-effort setting in the entire Data block.** It turns every
unnoticed N+1 in the application into an N/25+1, which is usually the difference between a latency
problem and no problem at all. It is not a substitute for fetching correctly, but it is an excellent
floor.

### 4. ⭐ Projections — the best answer for reads

```java
public record OrderSummary(UUID id, String customerName, BigDecimal total) {}

@Query("""
    select new com.acme.order.OrderSummary(o.publicId, c.name, o.total)
    from Order o join o.customer c
    where o.placedAt > :since
""")
List<OrderSummary> summaries(@Param("since") Instant since);
```

**One query, three columns, no entities, no proxies, no persistence context overhead, and N+1 is
structurally impossible** — there is no lazy reference to trigger.

This is Day 147's argument arriving from the database side, and it is why that day ranked query
projection as the best mapping strategy for reads. Day 161 covers projections in full.

## The decision table

| Situation | Use |
|---|---|
| Read-only, shipping a DTO | ⭐ **projection** |
| Need the entity graph to modify it | `join fetch` / `@EntityGraph` |
| Several `@ManyToOne`s | `@EntityGraph` |
| More than one collection | ⭐ **two queries**, or `@BatchSize` |
| Paginated + a collection | ⭐ `@BatchSize` — never `join fetch` |
| Safety net across the app | ⭐ `default_batch_fetch_size: 25` |

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Leaving `@ManyToOne`/`@OneToOne` eager | transitive, unbounded, unoverridable |
| "Fixing" `LazyInitializationException` with `open-in-view: true` | hides an N+1 and holds a connection through serialization |
| `Hibernate.initialize()` in a loop | hand-written N+1 |
| Two collection `join fetch`es | cartesian product or `MultipleBagFetchException` |
| `join fetch` with `Pageable` | pagination in memory over the whole table |
| Omitting `distinct` | duplicate parents |
| No `default_batch_fetch_size` | every missed N+1 stays linear |
| Returning entities from the service | Day 147 — lazy loads outside the transaction |
| `toString()` touching a relationship | N+1 that appears only with debug logging |
| No query-count test | the fix regresses within a quarter |

## Interview questions

**Q: What is the N+1 problem?**
One query returns N parents, then accessing a lazy association on each issues one more query — N+1
total. Each is fast, but the round trips dominate: 201 queries at 1 ms of latency is 200 ms for data
one query returns in 3 ms. It hides in development because it scales with row count.

**Q: Solve it with eager fetching?**
No. Eager is transitive, so you load a graph you never asked for on every query; it makes `findAll`
catastrophic; and critically it cannot be overridden per query, whereas lazy can be. Lazy plus
explicit fetching is the only strategy that keeps the decision at the call site.

**Q: What does `LazyInitializationException` really tell you?**
That I asked for data I did not fetch. It is a design question surfacing at the right time. The fix
is to fetch it in the query or map to a DTO inside the transaction — not `open-in-view`, which just
moves the same N+1 into serialization while holding a database connection.

**Q: How do you stop N+1 coming back?**
A test that asserts the query count. Everything else — review, vigilance, documentation — decays.
And `default_batch_fetch_size` globally as a floor, so the ones I miss are sublinear rather than
linear.

**Q: Why can't you `join fetch` two collections?**
It produces a cartesian product — 10 items and 5 payments give 50 rows per parent. Hibernate throws
`MultipleBagFetchException` for two `List`s, and silently builds the product for `Set`s. One
collection per query; batch-fetch or a second query for the rest.

3. Set `open-in-view: false` and hit `LazyInitializationException`. Do not fix it yet — read it.
4. Fix it with `join fetch` + `distinct`. Count queries.
5. Try two collection `join fetch`es. Get `MultipleBagFetchException`. Switch to `Set` and count the
   rows returned.
6. Try `join fetch` with `Pageable`. Find `HHH90003004`. Turn on

8. Rewrite as a projection. Count queries and compare latency against every previous version.

   the test fail.
