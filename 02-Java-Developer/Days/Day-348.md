# Part 1 — ⭐ Requirements and the shape they force

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| `get(key)`, `put(key, value)`, `delete(key)` | ⭐⭐ **always writeable — availability over consistency** |
| ⭐ Values up to ~1 MB | ⭐ **tunable consistency per operation** |
| ⭐ **Tunable N, W, R** | ⭐ low latency: p99 < 10 ms |
| No queries by value, no joins, no transactions | ⭐ **linear scaling by adding nodes** |
| Optional TTL | ⭐ no single point of failure — **no leader at all** |

> **⭐ The defining decision, stated first: leaderless.** Every node can accept a write for any key it
> replicates. **That is what buys "always writeable" — and it is what forces every hard problem
> today**, because with no single ordering authority, conflicts are inevitable (Day 328).

```
⭐ ESTIMATE
⭐   100k writes/s, 500k reads/s · 1 KB average value
⭐   ⭐ 100k × 1 KB × 86,400 = 8.6 TB/day raw ⇒ ⭐ ×3 replicas = 26 TB/day
⭐   ⇒ ⭐ at 10 TB usable per node, ~100 nodes just for a few days of retention
⭐   ⇒ ⭐⭐ so: many nodes, cheap disks, and the storage engine matters enormously
```

# Part 2 — ⭐ Placement, replication, and membership

## ⭐ The ring (Day 326)

```
⭐ hash(key) → a point on the ring → ⭐ the first N distinct physical nodes clockwise are the replicas
⭐ ⭐ 150+ virtual nodes per physical node, or load is 2–3× uneven and removals dump on one neighbour
```

| ⭐ Property | |
|---|---|
| ⭐ Adding a node moves ~1/N of keys | ⭐ **not 80%** (Day 326) |
| ⭐ **Any node can route** | it knows the ring, so it forwards or serves — **no separate router tier** |
| ⭐ Weighting is free | a bigger machine gets more virtual nodes |

## ⭐ Quorums (Day 328)

```
⭐ N = 3 replicas · ⭐ W + R > N ⇒ overlap ⇒ you see the latest write
⭐   W=2, R=2  ⭐ the default — survives one node down for both reads and writes
⭐   W=1, R=1  ⭐ fastest, ⭐⭐ stale reads expected
⭐   W=3, R=1  fast reads, ⭐ no write availability if any replica is down
```

⚠️ **And repeat Day 328's honesty: `W + R > N` is a heuristic, not linearizability.** With concurrent
writes, sloppy quorums or a partially-failed write, **you can still read stale or conflicting data.**
Say it before being asked.

## ⭐ Availability tricks

| Mechanism | ⭐ What it does |
|---|---|
| ⭐ **Sloppy quorum** | ⭐ if a replica is unreachable, write to the **next healthy node** instead |
| ⭐ **Hinted handoff** | ⭐⭐ that substitute holds a *hint* and delivers it when the real owner returns |
| ⭐ Read repair | a read that sees divergent replicas fixes them inline |
| ⭐ **Anti-entropy (Merkle trees)** | ⭐ background comparison — **exchange hashes, not data**, so only differing ranges are shipped |
| ⭐ Gossip | ⭐ membership and failure detection with no coordinator |

> **⭐ Merkle trees are worth thirty seconds: each node builds a hash tree over its key ranges, and
> two replicas compare roots.** Equal roots means identical data with one comparison; **differences
> narrow down the tree**, so repairing a terabyte of mostly-identical data costs kilobytes of
> comparison.

# Part 3 — ⭐⭐ Deep dive A: conflict resolution

```
⭐ Node 1 (partitioned) : put("cart", [milk])
⭐ Node 2 (partitioned) : put("cart", [bread])
⭐ ⇒ ⭐⭐ Two values, no ordering between them. Which is "right"?
```

| ⭐ Strategy | ⭐ Verdict |
|---|---|
| ⭐ **Last-write-wins by timestamp** | ⭐⭐ **simple, and it DISCARDS a write — decided by unsynchronised clocks** (Day 328) |
| ⭐⭐ **Vector clocks + siblings** | ⭐⭐ **detects concurrency instead of guessing; the client resolves** |
| ⭐ CRDT values | ⭐ merge automatically — **only for types with a commutative merge** (Day 331) |
| Application merge | correct, and it is now your caller's problem |

## ⭐ Vector clocks in one breath

```
⭐ A version is a map: {nodeA: 2, nodeB: 1}
⭐ ⭐ V1 dominates V2 if every counter in V1 ≥ V2's ⇒ V2 is an ancestor, discard it.
⭐ ⭐ Neither dominates ⇒ ⭐⭐ CONCURRENT ⇒ keep BOTH as siblings and return both on read.
```

| ⭐ Point | |
|---|---|
| ⭐ **It detects concurrency; it does not resolve it** | ⭐ the store returns siblings and the client merges |
| ⭐ The shopping-cart example is canonical | ⭐ **union the carts — losing an item is worse than an extra one** |
| ⭐ **Clocks grow** | truncation is needed; **truncation can create false conflicts** |
| ⭐ Cassandra chose LWW instead | ⭐ **simpler API, at the price of silent loss — a defensible product decision** |

> **⭐ The judgement to voice: vector clocks push the problem to the application, which is correct
> when only the application can decide (a cart, a document) and unhelpful when it cannot.** Most
> systems take LWW and accept the loss — **but they should know they took it.**

# Part 4 — ⭐⭐ Deep dive B: the storage engine, and why writes are fast

```
⭐ LSM TREE (log-structured merge):
⭐  1. append to a WAL (durability)
⭐  2. insert into an in-memory MEMTABLE (sorted)
⭐  3. when full ⇒ ⭐ flush to disk as an immutable SSTable — ⭐ SEQUENTIAL WRITE
⭐  4. background COMPACTION merges SSTables, discarding overwritten and deleted keys
```

| | ⭐ LSM tree | ⭐ B-tree (Day 190) |
|---|---|---|
| ⭐ **Writes** | ⭐⭐ **sequential, append-only — very fast** | random page writes |
| ⭐ **Reads** | ⭐ **may check several SSTables — slower** | one tree descent |
| Space | ⭐ compaction reclaims; **temporary amplification** | in-place, fragmentation |
| ⭐ **Amplification** | ⭐ high **write** amplification from compaction | high **read-modify-write** cost |
| Used by | ⭐ Cassandra, RocksDB, LevelDB, HBase | PostgreSQL, MySQL/InnoDB |

**⭐ Two mechanisms that make reads survivable, and both are worth naming:**

| Mechanism | ⭐ Effect |
|---|---|
| ⭐⭐ **A Bloom filter per SSTable** | ⭐⭐ **answers "definitely not here" in memory — most SSTables are skipped without touching disk** |
| ⭐ A sparse index + sorted blocks | one seek to the right block |

⚠️ **Deletes are tombstones**, not removals — an immutable file cannot be edited. **A tombstone must
outlive any replica that might still hold the old value**, or a repair resurrects deleted data. **That
is why Cassandra's `gc_grace_seconds` exists, and why deleting a lot of data makes reads slower
before it makes them faster.**

> **⭐ The whole point in one line: an LSM tree trades read effort and background CPU for sequential
> writes** — which is exactly the right trade for a write-heavy, cheap-disk, many-node store.

# Part 5 — ⭐ Failure, and what breaks

| ⭐ Failure | ⭐ Behaviour |
|---|---|
| ⭐ One replica down | ⭐ W=2, R=2 keeps working; hinted handoff covers the gap |
| ⭐⭐ **Partition** | ⭐⭐ **both sides accept writes at low consistency levels — divergence, resolved later** (Day 330: PA/EL) |
| ⭐ Node permanently lost | its ranges rebuild from replicas; **only ~1/N of keys move** |
| ⭐ **Compaction storm** | ⭐ background I/O starves foreground reads — **throttle it, and alert on pending compactions** |
| ⭐ Hot key | ⭐ **hashing puts it on one node — split the key** (Day 326) |
| ⭐ **Wide partition** | ⭐⭐ one key with millions of values — **an unbalanced node and slow reads** |

```
⭐ MONITOR: p99 by consistency level · ⭐ pending compactions · hinted handoff backlog
⭐          ⭐ sibling count (rising = a merge bug) · ⭐ tombstone ratio · per-node load skew
⭐ CUT:     secondary indexes, transactions, range scans across partitions
⭐ AT 10×:  ⭐ add nodes — that IS the design. Nothing structural changes.
```

---

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Consistent hashing without virtual nodes | 2–3× load skew (Day 326) |
| ⭐⭐ Claiming `W + R > N` is strong consistency | ⭐⭐ **it is a heuristic** |
| ⭐ LWW with no acknowledgement of loss | ⭐ silent data loss, decided by clocks |
| ⭐ Vector clocks with no truncation plan | unbounded metadata |
| Truncating clocks carelessly | false conflicts |
| ⭐ **Forgetting tombstones and grace periods** | ⭐⭐ **deleted data resurrects after a repair** |
| ⭐ Mass deletes then wondering why reads slowed | ⭐ tombstones are scanned |
| ⭐ Unthrottled compaction | background I/O starves reads |
| ⭐ **Wide partitions** | one node carries a key that will not fit |
| Expecting range scans across the ring | hashing destroyed the ordering |
| Adding secondary indexes casually | ⭐ they are scatter-gather or eventually consistent (Day 329) |

## Interview questions

**Q: How do you place and replicate data?**
Consistent hashing with virtual nodes: the key hashes to a point on the ring and the first N distinct
physical nodes clockwise are its replicas. Virtual nodes matter — with one point per node the load is
two or three times uneven and removing a node dumps its whole range on one neighbour. Every node
knows the ring, so any node can route, which removes a separate router tier.

**Q: How do you handle a write during a partition?**
At low consistency levels both sides accept it, which is the point of a leaderless design — always
writeable. Sloppy quorums let a write go to the next healthy node with a hint, delivered when the
real owner returns. The cost is divergence, repaired later by read repair and by anti-entropy using
Merkle trees, which compare hashes rather than data so a terabyte of mostly-identical replicas costs
kilobytes to reconcile.

**Q: Two clients write the same key concurrently. What happens?**
With last-write-wins, one is silently discarded and unsynchronised clocks decide which — a node two
hundred milliseconds fast wins every conflict. With vector clocks the store detects that neither
version dominates and returns both as siblings for the client to merge, which is right for a shopping
cart where losing an item is worse than gaining one. Vector clocks detect concurrency; they do not
resolve it, so the application still has to decide.

**Q: Why are writes fast?**
The storage engine is an LSM tree. A write appends to a log and goes into a sorted in-memory table;
when that fills it is flushed as an immutable file, so all disk writes are sequential. The cost is
paid on reads, which may consult several files, and on background compaction. A Bloom filter per file
makes most of those consultations free by answering "definitely not here" from memory.

**Q: What is a tombstone and why does it matter?**
A delete marker, because immutable files cannot be edited. It must live longer than any replica that
might still hold the old value, or a repair resurrects deleted data — hence a grace period. It also
means deleting a lot of data makes reads slower before it makes them faster, since tombstones are
scanned until compaction clears them, which surprises people operating these systems for the first
time.

## 🎙️ Articulation drill

**Three minutes:** *"Why can this store take so many writes?"*

**⭐ The strong answer is two mechanisms, not one.** Horizontally: **consistent hashing spreads keys
across many nodes and any node can accept a write, because there is no leader to serialise on.**
Vertically: **the LSM engine turns every write into a sequential append, so a single node's write
throughput is far above what a B-tree can do.**

**⭐ Then close with what it cost** — reads consult several files, compaction burns background I/O,
deletes leave tombstones, and concurrent writes conflict because nothing ordered them. **Naming the
bill is what makes the answer credible.**
