# Part 1 — `@Value` vs `@ConfigurationProperties`

```java
// Style A — @Value
@Service
public class PaymentService {
    @Value("${payment.gateway.url}") private String url;
    @Value("${payment.gateway.timeout-ms:5000}") private int timeoutMs;
    @Value("${payment.gateway.api-key}") private String apiKey;
}
```

```java
// Style B — @ConfigurationProperties  ⭐
@ConfigurationProperties(prefix = "payment.gateway")
@Validated
public record PaymentGatewayProperties(
        @NotBlank String url,
        @Positive @DefaultValue("5000") int timeoutMs,
        @NotBlank String apiKey) { }
```

**B is the default choice, and the reasons are not stylistic:**

| | `@Value` | `@ConfigurationProperties` |
|---|---|---|
| Missing property | fails at **bean creation**, one at a time, mid-startup | fails at **binding**, all violations reported together |
| Validation | none | JSR-380 via `@Validated` — Day 148's machinery |
| Type safety | string coercion, silent surprises | bound and converted, with relaxed binding |
| Discoverability | grep the codebase for `${` | one class lists the whole contract |
| IDE completion in `application.yml` | none | yes, via the metadata processor |
| Testability | needs a Spring context | plain object; construct it in a unit test |
| Relaxed binding | no | yes |

**Wire it up:**

```java
@ConfigurationPropertiesScan          // on the main class — finds all @ConfigurationProperties
@SpringBootApplication
public class OrdersApplication { }
```

Then inject the record like any other bean. Note what this gives you: `PaymentService` now takes
`PaymentGatewayProperties` in its constructor, so a unit test constructs one directly with no Spring
at all — Day 131's argument for constructor injection, paying off in configuration.

## Relaxed binding, and why it exists

All of these bind to `timeoutMs`:

```
payment.gateway.timeout-ms=5000        ← kebab-case, ⭐ canonical form for files
payment.gateway.timeoutMs=5000
payment.gateway.timeout_ms=5000
PAYMENT_GATEWAY_TIMEOUTMS=5000         ← environment variable
PAYMENT_GATEWAY_TIMEOUT_MS=5000        ← ⭐ the one you use in Docker/Kubernetes
```

**This is why it exists:** environment variables cannot contain dots or hyphens on most systems, and
uppercase-with-underscores is the universal convention. Relaxed binding is the bridge between
`application.yml` conventions and the environment-variable world Day 129B put you in. Without it,
twelve-factor configuration in Java would be miserable.

**Note the asymmetry:** relaxed binding applies to `@ConfigurationProperties`. `@Value("${a.b-c}")`
matches literally. One more reason for B.

# Part 2 — The precedence order, and the two entries that matter most

Day 138 listed it. The operative slice, **later wins**:

```
1. application.yml inside the jar                    ← your defaults
2. application-{profile}.yml inside the jar          ← profile overlays
3. application.yml outside the jar (./config/)       ← ops overrides
4. OS environment variables                          ← ⭐ containers, Kubernetes
5. Java system properties (-D)
6. Command-line arguments (--server.port=9090)       ← ⭐ highest, wins everything
```

**Entry 4 is the one that makes containers work.** Your image ships with sane defaults baked in;
Kubernetes injects `SPRING_DATASOURCE_URL` and `PAYMENT_GATEWAY_API_KEY` at pod start; the same image
runs in staging and production with different behaviour and no rebuild.

**Entry 6 is the one that saves an incident.** `java -jar app.jar --logging.level.com.acme=DEBUG`
overrides everything without touching a file or an image.

**Prove the order rather than believing it:**

```
GET /actuator/env/payment.gateway.timeout-ms
```

Actuator (Day 143) reports **every source that has an opinion on that key, in order, with the winner
marked**. When someone insists "the config isn't taking effect", this endpoint ends the argument in
ten seconds.

# Part 3 — Profiles, and the two ways to use them

```yaml
# application.yml  — the defaults, always applied
payment:
  gateway:
    url: https://sandbox.payments.example.com
    timeout-ms: 5000

---
spring:
  config:
    activate:
      on-profile: prod                  # ⭐ Boot 2.4+ syntax
payment:
  gateway:
    url: https://payments.example.com
    timeout-ms: 2000
```

**Profiles layer, they do not replace.** With `prod` active you get the prod `url` and `timeout-ms`,
and every other key from the base document. This is exactly why Day 141 said a test
`application.yml` is a trap and `application-test.yml` is not.

**Activate:** `SPRING_PROFILES_ACTIVE=prod`, `--spring.profiles.active=prod`, or `@ActiveProfiles`
in tests. Multiple profiles are comma-separated and **later wins**: `prod,eu-west` means `eu-west`
overrides `prod`.

## ⭐ The use of profiles that is fine, and the use that is dangerous

**Fine — profiles change *values*:**

```yaml
spring.config.activate.on-profile: prod
payment.gateway.url: https://payments.example.com
logging.level.com.acme: INFO
```

**Dangerous — profiles change *code paths*:**

```java
@Service @Profile("!prod")  class FakePaymentGateway implements PaymentGateway { }
@Service @Profile("prod")   class StripePaymentGateway implements PaymentGateway { }
```

Day 136 raised this and it is worth restating with the consequence spelled out: **the class that runs
in production is now the one class no test ever exercises.** Every test, every local run, every CI
job runs `FakePaymentGateway`. `StripePaymentGateway` is first executed by real customers.

The fix is not "never fake the gateway" — you must. The fix is that the fake is chosen **by the
test**, not by the environment:

```java
@SpringBootTest
class CheckoutTest {
    @MockitoBean PaymentGateway gateway;        // this test's choice, explicit and local
}
```

and the real implementation is covered by a contract test against a sandbox or a WireMock recording
(Day 184). Same isolation, without a production code path that has never run.

## Profile groups

```yaml
spring.profiles.group.prod: prod-db, prod-cache, prod-metrics
```

`SPRING_PROFILES_ACTIVE=prod` now activates four. Useful; also a good way to be surprised by which
files are loaded, so keep the groups shallow.

# Part 4 — Secrets

Day 112 and Day 100A both landed on the same rule: **secrets do not live in the repository.** Boot
gives you three real options.

| Approach | How | Verdict |
|---|---|---|
| Environment variables | `SPRING_DATASOURCE_PASSWORD` | ✅ the baseline. Works everywhere. Visible in `/proc/<pid>/environ` and in crash dumps — acceptable for most, not for the highest tiers |
| **Config trees** | `spring.config.import: configtree:/run/secrets/` | ⭐ best fit for Kubernetes and Docker secrets. Each file's *name* is the property, its *content* the value. Never in the environment, never in the image |
| Vault / cloud secret manager | `spring-cloud-vault`, AWS Secrets Manager | ✅ rotation, audit, dynamic credentials. Real operational cost |

```
/run/secrets/
├── payment.gateway.api-key       → contents become the value of payment.gateway.api-key
└── spring.datasource.password
```

**Whichever you choose, do these three:**

1. **Never log a properties object.** A `record` with an `apiKey` field will print the key in every
   `toString()`, including inside a stack trace or a debug log. Either mark the field or wrap it:

   ```java
   public record PaymentGatewayProperties(String url, int timeoutMs, String apiKey) {
       @Override public String toString() {
           return "PaymentGatewayProperties[url=%s, timeoutMs=%d, apiKey=***]".formatted(url, timeoutMs);
       }
   }
   ```

2. **Secure `/actuator/env` and `/actuator/configprops`** — they dump configuration. Boot sanitises
   keys matching `password`, `secret`, `key`, `token` by default, but `payment.gateway.credential`
   does not match, and the default sanitisation has been changed across versions. Day 143 covers
   locking the endpoints down; do not rely on sanitisation as the only control.

3. **Fail fast on a missing secret.** `@NotBlank` on the property means the application refuses to
   start rather than starting healthy and failing on the first customer payment. Day 133's argument:
   a startup failure is a deploy that rolls back; a runtime failure is an incident.

## Validation as a startup gate

```java
@ConfigurationProperties(prefix = "payment.gateway")
@Validated
public record PaymentGatewayProperties(
        @NotBlank String url,
        @Positive @Max(30_000) int timeoutMs,
        @NotBlank String apiKey) {
    public PaymentGatewayProperties {
        if (!url.startsWith("https://")) throw new IllegalArgumentException("gateway url must be https");
    }
}
```

Two layers: annotations for shape, the compact constructor for rules annotations cannot express. Both
run before the context finishes starting. **A misconfigured service should never reach the readiness
probe** (Day 128) — it should die loudly in the deploy.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| `@Value` everywhere | no validation, no types, contract scattered across 40 files |
| Profile-switched implementations | the production class is never tested (Day 097) |
| Secrets in `application.yml`, committed | Day 085 — the fix is rotation, not a delete commit |
| `toString()` on a properties record with a secret | keys in logs, and in every stack trace |
| Test `application.yml` instead of `application-test.yml` | replaces rather than layers |
| No validation on required properties | starts healthy, fails on first real request |
| Assuming precedence instead of checking `/actuator/env` | hours lost to "the config isn't applying" |
| `@Profile` on `@Configuration` used for feature flags | redeploy to flip a flag; use a real flag system |

## Interview questions

**Q: `@Value` or `@ConfigurationProperties`?**
`@ConfigurationProperties`, because it is validated, typed, relaxed-bound, and testable without a
Spring context — and because it puts the whole configuration contract for a feature in one file
instead of scattering `${}` across the codebase.

**Q: How do you configure the same image for three environments?**
Baked-in defaults in `application.yml`, profile overlays for values that differ, environment variables
for anything the platform injects, and secrets via config tree or a secret manager. The image never
changes; only the environment does.

**Q: What is relaxed binding for?**
Environment variables cannot contain dots or hyphens, so `PAYMENT_GATEWAY_TIMEOUT_MS` has to be able
to reach `payment.gateway.timeout-ms`. It is the bridge between YAML conventions and the container
world.

**Q: What is wrong with `@Profile("!prod")` on a fake payment gateway?**
The real implementation becomes the only class in the system that no test exercises. The fake should
be selected by the test, not by the environment.

## Mini task

1. Convert three `@Value` fields into one validated `@ConfigurationProperties` record. Add
   `@ConfigurationPropertiesScan`.
2. Delete a required property and start the app. Read the binding failure — note that it reports
   **all** violations at once.
3. Set the same property in `application.yml`, then override it with an env var, then override that
   with `--`. Confirm each step with `GET /actuator/env/<key>`.
4. Add `application-prod.yml` changing only `timeout-ms`. Start with `--spring.profiles.active=prod`
   and confirm the other properties survived.
5. Put a secret in a file under `./secrets/payment.gateway.api-key` and load it with
   `spring.config.import=configtree:./secrets/`.
6. Log the properties record and watch your key appear. Fix the `toString()`.

## 🎙️ Articulation drill

Two minutes: **"How do you handle configuration across environments?"**

Start from the constraint — one immutable image — so config must come from outside it. Defaults in
the jar, profile overlays for what differs, environment variables for what the platform injects,
config trees or a secret manager for secrets. Typed and validated properties classes so a
misconfiguration is a failed deploy rather than a 3 a.m. page. Then say what you deliberately do
*not* do: swap implementations by profile, because that leaves the production path untested.
