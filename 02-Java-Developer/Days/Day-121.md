# Part 1 — Why invalidation is hard

**Because a cache is a second copy of the truth, and the two can disagree.** Every strategy is a
choice about *how much* disagreement you accept and for how long.

```
Source of truth ──► Cache ──► Client
        │              │
        └── changes ───┘  … when? how? who tells whom?
```

The difficulty compounds with distribution: with ten application instances each holding an in-process
cache, "invalidate" means a message to ten places, any of which may miss it, and any of which may be
mid-read when it arrives.

# Part 2 — TTL strategy

The simplest approach and, for a great many cases, the correct one.

```java
cache.set(key, value, Duration.ofMinutes(5));
```

> **The question is not "how long is the data valid?" It is "how stale can this be before someone is
> harmed?"**

| Data | TTL | Reasoning |
|---|---|---|
| Reference data (countries, currencies) | hours–days | Changes almost never |
| Product catalogue | 5–15 min | Slight staleness is acceptable |
| User profile | 1–5 min | Users notice their own edits |
| Search results | 30–60 s | Freshness matters |
| Inventory count | 5–30 s | Overselling has a cost |
| Account balance | ❌ **do not cache** | Staleness is a correctness bug |
| Session data | = session lifetime | |
| Aggregates / reports | 5–60 min | Expensive to compute, rarely urgent |

## ⭐ TTL jitter

**The most under-used caching technique**, and the fix for a specific real outage shape:

```java
// ❌ everything cached at the same moment expires at the same moment
cache.set(key, value, Duration.ofMinutes(5));

// ✅ spread expiry across a window
Duration ttl = Duration.ofMinutes(5).plusSeconds(ThreadLocalRandom.current().nextInt(60));
cache.set(key, value, ttl);
```

A deploy warms 10,000 keys in a few seconds. Without jitter, **all 10,000 expire within the same few
seconds five minutes later**, and every one of them misses simultaneously. The database sees its
entire working set requested at once.

This is the same principle as Day 062's retry jitter and Day 071's livelock fix: **randomness breaks
synchronisation.** Recognising it as one idea appearing in three places is worth stating in an
interview.

# Part 3 — Cache stampede

Also called the **thundering herd** or **dogpile**.

```
A popular key expires.
1,000 concurrent requests all miss.
1,000 identical queries hit the database SIMULTANEOUSLY.
The database saturates. Latency climbs. More requests queue. The cache never gets repopulated.
```

**The failure mode is self-reinforcing**, which is why it takes systems down rather than merely
slowing them: the slower the source gets, the longer the window during which more requests miss.

## Fix 1 — Locking / single-flight ⭐

**Only one caller recomputes; the rest wait for that result.**

```java
public Order get(String id) {
    Order cached = cache.get(key(id));
    if (cached != null) return cached;

    String lockKey = "lock:" + key(id);
    if (redis.setIfAbsent(lockKey, token, Duration.ofSeconds(10))) {     // SET NX PX
        try {
            Order fresh = repository.findById(id).orElseThrow();
            cache.set(key(id), fresh, jitteredTtl());
            return fresh;
        } finally {
            redis.deleteIfValueMatches(lockKey, token);   // ← only if WE still hold it
        }
    }
    // someone else is recomputing — brief wait, then re-read
    Thread.sleep(50);
    Order retry = cache.get(key(id));
    return retry != null ? retry : repository.findById(id).orElseThrow();   // bounded fallback
}
```

Three details that make it correct:

- **A TTL on the lock**, so a crashed holder does not block everyone forever.
- **A token, released only if it still matches** — otherwise a slow holder deletes a lock a *later*
  holder acquired (this is the same check-then-act problem as Day 065).
- **A bounded fallback** — waiters must not loop indefinitely.

In-process this is far simpler: `Caffeine`'s loading cache and `CompletableFuture` deduplication
(Day 069) give you single-flight for free. **This is the same pattern as Day 115's refresh
single-flight**, which is worth noticing — the problem shape recurs.

## Fix 2 — Probabilistic early expiration

Elegant, and it eliminates the miss entirely rather than managing it:

```java
// XFetch: the closer to expiry, the more likely a given request refreshes EARLY
long remaining = expiryTime - now;
double beta = 1.0;
if (remaining <= 0 ||
    -Math.log(ThreadLocalRandom.current().nextDouble()) * beta * computeTimeMs > remaining) {
    refreshInBackground(key);          // this caller refreshes; everyone still gets the cached value
}
return cached;
```

**Nobody ever waits**, and the probability of a *simultaneous* refresh is negligible because each
request rolls independently. It also scales with `computeTimeMs`, so expensive entries are refreshed
earlier.

## Fix 3 — Stale-while-revalidate ⭐

The most practical, and the one you should reach for by default:

```
Serve the STALE value immediately.
Refresh in the BACKGROUND.
```

```java
public Order get(String id) {
    Entry<Order> e = cache.getWithMetadata(key(id));
    if (e == null) return loadAndCache(id);                    // genuine cold miss

    if (e.isStale() && staleLock.tryAcquire(id)) {
        executor.submit(() -> { try { loadAndCache(id); } finally { staleLock.release(id); } });
    }
    return e.value();                                          // ← always fast
}
```

HTTP standardises exactly this (Day 102):

```http
Cache-Control: max-age=60, stale-while-revalidate=300, stale-if-error=86400
```

- `max-age=60` — fresh for a minute.
- `stale-while-revalidate=300` — for five more minutes, serve stale *and* refresh in the background.
- **`stale-if-error=86400`** — if the origin is down, keep serving stale for a day.

**That last directive is a resilience feature, not a performance one.** A cache serving stale data
during an outage is often far better than an error page — for a product catalogue it may be
indistinguishable to the user.

## Fix 4 — Never expire; refresh proactively

```java
scheduler.scheduleAtFixedRate(() -> hotKeys.forEach(this::refresh), 0, 1, MINUTES);
```

For a small set of very hot keys, there is no expiry at all — a background job keeps them current, so
a miss is impossible. Correct for homepage content, feature flags and configuration; unworkable
beyond a bounded key set.

# Part 4 — Invalidation strategies

| Strategy | Freshness | Complexity |
|---|---|---|
| **TTL only** | Stale up to the TTL | ✅ trivial |
| **Invalidate on write** | Near-immediate | ⚠️ every writer must know every key |
| **Write-through** | Never stale | ⚠️ slower writes |
| **⭐ Versioned keys** | Never stale | ✅ **no invalidation at all** |
| **Event-driven** | Near-immediate | ❌ needs a message bus |
| **CDC** (change data capture) | Near-immediate | ❌ infrastructure, but catches *every* writer |

## Versioned keys — the technique to reach for

```java
// A version per entity, or per collection
long version = redis.incr("v:order:" + id);              // bumped on every write
String key = "order:" + id + ":v" + version;
```

**No invalidation message is ever sent.** Bumping the version makes every old key unreachable, and
those entries expire naturally under their TTL.

Why this is so good:

- **No race** — there is no window between "write" and "invalidate" (Day 120's stale-forever race
  cannot occur).
- **No distributed coordination** — every instance derives the same key from the same version.
- **Collection invalidation is free** — bump `v:orders:{tenantId}` and every cached list for that
  tenant becomes unreachable at once, without enumerating keys.

The cost is memory: superseded entries linger until their TTL. With a sane TTL and Redis eviction
(`allkeys-lru`), that is usually a non-issue.

## Invalidate on write — and its traps

```java
@Transactional
public void updateOrder(Order order) {
    repository.save(order);
    cache.delete(key(order.id()));
    cache.delete(listKey(order.customerId()));      // ⚠️ do not forget derived keys
}
```

Three problems, all real:

**1. Derived keys.** An order appears in `order:42`, in `orders:customer:17`, in
`orders:status:PAID`, and in a dashboard aggregate. Missing one leaves stale data with no expiry
pressure. **This is the strongest argument for versioned keys.**

**2. Transaction boundaries.** Invalidating *before* commit means a concurrent read repopulates the
cache from the pre-commit state.

```java
// ✅ invalidate AFTER commit
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override public void afterCommit() { cache.delete(key(order.id())); }
});
```

**3. Other writers.** A migration script, an admin tool, or a second service writing to the same
table will not invalidate anything. **CDC (Debezium reading the WAL) is the only approach that
catches every writer**, which is why it exists — and it is also why a TTL should always be present as
a backstop regardless of your invalidation strategy.

## Delete, do not update

```java
cache.delete(key);            // ✅ the next read repopulates from the source
cache.set(key, newValue);     // ⚠️ two concurrent writers can leave the older value cached
```

Deletion is idempotent and cannot store a stale value. Updating races.

# Part 5 — Eviction and operations

## Eviction policies

| Policy | Evicts | Good for |
|---|---|---|
| **LRU** | Least recently used | ✅ general purpose |
| **LFU** | Least frequently used | Stable hot sets; resists scan pollution |
| FIFO | Oldest inserted | Rarely right |
| **TTL / volatile-lru** | Expired first, then LRU among those with a TTL | ✅ Redis default choice |
| Random | Random | Cheap; surprisingly acceptable |

```
maxmemory 4gb
maxmemory-policy allkeys-lru        # evict any key when full
# volatile-lru — only keys WITH a TTL. ⚠️ if nothing has a TTL, writes FAIL with OOM.
```

**That warning is a real production incident**: `volatile-lru` with keys that have no TTL means Redis
has nothing it is permitted to evict, so it starts rejecting writes. Either set TTLs on everything or
use `allkeys-lru`.

**Scan pollution** is the case for LFU: a batch job reading every record evicts your hot set under
LRU, because everything it touched is "recently used". Redis's `allkeys-lfu` resists it, as does
Caffeine's **W-TinyLFU**, which is why Caffeine typically outperforms an LRU cache of the same size.

## Metrics that matter

```java
meterRegistry.counter("cache.requests", "result", "hit").increment();
```

```
Hit rate            ⭐ the headline number — below 80%, question the cache
Latency p50/p99     is the cache actually faster than the source?
Eviction rate       high ⇒ the cache is too small
Memory usage        approaching maxmemory?
Stampede events     lock acquisitions, background refreshes
Staleness           age of served entries
```

**Alert on hit rate dropping**, not only on cache errors. A cache quietly degrading to a 20% hit rate
is a database outage waiting for peak traffic.

## The failure question

> **What happens when the cache is unavailable?**

```java
try {
    Order cached = cache.get(key);
    if (cached != null) return cached;
} catch (RedisException e) {
    log.warn("cache unavailable, falling through", e);      // ← degrade, do not fail
}
return repository.findById(id).orElseThrow();
```

**Fail open for reads** — degrade to slow rather than broken (which is cache-aside's key advantage).
But be honest about the consequence: **if your database cannot survive 100% of traffic, a cache
outage becomes a total outage.** Load-shed and rate-limit (Day 122) so the fallback degrades
gracefully rather than collapsing.

And set a **short timeout on cache calls**. A Redis call that hangs for 30 seconds is worse than a
cache miss — you have added latency *and* lost the value.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Identical TTLs set together | Synchronised mass expiry; stampede |
| No stampede protection on hot keys | The database is saturated by identical queries |
| Invalidating before commit | A concurrent read repopulates stale data |
| Forgetting derived and list keys | Stale data with no expiry pressure |
| Assuming your app is the only writer | Migrations and other services bypass invalidation |
| No TTL when invalidating on write | One missed invalidation is permanent |
| `set` instead of `delete` on write | Concurrent writers leave the older value |
| `volatile-lru` with no TTLs | Redis rejects writes when full |
| LRU with periodic batch scans | The hot set is evicted |
| No hit-rate monitoring | Silent degradation until peak |
| Failing requests when the cache is down | An optimisation became a dependency |
| No timeout on cache calls | Added latency and no value |

## Interview questions

**Q: What is a cache stampede and how do you prevent it?**
A popular key expires and every concurrent request misses simultaneously, sending identical queries
to the source and often saturating it. Prevent it with single-flight locking, probabilistic early
expiration, or — usually best — stale-while-revalidate, which serves the stale value and refreshes in
the background so nobody ever waits.

**Q: Why add jitter to TTLs?**
Entries cached together otherwise expire together, so a deploy that warms 10,000 keys produces 10,000
simultaneous misses five minutes later. Jitter spreads expiry — the same principle as retry jitter and
the livelock fix.

**Q: What is stale-while-revalidate?**
Serve the expired value immediately while refreshing asynchronously. It is standardised in
`Cache-Control`, and `stale-if-error` extends it into a resilience feature: keep serving stale data
while the origin is down.

**Q: How would you invalidate a cache?**
Versioned keys where possible — bump a version on write and old keys become unreachable, so there is
no invalidation message, no race and no coordination, and collection invalidation is free. Otherwise
invalidate after commit, delete rather than update, and always keep a TTL as a backstop because other
writers exist.

**Q: Why delete rather than update on write?**
Deletion is idempotent and cannot store a stale value; two concurrent writers updating can leave the
older value cached.

**Q: What happens when your cache goes down?**
Reads should fail open and fall through to the source — but only if the source can absorb full
traffic. If it cannot, a cache outage becomes a total outage, so you also need load shedding and rate
limiting.

**Q: Which eviction policy?**
`allkeys-lru` generally. LFU when periodic scans would otherwise pollute the hot set.
`volatile-lru` only if everything genuinely has a TTL — otherwise Redis has nothing it may evict and
writes start failing.

## 🎙️ Articulation drill

Two minutes: **"How do you keep a cache consistent with the database?"**

Be honest that you are choosing an acceptable staleness rather than achieving consistency. TTL with
jitter as the baseline, versioned keys to avoid invalidation entirely, invalidate-after-commit where
you must, a TTL as a backstop because other writers exist, and stale-while-revalidate so expiry never
becomes a stampede. Close with the failure question — what happens when the cache is down — because
that is what separates a design from a feature.
