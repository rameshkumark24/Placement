# Day 290 ⭐🏗️

**P-290** · The risk engine I — re-deriving the rules, and making them explicable

**Time:** 3+ hrs · **Mode:** BUILD

> **⭐ A risk engine has a property that most software does not: being wrong is worse than being
> down.** An outage is noticed in minutes; a subtly wrong score is *believed*, acted upon, and
> discovered months later — if ever.
>
> **⭐ So the design goals are different.** Correctness, yes — but above all **determinism,
> reproducibility and explicability**, because a score nobody can explain is a score nobody should
> act on.

---

# Part 1 — ⭐ Extract the rules from the code, into language

**⭐ Before touching anything: write down every rule the current engine implements, in business
language, from the code.**

```markdown
# docs/RISK-RULES.md
| ID | ⭐ Rule (business language) | ⭐ Inputs | ⭐ Weight | ⭐ Source | ⭐ Why? |
|----|---------------------------|---------|--------|--------|------|
| R-01 | Entities with no activity in 90 days score higher | last_activity | 0.15 | RiskEngine:88 | ⭐ **unknown** |
| R-02 | More than 3 failed checks in 30 days | check_history | 0.30 | :112 | ⭐ **unknown** |
```

**⭐ The "why?" column will be mostly empty, and that is the finding.** A rule whose justification
nobody can state is a rule nobody can defend to a customer, a regulator, or the person it scored
badly.

**⭐ Three questions per rule, and each has a different consequence:**

| Question | ⭐ If the answer is no |
|---|---|
| ⭐ **Where did this weight come from?** | ⭐ it is a guess wearing a decimal point |
| ⭐ **What happens if the input is missing?** | ⭐ **a null becoming zero silently changes the score** |
| ⭐ **Can a human check this rule fired correctly?** | ⭐ the output is unverifiable |

**⭐ The second question is the one that produces silent wrongness.** A missing input treated as zero
is a *confident* answer computed from absent data — **and it looks identical to a real low-risk
score.** Day 150's `FAIL_ON_NULL_FOR_PRIMITIVES` argument, at the level that matters most.

---

# Part 2 — ⭐⭐ Rules as data, not as code

> **⭐⭐ The single most consequential change in this rebuild: if a rule weight requires a redeploy to
> change, the engine cannot be tuned, cannot be A/B tested, and cannot explain a historical score.**

```
⭐ ruleset:        id, version, effective_from, ⭐ status (DRAFT/ACTIVE/RETIRED)
⭐ rule:           ruleset_id, code, weight, threshold, enabled
⭐ assessment:     ⭐ ruleset_version, inputs (jsonb), score, ⭐ rule_contributions (jsonb)
```

**⭐ Four properties this buys, and each answers a question the current engine probably cannot:**

| Property | ⭐ The question it answers |
|---|---|
| ⭐ **Versioned rulesets** | ⭐ *"which rules produced this score?"* |
| ⭐ **Frozen inputs** | ⭐ *"what was it computed from?"* |
| ⭐ **Per-rule contributions** | ⭐⭐ *"why is this score 0.82?"* |
| Draft → active workflow | *"can I test a change before it affects anyone?"* |

**⭐ The third is the product feature disguised as an implementation detail.** Storing each rule's
contribution means an assessment can be explained line by line — **and "why did I score badly?" is
the question every risk system is eventually asked.**

**⭐ Day 198's `jsonb` judgement applies to the two `jsonb` columns**: inputs and contributions vary
in shape by rule, are read as a whole, and are not filtered on individually — **which is exactly the
case `jsonb` is for.** If you later filter on one input constantly, Day 198's answer is a generated
column, not a schema change.

# Part 3 — ⭐⭐ Determinism, and the four things that break it

> **⭐⭐ The same inputs and the same ruleset must always produce the same score. If they do not, the
> engine cannot be tested, cannot be audited, and cannot be trusted.**

**⭐ Find and eliminate all four:**

| # | Breaks determinism | ⭐ Fix |
|---|---|---|
| ⭐ 1 | ⭐ **`Instant.now()` inside a rule** | ⭐ pass an evaluation time in; ⭐ inject a `Clock` (Day 183) |
| ⭐ 2 | ⭐ **Reading current state instead of frozen inputs** | ⭐ snapshot inputs, then evaluate |
| ⭐ 3 | ⭐ **Iteration order over a `HashMap` or `HashSet`** | ⭐ ordered collections where order affects the result |
| ⭐ 4 | ⭐ **Floating-point accumulation order** | ⭐ `BigDecimal`, ⭐ **fixed rounding, fixed order** |

**⭐ Number 1 is the most common and the most subtle**: a rule that says "no activity in 90 days"
evaluated at a different moment gives a different answer, so **re-running an assessment produces a
different score and nothing is wrong.** Passing evaluation time as an explicit input makes the
assessment reproducible forever.

**⭐ Number 4 matters more than people expect.** `double` accumulation is order-dependent, so
parallelising rule evaluation — or merely reordering the rules — changes the score in the last
decimal place. **For a threshold-based decision that can flip an outcome.** `BigDecimal` with an
explicit scale and rounding mode, applied in a fixed order (Day 106).

## ⭐ The property test that proves it

```
⭐ For any inputs and any ruleset: evaluate twice → ⭐ identical scores
⭐ For any inputs: evaluate with the rules in a shuffled order → ⭐ identical scores
⭐ For any stored assessment: re-evaluate from its frozen inputs → ⭐ THE STORED SCORE
```

**⭐ The third is the reproducibility test and it is the centrepiece.** Run it across your entire
golden dataset (Day 288). **If any historical assessment cannot be reproduced from its own record,
you have found a Critical defect** — and fixing it is the most valuable thing in this rebuild.

# Part 4 — ⭐ Structure it so a human can follow it

## ⭐ One rule, one class, one test

```
⭐ interface RiskRule { RuleResult evaluate(RiskInputs inputs, RuleConfig config); }
⭐ RuleResult: ⭐ contribution, ⭐ triggered (boolean), ⭐ explanation (human-readable)
```

**⭐ Three properties this gives you** (Day 254's rich-domain argument, applied):

| | |
|---|---|
| ⭐ 1 | ⭐ **Each rule is unit-testable with `new`** — no Spring, milliseconds |
| ⭐ 2 | ⭐ **The engine is a loop**, so the aggregation logic is tiny and reviewable |
| ⭐ 3 | ⭐ **Every rule carries its own explanation** — the audit trail writes itself |

**⭐ The `explanation` field is not documentation.** It is the sentence a support agent reads to a
customer: *"scored 0.30 because 4 checks failed in the last 30 days, threshold 3."* **A rule that
cannot produce that sentence is a rule that cannot be defended.**

## ⭐ The engine's own rules

```
⭐ No I/O inside a rule           ← ⭐ inputs are gathered ONCE, before evaluation
⭐ No rule depends on another      ← ⭐ or order matters and determinism is fragile
⭐ Missing input → EXPLICIT        ← ⭐ a rule must declare "cannot evaluate", not return 0
⭐ Every rule is pure              ← ⭐ same inputs, same output, no side effects
```

**⭐ The third is the one that prevents the silent-wrongness failure mode.** A rule that cannot
evaluate must say so, and the assessment must record that it was incomplete — **because a score
computed from half the inputs is not a lower score, it is an unreliable one.**

```
⭐ Assessment status: COMPLETE · ⭐ PARTIAL (n rules could not evaluate) · FAILED
```

**⭐ Surfacing `PARTIAL` to the caller is a product decision and the honest one.** Most engines
silently degrade; making incompleteness visible is a genuine improvement to point at.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Weights hardcoded | ⭐ tuning requires a deploy; history cannot be explained |
| ⭐ **No rule version on the assessment** | ⭐⭐ **no score can be reproduced or explained** |
| ⭐ Inputs not frozen | ⭐ re-evaluation gives a different answer |
| ⭐ **Missing input treated as zero** | ⭐⭐ **a confident score from absent data** |
| ⭐ `Instant.now()` inside a rule | non-reproducible |
| ⭐ `double` accumulation | ⭐ order-dependent; can flip a threshold |
| Unordered iteration affecting the result | non-deterministic |
| I/O inside a rule | slow, untestable, and non-deterministic |
| Rules depending on each other | order matters; reasoning becomes global |
| ⭐ No per-rule contribution stored | ⭐ "why is my score 0.82?" is unanswerable |
| ⭐ No human-readable explanation | the output cannot be defended to a person |
| Silently degrading on partial inputs | an unreliable score presented as a low one |

## ⭐ Self-review

- [ ] ⭐ **Every rule extracted into `RISK-RULES.md`** in business language
- [ ] ⭐ The **"why?"** column filled where possible; ⭐ **gaps recorded as findings**
- [ ] ⭐ **Rules are data**: versioned rulesets, weights in rows, draft/active workflow
- [ ] ⭐ Assessments store ⭐ **ruleset version, frozen inputs, and per-rule contributions**
- [ ] ⭐ **All four determinism breakers found and eliminated**
- [ ] ⭐ `BigDecimal` with explicit scale, rounding and ⭐ **fixed accumulation order**
- [ ] ⭐ **All three property tests pass**, including ⭐ **re-evaluation of the whole golden dataset**
- [ ] One rule per class, unit-testable with `new`, ⭐ **each with an `explanation`**
- [ ] ⭐ No I/O in rules; ⭐ **missing inputs produce `PARTIAL`, never zero**
- [ ] ⭐ Characterisation tests reviewed: ⭐ **every behaviour change classified as fix or regression**

## 🎤 Defence questions

1. **⭐ Why is this score 0.82?** (⭐ you must be able to answer for a specific assessment)
2. **⭐ Can you reproduce an assessment from six months ago, exactly?**
3. **⭐ What happens if an input is missing?**
4. **⭐ How do you change a rule weight?** (⭐ and how did you before?)
5. **⭐ Why `BigDecimal` rather than `double`?**
6. **⭐ How do you know the engine is deterministic?**
7. **⭐ What did your characterisation tests reveal when you rebuilt it?**
8. **⭐ Which rule could you not justify, and what did you do about it?**

## ✅ Done when

- ⭐ Every historical assessment in the golden dataset **reproduces exactly**
- ⭐ **A rule weight can be changed without a deploy**
- ⭐ **Any score can be explained rule by rule, in a sentence a customer would understand**
- ⭐ Every characterisation-test difference is classified
