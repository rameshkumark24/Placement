# Day 097

**L-097** · Testing philosophy — unit vs integration vs e2e, the pyramid, test doubles
**D-07** · SQL I — `SELECT`, `WHERE`, `ORDER BY`, NULL semantics

**Time:** 3 hrs · **Mode:** NEW

> Day 074 was JUnit mechanics and Day 075 was Mockito. Today is the question those two do not
> answer: **what should you test, at what level, and how do you know the suite is any good?** This
> is where most teams get it wrong — not by writing bad tests, but by writing them at the wrong
> level.

---

# Part 1 — Why tests exist

Not "to find bugs". A test suite's real jobs, in order of value:

1. **Enable change.** Without tests, every modification is a gamble, so people stop modifying and
   the codebase calcifies. This is the entire justification for Day 096.
2. **Specify behaviour.** A good test is executable documentation that cannot go stale — unlike a
   comment (Day 089), something checks it.
3. **Provide fast feedback.** Seconds, not a deploy cycle.
4. **Prevent regressions.** Every bug fixed gets a test so it cannot return.
5. **Pressure the design.** Code that is hard to test is usually badly designed — the difficulty is
   information (Day 075).

> **A test suite you do not trust is worse than none**, because you spend time running it and then
> ignore the result. That makes flakiness (Day 074) the most expensive defect a suite can have.

# Part 2 — The levels

## The pyramid

```
          ╱ ╲          E2E / UI          few      slow (min)     brittle    high confidence
         ╱───╲         Integration       some     medium (s)     moderate
        ╱─────╲        Unit              many     fast (ms)      stable     narrow confidence
       ╱───────╲
```

**Why the shape:** cost and speed pull one way, confidence pulls the other. A unit test is
milliseconds and tells you one class works; an e2e test is minutes and tells you the *system* works.
You want the fastest test that could plausibly catch the bug — and *most* bugs are catchable cheaply.

| Level | Scope | Speed | Fails when |
|---|---|---|---|
| **Unit** | One class/function, collaborators substituted | < 10 ms | Logic is wrong |
| **Integration** | Several components, one real dependency | 100 ms – 5 s | Wiring, SQL, serialization is wrong |
| **E2E** | The whole system through its real interface | 10 s – minutes | The user journey is broken |
| **Contract** | The boundary between two services | fast | Producer and consumer disagree |

## The two anti-shapes

**The ice cream cone** — mostly manual and e2e tests, few unit tests. Slow, flaky, and failures do not
localise: a red build tells you "checkout is broken" and you still have to find where.

**The hourglass** — many unit, many e2e, no integration. Common and dangerous, because the integration
layer is exactly where the interesting bugs live: SQL that does not match the entity, serialization
mismatches, transaction boundaries, N+1 queries.

## The honest revision to the pyramid

The classic pyramid was written when integration tests meant a shared, slow, hand-maintained
database. **Testcontainers changed the economics**: a real PostgreSQL in Docker starts in seconds and
is disposable, so an integration test now costs one or two seconds rather than minutes of setup.

The modern consensus, and the one worth stating in an interview:

> **Write the test at the lowest level that could actually catch the bug — but do not mock what you
> could cheaply run for real.** A repository test against a real PostgreSQL is worth ten mocked ones,
> because the mocked ones cannot catch wrong SQL.

A "unit" test that mocks the database to verify a query is testing your mock's configuration, not
your query.

## What belongs where

| Test this | At this level | Because |
|---|---|---|
| Business rules, calculations, validation | **Unit** | Pure logic, many cases, must be fast |
| Edge cases and error paths | **Unit** | Cheap to enumerate |
| SQL / repository methods | **Integration** (real DB) | A mock cannot catch wrong SQL |
| JSON serialization | **Integration** | Annotations and field names must be exercised |
| Transaction boundaries and rollback | **Integration** | Only real transactions demonstrate it |
| Security rules (who may access what) | **Integration** | Filter chains and annotations must run |
| One critical user journey | **E2E** | Confidence that the whole thing works |
| Every user journey | ❌ | Too slow and too brittle to maintain |

# Part 3 — Properties of a good test

The **FIRST** acronym is worth knowing because it is a checklist you can run against a suite:

| | Meaning |
|---|---|
| **F**ast | Milliseconds. A slow suite stops being run. |
| **I**ndependent | Any order, any subset, no shared state (Day 074) |
| **R**epeatable | Same result everywhere — no clock, no network, no randomness without a seed |
| **S**elf-validating | Passes or fails; no human reading output |
| **T**imely | Written with the code, not months later |

**Repeatable is where most flakiness comes from**, and the three causes are always the same:
time, concurrency and shared state.

```java
// ❌ flaky: fails at midnight, fails in another timezone, fails in December
assertEquals(LocalDate.now().plusDays(30), subscription.expiryDate());

// ✅ inject a Clock (Day 075)
Clock clock = Clock.fixed(Instant.parse("2026-08-14T00:00:00Z"), UTC);

// ❌ flaky: passes on a fast machine, fails in CI
Thread.sleep(500);
assertTrue(job.isComplete());

// ✅ wait for the condition, with a timeout
await().atMost(5, SECONDS).until(job::isComplete);          // awaitility
// or a CountDownLatch (Day 070)
```

**A flaky test must be fixed or deleted within a day.** A tolerated flaky test teaches the team that
red builds are ignorable, and that habit then hides a real failure. This is a cultural point more
than a technical one, and it is worth saying out loud in an interview.

## Test structure and naming

```java
@Test
void withdraw_whenBalanceIsInsufficient_throwsAndLeavesBalanceUnchanged() {
    // ARRANGE
    Account account = new Account(Money.of(100));

    // ACT + ASSERT
    assertThrows(InsufficientFundsException.class, () -> account.withdraw(Money.of(150)));

    // ASSERT the invariant — the part people forget
    assertEquals(Money.of(100), account.balance());
}
```

That second assertion is the important one: **testing that an operation fails is half a test.**
Testing that it fails *without leaving corrupt state* is the whole one. Most real bugs live in
partially-applied operations.

## Testing the boundaries

Bugs cluster at boundaries, so test them explicitly: **0, 1, n, n−1, n+1, max, min, negative, null,
empty, and the exact threshold**.

```java
@ParameterizedTest
@CsvSource({ "999, false", "1000, false", "1001, true" })     // the exact boundary
void bulkDiscountAppliesAboveOneThousand(int amount, boolean expected) { … }
```

`@ParameterizedTest` (Day 074) is what makes this cheap enough to actually do.

## Coverage, honestly

Coverage tells you what is **not** tested. It says nothing about whether what *is* covered is tested
well:

```java
@Test void coversEverythingProvesNothing() {
    service.processOrder(order);        // 100% line coverage of processOrder. Zero assertions.
}
```

- Use it to **find gaps** — an uncovered `catch` block is a genuine finding.
- **Never mandate a percentage.** Teams asked for 90% write tests that touch lines.
- **Branch coverage > line coverage.** A single-line `if` with no else is one line and two branches.
- **Mutation testing** (PIT) is the honest measure: it changes your code — flips a `>` to `>=`,
  removes a call — and checks whether a test fails. A surviving mutant is a line that is covered but
  not actually verified. Expensive to run; run it occasionally on critical modules.

## Test doubles — the level question

Day 075 gave the five doubles. The level question is which to use where:

| Level | Substitute |
|---|---|
| Unit | Fakes and stubs; mocks for failure injection and outbound side effects |
| Integration | **Real** database, real serialization; stub only external HTTP (WireMock) |
| E2E | Everything real, except third parties that charge money or send messages |

Two rules from Day 075 that matter most here: **do not mock types you do not own** (wrap them), and
**prefer a fake over a mock** when the collaborator has meaningful behaviour.

## Where TDD sits

Tomorrow is TDD in practice. Today's framing: TDD is a *design* technique that happens to produce
tests. It works well for logic with clear inputs and outputs, and badly for exploratory work where
you do not yet know the shape. **Test-after is acceptable; test-never is not.**

# Part 4 — D-07 · SQL I

## `SELECT` and logical evaluation order

The clause order you write is not the order the engine evaluates:

```
WRITTEN:    SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT
EVALUATED:  FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

**This one table explains three common errors**, and it is a standard interview question:

```sql
-- ❌ alias not available in WHERE: SELECT runs AFTER WHERE
SELECT price * qty AS total FROM line WHERE total > 100;      -- ERROR

-- ✅ alias IS available in ORDER BY: it runs after SELECT
SELECT price * qty AS total FROM line ORDER BY total DESC;    -- works

-- ❌ WHERE cannot filter an aggregate — the aggregate does not exist yet
SELECT dept, COUNT(*) FROM emp WHERE COUNT(*) > 5 GROUP BY dept;   -- ERROR
-- ✅ HAVING filters groups, after GROUP BY
SELECT dept, COUNT(*) FROM emp GROUP BY dept HAVING COUNT(*) > 5;
```

> **`WHERE` filters rows before grouping; `HAVING` filters groups after.** Put every condition you
> can in `WHERE` — it reduces the rows that must be grouped (Day 094's selection pushdown).

## `WHERE`

```sql
WHERE status = 'PAID'
  AND created_at >= DATE '2026-08-01'
  AND total_cents BETWEEN 1000 AND 5000          -- inclusive both ends
  AND region IN ('TN', 'KA', 'KL')
  AND email LIKE '%@acme.com'                    -- leading % ⇒ no index usable
  AND name ILIKE 'ram%'                          -- Postgres case-insensitive
  AND deleted_at IS NULL                         -- NOT = NULL
```

**A leading wildcard prevents index use**, because a B-tree is ordered by prefix. `LIKE 'ram%'` can
use an index; `LIKE '%ram'` cannot. That is the most practically useful indexing fact available
before Stage 5.

The same rule generalises: **any function applied to a column defeats the index on it**.

```sql
WHERE YEAR(created_at) = 2026                   -- ❌ no index on created_at can be used
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01'                -- ✅ sargable, uses the index
```

"**Sargable**" — Search ARGument ABLE — is the word for a predicate an index can serve. Keep the
column bare on one side of the comparison.

## NULL — the three-valued logic

Day 081's D-02 introduced it; here it is operationally.

```sql
NULL = NULL          → UNKNOWN     (not TRUE)  → use IS NULL / IS NOT NULL
NULL <> 5            → UNKNOWN
NULL + 5             → NULL
'abc' || NULL        → NULL        (concatenation with NULL erases the string)

WHERE status <> 'CANCELLED'        -- ❌ silently EXCLUDES rows where status IS NULL
WHERE status IS DISTINCT FROM 'CANCELLED'   -- ✅ null-safe (Postgres)
WHERE (status <> 'CANCELLED' OR status IS NULL)   -- ✅ portable

WHERE id NOT IN (SELECT parent_id FROM child)     -- ⚠️ returns NOTHING if any parent_id is NULL
WHERE NOT EXISTS (SELECT 1 FROM child c WHERE c.parent_id = t.id)  -- ✅ always correct
```

**`NOT IN` with a NULL in the subquery returning zero rows is one of the most confusing bugs in
SQL**, and the explanation is exact: `x NOT IN (1, NULL)` is `x <> 1 AND x <> NULL`, and
`x <> NULL` is UNKNOWN, so the whole conjunction is never TRUE. **Prefer `NOT EXISTS`.**

Aggregates and NULL:

```sql
COUNT(*)        -- counts rows
COUNT(col)      -- SKIPS nulls        ← the usual surprise
AVG(col)        -- divides by the NON-NULL count
SUM(col)        -- NULL if every value is null (not 0)

COALESCE(a, b, 'default')       -- first non-null
NULLIF(a, b)                    -- NULL if a = b — useful for divide-by-zero: x / NULLIF(y, 0)
```

## `ORDER BY` and `LIMIT`

```sql
ORDER BY created_at DESC, id DESC        -- ← ALWAYS add a tiebreaker
ORDER BY total DESC NULLS LAST           -- Postgres; nulls sort last by default on DESC
LIMIT 20 OFFSET 40                       -- page 3
```

**A tiebreaker is not optional for pagination.** Without a unique final sort key, rows with equal
sort values may come back in any order between queries, so page 2 can repeat or skip a row that page
1 already showed. Add the primary key.

And the deeper pagination problem:

```sql
-- ❌ OFFSET 100000 makes the database produce and discard 100,000 rows
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- ✅ keyset ("seek") pagination — uses the index, constant cost at any depth
SELECT * FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC LIMIT 20;
```

Keyset pagination is the standard answer to "our page 5000 is slow", and it is worth knowing now
because it also shapes API design — it is why well-designed APIs return a **cursor** rather than a
page number.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Ice cream cone | Slow, flaky, failures do not localise |
| Hourglass | The layer with the interesting bugs is untested |
| Mocking the database to test a query | Tests the mock, not the SQL |
| Tolerating flaky tests | The suite loses credibility; real failures get ignored |
| `Thread.sleep` in tests | Slow and machine-dependent |
| `LocalDate.now()` in tested code | Fails at midnight, in another timezone, in December |
| Asserting failure without asserting state | Misses partially-applied operations |
| Coverage as a target | Tests written to touch lines |
| Alias in `WHERE` | Evaluation order — `SELECT` has not run |
| Aggregate in `WHERE` | Use `HAVING` |
| Function on an indexed column | Index unusable |
| `NOT IN` with a nullable subquery | Zero rows, silently |
| `ORDER BY` with no tiebreaker | Pagination repeats and skips rows |
| Deep `OFFSET` | The database produces and throws away everything before it |

## Interview questions

**Q: Explain the test pyramid — and would you change it?**
Many fast unit tests, fewer integration tests, very few e2e. The shape follows from cost versus
confidence. I would revise it upward at the integration layer: Testcontainers made real dependencies
cheap, and mocked repository tests cannot catch wrong SQL.

**Q: What makes a good test?**
FIRST — fast, independent, repeatable, self-validating, timely — plus a name that states the
behaviour and an assertion on state after a failure, not just that the failure occurred.

**Q: How do you deal with a flaky test?**
Fix it or delete it within a day. The three causes are almost always time, concurrency and shared
state — inject a `Clock`, wait for conditions rather than sleeping, and eliminate shared fixtures.
Tolerating flakiness destroys trust in the whole suite.

**Q: What is your view on coverage?**
A tool to find untested paths, never a target. Branch coverage is more meaningful than line coverage,
and mutation testing is the honest measure of whether covered code is actually verified.

**Q: What is SQL's logical evaluation order and why does it matter?**
FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT. It explains why a `SELECT` alias
works in `ORDER BY` but not in `WHERE`, and why an aggregate must be filtered in `HAVING`.

**Q: `WHERE` vs `HAVING`?**
`WHERE` filters rows before grouping; `HAVING` filters groups after. Push everything you can into
`WHERE` so fewer rows are grouped.

**Q: Why does `NOT IN` sometimes return nothing?**
If the subquery yields a NULL, the expansion contains `x <> NULL`, which is UNKNOWN, so the
conjunction is never TRUE. Use `NOT EXISTS`.

**Q: Why is `OFFSET 100000` slow, and what replaces it?**
The database must produce and discard every preceding row. Keyset pagination compares against the
last row's sort key, which uses the index and costs the same at any depth.

## 🎙️ Articulation drill

Two minutes: **"How do you decide what to test and at what level?"**

Lowest level that could catch the bug; do not mock what you can cheaply run for real; business rules
and edge cases at unit level; SQL, serialization, transactions and security at integration level;
one or two critical journeys end to end. Then the culture point — a flaky test gets fixed or deleted
the same day, because a suite nobody trusts is worse than no suite.
