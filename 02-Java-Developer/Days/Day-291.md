# Day 291 🏗️

**P-291** · The risk engine II — evaluation, safe change, and operating it

**Time:** 3 hrs · **Mode:** BUILD

> Day 290 made the engine deterministic and explicable. **Today makes it changeable** — because a
> risk engine whose rules cannot be safely tuned is a risk engine that will not be tuned, and one
> that is tuned recklessly is worse.
>
> **⭐ The question this day answers: how do you change a rule and know you have not made things
> worse?**

---

# Part 1 — ⭐ How do you know the engine is any good?

**⭐ Determinism means it always gives the same answer. It says nothing about whether the answer is
right.** Those are different problems and this is the one people skip.

```markdown
# docs/RISK-EVALUATION.md
⭐ What does a "correct" score mean for NexOps?
⭐ What outcome are we predicting, and can we observe it?
⭐ What is the cost of a false positive versus a false negative?
```

**⭐ That third question determines everything about tuning**, and it is asymmetric in almost every
real system:

| System | ⭐ False positive | ⭐ False negative |
|---|---|---|
| Fraud detection | ⭐ a blocked legitimate customer | ⭐ money lost |
| Safety / compliance | ⭐ a wasted review | ⭐ **an incident** |
| Credit | a lost sale | a default |

> **⭐⭐ If you cannot say which error is worse and roughly by how much, you cannot choose a
> threshold** — you can only choose one arbitrarily and defend it with a number that looks precise.

**⭐ And be honest about the ground truth problem.** For many risk systems the true outcome is
unobservable, delayed, or only observed for the cases you *did not* block — **which is a selection
bias worth naming**, because it means your measured accuracy is measured on a skewed sample.

**⭐ Say that out loud in an interview.** "We could only observe outcomes for entities we did not
block, so our precision estimate was biased" is a sophisticated observation that most people building
scoring systems never make.

# Part 2 — ⭐ Evaluate a ruleset change before it affects anyone

**⭐ Three techniques, in increasing order of confidence.**

### ⭐ 1. Backtesting — replay history through the new rules

```
⭐ For every historical assessment: re-evaluate its FROZEN INPUTS with ruleset v5
⭐ Compare against the stored v4 score
```

**⭐ This is only possible because Day 290 froze the inputs.** It is the direct payoff of that
decision, and it turns "I think this weight is better" into a distribution you can look at.

```
⭐ Report: how many scores moved · ⭐ how many crossed a decision threshold
⭐ ⭐ WHICH ONES — the entities whose classification would have changed
```

**⭐ The threshold crossings are what matter, not the average change.** A tuning that moves every
score by 0.01 and flips no decisions changed nothing; one that moves few scores but flips two hundred
classifications is a significant change.

### ⭐ 2. Shadow mode — run both, act on one

```
⭐ Evaluate with the ACTIVE ruleset (acted on) and the DRAFT ruleset (recorded only)
⭐ Compare over real traffic for a period
```

**⭐ Shadow mode catches what backtesting cannot: inputs that only occur in live traffic.** Backtesting
uses the past; shadow mode uses the present, including data shapes that did not exist when the
history was written.

**⭐ It costs one extra evaluation per assessment**, which is cheap because Day 290 made rules pure and
I/O-free — **another payoff of that design.**

### ⭐ 3. Gradual rollout

```
⭐ 5% → observe → 25% → observe → 100%, with the ability to revert instantly
```

**⭐ Revert must be a ruleset version change, not a deploy** (Day 290's rules-as-data). **That is what
makes this safe**: if the new ruleset behaves badly, you set the previous version active and every
subsequent assessment uses it — with the assessments made under the bad version still explicable,
because each records its own ruleset version.

## ⭐ The metrics to watch during a change

```
⭐ score_distribution           ← ⭐ a histogram. A shifted distribution is the first signal
⭐ decisions_by_class_total     ← ⭐ how many entities in each classification
⭐ rule_triggered_total{rule}   ← ⭐ which rules fire, and how often
⭐ assessments_partial_total    ← ⭐ Day 290's PARTIAL — rising means inputs are degrading
```

**⭐ `rule_triggered_total` is the diagnostic one.** A rule that never fires is dead weight; a rule
that fires on everything is not discriminating. **Both are findings you can only see with the
metric**, and both are common in engines that have been tuned by intuition.

# Part 3 — ⭐ Performance and the operational shape

## ⭐ Where the time actually goes

**⭐ Day 290's design makes this measurable**: rules are pure and I/O-free, so **the cost is input
gathering, not evaluation.**

```
⭐ Time the two phases separately: ⭐ input gathering vs rule evaluation
```

**⭐ The finding is almost always that gathering dominates**, which changes what you optimise:

| Finding | ⭐ Fix |
|---|---|
| ⭐ N+1 while gathering inputs | ⭐ one query, or a projection (Day 160, Day 161) |
| ⭐ Sequential external lookups | ⭐ parallel fan-out with a timeout (Day 265) |
| Re-gathering unchanged inputs | ⭐ cache with a TTL matched to input volatility (Day 266) |
| Evaluation itself slow | ⭐ rare — and suspicious. Look for hidden I/O in a rule |

**⭐ The last row is a check on Day 290's rule**: if evaluation is slow, a rule is doing I/O it should
not be doing.

## ⭐ Batch versus on-demand

| Mode | ⭐ Consideration |
|---|---|
| ⭐ **On-demand** | latency is on the request path; ⭐ needs input caching |
| ⭐ **Batch (scheduled)** | ⭐ Day 264's rules apply — ⭐ idempotent claim, batched, one transaction per batch |
| ⭐ **Event-driven** | ⭐ re-assess when an input changes — ⭐ needs the outbox (Day 263) |

**⭐ Event-driven re-assessment is the most interesting of the three**, and the most likely to be
wrong in the original: **when an input changes, the entity's score is stale until something
recomputes it.** If nothing does, the system reports confident scores computed from data that has
since changed.

**⭐ Ask of NexOps: how long can a score be stale, and does anything enforce that?** If the answer is
"indefinitely", that is a finding — and the fix is an outbox event on input change plus a job that
re-assesses (Days 263, 264).

## ⭐ Operating it

```
⭐ score_computed_total, ⭐ assessment_duration (with the two phases separated)
⭐ ⭐ ALERT: assessments_partial_total rising     ← ⭐ inputs are degrading
⭐ ⭐ ALERT: score_distribution shifted           ← ⭐ something changed upstream
⭐ ⭐ ALERT: staleness — oldest un-reassessed entity age
```

**⭐ The distribution alert is the one that catches the failure nobody designs for**: an upstream data
source starts returning nulls, every score drops, and **nothing errors.** Day 290's `PARTIAL` status
plus a distribution alert is what makes that visible.

# Part 4 — ⭐ Explainability as a feature

**⭐ Day 290 stored per-rule contributions. Today make them usable.**

```
⭐ GET /api/v1/assessments/{id}/explanation
⭐ → score, ruleset version, evaluated_at, ⭐ each rule: triggered, contribution, explanation
⭐ → ⭐ which inputs were used, and ⭐ which were missing
```

**⭐ Three audiences, three needs:**

| Audience | ⭐ Needs |
|---|---|
| ⭐ **A support agent** | ⭐ one sentence per triggered rule, in plain language |
| ⭐ **An auditor** | ⭐ the full record — inputs, ruleset version, timestamps |
| ⭐ **You, debugging** | the same, plus the input gathering trace |

**⭐ Authorization matters here** (Day 259): an explanation reveals the rules, so **who may see it is a
decision, not a default.** Scope it by owner and tenant in the query.

## ⭐ The counterfactual — the answer people actually want

```
⭐ "Your score would be 0.4 instead of 0.8 if you had fewer than 3 failed checks."
```

**⭐ For a simple additive engine this is computable**: for each triggered rule, what would the score
be without it. **It is the difference between "here is your score" and "here is what to do about
it"**, and it is a genuinely valuable feature that falls out of Day 290's design almost for free.

**⭐ Be honest about the limit**: counterfactuals are only meaningful for an additive model with
independent rules. **If the engine has interactions, saying so is better than producing a misleading
number** — and knowing why is a good answer.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Determinism mistaken for correctness | ⭐ consistently wrong |
| ⭐ No false-positive/negative cost | ⭐ the threshold is arbitrary |
| ⭐ Ignoring selection bias in outcomes | ⭐ accuracy measured on a skewed sample |
| ⭐ Changing weights without backtesting | ⭐ unknown impact on real decisions |
| ⭐ Reporting mean score change | ⭐ **threshold crossings are what matter** |
| No shadow mode | live-only data shapes are untested |
| ⭐ Revert requiring a deploy | slow rollback during a bad change |
| ⭐ No `rule_triggered` metric | dead rules and non-discriminating rules stay invisible |
| Optimising evaluation instead of gathering | the wrong phase |
| Hidden I/O in a rule | slow, non-deterministic, untestable |
| ⭐ **No staleness bound** | ⭐ confident scores from data that changed |
| ⭐ No distribution alert | ⭐ an upstream failure silently shifts every score |
| Explanations without authorization | the ruleset leaks |
| ⭐ Counterfactuals on a non-additive model | a misleading number |

## ⭐ Self-review

- [ ] ⭐ **`RISK-EVALUATION.md` states what correct means** and ⭐ **the cost asymmetry**
- [ ] ⭐ Selection bias in outcome data **named honestly**
- [ ] ⭐ **Backtesting works** — replay history through a new ruleset
- [ ] ⭐ The report shows ⭐ **threshold crossings**, not just score deltas
- [ ] ⭐ **Shadow mode** implemented; ⭐ gradual rollout with ⭐ **instant revert by version**
- [ ] ⭐ All four change-metrics emitted, including ⭐ `rule_triggered_total`
- [ ] ⭐ Gathering and evaluation **timed separately**; ⭐ the dominant phase optimised
- [ ] ⭐ **A staleness bound exists and is enforced**, with an alert
- [ ] ⭐ Alerts on ⭐ `PARTIAL` rate and ⭐ **score distribution shift**
- [ ] ⭐ An **explanation endpoint**, authorized, ⭐ with plain-language sentences
- [ ] ⭐ Counterfactuals where the model supports them, ⭐ **and the limit stated where it does not**

## 🎤 Defence questions

1. **⭐ How do you know the engine is accurate, not just consistent?**
2. **⭐ Which error is worse for your system, and by roughly how much?**
3. **⭐ How do you change a weight and know you have not made things worse?**
4. **⭐ How many decisions would that change have flipped?**
5. **⭐ How fast can you revert a bad ruleset?**
6. **⭐ Which of your rules never fires?**
7. **⭐ How stale can a score be, and what enforces that?**
8. **⭐ A customer asks why they scored 0.82. What do you show them?**
9. **⭐ What would have to change for their score to improve?**

## ✅ Done when

- ⭐ **A ruleset change can be backtested, shadowed, rolled out gradually and reverted instantly**
- ⭐ The staleness bound is enforced and alerted
- ⭐ **An assessment can be explained to a non-technical person**
