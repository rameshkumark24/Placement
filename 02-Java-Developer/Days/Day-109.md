**L-109** · API versioning — URI, header, media type · deprecation policy

**Time:** 3 hrs · **Mode:** NEW

> on it. Today: how to change an API anyway.
>
> The most useful realisation is that **the versioning-strategy debate is the less important half**.
> The half that decides whether you succeed is knowing what counts as a breaking change, and how to

# Part 1 — What is actually breaking

## The compatibility rules

**Backward compatible (safe) — old clients keep working:**

| Change | Why it is safe |
|---|---|
| **Adding** an optional request field | Old clients omit it; the default applies |
| **Adding** a response field | Old clients ignore unknown fields — *if they were built to* |
| **Adding** a new endpoint | Nobody was calling it |
| **Adding** an optional query parameter | |
| **Adding** a new enum value ⚠️ | Only if clients handle unknowns — see below |
| **Relaxing** validation | Previously-valid requests remain valid |
| Making a required response field **always present** | |

**Breaking — old clients fail:**

| Change | Why it breaks |
|---|---|
| **Removing or renaming** any field | The client reads `null` or crashes |
| **Changing a type** (`"42"` → `42`, number → string) | Parse failure or silent corruption |
| **Adding a required** request field | Every existing request now fails validation |
| **Tightening** validation | Previously-valid requests are rejected |
| **Changing a URL** | 404 |
| **Changing a status code** for a case | Client branching breaks |
| **Changing an error `type`** (Day 104) | Client error handling breaks |
| **Changing default behaviour** | Silently different results |
| **Changing pagination or sort defaults** | Different data, no error |
| **Removing an enum value** | Client cannot represent existing data |

## The three that surprise people

**1. Adding an enum value can break clients.** A client with `switch (status)` over four values, with
no default, throws on the fifth. **This is why enum handling must be specified in your documentation
from day one**: "clients must tolerate unknown enum values and treat them as `UNKNOWN`." Say it
before you need it — afterwards it is too late.

**2. Making a response field *stricter* about nulls breaks clients that check for null.** Rare, but
real: a client that branches on `if (field == null)` gets a code path that never runs.

**3. Fixing a bug can be a breaking change.** If clients worked around the bug, the fix breaks the
workaround. Hyrum's Law is the formulation worth knowing:

> **With a sufficient number of users, every observable behaviour of your system will be depended on
> by somebody — regardless of what you documented.**

Response field *order*, incidental sort order, an error message's exact wording, the precise number
of milliseconds something takes. You cannot prevent this; you can reduce it by **documenting what is
*not* guaranteed** and, where it matters, by deliberately randomising unguaranteed things (some APIs
randomise field order in JSON so nobody can depend on it).

## The best versioning strategy is not needing one

Before reaching for `/v2`, exhaust these:

- **Add rather than change.** A new field beside the old one, both populated during the transition.
- **Expand and contract** (the same pattern as a database migration): add the new, dual-write, migrate
  clients, then remove the old — three deploys, no breaking change.
- **Tolerant reader on your side too.** Accept both the old and new shapes for a period.
- **Feature negotiation instead of versioning** — an opt-in header or query parameter for a specific
  behaviour change, rather than a whole new version.

> **Every version you publish is a version you must maintain, test and secure — potentially for
> years.** Two live versions roughly doubles your surface area. The cheapest version is the one you
> never created.

# Part 2 — The strategies

## 1. URI path versioning

```http
GET /v1/orders/42
GET /v2/orders/42
```

**Pros:** unmissable, trivially routable at the gateway, works in a browser address bar, easy to
document and to demo, easy to run both versions side by side.

**Cons:** purists object that the URI should identify the *resource* and `/v1/orders/42` and
`/v2/orders/42` are the same order. It also tends to version the *entire* API when only one endpoint
changed.

**This is what almost everyone does** — Stripe, GitHub, Twilio, Kubernetes. Practicality wins.

## 2. Custom header

```http
GET /orders/42
X-API-Version: 2
```

**Pros:** clean URIs; per-request versioning.
**Cons:** invisible in a browser or a log by default, harder to test with `curl`, easy to forget, and
caches need `Vary: X-API-Version` or they will serve one version's response to the other (Day 102).

## 3. Media-type ("content negotiation") versioning

```http
GET /orders/42
Accept: application/vnd.acme.order.v2+json
```

**Pros:** the most theoretically correct — the version describes the *representation*, which is
exactly what `Accept` is for. Allows per-resource versioning.
**Cons:** verbose, poor tooling support, confusing for most consumers, and the same `Vary` caching
requirement.

GitHub used this and has largely moved away from it — which is itself informative.

## 4. Query parameter

```http
GET /orders/42?version=2
```

Easy, but it mixes a protocol concern with filter parameters and is easy to drop accidentally.
Generally the weakest option.

## 5. Date-based versioning — worth knowing

```http
GET /orders/42
Stripe-Version: 2026-08-14
```

Stripe's approach: **a customer's version is pinned at signup**, and every breaking change becomes a
dated "version" that the API applies as a transformation on the way out. Internally there is one
current implementation plus a chain of small compatibility shims.

That is genuinely elegant — the codebase does not fork — but it demands serious discipline and
tooling. Know it as the sophisticated option.

## Choosing

| Situation | Strategy |
|---|---|
| Public API, many unknown consumers | **URI path** — visible, obvious, routable |
| Internal service-to-service | Often none — coordinate deploys; use expand/contract |
| Rapidly evolving with pinned customers | Date-based |
| Strict REST requirement | Media type |

**Version the major only.** `/v1`, not `/v1.2.3` — minor and patch changes are, by definition,
backward compatible, so they need no version.

# Part 3 — Deprecation, done properly

A version you cannot retire is a version you maintain forever. Retiring one requires a **process**,
not an announcement.

## The lifecycle

```
1. ANNOUNCE      in the changelog, docs, email, and IN THE RESPONSE
2. INSTRUMENT    measure who is still calling it — by client id, not just count
3. WARN          Deprecation and Sunset headers on every response
4. NUDGE         contact the remaining callers directly
5. BROWNOUT      brief scheduled outages to surface silent dependencies
6. SUNSET        410 Gone with a link to the migration guide
```

**Steps 2 and 5 are the ones people skip and they are the ones that work.**

You cannot deprecate what you cannot measure. Log every request with its API version and client
identity, and build the dashboard *before* announcing the deprecation — otherwise you will be
guessing about impact for the whole window.

**Brownouts** are scheduled short outages of the old version — 30 minutes, announced in advance —
before the real shutdown. They convert "nobody responded to our emails" into a support ticket from
the team that did not know they were still calling it. Far better than discovering it at sunset.

## The headers

```http
HTTP/1.1 200 OK
Deprecation: Sun, 01 Feb 2026 00:00:00 GMT           # RFC 9745 — when it was deprecated
Sunset: Wed, 01 Jul 2026 00:00:00 GMT                # RFC 8594 — when it will STOP working
Link: <https://docs.acme.com/migrate/v2>; rel="deprecation"; type="text/html"
Warning: 299 - "The v1 orders API is deprecated and will be removed on 2026-07-01."
```

These are machine-readable standards, so client tooling and gateways can surface them automatically.

## After sunset

```http
HTTP/1.1 410 Gone
Content-Type: application/problem+json

{ "type": "https://api.acme.com/problems/version-sunset",
  "title": "API version v1 has been removed",
  "status": 410,
  "detail": "v1 was sunset on 2026-07-01. See the migration guide.",
  "migration_guide": "https://docs.acme.com/migrate/v2" }
```

**`410 Gone`, not `404`.** `404` says "we cannot find that", which sends a developer looking for a
typo. `410` says "this existed and was deliberately removed" — an actionable answer (Day 104).

## Timelines

| Consumer | Reasonable notice |
|---|---|
| Internal, same team | Days — just coordinate |
| Internal, other teams | 1–3 months |
| External developers | **6–12 months minimum** |
| Enterprise contracts | 12–24 months, often contractual |
| Mobile apps ⚠️ | **Longer than you think** |

**Mobile is the constraint that catches people.** You cannot force an app upgrade — old versions run
on devices for years, and a meaningful fraction of users never update. Any API serving a mobile
client needs either a very long deprecation window or a forced-upgrade mechanism built into the app
from version 1. **Build the "this version is no longer supported" screen before you ship** — retrofit
is impossible.

## Documenting the contract

Put this in your docs before your first external consumer:

```markdown
## API stability

We may, without a new version:
- add new endpoints
- add optional request parameters
- add fields to responses
- add new enum values

**Clients MUST therefore:**
- ignore unknown response fields
- tolerate unknown enum values (treat them as UNKNOWN)
- not depend on field ordering
- not depend on the exact wording of error messages — branch on `type`

Breaking changes ship in a new major version with at least 6 months' notice.
```

**That list is the single most valuable paragraph in an API's documentation**, because it converts
"you broke us" into "you did not follow the documented client requirements" — and, more usefully,
because clients that follow it genuinely do not break.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Versioning before it is needed | Two surfaces to maintain from day one |
| Adding a required request field | Every existing client fails immediately |
| Adding an enum value with no documented policy | Clients with exhaustive switches throw |
| Assuming a bug fix is safe | Clients depended on the bug (Hyrum's Law) |
| Header or media-type versioning without `Vary` | A cache serves the wrong version |
| Deprecating without instrumentation | No idea who breaks |
| Announcing without brownouts | Silent dependencies discovered at sunset |
| `404` after sunset | Developers hunt for a typo |
| Short windows for mobile clients | Old app versions break in users' hands |
| No documented stability contract | Every addition is arguably a breaking change |
| Maintaining old versions indefinitely | Compounding cost, and old security posture |

## Interview questions

**Q: Which versioning strategy would you choose?**
URI path versioning for a public API — visible, routable, obvious in logs and documentation, and it
is what Stripe, GitHub and Kubernetes do. Media types are more theoretically correct but poorly
tooled. The strategy matters less than the discipline of avoiding breaking changes in the first
place.

**Q: What counts as a breaking change?**
Removing or renaming a field, changing a type, adding a required request field, tightening
validation, changing URLs or status codes or error identifiers, and changing defaults. Adding
optional things is safe — except adding an enum value, unless clients were told to tolerate unknowns.

**Q: How do you avoid needing a new version?**
Add rather than change; use expand-and-contract with dual writes; be a tolerant reader; and use
opt-in feature negotiation for specific behaviour changes rather than a whole new version.

**Q: What is Hyrum's Law and what does it mean for you?**
With enough users, every observable behaviour will be depended on regardless of your documentation —
including field order and error wording. It means even bug fixes can break clients, and it argues for
explicitly documenting what is *not* guaranteed.

**Q: How do you deprecate a version?**
Announce, then instrument to see who is actually calling it, then send `Deprecation` and `Sunset`
headers, contact remaining callers directly, run brownouts to surface silent dependencies, and
finally return `410 Gone` with a migration link. Six to twelve months for external consumers, longer
for mobile.

**Q: Why `410` rather than `404` after sunset?**
`404` suggests a mistake and sends the developer looking for a typo. `410` states that the resource
was deliberately removed, which is actionable.

**Q: What makes mobile clients special?**
You cannot force an upgrade, and old versions run for years. Either plan very long windows or build a
forced-upgrade mechanism into the app before launch, because it cannot be retrofitted.

## Mini task

1. Take an API you have and classify twenty possible changes as breaking or non-breaking. Check your
   answers against the tables.
2. Write the "API stability" section for it, including the client requirements.
3. Implement URI path versioning with `/v1` and `/v2` sharing a service layer, where only the
   response mapping differs. Note how much code is actually duplicated.
4. Add `Deprecation`, `Sunset` and `Link` headers to a v1 endpoint and verify them with `curl -i`.
5. Add per-version, per-client request logging and build a small usage report. That report is the
   thing that makes deprecation possible.
6. Implement the `410 Gone` sunset response with a problem+json body.
7. Demonstrate the enum-break: write a client that switches exhaustively over four values, then add
   a fifth on the server.
8. Do an expand-and-contract rename of a response field: add the new name, populate both, then
   remove the old. Three commits, no breaking change.
9. Add header-based versioning to one endpoint and demonstrate the caching bug by omitting `Vary`.

## 🎙️ Articulation drill

Two minutes: **"How do you version an API?"**

Lead with avoidance — add rather than change, expand and contract, tolerant readers — because the
best version is the one you never shipped. Then URI path versioning with the reasoning, then the
deprecation process with instrumentation and brownouts as the parts that actually work. Close with
mobile as the constraint that sets the timeline. Talking about *retirement* rather than only about
*numbering* is what distinguishes the answer.
