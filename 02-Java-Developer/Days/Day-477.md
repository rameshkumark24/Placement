> **⭐⭐ An LLD round is not "write classes". It is a negotiation about scope followed by a demonstration

# Part 1 — ⭐⭐ The 45-minute LLD clock

```
⭐ 0–6    ⭐⭐ REQUIREMENTS — ⭐⭐ negotiate scope OUT LOUD. ⭐ Say what you are NOT building.
⭐ 6–12   ⭐ ENTITIES and their relationships. ⭐⭐ Nouns first, then behaviour.
⭐ 12–20  ⭐⭐ THE CORE INTERACTION — one flow, end to end, in code.
⭐ 20–32  ⭐⭐ THE HARD PART — ⭐⭐ the bit that is actually a design problem, not CRUD.
⭐ 32–40  ⭐⭐ THE EXTENSION they add. ⭐ This is the block being scored hardest.
⭐ 40–45  ⭐ what you left out, and what you would change first.
```

| ⭐ The rule that governs the whole hour | |
|---|---|
| ⭐⭐ **You will not finish. That is expected.** | ⭐⭐ **depth on one thing beats breadth on eight** |
| ⭐ Say so explicitly | ⭐ *"I'll go deep on allocation and pricing and stay shallow on payments — tell me if you'd rather flip that."* |
| ⭐⭐ **Write real Java, not pseudocode** | ⭐⭐ this is a Java round; the interfaces are the answer |
| ⭐ Do not write getters and setters | ⭐⭐ nobody scores those, and they eat the clock |

## ⭐⭐ The requirements script — ninety seconds, always the same

```
⭐ 1. ⭐⭐ "Let me state what I think we're building and you correct me."   ⭐ one sentence
⭐ 2. ⭐ FUNCTIONAL — 4–6 bullets, said aloud, ⭐⭐ and CONFIRMED
⭐ 3. ⭐⭐ EXPLICITLY OUT OF SCOPE — 3 bullets. ⭐⭐ THIS IS THE MOVE PEOPLE SKIP.
⭐ 4. ⭐ SCALE — "one site or a thousand?" ⭐⭐ this single question changes the design
⭐ 5. ⭐ NON-FUNCTIONAL — concurrency? persistence? in-memory?
⭐ ⇒ ⭐⭐ Naming what you will NOT build is what makes the scope yours rather than theirs.
```

# Part 2 — ⭐⭐ The round: design a parking lot

> **Design a parking lot system. Multiple floors, different vehicle sizes, ticketing, and payment on
> exit.**

## ⭐ 0–6 — the negotiation

| ⭐ Ask | ⭐ Why it changes the design |
|---|---|
| ⭐⭐ **"One lot, or a chain of lots?"** | ⭐⭐ one lot = in-memory; a chain = a service, IDs, and a different data model |
| ⭐ "Do spot types map to vehicle types strictly, or can a car use a large spot?" | ⭐⭐ **this is the allocation policy question in disguise** |
| ⭐ "Is pricing flat, hourly, or tiered?" | ⭐ decides whether pricing is a strategy or a constant |
| ⭐ "Reservations, or walk-up only?" | ⭐ reservations add a hold with an expiry (Day 320A) |
| ⭐⭐ **"Concurrent entries at multiple gates?"** | ⭐⭐ **the real difficulty — see Part 3** |

**⭐ Then say the out-of-scope line:** *"I'll assume no reservations, single lot, and I'll treat payment
as an interface rather than implementing a gateway. I'll go deep on allocation and pricing."*

## ⭐ 6–20 — entities and the core flow

```java
enum VehicleType { MOTORCYCLE, CAR, VAN }
enum SpotSize    { SMALL, MEDIUM, LARGE }

record Vehicle(String plate, VehicleType type) { }

final class Spot {
    final String id; final SpotSize size; final int floor;
    private String occupiedBy;                       // ⭐ null = free
}

final class Ticket {                                 // ⭐⭐ the entity that ties it together
    final String id; final String plate; final String spotId;
    final Instant entryAt;  Instant exitAt;  Money amount;  TicketStatus status;
}

interface ParkingLot {
    Ticket park(Vehicle v);                          // ⭐ throws LotFullException
    Money  unpark(String ticketId, Instant now);
}
```

| ⭐ Two design points to say aloud here | |
|---|---|
| ⭐⭐ **`Money`, not `double`** | ⭐⭐ `long` minor units or `BigDecimal` — **a float in a billing system is a defect** (Day 357) |
| ⭐⭐ **The ticket is the aggregate** | ⭐⭐ spot occupancy and charge both hang off it, so it is the consistency boundary (Day 305) |

## ⭐⭐ 20–32 — the hard part: allocation and pricing

```java
// ⭐⭐ Allocation is a POLICY, and naming it as one is the point
interface SpotAllocationStrategy {
    Optional<Spot> allocate(List<Spot> free, Vehicle v);
}
// ⭐ NearestToEntrance · BestFit (smallest that fits) · FloorBalancing
// ⭐⭐ Say why: "the rule for which spot changes per site and per marketing decision.
// ⭐   If it's an if-else in the lot class, every change edits the class that must not change."

// ⭐⭐ Pricing is also a policy, and it is the one they will extend
interface PricingStrategy { Money priceFor(Ticket t, Instant exit); }

final class HourlyPricing implements PricingStrategy {
    public Money priceFor(Ticket t, Instant exit) {
        long hours = Math.max(1, Duration.between(t.entryAt(), exit).toHours());  // ⭐ ceil, min 1
        return rateFor(t.vehicleType()).times(hours);
    }
}
```

> **⭐ The sentence that scores: "Both of these are policies rather than logic, because they change for
> different reasons and at different times than the parking rules do."** That is the open/closed
> principle stated as a *reason* rather than as a name (Day 302).

# Part 3 — ⭐⭐ The concurrency question, which is the real round

```
⭐⭐ "Two cars arrive at two gates at the same moment and there is ONE free spot."
⭐ ❌ ⭐⭐ synchronized on the whole lot ⇒ correct, and it serialises every gate in the building
⭐ ✅ ⭐⭐ AN ATOMIC CONDITIONAL CLAIM — the same mechanism as everything else in this roadmap:

⭐   in-memory:  ⭐⭐ spot.occupiedBy.compareAndSet(null, plate)   ⇒ ⭐⭐ true = you have it
⭐   distributed: ⭐⭐ UPDATE spots SET occupied_by = ? WHERE id = ? AND occupied_by IS NULL
⭐                ⇒ ⭐⭐ rowsAffected = 1 means you won. Retry with the next candidate on 0.
⭐ ⇒ ⭐⭐ Day 316, Day 320A, Day 393's visibility timeout, Day 411's conditional write.
⭐   ⭐⭐ Being able to say "this is the same mechanism as a seat hold" is a strong senior signal.
```

| ⭐ Also worth naming | |
|---|---|
| ⭐ Free-spot lookup by size | ⭐ `EnumMap<SpotSize, ConcurrentLinkedQueue<Spot>>` — **poll is already atomic** |
| ⭐⭐ **The retry loop** | ⭐⭐ claim fails ⇒ take the next candidate ⇒ bounded attempts ⇒ then `LotFull` |
| ⭐ Exit is easier | ⭐ one ticket, one owner, no contention |

# Part 4 — ⭐⭐ The extension at minute 32

| ⭐ Likely extension | ⭐ What it tests |
|---|---|
| ⭐⭐ **"Now add electric charging spots that cost per kWh."** | ⭐⭐ does pricing compose, or did you hard-code it |
| ⭐ "Now support monthly pass holders." | ⭐ a pricing strategy that returns zero, **not an if-else in `unpark`** |
| ⭐⭐ **"Now it's 500 lots and one app."** | ⭐⭐ the in-memory claim becomes the conditional UPDATE |
| ⭐ "Now the pricing changes at midnight." | ⭐⭐ **freeze the rate at entry, or price the whole stay at exit — ask which** |
| ⭐ "Lost ticket." | ⭐ a flat penalty; where does that rule live? |

⚠️ **The midnight-pricing extension is the best one, because it has no correct answer without asking.**
"Do we charge the rate in force at entry, or split the stay across rate periods?" **is a business question,
and reaching for it instead of guessing is exactly the judgement being scored** — and it is Day 359's
frozen-inputs rule appearing in a parking lot.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Drawing classes at minute one** | ⭐⭐ you built the wrong scope, confidently |
| ⭐⭐ **No explicit out-of-scope statement** | ⭐⭐ the move that makes the scope yours |
| ⭐ Not asking one-site-versus-many | ⭐⭐ it changes the entire design |
| ⭐⭐ **`double` for money** | ⭐⭐ a defect, not a style choice |
| ⭐ Getters and setters written out | ⭐ unscored, and they eat the clock |
| ⭐⭐ **Pricing as an if-else chain** | ⭐⭐ the extension then requires editing it |
| ⭐ Naming a pattern without the reason | ⭐⭐ "strategy" is not an argument; "changes for a different reason" is |
| ⭐⭐ **`synchronized` on the whole lot** | ⭐⭐ correct and useless — it serialises every gate |
| ⭐ No retry after a failed claim | the second car is rejected while spots exist |
| ⭐ Guessing on the midnight-pricing rule | ⭐⭐ it is a business question — ask it |
| ⭐ Trying to finish everything | ⭐⭐ depth on one thing beats breadth on eight |
| Pseudocode in a Java LLD round | the interfaces are the deliverable |

## Interview questions

**Q: How do you open an LLD round?**
By negotiating scope for about five minutes rather than drawing classes. I restate what I think we are
building in one sentence, list four to six functional requirements and get them confirmed, and then — the
part people skip — say explicitly what I am not building. Naming the exclusions is what makes the scope
mine rather than something I discover at minute thirty. I also ask the scale question early, because "one
parking lot" and "five hundred lots and one app" are different designs, and I would rather know which one
I am in.

**Q: Two cars arrive at two gates and there is one free spot. What happens?**
Not a lock on the whole lot — that is correct and useless, because it serialises every gate in the
building. The answer is an atomic conditional claim: in memory, a compare-and-set on the spot's occupant
from null to the plate; distributed, an update that sets the occupant where the id matches and the
occupant is still null, with rows-affected as the arbiter. A failed claim means someone beat you, so you
retry with the next candidate spot and give up after a bounded number of attempts. It is the same
mechanism as a seat hold, a rate limiter token and an SQS visibility timeout.

**Q: Why is pricing an interface?**
Because it changes for different reasons and on a different schedule than the parking rules do. Rates
change for commercial reasons, the rules about which vehicle fits which spot change for physical reasons,
and coupling them means every price change edits a class that should be stable. So both allocation and
pricing are policies. I would say that reason out loud rather than just naming the strategy pattern —
naming a pattern is not an argument, and interviewers can tell the difference.

**Q: The rate changes at midnight and a car stays from 11pm to 2am. What do you charge?**
That is a business question and I would ask it rather than guess. There are two defensible answers —
freeze the rate in force at entry for the whole stay, or split the stay across rate periods — and they
have different implementations and different customer-facing consequences. Reaching for the question
instead of picking one is the point, and it is the same rule as anywhere else: anything charged or
judged should use frozen inputs unless the business has said otherwise.

**Q: You did not finish. Is that a problem?**
No, and I would say so at the start. Forty-five minutes is not enough to design the whole system, so the
choice is depth on one thing or shallow coverage of eight, and depth scores better. I state which part I
am going deep on and offer to flip it if they would rather see something else. Then in the last five
minutes I name what I deliberately left out and what I would change first, which is more useful than a
half-built payment module.

## Mini task

1. ⭐⭐ Run the **full 45-minute round** with the clock visible. Recorded. Real Java, no pseudocode.
2. ⭐⭐ Time your **requirements block.** If it was under three minutes, that is the habit to fix.
3. ⭐ Write your **out-of-scope sentence** and say it aloud.
4. ⭐⭐ Implement the **atomic conditional claim** both ways — CAS in memory, conditional UPDATE — and
   prove correctness with a concurrency test at two gates.
5. ⭐ Implement `synchronized` on the whole lot and **measure the throughput difference** at 8 gates.
6. ⭐⭐ Have your partner add the **electric charging** extension. Absorb it **without editing an existing
   class.**
7. ⭐ Then the **monthly pass** extension. Same rule.
8. ⭐⭐ Then **"now it's 500 lots"** — convert the in-memory claim to the conditional UPDATE.
9. ⭐ Ask the **midnight-pricing question** aloud and implement both answers.
10. ⭐⭐ Score with the rubric. Rows 1, 4, 6, 7 and 9 are the ones that decide it.

## 🎙️ Articulation drill

**Ninety seconds:** the requirements block, alone, out loud, from a cold start.

**⭐ "So we're building a system for a parking lot: vehicles enter, get assigned a spot, receive a ticket,
and pay on exit based on how long they stayed. Functionally I'll cover entry with allocation, ticketing,
exit with pricing, and spot availability. I'm going to treat payment processing as an interface rather
than implement a gateway, I'll assume no reservations, and I'll leave out the display boards."**

**⭐ Then the two questions that shape everything: "Is this one lot or a chain — because one lot is an
in-memory design and five hundred is a service with a database. And are there concurrent entries at
multiple gates, because that is where the interesting problem is." Practise until it is ninety seconds
flat and sounds unrehearsed.**
