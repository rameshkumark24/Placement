# Day 124

**L-124** · Background jobs — why you don't do work in the request cycle

**Time:** 3 hrs · **Mode:** NEW

> A request handler should do one thing: **accept the work and answer.** Everything that does not
> need to happen before the response belongs somewhere else. Today is why that rule exists and what
> "somewhere else" actually means.

---

# Part 1 — Why work leaves the request cycle

## The problem

```java
@PostMapping("/orders")
public OrderResponse create(@RequestBody CreateOrderRequest req) {
    Order order = orderService.create(req);        //   50 ms
    emailService.sendConfirmation(order);          //  800 ms  ← SMTP
    pdfService.generateInvoice(order);             // 2000 ms  ← CPU
    analytics.track(order);                        //  300 ms  ← third party
    warehouse.notify(order);                       //  500 ms  ← partner API
    return OrderResponse.from(order);              // total ≈ 3.7 s
}
```

Five things wrong, and each is independently serious:

**1. The user waits 3.7 seconds** for work they do not care about. They wanted an order id.

**2. Any failure fails the whole request.** The order was created and committed — but the email
provider is down, so the user sees a `500` and *retries*, creating a second order. **A non-essential
failure has become a correctness bug.**

**3. Retries are impossible.** If the email fails, there is nowhere to retry from. The information is
gone with the request.

**4. A request thread is held for 3.7 seconds.** At 100 requests per second that is 370 concurrent
threads doing nothing but waiting (Day 069). This is how thread pools exhaust and how a slow partner
takes your service down.

**5. There is no visibility.** How many invoices failed yesterday? Nobody knows.

## The fix

```java
@PostMapping("/orders")
public OrderResponse create(@RequestBody CreateOrderRequest req) {
    Order order = orderService.create(req);              // 50 ms — everything the user needs
    jobQueue.enqueue(new SendConfirmationJob(order.id()));
    jobQueue.enqueue(new GenerateInvoiceJob(order.id()));
    jobQueue.enqueue(new NotifyWarehouseJob(order.id()));
    return OrderResponse.from(order);                    // ≈ 55 ms
}
```

**70× faster, and every side effect is now independently retryable, observable and scalable.**

## The decision rule

> **Does the user need this to have happened before they see the response?**

| Synchronous | Asynchronous |
|---|---|
| Validation | Sending email or SMS |
| Persisting the core entity | Generating PDFs, reports, thumbnails |
| Payment authorization (usually) | Analytics and tracking |
| Anything whose result is in the response | Notifying partners |
| Anything whose failure must abort the operation | Search index updates |
| Authorization checks | Cache warming, cleanup |

**The edge case worth thinking about:** payment. If the user must see "payment confirmed", it is
synchronous. If "we are processing your payment" is acceptable, it becomes asynchronous — and the
architecture changes completely (Day 125's status-polling pattern).

## What you trade away

Asynchronous work is not free, and stating the costs is what makes the argument credible:

| Gain | Cost |
|---|---|
| Fast responses | **Eventual consistency** — the email has not been sent when you reply |
| Independent retries | The user cannot be told immediately if it fails |
| Independent scaling | More infrastructure to operate and monitor |
| Failure isolation | **Harder to debug** — the trace spans two systems |
| Load smoothing | Ordering is no longer guaranteed |

> **The response now means "accepted", not "done".** Your API contract must say so — `202 Accepted`
> with a status URL (Day 102), not `200 OK`.

# Part 2 — ⭐ The dual-write problem

The most important correctness issue in this whole topic, and the one most implementations get wrong.

```java
@Transactional
public Order create(CreateOrderRequest req) {
    Order order = repository.save(req.toOrder());     // 1. database
    queue.enqueue(new SendEmailJob(order.id()));      // 2. queue  ← a DIFFERENT system
    return order;
}
```

**Two systems, no shared transaction.** Two failure modes, and both happen:

```
A) Commit succeeds, enqueue fails      ⇒ the order exists, no email is ever sent
B) Enqueue succeeds, commit rolls back ⇒ a job for an order that does not exist  💀
```

Case B is the nastier one: the worker starts, cannot find the order, and either crashes repeatedly or
silently does nothing. And if the worker is fast, it can even see the *pre-commit* state.

**⚠️ `@Transactional` does not help.** The queue is not enlisted in the database transaction.
Distributed transactions across a database and a broker (XA/2PC) exist and are avoided for the
reasons in Day 117.

## ⭐ The transactional outbox — the standard fix

**Write the message to a table in the same transaction as the data.** One transaction, one system, so
it is atomic by construction.

```sql
CREATE TABLE outbox (
    id           BIGSERIAL PRIMARY KEY,
    aggregate_id TEXT        NOT NULL,
    type         TEXT        NOT NULL,
    payload      JSONB       NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ
);
CREATE INDEX ON outbox (id) WHERE published_at IS NULL;     -- partial index (Day 110)
```

```java
@Transactional
public Order create(CreateOrderRequest req) {
    Order order = repository.save(req.toOrder());
    outbox.insert(new OutboxRecord(order.id(), "OrderCreated", json(order)));  // SAME transaction
    return order;
}
```

```java
// A separate publisher — polling, or reading the WAL with Debezium (CDC)
@Scheduled(fixedDelay = 500)
public void publish() {
    for (OutboxRecord r : outbox.fetchUnpublished(100)) {      // FOR UPDATE SKIP LOCKED (Day 123)
        broker.send(r.type(), r.payload());
        outbox.markPublished(r.id());
    }
}
```

**The guarantee is at-least-once, not exactly-once** — the publisher can crash after sending and
before marking, so the message is sent twice. **Which is fine, because consumers are idempotent**
(Day 123). That sentence is the whole design: outbox gives atomicity, idempotency handles the
duplicates.

**CDC (Debezium reading the WAL) is the better publisher** where you can run it: no polling, lower
latency, and it cannot miss a row because it reads the same log the database uses for replication.

## The inbox pattern

The mirror image on the consumer side:

```java
@Transactional
public void handle(Message msg) {
    if (!inbox.tryInsert(msg.id())) return;      // already processed — unique constraint
    doTheWork(msg);                              // same transaction as the dedup record
}
```

**The dedup record and the work commit together**, so a crash cannot leave one without the other.
Same shape as Day 123's idempotency key, applied to messages.

# Part 3 — Where jobs run

## In-process — the simplest thing that works

```java
@Async
public void sendEmail(Order order) { … }         // Spring's executor

// or plainly
executor.submit(() -> emailService.send(order));  // Day 069
```

✅ No infrastructure.
❌ **Jobs are lost on restart** — including every deploy. No retries, no visibility, no scaling.

**Acceptable only when losing the job is acceptable**: cache warming, best-effort analytics.
Deploying five times a day means five chances to drop work.

## Database-backed queue

```sql
CREATE TABLE job (
    id            BIGSERIAL PRIMARY KEY,
    type          TEXT NOT NULL,
    payload       JSONB NOT NULL,
    status        TEXT NOT NULL DEFAULT 'PENDING',
    attempts      INT  NOT NULL DEFAULT 0,
    run_after     TIMESTAMPTZ NOT NULL DEFAULT now(),   -- for delays and backoff
    locked_until  TIMESTAMPTZ,
    last_error    TEXT,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON job (run_after) WHERE status = 'PENDING';
```

```sql
-- Claiming work: Day 123's SKIP LOCKED
UPDATE job SET status = 'RUNNING', locked_until = now() + interval '5 minutes', attempts = attempts + 1
WHERE id IN (
    SELECT id FROM job
    WHERE status = 'PENDING' AND run_after <= now()
    ORDER BY run_after
    LIMIT 10
    FOR UPDATE SKIP LOCKED          -- ⭐ workers claim DISJOINT rows, none block
)
RETURNING *;
```

✅ **Transactional with your data** — the outbox problem disappears entirely, because the job table
*is* in the same database. Easy to inspect: jobs are rows you can query. No new infrastructure.
❌ Polling load, and it does not scale to very high throughput (roughly thousands per second).

> **This is the right starting point for most applications**, and it is dramatically under-used —
> teams reach for Kafka when a `job` table and `SKIP LOCKED` would serve them for years. Libraries
> exist: `pg-boss`, `Que`, `delayed_job`, `JobRunr`.

## Dedicated queues and brokers

Redis-backed (Sidekiq, BullMQ, `JobRunr`), or a real broker — RabbitMQ, SQS, Kafka. **Day 125** is
all of this: acknowledgements, dead-letter queues, visibility timeouts and delivery guarantees.

## Scheduled jobs

```java
@Scheduled(cron = "0 0 3 * * *")                 // 03:00 daily
public void generateDailyReport() { … }
```

⚠️ **The distributed-cron problem:** with three instances, this runs **three times**. Every scheduled
job needs a lock:

```java
@SchedulerLock(name = "dailyReport", lockAtMostFor = "10m")   // ShedLock, over your database
```

Alternatives: a single designated leader instance, Kubernetes `CronJob`, or a managed scheduler
(EventBridge). But **the lock is the cheapest correct answer**, and forgetting it is one of the most
common bugs when a service is first scaled beyond one instance.

Other scheduling rules: `@Scheduled` uses **one thread by default**, so a slow job delays every other
one — configure a pool. And **make scheduled jobs idempotent**: they will overlap eventually.

# Part 4 — Writing a job properly

```java
public class SendConfirmationJob implements Job {

    private final long orderId;          // ⭐ pass the ID, never the whole object

    @Override
    public void run(JobContext ctx) {
        Order order = orderRepository.findById(orderId)
                .orElseThrow(() -> new PermanentFailure("order " + orderId + " no longer exists"));

        if (order.confirmationSentAt() != null) return;      // ⭐ idempotent

        try {
            emailService.send(order.customerEmail(), render(order));
            orderRepository.markConfirmationSent(orderId, Instant.now());
        } catch (RateLimitedException e) {
            throw new RetryableFailure(e.retryAfter());       // ← the queue reschedules
        } catch (InvalidAddressException e) {
            throw new PermanentFailure(e);                    // ← straight to the DLQ, no retries
        }
    }
}
```

Six rules, each of which is a production incident if broken:

| Rule | Why |
|---|---|
| **Pass ids, not objects** | The payload would otherwise be stale, large, and a serialization contract |
| **Idempotent** | At-least-once delivery guarantees duplicates (Day 123) |
| **Distinguish retryable from permanent** | Retrying an invalid email address forever costs money |
| **Small and single-purpose** | Retrying a job that does five things repeats the four that worked |
| **Bounded runtime** | An unbounded job blocks a worker indefinitely |
| **Log with a correlation id** | Otherwise the job is untraceable back to the request (Day 127) |

**"Pass ids, not objects" is the one that surprises people.** A serialized `Order` in the payload is
a snapshot from enqueue time — by the time the job runs, the order may have been cancelled, and you
will act on stale data. It also couples the queue to your class structure (Day 063A).

## Retries and the DLQ

```
attempt 1 → fail → wait  1 min  (jitter)
attempt 2 → fail → wait  5 min
attempt 3 → fail → wait 30 min
attempt 4 → fail → wait  2 hr
attempt 5 → fail → ⇒ DEAD LETTER QUEUE + alert
```

Day 123's rules apply unchanged: exponential backoff, full jitter, a cap on attempts.

**The dead-letter queue is where failed jobs go to be looked at by a human.** Its two requirements:

- **Alert when anything lands in it.** A DLQ nobody watches is a silent data-loss mechanism, and
  this is extremely common.
- **Make it replayable** — after fixing the bug, you must be able to re-enqueue the failures.

## Observability — the minimum

```
Queue depth      per queue ⭐   growing = consumers cannot keep up
Job age          oldest pending job — the real user-facing latency
Processing time  p50/p99 per job type
Failure rate     per job type
Retry rate       climbing = something is degrading
DLQ size         ⭐ must be zero, must alert
Worker health    are consumers even running?
```

**Queue depth and DLQ size are the two to alert on.** A queue growing without bound means you are
losing ground; anything in the DLQ means work was silently dropped.

**The failure mode nobody plans for:** the workers stop and nothing breaks visibly. The API is fine,
requests succeed, and emails silently stop for six hours. **Alert on the absence of processing**, not
only on errors.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Doing slow work in the request | Slow responses; thread exhaustion; failure cascades |
| Failing the request because a side effect failed | Users retry and duplicate the core operation |
| Enqueueing outside the transaction | **Dual write** — orphan jobs or lost jobs |
| Enqueueing before commit | The worker sees pre-commit state or a missing row |
| In-process executors for important work | Lost on every deploy |
| Serializing whole objects into the payload | Stale data; a serialization contract you cannot change |
| Non-idempotent jobs | At-least-once delivery duplicates the effect |
| Retrying permanent failures | Cost and noise, forever |
| `@Scheduled` with multiple instances | The job runs N times |
| One thread for all scheduled jobs | A slow job delays everything |
| No DLQ | Failures vanish |
| A DLQ with no alert | Silent data loss |
| No queue-depth monitoring | You discover the backlog from customers |
| No alert on zero throughput | Workers die and nothing tells you |

## Interview questions

**Q: What belongs in a background job?**
Anything the user does not need to have happened before they see the response: email, PDF generation,
analytics, partner notifications, index updates. Anything whose result is in the response, or whose
failure must abort the operation, stays synchronous.

**Q: What is the dual-write problem?**
Writing to the database and enqueueing to a broker are two systems with no shared transaction, so
either the data commits without the message, or the message is sent and the data rolls back — leaving
a job for a row that does not exist.

**Q: How do you solve it?**
The transactional outbox: write the message into a table in the same transaction as the data, then a
separate publisher polls the table — or reads the WAL with CDC — and forwards it. That gives
at-least-once delivery, and consumer idempotency handles the duplicates.

**Q: Why pass an id rather than the object?**
The serialized object is a snapshot from enqueue time, so the job may act on stale state, and the
payload becomes a serialization contract coupled to your classes. Loading by id gets current data and
lets the job detect that the entity no longer exists.

**Q: How do you run scheduled jobs across multiple instances?**
With a distributed lock — ShedLock over the database, for example — or a designated leader, or an
external scheduler. Without one, `@Scheduled` runs once per instance.

**Q: When is a database table good enough as a queue?**
Very often. `SELECT … FOR UPDATE SKIP LOCKED` gives you disjoint claiming with no new infrastructure,
the job write is transactional with your data so the dual-write problem disappears, and jobs are rows
you can inspect. It scales to thousands per second, which most applications never exceed.

**Q: What do you monitor?**
Queue depth and the age of the oldest pending job, per-type processing time and failure rate, DLQ
size — and throughput itself, because the failure nobody plans for is workers stopping silently while
the API stays healthy.

## 🎙️ Articulation drill

Two minutes: **"A user creates an order and we need to send an email, generate an invoice and notify
a partner. How do you design that?"**

Return as soon as the order is persisted; write the side effects to an outbox in the same
transaction; a publisher forwards them; workers process idempotently with classified retries and a
monitored DLQ. Then name the trade you made — the response means accepted rather than done, so the
contract is `202` with a status URL. Naming the dual-write problem unprompted is what separates this
from "we use a queue".
