## 🎙️ Articulation drill

⭐⭐ **Three minutes: the full flagship-frontend defence.**

Open with the thesis, not the stack. **I built the client for my own API. The point wasn't to become a
frontend engineer — it was that an API whose UI I've never written is an API I've only half designed.
The UI is the artefact; the API changes are the result.**

Demo, then go to findings. **Ninety seconds through the workflow, and then I kill the backend on purpose
— the UI names the error and offers a retry, it recovers when I bring it back, and the request id in
that message greps straight to the Spring log line.**

Give the findings as a list with numbers. **Building it changed ten things on the server. The first
screen needed four round trips, which I couldn't see from the server side because every endpoint was
individually fine. My validation errors weren't field-addressable, so I added a `ProblemDetail` advice.
Reading my own payloads in DevTools found endpoints returning entities rather than DTOs. Rows duplicated
across pages, which was an unstable sort — ordering by a timestamp with ties, fixed with an id
tiebreak, and it looked like data corruption. And a double-click created two orders, so the endpoint
took an idempotency key with a unique constraint behind it.**

Show the generalisations. **A few principles came out of it. The client is a suggestion — hidden buttons
are UX and `@PreAuthorize` is the boundary, so the server now sends a permissions object computed by
the same bean that enforces the rule. Two versions are always live because of open tabs, so a deploy is
a rollout and every API change is additive or a migration. And my p99 of forty milliseconds was about
one percent of what the user waited.**

Close on scope, deliberately. **I'm not a frontend specialist — no design systems at scale, no
animation, and I test with the keyboard rather than claiming a WCAG level I haven't audited. What I can
do is build and ship a competent, accessible, secure client for an API I designed, and read the error
reporting afterwards. And the reason I'd do it again is those ten server-side findings.**
