# Day 199

**L-199** · Full-text search — when PostgreSQL is enough, and when it is not

**Time:** 3 hrs · **Mode:** NEW

> Day 189 established that `like '%term%'` cannot use a B-tree and is a scan. Day 190 gave trigram
> indexes as the fix for substring matching. **Today is real search** — stemming, ranking, phrase
> queries — and the more valuable half of the day is the honest boundary: **when PostgreSQL's search
> is genuinely sufficient, and when reaching for it is a mistake.**

---

# Part 1 — The three types, distinguished

```sql
select to_tsvector('english', 'The quick brown foxes were running quickly');
-- ⭐ 'brown':3 'fox':4 'quick':2 'quickli':7 'run':6
--    ⭐ stemmed (foxes→fox, running→run), stop words removed (the, were), positions recorded

select to_tsquery('english', 'fox & running');
-- ⭐ 'fox' & 'run'   — the QUERY is stemmed the same way, which is why matching works
```

| Type | Meaning |
|---|---|
| ⭐ `tsvector` | the **document**, normalised: lexemes with positions |
| ⭐ `tsquery` | the **search**, normalised the same way |
| ⭐ `@@` | ⭐ **the match operator** |

**⭐ The key idea: both sides go through the same normalisation**, so "running" matches "runs",
"ran" and "run". That is what distinguishes full-text search from `LIKE` — and from trigram search,
which matches character sequences and has no idea that "ran" and "running" are related.

## ⭐ The four query constructors, and the one you should use for user input

```sql
to_tsquery('english', 'fox & run')             -- ⭐ full syntax; THROWS on malformed input
plainto_tsquery('english', 'quick brown fox')  -- ⭐ all words ANDed. Safe
phraseto_tsquery('english', 'quick brown fox') -- ⭐ words must be adjacent, in order
websearch_to_tsquery('english',
    '"quick brown" -slow fox OR dog')          -- ⭐⭐ Google-like syntax. Never throws.
```

**⭐ `websearch_to_tsquery` is the right choice for a user-facing search box**, and it is the one
people do not know about:

- it understands quoted phrases, `OR`, and `-exclusion` — the syntax users already expect;
- ⭐ **it never throws on malformed input**, whereas `to_tsquery` raises a syntax error on a stray
  `&` or an unbalanced quote.

**⭐ Passing raw user input to `to_tsquery` is a reliable source of 500 errors** — a user types
`c++ & ` and your search endpoint throws. Use `websearch_to_tsquery` or `plainto_tsquery`.

# Part 2 — ⭐ Indexing it properly

**⭐ Never compute `to_tsvector` at query time on an unindexed column** — that is a function applied
to every row (Day 189).

```sql
-- ⭐⭐ The right way: a generated column (Day 188) + a GIN index
alter table articles add column search_vector tsvector
    generated always as (
        setweight(to_tsvector('english', coalesce(title, '')),   'A') ||   -- ⭐ weights
        setweight(to_tsvector('english', coalesce(summary, '')), 'B') ||
        setweight(to_tsvector('english', coalesce(body, '')),    'C')
    ) stored;

create index ix_articles_search on articles using gin (search_vector);
```

**⭐ Three things that code gets right:**

1. ⭐ **A generated column** — it cannot drift from the source text, unlike a trigger-maintained
   column that a bulk update bypasses (Day 162).
2. ⭐ **`coalesce`** — `to_tsvector` of `NULL` is `NULL`, and concatenating anything with `NULL`
   yields `NULL`. **One null summary silently makes the whole document unsearchable**, which is
   Day 097's NULL trap in a new place.
3. ⭐ **`setweight`** — A through D let ranking know a title match matters more than a body match.
   Without it, an article that mentions a term once in a footnote ranks equally with one whose title
   is that term.

```sql
select id, title, ts_rank(search_vector, query) as rank
from articles, websearch_to_tsquery('english', :q) query
where search_vector @@ query
order by rank desc limit 20;                                -- ⭐ indexed, ranked
```

**⭐ `ts_rank_cd`** ("cover density") also considers how close the terms are to each other, which is
usually better for phrase-like queries. **Try both against real queries** — ranking quality is
empirical, not theoretical.

## Highlighting

```sql
select ts_headline('english', body, query, 'MaxWords=35, MinWords=15, StartSel=<b>, StopSel=</b>')
from articles, websearch_to_tsquery('english', :q) query
where search_vector @@ query;
```

⚠️ **⭐ `ts_headline` re-reads and re-processes the full document text**, so it is expensive.
**Apply it only to the page of results you are returning**, never to the whole match set — a
`LIMIT` in a subquery first, then headline the survivors.

# Part 3 — ⭐ Search that behaves the way users expect

**Real search is three techniques combined**, because each fails where the others work.

| Technique | Handles | Fails on |
|---|---|---|
| ⭐ **Full-text** | word matching, stemming, ranking | ⭐ typos, partial words |
| ⭐ **Trigram** (Day 190) | ⭐ typos, substrings, fuzzy | ⭐ no stemming or ranking |
| Prefix `tsquery` | autocomplete | mid-word matching |

```sql
-- ⭐ Prefix matching for autocomplete
where search_vector @@ to_tsquery('english', 'postgr:*');   -- ⭐ the :* suffix

-- ⭐ Fuzzy fallback: full-text first, trigram similarity when it finds nothing
select id, title,
       ts_rank(search_vector, q) as rank,
       similarity(title, :raw)   as sim
from articles, websearch_to_tsquery('english', :q) q
where search_vector @@ q or title % :raw            -- ⭐ % = trigram similarity
order by greatest(ts_rank(search_vector,q), similarity(title,:raw)) desc
limit 20;
```

**⭐ "postgersql" finds nothing with full-text search** — the stemmer has no notion of a typo. The
trigram operator matches it against "postgresql" by character overlap. **Combining them is what makes
a search box feel competent**, and it is a genuinely useful thing to be able to describe.

## Multi-language

```sql
alter table articles add column language regconfig not null default 'english';
-- ⭐ the generated column must then use a fixed config, since generated columns must be immutable
```

⚠️ **⭐ A generated column requires an immutable expression, so it cannot depend on a per-row
language column.** Options: one search column per supported language, a trigger instead of a
generated column, or the `'simple'` configuration (no stemming) as a language-neutral fallback. **The
trigger version reintroduces the drift risk**, so choose deliberately.

# Part 4 — ⭐⭐ The honest boundary: PostgreSQL or Elasticsearch?

**⭐ PostgreSQL full-text search is genuinely good, and reaching for Elasticsearch by reflex is a
common and expensive mistake.**

| ⭐ Use PostgreSQL when | ⭐ Use a dedicated engine when |
|---|---|
| ⭐ Up to a few million documents | tens of millions, with heavy search traffic |
| Search is a feature, not the product | ⭐ **search *is* the product** |
| ⭐ You need results consistent with the transaction | eventual consistency is acceptable |
| Filters combine search with relational conditions | ⭐ complex faceting and aggregations |
| ⭐ You do not want another system to run | you can operate a cluster |
| Basic ranking is enough | ⭐ synonyms, custom analysers, learning-to-rank |
| ⭐ **Documents change constantly** | ⭐ near-real-time is enough |

**⭐ Three arguments for staying in PostgreSQL that are stronger than people expect:**

1. ⭐ **No synchronisation problem.** An external index means a dual-write (Day 124) — the search
   index and the database can disagree, and reconciling them is permanent operational work. A
   generated column cannot drift, ever.
2. ⭐ **Transactional consistency.** A document created in a transaction is searchable the instant it
   commits, and invisible if it rolls back. Elasticsearch is near-real-time and eventually
   consistent.
3. ⭐ **Combining search with relational filters is trivial** — `where search_vector @@ q and
   tenant_id = :t and price < 100 and status = 'ACTIVE'` is one query. In a split architecture that
   is either a join across systems or duplicated data.

**⭐ The honest counter-argument, stated fairly:** at high document counts and high query volume, GIN
index maintenance becomes a real write cost, ranking quality is meaningfully worse than a tuned
Elasticsearch, and there is no faceting, no synonym management and no relevance tuning worth the
name. **If search is the product, PostgreSQL is not enough.**

**⭐ And if you do go external, the outbox pattern (Day 124) is the correct way to keep it in sync** —
not a dual write from the service, and not a nightly reindex.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `to_tsvector` computed at query time | a function per row — full scan |
| ⭐ No `coalesce` around nullable fields | one NULL makes the whole document unsearchable |
| Trigger-maintained vector instead of generated | drifts on bulk updates (Day 162) |
| ⭐ Raw user input into `to_tsquery` | syntax errors become 500s |
| No `setweight` | a title match ranks the same as a footnote |
| ⭐ `ts_headline` over the full match set | re-reads every document |
| Expecting full-text to handle typos | it stems; it does not correct |
| Using trigram alone for word search | no stemming, no ranking |
| ⭐ Reaching for Elasticsearch by default | a whole system, and a sync problem, for a feature |
| ⭐ Dual-writing to an external index | Day 124 — use the outbox |
| Expecting a generated column to switch language per row | it must be immutable |
| GIN on a very write-heavy document table | Day 190's write amplification |

## Interview questions

**Q: How does PostgreSQL full-text search work?**
Documents become `tsvector`s — stemmed lexemes with positions and stop words removed — and queries
become `tsquery`s normalised the same way, matched with `@@`. Because both sides are stemmed
identically, "running" matches "runs". I store the vector as a generated column with `setweight` so
title matches outrank body matches, and index it with GIN.

**Q: How do you handle typos?**
Full-text search does not — the stemmer has no notion of a misspelling. I combine it with a trigram
index, so the query matches on lexemes first and falls back to character similarity. That combination
is what makes a search box feel competent.

**Q: PostgreSQL or Elasticsearch?**
PostgreSQL up to a few million documents where search is a feature rather than the product, and the
strongest reason is that there is no synchronisation problem — a generated column cannot drift,
whereas an external index is a dual-write you have to reconcile forever. Elasticsearch when search
*is* the product and I need faceting, synonyms and real relevance tuning. And if I do split, the
index is fed from an outbox, not a dual write.

**Q: Why is `websearch_to_tsquery` the right function for a search box?**
It accepts the syntax users already type — quoted phrases, `OR`, minus for exclusion — and it never
throws on malformed input. `to_tsquery` raises a syntax error on a stray operator, which turns a
user's typo into a 500.

## Mini task

**500,000 documents of real text.**

1. `to_tsvector` a paragraph and read the output. Identify the stemming and the removed stop words.
2. Search with `like '%running%'` and time it. Then with `@@` and a GIN index. **Compare.**
3. Build the generated column with `setweight`. **Then remove one `coalesce` and set a summary to
   NULL — watch that document vanish from all results.**
4. Compare `ts_rank` and `ts_rank_cd` on ten real queries. **Judge the results yourself.**
5. Pass `c++ &` to `to_tsquery` and get the error. Switch to `websearch_to_tsquery`.
6. Search for a deliberate typo. Confirm zero results. Add the trigram fallback and confirm it is
   found.
7. Implement prefix autocomplete with `:*` and measure latency at 500k documents.
8. Apply `ts_headline` to the full match set, then only to the returned page. **Time both.**
9. Time 100k document inserts with and without the GIN index.
10. Write one query combining full-text search with a tenant filter, a price range and a status.
    **Note how hard that is in a split architecture.**

## 🎙️ Articulation drill

Two minutes: **"Would you use PostgreSQL for search, or Elasticsearch?"**

Answer with a boundary and a reason, not a preference. PostgreSQL up to a few million documents when
search is a feature — and lead with the strongest argument, which is that there is no synchronisation
problem, because an external index is a dual write you reconcile forever while a generated column
cannot drift. Add that combining search with relational filters and tenant scoping is one query.
Then be fair about the limit: if search is the product and you need faceting, synonyms and relevance
tuning, PostgreSQL is not enough — and in that case the index is fed from an outbox.
