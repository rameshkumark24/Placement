# Part 2 — ⭐⭐ The state machine, visible

```
⭐⭐ YOU BUILT A STATE MACHINE ON THE SERVER (Day 249). PUT IT ON
⭐   THE SCREEN — this is the highest-value thing on this page.

⭐   PENDING → PAID → SHIPPED → DELIVERED
⭐               ↘ REFUNDED     ↘ RETURNED

⭐   ⇒ ⭐ THE BADGE shows where it is.
⭐   ⇒ ⭐⭐ THE AVAILABLE ACTIONS ARE THE **LEGAL TRANSITIONS FROM
⭐     THIS STATE** — and they come from the server (Day 236), not
⭐     from a switch in the component.
⭐   ⇒ ⭐⭐ SO A DISABLED "Refund" BUTTON MUST SAY **WHY**:
⭐     ❌ a greyed button                 ⇒ the user thinks it is broken
⭐     ✅ "Refund — unavailable: this order has already been refunded"
⭐        ⭐ tooltip AND aria-describedby (Day 239)
```

```tsx
// ⭐⭐ exhaustive: adding an enum value in Java fails this build (Day 272)
function actionsFor(o: Order): Action[] {
  switch (o.status) {
    case "PENDING":   return ["cancel"];
    case "PAID":      return ["refund", "ship"];
    case "SHIPPED":   return ["markDelivered"];
    case "DELIVERED": return ["return"];
    case "REFUNDED":
    case "RETURNED":  return [];
    // ⭐ no default ⇒ TypeScript errors on a new value
  }
}
```

> ⭐⭐ **Do not let this be the *only* enforcement.** The server's `@PreAuthorize` and its own transition
> check are the boundary (Day 236). ⭐ This switch decides what to *render*; the server decides what is
> *permitted*. **Say that distinction out loud when you demo it.**

# Part 3 — ⭐⭐ The dangerous action

```
⭐⭐ FIVE THINGS AN IRREVERSIBLE ACTION NEEDS. MOST DEMOS HAVE ONE.

⭐ ① ⭐ CONFIRMATION THAT NAMES THE CONSEQUENCE
⭐    ❌ "Are you sure?"
⭐    ✅ ⭐⭐ "Refund £48.00 to Ada Lovelace? This cannot be undone."
⭐ ② ⭐ THE DESTRUCTIVE VARIANT on the confirm button, and
⭐    ⭐⭐ CANCEL AS THE DEFAULT FOCUS — so Enter does the safe thing
⭐ ③ ⭐⭐ AN IDEMPOTENCY KEY generated ONCE when the dialog opens
⭐    (Day 229) ⇒ double-click cannot refund twice
⭐ ④ ⭐ THE BUTTON DISABLES AND SHOWS LOADING (Day 272)
⭐ ⑤ ⭐⭐ THE RESULT IS VISIBLE — the badge changes, the history
⭐    gains a row. ⭐ A toast alone is not evidence.

⭐   ⭐⭐ AND FOR GENUINELY HIGH-STAKES ONES: TYPE-TO-CONFIRM.
⭐     "Type DELETE to confirm" ⇒ ⭐ it defeats muscle memory, which
⭐     is the actual failure mode for a user who has done this
⭐     forty times.
```

| ⭐ Failure handling | |
|---|---|
| **409 conflict** | ⭐⭐ *"This order changed since you loaded it — refresh to see the current state."* Optimistic locking, surfaced honestly |
| **403** | ⭐ *"You don't have permission to refund"* — from the server, not guessed |
| **Timeout** | ⭐⭐ **The hardest one.** *"We're not sure this completed — check the order history before retrying."* ⭐ Never silently retry a payment (Day 484). |

# Part 4 — Optimistic updates, honestly

```jsx
useMutation({
  mutationFn: refund,
  onMutate: async (vars) => {
    await qc.cancelQueries({ queryKey: keys.orders.detail(vars.id) });
    const prev = qc.getQueryData(keys.orders.detail(vars.id));  // ⭐ snapshot
    qc.setQueryData(keys.orders.detail(vars.id),
      o => ({ ...o, status: "REFUNDED" }));                     // ⭐ guess
    return { prev };
  },
  onError: (_e, vars, ctx) =>
    qc.setQueryData(keys.orders.detail(vars.id), ctx.prev),     // ⭐⭐ ROLL BACK
  onSettled: (_d, _e, vars) =>
    qc.invalidateQueries({ queryKey: keys.orders.all }),        // ⭐ reconcile
});
```

```
⭐⭐ WHEN OPTIMISTIC IS RIGHT — AND WHEN IT IS RECKLESS

⭐   ✅ ⭐ HIGH SUCCESS RATE, LOW STAKES, CHEAPLY REVERSIBLE:
⭐      a toggle, a like, marking read, reordering a list.
⭐   ❌ ⭐⭐ MONEY. ANYTHING IRREVERSIBLE. ANYTHING THE SERVER MIGHT
⭐      LEGITIMATELY REJECT.
⭐      ⇒ ⭐⭐ SHOWING "REFUNDED" AND ROLLING IT BACK TWO SECONDS
⭐        LATER IS WORSE THAN A SPINNER: THE USER ALREADY TOLD THE
⭐        CUSTOMER IT WAS DONE.

⭐   ⇒ ⭐ THE RULE: OPTIMISM IS A **UX** TECHNIQUE, AND ITS PRICE IS
⭐     A LIE YOU MIGHT HAVE TO RETRACT. ⭐⭐ CHARGE THAT PRICE ONLY
⭐     WHERE THE RETRACTION IS CHEAP.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "show me the most interesting screen."**

Say why it is the interesting one. **The detail screen, because it's where the domain stops being CRUD.
The order's state machine is on screen — the badge shows where it is, and the available actions are the
legal transitions from that state.**

Make the layering explicit, because it is the part that shows judgement. **Those actions come from a
permissions object the server computes with the same bean that enforces the rule. The switch in the
component decides what to render; the server decides what's permitted. And it's exhaustive, so adding a
status to the Java enum fails the frontend build.**

Then the dangerous action. **Refund is irreversible, so it names the consequence — "Refund forty-eight
pounds to Ada Lovelace, this cannot be undone" — cancel takes default focus so Enter does the safe
thing, and an idempotency key is generated once when the dialog opens, so a double-click can't refund
twice. The result is visible in the badge and the history, not just a toast.**

Cover the failure paths. **A 409 says the order changed since you loaded it. A timeout is the hard one:
I don't retry and I don't claim success — I say we're not sure it completed and to check the history,
because the response was lost, not the request.**

Close on the decision you deliberately didn't make. **I use optimistic updates on toggles and not on
the refund. Optimism is a UX technique whose price is a lie you might have to retract — showing
"refunded" and rolling it back two seconds later is worse than a spinner, because the user has already
told the customer it was done.**
