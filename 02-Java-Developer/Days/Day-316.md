# Day 316 ⭐

**L-316** · ⭐ BookMyShow — holding a seat across a payment

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Day 310 ended on one sentence: never hold a lock across a user interaction. This is the problem
> that sentence was written for.**
>
> A seat must be guaranteed to one user for the three minutes they spend typing card details — and no
> lock can survive that. **The answer is a reservation with an expiry, and building it correctly is
> the entire round.**

---

# Part 1 — ⭐⭐ The modelling insight everyone misses

```java
class Seat {
    String row; int number; SeatType type;
    boolean isBooked;          // ⭐⭐ WRONG. Catastrophically.
}
```

> **⭐ A seat is physical and belongs to a screen. Availability belongs to a *showing*.** Seat A12
> exists once; it is free for the 6pm show and taken for the 9pm one. **`isBooked` on `Seat` means
> booking the 6pm show blocks the 9pm one.**

```
   Cinema 1 ──◆ * Screen 1 ──◆ * Seat          ⭐ PHYSICAL — created once, rarely changes
                    │ 1
                    └──── * Show               ⭐ Screen + Movie + startTime
                             │ 1
                             └──── * ShowSeat  ⭐⭐ (Show × Seat) — THE availability record
                                       ├─ status: AVAILABLE | HELD | BOOKED
                                       ├─ heldBy: UserId?, heldUntil: Instant?
                                       └─ price: Money        ⭐ price varies by show, not by seat
```

**⭐ This same split appears three more times in this stage** — a book versus a copy, a product versus
its stock, a parking spot versus its occupancy. **Naming it as a general pattern scores:** *"the
physical thing and its availability-in-a-context are different entities."*

| ⭐ Say | ⭐ Why |
|---|---|
| ⭐ **"`ShowSeat` is the aggregate"** | ⭐ one seat's booking is one consistency boundary (Day 305) |
| ⭐ "Rows generate seats; I won't store a seat map per show" | ⭐ 200 seats × 20 shows/day is fine; **say the number** |
| ⭐ "Price lives on `ShowSeat`" | matinees, weekends, premium rows — all one field |

# Part 2 — ⭐⭐ The reservation lifecycle

```
                  ⭐ hold(user, 5 min)                ⭐ pay()
   ┌────────────┐──────────────────────►┌──────┐───────────────►┌────────┐
   │ AVAILABLE  │                       │ HELD │                │ BOOKED │
   └────────────┘◄──────────────────────└──────┘                └────────┘
          ▲       ⭐ release / EXPIRE       │                        │
          │                                │                        │ ⭐ cancel →
          └────────────────────────────────┘                        │   REFUNDED,
                                                                    ▼   not AVAILABLE
                                                              ⭐ (a separate flow)
```

**⭐ Four rules that make this correct:**

| Rule | ⭐ Why |
|---|---|
| ⭐ **The hold carries `heldBy` and `heldUntil`** | ⭐ **a hold without an owner cannot be confirmed safely** |
| ⭐ **Expiry is checked lazily, not swept** | ⭐ **see below — this is the good answer** |
| ⭐ **Only `heldBy` may confirm** | otherwise another user pays for your hold |
| ⭐ **BOOKED → AVAILABLE never happens directly** | ⭐ a cancellation is a refund flow (Day 309's missing arrow) |

## ⭐⭐ Expiring holds — three options, and why lazy wins

| Option | ⭐ Verdict |
|---|---|
| ⭐ A scheduled sweeper (`UPDATE … WHERE held_until < now()`) | ⭐ works, but availability is **wrong between sweeps** |
| ⭐ A timer per hold | ⭐ **a thread/task per held seat — does not scale, and dies with the process** |
| ⭐⭐ **Treat expired holds as available in the query itself** | ⭐⭐ **always correct, no coordination, no background job** |

```sql
-- ⭐ Availability is DERIVED, so an expired hold is free the instant it expires
SELECT * FROM show_seat
WHERE show_id = ?
  AND (status = 'AVAILABLE'
       OR (status = 'HELD' AND held_until < now()));   -- ⭐ no sweeper needed for CORRECTNESS
```

> **⭐ Say this explicitly: "expiry is a read-time predicate, not a background job. A sweeper is an
> optional tidy-up for row hygiene, not the mechanism — if correctness depends on a cron job having
> run, the design is wrong."** That reasoning is the same one behind Day 313's lazy TTL, and
> noticing the repetition is worth a sentence.

⚠️ **Add a Redis key with a TTL if you want the hold visible to a fast in-memory path** (Day 208) —
**but the database predicate stays the source of truth.** Two mechanisms, one authority.

# Part 3 — ⭐⭐ The concurrency, properly

## ⭐ One seat

```
⭐ Thread A                             ⭐ Thread B
   read A12 → AVAILABLE
                                        read A12 → AVAILABLE
   write HELD(userA)
                                        write HELD(userB)      ⭐ A's hold silently lost
```

| Layer | ⭐ Guard |
|---|---|
| ⭐ **In-process** | `AtomicReference` CAS on status (Day 310) |
| ⭐⭐ **Single database** | ⭐⭐ **conditional update — the whole fix in one statement** |
| Optimistic locking | a `version` column; the loser retries (Day 165) |
| ⭐ Belt and braces | ⭐ a partial unique index on `(show_id, seat_id) WHERE status = 'BOOKED'` |

```sql
-- ⭐ Atomic check-then-act in ONE statement. rowsAffected == 0 means you lost.
UPDATE show_seat
   SET status = 'HELD', held_by = :user, held_until = now() + interval '5 minutes'
 WHERE show_id = :show AND seat_id = :seat
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND held_until < now()));
```

> **⭐ `rowsAffected` is the arbiter.** No `SELECT` first, no read-modify-write, no lock held across
> anything. **This one statement is the strongest single answer available in this problem.**

## ⭐⭐ Multiple seats — the part that separates candidates

**⭐ "Four seats together" must be all-or-nothing**, and that introduces two new problems:

```java
@Transactional
public Hold holdSeats(ShowId show, List<SeatId> seats, UserId user) {
    List<SeatId> ordered = seats.stream().sorted().toList();      // ⭐ GLOBAL ORDERING → no deadlock
    for (SeatId seat : ordered) {
        int rows = seatRepo.tryHold(show, seat, user, ttl);
        if (rows == 0) throw new SeatUnavailable(seat);           // ⭐ rollback releases the earlier holds
    }
    return Hold.of(show, ordered, user, clock.instant().plus(ttl));
}
```

| ⭐ Problem | ⭐ Fix |
|---|---|
| ⭐ **Deadlock** — A takes 1,2 while B takes 2,1 | ⭐⭐ **sort seat ids before acquiring — Day 310's one rule** |
| Partial success | ⭐ one transaction; a failure rolls back the earlier holds |
| ⭐ "Four *adjacent* seats" | ⭐ a scan for a run of N consecutive free seats in a row |
| ⭐ **Leaving a single orphan seat** | ⭐ **a real product rule** — prefer runs that do not strand a lone gap |

**⭐ The adjacency query is a nice detail to volunteer:** seats in a row are ordered, so it is a
sliding window over the row's availability bitmap — **O(seats in row), and the "don't strand a single
seat" heuristic is a scoring function over candidate windows**, which is Day 312's cost function
reappearing.

## ⭐ Payment — and what happens when it fails

```
⭐ hold (5 min) ──► user pays ──► gateway callback ──► confirm booking
                        │                                    │
                        │ ⭐ times out                        │ ⭐ arrives TWICE
                        ▼                                    ▼
                 ⭐ hold expires; seat freed         ⭐ IDEMPOTENCY KEY (Day 122)
```

| ⭐ Case | ⭐ Handling |
|---|---|
| ⭐ **Payment succeeds after the hold expired** | ⭐⭐ **the nasty one — the seat may be gone. Refund automatically and tell the user; never double-sell.** |
| ⭐ Duplicate callback | idempotency key on the payment reference — the second is a no-op |
| ⭐ **Hold TTL vs gateway timeout** | ⭐ **the hold must outlive the gateway's timeout, or you generate the case above by design** |
| User abandons | expiry handles it — no cleanup path needed |

> **⭐ Naming the "paid after expiry" case unprompted is the highest-value moment in this problem.**
> It is a real-world failure, it has no clean answer, and having a stated policy — auto-refund, notify,
> never oversell — is exactly what a payments-adjacent interviewer is listening for.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ `isBooked` on `Seat` | ⭐⭐ **one booking blocks every show on that screen** |
| ⭐ A lock held across the payment | ⭐ **a connection or a lock held for minutes** |
| ⭐ Correctness depending on a sweeper | ⭐ availability is wrong between runs |
| A timer per held seat | a task per seat; lost on restart |
| ⭐ `SELECT` then `UPDATE` | ⭐ the double-book race |
| ⭐ Multi-seat holds without id ordering | ⭐ **deadlock under load** |
| No idempotency on the payment callback | double charges |
| ⭐ Hold TTL shorter than the gateway timeout | ⭐ you manufacture the paid-after-expiry case |
| BOOKED → AVAILABLE on cancel | the refund and audit trail vanish |
| Ignoring the orphan-seat rule | technically correct, commercially wrong |

## Interview questions

**Q: Where does seat availability live?**
On a `ShowSeat` — the pairing of a show and a physical seat — not on the seat itself. A seat is
physical and belongs to a screen; whether it is taken depends on which showing you mean. Putting
`isBooked` on `Seat` means the 6pm booking blocks the 9pm show. The same split shows up as book
versus copy and product versus stock.

**Q: How do you hold a seat while the user pays?**
A reservation with an expiry, never a lock — you cannot hold a lock across a human. The row moves to
HELD with a holder and a `held_until`, and the hold is claimed by a single conditional update whose
`rowsAffected` decides the winner. No select-then-update, nothing held across the payment.

**Q: How do holds expire?**
As a read-time predicate: a HELD row whose `held_until` has passed is treated as available by the
availability query. That is always correct with no coordination. A sweeper is optional tidying — if
correctness depends on a cron job having run, the design is wrong.

**Q: Four seats together, and two users want three of the same four.**
One transaction, seat ids sorted before acquiring so two users grabbing overlapping sets cannot
deadlock, and any failed conditional update rolls the whole thing back. For adjacency I slide a
window over the row's availability, and I would score candidate windows so we avoid stranding a
single orphan seat — a real commercial rule, and it is the same cost-function shape as elevator
dispatch.

**Q: The payment succeeds but the hold already expired.**
The seat may have been sold to someone else, so the rule is never oversell: refund automatically and
notify. I also set the hold TTL longer than the gateway's timeout, because otherwise the design
manufactures this case. And the callback carries an idempotency key, since gateways retry and a
duplicate must be a no-op.

## Mini task

1. Model `Seat` and `ShowSeat` separately. **Then write the test that fails with `isBooked` on
   `Seat`**: book A12 for the 6pm show, assert it is still free at 9pm.
2. Implement the **conditional-update hold** and assert on `rowsAffected`. **Run 100 threads at one
   seat and assert exactly one hold** (Day 310's harness).
3. Implement **lazy expiry as a query predicate.** Advance an injected `Clock` past the TTL and
   confirm the seat is available **with no background job running.**
4. ⭐ Build the **multi-seat deadlock**: thread A takes seats [1,2], thread B takes [2,1], no
   ordering. Reproduce it. **Then sort the ids and confirm it disappears.**
5. Implement **adjacency search** for N consecutive seats, then add the **no-orphan-seat** scoring
   rule and compare the seats chosen.
6. ⭐ Simulate **payment success after expiry**: hold, expire, sell to another user, then deliver the
   callback. **Assert no double-sell and that a refund was issued.**
7. Deliver the payment callback **twice** and assert exactly one booking.
8. Set the hold TTL below the gateway timeout and **measure how often case 6 occurs** under load.

## 🎙️ Articulation drill

**Three minutes:** *"Two people are looking at the last seat for tonight's show. Take me through
everything from click to confirmation."*

**⭐ The full-marks answer names five things in order:** availability lives on `ShowSeat` · the hold
is a reservation with an expiry, never a lock · the claim is one conditional update and `rowsAffected`
decides · expiry is a read-time predicate · **and the payment-after-expiry case, with a stated

the fifth shows you have thought about money.
