**L-130** · Why Spring exists — the problem it solves

# Part 1 — Build the problem

Here is a service written the way Stage 3 left you — no framework:

```java
public class OrderService {
    private final OrderRepository repository = new PostgresOrderRepository(
            new HikariDataSource(hikariConfigFrom(System.getenv("DATABASE_URL"))));
    private final PaymentGateway payments = new StripeGateway(System.getenv("STRIPE_KEY"));
    private final NotificationSender notifier = new EmailSender(
            new SmtpClient(System.getenv("SMTP_HOST"), Integer.parseInt(System.getenv("SMTP_PORT"))));
    private final Cache cache = new RedisCache(new JedisPool(System.getenv("REDIS_URL")));

    public Order place(CreateOrderRequest req) { … }
}
```

**Every problem in this file is one Spring solves.** Name them before reading on:

| Problem | Consequence |
|---|---|
| **`new` inside the class** | Violates DIP (Day 091) — cannot substitute anything |
| **Untestable** | A unit test needs a real database, Stripe and SMTP server (Day 075) |
| **Configuration read inline** | Scattered, unvalidated, no defaults, no profiles |
| **Lifecycle unmanaged** | Who closes the pool? When? In what order? |
| **Wiring duplicated** | Every service constructs its own `DataSource` — several pools |
| **No cross-cutting concerns** | Transactions, security, metrics must be written in every method |

## Try to fix it by hand

Move construction out — Day 091's dependency inversion:

```java
public class OrderService {
    private final OrderRepository repository;
    private final PaymentGateway payments;
    public OrderService(OrderRepository repository, PaymentGateway payments) { … }
}
```

Better. But now *something* must build the graph:

```java
public class Main {
    public static void main(String[] args) {
        Config config = Config.load();

        DataSource ds = new HikariDataSource(config.hikari());
        Cache cache = new RedisCache(new JedisPool(config.redisUrl()));

        OrderRepository orderRepo = new CachingOrderRepository(     // decorator, Day 094
                new PostgresOrderRepository(ds), cache);
        CustomerRepository customerRepo = new PostgresCustomerRepository(ds);
        PaymentGateway payments = new StripeGateway(config.stripeKey());
        NotificationSender notifier = new EmailSender(new SmtpClient(config.smtp()));

        OrderService orderService = new OrderService(orderRepo, payments, notifier);
        CustomerService customerService = new CustomerService(customerRepo);
        // …and 60 more, in dependency order, by hand

        Runtime.getRuntime().addShutdownHook(new Thread(() -> {     // Day 081
            ds.close(); cache.close();                              // in the RIGHT order
        }));
    }
}
```

**This file is the problem.** It is called a *composition root*, and by itself it is a perfectly
respectable pattern — for a small application. At sixty services it becomes:

- **Hundreds of lines of ordering-sensitive construction**, where a mistake is a `NullPointerException`
  at startup or, worse, two instances of something meant to be one.
- **Impossible to vary by environment** without conditionals throughout.
- **Manual lifecycle** — start and stop order, and nothing enforces it.

> **Dependency injection is a design principle you already applied (Day 091). Spring is a *container*
> that automates the composition root.** Those are different things, and conflating them is why
> people think DI requires a framework.

## And the harder problem

Now add a transaction to `place()`:

```java
public Order place(CreateOrderRequest req) {
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);                              // Day 117
    try {
        Order order = repository.save(conn, req.toOrder()); // ← pass the connection down?
        payments.charge(conn, …);                           // ← everywhere?
        conn.commit();
    } catch (Exception e) { conn.rollback(); throw e; }
    finally { conn.close(); }
}
```

**Every method that participates in a transaction must receive the connection**, so the plumbing
infects every signature. The alternative is to bind it to the thread — which is **exactly what you
built on Day 066A** with `ThreadLocal`, and exactly what Spring's
`TransactionSynchronizationManager` does.

Then repeat the same boilerplate for security checks, metrics, retries, caching and logging in every
method. **That repetition is the cross-cutting-concerns problem**, and Day 137's AOP is the answer.

# Part 2 — What Spring actually is

```
Spring Framework (2004)     the core: IoC container, DI, AOP, transactions, MVC, JDBC
Spring Boot (2014)          opinionated auto-configuration and an embedded server ON TOP
Spring Data / Security / …  modules for specific concerns
```

**Spring is not one thing.** The Framework is the container and its programming model; **Boot is a
configuration layer over it** that guesses sensible defaults so you write almost none of it.

## The three things the container gives you

**1. Object construction and wiring.** You declare what exists and what it needs; the container works
out the order and builds the graph.

**2. Lifecycle management.** Initialisation, destruction, ordering, scopes — the container calls your
hooks (Day 133) and shuts things down in reverse dependency order.

**3. ⭐ Cross-cutting behaviour, via proxies.** This is the one people underestimate. Because the
container creates your objects, it can wrap them (Day 094's Proxy pattern, Day 056A's dynamic
proxies) — and *that* is how one annotation adds a transaction, a security check, a cache or a retry
to a method you did not modify.

> **Spring's leverage is not `new` avoidance. It is that owning object creation lets it decorate
> everything.** `@Transactional`, `@Cacheable`, `@PreAuthorize`, `@Async`, `@Retryable` are all the
> same mechanism.

## Inversion of Control

> **You do not call the framework. The framework calls you.**

```java
// Traditional: your code is in charge
public static void main(String[] args) {
    Server server = new Server(8080);
    server.route("/orders", new OrderHandler(new OrderService(…)));
    server.start();
}

// IoC: the container is in charge; you supply components
@RestController
class OrderController {
    OrderController(OrderService service) { … }    // ← the container decides when and how
}
```

**"Inversion of control" names who holds the main loop.** Day 004's server had you writing the
`accept()` loop; Spring writes it and calls your handler. DI is one form of IoC — inverting *who
supplies dependencies*.

This is the payoff for Stage 3's ordering. **Every item below is something you built or reasoned
about by hand, which Spring is about to package:**

| …and its `ThreadLocal` connection | `ThreadLocal` · Day 066A |
| `@Cacheable` | Cache-aside, TTL, stampede · Days 120–121 |
| Spring Security's filter chain | Sessions, JWT, OAuth, RBAC · Days 111–119b |
| `PasswordEncoder` | argon2/bcrypt, work factors · Day 112 |
| `@ControllerAdvice` | RFC 7807 error contracts · Day 104 |
| `Pageable` | Offset vs keyset pagination · Day 107 |
| DTO validation | The trust boundary, mass assignment · Day 105 |
| Actuator health endpoints | Liveness vs readiness · Day 128 |
| Micrometer | RED/USE, cardinality · Day 128 |
| `@Async`, `@Scheduled` | Executors, distributed cron · Days 069, 124 |
| `@Retryable` | Backoff with jitter · Day 123 |
| Spring Data repositories | SQL, indexes, N+1 · Days 097–110 |

**Read Stage 4 as "which of my decisions has Spring already made, and do I agree?"** That is a
completely different posture from learning annotations, and it is the one that makes you dangerous
in an interview.

## What Spring costs

Be honest about this, because an answer that is only positive is unconvincing:

| Cost | Detail |
|---|---|
| **Magic** | Behaviour with no visible call site; `@Transactional` failing silently on self-invocation |
| **Startup time** | Classpath scanning and context creation — seconds, which matters for serverless |
| **Memory** | The context, proxies and metadata |
| **Debugging depth** | Stack traces through dozens of framework frames |
| **Learning curve** | You must understand the container to debug it |
| **Lock-in** | Pervasive in a codebase; hard to remove |

**The alternatives are real:** Quarkus and Micronaut do dependency injection and AOP at **compile
time**, producing faster startup, lower memory and no reflection — which matters for GraalVM native
images and serverless. Spring Boot 3 closed much of the gap with AOT processing (Day 185B).

> **Choose Spring for its ecosystem and maturity, not because it is the only option.** For a small
> service with strict startup requirements, a lighter container or plain Java may genuinely be
> better — and saying so is a strength, not heresy.

# Part 4 — The smallest possible Spring application

**Type this.** Two files, and it should feel underwhelming — that is the point.

```java
// build.gradle: implementation("org.springframework.boot:spring-boot-starter-web")

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@RestController
class HelloController {
    private final GreetingService service;
    HelloController(GreetingService service) { this.service = service; }   // ⭐ constructor injection

    @GetMapping("/hello")
    String hello(@RequestParam(defaultValue = "world") String name) {
        return service.greet(name);
    }
}

@Service
class GreetingService {
    String greet(String name) { return "hello, " + name; }
}
```

**What just happened, which you should be able to enumerate:**

1. `SpringApplication.run` created an **ApplicationContext** — the container.
2. It **scanned** the package of `DemoApplication` for annotated classes (Day 135).
3. It found `HelloController` and `GreetingService`, and **instantiated them in dependency order**.
4. It saw `spring-boot-starter-web` on the classpath and **auto-configured** an embedded Tomcat,
   Jackson and a `DispatcherServlet` (Days 139–140).
5. It **mapped** `/hello` to a method.
6. It started the server.

**None of it was configured.** That is Boot's contribution, and Days 139–140 explain exactly how the
guessing works — because a framework that guesses is only safe if you can find out what it guessed.

```bash
java -jar app.jar --debug        # ⭐ prints the auto-configuration report
```

Run that today. The output is a list of every decision Spring made on your behalf, with the condition
that triggered it. **That report is the antidote to "magic"**, and knowing it exists on day one of
Stage 4 changes how you experience the rest of the stage.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Believing DI requires a framework | It is a design principle (Day 091); the container just automates it |
| Confusing Spring Framework with Spring Boot | You cannot reason about what to configure |
| Treating annotations as magic | You cannot debug what you cannot explain |
| Not knowing `--debug` exists | Auto-configuration stays mysterious |
| Learning Spring before HTTP, SQL and transactions | You learn Spring's opinion instead of the concept |
| Assuming Spring is always the right choice | Startup and memory matter for serverless |

## Interview questions

**Q: What problem does Spring solve?**
Object construction and wiring, lifecycle management, and cross-cutting concerns. Without it you hand-
write a composition root that becomes hundreds of ordering-sensitive lines, and you repeat transaction,
security and metrics boilerplate in every method.

**Q: What is Inversion of Control?**
The framework holds the main loop and calls your code, rather than your code driving the framework.
Dependency injection is one form of it — inverting who supplies an object's dependencies.

**Q: Is dependency injection the same as Spring?**
No. DI is a design principle you can apply with plain constructors and a composition root. Spring is
a container that automates that composition root — and, more importantly, can decorate the objects it
creates.

**Q: What is Spring's real leverage?**
That it owns object creation, so it can wrap your beans in proxies. That is how a single annotation
adds transactions, caching, security or retries to a method you did not modify.

**Q: Spring Framework versus Spring Boot?**
The Framework is the container, DI, AOP, transactions and MVC. Boot is a layer on top providing
auto-configuration, starters, an embedded server and sensible defaults — so you configure almost
nothing.

**Q: What are Spring's costs, and when would you not use it?**
Startup time, memory, debugging depth through framework frames, and behaviour with no visible call
site. For strict startup or memory constraints — serverless, native images — Quarkus or Micronaut do
DI and AOP at compile time. Spring Boot 3's AOT narrows the gap but does not close it.

## Mini task

1. Write the manual composition root for a small application with at least eight collaborating
   objects, including a cache decorator and a shutdown hook that closes resources in the right order.
   Note how long it takes and where a mistake would be silent.
2. Add a transaction to one method and try to make two repositories share the connection *without*
   passing it through every signature. You will arrive at `ThreadLocal` (Day 066A).
3. Now add a security check and a metric to five methods. Count the duplicated lines — that number is
   the AOP argument.
4. Build the two-file Spring application above and run it.
5. Run it with `--debug` and read the auto-configuration report. Find three decisions Spring made
   that you did not ask for, and identify the condition that triggered each.
6. Print `context.getBeanDefinitionCount()` and list the bean names. Count how many exist that you
   did not write.
7. Measure startup time. Then measure it again with `spring-boot-starter-data-jpa` added.
8. For each row of the "you already built it" table, write one sentence on the decision *you* made in
   Stage 3, so you can compare it with Spring's when you reach that day.

## 🎙️ Articulation drill

Two minutes: **"Why do we use Spring?"**

Do not answer "for dependency injection" — that is a principle, not a framework. Answer: it automates
the composition root, manages lifecycles, and — because it creates your objects — can proxy them,
which is how one annotation adds transactions or security to code you did not modify. Then name the
costs and one situation where you would choose something else. That balance is what makes the answer
sound like judgement.
