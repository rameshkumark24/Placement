# Day 065 ⭐

**L-065** · The Java Memory Model — visibility, happens-before, reordering

**Time:** 3+ hrs · **Mode:** NEW · **Marquee day — Stage 1 exit gate**

> consequence of it. Most Java developers — including many with years of experience — know

# Part 1 — The problem that has nothing to do with interleaving

## Start with a program that should terminate

```java
public class Visibility {
    static boolean running = true;          // plain field

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long i = 0;
            while (running) { i++; }        // no synchronization, no I/O
            System.out.println("stopped after " + i);
        });
        worker.start();

        Thread.sleep(1000);
        running = false;                    // main writes
        System.out.println("main set running=false");
        worker.join();                      // ← may hang forever
        System.out.println("joined");
    }
}
```

Run this with `java -server Visibility` (or any modern JVM after the JIT warms up). **On most JVMs
it never terminates.** `main` prints its line, `running` is false in main's view, and the worker
loops forever.

There is no race here in the interleaving sense — one writer, one reader, one write. And yet the
worker never sees it.

**Why:** after a few thousand iterations, the JIT compiler notices that nothing inside the loop
modifies `running`, so it hoists the read out of the loop:

```java
boolean tmp = running;        // read ONCE
while (tmp) { i++; }          // now an infinite loop, provably
```

This is a completely legal optimisation, and the JVM is allowed to do it because **without
synchronization the JMM makes no promise that one thread's write is ever visible to another**.

Now change one word — `static volatile boolean running` — and it terminates immediately. That
single word is what today explains.

## Three layers conspire against you

The write may fail to be seen for reasons at three independent levels, and you should be able to
name all three:

**1. The compiler.** Hoisting, as above. Also reordering independent statements, eliminating
"redundant" reads, and keeping a value in a register.

**2. The CPU.** Modern cores execute out of order and use **store buffers** — a write goes into a
per-core buffer first and drains to cache later. Another core reads stale cache in the meantime.
Each core also has its own L1/L2 cache.

```
   Core 0                         Core 1
 ┌────────┐                     ┌────────┐
 │ store  │  running=false      │  L1    │  running == true  (stale)
 │ buffer │  (not drained)      │ cache  │
 └────────┘                     └────────┘
      └──────► shared memory ◄───────┘
```

**3. The memory system.** Cache coherence protocols propagate eventually, and "eventually" has no
bound you can rely on.

You cannot reason about your program by reading it in source order, because **the source order is
not what runs**.

## Why reordering is allowed at all

The rule the whole system obeys is deceptively small:

> **Within a single thread, the program must behave as if executed in program order.**

This is *as-if-serial* semantics. Everything is permitted as long as a single-threaded observer
cannot tell. And a single-threaded observer cannot tell that `a = 1; b = 2;` were swapped — so they
may be swapped. Another thread *can* tell. The JMM's job is to define the exact points where a
second thread's observations are constrained.

## The classic demonstration of reordering

```java
public class Reordering {
    static int x, y, a, b;

    public static void main(String[] args) throws Exception {
        int surprises = 0;
        for (int i = 0; i < 1_000_000; i++) {
            x = y = a = b = 0;

            Thread t1 = new Thread(() -> { a = 1; x = b; });
            Thread t2 = new Thread(() -> { b = 1; y = a; });
            t1.start(); t2.start(); t1.join(); t2.join();

            if (x == 0 && y == 0) surprises++;
        }
        System.out.println("x==0 && y==0 happened " + surprises + " times");
    }
}
```

Enumerate every interleaving of the four statements by hand. `x == 0 && y == 0` requires both reads
to happen before both writes — which **no interleaving allows**. Yet it happens, because `a = 1` and
`x = b` are independent within their thread and may be reordered, or because the store sits in a
store buffer while the load completes.

(This exact shape is called *Dekker's* or *store buffering*. Real hardware exhibits it on x86; run
it on ARM and the counts go up sharply, because ARM's memory model is weaker.)

# Part 2 — happens-before

## The definition

The JMM does not describe caches or buffers. It defines one partial order:

> **If action A *happens-before* action B, then the effects of A are visible to B, and A appears to
> occur before B.**
>
> **If two actions are not ordered by happens-before, no guarantee exists at all** — and if at least
> one is a write to the same location, that is a **data race**, and the program's behaviour is
> undefined by the model.

That is the whole model. Every concurrency guarantee in Java reduces to establishing a
happens-before edge.

## The rules that create edges

Memorise these seven. They are the answer to "how do I make this visible?"

| # | Rule | Edge |
|---|---|---|
| 1 | **Program order** | Within one thread, earlier statement → later statement |
| 2 | **Monitor lock** | `unlock(m)` → every subsequent `lock(m)` |
| 3 | **Volatile** | A write to `v` → every subsequent read of `v` |
| 4 | **Thread start** | `t.start()` → everything inside `t` |
| 5 | **Thread join** | Everything inside `t` → the return from `t.join()` |
| 6 | **Interruption** | `t.interrupt()` → the point `t` detects it |
| 7 | **Final field** | Constructor's writes to `final` fields → publication of the reference |
| — | **Transitivity** | A hb B and B hb C ⟹ A hb C |

Transitivity is what makes the model usable, and it is what most explanations skip. It means a
volatile write can carry *all* your preceding plain writes with it:

```java
// Thread A                          // Thread B
data = 42;              // plain     if (ready) {          // volatile read
ready = true;           // volatile      use(data);        // sees 42. GUARANTEED.
                                      }
```

`data = 42` happens-before `ready = true` by program order (rule 1). `ready = true`
happens-before B's read of `ready` (rule 3). By transitivity, `data = 42` happens-before `use(data)`.

**A volatile write publishes everything written before it.** That is the single most useful
consequence of the model, and it is the mechanism behind safe publication generally.

Rules 4 and 5 are worth pausing on too. Rule 4 says everything you set up before `t.start()` is
visible inside the new thread — no extra synchronization needed to hand a thread its initial data.
Rule 5 says everything the thread did is visible after `join()` returns. Those two make the
`ThreadBasics` counter demo's `join` correct in one respect while still racy in another.

## Applying it to the `synchronized` counter

```java
synchronized (lock) { counter++; }
```

The lock gives you **both** properties at once, and you should be able to name them separately:

- **Mutual exclusion** — only one thread inside at a time, so read-modify-write is atomic.
- **Visibility** — releasing the lock flushes everything the thread wrote; acquiring it invalidates
  the local view. Rule 2 plus transitivity means writes made under the lock are visible to the next
  holder.

**Most people only know the first.** In an interview, saying "a lock provides mutual exclusion *and*
establishes happens-before, so it fixes atomicity and visibility" is a distinctly senior answer.

Note the edge is *per monitor*: it only orders threads that lock the **same** object. Locking
different objects around the same data gives you nothing.

## Where `final` fits — rule 7

```java
class Config {
    private final Map<String, String> values;
    Config(Map<String, String> v) { this.values = Map.copyOf(v); }
    String get(String k) { return values.get(k); }
}
```

The final-field rule guarantees that **any thread that sees a correctly-constructed `Config`
reference sees fully-initialised `values`** — no synchronization required, ever. That is why
immutable objects are inherently thread-safe (Day 034A), and it is a stronger guarantee than most
people realise.

The escape hatch, and it is the one from Day 035: **the guarantee is void if `this` escapes during
construction**. Register a listener, start a thread, or store `this` in a static registry inside the
constructor, and another thread can observe the object before its final fields are written.

## The double-checked locking story

This is the canonical JMM problem and it is asked constantly.

```java
class Broken {
    private static Singleton instance;                 // NOT volatile
    static Singleton get() {
        if (instance == null) {                        // 1st check, no lock
            synchronized (Broken.class) {
                if (instance == null)                  // 2nd check, locked
                    instance = new Singleton();        // ← the problem
            }
        }
        return instance;
    }
}
```

The logic looks airtight. It is not, and the reason is one line: `instance = new Singleton()` is not
atomic. It compiles to roughly:

```
1. allocate memory
2. run the constructor
3. assign the reference to `instance`
```

**Steps 2 and 3 may be reordered** — as-if-serial permits it, since no single-threaded observer can
tell. So thread B can execute the first `if`, see a non-null `instance`, skip the lock entirely, and
**return a reference to an object whose constructor has not finished**. Its fields are zeros.

The fix is `volatile`:

```java
private static volatile Singleton instance;
```

Since Java 5, a volatile write cannot be reordered with the writes that precede it, so the
constructor is complete before the reference is publishable, and the volatile read on the fast path
sees a fully-built object.

**Better still, do not write it at all.** Use the holder idiom, which relies on the JVM's own
class-initialisation locking:

```java
class Holder {
    private Holder() {}
    private static class H { static final Holder INSTANCE = new Holder(); }
    static Holder get() { return H.INSTANCE; }         // lazy, thread-safe, lock-free, no volatile
}
```

`H` is not loaded until `get()` is first called, and the JVM guarantees class initialisation runs
exactly once under its own lock (Day 033's initialisation order). Or use an enum (Day 043).

## Code to type — prove all of it

```java
public class JmmDemo {

    static boolean plainFlag = true;
    static volatile boolean volatileFlag = true;
    static int data = 0;

    public static void main(String[] args) throws Exception {
        System.out.println("--- 1. plain field visibility ---");
        Thread t1 = new Thread(() -> { long i = 0; while (plainFlag) i++;
                                       System.out.println("plain loop exited at " + i); });
        t1.start();
        Thread.sleep(1000);
        plainFlag = false;
        t1.join(3000);
        System.out.println(t1.isAlive() ? "STILL RUNNING — visibility failure" : "exited");

        System.out.println("--- 2. volatile ---");
        Thread t2 = new Thread(() -> { long i = 0; while (volatileFlag) i++;
                                       System.out.println("volatile loop exited at " + i); });
        t2.start();
        Thread.sleep(1000);
        volatileFlag = false;
        t2.join(3000);
        System.out.println(t2.isAlive() ? "STILL RUNNING" : "exited");

        System.out.println("--- 3. piggybacking: data published by a volatile write ---");
        data = 42;                       // plain write
        volatileFlag = true;             // volatile write publishes it
        new Thread(() -> { if (volatileFlag) System.out.println("sees data=" + data); }).start();

        System.out.println("--- 4. what volatile does NOT do ---");
        Counter c = new Counter();
        Thread[] ts = new Thread[4];
        for (int i = 0; i < 4; i++) { ts[i] = new Thread(c::increment); ts[i].start(); }
        for (Thread t : ts) t.join();
        System.out.println("volatile count = " + c.count + "  (expected 400000)");
    }

    static class Counter {
        volatile int count = 0;
        void increment() { for (int i = 0; i < 100_000; i++) count++; }
    }
}
```

Part 1 hangs (kill it after the join timeout reports it). Part 2 exits instantly. **Part 4 is the
exit-gate question**: the count is *still* wrong, despite `volatile`.

## ⭐ Why `volatile` does not make `i++` safe

This is a Stage 1 exit-gate item. Be able to say it in one breath.

`count++` is three separate operations:

```
1. READ   count          ← volatile read: guaranteed to see the latest value
2. ADD    1              ← in a register
3. WRITE  count          ← volatile write: guaranteed visible to everyone
```

`volatile` makes step 1 and step 3 *individually* correct. **It does nothing about the gap between
them.** Two threads can both read 5, both compute 6, both write 6. One increment is lost — and both
threads saw a perfectly fresh value at every moment.

> **`volatile` gives you visibility, not atomicity.**
> `synchronized` gives you both.

Three fixes, and knowing which to reach for is the point:

```java
synchronized (this) { count++; }             // mutual exclusion + visibility
AtomicInteger count;  count.incrementAndGet(); // CAS — lock-free, Day 068
LongAdder count;      count.increment();      // striped, best under high contention
```

The one case where `volatile` *is* sufficient for a compound-looking operation is when only one
thread ever writes — a status flag, a shutdown signal, a cached-and-never-mutated reference. That
is precisely the `running` case we started with.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Assuming a write is eventually seen | Infinite loop; the JIT hoisted the read |
| `volatile` on a counter | Lost updates, and now the bug looks impossible |
| Locking different objects around the same data | No happens-before edge at all |
| Double-checked locking without `volatile` | Partially-constructed object escapes |
| Leaking `this` from a constructor | Voids the final-field guarantee |
| "It worked on my machine" | x86 is strongly ordered; ARM is not. Test on both. |
| Reasoning from source order | Source order is not execution order |
| Adding `synchronized` "to be safe" | Contention, and it hides the design question |

**On that "worked on my machine" row:** JMM bugs are the hardest class of bug in Java precisely
because they are timing-, JIT- and hardware-dependent. Code can run correctly for two years and then
fail after a JVM upgrade or a move to ARM instances. You cannot test your way to correctness here —
you reason with happens-before.

## Interview questions

**Q: What is the Java Memory Model?**
A specification of when a write by one thread becomes visible to another, defined as a
happens-before partial order. Actions not ordered by happens-before have no guarantees; if one is a
write to the same location, the program has a data race.

**Q: Why do we need it — isn't memory just memory?**
Because compilers reorder, CPUs execute out of order and buffer stores, and each core has its own
cache. All of that is legal as long as a single thread cannot tell. The JMM says exactly where
cross-thread observation is constrained.

**Q: What does `volatile` guarantee?**
Visibility and ordering: reads always see the latest write, and the write cannot be reordered with
preceding operations. It does **not** provide atomicity for read-modify-write.

**Q: Why doesn't `volatile` fix `i++`?**
Because `i++` is read-add-write. Volatile makes the read and the write individually visible but
leaves the interval between them unprotected, so two threads can read the same value and both write
back the same increment.

**Q: Explain double-checked locking.**
Without `volatile` the assignment can be reordered ahead of constructor completion, so a second
thread can see a non-null reference to a half-built object. Marking the field `volatile` (Java 5+)
fixes it; the holder idiom or an enum avoids the problem entirely.

**Q: How does a lock provide visibility?**
Release happens-before every subsequent acquire of the *same* monitor, and by transitivity
everything written before the release is visible after the acquire.

**Q: What makes an immutable object thread-safe with no synchronization?**
The final-field rule: writes to final fields in a constructor happen-before publication of the
reference — provided `this` did not escape during construction.
