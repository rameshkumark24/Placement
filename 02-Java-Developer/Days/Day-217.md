# Day 217 📡

**J-217** · 📡 **`fetch`** — ⭐⭐ the HTTP client whose error model has no errors in it

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `fetch` only rejects when the request never happened — a 500 carrying
> Spring's Whitelabel Error Page is a *successful* fetch, so every codebase that does not check
> `res.ok` has a silent bug where server errors render as blank screens instead of error states.**
>
> Today: the one-line trap, ⭐ the wrapper you write once, ⭐⭐ the four states, and cancellation.

---

# Part 1 — ⭐⭐ The trap

```javascript
// ❌ THE BUG THAT IS IN EVERY TUTORIAL
try {
  const res = await fetch("/api/items");
  const data = await res.json();
  setItems(data);
} catch (e) {
  setError(e);            // ⭐⭐ NEVER RUNS FOR A 404 OR A 500
}
```

```
⭐⭐ WHEN DOES fetch ACTUALLY REJECT?

⭐ ✅ IT REJECTS (throws) ONLY WHEN:
⭐    · the network is down / DNS fails
⭐    · CORS blocked it            (Day 237)
⭐    · the request was aborted    (Part 4)
⭐    · ⭐ THE REQUEST NEVER COMPLETED AS AN HTTP EXCHANGE

⭐ ❌ IT DOES **NOT** REJECT FOR:
⭐    · 400  401  403  404  422  429  500  502  503
⭐    ⭐⭐ ALL OF THESE ARE "SUCCESSFUL" FETCHES.
⭐    res.ok is false, and NOTHING ELSE TELLS YOU.

⭐⭐ ⇒ AND THEN res.json() THROWS A **SYNTAX ERROR**, because Spring's
⭐   default error page is HTML. So your catch block finally runs —
⭐   with "Unexpected token '<'" — and you spend an hour debugging a
⭐   JSON parser instead of reading a status code.
```

> ⭐⭐ **This is the opposite of every Java HTTP client you have used.** `RestTemplate` throws
> `HttpClientErrorException` on a 4xx; `WebClient` has `onStatus`; even `HttpClient` makes you look at
> `statusCode()` explicitly. **`fetch` models "did an HTTP exchange occur", not "did you get what you
> wanted"** — defensible, and not what anyone expects. The failure is dangerous specifically because
> it is quiet: no exception, no red console, just `undefined` flowing into a component that renders
> nothing. It is Day 455's lesson in a client.

# Part 2 — ⭐ The wrapper you write once

Never call raw `fetch` from a component. Same argument as a shared `RestClient` bean: one place to fix,
one place to test, one place to add a header.

```javascript
export class ApiError extends Error {
  constructor(status, body, url) {
    super(`${status} on ${url}`);
    this.status = status;      // ⭐ so callers can branch on 401 vs 400
    this.body = body;          // ⭐⭐ the PARSED problem detail, for field errors
    this.url = url;
  }
}

export async function api(path, { method = "GET", body, signal, ...rest } = {}) {
  let res;
  try {
    res = await fetch(`${BASE}${path}`, {
      method,
      signal,                                    // ⭐ Part 4
      credentials: "include",                    // ⭐⭐ cookies — Day 235
      headers: {
        ...(body ? { "Content-Type": "application/json" } : {}),
        ...rest.headers,
      },
      body: body ? JSON.stringify(body) : undefined,
    });
  } catch (cause) {
    if (cause.name === "AbortError") throw cause;          // ⭐ not an error
    throw new ApiError(0, null, path, { cause });          // ⭐⭐ network/CORS
  }

  if (res.status === 204) return null;                     // ⭐ no content

  const text = await res.text();                           // ⭐⭐ text FIRST
  let data = null;
  try { data = text ? JSON.parse(text) : null; } catch { data = { raw: text }; }
  //    ⭐ so a Whitelabel HTML 500 becomes {raw:"<html>..."} instead of
  //      a SyntaxError that destroys the original information

  if (!res.ok) throw new ApiError(res.status, data, path); // ⭐⭐ THE LINE
  return data;
}
```

| ⭐ Decision | Why |
|---|---|
| **`res.text()` then `JSON.parse`** | ⭐⭐ An error page is not JSON. Parsing text you already hold keeps the body for the bug report. |
| **`status` on the error** | ⭐ Callers branch: 401 → re-auth, 400 → field errors, 429 → back off, 5xx → retry |
| **`body` on the error** | ⭐⭐ Where your `ProblemDetail` lands — that is what puts the message next to the right input (Day 229) |
| **`AbortError` re-thrown as-is** | ⭐⭐ A cancelled request is **not a failure** and must never render an error |
| **`credentials: "include"`** | ⭐⭐ Cookies are **not** sent cross-origin by default. Day 235. |

```java
// ⭐⭐ your Spring side — make the client's job possible.
//    RFC 7807 ProblemDetail is built in since Spring 6; USE IT.
@RestControllerAdvice
class ApiExceptionHandler {

  @ExceptionHandler(MethodArgumentNotValidException.class)
  ProblemDetail onValidation(MethodArgumentNotValidException ex) {
    var pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
    pd.setTitle("Validation failed");
    pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
        .map(fe -> Map.of("field", fe.getField(),          // ⭐⭐ FIELD-ADDRESSABLE
                          "message", fe.getDefaultMessage()))
        .toList());
    return pd;                       // ⭐ application/problem+json — and it is JSON,
  }                                  //   so the client never meets an HTML error page
}
```

> ⭐⭐ **This is the Day 214 point arriving early.** You cannot render a good error state against an
> error shape that does not name the field. The client is where you discover that; the fix is in Spring.

# Part 3 — ⭐⭐ The four states

Every request has four outcomes. Most projects render one.

```
⭐⭐ LOADING · ERROR · EMPTY · SUCCESS

⭐   loading → ⭐ a skeleton, not a spinner that shifts the layout
⭐   error   → ⭐⭐ WHAT HAPPENED + WHAT THE USER CAN DO. A retry
⭐             button is the minimum.
⭐   empty   → ⭐⭐ ZERO RESULTS IS NOT AN ERROR AND NOT A BLANK BOX.
⭐             The state most often missed, and the one reviewers
⭐             notice immediately.
⭐   success → the boring one everyone builds first
```

| ⭐ State | The mistake | The fix |
|---|---|---|
| Loading | A spinner that replaces content, so the page jumps | ⭐ Skeleton the same size as the content |
| Error | One message for every status | ⭐⭐ Branch on `status`. 401 ≠ 400 ≠ 503. |
| Empty | Renders as an error, or as nothing | ⭐ "No orders yet" + the action that creates one |
| Success | — | ⭐ Also handle *partial* success (Day 216's `allSettled`) |

# Part 4 — Cancellation, and the race you will lose

```
⭐⭐ THE STALE RESPONSE RACE

⭐   user types "a"  → request A fires
⭐   user types "ab" → request B fires
⭐   ⭐ B RETURNS FIRST (faster path, smaller result)
⭐   ⭐ A RETURNS SECOND
⭐   ⇒ ⭐⭐ THE SCREEN NOW SHOWS RESULTS FOR "a" WHILE THE BOX
⭐     SAYS "ab". No error. No warning. Just wrong.
```

```javascript
const controller = new AbortController();
const data = await api("/search?q=ab", { signal: controller.signal });
controller.abort();                    // ⭐ cancels the in-flight request

await api("/slow", { signal: AbortSignal.timeout(5000) });   // ⭐ timeout, free
await api("/slow", { signal: AbortSignal.any([controller.signal,
                                              AbortSignal.timeout(5000)]) });
```

> ⭐⭐ **Cancel the previous request whenever a new one supersedes it** — search-as-you-type, tab
> switches, a component that unmounted. This is the same *last-write-wins* problem you solved with
> fencing tokens on Day 411: **you cannot rely on responses arriving in the order you sent them.**
> ⭐ `AbortController` is roughly `Future.cancel(true)`, except it genuinely aborts the transport.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you handle API errors on the client?"**

Open with the trap, because it establishes you have actually shipped this. **`fetch` only rejects when
the request never happened — network, CORS, abort. A 500 is a successful fetch. That's the opposite of
RestTemplate, which throws on a 4xx. So the tutorial try/catch never runs for server errors, and then
`res.json()` throws a syntax error because Spring returned a Whitelabel HTML page — and you debug a
JSON parser instead of reading a status code.**

Then the wrapper, framed as one decision. **Components never call `fetch`. There's one wrapper that
reads the body as text before parsing, so an HTML error page becomes data I can log rather than an
exception that loses it, and it throws a typed error carrying the status and parsed body. Status
matters because 401, 400, 429 and 503 are four different user experiences.**

Then the bit that reveals backend judgement. **Building the client changed my server. My validation
errors weren't field-addressable, so I added a `@RestControllerAdvice` returning RFC 7807
`ProblemDetail` with a field-and-message list. That also means the client never meets an HTML error
body — you can't render a good error state against a shape that doesn't name the field.**

Close on the race. **Search-as-you-type sends overlapping requests and they don't return in order, so
results for "a" can land after results for "ab" and the screen is silently wrong. Cancel the superseded
request with an AbortController — same ordering problem as any last-write-wins issue — and an abort is
not a failure, so it must never render as an error.**
