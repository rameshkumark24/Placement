# L-041

## `toString`

**Always override it.** The default is useless:

```java
com.app.Order@1b6d3586        // class name @ hex of the identity hash code
```

That hex is **not** the memory address — it's `Object.hashCode()`, typically derived from an
identity hash stored in the object header (Day 025). A common misconception worth correcting.

```java
@Override public String toString() {
    return "Order[id=" + id + ", customer=" + customer + ", total=" + total + "]";
}
```

**Where it shows up whether you like it or not:** log statements, exception messages, debugger
variable views, assertion failures in tests, string concatenation. **A missing `toString` costs you
every time you debug.**

**Rules:**
- Include the fields you'd want in a log line
- **Never include secrets** — passwords, tokens, PII. `toString` ends up in logs, and that's a real
  data-protection failure (your [security checklist](../../03-Web-Developer/06-Security.md) says
  "PII never written to logs" — this is one of the ways it happens by accident).
- Keep it cheap — it's called in hot logging paths
- Don't make the format a contract unless you document it as one; callers will parse it if you do

**Records generate it for you**, which is one more reason to prefer them for value types (Day 042).

## `Comparable` vs `Comparator`

**The distinction people fumble:**

| | `Comparable<T>` | `Comparator<T>` |
|---|---|---|
| Method | `int compareTo(T o)` | `int compare(T a, T b)` |
| Lives | **Inside** the class | **Outside**, as a separate object |
| How many | **One** — the natural ordering | **Many** |
| Modifies the class | ✅ yes | ❌ no |
| Use for | The one obvious ordering | Alternative or context-specific orderings |

```java
// Comparable — the class defines its own natural order
record Person(String name, int age) implements Comparable<Person> {
    @Override public int compareTo(Person o) { return Integer.compare(age, o.age); }
}
Collections.sort(people);                         // uses compareTo

// Comparator — orderings defined outside
people.sort(Comparator.comparing(Person::name));
people.sort(Comparator.comparingInt(Person::age).reversed());
```

**The decision:**

> **Is there one obviously correct ordering that's intrinsic to the type?** Then `Comparable`.
> Numbers, dates, strings — yes. A `Person`? Debatable. An `Order`? Almost certainly not — by date,
> by total, by customer are all equally valid.

**If you're unsure, use `Comparator`.** It doesn't require modifying the class, and you can have many.

### The contract

`compareTo` must return negative / zero / positive, and:

- **Antisymmetric:** `sgn(a.compareTo(b)) == -sgn(b.compareTo(a))`
- **Transitive:** `a > b` and `b > c` ⟹ `a > c`
- **Consistent:** `a.compareTo(b) == 0` ⟹ same comparison results against any `c`
- **Strongly recommended:** `a.compareTo(b) == 0` ⟺ `a.equals(b)`

**That last one is "recommended", not required — and violating it causes real, confusing bugs.**

```java
BigDecimal a = new BigDecimal("1.0");
BigDecimal b = new BigDecimal("1.00");

a.equals(b)        // FALSE — different scale
a.compareTo(b)     // 0     — numerically equal

Set<BigDecimal> hashSet = new HashSet<>();  hashSet.add(a); hashSet.add(b);  // size 2
Set<BigDecimal> treeSet = new TreeSet<>();  treeSet.add(a); treeSet.add(b);  // size 1 !
```

**The same two objects, two different set sizes**, because `HashSet` uses `equals` and `TreeSet` uses
`compareTo`. `BigDecimal` is the canonical example of this inconsistency, and it comes up again on
Day 042B.

### Building comparators

```java
Comparator<Person> byName = Comparator.comparing(Person::name);

people.sort(Comparator
        .comparing(Person::lastName)
        .thenComparing(Person::firstName)
        .thenComparingInt(Person::age)
        .reversed());

Comparator.nullsFirst(Comparator.comparing(Person::name));      // null-safe
Comparator.comparing(Person::name, String.CASE_INSENSITIVE_ORDER);
```

**Two traps:**

```java
// 💀 overflows for large or negative values (Day 028)
Comparator<Person> bad = (a, b) -> a.age() - b.age();

// ✅
Comparator<Person> good = Comparator.comparingInt(Person::age);
```

```java
// ⚠️ .reversed() applies to the WHOLE chain built so far, not just the last key
Comparator.comparing(Person::name).thenComparing(Person::age).reversed();
```

Both catch experienced people.

### Stability

`Collections.sort` and `List.sort` use **TimSort — stable** (Day 031). Equal elements keep their
relative order.

**That's why chained sorts work:** sort by age, then by name, and equal-named people remain in age
order. Primitive array sorts use quicksort and are *not* stable — but as Day 031 explained, stability
is meaningless for primitives.

## `Cloneable` — a case study in bad API design

```java
class Point implements Cloneable {
    @Override public Point clone() {
        try { return (Point) super.clone(); }
        catch (CloneNotSupportedException e) { throw new AssertionError(); }
    }
}
```

**Everything about this is wrong**, and enumerating why is a genuinely good interview answer:

**1. `Cloneable` declares no methods.** It's a marker interface (Day 039) that changes the behaviour
of `Object.clone()` — a protected method on a *different* type. A marker that modifies a method it
doesn't declare is incoherent.

**2. `clone()` is `protected` on `Object`.** You can't call `x.clone()` polymorphically through the
interface, so the interface gives you nothing.

**3. `CloneNotSupportedException` is checked** — and can't happen if you implemented `Cloneable`.
Every implementation contains dead `catch` blocks.

**4. `clone()` doesn't call a constructor.** It allocates and copies fields directly, bypassing your
invariants entirely. `final` fields can't be reassigned in a `clone`, so a class with final fields
can't clone properly at all.

**5. It's shallow by default.** Mutable fields are shared between original and copy — the same trap as
Day 031's 2D array clone and Day 034A's defensive copying.

```java
class Stack implements Cloneable {
    private Object[] elements;
    @Override public Stack clone() {
        Stack s = (Stack) super.clone();
        s.elements = elements.clone();     // MUST do this manually, or both share the array
        return s;
    }
}
```

**6. It interacts badly with inheritance.** A subclass may need deep copying the superclass knows
nothing about.

### The alternatives — use these

```java
// 1. Copy constructor
public Point(Point other) { this.x = other.x; this.y = other.y; }

// 2. Static copy factory — the JDK convention
public static Point copyOf(Point other) { return new Point(other.x, other.y); }

// 3. Just make it immutable — no copy needed at all
public record Point(int x, int y) { }
```

**All three are better:** they run a constructor so invariants hold, they work with `final` fields,
they can be documented, and they don't throw checked exceptions for impossible conditions.

**Option 3 is best.** An immutable object never needs copying — it's safe to share (Day 034A). This
is the real lesson: `Cloneable` mostly solves a problem that immutability makes disappear.

**Where you'll still meet clone:** `array.clone()` is fine and idiomatic (it's the only clean way to
copy an array), and some legacy APIs use it. But **never implement `Cloneable` in new code**.

## Type this yourself

```java
import java.math.BigDecimal;
import java.util.*;

public class ObjectMethodsDemo {

    record Person(String first, String last, int age) implements Comparable<Person> {
        @Override public int compareTo(Person o) { return Integer.compare(age, o.age); }
    }

    static class Stack implements Cloneable {
        private Object[] elements = new Object[10];
        private int size = 0;
        void push(Object o) { elements[size++] = o; }
        Object peek()       { return size == 0 ? null : elements[size - 1]; }
        void setTop(Object o) { if (size > 0) elements[size - 1] = o; }

        @Override public Stack clone() {
            try {
                Stack s = (Stack) super.clone();
                // s.elements = elements.clone();     // ← UNCOMMENT to fix the shallow copy
                return s;
            } catch (CloneNotSupportedException e) { throw new AssertionError(); }
        }
    }

    public static void main(String[] args) {

        // ---- toString ----
        System.out.println("--- toString ---");
        System.out.println("   record:  " + new Person("Ada", "Lovelace", 36));
        System.out.println("   no override: " + new Object());

        // ---- Comparable vs Comparator ----
        List<Person> people = new ArrayList<>(List.of(
                new Person("Ada", "Lovelace", 36),
                new Person("Alan", "Turing", 41),
                new Person("Grace", "Hopper", 41),
                new Person("Edsger", "Dijkstra", 72)));

        Collections.sort(people);                            // natural: by age
        System.out.println("\n--- natural order (Comparable, by age) ---");
        people.forEach(p -> System.out.println("   " + p));

        people.sort(Comparator.comparingInt(Person::age)
                              .thenComparing(Person::first));
        System.out.println("\n--- age, then first name (Comparator chain) ---");
        people.forEach(p -> System.out.println("   " + p));

        people.sort(Comparator.comparing(Person::last).reversed());
        System.out.println("\n--- last name, reversed ---");
        people.forEach(p -> System.out.println("   " + p));

        // ---- compareTo inconsistent with equals ----
        BigDecimal a = new BigDecimal("1.0"), b = new BigDecimal("1.00");
        System.out.println("\n--- BigDecimal: compareTo vs equals ---");
        System.out.println("   a.equals(b)    = " + a.equals(b));
        System.out.println("   a.compareTo(b) = " + a.compareTo(b));
        Set<BigDecimal> hash = new HashSet<>(List.of(a, b));
        Set<BigDecimal> tree = new TreeSet<>(List.of(a, b));
        System.out.println("   HashSet size = " + hash.size() + ", TreeSet size = " + tree.size()
                         + "   ← SAME objects, different sets");

        // ---- shallow clone ----
        Stack s1 = new Stack();
        s1.push("original");
        Stack s2 = s1.clone();
        s2.setTop("modified via the clone");
        System.out.println("\n--- Cloneable is shallow ---");
        System.out.println("   s1.peek() = " + s1.peek() + "   ← the ORIGINAL changed");

        // ---- comparator overflow ----
        Comparator<Integer> broken = (x, y) -> x - y;
        System.out.println("\n--- comparator subtraction overflow ---");
        System.out.println("   broken.compare(MAX, -1) = "
                + broken.compare(Integer.MAX_VALUE, -1) + "   ← negative, WRONG");
        System.out.println("   Integer.compare(MAX, -1) = "
                + Integer.compare(Integer.MAX_VALUE, -1) + "   ← correct");
    }
}
```

**Three results to note:**

1. **`HashSet` size 2, `TreeSet` size 1** for the same two `BigDecimal`s. That's `compareTo`
   inconsistent with `equals`, and it's a genuinely surprising behaviour to have seen once.
2. **Mutating the clone changed the original.** Uncomment the `elements.clone()` line and re-run.
3. **The subtraction comparator returns the wrong sign** on overflow — a real sorting bug.

## Common mistakes

| Mistake | Correction |
|---|---|
| No `toString` | Every log line and debugger view becomes useless. |
| Secrets or PII in `toString` | It ends up in logs. A real data-protection failure. |
| `(a, b) -> a - b` as a comparator | Overflows. Use `Integer.compare` / `comparingInt`. |
| Expecting `.reversed()` to affect only the last key | It reverses the whole chain built so far. |
| `compareTo` inconsistent with `equals` | Sorted and hashed collections disagree — see `BigDecimal`. |
| Implementing `Cloneable` in new code | Use a copy constructor, a copy factory, or immutability. |
| Assuming `clone()` is deep | It's shallow. Mutable fields are shared. |
| `Comparable` on a type with no obvious natural order | Use `Comparator` instead. |

## Interview questions

**Q: `Comparable` vs `Comparator`?**
> `Comparable` is implemented by the class itself and defines a single natural ordering via
> `compareTo`. `Comparator` is a separate object defining an ordering externally, so you can have many
> and you don't have to modify the class. Use `Comparable` when there's one obviously intrinsic
> ordering, and `Comparator` otherwise — which is most of the time for domain types.

**Q: What does it mean for `compareTo` to be inconsistent with `equals`?**
> That `compareTo` returns zero for objects `equals` considers different, or vice versa. It's
> permitted but causes sorted and hashed collections to disagree. `BigDecimal` is the canonical case:
> `1.0` and `1.00` compare as equal but aren't `equals`, so a `HashSet` of both has two elements and a
> `TreeSet` has one.

**Q: Why is `Cloneable` considered broken?**
> It's a marker interface that declares no methods yet changes the behaviour of `Object.clone`, which
> is protected, so the interface gives you no callable method. `CloneNotSupportedException` is checked
> but can't occur if you implemented the interface. `clone` bypasses constructors, so invariants
> aren't enforced and `final` fields can't be set. And it's shallow by default, so mutable fields are
> shared. A copy constructor, a static copy factory, or simply making the type immutable are all
> better.

**Q: Why is `(a, b) -> a - b` a bad comparator?**
> Integer subtraction overflows. Comparing `Integer.MAX_VALUE` with a negative number wraps and
> produces the wrong sign, so the sort order is corrupted. `Integer.compare` or
> `Comparator.comparingInt` avoid it.

**Q: Is Java's sort stable?**
> `Collections.sort` and `List.sort` use TimSort, which is stable — equal elements keep their relative
> order, which is what makes chained sorts work. Primitive array sorts use dual-pivot quicksort and
> aren't stable, but stability is meaningless for primitives since equal values are indistinguishable.
