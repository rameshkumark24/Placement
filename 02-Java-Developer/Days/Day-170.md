# Day 170

**L-170** · `AuthenticationManager`, `UserDetailsService`, and authorities

**Time:** 3 hrs · **Mode:** NEW

> Day 169 placed authentication in the chain: some filter recognises a credential and puts an
> `Authentication` in the context. Today is what happens inside that step — the three collaborators,
> how to plug in your own, and the two modelling decisions (roles vs authorities, and where to store
> them) that cause the most trouble later.

---

# Part 1 — The three collaborators

```
      filter extracts credentials
              │
              ▼
   ┌─ AuthenticationManager ──────────────────────────────┐
   │   ProviderManager                                    │
   │     ├── DaoAuthenticationProvider ───► UserDetailsService ───► your DB
   │     │                              └─► PasswordEncoder  (Day 171)
   │     ├── JwtAuthenticationProvider                     │
   │     └── LdapAuthenticationProvider                    │
   └──────────────────────────────────────────────────────┘
              │
              ▼
   authenticated Authentication → SecurityContextHolder
```

| Component | Job |
|---|---|
| `AuthenticationManager` | ⭐ one method: `authenticate(Authentication)` → authenticated, or throw |
| `ProviderManager` | the standard implementation. Tries each provider that `supports()` the token type |
| `AuthenticationProvider` | ⭐ knows *one* kind of credential |
| `UserDetailsService` | ⭐ **loads a user by username. It does not authenticate** |
| `PasswordEncoder` | ⭐ compares the presented password with the stored hash (Day 171) |

**⭐ The separation that matters:** `UserDetailsService` *only loads*. `DaoAuthenticationProvider`
does the comparing, the account-status checks and the error handling. People try to authenticate
inside `loadUserByUsername` and end up bypassing the checks the provider performs for free.

**`ProviderManager` tries providers in order** and returns the first success. If all decline, the
last exception is thrown. This is how you support password *and* JWT *and* API keys in one
application: one provider each.

# Part 2 — `UserDetailsService`, done properly

```java
@Service
public class DatabaseUserDetailsService implements UserDetailsService {

    private final UserRepository users;

    @Override
    @Transactional(readOnly = true)                              // ⭐ Day 164 — authorities are lazy
    public UserDetails loadUserByUsername(String username) {
        User user = users.findByEmailIgnoreCase(username)
            .orElseThrow(() -> new UsernameNotFoundException("user not found"));   // ⭐ generic

        return org.springframework.security.core.userdetails.User.builder()
            .username(user.getEmail())
            .password(user.getPasswordHash())                    // ⭐ the HASH, never a password
            .authorities(toAuthorities(user))
            .accountLocked(user.isLocked())
            .accountExpired(false)
            .credentialsExpired(user.passwordExpired())
            .disabled(!user.isEnabled())
            .build();
    }
}
```

**⭐ `@Transactional(readOnly = true)` is not optional here.** Authorities usually come from a lazy
`@ManyToMany` (Day 159), and `loadUserByUsername` is called from a *filter* — outside any transaction
the service layer would have opened. Without it you get `LazyInitializationException` during login,
which is an unpleasant thing to discover in production. Fetch the roles with an `@EntityGraph`
(Day 161) as the better fix.

## ⭐ The user-enumeration rule

```java
throw new UsernameNotFoundException("user not found");        // ⭐ same message always
```

Day 112's principle: **the response for "no such user" and "wrong password" must be identical** —
same status, same body, and ideally the same timing. Otherwise the login form is an oracle telling an
attacker which email addresses have accounts.

Spring helps by default: `DaoAuthenticationProvider` converts `UsernameNotFoundException` into
`BadCredentialsException` (via `hideUserNotFoundExceptions`, on by default) and performs a **dummy
password hash** when the user is absent, so the timing matches. **Do not disable either**, and do not
leak the distinction yourself in a custom provider.

## The four status flags, and what each is for

| Flag | Meaning | Exception |
|---|---|---|
| `disabled` | account deactivated, e.g. email unverified | `DisabledException` |
| `accountLocked` | ⭐ locked after failed attempts (Day 122) | `LockedException` |
| `accountExpired` | membership lapsed | `AccountExpiredException` |
| `credentialsExpired` | ⭐ password must be changed | `CredentialsExpiredException` |

**These are checked by the provider, not by you.** They are also a place to leak information — a
"your account is locked" message tells an attacker the account exists. **For a public login, return
the generic failure and send the detail by email; for an internal tool, showing the reason is
reasonable.** Decide deliberately.

# Part 3 — ⭐ Roles vs authorities, and the prefix that trips everyone

**They are the same type.** `GrantedAuthority` is just a string. A "role" is an authority whose name
begins with `ROLE_`, and that convention is the *only* difference.

```java
new SimpleGrantedAuthority("ROLE_ADMIN")      // a role
new SimpleGrantedAuthority("order:write")     // an authority (permission)
```

**⭐ The prefix rules, which are inconsistent and cause constant confusion:**

| API | Prefix handling |
|---|---|
| `hasRole("ADMIN")` | ⭐ **adds** `ROLE_` → checks `ROLE_ADMIN` |
| `hasAuthority("ROLE_ADMIN")` | ⭐ **literal** — you write the prefix |
| `@PreAuthorize("hasRole('ADMIN')")` | adds it |
| `.authorities("ADMIN")` in the builder | ⭐ **literal — no prefix added** |
| `.roles("ADMIN")` in the builder | ⭐ **adds** `ROLE_` |

```java
.authorities("ADMIN")        // stores "ADMIN"
.requestMatchers(...).hasRole("ADMIN")     // ⭐ checks "ROLE_ADMIN" → NEVER MATCHES
```

**The endpoint is now unreachable for everyone, and nothing says why.** Pick one convention —
store authorities with the `ROLE_` prefix and use `hasRole` without it — and write a test that
actually exercises a real admin user.

## ⭐ The modelling decision: roles or permissions?

| Approach | Check | Adding a permission |
|---|---|---|
| Role-based | `hasRole('ADMIN')` | ⭐ **redeploy** — the check is in code |
| **Permission-based** | ⭐ `hasAuthority('order:refund')` | grant it to a role in the database |

Day 118's argument, arriving in Spring:

```java
private Set<GrantedAuthority> toAuthorities(User user) {
    return Stream.concat(
        user.getRoles().stream().map(r -> new SimpleGrantedAuthority("ROLE_" + r.getName())),
        user.getRoles().stream().flatMap(r -> r.getPermissions().stream())
            .map(p -> new SimpleGrantedAuthority(p.getName()))          // ⭐ "order:refund"
    ).collect(toSet());
}
```

**Grant both.** Endpoints check *permissions*; roles remain for coarse checks and readability. Then
"support agents can now issue refunds" is a database change reviewed by whoever owns access control,
not a pull request and a deploy.

**The honest caveat:** permission-based access control is only as good as its administration. If
nobody audits which roles hold which permissions, you have replaced a reviewable code change with an
unreviewed database row. Ship it with an audit log (Day 165) of grant changes.

# Part 4 — Custom providers, and the login flow end to end

```java
@Component
public class ApiKeyAuthenticationProvider implements AuthenticationProvider {   // Day 115b

    private final ApiKeyService keys;

    @Override
    public Authentication authenticate(Authentication auth) {
        String presented = (String) auth.getCredentials();
        ApiKey key = keys.findByPrefix(prefixOf(presented))
                .orElseThrow(() -> new BadCredentialsException("invalid api key"));

        if (!keys.matches(presented, key.getHash())) {                 // ⭐ constant-time (Day 171)
            throw new BadCredentialsException("invalid api key");      // ⭐ same message
        }
        if (key.isRevoked() || key.isExpired()) throw new CredentialsExpiredException("key expired");

        return new ApiKeyAuthenticationToken(key.getClientId(), key.getAuthorities());  // ⭐ authenticated
    }

    @Override
    public boolean supports(Class<?> authentication) {
        return ApiKeyAuthenticationToken.class.isAssignableFrom(authentication);   // ⭐ required
    }
}
```

**`supports()` is what routes a token to the right provider.** Get it wrong and `ProviderManager`
skips your provider entirely — the credential is never checked and the request falls through to
anonymous.

## The login endpoint

```java
@PostMapping("/api/v1/auth/login")
TokenPair login(@Valid @RequestBody LoginRequest req) {
    Authentication auth = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(req.email(), req.password()));   // ⭐ unauthenticated token in
    return tokenService.issue(auth);                                                  // Day 173
}
```

```java
@Bean
AuthenticationManager authenticationManager(AuthenticationConfiguration c) throws Exception {
    return c.getAuthenticationManager();          // ⭐ Boot does not expose it as a bean by default
}
```

**Three things this endpoint must do beyond the happy path:**

1. ⭐ **Rate limit it** (Day 122). An unthrottled login endpoint is a credential-stuffing target, and
   password hashing is deliberately slow (Day 171), so it is also a CPU denial-of-service vector.
   Limit by IP *and* by username — by IP alone is defeated by a botnet; by username alone lets one
   IP spray thousands of accounts.
2. ⭐ **Log failures with the username and IP, and successes too** (Day 127). Detection depends on it.
   **Never log the password**, including in a request-body logging filter (Day 151).
3. **Lock after repeated failures**, with an exponential delay rather than a permanent lock —
   permanent locking is itself a denial of service against a known username.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Authenticating inside `loadUserByUsername` | bypasses the provider's status checks and timing defence |
| No `@Transactional`/`@EntityGraph` on it | `LazyInitializationException` during login |
| Different responses for unknown user vs wrong password | user enumeration |
| Disabling `hideUserNotFoundExceptions` | reintroduces enumeration |
| ⭐ `.authorities("ADMIN")` with `hasRole("ADMIN")` | never matches; endpoint unreachable |
| Roles hard-coded in every check | permission changes require a redeploy |
| Permissions with no audit of grants | unreviewed access changes |
| `supports()` wrong or missing | provider silently skipped |
| Unthrottled login | credential stuffing and hash-CPU DoS |
| Logging the password | credentials in the log store |
| Permanent account lock | DoS against a known username |
| Storing the password, not the hash, in `UserDetails` | catastrophic |

## Interview questions

**Q: Walk through what happens when someone logs in.**
The filter or controller builds an unauthenticated `UsernamePasswordAuthenticationToken` and passes
it to `AuthenticationManager`. `ProviderManager` finds a provider that supports that token type —
`DaoAuthenticationProvider` — which calls `UserDetailsService` to load the user, uses the
`PasswordEncoder` to compare, checks the account status flags, and returns an authenticated token
that goes into the `SecurityContext`.

**Q: What is the difference between a role and an authority?**
Nothing structural — a role is an authority whose name starts with `ROLE_`. The confusion is that
`hasRole` adds the prefix and `hasAuthority` does not, so storing `"ADMIN"` and checking
`hasRole("ADMIN")` never matches and the endpoint is unreachable with no error.

**Q: Roles or permissions in your checks?**
Permissions. Checking `hasAuthority('order:refund')` means granting that capability to a role is a
database change; checking `hasRole('ADMIN')` means a code change and a deploy. I grant both so roles
stay available for coarse checks, and I audit permission grants.

**Q: How do you avoid user enumeration on login?**
Identical response and identical timing for "no such user" and "wrong password". Spring does this by
default — it converts `UsernameNotFoundException` to `BadCredentialsException` and performs a dummy
hash when the user is absent, so the timing matches.
