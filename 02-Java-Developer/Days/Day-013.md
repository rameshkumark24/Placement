# Part 1 — L-013 · What CSS actually is

## The answer

**CSS is a declarative language for describing how a document tree should be presented.**

Unpack "declarative": you state the desired outcome, not the steps. You never write "measure this
box, then position it 40px down". You write `margin-top: 40px` and the browser's layout engine works
out how.

Like HTML (Day 012), it is **not a programming language** — no loops, no functions, no computation
beyond `calc()`. It has variables (custom properties) but no control flow.

And like HTML, it operates on the **tree** from Day 012. Every selector is a query over that tree:

```css
main > article p.intro { color: navy; }
      │        │
      │        └── descendant: any p.intro anywhere under article
      └── child: article must be a direct child of main
```

## The box model — the single most important idea

**Every element is a rectangular box.** Not "renders as" — *is*. Four nested regions:

```
    ┌─────────────────────────────────────────────┐
    │              MARGIN (transparent)           │
    │   ┌─────────────────────────────────────┐   │
    │   │           BORDER                    │   │
    │   │   ┌─────────────────────────────┐   │   │
    │   │   │        PADDING              │   │   │
    │   │   │   ┌─────────────────────┐   │   │   │
    │   │   │   │      CONTENT        │   │   │   │
    │   │   │   │   width × height    │   │   │   │
    │   │   │   └─────────────────────┘   │   │   │
    │   │   └─────────────────────────────┘   │   │
    │   └─────────────────────────────────────┘   │
    └─────────────────────────────────────────────┘
```

### The trap that has confused every beginner since 1996

```css
.box {
  width: 300px;
  padding: 20px;
  border: 5px solid;
}
```

**How wide is that box on screen?** With the default `box-sizing: content-box`: **350px**.
`width` sizes the *content area only*; padding and border are added on top.

Two 50%-wide boxes with padding won't fit side by side, and the layout breaks in a way that looks
like a bug in the browser.

**The fix, and you should put it in every project:**

```css
*, *::before, *::after { box-sizing: border-box; }
```

Now `width: 300px` means the box is 300px **including** padding and border. Content shrinks to fit.
This is what every CSS framework — including Tailwind — sets by default. Now you know what that line
in a reset stylesheet is doing.

### Margin collapsing

Adjacent vertical margins **merge into one**, taking the larger:

```
  <p style="margin-bottom: 30px">A</p>
  <p style="margin-top: 20px">B</p>

  Gap between them: 30px, not 50px.
```

Only vertical, only in normal flow, and it doesn't happen inside flex or grid containers. It's a
frequent source of "why is my spacing wrong" — and knowing it doesn't apply in flex/grid is half the
reason people prefer them.

## The cascade — where C, S and S come from

When multiple rules target the same element, which wins? The browser resolves in this order:

```
   1. Origin & importance     author !important > author > user agent (browser default)
   2. Specificity             more specific selector wins
   3. Source order            last one declared wins
```

### Specificity

Score each selector as a triple **(IDs, classes/attributes/pseudo-classes, elements)**:

| Selector | Score | Notes |
|---|---|---|
| `p` | (0,0,1) | |
| `.intro` | (0,1,0) | |
| `#main` | (1,0,0) | |
| `main p.intro` | (0,1,2) | |
| `#main .intro p` | (1,1,1) | |
| inline `style=""` | wins over all selectors | |
| `!important` | wins over everything | |

Compare left to right. **(1,0,0) beats (0,99,0)** — a single ID beats ninety-nine classes.
Specificity is not additive across columns; it's lexicographic.

**Why this matters practically:** it's why your `.button { color: red }` doesn't apply when someone
earlier wrote `#sidebar .button { color: blue }`, and why the temptation is to add `!important`.
Then someone else adds `!important`. Then you have a stylesheet nobody can reason about.

**The professional answer is to keep specificity flat** — mostly single classes, no IDs for styling.
That's exactly what utility CSS (Tailwind) enforces structurally: every utility is one class, so
specificity is uniform and the cascade stops being a puzzle. You already use Tailwind in the web
domain; this is the problem it solves.

## Layout algorithms

The browser has several, and you pick one per container. **This is the part that actually determines
whether CSS feels hard.**

| Mode | `display` | Use for |
|---|---|---|
| **Normal flow** | `block` / `inline` | Documents, text |
| **Flexbox** | `flex` | One dimension — a row or a column |
| **Grid** | `grid` | Two dimensions — rows and columns together |
| **Positioned** | `absolute` / `fixed` / `sticky` | Overlays, tooltips, sticky headers |

### Flexbox — one axis

```css
.container {
  display: flex;
  flex-direction: row;          /* the MAIN axis */
  justify-content: space-between;   /* along the main axis */
  align-items: center;              /* along the CROSS axis */
  gap: 1rem;
}
```

**The thing to internalise:** `justify-*` works on the main axis, `align-*` on the cross axis. Change
`flex-direction` to `column` and those two swap meaning. Almost every flexbox confusion is this.

### Grid — two axes

```css
.layout {
  display: grid;
  grid-template-columns: 200px 1fr;   /* fixed sidebar, flexible main */
  gap: 1rem;
}
```

`1fr` means "one fraction of the remaining space". Grid is the right choice for page-level layout;
flex for a row of buttons or a card's internals.

**Rule of thumb:** grid for the page, flex for the components. Nesting them is normal and correct.

### Positioning — and stacking contexts

`position: absolute` removes the element from flow and positions it against its nearest
**positioned ancestor** (one with `position` other than `static`). Forgetting to set
`position: relative` on the intended parent is why absolutely positioned things fly to the corner of
the page.

`z-index` only works on positioned elements, and only *within a stacking context*. A child can never
escape its parent's stacking context — which is why your modal with `z-index: 9999` still renders
behind a header. That's a real debugging trap; the fix is portalling the modal to the body, which is
exactly what UI libraries do.

## The units that matter

| Unit | Relative to | Use for |
|---|---|---|
| `px` | Nothing (absolute) | Borders, small fixed details |
| `rem` | Root font size | **Almost everything** — respects user font settings |
| `em` | Parent font size | Spacing that should scale with local text |
| `%` | Parent dimension | Widths |
| `vw` / `vh` | Viewport | Full-screen sections |
| `fr` | Free space in a grid | Grid columns |
| `ch` | Width of "0" | Max line length (~65ch is readable) |

**Use `rem` for font sizes, not `px`.** A user who has increased their browser's default font size
gets larger text with `rem` and is ignored with `px`. That's an accessibility requirement, and it
connects to the "dynamic font scaling" item in
[`04-App-Developer/02-Design-System.md`](../../04-App-Developer/02-Design-System.md).

## Type this yourself

```html
<!DOCTYPE html>
<html><head><style>
  * { box-sizing: border-box; }             /* comment this line out and reload */

  .demo { width: 300px; padding: 20px; border: 5px solid crimson;
          background: lightyellow; margin-bottom: 30px; }

  /* Specificity experiment — which colour wins? Predict BEFORE loading. */
  p              { color: green; }
  .text          { color: blue; }
  #special       { color: red; }
  main p.text    { color: purple; }

  .flex { display: flex; justify-content: space-between; align-items: center;
          gap: 1rem; background: #eee; padding: 1rem; }
  .flex > div { background: steelblue; color: white; padding: 1rem; }

  .grid { display: grid; grid-template-columns: 200px 1fr; gap: 1rem; margin-top: 2rem; }
  .grid > div { background: seagreen; color: white; padding: 1rem; }
</style></head>
<body>
  <div class="demo">Measure me in devtools.</div>

  <main>
    <p id="special" class="text">What colour am I?</p>
  </main>

  <div class="flex"><div>A</div><div>B</div><div>C</div></div>

  <div class="grid"><div>sidebar</div><div>main content</div></div>
</body></html>
```

**Do these four, in order:**

1. **Open devtools → Elements → Computed → scroll to the box model diagram.** Hover the `.demo`
   element. Read the four regions. This visual is the single best CSS debugging tool and most people
   never open it.
2. **Comment out the `box-sizing` line and reload.** Watch the box grow from 300px to 350px. That's
   the trap, measured.
3. **Predict the paragraph's colour, then check.** It's red — `#special` is (1,0,0) and beats
   `main p.text` at (0,1,2). One ID beats any number of classes.
4. **In devtools, change `flex-direction` to `column`** on `.flex` and watch `justify-content` and
   `align-items` swap which direction they control.

Then serve this from your Day 012 `HtmlServer` — put it in the `html` text block. You're now serving
HTML *and* CSS from a socket you wrote.

## Common mistakes

| Mistake | Correction |
|---|---|
| Not setting `box-sizing: border-box` | `width` excludes padding and border by default. Set it globally, always. |
| Fighting specificity with `!important` | It escalates. Keep specificity flat — single classes, no IDs for styling. |
| `z-index: 9999` to fix layering | z-index is scoped to a stacking context. A child can't escape its parent's. |
| Expecting `justify-content` to always mean horizontal | It means "along the main axis", which flips with `flex-direction`. |
| `px` for font sizes | Ignores the user's browser font setting. Use `rem`. |
| Absolute positioning without a positioned parent | It anchors to the nearest positioned ancestor, or the viewport. |
| Expecting margins to add up | Adjacent vertical margins collapse to the larger — in normal flow only. |

## Interview questions

**Q: What is CSS?**
> A declarative stylesheet language describing how a document tree should be presented. You state the
> desired result and the browser's layout engine determines how to achieve it. It selects elements by
> traversing the DOM tree and applies presentation rules resolved through the cascade.

**Q: Explain the box model and `box-sizing`.**
> Every element is a box with content, padding, border and margin regions. With the default
> `content-box`, the `width` property sizes only the content, so padding and border add to the
> rendered width. With `border-box`, `width` includes padding and border, which is almost always what
> you want — it's why resets set it globally.

**Q: How does the cascade resolve conflicting rules?**
> First by origin and importance — `!important` author styles beat normal author styles, which beat
> browser defaults. Then by specificity, scored as IDs, then classes and pseudo-classes, then
> elements, compared left to right. Ties are broken by source order, last one winning.

**Q: When would you use flexbox versus grid?**
> Flexbox for one-dimensional layout — a row or a column, where content size drives the distribution.
> Grid for two-dimensional layout, where you define rows and columns together. In practice, grid for
> page structure and flex within components.

**Q: Why doesn't my `z-index: 9999` element appear on top?**
> z-index only applies within a stacking context, and a child cannot escape its parent's. If an
> ancestor creates a stacking context — via `position` plus z-index, `transform`, `opacity` below 1,
> `filter` — the element is confined to it. The usual fix is rendering the element as a direct child
> of the body via a portal.

# Part 2 — C-09 · HTTP on the wire

*You covered the history and motivation on [Day 011](Day-011.md). This is the wire format — what the
bytes actually look like. If Day 011 is solid, this is a legitimate RECALL.*

## HTTP/1.1 — text, and you can type it

```
GET /index.html HTTP/1.1\r\n
Host: example.com\r\n
User-Agent: curl/8.0\r\n
\r\n
```

Human-readable, `telnet`-debuggable. **The cost:** headers are re-sent in full on every request. Load
70 resources and you send the same `Cookie` and `User-Agent` seventy times — often 600–800 bytes each.

## HTTP/2 — binary frames

Every message becomes typed frames on one connection, each tagged with a **stream ID**:

```
   ┌─────────────────────────────────────────────────┐
   │ Length (24) │ Type (8) │ Flags (8) │ Stream ID (31) │
   ├─────────────────────────────────────────────────┤
   │ Frame payload                                   │
   └─────────────────────────────────────────────────┘
```

| Frame type | Carries |
|---|---|
| `HEADERS` | Request/response headers (HPACK-compressed) |
| `DATA` | Body bytes |
| `SETTINGS` | Connection parameters, exchanged at start |
| `WINDOW_UPDATE` | Per-stream flow control |
| `RST_STREAM` | Cancel one stream without killing the connection |
| `GOAWAY` | Graceful connection shutdown |

**Stream IDs:** odd numbers are client-initiated, even are server-initiated. That's how both sides
open streams without colliding — no negotiation needed.

**`RST_STREAM` is quietly important.** In HTTP/1.1, cancelling a request means killing the whole TCP
connection. In HTTP/2 you cancel one stream and everything else continues. That's what makes
`AbortController` cheap in a browser — the cancellation you write about in
[`03-Web-Developer/03-Frontend.md`](../../03-Web-Developer/03-Frontend.md) maps to one frame.

### HPACK

Two mechanisms:

1. **Static table** — 61 predefined common header entries. `:method: GET` is index 2, so it's one
   byte on the wire.
2. **Dynamic table** — headers seen earlier in this connection get an index. The second request's
   `Cookie` is a reference, not the value.

Typically 80–90% header reduction. And it's why HTTP/2 has a *per-connection* state that HTTP/1.1
lacks — the dynamic table must stay in sync at both ends.

### Per-stream flow control

HTTP/2 adds its own flow control on top of TCP's (Day 007, C-05), because one TCP connection now
carries many logical streams and a slow consumer on one shouldn't stall the others.

## HTTP/3 — QUIC frames over UDP

Similar framing, but streams are native to QUIC rather than layered on top. Header compression
becomes **QPACK** — HPACK's dynamic table required strict ordering, which breaks when streams can
arrive out of order. QPACK decouples the table updates from the stream data to allow it.

**ALPN** negotiates the protocol during the TLS handshake: the client offers `h2`, `http/1.1`,
`h3`; the server picks. Zero extra round trips.

## Type this yourself

```bash
curl -v --http1.1 https://www.google.com 2>&1 | head -30
curl -v --http2   https://www.google.com 2>&1 | head -30
```

Compare. With `--http2` you'll see `* Using HTTP2, server supports multiplexing` and headers shown
with the `:method`, `:path`, `:authority` **pseudo-headers** — those colon-prefixed fields are how
HTTP/2 encodes the request line, since there is no text request line any more.

## Interview questions

**Q: What changes in the HTTP/2 wire format?**
> It becomes binary framing. Each message is split into typed frames — HEADERS, DATA and others —
> tagged with a stream ID, so many streams interleave on one connection and are reassembled by ID.
> Headers are compressed with HPACK using static and dynamic tables. The request line becomes pseudo-headers.

**Q: What does `RST_STREAM` give you that HTTP/1.1 lacks?**
> Cancelling a single request without tearing down the connection. In HTTP/1.1, aborting a request
> means closing the TCP connection and paying a new handshake for the next one.

**Q: Why does HTTP/3 need QPACK instead of HPACK?**
> HPACK's dynamic table assumes headers arrive in order, which holds over TCP. QUIC streams can
> arrive out of order, so QPACK separates table updates from stream data to avoid head-of-line
> blocking on the compression state.
