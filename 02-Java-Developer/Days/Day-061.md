# Part 1 — L-061 · Exceptions

## What an exception actually is

An exception is **a non-local transfer of control that carries a value**. That is the whole idea.
Normal control flow returns to the caller; an exception unwinds through every frame on the stack
until it finds a handler, discarding each frame's locals as it goes.

Concretely, when `throw` executes:

1. The JVM builds the exception object on the heap. Its constructor calls `fillInStackTrace()`,
   which **walks the entire call stack** and records each frame. This is the expensive part.
2. The JVM searches the current method's **exception table** — a per-method structure in the class
   file mapping bytecode ranges to handlers — for an entry whose type matches.
3. No match? The frame is popped and the search continues in the caller. Repeat.
4. No handler anywhere? The thread's `UncaughtExceptionHandler` runs, prints the trace, and the
   thread dies. If that thread is the only non-daemon thread, the JVM exits.

You can see the exception table with `javap -c` (Day 024):

```
Exception table:
   from    to  target type
       0     8    11   Class java/io/IOException
```

**No lookup happens at all when nothing is thrown.** A `try` block costs zero at runtime — the table
is consulted only during unwinding. This kills the folk belief that `try` blocks are slow. What is
slow is *throwing*, and specifically `fillInStackTrace`.

## The hierarchy — and why it has the shape it does

```
                    Throwable
                   /         \
              Error           Exception
             /     \         /         \
   OutOfMemory   Stack   RuntimeException   IOException, SQLException…
   Error         Overflow   /        \      (checked)
                        NullPointer  IllegalArgument…
                        (unchecked)
```

Three groups, three different intents:

| Group | Checked? | Meaning | You should |
|---|---|---|---|
| `Error` | no | The JVM or environment is broken | **not catch it** |
| `RuntimeException` | no | A bug in your code | fix the bug, not catch it |
| Other `Exception` | **yes** | An expected failure of the outside world | handle or declare |

The dividing question is **"could a correct program have prevented this?"** A `NullPointerException`
is preventable — you had a bug. A file being deleted between your check and your open is not
preventable, because another process owns that decision. That distinction is the entire checked /
unchecked design.

`Error` deserves emphasis. Catching `OutOfMemoryError` to "recover" almost never works: the handler
itself needs to allocate, so it usually throws again. `StackOverflowError` is marginally more
catchable but signals runaway recursion. `catch (Throwable t)` is a code smell in nearly all
application code — it swallows `Error` alongside everything else.

## Checked exceptions — the argument on both sides

Java is the only mainstream language that kept them. The intent was sound: the *type signature*
tells you what can go wrong, and the compiler makes you acknowledge it.

**Why they are criticised:**

- **They break abstraction.** Add a `throws SQLException` deep in the stack and every caller's
  signature changes. The storage mechanism leaks into unrelated layers.
- **They fight generics and lambdas.** `Function<T,R>.apply` declares no checked exception, so *no*
  lambda in the standard library can throw one. Day 057's exercises hit this.
- **They encourage the worst possible handler**, the empty catch block, because that is the fastest
  way to make the compiler stop complaining.

The modern consensus — and what Spring does throughout — is to **wrap checked exceptions in
unchecked ones at the boundary** where you cross an abstraction layer. Spring's
`DataAccessException` hierarchy is exactly this: `SQLException` becomes an unchecked
`DuplicateKeyException`, and callers who cannot do anything about it are not forced to mention it.

Know both sides. "Checked exceptions are bad" is a weak interview answer; "checked exceptions
express recoverable conditions but leak through layers, so most codebases translate them at the
boundary" is a strong one.

## Code to type — the anatomy

```java
public class ExceptionAnatomy {

    static void level3() {
        throw new IllegalStateException("bottom");
    }

    static void level2() {
        try {
            level3();
        } catch (IllegalStateException e) {
            // WRONG: destroys the original stack trace
            // throw new RuntimeException("level2 failed");

            // RIGHT: chain the cause
            throw new RuntimeException("level2 failed", e);
        }
    }

    static void level1() { level2(); }

    public static void main(String[] args) {
        try {
            level1();
        } catch (RuntimeException e) {
            System.out.println("caught: " + e.getMessage());
            System.out.println("cause : " + e.getCause().getMessage());
            e.printStackTrace();
        }

        // finally always runs — even on return
        System.out.println("f() returns " + f());

        // …and it can silently swallow an exception
        try {
            System.out.println("g() returns " + g());
        } catch (Exception e) {
            System.out.println("never reached");
        }
    }

    static int f() {
        try { return 1; }
        finally { System.out.println("finally ran"); }
    }

    @SuppressWarnings("finally")
    static int g() {
        try { throw new RuntimeException("lost!"); }
        finally { return 42; }        // 💀 discards the exception entirely
    }
}
```

Run it. Two things to notice.

**The chained trace prints `Caused by:`** and the *original* line number in `level3`. Without the
second constructor argument, that line is gone forever and you debug blind. This is the single most
common real-world mistake in exception handling.

**`g()` returns 42 and the exception vanishes.** A `return` (or `break`, or `continue`) inside
`finally` discards any in-flight exception. Compilers warn about it; treat the warning as an error.

## try-with-resources

Before Java 7 the correct close was genuinely hard:

```java
InputStream in = null;
try {
    in = new FileInputStream(f);
    ...
} finally {
    if (in != null) {
        try { in.close(); } catch (IOException ignored) {}   // nested try in a finally
    }
}
```

And it still had a bug: if the body throws *and* `close()` throws, the close exception replaces the
real one. Try-with-resources fixes both:

```java
try (var in  = new FileInputStream("in.txt");
     var out = new FileOutputStream("out.txt")) {
    in.transferTo(out);
}                       // closed in REVERSE order, out then in
```

Three properties worth knowing precisely:

1. **Reverse order close** — matches construction dependency, so a writer wrapping a stream closes
   before the stream it wraps.
2. **Suppressed exceptions** — if the body throws and `close()` also throws, the body's exception
   propagates and the close exception is attached, retrievable via `getSuppressed()` and printed as
   `Suppressed:`. Nothing is lost.
3. **The resource variable is implicitly final**, and since Java 9 you may name an
   already-effectively-final variable rather than declaring it inline.

Anything implementing `AutoCloseable` qualifies — including classes you write.

```java
class Resource implements AutoCloseable {
    private final String name;
    Resource(String name) { this.name = name; System.out.println("open " + name); }
    void use() { throw new RuntimeException("body failed in " + name); }
    @Override public void close() { throw new RuntimeException("close failed in " + name); }
}

public static void main(String[] args) {
    try (Resource a = new Resource("A"); Resource b = new Resource("B")) {
        b.use();
    } catch (Exception e) {
        System.out.println("primary: " + e.getMessage());
        for (Throwable s : e.getSuppressed())
            System.out.println("suppressed: " + s.getMessage());
    }
}
```

Predict the output before running: which exception is primary, and how many are suppressed?

## Custom exceptions

```java
public class InsufficientFundsException extends RuntimeException {
    private final String accountId;
    private final long shortfallCents;

    public InsufficientFundsException(String accountId, long shortfallCents) {
        super("Account %s short by %d cents".formatted(accountId, shortfallCents));
        this.accountId = accountId;
        this.shortfallCents = shortfallCents;
    }

    public String getAccountId() { return accountId; }
    public long getShortfallCents() { return shortfallCents; }
}
```

Two rules that matter:

**Carry structured data, not just a string.** The caller — or your error-handling layer, or Sentry
— may need the account id as a field. Parsing it back out of the message is what bad codebases do.

**Always offer a `(String message, Throwable cause)` constructor** if the exception can wrap
another. Omitting it is why so many codebases lose stack traces.

For hot paths where the trace is not needed (control-flow signalling inside a parser, for example)
you can suppress the expensive part:

```java
protected NoTraceException(String msg) {
    super(msg, null, /*enableSuppression*/ false, /*writableStackTrace*/ false);
}
```

That turns a ~10 microsecond throw into a ~20 nanosecond one. Use it rarely and deliberately; a
traceless exception in production is very hard to debug.

## Multi-catch and rethrow typing

```java
try {
    risky();
} catch (IOException | SQLException e) {     // e is effectively final; type is the LUB
    log.error("io or sql", e);
    throw e;                                  // precise rethrow — see below
}
```

Since Java 7 the compiler performs **precise rethrow analysis**: it knows the `try` block can only
throw `IOException` or `SQLException`, so the enclosing method may declare exactly
`throws IOException, SQLException` rather than the useless `throws Exception`.

## Common mistakes

| Mistake | What it costs you |
|---|---|
| `catch (Exception e) {}` | Silent failure. The worst bug class in existence. |
| `new RuntimeException(e.getMessage())` | Loses the cause and the whole trace. Pass `e`. |
| `catch (Exception e)` around a whole method | Catches bugs you meant to see and hides them. |
| `return`/`break` inside `finally` | Discards the in-flight exception. |
| Exceptions for control flow | 10–100× slower than a boolean, and it reads as noise. |
| `e.printStackTrace()` in production | Goes to stderr, unstructured, invisible to your log pipeline. |
| Catching `Throwable` | Swallows `OutOfMemoryError` and `ThreadDeath`. |
| Logging *and* rethrowing | The same failure appears three times in the log. Do one. |

That last one is worth expanding. **Log where you handle, throw where you don't.** If you log and
rethrow at every layer, a single failure produces four stack traces and you cannot tell whether
that was one incident or four.

## Interview questions

**Q: Checked vs unchecked — when do you use each?**
Checked for conditions a caller can plausibly recover from and that are outside the program's
control (a missing file, a network timeout). Unchecked for programming errors (null, bad argument,
illegal state). In practice most modern codebases translate checked to unchecked at layer
boundaries so the exception type does not leak through unrelated signatures.

**Q: What does `finally` guarantee?**
That it runs on normal completion, on `return`, and on exception — but *not* if the JVM exits
(`System.exit`), if the thread is killed at the OS level, or if the JVM crashes. With
try-with-resources you rarely need it.

**Q: Why is throwing expensive?**
`fillInStackTrace` walks the whole stack when the exception is constructed. Depth drives the cost.
The `try` block itself is free.

**Q: What is a suppressed exception?**
When a try-with-resources body throws and `close()` also throws, the body's exception propagates
and the close exception is attached via `addSuppressed`. Before Java 7 the close exception would
mask the real cause.

**Q: Can a constructor throw?**
Yes — that is the right way to reject invalid construction, and it pairs with Day 034A's
validate-then-copy ordering. The object is never published.

Two minutes: **"How do you handle errors in Java?"**

Weak answers describe try/catch syntax. Strong answers talk about *modelling*: which failures are

handle it or propagate it, never swallow it. Mention chaining the cause; interviewers notice.
