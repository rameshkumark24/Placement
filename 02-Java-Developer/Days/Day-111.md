# Day 111

**L-111** · Authentication vs authorization — the distinction people fail on

**Time:** 3 hrs · **Mode:** NEW

> it precisely right makes the next eight days coherent; getting it fuzzy makes them a pile of

---

# Part 1 — The three questions

```
   AuthN — Authentication:   WHO ARE YOU?          → identity
   AuthZ — Authorization:    WHAT MAY YOU DO?      → permission
   Accounting / Audit:       WHAT DID YOU DO?      → the record
```

**Authentication proves identity. Authorization grants permission. They are different systems, they
fail differently, and they must be implemented separately.**

The single sentence to have ready:

> **Authentication is the front door; authorization is which rooms you may enter.** Getting through
> the door tells you nothing about the rooms.

| | Authentication | Authorization |
|---|---|---|
| Question | Who are you? | May you do this? |
| Happens | **Once** per session or request | **Every** operation, on **every** resource |
| Failure | `401 Unauthorized` (means *unauthenticated*) | `403 Forbidden` (or `404` — Day 104) |
| Evidence | Password, token, certificate, biometric | Roles, ownership, policy |
| Answer | A principal, or nothing | Yes or no — per resource |
| Changes | Rarely during a session | Can change mid-session |

**The "every operation, every resource" row is the one that matters.** Authentication happens once
and is then carried; authorization must be re-evaluated for each individual object. Forgetting that
is IDOR (Day 105), and it is the most common serious API vulnerability there is.

## The failure that defines the difference

```java
@GetMapping("/orders/{id}")
public Order get(@PathVariable String id) {
    // Spring Security has authenticated the caller. A valid token is present.
    return repository.findById(id).orElseThrow();      // 💀 ANY user, ANY order.
}
```

**Perfect authentication. Zero authorization.** The system knows exactly who is asking and never asks
whether they may. Every user can read every order by changing a number in a URL.

That is why the distinction is not pedantry: a system can be flawlessly authenticated and completely
insecure.

# Part 2 — Authentication: the factors

```
Something you KNOW    password, PIN, security question
Something you HAVE    phone (TOTP), hardware key, smart card
Something you ARE     fingerprint, face, voice
Somewhere you ARE     geolocation, network (contextual)
```

**MFA means factors from *different* categories.** A password plus a security question is two things
you know — a single factor, twice. That is the definition question interviewers use.

### The strength ordering of second factors

| Method | Strength | Weakness |
|---|---|---|
| **SMS OTP** | ⚠️ weakest | **SIM swapping**, SS7 interception, phishable |
| Email OTP | weak | Only as strong as the email account |
| **TOTP** (Authenticator app) | good | Phishable — the user can be tricked into typing it |
| Push approval | good | "MFA fatigue" — spam prompts until someone taps accept |
| **WebAuthn / passkeys** | ✅ **strongest** | **Phishing-resistant by design** |

**Why WebAuthn is categorically different, not just better:** the browser signs a challenge with a
private key that never leaves the device, **and the signature is bound to the origin**. A phishing
site at `acme-login.com` cannot obtain a signature valid for `acme.com` — the browser will not
produce one. Every other method above can be relayed by a convincing fake page, because the user can
be induced to hand over the secret.

NIST deprecated SMS as a factor years ago. It is still better than nothing, and it is still the
weakest thing you can call MFA.

## Passwordless and passkeys

The direction of travel: **magic links**, **passkeys** (WebAuthn credentials synced across a user's
devices), and **OTP-only** flows. Passkeys remove the password entirely — no reuse, no phishing, no
database of hashes to leak. Apple, Google and Microsoft all ship them.

Day 112 covers password storage because you will inherit passwords for years, but **for a new system,
passkeys with a fallback are the modern default**.

## Authentication as a system, not a login form

The parts people forget — and each is a real breach vector:

- **Registration** and **email verification**
- **Password reset** ⚠️ the most-attacked flow in most applications
- **Session management** (Day 113) and logout
- **Account lockout / throttling** — and the tension below
- **Account recovery** ⚠️ often the weakest link in the entire system

> **A system is only as strong as its account recovery.** Perfect passkey authentication with a
> "forgot device? answer your mother's maiden name" fallback is as strong as the maiden name.
> Attackers always target the recovery path.

**Lockout is a genuine trade-off**, worth being able to argue both sides: locking after N failures
stops brute force but hands an attacker a denial-of-service — they can lock any account by failing
five times. The usual resolution is **exponential throttling with jitter rather than hard lockout**,
plus per-IP and per-account rate limits (Day 122), plus a check against known-breached password
lists.

**Timing attacks** matter here too:

```java
// ❌ returns fast for an unknown user, slow for a known one → user enumeration
User u = repo.findByEmail(email);
if (u == null) return failure();
if (!encoder.matches(password, u.hash())) return failure();

// ✅ constant-ish work regardless
User u = repo.findByEmail(email);
String hash = (u != null) ? u.hash() : DUMMY_HASH;    // hash a dummy anyway
boolean ok = encoder.matches(password, hash);
return (ok && u != null) ? success(u) : failure();
```

Same principle in the response: **"invalid email or password"**, never "no such user" — and the same
`202` for both cases in a password reset (Day 104).

# Part 3 — Authorization: the models

Day 118 covers these in depth. The shape now, so the security block has a frame:

**RBAC — Role-Based.** Users have roles; roles have permissions.

```
alice → ADMIN  → [orders:read, orders:write, users:manage]
bob   → VIEWER → [orders:read]
```

Simple, auditable, and it is what most systems need. It fails when permissions depend on *the
specific object*: "a manager may approve expenses, but not their own."

**ABAC — Attribute-Based.** A policy over attributes of the subject, the resource, the action and the
environment.

```
ALLOW when subject.department == resource.department
        AND subject.level >= resource.required_level
        AND action == 'read'
        AND time.hour BETWEEN 9 AND 18
```

Expressive; harder to audit and to answer "who can see this?"

**ReBAC — Relationship-Based.** Permission derives from a graph of relationships — Google Zanzibar,
OpenFGA, SpiceDB.

```
user:alice is owner of doc:readme
group:eng  is viewer of folder:specs
doc:readme is parent folder:specs   ⇒ eng can view readme
```

The right model for document sharing, nested resources and "anyone with the link".

**ACL — a per-object list.** Filesystem permissions; simple, but does not scale to policy questions.

> **Start with RBAC plus ownership checks.** That covers most systems. Add attributes when a real
> requirement demands them, and reach for ReBAC when the domain is genuinely a graph.

## Where authorization must live

```
┌─────────────────────────────────────────────────┐
│ Gateway / edge      coarse: is the token valid?  │  ← NOT sufficient
├─────────────────────────────────────────────────┤
│ Endpoint            "requires ROLE_ADMIN"        │  ← NOT sufficient
├─────────────────────────────────────────────────┤
│ Resource            "is this YOUR order?"        │  ← ⭐ THE ONE THAT MATTERS
├─────────────────────────────────────────────────┤
│ Field               "may you see the salary?"    │  ← for sensitive fields
├─────────────────────────────────────────────────┤
│ Database            row-level security           │  ← defence in depth
└─────────────────────────────────────────────────┘
```

**Endpoint-level authorization is where most systems stop, and it is not enough.** `@PreAuthorize
("hasRole('USER')")` says a user may call this endpoint. It says nothing about *which* order.

The structural fix from Day 105, restated because it is the most important defensive pattern in this
whole block:

```java
// ❌ fetch then check — the check can be forgotten, and often is
Order o = repo.findById(id);
if (!o.customerId().equals(caller.id())) throw new NotFoundException();

// ✅ scope the query — there is no unscoped method to call by mistake
Order o = repo.findByIdAndCustomerId(id, caller.id()).orElseThrow(NotFoundException::new);
```

**Make the insecure version impossible to write**, rather than remembering to write the secure one.
For multi-tenant systems, push it further down still — into database **row-level security**, so even
a forgotten `WHERE` clause cannot leak across tenants.

## Never trust the client for authorization

```javascript
if (user.role === 'ADMIN') { showDeleteButton(); }     // UX only (Day 105)
```

Hiding a button is not a permission. The endpoint must check, every time. The browser's devtools
remove the button's absence in three seconds.

Equally: **do not trust claims you did not verify.** A JWT's `role` claim is attacker-controlled
until the signature is verified (Day 114), and even then it is only as trustworthy as the issuer and
as *fresh* as the token's lifetime — which is why revocation matters (Day 115).

# Part 4 — The third question: audit

Often forgotten and frequently a compliance requirement.

**Log every security-relevant event**, and design the log so it can answer questions:

```
authentication:   success, failure, MFA challenge, MFA success/failure, logout
authorization:    every DENIED access attempt          ← the highest-signal events you have
account:          created, password changed, email changed, MFA enrolled/removed
privilege:        role granted or revoked, permission changed
data:             access to and export of sensitive records
```

**Denied authorization attempts are your best intrusion signal.** One `403` is a bug or a confused
user. Fifty from one principal across fifty different object ids in a minute is someone enumerating
— and it is exactly the signature of an IDOR probe. **Alert on the pattern, not the individual
event.**

The record must contain: **who, what, when, from where, and the outcome** — plus the correlation id
(Day 073A) so the full request can be reconstructed.

Two properties: **audit logs must be append-only and separately stored**, because an attacker's first
move after gaining access is to delete the evidence. And of course they must contain no credentials
(Day 073A).

## Common mistakes

| Mistake | Consequence |
|---|---|
| Treating authentication as sufficient | IDOR — every user reads every record |
| Authorization only at the endpoint | No per-object check |
| Client-side permission checks | Trivially bypassed |
| Trusting unverified token claims | Forged roles |
| Two factors from the same category | Not MFA |
| SMS as the primary second factor | SIM swap, SS7 |
| Hard lockout after N failures | An attacker can lock any account |
| Different responses for unknown user vs wrong password | User enumeration |
| Fast-fail on unknown users | Timing-based enumeration |
| Weak account recovery | The whole system reduces to it |
| Fetch-then-check | The check gets forgotten |
| No audit log for denials | No intrusion signal |
| Audit logs writable by the application | Deleted by the attacker |

## Interview questions

**Q: Authentication vs authorization?**
Authentication establishes who you are and happens once; authorization decides whether you may do a
specific thing to a specific resource and must be evaluated on every operation. `401` means
unauthenticated; `403` means authenticated but not permitted.

**Q: A system authenticates perfectly. Is it secure?**
No. Without per-resource authorization it has IDOR — every authenticated user can access every
record by changing an identifier. Authentication says who is asking, never whether they may.

**Q: What counts as multi-factor?**
Factors from different categories — know, have, are. A password plus a security question is one
factor twice.

**Q: Why is WebAuthn categorically stronger than TOTP?**
It is phishing-resistant by construction: the signature is bound to the origin and the private key
never leaves the device, so a fake site cannot obtain a usable credential. TOTP codes can be relayed
by a convincing phishing page.

**Q: Should you lock accounts after failed logins?**
It is a trade-off — lockout stops brute force but lets an attacker deny service to any account.
Prefer exponential throttling with jitter, per-IP and per-account limits, and breached-password
checks.

**Q: How do you prevent user enumeration on login?**
Identical responses and comparable timing for unknown user and wrong password — hash a dummy value
when the user does not exist — and generic messages. The same applies to registration and password
reset.

**Q: Where should authorization checks live?**
At the resource level, not just the endpoint — and structurally, by scoping every query to the
caller so an unscoped query does not exist. For multi-tenancy, push it into database row-level
security as defence in depth.

**Q: What should you audit?**
Authentication outcomes, all *denied* authorization attempts, account and privilege changes, and
sensitive data access — with who, what, when, where and outcome, append-only and stored separately.
Denials are the best intrusion signal you have.

## Mini task

1. Build a deliberately IDOR-vulnerable endpoint behind working authentication. Access another user's
   record with a valid token. Then fix it two ways — a check after the fetch, and a scoped repository
   method — and argue which is structurally safer.
2. Implement login with a dummy-hash path for unknown users. Measure response times for
   unknown-user, wrong-password and correct-password, and confirm they are comparable.
3. Implement exponential throttling with jitter instead of hard lockout. Demonstrate that an
   attacker cannot lock a victim out.
4. Add a permission model with RBAC plus an ownership check. Write a test proving that a `USER` role
   cannot read another user's resource even though the endpoint permits `USER`.
5. Implement audit logging for authentication and every denial. Then simulate an IDOR probe — fifty
   ids in a minute — and write the alert rule that would catch it.
6. Add row-level security to a multi-tenant table in PostgreSQL and confirm a forgotten `WHERE`
   clause still cannot cross tenants.
7. Register a WebAuthn credential with a browser API demo and observe that the assertion is bound to
   the origin.
8. Draw the five-layer authorization diagram for a system you know, and mark which layers actually
   exist today.

## 🎙️ Articulation drill

Two minutes: **"Explain the difference between authentication and authorization, with an example of
getting it wrong."**

Define both in one sentence each, then give the IDOR example — a system that authenticates perfectly
and lets every user read every record — because a concrete failure proves you understand the
distinction rather than reciting it. Close with the structural fix: scope queries by the caller so
the insecure version cannot be written.
