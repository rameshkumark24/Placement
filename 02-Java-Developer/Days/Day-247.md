# Part 2 — The five proofs

You have passed when you can **do** these, not describe them.

- [ ] **⭐⭐ One real screen, four states.** Loading skeleton, error branched by status with a retry,
      **empty split into never-had-any and filtered-to-zero**, and success. Against **your own API**.
- [ ] **⭐⭐ The index-key corruption, demonstrated.** Tick a row, delete another, watch the tick move.
      Then fix it. Reproducible on demand.
- [ ] **⭐ A generated client.** Rename a DTO field; the frontend build fails.
- [ ] **⭐⭐ The keyboard pass.** Tab the whole app with no mouse: everything reachable, focus always
      visible, modal traps and returns focus, first error focused on failed submit.
- [ ] **⭐⭐ A CSP that blocks your own XSS.** Inject a script through your own API, confirm it runs,
      add the CSP via Spring Security, confirm the bug still exists and the exploit no longer works.

⭐     ⭐⭐ WITH THE REASON YOU CHOSE THAT ONE.

# Part 4 — ⭐⭐ What this stage changed on the server

The real output of Stage 6 is not the UI. It is these, and they belong in your project defence.

| ⭐ Finding | Day |
|---|---|
| **An endpoint that needed four round trips to render one screen** | 214 |
| **A `@RestControllerAdvice` returning `ProblemDetail`** with per-field errors — so a 400 can be attached to an input | 217, 229 |
| **DTOs replacing entity returns**, discovered by reading your own payloads in DevTools | 236 |
| **Authorization expressed as `permissions` per resource**, computed by the bean `@PreAuthorize` calls | 236 |
| **`operationId` and declared error responses**, so the contract generates a usable client | 246 |
| **An idempotency key + unique constraint**, because a double-click made two orders | 229 |
| **Money sent as minor units or a string**, because `BigDecimal` does not survive a JS number | 246 |

> ⭐⭐ **Every one of those is a *backend* improvement discovered by writing a client.** That is the
> sentence that makes Stage 6 worth 34 days to an interviewer, and it is why this stage sits inside the
> backend track rather than beside it.

## 🎙️ Articulation drill

⭐⭐ **Three minutes: "tell me about the frontend work."**

Open with the reason, not the stack. **I built the client for my own API, and the point was never to
become a frontend engineer — it was that an API whose UI I've never written is an API I've only half
designed.**

Give the evidence as findings. **The first screen needed four round trips to render one view. Every
endpoint was individually correct and the API was wrong, and I couldn't have seen it from the server
side. My validation errors weren't field-addressable, so I added a `@RestControllerAdvice` returning
`ProblemDetail` with a field-and-message list. I opened DevTools on my own app and found endpoints
returning entities rather than DTOs — which is where "never return an entity from a controller" stopped
being pedantry and became something I could see. And a double-click on Save made two orders, so the
create endpoint took an idempotency key with a unique constraint behind it.**

Show the systems thinking. **A few things generalised. The client is a suggestion — hidden buttons and
client validation are UX, and `@PreAuthorize` is the only boundary, so the server now sends a
permissions object computed by the same bean that enforces the rule. Two versions are always live
because of open tabs — unlike a jar, where the whole program is replaced at once — so a frontend deploy
is a rollout and every API change is additive or a migration. And my p99 of forty milliseconds was
about one percent of what the user waited; Micrometer was honest about my layer and silent about every
other one.**

Close with scope, deliberately. **I'm not a frontend specialist. I can build a competent, accessible,
secure UI for an API I wrote and defend every decision in it, and I test with the keyboard rather than
claiming a compliance level I haven't audited. What the stage actually produced was seven changes to my
backend — which is why I'd do it again.**
