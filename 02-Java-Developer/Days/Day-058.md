**L-058** · Method references, `Optional` used correctly (not as a field)

# Part 1 — Method references

## The four forms

**A method reference is a lambda whose body is a single method call.**

| Form | Syntax | Equivalent lambda |
|---|---|---|
| **Static** | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| **Bound instance** | `System.out::println` | `x -> System.out.println(x)` |
| **Unbound instance** | `String::length` | `s -> s.length()` |
| **Constructor** | `ArrayList::new` | `() -> new ArrayList<>()` |

**The unbound form is the one that confuses people:**

```java
String::length         // the RECEIVER becomes the first parameter
// s -> s.length()

String::compareTo      // receiver + one argument
// (a, b) -> a.compareTo(b)
```

**Bound vs unbound, side by side:**

```java
String prefix = "Hello";
Supplier<Integer> bound = prefix::length;        // the receiver is FIXED — always "Hello"
Function<String, Integer> unbound = String::length;  // the receiver is the ARGUMENT
```

**Bound captures a specific object; unbound leaves the receiver to be supplied.** That's the whole
distinction, and it's a common interview question.

## Constructor references

```java
Supplier<List<String>> newList = ArrayList::new;
Function<Integer, List<String>> sized = ArrayList::new;      // the (int) constructor
Function<String, User> ctor = User::new;
IntFunction<String[]> arrayCtor = String[]::new;             // array constructor
```

**The array form matters:**

```java
String[] arr = stream.toArray(String[]::new);       // ← without this you get Object[]
```

**Overload resolution picks the constructor** based on the target functional interface's shape.

## When to use them

**Use a method reference when the lambda is *only* a call:**

```java
list.forEach(System.out::println);                  // ✅ clearer
list.forEach(x -> System.out.println(x));           // noise

names.stream().map(String::toUpperCase)             // ✅
names.stream().map(s -> s.toUpperCase())            // noise
```

**Keep the lambda when there's anything else:**

```java
.map(s -> s.trim().toUpperCase())                   // ✅ two calls — a lambda is correct
.map(s -> "prefix-" + s)                            // ✅ not a plain call
.filter(s -> s != null && !s.isEmpty())             // ✅
```

**The test: can you delete `x ->` and the parentheses and have it still mean the same thing?** If not,
keep the lambda.

# Part 2 — `Optional`

## What it's for

**`Optional<T>` makes "this may be absent" part of the type**, so the compiler forces you to consider
it — rather than a `null` that fails at runtime.

```java
// Before
User findUser(String id) { return null; }        // does the caller know?
findUser("x").getName();                          // 💥 NPE

// After
Optional<User> findUser(String id) { return Optional.empty(); }
findUser("x").map(User::getName).orElse("unknown");   // ✅ absence is unavoidable
```

## Creating

```java
Optional.of(value)              // throws NPE if value is null — asserts non-null
Optional.ofNullable(value)      // empty if null — the usual choice
Optional.empty()
```

**`of` versus `ofNullable` is a deliberate choice:** use `of` when null would be a bug you want to
surface immediately.

## Using it well

```java
opt.map(User::getName)                          // transform if present
   .filter(n -> !n.isBlank())
   .orElse("unknown");                           // default

opt.orElseGet(() -> expensiveDefault());         // LAZY default
opt.orElseThrow(() -> new NotFoundException(id));
opt.ifPresent(u -> log(u));
opt.ifPresentOrElse(u -> log(u), () -> logMissing());   // Java 9
opt.flatMap(this::findManager);                  // when the mapper returns an Optional
opt.or(() -> findInCache(id));                   // Java 9 — fallback Optional
opt.stream();                                    // Java 9 — 0 or 1 element
```

### `orElse` vs `orElseGet` — the trap

```java
opt.orElse(expensiveDefault());        // 💀 ALWAYS evaluates, even when present
opt.orElseGet(() -> expensiveDefault());  // ✅ only evaluates when empty
```

**`orElse` takes a value, so the argument is evaluated before the call.** If it's a database lookup or
an allocation, you pay for it every time — including when the `Optional` is present and the value is
discarded.

**Use `orElse` for constants, `orElseGet` for anything computed.** This is a genuinely common
performance bug.

## Where `Optional` does NOT belong

**This is the important half of the day**, and the part interviews probe.

### ❌ Not as a field

```java
class User {
    private Optional<String> middleName;      // 💀
}
```

- **`Optional` is not `Serializable`** — breaks serialization outright
- Adds an allocation per instance
- The field itself can still be null — you now have *three* states: null, empty, present
- Frameworks (JPA, Jackson) handle it inconsistently

```java
class User {
    private String middleName;                            // nullable field
    public Optional<String> getMiddleName() {              // ✅ Optional at the BOUNDARY
        return Optional.ofNullable(middleName);
    }
}
```

### ❌ Not as a method parameter

```java
void process(Optional<String> name) { }       // 💀

process(Optional.of("x"));
process(Optional.empty());
process(null);                                 // 💀 still possible! Three states again.
```

**Use an overload instead:**

```java
void process(String name) { }
void process() { }
```

### ❌ Not in a collection

```java
List<Optional<String>> list;         // 💀 a collection already expresses absence — omit the element
Map<String, Optional<User>> map;     // 💀 an absent key IS the absence
```

### ❌ Not for a collection return

```java
Optional<List<User>> findUsers();    // 💀 two ways to say "nothing"
List<User> findUsers();               // ✅ return an EMPTY list
```

**An empty collection already means "none".** Wrapping it in `Optional` gives the caller two cases to
handle for one concept.

### ✅ Where it belongs

**As a return type, when absence is a normal, expected outcome:**

```java
Optional<User> findById(String id);
Optional<Config> lookup(String key);
```

**That's it.** Brian Goetz, who led the JDK team that added it, has said it was designed specifically
as a **library method return type** for "no result", and that using it more broadly is a mistake.

**Being able to say where `Optional` is wrong is a stronger answer than listing its methods.**

## Optional anti-patterns

```java
// 💀 Worse than a null check — you've added an allocation and a call
if (opt.isPresent()) { use(opt.get()); }

// ✅
opt.ifPresent(this::use);
opt.map(this::transform).orElse(fallback);

// 💀 defeats the entire purpose
opt.get()                                    // throws NoSuchElementException if empty

// 💀 never do this
return opt.isPresent() ? opt.get() : null;
```

**`isPresent()` + `get()` is the code `Optional` exists to replace.** If you write it, you've gained
nothing and paid an allocation.

**`get()` was renamed `orElseThrow()` in Java 10** precisely because the short name encouraged
careless use.

## Type this yourself

```java
import java.util.*;
import java.util.function.*;
import java.util.stream.*;

public class OptionalDemo {

    record User(String name, String email, User manager) { }

    static final Map<String, User> DB = Map.of(
            "1", new User("Ada", "ada@x.com", null),
            "2", new User("Alan", null, new User("Ada", "ada@x.com", null)));

    static Optional<User> findById(String id) { return Optional.ofNullable(DB.get(id)); }

    static String expensiveDefault() {
        System.out.println("      [expensiveDefault() EVALUATED]");
        return "computed-default";
    }

    public static void main(String[] args) {

        // ---- method references ----
        System.out.println("--- method reference forms ---");
        Function<String, Integer> parse = Integer::parseInt;          // static
        System.out.println("   static:   " + parse.apply("42"));

        String prefix = "Hello";
        Supplier<Integer> bound = prefix::length;                     // bound instance
        System.out.println("   bound:    " + bound.get() + "   (receiver FIXED as \"Hello\")");

        Function<String, Integer> unbound = String::length;           // unbound instance
        System.out.println("   unbound:  " + unbound.apply("world") + "   (receiver is the ARG)");

        Supplier<List<String>> ctor = ArrayList::new;                 // constructor
        System.out.println("   ctor:     " + ctor.get());

        String[] arr = Stream.of("a", "b").toArray(String[]::new);    // array constructor
        System.out.println("   array:    " + Arrays.toString(arr) + " of type "
                + arr.getClass().getSimpleName());

        // ---- Optional basics ----
        System.out.println("\n--- Optional ---");
        System.out.println("   present: " + findById("1").map(User::name).orElse("unknown"));
        System.out.println("   absent:  " + findById("99").map(User::name).orElse("unknown"));

        // ---- chaining ----
        System.out.println("\n--- chaining ---");
        String email = findById("2")
                .map(User::email)
                .filter(e -> !e.isBlank())
                .orElse("no-email");
        System.out.println("   user 2 email: " + email + "   ← null email handled, no NPE");

        // ---- flatMap when the mapper returns an Optional ----
        System.out.println("\n--- flatMap ---");
        Optional<String> managerName = findById("2")
                .map(User::manager)                       // User (may be null)
                .map(User::name);
        System.out.println("   manager of 2: " + managerName.orElse("none"));

        // ---- orElse vs orElseGet ----
        System.out.println("\n--- orElse vs orElseGet (value IS present) ---");
        Optional<String> present = Optional.of("actual");
        System.out.println("   orElse:");
        System.out.println("      result = " + present.orElse(expensiveDefault()));
        System.out.println("   orElseGet:");
        System.out.println("      result = " + present.orElseGet(OptionalDemo::expensiveDefault));
        System.out.println("   ↑ orElse evaluated the default it then THREW AWAY");

        // ---- ifPresentOrElse and or ----
        System.out.println("\n--- Java 9 additions ---");
        findById("1").ifPresentOrElse(
                u -> System.out.println("   found: " + u.name()),
                () -> System.out.println("   not found"));
        System.out.println("   or(): " + findById("99")
                .or(() -> Optional.of(new User("fallback", null, null)))
                .map(User::name).orElse("?"));

        // ---- Optional.stream() ----
        System.out.println("\n--- Optional.stream() ---");
        List<String> names = Stream.of("1", "99", "2")
                .map(OptionalDemo::findById)
                .flatMap(Optional::stream)                 // drops the empties
                .map(User::name)
                .toList();
        System.out.println("   resolved names: " + names);

        // ---- the anti-pattern ----
        System.out.println("\n--- anti-pattern ---");
        Optional<User> opt = findById("1");
        if (opt.isPresent()) System.out.println("   isPresent+get: " + opt.get().name()
                + "   ← this is what Optional exists to REPLACE");
        opt.ifPresent(u -> System.out.println("   ifPresent:     " + u.name() + "   ← correct"));
    }
}
```

**The `orElse` demonstration is the one to internalise** — you'll see `[expensiveDefault()
EVALUATED]` printed even though the `Optional` was present and the value was discarded.

## Common mistakes

| Mistake | Correction |
|---|---|
| `Optional` as a field | Not serializable, adds allocation, and the field can still be null. |
| `Optional` as a parameter | Callers can still pass null. Use overloads. |
| `Optional<List<T>>` | Return an empty list — it already means "none". |
| `isPresent()` + `get()` | The pattern `Optional` replaces. Use `map`/`ifPresent`/`orElse`. |
| `orElse(expensive())` | Always evaluated. Use `orElseGet`. |
| `opt.get()` | Throws if empty. Use `orElseThrow` with a meaningful exception. |
| A lambda where a method reference reads better | `x -> f(x)` is just `f`. |
| A method reference where the lambda does more | Only use one when the body is a single call. |

## Interview questions

**Q: What's the difference between a bound and an unbound method reference?**
> A bound reference captures a specific receiver — `prefix::length` always calls `length` on that one
> string, so it's a `Supplier<Integer>`. An unbound reference names the type — `String::length` — so
> the receiver becomes the first parameter, making it a `Function<String,Integer>`.

**Q: Where should `Optional` be used, and where shouldn't it?**
> As a return type where absence is a normal outcome — a lookup that may find nothing. Not as a field,
> because it isn't serializable, adds an allocation, and the field itself can still be null giving
> three states. Not as a parameter, since callers can still pass null and overloads express it better.
> Not inside collections or wrapping a collection return, because an empty collection already means
> "none". Brian Goetz has said it was designed specifically as a library return type.

**Q: What's wrong with `opt.isPresent()` followed by `opt.get()`?**
> It's exactly the null check `Optional` was introduced to replace, with an extra allocation and no
> benefit. The point is to force handling through `map`, `filter`, `ifPresent` or `orElse`, so absence
> can't be forgotten.

**Q: `orElse` or `orElseGet`?**
> `orElse` takes a value, so its argument is evaluated before the call regardless of whether the
> `Optional` is present — meaning an expensive default is computed and then discarded. `orElseGet`
> takes a supplier and only invokes it when empty. Use `orElse` for constants and `orElseGet` for
> anything computed.

**Q: When is `flatMap` needed instead of `map`?**
> When the mapping function itself returns an `Optional`. Using `map` would give
> `Optional<Optional<T>>`; `flatMap` collapses it to a single level.
