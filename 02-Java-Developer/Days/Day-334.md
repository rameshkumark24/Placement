# Day 334

**L-334** · Kafka fundamentals — the log, the partition, and where ordering actually lives

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Kafka is one idea: an append-only log that is partitioned, replicated, retained, and read by
> position rather than consumed by deletion.**
>
> Every property people find surprising — ordering only within a partition, consumers capped by
> partition count, free replay — **falls directly out of that one sentence.**

---

# Part 1 — ⭐⭐ The log, and what follows from it

```
⭐ Topic: orders
⭐ ┌─ partition 0 ─────────────────────────────────────►  offsets 0,1,2,3,...
⭐ ├─ partition 1 ─────────────────────────────────────►
⭐ └─ partition 2 ─────────────────────────────────────►
⭐
⭐ ⭐ Writes APPEND.  ⭐ Reads are by OFFSET.  ⭐ Reading does not remove anything.
```

| ⭐ Property | ⭐ Consequence |
|---|---|
| ⭐ **Append-only** | ⭐ sequential disk I/O — **which is why one broker handles enormous throughput** |
| ⭐ **Read by offset, not consumed** | ⭐⭐ **replay is free; N independent consumers cost nothing extra** |
| ⭐ **Retained by time or size** | ⭐ **a bug can be fixed by reprocessing history** — the property a queue lacks |
| ⭐ **Partitioned** | ⭐ the unit of parallelism **and** of ordering |
| Replicated per partition | durability and failover (Day 328) |

> **⭐ The consumer offset lives with the consumer, not the broker.** That is what makes replay and
> multiple independent consumer groups possible — **and it is the structural difference from SQS or
> RabbitMQ, where acknowledgement deletes the message.**

## ⭐⭐ Ordering — the single most important fact

> **⭐ Kafka guarantees ordering WITHIN a partition. Across partitions there is no ordering at all.**

```
⭐ producer.send(new ProducerRecord<>("orders", orderId, event));
⭐                                               ▲
⭐                        ⭐ THE KEY. partition = hash(key) % partitionCount
```

| ⭐ Consequence | |
|---|---|
| ⭐ **Same key → same partition → ordered** | ⭐ **key by the entity whose ordering matters** — order id, account id, user id |
| ⭐ **No key → round robin** | ⭐ balanced, and **no ordering whatsoever** |
| ⭐⭐ **One partition = global order, and no parallelism** | ⭐⭐ **the trade is total: ordering scope vs throughput** |
| ⭐ Adding partitions changes the mapping | ⭐ **`hash(key) % N` — Day 326's problem. Existing keys move; ordering breaks across the change** |

⚠️ **That last row is a real operational trap.** Adding partitions to an existing topic **rehashes
keys**, so an entity's future events land elsewhere while its past ones stay — **ordering per entity
is broken across the boundary.** Over-provision partitions up front (Day 329's pre-splitting idea
again); **you can add later, but not cleanly.**

> **⭐ The design sentence: "I don't need global ordering — I need ordering per account, so I key by
> account id and get it for free while still parallelising across accounts."** That is almost always
> the right answer, and stating it pre-empts the "how do you handle ordering?" follow-up.

# Part 2 — ⭐ Consumer groups

```
⭐ Topic with 4 partitions

⭐ Group "billing"    : consumer A → p0,p1   consumer B → p2,p3
⭐ Group "analytics"  : consumer C → p0,p1,p2,p3      ⭐ independent offsets, same data
```

| ⭐ Rule | ⭐ Consequence |
|---|---|
| ⭐⭐ **One partition → at most one consumer per group** | ⭐⭐ **consumers > partitions means idle consumers** |
| ⭐ **Partition count caps consumer parallelism** | ⭐ **it is your scaling limit — choose it deliberately** |
| Groups are independent | each has its own offsets; adding a group costs the producer nothing |
| ⭐ Offsets committed per group per partition | ⭐ where at-least-once comes from (Day 335) |

⚠️ **Rebalancing is the operational pain.** When a consumer joins, leaves or times out, partitions are
reassigned — **and with the classic protocol every consumer stops during the reassignment.** A slow
consumer that exceeds `max.poll.interval.ms` is presumed dead, triggering a rebalance, which slows
everyone, which triggers another. **The fixes: cooperative-sticky assignment, a `max.poll.records`
small enough that processing fits the interval, and long-running work moved off the poll thread.**

# Part 3 — ⭐ Durability, and the configuration trap

| Setting | ⭐ Meaning |
|---|---|
| `acks=0` | ⭐ fire and forget — **data loss is normal** |
| `acks=1` | ⭐ the leader has it — **lost if the leader dies before replicating** |
| ⭐ **`acks=all`** | ⭐ **all in-sync replicas have it** |
| ⭐⭐ **`min.insync.replicas`** | ⭐⭐ **how many "all" actually means** |

```
⭐⭐ THE TRAP:  acks=all  +  min.insync.replicas=1
⭐             "all in-sync replicas" when only the leader is in sync
⭐             ⇒ ⭐⭐ acks=all silently degrades to acks=1. You believe you are durable. You are not.

⭐ CORRECT:    replication.factor=3, min.insync.replicas=2, acks=all
⭐             ⇒ survives one broker loss; refuses writes if two are gone (⭐ CP behaviour — Day 330)
```

> **⭐ Saying "replication factor 3, min in-sync 2, acks all" as a unit is the mark of someone who has
> configured this in production** — and the corollary is worth adding: **it means writes fail when
> two brokers are down, which is the correct trade for a durable log** (Day 330's CP choice, made
> explicit).

| Also | |
|---|---|
| ⭐ `enable.idempotence=true` | ⭐ **de-duplicates producer retries — on by default in recent versions; keep it** |
| `max.in.flight.requests` > 1 without idempotence | ⭐ **a retry can reorder within a partition** |
| ⭐ Compression (`lz4`, `zstd`) | ⭐ batches compress well — often the cheapest throughput win |
| ⭐ `linger.ms` | ⭐ wait a few ms to batch — **a large throughput gain for a tiny latency cost** |

# Part 4 — ⭐ Retention, compaction, and when not to use Kafka

## ⭐ Compacted topics — the feature that makes Kafka a database-ish thing

```
⭐ Normal retention:   keep everything for 7 days, then delete.
⭐ COMPACTION:         ⭐ keep the LATEST value per key, forever.

⭐ user:1 → {name:"A"}   user:1 → {name:"B"}   user:2 → {...}
⭐ after compaction:  ⭐ user:1 → {name:"B"},  user:2 → {...}
```

| ⭐ Use | |
|---|---|
| ⭐ **A changelog you can replay into a materialised view** | ⭐ a new service bootstraps state by reading from offset 0 |
| ⭐ CDC streams (Day 337's index sync) | the table's current state, as a topic |
| ⭐ **Deletes are tombstones** — a null value | ⭐ and they are removed only after `delete.retention.ms` |

## ⭐ When Kafka is the wrong tool

| ⭐ Need | ⭐ Use instead |
|---|---|
| ⭐ **Request/reply** | ⭐ HTTP or gRPC — a log is not an RPC mechanism |
| ⭐ **Per-message TTL or delayed delivery** | ⭐ RabbitMQ, SQS |
| ⭐ **Priority queues** | ⭐ RabbitMQ — **Kafka has no priority; a partition is FIFO** |
| ⭐ Complex routing by attribute | RabbitMQ exchanges |
| ⭐ **Low volume, no replay needed** | ⭐ SQS — **zero operations beats a cluster you must run** |
| Very many topics (100k+) | ⭐ per-partition file handles do not scale that way |

> **⭐ The honest summary: choose Kafka for retention, replay and ordered high-throughput streams.
> Choose a queue for work distribution with routing and TTLs.** Running a Kafka cluster for 200
> messages a second with no replay requirement is a real cost with no return — **and saying that
> reads as judgement, not ignorance.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Assuming global ordering | ⭐⭐ **it is per-partition only** |
| ⭐ No key when ordering matters | ⭐ round robin destroys per-entity order |
| ⭐ One partition for global ordering | ⭐ no parallelism at all — usually the wrong trade |
| ⭐ Adding partitions to a keyed topic | ⭐ **rehashes keys; ordering breaks across the change** |
| ⭐ Too few partitions at creation | ⭐ your consumer parallelism is capped |
| More consumers than partitions | idle consumers, no extra throughput |
| ⭐⭐ `acks=all` with `min.insync.replicas=1` | ⭐⭐ **silently equivalent to acks=1** |
| ⭐ Long processing on the poll thread | ⭐ rebalance storms |
| ⭐ Disabling producer idempotence | retries can duplicate and reorder |
| ⭐ Treating Kafka as a database | ⭐ no queries — compaction gives a changelog, not an index |
| Kafka for request/reply or priorities | wrong tool; significant cost |
| Ignoring consumer lag | Day 333 |

## Interview questions

**Q: What ordering guarantee does Kafka give?**
Ordering within a partition, and nothing across partitions. The key determines the partition, so
ordering is really "ordering per key". In practice I never need global ordering — I need ordering per
account or per order, so I key by that entity and get ordering for free while still parallelising
across entities. One partition would give global order at the cost of all parallelism.

**Q: How many consumers can you run?**
At most one per partition within a consumer group, so partition count is the ceiling on consumer
parallelism. Extra consumers sit idle. That makes partition count a capacity decision at creation
time, and it is awkward to change later — adding partitions rehashes keys, so an entity's new events
go to a different partition than its old ones and per-key ordering breaks across the boundary.

**Q: How do you configure Kafka for durability?**
Replication factor three, `min.insync.replicas` two, `acks=all`, and producer idempotence on. The
trap is `acks=all` with `min.insync.replicas` at one, which means "all" can mean just the leader, so
you silently have `acks=1` while believing you are durable. The correct configuration also means
writes fail when two brokers are down, and that is the right trade for a durable log.

**Q: What is a compacted topic for?**
Keeping the latest value per key indefinitely, so the topic becomes a changelog of current state. A
new service can bootstrap by reading from offset zero and building a materialised view, and CDC
streams use it to represent a table's present contents. Deletes are tombstones — a null value — which
are themselves retained for a window so every consumer sees them.

**Q: When would you not use Kafka?**
Request/reply, per-message TTL, delayed delivery, priorities, or routing by attribute — a partition
is FIFO with no priorities, and Kafka is not an RPC mechanism. And at low volume with no replay
requirement I would take SQS, because zero operations beats a cluster I have to run, patch and
rebalance. The question that decides it is whether I need to replay history.

## 🎙️ Articulation drill

**Three minutes:** *"Events for a single order must be processed in order, but you need to handle a
hundred thousand orders a second. How?"*

**⭐ The complete answer in one move: key by order id.** Ordering is per partition, the key chooses
the partition, so every event for one order is ordered while different orders parallelise across
partitions and consumers.

**⭐ Then volunteer the two consequences** — partition count caps consumer parallelism so it is
chosen up front and over-provisioned, and **a failed message cannot simply be skipped without
breaking the ordering you just promised**, which is exactly where Day 335 begins.
