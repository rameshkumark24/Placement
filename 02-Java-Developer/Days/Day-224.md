**Time:** 3 hrs · **Mode:** NEW

> should have been given `children` instead — configuration scales linearly with the callers you

# Part 1 — Props are a method signature

```tsx
type Props = {
  user: User;
  onSelect: (id: string) => void;     // ⭐ a handler is just a prop
  variant?: "primary" | "ghost";      // ⭐⭐ union, not string
  children?: React.ReactNode;         // ⭐ anything renderable
};

function UserCard({ user, onSelect, variant = "primary", children }: Props) {
  return (
    <article onClick={() => onSelect(user.id)} data-variant={variant}>
      <h3>{user.name}</h3>
      {children}                       {/* ⭐⭐ the extension point */}
    </article>
  );
}
```

| ⭐ Rule | Why |
|---|---|
| **Props are read-only** | ⭐⭐ Mutating a prop is the impurity of Day 223. Treat every prop as `final`. |
| **Name handlers `onX`, implementations `handleX`** | ⭐ An ecosystem-wide convention |
| **Prefer unions over booleans** | ⭐⭐ `variant="ghost"` beats `isGhost` — Part 3 |
| **Destructure in the signature** | ⭐ It *is* the documentation, and defaults live there |

> ⭐ **A component is a method whose return value happens to be a UI description.** Every design
> instinct from Stage 8 applies unchanged: small surface, one responsibility, no hidden coupling. ⭐⭐
> **There is no constructor, no field, and no lifecycle to hide state in** — which is a constraint that
> makes bad designs harder rather than easier.

# Part 2 — Composition

```jsx
// ❌ CONFIGURATION — the component must anticipate every caller
<Card title="X" showFooter footerText="Y" headerIcon={<I/>} bordered dense />

// ✅ COMPOSITION — the caller supplies the parts
<Card>
  <Card.Header icon={<I/>}>X</Card.Header>
  <Card.Body>…</Card.Body>
  <Card.Footer>Y</Card.Footer>
</Card>
```

| ⭐ Pattern | Use for |
|---|---|
| **`children`** | ⭐⭐ The default answer. If a prop's value is *JSX*, it probably wanted to be `children`. |
| **Slots** (named `ReactNode` props) | ⭐ Two or more holes: `<Layout sidebar={<Nav/>} main={<Page/>} />` |
| **Compound components** | ⭐ A family sharing implicit state — `Tabs`/`Tab` |
| **Render prop** | ⭐ Parent owns state, caller owns markup — ⭐ the template-method pattern, inverted |
| **⭐⭐ Custom hook** | **Share *logic*, not markup.** Usually the right answer when you were about to add a prop. |

```jsx
// ⭐⭐ the move that prevents most prop explosions:
//    lift the LOGIC into a hook, leave the MARKUP to the caller
function useSelection(items) {
  const [selected, setSelected] = useState(new Set());
  const toggle = (id) => setSelected(s => {
    const next = new Set(s);            // ⭐ new reference (Day 223)
    next.has(id) ? next.delete(id) : next.add(id);
    return next;
  });
  return { selected, toggle, clear: () => setSelected(new Set()) };
}
// ⇒ ⭐ any list is now selectable with NO new props on the list.
//   ⭐⭐ THIS IS COMPOSITION OVER INHERITANCE, WITHOUT THE CLASSES.
```

# Part 3 — ⭐⭐ The boolean explosion

```
⭐⭐ HOW EVERY SHARED COMPONENT DIES

⭐   <Button primary />
⭐   <Button primary large />
⭐   <Button primary large loading />
⭐   ... six months later:
⭐   <Button primary secondary danger large small loading disabled
⭐           iconOnly fullWidth rounded elevated compact />

⭐⭐ 12 BOOLEANS = 4,096 COMBINATIONS. You tested about six.
⭐   ⭐⭐ AND MOST ARE MUTUALLY EXCLUSIVE WITH NOTHING SAYING SO:
⭐     primary + secondary + danger — what renders? Whatever the
⭐     last if-branch happened to be. THE TYPE SYSTEM PERMITTED IT.

⭐ ✅ THE FIX — a union is a ⭐⭐ SEALED INTERFACE:
⭐   variant: "primary" | "secondary" | "danger"    ⭐ pick exactly one
⭐   size:    "sm" | "md" | "lg"
⭐   state:   "idle" | "loading" | "disabled"
⭐   ⇒ 3 props, 27 valid combinations, ⭐ ZERO CONTRADICTORY ONES,
⭐     and the compiler rejects the nonsense — exactly what a
⭐     sealed hierarchy plus exhaustive switch buys you in Java.
```

| ⭐ Smell | Fix |
|---|---|
| Two booleans that cannot both be true | ⭐⭐ One union |
| A prop only passed through to a child | ⭐ Pass the child instead |
| A prop named `render…` or `…Component` | ⭐ Probably wanted `children` |
| More than ~7 props | ⭐ Split it, or it is doing two jobs |
| A boolean that turns a *whole section* on | ⭐⭐ That section is a slot |

# Part 4 — Where to split

```
⭐⭐ SPLIT WHEN — real reasons only

⭐   ① ⭐ IT IS REUSED. The only unarguable reason.
⭐   ② ⭐⭐ IT HAS ITS OWN STATE the parent does not care about
⭐   ③ ⭐ IT IS A NAMED CONCEPT in the domain — <InvoiceRow> reads
⭐      better than 40 lines of nested divs
⭐   ④ ⭐ IT NEEDS ITS OWN TEST or loading boundary

⭐⭐ DO NOT SPLIT BECAUSE:
⭐   · "the file is long" — ⭐ A 200-LINE COMPONENT USED ONCE IS FINE.
⭐     ⭐⭐ THIS IS THE ONE JAVA HABITS GET WRONG: you are used to
⭐       one public class per file, so a long file feels illegal.
⭐       IT ISN'T. Eight one-use components in eight files is WORSE.
⭐   · "best practice"
⭐   · ⭐⭐ PREMATURE REUSE — abstracting the SECOND time is right;
⭐     the FIRST time invents the wrong seam.
```

> ⭐⭐ **The prop-drilling threshold.** Two levels is fine. Five levels of components that do not use
> it is a smell — but the fix is usually **composition** (pass the element down, not the data) rather
> than Context (Day 231). ⭐ Reaching for Context first is reaching for a static singleton because
> passing a parameter felt tedious.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you keep shared components from rotting?"**

Name the failure mode, since everyone recognises it. **Every shared component dies the same way: it
accumulates booleans. Primary, then large, then loading — six months later there are twelve, which is
four thousand combinations of which I've tested six. The real problem isn't the count, it's that most
are mutually exclusive and nothing says so. Primary plus danger is meaningless, and whatever renders is
whichever if-branch came last.**

Then the fix, in terms you already hold. **Replace booleans with unions — variant, size, state. Three
props, twenty-seven valid combinations, zero contradictory ones. A union is a sealed interface, and an
exhaustive switch over it is the same guarantee I'd get from pattern matching in Java: illegal states
become unrepresentable.**

Then the deeper move. **Configuration scales with the callers you anticipated; composition scales with
the ones you didn't. If a prop's value is JSX it wanted to be children. If a boolean turns a whole
section on, that section is a slot. And when I'm about to add a prop for behaviour rather than
appearance, the answer is usually a custom hook — composition over inheritance, without the classes.**

Close on the habit you had to unlearn. **I split when something is genuinely reused, has its own state,
or is a named domain concept — not because a file got long. Coming from Java, one public class per file
makes a two-hundred-line component feel illegal. It isn't, and eight single-use components across eight
files is harder to read, not easier.**
