# Part 1 — Conflicts

## What a conflict actually is

From Day 086's table: both sides changed the same region differently, relative to the merge base.
Git cannot choose, so it writes both into the file and stops.

```java
public int timeout() {
<<<<<<< HEAD                    ← "ours": the branch you are ON
    return 5;
||||||| merged common ancestor  ← the BASE (only with diff3 style)
    return 30;
=======
    return 10;
>>>>>>> feature/timeout         ← "theirs": the branch being merged in
}
```

**Turn on diff3 style permanently.** It is the single best conflict-resolution improvement available:

```bash
git config --global merge.conflictStyle zdiff3
```

Without the base you see two alternatives and must guess. With it you see what *both* sides changed
*from* — and in the example above the base tells you main reduced 30→5 and the feature reduced
30→10, so the answer is a discussion about which target is right, not a coin flip.

## Resolving

```bash
git status                        # "Unmerged paths" — the list
git diff                          # conflicted hunks only
git diff --ours / --theirs        # each side against the merge result

# resolve by editing, then:
git add <file>                    # ← staging IS how you mark it resolved
git commit                        # (message is pre-filled for a merge)

# or take a whole side:
git checkout --ours   file        # ⚠️ discards their change ENTIRELY for that file
git checkout --theirs file
git checkout --merge  file        # restore the conflict markers, start over

git merge --abort                 # ← always available before committing
git rebase --abort
```

`--ours`/`--theirs` are per-*file*, not per-hunk, and they discard the other side's changes to that
file completely. Use them only when one side's version is genuinely correct in full — for a
generated file such as a lockfile, for instance, where the right move is usually to take one side and
regenerate.

**The meaning of "ours" flips during a rebase.** In a merge, "ours" is your current branch. In a
rebase, Git is replaying *your* commits onto *their* base, so "ours" is the upstream branch and
"theirs" is your commit. This reversal causes real mistakes; when in doubt use diff3 style and read
the content rather than trusting the labels.

## Tools and prevention

```bash
git mergetool                            # configured GUI/3-way tool
git config --global merge.tool vimdiff   # or meld, kdiff3, vscode

git config --global rerere.enabled true  # REuse REcorded REsolution
```

**`rerere`** records how you resolved a conflict and replays it automatically the next time the same
conflict appears. During a long rebase where the same conflict recurs on commit after commit, it
turns a miserable afternoon into a few keystrokes. Enable it once and forget it.

Prevention beats resolution:

- **Merge `main` into your branch often** (or rebase onto it). Conflict pain grows superlinearly with
  divergence.
- **Short-lived branches.** A three-day branch rarely conflicts; a three-month branch always does.
- **Agree formatting** and commit a formatter config. Most "conflicts" in undisciplined repos are
  whitespace and import-order noise.
- Give generated files (lockfiles, `.pb.go`) a `.gitattributes` merge strategy so they are
  regenerated rather than merged.

After any non-trivial resolution: **build and run the tests.** A conflict resolution that compiles is
not the same as one that is correct — you can produce syntactically valid code that implements
neither side's intent, and no tool will tell you.

# Part 2 — The recovery toolkit

## The three commands people confuse

| Command | Operates on | Moves HEAD? | Destroys? |
|---|---|---|---|
| `git restore` | **files** | no | ⚠️ yes, working-tree changes |
| `git reset` | **the branch pointer** (and optionally index/tree) | yes | only with `--hard` |
| `git revert` | **history**, by adding a commit | no | never |

```bash
git reset --soft  HEAD~1     # move the branch; index and working tree untouched
                             #   → changes are STAGED, ready to recommit
git reset         HEAD~1     # (--mixed, default) reset index too
                             #   → changes are UNSTAGED
git reset --hard  HEAD~1     # ⚠️ reset working tree too — uncommitted work is GONE
```

The mental model straight from Day 084: **`reset` moves the branch pointer**; the three flags decide
how far the index and working tree follow it. The commits themselves are never deleted — they become
unreachable, and the reflog still knows them.

```bash
git revert <hash>            # a NEW commit that undoes <hash>
git revert -n <hash>         # stage the inversion without committing
git revert -m 1 <merge>      # revert a merge, keeping parent 1 (main) as mainline
```

> **`reset` for local history. `revert` for anything pushed.**

Reverting a merge needs `-m` because Git must know which parent is "the line you are staying on" —
`-m 1` is almost always the target branch. Note the subtlety worth knowing: after reverting a merge,
re-merging that branch later does *nothing*, because those commits are already ancestors. You must
revert the revert.

## `git reflog` — the safety net

```bash
git reflog                       # HEAD's movement history
git reflog show feature          # one branch's
git reset --hard HEAD@{3}        # go back to where you were 3 moves ago
git reflog --date=relative
```

```
a1b2c3d HEAD@{0}: rebase finished: returning to refs/heads/feature
9f8e7d6 HEAD@{1}: rebase: Add validator
3c2b1a0 HEAD@{2}: reset: moving to HEAD~3      ← the mistake
7e6d5c4 HEAD@{3}: commit: Add rate limiter     ← where you want to be
```

**The reflog records every movement of HEAD**, including ones that made commits unreachable. It is
local, it is not pushed, and entries expire after ~90 days (30 for unreachable objects).

Therefore:

> **You cannot lose a commit. You can only lose a *reference* to it — and the reflog is a reference.**

The recovery drill, which every developer should have done at least once deliberately:

```bash
git commit -m "important work"
git reset --hard HEAD~1          # "destroyed"
git reflog                       # find the hash
git reset --hard <hash>          # restored, byte for byte
```

For commits with no reflog entry at all (an abandoned detached HEAD from a previous session):

```bash
git fsck --lost-found            # dangling commits
git show <dangling-hash>
git branch rescued <dangling-hash>
```

**What the reflog cannot save:** changes never committed. `git restore <file>`, `git reset --hard`
with uncommitted edits, `git clean -fd`. There is no object, so there is nothing to find. That
asymmetry is the argument for committing early and often — you can always reshape commits (Day 086),
you cannot resurrect an unsaved edit.

## `git bisect` — binary search over history

The most under-used command in Git. "It worked in the release two weeks ago and it is broken now"
across 500 commits: bisect finds the culprit in about 9 steps.

```bash
git bisect start
git bisect bad                    # current commit is broken
git bisect good v1.4.0            # this tag was fine
# Git checks out the midpoint. Test it, then:
git bisect good     # or: git bisect bad
# repeat ~log2(n) times
git bisect reset                  # back to where you started
```

Automate it, which is the version worth knowing:

```bash
git bisect start HEAD v1.4.0
git bisect run ./test.sh          # exit 0 = good, 1–124 = bad, 125 = skip
```

`test.sh` can be anything — `mvn -q test -Dtest=TheFailingTest`, a curl against a locally started
server, a script that greps a log. Git will run it at each midpoint and hand you the first bad
commit with no further input. **A 500-commit range resolves in nine automated runs.**

This is also the concrete payoff for Day 085's rule that **every commit must build**: a commit that
does not compile makes bisect report the wrong culprit. Use `git bisect skip` for genuinely
untestable commits.

## `git clean` and other sharp edges

```bash
git clean -n           # DRY RUN — always do this first
git clean -fd          # remove untracked files and directories
git clean -fdx         # ⚠️ including ignored files — wipes target/, .env, node_modules
```

`git clean -fdx` deletes your untracked `.env`. There is no recovery. **Always `-n` first.**

```bash
git stash              # (Day 085) — the safe alternative when unsure
```

# Part 3 — D-04 · Functional dependencies

## The definition

> **X → Y** ("X functionally determines Y") means: **any two tuples that agree on X must agree on
> Y.**

It is a statement about *the business rules*, not about the data currently in the table. `email →
name` says one email address always belongs to one name — data showing otherwise is a violation, not
a counterexample to the rule.

```
student(sid, sname, cid, cname, instructor, grade)

sid           → sname
cid           → cname, instructor
sid, cid      → grade
```

**Every problem with this table is visible in those dependencies**, and that is the point of writing
them down:

- `cid → cname` means the course name is repeated on every enrollment row (**redundancy**).
- Updating a course name requires updating many rows, and missing one creates **inconsistency**.
- You cannot record a course with no students (**insertion anomaly**).
- Deleting the last enrollment loses the course (**deletion anomaly**).

Those three anomalies are the entire motivation for normalization (Day 091's D-05).

## Trivial, partial, transitive

- **Trivial:** Y ⊆ X. `{sid, cid} → sid`. Always true, tells you nothing.
- **Partial:** a non-key attribute depends on *part* of a composite key. `sid → sname` when the key
  is `{sid, cid}`. **This is what 2NF forbids.**
- **Transitive:** X → Y and Y → Z, so X → Z through a non-key attribute. `sid → dept → dept_head`.
  **This is what 3NF forbids.**

Naming which kind you are looking at is how you decide which normal form is violated.

## Armstrong's axioms

Three rules from which all others follow:

| Axiom | Rule |
|---|---|
| **Reflexivity** | If Y ⊆ X then X → Y |
| **Augmentation** | If X → Y then XZ → YZ |
| **Transitivity** | If X → Y and Y → Z then X → Z |

Derived, and more useful in practice:

- **Union:** X → Y and X → Z ⟹ X → YZ
- **Decomposition:** X → YZ ⟹ X → Y and X → Z
- **Pseudotransitivity:** X → Y and WY → Z ⟹ WX → Z

## Attribute closure — the algorithm you must be able to run

**X⁺** is every attribute determined by X.

```
X⁺ := X
repeat until no change:
    for each dependency A → B in F:
        if A ⊆ X⁺ then X⁺ := X⁺ ∪ B
```

Worked example:

```
R(A, B, C, D, E)
F = { A → B,  BC → D,  D → E,  A → C }

Compute A⁺:
  start          A⁺ = {A}
  A → B          A⁺ = {A, B}
  A → C          A⁺ = {A, B, C}
  BC → D  (BC ⊆ A⁺)   A⁺ = {A, B, C, D}
  D → E          A⁺ = {A, B, C, D, E}

A⁺ = {A,B,C,D,E} = R  →  A is a SUPERKEY.
A has no proper subset, so A is a CANDIDATE KEY.
```

Closure answers the two questions you will actually be asked:

1. **Is X a key?** Compute X⁺; if it equals R, X is a superkey. Check minimality for candidate key.
2. **Does F imply X → Y?** Compute X⁺ and check whether Y ⊆ X⁺. **You never need to derive it by
   hand** — this is what closure is for.

Finding all candidate keys, practically: attributes appearing **only on the left** of any dependency
must be in every key; attributes appearing **only on the right** are in none. Start from the
must-haves and add the ambiguous ones minimally.

## Minimal cover

A **minimal (canonical) cover** F_c is an equivalent set of dependencies that is as simple as
possible:

1. Every right-hand side is a **single attribute**.
2. No dependency is **redundant** (removing it does not change the closure).
3. No left-hand side has an **extraneous attribute**.

```
F = { A → BC,  B → C,  A → B,  AB → C }

1. Decompose RHS:      A → B,  A → C,  B → C,  A → B,  AB → C
2. Remove duplicates:  A → B,  A → C,  B → C,  AB → C
3. Extraneous LHS: in AB → C, A⁺ (without it) already gives C  →  becomes A → C, a duplicate. Drop.
                       A → B,  A → C,  B → C
4. Redundant: is A → C implied by the rest? A⁺ using {A→B, B→C} = {A,B,C} ⊇ C.  YES → drop it.

F_c = { A → B,  B → C }
```

Minimal cover is the input to the 3NF synthesis algorithm (Day 091), which is why it is worth being
able to compute rather than merely define.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Resolving conflicts without diff3 | Guessing between two options with no context |
| `--ours`/`--theirs` per file | Silently discards the other side's whole file |
| Assuming "ours" means the same in a rebase | It is reversed — you take the wrong side |
| Not building after resolving | Compiles, but implements neither intent |
| `reset --hard` with uncommitted work | Unrecoverable |
| `git clean -fdx` without `-n` | Deletes `.env` and every ignored file |
| `reset` on a pushed branch | Forces a rewrite others must deal with — use `revert` |
| Forgetting to revert-the-revert | Re-merging a reverted branch appears to do nothing |
| Not knowing the reflog exists | Unnecessary panic, and real work thrown away |
| Not using bisect | Hours of manual searching for a 9-step answer |
| Treating an FD as a fact about current data | It is a business rule |
| Deriving implications by hand | Compute the closure instead |

## Interview questions

**Q: `reset` vs `revert` vs `restore`?**
`restore` changes files. `reset` moves the branch pointer, with `--soft`/`--mixed`/`--hard`
controlling how far the index and working tree follow. `revert` adds a new commit that inverts an
old one. Reset for local history, revert for anything pushed.

**Q: You deleted a branch with unmerged commits. Recover it.**
`git reflog` (or `git fsck --lost-found`) to find the tip hash, then `git branch <name> <hash>`. The
commits were never deleted — only the reference was.

**Q: What can the reflog *not* recover?**
Anything never committed: `restore`d files, `reset --hard` over uncommitted edits, `git clean`. No
object was ever created.

**Q: How do you find which commit introduced a bug?**
`git bisect start`, mark a known-good tag and the bad HEAD, then `git bisect run ./test.sh` — binary
search, about log₂(n) steps, fully automated. It requires that every commit builds.

**Q: What is a functional dependency, and what is closure for?**
X → Y means tuples agreeing on X must agree on Y — a business rule. Attribute closure X⁺ computes
everything X determines, which tells you whether X is a key and whether a given dependency is
implied.

**Q: What are the anomalies that motivate normalization?**
Redundancy, update inconsistency, insertion anomaly (cannot record a course with no students) and
deletion anomaly (deleting the last enrollment loses the course).

## 🎙️ Articulation drill

Two minutes: **"You just realised you force-pushed over a colleague's commits. What now?"**

Do not panic and do not touch anything else. Their commits are in *their* reflog and probably in your
`origin/…` reflog too; find the previous remote tip, restore the branch to a commit containing both
lines of work, push with `--force-with-lease`, and tell them before they pull. Then adopt
`--force-with-lease` permanently. Calm, mechanical recovery is the answer being assessed.
