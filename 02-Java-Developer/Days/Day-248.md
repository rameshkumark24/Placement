# Part 1 — ⭐ What makes a project defensible

**⭐ The interviewer is not evaluating your project. They are evaluating whether you made decisions
and can explain them.** A CRUD todo app with three genuinely hard, well-reasoned decisions beats a
sprawling clone with none.

| ⭐ Defensible | ❌ Not defensible |
|---|---|
| ⭐ **Solves a problem you can describe in one sentence** | "an e-commerce clone" |
| ⭐ **Has at least three decisions with real trade-offs** | every choice was the tutorial's default |
| ⭐ **Has a failure mode you designed around** | nothing could go wrong because nothing is concurrent |
| ⭐ **Is deployed and observable** | runs on your laptop |
| ⭐ **Has tests that would catch a regression** | a coverage number with no assertions |
| Small enough to finish | 40% built, abandoned |

**⭐ The single best signal you can give: "I built X, then found it broke under Y, so I changed it to
Z — and here is the measurement."** That sentence requires a real system, real load, and a real
change. It is worth more than any feature list.

## ⭐ The requirements this project must satisfy

**Stage 7's flagship must exercise Stages 3–5**, because the whole point is that you can now build
what you spent 100 days learning. **It must include, non-negotiably:**

| # | Requirement | Days |
|---|---|---|
| 1 | ⭐ **JWT auth with refresh rotation and reuse detection** | 114, 115, 173 |
| 2 | ⭐ **Authorization at the record level** — not just URL rules | 118, 174 |
| 3 | ⭐ **A domain with a real state machine** and enforced invariants | 187, 188 |
| 4 | ⭐ **N+1 solved *and verified by a test*** | 160, 183 |
| 5 | ⭐ **Concurrency handled deliberately** — optimistic locking or a queue | 165, 195 |
| 6 | ⭐ **An async path that must not lose work** — outbox | 124, 179 |
| 7 | **Redis** for something real — cache, rate limit, or lock | 168, 206–208 |
| 8 | ⭐ **RFC 7807 errors, everywhere** | 104, 149 |
| 9 | ⭐ **Testcontainers integration tests** | 184 |
| 10 | ⭐ **Deployed, with metrics, logs and an alert that has fired** | 143, 182, 185 |

**⭐ If your project idea cannot naturally accommodate all ten, pick a different idea.** Bolting a
WebSocket onto a system that has nothing to push is worse than not having one — the interviewer will
ask why, and "to demonstrate WebSockets" is a bad answer.

# Part 2 — ⭐ Choosing

## ⭐ The three questions

> **⭐ 1. Can you describe the problem, and the user, in one sentence — without saying "like X but"?**
>
> **⭐ 2. Does it *naturally* need concurrency control, async work and authorization?**
>
> **⭐ 3. Would you use it, or would someone you know?**

**⭐ Question 2 is the one that eliminates most ideas.** A blog has no concurrency problem. A todo app
has no meaningful authorization beyond ownership. **You need a domain where two users can genuinely
collide.**

## ⭐ Domains that work, and the collision each provides

| Domain | ⭐ The natural hard problem |
|---|---|
| ⭐ **Booking / scheduling** | ⭐ **double-booking** — Day 187's exclusion constraint, Day 195's write skew |
| ⭐ **Inventory / ordering** | ⭐ **overselling** — Day 165's atomic update, Day 195's lost update |
| ⭐ **Ticketing / seat selection** | ⭐ **hold-then-confirm with expiry** — Day 204's sorted set, Day 207's lock |
| **Approval workflows** | a state machine with per-role transitions (Day 174) |
| ⭐ **Multi-tenant SaaS tooling** | ⭐ **tenant isolation** — Day 176's RLS |
| **Collaborative editing** | conflict resolution, WebSockets (Day 180) |

**⭐ Pick one of the first three if you are unsure.** They give you a concurrency problem that is easy
to state, easy to demonstrate breaking, and easy to demonstrate fixed — which is exactly the shape of
the best interview story.

## ⭐ Scope — and cut it harder than feels right

> **⭐ The most common Stage 7 failure is not a bad project. It is an unfinished one.**

**⭐ Rule: one core flow, done to production quality, beats five flows half-built.**

```
⭐ IN SCOPE  — one user journey, end to end, deployed, tested, observable
⭐ OUT       — admin dashboards, analytics, notifications, search,
               social features, mobile apps, "we could also..."
```

**⭐ Write the out-of-scope list down.** It is the most useful artefact of today, because in three
weeks you will want to add something and the list will remind you why you decided not to.

⭐ **And keep a `FUTURE.md`.** "I deliberately deferred X because Y" is a strong interview answer;
"I never thought about X" is not.

# Part 3 — ⭐ Today's deliverables

**Write these in the repository. They are the first commits.**

### ⭐ 1. `README.md` — the one-paragraph pitch

```
⭐ What it does · who for · why it is not trivial · the hard problem it solves
```

**⭐ If you cannot write this in one paragraph, the idea is not clear enough yet.** Rewrite it until
it is. This paragraph is also what you will say in the first thirty seconds of every interview
conversation about the project.

### ⭐ 2. `docs/SCOPE.md`

| Section | Content |
|---|---|
| The one core flow | step by step, in user language |
| ⭐ **Explicitly out of scope** | ⭐ the list, with a reason each |
| ⭐ **The hard problem** | the concurrency or consistency challenge, named |
| Success criteria | what "done" means, measurably |

### ⭐ 3. `docs/adr/0001-project-choice.md`

**Day 101's ADR format**, and this is the first of many:

```
# ADR-0001: Project choice and scope
## Status: Accepted
## Context   — what I want to demonstrate, and the ten requirements
## Decision  — the domain, the one core flow, and why
## Consequences — what I gain, ⭐ what I give up, what I deliberately defer
```

**⭐ The "what I give up" section is the one that matters.** An ADR without honest consequences is a
press release. Practise writing it now, because Days 249–252 produce four more.

### ⭐ 4. The repository, initialised properly

```
⭐ git init · a real .gitignore · README · docs/ · docs/adr/ · a LICENCE
⭐ First commit TODAY. The commit history is part of the artefact.
```

**⭐ Your commit history will be read.** Day 085's rules apply from commit one: small commits,
meaningful messages, no secrets, no `wip` as a message. **An interviewer scrolling a clean history
with real messages forms an impression before reading a line of code.**

# Part 4 — ⭐ The traps of this stage

| Trap | Why it kills the project |
|---|---|
| ⭐ **Starting to code today** | ⭐ you will build the wrong thing well. Days 249–252 exist for this reason |
| ⭐ **Scope creep** | ⭐ **the number one cause of an unfinished flagship** |
| ⭐ **Choosing a domain with no hard problem** | nothing to defend |
| ⭐ **Copying a tutorial's architecture** | every decision is someone else's |
| **Perfectionism on the first component** | the auth layer is beautiful; nothing else exists |
| ⭐ **Not deploying until the end** | ⭐ deploy in week one, even with one endpoint |
| **Building the frontend first** | it becomes the project; the backend is what you are interviewing for |
| ⭐ **No tests until "later"** | later never comes, and retrofitting is worse |

**⭐ On deploying early:** Day 185's checklist is far easier to satisfy incrementally than at the end.
**Get one endpoint deployed with a health check and a metric by Day 253.** Everything after that is
an increment rather than a project.

## 🎤 Defence questions — start rehearsing now

**⭐ You will answer these dozens of times. Begin today.**

1. **What does it do, in thirty seconds?**
2. **⭐ What was the hardest part?** (⭐ the answer must be technical and specific)
3. **What would you do differently?**
4. **⭐ What did you deliberately leave out, and why?**
5. **⭐ What breaks first if it gets a hundred times the traffic?**

**⭐ Question 2 is the one that separates candidates.** "Setting up Spring Security" is a weak answer.
"Preventing double-booking under concurrency — I started with a `SELECT` then an `INSERT`, reproduced
the race with two threads, and replaced it with an exclusion constraint" is a strong one.
