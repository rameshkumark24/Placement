# L-039 · Abstract classes and interfaces

## The comparison table

| | Abstract class | Interface |
|---|---|---|
| Instantiable | ❌ | ❌ |
| Constructors | ✅ | ❌ |
| **Instance fields** | ✅ | ❌ — only `public static final` constants |
| Method bodies | ✅ | ✅ since Java 8 (`default`, `static`, `private`) |
| Access modifiers on methods | Any | `public` (or `private` for helpers) |
| **Multiple inheritance** | ❌ one `extends` | ✅ many `implements` |
| State | ✅ | ❌ |
| Models | **is-a**, a partial implementation | **can-do**, a capability |

**Since Java 8 the feature gap has narrowed a lot.** Interfaces can have behaviour. The two
differences that remain and actually matter:

> **1. An abstract class can hold state. An interface cannot.**
> **2. A class can implement many interfaces but extend only one class.**

Everything else follows from those two.

## What each one models

**An interface is a contract: "I can do this."**

```java
interface Comparable<T> { int compareTo(T o); }        // can-do: be ordered
interface Serializable { }                              // can-do: be serialised
interface AutoCloseable { void close(); }               // can-do: be closed
```

A `String` is comparable, serialisable and a `CharSequence` — three unrelated capabilities. **That's
what multiple interface implementation is for.**

**An abstract class is a partial implementation: "I am a kind of this, and here's shared machinery."**

```java
abstract class AbstractList<E> implements List<E> {
    // real implementations of most List methods, delegating to...
    public abstract E get(int index);      // ...these, which subclasses must supply
    public abstract int size();
}
```

`AbstractList` gives you `iterator`, `indexOf`, `contains`, `equals`, `hashCode` and more, built on
just `get` and `size`. **That's the template method pattern** (Day 095), and it's the honest use case
for an abstract class.

## The decision

```
   Do implementers need shared MUTABLE STATE?         → abstract class
   Will implementers already extend something else?   → interface
   Is it a capability rather than an identity?        → interface
   Do you need constructors or non-public members?    → abstract class
   Unsure?                                            → INTERFACE
```

**Default to the interface.** It's the lower-commitment choice: a class can add an interface later,
but it can never gain a second superclass. Abstract classes impose a permanent structural constraint
on everyone who uses them.

**The idiomatic Java pattern is both:**

```java
public interface List<E> { ... }                        // the contract
public abstract class AbstractList<E> implements List<E> { ... }   // a skeletal implementation
public class ArrayList<E> extends AbstractList<E> { ... }          // a concrete one
```

The interface defines what it *is*; the abstract class offers help you can *choose* to take. If you'd
rather extend something else, implement the interface directly. **That's the design to imitate.**

## Default methods

Java 8 added method bodies to interfaces:

```java
interface Collection<E> {
    boolean removeIf(Predicate<? super E> filter);      // was abstract...

    default boolean removeIf(Predicate<? super E> filter) {   // ...now has a body
        boolean removed = false;
        Iterator<E> each = iterator();
        while (each.hasNext()) { if (filter.test(each.next())) { each.remove(); removed = true; } }
        return removed;
    }
}
```

**Why they exist — and this is the answer interviewers want:**

**Interface evolution.** Before Java 8, adding a method to an interface broke every implementation
everywhere. Lambdas and streams required adding `stream()`, `forEach()` and `removeIf()` to
`Collection` — which would have broken essentially all Java code on earth.

**Default methods made that backward compatible.** Existing implementations inherit the default and
keep compiling.

**They are not** a way to do multiple inheritance of state — interfaces still cannot hold instance
fields, so a default method can only use other interface methods.

### Static and private interface methods

```java
interface Validator {
    static Validator alwaysTrue() { return s -> true; }     // factory, Java 8

    default boolean validateAll(List<String> items) {
        return items.stream().allMatch(this::check);
    }

    private boolean check(String s) { return validate(s); }  // Java 9 — shared helper, not API

    boolean validate(String s);
}
```

**Static methods** let a factory live on the interface itself, instead of a separate `Validators`
utility class — which is why `List.of`, `Comparator.comparing` and `Predicate.not` exist where they
do.

**Private methods** (Java 9) let default methods share logic without exposing it as API.

## The diamond problem

**This is why Java forbids multiple class inheritance:**

```
        A
       / \
      B   C          B and C both override A.method()
       \ /
        D            which one does D inherit?
```

With state, it's worse: does `D` get one copy of `A`'s fields or two? C++ needs virtual inheritance
to answer this; Java sidesteps it by allowing only one superclass.

**Default methods reintroduce the diamond for behaviour** — but Java makes it a compile error rather
than picking silently:

```java
interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }

class C implements A, B { }          // ❌ compile error: inherits unrelated defaults

class C implements A, B {            // ✅ you must resolve it explicitly
    @Override public String hello() { return A.super.hello(); }
}
```

**`A.super.hello()`** is the syntax for choosing a specific interface's default. Unusual, worth
knowing.

### The resolution rules

When a method could come from several places:

```
   1. CLASS WINS.  A method inherited from a superclass beats any interface default.
   2. MOST SPECIFIC INTERFACE WINS.  A sub-interface's default beats its parent's.
   3. OTHERWISE: compile error — you must override and disambiguate.
```

**Rule 1 is the important one.** "The class always wins" prevents a default method from silently
changing the behaviour of an existing class — which is exactly what backward compatibility required.

## Functional interfaces

**An interface with exactly one abstract method.** That's the whole definition.

```java
@FunctionalInterface
interface Transformer<T, R> {
    R transform(T input);                              // the ONE abstract method

    default Transformer<T,R> andLog() { ... }          // defaults don't count
    static Transformer<String,String> upper() { ... }  // statics don't count
}

Transformer<String, Integer> len = s -> s.length();     // lambda target
```

**`@FunctionalInterface` is optional but use it** — like `@Override` (Day 037), it's a compile-time
assertion. Add a second abstract method and the build fails immediately, rather than breaking every
lambda that used it.

**Because defaults and statics don't count**, an interface can be functional *and* have plenty of
behaviour — which is exactly how `Comparator` works: one abstract `compare`, plus `reversed`,
`thenComparing`, `comparing` and more.

Day 057 covers the built-in set: `Function`, `Predicate`, `Supplier`, `Consumer`.

## Marker interfaces

```java
interface Serializable { }        // no methods at all
interface Cloneable { }
```

**A type with no members, used purely as a runtime flag** checked via `instanceof`.

**Largely superseded by annotations**, which carry data and don't pollute the type hierarchy.
`Cloneable` in particular is a design failure — it's a marker that doesn't declare `clone()`, so it
signals an intent it can't enforce. Day 041.

## Type this yourself

```java
import java.util.*;
import java.util.function.*;

public class InterfaceDemo {

    // ---- diamond ----
    interface Greeter { default String hello() { return "Greeter"; } }
    interface Waver   { default String hello() { return "Waver";  } }

    static class Both implements Greeter, Waver {
        @Override public String hello() {
            return Greeter.super.hello() + " + " + Waver.super.hello();   // explicit resolution
        }
    }

    // ---- class wins over interface default ----
    interface Speaker { default String speak() { return "interface default"; } }
    static class Base { public String speak() { return "class method"; } }
    static class Derived extends Base implements Speaker { }

    // ---- functional interface with defaults and statics ----
    @FunctionalInterface
    interface Validator {
        boolean validate(String s);                                    // the ONE abstract method

        default Validator and(Validator other) {                       // doesn't count
            return s -> this.validate(s) && other.validate(s);
        }
        static Validator notEmpty() { return s -> s != null && !s.isBlank(); }   // doesn't count
        static Validator maxLength(int n) { return s -> s.length() <= n; }
    }

    // ---- interface + skeletal implementation, the JDK pattern ----
    interface Shape {
        double area();
        default String describe() { return getClass().getSimpleName() + " area=" + area(); }
    }
    static abstract class AbstractShape implements Shape {
        protected final String name;                     // STATE — only possible in a class
        protected AbstractShape(String name) { this.name = name; }   // CONSTRUCTOR — ditto
        @Override public String describe() { return name + " area=" + area(); }
    }
    static class Circle extends AbstractShape {
        private final double r;
        Circle(double r) { super("Circle"); this.r = r; }
        @Override public double area() { return Math.PI * r * r; }
    }
    static class Triangle implements Shape {             // skips the abstract class entirely
        public double area() { return 6.0; }
    }

    public static void main(String[] args) {
        System.out.println("--- diamond, resolved explicitly ---");
        System.out.println("   " + new Both().hello());

        System.out.println("\n--- class wins over interface default ---");
        System.out.println("   " + new Derived().speak());       // "class method"

        System.out.println("\n--- functional interface ---");
        Validator v = Validator.notEmpty().and(Validator.maxLength(5));
        for (String s : new String[]{"ok", "", "toolongvalue"})
            System.out.printf("   %-14s -> %b%n", "\"" + s + "\"", v.validate(s));

        System.out.println("\n--- interface + optional skeleton ---");
        List<Shape> shapes = List.of(new Circle(2), new Triangle());
        shapes.forEach(s -> System.out.println("   " + s.describe()));
    }
}
```

**Three experiments:**

1. **Remove the `hello()` override in `Both`.** Read the compile error — Java refuses to guess.
2. **`Derived.speak()` prints `"class method"`.** The superclass beat the interface default. That's
   resolution rule 1, and it's why default methods can't silently change existing behaviour.
3. **Add a second abstract method to `Validator`.** `@FunctionalInterface` fails the build
   immediately, before any lambda breaks.

## Common mistakes

| Mistake | Correction |
|---|---|
| Choosing by feature list rather than by what's modelled | Interface = capability; abstract class = partial implementation with state. |
| Using an abstract class when there's no shared state | An interface leaves implementers free to extend something else. |
| Thinking default methods give multiple inheritance of state | Interfaces still have no instance fields. |
| Expecting Java to pick a default when two conflict | Compile error. Resolve with `X.super.method()`. |
| Omitting `@FunctionalInterface` | It's a compile-time assertion that protects every lambda using the type. |
| Constants in interfaces as a namespace | The "constant interface" antipattern. Use an enum or a utility class. |
| Marker interfaces in new code | Use annotations — they carry data and don't add a type. |

## Interview questions

**Q: Abstract class or interface — how do you choose?**
> By what you're modelling. An interface is a capability contract — "can do" — and a class can
> implement many, so it's the lower-commitment choice. An abstract class is a partial implementation
> with shared state, and since a class can only extend one, it imposes a permanent structural
> constraint. If implementers need shared mutable state or constructors, use an abstract class;
> otherwise use an interface. The JDK does both — `List`, `AbstractList`, `ArrayList`.

**Q: Why were default methods added?**
> Interface evolution. Adding a method to an interface used to break every implementation, so
> introducing `stream`, `forEach` and `removeIf` on `Collection` for Java 8 would have broken
> essentially all existing Java. Default methods let new methods carry an implementation that existing
> classes inherit, keeping them source and binary compatible.

**Q: Do default methods bring back the diamond problem?**
> For behaviour, yes — but Java refuses to guess. If a class inherits conflicting defaults from two
> interfaces it's a compile error, and you must override and choose with `Interface.super.method()`.
> State is unaffected, since interfaces still have no instance fields. The resolution rules are: a
> class method always wins over an interface default, then the most specific interface wins, otherwise
> it's an error.

**Q: What is a functional interface?**
> An interface with exactly one abstract method, which makes it a valid lambda target. Default and
> static methods don't count, which is why `Comparator` can be functional despite having many methods.
> `@FunctionalInterface` is an optional annotation that makes the compiler enforce it.

**Q: Why does "the class always wins" over an interface default?**
> Backward compatibility. If an interface default could override an inherited class method, adding a
> default to an interface could silently change the behaviour of existing classes — exactly what
> default methods were introduced to avoid.
