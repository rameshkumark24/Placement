# Day 342 ⭐

**L-342** · ⭐ Distributed transactions — 2PC, sagas, and compensations that are not rollbacks

**Time:** 3 hrs · **Mode:** NEW

> **⭐ The moment a business operation spans two systems, ACID is gone. What replaces it is not a
> weaker transaction — it is a different design in which failure is a first-class path.**
>
> The key idea, and the one candidates get wrong: **a compensation is not a rollback.** You cannot
> un-send an email or un-ship a parcel. **You can only do something that makes it right.**

---

# Part 1 — ⭐ Two-phase commit, and why it is rare

```
⭐ PHASE 1 — PREPARE
⭐   coordinator → all participants: "can you commit?"
⭐   each: does the work, ⭐ HOLDS LOCKS, writes to its log, replies "yes"
⭐ PHASE 2 — COMMIT
⭐   coordinator → all: "commit"   (or "abort" if any said no)
```

| ⭐ It gives | ⭐ It costs |
|---|---|
| ⭐ Genuine atomicity across systems | ⭐⭐ **BLOCKING: if the coordinator dies after prepare, participants hold locks INDEFINITELY** |
| Strong isolation | ⭐ **locks held across a network round trip** (Day 196's queue, distributed) |
| A familiar programming model | ⭐ **availability multiplies down** (Day 340) — every participant must be up |
| | ⭐ Poor throughput; XA support is patchy and slow |

> **⭐ The killer is the blocking window.** Between "prepared" and "commit", a participant has
> promised it can commit and **cannot release its locks or decide alone.** If the coordinator is
> partitioned away, **that row is locked until a human intervenes** — and by Day 330's argument, you
> cannot distinguish a dead coordinator from a slow one.

**⭐ Where 2PC is still legitimate:** within one database across shards, inside a single trusted
cluster with a highly available coordinator, or in messaging-plus-database XA on a small scale.
**Across service boundaries over the internet, it is the wrong tool** — and saying "2PC is available
but I would not use it here, because a coordinator failure holds locks in every participant" is
exactly the answer expected.

# Part 2 — ⭐⭐ The saga

> **⭐ A saga is a sequence of local transactions. Each one commits immediately. If a later step
> fails, earlier steps are undone by compensating transactions.**

```
⭐ T1 create order ─► T2 charge card ─► T3 reserve stock ─► T4 create shipment
⭐                                             ✗ fails
⭐ C2 refund card ◄─ C1 cancel order ◄─────────┘
⭐ ⭐ Each Cn is a NEW transaction, not a rollback. Everything is already committed and visible.
```

| ⭐ Property | ⭐ Consequence |
|---|---|
| ⭐ **Each step commits independently** | ⭐ no locks held across the network |
| ⭐⭐ **No isolation** | ⭐⭐ **other transactions SEE the intermediate states — Part 3** |
| ⭐ Atomicity is eventual | it completes or compensates — but not instantly |
| ⭐ **Every step must be idempotent** | retries are guaranteed (Day 335) |
| ⭐ Every step needs a timeout | ⭐ otherwise a saga hangs forever with no owner |

## ⭐⭐ Compensations are semantic, not mechanical

| Operation | ⭐ Compensation | ⭐ Note |
|---|---|---|
| Reserve stock | release the reservation | ⭐ clean |
| Charge card | ⭐ **refund** | ⭐ **not "un-charge" — the original charge is on the statement forever** |
| ⭐ Send an email | ⭐⭐ **send a correction** | ⭐⭐ **you cannot un-send it** |
| Ship a parcel | ⭐ a returns process, and a cost | ⭐ some compensations involve humans |
| ⭐ **Delete a record** | ⭐⭐ **often impossible to compensate** | ⭐ so use soft deletes in a saga |

> **⭐ The design rule that falls out: order your steps so the reversible, cheap ones happen first and
> the irreversible ones last.** Reserve stock and authorise payment early; **capture the payment and
> dispatch the parcel last**, because those are the steps you cannot cleanly undo. **This is why
> authorise-then-capture exists** (Day 320A).

⚠️ **And a compensation can itself fail.** A refund API can be down. **The saga must retry
compensations indefinitely with backoff, and escalate to a human queue if they keep failing** —
**there is no "give up" state that leaves the system consistent.**

## ⭐ Orchestration vs choreography — the same choice as Day 333

| | ⭐ Orchestrated saga | ⭐ Choreographed saga |
|---|---|---|
| ⭐ **Flow lives in** | ⭐ **one coordinator with a state machine** | ⭐ scattered across event handlers |
| ⭐ **"Where is order 123?"** | ⭐⭐ **answerable — query the saga state** | ⭐⭐ **grep five services' logs** |
| Adding a step | edit the orchestrator | subscribe a new service |
| Coupling | ⭐ the orchestrator knows everyone | ⭐ services know event shapes |
| ⭐ Compensation logic | ⭐ **explicit and testable in one place** | ⭐ each service must know what to undo |

> **⭐ For sagas specifically, orchestrate.** The compensation path is the hard part, and it must be
> visible, testable and queryable. **A choreographed saga has no state machine, so nobody can answer
> whether a failed order was compensated** — and that question gets asked by a customer with money
> involved.

# Part 3 — ⭐⭐ The isolation you lost, and how to cope

**⭐ This is the section most candidates never reach, and it is where the real bugs live.**

```
⭐ T1 creates the order (status: PENDING) and commits.
⭐ ⭐ Another user's request now SEES a pending order that may never exist.
⭐ T3 fails; C1 cancels the order.
⭐ ⇒ ⭐⭐ A DIRTY READ that a database would have prevented — and it lasted seconds, not microseconds.
```

| ⭐ Countermeasure | ⭐ How |
|---|---|
| ⭐⭐ **Semantic lock** | ⭐⭐ **a `PENDING` status that other operations must respect — the most common answer** |
| ⭐ **Commutative updates** | ⭐ use `balance = balance + x` rather than absolute writes, so order does not matter |
| ⭐ Pessimistic ordering | ⭐ do the step that is hardest to compensate **last** — as above |
| ⭐ **Re-read and verify** | before an irreversible step, re-check the invariant still holds |
| ⭐ Version/rerun check | ⭐ detect that data changed under you and abort |

> **⭐ The `PENDING` state is the workhorse.** A seat, a stock unit or a balance held in a pending
> state is **exactly Day 316's reservation with an expiry** — and pointing out that a saga's semantic
> lock and a seat hold are the same mechanism ties the whole stage together.

# Part 4 — ⭐ Making it reliable: the outbox and the state machine

```
⭐ The saga's own problem: it must write its state AND send a message. ⭐ Two systems again.
⭐ ⇒ ⭐⭐ THE OUTBOX (Days 124, 263, 335):
⭐    write the state change and the outgoing message to the SAME database, in ONE transaction;
⭐    a publisher reads the outbox and sends. ⭐ At-least-once, so consumers are idempotent.
```

| ⭐ The saga coordinator needs | ⭐ Why |
|---|---|
| ⭐ **Durable state per saga instance** | ⭐ it must survive a restart mid-flow |
| ⭐ **A step timeout** | ⭐⭐ **a step that never replies must trigger compensation, not silence** |
| ⭐ **Idempotent step invocation** | at-least-once delivery guarantees repeats |
| ⭐⭐ **An alert on stuck sagas** | ⭐⭐ **"12 sagas have been in AWAITING_PAYMENT for over an hour"** |
| A human resolution path | some sagas need a person; give them a screen |

> **⭐ The stuck-saga alert is the operational answer to Day 333's question.** It is also what makes
> the design defensible: **"failed sagas compensate automatically; sagas stuck beyond their timeout
> alert with the order id, and there is a queue a human can work."**

## ⭐⭐ And the most important recommendation

> **⭐ The best distributed transaction is the one you do not need.** Choose aggregate and service
> boundaries (Days 305, 340) so that **most operations are local**, and reserve sagas for the few
> that genuinely span capabilities.

**⭐ If most of your operations need sagas, your boundaries are wrong** — you have split things that
change together, which Day 298 warned about. **Saying that unprompted is the strongest possible
close on this topic.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ 2PC across services | ⭐⭐ **coordinator failure holds locks everywhere, indefinitely** |
| ⭐⭐ Treating a compensation as a rollback | ⭐⭐ **you cannot un-send, un-ship or un-charge** |
| ⭐ Irreversible steps early in the saga | ⭐ you cannot cleanly undo them |
| ⭐ No plan for a failing compensation | ⭐ **the system stays inconsistent with nobody notified** |
| ⭐ Choreographed sagas | ⭐⭐ **no state machine — nobody can say whether it compensated** |
| ⭐ **Ignoring lost isolation** | ⭐⭐ **dirty reads lasting seconds** |
| No semantic lock / pending state | other operations act on data that may vanish |
| Non-idempotent steps | at-least-once turns into double charges (Day 335) |
| ⭐ No step timeout | ⭐ sagas hang silently forever |
| ⭐ **No stuck-saga alert** | you find out from the customer |
| Publishing outside the transaction | the dual-write problem — use an outbox |
| ⭐ Sagas everywhere | ⭐ **your service boundaries are wrong** |

## Interview questions

**Q: How do you do a transaction across two services?**
You do not — you design for the absence of one. Two-phase commit exists but blocks: between prepare
and commit a participant holds locks and cannot decide alone, so a coordinator failure locks rows in
every participant until someone intervenes, and you cannot tell a dead coordinator from a slow one.
So a saga: a sequence of local transactions, each committing immediately, with compensating
transactions if a later step fails.

**Q: What is a compensation, exactly?**
A new transaction that makes things right — not a rollback. You cannot un-charge a card, you issue a
refund; you cannot un-send an email, you send a correction; you cannot un-ship a parcel, you run a
return. That asymmetry produces the ordering rule: reversible and cheap steps first, irreversible
ones last, which is exactly why payment authorisation and capture are separate operations.

**Q: What do you lose compared with a database transaction?**
Isolation. Every step commits and is immediately visible, so other operations can read a pending
order that may never exist — a dirty read lasting seconds rather than microseconds. The
countermeasures are semantic locks, which is a pending status other operations must respect,
commutative updates so ordering does not matter, re-reading before irreversible steps, and ordering
the steps pessimistically.

**Q: Orchestrated or choreographed sagas?**
Orchestrated. The compensation path is the hard part and it must be in one place where it can be
tested and queried. A choreographed saga has no state machine, so when a customer asks whether their
failed order was refunded, nobody can answer without grepping five services' logs. I keep
choreography for genuinely optional consumers — analytics, notifications, search indexing.

**Q: How do you make the saga itself reliable?**
Durable state per saga instance so it survives a restart, an outbox so the state change and the
outgoing message commit together, idempotent steps because delivery is at-least-once, a timeout on
every step so a silent participant triggers compensation rather than nothing, indefinite retry with
backoff on compensations, and an alert on sagas stuck past their timeout with a queue a human can
work. And the honest framing is that the best distributed transaction is the one you avoided by
choosing better boundaries.

## Mini task

1. **Pick one cross-service operation** and write its saga: steps, compensations, and the order that
   puts irreversible actions last.
2. ⭐ **For each step, write the compensation and mark it clean, lossy or impossible.** Any
   "impossible" must move later in the sequence.
3. ⭐⭐ **Reproduce the isolation loss**: create a pending order, read it from another request, then
   compensate. **Show the dirty read.** Add a semantic lock and confirm the reader respects it.
4. Build the **orchestrator with a persisted state machine.** Kill it mid-saga, restart, and confirm
   it resumes.
5. ⭐ Make step 3 never reply. **Confirm the timeout fires and compensation runs**, rather than the
   saga hanging.
6. ⭐ Make a **compensation fail.** Verify it retries with backoff and eventually alerts rather than
   giving up.
7. Deliver a step invocation twice and **assert exactly one effect** (Day 335).
8. ⭐ Implement the **outbox** for saga messages. Kill the process between the state write and the
   publish, and confirm the message still goes.
9. ⭐ Add the **stuck-saga alert** and dashboard. Simulate three stuck sagas and confirm you can name
   the order ids.
10. ⭐ **Count how many of your operations need a saga.** If it is most of them, redraw the
    boundaries.

## 🎙️ Articulation drill

**Three minutes:** *"An order must charge a card, reserve stock, and create a shipment across three
services. How?"*

**⭐ The full answer has five beats.** Not 2PC, with the blocking reason given · an orchestrated saga
with a persisted state machine · **compensations that are semantic, with irreversible steps ordered
last** · the isolation loss named, with a pending status as the semantic lock · **and the operational
close — outbox, step timeouts, idempotent steps, and an alert on stuck sagas.**

**⭐ Then the sentence that finishes it: "and I would first check whether these three genuinely belong
in different services, because a saga is the price of a boundary — if most operations need one, the
boundaries are wrong."**
