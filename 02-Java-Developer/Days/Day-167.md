# Day 167

**L-167** · The second-level cache — what it is, and why you probably should not use it

**Time:** 3 hrs · **Mode:** NEW

> Day 162 covered the first-level cache: the persistence context, scoped to one transaction, and not
> optional. The **second-level cache** is scoped to the `SessionFactory` — shared across transactions
> and, in a cluster, across nodes.
>
> Today is an honest day. The second-level cache is heavily documented, prominently featured in
> Hibernate's manual, and **the wrong tool for most Spring applications.** Knowing what it does *and*
> knowing when to reject it is a better answer than either enthusiasm or ignorance.

---

# Part 1 — What it caches, which is narrower than people think

```java
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)      // ⭐ Hibernate-specific
@Cacheable                                                // JPA standard
public class Product {
    @Id private Long id;
    private String name;
    private BigDecimal price;

    @OneToMany(mappedBy = "product")
    @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)   // ⭐ collections cache SEPARATELY
    private List<Review> reviews;
}
```

```java
Product a = em.find(Product.class, 1L);      // SELECT
// different transaction, possibly a different node
Product b = em.find(Product.class, 1L);      // ⭐ from the second-level cache, no SQL
```

**⭐ The critical limitation, and the one that decides most of it:**

> **The entity cache is keyed by primary key, so it only serves `find(id)` and lazy-association
> loads. A query — `where status = 'PENDING'` — does not use it at all.**

`repo.findByStatus(PENDING)` hits the database even if all 400 matching products are cached, because
the cache has no idea which ids match that predicate. Since **most application queries are queries,
not id lookups**, the hit rate in a typical service is far lower than people expect.

There is a separate **query cache** for that, and it comes with its own problem — see Part 3.

## The four concurrency strategies

| Strategy | Semantics | Use |
|---|---|---|
| `READ_ONLY` | ⭐ never modified. Fastest, no locking | reference data — currencies, countries, categories |
| `NONSTRICT_READ_WRITE` | invalidates *after* commit — ⭐ a stale window exists | data where brief staleness is acceptable |
| **`READ_WRITE`** | soft locks around the write; near-strict | the usual choice for mutable entities |
| `TRANSACTIONAL` | full JTA participation | needs a JTA provider; rare |

**`READ_ONLY` on genuinely immutable data is the case where the second-level cache is unambiguously
correct.** Everything else is a trade-off.

## Setup

```xml
<dependency><groupId>org.hibernate.orm</groupId>
            <artifactId>hibernate-jcache</artifactId></dependency>
<dependency><groupId>org.ehcache</groupId><artifactId>ehcache</artifactId></dependency>
```

```yaml
spring.jpa.properties.hibernate:
  cache.use_second_level_cache: true
  cache.region.factory_class: jcache
  generate_statistics: true                  # ⭐ non-negotiable — see Part 4
```

# Part 2 — ⭐ The four reasons to be sceptical

### 1. It is a distributed cache invalidation problem

Six instances, each with a local cache. Instance 1 updates a product. **Instances 2–6 hold stale
copies and do not know.** Options:

- **A replicated/distributed cache** (Hazelcast, Infinispan) — now you are running and operating a
  distributed system, with its own network partitions, its own memory pressure and its own failure
  modes.
- **A short TTL** — you have accepted staleness, which means you did not need strong consistency,
  which means a simpler cache would have done.

### 2. ⭐ Anything that bypasses Hibernate leaves the cache wrong

| Writer | Cache updated? |
|---|---|
| Hibernate entity update | ✅ |
| Bulk JPQL `@Modifying` | ❌ **stale** |
| Native SQL | ❌ **stale** |
| A different service | ❌ **stale** |
| A DBA, a script, a Flyway data migration | ❌ **stale** |

**Day 162's bulk-update hole, made worse:** at the persistence-context level a stale entity lasted one
transaction. Here it lasts until eviction, on every node.

**If any other process writes your tables, the second-level cache is unsafe.** In a microservices
architecture where one service owns its tables that is manageable; in a system with batch jobs,
reporting writes or a legacy application on the same schema, it is not.

### 3. It caches the wrong layer

The second-level cache stores **entities** — hydrated objects with proxies and snapshots. What your
endpoint actually returns is a **DTO**. So a cache hit still costs you entity hydration, DTO mapping
and serialization.

**Caching the DTO at the service layer skips all three** (Day 168), and it is usually the bigger win.
Day 147's argument once more: the entity is not what the caller wanted.

### 4. It is often solving a problem an index would solve

**A query taking 200 ms because it lacks an index is not a caching problem.** Adding a cache in front
of it means the first request is still 200 ms, cold caches after a deploy are still 200 ms, and you
have added invalidation complexity to avoid fixing a one-line problem.

**Check the query plan before you cache** — D-11 and D-12 exist for exactly this. A cache should make
already-fast things free, not make slow things intermittently tolerable.

# Part 3 — The query cache, and why it is usually a trap

```java
@QueryHints(@QueryHint(name = "org.hibernate.cacheable", value = "true"))
List<Product> findByCategory(String category);
```

```yaml
spring.jpa.properties.hibernate.cache.use_query_cache: true
```

**How it works:** the cache stores the query text plus parameters → **a list of ids**. On a hit,
Hibernate then loads each entity — from the second-level cache if present, from the database if not.

**⭐ Two consequences that make it a poor default:**

1. **Without the entity cache enabled too, a query-cache hit is an N+1** — it has ids and must fetch
   each entity.
2. ⭐ **Any modification to the entity invalidates every cached query for that table.** One product
   price update wipes all 500 cached category queries. On a table with any write traffic the hit rate
   collapses, and you are paying cache maintenance for almost no benefit.

**Use the query cache only for near-static reference data**, where the entity cache is `READ_ONLY` and
writes are rare. Otherwise, cache the result at the service layer where you control invalidation
explicitly.

# Part 4 — Measuring it, which is the only honest way to decide

```yaml
spring.jpa.properties.hibernate.generate_statistics: true
logging.level.org.hibernate.stat: DEBUG
```

```java
Statistics stats = sessionFactory.getStatistics();
stats.getSecondLevelCacheHitCount();
stats.getSecondLevelCacheMissCount();
stats.getSecondLevelCachePutCount();      // ⭐ compare with hits
```

**⭐ The number that tells you the truth is puts versus hits.** If puts exceed hits, the cache is doing
more work than it saves — you are paying serialization, memory and eviction on every miss to serve
fewer reads than that. That is a cache to delete, and it is a common outcome.

Expose the ratio via Micrometer (Day 143) and put it on the dashboard. **A cache without a hit-rate
metric is a cache nobody can evaluate**, and it will stay in the codebase forever on the assumption
that it helps.

## The honest decision table

| Situation | Answer |
|---|---|
| Immutable reference data — currencies, countries, tax rates | ⭐ **second-level cache, `READ_ONLY`.** The clear win |
| Read-heavy entity fetched by id, one writer service | ✅ `READ_WRITE`, with metrics |
| An expensive computed result | ⭐ **`@Cacheable` on the service method** (Day 168) |
| An expensive DTO an endpoint returns | ⭐ **Redis at the service layer** (Day 120) |
| A slow query | ⭐ **fix the query** — index, projection, rewrite. Then reconsider |
| Any other process writes these tables | ❌ **do not use it** |
| Query results on a table with writes | ❌ query cache invalidates constantly |
| A single instance with a small dataset | ⭐ probably nothing — the database's own buffer cache is already doing this |

**The last row deserves emphasis.** PostgreSQL's shared buffers already cache hot pages in memory. A
primary-key lookup on a cached page is well under a millisecond. **The second-level cache is saving
you a network round trip, not a disk read** — which is real, but it is one millisecond, and it should
be weighed honestly against the invalidation complexity it introduces.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Expecting it to serve queries | it is keyed by primary key only |
| Enabling it without measuring | often net negative; nobody ever checks |
| Using it when another process writes the tables | permanently stale data |
| Bulk updates with a second-level cache | stale on every node until eviction |
| Query cache on a written table | one write invalidates every cached query |
| Query cache without the entity cache | a hit becomes an N+1 |
| Caching instead of indexing | first request and every cold cache still slow |
| Local caches across six instances | six divergent views of the same row |
| Caching entities when DTOs are what you return | still pay hydration, mapping and serialization |
| No hit-rate metric | the cache is unevaluable and lives forever |

## Interview questions

**Q: What is the second-level cache and how does it differ from the first?**
The first-level cache is the persistence context — transaction-scoped, mandatory, and the reason
`findById` twice in one transaction issues one query. The second-level cache is
`SessionFactory`-scoped and shared across transactions, keyed by primary key — so it serves
`find(id)` and lazy loads, but not queries.

**Q: Would you enable it?**
For immutable reference data, yes — `READ_ONLY`, no invalidation problem. Otherwise I would be
cautious: it goes stale on bulk updates, native SQL and any other writer; across instances it becomes
a distributed invalidation problem; and it caches entities when what the endpoint returns is a DTO.
Usually caching the DTO at the service layer is the bigger win.

**Q: What is wrong with the query cache?**
Any modification to an entity invalidates every cached query for that table, so on a table with write
traffic the hit rate collapses. And without the entity cache enabled, a query-cache hit returns ids
and then loads each entity — an N+1.

**Q: How do you decide whether a cache is helping?**
Hibernate statistics, comparing puts against hits. If puts exceed hits the cache costs more than it
saves. That ratio goes on a dashboard — a cache without a hit-rate metric cannot be evaluated and
will never be removed.

## Mini task

1. Enable the second-level cache with Ehcache and `generate_statistics`. Cache `Product` as
   `READ_WRITE`.
2. `findById` the same product in two transactions. Confirm one SELECT.
3. Now `findByName`. **Confirm it hits the database despite the entity being cached.** That is the
   day's central limitation.
4. Enable the query cache and mark that method cacheable. Confirm the hit. Then update one product
   and re-run — **confirm every cached query for that table is gone.**
5. Run a bulk `@Modifying` update. Read the entity again and confirm the stale value.
6. Run two instances against one database. Update on instance 1, read on instance 2. Observe.
7. Log hits, misses and puts for a realistic mixed workload. **Compute the ratio and decide honestly
   whether to keep it.**
8. Take a slow unindexed query, cache it, and measure p99. Then delete the cache and add the index.
   Compare — including the cold-cache case after a restart.

## 🎙️ Articulation drill

Two minutes: **"Would you use Hibernate's second-level cache?"**

Answer with a decision, not a description: yes for immutable reference data with `READ_ONLY`, rarely
otherwise — then give the reasons. It is keyed by primary key so it does not serve queries; it goes
stale on bulk updates, native SQL and any external writer; across instances it becomes a distributed
invalidation problem; and it caches entities when the thing you return is a DTO. Close on the two
signals of maturity: check the query plan before caching, because a cache is not a fix for a missing
index, and put hits-versus-puts on a dashboard, because a cache nobody measures is a cache nobody can
remove.
