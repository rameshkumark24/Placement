# Part 1 — The staging area

## Why it exists

Most version control systems go working-copy → repository. Git inserts the index, and the reason is
this: **what you edited and what you should commit are different things.**

In one editing session you typically fix a bug, rename a variable, add a log line and correct a typo
in a comment. Committing all four together produces a commit that cannot be reviewed, cannot be
reverted selectively, and cannot be bisected usefully (Day 087). The index lets you assemble one
logical change at a time out of a messy working tree.

```bash
git add file.java                # whole file
git add src/                     # directory
git add -A                       # everything, including deletions
git add -u                       # only already-tracked files
git add -p                       # ← INTERACTIVE, hunk by hunk
git add -N newfile && git add -p # stage parts of a NEW file too
```

## `git add -p` — the habit worth building

```
Stage this hunk [y,n,q,a,d,s,e,?]?
```

| Key | Does |
|---|---|
| `y` / `n` | stage / skip this hunk |
| `s` | **split** into smaller hunks |
| `e` | **edit** the hunk manually — stage individual lines |
| `a` / `d` | all / none of the rest in this file |
| `q` | quit |

Two benefits, and the second is the bigger one:

1. Commits become coherent.
2. **You re-read every line you are about to commit.** This is the cheapest code review that exists,
   and it catches an astonishing amount — a leftover `System.out.println`, a commented-out block, a
   hard-coded token, a debug timeout you meant to restore.

`git diff --staged` before every commit is the same discipline in one command. Make it reflex.

## Undoing, correctly

The commands are notoriously badly named. This table is the one to memorise:

| Goal | Command |
|---|---|
| Unstage, keep the edit | `git restore --staged <file>` (old: `git reset HEAD <file>`) |
| Discard a working-tree edit ⚠️ | `git restore <file>` (old: `git checkout -- <file>`) |
| Unstage everything | `git reset` |
| Amend the last commit | `git commit --amend` |
| Undo the last commit, keep changes staged | `git reset --soft HEAD~1` |
| Undo the last commit, keep changes unstaged | `git reset HEAD~1` (mixed, the default) |
| Undo the last commit, **destroy** changes ⚠️ | `git reset --hard HEAD~1` |
| Undo a *pushed* commit safely | `git revert <hash>` |

**`git restore <file>` and `git reset --hard` are the only two commands here that can lose work
permanently**, because the changes were never in an object. Everything committed is recoverable via
the reflog (Day 087). That distinction — committed is safe, uncommitted is not — is worth stating to
yourself before you type either one.

Hence the practical advice: **when in doubt, commit.** A messy commit can be reshaped later; an
uncommitted change destroyed by `restore` is gone.

## `git stash`

```bash
git stash push -m "wip: half-done validation"
git stash list
git stash show -p stash@{0}
git stash pop                    # apply and remove
git stash apply                  # apply and keep
git stash push -u                # include untracked files
git stash push -p                # interactively choose what to stash
git stash branch fix-later       # turn a stash into a branch
```

Stash is a stack of temporary commits on a hidden ref. Use it for "I need to switch branches right
now"; **do not use it as storage** — an unlabelled stash from three weeks ago is a mystery you will
delete rather than examine. If work matters, put it on a branch.

## `.gitignore`

```gitignore
# Build output
target/
build/
*.class
*.jar

# IDE
.idea/
*.iml
.vscode/
.settings/

# OS
.DS_Store
Thumbs.db

# Logs and local data
*.log
/data/

# SECRETS — never commit
.env
.env.*
!.env.example          # ← negation: DO commit the template
*.pem
*.key
application-local.yml
```

Rules: a trailing `/` matches directories only; a leading `/` anchors to the repo root; `!` negates a
previous pattern; `**/` matches at any depth.

**`.gitignore` only affects untracked files.** Adding a pattern for a file already tracked does
nothing:

```bash
git rm --cached path/to/file      # untrack it, keep it on disk
git rm -r --cached .              # re-apply .gitignore to everything (then re-add)
git check-ignore -v path          # ← which rule is ignoring this?
```

`git check-ignore -v` answers "why is Git not seeing my file", which is otherwise a ten-minute
mystery.

Also: `~/.gitignore_global` for editor and OS noise, so you are not pushing `.DS_Store` rules into
every project's repo.

## Secrets — the incident, and the correct response

> **If a secret is committed and pushed, it is compromised. Rotate it. Removing it from history is
> cleanup, not remediation.**

This is the part people get wrong. They rewrite history, force-push, and consider it handled — but
the secret was on GitHub, in clones, in CI caches, in forks and quite possibly in a bot's index
within seconds. Public-repo secrets are scraped in **minutes**; there are people running scanners
solely for that.

So the order is:

1. **Rotate the credential immediately.** This is the only step that actually fixes anything.
2. Then remove it from history — `git filter-repo` (the modern tool) or BFG Repo-Cleaner.
3. Then force-push and tell everyone to re-clone.
4. Then add prevention: `gitleaks` or `git-secrets` as a **pre-commit hook**, plus a server-side
   scan.

```bash
pip install git-filter-repo
git filter-repo --path .env --invert-paths       # remove a file from ALL history
```

Prevention is cheap:

```bash
# .git/hooks/pre-commit  (or use pre-commit / husky so it's shared)
#!/usr/bin/env bash
set -euo pipefail
if git diff --cached --name-only -z | xargs -0 grep -lIE \
     '(AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY|password\s*=\s*["'\''][^"'\'']{6,})' 2>/dev/null; then
    echo "possible secret in staged changes — commit blocked" >&2
    exit 1
fi
```

Note the hook lives in `.git/hooks`, which is **not** committed — that is why teams use the
`pre-commit` framework or Husky, which do get committed.

# Part 2 — Commit messages

## The format

```
Add rate limiting to the payments endpoint

The payment provider began returning 429s during the Diwali sale
because we were sending bursts of up to 400 requests per second
against their documented limit of 100.

Adds a token-bucket limiter in front of PaymentClient, sized from
the provider's published limit and configurable per environment.
Requests that exceed the bucket queue for up to 2s and then fail
fast with a 503 rather than being dropped.

Considered a global semaphore instead, but the limit is per-API-key
and we hold three keys, so a per-client bucket is the correct unit.

Fixes #4471
```

The structure:

| Part | Rule |
|---|---|
| Subject | ≤ 50 chars, **imperative mood**, capitalised, **no trailing period** |
| Blank line | Mandatory — tools rely on it |
| Body | Wrap at 72. Explain **why**, not what |
| Footer | Issue references, `Co-Authored-By`, `BREAKING CHANGE:` |

**Imperative mood** — "Add", not "Added" or "Adds" — because the message completes the sentence
*"If applied, this commit will…"*. Git's own generated messages ("Merge branch…", "Revert…") use it,
so your history stays consistent.

## Why "why" is the whole point

The diff already shows *what* changed — perfectly, in complete detail, forever. It can never show
**why**, and that is the only information that is lost when the author leaves.

```
❌ "fix bug"
❌ "updates"
❌ "Changed the timeout from 30 to 5"        ← the diff already says this
✅ "Reduce the HTTP timeout to 5s

    The upstream service's p99 is 1.2s, so a 30s timeout meant a
    single hung request held a pool thread for the whole window and
    50 concurrent hangs exhausted the pool. 5s is p99 plus 4x margin."
```

The test: **six months from now, someone is about to change this line back. Does your message stop
them?** The second version does. The first three do not.

This is also why `git blame` is a research tool rather than an accusation one — you find the line,
read the commit, and learn the constraint you were about to violate.

## What makes one commit

> **One commit = one logical change that leaves the build green.**

- Not one file. A feature touching six files is one commit.
- Not one day's work.
- **Separate refactoring from behaviour change.** A commit that both moves code and changes what it
  does is unreviewable — the reviewer cannot tell which lines are the real change. Two commits:
  "Extract PaymentValidator" then "Reject expired cards".
- Every commit should build and pass tests, so `git bisect` works (Day 087). A broken intermediate
  commit makes bisect return the wrong answer.

## Conventional Commits

```
<type>(<scope>): <subject>

feat(payments): add rate limiting to the charge endpoint
fix(auth): reject tokens whose issuer does not match the tenant
refactor(orders): extract OrderValidator from OrderService
docs(readme): document the required environment variables
test(payments): cover the 429 retry path
chore(deps): bump jackson-databind to 2.17.1
perf(search): add a covering index on (tenant_id, created_at)

BREAKING CHANGE: the /v1/orders response no longer includes `legacyId`
```

Machine-readable, which enables automatic changelogs and semantic versioning (`feat` → minor,
`fix` → patch, `BREAKING CHANGE` → major). Adopt it if the team does; **consistency matters more
than which convention**.

## Housekeeping

```bash
git config --global user.name "Ram"
git config --global user.email "ram@example.com"
git config --global core.editor "code --wait"
git config --global init.defaultBranch main
git config --global pull.rebase true          # ← avoids merge commits on every pull
git config --global rerere.enabled true       # remember conflict resolutions (Day 087)
git config --global diff.algorithm histogram  # better diffs than the default
git config --global fetch.prune true          # drop deleted remote branches
```

`pull.rebase true` and `rerere.enabled true` are the two most under-used settings in Git; the first
keeps history linear, the second stops you resolving the same conflict repeatedly during a long
rebase.

## Useful history commands

```bash
git log --oneline --graph --decorate --all      # ← alias this. The mental picture.
git log -p file.java                            # every diff touching a file
git log --follow file.java                      # across renames (a heuristic — Day 084)
git log -S "functionName"                       # commits that ADDED or REMOVED that string
git log -G "regex"                              # commits whose diff matches
git log --author="Ram" --since="2 weeks ago"
git log main..feature                           # in feature, not in main
git blame -L 40,60 file.java
git blame -w -C file.java                       # ignore whitespace, detect moved code
git shortlog -sn                                # commits per author
```

**`git log -S` is the "pickaxe" and it is the best-kept secret here.** "When was this constant
introduced?" "Who deleted this call?" — one command, straight to the commit, and then to the message
explaining why.

`git blame -w -C` is the version that survives reformatting: without those flags, a whitespace change
or a file split attributes every line to whoever reformatted it.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Committing everything with `git add -A` blindly | Unreviewable commits; accidental secrets |
| Editing after `git add` | Committing the older content |
| "fix", "updates", "wip" as messages | History with no information |
| Describing *what* rather than *why* | Duplicates the diff, loses the reason |
| Mixing refactoring with behaviour change | Unreviewable |
| Commits that do not build | Bisect returns the wrong commit |
| Adding to `.gitignore` for a tracked file | No effect — needs `git rm --cached` |
| Rewriting history as secret "remediation" | The secret is already compromised — rotate |
| Using stash as long-term storage | Unlabelled mystery, eventually deleted |
| `git reset --hard` reflexively | The one command that destroys uncommitted work |

## Interview questions

**Q: Why does Git have a staging area?**
Because what you edited and what should be one commit are different. It lets you build a coherent
change out of a messy working tree, and reading each hunk as you stage is a free self-review.

**Q: What makes a good commit?**
One logical change, building and passing tests, refactoring separated from behaviour change, and a
message whose body explains *why* — because the diff already shows what.

**Q: How do you undo a commit that has been pushed?**
`git revert` — it creates a new commit that inverts the change, so shared history is not rewritten.
`reset` is for local commits only.

**Q: A secret was committed and pushed. What do you do?**
Rotate the credential first — it is compromised regardless. Then purge history with `git filter-repo`
or BFG, force-push, have everyone re-clone, and add a secret-scanning pre-commit hook plus a
server-side scan.

**Q: Why does adding a file to `.gitignore` not always work?**
`.gitignore` only affects untracked files. An already-tracked file needs `git rm --cached`.

**Q: How do you find when a line of code was introduced?**
`git log -S "text"` to find the commit that added or removed it, or `git blame -w -C` for
attribution that survives reformatting and code movement.

## Mini task

1. Make four unrelated changes in one file, then use `git add -p` to commit them as three separate
   commits — using `s` to split and `e` to edit a hunk at least once.
2. Stage a file, edit it further, and confirm with `git diff` vs `git diff --staged` that the commit
   would capture the earlier version.
3. Practise every row of the undo table on a scratch repository until you do not have to look it up.
4. Write a `.gitignore` for a Java project, then track a file it should ignore and fix it with
   `git rm --cached`. Use `git check-ignore -v` to confirm.
5. Install the pre-commit secret hook above and prove it blocks a fake AWS key.
6. Take five of your own past commit messages and rewrite them properly. Note which were impossible
   to rewrite because you no longer remember why.
7. Run `git log -S` for a string in any repository you have and find the commit that introduced it.
8. Run `git blame` on a file, then `git blame -w -C`, and compare the attributions.
9. Enable `pull.rebase`, `rerere.enabled` and `fetch.prune` globally.

## 🎙️ Articulation drill

Two minutes: **"What does a good commit history look like, and why does it matter?"**

Atomic commits that build, refactoring separated from behaviour, messages explaining why. Then the
payoff: bisect works, revert works, blame teaches instead of accuses, and review is possible at all.
Close with the six-months test — history is written for the person who has to change this code
without you.
