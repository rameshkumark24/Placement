# Day 282 🏗️

**P-282** · The container image — small, layered, non-root, and sized correctly

**Time:** 3 hrs · **Mode:** BUILD

> Day 129B built Docker layer caching and the JVM-in-a-container problem. Day 144 covered fat jars
> and layered extraction. **Today you apply both to your own image, and measure the result.**
>
> **⭐ The three numbers to move today: image size, push time on a code-only change, and the heap the
> JVM actually chooses inside the container.** The third is the one that causes outages.

# Part 1 — ⭐ Layering, and the number it changes

**⭐ Measure first.** Build, change one line of Java, rebuild, and record the pushed layer size.

```
❌ COPY target/app.jar app.jar     ⭐ one 60 MB layer; EVERY code change re-pushes ALL of it
```

**Day 144's fix:**

```
⭐ java -Djarmode=tools -jar app.jar extract --layers --launcher
⭐ COPY dependencies/ → spring-boot-loader/ → snapshot-dependencies/ → application/
⭐ ENTRYPOINT ["java","org.springframework.boot.loader.launch.JarLauncher"]
```

**⭐ Order matters: least-frequently-changed first** (Day 129B). Dependencies change monthly;
`application/` changes every commit.

**⭐ Expected result: a code-only change pushes under a megabyte instead of sixty.** Across a team
pushing thirty times a day that is the difference between CI that feels instant and CI that does not.

> ⚠️ **⭐ Boot 3.3+ uses `-Djarmode=tools extract`, not `layertools`** — most blog posts and copied
> Dockerfiles still show the old form (Day 144).

**⭐ Verify the caching actually works:**

```
⭐ Change one line of Java → rebuild → ⭐ only the application layer should be rebuilt
⭐ Change pom.xml         → rebuild → ⭐ the dependency layer rebuilds too
```

# Part 2 — ⭐⭐ The JVM in a container — the settings that prevent an outage

```
⭐ ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 \
      -XX:+ExitOnOutOfMemoryError \
      -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps"
```

| Flag | ⭐ The failure it prevents |
|---|---|
| ⭐ **`MaxRAMPercentage=75`** | ⭐ the JVM sizes the heap from the *host's* RAM, exceeds the container limit, and is **OOM-killed** |
| ⭐ **`ExitOnOutOfMemoryError`** | ⭐ after an OOM the JVM is in an undefined state — ⭐ **dying lets the orchestrator replace it; limping corrupts data** |
| ⭐ **`HeapDumpOnOutOfMemoryError`** to a **volume** | ⭐ you get exactly one chance to capture the evidence, and it is at the moment of failure |

**⭐ Prove it today rather than trusting it:**

```
⭐ docker run -m 512m ... and print Runtime.getRuntime().maxMemory()
⭐ Without the flag: the JVM may size from host RAM → ⭐ OOM-kill under load
⭐ With it: ~384 MB, ⭐ leaving room for metaspace, thread stacks and native memory
```

**⭐ And the 25% that is not heap is not waste.** Metaspace, code cache, thread stacks (1 MB each —
so 200 Tomcat threads is 200 MB), direct byte buffers and the GC's own structures all live there.
**A container sized with `MaxRAMPercentage=95` gets OOM-killed even though the heap never fills**,
which is a genuinely confusing failure.

**⭐ Also mount `/dumps`**, or the heap dump dies with the container that produced it — which is the
one moment you needed it.

## ⭐ Base image and size

| Choice | Note |
|---|---|
| ⭐ **JRE, not JDK** | ⭐ roughly half the size; you are not compiling in production |
| `-alpine` | smallest — ⭐ musl libc; verify your native dependencies |
| ⭐ **Distroless** | ⭐ **no shell, no package manager** — a much smaller attack surface |
| ⭐ **`jlink` custom runtime** | ⭐ smallest JRE possible; a real optimisation for a known module set |

**⭐ Distroless is the security-minded default**: no shell means an attacker who achieves code
execution has no `sh`, no `curl` and no package manager. **The cost is that you cannot `exec` into it
to debug** — which is a trade worth making deliberately, and worth saying you made.

# Part 3 — ⭐ Security of the image

```
⭐ USER 1000:1000                    ← ⭐ NEVER root
⭐ A read-only root filesystem, with a writable /tmp and /dumps
⭐ Drop all Linux capabilities
⭐ No secrets in the image — ⭐ not in ENV, not in layers, ⭐ not in the build history
```

**⭐ The build-history point catches people**: a secret passed as a build argument is visible in
`docker history` **even if a later layer removes the file.** Use BuildKit secret mounts, or inject at
runtime (Day 142).

**⭐ Non-root matters because a container escape from a root process is root on the node.** It is one
line and it is on every hardening checklist for a reason.

## ⭐ Scan it, and pin it

```
⭐ trivy image myapp:latest --severity HIGH,CRITICAL   ← ⭐ IN CI, failing the build
⭐ Pin the base image by DIGEST, not by tag
⭐ Rebuild regularly — ⭐ a base image accumulates CVEs even if your code does not change
```

**⭐ That last point is the one people miss.** Your image was clean when built; three months later the
base has fourteen known vulnerabilities and nothing in your repository changed. **A scheduled rebuild
is part of the deployment strategy**, not an optimisation — and Day 185's item 38 said most breaches
are known CVEs.

**⭐ Generate an SBOM** (Day 100A) with `syft` and attach it to the image. **"I can tell you every
component in my production image" is a strong answer**, and it takes one CI step.

# Part 4 — ⭐ Startup, health, and the alternative you did not take

## ⭐ Startup time — measured, then decided

```
⭐ Baseline                          2–4 s
⭐ + CDS (-XX:SharedArchiveFile)     ⭐ 20–35% faster — ⭐ a build flag, low risk
⭐ + Spring AOT (process-aot)        15–30% faster
⭐ GraalVM native                    ~50 ms — ⭐ 5–10 min builds, reflection constraints
```

**⭐ Day 144's ranking stands: CDS is the pragmatic win.** For a long-running service, native's
transformation of startup buys almost nothing amortised over a week of uptime, and costs build time
and runtime dynamism.

**⭐ Measure your startup and write the number down.** It determines your startup-probe threshold, and
"my service starts in 2.8 seconds so the startup probe allows 60" is a better answer than a copied
number.

## ⭐ Health and shutdown in the container

```
⭐ Liveness  → /actuator/health/liveness    ⭐ NO dependency checks (Day 128)
⭐ Readiness → /actuator/health/readiness   ⭐ dependencies here
⭐ Startup   → generous failureThreshold    ⭐ a JVM takes seconds
⭐ server.shutdown: graceful + a pre-stop delay   (Day 265)
```

**⭐ Test the shutdown behaviour in the container**: send `SIGTERM` during a load test and confirm
in-flight requests complete rather than being dropped.

## ⭐ Buildpacks — the alternative worth naming

```
⭐ ./mvnw spring-boot:build-image
```

**⭐ Layered automatically, non-root, a memory calculator that sizes the heap from the container
limit, and an SBOM — with no Dockerfile.** For a team that does not want to own Dockerfile
maintenance it is a genuinely good default (Day 144).

**⭐ You should know both and be able to say why you chose yours.** "Buildpacks give me all of this
for free; I wrote a Dockerfile because I wanted distroless and control over the base image" is a good
answer. So is the reverse.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Unlayered `COPY app.jar` | every commit re-pushes 60 MB |
| ⭐ `layertools` on Boot 3.3+ | build fails, or silently uses an old path |
| ⭐⭐ **No `MaxRAMPercentage`** | ⭐⭐ **OOM-killed under load** |
| ⭐ `MaxRAMPercentage` too high (95) | killed even though the heap never fills |
| ⭐ No `ExitOnOutOfMemoryError` | a broken JVM keeps serving and corrupting |
| Heap dump path inside the container | the evidence dies with the container |
| JDK base image | double the size for no reason |
| ⭐ Running as root | a container escape is root on the node |
| ⭐ Secrets in build args | ⭐ visible in `docker history` forever |
| Unpinned base image | reproducibility gone |
| ⭐ **Never rebuilding** | ⭐ CVEs accumulate with no code change |
| No image scan in CI | Day 185's item 38 |
| A copied startup-probe threshold | either too short or masking a real regression |
| Native images for a long-running service | build and reflection cost for unneeded startup |

## ⭐ Self-review

- [ ] ⭐ **Layered image**; ⭐ a code change pushes **under a megabyte** — measured
- [ ] ⭐ `MaxRAMPercentage`, `ExitOnOutOfMemoryError`, `HeapDumpOnOutOfMemoryError` to a **mounted
      volume**
- [ ] ⭐ **Heap size verified under `-m 512m`**
- [ ] JRE or distroless base; ⭐ **pinned by digest**
- [ ] ⭐ **Non-root**; read-only root filesystem; capabilities dropped
- [ ] ⭐ **No secrets in ENV, layers or build history**
- [ ] ⭐ **Trivy in CI failing on HIGH/CRITICAL**; ⭐ an SBOM generated
- [ ] ⭐ A **scheduled rebuild** for base-image CVEs
- [ ] ⭐ **Startup measured**; the probe threshold derived from it
- [ ] Probes split correctly; graceful shutdown **tested under load in the container**
- [ ] ⭐ The Dockerfile-versus-buildpacks choice **written down**

## 🎤 Defence questions

1. **⭐ How big is your image, and what does a code change push?**
2. **⭐ What heap does your JVM choose in a 512 MB container, and why?**
3. **⭐ What happens on an OutOfMemoryError, and why is dying the right behaviour?**
4. **⭐ Why non-root, and why distroless?**
5. **⭐ Your image was clean three months ago. Is it clean now — and how do you know?**
6. **⭐ How long does your service take to start, and how does that set your probe?**
7. **⭐ Why a Dockerfile rather than buildpacks?**
8. **⭐ Where would a secret leak in a container build?**

## ✅ Done when

- ⭐ The layered push size is measured and small
- ⭐ The heap-in-container behaviour is verified
- ⭐ Trivy is green in CI and a scheduled rebuild exists
