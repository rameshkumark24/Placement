# Day 324

**L-324** · Vertical vs horizontal scaling — and what "stateless" really means

**Time:** 3 hrs · **Mode:** NEW

> **⭐ "Just add more servers" is only true for services that hold nothing. Most services hold
> something, and the something is why horizontal scaling fails in practice.**
>
> Today: when a bigger machine is the correct answer, the precise definition of stateless, where the
> state actually goes — and the autoscaling failure that takes down the database you were protecting.

---

# Part 1 — ⭐ Vertical scaling, defended

**⭐ The unfashionable answer is often right, and being able to argue for it is a differentiator.**

| ⭐ Vertical wins on | ⭐ Detail |
|---|---|
| ⭐ **Simplicity** | ⭐ **no distribution, no consistency problems, no partial failure** |
| ⭐ **Latency** | ⭐ an in-process call beats a network hop by four orders of magnitude |
| ⭐ **Transactions** | ⭐ **one machine means real ACID, not a saga** |
| Operations | one thing to monitor, back up, patch |
| ⭐ **Speed of delivery** | ⭐ you ship features instead of infrastructure |

| ⭐ Vertical loses on | ⭐ Detail |
|---|---|
| ⭐ **A hard ceiling** | ⭐ the largest instance exists; you will meet it |
| ⭐⭐ **Superlinear cost** | ⭐⭐ **2× the machine is often 3–4× the price** |
| ⭐ **Single point of failure** | ⭐ **the real objection — not the ceiling** |
| ⭐ Downtime to resize | ⭐ usually a restart |

> **⭐ The honest framing: the modern ceiling is high.** A large cloud instance offers hundreds of
> cores and terabytes of RAM. **Most systems that adopted distributed architectures did not need to,
> and the availability argument — not the capacity one — is usually the real reason to go
> horizontal.**

**⭐ The scaling ladder — say this before reaching for a distributed answer:**

```
⭐ 1. Fix the query / add the index      ⭐ (Days 190–192) — usually 10–100×, for a day's work
⭐ 2. Cache                              ⭐ (Day 326) — usually another 10×
⭐ 3. Bigger machine                     ⭐ cheap, immediate, buys a year
⭐ 4. Read replicas                      ⭐ (Day 328) — if reads dominate
⭐ 5. Partition within one machine       ⭐ (Day 200)
⭐ 6. Shard                              ⭐ (Day 329) — ⭐ LAST, and irreversible in practice
```

# Part 2 — ⭐⭐ What "stateless" actually means

> **⭐ Stateless does not mean the service has no data. It means no request depends on which instance
> handles it.**

**⭐ Five kinds of hidden state that break horizontal scaling**, and every one appears in real code:

| Hidden state | ⭐ Symptom | ⭐ Where it must go |
|---|---|---|
| ⭐ **In-memory sessions** | ⭐ **log in, then log out at random** | ⭐ Redis, or a signed token (Day 173) |
| ⭐ **Local file uploads** | ⭐ "file not found" on a later request | ⭐ **object storage** (Day 327) |
| ⭐ **In-process caches** | ⭐ **stale reads on some instances only — the hardest to debug** | shared cache, or accept + bound TTL |
| ⭐ **Scheduled jobs on every node** | ⭐ **the job runs N times** | ⭐ a lock or a leader (Day 178) |
| ⭐ **In-memory counters / rate limiters** | ⭐ **the limit is N× what you configured** (Day 314) | shared store |
| ⭐ WebSocket connections | ⭐ **inherently sticky — a message reaches the wrong node** | ⭐ a pub/sub backplane (Day 180) |

⚠️ **The in-process cache is the subtle one.** It usually *works*, which is why it survives review —
until a user updates something, refreshes, hits a different instance and sees the old value. **The
bug is intermittent and correlated with load-balancer behaviour**, which makes it very expensive to
diagnose.

## ⭐ Sticky sessions — why they are a trap

| ⭐ Problem | ⭐ Consequence |
|---|---|
| ⭐ **An instance dies, its users lose everything** | ⭐ you have distributed the outage, not removed it |
| ⭐ **Load becomes uneven** | ⭐ long-lived sessions pile onto whichever node got them |
| ⭐ **Deploys are disruptive** | ⭐ **every restart logs people out** |
| Autoscaling barely helps | new instances get only new sessions |

> **⭐ Sticky sessions are a way to postpone making a service stateless while getting most of the
> disadvantages of both.** They are defensible for WebSockets, where the connection genuinely lives
> on one node — **and even there, the messages need a backplane.**

## ⭐ Where the state goes

```
⭐ Session   → Redis (shared) or a signed JWT (nowhere)   ⭐ Day 172's trade-off, at scale
⭐ Files     → object storage, via presigned URLs         ⭐ Day 327
⭐ Cache     → Redis; local caches only with short TTLs and no correctness dependence
⭐ Jobs      → a scheduler with locking (ShedLock) or leader election  ⭐ Day 178
⭐ Counters  → Redis INCR or the database                 ⭐ Day 314
⭐ Sockets   → a pub/sub backplane                        ⭐ Day 180
```

# Part 3 — ⭐ Scaling reads, then writes

| ⭐ Reads | ⭐ Writes |
|---|---|
| ⭐ **Easy** — cache, then replicas | ⭐ **hard — one leader per key, always** |
| Adding replicas is cheap and reversible | ⭐ sharding is expensive and effectively permanent |
| ⭐ Cost: replication lag (Day 328) | ⭐ cost: cross-shard queries and transactions (Day 329) |

> **⭐ The line that frames every scaling discussion: reads scale by adding copies; writes scale only
> by splitting the data.** Copies are cheap and reversible; splits are neither. **Which is why the
> read:write ratio (Day 323) is the first question.**

⚠️ **And the wall is almost always the database.** Stateless application servers scale trivially — you
add instances. **The interesting question is never "how do I add app servers", it is "what happens to
the database when I do", and the answer is usually the next section.**

# Part 4 — ⭐⭐ Autoscaling, and the failure it causes

```
⭐ Traffic spikes → autoscaler adds 40 instances
⭐ Each instance opens a pool of 20 connections
⭐ ⇒ ⭐⭐ 800 connections at a database sized for 200
⭐ ⇒ ⭐⭐ THE DATABASE FALLS OVER — because you scaled the app tier
```

> **⭐ This is Day 156's connection-pool arithmetic at fleet scale, and it is one of the most common
> real production outages.** Pool size must be sized **fleet-wide**: `max instances × pool size ≤
> database capacity`, or a connection proxy (PgBouncer, Day 197) must sit in between.

| ⭐ Autoscaling hazard | ⭐ Mitigation |
|---|---|
| ⭐ **Connection multiplication** | ⭐ **fleet-wide pool budget, or PgBouncer** |
| ⭐ **Cold start** | ⭐ JVM warm-up means a new instance is slow for 30–60 s — **pre-warm, or scale early** |
| ⭐ Scaling on the wrong metric | ⭐ **CPU misses I/O-bound saturation — scale on latency or queue depth** |
| ⭐ **Flapping** | ⭐ scale out fast, scale in slowly; cooldowns |
| ⭐ Scale-in mid-request | ⭐ graceful shutdown + connection draining (Day 286) |
| ⭐ **The spike outruns the autoscaler** | ⭐⭐ **provisioning takes minutes; a flash sale takes seconds — pre-scale for known events** |
| Downstream is not elastic | ⭐ you scale into a fixed dependency and DDoS it |

**⭐ The last row is the general principle worth stating: autoscaling one tier pushes load onto the
next.** If the next tier is a database, a third-party API or a legacy system, **you have converted a
front-end slowdown into a back-end outage.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Distributing before indexing and caching | ⭐ **skipping the 100× wins for the 2× one** |
| ⭐ Believing vertical scaling is obsolete | ⭐ modern instances are enormous; the real argument is availability |
| ⭐ In-memory sessions behind a load balancer | ⭐ random logouts |
| ⭐ Local file storage | uploads that vanish |
| ⭐ **In-process caches with correctness assumptions** | ⭐ **intermittent stale reads, very hard to diagnose** |
| Scheduled jobs on every instance | the job runs N times (Day 178) |
| ⭐ In-memory rate limits across N instances | ⭐ the limit is N× the configured one |
| ⭐ Sticky sessions as the scaling plan | ⭐ uneven load, disruptive deploys, no failure isolation |
| ⭐⭐ **Pool size chosen per instance** | ⭐⭐ **autoscaling kills the database** |
| Scaling on CPU for I/O-bound work | it never triggers, then everything times out |
| Aggressive scale-in | flapping, and requests killed mid-flight |
| ⭐ Assuming autoscaling handles a flash sale | ⭐ provisioning is minutes; the spike is seconds |

## Interview questions

**Q: Vertical or horizontal?**
Vertical first, usually — modern instances are huge, and it buys a year of runway for a day of work
with no distributed-systems cost. I go horizontal for availability rather than capacity: a single
machine is a single point of failure and needs downtime to resize. And before either I would index,
cache and add read replicas, because those are ten-to-hundred-times wins and sharding is neither
cheap nor reversible.

**Q: What does stateless actually mean?**
That no request depends on which instance serves it. Not that the service holds no data — it means no
in-memory sessions, no local files, no in-process cache anything depends on for correctness, no
per-instance counters, and no scheduled jobs that assume they are the only runner. Each of those has
a specific home: Redis or a token, object storage, a shared cache, a shared counter, a lock or leader
election.

**Q: What is wrong with sticky sessions?**
They give you most of the downsides of stateful and most of the complexity of stateless. An instance
dying takes its users' state with it, load becomes uneven because long sessions accumulate, and every
deploy logs people out. They are defensible for WebSockets, where the connection genuinely lives on
one node — but even there you need a pub/sub backplane so a message can reach a user connected
elsewhere.

**Q: You autoscale from ten instances to fifty and the database dies. Why?**
Connection pools multiply. Fifty instances at twenty connections each is a thousand connections
against a database sized for two hundred, so you scaled the tier that was fine and destroyed the tier
that was the constraint. Pool sizes have to be budgeted fleet-wide against database capacity, or you
put a proxy like PgBouncer in between. The general form is that autoscaling one tier pushes load onto
the next, and the next is often not elastic.

**Q: Which metric do you autoscale on?**
Not CPU by default — an I/O-bound service saturates on threads and connections while CPU looks idle,
so it never triggers until everything is already timing out. Request latency or queue depth reflects
the actual experience. And I scale out quickly but in slowly, with cooldowns, because flapping is
worse than being slightly over-provisioned.

## Mini task

1. **Audit your flagship for the five kinds of hidden state.** For each found, write where it should
   live and what breaks today with two instances.
2. ⭐ **Run two instances behind a load balancer** with in-memory sessions and reproduce the random
   logout. Move sessions to Redis and confirm it stops.
3. Add an in-process cache, update a record through instance A, read from B, and **reproduce the
   stale read.** Note how easy it would be to miss in review.
4. ⭐ Run a `@Scheduled` job on three instances and **watch it fire three times.** Add ShedLock.
5. Run your rate limiter on three instances and **measure the effective limit.**
6. ⭐ **Compute your fleet-wide connection budget**: max instances × pool size. Compare with
   `max_connections`. **If it exceeds it, you have this outage waiting.**
7. Autoscale on CPU during an I/O-bound load test and **watch it never trigger** while latency
   collapses. Switch to latency-based scaling.
8. ⭐ Time a **cold start** from launch to full throughput. **That number is how far ahead of a spike
   you must scale.**

## 🎙️ Articulation drill

**Two minutes:** *"Traffic is going to grow 10×. What do you do?"*

**⭐ The marker: you go up the ladder, not straight to distribution.** Measure first, then indexes and
queries, then caching, then a bigger machine, then replicas — **and only then discuss sharding, with
its cost named.** Then, unprompted: *"and I'd check the fleet-wide connection budget before adding
instances, because that is how scaling the app tier takes down the database."*

**⭐ Reaching for sharding in the first fifteen seconds is the answer that fails**, because the
follow-up — "what did you try first?" — has no good ending.
