# Part 1 — Generics, against the ones you know

```typescript
// ① identity over a container — ⭐ the api() wrapper from Day 217
async function api<T>(path: string, opts?: Options): Promise<T> { ... }
const users = await api<User[]>("/users");     // ⭐ users: User[]

// ② constrained — ⭐ <T extends HasId> is `<T extends HasId>` in Java too
function byId<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find(i => i.id === id);         // ⭐ returns T, not a widened type
}

// ③ ⭐⭐ keyof — NO JAVA EQUIVALENT, and genuinely useful
function sortBy<T, K extends keyof T>(items: T[], key: K): T[] {
  return [...items].sort((a, b) => (a[key] > b[key] ? 1 : -1));
}
sortBy(users, "name");    // ✅
sortBy(users, "nmae");    // ⭐⭐ compile error — the typo is caught

// ④ the built-ins — ⭐ used constantly, written never
type Draft = Partial<User>;              // all fields optional
type Card  = Pick<User, "id" | "name">;  // subset
type Safe  = Omit<User, "passwordHash">; // ⭐⭐ your DTO, derived not rewritten
```

| Java | TypeScript |
|---|---|
| `<T>` | `<T>` |
| `<T extends Number>` | `<T extends number>` |
| `? extends` / `? super` | ⭐ variance is inferred; you rarely write it |
| ⭐ a hand-written `UserSummaryDto` | ⭐⭐ `Pick<User, "id" \| "name">` — **derived, so it cannot drift** |
| — | ⭐⭐ `keyof T` — a checked field name, no reflection |

> ⭐ **`api<User[]>("/users")` is a lie you are choosing to tell.** Nothing verified the response is
> `User[]`; you asserted it — an unchecked cast. That is fine *only* if the boundary validates.

# Part 2 — Narrowing

```typescript
// ⭐ the four that work
if (typeof x === "string") ...          // ⭐ primitives
if (x instanceof ApiError) ...          // ⭐ real classes — this DOES work
if ("email" in user) ...                // ⭐ property presence
if (r.status === "success") ...         // ⭐⭐ discriminated union — the best one

// ⭐ the custom guard — your own `instanceof` for a shape
function isUser(x: unknown): x is User {          // ⭐⭐ "x is User" = the guard
  return typeof x === "object" && x !== null
      && "id" in x && typeof (x as any).id === "string";
}
```

```
⭐⭐ THE TRAP: NARROWING IS FORGOTTEN WHEN THE VALUE CAN CHANGE

⭐   if (user.email) {
⭐     await save();
⭐     send(user.email);   // ⭐⭐ STILL NARROWED (user is const)
⭐   }
⭐   ⭐ BUT if `user` is a `let` reassigned anywhere, or a property of
⭐     a mutable object captured in a closure, TS conservatively
⭐     widens it back — ⭐⭐ IT CANNOT PROVE NOBODY MUTATED IT.
⭐   ⇒ ⭐ COPY TO A CONST, WHICH IS THE `final` YOU WOULD HAVE WRITTEN:
⭐     const email = user.email;
⭐     if (!email) return;
⭐     ... email is string from here, unconditionally.
```

> ⭐ **`if (!x) return;` early beats nesting** — it narrows for the whole remaining method, and it is
> the same guard-clause discipline you already use to avoid arrow code.

# Part 3 — ⭐⭐ The validated boundary

Types are erased (Day 218), so a `User` annotation on a fetch response is an assumption. **Validate
where data enters, and only there.**

```typescript
import { z } from "zod";

// ⭐⭐ ONE definition produces BOTH the runtime check and the static type
const User = z.object({
  id: z.string().uuid(),
  name: z.string(),
  email: z.string().email().nullable(),    // ⭐ null from the wire (Day 215)
  role: z.enum(["admin", "user"]),
  createdAt: z.string().datetime(),
});
type User = z.infer<typeof User>;          // ⭐ the static type, derived

export async function getUsers(): Promise<User[]> {
  const raw = await api("/users");         // ⭐ unknown, honestly
  return z.array(User).parse(raw);         // ⭐⭐ THROWS if the API drifted
}
```

```java
// ⭐ you already do exactly this, on the other side of the wire
@PostMapping("/users")
User create(@Valid @RequestBody CreateUserDto dto) { ... }
//          ⭐⭐ VALIDATE AT THE EDGE. TRUST THE TYPE INSIDE.
```

```
⭐⭐ WHERE TO VALIDATE, AND WHERE NOT TO

⭐   ✅ VALIDATE  · API responses          · URL params & query strings
⭐               · localStorage reads     · websocket frames
⭐               · anything from a form    · env vars at startup
⭐   ❌ DON'T     · between your own components — ⭐⭐ THAT IS WHAT THE
⭐                 TYPES ARE FOR. You do not re-run @Valid between
⭐                 two service methods either.
```

| ⭐ Why validate a response you wrote yourself | |
|---|---|
| **The server deploys separately** | ⭐⭐ The client in a user's tab is an *old* client. Version skew is not hypothetical, it is Tuesday. |
| **The failure becomes loud** | ⭐ `users[3].email: expected string, got null` beats `undefined` on screen — Day 455's instinct |
| **You get the type free** | ⭐ `z.infer` means one source, no drift between checker and annotation |

> ⭐ **Cost, honestly:** a schema per response shape, a few KB, and parse time on large lists. **Worth
> it at the boundary, wasteful anywhere else.** Day 246 generates these from OpenAPI so you are not
> hand-maintaining them.

# Part 4 — The three errors that look terrifying

| ⭐ Error | What it actually means | Fix |
|---|---|---|
| `Type 'string \| undefined' is not assignable to type 'string'` | ⭐⭐ **The correct error** — the compiler found your NPE before runtime. Something may be absent and you assumed it isn't. | Narrow it. **Do not `!` it away.** |
| `Property 'x' does not exist on type 'never'` | ⭐ You narrowed a union to nothing — usually an impossible `case`, or an exhaustive switch you added a branch to | Read the union; a branch is impossible or the discriminant is wrong |
| `Types of property 'x' are incompatible… (100 lines)` | ⭐ Two big object types differ. **Read the LAST line first** — the nested leaf is the real mismatch | Compare the leaf types; ignore the wrapper noise |

```typescript
// ⭐⭐ the non-null assertion is a lie to the compiler
const el = document.getElementById("root")!;   // ⭐ "trust me"
// ⇒ ⭐⭐ if it's null you get a runtime crash with NO type error.
//    It is `@SuppressWarnings` plus a cast, in one character.
const el = document.getElementById("root");
if (!el) throw new Error("mount point #root missing");
```

> ⭐ **`!` and `as` are the two escape hatches, and both are you overruling the compiler.** Grep for
> them in review, exactly as you would grep for `@SuppressWarnings`. Each should carry a comment
> saying why you are more certain than the checker.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you keep types honest when data comes from outside?"**

State the principle first, in terms you already own. **It's `@Valid` on a `@RequestBody`, applied to
the other end of the wire. Types are erased, so they can only lie at the boundary — inside, the
compiler enforced them. So I validate once where data enters and never again.**

Make it concrete. **One Zod schema per response shape gives me the runtime check and the static type
from a single definition, so they can't drift. If the API changes I get `users[3].email: expected
string, got null` instead of the word "undefined" rendered to a customer — turning a quiet failure into
a loud one, which is the same instinct I apply on the server.**

Pre-empt the objection, since it is the interesting part. **People ask why I'd validate a response from
an API I wrote. Because the server deploys separately — the client in a user's tab is an old client,
and version skew isn't hypothetical. Without that check, `const u: User = await res.json()` is a cast
that can never fail and can always be wrong.**

Close on the parts that are better than Java. **`Omit<User, "passwordHash">` gives me a response DTO
derived from the model rather than a second class I hand-maintain — so it can't drift when a field is
added. And `keyof` gives me a compile-checked field name without reflection, which is something I
genuinely miss going back the other way.**
