# Day 349

**L-349** · Design 5 — a web crawler

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ A crawler is a queue with a politeness problem.**
>
> Fetching pages is trivial. **The design is entirely in the frontier — the structure that decides
> what to fetch next while never hammering one server, never crawling the same page twice, and never
> falling into an infinite URL space someone generated by accident.**

---

# Part 1 — ⭐ Requirements and estimates

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| Crawl from seed URLs, follow links | ⭐⭐ **politeness — never overload a host** |
| Store raw pages for downstream use | ⭐ **robots.txt respected, always** |
| ⭐ **Recrawl for freshness** | ⭐ extensible: HTML today, images later |
| ⭐ Deduplicate URLs and content | ⭐ **resumable after a crash** |
| Prioritise important pages | scale to billions of pages |

```
⭐ ESTIMATE
⭐   1B pages/month ⇒ 1B ÷ 2.5M s ⇒ ⭐ ~400 pages/s sustained ⇒ ⭐ peak ~1,000/s
⭐   500 KB/page ⇒ ⭐⭐ 500 TB/month raw ⇒ compressed ~150 TB
⭐   ⭐ Bandwidth: 400 × 500 KB = ⭐ 200 MB/s ≈ 1.6 Gbps sustained
⭐   URLs seen: ~10B ⇒ 100 B each = 1 TB of URL state ⇒ ⭐⭐ too big for a plain in-memory set
```

> **⭐ What the numbers decided:** 400 pages/s is modest, so **this is not a throughput problem** —
> it is a **coordination and storage** problem. **1 TB of URL state is what forces a Bloom filter.**
> And 500 TB/month means object storage (Day 327), never a database.

---

# Part 2 — ⭐ The pipeline

```
⭐ SEEDS ──► ⭐ FRONTIER ──► FETCHER ──► ⭐ CONTENT DEDUP ──► PARSER ──► LINK EXTRACTOR
⭐               ▲                          │                              │
⭐               │                          ▼                              │
⭐               │                    OBJECT STORAGE                       │
⭐               └───────── ⭐ URL DEDUP (Bloom filter) ◄──── URL NORMALISER
```

| Component | ⭐ Job |
|---|---|
| ⭐ **Frontier** | ⭐⭐ **what to fetch next — the whole design (Part 3)** |
| Fetcher | ⭐ DNS, connect, GET, with timeouts (Day 339) |
| ⭐ **URL normaliser** | ⭐ strip fragments, sort query params, lowercase host, resolve relative — **before dedup** |
| ⭐ **URL dedup** | ⭐ a Bloom filter — see below |
| ⭐ Content dedup | ⭐ **exact by hash, near-duplicate by simhash** |
| Parser / extractor | HTML → links + text |
| Storage | raw pages to object storage; metadata to a KV store |

⚠️ **Normalisation must happen before dedup, or it does nothing.**
`http://Example.com/a?b=1&c=2#top` and `http://example.com/a?c=2&b=1` are the same page and **must
hash identically** — otherwise the crawler fetches it twice and the whole dedup layer is decorative.

# Part 3 — ⭐⭐ The deep dive: the frontier

> **⭐ Two requirements pull in opposite directions.** Priority says *fetch the important page next*.
> Politeness says *do not fetch from a host you just fetched from.* **A single priority queue cannot
> satisfy both**, and that tension is the design.

## ⭐⭐ The two-tier queue (Mercator design)

```
⭐ FRONT QUEUES — PRIORITY
⭐   F1 (high) F2 F3 ... Fn (low)
⭐   A URL is placed by priority. A biased selector picks a front queue, favouring high priority.
⭐            │
⭐            ▼
⭐ BACK QUEUES — POLITENESS
⭐   B1 B2 B3 ... Bm     ⭐⭐ EACH BACK QUEUE HOLDS URLs FOR EXACTLY ONE HOST
⭐   ⭐ A host maps to exactly one back queue. ⭐ One worker per back queue.
⭐   ⭐ A min-heap of (nextAllowedTime, queueId) tells a worker which queue is due.
```

| ⭐ Why this works | |
|---|---|
| ⭐ **Front queues give priority** | important pages are selected sooner |
| ⭐⭐ **Back queues give politeness structurally** | ⭐⭐ **one host per queue, one worker per queue ⇒ requests to a host are serialised by construction** |
| ⭐ The heap gives timing | ⭐ a worker sleeps until the next host is due, rather than polling |
| ⭐ **The two concerns are decoupled** | ⭐ priority never violates politeness, and politeness never starves priority |

> **⭐ The insight worth stating: politeness is enforced by structure, not by checks.** There is no
> "have I called this host recently?" lookup — **it is impossible to have two in-flight requests to
> one host because one queue has one worker.**

**⭐ The delay itself:** `nextAllowedTime = now + k × lastResponseTime` (typically k = 10) — **so slow
servers are hit less often, automatically.** `Crawl-delay` from robots.txt overrides it where
present.

⚠️ **Politeness is per host, and a host is not a domain.** Thousands of subdomains on shared hosting
resolve to one IP; **politeness by hostname can still flatten that server.** The rigorous version
groups by resolved IP — **noticing this is a strong detail.**

## ⭐ Frontier persistence

**⭐ Ten billion URLs do not fit in memory.** The frontier is **disk-backed with an in-memory
working set**, and it must survive a restart — **a crawler that loses its frontier restarts a
month's work.**

# Part 4 — ⭐ Dedup, traps, and freshness

## ⭐⭐ URL dedup with a Bloom filter

```
⭐ 10B URLs × 100 B = 1 TB as a plain set.
⭐⭐ A Bloom filter at 1% false positives: ~10 bits per element ⇒ ⭐⭐ ~12 GB. Fits in RAM.
```

| ⭐ Property | ⭐ Consequence here |
|---|---|
| ⭐ **No false negatives** | ⭐ you never re-crawl something it says is new |
| ⭐⭐ **False positives possible** | ⭐⭐ **you skip a page you have not crawled — and that is ACCEPTABLE** |
| Cannot delete | ⭐ use a rotating or scalable variant for long-lived crawls |

> **⭐ The reason this is the right structure is the asymmetry of the error.** A false positive costs
> you one page out of a billion. **A false negative would cost a duplicate fetch, which is exactly
> what you were preventing.** Bloom filters have the error in the harmless direction — **say that,
> rather than just naming the structure.**

## ⭐ Content dedup — exact and near

| Level | ⭐ Mechanism |
|---|---|
| ⭐ **Exact** | ⭐ hash the normalised body; identical hash ⇒ skip |
| ⭐⭐ **Near-duplicate** | ⭐⭐ **simhash / shingling** — same article with a different ad, session ids in URLs, print versions |

**⭐ Near-duplicate detection matters more than exact**, because the web is full of *almost* the same
page. **Simhash produces a fingerprint where similar documents differ in few bits**, so a Hamming
distance under a threshold means "same content" — **and you compare fingerprints, not documents.**

## ⭐⭐ Crawler traps

| Trap | ⭐ Defence |
|---|---|
| ⭐ **Infinite calendars** — `/events?date=2027-01-01`, forever | ⭐ **depth limits and per-host page budgets** |
| ⭐ Session ids in URLs generating infinite variants | ⭐ normalisation strips known parameters |
| ⭐ **Deep directory recursion** — `/a/b/a/b/a/b/…` | pattern detection; a path-length cap |
| Spider traps designed to waste crawlers | ⭐ per-host quotas; anomaly alerts |
| ⭐ Enormous pages | ⭐ a size cap — **stream and abort** |

> **⭐ The general defence is a budget per host, not clever detection.** You cannot enumerate the
> ways a site can generate infinite URLs; **you can cap how much of your crawl any one host is
> allowed to consume.**

## ⭐ Freshness and DNS

| Concern | ⭐ Answer |
|---|---|
| ⭐ **Recrawl scheduling** | ⭐ estimate a change rate per page and recrawl proportionally — a news homepage hourly, an archive monthly |
| ⭐ Conditional requests | ⭐ `If-Modified-Since` / `ETag` — **a 304 costs almost nothing** (Day 102) |
| ⭐⭐ **DNS as a bottleneck** | ⭐⭐ **one lookup per host, and resolvers rate-limit you — run your own caching resolver** |
| Sitemaps | free hints about what changed |

```
⭐ MONITOR: pages/s · fetch error rate by host · frontier size · ⭐ Bloom filter fill ratio
⭐          ⭐ per-host politeness violations (should be ZERO) · trap detections · DNS latency
⭐ CUT:     JavaScript rendering, images, login-walled content, ranking
⭐ AT 10×:  ⭐ shard the frontier BY HOST across machines — ⭐ politeness stays local to a shard
```

⚠️ **Sharding by host is the only correct sharding here**, because politeness is per host: **if two
machines could hold URLs for the same host, they would need to coordinate on timing.** Hash the host
to a shard and the problem disappears — **and that is the same "keep related things in one
partition" idea as Day 331's causal consistency.**

---

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ A single priority queue | ⭐⭐ **priority and politeness cannot both be satisfied** |
| ⭐ Politeness by checking timestamps | ⭐ races; structure it instead |
| ⭐ Politeness by hostname only | ⭐ shared hosting still gets flattened |
| ⭐ Normalising after dedup | ⭐ **the dedup layer does nothing** |
| ⭐ A plain set for 10B URLs | ⭐ 1 TB of memory |
| ⭐ **No content near-dedup** | the web is mostly almost-duplicates |
| ⭐ No per-host budget | ⭐⭐ **one calendar consumes the entire crawl** |
| ⭐ Ignoring robots.txt or caching it forever | legal and ethical failure; stale rules |
| ⭐ **No DNS cache** | ⭐ resolvers throttle you; DNS becomes the bottleneck |
| A non-persistent frontier | a restart loses a month |
| Sharding by URL hash rather than host | politeness needs cross-shard coordination |
| Recrawling everything uniformly | wasted capacity on archives, stale news |

## Interview questions

**Q: What is actually hard about a crawler?**
The frontier. Fetching is trivial and four hundred pages a second is modest. The difficulty is that
priority and politeness pull in opposite directions — priority says fetch the important page next,
politeness says do not touch that host again yet — and a single queue cannot satisfy both.

**Q: How do you solve that?**
Two tiers. Front queues hold URLs by priority and a biased selector favours the important ones. Back
queues each hold URLs for exactly one host, with one worker per queue, so two simultaneous requests
to a host are structurally impossible — politeness is enforced by shape rather than by a check. A
min-heap of next-allowed times tells workers which host is due, and the delay is proportional to the
host's own response time, so slow servers are automatically hit less often.

**Q: How do you avoid crawling the same URL twice?**
Normalise first — strip fragments, sort query parameters, lowercase the host, resolve relatives —
because otherwise dedup is decorative. Then a Bloom filter rather than a set: ten billion URLs would
be a terabyte as a set and about twelve gigabytes as a filter at one percent false positives. The
error is in the harmless direction: a false positive skips one page in a billion, and there are no
false negatives, so nothing is fetched twice.

**Q: What is a crawler trap and how do you defend against one?**
Any site that generates infinite URLs — a calendar with a next-month link forever, session ids in
paths, recursive directories. You cannot enumerate the ways it happens, so the defence is a budget
rather than detection: a per-host page cap, a depth limit, a URL length cap, and normalisation that
strips known volatile parameters. Then an alert when one host consumes an unusual share of the crawl.

**Q: How would you shard this across machines?**
By host. Politeness is per host, so if two machines could hold URLs for the same host they would have
to coordinate on timing, which is exactly the coordination the back-queue structure was designed to
avoid. Hashing the host to a shard keeps politeness entirely local — the same principle as keeping
causally related data in one partition.

## Mini task

1. **Run the 45-minute framework**, timed and recorded, with **the frontier as your deep dive.**
2. ⭐ Implement the **two-tier frontier** with front queues, back queues and a due-time heap.
   **Assert zero concurrent requests to any host** across a run.
3. ⭐ Implement politeness by **timestamp checking** instead and **reproduce a race** where two workers
   hit one host.
4. Implement **URL normalisation.** Feed it fifty real-world variants of the same page and confirm
   they collapse to one.
5. ⭐ Compare a **`HashSet` vs a Bloom filter** for 10M URLs: memory and lookup time. **Measure the
   actual false-positive rate against the configured one.**
6. ⭐ Implement **simhash** and detect near-duplicates across a corpus with varying ads and session
   parameters.
7. ⭐⭐ **Build a calendar trap** (`/events?date=…` linking to the next day forever) and crawl it. Watch
   it consume everything. **Add a per-host budget and re-run.**
8. ⭐ Crawl 1,000 hosts **with and without a local DNS cache** and compare throughput.
9. Implement **conditional requests** and measure the bandwidth saved on a recrawl.
10. ⭐ Kill the crawler mid-run and **confirm it resumes from the persisted frontier** without
    re-fetching.

## 🎙️ Articulation drill

**Three minutes:** *"You need to crawl a billion pages a month. Where does the difficulty lie?"*

**⭐ The marker is that you dismiss the obvious answer.** Four hundred pages a second is a modest
fetch rate; **the difficulty is the frontier** — and then you explain the priority-versus-politeness
conflict and solve it structurally with two tiers.

**⭐ Then two details that read as experience**: politeness must be per resolved IP rather than per
hostname because of shared hosting, and **the defence against traps is a per-host budget rather than
clever detection, because you cannot enumerate the ways a site generates infinite URLs.**
