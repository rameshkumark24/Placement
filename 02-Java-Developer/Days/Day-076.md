# Part 1 — The debugger, properly

Most people know breakpoints and step-over. The features that actually save hours:

**Conditional breakpoints.** Right-click a breakpoint → condition: `order.getId().equals("ORD-88213")`.
Rather than pressing continue four thousand times, you stop on the one iteration that matters.

**Exception breakpoints.** Break when a `NullPointerException` is *thrown*, anywhere, including
inside library code. This is how you find an exception that is caught and swallowed three frames up
(Day 062) — you catch it at the throw site, before the evidence is destroyed.

**Field watchpoints.** Break when a field is read or written. The answer to "who is setting this to
null?" — a question that is otherwise a search through every assignment.

**Evaluate expression** (Alt+F8). Run arbitrary code in the paused frame: call a method, build an
object, inspect a collection with a stream. You are not limited to reading variables.

**Drop frame.** Re-execute the current method from the start. You stepped past the interesting line —
drop the frame and step again, without restarting. (Side effects already performed are not undone,
so it is not a time machine, but it is close enough to be very useful.)

**Logging breakpoints.** A breakpoint that prints and does not suspend — a `println` you did not have
to compile in, and did not have to remember to remove.

## Remote debugging

```bash
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar
```

Then "Remote JVM Debug" in your IDE pointed at port 5005. `suspend=y` waits for you to attach, which
is how you debug something that fails during startup.

⚠️ **JDWP is unauthenticated remote code execution by design.** Never expose it publicly, never leave
it on in production, and if you must use it, tunnel over SSH and bind to `localhost`. This is a real
finding in security reviews.

## Why you will still use logging

A debugger stops the world. That is fine locally and impossible for a race that appears once in ten
thousand requests, or a problem that only manifests under production load. **Concurrency bugs
frequently vanish under a debugger** because the timing changes — the "heisenbug". For those, logs,
metrics and JFR are the tools; the debugger is for deterministic, reproducible problems.

# Part 2 — The four commands

`jcmd` supersedes most of the older tools. Learn `jcmd`; recognise the rest.

```bash
jcmd                                    # list JVMs (or jps -l)
jcmd <pid> help                         # everything this JVM supports
```

## 1. Thread dumps — for a hang

```bash
jcmd <pid> Thread.print > dump1.txt
jstack <pid> > dump1.txt                          # equivalent
jcmd <pid> Thread.dump_to_file -format=json d.json  # JDK 21+, virtual-thread aware
```

**Take three, five seconds apart.** One dump tells you what threads are doing; three tell you what
they are *stuck* doing. What has not moved is your problem.

Reading one (Day 064's states, Day 071's signatures):

```
"http-nio-8080-exec-7" #61 daemon prio=5 tid=0x… nid=0x2f11 waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.acme.Cache.get(Cache.java:88)
        - waiting to lock <0x00000006c0a12345> (a com.acme.Cache)
        at com.acme.OrderService.load(OrderService.java:42)
```

| What you see | What it means |
|---|---|
| `Found one Java-level deadlock` | The JVM found it for you. Read the cycle. |
| 200 `BLOCKED` on one monitor address | Lock contention — find the one thread holding it |
| The holder is `RUNNABLE` in `socketRead0` | **A lock held across I/O** (Day 066). The classic. |
| All pool threads `WAITING` on `Future.get` | Thread starvation deadlock (Day 071) |
| Many `RUNNABLE` in the same method, high CPU | Hot loop or livelock |
| `TIMED_WAITING (parking)` on a queue | Idle workers — usually normal |

Note the JVM's *own* threads in the dump — `G1 Young RemSet Sampling`, `C2 CompilerThread`,
`VM Periodic Task` — and ignore them.

**On a container that only has stdout:** `kill -3 <pid>` sends `SIGQUIT`, and the JVM prints a thread
dump to stdout. It does **not** kill the process, despite how it looks. That is often the only way to
get a dump out of a locked-down container.

## 2. Heap dumps — for memory

```bash
jcmd <pid> GC.heap_info                                 # quick: is the heap actually full?
jcmd <pid> GC.class_histogram | head -30                # cheap: what is there, by count and bytes
jcmd <pid> GC.heap_dump /tmp/heap.hprof                 # full dump — PAUSES the JVM
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>     # older equivalent
```

Start with the **histogram** — it is cheap and often enough:

```
 num     #instances         #bytes  class name
   1:       3,201,442     512,230,720  [B                    ← byte arrays
   2:       3,200,001     102,400,032  com.acme.CachedItem   ← 3.2M of these. There it is.
   3:         890,331      21,367,944  java.lang.String
```

Three million of your own class is a lead. A `char[]`/`byte[]`/`String` top three is normal.

**The single most important flag, set on every service you deploy:**

```bash
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/app/
```

An OOM you have a dump for is a one-hour investigation. An OOM you do not is a week of guessing.
Add `-XX:+ExitOnOutOfMemoryError` if a supervisor will restart the process — a JVM limping along
after an OOM is usually in an undefined state.

Analyse with **Eclipse MAT** (free, best-in-class) or VisualVM. In MAT the workflow is:

1. **Leak Suspects report** — it is genuinely good; run it first.
2. **Dominator tree** — sorts objects by *retained* size, which is what actually keeps memory alive.
   **Shallow size is the object itself; retained size is everything that dies with it.** Retained is
   the number you want.
3. **Path to GC Roots** (excluding weak/soft references) — this answers the only question that
   matters: **what is still referencing this?**

The seven leak patterns from Day 027 all resolve here: a static collection, an unclosed resource, an
un-deregistered listener, a `ThreadLocal` on a pooled thread (Day 066A — the path to GC root will
terminate at a `Thread`), a mutable key in a `HashMap` (Day 048), a growing cache without eviction,
and a leaked class loader.

## 3. JFR — Flight Recorder, for "it is slow"

The most under-used tool in Java. Continuous, always-on profiling with **~1% overhead**, safe in
production.

```bash
# start a recording on a running JVM
jcmd <pid> JFR.start name=diag settings=profile duration=120s filename=/tmp/rec.jfr

jcmd <pid> JFR.check
jcmd <pid> JFR.dump name=diag filename=/tmp/now.jfr
jcmd <pid> JFR.stop name=diag

# or from startup, with a rolling buffer
java -XX:StartFlightRecording=disk=true,maxsize=200M,maxage=6h,settings=profile -jar app.jar
```

Open the `.jfr` in **JDK Mission Control**. What it answers, none of which a thread dump can:

| Question | Where to look |
|---|---|
| Which methods use the CPU? | Method Profiling — flame graph |
| What is allocating so much? | TLAB allocation — by class **and stack trace** |
| Why are GC pauses long? | Garbage Collections — pause durations and causes |
| Which locks are contended? | Java Monitor Blocked — with the stack |
| Which queries are slow? | Socket/File I/O events, JDBC events |
| Any exceptions being thrown and swallowed? | Exception events |

That last row is quietly excellent: JFR records exceptions **even when your code swallows them**
(Day 062), so an empty catch block that is silently eating a failure a thousand times a second shows
up here and nowhere else.

The **allocation profile** is the one that most often surprises people. The commonest performance
problem in Java services is not slow algorithms — it is allocation rate driving GC, and JFR tells you
the exact line allocating.

## 4. GC and the rest

```bash
jstat -gcutil <pid> 1000 20      # GC stats every second, 20 times
jcmd <pid> VM.flags              # every flag in effect, including ergonomic defaults
jcmd <pid> VM.system_properties
jcmd <pid> VM.native_memory summary   # requires -XX:NativeMemoryTracking=summary
jcmd <pid> GC.run                # suggest a GC (for testing only)
```

`jstat -gcutil` output: `S0 S1 E O M CCS YGC YGCT FGC FGCT GCT`. The diagnosis:

> **Old generation (`O`) near 100% with `FGC` climbing and the heap not shrinking after a full GC =
> you are not "under-provisioned", you have a leak.** GC is running constantly and freeing nothing.

`VM.native_memory` is how you explain the gap between RSS and `-Xmx` (Day 071's B-15) — metaspace,
thread stacks, code cache, direct buffers, GC structures.

## Code to type — break it three ways, then diagnose

```java
import java.util.*;
import java.util.concurrent.*;

public class DiagnoseMe {

    static final Map<String, byte[]> LEAK = new HashMap<>();     // 1. static, never evicted
    static final Object LOCK_A = new Object(), LOCK_B = new Object();

    public static void main(String[] args) throws Exception {
        String mode = args.length > 0 ? args[0] : "leak";
        System.out.println("pid " + ProcessHandle.current().pid() + " mode " + mode);

        switch (mode) {
            case "leak" -> {                              // → heap dump + histogram
                for (long i = 0; ; i++) {
                    LEAK.put("k" + i, new byte[10 * 1024]);
                    if (i % 1000 == 0) Thread.sleep(10);
                }
            }
            case "deadlock" -> {                          // → thread dump, 0% CPU
                new Thread(() -> { synchronized (LOCK_A) { sleep(100);
                        synchronized (LOCK_B) { } } }, "T1").start();
                new Thread(() -> { synchronized (LOCK_B) { sleep(100);
                        synchronized (LOCK_A) { } } }, "T2").start();
            }
            case "hot" -> {                               // → JFR / top -H, 100% CPU
                new Thread(DiagnoseMe::burn, "burner").start();
            }
            case "blocked" -> {                           // → thread dump, lock held across I/O
                ExecutorService pool = Executors.newFixedThreadPool(50);
                for (int i = 0; i < 50; i++)
                    pool.submit(() -> { synchronized (LOCK_A) { sleep(5000); } });
            }
        }
        Thread.sleep(Long.MAX_VALUE);
    }

    static void burn() { double d = 0; while (true) d += Math.sqrt(Math.random()); }
    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

Run each mode and practise the matching workflow:

```bash
java -Xmx256m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=. DiagnoseMe leak
jcmd <pid> GC.class_histogram | head -10       # watch byte[] and the map grow
jstat -gcutil <pid> 1000                       # watch O approach 100 and FGC climb

java DiagnoseMe deadlock
jcmd <pid> Thread.print | tail -40             # find "Found one Java-level deadlock"

java DiagnoseMe hot
jcmd <pid> JFR.start settings=profile duration=30s filename=hot.jfr
top -H -p <pid>                                # then hex, then grep nid= in the dump

java DiagnoseMe blocked
jcmd <pid> Thread.print | grep -c BLOCKED      # ~49 blocked on one monitor
```

**Doing all four of these yourself is worth more than reading about them ten times.** They are the
four shapes production failures actually take.

## The production triage order

```
1. Is it up?                       health endpoint, ps
2. CPU 0% or 100%?                 top -H -p <pid>          → deadlock vs hot loop
3. Three thread dumps, 5s apart    jcmd Thread.print        → what has not moved
4. Heap full? GC thrashing?        jstat -gcutil, GC.heap_info
5. What is on the heap?            GC.class_histogram       (cheap, before a full dump)
6. Full dump if needed             GC.heap_dump → MAT       → dominator tree, path to GC roots
7. Slow but healthy?               JFR 120s → JMC           → CPU, allocation, locks, I/O
8. File descriptors?               ls /proc/<pid>/fd | wc -l
```

Cheapest and most decisive first. Steps 2 and 3 resolve most hangs; step 7 resolves most "it is
slow".

## Common mistakes

| Mistake | Consequence |
|---|---|
| One thread dump | Cannot distinguish stuck from busy |
| Full heap dump as the first step | Pauses the JVM for seconds; the histogram was enough |
| No `HeapDumpOnOutOfMemoryError` | The one crash you needed evidence for produced none |
| Sorting by shallow size in MAT | You miss the object actually retaining the memory |
| Ignoring weak/soft refs in the GC-root path | You chase a reference that would not prevent collection |
| Thinking `kill -3` kills the process | It prints a dump; the fear is unfounded |
| JDWP open in production | Unauthenticated RCE |
| Debugging a race with a breakpoint | The timing changes; the bug disappears |
| Reading `RUNNABLE` as "using CPU" | It may be blocked in a syscall |
| Never using JFR | The tool that answers "why is it slow" goes unused |

## Interview questions

**Q: A production service is slow. Walk me through it.**
Confirm it is up, check CPU, take three thread dumps five seconds apart, check GC with `jstat`, then
start a 2-minute JFR recording and open it in JMC — CPU profile, allocation profile, monitor
contention, I/O. Fix based on evidence, not guesses.

**Q: How do you find a memory leak?**
`jstat -gcutil` to confirm old gen stays full after a full GC. `GC.class_histogram` for a cheap
first look. Then a heap dump into MAT: dominator tree for retained size, then path to GC roots
excluding weak references to find what holds it. Always deploy with
`-XX:+HeapDumpOnOutOfMemoryError`.

**Q: Shallow vs retained size?**
Shallow is the object's own memory; retained is everything that becomes unreachable if it is
collected. Retained size identifies the real culprit.

**Q: What is JFR and why is it special?**
A built-in, low-overhead (~1%) event recorder safe to run in production continuously. It gives CPU
profiles, allocation by stack trace, GC pauses, lock contention and I/O — including exceptions your
code swallowed.

**Q: How do you get a thread dump from a container with no shell tools?**
`kill -3 <pid>` sends `SIGQUIT` and the JVM writes a thread dump to stdout, which the platform is
already collecting. It does not terminate the process.

**Q: How do you diagnose a deadlock?**
CPU at 0%, then a thread dump — the JVM prints a "Found one Java-level deadlock" section with the
cycle for intrinsic locks. For `ReentrantLock`, use `ThreadMXBean.findDeadlockedThreads()`.

Two minutes: **"Production is degraded. Walk me through your first ten minutes."**

Triage order, cheapest first, with the specific command at each step and what each result would rule
