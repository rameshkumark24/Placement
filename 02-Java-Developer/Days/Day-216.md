# Part 1 — The model, against the one you have

```
⭐⭐ JVM                            ⭐⭐ BROWSER
⭐  thread per request              ⭐ ONE THREAD. TOTAL.
⭐  blocking is fine (and with      ⭐⭐ BLOCKING FREEZES THE ENTIRE
⭐    virtual threads, cheap)         UI — no clicks, no scroll, no
⭐                                    repaint, for as long as it runs
⭐  synchronized / locks            ⭐ NONE NEEDED — no preemption,
⭐                                    so no data races on your objects
⭐  CompletableFuture               ⭐ Promise
⭐  CompletableFuture.allOf()       Promise.all()
⭐  ExecutorService                 ⭐⭐ THERE ISN'T ONE. (Web Workers
⭐                                    are separate, message-passing.)

⭐⭐ THE ONE STRUCTURAL DIFFERENCE FROM CompletableFuture:
⭐   Java: CompletableFuture.supplyAsync(...) runs on a POOL.
⭐   JS:   ⭐⭐ THE ASYNC FUNCTION RUNS **ON THIS THREAD**, and only
⭐         yields at an `await`. ⭐ CONCURRENCY, NOT PARALLELISM.
⭐   ⇒ ⭐⭐ A TIGHT CPU LOOP INSIDE AN async FUNCTION STILL BLOCKS
⭐     EVERYTHING. `async` IS NOT "ON ANOTHER THREAD".
```

| ⭐ Concept | Java | JavaScript |
|---|---|---|
| The awaitable | `CompletableFuture<T>` | **Promise** — pending → fulfilled \| rejected |
| Start concurrently | `supplyAsync(...)` | ⭐ `const p = f()` — already started |
| Wait for all | `allOf(...).join()` | `Promise.all([...])` |
| All, keep failures | ⭐ `handle()` per future | ⭐⭐ `Promise.allSettled([...])` |
| First to finish | `anyOf(...)` | `Promise.race([...])` |
| First to **succeed** | ⭐ awkward | ⭐ `Promise.any([...])` |
| Timeout | `orTimeout(...)` | `AbortSignal.timeout(ms)` — Day 227 |
| Real parallelism | ⭐ more threads | ⭐⭐ a Web Worker, or nothing |

# Part 2 — ⭐⭐ Sequential `await` is `join()` in a loop

```javascript
// ❌ SEQUENTIAL — 4 requests × 200 ms = 800 ms
for (const id of ids) {
  const user = await fetchUser(id);       // ⭐⭐ each waits for the last
  users.push(user);
}

// ✅ CONCURRENT — 200 ms
const users = await Promise.all(ids.map(id => fetchUser(id)));
```

> ⭐⭐ **You have written this bug in Java** — calling `.join()` inside a loop instead of starting all
> the futures and joining once. **Identical shape, identical tell:** your latency is `n × one_request`
> and it scales linearly with a number you did not intend to make a multiplier.

```
⭐⭐ AND THE SAME CAVEAT: Promise.all IS UNBOUNDED.

⭐   ids.map(fetchUser)  with 5,000 ids
⭐   ⇒ ⭐⭐ 5,000 SIMULTANEOUS REQUESTS. The browser caps ~6 per host
⭐     so they queue — but you have also just DDoSed your own API.
⭐   ⇒ ⭐ THERE IS NO `Executors.newFixedThreadPool(10)` HERE.
⭐     You bound it yourself: batch, or a small concurrency limiter.
```

### The failure semantics differ, and it matters

| | Behaviour |
|---|---|
| `Promise.all` | ⭐⭐ **Rejects on the first failure.** You get one error and **lose the successful results.** The others keep running — they are not cancelled. |
| `Promise.allSettled` | ⭐ Never rejects. Returns `{status, value}` / `{status, reason}` per item. **Use this whenever partial success is meaningful.** |

```javascript
// ⭐⭐ dashboard: three widgets, one API each. One failing must not blank the page.
const [users, orders, stats] = await Promise.allSettled([
  fetchUsers(), fetchOrders(), fetchStats(),
]);
if (users.status === "fulfilled") render(users.value);
else showWidgetError("users", users.reason);   // ⭐ the other two still rendered
```

> ⭐ **The design question, not the API question:** *is partial success meaningful to the user?* On a
> dashboard, yes — `allSettled`. On a checkout where all three must succeed, no — `all`, and fail
> loudly. Choosing correctly is a design decision you should say out loud.

# Part 3 — Microtasks, and the frozen tab

```
⭐⭐ ONE TICK OF THE LOOP

⭐   1. run one macrotask   (a click, a timer, an I/O callback)
⭐   2. ⭐⭐ DRAIN THE ENTIRE MICROTASK QUEUE  (every .then / await
⭐      continuation — including ones queued while draining)
⭐   3. ⭐ RENDER IF NEEDED   ← ⭐⭐ THE STEP THE JVM HAS NO ANALOGUE FOR
⭐   4. next macrotask

⭐   ⇒ ⭐⭐ PROMISES ALWAYS BEAT setTimeout(0).
⭐   ⇒ ⭐⭐ AND SINCE RENDER IS STEP 3, ANYTHING THAT KEEPS STEPS 1–2
⭐     BUSY NEVER LETS THE SCREEN UPDATE. A 200 ms sort blocks a
⭐     frame; a 2 s loop looks like a crash.
```

```javascript
console.log("1");
setTimeout(() => console.log("2"), 0);           // macrotask
Promise.resolve().then(() => console.log("3"));  // microtask
console.log("4");
// ⭐⭐ 1, 4, 3, 2
```

> ⭐ **The priority-inversion shape is one you know** — Day 458's eval job starving user traffic. A
> queue always drained fully before the next thing gets a turn will starve that next thing. Here the
> starved thing is *the screen*.

# Part 4 — ⭐⭐ The rejection nobody catches

```javascript
// ❌ nothing awaits this. If it rejects, the app carries on as if fine.
saveDraft(doc);

// ⭐⭐ the user believes it saved. It did not. There is no error anywhere
//    in your UI — only an "Unhandled Promise Rejection" in a console
//    that nobody has open in production.
```

| ⭐ Fix | |
|---|---|
| **`await` it** | If the result matters, await it |
| **`.catch()` it explicitly** | ⭐ `saveDraft(doc).catch(reportError)` — deliberate fire-and-forget, failure still reported |
| **⭐⭐ A global handler** | `window.addEventListener("unhandledrejection", reportError)` — **wire this on day one** (Day 279) |
| **`void` for intent** | ⭐ `void saveDraft(doc).catch(log)` — signals "deliberately not awaited" |

```
⭐⭐ THE PARALLEL YOU ALREADY KNOW
⭐   Java: an exception inside a CompletableFuture that nobody
⭐   calls .join() or .exceptionally() on ⭐ VANISHES SILENTLY.
⭐   ⇒ ⭐⭐ SAME BUG, SAME SHAPE, DIFFERENT LANGUAGE:
⭐     AN ERROR NOBODY IS WAITING FOR IS AN ERROR NOBODY SEES.
⭐   ⇒ and it is Day 455's lesson again — the dangerous failure
⭐     does not raise.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "explain JavaScript's concurrency model to someone who knows the JVM."**

Lead with the inversion, because that is the useful part for your audience. **On the JVM I get a thread
per request, blocking is fine, and virtual threads made it cheap. The browser gives me one thread and
it also paints the screen. So a blocking call doesn't just delay a response, it freezes the UI — no
clicks, no scroll — and `async` doesn't put anything on another thread. It's concurrency, not
parallelism: a tight CPU loop inside an async function still blocks everything.**

Then what transfers. **Promises are CompletableFutures. `Promise.all` is `allOf`. And the bug transfers
exactly: awaiting inside a loop is joining inside a loop, and the tell is the same — latency is n times
one request. The difference is there's no thread pool to bound fan-out with, so `Promise.all` over five
thousand ids is five thousand requests and I have to bound it myself.**

Then the semantics choice. **`Promise.all` rejects on first failure and throws away the successes;
`allSettled` gives me every outcome. Which one I want isn't an API question, it's whether partial
success means anything to the user — on a dashboard it does, on a checkout it doesn't.**

Close on the silent failure. **Calling an async function starts it immediately, so fire-and-forget is
the default. A promise nobody awaited can reject and vanish — the user sees a save that silently didn't
happen, and the only trace is an unhandled rejection in a console nobody has open in production. That's
exactly a CompletableFuture whose exception nobody joins on: an error nobody is waiting for is an error
nobody sees.**
