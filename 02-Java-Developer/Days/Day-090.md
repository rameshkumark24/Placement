# Day 090

**L-090** · SOLID I — Single Responsibility, Open/Closed

**Time:** 3 hrs · **Mode:** NEW

> Two principles today, three tomorrow. SOLID is asked in almost every interview and usually
> answered as five memorised sentences, which convinces nobody. The way to answer well is to state
> **what problem each one prevents** and give a case where you would *not* apply it.

---

# Part 1 — S · Single Responsibility

## The definition people quote, and the one that is useful

Quoted: *"A class should have only one reason to change."*

Useful, and Robert Martin's own later clarification:

> **A module should be responsible to one, and only one, actor.**

The difference matters. "One reason to change" invites the useless argument that everything has one
reason if you squint. "One actor" is concrete: **who asks for this change?** If the finance team and
the operations team can both demand changes to the same class, that class has two responsibilities
and two groups who can break each other's work.

```java
// ❌ three actors
public class Employee {
    public Money calculatePay()  { … }   // ← finance/CFO
    public void  save()          { … }   // ← DBA/architecture
    public String reportHours()  { … }   // ← operations/COO
}
```

The failure mode is not aesthetic. Finance changes overtime rules, an engineer edits a shared helper,
and **operations' report silently changes**. Two actors, one class, one accidental breakage — that is
the actual harm SRP prevents.

```java
// ✅ separated by actor
public record Employee(EmployeeId id, String name, Grade grade, Hours hours) {}

public class PayCalculator   { public Money calculate(Employee e) { … } }   // finance
public class EmployeeRepository { public void save(Employee e) { … } }      // persistence
public class HoursReporter   { public String report(Employee e) { … } }     // operations
```

## Recognising a violation

- The class name contains **"and"** when you describe it honestly.
- It has **`Manager`, `Processor`, `Helper`, `Util`** in the name (Day 089's noise words).
- Its **imports span unrelated concerns** — JDBC *and* an email client *and* a PDF library.
- **Different tests break for unrelated reasons.**
- **Merge conflicts are frequent** on it, because several people work on it for different purposes.

That last one is a genuinely good real-world detector: `git log --format='%an' -- File.java | sort -u`
(Day 085). A file touched by six people for six different reasons is a file with six
responsibilities.

## Where SRP goes wrong

The over-application is real and worth naming, because interviewers probe for it:

```java
// 💀 SRP taken to absurdity
class OrderIdGenerator {}
class OrderIdValidator {}
class OrderIdFormatter {}
class OrderIdComparator {}
```

Now understanding an order id requires opening four files. **Cohesion is the other half of the
principle**: things that change together belong together. A class of four tiny methods that are
always used as a unit is *more* coupled than one class with four methods, because you have moved the
coupling from within a file to between files, where it is invisible.

> **SRP splits things that change for different reasons. It does not split things that change
> together.**

# Part 2 — O · Open/Closed

## The statement

> **Open for extension, closed for modification.** You should be able to add behaviour without
> editing existing, tested, working code.

The reason is risk. Editing working code risks breaking it; adding new code cannot break what it does
not touch. The principle is about **where the risk lands**.

## The smell

```java
// ❌ every new type edits this method — and every edit risks the existing cases
public Money shippingCost(Order order) {
    if (order.type() == STANDARD)      return Money.of(50);
    else if (order.type() == EXPRESS)  return Money.of(150);
    else if (order.type() == OVERNIGHT) return Money.of(400);
    // add SAME_DAY → edit here, retest everything, redeploy
    throw new IllegalArgumentException();
}
```

A growing `if`/`switch` on a *type* is the signature. Note the qualifier: switching on a type is the
smell; switching on a *value* (a status code, a character) usually is not.

## Three ways to close it

**1. Polymorphism** — the classic.

```java
public interface ShippingMethod {
    Money cost(Order order);
    Duration estimatedDelivery();
}

public class StandardShipping  implements ShippingMethod { … }
public class ExpressShipping   implements ShippingMethod { … }
public class SameDayShipping   implements ShippingMethod { … }   // ← NEW FILE ONLY

public class ShippingCalculator {
    private final Map<ShippingType, ShippingMethod> methods;      // injected
    public Money cost(Order order) {
        return methods.get(order.type()).cost(order);             // never edited again
    }
}
```

**2. An enum with behaviour** — often better in Java, and it is Day 043's material:

```java
public enum ShippingType {
    STANDARD(Money.of(50), Duration.ofDays(5)),
    EXPRESS(Money.of(150), Duration.ofDays(2)),
    SAME_DAY(Money.of(400), Duration.ofHours(6));

    private final Money cost; private final Duration eta;
    ShippingType(Money c, Duration e) { this.cost = c; this.eta = e; }
    public Money cost() { return cost; }
}
```

Adding a type is adding a constant. The compiler even helps: a `switch` **expression** over an enum
must be exhaustive (Day 030), so anywhere that genuinely must branch will fail to compile until you
handle the new case. That is the ideal — closed where you want closure, and a compile error where you
need attention.

**3. Strategy injection** — Day 095's pattern, and how Spring does it:

```java
@Component
public class ShippingCalculator {
    private final Map<ShippingType, ShippingMethod> methods;

    // Spring injects EVERY ShippingMethod bean. Adding a class registers it.
    public ShippingCalculator(List<ShippingMethod> all) {
        this.methods = all.stream().collect(toMap(ShippingMethod::type, identity()));
    }
}
```

Adding a `@Component` implementing the interface extends the system with **no edit anywhere**. This
is one of the most useful Spring idioms and it will reappear in Stage 4 — it is worth recognising
now as OCP rather than as framework magic.

## The honest caveat — do not close prematurely

You cannot make code open to *every* axis of change. Abstracting for a variation that never
materialises costs you an interface, an indirection, and a reader's time, permanently.

> **Close against the variation you have actually seen twice.** The first time, write it directly.
> The second time, notice the pattern. The third time, abstract.

Speculative extension points are the single most common way "SOLID" makes a codebase worse — a
`StrategyFactoryProvider` with exactly one implementation is not principled design, it is cost with
no benefit. This is YAGNI (Day 092) acting as SOLID's counterweight, and being able to state that
tension is what separates understanding from recitation.

## Code to type

```java
// Start here — the violation
public class NotificationService {
    public void notify(User user, String message, String channel) {
        if ("email".equals(channel)) {
            // build MIME, connect SMTP, send
            System.out.println("email to " + user.email() + ": " + message);
        } else if ("sms".equals(channel)) {
            System.out.println("sms to " + user.phone() + ": " + message);
        } else if ("push".equals(channel)) {
            System.out.println("push to " + user.deviceToken() + ": " + message);
        }
        auditLog.record(user, channel, message);
        metrics.increment("notifications." + channel);
    }
}
```

Two violations at once — find both before refactoring:

- **OCP**: adding WhatsApp edits `notify`.
- **SRP**: this class sends, audits *and* records metrics. Three actors: the messaging team, compliance,
  and the observability team.

Refactor to:

```java
public interface NotificationChannel {
    Channel type();
    void send(User user, String message);
}

public class EmailChannel implements NotificationChannel { … }
public class SmsChannel   implements NotificationChannel { … }
public class PushChannel  implements NotificationChannel { … }

public class NotificationService {
    private final Map<Channel, NotificationChannel> channels;
    private final NotificationAuditor auditor;        // compliance's concern
    private final NotificationMetrics metrics;        // observability's concern

    public void notify(User user, String message, Channel channel) {
        NotificationChannel target = channels.get(channel);
        if (target == null) throw new UnsupportedChannelException(channel);
        target.send(user, message);
        auditor.record(user, channel, message);
        metrics.recordSent(channel);
    }
}
```

Then **prove** it: add `WhatsAppChannel` and confirm you created exactly one new file and edited
nothing. That confirmation is the exercise — if you had to edit something, the abstraction is in the
wrong place.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Reading SRP as "one method" or "small class" | Fragmentation; coupling moves between files |
| Splitting things that change together | Lower cohesion; more files, same coupling |
| `Manager`/`Processor`/`Helper` classes | Multiple actors in one file |
| Growing `if`/`switch` on a type | Every new case risks the existing ones |
| Abstracting for a variation you have not seen | Permanent indirection, no benefit |
| Interfaces with exactly one implementation, forever | Ceremony |
| Treating SOLID as rules rather than trade-offs | Over-engineering defended by principle |

## Interview questions

**Q: What is the Single Responsibility Principle?**
A module should be responsible to a single actor — one group of stakeholders who can request changes
to it. If two groups can demand changes to the same class, one can silently break the other's
behaviour.

**Q: How do you spot an SRP violation?**
"And" in the honest description, noise-word names, imports spanning unrelated concerns, unrelated
tests breaking together, and frequent merge conflicts from several people editing it for different
reasons.

**Q: Can SRP be over-applied?**
Yes. Splitting things that change together lowers cohesion and moves coupling between files where it
is harder to see. Cohesion is the counterweight.

**Q: What is the Open/Closed Principle, and how do you achieve it in Java?**
New behaviour should require new code, not edits to working code. Achieved with polymorphism, enums
carrying behaviour, or strategy injection — in Spring, injecting a `List<Interface>` so a new
`@Component` registers itself.

**Q: When should you *not* apply OCP?**
Before you have seen the variation. Speculative extension points cost indirection permanently and
usually predict the wrong axis. Write it directly the first time; abstract when the pattern repeats.

**Q: Isn't a `switch` on an enum an OCP violation?**
Not necessarily. A `switch` *expression* over an enum is exhaustive, so adding a constant produces a
compile error rather than silent wrong behaviour — the change is safe and located. The violation is a
non-exhaustive chain that fails at runtime.

1. Refactor `NotificationService`, then add a WhatsApp channel and verify you edited nothing.
2. Do the same refactor a second way, using an enum with behaviour, and argue which fits better here.
3. Run `git log --format='%an' -- <BigFile.java> | sort | uniq -c | sort -rn` on any real project
   and find the file with the most distinct authors. Read it and name its actors.
4. Find a class in your own code with "and" in its honest description. Split it by actor.
5. Find a growing `if`/`switch` on a type. Close it, and count the files you had to touch to add the
   next case — before and after.
6. Find an interface in your code with exactly one implementation that has never had another. Decide
   honestly whether to inline it.
7. Convert one non-exhaustive `switch` statement into a `switch` expression and confirm the compiler
   now demands every case.

## 🎙️ Articulation drill

Two minutes: **"Explain SRP and OCP with an example from your own code."**

Use a real example, name the *actors* for SRP, and for OCP describe the `if`-chain you removed and
the fact that the next case was a new file only. Then volunteer the caveat — that you do not abstract
until you have seen the variation — because volunteering the trade-off is what makes it sound like
experience rather than a textbook.
