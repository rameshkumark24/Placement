# Part 1 — ⭐ Transactions, and why they are a last resort

```javascript
const session = client.startSession();
try {
  session.startTransaction({ readConcern: { level: "snapshot" },
                             writeConcern: { w: "majority" } });
  await orders.insertOne(order, { session });
  await inventory.updateOne({ sku }, { $inc: { qty: -1 } }, { session });
  await session.commitTransaction();
} catch (e) { await session.abortTransaction(); throw e; }
finally { await session.endSession(); }
```

**⭐ Multi-document ACID transactions exist since 4.0 (replica sets) and 4.2 (sharded).** They are
real. **They are also the wrong default in MongoDB**, and the reasons are concrete:

| Cost | Detail |
|---|---|
| ⭐ **60-second default limit** | ⭐ `transactionLifetimeLimitSeconds` — long transactions abort |
| ⭐ **Significant overhead** | ⭐ noticeably slower than single-document writes |
| ⭐ **Write conflicts abort** | ⭐ **you must retry** — like Day 195's `SERIALIZABLE` |
| Across shards | ⭐ a two-phase commit — much more expensive |
| Held resources | a long transaction pins the oldest snapshot, like Day 194's vacuum problem |

> **⭐ The rule: if you need multi-document transactions routinely, your document model is wrong —
> or MongoDB is.**

**⭐ Day 211's Rule 1 is the resolution**: embed what changes together, so the update is one
single-document atomic write and no transaction is needed. **The document model's whole promise is
that the aggregate boundary and the transaction boundary are the same thing.** Needing transactions
constantly means those boundaries disagree.

## ⭐ Read and write concerns — MongoDB's durability dial

```javascript
{ w: "majority", j: true, wtimeout: 5000 }     // ⭐ write concern
{ readConcern: { level: "majority" } }          // ⭐ read concern
```

| Write concern | Meaning |
|---|---|
| `w: 1` | ⭐ the primary acknowledged. **Lost if it fails before replicating** |
| ⭐ **`w: "majority"`** | ⭐ **a majority acknowledged — survives a failover** |
| `j: true` | written to the journal on disk |

**⭐ This is Day 205's Redis comparison with a better answer**: `w: "majority"` genuinely survives a
failover, because MongoDB's replica sets use a Raft-like consensus protocol rather than Redis's
asynchronous replication. **MongoDB can give you RPO 0; Redis cannot.**

⚠️ **`w: 1` is the default in some driver configurations.** Check it — the default is not always the
safe one, and the failure is silent.

| Read concern | Meaning |
|---|---|
| `local` | ⭐ may be rolled back later |
| ⭐ `majority` | ⭐ will not be rolled back |
| `linearizable` | ⭐ strongest, slowest — reflects all prior majority writes |

**⭐ `readConcern: local` on a primary can return a write that is subsequently rolled back** during a
failover. That is D-16's eventual consistency, and it is why `majority` matters for anything a user
will act on.

# Part 2 — Replica sets and sharding

## ⭐ Replica sets — and why the elections are better than Redis's

```
Primary ──oplog──► Secondary
        └─oplog──► Secondary        ⭐ Raft-like election on failure
```

| vs Day 201's PostgreSQL | vs Day 205's Redis |
|---|---|
| Similar: async replication by default, `w:"majority"` for safety | ⭐ **Better: real consensus, so `w:"majority"` genuinely survives failover** |
| ⭐ **Automatic failover built in** (PostgreSQL needs Patroni) | ⭐ Sentinel is weaker |

**⭐ Automatic failover with consensus, in the box, is a genuine MongoDB advantage** and worth saying
plainly — PostgreSQL needs Patroni or a managed service to match it.

**⭐ Reading from secondaries has the same trap as Day 201**: replication lag means read-after-write
returns "not found". `readPreference: "primaryPreferred"` and the fixes from Day 201 apply
identically.

## ⭐⭐ Sharding — and the decision that cannot be undone

```javascript
sh.shardCollection("app.orders", { customerId: "hashed" })
```

**⭐ The shard key is the most consequential decision in a MongoDB deployment**, and Day 200's
partition-key argument applies with more force because **it cannot be changed** (resharding exists
from 5.0 but is expensive and disruptive).

| ⭐ A good shard key | ⭐ A bad shard key |
|---|---|
| ⭐ **High cardinality** | ⭐ few distinct values → few chunks |
| ⭐ **Even write distribution** | ⭐ **monotonically increasing → all writes to one shard** |
| ⭐ **Present in most queries** | ⭐ **absent → scatter-gather to EVERY shard** |

**⭐ The two failure modes, and both are common:**

1. ⭐ **A monotonically increasing key** — a timestamp, or an `ObjectId` (Day 210: roughly
   time-ordered) — sends **every new write to the same shard**. You have added machines and
   concentrated the load. This is the classic hot-shard problem.
2. ⭐ **Queries that omit the shard key** become **scatter-gather**: every shard is queried, results
   are merged. **Slower than an unsharded collection**, which is exactly Day 200's warning about
   partition pruning.

**⭐ `hashed` fixes distribution and breaks range queries** — hashed keys have no useful ordering, so
"orders from last week" becomes scatter-gather. **A compound key like
`{ tenantId: 1, orderDate: 1 }` often balances both**: distribution by tenant, range queries within
one.

> **⭐ Choose the shard key from the dominant query pattern, exactly as Day 200 chose the partition
> key — and accept that you are choosing which queries stay fast.**

**⭐ And ask whether you need it at all.** Day 200's scepticism applies: a well-indexed replica set
handles very large workloads, and sharding adds config servers, `mongos` routers, balancer operations
and a permanent constraint on every query. **Most systems that shard did not need to.**

# Part 3 — ⭐⭐ The decision framework

**⭐ The stage's central deliverable.** Run it against a real system.

### ⭐ Choose PostgreSQL when — the default

| Signal |
|---|
| ⭐ **Relationships matter** — joins, referential integrity, cross-entity constraints |
| ⭐ **Transactions across entities are normal, not exceptional** |
| Ad-hoc reporting and analytics are required |
| ⭐ **The data has a shape** — and `jsonb` covers the parts that vary (Day 198) |
| Correctness matters more than write scale |
| ⭐ **You are not certain** — ⭐ **PostgreSQL is the lower-regret choice** |

### ⭐ Choose MongoDB when

| Signal |
|---|
| ⭐ **The data is genuinely aggregate-shaped** — read and written as a whole |
| ⭐ **Documents vary in structure by nature** — catalogues, CMS, form data |
| ⭐ **Write volume genuinely exceeds one machine**, and sharding is the plan |
| Time-series or geospatial at scale |
| ⭐ **Single-document atomicity matches your consistency needs** |

### ⭐ The arguments to reject

| Claim | Response |
|---|---|
| ⭐ "MongoDB is faster" | ⭐ its advantage is avoiding joins by embedding. Indexed relational lookups are comparably fast |
| ⭐ "We don't know the schema" | ⭐ `jsonb` gives that **with** constraints, joins and transactions |
| "It scales better" | ⭐ true only past one machine's write capacity, which most systems never reach |
| "No migrations" | ⭐ the migration moved into every read path (Day 210) |
| ⭐ "PostgreSQL can't do JSON" | ⭐ it has done it well for a decade |

### ⭐ And the answer that is usually right

> **⭐ Both. PostgreSQL as the system of record, Redis as the fast derived layer, and MongoDB for the
> one subsystem that is genuinely document-shaped — if any.** Polyglot persistence per bounded
> context, not per company.

**⭐ Its cost is real and worth naming: each store is another thing to operate, back up, monitor,
secure and staff.** Two databases is a reasonable price for a genuine fit; four for architectural
enthusiasm is not.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Multi-document transactions as the norm | the model and the aggregate boundary disagree |
| Not retrying on write conflict | Day 195's lesson, unlearned |
| ⭐ `w: 1` in production | a write lost on failover |
| `readConcern: local` for user-visible data | can be rolled back |
| ⭐ Monotonically increasing shard key | every write to one shard |
| ⭐ Queries omitting the shard key | scatter-gather — worse than unsharded |
| `hashed` where range queries dominate | every range query is scatter-gather |
| Sharding before it is needed | Day 200's scepticism |
| Reading secondaries without a lag plan | read-after-write "not found" |
| ⭐ Choosing a datastore on a rejected argument | a decade of consequences |
| Polyglot persistence per team enthusiasm | each store is a full operational commitment |

## Interview questions

**Q: When do you use MongoDB transactions?**
Rarely. They exist and work, but they carry real overhead, a sixty-second default limit, and write
conflicts you must retry. If I need them routinely, my document model is wrong — the whole promise of
the document model is that the aggregate boundary and the transaction boundary are the same, so
embedding what changes together makes the update one atomic single-document write.

**Q: How do MongoDB's durability guarantees compare to Redis and PostgreSQL?**
MongoDB with `w: "majority"` genuinely survives a failover, because replica sets use a consensus
protocol — so RPO 0 is achievable, which Redis cannot offer with asynchronous replication.
PostgreSQL achieves the same with synchronous replication but needs Patroni or a managed service for
automatic failover, which MongoDB has in the box.

**Q: What makes a good shard key?**
High cardinality, even write distribution, and presence in most queries. The failures are a
monotonically increasing key, which sends every write to one shard so you have added machines and
concentrated load; and queries omitting the key, which become scatter-gather across every shard —
slower than not sharding. It cannot be changed cheaply, so it comes from the dominant query pattern.

**Q: Postgres or Mongo for a new system?**
Three questions. Is the data aggregate-shaped, read and written as a whole? Are cross-entity
transactions and constraints the normal case? Will I exceed one machine's write capacity? If the
answers are not clearly yes, PostgreSQL — it is the lower-regret choice, and `jsonb` covers the parts
that genuinely vary. And I would reject "it's faster" and "we don't know the schema", because neither
survives examination.

**Q: What is the honest cost of polyglot persistence?**
Each store is a full operational commitment — backups, restores tested, monitoring, security,
upgrades, and people who understand it. PostgreSQL plus Redis is a reasonable default. Adding a third
needs a subsystem that genuinely fits it better, not architectural preference.

## Mini task

**⭐ The exit gate is the task.** Additionally:

1. Run a multi-document transaction and one embedded atomic update for the same change. **Compare
   latency.** Then force a write conflict and confirm you must retry.
2. Write with `w: 1`, kill the primary immediately, and **find the lost write.** Repeat with
   `w: "majority"`.
3. Shard a collection on `ObjectId`. Load a million documents and **watch one shard take every
   write.** Reshard on a hashed key and compare.
4. Query with and without the shard key. **Compare against the unsharded collection** — confirm
   scatter-gather is slower.
5. Read from a secondary immediately after a write and reproduce read-after-write.
6. ⭐ **Take a real system you know and run the three decision questions on it. Write the answer and
   the cost you accepted.**
7. ⭐ **Have someone give you three unfamiliar slow queries and diagnose them out loud, timed.**
