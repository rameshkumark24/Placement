# Part 1 — The resource server, which is almost all configuration

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-oauth2-resource-server</artifactId>
</dependency>
```

```yaml
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: https://auth.acme.com/realms/acme      # ⭐ that is the whole configuration
  audiences: acme-api
```

```java
http.oauth2ResourceServer(oauth -> oauth
    .jwt(jwt -> jwt.jwtAuthenticationConverter(authoritiesConverter())));
```

**⭐ What those two lines do that Day 173 needed a hundred for:**

| Day 173, by hand | Resource server |
|---|---|
| Algorithm allow-list | ✅ derived from the JWKS key type |
| Signature verification | ✅ |
| `exp` / `nbf` with clock skew | ✅ |
| Issuer validation | ✅ from `issuer-uri` |
| Audience validation | ✅ from `audiences` |
| ⭐ **Key rotation** | ✅ ⭐ **fetches JWKS, caches it, refetches on an unknown `kid`** |
| Public-key crypto | ✅ RS256/ES256 by default |

**Key rotation is the item that decides it.** `issuer-uri` triggers a fetch of
`/.well-known/openid-configuration`, which yields a `jwks_uri` holding the issuer's **public** keys.
When the issuer rotates a key, tokens arrive with a new `kid`, Spring refetches, and nothing breaks.

**A hand-rolled HS256 implementation cannot rotate at all** without coordinating a shared secret
change across every service simultaneously — which in practice means the secret is never rotated,
including after someone leaves the team.

**And the asymmetric-key property matters independently:** with RS256 the resource server holds only
the *public* key. **A compromised service cannot mint tokens.** With a shared HMAC secret, every
service that can verify can also forge — so one compromised service is a full estate compromise.

## Mapping claims to authorities

```java
@Bean
JwtAuthenticationConverter authoritiesConverter() {
    var scopes = new JwtGrantedAuthoritiesConverter();
    scopes.setAuthorityPrefix("SCOPE_");                 // ⭐ default
    scopes.setAuthoritiesClaimName("scope");

    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        var authorities = new ArrayList<GrantedAuthority>(scopes.convert(jwt));
        // ⭐ Keycloak nests roles; every provider does this differently
        Map<String, Object> realm = jwt.getClaim("realm_access");
        if (realm != null) {
            ((List<String>) realm.get("roles")).stream()
                .map(r -> new SimpleGrantedAuthority("ROLE_" + r))    // ⭐ Day 170's prefix
                .forEach(authorities::add);
        }
        return authorities;
    });
    return converter;
}
```

**⭐ Scopes are not roles, and conflating them is a real access-control error.**

| | Meaning | Example |
|---|---|---|
| **Scope** | ⭐ what the **client application** was authorised to do | `orders:read` |
| **Role** | ⭐ what the **user** is permitted to do | `ROLE_ADMIN` |

**Both must be checked.** A mobile app with `orders:read` scope, used by a customer, must not read
another customer's orders — the scope says the *app* may read orders; the user's identity says
*which*. Day 174's ownership check is still required.

```java
@PreAuthorize("hasAuthority('SCOPE_orders:read') and @orderGuard.isOwner(#id, authentication)")
```

## Opaque tokens

```yaml
spring.security.oauth2.resourceserver.opaquetoken:
  introspection-uri: https://auth.acme.com/oauth2/introspect
  client-id: acme-api
  client-secret: ${INTROSPECTION_SECRET}
```

**A network call per request** — slow, and a hard dependency on the auth server's availability. In
exchange you get **instant revocation**, which JWTs cannot give you (Day 173).

**The pragmatic hybrid:** JWTs with short lifetimes for normal traffic, introspection for
high-value operations only. And note that introspection responses can be cached briefly — which
trades back some of the revocation immediacy you paid for.

# Part 2 — The client side

```yaml
spring.security.oauth2.client:
  registration:
    google:
      client-id: ${GOOGLE_CLIENT_ID}
      client-secret: ${GOOGLE_CLIENT_SECRET}
      scope: openid, profile, email
      authorization-grant-type: authorization_code       # ⭐ PKCE automatic for public clients
    inventory-service:
      client-id: orders-service
      client-secret: ${INVENTORY_SECRET}
      authorization-grant-type: client_credentials       # ⭐ machine-to-machine (Day 116)
  provider:
    google:
      issuer-uri: https://accounts.google.com
```

```java
http.oauth2Login(login -> login
        .userInfoEndpoint(u -> u.oidcUserService(customOidcUserService()))   // ⭐ map to local user
        .defaultSuccessUrl("/dashboard", true));
```

Spring handles the redirect, the state parameter, the code exchange, and PKCE. **You mostly write the
`OidcUserService` that maps the external identity to a local account.**

## ⭐ The account-linking hazard, which is a real vulnerability class

```java
@Bean
OAuth2UserService<OidcUserRequest, OidcUser> customOidcUserService() {
    var delegate = new OidcUserService();
    return request -> {
        OidcUser oidc = delegate.loadUser(request);

        if (!Boolean.TRUE.equals(oidc.getEmailVerified())) {          // ⭐⭐ MANDATORY
            throw new OAuth2AuthenticationException("email not verified");
        }
        User local = users.findByProviderAndSubject(providerId(request), oidc.getSubject())
                .orElseGet(() -> linkOrCreate(oidc, request));
        return new AppOidcUser(oidc, local);
    };
}
```

**⭐ Two rules, and skipping either is an account-takeover bug:**

1. **Require `email_verified`.** A provider that lets anyone register `victim@gmail.com` without
   verification, matched to a local account by email, is an account takeover in one login.
2. ⭐ **Key the local account by `(issuer, sub)`, never by email alone.** `sub` is the stable,
   provider-scoped identifier. Emails change, are reused by organisations, and are not unique across
   providers. **Matching on email alone means whoever controls that address at any provider controls
   the account.**

## Machine-to-machine — client credentials

```java
@Bean
RestClient inventoryClient(RestClient.Builder builder,
                           OAuth2AuthorizedClientManager manager) {
    var interceptor = new OAuth2ClientHttpRequestInterceptor(manager);
    interceptor.setClientRegistrationIdResolver(r -> "inventory-service");
    return builder.baseUrl("https://inventory.acme.com")
                  .requestInterceptor(interceptor)      // ⭐ token fetched, cached, refreshed
                  .build();                             // ⭐ Day 154's timeouts still required
}
```

**This replaces hand-rolled service tokens** (Day 115b's API keys): tokens are short-lived,
automatically refreshed, centrally revocable, and scoped. It is the right default for
service-to-service calls inside an estate that already runs an authorization server.

# Part 3 — ⭐ Should you build an authorization server?

Spring Authorization Server exists and it is a real, competent implementation.

```java
@Bean @Order(1)
SecurityFilterChain authServer(HttpSecurity http) throws Exception {
    OAuth2AuthorizationServerConfiguration.applyDefaultSecurity(http);
    return http.build();
}
```

**And you should almost certainly not use it.** Running an authorization server means owning:

- key generation, storage, **rotation**, and JWKS publication;
- consent screens, and the storage of consent decisions;
- token, refresh-token and authorization-code lifecycle and cleanup;
- **the security of every protocol detail**, forever, as specifications evolve;
- login, MFA, password reset, account recovery, and the abuse handling around all of them;
- audit logs adequate for whatever compliance regime applies.

**Keycloak, Auth0, Okta, Entra ID or Cognito do all of this**, and identity is a domain where being a
year behind on a specification is a breach rather than a feature gap.

**⭐ The honest cases for building one:** a strict air-gapped or regulatory constraint that forbids
external identity providers, or a product whose *core offering* is identity. "We want to avoid the
licence cost" is usually a miscalculation — the engineering time to operate it safely exceeds the
licence within a year.

**Say this in an interview.** Recognising when *not* to build something is a stronger signal than
knowing the API.

# Part 4 — Migrating from Day 173's hand-rolled tokens

The migration is straightforward because a resource server can accept both during transition:

```
1. Deploy the auth server (or provision the SaaS tenant). Nothing changes yet.
2. Configure the resource server chain alongside the existing JWT filter,
   ⭐ matched on the token's issuer claim — old tokens keep working.
3. Move login to the auth server. New tokens are issued by it.
4. Wait for the old refresh-token TTL to elapse.       ⭐ 30 days, and the tail is the users
5. Delete the custom filter, JwtService, and the shared secret.
```

**Step 4 is the same waiting pattern as Day 166's expand/contract and Day 109's deprecation** — add
the new, support both, migrate, wait for the tail, remove. Third time this shape has appeared, and
noticing that is worth more than remembering any individual instance.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Hand-rolling JWT validation when a resource server exists | reimplements five validations and cannot rotate keys |
| Shared HMAC secret across services | any service can forge tokens for any other |
| Treating scopes as roles | the client's permission is not the user's |
| Checking scope without ownership | Day 174's IDOR, one layer up |
| ⭐ Not requiring `email_verified` | account takeover on first login |
| ⭐ Linking accounts by email | whoever controls the address controls the account |
| No timeouts on the JWKS fetch | auth server latency becomes your latency (Day 154) |
| Opaque tokens without measuring | a network call per request |
| Building an authorization server | owning key rotation, consent, MFA and protocol currency forever |
| No timeouts on the client-credentials client | Day 154 |
| Big-bang token migration | old refresh tokens are live for their full TTL |

## Interview questions

**Q: Why use a resource server instead of validating JWTs yourself?**
It does every validation I would otherwise write — signature, algorithm, expiry, issuer, audience —
and it handles key rotation by fetching JWKS and refetching on an unknown `kid`. A hand-rolled HMAC
implementation cannot rotate without a coordinated secret change everywhere, so in practice the
secret never rotates. Asymmetric keys also mean a compromised service can verify but not forge.

**Q: Scopes or roles?**
Both, and they answer different questions. A scope is what the client application was authorised to
do; a role is what the user may do. A mobile app with `orders:read` still must not read another
customer's orders, so the scope check does not remove the ownership check.

**Q: What is the main risk in social login?**
Account linking. If I match an external identity to a local account by email, anyone who controls
that email at any provider takes over the account — so I key on issuer plus subject, and I reject
identities where `email_verified` is false.

**Q: Would you build an authorization server?**
Almost never. It means owning key rotation, consent, token lifecycle, MFA, account recovery and
protocol currency indefinitely, in a domain where being behind the specification is a breach. I would
build one only under a regulatory constraint that forbids external providers, or if identity were the
product.
