# Day 172

**L-172** · Stateless APIs, sessions, and CSRF — when disabling it is right

**Time:** 3 hrs · **Mode:** NEW

> `csrf().disable()` is the most copy-pasted line in Spring Security, and most people who write it
> cannot say why it is safe. Sometimes it is. Sometimes it is a vulnerability.
>
> Day 113 built sessions and cookie flags. Day 155 established that CORS does not protect your

> **where does the browser store the credential, and does it send it automatically?**

# Part 1 — ⭐ Why CSRF exists, precisely

```html
<!-- evil.com, while the victim is logged into bank.com -->
<form action="https://bank.com/api/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="10000">
</form>
<script>document.forms[0].submit();</script>
```

**The browser attaches `bank.com`'s cookies automatically**, because cookies are scoped to the
destination, not the origin of the page. The request is authenticated. The transfer happens.

**⭐ The victim never sees a response** — Day 155's same-origin policy blocks *reading* it — and that
does not matter at all, because the damage is done by the write.

## The two conditions, and this is the whole decision

> **CSRF is possible if and only if:**
> **1. the credential is sent automatically by the browser, and**
> **2. the server accepts it without any request-specific proof.**

| Credential | Automatic? | CSRF risk |
|---|---|---|
| **Session cookie** | ⭐ yes | ✅ **vulnerable — CSRF protection required** |
| **JWT in a cookie** | ⭐ yes | ✅ ⭐ **vulnerable. The token being a JWT changes nothing** |
| **JWT in `Authorization: Bearer`** | ❌ JS must attach it | ⭐ **not vulnerable** |
| **API key in a header** | ❌ | not vulnerable |
| HTTP Basic | ⭐ yes, browser-cached | vulnerable |
| mTLS | yes | vulnerable to CSRF, though rarely browser-facing |

**⭐ Row two is the mistake.** "We use JWTs so we're stateless so CSRF doesn't apply" is wrong the
moment the JWT lives in a cookie — and putting it in a cookie is a common and otherwise-good choice
(see Part 3). The protection follows the *transport*, not the token format.

```java
// ✅ SAFE: bearer tokens in a header, no cookie authentication anywhere
http.csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));

// ❌ UNSAFE: disabled while a cookie carries the credential
http.csrf(AbstractHttpConfigurer::disable)
    .formLogin(withDefaults());          // ⭐ session cookie — now exploitable
```

# Part 2 — CSRF protection when you do need it

```java
http.csrf(csrf -> csrf
    .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())   // ⭐ JS must read it
    .csrfTokenRequestHandler(new SpaCsrfTokenRequestHandler())
    .ignoringRequestMatchers("/api/v1/webhooks/**"));                     // ⭐ see below
```

**The synchroniser-token pattern:** the server issues a random token, the client returns it in a
**header or form field**, and the server compares. `evil.com` cannot read the token — same-origin
policy — so it cannot forge the header. **The defence works precisely because the token is *not*
sent automatically.**

**`withHttpOnlyFalse()` looks alarming and is correct here.** JavaScript must read the CSRF cookie to
put it in a header. That is safe because the CSRF token is not a credential — stealing it alone
achieves nothing without also having the session cookie, and if you have XSS you have already lost
regardless.

⚠️ ⭐ **The Boot 3 / Security 6 change:** the `CsrfToken` is now loaded **lazily** via a
`Supplier`, which broke the standard SPA pattern — the cookie is not written until something reads
the token. This is why `SpaCsrfTokenRequestHandler` (or a filter that simply calls
`csrfToken.getToken()`) is needed. Symptom: every POST from your SPA returns 403 after upgrading, and
the configuration looks unchanged.

**Webhook endpoints must be excluded** (Day 129) — the sender is a server, not a browser, so it has
no CSRF token. Its authentication is the HMAC signature, which is request-specific proof and
therefore not CSRF-able.

## ⭐ `SameSite` — the second layer, not a replacement

```java
@Bean
CookieSameSiteSupplier sameSite() { return CookieSameSiteSupplier.ofLax(); }
```

| Value | Behaviour |
|---|---|
| `Strict` | never sent cross-site — ⭐ breaks arriving from an external link while logged in |
| **`Lax`** | ⭐ **the browser default now.** Sent on top-level GET navigation, **not on cross-site POST** |
| `None` | always sent — ⭐ **requires `Secure`**, and is what you need for a genuine cross-site SPA |

**`Lax` blocks the classic form-POST attack**, which is why CSRF is less exploitable than it once was.
**It is not sufficient on its own:** older browsers, `None` when your SPA is on a different site,
GET endpoints with side effects (which is a Day 102 violation anyway), and some
method-override tricks all survive it. **Defence in depth: `Lax` cookies *and* CSRF tokens.**

## Cookie flags — Day 113, as configuration

```yaml
server.servlet.session.cookie:
  http-only: true          # ⭐ JS cannot read it — the anti-XSS-theft flag
  secure: true             # ⭐ HTTPS only. Needs forward-headers-strategy (Day 155)
  same-site: lax
  max-age: 1800
```

**`Secure` silently does nothing if the app thinks it is on HTTP** behind a load balancer — one more
reason `forward-headers-strategy` matters.

# Part 3 — Stateless or sessions? The honest comparison

| | Session cookie | JWT (bearer) |
|---|---|---|
| Server state | ⭐ yes — a store | none |
| Revocation | ⭐ **instant** — delete the session | ❌ hard (Day 114) |
| Horizontal scaling | needs Redis or sticky sessions | ⭐ trivial |
| CSRF | ⭐ **required** | not applicable in a header |
| XSS theft | ⭐ **`HttpOnly` protects it** | ❌ **`localStorage` is readable by any script** |
| Size on the wire | ~40 bytes | 400–1500 bytes ⭐ **per request** |
| Mobile / third-party clients | awkward | ⭐ natural |

**⭐ The honest position, and it is not the fashionable one:** for a **first-party web application**,
sessions are usually the better choice. Instant revocation and `HttpOnly` protection against XSS are
worth more than statelessness, and Spring Session with Redis makes scaling a non-issue.

**JWTs earn their place** for mobile clients, third-party API consumers, service-to-service calls, and
genuinely distributed systems where a shared session store is undesirable.

### ⭐ The hybrid most teams should use

```java
// Access token: short-lived, in memory, sent as a bearer header
// Refresh token: HttpOnly + Secure + SameSite=Strict cookie, path=/api/v1/auth/refresh
ResponseCookie refresh = ResponseCookie.from("refresh_token", token)
    .httpOnly(true).secure(true).sameSite("Strict")
    .path("/api/v1/auth/refresh")                     // ⭐ sent to exactly one endpoint
    .maxAge(Duration.ofDays(30))
    .build();
```

**This gets both properties.** The access token is never in `localStorage`, so XSS cannot exfiltrate a
long-lived credential; the refresh token is `HttpOnly` so script cannot read it, and its narrow `path`
means it is transmitted on exactly one endpoint. CSRF protection is then needed only for the refresh
endpoint — which is one place, easy to reason about, and `SameSite=Strict` already covers it.

Day 173 implements this fully.

## Session configuration, and the fixation defence

```yaml
spring.session.store-type: redis        # ⭐ shared store — no sticky sessions needed
```

```java
http.sessionManagement(s -> s
    .sessionFixation(SessionFixationConfigurer::changeSessionId)   // ⭐ default, and correct
    .maximumSessions(3)
    .maxSessionsPreventsLogin(false)                               // ⭐ evict oldest
);
```

**Session fixation** (Day 113): an attacker sets a known session id, the victim logs in, and the
attacker now shares the authenticated session. `changeSessionId` issues a new id on authentication,
which breaks the attack. **It is the default — do not turn it off.**

**And the rule Day 171 already required:** invalidate every session on password change or reset.
Otherwise an attacker who compromised the account keeps their session after the victim "recovers" it.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `csrf().disable()` with cookie authentication | direct CSRF vulnerability |
| ⭐ "We use JWT so CSRF doesn't apply" | false if the JWT is in a cookie |
| CSRF enabled for a stateless bearer API | every POST 403s for no benefit |
| Relying on `SameSite` alone | older browsers, `None`, GET side effects |
| `SameSite=None` without `Secure` | browser rejects the cookie entirely |
| JWT in `localStorage` | any XSS steals a long-lived credential |
| ⭐ Not calling `getToken()` in Boot 3 | lazy `CsrfToken`; SPA 403s after upgrade |
| CSRF not excluded for webhooks | the sender has no token; endpoint always 403s |
| `Secure` behind a proxy without forwarded headers | flag never applied |
| Disabling session fixation protection | fixation attack works |
| Not invalidating sessions on password change | attacker retains access |
| GET endpoints with side effects | defeats `SameSite=Lax` and violates Day 102 |

## Interview questions

**Q: When is `csrf().disable()` safe?**
When no credential is sent automatically by the browser — bearer tokens in an `Authorization` header,
API keys in a header. It is not safe the moment a session cookie or a JWT-in-a-cookie authenticates
the request, because the browser attaches those automatically.

**Q: Explain CSRF and why the synchroniser token works.**
A third-party page triggers an authenticated request because the browser attaches cookies to the
destination automatically; the attacker cannot read the response but does not need to. The token
works because it must be sent in a header or form field that the attacker cannot read — same-origin
policy prevents it — so the one piece of proof that is not automatic is exactly what is missing.

**Q: JWT in `localStorage` or a cookie?**
Neither on its own. A short-lived access token held in memory and sent as a bearer header, with the
refresh token in an `HttpOnly`, `Secure`, `SameSite=Strict` cookie scoped to the refresh path. That
avoids XSS exfiltration of a long-lived credential and confines CSRF concern to one endpoint.

**Q: Sessions or stateless tokens?**
For a first-party web app, sessions — instant revocation and `HttpOnly` protection are worth more
than statelessness, and Spring Session with Redis removes the scaling objection. JWTs for mobile,
third parties and service-to-service.

## 🎙️ Articulation drill

Two minutes: **"When would you disable CSRF protection?"**

State the rule first — CSRF applies exactly when the browser attaches the credential automatically
and the server requires no request-specific proof — then apply it: safe for bearer tokens in a
header, unsafe the moment a cookie authenticates the request, including a cookie containing a JWT.
Explain why the token defence works, which is that the attacker cannot read cross-origin. Close on
the design you would actually ship: access token in memory as a bearer header, refresh token in an
`HttpOnly` `SameSite=Strict` cookie scoped to one path — which gets XSS protection and statelessness
at once and confines CSRF to a single endpoint.
