# Day 159

**L-159** · Relationships and the owning side — the concept people never quite learn

**Time:** 3 hrs · **Mode:** NEW

> Day 157 named the impedance mismatch's third item: **object references are directional and
> bidirectional; a foreign key is one column in one table.** The owning side is JPA's answer to that
> mismatch, and misunderstanding it produces the single most common "why isn't my change saved?"
> question in Java.
>
> Today: the four cardinalities, what "owning" means precisely, and the two rules that prevent every
> relationship bug.

---

# Part 1 — ⭐ The owning side, stated precisely

```java
@Entity
public class Order {
    @ManyToOne(fetch = FetchType.LAZY)          // ⭐ the OWNING side
    @JoinColumn(name = "customer_id")           // ⭐ this entity's table has the FK column
    private Customer customer;
}

@Entity
public class Customer {
    @OneToMany(mappedBy = "customer")           // ⭐ the INVERSE side. mappedBy = "I am not it"
    private List<Order> orders = new ArrayList<>();
}
```

> **The owning side is the side whose table contains the foreign key column. Hibernate writes the
> foreign key from the owning side and *from nowhere else*. Changes to the inverse side are ignored
> at write time — completely and silently.**

**`mappedBy` means "the other side owns this; my collection is a read-only view."**

## The bug this causes, and it is universal

```java
customer.getOrders().add(order);      // ⭐ inverse side only
repo.save(customer);
// → NO UPDATE. order.customer_id is still null. No error. No warning.
```

The developer has done the natural object-oriented thing — added to a collection — and JPA silently
did nothing, because that collection is not where the foreign key lives. The row is written; the
association is not.

**And the mirror-image bug is worse**, because it half-works:

```java
order.setCustomer(customer);          // ⭐ owning side — the FK IS written
// but customer.getOrders() does not contain `order` in this session
```

The database is now correct. But within the same persistence context (Day 162), `customer.getOrders()`
is stale — so a validation reading that collection sees the wrong thing, passes or fails wrongly, and
everything looks fine after a restart because the collection reloads from the database. **A bug that
disappears when you restart is the hardest kind to chase**, and this is one of the most common
sources of them.

## ⭐ The fix: a synchronisation helper, always

```java
@Entity
public class Customer {
    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();

    public void addOrder(Order order) {         // ⭐ the ONLY way to add
        orders.add(order);
        order.setCustomer(this);                // ⭐ set the owning side
    }

    public void removeOrder(Order order) {
        orders.remove(order);
        order.setCustomer(null);                // ⭐ or orphanRemoval never fires
    }
}
```

**Every bidirectional relationship needs this pair, and the setters on both sides should be
package-private or absent** so nobody can bypass them. Day 141's package-by-feature makes that
enforceable.

# Part 2 — The four cardinalities, and what to actually use

| Mapping | Reality | Verdict |
|---|---|---|
| **`@ManyToOne`** | one FK column | ⭐ **the workhorse. Prefer it, alone, most of the time** |
| `@OneToMany(mappedBy)` | inverse view of a `@ManyToOne` | ✅ when you genuinely navigate that way |
| `@OneToMany` **without** `mappedBy` | ❌ creates a **join table** you did not ask for | avoid |
| `@OneToOne` | FK with a unique constraint | ⚠️ lazy is broken on the inverse side — see below |
| `@ManyToMany` | join table, no extra columns | ⚠️ ⭐ **usually wrong** — see below |

### ⭐ The unidirectional `@ManyToOne` is underrated

```java
@Entity
public class Order {
    @ManyToOne(fetch = LAZY) @JoinColumn(name = "customer_id")
    private Customer customer;
}
// ⭐ Customer has NO orders collection at all
```

**You lose nothing and avoid a great deal.** To get a customer's orders you write
`orderRepository.findByCustomerId(id, pageable)` — which is *better*, because it is paginated
(Day 152), filterable, and cannot accidentally load 40,000 rows into memory.

A `@OneToMany` collection on the "one" side is an **unbounded collection in your object model**. A
customer with 40,000 orders is one `getOrders()` call from an `OutOfMemoryError`. The collection is
only appropriate when the child count is genuinely small and bounded — order *items*, yes; a
customer's orders, no.

**Ask of every `@OneToMany`: is this collection bounded, and do I actually navigate it?** If either
answer is no, delete it.

### ⭐ `@OneToOne` and the lazy problem

```java
@Entity class Order {
    @OneToOne(mappedBy = "order", fetch = LAZY)     // ⭐ inverse side
    private Invoice invoice;
}
```

**Lazy does not work on the inverse side of a `@OneToOne`.** To decide whether `invoice` should be a
proxy or `null`, Hibernate must know whether a row exists — which requires a query. So it issues one
every time, eagerly, and your `LAZY` annotation is decoration.

Three ways out: make it unidirectional from the owning side (which does lazy correctly), use
`@MapsId` so they share a primary key, or accept it and use a projection when you do not need the
invoice. The `@MapsId` version is the cleanest:

```java
@Entity class Invoice {
    @Id private Long id;
    @OneToOne @MapsId @JoinColumn(name = "id") private Order order;   // ⭐ shared PK
}
```

### ⭐ Why `@ManyToMany` is usually wrong

```java
@ManyToMany
@JoinTable(name = "student_course",
           joinColumns = @JoinColumn(name = "student_id"),
           inverseJoinColumns = @JoinColumn(name = "course_id"))
private Set<Course> courses = new HashSet<>();
```

This works exactly until someone asks: *when* did they enrol? What grade? Who approved it? **The join
table needs a column, and `@ManyToMany` cannot have one.** Now you are migrating a live schema and
rewriting every query.

**The standard answer is to model the join as an entity from the start:**

```java
@Entity
public class Enrolment {
    @EmbeddedId private EnrolmentId id;
    @ManyToOne @MapsId("studentId") private Student student;
    @ManyToOne @MapsId("courseId")  private Course course;
    private Instant enrolledAt;                   // ⭐ the column that was always coming
    private String grade;
}
```

Two `@ManyToOne`s and an entity. More typing today, no migration later, and every query becomes
expressible.

**If you do keep `@ManyToMany`:** use `Set`, never `List`. With a `List`, removing one element makes
Hibernate **delete every join row and re-insert the survivors** — 500 deletes and 499 inserts to
remove one. A `Set` issues a single delete.

# Part 3 — Cascade and `orphanRemoval`

| Cascade | Meaning |
|---|---|
| `PERSIST` | saving the parent saves new children |
| `MERGE` | merging the parent merges children |
| `REMOVE` | ⚠️ deleting the parent deletes children |
| `ALL` | all of the above |
| **`orphanRemoval = true`** | ⭐ removing a child *from the collection* deletes its row |

**The rule that decides it:**

> **Cascade only along a composition — where the child cannot meaningfully exist without the parent.**

| Relationship | Cascade? |
|---|---|
| `Order` → `OrderItem` | ⭐ yes, `ALL` + `orphanRemoval`. An item without an order is meaningless |
| `Order` → `Customer` | ❌ **absolutely not.** Deleting an order must not delete the customer |
| `Customer` → `Order` | ❌ no. Deleting a customer must not silently delete their order history — that is a legal and accounting question, not a mapping one |

**`CascadeType.REMOVE` from the wrong side is how people delete production data.** A `@ManyToOne` with
`cascade = ALL` on it means removing one order deletes the customer, and every other order of that
customer if those also cascade. It reads as a small convenience and it is a data-loss bug.

**Also note `REMOVE` performance:** cascading a delete loads every child and issues one `DELETE` per
row. Deleting a customer with 40,000 orders is 40,001 statements. A bulk `delete from orders where
customer_id = ?` is one — at the cost of bypassing the persistence context, which Day 162 covers.

## `orphanRemoval` vs `CascadeType.REMOVE`

They are different and the difference matters:

- `REMOVE` — deleting the **parent** deletes children.
- `orphanRemoval` — **removing a child from the collection** deletes it, even if the parent lives.

```java
order.getItems().remove(item);        // with orphanRemoval → DELETE FROM order_items ...
                                      // without           → the row stays, orphaned with a null FK
```

Without `orphanRemoval`, that line leaves an orphan row — or fails the not-null constraint, which is
at least loud.

# Part 4 — Collection type, and the one that changes behaviour

| Type | Behaviour |
|---|---|
| `List` | ⭐ **bag semantics.** Order not preserved unless `@OrderBy`/`@OrderColumn`. Two `List` fetch-joins → a cartesian product (Day 161) |
| `Set` | ⭐ **requires correct `equals`/`hashCode`** (Day 158). Deduplicates, which is often what you want |
| `Map` | `@MapKey` — occasionally exactly right |
| `@OrderBy("placedAt DESC")` | ✅ ORDER BY in the generated SQL. Cheap and usually correct |
| `@OrderColumn` | ⚠️ maintains a position column — expensive on reorder |

**`@OrderBy` is the one to reach for.** `@OrderColumn` means Hibernate rewrites index values on every
insertion into the middle, which is a surprising amount of UPDATE traffic.

## `FetchType` — the default is a trap and Day 160 is about it

| Mapping | JPA default |
|---|---|
| `@ManyToOne` | ❌ **EAGER** |
| `@OneToOne` | ❌ **EAGER** |
| `@OneToMany` | ✅ LAZY |
| `@ManyToMany` | ✅ LAZY |

**⭐ Set `fetch = LAZY` on every `@ManyToOne` and `@OneToOne`, without exception.** The eager default
means loading an `Order` also loads its `Customer`, and that customer's eager `Address`, and so on —
a graph you never asked for, on every single query, forever. Day 160 is the full argument.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Adding to the inverse collection only | no FK written, no error |
| Setting the owning side only | in-memory collection stale; bug vanishes on restart |
| No synchronisation helpers | the two above, repeatedly, forever |
| `@OneToMany` without `mappedBy` | a surprise join table |
| Unbounded `@OneToMany` | one `getOrders()` from an OOM |
| `@ManyToMany` for anything real | the join table always needs a column eventually |
| `@ManyToMany` with `List` | removing one row deletes and reinserts all of them |
| `cascade = ALL` on a `@ManyToOne` | deleting a child deletes the parent |
| `REMOVE` on `Customer` → `Order` | silent deletion of history |
| Missing `orphanRemoval` | orphan rows or constraint failures |
| Expecting lazy on an inverse `@OneToOne` | it is always eager |
| Leaving `@ManyToOne` eager | Day 160's graph explosion |
| `Set` without correct `equals` | Day 158's bug, activated |

## Interview questions

**Q: What is the owning side?**
The side whose table holds the foreign key. Hibernate writes the FK only from that side, so a change
to a `mappedBy` collection is ignored at write time — silently. That is why bidirectional
relationships need synchronisation helpers that set both sides.

**Q: Why avoid `@ManyToMany`?**
Because the join table always ends up needing a column — enrolled-at, role, approved-by — and
`@ManyToMany` cannot carry one. Modelling the join as an entity with two `@ManyToOne`s costs a little
typing now and avoids a schema migration later. And with a `List` it deletes and reinserts every join
row to remove one.

**Q: When do you cascade?**
Only along a composition, where the child cannot exist without the parent — order to order-items,
yes. Never from child to parent, and never for something like customer-to-orders, where deleting
history is a business decision rather than a mapping one.

**Q: Why is a `@OneToMany` collection often a bad idea?**
It is unbounded in the object model. A customer with 40,000 orders is one method call from an OOM.
A repository query with a `Pageable` is bounded, filterable and usually what you actually wanted.

## 🎙️ Articulation drill

Two minutes: **"Explain the owning side and how you model relationships."**

Define owning by the foreign key column, then give the consequence that makes it matter: writes to
the inverse side are ignored silently, so every bidirectional relationship needs helpers that set
both. Then show judgement about what you map at all — a unidirectional `@ManyToOne` with a paginated
repository query rather than an unbounded collection, a join entity rather than `@ManyToMany` because
the join table always grows a column, and cascade only along a composition. Close on the blanket
rule: `LAZY` on every `@ManyToOne` and `@OneToOne`, because the JPA default is eager.
