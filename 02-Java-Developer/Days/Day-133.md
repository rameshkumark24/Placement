# Day 133

**L-133** · The bean lifecycle — callbacks, ordering, and clean shutdown

**Time:** 3 hrs · **Mode:** NEW

> Day 132 gave the container's two phases. Today is what happens to **one bean** from creation to
> destruction — every callback, in order — and why the shutdown half matters more than the startup
> half.
>
> Shutdown is Day 081's `SIGTERM` handling, now managed for you. Managed badly, it drops in-flight
> requests on every deploy.

# Part 1 — The full sequence

```
   ① Instantiate            constructor called, dependencies injected      (Day 131)
   ▼
   ② Aware callbacks        BeanNameAware, BeanFactoryAware,
                            ApplicationContextAware
   ▼
   ③ BeanPostProcessor.postProcessBeforeInitialization
   ▼
   ④ @PostConstruct         ⭐ your initialisation
   ▼
   ⑤ InitializingBean.afterPropertiesSet()
   ▼
   ⑥ @Bean(initMethod = "…")
   ▼
   ⑦ BeanPostProcessor.postProcessAfterInitialization   ⭐ PROXY CREATED (Day 132)
   ▼
   ═══ BEAN IS READY AND IN THE CONTAINER ═══
   ▼
   ⑧ @PreDestroy            ⭐ your cleanup
   ▼
   ⑨ DisposableBean.destroy()
   ▼
   ⑩ @Bean(destroyMethod = "…")
```

**Three of the ten are yours to use**, and the ordering between them is worth knowing precisely:

```java
@Component
public class ConnectionManager implements InitializingBean, DisposableBean {

    private Connection connection;

    public ConnectionManager(Config config) { … }     // ① dependencies are available here

    @PostConstruct                                     // ④ runs FIRST of the three
    void init() { this.connection = open(); }

    @Override public void afterPropertiesSet() { }     // ⑤ second — couples you to Spring

    @PreDestroy                                        // ⑧
    void cleanup() { connection.close(); }

    @Override public void destroy() { }                // ⑨
}
```

> **Prefer `@PostConstruct` / `@PreDestroy`.** They are standard Jakarta annotations, so the class
> stays framework-independent. `InitializingBean` and `DisposableBean` couple you to Spring for no
> benefit, and `initMethod` / `destroyMethod` exist for third-party classes you cannot annotate.

⚠️ **Spring Boot 3 note:** these moved from `javax.annotation` to **`jakarta.annotation`** (Day
185B's namespace migration). An old import silently does nothing — the method simply never runs,
which is a genuinely nasty failure because there is no error.

## ⭐ Why the constructor is not enough

```java
@Component
public class CacheWarmer {
    private final ProductRepository repo;

    public CacheWarmer(ProductRepository repo) {
        this.repo = repo;
        warmCache();                    // 💀 DO NOT do work in the constructor
    }

    @PostConstruct
    void warm() { … }                   // ✅ here instead
}
```

Three reasons, and the third is the one that surprises people:

1. **`this` escapes during construction** (Day 035) — the object is not fully built, and any
   `final`-field guarantee (Day 065) is void for anyone who sees it.
2. **Setter- and field-injected dependencies are not yet set** — only constructor arguments are.
3. **⭐ The proxy does not exist yet.** Proxies are created at step ⑦, *after* initialisation — so
   a `@Transactional` method called from the constructor **runs with no transaction at all**, and a
   `@Cacheable` call is not cached.

That third point generalises: **any Spring behaviour added by a proxy is unavailable to your own
constructor and, in fact, to `@PostConstruct` too.** If you need a transaction during startup,
publish an event and do the work in a listener, or use `TransactionTemplate` explicitly.

# Part 2 — Application events

The lifecycle of the *context*, as opposed to one bean:

```
ApplicationStartingEvent          before almost anything
ApplicationEnvironmentPreparedEvent   properties and profiles resolved
ApplicationContextInitializedEvent
ApplicationPreparedEvent          definitions loaded, beans not yet created
ContextRefreshedEvent             ⭐ all singletons created and initialised
ApplicationStartedEvent           context refreshed, runners not yet run
ApplicationReadyEvent             ⭐ EVERYTHING done — the app is serving
ApplicationFailedEvent            startup failed
ContextClosedEvent                shutdown beginning
```

```java
@Component
class Warmup {
    @EventListener(ApplicationReadyEvent.class)     // ⭐ the correct hook for "when everything is up"
    void onReady() { warmCaches(); }
}
```

**`@PostConstruct` versus `ApplicationReadyEvent` is a real distinction:**

| Use `@PostConstruct` | Use `ApplicationReadyEvent` |
|---|---|
| Initialising **this bean's own state** | Work needing **other beans** to be ready |
| Validating configuration | Cache warming, background schedulers |
| Cheap, local setup | Anything slow — it delays readiness, not construction |
| | Anything needing a **transaction or a proxy** |

**Doing slow work in `@PostConstruct` delays the whole context**, and every bean after it, with no
indication of why startup is slow. `ApplicationReadyEvent` runs once, after everything.

`ApplicationRunner` and `CommandLineRunner` are the alternative for startup tasks, and they run
before `ApplicationReadyEvent`:

```java
@Component
class Seeder implements ApplicationRunner {
    public void run(ApplicationArguments args) { … }     // ordered with @Order
}
```

## Your own events

```java
public record OrderPlaced(String orderId, Instant at) { }

@Service
class OrderService {
    private final ApplicationEventPublisher events;

    @Transactional
    public Order place(CreateOrderRequest req) {
        Order order = repo.save(req.toOrder());
        events.publishEvent(new OrderPlaced(order.id(), Instant.now()));
        return order;
    }
}

@Component
class EmailListener {
    @TransactionalEventListener(phase = AFTER_COMMIT)     // ⭐ only if the transaction COMMITS
    void on(OrderPlaced e) { … }
}
```

**Three things to know**, and the second is a correctness issue:

**Events are synchronous by default** — `publishEvent` blocks until every listener returns, in the
publisher's thread and transaction. A slow listener slows the request.

**⭐ `@TransactionalEventListener(AFTER_COMMIT)` is usually what you want.** A plain
`@EventListener` runs *inside* the transaction, so if the transaction subsequently rolls back you
have already sent the email for an order that does not exist — Day 124's dual-write problem, in
miniature.

**`@Async` on a listener moves it off-thread** (Day 177) — and then it loses the transaction and the
`ThreadLocal` context (Day 066A), and a failure is invisible to the caller. That is often correct;
it must be deliberate.

> **In-process events decouple beans, and Day 131 used them to break a circular dependency.** For
> anything that must survive a crash, they are not enough — use the outbox (Day 124).

# Part 3 — ⭐ Shutdown

**The half that matters in production**, and the one most applications get wrong.

```
SIGTERM (Day 081)
   ▼
Spring registers a shutdown hook  →  context.close()
   ▼
1. Publish ContextClosedEvent
2. ⭐ Stop the web server accepting NEW requests
3. ⭐ Wait for in-flight requests to complete (up to a timeout)
4. Destroy singletons in REVERSE dependency order
       @PreDestroy → destroy() → destroyMethod
5. Close the context
```

**Steps 2 and 3 do not happen unless you enable them:**

```properties
server.shutdown=graceful                              # ⭐ NOT the default
spring.lifecycle.timeout-per-shutdown-phase=25s       # ⭐ must be < the platform grace period
```

Without `server.shutdown=graceful`, Tomcat stops immediately and **every in-flight request is
dropped** — on every deploy, invisibly, as occasional 502s that nobody attributes to deployment.

**The 25-second value is not arbitrary.** Kubernetes sends `SIGTERM`, waits
`terminationGracePeriodSeconds` (default 30) and then sends `SIGKILL` (Day 081). Your drain budget
must finish inside that window, with margin.

**Reverse-order destruction matters**: if `OrderService` depends on `DataSource`, the service is
destroyed first, so it can still use the connection pool during its own cleanup. Building that
ordering by hand was one of Day 130's arguments for a container.

## The full graceful-shutdown picture

```java
@Component
class ShutdownAware {
    @EventListener(ContextClosedEvent.class)
    void onShutdown() {
        log.info("shutting down — draining");
        // readiness has ALREADY started failing if you use Actuator's graceful support
    }
}
```

```properties
management.endpoint.health.probes.enabled=true
management.endpoints.web.exposure.include=health
```

Boot then exposes `/actuator/health/liveness` and `/actuator/health/readiness` and — crucially —
**sets readiness to `OUT_OF_SERVICE` when shutdown begins**, so the load balancer stops sending
traffic *before* the drain starts (Day 128).

**The correct deployment sequence, which you should be able to state:**

```
1. SIGTERM
2. Readiness → DOWN            ⇒ the LB stops routing new requests to this instance
3. Wait for the LB's own health-check interval to notice   ⚠️ often forgotten
4. Drain in-flight requests
5. Close pools and resources in reverse dependency order
6. Exit — inside the grace period
```

**Step 3 is the one people miss.** Failing readiness is not instantaneous from the load balancer's
perspective — it discovers it on its next check, up to several seconds later, and it will keep
sending requests until then. A `preStop` sleep of a few seconds before shutdown begins is the
standard fix, and without it you drop requests even with graceful shutdown enabled.

# Part 4 — What to do in each callback

| Callback | Do | Do not |
|---|---|---|
| Constructor | Assign dependencies, validate arguments | ⚠️ Any work; anything needing a proxy |
| `@PostConstruct` | Validate config, cheap local setup | Slow work; anything needing other beans; anything transactional |
| `ApplicationReadyEvent` | Cache warming, start schedulers, register with discovery | Anything that must block startup |
| `@PreDestroy` | Flush buffers, close resources this bean owns, deregister | Anything slow or unbounded |
| `ContextClosedEvent` | Application-wide shutdown coordination | |

**Two rules for `@PreDestroy`:**

**It must be fast and bounded.** You have seconds, not minutes. An unbounded flush blocks the whole
shutdown until `SIGKILL` arrives, at which point nothing is flushed at all.

**It does not run on `SIGKILL`, `Runtime.halt()`, or a JVM crash** (Day 081). So `@PreDestroy` is for
*graceful* cleanup only — anything that must survive a hard kill needs to be durable, not cleaned up
at exit.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Work in the constructor | `this` escapes; injections incomplete; **no proxy yet** |
| `@Transactional` called from `@PostConstruct` | No transaction — the proxy does not exist yet |
| `javax.annotation` imports in Boot 3 | The callback silently never runs |
| Slow work in `@PostConstruct` | Delays the entire context with no visible cause |
| Plain `@EventListener` for post-commit work | Side effect fires even when the transaction rolls back |
| Assuming events are asynchronous | They block the publisher's thread |
| `@Async` listener without considering context | Loses the transaction and the MDC/`ThreadLocal` |
| No `server.shutdown=graceful` | In-flight requests dropped on every deploy |
| Shutdown timeout ≥ the platform grace period | `SIGKILL` mid-drain |
| No delay between readiness-down and drain | The LB is still routing; requests dropped |
| Unbounded work in `@PreDestroy` | Blocks shutdown until it is killed |
| Relying on `@PreDestroy` for durability | It does not run on `SIGKILL` or a crash |

## Interview questions

**Q: Give the bean lifecycle in order.**
Instantiate and inject, `Aware` callbacks, `postProcessBeforeInitialization`, `@PostConstruct`,
`afterPropertiesSet`, custom `initMethod`, `postProcessAfterInitialization` — where the proxy is
created — then the bean is in use, and on shutdown `@PreDestroy`, `destroy()` and the custom
`destroyMethod`.

**Q: Why not do initialisation work in the constructor?**
`this` escapes before the object is fully constructed, non-constructor injections have not happened,
and — most importantly — the proxy does not exist yet, so `@Transactional` or `@Cacheable` on a
method called from the constructor does nothing.

**Q: `@PostConstruct` or `ApplicationReadyEvent`?**
`@PostConstruct` for this bean's own cheap setup and configuration validation. `ApplicationReadyEvent`
for anything needing other beans, anything slow, or anything requiring a proxy — because it runs once
after the whole context is up.

**Q: Why use `@TransactionalEventListener` rather than `@EventListener`?**
A plain listener runs inside the publisher's transaction, so the side effect happens even if that
transaction later rolls back — an email for an order that does not exist. `AFTER_COMMIT` runs the
listener only if the transaction commits.

**Q: Are Spring events asynchronous?**
No, synchronous by default — in the publisher's thread and transaction. `@Async` makes them
asynchronous, but the listener then loses the transaction and the `ThreadLocal` context, and failures
become invisible to the caller.

**Q: How do you shut down a Spring Boot application cleanly?**
Enable `server.shutdown=graceful` with a `timeout-per-shutdown-phase` below the platform's grace
period. On `SIGTERM`, readiness goes down, the load balancer stops routing, in-flight requests drain,
and singletons are destroyed in reverse dependency order. Add a short delay before draining so the
load balancer has actually noticed.

**Q: Why reverse-order destruction?**
So a bean can still use its dependencies during its own cleanup — the service is destroyed before the
connection pool it needs.

## 🎙️ Articulation drill

Two minutes: **"What happens when your service receives `SIGTERM` during a deploy?"**

Spring's shutdown hook closes the context: readiness goes down so the load balancer stops routing,
in-flight requests drain within the configured timeout, then singletons are destroyed in reverse
dependency order. Then the two things that are easy to get wrong — the timeout must be inside the
platform's grace period, and you need a short delay before draining because the load balancer takes
time to notice. Without `server.shutdown=graceful` none of it happens and every deploy drops
requests.
