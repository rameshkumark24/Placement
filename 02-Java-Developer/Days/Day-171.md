# Part 1 — The one line, and what it does

```java
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();     // ⭐ this one
}
```

```
{bcrypt}$2a$10$N9qo8uLOickgx2ZMRZoMye...
 ▲       ▲
 │       └── the hash, in that algorithm's own format
 └── ⭐ the algorithm ID, stored WITH the hash
```

**⭐ `DelegatingPasswordEncoder` is the correct default and the reason is the prefix.** Each hash
records which algorithm produced it, so:

- **verification** reads the prefix and routes to the right encoder — so bcrypt and argon2 hashes can
  coexist in one column;
- **new passwords** are encoded with the current default;
- **changing the default** does not invalidate anything.

Without the prefix, changing algorithms means a flag day: every user locked out, or a second column
and bespoke branching. **The prefix is what makes Part 3's migration possible at all.**

```java
@Bean
PasswordEncoder passwordEncoder() {
    String idForEncode = "argon2";
    Map<String, PasswordEncoder> encoders = Map.of(
        "argon2", Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8(),
        "bcrypt", new BCryptPasswordEncoder(12),
        "scrypt", SCryptPasswordEncoder.defaultsForSpringSecurity_v5_8());
    return new DelegatingPasswordEncoder(idForEncode, encoders);           // ⭐ argon2 for new
}
```

## Choosing the algorithm and the work factor

| Encoder | Verdict |
|---|---|
| **`Argon2PasswordEncoder`** | ⭐ **first choice.** Memory-hard — Day 112's key property, because GPUs and ASICs are memory-constrained, not compute-constrained |
| `SCryptPasswordEncoder` | ✅ also memory-hard. Fine |
| `BCryptPasswordEncoder` | ✅ **still perfectly acceptable.** Battle-tested, everywhere. ⚠️ ⭐ **truncates at 72 bytes** |
| `Pbkdf2PasswordEncoder` | ⚠️ FIPS environments only — not memory-hard |
| `NoOpPasswordEncoder` | ❌ ⭐ deprecated *for a reason*. Never, including in tests |
| `MessageDigestPasswordEncoder` (MD5/SHA) | ❌ legacy verification only. Day 112's 100-billion-per-second numbers |

**⭐ bcrypt's 72-byte truncation is a real vulnerability and it is not obvious.** Everything past 72
bytes is ignored, so a 100-character passphrase is silently reduced. Worse, some systems pre-hash
with SHA-256 and base64 the result, which can introduce a null byte — and older bcrypt
implementations truncate at the first null, reducing the effective password to almost nothing. If you
allow long passwords, use argon2.

**Calibrate the cost, do not copy it.** Day 112's rule: **target 250–500 ms per hash on your
production hardware.**

```java
@Test
void hashingCostIsCalibrated() {
    var encoder = new BCryptPasswordEncoder(12);
    long start = System.nanoTime();
    encoder.encode("a-representative-password");
    long ms = (System.nanoTime() - start) / 1_000_000;
    assertThat(ms).isBetween(200L, 600L);        // ⭐ fails when hardware changes
}
```

**⭐ And the operational consequence people forget:** 400 ms of CPU per login means an unthrottled
login endpoint is a CPU denial-of-service vector — a handful of requests per second per core is all
it takes. Day 170's rate limiting is not optional, and this is why.

# Part 2 — The rules that surround the encoder

**Encoding is one line. These are the rest of the system, and Day 112 covered each in principle.**

| Rule | Detail |
|---|---|
| ⭐ **Never log the password** | not in a request-logging filter (Day 151), not in `toString()`, not in a debug statement, not in a validation error message |
| ⭐ **Never return the hash** | Day 147 — a DTO makes it structurally impossible |
| **Enforce length, not composition** | ⭐ 12+ characters beats "one uppercase, one symbol", which produces `Password1!` — NIST agrees |
| ⭐ **Check against breach lists** | k-anonymity against Have I Been Pwned: send 5 characters of the SHA-1, match the rest locally. **You never transmit the password or its full hash** |
| **Cap the length** | ⭐ 128 characters. A 10 MB password is a hash-CPU DoS |
| **Rate limit login** | Day 122 — by IP *and* username |
| **Never enforce rotation** | ⭐ periodic forced changes produce `Summer2026!` → `Autumn2026!`. NIST removed this recommendation |
| **`char[]` over `String` where practical** | a `String` lingers in the heap until GC — visible in a heap dump (Day 143). Spring's API uses `CharSequence`, so this is partial at best |

## The reset flow, which is where accounts are actually stolen

Day 112 gave ten rules. The three that are most often broken in Spring code:

```java
public void requestReset(String email) {
    String token = generateToken();                       // ⭐ 1. SecureRandom, 32 bytes
    users.findByEmail(email).ifPresent(user ->
        resets.save(new ResetToken(
            user.getId(),
            hash(token),                                  // ⭐ 2. store the HASH, not the token
            Instant.now().plus(Duration.ofMinutes(15)))));  // ⭐ 3. short expiry, single use
    mailer.send(email, resetLink(token));                 // ⭐ 4. same response whether or not found
}
```

1. **`SecureRandom`, never `Random`** — `Random` is a linear congruential generator, so observing a
   few outputs predicts the rest.
2. ⭐ **Store the hash of the token.** A reset token is a live credential (Day 147's point): a leaked
   database or a stray log line otherwise hands over every pending reset.
3. **Single use, short expiry, and invalidate all sessions on success** (Day 172) — otherwise an
   attacker who had a session keeps it after the victim recovers the account.

# Part 3 — ⭐ Migrating 200,000 users to a stronger algorithm

**The constraint: you cannot rehash a password you do not have.** The plaintext exists only for the
instant a user logs in. So the migration is opportunistic — and the mechanism is **upgrade on
successful login**.

```java
@Bean
DaoAuthenticationProvider authenticationProvider(UserDetailsService uds, PasswordEncoder enc) {
    var provider = new DaoAuthenticationProvider();
    provider.setUserDetailsService(uds);
    provider.setPasswordEncoder(enc);
    return provider;
}
```

```java
@Component
public class PasswordUpgradeService implements UserDetailsPasswordService {   // ⭐ Spring calls this

    private final UserRepository users;

    @Override
    @Transactional
    public UserDetails updatePassword(UserDetails user, String newEncodedPassword) {
        users.updatePasswordHash(user.getUsername(), newEncodedPassword);      // ⭐ argon2 now
        log.info("password_hash_upgraded username={}", user.getUsername());    // Day 127
        return withNewPassword(user, newEncodedPassword);
    }
}
```

**How it works:** after a successful authentication, `DaoAuthenticationProvider` asks the encoder
`upgradeEncoding(storedHash)`. `DelegatingPasswordEncoder` returns `true` when the stored prefix is
not the current default. Spring then re-encodes the **plaintext it already has in hand** and calls
`updatePassword`.

**⭐ The user logs in normally and their hash is silently upgraded.** No reset email, no lockout, no
announcement.

## The migration plan, end to end

```
1. Deploy DelegatingPasswordEncoder with idForEncode = "bcrypt"     ⭐ no behaviour change
   → new hashes get {bcrypt} prefixes; existing bare hashes still verify (see below)
2. Backfill: prefix existing hashes in the database with {bcrypt}   ⭐ one Flyway migration
3. Deploy UserDetailsPasswordService                                 ⭐ upgrades start
4. Change idForEncode to "argon2"                                    ⭐ new + logins → argon2
5. Track the metric. Wait months.
6. For the tail: force a reset for accounts still on bcrypt after N months
```

**Step 2 needs care.** A bare hash with no prefix throws
`IllegalArgumentException: There is no PasswordEncoder mapped for the id "null"` — a total login
outage. Two ways to handle it:

```sql
-- Flyway (Day 166): prefix everything, idempotently
update users set password_hash = '{bcrypt}' || password_hash where password_hash not like '{%';
```

```java
// or a safety net for stragglers
var delegating = new DelegatingPasswordEncoder(idForEncode, encoders);
delegating.setDefaultPasswordEncoderForMatches(new BCryptPasswordEncoder());   // ⭐ unprefixed → bcrypt
```

**Track it, or you will never finish:**

```java
Gauge.builder("users.password.legacy_hash_count", users::countLegacyHashes)
     .register(registry);                                      // ⭐ Day 143
```

**⭐ Step 6 is the part people omit, and it is what makes the migration real.** Inactive accounts never
log in, so they never upgrade. Left alone, a "completed" migration still has 15,000 SHA-1 hashes in
it three years later. Decide the deadline up front, then force a reset for the remainder — and note
that forcing a reset here is legitimate precisely because it is not periodic rotation.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| A specific encoder instead of `DelegatingPasswordEncoder` | no algorithm migration path, ever |
| Changing algorithms without the prefix | every user locked out |
| Unprefixed legacy hashes with no default-for-matches | total login outage at deploy |
| Copying a work factor from a blog | wrong on your hardware in both directions |
| No calibration test | hardware upgrade silently weakens hashing |
| bcrypt with long passphrases | 72-byte truncation |
| `NoOpPasswordEncoder` in tests | it reaches production eventually |
| Composition rules instead of length | produces predictable passwords |
| No breach-list check | the most common real-world compromise |
| No password length cap | hash-CPU DoS |
| Storing the reset token, not its hash | a leaked table is every pending account |
| `Random` for tokens | predictable |
| Not invalidating sessions after a reset | the attacker keeps their session |
| Forced periodic rotation | measurably weaker passwords |
| No upgrade metric or deadline | migration never completes |

## Interview questions

**Q: Which `PasswordEncoder` do you use?**
`DelegatingPasswordEncoder`, with argon2 as the default for new hashes. The reason is the algorithm
prefix stored with each hash: it lets multiple algorithms coexist, so I can change the default
without invalidating a single existing password.

**Q: How do you migrate 200,000 users from bcrypt to argon2?**
Opportunistically, on login — because the plaintext only exists at that moment. Implement
`UserDetailsPasswordService`; after a successful authentication Spring notices the stored hash is not
the current algorithm and re-encodes the password it already has. Then track the count of legacy
hashes as a gauge and force a reset for the inactive tail, or the migration never completes.

**Q: Why argon2 over bcrypt?**
Memory-hardness. GPUs and ASICs give attackers enormous parallel *compute*, but memory per core is
expensive, so a memory-hard function narrows the attacker's advantage far more than raising an
iteration count. Also bcrypt silently truncates at 72 bytes, which matters if you allow passphrases.

**Q: What password rules do you enforce?**
Length, not composition — 12 characters minimum, capped at 128 — plus a breach-list check via
k-anonymity against Have I Been Pwned. No forced periodic rotation, because it produces predictable
increments; NIST removed that recommendation.

## 🎙️ Articulation drill

Two minutes: **"How do you store passwords, and how would you change the algorithm later?"**

Argon2 through `DelegatingPasswordEncoder`, and lead with *why the delegating one* — the prefix
