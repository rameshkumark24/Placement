# Day 410

**L-410** · ⭐⭐ Consensus — Raft in detail

**Time:** 3+ hrs · **Mode:** NEW

> **⭐⭐ Any two majorities of the same set must share at least one member. That single arithmetic fact is
> why consensus works, and everything in Raft is machinery built around it.**
>
> Today: leader election and why the randomised timeout is load-bearing, **the voting restriction that
> gives safety**, log replication and the commit rule, what consensus costs on every write, and **every
> system you already use that is running Raft underneath.**

---

# Part 1 — ⭐⭐ The quorum intersection, first

```
⭐ 5 nodes. Any majority = 3.
⭐   Majority M1 = {A,B,C}      Majority M2 = {C,D,E}
⭐   ⇒ ⭐⭐ THEY OVERLAP AT C. ⭐⭐ They MUST — 3 + 3 = 6 > 5.

⭐ ⇒ ⭐⭐ So if a value was accepted by a majority, ANY future majority CONTAINS A NODE THAT SAW IT.
⭐ ⇒ ⭐⭐ Decisions cannot be forgotten, and two conflicting decisions cannot both hold.
```

| ⭐ Cluster size | ⭐ Majority | ⭐⭐ Tolerates |
|---|---|---|
| ⭐ 3 | 2 | ⭐ **1 failure** |
| ⭐⭐ **5** | ⭐ 3 | ⭐⭐ **2 failures — the usual sweet spot** |
| ⭐ 7 | 4 | ⭐ 3 (and every write now waits for 4) |
| ⭐⭐ **4** | ⭐ 3 | ⭐⭐ **still only 1 — an even node buys NOTHING and costs latency** |
| ⭐⭐ **2** | ⭐ 2 | ⭐⭐ **0 — the worst configuration in distributed systems** |

> **⭐⭐ Odd numbers, always.** Four nodes tolerate exactly as many failures as three while requiring one
> more acknowledgement per write. **And a two-node cluster cannot form a majority after losing either
> node, so it is strictly worse than a single node** — it has two things that can break and no ability to
> survive either.

# Part 2 — ⭐⭐ Raft: three states and a term

```
⭐⭐ STATES:  ⭐ FOLLOWER  →(election timeout)→  ⭐ CANDIDATE  →(majority of votes)→  ⭐⭐ LEADER
⭐⭐ TERM: a monotonically increasing number — ⭐⭐ a LOGICAL CLOCK for leadership (Day 409).
⭐   ⇒ ⭐⭐ AT MOST ONE LEADER PER TERM. ⭐ Any message with a higher term makes you a follower, immediately.
```

## ⭐⭐ Leader election

```
⭐ 1. Follower hears no heartbeat for ⭐⭐ a RANDOMISED election timeout (e.g. 150–300 ms)
⭐ 2. ⇒ becomes CANDIDATE, ⭐ increments its term, votes for itself
⭐ 3. ⇒ sends RequestVote to everyone
⭐ 4. ⭐ Each node votes ⭐⭐ AT MOST ONCE PER TERM, first come first served
⭐ 5. ⭐⭐ Majority of votes ⇒ LEADER ⇒ sends heartbeats immediately to suppress other elections
```

| ⭐⭐ Why the timeout is RANDOMISED — this is the elegant bit | |
|---|---|
| ⭐ Fixed timeouts | ⭐⭐ **everyone times out together, everyone becomes a candidate, votes split, nobody wins** |
| ⭐ ⇒ they all time out together again | ⭐⭐ **a split-vote loop that can continue indefinitely** |
| ⭐⭐ **Randomising** | ⭐⭐ **one node almost always times out first and wins before the others start** |
| ⭐ Cost of tuning | too short ⇒ needless elections; too long ⇒ slow failover |

## ⭐⭐ The voting restriction — where safety actually comes from

```
⭐⭐ A voter REFUSES a candidate whose log is LESS UP-TO-DATE than its own.
⭐   "More up-to-date" = higher last log TERM, or same term and longer log.
⭐
⭐ ⇒ ⭐⭐ A candidate needs a MAJORITY of votes.
⭐ ⇒ ⭐⭐ Any committed entry is on a MAJORITY of logs.
⭐ ⇒ ⭐⭐ Those two majorities INTERSECT (Part 1).
⭐ ⇒ ⭐⭐ THEREFORE: a winning candidate's log ALREADY CONTAINS EVERY COMMITTED ENTRY.
⭐ ⇒ ⭐⭐ Committed data can never be lost by a leader change. ⭐ That is the whole safety argument.
```

> **⭐ If you can state that four-line chain, you understand Raft better than most people who have read
> the paper.** Everything else — heartbeats, terms, log matching — is mechanism. **This is the theorem.**

# Part 3 — ⭐⭐ Log replication and the commit rule

```
⭐ Client → LEADER (⭐⭐ all writes go through the leader, always)
⭐   1. leader APPENDS to its own log (uncommitted)
⭐   2. leader sends ⭐ AppendEntries to followers
⭐      ⭐⭐ carrying prevLogIndex + prevLogTerm — ⭐⭐ THE CONSISTENCY CHECK
⭐      ⇒ follower rejects if its log does not match there ⇒ leader backs up and retries
⭐      ⇒ ⭐⭐ this forces every follower's log to converge on the leader's
⭐   3. ⭐⭐ once a MAJORITY have written it ⇒ the entry is COMMITTED
⭐   4. leader applies it to the state machine and responds to the client
⭐   5. followers learn commitIndex from the next heartbeat and apply it too
```

| ⭐ Property | |
|---|---|
| ⭐⭐ **Log Matching** | ⭐⭐ if two logs have an entry with the same index and term, **all preceding entries are identical** |
| ⭐⭐ **Leader Append-Only** | ⭐⭐ **a leader never overwrites its own entries** — followers' conflicting entries are truncated |
| ⭐ Committed is permanent | ⭐ and a commit is majority-durable, not leader-durable |

⚠️ **A subtle rule worth knowing because interviewers who have read the paper ask it: a new leader must
not commit entries from *previous* terms merely by counting replicas.** It commits them **indirectly**,
by committing one entry of its own current term. **Skipping this allows a committed-looking entry to be
overwritten** — one of the few genuinely hard corners of the algorithm.

## ⭐⭐ What consensus costs

```
⭐⭐ EVERY WRITE = a round trip from the leader to a MAJORITY.
⭐   same-AZ  (~0.5 ms)  ⇒ ⭐ ~1 ms floor per write
⭐   multi-AZ (~1–2 ms)  ⇒ ⭐ ~2–4 ms floor
⭐   ⭐⭐ CROSS-REGION (~70 ms) ⇒ ⭐⭐ ~140 ms FLOOR ON EVERY SINGLE WRITE.
⭐ ⇒ ⭐⭐ "Just put the Raft cluster across three regions for durability" is a decision to
⭐   ⭐⭐ add 140 ms to every write, forever. ⭐ Sometimes correct. Never free.
⭐ ⇒ ⭐ And the leader is a single write bottleneck ⇒ ⭐⭐ SHARD (many Raft groups) to scale writes.
```

| ⭐ Reads are their own problem | |
|---|---|
| ⭐⭐ **Read from the leader** | ⭐⭐ still needs proof it is *still* leader — a heartbeat round trip, or a **lease** |
| ⭐ Lease reads | ⭐ fast; correctness depends on **bounded clock drift** (Day 409) |
| ⭐⭐ **Read from a follower** | ⭐⭐ **fast and possibly stale — a deliberate configuration choice, not a bug** |
| ⭐ ReadIndex | the standard linearizable-read protocol without a full log write |

# Part 4 — ⭐ Membership, and where you already meet Raft

| ⭐ Concern | |
|---|---|
| ⭐⭐ **Membership changes** | ⭐⭐ adding/removing nodes naively can create **two disjoint majorities** — two leaders |
| ⭐ Raft's answer | ⭐ **joint consensus** (both configurations must agree during the change), or one node at a time |
| ⭐ Log compaction | ⭐ snapshot the state machine and discard the prefix |
| ⭐ Pre-vote | ⭐⭐ stops a partitioned node returning with a high term and disrupting a healthy leader |

| ⭐⭐ Systems running Raft (or a close relative) | |
|---|---|
| ⭐⭐ **etcd** | ⭐⭐ **and therefore all of Kubernetes' state** (Day 377) |
| ⭐ Consul | service discovery, KV |
| ⭐⭐ **Kafka KRaft** | ⭐ the metadata quorum that replaced ZooKeeper (Day 403) |
| ⭐ RabbitMQ quorum queues | ⭐ Day 404 |
| ⭐ CockroachDB / TiKV | ⭐⭐ **one Raft group per data range** — this is how they scale writes |
| ⭐ MongoDB | Raft-like replica set elections |
| ⭐ ZooKeeper | ZAB — a different protocol, the same guarantees |

> **⭐ Paxos versus Raft in one line: Multi-Paxos provides the same guarantees and predates it; Raft was
> designed for understandability and won on that.** **The honest interview answer is "they solve the same
> problem; Raft decomposes it into election, replication and safety, which is why every recent system
> uses it."**

⚠️ **The most useful practical takeaway: you should almost never implement consensus.** Use etcd, use a
database that has it, use a quorum queue. **Hand-rolled leader election with a Redis key is the subject
of tomorrow, and it is where correctness usually dies.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **An even number of nodes** | ⭐⭐ same fault tolerance, one more ack per write |
| ⭐⭐ **A two-node cluster** | ⭐⭐ tolerates zero failures — worse than one node |
| ⭐ Fixed election timeouts | ⭐⭐ split votes that can loop indefinitely |
| ⭐ Election timeout tuned too low | needless elections during GC pauses |
| ⭐ Thinking the leader is elected by "most data" | ⭐⭐ it is majority vote **restricted** by log recency |
| ⭐ Missing the voting restriction | ⭐⭐ that is where safety comes from |
| ⭐ Committing previous-term entries by replica count | ⭐⭐ a committed entry can be overwritten |
| ⭐⭐ **Cross-region Raft without pricing the latency** | ⭐⭐ ~140 ms floor on every write |
| ⭐ Expecting one Raft group to scale writes | ⭐⭐ the leader is a bottleneck — shard into groups |
| ⭐ Assuming leader reads are automatically linearizable | ⭐ it must prove it is still leader |
| ⭐ Treating follower reads as a bug | ⭐ they are a deliberate staleness trade |
| ⭐ Naive membership changes | ⭐⭐ two disjoint majorities, two leaders |
| ⭐⭐ **Implementing consensus yourself** | ⭐⭐ use etcd |

## Interview questions

**Q: Why does consensus need a majority?**
Because any two majorities of the same set must overlap in at least one member — with five nodes, two sets
of three share at least one. That means if a value was accepted by a majority, any future majority
contains a node that saw it, so decisions cannot be forgotten and two conflicting decisions cannot both
hold. It is the whole basis of the algorithm, and it is why you use odd cluster sizes: four nodes tolerate
exactly one failure just like three, while requiring one more acknowledgement per write. A two-node
cluster is the worst configuration there is, because it cannot form a majority after losing either node —
strictly worse than running one.

**Q: Walk me through Raft leader election.**
A follower that hears no heartbeat for its election timeout becomes a candidate, increments the term,
votes for itself and requests votes. Each node votes at most once per term, first come first served, and a
majority wins. Two details carry the weight. The election timeout is randomised, because with fixed
timeouts every node becomes a candidate simultaneously, the votes split, nobody wins, and it repeats
indefinitely — randomisation means one node almost always times out first. And a voter refuses any
candidate whose log is less up to date than its own, which is where safety comes from.

**Q: How does Raft guarantee that committed data survives a leader change?**
A four-step argument. A candidate needs a majority of votes; every committed entry is on a majority of
logs; any two majorities intersect; and voters refuse candidates whose logs are less up to date.
Therefore any node that can win an election already has every committed entry in its log, so a leader
change cannot lose committed data. Everything else in Raft — heartbeats, terms, the log matching check —
is mechanism serving that theorem.

**Q: What does consensus cost?**
A round trip to a majority on every single write. Within one availability zone that is a floor of around a
millisecond; across zones, two to four; across regions with seventy milliseconds of latency, roughly a
hundred and forty milliseconds on every write, forever. So "put the Raft cluster across three regions for
durability" is a real decision with a permanent latency price, sometimes correct and never free. The
second cost is that all writes go through one leader, so a single Raft group does not scale writes —
systems like CockroachDB and TiKV run one Raft group per data range precisely to get around that.

**Q: Where do you already use Raft?**
etcd, which means all of Kubernetes' state; Consul; Kafka's KRaft metadata quorum since ZooKeeper was
removed; RabbitMQ quorum queues; CockroachDB and TiKV per range; and MongoDB's elections are Raft-like.
ZooKeeper uses ZAB, which is a different protocol with the same guarantees. The practical conclusion is
that you should essentially never implement consensus yourself — use etcd or a database that already has
it. Hand-rolled leader election on a Redis key is where correctness usually dies.

## 🎙️ Articulation drill

**Three minutes:** *"Explain consensus."*

**⭐ Open with the arithmetic, because it is the actual reason it works: any two majorities of the same
set must share a member. So if a value was accepted by a majority, every future majority contains someone
who saw it — decisions cannot be forgotten.**

**⭐ Then Raft in two moves. Election: a follower that stops hearing heartbeats becomes a candidate and
asks for votes, with a randomised timeout so the candidates do not all appear at once and split the vote
forever. And the restriction that matters — a voter refuses any candidate whose log is behind its own.**

**⭐ Then the safety theorem in one breath: a winner needs a majority, every committed entry is on a
majority, majorities intersect, and voters reject stale logs — therefore any possible leader already has
every committed entry. Committed data cannot be lost by a leader change.**

**⭐ Close with the cost, because that is what makes it an engineering answer: every write is a round trip
to a majority, so a cross-region cluster puts a hundred and forty milliseconds on every write forever,
and one Raft group has one leader and therefore one write bottleneck — which is why CockroachDB runs a
Raft group per range rather than per cluster.**
