# Day 411

**L-411** · Distributed locking, leader election and ⭐⭐ the fencing token

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ A lock with a timeout can expire while its holder is still working — a 15-second GC pause is
> enough. Now two processes both believe they hold it, and neither has done anything wrong.**
>
> Today: why every TTL-based lock is unsafe by construction, **the fencing token that is the only actual
> fix**, the Redlock debate settled with one question, leader election and lease renewal, and **the
> conditional write that usually means you never needed a lock at all.**

---

# Part 1 — ⭐⭐ Why the naive lock is broken

```java
// ⭐⭐ The lock everybody writes. It is unsafe, and the reason is not the code.
if (redis.set("lock:job", token, "NX", "PX", 30_000)) {
    try { doTheWork(); }
    finally { releaseIfMine("lock:job", token); }   // ⭐ Lua compare-and-delete
}
```

```
⭐⭐ THE FAILURE, WHICH REQUIRES NO BUG AND NO NETWORK PARTITION:
⭐   t=0    ⭐ Client A acquires the lock. TTL 30 s.
⭐   t=5    ⭐⭐ Client A enters a 40-SECOND STOP-THE-WORLD GC PAUSE.
⭐   t=30   ⭐⭐ The lock EXPIRES. Redis is behaving perfectly.
⭐   t=31   ⭐ Client B acquires the lock and starts working.
⭐   t=45   ⭐⭐ Client A WAKES UP, still believing it holds the lock, and WRITES.
⭐   ⇒ ⭐⭐ TWO WRITERS. ⭐⭐ Mutual exclusion violated with no bug anywhere.
```

| ⭐⭐ Why you cannot fix this by tuning | |
|---|---|
| ⭐ Longer TTL | ⭐⭐ longer outage when a holder genuinely dies; **and pauses have no upper bound** |
| ⭐ Shorter TTL | ⭐ more frequent spurious expiry |
| ⭐ "Check the lock before writing" | ⭐⭐ **the check and the write are not atomic** — pause between them |
| ⭐ A better lock service | ⭐⭐ **irrelevant — the problem is the CLIENT's pause, not the lock's correctness** |

> **⭐⭐ This is the ninth fallacy from Day 398 in its purest form: you cannot tell a paused process from
> a dead one, and the paused process cannot tell either.** No lock server can fix a client that stops
> existing for 40 seconds and then resumes as if nothing happened.

# Part 2 — ⭐⭐ The fencing token: the actual fix

```
⭐⭐ THE LOCK SERVICE RETURNS A MONOTONICALLY INCREASING TOKEN with every grant.
⭐   Client A acquires ⇒ ⭐ token 33
⭐   A pauses; lock expires
⭐   Client B acquires ⇒ ⭐⭐ token 34
⭐   B writes with token 34 ⇒ ⭐ storage records lastToken = 34
⭐   ⭐⭐ A wakes and writes with token 33 ⇒ ⭐⭐ 33 < 34 ⇒ ⭐⭐ THE STORAGE REJECTS IT.
```

```sql
-- ⭐⭐ The fence, implemented where it must be: AT THE RESOURCE.
UPDATE job_state
   SET payload = :new, last_token = :token
 WHERE job_id = :id
   AND last_token < :token;      -- ⭐⭐ rowsAffected = 0 ⇒ you are a ZOMBIE. Stop.
```

| ⭐⭐ The key insight | |
|---|---|
| ⭐⭐ **The RESOURCE must participate** | ⭐⭐ a lock the storage does not know about cannot be enforced |
| ⭐ Where tokens come from | ⭐ ZooKeeper `zxid` / sequential znodes · etcd revision · a database sequence |
| ⭐⭐ **Redis has no such token natively** | ⭐⭐ `INCR` is not the same — it is not tied to lock grants under partition |
| ⭐ If the resource cannot fence | ⭐⭐ **you cannot have a correct distributed lock. Accept it, or redesign.** |

⚠️ **Almost nobody implements fencing**, and most of the time nothing goes wrong — **because most locks
protect *efficiency*, not correctness.** Which is exactly the question you should be asking.

# Part 3 — ⭐⭐ The question that settles the whole debate

```
⭐⭐ "IS THIS LOCK FOR EFFICIENCY OR FOR CORRECTNESS?"

⭐⭐ EFFICIENCY: ⭐ two workers doing the same job is WASTE, not damage.
⭐   (regenerating a cache, sending a metrics roll-up, resizing an image)
⭐   ⇒ ⭐⭐ a simple Redis SET NX lock is FINE. ⭐ Occasional duplication costs money, not truth.

⭐⭐ CORRECTNESS: ⭐⭐ two writers CORRUPT DATA or DOUBLE-CHARGE.
⭐   ⇒ ⭐⭐ you need FENCING TOKENS + a consensus-backed lock service (etcd/ZooKeeper, Day 410)
⭐   ⇒ ⭐⭐ OR — better — ⭐⭐ DO NOT USE A LOCK AT ALL.
```

## ⭐⭐ The better answer: a conditional write

```sql
-- ⭐⭐ No lock. No lease. No token. No lock service. The RESOURCE arbitrates.
UPDATE seats
   SET status = 'HELD', held_by = :user, held_until = now() + interval '10 min'
 WHERE seat_id = :id
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND held_until < now()));
-- ⭐⭐ rowsAffected = 1 ⇒ you have it.  0 ⇒ someone else does.  ⭐ Atomic. Correct. Boring.
```

> **⭐⭐ This is Day 316's seat hold and Day 320A's pattern card, and it is the single most reusable
> answer in this entire roadmap: a limited resource claimed by an atomic conditional update and held
> with an expiry.** **The database's own atomicity is the lock**, so there is no second system to
> partition away from, no TTL to expire under a GC pause, **and no zombie problem — because the write
> itself is the claim.**

| ⭐ When you genuinely still need a lock | |
|---|---|
| ⭐ The resource is **external** and has no conditional write | ⭐ a third-party API, a printer, a file share |
| ⭐ You need **one leader** for a long-running role | ⭐ see Part 4 |
| ⭐ Coordination spans **several** resources | ⭐⭐ and then reconsider the design (Day 408) |

# Part 4 — ⭐ Leader election, and the lock recipes

| System | ⭐ Mechanism |
|---|---|
| ⭐⭐ **etcd** | ⭐⭐ **lease + key with `CreateRevision` as the fence**; the revision is a natural token |
| ⭐⭐ **ZooKeeper** | ⭐⭐ **ephemeral sequential znodes**; `zxid` is the token |
| ⭐ Kubernetes | ⭐ a `Lease` object — used by every controller's leader election |
| ⭐ Database | ⭐⭐ **a `leader` row with an expiry and a version — genuinely fine, and one fewer system** |
| ⭐ Redis | ⭐ efficiency-only, unless you add your own fence |

```
⭐⭐ THE ZOOKEEPER LOCK RECIPE, and why it is written that way:
⭐   1. create an EPHEMERAL SEQUENTIAL znode under /lock/
⭐   2. list children; ⭐ if yours is the lowest, YOU HOLD THE LOCK
⭐   3. ⭐⭐ otherwise WATCH ONLY THE NODE IMMEDIATELY BEFORE YOURS
⭐   ⇒ ⭐⭐ Why not watch the parent? ⭐⭐ THE HERD EFFECT: a release wakes ALL 500 waiters,
⭐     ⭐ all of whom re-list and go back to sleep. ⭐⭐ Watching your predecessor wakes exactly ONE.
⭐   ⇒ ⭐ Ephemeral = the node vanishes when the session dies ⇒ automatic release.
```

| ⭐⭐ Leader election's own hazard | |
|---|---|
| ⭐⭐ **"I think I am still the leader"** | ⭐⭐ **the same zombie problem, wearing a title** |
| ⭐ Renew the lease well before expiry | ⭐ renew at 1/3 of the TTL |
| ⭐⭐ **Stop working the moment renewal fails** | ⭐⭐ do not wait for expiry — **abandon the role immediately** |
| ⭐⭐ **Fence the leader's writes too** | ⭐⭐ include the lease revision on every write it makes |
| ⭐ Expect two leaders briefly | ⭐⭐ **design so that is survivable**, because it will happen |

⚠️ **A scheduled job "that must run exactly once" is the most common request here, and a lock is usually
the wrong tool.** **Make the job idempotent and claim its work with a conditional write** — `UPDATE jobs
SET claimed_by=?, claimed_at=now() WHERE id=? AND (claimed_at IS NULL OR claimed_at < now()-interval '5
min')`. **Then two schedulers firing is harmless**, which is a much stronger property than a lock that is
*probably* exclusive.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Assuming a TTL lock guarantees mutual exclusion** | ⭐⭐ a GC pause outlives the lease; two writers, no bug |
| ⭐ Trying to fix it by tuning the TTL | ⭐⭐ pauses have no upper bound |
| ⭐ Checking the lock before writing | ⭐⭐ check and write are not atomic |
| ⭐ Blaming the lock service | ⭐⭐ the problem is the client's pause |
| ⭐⭐ **No fencing token** | ⭐⭐ the only real fix, almost never implemented |
| ⭐ Fencing in the client instead of the resource | ⭐⭐ the resource must enforce it |
| ⭐ Not asking "efficiency or correctness?" | ⭐⭐ the question that decides the whole design |
| ⭐⭐ **Using a lock where a conditional write would do** | ⭐⭐ a whole extra system, and less safety |
| ⭐ Releasing a lock without checking ownership | ⭐ you release someone else's — use compare-and-delete |
| ⭐ Watching the parent znode | ⭐⭐ the herd effect — wake 500 to serve 1 |
| ⭐ Renewing a lease at 90% of TTL | ⭐ one slow renewal and you are out |
| ⭐⭐ **Continuing to work after a failed renewal** | ⭐⭐ you are a zombie leader |
| ⭐ Designing so two leaders is catastrophic | ⭐⭐ it will happen — make it survivable |
| A "run exactly once" job protected only by a lock | idempotency + conditional claim is stronger |

## Interview questions

**Q: What is wrong with a Redis lock with a TTL?**
It can expire while its holder is still working, and no bug is required — a long garbage collection pause,
a hypervisor stall or a network delay is enough. The holder wakes up still believing it owns the lock, the
lock has since been granted to someone else, and now two processes write. You cannot fix it by tuning the
timeout, because pauses have no upper bound, and you cannot fix it by checking the lock before writing,
because the check and the write are not atomic. Crucially, it is not the lock service's fault — the
problem is that a paused client cannot tell it was paused, which is the fundamental undetectability of
failure.

**Q: What is a fencing token?**
A monotonically increasing number returned with every lock grant, which the client must present on every
write, and which the storage system rejects if it is lower than the last one it saw. So a zombie holder
with token thirty-three cannot write after a new holder with token thirty-four has written. The key point
is that the resource has to participate — a lock the storage knows nothing about cannot be enforced, so
fencing is implemented as a condition on the update, not as a check in the client. ZooKeeper's zxid,
etcd's revision and a database sequence all provide suitable tokens; Redis has no equivalent natively.

**Q: How do you settle the Redlock argument?**
By asking what the lock is for. If it protects efficiency — two workers regenerating the same cache or
resizing the same image is waste rather than damage — then a simple Redis lock is entirely reasonable, and
occasional duplication costs money rather than correctness. If it protects correctness, where two writers
corrupt data or double-charge, then you need fencing tokens backed by a consensus system, and the Redlock
assumptions about bounded clock drift and bounded pauses are exactly what you cannot rely on. Framing it
that way makes the debate a design question rather than a theological one.

**Q: What would you do instead of a distributed lock?**
Usually a conditional write, letting the resource arbitrate. Updating a row where the status is available
or the previous hold has expired, and treating rows-affected as the answer, gives atomic exclusion using
the database's own guarantees — no second system to partition away from, no lease to expire during a
pause, and no zombie problem, because the write itself is the claim. That is the same mechanism as a seat
hold, a rate limiter and an SQS visibility timeout: a limited resource claimed atomically and held with an
expiry. I would only reach for a real lock when the resource is external and offers no conditional
operation, or when I need a single long-lived leader.

**Q: How do you do leader election safely?**
Use a lease from a consensus-backed system — etcd, ZooKeeper or a Kubernetes Lease — and renew at about a
third of the TTL rather than close to expiry. Two things matter more than the mechanism. The moment a
renewal fails you stop working immediately rather than waiting for the lease to expire, because between
those two points you are a zombie leader. And every write the leader makes carries the lease revision as a
fence, so a stale leader's writes are rejected. Then design the system so two leaders briefly coexisting is
survivable, because at some point it will happen regardless of what the algorithm promises.

## 🎙️ Articulation drill

**Two minutes:** *"How do you implement a distributed lock?"*

**⭐ Start by explaining why the question is a trap: any lock with a timeout can expire while its holder
is paused, and a long GC pause is enough — the holder wakes still believing it owns the lock and writes.
No bug is required, and no lock service can fix it, because the paused client cannot tell it was paused.**

**⭐ The only real fix is a fencing token: a monotonically increasing number issued with the lock and
checked by the resource on every write, so a zombie's older token is rejected by the database rather than
by trust. Which means the resource has to participate — a lock the storage does not know about cannot be
enforced.**

**⭐ Then the question that decides the design: is this lock for efficiency or correctness? If two workers
doing the same job is waste, a simple Redis lock is fine. If it corrupts data, I want fencing with etcd
— or, better, no lock at all: a conditional update where the row itself is the claim, which is atomic,
has no lease to expire, and is the same mechanism as a seat hold or a visibility timeout.**
