# Day 237 🔀

**J-237** · 🔀 **CORS from the other side** — ⭐⭐ it protects other sites from you

**Time:** 3 hrs · **Mode:** RECALL → NEW

> ⭐⭐ **The sentence to own: CORS is not a defence for your API — it is the browser relaxing a rule it
> imposes on *scripts*, so it protects a user's other tabs from your page, and an attacker with curl
> is entirely unaffected by any `@CrossOrigin` you write.**
>
> Today: the mental correction, ⭐ the preflight, ⭐⭐ the four errors, and the wildcard that cannot
> work with credentials.

---

# Part 1 — ⭐⭐ The correction

```
⭐⭐ WHAT THE SAME-ORIGIN POLICY IS ACTUALLY FOR

⭐   You are logged into bank.com. You visit evil.com.
⭐   evil.com runs: fetch("https://bank.com/balance", {credentials:"include"})
⭐   ⭐ THE REQUEST IS SENT. ⭐⭐ THE COOKIE IS ATTACHED. YOUR SPRING
⭐     CONTROLLER RUNS. ⭐ The browser then refuses to let evil.com
⭐     **READ THE RESPONSE**.

⭐   ⇒ ⭐⭐ SO CORS PROTECTS **bank.com's USER** FROM **evil.com's SCRIPT**.
⭐     IT DOES NOT PROTECT bank.com's API FROM ANYONE.
⭐   ⇒ ⭐⭐ AND NOTE: YOUR HANDLER ALREADY EXECUTED. If it was a
⭐     state-changing GET, THE DAMAGE IS DONE and CORS blocked only
⭐     the reading of the receipt. **THAT IS CSRF** (Day 235).
```

| ⭐ Belief | ⭐⭐ Reality |
|---|---|
| *"CORS secures my API"* | ⭐⭐ It does nothing against curl, Postman, or any server-to-server client |
| *"`*` is a vulnerability"* | ⭐ On a **public** API it is correct and normal. Only wrong **with credentials**. |
| *"A CORS error means Spring rejected it"* | ⭐⭐ Usually your controller **returned 200**. The *browser* hid the response from your JS. |

> ⭐ **Read that last row again in DevTools.** The Network tab shows the request and often a 200; the
> Console shows a CORS error. Both are true — and knowing that saves you an hour of debugging a
> service that is working fine.

# Part 2 — Simple requests vs preflight

```
⭐⭐ A "SIMPLE" REQUEST GOES STRAIGHT OUT — no preflight:
⭐   · GET, HEAD, or POST
⭐   · AND only "safe" headers
⭐   · AND Content-Type is text/plain, multipart/form-data, or
⭐     application/x-www-form-urlencoded

⭐⭐ ANYTHING ELSE IS PREFLIGHTED — and this catches everyone:
⭐   ⭐⭐ Content-Type: application/json  ⇒ **NOT SIMPLE**
⭐   ⭐ Authorization: Bearer ...        ⇒ NOT SIMPLE
⭐   ⭐ any custom header (X-Request-Id) ⇒ NOT SIMPLE
⭐   ⇒ ⭐⭐ SO ESSENTIALLY EVERY @RestController CALL IS PREFLIGHTED.
```

```java
// ⭐ Spring — the correct shape for a credentialed API
@Bean
CorsConfigurationSource corsConfigurationSource() {
    var config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com")); // ⭐⭐ EXPLICIT
    config.setAllowCredentials(true);                             //    never "*"
    config.setAllowedMethods(List.of("GET","POST","PATCH","DELETE"));
    config.setAllowedHeaders(List.of("content-type","authorization"));
    config.setMaxAge(86400L);            // ⭐⭐ CACHE THE PREFLIGHT
    var source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}
```

> ⭐⭐ **`maxAge` is a real performance setting.** Without it, every POST is two round trips. With it,
> one preflight per day per origin. **A free latency win people leave on the floor.**

# Part 3 — ⭐⭐ The four errors, decoded

| ⭐ Console says | ⭐⭐ What it means | Fix |
|---|---|---|
| *"No `Access-Control-Allow-Origin` header"* | ⭐⭐ Spring did not answer the preflight — **very often because a security filter rejected the OPTIONS request before CORS ran** | ⭐ `http.cors(withDefaults())` and ensure OPTIONS is permitted |
| *"…header has a value `*` that is not equal to the supplied origin"* | ⭐⭐ You sent credentials **and** returned `*`. **Forbidden combination.** | Echo the exact origin from an allow-list |
| *"Method PATCH is not allowed"* | The preflight response omitted it | Add to `setAllowedMethods` |
| *"Request header field x-tenant-id is not allowed"* | ⭐ Not in `setAllowedHeaders` | Add it |

```
⭐⭐ THE SPRING-SPECIFIC TRAP
⭐   ⭐ @CrossOrigin ON A CONTROLLER DOES NOT HELP IF SPRING SECURITY
⭐     REJECTS THE PREFLIGHT FIRST. ⭐⭐ AN OPTIONS REQUEST CARRIES NO
⭐     COOKIE AND NO AUTH HEADER — BY DESIGN — so an authenticated
⭐     filter chain 401s it, and the browser reports a CORS error
⭐     that has nothing to do with your CORS config.
⭐   ⇒ ⭐ THIS IS THE #1 "CORS DOESN'T WORK IN SPRING" CAUSE.

⭐⭐ AND THE ONE THAT IS ACTUALLY DANGEROUS
⭐   ❌ setAllowedOrigins(List.of(request.getHeader("Origin")))
⭐      + setAllowCredentials(true)
⭐   ⇒ ⭐⭐ THAT ALLOWS **EVERY** ORIGIN WITH COOKIES ATTACHED.
⭐     ⭐ ANY SITE CAN NOW READ YOUR API AS YOUR LOGGED-IN USER.
⭐   ⇒ ⭐ AN ALLOW-LIST, CHECKED, OR NOTHING.
⭐     ⭐⭐ AND setAllowedOriginPatterns WITH AN UNANCHORED PATTERN
⭐       MATCHES "evil-example.com.attacker.net". Anchor it.
```

# Part 4 — Making it a non-problem

```
⭐⭐ THE BEST CORS CONFIG IS NO CROSS-ORIGIN AT ALL

⭐   ① ⭐⭐ SAME ORIGIN: serve the app and the API from one origin,
⭐      /api/* routed to Spring.
⭐      ⇒ ⭐ NO CORS. NO PREFLIGHT. SameSite=Lax cookies just work.
⭐   ② dev proxy: Vite's server.proxy makes localhost:5173/api →
⭐      localhost:8080. ⭐ Dev matches prod, killing a whole class
⭐      of "works in dev" bugs.
⭐   ③ ⭐ SUBDOMAINS (app. + api.) still need CORS, but they are
⭐      SAME-SITE, so SameSite=Lax cookies work.
⭐   ④ genuinely different domains ⇒ ⭐⭐ CORS + SameSite=None; Secure
⭐      + A CSRF TOKEN. The most work, the most to get wrong.
```

> ⭐⭐ **Choosing same-origin deployment removes CORS, most CSRF exposure, and the `SameSite=None`
> requirement in one architectural decision** — a much better interview answer than any header config.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "explain CORS."**

Correct the framing first. **CORS isn't a defence for my API. It's the browser relaxing a rule it
imposes on scripts. If I'm logged into my bank and visit a malicious site, that site's fetch is still
sent, the cookie is still attached, and my controller still runs — the browser just refuses to let the
script read the response. So it protects the bank's user from the malicious page, not the bank's API
from anyone. Curl is unaffected.**

Add the consequence. **Because the request still happens, a state-changing GET is already done and CORS
only blocked reading the receipt. That's CSRF, which is why SameSite and an Origin check are separate
controls.**

Then the Spring-specific debugging insight, which is the useful part. **The number one cause of "CORS
doesn't work in Spring" isn't the CORS config — it's the security filter chain rejecting the preflight.
An OPTIONS request carries no cookie and no auth header by design, so an authenticated chain 401s it
and the browser reports a CORS error that has nothing to do with CORS. And generally, a CORS error
usually means my server replied 200 and the browser hid it — the Network tab showing success while the
console shows an error is both things being true.**

Close on the architectural answer. **The best CORS config is no cross-origin at all — serve the app and
API from one origin with `/api` routed to Spring. That removes CORS, most CSRF exposure and the
SameSite=None requirement in one decision, and it makes dev match prod.**
