# Day 317

**L-317** · Vending machine & ATM — the state pattern, and the money that must not diverge

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Two problems, one pattern, and one hard question each.**
>
> The vending machine's hard question is **change** — you can be unable to make it, and you must know
> that *before* taking the money. The ATM's is **atomicity** — the account debit and the cash leaving
> the slot are two different systems, and they can disagree.

# Part 1 — ⭐ The state pattern, and when it is actually worth it

```java
public interface VendingState {
    VendingState insertCoin(Machine m, Coin coin);
    VendingState select(Machine m, ItemCode code);
    VendingState dispense(Machine m);
    VendingState refund(Machine m);
}
```

```java
final class Idle implements VendingState {
    public VendingState insertCoin(Machine m, Coin c) { m.addCredit(c); return new HasCredit(); }
    public VendingState select(Machine m, ItemCode code) { throw new NoCreditInserted(); }
    public VendingState dispense(Machine m)             { throw new NothingSelected(); }
    public VendingState refund(Machine m)               { return this; }        // ⭐ harmless no-op
}
```

| ⭐ Decision | ⭐ Answer |
|---|---|
| ⭐ **Invalid operation — throw or ignore?** | ⭐ **throw for user errors, no-op for idempotent ones.** Say which and why |
| ⭐ **Who holds the state?** | ⭐ the machine holds a `VendingState` field; states return the next state |
| Do states hold data? | ⭐ **no — data lives on the machine; states are stateless and shareable** |

## ⭐ When the pattern earns its keep — and when it does not

| | ⭐ Enum + `switch` | ⭐ State classes |
|---|---|---|
| ⭐ **3 states, 2 events** | ⭐ **this. Less code, all logic visible in one place** | over-engineering |
| ⭐ **6+ states, 5+ events** | ⭐ a 30-case switch, edited for every new state | ⭐ **this — a new state is a new class** |
| ⭐ Behaviour per state | duplicated guards everywhere | ⭐ **encapsulated** |
| Seeing the whole machine | ⭐ **easy — one file** | ⭐ **harder — spread over N files** |

> **⭐ Say the trade rather than reaching for the pattern.** *"With four states and four operations I'd
> use a Java enum with abstract methods — it gives me per-state behaviour and keeps the whole machine
> in one file. I'd switch to separate classes when states start carrying their own collaborators."*
> **That is a better answer than either option alone**, and Java's enum-with-abstract-methods is the
> middle ground people forget:

```java
enum State {
    IDLE      { State insertCoin(Machine m, Coin c) { m.addCredit(c); return HAS_CREDIT; } },
    HAS_CREDIT{ State insertCoin(Machine m, Coin c) { m.addCredit(c); return this; }
                State select(Machine m, ItemCode k) { return m.canVend(k) ? DISPENSING : this; } };
    // ⭐ defaults throw; each constant overrides what it supports
}
```

# Part 2 — ⭐⭐ The vending machine's hard problem: change

```
⭐ Item costs £1.30. User inserts £2.00. Change due: £0.70.
⭐ Machine holds: 3 × 50p, 0 × 20p, 0 × 10p.
⭐ ⇒ CANNOT MAKE 70p. And you already took the £2.
```

> **⭐ The rule: check that change is available BEFORE accepting the sale, not after.** A machine that
> takes money and then cannot pay change has stolen from the customer — **and this is the design
> question, not the coin algorithm.**

```java
Optional<List<Coin>> changeFor(Money amount, CoinInventory inventory) { ... }

// ⭐ At selection time:
Money change = credit.minus(price);
if (changeFor(change, coins).isEmpty()) throw new CannotMakeChange(change);   // ⭐ refund the credit
```

## ⭐ Greedy is wrong in general — and the interviewer knows

| Coin system | Greedy for 6 | ⭐ Optimal |
|---|---|---|
| ⭐ {1, 2, 5, 10, 20, 50} (real currency) | ⭐ **correct** | — |
| ⭐ **{1, 3, 4}** | ⭐ **4+1+1 = 3 coins** | ⭐ **3+3 = 2 coins** |

```java
// ⭐ DP over amount, bounded by the coins actually IN the machine
// ⭐ (unbounded coin-change is the textbook version; this one is BOUNDED — you have 3 fifties, not ∞)
```

**⭐ Two things to say:** greedy is optimal for canonical systems like GBP/USD/EUR **so it is the
right production choice**, and it is provably not optimal in general — **and the machine's version is
*bounded* knapsack, because inventory is finite.** Naming the bounded distinction is the detail that
shows you read the problem rather than recalling the LeetCode version.

| ⭐ Also model | ⭐ Why |
|---|---|
| ⭐ **Coin inventory as part of the machine's state** | ⭐ it changes on every sale, both directions |
| ⭐ Restock and cash-collection operations | an operator is a second actor |
| ⭐ **Sold-out per slot, not per machine** | one empty slot is not an out-of-service machine |
| Partial refund on dispense failure | the jam case — see the ATM's journal below |

# Part 3 — ⭐⭐ The ATM's hard problem: two systems that can disagree

```
⭐ debit the account   (a database, elsewhere)
⭐ dispense the cash   (a physical machine, here)
⭐ ⇒ These are NOT one transaction. Anything in between can fail.
```

| Failure | ⭐ Consequence |
|---|---|
| ⭐ **Debited, cash not dispensed** | ⭐⭐ **the customer is robbed — the worst case** |
| ⭐ Cash dispensed, debit failed | the bank is robbed |
| Debited, dispensed, receipt fails | cosmetic |
| ⭐ **Power loss mid-dispense** | ⭐ **nobody knows how much came out** |

## ⭐ The journal — the answer, and it is how real ATMs work

```
⭐ 1. Write a JOURNAL entry: intent, amount, account, txn id     ⭐ ← durable, BEFORE anything
⭐ 2. Reserve/authorise the funds
⭐ 3. Dispense physically; record the actual notes dispensed
⭐ 4. Confirm the debit
⭐ 5. Mark the journal entry COMPLETE
⭐ ⇒ Any entry not COMPLETE is picked up by RECONCILIATION and resolved.
```

| ⭐ Property | ⭐ Why |
|---|---|
| ⭐ **Written before acting** | ⭐ **an intent record survives a crash; an in-flight operation does not** |
| ⭐ **Idempotent by txn id** | ⭐ a retried request cannot dispense twice (Day 122) |
| ⭐ **Reconciliation is a first-class flow** | ⭐ **this is why ATM disputes are resolved by counting the cassette** |
| Cash counted at cassette level | ⭐ the physical count is the ground truth, not the software's belief |

> **⭐ The sentence that lands: "the debit and the dispense are in different systems, so I write the
> intent to a durable journal first and reconcile anything that did not complete. This is the outbox
> idea from Day 263, applied to a physical actuator instead of a message broker."** Connecting them
> is what makes it read as understanding rather than recall.

## ⭐ The rest of the ATM

```
   IDLE ──card──► CARD_INSERTED ──pin──► AUTHENTICATED ──select──► TRANSACTION
     ▲                  │ ⭐ 3 failures       │                          │
     │                  ▼                     │                          ▼
     │            CARD_RETAINED               │                     DISPENSING
     └───────────────────────────────────────┴──────────────────────────┘
                                    ⭐ eject card, return to IDLE
```

| Detail | ⭐ Design |
|---|---|
| ⭐ **PIN attempts** | a counter on the card/account, **not on the machine** — ⭐ three ATMs, three attempts each otherwise |
| ⭐ **Note denominations** | ⭐ the same bounded change problem — £30 from a £20-only cassette fails |
| ⭐ Daily withdrawal limit | ⭐ **checked against the account, across all ATMs — a rate limiter** (Day 314) |
| ⭐ **Two ATMs, one account** | ⭐ **the balance is the shared mutable state — a conditional update, exactly Day 316's pattern** |
| Timeouts at every state | an abandoned session must return the card and reset |

⚠️ **The concurrency question here is the same one as the seat**: `UPDATE accounts SET balance =
balance - :amt WHERE id = :id AND balance >= :amt`, and `rowsAffected` decides. **Say that it is the
same shape — recognising the repetition across problems is the point of doing eleven of them.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ A `switch` on state duplicated across five methods | ⭐ a new state edits five places, and one gets missed |
| ⭐ The state pattern for three states | over-engineering; say the trade instead |
| States holding mutable data | two machines cannot share them; the machine's data splits |
| ⭐⭐ **Taking money before checking change** | ⭐⭐ **the machine steals from the customer** |
| ⭐ Greedy change with no caveat | it is wrong in general and the interviewer knows |
| ⭐ Unbounded coin change | ⭐ **the machine has three fifties, not infinite fifties** |
| Sold-out modelled per machine | one empty slot disables everything |
| ⭐⭐ **Debit and dispense with no journal** | ⭐⭐ **a crash robs the customer, with no record** |
| ⭐ PIN attempts counted on the machine | three ATMs, nine attempts |
| Withdrawal limits per machine | the limit belongs to the account |
| ⭐ No session timeout | a card left in an authenticated machine |

## Interview questions

**Q: State pattern or an enum with a switch?**
It depends on the state and event count. Three states and two events — an enum, or a switch, and the
whole machine stays readable in one file. Six states and five events — separate classes, because a
new state becomes a new class rather than an edit to five switch statements, one of which you will
forget. Java enums with abstract methods sit in between and are what I would reach for first here.

**Q: What is the hard part of a vending machine?**
Change. You can be unable to make it, so the check has to happen before you accept the sale — a
machine that takes two pounds and cannot return seventy pence has stolen from the customer. The coin
algorithm itself is secondary: greedy is optimal for real currencies so it is the right production
choice, but it is not optimal in general, and here the problem is bounded rather than unbounded,
because the machine has three fifty-pence pieces and not infinitely many.

**Q: The ATM debits the account and then the cash jams. What now?**
The debit and the dispense are in different systems, so they cannot be one transaction. I write a
durable journal entry with the intent and a transaction id before anything happens, dispense,
record what physically came out, then mark it complete. Anything not complete is picked up by
reconciliation, and the ground truth is the physical count in the cassette. It is the outbox pattern
pointed at an actuator instead of a message broker.

**Q: Where do the PIN attempt counter and the daily limit live?**
On the account, not the machine. A counter on the machine gives three attempts per ATM, so a
determined attacker walks down the street. The daily limit is the same argument — it is a rate limit
on the account across every channel, so it belongs where the account lives.

**Q: Two ATMs, one account, at the same time.**
The balance is shared mutable state, so it is a conditional update — decrement where the balance is
still sufficient — and `rowsAffected` decides the winner. That is exactly the seat-hold shape from
the booking problem; the same guard keeps appearing because the same check-then-act keeps appearing.

## Mini task

1. Implement the vending machine **three ways**: a `switch`, an enum with abstract methods, and state
   classes. **Add a fifth state to each and count the edits.**
2. Decide throw-vs-ignore for every invalid operation and **write the table** before coding.
3. ⭐ **Implement bounded change-making** over the machine's actual inventory. Test the {1,3,4} case
   and confirm greedy loses.
4. ⭐ **Write the test that must pass**: item £1.30, £2.00 inserted, only 50p coins available →
   **the sale is refused and the money returned**, not taken.
5. Model coin inventory changing in both directions and add restock and collection operations.
6. ⭐ Build the ATM **journal**. Kill the process between debit and dispense, restart, and **confirm
   reconciliation finds and resolves the entry.**
7. Move the PIN counter from the machine to the account. **Write the three-machines test** that fails
   before the change.
8. ⭐ Two threads withdrawing from one account: implement the conditional update and **assert the
   balance never goes negative** over 1,000 runs.

## 🎙️ Articulation drill

**Two minutes each, back to back:** *"What is the hardest part of a vending machine?"* then *"What is
the hardest part of an ATM?"*

**⭐ The marker: neither answer is about the state pattern.** The pattern is how you organise the
code; **the hard parts are that change can be unmakeable and that money can leave one system without
leaving the other.** Candidates who answer both questions with "I'd use the state pattern" have
described their file layout and nothing about the problem.
