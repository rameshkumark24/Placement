# The full trace

Twelve phases. Each links back to the day that taught it — if a phase feels shaky, that's your
revision list.

## Phase 1 — The keystroke reaches the browser

You press Enter. Before any network activity:

- The OS delivers a keyboard interrupt; the browser process receives the event
- The browser parses what you typed: is it a URL or a search query?
- **Autocomplete and HSTS check** — if `google.com` is in the HSTS preload list, the browser upgrades
  to `https://` **before sending anything.** No plaintext request is ever made. *(Day 009)*
- URL is normalised and percent-encoded

**Interview note:** mentioning the HSTS preload upgrade here is a strong opening — most people start
at DNS.

---

## Phase 2 — Resolve the name *(Day 007, C-08)*

```
1. Browser cache        "have I looked this up recently?"
2. OS cache             (Windows DNS Client / nscd / systemd-resolved)
3. hosts file           C:\Windows\System32\drivers\etc\hosts
4. RESOLVER  (ISP, or 8.8.8.8 / 1.1.1.1) — a RECURSIVE query
      │
      ├──▶ ROOT server        "who handles .com?"      ← ITERATIVE, returns a referral
      ├──▶ TLD server (.com)  "who handles google.com?" ← referral to the NS records
      └──▶ AUTHORITATIVE      "google.com = 142.250.183.100"  ← the A record
      │
      └─ each layer caches for the record's TTL
5. Answer returns to the OS, then the browser
```

**Detail worth adding:** the resolver's query goes out over **UDP port 53** — one small datagram each
way, because a TCP handshake would triple the cost of a lookup. *(Day 010, C-07)*

---

## Phase 3 — Open a TCP connection *(Days 003, 005, 008)*

The browser now has an IP. It needs a connection.

- The OS assigns an **ephemeral source port**, say 51234 *(Day 003)*
- The connection will be identified by the **4-tuple**:
  `(your_ip, 51234, 142.250.183.100, 443)`

```
   CLIENT                                          SERVER
     │  SYN     seq=x                                │
     │ ─────────────────────────────────────────────▶│
     │  SYN-ACK seq=y, ack=x+1                       │
     │ ◀─────────────────────────────────────────────│
     │  ACK     ack=y+1                              │
     │ ─────────────────────────────────────────────▶│
     │                ESTABLISHED                    │
```

**Cost: one full round trip.** Chennai↔Oregon ≈ 140 ms, set by the speed of light in fibre. *(Day 006)*

Both endpoints now hold a **TCB** — the connection is two in-memory state structures, with nothing in
between. *(Day 008)*

---

## Phase 4 — How the packets physically travel *(Days 002, 004, 006)*

Each packet, at each hop:

```
   Your NIC ──▶ home router ──▶ ISP ──▶ IXP ──▶ transit ──▶ submarine cable ──▶ Google's AS
```

At every hop the router:
1. Reads the **destination IP** in the IP header
2. Does a **longest-prefix match** against its routing table *(Day 004, C-03)*
3. **Decrements TTL**, recomputes the checksum
4. Resolves the next hop's MAC via **ARP** *(Day 002, C-02)*
5. **Rebuilds the layer-2 frame** and forwards

**The IP packet survives end to end; the Ethernet frame is destroyed and recreated every hop.**

Your home router also performs **NAT**, rewriting your private source address to its public one and
keeping a translation table. *(Day 004)*

---

## Phase 5 — TLS handshake *(Day 009)*

```
   ClientHello   → versions, cipher suites, SNI: google.com (IN THE CLEAR), ECDHE key share
   ServerHello   → chosen suite, key share, certificate, CertificateVerify, Finished
   [both derive the same symmetric key from the exchanged key shares]
   Finished      →
   ══ encrypted application data ══
```

- **One more round trip** (TLS 1.3). Running total: ~280 ms before a byte of HTTP moves.
- The browser validates the chain: signature valid, not expired, **SAN matches the hostname**, not
  revoked
- **ALPN** negotiates `h2` or `h3` during this handshake, costing no extra round trip *(Day 013, C-09)*
- **ECDHE** gives forward secrecy — a future compromise of the server's private key doesn't decrypt
  this session

---

## Phase 6 — The HTTP request *(Days 010, 011)*

```http
GET / HTTP/2
:authority: google.com
:scheme: https
:method: GET
accept: text/html,application/xhtml+xml
accept-encoding: gzip, br
cookie: NID=...
```

- Over HTTP/2 this is **binary frames on stream 1**, with headers HPACK-compressed, not the text
  above *(Day 013, C-09)*
- Cookies for this domain are attached **automatically** *(Day 019)*
- The connection is persistent — subsequent resources reuse it *(Day 011)*

---

## Phase 7 — What the request meets at Google's edge *(Day 018, C-12)*

It does not hit an application server directly:

```
   Anycast routing → nearest Google edge PoP
        ↓
   Load balancer (L7) → TLS terminated, routing decision on path/headers
        ↓
   Reverse proxy → cache check, compression, WAF
        ↓
   Application servers → the actual handler
        ↓
   Databases, caches, internal services
```

**REST constraint 5 — layered system — is what makes this invisible to you.** *(Day 016)* The client
cannot tell whether it's talking to the origin.

---

## Phase 8 — The server responds

```http
HTTP/2 200
content-type: text/html; charset=utf-8
content-encoding: br
cache-control: private, max-age=0
set-cookie: NID=...; HttpOnly; Secure; SameSite=Lax
```

- **Status code** signals the outcome *(Day 010)*
- `Set-Cookie` flags: `HttpOnly` blocks JS access, `Secure` requires HTTPS, `SameSite` limits CSRF
  *(Day 019)*
- Response is Brotli-compressed
- Bytes travel back through the same path, reassembled by TCP using sequence numbers *(Day 005)*

---

## Phase 9 — Parse and build the trees *(Days 012, 013)*

```
   bytes → characters → tokens → nodes → DOM
   CSS   → ...                        → CSSOM
```

- HTML parsing is **incremental** — the browser renders as bytes arrive
- Malformed markup is **repaired** by defined error-recovery rules
- **CSS is render-blocking** — nothing paints until the CSSOM is built
- A synchronous `<script>` **blocks parsing**; `defer` waits for parse completion *(Day 015)*
- Every referenced asset triggers its own request — multiplexed on the same HTTP/2 connection

---

## Phase 10 — Render *(Day 015)*

```
   DOM + CSSOM → Render tree → Layout → Paint → Composite
```

- Render tree contains only visible nodes (`display:none` is absent; `visibility:hidden` is present)
- **Layout** computes geometry — the expensive stage
- **Paint** fills pixels into layers
- **Composite** assembles them on the GPU
- **LCP** is measured when the largest element paints

---

## Phase 11 — JavaScript runs *(Day 014)*

- The V8 engine parses to bytecode, interprets, then JIT-compiles hot functions — **the same
  architecture as the JVM** *(Day 002)*
- **One call stack.** Timers and network calls are handled by browser threads, and their callbacks
  return via the **microtask and macrotask queues**
- The event loop drains **all** microtasks, then takes **one** macrotask
- Any synchronous work here blocks rendering and input — which is what **INP** measures

---

## Phase 12 — Subsequent requests

- **XHR/fetch to another origin** → the **same-origin policy** applies; cross-origin needs CORS, and
  anything sending JSON triggers a **preflight `OPTIONS`** *(Day 020)*
- **Real-time features** → SSE or a WebSocket upgrade *(Days 017, 018)*
- Cached assets → conditional requests with `If-None-Match`, answered `304 Not Modified` *(Day 010)*
- Static assets came from a **CDN edge**, not the origin *(Day 018, C-12)*

# The latency budget — the summary that impresses

```
   DNS (uncached)                    ~20–100 ms
   TCP handshake                     ~140 ms      (1 RTT)
   TLS 1.3 handshake                 ~140 ms      (1 RTT)
   Request + first byte              ~140 ms      (1 RTT)
   ──────────────────────────────────────────
   ≈ 440 ms before the first byte of HTML
```

**Then explain how each is attacked:**

| Cost | Mitigation | Day |
|---|---|---|
| DNS lookup | Caching at every layer; DNS prefetch | 007 |
| TCP handshake | Keep-alive, connection pooling | 011, 005 |
| TLS handshake | Session resumption; QUIC 0-RTT | 009, 011 |
| Distance | **CDN — the only real fix for physics** | 006, 018 |
| Multiple round trips | HTTP/2 multiplexing | 011 |
| Slow start ramp | Connection reuse | 008 |

**That table is the answer to "how would you make this faster?"** — and it's much stronger than
"add a cache", because it identifies *which* cost you're attacking.

# 🚪 Stage 0 Exit Gate

## 1. Mini project — raw TCP server speaking HTTP by hand

- [ ] Built on [Day 004](Day-004.md)
- [ ] Handles multiple clients concurrently
- [ ] Returns correct status codes and `Content-Length`
- [ ] You can explain every line

Your roadmap specifies Python's `socket` module. **Do it in Python as well as Java** — it's 20 lines
and proves the concepts are language-independent:

```python
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)   # skip TIME_WAIT — Day 008
server.bind(('', 8080))                                         # bind()
server.listen(5)                                                # listen()
print("http://localhost:8080")

while True:
    client, addr = server.accept()                              # accept() — blocks
    request = client.recv(4096).decode()
    print(request.split('\r\n')[0])

    body = "<h1>Written by hand in Python</h1>"
    response = (
        "HTTP/1.1 200 OK\r\n"
        "Content-Type: text/html\r\n"
        f"Content-Length: {len(body)}\r\n"
        "Connection: close\r\n"
        "\r\n" + body
    )
    client.sendall(response.encode())
    client.close()
```

**Same four system calls as Day 004.** Different language, identical concepts.

- [ ] *"What happens when you type google.com and press Enter?"*

**Structure it in the twelve phases above.** Time yourself. Record it.

**What good looks like:** you get through all twelve without notes, you name specific mechanisms

interrupted.

**What to avoid:** rushing to "and then the page loads". The interviewer is testing depth. Slow down
at DNS, TCP, TLS and rendering — those are where the follow-up questions live.

## 4. Oral exam — explain to a non-technical person

- [ ] *"What is HTML? What is a server? What's the difference?"*

Try:

> *"A server is a program that sits waiting, like a shop that's open — it does nothing until someone
> walks in and asks for something. HTML is what it hands you: a document with labels saying which bit
> is a heading, which is a paragraph, which is a picture. The server is the shop; the HTML is the
> thing in the bag."*

**Two audiences is the real test.** Anyone can memorise jargon; explaining without it proves you
understand.
