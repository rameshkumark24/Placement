# Day 082

**L-082** · Networking & files on Linux — `ssh`, `scp`, `curl`, `journalctl`

# Part 1 — `ssh`

## Keys, not passwords

```bash
ssh-keygen -t ed25519 -C "ram@laptop"       # ed25519, not RSA
ssh-copy-id user@server                      # appends to ~/.ssh/authorized_keys
ssh user@server
```

**Ed25519 over RSA:** smaller keys, faster, and no need to reason about key size. If a legacy system
demands RSA, use `-t rsa -b 4096`.

The permission rules — SSH **refuses to work** if they are wrong, and this is the most common
first-time failure:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519          # private key — 600, never readable by others
chmod 644 ~/.ssh/id_ed25519.pub
chmod 600 ~/.ssh/authorized_keys
```

The public key goes on the server; **the private key never leaves your machine**. If you ever paste
a private key anywhere, rotate it — including into a chat, a CI variable meant for something else,
or a repository. Use a passphrase and `ssh-agent`:

```bash
eval "$(ssh-agent -s)"; ssh-add ~/.ssh/id_ed25519
```

## `~/.ssh/config` — the file that saves you hours

```
Host prod
    HostName 10.0.4.12
    User appuser
    IdentityFile ~/.ssh/id_ed25519_prod
    ProxyJump bastion              # ← go through the bastion automatically
    ServerAliveInterval 60         # ← stops idle disconnects

Host bastion
    HostName bastion.acme.com
    User ram

Host *
    AddKeysToAgent yes
    ServerAliveInterval 60
```

Now `ssh prod` handles the jump host, the user, the key and keepalives. `ProxyJump` (`-J`) is the
correct way through a bastion — the old advice to store your private key *on* the bastion is a
security mistake, because a bastion compromise then hands over your key.

## Tunnels

```bash
ssh -L 5432:localhost:5432 prod     # LOCAL: my :5432 → prod's localhost:5432
ssh -R 8080:localhost:8080 prod     # REMOTE: prod's :8080 → my local app
ssh -D 1080 prod                    # SOCKS proxy
```

**Local forwarding is the one you will use constantly**: connect a local database client or your IDE
debugger to a database that is not exposed to the internet. It is also the *correct* way to use JDWP
(Day 076) — bind the debug port to `localhost` on the server and tunnel to it, never expose it.

```bash
ssh -N -f -L 5005:localhost:5005 prod    # -N no command, -f background
```

## Running things remotely

```bash
ssh prod 'systemctl status myapp'
ssh prod 'tail -f /var/log/app.log'
ssh prod 'bash -s' < local-script.sh          # run a local script remotely
ssh prod "cd /opt/app && ./deploy.sh"          # quote so the shell expands REMOTELY
```

The quoting rule bites here: with `ssh prod echo $HOSTNAME` your **local** shell expands the
variable. Single-quote it to have it expand on the remote host.

Host key verification is a real security control, not a nuisance: the first connection records the
server's key, and a later mismatch (`REMOTE HOST IDENTIFICATION HAS CHANGED`) means either the host
was rebuilt or you are being MITM'd. **Never blindly delete the `known_hosts` entry** — verify first.

## Copying

```bash
scp file.txt prod:/tmp/
scp prod:/var/log/app.log ./
scp -r dir/ prod:/opt/

rsync -avz --progress dir/ prod:/opt/dir/     # ← prefer rsync
rsync -avz --delete --exclude '*.log' src/ prod:/opt/app/
```

**`rsync` beats `scp` for anything non-trivial**: it transfers only differences, resumes, preserves
permissions, and can mirror with `--delete`. The trailing-slash rule catches everyone: `src/` copies
the *contents*, `src` copies the *directory*.

# Part 2 — `curl`

The tool for talking to HTTP directly — which is how you test an API without a client, reproduce a
bug outside your application, and check what a service really returns.

```bash
curl https://api.example.com/items                  # GET, body to stdout
curl -i https://…                                   # include response headers
curl -I https://…                                   # HEAD only
curl -v https://…                                   # verbose: TLS handshake, request, response
curl -s https://… | jq                              # silent (no progress bar) + parse
curl -L https://…                                   # follow redirects
curl -o out.json https://…                          # to a file
curl -f https://…                                   # FAIL (non-zero exit) on 4xx/5xx ← for scripts
```

```bash
# POST JSON
curl -X POST https://api.example.com/orders \
     -H 'Content-Type: application/json' \
     -H "Authorization: Bearer $TOKEN" \
     -d '{"sku":"A-1","qty":2}'

curl -X POST … -d @payload.json                     # body from a file
curl -X POST … -F file=@report.pdf -F name=report   # multipart upload
curl -u user:pass https://…                          # basic auth
curl --cookie-jar c.txt --cookie c.txt https://…     # session
curl --max-time 10 --connect-timeout 3 https://…     # ← always in scripts
curl --retry 3 --retry-delay 2 https://…
curl --resolve api.example.com:443:10.0.0.5 https://api.example.com/   # bypass DNS
```

Three flags to make habits:

**`-f`** — without it, `curl` exits 0 on a 500, so a deploy script "succeeds" while the health check
returns an error page. This is Day 079's exit-code discipline applied.

**`--max-time`** — a script that hangs forever on a stalled connection is worse than one that fails.

**`--resolve`** — test a specific backend before DNS points at it, or reproduce a problem on one
instance behind a load balancer. This is the flag that separates casual from operational use.

## Timing — turning curl into a measurement tool

```bash
curl -s -o /dev/null -w '
 dns:      %{time_namelookup}s
 connect:  %{time_connect}s
 tls:      %{time_appconnect}s
 ttfb:     %{time_starttransfer}s
 total:    %{time_total}s
 code:     %{http_code}
 size:     %{size_download}\n' https://api.example.com/items
```

This decomposes a slow request into **DNS vs TCP vs TLS vs server think-time vs transfer** — Days
006–011 as measurable numbers. A high `time_namelookup` is a DNS problem, not an application one;
`time_starttransfer` minus `time_appconnect` is the server actually working. Being able to say which
segment is slow is a different conversation from "the API is slow".

And the Web/App domains' exposure check, which is the same tool:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://yourdomain.com/.env
curl -s -o /dev/null -w "%{http_code}\n" https://yourdomain.com/.git/config
```

Anything other than 404 is an incident.

## `wget`, `nc`, `dig`, `ss`

```bash
wget -r -np -k https://site/          # recursive mirror — curl does not do this
wget -c https://…/big.iso             # resume

nc -zv host 5432                      # is the port open?
nc -l 9000                            # listen — a fake server for testing
printf 'GET / HTTP/1.1\r\nHost: x\r\n\r\n' | nc host 80    # HTTP by hand (Day 004!)

dig api.example.com +short            # DNS (Day 007)
dig api.example.com A +trace          # full resolution path
getent hosts api.example.com          # what the SYSTEM resolves (respects /etc/hosts)

ss -tanp | grep 8080                  # who is listening / connected
ss -s                                 # summary by state
```

`nc -zv host port` is the fastest way to answer "is it the network or the application?" — if the
port is closed, stop debugging your code.

# Part 3 — `journalctl`

```bash
journalctl -u myapp                    # one unit
journalctl -u myapp -f                 # follow  ← the common one
journalctl -u myapp -n 200             # last 200 lines
journalctl -u myapp --since "1 hour ago" --until "10 min ago"
journalctl -u myapp -p err             # priority: emerg alert crit err warning notice info debug
journalctl -u myapp -o json-pretty     # structured, with all metadata
journalctl -u myapp --since today | grep -i timeout
journalctl -b                          # this boot
journalctl -b -1                       # PREVIOUS boot ← what happened before the crash
journalctl -k                          # kernel messages
journalctl --disk-usage
journalctl --vacuum-time=7d
```

Two that repay knowing:

**`journalctl -b -1 -p err`** — after an unexplained restart, this shows the errors from *before* the
reboot. It is often where you find the OOM killer:

```bash
journalctl -k | grep -i "killed process"
dmesg -T | grep -i oom
# Out of memory: Killed process 4711 (java) total-vm:8G, anon-rss:6G
```

That line is the definitive answer to "the JVM died with no exception and no heap dump" — the kernel
killed it, which is Day 079's exit code 137 seen from the other side.

**`-o json-pretty`** shows that the journal is structured, not text: unit, pid, uid, boot id,
priority. That is why filtering by unit and priority is exact rather than a grep over a shared file.

## Code to type

```bash
# 1. SSH config and a jump — set up Host entries for any two machines you have
#    (a local VM, WSL, or a container running sshd is fine)
ssh -o BatchMode=yes localhost 'echo works' || echo "set up keys first"

# 2. curl timing against three different hosts — compare the segments
for h in https://example.com https://api.github.com https://httpbin.org/delay/2; do
  echo "== $h"
  curl -s -o /dev/null -w 'dns=%{time_namelookup} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} code=%{http_code}\n' "$h"
done

# 3. -f matters
curl -s -o /dev/null https://httpbin.org/status/500;    echo "without -f: $?"
curl -f -s -o /dev/null https://httpbin.org/status/500; echo "with -f:    $?"

# 4. HTTP by hand — Day 004 from the client side
printf 'GET /get HTTP/1.1\r\nHost: httpbin.org\r\nConnection: close\r\n\r\n' | nc httpbin.org 80

# 5. a local tunnel to a service only bound to localhost on the far side
python3 -m http.server 8000 --bind 127.0.0.1 &
ssh -N -f -L 9000:localhost:8000 localhost
curl -s localhost:9000 | head -3

# 6. journal
journalctl -f &                       # watch
logger -t mytest "hello from logger"  # write a journal entry
sleep 1; journalctl -t mytest -n 5
```

## Common mistakes

| Mistake | Consequence |
|---|---|
| Private key with wrong permissions | SSH silently refuses it |
| Private key stored on a bastion | Bastion compromise = your key |
| Deleting a `known_hosts` entry without checking | You may be accepting a MITM |
| `curl` without `-f` in a script | 500 responses count as success |
| `curl` without `--max-time` | Script hangs indefinitely |
| Unquoted remote commands over ssh | Local shell expands the variables |
| `scp -r` for large or repeated syncs | Use `rsync` |
| `rsync src` vs `rsync src/` | Wrong nesting |
| Exposing JDWP or a database port publicly | Use an SSH tunnel |
| Long remote job without tmux | Killed by disconnect |
| Ignoring `journalctl -b -1` after a restart | Miss the OOM kill |

## Interview questions

**Q: How do you connect to a database that is not exposed publicly?**
An SSH local port forward through a bastion: `ssh -L 5432:db-host:5432 bastion`, then point the
client at `localhost:5432`. The database never needs a public address.

**Q: Why `ProxyJump` rather than keeping a key on the bastion?**
The private key stays on your laptop; the bastion only relays an encrypted connection. Storing the
key on the bastion means compromising it compromises everything it can reach.

**Q: An API is slow. How do you find out where?**
`curl -w` with the timing variables to split DNS, TCP connect, TLS handshake, time-to-first-byte and
transfer. That tells you whether it is resolution, the network, the handshake, or the server
thinking.

**Q: Why does a shell script need `curl -f`?**
Without it curl exits 0 on HTTP errors, so a script cannot distinguish a healthy response from an
error page.

**Q: The JVM disappeared with no exception and no heap dump. What happened?**
Very likely the kernel OOM killer — check `journalctl -k | grep -i "killed process"` or `dmesg`, and
the exit code will be 137. The JVM never ran any code, so no hook and no dump.

**Q: What does `nc -zv host port` tell you?**
Whether the TCP port is reachable and accepting — which separates a network/firewall problem from an
application problem in one command.

## 🎙️ Articulation drill

Two minutes: **"A production API is returning 502s intermittently. Walk me through your
investigation from a terminal."**

`curl -v` and `-w` timing to see where it breaks, `nc -zv` and `ss` to check reachability and
connection states, `journalctl -u` for the service's own view, `-b -1` if it restarted, and the
kernel log for OOM. Say what each result would rule out. Naming what a result *eliminates* is what
makes it a methodology rather than a list.
