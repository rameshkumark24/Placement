# Day 385

**L-385** · EC2 and EBS — instance families, storage, and the burst-credit trap

# Part 1 — ⭐⭐ Reading an instance type

```
⭐⭐  m 7 g . large
⭐    │ │ │    └── ⭐ SIZE       — vCPU and memory scale linearly: large → xlarge → 2xlarge
⭐    │ │ └─────── ⭐⭐ PROCESSOR — ⭐⭐ g = Graviton (arm64) · i = Intel · a = AMD
⭐    │ └───────── ⭐ GENERATION — ⭐⭐ newer is almost always cheaper per unit of work
⭐    └─────────── ⭐⭐ FAMILY    — the vCPU-to-memory ratio
```

| Family | ⭐ Ratio | ⭐ For |
|---|---|---|
| ⭐⭐ **`m` general** | ⭐ 1 vCPU : 4 GB | ⭐⭐ **the default — start here for a JVM web service** |
| ⭐ `c` compute | 1 : 2 | CPU-bound: encoding, batch, some caches |
| ⭐⭐ **`r` memory** | ⭐ 1 : 8 | ⭐⭐ **large heaps, in-memory caches, JVMs that hold data** |
| ⭐ `t` burstable | ⭐ 1 : 4, **credit-limited** | ⭐⭐ **dev, low traffic — see Part 2** |
| `i` / `d` storage | NVMe local | databases needing local IOPS |
| `g`/`p`/`inf` accelerated | GPU/inference | ML (Stage 14) |

> **⭐⭐ Newer generation is nearly always the right move and people forget to do it.** An `m7g` is
> typically both cheaper *and* faster than an `m5` for the same nominal size. **"Upgrade the generation"
> is a one-line change that shows up on the bill and in p99 latency simultaneously** — and it is one of
> the first things to do on an inherited account (Day 396).

## ⭐⭐ Graviton: the free 20%

| | |
|---|---|
| ⭐⭐ **~20–40% better price/performance** | ⭐ for typical JVM web workloads |
| ⭐⭐ **The JVM runs natively on arm64** | ⭐ OpenJDK, Corretto, Temurin — all first-class |
| ⭐⭐ **The catch: your image must be arm64** | ⭐⭐ multi-arch build, or `--platform linux/arm64` (Day 362) |
| ⭐ What actually blocks it | ⭐⭐ **native dependencies** — an x86-only `.so`, a JNI library, an old agent |
| The test | build for arm64 and run the test suite; it usually just works |

⚠️ **The failure mode is not subtle but it is confusing the first time:** an x86 image on a Graviton
host gives `exec format error`, or — worse — runs under emulation somewhere in your toolchain at a
fraction of the speed. **Build multi-arch in CI (`docker buildx --platform linux/amd64,linux/arm64`)
and the whole question disappears.**

# Part 2 — ⭐⭐ The burstable-instance trap

```
⭐ A t3.medium has a BASELINE of 20% of 2 vCPUs. Above that it spends CPU CREDITS.
⭐ Credits accrue at a fixed rate per hour and cap at 24 hours' worth.

⭐⭐ Standard mode : credits exhausted ⇒ ⭐⭐ THROTTLED TO BASELINE. Your app crawls.
⭐⭐ Unlimited mode: credits exhausted ⇒ ⭐⭐ IT KEEPS GOING AND BILLS YOU. Silently.
```

| ⭐ The symptom you must recognise | |
|---|---|
| ⭐⭐ **"It was fine for twenty minutes, then everything got slow"** | ⭐⭐ **CPU credits ran out** |
| ⭐ A JVM makes this worse | ⭐ JIT compilation and GC are CPU bursts — **startup alone eats credits** |
| ⭐ The metric | ⭐⭐ `CPUCreditBalance` — **alarm on it approaching zero** |
| The other symptom | ⭐⭐ **a surprise bill line** from unlimited mode on a busy t-instance |

> **⭐ The rule: `t` for development, CI runners, and genuinely idle services. `m`/`c`/`r` for anything
> serving real traffic.** A t-instance under sustained load is either slow or expensive — **it is never
> both cheap and fast, which is exactly what people assume they bought.**

⚠️ **This bites hardest on a "small" production service that is idle most of the day and busy in one
window** — precisely the profile that looks perfect for burstable. The burst is real; **the sustained
window is where it fails.**

# Part 3 — ⭐⭐ EBS: network-attached storage, priced as three things

| Type | ⭐ Use | ⭐ Note |
|---|---|---|
| ⭐⭐ **gp3** | ⭐⭐ **the default for everything** | ⭐⭐ **3,000 IOPS and 125 MB/s baseline at ANY size** |
| ⭐ gp2 | ⭐ legacy | ⭐⭐ **IOPS = 3 × GB** — the reason people bought huge disks |
| ⭐ io2 / io2 Block Express | databases needing guaranteed IOPS | expensive; higher durability |
| ⭐ st1 / sc1 | ⭐ throughput/cold HDD | sequential only — terrible for random reads |
| ⭐⭐ **Instance store (NVMe)** | ⭐ scratch, local cache | ⭐⭐ **ephemeral — gone on stop/terminate** |

```
⭐⭐ THE gp2 → gp3 STORY, which is a real refactor:
⭐   gp2: IOPS scale with SIZE ⇒ ⭐ to get 3,000 IOPS you provisioned a ⭐⭐ 1 TB disk
⭐        for a 40 GB database. You were buying IOPS and paying for capacity.
⭐   gp3: ⭐⭐ IOPS and throughput are provisioned INDEPENDENTLY of size.
⭐   ⇒ ⭐⭐ 40 GB gp3 + 3,000 IOPS is ~20% cheaper per GB AND far cheaper overall.
⭐   ⇒ ⭐ Migration is an online volume modification. ⭐⭐ Nearly free money.
```

| ⭐ The limit people miss | |
|---|---|
| ⭐⭐ **EBS is network-attached** | ⭐⭐ throughput is capped by the **instance's** EBS bandwidth too |
| ⭐ So | ⭐⭐ a 16,000-IOPS volume on a small instance delivers far less |
| ⭐ Check | the instance type's documented EBS bandwidth, not just the volume spec |
| ⭐ Snapshots | ⭐ incremental to S3; **restored volumes are lazily loaded and slow until warmed** |

⚠️ **"The database is slow after a restore" is usually lazy loading, not a real problem** — blocks are
fetched from S3 on first access. **Fast Snapshot Restore exists and costs money; a `dd` read-through of
the volume is the free version.**

# Part 4 — ⭐ Images, bootstrapping and access

| Concept | ⭐ Note |
|---|---|
| ⭐ **AMI** | ⭐ a bootable image; **use Amazon Linux 2023 or a maintained base, not something ancient** |
| ⭐ **User data** | ⭐ a script at first boot — **runs once**, logs to `/var/log/cloud-init-output.log` |
| ⭐⭐ **Golden AMI vs container** | ⭐⭐ **if you are already building images (Day 362), the container is your artefact — do not maintain both** |
| ⭐ Launch template | the versioned definition an ASG uses (Day 389) |
| ⭐⭐ **SSM Session Manager** | ⭐⭐ **no SSH, no key pairs, no port 22** (Day 384) |
| ⭐ Termination protection | ⭐ for the one instance that should not be casually deleted |

> **⭐ The honest position for a Java service in 2026: you should rarely be choosing an AMI at all.** Your
> artefact is a container image; the instance is either a Fargate abstraction or an ECS/EKS node you
> never log into. **EC2 knowledge still matters because it is what every other service is built from —
> and because someone will hand you a fleet of instances to explain.**

## ⭐ Purchase options, briefly

| Option | ⭐ Discount | ⭐ Cost of the discount |
|---|---|---|
| On-Demand | — | none |
| ⭐ **Savings Plans** | ⭐ ~30–40% | ⭐ 1 or 3-year **spend** commitment |
| Reserved Instances | ~30–50% | commitment to a *type* — less flexible |

**⭐ Spot is genuinely excellent for CI runners, batch, and stateless workers behind a queue** — anything
that can lose a worker and retry (Day 393). **It is wrong for anything holding state or serving a long
request without a drain path.** Full treatment on Day 396.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Staying on an old generation | ⭐ newer is usually cheaper *and* faster |
| ⭐⭐ **`t` instances for production traffic** | ⭐⭐ throttled to baseline, or silently billed unlimited |
| ⭐ No alarm on `CPUCreditBalance` | ⭐ the slowdown is invisible until users report it |
| ⭐⭐ **gp2 with an oversized disk for IOPS** | ⭐⭐ gp3 decouples them — you are paying for capacity you do not need |
| ⭐ Provisioning volume IOPS above the instance's EBS bandwidth | ⭐ you cannot use them |
| ⭐ Expecting instance store to survive a stop | ⭐⭐ it is ephemeral by definition |
| ⭐ Blaming a slow restored volume | ⭐ lazy loading — warm it |
| ⭐⭐ **x86 image on a Graviton host** | ⭐⭐ `exec format error`, or silent emulation |
| ⭐ Maintaining golden AMIs *and* container images | ⭐ two artefact pipelines for one thing |
| ⭐ SSH key pairs and a bastion | ⭐⭐ SSM Session Manager (Day 384) |
| ⭐ Spot for stateful or long-request workloads | two minutes is not always enough |
| IMDSv1 left on | ⭐⭐ Day 382 |

## Interview questions

**Q: How do you choose an instance type?**
Four decisions in the name. Family sets the vCPU-to-memory ratio — `m` general purpose is where I start
for a JVM web service, `r` if the heap is large, `c` if it is genuinely CPU-bound. Generation should be
the newest available, because newer is usually cheaper per unit of work as well as faster. Processor —
Graviton unless a native dependency blocks it, because it is twenty to forty percent better price for
performance and the JVM is first-class on arm64. Size comes last and comes from measurement, not
estimation. And then I would verify against real utilisation rather than trusting the first choice.

**Q: An application is fine for twenty minutes after deploy and then goes slow. What do you check?**
CPU credit balance, if it is a t-family instance. Burstable instances have a baseline — twenty percent
of the vCPUs on a t3.medium — and above that they spend credits that accrue at a fixed rate. When the
balance hits zero, standard mode throttles you to baseline and everything crawls. A JVM makes it worse
because JIT compilation and garbage collection are CPU bursts, so startup itself consumes credits. The
alternative failure is unlimited mode, where it does not slow down and instead appears as a surprise on
the bill.

**Q: gp2 or gp3?**
gp3, essentially always. Under gp2, IOPS scaled with volume size at three per gigabyte, so the standard
workaround for needing three thousand IOPS was provisioning a one-terabyte volume for a forty-gigabyte
database — you were buying IOPS and paying for capacity. gp3 provisions IOPS and throughput
independently of size, gives three thousand IOPS at any size as a baseline, and is about twenty percent
cheaper per gigabyte. The migration is an online volume modification, so it is close to free money on an
inherited account.

**Q: What limits EBS throughput?**
Two things, and people only check one. The volume's own provisioned IOPS and throughput, and the
instance type's EBS bandwidth. Provisioning sixteen thousand IOPS on a volume attached to a small
instance does not give you sixteen thousand IOPS, because the network path to the volume is the
bottleneck. EBS is network-attached storage, not a local disk, and treating it as local is where the
mental model breaks.

**Q: When is Spot appropriate?**
When losing a worker mid-task is recoverable and cheap. CI runners, batch processing, and stateless
consumers pulling from a queue are ideal — the message becomes visible again and another worker takes
it. It is wrong for anything holding local state, anything serving a long-lived request without a drain
path, and anything where the two-minute interruption notice is not enough to finish cleanly. The
discount is seventy to ninety percent, which is large enough that designing workloads to be
interruptible is itself a cost strategy.

## Mini task

1. ⭐ Launch an `m7g` and an `m7i` of the same size. **Run the same benchmark on both** and compare
   price-performance yourself.
2. ⭐⭐ Build your flagship image **multi-arch** with `buildx` and run it on Graviton.
3. ⭐ Deliberately run an **x86-only image** on Graviton and read the error.
4. ⭐⭐ Put a load test on a **`t3.micro`** and watch `CPUCreditBalance` fall to zero. **Record the latency
   before and after.**
5. ⭐ Set a **CloudWatch alarm** on credit balance and prove it fires.
6. ⭐⭐ Create a gp2 volume and a gp3 volume, benchmark both with `fio`, and **compute the cost of the
   same IOPS each way.**
7. ⭐ Modify a gp2 volume **to gp3 online** and confirm no downtime.
8. ⭐ Attach a volume to an undersized instance and **demonstrate the instance-level bandwidth cap.**
9. ⭐ Restore a snapshot and **measure the lazy-load penalty** on first read, then warm it.
10. ⭐⭐ Run a batch job on **Spot**, handle the interruption notice, and prove the work completes anyway.

## 🎙️ Articulation drill

**Two minutes:** *"How would you size the compute for this service?"*

**⭐ Refuse to guess out loud, which is the actual answer they want.** Start at `m`-family, current
generation, Graviton, and the smallest size that fits the heap; **then load-test and read utilisation,
because the right size is measured rather than chosen.**

**⭐ Then name the two traps to show it is experience rather than a table: burstable instances are cheap
right up until sustained load, where they either throttle to baseline or quietly bill you unlimited — so
`t` is for dev. And EBS is network storage, so provisioned IOPS above the instance's EBS bandwidth is
money for nothing.**
