# Part 1 — ⭐⭐ Failure detection: heartbeats are a guess

```
⭐⭐ The limit, restated from Day 398: ⭐⭐ a crashed node and a slow node are indistinguishable.
⭐   ⇒ ⭐ short timeout ⇒ ⭐⭐ FALSE POSITIVES: healthy nodes evicted, needless rebalancing/elections
⭐   ⇒ ⭐ long timeout  ⇒ ⭐⭐ SLOW DETECTION: the system serves errors for 30 seconds
⭐   ⇒ ⭐⭐ THERE IS NO CORRECT VALUE. There is only a chosen trade.
```

| ⭐ Detector | ⭐ Idea |
|---|---|
| ⭐ **Fixed-timeout heartbeat** | ⭐ simple, brittle — one GC pause and you are declared dead |
| ⭐⭐ **Phi-accrual** | ⭐⭐ **outputs a SUSPICION LEVEL, not a boolean** — learns the observed heartbeat distribution and adapts |
| ⭐ Used by | ⭐ Cassandra, Akka Cluster |
| ⭐⭐ **Why it is better** | ⭐⭐ **different components can act at different thresholds** — log at φ=3, stop routing at φ=8, evict at φ=12 |

> **⭐ The generalisable idea: replace a boolean with a confidence, and let each consumer choose its own
> threshold.** Removing a node from a load balancer should be far more eager than evicting it from a
> cluster, **and a single `isAlive()` forces both to use the same tolerance.**

## ⭐ Gossip and SWIM

| | |
|---|---|
| ⭐ **Gossip** | ⭐ each node periodically exchanges state with a few random peers |
| ⭐⭐ **Spreads in O(log N) rounds** | ⭐⭐ **no coordinator, no all-to-all traffic** — this is why it scales to thousands |
| ⭐⭐ **SWIM's indirect probe** | ⭐⭐ A cannot reach B ⇒ **A asks C and D to probe B** — distinguishes "B is down" from "A→B is down" |
| ⭐ Result | ⭐⭐ dramatically fewer false positives from one bad network path |
| ⭐ Cost | ⭐ eventually consistent membership — **nodes briefly disagree about who is alive** |

⚠️ **All-to-all heartbeating is O(N²) and dies around a few hundred nodes.** Gossip's whole reason for
existing is that constant. **And the indirect probe is the detail worth remembering: most "node down"
events are actually "one path down".**

# Part 2 — ⭐⭐ Split brain and the three defences

```
⭐⭐ A network partition splits 5 nodes into {A,B} and {C,D,E}.
⭐   ⇒ each side sees the other as failed
⭐   ⇒ ⭐⭐ each side elects a leader ⇒ ⭐⭐ TWO LEADERS, both accepting writes
⭐   ⇒ ⭐⭐ the partition heals ⇒ ⭐⭐ TWO DIVERGENT HISTORIES AND NO RULE FOR MERGING THEM.
```

| ⭐ Defence | ⭐ How |
|---|---|
| ⭐⭐ **1. Quorum** | ⭐⭐ **only a majority may act; {A,B} cannot, so it refuses writes** (Day 410) |
| ⭐⭐ **2. Fencing** | ⭐⭐ **epoch/generation numbers — the storage rejects the old leader's writes** (Day 411) |
| ⭐ **3. STONITH** | ⭐ the surviving side forcibly powers off the other — brutal, and used in real HA clusters |
| ⭐ Witness / tiebreaker node | ⭐⭐ a cheap third voter so two data nodes can still form a majority |

```
⭐⭐ AND THE CONFIGURATION THAT MAKES IT INEVITABLE:
⭐   ⭐⭐ A TWO-NODE CLUSTER. Neither side can ever have a majority.
⭐   ⇒ ⭐ so either both stop (useless) or both continue (split brain).
⭐   ⇒ ⭐⭐ THERE IS NO THIRD OPTION. Add a witness, or accept one of those two outcomes.
```

> **⭐ The healed-partition merge is the part people underestimate.** Detecting divergence is
> mechanical; **deciding what the correct state is after two histories both accepted writes is a
> business decision** — and if you have not designed it in advance, it becomes a manual reconciliation
> under pressure.

# Part 3 — ⭐⭐ Dynamo-style quorums, honestly

```
⭐ N = replicas per key · W = replicas that must ack a write · R = replicas read
⭐   ⭐⭐ R + W > N ⇒ the read set and write set OVERLAP ⇒ a read sees at least one latest copy.
⭐   N=3, W=2, R=2  ⇒ ⭐ the standard balanced choice
⭐   N=3, W=3, R=1  ⇒ ⭐ fast reads, ⭐⭐ writes fail if ANY replica is down
⭐   N=3, W=1, R=1  ⇒ ⭐⭐ fast and lossy — ⭐⭐ R+W ≤ N, no overlap guarantee at all
```

```
⭐⭐ THE CORRECTION MOST PEOPLE NEED:
⭐   ⭐⭐ R + W > N DOES NOT GIVE LINEARIZABILITY.
⭐   ⇒ ⭐ it guarantees the read set CONTAINS a node with the newest write
⭐   ⇒ ⭐⭐ but you must still DECIDE WHICH VALUE IS NEWEST — and that is usually a TIMESTAMP,
⭐     ⭐⭐ which is Day 409's clock skew, so LWW can still pick the wrong one.
⭐   ⇒ ⭐⭐ Concurrent writes, failed writes partially applied, and read repair racing
⭐     all remain possible. ⭐⭐ It is "probably fresh", not "correct".
```

| ⭐ Mechanism | ⭐ What it does |
|---|---|
| ⭐ **Hinted handoff** | ⭐ a replica is down ⇒ another node stores the write **as a hint** and delivers it later |
| ⭐⭐ **Sloppy quorum** | ⭐⭐ **W acks from *any* W nodes, not the right N** — highly available, **and it breaks the R+W>N guarantee** |
| ⭐ **Read repair** | ⭐ a read sees divergent replicas ⇒ writes the newest back |
| ⭐⭐ **Anti-entropy / Merkle trees** | ⭐⭐ **compare hash trees to find differing ranges without shipping all the data** |

⚠️ **Sloppy quorum is the honest footnote people omit.** It is what makes Dynamo-style systems so
available — **and it means your quorum guarantee is conditional on the right nodes being the ones that
answered.** Say "R + W > N gives overlap under a strict quorum" and you have said something true.

# Part 4 — ⭐⭐ Conflict resolution, and CRDTs

| Strategy | ⭐ Verdict |
|---|---|
| ⭐ **Last-write-wins** | ⭐⭐ **simple, and silently loses data** (Day 409) |
| ⭐ **Vector clocks + siblings** | ⭐ detects conflicts; **the application must merge** |
| ⭐⭐ **CRDTs** | ⭐⭐ **converge automatically, by construction — no coordination, no conflicts** |
| ⭐ Application merge | ⭐ the honest general answer: your domain knows what "correct" means |

```
⭐⭐ A CRDT's merge is COMMUTATIVE, ASSOCIATIVE and IDEMPOTENT.
⭐ ⇒ ⭐⭐ any order, any duplication, any number of merges ⇒ ⭐⭐ THE SAME RESULT. Always.

⭐ G-Counter      ⭐ per-node counters; merge = element-wise max; value = sum   (⭐ increment-only)
⭐ PN-Counter     ⭐ two G-Counters (increments, decrements)
⭐ LWW-Register   ⭐ a value with a timestamp — ⭐⭐ still loses data, but converges
⭐ ⭐⭐ OR-Set      ⭐⭐ add/remove with unique tags ⇒ ⭐⭐ concurrent add+remove resolves to ADD
⭐ ⭐ RGA / Yjs    ⭐ sequence CRDTs — ⭐⭐ this is how collaborative text editors work
```

| ⭐ Where CRDTs are the right answer | ⭐ Where they are not |
|---|---|
| ⭐⭐ **Collaborative editing** (Yjs, Automerge) | ⭐ anything with a **global invariant** — a balance that must not go negative |
| ⭐ Offline-first mobile sync | ⭐ uniqueness constraints |
| ⭐ Presence, counters, tags, shopping carts | ⭐⭐ "the result converges" is not "the result is what the business wants" |
| ⭐ Multi-region caches | ⭐ where metadata overhead matters (tombstones accumulate) |

> **⭐⭐ The honest limit: a CRDT guarantees everyone ends up with the same value, not that the value is
> correct.** An OR-Set resolving concurrent add-and-remove to *add* is **mathematically consistent and
> may be commercially wrong** — which is Day 409's shopping-cart resurrection, with a proof attached.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Looking for the "right" timeout | ⭐⭐ there is only a trade between false positives and slow detection |
| ⭐ A single boolean `isAlive()` | ⭐⭐ forces every consumer to share one tolerance |
| ⭐ All-to-all heartbeats at scale | ⭐ O(N²) — use gossip |
| ⭐ No indirect probing | ⭐⭐ "node down" is usually "one path down" |
| ⭐⭐ **A two-node cluster** | ⭐⭐ split brain is unavoidable — add a witness |
| ⭐ No fencing after failover | ⭐⭐ the old leader keeps writing (Day 411) |
| ⭐ No plan for merging after a heal | ⭐⭐ manual reconciliation under pressure |
| ⭐⭐ **Claiming R+W>N gives linearizability** | ⭐⭐ it gives overlap; you still resolve by timestamp |
| ⭐ Forgetting sloppy quorum weakens the guarantee | ⭐⭐ availability was bought with that caveat |
| ⭐ No anti-entropy | replicas drift permanently |
| ⭐⭐ **LWW on data with concurrent writers** | ⭐⭐ silent loss (Day 409) |
| ⭐ CRDTs where an invariant exists | ⭐⭐ convergence is not correctness |
| Ignoring CRDT metadata growth | tombstones accumulate |

## Interview questions

**Q: How do you detect that a node has failed?**
You cannot, strictly — a crashed node and a slow one are indistinguishable, so all you can do is choose a
trade between false positives and slow detection. A fixed heartbeat timeout makes that choice once for
everybody, which is why phi-accrual detectors are better: they learn the observed heartbeat distribution
and output a suspicion level rather than a boolean, so different consumers can act at different
thresholds — log at low suspicion, stop routing traffic at medium, evict from the cluster at high.
Removing a node from a load balancer should be far more eager than evicting it, and one boolean cannot
express that.

**Q: Why gossip rather than heartbeating everyone?**
All-to-all heartbeating is quadratic and falls apart in the low hundreds of nodes. Gossip has each node
exchange state with a few random peers, which disseminates information in logarithmic rounds with no
coordinator and no quadratic traffic. SWIM adds the detail that matters most in practice: if A cannot
reach B, it asks C and D to probe B before declaring anything, which distinguishes "B is down" from "the
path from A to B is down". Most node-down events are really one-path-down events, so that single
indirection removes a large class of false positives. The cost is eventually consistent membership —
nodes briefly disagree about who is alive.

**Q: What is split brain and how do you prevent it?**
A partition where each side believes the other has failed, elects its own leader, and both accept writes —
so when the partition heals you have two divergent histories and no rule for merging them. Three
defences: quorum, so only a majority side may act and the minority refuses writes; fencing with epoch
numbers, so the storage rejects the old leader's writes after failover; and in real HA clusters, STONITH,
where the surviving side powers the other off. The configuration that makes it unavoidable is two nodes,
because neither side can ever hold a majority — so either both stop, which is useless, or both continue,
which is split brain. Add a witness or accept one of those outcomes.

**Q: Does R + W > N give you strong consistency?**
No, and this is the correction most people need. It guarantees that the set of replicas you read overlaps
the set that acknowledged the write, so at least one replica you contacted has the newest value. It does
not tell you which value is newest — that is usually decided by a timestamp, which brings back clock skew
and last-write-wins losing data. Concurrent writes, partially applied writes and read repair racing all
remain possible. And sloppy quorums, which are what make these systems so available, accept W
acknowledgements from any nodes rather than the correct replicas, which breaks the overlap guarantee
outright. The accurate sentence is that R + W > N gives overlap under a strict quorum.

**Q: What is a CRDT and when would you use one?**
A data type whose merge operation is commutative, associative and idempotent, so replicas converge to the
same value regardless of the order or duplication of updates, with no coordination at all. Counters,
sets, registers and sequences all have CRDT forms — sequence CRDTs are how collaborative text editors
work. They are excellent for collaborative editing, offline-first sync, presence and multi-region
caches. The limit is important though: a CRDT guarantees everyone ends up with the same value, not that
the value is what the business wants. An observed-remove set resolves a concurrent add and remove to add,
which is mathematically consistent and may be commercially wrong — that is the shopping cart resurrecting
a deleted item, with a proof attached. So no CRDTs where a global invariant like a non-negative balance
exists.

## 🎙️ Articulation drill

**Two minutes:** *"How does your system handle a network partition?"*

**⭐ Start with the detection problem, because it frames everything: a partitioned node and a dead node
look identical, so detection is a confidence rather than a fact — which is why phi-accrual detectors
output a suspicion level and let each consumer choose its own threshold.**

**⭐ Then the prevention: a majority quorum so the minority side refuses to act rather than diverging, and
fencing with epoch numbers so a stale leader's writes are rejected by the storage after failover. And I
would say plainly that a two-node cluster has no good answer — neither side can hold a majority, so it is
either total unavailability or split brain, and a witness node is the fix.**

**⭐ If it is an available-under-partition system instead, I would be precise about what quorums give you:
R plus W greater than N gives an overlap between the read and write sets, not linearizability — you still
have to decide which value is newest, and sloppy quorums weaken even that. Which is why conflict
resolution is a design decision, and CRDTs guarantee convergence rather than correctness.**
