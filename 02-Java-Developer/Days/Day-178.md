# Day 178

**L-178** · `@Scheduled` and the distributed scheduling problem

**Time:** 3 hrs · **Mode:** NEW

> `@Scheduled` is three lines and it works perfectly — until you run two instances. Then **every job
> runs on every instance**, and the failure is not an exception. It is duplicate invoices, double
> charges, two emails to every customer, and a nightly reconciliation that produces the wrong number
> because two copies raced each other.
>
> Today: the scheduler's real defaults, the distributed problem and its solutions, and the design
> rule that makes duplicate execution harmless.

---

# Part 1 — ⭐ The single-thread default, which surprises everyone

```java
@Configuration
@EnableScheduling                                   // ⭐ or nothing runs
class SchedulingConfig { }
```

```java
@Component
public class ReportJobs {
    @Scheduled(cron = "0 0 2 * * *", zone = "UTC")      // ⭐ ALWAYS set the zone
    public void nightlyReport() { ... }

    @Scheduled(fixedDelay = 60_000, initialDelay = 30_000)
    public void pollOutbox() { ... }                     // Day 124
}
```

**⭐ Spring's default `TaskScheduler` has exactly ONE thread.** So:

- a job that takes 40 minutes **delays every other job by 40 minutes**;
- a job that hangs **stops all scheduling forever**, with no error;
- jobs that look independent are serialised.

```java
@Bean
ThreadPoolTaskScheduler taskScheduler() {
    var s = new ThreadPoolTaskScheduler();
    s.setPoolSize(5);                                    // ⭐ at minimum
    s.setThreadNamePrefix("sched-");
    s.setWaitForTasksToCompleteOnShutdown(true);
    s.setAwaitTerminationSeconds(60);
    s.setErrorHandler(t -> log.error("scheduled_job_failed", t));   // ⭐ see Part 2
    return s;
}
```

## `fixedDelay` vs `fixedRate` vs `cron`

| | Meaning | Use |
|---|---|---|
| `fixedDelay` | ⭐ **gap between end and next start** | **the safe default** — cannot overlap |
| `fixedRate` | gap between **starts** | ⚠️ ⭐ if the job runs longer than the rate, executions **queue up** |
| `cron` | wall-clock schedule | anything time-of-day specific |

**⭐ `fixedRate` with a job slower than its rate is a genuine trap.** With a single-threaded scheduler
the runs queue and then fire back-to-back forever; with a pool they **overlap**, which for anything
non-idempotent is corruption. **Prefer `fixedDelay` unless you specifically need wall-clock cadence.**

**⭐ Always set `zone`.** Without it the cron uses the JVM's default timezone, which differs between
your laptop and a container (usually UTC). A job set for "2 a.m." runs at a different real time in
each environment — and across a DST boundary a local-time job **runs twice or not at all**.

# Part 2 — ⭐ Exceptions, and the job that silently stopped

```java
@Scheduled(fixedDelay = 60_000)
public void pollOutbox() {
    throw new RuntimeException("boom");
}
```

**With `fixedDelay`, Spring logs the exception and schedules the next run** — so the job limps on. But
two failure modes bite hard:

1. ⭐ **A `cron`-scheduled job that throws is logged and rescheduled, but nobody is watching the log.**
   Six weeks later someone notices the nightly report has been missing.
2. ⭐ **An `Error` — or an exception escaping in some scheduler configurations — can cancel the
   task permanently.** The job stops. No alert, no restart, and it only comes back on a deploy.

**Every scheduled job needs three things:**

```java
@Scheduled(cron = "0 0 2 * * *", zone = "UTC")
@SchedulerLock(name = "nightlyReport", lockAtMostFor = "PT30M")
public void nightlyReport() {
    var sample = Timer.start(registry);
    try {
        reportService.generate();
        registry.counter("job.runs", "job", "nightlyReport", "outcome", "success").increment();
    } catch (Exception e) {                                   // ⭐ 1. NEVER let it escape
        log.error("job_failed job=nightlyReport", e);         // ⭐ 2. structured (Day 127)
        registry.counter("job.runs", "job", "nightlyReport", "outcome", "failure").increment();
    } finally {
        sample.stop(registry.timer("job.duration", "job", "nightlyReport"));   // ⭐ 3.
    }
}
```

**⭐ And the alert that matters most is not on failure — it is on absence.** A job that fails loudly
gets noticed; a job that silently stops running does not.

```
# Prometheus: alert if the nightly job has not succeeded in 26 hours
absent_over_time(job_runs_total{job="nightlyReport",outcome="success"}[26h])
```

**A "dead man's switch" alert on every scheduled job.** This is the single highest-value operational
practice on this page.

# Part 3 — ⭐⭐ The distributed problem

```
Instance 1 ──┐
Instance 2 ──┼── 02:00 → ⭐ ALL THREE run nightlyReport()
Instance 3 ──┘
```

**Three invoices. Three emails. Three concurrent writes racing each other.** And it works perfectly in
development, where there is one instance.

## Solution 1 — ⭐ ShedLock (the usual answer)

```xml
<dependency><groupId>net.javacrumbs.shedlock</groupId>
            <artifactId>shedlock-spring</artifactId></dependency>
<dependency><groupId>net.javacrumbs.shedlock</groupId>
            <artifactId>shedlock-provider-jdbc-template</artifactId></dependency>
```

```java
@Configuration
@EnableSchedulerLock(defaultLockAtMostFor = "PT30M")
class ShedLockConfig {
    @Bean LockProvider lockProvider(DataSource ds) {
        return new JdbcTemplateLockProvider(builder().withJdbcTemplate(new JdbcTemplate(ds))
                .usingDbTime()                              // ⭐⭐ database clock, not the JVM's
                .build());
    }
}
```

```java
@Scheduled(cron = "0 0 2 * * *", zone = "UTC")
@SchedulerLock(name = "nightlyReport",
               lockAtMostFor = "PT30M",                     // ⭐ safety valve
               lockAtLeastFor = "PT1M")                     // ⭐ clock-skew guard
public void nightlyReport() { ... }
```

**How it works:** each instance tries to insert/update a row in `shedlock`. One wins; the rest skip
silently. The lock is held for the job's duration.

**⭐ The two parameters are the whole design and both matter:**

- **`lockAtMostFor`** — if the instance holding the lock is killed, the row would otherwise stay
  locked forever. This is the maximum hold time after which the lock is considered abandoned.
  ⭐ **It must exceed the job's worst-case runtime by a comfortable margin** — set it too short and a
  second instance starts the job while the first is still running, which is precisely the duplicate
  execution you were preventing.
- **`lockAtLeastFor`** — hold the lock at least this long even if the job finishes in 50 ms.
  ⭐ **This guards against clock skew**: without it, a fast job on an instance whose clock is two
  seconds ahead releases the lock before a slower-clocked instance reaches the trigger, and it runs
  again.

**⭐ `usingDbTime()` is important and easy to miss** — it makes lock timing use the *database's*
clock rather than each JVM's, removing skew from the equation entirely.

## Solution 2 — leader election

```java
if (!leaderElection.isLeader()) return;      // ⭐ Kubernetes lease, ZooKeeper, Consul
```

One instance is the leader and runs all jobs. Simpler mentally, and it concentrates all scheduled
load on one instance and needs a real election mechanism.

## Solution 3 — an external scheduler

**Kubernetes `CronJob`, or a workflow engine** (Airflow, Temporal, Quartz clustered) triggering an
endpoint or running a separate pod.

**⭐ For anything genuinely important, this is the better architecture.** It gives you retries,
history, alerting on non-execution, manual re-runs, and — critically — **the job does not depend on
your web application being up**. `@Scheduled` couples your batch reliability to your API's uptime and
deploy cadence.

| Approach | Use |
|---|---|
| ⭐ **ShedLock** | **the pragmatic default** for in-app jobs |
| Leader election | when a real election mechanism already exists |
| ⭐ **Kubernetes `CronJob`** | ⭐ important, long-running, or independently-scalable work |
| Quartz clustered | complex schedules, persistence, misfire policies |

# Part 4 — ⭐ The design rule that outranks the locking

> **Make jobs idempotent, then duplicate execution is a performance problem rather than a correctness
> problem.**

```java
// ❌ not idempotent — running twice sends two emails
public void sendReminders() {
    for (Order o : repo.findOverdue()) { mailer.send(o); }
}

// ⭐ idempotent — the claim is atomic (Day 165's atomic UPDATE)
public void sendReminders() {
    int claimed = repo.claimForReminder(instanceId, Instant.now(), 100);
    for (Order o : repo.findClaimedBy(instanceId)) {
        mailer.send(o);
        repo.markReminded(o.getId());        // ⭐ record the effect
    }
}
```

```sql
update orders set reminder_claimed_by = :instance, reminder_claimed_at = :now
where id in (select id from orders
             where reminder_sent_at is null and due_at < :now
             order by due_at limit :n
             for update skip locked);        -- ⭐ concurrent workers never collide
```

**⭐ `FOR UPDATE SKIP LOCKED` is the key primitive** and it is worth knowing by name. Each worker
claims a distinct batch; none block each other; duplicate execution becomes *parallelism* rather than
duplication. This is how a job becomes safe to run on all six instances simultaneously — which is
strictly better than making sure only one runs.

**Three more rules that make jobs operable:**

1. ⭐ **Batch and bound.** `findOverdue()` returning 400,000 rows is an OOM and a 40-minute
   transaction (Day 156, Day 162). Always `limit`, always loop.
2. **Never hold a transaction for the whole job.** One transaction per batch, or you hold a
   connection and locks for the duration.
3. ⭐ **Make jobs manually triggerable.** An admin endpoint or a CLI, guarded by `@PreAuthorize`
   (Day 174). When the nightly job fails at 2 a.m., you need to re-run it at 9 a.m. without waiting
   24 hours or deploying.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ No `@EnableScheduling` | nothing runs, no error |
| ⭐ Default single-thread scheduler | one slow job delays all; one hang stops everything |
| `fixedRate` on a slow job | queued or overlapping executions |
| No `zone` on cron | different real time per environment; DST double-run |
| ⭐ No locking with multiple instances | duplicate side effects |
| `lockAtMostFor` shorter than the job | the duplicate execution you were preventing |
| No `lockAtLeastFor` | clock skew causes a second run |
| Not using `usingDbTime()` | JVM clock skew decides correctness |
| Letting exceptions escape | logged where nobody looks; may cancel the task |
| ⭐ No alert on **non-execution** | silently stopped jobs go unnoticed for weeks |
| Unbounded queries in a job | OOM and a long-held transaction |
| Non-idempotent jobs | any duplicate is corruption |
| No manual trigger | a failed nightly job waits 24 hours |

## Interview questions

**Q: What happens to `@Scheduled` when you scale to three instances?**
Every job runs on every instance. It is not an error — you get three invoices, three emails, and
concurrent writes racing. ShedLock is the usual fix: instances contend for a database row and only
the winner runs.

**Q: What do `lockAtMostFor` and `lockAtLeastFor` do?**
`lockAtMostFor` bounds how long a lock survives if the holder is killed, so a crashed instance does
not block the job forever — it must exceed the worst-case runtime, or a second instance starts while
the first is running. `lockAtLeastFor` holds the lock a minimum time to absorb clock skew between
instances, so a fast job cannot release before a slower-clocked instance reaches its trigger.

**Q: What is wrong with Spring's default scheduler?**
It has one thread. A slow job delays every other job, and a hung job stops scheduling entirely with
no error.

**Q: What is better than locking?**
Idempotent jobs. If a job claims work atomically — `FOR UPDATE SKIP LOCKED` — and records what it
did, then running on all instances is parallelism rather than duplication. Locking prevents a
symptom; idempotency removes the problem.

**Q: When would you not use `@Scheduled` at all?**
For anything important or long-running. A Kubernetes `CronJob` or a workflow engine gives retries,
run history, alerting on non-execution and manual re-runs — and it does not couple batch reliability
to the API's uptime and deploy cadence.

## 🎙️ Articulation drill

Two minutes: **"How do you run scheduled jobs in a service with multiple instances?"**

Lead with the failure — every instance runs every job, and it is silent duplication rather than an
error. ShedLock as the pragmatic fix, and explain both parameters by the failure each prevents rather
than by definition. Then raise the level twice: alert on *non-execution*, because a job that silently
stops is the failure nobody notices; and prefer idempotent jobs claiming work with `FOR UPDATE SKIP
LOCKED`, because that turns duplicate execution into parallelism instead of merely preventing it.
Close by noting that anything genuinely important belongs in an external scheduler, so batch
reliability is not tied to the API's uptime.
