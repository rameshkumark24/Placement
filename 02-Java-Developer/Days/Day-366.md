# Day 366 🏗️

**L-366** · Containerising the flagship — properly, and measured

**Time:** 3+ hrs · **Mode:** BUILD

> **⭐ Days 360–365 were mechanisms. Today they are applied to your own system, with numbers before

# Part 1 — ⭐ Measure first

**⭐ If you already have a Dockerfile, record these before changing anything. If you do not, build
the naive version first and measure that** — the comparison is the deliverable.

| ⭐ Measurement | ⭐ How |
|---|---|
| ⭐ **Image size** | `docker images` |
| ⭐⭐ **Bytes pushed for a one-line code change** | ⭐⭐ **the number that matters most** (Day 363) |
| ⭐ Build time, cold and warm | `time docker build` |
| ⭐ **Build context size** | the first line of build output |
| ⭐ Startup time to readiness | container start → `/actuator/health/readiness` = UP |
| ⭐ **Survives `-m 512m`?** | ⭐ yes/no, and peak RSS |
| ⭐ **Time from SIGTERM to exit** | ⭐⭐ and whether in-flight requests completed |
| CVE count by severity | `trivy image` |
| ⭐ **Secrets in `docker history`** | ⭐ yes/no |

# Part 2 — ⭐⭐ The Dockerfile, item by item

```dockerfile
# ───── build ─────
FROM eclipse-temurin:21-jdk-jammy AS build
WORKDIR /src
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn -q -B dependency:go-offline    ⭐ cached mount, no layer
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -q -B -o package -DskipTests

# ───── extract layers ─────
FROM eclipse-temurin:21-jre-jammy AS extract
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --launcher     ⭐ Boot 3.3+ (older: layertools)

# ───── runtime ─────
FROM eclipse-temurin:21-jre-jammy
WORKDIR /app
⭐ RUN useradd -r -u 10001 appuser                       ⭐ numeric uid (Day 363)
COPY --from=extract /app/app/dependencies/          ./  ⭐ least-changing FIRST
COPY --from=extract /app/app/spring-boot-loader/    ./
COPY --from=extract /app/app/snapshot-dependencies/ ./
COPY --from=extract /app/app/application/           ./  ⭐⭐ ~1 MB, changes every commit
USER 10001
EXPOSE 8080
⭐ ENTRYPOINT ["java", \                                  ⭐ EXEC form — signals reach the JVM
⭐   "-XX:MaxRAMPercentage=75", \                         ⭐ percentage, not -Xmx (Day 361)
⭐   "-XX:+ExitOnOutOfMemoryError", \                     ⭐ die on OOM rather than limping
⭐   "-Djava.security.egd=file:/dev/urandom", \
⭐   "org.springframework.boot.loader.launch.JarLauncher"]
```

| ⭐ Line | ⭐ Why it is there |
|---|---|
| ⭐ Two-stage + extract stage | ⭐ the JDK and Maven never ship (Day 363) |
| ⭐ **Cache mounts** | dependencies persist across builds without entering a layer (Day 362) |
| ⭐ `pom.xml` before `src` | ⭐⭐ **the ordering rule** — the dependency layer survives code changes |
| ⭐ **Layered COPY, least-changing first** | ⭐⭐ **1 MB per deploy instead of 60** |
| ⭐ Numeric `USER` | ⭐ `runAsNonRoot` can verify it |
| ⭐ **Exec-form ENTRYPOINT** | ⭐⭐ **graceful shutdown depends on this** (Day 361) |
| ⭐ `MaxRAMPercentage` | ⭐ survives a limit change |
| ⭐ **`ExitOnOutOfMemoryError`** | ⭐ a JVM that has OOM'd is not recoverable — **let it be restarted** |

## ⭐ The `.dockerignore` that matters

```
⭐ target/        ⭐⭐ the big one — otherwise every build sees a changed context
⭐ .git/          ⭐ often hundreds of MB
⭐ .env           ⭐⭐ so it can never be COPYied by accident
*.md
.idea/ .vscode/
⭐ **/*.log
```

⚠️ **`target/` in the context is the most common cause of a permanently cold build cache** (Day 362).
**Measure the context size before and after — it is usually a dramatic difference.**

# Part 3 — ⭐ Compose, close to production

```yaml
services:
  app:
    build: .
    ⭐ deploy: { resources: { limits: { memory: 512M, cpus: "1.0" } } }   ⭐ so the JVM sees a cgroup
    environment:
      SPRING_PROFILES_ACTIVE: docker
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/app
      SPRING_CONFIG_IMPORT: "configtree:/run/secrets/"     ⭐ secrets as FILES (Day 364)
    volumes: ["./secrets:/run/secrets:ro"]
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_healthy }
    healthcheck:
      test: ["CMD","curl","-fsS","http://localhost:8080/actuator/health/readiness"]
      ⭐ start_period: 40s      ⭐⭐ WITHOUT THIS you get a restart loop (Day 364)
      interval: 10s
      retries: 3
    ⭐ stop_grace_period: 45s   ⭐⭐ must EXCEED your graceful-shutdown timeout

  postgres:
    ⭐ image: postgres:16.4     ⭐ pinned to the PRODUCTION version
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./init:/docker-entrypoint-initdb.d:ro
    healthcheck: { test: ["CMD-SHELL","pg_isready -U app -d app"], interval: 5s, retries: 10 }

  nginx:
    image: nginx:1.27
    ports: ["8443:443"]
    depends_on: [app]
    volumes: ["./nginx:/etc/nginx/conf.d:ro"]

volumes: { pgdata: }
```

**⭐ Then run it the way production runs:**

```
⭐ docker compose up -d --scale app=2       ⭐⭐ TWO replicas behind Nginx (Day 365)
```

> **⭐ Scaling to two locally is the step that finds the real bugs.** Sessions, in-process caches,
> `@Scheduled` jobs, in-memory rate limiters — **Day 324's whole list surfaces here, on your laptop,
> before it surfaces in production.**

# Part 4 — ⭐⭐ Verify: the eight tests

**⭐ Each of these either passes or produces a number. None is optional.**

```
⭐ 1. SIZE            docker images        ⭐ target: < 300 MB
⭐ 2. ⭐⭐ DEPLOY DELTA  change one line, rebuild, push  ⭐ target: ~1 MB, not 60
⭐ 3. ⭐ MEMORY        docker run -m 512m …  ⭐ runs for 10 min under load without exit 137
⭐ 4. ⭐⭐ SIGTERM       docker stop with a request in flight
⭐                     ⭐⭐ target: request COMPLETES, container exits ~4 s, exit code 143
⭐ 5. ⭐ NON-ROOT      docker exec … id     ⭐ uid=10001, not 0
⭐ 6. ⭐ READ-ONLY     --read-only --tmpfs /tmp   ⭐ still starts and serves
⭐ 7. ⭐⭐ SECRETS       docker history --no-trunc | grep -i secret   ⭐⭐ target: NOTHING
⭐ 8. ⭐ SCAN          trivy image --severity HIGH,CRITICAL  ⭐ zero fixable
```

⚠️ **Test 4 is the one people skip and the one that matters on every deploy.** Send a request that
takes ten seconds, `docker stop` mid-flight, and **watch whether it completes or is severed.** If it
is severed, work back through the chain: exec form → Spring `server.shutdown=graceful` →
`spring.lifecycle.timeout-per-shutdown-phase` → `stop_grace_period` (Day 361).

⚠️ **Test 3 must be under load, not idle.** An idle JVM fits in almost anything; **it is the loaded
heap, thread stacks and direct buffers together that breach the limit.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No baseline measurements | ⭐ the result is an opinion (Day 307) |
| ⭐ Optimising size but not layering | ⭐⭐ you fixed the number you feel least often |
| ⭐ **Shell-form ENTRYPOINT** | ⭐⭐ graceful shutdown silently absent |
| ⭐ Testing memory while idle | passes locally, exit 137 in production |
| ⭐ **`stop_grace_period` shorter than the drain timeout** | SIGKILL mid-drain |
| ⭐ No `start_period` on the healthcheck | ⭐ restart loop |
| ⭐ **`target/` not in `.dockerignore`** | a permanently cold cache |
| One replica locally | statelessness bugs stay hidden |
| A different local database version | a locally-passing query that fails live |
| ⭐ Secrets as environment variables | inspectable (Day 364) |
| Skipping the SIGTERM test | dropped requests on every deploy |

## Interview questions

**Q: Walk me through your Dockerfile.**
Three stages. A build stage with the JDK and Maven using cache mounts, with the pom copied before the
source so dependency resolution survives code changes. An extract stage that explodes the fat jar
into Boot's layers. Then a JRE runtime stage that copies those layers least-changing first, runs as a
numeric non-root uid, and uses an exec-form entrypoint with `MaxRAMPercentage` rather than a fixed
heap. The result is about 240 megabytes and roughly a megabyte moved per code change.

**Q: How do you know graceful shutdown works?**
I tested it. Send a request that takes ten seconds, `docker stop` mid-flight, and check that the
request completes and the container exits cleanly with 143 rather than being killed with 137. If it
fails, the chain is exec form so the JVM receives SIGTERM, Spring's graceful shutdown, the
per-phase timeout, and a stop grace period longer than that timeout. Every one of those has to be
right, and only the test tells you.

**Q: Why run two replicas locally?**
Because one replica hides an entire class of bug — in-memory sessions, in-process caches,
`@Scheduled` jobs firing on every node, per-instance rate limits. Two replicas behind Nginx costs one
flag and surfaces all of it on my laptop instead of in production. It also exercises the proxy path,
so forwarded headers and TLS termination get tested rather than assumed.

**Q: What is the single most valuable number here?**
Bytes pushed for a one-line change, not total image size. Total size matters for cold starts; bytes
per deploy is what you pay ten times a day, and layered jars take it from sixty megabytes to about
one. Teams optimise the number they see in `docker images` and ignore the one they actually feel.

**Q: How do you keep secrets out?**
Nothing secret enters the image at any layer, because layers are permanent — I verify with
`docker history --no-trunc` and by extracting layer tars. Build-time secrets use BuildKit mounts,
runtime secrets are mounted files read through Spring's config tree rather than environment
variables, and `.env` is in both `.gitignore` and `.dockerignore` so it cannot be copied in by
accident.

## Mini task

**⭐ The build is the task. Then:**

1. **Record all nine baseline measurements** before you change anything.
2. ⭐ Implement the three-stage Dockerfile with **layered jars** and re-measure. **Fill in the
   table.**
3. ⭐ Add the `.dockerignore` and **record the context size change.**
4. ⭐⭐ **Run the SIGTERM test.** If a request is severed, fix each link in the chain and re-test until
   it completes.
5. ⭐ Run under `-m 512m` **with load** for ten minutes. If it dies, tune `MaxRAMPercentage` and
   measure peak RSS.
6. ⭐ Run `--read-only --cap-drop=ALL --security-opt=no-new-privileges` and **fix what breaks.**
7. ⭐⭐ **Scale to two replicas behind Nginx.** Find and fix at least one statelessness bug.
8. ⭐ Move every secret to a **mounted file** via `configtree:`. **Verify `docker history` is clean.**
9. ⭐ Scan with Trivy; **drive fixable HIGH/CRITICAL to zero.**
10. ⭐ **Time fresh-clone to working system** and commit the before/after table.

## 🎙️ Articulation drill

**Three minutes:** *"Tell me how your application is packaged and deployed."*

**⭐ Lead with numbers, not the Dockerfile.** *"Two-forty megabytes, about a megabyte moved per code
change because the jar is layered, runs non-root under a 512 MB limit with the heap as a percentage
of the cgroup, and a `docker stop` mid-request completes it and exits cleanly in four seconds — I
tested that specifically."*

**⭐ The marker is the last clause.** Almost anyone can describe a multi-stage build. **Saying you
tested SIGTERM handling with a request in flight, and giving the number, is the thing that separates
someone who has operated a service from someone who has read about Docker.**
