# Day 352 ⭐

**L-352** · ⭐ Design 8 — the chat system

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Every other design in this stage is request/response. This one holds fifty million open
> connections, which makes the servers stateful — and everything hard follows from that.**
>
> The deep dive is routing: **a message arrives at gateway node 47 and must reach a user connected to
> gateway node 2,318.** Nothing in the previous seven designs prepares you for that.

---

# Part 1 — ⭐ Requirements and estimates

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| 1:1 and group chat | ⭐⭐ **delivery latency < 200 ms** |
| ⭐ **Delivery receipts: sent / delivered / read** | ⭐ **ordering per conversation** — never per system |
| ⭐ **Offline delivery** | ⭐ **no message loss, ever** — durability first |
| Message history | ⭐ availability 99.99% |
| ⭐ **Presence (online/last seen)** | ⭐ **multi-device consistency** |
| Media attachments | |

```
⭐ ESTIMATE
⭐   50M DAU · 40 messages/day ⇒ 2B/day ⇒ ⭐ ~23,000 msgs/s ⇒ peak ~70,000/s
⭐   ⭐⭐ Concurrent connections: ~20M ⇒ at 50k per gateway node ⇒ ⭐ ~400 GATEWAY NODES
⭐   Storage: 2B × 300 B = 600 GB/day ⇒ ⭐ 220 TB/year ⇒ ~1 PB provisioned over 5 years
⭐   ⭐ Fan-out: 1:1 = 1; a 500-member group = 500 deliveries per message
```

> **⭐ Twenty million concurrent connections across four hundred nodes is the fact that shapes
> everything.** Say it early: **this is not a QPS problem, it is a connection-state problem**, and it
> breaks the statelessness rule that Day 324 spent a whole day establishing.

# Part 2 — ⭐ The architecture

```
⭐ client ──WebSocket──► ⭐ GATEWAY NODE (holds the connection)
⭐                              │
⭐                              ▼
⭐                        ⭐ CHAT SERVICE ──► ⭐ message store (wide-column)
⭐                              │
⭐                              ├──► ⭐ SESSION REGISTRY: userId → gatewayNodeId
⭐                              └──► ⭐ PUSH SERVICE (offline recipients)
```

| Component | ⭐ Job |
|---|---|
| ⭐ **Gateway** | ⭐⭐ **holds WebSockets — stateful, and the only stateful tier** |
| ⭐ Chat service | ⭐ stateless: persist, assign sequence, route |
| ⭐ **Session registry** | ⭐⭐ **userId → which gateway node — the routing table** |
| Message store | durable history |
| Push service | APNs/FCM for offline users (Day 350) |

⚠️ **Keep the gateway dumb.** It terminates the connection, authenticates once, and forwards.
**Business logic in the gateway means you cannot deploy business changes without dropping twenty
million connections** — which is the practical reason the tiers are split.

# Part 3 — ⭐⭐ The deep dive: routing to a connection

```
⭐ Alice (on gateway 47) sends to Bob (on gateway 2318). ⭐ How does gateway 47 find gateway 2318?
```

| ⭐ Approach | ⭐ Verdict |
|---|---|
| ⭐ Broadcast to all 400 gateways | ⭐⭐ **400× amplification — 70k msgs/s becomes 28M** |
| ⭐⭐ **Session registry lookup, then direct send** | ⭐⭐ **one lookup, one hop — the standard answer** |
| ⭐ Pub/sub topic per user | ⭐ elegant, but 50M topics is beyond most brokers |
| Consistent hashing user → gateway | ⭐ **clients cannot choose their gateway; a reconnect lands anywhere** |

```
⭐ THE FLOW:
⭐  1. Gateway 47 → chat service: message
⭐  2. ⭐ Chat service PERSISTS FIRST, assigning a per-conversation sequence number
⭐  3. Lookup: session registry → Bob is on gateway 2318 (and gateway 91, second device)
⭐  4. Deliver to both gateways → they push over the sockets
⭐  5. ⭐ No session ⇒ Bob is offline ⇒ push notification; the message waits in the store
```

| ⭐ Detail | ⭐ Why |
|---|---|
| ⭐⭐ **Persist before delivering** | ⭐⭐ **the store is the source of truth; a delivery may fail and be retried from it** |
| ⭐ The registry is ephemeral | ⭐ Redis with a TTL, refreshed by heartbeat — **losing it means reconnects, not data loss** |
| ⭐ **A stale registry entry** | ⭐ delivery to a dead node fails ⇒ **treat as offline and fall back to push** |
| ⭐ Multi-device | ⭐ **one user maps to a SET of connections, not one** |

## ⭐⭐ Ordering — and why client timestamps are wrong

> **⭐ Ordering is per conversation, not global — exactly Day 334's partition rule.** And the sequence
> number is assigned by the **server**, at persist time.

```
⭐ ✗ Client timestamps: ⭐⭐ clocks disagree, so a reply can sort BEFORE the message it answers
⭐ ✓ ⭐ A monotonic per-conversation sequence, assigned server-side on persist
⭐ ⇒ ⭐ clients sort by sequence, detect gaps, and request what they missed
```

**⭐ The gap-detection consequence is the useful part:** a client that holds sequences 1–40 and 42
**knows** it missed 41 and can fetch it. **Without a sequence there is no way to know a message was
lost** — which is why "no message loss" is achievable at all.

## ⭐ Storage — the canonical wide-column case

```
⭐ PRIMARY KEY ((conversation_id), sequence DESC)      ⭐ Day 332's partition + clustering key
⭐ ⇒ ⭐ "the last 50 messages of this conversation" is ONE sequential read
⭐ ⇒ ⭐ writes are append-only and spread evenly by conversation
```

⚠️ **The wide-partition risk (Day 348): a conversation with ten million messages is one enormous
partition.** **Bucket it** — `((conversation_id, month), sequence)` — so partitions stay bounded and
old months can be tiered to cheap storage.

# Part 4 — ⭐ Groups, presence, receipts, and what breaks

## ⭐ Group fan-out — Day 351's problem, again

| Group size | ⭐ Strategy |
|---|---|
| ⭐ **Small (< ~500)** | ⭐ **fan out on write** — deliver to each member's connections |
| ⭐⭐ **Large channels (100k+)** | ⭐⭐ **fan out on READ** — members pull from the conversation on open |

> **⭐ Say the connection explicitly: this is the news feed's celebrity problem in a different
> costume.** A 100,000-member channel where someone posts is 100,000 deliveries; **the same hybrid
> threshold logic applies, and recognising the repeat is the point of doing eight designs.**

## ⭐⭐ Presence — the expensive feature nobody budgets for

```
⭐ NAIVE: every user subscribes to every contact's status.
⭐ ⇒ 50M users × 200 contacts = ⭐⭐ 10 BILLION subscriptions, and a status change fans out to 200.
⭐ ⇒ ⭐⭐ Presence traffic can EXCEED message traffic. This is real.
```

| ⭐ Mitigation | |
|---|---|
| ⭐⭐ **Only push presence for contacts currently on screen** | ⭐⭐ **the single biggest reduction** |
| ⭐ Heartbeats every 30 s, TTL in Redis | offline is inferred by expiry — no explicit disconnect needed |
| ⭐ **Coarse granularity** | ⭐ "active recently" rather than a live indicator |
| Debounce flapping | a poor mobile connection toggles constantly |

## ⭐ Receipts, and their cost

**⭐ Sent → delivered → read triples your write volume**, since each is a small update. **Batch them**:
a client acknowledges up to sequence N rather than per message, **which turns fifty updates into
one.**

## ⭐ Connections, deploys and what breaks

| ⭐ Problem | ⭐ Answer |
|---|---|
| ⭐⭐ **Deploying the gateway drops 50k connections per node** | ⭐⭐ **drain slowly, reconnect with jitter — a synchronised reconnect is a self-inflicted DDoS** |
| ⭐ **Thundering-herd reconnect** | ⭐ exponential backoff **with jitter**, enforced client-side |
| ⭐ Load balancing long-lived connections | ⭐ **L4 balances connections, not load** (Day 325) — rebalance by disconnecting the idlest |
| Mobile networks dropping sockets | ⭐ resume by sequence, not by replaying everything |
| ⭐ **Registry loss** | reconnects rebuild it; messages are safe in the store |
| Hot conversation | a huge group — read-time fan-out |

```
⭐ MONITOR: ⭐ connections per node · message delivery p99 · ⭐ registry lookup miss rate
⭐          reconnect rate (⭐ a spike = a deploy problem) · ⭐ messages/s (business metric)
⭐ CUT:     voice/video, reactions, threads, search, E2E encryption (⭐ mention it as a real change)
⭐ AT 10×:  ⭐ more gateway nodes and registry shards — ⭐ the shape holds
```

⚠️ **End-to-end encryption is worth one honest sentence: it removes the server's ability to do
search, moderation, server-side history sync and rich push previews.** It is not a feature you add
later — **it is an architecture.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Broadcasting to every gateway | ⭐⭐ **400× traffic amplification** |
| ⭐ Delivering before persisting | ⭐ a failed delivery has nothing to retry from |
| ⭐⭐ **Client timestamps for ordering** | ⭐⭐ **replies sort before their messages** |
| ⭐ No sequence numbers | ⭐ **gaps are undetectable — "no loss" becomes unprovable** |
| One connection per user assumed | multi-device breaks |
| ⭐ **Unbounded conversation partitions** | one chat becomes an unmanageable partition |
| ⭐ Fanning out to a 100k-member channel on write | ⭐ the celebrity problem, unrecognised |
| ⭐ **Naive presence subscriptions** | ⭐⭐ presence traffic exceeds message traffic |
| Per-message receipts | ⭐ triple write volume; batch by sequence |
| ⭐ Reconnect with no jitter | ⭐ **a self-inflicted DDoS after every deploy** |
| Business logic in the gateway | you cannot deploy without dropping 20M connections |
| Treating E2E as a later feature | it is an architectural decision |

## Interview questions

**Q: What makes chat different from every other design here?**
It is stateful. Twenty million concurrent WebSocket connections spread over four hundred gateway
nodes means a server holds something that matters — which breaks the statelessness that makes
everything else easy to scale. The consequences are a routing problem, a deployment problem, and a
load-balancing problem that ordinary request/response systems never face.

**Q: A message arrives for a user connected to another node. How does it get there?**
A session registry — userId to the set of gateway nodes holding that user's connections, kept in
Redis with a heartbeat TTL. The chat service persists the message first, assigns a per-conversation
sequence, looks up the registry and delivers to those specific gateways. Broadcasting to all four
hundred would be a four-hundred-fold amplification. If there is no session, the user is offline and
it becomes a push notification while the message waits in the store.

**Q: How do you guarantee ordering?**
Per conversation, with a monotonic sequence assigned server-side at persist time. Client timestamps
are unusable because clocks disagree, so a reply can sort before the message it answers. The
sequence also makes loss detectable: a client holding one to forty and forty-two knows it missed
forty-one and can request it — which is what makes "no message loss" a claim you can actually
support.

**Q: How do you store messages?**
Wide-column, partitioned by conversation with sequence as the clustering key, so the last fifty
messages of a conversation is one sequential read and writes spread evenly. The risk is a wide
partition — a conversation with ten million messages — so I bucket by conversation and month, which
bounds partitions and lets old buckets move to cheaper storage.

**Q: What does presence cost?**
More than people expect. Fifty million users with two hundred contacts each is ten billion potential
subscriptions, and a single status change fans out to two hundred people — presence traffic can
exceed message traffic. The fix is to only push presence for contacts currently visible on screen,
use heartbeats with a TTL so offline is inferred by expiry, and keep the granularity coarse. It is
the feature most often designed as an afterthought and most likely to dominate the bill.

**Q: What happens when you deploy the gateway?**
Fifty thousand connections per node drop, and if every client reconnects immediately you have built
your own denial of service. So: drain slowly, roll nodes gradually, and require exponential backoff
with jitter on the client. Reconnect rate is a metric I would watch specifically, because a spike in
it is almost always a deployment problem rather than a network one.

## 🎙️ Articulation drill

**Three minutes:** *"Alice sends Bob a message. Trace it from her keyboard to his screen."*

**⭐ The complete trace has seven steps** — WebSocket to her gateway · gateway to the chat service ·
**persist first, assigning a per-conversation sequence** · session registry lookup for Bob's
connections · deliver to those specific gateways, not all of them · **push notification if he has no
session** · and the delivery receipt flowing back.

**⭐ Two markers within it: "persist before delivering, because the store is what a retry reads
from", and "the sequence is assigned by the server, because client clocks disagree".** Both are one
sentence each, and both are the difference between describing a chat app and designing one.
