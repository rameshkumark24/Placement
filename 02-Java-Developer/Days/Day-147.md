# Day 147 ⭐

**L-147** · DTOs vs entities — never expose your entity

**Time:** 3 hrs · **Mode:** NEW · **Marquee day**

> **The highest-consequence-per-line-of-code day in the Web block.** Exposing a JPA entity directly is
> a single decision that simultaneously creates a security hole, a coupling problem, a performance
> cliff and a versioning trap — and it is the default thing every tutorial does.
>
> Day 105 gave you mass assignment and the trust boundary. Day 106 gave you the four JSON types that

# Part 1 — The four separate reasons, each fatal on its own

```java
@Entity
public class User {
    @Id @GeneratedValue Long id;
    String email;
    String passwordHash;                       // ⭐ 1
    String passwordResetToken;                 // ⭐ 1
    boolean admin;                             // ⭐ 2
    BigDecimal creditLimit;                    // ⭐ 2
    Instant createdAt;
    @OneToMany(mappedBy = "user") List<Order> orders;   // ⭐ 3
    @ManyToOne Organisation organisation;               // ⭐ 3
}

@GetMapping("/users/{id}")
User get(@PathVariable Long id) { return repo.findById(id).orElseThrow(); }   // ❌
```

### ⭐ 1 — Data exfiltration on read

That response contains `passwordHash` and `passwordResetToken`. The hash lets an attacker crack
offline at leisure (Day 112's GPU numbers). **The reset token is worse: it is a live credential.** Read
it from the JSON, use it, own the account. No exploit required — just a GET.

`@JsonIgnore` on the field *works*, and it is the wrong fix, because it is **deny-list security**.
Day 108's principle: the next person adds `twoFactorSecret` and forgets the annotation, and nothing
tells them. A DTO is the allow-list — a new entity field is invisible until someone deliberately adds
it to the response.

### ⭐ 2 — Mass assignment on write

```java
@PutMapping("/users/{id}")
User update(@PathVariable Long id, @RequestBody User user) { return repo.save(user); }   // ❌❌
```

```bash
curl -X PUT /users/42 -d '{"email":"me@x.com","admin":true,"creditLimit":1000000}'
```

**Day 105's mass assignment, in its purest form.** Jackson binds every field it is given; the entity
has an `admin` field; `save` persists it. This is the GitHub 2012 incident and it is still shipped
weekly. With `@RequestBody UpdateProfileRequest(String displayName, String email)` the attack has
nowhere to land — the field does not exist to be bound.

### ⭐ 3 — The performance cliff

`orders` is `LAZY`. Jackson serializes it, which triggers the load, which is one query — then each
order's `items` is lazy too, which is N more. **A single GET has become 200 queries**, and it happens
during serialization where no profiler you are looking at reports it.

Worse, `Order` has a `user` back-reference, so Jackson recurses: user → orders → user → orders →
`StackOverflowError`, or an infinite response if you "fixed" it with `@JsonManagedReference` badly.

And if the transaction closed before serialization (Day 143's `open-in-view: false`, which is the
correct setting) you instead get **`LazyInitializationException` thrown during writing**, after the
200 status line is already committed to the wire — producing a truncated, malformed response body
that no error handler can rescue. Day 160 covers this properly; note that the *root* cause is
serializing an entity.

### ⭐ 4 — Coupling and versioning

Day 109: **your API contract is now your database schema.** Rename a column for clarity and every
mobile client in the field breaks. Add a column for an internal migration and it appears in the public
API. Change a type from `int` to `long` and you shift a JSON number's range.

You cannot evolve either side independently. The DTO is precisely the seam that lets the database
change on database timescales and the API change on API timescales.

# Part 2 — The shape that works

```java
// ── Inbound: exactly what a client may say. Nothing else exists. ──
public record CreateOrderRequest(
        @NotBlank String productId,
        @Min(1) @Max(100) int quantity,
        @Valid ShippingAddress shipTo) { }

// ── Outbound: exactly what a client may see. ──
public record OrderResponse(
        UUID id,
        String productId,
        int quantity,
        BigDecimal total,
        String status,
        Instant placedAt) {

    static OrderResponse from(Order o) {                 // ⭐ mapping lives with the DTO
        return new OrderResponse(o.getId(), o.getProductId(), o.getQuantity(),
                                 o.getTotal(), o.getStatus().name(), o.getPlacedAt());
    }
}
```

**Records are close to ideal for DTOs**: immutable, compact, `equals`/`hashCode` free, and Jackson
supports them natively (Boot 3 + `-parameters`, which Day 145 covered). Day 060's records, doing the
job they were designed for.

## The five rules

| Rule | Why |
|---|---|
| **Separate request and response types** | they are different contracts. A response has `id`, `createdAt`, `total`; a request must not accept any of them. One shared `OrderDto` reintroduces mass assignment through the back door |
| **A different response per audience** | `OrderResponse` for customers, `AdminOrderResponse` with cost and margin for staff. Do not filter one type at runtime by role — that is a deny-list again, and one missed branch leaks margin data |
| **No entity type in any DTO field** | `record OrderResponse(User user)` has reintroduced every problem |
| **DTOs live in the feature package** | Day 141 — `order/CreateOrderRequest`, not a global `dto` package |
| **Map explicitly** | see below |

## Mapping: the honest comparison

| Approach | Verdict |
|---|---|
| **Static factory / constructor** | ⭐ **the default.** Zero dependencies, debuggable, and the compiler catches a new required field. Verbose — and the verbosity is *visible coupling*, which is information |
| **MapStruct** | Good at scale. Generates the code at compile time, so it is fast and steppable, and it **fails the build on an unmapped field**, which is the property that matters |
| **ModelMapper / reflection mappers** | ❌ avoid. Matches by name at runtime, so a rename silently produces a null, and it will happily map a lazy collection and trigger §3 |
| **Constructor projection in the query** | ⭐ **the best option for reads.** `select new OrderResponse(o.id, ...)` — the entity is never loaded at all, so there is no lazy collection to trigger. Day 161 |

**The last row deserves emphasis.** Mapping entity → DTO in Java still loads the whole entity graph.
Projecting directly in the query selects six columns and constructs the DTO. For a list endpoint this
is often the difference between 200 ms and 8 ms, and it makes §3 structurally impossible.

# Part 3 — The objections, answered honestly

**"This is boilerplate."** Some of it is. But count what it buys: an allow-list on read, no mass
assignment on write, no lazy loading in serialization, and independent evolution of schema and API.
Four classes of bug for a records file. And when the DTO looks identical to the entity today, that
is a snapshot, not a law — the value is precisely that it can stop being identical without breaking a
client.

**"I'll use `@JsonIgnore` / `@JsonView` instead."** Both are deny-lists. `@JsonView` is genuinely
better than bare `@JsonIgnore` for multi-audience responses, but it still means a new entity field is
exposed by default and the annotation is the only thing standing between it and the internet. Prefer
the shape where forgetting is safe.

**"My entity is internal, nobody sees it."** Until someone adds a controller. The property you want is
that the leak is *impossible*, not that it is *currently absent*.

**"DTOs everywhere is overkill for a CRUD admin panel."** Fair, and here is the honest threshold:
**if the endpoint is authenticated, internal, has one audience and no lazy relationships, exposing the
entity is a defensible shortcut.** For anything public, multi-audience, or with relationships, it is
not. Say exactly this in an interview — the nuance reads far better than dogma.

## Where the boundary sits

```
HTTP  ──►  CreateOrderRequest  ──►  OrderService  ──►  Order (entity)  ──►  DB
                                        │
HTTP  ◄──  OrderResponse       ◄────────┘
```

**The service takes and returns DTOs; the entity never leaves the service layer.** A common
half-measure — controller maps to entity, service takes an entity — leaves the entity in the
controller's vocabulary and the discipline erodes within a quarter.

Two adjacent decisions worth stating:

- **The service returns `OrderResponse`, not `Order`.** Otherwise the controller must map, which
  means the controller must import the entity, which is what you were avoiding.
- **Internal callers (jobs, consumers) use the same service methods**, so they get the same
  validation and the same rules. Day 146's point about business logic in controllers.

# Part 4 — Two things that make this cheap

## Bean Validation on the DTO does structural work for free

Day 148's subject, but note the fit: `@NotBlank`, `@Min`, `@Email` on a request DTO give you Day 105's
boundary validation with no code. On an entity, the same annotations are a *persistence* constraint,
which is a different concern with a different lifetime.

## `@JsonProperty(access = READ_ONLY)` for the one field you do share

```java
public record OrderDto(
        @JsonProperty(access = READ_ONLY) UUID id,     // serialized, never deserialized
        @NotBlank String productId) { }
```

If you genuinely must share a type between request and response, this is the tool. Treat it as a
concession, not a pattern.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Returning the entity | four independent bug classes at once |
| ⭐ `@RequestBody Entity` | mass assignment; privilege escalation via JSON |
| `@JsonIgnore` as the security model | deny-list; the next field leaks silently |
| One DTO for request and response | mass assignment returns through the shared fields |
| Runtime filtering by role in one response type | one missed branch leaks admin data |
| DTO containing an entity field | every problem, one level down |
| ModelMapper/reflection mapping | silent nulls on rename; triggers lazy loads |
| Mapping in Java when a projection would do | loads the whole graph to build six fields |
| Service methods taking entities | boundary erodes; controller imports the entity |

## Interview questions

**Q: Why not return your JPA entity from a controller?**
Four reasons and each stands alone: it leaks fields like password hashes on read; it enables mass
assignment on write; lazy relationships get serialized, causing N+1 or a
`LazyInitializationException` mid-response; and it welds the API contract to the database schema so
neither can change independently.

**Q: Isn't `@JsonIgnore` enough?**
It is a deny-list. Security that depends on remembering an annotation for every future field fails
the moment someone forgets. A DTO is an allow-list — a new entity field is invisible until someone
chooses to expose it.

**Q: How do you map?**
Static factory methods by default because they are explicit and the compiler helps; MapStruct at
scale because it fails the build on unmapped fields; and for read endpoints, constructor projection
in the query so the entity is never materialised at all. Never a reflective runtime mapper.

**Q: Is there any case where exposing the entity is fine?**
An internal, authenticated, single-audience endpoint with no lazy relationships — a small admin CRUD.
Anything public, multi-audience, or with relationships, no.

## Mini task

1. Build the naive version: `@Entity User` with `passwordHash`, returned from `GET /users/{id}`.
   **`curl` it and read your own password hash in the response.**
2. `PUT /users/1` with `{"admin":true}`. Query the database. Confirm you escalated your own
   privileges with a JSON field.
3. Add a lazy `@OneToMany`. Turn on `spring.jpa.show-sql`, GET the user, and **count the queries.**
4. Set `spring.jpa.open-in-view: false` and GET again. Watch the response truncate mid-JSON.
5. Now introduce `CreateUserRequest` and `UserResponse` records. Re-run all four attacks. All four
   fail — and note that three of them fail because the field *does not exist*, not because you
   defended against them.
6. Replace the read path with a constructor projection. Compare query count and latency.
7. Add a field to the entity. Confirm it does **not** appear in the API. That is the property you
   were buying.

## 🎙️ Articulation drill

Two minutes: **"Why don't you return entities from your API?"**

Give the four reasons crisply — leaks, mass assignment, lazy serialization, coupling — and make the
security point structural: the DTO is an allow-list, so a field added to the entity next year cannot
leak, whereas `@JsonIgnore` requires everyone to remember forever. Then show judgement rather than
dogma: name the case where you would expose the entity, and finish on the performance point most
people miss — for reads, project into the DTO in the query, so the entity is never loaded and the
lazy-loading problem cannot exist.
