# Day 221 📦

**J-221** · 📦 **npm against Maven** — ⭐⭐ 900 packages you did not choose

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: npm resolves dependencies by nesting rather than by picking one winner,
> so where Maven forces you to resolve a version conflict, npm silently installs five copies — which
> is why a React app has several hundred more transitive dependencies than an equivalent Spring app,
> from maintainers you will never recognise in an advisory.**
>
> Today: the lockfile, ⭐ the transitive explosion, ⭐⭐ the four attacks, and the rules.

---

# Part 1 — The files, and the command that matters

| npm | Maven equivalent | ⭐ What it is |
|---|---|---|
| `package.json` | `pom.xml` | Your **intent**. Ranges: `^18.2.0` = "18.x". |
| ⭐⭐ `package-lock.json` | ⭐ *(no true equivalent)* | **What you actually got** — exact versions + integrity hashes for the **whole tree**. **Commit it.** |
| `node_modules/` | `~/.m2/repository` | ⭐⭐ But **per-project**, not shared — hence the size |

```
⭐⭐ THE COMMANDS, AND THE ONE YOU WANT IN CI

⭐   npm install    ⇒ ⭐ MAY UPDATE THE LOCKFILE to satisfy ranges.
⭐                     Fine locally. ⭐⭐ WRONG IN CI — the build is
⭐                     no longer reproducible.
⭐   npm ci         ⇒ ⭐⭐ INSTALLS EXACTLY THE LOCKFILE. Fails if
⭐                     package.json and the lock disagree. ⭐ USE
⭐                     THIS IN CI, ALWAYS.

⭐   ⇒ ⭐⭐ MAVEN GIVES YOU REPRODUCIBILITY BY DEFAULT (fixed versions
⭐     in the pom). ⭐ NPM GIVES YOU RANGES BY DEFAULT AND MAKES
⭐     REPRODUCIBILITY OPT-IN. That inversion is the thing to know.
```

# Part 2 — ⭐⭐ Why there are 900 of them

```
⭐⭐ YOU ADD 12 PACKAGES. YOU GET ~900.
⭐   ⭐ Spring Boot web + JPA + security ⇒ ~200 jars, and you were
⭐     already uncomfortable about that.

⭐⭐ THE THREE STRUCTURAL REASONS IT IS WORSE:

⭐ ① ⭐⭐ NESTED RESOLUTION. Maven picks ONE version per artifact
⭐    (nearest-wins) and a genuine conflict is YOUR PROBLEM TO SOLVE.
⭐    ⭐ npm installs lodash@3 for one dep and lodash@4 for another,
⭐      IN SEPARATE FOLDERS, and never tells you.
⭐    ⇒ ⭐⭐ NO "DEPENDENCY HELL" — AND NO PRESSURE TO CONSOLIDATE.
⭐      The tree just grows.

⭐ ② ⭐ CULTURE OF TINY PACKAGES. is-odd, left-pad. A weak stdlib
⭐    that never caught up, so trivial things became dependencies.
⭐    ⭐ Java has a huge stdlib and Apache Commons; JS did not.

⭐ ③ ⭐ BUILD TOOLING IS ITSELF JAVASCRIPT. Your bundler, linter
⭐    and test runner are npm packages too — ⭐⭐ IMAGINE IF MAVEN
⭐      ITSELF WERE A TRANSITIVE DEPENDENCY IN YOUR POM.
```

| ⭐ Which of them can hurt you | |
|---|---|
| **`dependencies`** | ⭐⭐ Ship to users. An XSS or exfiltrator here reaches every visitor. |
| **`devDependencies`** | ⭐⭐ Do **not** ship — but they **run on your machine and in CI**, where your npm token, cloud creds and source live. ⭐ Same as a compromised Maven **plugin**, which also runs at build time. |
| **Transitive, either kind** | ⭐ You never chose them and will not recognise the name in an advisory |

# Part 3 — ⭐⭐ The four attacks

| Attack | ⭐ How it works | ⭐⭐ What stops it |
|---|---|---|
| **Typosquatting** | `reakt`, `lodahs`. ⭐ Also **AI-invented names** — a model hallucinates a plausible package, an attacker registers it | ⭐⭐ Read the name character by character. Check downloads and repo. |
| **Maintainer compromise** | A real, popular package ships a malicious version | ⭐⭐ **Delay adoption.** A malicious release is usually pulled within hours, so not auto-updating to brand-new versions is free protection. |
| **Install scripts** | ⭐⭐ `postinstall` runs **arbitrary code** on `npm install`, before any of your code | ⭐ `--ignore-scripts` where feasible. ⭐ Same class as a malicious Maven plugin in the build lifecycle. |
| **Dependency confusion** | An internal package name published publicly at a higher version | ⭐ Scope internal packages (`@yourco/x`), configure the registry per scope. ⭐⭐ Exactly the internal-Nexus-versus-Maven-Central problem. |

```
⭐⭐ THE CONTROLS THAT ACTUALLY WORK, IN ORDER OF VALUE

⭐   ① ⭐⭐ ADD FEWER PACKAGES. The only control with no ongoing cost.
⭐      "Can I write this in 20 lines?" — for a debounce, a class-name
⭐      joiner, a date format: yes, and you own it forever for free.
⭐   ② COMMIT THE LOCKFILE, BUILD WITH `npm ci`.
⭐   ③ npm audit --omit=dev in CI, ⭐ FAIL THE BUILD on high.
⭐      (⭐ your OWASP dependency-check equivalent)
⭐   ④ Dependabot/Renovate ⇒ ⭐ updates as REVIEWABLE PRs.
⭐   ⑤ ⭐⭐ CHECK EVERY PACKAGE AN AI SUGGESTS EXISTS AND IS THE
⭐      RIGHT ONE. Not theoretical.
```

> ⭐ **The honest limit of `npm audit`.** It reports *known* advisories, it is noisy with unreachable
> dev-only findings, and it says nothing about a package that is malicious today and undiscovered. **A
> floor, not a security programme** — same as any CVE scanner you already run.

# Part 4 — Reading a package before you add it

```
⭐⭐ THE 60-SECOND CHECK, before `npm i anything`

⭐   ① ⭐ WEEKLY DOWNLOADS — 40 is not the same risk as 4,000,000
⭐   ② ⭐⭐ LAST PUBLISH — unmaintained is a vulnerability with a delay
⭐   ③ ⭐ does the repo link actually resolve?
⭐   ④ ⭐⭐ ITS OWN DEPENDENCY COUNT — 0 deps is a different
⭐      proposition from one dragging in 40
⭐   ⑤ ⭐ BUNDLE SIZE — ⭐⭐ 300 KB FOR A DATE HELPER IS A
⭐      USER-VISIBLE COST. A 300 KB jar is not.
⭐   ⑥ ⭐⭐ LICENCE — AGPL in a commercial product is a real problem
```

| ⭐ Package | Ask first |
|---|---|
| `moment` (300 KB) | ⭐ `Intl.DateTimeFormat` is built in |
| `lodash` (whole) | ⭐ Import the one function, or write it |
| `axios` | ⭐⭐ `fetch` + your Day 217 wrapper is ~40 lines you already wrote |

> ⭐⭐ **`npm ls <pkg>` tells you *why* something is installed** — the chain that pulled it in. It is
> `mvn dependency:tree`, and it is the command that answers "is this advisory even reachable?"

## Today's build

1. `npm ci` a fresh React + TS + Vite app. ⭐ `npm ls --all | wc -l`. **Compare with `mvn dependency:tree | wc -l` on your Spring project.** Write both numbers down.
2. ⭐⭐ Run `npm audit`. Triage each finding: dev or prod? reachable? Do not blanket-fix.
3. Run the 60-second check on three dependencies. ⭐ Delete one you can write yourself.
4. ⭐⭐ **Write a `postinstall` that prints your env var names** in a throwaway local package. Install it. Watch it run before any of your code. Delete it — and remember it.
5. Add `npm ci` + `npm audit --omit=dev --audit-level=high` to CI. ⭐ Make it fail once, on purpose.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you manage frontend dependency risk?"**

Establish the scale by comparison, which is the fastest way to make the point to another JVM engineer.
**My Spring app has around two hundred jars and I was already uncomfortable with that. A normal React
app is around nine hundred packages. The structural reason is resolution: Maven picks one version per
artifact and a real conflict becomes my problem to solve, so there's constant pressure to consolidate.
npm nests — it installs two versions of the same library in separate folders and never mentions it. No
dependency hell, and no pressure to shrink the tree.**

Then the control that matters. **The highest-value control is adding fewer packages, because it's the
only one with no ongoing cost. Before adding anything I ask whether it's twenty lines I could own — I
dropped axios because fetch plus my own wrapper was forty lines I'd already written.**

Then the machinery, mapped to what you already do. **Lockfile committed, `npm ci` in CI so the build is
reproducible — Maven gives me that by default and npm makes it opt-in. Audit failing the build on high,
which is my dependency-check equivalent. Updates as reviewable PRs. And deliberately not jumping on
brand-new versions, because a compromised release is usually pulled within hours.**

Close on the two risks people underrate. **devDependencies never ship but they run in CI, where my
tokens and source are — that's a malicious Maven plugin, same class of problem. And every package an
agent suggests gets checked that it exists, because models invent plausible names and attackers
register them.**
