# Day 181

**L-181** · Resilience4j — circuit breakers, bulkheads, and the order they compose in

**Time:** 3 hrs · **Mode:** NEW

> Day 154 established the failure: no timeouts means one slow dependency parks every Tomcat thread and
> the whole service dies. Day 123 established retries with full jitter. Day 154 named the circuit

# Part 1 — The five patterns, and what each actually prevents

```xml
<dependency>
  <groupId>io.github.resilience4j</groupId>
  <artifactId>resilience4j-spring-boot3</artifactId>
</dependency>
```

| Pattern | Prevents |
|---|---|
| ⭐ **TimeLimiter** | ⭐ **unbounded waiting** — the Day 154 failure |
| ⭐ **CircuitBreaker** | ⭐ **hammering a dependency that is already failing** |
| **Bulkhead** | one dependency consuming all your concurrency |
| **Retry** | transient failures becoming user-visible errors |
| **RateLimiter** | ⭐ *you* overwhelming a downstream (the outbound twin of Day 122) |

**⭐ The ranking matters:** if you implement only one, implement the **timeout** — it is the one that
prevents total service death. The circuit breaker is second, because it prevents your recovery
attempts from prolonging someone else's outage.

# Part 2 — The circuit breaker, configured meaningfully

```yaml
resilience4j.circuitbreaker:
  instances:
    payments:
      sliding-window-type: COUNT_BASED
      sliding-window-size: 50                       # ⭐ last 50 calls
      minimum-number-of-calls: 20                   # ⭐⭐ don't judge on 2 calls
      failure-rate-threshold: 50                    # % failures to open
      slow-call-duration-threshold: 2s              # ⭐ slow counts as failed
      slow-call-rate-threshold: 80
      wait-duration-in-open-state: 30s
      permitted-number-of-calls-in-half-open-state: 5
      automatic-transition-from-open-to-half-open-enabled: true
      record-exceptions:
        - java.io.IOException
        - java.util.concurrent.TimeoutException
      ignore-exceptions:                            # ⭐⭐ THE most important setting
        - com.acme.InsufficientFundsException
```

```
        failure rate ≥ threshold
CLOSED ───────────────────────────► OPEN
  ▲                                  │  wait-duration elapses
  │  probes succeed                  ▼
  └────────────────────────── HALF_OPEN ──► OPEN (probes fail)
```

**⭐ `ignore-exceptions` is the setting people forget and it causes a genuine outage.** A business
rejection — insufficient funds, invalid card, product out of stock — is the dependency working
*correctly*. Counting those as failures means a marketing campaign that causes lots of declines
**opens the circuit and takes payments down for everyone.** The breaker must count only *infrastructure*
failures: timeouts, connection errors, 5xx.

**⭐ `minimum-number-of-calls` prevents the low-traffic false open.** Without it, two failures on a
quiet endpoint is a 100% failure rate and the circuit opens on almost no evidence.

**⭐ `slow-call-duration-threshold` is the underrated one.** A dependency returning 200s after 15
seconds is failing in every way that matters to your users, and without this the breaker never
notices because nothing threw.

## The fallback is where the design happens

```java
@Service
public class PaymentService {

    @CircuitBreaker(name = "payments", fallbackMethod = "paymentUnavailable")
    @Retry(name = "payments")                                  // ⭐ order matters — Part 4
    @TimeLimiter(name = "payments")
    public CompletableFuture<PaymentResult> charge(ChargeRequest req) { ... }

    // ⭐ signature must match + Throwable last
    private CompletableFuture<PaymentResult> paymentUnavailable(ChargeRequest req, Throwable t) {
        if (t instanceof CallNotPermittedException) {           // ⭐ circuit open, not a real failure
            metrics.counter("payments.circuit_open").increment();
        }
        log.warn("payments degraded, deferring charge", t);
        outbox.enqueueCharge(req);                              // ⭐⭐ Day 124 — the real design
        return completedFuture(PaymentResult.deferred());
    }
}
```

| Fallback | Verdict |
|---|---|
| ⭐ **Queue it and return "pending"** | **best.** The customer's order succeeds; the charge follows |
| Serve stale cached data | ⭐ excellent for reads (Day 121) |
| Degrade the feature | hide recommendations rather than fail the page |
| Return a clear error fast | ✅ acceptable — still better than hanging |
| ⭐ **Return a default that looks like success** | ❌ **dangerous** — "credit check passed" on failure |

**⭐ Distinguish `CallNotPermittedException` in the fallback.** It means the circuit is open — the
call was never attempted. Conflating it with a real failure makes your metrics lie about what your
dependency is doing.

# Part 3 — Bulkheads, and the isolation nobody configures

**Day 154's cascading failure again: 200 Tomcat threads, one slow dependency, everything dies.** A
timeout bounds each call; a **bulkhead bounds how many can be in flight at once**.

```yaml
resilience4j.bulkhead:
  instances:
    payments:      { max-concurrent-calls: 20, max-wait-duration: 100ms }
    recommendations: { max-concurrent-calls: 5 }        # ⭐ non-critical gets a small share
```

**⭐ The point: recommendations being slow must never be able to consume the threads that orders
need.** Without a bulkhead, your least important dependency can take down your most important
endpoint — and it will, because non-critical services get less operational attention.

| Type | Mechanism |
|---|---|
| `SemaphoreBulkhead` | ⭐ a permit count. Cheap, caller's thread |
| `ThreadPoolBulkhead` | ⭐ a **separate pool** — true isolation, but Day 177's context loss applies |

**And note the relationship to Day 156:** a bulkhead on a database-backed call is also protection for
the connection pool, since it caps how many of those calls can be holding connections.

# Part 4 — ⭐⭐ The composition order

**Spring's Resilience4j integration applies aspects in this order** (outermost first), and it is
configurable via `resilience4j.*.aspect-order`:

```
Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( yourMethod ) ) ) ) )
```

**Read it outside-in and the reasoning is clear:**

| Position | Why |
|---|---|
| ⭐ **Retry outermost** | so a retried attempt is a **fresh** circuit-breaker call, correctly counted |
| **CircuitBreaker next** | so it sees each attempt and can reject instantly once open |
| RateLimiter | throttle before doing work |
| TimeLimiter | bound each individual attempt |
| ⭐ **Bulkhead innermost** | a permit is held only for the actual call |

## ⭐ The wrong order, and what it does

**Retry *inside* the circuit breaker** means the breaker sees one call where three attempts happened.
Two consequences, both bad:

1. **The failure rate is understated** — three failures count as one — so the breaker opens far later
   than intended and you keep hammering a dying dependency.
2. **The breaker's timing is wrong.** One "call" now takes 3 × timeout + backoff, so
   `slow-call-duration-threshold` is measuring something else entirely.

**⭐ And the combination that must be checked in every configuration:**

> **Total worst case = attempts × per-attempt timeout + total backoff.**
> **This must fit inside your own SLA and inside your caller's timeout** (Day 154's budget rule).

Three attempts at 5 seconds with 2 seconds of backoff is **17 seconds** — for an endpoint that
promises 3. Your caller gave up 14 seconds ago; you are burning a thread on work nobody will read.
**Compute this number for every resilience configuration you write.** It is the most common mistake
on this page.

## Observability — otherwise none of this is operable

```yaml
management.endpoints.web.exposure.include: health,prometheus,circuitbreakers
management.health.circuitbreakers.enabled: true       # ⭐ but see the warning
```

```
resilience4j_circuitbreaker_state{name="payments",state="open"}
resilience4j_circuitbreaker_calls_seconds_count{name="payments",kind="failed"}
resilience4j_bulkhead_available_concurrent_calls{name="payments"}
```

**⭐ Alert on the state transition to open.** It is one of the highest-signal alerts you can have: it
means a dependency is failing *and* you are already degrading gracefully, so you have time to respond
rather than an outage.

⚠️ **Be careful with `management.health.circuitbreakers.enabled`.** If an open circuit makes your
health endpoint report DOWN and that feeds your **readiness** probe, then a payments outage removes
every pod from the load balancer — which is Day 128's exact outage. **A circuit breaker's whole
purpose is to let you keep serving; do not wire it to a probe that stops you serving.**

## Testing it

```java
@Test
void opensAfterFailures() {
    var cb = registry.circuitBreaker("payments");
    for (int i = 0; i < 20; i++) cb.onError(0, MILLISECONDS, new IOException());
    assertThat(cb.getState()).isEqualTo(State.OPEN);
    assertThatThrownBy(() -> service.charge(req)).isInstanceOf(CallNotPermittedException.class);
}

@Test
void businessRejectionDoesNotOpenTheCircuit() {          // ⭐ the test that matters
    for (int i = 0; i < 50; i++) simulate(new InsufficientFundsException());
    assertThat(registry.circuitBreaker("payments").getState()).isEqualTo(State.CLOSED);
}
```

**The second test is the one that catches the outage** described in Part 2. Write it.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ No timeout | Day 154 — everything dies |
| ⭐ Business exceptions counted as failures | declines open the circuit; payments down for everyone |
| No `minimum-number-of-calls` | two failures on a quiet endpoint opens it |
| No slow-call threshold | a dependency returning 200s in 15 s never trips it |
| ⭐ Retry inside the breaker | failure rate understated; breaker opens too late |
| ⭐ Attempts × timeout exceeding the SLA | you work on abandoned requests |
| Retrying non-idempotent operations | Day 123 — double charges |
| Fallback returning a plausible-looking success | "credit check passed" on failure |
| Not distinguishing `CallNotPermittedException` | metrics misreport the dependency |
| No bulkhead | a non-critical dependency starves a critical one |
| ⭐ Circuit-breaker health wired to readiness | Day 128's crash-loop outage |
| No alert on circuit open | the earliest signal, unused |
| Self-invocation | Day 137 — annotations do nothing |

## Interview questions

**Q: What do circuit breakers actually solve?**
Two things. They stop you sending load into a dependency that is already failing, which is what makes
retries dangerous on their own. And they fail fast, so your threads are not parked waiting on
something that will not answer — which is what turns a dependency outage into your outage.

**Q: In what order do these patterns compose, and why?**
Retry outermost, then circuit breaker, then rate limiter, time limiter, and bulkhead innermost. Retry
must be outside the breaker so each attempt is counted as its own call — inside, three failures look
like one, so the failure rate is understated and the breaker opens far too late.

**Q: What is the most commonly missed configuration?**
`ignore-exceptions`. A business rejection like insufficient funds is the dependency working correctly.
Counting those as failures means a spike in declines opens the circuit and takes payments down for
everyone.

**Q: What is the arithmetic you always check?**
Attempts multiplied by per-attempt timeout, plus total backoff. Three attempts at five seconds with
backoff is seventeen seconds, and if my endpoint promises three, my caller abandoned the request long
before I finish.

**Q: Should an open circuit make you unhealthy?**
No. If it feeds readiness, a dependency outage removes every pod from the load balancer — the exact
outage the breaker exists to prevent. Report it as a metric and alert on it, but keep serving.

## Mini task

1. Point a service at a dependency that sleeps 30 seconds. Set `server.tomcat.threads.max=10`. Fire
   20 requests and **watch every endpoint die.**
2. Add `@TimeLimiter`. Repeat. Note the containment.
3. Add the circuit breaker. Make the dependency fail. **Watch the state transitions in
   `/actuator/circuitbreakers` and the latency drop when it opens.**
4. Throw `InsufficientFundsException` 50 times. **Watch the circuit open.** Add `ignore-exceptions`
   and confirm it stays closed.
5. Set `minimum-number-of-calls: 1` and fail twice on a quiet endpoint. Observe.
6. Make the dependency return 200 after 10 seconds. Confirm the breaker never opens. Add the
   slow-call threshold.
7. **Compute your worst case**: 3 attempts × 5 s + backoff. Then set the caller's timeout to 3 s and
   observe both sides.
8. Reverse the aspect order so retry is inside. Fail consistently and **compare how long the breaker
   takes to open.**
9. Add bulkheads. Saturate recommendations and confirm orders still work.
10. Wire circuit-breaker health into readiness, open the circuit, and **watch Kubernetes remove every
    pod.** Undo it.

## 🎙️ Articulation drill

Two minutes: **"How do you make a service resilient to a failing dependency?"**

Timeouts first, and say why they rank first — without them one slow dependency parks every thread and
the whole service dies. Then a circuit breaker to stop your retries prolonging someone else's
outage, with `ignore-exceptions` called out, because counting business rejections as failures means a
spike in declines takes payments down. Bulkheads so a non-critical dependency cannot starve a
critical one. Then two things that show operational experience: the composition order, with retry
outside the breaker so attempts are counted individually — and the arithmetic, because three attempts
at five seconds does not fit a three-second promise.
