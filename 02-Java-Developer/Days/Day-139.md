# Day 139

**L-139** · Spring Boot starters and opinionated defaults

**Time:** 3 hrs · **Mode:** NEW

> The Boot block opens. Days 130–138 were the Spring **Framework** — the container. Boot is a layer
> on top whose entire contribution is **making decisions for you**, and today is about what those
> decisions are and how to find out.
>
> The framing that matters: **a framework that guesses is only safe if you can audit its guesses.**

# Part 1 — What Boot actually changed

Spring in 2013 was capable and laborious:

```xml
<!-- a dozen dependencies whose versions must be mutually compatible -->
<dependency>spring-webmvc 4.3.30</dependency>
<dependency>jackson-databind 2.9.10</dependency>
<dependency>hibernate-validator 5.4.3</dependency>
…
```

```xml
<!-- web.xml, a DispatcherServlet, a view resolver, a message converter, an external Tomcat… -->
```

```
Result: 200+ lines of XML and a WAR deployed into a servlet container you installed separately.
```

```gradle
// Boot, 2014 onward
implementation("org.springframework.boot:spring-boot-starter-web")
```

```java
@SpringBootApplication
public class App { public static void main(String[] a) { SpringApplication.run(App.class, a); } }
```

**Four things changed**, and it is worth separating them because people attribute all of it to
"auto-configuration":

| Contribution | What it solves |
|---|---|
| **Starters** | Dependency selection and version compatibility |
| **Dependency management (BOM)** | Version conflicts across 200+ libraries (Day 073) |
| **Auto-configuration** | Boilerplate bean definitions (Day 140) |
| **Embedded server** | Deployment — a jar, not a WAR |

## The embedded server is the underrated one

```
Before:  build a WAR → install Tomcat → configure it → deploy the WAR → hope the versions match
After:   java -jar app.jar
```

**The application owns its server**, so the server version is in your `pom.xml`, tested with your
code, and identical in development and production. That is what makes the container image
self-contained (Day 129B) and it is why "works on my machine" largely stopped being about the
servlet container.

# Part 2 — Starters

**A starter is a dependency that contains no code** — it is a curated, version-compatible list of
other dependencies.

```gradle
implementation("org.springframework.boot:spring-boot-starter-web")
```

pulls in:

```
spring-boot-starter          core, auto-configuration, logging
  ├── spring-boot-starter-logging  → Logback + SLF4J     (Day 073A)
  └── spring-core, spring-context, snakeyaml
spring-web, spring-webmvc
spring-boot-starter-json     → Jackson + JavaTimeModule  (Day 106)
spring-boot-starter-tomcat   → embedded Tomcat
spring-boot-starter-validation? — ⚠️ NOT included since Boot 2.3; add it explicitly
```

**Run `mvn dependency:tree` on a starter** (Day 073) — one line becomes about forty jars, and knowing
that is Day 100A's point: **you are responsible for every one of them.**

## The starters you will use

| Starter | Brings |
|---|---|
| `-web` | Spring MVC, embedded Tomcat, Jackson |
| `-webflux` | Reactive stack, Netty — ⚠️ **not** alongside `-web` |
| `-data-jpa` | Hibernate, Spring Data JPA, HikariCP |
| `-data-redis` | Lettuce, Spring Data Redis (Days 120–121) |
| `-security` | Spring Security's filter chain (Days 169+) |
| `-validation` | Hibernate Validator — ⭐ **must be added explicitly** |
| `-actuator` | Health, metrics, info (Day 128) |
| `-test` | JUnit 5, Mockito, AssertJ, Testcontainers support |
| `-oauth2-resource-server` | JWT validation (Day 114) |
| `-amqp` / `-kafka` | RabbitMQ / Kafka (Day 125) |

**⚠️ `-web` and `-webflux` together** silently gives you the servlet stack — Boot backs off WebFlux
when a servlet stack is present. This produces genuinely confusing behaviour: your reactive code
compiles and runs on a blocking stack.

## Writing your own starter

Worth knowing because it demystifies the mechanism — a starter is just a module with a
`spring.factories`-equivalent registration:

```
acme-notifications-spring-boot-starter/     ← naming convention: NOT "spring-boot-starter-*"
  src/main/java/  AcmeNotificationsAutoConfiguration.java
  src/main/resources/META-INF/spring/
      org.springframework.boot.autoconfigure.AutoConfiguration.imports    ⭐ Boot 3
```

```java
@AutoConfiguration
@ConditionalOnClass(NotificationSender.class)
@ConditionalOnProperty(prefix = "acme.notifications", name = "enabled", matchIfMissing = true)
@EnableConfigurationProperties(NotificationProperties.class)
public class AcmeNotificationsAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                       // ⭐ back off if the user defined one
    NotificationSender notificationSender(NotificationProperties props) {
        return new DefaultNotificationSender(props);
    }
}
```

**`spring-boot-starter-*` is reserved for official starters**; third-party ones use
`*-spring-boot-starter`. That convention exists so you can tell at a glance who maintains a
dependency.

# Part 3 — ⭐ The opinions

**Boot's real contribution is a set of defaults.** Some are excellent; several are wrong for
production and must be changed deliberately.

## Defaults that are right

```
Embedded Tomcat on 8080
Logback with a sensible console pattern            (Day 073A)
Jackson with JavaTimeModule registered             (Day 106)
HikariCP as the connection pool
UTF-8 everywhere
Graceful class-loading and a fat jar
Actuator health endpoint                            (Day 128)
```

## ⚠️ Defaults you must change

**This table is the most valuable part of the day.**

| Default | Problem | Set |
|---|---|---|
| `spring.jpa.open-in-view=true` | ⭐ **Holds a DB connection for the whole request** | `false` (Day 160) |
| `server.shutdown=immediate` | Drops in-flight requests on every deploy | `graceful` (Day 133) |
| `spring.jpa.hibernate.ddl-auto` (dev default `create-drop`) | Schema managed by Hibernate | `validate` + Flyway (Day 166) |
| `management.endpoints.web.exposure.include=health,info` | Fine — but people set `*` | Never `*` (Day 138) |
| No connection-pool sizing | Defaults to 10, unrelated to your load | Size it (Day 069) |
| `spring.jackson.default-property-inclusion` | Nulls serialized | `non_null` (Day 106) |
| No request timeouts on `RestTemplate`/`WebClient` | ⭐ **Hangs forever; thread-pool exhaustion** | Always set them (Day 123) |
| `logging.pattern` is human-readable | Not queryable | JSON encoder (Day 127) |
| Tomcat `max-threads=200` | May be far too many or too few | Size against your workload |

**⭐ `open-in-view` deserves its own paragraph**, because it is the most consequential wrong default
in Spring Boot. It keeps the Hibernate session — and therefore a database connection — open for the
entire HTTP request, including view rendering and JSON serialization. Consequences: connections held
far longer than needed, pool exhaustion under load, and lazy loading silently firing queries during
serialization (Day 160's N+1). It exists to make `LazyInitializationException` go away, which is
solving a symptom by hiding it.

```properties
spring.jpa.open-in-view=false      # ⭐ set this in every project, on day one
```

Boot even logs a warning about it at startup, which almost everyone ignores.

**The `RestTemplate` timeout default is the other one to internalise**: no timeout means a slow
dependency holds your request threads indefinitely, which is Day 069's cascading failure and Day
123's timeout rule.

## The principle behind the opinions

> **Boot's defaults optimise for "getting started quickly", not for "running in production".**

That is not a criticism — it is the correct trade for a framework whose adoption depends on the first
five minutes. But it means **every Boot application needs a deliberate review of the defaults**, and
the table above is that review's starting point.

# Part 4 — Auditing what you got

```bash
java -jar app.jar --debug              # ⭐ the conditions evaluation report (Days 130, 135)
```

```
Positive matches:
   DataSourceAutoConfiguration matched:
      - @ConditionalOnClass found 'javax.sql.DataSource'
   JacksonAutoConfiguration#jacksonObjectMapper matched:
      - @ConditionalOnMissingBean (types: ObjectMapper) did not find any beans
```

**That last line is the pattern to recognise**: Boot gave you an `ObjectMapper` *because you did not
define one*. Define your own and it backs off — `@ConditionalOnMissingBean` (Day 135) is the
mechanism behind every override in Spring Boot.

```java
// Override any Boot default simply by declaring the bean
@Bean
ObjectMapper objectMapper() {                                    // Day 106
    return JsonMapper.builder()
            .addModule(new JavaTimeModule())
            .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
            .serializationInclusion(NON_NULL)
            .build();
}
```

⚠️ **But prefer customisation to replacement.** Replacing the `ObjectMapper` wholesale discards
everything Boot configured for you — module discovery, Boot's property bindings, and modules
contributed by other starters:

```java
@Bean
Jackson2ObjectMapperBuilderCustomizer jacksonCustomizer() {       // ⭐ customise, do not replace
    return builder -> builder.serializationInclusion(NON_NULL)
                             .featuresToDisable(WRITE_DATES_AS_TIMESTAMPS);
}
```

**That `*Customizer` pattern recurs throughout Boot** — `WebMvcConfigurer`,
`RestTemplateCustomizer`, `TomcatConnectorCustomizer`. **Reach for the customiser before the
replacement**; it is the difference between adjusting a decision and discarding a hundred of them.

```bash
# see every property Boot bound, and from where
curl localhost:8080/actuator/configprops
curl localhost:8080/actuator/beans           # ⚠️ never public (Day 119)
```

# Part 5 — Costs

Day 130 listed Spring's costs generally. Boot's specific ones:

| Cost | Detail |
|---|---|
| **Startup time** | Classpath scanning plus ~150 auto-configuration classes evaluated |
| **Dependency weight** | One starter is ~40 jars — all of them your responsibility (Day 100A) |
| **Hidden behaviour** | Beans you did not declare, doing things you did not ask for |
| **Opinions that are wrong for you** | The table above |
| **Version coupling** | Boot's BOM pins ~200 libraries; overriding one can break others |

**On that last point:** the BOM is Boot's largest practical benefit *and* a constraint. Overriding a
managed version (`<jackson.version>`) is sometimes necessary — for a CVE, say (Day 100A) — and it
takes you outside the tested matrix. Do it deliberately and test.

**Startup time matters in specific contexts:** serverless (per-invocation cold starts), Kubernetes
scale-to-zero, and CI where hundreds of context starts add up. The mitigations are lazy
initialisation (`spring.main.lazy-initialization=true` — ⚠️ which trades away Day 132's fail-fast
startup), narrower component scanning (Day 135), and Boot 3's AOT and GraalVM native images (Day
185B).

> **Boot is the right default for most JVM backend work.** Where startup time or memory is the
> binding constraint, Quarkus and Micronaut do this work at compile time — and knowing why is more
> useful than knowing that.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Leaving `open-in-view=true` | ⭐ Connections held per request; hidden N+1 during serialization |
| No `server.shutdown=graceful` | Requests dropped on every deploy |
| `ddl-auto` other than `validate` in production | Hibernate managing your schema |
| No timeouts on HTTP clients | Thread-pool exhaustion from a slow dependency |
| `management.endpoints.web.exposure.include=*` | Configuration and internals exposed |
| `-web` and `-webflux` together | Reactive code silently running on a servlet stack |
| Assuming `-web` includes validation | It has not since Boot 2.3 |
| Replacing a Boot bean instead of customising | Discards everything else Boot configured |
| Not reading `--debug` | Auto-configuration stays mysterious |
| Overriding a BOM version casually | Outside the tested compatibility matrix |
| `lazy-initialization=true` for startup speed | Trades away fail-fast startup |

## Interview questions

**Q: What does Spring Boot add to Spring?**
Starters for curated, version-compatible dependencies; a BOM managing about 200 library versions;
auto-configuration that defines beans based on the classpath and your properties; and an embedded
server so the artifact is a runnable jar rather than a WAR.

**Q: What is a starter?**
A dependency containing no code — a curated list of other dependencies with compatible versions. One
line typically resolves to about forty jars.

**Q: Which Boot defaults would you change in production?**
`open-in-view=false` first, because it holds a database connection for the whole request and hides
N+1 queries during serialization. Then `server.shutdown=graceful`, `ddl-auto=validate` with Flyway,
explicit HTTP client timeouts, connection-pool sizing, and JSON logging.

**Q: What is `open-in-view` and why is it a problem?**
It keeps the Hibernate session open for the entire request so lazy loading works during view
rendering and serialization. That holds a connection far longer than needed, exhausts the pool under
load, and lets N+1 queries fire during JSON serialization where nobody sees them.

**Q: How do you override a Boot default?**
Define the bean yourself — auto-configuration uses `@ConditionalOnMissingBean` and backs off. But
prefer a `*Customizer` where one exists, because replacing a bean discards everything else Boot
configured on it, including contributions from other starters.

**Q: How do you find out what Boot configured?**
Run with `--debug` for the conditions evaluation report, which lists every positive and negative
match with the condition that decided it. `/actuator/configprops` and `/actuator/beans` show the
resolved result — neither should be publicly exposed.

**Q: What are Boot's costs?**
Startup time from scanning and condition evaluation, a large transitive dependency surface you are
responsible for, behaviour you did not declare, and opinionated defaults that are tuned for getting
started rather than for production.

## Mini task

1. Create a project with only `spring-boot-starter-web` and run `mvn dependency:tree`. Count the
   jars.
2. Run `--debug` and read the whole conditions report. Pick five positive matches and explain the
   condition that triggered each.
3. Find three negative matches and identify the missing class or property for each.
4. Go through the "defaults you must change" table against a real project. Fix every row and record
   what changed.
5. Turn on `open-in-view` and add an endpoint returning an entity with a lazy collection. Watch the
   queries fire during serialization with `spring.jpa.show-sql=true`. Turn it off and observe the
   `LazyInitializationException` — then fix it properly with a fetch join (Day 161).
6. Replace the `ObjectMapper` wholesale and confirm what you lost. Redo it with
   `Jackson2ObjectMapperBuilderCustomizer` and compare.
7. Add `-web` and `-webflux` together and determine which stack actually started.
8. Add validation annotations without `spring-boot-starter-validation` and confirm nothing is
   validated. Add the starter and confirm it works.
9. Measure startup time with and without `lazy-initialization=true`, then find a wiring error that
   the lazy version fails to catch at startup.
10. Write a minimal custom starter with an `@AutoConfiguration` class and `@ConditionalOnMissingBean`.
    Consume it from another project and confirm your override backs it off.

## 🎙️ Articulation drill

Two minutes: **"What does Spring Boot give you, and what would you change about its defaults?"**

Starters, the BOM, auto-configuration, and the embedded server — then immediately the second half,
because that is what shows production experience: `open-in-view=false`, graceful shutdown,
`ddl-auto=validate`, explicit client timeouts, pool sizing, JSON logging. Close with the framing —
Boot's defaults optimise for the first five minutes, not for production, so every application needs
a deliberate pass over them.
