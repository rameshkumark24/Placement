# Day 302

**L-302** · The service layer — application logic vs domain logic

**Time:** 3 hrs · **Mode:** NEW

> **⭐ "Service" is the most overloaded word in Java. It names three different things, and conflating
> them is what produces the 2,400-line `OrderService`.**
>
> Today separates them with one test you can apply to any method in under five seconds — and then
> uses that test to decide where transactions, validation and orchestration belong.

---

# Part 1 — ⭐⭐ The three services

| | ⭐ Application service | ⭐ Domain service | Infrastructure service |
|---|---|---|---|
| **Answers** | ⭐ "what happens in this use case?" | ⭐ "what is the rule?" | "how do we talk to X?" |
| Knows about | transactions, ports, security | ⭐ **only the domain** | HTTP, SQL, SMTP |
| ⭐ **Contains business rules?** | ⭐ **NO** | ⭐ **YES** | no |
| Depends on | ports, domain | ⭐ **nothing but domain** | libraries |
| Lives in | `application/` | ⭐ **`domain/`** | `adapter/out/` |
| Example | `PlaceOrderService` | `PricingPolicy`, `TransferService` | `StripePayments` |

```java
// ⭐ APPLICATION SERVICE — orchestration only. Read it: it has no opinions.
@Service
class ShipOrderService implements ShipOrder {

    @Transactional                                    // ⭐ the boundary lives here (Day 164)
    public void handle(ShipOrderCommand cmd) {
        Order order = orders.byId(cmd.orderId())      // ⭐ 1. load
                            .orElseThrow(OrderNotFound::new);
        order.ship(clock.instant());                  // ⭐ 2. DELEGATE — the rule is inside
        orders.save(order);                           // ⭐ 3. persist
        events.publish(new OrderShipped(order.id())); // ⭐ 4. notify
    }
}
```

> **⭐ The shape of every application service is the same four steps: load, delegate, persist,
> notify.** When one starts containing `if`s about the business, a rule has escaped its object.

## ⭐ The five-second test

> **⭐ Can you state this rule without mentioning a database, an HTTP request, a queue, a framework,
> or another use case?**
>
> **⭐ Yes → domain logic. No → application logic.**

| Statement | ⭐ Verdict |
|---|---|
| "An order can only ship if it is paid" | ⭐ **domain** |
| "Shipping an order requires the SHIPPER role" | ⭐ application — it is about *who is calling* |
| "Orders over £10,000 need approval" | ⭐ **domain** |
| "Load the order, ship it, publish an event" | ⭐ application |
| "The whole thing is one transaction" | ⭐ application |
| "A discount is 10% for gold customers" | ⭐ **domain** |
| "Send a confirmation email after shipping" | ⭐ application (usually via an event — Day 179) |

## ⭐ When a domain *service* is the right answer

**⭐ Most rules belong on an entity or value object. A domain service is for the rule that belongs to
no single object** — and the canonical example is genuinely canonical:

```java
// ⭐ Which account owns "transfer"? Neither. It is a rule ABOUT the pair.
public final class TransferService {
    public void transfer(Account from, Account to, Money amount) {
        from.withdraw(amount);        // ⭐ each object still protects its own invariant
        to.deposit(amount);
    }
}
```

| ⭐ Use a domain service when | ⭐ Do NOT when |
|---|---|
| the rule spans **two aggregates** | ⭐ it fits on one entity — put it there |
| it is a **policy that varies** (pricing, risk scoring) | ⭐ **you just want somewhere to put code** |
| it is a **calculation with no natural owner** | it needs a repository — that is application logic |

⚠️ **A domain service that takes a repository is an application service wearing the wrong label.**
The domain layer does not load things; it operates on things it was given. **Day 290's rules engine
is the model to copy: inputs in, decision out, nothing fetched.**

# Part 2 — ⭐ The 2,400-line service, and how it got there

```java
@Service
public class OrderService {         // ⭐ 47 methods, 14 dependencies
    // create, update, cancel, ship, refund, export, notify, recalculate,
    // syncToWarehouse, generateInvoice, applyPromotion, mergeGuestCart...
}
```

**⭐ Three forces produce it, and naming them is how you resist:**

1. ⭐ **The class is named after a noun, so anything about that noun goes in.** A file named
   `OrderService` has infinite capacity by construction.
2. ⭐ **Fourteen dependencies is a hint nobody reads.** A constructor with fourteen parameters is a
   cohesion failure the compiler is showing you (Day 298: coincidental cohesion).
3. **Every new use case is one more method, and each is individually reasonable.**

## ⭐ The fix — one class per use case

```
application/
├── PlaceOrderService.java      ⭐ 3 dependencies
├── ShipOrderService.java       ⭐ 2 dependencies
├── CancelOrderService.java     ⭐ 3 dependencies
└── RefundOrderService.java     ⭐ 4 dependencies
```

| Gains | ⭐ Detail |
|---|---|
| ⭐ **Dependencies are honest** | ⭐ each class declares only what its use case needs |
| ⭐ **Names are verbs** | ⭐ a class called `ShipOrderService` **cannot** absorb refund logic |
| Tests are focused | ⭐ no 400-line test class with fourteen mocks |
| ⭐ **Merge conflicts drop** | two people on two use cases touch two files |
| ⭐ **Security is per use case** | `@PreAuthorize` on the class, not scattered per method (Day 174) |

**⭐ The objection — "that's a lot of classes" — is real and answerable:** it is the same amount of
code in files that can be found by name, with the dependency list of each use case visible in its
constructor. **The 47-method class had the same complexity; it was just hidden.**

⚠️ **Do not do this to a CRUD module.** Four one-line classes to wrap four repository calls is
Day 299's sinkhole. **Split when a service exceeds roughly seven or eight dependencies, or when two
use cases in it have nothing in common.**

# Part 3 — ⭐ Where the responsibilities actually go

## ⭐ Validation — the three-layer split (Day 148, sharpened)

| Layer | Validates | Failure |
|---|---|---|
| ⭐ **Edge (DTO, `@Valid`)** | ⭐ shape — is it a well-formed request? | ⭐ 400 |
| ⭐ **Domain (constructor/VO)** | ⭐ **invariants — is this object legal at all?** | ⭐ exception — should be impossible |
| ⭐ **Application** | context — does the caller have permission, does the referenced thing exist? | ⭐ 403 / 404 / 409 |

> **⭐ The rule: if an invalid value could only arrive through a bug, it belongs in the domain and
> throws. If it could arrive from a user, it belongs at the edge and returns a message.** Day 304
> makes the domain half unbypassable by validating in constructors.

## ⭐ The transaction boundary

**⭐ One use case = one transaction = one application service method = ideally one aggregate changed**
(Day 305's rule).

| Rule | Why |
|---|---|
| ⭐ `@Transactional` on the application service **only** | ⭐ not controllers (too wide), not the domain (it does not know) |
| ⭐ **Never over an HTTP call** | Day 154 — a slow vendor holds a database connection (Day 156) |
| ⭐ **Never over a long computation** | Day 194's vacuum problem, Day 196's lock queue |
| ⭐ **Read-only for queries** | `readOnly = true` — Hibernate skips dirty checking |
| ⭐ Publish events **inside**, deliver **after commit** | Day 179; Day 263's outbox for anything that must not be lost |

**⭐ The single most common bug in this layer:**

```java
@Transactional
public void place(Command cmd) {
    orders.save(order);
    paymentGateway.charge(order);   // ⭐ 30s timeout inside a transaction.
}                                   // ⭐ The pool dies before the payment does (Day 156).
```

## ⭐ Commands, and why they beat parameter lists

```java
public record ShipOrderCommand(OrderId orderId, Instant requestedAt, UserId requestedBy) {}
```

| Benefit | ⭐ Detail |
|---|---|
| ⭐ **Kills connascence of position** | Day 298 — `ship(a, b, c, d)` with two `String`s adjacent |
| Adding a field does not change the signature | callers untouched |
| ⭐ **The use case's input is a named, documented type** | it can be logged, validated, replayed |
| ⭐ Maps to an audit log for free | Day 165's auditing |

**⭐ And they are not DTOs.** The DTO is the wire format (Day 147); the command is the application's
input. The controller maps one to the other, **which is exactly where the mass-assignment defence of
Day 105 lives.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Business `if`s in the application service | ⭐ **the rule is bypassable — Day 299's Rot 2** |
| ⭐ A domain service that injects a repository | ⭐ it is an application service; the domain now needs infrastructure to test |
| ⭐ One noun-named service per entity | ⭐ unbounded growth; fourteen dependencies |
| `@Transactional` on the controller | the boundary includes serialization and view rendering |
| ⭐ **An HTTP call inside a transaction** | ⭐ **the connection pool dies before the vendor does** |
| Missing `readOnly = true` on queries | needless dirty checking on every managed entity |
| ⭐ Passing DTOs into the application layer | the wire format reaches the domain |
| Long parameter lists | connascence of position; a silent bug when two `String`s swap |
| ⭐ Splitting a CRUD service into use cases | ceremony with no rules to protect |

## Interview questions

**Q: What is the difference between application logic and domain logic?**
Domain logic is a rule you can state without mentioning a database, an HTTP request or a framework —
"an unpaid order cannot ship". Application logic is orchestration: load, delegate, persist, notify,
plus transactions and authorization. The test matters because anything that fails it and still sits
in a service is a rule the next caller can bypass.

**Q: When do you use a domain service instead of a method on an entity?**
When the rule genuinely belongs to no single object — a transfer between two accounts, a pricing
policy across a cart and a customer. If it fits on one entity it goes there. And a domain service
must not take a repository; the moment it loads things it is an application service, and the domain
can no longer be tested without infrastructure.

**Q: How do you stop a service class from growing to 2,000 lines?**
One class per use case, named with a verb. A class called `ShipOrderService` cannot absorb refund
logic, whereas `OrderService` absorbs everything by construction. It also makes each use case's
dependency list honest — a fourteen-parameter constructor is a cohesion failure the compiler was
showing us all along. I would not do it to a CRUD module, where it is pure ceremony.

**Q: Where does the transaction boundary go, and what must stay outside it?**
On the application service, one per use case. Outside it: HTTP calls to third parties, long
computations, and anything waiting on a human — all three hold a pooled database connection while
doing no database work, which takes down the pool before the slow thing fails. Events are published
inside and delivered after commit, or through an outbox if they must not be lost.

**Q: Why commands rather than parameters?**
A named record removes connascence of position — with four parameters and two of them strings, a
swapped pair compiles and runs wrong. It also lets input be logged, validated and audited as one
thing, and it keeps DTOs out of the application layer, which is where mass-assignment defence
belongs.

## Mini task

1. **Open your largest service. Count methods and dependencies.** Split it into one class per use
   case and record both numbers before and after.
2. **Run the five-second test on every method.** Make a two-column list. **Move every domain-logic
   line into the entity or a domain service.**
3. Find one rule that exists in **two** services and unify it. Note how it got duplicated.
4. **Search for any HTTP or queue call inside a `@Transactional` method.** Move it out, after commit.
5. Add `readOnly = true` to every query method and measure one heavy read before and after.
6. Convert one use case to a **command record**. Log the command. **Notice you now have an audit
   trail you did not write.**
7. ⭐ **Find one domain service that takes a repository.** Rewrite it to take the loaded objects
   instead, and see the test lose its Spring context.

## 🎙️ Articulation drill

**Two minutes:** *"How do you decide what goes in the service layer and what goes in the model?"*

**⭐ The marker: you give the five-second test as a test, then immediately give the consequence** —
that a rule left in a service is bypassable by the next caller, so this is a correctness question
rather than a taste question. **Then name the one case where you deliberately keep it procedural:
CRUD with no invariants.** Knowing when the answer is "put it in the service and move on" is what
makes the rest credible.
