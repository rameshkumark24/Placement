# Part 1 — The `ObjectMapper` configuration that prevents Day 106's failures

Boot builds one `ObjectMapper` and reuses it everywhere. **Configure it with
`Jackson2ObjectMapperBuilderCustomizer`, not by defining your own `@Bean ObjectMapper`** — replacing
the bean discards every Boot default and every module other starters registered, and the symptoms
(dates suddenly serializing as arrays, `Optional` breaking) appear far from the change.

```java
@Configuration
class JacksonConfig {
    @Bean
    Jackson2ObjectMapperBuilderCustomizer customizer() {
        return b -> b
            .featuresToDisable(
                SerializationFeature.WRITE_DATES_AS_TIMESTAMPS,      // ⭐ 1
                DeserializationFeature.ADJUST_DATES_TO_CONTEXT_TIME_ZONE)
            .featuresToEnable(
                DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES,   // ⭐ 2 — see the caveat
                DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES,  // ⭐ 3
                SerializationFeature.WRITE_BIGDECIMAL_AS_PLAIN)      // ⭐ 4
            .serializationInclusion(JsonInclude.Include.NON_NULL)    // ⭐ 5 — see the caveat
            .timeZone(TimeZone.getTimeZone("UTC"));
    }
}
```

Or, equivalently and more readably for most of them:

```yaml
spring.jackson:
  serialization:
    write-dates-as-timestamps: false
    write-bigdecimal-as-plain: true
  deserialization:
    fail-on-unknown-properties: true
    fail-on-null-for-primitives: true
  default-property-inclusion: non_null
  time-zone: UTC
```

### ⭐ 1 — Dates (Day 106, item one)

Off: `1723632225.123`. On: `"2026-08-14T10:23:45.123Z"`. **Always the ISO string.** A timestamp
number is ambiguous about precision (seconds or millis?), unreadable in a log, and a nightmare in
JavaScript. Boot 3 registers `JavaTimeModule` automatically, so `Instant`, `LocalDate` and
`OffsetDateTime` all work — the only thing you must do is turn off the timestamp form.

**And the rule Day 106 gave:** `Instant` or `OffsetDateTime` on the wire, never `LocalDateTime`. A
`LocalDateTime` has no zone, so it means something different to the sender and the receiver, and the
bug appears only for users in another zone or twice a year at the DST boundary.

### ⭐ 2 — Unknown properties

Default is **ignore**. Enabling `FAIL_ON_UNKNOWN_PROPERTIES` turns a client's typo — `{"quantitiy":5}`
— into a 400 instead of a silent zero-quantity order.

**The caveat is real, so know both sides.** Strict parsing is right for a request body: a typo should
be loud. It is *wrong* for consuming a third party's response, where they may add fields at any time
and Day 109's tolerant-reader principle says a new field must not break you. **Strict inbound at your
own boundary, lenient when you are the client** — configure the client's mapper separately (Day 154).

### ⭐ 3 — Null into a primitive

`{"quantity":null}` into `int quantity` silently becomes **0** by default. An order for zero items
gets created. `FAIL_ON_NULL_FOR_PRIMITIVES` makes it a 400. This is Day 034's boxing trap arriving
through JSON, and it is the least-known of the four.

### ⭐ 4 — Money (Day 106, item two)

**`BigDecimal`, never `double`.** `0.1 + 0.2 != 0.3` does not stop being true because the number came
from JSON. `WRITE_BIGDECIMAL_AS_PLAIN` prevents `1E+2` appearing on the wire for a value of 100 —
which is valid JSON, and which some clients parse wrong.

**The stricter option some teams take:** serialize money as a string, `"total": "129.99"`, because
JSON numbers are IEEE-754 doubles in JavaScript and a large decimal loses precision the moment
`JSON.parse` touches it. Defensible; document it either way.

### ⭐ 5 — Nulls (Day 106, item four)

`NON_NULL` gives smaller payloads and no `"middleName": null` noise. **But it removes the client's
ability to distinguish "absent" from "explicitly null"**, which matters for PATCH semantics. Two
consequences worth stating:

- On a **response**, omitting nulls is usually fine.
- On a **PATCH request**, you need the distinction — `JsonNullable` (from `openapi-jackson-databind-nullable`)
  or an explicit `Optional<Optional<T>>` shape. Otherwise "clear my middle name" and "do not touch
  my middle name" are the same request.

### And item three from Day 106 — large integers

A Java `long` above 2^53 loses precision in JavaScript. If your IDs are `long` (a Snowflake ID, for
instance), serialize them as strings:

```java
@JsonSerialize(using = ToStringSerializer.class) long id;
```

Or use `UUID`/`String` ids and the problem never exists — which is why Day 147's DTOs use `UUID`.

# Part 2 — Per-field and per-type control

| Annotation | Use |
|---|---|
| `@JsonProperty("order_id")` | rename. ⭐ Better: set a global `PropertyNamingStrategies.SNAKE_CASE` once than annotate every field |
| `@JsonIgnore` | omit. Deny-list — Day 147's warning stands |
| `@JsonProperty(access = READ_ONLY)` | serialize, never deserialize |
| `@JsonInclude(NON_NULL)` | per-class override of the global setting |
| `@JsonFormat(pattern = "yyyy-MM-dd")` | ⭐ per-field date shape. Needed on `LocalDate` when the global default is not what one field wants |
| `@JsonSerialize/@JsonDeserialize(using=…)` | a custom type |
| `@JsonAnyGetter` | a dynamic map of extras |
| `@JsonView` | conditional views. Day 147 prefers separate DTOs |
| `@JsonUnwrapped` | flatten a value object into the parent |

## A custom serializer, for a type you own

```java
public record Money(BigDecimal amount, Currency currency) {}

class MoneySerializer extends JsonSerializer<Money> {
    @Override public void serialize(Money m, JsonGenerator g, SerializerProvider p) throws IOException {
        g.writeStartObject();
        g.writeStringField("amount", m.amount().setScale(2, RoundingMode.HALF_UP).toPlainString());
        g.writeStringField("currency", m.currency().getCurrencyCode());
        g.writeEndObject();
    }
}

@Bean Module moneyModule() {
    return new SimpleModule().addSerializer(Money.class, new MoneySerializer());
}
```

**Registering a `Module` bean is the correct extension point** — Boot picks up every `Module` bean
automatically and adds it to the one mapper, so this composes with everything else instead of
replacing it.

## The record + Jackson facts

- **Records need `-parameters`** to deserialize by constructor without `@JsonProperty` on each
  component. Boot's Maven plugin sets it; a custom build may not (Day 145's same footnote).
- **Validation and defaults belong in the compact constructor**, which Jackson does invoke, so
  invariants hold for deserialized instances too.
- **A single-component record** may serialize as a bare value rather than an object depending on
  configuration — a genuine surprise. `@JsonCreator(mode = PROPERTIES)` pins it.

# Part 3 — `ResponseEntity`, and the headers that are the actual feature

Day 146 covered when to use it. Here is what it is *for*.

```java
@GetMapping("/{id}")
ResponseEntity<OrderResponse> get(@PathVariable UUID id, @RequestHeader(name = IF_NONE_MATCH,
                                                                       required = false) String inm) {
    Order o = orders.get(id);
    String etag = "\"" + o.version() + "\"";

    if (etag.equals(inm)) {
        return ResponseEntity.status(NOT_MODIFIED).eTag(etag).build();   // ⭐ 304, no body
    }
    return ResponseEntity.ok()
            .eTag(etag)
            .cacheControl(CacheControl.maxAge(Duration.ofSeconds(30)).cachePrivate())
            .body(OrderResponse.from(o));
}
```

**That is Day 102's conditional GET**, and it is worth writing out because the saving is not the
compute — it is the bandwidth and the mobile client's battery. A 304 is roughly 200 bytes.

For the write side, Day 102's lost-update prevention:

```java
@PutMapping("/{id}")
ResponseEntity<OrderResponse> update(@PathVariable UUID id,
                                     @RequestHeader(IF_MATCH) String ifMatch,   // ⭐ required
                                     @Valid @RequestBody UpdateOrderRequest req) {
    return orders.update(id, req, parseVersion(ifMatch))
                 .map(o -> ResponseEntity.ok().eTag("\"" + o.version() + "\"").body(OrderResponse.from(o)))
                 .orElseThrow(() -> new PreconditionFailedException());          // 412
}
```

Making `If-Match` **required** turns "last write wins" into "you must have read the current version
first". Day 165's optimistic locking is the database half of the same idea.

## `ShallowEtagHeaderFilter` — and why it is mostly a trap

Boot offers a filter that computes an ETag by MD5-hashing the rendered response. It works, and it
saves *bandwidth only*: your controller ran, the database was queried, the JSON was built, and only
then is the body discarded. **Compare with the version-based ETag above, which short-circuits before
the work.** Use the filter when you cannot cheaply derive a version; prefer the explicit ETag when you
can.

## Streaming a large response

```java
@GetMapping(value = "/export", produces = APPLICATION_NDJSON_VALUE)
ResponseEntity<StreamingResponseBody> export() {
    StreamingResponseBody body = out -> orders.streamAll()
            .forEach(o -> writeLine(out, OrderResponse.from(o)));
    return ResponseEntity.ok()
            .header(CONTENT_DISPOSITION, "attachment; filename=orders.ndjson")
            .body(body);
}
```

**Never build a 500 MB `List<OrderResponse>` and return it** — that is an `OutOfMemoryError` under
concurrent load, and Day 144's `ExitOnOutOfMemoryError` will then correctly kill the pod. Stream it.
Note the honest cost: the status is committed before the body is written, so a mid-stream failure
cannot become a 500 (Day 149's third gap). NDJSON at least lets the consumer detect truncation.

## Compression

```yaml
server.compression.enabled: true
server.compression.mime-types: application/json,application/problem+json
server.compression.min-response-size: 2KB      # ⭐ below this, compression costs more than it saves
```

**Usually better at the ingress** (nginx, ALB, Envoy) than in the JVM, since it is CPU your
application threads should not spend. Enable in the app only when you have no such layer.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| `@Bean ObjectMapper` replacing Boot's | loses every default and module; distant, confusing symptoms |
| Timestamps for dates | ambiguous precision, unreadable, JS pain |
| `LocalDateTime` on the wire | means different instants to sender and receiver |
| `double` for money | Day 106; wrong totals |
| Unknown properties ignored on your own API | client typos become silent data loss |
| Strict parsing on a third-party response | their additive change breaks you (Day 109) |
| `null` into a primitive | silent `0` — orders for zero items |
| `NON_NULL` on PATCH inputs | cannot express "clear this field" |
| `long` IDs over 2^53 as JSON numbers | JS silently rounds them |
| Building a huge list instead of streaming | OOM under load |
| `ShallowEtagHeaderFilter` expecting compute savings | the work already happened |
| `@JsonProperty` on 80 fields | one naming strategy replaces all of them |

## Interview questions

**Q: How do you configure Jackson in Boot, and why not just define an `ObjectMapper` bean?**
Via `Jackson2ObjectMapperBuilderCustomizer` or `spring.jackson.*`, because replacing the bean discards
Boot's defaults and every module other starters contributed — and the breakage shows up far from the
change.

**Q: What are the JSON types that corrupt silently?**
Dates as timestamps or zone-less types; `double` for money; integers above 2^53 for JavaScript
clients; and null into a primitive, which becomes zero. All four are configuration or type choices,
not code.

**Q: Should you fail on unknown properties?**
Yes on my own request bodies, so a client's typo is a 400 rather than silent data loss. No when I am
the client consuming someone else's API, because they may add fields and a tolerant reader must not
break.

**Q: How do you implement conditional GET?**
Derive an ETag from the entity version, compare with `If-None-Match`, return 304 with no body if
equal. And require `If-Match` on writes so a stale client gets a 412 instead of clobbering a change.

## 🎙️ Articulation drill

Two minutes: **"How do you control what your API actually puts on the wire?"**

One `ObjectMapper` configured through the builder customizer, with the four Day 106 hazards closed:
ISO dates in UTC, `BigDecimal` for money, string IDs above 2^53, and failure on null-into-primitive.
Strict on unknown properties inbound, tolerant outbound. `ResponseEntity` where headers are the
feature — ETag and `If-None-Match` for a 304, required `If-Match` for a 412 instead of a lost update.
Then the operational detail: stream large responses, and know that once the status line is written no
error handler can rescue the response.
