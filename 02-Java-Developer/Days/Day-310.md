# Day 310 ⭐

**L-310** · ⭐ Concurrency in LLD — the question that ends most interviews

**Time:** 3 hrs · **Mode:** NEW

> **⭐ "What happens if two users do this at the same time?" is asked in almost every LLD round, and
> it is where most candidates stop being convincing.**
>
> Stage 1 taught you the primitives. Today is about the design-level version: **finding the shared
> mutable state in thirty seconds, choosing the narrowest correct guard, and saying what changes when
> the system is distributed.**

---

# Part 1 — ⭐⭐ Find the shared mutable state

> **⭐ Concurrency only matters where two threads can touch the same mutable thing. Everything else is
> free.** So the first move is always: **list what is shared and mutable.**

| In a typical LLD problem | ⭐ Shared? | ⭐ Mutable? |
|---|---|---|
| ⭐ **The spot/seat/inventory availability map** | ⭐ yes | ⭐ **yes — this is always the answer** |
| ⭐ **A counter (bookings, tokens, stock)** | yes | ⭐ yes |
| ⭐ **A cache** | yes | yes |
| The strategy objects | yes | ⭐ **no — stateless, so free** |
| Value objects (`Money`, ids) | yes | ⭐ **no — immutable (Day 304), so free** |
| A `Ticket` after issue | ⭐ typically not | — |

**⭐ Then the second move: name the exact race, as a two-column interleaving.** Vague concurrency talk
scores nothing; this scores immediately:

```
⭐ Thread A                          ⭐ Thread B
   findFreeSpot() → spot 42
                                     findFreeSpot() → spot 42     ⭐ ← both saw it free
   spot42.occupy()
                                     spot42.occupy()              ⭐ ← two cars, one spot
```

> **⭐ The general shape is always check-then-act**, and it is the single most common bug in every
> LLD problem: **the check and the act are not one operation, so something can happen in between.**

---

# Part 2 — ⭐ The four tools, in order of preference

| # | Tool | ⭐ Use when | Cost |
|---|---|---|---|
| ⭐ **1** | ⭐ **Immutability** | ⭐ **the value never changes — value objects, events, config** | ⭐ none |
| ⭐ **2** | ⭐ **Confinement** | ⭐ **one thread owns it — a queue + single consumer** | ⭐ throughput of one |
| ⭐ **3** | ⭐ **Atomics / CAS** | a single variable or reference | ⭐ retry loops, ABA |
| ⭐ **4** | ⭐ **Locks** | ⭐ **multiple fields must change together** | ⭐ contention, deadlock |

**⭐ Say them in this order in an interview.** Reaching straight for `synchronized` is correct often
enough, but showing that you considered making the thing immutable or confining it to one thread
first is what distinguishes a design answer from a syntax answer.

## ⭐ Tool 3 — CAS, and why it beats a lock for a single spot

```java
class Spot {
    private final AtomicReference<Status> status = new AtomicReference<>(FREE);

    boolean tryOccupy() {
        return status.compareAndSet(FREE, OCCUPIED);   // ⭐ atomic check-then-act. The loser gets false.
    }
}
```

```java
// ⭐ The allocator then retries — no lock at all, no contention between different spots
Spot allocate(VehicleType type) {
    for (Spot candidate : index.candidatesFor(type)) {
        if (candidate.tryOccupy()) return candidate;   // ⭐ first winner takes it
    }
    throw new LotFull();
}
```

**⭐ This is the answer that scores best on the parking-lot family**, because it is correct,
lock-free, and **the losing thread simply moves to the next spot rather than waiting** — which is
exactly what happens in the real world.

⚠️ **CAS works when one variable decides it.** If occupying a spot must *also* decrement a per-floor
counter and append to a log atomically, you need a lock or a transaction — **say that, rather than
pretending an atomic covers it.**

## ⭐ Tool 4 — locks, and the granularity decision

**⭐ Granularity is the whole design question. State the ladder:**

| Granularity | Throughput | ⭐ When |
|---|---|---|
| ⭐ **One global lock** | ⭐ **1 writer, whole system** | ⭐ **fine for a vending machine; fatal for a parking lot** |
| ⭐ **Per-partition** (floor, shard, stripe) | good | ⭐ **the usual right answer** |
| ⭐ **Per-entity** (per spot, per seat) | ⭐ best | ⭐ when entities are independent |
| Lock-free (CAS) | ⭐ best | single-variable decisions |

```java
// ⭐ Striped locking — bounded lock count, good concurrency, no per-entity object explosion
private final Object[] stripes = new Object[16];
private Object lockFor(SpotId id) { return stripes[Math.floorMod(id.hashCode(), stripes.length)]; }
```

**⭐ The `ConcurrentHashMap` answer is usually better than any of them**, because it does striping for
you and gives you atomic composites:

```java
// ⭐ WRONG — check-then-act across two calls
if (!bookings.containsKey(seatId)) bookings.put(seatId, userId);

// ⭐ RIGHT — one atomic operation. The loser gets the existing value back.
User winner = bookings.putIfAbsent(seatId, userId);
if (winner != null) throw new SeatTaken(seatId);

// ⭐ RIGHT — atomic read-modify-write, held only for this key
counts.compute(key, (k, v) -> v == null ? 1 : v + 1);
```

⚠️ **`computeIfAbsent`/`compute` hold a bin lock for the duration of your lambda.** Do not do I/O,
call another service, or acquire a second lock inside one — **that is a deadlock and a throughput
collapse in one line**, and it is a real bug in production systems.

## ⭐ Deadlock — the two-lock case, and the one rule

```java
// ⭐ Transfer between two accounts. A→B and B→A concurrently = classic deadlock.
void transfer(Account from, Account to, Money amount) {
    Account first  = from.id().compareTo(to.id()) < 0 ? from : to;    // ⭐ GLOBAL ORDERING
    Account second = (first == from) ? to : from;
    synchronized (first) { synchronized (second) { ... } }
}
```

> **⭐ One rule covers every LLD deadlock: acquire multiple locks in a globally consistent order.**
> Sort by id. Say it in one sentence and move on — it is a well-known answer and dwelling on it wastes
> time.

# Part 3 — ⭐ In-process vs distributed — the sentence that scores

**⭐ Almost every LLD design is single-JVM, and almost every interviewer will ask "what if you run
three instances?" Have the mapping ready:**

| In-process | ⭐ Distributed equivalent |
|---|---|
| ⭐ `synchronized` / `ReentrantLock` | ⭐ **a database row lock, or Day 207's Redis lock + fencing token** |
| ⭐ `AtomicReference.compareAndSet` | ⭐ **an optimistic version column** (Day 165) — ⭐ *the same idea* |
| `ConcurrentHashMap.putIfAbsent` | ⭐ **a unique constraint** (Day 189) — the database is the arbiter |
| An in-memory counter | ⭐ `UPDATE ... SET n = n + 1` **or Redis `INCR`** (Day 208) |
| A single-consumer queue | a partitioned queue / Kafka partition key |

> **⭐ The strongest version: "In one JVM I'd compare-and-set the seat's status. Across instances that
> is exactly an optimistic version column — same algorithm, the database is just the arbiter instead
> of the CPU. If I needed to hold it across a payment, I'd use a short-lived reservation row with an
> expiry rather than a lock, because you must never hold a lock across a user interaction."**

**⭐ That last clause is the highest-value sentence in this entire day**, and it applies to seat
booking, ticketing, inventory and checkout — **all of Day 316's problem.**

## ⭐ Single-threaded as a legitimate answer

**⭐ Confinement scales further than people expect, and Redis is the proof** (Day 203):

```
⭐ requests → BlockingQueue → ONE consumer thread → mutates state, no locks at all
```

| ⭐ Pro | ⭐ Con |
|---|---|
| ⭐ **No locks, no races, trivially correct** | ⭐ one core for the mutation |
| ⭐ **Deterministic and replayable** | a slow operation blocks everything |
| ⭐ Easy to reason about and to test | ⭐ needs partitioning to scale |

**⭐ Offer it for elevator controllers, order books and game engines.** It is often the *simplest
correct* design, and saying "I'd confine the state to one thread and shard by lot id if throughput
needs it" reads as seniority.

# Part 4 — ⭐ Proving it: the concurrency test

**⭐ Claiming thread-safety is worthless. This harness takes four minutes and turns it into
evidence:**

```java
@Test
void only_one_thread_can_take_a_spot() throws Exception {
    Spot spot = new Spot(SpotId.of(42));
    int threads = 100;
    var start = new CountDownLatch(1);              // ⭐ maximise the collision
    var done  = new CountDownLatch(threads);
    var wins  = new AtomicInteger();

    var pool = Executors.newFixedThreadPool(threads);
    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            try { start.await(); if (spot.tryOccupy()) wins.incrementAndGet(); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            finally { done.countDown(); }
        });
    }
    start.countDown();                              // ⭐ release all 100 at once
    assertThat(done.await(5, SECONDS)).isTrue();
    assertThat(wins.get()).isEqualTo(1);            // ⭐ EXACTLY ONE
}
```

| ⭐ Technique | ⭐ Why |
|---|---|
| ⭐ **A start latch** | ⭐ without it, threads trickle and never collide |
| ⭐ **Count winners, assert exactly 1** | ⭐ the invariant, stated as a number |
| ⭐ **Repeat 100–1000 times** | ⭐ a race that fails 1 in 50 runs passes once and lies |
| A timeout on `await` | a deadlock becomes a failed test, not a hung build |

⚠️ **A passing concurrency test proves nothing on its own; a failing one proves everything.**
**Always run it against the broken version first** — if it does not fail there, it is not testing the
race.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Not raising concurrency at all | ⭐ **the most commonly skipped section in LLD** |
| ⭐ Vague "I'd add synchronization" | ⭐ name the race as an interleaving instead |
| ⭐ `containsKey` then `put` | ⭐ **the canonical check-then-act bug** |
| ⭐ One global lock on a busy structure | ⭐ correct and useless — one writer for everything |
| ⭐ I/O inside `computeIfAbsent` | ⭐ **a bin lock held across a network call** |
| Two locks with no ordering | deadlock |
| ⭐ Holding a lock across a user interaction | ⭐ **use a reservation with an expiry instead** |
| ⭐ Synchronizing immutable or stateless objects | pure cost, and it signals confusion |
| Claiming thread-safety with no test | a claim, not evidence |
| A test with no start latch | the threads never actually collide |
| ⭐ No answer for "what if three instances?" | ⭐ the follow-up that ends the round |

## Interview questions

**Q: How do you approach concurrency in a design?**
Find the shared mutable state — in most of these problems it is one availability map or one counter —
then name the exact interleaving that breaks, usually a check-then-act. Then pick the weakest tool
that works: immutability first, then confining to one thread, then an atomic, and a lock only when
several fields must change together. Then I say what changes with multiple instances.

**Q: Two users try to book the last seat. Walk me through it.**
Both read the seat as free, both write, and one booking is silently lost — check-then-act. In one JVM
I compare-and-set the seat status, so exactly one wins and the loser retries or gets an error. Across
instances that is an optimistic version column or a unique constraint on (showId, seatId), letting
the database be the arbiter. And if the seat must be held across a payment, I use a reservation row
with an expiry rather than a lock, because you never hold a lock across a human.

**Q: Global lock, striped locks, or per-entity locks?**
Whatever is narrowest and still correct. A global lock is fine for a vending machine, which has one
user at a time, and fatal for a parking lot, which serialises every arrival. Per-entity is best when
entities are independent; striping bounds the number of lock objects. Usually a `ConcurrentHashMap`
with `putIfAbsent` or `compute` is better than any hand-rolled scheme — but not with I/O inside the
lambda, because that holds a bin lock across a network call.

**Q: When is single-threaded the right answer?**
When the state is one coherent thing and the operations are short — an elevator controller, an order
book, a game loop. Redis proves how far it scales. It is trivially correct, deterministic, replayable
and easy to test, and it shards by key when it needs more throughput. I would rather offer that than
a lock hierarchy I have to defend.

**Q: How do you test that your design is thread-safe?**
A latch-released burst of a hundred threads at the same operation, counting winners and asserting
exactly one, repeated hundreds of times with a timeout so a deadlock fails rather than hangs. And I
run it against the broken implementation first — if it does not fail there, it is not testing the
race.

## 🎙️ Articulation drill

**Three minutes:** *"Two users book the last seat at the same time. Tell me everything."*

**⭐ The full-marks answer has five parts, in this order:** the interleaving as two columns · the
in-process fix (CAS or `putIfAbsent`) · the distributed fix (version column or unique constraint,
named as *the same algorithm*) · **the payment-hold problem and the reservation-with-expiry answer**
· and the test that proves exactly one winner.

**⭐ Most candidates give part one and stop.** Parts three and four are where the round is decided.
