# Part 3 — ⭐⭐ The problems

## ⭐ Warm-up (target: 12 minutes)

> **Given an array of integers and a target, return the indices of two numbers that sum to the target.
> Exactly one solution exists; you may not use the same element twice.**

| ⭐ What is actually being tested | |
|---|---|
| ⭐⭐ **Do you jump straight to the hash map** | ⭐ or narrate the O(n²) first and then improve — **narrate it, briefly** |
| ⭐⭐ **The one-pass insight** | ⭐⭐ check for the complement *before* inserting, so you never match yourself |
| ⭐ Clarifications worth asking | ⭐ negatives? duplicates? is the array sorted? (if sorted, two pointers is O(1) space) |

```java
Map<Integer, Integer> seen = new HashMap<>();      // ⭐ value → index
for (int i = 0; i < nums.length; i++) {
    Integer j = seen.get(target - nums[i]);        // ⭐⭐ look BEFORE inserting
    if (j != null) return new int[]{j, i};
    seen.put(nums[i], i);
}
throw new IllegalArgumentException("no solution");
```

**⭐ Say aloud:** *"Brute force is O(n²). A hash map of value to index makes the complement lookup O(1),
so one pass, O(n) time and O(n) space. I check before inserting so an element cannot pair with itself."*

## ⭐⭐ Main problem (target: 30 minutes)

> **Given an array of integers, return all unique triplets `[a, b, c]` such that `a + b + c == 0`. The
> solution set must not contain duplicate triplets.**

| ⭐ The arc they want to see | |
|---|---|
| ⭐ 1. Brute force O(n³), stated and dismissed | ⭐ ten seconds |
| ⭐ 2. "Fix one element, then it is two-sum" — O(n²) with a hash set | ⭐⭐ **and the duplicate problem appears here** |
| ⭐⭐ 3. **Sort first, then fix `i` and two-pointer the rest** | ⭐⭐ O(n²) time, O(1) extra space, **and dedup becomes trivial** |
| ⭐⭐ 4. **The three skip conditions** | ⭐⭐ this is where most candidates lose it |

```java
Arrays.sort(nums);                                     // ⭐⭐ O(n log n) — enables both pointers AND dedup
List<List<Integer>> out = new ArrayList<>();

for (int i = 0; i + 2 < nums.length; i++) {
    if (nums[i] > 0) break;                            // ⭐ sorted: no triple can sum to 0 past here
    if (i > 0 && nums[i] == nums[i - 1]) continue;     // ⭐⭐ SKIP 1: duplicate anchor

    int lo = i + 1, hi = nums.length - 1;
    while (lo < hi) {
        int sum = nums[i] + nums[lo] + nums[hi];
        if (sum < 0) lo++;
        else if (sum > 0) hi--;
        else {
            out.add(List.of(nums[i], nums[lo], nums[hi]));
            while (lo < hi && nums[lo] == nums[lo + 1]) lo++;   // ⭐⭐ SKIP 2
            while (lo < hi && nums[hi] == nums[hi - 1]) hi--;   // ⭐⭐ SKIP 3
            lo++; hi--;                                        // ⭐⭐ MOVE BOTH — a classic bug
        }
    }
}
return out;
```

| ⭐⭐ The four bugs to expect in yourself | |
|---|---|
| ⭐⭐ **Forgetting to move both pointers after a hit** | ⭐⭐ infinite loop |
| ⭐⭐ **Deduping with a `Set<List<Integer>>` instead of skipping** | ⭐ works, but it is the *slower, memory-heavy* answer — say why you rejected it |
| ⭐ Skip conditions written before the check instead of after | ⭐ misses valid triplets |
| ⭐ `i > 0` guard omitted | ⭐ `nums[-1]` |

**⭐⭐ Narration that scores:** *"Sorting costs O(n log n), which is free relative to the O(n²) we are
already paying — and it buys two things: the two-pointer sweep, and duplicate handling by skipping equal
neighbours rather than by a set. That is the real reason to sort."*

# Part 4 — ⭐ The pattern family and its tells

| ⭐ Tell in the problem | ⭐ Reach for |
|---|---|
| ⭐⭐ "have I seen this value / count of" | ⭐⭐ **HashMap / HashSet** |
| ⭐⭐ "sorted array" or "pair summing to" | ⭐⭐ **two pointers, O(1) space** |
| ⭐ "contiguous subarray" | ⭐⭐ **sliding window** (Day 475) |
| ⭐ "prefix sums / subarray sums to k" | ⭐⭐ **prefix sum + hash map** — the pairing people forget |
| ⭐ "in place, O(1) extra space" | ⭐ two pointers, or index-as-hash |
| ⭐ "k-th something" | ⭐ heap or quickselect (Day 475) |

⚠️ **The one pairing worth memorising today: prefix sum + hash map.** "Count subarrays summing to k" is
O(n) with a map of prefix-sum frequencies, and candidates who have not met the pairing reach for a
nested loop and never find the linear solution. **`count += freq.getOrDefault(prefix - k, 0)` then
`freq.merge(prefix, 1, Integer::sum)`.**

## Interview questions

**Q: Two-sum — why the hash map, and why check before inserting?**
The brute force is quadratic because for each element you scan the rest looking for its complement. A map
from value to index turns that scan into a constant-time lookup, so it is one pass, linear time, linear
space. Checking for the complement before inserting the current element is what stops an element pairing
with itself when the target is exactly twice its value — it is a one-line detail that is the difference
between correct and subtly wrong.

**Q: Why sort in three-sum, when sorting costs O(n log n)?**
Because the algorithm is already O(n²), so the sort is free in asymptotic terms, and it buys two things.
It enables the two-pointer sweep, which gives O(1) extra space rather than a hash set per anchor. And it
makes duplicate handling trivial: equal elements are adjacent, so you skip them by comparing neighbours
instead of deduplicating a set of lists at the end. The second reason is the one people miss — the sort
is as much about correctness as about the pointer technique.

**Q: What are the failure modes in that inner loop?**
Four. Not advancing both pointers after recording a match, which is an infinite loop. Placing the skip
conditions before the sum check rather than after, which drops valid triplets. Omitting the `i > 0` guard
on the anchor dedup, which indexes out of bounds. And using a set of lists to dedupe, which is correct
but slower and memory-heavy — that one is fine to do if you say out loud why you would prefer skipping.

**Q: How do you count subarrays summing to k in linear time?**
Prefix sum with a hash map of prefix-sum frequencies. As you sweep, the number of subarrays ending here
with sum k is the number of times `prefix - k` has been seen, so you add that to the count and then
record the current prefix. It is O(n) time and space. It is worth knowing as a pairing rather than a
problem, because candidates who have not met it reach for nested loops and never find the linear
solution.

**Q: Why record a mock?**
Because nearly everything worth fixing is in the delivery, and you cannot observe your own delivery from
the inside. Watching it back you find the forty seconds of silence you did not notice, the fact that you
started coding before stating an approach, and that you never tested your own code. Those three account
for most of the gap between people who know the algorithms and people who pass the round — and none of
them are visible without the recording.

## 🎙️ Articulation drill

**Two minutes:** narrate the *first six minutes* of three-sum, without writing any code.

**⭐ Restate the problem. Ask about negatives, duplicates and whether the input can be modified — that
last one matters because sorting mutates it. State the brute force at O(n³) and dismiss it in one
sentence. Then the real reasoning: fixing one element reduces it to two-sum, which is O(n²); sorting
first is free against that bound and buys both the two-pointer sweep at O(1) space and duplicate
handling by adjacency.**

**⭐ Then the sentence that ends the block: "before I code — does that approach look reasonable to you?"
Practise it until it is reflex. It is fifteen seconds and it is the single highest-value habit in the
hour.**
