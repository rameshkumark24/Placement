# L-027 · When memory goes wrong

## Java has memory leaks. Yes, really.

**A Java memory leak is an object that is still *reachable* but will never be *used* again.**

GC only collects what's unreachable (Day 026). If you accidentally hold a reference, GC correctly
keeps the object — forever. The collector isn't wrong; your code is.

## The seven leak patterns

### 1. Static collections — the most common by far

```java
public class Cache {
    private static final Map<String, byte[]> CACHE = new HashMap<>();   // never cleared

    public static void put(String k, byte[] v) { CACHE.put(k, v); }     // grows forever
}
```

**Statics are GC roots** (Day 025). Everything reachable from one is immortal.

**Fix:** a bounded cache with eviction — Caffeine, or `LinkedHashMap` with `removeEldestEntry`
(Day 049).

### 2. Unclosed resources

```java
// 💀 leaks a file descriptor and its buffers on every call
InputStream in = new FileInputStream(f);
process(in);

// ✅
try (InputStream in = new FileInputStream(f)) { process(in); }
```

**This is the same bug class as your Day 004 experiment** — commenting out `client.close()` and
watching descriptors accumulate, and the `CLOSE_WAIT` sockets on Day 008. Same root cause, three
different symptoms.

### 3. Listeners never unregistered

```java
button.addListener(this);       // holds a reference to `this`
// ... this object is "finished" but the button still points at it
```

Common in UI code, event buses, and Spring `ApplicationListener`. Register in a lifecycle callback,
**unregister in the matching one**.

### 4. `ThreadLocal` in a thread pool

```java
private static final ThreadLocal<HeavyContext> CTX = new ThreadLocal<>();

public void handle(Request r) {
    CTX.set(new HeavyContext(r));
    // ... no remove()
}
```

**Pooled threads are never destroyed**, so the value stays attached to the thread and survives into
the *next* request handled by that thread. This is both a leak and a **correctness/security bug** —
request A's context visible to request B.

```java
try {
    CTX.set(new HeavyContext(r));
    handle(r);
} finally {
    CTX.remove();               // ← mandatory in a pool
}
```

Full treatment on Day 066A. Flagging it here because it's the leak most likely to bite you in Spring.

### 5. Inner classes holding the outer instance

```java
class Outer {
    byte[] huge = new byte[100_000_000];

    class Inner { }                          // NON-static inner: holds Outer.this implicitly

    Inner make() { return new Inner(); }     // returning this keeps `huge` alive!
}
```

**A non-static inner class holds a hidden reference to its enclosing instance.** Return one from a
long-lived object and you've pinned the outer object and everything it holds.

**Fix:** make it `static` unless you genuinely need the outer instance. Day 044.

### 6. Mutable keys in a `HashMap`

```java
Set<Point> set = new HashSet<>();
Point p = new Point(1, 1);
set.add(p);
p.x = 99;                       // hashCode changed — the entry is now in the WRONG bucket
set.remove(p);                  // fails
set.contains(p);                // false
```

The entry is unreachable *by lookup* but perfectly reachable *by GC*. **It can never be removed.**
Day 040 and Day 048 explain the bucket mechanics.

**Fix:** immutable keys. Use records (Day 042).

### 7. Substring / array views (historical, still worth knowing)

Before Java 7u6, `String.substring()` shared the parent's `char[]`, so a 5-character substring of a
100 MB string kept the whole array alive. Fixed by copying. Still a good illustration that **holding
a small view can retain a large backing structure** — which remains true for `Arrays.asList`,
`subList`, and `ByteBuffer.slice`.

## The `OutOfMemoryError` family — read the message

**The message tells you which problem you have.** Most people skip it.

| Message | Means | Look at |
|---|---|---|
| `Java heap space` | Heap genuinely full | A leak, or `-Xmx` too small |
| `GC overhead limit exceeded` | >98% of time in GC, <2% heap recovered | **Almost always a leak** |
| `Metaspace` | Too many classes loaded | Classloader leak — redeploys, dynamic proxies |
| `unable to create new native thread` | OS thread limit hit | Thread leak, unbounded pool |
| `Direct buffer memory` | Off-heap NIO buffers exhausted | Netty/NIO buffers not released |
| `Requested array size exceeds VM limit` | Array larger than ~2³¹ | A bug in a size calculation |

**`GC overhead limit exceeded` is the most diagnostic one.** It means the JVM is collecting
constantly and recovering almost nothing — the definition of a leak. If you see it, don't raise
`-Xmx`; find the leak.

## Diagnosis — the procedure

Follow this order. It works.

### 1. Confirm it's actually a leak

```bash
java -Xlog:gc* -Xlog:gc:file=gc.log YourApp
```

Look at **heap used *after* each full GC** over time:

```
   Not a leak:              A leak:
   used                     used
    │  ╱╲  ╱╲  ╱╲            │      ╱╲   ╱╲
    │ ╱  ╲╱  ╲╱  ╲           │   ╱╲╱  ╲ ╱  ╲
    │╱                       │ ╱╲╱      ╲╱
    └──────────────▶ time    └────────────────▶ time
   sawtooth returns          floor RISES after every collection
   to the same floor
```

**The rising floor is the signature.** A sawtooth that returns to the same baseline is healthy, no
matter how dramatic it looks.

### 2. Get a heap dump

```bash
# Automatically, on OOM — SET THIS IN PRODUCTION, ALWAYS
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps YourApp

# On demand
jcmd <pid> GC.heap_dump /tmp/heap.hprof
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>
```

> **`-XX:+HeapDumpOnOutOfMemoryError` costs nothing until it's needed and is the difference between
> diagnosing an OOM in an hour and never diagnosing it at all.** Put it in every production JVM.

### 3. Find the growth without a dump

```bash
jcmd <pid> GC.class_histogram | head -25
# wait 5 minutes
jcmd <pid> GC.class_histogram | head -25
```

**Diff the two.** Whatever's growing is your suspect. This often identifies the leak in two minutes
without any tooling.

### 4. Analyse the dump

Open in **Eclipse MAT** (best) or VisualVM.

The workflow that actually finds it:

1. **Leak Suspects report** — MAT's automated analysis, right surprisingly often
2. **Dominator tree** — which objects retain the most memory. **Sort by *retained* size, not shallow
   size.** Retained = what would be freed if this object went away.
3. **Path to GC Roots** on the suspect — *this is the answer.* It shows exactly which reference chain
   is keeping it alive.

**"Path to GC roots" is the single most useful feature in heap analysis**, and knowing to reach for
it is a strong signal in an interview.

### 5. Live profiling

```bash
# Java Flight Recorder — low overhead, safe in production
java -XX:StartFlightRecording=duration=60s,filename=rec.jfr YourApp
jcmd <pid> JFR.start duration=60s filename=rec.jfr
# open rec.jfr in JDK Mission Control
```

**JFR is production-safe** (~1% overhead). Use it rather than a heavyweight profiler on a live
service. Async-profiler is the other good option for allocation flame graphs.

## GC tuning — the honest version

**Rule 1: don't tune GC.** Modern defaults are good. Most "GC problems" are allocation problems or
leaks in disguise, and tuning flags to hide a leak makes it worse.

**Rule 2: measure before and after.** If you can't show a metric that improved, you didn't tune
anything.

### The flags actually worth setting

```bash
-Xms4g -Xmx4g                        # equal! avoids resize pauses; makes behaviour predictable
-XX:MaxGCPauseMillis=200             # G1's pause-time goal
-XX:+HeapDumpOnOutOfMemoryError      # always
-XX:HeapDumpPath=/var/dumps
-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=10M
-XX:+ExitOnOutOfMemoryError          # in a container: die and let the orchestrator restart you
```

**`-Xms` equal to `-Xmx`** is the highest-value setting on that list. The JVM otherwise starts small
and grows, and each growth is a pause. In a container with a fixed memory limit there's no reason to
start small.

### In containers — the one that catches everyone

```bash
-XX:MaxRAMPercentage=75.0
```

**Before JDK 10, the JVM read the *host's* memory, not the container's limit.** It would size a
4 GB heap inside a 512 MB container, and the OOM killer would kill the process with no Java-level
error — the container just dies, no stack trace, no heap dump.

Modern JVMs are container-aware, but **set `MaxRAMPercentage` explicitly** and leave headroom for
Metaspace, thread stacks, direct buffers and the JVM itself. 75% is a reasonable default.

**This is exactly the `-XX:MaxRAMPercentage=75` line in your
[Java cheatsheet](../Java-Vibe-Coding-Cheatsheet.md#7-delivery) delivery checklist.** Now you can
explain it.

### Choosing a collector

| Situation | Collector |
|---|---|
| Default, most services | **G1** — leave it alone |
| Batch processing, throughput over latency | Parallel |
| Latency-critical, large heap | ZGC |
| Tiny container, single CPU | Serial |

## Type this yourself

```java
import java.util.*;

public class LeakDemo {
    // A GC ROOT — everything in here is immortal
    static final List<byte[]> LEAK = new ArrayList<>();

    public static void main(String[] args) throws Exception {
        System.out.println("Watch the heap floor RISE. Run with:");
        System.out.println("  java -Xmx128m -Xlog:gc -XX:+HeapDumpOnOutOfMemoryError LeakDemo\n");

        Runtime rt = Runtime.getRuntime();
        for (int i = 1; ; i++) {
            LEAK.add(new byte[1_000_000]);              // 1 MB retained each iteration

            if (i % 10 == 0) {
                System.gc();
                Thread.sleep(50);
                long used = (rt.totalMemory() - rt.freeMemory()) / 1024 / 1024;
                System.out.printf("Iteration %3d — used after GC: %3d MB  <-- the FLOOR%n", i, used);
            }
        }
    }
}
```

Then the healthy contrast — same allocation volume, nothing retained:

```java
public class NoLeakDemo {
    public static void main(String[] args) throws Exception {
        Runtime rt = Runtime.getRuntime();
        for (int i = 1; i <= 200; i++) {
            byte[] temp = new byte[1_000_000];         // dies immediately
            if (i % 10 == 0) {
                System.gc();
                Thread.sleep(50);
                long used = (rt.totalMemory() - rt.freeMemory()) / 1024 / 1024;
                System.out.printf("Iteration %3d — used after GC: %3d MB  <-- STABLE%n", i, used);
            }
        }
        System.out.println("\n200 MB allocated, heap flat. Garbage is cheap; retention is not.");
    }
}
```

**Run both.** The numbers side by side are the entire lesson: identical allocation volume, completely
different memory behaviour. **What matters is what survives.**

Then analyse the crash:

```bash
java -Xmx128m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=. LeakDemo
# → java_pid<N>.hprof written on OOM

jhat java_pid1234.hprof          # basic built-in viewer, http://localhost:7000
# better: open it in Eclipse MAT → Leak Suspects → Path to GC Roots
```

**Find `LeakDemo.LEAK` in the dominator tree, then run "Path to GC Roots" on it.** You'll see the
static field named as the root. That's the exact workflow you'd use in production.

Live monitoring:

```bash
jps                              # find the PID
jstat -gc <pid> 1000 20          # GC stats every second, 20 times
jcmd <pid> GC.class_histogram | head -20
jcmd <pid> VM.native_memory summary     # needs -XX:NativeMemoryTracking=summary
```

## Common mistakes

| Mistake | Correction |
|---|---|
| "Java can't leak, it has GC" | It leaks reachable-but-unused objects. GC is doing its job correctly. |
| Raising `-Xmx` to fix an OOM | Delays the crash. Find the leak first. |
| Ignoring the OOM message text | The message names the memory area and usually the cause. |
| Tuning GC flags before measuring | Most GC problems are allocation or retention problems. |
| No `HeapDumpOnOutOfMemoryError` in production | You get one chance at the evidence and you threw it away. |
| Sorting a heap dump by shallow size | Sort by **retained** size — that's what would actually be freed. |
| `ThreadLocal` without `remove()` in a pool | Leak *and* cross-request data exposure. |
| Not setting `MaxRAMPercentage` in a container | The OOM killer terminates you with no Java error at all. |
| Using `SoftReference` as a cache | Unpredictable. Use a bounded cache with explicit eviction. |

## Interview questions

**Q: Can Java have memory leaks?**
> Yes. GC only reclaims unreachable objects, so anything still referenced is kept even if it will
> never be used again. The classic causes are static collections that grow without bound, unclosed
> resources, listeners that are never unregistered, and `ThreadLocal` values in a thread pool.

**Q: How would you diagnose an `OutOfMemoryError` in production?**
> First read the message — it identifies the memory area. Then check GC logs for whether heap usage
> after full GC is trending upward, which distinguishes a leak from an undersized heap. Then take a
> heap dump, ideally captured automatically with `-XX:+HeapDumpOnOutOfMemoryError`, and analyse it in
> MAT: dominator tree sorted by retained size, then "path to GC roots" on the suspect to find the
> reference chain holding it.

**Q: What does `GC overhead limit exceeded` mean?**
> The JVM spent over 98% of recent time collecting and recovered under 2% of the heap. It's a strong
> indicator of a genuine leak rather than an undersized heap, because collection is running
> constantly and achieving nothing.

**Q: Why does `ThreadLocal` leak in a thread pool?**
> Pooled threads are never destroyed, so a value set during one request stays attached to that thread
> and survives into subsequent requests. It's both a memory leak and a correctness issue, since one
> request can observe another's context. Always `remove()` in a `finally` block.

**Q: What JVM flags would you set in production?**
> `-Xms` equal to `-Xmx` to avoid resize pauses, `-XX:MaxRAMPercentage` in containers so the heap fits
> the cgroup limit, `-XX:+HeapDumpOnOutOfMemoryError` with a writable path, and GC logging to a
> rotating file. I'd leave the collector as G1 unless measurements justified otherwise.

**Q: Should you tune GC?**
> Usually not. Defaults are good and most apparent GC problems are allocation or retention problems.
> If you do tune, measure a specific metric before and after — otherwise you've changed flags, not
> improved anything.
