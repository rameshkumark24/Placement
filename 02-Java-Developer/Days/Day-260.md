# Day 260 🏗️

**P-260** · The rest of the API — pagination, filtering, and the operational endpoints

**Time:** 3 hrs · **Mode:** BUILD

> The core flow works. **Today is the surface around it** — the list endpoints, the search, the
> operational endpoints — and the reason this day exists separately is that **list endpoints are
> where projects quietly acquire their worst performance and their worst data leaks.**
>
> An unbounded list, a client-controlled sort, an N+1 in a page mapper: each is invisible at
> development volume and each is a real problem at Day 255's seeded 100,000 rows.

---

# Part 1 — ⭐ Pagination, implemented as Day 251 specified

```
⭐ Slice, not Page          → ⭐ no COUNT query per request (Day 152)
⭐ max-page-size: 100       → ⭐ ?size=100000 is a one-URL outage
⭐ Sort allow-list          → Day 108, Day 152
⭐⭐ A UNIQUE TIE-BREAK column, always appended
```

> **⭐⭐ The tie-break is the bug nobody finds locally.** Rows with equal sort keys have no defined
> order, so the database may order them differently between the page-1 and page-2 queries — producing
> duplicates and gaps. **It is one line, it costs nothing, and it is essentially unreproducible on
> test data** (Day 152).

**⭐ And the sort allow-list is a data leak, not a style rule** (Day 108): sorting by a field you never
return still orders every row by it. `?sort=internalRiskScore` twice reveals the ranking. **"They can
only sort, not select" is not a defence.**

## ⭐ Keyset pagination where it matters

```
⭐ Feeds, exports, and anything a third party will iterate  → keyset with an opaque cursor
⭐ Admin tables with page numbers                            → offset, ⭐ CAPPED
```

**⭐ The pragmatic hybrid is worth implementing and naming**: offer offset pagination but reject
`page > 500` with a documented error pointing at the cursor endpoint. **Most UIs never exceed page
ten, and the cap turns an availability risk into a documented limit** (Day 152).

**⭐ Cursor rules** (Day 152): opaque so it does not become a contract, validated so a corrupt cursor
is a **400 rather than a 500**, and the `WHERE` clause must mirror the `ORDER BY` exactly including
the tie-break — mismatch them and rows are silently skipped.

## ⭐ And the N+1 that pagination creates

```
⭐ Assert the query count on EVERY list endpoint (Day 255)
```

**Day 152: pagination is where an N+1 becomes expensive**, because you have promised a bounded
response and are issuing an unbounded number of queries to produce it. **And the fix people reach for
makes it worse** — `join fetch` with a `Pageable` makes Hibernate paginate in memory over the whole
table. Day 253 set `fail_on_pagination_over_collection_fetch: true`, so that now throws instead of
warning. **Confirm it does.**

# Part 2 — ⭐ Filtering and search, allow-listed all the way down

```
⭐ Named parameters, allow-listed: ?status=PENDING&from=...&roomId=...
❌ A query language: ?filter=status eq 'PENDING' and total gt 100
```

**⭐ Why not a query language** (Day 108): you have built a parser and an injection surface, you
cannot index for arbitrary predicates, and a client can construct a query that scans your largest
table. **Named parameters keep the query set finite and indexable.**

**⭐ For genuinely dynamic filters, Specifications** (Day 161) — the Criteria API builds a tree, so
values are always bound parameters and injection is structurally impossible. **But `Specification`
returns entities, so combine it with `@EntityGraph` or accept Day 253's `default_batch_fetch_size`
floor.**

## ⭐ Search, sized honestly

| Volume | ⭐ Approach | Day |
|---|---|---|
| Substring on a modest table | ⭐ **trigram GIN index** — ⭐ never `like '%x%'` on a B-tree | 190 |
| Real word search | full-text with a generated `tsvector` column + `setweight` | 199 |
| ⭐ Typo tolerance | ⭐ full-text **plus** trigram fallback | 199 |

**⭐ Two implementation details from Day 199 that will otherwise cost you an evening:**

```
⭐ websearch_to_tsquery for user input  — ⭐ to_tsquery THROWS on a stray operator → 500
⭐ coalesce() around every nullable field — ⭐ one NULL makes the WHOLE document unsearchable
```

**⭐ And the boundary is worth stating in an ADR** (Day 199): PostgreSQL search up to a few million
documents when search is a feature — **and the strongest reason is that there is no synchronisation
problem, because a generated column cannot drift, whereas an external index is a dual write you
reconcile forever.**

# Part 3 — ⭐ Caching, only where it earns its place

**⭐ Before caching anything, apply Day 167's test:**

> **⭐ Is this slow because it is doing genuinely necessary work, or because it lacks an index?**
> **⭐ A cache is not a fix for a missing index** — the first request is still slow, every cold cache
> is still slow, and you have added invalidation complexity.

**⭐ Check the query plan first** (Day 191). Then, if caching is right:

```
⭐ Versioned keys       → invalidation is one INCR, no enumeration (Day 206)
⭐ Jittered TTLs        → ⭐ one habit prevents stampede, avalanche AND expiry bursts
⭐ allkeys-lfu          → ⭐ LRU's batch-scan pathology evicts your working set
⭐ tenant_id IN THE KEY → ⭐⭐ a shared key is a cross-tenant leak (Day 206)
⭐ CacheErrorHandler    → ⭐⭐ Redis down = SLOW, never BROKEN (Day 168)
```

**⭐ The tenant-in-the-key rule is a security control**, not a naming preference — and it belongs on
Day 259's checklist too.

**⭐ And test the failure**: stop Redis under load and confirm the application degrades. **Day 168:
if flushing the cache takes your database down, the cache is an undeclared dependency** — a capacity
problem wearing a performance costume.

## ⭐ Rate limiting, wired in

```
⭐ Sliding-window counter in a Lua script — ⭐ atomic, or it over-admits exactly under load
⭐ Layered keys: IP, user, endpoint, tenant                       (Day 208)
⭐ 429 + Retry-After + RateLimit-* headers                        (Day 208)
⭐ exposedHeaders, or ⭐ the browser cannot read them              (Day 155)
⭐ A documented fail-open/fail-closed decision PER ENDPOINT       (Day 208)
```

**⭐ That last one is the answer that separates candidates**: general traffic fails open because a
protection mechanism must not become the outage; **login and password reset fail closed or fall back
to a local limiter**, because losing rate limiting on login during a Redis outage is exactly when you
cannot afford it.

# Part 4 — ⭐ Versioning, documentation, and the operational surface

## ⭐ Versioning discipline

```
⭐ /api/v1 from day one — visible in logs, routable at the gateway   (Day 153)
⭐ Version the EDGE only — ⭐ separate controllers and DTOs, ONE service
⭐ Additive changes need no new version                              (Day 109)
```

**⭐ "Version the edge, never the core" is the rule to state**: forking the service layer means every
bug is fixed in one of two places, which means it will eventually be fixed in one.

## ⭐ Documentation, kept honest by CI

```
⭐ springdoc with @Operation, @ApiResponses (⭐ INCLUDING errors), @Schema examples
⭐ Concrete return types — ⭐ ResponseEntity<?> erases the schema
⭐ The security scheme, or the UI cannot authenticate
⭐⭐ DISABLED in production — ⭐ a Swagger UI is a map of your attack surface (Day 153)
⭐ CI diffs the generated spec against docs/openapi.yaml            (Day 253)
```

## ⭐ The operational endpoints, checked against Day 143

| | |
|---|---|
| ⭐ Actuator on a **separate port**, allow-listed — never `*` | ⭐ a heap dump is every secret in one GET |
| ⭐ **Liveness and readiness split**; dependencies **only** in readiness | ⭐ Day 128's crash-loop |
| Startup probe configured | a JVM takes 30–60 s |
| ⭐ **Business metrics**, not just technical | see below |

```
⭐ bookings_created_total, bookings_cancelled_total, booking_conflicts_total,
⭐ refresh_token_reuse_detected_total, ratelimit_degraded_total
```

**⭐ Business metrics are what make the project look operated rather than deployed.** `booking_conflicts_total`
is directly your hard problem, observable in production — **"I can show you how often the concurrency
guard actually fires" is a very strong thing to be able to say.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No unique tie-break in the sort | ⭐ duplicated and skipped rows, unreproducible locally |
| ⭐ No `max-page-size` | `?size=100000` is a one-URL outage |
| ⭐ Client-controlled sort field | ⭐ leaks values you never return |
| ⭐ No query-count test on list endpoints | the N+1 arrives with real data |
| `join fetch` with `Pageable` | in-memory pagination over the whole table |
| Deep offsets on a public endpoint | someone iterates to page 50,000 |
| Cursor parse failure → 500 | should be 400 |
| ⭐ A query language in query parameters | a parser and an injection surface you now own |
| `like '%x%'` on a B-tree | Day 189 — a scan, and a DoS vector |
| ⭐ `to_tsquery` on raw user input | ⭐ a user's typo becomes a 500 |
| Missing `coalesce` in the tsvector | one NULL hides the whole document |
| ⭐ Caching instead of indexing | the first request and every cold cache are still slow |
| ⭐ No tenant in the cache key | ⭐ cross-tenant leak |
| ⭐ No `CacheErrorHandler` | Redis down takes the application down |
| Non-atomic rate limiter | over-admits precisely under load |
| Swagger UI live in production | a published map of the attack surface |
| Forking the service layer per version | bugs fixed once instead of twice |

## 🎤 Defence questions

1. **⭐ Why does every sort end with a unique column?**
2. **⭐ Why can't a client sort by any field they like?**
3. **⭐ How do you know your list endpoints have no N+1?**
4. **Why named filters rather than a query language?**
5. **⭐ What did you check before adding a cache?**
6. **⭐ What happens to your API when Redis is down?** (⭐ per endpoint)
