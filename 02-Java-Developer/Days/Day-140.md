# Part 1 — The mechanism, end to end

```
@SpringBootApplication
  └── @EnableAutoConfiguration
        └── @Import(AutoConfigurationImportSelector.class)
              │
              ▼
   1. Read META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
      from EVERY jar on the classpath          ⭐ ~150 class names in a typical app
              ▼
   2. Remove exclusions (@SpringBootApplication(exclude=…), spring.autoconfigure.exclude)
              ▼
   3. Filter by @Conditional* — ⭐ most are discarded here, cheaply
              ▼
   4. Sort by @AutoConfigureBefore / @AutoConfigureAfter / @AutoConfigureOrder
              ▼
   5. Register the survivors as ordinary @Configuration classes
              ▼
   6. Process them LAST — after all user configuration ⭐
```

**Step 6 is the one that makes the whole design work**, and it explains a behaviour you have already
relied on: because auto-configuration runs *after* your beans are registered,
`@ConditionalOnMissingBean` reliably sees whatever you defined. **That is why "declare your own and
Boot backs off" is dependable in auto-configuration and fragile in your own code** (Day 135).

## The imports file

```
# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.jackson.JacksonAutoConfiguration
org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
…
```

**Plain text, one class name per line.** That is the entire discovery mechanism — no scanning, no
annotation magic.

⚠️ **Boot 3 moved this.** Boot 2 used `META-INF/spring.factories` with an
`EnableAutoConfiguration=` key; Boot 3 uses the file above. A Boot-2-era custom starter **silently
contributes nothing** under Boot 3 — no error, the beans simply never appear (Day 185B).

**Open the file yourself:**

```bash
unzip -p ~/.m2/repository/org/springframework/boot/spring-boot-autoconfigure/*/*.jar \
  META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports | head -40
```

**Do this today.** Seeing the list as an ordinary text file is what converts "Boot magically knows"
into "Boot reads a file".

## Why it is fast despite ~150 candidates

Loading 150 configuration classes would be slow, so Boot short-circuits:

**`spring-autoconfigure-metadata.properties`** — generated at build time — records each candidate's
`@ConditionalOnClass` requirements as *strings*. Boot checks those against the classpath **without
loading the class**, discarding most candidates before any bytecode is read.

**That is why `@ConditionalOnClass` is the first condition on almost every auto-configuration
class**: it is the cheap filter. The expensive conditions run only on survivors.

# Part 2 — Reading an auto-configuration class

```java
@AutoConfiguration(after = DataSourceAutoConfiguration.class)      // ⭐ ordering
@ConditionalOnClass({ JdbcTemplate.class, DataSource.class })      // ⭐ cheap classpath check
@ConditionalOnSingleCandidate(DataSource.class)                    // exactly one DataSource
@EnableConfigurationProperties(JdbcProperties.class)               // Day 131
public class JdbcTemplateAutoConfiguration {

    @Bean
    @Primary
    @ConditionalOnMissingBean(JdbcOperations.class)                // ⭐ back off if the user has one
    JdbcTemplate jdbcTemplate(DataSource dataSource, JdbcProperties properties) {
        JdbcTemplate template = new JdbcTemplate(dataSource);
        template.setFetchSize(properties.getTemplate().getFetchSize());
        return template;
    }
}
```

**Read this as a sentence:** *if `JdbcTemplate` is on the classpath and exactly one `DataSource`
bean exists and the user has not defined a `JdbcOperations`, create a `JdbcTemplate` configured from
`spring.jdbc.*` properties — and do it after the `DataSource` auto-configuration has run.*

**Every Boot auto-configuration class reads this way.** They are short, they are on your classpath,
and you can open any of them in your IDE — which is the most effective way to answer "what did Boot
actually do?"

## The conditions

| Condition | Registers when |
|---|---|
| `@ConditionalOnClass` | ⭐ A class is present — the cheap first filter |
| `@ConditionalOnMissingClass` | It is absent |
| `@ConditionalOnBean` | Another bean exists |
| `@ConditionalOnMissingBean` | ⭐ It does not — the user-override mechanism |
| `@ConditionalOnSingleCandidate` | Exactly one, or one `@Primary` |
| `@ConditionalOnProperty` | A property has a value |
| `@ConditionalOnResource` | A file exists on the classpath |
| `@ConditionalOnWebApplication` | Servlet or reactive web app |
| `@ConditionalOnExpression` | A SpEL expression is true (Day 138) |
| `@ConditionalOnJava` | A Java version range |
| `@ConditionalOnCloudPlatform` | Running on Kubernetes, Heroku, … |

```java
@ConditionalOnProperty(prefix = "app.feature", name = "enabled",
                       havingValue = "true", matchIfMissing = true)   // ⭐ default ON when absent
```

`matchIfMissing = true` is how a feature is on by default but can be switched off — a small detail
that appears throughout Boot.

## ⭐ Ordering

```java
@AutoConfiguration(after = DataSourceAutoConfiguration.class)
@AutoConfiguration(before = WebMvcAutoConfiguration.class)
@AutoConfigureOrder(Ordered.HIGHEST_PRECEDENCE)
```

**Ordering matters because `@ConditionalOnBean` and `@ConditionalOnMissingBean` are evaluated against
what has been registered so far.** A condition asking "does a `DataSource` exist?" gives a different
answer depending on whether `DataSourceAutoConfiguration` has run.

> ⚠️ **Never use `@ConditionalOnBean` or `@ConditionalOnMissingBean` in your own `@Configuration`
> classes.** Boot's auto-configuration is explicitly ordered and runs last, so the conditions are
> reliable there. Your configuration has no such guarantee, and the behaviour becomes dependent on
> registration order — which changes when someone adds a class. Use `@ConditionalOnProperty` instead
> (Day 135).

# Part 3 — Debugging it

## The conditions report

```bash
java -jar app.jar --debug
```

```
============================
CONDITIONS EVALUATION REPORT
============================

Positive matches:
-----------------
   JacksonAutoConfiguration#jacksonObjectMapper matched:
      - @ConditionalOnMissingBean (types: com.fasterxml.jackson.databind.ObjectMapper)
        did not find any beans (OnBeanCondition)

Negative matches:
-----------------
   RedisAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class
           'org.springframework.data.redis.core.RedisOperations' (OnClassCondition)

Exclusions:
-----------
   org.springframework.boot.autoconfigure.security.servlet.SecurityAutoConfiguration

Unconditional classes:
----------------------
   org.springframework.boot.autoconfigure.context.ConfigurationPropertiesAutoConfiguration
```

**Four sections, and each answers a different question:**

| Section | Answers |
|---|---|
| **Positive matches** | Why does this bean exist? |
| **Negative matches** | ⭐ Why is this bean *missing*? |
| **Exclusions** | What did I switch off? |
| **Unconditional** | What always runs? |

> **"Negative matches" is the section to read first when something is missing**, and it tells you
> exactly which condition failed. Almost every "why isn't Spring doing X?" question is answered
> there in under a minute.

Programmatically:

```java
ConditionEvaluationReport report = ConditionEvaluationReport.get(
        (ConfigurableListableBeanFactory) ctx.getBeanFactory());
report.getConditionAndOutcomesBySource()
      .forEach((source, outcomes) -> outcomes.forEach(o ->
          System.out.println(source + " → " + o.getOutcome())));
```

## The four ways to influence it

```java
// 1. Exclude a whole auto-configuration
@SpringBootApplication(exclude = { DataSourceAutoConfiguration.class })
```
```properties
spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
```
```java
// 2. ⭐ Define the bean yourself — @ConditionalOnMissingBean backs off. The usual answer.
@Bean DataSource dataSource() { … }

// 3. Set a property — many auto-configurations are property-gated
```
```properties
spring.jpa.open-in-view=false          # Day 139
```
```java
// 4. Customise rather than replace                                   (Day 139)
@Bean Jackson2ObjectMapperBuilderCustomizer customizer() { … }
```

**Option 2 is almost always the right one.** Excluding an auto-configuration is a blunt instrument —
it removes *everything* it contributed, including things you did want.

⚠️ **`exclude` on a class that is not on the classpath fails the startup.** Use
`spring.autoconfigure.exclude` (string-based) for optional dependencies.

# Part 4 — Writing your own

The complete shape, and it is small:

```java
// 1. Typed, validated properties                                     (Day 131)
@ConfigurationProperties(prefix = "acme.notifications")
@Validated
public record NotificationProperties(
        @DefaultValue("true") boolean enabled,
        @NotBlank String apiUrl,
        @DefaultValue("5s") Duration timeout) { }

// 2. The auto-configuration
@AutoConfiguration
@ConditionalOnClass(NotificationSender.class)
@ConditionalOnProperty(prefix = "acme.notifications", name = "enabled",
                       havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(NotificationProperties.class)
public class NotificationAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                                 // ⭐ the user can override
    NotificationSender notificationSender(NotificationProperties props,
                                          RestClient.Builder builder) {
        return new HttpNotificationSender(builder.baseUrl(props.apiUrl()).build(), props);
    }
}
```

```
# 3. src/main/resources/META-INF/spring/
#    org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.notifications.NotificationAutoConfiguration
```

```json
// 4. OPTIONAL but excellent: additional-spring-configuration-metadata.json
{ "properties": [ { "name": "acme.notifications.timeout",
                    "type": "java.time.Duration",
                    "description": "Timeout for notification API calls.",
                    "defaultValue": "5s" } ] }
```

**That metadata file gives IDE autocompletion and inline documentation for your properties** in
`application.yml` — a small effort with a large usability return, and the reason Boot's own
properties autocomplete.

**The five rules for a well-behaved auto-configuration:**

1. **Always `@ConditionalOnMissingBean`** on every bean — never take a decision away from the user.
2. **Guard with `@ConditionalOnClass`** so the module is safe to have on the classpath unused.
3. **Provide a property to disable it** entirely.
4. **Order explicitly** with `after`/`before` if you depend on other auto-configuration.
5. **Ship the metadata JSON.**

# Part 5 — What auto-configuration costs

| Cost | Detail |
|---|---|
| **Startup time** | ~150 candidates evaluated; metadata filtering keeps it to ~100–300 ms |
| **Hidden beans** | Behaviour with no declaration in your codebase |
| **Debugging distance** | The cause of a problem may be in a jar you never opened |
| **Ordering subtleties** | Condition outcomes depend on evaluation order |
| **Version coupling** | An auto-configuration's behaviour changes across Boot versions |

**That last one is worth an example**, because it is a real upgrade hazard: Boot 2.6 disabled
circular references (Day 131), Boot 2.7 restructured the imports mechanism, and Boot 3.0 moved to
Jakarta (Day 185B). **Auto-configuration means a Boot upgrade can change behaviour you never
configured** — which is why upgrade release notes matter more in Boot than in most frameworks.

**Boot 3's AOT processing** resolves conditions at *build* time and generates explicit bean
registrations, eliminating both the runtime evaluation and the reflection — which is what makes
GraalVM native images possible (Day 185B). The trade is that anything determined at runtime, such as
a profile-dependent condition, must be fixed at build time instead.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Treating auto-configuration as magic | Cannot debug it |
| Not reading `--debug` when a bean is missing | Guessing instead of reading the answer |
| `@ConditionalOnBean`/`OnMissingBean` in your own config | Order-dependent, fragile behaviour |
| Excluding an auto-configuration to change one bean | Removes everything else it contributed |
| `exclude` on an absent class | Startup failure — use the property form |
| Boot 2 `spring.factories` in a Boot 3 starter | Contributes nothing, silently |
| Custom auto-config without `@ConditionalOnMissingBean` | Users cannot override you |
| No disable property | The module cannot be switched off |
| No metadata JSON | No IDE support for your properties |
| Assuming behaviour is stable across Boot versions | Upgrades change unconfigured behaviour |

## Interview questions

**Q: How does auto-configuration work?**
`@EnableAutoConfiguration` imports a selector that reads a plain-text imports file from every jar on
the classpath, filters the ~150 candidates by their `@Conditional` annotations, sorts them, and
registers the survivors as ordinary `@Configuration` classes — processed *after* all user
configuration.

**Q: Why does it run last?**
So `@ConditionalOnMissingBean` reliably sees anything you defined. That ordering is what makes
"declare your own and Boot backs off" dependable, and it is why the same conditions are unreliable in
your own configuration classes.

**Q: How is it fast with 150 candidates?**
A build-time metadata file records each candidate's `@ConditionalOnClass` requirements as strings, so
Boot checks the classpath without loading classes and discards most candidates before reading any
bytecode.

**Q: How do you override a Boot-configured bean?**
Define your own — `@ConditionalOnMissingBean` makes the auto-configuration back off. Prefer a
`*Customizer` where one exists, and avoid excluding the whole auto-configuration, which removes
everything else it contributed.

**Q: How do you find out why a bean is missing?**
Run with `--debug` and read the negative matches section of the conditions evaluation report, which
names the exact condition that failed.

**Q: Why should you not use `@ConditionalOnMissingBean` in your own configuration?**
It is evaluated against what has been registered so far, and your configuration has no guaranteed
ordering — so the outcome changes when someone adds a class. Boot's auto-configuration is explicitly
ordered and runs last, which is why it is safe there.

**Q: What changed in Boot 3 about custom starters?**
The registration file moved from `META-INF/spring.factories` to
`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`. A Boot 2 starter
silently contributes nothing under Boot 3.

**Q: What does AOT processing change?**
Conditions are evaluated at build time and explicit bean registrations are generated, removing
runtime condition evaluation and reflection — which enables GraalVM native images, at the cost of
fixing anything runtime-dependent at build time.

## 🎙️ Articulation drill

Two minutes: **"How does Spring Boot know to configure a `DataSource`?"**

Walk the mechanism: `@EnableAutoConfiguration` imports a selector that reads a plain-text file from
every jar, `DataSourceAutoConfiguration` is a candidate, `@ConditionalOnClass` sees a JDBC driver on
the classpath, `@ConditionalOnMissingBean` sees you have not defined one, and the properties come
from `spring.datasource.*`. Then close with how you would *prove* it — `--debug` and the conditions
report. Explaining it as a file and a set of conditions, rather than as magic, is the whole point.
