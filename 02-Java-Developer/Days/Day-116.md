# Day 116

**L-116** · OAuth 2.0 — the four grants, authorization code + PKCE, why implicit died

**Time:** 3 hrs · **Mode:** NEW

> OAuth is the most misunderstood protocol in web development, and the misunderstanding starts with
> its name. **OAuth 2.0 is an *authorization* framework, not an authentication protocol** — it was
> designed to let an application access data on a user's behalf, not to log the user in. Using it for
> login is what OpenID Connect (tomorrow) exists to fix.
>
> Get that sentence right and everything else follows.

---

# Part 1 — The problem it solves

Before OAuth, an application that wanted your Gmail contacts asked for your Gmail password.

That is catastrophic in five separate ways: the application sees your password, it gets **all** your
permissions rather than the one it needs, you cannot revoke it without changing your password,
revoking breaks every other application, and you have no record of what accessed what.

**OAuth replaces "give me your password" with "ask the provider to grant limited, revocable access".**

```
   Resource Owner   the USER who owns the data
   Client           the APPLICATION requesting access          ⚠️ "client" = the app, not the browser
   Authorization    issues tokens after the user consents      (accounts.google.com)
     Server
   Resource Server  holds the data, accepts the token          (gmail.googleapis.com)
```

**"Client" meaning the application, not the user's browser, is the single biggest source of
confusion** in every OAuth conversation. Fix it now.

# Part 2 — The Authorization Code flow with PKCE

**This is the flow. Learn this one properly and the others are footnotes.**

```
User          Client App              Auth Server           Resource Server
 │                │                        │                      │
 │  "Log in"      │                        │                      │
 │───────────────►│                        │                      │
 │                │ generate code_verifier (random 43-128 chars)   │
 │                │ code_challenge = BASE64URL(SHA256(verifier))   │
 │                │                        │                      │
 │  redirect to auth server ──────────────►│                      │
 │     ?client_id=…&redirect_uri=…&scope=…&state=…                │
 │      &code_challenge=…&code_challenge_method=S256              │
 │                │                        │                      │
 │◄── login page + CONSENT SCREEN ─────────│                      │
 │─── approves ───────────────────────────►│                      │
 │                │                        │                      │
 │◄── redirect to redirect_uri?code=AUTH_CODE&state=… ────────────│
 │───────────────►│                        │                      │
 │                │  POST /token           │                      │
 │                │  code, client_id, client_secret, code_verifier│
 │                │───────────────────────►│                      │
 │                │                        │ SHA256(verifier) == challenge?
 │                │◄── access_token, refresh_token ───────────────│
 │                │                        │                      │
 │                │  GET /data  Authorization: Bearer …  ────────►│
```

## Why two round trips instead of one

The obvious design — return the token directly to the browser — is exactly what the **implicit grant**
did, and it is why the implicit grant is dead.

**The authorization code is a one-time, short-lived (≈30–60 s) value that is useless on its own.**
Exchanging it for a token requires the **client secret**, which only the server has. So even if the
code leaks — in browser history, in a `Referer` header, in a proxy log — an attacker cannot redeem
it.

**The token never touches the browser's URL bar or its history.** That is the entire point.

## `state` — CSRF protection for the flow

```java
String state = randomUrlSafe(32);
session.put("oauth_state", state);         // or an HttpOnly cookie
// ... on callback:
if (!state.equals(session.remove("oauth_state"))) throw new SecurityException("CSRF");
```

Without `state`, an attacker starts an OAuth flow with **their own** account, captures the resulting
callback URL, and tricks the victim into visiting it — **linking the attacker's account to the
victim's session**. The victim then unknowingly operates on the attacker's data, or the attacker
gains access to whatever the victim subsequently stores.

`state` is mandatory. It is also a convenient place to carry the return path, but its purpose is
CSRF.

## ⭐ PKCE — Proof Key for Code Exchange

```
1. Client generates:  code_verifier   = 43–128 random URL-safe characters
2. Client computes:   code_challenge  = BASE64URL(SHA256(code_verifier))
3. Authorization request carries the CHALLENGE
4. Token request carries the VERIFIER
5. Auth server checks SHA256(verifier) == stored challenge
```

**The attack it prevents:** on mobile, `redirect_uri` is a custom scheme (`myapp://callback`) and a
malicious application can register the same scheme. It intercepts the redirect, steals the
authorization code, and redeems it — because a mobile app cannot keep a client secret (it ships
inside the binary, and anyone can extract it).

With PKCE, the stolen code is useless: the attacker does not have the verifier, and the challenge was
sent over a separate channel they never saw.

> **PKCE is now recommended for *all* clients, including confidential server-side ones** (OAuth 2.0
> Security BCP; mandatory in OAuth 2.1). It costs almost nothing and defends against code
> interception generally.

**Always `S256`, never `plain`.** The `plain` method sends the verifier as the challenge, which
defeats the entire mechanism.

# Part 3 — The grants

| Grant | For | Status |
|---|---|---|
| **Authorization Code + PKCE** | Web apps, SPAs, mobile, everything | ✅ **the answer** |
| **Client Credentials** | Machine-to-machine, no user involved | ✅ correct in its niche |
| **Device Code** | TVs, CLIs, input-constrained devices | ✅ |
| Refresh Token | Renewing an access token (Day 115) | ✅ |
| ~~Implicit~~ | SPAs, historically | ❌ **removed in OAuth 2.1** |
| ~~Resource Owner Password~~ | Trusted first-party apps | ❌ **removed in OAuth 2.1** |

## Client Credentials — no user at all

```http
POST /token
grant_type=client_credentials&client_id=…&client_secret=…&scope=orders:read
```

The application authenticates **as itself**. There is no user, no consent screen, no refresh token —
you simply request a new one when it expires. This is Day 115b's machine-to-machine case, done
through OAuth rather than a static API key, and it is the right choice when a central authorization
server already exists.

## Device Code — for things with no keyboard

```
1. Device: POST /device/code  → { device_code, user_code: "WDJB-MJHT",
                                  verification_uri: "https://acme.com/activate" }
2. Device displays: "Go to acme.com/activate and enter WDJB-MJHT"
3. User does this on their phone
4. Device polls POST /token with device_code until it succeeds
```

Every smart TV login you have ever done. The polling must **respect the `interval` and back off on
`slow_down`** — otherwise you are hammering the auth server (Day 123).

## ❌ Why the implicit grant died

```http
GET /authorize?response_type=token&…
→ 302 https://app.com/callback#access_token=eyJhbGc...       ← the TOKEN, in the URL fragment
```

Four fatal problems:

1. **The token appears in the URL** — browser history, `Referer` headers, server logs, screen shares.
2. **No client authentication**, so the auth server cannot verify who is asking.
3. **No refresh token** could safely be issued, forcing long-lived access tokens.
4. **Vulnerable to token injection** — an attacker's token can be substituted into another user's
   session.

It existed because browsers had no CORS support for cross-origin token requests. **Once CORS was
universal, authorization code + PKCE became viable for SPAs and implicit had no remaining
justification.** That is the historical answer, and giving it is what distinguishes understanding
from memorisation.

## ❌ Why Resource Owner Password Credentials died

```http
POST /token
grant_type=password&username=ram&password=hunter2
```

The application handles the user's password — **which is the exact thing OAuth exists to avoid.** It
also cannot support MFA, cannot support federated identity, and trains users to type their password
into third-party applications.

# Part 4 — Scopes, tokens and consent

## Scopes

```
scope=orders:read orders:write profile:read
```

Space-separated strings whose meaning **you define**. The rules:

**Granular, but not absurd.** `orders:read` and `orders:write`, not `read` and not
`orders:read:line_items:price`.

**Show them to the user in plain language.** "This app wants to read your orders" — not
`orders:read`. The consent screen is a security control, and an unreadable one is not.

**Enforce them on every request**, not only at issuance:

```java
if (!token.scopes().contains("orders:write")) throw new ForbiddenException();
```

> ⚠️ **A scope is not a permission.** `orders:write` means *the user allowed this app to write
> orders* — it does not mean *this user may write this particular order*. **You still need
> per-resource authorization** (Day 111). Conflating them is a real and common vulnerability: an
> application with a valid `orders:write` token writing to *someone else's* order.

## Token types

**Opaque** — a random string; the resource server calls an **introspection** endpoint (RFC 7662) to
validate. Instantly revocable; costs a network call per request.

**JWT** — self-contained, verified locally with a public key from JWKS (Day 114). Fast; not
instantly revocable.

**The hybrid most large providers use:** JWTs with a short lifetime *plus* introspection for
high-value operations. Google's access tokens are opaque; Auth0's are JWTs.

## Redirect URI validation — the most-attacked parameter

```java
// ❌ every one of these is exploitable
if (redirectUri.startsWith("https://app.acme.com"))    // https://app.acme.com.evil.com ✓ passes
if (redirectUri.contains("acme.com"))                   // https://evil.com/?x=acme.com  ✓ passes

// ✅ EXACT match against a pre-registered list
if (!registeredUris.contains(redirectUri)) throw new SecurityException();
```

**Exact string matching against a pre-registered allow-list. No wildcards, no prefixes, no
subdomains, no path suffixes.** An open redirect here means the authorization code is delivered to
the attacker, and every other protection in the flow is bypassed.

This is Day 108's allow-list rule at the highest possible stakes.

# Part 5 — Security summary

| Threat | Defence |
|---|---|
| CSRF on the callback | `state`, verified on return |
| Authorization code interception | **PKCE with `S256`** |
| Code delivered to an attacker | **Exact** `redirect_uri` matching |
| Token in browser history | Authorization code flow — never implicit |
| Token theft via XSS | Access token in memory, refresh in `HttpOnly` (Day 115) |
| Over-broad access | Minimal scopes, enforced per request |
| Confused deputy | ✅ Validate `aud` on the token (Day 114) |
| Replay of a code | One-time use, ≈60-second expiry |
| Mix-up between auth servers | `iss` in the authorization response (RFC 9207) |
| Client secret in a public client | PKCE — public clients have **no** secret |

**"Public" versus "confidential" client** is the distinction to be precise about: a confidential
client (a server-side application) can keep a secret; a public client (SPA, mobile, desktop) cannot,
because the code ships to the user. **A public client must never have a client secret** — putting one
in a mobile app or a JavaScript bundle is not a mitigation, it is a published secret. PKCE is what
replaces it.

## Being an OAuth client, practically

```java
// 1. Redirect
String verifier = randomUrlSafe(64);
session.put("pkce_verifier", verifier);
String state = randomUrlSafe(32);
session.put("oauth_state", state);

String url = authServer + "/authorize?" + params(
    "response_type", "code",
    "client_id",     clientId,
    "redirect_uri",  exactRegisteredUri,
    "scope",         "orders:read",
    "state",         state,
    "code_challenge", base64Url(sha256(verifier)),
    "code_challenge_method", "S256");

// 2. Callback — validate BEFORE anything else
if (!state.equals(session.remove("oauth_state"))) throw new SecurityException("state mismatch");
if (params.containsKey("error")) handleDenial(params.get("error"));

// 3. Exchange — server-side only, over TLS
TokenResponse tokens = http.post(authServer + "/token", form(
    "grant_type",    "authorization_code",
    "code",          params.get("code"),
    "redirect_uri",  exactRegisteredUri,          // must MATCH the authorize request
    "client_id",     clientId,
    "client_secret", clientSecret,                // confidential clients only
    "code_verifier", session.remove("pkce_verifier")));
```

**Use a library.** `spring-security-oauth2-client`, AppAuth, or your provider's SDK. Hand-rolling
OAuth is how the vulnerabilities in the table above get shipped — the flow has too many places where
a missing check is silently exploitable.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Treating OAuth as authentication | You do not know *who* the user is — use OIDC (Day 117) |
| Confusing "client" with the browser | Every subsequent sentence is wrong |
| Omitting or not verifying `state` | Account linking via CSRF |
| No PKCE | Authorization code interception, especially on mobile |
| `code_challenge_method=plain` | PKCE provides nothing |
| Prefix or substring `redirect_uri` matching | The code is delivered to the attacker |
| Client secret in a mobile app or SPA | A published secret |
| Using the implicit grant | Token in the URL; no client authentication |
| Using the password grant | Defeats OAuth's purpose; blocks MFA |
| Treating a scope as a permission | Cross-user access with a valid token |
| Not validating `aud` | A token for another service is accepted |
| Ignoring `slow_down` when polling the device flow | Hammering the auth server |
| Hand-rolling the protocol | A missing check that is silently exploitable |

## Interview questions

**Q: What problem does OAuth 2.0 solve?**
Delegated authorization: letting an application access a limited, revocable subset of a user's data
at another service, without the user handing over their password.

**Q: Is OAuth authentication?**
No. It is an authorization framework — an access token says an app may access a resource, not who the
user is. OpenID Connect is the authentication layer built on top.

**Q: Walk me through the authorization code flow with PKCE.**
Client generates a verifier and sends its SHA-256 challenge with the authorization request plus a
`state`; the user authenticates and consents; the auth server redirects back with a short-lived
one-time code; the client exchanges the code, the client secret if it has one, and the verifier for
tokens. The auth server checks that the hashed verifier matches the challenge.

**Q: Why does the code exist instead of returning the token directly?**
So the token never appears in the browser's URL, history or `Referer` headers. The code is
short-lived, single-use, and unusable without the client secret or the PKCE verifier.

**Q: What does `state` prevent?**
CSRF on the callback — an attacker completing a flow with their own account and tricking the victim
into using the resulting callback, linking the attacker's account to the victim's session.

**Q: What does PKCE prevent, and why is it now recommended everywhere?**
Authorization code interception — originally by a malicious mobile app registering the same custom
URI scheme. It is recommended for all clients because it defends against code interception generally
at almost no cost, and it is mandatory in OAuth 2.1.

**Q: Why did the implicit grant die?**
The token was returned in the URL fragment — exposed in history, `Referer` and logs — with no client
authentication and no safe refresh token. Once CORS was universally available, authorization code
with PKCE worked for SPAs and implicit had no justification left.

**Q: How should `redirect_uri` be validated?**
Exact string matching against pre-registered URIs. Prefix or substring matching is exploitable, and a
successful attack delivers the authorization code to the attacker.

**Q: Is a scope a permission?**
No. A scope records what the *user allowed the application* to do; it says nothing about whether that
user may act on a specific resource. Per-resource authorization is still required.
