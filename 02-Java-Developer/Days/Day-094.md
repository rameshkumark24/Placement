> Structural patterns are about **composing objects into larger structures**. You have used four of

> all wrap an object, and the difference is *intent*.

# Part 1 — The four wrappers, distinguished

This table is the single most useful thing in the day. All four wrap; the intent differs:

| Pattern | Interface vs the wrapped object | Intent |
|---|---|---|
| **Adapter** | **Different** | Make an incompatible interface usable |
| **Decorator** | **Same** | Add behaviour, keep the contract |
| **Facade** | **Simpler / new** | Hide complexity behind one entry point |
| **Proxy** | **Same** | Control *access* — lazily, remotely, or with checks |

Decorator and Proxy both keep the same interface, so their distinction is subtler: **Decorator adds
capability; Proxy controls access.** A `BufferedInputStream` adds buffering; an
`unmodifiableList` denies writes.

---

## Adapter

```java
// You have this — a third-party library you cannot change
public class LegacyXmlPaymentGateway {
    public String submitPayment(String xmlRequest) { … }
}

// Your system speaks this
public interface PaymentGateway {
    Receipt charge(Customer customer, Money amount);
}

// The adapter
public class LegacyGatewayAdapter implements PaymentGateway {
    private final LegacyXmlPaymentGateway legacy;

    @Override
    public Receipt charge(Customer customer, Money amount) {
        String xml = toXml(customer, amount);
        String response = legacy.submitPayment(xml);
        return parseReceipt(response);                 // translation lives HERE, in one place
    }
}
```

**The value is containment.** Without the adapter, XML-building leaks into your domain logic and
every caller depends on the legacy shape. With it, exactly one class knows about XML — and swapping
providers means writing one new adapter.

This is also Day 075's rule "do not mock types you do not own" in structural form: **wrap the
third-party type in your own interface, mock your interface, and integration-test the adapter.**

`Arrays.asList` and `InputStreamReader` (bytes → characters, Day 063) are JDK adapters.

---

## Decorator

Wrap an object in another with **the same interface**, adding behaviour. Composable at runtime, in
any order.

```java
var in = new DataInputStream(
             new BufferedInputStream(
                 new GZIPInputStream(
                     new FileInputStream("data.gz"))));
```

Day 063 introduced this; now it has a name. The properties that make it powerful:

- **Any combination**, chosen at runtime — 4 decorators give 16 behaviours from 4 classes, versus 16
  subclasses.
- **Order matters and is meaningful** — encrypt-then-compress and compress-then-encrypt are
  different, and the composition expresses which.
- **It is Day 092's composition-over-inheritance argument** in its purest form.

Writing one:

```java
public interface Notifier { void send(String message); }

public class EmailNotifier implements Notifier { … }                    // the component

public abstract class NotifierDecorator implements Notifier {
    protected final Notifier wrapped;
    protected NotifierDecorator(Notifier wrapped) { this.wrapped = wrapped; }
}

public class RetryingNotifier extends NotifierDecorator {
    public void send(String m) { withRetry(3, () -> wrapped.send(m)); }   // Day 062
}
public class RateLimitedNotifier extends NotifierDecorator {
    private final Semaphore permits;                                       // Day 070
    public void send(String m) { permits.acquire(); try { wrapped.send(m); } finally { … } }
}
public class AuditedNotifier extends NotifierDecorator {
    public void send(String m) { audit.record(m); wrapped.send(m); }
}

Notifier n = new RetryingNotifier(new RateLimitedNotifier(new AuditedNotifier(new EmailNotifier())));
```

**The cost**, which you should state: a stack of decorators produces deep, confusing stack traces and
makes debugging harder — you cannot tell from a variable's type what is actually in the chain. Keep
chains short.

---

## Facade

One simplified entry point over a complicated subsystem.

```java
// Without: the caller must know six classes and their correct ordering
VideoFile file = new VideoFile(name);
Codec codec = CodecFactory.extract(file);
BitrateReader reader = new BitrateReader(file, codec);
Buffer buffer = reader.read(0, file.length());
Buffer result = new AudioMixer().fix(buffer);
new File(result).save(target);

// With
public class VideoConverter {
    public File convert(String filename, Format target) { … }     // one method
}
```

The distinction from Adapter: **Adapter makes an incompatible interface usable; Facade makes a
complicated one convenient.** Adapter is forced on you by mismatch; Facade is a choice about
ergonomics.

**The failure mode:** a facade that becomes the only way in, grows every method anyone needs, and
turns into a god object. Keep the subsystem accessible for advanced use — a facade should be a
convenience, not a wall.

`java.net.http.HttpClient` is a facade over sockets, TLS, connection pooling and HTTP framing.

## Proxy

Same interface, controls access. Four common kinds:

| Kind | Purpose | Example |
|---|---|---|
| **Virtual** | Defer expensive creation | Hibernate lazy loading |
| **Protection** | Access control | `unmodifiableList`, security checks |
| **Remote** | Stand in for a remote object | RMI, gRPC stubs, Feign clients |
| **Smart/Caching** | Add caching, reference counting, logging | Spring `@Cacheable` |

```java
public class CachingImageProxy implements Image {
    private final String path;
    private HighResImage real;                  // not loaded until needed

    @Override public void display() {
        if (real == null) real = new HighResImage(path);      // virtual proxy
        real.display();
    }
}
```

Day 056A built a **dynamic proxy** and used it to explain Spring's `@Transactional`. That connection
is worth restating, because it is one of the highest-value facts in this whole roadmap:

> **Spring's `@Transactional`, `@Cacheable`, `@Async` and `@PreAuthorize` are all proxies.** Which is
> why **self-invocation does not work**: `this.method()` calls the target directly and bypasses the
> proxy entirely, so the annotation does nothing. Day 137 will ask this; you already have the answer.

Hibernate's lazy loading is a virtual proxy, which is also why `LazyInitializationException` happens
outside a session — the proxy is there, the session it needs is not.

## Composite

Treat individual objects and compositions of them **uniformly**, through one interface.

```java
public interface FileSystemNode {
    String name();
    long size();
}

public record FileNode(String name, long size) implements FileSystemNode { }

public class DirectoryNode implements FileSystemNode {
    private final String name;
    private final List<FileSystemNode> children = new ArrayList<>();

    @Override public long size() {
        return children.stream().mapToLong(FileSystemNode::size).sum();   // recursion, uniform
    }
    public DirectoryNode add(FileSystemNode child) { children.add(child); return this; }
}
```

**The point is that the client does not branch.** `node.size()` works whether `node` is one file or a
directory tree ten levels deep — no `instanceof`, no special-casing.

Everywhere you have already met it: the **DOM** (Day 012), Swing/JavaFX component trees, an
expression AST, a menu hierarchy, an org chart.

Two design decisions: put child-management methods on the composite only (type-safe, but the client
must know which is which) or on the shared interface (uniform, but `FileNode.add()` must throw — an
LSP violation, Day 091). **Prefer type safety** unless uniformity is genuinely the requirement.

## Flyweight and Bridge — brief

**Flyweight** — share intrinsic (immutable, common) state across many instances, keep extrinsic
(per-instance) state outside. `Integer.valueOf`'s cache (Day 028) and the string pool (Day 029) are
flyweights. Relevant when you have millions of similar objects; irrelevant otherwise.

**Bridge** — separate an abstraction hierarchy from its implementation hierarchy so both can vary
independently. `Shape` × `Renderer` gives 3+3 classes instead of 9 subclasses. It is Day 092's
combinatorial argument, structurally. JDBC is the textbook example: `java.sql` is the abstraction,
each vendor's driver the implementation.

# Part 2 — D-06 · Relational algebra

## Why bother

SQL is a *surface syntax* over relational algebra. The optimiser (Day 078's D-01) rewrites your query
into an algebra expression, transforms it using algebraic equivalences, and picks a plan. **Knowing
the algebra is knowing what the optimiser is allowed to do** — which is why Stage 5's query tuning
will make sense instead of being folklore.

## The six primitive operators

| Operator | Symbol | SQL | Does |
|---|---|---|---|
| **Selection** | σ (sigma) | `WHERE` | Choose **rows** |
| **Projection** | π (pi) | `SELECT` cols | Choose **columns** — and *removes duplicates* |
| **Union** | ∪ | `UNION` | Rows in either (set: deduplicates) |
| **Set difference** | − | `EXCEPT` | Rows in the first, not the second |
| **Cartesian product** | × | `CROSS JOIN` | Every pairing |
| **Rename** | ρ (rho) | `AS` | Rename a relation or attribute |

Everything else is derived: **intersection**, **join** (σ over ×), **division**, and the outer joins.

```
σ(salary > 50000)(employee)                              SELECT * FROM employee WHERE salary > 50000
π(name, dept)(employee)                                  SELECT DISTINCT name, dept FROM employee
employee ⋈(employee.dept_id = dept.id) dept              INNER JOIN
π(name)(σ(salary > 50000)(employee ⋈ dept))              the whole query
```

**Two facts SQL hides**, and both are standard interview material:

**Projection eliminates duplicates in the algebra; `SELECT` does not.** Because relations are sets
and SQL tables are bags (Day 081's D-02). That is precisely why `DISTINCT` exists as a keyword.

**A join is definitionally a selection over a Cartesian product.** `A ⋈θ B = σθ(A × B)`. No database
executes it that way — that would be O(n×m) — but the *meaning* is that, which is why an accidental
missing join condition produces a cross join and an explosion of rows rather than an error.

## Join types

```
Natural join    A ⋈ B          join on all same-named attributes.  ⚠️ Never use in production SQL:
                                adding a column changes the query's meaning silently.
Theta join      A ⋈θ B         any predicate
Equi-join       A ⋈(a=b) B     equality predicate
Left outer      A ⟕ B          all of A, nulls where B has no match
Right outer     A ⟖ B
Full outer      A ⟗ B
Semi-join       A ⋉ B          rows of A that HAVE a match  →  EXISTS / IN
Anti-join       A ▷ B          rows of A with NO match      →  NOT EXISTS
```

**Semi- and anti-joins are worth knowing by name**, because they are what the optimiser turns
`EXISTS` and `NOT EXISTS` into — and they can stop scanning at the first match, which an equivalent
join-and-distinct cannot. That is why `EXISTS` often beats `IN` on large subqueries.

## The equivalences that make optimisation possible

These are the rewrites an optimiser applies. Each has a direct performance consequence:

```
1. Selection pushdown        σ(A ⋈ B)  ≡  σ(A) ⋈ σ(B)         when the predicate touches one side
2. Projection pushdown       π(A ⋈ B)  ≡  π(π(A) ⋈ π(B))
3. Selection commutes        σp(σq(R)) ≡ σq(σp(R))
4. Join associativity        (A ⋈ B) ⋈ C ≡ A ⋈ (B ⋈ C)
5. Join commutativity        A ⋈ B ≡ B ⋈ A
6. Conjunction split         σ(p AND q)(R) ≡ σp(σq(R))
```

**Selection pushdown is the single most important optimisation in databases.** Filter before you
join, and the join has far fewer rows to process:

```
π(name)( σ(dept.location='Chennai')( employee × dept ) )      -- 1M × 100 rows produced first
   ≡
π(name)( employee ⋈ σ(location='Chennai')(dept) )             -- filter to 3 rows, then join
```

Rules 4 and 5 are why **join order** is the optimiser's hardest decision: n tables have up to n!
orderings, and the cost difference between the best and worst is often several orders of magnitude.
This is what the statistics in Stage 5's `EXPLAIN` output are feeding.

## Division — the "for all" operator

The one that is hard to express in SQL and worth recognising:

> **"Find students who have taken *every* course."**

```
takes(student, course) ÷ course(course)
```

SQL has no `DIVIDE`, so it becomes a double-negation: *students for whom there does not exist a
course they have not taken.*

```sql
SELECT s.id FROM student s
WHERE NOT EXISTS (
    SELECT 1 FROM course c
    WHERE NOT EXISTS (
        SELECT 1 FROM takes t WHERE t.student_id = s.id AND t.course_id = c.id));
```

If a requirement contains **"for all"** or **"every"**, this is the shape. Recognising it saves you
from writing something subtly wrong with `COUNT`.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Confusing Adapter with Facade | Wrong reason to introduce a class |
| Confusing Decorator with Proxy | Both wrap; intent differs (add vs control) |
| Long decorator chains | Unreadable stack traces, hidden behaviour |
| A facade that becomes the only way in | God object |
| Expecting `@Transactional` to work on self-invocation | It is a proxy; `this.x()` bypasses it |
| Composite with `add()` on the leaf interface | Forced `UnsupportedOperationException` (LSP) |
| Flyweight for a few thousand objects | Complexity for nothing |
| Natural join in production SQL | A new column silently changes results |
| Assuming `SELECT` deduplicates | It does not — SQL tables are bags |
| Missing a join condition | Cartesian product, not an error |

## Interview questions

**Q: Adapter vs Decorator vs Facade vs Proxy?**
All wrap. Adapter changes the interface to make an incompatible type usable. Decorator keeps the
interface and adds behaviour. Facade presents a simpler interface over a subsystem. Proxy keeps the
interface and controls access — lazily, remotely, or with permission checks.

**Q: Give a JDK example of Decorator.**
`java.io` — `new BufferedInputStream(new GZIPInputStream(new FileInputStream(f)))`. Each layer is an
`InputStream` wrapping an `InputStream`, composable in any order at runtime.

**Q: Why does `@Transactional` not work when a method calls another method on the same object?**
Spring creates a proxy around the bean. External calls go through the proxy; `this.method()` calls
the target directly, so the proxy's transaction logic never runs.

**Q: What is Composite for?**
Treating a single object and a tree of objects uniformly, so the client has no `instanceof`
branching. The DOM and any file-system tree are examples.

**Q: What is relational algebra and why should you care?**
The formal operations SQL compiles to. Knowing it tells you which rewrites the optimiser may
perform — especially selection pushdown, join commutativity and associativity, which is what makes
join ordering the optimiser's hardest problem.

**Q: Why does `EXISTS` often beat `IN` on large subqueries?**
`EXISTS` becomes a semi-join, which can stop at the first match, while an equivalent join usually
must produce all matches and then deduplicate.

**Q: Difference between projection in algebra and `SELECT` in SQL?**
Projection eliminates duplicates because relations are sets; `SELECT` does not because SQL tables are
bags. That is why `DISTINCT` exists.
