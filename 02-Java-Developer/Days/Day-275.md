# Part 1 — Filters in the URL

```jsx
// ⭐⭐ the URL is the single source of truth for the query (Day 233)
function useOrderFilters() {
  const [params, setParams] = useSearchParams();
  const filters = {
    status: params.get("status") ?? "all",       // ⭐ ?? not || (Day 215)
    q:      params.get("q") ?? "",
    page:   Number(params.get("page") ?? 1),
    sort:   params.get("sort") ?? "createdAt,desc",
  };
  const set = (patch, { replace = false } = {}) =>
    setParams(p => {
      Object.entries(patch).forEach(([k, v]) =>
        v == null || v === "" ? p.delete(k) : p.set(k, String(v)));
      if (!("page" in patch)) p.delete("page");   // ⭐⭐ RESET PAGE ON FILTER
      return p;
    }, { replace });
  return { filters, set };
}
```

| ⭐ Detail | Why |
|---|---|
| **⭐⭐ Reset page on filter change** | Otherwise the user lands on page 7 of a 2-page result and sees an empty list — **a bug that reads as "your app is broken"** |
| **Debounce the search box** | ⭐ 300 ms. And `replace: true` so Back is not eleven presses (Day 233) |
| **Delete empty params** | ⭐⭐ Keeps the URL shareable and the cache key stable — `?status=` and no param must not be two cache entries |
| **⭐ Filters are the cache key** | `keys.orders.list(filters)` (Day 273) |

# Part 2 — ⭐⭐ Pagination, and the trap under it

```
⭐⭐ OFFSET vs CURSOR — AND THIS IS A **BACKEND** DECISION THE LIST
⭐   SCREEN FORCES YOU TO MAKE.

⭐   OFFSET (?page=3&size=20)
⭐     ✅ jump to any page, show "page 3 of 47"
⭐     ❌ ⭐⭐ SLOW ON DEEP PAGES — OFFSET 100000 MAKES POSTGRES SCAN
⭐        AND DISCARD 100,000 ROWS
⭐     ❌ ⭐⭐ ROWS SHIFT: a new order arrives, everything moves down
⭐        one, and ⭐ THE USER SEES THE SAME ROW ON PAGE 2 THAT THEY
⭐        SAW ON PAGE 1 — or never sees one at all.

⭐   CURSOR (?after=eyJpZCI6...)
⭐     ✅ ⭐ stable under inserts, fast at any depth
⭐     ❌ no page numbers, no jumping

⭐   ⇒ ⭐⭐ AND THE TRAP UNDER BOTH: **UNSTABLE SORT**.
⭐     ORDER BY created_at with ties ⇒ ⭐ POSTGRES MAY RETURN TIES IN
⭐     A DIFFERENT ORDER PER QUERY ⇒ ⭐⭐ ROWS DUPLICATE ACROSS PAGES
⭐     AND OTHERS VANISH, WITH NO ERROR ANYWHERE.
⭐     ⇒ ⭐⭐ **ALWAYS ORDER BY created_at DESC, id DESC.** A TIEBREAK
⭐       ON A UNIQUE COLUMN. This is a one-line fix for a bug that
⭐       looks like data corruption.
```

| ⭐ Use | When |
|---|---|
| **Offset** | ⭐ Admin tables, stable data, page numbers wanted |
| **⭐⭐ Cursor** | Feeds, anything append-heavy, infinite scroll |

> ⭐ **`SELECT count(*)` for "of 47 pages" is a second full scan.** For large tables, either drop the
> total, cache it, or use an estimate. **Say that trade rather than shipping a slow count.**

# Part 3 — ⭐⭐ The two empty states

```jsx
if (q.isPending)  return <TableSkeleton rows={10} />;   // ⭐ shaped like content
if (q.isError)    return <ErrorState error={q.error} onRetry={q.refetch} />;

if (q.data.items.length === 0) {
  return hasActiveFilters(filters)
    ? <EmptyState                                    // ⭐⭐ FILTERED TO ZERO
        title={`No orders match "${filters.q}"`}
        action={<Button onClick={clearFilters}>Clear filters</Button>} />
    : <EmptyState                                    // ⭐⭐ NEVER HAD ANY
        title="No orders yet"
        body="Orders appear here once a customer checks out."
        action={<Button onClick={createDemo}>Create a test order</Button>} />;
}
```

```
⭐⭐ WHY THIS ONE DETAIL IS WORTH A DAY OF ATTENTION

⭐   ⭐ SHOWING "No orders yet" TO SOMEONE WITH 500 ORDERS AND A BAD
⭐     FILTER IS A **REAL BUG** — the user concludes their data is
⭐     gone. ⭐⭐ IT IS ALSO THE SINGLE MOST COMMON MISSING DETAIL IN
⭐     A PORTFOLIO PROJECT, AND REVIEWERS NOTICE IT IMMEDIATELY
⭐     BECAUSE FILTERING TO ZERO IS THE FIRST THING THEY TRY.
```

| ⭐ Also | |
|---|---|
| **Keep filters visible when empty** | ⭐⭐ Hiding the filter bar on an empty result strands the user with no way back |
| **⭐ Show the result count** | "12 orders" — and `aria-live` so it is announced (Day 239) |
| **Preserve scroll on refetch** | ⭐ Stale-while-revalidate (Day 228), not a spinner replacing content |

# Part 4 — ⭐⭐ What the list screen tells you about your API

Build it, then write these down. They are project-defence material.

| ⭐ Symptom on screen | ⭐⭐ The finding on the server |
|---|---|
| Row shows a name, response has 40 fields | ⭐⭐ Returning the entity, not a DTO (Day 236) |
| ⭐ You need a second call per row | **N+1 across the network.** Either the DTO needs the field or you need a batch endpoint |
| Filtering happens client-side | ⭐⭐ The endpoint does not support the filter. **Not a UI problem.** |
| Sorting only works on the current page | ⭐ You sorted the page, not the query |
| ⭐ Rows duplicate across pages | ⭐⭐ **Unstable sort — add the id tiebreak** |
| The count query is slower than the page | ⭐ Drop or cache the total |
| ⭐⭐ Every user sees every row | ⭐⭐ **The tenant/owner filter is missing.** Stop and fix (Day 236). |

> ⭐⭐ **That last row is the one to check first and hardest.** A list endpoint whose filter lived in the
> UI is the single most common way a portfolio project leaks every user's data — and it looks perfectly
> correct in the browser, because your UI is filtering it.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "tell me about your list screen."**

Frame it as diagnostic. **The list screen is where every server decision becomes visible at once, so I
treat it as a review of the API rather than a UI task.**

Give the findings. **Reading one row's payload in DevTools showed I was returning the entity rather
than a DTO — forty fields to render two. A filter was being applied client-side, which meant the
endpoint didn't support it and I was shipping the whole table to the browser. And rows duplicated
across pages, which turned out to be an unstable sort: ordering by `created_at` with ties lets Postgres
return them in a different order per query, so rows appear twice and others vanish with no error
anywhere. One line — add `id` as a tiebreak.**

Then the correctness detail. **I chose offset pagination because this is an admin table where page
numbers matter, and I know the trade: deep offsets make Postgres scan and discard rows, and inserts
shift everything down so a user can see the same row twice. Cursor pagination fixes both and costs
page numbers.**

Close on the two states. **The empty state is two states. Never had any needs an explanation and the
action that creates one. Filtered to zero needs the query echoed back and a way to clear it. Showing
"no orders yet" to someone with five hundred orders and a bad filter makes them think their data is
gone — and filtering to zero is the first thing a reviewer tries.**

**And the one I checked hardest: I called the list endpoint with curl as a different user, because a
list whose owner filter lives in the UI looks perfectly correct in the browser.**
