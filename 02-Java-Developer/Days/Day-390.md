# Day 390

**L-390** · ECS and Fargate — running the flagship, and ECS vs EKS decided honestly

**Time:** 3 hrs · **Mode:** NEW

> **⭐ ECS is Kubernetes with 90% fewer concepts and no cluster to operate. For a team running web
> services on AWS, that is usually a feature rather than a compromise — and saying so out loud is
> Day 378's "when is Kubernetes overkill" answered with a product name.**
>
> Today: the four ECS objects, **the execution-role/task-role diagnostic**, `awsvpc` networking and the
> IP exhaustion it causes, the deployment circuit breaker, and **`StopTimeout` — where Day 361's PID 1
> lesson finally gets paid.**

# Part 1 — ⭐ The four objects, and their Kubernetes equivalents

| ECS | ⭐ Kubernetes equivalent | ⭐ What it is |
|---|---|---|
| ⭐⭐ **Task definition** | ⭐⭐ **Pod spec** | ⭐ image, CPU/memory, ports, env, roles, logging — **versioned, immutable** |
| ⭐ **Task** | ⭐ Pod | ⭐ one running instance of a task definition |
| ⭐⭐ **Service** | ⭐⭐ **Deployment** | ⭐ keeps N tasks running, registers them with a target group |
| ⭐ **Cluster** | ⭐ Namespace + nodes | ⭐ a logical grouping + capacity |

```
⭐⭐ A task definition REVISION IS IMMUTABLE. You never edit one — you register a new revision.
⭐ ⇒ ⭐⭐ Deploying = update the service to point at revision N+1.
⭐ ⇒ ⭐⭐ ROLLING BACK = update the service to point at revision N. ⭐ It is that literal.
```

> **⭐ Immutable revisions are why ECS rollback is genuinely trivial**, and it is the same principle as
> Day 368's immutable digest — **the artefact you roll back to is not rebuilt, it is re-pointed.**

## ⭐ Fargate vs EC2 launch type

| | ⭐⭐ Fargate | ⭐ EC2 launch type |
|---|---|---|
| You manage | ⭐⭐ **nothing below the task** | ⭐ AMIs, patching, capacity, the ECS agent |
| ⭐ Price | ⭐ ~20–50% premium per vCPU-hour | ⭐ cheaper if **well packed** |
| ⭐⭐ **Utilisation** | ⭐⭐ **100% — you pay for the task** | ⭐⭐ you pay for the **instance**, packed or not |
| ⭐ GPU / privileged / daemons | ⭐ no | ⭐ yes |
| Spot | ⭐ Fargate Spot (~70% off) | Spot instances |
| ⭐ Scale-out speed | ⭐⭐ **~30–60s, no instance boot** | ⭐ + instance boot time |

> **⭐⭐ The Fargate premium is often an illusion, and this is the argument worth having:** an EC2 cluster
> at 40% packing efficiency costs *more* than Fargate at 100%, **plus the engineer-hours of patching
> AMIs.** Do the arithmetic on your real utilisation before calling Fargate expensive. **At genuinely
> large, well-packed scale, EC2 wins — and that is a different company than most.**

# Part 2 — ⭐⭐ The two roles, and the diagnostic

| | ⭐⭐ Execution role | ⭐⭐ Task role |
|---|---|---|
| ⭐ Used by | ⭐⭐ **the ECS agent, before your code exists** | ⭐⭐ **your application code** |
| ⭐ Needs | ECR pull, CloudWatch Logs, **injected secrets** | ⭐ S3, SQS, DynamoDB… (least privilege) |
| ⭐⭐ **If wrong** | ⭐⭐ **the task NEVER STARTS** — `CannotPullContainerError`, `ResourceInitializationError` | ⭐ task starts, then `AccessDenied` |

```
⭐⭐ THE DIAGNOSTIC, MEMORISED:
⭐   Task never starts            ⇒ ⭐⭐ EXECUTION role (or networking to ECR/S3)
⭐   Task starts, then AccessDenied ⇒ ⭐⭐ TASK role
```

⚠️ **`ResourceInitializationError: unable to pull secrets or registry auth` is the single most common
first-deploy failure on Fargate**, and it has exactly two causes: **the execution role lacks a
permission**, or **the task has no route to ECR** — no NAT and no interface endpoint (Day 384). **Both
are network-or-IAM, never your code.**

# Part 3 — ⭐⭐ `awsvpc` networking and IP exhaustion

```
⭐⭐ Every Fargate task gets ⭐⭐ ITS OWN ENI and ITS OWN PRIVATE IP.
⭐ ⇒ ⭐ Security groups apply PER TASK — excellent, granular (Day 384)
⭐ ⇒ ⭐⭐ BUT: 200 tasks = 200 IPs. ⭐⭐ A /24 subnet has 251 usable.
⭐ ⇒ ⭐⭐ AT SCALE YOU RUN OUT OF IP ADDRESSES AND DEPLOYS SIMPLY FAIL.
⭐   ⭐ And a rolling deploy briefly needs 200% of the IPs (Day 371).
```

| ⭐ Consequence for design | |
|---|---|
| ⭐⭐ **Size private subnets generously** | ⭐⭐ **`/20` (4,091 usable) not `/24`** — Day 383's plan mattering |
| ⭐ Target group type must be `ip` | ⭐ not `instance` — awsvpc requires it (Day 389) |
| ⭐ Endpoints, not NAT | ⭐ each task pulling images through NAT is billed per GB (Day 384, 396) |
| ⭐ Service Connect / Cloud Map | ⭐ DNS-based discovery between services (Day 341) |

# Part 4 — ⭐⭐ Deployments: the circuit breaker and the capacity question

| Setting | ⭐ Meaning |
|---|---|
| ⭐ `minimumHealthyPercent` | ⭐⭐ **100** = never go below desired count |
| ⭐ `maximumPercent` | ⭐⭐ **200** = may double during deploy — **requires the capacity and the IPs** |
| ⭐⭐ **Deployment circuit breaker** | ⭐⭐ **detects a failing deploy and ROLLS BACK automatically** — turn it on |
| ⭐ `healthCheckGracePeriodSeconds` | ⭐⭐ **the JVM needs 60–120s** or the service kills tasks during startup, forever |
| ⭐ Blue/green via CodeDeploy | ⭐ two target groups, traffic shifting, automatic rollback on alarm (Day 371) |

```
⭐⭐ THE STARTUP DEATH LOOP, which everyone hits once:
⭐   grace period 0 + a JVM that takes 45s to become ready
⭐   ⇒ ⭐ health check fails at t=10s ⇒ ⭐⭐ ECS kills the task ⇒ starts a new one
⭐   ⇒ ⭐⭐ FOREVER. ⭐ The service never stabilises and the logs look like the app is crashing.
⭐   ⇒ ⭐ Set healthCheckGracePeriodSeconds. ⭐⭐ This is Day 377's startup probe, in ECS form.
```

## ⭐⭐ Stopping: where Day 361 gets paid

```
⭐ ECS task shutdown:
⭐   1. ⭐ deregister from the target group (Day 389's deregistration delay)
⭐   2. ⭐⭐ SIGTERM to PID 1 in the container
⭐   3. ⭐⭐ wait `stopTimeout` — DEFAULT 30s, MAX 120s
⭐   4. ⭐⭐ SIGKILL

⭐⭐ ⇒ If your Dockerfile uses shell-form CMD, ⭐⭐ PID 1 IS /bin/sh AND THE JVM NEVER GETS SIGTERM.
⭐    It runs for 30 seconds doing nothing, then everything is SIGKILLed mid-request. (Day 361)
⭐⭐ ⇒ And stopTimeout must EXCEED your graceful shutdown period, or you SIGKILL yourself on schedule.
```

⚠️ **Order the numbers deliberately, once:** deregistration delay ≥ p99 request · Spring's
`spring.lifecycle.timeout-per-shutdown-phase` (say 25s) · ECS `stopTimeout` **greater than that** (say
40s). **Each must be larger than the one it contains, and a mismatch anywhere produces dropped requests
on every single deploy.**

# Part 5 — ⭐⭐ ECS vs EKS, argued rather than asserted

| ⭐ Choose **ECS** when | ⭐ Choose **EKS** when |
|---|---|
| ⭐ AWS-only, and you expect to stay | ⭐⭐ **multi-cloud or on-prem is a real requirement** |
| ⭐⭐ **Small team, no platform engineers** | ⭐ you have (or are) a platform team |
| ⭐ Workload is web services and workers | ⭐⭐ **you need the ecosystem** — operators, Argo, Istio, KEDA, CRDs |
| ⭐ You want less to learn and less to break | ⭐ the team already knows Kubernetes deeply |
| ⭐⭐ **Time-to-production is the priority** | ⭐ you run many teams on shared infrastructure |

> **⭐ The honest summary: ECS is genuinely simpler, is free (you pay only for compute), and covers the
> web-service case completely. EKS is more powerful, more portable, more expensive (a control plane fee
> plus real operational load), and is the right answer when the ecosystem or portability is worth
> that.**

⚠️ **The reason people pick EKS and regret it is CV-driven design.** Kubernetes is worth learning
(Days 377–378) — **but "we chose it so the team could learn Kubernetes" is a hiring decision disguised
as an architecture decision.** Being able to name that in an interview shows judgement; **so does saying
"here we would have picked EKS, because X".**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Editing task definitions instead of registering revisions | ⭐ loses the trivial rollback |
| ⭐⭐ **Confusing execution and task roles** | ⭐⭐ debugging the wrong one — use the diagnostic |
| ⭐ `ResourceInitializationError` blamed on the app | ⭐⭐ it is IAM or the route to ECR, never your code |
| ⭐⭐ **`/24` private subnets with awsvpc** | ⭐⭐ IP exhaustion; deploys fail at scale |
| ⭐ Target group type `instance` with awsvpc | ⭐ registration fails |
| ⭐⭐ **No health check grace period** | ⭐⭐ the JVM startup death loop |
| ⭐ Circuit breaker disabled | ⭐ a bad deploy stalls forever instead of rolling back |
| ⭐ `maximumPercent` 200 without capacity or IPs | the deploy cannot make progress |
| ⭐⭐ **Shell-form `CMD`** | ⭐⭐ SIGTERM never reaches the JVM (Day 361) |
| ⭐⭐ **`stopTimeout` < graceful shutdown** | ⭐⭐ you SIGKILL yourself on every deploy |
| ⭐ Secrets injected as env vars | ⭐ Day 372 — visible in `describe-tasks` |
| ⭐ Calling Fargate expensive without the packing arithmetic | ⭐⭐ 40%-packed EC2 costs more |
| Choosing EKS for the CV | a hiring decision disguised as architecture |

## Interview questions

**Q: Explain ECS in Kubernetes terms.**
A task definition is a pod spec, a task is a pod, a service is a deployment and a cluster is a namespace
plus capacity. The important difference is that task definition revisions are immutable — you never edit
one, you register a new revision and point the service at it. That makes rollback literally re-pointing
the service at the previous revision, with no rebuild involved, which is the same immutable-artefact
principle as deploying by digest.

**Q: A Fargate task will not start with `ResourceInitializationError`. Where do you look?**
Not at the application, because the application has not run. It is either the execution role — which the
ECS agent uses to pull from ECR, write logs and resolve injected secrets — or the network path to ECR
and S3, meaning no NAT gateway and no interface endpoints. The general diagnostic is worth memorising:
if the task never starts it is the execution role or networking; if the task starts and then gets access
denied on an API call, it is the task role.

**Q: Why do private subnets need to be large for Fargate?**
Because `awsvpc` networking gives every task its own elastic network interface and its own private IP.
Two hundred tasks means two hundred addresses, and a `/24` has two hundred and fifty-one usable — and a
rolling deploy at two hundred percent maximum briefly needs double. So you exhaust addresses and deploys
start failing with no obvious cause. I size private subnets at `/20` from the start, which is a decision
you make when writing the CIDR plan, because you cannot resize a VPC's primary range afterwards.

**Q: Your service keeps killing and restarting tasks and the logs show the app starting normally each
time. What is happening?**
The health check grace period is too short for JVM startup. ECS begins health checking at ten seconds,
Spring takes forty-five to become ready, the check fails, ECS kills the task and starts another, forever.
The service never stabilises and it looks like a crash loop even though nothing crashed. Setting
`healthCheckGracePeriodSeconds` to sixty or ninety fixes it, and it is exactly the problem Kubernetes
startup probes exist to solve.

**Q: ECS or EKS?**
It depends on what you are buying. ECS is simpler, has no control plane fee, and completely covers web
services and workers on AWS — for a small team without platform engineers it gets you to production
faster with less to break. EKS is worth it when you genuinely need portability, or the ecosystem —
operators, Argo, KEDA, custom resources — or when you already have deep Kubernetes expertise. What I try
to avoid is picking Kubernetes because it is the impressive answer; that is a hiring decision disguised
as an architecture decision, and the operational cost is paid by whoever is on call.

## Mini task

1. ⭐ Write a **task definition in Terraform** for your flagship. Register three revisions and **roll back
   by re-pointing the service.**
2. ⭐⭐ Break the **execution role** deliberately and read the exact error. Then break the **task role** and
   read that one. Learn the two signatures.
3. ⭐ Deploy into a `/28` subnet and **run out of IPs on purpose.** Then fix the subnet sizing.
4. ⭐⭐ Set `healthCheckGracePeriodSeconds` to 0 and **reproduce the startup death loop.** Then fix it.
5. ⭐ Enable the **deployment circuit breaker**, deploy a deliberately broken image, and **watch it roll
   back by itself.**
6. ⭐⭐ Use **shell-form `CMD`** and prove the JVM never receives SIGTERM. Switch to exec form and prove it
   does (Day 361).
7. ⭐⭐ Order the three timeouts (deregistration delay, Spring shutdown, `stopTimeout`) correctly and
   **deploy under load with zero dropped requests.**
8. ⭐ Add **VPC endpoints for ECR and S3** and measure the NAT data-processing drop (Day 396).
9. ⭐ Set up **Service Connect** between two services and call one from the other by name.
10. ⭐⭐ Run the same workload on **Fargate and on a packed EC2 cluster** and compute the real cost per
    request each way. **Let the arithmetic decide, not the reputation.**

## 🎙️ Articulation drill

**Two minutes:** *"Why ECS and not Kubernetes?"*

**⭐ Answer it as a trade, never as a dismissal.** ECS covers web services and workers on AWS completely,
has no control plane to operate or pay for, and its immutable task definition revisions make rollback a
one-line change. **For a small team without platform engineers, that is less to learn and less to break,
and time-to-production is a real engineering value.**

**⭐ Then earn credibility by naming when you would switch: multi-cloud or on-prem as a genuine
requirement, or needing the ecosystem — operators, Argo, KEDA, custom resources. And add the honest
observation: the most common reason teams pick EKS is so the team can learn Kubernetes, which is a
hiring decision wearing an architecture decision's clothes.**
