# Day 357 ⭐

**L-357** · ⭐ Design 13 — the payment system

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Every other design in this stage optimises for scale. This one optimises for being provably
> right, and it is the only design where the correct answer to "can we make it eventually
> consistent?" is no.**
>
> Three ideas carry it: **a double-entry ledger that makes lost money structurally impossible,
> idempotency at every boundary, and reconciliation as a first-class daily job — because the payment
> provider, not your database, is the source of truth about whether money moved.**

---

# Part 1 — ⭐ Requirements: correctness first

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| Charge a customer | ⭐⭐ **never double-charge** |
| Refund, partial refund | ⭐⭐ **never lose a payment** |
| ⭐ **Payouts to sellers** | ⭐⭐ **every penny explainable, forever** |
| ⭐ **A ledger and statements** | ⭐ consistency over availability — **this is the CP choice** (Day 330) |
| Multi-currency | ⭐ auditable: **who, what, when, why — immutable** |
| Chargebacks and disputes | availability 99.99%, but ⭐ **correctness > availability** |

```
⭐ ESTIMATE
⭐   1M payments/day ⇒ ~12/s ⇒ peak ~50/s   ⭐⭐ THE SCALE IS TRIVIAL
⭐   Ledger entries: 1M × ~6 entries = 6M/day ⇒ ⭐ 2B/year — ⭐ append-only, easily handled
⭐ ⭐⭐ CONCLUSION: this is NOT a scale problem. Do not design for scale. Design for CORRECTNESS.
```

> **⭐ Say that conclusion early.** A candidate who starts sharding a payment system has misread the
> problem. **Fifty transactions a second is one PostgreSQL instance** — and the entire remaining
> difficulty is that money is involved.

# Part 2 — ⭐⭐ The double-entry ledger

> **⭐ Every movement of money is recorded as two or more entries that sum to zero.** Money is never
> created or destroyed — **it moves between accounts.**

```
⭐ Customer pays £100 for an order:
⭐   ┌──────────────────────────┬──────────┐
⭐   │ customer_receivable      │  -10000  │   ⭐ minor units. Integers. Always.
⭐   │ merchant_payable         │   +9700  │
⭐   │ platform_fee_revenue     │    +300  │
⭐   └──────────────────────────┴──────────┘
⭐   ⭐⭐ SUM = 0. Enforced by a constraint, checked by a query.
```

| ⭐ Property | ⭐ Why it matters |
|---|---|
| ⭐⭐ **Entries sum to zero, always** | ⭐⭐ **"money was lost" becomes a query that returns rows — not an argument** |
| ⭐⭐ **The ledger is append-only** | ⭐ a correction is a **reversing entry**, never an update or delete |
| ⭐ **Balances are derived** | ⭐ `SUM(entries)` per account — materialised for speed, **re-derived to detect drift** |
| ⭐ Every entry references its cause | ⭐ a payment id, a refund id — **traceable in both directions** |
| ⭐ **Amounts are integers in minor units** | ⭐ `double` is fatal (Day 042B); currency travels with the amount |

⚠️ **Never update a ledger entry. Never delete one.** A mistake is corrected by writing its opposite
and then the correct version, **so the history shows what happened and what was done about it.** This
is [Day 290](Day-290.md)'s immutable-event rule at its strictest — **and here it is a regulatory
requirement, not a preference.**

**⭐ The invariant you can actually run:**

```sql
-- ⭐ Should ALWAYS return zero rows. Run it continuously. ⭐ Alert if it does not.
SELECT transaction_id FROM ledger_entries GROUP BY transaction_id HAVING SUM(amount) <> 0;
```

> **⭐ That query is the strongest artefact in this design.** It converts "I believe our accounting is
> correct" into a monitored assertion — **and being able to name it is worth more than any
> architecture diagram.**

# Part 3 — ⭐⭐ Idempotency and the state machine

## ⭐ Idempotency at every boundary

```
⭐ client ──Idempotency-Key──► your API ──idempotency key──► PSP
⭐   ⭐ Each layer needs its OWN key, because each can retry independently.
```

| ⭐ Layer | ⭐ Mechanism |
|---|---|
| ⭐ **Client → your API** | ⭐ key stored with the result; **a repeat returns the original response, not a new charge** |
| ⭐⭐ **Your API → the PSP** | ⭐⭐ **their idempotency key — your transaction cannot protect their side effect** |
| ⭐ Webhook → you | ⭐ dedupe on the event id (Day 335) |
| ⭐ **Internal retries** | the key and the effect commit in one transaction (Day 335) |

⚠️ **A key must be stored with the *result*, not just as a marker.** A repeat needs to return what
happened the first time — **otherwise the caller cannot distinguish "already done" from "not done"**,
which is exactly the ambiguity you were removing.

## ⭐ The state machine, and the arrow that does not exist

```
⭐ INITIATED → AUTHORIZED → CAPTURED → SETTLED
⭐      │           │            │
⭐      │           │            └──► ⭐ REFUNDED  (a NEW transaction, not a reversal of state)
⭐      │           └──► VOIDED            └──► ⭐ CHARGEBACK (a separate flow entirely)
⭐      └──► FAILED
⭐ ⭐⭐ There is NO arrow from CAPTURED back to INITIATED. Money moved. (Day 309's missing arrow)
```

| ⭐ Distinction | |
|---|---|
| ⭐ **Authorise** | funds reserved on the card; **reversible, expires** |
| ⭐ **Capture** | ⭐⭐ **money actually moves — the irreversible step** |
| ⭐ **Void vs refund** | ⭐ void before capture (free, invisible); **refund after (a new transaction, visible to the customer)** |
| ⭐ Settlement | the PSP pays you, days later — **a separate reconciliation** |

> **⭐ Authorise-then-capture is why cancellation windows exist** ([Day 320A](Day-320A.md)) — and it is
> the single most useful thing to know about payments in an interview. **Capture as late as possible**,
> because everything before it is cheap to undo.

# Part 4 — ⭐⭐ Reconciliation: the part nobody designs

```
⭐⭐ YOUR DATABASE IS NOT THE SOURCE OF TRUTH ABOUT WHETHER MONEY MOVED. THE PSP IS.
⭐ ⇒ ⭐ They can disagree, and they will:
⭐    · a request timed out — ⭐ did it succeed?
⭐    · a webhook was lost, duplicated, or arrived out of order
⭐    · a refund was issued in their dashboard by a human
⭐    · a chargeback arrived weeks later
```

| ⭐ Mechanism | ⭐ Detail |
|---|---|
| ⭐⭐ **A daily reconciliation job** | ⭐⭐ **fetch their settlement file; compare every transaction against your ledger** |
| ⭐ **Three difference classes** | ⭐ in yours not theirs · in theirs not yours · **amounts differ** |
| ⭐⭐ **A break queue with a human owner** | ⭐⭐ **unmatched items are a work queue, not an alert nobody reads** |
| ⭐ Automatic resolution where safe | a known-timeout transaction confirmed present in their file |
| ⭐ **Never auto-correct a money difference** | ⭐ a human decides; the correction is a reversing entry |

⚠️ **Webhooks are unreliable, unordered and duplicated.** Treat them as a *hint*: **on any webhook,
fetch the authoritative state from the PSP's API rather than trusting the payload**, and run a poller
as a backstop for events that never arrive. **That combination — webhook as a trigger, API as truth,
poller as a safety net — is the pattern to name.**

## ⭐ Multi-party payments — a saga

**⭐ Marketplace flows span systems** (Day 342): charge the buyer, hold funds, deliver, pay out the
seller. **Compensations are semantic — a refund, not an un-charge — and the irreversible step goes
last.**

## ⭐ Security, and what not to build

| ⭐ Rule | |
|---|---|
| ⭐⭐ **Never store card numbers** | ⭐⭐ **tokenise — the PSP holds the card; you hold a token** |
| ⭐ Reduce PCI scope deliberately | ⭐ card data never touching your servers removes most of the burden |
| Encrypt at rest, restrict access, log every read | |
| ⭐ **Idempotency keys are not secrets** | ⭐ but they are guessable if you generate them poorly — use UUIDs |

```
⭐ MONITOR: ⭐⭐ unbalanced transactions (must be ZERO) · ⭐ reconciliation breaks open and their age
⭐          ⭐ authorise/capture success rate by provider · duplicate-charge count (⭐ ZERO)
⭐          ⭐ payments succeeded/min (business metric) · settlement lag
⭐ CUT:     fraud scoring, multi-PSP routing, instalments, FX optimisation
⭐ AT 10×:  ⭐ nothing changes — ⭐⭐ 500/s is still one database. THAT is the answer.
```

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Designing for scale | ⭐⭐ **you misread the problem — it is a correctness problem** |
| ⭐⭐ Floating point for money | ⭐⭐ Day 042B — cumulative, silent, in a ledger |
| ⭐ A single-entry "balance" column | ⭐ **no invariant to check; lost money is undetectable** |
| ⭐⭐ **Updating or deleting ledger entries** | ⭐⭐ **history destroyed; audit impossible; often illegal** |
| ⭐ Stored balances never re-derived | drift with no detector |
| ⭐ An idempotency key without the stored result | the caller still cannot tell what happened |
| ⭐ **Assuming your database knows whether money moved** | ⭐⭐ the PSP does |
| ⭐ Trusting webhook payloads | unordered, duplicated, spoofable — **verify signatures and re-fetch** |
| ⭐ **No poller as a backstop** | a lost webhook is a silently stuck payment |
| ⭐ No reconciliation | ⭐⭐ **differences are discovered by customers** |
| Auto-correcting money differences | a human must decide |
| Treating a refund as a state reversal | it is a new transaction with its own entries |
| ⭐ Storing card numbers | enormous PCI scope and risk, for nothing |

## Interview questions

**Q: How do you make sure money is never lost?**
A double-entry ledger. Every movement is two or more entries that sum to zero, so "money was created
or destroyed" is not an argument — it is a query that returns rows, and I run it continuously and
alert on it. The ledger is append-only, so a mistake is corrected by a reversing entry rather than an
update, and balances are derived from the entries and re-derived periodically to detect drift in the
materialised copy.

**Q: How do you avoid double-charging?**
Idempotency at every boundary, with a separate key at each, because every layer can retry
independently. The client sends a key, I store it with the *result* so a repeat returns the original
response rather than charging again, and I pass a key to the payment provider too — my transaction
cannot protect a side effect that happens on their servers. Webhooks are deduped on event id.

**Q: What is the difference between authorising and capturing?**
Authorisation reserves funds and is reversible and expiring; capture is when money actually moves and
is irreversible. That is why voiding before capture is free and invisible while refunding after
capture is a new transaction the customer sees on their statement. It is also why order cancellation
windows exist — you capture as late as possible, because everything before capture is cheap to undo.

**Q: Your database says the payment succeeded but the provider disagrees.**
Then the provider is right — they are the source of truth about whether money moved, and my database
is a record of what I believe. That is why reconciliation is a first-class daily job: fetch their
settlement file, compare every transaction, and classify differences as ours-not-theirs,
theirs-not-ours, or amounts-differ. Unmatched items go into a break queue with a human owner, and I
never auto-correct a money difference — a person decides and the correction is a reversing entry.

**Q: How do you handle webhooks?**
As hints, not as data. They arrive out of order, duplicated, sometimes not at all, and they can be
spoofed — so I verify the signature, then fetch the authoritative state from the provider's API
rather than trusting the payload, and I run a poller as a backstop for events that never arrive.
Webhook as trigger, API as truth, poller as safety net.

**Q: How would you scale this?**
I would not, and that is the answer. A million payments a day is about fifty a second at peak, which
is one database. Every hour spent sharding a payment system is an hour not spent on the ledger
invariant, idempotency and reconciliation — and those are where the money actually gets lost.

## Mini task

1. **Run the 45-minute framework**, timed, with **the ledger as the deep dive.** Notice how little
   time estimation deserves here — say why.
2. ⭐ Implement a **double-entry ledger** with a constraint that entries sum to zero. **Try to write
   an unbalanced transaction and watch it fail.**
3. ⭐⭐ Write the **invariant query** and run it continuously. **Corrupt one entry directly and confirm
   the alert fires.**
4. ⭐ Implement **balances as derived**, then materialise them, then **write the drift-detection job.**
   Corrupt the materialised value and confirm detection.
5. ⭐ Implement **idempotency keys storing the result.** Fire the same charge 100 times concurrently
   and **assert one charge and 100 identical responses.**
6. Implement **authorise, void, capture and refund** as distinct operations. **Attempt a void after
   capture and confirm it is rejected.**
7. ⭐⭐ Build **reconciliation**: generate a provider file with three deliberate differences — one
   missing each way and one amount mismatch. **Confirm all three land in the break queue.**
8. ⭐ Deliver a webhook **twice, out of order, and with a bad signature.** Confirm correct handling of
   each.
9. ⭐ Drop a webhook entirely and **confirm the poller resolves the payment.**
10. ⭐ Implement a **refund as a reversing entry** and verify the account balance and the invariant
    both remain correct.
11. Run a property test: **10,000 random operations, then assert every transaction sums to zero and
    total system balance is unchanged.**

## 🎙️ Articulation drill

**Three minutes:** *"How do you know your payment system hasn't lost money?"*

**⭐ The answer that closes this design: "because it is a query, not an opinion."** Every transaction's
entries sum to zero by construction, the query that finds violations runs continuously, the ledger is
append-only so history cannot be quietly edited, materialised balances are re-derived and compared,
**and reconciliation against the provider's settlement file catches every case where their truth and
my record disagree — with unmatched items going to a human, never auto-corrected.**

**⭐ That is five monitored assertions in place of a claim, and it is exactly what
[Day 297](Day-297.md) meant by "defensible".**
