# Part 1 — ⭐⭐ Chaos engineering, done as science

```
⭐⭐ A CHAOS EXPERIMENT IS FOUR THINGS — and "randomly kill stuff" is none of them:
⭐   1. ⭐⭐ A STEADY-STATE METRIC        "p99 < 300 ms and error rate < 0.1%"
⭐   2. ⭐⭐ A HYPOTHESIS                 "killing one AZ will not change it"
⭐   3. ⭐⭐ THE SMALLEST BLAST RADIUS     one instance · 1% of traffic · staging first
⭐   4. ⭐⭐ A STOP CONDITION AND AN ABORT "revert if error rate exceeds 1%" — ⭐ tested BEFORE you start
⭐ ⇒ ⭐⭐ THE VALUE IS THE HYPOTHESIS THAT TURNS OUT FALSE. ⭐ Confirming what you knew teaches nothing.
```

| ⭐ Experiment | ⭐ What it finds | ⭐ Order |
|---|---|---|
| ⭐ Kill one instance | ⭐ health checks, draining (Day 389) | ⭐ 1 — easy, usually passes |
| ⭐ Kill an AZ | ⭐⭐ static stability, capacity headroom (Day 380) | 2 |
| ⭐⭐ **Inject LATENCY into a dependency** | ⭐⭐ **timeouts, pool exhaustion, cascades — the richest source of real bugs** | ⭐⭐ **3 — do this one** |
| ⭐ Make a dependency return errors | ⭐ circuit breakers, degradation paths | 4 |
| ⭐ Fill a disk / exhaust memory | ⭐⭐ the failures nobody has ever seen | 5 |
| ⭐⭐ **Partition the network** | ⭐⭐ split brain, quorum behaviour (Day 412) | ⭐ 6 — hardest, most revealing |
| ⭐ Skew a clock | ⭐⭐ Day 409's every assumption | 7 |

> **⭐⭐ Latency injection is the highest-yield experiment and the least performed.** Killing a node is a
> binary failure that health checks handle; **adding 800 ms to a dependency exposes a missing timeout, a
> pool that fills, a retry that amplifies, and a cascade — all at once, and all of them real.**

| ⭐ Game days | |
|---|---|
| ⭐ A scheduled, announced exercise with the on-call team | ⭐ staging first, production when you are ready |
| ⭐⭐ **The deliverable is not "we survived"** | ⭐⭐ **it is the runbook, the missing alarm and the fixed dashboard** |
| ⭐ Include the humans | ⭐⭐ "who has permission to do the rollback at 3am?" is a finding |
| ⭐ Write down what surprised you | ⭐ that list is the backlog |

⚠️ **Do not run chaos in production until deployment, observability and rollback are solid** (Stage 10).
**Chaos on a system you cannot observe is just an outage you caused** — and it destroys the organisational
permission you need to keep doing it.

# Part 2 — ⭐⭐ Load shedding and the retry storm

```
⭐⭐ THE RETRY STORM — the mechanism by which a blip becomes an outage:
⭐   dependency slows slightly ⇒ ⭐ some requests time out ⇒ ⭐ clients retry
⭐   ⇒ ⭐⭐ the dependency now receives MORE traffic while ALREADY struggling
⭐   ⇒ ⭐ more timeouts ⇒ ⭐⭐ more retries ⇒ ⭐⭐ COLLAPSE.
⭐   ⇒ ⭐⭐ And it does not recover when the original cause is fixed, because the retries continue.
```

| ⭐ Defence | ⭐ Why |
|---|---|
| ⭐⭐ **Retry budget** | ⭐⭐ **"retries may be at most 10% of requests"** — caps amplification regardless of layers |
| ⭐⭐ **Exponential backoff with JITTER** | ⭐⭐ without jitter, every client retries at the same instant |
| ⭐⭐ **Circuit breaker** | ⭐⭐ stop retrying a dependency that is clearly down (Day 340) |
| ⭐ Retry only at **one** layer | ⭐ 3 retries × 4 layers = **81 requests per user action** (Day 398) |
| ⭐ Never retry non-idempotent calls without a key | duplicates |

## ⭐⭐ Shedding: refuse work you cannot do

```
⭐⭐ WITHOUT SHEDDING: overload ⇒ ⭐ queues grow ⇒ ⭐ latency grows ⇒ ⭐⭐ EVERYTHING times out
⭐   ⇒ ⭐⭐ 100% of requests fail, after using 100% of your capacity. ⭐⭐ The worst possible outcome.
⭐⭐ WITH SHEDDING:    overload ⇒ ⭐⭐ reject 30% FAST ⇒ ⭐⭐ serve 70% WELL.
```

| ⭐ Strategy | |
|---|---|
| ⭐⭐ **Bounded queues** | ⭐⭐ **an unbounded queue is a latency bomb** — Little's Law (Day 322) |
| ⭐⭐ **Deadline-aware dequeue** | ⭐⭐ **if the deadline already passed, DROP IT — you would do the work for nobody** (Day 336) |
| ⭐⭐ **Priority shedding** | ⭐⭐ **shed retries before first attempts; shed batch before interactive; shed free tier before paid** |
| ⭐ Admission control | ⭐ reject at the edge, cheaply, before any expensive work |
| ⭐ Shed with `429` + `Retry-After` | ⭐⭐ tell the client when to come back — cooperative rather than opaque |

> **⭐⭐ Shedding the retry before the first attempt is the most valuable priority rule in the list.** A
> retry is by definition a request someone has already waited for once; **dropping it protects the
> requests that still have a chance, and it directly damps the storm.**

⚠️ **Shedding must be cheaper than serving, or it does not work.** A rejection that still parses the
body, hits the database and builds a response has not saved anything — **the check belongs at admission,
before the expensive part.**

## ⭐ Five questions to answer aloud, with numbers

1. **How does an event get from your database to another service without ever being lost or invented?**
2. **Where exactly does exactly-once stop working, and what do you do past that line?**
3. **Two of your services disagree about a value. Walk me through how that happened and how it resolves.**
4. **What is the latency cost of your consistency choices? Give a number.**
5. **What did chaos testing tell you that you did not already know?**

> **⭐ Question 5 is the gate.** An answer of "everything worked" means the experiments were too timid.
> **"We discovered our health check queried the database, so one blip failed the whole fleet" is what a
> real answer sounds like.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Chaos without a hypothesis or a stop condition** | ⭐⭐ that is an outage, not an experiment |
| ⭐ Only killing instances | ⭐⭐ latency injection finds far more |
| ⭐ Chaos before observability | ⭐⭐ you cannot see what you broke |
| ⭐ Game days measured by "we survived" | ⭐ the deliverable is the findings |
| ⭐⭐ **Retries without a budget** | ⭐⭐ amplification turns a blip into collapse |
| ⭐ Backoff without jitter | ⭐ synchronised retry spikes |
| ⭐ Retrying at every layer | ⭐ 81 requests per user action |
| ⭐⭐ **Unbounded queues** | ⭐⭐ a latency bomb; everything times out |
| ⭐ Not dropping expired work | ⭐⭐ doing work nobody is waiting for |
| ⭐ Shedding that costs as much as serving | ⭐ it saves nothing |
| ⭐ Shedding first attempts before retries | ⭐⭐ exactly backwards |
| Answering interview questions with features instead of trade-offs | the level is judgement, not recall |

## Interview questions

**Q: How do you run a chaos experiment properly?**
It is four things: a steady-state metric you would notice a change in, an explicit hypothesis about what
will not change, the smallest possible blast radius, and a stop condition with an abort you have tested
before starting. The value is entirely in hypotheses that turn out false — confirming what you already
believed teaches you nothing. And I would not run it in production until deployment, observability and
rollback are solid, because chaos on a system you cannot observe is just an outage you caused, and it
burns the organisational permission you need to keep going.

**Q: Which chaos experiment gives the most value?**
Latency injection, by a distance, and it is the least performed. Killing a node is a binary failure that
health checks and draining already handle, and it usually passes. Adding several hundred milliseconds to
a dependency simultaneously exposes a missing timeout, a connection pool filling up, a retry that
amplifies load, and a cascade into unrelated endpoints — all of which are real bugs that exist right now
in most systems.

**Q: What is a retry storm and how do you prevent it?**
A dependency slows slightly, some requests time out, clients retry, and the struggling dependency now
receives more traffic than before — which produces more timeouts and more retries until it collapses. The
nastiest property is that it does not recover when the original cause is fixed, because the retries keep
going. Prevention is a retry budget capping retries at something like ten percent of traffic regardless of
how many layers exist, exponential backoff with jitter so clients do not retry in lockstep, circuit
breakers so a dead dependency stops being called at all, and retrying at exactly one layer — three
retries at four layers is eighty-one requests for one user action.

**Q: What is load shedding and how do you prioritise?**
Deliberately refusing work you cannot complete, so that you serve most requests well instead of failing
all of them slowly. Without it, overload grows queues, queues grow latency, and eventually everything
times out — you have spent one hundred percent of your capacity to fail one hundred percent of requests.
The priorities that matter: shed retries before first attempts, since a retry is a request someone has
already waited for once and dropping it damps the storm directly; shed batch before interactive; shed free
tier before paid. Drop anything whose deadline has already passed, because completing it helps nobody. And
the rejection has to be cheaper than serving — the check belongs at admission, not after the database
call.

**Q: What did distributed systems change about how you design?**
Mostly that I assume every failure is undetectable and every message arrives twice. Concretely: every
mutation takes a client-supplied idempotency key, every remote call has a deadline and a bounded retry
budget, events leave the database through an outbox and arrive through an inbox so nothing is lost or
invented, and correctness never depends on a wall clock. And I try to state the trade rather than the
feature — exactly-once delivery does not exist, effectively-once processing does, and knowing exactly
where that boundary sits is more useful than either slogan.

## 🎙️ Articulation drill

**Three minutes:** *"Tell me about a distributed system you have worked on."*

**⭐ Structure: the shape, the failure you designed for, the evidence.**

**⭐ The shape in two sentences — services split by capability, events leaving the database through an
outbox and arriving through an inbox, ordering per aggregate via the partition key, and a saga with
compensations where a business process spans services.**

**⭐ Then the failures, named rather than hinted at: every mutation takes an idempotency key because a
lost acknowledgement is indistinguishable from a failure; correctness never depends on a wall clock
because clocks disagree and last-write-wins silently discards data; the lock we thought we needed became
a conditional update, because a lease can expire during a GC pause and no lock service can fix that.**

**⭐ Then the evidence, which is what separates this from reading: we injected eight hundred milliseconds
into a dependency and found a missing timeout and a pool that filled; we reproduced a retry storm and
stopped it with a budget and jitter; and we forced a saga compensation to fail and confirmed it escalates
to a human queue instead of sitting in pending forever.**
