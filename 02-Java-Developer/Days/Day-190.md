# Part 1 — ⭐⭐ Composite indexes and the leftmost-prefix rule

```sql
create index ix_orders on orders (customer_id, status, placed_at);
```

**⭐ The index is sorted by `customer_id`, then within each customer by `status`, then within each
status by `placed_at`.** Like a phone book sorted by surname, then first name.

| Query | Uses the index? |
|---|---|
| `where customer_id = 1` | ⭐ ✅ |
| `where customer_id = 1 and status = 'PENDING'` | ⭐ ✅ |
| `where customer_id = 1 and status = 'PENDING' and placed_at > x` | ⭐ ✅ fully |
| `where customer_id = 1 and placed_at > x` | ⚠️ ⭐ **partially** — see below |
| `where status = 'PENDING'` | ❌ **no** — cannot start in the middle |
| `where placed_at > x` | ❌ **no** |

**⭐ You cannot start in the middle of a phone book sorted by surname to find everyone named
"James".** That is the whole rule, and it is Day 189's cause #7.

## ⭐ The "partially" case, which is the interesting one

`where customer_id = 1 and placed_at > x` **can** use the index — PostgreSQL seeks to `customer_id =
1` and then scans *every* row for that customer, filtering on `placed_at` as it goes. It skipped the
`status` column, so it lost the ability to seek on `placed_at`.

**Fast if the customer has 50 orders. Slow if they have 500,000.** In `EXPLAIN` this appears as a
large gap between `Index Cond` and `Rows Removed by Filter` — Day 191's diagnostic.

## ⭐ The column-order rules

> **1. Equality columns first, range columns last.**

```sql
where status = 'PENDING' and placed_at > '2026-01-01'
create index on orders (status, placed_at);        -- ⭐ correct
create index on orders (placed_at, status);        -- ❌ scans a date range, filters status
```

**⭐ Once you hit a range, the index is no longer sorted usefully for anything after it.** Everything
following a range column is filter-only.

> **2. Highest selectivity first among equality columns** — the one that eliminates the most rows.

> **3. ⭐ A column used in `ORDER BY` can come last and give you free sorting.**

```sql
select * from orders where customer_id = 1 order by placed_at desc limit 20;
create index on orders (customer_id, placed_at desc);      -- ⭐ NO SORT NODE AT ALL
```

**⭐ This is the single most valuable composite-index trick**, and it is exactly Day 152's keyset
pagination: the index delivers rows already in order, so `limit 20` reads twenty index entries and
stops. Without it, PostgreSQL reads every matching row, sorts them all, and discards all but twenty.

> **4. ⭐ In a multi-tenant schema, `tenant_id` leads everything** (Day 176, Day 188).

## One composite or several single-column indexes?

**PostgreSQL can combine single-column indexes with a `BitmapAnd`** — build a bitmap from each and
intersect. It works, and **a composite index is substantially faster** when the combination is a
known, frequent query, because it is one traversal rather than two plus an intersection.

**⭐ The rule of thumb: a composite index for your known hot queries; single-column indexes for
ad-hoc filtering** where you cannot predict the combination.

**And note the containment:** an index on `(a, b, c)` also serves queries on `(a)` and `(a, b)`. So
you rarely need all three — **one well-ordered composite often replaces three indexes**, which is a
real saving on Day 189's write amplification.

# Part 2 — ⭐ Partial indexes

```sql
create index ix_orders_pending on orders (placed_at) where status = 'PENDING';
```

**⭐ This is the answer to Day 189's cause #4.** If 0.1% of a 100-million-row table is `PENDING`,
this index has 100,000 entries instead of 100 million — it is **1,000× smaller, fits in memory, and
is maintained only when a pending row changes.**

**⭐ The planner uses it only when it can prove the predicate is satisfied**, so the query must
contain the condition — with a literal or a parameter the planner can match:

```sql
where status = 'PENDING' and placed_at < now() - interval '1 day'   -- ⭐ uses it
where placed_at < now() - interval '1 day'                          -- ❌ does not
```

**The four cases where partial indexes are transformative:**

| Case | Index |
|---|---|
| ⭐ A work queue — few pending among many done | `where status = 'PENDING'` |
| ⭐ Soft deletes (Day 188) | `where deleted_at is null` |
| ⭐ Uniqueness among a subset (Day 187) | `unique (email) where deleted_at is null` |
| Excluding a dominant value | `where status <> 'ARCHIVED'` |

**⭐ The work-queue case deserves emphasis** because it is Day 178's job poller: `select ... where
status = 'PENDING' order by created_at for update skip locked limit 100`. With a partial index on
exactly that predicate, the poller touches a tiny index no matter how large the history table grows.
**Without it, the poller gets slower every day forever** — a genuinely common production problem.

# Part 3 — The four other index types

## ⭐ GIN — for values that contain multiple things

```sql
create index ix_orders_data on orders using gin (data);                    -- jsonb (Day 198)
create index ix_articles_fts on articles using gin (to_tsvector('english', body));  -- Day 199
create index ix_posts_tags on posts using gin (tags);                      -- array
```

**⭐ The mental model: a B-tree indexes one value per row; GIN indexes *many* values per row**, and
maps each to the rows containing it — an inverted index.

| Property | Note |
|---|---|
| Query speed | ⭐ excellent for containment: `@>`, `?`, `&&`, `@@` |
| ⭐ **Write cost** | ⭐ **high** — one row can produce dozens of index entries |
| Size | large |
| `fastupdate` | on by default — batches writes into a pending list, ⭐ so some reads pay to clean it |

**Use for `jsonb` containment, full-text search, and arrays. Do not put one on a
write-heavy column casually** — the write amplification is far worse than a B-tree's.

## ⭐ GiST — for "overlaps" and "near"

```sql
create index on bookings using gist (during);       -- ⭐ range overlap — Day 187's exclusion constraint
create index on places using gist (location);       -- geometry / PostGIS
```

**Answers questions a B-tree cannot express**: overlap, containment, nearest-neighbour. It is the
index that makes Day 187's exclusion constraint efficient, and it is why range types are practical.

## ⭐ BRIN — tiny, for naturally ordered data

```sql
create index ix_events_time_brin on events using brin (created_at);
```

**⭐ Stores only the min and max value per block range** — so an index on a billion-row table can be
a few hundred kilobytes rather than 20 GB.

**⭐ The condition is strict: it only works if the column's physical order correlates with its
value.** An append-only events table ordered by `created_at` is the perfect case. **A randomly
ordered column makes BRIN useless** — every block range covers the whole value range, so nothing is
excluded.

```sql
select attname, correlation from pg_stats where tablename = 'events';   -- ⭐ near 1.0 or -1.0 = good
```

**Check `correlation` before creating one.** BRIN on a time-series table is one of the highest
value-per-byte decisions available; BRIN on unordered data does nothing.

## Hash

```sql
create index on sessions using hash (session_token);
```

Equality only, no ranges, no ordering, no multi-column. **Marginally faster and smaller than a B-tree
for pure equality on large values** — and the B-tree does everything else, so the default answer
stays B-tree.

## Trigram — the fix for `like '%x%'`

```sql
create extension pg_trgm;
create index ix_users_name_trgm on users using gin (name gin_trgm_ops);

where name ilike '%smith%'        -- ⭐ NOW uses the index
where name % 'smyth'              -- ⭐ fuzzy similarity search
```

**⭐ This is the fix for Day 189's cause #3 and Day 163b's DoS vector**, and it also gives you
typo-tolerant search for free. For a search box over names or short text, a trigram index is often
the whole solution — reach for full-text search (Day 199) when you need stemming and ranking.

# Part 4 — Choosing, and maintaining

| Query shape | Index |
|---|---|
| `=`, `<`, `>`, `between`, `order by`, `like 'x%'` | ⭐ **B-tree** |
| `jsonb @>`, array containment, full-text | ⭐ **GIN** |
| range overlap, geometry, nearest-neighbour | **GiST** |
| ⭐ huge, naturally time-ordered table | ⭐ **BRIN** |
| `like '%x%'`, fuzzy matching | ⭐ **GIN + trigram** |
| pure equality on a large value | hash |

## Bloat and rebuilding

**⭐ Indexes bloat**, because Day 186's dead tuples leave dead index entries behind. A heavily updated
index can end up several times larger than necessary, which pushes it out of memory (Day 189).

```sql
reindex index concurrently ix_orders_status;      -- ⭐ PostgreSQL 12+, non-blocking
```

Day 194 covers detecting bloat. **Note `concurrently` here too** — a plain `REINDEX` takes an
exclusive lock, which on a busy table is an outage.

## ⭐ Multicolumn statistics — for the case the planner gets badly wrong

```sql
create statistics stx_orders (dependencies, ndistinct) on city, postcode from orders;
analyze orders;
```

**⭐ The planner assumes columns are independent**, so it estimates `where city = 'London' and
postcode = 'SW1'` as `P(city) × P(postcode)` — a tiny number, when in reality the postcode implies
the city and the true count is much larger. That underestimate produces a nested loop over hundreds
of thousands of rows.

**Extended statistics tell the planner the columns are correlated.** It is a niche tool and it is
*the* fix when `EXPLAIN` shows an estimate of 1 against an actual of 200,000 on correlated columns —
which is Day 191's most important diagnostic.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Wrong leading column | the index cannot be used at all |
| Range column before equality columns | everything after it is filter-only |
| Not putting the `ORDER BY` column last | a full sort of the matching set |
| ⭐ Missing `tenant_id` first | every tenant query loses the index |
| Three single-column indexes where one composite would do | write amplification for less benefit |
| Partial index whose predicate the query omits | never used |
| GIN on a write-heavy column | severe write amplification |
| ⭐ BRIN on unordered data | does nothing at all |
| Not checking `correlation` before BRIN | wasted effort |
| B-tree for `like '%x%'` | Day 189 — use trigram |
| `REINDEX` without `concurrently` | exclusive lock, outage |
| Ignoring correlated-column misestimates | catastrophic plans; use extended statistics |

## Interview questions

**Q: Explain the leftmost-prefix rule.**
A composite index is sorted by the first column, then the second within that, and so on — like a
phone book by surname then first name. So a query filtering only on the second column cannot use it,
because you cannot start in the middle of a sorted structure. That is why column order is the whole
design decision.

**Q: How do you order the columns?**
Equality columns first, range columns last, because once you hit a range the index is no longer
usefully sorted for anything after it. Highest selectivity first among the equality columns. And I
put the `ORDER BY` column last where I can, because then the index returns rows already sorted and a
`LIMIT 20` reads twenty entries instead of sorting the whole matching set.

**Q: When is a partial index the answer?**
When the predicate is highly selective and appears in the query — a work queue where a tiny fraction
is pending, soft deletes, or uniqueness over a subset. The index can be a thousand times smaller, fit
in memory, and only be maintained when a matching row changes. It is the correct response to the
planner ignoring an index on a low-selectivity column.

**Q: When would you use BRIN?**
A very large table whose physical order correlates with the column — an append-only events table on
`created_at`. The index is kilobytes instead of gigabytes. I check `correlation` in `pg_stats` first,
because on unordered data BRIN excludes nothing and is useless.

**Q: `EXPLAIN` estimates 1 row and the actual is 200,000 on two correlated columns. What is
happening?**
The planner assumes independence and multiplies the selectivities, so correlated columns like city
and postcode are drastically underestimated. Extended statistics with `dependencies` tells it they
are related, which usually turns a nested loop back into a hash join.

## 🎙️ Articulation drill

Two minutes: **"How do you design an index for a query?"**

Start from the query, not the table. Equality columns first ordered by selectivity, range column
next, sort column last so the index returns rows in order and a `LIMIT` stops early instead of
sorting everything. Say the leftmost-prefix rule as a constraint that follows from the structure
rather than a rule to memorise. Then show breadth: a partial index when the useful subset is small,
GIN for containment and search, BRIN when the table is huge and naturally ordered — and close on the
cost, because every index is a tax on every write.
