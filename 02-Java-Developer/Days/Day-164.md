# Part 1 — The mechanism, which explains every failure

```java
@Service
public class OrderService {
    @Transactional
    public Order place(CreateOrderRequest req) { ... }
}
```

Day 137's machinery, exactly:

1. `BeanPostProcessor` sees `@Transactional` and wraps the bean in a **proxy** (Day 132).
2. Everything injected anywhere is **the proxy**.
3. On call, `TransactionInterceptor` runs: get a connection, `setAutoCommit(false)`, bind it to a
   `ThreadLocal` (Day 066A) so the repository below uses the *same* connection, call the target,
   then commit or roll back.

**⭐ Everything that fails, fails because of step 2 or step 3.** Four failure modes fall straight out:

| Failure | Cause |
|---|---|
| ⭐ **Self-invocation** | `this.method()` bypasses the proxy — no transaction, no error |
| `private` / `final` method | cannot be proxied — silently ignored |
| Called from a different thread | the connection is in a `ThreadLocal` — a new thread has no transaction |
| Called before the proxy exists | Day 133 — `@PostConstruct` and constructors |

```java
@Service
public class OrderService {
    public void processAll(List<Request> reqs) {
        for (Request r : reqs) this.processOne(r);      // ❌ no transaction on any of them
    }
    @Transactional
    public void processOne(Request r) { ... }
}
```

**Prove it rather than guess:**
```yaml
logging.level.org.springframework.transaction.interceptor: TRACE
```
Prints every transaction the interceptor creates. **Absence is the evidence** — Day 137's technique,
applied where it matters most.

# Part 2 — Propagation

| Propagation | Behaviour | Use |
|---|---|---|
| **`REQUIRED`** | join if one exists, else start | ⭐ the default. Right ~95% of the time |
| **`REQUIRES_NEW`** | ⭐ **suspend the outer, start an independent one** | audit, outbox, "must survive a rollback" |
| `SUPPORTS` | join if present, else none | rare |
| `NOT_SUPPORTED` | suspend; run without | a long read that must not hold locks |
| `MANDATORY` | ⭐ **fail if no transaction exists** | an internal method that must never be called standalone |
| `NEVER` | fail if one exists | rare |
| `NESTED` | a savepoint | JDBC only, not JTA. Partial rollback |

## ⭐ `REQUIRES_NEW` uses a second connection — and that is the whole story

```java
@Transactional                                    // connection #1
public void place(Request req) {
    Order o = repo.save(toOrder(req));
    audit.record(o);                              // ⭐ REQUIRES_NEW → connection #2
    inventory.reserve(o);                         // may throw
}
```

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void record(Order o) { auditRepo.save(new AuditEntry(o)); }    // ⭐ commits independently
```

**The outer transaction is suspended, not closed — it still holds connection #1.** So this method now
holds **two pool connections at once**.

**⭐ The deadlock this causes is a genuine production incident and it is worth understanding:** with
`maximum-pool-size: 10` (Day 156), ten concurrent requests take all ten connections for their outer
transactions, then each asks for an eleventh for the inner one. **The pool is empty and every request
is waiting for a connection held by a request that is waiting.** Nothing times out unless
`connection-timeout` is set. The service stops completely.

**The rules:** use `REQUIRES_NEW` only when the inner work must survive the outer rollback, keep it
short, never nest it deeply, and size the pool knowing it doubles connection demand on those paths.

**`MANDATORY` is underused.** On a method that must only ever run inside a caller's transaction, it
turns "someone called this standalone and lost atomicity" from a silent bug into a startup-adjacent
failure.

# Part 3 — ⭐ Rollback rules, and the default that surprises everyone

> **Spring rolls back on `RuntimeException` and `Error`. It does *not* roll back on a checked
> exception.**

```java
@Transactional
public void transfer(Long from, Long to, BigDecimal amount) throws InsufficientFundsException {
    debit(from, amount);
    if (balance(to) == null) throw new InsufficientFundsException();   // ⭐ CHECKED
    credit(to, amount);
}
// ⭐⭐ The debit COMMITS. The money is gone.
```

**This is EJB-inherited behaviour and it is a genuine footgun.** The rule is trivial to state and
catastrophic to forget.

```java
@Transactional(rollbackFor = Exception.class)      // ⭐ roll back on everything
```

**Many teams set this globally**, and it is defensible: "any exception escaping a transactional method
means the operation did not complete" is a more sensible default than the specification's.

## ⭐ The other rollback bug: catching inside the transaction

```java
@Transactional
public void place(Request req) {
    repo.save(order);
    try {
        inventory.reserve(order);
    } catch (Exception e) {
        log.error("reserve failed", e);           // ⭐ swallowed — transaction COMMITS
    }
}
```

**The interceptor only sees exceptions that escape the method.** Caught means committed. Every "we
log the error and carry on" block inside a transaction is a potential half-completed operation.

## ⭐ And the third: `UnexpectedRollbackException`

```java
@Transactional public void outer() {
    try { inner(); } catch (Exception e) { log.warn("inner failed, continuing"); }
    repo.save(somethingElse);
}
@Transactional public void inner() { throw new RuntimeException(); }   // ⭐ REQUIRED — joins outer
```

```
org.springframework.transaction.UnexpectedRollbackException:
    Transaction silently rolled back because it has been marked as rollback-only
```

`inner()` **joined** the outer transaction — `REQUIRED` does not create a new one — and its exception
marked the *shared* transaction rollback-only. Catching it does not unmark it. The outer method runs
to completion and then fails at commit.

**The fix is to decide what you meant:** if `inner` may fail without invalidating the outer work, it
must be `REQUIRES_NEW` (a genuinely separate transaction). If it may not, do not catch it. Marking
`noRollbackFor` is a third option and usually a sign the boundary is wrong.

# Part 4 — Isolation, timeouts, and the rules that keep transactions healthy

## Isolation — D-14, in an annotation

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
```

| Level | Prevents | Note |
|---|---|---|
| `READ_UNCOMMITTED` | nothing | never |
| `READ_COMMITTED` | dirty reads | ⭐ PostgreSQL/Oracle default |
| `REPEATABLE_READ` | + non-repeatable reads | ⭐ MySQL default |
| `SERIALIZABLE` | + phantoms, ⭐ **and write skew** | correct, and costly |

**⭐ The `DEFAULT` trap:** `Isolation.DEFAULT` means "whatever the database does", and that differs
between PostgreSQL (`READ_COMMITTED`) and MySQL (`REPEATABLE_READ`). **Code correct on one is subtly
wrong on the other**, which is exactly why a bug reproduces in production and not in a test suite
running a different engine. Be explicit where it matters.

**Do not reach for `SERIALIZABLE` reflexively.** D-14's write skew is real, but the usual fix is
narrower: optimistic locking with `@Version` (Day 165), a `select ... for update`, or a database
constraint that makes the invalid state unrepresentable. A constraint beats an isolation level,
because it holds regardless of how the row is written.

## Timeouts

```java
@Transactional(timeout = 5)      // ⭐ seconds
```

**Without one, a transaction can hold locks and a connection indefinitely.** One stuck transaction
blocks writers on those rows, blocked writers accumulate, and the pool empties (Day 156). Set a
timeout on anything that touches contended rows.

## ⭐ The four rules that prevent most transaction problems

1. **Keep transactions short.** Every millisecond is locks held and a connection held.
2. **⭐ No network calls inside** — Day 156's rule. It is also Day 124's dual-write.
3. **Boundary in the service, never the repository or the controller.** "These succeed or fail
   together" is a business statement.
4. **`readOnly = true` on every read path** — skips dirty checking (Day 162) and can route to a
   replica.

## The correct tool for "after the transaction commits"

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderPlaced(OrderPlacedEvent e) {
    emailService.sendConfirmation(e.orderId());        // ⭐ only if the commit actually happened
}
```

Day 133 introduced this; here is where it earns its place. Sending the email inside the transaction
means sending it for orders that then roll back. `AFTER_COMMIT` guarantees the commit happened —
though note the honest gap: **the email can still fail after commit**, so for anything that must not
be lost, Day 124's outbox is the answer and this is the convenience version.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Self-invocation | no transaction, no error, no clue |
| `@Transactional` on `private`/`final` | silently ignored |
| ⭐ Checked exception, no `rollbackFor` | partial commit — the transfer bug |
| Catching an exception inside the transaction | commits the partial work |
| Catching a `REQUIRED` inner failure | `UnexpectedRollbackException` at commit |
| `REQUIRES_NEW` casually | ⭐ two connections per request; pool deadlock |
| Long transactions | locks and connections held; contention |
| HTTP call inside | Day 156 and Day 124 together |
| Boundary on repository methods | one transaction per call, no atomicity across them |
| Relying on `Isolation.DEFAULT` | different semantics per database |
| No `timeout` | one stuck transaction empties the pool |
| No `readOnly` on reads | dirty-check overhead on every row |
| Side effects inside instead of `AFTER_COMMIT` | emails for orders that never existed |

## Interview questions

**Q: How does `@Transactional` work?**
A `BeanPostProcessor` wraps the bean in a proxy; `TransactionInterceptor` gets a connection, disables
autocommit, binds it to a `ThreadLocal` so repositories below share it, and commits or rolls back
afterwards. Every failure mode follows from that: self-invocation bypasses the proxy, `private` and
`final` methods cannot be advised, and another thread has no bound connection.

**Q: Does `@Transactional` roll back on a checked exception?**
No — only `RuntimeException` and `Error` by default. That is inherited from EJB and it is a real
footgun: a checked exception thrown halfway through commits the work already done. I set
`rollbackFor = Exception.class`, often globally.

**Q: What is `UnexpectedRollbackException`?**
An inner `REQUIRED` method joined the caller's transaction and threw, marking the *shared* transaction
rollback-only. The caller caught the exception and carried on, then failed at commit. The fix is to
decide the semantics: if the inner work may fail independently it needs `REQUIRES_NEW`; if not, do
not catch it.

**Q: What is the risk of `REQUIRES_NEW`?**
It suspends the outer transaction without releasing its connection, so the request holds two. Under
concurrency equal to the pool size, every request holds one connection and waits for a second that
another request is holding — a self-inflicted deadlock that never resolves without a connection
timeout.

**Q: Where does the transaction boundary belong?**
The service layer. "These operations succeed or fail together" is a business statement, not a
persistence detail — and repository-level transactions give you one per call with no atomicity across
them.

## 🎙️ Articulation drill

Three minutes, no notes: **"Explain `@Transactional`."**

Mechanism first — proxy, interceptor, connection bound to a `ThreadLocal` — then derive the failures
instead of listing them: self-invocation, `private`, another thread. Propagation with `REQUIRES_NEW`
explained by its cost, two connections, and the pool deadlock that follows. Rollback rules with the
checked-exception bug stated as a concrete money-losing example. Then the boundary argument: it
belongs in the service because atomicity is a business statement. Close on the operational rules —
short, no network calls, `readOnly` on reads, and side effects on `AFTER_COMMIT`.
