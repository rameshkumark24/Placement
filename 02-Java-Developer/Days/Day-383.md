# Day 383

**L-383** · VPC I — CIDR, subnets, route tables, and what actually makes a subnet public

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ There is no "public" checkbox on a subnet. A subnet is public because its route table has a
> route to an internet gateway. That is the entire definition, and knowing it resolves most VPC
> confusion in one sentence.**
>
> Today: CIDR planning you cannot undo, the three-tier subnet layout, **the NAT gateway that quietly
> becomes one of your largest line items**, and how to read a routing failure.

---

# Part 1 — ⭐⭐ CIDR planning: the decision you cannot take back

```
⭐ 10.0.0.0/16   ⭐ 65,536 addresses  ⭐⭐ the sensible default VPC size
⭐ 10.0.1.0/24   ⭐ 256 addresses     ⭐ a typical subnet
⭐⭐ /28 is the smallest subnet, /16 the largest.
⭐⭐ You can ADD a secondary CIDR later. You can NEVER shrink or change the primary.
```

| ⭐⭐ The mistake that costs years | |
|---|---|
| ⭐⭐ **Using `10.0.0.0/16` in every account** | ⭐⭐ **overlapping CIDRs can never be peered or joined to a Transit Gateway** |
| ⭐ Consequence | ⭐ prod cannot talk to shared services; the fix is **rebuilding a VPC** |
| ⭐⭐ **The fix, done on day one** | ⭐⭐ **allocate a distinct range per account/region from a written plan** |

```
⭐ A plan that works:
⭐   10.0.0.0/16    prod      eu-west-1
⭐   10.1.0.0/16    prod      us-east-1
⭐   10.10.0.0/16   staging   eu-west-1
⭐   10.20.0.0/16   dev       eu-west-1
⭐   ⇒ ⭐⭐ nothing overlaps, ever, so anything can be connected later.
```

⚠️ **AWS reserves 5 IPs in every subnet** (network, VPC router, DNS, future use, broadcast). **A `/28`
gives you 11 usable addresses, not 16** — and with `awsvpc` networking each ECS task consumes one
(Day 390), so a small subnet exhausts far faster than the arithmetic suggests.

# Part 2 — ⭐⭐ Subnets, route tables and the actual definition

```
⭐ A SUBNET is:  ⭐ a CIDR slice  +  ⭐⭐ exactly ONE availability zone  +  ⭐ one route table
⭐⭐ ⇒ a subnet NEVER spans AZs. Multi-AZ means one subnet per AZ, per tier.
```

| ⭐ Subnet type | ⭐⭐ Defined by its route table |
|---|---|
| ⭐⭐ **Public** | ⭐⭐ `0.0.0.0/0 → igw-xxxx` (internet gateway) |
| ⭐⭐ **Private** | ⭐⭐ `0.0.0.0/0 → nat-xxxx` (NAT gateway) — **egress only** |
| ⭐⭐ **Isolated** | ⭐⭐ **no `0.0.0.0/0` route at all** — cannot reach or be reached from the internet |

```
⭐⭐ THE THREE-TIER LAYOUT — the answer to "design me a VPC":

⭐ PUBLIC  (one per AZ, /24)    ⭐⭐ ONLY: load balancers and NAT gateways. Nothing else. Ever.
⭐ PRIVATE (one per AZ, /20)    ⭐ application: ECS tasks, EC2, Lambda ENIs
⭐ ISOLATED(one per AZ, /24)    ⭐⭐ data: RDS, ElastiCache — no internet route in either direction
```

> **⭐ "Why is nothing else in the public subnet?" — because a public subnet is where an instance *can*
> get a public IP, and the only things that need to be reachable from the internet are the load
> balancer and the NAT.** Everything else reaching the internet does so *through* something. **This
> layout is not ceremony; it is the difference between one exposed component and forty.**

⚠️ **A public IP is not enough to be reachable, and a route is not enough either.** Reachability from
the internet requires **all four**: a route to the IGW, a public IP or Elastic IP, a security group
allowing it, and a NACL allowing it (Day 384). Missing any one is silent.

# Part 3 — ⭐ The gateways

| Gateway | ⭐ Direction | ⭐ Cost shape |
|---|---|---|
| ⭐⭐ **Internet Gateway** | ⭐ in **and** out | ⭐⭐ **free** — it is a route target, not a device |
| ⭐⭐ **NAT Gateway** | ⭐⭐ **out only** — private → internet | ⭐⭐ **~$0.045/hr + ~$0.045 per GB processed** |
| Egress-only IGW | out only, **IPv6** | free |
| VPC Endpoint | to AWS services **without** leaving the network | ⭐ gateway free, interface hourly + per-GB (Day 384) |
| VPC Peering / TGW | VPC ↔ VPC | per-GB, and **TGW has an attachment fee** |

## ⭐⭐ The NAT gateway, priced honestly

```
⭐ Three AZs, one NAT gateway each (⭐ required for AZ-independent egress):
⭐   3 × $0.045/hr × 730 hrs        ≈ ⭐ $99/month  ⭐ before ONE BYTE moves
⭐ Plus ⭐⭐ $0.045 per GB PROCESSED — which includes traffic to S3 and ECR
⭐   pulling a 400 MB image 200× a day ≈ 2.4 TB/month ≈ ⭐⭐ $108/month ⭐ of pure waste
⭐ ⇒ ⭐⭐ and an S3/ECR VPC ENDPOINT removes most of it. (Day 384, Day 396)
```

> **⭐⭐ The NAT gateway is the single most common "why is our bill like this?" answer in small AWS
> accounts.** It is also the classic **cost-versus-availability trade**: one NAT for all three AZs saves
> ~$66/month and **makes a single AZ failure take out egress for every AZ.** In dev, one NAT is
> correct. In prod, three is correct. **Knowing that they are different answers is the point.**

⚠️ **A NAT gateway is not a security control.** It permits *all* outbound traffic. If you need to
restrict where your workloads may call out to, you need a proxy or **AWS Network Firewall** — and if
your compliance story is "our instances are private", note that **private means unreachable inbound, not
restricted outbound.**

# Part 4 — ⭐ Routing, read properly

```
⭐ Route table for the PRIVATE subnets:
⭐   10.0.0.0/16    →  local          ⭐⭐ implicit, cannot be removed, ALWAYS wins inside the VPC
⭐   0.0.0.0/0      →  nat-0abc       ⭐ default route: everything else goes out via NAT
⭐   pl-6da54004    →  vpce-0def      ⭐ S3 prefix list via the gateway endpoint (Day 384)
```

| ⭐ Rule | |
|---|---|
| ⭐⭐ **Longest prefix wins** | ⭐ `/32` beats `/24` beats `/16` beats `0.0.0.0/0` |
| ⭐⭐ **`local` is implicit and unbeatable** | ⭐⭐ **you cannot route around in-VPC traffic** |
| ⭐ One route table may serve many subnets | ⭐ but a subnet has exactly one |
| ⭐ The **main** route table is the default | ⭐⭐ a new subnet silently inherits it — **often the bug** |

## ⭐ DNS in a VPC

| Setting | ⭐ Why it matters |
|---|---|
| ⭐ `enableDnsSupport` | ⭐ the `.2` resolver works at all |
| ⭐⭐ `enableDnsHostnames` | ⭐⭐ **required for RDS and interface endpoints to resolve to private IPs** |
| ⭐ Route 53 **private hosted zone** | ⭐ internal names resolvable only inside the VPC |
| ⭐⭐ Split-horizon behaviour | ⭐⭐ the same RDS hostname resolves **private inside**, public outside |

⚠️ **`enableDnsHostnames = false` is a genuinely maddening failure mode**: the RDS endpoint resolves to
a *public* IP from inside the VPC, traffic tries to leave via the NAT, and connection times out with no
useful message. **If a private endpoint resolves to a public address, check this flag first.**

# Part 5 — ⭐ Connecting VPCs, briefly

| Option | ⭐ When |
|---|---|
| ⭐ **VPC Peering** | ⭐ two VPCs, non-transitive, cheap — **A↔B and B↔C does not give A↔C** |
| ⭐⭐ **Transit Gateway** | ⭐⭐ **more than a handful of VPCs** — hub and spoke, transitive, per-attachment fee |
| ⭐⭐ **PrivateLink** | ⭐⭐ expose *one service* to another VPC **without joining the networks** — no CIDR overlap concern |
| Site-to-Site VPN / Direct Connect | on-premises |

> **⭐ PrivateLink is the one that changes designs**: it exposes a single endpoint rather than a network,
> so **overlapping CIDRs stop mattering** and the blast radius of the connection is one service instead
> of an entire address space. **For "let a partner call our API privately", it is almost always the
> right answer over peering.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Same CIDR in every account** | ⭐⭐ **can never be peered — the fix is rebuilding a VPC** |
| ⭐ Forgetting the 5 reserved IPs | ⭐ a `/28` has 11 usable, not 16 |
| ⭐ Subnets sized without ENI-per-task in mind | ⭐ IP exhaustion under scale (Day 390) |
| ⭐⭐ **Application or database in a public subnet** | ⭐⭐ exposed for no benefit |
| ⭐ Expecting a public IP alone to make something reachable | ⭐ route + IP + SG + NACL, all four |
| ⭐⭐ **One NAT gateway in production** | ⭐⭐ one AZ failure kills egress everywhere |
| ⭐ Three NAT gateways in a dev account | ⭐ ~$99/month for nothing |
| ⭐⭐ **No S3/ECR endpoint** | ⭐⭐ every image pull billed as NAT data processing |
| ⭐ Believing NAT is a security control | ⭐ it allows all outbound |
| ⭐ A new subnet on the main route table | ⭐⭐ silently public, or silently unrouted |
| ⭐⭐ `enableDnsHostnames` off | ⭐⭐ private endpoints resolve to public IPs and time out |
| Expecting peering to be transitive | it is not — use a Transit Gateway |

## Interview questions

**Q: What makes a subnet public?**
Its route table has a route for `0.0.0.0/0` pointing at an internet gateway. That is the whole
definition — there is no public flag. A private subnet routes its default to a NAT gateway, so it can
reach out but nothing can reach in; an isolated subnet has no default route at all. And being in a
public subnet is not sufficient for reachability: you also need a public or elastic IP, a permitting
security group, and a permitting network ACL.

**Q: How would you lay out a VPC for a web application?**
Three tiers across three availability zones. Public subnets contain only the load balancer and the NAT
gateways. Private subnets hold the application — ECS tasks or instances — with a default route to NAT
for outbound. Isolated subnets hold RDS and ElastiCache with no default route at all. Sizing comes from
a written CIDR plan where every account and region gets a distinct range, because overlapping CIDRs can
never be peered and discovering that later means rebuilding a VPC.

**Q: What does a NAT gateway actually cost, and how do you reduce it?**
About $0.045 per hour and the same again per gigabyte processed, so three of them for zone independence
is roughly a hundred dollars a month before any traffic moves, and image pulls and S3 traffic are billed
on top. The biggest reduction is VPC endpoints: the S3 and DynamoDB gateway endpoints are free and are
route table entries, and interface endpoints for ECR and the other services keep that traffic off the
NAT. After that it is a deliberate trade — one NAT in development, one per zone in production, because a
single NAT means one zone's failure removes egress for everything.

**Q: A private instance cannot reach the RDS endpoint. How do you debug it?**
In order: does the route table have a path — and is the subnet even on the route table I think it is,
rather than the main one. Then the security group on the database, which should reference the
application's security group rather than a CIDR. Then the network ACL, remembering it is stateless so
return traffic on ephemeral ports must be allowed. Then DNS: if the endpoint resolves to a public
address from inside the VPC, `enableDnsHostnames` is off, which produces exactly this symptom with no
useful error. Reachability Analyzer will answer the first three mechanically.

**Q: Peering or PrivateLink?**
Peering joins two networks, is non-transitive, and requires non-overlapping CIDRs — fine for two VPCs
you control. PrivateLink exposes a single service endpoint rather than a network, so CIDR overlap stops
mattering and the blast radius is one service instead of an entire address space. For exposing an API to
a partner or another business unit, PrivateLink is almost always correct. Once you are past a handful of
VPCs that genuinely need full connectivity, a Transit Gateway replaces the mesh of peerings.

## 🎙️ Articulation drill

**Two minutes:** *"Design me a VPC."*

**⭐ Open with the definition, because it proves you understand rather than recall: a subnet is public
only because its route table points at an internet gateway.**

**⭐ Then the layout in one breath:** three AZs; public subnets holding nothing but the load balancer and
the NAT gateways; private subnets for the application; isolated subnets with no default route for the
data tier. **Then the two details that show experience: a written CIDR plan so nothing ever overlaps and
future peering stays possible, and an S3 gateway endpoint on day one so image and object traffic is not
billed twice through NAT.**
