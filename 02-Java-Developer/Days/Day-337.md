# Day 337

**L-337** · Search and inverted indexes — and keeping a derived index honest

**Time:** 3 hrs · **Mode:** NEW

> **⭐ A search index is a second copy of your data with a different shape, a different consistency
> model and a different failure mode. The index is never the source of truth, and the day it becomes
> one is the day you cannot recover from a bad reindex.**
>
> Day 199 covered PostgreSQL full-text search. Today: the dedicated engine, why the data structure is
> the inverse of a B-tree's, and the synchronisation problem that is the actual engineering.

---

# Part 1 — ⭐ The inverted index

```
⭐ FORWARD (a normal row):   doc1 → "the quick brown fox"
⭐ INVERTED:                 "quick" → [doc1, doc7, doc23]
⭐                           "brown" → [doc1, doc4]
⭐                           "fox"   → [doc1, doc23]

⭐ Query "quick fox" → intersect the two posting lists → [doc1, doc23]
```

| ⭐ Versus a B-tree | |
|---|---|
| ⭐ **B-tree** (Day 190) | ⭐ one row → one key. Optimised for **ranges and equality on a value** |
| ⭐ **Inverted index** | ⭐ one row → **many terms**. Optimised for **"which documents contain this term"** |
| ⭐ Why a `LIKE '%fox%'` cannot use a B-tree | ⭐ **the row is not indexed by its words** — hence the separate structure |

| ⭐ Posting-list mechanics worth knowing | |
|---|---|
| ⭐ **Sorted doc ids** | ⭐ intersection is a merge — the reason `AND` queries are fast |
| ⭐ Skip lists over postings | ⭐ jump ahead during intersection |
| ⭐ Positions stored per term | ⭐ **required for phrase queries** — "quick fox" adjacent, not merely both present |
| Compression (delta + varint) | posting lists are enormous; they compress extremely well |

## ⭐ The analysis pipeline — where relevance is actually decided

```
⭐ "The Running Foxes!"
⭐  → tokenize   → [The, Running, Foxes]
⭐  → lowercase  → [the, running, foxes]
⭐  → stopwords  → [running, foxes]
⭐  → stemming   → ⭐ [run, fox]
⭐  → synonyms   → [run, sprint, fox]
```

> **⭐ The rule that causes the most confusion in practice: the query must be analysed the same way as
> the document.** Index `foxes` as `fox` and search for `foxes` unanalysed, **and you match
> nothing.** Most "search is broken" incidents are an analyzer mismatch between index and query time.

⚠️ **And analysis is destructive.** Once you have stemmed and dropped stopwords, **the original is
gone from the index** — so `"to be or not to be"` becomes empty if stopwords are removed. **Keep a
second, minimally-analysed field for exact and phrase matching**; this is why real mappings have
`title` and `title.keyword`.

## ⭐ Scoring — BM25 in one breath

| Factor | ⭐ Effect |
|---|---|
| ⭐ **Term frequency** | more occurrences → higher — ⭐ **but it saturates**, so 100 mentions is not 10× better than 10 |
| ⭐ **Inverse document frequency** | ⭐ a rare term is worth far more than a common one |
| ⭐ **Field length normalisation** | ⭐ a match in a 5-word title beats one in a 5,000-word body |

**⭐ That is enough.** BM25 is TF-IDF with saturation and length normalisation, and **being able to
say why saturation matters — keyword stuffing does not win — is more useful than the formula.**

# Part 2 — ⭐ Why search is a separate system

| ⭐ Property | ⭐ Consequence |
|---|---|
| ⭐ **Write-once, read-many, rebuilt in bulk** | ⭐ a different storage engine (segments, immutable, merged) |
| ⭐ **Relevance ranking, not filtering** | ⭐ SQL returns matches; search returns an *ordered* answer |
| ⭐ **Different scaling profile** | ⭐ heavy CPU and memory for scoring, and it scales independently |
| ⭐⭐ **It is DERIVED** | ⭐⭐ **must always be rebuildable from the source of truth** |

> **⭐ Say the derived rule as an absolute: nothing may live only in the search index.** The moment
> one field exists nowhere else, a corrupt reindex is data loss and you can never rebuild from
> scratch. **The ability to drop the whole index and rebuild it is the property that makes it safe to
> operate.**

⚠️ **The corollary: never write to the index and the database as a dual write from application code**
(Day 124). One of them will fail, and nothing will tell you. **The index is populated *from* the
database, by one mechanism.**

## ⭐⭐ Keeping it in sync — the actual engineering

| Approach | ⭐ Freshness | ⭐ Reliability |
|---|---|---|
| ⭐ Dual write from the app | fast | ⭐⭐ **broken — silent divergence** |
| ⭐ **Outbox → indexer** (Day 263) | seconds | ⭐⭐ **reliable, ordered, replayable** |
| ⭐ **CDC from the write-ahead log** (Debezium) | ⭐ sub-second | ⭐ reliable; **no application code at all** |
| Periodic full reindex | ⭐ hours | simple; the safety net |
| ⭐ **Both: CDC + a scheduled full rebuild** | ⭐ **the production answer** | drift is detected and corrected |

**⭐ Three details that come up:**

1. ⭐ **Ordering matters** — an update and a delete applied out of order resurrects a document.
   **Send a version with every document and let the engine reject older versions** (Day 335's
   order-tolerant handler, implemented by the index).
2. ⭐ **Bulk, do not trickle** — one document per request wastes most of the engine's throughput.
   **Batch, with a size and a time trigger.**
3. ⭐ **Reindex into a new index and swap an alias.** Never reindex in place — **the alias swap is
   atomic, and rollback is swapping it back.** This is the expand/contract pattern (Day 166) applied
   to search.

# Part 3 — ⭐ Sharding, and the traps

```
⭐ Index → N primary shards → each with R replicas
⭐ Query → coordinator ──fan out──► every shard ──► top-K each ──► merge → global top-K
```

| ⭐ Trap | ⭐ Detail |
|---|---|
| ⭐⭐ **Primary shard count is fixed at creation** | ⭐⭐ **changing it means a full reindex — over-provision deliberately** (Day 329) |
| ⭐ **Every query fans out to every shard** | ⭐ more shards = more coordination; **shards are not free** |
| ⭐ Deep pagination is quadratic | ⭐ **page 1000 makes each shard return 10,000 docs to the coordinator** — use `search_after` |
| ⭐ **Distributed IDF is approximate** | ⭐ each shard scores using its own statistics, so relevance varies slightly with sharding |
| Too many small shards | overhead dominates; a shard has a real fixed cost |

⚠️ **Deep pagination is the one that surprises people and it is the same shape as Day 107's offset
problem, amplified by fan-out.** `from=10000, size=10` requires every shard to produce 10,010 hits
for the coordinator to merge. **Cursor-based `search_after` is the fix, and "no, you cannot jump to
page 1000" is a legitimate product answer.**

## ⭐ Autocomplete is a different index

| Approach | ⭐ Note |
|---|---|
| ⭐ **Edge n-grams** — index `f, fo, fox` at build time | ⭐ fast queries, larger index — **the usual choice** |
| ⭐ Prefix query on a `keyword` field | simple; slower, no ranking on popularity |
| ⭐ **FST / trie in memory** (completion suggester) | ⭐⭐ **fastest; ranks by weight — but a separate structure that must be rebuilt** |
| Fuzzy matching | ⭐ edit distance ≤ 2 — **expensive; restrict it to short prefixes** |

> **⭐ The point to make: autocomplete is a prefix problem ranked by popularity, not a relevance
> problem.** It needs its own structure, its own data (query logs, not documents) and its own latency
> budget — **typically under 50 ms, because it fires on every keystroke.**

# Part 4 — ⭐ Do you need it at all, and how do you know it works

**⭐ PostgreSQL full-text search (Day 199) covers more than people expect:**

| ⭐ Stay with PostgreSQL when | ⭐ Move to a search engine when |
|---|---|
| ⭐ **One data source, modest volume** | ⭐ relevance tuning is a product requirement |
| Filtering matters more than ranking | ⭐ **facets, aggregations, highlighting, suggestions** |
| ⭐ **You want one system to operate** | ⭐ scoring load must scale independently |
| ⭐ **Transactional consistency with the data matters** | multi-language analysis, synonyms, fuzzy matching |

⚠️ **The honest framing: adding a search engine adds a cluster to run, a sync pipeline to keep
correct, and a second consistency model.** For a catalogue of 50,000 products with simple keyword
search, **`tsvector` with a GIN index and no new infrastructure is the better engineering decision** —
and saying so demonstrates judgement.

## ⭐ Measuring relevance — the part everyone skips

**⭐ Exactly Day 293's argument, in a non-AI setting:** without measurement, relevance tuning is
guessing, and every change is as likely to hurt as help.

```
⭐ A labelled set: 100–200 queries with known-good results
⭐ ⭐ Recall@10     — is the right document even in the top 10?
⭐ ⭐ Precision@10  — how much of the top 10 is junk?
⭐ ⭐ MRR / NDCG    — is the right answer near the TOP, not merely present?
⭐ ⭐ Zero-result rate — ⭐ the single most actionable production metric
```

> **⭐ Two things to say: keep a fixed evaluation set and run it on every change**, and **watch the
> zero-result rate in production**, because queries returning nothing are the clearest signal of an
> analyzer or synonym gap — and they are directly convertible into revenue or engagement.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Data that exists only in the index | ⭐⭐ **a bad reindex is data loss; you can never rebuild** |
| ⭐ Dual-writing to the database and the index | ⭐ silent divergence (Day 124) |
| ⭐ Different analyzers at index and query time | ⭐ **matches nothing; the most common "search is broken"** |
| ⭐ No unanalysed field kept | exact and phrase matching become impossible |
| ⭐ Indexing one document per request | throughput wasted; bulk instead |
| ⭐ No version on updates | ⭐ **an out-of-order delete resurrects a document** |
| ⭐ Reindexing in place | ⭐ **no rollback — reindex to a new index and swap the alias** |
| ⭐⭐ Fixed shard count chosen carelessly | ⭐⭐ **changing it requires a full reindex** |
| ⭐ Deep `from`/`size` pagination | quadratic fan-out cost |
| Autocomplete on the main relevance index | wrong structure, wrong ranking, wrong latency |
| ⭐ Tuning relevance with no evaluation set | ⭐ every change is a guess |
| Ignoring the zero-result rate | the most actionable metric, unwatched |
| Adding a cluster for 50k rows | Day 199 already solved it |

## Interview questions

**Q: What is an inverted index?**
A map from term to the list of documents containing it, which is the inverse of a normal row-oriented
index. It exists because a B-tree indexes a row by its value, not by the words inside it, so a
substring or keyword query cannot use one. Posting lists are sorted so intersections are merges, and
positions are stored per term so phrase queries can require adjacency rather than mere co-occurrence.

**Q: Why is search a separate system?**
Different access pattern, different storage engine — immutable segments merged in the background —
and different scaling, since scoring is CPU and memory heavy. But the property that matters most is
that it is derived: nothing may live only in the index, because the ability to drop it and rebuild
from the source of truth is what makes it safe to operate.

**Q: How do you keep it in sync?**
Not by dual writes from application code — one of the two will fail silently and nothing will tell
you. Either an outbox that an indexer consumes, or change data capture from the write-ahead log,
which needs no application changes at all. Both in bulk rather than per document, with a version on
each document so an out-of-order delete cannot resurrect it, plus a scheduled full rebuild that
detects and corrects drift.

**Q: How do you reindex without downtime?**
Build into a new index and swap an alias, which is atomic and makes rollback a second swap. Never in
place, because there is no way back. It is the same expand-contract discipline as a zero-downtime
schema migration, and it is also what forces you to over-provision shard count at creation, since
primary shard count cannot be changed without exactly this operation.

**Q: When would you not add Elasticsearch?**
When PostgreSQL full-text search covers it — one data source, modest volume, filtering mattering more
than ranking, and a desire to operate one system rather than two plus a sync pipeline. A catalogue of
fifty thousand products with keyword search is a `tsvector` and a GIN index. I would move when
relevance tuning becomes a product requirement, or when facets, highlighting and suggestions are
needed, or when scoring load has to scale independently.

**Q: How do you know your search is any good?**
A fixed evaluation set of a couple of hundred queries with known-good results, scored on recall and
precision at ten and on MRR, run on every relevance change — otherwise tuning is guessing and a
change is as likely to hurt as help. In production I watch the zero-result rate, because it is the
clearest signal of an analyzer or synonym gap and it converts directly into lost engagement.

## Mini task

1. **Build an inverted index by hand** for 1,000 documents: tokenise, lowercase, stem, build posting
   lists, intersect for an `AND` query. **Then add positions and support a phrase query.**
2. ⭐ **Reproduce the analyzer mismatch**: index with stemming, query without, and get zero results.
   Fix it and confirm.
3. Add a second unanalysed field and **make exact-phrase search work** alongside stemmed search.
4. ⭐ Set up **CDC or an outbox indexer.** Update a row and measure end-to-end freshness.
5. ⭐⭐ **Deliver an update and a delete out of order** and resurrect a document. Add versions and
   confirm the engine rejects the stale one.
6. Index 100k documents one at a time, then in bulk. **Compare wall-clock time.**
7. ⭐ **Reindex to a new index and swap an alias** with live queries running. **Assert zero failed
   queries**, then roll back by swapping again.
8. ⭐ Page to `from=10000` and **measure latency and coordinator memory.** Switch to `search_after`
   and re-measure.
9. ⭐ Build an **evaluation set of 50 queries** with expected results. Compute recall@10, then change
   one analyzer setting and **re-measure — note whether your intuition was right.**
10. Instrument the **zero-result rate** and look at the actual queries producing it.

## 🎙️ Articulation drill

**Three minutes:** *"Add search to a product catalogue."*

**⭐ The marker: you ask whether PostgreSQL full-text search is enough before proposing a cluster**,
and give the specific triggers that would change your mind — relevance tuning as a product
requirement, facets, or independently scaling scoring load.

**⭐ Then, if you do add one, lead with the sync mechanism and the derived rule** rather than the
mapping: CDC or an outbox, versioned documents, bulk indexing, reindex-and-alias-swap, and a
scheduled rebuild that catches drift. **The index is the easy part; keeping it honest is the
engineering.**
