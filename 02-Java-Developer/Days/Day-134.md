# Day 134

**L-134** · Bean scopes — and the singleton-with-state bug

**Time:** 3 hrs · **Mode:** NEW

> Scopes decide **how many instances exist and how long each lives**. The default is singleton, which
> is almost always right — and the source of the most common concurrency bug in Spring applications.
>
> You are already equipped to explain that bug precisely, because it is Day 065's shared mutable
> state with a different label on it.

---

# Part 1 — The scopes

| Scope | Instances | Lifetime | Use |
|---|---|---|---|
| **`singleton`** ⭐ | **one per container** | the application | ✅ the default, and nearly always correct |
| `prototype` | **a new one per injection or lookup** | until garbage collected | Stateful helpers, builders |
| `request` | one per HTTP request | the request | Request-scoped context |
| `session` | one per HTTP session | the session | User state (Day 113) |
| `application` | one per `ServletContext` | the application | Rare |
| `websocket` | one per WebSocket session | the session | |

```java
@Component
@Scope("prototype")
class ReportBuilder { }

@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = TARGET_CLASS)
class RequestContext { }
```

⚠️ **Spring's "singleton" is one per `ApplicationContext`, not the Singleton pattern (Day 093) and
not one per JVM.** Two contexts — a test context and the main one, or a parent/child hierarchy —
mean two instances. This distinction is exactly the one Day 093 made: you want *one instance*, and
the container gives it to you with the dependency still visible in the constructor.

# Part 2 — ⭐ The singleton-with-state bug

**Read this carefully. It is the most common serious bug in Spring applications.**

```java
@Service
public class InvoiceService {

    private BigDecimal runningTotal;         // 💀 MUTABLE STATE IN A SINGLETON
    private String currentCustomer;

    public Invoice generate(Order order) {
        this.currentCustomer = order.customerId();
        this.runningTotal = BigDecimal.ZERO;

        for (LineItem item : order.items()) {
            this.runningTotal = this.runningTotal.add(item.total());
        }
        return new Invoice(currentCustomer, runningTotal);
    }
}
```

**One instance. Every HTTP request thread calls it concurrently** (Day 064). So:

```
Thread A (customer 17): sets currentCustomer = "17", starts summing
Thread B (customer 99): sets currentCustomer = "99"           ← overwrites A's field
Thread A: finishes, returns Invoice("99", totalA)             💀 WRONG CUSTOMER'S INVOICE
```

**Customer 17 receives customer 99's invoice.** It works perfectly in development — one user, one
request at a time — and produces data leakage in production under concurrency.

> **⭐ Spring beans are singletons and are called by many threads simultaneously. They must be
> stateless, or their state must be thread-safe.**

**The fix is Day 025's insight**: locals live on the thread's own stack and are private by
construction.

```java
@Service
public class InvoiceService {                // ✅ STATELESS

    public Invoice generate(Order order) {
        BigDecimal total = BigDecimal.ZERO;   // ⭐ a local — one per invocation, per thread
        for (LineItem item : order.items()) {
            total = total.add(item.total());
        }
        return new Invoice(order.customerId(), total);
    }
}
```

## What may live in a singleton's fields

| ✅ Safe | 💀 Not safe |
|---|---|
| `final` injected dependencies (themselves stateless) | Any mutable field written during a request |
| Immutable configuration (Day 034A) | `SimpleDateFormat`, `Matcher` (Day 063B) |
| Thread-safe collaborators (`ConcurrentHashMap`, `AtomicLong`) | `HashMap`, `ArrayList` as accumulators |
| Metrics counters | Per-request context |
| `DateTimeFormatter` (immutable — Day 042A) | Anything with a setter |

**`SimpleDateFormat` as a field is the classic instance of this bug** (Day 066A) — it is mutable and
not thread-safe, so concurrent formatting produces silently wrong dates rather than an exception.
`DateTimeFormatter` is immutable and safe.

**Injected dependencies are fine** because they are themselves stateless singletons — the safety
composes only if it holds all the way down.

## Detecting it

```java
// A test that finds it, and belongs in any codebase with stateful-looking services
@Test void isThreadSafe() throws Exception {
    var service = new InvoiceService();
    var errors = new ConcurrentLinkedQueue<String>();
    var start = new CountDownLatch(1);                       // Day 070's starting pistol

    var threads = IntStream.range(0, 50).mapToObj(i -> new Thread(() -> {
        try { start.await();
            for (int n = 0; n < 1000; n++) {
                Invoice inv = service.generate(orderFor("cust-" + i));
                if (!inv.customerId().equals("cust-" + i)) errors.add("cross-contamination");
            }
        } catch (Exception e) { errors.add(e.toString()); }
    })).toList();

    threads.forEach(Thread::start);
    start.countDown();
    for (Thread t : threads) t.join();
    assertTrue(errors.isEmpty(), errors.toString());
}
```

**Run this against the buggy version and it fails within milliseconds.** Static analysis helps too —
SpotBugs' `IS2_INCONSISTENT_SYNC` and IntelliJ's inspections flag mutable fields in `@Service`
classes.

# Part 3 — Prototype, and the injection trap

```java
@Component @Scope("prototype")
class ReportBuilder { … }

@Service
class ReportService {
    private final ReportBuilder builder;                    // 💀 injected ONCE, at startup

    ReportService(ReportBuilder builder) { this.builder = builder; }

    public Report build() { return builder.reset().build(); }   // the SAME instance every time
}
```

**⭐ Injecting a prototype into a singleton gives you one instance, forever.** The prototype scope
applies at *injection time*, and a singleton is injected once — so you have a shared mutable object
with none of the isolation you thought you had. **This is the singleton-state bug wearing a
`@Scope("prototype")` disguise**, and it is worse because the annotation makes it look handled.

Three correct approaches:

```java
// 1. ⭐ ObjectProvider — a NEW instance per call
@Service
class ReportService {
    private final ObjectProvider<ReportBuilder> builders;
    public Report build() { return builders.getObject().build(); }
}

// 2. A factory you own — clearest, and no Spring coupling
@Service
class ReportService {
    private final ReportBuilderFactory factory;
    public Report build() { return factory.create().build(); }
}

// 3. @Lookup — method injection; Spring overrides the method with CGLIB
@Service
abstract class ReportService {
    @Lookup protected abstract ReportBuilder newBuilder();
    public Report build() { return newBuilder().build(); }
}
```

> **Prefer option 2.** If you need a new object per call, that is what `new` is for — a plain factory
> is clearer than any container mechanism, and it does not tie the class to Spring.

⚠️ **Spring does not manage a prototype's destruction.** `@PreDestroy` is **never called** on a
prototype bean — the container hands it over and forgets it. Anything holding a resource must be
closed by the caller (try-with-resources, Day 061), which is another argument for a plain factory.

# Part 4 — Web scopes and the scoped proxy

```java
@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)     // ⭐ proxyMode is REQUIRED
public class RequestContext {
    private String correlationId;
    private String tenantId;
    // getters and setters
}
```

**Why `proxyMode` is mandatory here:** a singleton is created once at startup, when no request
exists. Injecting a request-scoped bean into it would be impossible — there is nothing to inject.

The proxy resolves it:

```
Singleton holds  ──►  a PROXY (created once, at startup)
                        │  on every method call:
                        └──► look up the CURRENT request's instance and delegate
```

**And the lookup uses a `ThreadLocal`** — `RequestContextHolder`, which is Day 066A exactly. So the
same two caveats apply:

⚠️ **A request-scoped bean is unavailable outside a request** — in `@Async` code, a `@Scheduled` job,
or a background worker there is no request bound to the thread, and you get
`ScopeNotActiveException`.

⚠️ **It does not propagate across an executor hand-off** without explicit copying.

> **Prefer passing the value explicitly.** A request-scoped bean is invisible dependency injection
> (Day 066A's warning), and it makes methods behave differently depending on the calling thread. Use
> it for genuinely cross-cutting request context — a correlation id, the current tenant — and pass
> parameters for everything else.

**Session scope carries an extra caution:** session-scoped beans must be serializable if sessions are
replicated across a cluster (Day 063A), and every field held there multiplies by concurrent users.
It is server-side state with all the costs Day 113 listed.

# Part 5 — Choosing

```
Stateless service, repository, controller, component   → singleton (the default)   ⭐
Per-request context (correlation id, tenant)           → request scope + proxy, or a parameter
Per-user state                                         → session scope, or a session store (Day 113)
A new object per call                                  → ⭐ a plain factory, not prototype
Expensive shared resource (pool, cache, client)        → singleton
```

> **If you are reaching for a non-singleton scope, ask whether you actually need a parameter or a
> local variable.** Nine times out of ten, you do — and the scope was covering for state that should
> not have been in a field.

**Custom scopes exist** (`registerScope` with a `Scope` implementation) — thread scope, tenant scope,
job scope. Almost never worth it; the mechanism is worth recognising because Spring Batch and Spring
Cloud use it.

## Common mistakes

| Mistake | Consequence |
|---|---|
| **Mutable fields in a singleton** | ⭐ **Cross-request data corruption under concurrency** |
| `SimpleDateFormat` or `Matcher` as a field | Silently wrong output, not an exception |
| A non-thread-safe collection as an accumulator | Lost updates; `ConcurrentModificationException` |
| Injecting a prototype into a singleton | One instance forever — the bug, disguised |
| Expecting `@PreDestroy` on a prototype | Never called; resources leak |
| Request scope without `proxyMode` | Fails at startup — nothing to inject |
| Request-scoped bean used in `@Async` or `@Scheduled` | `ScopeNotActiveException` |
| Assuming request scope crosses a thread hand-off | Empty context on the pool thread |
| Session-scoped beans that are not serializable | Fails under session replication |
| Treating "singleton" as one per JVM | It is one per `ApplicationContext` |
| Using a scope to hide state that should be local | The design problem remains |

## Interview questions

**Q: What is the default bean scope, and why is it usually right?**
Singleton — one instance per `ApplicationContext`. It is right because services should be stateless,
so one instance serves every thread with no coordination and no allocation per request.

**Q: What is the singleton-with-state bug?**
A `@Service` with a mutable field, called concurrently by many request threads. One thread's write
overwrites another's, so a request can return a result computed from a different user's data. It
works perfectly in single-user development and corrupts data in production. The fix is locals rather
than fields.

**Q: What may safely be a field on a singleton?**
Final injected dependencies that are themselves stateless, immutable configuration, thread-safe
collaborators like `ConcurrentHashMap` or `AtomicLong`, and immutable helpers such as
`DateTimeFormatter`. Never a mutable object written during a request — `SimpleDateFormat` is the
classic offender.

**Q: What happens when you inject a prototype bean into a singleton?**
You get one instance, injected once at startup, shared forever — the scope does not apply per call.
Use `ObjectProvider`, `@Lookup`, or simply a factory, which is clearest.

**Q: Is `@PreDestroy` called on prototype beans?**
No. The container creates them and hands them over without tracking them, so cleanup is the caller's
responsibility.

**Q: Why does a request-scoped bean need a scoped proxy?**
Because the singleton that depends on it is created at startup, when no request exists. The proxy is
injected once and, on each method call, resolves the current request's instance from a `ThreadLocal`.

**Q: When would you not use a request-scoped bean?**
When a parameter would do. It is invisible dependency injection, it fails outside a request — in
`@Async` or `@Scheduled` code — and it does not propagate across an executor hand-off. Reserve it for
genuinely cross-cutting context.

## 🎙️ Articulation drill

Two minutes: **"Are Spring beans thread-safe?"**

The bean is a singleton called concurrently by every request thread, so **Spring guarantees nothing —
thread safety is your responsibility**. Give the invoice example with the interleaving, note that it
is invisible in single-user development, and give the fix: locals rather than fields, and only
immutable or thread-safe collaborators in fields. Close with the prototype-into-singleton trap,
because that is the version people believe they have already solved.
