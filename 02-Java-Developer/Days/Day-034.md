# L-034 · `final`

## The three uses

| On a | Means |
|---|---|
| **Variable** | The reference or value cannot be **reassigned** |
| **Method** | Cannot be **overridden** |
| **Class** | Cannot be **subclassed** |

Three different meanings. They share a word and not much else.

## `final` on variables — the misunderstanding

**`final` prevents reassignment. It says nothing whatsoever about the object's contents.**

```java
final List<String> list = new ArrayList<>();
list.add("hello");        // ✅ PERFECTLY LEGAL — mutating the object
list.add("world");        // ✅
list = new ArrayList<>(); // ❌ compile error — reassigning the reference
```

```
   final List<String> list
        │
        │  ← THIS binding is frozen
        ▼
   ┌──────────────────────┐
   │  ArrayList           │  ← the CONTENTS are completely mutable
   │  ["hello", "world"]  │
   └──────────────────────┘
```

**Say it precisely in an interview:**

> *"`final` freezes the reference, not the object. A `final List` can still be added to, cleared and
> reordered — you just can't point the variable at a different list."*

**For primitives it does mean constant**, because the value *is* the variable:

```java
final int MAX = 100;      // genuinely constant
```

**For references it means only "this variable always points here".**

### Where `final` variables can be assigned

```java
final int a = 1;                       // at declaration

final int b;
if (cond) b = 1; else b = 2;           // ✅ blank final — assigned exactly once on every path

class X {
    final int c;
    X() { c = compute(); }             // ✅ blank final field, assigned in the constructor
}
```

A **blank final** must be definitely assigned exactly once before use, on every code path. The
compiler proves it.

### Effectively final

```java
int count = 0;
Runnable r = () -> System.out.println(count);   // ✅ works if count is never reassigned
count = 1;                                       // ❌ now the lambda won't compile
```

**Lambdas and anonymous classes can only capture variables that are final or effectively final** —
never reassigned after initialisation.

**Why:** the captured value is *copied* into the lambda (Day 032's pass-by-value again). If the
original could change, the lambda would silently see a stale copy. Rather than allow that confusion,
the language forbids it.

**The workaround people reach for, and why it's a smell:**

```java
int[] counter = {0};                              // array to smuggle mutability in
list.forEach(x -> counter[0]++);                  // ⚠️ works, but also not thread-safe

AtomicInteger counter = new AtomicInteger();      // ✅ if you genuinely need shared mutation
long count = list.stream().filter(...).count();   // ✅ usually you don't
```

## `final` on methods

```java
class Parent { final void critical() { } }
class Child extends Parent {
    void critical() { }        // ❌ compile error
}
```

**Use when overriding would break a class invariant.** Template method patterns often make the
template `final` and the hooks abstract (Day 095).

**Note:** `private` methods are implicitly final — they aren't inherited, so they can't be
overridden. And Day 024 showed why: `invokespecial`, not `invokevirtual`.

**The performance myth:** `final` methods used to be described as faster because they could be
inlined. **This is obsolete.** The JIT does speculative devirtualisation (Day 023) — it inlines
non-final methods whenever only one implementation has been observed, guarding in case that changes.
**Never add `final` for performance.** Add it for design.

## `final` on classes

```java
public final class String { }          // cannot be extended
```

**Why `String` is final:**
- **Security** — a mutable `String` subclass could bypass a validated path check (Day 029's TOCTOU
  argument). If `String` could be subclassed, immutability wouldn't be guaranteed.
- **The pool** — interning requires that all instances behave identically
- **Hash caching** — a subclass could override `hashCode` inconsistently

Other final classes: `Integer` and the wrappers, `LocalDate` and the `java.time` types, records
(implicitly).

**When to make your class final:** when it isn't designed for extension. Which is most classes.

> *Effective Java*: **"Design and document for inheritance, or else prohibit it."** Inheritance is a
> strong coupling — a subclass depends on your implementation details, so any internal change can
> break it. If you haven't thought carefully about what a subclass may override and what invariants
> it must preserve, make the class `final` and offer composition instead.

## `static final` — constants

```java
public static final int MAX_SIZE = 100;                     // ✅ genuinely constant
public static final List<String> NAMES = new ArrayList<>(); // ⚠️ NOT constant!
NAMES.add("oops");                                           // legal
```

**`static final` on a mutable type is a global mutable variable wearing a disguise** — one of the
worst combinations in Java, since it's shared, thread-unsafe and immortal (Day 033).

```java
public static final List<String> NAMES = List.of("a", "b");          // ✅ truly immutable
public static final Map<String,Integer> M = Map.of("a", 1);          // ✅
```

**Compile-time constants** — `static final` primitives or Strings initialised with a constant
expression — are **inlined into the calling class's bytecode**:

```java
// Library.java
public static final int VERSION = 1;

// Client.java
if (Library.VERSION == 1) { }     // the literal 1 is COMPILED INTO Client.class
```

**Consequence:** change `VERSION` to 2, recompile only the library, and the client still sees 1
until *it* is recompiled. This causes genuinely baffling bugs in multi-module builds. Verify it with
`javap` (Day 024).

## `final` in method parameters

```java
void process(final String input) { }
```

Prevents reassigning the parameter inside the method. **Harmless but usually noise** — most style
guides omit it. The exception: it documents intent when a method is long, and some teams require it.
Either convention is defensible; consistency matters more.

## What `final` buys you

| Benefit | Real? |
|---|---|
| Prevents reassignment bugs | ✅ Genuinely useful |
| Documents intent | ✅ |
| Required for lambda capture | ✅ (or effectively final) |
| **Safe publication of final fields** | ✅ **Important — see below** |
| Performance | ❌ Obsolete — the JIT handles it |
| Immutability | ❌ **No. This is the misunderstanding.** |

### The one that matters for concurrency

**The Java Memory Model gives `final` fields a special guarantee** (Day 065): once a constructor
completes, any thread that sees the object is guaranteed to see its `final` fields correctly
initialised — **without any synchronisation**.

Non-final fields have no such guarantee. Another thread can observe a partially constructed object
with default values.

**This is why immutable objects are safe to share freely across threads**, and it's the deepest
reason `final` matters. Day 065 covers the mechanism; know today that the guarantee exists and
applies *only* to `final` fields.

## Type this yourself

```java
import java.util.*;
import java.util.concurrent.atomic.AtomicInteger;

public class FinalDemo {

    static final int CONSTANT = 100;
    static final List<String> MUTABLE_CONSTANT = new ArrayList<>();
    static final List<String> TRULY_IMMUTABLE = List.of("a", "b");

    public static void main(String[] args) {

        // ---- 1. final freezes the REFERENCE, not the object ----
        final List<String> list = new ArrayList<>();
        list.add("hello");
        list.add("world");
        list.set(0, "changed");
        list.clear();
        System.out.println("final List mutated freely: " + list);
        // list = new ArrayList<>();          // ← uncomment: compile error

        // ---- 2. static final on a mutable type is a global variable ----
        MUTABLE_CONSTANT.add("this should worry you");
        System.out.println("static final List: " + MUTABLE_CONSTANT);

        try { TRULY_IMMUTABLE.add("nope"); }
        catch (UnsupportedOperationException e) {
            System.out.println("List.of is genuinely immutable — add() throws");
        }

        // ---- 3. Effectively final and lambda capture ----
        int captured = 5;
        Runnable r = () -> System.out.println("\nLambda captured: " + captured);
        r.run();
        // captured = 6;      // ← uncomment: the LAMBDA stops compiling

        // ---- 4. The array workaround vs the right tool ----
        List<String> words = List.of("a", "bb", "ccc", "dddd");

        int[] hack = {0};
        words.forEach(w -> hack[0] += w.length());
        System.out.println("Array hack:     " + hack[0]);

        AtomicInteger atomic = new AtomicInteger();
        words.forEach(w -> atomic.addAndGet(w.length()));
        System.out.println("AtomicInteger:  " + atomic.get());

        int proper = words.stream().mapToInt(String::length).sum();
        System.out.println("Stream (best):  " + proper);

        // ---- 5. Blank final ----
        final int b;
        if (args.length > 0) b = 1; else b = 2;      // assigned on EVERY path
        System.out.println("\nBlank final: " + b);
    }
}
```

**Then prove constant inlining** — this is worth doing, it surprises people:

```java
// Lib.java
public class Lib { public static final int VERSION = 1; }

// Client.java
public class Client {
    public static void main(String[] a) { System.out.println(Lib.VERSION); }
}
```

```bash
javac Lib.java Client.java
javap -c Client            # → look for: bipush 1   — the LITERAL is baked in

# now change VERSION to 2 in Lib.java
javac Lib.java             # recompile ONLY the library
java Client                # still prints 1 !!
javac Client.java && java Client   # now prints 2
```

**That's the compile-time constant inlining trap**, demonstrated end to end. It causes real confusion
in multi-module Maven builds where only one module is rebuilt.

## Common mistakes

| Mistake | Correction |
|---|---|
| "`final` means immutable" | It prevents reassignment. The object's contents are untouched. |
| `static final` on a mutable collection | A global mutable variable. Use `List.of` / `Map.of`. |
| Adding `final` to methods for speed | Obsolete. The JIT devirtualises speculatively. |
| Assuming a `final` field is deeply immutable | Only the reference is fixed. See [Day 034A](Day-034A.md). |
| Using an array to mutate from a lambda | A smell, and not thread-safe. Use a stream or an atomic. |
| Changing a `public static final` constant without recompiling clients | It's inlined into their bytecode. |
| Leaving classes non-final by default | Design for inheritance or prohibit it. |

## Interview questions

**Q: What does `final` mean on a variable?**
> That it can be assigned exactly once. For a primitive, the value is constant. For a reference, the
> binding is fixed but the object it points to is fully mutable — a `final List` can still be added to
> and cleared. `final` prevents reassignment, not mutation.

**Q: What's the difference between `final` and immutable?**
> `final` is a compile-time constraint on a variable binding. Immutability is a property of an
> object's design — no mutators, defensive copies, deeply immutable fields. A `final` reference to a
> mutable object is not immutable, and an immutable object can be held in a non-final variable.

**Q: Why must a lambda only capture effectively final variables?**
> The value is copied into the lambda when it's created. If the original could later be reassigned,
> the lambda would silently observe a stale value. Rather than allow that ambiguity, the language
> requires captured locals to be final or effectively final.

**Q: Does `final` on a method improve performance?**
> Not meaningfully on a modern JVM. The JIT performs speculative devirtualisation — it inlines a
> non-final method when only one implementation has been observed, with a guard to deoptimise if a
> second appears. Use `final` for design intent, not speed.

**Q: Why is `String` final?**
> To guarantee immutability, which the string pool, hash caching and security all depend on. A mutable
> subclass could be passed where a String is expected and changed after validation, creating a
> time-of-check-to-time-of-use vulnerability.

**Q: What guarantee does the memory model give `final` fields?**
> Once a constructor returns, any thread that obtains a reference to the object is guaranteed to see
> its `final` fields fully initialised, with no synchronisation. Non-final fields carry no such
> guarantee, so another thread can observe a partially constructed object. This is why immutable
> objects are safe to share freely.
