# Part 1 — The processes

```
postmaster (the supervisor)
  ├── backend process ← ⭐ ONE PER CONNECTION. Your session.
  ├── backend process
  ├── backend process
  ├── background writer   ── flushes dirty buffers gradually
  ├── checkpointer        ── ⭐ writes all dirty buffers at a checkpoint
  ├── WAL writer          ── ⭐ flushes the write-ahead log
  ├── autovacuum launcher ── ⭐ spawns workers (Day 194)
  ├── stats collector
  └── archiver            ── ships WAL segments for PITR (Day 201)
```

**⭐ One OS process per connection is the single most consequential architectural fact about
PostgreSQL**, and it explains Day 156's whole page:

- **A connection costs a process fork** — several megabytes of memory, plus scheduler overhead.
- **500 connections means 500 processes**, most idle, all consuming memory and context switches.
- **This is why the pool must be small** (Day 156's 10–20 fleet-wide), and why **PgBouncer** exists
  (Day 197) — it multiplexes thousands of client connections onto a few backend processes.

Compare with MySQL, which is thread-per-connection: cheaper connections, but shared address space
means a crashing connection can take the server with it. PostgreSQL chose isolation over cheapness,
and you pay for that choice in the connection pool.

# Part 2 — ⭐ Shared buffers, and the two-level cache

```
        your query
            │
            ▼
   ┌─ shared_buffers ─────────┐   ⭐ PostgreSQL's own cache, in 8KB pages
   │  (typically 25% of RAM)  │      shared by ALL backends
   └────────────┬─────────────┘
                │ miss
                ▼
   ┌─ OS page cache ──────────┐   ⭐ the kernel's cache — usually most of the rest of RAM
   └────────────┬─────────────┘
                │ miss
                ▼
            the disk           ⭐ ~100µs on NVMe, ~10ms on spinning rust
```

**⭐ The 25% rule surprises people who expect "give the database all the memory".** PostgreSQL
deliberately relies on the OS page cache as a second tier, so a large `shared_buffers` is
*double-caching* — the same page held twice, in two places, halving your effective cache. 25% of RAM
is the standard starting point; going much beyond 40% rarely helps and often hurts.

**Everything is an 8KB page.** A row lives in a page; an index entry points at a page; the buffer
cache holds pages; WAL records describe changes to pages. **When you read one 200-byte row,
PostgreSQL reads 8KB** — which is exactly why Day 110's covering indexes matter and why a table with
narrow rows scans far more efficiently than one with wide ones.

```sql
-- Is your working set in memory?
select sum(heap_blks_read)  as disk_reads,
       sum(heap_blks_hit)   as cache_hits,
       round(100.0 * sum(heap_blks_hit) / nullif(sum(heap_blks_hit) + sum(heap_blks_read),0), 2)
         as hit_ratio_pct
from pg_statio_user_tables;
```

**⭐ A cache hit ratio below ~95% on an OLTP workload usually means your working set does not fit** —
which is a memory or a query problem, not a tuning knob. And note the honest caveat: this counts
`shared_buffers` hits only, so a "miss" may still have been served from the OS page cache in
microseconds. It is a signal, not a verdict.

# Part 3 — ⭐⭐ The WAL, which is the answer to most durability questions

**The rule that makes PostgreSQL durable:**

> **⭐ Write-Ahead Logging: the change is written to the WAL and flushed to disk *before* the data
> page is modified on disk.**

```
COMMIT arrives
   1. WAL record written to the WAL buffer
   2. ⭐ WAL buffer FLUSHED to disk (fsync)   ← the commit waits here
   3. ⭐ COMMIT returns to the client
   ...
   4. the actual data page is written later, by the checkpointer or bgwriter
```

**⭐ This is the single most important thing to understand about database write performance.** A
commit does **not** wait for the data pages to be written — it waits for one **sequential** write to
the WAL. That is why:

- **commits are fast** even when they touch pages scattered across a 500 GB table;
- **the WAL disk's latency is your commit latency** — putting WAL on slow storage throttles every
  write in the system;
- **a crash loses nothing committed**: on restart, PostgreSQL replays the WAL from the last
  checkpoint and reconstructs every change.

It is also D-13's durability, implemented: `synchronous_commit = on` means the `fsync` in step 2
completes before the client is told "committed".

## ⭐ `synchronous_commit` — the one knob with a real trade

```sql
set synchronous_commit = off;      -- ⭐ session-level, for a bulk load
```

| Setting | Behaviour |
|---|---|
| `on` (default) | ⭐ commit waits for the WAL `fsync`. **No committed transaction is ever lost** |
| `off` | commit returns immediately; WAL flushed within `wal_writer_delay` (default 200ms) |

**⭐ `off` risks losing the last fraction of a second of committed transactions on a crash — but it
never corrupts the database.** That distinction matters: it is not "unsafe", it is "durability
relaxed by 200ms". Legitimate for bulk imports, analytics loads and non-critical audit writes;
**never** for payments.

**⭐ It is settable per transaction**, which is the useful part — keep it `on` globally and turn it
off for the one bulk job. That is a far better answer than changing it server-wide.

## Checkpoints, and the write spike people misdiagnose

**A checkpoint flushes every dirty buffer to disk** and records that the WAL before it is no longer
needed for recovery.

```
checkpoint_timeout = 5min          -- ⭐ raise to 15min on a write-heavy system
max_wal_size = 1GB                 -- ⭐ checkpoint also triggers when WAL exceeds this
checkpoint_completion_target = 0.9 -- ⭐ spread the writes over 90% of the interval
```

**⭐ The classic symptom: latency spikes every few minutes, in a regular rhythm.** That is a
checkpoint dumping every dirty page at once. The fixes are counter-intuitive in the same direction —
**longer intervals and larger `max_wal_size`**, so checkpoints are less frequent and
`checkpoint_completion_target` spreads each one out.

```sql
select * from pg_stat_bgwriter;         -- ⭐ checkpoints_timed vs checkpoints_req
```

**⭐ `checkpoints_req` much greater than `checkpoints_timed` means `max_wal_size` is too small** —
you are checkpointing because WAL filled up, not because time elapsed. That is the specific reading
that tells you which knob to turn.

# Part 4 — Where a row actually lives, and the fact that explains Day 194

```
Table (heap)
 ├── page 0 ─ tuple, tuple, tuple ...
 ├── page 1 ─ ...
 └── ...

Each tuple header carries: ⭐ xmin (creating txid) · xmax (deleting txid) · ctid
```

**⭐ PostgreSQL never updates a row in place.** An `UPDATE` writes a **new tuple version** and marks
the old one as deleted by setting `xmax`. A `DELETE` only sets `xmax`. The old version stays on the
page.

**Three enormous consequences, each of which gets its own later day:**

| Consequence | Day |
|---|---|
| ⭐ **Readers never block writers, writers never block readers** — MVCC (D-15) | 194 |
| ⭐ **Dead tuples accumulate; something must reclaim them** — `VACUUM` | 194 |
| ⭐ **An `UPDATE` may write to every index on the table**, because the tuple moved | 189 |

**The third is the one that surprises Java developers.** Updating a single unindexed column can
require updating six indexes, because the new tuple is at a new location and every index must point
to it. HOT (heap-only tuple) updates avoid this when the new version fits on the same page and no
indexed column changed — which is why `fillfactor` and index count are performance decisions, not
just correctness ones.

```sql
-- ⭐ see the versions yourself
select ctid, xmin, xmax, * from orders where id = 1;
update orders set total = total + 1 where id = 1;
select ctid, xmin, xmax, * from orders where id = 1;   -- ⭐ different ctid, different xmin
```

**Run that.** Watching the `ctid` change is the moment MVCC stops being an abstraction.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Large connection counts | one process each — memory and context switching (Day 156) |
| `shared_buffers` at 60–80% of RAM | double-caching with the OS page cache |
| WAL on slow storage | the WAL `fsync` is your commit latency |
| `synchronous_commit = off` globally | relaxes durability for payments to speed up a report |
| Believing `off` corrupts data | it does not — it loses the last ~200ms of commits |
| ⭐ Default `max_wal_size` on a write-heavy system | frequent forced checkpoints; rhythmic latency spikes |
| Ignoring `pg_stat_bgwriter` | the exact reading that names the knob, unused |
| Assuming updates are in-place | every index may need updating |
| Many indexes on a hot-write table | each `UPDATE` multiplies |

## Interview questions

**Q: What happens when you `COMMIT` in PostgreSQL?**
The WAL record is flushed to disk with an `fsync`, and only then does the commit return. The data
pages themselves are written later by the checkpointer. That is why a commit touching pages scattered
across a huge table is still fast — it is one sequential write — and why WAL disk latency is
effectively commit latency.

**Q: Why does PostgreSQL only use 25% of RAM for `shared_buffers`?**
Because it deliberately relies on the OS page cache as a second tier. A larger setting double-caches
the same pages in both places, reducing effective cache size rather than increasing it.

**Q: You see latency spikes every five minutes. What is your first hypothesis?**
Checkpoints. I would check `pg_stat_bgwriter` — if `checkpoints_req` dominates `checkpoints_timed`,
`max_wal_size` is too small and I am checkpointing on WAL volume. The fix is a larger
`max_wal_size`, a longer `checkpoint_timeout`, and `checkpoint_completion_target` near 0.9 to spread
the writes.

**Q: Why is one process per connection significant?**
Each connection costs a fork and several megabytes, so hundreds of connections is real memory and
scheduler pressure. That is why the pool has to be small and why PgBouncer exists to multiplex many
client connections onto few backends.

**Q: Does PostgreSQL update rows in place?**
No. An update writes a new tuple version and marks the old one dead via `xmax`. That gives MVCC —
readers never block writers — but it means dead tuples accumulate and need vacuuming, and an update
may have to touch every index on the table.

## Mini task

1. `select count(*) from pg_stat_activity;` then open ten connections and look at the OS process list.
   **Watch the processes appear.**
2. `show shared_buffers;` and compare to total RAM. Compute the percentage.
3. Query `pg_statio_user_tables` for your hit ratio. Then restart PostgreSQL and query again —
   **watch the cold cache.**
4. Run the `ctid`/`xmin` experiment above. Update the row five times and watch the `ctid` move.
5. Time 10,000 single-row inserts with `synchronous_commit = on`, then `off`. **Record both numbers.**
6. `select * from pg_stat_bgwriter;` under a write load. Set `max_wal_size = 128MB`, generate writes,
   and watch `checkpoints_req` climb.
7. Find the WAL directory (`pg_wal`) and watch segment files appear and get recycled during a load.
8. `kill -9` the postmaster mid-write-load, restart, and **read the recovery messages in the log.**
   Confirm no committed data was lost.

## 🎙️ Articulation drill

Two minutes: **"What happens between your `INSERT` and the data being on disk?"**

The backend process writes the change to the WAL buffer, the WAL is flushed with an `fsync`, and only
then does the commit return — the data page itself is written later by the checkpointer. Draw the
consequence out loud: commit latency is WAL disk latency, not table size, which is why a write to a
500 GB table is as fast as one to a small one. Then close on the fact that shapes the rest of the
stage: updates are not in place, so old versions accumulate — which gives you MVCC for free and
vacuum as the bill.
