# Part 1 — DRY, and its most common misuse

> **Don't Repeat Yourself: every piece of *knowledge* must have a single, unambiguous, authoritative
> representation within a system.**

Note what the original definition says: **knowledge**, not *code*. That word is where almost all DRY
mistakes come from.

```java
// ✅ genuine duplication — one piece of knowledge, three copies
if (order.total() > 1000)              { applyDiscount(); }   // OrderService
if (cart.total() > 1000)               { showBanner(); }      // CartController
if (invoice.amount() > 1000)           { requireApproval(); } // InvoiceService

// the knowledge is "1000 is the bulk threshold"
public static final Money BULK_THRESHOLD = Money.of(1000);
```

```java
// ❌ coincidental similarity — two DIFFERENT pieces of knowledge that look alike
class UserValidator    { boolean valid(String s) { return s != null && s.length() <= 50; } }
class ProductValidator { boolean valid(String s) { return s != null && s.length() <= 50; } }

// "unify" them and you get:
class LengthValidator { boolean valid(String s, int max) { … } }
// Then product names go to 200 chars. Now you have a parameter, two call sites to check,
// and a shared class coupling two unrelated domains for no reason.
```

The distinction:

> **If the two copies must change together, always, because they encode the same rule — that is
> duplication. If they merely look the same today, it is coincidence.**

The test: *when requirement X changes, must both change?* If you cannot answer yes with confidence,
leave them apart.

## The cost of the wrong abstraction

Sandi Metz's formulation is the one to remember:

> **Duplication is far cheaper than the wrong abstraction.**

Because the failure modes are asymmetric. Duplicated code is *visible* and easy to unify later. A
wrong abstraction is invisible and gets *worse* over time — each new caller adds a parameter or a
flag, until you have a method with five booleans that nobody dares touch, and unwinding it means
untangling every caller.

**The practical rule: prefer waiting.** Write it twice. On the third occurrence, look at all three
and ask whether they are the same knowledge. Often the third one reveals that the first two were
different all along.

**WET** — "Write Everything Twice" — is the deliberately provocative name for this discipline.

# Part 2 — YAGNI

> **You Aren't Gonna Need It.** Do not build for requirements you imagine you will have.

```java
// ❌ built for a future that never arrived
public interface PaymentProcessor { … }
public abstract class AbstractPaymentProcessor implements PaymentProcessor { … }
public class PaymentProcessorFactory { … }
public class PaymentProcessorRegistry { … }
public class StripePaymentProcessor extends AbstractPaymentProcessor { … }
// Four years later: still exactly one processor.
```

Every speculative abstraction costs:

- Code to write, read, test and maintain — forever.
- **Cognitive load on every future reader**, who must understand the extension mechanism to change
  anything.
- **And it is usually wrong**, because you guessed the wrong axis of variation. When the second
  payment provider finally arrives, it needs a different lifecycle, not a different `process()`.

**The counter-argument, stated fairly:** some things genuinely are expensive to retrofit — the
database's data model, the public API contract, the security model, and anything with data
migration attached. Those deserve upfront thought. **YAGNI applies to code structure; it does not
apply to data models and external contracts.** That distinction is the honest version.

## Where YAGNI and OCP collide

They are in direct tension, and interviews probe this:

- **OCP:** be open to extension.
- **YAGNI:** do not build extension points you do not need.

The resolution is timing, not compromise:

> **Write it simply. When the second case arrives, refactor to the abstraction *then* — with two real
> examples in front of you, so the abstraction fits reality rather than a guess.**

This works because refactoring toward an abstraction with tests in place is cheap (Day 096), while
un-building a wrong abstraction is expensive.

# Part 3 — KISS

> **Keep It Simple.** Given two solutions that work, prefer the one that is easier to understand.

```java
// ❌ clever
IntStream.rangeClosed(1, n).boxed()
    .collect(collectingAndThen(toMap(identity(), i -> i * i),
             m -> m.entrySet().stream().filter(e -> e.getValue() % 2 == 0)
                   .map(Map.Entry::getKey).collect(toList())));

// ✅ obvious
List<Integer> result = new ArrayList<>();
for (int i = 1; i <= n; i++) {
    if ((i * i) % 2 == 0) result.add(i);
}
```

> **Debugging is twice as hard as writing the code. So if you write it as cleverly as you can, you
> are by definition not smart enough to debug it.** — Kernighan

Simple is not the same as short. `a?b:c` chains, one-letter names and dense stream pipelines are
short and hard. **Simple means the reader can hold it in their head.**

# Part 4 — Composition over inheritance

## Why inheritance disappoints

Day 037 established the fragile base class problem; Day 091 showed inheritance producing LSP
violations. The summary of what inheritance costs:

| Problem | Detail |
|---|---|
| **Strongest coupling in OO** | A subclass depends on the superclass's *implementation*, not just its interface |
| **Fragile base class** | A change in the base silently breaks subclasses |
| **Single inheritance** | You get one; choose wrong and you cannot change it |
| **Fixed at compile time** | Behaviour cannot vary per instance or change at runtime |
| **Breaks encapsulation** | `protected` members are public API to every subclass, forever |
| **Combinatorial explosion** | 3 axes × 3 options = 27 subclasses |

```java
// ❌ inheritance for reuse — and it does not scale
class Bird { void fly() { … } }
class Penguin extends Bird { void fly() { throw new UnsupportedOperationException(); } }  // LSP

class Duck extends Bird { }
class RubberDuck extends Duck { }        // …cannot fly, cannot quack, is not alive
```

```java
// ✅ composition — behaviour as collaborators
public class Bird {
    private final FlightBehaviour flight;
    private final SoundBehaviour  sound;

    public Bird(FlightBehaviour flight, SoundBehaviour sound) {
        this.flight = flight; this.sound = sound;
    }
    public void fly()   { flight.fly(); }
    public void speak() { sound.make(); }
    public void setFlight(FlightBehaviour f) { … }    // ← can even change at RUNTIME
}

Bird penguin = new Bird(new CannotFly(), new Squawk());
Bird eagle   = new Bird(new PoweredFlight(), new Screech());
```

Three axes with three options each is 9 small classes and any combination — versus 27 subclasses you
must anticipate. That combinatorial argument is the strongest one to give in an interview.

## When inheritance *is* right

Do not over-correct — "never use inheritance" is as wrong as using it for everything.

Inheritance is correct when **all three** hold:

1. It is a genuine **IS-A** relationship *behaviourally* (LSP-substitutable).
2. The subclass **is a specialisation**, not just a reuser of code.
3. The hierarchy is **stable** — you are not going to want a different axis next quarter.

Good examples: `IOException extends Exception`, `ArrayList implements List`, sealed hierarchies for
algebraic data types (Day 042). Template Method (Day 095) is a legitimate inheritance pattern.

**The clinching question:** *am I inheriting to reuse code, or to be substitutable?* Reuse is a
composition job.

## Delegation and the JDK's own mistake

```java
// The classic Effective Java example
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;
    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);          // ← addAll calls add() internally. DOUBLE COUNTED.
    }
}
```

`addCount` ends up at 6 after adding 3 elements, because `HashSet.addAll` is implemented in terms of
`add`. **You cannot know that from the interface** — it is an implementation detail you have become
dependent on, and it can change in the next JDK release. That is the fragile base class problem in
eight lines.

The fix is composition with delegation:

```java
public class InstrumentedSet<E> implements Set<E> {
    private final Set<E> delegate;         // ← wraps, does not extend
    private int addCount = 0;

    public InstrumentedSet(Set<E> delegate) { this.delegate = delegate; }

    @Override public boolean add(E e) { addCount++; return delegate.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size(); return delegate.addAll(c);      // no internal self-call
    }
    // … remaining Set methods delegate
}
```

It also now works with `TreeSet`, `LinkedHashSet` and any future `Set` — which inheritance never
could.

# Part 5 — The Law of Demeter

> **Talk only to your immediate friends.** A method may call methods on: itself, its parameters, its
> own fields, and objects it creates.

```java
// ❌ a train wreck — reaches through three objects
double discount = order.getCustomer().getMembership().getTier().getDiscountRate();
```

Every `.` past the first is a **dependency on someone else's internal structure**. This one line
couples the caller to `Customer`, `Membership` and `Tier` — so a change to *any* of them breaks this
code, and no compiler warning tells you where else you reached.

```java
// ✅ ask the object you know
double discount = order.discountRate();      // Order asks Customer, Customer asks Membership…
```

**"Tell, don't ask"** is the same idea from the other direction: instead of pulling data out to make
a decision, tell the object that owns the data to make it.

```java
// ❌ ask
if (account.getBalance() >= amount) { account.setBalance(account.getBalance() - amount); }

// ✅ tell — and now the invariant lives with the data
account.withdraw(amount);
```

The second version can enforce the overdraft rule, log the transaction, and be made thread-safe in
one place. The first version has scattered that responsibility to every caller — and the invariant
will be violated by the one caller who forgets the check.

**The exceptions**, which are real:

```java
// Fluent builders — each call returns the SAME object, not a new dependency
Order.builder().customer(c).item(i).build();

// Streams — same
list.stream().filter(…).map(…).toList();

// Data structures you legitimately traverse
config.get("db").get("host")
```

The law is about **not depending on the structure of a graph of collaborators**. A builder chain is
one object; a stream chain is one pipeline. Chaining on a data structure you own is fine.

# Part 6 — Resolving the conflicts

This is the section that matters most, because the principles genuinely disagree:

| Tension | Resolution |
|---|---|
| DRY vs the wrong abstraction | Duplicate until the third occurrence proves it is one piece of knowledge |
| OCP vs YAGNI | Write it simply; abstract when the second real case arrives |
| SRP vs cohesion | Split by *actor*, not by method count |
| Abstraction vs KISS | Abstract only where variation is real, not imagined |
| DIP vs YAGNI | Introduce an interface for a test seam or a real second implementation — not on principle |

The meta-rule underneath all of them:

> **Optimise for the cost of change, and remember that you do not know the future.** Prefer designs
> that are *easy to change later* over designs that try to be *already correct for later*.

That is why simplicity and duplication are often the better bet: both are cheap to fix once reality
arrives. A wrong abstraction is not.

---

## Common mistakes

| Mistake | Consequence |
|---|---|
| DRY applied to code rather than knowledge | Coupled, unrelated domains |
| Extracting on the second occurrence | Wrong abstraction; parameters accrue |
| Speculative interfaces and factories | Permanent cost, wrong axis |
| YAGNI applied to the data model | Expensive migrations later |
| Clever over obvious | Nobody can debug it, including you |
| Inheritance for code reuse | Fragile base class, LSP violations |
| Extending a JDK collection | Depends on internal self-calls |
| Train wrecks (`a.getB().getC()`) | Coupled to structure three levels deep |
| Ask instead of tell | Invariants scattered across callers |
| Quoting a principle to win an argument | Over-engineering with a defence |

## Interview questions

**Q: What does DRY actually say?**
Every piece of *knowledge* has one authoritative representation. It is about knowledge, not identical
lines — two methods that look alike but encode different rules should stay apart.

**Q: When is duplication better than abstraction?**
When you are not yet sure the copies represent the same knowledge. Duplication is visible and cheap
to remove; the wrong abstraction is invisible and gets worse as callers add parameters to bend it.

**Q: How do you reconcile YAGNI and Open/Closed?**
By timing. Write the simple version; when the second real case arrives, refactor to the abstraction
with two concrete examples in front of you. And note YAGNI applies to code structure, not to data
models or public contracts, which are expensive to change.

**Q: Why composition over inheritance?**
Inheritance is the strongest coupling in OO — you depend on the superclass's implementation, you get
only one, it is fixed at compile time, and combinations explode. Composition gives runtime
flexibility and any combination from a handful of small classes.

**Q: When is inheritance the right choice?**
A genuine behavioural IS-A, a real specialisation rather than code reuse, and a stable hierarchy.
Template Method and sealed algebraic hierarchies are legitimate uses.

**Q: What is the Law of Demeter, and what are its exceptions?**
Talk only to immediate collaborators — every extra `.` couples you to another object's structure.
Fluent builders, stream pipelines and traversing a data structure you own are not violations,
because you are not depending on a graph of collaborators.

**Q: What is "tell, don't ask"?**
Instead of pulling data out to decide, tell the object that owns the data to act — so the invariant
lives with the data rather than being re-implemented by every caller.

## Mini task

1. Find two similar methods in your code. Decide whether they are one piece of knowledge, and write
   down the requirement change that would prove it either way.
2. Find a "clever" line you wrote and rewrite it obviously. Time how long each takes to understand
   cold after a day away.
3. Find an interface with one implementation and no second one planned. Inline it and note what got
   simpler.
4. Implement `InstrumentedHashSet` by extension, reproduce the double-count, then rewrite it with
   delegation and confirm it works with `TreeSet` too.
5. Take an inheritance hierarchy you have with three or more levels and redesign it with composition.
   Count the classes each way and the combinations each supports.
6. Find a train wreck. Fix it by moving the behaviour to the object that owns the data.
7. Find an "ask" pattern where a caller reads state, decides, then writes it back. Convert it to
   "tell" and note the concurrency bug you just fixed (Day 065).
8. Write down, for one real decision in your code, which two principles conflicted and how you chose.

## 🎙️ Articulation drill

Two minutes: **"When would you *not* apply DRY?"**

This is a good interview question because reciting principles cannot answer it. Lead with knowledge
versus code, give a concrete pair of coincidentally-similar validators, state the asymmetry of costs,
and finish with the rule of three. Being able to argue *against* a principle you understand is the
clearest signal of seniority available in a design conversation.
