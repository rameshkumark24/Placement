# Part 1 — Configuration and startup

| # | Item | Built on |
|---|---|---|
| 1 | ⭐ **All environment-varying config from outside the image**; one image promoted | Day 142, Day 129B |
| 2 | ⭐ **Typed, validated `@ConfigurationProperties`** — missing config fails the deploy, not the customer | Day 142 |
| 3 | Secrets from env vars, config tree or a manager — **never committed** | Day 142, Day 085 |
| 4 | ⭐ `spring.jpa.hibernate.ddl-auto: validate` | Day 157 |
| 5 | ⭐ `spring.jpa.open-in-view: false` | Day 139, Day 156 |
| 6 | Flyway owns the schema; large migrations run as a separate step | Day 166 |
| 7 | ⭐ `server.shutdown: graceful` + executor drain + a pre-stop delay | Day 133, Day 177 |
| 8 | Profiles change **values**, not implementations | Day 136, Day 142 |

**⭐ Item 2 is the highest-leverage line on this page.** A `@NotBlank` on a required property turns a
misconfiguration into a failed deploy that rolls back automatically — instead of a service that
starts healthy and fails on the first real customer request.

**⭐ Item 7's detail people miss:** graceful shutdown must be preceded by a delay *after* the pod is
marked unready, because load balancers take seconds to notice. Shutting down the instant `SIGTERM`
arrives drops in-flight requests that were routed a moment earlier.

**⭐ Item 22 is the one that has caused real outages** in exactly the way Day 128 described: a
database check in the liveness probe turns a database outage into every pod crash-looping, removing
the capacity that could have served degraded responses.

that silently stopped is invisible for weeks. Day 178's `absent_over_time` alert.

**⭐ Item 30 is not paperwork.** An alert with no runbook wakes someone who then has to reconstruct
the system's behaviour at 3 a.m. Three sentences per alert is enough.

**⭐ Item 39 deserves its emphasis.** Every organisation has backups. A meaningful proportion discover
during an incident that they cannot restore them, or that the restore takes eleven hours, or that the
one table that matters was excluded. **Restore into a scratch environment on a schedule and time it.**

## The release itself

| # | Item |
|---|---|
| 46 | ⭐ **Rolling deploy, and both versions run simultaneously** — Day 166's constraint |
| 47 | ⭐ **A rollback that has been tested**, not assumed |
| 48 | Feature flags for risky changes, so release and deploy are separate decisions |
| 49 | ⭐ **Load tested at expected peak**, not at "it seemed fine" |
| 50 | ⭐ **A named owner and an on-call rotation** |

**⭐ Item 46 is the constraint that makes half of Day 166 necessary**, and it applies to more than the

running beside them.

## ⭐ The ranked short list

**If you have one day, do these five. They are ordered by the size of the outage each prevents.**

1. ⭐ **Timeouts on every outbound call** (12) — prevents total service death from someone else's problem.
2. ⭐ **Liveness/readiness split correctly** (22) — prevents turning a dependency outage into a crash loop.
3. ⭐ **Validated configuration** (2) — turns a misconfiguration into a rolled-back deploy.
4. ⭐ **A tested restore** (39) — the only item on this list where the failure is unrecoverable.
5. ⭐ **Dependency scanning** (38) — most breaches are a known CVE, not novel research.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Treating the checklist as paperwork | every item is here because it caused an outage |
| ⭐ Untested backups | discovered during the incident |
| ⭐ Untested rollback | a plan, not a capability |
| No owner | nobody notices when it degrades |
| Alerts with no runbook | someone reconstructs the system at 3 a.m. |
| Load testing skipped | capacity discovered by customers |
| Feature release coupled to deploy | every risky change needs a rollback rather than a flag |
| Config differing between staging and production | staging proves nothing |
| ⭐ Missing timeouts | the most common Java outage |
| Alerting on everything | alert fatigue; the real one is ignored |

## Interview questions

**Q: What does "production-ready" mean to you?**
That the service degrades rather than collapses, that a failure is diagnosable without a code change,
and that a bad deploy is reversible. Concretely: timeouts and circuit breakers on every dependency,
liveness and readiness split so a dependency outage does not crash-loop the fleet, validated
configuration so a misconfiguration fails the deploy, structured logs with a correlation id, alerts
with runbooks, and a restore and a rollback that have both actually been tested.

**Q: If you had one day on an unfamiliar service, what would you check?**
Outbound timeouts first — that is the most common way a Java service dies from someone else's outage.
Then whether liveness contains dependency checks, whether required configuration is validated at
startup, whether a restore has ever been performed, and whether dependencies are scanned.

**Q: What is the most commonly missed item?**
Timeouts, and second, alerting on job *non-execution*. A failing job is noisy; a job that silently
stopped running is invisible for weeks.

**Q: How do you deploy a schema change safely?**
Expand and contract, because a rolling deploy runs two versions of the code against one schema. Add
the new column, write both, backfill in batches, switch reads, stop writing the old, wait long enough
to keep the rollback path, then drop.

## Mini task

**Run the full 50-item checklist against a real service** — one you have built in this stage, or an
open-source Spring Boot application from GitHub.

1. Score each item: ✅ / ⚠️ / ❌ / N/A.
2. For every ❌, write **one sentence on the failure it enables**.
3. Rank by (likelihood × blast radius). Take the top five.
4. Fix them.
5. **Prove three of them by breaking something**: kill the database and confirm the pods do not
   crash-loop; make a dependency hang and confirm the request times out; delete a required property
   and confirm startup fails.
6. Perform an actual restore from backup into a scratch database. **Time it.** Write the number down.
7. Write a runbook for your three most important alerts. Three sentences each.
8. Practise a rollback, end to end.

## 🎙️ Articulation drill

Three minutes: **"How do you know a service is ready for production?"**

Do not recite fifty items. Give the three properties — it degrades rather than collapses, failures are
diagnosable without a code change, and a bad deploy is reversible — then support each with the two or
three concrete items that deliver it, naming the outage each prevents. Finish with the ranked short
list and say why timeouts are first: they are the difference between a dependency having a bad day
and your service having one.
