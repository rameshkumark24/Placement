# Day 271 🏗️

**J-271** · 🏗️ **The flagship's UI I** — ⭐⭐ the screen list, and what you refuse to build

**Time:** 3 hrs · **Mode:** BUILD · **⭐ The flagship frontend opens**

> ⭐⭐ **The sentence to own: the frontend is where projects die, because the UI has no natural
> stopping point — the backend is finished when the endpoints work and the tests pass, and the UI is
> "nearly done" forever — so the scope you write down today is the only thing that will make you
> stop.**
>
> Today: ⭐ the screen inventory, ⭐⭐ the cut list, the demo path, and the ninety-second rule.

# Part 1 — ⭐⭐ Why this is a scoping day, not a coding day

```
⭐⭐ HOW FLAGSHIP PROJECTS ACTUALLY FAIL

⭐   ⭐ NOT: "the backend was too hard"
⭐   ⭐ NOT: "I couldn't learn React"
⭐   ⭐⭐ BUT: 40 hours into a UI, 14 half-finished screens, nothing
⭐     demonstrable end to end, and ⭐ NO DATE ON WHICH IT COULD
⭐     POSSIBLY BE FINISHED.

⭐   ⇒ ⭐⭐ THE BACKEND HAD A DEFINITION OF DONE — the endpoints work
⭐     and the tests are green. ⭐ THE UI HAS NONE UNLESS YOU WRITE ONE.
```

| ⭐ The rule for these ten days | |
|---|---|
| **⭐⭐ One workflow, complete, beats six workflows, partial** | An interviewer follows one path. A half-built settings page adds nothing and costs a week. |
| **Every screen serves the demo** | ⭐ If it is not on the demo path, it is on the cut list |
| **⭐ Polish the path, not the app** | Four states (Day 240) on the demo path beats ten mediocre screens |
| **⭐⭐ You will be asked what you left out** | And *"here's the cut list and why"* is a **better** answer than a bigger app |

# Part 2 — The screen inventory

Write this on paper before you open an editor.

```
⭐⭐ FOR EVERY SCREEN, FIVE COLUMNS:

⭐   SCREEN | ⭐ WHAT IT PROVES | API CALLS | ⭐⭐ STATES | ON DEMO PATH?

⭐ ⭐⭐ THE MINIMUM VIABLE FLAGSHIP UI — FIVE SCREENS:
⭐   ① ⭐ LOGIN            ⇒ proves auth works end to end
⭐   ② ⭐⭐ THE LIST        ⇒ proves filtering, pagination, empty states
⭐   ③ ⭐⭐ THE DETAIL      ⇒ proves the domain model is real
⭐   ④ ⭐⭐ THE ACTION      ⇒ the ONE thing your app exists to do
⭐   ⑤ ⭐ THE RESULT       ⇒ proves the workflow completes and is visible

⭐   ⇒ ⭐⭐ THAT IS THE WHOLE DEMO. Everything else is optional and
⭐     most of it is a distraction.
```

| ⭐ Column | Why it is there |
|---|---|
| **What it proves** | ⭐⭐ A screen that proves nothing about your system is decoration. Delete it. |
| **API calls** | ⭐ More than two is a Day 214 finding — fix the API |
| **⭐⭐ States** | Forces you to plan loading/error/empty/success **before** building success only |
| **On demo path** | ⭐ The cut line |

# Part 3 — ⭐⭐ The cut list

```
⭐⭐ WRITE THESE DOWN AS **DELIBERATELY NOT BUILT**, NOT AS "TODO".
⭐   ⭐ A TODO reads as unfinished; a cut list reads as JUDGEMENT.
⭐     ⭐⭐ SAME WORK, OPPOSITE SIGNAL.

⭐ ❌ CUT, ALMOST ALWAYS
⭐   · ⭐ a settings page      ⇒ proves nothing, costs days
⭐   · ⭐⭐ ADMIN CRUD FOR EVERY ENTITY ⇒ the classic time sink, and
⭐     the one a Spring developer is most tempted by because the
⭐     repositories already exist
⭐   · dark mode              ⇒ ⭐ unless it is one token block
⭐   · a dashboard of charts  ⇒ ⭐⭐ looks impressive, proves nothing,
⭐                               and a chart library is 300 KB
⭐   · onboarding / tours     · notifications centre
⭐   · ⭐ MOBILE-SPECIFIC LAYOUTS ⇒ responsive-enough is enough

⭐ ✅ KEEP, ALWAYS
⭐   · ⭐⭐ THE FOUR STATES ON THE DEMO PATH
⭐   · ⭐ auth, including the expired-session path
⭐   · ⭐⭐ THE ONE THING THAT MAKES YOUR DOMAIN INTERESTING
⭐   · error handling that names what happened
```

> ⭐⭐ **The cut list is interview material.** Day 487's lesson: *"I decided not to build…"* is the
> single strongest scope sentence available to you, and it only exists if you wrote the decision down
> at the time. **Record the reason next to each cut, today.**

# Part 4 — The demo path and the ninety-second rule

```
⭐⭐ WRITE THE DEMO SCRIPT NOW — BEFORE THE CODE.

⭐   0:00  ⭐ "This is X. It solves Y." (⭐⭐ ONE SENTENCE, NO PREAMBLE)
⭐   0:15  log in
⭐   0:25  ⭐ the list — point at a filter, point at the empty state
⭐   0:45  ⭐⭐ THE ACTION — the interesting thing your app does
⭐   1:10  the result, visible
⭐   1:25  ⭐⭐ "AND HERE IS WHAT HAPPENS WHEN IT FAILS" ← ⭐ THE PART
⭐         NOBODY ELSE DEMOS, AND THE PART THAT LANDS
⭐   1:30  stop.

⭐   ⇒ ⭐⭐ IF THE SCRIPT NEEDS A SCREEN, BUILD IT. IF NOT, IT IS ON
⭐     THE CUT LIST. ⭐ THE SCRIPT IS THE SPEC.
```

| ⭐ Rule | |
|---|---|
| **Ninety seconds** | ⭐ Roughly what you get before questions start. Plan for the interruption. |
| **⭐⭐ Demo a failure on purpose** | Kill the API mid-demo and show the error state and retry. **Almost nobody does this.** |
| **Seed real-looking data** | ⭐ "Test User 1" and `asdf` make a working app look broken. A `data.sql` or a seed profile is 30 minutes. |
| **⭐ No console errors** | Interviewers open DevTools |

---

## Today's build

1. ⭐⭐ **Write the five-column screen inventory on paper.** Be honest about how many screens you imagined.
2. ⭐⭐ **Draw the cut line.** Move everything off the demo path into a written cut list — **with a reason each**.
3. ⭐ Write the ninety-second demo script, timed with an actual timer.
4. For each surviving screen, list its API calls. ⭐⭐ **Any screen needing 3+ is an API design finding — write it down.**
5. ⭐ Write the four states for each surviving screen. **Now you have a build plan for nine days.**
6. Set up the project: Vite + React + TS + your token file + the client generated from `/v3/api-docs` (Day 246).

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how did you decide what to build in the UI?"**

Lead with the failure mode you were avoiding. **The backend has a definition of done: the endpoints
work and the tests are green. A UI doesn't, so it's "nearly done" forever. That's how these projects
die — forty hours in, fourteen half-finished screens, nothing demonstrable end to end. So I wrote the
scope down before writing code.**

Then the method. **I inventoried every screen with five columns: what it proves, its API calls, its
states, and whether it's on the demo path. Anything off that path went onto a written cut list with a
reason. Five screens survived — login, list, detail, the action the app exists for, and the result. One
workflow complete beats six partial, because an interviewer follows one path.**

Then the finding, tied back to the backend. **The API-calls column immediately showed a screen needing
four round trips. That's an API design problem I couldn't see from the server, and I fixed the contract
rather than the UI.**

Close on the cut list as an asset. **The biggest cut was admin CRUD for every entity — which is the one
a Spring developer is most tempted by, because the repositories already exist and it feels almost free.
It isn't: it's days of work that proves nothing. "I decided not to build it, here's why" is a stronger
answer than a bigger app, and it only exists because I wrote the reason down at the time.**
