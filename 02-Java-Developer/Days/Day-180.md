# Day 180

**L-180** · WebSockets and STOMP — real-time, and the three things that break at scale

**Time:** 3 hrs · **Mode:** NEW

> WebSockets are the answer to "the server needs to push", and they are also the point at which a
> stateless HTTP service becomes **stateful and connection-oriented** — which changes load balancing,
> deployment, authentication and capacity planning all at once.
>
> Today: the protocol, Spring's STOMP support, and the three problems every WebSocket deployment hits
> — **scaling across instances, authentication, and what a deploy does to 50,000 open connections.**

# Part 1 — Choosing the transport honestly

| Option | Direction | Use |
|---|---|---|
| **Polling** | client pulls | ⭐ **underrated.** If 30-second freshness is fine, this is the whole solution |
| **Long polling** | client pulls, server holds | legacy fallback |
| ⭐ **SSE** (`text/event-stream`) | ⭐ **server → client only** | ⭐ **notifications, live dashboards, progress, LLM token streams.** Plain HTTP, auto-reconnects, works through every proxy |
| **WebSocket** | ⭐ full duplex | chat, collaborative editing, trading, multiplayer |

**⭐ Server-Sent Events are the right answer far more often than they are chosen.** If the client only
ever *receives*, SSE gives you push over ordinary HTTP/2: no protocol upgrade, no special proxy
configuration, automatic reconnection with `Last-Event-ID` built into the browser, and normal
`Authorization` headers.

```java
@GetMapping(value = "/api/v1/orders/{id}/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@PathVariable UUID id) {
    SseEmitter emitter = new SseEmitter(Duration.ofMinutes(30).toMillis());   // ⭐ always a timeout
    registry.register(id, emitter);
    emitter.onCompletion(() -> registry.remove(id, emitter));                 // ⭐⭐ or you leak
    emitter.onTimeout(()    -> registry.remove(id, emitter));
    emitter.onError(e       -> registry.remove(id, emitter));
    return emitter;
}
```

**⭐ Every emitter must be removed on all three callbacks.** A registry of dead emitters is a memory
leak that grows with every disconnect — and disconnects are constant on mobile.

**Choose a WebSocket only when the client genuinely needs to send too.** The complexity below is the
price.

# Part 2 — STOMP over WebSocket

```java
@Configuration
@EnableWebSocketMessageBroker
class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws")
                .setAllowedOrigins("https://app.acme.com");    // ⭐⭐ NOT "*" — Day 155
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.setApplicationDestinationPrefixes("/app");    // client → server
        registry.enableSimpleBroker("/topic", "/queue");       // ⚠️ in-memory — see Part 3
        registry.setUserDestinationPrefix("/user");            // ⭐ per-user destinations
    }
}
```

```java
@Controller
public class ChatController {

    @MessageMapping("/chat/{roomId}")                          // ⭐ client sends to /app/chat/42
    @SendTo("/topic/rooms/{roomId}")                           // ⭐ broadcast
    public ChatMessage handle(@DestinationVariable String roomId, ChatMessage msg, Principal user) {
        return new ChatMessage(user.getName(), msg.text(), Instant.now());
    }
}
```

```java
// Push from anywhere in the application
messagingTemplate.convertAndSendToUser(userId, "/queue/notifications", payload);
```

**⭐ Why STOMP rather than raw WebSocket frames:** raw WebSockets give you a byte pipe and nothing
else — no destinations, no subscriptions, no message types. STOMP adds an addressing model, which is
what lets Spring route messages to `@MessageMapping` handlers and lets clients subscribe to topics.
Without it you write that dispatch layer yourself, badly.

**⭐ `setAllowedOrigins("*")` is a real vulnerability.** The WebSocket handshake is **not covered by
the same-origin policy** the way `fetch` is — any page can open a WebSocket to your server. If the
connection is authenticated by a cookie, this is **Cross-Site WebSocket Hijacking**: `evil.com` opens
an authenticated socket and reads everything. **Always pin the origin, and prefer token
authentication over cookies.**

# Part 3 — ⭐ The three problems

## ⭐ Problem 1 — the simple broker does not scale

```java
registry.enableSimpleBroker("/topic");     // ⭐ subscriptions live in THIS JVM's memory
```

```
Alice → instance 1, subscribed to /topic/rooms/42
Bob   → instance 2, sends to /topic/rooms/42
⭐ Alice never receives it.
```

**Instance 2 has no idea Alice exists.** Everything works with one instance and silently breaks the
day you scale — messages are simply not delivered, with no error anywhere.

| Fix | Trade-off |
|---|---|
| **Sticky sessions** | ⭐ only helps if both parties land on the same instance — for a shared room, they will not |
| ⭐ **An external broker relay** | **the correct answer** |
| Redis pub/sub fan-out | ⭐ pragmatic — each instance subscribes and re-broadcasts locally |

```java
registry.enableStompBrokerRelay("/topic", "/queue")      // ⭐ RabbitMQ / ActiveMQ speaking STOMP
        .setRelayHost(brokerHost)
        .setClientLogin(user).setClientPasscode(pass)
        .setSystemHeartbeatSendInterval(10_000);
```

**Now the broker owns subscriptions and routing**, and instances are stateless with respect to
message delivery. That is what makes horizontal scaling work.

**The Redis pub/sub alternative** is lighter: every instance subscribes to a Redis channel and
re-publishes to its own local simple broker. Good enough for notifications; it gives you no
durability, no acknowledgements and no delivery guarantees, so do not use it where messages matter.

## ⭐ Problem 2 — authentication

**The WebSocket handshake is an HTTP request, so Spring Security's filter chain runs on it — once.**
After the upgrade there are no more HTTP requests, so **there is no per-message authentication unless
you add it.**

```java
@Component
public class StompAuthChannelInterceptor implements ChannelInterceptor {

    @Override
    public Message<?> preSend(Message<?> message, MessageChannel channel) {
        var accessor = StompHeaderAccessor.wrap(message);

        if (StompCommand.CONNECT.equals(accessor.getCommand())) {
            String token = accessor.getFirstNativeHeader("Authorization");     // ⭐ from the CONNECT frame
            Authentication auth = jwtService.authenticate(strip(token));       // Day 173
            accessor.setUser(auth);                                            // ⭐ bound to the session
        }
        return message;
    }
}
```

**⭐ Three rules that follow:**

1. **Authenticate on the STOMP `CONNECT` frame, not the handshake.** Browsers cannot set custom
   headers on a WebSocket handshake, so a bearer token cannot travel there — which is why so many
   implementations fall back to a cookie and inherit the hijacking problem above.
2. ⭐ **Never put the token in the URL** (`/ws?token=...`). It lands in access logs, proxy logs and
   browser history. If you must, use a **single-use, short-lived ticket** obtained from an
   authenticated HTTP call.
3. ⭐ **Authorize every SUBSCRIBE.** A connected user can subscribe to *any* destination unless you
   check — so `/topic/rooms/42` is readable by someone who was never in room 42. This is Day 174's
   IDOR, over a different transport:

```java
if (StompCommand.SUBSCRIBE.equals(accessor.getCommand())) {
    String destination = accessor.getDestination();
    if (!roomGuard.maySubscribe(accessor.getUser(), destination)) {
        throw new AccessDeniedException("not a member");           // ⭐ the check nobody writes
    }
}
```

**⭐ And the token-expiry problem:** a JWT verified at CONNECT is never re-checked, so a 15-minute
token authorises a connection that may live for hours. Either re-validate periodically on the
inbound channel, or bound the connection's lifetime to the token's.

## ⭐ Problem 3 — deploys and connection capacity

**Every deploy drops every connection.** With 50,000 clients that is a **reconnect thundering herd**
— all of them at once, all re-authenticating, all re-subscribing, all re-fetching missed state.

| Mitigation | Detail |
|---|---|
| ⭐ **Client-side reconnect with jittered backoff** | Day 123's full jitter. Without it, they return in one synchronised wave |
| **Rolling deploys with a drain period** | `server.shutdown: graceful` plus a delay (Day 133) |
| ⭐ **Resume by `Last-Event-ID`** | so a reconnect does not require a full state refetch |
| Separate the WebSocket service | ⭐ deploy it far less often than the API |

**Capacity is also different from HTTP.** Each connection holds a socket, buffers and session state —
so plan by *concurrent connections*, not requests per second, and set limits:

```java
registry.setMessageSizeLimit(64 * 1024);          // ⭐ per message
registry.setSendBufferSizeLimit(512 * 1024);      // ⭐ per session — a slow consumer otherwise
registry.setSendTimeLimit(20_000);                //   accumulates unbounded server memory
```

**⭐ A slow client with no send-buffer limit is a memory leak with a heartbeat.** Messages queue in
the server's buffer for a consumer that is not draining them.

Also: **enable heartbeats**, or dead connections (a phone that lost signal) linger and consume
resources until a TCP timeout that may be many minutes away.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| WebSockets where SSE would do | protocol upgrade, proxy issues, statefulness, for one direction |
| `SseEmitter` without removal on all three callbacks | memory leak growing with every disconnect |
| ⭐ `setAllowedOrigins("*")` | Cross-Site WebSocket Hijacking |
| Cookie authentication on WebSockets | combines with the above into a full read of the user's stream |
| ⭐ Simple broker with multiple instances | messages silently undelivered |
| Sticky sessions as the scaling fix | does not help two users in one room on different instances |
| ⭐ No SUBSCRIBE authorization | any user reads any destination |
| Token in the query string | logged everywhere |
| No token re-validation | a 15-minute token authorises a 6-hour connection |
| No send-buffer limit | one slow consumer exhausts server memory |
| No heartbeats | dead connections linger |
| No jittered client reconnect | thundering herd on every deploy |
| Capacity planned in RPS | the constraint is concurrent connections |

## Interview questions

**Q: WebSocket or SSE?**
SSE unless the client genuinely needs to send. It is plain HTTP, so it passes through proxies,
supports normal `Authorization` headers, and the browser reconnects automatically with
`Last-Event-ID`. WebSockets are for full duplex — chat, collaborative editing — and they cost you
statefulness, connection-based capacity planning and a deploy story.

**Q: Why does your WebSocket app break when you scale to two instances?**
The simple broker keeps subscriptions in that JVM's memory, so a message sent on instance 2 never
reaches a subscriber on instance 1. There is no error — messages are just not delivered. The fix is
an external STOMP broker relay so the broker owns routing, or Redis pub/sub fan-out for
non-critical notifications.

**Q: How do you authenticate a WebSocket?**
On the STOMP `CONNECT` frame with a bearer token, because browsers cannot set custom headers on the
handshake and cookie authentication exposes you to cross-site WebSocket hijacking. Then authorize
every SUBSCRIBE — a connected user can otherwise subscribe to any destination, which is IDOR over a
different transport.

**Q: What happens on deploy?**
Every connection drops and every client reconnects at once. Clients need jittered backoff, the
server needs a graceful drain, and ideally the reconnect resumes from a last-event id rather than
refetching all state. It is also an argument for deploying the WebSocket service separately from the
API.

## 🎙️ Articulation drill

Two minutes: **"How would you add real-time updates to your service?"**

Start by narrowing the requirement — if it is server-to-client only, SSE, and give the three reasons.
Then WebSockets with STOMP where full duplex is genuinely needed, and go straight to the three
problems that decide the architecture: the in-memory broker silently fails to deliver across
instances so you need a broker relay; authentication happens once at CONNECT so every SUBSCRIBE needs
its own authorization check; and every deploy drops every connection, so clients need jittered
reconnect and the service is a candidate for separate deployment.
