# Part 1 — Controlled vs uncontrolled

```jsx
// ⭐ CONTROLLED — React owns the value
<input value={name} onChange={e => setName(e.target.value)} />
// ⭐⭐ re-renders on EVERY KEYSTROKE. Fine for 5 fields.

// ⭐ UNCONTROLLED — the DOM owns it, you read it at submit
<input name="name" defaultValue={user.name} />
const data = Object.fromEntries(new FormData(e.target));
// ⭐⭐ NO re-renders while typing. What form libraries do.
//    ⭐ Closest to a plain HTML form POST, which you know from Thymeleaf.
```

| ⭐ Use controlled when | ⭐ Use uncontrolled when |
|---|---|
| You need the value **as it changes** — live search, a character counter | ⭐⭐ Most forms. You only need values at submit. |
| Cross-field logic on every keystroke | Big forms where typing lag appears |

> ⭐ **`value` without `onChange` makes an input read-only and React warns.** Switching a field between
> controlled and uncontrolled mid-life is a genuine warning you should never silence.

# Part 2 — ⭐⭐ One contract, two validators

```typescript
// schema.ts — ⭐⭐ ONE definition. Day 219's Zod, doing double duty.
export const CreateUser = z.object({
  email: z.string().email("Enter a valid email"),
  age: z.number().int().min(18, "Must be 18 or over"),
  role: z.enum(["admin", "user"]),
});
export type CreateUser = z.infer<typeof CreateUser>;
```

```java
// ⭐ the SAME rules on the server — the boundary that actually protects you
public record CreateUserDto(
    @Email                       String email,
    @Min(18)                     int age,
    @NotNull                     Role role
) {}

@PostMapping("/users")
User create(@Valid @RequestBody CreateUserDto dto) { ... }
```

```
⭐⭐ WHY BOTH, AND WHY THAT IS NOT DUPLICATION

⭐   CLIENT ⇒ ⭐ UX. Instant feedback, no round trip, no lost typing.
⭐            ⭐⭐ IT IS NOT SECURITY. curl ignores it entirely.
⭐   SERVER ⇒ ⭐⭐ THE ACTUAL BOUNDARY. @Valid is the only one that
⭐            counts. Assume every request is hand-crafted.

⭐   ⇒ ⭐⭐ THE REAL RISK IS NOT DUPLICATION — IT IS **DRIFT**.
⭐     You change @Min(18) to @Min(21); the client still says 18
⭐     ⇒ the user submits a valid-looking form and gets a mystery
⭐       rejection.
⭐   ⇒ ⭐ FIX: GENERATE ONE FROM THE OTHER (Day 246 — your OpenAPI
⭐     schema already carries `minimum` from @Min), or keep both in
⭐     one reviewed file with a test asserting they agree.
```

> ⭐ **springdoc emits your Bean Validation constraints into the OpenAPI schema.** That is not a
> coincidence you should ignore — **it is the mechanism that makes Day 246's generated client carry
> your rules for free.**

# Part 3 — ⭐⭐ Landing the server's error on the right field

The payoff of Day 217's `ProblemDetail`.

```jsx
const form = useForm({ resolver: zodResolver(CreateUser) });

const onSubmit = form.handleSubmit(async (values) => {
  try {
    await api("/users", { method: "POST", body: values });
  } catch (e) {
    if (e instanceof ApiError && e.status === 400) {
      for (const { field, message } of e.body.errors) {
        form.setError(field, { message });        // ⭐⭐ ON THE INPUT
      }
      return;
    }
    form.setError("root", { message: "Could not save. Try again." });
  }
});
```

| ⭐ Server says | ⭐⭐ The user must see |
|---|---|
| 400, `email` already taken | ⭐⭐ The message **under the email box** — not a toast |
| 400, several fields | ⭐ Each on its own field, **focus the first** |
| 409 conflict (optimistic lock failed) | ⭐⭐ *"Someone else changed this — refresh to see the current state"* |
| 500 | ⭐ Form-level, generic, ⭐⭐ **and the draft is not cleared** |
| 401 | ⭐ Re-auth, then **resubmit the same values** |

> ⭐⭐ **Never clear the form on failure.** The most user-hostile thing a form can do is discard what
> someone typed because the server said no.

# Part 4 — The four things every real form needs

```
⭐⭐ ① DOUBLE-SUBMIT PROTECTION
⭐   ❌ user double-clicks Save ⇒ ⭐⭐ TWO ORDERS.
⭐   ✅ disable while pending — ⭐ NECESSARY BUT NOT SUFFICIENT:
⭐      a slow network + Enter key can still race.
⭐   ⭐⭐ THE REAL FIX IS SERVER-SIDE: an idempotency key generated
⭐     ONCE PER FORM INSTANCE, with a unique constraint behind it.
⭐     ⭐ The client control is UX; the DB constraint is correctness.

⭐⭐ ② VALIDATION TIMING
⭐   ❌ validate on every keystroke ⇒ "invalid email" while typing "a"
⭐   ✅ ⭐ ON BLUR, THEN RE-VALIDATE ON CHANGE ONCE IT HAS ERRORED

⭐⭐ ③ THE UNSAVED-CHANGES GUARD
⭐   ⭐ if dirty, warn before navigating away.

⭐⭐ ④ ACCESSIBILITY — Day 239, but the minimum is here:
⭐   · ⭐⭐ EVERY INPUT HAS A <label htmlFor>. Placeholder is NOT a label.
⭐   · aria-invalid + aria-describedby pointing at the error text
⭐   · ⭐ the error is TEXT, not just a red border
⭐   · focus moves to the first error on failed submit
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you handle form validation?"**

Separate the two jobs immediately. **Client validation is a user-experience feature; Bean Validation on
the server is the security boundary. They're not duplicates, because curl ignores the client entirely.
I never describe client validation as protecting anything.**

Then name the risk that actually bites. **The problem isn't duplication, it's drift. If I tighten
`@Min(18)` to `@Min(21)` and the client still says eighteen, the user fills in a form that passes
locally and gets a mystery rejection. So the rules come from one place — springdoc already emits my
Bean Validation constraints into the OpenAPI schema, so the generated client carries them, and there's
a test asserting they agree.**

Then the payoff that shows end-to-end thinking. **A 400 has to land under the right input, not in a
toast. That requires the server's error to carry a field name, which is why I added a
`@RestControllerAdvice` returning `ProblemDetail` with a field-and-message list — I couldn't render a
good error state against Spring's default validation shape. And the form never clears on failure.**

Close on correctness. **Disabling the submit button while pending is UX, not a fix — a slow network and
the Enter key still race, and you get two orders. The real control is an idempotency key generated once
per form instance with a unique constraint behind it, so the database refuses the duplicate rather than
the button trying to.**
