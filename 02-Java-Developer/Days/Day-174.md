# Day 174

**L-174** · `@PreAuthorize` and method security — authorization where the data is

**Time:** 3 hrs · **Mode:** NEW

> Day 169's `AuthorizationFilter` answers "may this user reach this URL?" That is necessary and it is
> not sufficient, because the question that actually matters is usually **"may this user act on *this
> record*?"** — and a filter cannot answer that. It has not loaded the record.
>
> Day 118 built RBAC, ABAC and ReBAC. Day 119 gave IDOR as the number-one API vulnerability. Today
> is the layer that closes it.

---

# Part 1 — Why URL security is not enough

```java
.requestMatchers("/api/v1/orders/**").authenticated()      // ⭐ any logged-in user
```

```java
@GetMapping("/api/v1/orders/{id}")
OrderResponse get(@PathVariable UUID id) {
    return service.find(id);                                // ⭐ ANY order. Yours or not.
}
```

**That is IDOR** (Day 119), and it is the most common serious API vulnerability in existence. The URL
rule was satisfied — the user is authenticated. The rule it needed was *ownership*, and the filter
could not express it because at filter time nothing has been loaded.

**⭐ The distinction to hold onto:**

| Question | Answered by |
|---|---|
| "May any authenticated user reach `/api/v1/orders/**`?" | ⭐ `AuthorizationFilter` — coarse, URL-based |
| "May *this* user read order 7f3a?" | ⭐ **method security** — needs the record |

# Part 2 — The annotations

```java
@Configuration
@EnableMethodSecurity                        // ⭐ prePostEnabled is true by default in Boot 3
class MethodSecurityConfig { }
```

```java
@Service
public class OrderService {

    @PreAuthorize("hasAuthority('order:read')")
    public OrderResponse find(UUID id) { ... }

    @PreAuthorize("#customerId == authentication.principal.customerId")   // ⭐ argument-based
    public Page<OrderResponse> forCustomer(Long customerId, Pageable p) { ... }

    @PreAuthorize("hasRole('ADMIN') or @orderGuard.isOwner(#id, authentication)")  // ⭐ bean call
    public OrderResponse detail(UUID id) { ... }

    @PostAuthorize("returnObject.customerId == authentication.principal.customerId")  // ⚠️ see below
    public OrderResponse loadThenCheck(UUID id) { ... }

    @PreFilter("filterObject.customerId == authentication.principal.customerId")
    public void bulkUpdate(List<OrderUpdate> updates) { ... }

    @PostFilter("filterObject.customerId == authentication.principal.customerId")   // ❌ see Part 3
    public List<OrderResponse> all() { ... }
}
```

| Annotation | When | Note |
|---|---|---|
| `@PreAuthorize` | ⭐ before | the default choice |
| `@PostAuthorize` | after | ⚠️ ⭐ **the method already ran** |
| `@PreFilter` | before | filters a collection argument |
| `@PostFilter` | after | ❌ ⭐ filters in memory — see Part 3 |
| `@Secured` / `@RolesAllowed` | before | roles only, no SpEL. Legacy |

**⭐ It is AOP (Day 137), so every constraint applies:** self-invocation does nothing, `private` and
`final` methods are invisible, and a `@PreAuthorize` that never fires is almost always one of those.

## ⭐ `@PostAuthorize` — the side effects have already happened

```java
@PostAuthorize("returnObject.owner == authentication.name")
public Document delete(Long id) {
    Document doc = repo.findById(id).orElseThrow();
    repo.delete(doc);                        // ⭐⭐ ALREADY DELETED
    return doc;                              // → 403, and the document is gone
}
```

The check runs, throws, the transaction rolls back — *if* there is one (Day 164). Without a
transaction, or with any non-transactional side effect like a sent email or a published message, the
damage is permanent and the caller received a 403 telling them it did not happen.

**Rule: `@PostAuthorize` on read-only methods only, and never where the check could have been made
before.**

## The guard bean — the pattern that scales

```java
@Component("orderGuard")
public class OrderGuard {
    private final OrderRepository orders;

    public boolean isOwner(UUID orderId, Authentication auth) {
        var principal = (AppUserDetails) auth.getPrincipal();
        return orders.findCustomerIdByPublicId(orderId)                // ⭐ one column, not the entity
                     .map(cid -> cid.equals(principal.customerId()))
                     .orElse(false);                                    // ⭐ absent → deny
    }
}
```

**⭐ Why this beats writing logic in the SpEL string:**

- **It is testable** as a plain unit test.
- **It is refactorable** — the SpEL string is text, so a renamed method is a runtime failure.
- **It is debuggable** — you can put a breakpoint in it.
- **It is reusable** across many methods.

**Complex SpEL in an annotation is unreviewable business logic living in a string literal.** Keep the
expression to one call; put the thinking in Java.

**Note `findCustomerIdByPublicId`** — a projection (Day 161). Loading the whole entity to check
ownership doubles the query cost of every guarded call.

# Part 3 — ⭐ Where method security is the wrong tool

### `@PostFilter` on a collection

```java
@PostFilter("filterObject.customerId == authentication.principal.customerId")
public List<OrderResponse> all() {
    return repo.findAll();          // ⭐⭐ loads 2,000,000 rows, then filters to 12 in memory
}
```

**This is correct and catastrophic.** The database returned everything; Spring discarded 99.999% in
Java. It also breaks pagination completely — page 1 of 20 returns however many of those 20 you owned,
which is usually zero.

```java
Page<OrderResponse> mine(Pageable p) {
    return repo.findByCustomerId(currentCustomerId(), p);   // ⭐ filter in the QUERY
}
```

> **⭐ The rule: authorization on a single record is a check; authorization on a collection is a
> query predicate.** `@PostFilter` is only acceptable on a small, already-bounded list.

### The stronger version: never accept the identifier

```java
// ⚠️ needs a guard on every method
@GetMapping("/api/v1/orders/{id}")
OrderResponse get(@PathVariable UUID id) { ... }

// ⭐ structurally safe — the customer id comes from the token, not the request
@GetMapping("/api/v1/me/orders/{id}")
OrderResponse get(@PathVariable UUID id, @AuthenticationPrincipal AppUserDetails me) {
    return service.findForCustomer(id, me.customerId());     // ⭐ scoped in the WHERE clause
}
```

```sql
select ... from orders where public_id = ? and customer_id = ?    -- ⭐ IDOR is impossible
```

**Day 147's argument, applied to authorization: the best defence makes the attack unrepresentable
rather than blocked.** A missing guard annotation is a vulnerability; a missing `WHERE` clause is a
query that returns nothing.

**And return 404, not 403, for someone else's record** (Day 149) — a 403 confirms the record exists.

# Part 4 — Where the checks belong, and testing them

## Service layer, not controller

```java
// ❌ controller only
@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/api/v1/orders/{id}")
public void cancel(@PathVariable UUID id) { service.cancel(id); }
```

Day 146's argument with a security edge: **a Kafka consumer, a scheduled job or an admin CLI calling
`service.cancel(id)` bypasses the check entirely**, because it never passes through a controller. The
authorization must sit where every caller must pass.

**The counter-argument, stated fairly:** an internal job may legitimately need to act without a user
context, and a service-layer `@PreAuthorize` blocks it. Handle that explicitly — a system principal
via `RunAs`, or a separate method that documents its unauthenticated nature — rather than by moving
the check up to the controller and hoping.

## ⭐ The `@Async` gap

```java
@Async
@PreAuthorize("hasRole('ADMIN')")
public void backgroundJob() { }        // ⭐ anonymous — SecurityContextHolder is a ThreadLocal
```

Day 169's `ThreadLocal` fact. Day 177 has the fix (`DelegatingSecurityContextExecutor`); until then,
this check fails or passes wrongly depending on your configuration. **Never assume the context
crosses a thread boundary.**

## Testing — mandatory, because the failure is silent

```java
@Test @WithMockUser(username = "alice", authorities = "order:read")
void cannotReadAnotherCustomersOrder() {
    assertThatThrownBy(() -> service.detail(bobsOrderId))
        .isInstanceOf(AccessDeniedException.class);              // ⭐ THE test
}

@Test @WithMockUser(roles = "ADMIN")
void adminCanReadAnyOrder() {
    assertThat(service.detail(bobsOrderId)).isNotNull();
}
```

**An authorization bug returns 200 to the wrong person.** It throws nothing, logs nothing, and passes
every positive test. **The negative test is the only mechanism that notices**, and one per protected
operation is the standard.

`@WithMockUser` is fine for roles; for a custom principal with a `customerId`, write a
`@WithMockCustomUser` annotation backed by a `WithSecurityContextFactory`, or the ownership tests
cannot be expressed at all.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ URL rules only | IDOR — Day 119's top vulnerability |
| Forgetting `@EnableMethodSecurity` | every annotation silently inert |
| Self-invocation | Day 137 — no check runs |
| `@PostAuthorize` on a mutating method | side effects already happened |
| ⭐ `@PostFilter` on a large collection | loads everything, filters in memory, breaks pagination |
| Complex SpEL in the annotation | untestable, unrefactorable business logic in a string |
| Loading the whole entity in a guard | doubles the cost of every guarded call |
| Checks in the controller only | jobs and consumers bypass them |
| Accepting an id and then guarding it | one missing annotation is a breach |
| 403 for another user's record | confirms existence |
| Assuming the context reaches `@Async` | `ThreadLocal` |
| No negative tests | the failure mode is a silent 200 |

## Interview questions

**Q: Why isn't URL-based security enough?**
Because it answers "may this user reach this URL", and the question that matters is usually "may this
user act on this record". The filter runs before anything is loaded, so it cannot express ownership.
That gap is IDOR.

**Q: `@PreAuthorize` or `@PostAuthorize`?**
`@PreAuthorize` almost always. `@PostAuthorize` runs after the method body, so on anything mutating,
the side effects have already happened — the caller gets a 403 for an action that took place. I use
it only on read-only methods where the decision genuinely needs the returned object.

**Q: What is wrong with `@PostFilter`?**
It fetches everything and discards in memory — on a large table that is a full load to return twelve
rows — and it breaks pagination, because the page is filtered after it is cut. Collection
authorization belongs in the query as a predicate.

**Q: Where do you put the checks?**
The service layer, because jobs and message consumers never pass through a controller. And where
possible I remove the need for a check entirely by scoping the query — take the customer id from the
token and put it in the `WHERE` clause, so a missing annotation cannot be a breach.

## 🎙️ Articulation drill

Two minutes: **"How do you do authorization beyond URL rules?"**

Open with the gap — URL rules answer reachability, not ownership, and that gap is IDOR. Method
security with `@PreAuthorize` and a guard bean, in the service layer so jobs and consumers cannot
bypass it. Then show the two judgements that matter: collection authorization is a query predicate,
never `@PostFilter`, because filtering after fetching is both a performance disaster and broken
pagination — and the strongest form of the defence is scoping the query by the identity in the token,
so there is no annotation to forget. Close on testing: an authorization bug is a 200 to the wrong
person, so the negative test is the only thing that will ever notice.
