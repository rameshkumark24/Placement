# Day 399

**L-399** · Decomposition — by domain not layer, and sync vs async

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ The test for whether something is a service is one question: can it be changed, deployed and
> rolled back alone? If the answer is no, you have a distributed monolith — every cost of microservices
> and none of the benefits.**
>
> Today: the decomposition mistakes ranked by how much they hurt, **cognitive load as the real sizing
> constraint rather than lines of code**, the sync-versus-async decision made explicit, and **what
> happens to your joins when one service owns each table.**

---

# Part 1 — ⭐⭐ By domain, not by layer

```
⭐⭐ WRONG — decomposed by TECHNICAL LAYER:
⭐   api-service · business-logic-service · data-access-service
⭐   ⇒ ⭐⭐ EVERY feature touches ALL THREE. ⭐⭐ Every change is a three-team, three-deploy change.
⭐   ⇒ ⭐⭐ You have added network calls between the layers of one application. Nothing else.

⭐⭐ RIGHT — decomposed by BUSINESS CAPABILITY:
⭐   ordering · payments · inventory · shipping · notifications
⭐   ⇒ ⭐ a feature lands mostly in ONE service ⇒ ⭐⭐ one team, one deploy, one rollback.
```

| ⭐ Where the boundaries come from | |
|---|---|
| ⭐⭐ **Bounded contexts** (Day 304) | ⭐⭐ where the same word means different things — *"order" to shipping ≠ "order" to billing* |
| ⭐⭐ **Aggregates** (Day 305) | ⭐⭐ **the transactional boundary — a service must contain whole aggregates** |
| ⭐ Rate of change | ⭐ things that change together belong together |
| ⭐ Team ownership | ⭐ Conway's law is a constraint, not a warning (Day 341) |
| Data ownership | ⭐⭐ **one service owns each table — nobody else reads it directly** |

> **⭐ The strongest practical signal is the aggregate**: if two pieces of state must change in one
> transaction, **they cannot be in different services** — because you would need a distributed
> transaction, and the answer to that is a saga you did not want to build (Day 408).

## ⭐⭐ The distributed monolith — the worst outcome

| ⭐ Symptom | ⭐ What it means |
|---|---|
| ⭐⭐ **Services must be deployed together, in order** | ⭐⭐ **they are one system wearing five hats** |
| ⭐⭐ **A shared database** | ⭐⭐ **the schema is a public API nobody versions** |
| ⭐ A typical change touches four repos | ⭐ boundaries are in the wrong place |
| ⭐ Integration tests require the whole system running | ⭐ no service can be reasoned about alone |
| ⭐ A release train | ⭐⭐ you gave up independent deployment — the main thing you were buying |

```
⭐⭐ THE TEST, and it is the only one you need:
⭐   "Can I change this service, deploy it, and roll it back — ⭐⭐ ALONE?"
⭐   ⇒ ⭐⭐ No ⇒ it is not a service. ⭐ It is a module with network latency.
```

## ⭐ Sizing: cognitive load, not lines of code

| ⭐ Bad heuristic | ⭐ Better |
|---|---|
| "Under 500 lines" | ⭐⭐ **one team can hold the whole thing in their heads** |
| "One per entity" | ⭐ one per **bounded context** |
| "Two-pizza team" | ⭐ the team size follows the domain, not the reverse |
| Nano-services | ⭐⭐ **more services than engineers is a reliable predictor of pain** |

⚠️ **The honest default is still Day 306's modular monolith.** Extract a service when a *specific* force
demands it — a different scaling profile, a different failure domain, a different team, a different
release cadence. **"We might need to scale it later" is not one of those forces; you can extract later
precisely because the module boundary was already right.**

# Part 2 — ⭐⭐ Synchronous or asynchronous

| ⭐ Use **synchronous** when | ⭐ Use **asynchronous** when |
|---|---|
| ⭐⭐ **the caller cannot proceed without the answer** | ⭐⭐ **the caller only needs it to *happen*, not to happen *now*** |
| ⭐ the callee is fast and highly available | ⭐ the callee may be slow, down, or bursty |
| ⭐ a user is waiting on the result | ⭐ the work can be retried later |
| the operation is a query | ⭐⭐ **the operation is a side effect** |

```
⭐⭐ THE DEFAULT THAT SERVES MOST TEAMS:
⭐   ⭐ QUERIES — synchronous. ⭐ You need the data to render the response.
⭐   ⭐⭐ COMMANDS / SIDE EFFECTS — asynchronous. ⭐⭐ Emit an event; let the world react.
⭐   ⇒ ⭐ "Place the order" is synchronous (the user needs an id).
⭐     ⭐⭐ "Send the confirmation email, update analytics, reserve stock, notify the warehouse"
⭐        are ALL asynchronous — ⭐⭐ and each one you make synchronous multiplies your
⭐        availability down (Day 398) and adds latency the user pays for.
```

| ⭐ What async actually buys | |
|---|---|
| ⭐⭐ **Availability stops multiplying** | ⭐⭐ the callee being down is a queue depth, not an error |
| ⭐⭐ **The spike is absorbed** | ⭐ throughput failure becomes latency (Day 393) |
| ⭐ Adding a consumer needs no change to the producer | ⭐ this is the real decoupling |
| ⭐ Independent scaling and retry | ⭐ per-consumer DLQ |

| ⭐⭐ What async costs — say this too | |
|---|---|
| ⭐⭐ **Eventual consistency becomes a UX problem** | ⭐⭐ "I placed the order but it is not in my list" |
| ⭐⭐ **Debugging spans a broker** | ⭐ trace context must cross it (Day 376) |
| ⭐ Ordering and duplicates become your problem | ⭐ Day 401, Day 335 |
| ⭐ Operational surface grows | a broker to run, lag to watch, DLQs to drain |

⚠️ **The naive version of async is "fire and forget", and it is a bug.** If nobody checks whether the
work happened, **you have built silent data loss with extra steps.** Async requires a DLQ, an alarm on
it, and someone who looks (Day 393).

# Part 3 — ⭐⭐ Data: one owner, and what happens to your joins

```
⭐⭐ RULE: ⭐⭐ one service owns each table. ⭐⭐ No other service connects to that database. Ever.
⭐   ⇒ ⭐ because a shared schema is an unversioned public API, and the first ALTER TABLE
⭐     breaks a team that did not know they were a consumer.
```

| ⭐⭐ "But I need to join across services" — the four answers | |
|---|---|
| ⭐ **1. API composition** | ⭐ the caller fetches from each and joins in memory — **fine for small N, N+1 for large** |
| ⭐⭐ **2. A replicated read model** | ⭐⭐ **subscribe to events and keep a local copy of what you need** (Day 406) |
| ⭐ **3. CQRS read service** | ⭐ a service whose only job is the joined view |
| ⭐⭐ **4. The boundary is wrong** | ⭐⭐ **if you constantly join two services, they are one service** |

> **⭐ Answer 4 is the one people skip, and it is often correct.** A join you need on every request is
> the domain telling you where the boundary belongs. **The frequency of cross-service joins is the best
> available metric for a bad decomposition.**

| ⭐ Duplication is the point, not a smell | |
|---|---|
| ⭐⭐ Shipping storing the customer's **address at time of order** | ⭐⭐ not a cache — **a frozen input** (Day 359) |
| ⭐ Orders storing the product **name and price at purchase** | ⭐⭐ the price must not change retroactively |
| ⭐ The rule | ⭐⭐ **anything charged or judged must be frozen, not looked up** |

# Part 4 — ⭐ The extraction, done safely

```
⭐ Extracting a service from a monolith, in order:
⭐ 1. ⭐⭐ Make the module boundary real IN the monolith first (Day 306). ⭐ No shortcuts across it.
⭐ 2. ⭐ Put an INTERFACE in front of it, still in-process.
⭐ 3. ⭐ Move the data — ⭐⭐ this is the hard step, and where most extractions actually fail.
⭐ 4. ⭐ Implement the interface with a remote client behind a feature flag.
⭐ 5. ⭐⭐ Run BOTH: dual-write, or shadow-read and compare (Day 371).
⭐ 6. ⭐ Cut over, keep the flag, ⭐⭐ delete the old path only when you have been happy for a while.
```

⚠️ **Step 3 is the one to respect.** Code is easy to move; **data has foreign keys, reports, ad-hoc
queries and one analyst you have never met.** Budget for the data migration as the majority of the work,
**and expect to discover consumers of the table you did not know existed** — which is itself the
argument for never sharing a schema in the first place.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Decomposing by technical layer** | ⭐⭐ every change touches every service |
| ⭐ Boundaries that split an aggregate | ⭐⭐ you now need a distributed transaction |
| ⭐⭐ **A shared database between services** | ⭐⭐ an unversioned public API |
| ⭐⭐ **Services that must deploy together** | ⭐⭐ a distributed monolith — cost without benefit |
| ⭐ Sizing by lines of code | ⭐ cognitive load is the constraint |
| ⭐ More services than engineers | ⭐⭐ a reliable predictor of pain |
| ⭐⭐ **Synchronous side effects** | ⭐⭐ availability multiplies down and the user pays the latency |
| ⭐ Fire-and-forget with no DLQ | ⭐⭐ silent data loss with extra steps |
| ⭐ Ignoring the UX of eventual consistency | ⭐ "I placed it and it is not there" |
| ⭐ Constant cross-service joins | ⭐⭐ the boundary is wrong — merge them |
| ⭐ Treating duplicated data as a smell | ⭐⭐ frozen inputs are correctness, not caching |
| Extracting before the module boundary is real | you export the mess over a network |

## Interview questions

**Q: How do you decide service boundaries?**
By business capability, using bounded contexts, and constrained hard by aggregates: if two pieces of
state must change in one transaction, they cannot live in different services, because the alternative is
a distributed transaction you do not want. Then I check the boundary with one test — can this be changed,
deployed and rolled back alone? If not, it is a module with network latency rather than a service. And
I would look at how often a change touches multiple repos, because that number is the best available
metric for a bad decomposition.

**Q: What is a distributed monolith and how do you spot one?**
It has every cost of microservices and none of the benefits. The symptoms are services that must be
deployed together and in a specific order, a shared database, a typical change touching four
repositories, integration tests that need the whole system running, and a release train — which is the
formal surrender of independent deployment, the main thing you were buying. It usually comes from
splitting by technical layer instead of by domain, or from splitting before the module boundaries inside
the monolith were real.

**Q: Synchronous or asynchronous?**
My default is queries synchronous, side effects asynchronous. The caller of a query cannot proceed
without the answer; the caller of a side effect needs it to happen, not to happen now. Placing an order
is synchronous because the user needs an id, but the confirmation email, the analytics update, the stock
reservation and the warehouse notification are all asynchronous — and every one of those you make
synchronous multiplies your availability down and adds latency the user pays for. The honest cost is
that eventual consistency becomes a user experience problem and debugging crosses a broker, and
fire-and-forget without a dead letter queue and an alarm is just silent data loss.

**Q: A service needs to join data owned by another service. What do you do?**
Four options in increasing commitment. Compose in the caller by fetching from each — fine when the
result set is small, an N+1 problem when it is not. Keep a replicated read model by subscribing to the
other service's events, which is the usual answer at scale. Build a dedicated read service whose job is
the joined view. Or accept that the boundary is wrong and merge them, which is the option people skip
and which is often correct — a join you need on every request is the domain telling you where the
boundary belongs.

**Q: How do you extract a service from a monolith?**
Make the boundary real inside the monolith first, with no shortcuts across it, and put an interface in
front of it while it is still in-process. Then move the data, which is the step that actually decides
whether the extraction succeeds — code is easy to move, data has foreign keys, reports and consumers you
have never met. Then implement the interface with a remote client behind a flag, run both paths with
dual-writes or shadow reads and compare, cut over, and delete the old path only after a period of
confidence. If you extract before the module boundary is real, you have exported the mess over a
network.

## Mini task

1. ⭐⭐ Apply **the test** to every module in your flagship: can it be changed, deployed and rolled back
   alone? Write the honest answer.
2. ⭐ List your bounded contexts and **find one word that means two different things** in two of them.
3. ⭐⭐ Find any pair of state changes that **must** be in one transaction and confirm they are in one
   service.
4. ⭐ Count how many repos a typical change touches. **Track it for two weeks.**
5. ⭐⭐ Take one synchronous side effect and make it **asynchronous.** Measure the p99 change and
   recompute your availability chain.
6. ⭐⭐ Add a **DLQ and an alarm** to it. Then make it fail deliberately and confirm a human finds out.
7. ⭐ Design the **UX for eventual consistency** on that path — what does the user see in the gap?
8. ⭐ Find any place a service reads another service's table directly. **Write down what breaks when that
   schema changes.**
9. ⭐⭐ Identify the data you should be **freezing rather than looking up** — prices, addresses, names.
10. ⭐⭐ Plan a real **extraction** for one module, with the data migration as the majority of the plan.

## 🎙️ Articulation drill

**Two minutes:** *"How would you break this monolith into services?"*

**⭐ Start by refusing the premise politely, because that is the senior move: the first question is
whether to, and the default is a modular monolith with real boundaries — you extract when a specific
force demands it, like a different scaling profile, failure domain or team, not because it might be
needed later.**

**⭐ Then the method: boundaries come from bounded contexts and are constrained hard by aggregates,
because two things that must change in one transaction cannot be in two services. And I test every
proposed boundary with one question — can it be changed, deployed and rolled back alone?**

**⭐ Close on the trap: split by domain, never by technical layer, and never share a database — a shared
schema is a public API nobody versions, and the first ALTER TABLE breaks a team that did not know they
were a consumer.**
