# Part 1 — L-001 · What a computer actually is

## What it is

A computer is four things connected by wires:

| Part | Job | Speed | Volatile? |
|---|---|---|---|
| **CPU** | Executes instructions, one at a time, very fast | ~1 ns per operation | — |
| **RAM** | Holds the instructions and data currently in use | ~100 ns to read | Yes — lost on power off |
| **Disk** | Holds everything permanently | ~100 µs (SSD) to 10 ms (HDD) | No |
| **Bus** | The wires that carry data between them | — | — |

Get the numbers into your body, because every performance decision you make for the next 400 days
descends from them:

```
CPU register        ~0.3 ns      ← the CPU's own scratch space
L1 cache            ~1 ns
L2 cache            ~4 ns
L3 cache            ~15 ns
RAM                 ~100 ns      ← 300× slower than a register
SSD                 ~100,000 ns  (100 µs)
Network (same DC)   ~500,000 ns  (0.5 ms)
HDD seek         ~10,000,000 ns  (10 ms)
Network (India→US) ~150,000,000 ns (150 ms)
```

**Scale it up so it's human.** If a CPU register access were 1 second:
- RAM would be 5 minutes
- An SSD read would be 4 days
- A cross-continent network call would be **15 years**

This is why caching exists. This is why "just add a database call" is never free. This is why
Redis (RAM) beats Postgres (disk) for hot reads, and why both beat calling another service.

## Why it exists — the von Neumann model

Before 1945, "programming" a computer meant physically rewiring it. ENIAC took days to reconfigure.

Von Neumann's insight: **store the program in the same memory as the data.** A program becomes just
another array of bytes. That single idea gives you:

- Software as a thing you can copy, load, and change without touching hardware
- Compilers (a program whose input and output are both programs)
- The JVM (a program that reads other programs and runs them)
- Every security vulnerability where data gets executed as code

That last point is not a footnote. **Buffer overflows, SQL injection, and prompt injection are all
the same bug**: something you intended as data got treated as instructions. The von Neumann model is
why that confusion is even possible. You'll meet this again on Day 119 and every day you write an
API.

## How it works inside — the fetch-decode-execute cycle

The CPU does exactly one thing, in a loop, billions of times per second:

```
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
   ┌─────────┐    ┌─────────┐    ┌─────────┐      │
   │  FETCH  │───▶│ DECODE  │───▶│ EXECUTE │──────┘
   └─────────┘    └─────────┘    └─────────┘
   Read the       Work out       Do it. Update
   instruction    what it        registers/memory.
   at address     means and      Advance PC.
   in PC          what operands
                  it needs
```

**PC** = program counter, a register holding the address of the next instruction.

That's it. That's the whole machine. Everything else — operating systems, browsers, Spring Boot —
is an enormous pile of abstraction on top of this loop.

### Registers

The CPU can only operate on data in its own **registers** — a few dozen slots, each 64 bits. Data
must be loaded from RAM into a register before the CPU can touch it, and stored back afterwards.

```
  x = x + 1   becomes roughly:

  LOAD  r1, [address_of_x]    ; RAM → register  (~100 ns)
  ADD   r1, 1                 ; register only   (~0.3 ns)
  STORE [address_of_x], r1    ; register → RAM  (~100 ns)
```

**Look at that for a moment.** The addition — the thing you actually wanted — is 0.3% of the cost.
The other 99.7% is moving data. Now you understand:

- Why CPU caches exist
- Why array iteration is faster than linked-list traversal (contiguous memory prefetches well)
- Why `i++` is not atomic (three steps, and a thread can interleave between them) — this is
  Day 065, and it starts *here*

## What "running a program" actually means

You double-click something. In order:

1. **The program is bytes on disk** — an executable file. Inert. Nothing is happening.
2. **The OS loader reads it into RAM** — code section, data section, and it sets up a stack and heap
3. **The OS creates a process** — a bookkeeping record: which memory is yours, which files you have
   open, what your ID is
4. **The OS sets the PC** to the program's entry point (`main`)
5. **The CPU starts its fetch-decode-execute loop** at that address
6. When the OS's scheduler decides your turn is over, it **saves your registers**, loads another
   process's registers, and that process runs (Day 026, Day 033/B-04)

"Running" is not a property of the file. It is a *process*: memory + registers + OS bookkeeping,
being ticked forward by the CPU.

> **This is the answer to a question that ended your last interview.** "What is a server?" A server
> is a program in this state — running, in a loop, waiting. Day 004 makes that precise.

## Type this yourself

No copy-paste. Typing is how it lands.

```java
public class Day001 {
    public static void main(String[] args) {
        // Prove that memory access dominates arithmetic.
        int size = 50_000_000;
        int[] data = new int[size];

        // Sequential access — cache-friendly.
        long start = System.nanoTime();
        long sum1 = 0;
        for (int i = 0; i < size; i++) {
            sum1 += data[i];
        }
        long sequential = System.nanoTime() - start;

        // Strided access — same number of additions, defeats the cache.
        start = System.nanoTime();
        long sum2 = 0;
        for (int i = 0; i < size; i += 16) {
            sum2 += data[i];
        }
        long strided = System.nanoTime() - start;

        System.out.printf("Sequential (%d adds): %d ms%n", size, sequential / 1_000_000);
        System.out.printf("Strided    (%d adds): %d ms%n", size / 16, strided / 1_000_000);
        System.out.println("Strided does 1/16th the work. Did it take 1/16th the time?");
    }
}
```

Run it. The strided loop does **one sixteenth** the additions but nowhere near one sixteenth the
time — often it's within a factor of 2–3. You just measured the cache line. A cache line is 64
bytes = 16 `int`s, so striding by 16 forces a fresh memory fetch on every single iteration.

**Write the two numbers you got in your notes.** You will refer back to this when you learn why
`ArrayList` beats `LinkedList` (Day 047).

## Common mistakes

| Mistake | Correction |
|---|---|
| "RAM is memory, disk is storage" as if they're different in kind | Both store bytes. The difference is speed and volatility. Disk is ~1000× slower and survives power loss. |
| Thinking a program "is running" while it sits on disk | A file is inert. A process is a running thing. Same bytes, completely different state. |
| Assuming one line of Java is one CPU instruction | `x = x + 1` is at minimum three machine instructions. This is the seed of every race condition you'll ever debug. |
| Treating a network call as "just a bit slower than RAM" | It is 5,000× slower to the next rack, and 1,500,000× slower across the world. |
| "More RAM makes the CPU faster" | It lets you keep more data out of disk. The CPU's clock is unchanged. |

## Interview questions

**Q: What happens when you run a program?**
> The file is read from disk into RAM by the OS loader, which lays out the code and data sections
> and allocates a stack and heap. The OS creates a process record, sets the program counter to the
> entry point, and the CPU begins fetch-decode-execute from there. The scheduler timeshares the CPU
> between this and other processes by saving and restoring registers.

**Q: Why is RAM faster than disk?**
> RAM is addressed electronically with no moving parts, and sits closer to the CPU on a faster bus.
> An SSD has a controller, a protocol, and flash-translation overhead in the path; an HDD physically
> moves a head. Roughly 100 ns versus 100 µs — three orders of magnitude.

**Q: What is the von Neumann bottleneck?**
> Code and data share one memory and one bus, so the CPU spends most of its time waiting for memory
> rather than computing. Caches, pipelining and prefetching all exist to hide it.

**Q: Why does array iteration outperform linked-list traversal even with the same number of elements?**
> Arrays are contiguous, so one cache-line fetch brings in the next 16 elements and the prefetcher
> predicts the pattern. Linked-list nodes are scattered, so nearly every step is a cache miss —
> ~100 ns instead of ~1 ns.

# Part 2 — C-01 · Why layering exists

## The problem layering solves

You want a Java program in Chennai to send a message to a Java program in Oregon. Between them:
WiFi, a fibre backbone, an undersea cable, a dozen routers from different vendors, packets that
arrive out of order or not at all.

If your application had to handle all of that, every application would reimplement the entire
internet, and any change to the physical medium would break every program on earth.

**Layering is the fix:** each layer does one job, talks only to the layers directly above and below,
and hides its internals behind an interface. Your code says "send these bytes to this address" and
does not care whether the medium is copper, fibre, or radio.

This is exactly the same idea as an interface in Java (Day 039), a REST API contract (Day 103), and
hexagonal architecture (Day 300). **Layering is the single most reused idea in this roadmap.** You
are learning it on Day 1 because it recurs on Day 300.

## The two models

**OSI** — 7 layers, a teaching and reference model. **TCP/IP** — 4 layers, what actually runs.

```
   OSI (reference)              TCP/IP (reality)        Example
 ┌────────────────────┐      ┌──────────────────┐
 │ 7 Application      │      │                  │
 ├────────────────────┤      │  Application     │      HTTP, DNS, TLS
 │ 6 Presentation     │      │                  │
 ├────────────────────┤      │                  │
 │ 5 Session          │      │                  │
 ├────────────────────┤      ├──────────────────┤
 │ 4 Transport        │      │  Transport       │      TCP, UDP
 ├────────────────────┤      ├──────────────────┤
 │ 3 Network          │      │  Internet        │      IP
 ├────────────────────┤      ├──────────────────┤
 │ 2 Data Link        │      │                  │
 ├────────────────────┤      │  Link            │      Ethernet, WiFi
 │ 1 Physical         │      │                  │
 └────────────────────┘      └──────────────────┘
```

Memorise the TCP/IP four. Know the OSI seven exist and roughly map. Interviewers ask about OSI
because it's on syllabi; engineers reason in TCP/IP.

**What each layer's job actually is:**

| Layer | One job | Addresses by |
|---|---|---|
| **Application** | Speak a protocol both ends understand | URL / hostname |
| **Transport** | Get bytes to the right *program* on the machine, reliably (TCP) or not (UDP) | Port number |
| **Internet** | Get a packet to the right *machine* across networks | IP address |
| **Link** | Get a frame to the next device on this physical hop | MAC address |

Read that table again when you do Day 003 (ports) and Day 004 (servers). It's the same table.

## Encapsulation — how data actually moves

Each layer wraps the layer above in its own header, like nesting envelopes.

```
Application:                          [ HTTP request ]
Transport:               [ TCP hdr ][ HTTP request ]
Internet:      [ IP hdr ][ TCP hdr ][ HTTP request ]
Link:  [ Eth ][ IP hdr ][ TCP hdr ][ HTTP request ][ Eth trailer ]
       └──────────────── on the wire ─────────────────────────┘
```

Going up on the receiving side, each layer strips its own header and hands the rest upward. Each
layer only reads *its own* header — it neither knows nor cares what the payload contains.

**Two consequences worth carrying forward:**

1. **Headers are overhead.** ~40 bytes of TCP+IP header per packet. Sending 1 byte of data costs
   ~41 bytes on the wire. This is why chatty protocols are slow and batching helps.
2. **A router only reads the IP header.** It doesn't parse your HTTP. That's why HTTPS works —
   everything above the transport layer is encrypted, and the intermediate hops still route fine
   because they only need the IP header, which stays in the clear.

## Common mistakes

| Mistake | Correction |
|---|---|
| Saying "OSI layer 4 is TCP" as if OSI is real | OSI is a reference model. The internet runs TCP/IP. They map loosely. |
| Thinking a packet "travels" as one object end to end | It's decapsulated and re-encapsulated at every hop. The link-layer frame is rebuilt each time; the IP packet survives. |
| Confusing MAC and IP addressing | MAC gets you to the next device on this hop. IP gets you to the final machine. Both are needed, at different layers. |
| "HTTPS encrypts the whole packet" | It encrypts the payload above transport. IP and TCP headers are visible — routers need them. Observers see *who* you talked to, not *what* you said. |

---

## Interview questions

**Q: Why is the network layered?**
> Separation of concerns. Each layer has one job and a stable interface, so a change in one — WiFi
> instead of Ethernet — doesn't touch the others. Without it every application would reimplement
> routing and reliability.

**Q: Difference between TCP/IP and OSI?**
> OSI is a 7-layer reference model used for teaching. TCP/IP is the 4-layer model actually
> implemented. OSI's session, presentation and application layers collapse into TCP/IP's single
> application layer.

**Q: What is encapsulation in networking?**
> Each layer wraps the data from the layer above with its own header. Application data gets a TCP
> header, then an IP header, then an Ethernet frame. The receiver unwraps in reverse. Each layer
> reads only its own header.

**Q: If HTTPS encrypts traffic, how do routers still route it?**
> Encryption applies to the payload above the transport layer. The IP header — source and
> destination address — stays in plaintext, which is all a router needs. It's also why an observer
> can see which server you contacted even though they can't read the content.
