# L-032 · Methods and parameter passing

## Java is **always** pass-by-value. Always.

**There is no pass-by-reference in Java. None. Not for objects either.**

The confusion comes from a real subtlety, so state it precisely:

> **Java passes everything by value. For objects, the thing being passed by value is the
> *reference*.**

A copy of the reference is made. Both the caller's and the method's variable point at the *same*
object — but they are two independent variables.

### The proof

```java
static void reassign(StringBuilder sb) {
    sb = new StringBuilder("changed");     // reassigns the LOCAL copy of the reference
}

static void mutate(StringBuilder sb) {
    sb.append(" changed");                 // follows the reference, mutates the OBJECT
}

public static void main(String[] args) {
    StringBuilder a = new StringBuilder("original");
    reassign(a);
    System.out.println(a);          // "original"  ← unchanged!

    StringBuilder b = new StringBuilder("original");
    mutate(b);
    System.out.println(b);          // "original changed"
}
```

**If Java were pass-by-reference, `reassign` would have changed the caller's variable.** It doesn't.
That single experiment settles the question.

```
   BEFORE the call                 INSIDE reassign()
   ───────────────                 ─────────────────
   main:  a ──────────┐            main:  a ──────────┐
                      ▼                               ▼
              ┌──────────────┐              ┌──────────────┐
              │ "original"   │              │ "original"   │
              └──────────────┘              └──────────────┘
                                  method: sb ──▶ ┌──────────────┐
                                                 │ "changed"    │  ← new object,
                                                 └──────────────┘    only sb points here
```

**The classic swap that proves it:**

```java
static void swap(Object x, Object y) {
    Object t = x; x = y; y = t;        // swaps the local copies. Caller sees nothing.
}
```

**You cannot write a working `swap` in Java.** In C++ (`&` references) or C (pointers to pointers)
you can. That impossibility *is* the proof.

### The interview answer

> *"Java is always pass-by-value. For reference types, the value copied is the reference, so the
> method can mutate the object the reference points to — which is why it's often mistaken for
> pass-by-reference. But reassigning the parameter inside the method has no effect on the caller,
> which is the definitive test."*

## Method signatures and overloading

**A method's signature is its name plus its parameter types.** The return type is **not** part of it.

```java
void process(int x) { }
void process(String s) { }
void process(int x, int y) { }
void process(String s, int x) { }        // ✅ all distinct

int  process(int x) { }                  // ❌ differs only by return type — compile error
```

**Why not return type?** A call site that discards the result would be ambiguous:
`process(5);` — which one? *(Day 024: the return type is part of the bytecode descriptor but not the
overload-resolution signature.)*

### Overload resolution — the order

The compiler picks at **compile time**, based on **static types**, using three phases in order:

```
   1. Exact match / widening primitive conversion    int → long → float → double
   2. Boxing / unboxing                               int → Integer
   3. Varargs                                         int → int...
```

**It stops at the first phase that finds a match.** That produces genuinely surprising results:

```java
void f(long x)      { System.out.println("long"); }
void f(Integer x)   { System.out.println("Integer"); }
void f(int... x)    { System.out.println("varargs"); }

f(5);     // prints "long"
```

**Widening (phase 1) beats boxing (phase 2) beats varargs (phase 3).** This ordering exists for
backward compatibility — code written before Java 5 must keep behaving identically after autoboxing
and varargs were added.

### The `null` ambiguity

```java
void g(String s) { }
void g(Integer i) { }

g(null);      // ❌ compile error: reference to g is ambiguous
```

`null` matches both. Fix with a cast: `g((String) null)`.

### Overloading vs overriding — know the difference cold

| | Overloading | Overriding |
|---|---|---|
| Same name | ✅ | ✅ |
| Parameters | **Different** | **Identical** |
| Resolved | **Compile time** (static type) | **Runtime** (actual object type) |
| Called | Static dispatch | **Dynamic dispatch** |
| Bytecode | The target is chosen by `javac` | `invokevirtual` picks at runtime *(Day 024)* |

**Overloading is compile-time; overriding is runtime.** This is Day 037–038, but the distinction
belongs here because people conflate them.

## Varargs

```java
void log(String format, Object... args) { }

log("hi");                    // args = empty array
log("hi %s", name);           // args = new Object[]{name}
log("hi %s %s", a, b);
log("x", new Object[]{a, b}); // you can pass the array directly
```

**Varargs is syntax sugar for an array.** `Object... args` *is* `Object[] args`; the compiler builds
the array at the call site.

**Rules:**
- At most one varargs parameter
- It must be **last**
- Calling with zero arguments gives an **empty array**, never null

### The traps

```java
void f(Object... args) { }
f(null);                       // ⚠️ args IS null, not an empty array — NPE risk
f((Object) null);              // ✅ array of one null
f(new Object[0]);              // ✅ empty
```

```java
int[] nums = {1, 2, 3};
System.out.println(Arrays.asList(nums));     // one element (the array) — Day 031
```

**Every varargs call allocates an array.** In a hot logging path that matters, which is why SLF4J
offers one- and two-argument overloads before falling back to varargs (Day 073A).

## Recursion and the stack

```java
int factorial(int n) {
    if (n <= 1) return 1;              // base case — without it: StackOverflowError
    return n * factorial(n - 1);
}
```

Each call pushes a frame onto the **per-thread stack** (Day 025). Default stack allows roughly
10,000–20,000 frames.

**Java does not do tail-call optimisation.** A tail-recursive method still consumes a frame per call,
unlike Scala or functional languages. So deep recursion must be converted to iteration:

```java
int factorialIterative(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++) result *= i;
    return result;
}
```

**That's a real constraint for DSA** — a recursive DFS on a 100,000-node graph will overflow. Use an
explicit `Deque` as a stack. Worth noting in your [pattern journal](../Roadmap/DSA-Parallel-Track.md).

## Method design — what reviewers look for

| Guideline | Why |
|---|---|
| **Do one thing** | Testable, nameable, reusable |
| **Name it after what it does** | `calculateTotal` not `process` |
| **Few parameters** | Beyond 3–4, use a parameter object |
| **Avoid boolean parameters** | `render(true)` is unreadable — use an enum |
| **Don't mutate parameters** | Surprising to the caller; hard to reason about |
| **Return early** | Reduces nesting far more than any other single change |
| **Never return null for a collection** | Return an empty one — the caller shouldn't null-check |

```java
// 💀 deep nesting
if (user != null) { if (user.isActive()) { if (user.hasPermission()) { doThing(); } } }

// ✅ guard clauses
if (user == null) return;
if (!user.isActive()) return;
if (!user.hasPermission()) return;
doThing();
```

## Type this yourself

```java
import java.util.*;

public class MethodDemo {

    // ---- Pass by value ----
    static void reassign(StringBuilder sb) { sb = new StringBuilder("REASSIGNED"); }
    static void mutate(StringBuilder sb)   { sb.append(" MUTATED"); }
    static void changeInt(int x)           { x = 999; }
    static void changeArray(int[] a)       { a[0] = 999; }
    static void reassignArray(int[] a)     { a = new int[]{999}; }

    // ---- Overload resolution ----
    static void f(long x)    { System.out.println("  long"); }
    static void f(Integer x) { System.out.println("  Integer"); }
    static void f(int... x)  { System.out.println("  varargs"); }

    static void g(String s)  { System.out.println("  String"); }
    static void g(Object o)  { System.out.println("  Object"); }

    // ---- Varargs ----
    static void show(String label, Object... args) {
        System.out.println("  " + label + " args="
                + (args == null ? "NULL!" : args.length + " elements"));
    }

    public static void main(String[] args) {

        System.out.println("--- pass by value ---");
        StringBuilder a = new StringBuilder("original");
        reassign(a);
        System.out.println("after reassign: " + a);        // original — PROOF

        StringBuilder b = new StringBuilder("original");
        mutate(b);
        System.out.println("after mutate:   " + b);        // original MUTATED

        int n = 1;  changeInt(n);
        System.out.println("after changeInt: " + n);       // 1

        int[] arr = {1, 2, 3};  changeArray(arr);
        System.out.println("after changeArray:   " + Arrays.toString(arr));   // [999,2,3]
        reassignArray(arr);
        System.out.println("after reassignArray: " + Arrays.toString(arr));   // [999,2,3] — unchanged

        System.out.println("\n--- overload resolution ---");
        System.out.print("f(5)      ->"); f(5);            // long   (widening wins)
        System.out.print("f((Integer)5) ->"); f((Integer) 5);
        System.out.print("g(null)   ->"); g((String) null);  // needs the cast

        System.out.println("\n--- varargs ---");
        show("no args");
        show("two", 1, 2);
        show("explicit null", (Object[]) null);            // args is NULL
        show("cast null", (Object) null);                  // one-element array

        System.out.println("\n--- recursion depth ---");
        try { depth(0); } catch (StackOverflowError e) {
            System.out.println("  StackOverflowError at depth " + maxDepth
                             + " — no tail-call optimisation in Java");
        }
    }

    static int maxDepth = 0;
    static void depth(int d) { maxDepth = d; depth(d + 1); }
}
```

**Two experiments that matter:**

1. **`reassign` vs `mutate`.** Same parameter type, opposite results. **That contrast is the whole
   pass-by-value answer**, and having run it yourself is why you'll say it confidently.
2. **`f(5)` prints `long`, not `Integer` or `varargs`.** Widening beats boxing beats varargs. Now
   decompile with `javap -c` (Day 024) and see that `javac` hard-coded the choice — it's a
   compile-time decision.

## Common mistakes

| Mistake | Correction |
|---|---|
| "Objects are passed by reference" | The *reference* is passed by value. Reassignment inside the method is invisible to the caller. |
| Overloading on return type | Not part of the signature — compile error. |
| Assuming boxing beats widening | Widening is phase 1, boxing phase 2. `f(5)` picks `f(long)`. |
| `f(null)` with multiple reference overloads | Ambiguous. Cast it. |
| Passing `null` to a varargs method | The array is null, not empty. Cast to the element type. |
| Deep recursion in Java | No tail-call optimisation. Convert to iteration or an explicit stack. |
| Returning `null` for a collection | Return `List.of()` — don't force null checks on callers. |

## Interview questions

**Q: Is Java pass-by-value or pass-by-reference?**
> Always pass-by-value. For reference types the value copied is the reference, so the method can
> mutate the object it points to — which is why people mistake it for pass-by-reference. The
> definitive test is reassigning the parameter inside the method: the caller's variable is unaffected,
> which couldn't be true under pass-by-reference. It's also why you cannot write a working `swap`
> method in Java.

**Q: What makes up a method signature? Why isn't the return type included?**
> The name and the parameter types. The return type is excluded because a call site that discards the
> result would be ambiguous — there'd be no way to choose between two methods differing only in what
> they return.

**Q: How does the compiler resolve overloads?**
> In three phases, stopping at the first that matches: exact match or widening primitive conversion,
> then boxing or unboxing, then varargs. The ordering preserves backward compatibility with code
> written before autoboxing and varargs existed. Resolution happens at compile time using static
> types.

**Q: Overloading vs overriding?**
> Overloading is multiple methods with the same name and different parameters, resolved at compile
> time from the static type. Overriding is a subclass replacing a superclass method with an identical
> signature, dispatched at runtime based on the actual object type via `invokevirtual`.

**Q: What are varargs and what should you watch for?**
> Syntax sugar for an array parameter, which must be last and unique. Calling with no arguments gives
> an empty array, but passing a literal `null` makes the array itself null. Each call allocates an
> array, which is why performance-sensitive APIs provide fixed-arity overloads first.

**Q: Does Java optimise tail recursion?**
> No. Each call consumes a stack frame regardless of position, so deep recursion throws
> `StackOverflowError` at roughly ten to twenty thousand frames. Deep traversals need to be converted
> to iteration with an explicit stack.
