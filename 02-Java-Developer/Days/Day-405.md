# Day 405

**L-405** · Event sourcing — the power, and the cost stated honestly

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ In event sourcing the events are the truth and current state is a derived cache. That inversion
> gives you a perfect audit log, time travel and retroactive bug fixes — and it makes "delete this
> user's data" genuinely hard.**
>
> Today: state as a fold, **what you actually gain and what you actually pay**, versioning events you can
> never rewrite, the GDPR problem and its real answer, and **the honest verdict on when to use it.**

---

# Part 1 — ⭐⭐ State as a fold over events

```
⭐⭐ TRADITIONAL:      UPDATE accounts SET balance = 300 WHERE id = 1;
⭐   ⇒ ⭐⭐ the previous value is GONE. ⭐⭐ WHY it changed is gone. ⭐ You have the answer, not the story.

⭐⭐ EVENT SOURCED:    append AccountOpened{id:1} · Deposited{200} · Deposited{150} · Withdrawn{50}
⭐   ⇒ ⭐⭐ balance = fold(events) = 300
⭐   ⇒ ⭐⭐ AND you can answer: what was it on Tuesday · why did it change · who did it ·
⭐        what would it be if we replayed with the bug fixed.
```

```java
// ⭐ The aggregate is a fold. That is the entire programming model.
public record Account(String id, long balanceCents, long version) {

    Account apply(Event e) {
        return switch (e) {
            case Opened o    -> new Account(o.id(), 0, version + 1);
            case Deposited d -> new Account(id, balanceCents + d.cents(), version + 1);
            case Withdrawn w -> new Account(id, balanceCents - w.cents(), version + 1);
        };
    }

    // ⭐⭐ Commands VALIDATE against current state and EMIT events. They never mutate.
    List<Event> handle(Withdraw cmd) {
        if (cmd.cents() > balanceCents) throw new InsufficientFunds();   // ⭐ the invariant
        return List.of(new Withdrawn(id, cmd.cents()));
    }
}
```

| ⭐ Vocabulary that matters | |
|---|---|
| ⭐⭐ **Command** | ⭐ a request that may be rejected — imperative: `Withdraw` |
| ⭐⭐ **Event** | ⭐⭐ **a fact that already happened — past tense, never rejected: `Withdrawn`** |
| ⭐ Aggregate | ⭐⭐ **the consistency boundary** and the unit of the event stream (Day 305) |
| ⭐ Stream | ⭐ the ordered events of one aggregate instance |
| ⭐ Projection | ⭐ a read model built by folding events (Day 406) |

> **⭐ The past-tense discipline is not style.** An event is a fact; **you cannot reject, alter or undo
> a fact.** If you find yourself wanting to "cancel" an event, **you actually want to emit a new one** —
> which is the same insight as compensation in sagas (Day 408).

# Part 2 — ⭐⭐ Concurrency: optimistic, on the stream

```
⭐ appendToStream("account-1", ⭐⭐ expectedVersion = 42, [Withdrawn{50}])
⭐   ⇒ ⭐ someone else appended first ⇒ actual version is 43
⭐   ⇒ ⭐⭐ WrongExpectedVersion ⇒ ⭐⭐ RELOAD, RE-VALIDATE, RETRY
⭐ ⇒ ⭐⭐ This is optimistic locking with the stream version as the ETag —
⭐   and it is why the AGGREGATE must be the contention boundary (Day 305).
```

| ⭐ Consequence | |
|---|---|
| ⭐⭐ **A large aggregate = a hot stream = constant version conflicts** | ⭐⭐ Day 305's 40,000-product `Category` failure, again |
| ⭐ Long streams need **snapshots** | ⭐ fold 50,000 events on every load is not viable — snapshot every N |
| ⭐ Snapshots are a **cache** | ⭐⭐ **deletable and rebuildable** — never the source of truth |

# Part 3 — ⭐⭐ What it costs (the part that decides whether to do it)

| ⭐ Cost | ⭐ Detail |
|---|---|
| ⭐⭐ **Events are forever** | ⭐⭐ **you cannot fix a badly designed event** — the old ones are already written |
| ⭐⭐ **Versioning / upcasting** | ⭐⭐ every reader must understand **every historical shape**, forever |
| ⭐⭐ **No ad-hoc queries** | ⭐⭐ you cannot `WHERE balance > 100` on an event store — **you must have built a projection** |
| ⭐⭐ **Eventual consistency in reads** | ⭐ projections lag the write (Day 406) |
| ⭐⭐ **GDPR erasure** | ⭐⭐ **an immutable log versus the right to be forgotten** — see below |
| ⭐ Storage growth | ⭐ every change forever; usually fine, occasionally not |
| ⭐⭐ **Team cost** | ⭐⭐ **every new developer must learn a model they have never seen** — the largest cost, and the one nobody budgets |
| ⭐ Tooling | ⭐ debugging, admin fixes and "just update the row" all become harder |

```
⭐⭐ EVENT VERSIONING — the three techniques, since you cannot rewrite history:
⭐   1. ⭐⭐ WEAK SCHEMA: add optional fields only. ⭐ Solves 80% of cases. ⭐ Do this first.
⭐   2. ⭐⭐ UPCASTING: on read, transform v1 → v2 in a pipeline before the aggregate sees it.
⭐   3. ⭐ COPY-TRANSFORM: write a NEW stream from the old one. ⭐⭐ Breaks the "immutable" property —
⭐      it is a migration, and it is a big deal. ⭐ Reserve it for genuine emergencies.
```

## ⭐⭐ The GDPR problem, and its real answer

```
⭐⭐ "Delete all data for user X" versus ⭐⭐ AN APPEND-ONLY IMMUTABLE LOG. These conflict.
⭐   ❌ deleting events        ⇒ ⭐⭐ breaks the fold; state becomes wrong
⭐   ❌ rewriting events       ⇒ ⭐ breaks every downstream offset and hash
⭐   ✅ ⭐⭐ CRYPTO-SHREDDING:
⭐        ⭐ encrypt personal fields with a PER-SUBJECT key, stored OUTSIDE the log
⭐        ⭐⭐ erasure = DELETE THE KEY ⇒ ⭐⭐ the events remain, the personal data is unrecoverable
⭐   ⇒ ⭐ the structure survives, the fold still works, and the obligation is met. (Day 395)
```

> **⭐⭐ Decide this before your first event, not after your first data subject request.** Retrofitting
> crypto-shredding onto an existing log means re-encrypting history — **which is the copy-transform you
> were trying to avoid.**

# Part 4 — ⭐⭐ The honest verdict

| ⭐ Event sourcing **fits** when | ⭐ It **does not fit** when |
|---|---|
| ⭐⭐ **the history IS the product** — ledgers, trading, insurance, medical records | ⭐ the domain is CRUD with a form on top |
| ⭐⭐ **audit is a regulatory requirement** | ⭐ nobody has ever asked "why did this change?" |
| ⭐ "what did it look like on date X" is a real question | ⭐ ad-hoc querying is the main access pattern |
| ⭐ temporal/retroactive corrections happen | ⭐⭐ **the team has never used it and the deadline is short** |
| ⭐ the domain has rich, meaningful state transitions | ⭐ the entity has three fields and one lifecycle |

```
⭐⭐ THE PRACTICAL POSITION THAT MOST TEAMS SHOULD TAKE:
⭐   ⭐⭐ Do NOT event-source the whole system.
⭐   ⭐⭐ Event-source the ONE OR TWO AGGREGATES where history is genuinely the value —
⭐     the ledger, the order lifecycle, the policy — and leave the rest as ordinary CRUD.
⭐   ⇒ ⭐⭐ Teams that adopt it wholesale usually regret it.
⭐     ⭐ Teams that adopt it for one aggregate are usually glad.
```

| ⭐⭐ And "event sourcing lite", which is often the right amount | |
|---|---|
| ⭐ Keep normal mutable state as the source of truth | ⭐ ordinary tables, ordinary queries |
| ⭐⭐ **Also append a domain event row in the same transaction** | ⭐⭐ **this is the outbox** (Day 407) |
| ⭐ You get | ⭐ audit, integration events, and most of the debugging value |
| ⭐ You avoid | ⭐⭐ upcasting, snapshots, projection rebuilds and the team learning cost |

⚠️ **The distinction that keeps this honest: "we store events" is not event sourcing.** Event sourcing
means **state is derived from the events and cannot be edited any other way.** If you can `UPDATE` the
row, you have an audit log — **which is a perfectly good thing to have, and you should call it that.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Event-sourcing an entire system on first contact** | ⭐⭐ the cost lands everywhere, the benefit in two places |
| ⭐ Naming events imperatively (`UpdateBalance`) | ⭐⭐ events are facts, in the past tense |
| ⭐ Putting validation in the event | ⭐ commands validate; events already happened |
| ⭐⭐ **Aggregates too large** | ⭐⭐ a hot stream and constant version conflicts |
| ⭐ No snapshots on long streams | ⭐ folding 50,000 events per load |
| ⭐ Treating snapshots as the source of truth | ⭐⭐ they are a deletable cache |
| ⭐⭐ **Designing events technically** (`RowUpdated`) | ⭐⭐ the whole value is domain meaning |
| ⭐ Assuming you can fix a bad event later | ⭐⭐ it is already written |
| ⭐ No versioning strategy from day one | ⭐ upcasting bolted on under pressure |
| ⭐⭐ **No erasure plan before the first event** | ⭐⭐ retrofitting crypto-shredding means rewriting history |
| ⭐ Expecting ad-hoc queries | ⭐⭐ you can only query what you projected |
| ⭐ Calling an audit table "event sourcing" | ⭐ if you can UPDATE the row, it is not |
| Ignoring the team learning cost | the largest cost and the least budgeted |

## Interview questions

**Q: What is event sourcing?**
Storing state as the sequence of events that produced it rather than the current values, so current state
is a fold over the event stream and the events are the source of truth. A traditional update destroys the
previous value and the reason for the change; an event stream keeps both. Commands are requests that can
be rejected, events are facts in the past tense that cannot be, and the aggregate is both the consistency
boundary and the unit of the stream — concurrency is handled by optimistic locking on the stream version.

**Q: What does it actually cost?**
More than people expect. Events are forever, so a badly designed event cannot be fixed and every reader
must understand every historical shape via upcasting. You cannot query the event store ad hoc — you can
only query projections you thought to build. Reads are eventually consistent. Long streams need
snapshots, and snapshots must be treated as a rebuildable cache rather than truth. Erasure conflicts
directly with immutability. And the largest cost is the one nobody budgets: every new developer has to
learn a model they have not seen before, and routine operational fixes that used to be an UPDATE become
projects.

**Q: How do you delete a user's data from an immutable log?**
Crypto-shredding. Personal fields are encrypted with a per-subject key held outside the log, and erasure
means deleting the key — the events remain so the fold still works and downstream offsets are unaffected,
but the personal data is unrecoverable. Deleting or rewriting events is not viable: the first breaks the
fold and the second breaks every offset and hash downstream. The important part is that this has to be
decided before the first event is written, because retrofitting it means re-encrypting history, which is
the destructive migration you were trying to avoid.

**Q: When would you use it?**
When the history is the product. Ledgers, trading, insurance, medical records — domains where "what did
this look like on Tuesday", "why did it change" and "who changed it" are real business questions, and
where audit is a regulatory requirement rather than a nice-to-have. What I would not do is event-source a
whole system on first contact. The position that works is event-sourcing the one or two aggregates where
history genuinely is the value and leaving everything else as ordinary CRUD. Teams that adopt it wholesale
usually regret it; teams that adopt it for one aggregate are usually glad.

**Q: What is "event sourcing lite"?**
Keeping normal mutable state as the source of truth while also appending a domain event row in the same
database transaction — which is exactly the outbox pattern. You get the audit trail, the integration
events for other services, and most of the debugging value, without upcasting, snapshots, projection
rebuilds or the team learning curve. And it is worth being precise with the language: storing events
alongside mutable state is an audit log, not event sourcing. Event sourcing means state is derived from
events and cannot be changed any other way. If you can UPDATE the row, call it what it is.

## Mini task

1. ⭐⭐ Implement one aggregate as a **pure fold**: commands validate and emit, events apply. No mutation
   anywhere.
2. ⭐ Name every event in the **past tense** and remove any that reads like a command.
3. ⭐⭐ Implement **optimistic concurrency** with `expectedVersion` and reproduce a conflict from two
   concurrent commands.
4. ⭐⭐ Deliberately make the aggregate **too large** and demonstrate constant version conflicts. Then
   split it (Day 305).
5. ⭐ Add **snapshots** every 100 events, then **delete all snapshots** and confirm state still rebuilds.
6. ⭐⭐ Change an event's shape and implement **upcasting** so old events still load.
7. ⭐⭐ Implement **crypto-shredding**: per-subject key, encrypted personal fields, erasure by key
   deletion. Prove the fold still works afterwards.
8. ⭐ Try to answer an **ad-hoc query** against the event store and feel why projections are mandatory.
9. ⭐⭐ Write the **honest cost/benefit page** for event-sourcing one aggregate of your flagship — and
   decide, with reasons, whether to.
10. ⭐ Implement **event sourcing lite** for a different aggregate: normal state plus an event row in the
    same transaction. Compare the effort.

## 🎙️ Articulation drill

the value and leave the rest as CRUD. And for many teams the right amount is event sourcing lite —
ordinary state plus a domain event appended in the same transaction, which is the outbox, and which gets
you the audit and the integration events without the learning cost.**
