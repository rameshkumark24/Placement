# Part 1 — L-016 · REST

## What REST actually is

**REST is an architectural style, not a protocol, not a standard, and not "JSON over HTTP".**

Roy Fielding defined it in his 2000 PhD dissertation, *describing the architecture that already made
the web work*. He wasn't inventing an API pattern — he was explaining why the web scaled when other
distributed systems of the era didn't.

That framing matters, because almost every "REST API" in production violates at least one of his
constraints. Being able to say "this is REST-ish, and here's the constraint we're not meeting" is a
much stronger interview answer than reciting the six constraints.

## The six constraints

| # | Constraint | What it means | Why it scales |
|---|---|---|---|
| 1 | **Client–server** | Separate UI from data storage | Each evolves independently |
| 2 | **Stateless** | Every request carries everything needed | Any server handles any request → horizontal scaling |
| 3 | **Cacheable** | Responses say whether they can be cached | Eliminates requests entirely |
| 4 | **Uniform interface** | One consistent way to address and manipulate things | Decoupling; generic intermediaries work |
| 5 | **Layered system** | A client can't tell if it's talking to the origin | Proxies, CDNs, LBs can be inserted freely |
| 6 | **Code on demand** *(optional)* | Server can ship executable code | This is literally JavaScript |

**Constraint 2 (stateless) is the load-bearing one** — you met it on Day 010. It's why you can put
ten servers behind a load balancer with no sticky sessions.

**Constraint 5 (layered) is why the web survived its own growth.** CDNs, reverse proxies and load
balancers could be inserted decades later without changing a single client, because clients can't
tell the difference. That's the same idea as layering from Day 001.

## The uniform interface, in four parts

This is the constraint people actually implement, and it has sub-parts worth naming:

1. **Resource identification** — everything is a resource with a URI
2. **Manipulation through representations** — you exchange JSON/XML *representations*, not the
   resource itself
3. **Self-descriptive messages** — the message carries everything needed to process it
   (`Content-Type`, cache headers, status codes)
4. **HATEOAS** — the response contains links to what you can do next

### HATEOAS — the honest assessment

```json
{
  "id": 42,
  "status": "pending",
  "_links": {
    "self":   { "href": "/orders/42" },
    "cancel": { "href": "/orders/42/cancel", "method": "POST" },
    "pay":    { "href": "/orders/42/payment", "method": "POST" }
  }
}
```

The idea: the client discovers available actions from the response rather than hardcoding URLs, so
the server can change its URI structure freely.

**Almost nobody does this.** By Fielding's own definition, an API without HATEOAS is not REST. He has
said so, sharply and repeatedly.

**What to say in an interview:** *"Strictly, REST requires HATEOAS, and most APIs including mine
don't implement it — so they're REST-ish, level 2 on the Richardson Maturity Model. In practice the
cost of hypermedia rarely pays back for a first-party API with a known client, though it's genuinely
useful for long-lived public APIs."* That answer demonstrates you know the theory *and* have a
position on it.

### The Richardson Maturity Model

| Level | What you have | Reality |
|---|---|---|
| 0 | One URI, one verb — HTTP as a tunnel | SOAP-style |
| 1 | Resources — many URIs, still mostly POST | Common |
| 2 | **HTTP verbs + status codes used properly** | **Where 95% of "REST APIs" live** |
| 3 | HATEOAS | Rare |

Aim for level 2 and know that's what you're doing.

## Designing resources

**Resources are nouns. Verbs come from HTTP.**

```
✅  GET    /users              list
✅  POST   /users              create
✅  GET    /users/42           read
✅  PUT    /users/42           replace
✅  PATCH  /users/42           partial update
✅  DELETE /users/42           delete
✅  GET    /users/42/orders    sub-resource

❌  GET    /getUsers           verb in the URI
❌  POST   /createUser         the method already says "create"
❌  POST   /users/42/delete    that's what DELETE is for
```

**Conventions worth committing to:**

- **Plural nouns** — `/users` not `/user`. Consistency beats grammar debates.
- **Nest at most one level.** `/users/42/orders` is fine. `/users/42/orders/7/items/3/reviews` is
  not — use `/reviews?itemId=3`.
- **Filtering, sorting, pagination are query parameters**, not paths:
  `/orders?status=pending&sort=-createdAt&limit=20&cursor=abc`
- **Kebab-case in URIs**, `camelCase` or `snake_case` in JSON — pick one and never mix.

### When something genuinely isn't a noun

Some operations resist resource modelling: search, login, "send email", "recalculate".

Two acceptable answers, and you should be able to defend either:

```
POST /searches           ← model the action as a resource
POST /users/42/actions/deactivate   ← explicit action sub-resource
```

**Don't contort the model to avoid admitting it.** Fielding's constraints are a means to
scalability, not a religion. Saying "this endpoint is RPC-shaped because the operation isn't a
resource, and that's a deliberate choice" is a good answer.

## REST vs RPC vs GraphQL

| | REST | RPC (gRPC) | GraphQL |
|---|---|---|---|
| Model | Resources + verbs | Functions | One query language |
| Transport | HTTP | HTTP/2 (gRPC) | Usually HTTP POST |
| Format | JSON | Protobuf (binary) | JSON |
| Endpoints | Many | Many methods | **One** |
| Over/under-fetching | Common | Controlled | **Solved by design** |
| HTTP caching | **Works natively** | Poor | **Poor** — everything is a POST to one URL |
| Discoverability | OpenAPI | Reflection / .proto | Introspection — excellent |
| Best at | Public APIs, CRUD, cacheable reads | **Service-to-service, low latency** | Many clients with different data needs |

**The honest comparison:**

- **REST** wins for public APIs and anything cacheable. It rides HTTP's existing infrastructure —
  CDNs, proxies, browser caches all understand it for free.
- **gRPC** wins between your own services. Binary protobuf is compact and fast, HTTP/2 multiplexes
  (Day 011), and code generation gives type safety across languages. Poor browser support is
  irrelevant when both ends are yours.
- **GraphQL** wins when many different clients need different shapes of the same data, and
  over-fetching is a real cost — a mobile app on 3G fetching a 40-field object to show 3 fields.

**GraphQL's costs are real and worth naming:** HTTP caching mostly stops working (one URL, all
POSTs), the N+1 problem gets much worse and needs DataLoader, and a malicious deeply-nested query is
a denial-of-service vector requiring depth and complexity limits. It's not a free upgrade.

**The senior answer to "REST or GraphQL?"** is *"what are the clients, and is over-fetching actually
costing you anything?"* — not a preference.

## Type this yourself

Extend your Day 010 server into a proper REST resource.

```java
import java.io.*;
import java.net.*;
import java.util.*;
import java.util.concurrent.*;

public class RestServer {
    static final Map<Integer, String> users = new ConcurrentHashMap<>();
    static int nextId = 1;

    public static void main(String[] args) throws IOException {
        users.put(nextId++, "Ramesh");
        users.put(nextId++, "Priya");

        ServerSocket server = new ServerSocket(8080);
        System.out.println("http://localhost:8080/users");

        while (true) {
            try (Socket client = server.accept()) {
                BufferedReader in = new BufferedReader(
                        new InputStreamReader(client.getInputStream()));
                String requestLine = in.readLine();
                if (requestLine == null) continue;

                int contentLength = 0;
                String h;
                while ((h = in.readLine()) != null && !h.isEmpty()) {
                    if (h.toLowerCase().startsWith("content-length:"))
                        contentLength = Integer.parseInt(h.split(":")[1].trim());
                }
                char[] bodyBuf = new char[contentLength];
                if (contentLength > 0) in.read(bodyBuf);
                String body = new String(bodyBuf);

                String[] p = requestLine.split(" ");
                String method = p[0], path = p[1];
                System.out.println(method + " " + path);

                String status, json;

                if (path.equals("/users") && method.equals("GET")) {
                    StringBuilder sb = new StringBuilder("[");
                    users.forEach((id, name) -> sb.append("{\"id\":").append(id)
                            .append(",\"name\":\"").append(name).append("\"},"));
                    if (sb.length() > 1) sb.setLength(sb.length() - 1);
                    status = "200 OK"; json = sb.append("]").toString();

                } else if (path.equals("/users") && method.equals("POST")) {
                    int id = nextId++;
                    users.put(id, body.isBlank() ? "unnamed" : body.trim());
                    status = "201 Created";
                    json = "{\"id\":" + id + ",\"_links\":{\"self\":\"/users/" + id + "\"}}";

                } else if (path.matches("/users/\\d+")) {
                    int id = Integer.parseInt(path.substring("/users/".length()));
                    if (!users.containsKey(id)) { status = "404 Not Found"; json = "{\"error\":\"not found\"}"; }
                    else switch (method) {
                        case "GET"    -> { status = "200 OK";
                                           json = "{\"id\":" + id + ",\"name\":\"" + users.get(id) + "\"}"; }
                        case "PUT"    -> { users.put(id, body.trim()); status = "200 OK";
                                           json = "{\"id\":" + id + ",\"name\":\"" + users.get(id) + "\"}"; }
                        case "DELETE" -> { users.remove(id); status = "204 No Content"; json = ""; }
                        default       -> { status = "405 Method Not Allowed"; json = "{\"error\":\"bad method\"}"; }
                    }
                } else {
                    status = "404 Not Found"; json = "{\"error\":\"no such resource\"}";
                }

                byte[] out = json.getBytes();
                OutputStream os = client.getOutputStream();
                os.write(("HTTP/1.1 " + status + "\r\n"
                        + "Content-Type: application/json\r\n"
                        + "Content-Length: " + out.length + "\r\n"
                        + "Connection: close\r\n\r\n").getBytes());
                os.write(out);
                os.flush();
            }
        }
    }
}
```

```bash
curl -v localhost:8080/users
curl -v localhost:8080/users/1
curl -v -X POST -d "Arjun" localhost:8080/users
curl -v -X PUT  -d "Renamed" localhost:8080/users/1
curl -v -X DELETE localhost:8080/users/1
curl -v -X DELETE localhost:8080/users/1     # again — idempotent? check the state
curl -v -X PATCH localhost:8080/users/2      # 405
curl -v localhost:8080/nope                  # 404
```

**Two things to notice:**

1. **`DELETE` twice.** The second returns 404, but the *state* is identical — that's idempotence
   (Day 010), and now you've verified it rather than read it.
2. **`POST` returns `201` with a `_links` object.** That's a taste of HATEOAS. You've now built level
   2 with a hint of level 3.

## Common mistakes

| Mistake | Correction |
|---|---|
| "REST means JSON over HTTP" | It's an architectural style with six constraints. Format is irrelevant. |
| Verbs in URIs (`/getUser`, `/createOrder`) | The HTTP method is the verb. URIs name resources. |
| Everything as POST | Loses caching, idempotence and semantic clarity. |
| Deep nesting | More than one level becomes unusable. Use query parameters. |
| `200 OK` with an error in the body | Breaks every client and monitoring tool. Use real status codes. |
| Claiming full REST without HATEOAS | Know you're at Richardson level 2, and say so. |
| Choosing GraphQL by default | It costs you HTTP caching and adds N+1 and query-depth problems. |

## Interview questions

**Q: What is REST?**
> An architectural style described by Roy Fielding for distributed hypermedia systems, defined by six
> constraints: client-server, stateless, cacheable, uniform interface, layered system, and optionally
> code on demand. It isn't a protocol or a data format — it describes properties that make a system
> scalable and evolvable.

**Q: What does statelessness give you?**
> Every request carries all the information needed to serve it, so no server holds session context.
> Any server can handle any request, which enables horizontal scaling behind a load balancer without
> sticky sessions, and makes failover trivial. The cost is re-sending credentials on every request.

**Q: Is your API actually RESTful?**
> Most APIs, including ones I've built, sit at level 2 of the Richardson Maturity Model — proper
> resources, HTTP verbs and status codes, but no hypermedia. By Fielding's definition HATEOAS is
> required, so strictly they're REST-ish. For a first-party API with a known client the cost of
> hypermedia rarely pays back, though it matters for long-lived public APIs.

**Q: REST vs GraphQL — how would you choose?**
> By asking who the clients are and whether over-fetching costs anything. GraphQL suits many
> heterogeneous clients needing different shapes of data, especially on constrained networks. It
> costs you HTTP caching, since everything is a POST to one endpoint, and introduces N+1 and query
> complexity problems needing DataLoader and depth limits. For a cacheable public API, REST is
> usually better.

**Q: When would you use gRPC?**
> Service-to-service communication where both ends are yours. Binary protobuf is compact, HTTP/2
> multiplexes, and generated stubs give cross-language type safety. Browser support is poor, which
> doesn't matter internally.

# Part 2 — C-11 · Sockets

## The API under everything

Day 004 gave you four calls. Here is the complete picture, and the symmetry between the two sides:

```
   SERVER                              CLIENT
   ──────                              ──────
   socket()   create endpoint          socket()
   bind()     claim address:port
   listen()   mark as passive
   accept()   ─── blocks ───────────── connect()   ── handshake happens here (Day 005)
      │                                   │
      └── returns a NEW socket            └── this socket is now connected
      │                                   │
   read()/write()  ◀────────────────▶  read()/write()
   close()                                close()
```

**A socket is a file descriptor.** On Unix, "everything is a file" — and a socket is just another
integer the kernel maps to a resource. That's why:

- `read()` and `write()` work on sockets exactly as on files
- You can `select()`/`poll()`/`epoll()` over a mix of files and sockets
- Running out of file descriptors kills your server (`Too many open files` — `ulimit -n`), and this
  is what your leaked-socket experiment on Day 004 was heading toward

## Blocking vs non-blocking

| Mode | `accept()`/`read()` with no data |
|---|---|
| **Blocking** (default) | Thread parked by the OS until data arrives |
| **Non-blocking** | Returns immediately with `EWOULDBLOCK` |

Non-blocking alone is useless — you'd spin burning CPU. It's only useful with **multiplexing**: ask
the kernel "which of these 10,000 sockets is ready?" and act on those.

```
   select()   O(n) scan, 1024 fd limit          — the original
   poll()     O(n) scan, no fd limit
   epoll()    O(1), Linux                       — what everything uses today
   kqueue()   O(1), BSD/macOS
   IOCP       Windows
```

**`epoll` is the foundation under every high-concurrency server you'll ever touch** — Nginx, Node's
libuv, Netty, Redis. Java's NIO (`Selector`) wraps it. Day 064 (B-13) and Day 067 (B-14) go deeper;
knowing the name and the shape now is enough.

## The three concurrency models — the map for Stage 1

| Model | Cost per connection | Handles 10k? | Used by |
|---|---|---|---|
| **Thread per connection** | ~1 MB stack | Poorly | Classic Tomcat, your Day 004 fix |
| **Thread pool** | Bounded threads, queued work | Better; blocks under load | Tomcat, Spring MVC |
| **Event loop + epoll** | ~few KB | **Yes** | Nginx, Node, Netty, Redis |
| **Virtual threads** | ~few KB, blocking style | **Yes** | Java 21+ (Day 072) |

**This table is the through-line of Stage 1's concurrency section.** Day 004 gave you model 1 by
hand. Day 069 gives you model 2. B-13/B-14 give you model 3. Day 072 shows how model 4 gets model
3's cost with model 1's readability — which is the whole point of Project Loom.

## Type this yourself

```java
import java.nio.channels.*;
import java.nio.*;
import java.net.*;
import java.util.*;

public class NioServer {
    public static void main(String[] args) throws Exception {
        Selector selector = Selector.open();                       // epoll under the hood
        ServerSocketChannel server = ServerSocketChannel.open();
        server.bind(new InetSocketAddress(8080));
        server.configureBlocking(false);                            // ← non-blocking
        server.register(selector, SelectionKey.OP_ACCEPT);

        System.out.println("NIO server on 8080 — ONE thread, many connections");

        while (true) {
            selector.select();                                      // block until something is ready
            Iterator<SelectionKey> it = selector.selectedKeys().iterator();

            while (it.hasNext()) {
                SelectionKey key = it.next();
                it.remove();

                if (key.isAcceptable()) {
                    SocketChannel ch = server.accept();
                    ch.configureBlocking(false);
                    ch.register(selector, SelectionKey.OP_READ);
                    System.out.println("Accepted " + ch.getRemoteAddress());

                } else if (key.isReadable()) {
                    SocketChannel ch = (SocketChannel) key.channel();
                    ByteBuffer buf = ByteBuffer.allocate(1024);
                    int n = ch.read(buf);
                    if (n == -1) { ch.close(); continue; }

                    String body = "Handled by one thread: " + Thread.currentThread().getName();
                    String resp = "HTTP/1.1 200 OK\r\nContent-Length: " + body.length()
                                + "\r\nConnection: close\r\n\r\n" + body;
                    ch.write(ByteBuffer.wrap(resp.getBytes()));
                    ch.close();
                }
            }
        }
    }
}
```

**Compare this to Day 004's server.** Same protocol, same result — but **one thread serves every
connection simultaneously**, because `select()` asks the kernel which sockets are ready instead of
dedicating a thread to waiting on each.

Open ten browser tabs at once. One thread, ten connections, no blocking. That's the model Nginx and
Node use.

## Interview questions

**Q: What is a socket?**
> An endpoint for network communication, represented as a file descriptor. The same `read` and
> `write` calls work on it as on a file, which is why sockets can be multiplexed alongside files with
> `select` or `epoll`.

**Q: Blocking vs non-blocking I/O?**
> A blocking call parks the thread in the kernel until data is available, costing no CPU but one
> thread per waiting operation. A non-blocking call returns immediately, so it's only useful combined
> with a readiness mechanism like `epoll` that tells you which descriptors can proceed.

**Q: How does a server handle 10,000 concurrent connections?**
> Not with a thread each — that's about 10 GB of stack. Either an event loop over `epoll`, where one
> thread multiplexes all ready sockets, as Nginx and Node do; or lightweight threads such as Java's
> virtual threads, which give the blocking programming model at a few kilobytes per task.
