# Day 235 🔐

**J-235** · 🔐 **Auth in the browser** — ⭐⭐ the decision Spring Security cannot make for you

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `localStorage` is readable by any JavaScript that runs on your page, so a
> JWT stored there is a token that one XSS — including one from a compromised dependency you never
> wrote — exfiltrates permanently, while an `HttpOnly` cookie is not readable by script at all and
> therefore survives the same attack.**
>
> Today: the storage decision, ⭐ the cookie flags, ⭐⭐ refresh without a race, and logout.

---

# Part 1 — ⭐⭐ The decision

| | `localStorage` | ⭐⭐ `HttpOnly` cookie |
|---|---|---|
| Readable by JS | ⭐⭐ **Yes — the whole problem** | ⭐ **No.** Not by your code, not by an attacker's |
| Survives XSS | ❌ ⭐⭐ Token stolen, silently, forever | ✅ ⭐ Attacker can *act* while on the page, but **cannot take the token away** |
| Sent automatically | No — you attach it | ⭐ Yes, by the browser |
| CSRF exposure | ⭐ None | ⭐⭐ **Yes — needs `SameSite` + a token** |
| Stateless JWT story | ⭐ The one everyone teaches | ⭐ Works identically — the cookie just **carries** the JWT |
| Mobile / non-browser clients | ⭐ Fine | ⭐ Awkward — use a bearer header for those |

```
⭐⭐ THE ASYMMETRY THAT DECIDES IT

⭐   XSS + localStorage ⇒ ⭐⭐ THE ATTACKER TAKES THE TOKEN AND USES
⭐     IT FROM THEIR OWN MACHINE, AT LEISURE, UNTIL IT EXPIRES.
⭐     ⭐ Your logout does nothing. A stateless JWT CANNOT BE REVOKED
⭐       without the denylist you probably did not build.
⭐   XSS + HttpOnly cookie ⇒ ⭐ the attacker can make requests AS the
⭐     user WHILE THE PAGE IS OPEN — bad, but ⭐⭐ BOUNDED IN TIME AND
⭐     TO YOUR ORIGIN, and revoking the session ends it.

⭐   ⇒ ⭐⭐ NEITHER IS "XSS-PROOF". THE COOKIE LIMITS THE BLAST RADIUS.
⭐     THAT IS THE ENTIRE ARGUMENT, AND IT IS ENOUGH.
```

> ⭐⭐ **"But stateless JWTs are the point."** A JWT in an `HttpOnly` cookie is still a JWT and your
> resource server still validates the signature statelessly. **You have changed the transport, not the
> model** — and `Set-Cookie` from your auth endpoint is one line of Spring. ⭐ The "bearer token in
> localStorage" pattern is a tutorial default, not a security decision.
>
> ⭐ **`sessionStorage` is not a fix** — same JS-readable problem, shorter life.

# Part 2 — The flags

```java
// ⭐ Spring — the four that matter
ResponseCookie cookie = ResponseCookie.from("session", token)
    .httpOnly(true)     // ⭐⭐ JS CANNOT READ IT. The one that matters most.
    .secure(true)       // ⭐ HTTPS only
    .sameSite("Lax")    // ⭐⭐ not sent on cross-site POSTs ⇒ kills most CSRF
    .path("/")
    .maxAge(Duration.ofMinutes(15))
    .build();
response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());
```

| ⭐ Flag | Missing it means |
|---|---|
| `HttpOnly` | ⭐⭐ Any script reads it. **The default failure.** |
| `Secure` | ⭐ Sent over plain HTTP if anything downgrades |
| ⭐⭐ `SameSite=Lax` | Sent on cross-site requests ⇒ **CSRF** |
| `SameSite=None` | ⭐ Required for a genuinely cross-domain API — **and then you must add a CSRF token** |
| `Domain` too broad | ⭐⭐ `.example.com` shares the cookie with **every** subdomain |

```
⭐⭐ SameSite=Lax IS NOT A COMPLETE CSRF DEFENCE
⭐   · Lax still allows top-level GET navigations ⇒ ⭐⭐ ANY
⭐     STATE-CHANGING GET IS STILL EXPLOITABLE. (Never mutate on GET —
⭐     which is also just correct HTTP.)
⭐   · Subdomains are SAME-SITE ⇒ ⭐ a compromised subdomain still
⭐     sends your cookie.
⭐   ⇒ ⭐ FOR ANYTHING THAT MATTERS: Lax + Spring Security's CSRF
⭐     token repository, or an Origin check. ⭐⭐ AND NOTE: THE MOMENT
⭐     YOU USE COOKIES, `http.csrf().disable()` STOPS BEING FREE.
⭐     Most Spring API tutorials disable CSRF *because* they assumed
⭐     a bearer token. Change the transport, revisit that line.
```

# Part 3 — ⭐⭐ Refresh, and the race

```
⭐⭐ THE PATTERN
⭐   access token   ⇒ ⭐ SHORT (5–15 min), used on every request
⭐   refresh token  ⇒ ⭐ long (days), HttpOnly cookie, ⭐⭐ ONLY EVER
⭐                     SENT TO /auth/refresh (path-scoped)

⭐⭐ THE RACE NOBODY HANDLES ON THE FIRST ATTEMPT
⭐   the token expires while SIX requests are in flight
⭐   ⇒ all six get 401 ⇒ ⭐⭐ ALL SIX CALL /auth/refresh
⭐   ⇒ with refresh-token ROTATION, the first succeeds and
⭐     ⭐⭐ THE OTHER FIVE PRESENT A NOW-INVALID TOKEN
⭐   ⇒ ⭐⭐ THE SERVER SEES REUSE, ASSUMES THEFT, KILLS THE SESSION
⭐     ⇒ THE USER IS LOGGED OUT AT RANDOM.
```

```javascript
// ⭐⭐ SINGLE-FLIGHT REFRESH — one refresh, five waiters
let refreshing = null;                    // ⭐ the shared promise

async function withAuth(request) {
  let res = await request();
  if (res.status !== 401) return res;

  refreshing ??= refresh().finally(() => { refreshing = null; });
  //          ⭐⭐ every concurrent caller awaits THE SAME promise
  try { await refreshing; } catch { redirectToLogin(); throw; }

  return request();                        // ⭐ retry ONCE. Never loop.
}
```

> ⭐⭐ **This is the double-checked-locking / `computeIfAbsent` pattern you already know** — one leader
> does the work, everyone else waits on the same future, and the failure path must complete *all*
> waiters or they hang forever. **Same problem, single-threaded.**

# Part 4 — Logout, and what it must actually do

```
⭐⭐ LOGOUT IS A SERVER OPERATION. Deleting a client-side token
⭐   only makes the CURRENT TAB forget it.

⭐   ① ⭐ POST /auth/logout ⇒ ⭐⭐ SERVER REVOKES the refresh token
⭐   ② server clears the cookies (Max-Age=0)
⭐   ③ ⭐ client clears its query cache — ⭐⭐ OTHERWISE THE NEXT USER
⭐      ON THIS MACHINE SEES CACHED DATA FROM THE PREVIOUS ONE
⭐   ④ ⭐ redirect
⭐   ⭐⭐ AND ACROSS TABS: a `storage` event, or tab 2 keeps showing
⭐     a logged-in UI.
```

| ⭐ Trap | |
|---|---|
| **Access token still valid after logout** | ⭐⭐ **A stateless JWT cannot be revoked.** Short expiry is the mitigation. **Say the window out loud** — "up to 15 minutes" is an honest answer, and it is the real cost of statelessness. |
| **Query cache not cleared** | ⭐⭐ A genuine cross-user data leak on shared machines |
| **Redirect before revoke** | ⭐ Fire-and-forget logout that fails silently (Day 216) |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "where do you store the auth token?"**

Answer with the asymmetry. **An HttpOnly cookie, because `localStorage` is readable by any JavaScript
on the page. With XSS and localStorage the attacker takes the token and uses it from their own machine
until it expires — and a stateless JWT can't be revoked without a denylist most people haven't built.
With XSS and an HttpOnly cookie they can act as the user while the page is open, which is bad, but it's
bounded in time and to my origin, and revoking the session ends it. Neither is XSS-proof; the cookie
bounds the blast radius.**

Pre-empt the objection your audience will raise. **People say stateless JWTs are the point. A JWT in an
HttpOnly cookie is still a JWT — my resource server still validates the signature statelessly. I changed
the transport, not the model. Bearer-token-in-localStorage is a tutorial default, not a security
decision.**

Then the consequence people forget. **Once I'm on cookies, `csrf().disable()` stops being free. Most
Spring API tutorials disable CSRF because they assumed a bearer token, so changing the transport means
revisiting that line. SameSite=Lax kills most of it but not all — it still allows top-level GETs, so
nothing state-changing goes on GET.**

Close on the race. **When the token expires with six requests in flight, all six get a 401 and all six
try to refresh. With rotation the first succeeds, the rest present an invalidated token, the server
reads that as theft and kills the session — users get logged out at random. The fix is single-flight:
one refresh, everyone awaits the same promise, and the failure path must complete every waiter. It's
`computeIfAbsent` with a shared future, single-threaded.**
