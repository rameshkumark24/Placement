# Part 1 — L-075 · Test doubles

## The vocabulary — five things, not one

Everyone says "mock" for all of these. Interviewers ask you to distinguish them.

| Double | What it is | Example |
|---|---|---|
| **Dummy** | Passed to satisfy a signature, never used | `new Order(null, …)` |
| **Stub** | Returns canned answers | "`findById` always returns Alice" |
| **Spy** | A **real object** that records calls (or partially stubs) | a real list you also verify |
| **Mock** | Programmed with **expectations**; you verify interactions | "assert `send()` was called once" |
| **Fake** | A working lightweight implementation | in-memory repository, H2 database |

The distinction that matters most in practice is **stub versus mock**: a stub supports
**state-based** testing ("after this, the balance is 50"), while a mock supports
**interaction-based** testing ("`debit()` was called with 50"). State-based assertions are more
robust because they survive refactoring; interaction assertions break when you change *how* the code
achieves the same result.

> **Prefer asserting on outcomes. Verify interactions only when the interaction *is* the outcome** —
> sending an email, publishing an event, charging a card.

**Fakes are undervalued.** An in-memory repository written once is reusable, exercises real logic,
and produces tests that read like the domain rather than like a script of stubbing calls.

## The API

```java
@ExtendWith(MockitoExtension.class)          // JUnit 5 integration; strict stubs by default
class OrderServiceTest {

    @Mock  PaymentGateway gateway;
    @Mock  OrderRepository repo;
    @InjectMocks OrderService service;        // constructor injection of the two mocks

    @Test
    void chargesTheCustomerAndSavesTheOrder() {
        // STUB
        when(gateway.charge(any(), eq(Money.of(100)))).thenReturn(Receipt.ok("R-1"));
        when(repo.save(any())).thenAnswer(inv -> inv.getArgument(0));

        Order result = service.place(customer, Money.of(100));

        // ASSERT STATE first
        assertEquals("R-1", result.receiptId());
        assertEquals(Status.PAID, result.status());

        // VERIFY INTERACTION only where the interaction is the point
        verify(gateway).charge(customer, Money.of(100));
        verify(repo).save(argThat(o -> o.status() == Status.PAID));
        verifyNoMoreInteractions(gateway);
    }
}
```

The stubbing vocabulary:

```java
when(m.get(1)).thenReturn("a");
when(m.get(1)).thenReturn("a", "b", "c");        // consecutive calls
when(m.get(2)).thenThrow(new NotFoundException());
when(m.get(3)).thenAnswer(inv -> "computed-" + inv.getArgument(0));

doThrow(new IOException()).when(m).close();       // ← void methods need doXxx
doNothing().when(m).close();
doReturn("x").when(spy).method();                 // ← for spies. See the warning below.
```

Argument matchers:

```java
verify(m).save(any(Order.class));
verify(m).find(eq("A-1"));
verify(m).find(argThat(id -> id.startsWith("A")));
verify(m).count(anyInt());
verify(m, times(2)).ping();
verify(m, never()).delete(any());
verify(m, atLeastOnce()).log(any());
verify(m, timeout(500)).asyncCall();               // for async work
```

**The matcher rule that trips everyone up: if you use one matcher for an argument, you must use
matchers for *all* arguments.** `verify(m).find(eq("A-1"), anyInt())` — not `find("A-1", anyInt())`.
Mixing them throws `InvalidUseOfMatchersException`, and the message is confusing because the failure
often surfaces on the *next* test.

## `ArgumentCaptor` — inspecting what was passed

```java
@Captor ArgumentCaptor<Order> captor;

service.place(customer, Money.of(100));

verify(repo).save(captor.capture());
Order saved = captor.getValue();
assertEquals(Status.PAID, saved.status());
assertEquals(customer.id(), saved.customerId());
```

Use a captor when you need to assert several things about an argument, or when the object is built
inside the method under test and you have no other handle on it. For a single simple condition,
`argThat` is shorter — but its failure message is much worse ("wanted but not invoked"), so a captor
is usually kinder to your future self.

`captor.getAllValues()` gives every call in order, which is how you assert on a sequence.

## Spies — powerful and mostly a warning sign

```java
List<String> real = new ArrayList<>();
List<String> spy = spy(real);

spy.add("one");                  // REALLY adds
verify(spy).add("one");
assertEquals(1, spy.size());

when(spy.size()).thenReturn(100);   // 💀 calls the REAL size() while stubbing
doReturn(100).when(spy).size();     // ✅ correct form for a spy
```

That `when(...)` gotcha is worth internalising: with a spy, `when(spy.method())` **actually invokes
the method** in order to evaluate the argument, which can have side effects or throw. Always use
`doReturn(...).when(spy).method()` for spies.

A `@Spy` on your own class with some methods stubbed is a **partial mock**, and it almost always
means the class has two responsibilities that want separating (Day 090's SRP, ahead of you in Stage
2). Treat it as a design signal.

## Strict stubs

`MockitoExtension` defaults to `Strictness.STRICT_STUBS`, which fails the test on:

- **Unnecessary stubbing** — you stubbed something the code never called. Usually means the test is
  stale or you misunderstood the flow.
- **Argument mismatch** — you stubbed `find("A")` and the code called `find("B")`, so it silently got
  `null`. Under lenient mode this produces a baffling NPE far from the cause.

Both catch real bugs. `@MockitoSettings(strictness = Strictness.LENIENT)` exists; needing it usually
means the test is doing too much.

## What you cannot mock (and what that tells you)

Mockito cannot mock `static` methods, constructors, `final` classes/methods, or `private` methods —
not without the inline mock maker or PowerMock.

**These limitations are information.** Code that needs static mocking is code with a hidden hard
dependency:

```java
// 💀 untestable — the clock is baked in
if (LocalDate.now().isAfter(order.dueDate())) { … }

// ✅ testable — the dependency is explicit (and Day 042A gave you Clock)
private final Clock clock;
if (LocalDate.now(clock).isAfter(order.dueDate())) { … }
// test: Clock.fixed(Instant.parse("2026-08-14T00:00:00Z"), ZoneOffset.UTC)
```

`Clock` injection is the canonical example and one of the most useful habits in this whole block:
**time is a dependency**. Any test involving expiry, scheduling, or "older than 30 days" is either
trivially deterministic or hopelessly flaky depending on this one decision.

`mockStatic` exists in `mockito-inline` for genuinely unavoidable cases (a legacy static utility you
cannot change). Reach for it last, and scope it in a try-with-resources so the static stub does not
leak into other tests.

# Part 2 — When mocking is a smell

## The four signals

**1. More than three mocks in one test.**
The class under test has too many collaborators. That is Day 090's Single Responsibility Principle
failing, and the test is the first place it becomes visible. Split the class.

**2. Mocking a value object.**
`when(money.getAmount()).thenReturn(100)` — just build a real `Money`. Value objects are cheap,
immutable and have no dependencies. Mocking them makes the test lie about what the real object does.

**3. Mocks returning mocks.**
```java
when(repo.find(id)).thenReturn(order);
when(order.customer()).thenReturn(customer);
when(customer.address()).thenReturn(address);
```
This is a Law of Demeter violation (Day 092) reflected in the test. The code is reaching through
three objects; fix the code, not the test. `RETURNS_DEEP_STUBS` exists to paper over this and should
be read as an alarm.

**4. The test mirrors the implementation line by line.**
If every statement in the method has a corresponding `verify`, the test asserts *how* rather than
*what*. Any refactoring breaks it even though behaviour is unchanged — so the test now **prevents**
the improvement it was supposed to enable. This is the most expensive failure mode, because such
tests are usually deleted rather than fixed.

## What to mock, and what never to

| Mock | Do not mock |
|---|---|
| External services (HTTP, payment gateways) | Value objects, records, enums |
| Things that are slow (network, real DB) | Collections and JDK types |
| Things that are non-deterministic (clock, random, UUID) | The class under test |
| Things with side effects (email, SMS, queue publish) | Types you do not own — wrap them first |
| Failure paths that are hard to trigger otherwise | Simple data holders |

**"Do not mock types you do not own"** deserves expansion, since it is a well-known rule and a
frequent interview follow-up. When you mock `AmazonS3` or a driver class, your stub encodes *your
belief* about how that library behaves. If the belief is wrong — or a version changes it — your tests
still pass and production still breaks. Instead, wrap it in your own narrow interface
(`FileStore.put(key, bytes)`), mock that, and verify the real adapter with one integration test.

## The alternatives, in order of preference

**1. A real object.** Fastest and most honest when it is cheap to construct.

**2. A fake.** An in-memory implementation of your repository interface. Written once, used
everywhere, exercises real logic, and reads far better than a wall of `when(...)`.

```java
class InMemoryOrderRepo implements OrderRepository {
    private final Map<String, Order> store = new ConcurrentHashMap<>();
    public Order save(Order o) { store.put(o.id(), o); return o; }
    public Optional<Order> findById(String id) { return Optional.ofNullable(store.get(id)); }
}
```

**3. Testcontainers** — a real PostgreSQL, Redis or Kafka in Docker for integration tests. Slower,
but it tests your *actual* SQL against the *actual* engine, which no mock can. (Stage 5 uses this
heavily.)

**4. WireMock** for HTTP, so you test real serialization, real status codes and real timeouts against
a stub server rather than mocking your HTTP client.

**5. Mockito** — for the remainder.

## Where mocks are genuinely the right tool

Do not over-correct. Mocks are the correct choice for:

- **Failure injection**: "what does the service do when the gateway throws a timeout?" Triggering
  that against a real system is impractical.
- **Verifying a side effect that leaves the system**: an email sent, an event published, an audit
  record written.
- **Isolating slow or costly collaborators** in a fast unit test.

## Code to type

```java
import org.junit.jupiter.api.*;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.*;
import org.mockito.junit.jupiter.MockitoExtension;
import java.time.*;
import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)
class SubscriptionServiceTest {

    interface Mailer { void send(String to, String subject); }
    interface SubRepo { Subscription find(String id); Subscription save(Subscription s); }
    record Subscription(String id, String email, LocalDate expiresOn, boolean notified) {}

    @Mock Mailer mailer;
    @Mock SubRepo repo;
    @Captor ArgumentCaptor<String> subjectCaptor;

    Clock clock = Clock.fixed(Instant.parse("2026-08-14T00:00:00Z"), ZoneOffset.UTC);

    @Test
    void notifiesWhenExpiringWithinSevenDays() {
        var sub = new Subscription("S-1", "a@b.com", LocalDate.of(2026, 8, 18), false);
        when(repo.find("S-1")).thenReturn(sub);
        when(repo.save(any())).thenAnswer(inv -> inv.getArgument(0));

        var service = new SubscriptionService(repo, mailer, clock);
        Subscription result = service.checkExpiry("S-1");

        assertTrue(result.notified());                              // STATE
        verify(mailer).send(eq("a@b.com"), subjectCaptor.capture()); // INTERACTION (leaves the system)
        assertTrue(subjectCaptor.getValue().contains("4 days"));
    }

    @Test
    void doesNotNotifyTwice() {
        when(repo.find("S-1")).thenReturn(
                new Subscription("S-1", "a@b.com", LocalDate.of(2026, 8, 18), true));

        new SubscriptionService(repo, mailer, clock).checkExpiry("S-1");

        verify(mailer, never()).send(any(), any());
        verify(repo, never()).save(any());
    }

    @Test
    void surfacesMailerFailure() {
        when(repo.find("S-1")).thenReturn(
                new Subscription("S-1", "a@b.com", LocalDate.of(2026, 8, 18), false));
        doThrow(new RuntimeException("smtp down")).when(mailer).send(any(), any());

        var service = new SubscriptionService(repo, mailer, clock);
        assertThrows(NotificationException.class, () -> service.checkExpiry("S-1"));
        verify(repo, never()).save(any());        // ← not marked notified. The real assertion.
    }
}
```

Write `SubscriptionService` to make these pass. Three things this exercises deliberately: the
**fixed `Clock`** makes "4 days" deterministic forever; the **failure-injection test** is the case
mocks genuinely earn their place; and the last `verify(repo, never())` asserts the *invariant* — a
failed notification must not mark the subscription notified — which is exactly the kind of bug that
reaches production.

Then rewrite the whole class using an `InMemorySubRepo` fake instead of `@Mock SubRepo` and compare
which reads better.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Mixing raw values and matchers | `InvalidUseOfMatchersException`, often in the *next* test |
| `when(spy.m())` instead of `doReturn().when(spy).m()` | The real method actually runs |
| Mocking value objects | The test lies about real behaviour |
| Mocks returning mocks | Demeter violation hidden by the test |
| A `verify` per implementation line | Refactoring breaks passing tests |
| Six mocks in one test | The class has too many responsibilities |
| Mocking types you do not own | Your assumptions, not the library's behaviour |
| `LocalDate.now()` in business logic | Untestable or flaky; inject a `Clock` |
| Lenient strictness to silence warnings | Hides stale stubs and argument mismatches |
| `verifyNoMoreInteractions` everywhere | Brittle; every new call breaks unrelated tests |

## Interview questions

**Q: Difference between a mock, a stub, a spy and a fake?**
A stub returns canned data for state-based assertions; a mock is verified for interactions; a spy
wraps a real object and records (or partially stubs) calls; a fake is a working lightweight
implementation. Prefer stubs and fakes; verify interactions only when the interaction is the
observable outcome.

**Q: When is mocking a smell?**
More than about three mocks, mocking value objects, mocks returning mocks, or a test that mirrors the
implementation. Each points at a design problem: too many responsibilities, unnecessary indirection,
a Demeter violation, or testing *how* rather than *what*.

**Q: Why should you not mock types you do not own?**
Your mock encodes your assumption about the library. If the assumption is wrong, tests pass and
production fails. Wrap the library in your own interface, mock that, and integration-test the
adapter.

**Q: How do you test time-dependent logic?**
Inject a `Clock` and use `Clock.fixed` in tests. `LocalDate.now()` inline is either untestable or
flaky.

**Q: What is strict stubbing?**
Mockito fails the test on unused stubs and argument mismatches, which catch stale tests and silent
`null` returns respectively.

**Q: How do you test what an object was called *with*?**
`ArgumentCaptor` — capture in the `verify`, then assert on the captured value. Better failure
messages than `argThat` when several properties matter.

# 🚪 Exit questions

2. State the rule for when to verify an interaction rather than assert on state.
3. What is the matcher rule, and what is its confusing failure mode?
4. Why is `when(spy.m())` wrong, and what replaces it?
5. When is `ArgumentCaptor` better than `argThat`?

7. Why must you not mock types you do not own? What do you do instead?
8. Why is a partial mock a design signal?
9. What two bug classes does strict stubbing catch?
10. What does Mockito's inability to mock statics tell you about the code?
11. Why is `Clock` injection a testing decision *and* a design decision?
12. List the alternatives to mocking in preference order.

## 🎙️ Articulation drill

Two minutes: **"When do you use a mock, and when is reaching for one telling you something?"**

Lead with the outcomes-over-interactions rule, then the four smells with the design problem each
points at, then the preference ladder — real object, fake, Testcontainers, WireMock, mock. Finish by
naming where mocks genuinely win: failure injection and side effects that leave the system. That
balance is the answer; pure anti-mock zeal is as unconvincing as mocking everything.
