# Part 1 — L-074 · JUnit 5

## The architecture, and why it matters

JUnit 5 is not one library. It is three:

```
junit-jupiter-api        ← what you write against (@Test, Assertions)
junit-jupiter-engine     ← runs Jupiter tests            (runtime scope)
junit-platform-launcher  ← the platform IDEs and build tools drive
junit-vintage-engine     ← runs JUnit 4 tests on the same platform
```

The split exists so the *platform* can run any test engine — Jupiter, Vintage, Spock, Cucumber — and
so a JUnit 4 codebase can migrate one test at a time rather than all at once. That is the practical
answer to "how would you migrate off JUnit 4?"

```xml
<dependency>
  <groupId>org.junit.jupiter</groupId><artifactId>junit-jupiter</artifactId>
  <scope>test</scope>          <!-- ← test scope. Day 073. -->
</dependency>
```

## Anatomy of a good test

```java
class OrderServiceTest {

    @Test
    @DisplayName("rejects an order whose total exceeds the customer's credit limit")
    void rejectsOverLimitOrder() {
        // ARRANGE
        Customer customer = new Customer("C-1", Money.of(1000));
        OrderService service = new OrderService(new InMemoryRepo());

        // ACT
        Executable act = () -> service.place(customer, Money.of(1500));

        // ASSERT
        InsufficientCreditException e = assertThrows(InsufficientCreditException.class, act);
        assertEquals(Money.of(500), e.getShortfall());
    }
}
```

Three properties to insist on:

**The name is a sentence about behaviour.** `rejectsOverLimitOrder` and the `@DisplayName` tell you
what broke without opening the file. `testOrder1` tells you nothing — and a failing test's *name* is
the first thing you read at 2 AM in CI output.

**Arrange–Act–Assert, visibly separated.** If you cannot draw the line between the three, the test
is doing too much.

**One behaviour per test.** Not one assertion — one *behaviour*. Several assertions about the same
outcome are fine; two unrelated scenarios are two tests, because the first failure hides the second.

Note there is **no `public`** on classes or methods. Jupiter uses reflection (Day 056A) and does not
require it.

## Assertions

```java
assertEquals(expected, actual);              // ← order matters for the failure message
assertEquals(expected, actual, "context");
assertNotEquals(a, b);
assertTrue(cond, () -> "lazy message: " + expensive());
assertNull(x); assertNotNull(x);
assertSame(a, b);                            // reference identity — Day 040
assertArrayEquals(e, a);
assertIterableEquals(e, a);
assertThrows(Type.class, executable);        // returns the exception — assert on it
assertDoesNotThrow(executable);
assertTimeout(Duration.ofMillis(100), executable);
assertTimeoutPreemptively(Duration.ofMillis(100), executable);   // aborts; separate thread

assertAll("order",                            // ← reports ALL failures, not just the first
    () -> assertEquals("C-1", order.customerId()),
    () -> assertEquals(2, order.lines().size()),
    () -> assertTrue(order.total().isPositive()));
```

**`assertAll` is the one people miss.** Without it, the first failed assertion aborts the test and
you fix one thing, re-run, discover the next — three round trips. With it you see all three at once.

`assertThrows` **returns** the exception, so assert on its message or fields rather than merely its
type. And note `assertTimeoutPreemptively` runs the code on another thread, which breaks anything
`ThreadLocal`-based (Day 066A) — including Spring's transaction management.

Most teams then adopt AssertJ for readability:

```java
assertThat(order.lines()).hasSize(2)
    .extracting(Line::sku).containsExactly("A-1", "B-2");
assertThat(total).isEqualByComparingTo("1500.00");
```

Fluent, better failure messages, and far better collection assertions. Worth knowing it exists and
why teams choose it.

## Lifecycle

```java
class LifecycleTest {
    @BeforeAll  static void once()        { }   // static, unless @TestInstance(PER_CLASS)
    @BeforeEach void beforeEveryTest()    { }
    @AfterEach  void afterEveryTest()     { }
    @AfterAll   static void onceAtEnd()   { }
}
```

Order per test: `@BeforeAll` → (`@BeforeEach` → `@Test` → `@AfterEach`)* → `@AfterAll`.

**A new test-class instance is created for every test method by default.** This is deliberate: it
guarantees no state leaks between tests, so instance fields start fresh. `@TestInstance(PER_CLASS)`
changes it and lets `@BeforeAll` be non-static — convenient, and a way to reintroduce inter-test
coupling, so use it sparingly.

**Tests must not depend on execution order.** Order is deterministic but unspecified. A test that
only passes after another has run is a broken test — and `@Order`/`@TestMethodOrder` exists mainly
for reporting, not for building dependencies.

```java
@Disabled("flaky — see JIRA-4471")   // ← always give a reason
@Tag("slow")                          // filter: mvn test -Dgroups=slow
@Nested class WhenCustomerIsNew { }   // group related tests, share setup
@RepeatedTest(10)                     // useful for smoking out concurrency flakiness
@Timeout(5)
```

`@Nested` is genuinely useful: an inner class gets its own `@BeforeEach`, so you can express
"given a new customer… / given a returning customer…" as structure rather than as prefixes on
method names.

## Parameterized tests — the highest-value feature

```java
@ParameterizedTest
@ValueSource(strings = {"", " ", "\t", "\n"})
void rejectsBlankNames(String name) {
    assertThrows(IllegalArgumentException.class, () -> new Customer(name));
}

@ParameterizedTest(name = "{0} + {1} = {2}")
@CsvSource({ "1, 1, 2", "2, 3, 5", "-1, 1, 0", "0, 0, 0" })
void adds(int a, int b, int expected) {
    assertEquals(expected, Calculator.add(a, b));
}

@ParameterizedTest
@MethodSource("orderCases")
void computesTotal(Order order, Money expected) {
    assertEquals(expected, order.total());
}
static Stream<Arguments> orderCases() {
    return Stream.of(
        arguments(orderOf(1, "10.00"), Money.of("10.00")),
        arguments(orderOf(3, "10.00"), Money.of("30.00")));
}

@ParameterizedTest
@EnumSource(Status.class)
void everyStatusHasALabel(Status s) { assertNotNull(s.label()); }

@ParameterizedTest
@NullAndEmptySource @ValueSource(strings = {"  "})
void rejectsMissing(String v) { assertThrows(IllegalArgumentException.class, () -> parse(v)); }
```

Each case is reported as a **separate test** with its own name, so a failure tells you *which input*
broke. That is the difference from a loop inside one test, where the first failure hides the rest and
the message says nothing.

`@MethodSource` is the one to reach for when arguments are objects rather than literals.

## What to test, and what not to

| Test | Do not test |
|---|---|
| Business rules and edge cases | Getters and setters |
| Boundaries: 0, 1, n, max, negative | The framework's own behaviour |
| Error paths and exception messages | Private methods **directly** |
| Every bug you fix (a regression test) | Implementation details |
| Concurrency invariants where feasible | Third-party libraries |

**Private methods are tested through the public API.** If a private method is complex enough to
demand its own test, that is a signal it wants to be a separate class with its own public behaviour —
the test is telling you about the design.

**Coverage is a diagnostic, not a target.** 100% coverage with no assertions proves nothing;
uncovered `catch` blocks are a genuine finding. Use JaCoCo to *find gaps*, never as a number to hit —
mandating 90% coverage reliably produces tests written to touch lines rather than to verify
behaviour.

## Test naming and structure at scale

```java
@Test void transfer_movesMoneyBetweenAccounts() { }
@Test void transfer_throwsWhenSourceHasInsufficientFunds() { }
@Test void transfer_isAtomicWhenTheTargetRejects() { }
```

`method_condition_expectedResult` scales; pick one convention and hold it. In CI output you will
read hundreds of these names and never open the files.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Tests that depend on execution order | Passes locally, fails in CI |
| Shared mutable state between tests | Flakiness that wastes days |
| Testing getters to raise coverage | Effort with no signal |
| One test asserting five behaviours | The first failure hides the rest |
| `assertEquals(actual, expected)` reversed | "expected X but was Y" reads backwards |
| A loop instead of `@ParameterizedTest` | You lose which input failed |
| `@Disabled` with no reason | Dead tests nobody dares delete |
| Coverage as a target | Tests written to touch lines |
| `Thread.sleep` in tests | Slow and flaky — use awaitility or latches |
| Testing private methods by reflection | Locks in the implementation |
| `assertTimeoutPreemptively` with `ThreadLocal` code | Breaks Spring TX and MDC |

## Interview questions

**Q: What makes a good unit test?**
Fast, isolated, deterministic, and named for the behaviour it verifies. Arrange–act–assert, one
behaviour, no shared state, no ordering dependency, and a failure message that identifies the
problem without opening the file.

**Q: JUnit 5 vs 4?**
Modular (API/engine/platform), so engines are pluggable and JUnit 4 tests run via Vintage. Plus
`@ParameterizedTest`, `@Nested`, `assertAll`, `assertThrows`, lambda-based lazy messages, and
extensions replacing runners and rules — which removes JUnit 4's one-runner-at-a-time limitation.

**Q: Why a new test instance per method?**
To guarantee no state leaks between tests. `@TestInstance(PER_CLASS)` opts out.

**Q: When do you use a parameterized test?**
When the same behaviour is verified across many inputs — each case is reported separately, so a
failure names the input.

**Q: Should you test private methods?**
Not directly. Test them through the public API; if one is complex enough to need its own test, it
should probably be its own class.

**Q: What is your view on code coverage?**
A tool for finding untested paths, not a target. High coverage with weak assertions is worse than
honest lower coverage, because it creates false confidence.

## 🎙️ Articulation drill

Two minutes: **"How do you decide what to test?"**

Behaviour not implementation, boundaries and error paths, a regression test for every bug fixed, and
an explicit statement that coverage is a diagnostic. Then the flakiness rules — no shared state, no
ordering, no sleeps — because flaky tests destroy a suite's credibility faster than missing tests do.
