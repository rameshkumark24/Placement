# Day 375

**L-375** · Centralised logging — the most expensive signal

**Time:** 3 hrs · **Mode:** NEW

> **⭐ You cannot `ssh` into forty pods, and by the time you want the logs the pod is gone.**
>
> But logs are also the signal whose cost scales linearly with traffic, so the interesting questions
> are not "how do I collect them" — they are **what to keep, what to sample, what must never be
> written down, and how to find the twelve lines that matter among four billion.**

---

# Part 1 — ⭐ The pipeline

```
⭐ app ──stdout──► ⭐ COLLECTOR (Fluent Bit / Vector, one per node)
⭐                      │  ⭐ parse · enrich with pod/service/version · redact · batch
⭐                      ▼
⭐                ⭐ STORE (Loki / OpenSearch)  ──► query UI
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐⭐ **Applications write to stdout only** | ⭐⭐ 12-factor — **a log file inside a container is invisible and unrotated** (Day 364) |
| ⭐ The collector adds infrastructure context | ⭐ pod, node, namespace, **and the image version** |
| ⭐ **The collector redacts** | ⭐ a second line of defence for things that slipped through |
| ⭐ Buffering and backpressure | ⭐⭐ **a full log pipeline must never block the application** (Day 358A) |
| One collector per node | not a sidecar per pod — that is N× the overhead |

⚠️ **The application must never block on logging.** An async appender with a bounded queue that drops
by level under pressure (Day 318) is the correct configuration; **a blocking one turns a logging
outage into an application outage**, which is the worst possible trade.

# Part 2 — ⭐⭐ Structure, and the mandatory fields

```json
⭐ {"ts":"2026-08-15T09:14:22.481Z","level":"ERROR","logger":"c.a.OrderService",
⭐  "msg":"payment declined","service":"orders","version":"1.24.3","env":"prod",
⭐  "trace_id":"4bf92f...","span_id":"00f067...","order_id":"A-9931","user_id":"u_44821"}
```

| ⭐ Field | ⭐ Why mandatory |
|---|---|
| ⭐ `ts` (UTC, ISO-8601, millis) | ⭐ local time in logs makes correlation impossible |
| ⭐ `level`, `logger`, `msg` | the basics |
| ⭐⭐ **`trace_id`** | ⭐⭐ **the join key to traces and to every other service's logs** (Day 376) |
| ⭐ **`service`, `version`, `env`** | ⭐ **"is this only happening on the new version?" — answerable** |
| ⭐ Business identifiers | order id, tenant id — **how support finds one customer's request** |

> **⭐ Structured JSON is not about tidiness — it is about queryability.** `level=ERROR AND
> service=orders AND version=1.24.3` is a filter; **grepping free text for "declined" is archaeology.**
> And the moment logs are shipped somewhere central, **free text stops being searchable at any useful
> speed.**

⚠️ **Multi-line stack traces break naive collectors**, which ship each line as a separate record — so
one exception becomes forty useless entries. **Either configure multiline joining in the collector or,
better, log the stack trace as a single JSON field**, which is what a JSON encoder does by default.

⚠️ **And the MDC rule from Day 182 applies here with force: put the trace id in the MDC, and clear it
in a `finally`.** A pooled thread that keeps a previous request's MDC **attributes log lines to the
wrong request**, which is worse than having no correlation at all because it actively misleads.

# Part 3 — ⭐⭐ Cost, and the two storage philosophies

```
⭐ 1,000 requests/s × 5 log lines × 400 bytes = ⭐ 2 MB/s = ⭐⭐ ~170 GB/day = ~5 TB/month
⭐ ⇒ ⭐⭐ logs routinely cost more than the infrastructure they describe
```

| ⭐ Lever | ⭐ Effect |
|---|---|
| ⭐⭐ **INFO as the default, not DEBUG** | ⭐ the single biggest reduction |
| ⭐⭐ **Sample successful requests** | ⭐⭐ **keep 100% of errors, 1–10% of successes** — errors are what you read |
| ⭐ **Drop health checks and probes** | ⭐ otherwise probes are most of your volume |
| ⭐ Short retention, tiered | ⭐ 7 days hot, 30 days cold, archive to object storage |
| ⭐ **Do not log the whole request body** | one field, not a payload |
| Measure **log lines per request** | ⭐ a number teams never look at, and it is usually shocking |

## ⭐ Loki vs Elasticsearch — the real trade

| | ⭐ Loki | ⭐ Elasticsearch / OpenSearch |
|---|---|---|
| ⭐ **Indexes** | ⭐⭐ **only labels; the body is compressed chunks** | ⭐ the full text |
| ⭐ **Cost** | ⭐⭐ **much cheaper — often 5–10×** | expensive at volume |
| ⭐ **Query** | ⭐ fast *if* labels narrow it; **slow full scans otherwise** | ⭐⭐ fast arbitrary text search |
| ⭐ Cardinality | ⭐⭐ **labels have the same explosion risk as Prometheus** (Day 373) | high-cardinality fields are fine |
| Best for | ⭐ "show me this service's errors in this window" | ⭐ "find this string anywhere, last month" |

> **⭐ The decision rule: if you always know the service and the time window, Loki is dramatically
> cheaper. If you genuinely need arbitrary text search across everything, you pay for
> Elasticsearch.** Most teams believe they need the second and use the first pattern exclusively.

⚠️ **Loki's labels are not log fields.** Putting `user_id` in a label is the Prometheus cardinality
explosion again; **it belongs in the log line, where it is filtered at query time.** Labels are for
things with a handful of values: service, level, environment, namespace.

# Part 4 — ⭐⭐ What must never be logged, and dynamic levels

| ⭐ Never log | ⭐ Why |
|---|---|
| ⭐⭐ **Passwords, tokens, API keys, session ids** | ⭐⭐ a log store is read by more people than production is |
| ⭐ **Full card numbers, CVVs** | PCI — and there is no legitimate reason |
| ⭐ **Personal data** beyond an identifier | ⭐ GDPR: logs are personal data, with retention and erasure obligations |
| ⭐ Whole request/response bodies | ⭐ contains all of the above, unpredictably |
| Full stack traces at INFO | noise that hides real errors |

⚠️ **The GDPR angle is the one engineers miss: a log line containing an email address is personal
data**, subject to retention limits and erasure requests. **"We keep all logs for two years" is a
compliance position, not a technical default** — log an internal user id and join to the user store
when you need identity.

⚠️ **A leaked secret in a log is compromised** (Day 296). Redaction at the collector helps, **but the
fix is not logging it** — redaction is a safety net for what slips through, not the control.

## ⭐⭐ Dynamic log levels — the underused feature

```
⭐ POST /actuator/loggers/com.app.orders   {"configuredLevel":"DEBUG"}
⭐ ⇒ ⭐⭐ DEBUG for ONE package, at RUNTIME, ⭐ no restart, no redeploy
⭐ ⇒ ⭐ then set it back to null to inherit again
```

> **⭐ This is the answer to "we need DEBUG in production".** You do — occasionally, for one package,
> for five minutes. **Running DEBUG globally is what makes logs expensive**; turning it on for one
> logger during an investigation costs nothing and is Day 318's hierarchy paying off.

⚠️ **Secure the endpoint and set a timer.** An `/actuator/loggers` endpoint reachable from outside is
an information-disclosure and denial-of-service vector, **and DEBUG left on after an incident is a
bill nobody notices until the end of the month.**

## ⭐ Finding things

```
⭐ 1. ⭐ An alert fires (Day 374)  →  it links to a dashboard
⭐ 2. ⭐ The dashboard exemplar    →  ⭐ a trace_id for a slow or failed request
⭐ 3. ⭐⭐ Query logs by trace_id   →  ⭐⭐ EVERY line from EVERY service for that one request
⭐ 4. Widen: same service, same version, same window
```

**⭐ Step 3 is why the trace id is mandatory.** Without it you search by time and hope; **with it you
retrieve the exact request across six services in one query** — which is the whole reason the three
signals are worth correlating.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Log files inside containers | ⭐ invisible, unrotated, lost on restart |
| ⭐⭐ **A blocking log appender** | ⭐⭐ a logging outage becomes an application outage |
| ⭐ Unstructured free text | ⭐ unqueryable once centralised |
| ⭐⭐ **No trace id** | ⭐⭐ cross-service correlation is impossible |
| ⭐ MDC not cleared in `finally` | ⭐ lines attributed to the wrong request |
| ⭐ Multi-line stack traces unjoined | one exception becomes forty records |
| ⭐ Local time in timestamps | correlation across regions breaks |
| ⭐⭐ **DEBUG globally in production** | ⭐⭐ the single largest cost driver |
| ⭐ Logging health checks | probes dominate volume |
| ⭐ **No sampling of successes** | you pay full price for lines nobody reads |
| ⭐ High-cardinality Loki labels | the Prometheus explosion, again |
| ⭐⭐ **Secrets or PII in logs** | ⭐⭐ compromised, and a compliance problem |
| Unlimited retention | GDPR exposure and a large bill |
| ⭐ Not knowing log lines per request | the number nobody measures |

## Interview questions

**Q: What must be in every log line?**
Timestamp in UTC, level, logger, message — and then the fields that make it queryable: trace id,
service, version and environment, plus business identifiers like order id. The trace id is the one
that matters most, because it is the join key that retrieves every line from every service for a
single request. Without it you are searching by time and hoping.

**Q: Why is logging the most expensive signal?**
Because volume scales linearly with traffic. A thousand requests a second at five lines each is
roughly a hundred and seventy gigabytes a day, and logs routinely cost more than the infrastructure
they describe. The levers are INFO rather than DEBUG by default, sampling successful requests while
keeping all errors, dropping health checks, and short tiered retention. And I would measure log lines
per request, which is a number most teams have never looked at.

**Q: Loki or Elasticsearch?**
Loki if you always know the service and the time window, which in practice is how people search — it
only indexes labels and keeps the body as compressed chunks, so it is often five to ten times cheaper.
Elasticsearch if you genuinely need arbitrary text search across everything. The trap with Loki is
treating labels like log fields — putting a user id in a label is the Prometheus cardinality explosion
again; it belongs in the line and gets filtered at query time.

**Q: You need DEBUG logging in production. What do you do?**
Turn it on for one package at runtime through the loggers endpoint, for a few minutes, then set it
back. Running DEBUG globally is the single biggest cost driver and it buries the lines that matter.
The endpoint has to be secured and not externally reachable, and I would set a reminder to turn it
off, because DEBUG left on after an incident is a bill nobody notices until month end.

**Q: What must never be logged?**
Credentials, tokens, session ids, card data — a log store is readable by far more people than
production is, and a secret that reaches a log is compromised and must be rotated. Also personal data
beyond an identifier, because logs containing an email address are personal data subject to retention
limits and erasure requests. I log an internal user id and join to the user store when identity is
actually needed. Collector-side redaction is a safety net, not the control.

## Mini task

1. ⭐ Convert your application to **structured JSON logging** with all mandatory fields including
   `version`.
2. ⭐ **Measure log lines per request** and total bytes per day. **Extrapolate the monthly cost.**
3. ⭐ Turn on **DEBUG globally** for an hour and measure the volume increase. **That multiple is your
   argument.**
4. ⭐⭐ Use `/actuator/loggers` to enable DEBUG for **one package at runtime**, confirm it works, and
   set it back.
5. ⭐ Throw an exception and **confirm the stack trace arrives as one record**, not forty.
6. ⭐⭐ Remove the MDC `finally` clear, run under load with a pooled thread pool, and **reproduce log
   lines attributed to the wrong request.**
7. ⭐ Implement **sampling**: all errors, 5% of successes. Measure the reduction.
8. ⭐ Drop health-check logs and **measure what fraction of volume they were.**
9. ⭐ Put a `user_id` in a Loki **label** and watch the cardinality effect. Move it into the line.
10. ⭐⭐ Take a `trace_id` from a slow request and **retrieve every line from every service for it in
    one query.**
11. ⭐ Grep your log store for anything resembling a token or an email. **Whatever you find is the
    finding.**

## 🎙️ Articulation drill

**Two minutes:** *"Something failed for one customer twenty minutes ago. Find out what happened."*

**⭐ The path is the answer: find their request by order id or user id → take the `trace_id` from that
line → query every service's logs by that trace id → get the whole request's story across six
services in one query → then look at the trace itself for where the time went.**

**⭐ The marker is that the answer takes four steps and no guessing.** Someone whose answer involves
"search around that timestamp and see what looks relevant" **has described archaeology**, and the
difference between the two is one mandatory field.
