# Part 1 — Migrations as code

```
src/main/resources/db/migration/
├── V1__create_orders.sql
├── V2__add_status_index.sql
├── V3__add_customer_email.sql
└── V4__backfill_customer_email.sql
```

```sql
-- V3__add_customer_email.sql
alter table customers add column email varchar(320);
create unique index concurrently ix_customers_email on customers (lower(email));
```

Flyway runs pending migrations **at startup, before the application context finishes**, tracks them
in `flyway_schema_history`, and **verifies a checksum of every applied file**.

**⭐ The checksum is the most important feature and people fight it.** Editing an already-applied
migration fails startup with a validation error. That is correct: your database has the old version,
the file says something else, and Flyway cannot know which is true. **Never edit an applied migration
— write a new one.** `flyway repair` exists for genuine emergencies and is not a workflow.

## The rules

| Rule | Why |
|---|---|
| ⭐ **Never edit an applied migration** | checksum mismatch; environments diverge silently |
| **One logical change per file** | reviewable, and a failure has a clear cause |
| ⭐ **Version by timestamp** (`V20260814103000__`) | ⭐ two developers on branches both picking `V15` collide at merge. Timestamps never do |
| **Migrations are reviewed like code** | a migration is the highest-risk change in the repository |
| **Test the migration, not just the result** | run it against a copy of production-shaped data |
| **`validate` in the app** (Day 157) | entities and schema must agree, checked at startup |

## Repeatable migrations

```
R__order_summary_view.sql        -- ⭐ re-runs whenever its checksum changes
```

For views, functions and stored procedures — anything defined with `CREATE OR REPLACE`. They run
after versioned migrations, every time they change. This is genuinely useful: a view definition lives
in one file with a readable diff history, instead of accumulating as `V17__update_view`,
`V23__update_view_again`.

## Configuration worth setting

```yaml
spring.flyway:
  enabled: true
  locations: classpath:db/migration
  baseline-on-migrate: false        # ⭐ true only when adopting Flyway on an existing database
  out-of-order: false               # ⭐ false in production
  clean-disabled: true              # ⭐⭐ ALWAYS — `clean` drops every object in the schema
```

**`clean-disabled: true` is non-negotiable.** `flyway clean` drops everything in the schema. It exists
for development. Someone will eventually run it against the wrong `DATABASE_URL`, and Flyway made it
opt-in precisely because that happened enough times to matter.

## Flyway or Liquibase?

| | Flyway | Liquibase |
|---|---|---|
| Format | ⭐ plain SQL | XML/YAML/JSON/SQL |
| Rollback | manual (a new migration) | ⭐ automatic for many changes |
| Learning curve | ⭐ minimal — it is SQL | steeper abstraction |
| Database-specific SQL | ⭐ natural | fights the abstraction |

**Flyway unless you specifically need Liquibase's rollback support or database-agnostic changelogs.**
And note the honest caveat on rollback: automatic rollback cannot undo a dropped column's *data*, so
for the operations that actually scare you it does not help. Forward-only migration plus a tested
restore is the more reliable posture.

# Part 2 — ⭐ Migrations that lock, and the ones that take your service down

**A migration is not just correctness — it is a lock held on a live table.** Two properties decide
whether it is safe: how long it holds the lock, and how strong the lock is.

| Operation (PostgreSQL) | Lock | Safe on a live table? |
|---|---|---|
| `add column` (nullable, no default) | brief `ACCESS EXCLUSIVE` | ⭐ yes |
| `add column ... default X` | brief on PG 11+ | ✅ yes (rewrites the whole table on PG 10 and earlier) |
| `add column not null` (no default) | — | ❌ fails if rows exist |
| ⭐ `create index` | **blocks writes for the duration** | ❌ **use `create index concurrently`** |
| `alter column type` | full rewrite, `ACCESS EXCLUSIVE` | ❌ minutes of downtime on a large table |
| `add constraint ... check` | full scan | ❌ — use `not valid`, then `validate constraint` |
| `drop column` | brief (metadata only on PG) | ⚠️ safe technically, ❌ **breaks running instances** |
| `rename column` | brief | ❌❌ **breaks running instances instantly** |

### ⭐ `create index concurrently`

```sql
create index concurrently ix_orders_status on orders (status);
```

A plain `create index` on a 50-million-row table blocks every write for minutes. `concurrently` does
not — at the cost of two table scans and the possibility of leaving an **invalid index** if it fails,
which must then be dropped manually.

**The Flyway-specific gotcha:** `concurrently` cannot run inside a transaction, and Flyway wraps
migrations in one by default.

```sql
-- V7__add_status_index.sql
-- flyway:executeInTransaction=false      ⭐ required
create index concurrently if not exists ix_orders_status on orders (status);
```

Miss this and the migration fails with a cryptic transaction error at deploy time.

### The `not null` sequence, done safely

```sql
-- V8
alter table orders add column region varchar(10);                          -- nullable
-- V9  (batched, out of the deploy path for very large tables)
update orders set region = 'UNKNOWN' where region is null;
-- V10
alter table orders add constraint orders_region_nn check (region is not null) not valid;   -- ⭐ instant
-- V11
alter table orders validate constraint orders_region_nn;                   -- ⭐ scans, does not block writes
```

Four migrations instead of one `alter column set not null`, and no write outage.

# Part 3 — ⭐⭐ Expand/contract: renaming a column with zero downtime

**The core insight:** during a rolling deploy, **old and new application code run at the same time
against the same schema.** So the schema must be compatible with both, simultaneously. A rename is
not one change — it is a sequence of compatible changes across several deploys.

**Rename `orders.name` → `orders.customer_name`:**

```
┌── Deploy 1 — EXPAND ────────────────────────────────────────────────┐
│  V10: alter table orders add column customer_name varchar(255);     │
│  Code: WRITES BOTH columns. READS the old one.                      │
│  ⭐ Compatible with old instances, which know only `name`.          │
└─────────────────────────────────────────────────────────────────────┘
┌── Deploy 2 — BACKFILL ──────────────────────────────────────────────┐
│  V11: update orders set customer_name = name where customer_name    │
│       is null;   ⭐ batched — 10k rows at a time on a large table   │
│  Code: unchanged. Still writing both.                               │
└─────────────────────────────────────────────────────────────────────┘
┌── Deploy 3 — MIGRATE READS ─────────────────────────────────────────┐
│  Code: READS the new column. Still WRITES both.                     │
│  ⭐ Rollback is safe: the old column is still current.              │
└─────────────────────────────────────────────────────────────────────┘
┌── Deploy 4 — STOP WRITING THE OLD ──────────────────────────────────┐
│  Code: reads and writes ONLY customer_name.                         │
│  ⭐ WAIT HERE. Days, not minutes. `name` is now stale but present.  │
└─────────────────────────────────────────────────────────────────────┘
┌── Deploy 5 — CONTRACT ──────────────────────────────────────────────┐
│  V12: alter table orders drop column name;                          │
│  ⭐ Only after you are certain no rollback will need it.            │
└─────────────────────────────────────────────────────────────────────┘
```

**Five deploys to rename a column.** That is the honest cost of zero downtime, and stating it plainly
in an interview is a strong signal — most candidates say "rename it in a migration" and stop.

**⭐ Deploy 4's waiting period is the step people skip.** Its purpose is *rollback capability*: if
deploy 4 has a bug and you roll back to deploy 3, that code still reads `customer_name` — fine. But
if you have already dropped `name` and need to roll back further, you cannot. **The old column is your
rollback insurance and it is cheap to keep.**

**The same shape covers:**

| Change | Expand | Contract |
|---|---|---|
| Rename column | add new, write both | drop old |
| Change type | add new column of the new type, write both | drop old |
| Split a table | write to both | drop old |
| Drop a column | ⭐ **stop writing it first**, deploy, wait | then drop |
| Add `not null` | add nullable, backfill, `not valid` constraint, validate | — |

**Day 109's deprecation flow is the same algorithm.** Add the new thing, support both, migrate
consumers, wait, remove the old. Whether the consumer is a mobile client or a running instance of your
own application changes nothing about the shape.

## Two operational notes

**Migrations at startup vs as a separate step.** Flyway running in the application is convenient and
has two problems at scale: six instances starting simultaneously all attempt to migrate (Flyway takes
a lock, so it is safe, but five instances wait), and a long migration delays readiness past your probe
timeout (Day 143). **For large migrations, run them as a separate job before the deploy** —
`spring.flyway.enabled: false` in the app, migration as an init container or a pipeline step.

**Migration credentials should differ from application credentials.** The application user (Day 163b)
does not need DDL rights; the migration user does. Separating them means an injection flaw cannot
alter the schema.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| `ddl-auto: update` | unreviewable drift; no data migrations |
| Editing an applied migration | checksum failure; environments silently diverge |
| Sequential version numbers on branches | merge collisions |
| `create index` without `concurrently` | writes blocked for minutes |
| Forgetting `executeInTransaction=false` | concurrent index migration fails at deploy |
| `alter column type` on a large live table | full rewrite under an exclusive lock |
| Renaming a column in one deploy | running old instances break instantly |
| Dropping a column in the same deploy that stops using it | no rollback path |
| Unbatched backfill of 50M rows | one enormous transaction; locks and replication lag |
| `clean-disabled` not set | one wrong `DATABASE_URL` from an empty schema |
| Long migrations at application startup | readiness probe times out; deploy fails |
| Application user with DDL rights | injection escalates to schema damage |
| Trusting automatic rollback | cannot restore dropped data |

## Interview questions

**Q: Why not `ddl-auto: update`?**
It never drops or narrows anything, so the schema accumulates drift nobody reviewed, and it cannot
express a data migration. Flyway makes the schema an ordered, reviewed, checksummed sequence of SQL
files, and `ddl-auto: validate` then checks the entities agree at startup.

**Q: How do you rename a column with no downtime?**
Expand/contract, because during a rolling deploy old and new code run against the same schema. Add
the new column, write both, backfill in batches, switch reads, stop writing the old one, wait long
enough to preserve rollback, then drop it. Five deploys — and the wait before dropping is the step
people skip, because the old column is the rollback insurance.

**Q: What is dangerous about adding an index?**
A plain `create index` blocks writes for the duration, which on a large table is minutes of outage.
`create index concurrently` avoids it but cannot run in a transaction, so Flyway needs
`executeInTransaction=false`.

**Q: Should migrations run at application startup?**
Fine for small ones. For large ones, no — several instances contend, and a slow migration delays
readiness past the probe timeout and fails the deploy. Run it as a separate pipeline step or init
container, with credentials that have DDL rights the application user does not.

## Mini task

1. Set up Flyway with three migrations. Confirm `flyway_schema_history`.
2. Edit an applied migration. **Read the checksum failure.** Restore it and add a new one instead.
3. Create a 5-million-row table. Time a plain `create index` while running concurrent inserts —
   **watch the inserts block.** Then `concurrently` with `executeInTransaction=false`.
4. Try `alter column type` on that table and time it.
5. Do the full four-step `not null` sequence and confirm no write blocking.
6. **Execute the whole expand/contract rename**, running two application versions simultaneously at
   each step. Verify at every stage that both versions work.
7. At deploy step 4, roll back to step 3's code and confirm it still functions.
8. Backfill 5M rows in one statement, then in 10k batches. Compare lock duration and replication lag.
9. Set `spring.flyway.enabled: false` and run migrations from the CLI as a separate step.

## 🎙️ Articulation drill

Two minutes: **"How do you change a database schema safely?"**

Flyway as ordered, reviewed, checksummed SQL, with `ddl-auto: validate` checking the entities agree.
Then go straight to the interesting half: during a rolling deploy two versions of your code run
against one schema, so a rename is not one change but a sequence — expand, backfill, switch reads,
stop writing the old, wait, contract. Say "five deploys" out loud, and say why the wait exists: the
old column is your rollback path. Close on lock awareness — `create index concurrently`, batched
backfills, and long migrations run as a separate step so they do not fail the readiness probe.
