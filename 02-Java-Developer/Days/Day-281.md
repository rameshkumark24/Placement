# Day 281 🏗️

**P-281** · Test coverage and quality gates — making the suite mean something

**Time:** 3 hrs · **Mode:** BUILD

> Day 261 built the eight high-value test categories. **Today is the systematic pass: get coverage
> above 80% *in the places that matter*, and put gates in CI so it cannot regress.**
>
> **⭐ The trap of this day is optimising the number.** Coverage measures which lines ran, not which
> behaviours are protected — **so the work is to find the uncovered branches that represent real
> risk, and to ignore the ones that do not.**

---

# Part 1 — ⭐ Read the report correctly

```
⭐ JaCoCo with BRANCH coverage, not just line coverage
```

**⭐ Branch coverage is the number to look at.** A method with an `if` can be 100% line-covered by a
test that only exercises the true branch — **and the false branch is usually the guard.**

**⭐ Sort the report by *uncovered branches*, not by percentage, and triage:**

| ⭐ Must cover | ⭐ Legitimately exclude |
|---|---|
| ⭐ **Domain rules and every transition** | getters, `toString`, `equals` |
| ⭐ **Authorization paths** — especially the deny branches | `@Configuration` classes |
| ⭐ **Error handling** — every advice handler | generated code, DTO records |
| ⭐ **Concurrency guards** | trivial mappers |
| ⭐ **The outbox and job claim logic** | main methods |

```
⭐ Configure the exclusions explicitly in the JaCoCo config, not by wishing.
```

**⭐ Excluding DTOs and configuration typically moves a project from ~65% to ~85% without writing a
test** — which tells you something important about what the number means. **Do the exclusions first,
then look at what remains.**

## ⭐ The categories most likely to be uncovered right now

**⭐ Go and check each of these in your report:**

| Likely gap | Why it matters |
|---|---|
| ⭐ **`catch` blocks** | ⭐ the error path is what runs during an incident |
| ⭐ **Guard clauses that reject** | ⭐ the deny branch of every authorization check |
| ⭐ **Illegal state transitions** | Day 254 — a removed guard is not caught |
| ⭐ **Retry and fallback paths** | Day 181's circuit-breaker fallback |
| ⭐ **The dead-letter branch** | Day 263 — the path that handles permanent failure |
| Validation rejections | each `@Valid` failure shape |

**⭐ The `catch` blocks deserve emphasis.** They are the least-tested and most-important code in the
system: **they only execute when something has already gone wrong, and that is the worst time to
discover they are broken.**

# Part 2 — ⭐ Mutation testing — the honest measure

```
⭐ PIT (pitest) on the domain and service packages only
```

**⭐ Mutation testing changes your code — negates a condition, replaces a return, removes a call —
and checks whether a test fails.** It is the only tool that distinguishes *"this line ran"* from
*"this behaviour is protected"*.

**⭐ A surviving mutant is a hole.** Typical findings in a project at this stage:

| Surviving mutant | ⭐ What it reveals |
|---|---|
| ⭐ `>` changed to `>=` and no test failed | ⭐ the boundary is untested — your 2-hour cancellation rule |
| ⭐ A guard clause removed and no test failed | ⭐ the deny path has no assertion |
| A return value changed | you asserted the call, not the result |
| ⭐ A conditional negated | one branch has no test |

**⭐ Target a mutation score above 70% on the domain package.** Do not run it on the whole
application — it is slow, and the value is concentrated where the rules live.

**⭐ The boundary mutants are the most valuable finding**, because Day 249's acceptance criteria are
full of boundaries — "up to 2 hours before start", "between 1 and 100" — and **an off-by-one there is
a real business bug that line coverage happily reports as covered.**

# Part 3 — ⭐ The gates in CI

```
⭐ 1. Line coverage ≥ 80%, ⭐ branch coverage ≥ 70%    — ⭐ FAIL the build
⭐ 2. ⭐ Coverage must NOT DECREASE                     — ⭐ the more useful gate
⭐ 3. Mutation score ≥ 70% on domain                    — fail the build
⭐ 4. ArchUnit rules                                    — Day 253
⭐ 5. OpenAPI diff                                      — Day 251
⭐ 6. Dependency + secret scan                          — Day 253
⭐ 7. ⭐ Zero flaky tests: the suite runs twice          — see below
```

> **⭐ Gate 2 is more valuable than gate 1.** A fixed threshold gets gamed by excluding packages; a
> ratchet means every pull request must not make things worse, which is the property you actually
> want.

**⭐ Gate 7 is the one nobody adds.** Running the suite twice in CI catches order dependence and
timing flakiness before it erodes trust. **A flaky suite is worse than no suite**, because people
learn to re-run rather than investigate.

## ⭐ Static analysis — three tools, chosen for what they catch

| Tool | ⭐ Catches |
|---|---|
| ⭐ **SpotBugs + find-sec-bugs** | ⭐ `SQL_INJECTION_JPA`, hardcoded keys, weak crypto (Day 163b) |
| **Error Prone** | ⭐ real bugs at compile time — `equals` on different types, format mismatches |
| Checkstyle / Spotless | formatting — ⭐ **auto-fix, never fail the build on it** |

**⭐ Do not fail a build on formatting.** Auto-format on commit; a build that fails for a missing
space trains people to ignore build failures.

**⭐ Fix or explicitly suppress every SpotBugs finding**, with a comment saying why. **A suppression
file full of unexplained entries is worse than no tool.**

# Part 4 — ⭐ The tests that are still missing

**⭐ Work through this list against your project. Most projects at this stage are missing four or
five.**

```
⭐ 1.  ⭐ Every @RestControllerAdvice handler is triggered by a test
⭐ 2.  ⭐ Every circuit-breaker fallback executes in a test          (Day 181)
⭐ 3.  ⭐ Every retry path is exercised with a real failure          (Day 154)
⭐ 4.  ⭐ The dead-letter branch of the outbox                       (Day 263)
⭐ 5.  ⭐ Every job's failure path
⭐ 6.  ⭐ Boundary values: exactly at the limit, ±1                   (Day 249's ACs)
⭐ 7.  ⭐ Null and empty inputs at every boundary
⭐ 8.  ⭐ Concurrent access to every mutable shared thing            (Day 134)
⭐ 9.  ⭐ Startup: a missing required property fails                 (Day 142)
⭐ 10. ⭐ Migrations apply cleanly from EMPTY                        (Day 184)
```

**⭐ Item 10 runs automatically** if Day 253's Testcontainers setup is correct — **confirm it, because
it is a continuous test of the riskiest artefact in the repository.**

**⭐ Item 6 pairs with the mutation testing above.** If PIT survives a boundary mutant, item 6 is
missing for that rule.

## ⭐ Contract tests, if you have a frontend

```
⭐ swagger-request-validator: assert every response matches openapi.yaml
```

**⭐ Day 153's point: a specification is only a contract if something enforces it.** Otherwise it is
documentation that drifts, and Day 251's CI diff catches *deliberate* changes but not a response that
quietly omits a field.

## ⭐ Then re-measure the suite

```
⭐ Total time · domain-only time · ⭐ context count (Day 183)
```

**⭐ If the suite has grown past a few minutes, it is the context cache.** Turn on the cache DEBUG
logging, count the contexts, and collapse them onto the shared base class. **A slow suite gets run
less, which defeats the entire point of writing it.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Chasing the percentage | ⭐ 90% coverage with no deny-path assertions |
| Line coverage without branch coverage | guards report as covered |
| ⭐ Not excluding DTOs and config | you write pointless tests to move a number |
| ⭐ Excluding by wishing rather than configuration | the number is not reproducible |
| ⭐ **Uncovered `catch` blocks** | ⭐ the error path is broken exactly when needed |
| No mutation testing | ⭐ boundary bugs pass as "covered" |
| Running PIT on everything | slow; the value is in the domain |
| ⭐ A fixed threshold with no ratchet | gamed by exclusions |
| ⭐ No flaky-test gate | ⭐ trust in the suite erodes |
| Failing builds on formatting | people learn to ignore build failures |
| ⭐ Unexplained suppressions | worse than not running the tool |
| A slow suite | it stops being run |

## ⭐ Self-review

- [ ] ⭐ Branch coverage measured; ⭐ **exclusions configured explicitly**
- [ ] ⭐ Every `catch`, ⭐ **every deny branch**, every illegal transition covered
- [ ] ⭐ Line ≥ 80%, branch ≥ 70% — ⭐ **in the places that matter**
- [ ] ⭐ **PIT run on the domain**; ⭐ score > 70%; ⭐ **boundary mutants killed**
- [ ] ⭐ CI gates: coverage threshold, ⭐ **a ratchet**, mutation score, ArchUnit, OpenAPI, scans
- [ ] ⭐ **The suite runs twice in CI** — zero flakes
- [ ] SpotBugs + find-sec-bugs clean or explicitly suppressed **with reasons**
- [ ] ⭐ **All ten missing-test categories addressed**
- [ ] Contract tests validate responses against the specification
- [ ] ⭐ Suite time and context count re-measured

## 🎤 Defence questions

1. **⭐ What is your coverage, and why is that not the interesting question?**
2. **⭐ What does mutation testing tell you that coverage does not?**
3. **⭐ Show me a bug PIT found.**
4. **⭐ Why a coverage ratchet rather than a threshold?**
5. **⭐ Are your `catch` blocks tested?** (⭐ most projects' are not)
6. **⭐ How do you know you have no flaky tests?**
7. **⭐ What do you exclude from coverage, and why is that legitimate?**

## ✅ Done when

- ⭐ Coverage is above target **in the categories that matter**, with configured exclusions
- ⭐ **PIT found at least one real hole and you fixed it**
- ⭐ All seven CI gates are enforced and green
