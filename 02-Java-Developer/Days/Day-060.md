# Part 1 — L-060 · Collectors and parallelism

## `collect` — the general reduction

```java
<R, A> R collect(Collector<? super T, A, R> collector);
```

**A `Collector` has five parts**, and knowing them explains everything else:

| Part | Does |
|---|---|
| `supplier()` | Create a new result container |
| `accumulator()` | Fold one element into the container |
| `combiner()` | Merge two containers — **only used in parallel** |
| `finisher()` | Transform the container into the final result |
| `characteristics()` | `CONCURRENT`, `UNORDERED`, `IDENTITY_FINISH` |

```java
// toList(), written out
Collector.of(
    ArrayList::new,          // supplier
    List::add,               // accumulator
    (a, b) -> { a.addAll(b); return a; },   // combiner
    Collector.Characteristics.IDENTITY_FINISH);
```

**The combiner is why a mutable-accumulation `forEach` breaks in parallel** — collectors define how to
merge partial results; ad-hoc mutation doesn't.

## The collectors worth knowing

```java
// To collections
Collectors.toList()                  // modifiable
Collectors.toUnmodifiableList()
Collectors.toSet()
Collectors.toCollection(TreeSet::new)         // ← choose the implementation
Collectors.toMap(User::id, Function.identity())

// Strings
Collectors.joining()
Collectors.joining(", ")
Collectors.joining(", ", "[", "]")

// Numbers
Collectors.counting()
Collectors.summingInt(User::age)
Collectors.averagingDouble(Order::total)
Collectors.summarizingInt(User::age)          // all five stats

// Grouping — the important ones
Collectors.groupingBy(User::department)
Collectors.groupingBy(User::department, Collectors.counting())
Collectors.partitioningBy(u -> u.age() > 30)

// Reduction
Collectors.reducing(BigDecimal.ZERO, Order::total, BigDecimal::add)
Collectors.mapping(User::name, Collectors.toList())    // downstream transform
Collectors.filtering(u -> u.active(), Collectors.toList())   // Java 9
Collectors.flatMapping(u -> u.roles().stream(), Collectors.toSet())
Collectors.teeing(c1, c2, merger)             // Java 12 — TWO collectors, one pass
```

### `groupingBy` — and downstream collectors

**The second argument is the key idea.** It's a *downstream* collector applied to each group:

```java
Map<String, List<User>>    byDept = users.stream().collect(groupingBy(User::dept));
Map<String, Long>          counts = users.stream().collect(groupingBy(User::dept, counting()));
Map<String, List<String>>  names  = users.stream().collect(
        groupingBy(User::dept, mapping(User::name, toList())));
Map<String, Optional<User>> oldest = users.stream().collect(
        groupingBy(User::dept, maxBy(comparingInt(User::age))));

// Multi-level — a downstream groupingBy
Map<String, Map<Boolean, List<User>>> nested = users.stream().collect(
        groupingBy(User::dept, groupingBy(u -> u.age() > 30)));

// Choose the map implementation
Map<String, Long> sorted = users.stream().collect(
        groupingBy(User::dept, TreeMap::new, counting()));
```

**`groupingBy` with a downstream collector is the single most useful stream idiom**, and it's where
most people stop learning too early.

### `partitioningBy` vs `groupingBy`

```java
Map<Boolean, List<User>> parts = users.stream().collect(partitioningBy(u -> u.age() > 30));
parts.get(true); parts.get(false);       // BOTH keys always present, even if empty
```

**`partitioningBy` always returns both keys.** `groupingBy(u -> u.age() > 30)` gives a `Map<Boolean,
…>` too, but a key is absent if no element matched — so you'd need `getOrDefault`. Partitioning is
also slightly faster, using a specialised two-slot map.

### `toMap` — the duplicate-key trap

```java
users.stream().collect(toMap(User::dept, User::name));
// 💥 IllegalStateException: Duplicate key
```

**`toMap` throws on a duplicate key** unless you supply a merge function:

```java
toMap(User::dept, User::name, (a, b) -> a)                    // keep first
toMap(User::dept, User::name, (a, b) -> a + ", " + b)         // combine
toMap(User::dept, User::name, (a, b) -> a, TreeMap::new)      // and choose the map
```

**Also: `toMap` throws NPE on a null value**, unlike `HashMap.put`. Both are common surprises.

## Parallel streams — and their real cost

```java
list.parallelStream().filter(...).map(...).toList();
list.stream().parallel()...
```

**They use the common `ForkJoinPool`**, sized to `availableProcessors() - 1` by default.

### When parallel actually helps

**All of these must hold:**

| Condition | Why |
|---|---|
| **Large N** | Splitting and merging has fixed overhead — typically 10,000+ elements |
| **Expensive per-element work** | Cheap operations are dominated by coordination |
| **A splittable source** | `ArrayList` and arrays split well; `LinkedList` and `Stream.iterate` don't |
| **No shared mutable state** | Otherwise you have a race (Day 040) |
| **Stateless, side-effect-free lambdas** | Order of execution is unspecified |
| **Not already in a busy pool** | It shares the common pool with everything else |

### When it hurts — and this is the important half

**1. It shares one pool with your whole application.**

```java
list.parallelStream().map(this::callDatabase).toList();     // 💀
```

**A blocking operation in a parallel stream occupies a common-pool thread.** Every other parallel
stream in the JVM — including ones inside libraries — now starves. In a web application this can stall
unrelated requests.

**Never do blocking I/O in a parallel stream.** Use an `ExecutorService` you control (Day 069), or
`CompletableFuture`.

**2. Splitting cost depends heavily on the source.**

| Source | Splits |
|---|---|
| `ArrayList`, arrays, `IntStream.range` | **Excellently** — O(1) index split |
| `HashMap`, `HashSet` | Reasonably |
| `LinkedList` | **Badly** — must traverse to split |
| `Stream.iterate`, `BufferedReader.lines` | **Cannot split usefully** — inherently sequential |

**3. Ordering costs.**

`findFirst`, `limit` and `skip` must respect encounter order, which forces coordination. `findAny`
and `forEach` (unordered) are cheaper than `findFirst` and `forEachOrdered`.

**4. Boxing amplifies.** Use `IntStream.range().parallel()` rather than a boxed stream.

### The rule

> **Don't use `parallelStream()` unless you have measured that it helps.**

**And when you do, measure with JMH**, not `System.nanoTime` in a loop — Day 002's JIT warmup problem
applies doubly here.

```java
// ✅ a legitimate case: CPU-bound, large, splittable, no shared state
long count = IntStream.rangeClosed(2, 5_000_000)
                      .parallel()
                      .filter(MyMath::isPrime)
                      .count();
```

### The one that's always wrong

```java
List<String> results = new ArrayList<>();
list.parallelStream().forEach(results::add);      // 💀 RACE — ArrayList isn't thread-safe
```

**Use `collect`.** Collectors define a combiner precisely so parallel merging is safe.

## Type this yourself

```java
import java.util.*;
import java.util.stream.*;
import static java.util.stream.Collectors.*;

public class CollectorsDemo {
    record User(String name, String dept, int age, List<String> roles) { }

    static final List<User> USERS = List.of(
            new User("Ada", "Eng", 36, List.of("dev", "lead")),
            new User("Alan", "Eng", 41, List.of("dev")),
            new User("Grace", "Eng", 45, List.of("dev", "architect")),
            new User("Edsger", "Research", 52, List.of("scientist")),
            new User("Barbara", "Research", 29, List.of("scientist", "dev")));

    public static void main(String[] args) {

        System.out.println("--- groupingBy with downstream collectors ---");
        System.out.println("   plain:      " + USERS.stream()
                .collect(groupingBy(User::dept, counting())));
        System.out.println("   names:      " + USERS.stream()
                .collect(groupingBy(User::dept, mapping(User::name, toList()))));
        System.out.println("   avg age:    " + USERS.stream()
                .collect(groupingBy(User::dept, averagingInt(User::age))));
        System.out.println("   oldest:     " + USERS.stream()
                .collect(groupingBy(User::dept,
                        collectingAndThen(maxBy(Comparator.comparingInt(User::age)),
                                          o -> o.map(User::name).orElse("-")))));
        System.out.println("   all roles:  " + USERS.stream()
                .collect(groupingBy(User::dept, flatMapping(u -> u.roles().stream(), toSet()))));
        System.out.println("   sorted map: " + USERS.stream()
                .collect(groupingBy(User::dept, TreeMap::new, counting())));

        System.out.println("\n--- multi-level ---");
        Map<String, Map<Boolean, List<String>>> nested = USERS.stream()
                .collect(groupingBy(User::dept,
                         groupingBy(u -> u.age() > 40, mapping(User::name, toList()))));
        nested.forEach((d, m) -> System.out.println("   " + d + " → " + m));

        System.out.println("\n--- partitioningBy vs groupingBy ---");
        System.out.println("   partitioning: " + USERS.stream()
                .collect(partitioningBy(u -> u.age() > 100, counting())));
        System.out.println("   grouping:     " + USERS.stream()
                .collect(groupingBy(u -> u.age() > 100, counting())));
        System.out.println("   ↑ partitioning ALWAYS has both keys; grouping omits empty ones");

        System.out.println("\n--- toMap duplicate keys ---");
        try { USERS.stream().collect(toMap(User::dept, User::name)); }
        catch (IllegalStateException e) {
            System.out.println("   without a merge function: " + e.getMessage().split("\\(")[0].trim());
        }
        System.out.println("   with merge: " + USERS.stream()
                .collect(toMap(User::dept, User::name, (a, b) -> a + "/" + b)));

        System.out.println("\n--- joining, stats, teeing ---");
        System.out.println("   joined: " + USERS.stream().map(User::name).collect(joining(", ", "[", "]")));
        System.out.println("   stats:  " + USERS.stream().collect(summarizingInt(User::age)));
        var minMax = USERS.stream().collect(teeing(
                minBy(Comparator.comparingInt(User::age)),
                maxBy(Comparator.comparingInt(User::age)),
                (min, max) -> min.map(User::name).orElse("?") + " .. " + max.map(User::name).orElse("?")));
        System.out.println("   teeing (one pass): " + minMax);

        // ---- parallel: when it helps ----
        int n = 5_000_000;
        long start = System.currentTimeMillis();
        long seq = IntStream.rangeClosed(2, n).filter(CollectorsDemo::isPrime).count();
        long seqTime = System.currentTimeMillis() - start;

        start = System.currentTimeMillis();
        long par = IntStream.rangeClosed(2, n).parallel().filter(CollectorsDemo::isPrime).count();
        long parTime = System.currentTimeMillis() - start;

        System.out.printf("%n--- CPU-bound, %,d elements ---%n", n);
        System.out.printf("   sequential: %,5d ms%n", seqTime);
        System.out.printf("   parallel:   %,5d ms   (%.1f×)%n", parTime, (double) seqTime / parTime);
        System.out.println("   (primes: " + seq + " == " + par + ")");

        // ---- parallel: when it HURTS ----
        List<Integer> small = IntStream.rangeClosed(1, 1000).boxed().toList();
        start = System.nanoTime();
        for (int i = 0; i < 20_000; i++) small.stream().map(x -> x + 1).count();
        long smallSeq = System.nanoTime() - start;

        start = System.nanoTime();
        for (int i = 0; i < 20_000; i++) small.parallelStream().map(x -> x + 1).count();
        long smallPar = System.nanoTime() - start;

        System.out.println("\n--- small + cheap work ---");
        System.out.printf("   sequential: %,5d ms%n", smallSeq / 1_000_000);
        System.out.printf("   parallel:   %,5d ms   ← SLOWER%n", smallPar / 1_000_000);

        // ---- the race ----
        System.out.println("\n--- forEach into an ArrayList, in parallel ---");
        List<Integer> unsafe = new ArrayList<>();
        try {
            IntStream.range(0, 200_000).parallel().boxed().forEach(unsafe::add);
            System.out.println("   expected 200000, got " + unsafe.size() + "   ← may be wrong");
        } catch (Exception e) {
            System.out.println("   threw " + e.getClass().getSimpleName() + " — ArrayList isn't thread-safe");
        }
        List<Integer> safe = IntStream.range(0, 200_000).parallel().boxed().toList();
        System.out.println("   via collect: " + safe.size() + "   ← always correct");
    }

    static boolean isPrime(int n) {
        if (n < 2) return false;
        for (int i = 2; (long) i * i <= n; i++) if (n % i == 0) return false;
        return true;
    }
}
```

**Three results to record:**

1. **Parallel wins big** on CPU-bound work over 5 million elements.
2. **Parallel loses** on 1,000 elements with trivial work — the coordination dominates.
3. **`forEach` into an `ArrayList` in parallel gives a wrong count or throws.** `collect` is always
   correct.

# Part 2 — B-12 · File systems

## The inode

**A file's metadata lives in an inode; the name does not.**

```
   inode (a number, e.g. 12345)
   ├─ file type, permissions
   ├─ owner UID, group GID
   ├─ size
   ├─ timestamps (atime, mtime, ctime)
   ├─ link count
   └─ POINTERS TO DATA BLOCKS
        ├─ 12 direct pointers
        ├─ 1 single-indirect  → a block of pointers
        ├─ 1 double-indirect  → a block of blocks of pointers
        └─ 1 triple-indirect
```

**The indirection scheme is why small files are fast** — the first 12 blocks are reachable with no
extra reads — **while huge files remain possible**, at the cost of extra lookups.

**The filename is NOT in the inode.** A directory is a file whose contents are a list of
`(name → inode)` pairs. That single fact explains a lot:

| Behaviour | Because |
|---|---|
| **A hard link is free** | It's another directory entry pointing at the same inode; the link count increments |
| **Deleting doesn't free space if a link remains** | The file is removed when the link count *and* open-descriptor count reach zero |
| **You can delete an open file** | The name goes; the inode survives until the last descriptor closes |
| **Renaming is cheap** | Only the directory entry changes; no data moves |
| **You can't hard-link across filesystems** | Inode numbers are per-filesystem |

**"You can delete an open file" is a genuinely useful operational fact** — it's why deleting a log
file doesn't reclaim space until you restart the process holding it. A classic disk-full incident:
`df` shows full, `du` shows plenty free, and the answer is a deleted-but-open file.

**Symlinks are different** — a file whose contents are a *path*, resolved at access time. They can
cross filesystems and dangle.

## Journaling

**The problem:** a write involves several steps — allocate blocks, update the inode, update the
directory. **A crash between them leaves an inconsistent filesystem.**

**The fix:** write the intent to a journal first.

```
   1. Write the intended change to the JOURNAL
   2. Flush the journal
   3. Apply the change to the filesystem
   4. Mark the journal entry complete

   Crash after 2 → replay the journal on mount
   Crash before 2 → the change never happened; consistent either way
```

**Modes:**

| Mode | Journals | Trade-off |
|---|---|---|
| `writeback` | Metadata only, unordered | Fastest; data can be stale after a crash |
| `ordered` | Metadata, data written first | **The ext4 default** — good balance |
| `journal` | **Metadata and data** | Safest, roughly halves write throughput |

**Journaling is why `fsck` on a modern filesystem takes seconds rather than hours** — it replays a
log instead of scanning every inode.

## VFS — the Virtual File System

**A kernel abstraction layer presenting one interface over many filesystem implementations.**

```
   open() read() write() close()          ← the same syscalls always
            │
        ┌───▼───┐
        │  VFS  │
        └───┬───┘
    ┌───────┼───────┬────────┬─────────┐
  ext4    NTFS    tmpfs    procfs     NFS
```

**This is why `/proc/<pid>/status` can be read with `cat`** — procfs is a filesystem whose "files" are
generated by the kernel on read. Same for `/sys` and `/dev`.

**"Everything is a file" is implemented by VFS**, and it's the same layering principle as Day 001's
C-01.

## Durability — and where Java sits

**A `write()` returns after the data reaches the OS page cache, not the disk.**

```
   application → write() → PAGE CACHE → (later) → disk
                            ↑
                    a crash HERE loses the data
```

```java
FileOutputStream out = new FileOutputStream(f);
out.write(data);
out.flush();                       // flushes the JAVA buffer to the OS — NOT to disk
out.getFD().sync();                // ← fsync: forces the OS to write to the physical device
```

**`flush()` and `fsync()` are different things**, and conflating them is a real correctness bug:

- **`flush()`** pushes Java's `BufferedOutputStream` buffer into the OS
- **`sync()` / `force()`** asks the OS to persist to the device

**Databases call `fsync` on every commit** — it's the `D` in ACID (Day 117's D-13), and it's why
commit throughput is bounded by disk latency rather than CPU.

```java
FileChannel ch = FileChannel.open(path, WRITE);
ch.force(true);                    // fsync, including metadata
```

## Interview questions

**Q: What does `groupingBy` with a downstream collector do?**
> The downstream collector is applied to the elements of each group rather than collecting them into a
> list. So `groupingBy(User::dept, counting())` gives a count per department rather than a list per
> department. Downstream collectors compose — `mapping`, `filtering`, `flatMapping`, `maxBy`, and even
> another `groupingBy` for multi-level grouping.

**Q: `groupingBy` or `partitioningBy` for a boolean?**
> `partitioningBy` — it always returns both `true` and `false` keys even when one is empty, so you
> never need `getOrDefault`, and it uses a specialised two-slot map that's slightly faster. Grouping by
> a boolean omits a key entirely when nothing matches.

**Q: What goes wrong with `toMap`?**
> It throws `IllegalStateException` on a duplicate key unless you supply a merge function, and it
> throws `NullPointerException` on a null value, unlike `HashMap.put`. Both surprise people.

**Q: When should you use a parallel stream?**
> Only after measuring. It needs a large element count, genuinely expensive per-element work, a
> splittable source such as an array or `ArrayList`, and no shared mutable state. It's usually wrong
> for small collections or cheap operations, where coordination dominates.

**Q: Why is blocking I/O in a parallel stream dangerous?**
> Parallel streams share the common `ForkJoinPool` with the entire JVM. A blocking call occupies a
> common-pool thread, so every other parallel stream — including ones inside libraries — starves. In a
> server that can stall unrelated requests. Use an executor you control instead.

**Q: What is an inode, and why isn't the filename in it?**
> The inode holds a file's metadata and pointers to its data blocks. Names live in directories, which
> are files mapping names to inode numbers. That separation is why hard links are cheap, why renaming
> moves no data, why you can delete an open file — the inode survives until the last descriptor closes
> — and why disk space isn't reclaimed until then.

**Q: What does journaling protect against?**
> Filesystem inconsistency after a crash. A single logical operation involves several separate writes,
> so a crash between them could leave a corrupt structure. Writing the intent to a journal first means
> recovery replays or discards the entry, and it's why `fsck` takes seconds rather than hours.

**Q: What's the difference between `flush()` and `fsync()`?**
> `flush()` pushes the application's buffer into the operating system's page cache. `fsync` — via
> `getFD().sync()` or `FileChannel.force` — asks the OS to persist that data to the physical device.
> Data that is flushed but not synced is lost if the machine loses power, which is why databases fsync
> on every commit.
