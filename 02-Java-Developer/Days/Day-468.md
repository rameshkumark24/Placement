# Day 468

**L-468** · Project defence II — the decision log

**Time:** 3 hrs · **Mode:** NEW · **⭐ Project defence drills, 2 of 5**

> **⭐⭐ "Why did you use Postgres?" has exactly one bad answer, and it is "because I know it". The
> question is never about the technology — it is whether you chose or defaulted.**
>
> Today: the decision log as an artefact, **the three-part answer that survives every "why X?"**, the
> defaults you must be able to defend as defaults, and what to say when the honest answer is "I did not
> evaluate it".

---

# Part 1 — ⭐⭐ The three-part answer

```
⭐⭐ EVERY "why did you choose X?" IS ANSWERED IN THREE PARTS:
⭐   1. ⭐ THE FORCE      what the requirement actually demanded
⭐   2. ⭐⭐ THE REJECTED  what else you considered and ⭐⭐ WHY YOU DID NOT PICK IT
⭐   3. ⭐⭐ THE COST      ⭐⭐ what this choice costs you, stated voluntarily

⭐ ❌ "I used Postgres because it's reliable and I know it."
⭐ ✅ ⭐⭐ "The data is relational and the invariants matter — an order must not exist without
⭐      its line items, and I wanted that enforced by the database rather than by hope.
⭐      ⭐⭐ I considered Mongo, but I would have been reimplementing joins and transactions
⭐      in application code. ⭐⭐ The cost is that scaling writes means sharding eventually,
⭐      and I have a single primary today — I know where that ceiling is."
```

| ⭐⭐ Why part 3 matters more than part 1 | |
|---|---|
| ⭐⭐ **Naming the cost proves you evaluated rather than adopted** | ⭐⭐ anyone can list benefits |
| ⭐ It pre-empts the interviewer's next question | ⭐ and they were going to ask it |
| ⭐ It signals you know where the system breaks | ⭐⭐ which is Day 469's entire round |
| ⭐ Every choice has a cost | ⭐⭐ **a choice presented as pure upside reads as unexamined** |

# Part 2 — ⭐⭐ The decision log you should be able to produce

**⭐ Write this out for both projects. One row per decision. It is the single highest-value preparation
artefact in this stage.**

| ⭐ Decision | ⭐ The force | ⭐ Rejected, and why | ⭐⭐ The cost |
|---|---|---|---|
| ⭐ Postgres over Mongo | relational invariants, transactions | Mongo — joins in app code | single-primary write ceiling |
| ⭐ Monolith over microservices | one team, one deploy | microservices — Day 399's cost with no benefit yet | ⭐⭐ a shared deploy; boundaries must be enforced by discipline |
| ⭐⭐ **Outbox over publish-after-commit** | ⭐⭐ events were silently lost | 2PC — blocking, unavailable | ⭐⭐ ~1 s relay latency; a table to prune |
| ⭐ JWT with refresh rotation | stateless auth, revocation | sessions — server state | ⭐⭐ token revocation is not instant |
| ⭐ Redis read-through cache | p99 on a hot read path | in-process cache — inconsistent across tasks | ⭐⭐ a stampede risk on cold start (Day 388) |
| ⭐ ECS Fargate over EKS | small team, no platform engineers | EKS — control plane + ops | ⭐ less ecosystem; AWS lock-in |
| ⭐ Presigned S3 uploads | bytes must not cross the app | streaming through the API | ⭐⭐ cannot enforce size on a presigned PUT |
| ⭐ Flyway migrations as a job | ⭐ failure mode legibility | migrate at startup | ⭐ one more pipeline stage |
| ⭐ Single region | cost, and DNS failover is slow | multi-region active-active | ⭐⭐ a region outage is an outage |

```
⭐⭐ THE DRILL: cover the last two columns and answer from memory, out loud, in under 30 seconds each.
⭐   ⇒ ⭐⭐ Any row where you hesitate is a row the interviewer will find.
```

# Part 3 — ⭐ Defending a default as a default

```
⭐⭐ Not every choice was deliberated, and pretending otherwise is worse than admitting it.
⭐ ❌ inventing an evaluation you never did ⇒ ⭐⭐ collapses on the second follow-up
⭐ ✅ ⭐⭐ "Spring Boot was a default rather than a decision — it's what the ecosystem is,
⭐      and the cost of being different wasn't worth paying for this.
⭐      ⭐⭐ The choice I did make inside it was to keep the domain layer free of Spring
⭐      annotations, so the business rules are testable without a context." (Day 300)
⭐ ⇒ ⭐⭐ You have converted "I defaulted" into "I know which things deserve deliberation".
```

| ⭐ Legitimate defaults, and the reason each is fine | |
|---|---|
| ⭐ The language and framework | ⭐⭐ ecosystem gravity is a real engineering force |
| ⭐ The build tool | ⭐ zero differentiation |
| ⭐ The cloud provider | ⭐ usually whichever you have credits and experience for |
| ⭐⭐ **What must NOT be a default** | ⭐⭐ **the data model, the consistency choices, the failure behaviour, the boundaries** |

> **⭐ The distinction interviewers are actually probing: do you know which decisions matter?** A
> candidate who deliberated over Maven versus Gradle and defaulted on their consistency model **has their
> attention in exactly the wrong place** — and saying that out loud is itself a strong signal.

# Part 4 — ⭐⭐ The decisions most likely to be attacked

| ⭐ Attack | ⭐ What they are really testing |
|---|---|
| ⭐⭐ **"Why not microservices?"** | ⭐⭐ do you know the cost, or did you just not get there (Day 399) |
| ⭐⭐ **"Why not NoSQL / why NoSQL?"** | ⭐ can you name the access patterns that decided it (Day 331) |
| ⭐ "Why is this synchronous?" | ⭐⭐ availability multiplication (Day 398) |
| ⭐ "Why did you cache this?" | ⭐⭐ **did you measure before and after** (Day 266) |
| ⭐ "Why JWT and not sessions?" | ⭐ revocation, statelessness, and the honest trade |
| ⭐⭐ **"Why did you build X yourself?"** | ⭐⭐ judgement about buy-vs-build |
| ⭐ "Why this ORM / why raw SQL here?" | ⭐ N+1 awareness (Day 200-era) |
| ⭐⭐ **"What would you do differently?"** | ⭐⭐ **the highest-signal question in the round** |

```
⭐⭐ "WHAT WOULD YOU DO DIFFERENTLY?" — PREPARE THIS ONE PROPERLY.
⭐ ❌ "Nothing, I'm happy with it."            ⇒ ⭐⭐ reads as no reflection at all
⭐ ❌ "Everything, it's a mess."                ⇒ reads as no judgement
⭐ ✅ ⭐⭐ TWO items, one small and one structural, each with a REASON:
⭐    ⭐ small: "I'd have written the API contract before the entities — I let JPA shape the
⭐      public API and had to unpick it." (Day 251)
⭐    ⭐⭐ structural: "I'd have put the outbox in from the start rather than after finding
⭐      the bug, because I now treat any save-then-publish as a defect on sight."
⭐ ⇒ ⭐⭐ The second one shows a rule you now carry — which is what learning looks like.
```

⚠️ **And the counterpart: "what are you happy with?"** Have an answer to that too. **A candidate who can
only criticise their own work is as unconvincing as one who cannot** — the target is calibration, not
humility.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **"Because I know it"** | ⭐⭐ the one answer that is always wrong |
| ⭐ Listing benefits only | ⭐⭐ a pure-upside choice reads as unexamined |
| ⭐⭐ **Not naming what you rejected** | ⭐⭐ you cannot show a decision without an alternative |
| ⭐⭐ **Not naming the cost** | ⭐⭐ part 3 is what proves evaluation |
| ⭐ Inventing an evaluation you never did | ⭐⭐ collapses on the second follow-up |
| ⭐ Deliberating build tools, defaulting on the data model | ⭐⭐ attention in the wrong place |
| ⭐ "Why not microservices?" answered with fashion | ⭐ name the cost you avoided |
| ⭐ Cache with no before/after numbers | ⭐⭐ "I cached it" is not an answer |
| ⭐⭐ **"Nothing, I'm happy with it"** | ⭐⭐ reads as no reflection |
| ⭐ "Everything, it's a mess" | ⭐ reads as no judgement |
| ⭐ Only criticism, no confidence | ⭐⭐ calibration is the target |
| Hesitating on a row of your own decision log | it is where they will dig |

## Interview questions

**Q: Why did you choose Postgres?**
Three parts. The force: the data is relational and the invariants matter — an order must not exist
without line items — and I wanted that enforced by the database rather than by application discipline.
What I rejected: a document store, because I would have been reimplementing joins and transactions in
application code, which is where correctness goes to die. And the cost, which I would volunteer: scaling
writes eventually means sharding, and I have a single primary today, so I know where the ceiling is and
roughly when I would hit it.

**Q: Why does naming the cost matter more than naming the benefits?**
Because anyone can list benefits — they are in the marketing material. Naming what the choice costs you
is the thing that distinguishes evaluating from adopting, and a decision presented as pure upside reads
as unexamined. It also pre-empts the interviewer's next question, which was going to be exactly that, and
it demonstrates that I know where my system breaks, which is usually the following round anyway.

**Q: Some of your choices were surely just defaults. How do you handle that?**
By saying so, because inventing an evaluation collapses on the second follow-up. Spring Boot was a
default rather than a decision — ecosystem gravity is a real engineering force and being different has a
cost I had no reason to pay. What I then add is the choice I did make inside it: keeping the domain layer
free of framework annotations so business rules are testable without a context. That converts "I
defaulted" into "I know which things deserve deliberation", and the distinction they are actually probing
is whether I deliberated over the build tool while defaulting on my consistency model.

**Q: What would you do differently?**
Two things, one small and one structural. The small one: I would write the API contract before the
entities, because I let the persistence model shape the public API and had to unpick it later. The
structural one: I would put the outbox in from the start rather than after finding the bug, because I now
treat any save-then-publish as a defect on sight rather than a thing to revisit. The second is the more
useful answer, because it is a rule I carry forward rather than a regret about one project.

**Q: What are you happy with?**
The failure behaviour, because it is the part that is usually missing. Health checks that do not touch
the database, so a database blip cannot fail the whole fleet; a deploy that drops zero requests under
load, which I verified rather than assumed; and a forced database failover with eleven seconds of
client-visible impact, which was forty minutes the first time because the JVM was caching DNS forever.
Being able to say what I am happy with matters as much as self-criticism — a candidate who can only
criticise their own work is as uncalibrated as one who cannot.

## 🎙️ Articulation drill

**Two minutes:** have someone pick three rows of your decision log at random and ask "why?" for each.

**⭐ Each answer is thirty seconds and has the same shape: the force, the rejected alternative with the
reason, and the cost you are carrying. Do not wait to be asked for the cost — volunteering it is the
whole technique, because it converts a defence into an assessment.**

**⭐ Then the harder version: for each of the three, answer "and what would make you change that
decision?" Naming the condition that would flip your choice — "if writes outgrew a single primary", "if
we needed sub-second event latency" — is the strongest form of the answer, because it shows the decision
is live rather than historical.**
