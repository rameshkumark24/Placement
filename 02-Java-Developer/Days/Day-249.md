# Day 249 🏗️

**P-249** · Requirements — writing down what you are actually building

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ The purpose of today is not documentation. It is discovery.** Writing requirements as
> testable statements forces every ambiguity to the surface **before** it becomes a schema you cannot
> change and a decision you cannot explain.
>
> Every hour here saves several later, and the artefacts you produce are also what you will reason
> from in an interview when someone asks "how did you decide that?"

---

# Part 1 — ⭐ Functional requirements, written to be testable

**⭐ The rule: a requirement you cannot write a test for is not a requirement — it is a wish.**

| ❌ Vague | ⭐ Testable |
|---|---|
| "Users can book rooms" | ⭐ "An authenticated user can create a booking for a room and a time range, if no confirmed booking overlaps it" |
| "Bookings should be fast" | ⭐ "Creating a booking returns in under 300 ms at p99 with 50 concurrent users" |
| "Handle cancellations" | ⭐ "A booking in `CONFIRMED` may be cancelled by its owner or an admin up to 2 hours before start; after that it may not" |

**⭐ Notice what the third rewrite exposed**: who may cancel, from which state, and a time boundary —
three decisions that would otherwise have been made accidentally in a service method at 11pm.

## ⭐ Write them as user stories with acceptance criteria

```
⭐ US-04 — Cancel a booking
As a booking owner
I want to cancel my booking
So that the room is released for others

Acceptance criteria:
  ⭐ AC-1  Only the owner or an ADMIN may cancel                      → 403 otherwise
  ⭐ AC-2  Only from CONFIRMED or PENDING                             → 409 otherwise
  ⭐ AC-3  Not within 2 hours of start_time                           → 422 with a reason
  ⭐ AC-4  Cancelling frees the slot immediately for new bookings
  ⭐ AC-5  Cancelling emits a BookingCancelled event                  (Day 179)
  ⭐ AC-6  Cancelling twice is idempotent                             → 204 both times (Day 123)
```

**⭐ Each AC becomes a test.** That is the point: the requirements document and the test suite are the
same document written twice, and if they diverge, one of them is wrong.

**⭐ AC-1 through AC-3 also tell you the error contract** — 403, 409, 422 — which is Day 149's status
selection, decided at requirements time rather than improvised.

## ⭐ Cover every story with these five questions

> **⭐ 1. Who is allowed to do this?** (Day 174 — record-level, not just role)
> **⭐ 2. From what states, and to what state?** (the state machine)
> **⭐ 3. What happens if two people do it simultaneously?** (Day 195)
> **⭐ 4. What happens if it is retried?** (Day 123 — idempotency)
> **⭐ 5. What must happen afterwards, and must it survive a crash?** (Day 124 — outbox or not)

**⭐ Question 3 is the one everybody skips**, and it is where your project's hard problem lives.
Answer it explicitly for every story that writes.

# Part 2 — ⭐ Non-functional requirements, with numbers

**⭐ An NFR without a number is not a requirement.** "It should be fast" cannot be tested, cannot be
designed for, and cannot be defended.

| Category | ⭐ Write it like this |
|---|---|
| ⭐ **Latency** | ⭐ p50 < 100 ms, p99 < 500 ms for reads; p99 < 1 s for writes |
| ⭐ **Throughput** | 200 requests/sec sustained; 500 peak |
| ⭐ **Concurrency** | 50 users booking the same room within one second must produce exactly one booking |
| ⭐ **Availability** | 99.5% — ⭐ 3.6 hours of downtime per month is acceptable |
| ⭐ **RPO / RTO** | ⭐ RPO 5 min, RTO 1 hour (Day 201) |
| Data volume | 100k bookings/year, 5-year retention (Day 200) |
| ⭐ **Security** | passwords argon2; tokens 15 min; ⭐ record-level authorization on every endpoint |

**⭐ Three of these change your design, so decide them now:**

- ⭐ **The concurrency requirement** decides whether you need an exclusion constraint, optimistic
  locking, or a lock (Days 187, 165, 207).
- ⭐ **RPO/RTO** decides your backup and replication strategy (Day 201) — and whether you must ever
  test a restore.
- ⭐ **Data volume and retention** decides whether you partition (Day 200) on day one or never.

**⭐ These are also excellent interview answers**, because most candidates have never written an NFR
at all. "My availability target was 99.5%, which is why I did not build multi-region" demonstrates
that you understand a target constrains the architecture rather than decorating it.

# Part 3 — ⭐ The state machine — draw it today

**⭐ Every domain with a `status` field has a state machine, whether or not anyone drew it.** Drawing
it is how you find the transitions nobody thought about.

```
        create
          ↓
    ┌──────────┐  confirm   ┌───────────┐  check-in  ┌────────────┐
    │ PENDING  │───────────►│ CONFIRMED │───────────►│ IN_PROGRESS│
    └────┬─────┘            └─────┬─────┘            └──────┬─────┘
         │ cancel                 │ cancel (>2h)            │ complete
         │ ⭐ expire (15 min)     │                         ▼
         ▼                        ▼                   ┌───────────┐
    ┌───────────┐           ┌───────────┐             │ COMPLETED │
    │  EXPIRED  │           │ CANCELLED │             └───────────┘
    └───────────┘           └───────────┘
```

**⭐ For every transition, write down four things:**

| | |
|---|---|
| ⭐ **Who** may trigger it | owner, admin, ⭐ **the system** |
| ⭐ **Guard** conditions | "more than 2 hours before start" |
| ⭐ **Side effects** | release the slot, emit an event, refund |
| ⭐ **Is it idempotent?** | cancelling twice must be safe |

**⭐ Note `PENDING → EXPIRED` is triggered by the system**, not a user. That single arrow means you
need a scheduled job (Day 178) — which must be idempotent and locked across instances. **One arrow on
a diagram just created a whole subsystem**, and that is exactly what today is for.

**⭐ Then encode the machine in the database** (Day 187):

```
⭐ A check constraint: status ∈ the known set
⭐ A check constraint: CONFIRMED implies confirmed_at is not null
⭐ Transitions enforced in the domain layer, not scattered in services
```

# Part 4 — ⭐ Finding the hard problem, precisely

**⭐ Today's most valuable output: a one-page document stating your concurrency problem, the failure
it causes, and the three candidate solutions.**

```markdown
# docs/HARD-PROBLEM.md

## The problem
Two users book the same room for overlapping times simultaneously.

## ⭐ The failure, precisely
Both transactions SELECT to check for conflicts, both find none, both INSERT.
⭐ This is write skew (Day 195): they wrote different rows, so no row-level
conflict exists and REPEATABLE READ does not detect it.

## Candidates
| Option | Pros | ⭐ Cons |
|---|---|---|
| ⭐ Exclusion constraint (Day 187) | ⭐ database-enforced, no race, no retry | PostgreSQL-specific |
| SERIALIZABLE (Day 195) | standard | ⭐ requires a retry loop; abort rate under load |
| Distributed lock (Day 207) | works across stores | ⭐ not a safety guarantee (Day 207) |

## Decision
⭐ Exclusion constraint. It is the only option where the invariant holds
regardless of how the row is written — including by a migration or by a
future service.

## ⭐ How I will prove it
Two threads, same room, same slot, 100 iterations.
⭐ Assert exactly one succeeds and the other gets a 409.
```

**⭐ That last section is the difference between a claim and a demonstration.** Write the test before
the feature; it is Day 098's TDD applied at the level that matters most.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Requirements too vague to test | you discover the ambiguity in production code |
| ⭐ Not asking "what if two people do this at once?" | ⭐ the hard problem is found late, or never |
| Skipping the state machine | undefined transitions become bugs |
| ⭐ NFRs without numbers | nothing to design toward or defend |
| Missing system-triggered transitions | a whole subsystem discovered in week four |
| ⭐ Not deciding the error status per AC | Day 149 improvised at 11pm |
| Writing requirements for features you cut yesterday | Day 248's scope list exists for this |

- [ ] Every NFR has a **number**
- [ ] ⭐ The state machine is drawn, with who/guard/effects/idempotency per transition
- [ ] ⭐ `HARD-PROBLEM.md` exists, with three candidates and **how you will prove it**

## 🎤 Defence questions

1. **⭐ What happens if two users do the same thing at the same time?**
2. **What are your latency and availability targets, and what did they rule out?**
3. **Walk me through your state machine. Which transitions are system-triggered?**
4. **⭐ How do you know cancellation is idempotent?**
5. **⭐ Which requirement was hardest to pin down, and what did writing it reveal?**
