# Part 1 — L-068 · Compare-and-swap

## The instruction

```
CAS(address, expected, newValue):
    atomically:
        if (*address == expected) { *address = newValue; return true; }
        else                      { return false; }
```

The word doing all the work is **atomically**. This is a single CPU instruction — `LOCK CMPXCHG` on
x86, `LDREX`/`STREX` on older ARM, `CAS` on ARMv8.1 — and the hardware guarantees no other core can
observe or interleave with its middle. That is the entire primitive.

Note what it returns: a **boolean**, not the value. CAS can fail, and failure is normal. The caller's
job is to retry:

```java
int old, next;
do {
    old  = value.get();
    next = old + 1;
} while (!value.compareAndSet(old, next));     // retry until nobody beat us
```

This loop is the shape of every lock-free algorithm: **read, compute, attempt, retry on
interference**. Note it is *optimistic* — you do the work first and check for conflict afterwards,
the opposite of a lock, which pessimistically excludes everyone before you start.

## Why it fixes what `volatile` could not

Day 065's counter failed because `count++` is read-add-write with a gap in the middle. CAS closes
the gap differently — not by excluding others, but by **detecting** that someone else changed the
value and doing the work again.

```java
AtomicInteger count = new AtomicInteger();
count.incrementAndGet();     // implemented exactly as the retry loop above
```

Every atomic field is `volatile` internally, so you also get Day 065's visibility guarantees for
free. `AtomicInteger` gives you visibility *and* atomicity, with no lock.

## Lock-free is not wait-free — and not always faster

Three terms worth keeping straight:

- **Blocking** — a thread can be suspended holding the resource; if it is descheduled, everyone
  waits.
- **Lock-free** — *some* thread always makes progress. An individual thread may retry indefinitely.
- **Wait-free** — *every* thread completes in a bounded number of steps. Rare and expensive.

CAS gives you lock-free, not wait-free. The practical consequence: **under very high contention CAS
degrades**, because many threads spin, fail and retry, burning CPU. The comparison against locks:

| | Locks | CAS |
|---|---|---|
| Low contention | fast (one CAS to acquire anyway) | fastest |
| High contention | threads park; CPU is idle but switching | threads spin; CPU burns on retries |
| Thread killed mid-operation | everyone blocks forever | others proceed |
| Priority inversion | possible | impossible |
| Composability | multiple operations under one lock | one variable only |

That last row is the real limitation. **CAS operates on one memory location.** Any invariant
spanning two fields — transfer money from A to B, keep `size` in sync with the list — cannot be done
with a single CAS. That is why locks did not go away.

## The atomic classes

```java
AtomicInteger, AtomicLong, AtomicBoolean
AtomicReference<V>
AtomicIntegerArray, AtomicLongArray, AtomicReferenceArray
AtomicStampedReference<V>, AtomicMarkableReference<V>      // ← the ABA fix
LongAdder, LongAccumulator, DoubleAdder                    // ← the contention fix
AtomicIntegerFieldUpdater<T>                               // legacy; VarHandle replaces it
```

The core operations, all lock-free:

```java
AtomicInteger a = new AtomicInteger(5);

a.get(); a.set(7);                       // volatile read / write
a.incrementAndGet();                     // ++a
a.getAndIncrement();                     // a++
a.addAndGet(10);
a.compareAndSet(17, 20);                 // the primitive itself
a.getAndSet(99);
a.updateAndGet(x -> x * 2);              // CAS loop over a lambda — Java 8
a.accumulateAndGet(5, Math::max);        // CAS loop with a binary op
```

`updateAndGet` deserves a warning: the function **may be called multiple times** because the loop
retries. It must be pure and side-effect-free. A lambda that increments a metric or logs will do so
once per attempt, not once per success.

`AtomicReference` is how you make a *compound* update atomic — by making the compound state a single
immutable object:

```java
record Balance(long amount, long version) {}
AtomicReference<Balance> ref = new AtomicReference<>(new Balance(100, 0));

Balance old, next;
do {
    old = ref.get();
    next = new Balance(old.amount() - 50, old.version() + 1);
} while (!ref.compareAndSet(old, next));
```

**That is the general technique**: when you need two fields to change together without a lock, put
them in one immutable object and CAS the reference. It costs an allocation per update, and it is how
most lock-free data structures are built.

## `LongAdder` — when CAS contention is the problem

```java
LongAdder adder = new LongAdder();
adder.increment();
long total = adder.sum();
```

Under heavy contention every thread CASes the *same* cache line, so cores fight over exclusive
ownership of it — **false sharing / cache-line ping-pong**, and throughput collapses.

`LongAdder` spreads the count across an array of padded cells, one per contending thread (roughly),
so each thread usually CASes its own cache line uncontended. `sum()` adds them up.

```
AtomicLong:   [ value ]  ← 8 threads CAS the same line, 7 fail every time

LongAdder:    [cell0][cell1][cell2][cell3]  ← 8 threads spread across lines
              sum() = cell0 + cell1 + cell2 + cell3
```

The trade-off: `sum()` is **not atomic** with respect to concurrent updates — it is a snapshot that
may miss an in-flight increment. That is fine for a metrics counter and wrong for a value you make
decisions on.

> **Rule of thumb:** high-frequency writes and infrequent reads → `LongAdder`. Read-after-write
> consistency required → `AtomicLong`.

# Part 2 — The ABA problem

## What it is

CAS asks *"is the value still what I read?"* It cannot ask *"has the value changed since I read
it?"* — and those are different questions.

```
Thread 1: reads A                     … suspended …
Thread 2: changes A → B
Thread 2: changes B → A
Thread 1: resumes, CAS(expected=A, new=X) → SUCCEEDS
```

Thread 1's CAS succeeds even though the world changed underneath it twice. For a plain counter this
is harmless — the value really is A, and A is all the counter means. For a **reference**, it can be
catastrophic, because the identity is the same but the *state it implied* is not.

## The concrete failure: a lock-free stack

```java
class LockFreeStack<E> {
    static class Node<E> { E item; Node<E> next; Node(E i, Node<E> n) { item = i; next = n; } }
    private final AtomicReference<Node<E>> top = new AtomicReference<>();

    void push(E item) {
        Node<E> newTop, oldTop;
        do {
            oldTop = top.get();
            newTop = new Node<>(item, oldTop);
        } while (!top.compareAndSet(oldTop, newTop));
    }

    E pop() {
        Node<E> oldTop, newTop;
        do {
            oldTop = top.get();
            if (oldTop == null) return null;
            newTop = oldTop.next;                  // ← read BEFORE the CAS
        } while (!top.compareAndSet(oldTop, newTop));
        return oldTop.item;
    }
}
```

Now the interleaving. Stack is `A → B → C`.

```
T1: pop()  reads oldTop = A,  newTop = A.next = B      … suspended …
T2: pop()  removes A                       stack: B → C
T2: pop()  removes B                       stack: C
T2: push(A)  (reusing the same node object) stack: A → C     ← A.next is now C
T1: resumes.  CAS(top, expected=A, new=B)   SUCCEEDS — top is A!
    stack is now: B → ???     B was already popped. C is lost.
```

**The stack is corrupted.** The CAS was satisfied by object identity, but `A.next` had been rewritten
between the read and the CAS. T1 restored a stale link.

In Java this specific scenario is rarer than in C/C++ because the GC keeps a node alive as long as
anyone references it, so a *freed-and-reallocated* address cannot masquerade as the old one. But it
still occurs whenever objects are **pooled or reused** — which is exactly what high-performance code
does to reduce allocation.

## The fix: a version stamp

Attach a counter that only ever increases, and CAS the pair atomically:

```java
AtomicStampedReference<Node> top = new AtomicStampedReference<>(initial, 0);

int[] stampHolder = new int[1];
Node oldTop = top.get(stampHolder);
int  stamp   = stampHolder[0];
Node newTop  = oldTop.next;

top.compareAndSet(oldTop, newTop, stamp, stamp + 1);   // A→B→A now has a DIFFERENT stamp
```

Because the stamp increments on every change, A→B→A leaves the reference equal but the stamp
different, so the CAS fails and the retry loop re-reads correctly. `AtomicMarkableReference` is the
one-bit version, used for "logically deleted" flags in lock-free lists.

This is the same idea as **optimistic locking with a version column** in a database (Stage 5's
`@Version`) — and saying so in an interview shows you see the pattern rather than the API.

## Code to type

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class CasDemo {

    public static void main(String[] args) throws Exception {
        // 1. CAS as a retry loop, made visible
        AtomicInteger a = new AtomicInteger(0);
        AtomicInteger retries = new AtomicInteger(0);

        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) {
                int old, next;
                do {
                    old = a.get();
                    next = old + 1;
                    retries.incrementAndGet();
                } while (!a.compareAndSet(old, next));
                retries.decrementAndGet();          // one attempt was the successful one
            }
        };
        Thread[] ts = new Thread[4];
        for (int i = 0; i < 4; i++) { ts[i] = new Thread(task); ts[i].start(); }
        for (Thread t : ts) t.join();
        System.out.printf("value=%,d  wasted retries≈%,d%n", a.get(), retries.get());

        // 2. contention: AtomicLong vs LongAdder vs synchronized
        for (int threads : new int[]{1, 4, 16}) {
            System.out.printf("%n--- %d threads ---%n", threads);
            bench("AtomicLong", threads, new AtomicLong()::incrementAndGet);
            LongAdder adder = new LongAdder();
            bench("LongAdder ", threads, adder::increment);
            Object lock = new Object();
            long[] plain = new long[1];
            bench("synchronized", threads, () -> { synchronized (lock) { plain[0]++; } });
        }

        // 3. ABA
        AtomicReference<String> ref = new AtomicReference<>("A");
        AtomicStampedReference<String> stamped = new AtomicStampedReference<>("A", 0);

        String observed = ref.get();
        int[] holder = new int[1];
        String observedS = stamped.get(holder);
        int observedStamp = holder[0];

        ref.set("B"); ref.set("A");                                   // A → B → A
        stamped.set("B", 1); stamped.set("A", 2);

        System.out.println("\nplain CAS after ABA:   " + ref.compareAndSet(observed, "X"));
        System.out.println("stamped CAS after ABA: " +
                stamped.compareAndSet(observedS, "X", observedStamp, observedStamp + 1));
    }

    static void bench(String name, int threads, Runnable op) throws Exception {
        int perThread = 1_000_000;
        Thread[] ts = new Thread[threads];
        long t0 = System.nanoTime();
        for (int i = 0; i < threads; i++) {
            ts[i] = new Thread(() -> { for (int j = 0; j < perThread; j++) op.run(); });
            ts[i].start();
        }
        for (Thread t : ts) t.join();
        System.out.printf("  %-12s %6d ms%n", name, (System.nanoTime() - t0) / 1_000_000);
    }
}
```

Expected observations:

- **Wasted retries scale with thread count.** At 1 thread, near zero. At 16, most attempts fail.
- **`LongAdder` wins decisively at 16 threads** and loses slightly at 1 (extra indirection).
- **The ABA section prints `true` then `false`** — the plain CAS is fooled; the stamped one is not.

## Where CAS shows up in code you have already read

- `ConcurrentHashMap` (Day 053) — CAS to install the first node in an empty bin, no lock at all.
- `AQS` (Day 067) — CAS on the `state` word to acquire; queueing only on failure.
- Biased/thin locking (Day 066) — a CAS on the object's mark word.
- `ConcurrentLinkedQueue` — the Michael–Scott lock-free queue, CAS on head and tail.
- `CompletableFuture` (tomorrow) — CAS on the result field to complete exactly once.

## `VarHandle` — the modern way to CAS your own fields

`sun.misc.Unsafe` was how this was done for years and is not public API. Java 9 gave it a supported
replacement:

```java
class Node {
    volatile Node next;
    private static final VarHandle NEXT;
    static {
        try {
            NEXT = MethodHandles.lookup().findVarHandle(Node.class, "next", Node.class);
        } catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
    }
    boolean casNext(Node expect, Node update) { return NEXT.compareAndSet(this, expect, update); }
}
```

`VarHandle` also exposes finer-grained memory ordering than `volatile` — `getAcquire`,
`setRelease`, `getOpaque` — which is what the JDK itself uses to avoid paying for a full
`StoreLoad` barrier when acquire/release semantics suffice. You will rarely write this. Recognising
it is enough.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Forgetting CAS returns a boolean | Update silently lost |
| No retry loop around `compareAndSet` | Same |
| Side effects in an `updateAndGet` lambda | Executed once per *attempt* |
| Expecting CAS to span two fields | It cannot — use an immutable holder or a lock |
| `LongAdder.sum()` treated as exact | It is a snapshot |
| Assuming lock-free means faster | Under high contention it can be slower |
| Assuming lock-free means wait-free | An individual thread can retry indefinitely |
| Reusing nodes without a stamp | ABA corruption |
| Writing your own lock-free structure | Almost always a mistake; use `java.util.concurrent` |

## Interview questions

**Q: What is CAS?**
An atomic hardware instruction that writes a new value only if the current value equals an expected
one, returning whether it succeeded. It is the basis for lock-free algorithms — the caller retries
on failure.

**Q: How does `AtomicInteger.incrementAndGet` work?**
A loop: read the volatile value, compute value+1, `compareAndSet`; if another thread intervened the
CAS fails and the loop retries.

**Q: Atomics vs `synchronized`?**
Atomics are lock-free and generally faster at low-to-moderate contention, cannot deadlock, and are
not affected by a descheduled thread — but they cover a single variable and can spin badly under
heavy contention. Locks cover arbitrary regions and multiple variables.

**Q: What is the ABA problem?**
CAS checks equality, not "unchanged". If a value goes A→B→A, a stale CAS succeeds even though the
world moved. It matters for references whose associated state changed — the classic case is a
lock-free stack whose popped node was recycled. The fix is a version stamp, e.g.
`AtomicStampedReference`.

**Q: When do you use `LongAdder` over `AtomicLong`?**
High write contention with infrequent reads — metrics counters. It trades an exact, atomic read for
per-cell striping that avoids cache-line contention.

**Q: Is lock-free always faster?**
No. Under heavy contention CAS retries burn CPU while blocked threads at least yield it. Measure.
