# L-056 · Wildcards

## The problem

Day 054: generics are invariant. That's safe, and it's restrictive:

```java
static double sum(List<Number> numbers) { ... }

sum(List.of(1, 2, 3));           // ❌ List<Integer> is not a List<Number>
sum(List.of(1.5, 2.5));          // ❌ List<Double> is not a List<Number>
```

**A method that only *reads* numbers is rejected for a list of integers.** Wildcards relax invariance
where it's provably safe.

## The three forms

```java
List<?>              // unbounded — "a list of something, I don't know what"
List<? extends T>    // upper-bounded — "T or any subtype"
List<? super T>      // lower-bounded — "T or any supertype"
```

## `? extends` — covariance, for reading

```java
static double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();    // ✅ reading is safe
    return total;
}

sum(List.of(1, 2, 3));           // ✅ List<Integer>
sum(List.of(1.5, 2.5));          // ✅ List<Double>
```

**Why reading is safe:** whatever the actual type argument, every element **is-a** `Number`. So you
can always read out as `Number`.

**Why writing is forbidden:**

```java
void addTo(List<? extends Number> list) {
    list.add(42);            // ❌ COMPILE ERROR
}
```

**The list could be a `List<Double>`.** Adding an `Integer` would corrupt it. The compiler can't know
which subtype it actually is, so it forbids all writes.

**The only value you can add is `null`** — the one value that's a member of every reference type.

## `? super` — contravariance, for writing

```java
static void addNumbers(List<? super Integer> list) {
    list.add(1);             // ✅ writing is safe
    list.add(2);
    Object o = list.get(0);  // ⚠️ you can only read as Object
}

addNumbers(new ArrayList<Integer>());   // ✅
addNumbers(new ArrayList<Number>());    // ✅
addNumbers(new ArrayList<Object>());    // ✅
```

**Why writing is safe:** whatever the actual type is, it's `Integer` or a *supertype* of `Integer`. An
`Integer` fits into any of them.

**Why reading is limited:** the list could be `List<Object>`, so the only thing you can be certain of
is `Object`.

## PECS — Producer Extends, Consumer Super

**The rule:**

> **If the parameter is a producer — you read T out of it — use `? extends T`.**
> **If the parameter is a consumer — you write T into it — use `? super T`.**
> **If it's both, use no wildcard at all.**

The canonical example, straight from the JDK:

```java
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    //                            ↑ CONSUMER          ↑ PRODUCER
    for (int i = 0; i < src.size(); i++) dest.set(i, src.get(i));
}

List<Object> dest = new ArrayList<>(...);
List<Integer> src = List.of(1, 2, 3);
copy(dest, src);                 // ✅ works
```

**`src` produces T values (you read from it) → `extends`. `dest` consumes them (you write to it) →
`super`.** Once you see it as read-versus-write, the mnemonic stops being arbitrary.

### The real-world signatures

```java
// Collection
boolean addAll(Collection<? extends E> c);       // c PRODUCES elements to add

// Collections
static <T> void copy(List<? super T> dest, List<? extends T> src);
static <T> T max(Collection<? extends T> coll, Comparator<? super T> comp);

// Stream
<R> Stream<R> map(Function<? super T, ? extends R> mapper);
Stream<T> filter(Predicate<? super T> predicate);
void forEach(Consumer<? super T> action);
<R, A> R collect(Collector<? super T, A, R> collector);
```

**`Function<? super T, ? extends R>`** reads perfectly once you have PECS: the function **consumes**
`T` (so `super`) and **produces** `R` (so `extends`).

**And the practical benefit:**

```java
Stream<Integer> s = Stream.of(1, 2, 3);
Consumer<Object> printer = System.out::println;
s.forEach(printer);              // ✅ works BECAUSE the signature says Consumer<? super T>
```

A `Consumer<Object>` can handle an `Integer`. Without `? super`, that wouldn't compile — and you'd be
forced to write a `Consumer<Integer>` for no reason.

## `List<?>` vs `List<Object>` vs raw `List`

**Three things that look similar and behave very differently:**

| | Can add | Can read as | Type-checked |
|---|---|---|---|
| `List<Object>` | **Anything** | `Object` | ✅ |
| `List<?>` | **Only `null`** | `Object` | ✅ |
| `List` (raw) | Anything | `Object` | ❌ **no checking** |

```java
List<?> unknown = new ArrayList<String>();
unknown.add("x");        // ❌ — could be a List<Integer>
unknown.add(null);       // ✅ null is a member of every type
Object o = unknown.get(0);   // ✅
int n = unknown.size();      // ✅ — methods not involving the type parameter are fine
```

**`List<?>` means "a list of some specific unknown type"**, not "a list of anything". That distinction
is the whole point.

**Use `List<?>` when you don't care about the element type** — `size()`, `clear()`, `isEmpty()`,
printing. **Never use a raw `List`** — it disables checking entirely and generates unchecked warnings.

## Wildcard capture

```java
static void swapFirstTwo(List<?> list) {
    list.set(0, list.get(1));      // ❌ can't write to a List<?>
}

// The capture helper idiom:
static void swapFirstTwo(List<?> list) { swapHelper(list); }

private static <T> void swapHelper(List<T> list) {
    T tmp = list.get(0);
    list.set(0, list.get(1));      // ✅ now T is a definite type
    list.set(1, tmp);
}
```

**A generic method "captures" the wildcard into a real type parameter**, so the compiler can reason
that the read and the write involve the same type — even though it doesn't know which.

**You'll meet the error message `capture of ?`**, which is the compiler naming that anonymous captured
type. Recognising it is half the battle.

## When to use wildcards — and when not to

**Use them in method parameters** to maximise flexibility for callers.

**Don't use them as return types:**

```java
// 💀 forces every caller to deal with wildcards
static List<? extends Number> getNumbers() { ... }

// ✅
static List<Number> getNumbers() { ... }
```

**A wildcard return type is contagious** — it propagates into the caller's code for no benefit.

**Don't use them for a type used both ways:**

```java
// If you both read and write T, no wildcard is correct — use a plain type parameter
static <T> void process(List<T> list) { T t = list.get(0); list.add(t); }
```

**And the caller never writes them:**

```java
List<? extends Number> list = new ArrayList<>();   // 💀 almost useless — you can't add anything
List<Number> list = new ArrayList<>();             // ✅
```

**Wildcards belong in APIs you write for others, not in your local variables.**

## Type this yourself

```java
import java.util.*;
import java.util.function.*;

public class WildcardDemo {

    // PRODUCER — we read Numbers out
    static double sum(List<? extends Number> numbers) {
        double total = 0;
        for (Number n : numbers) total += n.doubleValue();
        // numbers.add(1);       // ← uncomment: compile error
        return total;
    }

    // CONSUMER — we write Integers in
    static void fill(List<? super Integer> list, int count) {
        for (int i = 0; i < count; i++) list.add(i);
        Object first = list.get(0);      // can only read as Object
    }

    // PECS together
    static <T> void copy(List<? super T> dest, List<? extends T> src) {
        for (T item : src) dest.add(item);
    }

    // wildcard capture
    static void reverse(List<?> list) { reverseHelper(list); }
    private static <T> void reverseHelper(List<T> list) {
        for (int i = 0, j = list.size() - 1; i < j; i++, j--) {
            T tmp = list.get(i);
            list.set(i, list.get(j));
            list.set(j, tmp);
        }
    }

    // no wildcard — T is used BOTH ways
    static <T> T firstOrDefault(List<T> list, T fallback) {
        return list.isEmpty() ? fallback : list.get(0);
    }

    public static void main(String[] args) {

        System.out.println("--- ? extends : producer ---");
        System.out.println("   sum(List<Integer>) = " + sum(List.of(1, 2, 3)));
        System.out.println("   sum(List<Double>)  = " + sum(List.of(1.5, 2.5)));
        System.out.println("   sum(List<Long>)    = " + sum(List.of(10L, 20L)));
        System.out.println("   ↑ none of these compile with List<Number>");

        System.out.println("\n--- ? super : consumer ---");
        List<Number> numbers = new ArrayList<>();
        List<Object> objects = new ArrayList<>();
        fill(numbers, 3); fill(objects, 3);
        System.out.println("   List<Number> ← " + numbers);
        System.out.println("   List<Object> ← " + objects);

        System.out.println("\n--- PECS: copy ---");
        List<Object> dest = new ArrayList<>();
        copy(dest, List.of(1, 2, 3));
        copy(dest, List.of("a", "b"));
        System.out.println("   dest = " + dest);

        System.out.println("\n--- List<?> vs List<Object> vs raw ---");
        List<?> unknown = new ArrayList<>(List.of("a", "b"));
        unknown.add(null);                       // the only legal add
        System.out.println("   List<?>.size() = " + unknown.size() + ", contents " + unknown);
        // unknown.add("c");                     // ← uncomment: compile error

        List<Object> anything = new ArrayList<>();
        anything.add("x"); anything.add(1); anything.add(true);
        System.out.println("   List<Object> accepts anything: " + anything);

        System.out.println("\n--- wildcard capture ---");
        List<String> words = new ArrayList<>(List.of("a", "b", "c", "d"));
        reverse(words);
        System.out.println("   reversed via capture helper: " + words);

        System.out.println("\n--- why the JDK uses ? super in Consumer ---");
        Consumer<Object> printer = o -> System.out.println("      got " + o);
        List.of(1, 2, 3).forEach(printer);
        System.out.println("   ↑ a Consumer<Object> handling a List<Integer>");
        System.out.println("     works only because forEach takes Consumer<? super T>");

        System.out.println("\n--- no wildcard when T is used both ways ---");
        System.out.println("   firstOrDefault([], \"none\") = " + firstOrDefault(List.of(), "none"));
    }
}
```

**Two experiments:** uncomment `numbers.add(1)` inside `sum` and read the error — the compiler
explains it can't verify the type. Then uncomment `unknown.add("c")` and note it fails **even though
you can see the list holds strings** — the compiler only knows it's `List<?>`.

## Common mistakes

| Mistake | Correction |
|---|---|
| Trying to add to a `? extends` list | It's a producer. Only reads are safe. |
| Expecting to read a specific type from `? super` | You can only read as `Object`. |
| Wildcards in return types | Contagious — forces wildcards on every caller. |
| Wildcards on local variables | You lose the ability to add. Use the concrete type. |
| Raw `List` instead of `List<?>` | Raw types disable checking entirely. |
| Wildcards where T is used both ways | Use a plain type parameter. |
| Memorising PECS without the reason | The derivation is the interview answer. |

## Interview questions

**Q: What does PECS mean?**
> Producer Extends, Consumer Super. If a parameter produces values you read out, declare it
> `? extends T`; if it consumes values you write in, declare it `? super T`. If you do both, use a
> plain type parameter with no wildcard. `Collections.copy(List<? super T> dest, List<? extends T>
> src)` is the canonical example.

**Q: Why can't you add to a `List<? extends Number>`?**
> Because the compiler doesn't know which subtype it actually is. It could be a `List<Double>`, so
> adding an `Integer` would corrupt it. Reading is safe because every element is guaranteed to be a
> `Number` whatever the actual type. The only value you can add is `null`, since null belongs to every
> reference type.

**Q: What's the difference between `List<?>`, `List<Object>` and raw `List`?**
> `List<?>` is a list of some specific but unknown type — you can read elements as `Object` and call
> methods that don't involve the type parameter, but you can only add `null`. `List<Object>` is a list
> that genuinely holds any object, so you can add anything. A raw `List` disables generic checking
> altogether, which permits heap pollution and generates unchecked warnings.

**Q: Why is `Stream.map` declared `Function<? super T, ? extends R>`?**
> PECS applied twice. The function consumes `T`, so `? super T` lets you pass a function accepting a
> supertype — a `Function<Object, String>` works on a `Stream<Integer>`. It produces `R`, so
> `? extends R` lets it return a subtype. Together they maximise which functions the caller can pass.

**Q: What is wildcard capture?**
> The compiler assigning a definite but anonymous type to a wildcard so it can reason about it. You
> can't write to a `List<?>` directly, but delegating to a generic helper `<T> void helper(List<T>)`
> captures the wildcard as `T`, letting the compiler verify that a read and a subsequent write involve
> the same type. The error message `capture of ?` is the compiler naming that captured type.
