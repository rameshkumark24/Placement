# Day 283 🏗️

**P-283** · The pipeline — build, verify, deploy, and roll back

**Time:** 3 hrs · **Mode:** BUILD

> Day 253 put a CI skeleton in place on day one. **Today it becomes a deployment pipeline**, and the
> property that matters is not that it deploys — it is that **it refuses to deploy something broken,
> and that you can undo a deployment in under two minutes.**
>
> **⭐ The measure of this day: you deploy, break it deliberately, and roll back — timed.**

---

# Part 1 — ⭐ The pipeline, in stages

```
⭐ 1. FAST FEEDBACK (< 2 min)   compile · unit tests · ArchUnit · lint
⭐ 2. VERIFY (< 10 min)         integration tests (Testcontainers) · coverage + ratchet
                                mutation score · OpenAPI diff
⭐ 3. SECURITY                  dependency scan · secret scan · image scan · SBOM
⭐ 4. PACKAGE                   layered image, ⭐ tagged with the GIT SHA
⭐ 5. DEPLOY → STAGING          ⭐ migrations first · smoke tests
⭐ 6. DEPLOY → PRODUCTION       ⭐ manual approval · ⭐ rolling · smoke tests · ⭐ auto-rollback
```

**⭐ Stage 1 exists for a reason: fast feedback changes behaviour.** A pipeline whose first failure
arrives at minute twelve gets ignored while people context-switch. **Put everything cheap first and
fail fast.**

**⭐ Tag images with the git SHA, never `latest`.** `latest` makes "which version is running?"
unanswerable and rollback ambiguous — and Day 143's `build-info` should report the same SHA, so the
deployed commit is one curl away.

## ⭐ Branch protection and the merge rules

```
⭐ main is protected: ⭐ no direct pushes, all checks required, at least one review
⭐ ⭐ Squash-merge with a meaningful message   ← the history is part of the artefact (Day 262)
⭐ Trunk-based: short-lived branches, merged within a day or two
```

**⭐ Day 088's argument: long-lived branches accumulate merge risk exponentially.** For a solo
project, still use pull requests — **your own PR is where you review your own diff** (Day 262), and
the history is what an interviewer scrolls.

# Part 2 — ⭐⭐ Migrations in the pipeline — the part that goes wrong

> **⭐⭐ Migrations run BEFORE the new code deploys, and the old code must still work against the new
> schema.** That is Day 166's expand/contract constraint, and it is the pipeline's hardest rule.

```
⭐ Stage 5a: run migrations as a SEPARATE STEP (a job, not application startup)
⭐ Stage 5b: deploy the application
```

**⭐ Three reasons to separate them** (Day 166):

| Reason | Detail |
|---|---|
| ⭐ **Six instances all migrate on startup** | Flyway locks, so it is safe — ⭐ but five instances wait |
| ⭐ **A long migration delays readiness** | ⭐ past the probe timeout → the deploy fails |
| ⭐ **Different credentials** | ⭐ the migration user needs DDL; the application user must not (Day 163b) |

**⭐ And every migration carries `set lock_timeout = '3s';`** (Day 196) — because the FIFO lock queue
means one slow query plus one waiting `ALTER` blocks **every subsequent read**, and the migration
that would have taken two milliseconds takes the site down.

**⭐ The CI check worth adding today:**

```
⭐ Run the NEW migrations against a database, then run the OLD application's tests against it.
⭐ If they fail, the migration is not backward-compatible → ⭐ FAIL THE BUILD.
```

**⭐ That single check enforces expand/contract mechanically** rather than by discipline, and it is
the thing that makes zero-downtime deploys actually reliable.

# Part 3 — ⭐ Deploy, verify, and roll back

## ⭐ Rolling deploy, with the health checks doing the work

```
⭐ maxSurge: 1, maxUnavailable: 0     ← ⭐ never below capacity
⭐ Readiness gates each new pod before traffic
⭐ Startup probe with a generous threshold  (Day 282's measured number)
⭐ A pre-stop delay before SIGTERM           (Day 265)
```

**⭐ The pre-stop delay is the item people omit and it drops requests on every single deploy**: load
balancers take seconds to notice a pod is unready, so shutting down the instant `SIGTERM` arrives
kills requests routed a moment earlier.

## ⭐ Smoke tests that actually verify

```
⭐ 1. /actuator/health → UP
⭐ 2. ⭐ /actuator/info reports THE SHA YOU JUST DEPLOYED   ← ⭐ catches a failed rollout
⭐ 3. ⭐ One real end-to-end request — authenticate, create, read back
⭐ 4. ⭐ Database connectivity via a real query, not just a ping
```

**⭐ Check 2 is the one that catches the silent failure**: the deployment "succeeded", the old pods
are still serving, and health is green. **Comparing the reported SHA to the one you deployed is the
only cheap way to notice.**

**⭐ Check 3 must be a real transaction.** A health check proves the process is alive; it does not
prove the application works.

## ⭐⭐ Rollback — practise it, timed

```
⭐ kubectl rollout undo deployment/app     — ⭐ or redeploy the previous SHA
```

> **⭐⭐ A rollback path that has never been exercised is a plan, not a capability.** Practise it
> today and **write down the elapsed time — that number is part of your RTO** (Day 201).

**⭐ And the constraint that shapes everything: the database usually cannot roll back.** Which is why
Day 166's expand/contract exists — **a deploy is only reversible if the schema change was
backward-compatible.**

```
⭐ Rollback is safe when:  the migration was additive
⭐ Rollback is NOT safe when: a column was dropped or narrowed  ← ⭐ hence the wait before contracting
```

**⭐ That is what Day 166's "wait before dropping" step is actually for**, and being able to state it
is a strong signal.

## ⭐ Feature flags — separating release from deploy

```
⭐ Deploy the code dark → enable for yourself → enable for 10% → enable for all
```

**⭐ The point: a risky change becomes a config toggle rather than a rollback.** It also lets you
deploy the frontend and backend independently. **Keep flags short-lived** — a flag older than a
quarter is dead code with a branch in it.

# Part 4 — ⭐ Environments, secrets, and the pipeline's own security

## ⭐ Staging must resemble production

| ⭐ Must match | ⭐ May differ |
|---|---|
| ⭐ **The database engine and version** | data volume (⭐ but seed realistically) |
| ⭐ **The configuration mechanism** | instance count |
| ⭐ **The deployment method** | resource sizes |
| ⭐ **TLS and the proxy layer** | domain names |

**⭐ The proxy layer matters more than it looks** (Day 155): without a proxy in staging you never
exercise `forward-headers-strategy`, so `Secure` cookies and IP rate limiting break for the first
time in production.

**⭐ Staging that differs in the configuration mechanism proves nothing** — which is Day 142's whole
argument for one image promoted unchanged.

## ⭐ Secrets in the pipeline

```
⭐ Never in the repository, ⭐ never in the image, ⭐ never in build args (Day 282)
⭐ From the CI secret store or a cloud secret manager
⭐ MASKED in logs — ⭐ verify by echoing one deliberately and checking it is redacted
⭐ Rotatable — ⭐ and rotate one today to prove it
```

**⭐ Rotating a secret today is the exercise**: if rotation requires a code change or a manual step
nobody has documented, you have a secret you can never rotate — **which means a compromised one is
permanent** (Day 085).

## ⭐ The pipeline itself is a security boundary

```
⭐ Pin action/plugin versions by SHA        ← ⭐ Day 100A's supply chain
⭐ Least-privilege deploy credentials
⭐ ⭐ Require review for changes to the pipeline itself
```

**⭐ A pipeline with production credentials that anyone can modify is a production credential anyone
can exfiltrate.** Protecting the workflow files is as important as protecting `main`.

---

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Slow feedback first | the pipeline gets ignored |
| ⭐ `latest` tags | "which version is running?" is unanswerable |
| ⭐ **Migrations at application startup** | ⭐ instances contend; readiness times out; the deploy fails |
| ⭐ **No backward-compatibility check** | ⭐ expand/contract enforced by discipline alone |
| ⭐ No `lock_timeout` in migrations | ⭐ one slow query plus an `ALTER` takes the site down |
| ⭐ No pre-stop delay | ⭐ dropped requests on **every** deploy |
| ⭐ Smoke tests that only hit `/health` | a failed rollout looks green |
| ⭐ Not verifying the deployed SHA | the old version is still serving |
| ⭐ **Never practising rollback** | ⭐ a plan, not a capability |
| Dropping a column in the same deploy that stops using it | no rollback path |
| Long-lived feature flags | dead code with branches |
| ⭐ Staging without a proxy | forwarded-header bugs appear first in production |
| Secrets in build args or logs | permanent exposure |
| ⭐ Unpinned CI actions | supply-chain risk (Day 100A) |
| ⭐ An unprotected pipeline with deploy credentials | anyone can exfiltrate them |

## ⭐ Self-review

- [ ] ⭐ Stage 1 gives feedback in **under two minutes**
- [ ] ⭐ Images tagged by **SHA**; ⭐ `/actuator/info` reports it
- [ ] ⭐ **Migrations run as a separate step**, ⭐ with DDL-capable credentials the app lacks
- [ ] ⭐ `lock_timeout` in **every** migration
- [ ] ⭐ **CI verifies the old code works against the new schema**
- [ ] Rolling deploy with `maxUnavailable: 0`; ⭐ **a pre-stop delay**
- [ ] ⭐ Smoke tests include ⭐ **the SHA check** and ⭐ **a real end-to-end transaction**
- [ ] ⭐ **Rollback practised and timed**; the number recorded as part of RTO
- [ ] Feature flags available for risky changes
- [ ] ⭐ Staging matches production in engine, config mechanism, deploy method **and proxy layer**
- [ ] ⭐ Secrets masked — ⭐ **verified**; ⭐ **one rotated today**
- [ ] ⭐ CI actions pinned by SHA; ⭐ **the pipeline itself is review-protected**

## 🎤 Defence questions

1. **⭐ Walk me through your pipeline from commit to production.**
2. **⭐ Why do migrations run separately from application startup?**
3. **⭐ How do you know a migration is backward-compatible?**
4. **⭐ How long does a rollback take?** (⭐ you have measured this)
5. **⭐ When is a rollback *not* safe?**
6. **⭐ How do you know the deploy actually replaced the old version?**
7. **⭐ Where are your secrets, and when did you last rotate one?**
8. **⭐ What stops someone modifying the pipeline to steal your deploy credentials?**

## ✅ Done when

- ⭐ A commit reaches production automatically, gated by approval
- ⭐ **You have rolled back, and recorded the time**
- ⭐ The backward-compatibility check is in CI
- ⭐ A secret has been rotated end to end
