# Part 1 — L-021 · What deployment actually does

## The honest definition

**Deployment is: transform source code into artifacts, put those artifacts somewhere a server can
serve them, and make traffic point at the new ones instead of the old ones.**

Three steps. Everything else — Vercel, Docker, Kubernetes, CI/CD — is machinery around those three.

```
   SOURCE            BUILD              ARTIFACT           HOST            TRAFFIC
   ──────            ─────              ────────           ────            ───────
   .java   ──────▶  javac/gradle ──▶   app.jar    ──▶   a running    ──▶  DNS / LB
   .tsx    ──────▶  bundler      ──▶   static files ─▶   CDN / server      points here
   .css                               index.html
```

## The build step

**What "build" means:** turning what's convenient for humans into what's efficient for machines.

| Source | Build does | Artifact |
|---|---|---|
| Java | Compile to bytecode (Day 002), package with dependencies | `app.jar` — a zip of `.class` files + a manifest |
| TypeScript | Type-check, strip types, transpile | `.js` |
| JSX/React | Transform to `React.createElement` calls | `.js` |
| Many modules | **Bundle** — resolve imports, produce few files | `main-a3f9c2.js` |
| Everything | **Minify** — remove whitespace, shorten names | Smaller |
| Everything | **Tree-shake** — drop unreachable exports | Smaller |
| Assets | Hash filenames, optimise images | `logo-8fe21b.png` |

### The two ideas worth genuinely understanding

**1. Content hashing solves cache invalidation.**

```
   app.js            ← change it, and every CDN and browser still serves the old one
   app-a3f9c2.js     ← change it, and the hash changes, so it's a NEW URL
```

New content means a new URL, so the old cached entry is simply never requested again. No purge, no
waiting for TTL. That's why bundlers hash filenames, and why you can set
`Cache-Control: max-age=31536000, immutable` on those files with no risk.

`index.html` is the exception — it must *not* be cached long, because it's what points at the hashed
files. **Short-cache the HTML, forever-cache everything it references.** That single pattern is most
of frontend caching.

**2. A JAR is just a zip.**

```bash
unzip -l app.jar          # look inside — it's .class files and META-INF/MANIFEST.MF
```

A "fat JAR" (Spring Boot's default) bundles your classes *and* every dependency, plus an embedded
Tomcat, so `java -jar app.jar` runs a complete web server. No application server to install. That's
Day 144.

## Static hosting vs a server

**The distinction that determines your entire deployment model.**

| | Static hosting | Application server |
|---|---|---|
| Serves | Pre-built files as-is | Responses computed per request |
| Runs code? | No | Yes |
| State | None | Possibly |
| Scaling | Trivial — copy files | Harder — processes, memory |
| Cost | Near zero | Per running instance |
| Examples | S3, GitHub Pages, Vercel static | Tomcat, your Day 004 server |

**Static is dramatically cheaper and more reliable, because there's nothing to crash.** A file
either exists or doesn't.

This is why the industry moved toward pre-rendering. If a page's content doesn't change per user,
build it once at deploy time and serve a file. Which gives the rendering strategies:

| Strategy | Rendered | Good for |
|---|---|---|
| **SSG** | At build time | Blogs, docs, marketing — content that changes on deploy |
| **SSR** | Per request, on the server | Personalised or fresh-data pages |
| **CSR** | In the browser | App-like dashboards behind a login |
| **ISR** | At build, re-generated periodically | Product pages — mostly static, occasionally stale |

**Your Java backend is always an application server.** The frontend may be static. That's the normal
split: static assets on a CDN, API on a server.

## What "deploy to a server" actually involves

Your Day 004 server on your laptop is one process. Production adds:

```
   1. Get the artifact onto the machine        (scp, docker pull, CI push)
   2. Run it as a managed service              (systemd, Docker, ECS, Kubernetes)
      → restart on crash, start on boot, capture logs
   3. Put a reverse proxy in front             (Nginx, ALB — Day 018 C-12)
      → TLS termination, load balancing
   4. Health checks                            (liveness vs readiness — Day 018)
   5. Point DNS at it                          (Day 007)
   6. Deploy the NEXT version without downtime
```

### Step 6 is the hard one

| Strategy | How | Cost |
|---|---|---|
| **Recreate** | Stop old, start new | Downtime. Rarely acceptable. |
| **Rolling** | Replace instances one at a time | **Both versions live at once** |
| **Blue-green** | Full parallel environment, switch traffic | Double infrastructure, instant rollback |
| **Canary** | 5% of traffic to new, watch, ramp | Best safety, most machinery |

**"Both versions live at once" has a consequence people miss:** during a rolling deploy, requests hit
old *and* new code simultaneously. So a database migration must be compatible with both.

```
   ❌  Deploy that renames a column      → old instances query a column that's gone
   ✅  Two deploys:
       1. Add new column, write to both, read from old
       2. (deploy) Read from new
       3. Later: drop the old column
```

**This is the expand-contract pattern**, and it's why "never `drop column` in the same deploy that
stops using it" is on your architecture checklist. Now it has a mechanism behind it.

## Edge and CDN

Day 018's C-12 covered CDN caching. **Edge compute** is the newer idea: run *code* at those same
locations, not just serve cached files.

```
   Traditional:  user (Chennai) ──140ms──▶ origin (Oregon) ──▶ compute ──▶ response
   Edge:         user (Chennai) ──5ms──▶ edge (Chennai) ──▶ compute ──▶ response
```

Good at the edge: auth checks, redirects, A/B splits, geolocation, header rewriting, personalisation
of otherwise-static pages.

**Constraints:** no persistent connections to your database (the edge is nowhere near it), limited
runtime, short execution budget. Putting a database call at the edge usually makes things *slower* —
you've moved the compute close to the user and far from the data.

## What Vercel is actually doing

Since you use it, here's the demystified version:

```
   git push
      ↓
   Vercel clones the repo
      ↓
   Runs your build command       → static assets + serverless function bundles
      ↓
   Uploads static assets to its CDN (hashed filenames, immutable caching)
      ↓
   Deploys API routes as serverless functions
      ↓
   Assigns a unique immutable deployment URL
      ↓
   Atomically points your domain's alias at the new deployment
```

**Two things worth knowing:**

- **Rollback is instant** because old deployments still exist — it just re-points the alias. Nothing
  is rebuilt.
- **Serverless functions cold-start.** No traffic → no running process → the first request pays
  startup. This is the classic argument against serverless for a JVM app: JVM startup plus JIT warmup
  (Day 002) is genuinely slow, which is why Java on Lambda needs SnapStart or GraalVM native image.

```bash
# 1. A JAR is a zip
jar cf hello.jar *.class          # or use an existing Spring Boot jar
unzip -l hello.jar
unzip -p hello.jar META-INF/MANIFEST.MF

# 2. Watch caching behaviour differ by filename
curl -I https://cdnjs.cloudflare.com/ajax/libs/jquery/3.7.1/jquery.min.js | grep -i cache-control
# then any site's index.html
curl -I https://vercel.com | grep -i cache-control
```

Compare the two `Cache-Control` values. The hashed/versioned asset gets a year; the HTML gets
seconds or `no-cache`. **That's the pattern, observed in the wild.**

# no application code runs. Files in, files out.

## Interview questions

**Q: What actually happens when you deploy?**
> Source is built into artifacts — a JAR for Java, bundled and hashed static files for a frontend.
> Those artifacts are placed where they can be served: a CDN for static files, a running process
> behind a reverse proxy for the application. Then traffic is switched to the new version, usually
> via a rolling or blue-green strategy so there's no downtime.

**Q: Why do bundlers put hashes in filenames?**
> To make cache invalidation automatic. Changed content produces a different hash and therefore a
> different URL, so caches never serve stale content and the files can be cached indefinitely. The
> HTML that references them is short-cached instead.

**Q: What's the risk during a rolling deployment?**
> Both versions run simultaneously, so schema and API changes must be backward compatible for the
> duration. A migration that renames or drops a column breaks the instances still running old code.
> The fix is expand-contract: add the new thing, migrate reads and writes across separate deploys,
> and remove the old thing later.

**Q: When is serverless a poor fit for a JVM service?**
> When cold starts matter. A JVM must boot, load classes lazily and JIT-compile hot paths, so the
> first request after idle is significantly slower. Long-running containers avoid it; GraalVM native
> image or SnapStart mitigate it.
