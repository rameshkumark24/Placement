# L-024 · Reading bytecode

## Why bother

Because these questions all have the same answer — *look at the bytecode*:

- Why is `String` concatenation in a loop slow? *(Day 029)*
- Why does `Integer` caching make `==` work up to 127? *(Day 028)*
- Why does an enhanced `for` loop over a `List` throw `ConcurrentModificationException`? *(Day 052)*
- What does a lambda actually compile to? *(Day 057)*
- Why can't you overload on return type alone? *(Day 032)*

You don't need to write bytecode. You need to be able to **read it and answer a question with it.**
That's a genuinely uncommon skill and it shows.

## The JVM is a stack machine

Not a register machine. Almost all instructions push and pop an **operand stack**.

```java
int c = a + b;
```

```
   iload_1        push a            stack: [a]
   iload_2        push b            stack: [a, b]
   iadd           pop 2, push sum   stack: [a+b]
   istore_3       pop into c        stack: []
```

**Why a stack machine?** Because the JVM must run on CPUs with wildly different register counts.
A stack is a portable abstraction; the JIT maps it onto real registers later (Day 023).

Each method frame holds:
- **Local variable array** — parameters and locals, indexed from 0
- **Operand stack** — the working area above
- A reference to the runtime constant pool

**For an instance method, slot 0 is always `this`.** For a static method, slot 0 is the first
parameter. That single fact explains a lot of what you'll read.

## The instruction naming pattern

Prefixes tell you the type:

| Prefix | Type |
|---|---|
| `i` | int (also boolean, byte, char, short) |
| `l` | long |
| `f` | float |
| `d` | double |
| `a` | **reference** (object) |

```
   iload / istore     int  local variable
   aload / astore     reference local variable
   iadd, isub, imul, idiv
   iconst_0..5        push a small int constant (compact, 1 byte)
   bipush / sipush    push a byte-sized / short-sized constant
   ldc                push from the constant pool (larger values, Strings)
   getfield / putfield        instance field
   getstatic / putstatic      static field
   invokevirtual      instance method — virtual dispatch
   invokestatic       static method
   invokespecial      constructor, private, super
   invokeinterface    interface method
   invokedynamic      lambdas, string concat (modern) — resolved at runtime
   new                allocate (does NOT run the constructor)
   dup                duplicate top of stack
   return / ireturn / areturn
```

**Learn the five `invoke*` instructions.** Which one the compiler chooses tells you exactly how
dispatch works, and that's Day 038's polymorphism question answered mechanically.

## Read your first method

```java
public class Simple {
    public int add(int a, int b) {
        int sum = a + b;
        return sum;
    }
}
```

```bash
javac Simple.java
javap -c Simple
```

```
  public int add(int, int);
    Code:
       0: iload_1        // slot 0 = this, slot 1 = a
       1: iload_2        // slot 2 = b
       2: iadd
       3: istore_3       // slot 3 = sum
       4: iload_3
       5: ireturn
```

Add `-v` for the full picture — constant pool, stack depth, local slot count:

```bash
javap -c -v Simple
```

```
  descriptor: (II)I           ← two ints in, int out
  stack=2, locals=4, args_size=3      ← args_size 3 because `this` counts
```

**`stack=2, locals=4`** — the JVM knows the exact maximum operand stack depth and local slot count
before running. That's part of what verification checks (Day 023).

## Five things worth decompiling

### 1. String concatenation — the `+=` in a loop trap

```java
public String bad(String[] parts) {
    String s = "";
    for (String p : parts) s += p;
    return s;
}
```

`javap -c` shows, **inside the loop**:

```
  invokedynamic #x, 0   // makeConcatWithConstants   ← a NEW concat per iteration
```

On Java 8 you'd see an explicit `new StringBuilder` / `append` / `toString` **inside the loop body**.
Either way, the allocation happens **every iteration** — O(n²) copying.

```java
public String good(String[] parts) {
    StringBuilder sb = new StringBuilder();
    for (String p : parts) sb.append(p);
    return sb.toString();
}
```

One builder, appended n times. **Now decompile both and see the difference for yourself** — this is
Day 029, pre-answered.

### 2. `new` doesn't construct

```java
Object o = new Object();
```

```
   new  #2       // allocate raw memory, push reference
   dup           // duplicate it (one for the constructor, one to store)
   invokespecial #1   // <init>  ← THE CONSTRUCTOR RUNS HERE
   astore_1
```

**Allocation and construction are two separate instructions.** `dup` exists because
`invokespecial` consumes a reference — you need a second copy to actually keep.

This is why a half-constructed object can leak if you publish `this` from a constructor, and it
underpins a subtle safe-publication issue in the memory model (Day 065).

### 3. Which `invoke` for which call

```java
class Parent { void method() {} }
class Child extends Parent {
    static void stat() {}
    private void priv() {}
    void test() {
        stat();                     // invokestatic
        priv();                     // invokespecial  (private = not virtual)
        method();                   // invokevirtual  (virtual dispatch)
        super.method();             // invokespecial  (explicit, bypasses dispatch)
        Runnable r = () -> {};      // invokedynamic
        r.run();                    // invokeinterface
    }
}
```

**`super.method()` compiles to `invokespecial`, not `invokevirtual`.** That's exactly why `super`
calls don't dispatch back to the override — a mechanical answer to a question people usually answer
with hand-waving.

### 4. What a lambda actually is

```java
Runnable r = () -> System.out.println("hi");
```

```
   invokedynamic #2,  0   // run:()Ljava/lang/Runnable;
```

**Not an anonymous class.** `invokedynamic` defers the decision to runtime, where
`LambdaMetafactory` generates an implementation the first time it's reached.

Why it matters: a lambda that captures nothing can be **reused as a singleton** rather than
allocated per call — cheaper than the anonymous inner class it replaced. Day 057.

### 5. The enhanced for loop

```java
for (String s : list) { use(s); }
```

```
   invokeinterface  java/util/List.iterator
   ...
   invokeinterface  java/util/Iterator.hasNext
   invokeinterface  java/util/Iterator.next
```

**It's an `Iterator`, desugared.** Which is precisely why modifying the collection inside the loop
throws `ConcurrentModificationException` — the iterator's `modCount` check fires. Day 052, answered
today.

(Over an array, it compiles to a plain indexed loop with no iterator at all.)

## Method descriptors

You'll see these constantly in stack traces and reflection output:

```
   (II)I                          (int, int) → int
   ()V                            () → void
   (Ljava/lang/String;)V          (String) → void
   ([Ljava/lang/String;)V         (String[]) → void          ← main's descriptor
   (Ljava/util/List;)Ljava/lang/String;   (List) → String
```

| Code | Type |
|---|---|
| `B S I J F D C Z` | byte, short, int, **long**, float, double, char, boolean |
| `V` | void |
| `L<class>;` | reference |
| `[` | array (prefix) |

**`J` is long and `Z` is boolean** — the two that catch people. `L` was taken by "class", so long got
`J`.

**Why this matters:** the return type is part of the descriptor but **not** part of a method's
signature for overloading purposes — which is exactly why you can't overload on return type alone.
Two methods differing only in return type would have distinct descriptors but the compiler forbids
it because call sites couldn't disambiguate.

## Type this yourself

```java
public class Decompile {

    public String concatBad(String[] parts) {
        String s = "";
        for (String p : parts) s += p;      // decompile this loop
        return s;
    }

    public String concatGood(String[] parts) {
        StringBuilder sb = new StringBuilder();
        for (String p : parts) sb.append(p);
        return sb.toString();
    }

    public void allocate() {
        Object o = new Object();            // find new / dup / invokespecial
    }

    public int ternary(int a, int b) {
        return a > b ? a : b;               // find the branch instructions
    }

    public void switchOnInt(int x) {        // tableswitch or lookupswitch?
        switch (x) { case 1: case 2: case 3: break; default: break; }
    }

    public void switchOnSparse(int x) {     // now compare with sparse cases
        switch (x) { case 1: case 100: case 10000: break; default: break; }
    }

    public void loop(java.util.List<String> list) {
        for (String s : list) { }           // find the iterator calls
    }

    public Runnable lambda() {
        return () -> System.out.println("x");   // invokedynamic
    }
}
```

```bash
javac Decompile.java
javap -c Decompile              # bytecode
javap -c -v Decompile           # + constant pool, stack/locals
javap -p -c Decompile           # include private members
```

**Four things to hunt for:**

1. **`concatBad` vs `concatGood`** — find the allocation inside the loop in one and not the other.
2. **`switchOnInt` vs `switchOnSparse`** — one emits `tableswitch` (a jump table, O(1)), the other
   `lookupswitch` (a binary search, O(log n)). **The compiler chooses based on case density.** Nice
   detail to have.
3. **`allocate`** — confirm `new`, `dup`, `invokespecial` are three separate instructions.
4. **`lambda`** — confirm `invokedynamic`, and note there's no anonymous class file generated
   (`ls *.class` — no `Decompile$1.class`).

## Common mistakes

| Mistake | Correction |
|---|---|
| "Bytecode is machine code" | It targets the JVM's abstract stack machine, not a CPU. |
| Assuming the JVM has registers | It's a stack machine. The JIT maps to registers later. |
| Thinking `new` runs the constructor | `new` allocates; `invokespecial` on `<init>` constructs. |
| "Lambdas are anonymous classes" | They're `invokedynamic`, resolved at runtime by `LambdaMetafactory`. |
| Expecting `javap` to show source | Use `-c` for bytecode. Source comes from `-g` debug info. |
| Confusing descriptor codes | `J` is long, `Z` is boolean. |

## Interview questions

**Q: What is bytecode and why is the JVM a stack machine?**
> Bytecode is the JVM's instruction set — a portable intermediate representation produced by `javac`.
> The JVM is a stack machine because it must run on CPUs with different register architectures; an
> operand stack is a portable abstraction, and the JIT maps it onto real registers at compile time.

**Q: Why is string concatenation in a loop slow?**
> Strings are immutable, so each `+=` creates a new object. Decompiling shows a fresh concatenation —
> `invokedynamic` on modern Java, a new `StringBuilder` on Java 8 — inside the loop body, making it
> quadratic in copying. A single `StringBuilder` outside the loop is linear.

**Q: Why does `super.method()` not dispatch to an override?**
> It compiles to `invokespecial` rather than `invokevirtual`. `invokespecial` resolves the target at
> compile time rather than dispatching on the runtime type, which is exactly what makes it usable for
> constructors, private methods and `super` calls.

**Q: What does a lambda compile to?**
> An `invokedynamic` instruction, not an anonymous inner class. The bootstrap method
> `LambdaMetafactory` generates the implementation class at runtime on first execution. Non-capturing
> lambdas can then be reused as a singleton rather than allocated each time.

**Q: Why can't you overload methods on return type alone?**
> The return type is part of the bytecode descriptor but not part of the signature used for overload
> resolution. A call site discarding the result couldn't disambiguate, so the language forbids it.

**Q: `tableswitch` vs `lookupswitch`?**
> `tableswitch` is a jump table used when case values are dense — constant-time dispatch.
> `lookupswitch` is a sorted key list searched in logarithmic time, used when cases are sparse. The
> compiler chooses based on the density of the case values.

## 🎙️ Articulation drill

Two minutes: **"Why is string concatenation in a loop slow in Java?"**

Answer it with the bytecode. *"Strings are immutable, so each concatenation allocates. If you
decompile it you can see the allocation inside the loop body — which makes the copying quadratic.
Hoisting a StringBuilder out makes it linear."* Proving it from the emitted code is far stronger than
asserting it.
