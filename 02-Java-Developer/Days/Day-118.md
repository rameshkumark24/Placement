# Day 118

**L-118** · Authorization models — RBAC, ABAC, ACLs, multi-tenancy

**Time:** 3 hrs · **Mode:** NEW

> Day 111 introduced the models in outline. Today is the design work: how permission is actually

# Part 1 — RBAC

```
User ──► Role ──► Permission
alice ─► ADMIN ─► [orders:read, orders:write, users:manage]
bob   ─► VIEWER ► [orders:read]
```

```sql
CREATE TABLE role       (id, name);
CREATE TABLE permission (id, name);                        -- 'orders:write'
CREATE TABLE role_permission (role_id, permission_id, PRIMARY KEY (role_id, permission_id));
CREATE TABLE user_role       (user_id, role_id,       PRIMARY KEY (user_id, role_id));
```

**Check permissions, not roles.** This is the single most valuable RBAC design rule:

```java
// ❌ brittle — every new role means editing every check
if (user.hasRole("ADMIN") || user.hasRole("MANAGER")) { … }

// ✅ roles are a grouping mechanism; permissions are the contract
if (user.hasPermission("orders:write")) { … }
```

With permission checks, adding a `SUPPORT_LEAD` role is a data change. With role checks, it is a
code change across every call site — and someone will miss one.

**Role hierarchy** is worth having: `ADMIN` implies `MANAGER` implies `USER`, so permissions are
inherited rather than duplicated. Keep it shallow — deep hierarchies become impossible to reason
about.

Naming convention: `resource:action` (`orders:read`, `users:manage`). Consistent, greppable, and it
maps directly onto OAuth scopes (Day 116).

**Where RBAC breaks:** every rule that depends on the *specific object*.

> *"A manager may approve expenses — but not their own."*
> *"A doctor may read patient records — but only for their own patients."*
> *"A user may edit a document — if they own it, or it was shared with them."*

No set of roles expresses these, because the answer depends on the relationship between the subject
and *this* resource. That is what the next two models are for.

# Part 2 — ABAC

A **policy** evaluated over attributes of the subject, resource, action and environment.

```
PERMIT when
    subject.department == resource.department
    AND subject.clearance >= resource.classification
    AND action == "read"
    AND environment.time BETWEEN 09:00 AND 18:00
    AND environment.ip IN corporate_ranges
```

```java
public interface Policy { Decision evaluate(Subject s, Resource r, Action a, Environment e); }
```

| | ABAC |
|---|---|
| ✅ | Expressive; handles ownership and context; policies change without code changes |
| ❌ | **Hard to audit** — "who can see this document?" requires evaluating every policy against every user; harder to test; policies can conflict |

That auditability weakness is the real cost. RBAC answers "who can do X?" with a query. ABAC answers
it with a search.

**Policy as code** is how ABAC is done seriously — Open Policy Agent with Rego, AWS IAM policies,
Cedar:

```rego
package authz
default allow = false

allow {
    input.action == "read"
    input.resource.owner == input.subject.id
}

allow {
    input.action == "read"
    input.subject.roles[_] == "auditor"
    input.resource.classification != "secret"
}
```

The value is that policy lives outside the application, is versioned and reviewed independently, and
is evaluated identically by every service.

# Part 3 — ReBAC and ACLs

## ACLs — a list per object

```sql
CREATE TABLE acl (resource_type, resource_id, principal_type, principal_id, permission);
-- ('document', 42, 'user',  17,   'read')
-- ('document', 42, 'group', 'eng','write')
```

Simple and precise. It scales poorly for questions like "every document alice can read", and it does
not express inheritance without extra work.

## ⭐ ReBAC — permission from relationships

Google's **Zanzibar** paper is the reference design, and it is what OpenFGA, SpiceDB and Auth0 FGA
implement.

```
document:readme#owner@user:alice          alice owns readme
folder:specs#viewer@group:eng#member      every member of eng views specs
document:readme#parent@folder:specs       readme is inside specs

⇒ anyone in eng can view readme, via inheritance
```

The authorization question becomes a **graph reachability** query: *is there a path from this user to
this permission on this object?*

**This is the right model when the domain is genuinely relational** — document sharing (Google Docs,
Dropbox), nested resource hierarchies, "anyone with the link", organisation-based access, and
transitive group membership. Trying to express those in RBAC produces a combinatorial explosion of
roles.

The cost is a dedicated authorization service and a new consistency problem: the permission graph and
your application data can disagree during updates. Zanzibar solves it with **zookies** — consistency
tokens that let a caller demand a snapshot at least as fresh as a known write.

## Choosing

```
Fixed permissions, few roles                      → RBAC
Permissions depend on the object's owner           → RBAC + ownership checks   ← most systems
Permissions depend on many attributes or context   → ABAC (policy as code)
Permissions flow through relationships and sharing → ReBAC
Regulatory, per-object, explicit                   → ACL
```

> **Start with RBAC plus ownership checks.** That is the correct answer for the large majority of
> systems, and adding models you do not need is Day 092's YAGNI.

# Part 4 — Where the decision is made

The standard vocabulary, worth knowing because it appears in every authorization product:

```
PEP  Policy Enforcement Point   — intercepts and enforces      (your middleware/annotation)
PDP  Policy Decision Point      — decides                       (your service or OPA)
PIP  Policy Information Point   — supplies attributes           (user service, resource store)
PAP  Policy Administration Point— where policies are authored
```

```java
// PEP
if (!authz.check(user, "orders:write", order)) throw new ForbiddenException();
```

**Centralise the decision, distribute the enforcement.** One `AuthorizationService` that every
endpoint consults means the logic is testable, auditable and changeable in one place — rather than
being scattered as ad-hoc `if` statements that drift apart.

## The three enforcement patterns

```java
// 1. Check after fetch — the obvious one, and the one that gets forgotten
Order o = repo.findById(id).orElseThrow();
if (!authz.canRead(user, o)) throw new NotFoundException();

// 2. Scoped query — the check CANNOT be forgotten (Day 105, Day 111)
Order o = repo.findByIdAndCustomerId(id, user.id()).orElseThrow(NotFoundException::new);

// 3. Row-level security — enforced by the DATABASE, below all application code
```

**Pattern 2 is the default you should reach for**, and pattern 3 is what you add when the consequence
of a mistake is cross-tenant data exposure.

## Filtering lists is the hard case

Checking one object is easy. Returning "every order this user may see" is where authorization gets
architecturally difficult:

```java
// ❌ fetch everything, filter in memory — correct, and it does not scale
repo.findAll().stream().filter(o -> authz.canRead(user, o)).toList();

// ✅ push the predicate into the query
repo.findAllVisibleTo(user.id(), user.tenantId(), pageable);
```

**This is the reason complex authorization models are hard in practice** — an ABAC policy that is
trivial to evaluate for one object may be impossible to express as a SQL predicate. It is also why
ReBAC systems provide a "list objects" API that returns the ids a user can access, which you then
join against.

# Part 5 — Multi-tenancy

**The isolation model is the single most important architectural decision in a SaaS product**, and it
is close to impossible to change later.

| Model | Isolation | Cost | Noisy neighbour |
|---|---|---|---|
| **Separate database per tenant** | ✅ strongest | ❌ high — N databases to migrate, back up, monitor | ✅ isolated |
| **Separate schema per tenant** | ✅ strong | ⚠️ moderate; migrations across N schemas | ⚠️ shared resources |
| **Shared schema, `tenant_id` column** | ⚠️ **application-enforced** | ✅ lowest | ❌ shared |
| **Hybrid** — shared by default, dedicated for large customers | ✅ | ⚠️ two code paths | ✅ where it matters |

**Shared schema is what most SaaS products use**, because the operational cost of the others is
brutal at scale. It is also the one where a single missing `WHERE` clause is a breach.

## Making shared-schema isolation safe

**Defence in depth, and every layer is worth having:**

```java
// 1. tenant from the AUTHENTICATED principal, never from a request parameter (Day 108)
TenantId tenant = principal.tenantId();

// 2. bound to the request, not passed through every signature
TenantContext.set(tenant);          // ThreadLocal — Day 066A, CLEARED in a finally

// 3. every repository method takes it — no unscoped method exists
List<Order> findByTenantId(TenantId tenant, …);

// 4. ⭐ database ROW-LEVEL SECURITY — enforced below all application code
```

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;          -- applies to the table owner too

CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- per connection, at checkout from the pool:
SET LOCAL app.tenant_id = '…';
```

> **Row-level security is the layer that makes a forgotten `WHERE` clause harmless.** Every query on
> that connection is silently filtered by the database, whatever the application wrote. For a
> shared-schema SaaS product it is close to mandatory.

Two implementation cautions: **use `SET LOCAL` inside a transaction** so the setting cannot leak to
the next user of a pooled connection (Day 066A's leak, in SQL form), and remember `FORCE ROW LEVEL
SECURITY` — otherwise the table owner bypasses the policy entirely, and your application user often
*is* the owner.

## The other tenancy details

- **Composite indexes must lead with `tenant_id`** — `(tenant_id, created_at)`, because every query
  filters on it (Day 110's leftmost-prefix rule).
- **Unique constraints are per tenant:** `UNIQUE (tenant_id, email)`, not `UNIQUE (email)`.
- **Cache keys must include the tenant** — `orders:{tenantId}:{id}`. A cache key without it is a
  cross-tenant leak that no `WHERE` clause can prevent (Day 120).
- **Rate limits per tenant** (Day 122), so one customer cannot exhaust shared capacity.
- **Background jobs and exports** must carry tenant context explicitly — they run outside the request
  where the `ThreadLocal` does not exist (Day 066A).
- **Test cross-tenant access deliberately.** Every integration test suite should contain a test that
  authenticates as tenant A and asserts it cannot read tenant B's row.

That last point deserves emphasis: **the cross-tenant test is the single highest-value test in a
multi-tenant product.** Write it for every resource.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Checking roles instead of permissions | Every new role is a code change across all call sites |
| Deep role hierarchies | Nobody can reason about effective permissions |
| ABAC when RBAC suffices | Unauditable; "who can see this?" becomes unanswerable |
| Authorization logic scattered across controllers | Drifts; cannot be audited or tested |
| Fetch-then-check as the default | The check gets forgotten |
| Filtering lists in application memory | Correct and unscalable |
| Tenant id from a request parameter | Trivial cross-tenant access |
| Shared schema with no row-level security | One missing `WHERE` is a breach |
| RLS without `FORCE` | The owner — often your app user — bypasses it |
| `SET` instead of `SET LOCAL` | Tenant setting leaks across pooled connections |
| Indexes not leading with `tenant_id` | Every query scans more than it should |
| Global unique constraints | Two tenants cannot both have `admin@…` |
| Cache keys without the tenant | Cross-tenant leak through the cache |
| Background jobs without tenant context | Operating on the wrong tenant, or all of them |
| No cross-tenant test | The most important isolation property is unverified |

## Interview questions

**Q: RBAC vs ABAC vs ReBAC?**
RBAC assigns permissions via roles — simple and auditable, but cannot express object-specific rules.
ABAC evaluates a policy over subject, resource, action and environment attributes — expressive but
hard to audit. ReBAC derives permission from a relationship graph, which is right for sharing and
nested hierarchies. Most systems want RBAC plus ownership checks.

**Q: Why check permissions rather than roles?**
Roles are a grouping mechanism that changes; permissions are the contract. Checking permissions means
adding a role is a data change rather than an edit to every call site.

**Q: Where does RBAC break down?**
Any rule that depends on the specific object — "a manager may approve expenses but not their own",
"a doctor may read their own patients' records". No role set expresses a subject-to-object
relationship.

**Q: How do you implement multi-tenancy?**
Usually a shared schema with a `tenant_id` column, with the tenant taken from the authenticated
principal and never from a parameter, every repository method scoped, and **row-level security in the
database** so a forgotten `WHERE` clause cannot leak data. Separate databases give stronger isolation
at much higher operational cost.

**Q: What is row-level security and why does it matter?**
A database policy that filters every query on a table by a session variable, enforced below all
application code. In a shared-schema SaaS product it converts "one missing `WHERE` clause is a
breach" into "one missing `WHERE` clause returns nothing".

**Q: What is the hardest part of authorization?**
Filtering collections. Checking one object is easy; returning "every object this user may see"
requires pushing the policy into the query, which a rich attribute-based policy may not express as
SQL. That is why ReBAC systems provide a list-objects API.

**Q: Name three multi-tenancy details people forget.**
Cache keys must include the tenant, unique constraints must be per tenant, and background jobs must
carry tenant context explicitly because they run outside the request.

## 🎙️ Articulation drill

Two minutes: **"How would you design authorization for a multi-tenant SaaS product?"**

RBAC with permission-based checks plus ownership, tenant from the authenticated principal and never
from a parameter, scoped repository methods so the unsafe query does not exist, row-level security in
the database as the layer that survives a mistake, and tenant-aware cache keys and background jobs.
Close with the cross-tenant test as the thing you would write first — because the property that
matters most is the one you must verify continuously.
