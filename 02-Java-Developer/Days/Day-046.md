# L-046 · `ArrayList`

## What it is

**A resizable array.** That's the whole idea — an `Object[]` plus a size counter, reallocated when it
fills.

```java
public class ArrayList<E> {
    transient Object[] elementData;      // the backing array
    private int size;                     // number of elements USED, not array length
}
```

**`size` and `capacity` are different**, and conflating them is a common misunderstanding:

```
   elementData: [ a │ b │ c │   │   │   │   │   │   │   ]
                 └───── size = 3 ─────┘
                 └────────── capacity = 10 ───────────┘
```

`size()` returns 3. There is no public way to read the capacity.

## Growth — the 1.5× factor

```java
private Object[] grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);    // 1.5×
    return elementData = Arrays.copyOf(elementData, newCapacity);
}
```

**`oldCapacity >> 1` is a right shift — divide by two.** So new capacity is old × 1.5.

```
   default 10 → 15 → 22 → 33 → 49 → 73 → 109 → 163 → ...
```

**Why 1.5 and not 2?**

| Factor | Trade-off |
|---|---|
| **2×** | Fewer reallocations; but the freed blocks are always smaller than the next request, so they can never be reused — memory fragmentation |
| **1.5×** | Slightly more copies; **freed blocks can eventually be coalesced and reused** |

**With 1.5×, the sum of all previously freed blocks eventually exceeds the next request**, so the
allocator can reuse that space. With 2× it never can. That's the actual reason, and it's a good
detail — most people just say "it's 1.5, or maybe 2".

*(C++'s `std::vector` typically uses 2× in libstdc++ and 1.5× in MSVC, for exactly this debated
reason.)*

## Amortised O(1) — the important idea

Adding to the end is *usually* O(1), and occasionally O(n) when it grows. The **average over n
additions is O(1)**.

**The proof, in one line:** growing by a constant *factor* means the total copying across n additions
is a geometric series — `n + n/1.5 + n/2.25 + …` which sums to about 3n. So n additions cost O(n)
total, hence O(1) each.

**Contrast with growing by a fixed amount:**

```
   grow by 10 each time:  10 + 20 + 30 + … + n  =  O(n²) total  →  O(n) per add
```

**Constant-factor growth is what makes amortised O(1) possible.** That's the answer to "why does the
growth factor matter", and it's the same argument behind `HashMap` doubling (Day 048).

## Cost per operation

| Operation | Cost | Why |
|---|---|---|
| `get(i)` / `set(i, e)` | **O(1)** | Address arithmetic (Day 031) |
| `add(e)` at end | **O(1) amortised** | Usually a write; occasionally a copy |
| `add(0, e)` at front | **O(n)** | Shifts every element right |
| `remove(i)` | **O(n)** | Shifts everything after `i` left |
| `remove(last)` | O(1) | Nothing to shift |
| `contains(o)` / `indexOf(o)` | **O(n)** | Linear scan |
| `size()`, `isEmpty()` | O(1) | A field |

**The shifting is `System.arraycopy`** (Day 031) — a JVM intrinsic that compiles to an optimised
native memory move, often SIMD. So O(n) here has a very small constant. Removing from the front of a
100,000-element `ArrayList` is O(n), but it's a single bulk memory move, not a loop.

**That matters for the `LinkedList` comparison tomorrow** — `ArrayList`'s O(n) is fast, and
`LinkedList`'s O(1) requires an O(n) traversal to reach.

```java
public E remove(int index) {
    E old = elementData(index);
    int numMoved = size - index - 1;
    if (numMoved > 0)
        System.arraycopy(elementData, index + 1, elementData, index, numMoved);
    elementData[--size] = null;        // ← null it out, or you LEAK the object
    return old;
}
```

**Note `elementData[--size] = null`.** Without it the array would keep a reference to a removed
element, keeping it alive (Day 027's leak patterns). A small detail that shows the JDK authors were
careful.

## Pre-sizing

```java
List<String> list = new ArrayList<>();            // capacity 10 on first add
List<String> list = new ArrayList<>(100_000);     // ✅ one allocation, no growth
```

**If you know the size, say so.** Building a 1,000,000-element list from the default capacity means
roughly 30 reallocations and about 3,000,000 element copies — all avoidable.

**`ensureCapacity(n)`** does the same for an existing list.

**Note the lazy default:** `new ArrayList<>()` doesn't allocate an array at all until the first
`add` — it uses a shared empty array constant. So an empty `ArrayList` is genuinely cheap, which
matters when you create many.

## Memory

| | `ArrayList<Integer>` (1M) | `int[]` (1M) |
|---|---|---|
| Array of references | ~4–8 MB | — |
| The `Integer` objects | ~16 MB | — |
| Total | **~20–24 MB** | **4 MB** |

**Five to six times the memory**, plus scattered layout that defeats the cache (Day 001). That's the
argument for `IntStream`, primitive-specialised collections (Eclipse Collections, fastutil), and
eventually Project Valhalla.

## `SubList` — a view, and a trap

```java
List<String> sub = list.subList(2, 5);
sub.set(0, "x");           // modifies the ORIGINAL list
sub.clear();               // removes those elements from the ORIGINAL

list.add("new");           // structurally modifies the parent...
sub.get(0);                // 💥 ConcurrentModificationException
```

**`subList` returns a live view, not a copy** — same trap family as `Arrays.asList` (Day 031) and
`unmodifiableList` (Day 034A). Structurally modifying the parent invalidates the sublist.

**To copy:** `new ArrayList<>(list.subList(2, 5))`.

## Type this yourself

```java
import java.lang.reflect.Field;
import java.util.*;

public class ArrayListDemo {

    // Read the private capacity via reflection (Day 056A previews this properly)
    static int capacityOf(ArrayList<?> list) throws Exception {
        Field f = ArrayList.class.getDeclaredField("elementData");
        f.setAccessible(true);
        return ((Object[]) f.get(list)).length;
    }

    public static void main(String[] args) throws Exception {

        // ---- 1. Watch the growth sequence ----
        System.out.println("--- capacity growth (1.5×) ---");
        ArrayList<Integer> list = new ArrayList<>();
        int lastCap = -1;
        for (int i = 0; i < 200; i++) {
            list.add(i);
            int cap = capacityOf(list);
            if (cap != lastCap) {
                System.out.printf("   size %3d → capacity %3d%n", list.size(), cap);
                lastCap = cap;
            }
        }

        // ---- 2. Pre-sizing ----
        int n = 3_000_000;
        long start = System.currentTimeMillis();
        List<Integer> grown = new ArrayList<>();
        for (int i = 0; i < n; i++) grown.add(i);
        long grownTime = System.currentTimeMillis() - start;

        start = System.currentTimeMillis();
        List<Integer> presized = new ArrayList<>(n);
        for (int i = 0; i < n; i++) presized.add(i);
        long presizedTime = System.currentTimeMillis() - start;

        System.out.printf("%n--- building %,d elements ---%n", n);
        System.out.printf("   default capacity: %,4d ms%n", grownTime);
        System.out.printf("   pre-sized:        %,4d ms%n", presizedTime);

        // ---- 3. add at front vs end ----
        int m = 100_000;
        List<Integer> front = new ArrayList<>();
        start = System.currentTimeMillis();
        for (int i = 0; i < m; i++) front.add(0, i);          // O(n) each → O(n²)
        long frontTime = System.currentTimeMillis() - start;

        List<Integer> end = new ArrayList<>();
        start = System.currentTimeMillis();
        for (int i = 0; i < m; i++) end.add(i);               // O(1) amortised
        long endTime = System.currentTimeMillis() - start;

        System.out.printf("%n--- inserting %,d elements ---%n", m);
        System.out.printf("   add(0, e) at front: %,5d ms   ← O(n²)%n", frontTime);
        System.out.printf("   add(e)    at end:   %,5d ms   ← O(n)%n", endTime);

        // ---- 4. subList is a VIEW ----
        System.out.println("\n--- subList is a live view ---");
        List<String> words = new ArrayList<>(List.of("a", "b", "c", "d", "e"));
        List<String> sub = words.subList(1, 4);
        sub.set(0, "CHANGED");
        System.out.println("   parent after sub.set: " + words);
        sub.clear();
        System.out.println("   parent after sub.clear: " + words);

        List<String> words2 = new ArrayList<>(List.of("a", "b", "c", "d", "e"));
        List<String> view = words2.subList(1, 4);
        words2.add("f");
        try { view.get(0); }
        catch (ConcurrentModificationException e) {
            System.out.println("   parent modified → sublist throws CME");
        }
    }
}
```

**Three things to record:**

1. **The growth sequence** — 10, 15, 22, 33, 49… Each is the previous × 1.5, rounded down.
2. **Pre-sizing wins**, sometimes substantially, purely by avoiding reallocation and copying.
3. **Front insertion is dramatically slower** — O(n²) versus O(n). This is the number to quote
   tomorrow when comparing with `LinkedList`.

## Common mistakes

| Mistake | Correction |
|---|---|
| Confusing `size()` with capacity | `size` is elements used; capacity is array length, and is not exposed. |
| Not pre-sizing a known-size list | Roughly 30 reallocations and 3M copies for a 1M list. |
| `add(0, e)` in a loop | O(n²). Use `ArrayDeque`, or add at the end and reverse. |
| `list.contains()` in a loop | O(n²). Use a `HashSet` (Day 045). |
| Treating `subList` as a copy | It's a live view; structural changes to the parent invalidate it. |
| `remove(Object)` vs `remove(int)` on a `List<Integer>` | `list.remove(1)` removes **index** 1. `list.remove(Integer.valueOf(1))` removes the value. |
| Using `ArrayList` for a queue | Front removal is O(n). Use `ArrayDeque`. |

**That `remove` overload is a genuine trap** — Day 032's overload resolution picking `remove(int)`
over `remove(Object)` because widening beats boxing.

## Interview questions

**Q: How does `ArrayList` work internally?**
> It wraps an `Object[]` plus a size counter. When the array fills, it allocates a new one at 1.5×
> the capacity and copies via `System.arraycopy`. Indexed access is O(1) address arithmetic; insertion
> and removal in the middle are O(n) because elements must be shifted.

**Q: What's the growth factor and why?**
> 1.5×, computed as `oldCapacity + (oldCapacity >> 1)`. Growing by a constant factor is what makes
> appends amortised O(1) — the total copying across n appends is a geometric series summing to about
> 3n. 1.5 rather than 2 because with 1.5 the previously freed blocks eventually sum to more than the
> next request, so the allocator can reuse them; with doubling they never can.

**Q: What does amortised O(1) mean here?**
> Most appends are a single array write, and occasionally one triggers an O(n) copy. Averaged over n
> appends the cost per operation is constant, because the total work is O(n). It depends on growing by
> a factor — growing by a fixed increment would make the total O(n²).

**Q: Why is removing from the middle O(n) but still fast?**
> Every subsequent element shifts left, which is linear in the number moved — but it's done with
> `System.arraycopy`, a JVM intrinsic that becomes an optimised native block move, so the constant
> factor is very small compared to pointer chasing.

**Q: What's the difference between `list.remove(1)` and `list.remove(Integer.valueOf(1))`?**
> The first calls `remove(int index)` and removes the element at index 1. The second calls
> `remove(Object)` and removes the first element equal to 1. Overload resolution prefers the exact
> `int` match over boxing, which surprises people working with a `List<Integer>`.
