# L-035 · Classes and construction

## Class vs object

**A class is a template. An object is an instance of it, living on the heap** (Day 025).

```java
class Dog { String name; }         // the template — metadata in Metaspace
Dog d = new Dog();                 // the object — bytes on the heap
```

Day 024 showed you what `new Dog()` compiles to:

```
   new          #2      // allocate raw memory, zero-initialised, push the reference
   dup                  // duplicate the reference
   invokespecial #3     // <init> — THE CONSTRUCTOR RUNS HERE
   astore_1
```

**Allocation and construction are two separate steps.** That fact drives most of today.

## What a constructor is — and isn't

```java
class User {
    private final String name;

    public User(String name) { this.name = name; }    // constructor
}
```

| | Constructor | Method |
|---|---|---|
| Name | Same as the class | Anything |
| Return type | **None** — not even `void` | Required |
| Inherited | ❌ | ✅ |
| Overridable | ❌ | ✅ |
| Called | Only via `new` (or `super`/`this`) | Directly |

**The trap:**

```java
class User {
    void User() { }         // ⚠️ this is a METHOD named User, not a constructor
}
```

It compiles. It is never called by `new`. The class silently gets a default constructor instead, and
your initialisation never runs. **A return type turns a constructor into a method** — a real bug
that's hard to spot because it looks correct.

## The default constructor

**If you declare no constructor, the compiler inserts a no-arg one.** If you declare *any*
constructor, it does not.

```java
class A { }                                   // gets A() automatically
class B { B(String s) { } }                   // NO no-arg constructor
new B();                                      // ❌ compile error
```

**This breaks things silently.** Frameworks that instantiate reflectively — JPA/Hibernate, Jackson —
require a no-arg constructor. Add a parameterised one to an entity and Hibernate fails at runtime
with a confusing error. That's why JPA entities conventionally declare an explicit
`protected NoArgs() {}`.

## `this`

Three uses, all common:

```java
class Point {
    private int x, y;

    Point(int x, int y) {
        this.x = x;                    // 1. disambiguate field from parameter
        this.y = y;
    }

    Point() {
        this(0, 0);                    // 2. constructor chaining — MUST be the first statement
    }

    Point moveTo(int x, int y) {
        this.x = x; this.y = y;
        return this;                   // 3. return the current instance (fluent APIs)
    }
}
```

**`this(...)` must be the first statement** in a constructor — you cannot call another constructor
after doing work, because the object must be fully initialised in one defined order.

**Same rule for `super(...)`**, and you can't have both — one or the other, first line.

## Constructor chaining — the telescoping pattern

```java
class Pizza {
    private final String size;
    private final boolean cheese, pepperoni;

    Pizza(String size)                     { this(size, false, false); }
    Pizza(String size, boolean cheese)     { this(size, cheese, false); }
    Pizza(String size, boolean cheese, boolean pepperoni) {   // the "canonical" one
        this.size = size;
        this.cheese = cheese;
        this.pepperoni = pepperoni;
    }
}
```

**One constructor does the real work; the others delegate to it.** Validation and assignment live in
exactly one place.

**Where it breaks down:**

```java
new Pizza("large", true, false, true, false, true);   // what ARE these?
```

Boolean parameters are unreadable at the call site (Day 032). Past three or four parameters,
telescoping constructors become worse than the problem they solve.

**The builder pattern is the answer** (Day 093):

```java
Pizza p = Pizza.builder().size("large").cheese(true).pepperoni(true).build();
```

## The full initialisation order — again, precisely

Day 033 gave you the six steps. Here it is at the constructor level, because it matters today:

```java
class Child extends Parent {
    private int field = init("3. Child field initialiser");

    Child() {
        // super();  ← IMPLICIT, inserted here if you don't write it
        System.out.println("4. Child constructor body");
    }
}
```

For `new Child()`:

```
   1. Parent's field initialisers and instance blocks
   2. Parent's constructor body
   3. Child's field initialisers and instance blocks    ← AFTER the parent constructor
   4. Child's constructor body
```

**Step 3 happening after step 2 is the source of the constructor-calls-override bug** (Day 033).
Worth re-stating because it comes up again in Day 037.

**If you write neither `this(...)` nor `super(...)`, the compiler inserts `super()`.** If the parent
has no no-arg constructor, that's a compile error — which is why an entity hierarchy without no-arg
constructors fails in surprising places.

## The `this` escape — a genuine concurrency bug

**Never let `this` escape from a constructor.**

```java
class Listener {
    Listener(EventBus bus) {
        bus.register(this);          // 💀 `this` is published BEFORE construction completes
        this.config = loadConfig();  // another thread may see config == null
    }
    private Config config;
}
```

Another thread can obtain the reference and observe a **partially constructed object** — fields at
their defaults. This is exactly why `final` fields get a special memory-model guarantee (Day 034)
and non-final fields don't.

**Forms of escape to watch for:**

```java
bus.register(this);                        // passing this out
new Thread(this).start();                  // starting a thread from a constructor
someList.add(this);
this.callback = () -> use(this.field);     // a non-static inner class or lambda capturing this
overridableMethod();                       // calling an override (Day 033)
```

**The fix:** a static factory that constructs first, then publishes.

```java
static Listener create(EventBus bus) {
    Listener l = new Listener();       // fully constructed
    bus.register(l);                    // THEN published
    return l;
}
```

Day 065 explains why this matters at the memory-model level. Today, know the rule.

## Static factory methods — usually better than constructors

```java
public static User of(String name) { return new User(name); }
public static Optional<User> tryParse(String s) { ... }
```

| Advantage over a constructor | Example |
|---|---|
| **They have names** | `BigDecimal.valueOf` vs three overloaded constructors |
| **Need not create a new instance** | `Integer.valueOf` caches (Day 028); `Boolean.valueOf` |
| **Can return a subtype** | `List.of` returns different implementations by size |
| **Can fail without throwing** | Return `Optional` instead |
| **Distinguish same-signature cases** | `Point.fromCartesian(x,y)` vs `Point.fromPolar(r,θ)` — impossible with constructors |

That last row is the killer argument: two constructors both taking `(double, double)` cannot
coexist. Named factories can.

**The cost:** a class with only private constructors can't be subclassed. Often that's a feature
(Day 034: prohibit inheritance unless designed for it).

**JDK conventions:** `of`, `valueOf`, `getInstance`, `newInstance`, `from`, `copyOf`.

## Type this yourself

```java
public class ConstructorDemo {

    // ---- 1. The return-type trap ----
    static class Trap {
        int value = -1;
        void Trap() { value = 42; }        // a METHOD, not a constructor
    }

    // ---- 2. Chaining ----
    static class Pizza {
        final String size; final boolean cheese, pepperoni;
        Pizza(String size)                 { this(size, false, false);
                                             System.out.println("  1-arg delegated"); }
        Pizza(String size, boolean cheese) { this(size, cheese, false); }
        Pizza(String size, boolean cheese, boolean pepperoni) {
            System.out.println("  canonical constructor runs");
            this.size = size; this.cheese = cheese; this.pepperoni = pepperoni;
        }
        public String toString() { return size + " cheese=" + cheese + " pep=" + pepperoni; }
    }

    // ---- 3. Initialisation order ----
    static class Parent {
        int p = log("1. Parent field");
        { log("2. Parent instance block"); }
        Parent() { log("3. Parent constructor body"); }
    }
    static class Child extends Parent {
        int c = log("4. Child field");
        { log("5. Child instance block"); }
        Child() { log("6. Child constructor body"); }
    }
    static int log(String m) { System.out.println("   " + m); return 0; }

    // ---- 4. The `this` escape ----
    interface Bus { void register(Escaper e); }
    static class Escaper {
        private String config;
        Escaper(Bus bus) {
            bus.register(this);                 // published BEFORE config is set
            this.config = "loaded";
        }
        String getConfig() { return config; }
    }

    public static void main(String[] args) {
        System.out.println("--- return-type trap ---");
        System.out.println("   value = " + new Trap().value + "   (expected 42? it's -1)");

        System.out.println("\n--- constructor chaining ---");
        System.out.println("   " + new Pizza("large"));

        System.out.println("\n--- initialisation order ---");
        new Child();

        System.out.println("\n--- this escape ---");
        new Escaper(e -> System.out.println("   observed config = " + e.getConfig()));
        //                                    prints NULL — object not yet constructed
    }
}
```

**Three things to observe:**

1. **`Trap.value` is `-1`.** The "constructor" never ran because a return type made it a method.
2. **The initialisation order prints 1–6 exactly** as the sequence predicts. Parent fully, then child.
3. **The escaped `this` observes `config = null`.** The object was published mid-construction. That's
   the bug, reproduced deterministically in one thread — imagine it across two.

## Common mistakes

| Mistake | Correction |
|---|---|
| Adding a return type to a constructor | Silently becomes a method. `new` calls the default instead. |
| Assuming a no-arg constructor always exists | Declaring any constructor removes the implicit one. |
| Calling `this(...)` after other statements | Must be the first statement. Same for `super(...)`. |
| Letting `this` escape a constructor | Publishes a partially constructed object. |
| Calling an overridable method from a constructor | Subclass fields aren't initialised yet (Day 033). |
| Telescoping past ~4 parameters | Unreadable call sites. Use a builder. |
| Constructors where a named factory would be clearer | Factories have names, can cache, and can return subtypes. |

## Interview questions

**Q: What happens, in order, when you call `new Child()`?**
> The JVM allocates zero-initialised memory and pushes the reference — that's the `new` instruction —
> then `invokespecial` invokes the constructor. Inside, the parent constructor runs first, meaning
> the parent's field initialisers and instance blocks, then its body. Only then do the child's field
> initialisers and instance blocks run, followed by the child's constructor body.

**Q: Why shouldn't `this` escape from a constructor?**
> Because the object isn't fully constructed. Any other thread — or any callback — that obtains the
> reference can observe fields at their default values. The memory model only guarantees correct
> visibility of `final` fields *after* construction completes, so escaping breaks that guarantee.

**Q: When would you prefer a static factory to a constructor?**
> When a name adds clarity, when you don't always need a new instance and can cache, when you want to
> return a subtype chosen at runtime, or when two creation paths would otherwise have identical
> signatures — `fromCartesian` and `fromPolar` both take two doubles and can't both be constructors.

**Q: Why do JPA entities need a no-arg constructor?**
> Hibernate instantiates entities reflectively before populating fields, which requires a no-arg
> constructor. Declaring any parameterised constructor removes the implicit default one, so you must
> add it back explicitly, conventionally as `protected`.

**Q: What does `this(...)` do and where must it appear?**
> It delegates to another constructor in the same class and must be the first statement, so
> initialisation happens in exactly one well-defined order. You can have `this(...)` or `super(...)`
> but not both.
