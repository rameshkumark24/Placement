# Part 1 — L-043 · Enums

## What an enum actually is

**A class with a fixed set of instances, created once, at class initialisation.**

```java
public enum Status { ACTIVE, INACTIVE, PENDING }
```

compiles to roughly:

```java
public final class Status extends Enum<Status> {
    public static final Status ACTIVE   = new Status("ACTIVE", 0);
    public static final Status INACTIVE = new Status("INACTIVE", 1);
    public static final Status PENDING  = new Status("PENDING", 2);
    private Status(String name, int ordinal) { super(name, ordinal); }
}
```

**Three consequences worth stating:**

1. **The constants are `static final` fields**, created during class initialisation (Day 033) — which
   the JVM guarantees is thread-safe and happens exactly once.
2. **The constructor is implicitly private.** You cannot create a new instance.
3. **They're real objects** — they can have fields, methods, and implement interfaces.

**`==` works on enums, and is preferred over `equals`.** There is exactly one instance per constant,
so reference comparison is correct, faster, and null-safe:

```java
if (status == Status.ACTIVE)          // ✅ null-safe, and won't compile on a type mismatch
if (status.equals(Status.ACTIVE))     // works, but NPEs if status is null
```

**This is the one place `==` on objects is the right answer** — contrast Days 025, 028 and 040 where
it's a bug.

## Enums with state and behaviour

```java
public enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    VENUS  (4.869e+24, 6.0518e6),
    EARTH  (5.976e+24, 6.37814e6);

    private final double mass;       // fields
    private final double radius;

    Planet(double mass, double radius) {     // constructor — implicitly private
        this.mass = mass;
        this.radius = radius;
    }

    public double surfaceGravity() {          // methods
        return 6.67300E-11 * mass / (radius * radius);
    }
}
```

**This is the feature people don't use enough.** An enum can carry data and behaviour, which turns a
scattered `switch` into a method on the type.

### Constant-specific bodies — the strategy pattern for free

```java
public enum Operation {
    PLUS("+")  { public double apply(double x, double y) { return x + y; } },
    MINUS("-") { public double apply(double x, double y) { return x - y; } },
    TIMES("*") { public double apply(double x, double y) { return x * y; } },
    DIVIDE("/"){ public double apply(double x, double y) { return x / y; } };

    private final String symbol;
    Operation(String symbol) { this.symbol = symbol; }

    public abstract double apply(double x, double y);      // each constant implements it
}

Operation.PLUS.apply(2, 3);      // 5.0
```

**Each constant is an anonymous subclass** (Day 044). Add a new operation and the compiler forces you
to implement `apply` — you cannot forget a case, which is the same guarantee sealed types give
(Day 042).

**Compare with the alternative:**

```java
// 💀 add a constant and this silently throws at runtime
double apply(Operation op, double x, double y) {
    switch (op) {
        case PLUS: return x + y;
        case MINUS: return x - y;
        default: throw new AssertionError("Unknown op: " + op);
    }
}
```

**Behaviour belongs on the enum, not in a switch elsewhere.**

## The enum singleton — the correct one

```java
public enum Registry {
    INSTANCE;

    private final Map<String, Object> data = new ConcurrentHashMap<>();
    public void put(String k, Object v) { data.put(k, v); }
}

Registry.INSTANCE.put("key", value);
```

***Effective Java* item 3: "a single-element enum type is the best way to implement a singleton."**
Why it beats every hand-rolled version:

| Problem | Hand-rolled singleton | Enum |
|---|---|---|
| Thread-safe lazy init | Needs double-checked locking with `volatile` — easy to get wrong | **Free** — class init is thread-safe |
| Reflection attack (`setAccessible` + constructor) | Possible | **Impossible** — the JVM forbids reflective enum construction |
| Serialization creates a second instance | Needs `readResolve` | **Free** — enums serialise by name |
| Boilerplate | Substantial | One line |

**Mentioning the reflection and serialization attacks is what makes this answer good** — most people
stop at "it's thread-safe".

## Enums as a state machine

```java
public enum OrderState {
    CREATED   { public OrderState next() { return PAID; } },
    PAID      { public OrderState next() { return SHIPPED; } },
    SHIPPED   { public OrderState next() { return DELIVERED; } },
    DELIVERED { public OrderState next() { throw new IllegalStateException("terminal"); } };

    public abstract OrderState next();
}
```

Or with explicit allowed transitions:

```java
public enum OrderState {
    CREATED, PAID, SHIPPED, DELIVERED, CANCELLED;

    private static final Map<OrderState, Set<OrderState>> ALLOWED = Map.of(
            CREATED,   EnumSet.of(PAID, CANCELLED),
            PAID,      EnumSet.of(SHIPPED, CANCELLED),
            SHIPPED,   EnumSet.of(DELIVERED),
            DELIVERED, EnumSet.noneOf(OrderState.class),
            CANCELLED, EnumSet.noneOf(OrderState.class));

    public boolean canTransitionTo(OrderState target) {
        return ALLOWED.get(this).contains(target);
    }
}
```

**The transitions are now data, in one place, testable.** Compare with `if` chains scattered across a
service — this is a genuinely good answer in an LLD round (Stage 8, Day 317's vending machine).

## The built-in methods

```java
Status.values()              // Status[] — a DEFENSIVE COPY each call
Status.valueOf("ACTIVE")     // throws IllegalArgumentException if no match
status.name()                // "ACTIVE" — the declared name, final
status.ordinal()             // 0 — the declaration position
status.compareTo(other)      // by ordinal
```

### Two traps

**`values()` allocates a new array every call.** In a hot loop, cache it:

```java
private static final Status[] VALUES = values();       // ✅ cached, don't expose it
```

**Never persist `ordinal()`.** It changes if anyone reorders or inserts a constant, silently
corrupting stored data:

```java
// 💀 the DB now holds meaningless integers if the enum is reordered
@Enumerated(EnumType.ORDINAL)
private Status status;

// ✅ store the name
@Enumerated(EnumType.STRING)
private Status status;
```

**That JPA default is `ORDINAL`**, which makes it a genuine production hazard. Always specify
`STRING`. Store an explicit code field if you need stability against renames too.

## `EnumMap` and `EnumSet` — use them

```java
Map<Status, Integer> counts = new EnumMap<>(Status.class);      // NOT HashMap
Set<Status> active = EnumSet.of(Status.ACTIVE, Status.PENDING); // NOT HashSet
```

- **`EnumMap`** is backed by a plain array indexed by ordinal — no hashing, no collisions, faster and
  smaller than `HashMap`, and iterates in declaration order.
- **`EnumSet`** is a **bit vector**. For ≤64 constants it's a single `long`. Operations are bitwise —
  extraordinarily fast, and tiny.

**Using `HashMap<SomeEnum, V>` is leaving free performance on the table**, and knowing `EnumSet` is a
bit vector is a nice detail.

## Type this yourself

```java
import java.util.*;

public class EnumDemo {

    enum Operation {
        PLUS("+")   { public double apply(double x, double y) { return x + y; } },
        MINUS("-")  { public double apply(double x, double y) { return x - y; } },
        TIMES("*")  { public double apply(double x, double y) { return x * y; } };

        private final String symbol;
        Operation(String symbol) { this.symbol = symbol; }
        public abstract double apply(double x, double y);
        @Override public String toString() { return symbol; }
    }

    enum OrderState {
        CREATED, PAID, SHIPPED, DELIVERED, CANCELLED;
        private static final Map<OrderState, Set<OrderState>> ALLOWED = Map.of(
                CREATED,   EnumSet.of(PAID, CANCELLED),
                PAID,      EnumSet.of(SHIPPED, CANCELLED),
                SHIPPED,   EnumSet.of(DELIVERED),
                DELIVERED, EnumSet.noneOf(OrderState.class),
                CANCELLED, EnumSet.noneOf(OrderState.class));
        boolean canGoTo(OrderState t) { return ALLOWED.get(this).contains(t); }
    }

    enum Registry {
        INSTANCE;
        private final Map<String, String> data = new HashMap<>();
        void put(String k, String v) { data.put(k, v); }
        String get(String k) { return data.get(k); }
    }

    public static void main(String[] args) {

        System.out.println("--- constant-specific behaviour ---");
        for (Operation op : Operation.values())
            System.out.printf("   6 %s 2 = %.1f%n", op, op.apply(6, 2));

        System.out.println("\n--- state machine ---");
        for (OrderState from : OrderState.values())
            System.out.printf("   %-10s -> %s%n", from, OrderState.ALLOWED.get(from));
        System.out.println("   CREATED -> SHIPPED allowed? " + OrderState.CREATED.canGoTo(OrderState.SHIPPED));
        System.out.println("   CREATED -> PAID    allowed? " + OrderState.CREATED.canGoTo(OrderState.PAID));

        System.out.println("\n--- singleton ---");
        Registry.INSTANCE.put("k", "v");
        System.out.println("   same instance everywhere: " + Registry.INSTANCE.get("k"));

        System.out.println("\n--- values() allocates ---");
        System.out.println("   values() == values() ? " + (Operation.values() == Operation.values()));

        System.out.println("\n--- EnumSet is a bit vector ---");
        EnumSet<OrderState> open = EnumSet.of(OrderState.CREATED, OrderState.PAID);
        EnumSet<OrderState> closed = EnumSet.complementOf(open);
        System.out.println("   open   = " + open);
        System.out.println("   closed = " + closed + "   ← complementOf, a bitwise NOT");

        System.out.println("\n--- EnumMap iterates in declaration order ---");
        Map<OrderState, Integer> counts = new EnumMap<>(OrderState.class);
        counts.put(OrderState.SHIPPED, 3);
        counts.put(OrderState.CREATED, 7);
        counts.put(OrderState.PAID, 5);
        System.out.println("   " + counts + "   ← inserted out of order, iterates in order");

        System.out.println("\n--- ordinal is fragile ---");
        System.out.println("   CREATED.ordinal() = " + OrderState.CREATED.ordinal()
                         + "   ← NEVER persist this");
        System.out.println("   CREATED.name()    = " + OrderState.CREATED.name() + "   ← persist this");
    }
}
```

**Two things to notice:** `values() == values()` is **false** — a fresh array each call. And the
`EnumMap` prints in *declaration* order despite being inserted out of order, because it's an
ordinal-indexed array.

## Interview questions

**Q: What is an enum, really?**
> A class with a fixed set of instances created as `static final` fields during class initialisation.
> The constructor is implicitly private, so no new instances can exist, which is why `==` is the
> correct comparison and is preferred over `equals` — it's faster and null-safe.

**Q: Why is a single-element enum the best singleton?**
> Class initialisation is thread-safe and happens exactly once, so you get lazy safe initialisation
> with no double-checked locking. The JVM forbids reflective construction of enum instances, so the
> `setAccessible` attack is impossible. And enums serialise by name, so deserialisation returns the
> existing instance rather than creating a second one — no `readResolve` needed.

**Q: Why should you never persist `ordinal()`?**
> It's the declaration position, so inserting or reordering constants silently changes every stored
> value. JPA's `@Enumerated` defaults to `ORDINAL`, which makes this a real production hazard —
> always specify `STRING`, or store an explicit stable code.

**Q: Why use `EnumMap` and `EnumSet`?**
> `EnumMap` is backed by an array indexed by ordinal, so there's no hashing or collision handling —
> it's faster and smaller than `HashMap` and iterates in declaration order. `EnumSet` is a bit vector,
> a single `long` for up to 64 constants, so set operations are bitwise and extremely fast.

**Q: When would you put behaviour on an enum?**
> Whenever behaviour varies by constant. Constant-specific method bodies make each constant implement
> an abstract method, so adding a constant is a compile error until you implement it — unlike a
> `switch` elsewhere, which fails at runtime. It's the strategy pattern with compiler enforcement.

# Part 2 — B-07 · Synchronization primitives

## The problem, restated

Day 040's B-06 established the race. Now: how do you actually enforce mutual exclusion?

## Mutex — mutual exclusion lock

**One holder at a time. The holder must be the releaser.**

```java
synchronized (lock) { /* critical section */ }        // implicit
lock.lock(); try { ... } finally { lock.unlock(); }   // explicit
```

**In Java every object has an intrinsic lock (a monitor).** `synchronized` acquires it on entry and
releases on exit — including on an exception, which is why it's harder to leak than an explicit lock.

## Semaphore — a counter

**Allows N holders. No ownership** — any thread may release, even one that never acquired.

```java
Semaphore permits = new Semaphore(5);       // at most 5 concurrent
permits.acquire();
try { doWork(); } finally { permits.release(); }
```

| | Mutex | Semaphore |
|---|---|---|
| Holders | 1 | N |
| Ownership | ✅ holder must release | ❌ anyone may release |
| Use for | Protecting shared state | **Limiting concurrency** — rate limiting, connection pools |

**A binary semaphore is not a mutex** — the missing ownership means it can't support reentrancy or
priority inheritance (Day 036, B-05). Use a mutex for exclusion, a semaphore for resource counting.

## Monitor — lock plus condition

**A monitor is a mutex bundled with the ability to wait for a condition.** Java's built-in model.

```java
synchronized (queue) {
    while (queue.isEmpty()) {      // ALWAYS a while loop, never if
        queue.wait();               // releases the lock and blocks
    }
    Object item = queue.remove();
}

synchronized (queue) {
    queue.add(item);
    queue.notifyAll();              // wakes waiters — they must re-acquire the lock
}
```

**Three rules that are all commonly broken:**

1. **`wait`/`notify` must be called while holding the monitor** — otherwise
   `IllegalMonitorStateException`.
2. **Always `while`, never `if`.** A thread can wake without the condition being true — *spurious
   wakeup*, and more importantly another thread may have consumed the item between the notify and
   your re-acquisition.
3. **Prefer `notifyAll` to `notify`.** `notify` wakes one arbitrary waiter, which may be waiting on a
   different condition, causing a lost wakeup and a hang.

**The `while` rule is the single most-asked detail** about `wait`/`notify`.

## Condition variables — the modern form

```java
Lock lock = new ReentrantLock();
Condition notEmpty = lock.newCondition();
Condition notFull  = lock.newCondition();      // MULTIPLE conditions per lock

lock.lock();
try {
    while (queue.isEmpty()) notEmpty.await();
    Object item = queue.remove();
    notFull.signal();                           // signal only the relevant waiters
} finally { lock.unlock(); }
```

**The advantage over `wait`/`notify`:** multiple condition queues on one lock. Producers wait on
`notFull`, consumers on `notEmpty`, so you never wake the wrong group. With intrinsic monitors you
have exactly one wait set per object.

Day 067 covers `ReentrantLock` fully. **In practice, use `BlockingQueue`** — it implements all of
this correctly, and hand-rolling producer-consumer is a known source of bugs.

## Reentrancy

```java
synchronized void a() { b(); }        // already holds the lock
synchronized void b() { }             // re-acquires it — fine, it's REENTRANT
```

**Java's intrinsic locks and `ReentrantLock` are reentrant** — the holder can re-acquire without
deadlocking. The lock keeps a hold count.

**Without reentrancy, any method calling another synchronized method on the same object would
self-deadlock.** That's why it's the default, and it's a good "why" question.

## Type this yourself

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.locks.*;

public class SyncDemo {

    // Hand-rolled bounded buffer with a monitor
    static class MonitorQueue<T> {
        private final Queue<T> q = new LinkedList<>();
        private final int capacity;
        MonitorQueue(int capacity) { this.capacity = capacity; }

        synchronized void put(T item) throws InterruptedException {
            while (q.size() == capacity) wait();      // WHILE, not if
            q.add(item);
            notifyAll();
        }
        synchronized T take() throws InterruptedException {
            while (q.isEmpty()) wait();
            T item = q.remove();
            notifyAll();
            return item;
        }
    }

    public static void main(String[] args) throws Exception {

        // ---- monitor-based producer/consumer ----
        MonitorQueue<Integer> queue = new MonitorQueue<>(3);
        Thread producer = new Thread(() -> {
            try { for (int i = 1; i <= 6; i++) { queue.put(i); System.out.println("   put " + i); } }
            catch (InterruptedException ignored) {}
        });
        Thread consumer = new Thread(() -> {
            try { for (int i = 1; i <= 6; i++) { Thread.sleep(50);
                       System.out.println("      took " + queue.take()); } }
            catch (InterruptedException ignored) {}
        });
        System.out.println("--- monitor: producer blocks when full (capacity 3) ---");
        producer.start(); consumer.start(); producer.join(); consumer.join();

        // ---- semaphore limits concurrency ----
        System.out.println("\n--- semaphore: max 2 concurrent ---");
        Semaphore permits = new Semaphore(2);
        ExecutorService pool = Executors.newFixedThreadPool(6);
        for (int i = 1; i <= 6; i++) {
            int id = i;
            pool.submit(() -> {
                try {
                    permits.acquire();
                    System.out.println("   task " + id + " running, permits left "
                            + permits.availablePermits());
                    Thread.sleep(200);
                } catch (InterruptedException ignored) {}
                finally { permits.release(); }
            });
        }
        pool.shutdown(); pool.awaitTermination(5, TimeUnit.SECONDS);

        // ---- reentrancy ----
        System.out.println("\n--- reentrancy ---");
        new SyncDemo().outer();

        // ---- what you should ACTUALLY use ----
        System.out.println("\n--- BlockingQueue does all of the above, correctly ---");
        BlockingQueue<String> bq = new ArrayBlockingQueue<>(2);
        bq.put("a"); bq.put("b");
        System.out.println("   took: " + bq.take() + ", " + bq.take());
    }

    synchronized void outer() { System.out.println("   in outer"); inner(); }
    synchronized void inner() { System.out.println("   in inner — re-acquired the same lock"); }
}
```

**Watch the producer block** when the queue hits capacity 3, then resume as the consumer drains it.
That's the monitor working — and then notice `BlockingQueue` does it in two lines.

## Interview questions

**Q: Mutex vs semaphore?**
> A mutex allows one holder and has ownership — the thread that acquired must release. A semaphore is
> a counter allowing N holders with no ownership, so any thread can release. Use a mutex to protect
> shared state and a semaphore to limit concurrency, such as capping simultaneous connections.

**Q: What is a monitor?**
> A mutex combined with the ability to wait for a condition. In Java every object has an intrinsic
> monitor: `synchronized` acquires it, and `wait`, `notify` and `notifyAll` operate on its single wait
> set.

**Q: Why must `wait` be in a `while` loop rather than an `if`?**
> Because waking doesn't guarantee the condition is true. Spurious wakeups are permitted, and more
> importantly another thread may consume the resource between the notify and your re-acquisition of
> the lock. The condition must be rechecked after waking.

**Q: `notify` or `notifyAll`?**
> `notifyAll` unless you're certain all waiters are waiting on the same condition. `notify` wakes one
> arbitrary thread, which may be waiting for something else, so the notification is lost and the
> thread that could have proceeded stays blocked.

**Q: Why are Java's locks reentrant?**
> So a thread already holding a lock can call another synchronized method on the same object without
> deadlocking itself. Without reentrancy any nested synchronized call would self-deadlock. The lock
> maintains a hold count and only releases when it reaches zero.
