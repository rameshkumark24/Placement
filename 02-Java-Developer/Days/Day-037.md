# L-037 · Inheritance

## What it gives you, and what it costs

```java
class Animal { void eat() { } }
class Dog extends Animal { void bark() { } }    // Dog IS-A Animal
```

**Java has single inheritance for classes** — one `extends` — and multiple inheritance for interfaces
via `implements`. That's a deliberate choice to avoid the *diamond problem* (Day 039).

**Every class implicitly extends `Object`**, which is where `equals`, `hashCode`, `toString`,
`getClass` and `wait`/`notify` come from.

**What inheritance actually does:** it couples the subclass to the *implementation* of the superclass,
not just its interface. That's the cost, and it's larger than people expect.

## The overriding rules

A method overrides when the signature matches. The rules:

| Rule | Detail |
|---|---|
| **Same name and parameter types** | Different parameters = overloading, not overriding (Day 032) |
| **Return type** | Same, or a **subtype** — *covariant return* |
| **Access** | Same or **wider**. Never narrower. |
| **Checked exceptions** | Same, fewer, or **narrower**. Never broader. |
| **Cannot override** | `static`, `private`, `final` methods |

```java
class Parent {
    protected Object get() throws IOException { return null; }
}

class Child extends Parent {
    @Override
    public String get() throws FileNotFoundException { return "x"; }
    //  ↑ wider     ↑ covariant return       ↑ narrower exception   — all legal
}
```

**Why access can only widen:** Liskov substitution (Day 091). A `Parent` reference must work wherever
a `Parent` is expected. If `Child` narrowed access to `private`, calling `get()` through a `Parent`
reference would break. Same reasoning for exceptions — a caller catching `IOException` must not be
surprised by something broader.

**Covariant returns** were added in Java 5 and are genuinely useful — `clone()` returning your actual
type rather than `Object`.

## `@Override` — use it always

```java
class Parent { void process(String s) { } }

class Child extends Parent {
    void proces(String s) { }              // 💀 typo — a NEW method, silently
    @Override void proces(String s) { }    // ✅ compile error: does not override
}
```

**It's not decoration; it's a compile-time assertion.** It catches:

- Typos in the method name
- Wrong parameter types (accidental overloading instead of overriding)
- A superclass method being renamed or removed later

```java
class Child extends Parent {
    @Override
    boolean equals(Parent p) { }     // 💀 compile error — Object.equals takes Object
}
```

**That one is a genuinely common bug** — overloading `equals` instead of overriding it, so collections
silently use `Object.equals` (identity). `@Override` catches it instantly. Day 040.

## Overriding vs hiding — the full table

Day 033 covered static hiding. Here's everything:

| Member | Behaviour | Resolved by |
|---|---|---|
| **Instance method** | **Overridden** | **Runtime type** (dynamic dispatch) |
| `static` method | **Hidden** | Compile-time type |
| **Field** | **Hidden** | Compile-time type |
| `private` method | Not inherited — a new method | Compile-time type |

```java
class Parent {
    String name = "Parent";
    static void stat()  { System.out.println("Parent.stat"); }
    void inst()         { System.out.println("Parent.inst"); }
}
class Child extends Parent {
    String name = "Child";                    // HIDES, doesn't override
    static void stat()  { System.out.println("Child.stat"); }
    @Override void inst() { System.out.println("Child.inst"); }
}

Parent p = new Child();
p.name          // "Parent"      ← FIELD: static type
p.stat();       // Parent.stat   ← STATIC: static type
p.inst();       // Child.inst    ← INSTANCE METHOD: runtime type
```

**Only instance methods are polymorphic.** Fields and statics are not.

**And this is why field hiding is a bug, not a feature.** The object genuinely has *two* `name`
fields, and which one you see depends on the reference type you're holding. Never shadow a field.

Day 024 gave the mechanism: `invokevirtual` dispatches at runtime; `invokestatic` and `getfield`
resolve at compile time.

## `super`

```java
class Child extends Parent {
    @Override void process() {
        super.process();          // call the parent's version
        // ... additional work
    }
    Child() { super(42); }        // call a parent constructor — FIRST statement
}
```

**`super.process()` compiles to `invokespecial`, not `invokevirtual`** (Day 024). That's precisely why
it doesn't dispatch back to the override and cause infinite recursion.

**You cannot do `super.super.method()`.** There's no syntax, deliberately — it would let you break a
class's control over its own hierarchy.

## The fragile base class problem

**The core argument against inheritance.** A subclass depends on the superclass's *implementation
details*, so a harmless-looking change to the parent breaks it.

The classic, from *Effective Java*:

```java
class CountingHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }
    public int getAddCount() { return addCount; }
}

var s = new CountingHashSet<String>();
s.addAll(List.of("a", "b", "c"));
s.getAddCount();      // 6, not 3 !!
```

**Why:** `HashSet.addAll` internally calls `add` for each element. So `addCount` increments three
times in `addAll`, then three more via the overridden `add`.

**Nothing in `HashSet`'s documentation promised that.** The subclass depended on an implementation
detail. If a future JDK changed `addAll` to not call `add`, the count would break the other way.

### Composition fixes it

```java
class CountingSet<E> {
    private final Set<E> delegate = new HashSet<>();     // HAS-A, not IS-A
    private int addCount = 0;

    public boolean add(E e)       { addCount++; return delegate.add(e); }
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return delegate.addAll(c);
    }
    public int getAddCount()      { return addCount; }
}
```

**You control every call.** The delegate's internals cannot leak into your logic, and a change to
`HashSet` cannot break you.

**"Favour composition over inheritance"** — that's the actual reason, and it's much better than
"inheritance is bad".

## When inheritance IS right

| Use inheritance | Use composition |
|---|---|
| A genuine **is-a** relationship | A **has-a** relationship |
| The parent was **designed** for extension, with documented hooks | Reusing an unrelated implementation |
| Template method pattern | You only want *some* of the parent's behaviour |
| Sealed hierarchies of a closed set of variants (Day 042) | Anything else |

**The test:** would every method on the parent make sense on the child, and is the child substitutable
everywhere the parent is? If not, it's not an is-a relationship.

`Stack extends Vector` in the JDK is the standard counterexample — a `Stack` inherits `get(int)` and
`insertElementAt`, so you can reach into the middle of a stack. It isn't a `Vector`; it *uses* one.
Use `Deque` instead (Day 051).

## Designing for inheritance

If you allow it, you owe the subclass documentation:

- **Document self-use.** Which methods call which overridable methods? (Exactly what `HashSet` failed
  to do.)
- **Provide hooks** — protected methods designed to be overridden.
- **Never call an overridable method from a constructor** (Day 033).
- **`clone` and `readObject` must not call overridable methods either** — same reason.
- **Test by writing three subclasses yourself** before shipping.

**If you're not doing all that: make the class `final`** (Day 034).

## Type this yourself

```java
import java.util.*;

public class InheritanceDemo {

    // ---- overriding vs hiding ----
    static class Parent {
        String name = "Parent";
        static void stat() { System.out.println("   Parent.stat"); }
        void inst()        { System.out.println("   Parent.inst"); }
        Object get()       { return "parent-object"; }
    }

    static class Child extends Parent {
        String name = "Child";                                  // HIDES
        static void stat() { System.out.println("   Child.stat"); }
        @Override void inst() { System.out.println("   Child.inst"); }
        @Override String get() { return "child-string"; }        // covariant return
    }

    // ---- the fragile base class ----
    static class CountingHashSet<E> extends HashSet<E> {
        int addCount = 0;
        @Override public boolean add(E e) { addCount++; return super.add(e); }
        @Override public boolean addAll(Collection<? extends E> c) {
            addCount += c.size(); return super.addAll(c);
        }
    }

    static class CountingSet<E> {
        private final Set<E> delegate = new HashSet<>();
        int addCount = 0;
        public boolean add(E e) { addCount++; return delegate.add(e); }
        public boolean addAll(Collection<? extends E> c) {
            addCount += c.size(); return delegate.addAll(c);
        }
    }

    public static void main(String[] args) {
        System.out.println("--- dispatch ---");
        Parent p = new Child();
        System.out.println("   p.name  = " + p.name);       // Parent — FIELD, static type
        System.out.println("   ((Child)p).name = " + ((Child) p).name);   // Child
        p.stat();                                            // Parent.stat — static type
        p.inst();                                            // Child.inst  — runtime type
        System.out.println("   p.get() = " + p.get());       // child-string

        System.out.println("\n--- fragile base class ---");
        var inherited = new CountingHashSet<String>();
        inherited.addAll(List.of("a", "b", "c"));
        System.out.println("   inheritance addCount = " + inherited.addCount + "   ← expected 3!");

        var composed = new CountingSet<String>();
        composed.addAll(List.of("a", "b", "c"));
        System.out.println("   composition addCount = " + composed.addCount + "   ← correct");
    }
}
```

**Three things to observe:**

1. **`p.name` is `"Parent"` while `p.inst()` prints `Child.inst`.** Same reference, opposite
   behaviour — fields are not polymorphic, instance methods are.
2. **The inherited counter reports 6 for three additions.** That's the fragile base class problem,
   reproduced in ten lines.
3. **The composed version is correct** and can never be broken by a JDK change.

**Then break `@Override` deliberately:** rename `inst` to `insst` in `Child` and keep `@Override`.
Read the compile error. That error is exactly what saves you from a silent typo bug.

## Common mistakes

| Mistake | Correction |
|---|---|
| Omitting `@Override` | It's a compile-time assertion, not decoration. Always use it. |
| `equals(MyType)` instead of `equals(Object)` | That's overloading. Collections silently use identity. |
| Shadowing a field in a subclass | Creates two fields; which you see depends on the reference type. Never do it. |
| Expecting static methods or fields to dispatch | Only instance methods are polymorphic. |
| Extending a class to reuse its code | If it isn't an is-a relationship, compose. |
| Extending a class not designed for extension | Fragile base class — internal changes break you. |
| Calling an overridable method from a constructor | Subclass fields aren't initialised (Day 033). |
| Narrowing access or broadening exceptions when overriding | Violates substitutability; won't compile. |

## Interview questions

**Q: What are the rules for overriding a method?**
> Same name and parameter types. The return type must be the same or a subtype — covariant returns.
> Access must be the same or wider, never narrower. Checked exceptions must be the same, fewer, or
> narrower. Static, private and final methods cannot be overridden. The access and exception rules
> exist to preserve substitutability — a subclass must work wherever the superclass does.

**Q: What's the difference between overriding and hiding?**
> Overriding applies to instance methods and is resolved at runtime by the object's actual type via
> `invokevirtual`. Hiding applies to static methods and fields, which are resolved at compile time
> from the declared type. So with `Parent p = new Child()`, an instance method call runs the child's
> version but a static call or field access uses the parent's.

**Q: Why use `@Override`?**
> It asserts at compile time that the method genuinely overrides something. Without it, a typo or a
> wrong parameter type silently creates a new method — most commonly writing `equals(MyType)` instead
> of `equals(Object)`, which makes collections fall back to identity comparison.

**Q: What is the fragile base class problem?**
> A subclass depends on the superclass's implementation details, not just its contract, so an internal
> change in the parent breaks the child. The classic example is subclassing `HashSet` to count
> additions: `addAll` internally calls `add`, so the count is doubled — behaviour that was never
> documented and could change. Composition with delegation avoids it entirely.

**Q: When should you use inheritance?**
> When there's a genuine is-a relationship and the superclass was explicitly designed and documented
> for extension — self-use documented, hooks provided, no overridable calls from constructors.
> Otherwise compose. If you haven't designed for inheritance, make the class final.

**Q: Why does `super.method()` not recurse infinitely?**
> It compiles to `invokespecial`, which resolves the target at compile time, rather than
> `invokevirtual`, which dispatches on the runtime type. That's the same instruction used for
> constructors and private methods.
