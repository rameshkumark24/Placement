# Part 1 — ⭐⭐ Heaps: the k-th element inversion

```
⭐⭐ "FIND THE k LARGEST ELEMENTS" ⇒ ⭐⭐ USE A MIN-HEAP OF SIZE k. ⭐ Not a max-heap.
⭐   ⇒ ⭐ keep exactly k elements; ⭐⭐ the smallest of your k is at the top
⭐   ⇒ ⭐ a new element bigger than the top replaces it; anything smaller is discarded instantly
⭐   ⇒ ⭐⭐ O(n log k) time, ⭐⭐ O(k) space — ⭐ and it works on a STREAM, which a sort cannot.
```

| ⭐ Problem | ⭐ Structure |
|---|---|
| ⭐⭐ **k largest** | ⭐⭐ **min-heap of size k** |
| ⭐⭐ **k smallest** | ⭐⭐ **max-heap of size k** |
| ⭐ Top-k frequent | ⭐ count with a map, then min-heap of size k on frequency |
| ⭐⭐ **Median of a stream** | ⭐⭐ **two heaps** — max-heap for the lower half, min-heap for the upper, sizes balanced |
| ⭐ Merge k sorted lists | ⭐ min-heap of the k list heads |
| ⭐ Dijkstra | ⭐ min-heap keyed by distance |

```java
// ⭐ k largest — the inversion, in four lines
PriorityQueue<Integer> heap = new PriorityQueue<>();     // ⭐⭐ MIN-heap (natural order)
for (int x : nums) {
    heap.offer(x);
    if (heap.size() > k) heap.poll();                    // ⭐⭐ evict the smallest
}
return heap.peek();                                      // ⭐ the k-th largest
```

⚠️ **Say the trade aloud: sorting is O(n log n) and a heap is O(n log k).** For k = 5 and n = a million
that matters; **for k close to n it does not, and sorting is simpler.** And **quickselect is O(n) average
but O(n²) worst case and destroys the input** — naming all three and choosing one is what scores.

# Part 2 — ⭐⭐ Intervals: sort by start, or sort by end

```
⭐⭐ SORT BY START  ⇒ ⭐⭐ MERGING overlapping intervals, inserting an interval
⭐⭐ SORT BY END    ⇒ ⭐⭐ MAXIMISING non-overlapping intervals (the classic greedy)
⭐   ⇒ ⭐⭐ Why end for maximising? ⭐⭐ finishing earliest leaves the most room for what follows.
⭐     ⭐ That one sentence is the whole proof, and it is worth saying.
```

## ⭐ Warm-up (target: 12 minutes)

> **Given a collection of intervals, merge all overlapping ones and return the result.**

```java
Arrays.sort(intervals, Comparator.comparingInt(a -> a[0]));   // ⭐⭐ by START
List<int[]> out = new ArrayList<>();
for (int[] cur : intervals) {
    if (out.isEmpty() || out.get(out.size() - 1)[1] < cur[0])  // ⭐⭐ strict < : [1,2],[2,3] MERGE
        out.add(cur);
    else
        out.get(out.size() - 1)[1] = Math.max(out.get(out.size() - 1)[1], cur[1]);  // ⭐⭐ MAX, not cur[1]
}
return out.toArray(new int[0][]);
```

| ⭐⭐ The two bugs | |
|---|---|
| ⭐⭐ **Assigning `cur[1]` instead of `max(prev[1], cur[1])`** | ⭐⭐ a fully-contained interval **shrinks** the merged one |
| ⭐⭐ **`<` versus `<=` on the touch case** | ⭐⭐ **ask whether `[1,2]` and `[2,3]` count as overlapping** — this is a real clarifying question |

**⭐ Say aloud:** *"Sorting by start means any interval that overlaps the current merged one must start
before the merged one ends, so I only ever compare against the last result. The `max` matters because the
new interval can be entirely inside the previous one. And I'd confirm whether touching endpoints count as
overlapping — that changes one comparison operator."*

## ⭐⭐ Main problem (target: 30 minutes)

> **Given an array of meeting time intervals, return the minimum number of meeting rooms required.**

| ⭐ Two correct approaches — give both | |
|---|---|
| ⭐⭐ **A: min-heap of end times** | ⭐ sort by start; for each meeting, if the earliest end ≤ its start, reuse that room (poll); always push its end. **Heap size = rooms.** |
| ⭐⭐ **B: the sweep line** | ⭐⭐ separate the starts and ends, sort each, walk with two pointers: a start increments, an end decrements, **track the maximum concurrent** |

```java
// ⭐ A — min-heap of end times
Arrays.sort(intervals, Comparator.comparingInt(a -> a[0]));
PriorityQueue<Integer> ends = new PriorityQueue<>();
for (int[] m : intervals) {
    if (!ends.isEmpty() && ends.peek() <= m[0]) ends.poll();   // ⭐⭐ a room freed up — reuse it
    ends.offer(m[1]);
}
return ends.size();                                            // ⭐⭐ peak concurrency

// ⭐⭐ B — sweep line: often cleaner, and it generalises
int[] starts = ..., ends = ...;  Arrays.sort(starts); Arrays.sort(ends);
int rooms = 0, max = 0, e = 0;
for (int s = 0; s < starts.length; s++) {
    while (e < ends.length && ends[e] <= starts[s]) { rooms--; e++; }
    rooms++; max = Math.max(max, rooms);
}
return max;
```

> **⭐⭐ Offering both and choosing one is the highest-scoring move here.** *"The heap version reads as the
> physical problem — rooms with end times. The sweep line is cleaner and generalises to 'maximum
> concurrent anything', which is why I'd pick it if we later needed the busiest interval rather than just
> the count."* **That is a design conversation inside an algorithms question.**

# Part 3 — ⭐⭐ The sliding window template

```
⭐⭐ THE TELL: "contiguous subarray/substring" + "longest / shortest / at most k / exactly k"
⭐
⭐ int left = 0;  ⭐ for (int right = 0; right < n; right++) {
⭐     ⭐ add(s[right]);                                  // grow
⭐     ⭐⭐ while (WINDOW IS INVALID) { remove(s[left]); left++; }   // ⭐⭐ shrink until valid again
⭐     ⭐ best = max(best, right - left + 1);             // record
⭐ }
⭐ ⇒ ⭐⭐ Each element enters once and leaves once ⇒ ⭐⭐ O(n), despite the nested loop.
⭐   ⭐ Say that out loud — interviewers listen for whether you know why it is linear.
```

| ⭐ Variant | ⭐ The invalid condition |
|---|---|
| ⭐ Longest substring, no repeats | ⭐ a duplicate is in the window |
| ⭐ Longest with **at most k distinct** | ⭐ map size > k |
| ⭐⭐ **Exactly k distinct** | ⭐⭐ **atMost(k) − atMost(k−1)** — the trick worth knowing |
| ⭐ Minimum window containing all of t | ⭐⭐ shrink **while valid**, and record the minimum |
| ⭐ Fixed-size window | ⭐ no while loop — just evict at `right - k` |

⚠️ **"Exactly k" is nearly always solved as "at most k minus at most k−1"**, because shrinking on an
exact condition does not have the monotonic property the template relies on. **Reaching for that
identity immediately marks the pattern as understood rather than memorised.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Max-heap for k largest** | ⭐⭐ O(n log n) space and time — the inversion is the whole point |
| ⭐ Not comparing heap with sorting | ⭐ O(n log k) vs O(n log n) is the trade being tested |
| ⭐ Forgetting quickselect exists | ⭐ O(n) average, and it mutates the input |
| ⭐⭐ **Sorting intervals by the wrong key** | ⭐⭐ start for merging, end for maximising non-overlap |
| ⭐ Not knowing *why* end-sort maximises | ⭐⭐ "finishing earliest leaves most room" is the proof |
| ⭐⭐ **Assigning `cur[1]` when merging** | ⭐⭐ a contained interval shrinks the merge |
| ⭐⭐ **Not asking about touching endpoints** | ⭐⭐ one operator, two different problems |
| ⭐ Only one approach to meeting rooms | ⭐ two + a choice is the scoring move |
| ⭐ Not explaining why the window is linear | ⭐⭐ they listen for this specifically |
| ⭐ Shrinking on an exact-k condition | ⭐⭐ use atMost(k) − atMost(k−1) |
| ⭐ Forgetting to shrink at all | an O(n²) window |
| Recording the answer before restoring validity | off-by-one on every result |

## Interview questions

**Q: Find the k-th largest element. What structure?**
A min-heap of size k, which is the inversion people get backwards. You keep exactly k elements, the
smallest of them sits at the top, and anything smaller than that top is discarded immediately — so it is
O(n log k) time and O(k) space, and it works on a stream where sorting cannot. Sorting is O(n log n) and
simpler, so for k close to n I would just sort. Quickselect is O(n) on average, O(n²) in the worst case,
and it mutates the input. Naming all three and choosing deliberately is more useful than knowing the
fastest one.

**Q: How do you know whether to sort intervals by start or by end?**
By what the question asks. Merging overlapping intervals or inserting one sorts by start, because then
anything that overlaps the current merged interval must begin before it ends, so you only ever compare
against the last result. Maximising the number of non-overlapping intervals sorts by end, and the reason
is a one-line proof: choosing the meeting that finishes earliest leaves the most room for everything
after it. If I cannot state that reason, I do not actually know which key to use.

**Q: Meeting rooms — walk me through it.**
Two approaches. The heap version sorts by start and keeps a min-heap of end times: for each meeting, if
the earliest ending room has already finished, reuse it, then push this meeting's end. The heap size is
the answer, because it is the peak concurrency. The sweep line separates starts and ends, sorts both, and
walks them with two pointers incrementing on a start and decrementing on an end while tracking the
maximum. I would pick the sweep line, because it generalises to maximum-concurrent-anything — if we later
needed the busiest window rather than just the count, it already gives it.

**Q: Why is a sliding window O(n) when it has a nested loop?**
Because each element enters the window exactly once and leaves exactly once, so the inner loop's total
work across the whole run is bounded by n, not by n per iteration. That is amortised analysis, and it is
the thing interviewers listen for — a candidate who writes the template correctly but says "O(n²) because
of the nested while" has not understood why the pattern works.

**Q: Longest substring with exactly k distinct characters?**
As at-most-k minus at-most-k-minus-one. The template relies on the invalid condition being monotonic —
you shrink until the window is valid again — and "exactly k" is not monotonic in that way, since removing
a character can take you from exactly k to k minus one rather than back to valid. Counting at most k and
subtracting at most k minus one converts it into two problems the template handles. Reaching for that
identity is what distinguishes understanding the pattern from remembering it.
