# L-003 · Processes and ports

## What a process is

A **process** is a running program plus everything the OS tracks about it:

```
┌─────────────────────────── PROCESS ────────────────────────────┐
│                                                                │
│  PID 4821                                                      │
│                                                                │
│  ┌──────────────────────── MEMORY ──────────────────────────┐  │
│  │  Stack    ↓  local variables, call frames, return addrs  │  │
│  │           ↓  (grows down)                                │  │
│  │                                                          │  │
│  │           ↑  (grows up)                                  │  │
│  │  Heap     ↑  dynamically allocated objects               │  │
│  │  Data        static/global variables                     │  │
│  │  Code        the instructions themselves                 │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  Registers (incl. PC)   ·   Open file descriptors              │
│  Open sockets           ·   User/group, working directory      │
└────────────────────────────────────────────────────────────────┘
```

**The critical property: each process gets its own private address space.**

When process A reads memory address `0x7fff0000` and process B reads the same address, they get
different data. The OS and the CPU's MMU translate each process's *virtual* addresses to different
*physical* RAM. Process A cannot read process B's memory. Not "shouldn't" — *cannot*. The hardware
refuses.

This is why a crashing Chrome tab doesn't take down your IDE. Isolation is enforced in silicon.

> That stack/heap picture is the same one you'll see on **Day 025** for the JVM. The JVM is a
> process; its heap lives inside the process heap above. Learning it now means Day 025 is a refinement,
> not a new idea.

### Process vs thread — get this right now

| | Process | Thread |
|---|---|---|
| Memory | Private address space | **Shares** the process's heap |
| Has its own | Everything | Stack, registers, program counter |
| Isolation | Hardware-enforced | **None** — shared heap |
| Cost to create | Heavy (~ms) | Light (~µs) |
| Communication | IPC (pipes, sockets, shared memory) | Just read the same variable |
| A crash | Kills only that process | Can take down the whole process |

**"Threads share the heap, each gets its own stack"** — say it until it's automatic. Every
concurrency bug in Stage 1 (Days 064–072) comes from that one line. Two threads sharing a heap
object with no coordination *is* the race condition.

## What a port is

A machine has one IP address but runs many network programs. A packet arrives. Which program gets it?

**The port number.** 16 bits, so 0–65535.

```
                    Machine: 203.0.113.7
      ┌──────────────────────────────────────────────┐
      │                                              │
      │   :22    ──▶  sshd          (PID 900)        │
      │   :80    ──▶  nginx         (PID 1204)       │
      │   :443   ──▶  nginx         (PID 1204)       │
      │   :5432  ──▶  postgres      (PID 2100)       │
      │   :6379  ──▶  redis         (PID 2340)       │
      │   :8080  ──▶  your Spring app (PID 4821)     │
      │                                              │
      └──────────────────────────────────────────────┘
                          ▲
                          │  packet for 203.0.113.7:8080
                          │  → OS reads the TCP header's
                          │    destination port → routes
                          │    to PID 4821
```

**IP gets you to the machine. Port gets you to the program.** That's the entire idea, and it's the
transport layer's whole job from yesterday's table (C-01).

### Port ranges

| Range | Name | Notes |
|---|---|---|
| 0–1023 | Well-known | Need root/admin to bind. 22 SSH, 80 HTTP, 443 HTTPS, 53 DNS |
| 1024–49151 | Registered | 3306 MySQL, 5432 Postgres, 6379 Redis, 8080 HTTP-alt |
| 49152–65535 | Ephemeral | The OS picks these for *outgoing* connections |

Learn the second row — you will type them for the next 400 days.

### The bit almost everyone gets wrong

**A connection is identified by four things, not one:**

```
(source IP, source port, destination IP, destination port)
```

When your browser connects to a server on :443, your browser also has a port — an ephemeral one the
OS assigned, say 51234. The server sees:

```
(your_ip, 51234, server_ip, 443)
```

Open a second tab to the same site:

```
(your_ip, 51235, server_ip, 443)      ← different source port
```

**This is how one server on one port serves thousands of simultaneous clients.** The destination
port is always 443; the tuple is unique because the source port differs. People assume a server
"needs a port per client" — it does not. It needs a *socket* per client, and sockets are
distinguished by the full 4-tuple.

That single fact is the answer to "how does a server handle concurrent connections", and it's the
setup for tomorrow.

## How the OS keeps programs separate

Three mechanisms, all enforced below your code:

1. **Virtual memory** — every process sees addresses starting at 0; the MMU maps them to different
   physical RAM. (Full treatment: B-10, Day 053.)
2. **User/kernel mode** — a CPU privilege bit. Your code runs in user mode and cannot touch
   hardware, other processes' memory, or the page tables. To do anything privileged it must ask the
   kernel via a **system call**, which is a controlled doorway. (B-01, Day 023.)
3. **The port table** — only one process may bind a given port. Try a second and you get
   `Address already in use`.

That last one is the most common error you will hit in Stage 4. Now you know it's not a Spring
problem — it's the OS refusing to let two programs claim the same doorway.

## Type this yourself

```java
import java.net.ServerSocket;

public class PortDemo {
    public static void main(String[] args) throws Exception {
        ServerSocket server = new ServerSocket(8080);
        System.out.println("Bound to port 8080. PID: " + ProcessHandle.current().pid());
        System.out.println("Now run this same program again in another terminal.");
        Thread.sleep(300_000);   // hold the port for 5 minutes
    }
}
```

Run it. Then run it **again in a second terminal**. Read the exception — `BindException: Address
already in use`. You just proved mechanism 3 yourself.

While it's running, in a third terminal:

```bash
# Windows
netstat -ano | findstr :8080
tasklist | findstr <PID>

# Linux/Mac
lsof -i :8080
```

Match the PID to the one your program printed. You are now looking at your own process in the OS's
port table.

## Common mistakes

| Mistake | Correction |
|---|---|
| "A server needs one port per client" | One listening port serves thousands. Connections are distinguished by the 4-tuple, not the port alone. |
| Thinking threads have separate memory | Threads share the heap. That sharing is the entire source of concurrency bugs. |
| "localhost and 127.0.0.1 are different things" | Same thing — `localhost` is a hostname that resolves to the loopback address. |
| Confusing PID and port | A PID identifies a process to the OS. A port identifies a network endpoint. One process can hold many ports. |
| Assuming `Address already in use` is a framework bug | It's the OS. Something already holds that port — often your own previous run that didn't exit. |

## Interview questions

**Q: What's the difference between a process and a thread?**
> A process has its own private virtual address space enforced by the MMU; a thread lives inside a
> process and shares its heap, having only its own stack, registers and program counter. Processes
> are isolated and expensive to create; threads are cheap and share memory, which is why they need
> synchronisation.

**Q: What is a port?**
> A 16-bit number identifying a network endpoint within a machine. The IP address routes a packet to
> the machine; the port tells the OS which process should receive it.

**Q: How does one web server handle thousands of simultaneous connections on port 443?**
> A TCP connection is identified by the 4-tuple of source IP, source port, destination IP and
> destination port. Every client has a different source IP or ephemeral source port, so every
> connection is a distinct tuple even though the destination port is always 443. The server holds a
> separate socket per connection.

**Q: Why can't one process read another's memory?**
> Virtual memory. Each process has its own page table mapping virtual to physical addresses, and the
> MMU enforces it in hardware. An access outside your mapping traps to the kernel as a segmentation
> fault.

**Q: What does "Address already in use" mean?**
> Another process is already bound to that port. Only one process may listen on a given port and
> interface. It can also occur briefly after a process exits, while the socket sits in `TIME_WAIT`.
