# Day 163

**L-163** · Spring Data repositories — what is generated, and where it stops helping

**Time:** 3 hrs · **Mode:** NEW

> Spring Data is the layer people meet first and understand last. You declare an interface, never
> write an implementation, and queries appear. Today is what is actually happening, the four ways to
> define a query and when each is right, and — more usefully — **the three places where the
> convenience becomes a liability.**

---

# Part 1 — What is generated, and how

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByStatusAndPlacedAtAfter(OrderStatus status, Instant after);
}
```

At startup, `JpaRepositoryFactoryBean` creates a **JDK dynamic proxy** implementing your interface.
Every call is intercepted and routed: to `SimpleJpaRepository` for the inherited CRUD methods, or to
a **`PartTreeJpaQuery`** built by parsing the method name for derived queries.

**The parse happens at startup**, so a method name Spring cannot resolve — a misspelled property, a
field that does not exist — is a **startup failure**, not a runtime one. Day 133's principle again,
and it is one of Spring Data's genuinely good properties.

This is Day 132's `BeanPostProcessor` plus Day 137's proxying plus Day 056A's dynamic proxies, all
doing one job. **You built each of those by hand before meeting this.**

## The interface hierarchy, and which to extend

| Interface | Gives you |
|---|---|
| `Repository<T,ID>` | ⭐ nothing — a pure marker. **Best default for a curated API** |
| `CrudRepository` | `save`, `findById`, `delete`, `count` |
| `PagingAndSortingRepository` | plus `findAll(Pageable)` |
| `JpaRepository` | plus `flush`, `saveAll`, `getReferenceById`, `deleteAllInBatch` |

**⭐ The argument for `Repository<T,ID>`:** `JpaRepository` exposes `findAll()` with no arguments and
`deleteAll()` on your domain API. Every caller in the codebase can now load the entire table into
memory or delete everything, and neither is a thing you intended to offer.

```java
public interface OrderRepository extends Repository<Order, Long> {
    Optional<Order> findById(Long id);
    Order save(Order order);
    Page<Order> findByCustomerId(Long customerId, Pageable pageable);   // ⭐ always paginated
}
```

**Declare exactly the operations the domain needs.** This is Day 090's interface segregation applied
to persistence, and it takes thirty seconds.

**`getReferenceById` is worth knowing:** it returns a lazy proxy without hitting the database — ideal
for setting a `@ManyToOne` when you have only the id, since you need the reference, not the data.

# Part 2 — The four ways to define a query

### 1. Derived from the method name

```java
List<Order> findByStatus(OrderStatus status);
List<Order> findByCustomerIdAndStatusOrderByPlacedAtDesc(Long id, OrderStatus s);
Optional<Order> findFirstByCustomerIdOrderByPlacedAtDesc(Long customerId);
boolean existsByPublicId(UUID publicId);                    // ⭐ cheaper than findBy + isPresent
long countByStatus(OrderStatus status);
List<Order> findByTotalBetween(BigDecimal min, BigDecimal max);
List<Order> findByCustomerNameContainingIgnoreCase(String q);
```

Great for one or two conditions. **The limit is legibility**, and it arrives fast:

```java
List<Order> findByStatusAndCustomerIdAndPlacedAtBetweenAndTotalGreaterThanOrderByPlacedAtDesc(...);
```

**Rule of thumb: three conditions maximum, then switch to `@Query`.** The name is not
self-documenting past that, and a rename means touching every call site.

⚠️ `findByCustomerName` traverses `customer.name` — a **join**, which is fine, but be aware you have
written a join in a method name and it will not be obvious to a reviewer.

### 2. `@Query` with JPQL

```java
@Query("""
    select o from Order o
    where o.status = :status
      and o.placedAt between :from and :to
      and o.total > :min
    order by o.placedAt desc
""")
List<Order> search(@Param("status") OrderStatus status, @Param("from") Instant from,
                   @Param("to") Instant to, @Param("min") BigDecimal min);
```

⭐ **JPQL in `@Query` is validated at startup.** A typo in a property name fails the application
start. Native queries are not — which is one more reason to prefer JPQL where it suffices.

**Always `:named` parameters, never `?1`** — positional parameters silently break when someone
reorders the method signature, and nothing warns you.

### 3. Specifications — Day 161

For genuinely dynamic filters. Not for static queries; the verbosity is not worth it.

### 4. A custom fragment — for anything the above cannot do

```java
public interface OrderRepositoryCustom {
    List<OrderStats> statsFor(Long customerId);
}

class OrderRepositoryCustomImpl implements OrderRepositoryCustom {    // ⭐ the "Impl" suffix is required
    private final JdbcClient db;
    public List<OrderStats> statsFor(Long customerId) { ... }         // Day 156
}

public interface OrderRepository extends Repository<Order, Long>, OrderRepositoryCustom { }
```

**Spring Data finds `<InterfaceName>Impl` by naming convention.** Get the suffix wrong and the bean is
simply not found, with a confusing startup error. This is the correct place for `JdbcClient` work,
window functions, or anything JPA makes awkward — and it keeps the caller's view as one repository.

# Part 3 — ⭐ The three places the convenience turns into a liability

### 1. `save()` in a loop

```java
for (Order o : orders) repo.save(o);     // ⭐ flushes? selects? depends.
```

For **new** entities this is fine — `persist`, batched if Day 158's `SEQUENCE` is in place. For
**detached** entities each `save` is a `merge`, which is **a SELECT per entity** (Day 162). Ten
thousand detached saves is twenty thousand statements.

```java
repo.saveAll(orders);      // ⭐ better: still per-entity, but batching engages properly
```

**And the honest answer for a real bulk operation** is a single `@Modifying` statement or a
`JdbcClient` batch. `saveAll` is not a bulk operation; it is a loop with better batching.

### 2. `deleteAll()` and `deleteById` in a loop

```java
repo.deleteAll();                    // ⭐ SELECTs everything, then one DELETE per row
repo.deleteAllInBatch();             // ⭐ one DELETE statement
```

`deleteAll()` loads every entity first — because it must cascade and fire callbacks.
`deleteAllInBatch()` issues one statement and skips both. **Know which semantics you need**; the
performance difference on 100,000 rows is four orders of magnitude.

### 3. ⭐ Repository methods returning entities to the service layer

Every derived method returns managed entities, which means Day 160's fetch concerns apply to all of
them. `findByStatus` returning 50,000 orders with a lazy customer is an N+1 waiting for a caller.

**The discipline:** every collection-returning method takes a `Pageable`, and read paths return
projections rather than entities. If a repository method returns `List<Order>` with no bound, ask what
stops it returning the whole table.

## Two more sharp edges worth knowing

**`Optional` vs `null` vs exception:**
```java
Optional<Order> findByPublicId(UUID id);       // ⭐ correct for "may not exist"
Order getByPublicId(UUID id);                  // returns null — avoid
@Query(...) Stream<Order> streamAll();          // must be closed (Day 161)
```

**Derived delete methods run per row:**
```java
@Transactional
long deleteByStatus(OrderStatus status);       // ⭐ SELECT then one DELETE per row
```
Same shape as `deleteAll()`. For volume, use `@Modifying`.

# Part 4 — Repository or service? The layering question

```java
// ❌ transaction boundary in the repository
public interface OrderRepository { @Transactional Order save(Order o); }

// ✅ transaction boundary in the service
@Service
public class OrderService {
    @Transactional
    public OrderResponse place(CreateOrderRequest req) {
        Order order = repo.save(toOrder(req));
        inventory.reserve(order);              // ⭐ same transaction, by design
        return OrderResponse.from(order);
    }
}
```

**The transaction boundary is a business decision, not a persistence one** — "these operations
succeed or fail together" is a statement about the domain. Day 164 develops this properly.

Note that `SimpleJpaRepository`'s methods are already `@Transactional`, so calling `save()` outside a
service transaction still works — it starts its own. That convenience is exactly why people
accidentally end up with one transaction per repository call and no atomicity across them.

**Should you wrap repositories behind your own interface?** The purist DDD answer is yes — define
`OrderRepository` in the domain, implement it in infrastructure, keep JPA out of the domain. The
pragmatic answer is that `Repository<T,ID>` with a curated method list already gives you most of that
benefit for a fraction of the code. **Take the curated interface; add the port-and-adapter layer only
if the domain genuinely needs to be persistence-ignorant.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Extending `JpaRepository` by default | exposes `findAll()` and `deleteAll()` to every caller |
| Derived names with five conditions | unreadable; rename touches every call site |
| Positional `?1` parameters | silently break on signature reorder |
| Native query where JPQL would do | loses startup validation |
| `save()` in a loop over detached entities | one SELECT per entity |
| `deleteAll()` for volume | loads everything first |
| Unbounded `List<Order>` return types | one caller from loading the table |
| Entities returned to the web layer | Day 147 and Day 160 |
| `@Transactional` on repository methods | transaction boundary in the wrong layer |
| Wrong `Impl` suffix on a fragment | bean not found, confusing error |
| `findBy...().isPresent()` instead of `existsBy` | loads the whole row to answer a boolean |

## Interview questions

**Q: How does Spring Data generate an implementation?**
A JDK dynamic proxy created at startup by a `BeanPostProcessor`. Calls route either to
`SimpleJpaRepository` for CRUD or to a query built by parsing the method name. Because parsing is at
startup, an invalid method name fails the application start rather than the first request.

**Q: Which repository interface do you extend?**
`Repository<T,ID>` with the methods I actually want. `JpaRepository` publishes `findAll()` and
`deleteAll()` on my domain API, and I do not want every caller able to load or delete the whole
table.

**Q: When do you stop using derived query methods?**
About three conditions. Past that the name stops being readable and a rename touches every call site,
so `@Query` with JPQL — which is still validated at startup — is better.

**Q: What is wrong with `save()` in a loop?**
For detached entities each call is a `merge`, which selects the current row first — so 10,000 saves
is 20,000 statements. `saveAll` batches better, but a real bulk change should be one `@Modifying`
statement.

1. Declare a repository with a deliberately misspelled property in a derived method. **Read the

2. Extend `JpaRepository`, then rewrite as `Repository<Order, Long>` with four methods. Note what you

## 🎙️ Articulation drill

Two minutes: **"How do Spring Data repositories work, and how do you use them well?"**

Explain the generation — a proxy built at startup, method names parsed then, so mistakes fail the
deploy. Then move straight to judgement, because that is what separates answers: extend
`Repository<T,ID>` and declare only what the domain needs, so `findAll()` and `deleteAll()` are not
part of your API; derived names up to about three conditions and JPQL after that; a `JdbcClient`
fragment for anything JPA makes awkward. Close on the two performance traps — `save()` in a loop is a
select per entity, and `deleteAll()` loads every row before deleting it.
