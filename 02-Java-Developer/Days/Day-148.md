# Day 148

**L-148** · Bean Validation — `@Valid`, groups, custom constraints, and where validation belongs

**Time:** 3 hrs · **Mode:** NEW

> Day 105 drew the trust boundary and made the distinction that matters: **structural validation at
> the edge, business rules in the domain.** Today is the machinery for the first half, plus the
> discipline to keep the second half out of it.
>
> The trap on this day is subtle: Bean Validation is pleasant enough that people push business rules
> into it, and then discover those rules are unreachable from jobs, unenforceable in the database, and
> untestable without a validator factory.

# Part 1 — The mechanism, so the failures make sense

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

**Not transitive in Boot 3** — `spring-boot-starter-web` no longer brings it. The failure mode is
silent and nasty: your `@NotBlank` annotations compile, they are on the classpath as annotations, and
**nothing validates anything**. Blank product IDs sail through. If validation appears to do nothing,
this is the first thing to check.

```java
@PostMapping
OrderResponse create(@Valid @RequestBody CreateOrderRequest req) { ... }
```

At Day 145's step 4, `RequestResponseBodyMethodProcessor` reads the body, then — seeing `@Valid` —
runs the validator. Failure throws `MethodArgumentNotValidException`, which
`DefaultHandlerExceptionResolver` maps to **400** at step 8. Your controller body never executes.

**⭐ The three annotations, distinguished — this is a standing interview question:**

| | Where | What it does |
|---|---|---|
| `@Valid` | parameters, fields | JSR-380 standard. Cascades into nested objects |
| `@Validated` | ⭐ **class level** | Spring's. Enables **method-level validation via an AOP proxy** (Day 137), and is the only one that takes **groups** |
| `@Valid` on a nested field | field | ⭐ **required for cascade.** Without it, the nested object is not validated at all |

```java
public record CreateOrderRequest(
        @NotBlank String productId,
        @Min(1) int quantity,
        @Valid @NotNull ShippingAddress shipTo) { }   // ⭐ @Valid or shipTo's own rules are skipped
```

**The missing-cascade bug is the single most common Bean Validation defect**, because it fails open:
everything looks validated, and the nested object is not.

## Validating things that are not request bodies

```java
// Query params and path variables need @Validated on the CLASS
@RestController
@Validated                                                    // ⭐ enables the proxy
class OrderController {
    @GetMapping
    Page<OrderResponse> list(@RequestParam @Min(1) @Max(100) int size) { ... }
}
```

Without class-level `@Validated`, constraints on `@RequestParam`/`@PathVariable` are **silently
ignored** — the annotation is present and does nothing. And note the different exception:
`ConstraintViolationException`, **not** `MethodArgumentNotValidException`, which by default becomes a
**500**, not a 400. Day 149 must handle both, and this is the reason.

## Property validation

Day 142 used this: `@Validated` on a `@ConfigurationProperties` class makes the constraints a
**startup gate**. Same annotations, entirely different lifetime — a misconfiguration fails the deploy
rather than the customer.

# Part 2 — The catalogue, and the ones with sharp edges

| Constraint | Note |
|---|---|
| `@NotNull` / `@NotEmpty` / `@NotBlank` | ⭐ `""` passes `@NotNull`; `" "` passes `@NotEmpty`. **`@NotBlank` for strings, almost always** |
| `@Size(min,max)` | strings, collections, maps, arrays |
| `@Min` `@Max` | integral types only — **not `BigDecimal`** |
| `@DecimalMin` `@DecimalMax` | ⭐ use for money |
| `@Digits(integer,fraction)` | the right money constraint: `@Digits(integer=10, fraction=2)` |
| `@Positive` `@PositiveOrZero` | clearer than `@Min(0)` |
| `@Email` | ⭐ **very permissive by design.** `a@b` passes. It is a typo check, not verification — Day 112: the only real check is sending a mail |
| `@Pattern` | ⚠️ **ReDoS** (Day 069). A user-facing `@Pattern` with nested quantifiers is a DoS vector |
| `@Past` `@Future` `@PastOrPresent` | use `@FutureOrPresent` for "not in the past" or clock skew bites |
| `@AssertTrue` | on a **method** — see below |

## `@AssertTrue` — cross-field validation without a custom constraint

```java
public record DateRange(@NotNull LocalDate from, @NotNull LocalDate to) {
    @AssertTrue(message = "'from' must not be after 'to'")
    boolean isRangeValid() {                       // ⭐ "is"/"get" prefix required
        return from == null || to == null || !from.isAfter(to);
    }
}
```

**The cheapest correct answer to cross-field validation**, and most people write a whole custom
constraint instead. Two rules: the method must follow JavaBean naming, and it must tolerate nulls —
it runs even when `@NotNull` has already failed, so an unguarded version NPEs inside the validator.

Its limitation is the error path: the violation is reported against `rangeValid`, not against `from`
or `to`, so a form cannot highlight the right field. When that matters, write the class-level custom
constraint.

## A custom constraint, properly

```java
@Target({FIELD, PARAMETER})
@Retention(RUNTIME)
@Constraint(validatedBy = ProductIdValidator.class)
public @interface ValidProductId {
    String message() default "must be a known product id";
    Class<?>[] groups() default {};                          // ⭐ required by spec
    Class<? extends Payload>[] payload() default {};         // ⭐ required by spec
}

class ProductIdValidator implements ConstraintValidator<ValidProductId, String> {
    private final ProductCatalog catalog;
    ProductIdValidator(ProductCatalog catalog) { this.catalog = catalog; }   // ⭐ DI works

    @Override public boolean isValid(String value, ConstraintValidatorContext ctx) {
        return value == null || catalog.exists(value);       // ⭐ null is @NotNull's job
    }
}
```

Two rules that are conventions with teeth:

1. **Return `true` for null.** Each constraint has exactly one job. Combining null-checking into
   every validator means `@NotNull` becomes optional and error messages get confusing.
2. **Validators are Spring beans**, so they can inject repositories. Which raises the day's real
   question.

# Part 3 — ⭐ The line: structural validation vs business rules

**A database lookup inside a validator is where this goes wrong**, and the reasons are concrete:

| Problem | Detail |
|---|---|
| **Unreachable** | a Kafka consumer or batch job creating an order never passes through `@Valid`, so the rule is simply absent there |
| **TOCTOU** | the product exists at validation time and is deleted 5 ms later. The check gives an illusion of safety that only the database constraint can actually provide |
| **Wrong error contract** | "product not found" is a 404 or a 422 business outcome, not a 400 malformed-request |
| **Hidden I/O** | a query per field, per request, invisible in the controller |
| **Untestable cheaply** | needs a validator factory and a repository |

**The rule Day 105 gave, restated with the Spring names:**

> **`@Valid` answers "is this request well-formed?" The service answers "is this operation
> allowed?"** The first can be decided from the payload alone. The second needs state.

| Rule | Where |
|---|---|
| `quantity` is between 1 and 100 | ⭐ `@Min`/`@Max` — payload alone |
| `email` looks like an email | ⭐ `@Email` |
| `from` is not after `to` | ⭐ `@AssertTrue` |
| the product **exists** | service — needs state |
| the customer has **credit** | service |
| the order is **cancellable in its current status** | service — needs the entity |
| the user **may** cancel this order | ⭐ authorization (Day 118), not validation at all |

The last row is worth a beat: "may this user do this?" being answered in a validator is a real
pattern in the wild, and it means the authorization decision is invisible to security review, absent
from every non-HTTP path, and reported as a 400 instead of a 403.

## Validation groups — for the case where the same type has two contracts

```java
public interface OnCreate {}
public interface OnUpdate {}

public record CustomerDto(
        @Null(groups = OnCreate.class) @NotNull(groups = OnUpdate.class) UUID id,
        @NotBlank(groups = {OnCreate.class, OnUpdate.class}) String name) { }

@PostMapping void create(@Validated(OnCreate.class) @RequestBody CustomerDto dto) { }
@PutMapping  void update(@Validated(OnUpdate.class) @RequestBody CustomerDto dto) { }
```

**Note `@Validated`, not `@Valid` — only Spring's annotation carries groups.**

And note the honest caveat: this exists because someone shared a DTO between create and update, which
Day 147 argued against. **Separate `CreateCustomerRequest` and `UpdateCustomerRequest` types are
simpler and need no groups at all.** Groups earn their place in a legacy contract you cannot split,
or where the same type is validated at genuinely different lifecycle stages.

## Messages that reach a human

```properties
# messages.properties
order.quantity.range=Quantity must be between {min} and {max}
```
```java
@Min(value = 1, message = "{order.quantity.range}")
```

Externalised messages give you i18n and, more usefully, a single place to keep wording consistent.
Day 149 shapes these into the RFC 7807 `errors` array. **Do not put internal detail in a message** —
it goes to the client verbatim.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Missing `starter-validation` in Boot 3 | annotations present, nothing validated, fails open |
| ⭐ No `@Valid` on a nested field | nested object silently unvalidated |
| No `@Validated` on the class for param constraints | constraints silently ignored |
| Not handling `ConstraintViolationException` | param violations return 500 instead of 400 |
| `@NotNull` on a string that must have content | `""` and `"   "` pass |
| `@Min` on `BigDecimal` | does not apply; use `@DecimalMin`/`@Digits` |
| Repository lookups in validators | unreachable from jobs, TOCTOU, wrong status code |
| Authorization in a validator | invisible to security review; 400 instead of 403 |
| Validator NPEs on null | forgot the "null is `@NotNull`'s job" rule |
| Missing `groups()`/`payload()` in a custom annotation | fails at runtime with an unhelpful message |
| `@Pattern` from user input with nested quantifiers | ReDoS (Day 069) |
| Validating only on the entity | the error arrives at flush time, far from the request |

## Interview questions

**Q: `@Valid` vs `@Validated`?**
`@Valid` is the JSR-380 standard, used on parameters and nested fields to cascade. `@Validated` is
Spring's — it goes on the class to enable method-level validation via a proxy, and it is the only one
that supports groups. Also, they throw different exceptions, so error handling must cover both.

**Q: Where do you draw the line between validation and business rules?**
Validation answers "is this well-formed?" from the payload alone. Anything that needs state — does
the product exist, has the customer got credit — belongs in the service, because the same operation
also arrives from jobs and consumers that never pass through `@Valid`, and because a database check
in a validator is a TOCTOU illusion.

**Q: How do you validate that one field is not after another?**
`@AssertTrue` on a boolean method for the simple case. A class-level custom constraint when the error
has to be attributed to a specific field for the UI.

**Q: Why might validation silently do nothing?**
In Boot 3, `spring-boot-starter-validation` is not pulled in by `starter-web`. Or the nested field is
missing `@Valid`, or the class is missing `@Validated` for parameter constraints.

## 🎙️ Articulation drill

Two minutes: **"How do you handle validation in a Spring API?"**

Structural validation at the boundary with Bean Validation on request DTOs — `@Valid`, cascaded into
nested objects, `@AssertTrue` for cross-field. Then draw the line explicitly: anything requiring
state goes in the service, because the same operation arrives from jobs and consumers, and because a
database check in a validator is a race condition wearing a helpful annotation. Finish on the failure
mode that shows you have shipped this: parameter constraints throw a different exception than body
constraints, and if the advice does not handle both, half your validation errors are 500s.
