# Part 1 — The test types, cheapest first

| Type | Starts | Speed | Verifies |
|---|---|---|---|
| ⭐ **Plain JUnit** | ⭐ **nothing** | ⭐ ms | **business logic. Most of your tests** |
| `@WebMvcTest` | web layer only | ~1 s | routing, serialization, validation, security |
| `@DataJpaTest` | JPA + a database | ~2 s | queries, mapping, constraints |
| `@RestClientTest` | HTTP client | ~1 s | outbound calls (Day 154) |
| `@JsonTest` | Jackson only | fast | serialization contracts (Day 150) |
| `@SpringBootTest` | ⭐ everything | ⭐ 5–30 s | wiring and end-to-end flows. **A few** |

**⭐ The rule that keeps a suite fast: if the test does not need Spring, do not start Spring.**

```java
// ⭐ No annotations. No context. Milliseconds.
class OrderPricingTest {
    private final OrderPricing pricing = new OrderPricing(new FixedTaxRates());

    @Test void appliesBulkDiscountAboveTenUnits() {
        assertThat(pricing.total(item("P-1", new BigDecimal("10.00"), 12)))
            .isEqualByComparingTo("108.00");
    }
}
```

**Day 131's constructor injection is what makes this possible** — a class with constructor
dependencies is `new`-able in a test. Field injection would force a Spring context for a pure
calculation. That is the practical payoff of a decision made 52 days earlier.

# Part 2 — The slices worth knowing

## `@WebMvcTest`

```java
@WebMvcTest(OrderController.class)
@Import(SecurityConfig.class)                       // ⭐ or your real security is NOT applied
class OrderControllerTest {

    @Autowired MockMvc mockMvc;
    @MockitoBean OrderService service;               // ⭐ Boot 3.4+; was @MockBean

    @Test
    @WithMockUser(authorities = "order:write")
    void createsOrder() throws Exception {
        given(service.place(any())).willReturn(new OrderResponse(ID, "P-1", 2, TEN, "PENDING", NOW));

        mockMvc.perform(post("/api/v1/orders")
                    .contentType(APPLICATION_JSON)
                    .content("""{"productId":"P-1","quantity":2}""")
                    .with(csrf()))                                     // ⭐ if CSRF is enabled
               .andExpect(status().isCreated())
               .andExpect(header().exists("Location"))                 // ⭐ Day 146
               .andExpect(jsonPath("$.status").value("PENDING"));
    }

    @Test
    @WithMockUser
    void rejectsInvalidQuantity() throws Exception {
        mockMvc.perform(post("/api/v1/orders").contentType(APPLICATION_JSON)
                    .content("""{"productId":"P-1","quantity":0}""").with(csrf()))
               .andExpect(status().isBadRequest())
               .andExpect(jsonPath("$.type").value(containsString("validation-error")))  // Day 149
               .andExpect(jsonPath("$.errors[0].field").value("quantity"));
    }
}
```

**⭐ This slice is where four of Stage 4's days are actually verified:** Jackson configuration
(Day 150), Bean Validation (Day 148), the RFC 7807 contract (Day 149), and security rules (Day 169).
It is fast enough to run on every save, and it exercises the real serializer, the real validator and
the real filter chain.

**⭐ `@Import(SecurityConfig.class)` is easy to forget and dangerous.** Without it Boot applies a
*default* security configuration, so your security tests pass against rules you never wrote and your
real ones go untested.

**Two more facts:** `@WebMvcTest` does not start a server — `MockMvc` calls the DispatcherServlet
directly, which is why it is fast and also why it does not catch a problem in the servlet container.
And `.with(csrf())` is needed wherever CSRF is enabled (Day 172), or every POST is 403.

## `@DataJpaTest`

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = NONE)          // ⭐⭐ use the REAL database (Day 184)
class OrderRepositoryTest {

    @Autowired OrderRepository repo;
    @Autowired TestEntityManager em;

    @Test
    void findsByStatusWithOneQuery() {
        em.persist(order(PENDING)); em.persist(order(SHIPPED));
        em.flush(); em.clear();                                    // ⭐⭐ see below

        SQLStatementCountValidator.reset();
        var results = repo.findByStatus(PENDING);
        assertThat(results).hasSize(1);
        SQLStatementCountValidator.assertSelectCount(1);           // ⭐ Day 160's N+1 guard
    }
}
```

**⭐ `em.flush(); em.clear();` is the line that makes repository tests honest.** Without it the entity
is still in the persistence context (Day 162), so `findById` returns it from the first-level cache
and **your query is never executed.** The test passes whether or not the mapping is correct.

**⭐ `replace = NONE` matters even more.** `@DataJpaTest` defaults to swapping in an embedded H2, and
H2 is not PostgreSQL: different SQL dialect, different constraint behaviour, no partial indexes, no
`jsonb`, different locking. **A test suite green on H2 tells you nothing about production.** Day 184
is the answer.

`@DataJpaTest` is transactional and rolls back per test, which is convenient and hides one thing:
constraint violations that surface only at commit. Use `@Commit` or flush explicitly to check those.

## `@RestClientTest` and `@JsonTest`

```java
@JsonTest
class OrderResponseJsonTest {
    @Autowired JacksonTester<OrderResponse> json;

    @Test void serialisesInstantAsIso() throws Exception {
        assertThat(json.write(response)).extractingJsonPathStringValue("$.placedAt")
            .isEqualTo("2026-08-14T10:23:45Z");                   // ⭐ Day 150's contract, pinned
    }
}
```

**A serialization change is an API breaking change** (Day 109). This slice pins it in milliseconds.

# Part 3 — ⭐ The context cache, which decides your suite's runtime

**Spring caches application contexts across test classes, keyed by the full configuration.** Two test
classes with identical configuration share one context; **any difference creates a new one.**

**⭐ Each new context is 3–20 seconds.** A suite with 40 distinct configurations spends ten minutes
starting Spring.

**What creates a new context:**

| Cause | Note |
|---|---|
| A different slice annotation | expected |
| ⭐ **Different `@MockitoBean` sets** | ⭐ **the most common accidental cause** |
| `@TestPropertySource` / different `@ActiveProfiles` | |
| `@DirtiesContext` | ⭐ evicts the cache entry — use very sparingly |
| A different `@Import` or nested `@Configuration` | |

**⭐ The single highest-impact optimisation in a Spring test suite is standardising configurations.**

```java
// ⭐ One base class → ONE context shared by every integration test
@SpringBootTest(webEnvironment = RANDOM_PORT)
@ActiveProfiles("test")
@Testcontainers                                       // Day 184
abstract class IntegrationTestBase {
    @Container static final PostgreSQLContainer<?> POSTGRES = new PostgreSQLContainer<>("postgres:16");
    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) { r.add("spring.datasource.url", POSTGRES::getJdbcUrl); }
}
```

**Then every integration test extends it and the context starts once for the whole run.**

```
-Dspring.test.context.cache.maxSize=64      # ⭐ default is 32; raise it for large suites
logging.level.org.springframework.test.context.cache=DEBUG   # ⭐ prints cache hits and misses
```

**Turn that logging on once and read it.** Seeing the misses is what turns "the tests are slow" into
a specific, fixable list.

**⭐ And `@DirtiesContext` deserves a warning:** it evicts the cached context, so every subsequent
test class pays a full restart. One careless annotation can add minutes. If a test needs a clean
state, reset the state — not the context.

# Part 4 — What to test at each level, and the mocking line

## The split

| Level | Test |
|---|---|
| ⭐ **Unit** | ⭐ **business rules, calculations, state machines, edge cases.** The bulk |
| Slice | serialization, validation, routing, security, queries |
| ⭐ **Integration** | ⭐ **the wiring, and a few real end-to-end flows** |

**Day 097's pyramid, concretely: if your suite is mostly `@SpringBootTest`, the design is telling you
your business logic is not separable from the framework** — which is a coupling problem, not a
testing problem.

## ⭐ Where mocking stops helping

Day 075's argument, applied:

```java
// ❌ tests the mock, not the behaviour
@Test void placesOrder() {
    given(repo.save(any())).willReturn(order);
    service.place(request);
    verify(repo).save(any());                    // ⭐ asserts you called a method you wrote
}
```

**⭐ Never mock the thing under test's collaborator when the collaborator's *behaviour* is the point.**
Mocking a repository verifies you called `save`; it cannot verify the constraint held, the query was
right, or the transaction committed. **Repositories and HTTP clients are better tested against the
real thing** — Testcontainers and WireMock (Day 184).

**Mock at the boundary you do not own and cannot make fast:** a payment gateway, an email provider,
the clock.

```java
@Bean Clock clock() { return Clock.systemUTC(); }              // ⭐ inject it
// in tests:
Clock.fixed(Instant.parse("2026-08-14T10:00:00Z"), UTC);       // ⭐ deterministic time
```

**⭐ `Instant.now()` scattered through the code makes time untestable** and produces the classic
flaky test that fails at midnight or during DST. Injecting a `Clock` is a small discipline with a
large payoff — and it is the FIRST principle's "repeatable" made concrete.

## Testing the things Stage 4 built

```java
@Test void asyncMethodRunsOnAnotherThread() { ... }            // Day 177 — use Awaitility, not sleep
@Test void scheduledJobIsIdempotent() { ... }                  // Day 178
@Test void circuitOpensOnInfrastructureFailureOnly() { ... }   // Day 181
@Test void tenantCannotSeeAnotherTenantsData() { ... }         // Day 176 — the highest-value test
```

```java
await().atMost(5, SECONDS).untilAsserted(() -> verify(mailer).send(any()));   // ⭐ Awaitility
```

**⭐ `Thread.sleep` in a test is a flaky test with a delay built in.** Awaitility polls until the
condition holds or the timeout expires — faster when things work, and it fails with a useful message
when they do not.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `@SpringBootTest` for everything | minutes of runtime; slow feedback kills TDD |
| ⭐ Forgetting `@Import(SecurityConfig)` in `@WebMvcTest` | tests a default config you never wrote |
| ⭐ H2 instead of the real database | dialect, constraints and locking all differ |
| No `em.flush()/clear()` in repository tests | the query never runs; first-level cache answers |
| ⭐ Many distinct `@MockitoBean` sets | a new context each — minutes of startup |
| `@DirtiesContext` casually | evicts the cache; everything after pays |
| Mocking repositories to test queries | verifies you called a method you wrote |
| `Instant.now()` instead of an injected `Clock` | untestable, flaky at boundaries |
| `Thread.sleep` for async | flaky and slow |
| Missing `.with(csrf())` | every POST 403s and you disable CSRF to "fix" it |
| Only positive security tests | authorization bugs return 200 (Day 169) |
| Tests sharing mutable state | order-dependent failures |

## Interview questions

**Q: How do you structure tests in a Spring application?**
Mostly plain JUnit for business logic with no Spring context at all — constructor injection makes
that possible. Slices for the framework-owned concerns: `@WebMvcTest` for routing, serialization,
validation and security, `@DataJpaTest` against a real database for queries. A small number of full
`@SpringBootTest` runs for wiring and key end-to-end flows.

**Q: Why is your test suite slow, and what do you do about it?**
Almost always the context cache. Spring caches contexts keyed by configuration, and any variation —
especially different sets of mocked beans — creates a new one at several seconds each. I standardise
integration tests onto a shared base class so one context serves the whole run, and I turn on the
context-cache DEBUG logging to see the misses.

**Q: Why not H2 for repository tests?**
Because it is a different database. Dialect, constraint behaviour, locking, partial indexes, `jsonb`
— all differ, so a green suite proves nothing about production. Testcontainers runs the real engine.

**Q: When is mocking the wrong choice?**
When the collaborator's behaviour is what you are verifying. Mocking a repository to test a query
asserts that you called a method you wrote — it cannot tell you the SQL is right or the constraint
holds. Mock the boundaries you do not own; use the real thing for the ones you do.

## Mini task

1. Take one `@SpringBootTest` for a pure calculation and rewrite it as plain JUnit. Compare runtimes.
2. Write a `@WebMvcTest` covering a 201 with `Location`, a 400 with RFC 7807 errors, and a 403.
   **Then remove `@Import(SecurityConfig)` and watch the 403 test change behaviour.**
3. Write a `@DataJpaTest` without `em.flush()/clear()`. Break the entity mapping. **Confirm the test
   still passes.** Add the two calls.
4. Run it against H2 and then against real PostgreSQL with `replace = NONE`. Find one behaviour that
   differs.
5. Enable context-cache DEBUG logging. Run the full suite and **count the contexts created.**
6. Introduce a shared `IntegrationTestBase`. Re-run and compare total time.
7. Add `@DirtiesContext` to one class and measure the suite again.
8. Replace `Instant.now()` with an injected `Clock`. Write a test that pins time across a DST
   boundary.
9. Replace a `Thread.sleep` in an async test with Awaitility. Compare runtime and reliability over 20
   runs.
10. Write the cross-tenant negative test (Day 176). Delete a filter and confirm only that test fails.

## 🎙️ Articulation drill

Two minutes: **"How do you test a Spring Boot application?"**

Cheapest thing that verifies the claim: plain JUnit for logic — and note that constructor injection
is what makes it possible — slices for framework concerns, a handful of full context tests for wiring.
Then the two things that separate someone who has maintained a suite: the context cache, where
varying mocked beans silently creates a new several-second context per test class, so integration
tests share a base class; and using the real database rather than H2, because dialect and constraint
behaviour differ enough that a green suite proves nothing.
