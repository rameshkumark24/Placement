# Day 369

**L-369** · GitHub Actions — caching, secrets, and the supply-chain traps

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Actions is easy to use badly and the failures are quiet: a cache key that never hits, a
> long-lived cloud credential in a secret, and an action pinned by tag that its author can replace
> tomorrow.**
>
> The mechanics take twenty minutes. **The rest of today is the three things that actually go
> wrong.**

---

# Part 1 — ⭐ The model

```
⭐ EVENT (push, pull_request, schedule, workflow_dispatch)
⭐   └─ WORKFLOW  (.github/workflows/ci.yml)
⭐        └─ JOB  ⭐ runs on its own fresh runner — ⭐⭐ jobs share NOTHING except artefacts
⭐             └─ STEP  ⭐ a shell command or a reusable `uses:` action
```

| ⭐ Fact | ⭐ Consequence |
|---|---|
| ⭐⭐ **Each job gets a clean VM** | ⭐⭐ **nothing carries between jobs — pass state via artefacts or outputs** |
| Steps in a job share a filesystem | so a job is the unit of "things that need each other" |
| ⭐ Jobs run in parallel by default | ⭐ `needs:` creates ordering |
| ⭐ **`GITHUB_TOKEN` is auto-provided** | ⭐ scope it with `permissions:` — **the default is broader than you want** |
| Matrix expands a job | one definition, many combinations |

```yaml
permissions:            # ⭐⭐ set at the TOP, least privilege, then widen per job
  contents: read
concurrency:            # ⭐ cancel superseded runs on the same branch
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

> **⭐ `concurrency` with `cancel-in-progress` is a two-line change that removes most wasted CI
> minutes**, because pushing three times to a branch otherwise runs three full pipelines to
> completion for results nobody will read.

# Part 2 — ⭐⭐ Caching: the key is the whole game

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.m2/repository
    ⭐ key:  ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}
    ⭐ restore-keys: |
    ⭐   ${{ runner.os }}-m2-
```

| ⭐ Concept | ⭐ Detail |
|---|---|
| ⭐⭐ **`key` is an exact match** | ⭐ hit → restore and **do not save again at the end** |
| ⭐⭐ **`restore-keys` is a prefix fallback** | ⭐⭐ **without it, ANY pom change means a completely cold cache** |
| ⭐ Caches are immutable | ⭐ a key that hit is never updated — **that is why the hash is in the key** |
| ⭐ **Scope** | ⭐ a branch reads its own cache and the default branch's; **not a sibling branch's** |
| Eviction | 7 days unused, or an overall repo size limit |

⚠️ **Two failure modes, and both are silent.** A key with **no hash** never invalidates, so you serve
a stale cache forever. A key with **no `restore-keys`** means one dependency change downloads
everything from scratch. **Neither fails the build — you just quietly pay for it every run.**

⚠️ **And do not cache what you should not trust.** A cache is writable by any workflow that can run
on the repository, **so cached build outputs are an integration point** — cache dependencies, not
compiled artefacts you will ship.

**⭐ For Docker layers**, prefer BuildKit's registry cache over the generic action:

```yaml
- uses: docker/build-push-action@v6
  with:
    ⭐ cache-from: type=registry,ref=ghcr.io/org/app:buildcache
    ⭐ cache-to:   type=registry,ref=ghcr.io/org/app:buildcache,mode=max
```

# Part 3 — ⭐⭐ Secrets, and the modern answer

| ⭐ Mechanism | ⭐ Use |
|---|---|
| Repository secrets | ⭐ shared, low-sensitivity |
| ⭐ **Environment secrets** | ⭐⭐ **scoped to `production`, with required reviewers — an approval gate** |
| Organisation secrets | shared across repos, with a repo allow-list |
| ⭐⭐ **OIDC federation** | ⭐⭐ **no stored cloud credentials at all — the right answer** |

```yaml
⭐ ✗ AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY as secrets
⭐   ⇒ ⭐⭐ long-lived, rotated never, valid from anywhere on earth if leaked

⭐ ✓ OIDC:
permissions: { id-token: write, contents: read }
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      ⭐ role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
      aws-region: eu-west-2
⭐ ⇒ ⭐⭐ a SHORT-LIVED token, and the cloud role trusts only THIS repo and THIS branch
```

> **⭐ OIDC is the single most valuable thing to know about Actions.** It removes standing
> credentials entirely: GitHub signs a token asserting *which repository, which branch, which
> workflow*, and the cloud role's trust policy checks those claims. **A leaked log line is worthless,
> because the token expired in an hour and only works for that context.**

⚠️ **The trust policy must be scoped tightly.** A condition of `repo:org/*:*` means **any repository
in your organisation can assume the deployment role** — including a new one created by anyone with
access. **Pin the repo and, for production, the branch or environment.**

| ⭐ Secret hygiene | |
|---|---|
| ⭐ Actions masks secrets in logs | ⭐⭐ **but not if you transform them** — base64, split or echo a substring and it prints |
| ⭐ **Never `echo` a secret**, even to debug | it lands in a log someone can read |
| ⭐ Secrets are unavailable to forked-PR workflows | ⭐ deliberately — see below |
| ⭐ **Rotate on any suspicion** | ⭐ a secret that reached a log is compromised (Day 296) |

# Part 4 — ⭐⭐ The supply-chain traps

## ⭐⭐ 1. `pull_request_target` — the dangerous trigger

```
⭐ pull_request        ⭐ runs the PR's code, ⭐ NO secrets, ⭐ read-only token   ⭐ SAFE
⭐ pull_request_target ⭐⭐ runs the BASE branch's workflow ⭐ WITH secrets and write access
⭐                     ⭐⭐ …but people then check out the PR's code and run it. ⭐⭐ FULL COMPROMISE.
```

⚠️ **This is the best-known Actions vulnerability class.** `pull_request_target` exists so trusted
workflows can label or comment on PRs from forks. **The moment it checks out and executes untrusted
code, an attacker's pull request runs with your secrets and write access to your repository.**
**Never check out PR head under `pull_request_target`.**

## ⭐⭐ 2. Pin actions by SHA, not tag

```yaml
⭐ ✗ uses: some-org/some-action@v3          ⭐⭐ a tag — the author can repoint it at any commit
⭐ ✓ uses: some-org/some-action@e4b2f1c…    ⭐ a commit SHA — immutable
```

**⭐ Day 362's tag argument, applied to your CI.** A third-party action runs **with your token and
your secrets**; a compromised maintainer account can silently replace `v3`. **Pin by SHA, and use
Dependabot to bump the pins** — otherwise you are pinned to a version that stops receiving fixes.

## ⭐ 3. Least privilege on `GITHUB_TOKEN`

```yaml
⭐ permissions: { contents: read }        ⭐ default for everything
⭐ # widen only where needed:
jobs:
  publish:
    permissions: { contents: read, packages: write, id-token: write }
```

⚠️ **A workflow with `contents: write` that runs untrusted input can push to your repository.**
Setting a restrictive default at the top and widening per job is one line and closes most of the
blast radius.

## ⭐ Self-hosted runners

| ⭐ When | ⭐ The caveat |
|---|---|
| Private network access, big machines, cost at volume | ⭐⭐ **NEVER use them on a public repository** |
| | ⭐ a fork's PR would execute arbitrary code **on your infrastructure** |
| | ⭐ use ephemeral runners — **a persistent runner accumulates state between jobs** |

## ⭐ The practical workflow shape

```yaml
jobs:
  build:                    ⭐ lint + test + build ONE artefact (Day 368)
  scan:    { needs: build } ⭐ Trivy on the built image (Day 363)
  deploy-staging: { needs: [build, scan], environment: staging }
  deploy-prod:
    needs: deploy-staging
    ⭐ environment: production      ⭐⭐ required reviewers = an approval gate
    ⭐ # deploys the SAME digest built above — never rebuilds
```

> **⭐ `environment:` is the underused feature.** It gives you approval gates, environment-scoped
> secrets, and a deployment history in the GitHub UI — **which turns "who deployed what, when, and
> who approved it" into an auditable record for free.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Cache key with no hash | ⭐ a stale cache forever |
| ⭐⭐ **No `restore-keys`** | ⭐⭐ **one pom change = fully cold cache** |
| ⭐ Caching build outputs you ship | a writable integration point |
| ⭐⭐ **Long-lived cloud keys as secrets** | ⭐⭐ **valid from anywhere, rotated never — use OIDC** |
| ⭐ An OIDC trust policy scoped to `repo:org/*` | any repo in the org can deploy |
| ⭐ **`echo`ing or transforming a secret** | masking is bypassed; it prints |
| ⭐⭐ **`pull_request_target` + checkout of PR head** | ⭐⭐ **full repository compromise** |
| ⭐ Actions pinned by tag | ⭐ the author can repoint it |
| ⭐ Pinning by SHA with no update automation | you freeze on an unpatched version |
| ⭐ **Default `GITHUB_TOKEN` permissions** | broader write access than needed |
| ⭐ Self-hosted runners on public repos | ⭐⭐ arbitrary code on your infrastructure |
| Persistent (non-ephemeral) runners | state leaks between jobs |
| No `concurrency` group | three pipelines for results nobody reads |
| Rebuilding in the deploy job | Day 368's property, broken |

## Interview questions

**Q: How does caching work, and what is the most common mistake?**
The key is an exact match and `restore-keys` are prefix fallbacks. The most common mistake is
omitting `restore-keys`, so a single dependency change means a completely cold cache and a full
download. The second is a key with no content hash, which never invalidates and serves a stale cache
forever. Both fail silently — the build still passes, you just pay for it on every run.

**Q: How do you give a workflow access to your cloud account?**
OIDC federation, not stored keys. GitHub signs a short-lived token asserting which repository,
branch and workflow is running, and the cloud role's trust policy validates those claims. There are
no standing credentials to leak or rotate, and a token that escaped into a log is worthless because
it expired and only works from that context. The thing to get right is scoping the trust policy — a
wildcard across the organisation means any repository can assume the deployment role.

**Q: What is wrong with `pull_request_target`?**
It runs the base branch's workflow with your secrets and write access, which is intentional so
trusted workflows can label or comment on fork PRs. The vulnerability is when people then check out
and execute the pull request's code under it — at which point an attacker's PR runs arbitrary code
with your credentials. The rule is never to check out PR head under that trigger.

**Q: Why pin actions by SHA?**
Because a tag is a mutable pointer and a third-party action runs with your token and your secrets. A
compromised maintainer account can repoint `v3` at malicious code and every consumer picks it up
silently. Pinning by commit SHA makes it immutable — paired with Dependabot to bump the pins, because
pinning without automation just means freezing on a version that stops getting security fixes.

**Q: When would you use self-hosted runners?**
For access to a private network, for machines bigger than hosted runners, or for cost at high volume.
Never on a public repository, because a fork's pull request would execute arbitrary code on my
infrastructure. And they should be ephemeral — a persistent runner accumulates state between jobs, so
one workflow can leave something behind that the next one picks up.

## Mini task

1. **Write a workflow** with lint, test, build-once, scan, and staged deploys using `needs:`.
2. ⭐ Add caching **without** `restore-keys`. Change `pom.xml` and **measure the cold build.** Add
   them and measure again. **Record both.**
3. ⭐ Use a cache key with no hash and **demonstrate it serving stale dependencies.**
4. ⭐ Add `concurrency` with cancel-in-progress. **Push three times quickly and confirm two runs are
   cancelled.**
5. ⭐⭐ Replace stored cloud keys with **OIDC.** Then **tighten the trust policy** from a wildcard to a
   specific repo and branch, and verify the wildcard version would have allowed another repo.
6. ⭐ Try to print a secret directly (masked), then **base64-encode it and print that** — watch the
   masking fail.
7. ⭐ Set top-level `permissions: contents: read` and **find every job that breaks.** That list is
   your true privilege requirement.
8. ⭐ **Pin every third-party action by SHA** and enable Dependabot for Actions.
9. ⭐ Add an `environment: production` with required reviewers. **Deploy and confirm the approval gate
   and the deployment record.**
10. ⭐ Verify the production job deploys **the same digest** the build job produced (Day 368) rather
    than rebuilding.

## 🎙️ Articulation drill

**Two minutes:** *"How does your pipeline authenticate to deploy?"*

**⭐ The answer that marks you out: "It doesn't hold credentials at all."** OIDC — GitHub signs a
short-lived token asserting the repository, branch and workflow, and the cloud role trusts exactly
those claims. **Nothing to leak, nothing to rotate, and a leaked token is useless outside that
context.**

**⭐ Then the scoping detail, because it is where people get it wrong:** *"and the trust policy names
the specific repo and the main branch — a wildcard across the org would let any repository assume the
deploy role."* **That sentence is the difference between having read about OIDC and having configured
it.**
