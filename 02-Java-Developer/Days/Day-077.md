# Part 2 — Answer key

**1.** Bootstrap → Platform → Application, with parent-first delegation: every loader asks its
parent before trying itself, so JDK classes always resolve from Bootstrap. *(023, 076A)*

**2.** Local `int` and local reference: the thread's **stack**. The object: **heap**. `static` field:
heap, in the class's storage referenced from metaspace. String literal: the **string pool**, in the
heap since Java 7. Class metadata: **metaspace**, native memory. *(025)*

**3.** `true false true`. Literals are interned to the same pooled object; `new String` creates a
distinct object; `intern()` returns the pooled one. *(029)*

**4.** Metaspace, thread stacks (~1 MB each — 500 threads is 500 MB), the JIT code cache, direct
`ByteBuffer`s, GC internal structures, and the JVM's own native allocations. *(071 B-15, 076)*

**5.** **Leak.** An undersized heap recovers after a full GC; a leak does not, because the objects
are still reachable. Confirm with `jstat -gcutil` (old gen stays high, `FGC` climbing) then a heap
dump and a path-to-GC-roots in MAT. *(027, 076)*

**6.** `true false`. The `Integer` cache covers −128..127, so `valueOf` returns the same object in
that range and a new one outside it. Use `equals`. *(028)*

**7.** `false`, and `0.30000000000000004`. Binary floating point cannot represent 0.1 or 0.2
exactly. Use `BigDecimal` — constructed **from a String**, never from a `double`. *(042B)*

**8.** O(n²). `String` is immutable, so each `+=` allocates a new `String` and copies everything so
far. `StringBuilder` makes it O(n). *(029)*

**9.** `ab`. Java is pass-by-value; the *reference* is copied, so mutation through it is visible but
reassigning the parameter is not. *(032)*

**10.** Field: assign once. Method: cannot be overridden. Class: cannot be extended. Parameter:
cannot be reassigned inside the method. None of them means the object is immutable. *(034)*

**11.** `List.of` returns an immutable list whose `add` throws `UnsupportedOperationException`. The
*interface* declares `add`, so it compiles; immutability is a runtime property of the
implementation, not part of the type. *(034A)*

**12.** Prints `B x=0`. The superclass constructor runs before the subclass's field initialisers, so
the overridden method sees `x` at its default. **Never call an overridable method from a
constructor.** *(035, 037)*

**13.** `contains` returns `false`. `HashSet` computes the bucket from `hashCode` first; different
hashes mean different buckets, so `equals` is never even called. *(040)*

**14.** `false 1`. Mutating a key changes its hash, so the lookup goes to a different bucket while
the entry remains in the old one — unreachable and unremovable. **Never mutate a key.** *(048)*

**15.** `static` methods are **hidden**, not overridden: they are resolved at compile time by the
reference type, so `A a = new B(); a.staticMethod()` calls `A`'s. *(033, 037)*

**16.** `clone()` is `protected` on `Object` while `Cloneable` declares no method, so the interface
does not give you the ability it implies; and the default is a **shallow** copy that silently shares
mutable state. Use a copy constructor or static factory. *(041)*

**17.** No. The record's `List` reference is final, but the list itself can be mutated by anyone
holding it. Defensively copy in a compact constructor: `list = List.copyOf(list)`. *(042, 034A)*

**18.** `hash(key)` = `h ^ (h >>> 16)` — the **spread**, mixing high bits down because the index is
`hash & (n-1)` and would otherwise ignore them. Index the bucket; if empty, place a node; if
occupied, walk the chain comparing `hash` then `equals`; at **8** nodes with capacity ≥ 64,
**treeify** to a red-black tree. Resize at `size > capacity × loadFactor`. *(048)*

**19.** It is the balance point between space and collisions. With a good hash the bucket occupancy
follows a Poisson distribution; at 0.75 the chance of a bucket reaching 8 entries is about 1 in 10
million — which is why the treeify threshold is 8. *(048)*

**20.** Each node's `hash & oldCapacity` is tested: 0 means it stays at index `j`, non-zero means it
moves to `j + oldCapacity`. **One bit decides it**, and the split preserves relative order — which is
what removed Java 7's resize-cycle infinite loop. *(048, 053)*

**21.** `ConcurrentModificationException` — the for-each uses an iterator, and `list.remove` bumps
`modCount` without updating the iterator's `expectedModCount`. Use `iterator.remove()` or
`removeIf`. *(052)*

**22.** `[1, 3]`. `remove(int)` beats `remove(Object)` in overload resolution because `1` is an
`int`, so it removes by **index**. `list.remove(Integer.valueOf(1))` removes by value. *(032, 045)*

**23.** No. Each method is atomic; the *sequence* is not — two threads can both see the key absent.
Use `putIfAbsent` or `computeIfAbsent`. *(053)*

**24.** Because `map.get(k) == null` would be ambiguous — absent, or present with a null value — and
in a concurrent map you cannot disambiguate with `containsKey`, since the state may change between
the two calls. *(053)*

**25.** The assignment does **not** compile: generics are invariant. The array version **does**
compile, because arrays are covariant, and throws `ArrayStoreException` at runtime. Same logical
error, caught at different times. *(054)*

**26.** Type erasure — `T` is not available at runtime, so the JVM cannot know the array's component
type, and arrays are reified. Use `(T[]) new Object[10]` internally, or
`Array.newInstance(clazz, n)` with a `Class<T>` token. *(055)*

**27.** **P**roducer **E**xtends, **C**onsumer **S**uper. From a `? extends T` you can safely *read* a
`T` but cannot write, because the actual type could be any subtype. Into a `? super T` you can
safely *write* a `T` but reads only give `Object`. `Stream.map` consumes `T` (so `? super T`) and
produces `R` (so `? extends R`), which makes it usable with functions declared on supertypes. *(056)*

**28.** `created`, then `1 2 3`. Streams are lazy — no intermediate operation runs until the terminal
operation. *(059)*

**29.** **Immediately, and always** — arguments are evaluated before the call, so the default is
computed even when a user is found and then thrown away. Use `orElseGet(this::expensiveDefault)`.
*(058)*

**30.** Splitting, merging and boxing overhead can exceed the gain; `LinkedList` and `Iterator`
sources split badly; and small workloads never repay the cost. The common-pool hazard: parallel
streams use `ForkJoinPool.commonPool()` with `cores − 1` threads, shared JVM-wide, so one blocking
task there stalls unrelated work. *(060, 069)*

**31.** `2`. A `return` in `finally` discards the in-flight return **and any in-flight exception**.
Never return from `finally`. *(061)*

**32.** It loses the cause and the entire original stack trace, so the log shows the symptom with no
origin. Pass the exception: `new RuntimeException("context", e)`. *(061)*

**33.** It uses the **platform default charset**, so the same file reads differently on different
machines. Use `Files.readString` or an explicit `InputStreamReader(..., UTF_8)`. *(063)*

**34.** It is base64 for `ACED0005` — a **Java serialized object** crossing a trust boundary. Treat
it as a potential RCE (CWE-502): do not deserialize untrusted input; move to JSON, or apply an
allow-list `ObjectInputFilter`. *(063A)*

**35.** Catastrophic backtracking. Java's engine backtracks, and a nested quantifier over an
overlapping class makes the engine try 2^(n−1) partitions before it can conclude "no match" — the
trailing failing character forces every path to be explored. Bound the input length, flatten the
pattern, or use an atomic group `(?>a+)+`. *(063B)*

**36.** **No — it usually loops forever.** With no synchronization there is no happens-before edge,
so the JIT may hoist the read out of the loop, and the write may sit in a store buffer. `volatile`
fixes it. *(065)*

**37.** ⭐ `count++` is **read, add, write**. `volatile` makes the read see the latest value and the
write immediately visible, but does nothing about the interval between them — two threads can both
read 5, both compute 6, and both write 6. One increment is lost. Use `synchronized`,
`AtomicInteger`, or `LongAdder`. *(065)*

**38.** `instance = new Singleton()` compiles to allocate → construct → assign, and **steps 2 and 3
may be reordered**. Another thread can then see a non-null reference to a partially-constructed
object. `volatile` forbids that reordering. Better: the holder idiom or an enum. *(065)*

**39.** **Two.** A task is queued whenever the queue accepts it, and an unbounded queue always
accepts — so the pool never grows past core size and `maximumPoolSize` is dead configuration. The
queue then grows until the heap is exhausted. *(069)*

**40.** **Memory leak** — the `ThreadLocalMap` lives on the pooled thread and holds a *strong*
reference to the value, so it is retained as long as the thread lives (and can retain a webapp class
loader). **And a correctness/authorization bug** — the next request served by that thread sees the
previous request's user. *(066A)*
