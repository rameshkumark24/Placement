# Day 177

**L-177** · `@Async` — executors, context propagation, and the default that will hurt you

**Time:** 3 hrs · **Mode:** NEW

> Day 071 built `ThreadPoolExecutor` and its submission algorithm by hand — core pool, queue, max
> pool, rejection policy, and the counter-intuitive rule that **an unbounded queue means the maximum
> pool size is never reached.**
>
> `@Async` is a one-annotation wrapper over exactly that, and it ships with defaults that Day 071
> already taught you to distrust. Today: the executor you must configure, the four things that do not
> cross the thread boundary, and the exceptions that vanish.

# Part 1 — ⭐ The default executor, and why you must replace it

```java
@Configuration
@EnableAsync                                    // ⭐ without this, @Async does nothing at all
class AsyncConfig { }
```

```java
@Service
public class ReportService {
    @Async
    public void generate(Long reportId) { ... }         // returns immediately
}
```

**Boot's default is a `SimpleAsyncTaskExecutor`-backed `ThreadPoolTaskExecutor` with `core = 8`,
`max = Integer.MAX_VALUE`, and an *unbounded* queue.** Day 071's arithmetic applies directly:

```
tasks arriving > 8 concurrent  →  queue (unbounded)
queue never full               →  ⭐ max pool size NEVER reached
```

**So you have eight threads and an infinite backlog.** Under load the queue grows until the heap is
gone, and Day 144's `ExitOnOutOfMemoryError` correctly kills the pod. There is no backpressure and no
signal — just latency that grows and then a crash.

```java
@Bean("taskExecutor")                              // ⭐ this name is the @Async default
ThreadPoolTaskExecutor taskExecutor() {
    var ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(8);
    ex.setMaxPoolSize(16);
    ex.setQueueCapacity(200);                      // ⭐⭐ BOUNDED — Day 070's backpressure
    ex.setThreadNamePrefix("async-");              // ⭐ readable thread dumps (Day 076)
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());   // ⭐ see below
    ex.setWaitForTasksToCompleteOnShutdown(true);  // ⭐ Day 133's graceful shutdown
    ex.setAwaitTerminationSeconds(30);
    ex.initialize();
    return ex;
}
```

**⭐ `CallerRunsPolicy` is the choice worth defending.** When the queue is full, the *submitting*
thread runs the task itself. That slows the producer down — which is exactly Day 070's backpressure:
the system degrades rather than collapsing. `AbortPolicy` (the default) throws
`RejectedExecutionException`, which is honest but requires you to handle it; a silent
`DiscardPolicy` is almost never right.

**Separate pools per workload:**

```java
@Async("emailExecutor")  public void sendEmail(...) { }
@Async("reportExecutor") public void generate(...) { }
```

**⭐ One shared pool means a slow report blocks every email.** Day 071's bulkhead argument: isolate
workloads that fail independently, so saturation in one does not become an outage in all.

## ⭐ Virtual threads change this materially

```yaml
spring.threads.virtual.enabled: true         # ⭐ Boot 3.2+, Java 21
```

For **I/O-bound** async work, a virtual-thread executor removes the sizing problem entirely — Day 072's
argument. `SimpleAsyncTaskExecutor` with virtual threads enabled creates one per task, and blocking
is cheap.

**Two caveats from Day 072 still apply:** virtual threads do not help CPU-bound work (you still have
N cores), and **a bounded queue is still how you get backpressure** — unlimited virtual threads means
unlimited concurrent database calls, which just moves the collapse to the connection pool (Day 156).

# Part 2 — ⭐ The four things that do not cross the thread boundary

**All four are `ThreadLocal`s, and this is the same fact four times.**

| Lost | Symptom | Fix |
|---|---|---|
| ⭐ **`SecurityContext`** | `@PreAuthorize` sees anonymous (Day 169) | `DelegatingSecurityContextExecutor` |
| ⭐ **MDC** (correlation id) | async logs unlinkable to the request (Day 127) | a `TaskDecorator` |
| **Request scope** | `ScopedProxyMode` failures (Day 134) | pass values as arguments |
| ⭐ **Transaction** | ⭐ **a new thread has NO transaction** (Day 164) | open one inside the async method |

```java
public class ContextPropagatingTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable task) {
        Map<String, String> mdc = MDC.getCopyOfContextMap();          // ⭐ captured on the CALLER
        SecurityContext security = SecurityContextHolder.getContext();
        return () -> {
            try {
                if (mdc != null) MDC.setContextMap(mdc);
                SecurityContextHolder.setContext(security);
                task.run();
            } finally {
                MDC.clear();                                          // ⭐⭐ pooled thread
                SecurityContextHolder.clearContext();                 // ⭐⭐ Day 066A
            }
        };
    }
}
```

```java
ex.setTaskDecorator(new ContextPropagatingTaskDecorator());
```

**⭐ The `finally` is as important as the propagation.** Async threads are pooled, so a context left
behind is inherited by the next unrelated task — which for `SecurityContext` means **running someone
else's work as the wrong user.**

## ⭐ The transaction one is the most dangerous

```java
@Transactional
public void placeOrder(Request req) {
    Order order = repo.save(toOrder(req));
    asyncService.notifyWarehouse(order.getId());   // ⭐ @Async — DIFFERENT THREAD
}
```

```java
@Async
public void notifyWarehouse(Long orderId) {
    Order order = repo.findById(orderId).orElseThrow();   // ⭐⭐ may not exist yet!
}
```

**Two independent bugs in three lines:**

1. **A race.** The async method may run *before* the outer transaction commits, so the row is not
   visible — an intermittent `NoSuchElementException` that never reproduces locally.
2. **No rollback linkage.** If the outer transaction rolls back, the notification was already sent.
   **Day 124's dual-write, one more time.**

```java
@TransactionalEventListener(phase = AFTER_COMMIT)      // ⭐ Day 179
@Async
public void onOrderPlaced(OrderPlacedEvent e) { ... }  // ⭐ runs only after commit, on another thread
```

**`@TransactionalEventListener` plus `@Async` is the correct combination** — commit first, then hand
off. Day 179 develops it; note here that `@Async` *alone* on a method called from a transaction is
almost always a bug.

# Part 3 — ⭐ Return types, and the exceptions that vanish

```java
@Async public void fireAndForget() { throw new RuntimeException("gone"); }   // ⭐⭐ SWALLOWED
```

**A `void` `@Async` method's exception goes nowhere.** No caller receives it, no advice sees it
(Day 149's gap — a different thread entirely), and by default it is logged by
`SimpleAsyncUncaughtExceptionHandler` at a level people do not watch. **Silent failure.**

```java
@Configuration
@EnableAsync
class AsyncConfig implements AsyncConfigurer {
    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) -> {
            log.error("async_failed method={} params={}", method.getName(), params, ex);
            failureCounter.increment();                         // ⭐ Day 143 — alert on it
        };
    }
}
```

**Configure this handler. It applies only to `void` methods** — futures carry their own exception.

| Return type | Verdict |
|---|---|
| `void` | ⚠️ fire-and-forget. **Requires the handler above** |
| `Future<T>` | legacy. `get()` blocks with no composition |
| **`CompletableFuture<T>`** | ⭐ **the right choice.** Composable, `exceptionally`, `orTimeout` |

```java
@Async
public CompletableFuture<PriceQuote> quote(String sku) {
    return CompletableFuture.completedFuture(pricing.lookup(sku));   // ⭐ Spring unwraps it
}

// ⭐ Real parallel fan-out — three calls in the time of the slowest
var a = quotes.quote("A");
var b = quotes.quote("B");
var c = quotes.quote("C");
CompletableFuture.allOf(a, b, c).orTimeout(3, SECONDS).join();      // ⭐ ALWAYS bound it
```

**⭐ Two rules for fan-out:** always set a timeout — otherwise one slow dependency holds the caller's
thread indefinitely (Day 154) — and remember the caller is *still blocked* on `join()`, so this
reduces latency, not thread consumption. Use it when three sequential calls at 300 ms each should be
one at 300 ms.

## ⭐ Self-invocation, one last time

```java
@Service
public class ReportService {
    public void run() { this.generate(); }      // ❌ SYNCHRONOUS — proxy bypassed
    @Async public void generate() { }
}
```

Day 137's mechanism. `@Async` is a proxy, so `this.generate()` runs on the calling thread — and
unlike `@Transactional`, the symptom is only "it was slower than expected", which nobody
investigates.

# Part 4 — When *not* to use `@Async`

**⭐ `@Async` is in-process, in-memory, and lost on restart.** That makes it wrong for a large class
of work people use it for.

| Requirement | `@Async` | Correct tool |
|---|---|---|
| Fire-and-forget, loss acceptable | ⭐ ✅ | — |
| Parallel fan-out to reduce latency | ⭐ ✅ | — |
| ⭐ **Must not be lost** | ❌ **a restart drops the queue** | ⭐ Day 124's outbox / a message queue |
| Must be retried on failure | ❌ | a queue with a DLQ (Day 125) |
| Must run exactly once across instances | ❌ | Day 178's ShedLock |
| Long-running (minutes) | ⚠️ holds a thread | a job runner |
| Must survive deploys | ❌ | a broker |

**The test to apply:** *if this pod is killed one second from now, does it matter that this task never
happened?* If yes, `@Async` is the wrong mechanism, and no amount of configuration fixes it.

**Graceful shutdown reduces the window but does not close it:**

```yaml
server.shutdown: graceful
spring.lifecycle.timeout-per-shutdown-phase: 30s
```
```java
ex.setWaitForTasksToCompleteOnShutdown(true);
ex.setAwaitTerminationSeconds(30);
```

That drains in-flight tasks on a *clean* shutdown (Day 133). A `SIGKILL`, an OOM kill, or a node
failure still loses everything queued.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ No `@EnableAsync` | every annotation silently synchronous |
| ⭐ Default unbounded queue | Day 071 — max pool never reached; OOM under load |
| One shared executor | a slow workload starves every other |
| No `RejectedExecutionHandler` chosen deliberately | either exceptions or silent discards |
| ⭐ No `TaskDecorator` | security context and correlation id lost |
| Not clearing context in `finally` | pooled thread runs as the previous user |
| ⭐ `@Async` called from within a transaction | race against commit, plus dual-write |
| `void` return with no exception handler | failures vanish |
| Unbounded `CompletableFuture.join()` | one slow call blocks the caller forever |
| Self-invocation | silently synchronous |
| `@Async` for work that must not be lost | a restart drops it |
| No thread name prefix | unreadable thread dumps |

## Interview questions

**Q: What is wrong with Spring's default async executor?**
It has an unbounded queue, which by `ThreadPoolExecutor`'s submission algorithm means the maximum
pool size is never reached — the queue absorbs everything. So you get eight threads and an infinite
backlog that grows until the heap is exhausted. I set a bounded queue and choose the rejection policy
deliberately, usually `CallerRunsPolicy` so the producer is slowed rather than the system collapsing.

**Q: What is lost when work moves to an async thread?**
Four things, all `ThreadLocal`s: the security context, the MDC, request scope, and the transaction.
The first two are fixed with a `TaskDecorator` that captures on the caller and clears in a `finally`.
The transaction cannot be propagated — the async method needs its own.

**Q: What happens to an exception in a `void @Async` method?**
Nothing useful. No caller sees it and no error advice applies, because it is a different thread. You
must configure an `AsyncUncaughtExceptionHandler` that logs and increments a metric, or failures are
silent.

**Q: When would you not use `@Async`?**
When losing the task matters. It is in-memory and in-process, so a restart drops the queue. Anything
that must not be lost belongs in an outbox or a message queue with retries and a dead-letter queue.

## Mini task

1. `@Async` without `@EnableAsync`. Confirm it runs synchronously by printing the thread name.
2. Use the default executor. Submit 100,000 tasks that sleep. **Watch the queue grow and the heap
   with it.**
3. Configure a bounded queue with `AbortPolicy`. Watch rejections. Switch to `CallerRunsPolicy` and
   observe the caller slowing instead.
4. Log the correlation id and `SecurityContextHolder` inside an async method. **Confirm both are
   missing.** Add the `TaskDecorator`.
5. Remove the `finally` from the decorator, run two tasks as different users, and confirm the leak.
6. Call an `@Async` method from inside `@Transactional` and query the row. **Reproduce the race.**
   Fix it with `@TransactionalEventListener(AFTER_COMMIT)`.
7. Throw from a `void @Async` method. Confirm nothing surfaces. Add the handler.
8. Fan out three 300 ms calls with `CompletableFuture`. Measure sequential vs parallel. Then remove
   `orTimeout` and make one hang.
9. Queue 1,000 tasks and `kill -9` the process. **Count what was lost.**

## 🎙️ Articulation drill

Two minutes: **"How do you run work asynchronously in Spring?"**

Configure the executor rather than accepting the default, and explain why in terms of the submission
algorithm — an unbounded queue means the max pool is never reached, so you get eight threads and an
infinite backlog. Bounded queue, `CallerRunsPolicy` for backpressure, separate pools per workload.
Then the propagation issue as one fact, not four: everything contextual is a `ThreadLocal`, so
security and MDC need a decorator and the transaction simply does not travel. Close on the boundary:
`@Async` is in-memory, so anything that must not be lost belongs in a queue.
