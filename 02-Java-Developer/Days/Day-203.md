# Day 203

**L-203** · Redis architecture — the single-threaded event loop

**Time:** 3 hrs · **Mode:** NEW

> Day 168 used Redis through `@Cacheable` and `RedisTemplate`. **Today is what is actually running**,
> and the answer is one thread — which sounds like a limitation and is the source of both its speed
> and its most important guarantee.
>
> **Every design decision in the next six days follows from that one fact**, including why a
> distributed lock can work at all (Day 207) and why one careless command takes your cache down.

# Part 1 — ⭐ Why one thread is fast

```
        clients                    ┌── Redis process ──────────────┐
   ┌───┐ ┌───┐ ┌───┐               │  ⭐ epoll / kqueue event loop │
   │ A │ │ B │ │ C │ ────────────► │        ↓                      │
   └───┘ └───┘ └───┘               │  ⭐ ONE thread executes       │
                                   │     commands, one at a time   │
                                   │        ↓                      │
                                   │  in-memory data structures    │
                                   └───────────────────────────────┘
```

**⭐ Redis is not slow because it is single-threaded. It is fast because it does not need more than
one thread.**

| Cost | Redis |
|---|---|
| Disk I/O | ⭐ **none on the request path** — everything is in memory |
| Locking | ⭐ **none** — one thread means no contention, no mutexes |
| Context switching | ⭐ **none between commands** |
| Actual bottleneck | ⭐ **the network**, not the CPU |

**A typical Redis instance handles 100,000+ operations per second on one core.** The limiting factor
is how fast the network can deliver commands, which is why pipelining (Part 3) matters far more than
CPU.

**⭐ Redis 6+ added I/O threads** (`io-threads 4`) for *reading and writing sockets* — but **command
execution is still single-threaded.** The data-structure operations never run concurrently, which
preserves the guarantee below.

## ⭐⭐ The guarantee that follows: every command is atomic

> **⭐ Because one thread executes commands one at a time to completion, every Redis command is
> atomic. There is no interleaving. Ever.**

```
INCR counter          ⭐ atomic — no read-modify-write race (compare Day 195's lost update)
SETNX lock 1          ⭐ atomic — the basis of Day 207's distributed lock
LPUSH queue job       ⭐ atomic
GETSET key value      ⭐ atomic read-and-replace
```

**⭐ This is the property Day 122's rate limiter and Day 207's lock are built on**, and it is why
Redis can serve as a coordination primitive at all. In a multi-threaded store, `SETNX` would need
internal locking to be correct; here it is free.

**⭐ And the flip side, which is the practical warning:**

> **⭐ One slow command blocks *everything*.** There is no other thread to serve the next client.

```
KEYS *              ⭐⭐ O(N) over the whole keyspace. On 10M keys: SECONDS of total blockage
FLUSHALL            ⭐ blocks until done
SMEMBERS big_set    ⭐ O(N) — a 1M-member set blocks the server
SORT huge_list      ⭐ O(N log N), blocking
DEL huge_hash       ⭐ freeing 5M fields blocks — use UNLINK instead
```

**⭐ `KEYS *` in production is the classic Redis outage.** It is in every tutorial, it works instantly
on a development instance with 40 keys, and on a real instance it stops the world.

```
SCAN 0 MATCH user:* COUNT 100     -- ⭐ cursor-based, O(1) per call. ALWAYS use this
UNLINK bigkey                     -- ⭐ frees memory in a background thread
```

**⭐ Rename `KEYS` and `FLUSHALL` in production:**

```
rename-command KEYS ""            # ⭐ disable entirely
rename-command FLUSHALL ""
rename-command CONFIG "CONFIG_a8f3c2"
```

# Part 2 — Memory, and where it actually goes

**⭐ Redis is memory-resident. Every design decision is a memory decision.**

```
INFO memory
used_memory_human:2.14G
used_memory_rss_human:2.61G          ⭐ what the OS sees — the gap is FRAGMENTATION
mem_fragmentation_ratio:1.22         ⭐ above ~1.5 is a problem
maxmemory_policy:allkeys-lru
```

| Metric | Meaning |
|---|---|
| `used_memory` | what Redis thinks it holds |
| ⭐ `used_memory_rss` | ⭐ what the OS has allocated |
| ⭐ `mem_fragmentation_ratio` | ⭐ **rss/used. Above 1.5 = fragmentation; below 1 = swapping** |

**⭐ A ratio below 1 means part of Redis is swapped to disk**, which for an in-memory database is
catastrophic — a "microsecond" operation becomes a disk read. **Disable swap on Redis hosts, or set
`vm.swappiness = 1`.**

## ⭐ Per-key overhead

**⭐ Every key costs ~50–100 bytes of overhead** beyond its value — the key string, the dictionary
entry, the object header, the expiry entry.

```
10 million keys × 80 bytes = ⭐ 800 MB of pure overhead, before any values
```

**⭐ This drives real design decisions:**

```
SET user:1000:name "alice"     ⭐ 3 keys, 3× overhead
SET user:1000:email "a@b.com"
SET user:1000:age 30

HSET user:1000 name alice email a@b.com age 30    ⭐⭐ ONE key. Far less memory
```

**⭐ Small hashes, lists, sets and sorted sets use a compact encoding** (`listpack`) below configured
thresholds, which is dramatically more memory-efficient:

```
hash-max-listpack-entries 128       # ⭐ below this, a hash is a flat packed array
hash-max-listpack-value 64
```

**A hash with 100 small fields may use a tenth of the memory of 100 separate keys.** Grouping related
fields into a hash is one of the highest-value Redis design habits.

```
MEMORY USAGE user:1000            -- ⭐ bytes for one key
redis-cli --bigkeys               -- ⭐ scan for the largest keys per type
redis-cli --memkeys               -- sample memory by key
```

**⭐ `--bigkeys` is the first thing to run on an unfamiliar Redis**, exactly as
`pg_stat_statements` is for PostgreSQL (Day 202). Big keys are the cause of both memory surprises and
blocking commands.

# Part 3 — ⭐ Latency, and the thing that actually costs you

**⭐ A Redis command takes microseconds. A network round trip takes ~0.5 ms in a datacentre.** So the
network dominates by three orders of magnitude, and **the optimisation that matters is reducing round
trips, not commands.**

```java
// ❌ 1,000 round trips ≈ 500 ms
for (String id : ids) redis.opsForValue().get("user:" + id);

// ⭐ ONE round trip ≈ 1 ms
List<Object> results = redis.executePipelined((RedisCallback<Object>) conn -> {
    ids.forEach(id -> conn.stringCommands().get(("user:" + id).getBytes()));
    return null;
});

// ⭐ Or, for plain reads, one command
redis.opsForValue().multiGet(keys);        // MGET
```

**⭐ This is Day 160's N+1, in a different store** — and the fix is the same shape: state everything
you need up front instead of asking one question at a time.

| Technique | Use |
|---|---|
| ⭐ **Pipelining** | ⭐ many independent commands, one round trip. **No atomicity** |
| `MGET`/`MSET`/`HMGET` | multiple keys in one command |
| ⭐ **Lua script (`EVAL`)** | ⭐ **atomic** multi-step logic — Day 207, Day 208 |
| `MULTI`/`EXEC` | a transaction — see below |

## ⭐ `MULTI`/`EXEC` is not a transaction in the ACID sense

```
MULTI
INCR balance
DECR other
EXEC              ⭐ commands queued, then executed atomically as a block
```

**⭐ It is atomic — no other client interleaves — but there is NO ROLLBACK.** If one command fails at
runtime (wrong type for the key), the others still execute. D-13's atomicity in the "all or nothing"
sense does not apply.

**⭐ And you cannot read a value and branch on it inside `MULTI`**, because results are not available
until `EXEC`. `WATCH` gives optimistic locking (Day 165's pattern), but:

> **⭐ For anything that needs read-then-decide logic atomically, use a Lua script.** It runs on the
> single thread, so it is atomic by construction — that is Day 122's rate limiter and Day 207's lock
> release.

```lua
-- ⭐ atomic because the server is single-threaded
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

⚠️ **A Lua script blocks the server for its duration** — the same single-thread rule. **Keep scripts
short and never loop over a large keyspace inside one.**

# Part 4 — Deployment topologies

| Mode | Gives you | Cost |
|---|---|---|
| **Standalone** | ⭐ simplest | no HA |
| **Replication** | read replicas, a warm standby | ⭐ **async — data loss on failover** |
| ⭐ **Sentinel** | ⭐ automatic failover | still one master's worth of memory |
| ⭐ **Cluster** | ⭐ **sharding across nodes** | ⭐ multi-key ops constrained — see below |

**⭐ Replication is asynchronous**, so a failover loses whatever had not replicated — exactly
Day 201's RPO discussion. `WAIT numreplicas timeout` gives a weak synchronous guarantee, and it is
**not** a strong one: it waits for acknowledgement of receipt, not of durability.

**⭐ The honest framing: Redis is not a system of record.** Treat a Redis failover as potentially
losing the last few seconds. For a cache that is fine; for a distributed lock it is the entire
Redlock argument (Day 207).

## ⭐ Cluster mode and hash slots

**Cluster shards the keyspace into 16,384 hash slots**, distributed across masters.

```
⭐ Multi-key commands only work if all keys are in the SAME slot.
MGET user:1 user:2                     ⭐ likely CROSSSLOT error
MGET {user:1000}:name {user:1000}:email  ⭐ hash tag {...} forces the same slot
```

**⭐ Hash tags are the mechanism**: only the part inside `{}` is hashed, so `{order:42}:items` and
`{order:42}:total` land together.

**⭐ This has to be designed in.** Retrofitting cluster mode onto a codebase full of multi-key
operations and Lua scripts spanning unrelated keys is genuinely painful — Lua scripts must declare
all keys in `KEYS[]` and all must be in one slot.

**⭐ Do you need cluster?** A single Redis instance handles enormous throughput and up to tens of
gigabytes comfortably. **Cluster is for when your data exceeds one machine's memory**, not for
throughput — and Sentinel plus a bigger instance is simpler for most systems.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `KEYS *` in production | O(N) on a single thread — the classic outage |
| `SMEMBERS` on a huge set | same |
| `DEL` on a huge structure | blocks; use `UNLINK` |
| ⭐ Not renaming/disabling dangerous commands | one accidental `FLUSHALL` |
| One key per field | ⭐ 50–100 bytes overhead each; use a hash |
| Ignoring `mem_fragmentation_ratio` | below 1 means swapping — catastrophic |
| Swap enabled on the host | microseconds become milliseconds |
| ⭐ A loop of `GET`s | Day 160's N+1; pipeline or `MGET` |
| Expecting `MULTI` to roll back | it does not |
| Read-then-decide across two commands | ⭐ a race; use Lua |
| A long-running Lua script | blocks the whole server |
| Treating Redis as durable | ⭐ async replication loses the last seconds |
| Cluster without hash tags | `CROSSSLOT` errors at runtime |
| Cluster for throughput | one instance is already very fast |

## Interview questions

**Q: Redis is single-threaded. Isn't that a limitation?**
It is the source of its two best properties. There is no locking, no context switching and no disk on
the request path, so one core handles well over a hundred thousand operations per second and the
bottleneck is the network. And because commands execute one at a time to completion, **every command
is atomic** — which is what makes `INCR` and `SETNX` usable as coordination primitives with no extra
machinery.

**Q: What is the danger of that model?**
One slow command blocks every client, because there is no other thread. `KEYS *` on ten million keys
is seconds of total unavailability, and it is in every tutorial. `SCAN` is the cursor-based
replacement, `UNLINK` replaces `DEL` for large structures, and I rename or disable the dangerous
commands in production.

**Q: How do you make a thousand lookups fast?**
One round trip, not a thousand. Pipelining or `MGET` — because the command takes microseconds and the
network takes half a millisecond, so round trips dominate by three orders of magnitude. It is the
same problem as an N+1 in a relational database.

**Q: Is `MULTI`/`EXEC` a transaction?**
It is atomic in that no other client interleaves, but there is no rollback — if one command fails at
runtime the others still apply. And you cannot read a value and branch on it inside the block. For
read-then-decide logic I use a Lua script, which is atomic because the server is single-threaded.

**Q: When do you need Redis Cluster?**
When the dataset exceeds one machine's memory. Not for throughput — a single instance is already very
fast. And it constrains the design: multi-key operations require all keys in one hash slot, so hash
tags have to be planned in rather than retrofitted.

## Mini task

1. Load 5 million keys. Run `KEYS *` and **time how long other clients are blocked.** Then `SCAN`.
2. Store a user as 5 separate keys, then as one hash. **Compare `MEMORY USAGE` and total memory for
   100,000 users.**
3. Push a hash past `hash-max-listpack-entries` and measure the memory jump.
4. `redis-cli --bigkeys` on your loaded instance. Identify the top three.
5. `DEL` a 2-million-field hash and time the block. Then `UNLINK`.
6. Fetch 1,000 keys in a loop, then with `MGET`, then pipelined. **Three timings.**
7. Write a read-then-decide operation with two commands, run it from 50 threads, and **find the
   race.** Rewrite as Lua and confirm it disappears.
8. Run a `MULTI` block where the second command has a type error. **Confirm the first still applied.**
9. Check `mem_fragmentation_ratio`. Then set `maxmemory` below your data size and watch eviction.
10. Start a 3-node cluster. Run `MGET` across slots and get `CROSSSLOT`. Fix it with hash tags.
