# Day 179

**L-179** · Application events — decoupling in-process, and its honest limits

**Time:** 3 hrs · **Mode:** NEW

> Day 095 built the observer pattern. Day 133 introduced `@TransactionalEventListener`. Day 124
> established the dual-write problem and the outbox. Today assembles them into Spring's event
> mechanism — and, more importantly, draws the line where in-process events stop being adequate.
>
> **The failure mode of this feature is not technical. It is architectural:** events are so pleasant
> that people use them to decouple things that should not be decoupled, and end up with control flow
> that no reader can follow and no test can pin down.

---

# Part 1 — The mechanism

```java
public record OrderPlacedEvent(UUID orderId, Long customerId, BigDecimal total, Instant at) { }
```

```java
@Service
public class OrderService {
    private final ApplicationEventPublisher events;

    @Transactional
    public Order place(CreateOrderRequest req) {
        Order order = repo.save(toOrder(req));
        events.publishEvent(new OrderPlacedEvent(order.getPublicId(), order.getCustomerId(),
                                                 order.getTotal(), Instant.now()));
        return order;
    }
}
```

```java
@Component
public class OrderPlacedListeners {
    @EventListener
    public void sendConfirmation(OrderPlacedEvent e) { ... }

    @EventListener
    @Order(1)                                   // ⭐ ordering within the same phase
    public void updateAnalytics(OrderPlacedEvent e) { ... }
}
```

**⭐ `publishEvent` is SYNCHRONOUS by default.** This is the single most misunderstood fact about
Spring events. The publisher blocks while every listener runs, **on the same thread, in the same
transaction**.

Three consequences:

1. **A slow listener slows the request.** Sending an email inline adds 400 ms to `place()`.
2. ⭐ **A listener that throws rolls back the publisher's transaction.** The order is not saved
   because the analytics update failed.
3. **The listener sees the publisher's uncommitted state**, since it shares the persistence context
   (Day 162) — sometimes useful, often surprising.

**People assume events are asynchronous and fire-and-forget. They are neither.**

## `@TransactionalEventListener` — the fix Day 133 promised

```java
@Component
public class OrderNotifications {

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)     // ⭐ default phase
    @Async("emailExecutor")                                                // ⭐ Day 177
    public void sendConfirmation(OrderPlacedEvent e) {
        mailer.sendOrderConfirmation(e.orderId());
    }
}
```

| Phase | Runs | Use |
|---|---|---|
| **`AFTER_COMMIT`** | ⭐ after a successful commit | **the default and usually right** |
| `AFTER_ROLLBACK` | after rollback | compensations, alerting |
| `AFTER_COMPLETION` | either | cleanup |
| `BEFORE_COMMIT` | still inside the transaction | ⭐ additional writes that must be atomic with it |

**⭐ Two traps that produce silent no-ops:**

1. **No transaction, no event.** By default a `@TransactionalEventListener` published outside a
   transaction is **dropped silently**. `fallbackExecution = true` changes that — and note it makes
   the listener run immediately, which may not be what you want either.
2. ⭐ **Writes in an `AFTER_COMMIT` listener need a new transaction.** The original is finished. Use
   `@Transactional(propagation = REQUIRES_NEW)` — and remember Day 164: that is a second connection.

## `@Async` + `AFTER_COMMIT`, and what it does not give you

**This combination is correct and it is not durable.** Day 177's rule stands: if the process dies
between commit and the async listener running, **the event is gone**. No retry, no record, no trace.

**For anything that must not be lost, this is the outbox** (Day 124):

```java
@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)   // ⭐ inside the transaction
public void recordOutbox(OrderPlacedEvent e) {
    outbox.save(new OutboxEntry("OrderPlaced", toJson(e)));           // ⭐ commits atomically
}
```

Then Day 178's poller publishes from the outbox with retries. **The event is committed with the order
or not at all** — which is the entire point of the pattern.

# Part 2 — ⭐ Where events are the right tool, and where they are not

**The honest test:**

> **Would you be comfortable if this listener never ran?**
> If no, the event must be durable — an outbox or a broker, not `publishEvent`.

| Use | Verdict |
|---|---|
| Decoupling a side effect within one module | ⭐ ✅ good |
| Domain events recorded for an audit narrative (Day 165) | ⭐ ✅ good |
| Cache invalidation after a write | ✅ good |
| Publishing to Kafka after commit | ⚠️ ⭐ only via the outbox |
| ⭐ **Core business flow across modules** | ❌ **see below** |
| Anything that must not be lost | ❌ Day 124 |
| Cross-service communication | ❌ a broker (Day 125) |

## ⭐ The architectural failure mode

```java
@EventListener public void a(OrderPlacedEvent e) { events.publishEvent(new StockReservedEvent(...)); }
@EventListener public void b(StockReservedEvent e) { events.publishEvent(new PaymentDueEvent(...)); }
@EventListener public void c(PaymentDueEvent e)   { events.publishEvent(new InvoiceCreatedEvent(...)); }
```

**This is a distributed system inside one JVM, with none of the benefits.** Specifically:

- **You cannot read the flow.** "What happens when an order is placed?" requires grepping for every
  listener of every event in the chain, recursively.
- **You cannot debug it.** The stack trace is a chain of `SimpleApplicationEventMulticaster` frames.
- **Ordering is implicit** — `@Order` on listeners, which nobody sees from the publisher's side.
- **Failure semantics are unclear.** Which of these are in the transaction? Which are async? A reader
  cannot tell without opening each listener.
- ⭐ **It cannot be tested as a unit**, because the behaviour lives in the wiring, not in any class.

**⭐ The rule:** *events are for notification, not orchestration.* "The order was placed" is a
notification. "Now reserve stock, then charge, then invoice" is orchestration, and orchestration
should be **an explicit method that a reader can follow top to bottom**:

```java
@Transactional
public Order place(CreateOrderRequest req) {
    Order order = repo.save(toOrder(req));
    inventory.reserve(order);                                   // ⭐ explicit
    payments.authorise(order);                                  // ⭐ explicit
    events.publishEvent(new OrderPlacedEvent(...));             // ⭐ notification only
    return order;
}
```

**One method, readable, testable, with visible ordering and visible failure semantics.** Events carry
only the things that genuinely do not affect the outcome.

# Part 3 — The useful details

## Built-in lifecycle events

| Event | Use |
|---|---|
| `ApplicationReadyEvent` | ⭐ **startup work.** Runs after the context is fully initialised — unlike `@PostConstruct` (Day 133), where proxies may not exist |
| `ContextRefreshedEvent` | ⚠️ can fire more than once with a parent context |
| `ContextClosedEvent` | shutdown work — Day 133's graceful drain |
| `AvailabilityChangeEvent` | ⭐ drive readiness manually (Day 143) |

```java
@EventListener(ApplicationReadyEvent.class)
public void warmCaches() { ... }                    // ⭐ the right place for startup work
```

```java
// ⭐ Take yourself out of the load balancer before a long maintenance task
AvailabilityChangeEvent.publish(context, ReadinessState.REFUSING_TRAFFIC);
```

## Conditional and generic listeners

```java
@EventListener(condition = "#event.total > 1000")                    // ⭐ SpEL — Day 138
public void flagHighValue(OrderPlacedEvent event) { ... }

@EventListener
public void onAnyEntityChange(EntityChangedEvent<?> e) { ... }       // ⭐ generics respected
```

## `@DomainEvents` — events from the aggregate

```java
@Entity
public class Order extends AbstractAggregateRoot<Order> {
    public void ship(String tracking) {
        this.status = SHIPPED;
        registerEvent(new OrderShippedEvent(publicId, tracking));   // ⭐ published on save()
    }
}
```

Day 165's domain events. **The advantage over publishing from the service:** the event is registered
by the *domain rule that caused it*, so it cannot be forgotten by a second caller who also ships an
order.

## Testing

```java
@SpringBootTest
@RecordApplicationEvents                                    // ⭐ Spring 5.3.3+
class OrderServiceTest {
    @Autowired ApplicationEvents events;

    @Test void publishesOrderPlaced() {
        service.place(request);
        assertThat(events.stream(OrderPlacedEvent.class)).hasSize(1);
    }
}
```

**Test that the event is published, separately from testing each listener.** That is the boundary the
event created — and if you cannot test the two halves independently, the event was not buying you
decoupling.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Assuming `publishEvent` is async | it is synchronous, in-transaction |
| A throwing listener | rolls back the publisher's transaction |
| Side effects on plain `@EventListener` | email sent for an order that rolls back (Day 124) |
| ⭐ `@TransactionalEventListener` outside a transaction | silently dropped |
| Writing in `AFTER_COMMIT` without `REQUIRES_NEW` | no transaction; nothing persists |
| `@Async` + `AFTER_COMMIT` for critical work | lost on crash — needs the outbox |
| ⭐ Event chains as control flow | unreadable, undebuggable, untestable |
| Ordering via `@Order` on listeners | implicit sequencing invisible from the publisher |
| Entities inside events | detached, lazy, possibly stale — send ids and values |
| `@PostConstruct` for startup work | proxies may not exist; use `ApplicationReadyEvent` |
| Events across services | needs a broker (Day 125) |

## Interview questions

**Q: Are Spring application events asynchronous?**
No — `publishEvent` is synchronous by default and runs on the publisher's thread inside its
transaction. So a slow listener slows the request, and a listener that throws rolls back the
publisher's work. `@Async` makes it asynchronous, and `@TransactionalEventListener(AFTER_COMMIT)` is
what stops a side effect firing for work that rolls back.

**Q: When would you use events, and when not?**
For notification of something that has already happened, where the listener is genuinely optional.
Not for orchestration — a chain of listeners publishing further events is a distributed system inside
one JVM with none of the benefits: you cannot read the flow, debug it, or test it as a unit. And not
for anything that must not be lost, because an in-process event dies with the process.

**Q: How do you publish to Kafka after a database commit?**
Through an outbox. A `BEFORE_COMMIT` listener writes the event to an outbox table in the same
transaction, so it commits atomically with the business data, and a poller publishes it with retries.
`AFTER_COMMIT` plus a direct publish loses the event if the process dies in between.

**Q: Why `ApplicationReadyEvent` rather than `@PostConstruct` for startup work?**
`@PostConstruct` runs during bean initialisation, when proxies may not exist and other beans may not
be ready. `ApplicationReadyEvent` fires once the context is fully started.

## Mini task

1. Publish an event and **print the thread name in the listener.** Confirm it is the caller's.
2. Throw from a listener inside a transactional publisher. **Confirm the publisher's write is rolled
   back.**
3. Send an "email" from a plain `@EventListener` and force a rollback. Confirm it was sent anyway.
4. Switch to `@TransactionalEventListener(AFTER_COMMIT)`. Confirm it is not sent.
5. Publish outside a transaction and confirm the listener is **silently skipped**. Add
   `fallbackExecution = true`.
6. Write to the database in an `AFTER_COMMIT` listener without `REQUIRES_NEW`. Confirm nothing
   persists.
7. Add `@Async`, then `kill -9` between commit and the listener. **Confirm the loss.**
8. Implement the `BEFORE_COMMIT` outbox and confirm atomicity by rolling back.
9. Build a three-event chain, then **draw the flow from the code alone.** Time yourself. Refactor to
   one explicit method and compare.
10. Use `@RecordApplicationEvents` to assert publication.

## 🎙️ Articulation drill

Two minutes: **"How do Spring application events work, and when do you use them?"**

Correct the common assumption first — synchronous, on the caller's thread, inside the transaction, so
a listener that throws rolls back the publisher. Then the phases and why `AFTER_COMMIT` exists. Then
the judgement, which is the real content: events are for notification, not orchestration, because a
chain of listeners is a distributed system inside one JVM that you cannot read, debug or test. Close
on durability — an in-process event dies with the process, so anything that must not be lost goes
through an outbox written in the same transaction.
