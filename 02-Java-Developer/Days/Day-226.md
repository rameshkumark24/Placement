# Part 1 — ⭐⭐ Most effects should not exist

```jsx
// ❌ ① DERIVED STATE — Day 225 wearing a hook
useEffect(() => { setFullName(first + " " + last); }, [first, last]);
// ✅ const fullName = first + " " + last;
//    ⭐⭐ the effect version renders TWICE and shows a stale value between

// ❌ ② EVENT HANDLING — the logic belongs in the handler
useEffect(() => { if (submitted) postForm(data); }, [submitted]);
// ✅ async function handleSubmit() { await postForm(data); }
//    ⭐⭐ "submitted" is not state; it is a thing that HAPPENED.

// ❌ ③ RESETTING ON A PROP CHANGE
useEffect(() => { setDraft(""); }, [userId]);
// ✅ <Editor key={userId} />     ⭐ Day 225 again

// ❌ ④ FETCHING (Day 227 gives the real answer)
useEffect(() => { fetch(url).then(r => r.json()).then(setData); }, [url]);
// ⭐⭐ races, no cancel, no cache, double-fires in StrictMode, no retry
```

```
⭐⭐ WHAT AN EFFECT IS ACTUALLY FOR — synchronising with the OUTSIDE
⭐   · a subscription (WebSocket, EventSource, store, media query)
⭐   · a browser API (title, focus, IntersectionObserver)
⭐   · a non-React widget (a map, a chart lib, a video player)
⭐   · analytics tied to a VIEW rather than a click
⭐   ⇒ ⭐⭐ IF NOTHING OUTSIDE REACT IS INVOLVED, IT IS PROBABLY NOT
⭐     AN EFFECT.

⭐   ⭐ THE CLOSEST THING YOU KNOW: @PostConstruct / @PreDestroy on a
⭐     bean that opens a resource. ⭐⭐ NOT a general-purpose
⭐     "run some logic when a field changes" hook — that instinct is
⭐     what produces all four bugs above.
```

# Part 2 — The dependency array

```jsx
useEffect(fn);              // ⭐ EVERY render — almost always wrong
useEffect(fn, []);          // ⭐ mount only (⭐⭐ twice in StrictMode dev)
useEffect(fn, [a, b]);      // ⭐ when a or b changes (Object.is)
```

```
⭐⭐ THE MISSING DEPENDENCY — ⭐ THE BUG THAT SENDS YOU A BILL

⭐   useEffect(() => {
⭐     fetchExpensiveThing(options);       // ⭐ options is an OBJECT
⭐   }, [options]);

⭐   ...and above it:
⭐   const options = { userId, limit: 20 };   ⭐⭐ NEW OBJECT EVERY RENDER

⭐   ⇒ effect runs → setState → re-render → NEW options object
⭐     → identity says CHANGED → effect runs → ... ⭐⭐ FOREVER.
⭐   ⇒ ⭐⭐ AN INFINITE LOOP OF PAID API CALLS. The page looks FINE.
⭐     Nothing errors. You find out from the invoice.
⭐   ⇒ ⭐ IN JAVA YOU WOULD HAVE OVERRIDDEN equals() AND THIS WOULD
⭐     NOT HAPPEN. ⭐⭐ HERE THERE IS NO equals() — Day 215, and this
⭐     is what it costs.
```

> ⭐⭐ **This is repo-README failure #1 — "huge surprise bill: an API call in a `useEffect` with no dep
> array" — and this is its precise mechanism.**

| ⭐ Fix | When |
|---|---|
| **Depend on primitives** | ⭐⭐ `[userId, limit]` instead of `[options]`. **Simplest and best.** |
| **Move the object inside** | ⭐ Construct `options` *in* the effect — then it is not a dep |
| **`useMemo` the object** | ⭐ When it must be shared |
| **`useCallback` the function** | ⭐ Same problem, for function deps |

> ⭐⭐ **Never silence the lint rule.** `// eslint-disable-next-line react-hooks/exhaustive-deps` is how
> a stale-closure bug gets committed with a comment claiming it is intentional. **If the honest deps
> loop, the effect is wrong — fix the effect, not the array.**

# Part 3 — ⭐ The stale closure

```jsx
// ❌ logs 0 forever
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []);                         // ⭐⭐ [] captured count FROM THE FIRST RENDER
```

```
⭐⭐ WHY: the effect closed over `count` as it was AT THAT RENDER.
⭐   `count` is effectively final per render (Day 223). ⭐ An empty
⭐   dep array means "never re-create this closure", so it keeps
⭐   the FIRST render's value forever.
⭐   ⇒ ⭐⭐ THIS IS EXACTLY THE JAVA RULE YOU ALREADY KNOW: A LAMBDA
⭐     CAPTURES THE **VALUE** OF AN EFFECTIVELY-FINAL LOCAL, NOT THE
⭐     VARIABLE. ⭐ You have hit it with a captured loop counter.
```

| ⭐ Fix | Code |
|---|---|
| **Functional update** | ⭐⭐ `setCount(c => c + 1)` — never reads the captured value |
| **Add the dep** | `[count]` — recreates the interval each change |
| **A ref for the latest value** | ⭐ `ref.current` when you need "the newest" without re-subscribing |

# Part 4 — Cleanup, and why StrictMode double-fires

```jsx
useEffect(() => {
  const ws = new WebSocket(url);
  ws.onmessage = onMessage;
  return () => ws.close();       // ⭐⭐ CLEANUP — not optional
}, [url]);
```

```
⭐⭐ CLEANUP RUNS: before every re-run, and on unmount.
⭐   ⭐ It is the finally block / @PreDestroy / try-with-resources
⭐     close — and forgetting it leaks exactly the same way.

⭐   ⇒ ⭐ StrictMode in dev does: setup → CLEANUP → setup.
⭐     ⭐⭐ THAT IS A TEST OF ONE THING: "DOES YOUR EFFECT SURVIVE
⭐     BEING RUN TWICE?" ⭐ If double-mounting breaks it, so would a
⭐     fast navigation away and back. StrictMode found a REAL bug.
```

| ⭐ Must clean up | Or you get |
|---|---|
| `setInterval` / `setTimeout` | ⭐⭐ Timers firing on unmounted components forever |
| Subscriptions, WebSockets | ⭐ Connection leak — N tabs × N navigations |
| `addEventListener` on `window` | ⭐⭐ A listener leak retaining the whole closure |
| In-flight requests | ⭐ The Day 217 race — cancel with `AbortController` |

```jsx
// ⭐⭐ the ignore-flag pattern, for when you cannot cancel
useEffect(() => {
  let ignore = false;
  load().then(d => { if (!ignore) setData(d); });
  return () => { ignore = true; };
}, [id]);
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "when do you use `useEffect`?"**

Answer the question they didn't ask first. **Mostly I don't. An effect is for synchronising with
something outside React — a subscription, a browser API, a non-React widget. It's `@PostConstruct` and
`@PreDestroy` on a bean that owns a resource, not a general "run logic when a field changes" hook. Most
effects people write are derived state or event handling in disguise, so the first question is whether
it should exist at all.**

Then the expensive bug, concretely. **The dependency array compares by reference, so an object literal
is new every render. Effect runs, sets state, re-renders, new object, deps "changed", effect runs
again — an infinite loop of paid API calls where the page looks completely fine. Nothing errors; you
find out from the invoice. In Java I'd have overridden `equals` and it wouldn't happen. There's no
`equals` here, and that's what it costs. The fix is depending on primitives.**

Then the closure, in terms you already own. **An empty dep array captures values from the first render,
so an interval logs zero forever. That's exactly the Java rule that a lambda captures the value of an
effectively-final local rather than the variable — I've hit it with a captured loop counter. The
functional update form fixes it because it never reads the captured value.**

Close on StrictMode. **Double-invoking in development isn't noise to disable. Setup, cleanup, setup
tests one thing: does my effect survive running twice? If it doesn't, it would also break on a fast
navigation away and back. It found a real bug early — it didn't create one.**
