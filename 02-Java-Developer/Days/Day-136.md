# Part 1 — Resolving ambiguity

```java
public interface PaymentGateway { Receipt charge(Money amount); }

@Component class StripeGateway   implements PaymentGateway { }
@Component class RazorpayGateway implements PaymentGateway { }
```

```
NoUniqueBeanDefinitionException: expected single matching bean but found 2:
stripeGateway, razorpayGateway
```

## 1. `@Qualifier` — explicit selection

```java
@Service
class OrderService {
    OrderService(@Qualifier("stripeGateway") PaymentGateway gateway) { … }
}
```

Clear and local to the injection point. Its weakness is the string: a typo is a **startup failure**
rather than a compile error, and refactoring tools do not follow it.

## ⭐ 2. A custom qualifier annotation — the better form

```java
@Qualifier
@Retention(RUNTIME)
@Target({FIELD, METHOD, PARAMETER, TYPE})
public @interface Stripe { }

@Component @Stripe class StripeGateway implements PaymentGateway { }

@Service
class OrderService {
    OrderService(@Stripe PaymentGateway gateway) { … }      // ⭐ compile-checked
}
```

**Type-safe, refactor-safe, and self-documenting.** A typo does not compile; "find usages" works;
renaming propagates. This should be your default whenever there is more than one candidate, and it is
under-used.

Qualifiers can also carry attributes, which is a neat way to express a dimension rather than a name:

```java
@Qualifier @Retention(RUNTIME)
public @interface Gateway { Provider value(); }

@Component @Gateway(Provider.STRIPE) class StripeGateway implements PaymentGateway { }
OrderService(@Gateway(Provider.STRIPE) PaymentGateway gateway) { … }
```

## 3. `@Primary` — a default

```java
@Component @Primary class StripeGateway   implements PaymentGateway { }
@Component          class RazorpayGateway implements PaymentGateway { }

OrderService(PaymentGateway gateway) { … }        // gets Stripe, unqualified
```

**Use it when one implementation is right almost everywhere** and the others are exceptions. The cost
is that the choice is invisible at the injection point — a reader of `OrderService` cannot tell which
gateway they are getting without going to look.

> **`@Primary` for a genuine default; a qualifier when the choice is a real decision.** If you find
> yourself qualifying most injection points, the `@Primary` is on the wrong bean.

## 4. Inject them all and choose at runtime

```java
@Service
class PaymentRouter {
    private final Map<String, PaymentGateway> gateways;       // bean name → bean

    PaymentRouter(Map<String, PaymentGateway> gateways) { this.gateways = gateways; }

    Receipt charge(String provider, Money amount) {
        PaymentGateway gw = gateways.get(provider + "Gateway");
        if (gw == null) throw new UnsupportedProviderException(provider);
        return gw.charge(amount);
    }
}
```

**This is Day 090's Open/Closed idiom.** Adding a provider is a new `@Component` and nothing else
changes.

**Better still, let the beans declare what they support** — no string keys at all:

```java
public interface PaymentGateway {
    Provider provider();
    Receipt charge(Money amount);
}

@Service
class PaymentRouter {
    private final Map<Provider, PaymentGateway> byProvider;

    PaymentRouter(List<PaymentGateway> gateways) {
        this.byProvider = gateways.stream()
                .collect(toMap(PaymentGateway::provider, identity()));   // Day 060
    }
}
```

`List<T>` injection is ordered by `@Order` or `Ordered`, which matters when the collaborators form a
chain — validators, filters, interceptors.

⚠️ **An empty `List<T>` injection succeeds with an empty list.** If at least one implementation is
required, assert it in the constructor — otherwise a mis-scanned package (Day 135) produces a
silently inert router rather than a startup failure.

# Part 2 — Profiles

**Profiles are named sets of beans and configuration, activated per environment.**

```java
@Component
@Profile("dev")
class InMemoryOrderRepository implements OrderRepository { }

@Component
@Profile("prod")
class PostgresOrderRepository implements OrderRepository { }

@Component
@Profile("!prod")                       // ⭐ NOT prod
class VerboseLoggingConfig { }

@Component
@Profile({"dev", "test"})               // dev OR test
class FakeEmailSender implements EmailSender { }

@Configuration
@Profile("prod & !legacy")              // ⭐ expressions (Spring 5.1+)
class ModernProdConfig { }
```

## Activating

```properties
spring.profiles.active=prod,metrics
```

```bash
java -jar app.jar --spring.profiles.active=prod
SPRING_PROFILES_ACTIVE=prod java -jar app.jar          # ⭐ the usual production form
```

```java
@ActiveProfiles("test")                  // in tests
class OrderServiceTest { }
```

**Profile-specific property files are merged over the base**, which is the mechanism you will use
most:

```
application.yml               ← always loaded
application-dev.yml           ← merged over it when `dev` is active
application-prod.yml
```

```yaml
# application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
app:
  payment:
    timeout: 5s

---
# application-prod.yml    (only the OVERRIDES)
spring:
  datasource:
    hikari:
      maximum-pool-size: 50
```

**Only override what differs.** Duplicating the whole file per profile guarantees they drift.

## ⭐ Where profiles go wrong

**Profile sprawl.** Ten profiles that can be combined arbitrarily produce a configuration space
nobody can reason about, and a combination that is never tested will eventually be deployed.

> **Keep profiles few and orthogonal.** `dev`, `test`, `prod` plus a small number of *feature*
> profiles (`metrics`, `kafka`). If you cannot enumerate the valid combinations, there are too many.

**Profiles used for feature flags.** A profile is fixed at startup; a feature flag must change at
runtime (Day 088). Using a profile to enable a feature means a restart to toggle it, and no gradual
rollout.

**⚠️ Different beans per environment is a testing hazard.** If `dev` uses an in-memory repository and
`prod` uses Postgres, **your tests never exercise the production code path** — which is exactly Day
097's argument for Testcontainers. Use profiles for *configuration* differences; use the same
implementations everywhere and give them different configuration.

```java
// ⚠️ different implementation per environment — the SQL is never tested
@Profile("dev")  @Component class InMemoryOrderRepository implements OrderRepository { }
@Profile("prod") @Component class PostgresOrderRepository implements OrderRepository { }

// ✅ one implementation, different configuration — and Testcontainers in tests
@Component class PostgresOrderRepository implements OrderRepository { }
// application-dev.yml points at a local Postgres from your compose stack (Day 129C)
```

**`@Profile("default")`** applies when no profile is active — useful as a safety net, and worth
knowing because a missing `SPRING_PROFILES_ACTIVE` in production is a real incident: the application
starts happily with development settings.

**Fail loudly instead:**

```java
@Component
class ProfileGuard {
    ProfileGuard(Environment env) {
        if (env.getActiveProfiles().length == 0)
            throw new IllegalStateException("No active profile. Set spring.profiles.active.");
    }
}
```

## Programmatic checks

```java
@Service
class ReportService {
    private final Environment env;

    void generate() {
        if (env.acceptsProfiles(Profiles.of("prod"))) { … }    // ⚠️ a smell — see below
    }
}
```

**Checking the profile inside business logic is a design smell.** It is a conditional that varies
behaviour by environment, which means the behaviour you test is not the behaviour you ship. Inject a
differently-*configured* collaborator instead, so the code path is identical everywhere.

# Part 3 — Choosing between the mechanisms

```
Two implementations, choice is a real decision       → ⭐ a custom qualifier annotation
One usual implementation, others are exceptions      → @Primary + qualifiers on the exceptions
Choice depends on runtime data                       → inject List/Map and dispatch
Choice depends on the ENVIRONMENT                    → @Profile — for configuration, not logic
Choice depends on the classpath or a property        → @Conditional* (Day 135)
Choice must change without a restart                 → ⭐ a feature flag, not any of the above
```

**The last row is the one people get wrong.** Every mechanism on this page is resolved at startup.
Anything that must be toggled while running is a runtime check inside the method (Day 088), not a
wiring decision.

## A worked combination

```java
public interface StorageService { String store(byte[] data, String name); }   // Day 126

@Component @Profile("!prod")
class LocalStorageService implements StorageService { }                  // dev and test

@Component @Profile("prod")
class S3StorageService implements StorageService {
    S3StorageService(S3Properties props) { … }                            // Day 131
}

@Service
class UploadService {
    private final StorageService storage;                   // ⭐ ONE candidate active at a time
    UploadService(StorageService storage) { this.storage = storage; }
}
```

**Because profiles filter the definitions, exactly one candidate exists** — so no qualifier is
needed, and `UploadService` has no idea which environment it is in. That is the property to aim for:
**the selection is visible in configuration, and invisible in code.**

Better still for this case, per the warning above: run **MinIO in your compose stack** (Day 129C) so
even development uses the S3 implementation, and only the endpoint differs.

## Common mistakes

| Mistake | Consequence |
|---|---|
| String `@Qualifier` everywhere | Typos become startup failures; refactoring misses them |
| `@Primary` where the choice is a real decision | The selection is invisible at the injection point |
| Qualifying most injection points | The `@Primary` is on the wrong bean |
| Assuming `List<T>` injection fails when empty | It succeeds with an empty list — silently inert |
| Profile sprawl | An untested combination will be deployed |
| Profiles as feature flags | Requires a restart; no gradual rollout |
| **Different implementations per profile** | **Production code paths are never tested** |
| No active profile in production | Starts with development defaults |
| `env.acceptsProfiles` inside business logic | Behaviour differs between test and production |
| Duplicating whole property files per profile | They drift |

## Interview questions

**Q: Two beans implement one interface. How do you choose?**
A qualifier — preferably a custom qualifier annotation rather than a string, so it is compile-checked
and refactor-safe. `@Primary` when one is a genuine default and the others are exceptions. If the
choice depends on runtime data, inject all of them as a `List` or `Map` and dispatch.

**Q: `@Qualifier` or `@Primary`?**
`@Primary` marks a default and makes the choice invisible at the injection point; a qualifier makes
it explicit. If you find yourself qualifying most injection points, the `@Primary` is wrong.

**Q: What are profiles for?**
Activating different beans and property files per environment, declaratively, so environment
differences live in configuration rather than in conditionals scattered through the code.

**Q: What is the danger of using profiles to swap implementations?**
Your tests exercise the development implementation and production runs a different one — so the code
path that matters is never tested. Use profiles for configuration differences and keep one
implementation, with Testcontainers or a compose stack providing real dependencies locally.

**Q: Can profiles be used as feature flags?**
No. They are fixed at startup, so toggling requires a restart and there is no gradual rollout. A
feature flag is a runtime check.

**Q: What happens if no profile is active in production?**
The application starts with the base configuration — often development defaults — which is a real
incident class. Guard against it explicitly by failing startup when no profile is set.

**Q: Why is checking the active profile inside business logic a smell?**
It makes behaviour environment-dependent, so what you test is not what you ship. Inject a
differently-configured collaborator instead and keep one code path.

## 🎙️ Articulation drill

Two minutes: **"How do you handle environment-specific configuration in Spring?"**

Profile-specific property files overriding a shared base, with only the differences duplicated;
profiles kept few and orthogonal; and — the part that shows judgement — **profiles for configuration
differences, not for swapping implementations**, because a production code path that only runs in
production is a code path you never test. Close with feature flags for anything that must change
without a restart.
