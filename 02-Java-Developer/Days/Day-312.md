# Day 312

**L-312** · Elevator — state machines, scheduling, and who is in charge

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Everyone models the elevator. The interview is about the dispatcher.**
>
> The single decision that separates answers: **does an elevator decide where to go, or does a
> controller decide for it?** Get that wrong and multi-elevator dispatch — which is where the round
> is heading — has nowhere to live.

---

# Part 1 — ⭐ Clarify, and the two request types

| Ask | ⭐ Why |
|---|---|
| ⭐ **"How many elevators?"** | ⭐ **one → a scheduling problem. Many → a dispatch problem. Assume many.** |
| ⭐ "Do requests know direction?" | ⭐ hall calls do, car calls do not — **this is the modelling crux** |
| "Express floors, service mode, capacity?" | ⭐ scope cut — mention, exclude |

> **⭐ The distinction that most candidates miss and that the whole model hangs on:**

| | ⭐ Hall call (external) | ⭐ Car call (internal) |
|---|---|---|
| Made from | ⭐ a floor | ⭐ inside the car |
| ⭐ **Carries** | ⭐ **floor + DIRECTION** | ⭐ **floor only** |
| ⭐ **Served by** | ⭐ **any elevator — the dispatcher chooses** | ⭐ **that specific elevator only** |
| Meaning | "someone wants to go up from 5" | "take me to 12" |

**⭐ Say it out loud:** *"A hall call is up-from-5 and can be served by any car; a car call is
to-12 and belongs to one car. So hall calls go to a dispatcher and car calls go straight to the
elevator's own queue."* **That one sentence structures the entire design.**

# Part 2 — ⭐ The model

```
   ⭐ ElevatorSystem
        │ 1
        ├──── * Elevator          ⭐ knows only ITS OWN stops
        │        ├─ state: IDLE | MOVING_UP | MOVING_DOWN | DOORS_OPEN | OUT_OF_SERVICE
        │        ├─ currentFloor, direction
        │        └─ up: TreeSet<Integer>, down: TreeSet<Integer>   ⭐ two ordered stop sets
        │
        ├──── Dispatcher  «interface»    ⭐ THE strategy — chooses which elevator
        └──── Request (Hall | Car)       ⭐ sealed (Day 042)
```

**⭐ The ownership decision, stated:**

> **⭐ The elevator owns its own stop list and how it moves through it. The dispatcher owns which
> elevator gets a hall call.** Two responsibilities, two classes, and multi-elevator scheduling
> becomes swapping one strategy rather than rewriting the elevator.

## ⭐ The state machine (draw it — Day 309)

```
                  ┌──────────────┐
      ┌──────────►│     IDLE     │◄───────────┐
      │           └──────┬───────┘            │  ⭐ no stops left
      │      request     │                    │
      │                  ▼                    │
   ┌──┴────────┐  ┌──────────────┐   arrive  ┌┴─────────────┐
   │ MOVING_UP │◄─┤   dispatch   ├─────────► │ DOORS_OPEN   │
   └───────────┘  └──────┬───────┘           └──────────────┘
                         ▼                       ⭐ timer → close → resume
                  ┌──────────────┐
                  │ MOVING_DOWN  │
                  └──────────────┘
```

| ⭐ Rule the diagram encodes | ⭐ Why it matters |
|---|---|
| ⭐ **No MOVING_UP → MOVING_DOWN directly** | ⭐ **you must pass through a stop — reversal happens at an extreme** |
| ⭐ **DOORS_OPEN accepts no movement** | ⭐ the safety invariant, and interviewers ask |
| ⭐ OUT_OF_SERVICE is reachable from anywhere | maintenance mode |
| Stops added while moving | ⭐ **the interesting case — see below** |

# Part 3 — ⭐⭐ The scheduling algorithm

## ⭐ Why FCFS is wrong, in one example

```
⭐ Car at floor 1. Requests arrive: 10, then 2.
⭐ FCFS:  1 → 10 → 2      = 17 floors of travel, and the person on 2 waited the whole trip
⭐ LOOK:  1 → 2 → 10      = 9 floors
```

> **⭐ An elevator does not serve requests in arrival order — it sweeps.** That is the LOOK algorithm
> (SCAN without going to the extreme), and it is the same disk-scheduling idea from B-series
> operating-systems work.

```java
// ⭐ Two sorted sets: stops above, stops below. The direction picks which one is active.
private final NavigableSet<Integer> up   = new TreeSet<>();
private final NavigableSet<Integer> down = new TreeSet<>(Comparator.reverseOrder());

void addStop(int floor) {
    if (floor > currentFloor) up.add(floor);
    else if (floor < currentFloor) down.add(floor);
    else openDoors();                                  // ⭐ already here
}

Optional<Integer> nextStop() {
    return switch (direction) {
        // ⭐ continue the sweep; if the active set is empty, REVERSE rather than idle
        case UP   -> first(up).or(() -> { direction = DOWN; return first(down); });
        case DOWN -> first(down).or(() -> { direction = UP;  return first(up);  });
        case NONE -> first(up).or(() -> first(down));
    };
}
```

**⭐ The property that makes it elegant, and worth saying:** a stop added *ahead of you in your
current direction* is served on this sweep automatically. **No re-planning, no re-sorting — the
ordered set does it.**

⚠️ **Starvation is the honest flaw.** With continuous traffic in one direction, the opposite
direction waits indefinitely. **Say it and give the fix:** cap the sweep, or age requests and force a
reversal past a threshold. **Naming the flaw in your own algorithm is a strong signal.**

## ⭐⭐ Multi-elevator dispatch — a cost function

**⭐ This is the part interviewers actually want.** Do not write a rule chain; write a cost:

```java
public interface Dispatcher { Elevator choose(HallCall call, List<Elevator> elevators); }

public final class NearestCarDispatcher implements Dispatcher {
    public Elevator choose(HallCall call, List<Elevator> elevators) {
        return elevators.stream()
                .filter(Elevator::inService)
                .min(Comparator.comparingInt(e -> cost(e, call)))     // ⭐ min cost wins
                .orElseThrow(NoElevatorAvailable::new);
    }

    private int cost(Elevator e, HallCall call) {
        int distance = Math.abs(e.currentFloor() - call.floor());
        if (e.isIdle())                                   return distance;              // ⭐ best
        if (e.movingToward(call.floor())
                && e.direction() == call.direction())     return distance;              // ⭐ free pickup
        if (e.movingToward(call.floor()))                 return distance + PENALTY;    // ⭐ wrong direction
        return distance + e.remainingStops() * PENALTY;                                 // ⭐ must turn around
    }
}
```

| ⭐ Why a cost function | |
|---|---|
| ⭐ **Tunable without restructuring** | change weights, not branches |
| ⭐ **Extends to new objectives** | ⭐ add load, energy, wait-time-so-far as terms |
| ⭐ **Explains itself** | you can print why an elevator was chosen |
| ⭐ It is how real systems work | ⭐ and it echoes Day 290: **rules as data** |

> **⭐ The case that shows you understand the domain: an elevator already moving up past floor 5, with
> an up hall call at 5, picks it up for free.** A cost function captures that naturally; an
> if-chain has to special-case it. **Mention this case explicitly.**

# Part 4 — ⭐ Concurrency, and the answer that simplifies everything

**⭐ Shared mutable state: each elevator's stop sets, plus the dispatcher's view of all elevators.**

**⭐ Offer the single-threaded controller (Day 310) — it is the right answer here:**

```
⭐ button presses ──► BlockingQueue<Request> ──► ONE controller thread
                                                  └─► tick(): move, open, close, dispatch
```

| ⭐ Why it wins here | |
|---|---|
| ⭐ **The state is one coherent thing** | positions, directions and stops must agree |
| ⭐ **Operations are microseconds** | ⭐ physical movement is seconds — throughput is a non-issue |
| ⭐ **Deterministic and replayable** | ⭐ **you can unit-test a whole traffic scenario tick by tick** |
| No locks at all | no deadlock, no interleaving to reason about |

> **⭐ Say it as a decision: "The physical system does one thing per tick, so I'll confine all state to
> a single controller thread with a request queue. Buttons are producers. That removes every race,
> and if I ever needed more throughput I'd shard by elevator bank — but a building will never need
> it."** That is both correct and clearly reasoned, which is the point.

**⭐ If they insist on locks:** per-elevator lock for its stop sets, and the dispatcher reads a
**snapshot** — a slightly stale view is fine because it only affects which elevator is chosen, never
correctness.

## ⭐ Extensions

| "Now add…" | ⭐ Answer |
|---|---|
| ⭐ **Capacity / weight** | a term in the cost function; a full car declines hall calls but keeps car calls |
| ⭐ **Express elevators** | ⭐ a `servesFloor(int)` filter before the cost function |
| ⭐ **Rush-hour modes** | ⭐ **a different `Dispatcher` — free, by design** (up-peak parks idle cars at the lobby) |
| Fire / service mode | a state, plus a system-wide override that clears queues |
| ⭐ **Destination dispatch** (enter your floor in the lobby) | ⭐ **the deep one — hall calls now carry a destination, so cars can be grouped by target** |
| Energy optimisation | another cost term |

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ FCFS scheduling | ⭐ absurd travel; the first thing they probe |
| ⭐ Not distinguishing hall and car calls | ⭐ **the dispatcher has nothing to dispatch** |
| ⭐ The elevator choosing itself | ⭐ multi-elevator has nowhere to live |
| An if-chain instead of a cost function | untunable; misses the free-pickup case |
| ⭐ Unsorted stop lists | you re-plan on every request instead of sweeping |
| ⭐ Not naming starvation | ⭐ the flaw in your own algorithm, unmentioned |
| Movement possible while DOORS_OPEN | the safety invariant, unmodelled |
| ⭐ Direct MOVING_UP → MOVING_DOWN | physically impossible; the state diagram catches it |
| Locks everywhere | you were offered a single-threaded design and did not take it |
| Real time in the domain | untestable — tick or a `Clock` port |

## Interview questions

**Q: What is the difference between the two request types, and why does it matter?**
A hall call is made from a floor and carries a direction; a car call is made inside and carries only
a target. Hall calls can be served by any elevator, so they go to a dispatcher; car calls belong to
one elevator's own queue. Without that split there is nothing for a dispatcher to decide, and
multi-elevator scheduling has no home.

**Q: What scheduling algorithm, and what is wrong with it?**
LOOK — sweep in one direction serving stops in order, then reverse. FCFS sends a car from 1 to 10 and
back to 2 for the same two requests. I keep two sorted sets, above and below, so a stop added ahead
of the car in its current direction is served this sweep with no re-planning. The honest flaw is
starvation under sustained one-direction traffic, which I would fix by ageing requests and forcing a
reversal.

**Q: How do you choose which elevator serves a hall call?**
A cost function, not a rule chain — distance, plus penalties for wrong direction and for having to
turn around, and idle cars preferred. It captures the case that matters: a car already travelling up
past floor five picks up an up-call at five for free. It is also tunable, extensible to load and
energy, and it can explain its own choice, which an if-chain cannot.

**Q: How do you handle concurrency?**
I confine all state to one controller thread fed by a request queue. The physical system does one
thing per tick and movement takes seconds, so throughput is a non-issue, and confinement removes
every race while making the whole thing deterministic and replayable in tests. If forced to use
locks, one per elevator for its stop sets, with the dispatcher reading a possibly-stale snapshot,
since staleness only affects which car is chosen and never correctness.

**Q: Now add destination dispatch.**
Hall calls carry a destination rather than a direction, so the dispatcher can group passengers going
to similar floors into the same car — which changes the cost function from "who is nearest" to "who
is already going there". It also removes car calls entirely, since the destination is known at
request time. That is the biggest structural change of any extension here, and it is a genuine
improvement in throughput for tall buildings.

## Mini task

1. **Run the 45-minute method** on this problem, timed and recorded.
2. Implement LOOK with **two sorted sets.** Test: from floor 1, request 10 then 2, and **assert the
   visit order is 2 then 10.**
3. Implement FCFS as well, and **compare total travel over 100 random requests.**
4. ⭐ **Write the free-pickup test**: a car moving up from 2 to 10, an up hall call at 5, and assert
   it is served on the way without extra travel.
5. Implement the cost-function dispatcher with three elevators. **Print the cost of each choice** and

6. ⭐ **Reproduce starvation**: sustained up traffic, one down request, and measure its wait. Then add
   ageing and measure again.

   ticks, asserting exact positions. **Note how much easier this is than testing a locked design.**
