# Part 1 — Safety and idempotency

Two properties, constantly confused, and both are contracts *you* must honour — HTTP defines them
but cannot enforce them.

| Method | Safe? | Idempotent? | Cacheable? |
|---|---|---|---|
| `GET` | ✅ | ✅ | ✅ |
| `HEAD` | ✅ | ✅ | ✅ |
| `OPTIONS` | ✅ | ✅ | ❌ |
| `PUT` | ❌ | ✅ | ❌ |
| `DELETE` | ❌ | ✅ | ❌ |
| `POST` | ❌ | ❌ | rarely |
| `PATCH` | ❌ | ❌ | ❌ |

**Safe** = no observable state change. A `GET` must not modify anything.

> **A `GET` that changes state is the classic disaster.** A "delete" link behind a `GET` gets
> crawled by a search-engine bot or a link preview, and your data disappears. This has happened to
> real companies.

Analytics counters and access logs are an accepted exception — the *resource* has not changed.

**Idempotent** = N identical requests have the same effect as one. Not the same *response* — the
same *effect*.

```
DELETE /orders/42   → 204   (deleted)
DELETE /orders/42   → 404   (already gone)     ← different response, SAME effect. Still idempotent.
```

**Why it matters:** the client cannot distinguish "the request never arrived" from "it arrived and
the response was lost". If the method is idempotent, retrying is safe. If not, retrying may charge
the card twice.

**`PATCH` is not idempotent in general.** `{"op":"increment","field":"quantity"}` applied twice gives
a different result. A `PATCH` that sets absolute values is idempotent in practice — but the *method*
makes no promise, so clients cannot assume it.

**`POST` is the problem case**, and Day 123 solves it with **idempotency keys**:

```http
POST /payments
Idempotency-Key: 8f14e45f-ea4d-4b2e-9f8a-1c2d3e4f5a6b

→ server stores (key → response). A repeat of the SAME key returns the STORED response
  without re-executing.
```

Stripe requires this. Any API that moves money should.

# Part 2 — The methods, precisely

## `PUT` vs `PATCH` vs `POST`

```http
POST /orders            → create; the SERVER assigns the URI → 201 + Location header
PUT  /orders/42         → full replace at a URI the CLIENT chose. Omitted fields are CLEARED.
PATCH /orders/42        → partial update
```

**The `PUT` trap:** it is a *replacement*. Send `{"status":"PAID"}` to `PUT /orders/42` and every
other field is legitimately erased. Many APIs implement `PUT` as a partial update, which is
convenient and wrong, and clients then get surprised by the one server that does it correctly.

`PUT` can also create, if the client knows the URI (`PUT /users/ram` where the username is the key)
— that is what makes it idempotent where `POST` is not.

Two `PATCH` formats worth knowing by name:

```http
Content-Type: application/merge-patch+json      RFC 7386
{"status": "PAID", "note": null}                ← null MEANS delete this field

Content-Type: application/json-patch+json       RFC 6902
[{"op":"replace","path":"/status","value":"PAID"},
 {"op":"add","path":"/tags/-","value":"urgent"}]
```

Merge-patch is simpler and cannot express "append to an array" or distinguish "set to null" from
"leave alone" without the null convention. JSON Patch is precise and verbose. **Pick one and state it
in your docs**; ambiguity here causes real bugs.

## Response codes for writes

```
201 Created          + Location: /orders/42      ← always include Location
202 Accepted         accepted, not yet done (async) — include a status URL
204 No Content       success, nothing to return (DELETE, PUT)
200 OK               success with a body
409 Conflict         version conflict, duplicate, illegal state transition
422 Unprocessable    syntactically valid, semantically wrong
```

# Part 3 — Caching

The most under-used capability in HTTP. **A response served from a cache costs you nothing** — and
most APIs disable caching by reflex without understanding what they gave up.

## `Cache-Control`

```http
Cache-Control: no-store                      # never store. Auth tokens, personal data.
Cache-Control: no-cache                      # store, but REVALIDATE before every use
Cache-Control: private, max-age=300          # browser only, 5 min. Per-user data.
Cache-Control: public, max-age=31536000, immutable    # CDN + browser, a year. Hashed assets.
Cache-Control: public, max-age=60, stale-while-revalidate=300
Cache-Control: must-revalidate               # once stale, do NOT serve without checking
```

Two distinctions that matter constantly:

**`no-cache` does not mean "do not cache".** It means "cache it, but revalidate every time before
serving". The one that means do not store is **`no-store`**.

**`private` vs `public`** decides whether *shared* caches (CDN, proxy) may store it. A response
containing one user's data with `public` is a data leak — a CDN will serve it to the next person.
**This is a real and recurring incident class**; it is why user-specific responses must be `private`
or `no-store`, and why `Vary: Authorization` matters.

```http
Vary: Accept-Encoding, Accept-Language, Authorization
```

`Vary` tells caches which request headers change the response. **Omitting `Vary: Authorization` on an
authenticated response is how one user gets served another's data from a shared cache.**

## Conditional requests — the bandwidth win

```http
# First response
HTTP/1.1 200 OK
ETag: "a1b2c3d4"
Last-Modified: Thu, 14 Aug 2026 10:22:01 GMT
Cache-Control: private, max-age=60

# Later, the client asks "has it changed?"
GET /orders/42
If-None-Match: "a1b2c3d4"

HTTP/1.1 304 Not Modified          ← NO BODY. Headers only.
```

A `304` costs a round trip and a few hundred bytes instead of the full payload. On a mobile client
polling a resource, that is the difference between a usable app and a battery complaint.

Implementing an `ETag` is trivial and worth doing:

```java
String etag = "\"" + Integer.toHexString(order.hashCode()) + "\"";   // or a version column
if (etag.equals(request.getHeader("If-None-Match"))) {
    return ResponseEntity.status(304).eTag(etag).build();
}
return ResponseEntity.ok().eTag(etag).body(order);
```

**Strong vs weak:** `"abc"` means byte-identical; `W/"abc"` means semantically equivalent. Use a
version column or an `updated_at` timestamp rather than hashing the serialized body — hashing means
you did all the work anyway, which loses most of the benefit.

## `ETag` for optimistic concurrency — the better use

This is the part most people miss, and it solves a real problem:

```http
PUT /orders/42
If-Match: "a1b2c3d4"

→ 200 OK              if the current ETag matches
→ 412 Precondition Failed    if someone else modified it first
```

**That is optimistic locking over HTTP** — the same idea as a `@Version` column (Day 091's D-05
lineage, and Stage 5's JPA). It prevents the lost update where two clients both `GET`, both edit, and
the second silently overwrites the first.

```http
If-None-Match: *          # create only if it does not exist → 412 if it does
```

# Part 4 — The rest of the wire

## Content negotiation

```http
Accept: application/json, application/xml;q=0.8
Accept-Language: ta-IN, en;q=0.9
Accept-Encoding: gzip, br
Content-Type: application/json; charset=utf-8
```

The `q` value is a preference weight from 0 to 1. If you cannot satisfy `Accept`, return
**`406 Not Acceptable`**; if you do not understand the request's `Content-Type`, return
**`415 Unsupported Media Type`**.

## Compression

`Content-Encoding: gzip` typically cuts JSON by 70–90%. Enable it — but **not for already-compressed
payloads** (images, video, `.gz`) where it costs CPU and gains nothing. `br` (Brotli) beats gzip by
roughly 15–20% and is universally supported now.

⚠️ **BREACH:** compressing a response that contains both a secret (a CSRF token) and
attacker-controlled input can leak the secret through response *size*. The practical mitigations are
to keep secrets out of compressed response bodies and to rely on TLS plus per-request token
randomisation.

## Range requests

```http
Range: bytes=0-1023
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-1023/146515
Accept-Ranges: bytes
```

Resumable downloads and video seeking. Advertise `Accept-Ranges` if you serve large files.

## Timeouts, connections and the headers that bite

```http
Connection: keep-alive          # default in HTTP/1.1 — reuses the TCP connection (Day 008)
Retry-After: 120                # send with 503 and 429. Clients should honour it.
Location: /orders/42            # with 201 and 3xx
```

**Every client you write needs both a connect timeout and a read timeout** (Day 082). A hung request
with no timeout holds a thread until the pool is exhausted (Day 069) — the most common cascading
failure in backend systems.

## HTTP/2 and HTTP/3 for the server side

Day 011 covered the protocol. What changes for you as a backend engineer:

- **Multiplexing removes the need for domain sharding and asset concatenation.**
- **Header compression** (HPACK) makes small frequent requests much cheaper — so chatty APIs hurt
  less than they used to, though they still hurt.
- **Server push is dead** — removed from Chrome; use `103 Early Hints` instead.
- **HTTP/3 over QUIC** eliminates TCP head-of-line blocking; it matters most on lossy mobile
  networks.

## Common mistakes

| Mistake | Consequence |
|---|---|
| State-changing `GET` | A crawler deletes your data |
| Assuming `POST` retries are safe | Double charges |
| `PUT` implemented as a partial update | Clients surprised; fields silently retained |
| `no-cache` believed to mean "do not cache" | It means revalidate; use `no-store` |
| `public` on a per-user response | A CDN serves one user's data to another |
| Missing `Vary: Authorization` | Same leak, through a shared cache |
| `no-store` on everything by reflex | Free performance discarded |
| `ETag` computed by hashing the rendered body | You did all the work anyway |
| No `If-Match` on updates | Silent lost updates |
| No `Location` header on `201` | The client cannot find what it created |
| Compressing already-compressed payloads | CPU for nothing |
| No client timeouts | Thread-pool exhaustion cascades |

## Interview questions

**Q: Safe vs idempotent?**
Safe means no observable state change — `GET`, `HEAD`, `OPTIONS`. Idempotent means N identical
requests have the same *effect* as one; the responses may differ. `DELETE` returning 404 the second
time is still idempotent.

**Q: Is `PATCH` idempotent?**
Not in general — an increment operation is not. A `PATCH` that sets absolute values happens to be,
but the method makes no promise, so clients must not assume it.

**Q: How do you make `POST` safe to retry?**
An idempotency key: the client sends a unique key, the server stores key → response, and a repeat of
the same key returns the stored response without re-executing.

**Q: What does `Cache-Control: no-cache` mean?**
Store it, but revalidate with the origin before serving. `no-store` is the directive that forbids
storing.

**Q: Why is `Vary` important?**
It tells shared caches which request headers change the response. Without `Vary: Authorization`, a
cache can serve one authenticated user's response to another.

**Q: How would you implement optimistic concurrency over HTTP?**
`ETag` plus `If-Match`: the client sends the ETag it read, and the server returns `412 Precondition
Failed` if the resource changed in the meantime — preventing the lost update.

**Q: What is a `304` worth?**
A round trip and a few hundred bytes instead of the full body. On mobile and polling clients it is
the difference between acceptable and not.

## 🎙️ Articulation drill

Two minutes: **"How does HTTP caching work, and how would you use it in an API?"**

`Cache-Control` for freshness, `ETag`/`Last-Modified` for validation, `304` for the cheap revalidate,
`Vary` for correctness with shared caches, and `private` versus `public` as a security decision, not
a performance one. Then the twist most people miss: `ETag` plus `If-Match` gives you optimistic
concurrency for free.
