# Part 1 — L-081 · Processes and signals

## Inspecting

```bash
ps aux                       # BSD style: every process, every user
ps -ef                       # System V style: same thing
ps -eLf                      # one line per THREAD
ps -o pid,ppid,rss,%cpu,etime,cmd -p <pid>
ps aux --sort=-%mem | head
pstree -p <pid>              # the process tree
top / htop                   # live
top -H -p <pid>              # threads of one process — Day 071
```

`ps aux` columns worth reading correctly:

| Column | Means |
|---|---|
| `VSZ` | Virtual size — address space *reserved*. **Usually meaningless** for a JVM |
| `RSS` | Resident set — actual physical RAM. **This is the real number** |
| `STAT` | `R` running, `S` sleeping, `D` uninterruptible (disk), `Z` zombie, `T` stopped |
| `%CPU` | Averaged over the process's lifetime in `ps`, instantaneous in `top` |

**`STAT D` is the one to notice.** Uninterruptible sleep means blocked in a kernel I/O call — it
cannot even be killed with `-9` until the I/O completes. A pile of `D` processes means the storage
layer is in trouble, not your application.

**A JVM's `VSZ` is enormous and irrelevant** — it reserves the whole heap's address space up front.
Compare `RSS` against `-Xmx` (Day 071).

## Signals

A signal is **an asynchronous notification delivered to a process by the kernel**. The process can
handle most of them, ignore some, and cannot touch two.

| Signal | Num | Default | Catchable | Use |
|---|---|---|---|---|
| `SIGHUP` | 1 | terminate | ✅ | Terminal closed; conventionally **"reload config"** |
| `SIGINT` | 2 | terminate | ✅ | Ctrl-C |
| `SIGQUIT` | 3 | core dump | ✅ | **JVM: prints a thread dump** (Day 076) |
| `SIGKILL` | **9** | terminate | ❌ **never** | Last resort |
| `SIGTERM` | **15** | terminate | ✅ | **The polite stop. The default of `kill`** |
| `SIGSTOP` | 19 | stop | ❌ | Suspend |
| `SIGCONT` | 18 | continue | ✅ | Resume |
| `SIGUSR1/2` | 10/12 | terminate | ✅ | Application-defined |

```bash
kill <pid>            # sends SIGTERM (15) — the default
kill -9 <pid>         # SIGKILL
kill -TERM <pid>
kill -3 <pid>         # JVM thread dump to stdout
kill -l               # list all signals
pkill -f "java.*myapp"
killall java
```

### Why `kill -9` is the wrong first instinct

`SIGTERM` is deliverable to the process, so the application can **shut down gracefully**: finish
in-flight requests, flush buffers, close connections, deregister from the load balancer, run
shutdown hooks.

`SIGKILL` is handled entirely by the kernel — **the process never sees it**. So:

- buffered writes are lost (Day 063 — including the last log lines),
- files are left half-written,
- database connections are not closed and linger until the server times them out,
- locks in shared systems are not released,
- **JVM shutdown hooks do not run.**

> **`kill` first. Wait. `kill -9` only if it will not stop.**

The JVM side, which you will actually write:

```java
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    log.info("SIGTERM received — draining");
    server.stopAcceptingConnections();
    pool.shutdown();                                  // Day 069
    pool.awaitTermination(25, TimeUnit.SECONDS);
    dataSource.close();
}));
```

Shutdown hooks run on `SIGTERM`, `SIGINT` and normal exit. They do **not** run on `SIGKILL`,
`Runtime.halt()`, or a JVM crash. Keep them fast — most orchestrators wait 30 seconds and then send
`SIGKILL`. That number matters: **Kubernetes sends `SIGTERM`, waits `terminationGracePeriodSeconds`
(default 30), then `SIGKILL`** — so a 25-second drain budget with a 30-second grace period is a
deliberate pairing, not a coincidence.

## Zombies and orphans

A **zombie** (`STAT Z`) is a process that has exited but whose parent has not called `wait()` to
collect its exit status. It holds no memory — only a process-table entry. **You cannot kill a
zombie; it is already dead.** Fix the parent, or kill the parent so `init` (pid 1) reaps it.

An **orphan** is a live process whose parent died; `init`/`systemd` adopts it.

This matters in containers: **if your app runs as pid 1, it inherits the responsibility of reaping
orphans**, and most applications do not. That is why `docker run --init` exists, and why zombie
accumulation in containers is a known failure mode.

## `nohup`, `&`, and process groups

```bash
cmd &                  # background job, still in the terminal's process group
nohup cmd &            # ignores SIGHUP; survives logout
setsid cmd             # new session — fully detached
```

Ctrl-C sends `SIGINT` to the whole **foreground process group**, which is why it kills a pipeline and
not just the last command.

## `systemd` — what actually runs your service

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My Java Application
After=network.target postgresql.service
Requires=postgresql.service

[Service]
Type=simple
User=appuser                      # ← never root (Day 078)
Group=appgroup
WorkingDirectory=/opt/myapp
Environment="JAVA_OPTS=-Xmx2g -XX:+HeapDumpOnOutOfMemoryError"
EnvironmentFile=-/etc/myapp/env   # '-' = optional
ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/myapp/app.jar
ExecReload=/bin/kill -HUP $MAINPID

Restart=on-failure                # no | always | on-failure | on-abnormal
RestartSec=5
StartLimitIntervalSec=300         # ← without these two, a crash-loop
StartLimitBurst=5                 #    restarts forever, hammering dependencies

TimeoutStopSec=30                 # SIGTERM, then SIGKILL after 30s
KillSignal=SIGTERM

# hardening — cheap and worth doing
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/log/myapp /var/lib/myapp

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload      # after ANY unit-file change
sudo systemctl enable --now myapp # start + start at boot
systemctl status myapp
systemctl restart myapp
journalctl -u myapp -f            # follow
journalctl -u myapp --since "10 min ago" -p err
systemctl list-units --failed
```

Three details that matter operationally:

**`Restart=on-failure` plus `StartLimitBurst`.** Without the limit, a service that crashes on
startup restarts forever — hammering the database it cannot reach and filling the disk with logs.
With it, systemd gives up and marks the unit failed, which is what you want your alerting to see.

**`After=` is ordering, `Requires=` is dependency.** `After` without `Requires` means "start me after
it *if* it is starting", not "it must be running".

**stdout goes to the journal.** Which is Day 073A's point: log to stdout, let the platform collect
it. `journalctl -u myapp` then works with no file configuration at all.

## `ulimit` — the limits your JVM will hit

```bash
ulimit -a
ulimit -n              # open file descriptors — the one that bites (Day 071)
ulimit -u              # max processes/threads
ulimit -v              # virtual memory
cat /proc/<pid>/limits # what is ACTUALLY in force for a running process
```

The default `nofile` of 1024 is the cause of most "Too many open files" incidents. In systemd set
`LimitNOFILE=65536`; shell `ulimit` does **not** affect a systemd-managed service.

# Part 2 — D-02 · The relational model

## Codd's idea

Edgar Codd's 1970 insight: **represent all data as relations — mathematical sets of tuples — and
query them with a language based on set operations.** No pointers, no navigation paths, no knowledge
of physical layout. That decoupling is Day 078's physical data independence.

| Formal term | SQL term | Is |
|---|---|---|
| Relation | Table | A **set** of tuples |
| Tuple | Row | One fact |
| Attribute | Column | A named component |
| Domain | Data type + constraints | The legal values |
| Cardinality | Row count | |
| Degree | Column count | |

Two properties of the *formal* model that SQL relaxes, and the gap is a favourite interview
question:

- **A relation is a set** — no duplicate tuples and no ordering. **SQL tables are bags**: duplicates
  are allowed unless a key forbids them, which is why `SELECT DISTINCT` and `UNION ALL` both exist.
- **Attributes are unordered** in the model; SQL gives columns a position, which is why
  `SELECT *` order is stable and why `INSERT` without a column list is fragile.

**First Normal Form is baked into the definition:** every attribute value is atomic. No arrays, no
nested structures, no comma-separated lists in a column. (Modern PostgreSQL offers arrays and
`jsonb` — using them is a deliberate, documented departure, not a default.)

## Keys — the whole family

```sql
CREATE TABLE enrollment (
    student_id  INT      NOT NULL REFERENCES student(id),
    course_id   INT      NOT NULL REFERENCES course(id),
    enrolled_on DATE     NOT NULL,
    grade       CHAR(2),
    PRIMARY KEY (student_id, course_id)          -- composite
);
```

| Key | Definition |
|---|---|
| **Superkey** | Any attribute set that uniquely identifies a tuple |
| **Candidate key** | A **minimal** superkey — remove any attribute and uniqueness is lost |
| **Primary key** | The chosen candidate key. Implies `NOT NULL` + `UNIQUE` |
| **Alternate key** | The candidate keys not chosen |
| **Composite key** | A key over more than one attribute |
| **Foreign key** | An attribute set referencing another relation's key |
| **Surrogate key** | A system-generated id with no business meaning |
| **Natural key** | A key from the data itself (email, ISBN) |

**Minimality is what separates a superkey from a candidate key**, and it is the definition
interviewers check. `{student_id, course_id, enrolled_on}` is a superkey; it is not a candidate key
because a proper subset already identifies the row.

### Surrogate vs natural — the argument

| | Surrogate (`id BIGSERIAL`) | Natural (`email`, `isbn`) |
|---|---|---|
| Stable when the business changes | ✅ | ❌ people change email |
| Narrow, fast to join and index | ✅ | ❌ wide strings |
| Meaningful without a join | ❌ | ✅ |
| Prevents duplicates by itself | ❌ | ✅ |

**Use a surrogate primary key and a unique constraint on the natural key.** That gets both: stable
joins and enforced business uniqueness. This is the standard answer and it is what JPA assumes.

One caution to state: a surrogate key alone does **not** prevent duplicate rows. A table with an
auto-increment id and no unique constraint on `email` will happily hold the same person twice.

## Integrity constraints

```sql
CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customer(id) ON DELETE RESTRICT,
    total_cents BIGINT NOT NULL CHECK (total_cents >= 0),
    status      TEXT   NOT NULL CHECK (status IN ('NEW','PAID','SHIPPED','CANCELLED')),
    email       TEXT   NOT NULL UNIQUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- **Domain integrity** — the value is in the type's legal set (`CHECK`, `NOT NULL`, enum).
- **Entity integrity** — the primary key is unique and never null. *Null cannot identify anything.*
- **Referential integrity** — every foreign key value exists in the referenced relation, or is null.

Referential actions on delete: `RESTRICT`/`NO ACTION` (refuse), `CASCADE` (delete children),
`SET NULL`, `SET DEFAULT`. **Prefer `RESTRICT` by default** — `CASCADE` deleting a customer and
silently taking a year of orders with it is a data-loss incident waiting to happen.

> **Constraints belong in the database, not only in the application.** The database is the last line
> of defence and the only one that survives a second application, a migration script, or someone
> with a SQL client. An application-only check is a suggestion.

## NULL — three-valued logic

**NULL means "unknown", not "empty" and not "zero".** Everything follows:

```sql
NULL = NULL          -- UNKNOWN, not TRUE   ← use IS NULL
NULL <> 5            -- UNKNOWN
NULL + 5             -- NULL
COUNT(*)             -- counts rows
COUNT(col)           -- SKIPS nulls          ← a common bug
SUM/AVG              -- skip nulls (AVG divides by the non-null count)
WHERE col <> 'X'     -- EXCLUDES rows where col IS NULL. Almost never what you meant.
```

That last one is the practical trap: filtering "status is not cancelled" with `<> 'CANCELLED'`
silently drops every row with a null status. Write `WHERE col IS DISTINCT FROM 'X'` or
`WHERE (col <> 'X' OR col IS NULL)`.

Also: `UNIQUE` allows **multiple** nulls, because two unknowns are not known to be equal.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `kill -9` first | Lost buffers, no shutdown hooks, stale connections |
| Trying to kill a zombie | It is already dead — fix or kill the parent |
| Reading `VSZ` as memory usage | Wildly misleading for a JVM |
| App running as root | Compromise escalates |
| No `StartLimitBurst` | Infinite crash-loop |
| Shell `ulimit` for a systemd service | Ignored — use `LimitNOFILE` |
| Forgetting `daemon-reload` | Your unit-file edit does nothing |
| Constraints only in the application | Bad data arrives by another path |
| `CASCADE` by default | Silent mass deletion |
| `col <> 'X'` with nullable columns | Rows silently excluded |
| Natural key as the primary key | Business change breaks every foreign key |

## Interview questions

**Q: `SIGTERM` vs `SIGKILL`?**
`SIGTERM` is catchable, so the process can drain and clean up; `SIGKILL` is handled by the kernel and
the process never sees it, so buffers, connections and shutdown hooks are lost. Always TERM first.

**Q: What is a zombie process?**
An exited process whose parent has not reaped its exit status. It uses no memory, only a table
entry, and cannot be killed. In containers this matters because pid 1 must reap orphans.

**Q: How does a graceful shutdown work for a JVM in Kubernetes?**
Kubernetes sends `SIGTERM`, the JVM runs shutdown hooks — stop accepting, drain in-flight work,
close pools — and after `terminationGracePeriodSeconds` (default 30) it sends `SIGKILL`. So the
drain budget must be under the grace period.

**Q: Superkey vs candidate key vs primary key?**
A superkey uniquely identifies a tuple; a candidate key is a *minimal* superkey; the primary key is
the chosen candidate key, implying `NOT NULL` and `UNIQUE`.

**Q: Surrogate or natural primary key?**
Surrogate for the primary key — stable, narrow, fast to join — plus a unique constraint on the
natural key so business uniqueness is still enforced.

**Q: What does NULL mean, and name two consequences.**
Unknown. Comparisons yield UNKNOWN rather than TRUE, so you need `IS NULL`; `COUNT(col)` skips
nulls; `WHERE col <> 'X'` excludes null rows; and `UNIQUE` permits multiple nulls.

**Q: Where do constraints belong?**
In the database. The application is one of several possible writers; the database is the only place
that constrains all of them.

## 🎙️ Articulation drill

Two minutes: **"What happens when your service is deployed and the old pod is terminated?"**

`SIGTERM` → shutdown hook → stop accepting, deregister from the load balancer, drain in-flight
requests, close the pool → exit within the grace period, or `SIGKILL`. Then say what breaks if you
skip it: dropped requests mid-flight and connections the database holds open until timeout. That is
a deployment answer built from signals, which is exactly the level Stage 2 is aiming at.
