```

⭐   ⭐⭐ ONE ORIGIN: https://app.example.com

⭐        /api/*       ⇒ ⭐ reverse-proxied to Spring
```

# Part 2 — ⭐⭐ Error reporting

```
⭐⭐ WITHOUT THIS, YOUR ERROR RATE IS **UNKNOWN**, NOT ZERO.

⭐   ⭐ A user hits a bug on Safari 16 on an old iPhone.
⭐     ⭐⭐ THEY DO NOT REPORT IT. THEY LEAVE.
⭐   ⇒ ⭐ Your Spring logs show nothing — the request never failed,
⭐     or was never made.
⭐   ⇒ ⭐⭐ THE ERROR EXISTS ONLY ON THEIR MACHINE UNLESS YOU SHIP
⭐     IT BACK.
```

```javascript
Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,        // ⭐ public by design
  environment: import.meta.env.MODE,
  release: __BUILD_ID__,                        // ⭐⭐ ties errors to a deploy
  tracesSampleRate: 0.1,
  beforeSend(event) {
    scrubPII(event);                            // ⭐⭐ Day 450 — see below
    return event;
  },
});
```

```
⭐⭐ THE FOUR SOURCES, AND YOU NEED ALL FOUR (Day 240)
⭐   ① error boundaries      ⇒ render errors
⭐   ② ⭐ window.onerror      ⇒ everything else synchronous
⭐   ③ ⭐⭐ unhandledrejection ⇒ **MOST OF YOUR REAL SURFACE** (Day 216)
⭐   ④ your API layer        ⇒ ⭐ failed requests, with the request id
```

| ⭐ Make a report useful | |
|---|---|
| **⭐⭐ The request id** | Day 273. **Turns a browser error into a Spring log line.** |
| **Release/build id** | ⭐ "Only on the build from Tuesday" |
| **Breadcrumbs** | ⭐ The clicks before the error |
| **⭐⭐ Scrub PII** | Emails, tokens, form values, URLs with ids. **Your error tracker becomes a data store you did not design** (Day 450) — and it is often the least-protected one you own. |

# Part 3 — The three analytics events

```
⭐⭐ NOT PAGE VIEWS. THREE EVENTS THAT ANSWER REAL QUESTIONS.

⭐ ① ⭐ WORKFLOW STARTED   ⇒ they began the thing your app is for
⭐ ② ⭐⭐ WORKFLOW COMPLETED ⇒ they finished it
⭐ ③ ⭐⭐ WORKFLOW FAILED    ⇒ with the reason

⭐   ⇒ ⭐⭐ THOSE THREE GIVE YOU A **FUNNEL** AND A **FAILURE RATE**,
⭐     WHICH ARE THE ONLY TWO NUMBERS THAT MATTER FOR A PROJECT
⭐     THIS SIZE.
⭐   ⇒ ⭐ AND THEY GIVE YOU AN INTERVIEW SENTENCE WITH A NUMBER IN
⭐     IT: "the refund flow completed 94% of the time; the 6% were
⭐     mostly 409s from stale data, so I added the conflict banner."
⭐     ⭐⭐ THAT IS A DAY 463 NUMBER YOU CAN RECONSTRUCT.
```

| ⭐ Rule | |
|---|---|
| **Name events as past-tense facts** | ⭐ `order.refunded`, not `clicked_button_3` |
| **⭐⭐ No PII in properties** | Ids, not names or emails |
| **Respect Do Not Track / consent** | ⭐ And say you do |
| **⭐ Web vitals go here too** | Day 241's RUM beacon |

# Part 4 — ⭐⭐ The live check

```
⭐⭐ AFTER THE FIRST DEPLOY, DO ALL OF THIS ON THE REAL URL.
⭐   ⭐ NOT localhost. THINGS THAT ONLY BREAK IN PRODUCTION:

⭐   □ ⭐ HTTPS, valid cert, no mixed-content warnings
⭐   □ ⭐⭐ COOKIES SET WITH Secure + HttpOnly + SameSite — CHECK IN
⭐     THE APPLICATION TAB. ⭐ Secure cookies silently do not set
⭐     over plain HTTP, so this is the classic "works locally" bug.
⭐   □ login → the workflow → logout, on the real domain
⭐   □ ⭐ HARD REFRESH ON A DEEP ROUTE ⇒ ⭐⭐ /orders/4471 MUST NOT
⭐     404. Your proxy needs an SPA fallback to index.html.
⭐   □ ⭐ THE BACK BUTTON through the whole flow
⭐   □ ⭐⭐ ON A REAL PHONE, ON MOBILE DATA
⭐   □ ⭐ TRIGGER A REAL ERROR ⇒ confirm it lands in Sentry with
⭐     the request id ⇒ ⭐⭐ GREP THAT ID IN THE SPRING LOG
⭐   □ ⭐ curl the API from another origin ⇒ CORS behaves
⭐   □ ⭐⭐ curl a protected endpoint WITH NO AUTH ⇒ 401/403 (Day 236)
⭐   □ Lighthouse on the deployed URL (Day 241)
```

> ⭐⭐ **The deep-route 404 catches nearly everyone.** The dev server handles it silently; nginx or S3
> does not, and you only find out when someone shares a link.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you know if your frontend is broken in production?"**

Open with the asymmetry. **Because I ship the errors back to myself. A frontend has no logs I can tail
— every error happens on a machine I don't own, in a browser I didn't choose. A user hits a bug on an
old Safari and doesn't report it, they just leave. Without reporting, my error rate isn't zero, it's
unknown.**

Then the completeness. **Four sources: error boundaries for render errors, `window.onerror`, unhandled
promise rejections — which is most of the real surface, because a rejected promise nobody awaited fails
silently — and my API layer for failed requests.**

Then the field that makes it work. **Every report carries the request id my transport generates. A
Spring filter puts it in the MDC, so a browser error report leads directly to the log lines for that
request. That's the difference between debugging a report and dismissing it. Reports also carry the
build id, so I can say "only on Tuesday's deploy", and I scrub PII in `beforeSend`, because otherwise
the error tracker becomes a data store I never designed and it's usually the least-protected one I own.**

Then the numbers. **Three analytics events — workflow started, completed, failed with a reason. That's
a funnel and a failure rate, which are the only two numbers a project this size needs. Mine says the
refund flow completes about ninety-four percent of the time and most failures are 409s from stale data,
which is why I added the conflict banner.**

Close on deployment. **Same origin with `/api` proxied, which removes CORS, SameSite=None and preflight
in one decision. And the check that catches nearly everyone: hard-refreshing a deep route. The dev
server handles it silently and nginx doesn't, so you find out when someone shares a link.**
