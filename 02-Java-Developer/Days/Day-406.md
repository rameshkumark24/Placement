# Day 406

**L-406** · CQRS, read models and projection lag

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ CQRS is four separate decisions people collapse into one word, and the cost rises sharply at
> each step. Almost everyone who "does CQRS" needs only the first two.**
>
> Today: the four levels priced individually, **the projection lag that breaks read-your-writes and the
> four ways to handle it**, rebuilding a read model as the superpower, and **why projections must be
> idempotent by construction.**

---

# Part 1 — ⭐⭐ The four levels of CQRS

| Level | ⭐ What it is | ⭐ Cost | ⭐ Buys |
|---|---|---|---|
| ⭐⭐ **1. Separate models in code** | ⭐⭐ command objects and query DTOs; **no shared "entity" doing both** | ⭐⭐ **almost zero** | ⭐⭐ clarity — reads stop distorting your domain model |
| ⭐⭐ **2. Separate queries, same database** | ⭐ hand-written SQL/views for reads, ORM for writes | ⭐ low | ⭐⭐ **performance, without the ORM fighting you** |
| ⭐ **3. Separate read store** | ⭐ projections into Elasticsearch, Redis, a denormalised table | ⭐⭐ **eventual consistency arrives here** | ⭐ query shapes the write store cannot serve |
| ⭐ **4. Separate service** | ⭐ a read service with its own deployment | ⭐⭐ high | ⭐ independent scaling and ownership |

```
⭐⭐ THE RULE: ⭐⭐ take the LOWEST level that solves your actual problem.
⭐   ⇒ ⭐ Level 1 is just good design and you should do it everywhere.
⭐   ⇒ ⭐ Level 2 solves most read performance problems.
⭐   ⇒ ⭐⭐ Level 3 is where you START PAYING — eventual consistency becomes a UX problem,
⭐     you own a projection pipeline, and "the read model is stale" becomes a support ticket type.
⭐   ⇒ ⭐ Level 4 is an organisational decision, not a technical one (Day 399).
```

> **⭐ CQRS does not require event sourcing.** Level 2 against a plain relational database is CQRS and it
> is the version most teams should stop at. **Event sourcing, however, more or less requires CQRS** —
> because you cannot query an event store (Day 405).

# Part 2 — ⭐⭐ Projections, and the lag

```
⭐ WRITE:  command → aggregate → ⭐ events appended
⭐ ⇒ ⭐ projector consumes events → ⭐ updates the read model
⭐ ⇒ ⭐ READ: query the read model
⭐
⭐ ⭐⭐ THE GAP BETWEEN APPEND AND PROJECT IS THE LAG. ⭐ It is usually milliseconds.
⭐ ⭐⭐ It is NEVER zero, and your users find the one time it is 4 seconds.
```

```
⭐⭐ THE BUG, WHICH IS ALWAYS THE SAME BUG:
⭐   user submits the form → 200 OK → ⭐ UI redirects to the list
⭐   → ⭐⭐ the list reads the projection → ⭐⭐ THE ITEM ISN'T THERE
⭐   → ⭐⭐ the user submits again.
⭐ ⇒ ⭐ This is Day 387's replica lag and Day 328's read-your-writes, for the third time.
⭐   ⭐⭐ The pattern recurring is the point: ANY asynchronous read path breaks read-your-writes.
```

| ⭐⭐ The four fixes, in order of preference | |
|---|---|
| ⭐⭐ **1. Return the result from the command** | ⭐⭐ **the write side knows the new state — send it back and render it.** Cheapest, best |
| ⭐⭐ **2. Read-your-writes token** | ⭐ command returns a version; the query **waits for the projection to reach it** (bounded) |
| ⭐ **3. Route this user's reads to the write model** | ⭐ briefly, per session — the sticky-read window (Day 387) |
| ⭐ **4. Optimistic UI** | ⭐⭐ render what the user just did **without re-reading** — free, and honest if reconciled |

⚠️ **Never solve it by "wait 500 ms and refresh".** It is a race with a comfortable-looking constant,
**it fails under exactly the load where it matters**, and it is untestable. **Fix 1 is available far more
often than people realise** — the command handler already knows what it created.

# Part 3 — ⭐⭐ Projections must be idempotent and rebuildable

```java
// ⭐⭐ Wrong: not idempotent. A redelivery double-counts, permanently and invisibly.
void on(OrderPlaced e) { jdbc.update("UPDATE stats SET total = total + ?", e.amount()); }

// ⭐⭐ Right: the last-processed position is written IN THE SAME TRANSACTION as the update.
@Transactional
void on(OrderPlaced e, long position) {
    if (position <= checkpoints.get(PROJECTION)) return;      // ⭐⭐ already applied — skip
    jdbc.update("UPDATE stats SET total = total + ?", e.amount());
    checkpoints.set(PROJECTION, position);                    // ⭐⭐ atomic with the effect
}
```

| ⭐ Rule | |
|---|---|
| ⭐⭐ **Checkpoint + effect in ONE transaction** | ⭐⭐ this is the inbox pattern again (Day 335, 407) |
| ⭐ Prefer **absolute** writes to relative ones | ⭐ `SET total = ?` is naturally idempotent; `total + ?` is not |
| ⭐⭐ **Assume every event will be delivered twice** | ⭐⭐ because at some point it will be |
| ⭐ Projections must not call other services | ⭐⭐ a projection that does I/O is slow, flaky and hard to rebuild |

## ⭐⭐ Rebuilding — the actual superpower

```
⭐⭐ A BUG IN A READ MODEL IS NOT A DATA MIGRATION. It is a REPLAY.
⭐   1. fix the projector code
⭐   2. ⭐ build "orders_v2" ALONGSIDE the live one, from position 0
⭐   3. ⭐ let it catch up (⭐⭐ watch the lag close)
⭐   4. ⭐⭐ switch reads atomically ⇒ ⭐ delete v1 when confident
⭐ ⇒ ⭐⭐ No downtime, no ALTER TABLE on 400 million rows, ⭐⭐ and a rollback is switching back.
```

> **⭐⭐ This is the single strongest practical argument for the whole event-driven approach**, and it is
> Day 371's blue/green applied to data. **Adding a completely new read shape — a search index, a report,
> a per-tenant rollup — is "run a new projector from the beginning", not a migration project.**

| ⭐ What makes rebuild possible | |
|---|---|
| ⭐⭐ The event log is retained | ⭐ Kafka compaction or an event store (Day 403) |
| ⭐ Projections are pure functions of events | ⭐⭐ no external calls, no wall-clock reads |
| ⭐ Read models are **versioned artefacts**, not schemas you migrate | ⭐ `orders_v2`, not `ALTER TABLE orders` |

⚠️ **Rebuild time is a capacity you must know.** "We can always replay" is worthless if replaying four
years of events takes eleven days. **Measure it, and if it is too slow, snapshot the projection or
parallelise by key** — **the plan that has never been run is not a plan** (Day 283, again).

# Part 4 — ⭐ Where the read model lives

| Store | ⭐ Good for |
|---|---|
| ⭐ **A denormalised table in the same DB** | ⭐⭐ **start here** — transactional checkpoint, no new infrastructure |
| ⭐ **Elasticsearch/OpenSearch** | ⭐ full-text, faceting, ad-hoc filtering (Day 338) |
| ⭐ **Redis** | ⭐ counters, leaderboards, session-shaped reads |
| ⭐ A column store | analytics, aggregates over history |
| Materialised view | ⭐ the database's own projection — cheap, and refresh is your lag |

**⭐ Note the first row's quiet advantage: a read model in the same database can update its checkpoint in
the same transaction as the projection**, which makes exactly-once projection trivial. **Move it to
another store and you inherit the dual-write problem** — which is Day 407.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Jumping to level 3 or 4 immediately** | ⭐⭐ eventual consistency and a pipeline you did not need |
| ⭐ Thinking CQRS requires event sourcing | ⭐ level 2 on plain SQL is CQRS |
| ⭐⭐ **Ignoring read-your-writes** | ⭐⭐ users submit twice; support tickets you cannot reproduce |
| ⭐ "Wait 500 ms and refresh" | ⭐⭐ a race with a comfortable constant |
| ⭐ Not returning the result from the command | ⭐⭐ the cheapest fix, unused |
| ⭐⭐ **Non-idempotent projections** | ⭐⭐ redelivery double-counts, silently and permanently |
| ⭐ Checkpoint committed separately from the effect | ⭐⭐ dual write — the exact bug Day 407 fixes |
| ⭐ Relative updates where absolute would do | ⭐ needless non-idempotency |
| ⭐ Projections that call other services | ⭐⭐ slow, flaky, and unrebuildable |
| ⭐⭐ **Migrating a read model instead of rebuilding it** | ⭐⭐ you gave up the main benefit |
| ⭐ Never measuring rebuild time | ⭐⭐ "we can replay" is untrue at eleven days |
| One read model trying to serve every query | it becomes the write model with extra lag |

## Interview questions

**Q: What is CQRS, and how much of it do you need?**
It is separating the model you write through from the models you read through, and it comes in four
levels with sharply rising cost. Level one is separate command and query types in code, which is close to
free and just good design. Level two is separate read queries against the same database — hand-written
SQL where the ORM gets in the way — which solves most read performance problems. Level three is a
separate read store, and that is where you start paying, because eventual consistency arrives and you own
a projection pipeline. Level four is a separate service, which is an organisational decision. Most teams
who say they need CQRS need level two.

**Q: A user creates something, is redirected, and it is not there. What is happening and how do you fix
it?**
Projection lag — the write completed but the read model has not caught up. It is the same bug as
read-your-writes against a database replica, and it appears in every asynchronous read path. The best fix
is usually the cheapest: return the created state from the command and render that, because the write
side already knows it. Failing that, have the command return a version token and let the query wait
briefly until the projection reaches it, or route that session's reads to the write model for a few
seconds, or use an optimistic UI that renders what the user just did. What I would not do is sleep and
refresh, which is a race with a comfortable-looking constant that fails under exactly the load where it
matters.

**Q: How do you make a projection safe?**
Assume every event will be delivered twice, because at some point it will be. The projector writes its
last-processed position in the same transaction as the effect and skips anything at or below that
position, which is the inbox pattern. Where possible I prefer absolute writes over relative ones, since
setting a value is naturally idempotent while incrementing is not. And a projection must be a pure
function of the events — no calls to other services, no reading the wall clock — otherwise it is slow,
flaky, and cannot be rebuilt deterministically.

**Q: What is the biggest practical benefit of read models?**
A bug in a read model is a replay rather than a migration. You fix the projector, build a v2 projection
alongside the live one from the beginning, watch the lag close, switch reads atomically, and delete v1 —
no downtime, no ALTER TABLE on hundreds of millions of rows, and rolling back is switching back. Adding an
entirely new read shape, like a search index or a per-tenant rollup, is running a new projector rather
than a migration project. The caveat is that you have to measure rebuild time, because "we can always
replay" means nothing if replaying four years takes eleven days.

**Q: Where should a read model live?**
Start with a denormalised table in the same database, because then the projection's checkpoint can be
committed in the same transaction as the data, which makes exactly-once projection trivial. Move to
Elasticsearch when the query genuinely needs full-text or faceting, or Redis for counters and
leaderboards. But note what you give up in that move: once the read store is a different system from the
checkpoint store, you have a dual-write problem, which is the next day's subject.

## Mini task

1. ⭐ Refactor one endpoint to **level 1** — separate command and query types, no shared entity.
2. ⭐ Replace one ORM-heavy read with **hand-written SQL** (level 2) and measure the difference.
3. ⭐⭐ Build a **projection into a separate read table** and instrument the lag as a metric.
4. ⭐⭐ **Reproduce the read-your-writes bug** with a real UI flow. Then fix it by **returning the result
   from the command** and confirm it is gone.
5. ⭐ Implement the **version-token wait** as well, with a bounded timeout, and decide which you prefer.
6. ⭐⭐ Write a **non-idempotent projection**, redeliver an event, and **watch the total go wrong.** Then
   fix it with a transactional checkpoint.
7. ⭐ Convert a relative update into an **absolute** one and note that idempotency became free.
8. ⭐⭐ **Rebuild a projection from scratch as v2**, run both, switch reads, delete v1 — with **zero
   downtime.**
9. ⭐⭐ **Measure your full rebuild time.** If it is unacceptable, parallelise by key or snapshot, and
   measure again.
10. ⭐ Add a **completely new read shape** (a search index or a rollup) purely by running a new projector.

## 🎙️ Articulation drill

**Two minutes:** *"Would you use CQRS here?"*

**⭐ Break the word into levels, because that alone is the senior answer: separate command and query
types in code is free and I do it everywhere; separate read queries against the same database solves most
performance problems; a separate read store is where the cost starts, because eventual consistency
becomes a user experience problem and I now own a pipeline.**

**⭐ So the answer is usually "the first two, yes, immediately — the third only when a query shape the
write store genuinely cannot serve appears".**

**⭐ Then name the benefit that justifies level three when you get there: a bug in a read model becomes a
replay rather than a migration. Fix the projector, build v2 alongside, switch reads atomically, delete
v1 — no downtime and rollback is switching back. Provided the projection is idempotent, checkpoints in
the same transaction as its effect, and I have actually measured how long a full rebuild takes.**
