# Part 1 — L-047 · `LinkedList`

## What it is

**A doubly-linked list.** Each element is a separate heap object holding the value and two pointers.

```java
private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;
}

transient Node<E> first;
transient Node<E> last;
transient int size;
```

```
   null ← [prev|A|next] ⇄ [prev|B|next] ⇄ [prev|C|next] → null
             ↑                                  ↑
           first                               last
```

**It implements both `List` and `Deque`** — so it's usable as a list, a queue, a stack or a deque.

## The textbook comparison, and why it's misleading

| Operation | `ArrayList` | `LinkedList` |
|---|---|---|
| `get(i)` | **O(1)** | **O(n)** |
| `add` at end | O(1) amortised | O(1) |
| `add`/`remove` at front | O(n) | **O(1)** |
| `add(i, e)` at an arbitrary index | O(n) shift | **O(n) to find** + O(1) to link |
| `remove(Object)` | O(n) | O(n) |
| Memory per element | ~4–8 bytes | **~40 bytes** |

**The textbook conclusion — "use `LinkedList` for frequent insertions" — is wrong in practice**, and
being able to explain why is a good interview answer.

### Reason 1: O(1) insertion requires an O(n) traversal

```java
list.add(5000, "x");        // "O(1) insertion"
```

To insert at index 5000, `LinkedList` must **walk 5000 nodes** to find the position. The linking is
O(1); getting there is O(n).

**The O(1) only applies when you already hold the node** — which means iterating with an `Iterator`
and using `it.add()`. Almost nobody does.

### Reason 2: memory layout

```
   ArrayList:   [A][B][C][D][E][F][G][H]     ← contiguous, one cache line holds ~16 refs
   LinkedList:  [A]→ ... [F]→ ... [C]→ ...   ← scattered, each hop is likely a cache miss
```

**Day 001's measurement applies directly.** L1 cache is ~1 ns; RAM is ~100 ns. Traversing a
`LinkedList` is a chain of dependent loads — the CPU cannot prefetch, because it doesn't know the
next address until the current node arrives.

**`ArrayList`'s O(n) shift is a single bulk `System.arraycopy`** (Day 046) — SIMD-optimised, cache
friendly. `LinkedList`'s O(n) traversal is n dependent cache misses.

**So `ArrayList`'s O(n) is often faster than `LinkedList`'s O(n)** by a large constant factor.

### Reason 3: memory overhead

Per element, `LinkedList` allocates a `Node` object: 16-byte header + 3 references ≈ **40 bytes**,
versus 4–8 bytes for a slot in `ArrayList`'s array.

**Five to ten times the memory**, plus GC pressure from n separate objects (Day 026).

## When `LinkedList` actually wins

**Almost never — and `ArrayDeque` usually beats it even then.**

| Scenario | Better choice |
|---|---|
| Queue / deque — add and remove at both ends | **`ArrayDeque`** — array-backed circular buffer, faster and smaller |
| Stack | **`ArrayDeque`** |
| Frequent insertion at a *known* iterator position | `LinkedList` — genuinely, but this is rare |
| Very large elements where copying is expensive | Marginal — you're copying *references*, not objects |

**The honest answer: use `ArrayList` for lists and `ArrayDeque` for queues and stacks. `LinkedList` is
rarely the right choice.** Josh Bloch, who wrote it, has said publicly that he doesn't think anyone
uses it and he wrote it.

**Where you'll still meet it:** as a `Queue` in older code, and in `LinkedHashMap`'s internals
(Day 049), where the linking serves a different purpose.

## The one real advantage

```java
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (shouldRemove(it.next())) it.remove();       // O(1) for LinkedList, O(n) for ArrayList
}
```

**Removing through an iterator is O(1) on `LinkedList`** because you already hold the node. On
`ArrayList` each removal shifts the tail.

**But `removeIf` on an `ArrayList` is smarter** — it does a single pass, marking survivors, then one
compaction. So even here `ArrayList` typically wins.

## Type this yourself

```java
import java.util.*;

public class LinkedListDemo {
    public static void main(String[] args) {
        int n = 100_000;

        List<Integer> arrayList = new ArrayList<>();
        List<Integer> linkedList = new LinkedList<>();
        for (int i = 0; i < n; i++) { arrayList.add(i); linkedList.add(i); }

        // ---- 1. Random access ----
        Random rnd = new Random(42);
        int[] indices = new int[50_000];
        for (int i = 0; i < indices.length; i++) indices[i] = rnd.nextInt(n);

        long start = System.currentTimeMillis();
        long sum = 0;
        for (int i : indices) sum += arrayList.get(i);
        long alGet = System.currentTimeMillis() - start;

        start = System.currentTimeMillis();
        for (int i : indices) sum += linkedList.get(i);
        long llGet = System.currentTimeMillis() - start;

        System.out.println("--- random get() ---");
        System.out.printf("   ArrayList:  %,6d ms%n", alGet);
        System.out.printf("   LinkedList: %,6d ms   ← O(n) traversal each time%n", llGet);

        // ---- 2. Insertion at the FRONT — LinkedList's supposed win ----
        int m = 100_000;
        List<Integer> al = new ArrayList<>(), ll = new LinkedList<>();

        start = System.currentTimeMillis();
        for (int i = 0; i < m; i++) al.add(0, i);
        long alFront = System.currentTimeMillis() - start;

        start = System.currentTimeMillis();
        for (int i = 0; i < m; i++) ll.add(0, i);
        long llFront = System.currentTimeMillis() - start;

        Deque<Integer> dq = new ArrayDeque<>();
        start = System.currentTimeMillis();
        for (int i = 0; i < m; i++) dq.addFirst(i);
        long dqFront = System.currentTimeMillis() - start;

        System.out.printf("%n--- %,d insertions at the FRONT ---%n", m);
        System.out.printf("   ArrayList:   %,6d ms%n", alFront);
        System.out.printf("   LinkedList:  %,6d ms   ← wins here%n", llFront);
        System.out.printf("   ArrayDeque:  %,6d ms   ← wins MORE%n", dqFront);

        // ---- 3. Insertion at a MIDDLE index — the myth ----
        List<Integer> al2 = new ArrayList<>(), ll2 = new LinkedList<>();
        for (int i = 0; i < 50_000; i++) { al2.add(i); ll2.add(i); }

        start = System.currentTimeMillis();
        for (int i = 0; i < 20_000; i++) al2.add(al2.size() / 2, i);
        long alMid = System.currentTimeMillis() - start;

        start = System.currentTimeMillis();
        for (int i = 0; i < 20_000; i++) ll2.add(ll2.size() / 2, i);
        long llMid = System.currentTimeMillis() - start;

        System.out.println("\n--- 20,000 insertions at the MIDDLE index ---");
        System.out.printf("   ArrayList:  %,6d ms   ← bulk arraycopy%n", alMid);
        System.out.printf("   LinkedList: %,6d ms   ← O(n) walk EVERY time%n", llMid);
        System.out.println("   ↑ this is where the textbook advice breaks down");

        // ---- 4. Sequential iteration ----
        start = System.nanoTime();
        sum = 0; for (int v : arrayList) sum += v;
        long alIter = System.nanoTime() - start;

        start = System.nanoTime();
        sum = 0; for (int v : linkedList) sum += v;
        long llIter = System.nanoTime() - start;

        System.out.println("\n--- sequential iteration ---");
        System.out.printf("   ArrayList:  %,6d µs   ← contiguous, prefetches%n", alIter / 1000);
        System.out.printf("   LinkedList: %,6d µs   ← pointer chasing%n", llIter / 1000);
        System.out.println("   (sum=" + sum + ")");
    }
}
```

**Record all four comparisons.** The middle-insertion result is the important one — the case the
textbook says `LinkedList` should win, and it typically loses badly because the O(n) walk happens on
every single insertion while `ArrayList` does one bulk memory move.

## Interview questions

**Q: `ArrayList` or `LinkedList`?**
> `ArrayList` almost always. Indexed access is O(1) versus O(n), memory per element is five to ten
> times smaller, and the contiguous layout means iteration and even the O(n) shift are cache-friendly
> — the shift is a single `System.arraycopy`. `LinkedList`'s O(1) insertion only applies when you
> already hold the node; inserting at an index still costs an O(n) traversal, and every hop in that
> traversal is likely a cache miss.

**Q: When does `LinkedList` genuinely win?**
> Adding and removing at the ends, and removing through an iterator you already hold. But `ArrayDeque`
> beats it at both — it's an array-backed circular buffer with better locality and no per-element node
> allocation. In practice `LinkedList` is rarely the right choice.

**Q: Why is `ArrayList`'s O(n) shift often faster than `LinkedList`'s O(n) traversal?**
> They're both linear but with very different constants. The shift is one bulk memory move that the
> JIT compiles to an optimised intrinsic, operating on contiguous memory the CPU can prefetch. The
> traversal is a chain of dependent pointer loads to scattered addresses, so the CPU can't prefetch
> and most hops are cache misses at around a hundred times the latency of a cache hit.

# Part 2 — B-08 · Deadlock

## The four necessary conditions

**Deadlock requires all four simultaneously.** Break any one and it cannot occur — that's the whole
framework.

| # | Condition | Meaning |
|---|---|---|
| 1 | **Mutual exclusion** | A resource can be held by only one thread |
| 2 | **Hold and wait** | A thread holds one resource while waiting for another |
| 3 | **No preemption** | A resource can't be forcibly taken from its holder |
| 4 | **Circular wait** | A cycle exists: A waits on B, B waits on A |

```java
// Thread 1                        // Thread 2
synchronized (lockA) {             synchronized (lockB) {
    synchronized (lockB) { }           synchronized (lockA) { }
}                                  }
```

**Both threads hold one lock and wait for the other. Neither can proceed. Forever.**

## The four strategies

### 1. Prevention — break a condition

| Break | How | Practical? |
|---|---|---|
| Mutual exclusion | Use lock-free structures, immutable data | ✅ Where applicable |
| Hold and wait | Acquire all locks at once, or none | ⚠️ Hard, and reduces concurrency |
| No preemption | Use `tryLock` with a timeout and back off | ✅ **Practical** |
| **Circular wait** | **Impose a global lock ordering** | ✅ **The standard answer** |

**Lock ordering is the technique you should name:**

```java
// 💀 order depends on the arguments
void transfer(Account from, Account to, BigDecimal amount) {
    synchronized (from) { synchronized (to) { ... } }
}
// transfer(A,B) and transfer(B,A) concurrently → deadlock

// ✅ always acquire in a consistent global order
void transfer(Account from, Account to, BigDecimal amount) {
    Account first  = from.id() < to.id() ? from : to;
    Account second = from.id() < to.id() ? to : from;
    synchronized (first) { synchronized (second) { ... } }
}
```

**Order by any stable total ordering** — an ID, `System.identityHashCode`, anything consistent. With a
global order, a cycle is impossible: a cycle requires some thread to acquire a lower-ordered lock
while holding a higher one.

**This is the classic bank-transfer deadlock**, and it's a common interview question and LLD problem
(Day 315, Splitwise).

### 2. Avoidance — the banker's algorithm

The system knows each thread's *maximum* future resource needs, and grants a request only if the
resulting state is **safe** — meaning some ordering exists in which all threads can complete.

**Theoretically elegant, practically unused.** It requires knowing maximum needs in advance, which
general-purpose software never does. Know it exists and why it's impractical.

### 3. Detection and recovery

Build a **wait-for graph** and look for cycles. On detection, abort a thread or roll back a
transaction.

**This is what databases do.** Postgres detects deadlocks between transactions and kills one with
`deadlock detected` — Day 196. It's practical there because a transaction can be rolled back;
killing a thread mid-way generally can't be made safe.

### 4. The ostrich algorithm

**Ignore it.** If deadlock is rare and the cost of prevention is high, accept the risk and restart
when it happens. Most operating systems do this for user processes.

## Detecting it in Java

```bash
jstack <pid>          # ← the JVM DETECTS and REPORTS deadlocks automatically
```

```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "Thread-0"
"Thread-0":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "Thread-1"
```

**`jstack` explicitly names deadlocks** — you don't have to work it out from the stack traces. Also
available via `jcmd <pid> Thread.print`, JConsole, and `ThreadMXBean.findDeadlockedThreads()`
programmatically.

## Related failures — know the distinction

| | Meaning |
|---|---|
| **Deadlock** | Threads blocked forever waiting on each other |
| **Livelock** | Threads keep *responding* to each other and make no progress — two people stepping aside in a corridor |
| **Starvation** | A thread never gets a resource because others keep taking it |

**Livelock is the subtle one:** the threads aren't blocked, they're busy — CPU usage looks normal —
but no work completes. A retry loop where both parties back off and retry in lockstep produces it,
which is why **jitter matters** (Day 005, and your API-safety rules).

## Type this yourself

```java
import java.util.concurrent.locks.*;
import java.util.concurrent.*;

public class DeadlockDemo {
    static final Object lockA = new Object();
    static final Object lockB = new Object();

    public static void main(String[] args) throws Exception {
        System.out.println("Starting a deadlock. Run in another terminal:");
        System.out.println("   jps            (find the pid)");
        System.out.println("   jstack <pid>   (look for 'Found one Java-level deadlock')\n");

        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                System.out.println("T1 holds A, wants B");
                sleep(100);
                synchronized (lockB) { System.out.println("T1 got both"); }
            }
        }, "Thread-1");

        Thread t2 = new Thread(() -> {
            synchronized (lockB) {
                System.out.println("T2 holds B, wants A");
                sleep(100);
                synchronized (lockA) { System.out.println("T2 got both"); }
            }
        }, "Thread-2");

        t1.start(); t2.start();
        Thread.sleep(2000);
        System.out.println("\nStill deadlocked. Now the FIXED version:\n");

        // ---- fix 1: global lock ordering ----
        Runnable ordered1 = () -> transferOrdered(1, 2);
        Runnable ordered2 = () -> transferOrdered(2, 1);
        Thread t3 = new Thread(ordered1), t4 = new Thread(ordered2);
        t3.start(); t4.start(); t3.join(); t4.join();
        System.out.println("Ordered locking completed — no deadlock possible");

        // ---- fix 2: tryLock with timeout (breaks 'no preemption') ----
        ReentrantLock l1 = new ReentrantLock(), l2 = new ReentrantLock();
        Runnable tryBoth = () -> {
            for (int attempt = 0; attempt < 5; attempt++) {
                try {
                    if (l1.tryLock(50, TimeUnit.MILLISECONDS)) {
                        try {
                            if (l2.tryLock(50, TimeUnit.MILLISECONDS)) {
                                try { System.out.println("   " + Thread.currentThread().getName()
                                        + " acquired both"); return; }
                                finally { l2.unlock(); }
                            }
                        } finally { l1.unlock(); }
                    }
                    Thread.sleep((long) (Math.random() * 50));      // JITTER — avoids livelock
                } catch (InterruptedException ignored) {}
            }
        };
        Thread t5 = new Thread(tryBoth, "A"), t6 = new Thread(tryBoth, "B");
        t5.start(); t6.start(); t5.join(); t6.join();

        System.exit(0);        // t1/t2 are still deadlocked
    }

    static final Object[] LOCKS = { new Object(), new Object(), new Object() };

    static void transferOrdered(int from, int to) {
        Object first  = LOCKS[Math.min(from, to)];
        Object second = LOCKS[Math.max(from, to)];
        synchronized (first) { sleep(50); synchronized (second) { /* transfer */ } }
    }

    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException ignored) {} }
}
```

**Run it, then run `jstack` on the PID while it's hung.** Reading a real deadlock report — with the
JVM naming both threads and both monitors — is worth far more than reading about one.

## Interview questions

**Q: What are the four conditions for deadlock?**
> Mutual exclusion, hold and wait, no preemption, and circular wait. All four must hold
> simultaneously, so preventing any one prevents deadlock entirely.

**Q: How would you prevent deadlock in practice?**
> Impose a global ordering on lock acquisition, so every thread acquires locks in the same sequence —
> that makes circular wait impossible. The classic case is a bank transfer where two threads transfer
> in opposite directions; ordering the locks by account ID fixes it. The other practical technique is
> `tryLock` with a timeout and randomised backoff, which breaks the no-preemption condition.

**Q: How do you diagnose a deadlock in a running Java service?**
> `jstack` on the process — the JVM detects Java-level deadlocks and reports them explicitly, naming
> the threads and the monitors involved. `jcmd Thread.print` and `ThreadMXBean.findDeadlockedThreads`
> do the same.

**Q: What's the difference between deadlock and livelock?**
> In deadlock the threads are blocked and consume no CPU. In livelock they're actively running and
> responding to each other but making no progress — like two people repeatedly stepping aside in a
> corridor. Livelock is harder to spot because CPU usage looks normal. Randomised backoff is the usual
> fix, which is why retry jitter matters.
