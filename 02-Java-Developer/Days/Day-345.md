# Day 345

**L-345** · Design 1 — the URL shortener

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ The canonical first system design, and it is asked because it looks trivial and is not.**
>
> Three things are genuinely hard: **generating short unique keys without a coordination bottleneck,
> serving a redirect at 300,000 requests a second, and deciding a redirect status code that will
> either keep or destroy your analytics forever.**

---

# Part 1 — ⭐ Requirements and estimates

| ⭐ Functional | ⭐ Out of scope |
|---|---|
| Shorten a URL → short code | user accounts beyond an API key |
| ⭐ **Redirect a code → original URL** | link previews, QR codes |
| Custom aliases | ⭐ malware scanning (mention, exclude) |
| ⭐ Expiry | full analytics UI |
| Basic click counts | |

| ⭐ Non-functional | ⭐ Value |
|---|---|
| ⭐⭐ **Read:write** | ⭐⭐ **100:1 — this decides everything** |
| ⭐ **Redirect latency** | ⭐ **< 50 ms p99 — it is on the user's critical path** |
| ⭐ **Availability** | ⭐⭐ **redirects: 99.99%. Creation: 99.9% is fine** |
| Consistency | ⭐ a new link readable immediately; **click counts may lag minutes** |
| Durability | ⭐ **a lost mapping is a dead link forever — no loss** |

```
⭐ ESTIMATE (Day 323)
⭐   100M new URLs/day  ⇒ 1,200 writes/s  ⇒ ⭐ peak ~3,000/s
⭐   100:1              ⇒ 120,000 reads/s ⇒ ⭐ peak ~300,000/s
⭐   500 B/record × 100M = 50 GB/day ⇒ ⭐ 90 TB over 5 years ⇒ ⭐ ~500 TB provisioned
⭐   Cache: 20% of a day's hot links ≈ ⭐ 10 GB — fits one Redis node
⭐   Keyspace: 180B URLs over 5 yr ⇒ base62^7 = 3.5T ⇒ ⭐⭐ 7 CHARACTERS
```

> **⭐ Say what each decided:** 3,000 writes/s is one primary, so no write sharding · 300,000 reads/s
> means a cache is mandatory, not an optimisation · 90 TB means the storage is sharded even though
> the writes are not · **and the keyspace arithmetic answered "how long is the code" directly.**

# Part 2 — ⭐ API, and the status code that matters

```
⭐ POST /urls          { url, customAlias?, expiresAt? }  → { shortUrl, code }
⭐ GET  /{code}        → ⭐ 302 redirect
⭐ GET  /urls/{code}/stats                                → { clicks, createdAt }
⭐ DELETE /urls/{code}
```

| ⭐ 301 permanent | ⭐ 302 found |
|---|---|
| ⭐⭐ **Cached by browsers and proxies, sometimes forever** | ⭐ not cached by default |
| ⭐ Fewer requests reach you — cheaper | ⭐ every click reaches you |
| ⭐⭐ **You lose click analytics entirely** | ⭐⭐ **analytics work** |
| ⭐⭐ **You can never change or expire the target** | ⭐ expiry and updates work |
| SEO passes link equity | |

> **⭐ Choose 302 and say why: the analytics are the product, and a 301 is effectively irreversible
> because you cannot un-cache a browser.** A user's browser will redirect to the old target for
> months regardless of what your database says. **Naming that irreversibility is the point of the
> question.**

⚠️ **If you do want CDN caching for scale, use `302` with a short `Cache-Control: max-age=60`** —
you keep the ability to expire links while still absorbing repeated clicks. **Never `301` unless
links are genuinely immutable and analytics do not matter.**

# Part 3 — ⭐⭐ The deep dive: key generation

**⭐ Four approaches. This is the deep dive for this problem, so go to mechanism level.**

| Approach | ⭐ How | ⭐ Verdict |
|---|---|---|
| ⭐ **Random + collision check** | generate 7 random base62 chars, `INSERT` if absent | ⭐ **simple; a read before every write, and collisions rise as it fills** |
| ⭐ **Counter + base62** | a global counter, encoded | ⭐⭐ **no collisions ever — but the counter is a bottleneck and the codes are guessable** |
| ⭐ **Hash + truncate** | `base62(md5(url))[0:7]` | ⭐ same URL → same code (nice), **but truncation collides and needs a fallback** |
| ⭐⭐ **Pre-generated key pool** | ⭐⭐ **a service generates unused keys in advance; app servers take batches** | ⭐⭐ **no collision check, no per-write coordination — the strong answer** |

## ⭐⭐ Solving the counter bottleneck

```
⭐ NAIVE: one global counter ⇒ ⭐ every write goes through it. SPOF and a serialisation point.

⭐⭐ RANGE ALLOCATION — the standard fix:
⭐   Each app server takes a BLOCK: server A gets 1–100,000, server B gets 100,001–200,000
⭐   ⇒ ⭐ one coordination call per 100,000 writes, not per write
⭐   ⇒ ⭐ a server crash wastes at most one block. Wasting keys is FINE — there are 3.5 trillion.

⭐ ALTERNATIVE — SNOWFLAKE-STYLE:
⭐   [timestamp | machine id | sequence] ⇒ ⭐ no coordination at all
⭐   ⇒ ⭐ but codes are longer and time-ordered, hence enumerable
```

⚠️ **Sequential codes are enumerable.** `aaaaab` follows `aaaaaa`, so anyone can crawl every link
you have ever created — **a genuine privacy problem for "unlisted" links.** Fixes: **encrypt or
permute the counter before encoding** (a Feistel network or simply a fixed bijective transform), or
**use the pre-generated pool with random keys.** *Naming enumeration unprompted is a strong move.*

**⭐ Custom aliases are the recurring mechanism again:**

```sql
INSERT INTO urls (code, url) VALUES (:alias, :url) ON CONFLICT DO NOTHING;
-- ⭐ rowsAffected = 0 means it was taken. Day 316's conditional update, one more time.
```

⚠️ **Custom aliases must not collide with generated ones** — keep them in a separate namespace, or
reserve them in the same table before generation can pick them.

# Part 4 — ⭐ The read path, storage, and what breaks

## ⭐ The redirect path — make it as short as possible

```
⭐ GET /{code}
⭐   1. Redis GET code            ⭐ ~95% hit  → 302 immediately
⭐   2. miss → datastore lookup   → populate cache → 302
⭐   3. ⭐⭐ FIRE the click event ASYNCHRONOUSLY — never before the redirect
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐⭐ **Nothing synchronous but the lookup** | ⭐⭐ **counting a click inline adds a write to every read** |
| ⭐ Cache is not load-bearing — but nearly | ⭐ at 0% hit rate the store sees 300k/s. **Say this** (Day 326) |
| ⭐ **Expiry checked at read time** | ⭐ Day 316's lazy predicate — no sweeper needed for correctness |
| ⭐ Not-found is cached too | ⭐ negative caching stops enumeration attacks hitting the store |

## ⭐ Storage

| ⭐ Choice | ⭐ Reason |
|---|---|
| ⭐⭐ **Key-value store, partitioned by code** | ⭐⭐ **the only access pattern is get-by-code — this is the definition of a KV workload** (Day 332) |
| ⭐ Shard key = the code | ⭐ high cardinality, uniform (it is effectively random), present in every query (Day 329) |
| ⭐ Relational is also fine | at this size, PostgreSQL with a primary key on `code` and read replicas is defensible |
| ⭐ Clicks in a separate store | ⭐ **time-series or aggregated counters — never in the redirect path** |

## ⭐ Analytics, asynchronously

```
⭐ redirect → emit {code, ts, ip, referrer, ua} → queue → workers → aggregate
⭐ ⭐ Counts are approximate and lag by seconds. ⭐ THAT WAS IN THE REQUIREMENTS.
⭐ ⭐ For raw counts at this volume, Redis INCR then flush periodically, or HyperLogLog for uniques.
```

## ⭐ Bottlenecks and the closing five minutes

| ⭐ Breaks first | ⭐ Mitigation |
|---|---|
| ⭐⭐ **A viral link — one hot key** | ⭐⭐ **local in-process cache in front of Redis** (Day 326) — the classic answer |
| ⭐ The key counter | range allocation, as above |
| ⭐ Cache node loss | ⭐ consistent hashing, so only 1/N of keys are lost (Day 326) |
| ⭐ **Enumeration / scraping** | ⭐ non-sequential codes, rate limiting per IP, negative caching |
| Abuse — phishing links | async scanning, blocklists, a takedown path |
| Storage growth | expiry, cold tiering, sharding by code |

```
⭐ MONITOR: redirect p99 · cache hit rate · 404 rate · ⭐ links created per minute (business metric)
⭐ CUT:     malware scanning, a UI, per-user quotas, geo analytics
⭐ AT 10×:  ⭐ CDN in front of redirects with a 60s TTL; regional read replicas of the KV store
```

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Choosing 301 | ⭐⭐ **analytics gone, and the target can never change** |
| ⭐ Counting clicks synchronously | a write on every read |
| ⭐ A single global counter | ⭐ a serialisation point and a SPOF |
| ⭐ **Sequential codes with no permutation** | ⭐ every link is enumerable |
| ⭐ Collision check on every write | a read before every write, worsening as it fills |
| Custom aliases sharing the generated namespace | future collisions |
| ⭐ No negative caching | enumeration attacks hit the datastore |
| ⭐ **No hot-key plan** | ⭐ one viral link saturates a cache node |
| A sweeper for expiry | Day 316 — check at read time |
| ⭐ Deriving the code length by guessing | ⭐ **it is `log₆₂(lifetime volume)` — compute it** |

## Interview questions

**Q: 301 or 302?**
302. A 301 is cached by browsers and proxies, sometimes indefinitely, which destroys click analytics
and — more seriously — means you can never change or expire the target, because a user's browser will
keep redirecting to the old one regardless of your database. That is effectively irreversible. If I
need caching for scale I use 302 with a short max-age, which absorbs repeated clicks while keeping
control.

**Q: How do you generate the short codes?**
I would use a pre-generated key pool: a service produces unused random base62 keys in advance and app
servers take batches, so there is no collision check and no coordination per write. The alternative
is a counter with range allocation — each server takes a block of a hundred thousand, so coordination
happens once per block, and wasted keys on a crash do not matter against three and a half trillion.
Whichever I use, the codes must not be sequentially enumerable, or every unlisted link can be
crawled.

**Q: How long is the code?**
Computed, not chosen. A hundred million a day for five years is a hundred and eighty billion URLs;
base62 to the seventh is about 3.5 trillion, which leaves comfortable headroom. Six characters would
be 56 billion, which is too tight. So seven.

**Q: How do you serve three hundred thousand redirects a second?**
The redirect path does one cache lookup and nothing else. Around ninety-five percent hit a
distributed cache holding the day's hot links, which is roughly ten gigabytes; misses go to a
key-value store partitioned by code, which is the ideal shard key because it is high cardinality,
uniform and present in every query. The click event is emitted asynchronously — counting inline would
put a write on the path of every read.

**Q: A link goes viral. What happens?**
It becomes a hot key, and consistent hashing does not help because that key hashes to one node by
definition. A small in-process cache in front of the distributed one fixes it — even a one-second TTL
removes almost all the traffic for a key that hot. Beyond that I would let a CDN cache the redirect
with a short TTL, accepting that expiry becomes eventually consistent for that window.

## Mini task

**⭐ The 45-minute run is the task. Then:**

1. **Do the full run timed and recorded**, following Day 344's clock. **Play it back and check every
   component arrived with a number.**
2. ⭐ Implement **all four key-generation strategies.** Measure write throughput and collision rate at
   50% and 90% keyspace fill.
3. ⭐ Implement **range allocation.** Kill a server mid-block and confirm only that block is wasted.
4. ⭐ Generate sequential codes and **write the crawler that enumerates them.** Then permute the
   counter and confirm the crawler fails.
5. Implement the redirect with cache-then-store and **measure p99 at 95% and 0% hit rate.** Decide
   whether your cache is load-bearing.
6. ⭐ Count clicks **synchronously**, measure redirect latency, then move it to a queue and measure
   again. **Record both numbers.**
7. ⭐ Make one key 40% of traffic and **saturate a cache node.** Add an in-process cache with a
   one-second TTL and re-measure.
8. Implement custom aliases with a conditional insert and **prove that two concurrent claims produce
   one winner.**
9. Implement **lazy expiry** and confirm an expired link 404s with no sweeper running.
10. ⭐ Add negative caching and **measure datastore load under an enumeration attack** with and
    without it.
