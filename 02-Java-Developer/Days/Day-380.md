# Day 380

**L-380** · The cloud model — regions, AZs, shared responsibility, and the two planes

**Time:** 3 hrs · **Mode:** NEW · **⭐ Stage 11 opens**

> **⭐ You are not renting servers. You are renting an API that creates servers — and the difference
> between those two sentences is the whole of cloud engineering.**
>
> Today: what an availability zone actually is, why `us-east-1` is not just another region, why the
> account rather than the VPC is your blast radius, and **the control-plane/data-plane split that
> explains almost every large AWS outage you have read about.**

# Part 1 — ⭐ What you are actually buying

| Model | ⭐ You manage | ⭐ They manage |
|---|---|---|
| On-premises | everything | nothing |
| ⭐ **IaaS** (EC2) | ⭐ OS, runtime, app, scaling | hardware, network, hypervisor |
| ⭐ **PaaS / managed** (RDS, ECS) | ⭐ schema, config, app | ⭐ engine patching, backups, failover |
| ⭐⭐ **FaaS** (Lambda) | ⭐⭐ **the function and an IAM role** | ⭐ everything else |

> **⭐ The real product is elasticity and the API, not the hardware.** A rack in a colo is cheaper per
> CPU-hour than EC2 and always will be. **What you are paying the premium for is: capacity in ninety
> seconds, capacity you can give back, and an audited API in front of every change.**

⚠️ **If your workload is flat, predictable and running 24/7 at high utilisation, the cloud is more
expensive than owning hardware — and saying so is a mark of seniority, not heresy.** The cloud wins
on *variance*, *speed of change* and *not employing a data-centre team*. Know which of those you are
actually buying.

## ⭐ Everything is an API call

```
⭐ Console  ─┐
⭐ CLI      ─┼─⭐⭐ ALL of these call the SAME public API ─→ ⭐ AWS service
⭐ SDK      ─┤
⭐ Terraform─┘
⭐ ⇒ ⭐⭐ there is NO privileged back door the console uses. ⭐ Everything is IAM-authorised,
⭐   and ⭐⭐ everything appears in CloudTrail (Day 394).
```

**⭐ This single fact is why infrastructure as code works at all** (Day 379): Terraform is not
scripting a UI, **it is calling exactly what the console calls.**

# Part 2 — ⭐⭐ Regions and availability zones

| ⭐ Unit | ⭐ What it is | ⭐ Latency between |
|---|---|---|
| ⭐⭐ **Availability Zone** | ⭐⭐ **one or more discrete data centres** — own power, cooling, network | ⭐ **~1–2 ms** within a region |
| ⭐⭐ **Region** | ⭐ **3+ AZs**, tens of km apart — far enough for independent failure, close for sync replication | ⭐⭐ **10–200 ms** between regions |
| Local Zone / Edge | latency-sensitive extensions, CloudFront PoPs | — |

> **⭐ The AZ distance is engineered to a purpose: far enough apart that one flood, fire or substation
> failure cannot take two of them, close enough that synchronous replication is viable.** That is why
> RDS Multi-AZ can be synchronous (Day 387) and cross-*region* replication cannot.

⚠️ **Regions are isolated from each other by design, and this is a feature.** A region does not
automatically fail over to another region. **Nothing is multi-region unless you built it that way, paid
for it, and tested it** — and multi-region active-active is one of the most expensive commitments in
this entire stage. Most companies correctly choose **multi-AZ, single region.**

## ⭐⭐ `us-east-1` is not an ordinary region

| ⭐ Why it is special | ⭐ Consequence |
|---|---|
| ⭐⭐ **Global service control planes live there** — IAM, Route 53, CloudFront, Organizations | ⭐⭐ a `us-east-1` outage degrades "global" things everywhere |
| ⭐ **ACM certificates for CloudFront must be issued there** | ⭐ a classic first-deploy failure (Day 392) |
| ⭐ Largest, oldest, most-used region | ⭐ new features land first; **so do novel failures** |
| ⭐ IAM changes are eventually consistent globally | ⭐ a new role may not work for a few seconds everywhere |

**⭐ Being able to say "IAM writes go to `us-east-1` and propagate, which is why a brand-new role
sometimes fails for a moment" is a small detail that lands very well in an interview.**

# Part 3 — ⭐⭐ Control plane vs data plane

```
⭐⭐ CONTROL PLANE  ⭐ the APIs that CREATE and CHANGE things
⭐    RunInstances · CreateTable · UpdateService · AttachVolume
⭐    ⇒ ⭐⭐ complex, stateful, MORE failure-prone

⭐⭐ DATA PLANE     ⭐ the path that SERVES traffic to things that already exist
⭐    an HTTP request to a running EC2 · a GET to an existing S3 object
⭐    ⇒ ⭐⭐ simpler, hardened, HIGHER availability
```

> **⭐⭐ In almost every large AWS incident, the data plane kept working and the control plane did
> not.** Existing instances served traffic; **launching new ones failed.** Existing tasks ran;
> **deployments hung.**

| ⭐ Design consequence — ⭐⭐ *static stability* | |
|---|---|
| ⭐⭐ **Do not require the control plane to recover** | ⭐⭐ if failover needs *new* capacity, it needs the plane that is broken |
| ⭐ **Pre-provision across AZs** | ⭐ run N+1 so losing an AZ needs **no scaling action at all** |
| ⭐ Autoscaling is for trends, not for disasters | ⭐ it is a control-plane operation (Day 389) |
| ⭐ **Cache what you must not lose** | ⭐ a config fetch at startup makes startup depend on another service |

⚠️ **The concrete version: if your AZ-failure plan is "the ASG launches replacements in the surviving
AZs", your plan depends on `RunInstances` succeeding during the exact event most likely to strain it.**
**Running 150% of needed capacity spread over three AZs costs money and needs no API call to survive
one AZ.** That trade — **money for static stability** — is the single most important architectural
decision in this stage.

# Part 4 — ⭐ Shared responsibility, and the line that moves

```
⭐⭐ AWS: security OF the cloud   ⭐ hardware, hypervisor, physical access, managed-service internals
⭐⭐ YOU: security IN the cloud   ⭐ IAM, network rules, patching what you own, YOUR DATA, encryption
```

| Service | ⭐ AWS patches | ⭐⭐ You still own |
|---|---|---|
| ⭐ **EC2** | hypervisor only | ⭐⭐ **the OS, the JVM, every library, the AMI** |
| ⭐ **RDS** | ⭐ the engine, the OS | ⭐⭐ **schema, users, grants, parameter groups, the data** |
| ⭐ **ECS/Fargate** | the host and agent | ⭐⭐ **your image and everything in it** (Day 363) |
| ⭐ **Lambda** | ⭐ runtime and host | ⭐⭐ **your code, its dependencies, its IAM role** |
| ⭐⭐ **S3** | ⭐ durability, availability | ⭐⭐ **who can read it** — every public-bucket story is this row |

> **⭐⭐ The line moves service by service, and IAM never moves.** However managed the service, **who is
> allowed to call it is always yours.** Which is why Stage 11 spends the next two days on IAM before
> it launches a single server.

## ⭐ The account is the blast radius

| Boundary | ⭐ Strength |
|---|---|
| Security group | ⭐ a rule, easily changed |
| VPC | ⭐ a network boundary — **but same-account IAM crosses it freely** |
| ⭐⭐ **AWS account** | ⭐⭐ **the real isolation boundary — separate IAM, separate quotas, separate bill** |
| ⭐ **Organization + SCPs** | ⭐ a ceiling no one in the account can exceed (Day 381) |

⚠️ **"Prod and dev in one account, separated by tags" is not separation.** One overly broad IAM policy
or one wrong `terraform apply` reaches both. **Separate accounts per environment is the standard
answer, and it costs nothing** — accounts are free; you pay only for resources.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ "The cloud is cheaper" as an unqualified claim | ⭐ flat 24/7 high-utilisation workloads are cheaper on hardware |
| ⭐⭐ Assuming regions fail over automatically | ⭐⭐ **nothing is multi-region unless you built and tested it** |
| ⭐ Treating `us-east-1` as an ordinary region | ⭐ global control planes and CloudFront certs live there |
| ⭐⭐ **A recovery plan that needs the control plane** | ⭐⭐ it depends on the part most likely to be degraded |
| ⭐ Relying on autoscaling to survive an AZ loss | ⭐ pre-provision instead — static stability |
| ⭐ Believing "managed" means "secure" | ⭐⭐ RDS patches the engine; **your grants and data are yours** |
| ⭐⭐ **Prod and dev in one account** | ⭐⭐ one bad policy or apply reaches both |
| ⭐ Console changes outside IaC | ⭐ silently reverted by the next apply (Day 379) |
| Ignoring service quotas until launch day | quotas are per-account, per-region, and often the real limit |

## Interview questions

**Q: What is an availability zone, and why three?**
An AZ is one or more discrete data centres with independent power, cooling and networking, deliberately
placed far enough apart that a single physical event cannot take two of them, but close enough — a
millisecond or two — that synchronous replication between them is viable. Three rather than two because
quorum systems need an odd number to tolerate one loss, and because with two AZs losing one means losing
half your capacity, so you must run at 50% utilisation to survive it.

**Q: Distinguish the control plane from the data plane, and why it matters.**
The control plane is the APIs that create and modify resources; the data plane is the path that serves
traffic to resources that already exist. The control plane is more complex, more stateful and
historically less available. That matters because it dictates recovery design: if your response to
losing an availability zone is "the auto scaling group launches replacements", your recovery depends on
the control plane at the moment it is most likely to be degraded. The alternative is static stability —
pre-provision capacity across zones so that surviving a zone failure requires no API call at all.

**Q: Where does the shared responsibility line sit for RDS?**
AWS operates the host, the storage layer, engine patching, automated backups and the failover mechanism.
You own the schema, the users and grants, the parameter group, whether encryption is enabled, whether
it is publicly accessible, and the data itself. The rule of thumb: the more managed the service, the
less operating system you own, but who is allowed to call it is always yours — IAM never moves across
that line.

**Q: How do you separate production from development?**
Separate AWS accounts, joined in an Organization, with service control policies as a ceiling. Accounts
are free; you pay only for what runs in them. Tags or VPCs inside one account are not separation because
same-account IAM crosses both freely, and a single overly broad policy or a misdirected apply reaches
production. Separate accounts also give separate quotas and a per-environment bill, which turns cost
attribution into a fact rather than an estimate.

**Q: When is the cloud the wrong choice?**
When the workload is flat, predictable, high-utilisation and long-lived, and you already have the
operational capability to run hardware. You pay a premium for elasticity, and if you never flex you are
buying an option you do not exercise. The honest framing is that you are buying variance absorption,
speed of change and not employing a data-centre team — if none of those are worth much to you, the
economics do not favour the cloud.

## Mini task

1. ⭐ Create a **dedicated AWS account** for this stage. Enable MFA on the root user and then **never use
   root again.**
2. ⭐ Set a **billing alarm at a number that would genuinely annoy you** before creating anything else.
3. ⭐ Install the CLI, configure a profile, and run `aws sts get-caller-identity`. **Understand every
   field it returns.**
4. ⭐ List the AZs in your region: `aws ec2 describe-availability-zones`. Note that **AZ names are
   per-account aliases** — your `us-east-1a` is not someone else's.
5. ⭐ Run the same describe call with `--region` set to two other regions and **confirm the results are
   completely independent.**
6. ⭐⭐ Do one action in the console, then find it in **CloudTrail**. Confirm the console called the same
   public API you would have.
7. ⭐ Look up **service quotas** for EC2 vCPUs and Elastic IPs in your account. Note the numbers.
8. ⭐⭐ Write down, for your flagship, **what happens if one AZ disappears right now** — and whether the
   answer needs the control plane.
9. ⭐ Sketch the account structure you would use for a real product: management, prod, staging, dev.
10. ⭐ Estimate what your flagship would cost on-premises vs on AWS. **Be honest about which is cheaper
    and why you would still choose AWS.**

## 🎙️ Articulation drill

**Two minutes:** *"How do you make a service survive losing an availability zone?"*

**⭐ The weak answer is "multi-AZ and auto scaling".** The strong one names the trap: **an auto scaling
response to an AZ loss is a control-plane operation, executed at the moment the control plane is most
likely to be strained.**

**⭐ So: run across three AZs at a capacity where losing one requires no scaling action — static
stability — and accept that you are paying roughly 50% more compute for the privilege of not needing an
API call during an incident.** Then say the second half: **the database is the harder half, because
Multi-AZ failover is a DNS change and your JVM caches DNS** (Day 387).
