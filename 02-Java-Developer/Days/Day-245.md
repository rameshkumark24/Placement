# Day 245 🚀

**J-245** · 🚀 **Deploying a frontend** — ⭐⭐ the deploy that breaks every open tab

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: deploying a frontend does not replace the running application — every
> user with an open tab is still executing yesterday's bundle against today's API, so a frontend
> deploy is a *rollout* with two versions live, and the failure it causes is a chunk that no longer
> exists on the server.**
>
> Today: ⭐ cache headers, ⭐⭐ the stale tab, config without rebuilding, and rollback.

---

# Part 1 — Cache headers, the two rules

```
⭐⭐ THE ENTIRE STRATEGY IS TWO LINES, AND GETTING THEM BACKWARDS
⭐   IS THE CLASSIC FRONTEND OUTAGE.

⭐   /index.html          ⇒ ⭐⭐ Cache-Control: no-cache
⭐     ⭐ It is the MANIFEST that points at the hashed files.
⭐     ⭐⭐ CACHE THIS AND USERS RUN THE OLD APP FOREVER — and no
⭐       deploy will fix it.

⭐   /assets/app.9f2c1a.js ⇒ ⭐⭐ max-age=31536000, immutable
⭐     ⭐ Safe for a YEAR because ⭐⭐ THE FILENAME CHANGES WHEN THE
⭐       CONTENT CHANGES (Day 222).

⭐   ⇒ ⭐⭐ THIS IS CONTENT-ADDRESSED CACHING — the same idea as a
⭐     Maven release version being immutable while SNAPSHOT is not.
⭐     ⭐ The NAME is the version, so invalidation stops being a
⭐       problem you have.
```

| ⭐ Getting it wrong | Symptom |
|---|---|
| `index.html` cached | ⭐⭐ Users stuck on an old app; deploys appear to do nothing |
| Hashed assets `no-cache` | ⭐ Every visit re-downloads the whole bundle |
| No hashing at all | ⭐⭐ Purge the CDN on every deploy and pray |

# Part 2 — ⭐⭐ The stale tab

```
⭐⭐ THE FAILURE, IN ORDER

⭐   ① user opens the app at 09:00 — running build A
⭐   ② you deploy build B at 10:00. ⭐ Old chunks are DELETED.
⭐   ③ at 10:05 the user clicks a link to a lazy route
⭐   ④ ⭐⭐ THE BROWSER REQUESTS /assets/reports.OLDHASH.js
⭐   ⑤ ⭐⭐ 404 ⇒ CHUNK LOAD ERROR ⇒ it happens during render ⇒
⭐     ⭐ THE WHITE SCREEN (Day 240).

⭐   ⇒ ⭐⭐ THE USER DID NOTHING WRONG AND SEES A DEAD APP.
⭐     ⭐ The most common frontend production incident there is.
⭐   ⇒ ⭐⭐ NOTE HOW UNLIKE A JAR DEPLOY THIS IS. Replacing a jar
⭐     replaces the whole running program. Here the OLD PROGRAM
⭐     KEEPS RUNNING IN THE USER'S BROWSER AND STARTS ASKING FOR
⭐     FILES YOU JUST DELETED.
```

| ⭐ Fix | |
|---|---|
| **⭐⭐ Keep old assets** | Do **not** delete previous builds. Keep 2–3 deploys. **This alone fixes most of it.** |
| **⭐⭐ Catch chunk errors and reload once** | A boundary that detects `ChunkLoadError`, sets a flag, and reloads — **once**, or you get a reload loop |
| **Version endpoint + a prompt** | ⭐ Poll `/version`; on change show "A new version is available — Reload" |

```jsx
// ⭐⭐ the reload-once guard — the loop is the trap
if (/ChunkLoadError|Loading chunk .* failed/.test(error.message)) {
  if (!sessionStorage.getItem("chunk-reloaded")) {
    sessionStorage.setItem("chunk-reloaded", "1");   // ⭐ ONCE
    location.reload();
  }
}
```

> ⭐⭐ **This is a compatibility window, exactly like a Flyway migration** (Stage 5). **Two versions are
> live at once and old clients must keep working** — which also means your API cannot break a contract
> the moment the new frontend ships. **Expand, migrate, contract** applies here too (Day 246).

# Part 3 — Config without rebuilding

```
⭐⭐ THE PROBLEM: import.meta.env IS BAKED IN AT BUILD TIME.
⭐   ⇒ ⭐⭐ "SAME ARTEFACT TO EVERY ENVIRONMENT" — which you get free
⭐     with a jar plus an external application.yml — IS IMPOSSIBLE
⭐     if the API URL is compiled into the bundle. ⭐ You must
⭐     rebuild per environment, so THE THING YOU TESTED IN STAGING
⭐     IS NOT THE THING YOU SHIP.
```

| ⭐ Approach | Trade |
|---|---|
| **Build-time env** | ⭐ Simple. One build per environment. Fine for most apps. |
| **⭐⭐ Runtime config endpoint** | `/config.json` fetched at startup, `no-cache`. **One artefact, every environment** — the closest thing to your external config. |
| **Injected `<script>` in `index.html`** | ⭐ The server templates `window.__CONFIG__`. No extra request. |
| **Same-origin `/api`** | ⭐⭐ **Removes the problem entirely** (Day 237) |

> ⭐ **And whichever you pick: no secrets** (Day 222). Runtime config is still public.

# Part 4 — Rollout and rollback

```
⭐⭐ THE FRONTEND'S ADVANTAGE: ROLLBACK IS ALMOST FREE.

⭐   ⭐ No state, no migration, no draining connections, no
⭐     in-flight requests to finish — just a different set of
⭐     static files. ⭐⭐ REVERTING IS REPOINTING AN ALIAS: SECONDS.
⭐   ⇒ ⭐⭐ SO: SHIP SMALL AND OFTEN. Rank changes by rollback cost
⭐     (Day 459); a frontend change sits at the CHEAP end.

⭐   ⭐ THE EXCEPTION THAT IS NOT CHEAP: a frontend change that
⭐     required an API change. ⭐⭐ ROLLING BACK THE UI LEAVES THE
⭐     API AHEAD. ⇒ SHIP THE API FIRST, BACKWARD-COMPATIBLE,
⭐     THEN THE UI. ⭐ Same ordering rule as a schema migration.
```

| ⭐ Practice | |
|---|---|
| **Preview deploys per PR** | ⭐⭐ Every branch gets a URL. **Reviewers click instead of imagining.** |
| **Smoke test after deploy** | ⭐ Load the page, assert the bundle parses, assert one API call works |
| **⭐ Source maps to Sentry, not the CDN** | Day 222 |
| **Deploy = a new immutable directory** | ⭐ Never overwrite in place; that is what makes rollback trivial |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "what happens when you deploy a frontend?"**

Lead with the reframe. **Deploying doesn't replace the running app. Every user with an open tab is
still executing yesterday's bundle against today's API. It's a rollout with two versions live, not a
swap — and that's genuinely unlike replacing a jar, where the whole running program is replaced at
once.**

Then the failure. **The tab was opened at nine, I deploy at ten and old chunks are deleted, and at five
past the user clicks a lazily loaded route. The browser requests a chunk that no longer exists, gets a
404, and because it fails during render the whole app unmounts. The user did nothing wrong. It's the
most common frontend production incident there is, and most of it is fixed by not deleting the previous
build.**

Then the caching rules. **`index.html` is `no-cache` because it's the manifest pointing at the hashed
files — cache it and users run the old app forever and no deploy fixes it. Hashed assets are immutable
for a year, safely, because the name changes when the content does. It's content-addressed caching, the
same reason a Maven release version is immutable and a SNAPSHOT isn't.**

Close on what makes frontend deploys pleasant, and the trap. **Rollback is nearly free — no state, no
migration, no connections to drain, just repointing an alias in seconds. So shipping small and often is
right. The exception is a UI change that needed an API change: rolling back the UI leaves the API
ahead, so the API ships first and backward-compatible. Same ordering rule as a schema migration.**
