# Day 103

**L-103** · REST API design — resource modelling, URI design, nesting, and a HATEOAS reality check

**Time:** 3 hrs · **Mode:** NEW

> Day 016 covered what Fielding actually said. Today is the practice: how you decide what the
> resources *are*, what the URLs look like, and where to stop nesting.
>
> **This is where the most expensive API mistakes are made**, because a published URL is close to
> permanent — clients you do not control have hard-coded it.

# Part 1 — Resource modelling

## Resources are nouns, not functions

The first instinct of most developers is to expose their service methods:

```
❌ POST /createOrder
❌ GET  /getOrderById?id=42
❌ POST /order/42/cancelOrder
❌ POST /updateUserEmailAddress
```

That is RPC wearing HTTP's clothes. The verb is already in the method:

```
✅ POST   /orders
✅ GET    /orders/42
✅ DELETE /orders/42
✅ PATCH  /users/17
```

## Resources are not your database tables

This is the mistake that survives the first one. Resources are **concepts in your API's domain**, and
the mapping to tables is a coincidence you should not preserve deliberately.

```
Table: order, order_line, order_status_history, order_payment

❌ /order_lines?order_id=42          — exposing the schema
✅ /orders/42                        — one resource, lines embedded
✅ /orders/42/timeline               — a concept, not a table
```

Conversely, one resource may span several tables, and some resources have no table at all
(`/reports/daily-revenue`).

> **Your URL structure is a public contract. Your schema is an implementation detail. Coupling them
> means a migration becomes a breaking API change.**

## Finding the resources

Ask what the *client* thinks about, not what you store:

1. **What nouns does the user talk about?** Order, cart, invoice, subscription.
2. **What does the client need to address individually?** If it needs its own URL, it is a resource.
3. **What has its own lifecycle?** A cart is created, modified and converted — a resource. A
   line item exists only within a cart — probably a sub-resource.

## Actions that are not CRUD

The hard part. What is the URL for "cancel this order", "send a password reset", "publish this
article"?

Three approaches, in order of preference:

**1. Model the action's *result* as a resource** — best when the action produces a thing.

```http
POST /orders/42/cancellation        → 201, the cancellation is now a resource
POST /password-reset-requests       → 202
POST /articles/17/publication       → 201
```

**2. Model it as a state transition** — best when the action changes a field.

```http
PATCH /orders/42
{"status": "CANCELLED"}
```

Honest about what happens, and idempotent (Day 102). The cost: the server must validate the
transition (Day 095's state machine) and cannot easily accept action-specific parameters.

**3. A verb sub-resource** — pragmatic, and everyone does it.

```http
POST /orders/42/cancel
{"reason": "customer_request"}
```

Purists object. It is clear, discoverable, allows parameters, and GitHub, Stripe and Kubernetes all
do it. **Be consistent** — a codebase that mixes all three is worse than one that consistently uses
the "impure" option.

> The real rule: **consistency beats purity.** An API where every action follows the same convention
> is easier to use than one that is theoretically pure in three different ways.

# Part 2 — URI design

## The conventions

```
/orders                    plural nouns, lowercase
/orders/42                 identifier in the path
/orders/42/line-items      hyphens, not underscores or camelCase
/orders?status=paid        filtering in the query string
```

| Rule | Why |
|---|---|
| **Plural nouns** | `/orders/42` reads as "the 42nd of the orders". Consistency beats grammar. |
| **Lowercase** | Path is case-sensitive per RFC 3986; mixed case guarantees 404s |
| **Hyphens, not underscores** | Underscores can be hidden by link underlining; hyphens are the web convention |
| **No file extensions** | Use `Accept` (Day 102), not `/orders/42.json` |
| **No trailing slash** | Pick one and redirect the other, consistently |
| **No verbs in paths** | Except deliberate action sub-resources |
| **Identifiers in the path, filters in the query** | Path identifies; query modifies |

## Nesting — where to stop

```
✅ /customers/17/orders           one level: "orders belonging to customer 17"
⚠️ /customers/17/orders/42        redundant — order 42 is already unique
❌ /customers/17/orders/42/lines/3/product/9      unusable
```

> **Rule: nest at most one level, and only when the child cannot exist without the parent.**

The test is whether the child is independently addressable. If `/orders/42` is unique, then
`/customers/17/orders/42` adds nothing except a second URL for the same thing — and now you must
decide what to do when customer 17 does not own order 42 (`404`? `403`? both leak information —
see Day 119).

The idiomatic compromise: use nesting for **collections**, flat URLs for **items**.

```
GET  /customers/17/orders          list — the nesting IS the filter
POST /customers/17/orders          create under a parent
GET  /orders/42                    the item, flat
PATCH /orders/42
```

**Singleton sub-resources** are a legitimate exception, where a child genuinely has no independent
identity:

```
GET /users/17/settings
PUT /users/17/avatar
GET /orders/42/invoice
```

## Identifiers

| Type | Pros | Cons |
|---|---|---|
| Sequential integer | Short, index-friendly | **Leaks volume**, enumerable (Day 119's IDOR) |
| UUID v4 | Unguessable, client-generatable | 36 chars, random → poor index locality |
| **UUID v7 / ULID** | Unguessable **and time-ordered** | Slightly newer; leaks creation time |
| Prefixed (`ord_8f14e45f`) | Self-describing in logs and support tickets | Non-standard |

**Sequential integers leak more than people expect.** `/orders/1042` tells a competitor you have had
about a thousand orders, and it lets an attacker enumerate every record if authorization is weak.

**UUID v7 is the current best default for a database key**: unguessable like v4, but time-ordered, so
B-tree inserts stay at the right edge of the index instead of scattering across it (Day 110's D-11
covers why that matters). Stripe's `cus_`/`ch_` prefixes are worth copying — being able to tell what
an id refers to from a log line is worth the four characters.

## Query parameters

```
GET /orders?status=paid&status=shipped     # repeated key = OR
        &created_after=2026-08-01
        &sort=-created_at,total            # '-' prefix = descending
        &fields=id,total,status            # sparse fieldset (Day 108)
        &page[size]=20&page[cursor]=abc    # pagination (Day 107)
```

**Be consistent about repeated keys.** `?status=paid&status=shipped` and `?status=paid,shipped` are
both defensible; pick one, document it, never mix.

Reserve a small set of names across the whole API: `sort`, `fields`, `filter`, `page`, `q`,
`include`. A client that learns them once should not have to relearn per endpoint.

# Part 3 — Response shape

## Consistency is the whole game

```json
{
  "data": {
    "id": "ord_8f14e45f",
    "type": "order",
    "status": "PAID",
    "total": { "amount": "1499.00", "currency": "INR" },
    "created_at": "2026-08-14T10:22:01Z",
    "customer": { "id": "cus_1a2b3c", "href": "/customers/cus_1a2b3c" }
  }
}
```

Decisions to make **once, for the entire API**, and then never revisit:

| Decision | Recommendation |
|---|---|
| Envelope or bare object? | Either — but the *same* one everywhere |
| Field naming | `snake_case` or `camelCase`, consistently. Do not mix. |
| Dates | **ISO 8601 with an explicit offset**, always UTC (`2026-08-14T10:22:01Z`) |
| Money | **A string amount plus a currency code** — never a float (Day 042B) |
| Enums | Uppercase strings, never integers — `"PAID"` survives a schema change; `3` does not |
| Nulls | Omit, or include as `null` — consistently. Omitting is smaller; including is clearer. |
| Booleans | Name them positively: `is_active`, not `is_not_disabled` |
| IDs | Strings, even when numeric underneath — you may need to change the format later |

**Money as a string is not pedantry.** `1499.00` parsed as a JSON number becomes an IEEE-754 double
in most clients, and JavaScript will happily turn `0.1 + 0.2` into `0.30000000000000004`. Send the
string; the client parses it into its own decimal type.

**IDs as strings** is the same argument one level up: a numeric id in JSON exceeds JavaScript's safe
integer range at 2^53, and Twitter had to add `id_str` to every API response for exactly this reason.

## Embedding vs linking

```json
// Linking — smaller, needs another request
"customer": { "id": "cus_1a2b3c", "href": "/customers/cus_1a2b3c" }

// Embedding — one request, larger payload
"customer": { "id": "cus_1a2b3c", "name": "Ram", "email": "…" }

// Client-controlled — the pragmatic answer
GET /orders/42?include=customer,line_items
```

`?include=` lets the client choose, avoiding both the N+1 request problem and the over-fetching
problem. It is what JSON:API standardises and what most good APIs converge on.

# Part 4 — The HATEOAS reality check

Fielding's Level 3 (Day 016) requires that responses contain links, so a client discovers what it can
do next rather than hard-coding URLs:

```json
{
  "id": "ord_42", "status": "PAID",
  "_links": {
    "self":   { "href": "/orders/42" },
    "cancel": { "href": "/orders/42/cancellation", "method": "POST" },
    "invoice":{ "href": "/orders/42/invoice" }
  }
}
```

**The honest assessment:** almost nobody implements it, and the reason is not laziness.

- **Clients hard-code URLs anyway.** The decoupling HATEOAS promises requires a generic client, and
  almost every real client is written against a specific API by a developer reading documentation.
- **It does not remove the need for docs.** A link named `cancel` does not tell you the request body.
- **It adds significant payload weight** for links most clients ignore.
- **The tooling never arrived** — OpenAPI (Day 110) won instead, because generated clients and typed
  SDKs deliver more value than runtime discovery.

**Where it genuinely helps**, and this is worth saying rather than dismissing it entirely:

- **State-dependent actions.** Sending `cancel` only when cancellation is currently legal means the
  client does not reimplement your state machine (Day 095). This is real value.
- **Pagination links** — `next` and `prev` as opaque cursors is HATEOAS, and everyone does it without
  noticing (Day 107).

> **The pragmatic position: include links where the *available actions* depend on state, and for
> pagination. Do not build a fully hypermedia-driven API unless you control both ends and have a
> specific reason.**

That is a defensible interview answer — it shows you know the model *and* the industry's verdict on
it, which is a stronger position than either purism or ignorance.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Verbs in URLs (`/getOrder`) | RPC over HTTP; loses every HTTP guarantee |
| URLs mirroring tables | A migration becomes a breaking API change |
| Nesting three levels deep | Unusable URLs, ambiguous authorization failures |
| Inconsistent naming across endpoints | Every endpoint must be learned separately |
| Sequential integer ids | Volume leak plus enumeration |
| Money as a JSON number | Floating-point corruption in the client |
| Numeric ids over 2^53 | Silently mangled by JavaScript |
| Integer enums | Meaningless in logs; breaks on reorder |
| Mixing `snake_case` and `camelCase` | Constant client-side friction |
| Dates without an offset | Timezone bugs across every client |
| Full HATEOAS with no consumer | Payload weight for nothing |
| Changing a published URL | Breaks clients you do not control |

## Interview questions

**Q: How do you model an action that is not CRUD, like cancelling an order?**
Three options: model the result as a resource (`POST /orders/42/cancellation`), model it as a state
transition (`PATCH` with a new status), or use a verb sub-resource (`POST /orders/42/cancel`). All
are defensible; consistency across the API matters more than which you pick.

**Q: How deep should URLs nest?**
At most one level, and only when the child cannot exist independently. Use nesting for collections
(`/customers/17/orders`) and flat URLs for items (`/orders/42`), since deep nesting creates duplicate
URLs and ambiguous authorization failures.

**Q: Which identifier type would you use?**
UUID v7 or ULID as a default — unguessable like v4 but time-ordered, so index inserts stay local.
Sequential integers leak business volume and enable enumeration. A type prefix like Stripe's `ord_`
makes logs and support tickets far easier.

**Q: Why send money as a string?**
JSON numbers become doubles in most clients, and decimal amounts cannot be represented exactly. Send
the amount as a string plus a currency code so the client parses it into its own decimal type.

**Q: Should URLs mirror your database schema?**
No. The URL structure is a public contract and the schema is an implementation detail. Coupling them
turns any migration into a breaking change.

**Q: What is HATEOAS, and do you use it?**
Responses carry links so clients discover available actions rather than hard-coding URLs. In practice
almost nobody implements it fully — clients hard-code anyway and OpenAPI won. It is genuinely useful
for state-dependent actions and pagination cursors, and I use it there.

## 🎙️ Articulation drill

Two minutes: **"Design the API for an e-commerce checkout."**

Name the resources first, then the URLs, then the non-CRUD actions and your convention for them, then
the response shape decisions — money as a string, ISO dates, string ids. Finish with what you would
*not* do: no deep nesting, no schema mirroring, no sequential ids. Stating the constraints you chose
is what makes it a design rather than a list.
