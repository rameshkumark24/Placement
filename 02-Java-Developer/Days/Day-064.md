# Part 1 — L-064 · Threads

## What a Java thread actually is

A `java.lang.Thread` is **a thin wrapper over an operating-system thread**. Day 029's B-03 covered
the OS side; the Java specifics:

- `new Thread(...)` allocates a Java object. **No OS thread exists yet.**
- `start()` makes a native call that asks the OS to create a real thread, which then executes `run()`
  on its own stack.
- Calling `run()` directly just invokes a method **on the current thread**. This is the single most
  common beginner mistake and it produces no error — the code works, sequentially, and you cannot
  tell from the output unless you print the thread name.
- `start()` twice throws `IllegalThreadStateException`. A `Thread` object is single-use.

Each thread gets its own **stack** — 512 KB to 1 MB by default (`-Xss`) — and shares the **heap**
with every other thread. That one sentence is the whole of Java concurrency in miniature: locals are
private and safe (Day 025), objects on the heap are shared and dangerous.

The cost follows directly. A 1 MB stack means **~1,000 threads consume 1 GB of stack space**, and a
context switch costs 1–10 microseconds (Day 033's B-04) plus the cache and TLB damage (Day 053's
B-10). This is why thread-per-request stops scaling around a few thousand connections — and it is
exactly the problem virtual threads (Day 072) exist to solve.

## The lifecycle

```
              start()                    scheduler picks it
   NEW ─────────────────► RUNNABLE ◄──────────────────────┐
                          │  │  │                          │
      synchronized blocked│  │  │wait()/join()/park()      │
                          ▼  │  ▼                          │
                     BLOCKED │  WAITING ──── notify() ─────┤
                          │  │  TIMED_WAITING ── timeout ──┘
                          └──┴──► run() returns / throws
                                       ▼
                                  TERMINATED
```

The distinction that matters for reading a thread dump (Day 076):

| State | Means |
|---|---|
| `RUNNABLE` | running, **or blocked in a syscall** — the JVM cannot tell the difference |
| `BLOCKED` | waiting to acquire a `synchronized` monitor |
| `WAITING` | `wait()`, `join()`, `LockSupport.park()` — waiting for another thread to act |
| `TIMED_WAITING` | the same with a deadline, plus `sleep` |

**A thread stuck reading from a socket shows as `RUNNABLE`.** That surprises people debugging a hung
service — the state name means "not waiting on a Java-level monitor", not "consuming CPU". Cross-
check with actual CPU usage (B-15, Day 071).

## `Runnable` vs `Callable`

```java
Runnable r = () -> System.out.println("no result, no checked exception");

Callable<Integer> c = () -> {
    Thread.sleep(100);          // ✅ allowed — Callable declares throws Exception
    return 42;
};
```

|  | `Runnable` | `Callable<V>` |
|---|---|---|
| Returns | `void` | `V` |
| Checked exceptions | cannot throw | `throws Exception` |
| Usable with | `Thread`, executors | **executors only** |
| Result handling | none | `Future<V>` |

`Callable` exists because `Runnable` cannot report either a value or a failure. With a raw
`Runnable`, an exception kills the thread and — unless you installed an
`UncaughtExceptionHandler` — the only trace is a message on stderr. `Callable` packages both the
result and the exception into a `Future`, which is why executors (Day 069) prefer it.

## Daemon threads

```java
Thread t = new Thread(this::backgroundWork);
t.setDaemon(true);       // MUST be set before start()
t.start();
```

**The JVM exits when the last non-daemon thread finishes.** Daemon threads are killed abruptly at
that point — no `finally` blocks, no cleanup, mid-write if that is where they are.

So: daemon for genuinely disposable background work (metrics sampling, cache eviction); **never**
for anything that writes data or holds a resource. Your `main` thread is non-daemon; GC threads are
daemon.

## Interruption — cooperative cancellation

Java has no safe way to stop a thread. `Thread.stop()` is deprecated and dangerous because it
throws `ThreadDeath` at an arbitrary bytecode, potentially leaving invariants broken and monitors
released mid-update. What exists instead is a *request*:

```java
public class Interruption {

    static void worker() {
        while (!Thread.currentThread().isInterrupted()) {   // 1. poll the flag
            try {
                doChunkOfWork();
                Thread.sleep(100);                          // 2. or be woken by it
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();         // 3. RESTORE and exit
                break;
            }
        }
        System.out.println("clean exit");
    }

    public static void main(String[] args) throws Exception {
        Thread t = new Thread(Interruption::worker, "worker");
        t.start();
        Thread.sleep(500);
        t.interrupt();          // a request, not a kill
        t.join();
    }
}
```

The rules, which Day 062 previewed:

1. `interrupt()` sets a **flag**. It does not stop anything.
2. If the thread is in `sleep`, `wait`, `join` or most `java.util.concurrent` blocking calls, that
   call throws `InterruptedException` **and clears the flag**.
3. Therefore: either propagate the exception, or restore the flag and return. Never swallow it.
4. `Thread.interrupted()` (static) checks **and clears**; `isInterrupted()` (instance) only checks.
   Confusing these is a real bug — the static one silently consumes the signal.

Blocking socket I/O is *not* interruptible. That is one of the reasons a hung network call is so
hard to kill, and one more argument for timeouts on every client.

## Code to type — the race, and thread names

```java
public class ThreadBasics {
    static int counter = 0;                 // shared, unsynchronized

    public static void main(String[] args) throws Exception {
        // 1. run() vs start()
        Runnable task = () -> System.out.println("running on " + Thread.currentThread().getName());
        task.run();                                     // main
        new Thread(task, "worker-1").start();           // worker-1

        Thread.sleep(50);

        // 2. the lost update
        Thread a = new Thread(ThreadBasics::bump, "a");
        Thread b = new Thread(ThreadBasics::bump, "b");
        a.start(); b.start();
        a.join();  b.join();
        System.out.println("counter = " + counter + " (expected 200000)");

        // 3. an uncaught exception
        Thread boom = new Thread(() -> { throw new RuntimeException("died"); }, "boom");
        boom.setUncaughtExceptionHandler(
                (th, e) -> System.out.println("handler saw " + th.getName() + ": " + e.getMessage()));
        boom.start();
        boom.join();
        System.out.println("main still alive");

        // 4. stack cost
        System.out.println("threads created before OOM: " + countUntilFailure());
    }

    static void bump() { for (int i = 0; i < 100_000; i++) counter++; }

    static int countUntilFailure() {
        List<Thread> live = new ArrayList<>();
        try {
            while (true) {
                Thread t = new Thread(() -> {
                    try { Thread.sleep(60_000); } catch (InterruptedException ignored) {}
                });
                t.start(); live.add(t);
                if (live.size() >= 10_000) break;      // stop before hurting the machine
            }
        } catch (OutOfMemoryError e) { /* expected */ }
        live.forEach(Thread::interrupt);
        return live.size();
    }
}
```

Run it several times. `counter` will land somewhere below 200,000 and **a different value each
time** — that non-determinism is the point. `counter++` is read, add, write: three operations, and
two threads can interleave between any of them. This is the race Day 065 explains formally and Day
066 fixes.

Also notice `main` survives the `boom` thread's death. **An exception in one thread does not affect
others.** Silent thread death is a real production failure mode; that is why executors capture the
exception into a `Future` instead.

# Part 2 — B-13 · I/O models

Everything above says threads are expensive. This is the other half of the story: what you do
instead.

## The four models

**1. Blocking I/O.** `read()` puts the thread to sleep until data arrives. Simple, and the thread is
100% idle while waiting. **One thread per connection.** 10,000 connections = 10,000 threads = ~10 GB
of stacks and a scheduler drowning in context switches. This is Day 004's server.

**2. Non-blocking I/O.** Set the socket to non-blocking; `read()` returns `-EWOULDBLOCK` immediately
if nothing is ready. Now one thread *can* serve many sockets — but only by **polling** all of them
in a loop, which burns CPU proportional to the number of connections regardless of activity. Not a
real solution.

**3. I/O multiplexing.** Ask the kernel: *"here are 10,000 file descriptors; block me until at least
one is ready, then tell me which."* One thread, one syscall, N connections.

```
    ┌──────────┐
    │  thread  │ ──── epoll_wait() ───► kernel: sleeps until something is ready
    └──────────┘ ◄─── "fd 7, fd 92 readable" ───┘
         │
         └─► read fd 7, read fd 92, handle, loop
```

**4. Asynchronous I/O.** "Do this read and notify me when the *data is already in my buffer*."
Multiplexing tells you when you *may* read; true async does the read for you. Windows IOCP and
Linux `io_uring` do this; `epoll` does not.

## `select` → `poll` → `epoll`

| API | Cost per call | Limit | Why superseded |
|---|---|---|---|
| `select` | **O(n)** — copies and scans the full fd set every call | 1024 fds | Both |
| `poll` | **O(n)** — no fd limit, still rescans everything | none | Still O(n) |
| `epoll` | **O(1)** — kernel keeps the interest set; returns only ready fds | none | — |

`epoll` splits the work: `epoll_ctl` registers a descriptor once, and `epoll_wait` returns only the
ready ones. **The cost stops scaling with the number of idle connections** — it scales with the
number of *active* ones, which is what you actually want. This is what "solves the C10K problem"
means.

BSD/macOS calls it `kqueue`; Windows uses IOCP. Java's `Selector` abstracts all three:

```java
Selector selector = Selector.open();
ServerSocketChannel server = ServerSocketChannel.open();
server.bind(new InetSocketAddress(8080));
server.configureBlocking(false);
server.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();                                  // ← blocks in epoll_wait
    Iterator<SelectionKey> it = selector.selectedKeys().iterator();
    while (it.hasNext()) {
        SelectionKey key = it.next();
        it.remove();                                    // MUST remove — or you re-handle it
        if (key.isAcceptable()) { /* accept, register OP_READ */ }
        else if (key.isReadable()) { /* read without blocking */ }
    }
}
```

That loop is the entire architecture of Netty, and therefore of Tomcat's NIO connector, Spring
WebFlux, Vert.x, Cassandra and Elasticsearch. **It is also exactly Node.js's event loop and nginx's
worker model** — the same kernel primitive, different language wrappers.

The trade-off is real: this code is dramatically harder to write and to debug than the blocking
version, because no operation may block. One accidental blocking database call inside an event-loop
callback stalls every connection that loop owns. **That** is what Day 072's virtual threads are
trying to eliminate — blocking-style code with multiplexed-style scaling.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `run()` instead of `start()` | Runs on the caller's thread; no concurrency, no error |
| `setDaemon` after `start()` | `IllegalThreadStateException` |
| Daemon threads doing real work | Killed mid-operation at JVM exit |
| Swallowing `InterruptedException` | Cancellation is lost; shutdown hangs |
| `Thread.interrupted()` when you meant `isInterrupted()` | Silently clears the flag |
| Expecting `RUNNABLE` to mean "using CPU" | Misreads every thread dump |
| Unbounded thread creation | `OutOfMemoryError: unable to create native thread` |
| Blocking call inside an event loop | Stalls every connection on that loop |
| Not removing from `selectedKeys()` | The same event handled forever |

## Interview questions

**Q: `start()` vs `run()`?**
`start()` asks the OS for a new thread which then executes `run()`. Calling `run()` directly is an
ordinary method call on the current thread — no concurrency, and no warning.

**Q: `Runnable` vs `Callable`?**
`Callable` returns a value and may throw checked exceptions; it only works with executors, which
deliver both through a `Future`. `Runnable` loses both.

**Q: What is a daemon thread?**
One that does not keep the JVM alive. When the last non-daemon thread ends, daemons are killed
without cleanup — so never use one for work that must complete.

**Q: How do you stop a thread?**
You ask. `interrupt()` sets a flag and causes blocking calls to throw `InterruptedException`; the
thread must cooperate by polling the flag or handling the exception. `stop()` is deprecated because
it can break invariants mid-update.

**Q: Why can't you have a thread per connection at scale?**
Stack memory (~1 MB each) plus context-switch and cache costs. Beyond a few thousand you spend more
time switching than working — hence multiplexing, or virtual threads.

**Q: What does `epoll` do that `select` does not?**
Registration is separate from waiting, so the kernel maintains the interest set and returns only
ready descriptors — O(1) in the number of idle connections instead of O(n).
