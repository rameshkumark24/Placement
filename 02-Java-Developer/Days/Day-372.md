# Day 372

**L-372** · Configuration and secrets — 12-factor, honestly

**Time:** 3 hrs · **Mode:** NEW

> **⭐ "Store config in the environment" is the most quoted and most over-applied rule in the whole
> twelve factors — because it is right about config and wrong about secrets.**
>
> Today: which factors still earn their place, why a missing property must kill your process at
> startup rather than at 3am, and how an application gets a secret without holding a credential to
> fetch it.

---

# Part 1 — ⭐ The factors that still matter

| ⭐ Factor | ⭐ Verdict |
|---|---|
| ⭐⭐ **III. Config in the environment** | ⭐ **right for config, wrong for secrets** — see Part 2 |
| ⭐⭐ **VI. Processes are stateless** | ⭐⭐ **the one that matters most** (Day 324) |
| ⭐ **IX. Disposability — fast start, graceful stop** | ⭐ Day 361; this is what makes rolling deploys work |
| ⭐ **X. Dev/prod parity** | ⭐ Day 365's two-replica argument |
| ⭐ **XI. Logs to stdout** | ⭐ the platform collects (Day 375) |
| ⭐ IV. Backing services are attached resources | swap a database by changing a URL |
| ⭐ **XII. Admin tasks as one-off processes** | ⭐ migrations as a job, not at startup (Day 370) |
| V. Build/release/run separation | ⭐ build once, promote many (Day 368) |
| ⭐ VIII. Concurrency via the process model | ⭐⭐ **dated for the JVM** — threads are the unit, not processes |
| VII. Port binding | ⭐ Boot does this anyway |

> **⭐ Be willing to say which factors are dated.** The process-model concurrency factor came from
> Ruby and does not describe the JVM, where one process with a thread pool is correct. **Reciting all
> twelve as gospel is weaker than knowing which three actually change your design.**

## ⭐ The configuration hierarchy

```
⭐ 1. Sensible DEFAULTS in code                  ⭐ the app runs with nothing set
⭐ 2. Bundled profile files (application-*.yml)  ⭐ per-environment SHAPE, no secrets
⭐ 3. ⭐ Environment variables / mounted files    ⭐ per-deployment VALUES
⭐ 4. Runtime overrides (a flag service)         ⭐ things that change without a deploy
⭐ ⇒ ⭐⭐ ONE image, all environments. ⭐ Nothing environment-specific is ever baked in.
```

⚠️ **The test is blunt: can you run the production image locally by changing only environment
values?** If not, something environment-specific is inside the image, **and the artefact you tested
is not the artefact you shipped** (Day 368).

# Part 2 — ⭐⭐ Validated config: fail at startup

```java
@ConfigurationProperties("payments")
@Validated
public record PaymentsConfig(
    @NotBlank String gatewayUrl,
    @NotNull  @Positive Duration timeout,
    @NotBlank String merchantId) { }
```

| ⭐ Without validation | ⭐ With |
|---|---|
| ⭐⭐ a missing property is `null` | ⭐⭐ **the process refuses to start** |
| ⭐ discovered on the first request that needs it | ⭐ discovered by the deploy, in seconds |
| ⭐⭐ **at 3am, as a NullPointerException** | ⭐⭐ **at deploy time, as a rolled-back release** |
| the bad config is live and serving | ⭐ readiness never passes, so no traffic arrives |

> **⭐ This is Day 287's checklist item 2, and it converts a whole class of production incident into
> a failed deploy.** With a rolling update and a readiness gate, **a misconfigured release never
> takes traffic at all** — the rollout stalls and rolls back (Day 371).

**⭐ Validate more than presence:** a URL that parses, a timeout inside the SLA budget (Day 339), a
pool size within the fleet-wide connection budget (Day 324). **Config validation is a place to encode
invariants, not just check for nulls.**

⚠️ **And log the effective configuration at startup — with secrets masked.** "Which config is this
instance actually using?" is a question you will ask during an incident, **and the answer should be
in the first hundred lines of the log** rather than reconstructed from four sources.

# Part 3 — ⭐⭐ Secrets: the bootstrapping problem

```
⭐ The application needs a database password.
⭐   ⇒ fetch it from a secret manager
⭐   ⇒ ⭐⭐ but to authenticate to the secret manager it needs… a credential.
⭐   ⇒ ⭐⭐ THE CHICKEN-AND-EGG PROBLEM. Where does the FIRST secret come from?
```

| ⭐ Answer | ⭐ How |
|---|---|
| ⭐⭐ **Workload identity** | ⭐⭐ **the platform vouches for the workload — no credential is ever stored** |
| ⭐ AWS: IAM roles for service accounts | the pod's service account maps to a role |
| ⭐ Kubernetes: projected SA tokens | short-lived, audience-scoped, rotated automatically |
| ⭐ **GitHub Actions: OIDC** | ⭐ Day 369 — the same idea in CI |
| Vault: Kubernetes auth | Vault verifies the SA token with the API server |

> **⭐ The pattern is identical everywhere: the platform signs an assertion about *who this workload
> is*, and the secret store trusts that assertion instead of a shared password.** It removes the
> bottom secret from the chain entirely — **which is the only real solution to bootstrapping.**

## ⭐ Delivery: how the secret reaches the process

| Mechanism | ⭐ Verdict |
|---|---|
| ⭐⭐ **Environment variables** | ⭐⭐ **avoid** — `docker inspect`, `/proc`, child processes, crash dumps (Day 364) |
| ⭐⭐ **Mounted files** (tmpfs) | ⭐⭐ **the default answer** — plus Spring's `configtree:` |
| ⭐ **Fetched at startup via workload identity** | ⭐ best for rotation; a startup dependency |
| ⭐ A sidecar that refreshes files | ⭐ rotation without app changes |
| ⭐ **In the image** | ⭐⭐ **never — permanent** (Day 362) |

⚠️ **Kubernetes `Secret` objects are base64, not encryption.** Anyone with read access to the
namespace, or to etcd, has the plaintext. **Enable encryption at rest, restrict RBAC, and treat a
`Secret` as "not in the image and not in git" rather than "protected".**

## ⭐⭐ Rotation is the point

> **⭐ A secret manager you never rotate from is an expensive environment variable.** Rotation is the
> capability you are paying for — and **the application has to participate.**

| ⭐ Requirement | |
|---|---|
| ⭐ **Re-read without a restart** | ⭐ watch the file, or refresh on a schedule |
| ⭐⭐ **Two credentials valid at once during rotation** | ⭐⭐ **or every rotation is a brief outage** |
| ⭐ Connection pools must be recycled | Hikari holds authenticated connections (Day 156) |
| ⭐ **Rotation must be exercised** | ⭐ Day 283 — an untested rotation fails when it matters |
| Short-lived dynamic credentials | ⭐ **the strongest form — a per-instance database user with a TTL** |

⚠️ **And the rule from Day 296, restated because it is the one people resist: a secret that has ever
been committed, logged or built into an image is compromised.** Removing it from git history does not
help — **it was cloned, it is in a fork, it is in a CI log.** **Rotate. Removal is cleanup, not
remediation.**

# Part 4 — ⭐ Flags, and the config/flag boundary

| | ⭐ Configuration | ⭐ Feature flag |
|---|---|---|
| ⭐ Changes | per environment, rarely | ⭐ **at runtime, often, per user** |
| Set by | deployment | ⭐ a flag service or console |
| ⭐ **Failure default** | the app will not start | ⭐⭐ **must fail to a known state — usually "off"** |
| Example | database URL, pool size | new checkout flow, a kill switch |

> **⭐ The most valuable flag is not a feature flag at all — it is a kill switch** for an expensive or
> risky subsystem: recommendations, a third-party call, an experimental path. **When that dependency
> misbehaves, turning it off in seconds beats any rollback** (Day 339's degradation matrix, made
> operable).

⚠️ **The flag service becomes a critical dependency.** It must be cached locally, must have a
sensible default when unreachable, **and must never be a synchronous blocking call on the request
path.** A flag system that takes down the application it was meant to protect is a genuinely common
irony.

## ⭐ The audit dimension

| ⭐ Requirement | |
|---|---|
| ⭐ Who changed which config, when | ⭐ **config changes cause incidents as often as code** |
| ⭐⭐ **Config in version control** | ⭐⭐ reviewed and diffable — GitOps, for everything except secret *values* |
| ⭐ Secret **access** logged | who read which secret, and when |
| Flag changes audited | ⭐ "nobody deployed" is often false — someone flipped a flag |

**⭐ "Nothing changed" during an incident is usually wrong**, and config and flags are the two places
people forget to look. **Making both auditable turns a twenty-minute argument into a one-line
answer.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Reciting all twelve factors uncritically | ⭐ some are dated for the JVM |
| ⭐⭐ **Environment-specific values in the image** | ⭐⭐ you tested one artefact and shipped another |
| ⭐⭐ **Unvalidated config** | ⭐⭐ **a missing property becomes a 3am NPE instead of a failed deploy** |
| ⭐ Not logging effective config | you reconstruct it during an incident |
| ⭐⭐ **Secrets in environment variables** | ⭐ inspectable, inherited, in crash dumps |
| ⭐ Treating a Kubernetes `Secret` as encrypted | it is base64 |
| ⭐ **A credential to fetch credentials** | ⭐⭐ the bootstrapping problem, unsolved — use workload identity |
| ⭐ A secret manager with no rotation | an expensive environment variable |
| ⭐⭐ **Rotation with only one valid credential** | ⭐⭐ every rotation is an outage |
| ⭐ Removing a leaked secret without rotating | ⭐⭐ it is already cloned, forked and logged |
| ⭐ A flag service with no local cache or default | ⭐ it takes down what it was protecting |
| Flags on the synchronous request path | added latency and a new failure mode |
| No audit trail for config or flags | "nothing changed" is unfalsifiable |

## Interview questions

**Q: Should configuration live in environment variables?**
Config, yes — it keeps one image running in every environment and makes backing services attachable.
Secrets, no. Environment variables are visible via `docker inspect` and `/proc`, are inherited by
every child process, frequently end up in crash dumps and logs, and cannot be rotated without a
restart. Secrets go in mounted files, ideally on tmpfs, read through something like Spring's config
tree so they are ordinary properties with no code change.

**Q: What happens when a required property is missing?**
The process should refuse to start. Without validation it becomes null and surfaces on the first
request that needs it, which in practice is at three in the morning as a NullPointerException. With
validation and a readiness gate, a misconfigured release never takes traffic at all — the rollout
stalls and rolls back. It converts a production incident into a failed deploy, which is the whole
point.

**Q: How does an application authenticate to a secret manager?**
Workload identity, otherwise you have a credential to fetch credentials and have solved nothing. The
platform signs an assertion about which workload this is — an IAM role bound to a service account, a
projected Kubernetes token, OIDC in CI — and the secret store trusts that assertion rather than a
shared password. It is the same mechanism in every environment, and it removes the bottom secret from
the chain entirely.

**Q: Why is rotation the point of a secret manager?**
Because without it you have paid for an expensive environment variable. And the application has to
participate: it must re-read without restarting, connection pools have to be recycled since they hold
authenticated connections, and two credentials must be valid simultaneously during the changeover or
every rotation is a brief outage. The strongest form is short-lived dynamic credentials — a
per-instance database user with a TTL — where rotation is continuous rather than an event.

**Q: A secret was committed to git two years ago. What do you do?**
Rotate it. Removing it from history is cleanup, not remediation — the repository was cloned, forked,
mirrored into CI logs and possibly scanned by someone else within minutes. Then find out how it got
there and add scanning to the pre-commit hook and the pipeline, and check whether it appears in any
image layer as well, because that is equally permanent.

## Mini task

1. ⭐ **Run your production image locally** changing only environment values. **Anything that stops
   you is baked-in config.**
2. ⭐ Add `@Validated` `@ConfigurationProperties` for one component. **Delete a required property and
   confirm the app refuses to start.**
3. ⭐ Add a **cross-field validation** — a timeout that must fit inside the SLA budget — and prove it
   rejects a bad combination.
4. ⭐ Log the **effective configuration at startup with secrets masked.** Confirm no secret appears.
5. ⭐⭐ Move every secret from environment variables to **mounted files** via `configtree:`. Verify
   with `docker inspect` and `/proc/<pid>/environ`.
6. ⭐ Set up **workload identity** for one secret fetch. **Confirm no static credential exists
   anywhere.**
7. ⭐⭐ **Rotate a database password with the application running.** If it drops connections, implement
   dual-credential rotation and pool recycling, then repeat.
8. ⭐ Add a **kill switch** for one non-critical dependency. Turn it off under load and **confirm
   graceful degradation** (Day 339).
9. ⭐ Make the flag service unreachable and **verify the default behaviour is the one you intended.**
10. Add audit logging for config and flag changes, and **answer "what changed in the last hour?" in
    one query.**

## 🎙️ Articulation drill

**Two minutes:** *"Where do your secrets live?"*

**⭐ The full answer is four sentences.** Not in the image at any layer, because layers are permanent
· not in environment variables, because they are inspectable and inherited · mounted as files read
through the config tree, so rotation is a file change rather than a restart · **and the application
authenticates to the secret store with workload identity, so there is no bottom credential to
protect.**

**⭐ Then the closing line that shows operational maturity: "and rotation is exercised, not assumed —
including keeping two credentials valid during the changeover, or every rotation is a small
outage."**
