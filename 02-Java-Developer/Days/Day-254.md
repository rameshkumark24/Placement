# Day 254 🏗️

**P-254** · The domain layer — entities, invariants, and the state machine in code

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Today you write the part of the system that has no framework in it.** Entities with behaviour,
> invariants enforced in constructors and transition methods, and the state machine from Day 249
> turned into code that makes an invalid state unrepresentable.
>
> **⭐ The test of a good domain layer: you can unit-test every business rule with `new`, no Spring
> context, in milliseconds.** If you cannot, the rules are somewhere else — usually scattered across
> service methods where each caller must remember them.

---

# Part 1 — ⭐ Entities with behaviour, not data holders

**⭐ The anaemic model is the default failure**, and it looks harmless:

```
⭐ Anaemic:  entity has getters and setters; ALL logic is in the service
⭐ Rich:     entity owns its invariants; the service orchestrates
```

**⭐ Why anaemic is a real problem rather than a style opinion:**

| Consequence | Detail |
|---|---|
| ⭐ **Rules are unenforceable** | any caller can `setStatus(SHIPPED)` and skip the guard |
| ⭐ **Rules get duplicated** | the job, the consumer and the controller each reimplement them |
| ⭐ **Invalid states are representable** | `CONFIRMED` with no `confirmedAt` (Day 187) |
| ⭐ **Testing needs Spring** | the rule lives in a service with five dependencies |

## ⭐ The three rules for today

> **⭐ 1. No public setters on anything with an invariant.** State changes go through named methods
> that express the transition and enforce the guard.
>
> **⭐ 2. The constructor cannot produce an invalid object.** Validate in it; throw if the arguments
> cannot form a valid entity.
>
> **⭐ 3. Every state transition is a method whose name is the transition** — `confirm()`, `cancel()`,
> `expire()` — and each checks the current state before changing it.

**⭐ Rule 3 is what turns Day 249's diagram into enforcement.** A `cancel()` method that checks the
current state and the two-hour guard means **there is exactly one place cancellation logic lives**,
and the batch job, the controller and the consumer all pass through it.

**⭐ And JPA's requirements still apply** (Day 158):

```
⭐ A protected no-arg constructor — JPA needs it; nobody else should use it
⭐ The class NOT final — or lazy loading silently becomes eager
⭐ equals/hashCode on the business key (public_id), not the generated id
⭐ EnumType.STRING — ORDINAL silently reinterprets rows when you add a constant
```

# Part 2 — ⭐ Value objects, and what they eliminate

**⭐ Every primitive that has rules is a value object waiting to be extracted.**

| Primitive | ⭐ Value object | ⭐ What it eliminates |
|---|---|---|
| `BigDecimal amount` + `String currency` | ⭐ `Money` | adding GBP to USD |
| `Instant start` + `Instant end` | ⭐ `TimeRange` | end before start; overlap logic duplicated everywhere |
| `String email` | ⭐ `EmailAddress` | invalid emails past the boundary; casing bugs |
| `String status` | ⭐ an enum + transition rules | typos, invented values |

**⭐ Records are close to ideal** (Day 060, Day 147): immutable, compact, `equals` free, and they map
to `@Embeddable` (Day 158).

**⭐ The property that makes them worth the effort: validate once, in the constructor, and every
instance in the system is valid forever.** A `TimeRange` that cannot be constructed with `end` before
`start` means no method anywhere needs to check that — and no method can forget to.

**⭐ And `TimeRange` is where your overlap logic belongs**, as a method on the value object. The
database enforces it too (Day 187's exclusion constraint), but having it in the domain means you can
unit-test the rule in microseconds and give the user a good error message rather than a constraint
violation.

**⭐ Two implementation notes:**

| | |
|---|---|
| ⭐ Prefer **immutable** value objects | Day 198's warning: a mutable embedded field may not be detected as dirty (Day 162) |
| ⭐ Put the **domain rule** on the object | `range.overlaps(other)`, `money.plus(other)` — not in a utility class |

# Part 3 — ⭐ The domain has no framework in it

```
⭐ domain/     — entities, value objects, domain exceptions, domain services.
                 ⭐ NO Spring. NO Jackson. NO javax.servlet.
⭐ Only JPA annotations, and even those are a compromise worth noting.
```

**⭐ Enforce it with the ArchUnit rule you wrote on Day 253:**

```
⭐ noClasses().that().resideInAPackage("..domain..")
     .should().dependOnClassesThat().resideInAPackage("org.springframework..")
```

**⭐ The payoff is concrete, not architectural aesthetics:**

| Benefit | Why |
|---|---|
| ⭐ **Business rules unit-testable with `new`** | ⭐ **milliseconds, thousands of tests** (Day 183) |
| The rules survive a framework change | Spring is not in them |
| ⭐ **The rules are readable** | no annotations obscuring the logic |
| ⭐ **Reviewers can find them** | one package holds the domain |

**⭐ The honest compromise: JPA annotations are in the domain.** The purist alternative — separate
domain objects and persistence entities with mapping between them — is real and costs a mapping layer
for every entity. **For a single-service project, JPA annotations in the domain is the right trade,
and being able to say *why* you took it is the point.** Write it in an ADR.

## ⭐ Domain exceptions, mapped once

```
⭐ domain/  BookingOverlapException, TooLateToCancelException, InvalidTransitionException
⭐ Each carries the data the client needs to act (Day 149's extension members)
```

**⭐ Domain exceptions must not know about HTTP.** No status codes, no `ResponseStatusException`.
**Day 149's `@RestControllerAdvice` maps them to status codes in one place** — which is what lets the
same domain be used by a Kafka consumer that has no notion of a 409.

# Part 4 — ⭐ Testing the domain, and what those tests prove

**⭐ These are the fastest and most valuable tests in the project.** No Spring, no database, no mocks.

**⭐ Write a test for every guard on every transition**, including the ones you expect to pass:

```
⭐ For each transition in Day 249's diagram:
   1. It succeeds from every legal source state
   2. ⭐ It THROWS from every illegal source state          ← the ones people skip
   3. ⭐ Every guard rejects (the 2-hour rule, the ownership rule)
   4. ⭐ It is idempotent where the AC says so
   5. ⭐ Side effects happen (the event is registered)
```

**⭐ Point 2 is the set most people omit**, and it is the set that catches a refactor removing a
guard. A test asserting `cancel()` throws from `COMPLETED` is what stops someone "simplifying" that
check away in month three.

**⭐ Property-based testing earns its place here**, if you want one high-value addition:

```
⭐ jqwik / junit-quickcheck: for any two TimeRanges, overlaps() is symmetric
⭐ For any sequence of legal transitions, the entity never reaches an invalid state
```

**⭐ The second property is the strongest test you can write about a state machine**, because it
checks something no example-based test can: that *no path* reaches an invalid state.

## ⭐ Domain events, registered here

```
⭐ AbstractAggregateRoot: registerEvent(new BookingCancelledEvent(...)) inside cancel()
```

**⭐ Day 179's argument for registering in the aggregate rather than the service: the event is emitted
by the rule that caused it**, so a second caller who also cancels cannot forget it.

**⭐ And Day 179's boundary applies from today: the event is a notification, not orchestration.** If
you find a listener publishing another event, stop — that is control flow you cannot read, debug or
test.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Public setters on entities | ⭐ every rule is optional |
| ⭐ Business logic in services instead of entities | duplicated across callers; needs Spring to test |
| Constructors that allow invalid objects | validity checked at every use instead of once |
| ⭐ Primitives where value objects belong | rules scattered; unit mix-ups |
| Mutable embedded value objects | dirty-checking surprises (Day 162) |
| ⭐ Spring in the domain package | domain untestable without a context |
| ⭐ HTTP status codes in domain exceptions | the domain cannot be used off the web path |
| ⭐ Only testing the happy transitions | a removed guard is not caught |
| `EnumType.ORDINAL` | Day 158 — silent data reinterpretation |
| `final` entity class | lazy loading silently eager |
| Events published from services rather than aggregates | a second caller forgets |
| ⭐ Event chains | Day 179 — a distributed system inside one JVM |
