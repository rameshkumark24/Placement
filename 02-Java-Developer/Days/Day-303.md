# Day 303

**L-303** · Dependency injection by hand — then build the container

**Time:** 3 hrs · **Mode:** NEW

> **⭐ You have used `@Autowired` for 160 days. Today you write the thing that implements it — in
> about eighty lines — and discover that dependency injection is a two-line idea and the container is
> a convenience.**
>
> That matters for LLD interviews specifically: **there is no Spring on a whiteboard.** If your
> design only assembles itself when a framework is present, you cannot draw it.

# Part 1 — ⭐ DI is not DIP, and neither is a container

**⭐ Three things constantly conflated. Separate them once and the confusion ends.**

| | ⭐ What it is | ⭐ Needs a framework? |
|---|---|---|
| ⭐ **Dependency injection** | ⭐ **pass collaborators in; do not construct them inside** | ⭐ **no — it is `new`** |
| ⭐ **Dependency inversion (DIP)** | ⭐ **depend on an abstraction the caller's side owns** (Day 091, Day 300) | no |
| **A DI container** | a tool that does the wiring for you | ⭐ it *is* the framework |

```java
// ⭐ DI, with no framework whatsoever:
new ShipOrderService(orders, events, clock);

// ⭐ NOT DI — the dependency is welded in, and untestable:
class ShipOrderService {
    private final Orders orders = new JpaOrders();   // ⭐ ← this line is the whole problem
}
```

> **⭐ You can have DI with no inversion** (injecting a concrete `JpaOrders`) — useful but not
> flexible. **You can have inversion with no container** (Day 300's ports, wired by hand). **The
> container adds neither; it removes typing.**

## ⭐ What the container genuinely gives you

| Real benefit | ⭐ Worth it when |
|---|---|
| ⭐ **Transitive wiring** | ⭐ 200 beans deep — hand-wiring is genuinely painful |
| ⭐ **Lifecycle & scopes** | singleton, request, prototype — and proper shutdown |
| ⭐ **Proxies** | ⭐ `@Transactional`, `@Cacheable`, `@Async` (Day 137, Day 164) |
| Conditional wiring | profiles, `@ConditionalOnProperty` (Day 140) |
| ⭐ **Ecosystem** | ⭐ the real reason — everything Spring assumes it |

**⭐ And what it costs**, which is worth being able to state:

- ⭐ **Wiring errors move from compile time to startup time.** A missing constructor argument is a
  compiler error; a missing bean is a runtime failure — better than production, worse than the
  compiler.
- ⭐ **The object graph becomes invisible.** Nobody can point to where the application is assembled.
- ⭐ **It invites field injection**, which is the next section.

# Part 2 — ⭐⭐ Constructor injection, and why the alternatives are wrong

```java
@Service
class ShipOrderService {
    private final Orders orders;                 // ⭐ final
    private final DomainEvents events;
    ShipOrderService(Orders orders, DomainEvents events) {   // ⭐ no @Autowired needed since Spring 4.3
        this.orders = orders; this.events = events;
    }
}
```

| | ⭐ Constructor | Field (`@Autowired`) | Setter |
|---|---|---|---|
| ⭐ **Can be `final`** | ⭐ **yes — immutable, thread-safe** | ⭐ no | no |
| ⭐ **Usable without Spring** | ⭐ **yes — `new` it in a test** | ⭐ **no — needs reflection** | yes |
| ⭐ **Dependencies visible** | ⭐ **yes — the signature is the list** | ⭐ **no — hidden in the class body** | no |
| ⭐ **Too many deps is obvious** | ⭐ **yes — a painful constructor** | ⭐ **no — you can add the 15th quietly** | no |
| ⭐ **Circular deps** | ⭐ **fail at startup** | ⭐ **silently "work" — a half-built object** | silently work |
| Fully initialised object | ⭐ always | ⭐ **never guaranteed** | no |

**⭐ The strongest argument against field injection is not testability — it is that it hides the
design smell.** A class with eleven dependencies is a cohesion failure (Day 302). **A constructor
makes it hurt; a field annotation makes it invisible.**

⚠️ **Circular dependencies are the diagnostic that matters most.** Spring 2.6+ rejects them by
default, and the correct fix is almost never `@Lazy` — it is that **A and B want to be one thing, or
there is a third thing they both need.** The container is reporting a real design error; do not
silence it.

# Part 3 — ⭐⭐ Build the container

**⭐ Eighty lines, using Day 056A's reflection. Then you will never be mystified by a
`NoSuchBeanDefinitionException` again.**

```java
public class MiniContainer {

    private final Map<Class<?>, Object> singletons = new HashMap<>();
    private final Map<Class<?>, Class<?>> bindings = new HashMap<>();   // ⭐ port → adapter
    private final Set<Class<?>> underConstruction = new LinkedHashSet<>();

    public <T> void bind(Class<T> port, Class<? extends T> impl) { bindings.put(port, impl); }

    public <T> T get(Class<T> type) {
        Object existing = singletons.get(type);                          // ⭐ 1. singleton scope
        if (existing != null) return type.cast(existing);

        Class<?> impl = bindings.getOrDefault(type, type);               // ⭐ 2. resolve the binding
        if (impl.isInterface())
            throw new IllegalStateException("No binding for " + type.getName());   // ⭐ ← "No qualifying bean"

        if (!underConstruction.add(impl))                                // ⭐ 3. cycle detection
            throw new IllegalStateException("Circular dependency: " + underConstruction);

        try {
            Constructor<?> ctor = chooseConstructor(impl);               // ⭐ 4. which constructor?
            Object[] args = Arrays.stream(ctor.getParameterTypes())
                                  .map(this::get)                        // ⭐ 5. RECURSION — that is all wiring is
                                  .toArray();
            Object instance = ctor.newInstance(args);
            singletons.put(type, instance);
            return type.cast(instance);
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException("Cannot construct " + impl.getName(), e);
        } finally {
            underConstruction.remove(impl);
        }
    }

    private Constructor<?> chooseConstructor(Class<?> impl) {
        Constructor<?>[] ctors = impl.getDeclaredConstructors();
        if (ctors.length == 1) return ctors[0];                          // ⭐ Spring's exact rule
        return Arrays.stream(ctors).filter(c -> c.isAnnotationPresent(Inject.class))
                     .findFirst().orElseThrow(() -> new IllegalStateException("Ambiguous constructor"));
    }
}
```

```java
var c = new MiniContainer();
c.bind(Orders.class, JpaOrders.class);          // ⭐ this line IS your architecture
c.bind(Payments.class, StripePayments.class);
ShipOrderService svc = c.get(ShipOrderService.class);
```

**⭐ Five things this makes concrete, each of which you have hit in Spring:**

| In your container | ⭐ In Spring |
|---|---|
| `impl.isInterface()` throw | ⭐ **`NoSuchBeanDefinitionException`** — no implementation was registered |
| ⭐ **`underConstruction` set** | ⭐ the circular-reference error, and why `@Lazy` "fixes" it |
| `singletons` map | ⭐ the default singleton scope — one instance, shared, **so keep beans stateless** |
| ⭐ **Recursion in `get()`** | ⭐ **the entire dependency graph resolution** |
| `chooseConstructor` | ⭐ why one constructor needs no annotation and two need `@Autowired` |

**⭐ What you did NOT build, and what each is worth:** proxies (so no `@Transactional`), scopes beyond
singleton, ordered shutdown, conditional registration, and component scanning. **Component scanning
is the smallest of these and the one people think is the point.**

## ⭐ The composition root

> **⭐ Exactly one place in the application knows every concrete type. Everything else knows only
> interfaces.**

```java
// ⭐ Main.java — the composition root, hand-wired, no framework
public static void main(String[] args) {
    Clock clock       = Clock.systemUTC();
    Orders orders     = new JpaOrders(entityManager, new OrderMapper());
    Payments payments = new StripePayments(httpClient, apiKey);
    var placeOrder    = new PlaceOrderService(orders, payments, clock);
    new HttpServer(new OrderController(placeOrder)).start();
}
```

**⭐ Hand-wiring is genuinely viable up to a few dozen objects, and in an LLD interview it is
mandatory** — you will be asked to show how the pieces connect, and `@Autowired` is not an answer.

**⭐ The hybrid worth defending in a real system:** Spring wires the adapters and infrastructure,
**and one `@Configuration` class hand-constructs the application and domain objects with `new`.**

```java
@Configuration
class OrderWiring {                                    // ⭐ the composition root, kept visible
    @Bean PlaceOrder placeOrder(Orders orders, Payments payments, Clock clock) {
        return new PlaceOrderService(orders, payments, clock);   // ⭐ plain constructor — no annotations inside
    }
}
```

**⭐ The payoff: your application layer has zero Spring annotations**, so Day 300's dependency rule is
enforced by the fact that the domain and application packages do not even have Spring on the
classpath — **the strongest possible version of that rule.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Field injection | ⭐ **hides the smell, breaks `new`, hides cycles until runtime** |
| ⭐ Believing DI requires a container | ⭐ **you cannot design on a whiteboard** |
| Confusing DI with DIP | you inject concrete classes and call it inverted |
| ⭐ `@Lazy` to fix a circular dependency | ⭐ silences a real design error |
| ⭐ Stateful singletons | ⭐ one instance shared across every request — a race (Day 040s, B-06) |
| Injecting the container itself | service locator — dependencies invisible again |
| ⭐ No composition root | ⭐ nobody can say what the application is made of |
| Spring annotations in the domain | the framework is now in the stable core |
| ⭐ 11 constructor parameters treated as normal | ⭐ the compiler was telling you about cohesion |

## Interview questions

**Q: What is dependency injection, and does it need a framework?**
Passing collaborators in rather than constructing them inside. It is `new` — no framework required. A
container adds transitive wiring, scopes and proxies; it does not add DI. That distinction matters
because a design that only assembles under Spring cannot be drawn on a whiteboard or tested without a
context.

**Q: Is DI the same as the dependency inversion principle?**
No. You can inject a concrete class — that is DI without inversion. Inversion is about who owns the
abstraction: the interface belongs to the consumer's side, and the implementation depends on it.
That is what makes hexagonal architecture work, and it is independent of how the wiring happens.

**Q: Why constructor injection?**
Fields can be final, so objects are immutable and thread-safe; the object is fully initialised the
moment it exists; the dependency list is visible in the signature; circular dependencies fail at
startup instead of silently producing a half-built object; and the class can be instantiated with
`new` in a test. Most importantly it makes a class with eleven dependencies painful, which field
injection hides.

**Q: What happens when Spring finds a circular dependency, and how do you fix it?**
With constructor injection it fails at startup, which is correct. `@Lazy` or moving to setter
injection makes it start, but that silences a real error: usually A and B are one concept, or there
is a third thing both need. I would extract rather than annotate.

**Q: How would you wire this design without Spring?**
A composition root — one place, usually `main` or one `@Configuration` class, that constructs the
concrete types and passes them in. Everything else knows only interfaces. I sometimes keep that even
inside a Spring app so the application and domain layers carry no framework annotations at all.

## Mini task

1. **Write `MiniContainer`.** Make all three failures happen deliberately: no binding, a circular
   dependency, an ambiguous constructor. **Compare each message with Spring's.**
2. Add **prototype scope** via a marker annotation. Notice how little changes — and how much
   *lifecycle* you still have not implemented.
3. Take one Spring service, **`new` it in a test with hand-built dependencies.** If you cannot, find
   out why — that reason is a design defect.
4. **Grep for `@Autowired` on fields.** Convert them to constructors. **Note every class where the
   parameter count is embarrassing.**
5. Create a **`@Configuration` composition root** for one feature and remove `@Service`/`@Component`
   from its application classes. **Confirm the package no longer imports Spring at all.**
6. Deliberately introduce a circular dependency with fields, then with constructors. **Observe that
   one starts and one does not** — and reason about which failure you would rather have.
7. ⭐ Add a mutable field to a singleton `@Service`, hit it with 50 concurrent requests, and
   **reproduce the corruption.**
