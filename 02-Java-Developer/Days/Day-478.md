# Day 478

**L-478** · LLD round 2 — a notification service

**Time:** 3 hrs (45 min round + 2 hrs review) · **Mode:** DRILL · **⭐ LLD round 2 of 4**

> **⭐⭐ Every product eventually builds this, and almost every first version is a `NotificationService`
> with a switch on channel type, a hard-coded template and no retry — which is why it is such a good
> round: the naive design is obvious, and every requirement they add breaks it.**

> Today: channels as strategies, **templating and preferences as data rather than code**, delivery

# Part 2 — ⭐⭐ The core design (6–20)

```java
// ⭐⭐ The request is WHAT happened, not HOW to send it — this separation is the whole design
record NotificationRequest(
    String eventId,            // ⭐⭐ the idempotency key — supplied by the CALLER
    String userId,
    NotificationType type,     // ORDER_SHIPPED, PASSWORD_RESET, WEEKLY_DIGEST
    Map<String, Object> data   // ⭐ template variables, not rendered text
) { }

// ⭐ One channel, one implementation. Adding a channel adds a class.
interface NotificationChannel {
    Channel channel();
    DeliveryResult send(RenderedMessage msg, Recipient to);   // ⭐⭐ result, not void
}

// ⭐⭐ Templates are DATA, versioned, per type and per channel and per locale
interface TemplateRepository { Template find(NotificationType t, Channel c, Locale l); }
interface TemplateRenderer   { RenderedMessage render(Template t, Map<String,Object> data); }

// ⭐⭐ Preferences decide WHICH channels, and it is a policy of its own
interface PreferenceResolver { List<Channel> channelsFor(String userId, NotificationType type); }
```

| ⭐⭐ The three design points to say out loud | |
|---|---|
| ⭐⭐ **The caller says what happened, not how to notify** | ⭐⭐ otherwise every caller has to know about channels and preferences |
| ⭐⭐ **Templates are data, not string concatenation in code** | ⭐⭐ marketing changes copy weekly; **a deploy per copy change is the real cost** |
| ⭐⭐ **`send` returns a result, never `void`** | ⭐⭐ a `void` send cannot be retried, measured or dead-lettered |

```java
// ⭐ The orchestration — small, and it delegates everything
void notify(NotificationRequest req) {
    if (!dedupe.claim(req.eventId())) return;                 // ⭐⭐ idempotency, first
    for (Channel c : preferences.channelsFor(req.userId(), req.type())) {
        Template t = templates.find(req.type(), c, user.locale());
        outbox.enqueue(new SendJob(req.eventId(), c, renderer.render(t, req.data())));
    }
}
```

⚠️ **Note what is *not* in that method: no provider calls, no retries, no channel-specific branching.**
It resolves preferences, renders, and enqueues. **A method that resolves and delegates is the shape you
want** — the interviewer is watching whether the orchestrator stays small.

# Part 3 — ⭐⭐ The hard part: delivery (20–32)

```
⭐⭐ THE THREE THINGS THAT MAKE THIS A REAL DESIGN PROBLEM:
⭐ 1. ⭐⭐ IDEMPOTENCY — the caller retries, the queue redelivers.
⭐    ⇒ ⭐⭐ dedupe on (eventId, channel) with a unique constraint — ⭐ Day 407's inbox
⭐    ⇒ ⭐⭐ "the customer got the same email four times" is the classic production incident here
⭐ 2. ⭐⭐ RETRY — providers fail transiently, constantly.
⭐    ⇒ ⭐ exponential backoff + jitter, bounded attempts, ⭐⭐ then a DLQ WITH AN ALARM (Day 393)
⭐    ⇒ ⭐⭐ and retry is PER CHANNEL — email failing must not resend the SMS
⭐ 3. ⭐⭐ ISOLATION — one slow provider must not stop the others.
⭐    ⇒ ⭐⭐ a queue and a worker pool PER CHANNEL — the bulkhead (Day 340)
```

| ⭐ Failure classification, which people forget | |
|---|---|
| ⭐⭐ **Retryable** | ⭐ 5xx, timeout, 429 — **retry with backoff** |
| ⭐⭐ **Permanent** | ⭐⭐ invalid address, unsubscribed, hard bounce — **do NOT retry; mark the recipient** |
| ⭐ Ambiguous | ⭐⭐ a timeout after the provider accepted it — **it may have been sent** ⇒ this is why idempotency is on the *provider* call too, via a provider-side key |

> **⭐ The strongest sentence in this round: "a hard bounce must not be retried, and it must update the
> user's contact state — otherwise the same dead address is retried forever and your sender reputation
> degrades."** That is domain knowledge, not pattern knowledge, and it lands.

## ⭐ Rate limits and quiet hours

| Concern | ⭐ Design |
|---|---|
| ⭐ Provider rate limits | ⭐ a token bucket per channel (Day 313), shared across workers via Redis |
| ⭐⭐ **User-level throttling** | ⭐⭐ "at most 3 marketing emails a week" — **a policy, checked before enqueue** |
| ⭐ Quiet hours | ⭐⭐ **schedule rather than drop** — and never for transactional |
| ⭐⭐ **Transactional bypasses everything** | ⭐⭐ a password reset is not subject to marketing preferences — **say this explicitly** |

# Part 4 — ⭐⭐ The extensions (32–40)

| ⭐ Extension | ⭐ The good answer |
|---|---|
| ⭐⭐ **"The SMS provider is down for two hours."** | ⭐⭐ circuit breaker opens ⇒ **stop calling it**; messages queue rather than burn retries; **a fallback provider behind the same interface**, chosen by a routing policy |
| ⭐⭐ **"Add WhatsApp."** | ⭐⭐ **a new class implementing `NotificationChannel`, a new template row. No existing class edited.** |
| ⭐ "Users should get a digest instead of 40 emails." | ⭐ an aggregation window — **a scheduled batch job reading pending notifications**, not a change to send |
| ⭐ "We need delivery status from the provider webhook." | ⭐ status transitions on the notification record: `QUEUED → SENT → DELIVERED / BOUNCED` |
| ⭐⭐ **"Marketing wants A/B tests on subject lines."** | ⭐⭐ a template **variant** selected by a deterministic hash of the user id — deterministic so it is stable |

```
⭐⭐ THE MULTI-PROVIDER ANSWER, spelled out, because it is the discriminating one:
⭐   interface SmsProvider { ... }                 ⭐ Twilio, Vonage, a regional provider
⭐   ⭐⭐ SmsChannel holds a LIST of providers + a ROUTING POLICY
⭐   ⇒ ⭐ primary/failover · least-cost · per-country routing
⭐   ⇒ ⭐⭐ each wrapped in its own circuit breaker, ⭐ so one dead provider is routed around
⭐   ⇒ ⭐⭐ and the CHANNEL abstraction is unchanged — which is the proof the design was right.
```

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **A switch on channel type** | ⭐⭐ every new channel edits it |
| ⭐⭐ **Callers specifying the channel** | ⭐⭐ every caller now knows about preferences |
| ⭐⭐ **Templates as string concatenation** | ⭐⭐ a deploy for every copy change |
| ⭐ No locale in the template lookup | retrofitting i18n is expensive |
| ⭐⭐ **`void send(...)`** | ⭐⭐ cannot retry, measure or dead-letter |
| ⭐⭐ **No idempotency key** | ⭐⭐ "the customer got it four times" |
| ⭐ Deduping per event but not per channel | email suppresses the SMS |
| ⭐⭐ **Retrying a hard bounce** | ⭐⭐ forever, and it degrades sender reputation |
| ⭐ One shared queue for all channels | ⭐⭐ a slow provider blocks every channel |
| ⭐ No circuit breaker per provider | ⭐ retries burn against a dead endpoint |
| ⭐ Marketing preferences applied to a password reset | ⭐⭐ a support incident, and a real one |
| ⭐ Dropping messages in quiet hours | ⭐ schedule instead |
| Non-deterministic A/B assignment | a user flips variants between sends |

## Interview questions

**Q: What is the central abstraction here?**
That the caller says what happened, not how to notify. The request carries an event id, a user, a
notification type and a map of data — never a channel and never rendered text. Otherwise every calling
service has to know about channels, preferences and templates, and the notification logic ends up spread
across the whole codebase. The service resolves preferences to a set of channels, renders a versioned
template per channel and locale, and enqueues. Everything channel-specific lives behind one interface, so
adding WhatsApp is a new class and a new template row rather than an edit anywhere.

**Q: How do you make sure a user does not receive the same message twice?**
The caller supplies an event id, and I deduplicate on the pair of event id and channel with a unique
constraint — per channel, because otherwise a successful email suppresses the SMS. That is the inbox
pattern: the dedupe insert and the state change in one transaction, so redelivery is harmless. It matters
because delivery is at-least-once by construction — the caller retries, the queue redelivers, and the
worker can crash after sending but before acknowledging. "The customer got the same email four times" is
the canonical production incident in this system.

**Q: How do you handle provider failures?**
By classifying them first, which is the step people skip. Timeouts, 5xx and 429 are retryable, with
exponential backoff, jitter and a bounded attempt count before a dead letter queue that has an alarm on
it. Invalid addresses, unsubscribes and hard bounces are permanent — retrying those is not just wasted
work, it degrades your sender reputation, so the correct handling is to stop and update the recipient's
contact state. And there is an ambiguous class: a timeout after the provider already accepted the
message, which is why the provider call carries its own idempotency key too.

**Q: The SMS provider goes down for two hours. What happens?**
A circuit breaker per provider opens, so we stop burning retries against a dead endpoint, and messages
accumulate in the SMS queue rather than failing. Because each channel has its own queue and worker pool,
email and push are entirely unaffected — that isolation is the reason for the per-channel bulkhead rather
than one shared queue. And the real answer is a second provider behind the same interface with a routing
policy: primary and failover, or least cost, or per-country. The channel abstraction does not change at
all, which is the evidence the design was right.

**Q: How would you add a weekly digest instead of forty separate emails?**
As an aggregation window rather than a change to the send path. Notifications of digest-eligible types
are written as pending rather than dispatched, and a scheduled job groups them per user per window,
renders one digest template and sends that. The important part is that nothing in the channel or delivery
layer changes — it is a policy about when to dispatch, which is why preference resolution and dispatch
are separate concerns in the first place.
