# Part 1 — What CORS actually is

**The same-origin policy** is a browser rule: JavaScript on `https://app.acme.com` may not *read* the
response from `https://api.acme.com`. Origin = scheme + host + port; all three must match.

**Three facts that dissolve most confusion:**

1. **The request is still sent.** The browser makes the call, the server processes it, and the
   browser then refuses to hand the response to JavaScript. Your database write happened.
2. **CORS is the server *opting out*** of that restriction by sending `Access-Control-Allow-Origin`.
   It permits, it never restricts.
3. **⭐ Non-browser clients ignore all of it.** `curl`, Postman, your mobile app, a Python script —
   none of them implement the same-origin policy. **CORS provides exactly zero protection against
   any of them.**

> **The consequence:** if your API's protection is "we only allow our origin", you have no protection.
> Authentication and authorization protect your API. CORS decides which *browser pages* may read the
> response. They are unrelated concerns and confusing them is the root of every CORS security bug.

## The preflight

For anything beyond a "simple" request — any method other than GET/HEAD/POST, `Content-Type:
application/json`, or a custom header like `Authorization` — the browser first sends:

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://app.acme.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization
```

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.acme.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 3600                        ⭐ cache the preflight
```

**Effectively every JSON API call is preflighted**, because `Content-Type: application/json` is not
in the simple-request list. Without `Access-Control-Max-Age` that is **two round trips per request** —
on a mobile connection with 150 ms RTT, an extra 150 ms on every single call. Setting it to an hour
is one of the cheapest latency wins available.

# Part 2 — Configuring it, and the combination the browser refuses

```java
@Configuration
class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("https://app.acme.com", "https://admin.acme.com")  // ⭐ explicit
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("Authorization", "Content-Type", "X-Correlation-Id")
                .exposedHeaders("X-Correlation-Id", "X-RateLimit-Remaining", "ETag")  // ⭐
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

### ⭐ `exposedHeaders` — the one people always miss

**By default JavaScript can read only six response headers.** Everything else is invisible, including
`ETag`, `Location`, and your rate-limit headers. So Day 150's conditional GET silently cannot work
from a browser and Day 122's `X-RateLimit-Remaining` is unreadable — and the symptom is
`response.headers.get('ETag') === null` with no error anywhere.

If you set a header a browser client needs, you must list it in `exposedHeaders`.

### ⭐ The combination the browser rejects outright

```java
.allowedOrigins("*").allowCredentials(true)     // ❌ browser refuses, and rightly
```

The spec forbids it: wildcard origin with credentials would mean **any website could make
authenticated requests as your logged-in user and read the responses.** Browsers reject the
combination.

**And this is where the dangerous "fix" appears.** People work around it by reflecting the origin:

```java
.allowedOriginPatterns("*").allowCredentials(true)      // ❌❌ echoes Origin back
```

That echoes whatever `Origin` the request carried, which is *functionally identical* to the forbidden
combination — the browser accepts it because the header is not literally `*`. **`evil.com` can now
make credentialed requests as your logged-in user and read every response.** It is CSRF with response
reading, and Day 119's checklist lists it as a real finding.

**`allowedOriginPatterns` is legitimate for genuine patterns** — `https://*.acme.com`,
`http://localhost:[*]` in a dev profile. It is never legitimate as `*` with credentials.

### The `null` origin

`Origin: null` arrives from sandboxed iframes, `file://` pages and some redirects. **Never allow it**
— any attacker can produce a `null` origin from a sandboxed iframe, so allowing it is equivalent to
allowing everyone.

## Where to configure it

| Approach | Use |
|---|---|
| `WebMvcConfigurer` global | ⭐ the default — one policy, reviewable in one file |
| `@CrossOrigin` on a controller | ⚠️ scatters policy. Easy to miss in review |
| `CorsFilter` bean | needed when Spring Security is present — see below |
| **At the gateway/ingress** | ⭐ best for a fleet: one policy for every service |

### ⭐ With Spring Security, CORS must be explicitly enabled

```java
http.cors(withDefaults())      // ⭐ without this, preflight is rejected before MVC sees it
    .authorizeHttpRequests(a -> a.anyRequest().authenticated());
```

Day 145's diagram is the explanation. Security is a **filter**; CORS configured via
`WebMvcConfigurer` lives **inside** the DispatcherServlet. The `OPTIONS` preflight carries no
`Authorization` header — browsers never send credentials on a preflight — so Security rejects it with
a 401 before MVC's CORS handling is ever reached.

The browser then reports a generic CORS failure and everyone spends an afternoon adjusting CORS
config that was correct all along. `http.cors()` installs the CORS filter early in the chain so
preflight is answered before authentication.

**This is the single most common Spring CORS bug, and Day 145's diagram predicts it exactly.**

# Part 3 — Behind a reverse proxy

Every production deployment has a load balancer or ingress terminating TLS. To your application the
connection then looks like plain HTTP from an internal IP — which quietly breaks four things.

```yaml
server:
  forward-headers-strategy: framework       # ⭐ trust X-Forwarded-* / Forwarded
```

| Without it | Symptom |
|---|---|
| `Location` header (Day 146) | `http://10.0.3.14:8080/api/orders/42` — client follows it nowhere |
| `request.isSecure()` | false → `Secure` cookies dropped (Day 113) or a redirect loop |
| `request.getRemoteAddr()` | every request appears to come from the load balancer, so ⭐ **rate limiting by IP limits the entire internet as one client** (Day 122) |
| Generated URLs, springdoc server URL | all wrong |

**And the security caveat that must accompany it:** `X-Forwarded-For` is a header, so a client can
send one. If your application trusts it unconditionally, an attacker spoofs their IP and defeats
IP-based rate limiting and IP allow-lists.

**The rule: only trust forwarded headers from a trusted proxy**, and make sure the proxy *overwrites*
rather than appends the client-controlled value. `forward-headers-strategy: native` delegates to
Tomcat's `RemoteIpValve`, which supports an `internalProxies` regex — the right choice when you need
to be precise about which hops to trust.

**Related, and worth the one line:**

```yaml
server.tomcat.max-http-form-post-size: 2MB
server.max-http-request-header-size: 8KB      # ⭐ bounded — a large JWT plus cookies gets close
spring.servlet.multipart.max-file-size: 10MB  # Day 126
```

A 431 on requests with many cookies and a big JWT is a real production surprise; the default header
limit is 8 KB and a token plus session cookies can exceed it.

### The build

An `/api/v1/orders` service with:

1. `POST /api/v1/orders` — validated request DTO, **201 + `Location`** via `UriComponentsBuilder`
2. `GET /api/v1/orders/{id}` — **ETag + `If-None-Match` → 304**
3. `PUT /api/v1/orders/{id}` — **required `If-Match` → 412** on mismatch
4. `GET /api/v1/orders` — `Slice`, capped page size, **allow-listed sort with a unique tie-break**
5. `DELETE /api/v1/orders/{id}` — **204**
6. `GET /api/v1/orders/export` — `StreamingResponseBody`, NDJSON
7. One `@RestControllerAdvice` producing **RFC 7807** for all seven failure classes, with a
   correlation ID on 500
8. A `OncePerRequestFilter` for correlation IDs that **clears the MDC in a `finally`**
9. An outbound `RestClient` with **all four timeouts**, jittered retry, and correlation-ID
   propagation
10. Jackson configured against **all four of Day 106's hazards**
11. CORS for one explicit origin, with `exposedHeaders` for `ETag`, and `http.cors()` if Security is
    present
12. springdoc with documented error responses, **disabled in production**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Believing CORS protects the API | `curl` ignores it entirely |
| `allowedOriginPatterns("*")` + credentials | any site can act as your logged-in user and read responses |
| Allowing `Origin: null` | trivially forged from a sandboxed iframe |
| Forgetting `exposedHeaders` | `ETag` and rate-limit headers invisible to JS, silently |
| No `maxAge` | a preflight round trip on every request |
| ⭐ Forgetting `http.cors()` with Security | preflight 401s; the CORS config was never the problem |
| `@CrossOrigin` scattered on controllers | no single place to review the policy |
| No `forward-headers-strategy` | broken `Location`, dropped `Secure` cookies, rate limiting by the LB's IP |
| Trusting `X-Forwarded-For` from anywhere | spoofed IPs defeat rate limits and allow-lists |

## Interview questions

**Q: Is CORS a security feature?**
Not for the server. It is a browser mechanism, and it *relaxes* the same-origin policy rather than
enforcing anything. The request still reaches my server and is still processed; the browser just
withholds the response from JavaScript. Any non-browser client ignores it completely, so
authentication and authorization are what protect the API.

**Q: Why does the browser reject wildcard origin with credentials?**
Because it would let any website make authenticated requests as the logged-in user and read the
responses. The dangerous workaround is reflecting the `Origin` header back, which is functionally the
same thing while passing the browser's check.

**Q: CORS is configured correctly and preflight still 401s. Why?**
Spring Security is a servlet filter and runs before the DispatcherServlet, and the preflight `OPTIONS`
carries no credentials, so Security rejects it before MVC's CORS handling. `http.cors()` installs the
CORS filter early in the chain.

**Q: What breaks behind a load balancer?**
`Location` headers point at internal addresses, `isSecure()` is false so `Secure` cookies are dropped,
and `getRemoteAddr()` returns the balancer — which makes IP rate limiting treat the whole internet as
one client. `forward-headers-strategy` fixes it, but only trusted proxies may be believed.

## Mini task

The exit gate above **is** the mini task. Additionally:

1. Serve a page from `http://localhost:3000` that fetches your API on `:8080`. Watch it fail in the
   console — then `curl` the same endpoint and confirm it succeeds. **That contrast is the day.**
2. Configure CORS. Watch the preflight in the Network tab. Add `maxAge` and watch it disappear.
3. Try to read `ETag` from JavaScript. Fail. Add `exposedHeaders`. Succeed.
4. Add Spring Security without `http.cors()`. Reproduce the 401 preflight. Fix it.
5. Put nginx in front, confirm `Location` points at `localhost:8080`, then set
   `forward-headers-strategy: framework`.
6. Send a spoofed `X-Forwarded-For` and confirm your rate limiter believes it.

## 🎙️ Articulation drill

Two minutes: **"Explain CORS."**

Lead with what it is *not* — it does not protect your server, and `curl` ignores it. Then what it is:
a browser mechanism where the server opts out of the same-origin restriction for named origins. Cover
the preflight and why caching it matters, then the two failures that show real experience: exposed
headers, because otherwise the browser silently cannot read your ETag, and the Spring Security
ordering, because a preflight carries no credentials and gets rejected by a filter before your
perfectly correct CORS config is ever consulted.
