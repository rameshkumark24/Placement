## ⭐ Problem A (target: 15 minutes)

> **Given a string containing only `(`, `)`, `{`, `}`, `[` and `]`, determine whether the brackets are
> correctly balanced and correctly nested.**

| ⭐ What is tested | |
|---|---|
| ⭐⭐ **Recognising the stack immediately** | ⭐ "nesting" is the tell, always |
| ⭐⭐ **The two failure cases people forget** | ⭐⭐ a closing bracket on an **empty** stack, and a **non-empty stack at the end** |
| ⭐ Clean mapping | ⭐ push the *expected closer* rather than the opener — one comparison, no map lookup at close |

```java
Deque<Character> st = new ArrayDeque<>();
for (char c : s.toCharArray()) {
    switch (c) {
        case '(' -> st.push(')');
        case '[' -> st.push(']');
        case '{' -> st.push('}');
        default  -> { if (st.isEmpty() || st.pop() != c) return false; }  // ⭐⭐ empty check FIRST
    }
}
return st.isEmpty();                       // ⭐⭐ the case people forget: "((("
```

## ⭐⭐ Problem B (target: 30 minutes)

> **Design and implement an LRU cache with `get(key)` and `put(key, value)`, both in O(1) average time.
> The cache has a fixed capacity; inserting beyond it evicts the least recently used entry.**

| ⭐ The arc | |
|---|---|
| ⭐⭐ 1. **State the requirement that forces the design** | ⭐⭐ O(1) get *and* O(1) eviction ⇒ **a map alone is not enough** |
| ⭐⭐ 2. **HashMap + doubly linked list** | ⭐⭐ map for lookup, list for recency order; **the map stores node references** |
| ⭐ 3. Sentinel head and tail nodes | ⭐⭐ removes every null check from the pointer surgery |
| ⭐ 4. `get` must also **promote** | ⭐ a read changes recency — easy to forget |
| ⭐ 5. `put` on an existing key updates **and** promotes | ⭐ does not evict |

```java
class Node { int k, v; Node prev, next; }

private final Map<Integer, Node> map = new HashMap<>();
private final Node head = new Node(), tail = new Node();   // ⭐⭐ sentinels — no null checks anywhere
{ head.next = tail; tail.prev = head; }

public int get(int key) {
    Node n = map.get(key);
    if (n == null) return -1;
    moveToFront(n);                       // ⭐⭐ a READ changes recency — the commonly missed line
    return n.v;
}

public void put(int key, int value) {
    Node n = map.get(key);
    if (n != null) { n.v = value; moveToFront(n); return; }   // ⭐ update, no eviction
    if (map.size() == capacity) {
        Node lru = tail.prev;
        remove(lru); map.remove(lru.k);   // ⭐⭐ remove from BOTH — the classic leak
    }
    Node fresh = new Node(); fresh.k = key; fresh.v = value;
    map.put(key, fresh); addFront(fresh);
}
```

| ⭐⭐ The five bugs to expect | |
|---|---|
| ⭐⭐ **`get` not promoting** | ⭐⭐ it is an LRU, and a read counts as a use |
| ⭐⭐ **Evicting from the list but not the map** | ⭐⭐ an unbounded map — the leak |
| ⭐ Not using sentinels | ⭐ null checks everywhere, and a bug in one of them |
| ⭐ `put` on an existing key triggering eviction | ⭐ capacity never actually exceeded |
| ⭐ Storing values in the map instead of nodes | ⭐⭐ then you cannot unlink in O(1) |

> **⭐ Say the design sentence aloud: "A hash map gives O(1) lookup but no order. A linked list gives O(1)
> removal from anywhere but no lookup. Combining them — the map's values are list nodes — gives both,
> which is why this exact pair is the answer."** **That framing is what they want to hear** (Day 313).

## Interview questions

**Q: Design an LRU cache.**
The requirement that forces the design is constant-time get and constant-time eviction together. A hash
map gives O(1) lookup but has no order, and a doubly linked list gives O(1) removal from anywhere but no
lookup — so you combine them, with the map's values being list nodes rather than raw values, which is what
lets you unlink in constant time. I use sentinel head and tail nodes so there are no null checks in the
pointer surgery. The two things people miss: get has to promote, because a read is a use in an LRU, and
eviction has to remove from both structures or the map grows without bound.

**Q: What did five recorded mocks tell you?**
More than fifty more problems would have. Aggregating the same ten criteria across all five and reading
the row totals rather than the mock totals shows habits rather than bad days — and the habit that costs
most people the round is not algorithmic. It is stating the approach and its complexity before coding,
explicitly checking that approach with the interviewer, and testing your own code before being asked.
Those three rows are worth more marginal points than any additional pattern I could learn in a month.

**Q: You solve the problem but always at minute forty-four. Is that a pass?**
Usually not, because there is no time left to test, state complexity or discuss improvements — and those
are scored. The diagnosis is pacing rather than knowledge, and the fix is mechanical: cap the approach
block at eight minutes and start coding on time even if the approach is not perfect, because an
imperfect approach discussed at minute six is recoverable and a perfect one reached at minute twenty is
not.

**Q: What do you do in the last two weeks?**
Not new problems. One timed, recorded mock every two days; re-solving the problems I previously got
wrong, since those are the ones with information in them; twenty to thirty minutes a day writing Java in
a plain editor so syntax fluency does not eat my clock; and re-reading my pattern journal rather than
editorials. The journal has three columns — the tell in the wording, the technique, and the specific
mistake I made — and the third column is the only part that is actually about me.

**Q: How do you know whether your problem is knowledge or delivery?**
The row totals separate them cleanly. If I cannot find the approach at all, that is a genuine knowledge
gap and the fix is twenty targeted problems in that family — but it is the rarest outcome. If I find the
approach and still score badly, it is delivery: coding before narrating, never testing, or going silent
when stuck. Those look identical from the inside, which is exactly why the recording matters — you cannot
diagnose your own delivery without watching it.

## Mini task

1. ⭐⭐ Run **mock 5 cold**, without reading the problems first. Recorded, 45 minutes.
2. ⭐⭐ Build the **aggregate table** across all five mocks. Total each row.

   strangers.

## 🎙️ Articulation drill

**Five minutes:** record a spoken debrief of your own five mocks, as if reporting to a mentor.

**⭐ Structure it as evidence, not feelings: "Across five mocks my two lowest rows were stating the
approach before coding — three out of ten — and testing my own code, two out of ten. My highest was
finishing in time. So my problem is not algorithms; twice I had the right approach by minute five and
still lost the round by coding immediately and never testing."**

**⭐ Then the plan, specific and mechanical: "The fixes are behavioural. I do not touch the keyboard until
minute six, and I set an alarm at minute thirty to force the test block. I am re-solving the six problems
I got wrong rather than starting new ones, and I have two mocks booked with people I do not know, because
I score noticeably worse when someone is actually watching."**

**⭐ That debrief — evidence, diagnosis, mechanical fix — is also exactly the shape of a good engineering
post-mortem, which is not a coincidence.**
