**L-191** · `EXPLAIN ANALYZE` — reading a plan like a diagnosis

**Time:** 3+ hrs · **Mode:** NEW · **Marquee day**

> three slow queries, diagnose and fix them live" — and every one of those diagnoses starts here.
>
> D-12 covered query processing in principle. Today is reading the actual output: what each number
> means, which one to look at first, and the five patterns that account for nearly every slow query
> you will ever meet.

---

# Part 1 — The command, and the options that matter

```sql
explain (analyze, buffers, verbose, settings) select ...;
```

| Option | Gives you |
|---|---|
| *(none)* | ⭐ the **estimated** plan. Does not run the query |
| ⭐ `analyze` | ⭐ **actually runs it** and reports real times and row counts |
| ⭐ `buffers` | ⭐ **page reads — the real measure of work** |
| `verbose` | output columns, schema-qualified names |
| `settings` | non-default settings affecting the plan |
| `wal` | WAL generated (for writes) |

**⭐ Always `(analyze, buffers)`.** Estimates alone tell you what PostgreSQL *believed*; you need what
happened.

> ⚠️ **`EXPLAIN ANALYZE` executes the query.** On an `UPDATE` or `DELETE` that means it really
> updates or deletes. Wrap it: `begin; explain (analyze) delete ...; rollback;`

# Part 2 — ⭐ Reading a plan

```
Nested Loop  (cost=0.72..1284.51 rows=100 width=64) (actual time=0.045..812.334 rows=98234 loops=1)
  Buffers: shared hit=284512 read=1893
  ->  Seq Scan on customers c  (cost=0.00..421.00 rows=1 width=32)
                               (actual time=0.011..8.234 rows=982 loops=1)
        Filter: (country = 'UK'::text)
        Rows Removed by Filter: 19018
  ->  Index Scan using ix_orders_customer on orders o
                               (cost=0.43..8.45 rows=100 width=32)
                               (actual time=0.005..0.712 rows=100 loops=982)
        Index Cond: (customer_id = c.id)
Planning Time: 0.412 ms
Execution Time: 823.115 ms
```

**⭐ Read it inside-out and bottom-up.** The innermost, most-indented nodes run first and feed their
parents.

| Field | Meaning |
|---|---|
| `cost=0.72..1284.51` | ⭐ estimated startup..total, in arbitrary units. **Only useful for comparison** |
| ⭐ `rows=100` vs `rows=98234` | ⭐⭐ **estimated vs ACTUAL. THE most important comparison** |
| `actual time=0.045..812.334` | ⭐ startup..total **per loop**, in ms |
| ⭐ `loops=982` | ⭐ **how many times this node ran** |
| `Buffers: shared hit / read` | ⭐ pages from cache / from disk |
| `Rows Removed by Filter` | ⭐ rows read and thrown away — wasted work |

## ⭐⭐ The three rules for reading any plan

> **Rule 1 — Find the largest gap between estimated and actual rows. Start there.**

Above: `rows=1` estimated, `rows=982` actual on the customers scan. **A 982× underestimate.** Every
decision above it was made on that fiction — which is why the planner chose a nested loop.

> **Rule 2 — ⭐ Multiply by `loops`.**

The index scan shows `actual time=0.005..0.712` and `loops=982`. **The real cost is 0.712 × 982 ≈
699 ms**, not 0.712 ms. **This is the single most misread number in `EXPLAIN` output** — people see a
sub-millisecond inner node and look elsewhere while it is 85% of the runtime.

> **Rule 3 — `Buffers` is the truth about how much work happened.**

`shared hit=284512` is 284,512 page reads — over 2 GB of pages touched. **Buffer counts are stable
across runs; timings are not**, so buffers are the right metric when comparing two plans.

# Part 3 — ⭐ The node types

## Scans

| Node | Meaning | Concern |
|---|---|---|
| **Seq Scan** | reads every page | ⭐ fine on small tables and high-selectivity queries; a problem otherwise |
| **Index Scan** | index → heap, row by row | ⭐ good for few rows; **random I/O** if many |
| **Index Only Scan** | ⭐ no heap fetch | ⭐ best. Watch `Heap Fetches` (Day 189) |
| **Bitmap Heap Scan** | ⭐ collect ctids, sort, read pages in order | ⭐ **the middle ground** — see below |

**⭐ The bitmap scan is the one people do not understand and it is the planner being clever.** For a
medium number of rows — too many for random single-row fetches, too few for a full scan — PostgreSQL
builds a bitmap of matching pages, sorts it, and reads the heap **sequentially**. It converts random
I/O into sequential I/O.

```
Bitmap Heap Scan on orders  (actual rows=48213 loops=1)
  Recheck Cond: (status = 'PENDING')
  ⭐ Heap Blocks: exact=2841
  ->  Bitmap Index Scan on ix_orders_status  (actual rows=48213 loops=1)
```

⚠️ **`Heap Blocks: lossy=N` means `work_mem` was too small** to hold the exact bitmap, so PostgreSQL
degraded to page-level granularity and must recheck every row on those pages. **Lossy blocks are a
`work_mem` signal**, and one of the easiest wins in a plan.

## Joins — Day 192's subject, in summary

| Node | Good when |
|---|---|
| **Nested Loop** | ⭐ outer side is *small* and inner is indexed |
| **Hash Join** | ⭐ one side fits in `work_mem` |
| **Merge Join** | both sides already sorted |

**⭐ A nested loop with a large outer side is the classic disaster plan**, and it is almost always
caused by a row underestimate (Rule 1).

## The nodes that signal a problem

| Node | Meaning |
|---|---|
| ⭐ **Sort** with `Sort Method: external merge Disk: 45MB` | ⭐ **spilled to disk — raise `work_mem`** |
| ⭐ **Hash** with `Batches: 8` | ⭐ **spilled — should be `Batches: 1`** |
| **Materialize** | caching an inner result — often a nested-loop smell |
| ⭐ **Rows Removed by Filter: 4821934** | ⭐ **read 5M rows to return 12. A missing index** |
| **Subplan / correlated subquery** | ⭐ runs per outer row — often rewritable as a join |
| ⭐ **Nested Loop** with high `loops` | Rule 2 — this is your time |

```
Sort  (actual time=1823.4..2104.9 rows=1284000 loops=1)
  Sort Key: placed_at DESC
  ⭐ Sort Method: external merge  Disk: 45280kB
```

**⭐ `external merge` means the sort did not fit in `work_mem` and went to disk.** Raising `work_mem`
for that query is often a 10× improvement — and it is a **per-operation, per-connection** setting, so
`work_mem = 256MB` globally with 100 connections and 3 sorts each is 75 GB of potential allocation.
**Set it per session or per role, not globally.**

# Part 4 — ⭐⭐ The five patterns, and the workflow

### ⭐ Pattern 1 — Row misestimate → wrong join

```
->  Seq Scan on customers  (rows=1) (actual rows=982 loops=1)     ⭐ 982× off
Nested Loop ... loops=982
```
**Causes:** stale statistics (Day 189 #6), correlated columns (Day 190's extended statistics), or a
predicate the planner cannot estimate — a function result, a `jsonb` extraction.
**Fixes:** `ANALYZE`; `CREATE STATISTICS`; raise `default_statistics_target` for that column.

### ⭐ Pattern 2 — Sequential scan on a large table

```
Seq Scan on orders (actual rows=48 loops=1)
  Filter: (lower(email) = 'a@b.com')
  ⭐ Rows Removed by Filter: 9999952
```
**Cause:** Day 189's eight. Here, a function on the column.
**Fix:** the expression index.

### ⭐ Pattern 3 — Sort or hash spilling to disk

```
Sort Method: external merge  Disk: 128MB
```
**Fix:** raise `work_mem` **for that query**; or make the index provide the order (Day 190's rule 3);
or reduce the row count earlier.

### ⭐ Pattern 4 — The correlated subquery

```
SubPlan 1
  ->  Aggregate (actual time=0.087..0.087 rows=1 ⭐ loops=100000)
```
**100,000 loops × 0.087 ms = 8.7 seconds** — Rule 2 again.
**Fix:** rewrite as a join or a lateral join.

```sql
-- ❌ per-row subquery
select c.*, (select count(*) from orders o where o.customer_id = c.id) from customers c;
-- ⭐ one aggregate
select c.*, coalesce(o.cnt,0) from customers c
left join (select customer_id, count(*) cnt from orders group by 1) o on o.customer_id = c.id;
```

### ⭐ Pattern 5 — `LIMIT` that does not limit

```
Limit (actual time=8234..8234 rows=20 loops=1)
  ->  Sort (actual rows=2000000 loops=1)          ⭐ sorted 2M rows to return 20
```
**Fix:** Day 190's rule 3 — an index providing the sort order, so `LIMIT` stops after 20 entries.
**This is also Day 152's pagination argument**, seen from the plan side.

## ⭐ The workflow

```
1. explain (analyze, buffers)
2. ⭐ Find the biggest estimated-vs-actual gap → often the whole diagnosis
3. ⭐ Multiply every node's time by its loops → find where the time REALLY is
4. Look for: Seq Scan on big tables · Rows Removed by Filter · Disk spills · high loops
5. Form ONE hypothesis. Change ONE thing.
6. Re-run. Compare BUFFERS, not just time.
7. Repeat.
```

**⭐ Step 5 is the discipline that separates diagnosis from flailing.** Day 099's debugging
methodology, applied to queries: one hypothesis, one change, one measurement.

## Tools and settings

```sql
-- ⭐ paste plans into explain.dalibo.com or explain.depesz.com — they highlight the hot node
set work_mem = '256MB';                          -- ⭐ session only
set enable_seqscan = off;                        -- ⭐ DIAGNOSTIC ONLY — never in production
```

**`enable_seqscan = off` is a question, not a fix**: "what would the planner do if it had to use the
index, and would it actually be faster?" If the forced plan is faster, your statistics or cost
settings are wrong — that is the finding, not the remedy.

```sql
auto_explain.log_min_duration = '1s'             -- ⭐ log plans for slow queries automatically
auto_explain.log_analyze = on
```

**⭐ `auto_explain` captures the plan of the slow query *as it happened in production*** — with real
parameters and real data. That is far more useful than reproducing it later, because the plan may
differ.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| `EXPLAIN` without `ANALYZE` | estimates only — you learn what it believed, not what happened |
| ⭐ Ignoring `loops` | the 0.7 ms node is 700 ms |
| ⭐ Ignoring estimated-vs-actual | miss the actual root cause |
| Comparing costs across queries | cost units are only comparable within one plan |
| Comparing times, not buffers | timings vary with cache state |
| Missing `external merge`/`Batches: 8` | an easy 10× left on the table |
| ⭐ `work_mem` raised globally | per-operation, per-connection — memory exhaustion |
| Leaving `enable_seqscan = off` on | it is a diagnostic |
| ⭐ Changing several things at once | you learn nothing |
| `EXPLAIN ANALYZE` on a `DELETE` without a transaction | it really deletes |
| Not using `auto_explain` | you never see the production plan |

## Interview questions

**Q: Walk me through diagnosing a slow query.**
`EXPLAIN (ANALYZE, BUFFERS)`. First I compare estimated to actual rows and find the biggest
divergence, because if the planner was wrong about row counts every choice above that node was made
on bad information. Then I multiply each node's time by its loop count to find where the time
actually is — an inner node showing 0.7 ms with 1,000 loops is 700 ms. Then I look for sequential
scans on large tables, large `Rows Removed by Filter`, and disk spills. One hypothesis, one change,
re-measure with buffers.

**Q: What is the most misread number in a plan?**
`actual time` on an inner node, because it is per loop. With `loops=982` a sub-millisecond node can
be most of the runtime, and people look elsewhere.

**Q: What does `Sort Method: external merge` mean?**
The sort exceeded `work_mem` and spilled to disk. Raising `work_mem` for that query often gives a
large win — but it is per operation per connection, so I set it on the session or the role, never
globally, or a hundred connections running three sorts each can exhaust memory.

**Q: What is a bitmap heap scan?**
The middle ground between an index scan and a sequential scan. For a medium number of matching rows
PostgreSQL collects the row locations into a bitmap, sorts it, and reads the heap in physical order —
converting random I/O into sequential. If it reports lossy heap blocks, `work_mem` was too small to
hold the exact bitmap.

**Q: Why compare buffers rather than execution time?**
Timings depend on cache state, so the second run of a query is always faster and tells you nothing.
Buffer counts are the amount of work done and are stable across runs.

## Mini task

**Build a 5M-row dataset. Every exercise is on real volume.**

1. `explain (analyze, buffers)` on a simple query. **Identify every field in the output** and say what
   it means.
2. **Reproduce all five patterns deliberately.** For each: capture the plan, name the giveaway, apply
   one fix, and compare buffers before and after.
3. Build a query with a nested loop whose inner node shows `loops > 1000`. **Compute the real cost by
   hand**, then confirm against total execution time.
4. Bulk-load 2M rows without `ANALYZE`. Capture the misestimate. `ANALYZE`. Capture again.
5. Force a disk sort with `work_mem = '64kB'`. Find `external merge`. Raise it and compare.
6. Find a query producing `Heap Blocks: lossy`. Raise `work_mem` until it is exact.
7. Write the correlated-subquery version and the join version of the same result. Compare plans,
   loops, buffers and time.
8. Write `order by ... limit 20` with and without a supporting index. **Find the 2M-row sort.**
9. `set enable_seqscan = off` on a query the planner seq-scans. Is the forced plan faster? **What does
   the answer tell you?**
10. Enable `auto_explain` with a 100 ms threshold. Run a mixed workload and read the captured plans.
11. Paste your worst plan into explain.dalibo.com and compare its diagnosis to yours.

## 🎙️ Articulation drill

Three minutes, with a real plan in front of you: **"Diagnose this query."**

Narrate the process, not the conclusion. Read inside-out. Say which node you are looking at and why.
Call out the estimated-versus-actual gap first and explain why it dominates everything above it.
Multiply by loops out loud. Name your single hypothesis, the single change you would make, and what
number you would expect to move. **Being able to say "I would change this one thing and expect
buffers to drop from 280,000 to about 400" is the answer that gets the offer.**
