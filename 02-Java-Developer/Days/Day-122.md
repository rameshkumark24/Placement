# Day 122 ⭐

**L-122** · Rate limiting — fixed window, sliding window, token bucket, leaky bucket

**Time:** 3 hrs · **Mode:** NEW · **Marquee day**

> A favourite system-design question, and one where most answers stop at "use a counter" — which has
> a specific, well-known flaw. Today: the four algorithms, why the naive one fails at window
> boundaries, and what changes when you have more than one server.
>
> You already built one test-first on Day 098. Today is the theory behind it.

# Part 1 — Why rate limit

| Purpose | Example |
|---|---|
| **Protect capacity** | One client cannot exhaust the database connection pool |
| **Prevent abuse** | Brute force (Day 111), scraping, spam |
| **Fairness** | One tenant cannot starve the others (Day 118) |
| **Cost control** | Each request costs money — LLM tokens, third-party API calls |
| **Contractual tiers** | Free: 100/hour. Pro: 10,000/hour. |
| **Cascade prevention** | Shed load before the system collapses |

**The last one is the most important and the least understood.** Under overload, an unprotected
system does not degrade — it *collapses*: queues grow, latency rises, timeouts fire, clients retry,
load increases further. **Rejecting 10% of requests quickly is far better than serving 100% of them
too slowly to be useful.** That is load shedding, and rate limiting is its front line.

## What to key on

```
Per IP            crude — NAT means thousands share one; IPv6 makes it meaningless
Per user          ✅ the right unit for authenticated traffic
Per API key       ✅ for third parties (Day 115b)
Per tenant        ✅ for multi-tenant fairness
Per endpoint      login and search need far tighter limits than a health check
Global            a backstop for total capacity
Composite         ⭐ several at once — the usual production answer
```

**Real systems apply several simultaneously:** per-user *and* per-IP *and* per-endpoint *and*
global. A generous per-user limit stops abuse by one account; a per-IP limit stops a botnet creating
accounts; a global limit protects the system when both are bypassed.

⚠️ **Never rate limit on `X-Forwarded-For` without validating it** (Day 105) — a client can set any
value and bypass the limit entirely. Trust only the hop your own proxy appends, and configure how
many proxies are in front of you.

# Part 2 — The four algorithms

## 1. Fixed window — simple, and broken at the boundary

```java
String key = "rl:" + userId + ":" + (now.getEpochSecond() / 60);   // one bucket per minute
long count = redis.incr(key);
if (count == 1) redis.expire(key, 60);
if (count > limit) reject();
```

✅ Trivial, O(1), tiny memory.
❌ **The boundary problem**, which is the flaw you must be able to name:

```
Limit: 100 per minute

10:00:59 → 100 requests   (window 10:00 — allowed)
10:01:00 → 100 requests   (window 10:01 — allowed)

⇒ 200 requests in ONE SECOND, and the limiter is behaving exactly as specified.
```

**Effectively double the intended rate, in a burst, across every window boundary.** Everything else
below exists because of this.

## 2. Sliding window log — precise, and expensive

```java
long now = System.currentTimeMillis();
redis.zremrangeByScore(key, 0, now - windowMs);        // drop entries outside the window
long count = redis.zcard(key);
if (count >= limit) reject();
redis.zadd(key, now, UUID.randomUUID().toString());     // record this request
redis.expire(key, windowSeconds);
```

✅ **Exactly correct** — a true sliding window, no boundary artefact.
❌ **Stores one entry per request.** A limit of 10,000/hour means up to 10,000 entries per user.
Memory and `ZREMRANGEBYSCORE` cost scale with the limit, not with the number of users.

Correct for low limits (login attempts: 5 per 15 minutes). Unusable for high ones.

## 3. ⭐ Sliding window counter — the practical answer

Interpolate between the previous and current fixed windows:

```java
long windowStart = now - (now % windowMs);
double elapsed = (now - windowStart) / (double) windowMs;    // 0.0 → 1.0 through the window

long current  = redis.get("rl:" + id + ":" + windowId);
long previous = redis.get("rl:" + id + ":" + (windowId - 1));

double estimated = previous * (1 - elapsed) + current;
if (estimated >= limit) reject();
redis.incr("rl:" + id + ":" + windowId);
```

```
At 30 seconds into the current minute:
   previous window had 80,  current has 40
   estimate = 80 × 0.5 + 40 = 80        ← the previous window still counts, weighted
```

✅ **Fixed-window memory (two counters) with near-sliding-window accuracy.** Cloudflare's published
analysis found the error under 1% on real traffic.
❌ Assumes requests were uniformly distributed within the previous window.

> **This is what most production systems use**, and it is the right answer to give first.

## 4. ⭐ Token bucket — the one that allows bursts

```java
class TokenBucket {
    private final long capacity;         // burst size
    private final double refillPerSec;   // sustained rate
    private double tokens;
    private long lastRefill;

    synchronized boolean tryConsume(long n) {
        long now = System.nanoTime();
        double elapsed = (now - lastRefill) / 1e9;
        tokens = Math.min(capacity, tokens + elapsed * refillPerSec);   // ← LAZY refill
        lastRefill = now;
        if (tokens >= n) { tokens -= n; return true; }
        return false;
    }
}
```

**The two parameters are independent, and that is the point:**

- **Capacity = burst tolerance.** How many requests can arrive at once.
- **Refill rate = sustained throughput.** The long-run average.

```
capacity 100, refill 10/s
⇒ idle for 10 s, then 100 requests instantly ✅, then 10/s sustained
```

**This matches real client behaviour.** An application that is quiet then does a page-load burst of
20 parallel requests is normal, not abusive. Fixed and sliding windows punish it; a token bucket
accommodates it while still capping the average.

✅ Smooth, burst-friendly, O(1), tiny state — two numbers per key.
❌ Two parameters to tune rather than one.

**The lazy refill is worth noticing**: no background thread, no timer. Tokens are computed from
elapsed time on access, which is what makes it cheap enough to run per-user at scale. And it is
naturally suited to **weighted costs**:

```java
bucket.tryConsume(1);      // a cheap read
bucket.tryConsume(50);     // an expensive report — costs 50 tokens
```

## 5. Leaky bucket — output smoothing

```
Requests → [ queue ] → processed at a CONSTANT rate → downstream
                       overflow ⇒ rejected
```

Token bucket limits the **input** rate and permits bursts. Leaky bucket enforces a **constant output**
rate — the downstream never sees a burst at all.

Use it when the thing you are protecting cannot tolerate bursts: a legacy system, a third-party API
with a strict per-second cap, or an SMS gateway. The cost is queueing latency, and the queue must be
bounded (Day 070's backpressure).

## Choosing

| Need | Algorithm |
|---|---|
| Simplest possible, boundary burst acceptable | Fixed window |
| Exact enforcement, small limits (login) | Sliding window log |
| **General API rate limiting** | ⭐ **Sliding window counter** |
| **Burst tolerance with a sustained cap** | ⭐ **Token bucket** |
| Protecting a burst-intolerant downstream | Leaky bucket |

# Part 3 — Distributed rate limiting

Everything above is trivial on one server. With N servers, a per-server limit of `L/N` fails: load
balancing is not perfectly even, and a server that is down leaves its share unused.

**Shared state is required, and Redis is the standard answer.**

## The atomicity problem

```java
long count = redis.get(key);         // ← two round trips
if (count < limit) redis.incr(key);  // ← another request can slip between them
```

Classic check-then-act (Day 065). Under concurrency the limit is exceeded.

**Fix 1 — atomic increment:**

```java
long count = redis.incr(key);                       // atomic
if (count == 1) redis.expire(key, windowSeconds);   // ⚠️ two operations — see below
if (count > limit) reject();
```

⚠️ **If the process dies between `INCR` and `EXPIRE`, the key never expires** and that user is
blocked permanently. Use a Lua script.

**Fix 2 — a Lua script, executed atomically by Redis:**

```lua
-- token bucket, atomic
local tokens_key = KEYS[1]
local ts_key     = KEYS[2]
local rate       = tonumber(ARGV[1])
local capacity   = tonumber(ARGV[2])
local now        = tonumber(ARGV[3])
local requested  = tonumber(ARGV[4])

local tokens = tonumber(redis.call("get", tokens_key)) or capacity
local last   = tonumber(redis.call("get", ts_key))     or now

local delta  = math.max(0, now - last)
tokens = math.min(capacity, tokens + delta * rate)

local allowed = tokens >= requested
if allowed then tokens = tokens - requested end

local ttl = math.ceil(capacity / rate) * 2
redis.call("setex", tokens_key, ttl, tokens)
redis.call("setex", ts_key,     ttl, now)

return { allowed and 1 or 0, tokens }
```

**One round trip, fully atomic, no race.** This is how production rate limiters are built; Redis's
own `redis-cell` module implements a variant (GCRA) natively.

## Latency and failure

**Every request now makes a Redis call.** Two consequences:

**Set a tight timeout** — 5–10 ms. A rate limiter that adds 50 ms to every request is worse than the
abuse it prevents.

**Decide fail-open or fail-closed, deliberately:**

```java
try {
    return limiter.tryAcquire(key);
} catch (RedisException e) {
    metrics.increment("ratelimit.unavailable");
    return true;         // FAIL OPEN — availability over enforcement
}
```

| | Fail open | Fail closed |
|---|---|---|
| Redis down ⇒ | All traffic allowed | All traffic rejected |
| Right for | General API protection | Payments, login, anything abuse-critical |

**Fail open for capacity protection; fail closed for security-critical endpoints.** A login limiter
that fails open during a Redis outage is a brute-force window.

**The hybrid most large systems use:** a local in-process limiter as a coarse backstop (each instance
allows at most `L/N × 1.5`) plus the distributed limiter for accuracy — so a Redis outage degrades to
approximate enforcement rather than none.

# Part 4 — The response

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30
Content-Type: application/problem+json

{ "type": "https://api.acme.com/problems/rate-limit-exceeded",
  "title": "Rate limit exceeded",
  "status": 429,
  "detail": "100 requests per minute allowed. Retry in 30 seconds.",
  "retry_after": 30 }
```

**`Retry-After` is not optional.** Without it, clients retry immediately and make the situation
worse — and a well-behaved client cannot do the right thing even if it wants to.

**Send the `RateLimit-*` headers on *successful* responses too.** A client that can see it has 5
requests remaining can slow down *before* being rejected. This is the difference between a limiter
that punishes clients and one that cooperates with them.

`429` versus `503`: use **`429` when this client exceeded their quota**, and **`503` + `Retry-After`
when the system as a whole is shedding load**. They are different conditions and clients should treat
them differently.

## Client-side obligations

Day 062's retry rules, and they matter as much on this side:

```java
if (response.status() == 429) {
    long wait = response.header("Retry-After").map(Long::parseLong).orElse(backoff(attempt));
    Thread.sleep(wait * 1000 + jitter());        // ⭐ JITTER — or every client retries in lockstep
}
```

**Without jitter, every rate-limited client retries at exactly the same moment** and produces a
second thundering herd (Day 121). The same principle again.

## Where to enforce it

```
CDN / WAF (Cloudflare)   ✅ cheapest — the request never reaches you. Coarse, IP-based.
API Gateway               ✅ centralised, per-key, before your code runs
Application               ✅ finest granularity — per-endpoint, per-tenant, cost-weighted
Database / downstream     the last resort — a connection pool IS a rate limit
```

**Enforce at several layers.** The edge handles volumetric abuse cheaply; the application handles
business rules the edge cannot know about.

## Beyond rate limiting

Rate limiting is one member of a family, and naming the others is what makes a system-design answer
complete:

- **Concurrency limiting** — a semaphore capping *in-flight* requests (Day 070). Often more directly
  protective than a rate limit, because it bounds resource usage rather than arrival rate.
- **Load shedding** — reject work when latency or queue depth exceeds a threshold, prioritising by
  request importance.
- **Circuit breakers** — stop calling a failing dependency entirely (Stage 12).
- **Quotas** — long-window budgets (per day, per month) rather than per-second limits.
- **Adaptive limits** — Netflix's concurrency-limits library adjusts the limit from observed latency,
  so no static number needs tuning.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Fixed window with no awareness of the boundary | 2× the intended rate in a burst |
| Sliding window log with high limits | Memory proportional to the limit, per user |
| Check-then-act on the counter | The limit is exceeded under concurrency |
| `INCR` and `EXPIRE` as separate operations | A crash between them blocks a user forever |
| Rate limiting on unvalidated `X-Forwarded-For` | Trivially bypassed |
| IP-only limiting | NAT punishes many users; IPv6 makes it useless |
| No timeout on the Redis call | The limiter becomes the latency problem |
| Not deciding fail-open vs fail-closed | Either an outage or a brute-force window |
| Failing open on a login limiter | A brute-force window during any Redis blip |
| `429` without `Retry-After` | Clients retry immediately and worsen it |
| No `RateLimit-*` headers on success | Clients cannot self-regulate |
| Clients retrying without jitter | A synchronised second wave |
| One global limit for all endpoints | Login needs a far tighter limit than a health check |
| Rate limiting without concurrency limiting | Slow expensive requests still exhaust resources |

## Interview questions

**Q: Design a rate limiter.**
Clarify the unit first — per user, per key, per tenant, per endpoint — then propose a token bucket
or sliding window counter in Redis with an atomic Lua script, `429` with `Retry-After` and
`RateLimit-*` headers, a tight timeout with an explicit fail-open or fail-closed decision, and
enforcement at both the edge and the application.

**Q: What is wrong with a fixed window?**
The boundary: 100 requests at 10:00:59 and 100 at 10:01:00 are both allowed, so 200 arrive within a
second. Effectively double the intended rate in a burst.

**Q: Compare sliding window log and sliding window counter.**
The log is exact but stores an entry per request, so memory scales with the limit — fine for a
5-per-15-minutes login limit, unusable at 10,000 per hour. The counter interpolates between two
fixed windows: constant memory, under about 1% error, and it is what most production systems use.

**Q: Why choose a token bucket?**
Because burst capacity and sustained rate are independent parameters, which matches real client
behaviour — a page load firing 20 parallel requests is normal, not abusive. It is also O(1) with two
numbers of state, refills lazily with no timer, and supports weighted costs for expensive endpoints.

**Q: How do you make it work across many servers?**
Shared state in Redis with the whole check-and-decrement in a single atomic Lua script — one round
trip, no check-then-act race and no `INCR`/`EXPIRE` gap. Optionally a local coarse limiter as a
backstop so a Redis outage degrades to approximate enforcement.

**Q: Fail open or fail closed?**
Fail open for general capacity protection — availability matters more than exact enforcement. Fail
closed for security-critical endpoints like login and payments, where failing open creates a
brute-force window.

**Q: What should the 429 response contain?**
`Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` — the last three on
successful responses too, so clients can slow down before they are rejected — plus a structured
problem+json body.

**Q: What else would you add alongside rate limiting?**
Concurrency limiting with a semaphore, because it bounds resource usage directly rather than arrival
rate; plus load shedding, circuit breakers and long-window quotas.
