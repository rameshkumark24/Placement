# Day 270 🚪🏗️

**P-270** · The data and async review gate

**Time:** 3 hrs · **Mode:** REVIEW · **Gate**

> Eight days of asynchronous machinery: an outbox, a poller, scheduled jobs, an async executor,
> caching, uploads, real-time, and reports. **Every one of them is a place where work can be lost,
> duplicated, or silently stop.**
>
> **⭐ Today's question for every mechanism is the same: how would you know if it broke?** If the
> answer is "a customer would tell me", it is not finished.

# Part 2 — ⭐⭐ The failure drill

> **⭐⭐ For each mechanism: break it, and time how long until you would have known.**

**⭐ This is the most valuable hour of the day.** Run each one against your deployed instance while a
load test runs.

| # | Break | ⭐ Expected | ⭐ How long until you knew? |
|---|---|---|---|
| ⭐ 1 | **Stop the outbox poller** | events stop flowing | ⭐ lag-age alert |
| ⭐ 2 | **Make a message permanently fail** | dead-lettered after N | ⭐ DLQ alert |
| ⭐ 3 | **Stop the expiry job** | ⭐ **nothing visible** | ⭐⭐ **non-execution alert — or never** |
| ⭐ 4 | **Fill the async queue** | `CallerRunsPolicy` slows producers | latency metric |
| ⭐ 5 | **Throw from a `void @Async`** | handler fires | ⭐ failure counter |
| ⭐ 6 | **Stop Redis** | ⭐ degraded, not broken | error-rate metric flat |
| ⭐ 7 | **Kill an instance mid-batch** | another claims the rows | ⭐ no data loss |
| ⭐ 8 | **`kill -9` with tasks queued** | ⭐ **queued `@Async` work is lost** | ⭐ acceptable per Day 265 |
| ⭐ 9 | **Break the materialized view refresh** | stale dashboard | ⭐ non-execution alert |
| ⭐ 10 | **Disconnect 1,000 SSE clients** | registry returns to zero | ⭐ the gauge |

**⭐ Number 3 is the one that exposes the gap**, and it is why Day 264 emphasised it: **a stopped job
produces no error, no log, and no user complaint for days.** If your answer to "how long until you
knew?" is anything other than "the alert fired in ten minutes", write the alert now.

**⭐ Number 8 is the honest one.** You will lose queued `@Async` work. **The correct outcome is that
the loss is acceptable because Day 265 classified it** — and if it is not, that item belongs in the
outbox.

# Part 3 — ⭐ The end-to-end trace

**⭐ Run one booking through the entire system and follow it. This is the integration test that no
unit test replaces.**

```
⭐ 1.  POST /api/v1/bookings                      → 201 + Location
⭐ 2.  ⭐ The exclusion constraint holds under two concurrent requests
⭐ 3.  The outbox row is written in the SAME transaction
⭐ 4.  ⭐ The poller publishes it
⭐ 5.  ⭐ The consumer is idempotent — deliver twice, ⭐ one effect
⭐ 6.  ⭐ AFTER_COMMIT pushes to SSE — ⭐ ACROSS instances
⭐ 7.  The confirmation email is in the outbox, not @Async
⭐ 8.  ⭐ Left unconfirmed → the expiry job claims it, on any instance
⭐ 9.  ⭐ The cache is invalidated by a version INCR
⭐ 10. ⭐ ONE correlation ID appears in every log line, ⭐ INCLUDING the async ones
⭐ 11. Business metrics moved: bookings_created, booking_conflicts
```

**⭐ Step 10 is the proof that Day 265's `TaskDecorator` works**, and it is the thing that makes an
incident tractable: **one id, one query, the whole story including the background work.**

**⭐ Step 5 is the proof of Day 263's central claim.** Deliver the same event twice and assert one
effect.

# Part 4 — 🚪 ⭐ The gate

## ⭐ You may not proceed until

- [ ] ⭐ **All 35 audit rows ✅**, or ❌ with a justification in `KNOWN-GAPS.md`
- [ ] ⭐ **All ten failure drills performed**, ⭐ with "how long until I knew" recorded for each
- [ ] ⭐ **Every mechanism has an alert** — and the alert has been made to fire at least once
- [ ] ⭐ **The end-to-end trace passes**, ⭐ including one correlation ID across async boundaries
- [ ] ⭐ Every ADR from this week committed: outbox, async classification, transport choice, search
      boundary
- [ ] ⭐ **A runbook per alert** — three sentences: what it means, what to check, what to do
- [ ] CI green; the deployed instance carries all of it

## ⭐ `docs/RUNBOOK.md` — write it today

```markdown
## ⭐ Alert: outbox_oldest_unpublished_age > 300s
⭐ Means:  the poller is stuck or the transport is down.
⭐ Check:  is the poller instance alive? outbox_failed_total? the broker?
⭐ Do:     restart the poller; if messages are dead-lettered, inspect last_error.
```

**⭐ An alert with no runbook wakes someone who must then reconstruct the system's behaviour at
3 a.m.** Three sentences each is enough, and writing them now — while you remember why each alert
exists — is far easier than later.

## ⭐ Defence questions

1. **⭐ How would you know if the outbox poller stopped?**
2. **⭐ How would you know if a scheduled job stopped?** (⭐ and why is this harder?)
3. **⭐ What is lost if a pod is killed right now?** (⭐ you measured this)
4. **⭐ Which of your async work is in the outbox and which is not, and why?**
5. **⭐ Walk me through one booking from POST to the confirmation email.**
6. **⭐ Show me one correlation ID crossing into a background thread.**
7. **⭐ What happens to your API when Redis is down?** (⭐ you have tried it)
8. **⭐ Which alert have you actually seen fire?**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Auditing without breaking anything | ⭐ you learn nothing about detection |
| ⭐ Alerts that have never fired | ⭐ they may not work — most untested alerts do not |
| No runbooks | the alert wakes someone with no context |
| ⭐ The async classification only in your head | it cannot be reviewed or defended |
| ⭐ Skipping the end-to-end trace | ⭐ the seams between mechanisms are where bugs live |
| Moving on with ❌ rows and no `KNOWN-GAPS` entry | you will be caught out by a question you could have owned |

## ✅ Done when

- ⭐ Every gate box is ticked
- ⭐ **Every alert has fired once, deliberately**
- ⭐ **The end-to-end trace passes with one correlation ID throughout**
