# L-014 · JavaScript in the browser

## What JavaScript is

**A single-threaded, interpreted-then-JIT-compiled language with an event loop, embedded in a host
environment that gives it capabilities the language itself doesn't have.**

Every word there is load-bearing. Unpack them:

- **Single-threaded** — one call stack. One thing executes at a time. Always.
- **JIT-compiled** — V8 parses to bytecode, interprets (Ignition), then compiles hot functions to
  machine code (TurboFan). **This is the same architecture as the JVM** from Day 002. Same idea, same
  reasons.
- **Host environment** — the language spec (ECMAScript) has no `fetch`, no `setTimeout`, no DOM.
  Those come from the browser. Node gives different ones (`fs`, `http`).

That last point is the one people miss. `setTimeout` is **not JavaScript**. It's a browser API that
JavaScript can call.

## The runtime, drawn

```
 ┌──────────────────────────────────────────────────────────────┐
 │  JS ENGINE (V8)                                              │
 │   ┌───────────────┐          ┌─────────────────┐             │
 │   │  CALL STACK   │          │      HEAP       │             │
 │   │               │          │                 │             │
 │   │  ┌─────────┐  │          │  objects,       │             │
 │   │  │ inner() │  │          │  closures,      │             │
 │   │  ├─────────┤  │          │  functions      │             │
 │   │  │ outer() │  │          │                 │             │
 │   │  ├─────────┤  │          └─────────────────┘             │
 │   │  │ main    │  │                                          │
 │   │  └─────────┘  │   ← ONE stack. One thing at a time.      │
 │   └───────────────┘                                          │

 │   setTimeout timers      │   │  while (true) {                │
 │   fetch / XHR            │──▶│    if (stack empty) {          │
 │   DOM events             │   │      drain ALL microtasks      │
 │   ...run OUTSIDE the JS  │   │      then take ONE macrotask   │
 │      thread              │   │    }                           │
 └──────────────────────────┘   │  }                             │
                                └────────────────────────────────┘
                                     ▲                    ▲

                          │ MICROTASK QUEUE  │  │  MACROTASK QUEUE   │
                          │ Promise.then     │  │  setTimeout        │

                          │ MutationObserver │  │  DOM events, I/O   │
                          └──────────────────┘  └────────────────────┘
```

**The key insight: "asynchronous JavaScript" doesn't mean JavaScript runs concurrently.** It means
the *browser* does the waiting — on a different thread, in C++ — and hands a callback back to the JS
thread when it's done. Your JS never runs in parallel with itself.

## The call stack

Standard LIFO frames. Same as the JVM stack from Day 003.

```js
function third()  { console.log("third"); }
function second() { third(); }
function first()  { second(); }
first();
```

```
   push first  →  push second  →  push third  →  log  →  pop  →  pop  →  pop
```

**Stack overflow is real and easy to hit:**

```js
function recurse() { return recurse(); }
recurse();   // RangeError: Maximum call stack size exceeded
```

**And this is why a long loop freezes the page:**

```js
// The tab is completely unresponsive for ~5 seconds. No clicks, no scrolling, no rendering.
const end = Date.now() + 5000;
while (Date.now() < end) {}
```

Rendering, event handling and your code all share the one thread. Block it and everything stops.
Which is exactly why heavy work belongs in a Web Worker — a genuinely separate thread with no DOM
access.

## The event loop — and the rule that trips everyone

The loop does this, forever:

```
   1. Is the call stack empty?
   2. If yes: drain the ENTIRE microtask queue (including any added while draining)
   3. Then take exactly ONE macrotask and run it
   4. Render if it's time
   5. Repeat
```

**Microtasks starve macrotasks.** *All* microtasks run before the *next single* macrotask. This is
the single most-tested detail about the event loop.

### The canonical puzzle — work it out before reading on

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

console.log('4');
```

**Output: `1 4 3 2`**

Trace it:

| Step | What happens |
|---|---|
| `console.log('1')` | Synchronous → prints **1** |
| `setTimeout(…, 0)` | Handed to the browser. Callback → **macrotask** queue |
| `Promise.resolve().then(…)` | Already resolved → callback → **microtask** queue |
| `console.log('4')` | Synchronous → prints **4** |
| Stack empties | Event loop drains microtasks → prints **3** |
| Microtasks empty | Takes one macrotask → prints **2** |

**`setTimeout(fn, 0)` does not mean "run now".** It means "run after the current synchronous code
*and* after every pending microtask". The 0 is a minimum, not a promise — and browsers clamp nested
timers to 4ms anyway.

### A harder one

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve()
  .then(() => { console.log('C'); return Promise.resolve(); })
  .then(() => console.log('D'));
queueMicrotask(() => console.log('E'));
console.log('F');
```

`A F C E D B`. Sync first (`A`, `F`), then microtasks in queue order — `C`, then `E` (queued before
`D` existed), then `D` (queued when `C`'s promise resolved) — then the macrotask `B`.

## Why this matters for the rest of the roadmap

**1. It explains `useEffect` loops.** Your React state update queues a microtask; the re-render
queues another effect; that effect fetches and sets state again. Nothing blocks, so the loop runs at
whatever rate the event loop can spin — which is why an unguarded `useEffect` produces *millions* of
requests, not dozens. That's the bug in
[`03-Web-Developer/03-Frontend.md`](../../03-Web-Developer/03-Frontend.md),
now explained mechanically.

**2. It's the exact contrast with Java.** Java gives you real threads that genuinely run in parallel,
which is why Java needs `synchronized`, `volatile` and the memory model (Days 064–072). **JavaScript
needs none of that** — one thread means no data races on JS objects. Two models, opposite tradeoffs:

| | JavaScript | Java |
|---|---|---|
| Concurrency | One thread + event loop | Many OS threads |
| Parallelism | None (except Workers) | Real |
| Data races | Impossible in JS code | Constant hazard |
| Blocking I/O | Freezes everything | Blocks one thread |
| Cost per concurrent task | ~nothing | ~1 MB stack per thread |

**Neither is better.** Node handles 10,000 idle connections cheaply; Java handles CPU-bound work
across cores. And virtual threads (Day 072) are Java's attempt to get Node's cheapness without
giving up the blocking style.

**3. It's why `async/await` is not threading.** `await` doesn't block a thread — it *suspends the
function* and returns control to the event loop, resuming later via a microtask. Nothing runs in
parallel. `Promise.all` doesn't parallelise your JS; it lets the *browser* have several network
requests in flight while your single thread does nothing.

## `var`, `let`, hoisting — the short version

Day 214 covers this properly. For now:

```js
console.log(a);   // undefined  — var is hoisted and initialised to undefined
var a = 1;

console.log(b);   // ReferenceError — let is hoisted but in the "temporal dead zone"
let b = 1;
```

`var` is function-scoped, `let`/`const` are block-scoped. **Use `const` by default, `let` when you
must reassign, `var` never.**

## Type this yourself

```html
<!DOCTYPE html>
<html><body>
<button id="block">Block for 3s</button>
<button id="click">Click me</button>
<p id="out"></p>

<script>
  const out = document.getElementById('out');
  const log = m => { out.textContent += m + ' '; console.log(m); };

  // ── 1. Event loop ordering. PREDICT the output before running. ──
  log('1');
  setTimeout(() => log('2'), 0);
  Promise.resolve().then(() => log('3'));
  queueMicrotask(() => log('4'));
  log('5');

  // ── 2. Prove the thread is shared ──
  document.getElementById('click').onclick = () => log('clicked!');

  document.getElementById('block').onclick = () => {
    log('blocking...');
    const end = Date.now() + 3000;
    while (Date.now() < end) {}          // busy-wait, holds the thread
    log('done');
  };

  // ── 3. Microtask starvation — UNCOMMENT AND WATCH THE TAB DIE ──
  // function starve() { Promise.resolve().then(starve); }
  // starve();
</script>
</body></html>
```

**Do all three:**

1. **Predict the output**, then load. You should get `1 5 3 4 2`.
2. **Click "Block for 3s", then immediately spam "Click me".** Nothing happens for three seconds —
   then every click fires at once. Those events were queued while the thread was busy. **You just
   watched the single-threaded model, directly.** Try scrolling during the block too.
3. **Uncomment the starvation loop.** The tab locks up permanently and you have to close it. That
   loop queues a microtask from within a microtask, so the microtask queue never drains, so the event
   loop never reaches rendering or macrotasks. This is why "microtasks starve macrotasks" isn't
   trivia.

## Common mistakes

| Mistake | Correction |
|---|---|
| "JavaScript is multithreaded because it's async" | One thread. The *browser* does the waiting on other threads and queues callbacks back. |
| `setTimeout(fn, 0)` runs immediately | It runs after all synchronous code and all pending microtasks. |
| Expecting promises and timers to interleave | All microtasks drain before the next single macrotask. |
| Thinking `await` blocks a thread | It suspends the function and yields to the event loop. Nothing blocks. |
| Heavy computation on the main thread | Freezes rendering and input. Use a Web Worker. |
| `var` in modern code | Function-scoped and hoisted-as-undefined. Use `const`/`let`. |
| "`Promise.all` runs my code in parallel" | It runs *I/O* concurrently. Your JS still executes one statement at a time. |

## Interview questions

**Q: Is JavaScript single-threaded or multi-threaded?**
> The JavaScript execution itself is single-threaded — one call stack, one thing at a time. The host
> environment is not: timers, network requests and I/O run on browser threads outside the JS thread,
> and their callbacks are queued back to the single JS thread via the event loop. Web Workers give
> genuinely separate threads, but with no shared DOM and message-passing only.

**Q: Explain the event loop.**
> When the call stack is empty, the event loop drains the entire microtask queue — promise callbacks,
> `queueMicrotask`, MutationObserver — then takes exactly one macrotask, such as a timer callback or
> a DOM event, runs it, and repeats. Rendering happens between iterations.

**Q: What does this print?** `console.log(1); setTimeout(()=>console.log(2),0); Promise.resolve().then(()=>console.log(3)); console.log(4);`
> `1 4 3 2`. The two synchronous logs run first. Then the stack empties and microtasks drain, giving
> 3. Then one macrotask runs, giving 2.

**Q: Why does an infinite loop freeze the browser tab?**
> Script execution, event handling and rendering share the single main thread. A synchronous loop
> never yields, so the event loop never runs, so nothing can be painted or handled until it finishes.

**Q: How does this differ from Java's concurrency model?**
> Java uses real OS threads that execute in parallel, so it needs synchronisation, `volatile` and a
> memory model to manage shared mutable state. JavaScript's single thread makes data races on JS
> objects impossible, but means any blocking work stalls everything, so all I/O must be asynchronous.
