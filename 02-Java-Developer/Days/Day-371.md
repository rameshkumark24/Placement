# Day 371

**L-371** · Deployment strategies — and the precondition nobody states

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Every zero-downtime strategy has the same hidden requirement: both versions run at the same
> time. If your code or your schema cannot tolerate that, no strategy helps you.**
>
> That is why [Day 166](Day-166.md)'s expand/contract discipline is not a database topic — **it is
> the thing that makes rolling deploys possible at all.**

---

# Part 1 — ⭐⭐ The precondition

```
⭐ ROLLING DEPLOY, minute 3:
⭐   3 instances of v1  ·  2 instances of v2  ⭐⭐ SIMULTANEOUSLY, against ONE database
⭐
⭐ ⇒ ⭐ v1 must tolerate v2's schema
⭐ ⇒ ⭐ v2 must tolerate v1's data
⭐ ⇒ ⭐⭐ v1 and v2 must both handle each other's messages, cache entries and sessions
```

| ⭐ What must be backward compatible | ⭐ Failure if not |
|---|---|
| ⭐⭐ **The database schema** | ⭐⭐ **v1 crashes on a dropped column; v2 crashes on a missing one** |
| ⭐ **Message formats** (Day 333) | v1 consumes a v2 event it cannot parse |
| ⭐ **Cache entry shapes** | ⭐ a deserialization failure on a shared Redis — **use versioned keys** (Day 326) |
| ⭐ Session data | a user bounced between versions is logged out |
| ⭐ **API contracts** | ⭐ a client mid-session sees two different behaviours |

> **⭐ Say this before naming any strategy: "the first question is whether v1 and v2 can coexist,
> because everything below assumes they can."** It is the answer most candidates skip, and it is the
> one that determines whether a deploy is safe.

**⭐ Which makes the release a multi-step operation, not one deploy:**

```
⭐ Deploy 1: EXPAND   — add the new column, nullable; write to both; read from the old
⭐ Deploy 2: MIGRATE  — backfill; read from the new; keep writing both
⭐ Deploy 3: CONTRACT — stop writing the old; drop it
⭐ ⇒ ⭐⭐ each deploy is individually rollback-safe. ⭐ That is the whole point.
```

# Part 2 — ⭐ The five strategies

| Strategy | ⭐ Downtime | ⭐ Extra capacity | ⭐ Rollback speed | ⭐ Blast radius |
|---|---|---|---|---|
| ⭐ **Recreate** | ⭐⭐ yes | none | redeploy | 100% |
| ⭐ **Rolling** | none | ⭐ a little (surge) | ⭐ slow — roll back through | ⭐ grows during rollout |
| ⭐ **Blue-green** | none | ⭐⭐ **2×** | ⭐⭐ **instant — flip back** | ⭐⭐ 100% at once |
| ⭐⭐ **Canary** | none | a little | ⭐ fast | ⭐⭐ **1% first — the smallest** |
| ⭐ **Shadow** | none | ⭐ 2× compute | n/a — no user traffic | ⭐⭐ **zero** |

## ⭐ Rolling — the default, and its arithmetic

```
⭐ maxUnavailable: 25%   maxSurge: 25%
⭐ ⇒ ⭐ with 8 replicas: never below 6 serving, never above 10 running
⭐ ⇒ ⭐⭐ CAPACITY CHECK: can 6 replicas carry peak traffic? If not, your deploy causes the incident.
```

| ⭐ Requirement | |
|---|---|
| ⭐⭐ **Readiness gates the rollout** | ⭐ a new pod takes traffic only when ready; **a bad build stalls rather than spreads** |
| ⭐ **Headroom** | ⭐ deploying at 90% utilisation with 25% unavailable is a self-inflicted outage (Day 322) |
| ⭐ Graceful shutdown | in-flight requests complete (Day 361) |
| ⭐ **Slow rollback** | ⭐ rolling back is another rolling deploy — minutes, not seconds |

## ⭐ Blue-green — instant rollback, at a price

```
⭐ blue (v1, live) ── router ──► users
⭐ green (v2, warm, tested) ⭐ ← flip the router ⇒ ⭐⭐ instant switch, instant rollback
```

| ⭐ Pro | ⭐ Con |
|---|---|
| ⭐⭐ **Rollback is one router change — seconds** | ⭐⭐ **double the infrastructure during the switch** |
| ⭐ Full testing against production-like green | ⭐⭐ **100% of users move at once — no gradual signal** |
| Simple mental model | ⭐⭐ **the database is shared and cannot be flipped** |

⚠️ **The database is what makes blue-green harder than the diagrams suggest.** You can flip
application servers instantly; **you cannot flip a stateful database**, so the schema must serve both
colours — **which is expand/contract again.** Anyone presenting blue-green without mentioning the
database has drawn a picture rather than a plan.

## ⭐⭐ Canary — the best default when you have the tooling

```
⭐ 1% of traffic → v2 ⭐ for 10 minutes
⭐   ⭐ compare v2's error rate, p99 and SLO burn against v1 (Day 338)
⭐   ⭐ clean ⇒ 5% → 25% → 50% → 100%
⭐   ⭐⭐ breach ⇒ AUTOMATIC ROLLBACK, and 99% of users never saw it
```

| ⭐ Requirement | |
|---|---|
| ⭐⭐ **Per-version metrics** | ⭐⭐ **you must be able to compare v1 and v2 separately — label by version** |
| ⭐ Traffic splitting | a mesh, an ingress controller, or a load balancer that supports weights |
| ⭐ **Enough traffic** | ⭐ 1% of 100 requests/day is not a signal — **canaries need volume** |
| ⭐ Sticky assignment | ⭐ a user flipping between versions mid-session is its own bug |
| ⭐ **An automated decision** | ⭐ a human watching a dashboard is not a canary, it is a vigil |

⚠️ **Canary needs statistical honesty.** Comparing a 1% slice for two minutes will show noise as often
as signal. **Either wait for enough samples or compare against a control slice of the old version
rather than against the whole fleet**, which removes the "the canary pods are newer and colder" bias.

## ⭐ Shadow — for the changes you cannot risk

**⭐ Duplicate real traffic to the new version, discard its responses, compare.** Zero user impact,
and it is the only way to validate a rewrite of something critical against real production traffic
(Day 291's shadow mode).

⚠️ **Side effects must be disabled in the shadow path**, or you send every email twice and charge
every card twice. **That is the entire difficulty of shadow deployment.**

# Part 3 — ⭐⭐ Feature flags: the fifth option, often the best

```
⭐ Deploy the code with the feature OFF ⇒ ⭐⭐ deployment risk and release risk are now SEPARATE
⭐   enable for internal users → 1% → 10% → 100%
⭐   ⭐⭐ a problem ⇒ turn it off in SECONDS. No rollback, no redeploy, no rolling wait.
```

| ⭐ Advantage over canary | |
|---|---|
| ⭐⭐ **Per-feature, not per-deploy** | ⭐ one bad feature disabled without reverting five good ones |
| ⭐⭐ **Rollback in seconds** | ⭐ a config change beats any deployment strategy |
| ⭐ Target by user, plan or region | test with internal users first |
| ⭐ **Enables trunk-based development** | unfinished work ships disabled (Day 368) |

| ⭐ Cost | |
|---|---|
| ⭐ **Flags accumulate** | ⭐⭐ **every flag is a branch in the code — they need an expiry and a removal ticket** |
| ⭐ Combinatorial testing | you cannot test every flag combination |
| ⭐ **The flag system becomes critical** | if it is down, what is the default? — **it must fail to a known state** |

> **⭐ The strongest deployment answer combines them: canary the deploy, flag the feature.** The
> canary protects against the release being broken; **the flag protects against the feature being
> wrong** — and those are different failures with different fixes.

# Part 4 — ⭐ Choosing, and the automatic decision

| ⭐ Situation | ⭐ Strategy |
|---|---|
| Internal tool, downtime acceptable | ⭐ recreate — **simplest, and honest** |
| ⭐ **Default for a stateless service** | ⭐ **rolling + feature flags** |
| ⭐ Rollback speed is critical | ⭐ blue-green, if you can afford 2× |
| ⭐⭐ **User-facing, high traffic, real consequences** | ⭐⭐ **canary with automated analysis** |
| ⭐ A rewrite of something critical | ⭐ shadow first, then canary |
| A schema change | ⭐⭐ **expand/contract across several deploys, regardless of strategy** |

## ⭐ The rollback trigger

```
⭐ Roll back automatically on:
⭐   ⭐ error rate above baseline + threshold
⭐   ⭐ p99 latency regression beyond X%
⭐   ⭐⭐ SLO burn rate spike (Day 338) — ⭐ the best single signal
⭐   ⭐ a business metric drop (orders/min) — ⭐⭐ catches the SILENT failure nothing technical sees
```

⚠️ **The business metric is the one that catches a deploy which is technically perfect and
commercially broken** — a checkout button that renders but does nothing produces normal latency, zero
errors, and no orders (Day 338).

**⭐ And what makes rollback safe:** it must be practised, timed and **compatible** — you can only
roll back to a version the current schema still supports, **which is the whole reason for
expand/contract.** A deploy that cannot be rolled back is not a deploy, it is a migration.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Not stating the coexistence precondition | ⭐⭐ **every strategy silently assumes it** |
| ⭐ A schema change in one deploy | ⭐ v1 and v2 cannot both work |
| ⭐ **Down migrations as the rollback plan** | data loss (Day 370) |
| ⭐ Rolling deploy with no headroom | ⭐ 25% unavailable at 90% utilisation is an outage |
| ⭐ **Readiness probe that lies** | ⭐⭐ a bad build rolls out fully instead of stalling |
| ⭐ Blue-green with no database story | the picture works; the plan does not |
| ⭐ **A canary judged by a human on a dashboard** | ⭐ that is a vigil, not a canary |
| ⭐ Canary with no per-version metrics | nothing to compare |
| ⭐ Canary on low traffic | ⭐ noise indistinguishable from signal |
| ⭐ **Shadow traffic with live side effects** | ⭐⭐ duplicate emails and charges |
| ⭐ Flags with no expiry | permanent branching in the code |
| A flag system with no failure default | it goes down and behaviour is undefined |
| ⭐ **No business-metric rollback trigger** | the technically-perfect broken deploy |

## Interview questions

**Q: How do you deploy without downtime?**
The first question is not the strategy, it is whether the old and new versions can run at the same
time — because rolling, blue-green and canary all assume they can. That means the schema, message
formats, cache shapes and API contracts all have to be backward compatible, which turns a schema
change into a multi-deploy expand-migrate-contract sequence where each step is individually
rollback-safe. Once that holds, rolling is the sane default and canary is better if you have the
tooling.

**Q: Blue-green or canary?**
Canary for anything user-facing with real traffic, because the blast radius starts at one percent and
the decision can be automated on error rate, latency and SLO burn. Blue-green gives instant rollback
— a router flip rather than another rolling deploy — but it moves a hundred percent of users at once
and costs double the infrastructure. And neither of them solves the database: you can flip
application servers, you cannot flip a schema.

**Q: What makes a canary real rather than theatrical?**
Per-version metrics so you can actually compare, enough traffic for the sample to mean anything, and
an automated promotion or rollback decision. A human watching a dashboard for ten minutes is a vigil,
not a canary. I would also compare against a control slice of the old version rather than the whole
fleet, because the canary pods are newer and colder and that bias shows up as a latency regression
that is not real.

**Q: Where do feature flags fit?**
They separate deployment risk from release risk. The code ships disabled, gets enabled for internal
users then a small percentage, and if something is wrong it is off in seconds — faster than any
deployment strategy, and per-feature rather than per-deploy, so one bad feature does not require
reverting four good ones. The cost is that flags accumulate as permanent branches, so each one needs
an expiry and a removal ticket, and the flag system itself must fail to a known default.

**Q: What triggers an automatic rollback?**
Error rate above baseline, a p99 regression, an SLO burn-rate spike — and a business metric such as
orders per minute, which is the one that catches a deploy that is technically perfect and
commercially broken. A checkout that renders but does nothing produces normal latency and zero
errors; only the order rate notices.

## Mini task

1. **List everything that must be backward compatible** in your system, and check each one honestly.
2. ⭐⭐ Deploy a **schema change in a single step** to a test environment during a rolling update and
   **reproduce v1 crashing.** Redo it as expand/contract.
3. ⭐ Configure rolling with `maxUnavailable: 25%` and **verify the reduced replica count can carry
   peak load.** If not, change the setting.
4. ⭐ Make the readiness probe **always return healthy** and deploy a broken build. **Watch it roll
   out completely.** Fix the probe and repeat.
5. ⭐ Implement **blue-green** and time a rollback. Then write down what you would do about the
   database.
6. ⭐⭐ Implement a **canary with automated analysis.** Deploy a build with a 5% error rate and
   **confirm it rolls back without a human.**
7. ⭐ Add **per-version labels** to your metrics and build a v1-versus-v2 comparison panel.
8. ⭐ Add a **business-metric rollback trigger.** Deploy a build where a button silently does nothing
   and **confirm the order rate catches what error rates did not.**
9. ⭐ Implement one feature behind a **flag**, enable it for 1%, then **disable it and time that.**
10. ⭐ Set up **shadow traffic** for one endpoint with all side effects disabled, and compare
    responses.

## 🎙️ Articulation drill

**Three minutes:** *"How do you ship a change that adds a column and uses it?"*

**⭐ The marker: you do not answer with a deployment strategy — you answer with three deploys.**
Expand (add nullable, dual-write, read old), migrate (backfill, read new), contract (stop writing old,
drop it). **Then say why: each step is individually reversible, and during every rollout both versions
are running against one database.**

**⭐ Close on what that buys: "which is what makes rollback possible at all — you can only roll back
to a version the current schema still supports."** That sentence connects deployment strategy to
database discipline, and it is the connection most people never make out loud.
