# Part 1 — L-071 · The three liveness failures

|  | CPU usage | What is happening |
|---|---|---|
| **Deadlock** | **0%** | Everyone is blocked, waiting on someone else. Nothing moves, forever. |
| **Livelock** | **100%** | Everyone is *active* and responding to each other, but no progress. |
| **Starvation** | varies | Some threads progress; one never gets scheduled or never wins the lock. |

The CPU column is the fastest diagnostic you have. **A hung service at 0% CPU is a deadlock; a hung
service at 100% CPU is a livelock or an infinite loop.** That single distinction narrows the search
enormously before you have read a single stack.

## Deadlock — the four Coffman conditions

All four must hold simultaneously. Break any one and deadlock is impossible:

1. **Mutual exclusion** — a resource is held exclusively.
2. **Hold and wait** — a thread holds one resource while requesting another.
3. **No preemption** — a resource cannot be forcibly taken.
4. **Circular wait** — a cycle exists in the wait-for graph.

Java gives you no control over 1 and 3 with intrinsic locks. **So in practice you break 2 or 4** —
and breaking 4 with lock ordering is the standard answer.

## Reproduce it

```java
public class Deadlock {
    static final Object LOCK_A = new Object();
    static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (LOCK_A) {
                System.out.println("T1 holds A");
                sleep(100);
                System.out.println("T1 wants B");
                synchronized (LOCK_B) { System.out.println("T1 never gets here"); }
            }
        }, "T1").start();

        new Thread(() -> {
            synchronized (LOCK_B) {                 // ← OPPOSITE order
                System.out.println("T2 holds B");
                sleep(100);
                System.out.println("T2 wants A");
                synchronized (LOCK_A) { System.out.println("T2 never gets here"); }
            }
        }, "T2").start();
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

Run it. It prints four lines and hangs at 0% CPU forever. Now diagnose it:

```bash
jps                              # find the pid
jstack <pid>                     # or: jcmd <pid> Thread.print
```

At the bottom of the output:

```
Found one Java-level deadlock:
=============================
"T1":
  waiting to lock monitor 0x00007f... (object 0x000000076ab, a java.lang.Object),
  which is held by "T2"
"T2":
  waiting to lock monitor 0x00007f... (object 0x000000076ac, a java.lang.Object),
  which is held by "T1"
```

**The JVM detects and reports intrinsic-lock deadlocks for you.** It will not fix them, and it does
not detect deadlocks formed via `ReentrantLock` unless you use `ThreadMXBean.findDeadlockedThreads()`
— but for `synchronized`, `jstack` hands you the answer. Knowing that this section exists at the
bottom of a thread dump is worth stating in an interview.

## The realistic version — and why it hides

Nobody writes the code above. They write this:

```java
void transfer(Account from, Account to, long amount) {
    synchronized (from) {
        synchronized (to) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
```

This looks fine, and it is fine — until `transfer(alice, bob)` and `transfer(bob, alice)` run
concurrently. Then the lock order is A→B in one thread and B→A in the other, and you have the exact
code above. **The bug is in the data, not the code**, which is why it survives review and appears
only under production concurrency.

## Fix 1 — global lock ordering

Impose a total order on locks and always acquire in that order:

```java
void transfer(Account from, Account to, long amount) {
    Account first  = from.id() < to.id() ? from : to;      // deterministic order
    Account second = from.id() < to.id() ? to   : from;

    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
```

Now every thread acquires in ascending id order, so no cycle can form. If ids can collide (or you
have no natural key), fall back to `System.identityHashCode` with a tie-breaker lock:

```java
int h1 = System.identityHashCode(from), h2 = System.identityHashCode(to);
if (h1 == h2) { synchronized (TIE_BREAKER) { ordered(from, to); } }   // rare
```

**Lock ordering is the primary defence and the answer to give first.**

## Fix 2 — timeout and back off

```java
boolean transfer(Account from, Account to, long amount) throws InterruptedException {
    long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(2);
    while (System.nanoTime() < deadline) {
        if (from.lock().tryLock(50, TimeUnit.MILLISECONDS)) {
            try {
                if (to.lock().tryLock(50, TimeUnit.MILLISECONDS)) {
                    try { from.debit(amount); to.credit(amount); return true; }
                    finally { to.lock().unlock(); }
                }
            } finally { from.lock().unlock(); }
        }
        Thread.sleep(ThreadLocalRandom.current().nextInt(20));   // ← jitter matters. See below.
    }
    return false;
}
```

This breaks **hold-and-wait**: failing to get the second lock releases the first. It requires
`ReentrantLock` (Day 067) — you cannot do this with `synchronized`, which is the single most
practical reason to reach for the explicit lock.

## Fix 3 — do not hold two locks at once

The best fix is often structural: shrink the critical sections so you only ever hold one lock, or
replace the two locks with one coarser lock, or use a lock-free structure. **The deadlock you cannot
have is the one where there is nothing to order.**

## Livelock — busy and going nowhere

```java
public class Livelock {
    static class Worker {
        private final String name;
        private boolean active = true;
        Worker(String name) { this.name = name; }
        boolean isActive() { return active; }

        synchronized void work(Resource r, Worker other) {
            while (active) {
                if (r.getOwner() != this) { sleep(10); continue; }
                if (other.isActive()) {
                    System.out.println(name + ": you go first");
                    r.setOwner(other);                 // politely hands it over
                    continue;                          // …and the other does the same
                }
                r.use();
                active = false;
                r.setOwner(other);
            }
        }
    }
}
```

Both workers are running, both are responsive, both keep deferring to the other, and neither ever
uses the resource. That is livelock: **failure without blocking**.

The real-world instances are more mundane:

- Two nodes both retry a failed operation at exactly the same interval and collide every time.
- Two threads detect a deadlock, both release and retry immediately, and re-acquire in the same
  order — repeatedly.
- A message that fails processing is returned to the queue, redelivered, fails again, forever.

**The fix is randomness.** Randomised backoff — jitter — is precisely what breaks the symmetry, and
it is the same jitter from Day 062's retry, Day 021's rollout, and the Web domain's API safety
rules. Livelock is the reason jitter exists; make that connection explicit, because it converts
"add jitter" from folklore into a derived rule.

The Ethernet analogy is worth remembering: CSMA/CD collision detection uses **randomised exponential
backoff** for exactly this reason. Two stations that back off deterministically collide forever.

## Starvation

A thread never gets the resource it needs. Causes:

- **Unfair locks.** A barging lock (Day 067) can let short tasks repeatedly beat a long-waiting
  thread. Fix: `new ReentrantLock(true)` — at a real throughput cost.
- **Thread priorities.** `Thread.setPriority` is a *hint* the OS may ignore entirely; on Linux it
  usually does. Never build correctness on it.
- **Pool exhaustion.** All threads are occupied by slow tasks, so a fast task never runs. Fix:
  separate pools per workload — the bulkhead again (Day 069).
- **Writer starvation** under `ReentrantReadWriteLock` with continuous readers (Day 067).

**Thread starvation deadlock** is the vicious variant, and it is worth its own warning:

```java
ExecutorService pool = Executors.newFixedThreadPool(2);

pool.submit(() -> {
    Future<String> inner = pool.submit(() -> "nested");   // 💀 same pool
    return inner.get();                                    // waits for a thread that will never free
});
```

If two such tasks occupy both threads, both wait for an inner task that can never be scheduled,
because the only threads that could run it are the ones waiting. The pool is deadlocked with no lock
involved. **Never submit a task to the pool you are running on and then block on its result.**

## Detecting all of it programmatically

```java
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] deadlocked = bean.findDeadlockedThreads();          // includes ReentrantLock
if (deadlocked != null) {
    for (ThreadInfo info : bean.getThreadInfo(deadlocked, true, true))
        log.error("DEADLOCK: {} blocked on {} held by {}",
                  info.getThreadName(), info.getLockName(), info.getLockOwnerName());
}
```

Wiring this into a health check every 30 seconds means a deadlock pages you instead of being
discovered by a customer. `findMonitorDeadlockedThreads()` covers only intrinsic locks;
`findDeadlockedThreads()` covers owned `Lock`s too.

## Reading a thread dump — the signatures

Take a dump three times, 5 seconds apart. **What has not moved is your problem.**

```
"orders-7" #42 prio=5 tid=0x... nid=0x1a03 waiting for monitor entry [0x...]
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.acme.Ledger.transfer(Ledger.java:45)
        - waiting to lock <0x000000076ab12345> (a com.acme.Account)
        - locked <0x000000076ab99999> (a com.acme.Account)      ← holds one, wants another
```

| Signature | Diagnosis |
|---|---|
| `Found one Java-level deadlock` | Deadlock — read the cycle it prints |
| Many `BLOCKED` on one monitor, one `RUNNABLE` holding it | Lock contention / a lock held across I/O (Day 066) |
| Many `RUNNABLE` in the *same* method, high CPU | Livelock or a hot loop |
| All pool threads `WAITING` on `Future.get` | Thread starvation deadlock |
| `WAITING (parking)` on a queue | Idle consumers — usually normal |
| `RUNNABLE` in `socketRead0` | Blocked on I/O, *not* burning CPU (Day 064) |

# Part 2 — B-15 · Linux in practice

The thread dump tells you what Java thinks. The OS tells you the truth. Six commands.

## `top` / `htop` — is it CPU, or is it waiting?

```bash
top -H -p <pid>            # -H = show individual THREADS
```

`%CPU` per thread is the key column. Note the **`nid`** in the thread dump is the OS thread id in
**hex**; `top -H` shows it in decimal. That gives you the highest-value diagnostic recipe in Java
operations:

```bash
top -H -p <pid>                       # find the thread eating CPU, note its PID, e.g. 12345
printf '%x\n' 12345                   # → 3039
jstack <pid> | grep -A 30 'nid=0x3039'   # the exact Java stack burning your CPU
```

**Memorise that three-step recipe.** It turns "the service is at 100% CPU" into a specific line
number in about twenty seconds, and being able to describe it is a strong signal in an interview.

Also read the load average and the `wa` (iowait) column: high load with low CPU and high `wa` means
you are disk-bound, not compute-bound.

## `/proc` — the kernel as a filesystem

```bash
cat /proc/<pid>/status          # threads, memory (VmRSS is the real one), state
ls /proc/<pid>/fd | wc -l       # open file descriptors — the leak check
cat /proc/<pid>/limits          # ulimits actually in force
cat /proc/<pid>/cmdline | tr '\0' ' '   # the exact command line, JVM flags included
ls /proc/<pid>/task | wc -l     # thread count
cat /proc/meminfo               # system-wide memory
```

`VmRSS` versus heap size is the number that explains "the JVM is using more memory than `-Xmx`" —
metaspace, thread stacks (1 MB each!), code cache, direct byte buffers and the GC's own structures
all live outside the heap.

## `ps` — a snapshot

```bash
ps -eLf | grep java            # -L = one line per thread
ps -o pid,ppid,rss,vsz,etime,cmd -p <pid>
ps aux --sort=-%mem | head     # top memory consumers
```

## `lsof` — what is this process holding open?

```bash
lsof -p <pid>                  # everything
lsof -p <pid> | grep TCP       # connections — leaked sockets show here
lsof -i :8080                  # who owns the port ("address already in use")
lsof -p <pid> | wc -l          # against the fd limit
```

**"Too many open files" is one of the most common Java production failures**, and it is almost
always an unclosed stream, connection or socket (Day 063's try-with-resources). `lsof` shows you
exactly which kind is accumulating.

## `strace` — every system call

```bash
strace -p <pid> -f                     # -f follows threads
strace -p <pid> -e trace=network       # only network syscalls
strace -c -p <pid>                     # SUMMARY: count and time per syscall
```

`strace -c` answers "where is the time going" at the kernel boundary — and it is how you *see* Day
063's buffering lesson: an unbuffered read shows millions of `read()` calls; the buffered version
shows thousands.

⚠️ `strace` can slow a process by 10–100×. Never attach it casually to a live production JVM.

## `netstat` / `ss`

```bash
ss -tanp | grep <pid>
ss -s                          # summary by state
netstat -an | grep TIME_WAIT | wc -l
```

Thousands of `CLOSE_WAIT` sockets means **your application is not closing connections** (Day 008) —
the remote end closed, you never called close. Thousands of `TIME_WAIT` is usually normal for a busy
client.

## The 3 AM checklist

```
1. Is the process alive?             ps / systemctl status
2. CPU: 0% or 100%?                  top -H -p <pid>
3. Memory: RSS vs -Xmx?              /proc/<pid>/status, jcmd <pid> GC.heap_info
4. File descriptors near the limit?  ls /proc/<pid>/fd | wc -l  vs  /proc/<pid>/limits
5. Three thread dumps, 5s apart      jcmd <pid> Thread.print — what has not moved?
6. GC thrashing?                     jstat -gcutil <pid> 1000
7. Blocked on the network?           ss -tanp, and check the dependency's health
```

That ordering is deliberate: cheapest and most decisive first. Steps 2 and 5 together resolve most
hangs.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Inconsistent lock ordering | Deadlock under production concurrency only |
| Assuming code review catches it | The order comes from *data*, not code |
| Retrying without jitter | Livelock |
| Relying on thread priorities | Ignored by the OS |
| Blocking on a `Future` from the same pool | Thread starvation deadlock |
| Fair locks everywhere "to be safe" | Large throughput loss |
| One thread dump | You cannot tell stuck from slow. Take three. |
| `strace` on a live production JVM | 10–100× slowdown |
| Reading `RUNNABLE` as "using CPU" | Misdiagnosis; cross-check with `top -H` |

## Interview questions

**Q: What is a deadlock and how do you prevent it?**
A cycle in the wait-for graph where each thread holds a resource another needs. The four Coffman
conditions must all hold; the practical defences are a global lock ordering (breaks circular wait)
and `tryLock` with a timeout (breaks hold-and-wait). Best of all, avoid holding two locks.

**Q: Deadlock vs livelock?**
Deadlock is blocked and at 0% CPU. Livelock is running at 100% CPU while making no progress — threads
keep responding to each other. Randomised backoff fixes livelock; ordering fixes deadlock.

**Q: How do you diagnose a hung Java service?**
Check CPU first — 0% suggests deadlock, 100% suggests livelock or a hot loop. Take three thread dumps
five seconds apart and look for what has not moved. `jstack` reports intrinsic deadlocks explicitly.
Then check fds, RSS and GC.

**Q: How do you find which Java thread is burning CPU?**
`top -H -p <pid>` for the thread id, convert it to hex, then grep that `nid=0x…` in the thread dump.

**Q: What is thread starvation deadlock?**
A task submitted to a bounded pool blocks waiting on another task submitted to the same pool; if all
threads do this, none can free up. Use a separate pool, or do not block on nested results.

**Q: What causes "too many open files"?**
Unclosed streams, sockets or connections. `lsof -p <pid>` shows which type is accumulating; compare
the count against `/proc/<pid>/limits`.

## 🎙️ Articulation drill

Two minutes: **"A production service is hung. Walk me through your diagnosis."**

CPU first, then three thread dumps five seconds apart, then the specific signatures — deadlock
section, mass `BLOCKED` on one monitor, all threads on `Future.get`. Then fds, RSS and GC. Naming
the tools *and the order* is what makes this sound like something you have actually done.
