# L-011 · How HTTP evolved, and why

## The single thread running through all of it

```
   Chennai ↔ Oregon RTT ≈ 140 ms   (physics, Day 006)

   TCP handshake       1 RTT
   TLS handshake       1 RTT  (TLS 1.3)
   HTTP request/reply  1 RTT
   ─────────────────────────
   3 RTT ≈ 420 ms before you see a single byte
```

A modern page loads 70+ resources. **Every version of HTTP since 1996 has been an attempt to stop
paying that cost repeatedly.**

Hold that frame and the whole history is obvious.

---

## HTTP/0.9 (1991) — the one-liner

```
GET /index.html
```

No headers, no status codes, no versions. Server returns HTML and closes. That's the whole protocol.

Worth knowing only because it shows what got added and why.

---

## HTTP/1.0 (1996) — headers and status codes

Added everything from Day 010: methods, headers, status codes, content types, bodies.

**The fatal flaw: one connection per request.**

```
   GET /index.html    → TCP handshake → response → CLOSE
   GET /style.css     → TCP handshake → response → CLOSE
   GET /logo.png      → TCP handshake → response → CLOSE
```

Every single resource paid a full handshake. A page with 30 assets paid 30 handshakes — and each new
connection also restarted **slow start** (Day 008, C-06), so none of them ever reached full speed.

**Two costs, compounding.** This is the problem everything after 1.0 is trying to solve.

---

## HTTP/1.1 (1997) — keep-alive, and the head-of-line problem

### What it fixed: persistent connections

```
   Connection: keep-alive          ← the default in 1.1

   TCP handshake (once)
     → GET /index.html → response
     → GET /style.css  → response
     → GET /logo.png   → response
   close
```

One handshake, many requests. Slow start's ramp is amortised. **This is the single biggest
performance win in HTTP's history.**

### It also added

- **`Host` header, mandatory** — enabling virtual hosting: many domains on one IP (Day 010)
- **Chunked transfer encoding** — stream a response without knowing its total length upfront
- **Better caching** — `Cache-Control`, `ETag`, conditional requests
- **Range requests** — resume a download, seek in a video

### What it didn't fix: head-of-line blocking

Requests on a persistent connection are still **strictly sequential**. Response 1 must complete
before response 2 begins.

```
   ───[ request A ]────[ A is slow ]─────────[ response A ]──[ request B ]──[ response B ]──▶
                                                              ↑
                                        B waited for A, even though B was ready
```

**Pipelining** was specified — send B before A returns — but responses still had to come back *in
order*, so a slow A still blocked B. It was buggy in proxies and is disabled everywhere. Effectively
dead.

### The workarounds browsers invented

Since one connection was serial, browsers opened **6 parallel connections per domain**. Developers
then gamed that:

| Hack | What it did | What it cost |
|---|---|---|
| **Domain sharding** | `img1.site.com`, `img2.site.com` → 12+ parallel connections | Extra DNS lookups, extra handshakes |
| **Sprite sheets** | Combine 20 icons into one image, crop with CSS | One byte changes → whole sheet re-downloads |
| **Concatenation** | Bundle all JS into one file | Same problem; and one change busts the whole cache |
| **Inlining** | Base64 images into CSS | Uncacheable separately, 33% size penalty |

**Every one of these is a workaround for "connections are expensive and serial".** Remember this
list — HTTP/2 makes all of them *counterproductive*, and plenty of codebases still carry them.

---

## HTTP/2 (2015) — multiplexing

Based on Google's SPDY. **The core change: one TCP connection, many concurrent streams.**

```
   HTTP/1.1                          HTTP/2
   ────────────                      ──────────
   conn 1: [A....][D....]            conn 1: [A][B][C][A][B][D][C][A]...
   conn 2: [B....][E....]                     ↑ interleaved frames,
   conn 3: [C....]                              reassembled by stream ID
```

### What changed

**1. Binary framing.** HTTP/2 is not text. Messages become binary frames tagged with a stream ID.
This is why you can no longer debug it with `telnet` — you need `curl --http2 -v` or browser
devtools.

**2. Multiplexing.** Many requests and responses in flight simultaneously on one connection,
interleaved at frame level, reassembled by stream ID. **Application-level head-of-line blocking is
gone.**

**3. Header compression (HPACK).** HTTP headers are enormously repetitive — the same `User-Agent`,
`Cookie` and `Accept` on all 70 requests. HPACK keeps a shared table of previously-sent headers and
sends references. Often 80–90% reduction.

**4. Server push.** The server sends resources you haven't asked for yet. *This has been removed —
Chrome disabled it in 2022.* It was hard to use correctly and usually pushed things already cached.
Know it existed; don't plan around it. `103 Early Hints` is the surviving idea.

**5. Stream prioritisation.** Clients express which streams matter more.

### The consequence for your code

**The HTTP/1.1 hacks become harmful:**

| Practice | Under HTTP/2 |
|---|---|
| Domain sharding | ❌ Harmful — defeats multiplexing, adds handshakes |
| Sprite sheets | ❌ Mostly harmful — hurts caching granularity |
| Aggressive bundling | ⚠️ Less useful — many small cacheable files are now fine |
| Inlining | ❌ Harmful — kills separate caching |

If you inherit a codebase full of sharding and sprites, it may be actively slowing the site down.

### What HTTP/2 did *not* fix

**TCP-level head-of-line blocking.**

HTTP/2 removed the blocking *in HTTP*. But all streams still ride one TCP connection, and TCP
guarantees in-order delivery of *the whole byte stream*. So:

```
   Streams A, B, C multiplexed on one TCP connection.
   A packet belonging to stream A is lost.
   → TCP holds ALL subsequent bytes — including B's and C's, which arrived fine —
     until A's packet is retransmitted.
```

**Ironically, on a lossy network HTTP/2 can be *worse* than HTTP/1.1**, because 1.1's six separate
connections mean a loss on one doesn't stall the other five.

This is the exact problem UDP's lack of ordering solves (Day 010, C-07) — and it's why HTTP/3 exists.

---

## HTTP/3 (2022) — QUIC over UDP

**The change: replace TCP.**

```
   HTTP/2                         HTTP/3
   ────────                       ────────
   HTTP/2                         HTTP/3
   TLS 1.3                        QUIC  (streams + reliability + TLS 1.3, all in one)
   TCP                            UDP
   IP                             IP
```

QUIC is a transport protocol built **on UDP, in userspace**, that reimplements reliability, ordering
and congestion control — but **per stream** rather than per connection.

### What it buys

**1. No transport-level head-of-line blocking.** Each stream is independently reliable. A lost
packet for stream A stalls only stream A. B and C carry on. This is *the* headline feature.

**2. Faster handshake — 1 RTT, or 0-RTT on resumption.**

```
   TCP + TLS 1.3:  1 RTT (TCP) + 1 RTT (TLS) = 2 RTT
   QUIC:           1 RTT total — transport and crypto handshake combined
   QUIC resumed:   0 RTT — data in the very first packet
```

At 140 ms RTT that's saving 140–280 ms on *every* new connection.

**3. Connection migration.** A QUIC connection is identified by a **connection ID**, not by the
4-tuple (Day 003). Switch from WiFi to 5G and your IP changes — a TCP connection dies (its TCB is
keyed on the 4-tuple, Day 008), a QUIC connection survives. Your video call doesn't drop as you walk
out of the building.

**4. Encrypted by default.** TLS 1.3 is built in, not layered on. There is no unencrypted QUIC.

**5. Evolvable.** Because QUIC lives in userspace rather than the OS kernel, it can be updated by
shipping a new browser or library — not by waiting a decade for every middlebox on earth. TCP is
effectively frozen because firewalls and NATs would drop anything unfamiliar.

### The costs

- UDP is sometimes throttled or blocked by corporate firewalls — clients fall back to HTTP/2
- More CPU than TCP (userspace processing, no decades of kernel and NIC offload)
- Harder to debug and to inspect at the network layer

## Summary table — learn this

| | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|---|
| Year | 1996 | 1997 | 2015 | 2022 |
| Transport | TCP | TCP | TCP | **UDP (QUIC)** |
| Format | Text | Text | **Binary** | Binary |
| Connections | One per request | Persistent | **One, multiplexed** | One, multiplexed |
| Concurrency | None | Serial per conn | **Streams** | **Independent streams** |
| Header compression | No | No | **HPACK** | QPACK |
| App-level HOL blocking | Yes | Yes | **No** | No |
| Transport-level HOL blocking | — | Yes | **Yes** | **No** |
| Handshake to first byte | 2 RTT | 2 RTT | 2 RTT | **1 RTT / 0-RTT** |
| Connection migration | No | No | No | **Yes** |

**The one-line story:** 1.1 stopped re-handshaking, 2 stopped serialising requests, 3 stopped one
lost packet from stalling everything.

## Type this yourself

```bash
# Which version does a site negotiate?
curl -I --http2 https://www.google.com
curl -I --http3 https://www.cloudflare.com     # if your curl supports it

# Verbose — watch ALPN negotiate the protocol during the TLS handshake
curl -v --http2 https://www.google.com 2>&1 | grep -i -E "ALPN|HTTP/"
```

**ALPN** (Application-Layer Protocol Negotiation) is a TLS extension where client and server agree on
`h2`, `http/1.1` or `h3` *during* the TLS handshake — costing zero extra round trips. That's a neat
detail worth mentioning.

Then in the browser:

1. Open devtools → Network
2. Right-click the column headers → enable **Protocol**
3. Load a few sites and read the column: `http/1.1`, `h2`, `h3`

**Compare a site on h2 vs one on http/1.1** with 50+ resources. Look at the waterfall shape — h2's
requests start together; 1.1's stair-step in batches of six.

## Common mistakes

| Mistake | Correction |
|---|---|
| "HTTP/2 is just faster HTTP" | It's a different wire format — binary framing, multiplexed streams, compressed headers. |
| Still domain-sharding and spriting | These are HTTP/1.1 workarounds and are counterproductive under HTTP/2. |
| "HTTP/2 removed head-of-line blocking" | At the HTTP layer, yes. TCP-level blocking remains — that's HTTP/3's reason to exist. |
| Thinking HTTP/3 is "HTTP over UDP, so unreliable" | QUIC rebuilds reliability in userspace, per stream. It's reliable — just not TCP. |
| Planning around HTTP/2 server push | Removed from Chrome in 2022. Use `103 Early Hints`. |
| "HTTP/2 requires HTTPS" | Not by spec, but every browser requires it in practice. Treat it as required. |

## Interview questions

**Q: What problem did HTTP/1.1's keep-alive solve?**
> HTTP/1.0 opened a new TCP connection per request, paying a handshake and restarting slow start each
> time. Persistent connections reuse one connection for many requests, amortising both costs.

**Q: What is head-of-line blocking, and how do HTTP/2 and HTTP/3 each address it?**
> One item at the front of a queue blocking everything behind it. In HTTP/1.1 responses are serial,
> so a slow response blocks later ones — HTTP/2 fixes this with multiplexed streams. But HTTP/2's
> streams share one TCP connection, and TCP's in-order guarantee means a single lost packet stalls
> all streams. HTTP/3 fixes that by running over QUIC, where each stream is independently reliable.

**Q: Why does HTTP/3 use UDP?**
> Not for unreliability — QUIC reimplements reliability per stream in userspace. UDP is used because
> TCP applies ordering to the whole connection and can't be changed, since middleboxes worldwide
> would drop a modified TCP. Building on UDP allows per-stream reliability, a combined
> transport-and-crypto handshake, connection migration, and the ability to evolve without OS updates.

**Q: What is connection migration and why can't TCP do it?**
> QUIC identifies a connection by a connection ID rather than the source/destination IP-port tuple, so
> a client can change networks — WiFi to cellular — and keep the connection. TCP keys its connection
> state on the 4-tuple, so a changed IP destroys the connection.

**Q: Should you still bundle and sprite assets?**
> Much less. Those were workarounds for HTTP/1.1's connection limits. Under HTTP/2 and HTTP/3, many
> small cacheable files multiplex fine and give better cache granularity — one change doesn't
> invalidate a whole bundle. Domain sharding is actively harmful because it defeats multiplexing.
