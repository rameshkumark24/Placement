# Part 1 — ⭐ DTOs, and the boundary they create

```
⭐ CreateBookingRequest   — exactly what a client MAY send. Nothing else exists.
⭐ BookingResponse        — exactly what a client MAY see.
⭐ AdminBookingResponse   — a SECOND type, not a runtime filter (Day 147)
```

**⭐ Day 147's four reasons, and each one applies to your project specifically:**

| | Applied here |
|---|---|
| ⭐ 1 | ⭐ your `User` entity has a password hash; a DTO makes leaking it impossible |
| ⭐ 2 | mass assignment — `{"status":"CONFIRMED"}` has nowhere to land if the field is not in the request type |
| ⭐ 3 | lazy relationships serialised → the N+1 you eliminated on Day 255 returns |
| ⭐ 4 | ⭐ a schema change becomes an API change; Day 251's contract stops meaning anything |

**⭐ Records, and the five rules** (Day 147):

```
⭐ Separate request and response types — one shared type reintroduces mass assignment
⭐ A different response per audience — never filter one type by role at runtime
⭐ No entity type in any DTO field
⭐ DTOs live in the feature package (Day 141)
⭐ Map explicitly — static factory, or a query projection for reads
```

**⭐ Prefer the projection for read paths** (Day 255): the entity is never loaded, so the lazy-loading
problem is structurally impossible rather than avoided.

# Part 2 — ⭐ Validation at the boundary, rules in the domain

**Day 148's line, and your project must respect it:**

| ⭐ Boundary (`@Valid` on the DTO) | ⭐ Domain / service |
|---|---|
| `@NotBlank`, `@Min`, `@Email`, `@Future` | ⭐ does the room exist? |
| ⭐ `@AssertTrue` for cross-field — end after start | ⭐ is the user allowed? |
| Shape, format, range | ⭐ is the transition legal from this state? |

**⭐ Why the split matters here specifically: the same booking is created by your API *and* by the
expiry job *and* by any admin path.** A rule in a Bean Validation annotation only runs on the first.
**Structural checks at the edge; anything needing state in the domain** (Day 254).

**⭐ The three Boot 3 traps that will cost you an evening if you hit them cold:**

```
⭐ 1. spring-boot-starter-validation is NOT transitive → annotations present, nothing validated
⭐ 2. Nested objects need @Valid on the FIELD or their rules are silently skipped
⭐ 3. Constraints on @RequestParam need @Validated on the CLASS
      ⭐ and they throw a DIFFERENT exception → 500 unless Day 149's advice handles both
```

**⭐ Verify all three today.** Trap 1 fails open, which is the worst kind: everything compiles,
everything looks right, and nothing is validated.

## ⭐ Defence in depth against mass assignment

```
⭐ Primary:   the request DTO has no `status`, `id`, or `ownerId` field — nothing to bind
⭐ Secondary: @InitBinder setDisallowedFields as a second layer
```

**⭐ And the parameter trap from Day 145**: a parameter with no `@RequestBody` falls through to
model-attribute binding, which binds from query parameters. **That is both an empty-DTO bug and a
mass-assignment surface, in one missing annotation.**

# Part 3 — ⭐ The error contract, implemented once

**Day 149's `@RestControllerAdvice`, built to match Day 251's `ERRORS.md` exactly.**

```
⭐ One handler per domain exception → the type URI from ERRORS.md
⭐ MethodArgumentNotValidException  → 400, ALL field errors, not the first
⭐ ConstraintViolationException     → 400  ⭐ the one people miss (Day 148)
⭐ ObjectOptimisticLockingFailure   → 409, "reload and retry" (Day 165)
⭐ HttpMessageNotReadable           → 400, ⭐ WITHOUT the exception message
⭐ Exception (catch-all)            → 500, ⭐ logged fully, correlation ID returned
```

**⭐ The catch-all is the most important handler**, and its value is the correlation ID: a customer
says "I got an error, ID 7f3a" and one log query gives you the exact stack trace and request
(Day 127, Day 149). **Verify that round trip today** — trigger a 500, take the ID from the response,
find the log line.

**⭐ And close Day 149's three gaps, because your project has all three:**

| Gap | Fix |
|---|---|
| ⭐ **The JWT filter's exceptions** (Day 258) | ⭐ the filter writes `ProblemDetail` itself |
| ⭐ **Security's 401 and 403** | ⭐ `AuthenticationEntryPoint` + `AccessDeniedHandler` |
| Serialization failures mid-response | ⭐ not fixable — this is why DTOs and `open-in-view: false` matter |

**⭐ Without the first two, your API returns RFC 7807 everywhere except the two most common
failures**, which is exactly where a client notices.

```yaml
server.error.include-stacktrace: never      # ⭐⭐ Day 149 — non-negotiable
```

# Part 4 — ⭐ Controllers, and the cross-cutting layer

## ⭐ The controller does four things

```
⭐ 201 + Location via UriComponentsBuilder   (Day 146 — correct behind a proxy)
⭐ 204 on delete, no body
⭐ ETag on GET; If-Match REQUIRED on PUT → 412  (Day 165, Day 251)
⭐ Concrete return types — never ResponseEntity<?> (Day 146: it erases the schema)
```

**⭐ And `/me/` wherever the subject is the caller** (Day 251) — the identity comes from the token, so
there is no id to forge.

## ⭐ Jackson, configured against Day 106's four hazards

```
⭐ Dates: ISO strings in UTC — Instant, never LocalDateTime
⭐ Money: BigDecimal, WRITE_BIGDECIMAL_AS_PLAIN, or serialise as a string
⭐ IDs above 2^53: as strings — or UUIDs, which you have (Day 250)
⭐ FAIL_ON_NULL_FOR_PRIMITIVES: on   ⭐ null → 0 is a silent order for zero items
⭐ FAIL_ON_UNKNOWN_PROPERTIES: on for YOUR requests, off for THEIR responses (Day 154)
```

**⭐ Via `Jackson2ObjectMapperBuilderCustomizer`, never a replacement `ObjectMapper` bean** (Day 150)
— replacing it discards Boot's defaults and every module other starters registered, with symptoms
that appear far from the change.

## ⭐ Filters and interceptors — the right hook

| Concern | ⭐ Mechanism | Day |
|---|---|---|
| ⭐ Correlation ID | ⭐ `OncePerRequestFilter`, ⭐ **`MDC.clear()` in `finally`** | 151 |
| Request logging | filter — it sees the final status | 151, 182 |
| Rate limiting | filter, URL-scoped — ⭐ not on `/actuator` | 208 |
| Annotation-driven auditing | interceptor — only it has the `HandlerMethod` | 151 |
| Timing, retries, transactions | ⭐ AOP — ⭐ **so jobs and consumers get them too** | 151 |

**⭐ `MDC.clear()` in a `finally` is the rule that recurs in Days 066A, 151, 176 and 177**, and here
the consequence is logs attributed to the previous user — worse than no logs during an investigation.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Missing `spring-boot-starter-validation` | ⭐ **fails open — nothing is validated** |
| ⭐ Missing `@Valid` on a nested field | nested rules silently skipped |
| ⭐ Param constraints without class-level `@Validated` | silently ignored, then 500 |
| ⭐ Handling only `MethodArgumentNotValidException` | half your validation errors are 500s |
| ⭐ Missing `@RequestBody` | empty DTO **and** mass assignment (Day 145) |
| One DTO for request and response | mass assignment via the shared fields |
| Runtime role filtering in one response type | one missed branch leaks admin data |
| ⭐ `include-stacktrace` enabled | Day 119 information disclosure |
| `e.getMessage()` in a response | leaks SQL, hostnames, table names |
| ⭐ No entry point / denied handler | two error formats on the commonest failures |
| ⭐ No correlation ID on 500s | support cannot connect a report to a log |
| `ResponseEntity<?>` | schema erased; generated clients useless |
| ⭐ No `MDC.clear()` | the previous user's ID on this user's logs |
| Business logic in controllers | jobs and consumers skip it |
