# Part 1 — The problem with documentation

> **Documentation rots because nothing verifies it.**

Code has a compiler and tests. A comment (Day 089) has nothing, and neither does a wiki page. Six
months after it is written, a document describes a system that no longer exists — and a *wrong*
document is worse than a missing one, because a missing one makes you read the code while a wrong one
makes you confident and mistaken.

Two principles follow, and they shape everything else today:

**1. Prefer documentation that cannot rot.** In descending order of durability:

```
Code that is self-explanatory        ← cannot rot; the compiler checks it
Tests                                ← cannot rot; they fail
Types and constraints                ← cannot rot
Generated docs (OpenAPI from code)   ← rots only if generation stops
ADRs                                 ← IMMUTABLE by design (see below)
Committed diagrams-as-code           ← rots, but visibly, in review
Prose in the repo                    ← rots
A wiki in another system             ← rots fastest, unnoticed
```

**2. Document what code cannot express: WHY.** The code shows *what* and *how*, always accurately.
It can never show why this approach rather than the three alternatives — which is precisely the
information that is lost when someone leaves.

**3. Keep it next to the code**, in the repository, changed in the same commit and reviewed in the
same PR. Documentation in a separate system is documentation nobody updates.

# Part 2 — The README

The single highest-value document, because it is read most and is cheapest to keep true.

Its job is **to get a new person productive**, not to describe the architecture:

```markdown
# Order Service

Processes customer orders: validation, payment capture, and fulfilment hand-off.
Part of the commerce platform — see the platform overview in `docs/architecture.md`.

## Quick start

    git clone …
    cp .env.example .env          # fill in the values marked REQUIRED
    docker compose up -d          # postgres + redis
    ./mvnw spring-boot:run

Then: http://localhost:8080/actuator/health

## Requirements
- Java 21+
- Docker (for the local database)

## Running tests

    ./mvnw test                   # unit only, ~10s
    ./mvnw verify                 # + integration (Testcontainers), ~2min

## Configuration

| Variable | Required | Default | Description |
|---|---|---|---|
| `DATABASE_URL` | ✅ | — | Postgres JDBC URL |
| `PAYMENT_API_KEY` | ✅ | — | Provider key. Get one from the vault. |
| `RATE_LIMIT_RPS` | | 90 | Provider caps at 100; we stay under. |

## Architecture

Hexagonal — domain in `domain/`, adapters in `adapters/`.
Decisions recorded in `docs/adr/`.

## Common tasks
- Add a migration: `docs/migrations.md`
- Run against staging data: `docs/staging.md`

## Troubleshooting
- **`Connection refused` on startup** — Docker not running, or port 5432 in use.
- **Tests hang on first run** — Testcontainers is pulling images; give it 3 minutes.

## Who to ask
`#team-commerce` on Slack · owners in `CODEOWNERS`
```

Three things that make a README good rather than present:

**The quick start must actually work, from a clean clone.** Test it on a colleague's machine, or on a
fresh container. A README whose first command fails destroys trust in the whole document.

**The troubleshooting section is the highest-value part** and the one people omit. Every question
asked twice in Slack belongs there — that is the test for what to add.

**Document the *why* for configuration values.** `RATE_LIMIT_RPS=90` with "provider caps at 100"
prevents someone raising it to 500 next year.

# Part 3 — Architecture Decision Records

The best documentation format there is, because **it cannot go stale — it is a record of a decision
made at a point in time, not a description of the current state.**

```markdown
# ADR-0007: Use PostgreSQL rather than MongoDB for the order store

Date: 2026-08-14
Status: Accepted
Deciders: Ram, Priya, Karthik

## Context

The order service needs durable storage for orders, line items and payment records.
Expected volume is 50k orders/day growing to 200k within a year. Orders are read far
more than written (roughly 20:1) and are frequently queried across relationships —
"all orders for a customer in a date range with their line items and payment status".

We must support exactly-once payment capture, which requires multi-row transactional
consistency across `orders` and `payments`.

The team has strong SQL experience and no production MongoDB experience.

## Decision

We will use PostgreSQL 16.

## Consequences

**Positive**
- ACID transactions across orders and payments — required for payment correctness.
- Relational queries without application-side joins.
- Team expertise; no new operational learning curve.
- `jsonb` covers the semi-structured provider-response field, so we do not need a
  second store.

**Negative**
- Horizontal write scaling is harder than with Mongo. At 200k/day we are far from
  needing it; revisit above ~5k writes/second.
- Schema migrations require discipline (Flyway, expand-then-contract).

**Neutral**
- Managed Postgres (RDS) costs marginally more than the equivalent Mongo Atlas tier.

## Alternatives considered

- **MongoDB** — rejected: multi-document transactions exist but are less mature, and
  the relational query pattern fights the document model.
- **DynamoDB** — rejected: access patterns are not yet stable, and DynamoDB punishes
  changing them. Revisit if the read pattern settles and scale demands it.
- **Postgres + a separate document store** — rejected as premature (YAGNI); `jsonb`
  suffices for now.
```

## Why ADRs work

**They are immutable.** You never edit an accepted ADR. If the decision changes, you write a *new*
one that supersedes it:

```markdown
# ADR-0019: Move the order store to DynamoDB
Status: Accepted
Supersedes: ADR-0007
```

and update the old one's status to `Superseded by ADR-0019`. So the record is a **decision log**,
not a description — and a log of past decisions cannot become wrong.

**They capture the alternatives**, which is the part that is otherwise lost entirely. Two years
later, when someone asks "why aren't we using Mongo?", the answer exists with its reasoning and its
revisit condition. Without it, the team re-litigates the same debate every eighteen months.

**They record the trigger for revisiting.** "Revisit above ~5k writes/second" turns a decision into
something falsifiable.

Statuses: `Proposed` → `Accepted` → `Deprecated` / `Superseded by ADR-NNNN`.

**What deserves an ADR:** anything expensive to reverse — database and language choices,
authentication approach, API style, deployment model, a significant library, a deliberate
architectural constraint. **What does not:** naming conventions, formatting, anything a linter can
enforce.

Keep them in `docs/adr/NNNN-short-title.md`, numbered, in the repo, reviewed in a PR like code.
Fifteen minutes to write; it repays itself the first time someone asks why.

# Part 4 — Diagrams

## Diagrams as code

```
❌  A .png exported from a drawing tool, committed once, stale in three months,
    unmodifiable by anyone who lacks the source file.

✅  A Mermaid or PlantUML source file in the repo — diffable, reviewable, and
    changed in the same commit as the code it describes.
```

````markdown
```mermaid
sequenceDiagram
    participant C as Client
    participant A as API
    participant P as PaymentProvider
    participant D as Database

    C->>A: POST /orders
    A->>D: BEGIN; INSERT order (PENDING)
    A->>P: charge(idempotencyKey)
    alt success
        P-->>A: receipt
        A->>D: UPDATE order PAID; COMMIT
        A-->>C: 201 Created
    else provider timeout
        P--xA: timeout
        A->>D: ROLLBACK
        A-->>C: 503 (client retries with the SAME idempotency key)
    end
```
````

GitHub renders Mermaid natively, so a diagram in a Markdown file just works — no build step and no
external tool.

## The C4 model — the levels that matter

The useful insight of C4 is that a single "architecture diagram" tries to serve four audiences and
serves none:

| Level | Shows | Audience |
|---|---|---|
| **1 — Context** | Your system, its users, and external systems | Everyone, including non-technical |
| **2 — Container** | Deployable units: services, databases, queues | Engineers, ops |
| **3 — Component** | Major parts inside one container | Engineers on that service |
| **4 — Code** | Classes | ❌ Generate it; never draw it |

**Draw levels 1 and 2. Draw level 3 for complex services only. Never draw level 4** — it is the class
diagram, it rots in a week, and your IDE generates it on demand.

## Rules for diagrams that stay true

- **One purpose per diagram.** A diagram showing deployment *and* data flow *and* class structure
  communicates nothing.
- **Label the arrows.** "Service A → Service B" is nearly useless; "Service A → Service B: POST
  /orders, synchronous, 2s timeout" is a design statement.
- **Show what is interesting**, not everything. A diagram containing all 40 services is wallpaper.
- **Date it, or generate it.** An undated diagram is assumed current and probably is not.

# Part 5 — The rest

## API documentation — generate it

```java
@Operation(summary = "Create an order",
           description = "Creates an order and captures payment. Idempotent on Idempotency-Key.")
@ApiResponse(responseCode = "201", description = "Created")
@ApiResponse(responseCode = "409", description = "Duplicate idempotency key")
@PostMapping("/orders")
public ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest request) { … }
```

Generated OpenAPI from annotations (springdoc) is **derived from the code**, so it cannot drift from
the signatures. Hand-written API docs always drift. Include real examples, every error response, and
the auth requirements — the three things generated specs most often omit.

## Javadoc — where it earns its place

Public APIs and libraries: yes. Internal code: only where the contract is non-obvious.

```java
/**
 * Attempts to acquire a permit for the given key.
 *
 * <p>Thread-safe. Refill is lazy: permits are recomputed on access rather than by a
 * background task, so an idle key consumes no resources.
 *
 * @param key the rate-limit bucket, typically a user or API key. Must not be null.
 * @return true if a permit was granted; false if the limit is currently exhausted
 * @throws NullPointerException if key is null
 */
public boolean tryAcquire(String key) { … }
```

Document **thread-safety, nullability and the contract** — the things a caller cannot infer from the
signature. Do not write `@param key the key` (Day 089's "explains what the code already says").

## Runbooks

For anything that gets paged, one page per alert:

```markdown
# Runbook: OrderService high error rate

**Alert:** 5xx rate > 5% for 5 minutes
**Severity:** page

## Impact
Customers cannot place orders. Revenue-affecting.

## Diagnosis
1. Check the payment provider's status page — most common cause.
2. `kubectl logs -l app=order-service --since=10m | grep ERROR`
3. Dashboard: <link> — look at DB connection pool saturation.
4. Recent deploy? <link to deploy history>

## Mitigation
- Provider down → enable `payments.queue-mode` (orders queue, capture later): <command>
- Pool exhausted → scale replicas: `kubectl scale --replicas=6 …`
- Bad deploy → roll back: <command>

## Escalation
#team-commerce → on-call lead → payments vendor support (contract #4471)
```

**Written before the incident, tested during a game day.** A runbook written at 3 AM during the
incident is not a runbook.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Documentation in a separate wiki | Nobody updates it; it rots invisibly |
| A README whose quick start does not work | Trust in the whole document is gone |
| Documenting *what* instead of *why* | Duplicates the code and drifts |
| Editing an accepted ADR | Destroys the decision log's value |
| Exported images as diagrams | Undiffable, unmodifiable, stale |
| Class-level (C4 level 4) diagrams | Rot within a week |
| Unlabelled arrows | Communicates nothing |
| Hand-written API docs | Always drift from the code |
| Javadoc restating the signature | Noise |
| No runbook for a paging alert | Every incident is improvised |
| Documenting everything | Nothing is maintained |

## Interview questions

**Q: How do you keep documentation from going stale?**
Prefer forms that cannot rot — self-explanatory code, tests, types, generated API specs — keep prose
in the repo so it is changed and reviewed with the code, and use ADRs for decisions, which are
immutable by construction.

**Q: What is an ADR?**
A short record of one significant decision: context, the decision, consequences, and alternatives
considered. Never edited — superseded by a new one. It is a decision log rather than a description,
so it cannot become wrong, and it preserves the reasoning that is otherwise lost.

**Q: What belongs in a README?**
Enough to get someone productive: what the service does, a quick start that actually works,
configuration with the *why* for each value, how to run tests, troubleshooting for the questions
asked twice, and who to ask.

**Q: What is the C4 model, and which levels do you draw?**
Context, Container, Component, Code. Draw 1 and 2, draw 3 for complex services, never 4 — the class
level rots immediately and the IDE generates it.

**Q: What documentation would you write for a new service?**
A README, ADRs for the decisions that are expensive to reverse, a generated OpenAPI spec, a container
diagram, and a runbook for every paging alert. Nothing else until someone asks the same question
twice.

## Mini task

1. Rewrite the README for one of your projects using the structure above. Then hand it to someone
   who has never seen the project and watch them follow it — fix everything they stumble on.
2. Write three ADRs retrospectively for real decisions in your work, including the alternatives you
   rejected and the condition that would make you revisit.
3. Write one ADR that supersedes another. Update the original's status.
4. Convert one existing diagram to Mermaid and commit it. Confirm it renders in GitHub.
5. Draw C4 levels 1 and 2 for a system you know. Label every arrow with protocol, synchronicity and
   timeout.
6. Add springdoc (or manual OpenAPI) to a service and confirm the spec is generated from the code.
7. Write a runbook for one realistic failure, then have someone else try to follow it while you say
   nothing.
8. Find the three questions your team or your own past self has asked twice. Add each to a
   troubleshooting section.

## 🎙️ Articulation drill

Two minutes: **"How do you document a system?"**

Lead with the failure mode — documentation rots because nothing verifies it — then the strategy:
prefer forms that cannot rot, keep prose in the repo, document *why* rather than *what*, and use ADRs
for decisions because a decision log is immune to staleness. Name the four artefacts you would
actually create: README, ADRs, generated OpenAPI, runbooks. Concreteness is what makes this answer
land.
