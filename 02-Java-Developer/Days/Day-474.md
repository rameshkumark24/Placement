# Part 1 — ⭐⭐ The four-step method

```
⭐⭐ 1. DEFINE THE STATE, in a sentence, precisely.
⭐    ⭐⭐ "dp[i] = the length of the longest increasing subsequence ENDING AT i"
⭐    ⭐⭐ ← the "ending at i" is not decoration. ⭐⭐ A vague state is the #1 cause of wrong DP.
⭐⭐ 2. WRITE THE RECURRENCE — what decision is made at step i, and what does it depend on?
⭐⭐ 3. IDENTIFY THE BASE CASES — the smallest inputs, stated explicitly.
⭐⭐ 4. DETERMINE THE ORDER — what must be computed before what?
⭐ ⇒ ⭐⭐ Only NOW do you decide memoised recursion or a bottom-up table. ⭐ That is an implementation
⭐   detail; steps 1–3 are the actual problem.
```

| ⭐⭐ How to know it is a DP problem | |
|---|---|
| ⭐⭐ **"Maximum / minimum / count the number of ways"** | ⭐ over a set of choices |
| ⭐⭐ **A choice at each step, and choices interact** | ⭐⭐ greedy fails because a local best is not global |
| ⭐ Overlapping subproblems | ⭐ the recursion tree recomputes the same call |
| ⭐ Optimal substructure | ⭐ the best solution contains best solutions to subproblems |
| ⭐ The tell | ⭐⭐ **you wrote a recursion and it is exponential** — memoise it |

> **⭐ The honest path under a clock: write the brute-force recursion first, out loud, in five minutes.**
> Then say *"this recomputes the same states, so I'll memoise — that makes it O(n²)"*. **You have now
> derived DP in front of them rather than recalling it**, which scores far better and is much harder to
> get wrong.

# Part 2 — ⭐⭐ The problems

## ⭐ Warm-up (target: 12 minutes)

> **You are climbing a staircase of `n` steps. Each move is 1 or 2 steps. How many distinct ways can you
> reach the top?**

```java
// ⭐ State: dp[i] = number of distinct ways to reach step i
// ⭐⭐ Recurrence: to arrive at i you came from i-1 or i-2  ⇒  dp[i] = dp[i-1] + dp[i-2]
// ⭐ Base: dp[0] = 1 (one way to stand still), dp[1] = 1
int a = 1, b = 1;                     // ⭐⭐ O(1) space — only the last two matter
for (int i = 2; i <= n; i++) { int c = a + b; a = b; b = c; }
return b;
```

**⭐ Say aloud:** *"The state is the number of ways to reach step i. The recurrence falls out of asking
where I could have come from — only i-1 or i-2. That is Fibonacci. The table is O(n), but the recurrence
only looks back two steps, so I can hold two variables and use O(1) space."*

⚠️ **The base case `dp[0] = 1` catches people.** "One way to be at the bottom" feels wrong until you see
it is the empty sequence of moves. **State base cases explicitly rather than deriving them from the loop
— that is where off-by-one lives.**

## ⭐⭐ Main problem (target: 30 minutes)

> **Given `coins` of distinct denominations and an `amount`, return the fewest coins needed to make that
> amount, or `-1` if it cannot be made. You have unlimited coins of each denomination.**

| ⭐ The arc they want | |
|---|---|
| ⭐⭐ 1. **Reject greedy explicitly, with a counterexample** | ⭐⭐ coins `[1,3,4]`, amount 6: greedy gives 4+1+1 = 3 coins, **optimal is 3+3 = 2** |
| ⭐ 2. State: `dp[a]` = fewest coins to make amount `a` | ⭐ one dimension |
| ⭐⭐ 3. Recurrence: `dp[a] = 1 + min(dp[a - c])` over all coins `c ≤ a` | ⭐ the decision is *which coin do I use last* |
| ⭐ 4. Base: `dp[0] = 0` | ⭐⭐ and everything else starts unreachable |

```java
int[] dp = new int[amount + 1];
Arrays.fill(dp, amount + 1);              // ⭐⭐ sentinel: bigger than any real answer, avoids overflow
dp[0] = 0;                                // ⭐ base case, stated

for (int a = 1; a <= amount; a++)
    for (int c : coins)
        if (c <= a)                       // ⭐ guard before indexing
            dp[a] = Math.min(dp[a], dp[a - c] + 1);

return dp[amount] > amount ? -1 : dp[amount];   // ⭐⭐ still sentinel ⇒ unreachable
```

| ⭐⭐ The four failures to expect | |
|---|---|
| ⭐⭐ **Not rejecting greedy out loud** | ⭐⭐ the counterexample is the strongest thing you say in the round |
| ⭐⭐ **Using `Integer.MAX_VALUE` as the sentinel** | ⭐⭐ `MAX_VALUE + 1` overflows to negative — a silent wrong answer |
| ⭐ Forgetting the `-1` unreachable case | ⭐ returns the sentinel |
| ⭐ Confusing this with *counting* combinations | ⭐⭐ counting needs the coin loop **outside** to avoid permutations |

**⭐⭐ The last row is worth stating aloud even if unasked:** *"If the question were how many ways rather
than how few coins, the loop order matters — coins outside, amounts inside — otherwise you count 1+3 and
3+1 as different. Here I'm minimising, so the order doesn't affect correctness."* **That single sentence
demonstrates you understand the structure rather than the template.**

# Part 3 — ⭐⭐ The state-definition failures

```
⭐⭐ THE SAME PROBLEM, TWO STATES — one works, one does not:

⭐ Longest Increasing Subsequence:
⭐   ❌ ⭐⭐ "dp[i] = the LIS of the first i elements"
⭐      ⇒ ⭐⭐ you cannot write a recurrence — you don't know what the last element WAS,
⭐        so you cannot tell whether nums[i] can extend it.
⭐   ✅ ⭐⭐ "dp[i] = the LIS ENDING AT i"
⭐      ⇒ ⭐ dp[i] = 1 + max(dp[j]) for all j < i with nums[j] < nums[i]
⭐      ⇒ ⭐⭐ the answer is max(dp), NOT dp[n-1] — ⭐ and that catches people too.
```

| ⭐ Rule | |
|---|---|
| ⭐⭐ **A state you cannot write a recurrence for is the wrong state** | ⭐⭐ do not push on — redefine it |
| ⭐⭐ **"ending at i" vs "up to i" is a real distinction** | ⭐ and it changes where the answer lives |
| ⭐ If one dimension will not close, add one | ⭐ `dp[i][j]`, `dp[i][remaining]`, `dp[i][heldOrNot]` |
| ⭐ Say the state sentence out loud before coding | ⭐⭐ if it takes more than one sentence, it is probably wrong |

## ⭐ The classic families, and their state

| ⭐ Family | ⭐ State |
|---|---|
| ⭐ Fibonacci-shaped (stairs, house robber) | ⭐ `dp[i]` = best up to i |
| ⭐⭐ **0/1 knapsack** | ⭐⭐ `dp[i][w]` = best using first i items with capacity w |
| ⭐ Unbounded knapsack (coin change) | ⭐ `dp[amount]`, coins reusable |
| ⭐⭐ **LCS / edit distance** | ⭐⭐ `dp[i][j]` over two strings — **the two-pointer-into-a-grid shape** |
| ⭐ LIS | ⭐⭐ `dp[i]` = best **ending at** i · (O(n log n) with patience sorting) |
| ⭐ Interval / partition DP | `dp[i][j]` over a range |
| ⭐ Grid paths | ⭐ `dp[r][c]` — often O(1)-row space |

# Part 4 — ⭐ Memo vs table, and space

| | ⭐ Memoised recursion | ⭐ Bottom-up table |
|---|---|---|
| ⭐ Write it | ⭐⭐ **faster under a clock, and closer to your reasoning** | ⭐ needs the order worked out |
| ⭐ Computes | ⭐ only reachable states | ⭐ all states |
| ⭐ Risk | ⭐⭐ **stack depth on large n** | ⭐ none |
| ⭐ Space optimisation | ⭐ hard | ⭐⭐ **easy — roll the array** |

```
⭐⭐ UNDER A CLOCK: write the recursion, memoise it, SAY "this converts to a bottom-up table
⭐   by iterating states in dependency order, and then I can reduce the space because each row
⭐   only depends on the previous one."
⭐ ⇒ ⭐⭐ You get the correctness of the recursion AND demonstrate you know the optimisation,
⭐   without spending ten minutes rewriting it. ⭐ That is the right trade in 45 minutes.
```

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Writing the table before the recurrence** | ⭐⭐ you are guessing at structure |
| ⭐⭐ **A vague state definition** | ⭐⭐ the number one cause of wrong DP |
| ⭐ Pushing on with a state that will not close | ⭐⭐ redefine instead |
| ⭐⭐ **Not rejecting greedy explicitly** | ⭐⭐ the counterexample is the best line in the round |
| ⭐⭐ **`Integer.MAX_VALUE` as a sentinel** | ⭐⭐ `+1` overflows to negative; silent wrong answer |
| ⭐ Returning `dp[n-1]` where the answer is `max(dp)` | ⭐ LIS specifically |
| ⭐ Base cases derived from the loop rather than stated | ⭐⭐ where off-by-one lives |
| ⭐ Confusing minimise-coins with count-ways | ⭐⭐ loop order matters for one and not the other |
| ⭐ Deep recursion with no note on stack depth | ⭐ a real failure at scale |
| ⭐ Rewriting memo → table under the clock | ⭐⭐ say it instead; spend the time testing |
| Never tracing a small input | the off-by-one survives |

## Interview questions

**Q: How do you approach a DP problem?**
Four steps, and none of them start with a table. Define the state in one precise sentence — and precision
matters, because "the longest increasing subsequence ending at i" is a workable state while "of the first
i elements" is not, since you cannot tell whether the next element extends it. Then write the recurrence
by asking what decision is made at this step and what it depends on. Then state the base cases
explicitly. Then work out the computation order. Memoised recursion versus a bottom-up table is an
implementation detail after all of that.

**Q: Why can't you use greedy for coin change?**
Because a locally optimal choice is not globally optimal with arbitrary denominations. With coins of one,
three and four making six, greedy takes the four and then needs two ones for three coins, while the
optimal answer is two threes. That counterexample is the single most valuable thing I can say in that
problem — it justifies the whole approach in one sentence, and giving it unprompted is much stronger than
asserting that greedy fails.

**Q: What sentinel do you use for an unreachable state?**
Something larger than any real answer but safe to add one to — amount plus one works here. Using
`Integer.MAX_VALUE` is the trap, because the recurrence adds one to it and overflows to a negative
number, which then wins the minimum and produces a silently wrong answer that looks fine on small
inputs. Choosing the sentinel deliberately and saying why is a small thing that signals you have been
bitten by it.

**Q: When do you memoise rather than build a table?**
Under a forty-five-minute clock, almost always memoise, because it is much closer to how I reasoned about
the problem and therefore less likely to be wrong. Then I say out loud that it converts to bottom-up by
iterating states in dependency order, and that the space can usually be reduced because each row only
depends on the previous one. That gets me the correctness of the recursion and demonstrates I know the
optimisation, without spending ten minutes rewriting code I would rather spend testing. I would flag
stack depth as the risk if n is large.

**Q: Coin change minimum versus counting the ways — what changes?**
The loop order starts to matter. For the minimum, iterating amounts outside and coins inside or the other
way round both give the right answer. For counting combinations, the coin loop has to be outside,
otherwise you count one-plus-three and three-plus-one as different arrangements and end up counting
permutations. Knowing which of those two problems you are in, and that the loop order encodes it, is the
difference between understanding the structure and remembering a template.

## 🎙️ Articulation drill

**Two minutes:** narrate the opening of coin change without writing code.

**⭐ Reject greedy first, with the counterexample, because it justifies everything that follows: "coins
one, three and four, amount six — greedy takes four then two ones for three coins, but two threes is
two. So a local best isn't global, which rules out greedy and points at DP."**

**⭐ Then the four steps, out loud: "State: dp of a is the fewest coins to make amount a. Recurrence: the
decision is which coin I use last, so dp of a is one plus the minimum over dp of a minus c for every coin
c that fits. Base: dp of zero is zero. Order: ascending, because a depends only on smaller amounts. It's
O(amount × coins) time and O(amount) space — and I'll use a sentinel of amount plus one rather than
MAX_VALUE, because adding one to MAX_VALUE overflows negative and silently wins the minimum."**
