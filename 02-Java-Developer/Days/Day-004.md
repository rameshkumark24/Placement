# Part 1 — L-004 · What a server actually is

## The answer, in one sentence

**A server is a program that binds to a port and sits in an infinite loop waiting for connections.**

That's it. No special hardware, no special OS, no magic. It's a `while (true)` loop that blocks on a
system call. Everything else — Nginx, Tomcat, Spring Boot, Node — is that loop plus a very large
amount of convenience.

The word "server" is overloaded, which is where the confusion comes from:

| "Server" can mean | Actually is |
|---|---|
| Server *program* | A process in a loop, waiting on a port ← **this is the real meaning** |
| Server *machine* | A computer that happens to run such programs |
| Server *rack/data centre* | Where those machines physically live |

When an interviewer asks "what is a server", they want the first one. Answer with the loop.

## Why it exists

A client initiates. A server waits. Someone has to be reachable at a known, stable address —
otherwise two programs could never find each other.

That asymmetry is the entire client-server model:

- The **server** commits to an address in advance (this IP, this port) and waits indefinitely
- The **client** knows that address and initiates when it wants something

The server is passive. It does nothing until contacted. A running server that nobody talks to
consumes almost no CPU — it's blocked in a system call, and the OS won't even schedule it.

## How it works inside — the four system calls

Every server on earth, in every language, makes these four calls in this order:

```
   ┌─────────────────────────────────────────────────────────────┐
   │  1. socket()   Create an endpoint. Get back a file          │
   │                descriptor — a number the OS uses to         │
   │                identify this socket.                        │
   ├─────────────────────────────────────────────────────────────┤
   │  2. bind()     Claim an address+port. "I am 0.0.0.0:8080."  │
   │                Fails if something else holds it. ← Day 003  │
   ├─────────────────────────────────────────────────────────────┤
   │  3. listen()   Tell the OS: queue incoming connections      │
   │                for me. Sets the backlog size.               │
   ├─────────────────────────────────────────────────────────────┤
   │  4. accept()   BLOCK until a client connects. Returns a     │
   │                NEW socket for that one client.              │
   └─────────────────────────────────────────────────────────────┘
                            │
                            ▼
            ┌──────── while (true) ────────┐
            │  accept()  → blocks here     │
            │  read()    → client's bytes  │
            │  write()   → your response   │
            │  close()   → this client     │
            └──────────────────────────────┘
```

### The two things that actually confuse people

**1. `accept()` returns a *different* socket.**

You have a **listening socket** on port 8080. When a client connects, `accept()` gives you a
**connected socket** for that specific client. The listening socket stays open, still on 8080, ready
for the next one.

```
  Listening socket:  (*, *, 0.0.0.0, 8080)          ← always there, accepts new
  Client A socket:   (1.2.3.4, 51234, myip, 8080)   ← from accept()
  Client B socket:   (5.6.7.8, 44100, myip, 8080)   ← from accept()
```

**This is yesterday's 4-tuple, doing its job.** All three sockets involve port 8080 and there's no
conflict, because a connection is identified by all four values. If you understood Day 003, this is
already obvious — which was the point of Day 003.

**2. "Blocking" means the OS parks your thread.**

When you call `accept()` and no one has connected, your thread is *not* spinning and burning CPU.
The OS marks it not-runnable, removes it from the scheduler's queue, and wakes it when a connection
arrives. Zero CPU while waiting.

This is why an idle server costs nothing, and it's the foundation for understanding thread-per-request
(Day 069), non-blocking I/O and epoll (B-13/B-14), and virtual threads (Day 072).

## Write one. Right now.

Type this. No copy-paste. This is the most important 30 lines in Stage 0.

```java
import java.io.*;
import java.net.*;

public class TinyServer {
    public static void main(String[] args) throws IOException {

        // 1+2+3: socket(), bind(), listen() — all in one constructor.
        ServerSocket listening = new ServerSocket(8080);
        System.out.println("Listening on http://localhost:8080");

        while (true) {
            // 4. accept() — BLOCKS here until a client connects.
            Socket client = listening.accept();
            System.out.println("Connected: " + client.getRemoteSocketAddress());

            BufferedReader in = new BufferedReader(
                    new InputStreamReader(client.getInputStream()));
            OutputStream out = client.getOutputStream();

            // Read the request line, e.g. "GET / HTTP/1.1"
            String requestLine = in.readLine();
            System.out.println("Request: " + requestLine);

            // Drain the headers — they end with a blank line.
            String header;
            while ((header = in.readLine()) != null && !header.isEmpty()) {
                System.out.println("  " + header);
            }

            // Write an HTTP response BY HAND. This is all HTTP is: text.
            String body = "<h1>I wrote this server myself</h1>";
            String response =
                    "HTTP/1.1 200 OK\r\n" +
                    "Content-Type: text/html\r\n" +
                    "Content-Length: " + body.length() + "\r\n" +
                    "\r\n" +                                   // blank line = headers done
                    body;

            out.write(response.getBytes());
            out.flush();
            client.close();
        }
    }
}
```

Run it. Open `http://localhost:8080` in a browser.

**You just wrote a web server.** Not a toy version of one — the same four system calls Nginx makes.
Nginx has 200,000 more lines of edge cases, performance work and configuration, but the loop is this
loop.

### Now look at what you did

- **You typed the HTTP response by hand.** HTTP is *text*, with a specific shape: status line,
  headers, blank line, body. That `\r\n\r\n` is the whole protocol boundary. When Day 010 covers
  HTTP anatomy, you'll already have written one.
- **You read the request the browser sent.** Look at your console — those are real HTTP headers the
  browser chose to send. Read them.
- **`Content-Length` matters.** Change it to a wrong number and reload. The browser will hang
  waiting for bytes that never come, or truncate. That's you feeling why the header exists.

### Three experiments, do all of them

**1. Connect with `telnet` instead of a browser** and be the client yourself:

```bash
telnet localhost 8080
GET / HTTP/1.1
Host: localhost
<press Enter twice>
```

You just spoke HTTP with your fingers. A browser is only doing this faster.

**2. Comment out `client.close()`.** Reload a few times. Watch what happens — file descriptors leak,
and eventually you run out. That's a resource leak, and it's why `try-with-resources` (Day 061)
exists.

**3. Add `Thread.sleep(10000)` before the response, then open two browser tabs.**

The second tab waits for the first. **Your server handles exactly one client at a time**, because
the loop can't reach `accept()` again until it finishes with the current client.

This is the single-threaded server problem, and it is *the* motivation for:

- Thread-per-request (Day 064, 069) — spawn a thread per client, loop back to `accept()` immediately
- Thread pools (Day 069) — because unbounded thread creation dies under load
- Non-blocking I/O and epoll (B-13, B-14) — one thread, many connections
- Virtual threads (Day 072) — thread-per-request ergonomics without the cost
- Tomcat's `server.tomcat.max-threads` (Day 185) — a number you'll now understand

**Fix it yourself** before reading on. One line, wrapping the handling in `new Thread(...)`. Then
open two tabs again.

## Common mistakes

| Mistake | Correction |
|---|---|
| Thinking a server is special hardware | It's a process on an ordinary machine. Your laptop is running several right now. |
| Not knowing `accept()` returns a new socket | The listening socket keeps listening. The returned socket is for one client. |
| Thinking a blocked server burns CPU | The OS parks the thread. An idle server uses ~0% CPU. |
| "Frameworks do something fundamentally different" | Spring Boot embeds Tomcat, which makes these same four calls. Everything above is dispatch and convenience. |
| Forgetting `Content-Length` or the blank line | The client can't tell where headers end or the body stops. This is why your hand-written response hangs. |
| Assuming concurrency is free | Your first server handles one client at a time. Concurrency is a *decision* you make. |

## Interview questions

**Q: What is a server?**
> A program that creates a socket, binds it to a port, listens, and then loops calling `accept()`,
> which blocks until a client connects. Each accepted connection gives a new socket for that client.
> It's a process in a wait loop — not special hardware.

**Q: What happens when a client connects?**
> The TCP handshake completes in the kernel and the connection is placed on the listen backlog
> queue. The next `accept()` call removes it from that queue and returns a connected socket
> identified by the 4-tuple. The listening socket is unaffected and continues accepting.

**Q: How does a server handle multiple clients on one port?**
> Connections are identified by source IP, source port, destination IP and destination port, so each
> client's connection is a distinct tuple despite sharing the destination port. Concurrency is then a
> separate choice — a thread per connection, a thread pool, or non-blocking I/O with an event loop.

**Q: What does it mean that `accept()` blocks?**
> The calling thread is put into a non-runnable state by the OS and consumes no CPU. The kernel wakes
> it when a connection lands on the backlog queue.

**Q: What's the difference between a listening socket and a connected socket?**
> The listening socket is bound to a port and only produces new connections via `accept()`; you never
> read or write data on it. A connected socket represents one client conversation and is what you
> read from and write to.

# Part 2 — C-03 · The network layer

## The job

Data link (C-02) gets a frame to the **next device**. The network layer gets a packet to the
**final machine**, across any number of intermediate networks. That's routing.

## IP addressing

IPv4: 32 bits, written as four octets — `203.0.113.7`. Every address splits into a **network part**
and a **host part**.

**CIDR notation** says where the split is:

```
   192.168.1.0/24
   └──────┬─────┘ └┬┘
      address    prefix length = how many bits are the network

   /24  →  first 24 bits network, last 8 bits host
        →  192.168.1.0   network address (not usable)
           192.168.1.1 – 192.168.1.254   usable hosts
           192.168.1.255 broadcast
        →  254 usable addresses
```

| CIDR | Subnet mask | Usable hosts |
|---|---|---|
| /24 | 255.255.255.0 | 254 |
| /16 | 255.255.0.0 | 65,534 |
| /8 | 255.0.0.0 | 16,777,214 |
| /30 | 255.255.255.252 | 2 (point-to-point links) |

**Quick formula:** usable hosts = 2^(32 − prefix) − 2. The two subtracted are the network address
and the broadcast address.

You will use this directly when you build a VPC on Day 383, and every time you write a security
group rule.

### Private ranges

Not routable on the public internet — reserved for internal networks:

```
10.0.0.0/8         10.0.0.0     – 10.255.255.255      (AWS VPCs love this one)
172.16.0.0/12      172.16.0.0   – 172.31.255.255      (Docker's default range)
192.168.0.0/16     192.168.0.0  – 192.168.255.255     (your home router)
127.0.0.0/8        loopback — localhost
```

Recognise these on sight. When you see `172.17.0.2` you should immediately think "that's a Docker
container".

## Routing

A router holds a **routing table** mapping destination networks to next hops.

```
   Destination        Next hop       Interface
   192.168.1.0/24     direct         eth0        ← my own network
   10.0.0.0/8         192.168.1.254  eth0
   0.0.0.0/0          192.168.1.1    eth0        ← default route: everything else
```

For each packet the router picks the **longest prefix match** — the most specific rule wins. A
packet for `10.1.2.3` matches both `10.0.0.0/8` and `0.0.0.0/0`; the /8 is more specific, so it wins.

Each hop makes an independent decision. No router knows the full path. **TTL** (time to live)
decrements at every hop and the packet is dropped at zero — that's what prevents infinite loops, and
it's exactly what `traceroute` exploits to map a path.

## NAT

There aren't enough IPv4 addresses. **Network Address Translation** lets many private addresses
share one public one.

```
  Your laptop                Router (NAT)                    Server
  192.168.1.5:51234  ───▶   rewrites source to        ───▶  203.0.113.9:443
                            198.51.100.7:62001

                            keeps a table:
                            198.51.100.7:62001 ↔ 192.168.1.5:51234

  192.168.1.5:51234  ◀───   rewrites destination back ◀───  reply to
                                                            198.51.100.7:62001
```

**Two consequences you'll hit:**

1. **Inbound connections don't work by default.** Nothing outside can initiate a connection to
   `192.168.1.5` — the NAT has no table entry until *you* initiate. This is why you need port
   forwarding to host from home, and why `localhost:8080` works on your machine but nobody else can
   reach it.
2. **NAT is stateful.** The table entry expires. That's why long-idle connections silently die, and
   why TCP keepalives and WebSocket ping/pong frames (Day 017) exist.

## Type this yourself

```bash
ipconfig              # Windows: your IP, subnet mask, default gateway
route print           # Windows: your routing table
tracert google.com    # watch TTL expiry reveal each hop

# Linux/Mac equivalents
ip addr ; ip route ; traceroute google.com
```

Look at your own IP. Is it `192.168.x.x` or `10.x.x.x`? Then you're behind NAT. Compare it to what
[whatismyip.com](https://whatismyip.com) reports — that's your router's public address. **Those two
being different is NAT, observed directly.**

## Interview questions

**Q: What does /24 mean?**
> The first 24 bits are the network portion, leaving 8 bits for hosts — 256 addresses, 254 usable
> after excluding the network and broadcast addresses.

**Q: How does a router decide where to send a packet?**
> Longest prefix match against its routing table — the most specific matching route wins, falling
> back to the default route `0.0.0.0/0`. Each router decides independently; none knows the whole path.

**Q: What is NAT and what problem does it create?**
> It maps many private addresses to one public address by rewriting source address and port, and
> keeping a translation table. It conserves IPv4 addresses, but breaks inbound connections — nothing
> external can initiate to a private host without explicit port forwarding.

**Q: Why does TTL exist?**
> It's decremented at each hop and the packet is discarded at zero, preventing packets from looping
> forever when routing tables are inconsistent. `traceroute` deliberately sends low TTLs to make each
> hop reveal itself.
