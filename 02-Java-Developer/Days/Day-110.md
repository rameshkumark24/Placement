# Part 1 — L-110 · OpenAPI

## What it is

**OpenAPI** (formerly Swagger) is a specification for describing an HTTP API in a machine-readable
document. **Swagger** now refers to the tooling around it — Swagger UI, Swagger Codegen.

The point is not documentation. It is that **a machine-readable contract can be used by tools**:

| Tool | Uses the spec to |
|---|---|
| Swagger UI / Redoc | Render browsable, executable documentation |
| openapi-generator | Generate typed clients in ~50 languages, and server stubs |
| Prism, WireMock | Run a mock server before any code exists |
| Schemathesis, Dredd | **Generate tests** from the spec and fuzz your API against it |
| Spectral | Lint the spec against your organisation's style rules |
| API gateways | Enforce request validation and rate limits at the edge |
| openapi-diff | **Detect breaking changes in CI** (Day 109) |

That last one is worth pausing on: **`openapi-diff` in CI turns Day 109's compatibility rules into an
automated check.** A PR that removes a response field or adds a required parameter fails the build.
That is the single highest-value thing you can do with an OpenAPI document.

## The document

```yaml
openapi: 3.1.0
info:
  title: Orders API
  version: 1.4.0
  description: Order lifecycle management.
servers:
  - url: https://api.acme.com/v1
    description: Production
  - url: https://sandbox.acme.com/v1

paths:
  /orders:
    get:
      summary: List orders
      operationId: listOrders          # ← becomes the generated client's method name
      parameters:
        - name: status
          in: query
          schema: { $ref: '#/components/schemas/OrderStatus' }
        - name: cursor
          in: query
          schema: { type: string }
        - name: limit
          in: query
          schema: { type: integer, minimum: 1, maximum: 100, default: 20 }
      responses:
        '200':
          description: A page of orders
          content:
            application/json:
              schema: { $ref: '#/components/schemas/OrderPage' }
        '400': { $ref: '#/components/responses/Problem' }
        '429': { $ref: '#/components/responses/Problem' }

    post:
      summary: Create an order
      operationId: createOrder
      parameters:
        - name: Idempotency-Key         # ← Day 102
          in: header
          required: true
          schema: { type: string, format: uuid }
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/CreateOrderRequest' }
      responses:
        '201':
          description: Created
          headers:
            Location: { schema: { type: string, format: uri } }
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '422': { $ref: '#/components/responses/Problem' }

components:
  schemas:
    OrderStatus:
      type: string
      enum: [NEW, PAID, SHIPPED, DELIVERED, CANCELLED]
    Money:
      type: object
      required: [amount, currency]
      properties:
        amount:   { type: string, pattern: '^-?\d+\.\d{2}$', example: '1499.00' }  # ← Day 106
        currency: { type: string, minLength: 3, maxLength: 3, example: INR }
    Order:
      type: object
      required: [id, status, total, created_at]
      properties:
        id:         { type: string, example: ord_8f14e45f }      # ← string ids, Day 103
        status:     { $ref: '#/components/schemas/OrderStatus' }
        total:      { $ref: '#/components/schemas/Money' }
        created_at: { type: string, format: date-time }

  responses:
    Problem:                                                      # ← Day 104
      description: An error occurred
      content:
        application/problem+json:
          schema:
            type: object
            required: [type, title, status]
            properties:
              type:   { type: string, format: uri }
              title:  { type: string }
              status: { type: integer }
              detail: { type: string }

  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }

security:
  - bearerAuth: []
```

Note how much of Stages 3's earlier days is encoded here: money as a patterned string, string ids,
the problem+json error shape, the idempotency key, cursor pagination, a bounded `limit`. **The spec
is where your design decisions become enforceable.**

## Contract-first vs code-first

**Code-first** — write the Java, generate the spec from annotations (springdoc, swagger-core).

```java
@Operation(summary = "Create an order")
@ApiResponse(responseCode = "201", description = "Created")
@PostMapping("/orders")
public ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest r) { … }
```

✅ The spec cannot drift from the implementation — it is derived from it. Fast to start, no extra
tooling.
❌ The spec is a *consequence* of your code, so accidental implementation details leak into your
public contract. Frontend teams cannot start until the backend exists. And it invites designing the
API by writing controllers, which is how you end up with an API shaped like your service layer
(Day 103).

**Contract-first** — write the YAML, generate stubs and clients, implement against it.

✅ **The API is designed deliberately, before code exists.** Frontend, mobile and backend can work in
parallel against a generated mock from day one. The contract is reviewable by consumers *before* it
is expensive to change. Breaking-change detection is natural.
❌ The spec and implementation can drift unless you enforce conformance. YAML is verbose. There is a
learning curve.

> **Recommendation: contract-first for a public API or when several teams consume it; code-first for
> an internal service where the consumer is you.**

**The drift problem has a real fix**, and it is what makes contract-first practical:

```bash
schemathesis run --checks all openapi.yaml --base-url http://localhost:8080
```

Schemathesis generates requests from the spec — including edge cases and malformed inputs — and
asserts that responses conform. **Run it in CI and drift becomes a test failure**, which removes
contract-first's main objection.

## Practical notes

**JSON Schema alignment.** OpenAPI 3.1 is fully JSON Schema 2020-12 compatible, which 3.0 was not.
Use 3.1 for new work; you can then reuse the same schemas for validation elsewhere.

**`$ref` everything.** Duplicated inline schemas drift. Define once in `components`, reference
everywhere.

**Examples are the most-read part of your documentation.** Developers read examples, not schemas.
Provide a realistic one for every request and response — and for the error cases especially.

**Document errors, not just the happy path.** An API whose spec shows only `200` is half a
specification, and it is the half nobody needs.

**Lint it.** Spectral enforces your conventions (Day 103's consistency decisions) automatically —
naming style, required descriptions, forbidden patterns.

**Do not commit generated clients.** Generate at build time from the pinned spec version, so they
cannot drift.

# Part 2 — D-11 ⭐ · Indexes

## What an index is

**A separate data structure that makes lookups fast, at the cost of space and slower writes.** The
table is the data; the index is a sorted map from a value to the rows holding it.

```
Table (heap):                     Index on email (B+ tree):
  row 1: ram@…,  Ram                  ada@… → row 3
  row 2: sita@…, Sita                 ram@… → row 1
  row 3: ada@…,  Ada                  sita@…→ row 2
```

Without an index: **a sequential scan** — read every row, O(n). With one: **an index scan** —
O(log n) tree descent, then a lookup.

On 10 million rows that is roughly 23 comparisons versus 10 million reads.

## B+ tree — the default, and why

Nearly every index you meet is a B+ tree. The structure:

```
                    [ 50 | 100 ]                      ← internal nodes: keys only, for routing
                   /     |      \
        [10|25|40]   [60|75|90]   [120|150]
           /  |  \                                    ← LEAF nodes: keys + row pointers
     [leaf]…[leaf]…[leaf] ⇄ [leaf] ⇄ [leaf] ⇄ …      ← leaves are LINKED
```

Four properties, each with a direct consequence:

1. **Balanced** — every leaf is at the same depth, so every lookup costs the same. No pathological
   case.
2. **High fan-out** — a node is one disk page (8 KB) holding hundreds of keys, so a tree over
   millions of rows is only **3–4 levels deep**. Three or four page reads to find any row, and the
   upper levels are always cached.
3. **All data in the leaves; internal nodes are routing only** — that is the "+" in B+ tree, and it
   is what maximises fan-out.
4. **Leaves are linked** — so a **range scan** is a descent to the start followed by a linear walk.
   This is why one index serves `=`, `<`, `>`, `BETWEEN`, `ORDER BY` *and* prefix `LIKE`.

That fourth property is the practical reason B+ trees beat hash indexes almost everywhere.

## The other index types

| Type | Structure | Good for | Cannot do |
|---|---|---|---|
| **B+ tree** | Balanced tree | `=`, ranges, `ORDER BY`, prefix `LIKE` | — |
| **Hash** | Hash table | `=` only, O(1) | **No ranges, no sorting** |
| **GIN** | Inverted index | Full-text, arrays, `jsonb` containment (Day 108) | Slow writes |
| **GiST** | Generalised search tree | Geometric, nearest-neighbour, ranges | |
| **BRIN** | Min/max per block range | **Huge naturally-ordered tables** (time series) — tiny index | Only correlated data |
| **Bitmap** | Bit per row per value | Low-cardinality columns in warehouses | Poor for OLTP writes |

**BRIN is the under-used one worth knowing**: on a 500 GB append-only events table ordered by time, a
BRIN index on `created_at` is a few megabytes and prunes almost all blocks. A B+ tree on the same
column would be tens of gigabytes.

## Clustered vs non-clustered

**This is the concept that most affects real query performance**, and it differs by engine.

**Clustered index** — the table *is* the index; rows are stored in the index's leaves, in key order.
**One per table**, by definition.

**Non-clustered (secondary)** — a separate structure whose leaves hold pointers back to the rows.

| Engine | Behaviour |
|---|---|
| **MySQL / InnoDB** | The primary key is **always clustered**. Secondary indexes store the **PK value**, so every secondary lookup is two tree descents. |
| **PostgreSQL** | **No clustered indexes.** All indexes are secondary and point at a heap tuple (`ctid`). `CLUSTER` is a one-off physical reorder that is not maintained. |
| **SQL Server** | The PK is clustered by default; you may choose otherwise. |

Two consequences that come up constantly:

**In InnoDB, your primary key choice affects every index.** A UUID v4 primary key means (a) random
insert positions causing page splits and fragmentation, and (b) a 16-byte value copied into every
secondary index. This is exactly why **UUID v7 / ULID** (Day 103) matters — time-ordered keys append
at the right edge of the tree instead of scattering.

**In PostgreSQL, an index scan usually needs a heap fetch too**, unless the visibility map allows an
index-only scan — which is why `VACUUM` affects read performance, not just space.

## Composite indexes and the leftmost-prefix rule

```sql
CREATE INDEX idx_orders ON orders (customer_id, status, created_at);
```

**Column order is everything.** The index is sorted by `customer_id`, then `status`, then
`created_at` — like a phone book sorted by surname, then first name.

| Query | Uses the index? |
|---|---|
| `WHERE customer_id = 1` | ✅ |
| `WHERE customer_id = 1 AND status = 'PAID'` | ✅ |
| `WHERE customer_id = 1 AND status = 'PAID' AND created_at > …` | ✅ fully |
| `WHERE customer_id = 1 AND created_at > …` | ⚠️ partially — only `customer_id`, then filter |
| `WHERE status = 'PAID'` | ❌ **no leftmost prefix** |
| `WHERE created_at > …` | ❌ |

> **A composite index can be used for any *leftmost prefix* of its columns, and for a range on the
> first column that is not fully specified — but nothing after a range is usable for seeking.**

The ordering heuristic: **equality columns first, then the range column, then the sort column.**
`WHERE customer_id = ? AND created_at > ? ORDER BY created_at` wants
`(customer_id, created_at)` — equality, then range-and-sort together.

## Covering indexes and index-only scans

```sql
-- The query needs only three columns
SELECT customer_id, status, created_at FROM orders WHERE customer_id = 42;

CREATE INDEX idx ON orders (customer_id, status, created_at);
-- ⇒ every column is IN the index ⇒ the table is never touched. INDEX-ONLY SCAN.
```

A **covering index** contains every column the query needs, so the database answers entirely from the
index. This often gives a 2–10× improvement, because it eliminates the random heap access.

```sql
-- INCLUDE: extra columns stored in the LEAVES only — not part of the key, so no sort cost
CREATE INDEX idx ON orders (customer_id) INCLUDE (status, total_cents);
```

`INCLUDE` (PostgreSQL 11+, SQL Server) is the right tool: keeps the key narrow while still covering.

## Partial and expression indexes

```sql
-- PARTIAL: index only the rows you actually query
CREATE INDEX idx_active ON orders (created_at) WHERE status = 'PENDING';
-- If 1% of orders are pending, this index is 1% of the size and far hotter in cache.

-- Also enforces a conditional constraint (Day 084's library example)
CREATE UNIQUE INDEX one_active_loan ON loan (copy_id) WHERE returned_on IS NULL;

-- EXPRESSION: makes a non-sargable predicate sargable (Day 097)
CREATE INDEX idx_lower_email ON users (LOWER(email));
SELECT * FROM users WHERE LOWER(email) = LOWER(:input);     -- ✅ now uses the index
```

Partial indexes are dramatically under-used and are often the cheapest big win available on a table
where queries always filter on one status.

## When an index does *not* help

| Situation | Why |
|---|---|
| Low cardinality (`is_active` with 2 values) | Half the table matches; a scan is cheaper |
| The query returns a large fraction of rows | Random I/O per row beats sequential reading |
| A function on the column | Not sargable — needs an expression index |
| Leading wildcard `LIKE '%x'` | No usable prefix |
| Implicit type conversion | `WHERE varchar_col = 123` may disable the index |
| Small table | The whole thing fits in one or two pages |
| `OR` across different columns | May need two indexes and a bitmap combine |

**The cost of every index:**

- **Writes slow down.** Every `INSERT`, `UPDATE` and `DELETE` must maintain every affected index. A
  table with eight indexes has slow writes, and that is usually the cause when someone says "our
  inserts got slow".
- **Space** — often 10–30% of the table each.
- **The planner has more options**, and occasionally chooses badly.

> **Index for your actual queries, not speculatively.** Find unused indexes and drop them:

```sql
SELECT relname, indexrelname, idx_scan FROM pg_stat_user_indexes WHERE idx_scan = 0;
```

## Reading a plan

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_id = 42 AND status = 'PAID';
```

What to look for:

| Sign | Meaning |
|---|---|
| `Seq Scan` on a large table with a selective filter | A missing index |
| `Index Scan` then `Heap Fetches: 0` | An index-only scan — ideal |
| **`rows=1000` estimated vs `actual rows=900000`** | **Stale statistics — run `ANALYZE`** |
| `Nested Loop` with a large outer | Missing index on the inner side (Day 100) |
| `Sort` with `Disk` spill | `work_mem` too small, or a missing index for the sort |
| `Filter: …` removing many rows | The predicate is not in the index |

**Estimated versus actual is the single most useful number in the output.** A large divergence means
the planner is choosing based on wrong information, and `ANALYZE` fixes more "sudden slowdowns" than
any query rewrite.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Code-first for a public API | Implementation details leak into the contract |
| Duplicated inline schemas | Drift between endpoints |
| Documenting only the happy path | Half a specification |
| No breaking-change check in CI | Day 109's rules are unenforced |
| Committing generated clients | They drift from the spec |
| Indexing every column | Slow writes, wasted space |
| Wrong composite column order | The index is never used |
| Range column before equality columns | Everything after the range is unusable |
| Function on an indexed column | Not sargable |
| UUID v4 primary key in InnoDB | Page splits, fragmentation, bloated secondary indexes |
| Assuming an index always helps | Low cardinality and large result sets do not benefit |
| Never checking `pg_stat_user_indexes` | Unused indexes cost writes forever |
| Not running `ANALYZE` | Bad plans from stale statistics |

## Interview questions

**Q: Contract-first or code-first?**
Contract-first for public or multi-consumer APIs — the API is designed deliberately, consumers can
work against a mock immediately, and the contract is reviewable before it is expensive. Code-first
for internal services. Drift is handled by running schemathesis against the spec in CI.

**Q: What is the highest-value use of an OpenAPI document?**
Automated breaking-change detection in CI with `openapi-diff` — it turns compatibility rules into a
build failure instead of a support incident.

**Q: Why is a B+ tree used rather than a binary tree or a hash table?**
High fan-out means only 3–4 levels over millions of rows, so few disk reads; it is balanced, so every
lookup costs the same; and the linked leaves make ranges and ordering efficient — which a hash index
cannot do at all.

**Q: Explain the leftmost-prefix rule.**
A composite index on `(a, b, c)` serves queries filtering on `a`, `a+b`, or `a+b+c` — any leftmost
prefix. A query on `b` alone cannot use it, and nothing after a range predicate can be used for
seeking.

**Q: What is a covering index?**
One containing every column a query needs, so the query is answered from the index alone without
touching the table — often 2–10× faster because it avoids random heap access. `INCLUDE` adds
non-key columns to the leaves for exactly this.

**Q: Clustered vs non-clustered?**
A clustered index stores the rows themselves in key order, so there is one per table. In InnoDB the
primary key is always clustered and secondary indexes store the PK value, meaning two descents per
secondary lookup. PostgreSQL has no clustered indexes — all are secondary, pointing into the heap.

**Q: When does an index not help?**
Low cardinality, queries returning a large fraction of rows, non-sargable predicates, leading
wildcards, and small tables. And every index slows writes, so unused ones are pure cost.

**Q: A query suddenly got slow with no code change. Why?**
Most often stale statistics — the planner's row estimates diverged from reality and it chose a
different plan. Check estimated versus actual rows in `EXPLAIN ANALYZE` and run `ANALYZE`. Data
growth crossing a planner threshold is the other usual cause.

## 🎙️ Articulation drill

Three minutes today: **"A query is slow. Walk me through diagnosing and fixing it."**

`EXPLAIN ANALYZE` first; compare estimated to actual rows and run `ANALYZE` if they diverge; look for
a sequential scan with a selective filter; check whether the predicate is sargable; design a
composite index with equality columns first, then the range, then the sort; consider covering it with
`INCLUDE` to get an index-only scan; then verify with `BUFFERS` and confirm you have not slowed
writes. Naming the *order* is what makes it a method.
