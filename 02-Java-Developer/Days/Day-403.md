# Part 1 — ⭐⭐ Replication, ISR and the high watermark

```
⭐ Partition P0, replication.factor=3:
⭐   ⭐⭐ LEADER (broker 1)  ← all reads and writes go here
⭐   follower (broker 2)  ← fetches from the leader
⭐   follower (broker 3)  ← fetches from the leader

⭐⭐ ISR = IN-SYNC REPLICAS = replicas that have fetched within `replica.lag.time.max.ms` (~30 s)
⭐   ⇒ ⭐ a slow or restarting broker DROPS OUT of the ISR and rejoins when caught up
⭐   ⇒ ⭐⭐ min.insync.replicas is checked against the ISR SIZE (Day 401)
```

| ⭐⭐ The high watermark | |
|---|---|
| ⭐⭐ **Consumers can only read up to the high watermark** | ⭐⭐ the highest offset replicated to **all** ISR members |
| ⭐ Why | ⭐⭐ **so a consumer never reads a message that a leader failure could un-write** |
| ⭐ Consequence | ⭐ replication lag is **consumer-visible latency**, not just a durability metric |

```
⭐⭐ UNCLEAN LEADER ELECTION — the availability/durability switch, stated plainly:
⭐   unclean.leader.election.enable = FALSE (⭐ default, ⭐⭐ correct)
⭐     ⇒ ⭐ if no ISR member survives, ⭐⭐ THE PARTITION GOES OFFLINE. You lose availability.
⭐   unclean.leader.election.enable = TRUE
⭐     ⇒ ⭐ an out-of-sync replica becomes leader ⇒ ⭐⭐ COMMITTED MESSAGES SILENTLY VANISH,
⭐       ⭐⭐ and consumers may have already read them. ⭐ The log TRUNCATES backwards.
⭐ ⇒ ⭐⭐ This is CAP as a boolean in a properties file (Day 330).
```

# Part 2 — ⭐⭐ Retention, and compaction as a table

| Policy | ⭐ Behaviour |
|---|---|
| ⭐ `cleanup.policy=delete` | ⭐ drop segments older than `retention.ms` or beyond `retention.bytes` |
| ⭐⭐ **`cleanup.policy=compact`** | ⭐⭐ **keep the LATEST value for every key, forever** |
| ⭐ `compact,delete` | compact, and also drop very old data |

```
⭐⭐ COMPACTION TURNS A STREAM INTO A TABLE:
⭐   before:  (k1,v1) (k2,v1) (k1,v2) (k3,v1) (k1,v3) (k2,v2)
⭐   after:                    ⭐⭐ (k3,v1) (k1,v3) (k2,v2)
⭐   ⇒ ⭐⭐ the topic now IS the current state of every key — a durable, replayable KEY-VALUE STORE
⭐   ⇒ ⭐⭐ a new consumer replaying from offset 0 rebuilds the ENTIRE state. From the log.
```

| ⭐ What compaction makes possible | |
|---|---|
| ⭐⭐ **Kafka Streams state stores / KTables** | ⭐⭐ a changelog topic that can rebuild local state after a crash |
| ⭐⭐ **Debezium and CDC snapshots** | ⭐ the current row per primary key (Day 407) |
| ⭐ Config distribution, entitlements, reference data | ⭐ "the latest value per key" is exactly the semantics |
| ⭐⭐ **Tombstones** | ⭐⭐ a record with a **null value** marks a key deleted; removed after `delete.retention.ms` |

⚠️ **Compaction guarantees are weaker than people assume.** It is **eventual** — the head of the log
(the active segment) is never compacted, so duplicates for a key exist for a while. **You get "the latest
value survives", not "only one record per key at all times"** — so consumers must still be idempotent and
must handle seeing an older value before a newer one during replay.

⚠️ **And the GDPR consequence is real:** a compacted topic keeps the latest value **forever**. To erase a
key you must write a **tombstone** and then wait out `delete.retention.ms`. **If the data is personal,
plan the erasure path before you create the topic** — or encrypt per subject and delete the key
(Day 395's crypto-shredding, and Day 405 again).

# Part 3 — ⭐⭐ Transactions and exactly-once, bounded honestly

```
⭐ Kafka transactions let you make ⭐⭐ ATOMIC a "read-process-write" cycle:
⭐   consume from topic A → produce to topic B → ⭐⭐ COMMIT THE CONSUMER OFFSET IN THE SAME TXN
⭐   ⇒ ⭐⭐ either the output AND the offset are visible, or NEITHER is.
```

```java
producer.initTransactions();                     // ⭐ once, with a stable transactional.id
while (running) {
    var records = consumer.poll(Duration.ofMillis(500));
    producer.beginTransaction();
    for (var r : records) producer.send(transform(r));
    // ⭐⭐ the offsets are part of the transaction — this is the whole trick
    producer.sendOffsetsToTransaction(offsetsOf(records), consumer.groupMetadata());
    producer.commitTransaction();
}
```

| ⭐ Requirement | |
|---|---|
| ⭐⭐ `isolation.level=read_committed` on consumers | ⭐⭐ **otherwise they read aborted messages** |
| ⭐ A stable `transactional.id` per logical producer | ⭐ enables zombie fencing across restarts |
| ⭐ `processing.guarantee=exactly_once_v2` in Streams | ⭐ Kafka Streams does all of this for you |
| ⭐⭐ **Cost** | ⭐⭐ extra round trips, higher latency, and `read_committed` consumers **wait for the LSO** |

```
⭐⭐ WHERE THE GUARANTEE STOPS — say this precisely, it is the point of the day:
⭐   ✅ ⭐⭐ Kafka → (process) → Kafka          ⇒ ⭐⭐ EXACTLY ONCE. Genuinely.
⭐   ❌ ⭐⭐ Kafka → (process) → POSTGRES        ⇒ ⭐⭐ two systems, no shared transaction
⭐   ❌ ⭐⭐ Kafka → (process) → PAYMENT GATEWAY ⇒ ⭐⭐ you cannot un-charge a card by aborting
⭐   ❌ ⭐⭐ Kafka → (process) → EMAIL           ⇒ ⭐⭐ the email is sent. There is no rollback.
⭐ ⇒ ⭐⭐ For those, the answer is UNCHANGED: at-least-once + an IDEMPOTENT consumer,
⭐   ⭐ with the dedup key and the business change in ONE database transaction (Day 335, 407).
```

> **⭐⭐ This refines Day 334 rather than contradicting it.** "Exactly-once delivery is impossible" is
> still true. **What Kafka provides is exactly-once *processing* inside a closed system**, which is a
> real and useful thing — **and which stops being available the instant an external side effect
> appears.** Being able to draw that boundary is a senior-level distinction.

# Part 4 — ⭐ Operating it, and the modern shape

| Topic | ⭐ Note |
|---|---|
| ⭐⭐ **KRaft** | ⭐⭐ ZooKeeper is gone — Kafka runs its own **Raft** quorum for metadata (Day 410) |
| ⭐ **Tiered storage** | ⭐ old segments to S3 — **retention stops being a disk-size decision** |
| ⭐ Rack awareness | ⭐⭐ `broker.rack` spreads replicas across AZs — **without it, RF=3 can land in one AZ** |
| ⭐ Cross-AZ cost | ⭐⭐ replication traffic is cross-AZ traffic (Day 396); **follower fetching** helps consumers |
| ⭐ Quotas | per-client throughput limits — a real noisy-neighbour control |
| ⭐⭐ **Schema registry** | ⭐⭐ compatibility enforced at produce time, not at incident time (Day 400) |

⚠️ **Kafka is expensive and operationally heavy.** Three brokers minimum for a meaningful RF, cross-AZ
replication traffic, disks, and an on-call rotation that understands ISR shrinkage. **For a team that
needs a work queue, SQS or RabbitMQ is a better answer** (Day 404) — **choose Kafka for replay, multiple
independent consumers, retention as a feature, and stream processing.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Not knowing the high watermark exists | ⭐ replication lag surprises you as consumer latency |
| ⭐⭐ **`unclean.leader.election=true`** | ⭐⭐ committed messages vanish and the log truncates |
| ⭐ No `broker.rack` | ⭐⭐ three replicas in one AZ — RF=3 that survives nothing |
| ⭐ Treating compaction as immediate | ⭐⭐ it is eventual; the active segment is never compacted |
| ⭐ Expecting one record per key | ⭐ you get "the latest survives", not uniqueness |
| ⭐ Forgetting tombstones for deletes | ⭐⭐ a compacted topic keeps the value forever |
| ⭐⭐ **Personal data in a compacted topic with no erasure plan** | ⭐⭐ GDPR erasure becomes very hard |
| ⭐⭐ **Claiming exactly-once for external side effects** | ⭐⭐ it applies only Kafka-to-Kafka |
| ⭐ Transactions without `read_committed` | ⭐⭐ consumers read aborted records |
| ⭐ Transactions with an unstable `transactional.id` | zombie fencing does not work |
| ⭐ Using transactions everywhere by default | ⭐ latency cost for a guarantee you often do not need |
| Choosing Kafka for a simple work queue | operational weight for unused capability |

## Interview questions

**Q: What is the ISR and why does it matter?**
The in-sync replica set is the replicas that have fetched from the leader recently enough. It matters
twice: `min.insync.replicas` is checked against its size, so durability guarantees are really guarantees
about the ISR, and consumers can only read up to the high watermark — the highest offset present on all
ISR members — so a message is invisible until it is safely replicated. That is deliberate: it stops a
consumer reading something a leader failure could un-write. A practical consequence people miss is that
replication lag is consumer-visible latency, not just a durability metric.

**Q: What does unclean leader election trade?**
Durability for availability, as a boolean in a properties file. Left false, if no in-sync replica
survives, the partition simply goes offline and you have an outage. Set true, an out-of-sync replica is
promoted, the log truncates backwards, and committed messages vanish — possibly messages consumers have
already read and acted on. It is the CAP choice made concrete, and the default is false because silent
data loss is almost always worse than a visible outage.

**Q: What is log compaction for?**
It turns a stream into a table. With `cleanup.policy=compact` Kafka retains the latest value for every
key indefinitely, so the topic becomes a durable, replayable key-value store and a new consumer replaying
from offset zero rebuilds the entire current state. That is what makes Kafka Streams state stores
recoverable and what CDC snapshots rely on. Two caveats: compaction is eventual — the active segment is
never compacted, so duplicates for a key exist for a while — and deletion requires writing a tombstone,
which makes personal data in a compacted topic something you have to plan an erasure path for before you
create it.

**Q: Does Kafka give you exactly-once?**
Within Kafka, yes, and it is genuine: transactions make a read-process-write cycle atomic by committing
the consumer offsets as part of the same transaction as the output records, so either both are visible or
neither is — provided consumers read with `read_committed`. Outside Kafka, no. The moment the side effect
is a Postgres row, a payment authorisation or an email, you have two systems and no shared transaction,
and you are back to at-least-once with an idempotent consumer. So exactly-once processing inside a closed
system is real; exactly-once delivery to the outside world remains impossible, and drawing that boundary
precisely is the point.

**Q: When would you not choose Kafka?**
When you want a work queue. Kafka is expensive and operationally heavy — several brokers, cross-zone
replication traffic, disks, and people who understand what a shrinking ISR means. If what you need is
competing consumers with per-message acknowledgement, retries and a dead letter queue, SQS or RabbitMQ
gives you that with no operational burden and better per-message semantics. Kafka earns its cost when you
need replay, several independent consumer groups reading the same stream, retention as a product feature,
ordering per key at volume, or stream processing.

## 🎙️ Articulation drill

**Two minutes:** *"Does Kafka give you exactly-once?"*

**⭐ Answer with a boundary, not a yes or no. Inside Kafka it is real: transactions commit the consumer
offsets as part of the same transaction as the produced records, so a read-process-write cycle is atomic
— either the output and the offset are both visible or neither is, provided consumers read committed.**

**⭐ The moment a side effect leaves Kafka, it stops. A Postgres write, a card authorisation, an email —
two systems, no shared transaction, and no amount of broker configuration changes that. There the answer
is unchanged: at-least-once delivery with an idempotent consumer, dedup key and business change in one
database transaction.**

world is still impossible. Knowing precisely where that line sits is more useful than either slogan.**
