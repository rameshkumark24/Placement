# Day 264 🏗️

**P-264** · Background jobs — the expiry job, and everything it teaches

**Time:** 3 hrs · **Mode:** BUILD

> Day 249's state machine had an arrow nobody triggers: `PENDING → EXPIRED`. **That single arrow is a
> whole subsystem**, and building it correctly exercises Day 178 completely — the single-threaded
> scheduler, the distributed problem, idempotency, and the alert nobody writes.
>
> **⭐ The measure of this day: your job runs safely on three instances with no lock at all**, because
> it claims work atomically. That is a stronger position than locking, and it is the answer Day 178
> ranked above ShedLock.

---

# Part 1 — ⭐ The scheduler, configured

```
⭐ @EnableScheduling — or nothing runs, with no error
⭐ ThreadPoolTaskScheduler with poolSize ≥ 5   ← ⭐ the DEFAULT IS ONE THREAD
⭐ setErrorHandler, setWaitForTasksToCompleteOnShutdown, setAwaitTerminationSeconds
⭐ Thread name prefix — readable thread dumps (Day 076)
```

**⭐ The single-thread default is the first trap** (Day 178): one slow job delays every other job, and
**a hung job stops all scheduling forever with no error.** Your project will have at least three jobs
by Day 270 — the outbox poller, the expiry job, and a cleanup — so this matters immediately.

```
⭐ @Scheduled(fixedDelay = 60_000)         ← ⭐ fixedDelay, not fixedRate
⭐ @Scheduled(cron = "0 0 2 * * *", zone = "UTC")   ← ⭐ ALWAYS set the zone
```

**⭐ `fixedDelay` cannot overlap; `fixedRate` queues or overlaps if the job runs longer than the
interval.** And a cron without `zone` fires at a different real time in each environment, and **runs
twice or not at all across a DST boundary** (Day 178).

# Part 2 — ⭐⭐ Make the job idempotent, then locking is unnecessary

**⭐ Day 178's rule, applied: ask "what if this runs twice?" before "how do I lock it?"**

```sql
-- ⭐ Claim atomically. Every instance can run this simultaneously and safely.
update bookings set status = 'EXPIRED', expired_at = now()
where id in (
    select id from bookings
    where status = 'PENDING' and expires_at < now()
    order by expires_at
    limit 100
    ⭐ for update skip locked
)
returning id;
```

**⭐ Three properties this gives you, none of which a lock gives you:**

| Property | Why |
|---|---|
| ⭐ **Safe on N instances** | each claims a distinct batch; none block |
| ⭐ **Duplicate execution is parallelism** | ⭐ not duplication |
| ⭐ **A crashed instance loses nothing** | unclaimed rows are claimed next tick |

**⭐ And the partial index makes it stay fast forever** (Day 190):

```sql
create index ix_bookings_expiring on bookings (expires_at) where status = 'PENDING';
```

**⭐ Without it, the job scans a bookings table that grows forever** — the exact case Day 190 said
gets slower every day.

## ⭐ Where ShedLock is still right

**⭐ Not everything can be made idempotent.** A nightly report emailed to finance must be sent once.

```
⭐ @SchedulerLock(name = "nightlyReport", lockAtMostFor = "PT30M", lockAtLeastFor = "PT1M")
⭐ JdbcTemplateLockProvider with .usingDbTime()
```

**⭐ Both parameters by the failure they prevent** (Day 178):

- ⭐ **`lockAtMostFor`** — if the holder is killed the lock would be held forever. **It must exceed
  the worst-case runtime**, or a second instance starts while the first is still running, which is
  the duplication you were preventing.
- ⭐ **`lockAtLeastFor`** — guards against clock skew: without it a fast job on a slightly-ahead clock
  releases before a slower-clocked instance reaches the trigger, and it runs again.
- ⭐ **`usingDbTime()`** — lock timing uses the *database's* clock, removing skew entirely.

# Part 3 — ⭐ Batching, bounding, and the transaction

**⭐ Three rules that make a job operable rather than a liability:**

```
⭐ 1. ALWAYS limit and loop  — findExpired() returning 400,000 rows is an OOM
⭐ 2. ONE transaction PER BATCH — never one for the whole job (Day 156, Day 194)
⭐ 3. A total time budget    — stop after N minutes and resume next tick
```

**⭐ Rule 2 is the one with the widest blast radius.** A job holding one transaction for forty minutes
holds a connection for forty minutes (Day 156) **and blocks vacuum database-wide for forty minutes**
(Day 194's failure 1). **A long-running job is one of the most common causes of table bloat in an
otherwise healthy system.**

**⭐ And Day 194's other lesson applies to your cleanup job**: a bulk `delete from ... where created_at
< x` on millions of rows leaves millions of dead tuples and a table that will not shrink. **Partition
and drop** (Day 200), or delete in small batches.

## ⭐ Exceptions, and the failure nobody notices

```
⭐ try { doWork(); metric(success); }
⭐ catch (Exception e) { log.error("job_failed job=expiry", e); metric(failure); }
⭐ finally { timer.stop(); }
```

**⭐ Never let an exception escape a scheduled method** (Day 178). With `fixedDelay` Spring logs and
reschedules, but **an `Error` — or some configurations — can cancel the task permanently.** The job
stops, silently, and comes back only on a deploy.

## ⭐⭐ The alert that matters is on NON-execution

```
⭐ absent_over_time(job_runs_total{job="expiry",outcome="success"}[10m])
```

> **⭐⭐ A failing job is noisy and gets noticed. A job that silently stopped running is invisible for
> weeks.** This is the single highest-value operational practice on this page, and almost nobody
> implements it.

**⭐ Write a dead-man's-switch alert for every scheduled job in your project today** — the outbox
poller, the expiry job, the cleanup.

# Part 4 — ⭐ Make it triggerable, and test it properly

## ⭐ A manual trigger endpoint

```
⭐ POST /api/v1/admin/jobs/{name}/run   — ⭐ @PreAuthorize, audited
```

**⭐ When the nightly job fails at 2 a.m., you need to re-run it at 9 a.m. without waiting 24 hours or
shipping a deploy.** This is a five-minute addition that pays for itself the first time.

## ⭐ Testing jobs

```
⭐ 1. Unit-test the WORK, separately from the schedule   ← ⭐ never test the cron expression
⭐ 2. Three concurrent workers → ⭐ each row claimed exactly once
⭐ 3. Kill a worker mid-batch → ⭐ its unclaimed rows are picked up next tick
⭐ 4. A batch bigger than the limit → ⭐ it loops and completes
⭐ 5. An injected Clock → ⭐ test the expiry boundary exactly (Day 183)
```

**⭐ Point 1 is a discipline**: the scheduled method should be a thin wrapper that calls a service
method, so the logic is testable without a scheduler at all. **Testing `@Scheduled` firing is testing
Spring.**

**⭐ Point 2 must run against real PostgreSQL** (Day 184) — `SKIP LOCKED` does not exist in H2, so the
test would pass while proving nothing.

## ⭐ And know when `@Scheduled` is the wrong tool

**Day 178's table**, applied to your project:

| Job | ⭐ Right home |
|---|---|
| The expiry job (seconds, idempotent) | ⭐ `@Scheduled` in the app |
| The outbox poller | ⭐ `@Scheduled` in the app (Day 263) |
| ⭐ A nightly report (minutes, must not be missed) | ⭐ **a Kubernetes `CronJob`** |
| A data migration or backfill | ⭐ a separate one-off job, never `@Scheduled` |

**⭐ The argument for external scheduling** (Day 178): retries, run history, alerting on
non-execution, manual re-runs — **and batch reliability stops being coupled to your API's uptime and
deploy cadence.** Having moved one job out, and being able to say why, is a good defence point.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No `@EnableScheduling` | nothing runs, no error |
| ⭐ Default single-thread scheduler | ⭐ one slow job delays all; a hang stops everything |
| `fixedRate` on a slow job | queued or overlapping runs |
| ⭐ No `zone` on cron | different real time per environment; DST double-run |
| ⭐ No locking or idempotency on N instances | ⭐ duplicate side effects, silently |
| `lockAtMostFor` shorter than the job | the duplication you were preventing |
| No `lockAtLeastFor` / `usingDbTime` | clock skew causes a second run |
| ⭐ Unbounded queries in a job | OOM and a very long transaction |
| ⭐ One transaction for the whole job | ⭐ blocks vacuum database-wide (Day 194) |
| Bulk-deleting millions of rows | bloat; partition and drop instead |
| ⭐ Letting exceptions escape | ⭐ the task may be cancelled permanently |
| ⭐ **No alert on non-execution** | ⭐ a stopped job is invisible for weeks |
| No manual trigger | a failed nightly job waits 24 hours |
| Testing the cron expression | you are testing Spring |
| H2 for the `SKIP LOCKED` test | passes while proving nothing |
