# Day 332

**L-332** · SQL vs NoSQL at scale — the framework, and what "NoSQL" actually means

**Time:** 3 hrs · **Mode:** NEW

> **⭐ The real difference is not schemas, and it is not scale. It is when you are allowed to decide
> your queries.**
>
> Relational databases let you defer that decision forever. Everything else makes you commit up
> front and punishes you for changing your mind. **Once you see the trade that way, the whole
> landscape sorts itself out.**

---

# Part 1 — ⭐⭐ The framing that matters

| | ⭐ Relational | ⭐ Everything else |
|---|---|---|
| ⭐ **You model** | ⭐ **the data** — normalise, then query however | ⭐ **the queries** — the schema is a consequence |
| A new access pattern | ⭐ **a new query, maybe an index** | ⭐⭐ **a new table, a backfill, a migration** |
| Optimised for | ⭐ flexibility | ⭐ a known pattern, at scale |
| ⭐ **Punishes** | ⭐ scale beyond one leader | ⭐ **changing your mind** |

> **⭐ Say this in an interview and most follow-ups resolve themselves: "NoSQL doesn't mean
> schemaless — the schema moved from the database into the application, and it is now enforced by
> nobody. What you actually bought was a data model shaped like one specific access pattern, in
> exchange for scale on that pattern."**

⚠️ **The corollary interviewers probe: how well do you know your access patterns?** For a system
being invented, the honest answer is "not well", **which is an argument for relational** — you will
be wrong, and relational is the cheapest place to be wrong.

---

# Part 2 — ⭐ The five families

| Family | ⭐ Optimised for | ⭐ Cost | Examples |
|---|---|---|---|
| ⭐ **Relational** | ⭐ **arbitrary queries, joins, transactions, constraints** | ⭐ one write leader (Day 329) | PostgreSQL, MySQL |
| ⭐ **Document** | ⭐ **aggregate-shaped reads and writes** | ⭐ cross-document work is manual (Day 211) | MongoDB, DynamoDB |
| ⭐ **Key-value** | ⭐ **O(1) by key, enormous throughput** | ⭐ **no querying by anything else** | Redis, Memcached |
| ⭐ **Wide-column** | ⭐⭐ **massive write volume, known query patterns** | ⭐⭐ **queries must be designed before data** | Cassandra, HBase, Bigtable |
| ⭐ **Graph** | ⭐ **deep traversals — friends of friends of friends** | small scale; awkward for anything else | Neo4j |

| Specialist | ⭐ When |
|---|---|
| ⭐ **Time-series** | append-only, time-ordered, downsampled, aged out — InfluxDB, Timescale |
| ⭐ **Search** | relevance ranking and text analysis (Day 337) |
| ⭐ **Distributed SQL** | ⭐ **SQL semantics past one leader** — Spanner, CockroachDB, Vitess |

## ⭐⭐ Wide-column, because it is the least understood

```
⭐ PRIMARY KEY ((partition_key), clustering_key)
⭐    partition key  → ⭐ WHICH machine. Every query MUST supply it.
⭐    clustering key → ⭐ the sort order WITHIN that partition.

⭐ SELECT * FROM messages WHERE chat_id = ? ORDER BY sent_at DESC LIMIT 50   ⭐ fast, always
⭐ SELECT * FROM messages WHERE sender_id = ?                                ⭐⭐ ILLEGAL or a full scan
```

| ⭐ Rule | ⭐ Consequence |
|---|---|
| ⭐ **One table per query pattern** | ⭐ **you denormalise deliberately and write the same data several times** |
| ⭐ **No joins, no ad-hoc queries** | the application does the joining, or you duplicate |
| ⭐ **Writes are cheap** (LSM trees, append-only) | ⭐ this is why it takes enormous write volume |
| ⭐ **A new query pattern = a new table + a backfill** | ⭐⭐ **this is the entire trade** |

> **⭐ DynamoDB's "single-table design" is the same idea taken further** — one table, a generic
> partition/sort key, and every access pattern encoded into key prefixes. **It is genuinely fast and
> genuinely rigid**, and describing it as "you enumerate every access pattern before you create the
> table" is the honest summary.

## ⭐ Graph, briefly and usefully

**⭐ The test is traversal depth, not the presence of relationships.** Relational databases handle
relationships well — they are made of them. **A graph database wins when the query is "how is A
connected to B" over an unbounded number of hops**, because each join in SQL is a separate operation
and depth-6 traversals become unwritable.

**⭐ And say the scale caveat:** graph databases are the hardest family to shard, because a graph's
whole value is that edges cross everything. **Most "we need a graph database" cases are three joins
and a recursive CTE** (Day 107).

# Part 3 — ⭐ Distributed SQL — the third option people forget

| | ⭐ What it gives | ⭐ What it costs |
|---|---|---|
| ⭐ **Spanner / CockroachDB** | ⭐⭐ **SQL, joins, transactions — sharded automatically** | ⭐ **cross-shard transactions cost round trips** (Day 330) |
| ⭐ **Vitess / Citus** | ⭐ shards a familiar engine (MySQL/PostgreSQL) | ⭐ **you still pick a shard key** (Day 329) |

> **⭐ Worth naming because it reframes the question: "NoSQL for scale" was a trade forced by 2010's
> options. Distributed SQL means you can often keep transactions and joins and still scale writes —
> at the price of latency on cross-shard operations and a more complex operational story.**

---

# Part 4 — ⭐⭐ The decision framework

**⭐ Five questions, in order. Each eliminates something.**

```
⭐ 1. Do I know my access patterns, and are they stable?
⭐        NO  → ⭐ relational. You will be wrong, and this is the cheapest place to be wrong.
⭐ 2. Do I need transactions or constraints across entities?
⭐        YES → ⭐ relational or distributed SQL. Do not talk yourself out of this.
⭐ 3. Does write volume genuinely exceed one leader (Day 323's arithmetic)?
⭐        NO  → ⭐⭐ relational. Most systems never reach this, and think they have.
⭐ 4. Is the data aggregate-shaped — read and written whole?
⭐        YES → document may fit (Day 211's four rules)
⭐ 5. Is it a specialist workload — time-series, search, deep traversal, pure cache?
⭐        YES → ⭐ a specialist store, ALONGSIDE the primary — not instead of it.
```

| ⭐ Argument | ⭐ Response |
|---|---|
| ⭐ "It's faster" | ⭐ **on its one access pattern. Indexed relational lookups are comparable** |
| ⭐ "We don't know the schema" | ⭐ **then you certainly do not know the access patterns — the worst case for NoSQL** |
| "It scales better" | ⭐ true past one leader's write capacity, which you should have estimated |
| ⭐ "No migrations" | ⭐ **the migration moved into every read path, forever** (Day 210) |
| ⭐ "Everyone uses it" | ⭐ at a scale you have quantified? |

⚠️ **And the cost of polyglot persistence, unchanged from Day 213 but sharper at scale:** every store
is a full operational commitment — backups **restored and timed**, monitoring, security patching,
capacity, on-call expertise, and a consistency story between them. **Two stores is a reasonable
price for a genuine fit. Four is architecture as a hobby.**

> **⭐ The shape of a good answer: PostgreSQL as the system of record, Redis for the fast derived
> layer, object storage for blobs, and one specialist store only where a workload genuinely does not
> fit — with the sync mechanism named** (Day 337's CDC, or an outbox).

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Treating "NoSQL" as one thing | ⭐ five families with opposite trade-offs |
| ⭐ "Schemaless" as a benefit | ⭐ **the schema moved to the application and is enforced by nobody** |
| ⭐⭐ Choosing wide-column without enumerating queries | ⭐⭐ **a new pattern is a new table and a backfill** |
| ⭐ Picking for scale you have not estimated | ⭐ Day 323 exists for this |
| Graph databases for three joins | a recursive CTE was the answer |
| ⭐ Ignoring distributed SQL | ⭐ the "scale or transactions" dilemma is often false now |
| ⭐ A specialist store as the source of truth | ⭐ **search indexes and caches are derived — always rebuildable** |
| Four datastores in one system | operational cost multiplied, expertise divided |
| ⭐ No sync mechanism named | ⭐ the copies diverge and nobody notices |

## Interview questions

**Q: SQL or NoSQL?**
The question I actually answer is when I have to commit to my access patterns. Relational lets me
defer that indefinitely — a new query is a query, maybe an index. Wide-column and single-table
designs make me enumerate every pattern before the data exists, and a new one means a new table and
a backfill. So if the system is new and the patterns are unstable, relational, because I will be
wrong and that is the cheapest place to be wrong.

**Q: What does "schemaless" really mean?**
That the schema moved from the database into the application, where nothing enforces it. You still
have one — it is just implicit, undocumented, and different in each of the four services that write
to the collection. The migration did not disappear either; it moved into every read path, because
every reader now handles both old and new shapes forever.

**Q: When is Cassandra the right choice?**
When write volume genuinely exceeds a single leader and the query patterns are known, small in
number and stable — a chat history read by conversation, or event ingestion read by device and time.
Every query must supply the partition key, so I model one table per access pattern and accept
writing the same data several times. If I cannot list the queries up front, that is the signal to
choose something else.

**Q: Does distributed SQL change the calculus?**
Considerably. The "scale or transactions" dilemma was a product of 2010's options — Spanner,
CockroachDB, Vitess and Citus shard while keeping SQL, joins and transactions. The cost is real:
cross-shard transactions need extra round trips, and you still choose a shard key that determines
which queries stay fast. But "we need NoSQL because we need to scale writes" now needs a second
sentence.

**Q: What is the cost of using four datastores?**
Each is a full operational commitment — backups you have actually restored and timed, monitoring,
security patching, capacity planning, and people who know it at 3am. Plus a consistency story
between them, which is usually the part nobody designs. PostgreSQL plus Redis is a reasonable
default; a third needs a workload that genuinely does not fit, and the sync mechanism named
explicitly.

## Mini task

1. **Run the five questions on your flagship**, writing an answer to each. **Note which question
   would have changed your choice.**
2. ⭐ **Enumerate every access pattern** for one entity. Now design the Cassandra tables for them.
   **Count the tables and the duplicated writes.**
3. ⭐ Add a **new** access pattern to that design and **write out the full migration** — new table,
   backfill, dual write, cutover. That is the cost of the model.
4. Model the same entity in PostgreSQL and answer the new pattern with **one index.** Compare.
5. ⭐ Take a "we need a graph database" query and **write it as a recursive CTE** (Day 107). Measure
   at depth 3, 5 and 8, and find where it genuinely breaks down.
6. Estimate your write volume (Day 323) and **compare it with one PostgreSQL leader's capacity.**
   Write down the multiple — that number is your honest scaling headroom.
7. ⭐ For every datastore you run, **write the sync mechanism and what happens when it stops.** Any
   store with no answer is a divergence waiting to happen.

## 🎙️ Articulation drill

**Three minutes:** *"We're building a new product. Which database?"*

**⭐ The marker: you ask how well the access patterns are known, and use "not well" as an argument
for relational rather than against it.** *"You are going to be wrong about the queries — everyone is
— so I want the store where being wrong costs an index instead of a table and a backfill."*

**⭐ Then name the second store deliberately**, with the sync mechanism and what happens when it
stops. **Choosing one primary store and one derived store, and being able to say why the derived one
is rebuildable, is a stronger answer than any comparison table.**
