# Part 1 — Remotes

## What a remote is

A named URL, plus a set of **remote-tracking branches** that cache what that remote looked like the
last time you talked to it.

```bash
git remote -v
git remote add upstream https://github.com/original/repo.git
git remote set-url origin git@github.com:me/repo.git
git remote show origin          # branches, tracking, what's stale
```

```
refs/heads/main            your local branch — you commit here
refs/remotes/origin/main   a READ-ONLY cache of origin's main as of your last fetch
```

**`origin/main` is not "the server".** It is your snapshot of the server. It only changes when you
`fetch`. Understanding this dissolves most confusion about push and pull.

## fetch, pull, push

```bash
git fetch origin                # download objects + update origin/*. Touches NOTHING local.
git fetch --all --prune         # prune deletes stale origin/* for deleted remote branches
git pull                        # = fetch + merge (or rebase, if pull.rebase is set)
git pull --rebase               # explicitly
git push origin main
git push -u origin feature      # -u sets upstream tracking; afterwards bare `git push` works
git push --force-with-lease     # ← never plain --force (Day 086)
git push origin --delete feature
```

> **`git fetch` is always safe.** It never changes your branches or working tree.

The professional habit is `fetch` then look, rather than `pull` and hope:

```bash
git fetch
git log --oneline HEAD..origin/main     # what's coming
git log --oneline origin/main..HEAD     # what I have that they don't
git diff origin/main                    # the actual change
```

That is ten seconds and it removes every "what just happened to my branch" surprise.

## Tracking

```bash
git branch -vv                          # which local tracks which remote, and ahead/behind
git branch --set-upstream-to=origin/main main
```

"Ahead 3, behind 2" means your branch and `origin/main` diverged — 3 commits only you have, 2 only
they have. A plain `push` will be refused; you must integrate first (merge or rebase), which is
exactly the decision from Day 086.

## Forks

```bash
git remote add upstream https://github.com/original/repo.git
git fetch upstream
git rebase upstream/main                # or merge
git push origin feature
```

The open-source shape: `origin` is your fork (you can push), `upstream` is the original (you cannot).
Keep your fork's `main` a clean mirror of upstream and never commit to it directly — work always on
branches.

# Part 2 — Workflows

## git-flow

```
main        ─────●─────────────●──────   production, tagged releases
                 │             │
release          ●──●          ●──       stabilisation
                /                \
develop  ──●───●────●────●────●───●──    integration
            \      /      \    /
feature      ●────●        ●──●
hotfix                        ●──►main + develop
```

Five branch types: `main`, `develop`, `feature/*`, `release/*`, `hotfix/*`.

**Designed for versioned software with scheduled releases** — desktop applications, libraries, on-
premise products where multiple versions are supported simultaneously.

Its problems in a web-service context are real: long-lived branches diverge and conflict, `develop`
and `main` drift apart, merges are large and risky, and continuous deployment is impossible because
the model assumes a release is an event. Its own author published a note saying it is often applied
where it does not belong.

**Say this in an interview:** git-flow is a good fit for versioned releases, a poor fit for a
continuously deployed service.

## Trunk-based development

```
main   ──●──●──●──●──●──●──●──●──   always deployable, everyone integrates daily
          \    /   \   /
feature    ●──●     ●─●            hours to 2 days, never longer
```

One long-lived branch. Short branches merged at least daily. Every merge to `main` is deployable,
protected by CI and often deployed automatically.

**This is what most modern web teams do**, and it is what the DORA research associates with high
performance. The mechanism is simple: integration pain is superlinear in divergence, so integrating
constantly keeps it near zero.

The obvious objection — "what about unfinished features?" — has a standard answer:

```java
if (features.isEnabled("new-checkout", user)) {
    return newCheckout(user);
}
return legacyCheckout(user);
```

**Feature flags decouple deploy from release.** Incomplete code ships dark, is enabled for internal
users, then a percentage, then everyone. That also gives you an instant rollback that does not
require a deploy — the single most valuable operational property here.

The cost, which you should state honestly: flags are debt. Each one doubles a code path, and a
codebase with 200 stale flags is unmaintainable. **Every flag needs an owner and a removal date.**

## GitHub Flow

Trunk-based plus pull requests: branch from `main`, open a PR, review, CI, merge, deploy. Simple,
and the default for most teams and all open source.

## Choosing

| Context | Workflow |
|---|---|
| Continuously deployed web service | **Trunk-based / GitHub Flow** |
| Library or product with supported versions | git-flow, or trunk + release branches |
| Open source with external contributors | Fork + PR |
| Regulated environment needing sign-off | Trunk + release branches + tagged approvals |
| Mobile app (store review lag) | Trunk + release branches (you cannot roll back a store release) |

That last row is worth knowing: **an app-store release cannot be rolled back**, so mobile keeps
release branches even on otherwise trunk-based teams. It is a good example of the workflow following
the deployment constraint, not fashion.

## Branch protection

```
main:
  ✅ require a pull request before merging
  ✅ require 1–2 approvals
  ✅ require status checks (build, tests, lint, security scan) to pass
  ✅ require branches to be up to date before merging
  ✅ require signed commits (optional but good)
  ✅ include administrators          ← otherwise the rule is advisory
  ❌ allow force pushes
  ❌ allow deletions
```

"Include administrators" is the one people skip, and it is the one that matters: an unenforced rule
is a suggestion.

## Tags and releases

```bash
git tag -a v1.4.0 -m "Release 1.4.0"      # ANNOTATED — a real object with author and message
git tag v1.4.0                             # lightweight — just a ref. Avoid for releases.
git tag -s v1.4.0 -m "…"                   # signed
git push origin v1.4.0
git push origin --tags
git describe --tags                        # v1.4.0-12-gA1B2C3 ← great for build metadata
```

**Use annotated tags for releases** — they are objects with a tagger, date and message, so they carry
provenance. `git describe` produces a human-readable version string containing the last tag, the
commit count since, and the hash: perfect for stamping into a build so a running binary can tell you
exactly what it is.

Semantic versioning: **MAJOR.MINOR.PATCH** — breaking, feature, fix.

# Part 3 — Pull request discipline

## As the author

**1. Keep it small.** Review quality collapses above roughly 400 lines; a 2,000-line PR gets
"LGTM" and no scrutiny, which is worse than no review because it launders responsibility. If a
change is large, split it: refactor first (behaviour-preserving, easy to review), then the feature.

**2. Write the description for someone with no context.**

```markdown
## What
Adds rate limiting to the payments endpoint.

## Why
The provider returned 429s during the sale — we sent up to 400 rps against
their documented limit of 100. See incident #221.

## How
Token bucket in front of PaymentClient, sized per API key, configurable per
environment. Over-limit requests queue for 2s then fail with 503.

## Testing
Unit tests for the bucket; integration test asserting the 101st request in a
second is rejected. Load-tested locally at 500 rps.

## Risk / rollback
Behind the `payments.ratelimit.enabled` flag, default off. Rollback = flip the flag.

## Not in this PR
Per-tenant limits (#4480).
```

The **"Not in this PR"** section is underused and prevents the most common review derail — a
reviewer asking for scope you deliberately deferred.

**3. Review your own diff first.** Open the "Files changed" tab before requesting review. You will
find the debug statement, the commented-out block, and the accidentally committed config. This is
Day 085's `add -p` discipline at PR scale.

**4. CI green before requesting review.** Asking a human to look at something the machine has not
approved wastes the scarcer resource.

**5. Respond to every comment.** Fix it, or explain why not. Silence reads as dismissal, and
unresolved threads are how disagreements become resentment.

## As the reviewer

**Priority order — spend your attention top-down:**

1. **Correctness** — does it do what it claims? Edge cases, null, empty, concurrency, error paths.
2. **Security** — injection, authorization checks, secrets, unsafe deserialization (Day 063A),
   logging of sensitive data (Day 073A).
3. **Design** — is this the right structure? Will it be extended? This is the expensive-to-change
   part, so it deserves the most thought.
4. **Tests** — do they test behaviour, and would they fail if the code were wrong?
5. **Readability** — naming, clarity.
6. **Style** — **automate this**. A human arguing about formatting is a formatter that has not been
   installed.

**Comment conventions that reduce friction enormously:**

```
blocking:  This allows an IDOR — any user can pass another user's orderId.
           We need an ownership check before the lookup.

question:  Is the 30s timeout deliberate? The upstream p99 is 1.2s.

nit:       Could be `isEmpty()` — non-blocking, take it or leave it.

praise:    Nice — extracting the validator made this much clearer.
```

Labelling severity is the highest-value habit in code review. Without it, a reviewer's stylistic
preference and a genuine security bug arrive with identical weight, and the author has to guess which
must be fixed. **`nit:` and `blocking:` alone transform review culture.**

Two more: **review the code, not the person** ("this method does X" not "you did X"), and **praise
explicitly** — reviews that only ever contain criticism make people avoid submitting.

## Receiving review

Separate the code from yourself. A comment on your code is not a comment on you, and the reviewer
usually has context you lack — or lacks context you have, in which case the fix is to *add it to the
PR description* so the next reader does not need the conversation.

If you disagree, say why with reasoning. If you disagree twice, take it to a call — text is a poor
medium for design disagreement and a good medium for entrenching one.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Thinking `origin/main` is live | Confusion about what push/pull will do |
| `pull` without looking first | Surprise merges |
| `git push --force` on shared branches | Overwrites colleagues' work |
| Long-lived feature branches | Superlinear merge pain |
| git-flow on a continuously deployed service | Ceremony with no benefit |
| Feature flags with no removal plan | Permanent doubled code paths |
| Branch protection excluding admins | The rule is advisory |
| Lightweight tags for releases | No author, date or message |
| 2,000-line PRs | Rubber-stamp reviews |
| No PR description | Reviewer reconstructs intent from the diff |
| Unlabelled review comments | Nits read as blockers, blockers read as nits |
| Style debates in review | Install a formatter |

## Interview questions

**Q: `fetch` vs `pull`?**
`fetch` downloads objects and updates remote-tracking branches, changing nothing local — always safe.
`pull` is fetch plus merge or rebase, which changes your branch. Fetch and inspect, then integrate
deliberately.

**Q: What is `origin/main`?**
A remote-tracking branch: a local, read-only cache of what `origin`'s `main` was at your last fetch.
Not a live view of the server.

**Q: Which workflow would you use and why?**
Trunk-based with short-lived branches and PRs for a continuously deployed service — integration pain
grows with divergence, so integrate daily and use feature flags to decouple deploy from release. A
versioned product or a mobile app needs release branches, because a release is an event you cannot
roll back.

**Q: How do you ship an unfinished feature on trunk?**
Behind a feature flag, off by default, enabled progressively. It also gives you rollback without
deploying. Flags need owners and removal dates or they become permanent debt.

**Q: What makes a good pull request?**
Small, single-purpose, green CI, a description covering what/why/how/testing/risk, and self-reviewed
before requesting review.

**Q: What do you look for when reviewing?**
Correctness first, then security, then design, then tests, then readability — with style automated. I
label comments as blocking, question or nit so severity is unambiguous.

## Mini task

1. Add a second remote to a repository and practise `fetch` + `log HEAD..origin/main` before every
   integration for a week.
2. Create a divergence (commit locally, push a different commit from another clone) and resolve it
   both by merge and by rebase. Compare the graphs.
3. Set `fetch.prune = true` and confirm deleted remote branches disappear from `git branch -a`.
4. Fork a public repository, add `upstream`, and sync your fork's `main` from it.
5. Configure branch protection on a repository you own, including "include administrators", and try
   to push directly to `main`.
6. Create an annotated tag, push it, and use `git describe --tags` to generate a version string.
7. Write a PR description using the template above for the last non-trivial change you made.
8. Review someone's open-source PR (or an old one of your own) using the priority order, labelling
   every comment as blocking / question / nit.
9. Implement a feature flag in a small project, ship the code disabled, and enable it at runtime.

# 🚪 Exit questions

1. What is a remote-tracking branch, and when does it change?
2. Why is `fetch` always safe?
3. Give the two `log` ranges that show incoming and outgoing commits.
4. What does "ahead 3, behind 2" mean and what must you do?
5. Describe git-flow's five branches and the context it suits.
6. Describe trunk-based development and the reason it works.
7. How do feature flags make it possible, and what do they cost?
8. Why do mobile teams keep release branches?
9. Why does branch protection need "include administrators"?
10. Annotated vs lightweight tags — which for releases, and why?
11. Give the reviewer's priority order and say which item should be automated.
12. What do `blocking:`, `question:` and `nit:` solve?

## 🎙️ Articulation drill

Two minutes: **"Describe your team's Git workflow and why it is set up that way."**

Even if you are answering hypothetically, answer as a decision: trunk-based with short branches
because integration pain scales with divergence, PRs with required checks because review catches what
tests do not, feature flags to decouple deploy from release, protected `main` including admins,
annotated tags for releases. Then name the case where you would choose differently — versioned
products and mobile. Naming the exception is what makes it sound like a decision rather than a habit.
