**L-387** · RDS and Aurora — Multi-AZ, read replicas, and the JVM's DNS cache

> **⭐⭐ Multi-AZ is not a read replica. It gives you zero extra read capacity, and confusing the two is
> the most common RDS misunderstanding there is.**

> constraint, and where Aurora genuinely differs.

# Part 1 — ⭐⭐ Multi-AZ vs read replicas

| | ⭐⭐ Multi-AZ standby | ⭐⭐ Read replica |
|---|---|---|
| ⭐ Replication | ⭐⭐ **synchronous** | ⭐⭐ **asynchronous** |
| ⭐⭐ **Serves reads?** | ⭐⭐ **NO — it serves nothing** | ⭐⭐ **yes** |
| Purpose | ⭐ **availability** | ⭐ **read scale** |
| ⭐ On primary failure | ⭐⭐ **automatic failover, 60–120s** | ⭐ manual promotion (and it becomes standalone) |
| ⭐ Data loss | ⭐⭐ **none — commits are on both** | ⭐ whatever the lag was |
| ⭐ Cost | ⭐⭐ **2× the instance, for zero throughput** | 1× per replica, **for real throughput** |
| Cross-region | ⭐ Multi-AZ is within a region | ⭐ replicas can be cross-region |

```
⭐⭐ SAY IT ONCE, CORRECTLY:
⭐   "Multi-AZ doubles my database bill and gives me NO extra capacity.
⭐    ⭐⭐ I am buying automatic failover with zero data loss, and that is the entire product."
⭐   "Read replicas give me capacity and ⭐⭐ NO availability guarantee,
⭐    because promotion is manual and lossy."
⭐ ⇒ ⭐⭐ They solve DIFFERENT problems. Production usually needs BOTH.
```

⚠️ **Multi-AZ *does* have a second benefit people forget: it makes maintenance and minor version
upgrades near-online**, because AWS patches the standby, fails over, then patches the old primary.
**Without Multi-AZ, a minor version upgrade is a multi-minute outage on your primary.**

## ⭐ Multi-AZ DB *cluster* (the newer option)

| | |
|---|---|
| ⭐ Two **readable** standbys instead of one idle one | ⭐ failover in ~35s, and you get read capacity |
| ⭐ Semi-synchronous | ⭐ commit acknowledged by one of two standbys |
| ⭐ Worth knowing exists | ⭐⭐ it partly dissolves the "standby serves nothing" complaint |

# Part 2 — ⭐⭐ Failover is a DNS change, and the JVM caches DNS

```
⭐ RDS failover mechanism:
⭐   mydb.abc123.eu-west-1.rds.amazonaws.com  ⭐⭐ is a CNAME
⭐   ⇒ on failover, AWS repoints it at the standby's address. ⭐ 60–120 seconds.
⭐   ⇒ ⭐⭐ Your endpoint string NEVER CHANGES. That is the whole design.
```

```
⭐⭐ AND HERE IS THE JAVA-SPECIFIC TRAP:
⭐   java.security.Security  networkaddress.cache.ttl
⭐   ⭐⭐ With a SecurityManager historically installed: −1 = ⭐⭐ CACHE FOREVER.
⭐   ⇒ ⭐⭐ Your JVM keeps resolving the OLD IP. The failover completed.
⭐        The database is healthy. ⭐⭐ Your application stays down until it is restarted.
⭐   ⇒ ⭐ FIX: java.security.Security.setProperty("networkaddress.cache.ttl", "30");
⭐        (⭐ and networkaddress.cache.negative.ttl = "0")
```

> **⭐⭐ This is the single most valuable Java-specific fact in Stage 11**, because it explains an outage
> that looks impossible: AWS says the database failed over in ninety seconds, and your service was down
> for forty minutes until someone restarted it. **Set the DNS TTL, and verify it — do not assume your
> base image or framework did.**

| ⭐ The rest of the failover checklist | |
|---|---|
| ⭐⭐ **Connection pool must evict broken connections** | ⭐ Hikari: `validationTimeout`, `keepaliveTime` (Day 156) |
| ⭐ Application must retry | ⭐⭐ a failover is a **transient** failure — retry with backoff (Day 340) |
| ⭐ Use the **cluster/writer endpoint** | never the instance endpoint |
| ⭐⭐ **Test it** | ⭐⭐ `aws rds reboot-db-instance --force-failover` — **do it in staging, deliberately** |
| Aurora: use the JDBC wrapper driver | it tracks topology and fails over in seconds, not DNS time |

⚠️ **"We have Multi-AZ" is a claim about AWS. "We failed over on purpose last month and the application
recovered in eleven seconds" is a claim about your system.** Only the second one is worth anything —
and it is Day 283's argument applied to the database.

# Part 3 — ⭐ Replicas, lag, and read-your-writes

| | |
|---|---|
| ⭐ Replication is **asynchronous** | ⭐⭐ `ReplicaLag` is a metric you must alarm on |
| ⭐⭐ **Read-your-writes breaks** | ⭐⭐ user updates their profile, is redirected, sees the old value |
| ⭐ Day 328's anomalies, in AWS form | ⭐ this is exactly the "read your own writes" guarantee, lost |
| ⭐⭐ **The fix** | ⭐⭐ **route reads to the primary within a session after a write** — a sticky read window |
| Lag spikes on | ⭐ large writes, index builds, long transactions on the primary |
| Aurora replicas | ⭐ ~10–20 ms lag — **shared storage, not log shipping** |

```java
// ⭐ The routing decision belongs in one place, not scattered
@Transactional(readOnly = true)   // ⭐ Spring routes to a replica via a routing DataSource
public List<Order> recentOrders(Long userId) { ... }

// ⭐⭐ but after a write in this session, force the primary for N seconds —
// ⭐   otherwise the user's own change appears to have been lost.
```

> **⭐ Report queries, analytics and exports are the *correct* replica workload** because staleness is
> genuinely acceptable there. **Serving a user their own data from a replica is where it goes wrong**,
> and the bug is intermittent, unreproducible and blamed on caching for two weeks.

# Part 4 — ⭐⭐ Backups, and what "restore" actually means

| Mechanism | ⭐ What it is |
|---|---|
| ⭐ **Automated backups** | ⭐ daily snapshot + transaction logs; retention 0–35 days (**0 disables it**) |
| ⭐⭐ **Point-in-time recovery** | ⭐⭐ **restore to any second in the retention window** |
| ⭐ Manual snapshots | ⭐ kept until you delete them — **survive instance deletion** |
| ⭐⭐ **The catch** | ⭐⭐ **a restore creates a NEW INSTANCE with a NEW ENDPOINT** |

```
⭐⭐ "RESTORE" IS NOT "UNDO".
⭐ Restoring to 14:32 gives you a SECOND database. To use it you must:
⭐   1. wait (⭐ can be tens of minutes for a large instance)
⭐   2. ⭐⭐ repoint the application — DNS/secret change, i.e. a deploy
⭐   3. ⭐⭐ decide what to do with the writes that happened between 14:32 and now
⭐ ⇒ ⭐⭐ Step 3 is the hard one, and it is a BUSINESS decision, not a technical one.
```

⚠️ **Deleting an RDS instance deletes its automated backups.** The final snapshot prompt is the only
thing between you and permanent loss — **and `skip_final_snapshot = true` in Terraform, which people set
to make `destroy` work in dev, is the same flag that runs in prod.** Guard it with `prevent_destroy` and
deletion protection.

| ⭐ Also worth knowing | |
|---|---|
| ⭐ **AWS Backup** | ⭐ cross-account, cross-region vault — **the real disaster story** |
| ⭐ Storage **cannot shrink** | ⭐⭐ autoscaling grows it; the only way down is dump/restore |
| ⭐ Parameter groups | ⭐ some parameters are **static** — they need a reboot to apply |
| ⭐⭐ **Enable Performance Insights** | ⭐⭐ it is how you find the slow query in production, for free at 7 days |

# Part 5 — ⭐⭐ Connections, RDS Proxy, and Aurora

```
⭐⭐ RDS connection limits scale with INSTANCE MEMORY.
⭐   db.t3.medium (4 GB)  ≈ ⭐ ~400 max_connections
⭐   ⭐ 40 ECS tasks × Hikari pool of 20 = ⭐⭐ 800 connections. ⭐⭐ You are already over.
⭐ ⇒ ⭐⭐ Day 324's fleet-wide connection budget, with a real number attached.
```

| ⭐ Answer | ⭐ When |
|---|---|
| ⭐⭐ **Shrink the pool** | ⭐⭐ **first, always** — a pool of 10 per task is usually more than enough |
| ⭐⭐ **RDS Proxy** | ⭐⭐ **many short-lived clients — Lambda, or a large fleet.** Multiplexes and survives failover faster |
| ⭐ Bigger instance | buys connections, and everything else too |
| PgBouncer yourself | more control, more operations |

## ⭐ Aurora, where it genuinely differs

| | |
|---|---|
| ⭐⭐ **Storage is a separate distributed service** | ⭐⭐ **6 copies across 3 AZs**, self-healing |
| ⭐⭐ Replicas **share the storage** | ⭐⭐ so lag is ~10–20 ms, not seconds — and adding one is fast |
| ⭐ Failover | ⭐ ~30s, faster with the JDBC wrapper driver |
| ⭐ **Aurora Serverless v2** | ⭐ scales ACU in seconds — **genuinely good for spiky and for dev** |
| ⭐⭐ **The cost surprise** | ⭐⭐ standard Aurora bills **per I/O request** — a chatty workload can dwarf the instance cost |
| ⭐ The fix for that | ⭐ **Aurora I/O-Optimized** — higher instance price, no I/O charges. Break-even ≈ 25% of spend on I/O |

> **⭐ Aurora is not automatically the right answer.** It is more expensive per instance-hour, its I/O
> billing surprises people, and for a modest workload plain RDS Postgres with Multi-AZ is simpler and
> cheaper. **Choose Aurora for fast replicas, fast failover, and storage that grows without thought —
> not because it is the premium option.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Thinking Multi-AZ adds read capacity** | ⭐⭐ it serves nothing — 2× cost, 0× throughput |
| ⭐ Thinking read replicas give availability | ⭐ promotion is manual and lossy |
| ⭐⭐ **JVM DNS caching left at default/forever** | ⭐⭐ failover completes, your app stays down |
| ⭐ No connection validation in the pool | broken connections handed out after failover |
| ⭐ Never testing failover | ⭐⭐ "we have Multi-AZ" is a claim about AWS, not about you |
| ⭐⭐ **Serving read-your-writes from a replica** | ⭐⭐ intermittent, unreproducible, blamed on caching |
| ⭐ No alarm on `ReplicaLag` | you find out from a user |
| ⭐⭐ **Believing restore means undo** | ⭐⭐ new instance, new endpoint, and a data-gap decision |
| ⭐ `skip_final_snapshot = true` reaching production | ⭐⭐ permanent loss, one `destroy` away |
| ⭐ Forgetting backups die with the instance | manual snapshots and AWS Backup survive |
| ⭐⭐ **Pool size × task count > max_connections** | ⭐⭐ connection exhaustion under scale-out |
| ⭐ Aurora chosen by reflex | ⭐ per-I/O billing can dwarf the instance cost |
| Not enabling Performance Insights | the slow query stays invisible |

## Interview questions

**Q: Multi-AZ or a read replica?**
They solve different problems and production usually needs both. A Multi-AZ standby is synchronous,
serves no traffic at all, and exists purely to give automatic failover with no data loss — so it doubles
the database bill for zero extra capacity, and that is the honest description of what you are buying. A
read replica is asynchronous, serves reads, and gives no availability guarantee because promotion is
manual and loses whatever was in the lag. Multi-AZ also makes minor version upgrades near-online, which
is an underrated second benefit.

**Q: RDS failed over in ninety seconds but the application was down for forty minutes. Explain.**
Almost certainly JVM DNS caching. RDS failover works by repointing the endpoint's CNAME at the standby,
so the hostname never changes — but if the JVM caches DNS resolutions indefinitely, the application keeps
connecting to the old IP address until somebody restarts it. The fix is setting
`networkaddress.cache.ttl` to something like thirty seconds and the negative TTL to zero, plus a
connection pool that validates and evicts broken connections, plus retry logic that treats a failover as
a transient failure. And then actually forcing a failover in staging to prove all three work together.

**Q: A user updates their profile and immediately sees the old value. What happened?**
Their read went to an asynchronous replica that had not caught up — read-your-writes broken by
replication lag. The fix is a sticky read window: after a write in a session, route that session's reads
to the primary for a few seconds. The broader rule is that replicas are correct for reports, analytics
and exports where staleness is genuinely acceptable, and wrong for serving a user their own data. The
bug is intermittent and unreproducible, which is why it usually gets blamed on caching for two weeks
first.

**Q: What does restoring from a backup actually involve?**
Point-in-time recovery restores to any second in the retention window, but it creates a new instance
with a new endpoint — it is not an undo button. So the sequence is: wait for the restore, which can be
tens of minutes for a large instance; repoint the application, which is a deploy or a secret change; and
then decide what to do about every write that happened between the restore point and now. That third
step is a business decision, not a technical one, and it is the part that makes restores slow in
practice. Separately, deleting an instance deletes its automated backups, so manual snapshots or AWS
Backup in another account is what actually survives a mistake.

**Q: Forty tasks each with a pool of twenty against a db.t3.medium. What happens?**
You have provisioned eight hundred connections against an instance that allows roughly four hundred, so
connections get refused as soon as the fleet scales out — and it fails at the worst moment, under load.
The first fix is shrinking the pool, because a pool of ten per task is usually generous and pool size is
almost always chosen by superstition. Then RDS Proxy if the client count is genuinely large or the
clients are Lambda functions, since it multiplexes and also shortens failover. It is the fleet-wide
connection budget from system design with a concrete number attached.

## 🎙️ Articulation drill

**Two minutes:** *"How is your database made highly available?"*

**⭐ Start by separating the two things people merge: Multi-AZ is a synchronous standby that serves no
traffic and buys automatic failover with no data loss; read replicas are asynchronous, serve reads and
buy no availability. Production has both, for different reasons.**

**⭐ Then go where almost nobody goes, which is what makes it a good answer: failover is a DNS change, so
the application has to cooperate — a JVM DNS TTL of thirty seconds rather than forever, a pool that
validates and evicts, and retries that treat failover as transient. And we know it works because we
forced a failover in staging and measured eleven seconds of client-visible impact, rather than trusting
the feature name.**
