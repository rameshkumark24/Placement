# Day 346

**L-346** · Design 2 — Pastebin, and where large content actually lives

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Pastebin looks like the URL shortener with a bigger payload. It is not — and the difference is
> the whole problem.**
>
> A short URL is 200 bytes and belongs in a key-value store. **A paste is kilobytes to megabytes,
> which means the content leaves the database entirely** — and once it lives in object storage behind
> a CDN, access control becomes genuinely hard.

---

# Part 1 — ⭐ Requirements, estimates, and the split they force

| ⭐ Functional | ⭐ Out of scope |
|---|---|
| Create a paste (text, up to ~10 MB) | editing (a paste is immutable) |
| ⭐ **Read by short URL** | accounts beyond an optional API key |
| ⭐ Expiry (10 min → never) | syntax highlighting — **client-side** |
| ⭐ **Visibility: public / unlisted / private** | comments, forking |
| View counts | |

```
⭐ ESTIMATE
⭐   1M pastes/day ⇒ ~12 writes/s (peak ~35)  ⭐ trivially one primary
⭐   Read:write 10:1 ⇒ ~120 reads/s           ⭐ ALSO small
⭐   ⭐⭐ Average paste 10 KB ⇒ 10 GB/day ⇒ 3.6 TB/year ⇒ ~20 TB provisioned
⭐   ⭐⭐ Bandwidth: 120 reads/s × 10 KB = 1.2 MB/s — ⭐ but a viral paste is 100× that
```

> **⭐ Say what the numbers decided, and note the inversion from Day 345:** the request rate is
> tiny — **this is not a QPS problem.** It is a **storage and bandwidth** problem, and **that is what
> moves the content out of the database.**

| ⭐ Where content must NOT go | ⭐ Why |
|---|---|
| ⭐⭐ **A `TEXT`/`BLOB` column** | ⭐⭐ **10 KB rows destroy the buffer pool** (Day 186), bloat every backup, and make replication crawl |
| ⭐ The same store as metadata | different access pattern, different lifecycle, different cost per byte |

```
⭐ THE SPLIT:
⭐   METADATA  → relational / KV:  code, ownerId, visibility, expiresAt, size, contentHash, objectKey
⭐   CONTENT   → ⭐ OBJECT STORAGE (Day 327), served via CDN
```

**⭐ This is Day 327's metadata rule, and it is the design.** Everything else follows from it.

---

# Part 2 — ⭐ API and the read paths

```
⭐ POST /pastes    { content, expiresIn?, visibility?, alias? } → { code, url }
⭐ GET  /pastes/{code}                                          → { metadata, contentUrl }
⭐ GET  /raw/{code}                                             → the bytes
⭐ DELETE /pastes/{code}
```

**⭐ Three read paths, and choosing between them is a real decision:**

| Visibility | ⭐ Path | ⭐ Mechanism |
|---|---|---|
| ⭐ **Public / unlisted** | ⭐⭐ **CDN → object storage, direct** | ⭐ the app is not on the read path at all |
| ⭐ **Private** | ⭐ app checks auth → **presigned URL** (Day 327) | ⭐ short expiry; the app authorises, storage serves |
| ⭐ Any, if you need view counts | app returns a URL and **fires an async event** | never count synchronously (Day 345) |

> **⭐ The tension to name out loud: a CDN cannot enforce your authorisation rules.** Once content is
> cacheable at the edge, **anyone with the URL has it.** So unlisted is *security by obscurity* —
> which is fine and honest if you say so — **and genuinely private content must be served through
> signed, short-lived URLs that the CDN keys on**, or not through a shared CDN cache at all.

⚠️ **Two related traps.** A signed URL that is cached by the CDN under a key that ignores the
signature **leaks content to the next requester** — the cache key must include enough to be safe.
And **a "deleted" paste stays in edge caches until its TTL expires**, so deletion is eventually
consistent unless you purge (slow, per-POP — Day 327).

# Part 3 — ⭐⭐ The deep dive: content-addressed storage and deduplication

**⭐ Pastes repeat constantly** — the same stack trace, the same config file, the same leaked key
pasted by twenty people. **Content addressing is the natural design:**

```
⭐ objectKey = sha256(content)          ⭐ identical content ⇒ identical key ⇒ stored ONCE
⭐ metadata row: code → objectKey       ⭐ many codes may point at one object
```

| ⭐ Gains | ⭐ Costs |
|---|---|
| ⭐ **Storage saved on duplicates** | ⭐⭐ **you can no longer delete an object when one paste is deleted** |
| ⭐ **Uploads become idempotent** — re-uploading is a no-op | ⭐ per-paste expiry no longer maps to object lifetime |
| ⭐ Immutability for free — the key IS the content | ⭐ a hash collision is theoretically possible (sha256: ignore it, and say so) |
| Verification is trivial | ⭐ **privacy: identical content is now shared across users** |

## ⭐⭐ The deletion problem, and three honest answers

```
⭐ Paste A and paste B both point at object X. A is deleted.
⭐ ⇒ ⭐ You MUST NOT delete X. But nothing tracks that B still needs it.
```

| ⭐ Approach | ⭐ Trade |
|---|---|
| ⭐ **Reference counting** | ⭐ **correct, but the counter is now a hot, transactional thing** — and a crash between decrement and delete leaks or loses data |
| ⭐⭐ **Mark-and-sweep garbage collection** | ⭐⭐ **a periodic job lists objects with no live metadata row and deletes them — eventually consistent, simple, and the usual answer** |
| ⭐ Do not deduplicate at all | ⭐ **storage is cheap; this is often the right call** — say so |

> **⭐ The honest conclusion is the strongest answer here: at 3.6 TB a year, deduplication saves money
> that does not matter and buys a garbage-collection problem, a privacy question and a deletion
> subtlety.** Content addressing earns its place when content is *large* — video, build artefacts,
> backups — **not when it is 10 KB.** *Deciding not to deduplicate, with the reason, is the mature
> answer.*

⚠️ **The privacy point deserves its own sentence in an interview:** with content addressing, **an
attacker who guesses content can confirm it exists** by observing that their upload was
instantaneous. **For a paste site holding leaked credentials that is a real information leak** — and
it is the kind of second-order consequence interviewers reward noticing.

# Part 4 — ⭐ Expiry, abuse, and what breaks

## ⭐ Expiry — two mechanisms, and let the platform do it

| Layer | ⭐ Mechanism |
|---|---|
| ⭐ **Metadata** | ⭐ `expiresAt` checked at read time — **Day 316's lazy predicate; no sweeper for correctness** |
| ⭐ **Object storage** | ⭐⭐ **a lifecycle rule deletes objects after N days — the platform reclaims space for free** |
| ⭐ CDN | a TTL no longer than the shortest expiry, **or expired content is served from the edge** |

⚠️ **The CDN TTL must not exceed the paste's expiry.** A ten-minute paste behind a one-hour edge
cache is **available for an hour** — which, for a paste site whose whole point is short-lived
secrets, is a correctness failure rather than a performance one.

## ⭐ Abuse — the part that is actually the business

**⭐ A public text host is used for malware, phishing kits and leaked credentials.** Say this
unprompted; **it is the operational reality of the product.**

| Control | ⭐ Note |
|---|---|
| ⭐ Rate limiting per IP and per key (Day 336) | at the edge |
| ⭐ **Async scanning** — secret patterns, known malware hashes | ⭐ never inline; it would put a scanner on the write path |
| ⭐ Quarantine rather than delete | a false positive must be reversible |
| ⭐ **A takedown path with an audit trail** | legal requirement, not a feature |
| Blocklists and captcha for anonymous writes | |

## ⭐ Bottlenecks and the close

| ⭐ Breaks first | ⭐ Mitigation |
|---|---|
| ⭐⭐ **A viral paste** — one object, enormous read volume | ⭐⭐ **the CDN absorbs it entirely — this is what a CDN is for** |
| Metadata store | tiny load; a cache in front if needed |
| ⭐ Object storage request rate on a hot prefix | ⭐ hashed keys spread it (Day 327) |
| ⭐ **Storage growth** | expiry + lifecycle rules + cold tiering |
| Abuse volume | scanning throughput, not serving throughput |

```
⭐ MONITOR: read latency by path (CDN vs origin) · CDN hit rate · storage growth/day
⭐          ⭐ pastes created/min (business metric) · scanner backlog
⭐ CUT:     search, accounts, editing, syntax highlighting server-side
⭐ AT 10×:  nothing structural changes — ⭐ THAT is the sign the design is right
```

---

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Content in a database column | ⭐⭐ **buffer pool, backups and replication all wrecked** |
| ⭐ Serving bytes through the application | threads held; bandwidth paid twice (Day 327) |
| ⭐ **CDN TTL longer than the expiry** | ⭐ expired secrets still served |
| ⭐ Assuming a CDN can enforce authorisation | ⭐⭐ **private content leaks** |
| A signed URL cached under a signature-blind key | one user's URL serves another |
| ⭐ Deduplicating without a deletion plan | ⭐ orphaned objects or deleted live content |
| Ignoring the dedup privacy leak | existence confirmation via timing |
| ⭐ Synchronous scanning | a scanner on the write path |
| Deleting on a false positive | irreversible |
| ⭐ **No abuse story at all** | ⭐ the operational reality of this product, unaddressed |

## Interview questions

**Q: Where does the paste content live?**
Object storage, with only metadata in the database — code, owner, visibility, expiry, size and the
object key. Ten-kilobyte rows evict useful pages from the buffer pool, bloat every backup and slow
replication, and you lose the ability to serve content from a CDN without proxying it. The request
rate here is trivial; this is a storage and bandwidth problem, and that is what forces the split.

**Q: How do you serve private pastes?**
Not through a shared CDN cache, because a CDN cannot evaluate your authorisation rules — once
content is cacheable at the edge, anyone with the URL has it. The application authorises and issues
a short-lived presigned URL, and the cache key must include enough that a signature-blind cache
cannot serve one user's URL to another. Unlisted, by contrast, is security by obscurity, which is
acceptable if you say so plainly.

**Q: Would you deduplicate identical pastes by content hash?**
Probably not, and the reasoning is the answer. Content addressing gives free immutability and
idempotent uploads, but it means you cannot delete an object when one paste referencing it is
deleted — so you need reference counting or a mark-and-sweep collector — and it introduces a privacy
leak, since an attacker can confirm content exists by observing an instantaneous upload. At a few
terabytes a year the storage saved does not justify that. It earns its place for large objects, not
ten-kilobyte text.

**Q: How does expiry work?**
Checked as a read-time predicate on the metadata, so correctness never depends on a sweeper having
run, plus an object-storage lifecycle rule to actually reclaim the bytes. The subtle part is the CDN:
its TTL must not exceed the shortest expiry, or a ten-minute paste stays available for an hour, which
on a site whose purpose is short-lived content is a correctness bug rather than a performance one.

**Q: What breaks at scale here?**
Almost nothing, which is worth saying. A viral paste is a single hot object and a CDN absorbs it
entirely — that is precisely what a CDN is for. The real operational pressures are storage growth,
which expiry and lifecycle rules handle, and abuse: a public text host is used for malware and leaked
credentials, so asynchronous scanning, quarantine rather than deletion, and a takedown path with an
audit trail are part of the design, not an afterthought.

## 🎙️ Articulation drill

**Two minutes:** *"How is this different from the URL shortener?"*

**⭐ The complete answer inverts the two constraints.** The shortener is a QPS problem with a tiny
payload, so it is cache and key generation. **Pastebin is a storage and bandwidth problem with a
trivial request rate, so the content leaves the database, the CDN carries the reads, and the
interesting questions become authorisation on cached content, expiry across three layers, and
abuse.**

**⭐ Recognising that two superficially similar problems have opposite bottlenecks is exactly the
transfer skill Stage 8 was built for.**
