# Day 201

**L-201** · Replication, failover, and point-in-time recovery

**Time:** 3 hrs · **Mode:** NEW

> Day 186 established that every change is written to the WAL before the data pages. **Replication is
> just shipping that WAL somewhere else and replaying it** — which means one mechanism gives you read
> replicas, high availability, and the ability to restore the database to any second in the past.
>
> Day 185's checklist item 39 said an untested backup is not a backup. Today is the machinery behind
> that claim, and the two numbers — **RPO and RTO** — that turn "we have backups" into an engineering
> statement.

---

# Part 1 — Streaming replication

```
     PRIMARY                              REPLICA
   ┌──────────┐   ⭐ WAL stream        ┌──────────┐
   │ walsender├──────────────────────►│walreceiver│
   │          │                        │  replays  │
   └──────────┘                        └──────────┘
                                       ⭐ read-only, queryable
```

```
# primary
wal_level = replica
max_wal_senders = 10
⭐ wal_keep_size = '1GB'          # or use a replication slot

# replica
primary_conninfo = 'host=primary user=replicator ...'
⭐ hot_standby = on               # allows read queries
```

**⭐ Replication slots — the safety feature with a sharp edge:**

```sql
select pg_create_physical_replication_slot('replica1');
```

**A slot guarantees the primary retains WAL until the replica has consumed it**, so a replica that
falls behind can always catch up rather than needing a full rebuild.

**⭐ The sharp edge: a slot for a replica that is gone forever will fill the primary's disk.** WAL
accumulates without bound until `pg_wal` exhausts the volume and **the primary stops accepting
writes** — a self-inflicted outage caused by a safety feature.

```sql
select slot_name, active, pg_size_pretty(
    pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) as retained_wal
from pg_replication_slots;                          -- ⭐ ALERT on this
```

```
max_slot_wal_keep_size = '10GB'      -- ⭐ PG13+: invalidate the slot rather than fill the disk
```

**⭐ Set `max_slot_wal_keep_size`.** Losing a replica is recoverable; a primary that cannot write is
an outage. This is also one of the causes Day 194 listed for wraparound — an abandoned slot blocks
WAL recycling *and* can hold back vacuum.

## ⭐ Synchronous versus asynchronous — the RPO decision

```
synchronous_commit = on                    -- ⭐ async replication (the default)
synchronous_standby_names = 'ANY 1 (r1,r2)'  -- ⭐ makes commits wait for a replica
```

| Mode | Commit waits for | ⭐ Data loss on primary failure |
|---|---|---|
| ⭐ **Async** (default) | ⭐ local WAL fsync only | ⭐ **the last few seconds of commits** |
| `remote_write` | replica received it (not fsynced) | small window |
| ⭐ **`on` / `remote_apply`** | ⭐ replica fsynced / applied | ⭐ **zero — RPO = 0** |

**⭐ Synchronous replication makes every commit wait for a network round trip.** Across an
availability zone that is 1–2 ms added to *every write*; across a region it is 50–100 ms, which is
usually unacceptable.

**⭐ The standard production shape: `ANY 1 (replica_a, replica_b)` with two synchronous candidates in
the same region, plus an asynchronous replica elsewhere.** You get RPO 0 for the common failure and
survive losing one replica without blocking writes — **because a single synchronous standby that goes
down blocks every commit on the primary**, which is a failure mode people discover the hard way.

# Part 2 — ⭐ Replicas as read scaling, and the trap

```java
@Transactional(readOnly = true)          // ⭐ Day 156 — routes to a replica
public Page<OrderResponse> list(Pageable p) { ... }
```

**⭐ Replication lag means a replica is behind.** Usually milliseconds; under load or a long
transaction, seconds or minutes.

```sql
-- on the replica
select now() - pg_last_xact_replay_timestamp() as lag;    -- ⭐ monitor and alert
```

## ⭐ The read-after-write problem

```
1. User submits an order      → PRIMARY
2. Redirect to the order page → ⭐ REPLICA
3. ⭐⭐ "Order not found"
```

**⭐ This is Day 126's eventual consistency inside your own database**, and it is the bug that makes
naive read-replica routing feel broken to users.

| Fix | Note |
|---|---|
| ⭐ **Read from the primary within N seconds of a write** | ⭐ a session flag; simple and effective |
| ⭐ **Sticky: route a user's reads to the primary after a write** | same idea, per session |
| LSN tracking | ⭐ precise — record the write's LSN and wait for the replica to reach it |
| Return the created object in the write response | ⭐ **often removes the read entirely** (Day 146's 201 + body) |

**⭐ The last one is the best answer where it applies** and it is a design fix rather than an
infrastructure one: a `POST` returning the created representation means there is no follow-up read to
be stale.

## ⭐ `hot_standby_feedback` — the trade-off with Day 194

```
hot_standby_feedback = on     # ⭐ replica tells the primary which rows its queries still need
```

| | `off` (default) | `on` |
|---|---|---|
| Long replica query | ⭐ **cancelled**: "canceling statement due to conflict with recovery" | ⭐ completes |
| Effect on the primary | none | ⭐⭐ **blocks vacuum — Day 194's failure 1, across servers** |

**⭐ Either choice has a real cost.** `off` means analytics queries on the replica get cancelled
mid-run; `on` means a long analytics query on the replica causes bloat on the primary.

**⭐ The usual compromise: `hot_standby_feedback = on` plus a `statement_timeout` on the replica**, so
queries complete but cannot run long enough to damage the primary. Say that in an interview — it
shows you know both sides.

## Logical replication

```sql
create publication orders_pub for table orders, order_items;      -- ⭐ primary
create subscription orders_sub connection '...' publication orders_pub;   -- ⭐ subscriber
```

| | Physical | Logical |
|---|---|---|
| Granularity | ⭐ whole cluster | ⭐ **per table** |
| Version | ⭐ must match | ⭐ **can differ — enables major-version upgrades** |
| Target writable | no | ⭐ yes |
| DDL | replicated | ⭐ ❌ **not replicated** |

**⭐ Logical replication's headline use is a near-zero-downtime major version upgrade**: replicate
from 14 to 16, then switch over. It is also the mechanism behind CDC tools like Debezium (Day 185A's
outbox alternative).

# Part 3 — ⭐⭐ Backups and PITR

> **⭐ A base backup plus the WAL since it lets you restore to any point in time.** That is the whole
> idea, and it is why the WAL is worth understanding.

```bash
pg_basebackup -h primary -D /backup/base -Ft -z -P -X stream    # ⭐ full physical copy
```

```
archive_mode = on
archive_command = 'pgbackrest --stanza=app archive-push %p'     -- ⭐ ship every WAL segment
```

```
# restore to an exact moment — e.g. just before someone ran the bad DELETE
recovery_target_time = '2026-08-14 10:23:00+00'
recovery_target_action = 'promote'
```

**⭐ Use `pgBackRest` or `barman`, not hand-rolled scripts.** They handle parallel compression,
incremental backups, retention, and — critically — **verification**. A hand-rolled
`archive_command` that silently fails is a category of disaster with its own history.

## ⭐ RPO and RTO — the two numbers that define your strategy

| | Meaning | Determined by |
|---|---|---|
| ⭐ **RPO** — Recovery Point Objective | ⭐ **how much data may be lost** | replication mode and WAL archive frequency |
| ⭐ **RTO** — Recovery Time Objective | ⭐ **how long recovery may take** | ⭐ restore speed, or failover speed |

| Strategy | RPO | RTO |
|---|---|---|
| Nightly `pg_dump` | ⭐ **up to 24 hours** | ⭐ hours (restore + replay) |
| Base backup + WAL archive | ⭐ seconds to minutes | ⭐ hours — proportional to database size |
| + async replica | seconds | ⭐ **minutes** (promote) |
| ⭐ + sync replica | ⭐ **zero** | ⭐ **seconds to a minute** |

**⭐ The insight that reframes the conversation: a replica is not a backup.**

**A replica replicates your mistakes.** `DROP TABLE orders` on the primary is replicated to every
replica in milliseconds. **Replicas give you low RTO; only backups give you recovery from logical
errors** — a bad migration, a bad `DELETE`, corruption, or ransomware.

**⭐ You need both, and they answer different questions.** Being able to state that cleanly is a
strong interview signal.

## ⭐ Test the restore

**Day 185's item 39, restated because it is the one item on this page whose failure is
unrecoverable:**

> **⭐ An untested backup is a hope. Restore it on a schedule, into a scratch environment, and time
> it — because that time *is* your RTO, and most people have never measured it.**

```bash
pgbackrest --stanza=app --type=time --target='2026-08-14 10:23:00' restore   # ⭐ monthly, automated
```

**Verify three things every time:** it restores, the row counts match, and **the elapsed time is
within your RTO.** A restore that works but takes eleven hours against a four-hour RTO is a failed
test, and that is exactly the discovery you want to make on a Tuesday rather than during an incident.

# Part 4 — Failover

## ⭐ Manual promotion, and the danger

```bash
pg_ctl promote -D /var/lib/postgresql/data
```

**⭐ Split-brain: if the old primary comes back and still accepts writes, you have two divergent
databases** and reconciling them is manual, slow and lossy.

**⭐ Fencing is mandatory** — the old primary must be made unable to accept writes before the new one
is promoted. That is what automated tools exist to get right.

## Automated failover

| Tool | Note |
|---|---|
| ⭐ **Patroni** | ⭐ the standard. Uses etcd/Consul for consensus and leader election |
| repmgr | simpler, less automated |
| ⭐ **Managed (RDS, Cloud SQL, Aurora)** | ⭐ **it is done for you — a real argument for managed databases** |

**⭐ `pg_rewind` is the tool that makes a failed primary reusable** as a replica without a full base
backup — otherwise re-seeding a 2 TB database takes hours.

## ⭐ What the application must do

**⭐ Failover is not transparent, and this is the part application engineers own:**

1. ⭐ **Every in-flight transaction is aborted.** The pool must reconnect (Day 156) and the
   application must handle the error.
2. ⭐ **There is a window with no primary** — seconds to a minute. Writes fail during it.
3. ⭐ **Retry logic must be idempotent** (Day 123). Retrying a write across a failover without an
   idempotency key can double-apply it.
4. **Connection strings must point at something that moves** — a virtual IP, a DNS record with a
   short TTL, or a pooler (Day 197). **A hardcoded primary hostname means failover requires a
   deploy.**
5. ⭐ **The circuit breaker should open** (Day 181) rather than retrying into a database with no
   primary.

```
jdbc:postgresql://host1:5432,host2:5432/app?targetServerType=primary   -- ⭐ driver-level failover
```

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Treating a replica as a backup | it replicates your `DROP TABLE` too |
| ⭐ Never testing a restore | the one failure that is unrecoverable |
| Not measuring restore time | your RTO is a guess |
| ⭐ Abandoned replication slot | WAL fills the primary's disk; writes stop |
| ⭐ A single synchronous standby | its failure blocks every commit |
| Synchronous replication across regions | 50–100 ms on every write |
| Ignoring replication lag | read-after-write shows "not found" |
| ⭐ `hot_standby_feedback` without a statement timeout | replica queries bloat the primary |
| Hand-rolled `archive_command` | silent failure until you need it |
| Promotion without fencing | ⭐ split-brain |
| Hardcoded primary hostname | failover needs a deploy |
| Non-idempotent retries across failover | double-applied writes |
| Expecting failover to be transparent | in-flight transactions abort |

## Interview questions

**Q: Is a replica a backup?**
No, and the distinction matters. A replica replicates everything including your mistakes — a `DROP
TABLE` reaches every replica in milliseconds. A replica gives you a low recovery *time*; only backups
plus WAL archiving let you recover from a logical error like a bad migration or a bad delete. You
need both because they answer different questions.

**Q: What are RPO and RTO, and what determines each?**
RPO is how much data you can afford to lose, determined by replication mode and WAL archive
frequency — zero with synchronous replication, seconds with async, up to a day with nightly dumps.
RTO is how long recovery may take, determined by restore speed or failover speed. And I measure RTO
by actually restoring, because an untested restore time is a guess.

**Q: What are the risks of synchronous replication?**
Every commit waits for a network round trip, so it adds a millisecond or two within a zone and 50 to
100 across regions. And a single synchronous standby is a liability: if it goes down, every commit on
the primary blocks. The standard shape is `ANY 1` of two candidates, so losing one does not stop
writes.

**Q: A user creates an order and immediately gets "not found". Why?**
The write went to the primary and the read went to a lagging replica. Fixes are routing reads to the
primary for a short window after a write, tracking the write's LSN and waiting for the replica to
reach it, or best — returning the created object in the write response so there is no follow-up read.

**Q: What is split-brain and how do you prevent it?**
Two nodes both accepting writes after a failover, producing divergent data that must be reconciled
manually. Prevention is fencing — the old primary is made unable to accept writes before the new one
is promoted — which is the main reason to use Patroni or a managed service rather than promoting by
hand.

## Mini task

1. Set up a primary and a streaming replica in Docker. Write on the primary, read on the replica.
2. Measure lag with `pg_last_xact_replay_timestamp`. Run a heavy write load and watch it grow.
3. **Reproduce read-after-write**: insert on the primary, immediately select on the replica.
4. Create a replication slot, stop the replica, and **watch `pg_wal` grow.** Set
   `max_slot_wal_keep_size` and confirm the slot is invalidated instead.
5. Enable synchronous replication. **Time 1,000 inserts before and after.** Then stop the single
   standby and **watch every commit block.** Switch to `ANY 1` of two.
6. Run a 60-second query on the replica during heavy primary writes. **Get the recovery conflict
   cancellation.** Enable `hot_standby_feedback` and confirm it completes — then check `n_dead_tup`
   on the primary.
7. ⭐ Take a base backup, archive WAL, insert rows noting the time, run a destructive `DELETE`, then
   **restore to the moment before it.** That exercise is the day.
8. **Time the full restore.** Write the number down. **That is your RTO.**
9. Promote the replica. Point the application at it. **Measure the write-unavailability window.**
10. Bring the old primary back without fencing and **create split-brain deliberately.** Then use
    `pg_rewind` to rejoin it.
11. Set up logical replication for one table between two different major versions.

## 🎙️ Articulation drill

Three minutes: **"How do you make a database highly available and recoverable?"**

Separate the two problems, because conflating them is the mistake: replicas give you low RTO,
backups plus WAL archiving give you recovery from logical errors — and a replica happily replicates
your `DROP TABLE`. State your RPO and RTO targets and derive the architecture from them. Then the
operational half: fencing to prevent split-brain, a scheduled restore test whose duration *is* your
measured RTO, and what the application must do — abort in-flight transactions, retry idempotently,
and connect to something that can move.
