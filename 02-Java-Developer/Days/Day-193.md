# The setup

```sql
create table customers (
    id bigint generated always as identity primary key,
    email text not null, name text not null, country text not null,
    signup_date date not null, tier text not null, deleted_at timestamptz
);
create table products (
    id bigint generated always as identity primary key,
    sku text not null, name text not null, category text not null,
    price numeric(19,4) not null, attributes jsonb
);
create table orders (
    id bigint generated always as identity primary key,
    customer_id bigint not null references customers(id),
    status text not null, total numeric(19,4) not null,
    placed_at timestamptz not null, shipped_at timestamptz
);
create table order_items (
    id bigint generated always as identity primary key,
    order_id bigint not null references orders(id),
    product_id bigint not null references products(id),
    quantity integer not null, unit_price numeric(19,4) not null
);
```

```sql
-- ⭐ 500k customers, 5M orders, 15M items, 50k products. Generate them, then:
analyze;
-- ⭐ ONLY these indexes exist: the four primary keys. Nothing else.
```

**⭐ That last line is deliberate.** Not indexing foreign keys is Day 189's most common real-world
omission, and starting from it makes several cases realistic rather than contrived.

**For every case:** capture `explain (analyze, buffers)`, state the diagnosis in one sentence, make
**one** change, re-measure, and **record the buffer counts before and after.**

# Part 1 — Cases 1–5

### Case 1
```sql
select * from orders where customer_id = 384621;
```
<details><summary><b>Diagnosis</b></summary>

**Seq Scan, ~5M rows read to return ~10.** The foreign key has no index — PostgreSQL indexes primary
keys, not foreign keys (Day 189).

```sql
create index concurrently ix_orders_customer on orders (customer_id);
```
**Expect buffers to fall from ~50,000 to ~5.** Also time `delete from customers where id = ?` before
and after — the parent delete was scanning the child table.
</details>

### Case 2
```sql
select * from customers where lower(email) = 'alice@example.com';
```
<details><summary><b>Diagnosis</b></summary>

Non-sargable — a function on the column (Day 189 #1). Even an index on `email` is useless.
```sql
create index concurrently ix_customers_email_lower on customers (lower(email));
```
⭐ **Then check the application**: if it does `where email = ?` in one place and `lower(email)` in
another, you need both indexes or one consistent convention. **Pick the convention.**
</details>

### Case 3
```sql
select * from orders where date(placed_at) = '2026-08-14';
```
<details><summary><b>Diagnosis</b></summary>

Same cause, different disguise. **The better fix is the query, not an index:**
```sql
where placed_at >= '2026-08-14' and placed_at < '2026-08-15'   -- ⭐ sargable, half-open
```
Now an index on `placed_at` works — and it serves every other date-range query too, which an
expression index on `date(placed_at)` would not.
</details>

### Case 4
```sql
select * from orders where status = 'PENDING' order by placed_at limit 100;
-- 0.2% of orders are PENDING
```
<details><summary><b>Diagnosis</b></summary>

Two problems: no index on `status`, and a full sort to return 100 rows (Day 191 pattern 5).

```sql
create index concurrently ix_orders_pending on orders (placed_at) where status = 'PENDING';
```
⭐ **A partial index solves both at once.** It is 0.2% the size, and because it is ordered by
`placed_at` the `LIMIT` stops after 100 entries — no `Sort` node at all.

**This is Day 178's job-poller index.** Confirm the `Sort` node is gone.
</details>

### Case 5
```sql
select c.name, count(o.id)
from customers c left join orders o on o.customer_id = c.id
where c.country = 'UK'
group by c.id, c.name;
```
<details><summary><b>Diagnosis</b></summary>

Depends on what the plan says. Two likely findings:
- ⭐ `Hash` with `Batches: 8` — a spill. Raise `work_mem` for the session.
- A nested loop over a large outer set if `country` is misestimated.

```sql
create index concurrently ix_customers_country on customers (country);
set work_mem = '128MB';
```
⭐ **If `country = 'UK'` is 60% of the table, the seq scan is correct** and the index will be ignored
(Day 189 #4). **Check the selectivity before concluding.**
</details>

# Part 2 — Cases 6–10

### Case 6
```sql
select c.*, (select count(*) from orders o where o.customer_id = c.id) as order_count
from customers c where c.tier = 'GOLD';
```
<details><summary><b>Diagnosis</b></summary>

Correlated subquery — `SubPlan` with `loops = 50000` (Day 191 pattern 4). Rewrite as an aggregate
join:
```sql
select c.*, coalesce(o.cnt, 0)
from customers c
left join (select customer_id, count(*) cnt from orders group by 1) o on o.customer_id = c.id
where c.tier = 'GOLD';
```
⭐ **Or better, if only GOLD customers are needed, use a lateral so the aggregate is not computed for
all 500k customers:**
```sql
left join lateral (select count(*) cnt from orders o where o.customer_id = c.id) o on true
```
**Measure both.** Which wins depends on how many customers are GOLD — that is the real lesson.
</details>

### Case 7
```sql
select * from orders order by placed_at desc offset 400000 limit 20;
```
<details><summary><b>Diagnosis</b></summary>

Day 107 and Day 152, in a plan: **PostgreSQL reads and discards 400,000 rows.** An index on
`placed_at desc` helps but the offset cost remains linear.

⭐ **The real fix is keyset pagination:**
```sql
where (placed_at, id) < (:last_placed_at, :last_id) order by placed_at desc, id desc limit 20;
create index concurrently ix_orders_placed_id on orders (placed_at desc, id desc);
```
**Time page 1 and page 20000 for both approaches.** The offset version degrades linearly; the keyset
version is flat. That comparison is the entire argument.
</details>

### Case 8
```sql
select p.name, sum(oi.quantity * oi.unit_price) as revenue
from order_items oi join products p on p.id = oi.product_id
join orders o on o.id = oi.order_id
where o.placed_at >= '2026-01-01' and p.category = 'electronics'
group by p.name order by revenue desc limit 20;
```
<details><summary><b>Diagnosis</b></summary>

A reporting query over 15M rows. Index the joins and the filters:
```sql
create index concurrently ix_items_order on order_items (order_id);
create index concurrently ix_items_product on order_items (product_id);
create index concurrently ix_orders_placed on orders (placed_at);
create index concurrently ix_products_category on products (category);
```
⭐ **Then accept that it may still be slow, and ask the right question: does this need to be live?**
If it feeds a dashboard, a materialized view refreshed hourly (Day 188) turns an 8-second query into
a 3 ms one.

**⭐ The judgement is the lesson: not every slow query should be optimised — some should be
precomputed.**
</details>

### Case 9
```sql
select * from customers
where country = 'UK' and signup_date between '2020-01-01' and '2020-12-31';
```
<details><summary><b>Diagnosis</b></summary>

Correlated columns (Day 190, Day 192). `EXPLAIN` shows an estimate of ~50 against an actual of
~80,000, because the planner multiplies the two selectivities as if independent.

```sql
create statistics stx_customers (dependencies, ndistinct) on country, signup_date from customers;
analyze customers;
create index concurrently ix_customers_country_signup on customers (country, signup_date);
```
⭐ **Equality first, range last** (Day 190). Re-check the estimate after `ANALYZE` — **that number
improving is the actual fix**; the index is secondary.
</details>

### Case 10
```sql
select * from customers where name ilike '%smith%' and deleted_at is null;
```
<details><summary><b>Diagnosis</b></summary>

Leading wildcard — no B-tree can help (Day 189 #3), and it is Day 163b's DoS vector.
```sql
create extension if not exists pg_trgm;
create index concurrently ix_customers_name_trgm on customers using gin (name gin_trgm_ops)
    where deleted_at is null;                    -- ⭐ partial AND trigram together
```
⭐ **Combining a partial predicate with a trigram index** is the complete fix: it only indexes live
rows and it handles the substring search. Confirm both conditions appear in the plan.
</details>

# Part 3 — ⭐ The workflow, and the two questions above it

```
1. explain (analyze, buffers)
2. ⭐ Biggest estimated-vs-actual gap?          → statistics / extended statistics
3. ⭐ Multiply every node's time by its loops   → where is the time REALLY?
4. Seq Scan on a big table?                     → is it sargable? selective enough?
5. Rows Removed by Filter huge?                 → missing or wrong index
6. Sort / Hash spilling?                        → work_mem, or index-provided order
7. High loops?                                  → correlated subquery, or a bad join choice
8. ⭐ ONE hypothesis. ONE change. Re-measure BUFFERS.
```

**⭐ And two questions that sit above the whole workflow:**

> **Does this query need to run at all?** An N+1 from the application (Day 160), a query inside a
> loop, a dashboard polling every 5 seconds — the fastest query is the one you do not issue.

> **Does it need to be live?** Case 8's answer. A materialized view, a cache (Day 168), or a
> precomputed counter (Day 188) beats any amount of index tuning, and it is the answer a senior
> engineer reaches for that a junior one does not.

## The optimisation menu, in order of preference

| Fix | Note |
|---|---|
| ⭐ 1. **Do not run the query** | fix the N+1, cache the result |
| ⭐ 2. **Rewrite it** | sargable predicates, `NOT EXISTS`, join instead of subquery, keyset instead of offset |
| ⭐ 3. **Fix the statistics** | `ANALYZE`, extended statistics — helps every plan, not one |
| 4. **Add the right index** | including partial, expression, covering |
| 5. **Tune settings** | `work_mem` per session, `random_page_cost` |
| 6. **Precompute** | materialized view, counter |
| 7. Change the schema | partitioning (Day 200), denormalization (Day 188) |
| ❌ 8. Force the plan | last resort; correct only for today's data |

**⭐ Note that "add an index" is fourth, not first.** Most people start there. Rewriting and fixing
statistics are cheaper, help more queries, and do not add write cost.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Adding indexes before reading the plan | often the wrong index; always a write cost |
| Changing several things at once | you learn nothing (Day 099) |
| Comparing times, not buffers | cache state dominates timings |
| Optimising a query that should not run | Day 160 |
| Optimising a report that could be precomputed | Case 8 |
| Not checking selectivity before indexing | Day 189 #4 |
| ⭐ Forgetting `ANALYZE` after loading test data | you optimise against a fiction |
| Testing on a small dataset | every plan is a seq scan |
| Leaving planner switches on | a diagnostic used as a fix |
| Not indexing foreign keys | Case 1 — the most common real omission |

## Interview questions

**Q: Given a slow query, walk me through your process.**
`EXPLAIN (ANALYZE, BUFFERS)` first. Compare estimated to actual rows and start at the biggest
divergence, because everything above a bad estimate was decided on bad information. Multiply each
node by its loop count to find where the time really is. Then check sargability, selectivity and
spills. One hypothesis, one change, re-measure buffers. And before all of that, two questions: does
this query need to run, and does it need to be live?

**Q: What do you try before adding an index?**
Rewriting the query — making predicates sargable, replacing a correlated subquery with a join,
replacing offset with keyset — and fixing statistics. Both are cheaper than an index, both help more
than one query, and neither adds write cost. An index is the fourth option, not the first.

**Q: When do you stop optimising and change the approach?**
When the query is doing genuinely necessary work over a large dataset and the requirement does not
actually need live data. A dashboard aggregate over 15 million rows should be a materialized view,
not a heroically tuned query.

**Q: Why compare buffers rather than execution time?**
Timings depend on what happens to be cached, so a second run is always faster and proves nothing.
Buffers measure the work done and are stable.

## Mini task

**This day *is* the mini task.**

1. Build the schema and generate the data at full volume. `ANALYZE`.
2. Work all ten cases without reading the diagnoses. For each: plan, one-sentence diagnosis, one
   change, re-measure. **Record buffers before and after in a table.**
3. **Then** read the diagnoses and compare. Where you differed, work out why.
4. **Now do it against the clock.** Regenerate the data, drop all indexes, shuffle the case order,
   and give yourself **10 minutes per query.** That is the exit-gate condition.
5. Write your own case 11: break something in a way none of these cover, then diagnose it.
6. Turn on `auto_explain` with a 500 ms threshold and run a mixed workload. Diagnose whatever it
   catches, without knowing in advance what is wrong. **That is the closest thing to production.**

3. Give the optimisation menu in order, and say why indexing is fourth.
4. For each of the ten cases: name the diagnosis in one sentence.

6. Which case is fixed by statistics rather than an index?
7. Which case should be precomputed instead of optimised?
8. Which case needs two index features combined?

## 🎙️ Articulation drill

**Have someone hand you an unfamiliar slow query and a plan. Ten minutes, narrating throughout.**

Say what you are looking at and why, in order. Name your hypothesis before you make a change, and say
what number you expect to move. Make one change. Re-measure. **If you cannot fix it, say what you
would investigate next and what you would need** — "I would want to see `pg_stat_user_indexes` and
the row counts" is a strong answer; silence is not.
