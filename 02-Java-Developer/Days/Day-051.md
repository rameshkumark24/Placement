# L-051 · Queues, deques and heaps

## `ArrayDeque` — the one you should default to

**A resizable circular buffer.** Not a linked list.

```
   elements: [ │ │ D │ E │ A │ B │ C │ │ ]
                     ↑           ↑
                   head        tail

   addFirst → head--  (wrapping to the end)
   addLast  → tail++  (wrapping to the start)
```

**Head and tail indices wrap around modulo the array length** — which is a power of two, so the
wrap is a bitwise AND, exactly as in `HashMap` (Day 048).

| | `ArrayDeque` | `LinkedList` |
|---|---|---|
| Structure | Circular array | Doubly-linked nodes |
| Memory per element | ~4–8 bytes | ~40 bytes |
| Cache locality | **Excellent** | Poor |
| `addFirst`/`addLast` | O(1) amortised | O(1) |
| `get(index)` | ❌ not supported | O(n) |
| Nulls | ❌ **rejected** | ✅ |

**`ArrayDeque` beats `LinkedList` at both queue and stack usage** — Day 047's measurement showed it.
The JDK docs say so explicitly: *"likely to be faster than `Stack` when used as a stack, and faster
than `LinkedList` when used as a queue."*

**Why nulls are rejected:** `poll()` and `peek()` return `null` to mean "empty". A stored null would
be indistinguishable from an empty deque — the same ambiguity argument as `ConcurrentHashMap`
(Day 045).

## Never use `Stack`

```java
Stack<Integer> stack = new Stack<>();        // 💀
Deque<Integer> stack = new ArrayDeque<>();   // ✅
```

**Three reasons, and they're all real:**

1. **It extends `Vector`** (Day 037's inheritance-misuse example). So it inherits `get(int)`,
   `insertElementAt`, `remove(int)` — **you can index into the middle of a "stack"**, which destroys
   the abstraction. `Stack` isn't a `Vector`; it *uses* one.
2. **Every method is `synchronized`** — you pay for thread safety you almost never want, and it's
   insufficient anyway for compound operations (Day 045).
3. **The iteration order is backwards.** `Stack` iterates bottom-to-top — the *opposite* of pop
   order. `ArrayDeque` iterates in pop order. This has caused real bugs.

```java
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1); stack.push(2); stack.push(3);
// push = addFirst, pop = removeFirst, peek = peekFirst
```

## `Deque` as both — learn the method table

**`Deque` has three naming families, which is confusing until you see the mapping:**

| Intent | Deque method | Queue equivalent | Stack equivalent |
|---|---|---|---|
| Add at head | `addFirst` / `offerFirst` | — | `push` |
| Add at tail | `addLast` / `offerLast` | `add` / `offer` | — |
| Remove head | `removeFirst` / `pollFirst` | `remove` / `poll` | `pop` |
| Remove tail | `removeLast` / `pollLast` | — | — |
| Inspect head | `getFirst` / `peekFirst` | `element` / `peek` | `peek` |

**The `add`/`offer` distinction matters:**

| Family | On failure |
|---|---|
| `add`, `remove`, `element` | **Throws** an exception |
| `offer`, `poll`, `peek` | Returns `false` / `null` |

**Use `offer`/`poll`/`peek` for a bounded or possibly-empty queue** — exceptions for expected
conditions are poor design. Use `add`/`remove` when emptiness would be a bug worth failing on.

## `PriorityQueue` — a binary heap

**An array-backed binary min-heap.** Not sorted — only the *head* is guaranteed smallest.

```
   Conceptually:            Stored as an array:
          1                 [1, 3, 2, 7, 5, 4]
        /   \                index:  0  1  2  3  4  5
       3     2
      / \   /                for index i:
     7   5 4                    parent = (i-1)/2
                                left   = 2i+1
                                right  = 2i+2
```

**No pointers — the tree structure is implicit in the indices.** That's why heaps are so
cache-friendly and memory-efficient.

| Operation | Cost |
|---|---|
| `peek` | **O(1)** |
| `offer` | O(log n) — sift up |
| `poll` | O(log n) — move last to root, sift down |
| `contains` | **O(n)** — it's not sorted |
| `remove(Object)` | O(n) |
| Build from a collection | **O(n)** — heapify, not O(n log n) |

**Two things people get wrong:**

**1. Iteration is NOT in priority order.**

```java
PriorityQueue<Integer> pq = new PriorityQueue<>(List.of(5, 1, 3, 2));
for (int x : pq) System.out.print(x + " ");     // 1 2 3 5 — or some other heap order
```

**Only `poll()` gives sorted order.** The heap invariant is only parent ≤ children — siblings are
unordered. Printing a `PriorityQueue` and expecting sorted output is a common bug.

**2. `toString` is also heap order**, not sorted. Same reason.

### Min-heap by default; max-heap by comparator

```java
PriorityQueue<Integer> min = new PriorityQueue<>();                          // smallest first
PriorityQueue<Integer> max = new PriorityQueue<>(Comparator.reverseOrder()); // largest first
PriorityQueue<Task> byPriority = new PriorityQueue<>(
        Comparator.comparingInt(Task::priority).thenComparing(Task::created));
```

**Never write `(a, b) -> a - b`** — overflow (Day 041).

### The "top k" pattern — worth memorising

```java
// k LARGEST elements → use a MIN-heap of size k
PriorityQueue<Integer> heap = new PriorityQueue<>();     // min-heap
for (int x : data) {
    heap.offer(x);
    if (heap.size() > k) heap.poll();      // evict the smallest
}
// the heap now holds the k largest
```

**Counter-intuitive and important: for the k *largest*, use a *min*-heap.** The head is the smallest
of your current best k, so it's the one to evict when a better candidate arrives.

**O(n log k) time, O(k) space** — versus O(n log n) to sort everything. For k=10 out of a billion,
that's the difference between feasible and not.

**This is on your [DSA track](../Roadmap/DSA-Parallel-Track.md)** under the heap pattern. The signal
is "top k", "k largest", "k closest", "median of a stream".

## Other queue types

| Type | Use |
|---|---|
| `ArrayBlockingQueue` | Bounded producer-consumer (Day 043) |
| `LinkedBlockingQueue` | Optionally bounded, higher throughput |
| `PriorityBlockingQueue` | Priority + blocking |
| `DelayQueue` | Elements become available after a delay — scheduling |
| `ConcurrentLinkedQueue` | Lock-free, unbounded |
| `SynchronousQueue` | Zero capacity — a direct hand-off. Used by `newCachedThreadPool` |

**`SynchronousQueue` is worth knowing** — it has no storage at all; a `put` blocks until a `take`
arrives. That's exactly why `Executors.newCachedThreadPool()` creates unbounded threads: with no
queue to buffer into, every task that can't be handed off immediately spawns a thread. It's the
mechanism behind that pool's dangerous behaviour (Day 069).

## Type this yourself

```java
import java.util.*;

public class QueueDemo {
    record Task(String name, int priority) { }

    public static void main(String[] args) {

        // ---- Deque as a stack ----
        System.out.println("--- ArrayDeque as a stack ---");
        Deque<Integer> stack = new ArrayDeque<>();
        stack.push(1); stack.push(2); stack.push(3);
        System.out.println("   iteration: " + stack + "   ← pop order, correct");
        System.out.print("   popping:  ");
        while (!stack.isEmpty()) System.out.print(stack.pop() + " ");

        Stack<Integer> legacy = new Stack<>();
        legacy.push(1); legacy.push(2); legacy.push(3);
        System.out.println("\n   legacy Stack iterates: " + legacy + "   ← BACKWARDS");
        System.out.println("   and it inherits get(0) = " + legacy.get(0)
                         + "   ← you can index into a 'stack'");

        // ---- Deque as a queue ----
        System.out.println("\n--- ArrayDeque as a queue ---");
        Deque<String> queue = new ArrayDeque<>();
        queue.offer("a"); queue.offer("b"); queue.offer("c");
        System.out.print("   polling: ");
        while (!queue.isEmpty()) System.out.print(queue.poll() + " ");
        System.out.println();

        // ---- PriorityQueue: iteration is NOT sorted ----
        System.out.println("\n--- PriorityQueue ---");
        PriorityQueue<Integer> pq = new PriorityQueue<>(List.of(5, 1, 8, 3, 9, 2));
        System.out.println("   toString():  " + pq + "   ← HEAP order, not sorted");
        System.out.print("   polling:     ");
        PriorityQueue<Integer> copy = new PriorityQueue<>(pq);
        while (!copy.isEmpty()) System.out.print(copy.poll() + " ");
        System.out.println("   ← sorted");

        // ---- custom comparator ----
        System.out.println("\n--- task priority ---");
        PriorityQueue<Task> tasks = new PriorityQueue<>(
                Comparator.comparingInt(Task::priority).reversed());
        tasks.offer(new Task("low", 1));
        tasks.offer(new Task("urgent", 10));
        tasks.offer(new Task("medium", 5));
        while (!tasks.isEmpty()) System.out.println("   " + tasks.poll());

        // ---- top-k with a MIN heap ----
        System.out.println("\n--- top 3 largest via a MIN-heap ---");
        int[] data = {15, 3, 42, 8, 23, 4, 16, 99, 1};
        int k = 3;
        PriorityQueue<Integer> topK = new PriorityQueue<>();
        for (int x : data) { topK.offer(x); if (topK.size() > k) topK.poll(); }
        System.out.println("   input:  " + Arrays.toString(data));
        System.out.println("   top " + k + ":  " + new TreeSet<>(topK).descendingSet());

        // ---- ArrayDeque vs LinkedList, as a queue ----
        int n = 3_000_000;
        Deque<Integer> ad = new ArrayDeque<>();
        long start = System.currentTimeMillis();
        for (int i = 0; i < n; i++) ad.addLast(i);
        for (int i = 0; i < n; i++) ad.pollFirst();
        long adTime = System.currentTimeMillis() - start;

        Deque<Integer> ll = new LinkedList<>();
        start = System.currentTimeMillis();
        for (int i = 0; i < n; i++) ll.addLast(i);
        for (int i = 0; i < n; i++) ll.pollFirst();
        long llTime = System.currentTimeMillis() - start;

        System.out.printf("%n--- %,d enqueue + dequeue ---%n", n);
        System.out.printf("   ArrayDeque: %,5d ms%n", adTime);
        System.out.printf("   LinkedList: %,5d ms   ← %d objects allocated%n", llTime, n);

        // ---- nulls ----
        System.out.println("\n--- nulls ---");
        try { new ArrayDeque<String>().add(null); }
        catch (NullPointerException e) {
            System.out.println("   ArrayDeque rejects null — poll() returning null must mean EMPTY");
        }
    }
}
```

**Two results to note:** legacy `Stack` iterates **backwards** from pop order and lets you call
`get(0)` — both consequences of extending `Vector`. And `ArrayDeque` beats `LinkedList` substantially
on the same queue workload, because it allocates one array instead of three million nodes.

## Interview questions

**Q: Why shouldn't you use `Stack`?**
> It extends `Vector`, so it inherits indexed access and insertion — you can reach into the middle of
> a stack, which breaks the abstraction. Every method is synchronized, which costs on every call and
> still doesn't make compound operations atomic. And its iteration order is bottom-to-top, the
> opposite of pop order, which is a genuine source of bugs. Use `ArrayDeque`.

**Q: How is `ArrayDeque` implemented?**
> A circular array with head and tail indices that wrap modulo the array length, which is a power of
> two so the wrap is a bitwise AND. Adding at either end is amortised O(1), and it resizes by doubling
> when full. It beats `LinkedList` for both queue and stack use because it has no per-element node
> allocation and far better cache locality.

**Q: How does `PriorityQueue` work?**
> It's an array-backed binary heap. The tree structure is implicit in the indices — for index i, the
> parent is (i−1)/2 and the children are 2i+1 and 2i+2 — so there are no pointers. `peek` is O(1);
> `offer` sifts up and `poll` moves the last element to the root and sifts down, both O(log n).
> Building from a collection is O(n) via heapify.

**Q: Why isn't iterating a `PriorityQueue` sorted?**
> The heap invariant only requires each parent to be ordered before its children; siblings and
> subtrees are unordered relative to each other. Only repeated `poll` produces sorted output.
> `toString` shows the raw array, which is heap order.

**Q: How do you find the k largest elements in a stream?**
> Maintain a min-heap of size k. Offer each element, and if the heap exceeds k, poll — which removes
> the smallest of the current best k. It's counter-intuitive that the k *largest* needs a *min*-heap,
> but the head being the weakest candidate is exactly what makes eviction O(log k). Total cost is
> O(n log k) time and O(k) space, versus O(n log n) to sort everything.

**Q: Why does `ArrayDeque` reject nulls?**
> Because `poll` and `peek` return null to signal an empty deque. A stored null would be
> indistinguishable from emptiness, so the ambiguity is prevented by disallowing it.
