# Day 211

**L-211** · Embedding vs referencing — the only schema decision that matters

**Time:** 3 hrs · **Mode:** NEW

> **⭐ This is MongoDB's equivalent of Day 188.** In a relational database normalization gives you a
> default and you deviate with a reason. In MongoDB there is no default — **every relationship is an
> explicit choice between embedding and referencing**, and getting it wrong is expensive to reverse
> because there is no `ALTER TABLE` to fix it.
>
> Day 188's event-versus-entity distinction returns here, and it is the single most useful test.

---

# Part 1 — The two options

```javascript
// ⭐ EMBEDDED — one document, one read
{ _id: 1, orderNumber: "ORD-8842",
  items: [ { sku: "P-42", name: "Widget", qty: 2, unitPrice: NumberDecimal("29.99") } ] }

// ⭐ REFERENCED — two collections, two reads (or a $lookup)
{ _id: 1, orderNumber: "ORD-8842" }
{ _id: 9, orderId: 1, sku: "P-42", qty: 2 }
```

| | ⭐ Embed | ⭐ Reference |
|---|---|---|
| Read the whole thing | ⭐ **one operation** | ⭐ two, or a `$lookup` |
| Atomic update of the whole | ⭐ **yes — single-document atomicity** | ⭐ needs a transaction |
| Data duplication | ⭐ yes | no |
| Update a shared value | ⭐ **update every copy** | ⭐ one place |
| Unbounded growth | ⭐⭐ **hits the 16 MB limit** | ⭐ fine |
| Query the child independently | ⭐ awkward | ⭐ natural |

# Part 2 — ⭐⭐ The four rules

## ⭐ Rule 1 — Embed what is read together and does not exist alone

```javascript
{ _id: 1, items: [...], shippingAddress: {...}, payment: {...} }
```

**⭐ Order items have no independent existence** — nobody queries "all order items" as a primary use
case, and they are always read with the order. **That is a composition** (Day 159's cascade rule),
and embedding is correct.

**⭐ And it buys the property MongoDB is genuinely good at: single-document atomicity.** Updating the
order and its items is one atomic write with no transaction. Referencing them would require a
multi-document transaction for something that is conceptually one change.

## ⭐⭐ Rule 2 — Never embed anything unbounded

```javascript
// ❌❌ The classic MongoDB modelling failure
{ _id: 1, name: "Alice", orders: [ /* ⭐ 40,000 and counting */ ] }
```

**⭐ Three separate failures, and each alone is disqualifying:**

1. ⭐ **The 16 MB document limit.** Eventually every write fails. Not gradually — completely.
2. ⭐ **Every read of the customer fetches all 40,000 orders**, even to display their name.
3. ⭐ **Every append rewrites and may relocate the document**, growing slower over time.

> **⭐ The test: can this array grow without bound? If yes, reference. No exceptions.**

**⭐ Day 159's warning is the same argument in a different database** — an unbounded `@OneToMany`
collection is one `getOrders()` from an OOM. Both databases punish modelling an unbounded
relationship as a contained one.

## ⭐⭐ Rule 3 — Duplicate what must not change; reference what must stay current

**⭐ This is Day 188's event-versus-entity distinction, and it is the rule people most often get
backwards.**

```javascript
{ _id: 1,
  customer: { id: 1000, name: "Alice" },        // ⭐ SNAPSHOT — who ordered, at the time
  items: [{ sku: "P-42",
            name: "Widget",                     // ⭐ SNAPSHOT — the name when sold
            unitPrice: NumberDecimal("29.99")   // ⭐⭐ SNAPSHOT — the price PAID
          }]
}
```

**⭐ Embedding the price is not denormalization — it is a different fact.** `products.price` is the
current price; `unitPrice` is what this customer paid. **Looking it up live means last year's
invoices change when someone edits a price**, which is an accounting and legal problem, not a
performance one.

**⭐ Conversely, a product's current stock level must never be embedded in an order** — it must stay
current, so it is referenced.

> **⭐ The test: does this value describe an *event* (what happened) or an *entity* (what is true
> now)? Events are copied. Entities are referenced.**

## ⭐ Rule 4 — Use the extended reference pattern

```javascript
// ⭐ Reference the id, PLUS copy the two or three fields you always display
{ _id: 1,
  customer: { id: 1000, name: "Alice", email: "a@b.com" },   // ⭐ enough to render a list
  ... }
```

**⭐ The pragmatic middle ground and the most commonly correct answer**: one read renders the order
list with the customer's name — no `$lookup` — and the full customer document is fetched only when
someone opens the customer page.

**⭐ The cost is a consistency job**: when the customer's name changes, 40,000 embedded copies are
stale. Three responses, and choosing deliberately is the point:

| Response | When |
|---|---|
| ⭐ **Accept it — it is a snapshot** | ⭐ **usually correct.** The order shows the name used at the time |
| Background update job | when the copy must eventually agree |
| Change stream triggering the update | ⭐ near-real-time; more machinery |

**⭐ Notice that the first option is Rule 3 in disguise.** Most extended-reference staleness is not a
bug — it is a snapshot you failed to recognise as one.

# Part 3 — ⭐ Patterns for the harder cases

## ⭐ The bucket pattern — for time series

```javascript
// ❌ one document per reading: 86,400 documents per sensor per day
{ sensorId: "S1", ts: ISODate("..."), value: 23.4 }

// ⭐ one document per sensor per hour
{ sensorId: "S1", hour: ISODate("2026-08-14T10:00Z"),
  count: 3600, sum: 84240, min: 20.1, max: 26.8,     // ⭐ pre-aggregated
  readings: [ { t: 0, v: 23.4 }, { t: 1, v: 23.5 }, ... ] }
```

**⭐ 3,600 documents become one.** Index overhead falls by the same factor, and the pre-aggregated
`count`/`sum`/`min`/`max` answer most queries without touching the array at all.

**⭐ The bucket must be bounded** — one hour, or 1,000 readings — which is Rule 2 applied. MongoDB's
native time-series collections do this automatically and are the better choice on modern versions.

## ⭐ The subset pattern — bounded embedding

```javascript
{ _id: "P-42", name: "Widget",
  recentReviews: [ /* ⭐ the newest 10, embedded */ ],
  reviewCount: 4213 }
// ⭐ the full reviews live in their own collection
```

**⭐ The product page renders in one read**, and "see all reviews" is a second query nobody makes
first. **This is Rule 2 and Rule 1 reconciled**: embed a bounded subset, reference the unbounded
whole.

Maintain it with `$push` plus `$slice`:

```javascript
{ $push: { recentReviews: { $each: [newReview], $sort: { createdAt: -1 }, $slice: 10 } } }
```

**⭐ That is atomic and self-bounding** — one operation adds and trims, so the array cannot grow.

## Other patterns worth naming

| Pattern | Use |
|---|---|
| ⭐ **Computed** | store the total alongside the items — Day 188's counter, with the same reconciliation duty |
| **Outlier** | 99% fit the normal shape; the 1% get an overflow document |
| ⭐ **Schema versioning** | Day 210 — a `schemaVersion` field so migration is finishable |
| **Tree: parent reference** | `{ parentId }` — Day 188's adjacency list |
| ⭐ **Tree: materialised path** | ⭐ `{ path: "/1/7/22/" }` — one regex query for a subtree |

**⭐ `$graphLookup` performs recursive traversal** — MongoDB's answer to Day 188's recursive CTE — but
a materialised path is usually faster and simpler for read-heavy trees.

## ⭐ Many-to-many

```javascript
// ⭐ Embed the id array on the side with the BOUNDED count
{ _id: "student1", name: "Alice", courseIds: ["c1","c2","c3"] }   // ⭐ a student takes ~40 courses
{ _id: "c1", name: "Databases" }                                   // ⭐ a course has 10,000 students
```

**⭐ Embed on the bounded side, never both.** Embedding students in courses violates Rule 2, and
embedding both creates two copies that will disagree.

⚠️ **If the relationship needs its own fields** — enrolled-at, grade — **that is a separate
collection**, which is exactly Day 159's argument against `@ManyToMany`. **The same conclusion in
both databases: a relationship with attributes is an entity.**

# Part 4 — ⭐ The consequences you must accept

## ⭐ The 16 MB limit is a hard wall

**Not a warning, not degraded performance — writes fail.** And you find out in production, because
the document grew past it gradually.

```javascript
db.orders.aggregate([
  { $project: { size: { $bsonSize: "$$ROOT" } } },
  { $sort: { size: -1 } }, { $limit: 10 }
])                            // ⭐ monitor your largest documents. Do this.
```

**⭐ Alert at 8 MB.** By 16 MB it is an outage, and the fix — restructuring the model — is not a quick
one.

## ⭐ Document growth costs writes

**A document that grows is rewritten**, and if it no longer fits its allocated space it is relocated,
which means **every index entry pointing at it must be updated.** Day 186's non-in-place-update
argument, in a different engine — and the same conclusion: **frequent appends to a large embedded
array are expensive**, and the subset pattern exists to avoid them.

## ⭐ Reversing the decision is expensive

**⭐ There is no `ALTER TABLE`.** Converting embedded to referenced means a migration script that
reads every document, writes to a new collection, and updates every query — while the application
runs. **That is Day 166's expand/contract with no database help at all.**

**⭐ Which is why the decision deserves more time than it usually gets**, and why an interviewer
asking about it is asking whether you have felt the consequence.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Embedding an unbounded array | ⭐ 16 MB wall, huge reads, slow appends |
| Embedding for a relationship queried independently | awkward and slow |
| ⭐ Referencing a price that should be a snapshot | old invoices change when prices do |
| ⭐ Embedding a value that must stay current | stale stock levels |
| Embedding both sides of many-to-many | two copies that disagree |
| A many-to-many with attributes | it is an entity — a separate collection |
| Extended reference with no staleness decision | you discover the divergence in support tickets |
| Unbounded buckets in a time series | Rule 2 again |
| `$push` without `$slice` | the subset array is unbounded |
| ⭐ Not monitoring document size | the limit is a wall, hit in production |
| Frequent appends to a large array | rewrites and relocations |
| ⭐ Treating the choice as reversible | there is no `ALTER TABLE` |

## Interview questions

**Q: When do you embed, and when do you reference?**
Embed what is read together and has no independent existence — order items — because that gives one
read and single-document atomicity. Reference anything unbounded, because the 16 MB document limit is
a hard wall, every read fetches the whole array, and appends get slower. And reference anything that
must stay current, while duplicating anything that is a snapshot of what happened.

**Q: Give me the snapshot rule precisely.**
Does the value describe an event or an entity? A price paid describes an event, so it is copied into
the order — looking it up live means last year's invoices change when someone edits a price. A
product's current stock describes an entity, so it is referenced. It is the same distinction that
governs when copying data into a relational child table is not denormalization.

**Q: What is the extended reference pattern?**
Store the referenced id plus the two or three fields you always display, so a list renders in one read
without a `$lookup`. The cost is that those copies go stale — and the important part is deciding
which of three responses applies: accept it because it is genuinely a snapshot, run a background
update, or use a change stream. Usually the first, because most extended-reference staleness is a
snapshot you did not recognise.

**Q: How do you model time-series data?**
The bucket pattern — one document per sensor per hour with the readings in a bounded array, plus
pre-aggregated count, sum, min and max so most queries never touch the array. That turns 3,600
documents into one and cuts index overhead by the same factor. On modern MongoDB, native time-series
collections do it for you.

**Q: What happens if you get the decision wrong?**
It is expensive. There is no `ALTER TABLE` — converting embedded to referenced means reading every
document, writing a new collection, and rewriting every query, while the application is running. It
is expand/contract with no database support, which is why the decision deserves real thought up
front.

## Mini task

1. Model orders with embedded items and with referenced items. Load 1M. **Time reading one order,
   and time "all orders containing SKU P-42", in both.**
2. Embed orders inside customers. Generate a customer with 50,000 orders. **Find where it breaks** and
   check `$bsonSize`.
3. Time fetching just that customer's name from the bloated document versus a lean one.
4. Reference `unitPrice` from products. Change a price. **Reprint a six-month-old invoice.** Then
   embed it and repeat.
5. Build the extended reference. Change a customer name and **find the 40,000 stale copies.**
   Implement each of the three responses and compare effort.
6. Build a time series one-document-per-reading and as hourly buckets. **Compare document count,
   index size, and the time for "average for this hour".**
7. Implement the subset pattern with `$push`/`$slice`. Confirm the array stays at 10.
8. Model students and courses. Then add a grade to the relationship and **restructure it.**
9. Build a category tree with parent references, then materialised paths. Compare subtree queries and
   `$graphLookup`.
10. Write the aggregation that finds your ten largest documents. **Set up the alert.**
11. Write the migration converting embedded items to a referenced collection **with the application
    running.** Time it and count the query call sites you had to change.

## 🎙️ Articulation drill

Two minutes: **"How do you model relationships in MongoDB?"**

Give the four rules as decisions with reasons, not as a list. Embed what is read together and has no
independent existence, because that buys single-document atomicity. Never embed anything unbounded,
because the 16 MB limit is a wall rather than a slope. Snapshot what describes an event and reference
what must stay current — and use the price-paid example, because it is the one that makes the
distinction concrete. Close with the extended reference as the usual middle ground, and the point
that its staleness is usually a snapshot rather than a bug.
