# Day 408

**L-408** · Sagas — orchestration, choreography and compensation

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ A compensation is not a rollback. A rollback erases; a compensation is a new business action that
> partially offsets a completed one — and a refund is not an un-charge, because the customer saw the
> charge on their statement.**
>
> Today: sagas as ACD rather than ACID, **choreography versus orchestration decided by one question**,
> the countermeasures that recover the isolation you gave up, and **the timeout that every step needs and
> nobody writes.**

---

# Part 1 — ⭐⭐ What a saga is, and what it gives up

```
⭐ ONE transaction across services is impossible (Day 342: 2PC is blocking and unavailable).
⭐ ⇒ ⭐⭐ A SAGA is a SEQUENCE OF LOCAL TRANSACTIONS, each with a COMPENSATING transaction.

⭐   T1 reserve stock   → C1 release stock
⭐   T2 charge card     → C2 refund
⭐   T3 create shipment → C3 cancel shipment
⭐ ⇒ ⭐ T3 fails ⇒ ⭐⭐ run C2 then C1. ⭐⭐ Backwards, in reverse order.
```

| ⭐⭐ ACID → ACD | |
|---|---|
| ⭐ **A**tomicity | ⭐⭐ **eventually**, via compensation — not instantaneously |
| ⭐ **C**onsistency | ⭐ preserved at the end |
| ⭐⭐ **I**solation | ⭐⭐ **GONE. This is the cost, and it is the one people miss.** |
| ⭐ **D**urability | ⭐ each local transaction is durable |

```
⭐⭐ NO ISOLATION MEANS INTERMEDIATE STATE IS VISIBLE:
⭐   T1 reserved stock · T2 charged · ⭐⭐ T3 fails and compensation is running
⭐   ⇒ ⭐⭐ for those seconds, another user sees stock reserved that is about to be released,
⭐     and the customer sees a charge that is about to be refunded.
⭐   ⇒ ⭐⭐ Every saga has a window where the world is in a state your domain model does not describe.
```

## ⭐⭐ Compensation is not rollback

| ⭐ Type | ⭐ Compensable? |
|---|---|
| ⭐ Reserve stock, create a draft, place a hold | ✅ ⭐ cleanly reversible |
| ⭐ Charge a card | ⚠️ ⭐⭐ **refundable, not reversible** — fees, statements, an unhappy customer |
| ⭐⭐ **Send an email / SMS / push** | ❌ ⭐⭐ **impossible. It has been read.** |
| ⭐ Call a third-party API with a side effect | ⚠️ ⭐ depends entirely on them |
| ⭐⭐ **Ship a physical item** | ❌ ⭐⭐ it is on a van |

> **⭐⭐ The design rule that falls out: order the steps so the least reversible one is LAST.** Reserve,
> validate, authorise — **then** charge, **then** send the email. **A saga that emails at step 2 and
> fails at step 4 has no way back**, and no amount of framework helps.

⚠️ **And its cousin: prefer *authorise* then *capture* over *charge*.** An authorisation hold that
expires is a genuinely reversible step; **a capture is not.** Payment APIs give you this split precisely
because saga-shaped failures are the normal case.

# Part 2 — ⭐⭐ Choreography vs orchestration

| | ⭐ Choreography | ⭐⭐ Orchestration |
|---|---|---|
| ⭐ How | ⭐ each service reacts to events and emits its own | ⭐⭐ **a coordinator issues commands and tracks state** |
| ⭐ Coupling | ⭐ no central component | ⭐ everyone couples to the orchestrator |
| ⭐⭐ **"Where is order 123?"** | ⭐⭐ **nobody knows — reconstruct it from logs across five services** | ⭐⭐ **one row. One query.** |
| ⭐ Adding a step | ⭐ subscribe a new service — no existing code changes | ⭐ edit the orchestrator |
| ⭐⭐ **Compensation** | ⭐⭐ **each service must know what to undo and in what order — this is where it breaks** | ⭐ the coordinator runs it |
| ⭐ Testing | ⭐⭐ integration-only, and hard | ⭐⭐ **the state machine is unit-testable** |
| ⭐ Cyclic dependencies | ⭐⭐ easy to create accidentally | ⭐ visible |

```
⭐⭐ THE DECIDING QUESTION:
⭐   ⭐⭐ "Will anyone ever ask WHERE A GIVEN TRANSACTION IS, or WHY IT STOPPED?"
⭐   ⇒ ⭐⭐ yes (and the answer is always yes in a business process) ⇒ ⭐⭐ ORCHESTRATION.
⭐
⭐ ⭐ Rough rule: ⭐ 2–3 steps, no compensation ⇒ choreography is fine and pleasantly simple.
⭐              ⭐⭐ 4+ steps, or ANY compensation ⇒ ⭐⭐ orchestrate. Always.
```

> **⭐ Choreography's failure mode is not technical, it is organisational.** After a year nobody can draw
> the flow, **because the flow does not exist anywhere — it is emergent from eight subscriptions.**
> Debugging a stuck order becomes archaeology across five services' logs, **and the trace is the only
> artefact that even hints at the shape.**

| ⭐ Implementing an orchestrator | |
|---|---|
| ⭐⭐ **A state machine table + the outbox** | ⭐⭐ **the version you can build today** (Day 407) |
| ⭐ **AWS Step Functions** | ⭐ visual, managed, retries and catch built in (Day 393) |
| ⭐⭐ **Temporal / Cadence** | ⭐⭐ durable execution — **you write it as ordinary sequential code and the platform survives crashes** |
| ⭐ Camunda / Zeebe | BPMN, strong for human-in-the-loop processes |

# Part 3 — ⭐⭐ Getting isolation back: the countermeasures

| ⭐ Countermeasure | ⭐ What it does |
|---|---|
| ⭐⭐ **Semantic lock** | ⭐⭐ a **pending** state on the record — `status = PENDING_PAYMENT` — so others know it is mid-flight |
| ⭐⭐ **Commutative updates** | ⭐⭐ `balance += x` commutes; `balance = x` does not — **order stops mattering** |
| ⭐ **Pessimistic view** | ⭐⭐ **reorder steps so the risky one is last** (the rule from Part 1) |
| ⭐ **Reread value** | ⭐ re-check the record has not changed before acting — optimistic offline lock |
| ⭐ **Version file** | ⭐ record operations and reorder/reconcile them |
| ⭐ **By value** | ⭐⭐ **route by risk: small orders take the saga, large ones take 2PC or a human** |

> **⭐⭐ The semantic lock is the one you will use.** `PENDING` is not a technicality — **it is you
> admitting in the schema that the intermediate state exists**, so queries, UI and other sagas can see
> it and behave correctly. **A domain model with no pending states is a domain model that pretends sagas
> are atomic.**

⚠️ **And "by value" deserves a moment because it is the most commercially sensible idea in the saga
literature: not every transaction needs the same machinery.** A £5 order can take the eventually
consistent path; **a £5,000,000 trade can take a slower path with stronger guarantees or a human check.**
**Uniform mechanism is a choice, not a requirement.**

# Part 4 — ⭐⭐ Making one survive production

| ⭐ Requirement | ⭐ Why |
|---|---|
| ⭐⭐ **Every step idempotent** | ⭐⭐ retries are guaranteed (Day 398, 407) |
| ⭐⭐ **Every step has a TIMEOUT** | ⭐⭐ **a step with no timeout means a saga stuck forever with no alarm** |
| ⭐⭐ **Compensations are idempotent too** | ⭐⭐ compensation runs are retried as well — **double refunds are a real incident** |
| ⭐ Terminal states are explicit | ⭐ `COMPLETED`, `COMPENSATED`, **`FAILED_MANUAL_INTERVENTION`** |
| ⭐⭐ **A compensation can fail** | ⭐⭐ retry, then **escalate to a human** — you cannot compensate a compensation |
| ⭐ Persist state before each step | ⭐ so a crash resumes rather than restarts |
| ⭐⭐ **Alarm on stuck sagas** | ⭐⭐ "any saga in a non-terminal state for > 15 minutes" — **the single most valuable alert here** |
| ⭐ One trace id across the whole saga | ⭐ otherwise debugging is impossible (Day 376) |

```
⭐⭐ THE STATE THAT MUST EXIST AND USUALLY DOES NOT:
⭐   ⭐⭐ FAILED_MANUAL_INTERVENTION
⭐   ⇒ ⭐ the compensation failed, or the step is not compensable, or a human must decide.
⭐   ⇒ ⭐⭐ Without it, a saga silently sits in PENDING forever and someone finds it in six weeks
⭐     ⭐⭐ via a customer complaint. ⭐ With it, there is a queue, an owner and a dashboard.
```

> **⭐ The mature framing: a saga is a business process with failure modes, not a technical retry loop.**
> Some failures genuinely require a person. **Designing that in — a queue, an owner, an SLA — is what
> separates a saga that works from one that quietly accumulates broken orders.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Calling compensation "rollback"** | ⭐⭐ it is a new business action; some steps cannot be undone |
| ⭐⭐ **A non-compensable step early in the saga** | ⭐⭐ no way back from a later failure |
| ⭐ Charging instead of authorise-then-capture | ⭐ throws away a reversible step the API gave you |
| ⭐⭐ **Forgetting isolation is gone** | ⭐⭐ intermediate states are visible and unmodelled |
| ⭐ No pending/semantic-lock states | ⭐⭐ the schema pretends sagas are atomic |
| ⭐⭐ **Choreography for a 6-step process with compensation** | ⭐⭐ nobody can answer "where is order 123?" |
| ⭐ Accidental event cycles in choreography | ⭐ infinite loops nobody designed |
| ⭐ Non-idempotent steps | ⭐⭐ retries duplicate effects |
| ⭐⭐ **Non-idempotent compensations** | ⭐⭐ double refunds |
| ⭐⭐ **No per-step timeout** | ⭐⭐ sagas stuck forever, silently |
| ⭐⭐ **No `FAILED_MANUAL_INTERVENTION` state** | ⭐⭐ found six weeks later via a complaint |
| ⭐ No alarm on non-terminal sagas | the same, but slower |
| Uniform mechanism for every value of transaction | "by value" routing exists for a reason |

## Interview questions

**Q: What is a saga and what does it give up?**
A sequence of local transactions, each with a compensating action, used because a single transaction
across services is not available — two-phase commit is blocking and reduces availability. What you give
up is isolation. You keep atomicity eventually, consistency at the end and durability per step, but for
the duration of the saga the intermediate state is visible to everyone: stock reserved that is about to be
released, a charge about to be refunded. Every saga has a window where the world is in a state your domain
model probably does not describe, which is why pending states belong in the schema.

**Q: Why is compensation not rollback?**
Because a rollback erases and a compensation is a new business action that partially offsets a completed
one. A refund is not an un-charge — the customer saw the charge, there may be fees, and their statement
records both. Some steps cannot be compensated at all: an email has been read, an item is on a van. That
drives the most important design rule in sagas, which is to order steps so the least reversible one runs
last, and to prefer an authorisation hold over a capture wherever the API allows it, because a hold
expires and a capture does not.

**Q: Orchestration or choreography?**
One question decides it: will anyone ever need to know where a given transaction is or why it stopped? In
a business process the answer is always yes, and with an orchestrator that is one row and one query, while
with choreography nobody knows because the flow does not exist anywhere — it is emergent from eight
subscriptions. My rule is that two or three steps with no compensation can be choreographed and it is
pleasantly simple; four or more steps, or any compensation at all, should be orchestrated. Choreography's
real failure is organisational: after a year nobody can draw the flow, and debugging a stuck order becomes
archaeology across five services' logs.

**Q: Sagas have no isolation. What do you do about it?**
Use the countermeasures from the saga literature, and the one that carries most of the weight is the
semantic lock — an explicit pending state on the record, so other readers and other sagas can see that it
is mid-flight and behave accordingly. Beyond that: make updates commutative where possible so ordering
stops mattering, reorder steps so the risky one is last, re-read and version-check before acting, and
route by value — a five pound order can take the eventually consistent path while a very large one takes a
slower path or a human check. Uniform mechanism for every transaction size is a choice, not a requirement.

**Q: What makes a saga survive production?**
Idempotency on every step, because retries are guaranteed — and idempotency on every compensation too,
since double refunds are a real incident. A timeout on every step, because a step without one means a saga
stuck forever with nothing to alert on. Persisting state before each step so a crash resumes rather than
restarts. A single trace id across the whole flow. And the state most implementations lack: an explicit
failed-manual-intervention terminal state, for when the compensation itself fails or the step was never
compensable. Without it those sagas sit in pending forever and someone finds them six weeks later via a
customer complaint. With it there is a queue, an owner and an alert on any saga non-terminal for more
than fifteen minutes.

   dashboard.

    finds out.

## 🎙️ Articulation drill

**Two minutes:** *"How do you keep data consistent across three services?"*

**⭐ Rule out the wrong answer first: not a distributed transaction — two-phase commit blocks and takes
your availability down to the product of every participant. So a saga: local transactions with
compensations.**

**⭐ Then the two things people leave out. Compensation is not rollback — a refund is not an un-charge and
an email cannot be unsent — so the steps are ordered with the least reversible one last, and payments use
an authorisation hold rather than a capture wherever possible. And sagas give up isolation, so the
intermediate state is visible and belongs in the schema as an explicit pending state rather than being
pretended away.**

**⭐ I orchestrate rather than choreograph as soon as there are more than about three steps or any
compensation, because someone will ask where order 123 is, and with an orchestrator that is one query.
Every step is idempotent and has a timeout, compensations are idempotent too, and there is an explicit
manual-intervention state with an alert on anything non-terminal for fifteen minutes — because some
failures genuinely need a person, and designing that in is what stops broken orders quietly
accumulating.**
