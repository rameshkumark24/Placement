# Day 268 🏗️

**P-268** · Real-time updates — and the honest choice between SSE and WebSockets

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ The most valuable thing you can do today is narrow the requirement before building anything.**
> Day 180's argument: SSE is the right answer far more often than it is chosen, and a WebSocket
> turns a stateless service into a connection-oriented one — which changes load balancing,
> deployment, authentication and capacity planning at once.
>
> **⭐ "I used SSE because the client only receives, and here is what that saved me" is a stronger
> answer than a WebSocket you did not need.**

---

# Part 1 — ⭐ Narrow the requirement first

**⭐ Three questions, in order:**

> **⭐ 1. Does the client need to *send*, or only *receive*?**
> **⭐ 2. How fresh must it be — 30 seconds, 2 seconds, or immediate?**
> **⭐ 3. How many concurrent connections at peak?**

| Answer | ⭐ Choice |
|---|---|
| ⭐ 30 s freshness is fine | ⭐ **polling. This is a legitimate answer** — say so |
| ⭐ Receive only, needs to be immediate | ⭐⭐ **SSE** |
| Genuine bidirectional — chat, collaborative editing | WebSocket + STOMP |
| Very high connection counts | ⭐ WebSocket, and plan Part 3 seriously |

**⭐ For most flagship projects the answer is SSE**, and Day 180's three advantages are concrete:

| | |
|---|---|
| ⭐ 1 | ⭐ **Plain HTTP** — passes through every proxy, no upgrade, no special configuration |
| ⭐ 2 | ⭐ **Normal `Authorization` headers** — Day 258's bearer token works unchanged |
| ⭐ 3 | ⭐ **The browser reconnects automatically** with `Last-Event-ID` — free resumption |

**⭐ Point 3 is the one that saves you the most work.** With a WebSocket you write reconnection,
backoff and resumption yourself; with SSE the browser does it.

# Part 2 — ⭐ SSE, built correctly

```
⭐ SseEmitter with an EXPLICIT TIMEOUT — never the default
⭐ Registry keyed by userId (or tenant + resource)
⭐⭐ Remove on ALL THREE callbacks: onCompletion, onTimeout, onError
```

> **⭐⭐ A registry of dead emitters is a memory leak that grows with every disconnect — and
> disconnects are constant on mobile.** This is Day 180's first trap and it is easy to hit: the happy
> path works perfectly and memory climbs for a week.

**⭐ Test it explicitly**: connect and disconnect 1,000 times and watch the registry size return to
zero.

## ⭐ Emitting from the domain

```
⭐ @TransactionalEventListener(AFTER_COMMIT) → push to connected emitters
```

**⭐ `AFTER_COMMIT`, not the plain listener** (Day 179): otherwise you push "booking confirmed" to a
client for a transaction that then rolls back — **and unlike a database write, you cannot take it
back.**

**⭐ And the multi-instance problem is the same as Day 180's:**

```
⭐ Alice's SSE connection is on instance 1.
⭐ The booking is confirmed on instance 2.
⭐⭐ Instance 2 has no emitter for Alice.
```

**⭐ Redis Pub/Sub is the correct fan-out here** (Day 209): every instance subscribes, and each pushes
to its own local emitters. **Pub/Sub's at-most-once nature is acceptable** because a missed message
means one missed update, which the client's reconnect-and-refetch recovers.

**⭐ Say that trade-off explicitly** — "I used Pub/Sub rather than Streams because loss is acceptable
here and the client refetches on reconnect" is exactly the kind of reasoning being assessed.

## ⭐ Resumption

```
⭐ Send an event id with every message
⭐ On reconnect the browser sends Last-Event-ID → ⭐ replay what was missed
```

**⭐ Without this a reconnect means a full state refetch**, which on a deploy means every client
refetching at once — Day 180's thundering herd. **A small Redis Stream or sorted set of recent events
per user makes resumption cheap** (Day 204).

# Part 3 — ⭐ If you genuinely need WebSockets: the three problems

**⭐ Only proceed here if question 1 in Part 1 was "the client needs to send".**

### ⭐⭐ 1. The simple broker does not scale

```
⭐ registry.enableSimpleBroker(...)   ← ⭐ subscriptions live in THIS JVM's memory
```

**⭐ Two users in the same room on different instances never see each other's messages** — and there
is **no error**. It works perfectly on one instance and silently breaks on two.

| Fix | Note |
|---|---|
| ⭐ **A STOMP broker relay** (RabbitMQ) | ⭐ the correct answer — the broker owns routing |
| Redis Pub/Sub fan-out | ⭐ pragmatic; no durability or acknowledgements |
| ⭐ Sticky sessions | ⭐ **does not help** — two users in one room still land on different instances |

**⭐ The sticky-sessions point is worth knowing** because it is the intuitive fix and it does not work.

### ⭐⭐ 2. Authentication happens once

```
⭐ Authenticate on the STOMP CONNECT frame — ⭐ NOT the handshake
⭐⭐ AUTHORIZE EVERY SUBSCRIBE
```

**⭐ Browsers cannot set custom headers on a WebSocket handshake**, which is why so many
implementations fall back to a cookie — **and then inherit Cross-Site WebSocket Hijacking**, because
the handshake is not covered by the same-origin policy the way `fetch` is (Day 180).

> **⭐⭐ A connected user can subscribe to *any* destination unless you check.** `/topic/rooms/42` is
> readable by someone who was never in room 42 — **Day 174's IDOR over a different transport**, and
> almost nobody writes the check.

**⭐ And never put the token in the query string** — it lands in access logs, proxy logs and browser
history. If you must, use a single-use short-lived ticket obtained from an authenticated HTTP call.

**⭐ Also: a token verified at CONNECT is never re-checked**, so a 15-minute token authorises a
connection that may live for hours. Bound the connection lifetime, or re-validate periodically.

### ⭐ 3. Every deploy drops every connection

```
⭐ Client-side jittered reconnect backoff        ← ⭐ Day 123's full jitter
⭐ Graceful drain before shutdown                ← Day 133
⭐ Resume by last-event-id                       ← so reconnect ≠ full refetch
```

**⭐ And the capacity model is different**: plan by *concurrent connections*, not requests per second.
Each connection holds a socket, buffers and session state.

```
⭐ setMessageSizeLimit, ⭐ setSendBufferSizeLimit, setSendTimeLimit
⭐ Heartbeats enabled
```

**⭐ A slow client with no send-buffer limit is a memory leak with a heartbeat** — messages queue
server-side for a consumer that is not draining them (Day 180).

# Part 4 — ⭐ Prove it, and know what you would do at scale

```
⭐ 1.  1,000 connect/disconnect cycles     → ⭐ the registry returns to zero
⭐ 2.  Two instances, event on instance 2  → ⭐ the client on instance 1 receives it
⭐ 3.  Roll back after emitting            → ⭐ NOTHING was pushed (AFTER_COMMIT)
⭐ 4.  Kill the server mid-stream          → ⭐ the browser reconnects automatically
⭐ 5.  Reconnect with Last-Event-ID        → ⭐ missed events replayed, no full refetch
⭐ 6.  Subscribe to another tenant's stream → ⭐ REJECTED
⭐ 7.  A client that never reads           → ⭐ bounded by the send-buffer limit
⭐ 8.  500 connections, restart            → ⭐ observe the reconnect pattern with and without jitter
```

**⭐ Test 6 is the one that matters most** — it is the authorization check that the transport makes
easy to forget, and it is a real vulnerability class.

**⭐ Test 8 is the demonstration**: without jitter, 500 clients return in one synchronised wave.

## ⭐ Metrics

```
⭐ sse_connections_active / websocket_sessions_active   ← ⭐ a GAUGE — your real capacity metric
⭐ messages_pushed_total, ⭐ push_failures_total
⭐ reconnects_total                                      ← ⭐ a spike means instability
```

**⭐ The active-connections gauge is the capacity number to alert on**, because it is the resource
that saturates first — not CPU, not the connection pool.

## ⭐ And say what you would do at ten times the scale

**⭐ A good defence answer names the next step without pretending you needed it:**

> **⭐ "At this volume one instance holds all connections. At ten times, I would deploy the real-time
> path as a separate service — so it deploys on a different cadence from the API — and move the
> broker out of process."**

**⭐ Separating the real-time service is the right architectural move** (Day 180) precisely because
every deploy drops every connection: **you want to deploy the API frequently and the connection
holder rarely.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ WebSockets where SSE would do | ⭐ statefulness, proxy issues, hand-written reconnection |
| ⭐⭐ **Emitter not removed on all three callbacks** | ⭐⭐ a leak that grows with every disconnect |
| No emitter timeout | connections accumulate forever |
| ⭐ Pushing before commit | ⭐ an update for a transaction that rolled back |
| ⭐ **Simple broker with multiple instances** | ⭐ messages silently undelivered |
| Sticky sessions as the fix | does not solve two users in one room |
| ⭐ `setAllowedOrigins("*")` | ⭐ Cross-Site WebSocket Hijacking |
| Cookie authentication on WebSockets | combines with the above into a full read |
| ⭐⭐ **No SUBSCRIBE authorization** | ⭐⭐ any user reads any destination |
| Token in the query string | logged everywhere |
| No token re-validation | a 15-minute token authorises a 6-hour connection |
| ⭐ No send-buffer limit | one slow consumer exhausts server memory |
| No heartbeats | dead connections linger |
| ⭐ No client jitter on reconnect | a thundering herd on every deploy |
| No resumption | every reconnect is a full state refetch |
| Capacity planned in RPS | the constraint is concurrent connections |

## 🎤 Defence questions

1. **⭐ Why SSE rather than WebSockets — or why not?**
2. **⭐ What happens to your emitters when a client disconnects?** (⭐ and how do you know?)
3. **⭐ You run two instances. The event happens on one and the client is on the other. Then what?**
4. **⭐ Why do you push on `AFTER_COMMIT`?**
5. **⭐ Why Pub/Sub rather than Streams for this?**
6. **⭐ What stops a user subscribing to another tenant's stream?**
7. **⭐ What happens to all your connections when you deploy?**
8. **⭐ What is your capacity metric, and what would you do at ten times the scale?**
