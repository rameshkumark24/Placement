# Day 207 ⭐

**L-207** · Distributed locks — why naive `SETNX` is wrong, and the Redlock debate

**Time:** 3+ hrs · **Mode:** NEW · **Marquee day**

> **⭐ This is the best distributed-systems interview topic in the entire stage**, because the naive
> answer is three lines of code, and every step from there to a correct answer teaches something real
> about failure modes, clocks and consensus.
>
> Day 178 used ShedLock without examining it. Day 205 established that Redis replication is
> asynchronous with no RPO-0 failover. **Today those two facts collide**, and the honest conclusion
> is more interesting than either "use Redlock" or "never use Redlock".

---

# Part 1 — Building it wrong, four times

### ⭐ Attempt 1 — `SETNX` alone

```
SETNX lock:orders 1        -- acquired if it returns 1
... do the work ...
DEL lock:orders
```

**⭐ Fatal flaw: if the holder crashes, the lock is held forever.** Nothing else ever runs. A
deployment, an OOM kill, or a network partition permanently wedges the job.

### ⭐ Attempt 2 — add an expiry

```
SETNX lock:orders 1
EXPIRE lock:orders 30       -- ⭐⭐ TWO commands
```

**⭐ Fatal flaw: the gap between them.** If the client dies after `SETNX` and before `EXPIRE`, the
lock has no TTL and you are back to attempt 1 — **but only occasionally**, which is worse, because it
passes every test.

```
SET lock:orders 1 NX EX 30     -- ⭐ one atomic command (Day 204). Fixes THIS bug only.
```

### ⭐⭐ Attempt 3 — the bug that actually corrupts data

```
SET lock:orders 1 NX EX 30      -- A acquires
-- ⭐ A pauses: GC pause, slow disk, network blip. 35 seconds elapse.
-- ⭐ The lock EXPIRES. B acquires it and starts working.
-- ⭐ A wakes up, finishes its work, and calls:
DEL lock:orders                  -- ⭐⭐ A DELETES B's LOCK.
-- ⭐ C now acquires it. B and C run concurrently.
```

**⭐ Two independent failures in that sequence, and people usually only fix one:**

1. ⭐ **A released a lock it no longer owned.** Fixed by a unique token:

```java
String token = UUID.randomUUID().toString();
redis.opsForValue().setIfAbsent(key, token, Duration.ofSeconds(30));
```

```lua
-- ⭐⭐ release MUST be atomic: check-and-delete cannot be two commands (Day 203)
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

**⭐ Checking ownership with `GET` then calling `DEL` is the same two-command race one level up** —
the lock can expire between them. It must be one Lua script.

2. ⭐⭐ **A and B ran concurrently regardless.** The token fixes the *release*; it does not stop two
   holders existing. **That is the flaw no amount of Redis-side correctness fixes**, and it is the
   heart of the day.

### ⭐ Attempt 4 — extend the lease (a watchdog)

```java
// ⭐ a background timer extends the TTL while work continues — what Redisson does
scheduler.scheduleAtFixedRate(() -> extendIfOwner(key, token, 30), 10, 10, SECONDS);
```

**Better — and still not a guarantee.** ⭐ **A process paused for 40 seconds cannot extend its own
lease**, because it is not running. The watchdog reduces the probability; it does not remove the
failure mode.

# Part 2 — ⭐⭐ The fundamental problem

> **⭐ A lock with a timeout cannot guarantee mutual exclusion, because the holder cannot know it
> still holds the lock.**

**⭐ Between checking the lock and performing the action, any of these can exceed the TTL:**

| Cause | Note |
|---|---|
| ⭐ **A stop-the-world GC pause** | ⭐ a multi-second JVM pause is entirely normal |
| ⭐ **Process suspension** | the OS descheduled it; a VM was live-migrated |
| Slow disk or network I/O | |
| ⭐ **Clock drift or an NTP jump** | the TTL is measured in wall-clock time |

**⭐ The JVM point is not theoretical.** A full GC on a large heap is seconds. Your code cannot detect
that it was paused, and by the time it resumes, the lock it "holds" belongs to someone else.

## ⭐ Redlock, and Martin Kleppmann's objection

**Redlock** acquires the lock on a majority of N independent Redis masters (typically 5), requiring
that acquisition took much less than the TTL.

**⭐ Kleppmann's critique, and the reply from Salvatore Sanfilippo (Redis's author), are the material
worth knowing** — this exchange is what the interview question is really about.

| Kleppmann's objection | The counter-argument |
|---|---|
| ⭐ **A GC pause breaks it regardless of how many nodes agree** | ⭐ true of *every* timeout-based lock, not just Redlock |
| ⭐ **It depends on bounded clock drift** — an NTP jump can expire a lease early | operationally manageable with monitored NTP |
| Redis has no consensus protocol or fencing | ⭐ ZooKeeper/etcd also cannot stop a paused process |
| ⭐ **It is neither efficient nor safe: too complex for efficiency, too weak for correctness** | ⭐ **the strongest form of the objection** |

**⭐ The synthesis, and this is the answer that lands in an interview:**

> **⭐ Redlock is not meaningfully safer than a single-instance lock for *correctness*, because no
> timeout-based lock is safe against a paused process. It is more *available* — it survives one Redis
> node failing. If you need correctness you need fencing; if you need availability you need
> replication. Redlock buys the second and is often mistaken for the first.**

## ⭐⭐ Fencing tokens — the actual solution

**⭐ Kleppmann's constructive answer, and the part people skip:**

```
1. The lock service issues a monotonically increasing token with each grant.
   A gets token 33. A pauses.
   B acquires after expiry and gets token 34.

2. ⭐⭐ EVERY WRITE CARRIES ITS TOKEN, and the STORAGE rejects a stale one.
   B writes with token 34 → accepted. The storage records 34.
   A wakes and writes with token 33 → ⭐ REJECTED, 33 < 34.
```

**⭐ The lock is no longer the safety mechanism — the storage is.** Correctness moves to the place
that can actually enforce it.

```sql
-- ⭐ in PostgreSQL, this is one WHERE clause
update jobs set status = 'DONE', fence = :token where id = :id and fence < :token;
```

**⭐ And notice what that is: Day 165's optimistic locking.** A version column *is* a fencing token.
The connection between "distributed lock" and "`@Version`" is exactly this, and being able to state
it is a strong signal.

**⭐ The catch: your storage must support it.** Redis `INCR` provides monotonic tokens, but the
*resource being protected* must check them. If you are calling a third-party API that has no such
check, fencing is unavailable — which is precisely when you need idempotency keys instead (Day 123).

# Part 3 — ⭐ What to actually do

**⭐ The decision that matters is not which lock — it is what happens if the lock fails.**

| Requirement | Answer |
|---|---|
| ⭐ **Efficiency** — avoid duplicate work; duplicates are merely wasteful | ⭐ **a single-instance Redis lock is fine.** Redlock is overkill |
| ⭐ **Correctness** — duplicates corrupt data | ⭐⭐ **a lock is NOT sufficient.** Fencing tokens, or a database constraint |
| Job scheduling across instances | ⭐ ShedLock (Day 178) — efficiency, not correctness |
| ⭐ **Genuine mutual exclusion** | ⭐ ZooKeeper/etcd + fencing, or ⭐ **do it in the database** |

**⭐ The reframe that resolves most real cases:**

> **⭐ Most things people use a distributed lock for should be idempotent instead.** Day 178's
> argument: a job that claims work atomically with `FOR UPDATE SKIP LOCKED` and records what it did
> **does not need a lock at all** — duplicate execution becomes parallelism.

**⭐ Ask "what if this runs twice?" before asking "how do I lock it?"** If the answer is "nothing
bad", you have saved yourself the entire problem.

## ⭐ The database as the lock

```sql
select pg_advisory_xact_lock(hashtext('nightly-report'));   -- ⭐ released at commit, always
```

**⭐ PostgreSQL advisory locks are safer than any Redis lock** for work that already touches the
database:

- ⭐ **No TTL, so no expiry race** — the transaction-scoped form is released when the transaction
  ends, including on a connection drop.
- ⭐ **The lock and the work share one transaction**, so there is no window between them.
- No extra system to run.

⚠️ **Use `pg_advisory_xact_lock`, not `pg_advisory_lock`** — the session-scoped version survives the
transaction and leaks if you forget to unlock, and it does not survive PgBouncer transaction mode
(Day 197) at all.

**⭐ The limitation is honest: it requires a database connection for the lock's duration**, which for
a long job holds a pooled connection (Day 156). For short critical sections it is the best answer
available.

## ⭐ If you do use Redis: use Redisson

```java
RLock lock = redisson.getLock("orders:nightly");
if (lock.tryLock(5, 30, TimeUnit.SECONDS)) {        // ⭐ wait 5s, lease 30s
    try { doWork(); } finally { lock.unlock(); }     // ⭐ unlock in a finally, always
}
```

**⭐ Redisson gets right what hand-rolled locks get wrong**: unique ownership tokens, atomic Lua
release, a watchdog that extends the lease, reentrancy, and a `RedissonRedLock` if you want it.
**Do not hand-roll this** — every step of Part 1 is a bug someone has shipped.

**⭐ And always `tryLock` with a timeout, never a blocking `lock()`.** An unbounded wait for a lock is
Day 154's missing-timeout failure in another guise: threads pile up and the service stops.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `SETNX` with no expiry | a crashed holder wedges it forever |
| ⭐ `SETNX` + `EXPIRE` as two commands | intermittent lock with no TTL |
| ⭐ No ownership token | you delete someone else's lock |
| ⭐ `GET` then `DEL` to release | the same race one level up; use Lua |
| ⭐ Believing a token prevents concurrent holders | it prevents wrong *release*, not double execution |
| Assuming a watchdog is a guarantee | a paused process cannot extend its lease |
| ⭐ Believing Redlock gives correctness | no timeout-based lock does |
| Ignoring the GC-pause failure mode | multi-second JVM pauses are normal |
| ⭐ Not asking "what if this runs twice?" | you solve the hard problem instead of removing it |
| ⭐ No fencing token on the write | the storage cannot reject the stale writer |
| Hand-rolling instead of Redisson | every Part 1 bug |
| Blocking `lock()` with no timeout | thread pile-up (Day 154) |
| ⭐ `pg_advisory_lock` instead of the `_xact_` form | leaks; broken under PgBouncer |

## Interview questions

**Q: Implement a distributed lock with Redis.**
`SET key token NX EX ttl` for acquisition — one atomic command, with a unique token — and a Lua
script for release that checks the token and deletes in one step, because check-then-delete is a
race. But I would lead with the caveat: this prevents releasing someone else's lock; it does not
prevent two processes believing they hold it.

**Q: Why can't it prevent that?**
Because the holder cannot know it still holds the lock. A stop-the-world GC pause, a descheduled
process, or a clock jump can exceed the TTL, and the process has no way to detect that it was paused.
It resumes believing it holds a lock that expired and was reacquired. That is true of every
timeout-based lock, regardless of how many nodes agree.

**Q: What is Redlock, and is it safe?**
Acquiring on a majority of independent Redis masters. Kleppmann's objection is that it is neither
efficient nor safe — too complex if you only need efficiency, and still broken by a GC pause if you
need correctness, plus it assumes bounded clock drift. My position is that Redlock buys
*availability*, not correctness, and is often mistaken for the latter.

**Q: So how do you get correctness?**
Fencing tokens. The lock issues a monotonically increasing number, every write carries it, and the
storage rejects a token lower than the last one it accepted — so a paused process that wakes up
cannot write. That moves correctness to the storage, which is the only layer that can enforce it. And
in PostgreSQL a fencing token is just a version column, so it is Day 165's optimistic locking.

**Q: What would you actually build?**
First I would ask what happens if the work runs twice. If the answer is "nothing bad", I make it
idempotent and skip the lock entirely — a job claiming rows with `FOR UPDATE SKIP LOCKED` needs no
lock. If I need mutual exclusion for efficiency, Redisson or ShedLock. If I need it for correctness,
a database advisory lock in the same transaction as the work, or fencing tokens — not a Redis lock.

## Mini task

1. Implement all four attempts in order. **For each, write the failing sequence, then reproduce it**
   — kill the process at the exact moment, or use a debugger breakpoint.
2. Reproduce attempt 3: acquire with a 5-second TTL, `Thread.sleep(7000)`, and release. **Confirm you
   deleted a lock acquired by a second process.**
3. Add the token. Confirm the release is rejected. **Then confirm both processes still ran
   concurrently** — that is the point.
4. Implement the Lua release. Then implement it as `GET` + `DEL` and **reproduce the race** with a
   TTL expiring between them.
5. Simulate a GC pause with `-XX:+UseSerialGC` and a large allocation, or just `SIGSTOP` the process
   for 40 seconds. **Watch the lock expire under a live holder.**
6. Implement fencing tokens end to end: `INCR` for the token, a `fence` column, and
   `where fence < :token`. **Reproduce the paused-writer case and confirm the stale write is
   rejected.**
7. Switch to Redisson. Confirm the watchdog extends the lease during long work.
8. Implement the same protection with `pg_advisory_xact_lock` and compare complexity.
9. Take a job that currently uses a lock and **make it idempotent instead** (Day 178). Run it on
   three instances with no lock and confirm correctness.
10. Run a blocking `lock()` with no timeout under contention and **watch threads accumulate.**

## 🎙️ Articulation drill

**Three minutes, and treat it as the flagship distributed-systems answer: "Implement a distributed
lock."**

Build it wrong on purpose, out loud — `SETNX`, then the expiry gap, then the deleted-someone-else's-
lock case — fixing each and naming what the fix does and does not cover. Then state the fundamental
limit: a paused process cannot know it still holds the lock, and a JVM GC pause is the everyday
version of that. Position Redlock as availability rather than correctness, give fencing tokens as the
real answer, and connect them to optimistic locking. **Then finish with the senior move: ask what
happens if the work runs twice, because making it idempotent removes the problem instead of solving
it.**
