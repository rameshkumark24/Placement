# Day 210

**L-210** · MongoDB and the document model — when it fits, and when it is a mistake

**Time:** 3 hrs · **Mode:** NEW

# Part 1 — The model, and what it actually changes

```javascript
// ⭐ A document. One order, everything about it, in one place.
{
  _id: ObjectId("66bd..."),
  orderNumber: "ORD-8842",
  customer: { id: 1000, name: "Alice", email: "a@b.com" },   // ⭐ embedded
  items: [                                                    // ⭐ embedded array
    { sku: "P-42", name: "Widget", qty: 2, unitPrice: NumberDecimal("29.99") }
  ],
  total: NumberDecimal("59.98"),
  status: "PENDING",
  placedAt: ISODate("2026-08-14T10:23:45Z")
}
```

| Relational | MongoDB |
|---|---|
| table | collection |
| row | ⭐ document (BSON) |
| column | field |
| join | ⭐ **embedding, or `$lookup`** |
| schema enforced by DDL | ⭐ **schema by convention, or a validator** |

**⭐ The genuine advantage: one read gets the whole aggregate.** No join, no N+1 (Day 160), no
ORM impedance mismatch (Day 157). An order and its items arrive as one document, already shaped like
the object your code wants.

**⭐ The genuine cost: the same data may live in many documents, and nothing keeps the copies in
agreement.** If the customer's name is embedded in 40,000 orders and they change it, you either
update 40,000 documents or accept divergence — and Day 188's event-versus-entity distinction is what
tells you which is correct.

## ⭐ Types worth knowing immediately

```javascript
NumberDecimal("59.98")     // ⭐⭐ MONEY. Not `59.98`, which is a double (Day 106)
ISODate("2026-08-14...")   // ⭐ a real date type, stored as UTC
ObjectId("66bd...")        // ⭐ 12 bytes: timestamp + random + counter — roughly time-ordered
```

**⭐ A bare `59.98` in a document is an IEEE-754 double**, so Day 106's money rule applies with
force: `NumberDecimal` or store integer minor units. **This is one of the most common real MongoDB
data bugs**, because JavaScript and JSON make the wrong thing the default.

**⭐ `ObjectId` is roughly time-ordered**, like UUIDv7 (Day 158) — so it indexes well and encodes a
creation timestamp. It is also predictable enough that it should not be treated as an unguessable
secret (Day 119).

# Part 2 — ⭐ Schema flexibility, and the discipline it requires

**⭐ "Schemaless" is a description of the database, not a licence for the application.** Every reader
still needs to know the shape; the only question is whether that knowledge is written down and
enforced.

```javascript
// ⭐ Schema validation — use it. This is the Day 187 argument in MongoDB.
db.createCollection("orders", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["orderNumber", "status", "total", "placedAt"],
    properties: {
      orderNumber: { bsonType: "string" },
      status: { enum: ["PENDING","SHIPPED","DELIVERED","CANCELLED"] },   // ⭐
      total: { bsonType: "decimal", minimum: 0 },
      items: { bsonType: "array", minItems: 1 }
    }
  }},
  validationLevel: "strict",
  validationAction: "error"          // ⭐ not "warn"
})
```

**⭐ Day 187's argument transfers directly: the application is not the only writer.** A migration
script, an admin in the shell, an ETL job and the previous version of your code during a rolling
deploy all bypass application validation. **A validator is the only rule they all obey.**

**⭐ And what MongoDB still cannot give you** — the list that matters when choosing:

| Missing | Consequence |
|---|---|
| ⭐ **Foreign keys** | ⭐ a reference to a deleted document is not prevented or detected |
| ⭐ **Cross-document constraints** | "at most one primary address" cannot be enforced |
| Cross-collection uniqueness | only per-collection unique indexes |
| ⭐ **Cascading behaviour** | orphans are your problem |

**⭐ The foreign-key gap is the one to state in an interview.** Referential integrity moves from the
database to the application, which means every writer must implement it correctly, forever — and
Day 187's argument says that is exactly the assumption that fails.

## ⭐ Schema evolution — the honest version

**⭐ The claimed advantage — "no migrations" — is half true.** Adding a field needs no DDL, which is
genuinely convenient. But:

```javascript
// ⭐ Every reader must now handle BOTH shapes, forever
const email = doc.contact?.email ?? doc.email;
```

**⭐ You have not removed the migration; you have moved it into every read path**, where it is
invisible, untested and permanent. Documents written in 2023 still have the 2023 shape.

**⭐ The disciplined approach is a schema version field:**

```javascript
{ _id: ..., schemaVersion: 3, ... }
```

Then migrate lazily on read (upgrading and rewriting), or in a background job — and **you can
actually tell when the old shape is gone.** Without a version field you never know, and the
compatibility branches live forever.

# Part 3 — ⭐⭐ When MongoDB fits, and when it does not

## ⭐ Genuinely good fits

| Case | Why |
|---|---|
| ⭐ **Documents with genuinely variable shape** | product catalogues, CMS content, form submissions |
| ⭐ **Aggregates read and written as a whole** | ⭐ an order with items; one read, one write |
| ⭐ **High write volume with horizontal scale** | ⭐ sharding is built in (Day 213) |
| **Rapid early-stage iteration** | shape genuinely unknown |
| ⭐ **Geospatial and time-series** | strong first-class support |
| **Event/log storage** | append-heavy, schema-varying |

## ⭐⭐ The mistakes — and these are common

| Sign | What it means |
|---|---|
| ⭐ **Highly relational data** | ⭐ ⭐ many-to-many, deep joins — you will write `$lookup` everywhere and it is worse than SQL |
| ⭐ **You need transactions across many documents** | ⭐ available since 4.0, but expensive and constrained |
| ⭐ **Referential integrity matters** | no foreign keys — orphans are inevitable |
| **Complex ad-hoc reporting** | the aggregation pipeline is capable and far harder to write than SQL |
| ⭐ **"It's faster than SQL"** | ⭐ **usually not.** An indexed PostgreSQL lookup is comparably fast |
| ⭐ **"We don't know the schema yet"** | ⭐ `jsonb` gives you that inside PostgreSQL (Day 198) |

**⭐ The last two are the reasons most wrong choices are made**, and both deserve a direct answer:

- ⭐ **Speed:** MongoDB's advantage is *avoiding joins by embedding*, not raw operation speed. If you
  denormalize equivalently in PostgreSQL you get similar results — and if your data is relational,
  PostgreSQL's joins beat `$lookup` comfortably.
- ⭐ **Flexibility:** `jsonb` with a GIN index gives you schemaless columns *plus* transactions,
  foreign keys, constraints and joins on the structured parts. **The flexibility argument for
  MongoDB is much weaker than it was ten years ago**, and saying so demonstrates you have thought
  about it.

## ⭐ The framework — three questions

> **⭐ 1. Is your data naturally aggregate-shaped, read and written as a unit?**
> Yes → the document model helps. No → relational.
>
> **⭐ 2. Do you need cross-entity constraints and transactions as the normal case?**
> Yes → PostgreSQL. Occasionally → either.
>
> **⭐ 3. Will you exceed one machine's write capacity?**
> Yes → MongoDB's sharding is genuinely easier than PostgreSQL's. No → this is not a reason.

**⭐ Question 3 deserves scepticism.** A single well-tuned PostgreSQL instance handles far more than
most teams estimate, and "we might need to scale" is the most common premature justification. **Day
200's distinction applies: partitioning is not sharding, and most systems need neither.**

# Part 4 — From Java

```java
@Document(collection = "orders")
public class Order {
    @Id private String id;
    @Indexed(unique = true) private String orderNumber;
    private CustomerRef customer;              // ⭐ embedded
    private List<OrderItem> items;             // ⭐ embedded
    @Field(targetType = FieldType.DECIMAL128)  // ⭐⭐ NOT a double
    private BigDecimal total;
    private Instant placedAt;
    @Version private Long version;             // ⭐ Day 165's optimistic locking works here too
}
```

```java
public interface OrderRepository extends MongoRepository<Order, String> {
    List<Order> findByStatusAndPlacedAtAfter(String status, Instant after);   // ⭐ derived, as Day 163

    @Query("{ 'items.sku': ?0 }")               // ⭐ query inside an embedded array
    List<Order> findByItemSku(String sku);
}
```

**⭐ Spring Data MongoDB mirrors Spring Data JPA deliberately** — derived queries, `Pageable`,
`@Query`, projections — so Day 163's judgements transfer: extend `Repository<T,ID>` rather than
`MongoRepository` to avoid publishing `findAll()` and `deleteAll()`, always paginate, and prefer
projections for reads.

**⭐ Two Java-specific traps:**

1. ⭐ **`@Field(targetType = DECIMAL128)`** — without it a `BigDecimal` may be stored as a string or a
   double depending on version and configuration. **Verify what is actually in the database**, do not
   assume.
2. ⭐ **`_class` discriminator** — Spring Data writes a `_class` field into every document by default,
   which couples your stored data to your Java package names. **Rename a package and old documents
   fail to deserialize.** Configure a `MappingMongoConverter` with a null type mapper if other
   consumers read the collection.

**⭐ And Day 147's rule stands unchanged: never expose the document class from your API.** The
argument is identical — coupling, mass assignment, and the fact that a schema change becomes an API
change.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Choosing MongoDB for "flexibility" | ⭐ `jsonb` gives that with constraints and joins |
| ⭐ Choosing it for speed | an indexed relational lookup is comparably fast |
| ⭐ Using it for highly relational data | `$lookup` everywhere, worse than SQL |
| ⭐ No schema validator | ⭐ every non-application writer bypasses your rules |
| `validationAction: "warn"` | a rule nobody enforces |
| ⭐ Doubles for money | Day 106; use `NumberDecimal` |
| No schema version field | compatibility branches live forever |
| Handling old shapes in read paths indefinitely | the migration you avoided, now invisible |
| ⭐ Assuming referential integrity | there are no foreign keys |
| Treating `ObjectId` as unguessable | it is roughly sequential |
| ⭐ `_class` written into shared collections | a package rename breaks deserialization |
| `BigDecimal` without `DECIMAL128` | stored as a string or a double |
| Exposing documents from the API | Day 147 |

## Interview questions

**Q: When would you choose MongoDB over PostgreSQL?**
Three questions. Is the data naturally aggregate-shaped — read and written as a whole — because that
is where embedding genuinely wins. Do I need cross-entity constraints and transactions as the normal
case, because then PostgreSQL. And will I exceed one machine's write capacity, because MongoDB's
sharding is genuinely easier. If the honest answers are "not really", PostgreSQL with `jsonb` gives
me the flexibility plus foreign keys, constraints and joins.

**Q: What does MongoDB not give you?**
Foreign keys, so referential integrity moves into the application and every writer must implement it
correctly forever. Cross-document constraints — "at most one primary address" is unenforceable.
Cascading behaviour, so orphans are your problem. And multi-document transactions exist but are
expensive enough that designing around them is the norm.

**Q: Is "schemaless" an advantage?**
It removes DDL for adding a field, which is convenient. But the schema does not disappear — it moves
into every read path, where old documents keep their old shape forever and compatibility branches
become permanent and untested. I use a schema validator and a version field, so the flexibility is
deliberate and I can tell when a migration is actually finished.

**Q: Is MongoDB faster than PostgreSQL?**
Usually not in raw operation terms. Its advantage is avoiding joins by embedding the aggregate — one
read instead of several. If the data is relational, PostgreSQL's join execution beats `$lookup`
comfortably, and an indexed primary-key lookup is fast in both.

1. Model an order two ways: normalised in PostgreSQL and embedded in MongoDB. Load 1M orders into

   honestly.

## 🎙️ Articulation drill

Two minutes: **"MongoDB or PostgreSQL?"**

Ask the three questions out loud and answer them for a concrete system, rather than listing features.
Be specific about where the document model genuinely wins — an aggregate read and written as a whole,
in one operation, with no impedance mismatch. Then be equally specific about what you gave up: no
foreign keys, so referential integrity is now every writer's responsibility forever. Close by
disarming the two weak arguments: MongoDB is not generally faster, and `jsonb` gives you schema
flexibility without giving up constraints, joins or transactions.
