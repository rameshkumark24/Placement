# Day 314

**L-314** · Rate limiter — four algorithms, one interface, and the boundary burst

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ There is exactly one question in this problem, and it is: what is wrong with a fixed window?**
>
> Everything else — the interface, the per-key map, the thread safety, the distributed version — is
> ordinary design. **The boundary burst is the discriminator, and it is a picture you should be able
> to draw in fifteen seconds.**

---

# Part 1 — ⭐⭐ The four algorithms

## ⭐ 1. Fixed window — and why it fails

```java
// ⭐ 100 requests per minute
long window = clock.instant().getEpochSecond() / 60;
int count = counts.merge(key + ":" + window, 1, Integer::sum);
return count <= 100;
```

```
⭐ THE BOUNDARY BURST:

     minute 1                 │  minute 2
   ──────────────────────────►│◄──────────────────────────
                    100 reqs  │  100 reqs
                    at 11:59.9│  at 12:00.1
                              │
   ⭐ 200 requests in 0.2 seconds — both windows are "within limit".
   ⭐ The effective limit is 2× the configured one.
```

| ⭐ Pro | ⭐ Con |
|---|---|
| ⭐ trivially cheap — one counter per key per window | ⭐⭐ **2× burst at the boundary** |
| memory O(keys) | ⭐ unfair: a user resets at a wall-clock instant, not relative to their own usage |

## ⭐ 2. Sliding window log — correct and expensive

```java
Deque<Instant> timestamps = log.get(key);
Instant cutoff = now.minus(window);
while (!timestamps.isEmpty() && timestamps.peekFirst().isBefore(cutoff)) timestamps.pollFirst();
if (timestamps.size() >= limit) return false;
timestamps.addLast(now);
```

| ⭐ Pro | ⭐ Con |
|---|---|
| ⭐ **exactly correct — no burst** | ⭐⭐ **O(limit) memory PER KEY** — 10k rps × 60 s = 600k timestamps |
| supports any window | ⭐ the reason it is rarely used at scale |

## ⭐ 3. Sliding window counter — the practical compromise

```java
// ⭐ Weight the previous window by how much of it still overlaps
double weight = 1.0 - (secondsIntoCurrentWindow / (double) windowSeconds);
double estimate = previousWindowCount * weight + currentWindowCount;
return estimate < limit;
```

**⭐ Two counters per key, no burst in practice, and the error is bounded and small.** It assumes
requests were evenly distributed in the previous window — **say that assumption out loud**; it is the
whole trade.

## ⭐⭐ 4. Token bucket — the default, and the one to implement

```java
public final class TokenBucket {
    private final long capacity;              // ⭐ burst size
    private final double refillPerSecond;     // ⭐ sustained rate
    private double tokens;
    private Instant lastRefill;

    synchronized boolean tryConsume(int permits) {
        refill();                                                     // ⭐ LAZY — no background thread
        if (tokens < permits) return false;
        tokens -= permits;
        return true;
    }

    private void refill() {
        Instant now = clock.instant();
        double elapsed = Duration.between(lastRefill, now).toNanos() / 1_000_000_000.0;
        tokens = Math.min(capacity, tokens + elapsed * refillPerSecond);   // ⭐ CLAMP to capacity
        lastRefill = now;
    }
}
```

| ⭐ Why it wins | |
|---|---|
| ⭐ **Two decoupled dials** | ⭐ **capacity = allowed burst, refill rate = sustained rate** |
| ⭐ **Lazy refill** | ⭐ **no timer thread, no scheduled task — the key implementation trick** |
| O(1) time, O(1) memory per key | ⭐ two doubles and an instant |
| ⭐ Bursts are allowed *deliberately* | ⭐ which matches how APIs are actually used |

> **⭐ Say the lazy-refill line explicitly: "I don't need a background thread — I compute how many
> tokens should have arrived since the last call."** Candidates who schedule a refill task per key
> have built something that does not scale to a million keys, and they usually do not notice.

**⭐ Leaky bucket** is the fifth: a queue drained at a fixed rate. **It smooths output** rather than
limiting input, so it is right for a downstream that needs a steady feed, and it adds latency instead
of rejecting. **Mention it in one line and move on.**

| Choose | ⭐ When |
|---|---|
| ⭐ **Token bucket** | ⭐ **default — API rate limits, per-user quotas** |
| Sliding window counter | strict "no more than N per minute" billing semantics |
| Sliding window log | small limits where exactness matters (login attempts) |
| Leaky bucket | ⭐ protecting a fragile downstream at a fixed rate |
| Fixed window | ⭐ **only when 2× burst is genuinely acceptable** |

# Part 2 — ⭐ The design around it

```java
public interface RateLimiter {
    Decision tryAcquire(String key, int permits);
}

public record Decision(boolean allowed, int remaining, Duration retryAfter) { }
```

**⭐ Returning a `Decision` rather than a boolean is a small move that scores**, because it gives the
caller what it needs for the HTTP response (Day 104):

```
⭐ 429 Too Many Requests
⭐ Retry-After: 12
⭐ X-RateLimit-Limit: 100   X-RateLimit-Remaining: 0   X-RateLimit-Reset: 1699999999
```

## ⭐ Rules as data (Day 290, again)

```java
public record LimitRule(String name, KeySelector selector, long capacity,
                        double refillPerSecond, int priority) { }
```

| ⭐ Requirement | ⭐ Design |
|---|---|
| ⭐ Different limits per plan/endpoint | ⭐ **a rule list, evaluated in priority order** |
| ⭐ **Multiple limits at once** (10/s AND 1000/hr) | ⭐ **ALL must pass — and consume from all only if all pass** |
| Changing a limit without a deploy | rules from config, hot-reloaded |
| Key composition | ⭐ `user:123`, `ip:1.2.3.4`, `user:123:endpoint:/search` |

⚠️ **The multi-limit trap: if you consume a token from the per-second bucket and then the per-hour
bucket rejects, you have silently spent a token.** **Check all, then consume all** — or compensate.
**Volunteering this is a strong detail.**

## ⭐⭐ The per-key map that grows forever

```java
private final Map<String, TokenBucket> buckets = new ConcurrentHashMap<>();
```

> **⭐ This is a memory leak, and it is the most commonly missed flaw in the whole problem.** One
> entry per user, per IP, per endpoint combination — **including every IP that hit you once.**

| ⭐ Fix | Note |
|---|---|
| ⭐ **A bounded LRU** (Day 313) | ⭐ **evicting a full bucket is *safe* — it just resets to full capacity** |
| ⭐ Expire buckets idle for > refill time | once a bucket is full, it is indistinguishable from a new one |
| Cap total keys, fail open past it | a deliberate policy |

**⭐ The reason eviction is safe is worth saying:** a bucket that has refilled to capacity carries no
information. **Evicting it loses nothing.** That is a genuinely nice property of token bucket, and it
is not true of the sliding window log.

# Part 3 — ⭐ Concurrency and distribution

**⭐ In-process:** the bucket's `tokens` and `lastRefill` must change together, so **`synchronized` on
the bucket is correct** — and it is per-key, so different users never contend. **A CAS loop over an
immutable `(tokens, lastRefill)` pair is the lock-free version; mention it, do not necessarily write
it.**

```java
buckets.computeIfAbsent(key, k -> new TokenBucket(rule));   // ⭐ creation is atomic
```

⚠️ **Do not call `tryConsume` inside `computeIfAbsent`** — Day 310's bin-lock rule. Get the bucket,
then consume.

## ⭐ Distributed — and the honest answer

**⭐ Three instances each allowing 100/min means the real limit is 300/min. Say this before you are
asked.**

| Option | ⭐ Trade |
|---|---|
| ⭐ **Divide the limit by N** | ⭐ simple; **wrong under uneven load balancing**, and breaks on scale-up |
| ⭐⭐ **Central Redis, atomic Lua** (Day 208) | ⭐⭐ **correct; adds a network hop to every request** |
| ⭐ **Local buckets + async reconciliation** | ⭐ approximate, fast — **usually the right production answer** |
| Sticky routing by key | correct if the balancer cooperates; fragile |

```lua
-- ⭐ Day 208's script: read, refill, decide, write — atomically, one round trip
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens')) or capacity
...
redis.call('HSET', KEYS[1], 'tokens', tokens - 1, 'ts', now)
```

**⭐ And the failure question, which is a values question:**

> **⭐ "If Redis is down, do you fail open or fail closed?"** — **Open for general API limits**
> (a limiter outage should not become a site outage). **Closed for anything protecting money or
> login attempts.** **The right answer is "it depends on what the limit protects", and you must say
> which for your design.** That is Day 206's fail-open/fail-closed question, arriving in an LLD
> round.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Fixed window without naming the burst | ⭐ **the one thing being tested** |
| ⭐ A background refill thread per key | ⭐ does not scale past a few thousand keys |
| Not clamping tokens to capacity | unlimited accumulation → an unlimited burst |
| ⭐ **An unbounded per-key map** | ⭐⭐ **a memory leak, and the most-missed flaw** |
| ⭐ Consuming before all limits pass | ⭐ tokens silently spent on rejected requests |
| Returning a bare boolean | no `Retry-After`, no headers |
| ⭐ `tryConsume` inside `computeIfAbsent` | a bin lock held across the decision |
| ⭐ Ignoring multi-instance | ⭐ **3 instances = 3× the limit** |
| ⭐ No fail-open/closed decision | the limiter becomes the outage |
| `Instant.now()` inside the bucket | untestable — every test needs `Thread.sleep` |

## Interview questions

**Q: What is wrong with a fixed window counter?**
The boundary burst. A hundred requests at 11:59.9 and a hundred at 12:00.1 are both within limit, so
the effective rate is twice the configured one over a fraction of a second. It is also unfair — the
window resets on wall-clock time rather than relative to a user's own usage.

**Q: Which algorithm would you pick and why?**
Token bucket, by default. It gives two independent dials — capacity is the burst you tolerate, refill
rate is the sustained rate — and it needs no background thread, because I compute the tokens that
should have arrived since the last call. Sliding window counter if the semantics must be strictly N
per minute; sliding window log only for small limits like login attempts, since it costs one
timestamp per request per key.

**Q: What is the flaw in a map of buckets keyed by user?**
It grows without bound — every IP that ever hit you keeps an entry. I bound it with an LRU, and
eviction is safe here precisely because a bucket that has refilled to capacity carries no
information, so a returning user simply starts full. That is not true of a sliding window log, where
eviction loses history.

**Q: How do you make it work across three instances?**
Naively you do not — three instances each allowing a hundred a minute allows three hundred. Dividing
the limit by instance count breaks under uneven balancing and on scale-up. The correct version is a
central Redis counter updated by an atomic Lua script, at the cost of a network hop per request. In
practice I would often run local buckets with asynchronous reconciliation and accept approximate
enforcement, because rate limits are a policy, not an invariant.

**Q: Redis is down. Allow or reject?**
Depends on what the limit protects. For general API throttling, fail open — a limiter outage should
not become a site outage. For login attempts, payment endpoints or anything where excess is a
security or money problem, fail closed. I would make it configurable per rule and set the default
per what that rule guards.
