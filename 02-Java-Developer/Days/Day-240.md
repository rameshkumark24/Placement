# Day 240 🩹

**J-240** · 🩹 **Error boundaries and empty states** — ⭐⭐ the white screen, and what boundaries miss

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: an uncaught render error unmounts your entire application and leaves a
> blank white page — React does this deliberately, because a half-rendered UI can show wrong data — so
> a boundary is not a nicety, it is the difference between one broken widget and a dead app.**
>
> Today: the white screen, ⭐⭐ the four things boundaries do **not** catch, ⭐ placement, and empty
> states done properly.

---

# Part 1 — The white screen

```jsx
function OrderTotal({ order }) {
  return <p>{order.total.toFixed(2)}</p>;   // ⭐⭐ order.total is null
}                                            //    ⇒ TypeError ⇒ WHOLE APP GONE
```

```
⭐⭐ WHY REACT UNMOUNTS EVERYTHING

⭐   ⭐ A component that threw is in an UNKNOWN state. React's choice:
⭐     show NOTHING rather than something POSSIBLY WRONG.
⭐   ⇒ ⭐⭐ THE BLAST RADIUS IS THE OPPOSITE OF WHAT YOU ARE USED TO.
⭐     ⭐ A NullPointerException in one @RestController method returns
⭐       a 500 for THAT REQUEST; every other endpoint keeps serving.
⭐     ⭐⭐ HERE, ONE NULL FIELD IN ONE COMPONENT TAKES DOWN THE
⭐       WHOLE PAGE — THERE IS NO PER-REQUEST ISOLATION.
⭐   ⇒ ⭐ SO THE BOUNDARY IS HOW YOU CREATE THAT ISOLATION YOURSELF.
```

```jsx
class ErrorBoundary extends React.Component {   // ⭐ must be a class, still
  state = { error: null };
  static getDerivedStateFromError(error) { return { error }; }
  componentDidCatch(error, info) {
    reportError(error, { componentStack: info.componentStack });  // ⭐ Day 279
  }
  render() {
    if (this.state.error) {
      return this.props.fallback ?? <ErrorPanel
        onRetry={() => this.setState({ error: null })} />;  // ⭐⭐ RETRY
    }
    return this.props.children;
  }
}
```

> ⭐ **The retry matters.** A boundary with no way back forces a full page reload, losing everything
> the user typed.

# Part 2 — ⭐⭐ What boundaries do NOT catch

```
⭐⭐ THIS IS THE PART PEOPLE GET WRONG IN INTERVIEWS.

⭐   ❌ ① EVENT HANDLERS
⭐        onClick={() => { throw new Error() }}  ⇒ ⭐⭐ NOT CAUGHT.
⭐   ❌ ② ASYNC CODE
⭐        ⭐⭐ ANYTHING AFTER AN await ⇒ NOT CAUGHT.
⭐        ⭐ This is most of your real error surface.
⭐   ❌ ③ SERVER-SIDE RENDERING errors
⭐   ❌ ④ ⭐⭐ ERRORS THROWN BY THE BOUNDARY'S **OWN** FALLBACK
⭐        ⇒ ⭐ propagates UP; with nothing above, white screen anyway.
⭐          KEEP FALLBACKS TRIVIAL.

⭐   ⇒ ⭐⭐ A BOUNDARY CATCHES **RENDER** ERRORS. THAT IS ALL.
⭐     ⭐ IT IS NOT @ControllerAdvice. @ExceptionHandler catches
⭐       anything thrown in the request thread; a boundary catches
⭐       one lifecycle phase.
⭐   ⇒ so you ALSO need: the Day 216 unhandledrejection listener,
⭐     window.onerror, and try/catch in handlers.
```

| ⭐ Error source | ⭐ Caught by |
|---|---|
| Render, lifecycle, constructor | ⭐⭐ Error boundary |
| Event handler | `try/catch` in the handler |
| Promise rejection | ⭐⭐ `unhandledrejection` listener |
| A query's fetch | ⭐ The query library's `isError` — **handled, not thrown** |
| Everything else | `window.onerror` |

# Part 3 — Where to put them

```
⭐⭐ THREE LEVELS. NOT ONE, NOT FIFTY.

⭐   ① ⭐ ROOT — the last resort. ⭐⭐ Its ONLY job is to never be blank.
⭐   ② ⭐⭐ PER ROUTE — a broken /reports must not kill /orders.
⭐        ⭐ Nested layouts (Day 233) give you this for free.
⭐   ③ ⭐ PER INDEPENDENT WIDGET — a dashboard where the revenue
⭐        chart fails but five other panels still render.

⭐   ⇒ ⭐⭐ THE QUESTION IS ALWAYS: "WHAT IS THE SMALLEST THING THAT
⭐     CAN FAIL WITHOUT MAKING THE REST USELESS?"
⭐     ⇒ ⭐ That is bulkheading, from Stage 12.
```

| ⭐ Fallback should say | Not |
|---|---|
| ⭐⭐ What failed, in user terms | "Error" |
| ⭐ What they can do — **Retry**, go back | A dead end |
| ⭐ A reference id for support | ⭐⭐ A stack trace (leaks internals, helps nobody) |

# Part 4 — ⭐⭐ The four states, finally

```
⭐⭐ EVERY DATA-DRIVEN SCREEN. NO EXCEPTIONS.

⭐ ① LOADING ⇒ ⭐ a SKELETON shaped like the content.
⭐    ⭐⭐ NOT a centred spinner replaced by content of a different
⭐      size — that is layout shift, and it is measured (Day 241).
⭐    ⭐ Do not show it for <200 ms — a flash is worse than a wait.

⭐ ② ERROR ⇒ ⭐⭐ WHAT HAPPENED + WHAT TO DO. Branch on status:
⭐      401 ⇒ sign in again      403 ⇒ "you don't have access"
⭐      404 ⇒ "not found" + back  429 ⇒ "too many requests"
⭐      5xx ⇒ "our side — retry"  offline ⇒ "you appear to be offline"

⭐ ③ ⭐⭐ EMPTY ⇒ THE MOST-MISSED STATE, AND THE MOST NOTICED.
⭐    ⭐ SPLIT IT IN TWO:
⭐      · ⭐⭐ NEVER HAD ANY ⇒ explain + THE ACTION THAT CREATES ONE
⭐      · ⭐⭐ FILTERED TO ZERO ⇒ "No orders match 'xyz'"
⭐        + [Clear filters]  ⇒ ⭐ SHOWING "no orders yet" TO SOMEONE
⭐        WITH 500 ORDERS AND A BAD FILTER IS A REAL BUG.

⭐ ④ SUCCESS ⇒ the one everybody builds first.
```

> ⭐ **Two more that separate a real app from a demo:** *partial* success (Day 216's `allSettled`) and
> *stale* (showing cached data while refetching, with a subtle indicator rather than a spinner that
> hides working content).

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "what happens when a component throws?"**

State the behaviour and contrast the blast radius. **The whole app unmounts and you get a blank white
page. React does that deliberately — a component that threw is in an unknown state, and showing nothing
is safer than showing something wrong. But the blast radius is the opposite of what I'm used to: a null
pointer in one controller method returns a 500 for that request and every other endpoint keeps serving.
Here one null field takes down the entire page, because there's no per-request isolation. A boundary is
how I create that isolation myself.**

Then the limits, where most answers stop too early. **A boundary catches render errors and nothing
else. Not event handlers, not anything after an await, not errors thrown by its own fallback. It is not
`@ControllerAdvice` — `@ExceptionHandler` catches anything thrown in the request thread, a boundary
catches one lifecycle phase. Async is most of my real error surface, so I also need an
unhandledrejection listener and try/catch in handlers.**

Then placement. **Three levels: root so it's never blank, per route so a broken reports page doesn't
kill orders, and per independent widget. The question is what the smallest thing is that can fail
without making the rest useless — bulkheading.**

Close on the state everyone forgets. **Every screen gets four states, and empty is the one that's missed
and the one reviewers notice. It has to be split in two: never had any, which needs the action that
creates one, versus filtered to zero, which needs a way to clear the filter. Showing "no orders yet" to
someone with five hundred orders and a bad filter is a real bug.**
