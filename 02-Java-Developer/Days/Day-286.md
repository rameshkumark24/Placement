# Day 286 🏗️

**P-286** · Load testing and breaking it on purpose

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Today produces the single most valuable artefact of the whole project: a number, a change, and
> a better number.**
>
> Day 248's defence question — *what breaks first at 100× the traffic?* — has been a hypothesis until
> now. **Today you find out**, and "I load tested it, the connection pool saturated at 340 rps, I
> found an unindexed query holding connections, and after fixing it we reached 900" is worth more
> than any feature you could add instead.

---

# Part 1 — ⭐ Load test properly

```
⭐ k6 or Gatling, against the DEPLOYED instance — ⭐ never your laptop
```

**⭐ Four scenarios, in this order:**

| # | Scenario | ⭐ Question it answers |
|---|---|---|
| ⭐ 1 | **Baseline** — expected load, 10 min | does it meet the Day 249 SLO? |
| ⭐ 2 | **Ramp** — increase until something breaks | ⭐ **where is the knee, and what saturated?** |
| ⭐ 3 | **Soak** — expected load, 1 hour+ | ⭐ **memory leaks, connection leaks, unbounded growth** |
| ⭐ 4 | **Spike** — 10× instantly | recovery behaviour, and whether it recovers at all |

**⭐ Scenario 3 is the one people skip and it finds the most interesting bugs.** A leak is invisible
in a ten-minute test: an emitter registry that never shrinks (Day 268), a cache with no TTL
(Day 266), a `ThreadLocal` never cleared (Day 265), an outbox table that only grows (Day 263). **Run
it for an hour and watch the heap and the connection count.**

## ⭐ Make the load realistic

```
⭐ 1. ⭐ REALISTIC MIX — 80% reads, 20% writes, not 100% of one endpoint
⭐ 2. ⭐ REALISTIC DATA — Day 255's skewed dataset, not 20 rows
⭐ 3. ⭐ REALISTIC SKEW — some users have thousands of records, most have three
⭐ 4. ⭐ THINK TIME — real users pause; back-to-back requests are not real load
⭐ 5. ⭐ Real authentication — ⭐ token issuance and validation is part of the cost
```

**⭐ Point 3 matters most.** Uniform data hides the hot-key problem (Day 206), the deep-pagination
problem (Day 152) and the large-collection N+1 (Day 160). **The user with 5,000 bookings is where
your endpoints break, and a uniform test never generates one.**

**⭐ Point 5 is commonly omitted**: hashing is deliberately slow (Day 171), so a login-heavy load test
saturates CPU at a rate that a token-reuse test never reveals.

## ⭐ Watch the right things during the run

```
⭐ p50 / p95 / p99 / error rate            ← ⭐ p99, not average — averages hide everything
⭐ hikaricp_connections_pending             ← ⭐⭐ usually the first to move
⭐ JVM heap and GC pause time · Tomcat busy threads
⭐ CPU throttling (Day 284) · Redis hit ratio and evictions
⭐ Database: pg_stat_statements, ⭐ locks, ⭐ connections
```

**⭐ Record the knee point precisely**: the rps at which p99 leaves the SLO, and **which metric moved
first.** That metric is your bottleneck.

# Part 2 — ⭐ The bottleneck, found and fixed

**⭐ The findings, in order of how often they are the answer:**

| ⭐ Likely bottleneck | ⭐ Signal | Day |
|---|---|---|
| ⭐ **The connection pool** | ⭐ `connections_pending` > 0 | 156 |
| ⭐ **A slow query holding connections** | ⭐ `pg_stat_statements` by **total** time | 202 |
| ⭐ **An N+1 that survived** | ⭐ query count per request climbing with data | 160 |
| **Tomcat threads** | busy threads at max, low CPU | 145 |
| ⭐ **An external call with no timeout** | threads parked | 154 |
| ⭐ **A hot cache key** | one key dominating Redis | 206 |
| Serialization / large payloads | CPU high, mostly in Jackson | 150 |
| ⭐ **A single-instance job** | one instance's CPU pinned | 264 |

**⭐ `connections_pending` is the most common answer**, and it is the one whose diagnosis is
counter-intuitive: **the fix is usually not a bigger pool** (Day 156 — bigger pools reduce
throughput). **It is finding the query holding connections too long.**

## ⭐ The workflow — one change at a time

```
⭐ 1. Find the knee and the first metric to move
⭐ 2. ⭐ ONE hypothesis                                   (Day 099, Day 193)
⭐ 3. ⭐ ONE change
⭐ 4. ⭐ RE-RUN THE SAME TEST
⭐ 5. ⭐ Record: before → after, with the metric that moved
⭐ 6. Repeat until the SLO holds at target load
```

**⭐ Step 5 is the deliverable.** A table in your README:

```markdown
| Change | ⭐ Before | ⭐ After |
|---|---|---|
| ⭐ Added index on bookings(room_id, starts_at) | ⭐ 340 rps, p99 2.1s | ⭐ 780 rps, p99 210ms |
| ⭐ Fixed N+1 in the list endpoint (projection)  | ⭐ 780 rps | ⭐ 1,100 rps |
| ⭐ Raised Hikari 10 → 15 after fixing the query  | ⭐ 1,100 rps | ⭐ 1,180 rps |
```

**⭐ Note the ordering in that table, because it is the lesson**: the pool increase came *last* and
gave the smallest gain. **Raising the pool first would have looked like a fix and hidden the real
problem** — which is exactly Day 197's warning about using a pooler to mask slow queries.

# Part 3 — ⭐⭐ Break it on purpose

> **⭐⭐ Chaos engineering at project scale: you are not testing whether it fails. You are testing
> whether you notice, and whether it recovers.**

**⭐ Run each of these against the deployed instance while a load test runs**, and record two numbers:
**time to detect** and **time to recover**.

| # | Break | ⭐ Expected | Detect | Recover |
|---|---|---|---|---|
| ⭐ 1 | **Kill one instance** | ⭐ traffic shifts, no errors | | |
| ⭐ 2 | **Stop the database** | ⭐ readiness down, ⭐ **liveness UP, no crash loop** | ⭐ alert | |
| ⭐ 3 | **Stop Redis** | ⭐ **degraded, not broken** | ⭐ alert | |
| ⭐ 4 | **Delay an external API by 30 s** | ⭐ **timeout fires, circuit opens** | ⭐ alert | |
| ⭐ 5 | **Fill the disk** | ⭐ graceful failure, not corruption | ⭐ alert | |
| ⭐ 6 | **Stop the outbox poller** | events queue | ⭐ **lag-age alert** | |
| ⭐ 7 | **Stop a scheduled job** | ⭐ **nothing visible** | ⭐⭐ **non-execution alert** | |
| ⭐ 8 | **`kill -9` mid-request** | in-flight lost; ⭐ **no data corruption** | | |
| ⭐ 9 | **Saturate the connection pool** | ⭐ fast failures, not a hang | ⭐ alert | |
| ⭐ 10 | **Deploy during peak load** | ⭐ **zero dropped requests** | | ⭐ pre-stop delay |

**⭐ Number 2 is the one that has caused real outages** (Day 128): if a dependency check is in the
liveness probe, a database blip crash-loops every pod. **Verify it.**

**⭐ Number 7 is the one that exposes the gap.** A stopped job produces no error, no log and no
complaint for days — **if your detection time is "never", write the alert now** (Day 264).

**⭐ Number 10 is the deploy-safety proof.** Without Day 265's pre-stop delay you will see dropped
requests, and it will be a small enough number that you might not have noticed without a load test
running.

## ⭐ Then write the postmortem

**⭐ Pick the most interesting failure and write it up properly** (Day 285's format). **"I broke it
deliberately, here is what I learned, here is what I changed" is a genuinely strong artefact** — and
it is what turns "tell me about a time something broke" from an awkward question into a document.

# Part 4 — ⭐ Capacity, and the honest limits

## ⭐ Answer Day 248's question with numbers

> **⭐ "What breaks first at 100× traffic?"**

```
⭐ Now you can answer: "at ~1,200 rps the connection pool saturates, because the
⭐  availability query holds a connection for 40ms. At 100× current traffic I would need
⭐  a read replica for the availability endpoint and a cache on the room list — I have
⭐  measured both and they are in FUTURE.md."
```

**⭐ Compute the capacity per instance from the measurement**, then state what you would change at
each order of magnitude:

| Scale | ⭐ What changes |
|---|---|
| ⭐ **10×** | ⭐ more instances — ⭐ **but the connection pool is fleet-wide** (Day 156) |
| ⭐ **100×** | ⭐ read replicas, caching, ⭐ PgBouncer (Day 197) |
| ⭐ **1000×** | ⭐ partitioning (Day 200), a separate real-time service (Day 268), asynchronous writes |

**⭐ The 10× row contains the subtlety worth stating**: adding instances does not add database
capacity, and each new instance brings its own pool — **so scaling out without PgBouncer eventually
saturates PostgreSQL rather than helping.**

## ⭐ Cost per request

```
⭐ Monthly cost ÷ monthly requests = ⭐ cost per request
```

**⭐ Almost nobody has this number, and it reframes optimisation as economics.** It is also the answer
to "would you optimise this?" — **if a change saves 5 ms on an endpoint costing £0.00002 per request,
you now know whether it is worth an afternoon.**

## ⭐ Update the documents

```
⭐ README:       ⭐ the before/after performance table
⭐ FUTURE.md:    ⭐ what you would do at each scale, with the measurement behind it
⭐ KNOWN-GAPS:   ⭐ anything the load test revealed that you chose not to fix
⭐ postmortem:   ⭐ the most interesting failure
```

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Load testing your laptop | ⭐ the numbers mean nothing |
| ⭐ One endpoint at 100% | not a realistic mix |
| ⭐ Uniform test data | ⭐ hides hot keys, deep pagination, large-collection N+1 |
| No think time | not real load |
| ⭐ Skipping the soak test | ⭐ leaks are invisible in ten minutes |
| ⭐ Watching averages | p99 is where users live |
| ⭐ **Raising the pool first** | ⭐ looks like a fix; hides the real problem |
| Changing several things at once | you learn nothing |
| ⭐ Not re-running the same test | before/after is not comparable |
| ⭐ **Never breaking it deliberately** | ⭐ recovery behaviour is a hope |
| ⭐ Not recording detection time | you do not know if your alerts work |
| Not deploying under load | dropped requests go unnoticed |
| ⭐ No capacity answer | Day 248's question is still a guess |

## 🎤 Defence questions

1. **⭐ What is your throughput, and what saturated first?**
2. **⭐ Show me a performance improvement with numbers.**
3. **⭐ Why didn't you just increase the connection pool?**
4. **⭐ What did the soak test find?**
5. **⭐ What happens when the database goes away — and how long until you know?**
6. **⭐ What would you change at 100× traffic?**
7. **⭐ Can you deploy during peak traffic without dropping requests?** (⭐ you have tried)
8. **⭐ What does one request cost you?**
