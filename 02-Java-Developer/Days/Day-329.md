# Day 329 ⭐

**L-329** · ⭐ Sharding — the key, the hotspot, and the resharding you cannot afford

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Sharding is the only way to scale writes, and it is the least reversible decision in system
> design.**
>
> Day 200 partitioned inside one PostgreSQL instance and Day 213 chose a MongoDB shard key. Today
> generalises both — **and spends as much time on why not to shard, and on the pre-splitting trick
> that makes resharding survivable, as on the mechanics.**

---

# Part 1 — ⭐ When, and the ladder before it

| ⭐ Legitimate reason | ⭐ Note |
|---|---|
| ⭐ **Write throughput exceeds one leader** | ⭐ the only reason that cannot be solved another way (Day 328) |
| ⭐ **Data exceeds one machine's storage** | ⭐ or its working set exceeds RAM — often the real trigger |
| ⭐ Blast radius | one shard down ≠ everything down |
| ⭐ Regulatory locality | EU data in the EU — a form of geographic sharding |

| ⭐ NOT a reason | ⭐ Do instead |
|---|---|
| ⭐ "Reads are slow" | ⭐ **index, cache, add replicas** — Day 324's ladder |
| "The table is big" | ⭐ **partition inside one instance** (Day 200) — most of the benefit, none of the cost |
| "We might need it later" | ⭐ **you will not choose the right key before you understand the workload** |

> **⭐ The sentence that frames the whole day: "sharding is the last step on the ladder because
> everything above it is reversible and sharding is not."** Adding an index, a cache or a replica can
> be undone in an afternoon. **Un-sharding is a migration project.**

**⭐ And say the cost list before the mechanics — it is what makes the answer credible:**

| ⭐ You give up | |
|---|---|
| ⭐ **Cross-shard joins** | ⭐ application-side joins, or denormalised data |
| ⭐ **Cross-shard transactions** | ⭐ **sagas** (Day 342) — no ACID across shards |
| ⭐ Global uniqueness and auto-increment ids | ⭐ UUIDs, or Snowflake-style ids |
| ⭐ **Global secondary indexes** | ⭐ **scatter-gather, or a separate index shard** |
| Simple aggregate queries | `COUNT(*)` becomes a fan-out |
| Operational simplicity | N times the backups, monitoring and migrations |

# Part 2 — ⭐⭐ The shard key

> **⭐ Three properties, and a key must have all three:**

| ⭐ Property | ⭐ Failure if missing |
|---|---|
| ⭐ **High cardinality** | ⭐ few distinct values → few shards → no scaling (`country` gives you ~200 buckets) |
| ⭐ **Even distribution** | ⭐ **hotspots — Part 3** |
| ⭐⭐ **Present in most queries** | ⭐⭐ **every query becomes scatter-gather — slower than not sharding** |

**⭐ The third one is the one candidates miss, and it is the most consequential.** A perfectly
distributed key that is absent from your queries means **every read hits every shard**, so you have
added machines and made reads slower.

## ⭐ The four strategies

| Strategy | ⭐ Range queries | ⭐ Distribution | ⭐ Rebalancing |
|---|---|---|---|
| ⭐ **Range** (`a–f`, `g–m`) | ⭐ **excellent** | ⭐⭐ **poor — sequential keys pile on one shard** | split a range |
| ⭐ **Hash** | ⭐ **destroyed** | ⭐ **excellent** | ⭐ consistent hashing (Day 326) |
| ⭐ **Directory / lookup table** | any | ⭐ **fully controllable** | ⭐⭐ **move any key at will — the most flexible** |
| Geographic | by region | uneven by population | move a region |

> **⭐ The directory approach is underrated and worth naming**: a lookup service maps key → shard, so
> you can move individual tenants, isolate a noisy one, or rebalance surgically. **The cost is a
> lookup on every request (cached) and a new critical dependency** — but for multi-tenant systems it
> is frequently the right answer, because tenants differ in size by orders of magnitude.

## ⭐ Compound keys — the usual real answer

```
⭐ tenant_id alone      → ⭐ one huge tenant is a hotspot
⭐ hash(order_id) alone → ⭐ every tenant query is scatter-gather
⭐⭐ (tenant_id, order_id) → distribution by tenant, ⭐ AND a tenant's queries hit one shard
```

**⭐ That is the same reasoning as Day 213's MongoDB compound key and Day 192's index-ordering rules
— distribute on the high-cardinality part, keep the query's leading predicate first.**

# Part 3 — ⭐⭐ Hotspots

## ⭐ The three causes

| Cause | ⭐ Example | ⭐ Fix |
|---|---|---|
| ⭐ **Monotonic key** | ⭐ timestamp, auto-increment, ULID | ⭐ **hash it, or prefix with something distributing** |
| ⭐⭐ **Celebrity / whale** | ⭐⭐ **one user with 100 M followers; one tenant with 90% of the data** | ⭐ **split the key; a dedicated shard; a different code path** |
| Skewed access | 1% of products get 90% of views | ⭐ cache in front (Day 326) — **not a sharding fix** |

```
⭐ MONOTONIC KEY, THE CLASSIC:
⭐   shard = f(created_at)
⭐   ⇒ ⭐⭐ EVERY new write goes to the last shard. You have bought machines
⭐      and concentrated the load onto one of them.
```

## ⭐ Salting — and its honest cost

```
⭐ key = hash(user_id + "#" + random(0..9))     ⭐ one hot key spread over 10 shards
⭐ ⇒ ⭐⭐ but every READ of that key must now query all 10 and merge.
```

**⭐ State the trade explicitly: salting converts a write hotspot into a read fan-out.** It is right
when writes dominate (event ingestion) and wrong when reads dominate. **A hybrid — salt only the keys
detected as hot — is the production answer, and it requires hot-key detection.**

> **⭐ The celebrity problem generalises: any system with a power-law distribution has a shard-key
> problem that the average case hides.** Day 323's estimate is what surfaces it — **the average user
> has 200 followers and the design is decided by the one with 100 million.**

# Part 4 — ⭐⭐ Resharding, and the trick that makes it survivable

## ⭐ Why it is painful

```
⭐ 4 shards → 8 shards, naively:
⭐   ✗ every key's destination changes
⭐   ✗ terabytes moved while serving live traffic
⭐   ✗ reads and writes must work throughout
⭐   ✗ ⭐ no atomic switchover — there is a window where a key lives in two places
```

## ⭐⭐ Pre-splitting — the answer

> **⭐ Create many more logical shards than physical nodes, up front. Map logical → physical. To
> rebalance, move whole logical shards between machines; the key mapping never changes.**

```
⭐ 1,024 logical shards (or Redis Cluster's 16,384 hash slots)
⭐ shard_id = hash(key) % 1024        ⭐ ← FIXED FOREVER. The key's shard never changes.

⭐ 4 machines  → 256 logical shards each
⭐ 8 machines  → 128 each             ⭐ move 128 logical shards. No rehashing. No key moves.
⭐ 16 machines → 64 each
```

| ⭐ Property | |
|---|---|
| ⭐⭐ **The key→shard function never changes** | ⭐⭐ **so resharding is a data move, not a remap** |
| ⭐ Move a *unit* at a time | ⭐ resumable, cancellable, throttleable |
| ⭐ **Hot logical shards can be isolated** | move just that one to its own machine |
| Cost | ⭐ pick the count high enough at the start — **1,024 or 4,096 is cheap; 8 is a mistake** |

**⭐ This is what Redis Cluster (16,384 slots), Vitess, Citus and Elasticsearch all do**, and naming
one of them makes the answer concrete.

## ⭐ The migration, live

```
⭐ 1. Dual write   — writes go to both old and new shard      ⭐ (the expand phase, Day 166)
⭐ 2. Backfill     — copy historical data, throttled
⭐ 3. Verify       — ⭐ compare row counts and checksums; do not skip this
⭐ 4. Switch reads — ⭐ per logical shard, gradually
⭐ 5. Stop dual writes and drop the old copy                  ⭐ (the contract phase)
```

⚠️ **Step 3 is the one people skip and the one that saves you.** Dual writes fail silently — a lost
write, a serialisation difference, a schema mismatch — **and discovering it after switching reads is
data loss.**

## ⭐ Secondary indexes

| | ⭐ Local (per shard) | ⭐ Global |
|---|---|---|
| Written | ⭐ with the row — same shard, atomic | ⭐ **a different shard — a distributed write** |
| Query by the indexed field | ⭐⭐ **scatter-gather across every shard** | ⭐ one lookup |
| Consistency | ⭐ strong | ⭐ **usually asynchronous — read-your-writes breaks** |
| Used by | Cassandra, Elasticsearch per-shard indexes | DynamoDB GSIs |

**⭐ "Query by email when sharded by user id" is the classic instance**: either scatter-gather across
all shards, or maintain an `email → user_id` lookup table (itself sharded by email) — **which is a
global index you built yourself, with the same eventual-consistency caveat.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Sharding before indexing, caching and replicas | ⭐ **enormous cost for a problem with a cheaper fix** |
| ⭐⭐ A key absent from most queries | ⭐⭐ **every read is scatter-gather — slower than one machine** |
| ⭐ Low-cardinality key | a handful of buckets; no scaling |
| ⭐ **Monotonic shard key** | ⭐⭐ **every new write on one shard** |
| ⭐ Ignoring the celebrity case | ⭐ the average hides the design problem |
| Salting a read-heavy key | you traded a write hotspot for a read fan-out |
| ⭐⭐ **Shard count equal to machine count** | ⭐⭐ **every capacity change is a full rehash** |
| Too few logical shards | you cannot grow past that number of machines |
| ⭐ Skipping verification during migration | ⭐ **silent data loss discovered after cutover** |
| Cross-shard transactions | there are none — you need a saga |
| ⭐ Expecting global uniqueness | auto-increment does not survive sharding |
| Global secondary indexes assumed consistent | they are asynchronous |

## Interview questions

**Q: When do you shard?**
When write throughput exceeds what one leader can take, or the data no longer fits one machine —
those are the two things nothing else solves. Before that I index, cache, add read replicas, scale
vertically, and partition inside a single instance, because all of those are reversible in an
afternoon and sharding is a migration project you cannot undo.

**Q: How do you choose the shard key?**
Three properties: high cardinality, even distribution, and present in most queries. The third is the
one people miss and it is the most damaging — a perfectly distributed key that your queries do not
carry means every read fans out to every shard, so you have added machines and made reads slower than
they were on one. In practice a compound key usually wins: distribute on tenant, order within it, so
a tenant's queries land on one shard.

**Q: What is the celebrity problem?**
A key whose distribution is power-law rather than uniform — one user with a hundred million
followers, or one tenant holding ninety percent of the data. The average hides it completely, which
is why the estimate matters: designing for the mean produces a system that falls over on the
outlier. Fixes are splitting that key across sub-keys, giving it a dedicated shard, or a different
code path entirely, and salting only helps if writes dominate, because it turns one write hotspot
into a read fan-out.

**Q: How do you go from four shards to eight without downtime?**
You do not rehash. You pre-split into far more logical shards than machines — a thousand or so, or
Redis Cluster's sixteen thousand slots — so `hash(key) % 1024` is fixed forever and resharding is
just moving logical shards between machines. Then it is dual writes, a throttled backfill,
verification by checksum, gradual read switching per logical shard, and finally dropping the old
copy. The verification step is the one people skip, and it is the one that prevents silent data loss.

**Q: You shard by user id and need to query by email.**
Either scatter-gather across every shard, which is fine for a rare admin query and unacceptable for
login, or maintain an email-to-user-id lookup sharded by email. That second one is a global secondary
index built by hand, and it carries the usual caveat: it is updated asynchronously, so it is
eventually consistent and read-your-writes can fail right after a signup.

## Mini task

1. **Write down the ladder for your flagship** and honestly mark which steps you have taken. **If you
   have not indexed and cached, you are not ready to discuss sharding.**
2. ⭐ Take a real table and **evaluate three candidate shard keys against the three properties.**
   For each, list which queries become scatter-gather.
3. ⭐ Simulate a **monotonic key**: shard by timestamp, generate a million writes, and **plot writes
   per shard.** Then hash the key and re-plot.
4. Build a **power-law dataset** (one key with 40% of traffic) and measure per-shard load. Apply
   salting and measure **both** write distribution and read fan-out.
5. ⭐⭐ Implement **1,024 logical shards** over 4 physical nodes. Move to 8 nodes by **relocating
   logical shards only**, and assert that no key's logical shard changed.
6. ⭐ Run a live migration: dual write, backfill, **verify with checksums**, switch reads. Then
   deliberately drop 0.1% of dual writes and **confirm verification catches it.**
7. Implement a **secondary lookup table** for a non-shard-key field. Measure both approaches, and
   **demonstrate the read-your-writes failure** immediately after a signup.
8. Attempt a transaction across two shards. **Write down exactly what you cannot guarantee.**

## 🎙️ Articulation drill

**Three minutes:** *"Our database can't keep up with writes. Walk me through sharding it."*

**⭐ Three markers.** You go up the ladder first and confirm the writes genuinely exceed one leader.
**You choose the key on all three properties and say out loud which queries become scatter-gather**
— naming what you are giving up. And you propose **pre-split logical shards**, so the follow-up
question ("what happens when you need to double again?") already has an answer.

**⭐ The candidate who names the cost before being asked is the one who has done it.** Sharding is
mostly a list of things you can no longer do, and knowing that list is the expertise.
