# Day 184

**L-184** · Testcontainers — testing against the real thing

**Time:** 3 hrs · **Mode:** NEW

> Day 183 ended on the claim that H2 tells you nothing about PostgreSQL. Today is the evidence and
> the alternative: **real dependencies, started in Docker, per test run, disposed automatically.**
>
> This is the single largest improvement most Java test suites can make — it turns a category of bug
> that currently reaches production into one that fails in CI.

---

# Part 1 — ⭐ The case against in-memory substitutes

| Behaviour | H2 | PostgreSQL |
|---|---|---|
| SQL dialect | its own, with compatibility modes | ⭐ real |
| `jsonb`, arrays, `ltree` | ❌ absent or emulated | ✅ |
| Partial and expression indexes | ❌ | ✅ ⭐ your uniqueness constraint may not exist |
| `FOR UPDATE SKIP LOCKED` | ⚠️ different | ⭐ Day 178 depends on it |
| Isolation and MVCC | different | ⭐ D-14/D-15's semantics |
| ⭐ **Row-level security** | ❌ **absent** | ⭐ **Day 176's only real control, untested** |
| Sequence and identity behaviour | differs | Day 158's batching |
| Error codes | different | Day 157's exception translation |
| Full-text search | ❌ | ✅ |

**⭐ The three that should end the argument:**

1. **Your multi-tenancy control is RLS, and H2 cannot express it** — so the most important security
   property in the system is untested.
2. **Your job-claiming query uses `SKIP LOCKED`** — so Day 178's idempotency is untested.
3. **Your unique constraint may be a partial index** — `unique (email) where deleted_at is null` —
   which does not exist in H2, so a test suite proving "duplicate emails are rejected" proves it
   against a constraint production does not have.

**⭐ The general principle: a test that passes against a different implementation than production
verifies that implementation, not yours.** That is not a purity argument; it is what the three cases
above make concrete.

# Part 2 — Setting it up

```xml
<dependency><groupId>org.testcontainers</groupId><artifactId>postgresql</artifactId><scope>test</scope></dependency>
<dependency><groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-testcontainers</artifactId><scope>test</scope></dependency>
```

```java
@SpringBootTest
@Testcontainers
abstract class IntegrationTestBase {                        // ⭐ Day 183 — ONE shared context

    @Container
    @ServiceConnection                                      // ⭐⭐ Boot 3.1+ — no property wiring
    static final PostgreSQLContainer<?> POSTGRES =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Container
    @ServiceConnection
    static final GenericContainer<?> REDIS =
            new GenericContainer<>("redis:7-alpine").withExposedPorts(6379);
}
```

**⭐ `@ServiceConnection` replaces `@DynamicPropertySource` entirely** — Boot inspects the container
and configures the datasource, the Redis connection, the Kafka bootstrap servers. Two annotations and
your integration tests run against the real thing.

**⭐ `static` is the performance-critical keyword.** A `static @Container` starts once per class (and
once for the whole run when it lives on a shared base class); a non-static one starts and stops **per
test method** — a two-second container turning a 200-test suite into seven minutes.

```java
@Container static final GenericContainer<?> WIREMOCK =           // ⭐ Day 154's HTTP dependency
    new GenericContainer<>("wiremock/wiremock:3.9.1").withExposedPorts(8080);

@Container static final LocalStackContainer AWS =                // S3, SQS (Day 126)
    new LocalStackContainer(parse("localstack/localstack:3")).withServices(S3, SQS);

@Container static final KafkaContainer KAFKA =                   // Day 185A
    new KafkaContainer(parse("confluentinc/cp-kafka:7.6.0"));
```

## ⭐ Reuse — the setting that makes local development bearable

```
# ~/.testcontainers.properties
testcontainers.reuse.enable=true
```
```java
new PostgreSQLContainer<>("postgres:16-alpine").withReuse(true);   // ⭐ survives between runs
```

**Containers stay running between test runs**, so the second run onward pays no startup cost. Local
feedback goes from "eight seconds before anything happens" to immediate.

⚠️ **Reuse keeps state between runs**, so tests must clean up after themselves — which they should
anyway (Day 097's *independent*). And **disable it in CI**, where a fresh environment is the point.

# Part 3 — ⭐ The practices that make it correct as well as real

## Test the actual migrations

```java
@Test
void flywayMigrationsApplyCleanly() {
    assertThat(flyway.info().applied()).isNotEmpty();
    assertThat(flyway.validate().validationSuccessful()).isTrue();     // ⭐ Day 166
}
```

**⭐ Testcontainers starts an empty database, so every run applies your migrations from V1.** That is
a real, continuous test of the thing that is otherwise only exercised in production. A migration that
fails on an empty database, or a checksum mismatch, fails in CI instead of at deploy.

**Do not use `ddl-auto: create` in tests.** It would test a schema Hibernate invented rather than the
one Flyway produces — and Day 157's whole point was that those two can drift.

## ⭐ Clean state without `@Transactional`

```java
@Test
@Sql(scripts = "/sql/clean.sql", executionPhase = BEFORE_TEST_METHOD)   // ⭐ truncate + reseed
void placesOrderAndCommits() { ... }
```

**`@Transactional` on an integration test rolls back — and that hides real behaviour:**

- ⭐ **`@TransactionalEventListener(AFTER_COMMIT)` never fires** (Day 179), so the notification path
  is untested;
- **deferred constraints and commit-time failures never surface;**
- **anything asynchronous reads a state that was never committed** (Day 177's race).

**For tests that verify commit-dependent behaviour, do not roll back — truncate.** It is slower and
it is testing what actually happens.

## WireMock for the HTTP dependency

```java
@Test
void openesCircuitOnGatewayTimeout() {                       // ⭐ Day 181
    wireMock.stubFor(post("/charges").willReturn(aResponse().withFixedDelay(10_000)));
    // ⭐ only a real HTTP server can verify that your timeout actually fires
}
```

**Day 154's argument: you cannot test a timeout against a mocked client.** A mock returns instantly;
only a server that is genuinely slow proves the timeout, the retry, the backoff and the circuit
breaker behave as configured.

## ⭐ The tests that only Testcontainers makes possible

```java
@Test void tenantCannotReadAnotherTenantsRow() { ... }        // ⭐ RLS — Day 176
@Test void jobClaimIsExclusiveAcrossWorkers() { ... }         // ⭐ SKIP LOCKED — Day 178
@Test void concurrentUpdateThrowsOptimisticLock() { ... }     // ⭐ Day 165
@Test void partialUniqueIndexAllowsSoftDeletedDuplicates() { }// ⭐ Day 166
@Test void bulkUpdateDoesNotIncrementVersion() { ... }        // ⭐ Day 162
```

**⭐ Every one of these is a correctness property that H2 cannot express.** Look at that list against
what Stage 4 built — the multi-tenancy control, the job idempotency, the lost-update defence — and
the case is settled: **the most important guarantees in the system are exactly the ones an in-memory
database cannot verify.**

# Part 4 — Cost, and the honest trade-offs

| Concern | Reality |
|---|---|
| **Startup time** | ⭐ 2–5 s per container, **once** with `static` + a shared base class |
| **Docker required** | ⭐ ⚠️ **CI must provide it** — a real constraint on some runners |
| Resource use | a few hundred MB per container |
| Flakiness | ⭐ image pulls and port binding — mitigate with a registry mirror and pinned tags |
| Debugging | ⭐ `container.getLogs()` when a test fails mysteriously |

**⭐ Pin image tags exactly.** `postgres:16-alpine` moves; `postgres:16.4-alpine` does not. An
unpinned tag means your test suite's behaviour changes when someone upstream publishes — Day 073's
dependency-pinning argument, applied to containers.

## The layered strategy

```
Unit tests (no Spring)              ← ⭐ thousands, milliseconds       (Day 183)
Slice tests                         ← hundreds, ~1 s
Integration + Testcontainers        ← ⭐ dozens, one shared context
Contract tests (WireMock/OpenAPI)   ← Day 153
Smoke tests against a real env      ← a handful, post-deploy
```

**⭐ Testcontainers does not replace the pyramid — it makes the integration layer trustworthy.** If
you find yourself writing hundreds of Testcontainers tests, the logic they exercise probably belongs
in unit tests.

## `@ServiceConnection` vs `@DynamicPropertySource`

```java
// ⭐ For anything without a ServiceConnection factory
@DynamicPropertySource
static void props(DynamicPropertyRegistry registry) {
    registry.add("payment.gateway.url", () -> "http://localhost:" + WIREMOCK.getMappedPort(8080));
}
```

**Always use `getMappedPort()`, never the fixed port.** Testcontainers binds a random host port so
parallel runs and local services do not collide — hard-coding 5432 works until two builds run at
once.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ H2 instead of the real engine | RLS, `SKIP LOCKED`, partial indexes and MVCC all untested |
| ⭐ Non-`static` `@Container` | starts per test method; suite time explodes |
| A container per test class instead of a shared base | many contexts and many containers (Day 183) |
| ⭐ `ddl-auto: create` in tests | tests a schema Flyway never produces |
| ⭐ `@Transactional` on integration tests | `AFTER_COMMIT` listeners and commit-time failures untested |
| Hard-coded ports | collides in parallel or with a local service |
| Unpinned image tags | the suite changes when upstream publishes |
| Reuse enabled in CI | stale state between builds |
| Mocking the HTTP client instead of WireMock | cannot verify timeouts or the circuit breaker |
| Hundreds of Testcontainers tests | the pyramid inverted; slow feedback |
| Not reading `container.getLogs()` | mysterious failures stay mysterious |

## Interview questions

**Q: Why Testcontainers instead of H2?**
Because the properties I most need to verify cannot be expressed in H2. Row-level security is my
multi-tenancy control, `FOR UPDATE SKIP LOCKED` is how my jobs claim work idempotently, and partial
unique indexes are how soft-deletes work — none exist in H2. A test passing against a different
database verifies that database, not mine.

**Q: How do you keep it fast?**
`static` containers on a shared abstract base class, so one container and one Spring context serve
the whole suite, plus container reuse locally. The containers are a few seconds once, not per test.

**Q: Why not make integration tests `@Transactional`?**
Because rollback hides commit-dependent behaviour — `AFTER_COMMIT` event listeners never fire,
deferred constraints never trigger, and async work reads a state that was never committed. I truncate
between tests instead.

**Q: What does Testcontainers let you test that you otherwise could not?**
Migrations from an empty database on every run, real concurrency — optimistic locking, `SKIP LOCKED`,
isolation semantics — row-level security, and with WireMock the timeout and circuit-breaker behaviour
that a mocked client can never exercise.

row-level security, `SKIP LOCKED`, partial unique indexes — and observe that those are the

the most important guarantees in the system. Then the operational half: static containers on a shared
base class so it costs seconds once, migrations tested from empty on every run, and no `@Transactional`
on integration tests because rollback hides everything that happens at commit.
