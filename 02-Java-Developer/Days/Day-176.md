# Part 1 — The three models, and the honest cost of each

| Model | Isolation | Cost |
|---|---|---|
| **Database per tenant** | ⭐ strongest | N databases to migrate, back up, monitor. Expensive past ~50 tenants |
| **Schema per tenant** | strong | one database, N schemas. Migrations run N times; connection pool per schema is awkward |
| **Shared schema + `tenant_id`** | ⭐ **weakest — one query from a breach** | ⭐ cheapest to operate. What most SaaS actually runs |

**Choose by the cost of a breach, not by convenience.** Handling health or financial data for large
enterprise customers with contractual isolation requirements? Database per tenant. A self-serve
product with 40,000 small tenants? Shared schema, with the defences below applied rigorously.

**And the hybrid worth naming:** shared schema for the long tail, dedicated databases for the handful
of enterprise customers who pay for and contractually require isolation. That is what most mature
SaaS platforms actually do.

# Part 2 — Shared schema, defended in depth

### Layer 1 — the tenant context

```java
public final class TenantContext {
    private static final ThreadLocal<String> CURRENT = new ThreadLocal<>();   // ⭐ Day 066A
    public static void set(String tenantId) { CURRENT.set(tenantId); }
    public static String require() {
        String t = CURRENT.get();
        if (t == null) throw new IllegalStateException("no tenant in context");  // ⭐ fail closed
        return t;
    }
    public static void clear() { CURRENT.remove(); }
}
```

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 20)                 // ⭐ after authentication
public class TenantFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        try {
            var auth = SecurityContextHolder.getContext().getAuthentication();
            if (auth != null && auth.getPrincipal() instanceof AppUserDetails u) {
                TenantContext.set(u.tenantId());         // ⭐⭐ FROM THE TOKEN. NEVER FROM A HEADER
            }
            MDC.put("tenantId", TenantContext.require()); // Day 127
            chain.doFilter(req, res);
        } finally {
            TenantContext.clear();                       // ⭐⭐ Day 151 — non-negotiable
            MDC.remove("tenantId");
        }
    }
}
```

**⭐ Two lines carry the whole security model:**

1. **The tenant comes from the authenticated principal**, never from an `X-Tenant-Id` header. A
   client-supplied tenant id is an "act as any tenant" parameter — this is IDOR at the tenancy level
   and it is a total breach.
2. **`clear()` in a `finally`.** Day 066A's pooled-thread leak, with the worst possible payload:
   the next request on that Tomcat thread would read and write **another tenant's data**. Silent,
   intermittent, and catastrophic.

### Layer 2 — automatic filtering

```java
@Entity
@FilterDef(name = "tenantFilter", parameters = @ParamDef(name = "tenantId", type = String.class))
@Filter(name = "tenantFilter", condition = "tenant_id = :tenantId")     // ⭐ Day 163b: parameterised
public class Order { }
```

```java
@Component
public class TenantFilterActivator {
    @PersistenceContext private EntityManager em;

    @EventListener(TransactionBeginEvent.class)     // or an AOP aspect / EntityManager customiser
    public void enable() {
        em.unwrap(Session.class)
          .enableFilter("tenantFilter")
          .setParameter("tenantId", TenantContext.require());
    }
}
```

**Useful, and not a control.** Hibernate `@Filter` **does not apply to `find()` by primary key**, and
it does not apply to native queries. So `repo.findById(otherTenantsOrderId)` returns the row. It
reduces the number of places you can make a mistake; it does not eliminate them.

### ⭐ Layer 3 — row-level security, the only real control

```sql
-- Flyway migration (Day 166)
alter table orders enable row level security;
alter table orders force row level security;              -- ⭐ applies to the table owner too

create policy tenant_isolation on orders
  using (tenant_id = current_setting('app.tenant_id', true));
```

```java
@Component
public class RlsConnectionPreparer {
    public void prepare(Connection conn, String tenantId) throws SQLException {
        try (var ps = conn.prepareStatement("select set_config('app.tenant_id', ?, true)")) {
            ps.setString(1, tenantId);                    // ⭐ bound, and true = transaction-scoped
            ps.execute();
        }
    }
}
```

**⭐ Why this is qualitatively different from every other layer:** the database enforces it. A missing
`WHERE` clause, a native query, a `findById` with a foreign id, a `psql` session by an on-call
engineer, a reporting tool — **all of them see only the current tenant.** Application bugs stop being
breaches.

**Two operational cautions:**

- **The setting must be transaction-scoped** (`true` in `set_config`) and set on every connection
  checkout, or a pooled connection carries the previous tenant's setting — Day 156's pool meeting
  Day 066A's leak.
- **The application's database user must not be a superuser or the table owner without `force`** —
  both bypass RLS entirely, which is a startlingly easy way to have the policy silently do nothing.

### Layer 4 — tests that specifically look for it

```java
@Test
void cannotReadAnotherTenantsOrder() {
    TenantContext.set("tenant-a");
    UUID orderId = orders.create(...).id();

    TenantContext.set("tenant-b");
    assertThat(orders.findById(orderId)).isEmpty();        // ⭐ THE test
}

@Test
void repositoryQueriesAllFilterByTenant() {                 // ⭐ ArchUnit or a SQL-capturing test
    // assert every generated SQL statement against a tenant-scoped table contains tenant_id
}
```

**Write a cross-tenant negative test for every entity.** This is the single highest-value test suite
in a multi-tenant system, because the failure mode returns 200 with someone else's data.

# Part 3 — The misconfiguration checklist

**Each of these has caused a real breach. Go through it before every release.**

| # | Check | Failure |
|---|---|---|
| 1 | `.anyRequest().authenticated()` last in every chain | new endpoints public by default |
| 2 | ⭐ Chains ordered most-specific first | later chains dead; endpoints open (Day 169) |
| 3 | No `WebSecurityCustomizer.ignoring()` | bypasses the whole chain |
| 4 | CSRF enabled wherever a cookie authenticates | Day 172 |
| 5 | ⭐ CORS not `allowedOriginPatterns("*")` with credentials | any site acts as the user (Day 155) |
| 6 | Actuator on a separate port, allow-listed | heap dump = every secret (Day 143) |
| 7 | ⭐ `include-stacktrace: never` | information disclosure (Day 149) |
| 8 | Swagger UI disabled in production | a map of the attack surface (Day 153) |
| 9 | ⭐ Secrets from the environment, never committed | Day 085, Day 142 |
| 10 | ⭐ JWT algorithm allow-list + token-type claim | Day 173 |
| 11 | Ownership checks on every by-id endpoint | IDOR (Day 174) |
| 12 | ⭐ 404 not 403 for another tenant's record | existence oracle |
| 13 | Rate limiting on login, reset, and token endpoints | credential stuffing, hash-CPU DoS |
| 14 | `HttpOnly`, `Secure`, `SameSite` on every cookie | Day 113 |
| 15 | ⭐ `forward-headers-strategy` set behind a proxy | `Secure` never applies; IP rate limiting broken |
| 16 | ⭐ CSP header set | the one Spring does not set (Day 169) |
| 17 | Least-privilege database user | Day 163b — injection reads instead of destroys |
| 18 | ⭐ Dependency scanning in CI | Day 100A — most breaches are known CVEs |
| 19 | Security events logged and alerted | reuse detection, lockouts, denials (Day 143) |
| 20 | ⭐ No sensitive data in JWT claims or logs | signed ≠ encrypted; Day 127 |

**⭐ Numbers 18 and 19 deserve emphasis.** Most real-world compromises are not novel attacks against
your code — they are a known CVE in a dependency you did not upgrade, or an intrusion nobody noticed
for eleven weeks. **Scanning and alerting outrank almost everything else on this list.**

# Part 4 — 🚪 Security block exit gate (Days 169–176)

### The build — one sitting, no reference material

1. Two `SecurityFilterChain`s, correctly ordered, `.anyRequest().authenticated()` last
2. `DelegatingPasswordEncoder` with argon2, plus `UserDetailsPasswordService` upgrade-on-login
3. Login with rate limiting by IP **and** username, no enumeration in response or timing
4. JWT filter with **all five validations**, writing `ProblemDetail` itself
5. Refresh rotation with **family revocation on reuse**, tokens stored as hashes
6. Access token in the body, refresh token in an `HttpOnly` `SameSite=Strict` path-scoped cookie
7. `@PreAuthorize` with a guard bean **in the service layer**; collection authorization as a query
   predicate
8. `AuthenticationEntryPoint` and `AccessDeniedHandler` producing RFC 7807
9. Tenant context from the token, cleared in a `finally`, **plus PostgreSQL RLS**
10. Negative tests: anonymous → 401, wrong role → 403, other user's record → 404, other tenant → empty

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Tenant id from a header | "act as any tenant" — total breach |
| ⭐ `TenantContext` not cleared | next request serves another tenant's data |
| Relying on `@Filter` alone | bypassed by `findById` and native queries |
| RLS without `force` | the table owner bypasses the policy silently |
| RLS setting not transaction-scoped | pooled connection carries the previous tenant |
| Application connecting as superuser | RLS does nothing |
| No cross-tenant tests | the breach returns 200 |
| Shared schema for contractually-isolated customers | a model chosen by convenience, not by risk |

## Interview questions

**Q: How do you implement multi-tenancy?**
By the cost of a breach. Shared schema with a `tenant_id` for a large self-serve tenant base,
defended in layers: tenant from the authenticated token and never a header, a `ThreadLocal` cleared
in a `finally`, Hibernate filters as a convenience, and **PostgreSQL row-level security as the actual
control** — because that is the only layer where a missing `WHERE` clause stops being a breach.
Dedicated databases for enterprise customers who require isolation.

**Q: Why isn't a Hibernate `@Filter` enough?**
It does not apply to `find()` by primary key or to native queries, so a `findById` with another
tenant's id returns the row. It reduces the surface for mistakes; it does not enforce anything.

**Q: What is the most dangerous thing about a shared-schema system?**
That a missing `WHERE` clause is a data breach, and it does not throw, log or fail any test that is
not specifically looking for it. That is why the control has to be in the database and why the
negative cross-tenant test exists for every entity.

3. Add RLS with `force`. Confirm `findById` now returns nothing across tenants.

## 🎙️ Articulation drill

Two minutes: **"How would you build a multi-tenant SaaS securely?"**

Choose the model by breach cost, not convenience, and say what you would run: shared schema for the
long tail, dedicated databases for enterprise. Then defence in depth, and be explicit that only one
layer is a real control — the tenant comes from the token, the context is cleared in a `finally`,
Hibernate filters reduce mistakes, and row-level security in the database is what makes an
application bug stop being a breach. Close on why this needs its own test suite: a cross-tenant leak
returns 200 with someone else's data, so nothing except a test written to look for it will ever
notice.
