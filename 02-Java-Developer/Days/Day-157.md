# Day 157

**L-157** · JPA vs Hibernate vs Spring Data — three layers, three different things

**Time:** 3 hrs · **Mode:** NEW

> People use these three words interchangeably and then cannot explain a stack trace, because the
> exception class tells you *which layer* failed and they do not know there are layers.
>
> Today separates them, states what an ORM is actually solving and what it costs, and gives the
> honest account of when not to use one. It is short on code and long on judgement — which is
> exactly what the interview question rewards.

# Part 1 — The three layers

```
┌──────────────────────────────────────────────────────────────┐
│  Spring Data JPA        interface OrderRepository            │  ← convenience
│  (a Spring project)     extends JpaRepository<Order, UUID>   │
├──────────────────────────────────────────────────────────────┤
│  JPA                    @Entity  EntityManager  JPQL         │  ← ⭐ the SPECIFICATION
│  (jakarta.persistence)  the interface, no implementation     │
├──────────────────────────────────────────────────────────────┤
│  Hibernate              SessionFactory, Session, dialects,   │  ← ⭐ the IMPLEMENTATION
│  (org.hibernate)        the persistence context, HQL         │
├──────────────────────────────────────────────────────────────┤
│  JDBC                   Connection, PreparedStatement        │  ← Day 156
├──────────────────────────────────────────────────────────────┤
│  The database                                                │
└──────────────────────────────────────────────────────────────┘
```

| | What it is | Who owns it | You'd swap it? |
|---|---|---|---|
| **JPA** | a **specification** — annotations and interfaces, no behaviour | Jakarta EE | it is the API you code against |
| **Hibernate** | the **implementation** that does the work | Red Hat | in theory yes, in practice ⭐ never |
| **Spring Data JPA** | generates repository implementations at runtime | Spring | yes, easily — it is a thin layer |

**⭐ The point that matters practically:** JPA is a small specification and Hibernate is a large
product. The moment you need batch sizes, `@Filter`, multi-tenancy, statistics, a natural-id cache,
or `@DynamicUpdate`, you are using Hibernate-specific features — and that is fine. **"We stay
strictly JPA-compliant so we can swap providers" is a portability argument almost nobody cashes in**,
and it costs you real capability. Be able to say that; interviewers respect the honesty more than the
recital.

## Reading a stack trace by layer

| Exception | Layer | Means |
|---|---|---|
| `jakarta.persistence.EntityNotFoundException` | JPA | spec-defined |
| `org.hibernate.LazyInitializationException` | ⭐ Hibernate | no JPA equivalent — Day 160 |
| `org.hibernate.StaleObjectStateException` | Hibernate | optimistic lock — Day 165 |
| `org.springframework.dao.DataIntegrityViolationException` | ⭐ Spring | **translated** from a vendor code |
| `org.springframework.orm.ObjectOptimisticLockingFailureException` | Spring | translated Hibernate |
| `java.sql.SQLException` | JDBC | raw |

**Spring's exception translation is a genuinely valuable and under-appreciated feature.** PostgreSQL
signals a unique-constraint violation with SQL state `23505`, MySQL with error `1062`. Spring
translates both into `DuplicateKeyException`, so your catch block is portable and readable. That
translation is why `@Repository` exists as a distinct annotation — it enables the
`PersistenceExceptionTranslationPostProcessor`, which is a `BeanPostProcessor` (Day 132) wrapping the
bean in a proxy (Day 137). The whole Stage 4 mechanism, doing one small useful job.

# Part 2 — What an ORM actually solves, and what it costs

**The impedance mismatch** is real and it is four separate problems:

| Mismatch | Objects | Tables |
|---|---|---|
| **Granularity** | `Order` has an `Address` object | address columns are inline, or a joined table |
| **Identity** | `==` and `.equals()` | primary key |
| **Associations** | directional references, both ways possible | foreign keys, one direction only |
| **Inheritance** | first-class | ⭐ **does not exist** |
| **Navigation** | `order.getCustomer().getAddress().getCity()` | you must join, or you issue N queries |

**The last row is the one that causes every N+1 problem in existence.** Object code navigates
pointer by pointer, one step at a time. SQL wants you to state the entire shape you need up front and
fetch it in one round trip. An ORM lets you write the first while it silently issues the second —
badly — unless you tell it what you actually want. **Day 160 and Day 161 are entirely about closing
that gap.**

## The honest cost list

| Cost | Detail |
|---|---|
| ⭐ **A leaky abstraction** | you must understand *both* objects and SQL, plus how the ORM maps between them. That is more to know, not less |
| **Generated SQL surprises** | Day 160's N+1, the in-memory pagination of Day 152, cartesian products from multiple `join fetch` |
| **The persistence context** | a stateful cache with its own lifecycle you must reason about (Day 162) |
| **Hard things stay hard** | reporting, bulk updates, window functions, `ON CONFLICT` — Day 156's `JdbcClient` |
| **Learning curve** | the failure modes are non-obvious and mostly silent |

**What it genuinely buys you:** dirty checking (change an object, the UPDATE writes itself), identity
guarantees within a transaction, cascading, optimistic locking, a first-level cache, and the fact
that CRUD across forty tables is close to zero code.

## The competitors, positioned honestly

| Tool | Model | Best at |
|---|---|---|
| **Spring Data JPA / Hibernate** | full ORM | ⭐ CRUD-heavy domains with rich relationships; the default in the Java job market |
| **jOOQ** | typed SQL DSL | ⭐ SQL-heavy, reporting, complex queries. Compile-time-checked SQL generated from the actual schema |
| **MyBatis** | SQL mapper | you want to own every query, with mapping help |
| **Spring Data JDBC** | simple aggregate mapping | ⭐ DDD aggregates, no lazy loading, no persistence context — far fewer surprises |
| **`JdbcClient`** | raw | reports, bulk work, anything ORM makes awkward |

**The mature answer to "which ORM?"** is that a real system uses two: JPA for the transactional
domain model where dirty checking and cascading earn their keep, and `JdbcClient` or jOOQ for reads,
reports and bulk operations. Treating "we use JPA" as a rule that forbids writing SQL is how teams
end up with unreadable Criteria queries reimplementing a `GROUP BY`.

**And Spring Data JDBC deserves a real look.** No lazy loading means no `LazyInitializationException`
and no accidental N+1; no persistence context means no dirty-checking surprises. You give up
cascading convenience and get predictability, which for many services is the better trade.

# Part 3 — Setup, and the four settings to get right immediately

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
```

```yaml
spring:
  jpa:
    open-in-view: false                          # ⭐⭐ 1
    hibernate.ddl-auto: validate                 # ⭐⭐ 2
    properties:
      hibernate:
        jdbc.batch_size: 50                      # Day 156
        order_inserts: true
        order_updates: true
        query.fail_on_pagination_over_collection_fetch: true   # ⭐ 3
        query.in_clause_parameter_padding: true
  jpa.show-sql: false                            # ⭐ 4 — see below
```

### ⭐ 1 — `open-in-view: false`

Day 139 named it the most consequential wrong default in Spring Boot. Concretely, `true` means:

- a database connection is held for the whole request, including JSON serialization and the time
  spent writing to a slow client (Day 156's arithmetic);
- lazy loads fire **during serialization**, where no profiler you are watching attributes them;
- so N+1 problems are invisible in development and appear as latency in production.

Setting `false` **surfaces bugs rather than causing them.** Something breaking with
`LazyInitializationException` was always broken — you were paying for it in queries.

### ⭐ 2 — `ddl-auto: validate`

| Value | Use |
|---|---|
| `none` / `validate` | ⭐ **production and every shared environment.** `validate` fails startup if entities and schema disagree — a superb early warning |
| `update` | ❌ **never.** It never drops or narrows anything, so the schema silently accumulates dead columns, it cannot express a data migration, and it is not reviewable |
| `create-drop` | throwaway tests only |

Day 166's Flyway owns the schema. `validate` is how the application checks that the migrations and
the entities agree, and it fails the **deploy** rather than the first query that touches a missing
column.

### ⭐ 3 — `fail_on_pagination_over_collection_fetch`

Turns Day 152's `HHH90003004` warning — Hibernate silently paginating the whole table in memory —
into an **exception**. A warning in a busy log is not a control; an exception is. Turn this on.

### ⭐ 4 — Logging SQL properly

```yaml
logging.level.org.hibernate.SQL: DEBUG
logging.level.org.hibernate.orm.jdbc.bind: TRACE     # ⭐ Hibernate 6 path for parameter values
```

**Not `spring.jpa.show-sql: true`** — it writes to `System.out`, bypassing your logging framework
entirely, so it is unstructured (Day 127), unfilterable, and cannot be turned on per-package in
production.

**And the tool that matters more than either:**

```xml
<dependency>
  <groupId>com.github.gavlyukovskiy</groupId>
  <artifactId>datasource-proxy-spring-boot-starter</artifactId>
</dependency>
```

Logs each query **with its bound parameters, its execution time, and a per-transaction query count**.
That count is how you catch an N+1 — and asserting on it in a test is how you stop one from coming
back (Day 160).

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Using the three names interchangeably | cannot read a stack trace by layer |
| "Stay JPA-pure for portability" | gives up real Hibernate capability for a swap that never happens |
| `ddl-auto: update` | unreviewable schema drift; no data migrations |
| `open-in-view: true` | N+1 invisible in dev, connections held through serialization |
| `show-sql: true` | bypasses logging config; unusable in production |
| Forcing every query through JPA | unreadable Criteria reimplementations of `GROUP BY` |
| Not knowing Spring translates exceptions | vendor-specific catch blocks |
| Ignoring Spring Data JDBC as an option | takes on lazy-loading complexity that was never needed |

## Interview questions

**Q: What is the difference between JPA, Hibernate and Spring Data JPA?**
JPA is a specification — annotations and interfaces with no behaviour. Hibernate is the
implementation that actually does the work, and it has a large feature set beyond the spec. Spring
Data JPA is a Spring project that generates repository implementations over JPA. In practice you
code to JPA, run on Hibernate, and use Hibernate-specific features whenever they earn their place.

**Q: What problem does an ORM solve, and what does it cost?**
The object-relational impedance mismatch — granularity, identity, associations, inheritance, and
above all navigation: object code walks references one at a time while SQL wants the whole shape in
one round trip. The cost is a leaky abstraction: you now have to understand objects, SQL, *and* the
mapping, and the failure modes are mostly silent.

**Q: Why is `ddl-auto: update` dangerous?**
It never removes or narrows anything, so the schema accumulates dead columns and diverges from the
entities in ways nobody reviewed. It also cannot express a data migration. Flyway owns the schema and
`validate` checks that the entities agree with it, at startup.

**Q: Would you always use JPA?**
No. JPA for the transactional domain model where dirty checking and cascading pay off, and
`JdbcClient` or jOOQ for reports, aggregations and bulk work. For a simple aggregate-shaped domain,
Spring Data JDBC is often better precisely because it has no lazy loading and no persistence context.

## 🎙️ Articulation drill

Two minutes: **"Explain JPA, Hibernate and Spring Data JPA."**

Separate the three by *kind*: specification, implementation, convenience layer — then say why it
matters, which is that the package name in a stack trace tells you which layer failed. Move to what
an ORM is solving: the impedance mismatch, and specifically that object code navigates one reference
at a time while SQL wants the whole shape at once. Then show judgement — an ORM is a leaky
abstraction you must understand at both ends, and a real system pairs JPA for the transactional model
with plain SQL for reports, rather than forcing everything through one tool.
