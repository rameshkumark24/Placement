# Part 1 — L-005 · The client side

## What a client is

**A client is a program that initiates a connection to a known address.**

That's the entire definition, and it's the mirror of Day 004:

| | Server | Client |
|---|---|---|
| Address | Commits to one in advance | Gets one assigned by the OS |
| Behaviour | Waits (`accept()` blocks) | Initiates (`connect()`) |
| Lifetime | Long-running, often forever | Often short-lived |
| Knows about the other | Nothing until contacted | Must know the address |

Look at the code side by side:

```java
// SERVER                                  // CLIENT
ServerSocket s = new ServerSocket(8080);   Socket c = new Socket("localhost", 8080);
Socket conn = s.accept();   // wait                        // connect
conn.getInputStream();                     c.getInputStream();
conn.getOutputStream();                    c.getOutputStream();
```

**After the connection is established, the two sides are symmetric.** Both have a socket. Both can
read and write. The asymmetry existed only during setup — one waited, one initiated.

This is why the distinction is a *role*, not a *type*. Your Spring Boot service is a server to the
browser and a client to Postgres, simultaneously, in the same process.

## Why the web is client-server

It could have been peer-to-peer. Some things are (BitTorrent, some blockchains). The web isn't,
because:

1. **Discovery.** For two peers to talk, at least one needs a stable, findable address. Servers have
   one; your laptop behind NAT (Day 004, C-03) does not.
2. **Availability.** A server is up 24/7. Peers come and go.
3. **Authority.** Someone must hold the canonical data. If every browser held a copy of your bank
   balance, "which copy is right" becomes unanswerable.
4. **Trust.** You can secure and audit one server. You cannot audit ten million browsers.

**NAT is the practical killer.** Your machine has no publicly reachable address, so it cannot be
contacted first. It can only initiate. That single fact forces client-server on almost all consumer
software — and it's why WebRTC needs STUN/TURN servers to do peer-to-peer at all.

## Request/response is a *model*, not a law

HTTP works like this:

```
   Client ──── request ────▶ Server
   Client ◀─── response ──── Server
                                     ← conversation over
```

Strictly alternating. Client speaks first. Server cannot speak unprompted.

**That last constraint is the source of an enormous amount of web architecture.** The server has
data — a new message arrived, a price changed — and *no way to tell you*.

The workarounds, in the order they were invented:

| Approach | How | Cost |
|---|---|---|
| **Polling** | Client asks every N seconds | Wasteful; 99% of requests return "nothing new". Latency up to N. |
| **Long polling** | Client asks; server *holds* the request open until it has news | Holds a connection and a thread per client |
| **SSE** | One long-lived response the server streams into | Server → client only |
| **WebSockets** | Upgrade to a full-duplex connection; either side speaks anytime | Not request/response any more — a different model |

You'll do the decision table properly on Day 018. What matters today: **all four exist because the
request/response model forbids the server from speaking first.** Every one of them is a workaround
for that one rule.

> Connect this forward: in [`03-Web-Developer` Phase 05](../../03-Web-Developer/05-API-Safety.md),
> the "polling leak" is a bug where a client polls every second and nobody clears the interval. Now
> you know *why* anyone polls at all.

## Type this yourself

Talk to the server you wrote yesterday. Start `TinyServer`, then run this:

```java
import java.io.*;
import java.net.*;

public class TinyClient {
    public static void main(String[] args) throws IOException {

        // connect() — the client's equivalent of the server's bind+listen+accept
        Socket socket = new Socket("localhost", 8080);
        System.out.println("Local (my ephemeral port): " + socket.getLocalSocketAddress());
        System.out.println("Remote (the server):       " + socket.getRemoteSocketAddress());

        // Write an HTTP request BY HAND. Same shape as the response you wrote yesterday.
        PrintWriter out = new PrintWriter(socket.getOutputStream());
        out.print("GET / HTTP/1.1\r\n");
        out.print("Host: localhost:8080\r\n");
        out.print("Connection: close\r\n");
        out.print("\r\n");                       // blank line = end of headers
        out.flush();

        // Read the whole response.
        BufferedReader in = new BufferedReader(
                new InputStreamReader(socket.getInputStream()));
        String line;
        while ((line = in.readLine()) != null) {
            System.out.println(line);
        }
        socket.close();
    }
}
```

**Look at the two addresses it prints.** The local one has a port you never chose — the OS assigned
it from the ephemeral range (Day 003). That's the source port in the 4-tuple.

**Run the client three times.** Write down the local port each time. It changes. That is exactly how
three simultaneous connections to the same server stay distinct.

### Then be the client with your bare hands

```bash
curl -v http://localhost:8080
```

`-v` shows you the raw request and response. Compare it to what you typed above — `curl` is doing
the same thing with more headers.

## Common mistakes

| Mistake | Correction |
|---|---|
| "A client is a browser" | A browser is one client. `curl`, your Spring app calling Postgres, a mobile app, another microservice — all clients. |
| Thinking client/server is a property of the program | It's a role per connection. One process is routinely both at once. |
| "The server can push whenever it wants" | Not in HTTP request/response. It needs SSE, WebSockets, or the client asking. |
| Choosing the client's port | You don't. The OS assigns an ephemeral one. You choose the *destination* port. |
| Forgetting the blank line after headers | The server waits forever for headers that already ended. Your request hangs. |

## Interview questions

**Q: What's the difference between a client and a server?**
> A server binds to a known port and waits for connections; a client initiates a connection to a
> known address. It's a role within a conversation, not a type of program — a backend service is a
> server to its callers and a client to its database in the same process.

**Q: Why is the web client-server rather than peer-to-peer?**
> Discovery and availability, mostly. A server has a stable, publicly reachable address and is up
> continuously; consumer machines sit behind NAT with no reachable address and go offline. Plus a
> single authoritative copy of data and a securable trust boundary.

**Q: If HTTP is request/response, how do real-time features work?**
> They work around it. Polling, long polling, Server-Sent Events for one-way server→client streaming,
> or WebSockets, which upgrade the connection to full duplex and abandon request/response entirely.

# Part 2 — C-04 · TCP I — the handshake and sequence numbers

## What TCP gives you

IP (C-03) delivers packets to a machine, but makes **no promises**: packets may be lost, duplicated,
reordered, or corrupted. That's fine for the network layer — it keeps routers simple and fast.

TCP builds four guarantees on top of that unreliable foundation:

1. **Reliable** — lost data is retransmitted
2. **Ordered** — bytes arrive in the order sent
3. **Error-checked** — corrupted segments are discarded and resent
4. **Flow-controlled** — a fast sender can't drown a slow receiver

**It gives you the illusion of a continuous byte stream** over a medium that delivers discrete,
unreliable packets. That illusion is the single most useful abstraction in networking.

## Sequence and acknowledgement numbers

The mechanism behind all four guarantees is simple: **number every byte**.

- **SEQ** — "the first byte in this segment is byte number N of my stream"
- **ACK** — "I have received everything up to byte N−1; send me N next"

```
  Client sends 100 bytes starting at SEQ=1000
       ──────────────────────────────────────▶  SEQ=1000, len=100

  Server received all of it, wants byte 1100 next
       ◀──────────────────────────────────────  ACK=1100
```

From that one idea you get everything:

- **Loss detection** — no ACK arrives → retransmit
- **Reordering** — segments arrive out of order → the receiver buffers and reassembles by SEQ
- **Duplicate detection** — a SEQ already received → discard
- **Flow control** — the ACK also carries a *window* saying how much more you may send (C-05)

Initial sequence numbers are **random**, not zero. If they were predictable, an attacker who knew
your IP could forge segments into your connection. Randomised ISNs make blind injection impractical.

## The three-way handshake

```
   CLIENT                                          SERVER
     │                                               │
     │  1.  SYN     seq=x                            │   "I want to talk.
     │ ─────────────────────────────────────────────▶│    My stream starts at x."
     │                                               │
     │  2.  SYN-ACK seq=y, ack=x+1                   │   "OK. Mine starts at y.
     │ ◀─────────────────────────────────────────────│    I got your x."
     │                                               │
     │  3.  ACK     ack=y+1                          │   "I got your y."
     │ ─────────────────────────────────────────────▶│
     │                                               │
     │            ESTABLISHED — data flows           │
     │ ◀────────────────────────────────────────────▶│
```

### Why three, not two?

Because **both directions must be confirmed**, and each side needs to know its own SYN was received.

- Message 1 proves the client can send
- Message 2 proves the server received it *and* can send
- Message 3 proves the client received the server's SYN

After two messages, the server knows the client can reach it, but the client hasn't confirmed it
received the server's sequence number. Without step 3, the server would start sending data that the
client might not be able to order correctly.

**This is a standard interview question.** The answer is: three is the minimum to establish agreed
starting sequence numbers *in both directions*.

### What this costs you

**One full round trip before a single byte of your data moves.** Chennai → Oregon is ~200 ms RTT,
so the handshake alone costs 200 ms. Add TLS (Day 009) and it's 400 ms before your HTTP request even
starts.

That cost is why:
- HTTP/1.1 added **keep-alive** — reuse the connection, pay the handshake once (Day 011)
- Connection **pooling** exists — HikariCP holds open connections to Postgres so you never pay it
  per query (Day 156, and why Day 197 matters)
- QUIC folds the transport and crypto handshakes together (Day 011)

## The four-way teardown

Closing takes four messages, because **each direction closes independently**. TCP connections are
full-duplex, so "I'm done sending" doesn't mean "I'm done receiving".

```
   CLIENT                                          SERVER
     │  FIN                                          │  "I've finished sending."
     │ ─────────────────────────────────────────────▶│
     │  ACK                                          │
     │ ◀─────────────────────────────────────────────│
     │                                               │
     │        server can still send here             │  ← half-open. This is legal.
     │ ◀─────────────────────────────────────────────│
     │                                               │
     │  FIN                                          │  "Now I've finished too."
     │ ◀─────────────────────────────────────────────│
     │  ACK                                          │
     │ ─────────────────────────────────────────────▶│
     │                                               │
     │  TIME_WAIT (2×MSL, typically 60s)             │
```

**`TIME_WAIT`** — the side that closes first waits ~60 seconds before fully releasing the socket.
Why: a delayed duplicate segment from this connection could otherwise arrive and be misread as
belonging to a *new* connection reusing the same 4-tuple.

This is the direct explanation for something you'll hit constantly:

> You stop your Spring Boot app, restart it immediately, and get `Address already in use` even
> though nothing is running.

That's `TIME_WAIT`. The socket is in a shutdown state, not free yet. `SO_REUSEADDR` is the flag that
tells the OS to allow the bind anyway.

You'll go deeper into the state machine on Day 008.

## Type this yourself

Watch a real handshake:

```bash
# Terminal 1 — capture (needs admin; Wireshark's GUI works too)
# Windows: use Wireshark, filter:  tcp.port == 8080
# Linux/Mac:
sudo tcpdump -i lo -n 'tcp port 8080' -c 20

# Terminal 2 — start TinyServer, then run TinyClient
```

You will see, literally:

```
IP 127.0.0.1.51234 > 127.0.0.1.8080: Flags [S],  seq 2847362891
IP 127.0.0.1.8080 > 127.0.0.1.51234: Flags [S.], seq 918273645, ack 2847362892
IP 127.0.0.1.51234 > 127.0.0.1.8080: Flags [.],  ack 918273646
```

`[S]` = SYN, `[S.]` = SYN-ACK, `[.]` = ACK. **That is the diagram above, on your own machine.**
Note the random initial sequence numbers, and that each ACK is the other's SEQ + 1.

Then check states:

```bash
netstat -an | findstr 8080        # Windows
ss -tan | grep 8080               # Linux
```

Look for `ESTABLISHED`, then run the client again and catch `TIME_WAIT`.

## Interview questions

**Q: Why is the TCP handshake three-way and not two-way?**
> Both sides must agree on a starting sequence number and each must confirm the other's was
> received. Two messages confirm only one direction — the client would not have acknowledged the
> server's sequence number, so the server couldn't safely start sending.

**Q: What are sequence and acknowledgement numbers for?**
> SEQ labels the position of the segment's first byte in the sender's stream; ACK tells the sender
> the next byte expected. Together they provide ordering, loss detection, duplicate rejection and
> the basis for flow control.

**Q: Why are initial sequence numbers random?**
> To prevent blind injection. A predictable ISN would let an off-path attacker forge segments that
> the receiver accepts as part of the connection.

**Q: What is `TIME_WAIT` and why does it exist?**
> After closing, the initiating side holds the socket for roughly twice the maximum segment lifetime
> so that delayed duplicates from the old connection can't be misinterpreted as belonging to a new
> connection on the same 4-tuple. It's why you sometimes can't immediately rebind a port after
> restarting a service.

**Q: Why does closing take four messages?**
> TCP is full-duplex and each direction closes independently. One side sends FIN and gets an ACK,
> but the other may still have data to send; it sends its own FIN later, which is acknowledged in
> turn.
