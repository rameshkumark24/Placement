# Day 377

**L-377** · Kubernetes I — the reconciliation loop, and the four objects that matter

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Kubernetes is one idea repeated: you declare desired state, and a controller loops forever
> trying to make reality match.**
>
> Deployments, Services, autoscalers, ingress — **every one of them is that same loop with different
> nouns.** Once you see it, the API stops being a list of YAML kinds and becomes predictable.

---

# Part 1 — ⭐⭐ The one idea

```
⭐ for (;;) {
⭐   desired = apiServer.read(spec);      ⭐ what you asked for
⭐   actual  = observe();                 ⭐ what exists
⭐   if (desired != actual) act();        ⭐ move one step closer
⭐   report(status);                      ⭐ and write down what is true
⭐ }
```

| ⭐ Consequence | |
|---|---|
| ⭐⭐ **Declarative, not imperative** | ⭐⭐ you never say "start a pod" — you say "three should exist" |
| ⭐ **Self-healing is free** | ⭐ a deleted pod is just a mismatch the loop corrects |
| ⭐ **Everything is eventually consistent** | ⭐⭐ `kubectl apply` returns before anything has happened |
| ⭐ `status` vs `spec` | ⭐ **spec is your intent; status is the controller's report** |
| Extensible | a custom controller is the same loop over your own CRD |

> **⭐ The mental habit this buys: when something is wrong, ask "which controller owns this, and what
> does it think?"** Almost all debugging is reading `status` and events, **not reading logs** —
> `kubectl describe` before `kubectl logs`.

# Part 2 — ⭐ The objects you actually use

```
⭐ Deployment ──manages──► ReplicaSet ──manages──► Pods
⭐      ⭐ rollout, history, rollback        ⭐ "N copies exist"   ⭐ one or more containers
⭐
⭐ Service ──selects pods by LABEL──► a stable virtual IP + DNS name
⭐ Ingress ──routes host/path──► Service        ⭐ (the gateway of Day 341)
```

| Object | ⭐ Job |
|---|---|
| ⭐ **Pod** | ⭐ the unit of scheduling — **containers that share a network namespace and lifecycle** |
| ⭐ ReplicaSet | keeps N pods running — **you never create one directly** |
| ⭐ **Deployment** | ⭐ rollouts, rollback, history — **the thing you actually write** |
| ⭐ **Service** | ⭐⭐ **a stable name and IP over a changing set of pods** — this is service discovery (Day 341) |
| Ingress / Gateway | HTTP routing, TLS, host and path rules |
| ConfigMap / Secret | ⭐ config and credentials as env vars or mounted files (Day 364) |

⚠️ **A Service selects pods by label, not by Deployment.** Two Deployments whose pods share a label
**both receive traffic** — which is either an elegant canary mechanism or a very confusing bug,
depending on whether you meant it.

⚠️ **And Secrets are base64, not encryption** (Day 372). Anyone with read access to the namespace has
the plaintext. **Enable encryption at rest, restrict RBAC, and treat them as "not in git" rather than
"protected".**

# Part 3 — ⭐⭐ Probes: the three that behave differently

| Probe | ⭐ Failing means | ⭐ Consequence |
|---|---|---|
| ⭐⭐ **liveness** | "I am broken" | ⭐⭐ **the container is KILLED and restarted** |
| ⭐⭐ **readiness** | "do not send me traffic" | ⭐ removed from the Service's endpoints — **not killed** |
| ⭐ **startup** | "still booting" | ⭐⭐ **suspends liveness until it passes — the JVM's friend** |

```yaml
⭐ startupProbe:                              ⭐⭐ WITHOUT THIS: a slow JVM start is a restart loop
⭐   httpGet: { path: /actuator/health/liveness, port: 8080 }
⭐   failureThreshold: 30
⭐   periodSeconds: 5                          ⭐ ⇒ up to 150 s to start, then liveness takes over
⭐ livenessProbe:
⭐   httpGet: { path: /actuator/health/liveness, port: 8080 }   ⭐⭐ SHALLOW — see below
⭐ readinessProbe:
⭐   httpGet: { path: /actuator/health/readiness, port: 8080 }  ⭐ may consider dependencies
```

⚠️ **The most damaging Kubernetes misconfiguration is a liveness probe that checks the database.**
The database blips → **every pod fails liveness → every pod is killed → the whole fleet restarts
simultaneously** → and when the database returns it is met by a cold-start stampede. **Liveness
answers "is this process wedged?" and nothing else** (Day 143, Day 325).

⚠️ **Readiness failing on every pod removes every endpoint**, so the Service has nowhere to send
traffic — the death spiral of Day 325, expressed in Kubernetes objects. **Some ingress setups can be
configured not to drop the last endpoints; know whether yours does.**

> **⭐ Spring Boot gives you `/actuator/health/liveness` and `/readiness` separately** (Day 143). **Use
> both, and do not point liveness at the aggregate `/health`**, which includes every dependency
> indicator by default.

# Part 4 — ⭐⭐ Requests, limits, and the CPU argument

```yaml
⭐ resources:
⭐   requests: { memory: "512Mi", cpu: "500m" }   ⭐⭐ SCHEDULING + guaranteed share
⭐   limits:   { memory: "512Mi", cpu: "2" }      ⭐ the ceiling
```

| ⭐ Field | ⭐ Meaning |
|---|---|
| ⭐⭐ **requests** | ⭐⭐ **what the scheduler reserves — this is what decides where a pod lands** |
| ⭐ **memory limit** | ⭐⭐ **exceed it and you are OOMKilled — exit 137** (Day 361) |
| ⭐ **cpu limit** | ⭐⭐ **throttling, not killing** — and it is contentious |

## ⭐ QoS classes decide who dies first

| Class | ⭐ Condition | ⭐ Eviction order under node pressure |
|---|---|---|
| ⭐ **Guaranteed** | requests == limits, both set | ⭐⭐ **evicted last** |
| Burstable | requests < limits | middle |
| ⭐ **BestEffort** | ⭐ nothing set | ⭐⭐ **evicted first** |

> **⭐ "We did not set resources" therefore means "evict us first, and schedule us anywhere."** For
> anything that matters, **always set requests** — it is the field that decides both placement and
> survival.

## ⭐⭐ The CPU limits argument, honestly

```
⭐ FOR limits:    predictable, prevents one pod starving a node, enforces fairness
⭐ ⭐⭐ AGAINST:    ⭐ CPU limits THROTTLE (Day 361) — a pod is frozen for part of each 100 ms period
⭐                 ⭐⭐ so a bursty JVM (GC, JIT, startup) gets latency SPIKES even when the node is idle
⭐
⭐ ⭐ The common position: ⭐⭐ ALWAYS set memory limits (OOM is unbounded and dangerous),
⭐ ⭐ and often set only CPU REQUESTS, relying on shares for fairness.
```

⚠️ **Be able to argue both sides.** Removing CPU limits improves tail latency and risks a noisy
neighbour; **keeping them makes behaviour reproducible and risks throttling something that had
capacity available.** The answer depends on whether the cluster is shared and how bursty the workload
is — **and `container_cpu_cfs_throttled_seconds_total` is the metric that tells you which problem you
actually have.**

**⭐ And the JVM link (Day 361): the memory limit is what `MaxRAMPercentage` is a percentage of.**
Requests without limits means the JVM sees the node's memory — **and sizes its heap for a machine it
does not own.**

## ⭐ Debugging, in order

```
⭐ kubectl get pods                    ⭐ what state? CrashLoopBackOff, Pending, ImagePullBackOff
⭐ ⭐⭐ kubectl describe pod <name>      ⭐⭐ EVENTS — scheduling failures, probe failures, OOMKills
⭐ kubectl logs <name> --previous      ⭐ the CRASHED container's logs, not the new one
⭐ kubectl get events --sort-by=...    ⭐ cluster-wide context
⭐ kubectl exec / debug                last resort
```

| ⭐ State | ⭐ Usual cause |
|---|---|
| ⭐ `Pending` | ⭐ **no node satisfies the requests** — read the events |
| ⭐ `CrashLoopBackOff` | ⭐ the app exits, or **liveness fails during startup** (no startup probe) |
| `ImagePullBackOff` | wrong tag, or registry credentials |
| ⭐ `OOMKilled` | ⭐ exit 137 — memory limit vs JVM heap (Day 361) |
| ⭐ **Running but no traffic** | ⭐⭐ **readiness failing, or the Service's label selector does not match** |

> **⭐ `--previous` is the flag people forget.** When a pod is crash-looping, **the logs you want
> belong to the container that already died**, not the one currently starting.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Thinking imperatively | ⭐ you fight the controller instead of changing the spec |
| ⭐ Reading logs before `describe` | ⭐ events hold the actual reason |
| ⭐⭐ **Liveness probe checking dependencies** | ⭐⭐ **one database blip restarts the entire fleet** |
| ⭐ **No startup probe on a JVM** | ⭐⭐ a slow start becomes a restart loop |
| ⭐ Liveness pointed at aggregate `/health` | it includes every dependency |
| ⭐ **No resource requests** | ⭐ BestEffort — evicted first, scheduled anywhere |
| ⭐ **No memory limit** | ⭐ the JVM sizes its heap for the node |
| ⭐ CPU limits set without measuring throttling | ⭐ latency spikes on an idle node |
| ⭐ **Overlapping label selectors** | two Deployments serving one Service by accident |
| ⭐ Treating Secrets as encrypted | base64 |
| ⭐ Forgetting `--previous` | you read the wrong container's logs |
| Creating ReplicaSets directly | you lose rollout and rollback |

## Interview questions

**Q: What is the core idea of Kubernetes?**
A reconciliation loop. You declare desired state and a controller runs forever comparing it to
reality and taking one step to close the gap. Deployments, Services, autoscalers and ingress are all
that same loop with different nouns. It is why self-healing is free — a deleted pod is just a
mismatch — and why everything is eventually consistent, since `apply` returns before anything has
happened.

**Q: What is the difference between liveness and readiness?**
Failing liveness kills and restarts the container; failing readiness only removes it from the
Service's endpoints. That difference is why a liveness probe must never check dependencies — if it
does, a database blip fails every pod's liveness, the whole fleet restarts simultaneously, and the
recovering database is met by a cold-start stampede. Liveness answers "is this process wedged?" and
nothing else.

**Q: Why does a Spring Boot pod crash-loop on a slow node?**
Usually no startup probe. A JVM can take thirty or forty seconds to become ready, and without a
startup probe the liveness check fails during boot and the container is killed before it ever
finishes starting. A startup probe with a generous failure threshold suspends liveness until the app
is up, and then normal liveness semantics take over.

**Q: Requests or limits?**
Requests are what the scheduler reserves and what determines placement and QoS class — a pod with
nothing set is BestEffort and gets evicted first. Memory limits I always set, because exceeding
memory is an OOMKill and unbounded growth is dangerous, and the limit is also what
`MaxRAMPercentage` is a percentage of. CPU limits are contentious: they throttle rather than slow, so
a bursty JVM gets latency spikes even on an idle node. Many teams set CPU requests only and rely on
shares, and I would check the CFS throttling metric before deciding.

**Q: A pod is Running but gets no traffic.**
Readiness is failing, or the Service's label selector does not match the pod's labels. Those are the
two causes, and `describe` on both the pod and the Service tells you which. It is also worth checking
whether another Deployment shares the label, because a Service selects by label rather than by
Deployment, and overlapping selectors send traffic somewhere you did not intend.

## Mini task

1. Deploy your flagship as a **Deployment + Service + Ingress**. Then **delete a pod and watch it
   return** — that is the loop.
2. ⭐ Run `kubectl describe` on a healthy pod and **read the whole event list.** Learn what normal
   looks like.
3. ⭐⭐ Point **liveness at a dependency check**, stop the database, and **watch every pod restart.**
   Split into liveness and readiness and repeat.
4. ⭐ Remove the **startup probe** and deploy on a throttled node. **Reproduce the crash loop.**
5. ⭐ Deploy with **no resources set.** Confirm the QoS class is BestEffort, then fill the node and
   **watch it get evicted first.**
6. ⭐⭐ Set a **memory limit with no JVM flags** and reproduce OOMKilled (exit 137). Add
   `MaxRAMPercentage`.
7. ⭐⭐ Set a **CPU limit of 500m**, run a CPU-bound load, and **graph
   `container_cpu_cfs_throttled_seconds_total` against p99 latency.** Remove the limit and compare.
8. ⭐ Give two Deployments an **overlapping label** and watch one Service feed both.
9. ⭐ Break a Service's **selector** and diagnose "Running but no traffic" from `describe` alone.
10. ⭐ Crash-loop a pod and read its logs **with and without `--previous`.**

## 🎙️ Articulation drill

**Three minutes:** *"A pod is in CrashLoopBackOff. Debug it."*

**⭐ The order is the answer: `describe` first for events — OOMKilled, probe failure, image pull,
scheduling — then `logs --previous`, because the current container has not failed yet.** Then the
three usual causes: **no startup probe on a slow JVM, a memory limit without JVM container flags, or
a liveness probe checking a dependency.**

**⭐ The marker is `--previous` and reading events before logs.** Both are small, both are what people
actually do wrong, **and both signal that you have debugged a cluster rather than read about one.**
