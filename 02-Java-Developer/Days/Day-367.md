# Day 367

**L-367** · Nginx — reverse proxy, TLS termination, and the slow client

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Ask most engineers why there is a reverse proxy in front of the app and they say "TLS". That
> is the least interesting reason.**
>
> The best one is invisible: **without buffering, a client on a bad mobile connection occupies one of
> your application threads for the entire duration of its slow upload** — and a hundred such clients
> can exhaust a thread pool that has nothing else wrong with it.

---

# Part 1 — ⭐ Why a reverse proxy at all

| ⭐ Reason | ⭐ Detail |
|---|---|
| ⭐⭐ **Buffering slow clients** | ⭐⭐ **the proxy absorbs slow reads and writes so app threads are never held by a slow network** |
| ⭐ **TLS termination** | ⭐ certificates, protocols and ciphers in one place, not in every service |
| ⭐ **Static and media files** | ⭐ served by C at kernel speed instead of by a JVM thread |
| ⭐ Connection management | keep-alive to clients, pooled connections upstream |
| ⭐ **Edge rate limiting** (Day 336) | reject before your application spends anything |
| Routing, canaries, path splitting | one hostname, several services |
| Compression, caching, request-id injection | cheap at the edge |
| ⭐ **A place to fail gracefully** | a maintenance page when everything behind it is down |

> **⭐ The slow-client argument in one sentence: a request that takes 30 seconds to arrive costs the
> proxy a few kilobytes of buffer and costs the application nothing, because the app only sees the
> request once it is complete.** Without it, that same request holds a Tomcat thread for 30 seconds
> — **which is Day 322's Little's Law with W set by the client's network rather than your code.**

⚠️ **This is the mechanism behind Slowloris**, where an attacker opens many connections and sends
headers a byte at a time. **A buffering proxy makes it a non-event; a bare application server does
not.**

# Part 2 — ⭐ The configuration that matters

```nginx
upstream app {
    ⭐ least_conn;                            ⭐ better than round robin for variable requests (Day 325)
    server app:8080 max_fails=3 fail_timeout=15s;
    ⭐ keepalive 32;                          ⭐⭐ reuse upstream connections — big latency win
}

server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ⭐ ssl_protocols TLSv1.2 TLSv1.3;         ⭐ nothing older
    ssl_session_cache shared:SSL:10m;

    ⭐ add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location / {
        proxy_pass http://app;
        ⭐ proxy_http_version 1.1;            ⭐⭐ REQUIRED for upstream keepalive to work
        ⭐ proxy_set_header Connection "";     ⭐⭐ and so is this — 1.0 sends `close`

        ⭐ proxy_set_header Host              $host;
        ⭐ proxy_set_header X-Real-IP         $remote_addr;
        ⭐ proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        ⭐ proxy_set_header X-Forwarded-Proto $scheme;   ⭐⭐ or your app builds http:// redirect URLs

        ⭐ proxy_connect_timeout 3s;
        ⭐ proxy_read_timeout   25s;          ⭐⭐ must EXCEED the app's own timeout (Day 325)
        ⭐ client_max_body_size 20m;          ⭐⭐ the default is 1 MB — the classic 413
    }
}
```

## ⭐⭐ The forwarded-headers trap

```
⭐ Your app sees the PROXY's IP and http:// unless you both SET and TRUST the headers.
⭐ ⇒ ⭐ every log line and rate limit uses one IP — the proxy's
⭐ ⇒ ⭐⭐ redirects and generated links come out as http://, causing loops behind TLS
⭐
⭐ Nginx: set X-Forwarded-For / -Proto / Host   ⭐ (above)
⭐ Spring: server.forward-headers-strategy=framework   ⭐ (Day 155)
```

⚠️ **And the security half nobody mentions: trusting `X-Forwarded-For` unconditionally lets a client
forge its own IP.** Only trust it from known proxy addresses — **otherwise your IP-based rate limiting
and audit logs are attacker-controlled.**

⚠️ **`client_max_body_size` defaults to 1 MB**, so a file upload larger than that returns a 413 that
never reaches your application. **It is the single most common "works locally, fails behind the
proxy" bug.**

# Part 3 — ⭐ TLS, properly

| ⭐ Item | ⭐ Detail |
|---|---|
| ⭐ **Certificates** | ⭐ Let's Encrypt via certbot or the ACME module — **and automated renewal, tested** |
| ⭐⭐ **Renewal failure is a total outage** | ⭐⭐ **alert on days-to-expiry, do not trust the cron** |
| ⭐ Protocols | ⭐ TLS 1.2 and 1.3 only |
| ⭐ **HSTS** | ⭐ tells browsers to never use http — **`includeSubDomains` is a commitment you cannot undo quickly** |
| OCSP stapling | the proxy fetches revocation status so clients do not have to |
| ⭐ **Full chain, not just the leaf** | ⭐ a missing intermediate works in browsers and **fails in Java clients** |
| ⭐ Redirect 80 → 443 | ⭐ and serve the ACME challenge path over http |

⚠️ **The missing-intermediate bug is worth its own note because it is so confusing:** browsers often
fetch the missing intermediate certificate themselves, **so the site looks fine while every JVM client
fails with a certificate path error.** Always test with `openssl s_client`, not only a browser.

## ⭐ WebSockets need explicit handling

```nginx
location /ws {
    proxy_pass http://app;
    ⭐ proxy_http_version 1.1;
    ⭐ proxy_set_header Upgrade $http_upgrade;      ⭐⭐ without these the upgrade fails
    ⭐ proxy_set_header Connection "upgrade";
    ⭐ proxy_read_timeout 3600s;                    ⭐⭐ or an idle socket is closed after 60 s
}
```

> **⭐ The 60-second default read timeout silently killing idle WebSocket connections is a classic**,
> and it presents as "the app randomly disconnects users" (Day 352). **Long-lived connections need an
> explicit timeout and application-level pings.**

# Part 4 — ⭐ Edge behaviours worth configuring

| Feature | ⭐ Why |
|---|---|
| ⭐ **Rate limiting** — `limit_req_zone` | ⭐ reject floods before your app spends a thread (Day 336) |
| ⭐ Connection limits — `limit_conn` | one client cannot hold hundreds of sockets |
| ⭐ **`gzip` / `brotli`** | ⭐ JSON compresses 5–10×; **do it here, not in the JVM** |
| ⭐ Static file serving | ⭐ **never let the application serve assets** (Day 327) |
| ⭐ **Request id injection** | ⭐ `$request_id` into a header — **the correlation id starts at the edge** (Day 338) |
| ⭐ `proxy_next_upstream` | retry an idempotent request on another backend |
| ⭐ **A custom 502/503 page** | ⭐ users see something honest when everything behind is down |
| Access logs off for health checks | otherwise probes dominate your logs |

⚠️ **Timeout ordering must be deliberate** (Day 325): **client > proxy > application > downstream.**
If the proxy times out first, the application keeps working on a request nobody is waiting for —
burning a thread, and possibly being retried on top of.

## ⭐ Reload, and the thing that makes Nginx pleasant

```
⭐ nginx -t                ⭐⭐ ALWAYS validate before reloading
⭐ nginx -s reload          ⭐ graceful: new workers take new connections, old ones drain
```

**⭐ A reload never drops a connection**, which is why config changes and certificate renewals are
routine rather than a maintenance window. **`nginx -t` in CI, before deploying the config, is the
cheap habit that prevents a self-inflicted outage.**

## ⭐ And the honest scoping

> **⭐ On Kubernetes you usually do not run Nginx yourself — an Ingress controller does this**
> (frequently Nginx underneath). **The concepts are identical**; the configuration lives in Ingress
> objects instead. **Say that**, because it shows you know where the knowledge transfers rather than
> assuming one deployment model.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Thinking a proxy is only for TLS | ⭐⭐ buffering is the better reason |
| ⭐⭐ Missing `proxy_http_version 1.1` + empty `Connection` | ⭐⭐ **upstream keepalive silently does nothing** |
| ⭐⭐ **Forwarded headers not set or not trusted** | ⭐⭐ one IP in every log; http:// redirect loops |
| ⭐ Trusting `X-Forwarded-For` from anywhere | ⭐ clients forge their own IP |
| ⭐ **Default `client_max_body_size`** | ⭐ 413 on any upload over 1 MB |
| ⭐ **Proxy timeout shorter than the app's** | ⭐ orphaned work, amplified load |
| ⭐ No WebSocket upgrade headers or timeout | ⭐ upgrades fail; idle sockets closed at 60 s |
| ⭐ Only the leaf certificate | ⭐⭐ browsers fine, Java clients fail |
| ⭐ **Unmonitored certificate renewal** | ⭐⭐ a total outage on a known date |
| `includeSubDomains` without meaning it | you cannot undo it quickly |
| Reloading without `nginx -t` | a syntax error takes the site down |
| Serving static assets from the app | JVM threads doing a file server's job |
| Logging health checks | probes drown the access log |

## Interview questions

**Q: Why put Nginx in front of a Spring Boot app?**
The best reason is buffering. Without it, a client on a slow connection holds an application thread
for the whole duration of its upload or download, so a hundred slow clients exhaust a pool that is
otherwise healthy — that is Little's Law with the time set by someone else's network. The proxy
absorbs that for a few kilobytes each. TLS termination, static files, edge rate limiting and a place
to serve an honest error page are all real, but they come second.

**Q: Your app logs show every request coming from one IP and your redirects are http.**
Forwarded headers. The proxy is not setting `X-Forwarded-For` and `X-Forwarded-Proto`, or the
application is not configured to trust them — Spring needs a forward-headers strategy. And the
security half matters: those headers should only be trusted from known proxy addresses, otherwise a
client can forge its own IP and your rate limiting and audit logs become attacker-controlled.

**Q: Uploads work locally and fail behind the proxy with a 413.**
`client_max_body_size` defaults to one megabyte, so the proxy rejects the request before your
application ever sees it. It is the most common works-locally-fails-in-production proxy bug, and it
pairs with checking that the proxy read timeout exceeds the application's own timeout, so a slow
upload is not severed halfway.

**Q: WebSocket connections drop after about a minute. Why?**
The default proxy read timeout is sixty seconds, and an idle WebSocket looks like an idle HTTP
response. You need the upgrade headers so the handshake works at all, an explicit long read timeout,
and application-level pings so the connection is never actually idle. It presents as "users randomly
get disconnected", which sends people looking in the wrong place entirely.

**Q: The certificate works in Chrome but Java clients fail.**
Almost always a missing intermediate — you served only the leaf certificate. Browsers frequently
fetch the missing intermediate themselves, so the site looks perfect while every JVM client fails
certificate path validation. The fix is serving the full chain, and the habit is testing with
`openssl s_client` rather than trusting a browser.

## Mini task

1. **Put Nginx in front of your app** with two replicas (Day 366) and confirm both receive traffic.
2. ⭐⭐ **Reproduce the slow-client problem**: send a request with a deliberately slow body directly to
   the app, and watch a thread be held. **Then send it through Nginx and confirm the app is not
   affected.**
3. ⭐ Remove `proxy_http_version 1.1` and the empty `Connection` header. **Measure upstream connection
   churn** with and without.
4. ⭐ Drop the forwarded headers and **watch every log line show the proxy IP.** Add them, configure
   Spring, and confirm real client IPs.
5. ⭐ Try to forge `X-Forwarded-For` from a client and **confirm your app believes it.** Then restrict
   trust to the proxy.
6. ⭐ Upload a 5 MB file with the default body size limit and **reproduce the 413.**
7. ⭐ Set the proxy read timeout **below** the app timeout and observe orphaned work under load.
8. ⭐ Proxy a WebSocket **without** upgrade headers, then with them, then **wait 61 seconds idle** and
   watch it drop before fixing the timeout.
9. ⭐ Serve **only the leaf certificate** and test with a browser and with `openssl s_client` — see
   them disagree.
10. Add edge rate limiting and confirm rejections never reach the application.
11. ⭐ Inject `$request_id` and **trace one request from the access log into application logs**
    (Day 338).
