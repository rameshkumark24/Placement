# Day 354

**L-354** · Design 10 — file storage and sync

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Dropbox looks like Day 327's object storage with a folder tree on top. The difference is one
> word: sync.**
>
> Files change. Devices are offline. Two people edit the same document. **And the design that makes
> all of it affordable is a single idea — stop thinking about files and start thinking about
> chunks.**

---

# Part 1 — ⭐ Requirements and estimates

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| Upload, download, delete | ⭐⭐ **sync latency < 10 s for a small change** |
| ⭐ **Sync across devices, including after being offline** | ⭐ **never lose a byte** — durability first |
| ⭐ Version history | ⭐ bandwidth efficiency — **the mobile constraint** |
| Sharing and permissions | availability 99.99% |
| ⭐ **Conflict handling** | ⭐ resumable transfers on flaky networks |

```
⭐ ESTIMATE
⭐   50M users · 50 GB average ⇒ ⭐⭐ 2.5 EB raw — ⭐ before dedup
⭐   10M active/day · 20 file changes each ⇒ 200M changes/day ⇒ ⭐ ~2,300/s
⭐   ⭐⭐ NAIVE: a 100 MB file with a 1-byte edit = 100 MB uploaded, EVERY SAVE
⭐   ⭐⭐ CHUNKED: 4 MB chunks ⇒ ⭐ ONE 4 MB chunk uploaded. ⭐ 25× less, and often far more.
```

> **⭐ That last comparison is the design.** Sync is a bandwidth problem, and **chunking is what turns
> an unaffordable product into an affordable one** — everything else today follows from it.

# Part 2 — ⭐⭐ The deep dive: chunks

```
⭐ file ──split──► [c1][c2][c3][c4] ──hash each──► sha256 per chunk
⭐ ⭐ METADATA:  file → ordered list of chunk hashes
⭐ ⭐ BLOCKS:    chunkHash → bytes, in object storage (content-addressed)
```

| ⭐ What chunking buys | ⭐ How |
|---|---|
| ⭐⭐ **Delta sync** | ⭐⭐ **upload only chunks whose hash changed** |
| ⭐ **Deduplication** | ⭐ the same chunk stored once — **globally, across all users** |
| ⭐ **Resumability** | a dropped connection loses one chunk, not the file |
| ⭐ **Version history is nearly free** | ⭐ a version is just a different *list* of chunk hashes |
| ⭐ Parallel transfer | many chunks at once |
| Integrity | the hash verifies the bytes |

## ⭐ Fixed vs content-defined chunking

```
⭐ FIXED 4 MB boundaries:
⭐   ⭐⭐ INSERT one byte at the start ⇒ every subsequent boundary shifts ⇒ ⭐⭐ EVERY chunk changes.
⭐   ⇒ delta sync gains nothing on inserts.

⭐⭐ CONTENT-DEFINED (rolling hash, e.g. Rabin):
⭐   ⭐ a boundary is placed where the rolling hash matches a pattern
⭐   ⇒ ⭐⭐ an insert shifts only the LOCAL boundary; the rest of the chunks are unchanged.
```

> **⭐ Fixed chunking is fine for appends and in-place edits; content-defined chunking is what
> survives inserts.** Fixed is simpler and Dropbox historically used it; **naming the insert failure
> and the rolling-hash fix is the detail that shows you understand why the choice exists.**

⚠️ **Cross-user dedup carries the same privacy leak as [Day 346](Day-346.md):** if uploading a file
someone else already has completes instantly, **an attacker can confirm a file's existence.** The
mitigations are per-user dedup, or making the client always upload despite the server discarding — and
noting the trade honestly is worth more than either.

# Part 3 — ⭐ The two services, and why they are separate

```
⭐ ⭐ METADATA SERVICE          ⭐ BLOCK SERVICE
⭐   file tree, versions,          chunk bytes in object storage
⭐   chunk lists, permissions      ⭐ presigned direct transfer (Day 327)
⭐   ⭐ small, hot, TRANSACTIONAL   ⭐ enormous, cheap, IMMUTABLE
⭐   ⇒ relational / sharded by user ⇒ content-addressed, no transactions
```

| ⭐ Why split | |
|---|---|
| ⭐⭐ **Completely different profiles** | ⭐ kilobytes and consistency vs petabytes and throughput |
| ⭐ **Bytes never touch your services** | presigned URLs, both directions (Day 327) |
| ⭐ Metadata needs transactions | a rename must be atomic; a chunk does not |
| ⭐ **Blocks are immutable** | ⭐ so they cache perfectly and replicate trivially |

## ⭐ The sync protocol

```
⭐ 1. Client holds a CURSOR — a version marker for its view of the tree
⭐ 2. ⭐ Notification service tells it "something changed" (long poll or push)
⭐ 3. Client asks: "what changed since cursor X?" ⇒ ⭐ a delta of metadata, not files
⭐ 4. Client diffs its local chunk list vs the new one
⭐ 5. ⭐ Downloads only the missing chunks; uploads only its new ones
⭐ 6. Advances the cursor
```

| ⭐ Detail | |
|---|---|
| ⭐⭐ **The cursor makes sync resumable and idempotent** | ⭐ a client that crashes replays from its last cursor |
| ⭐ Notification is a hint, not data | ⭐ **the client always pulls the authoritative delta** |
| ⭐ **Long poll rather than constant polling** | 50M clients polling every 5 s is 10M requests/s for nothing |
| Batching | many small changes coalesce into one delta |

> **⭐ "Notify, then pull" is the pattern to name.** Pushing the change itself means every notification
> must be reliable and ordered; **pushing only "something changed" makes the notification
> disposable** — a lost one costs a few seconds of delay, and the next one fixes it. **That is a
> deliberate reliability simplification.**

# Part 4 — ⭐⭐ Conflicts, and the honest answer

```
⭐ Device A (offline) edits report.docx.  Device B (online) edits report.docx.
⭐ A reconnects. ⭐⭐ Two divergent versions, no common ordering. Now what?
```

| ⭐ Option | ⭐ Verdict |
|---|---|
| ⭐ Last-write-wins | ⭐⭐ **silently destroys someone's work — unacceptable for user files** |
| ⭐ Merge | ⭐⭐ **impossible for binary formats; risky even for text** |
| ⭐⭐ **Keep both — `report (Alice's conflicted copy).docx`** | ⭐⭐ **ugly, honest, and correct — what real products do** |
| Lock files | kills offline editing, the feature you were building |

> **⭐ The principle: when you cannot resolve a conflict correctly, surface it rather than guess.**
> A conflicted copy is a small user annoyance; **a silently discarded afternoon of work is a lost
> customer.** Saying this plainly — and naming that it is what Dropbox actually does — is the mature
> answer.

⚠️ **Collaborative editors are a different product.** Google Docs merges because it uses operational
transforms or CRDTs (Day 331) **over a structured document with a live connection.** That is not
file sync — **it is a different data model, and conflating them is a common interview error.**

**⭐ Detecting the conflict needs versioning:** each file version records its parent. **If two versions
share a parent and neither descends from the other, they are concurrent** — which is Day 348's vector
clock reasoning applied to a file tree.

## ⭐ Sharing, tiering, and what breaks

| Concern | ⭐ Design |
|---|---|
| ⭐ Sharing | ⭐ permissions on the **metadata**; blocks are content-addressed and access is granted by presigned URL |
| ⭐ **A shared folder change** | notify every member's client — **fan-out on the notification, not the data** |
| ⭐ Storage tiering | ⭐ cold chunks to archive; **re-warm delay on first access** |
| ⭐ **Deleting a chunk** | ⭐⭐ reference counting or mark-and-sweep (Day 346) — **the same problem, and here dedup is genuinely worth it** |
| Trash / retention | a delete is a metadata state, not a chunk removal |

```
⭐ Breaks first: ⭐ metadata store hot shards (shard by user) · ⭐ notification fan-out on huge shared
⭐ folders · ⭐ a client with a million files doing a full diff · ⭐ chunk GC falling behind
⭐ MONITOR: ⭐ sync latency p99 · ⭐ bytes uploaded ÷ bytes changed (⭐ the delta-sync efficiency ratio)
⭐          conflicted copies created/day · dedup ratio · ⭐ files synced/min (business metric)
⭐ CUT:     collaborative editing, previews, search inside files, selective sync
⭐ AT 10×:  ⭐ more metadata shards; block storage was never the constraint
```

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Uploading whole files on every change | ⭐⭐ **100 MB for a one-byte edit** |
| ⭐ Fixed chunking with no note on inserts | ⭐ delta sync gains nothing on an insert |
| ⭐ **Bytes through your service** | Day 327 — threads and bandwidth |
| Metadata and blocks in one store | opposite profiles; neither is served well |
| ⭐ **Pushing changes instead of notifying** | every notification must now be reliable and ordered |
| ⭐ Constant polling from 50M clients | 10M requests/s of nothing |
| ⭐⭐ **Last-write-wins on user files** | ⭐⭐ **silently destroyed work** |
| ⭐ Promising a merge for binary files | impossible |
| Confusing file sync with collaborative editing | different data model entirely |
| ⭐ Dedup with no chunk GC plan | orphans, or deleted-live-data |
| Ignoring the cross-user dedup privacy leak | existence confirmation |
| No cursor | sync cannot resume or be made idempotent |

## Interview questions

**Q: What is the core idea?**
Chunking. Files are split into blocks, each hashed and stored content-addressed, and the metadata is
just an ordered list of hashes. That single change gives delta sync — you upload only the chunks
whose hash changed — plus deduplication, resumable transfers, parallel uploads, integrity checking,
and version history almost for free, because a version is a different list over the same immutable
chunks.

**Q: Fixed-size chunks or content-defined?**
Fixed is simpler and fine for appends and in-place edits. It fails on insertion: adding one byte at
the start shifts every boundary, so every chunk hash changes and delta sync gains nothing. A rolling
hash places boundaries based on content, so an insert only disturbs the local boundary. I would start
fixed and move to content-defined if the workload has real insert-heavy files.

**Q: Why separate metadata from blocks?**
Opposite profiles. Metadata is small, hot and transactional — a rename must be atomic — so it wants a
sharded relational store. Blocks are petabytes of immutable content-addressed bytes that want object
storage and a CDN, with clients transferring directly through presigned URLs so the bytes never touch
my services.

**Q: How does a client know something changed?**
A notification tells it *that* something changed, and it then pulls the authoritative delta since its
cursor. Pushing the change itself would make every notification something that must be reliable and
ordered; pushing only a hint makes it disposable, so a lost notification costs a few seconds and the
next one repairs it. The cursor is what makes sync resumable and idempotent after a crash.

**Q: Two devices edit the same file offline. What happens?**
You keep both, as a conflicted copy. Last-write-wins silently destroys someone's work, which is
unacceptable for user files, and merging is impossible for binary formats. Detecting it needs version
parentage — two versions sharing a parent with neither descending from the other are concurrent,
which is vector-clock reasoning on a file tree. And I would separate this from collaborative editing,
which merges only because it is a structured document with a live connection, not a file.

## 🎙️ Articulation drill

**Three minutes:** *"I change one byte in a 100 MB file. Trace what your system does."*

**⭐ The complete trace: re-chunk locally, hash each chunk, compare against the previous chunk list,
upload the single changed chunk directly to object storage, commit a new metadata version pointing at
the new list, notify other devices, and they pull the delta and download one chunk.**

**⭐ The marker is the sentence "the new version is a new list over mostly the same immutable
chunks" — because that is simultaneously the delta sync, the deduplication and the version history,
all falling out of one decision.**
