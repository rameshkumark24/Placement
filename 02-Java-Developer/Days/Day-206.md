# Part 1 — ⭐ Eviction, and the policy that is usually wrong

```
maxmemory 4gb
maxmemory-policy allkeys-lru       # ⭐ the DEFAULT is noeviction — see below
```

| Policy | Behaviour |
|---|---|
| ⭐ **`noeviction`** | ⭐⭐ **THE DEFAULT. Writes fail with an error when full** |
| ⭐ **`allkeys-lru`** | ⭐ evict least-recently-used from all keys. **The cache default** |
| ⭐ **`allkeys-lfu`** | ⭐ least-*frequently*-used. **Often better — see below** |
| `allkeys-random` | random victim. Cheap, surprisingly reasonable |
| `volatile-lru` / `-lfu` / `-ttl` / `-random` | ⭐ only keys **with a TTL** are candidates |

**⭐ `noeviction` being the default is the trap.** A Redis used as a cache with default settings does
not evict — it starts returning `OOM command not allowed when used memory > 'maxmemory'` on every
write. **Your cache stops accepting new entries and your application starts erroring**, which is the
opposite of what a cache should do under pressure.

**⭐ And the `volatile-*` trap is worse:** if some keys have no TTL, they are never eviction
candidates. **When only untagged keys remain, Redis behaves as `noeviction` and writes fail.** A
single forgotten `SET` without a TTL can, over time, fill the instance with unevictable keys.

## ⭐ LRU vs LFU — and why LFU is often the better choice

**⭐ LRU has a known pathology: one large scan evicts your entire working set.** A batch job that
touches a million keys once makes them all "recently used", pushing out the hot keys that serve
production traffic. **Your hit rate collapses and recovers slowly.**

**⭐ LFU tracks access *frequency* with a decaying counter**, so a key touched once by a batch job
never displaces one touched a thousand times an hour.

```
maxmemory-policy allkeys-lfu
lfu-log-factor 10          # ⭐ how quickly the counter saturates
lfu-decay-time 1           # ⭐ minutes before the counter decays — without this, old hot keys never die
```

**⭐ Choose LFU when access is skewed** — which describes almost every real cache, where a small
fraction of keys serve most requests. LRU is fine when recency genuinely predicts reuse, such as
sessions.

⚠️ **⭐ Redis's LRU is approximate**: it samples `maxmemory-samples` keys (default 5) and evicts the
best of that sample, because true LRU would need a linked list touched on every access. **Raising it
to 10 improves accuracy at some CPU cost.** Knowing it is sampled is a good interview detail.

## ⭐ Expiry is lazy plus sampled — not a timer

**⭐ A key with a TTL is not deleted the instant it expires.** Redis removes it either when someone
accesses it (lazy) or when the background cycle samples expired keys (active, ~10 times per second).

**⭐ Two consequences:**

1. **Expired keys still occupy memory** until collected — so `used_memory` can exceed the live
   dataset, and `DBSIZE` can overstate it.
2. **A mass expiry — a million keys with the same TTL — creates a deletion burst** that competes with
   command execution on the single thread (Day 203).

**⭐ Jitter your TTLs.** Day 121 required it to prevent a stampede; here it is *also* required to
avoid an expiry burst. **One habit, two problems solved:**

```java
Duration ttl = Duration.ofMinutes(30).plusSeconds(ThreadLocalRandom.current().nextInt(300));
```

# Part 2 — ⭐ Key design, which decides whether invalidation is possible

```
⭐ {service}:{entity}:{id}:{aspect}
orders:order:8842:summary
orders:customer:1000:recent-orders
orders:ratelimit:ip:203.0.113.7
```

| Rule | Why |
|---|---|
| ⭐ **A consistent, documented scheme** | ⭐ otherwise nobody can find or invalidate anything |
| **Service prefix** | multiple applications sharing one Redis |
| ⭐ **Never a user-supplied value unescaped** | ⭐ `user:{name}` with a name of `1:admin` collides |
| ⭐ **Short but readable** | keys are stored per entry (Day 203); 40 chars × 10M = 400 MB |
| ⭐ **Include the version** | see below |
| ⭐ **Include the tenant** | Day 176 — cross-tenant cache leakage is a breach |

**⭐ The tenant rule deserves emphasis.** A cache key of `product:42` in a multi-tenant system serves
tenant A's product to tenant B. **The key must be `t:{tenantId}:product:42`**, and this is a
security control, not a naming preference — it is Day 176's missing filter in a different store.

## ⭐⭐ Versioned keys — Day 121's pattern, and why it beats deletion

```java
// ❌ delete-based invalidation
redis.delete("product:" + id);              // ⭐ what about product:42:reviews, :price, :related?

// ⭐ version-based invalidation
String v = redis.opsForValue().get("ver:product:" + id);
String key = "product:" + id + ":v" + v;
// invalidate:
redis.opsForValue().increment("ver:product:" + id);   // ⭐⭐ EVERY derived key is now unreachable
```

**⭐ Three properties deletion cannot give you:**

1. ⭐ **Atomic invalidation of every derived key at once** — one increment, no enumeration.
2. ⭐ **No `KEYS`/`SCAN` pattern deletion** — which Day 203 showed is either an outage or slow.
3. ⭐ **Rollback** — decrement the version and the old cache is live again.

**The cost is one extra `GET` per read**, which can be avoided by pipelining it with the value fetch.
**Old versions are evicted naturally by LRU/LFU** since nothing reads them — you do not clean up.

**⭐ A global version is the emergency switch:** `INCR ver:global` invalidates the whole cache
instantly, without `FLUSHALL` blocking the server.

# Part 3 — ⭐ The four failure modes, named

## ⭐ 1. Cache stampede (thundering herd) — Day 121

A hot key expires; 500 concurrent requests all miss and hit the database simultaneously.

| Fix | Note |
|---|---|
| ⭐ **Jittered TTLs** | ⭐ prevents *synchronised* expiry. Always do this |
| ⭐ **A distributed lock on rebuild** | ⭐ one rebuilds, others wait or serve stale (Day 207) |
| ⭐ **Stale-while-revalidate** | ⭐ **best UX** — serve the stale value, refresh in the background |
| Probabilistic early expiry | refresh with rising probability as the TTL nears |

**⭐ Day 168's warning stands: `@Cacheable(sync = true)` locks within one JVM only.** Six instances
means six concurrent rebuilds — better than 500, not a solution.

## ⭐ 2. Cache penetration — requests for things that do not exist

**Repeated lookups for a non-existent id miss the cache *and* miss the database, every time.** If ids
come from the request, that is a trivially exploitable load amplifier.

| Fix | Note |
|---|---|
| ⭐ **Cache the negative result** with a short TTL | ⭐ 30–60 s. Day 168's `unless` decision |
| ⭐ **A Bloom filter** of existing ids | ⭐ definitive "definitely not present"; a few MB for millions |
| Validate the id format first | rejects garbage before any lookup |

## ⭐ 3. Cache avalanche — everything expires at once

**A million keys written at deploy time with the same TTL all expire in the same second.** The
database receives the entire load at once, plus Redis pays a deletion burst.

**⭐ Jitter. Again.** The same one-line habit solves stampede, avalanche and the expiry burst.

## ⭐ 4. Hot key — one key serving a disproportionate share

**A celebrity's profile, or a global config key, can saturate one connection or one cluster node.**

| Fix | Note |
|---|---|
| ⭐ **A local in-process cache in front** (Caffeine) | ⭐ **the best fix** — Redis never sees the traffic |
| Replicate the key across N suffixes | read a random one |
| Read replicas | spreads read load |

**⭐ The two-tier pattern is worth naming**: a small Caffeine cache with a 5-second TTL in front of
Redis absorbs hot keys entirely, and the 5-second staleness is usually acceptable for exactly the
data that is hot.

# Part 4 — Operating a cache

## ⭐ The metrics that tell you it is working

```
INFO stats
keyspace_hits:8234211
keyspace_misses:412093              ⭐ hit ratio = hits/(hits+misses) → 95.2%
evicted_keys:0                      ⭐⭐ above zero = maxmemory reached
expired_keys:1284213
instantaneous_ops_per_sec:42311
```

| Metric | Reading |
|---|---|
| ⭐ **Hit ratio** | ⭐ below ~80% means the TTL is too short, keys are wrong, or the cache is undersized |
| ⭐ **`evicted_keys` > 0** | ⭐ **you are at `maxmemory`** — the working set does not fit |
| `expired_keys` | normal TTL turnover |

**⭐ `evicted_keys` rising is not automatically bad** — it means the cache is full and doing its job.
**It is bad when the hit ratio falls with it**, which means you are evicting things you still need.
Track both together.

## ⭐ The cache must never be required

**Day 168's `CacheErrorHandler`, restated as an architecture rule:**

> **⭐ Redis being down must degrade you to a slow application, never a broken one.**

That means: every cache read falls through to the source on failure, timeouts are short (Day 154 —
Redis is a network call), and **the system has been tested with Redis stopped, under load.**

**⭐ If flushing the cache under production load takes the database down, the cache is not a cache —
it is an undeclared dependency**, and that is a capacity problem wearing a performance costume.

## ⭐ What not to cache

| Do not cache | Why |
|---|---|
| ⭐ Data that changes on nearly every read | invalidation cost exceeds the benefit |
| ⭐ Cheap queries | ⭐ a primary-key lookup on a cached page is already sub-millisecond |
| ⭐ **Authorization decisions** | ⭐ a stale permission is a security bug (Day 174) |
| Anything where staleness has legal consequences | balances, medical data |
| ⭐ **A slow query you have not tried to fix** | Day 167 — a cache is not an index |

**⭐ The last one is Day 167's argument restated**: caching a slow query means the first request is
still slow, every cold cache is still slow, and you have added invalidation complexity to avoid a
one-line fix.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Leaving `maxmemory-policy` at `noeviction` | ⭐ writes fail instead of evicting |
| `volatile-*` with untagged keys | ⭐ effectively `noeviction` over time |
| LRU where LFU fits | one batch scan evicts the working set |
| ⭐ No TTL jitter | stampede, avalanche and an expiry burst |
| Expecting expiry to be instant | it is lazy plus sampled |
| ⭐ No tenant in the key | ⭐ cross-tenant leakage — a breach |
| Unescaped user input in keys | key collisions |
| ⭐ Delete-based invalidation of derived keys | you cannot enumerate them safely |
| `KEYS pattern` to invalidate | Day 203's outage |
| Not caching negatives | penetration |
| ⭐ Relying on `sync = true` in a cluster | per-JVM only |
| No local cache for hot keys | one key saturates a node |
| ⭐ Cache failure propagating to the user | Day 168 |
| ⭐ Never testing with Redis down | the cache is an undeclared dependency |
| Caching authorization decisions | a stale permission is a security bug |

## Interview questions

**Q: What is the default eviction policy, and why does that matter?**
`noeviction` — so a Redis at `maxmemory` starts rejecting writes with an OOM error instead of
evicting. A cache with default settings stops accepting entries and starts erroring, which is exactly
backwards. For a cache I set `allkeys-lru` or `allkeys-lfu`.

**Q: LRU or LFU?**
LFU for most caches, because access is skewed and LRU has a known pathology: one batch job touching a
million keys makes them all recently used and evicts the working set that serves production. LFU
tracks decaying frequency, so a key touched once never displaces one touched a thousand times. And
Redis's LRU is approximate anyway — it samples a few keys and evicts the best of the sample.

**Q: How do you invalidate a cached entity with several derived keys?**
Versioned keys. The key includes a version, and invalidation is one `INCR` on the version — every
derived key becomes unreachable at once, with no enumeration, no `SCAN`, and no pattern delete. Old
versions are evicted naturally, and decrementing the version rolls the invalidation back.

**Q: Name the cache failure modes.**
Stampede — a hot key expires and hundreds of requests rebuild it simultaneously. Penetration —
repeated requests for a non-existent key miss both layers, which is exploitable if ids come from the
request. Avalanche — a million keys expiring in the same second. And hot key — one key saturating a
node, best fixed with a small in-process cache in front of Redis.

**Q: What must be true about a cache architecturally?**
That it can go away. Redis being down degrades me to a slow application, never a broken one — short
timeouts, fall through to the source, and an error handler that logs rather than rethrows. And I test
it by flushing under production load; if the database falls over, the cache was an undeclared
dependency and I have a capacity problem, not a caching one.

## Mini task

1. Set `maxmemory` small with the default policy. Fill it and **watch writes fail with OOM.** Switch
   to `allkeys-lru`.
2. Set `volatile-lru` and write keys with no TTL until full. **Confirm writes fail.**
3. Load a skewed workload (80% of hits on 5% of keys). Measure the hit ratio under LRU, then run a
   full-keyspace scan job, and **watch the hit ratio collapse.** Repeat under LFU.
4. Set `maxmemory-samples` to 2 then 10 and compare eviction quality on a known access pattern.
5. Write 1M keys with the same TTL. **Watch the expiry burst** in `expired_keys` and latency. Add
   jitter and repeat.
6. Implement versioned keys. Cache three derived keys, invalidate with one `INCR`, and confirm all
   three miss. **Then decrement and confirm they are live again.**
7. Reproduce a stampede: 500 concurrent requests on an expiring hot key. Count database queries. Add
   jitter, then a lock, then stale-while-revalidate. **Four numbers.**
8. Reproduce penetration with 10,000 requests for non-existent ids. Add negative caching, then a
   Bloom filter.
9. Create a hot key taking 40% of traffic. Add a 5-second Caffeine cache in front. **Compare Redis
   ops/sec.**
10. **Stop Redis under production-like load.** Confirm the application degrades rather than failing.
    Then `FLUSHALL` under load and watch the database.

## 🎙️ Articulation drill

Two minutes: **"How do you design a caching layer on Redis?"**

Key scheme first, and make the point that it is a design decision rather than a naming one — versioned
keys so invalidation is one increment rather than an enumeration you cannot safely perform, and the
tenant in the key because a shared key is a cross-tenant leak. Eviction policy set explicitly, with
LFU justified by LRU's batch-scan pathology. Jittered TTLs, and note that one habit prevents
stampede, avalanche and an expiry burst. Close on the architectural rule: the cache must be able to
disappear, and you only know that if you have flushed it under load.
