# Day 365

**L-365** · Docker Compose — and the gap between dev and production

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Compose exists so that "clone the repo and run one command" produces a working system. That is
> a real and underrated engineering deliverable.**
>
> It is also where two traps live: **`depends_on` does not mean "wait until it works"**, and a
> Compose setup that looks nothing like production teaches you habits you will have to unlearn.

---

# Part 1 — ⭐ What Compose is for

| ⭐ Good at | ⭐ Not for |
|---|---|
| ⭐⭐ **Local development — one command, whole stack** | ⭐ multi-host orchestration |
| ⭐ **Integration testing in CI** | ⭐ rolling updates, autoscaling, self-healing |
| ⭐ A single-host deployment for something small | ⭐⭐ **anything needing zero-downtime deploys** |
| ⭐ **Documenting the runtime shape of the system** | large fleets |

> **⭐ The underrated benefit: the Compose file is executable documentation.** It states what the
> system is made of, what depends on what, which ports matter and what configuration exists —
> **and unlike a README it cannot silently go out of date, because it is what people run.**

```yaml
services:
  app:
    build: .
    ports: ["8080:8080"]
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/app   # ⭐ service name, not localhost
    depends_on:
      postgres: { condition: service_healthy }      # ⭐⭐ THE important part — see Part 2
      redis:    { condition: service_started }

  postgres:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: dev }          # ⭐ a DEV password, and it looks like one
    volumes: ["pgdata:/var/lib/postgresql/data"]     # ⭐ named volume (Day 364)
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

  redis:
    image: redis:7
    command: ["redis-server", "--save", "60", "1"]

volumes: { pgdata: }
```

# Part 2 — ⭐⭐ `depends_on` is the trap

```yaml
⭐ ✗ depends_on: [postgres]
⭐   ⇒ ⭐⭐ Compose starts postgres FIRST, then immediately starts app.
⭐   ⇒ ⭐⭐ "Started" means the PROCESS launched — NOT that it accepts connections.
⭐   ⇒ ⭐ Postgres takes 3–8 seconds to be ready. Your app crashes on startup.

⭐ ✓ depends_on:
⭐     postgres: { condition: service_healthy }
⭐   ⇒ ⭐ waits for the HEALTHCHECK to pass
```

| ⭐ Condition | ⭐ Meaning |
|---|---|
| `service_started` | ⭐ the container was started — **almost never what you want for a database** |
| ⭐⭐ **`service_healthy`** | ⭐⭐ **its healthcheck passes — requires the dependency to define one** |
| `service_completed_successfully` | ⭐ for one-shot init/migration containers |

⚠️ **The historical workaround was `wait-for-it.sh` or a retry loop in an entrypoint. Healthcheck
conditions replaced it — but the deeper lesson survives: your application should tolerate its
dependencies being unavailable at startup anyway**, because in production nothing guarantees ordering
(Day 339). **Compose ordering is a convenience, not a correctness mechanism.**

> **⭐ Say both halves in an interview: "I use `condition: service_healthy` locally, and I also make
> the app retry its connection, because in Kubernetes there is no `depends_on` at all."**

# Part 3 — ⭐ The features that earn their place

## ⭐ Override files and profiles

```
⭐ docker-compose.yml            ⭐ the shared base
⭐ docker-compose.override.yml   ⭐ applied AUTOMATICALLY — dev-only: bind mounts, debug ports
⭐ docker-compose.ci.yml         ⭐ explicit: -f base -f ci
```

| ⭐ Feature | ⭐ Use |
|---|---|
| ⭐ **Automatic override** | ⭐ dev conveniences that must never reach CI |
| ⭐ **Profiles** | ⭐⭐ `--profile observability` brings up Grafana only when you want it |
| `extends` / YAML anchors | shared fragments |
| ⭐ **`env_file`** | ⭐ `.env` for local values — ⭐⭐ **and `.env` is in `.gitignore`, always** |

⚠️ **`.env` committed to git is one of the most common credential leaks there is**, and it is
permanent once pushed (Day 085). **Commit a `.env.example` with the keys and no values**, and make
the real one required.

## ⭐ The things people get wrong

| ⭐ Detail | ⭐ Right answer |
|---|---|
| ⭐ **`ports` vs `expose`** | ⭐ `ports` publishes to the host; **`expose` does nothing useful — services already reach each other** |
| ⭐ **Publishing everything** | ⭐⭐ only publish what you actually browse to; **internal services need no host port** |
| ⭐ `restart: always` in dev | ⭐ a crash-looping container you cannot stop |
| ⭐ **No resource limits** | ⭐ your laptop becomes unusable (Day 364) |
| ⭐ `container_name` | ⭐ **prevents running two projects at once** — let Compose name them |
| ⭐ **Rebuilding on every up** | ⭐ `docker compose up --build` only when you changed the image |
| Named volumes for source | ⭐ bind mounts for code, named volumes for data |

# Part 4 — ⭐⭐ The dev/prod divergence trap

```
⭐⭐ THE FAILURE: Compose runs one instance, no TLS, no proxy, an in-memory session store,
⭐   a dev password, and a database on the same host.
⭐   Production runs three replicas behind a proxy with TLS, Redis-backed sessions and a managed DB.
⭐ ⇒ ⭐⭐ Every bug that only appears with more than one instance is invisible until production.
```

| ⭐ Divergence | ⭐ What it hides |
|---|---|
| ⭐⭐ **One instance locally** | ⭐⭐ **in-memory sessions, local caches, per-instance schedulers** (Day 324) |
| ⭐ **No reverse proxy** | ⭐ `X-Forwarded-*` handling, TLS termination bugs (Day 155, Day 367) |
| ⭐ Different config mechanism | a production-only misconfiguration |
| ⭐ **A different database version** | a query that works locally and not in production |
| No resource limits locally | ⭐ the JVM behaves differently under a cgroup (Day 361) |

**⭐ The practical remedy, and it is cheap:**

```
⭐ 1. ⭐⭐ Run TWO app replicas locally (`--scale app=2`) behind Nginx
⭐    ⇒ ⭐⭐ every statelessness bug surfaces on your laptop instead of in production
⭐ 2. ⭐ Pin the SAME database and Redis versions as production
⭐ 3. ⭐ Set memory limits locally so the JVM sees a cgroup
⭐ 4. ⭐ Use the SAME image you would deploy — config from the environment, not a dev Dockerfile
⭐ 5. Keep dev-only conveniences in the override file, never the base
```

> **⭐ Point 1 is the highest-value line in this day.** Two replicas plus a proxy costs one line of
> config and **surfaces the entire class of bugs Day 324 catalogued** — random logouts, stale local
> caches, schedulers firing twice — **while you are sitting in front of the code.**

## ⭐ When Compose stops being enough

| ⭐ Signal | ⭐ Next step |
|---|---|
| ⭐ You need zero-downtime deploys | ⭐ an orchestrator (Day 377) |
| ⭐ **More than one host** | Swarm, Nomad, or Kubernetes |
| Autoscaling, self-healing, rescheduling | Kubernetes |
| ⭐ Secrets management, RBAC, network policy | a platform |
| ⭐ **None of the above** | ⭐⭐ **Compose on one server is a perfectly respectable production deployment for a small system — say so** |

⚠️ **Do not let anyone tell you Compose in production is automatically wrong.** For a low-traffic
internal service on a single VM, **Compose plus a systemd unit is simpler, cheaper and more reliable
than a Kubernetes cluster nobody has time to operate** — which is Day 377's argument arriving early.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ `depends_on` without a condition | ⭐⭐ **"started" is not "ready" — the app crashes on boot** |
| ⭐ Relying on ordering instead of retries | production has no `depends_on` |
| ⭐ **Committing `.env`** | ⭐⭐ a permanent credential leak |
| ⭐ Publishing every service's port | needless exposure; port collisions |
| ⭐ `container_name` everywhere | ⭐ cannot run two projects |
| ⭐ **One replica locally** | ⭐⭐ every statelessness bug hides until production |
| ⭐ **A different database version than production** | a locally-passing query that fails live |
| No resource limits locally | JVM behaves differently under cgroups |
| Dev conveniences in the base file | they reach CI |
| ⭐ Using Compose to orchestrate production at scale | no rolling updates, no self-healing |
| ⭐ Dismissing Compose for small production systems | ⭐ over-engineering |

## Interview questions

**Q: What is Compose actually for?**
Local development and integration testing — one command produces the whole working system — plus
executable documentation of what the system is made of, which unlike a README cannot drift because it
is what people run. It is also a reasonable production deployment for a small single-host service,
though it gives you no rolling updates, self-healing or autoscaling.

**Q: What does `depends_on` guarantee?**
Only start order, not readiness — "started" means the process launched, and Postgres takes several
seconds after that to accept connections, so the app crashes on boot. The fix is
`condition: service_healthy` with a healthcheck on the dependency. But I would also make the
application retry its connections, because in Kubernetes there is no `depends_on` at all and nothing
guarantees ordering.

**Q: What is the biggest risk with Compose?**
Divergence from production. If Compose runs one instance with no proxy, no TLS, a dev password and a
different database version, then every bug that only appears with multiple instances — in-memory
sessions, local caches, schedulers firing on every node — stays invisible until you deploy. The cheap
fix is running two replicas behind Nginx locally, which surfaces that whole class of bug on your
laptop for one line of config.

**Q: Is Compose acceptable in production?**
For a small single-host system, yes, and I would defend that. It has no rolling updates, no
self-healing and no multi-host scheduling, so the moment you need zero-downtime deploys or more than
one machine you have outgrown it. But Compose plus a systemd unit on one VM is simpler and more
reliable than a Kubernetes cluster nobody has time to operate.

**Q: How do you keep dev-only settings out of CI?**
The base file holds the shared truth; `docker-compose.override.yml` is applied automatically and
holds bind mounts, debug ports and dev conveniences; CI composes the base with an explicit CI file
instead. Profiles handle optional services like observability tooling. And `.env` holds local values,
is git-ignored, and ships as a `.env.example` with keys and no values.

## Mini task

1. **Write a Compose file** for your flagship: app, Postgres, Redis, with healthchecks and
   conditions.
2. ⭐ Use `depends_on: [postgres]` without a condition and **reproduce the startup crash.** Add the
   healthy condition and confirm.
3. ⭐ Then **remove the condition again and make the application retry instead.** Confirm it starts
   correctly either way — that is the production-safe version.
4. ⭐⭐ **Run `--scale app=2` behind Nginx.** Find at least one statelessness bug (Day 324) that a
   single instance was hiding.
5. ⭐ Set the local Postgres to a **different major version** than production and find a behavioural
   difference.
6. ⭐ Add **memory limits** locally and confirm the JVM's heap sizing changes (Day 361).
7. Split dev conveniences into an **override file** and confirm CI does not pick them up.
8. ⭐ Add a **profile** for Prometheus and Grafana; confirm they only start when requested.
9. ⭐ Commit `.env` deliberately in a scratch repo, then **try to remove it from history** — feel why
   the rule exists.
10. Time **fresh-clone to working system.** If it is over five minutes, fix it (Day 287's gate).

## 🎙️ Articulation drill

**Two minutes:** *"A new engineer joins on Monday. How long until they have the system running?"*

**⭐ The answer is a number and a mechanism.** *"Under five minutes — clone, `docker compose up`, and
the whole stack comes up with healthchecks so nothing starts before its dependencies are ready."*

**⭐ Then the sentence that shows depth: "and it runs two app replicas behind a proxy locally, with
the same database version as production, because a single-instance dev environment hides every
statelessness bug until deploy day."** **Most people describe Compose as a convenience; describing it
as a correctness tool is the better answer.**
