**L-402** · Kafka II — consumer groups, rebalancing and offsets

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ Auto-commit does not commit what you processed. It commits what you *polled* — so a crash
> mid-batch loses every message you fetched and had not finished. It is on by default.**

# Part 1 — ⭐⭐ Consumer groups and the parallelism ceiling

```
⭐ Topic "orders", 6 partitions · consumer group "billing":
⭐   3 consumers ⇒ ⭐ 2 partitions each
⭐   6 consumers ⇒ ⭐ 1 partition each        ⭐⭐ MAXIMUM USEFUL PARALLELISM
⭐   ⭐⭐ 8 consumers ⇒ ⭐⭐ 6 working, 2 IDLE FOREVER

⭐⭐ ONE PARTITION IS READ BY EXACTLY ONE CONSUMER IN A GROUP. ⭐ Always.
⭐ ⇒ ⭐⭐ PARTITION COUNT IS YOUR PARALLELISM CEILING, and Day 401 said you cannot raise it safely.
```

| ⭐ And the second group is free | |
|---|---|
| ⭐⭐ **A different `group.id` gets its own copy of everything** | ⭐⭐ **this is what makes Kafka not a queue** |
| ⭐ Adding an analytics consumer | ⭐ requires **no change to the producer and no change to the existing consumer** |
| ⭐ Each group has its own offsets | ⭐ so each moves at its own pace, and one being slow affects nobody |

> **⭐ "Add a consumer group" is the cheapest architectural move in the stage.** A new team can start
> consuming your events tomorrow **without you deploying anything** — and that, far more than
> throughput, is why Kafka wins where it wins.

## ⭐ Scaling beyond the partition count

| ⭐ Problem | ⭐ Answer |
|---|---|
| ⭐ Processing is slow, partitions are maxed | ⭐⭐ **parallelise *inside* the consumer** — but then you own ordering and offset safety |
| ⭐ Ordering only matters per key | ⭐ dispatch to per-key executors; **commit only the contiguous prefix** |
| ⭐ Ordering does not matter at all | ⭐ a bounded thread pool per partition, with careful commits |
| ⭐⭐ It genuinely needs more partitions | ⭐⭐ new topic + migration (Day 401) |

⚠️ **In-consumer parallelism breaks the simple offset story.** If message 5 finishes before message 3,
committing offset 6 means **3 is lost if you crash.** The correct rule: **commit the highest offset such
that everything below it is done** — a contiguous watermark, not the maximum.

# Part 2 — ⭐⭐ Offsets: what "committed" actually means

```
⭐ enable.auto.commit=true (⭐⭐ THE DEFAULT), auto.commit.interval.ms=5000
⭐   ⇒ ⭐⭐ the consumer commits offsets of records RETURNED BY poll(), on a timer,
⭐     ⭐⭐ REGARDLESS of whether your code finished processing them.
⭐   ⇒ ⭐⭐ poll() returns 500 records → commit fires at record 200 → CRASH
⭐   ⇒ ⭐⭐ 300 MESSAGES SILENTLY LOST. No error, no DLQ, no trace.
```

| ⭐ Mode | ⭐ Semantics |
|---|---|
| ⭐ Auto-commit | ⭐⭐ **at-most-once in practice — data loss on crash** |
| ⭐⭐ **Manual commit AFTER processing** | ⭐⭐ **at-least-once — duplicates on crash, which is the correct trade** |
| ⭐ Commit before processing | at-most-once, deliberately (rare, and only for telemetry) |
| ⭐⭐ **Store the offset in the same transaction as the effect** | ⭐⭐ **effectively-once** — the outbox/inbox idea (Day 407) |

```java
// ⭐⭐ The shape that is correct: process, THEN commit — and be idempotent regardless
while (running) {
    ConsumerRecords<String, Order> records = consumer.poll(Duration.ofMillis(500));
    for (var r : records) {
        process(r);                     // ⭐⭐ idempotent (Day 335) — you WILL see duplicates
    }
    consumer.commitSync();              // ⭐ at-least-once
}
```

> **⭐⭐ At-least-once plus an idempotent consumer is the correct default, and it is not a compromise —
> it is the only combination that survives every failure mode.** At-most-once loses data; true
> exactly-once delivery does not exist (Day 334); **effectively-once is achieved at the consumer, not by
> the broker.**

| ⭐ `auto.offset.reset` — the setting behind two different disasters | |
|---|---|
| ⭐⭐ `latest` | ⭐⭐ a **new group skips all history** — "we deployed the consumer and it processed nothing" |
| ⭐⭐ `earliest` | ⭐⭐ a group whose offsets **expired** reprocesses everything — "it sent 2 million emails" |
| ⭐ It only applies when there is **no committed offset** | ⭐ so it fires on first deploy, and after offset retention expiry |

# Part 3 — ⭐⭐ Rebalancing: the stop-the-world you did not know about

```
⭐ A rebalance triggers when: ⭐ a consumer joins · leaves · ⭐⭐ is DECLARED DEAD ·
⭐ partitions change · ⭐ (and on every rolling deploy, once per instance)

⭐⭐ EAGER (default, legacy): ⭐⭐ EVERY consumer revokes ALL partitions, then reassignment happens.
⭐   ⇒ ⭐⭐ THE ENTIRE GROUP STOPS CONSUMING for the duration. ⭐ Seconds, sometimes tens of seconds.
⭐   ⇒ ⭐⭐ A rolling deploy of 10 instances = 10 rebalances = ten stop-the-world pauses.

⭐⭐ COOPERATIVE / INCREMENTAL (CooperativeStickyAssignor):
⭐   ⇒ ⭐⭐ only the partitions that MOVE are revoked. ⭐ Everyone else keeps working.
⭐   ⇒ ⭐⭐ Use it. It is a one-line config change with an enormous operational payoff.
```

| ⭐ The two timeouts, and the confusion between them | |
|---|---|
| ⭐ `session.timeout.ms` (~45 s) | ⭐ heartbeats stop ⇒ declared dead. **Heartbeats run on a background thread.** |
| ⭐⭐ `max.poll.interval.ms` (~5 min) | ⭐⭐ **time between `poll()` calls** — exceeded ⇒ **declared dead even though heartbeats were fine** |

```
⭐⭐ THE CLASSIC BUG:
⭐   processing one batch takes 6 minutes (a slow downstream call)
⭐   ⇒ ⭐⭐ max.poll.interval.ms exceeded ⇒ consumer EJECTED from the group
⭐   ⇒ rebalance ⇒ another consumer takes the partition and ⭐⭐ REPROCESSES THE SAME BATCH
⭐   ⇒ ⭐⭐ that one also takes 6 minutes ⇒ ⭐⭐ AN INFINITE REBALANCE LOOP where nothing commits.
⭐   ⇒ ⭐ Symptom: "the consumer keeps leaving the group", zero progress, growing lag.
⭐ ⇒ ⭐⭐ FIX: reduce `max.poll.records`, or raise `max.poll.interval.ms`, or move slow work
⭐    off the poll thread — ⭐ and reduce the batch size FIRST, because it is the real cause.
```

| ⭐⭐ **Static membership** — the underused fix | |
|---|---|
| ⭐ Set `group.instance.id` per instance | ⭐⭐ **a restart within the session timeout causes NO rebalance** |
| ⭐ Why it matters | ⭐⭐ a rolling deploy stops triggering a rebalance per pod |
| Pair with | cooperative assignment, for a nearly rebalance-free deploy |

# Part 4 — ⭐⭐ The poison message, and the retry topic pattern

```
⭐⭐ A message that always fails BLOCKS ITS PARTITION.
⭐   You cannot skip it (offsets are sequential), and you cannot commit past it
⭐   without losing it. ⭐⭐ Every message behind it waits forever.
⭐ ⇒ ⭐⭐ This is Kafka's single biggest operational difference from SQS,
⭐   where one bad message is just one bad message (Day 393).
```

| ⭐ The pattern | |
|---|---|
| ⭐ 1. Try in-place, a couple of times, for transient failures | ⭐ with backoff |
| ⭐⭐ 2. **Publish to `orders.retry.5s`, commit the original offset** | ⭐⭐ the partition is unblocked immediately |
| ⭐ 3. Retry topics with increasing delays: 5s → 1m → 10m | ⭐ a consumer per delay topic |
| ⭐⭐ 4. Exhausted ⇒ **`orders.DLT`**, with the original headers and the exception | ⭐⭐ and **alarm on it** |
| ⭐ 5. Redrive from the DLT after a fix | ⭐ Spring Kafka gives you most of this |

⚠️ **Non-blocking retries break per-key ordering for the retried key** — the message that failed is now
processed after messages that came behind it. **That is a real trade and you must decide it consciously:
either ordering matters and you halt the partition (and page someone), or throughput matters and you
accept reordering for failures.** There is no configuration that gives both.

## ⭐ The metric that matters

| | |
|---|---|
| ⭐⭐ **Consumer lag** — not throughput | ⭐⭐ `records-lag-max`, per partition |
| ⭐ Lag in **time**, not messages | ⭐⭐ "we are 4 minutes behind" is the SLO; "80,000 messages" is not |
| ⭐ Alarm on lag **trend**, not absolute | ⭐ growing lag under steady traffic = you are losing |
| ⭐ Per-partition lag | ⭐⭐ one hot partition hides behind a healthy average (Day 323) |

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Leaving auto-commit on** | ⭐⭐ commits what you polled, not what you processed — silent loss |
| ⭐ More consumers than partitions | ⭐ the extras idle forever |
| ⭐ Not knowing the parallelism ceiling | ⭐ scaling out does nothing |
| ⭐ In-consumer parallelism with a naive commit | ⭐⭐ committing a high offset loses unfinished lower ones |
| ⭐⭐ **`auto.offset.reset=latest` on first deploy** | ⭐⭐ the consumer silently processes nothing |
| ⭐⭐ **`earliest` after offsets expire** | ⭐⭐ reprocesses everything — two million emails |
| ⭐ Eager rebalancing on a large group | ⭐⭐ stop-the-world on every deploy |
| ⭐ No `group.instance.id` | ⭐ a rebalance per pod on every rolling restart |
| ⭐⭐ **Slow processing exceeding `max.poll.interval.ms`** | ⭐⭐ infinite rebalance loop, zero progress |
| ⭐ Raising the timeout instead of shrinking the batch | ⭐ treats the symptom |
| ⭐⭐ **No retry topic / DLT** | ⭐⭐ one poison message blocks a partition forever |
| ⭐ Not knowing retries break ordering | ⭐ a trade made by accident |
| ⭐ Watching throughput instead of lag | ⭐⭐ lag is the health metric |
| Averaged lag across partitions | one hot partition hides |

## Interview questions

**Q: What is wrong with Kafka's default auto-commit?**
It commits the offsets of records returned by `poll()`, on a timer, regardless of whether your code has
processed them. If `poll()` returns five hundred records and the commit fires while you are on record two
hundred, a crash loses three hundred messages with no error, no dead letter and no trace. It is
at-most-once semantics presented as a convenience, and it is on by default. The correct pattern is manual
commit after processing, which gives at-least-once, combined with an idempotent consumer — because
duplicates are the failure mode you can defend against and silent loss is not.

**Q: How does parallelism work in a consumer group?**
One partition is read by exactly one consumer within a group, so the partition count is your parallelism
ceiling — with six partitions, an eighth consumer sits idle forever. Since increasing partitions breaks
key ordering, that ceiling is effectively fixed at topic creation, which is why you over-provision.
Separately, a different group id gets its own independent copy of the whole stream with its own offsets,
which is the property that makes Kafka a log rather than a queue: a new team can start consuming your
events without you deploying anything.

**Q: A consumer keeps leaving the group and lag grows. What is happening?**
Almost always `max.poll.interval.ms`. Heartbeats run on a background thread, so the session timeout looks
healthy, but if the time between `poll()` calls exceeds the poll interval — because processing a batch
takes minutes against a slow downstream — the consumer is ejected anyway. Then a rebalance hands the
partition to someone else who reprocesses the same batch, takes just as long, and is ejected too. It
becomes an infinite rebalance loop where nothing ever commits. The fix in order of preference is reducing
`max.poll.records` so a batch is smaller, moving slow work off the poll thread, and only then raising the
interval — because raising it treats the symptom.

**Q: How do you handle a message that always fails?**
Not in place, because a poison message blocks its partition — you cannot skip it and you cannot commit
past it without losing it, so everything behind it waits forever. That is the sharpest operational
difference from SQS. The pattern is a couple of quick in-place retries for transient failures, then
publish to a retry topic with a delay and commit the original offset, which unblocks the partition
immediately. Retry topics with escalating delays feed a dead letter topic, which has an alarm on it and
supports redrive after a fix. The trade to state explicitly is that this breaks per-key ordering for the
failed message — so either ordering matters and you halt the partition and page someone, or throughput
matters and you accept reordering on failure.

**Q: Which metric tells you a consumer is healthy?**
Consumer lag, expressed in time rather than message count, and per partition rather than averaged. "We
are four minutes behind" is an objective you can alert on and scale against; eighty thousand messages
means nothing without a rate. Throughput is misleading because a consumer can be processing at full speed
and still falling behind. And an averaged lag hides the case that matters most — one hot partition with a
skewed key sitting far behind while five healthy ones drag the average down.

processed, so a crash mid-batch silently loses everything in flight — it is at-most-once wearing a
