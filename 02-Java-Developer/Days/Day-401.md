# Day 401

**L-401** · Kafka I — the log, partitions, and the producer

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ Kafka is not a queue. It is a replicated, partitioned, append-only log that consumers read at
> their own position — and every difference between Kafka and RabbitMQ follows from that one sentence.**
>
> Today: where ordering actually lives, **`acks=all` with `min.insync.replicas=1`, which is a durability
> setting that guarantees nothing**, the idempotent producer, and **why you cannot casually increase
> partition count.**

# Part 1 — ⭐⭐ The log, and where ordering lives

```
⭐ TOPIC "orders", 3 partitions:
⭐   P0: [0][1][2][3][4]           ⭐ each partition is an ORDERED, IMMUTABLE, APPEND-ONLY sequence
⭐   P1: [0][1][2]                 ⭐ offsets are per-partition, monotonically increasing
⭐   P2: [0][1][2][3][4][5][6]

⭐⭐ ORDERING EXISTS *WITHIN* A PARTITION AND NOWHERE ELSE.
⭐   partition = ⭐⭐ hash(key) % numPartitions   ⇒ ⭐⭐ SAME KEY ⇒ SAME PARTITION ⇒ ORDERED
⭐   no key ⇒ round-robin (sticky batching) ⇒ ⭐⭐ NO ordering guarantee at all
```

| ⭐⭐ Consequence — the design decision of the whole day | |
|---|---|
| ⭐⭐ **The key IS your ordering scope** | ⭐ `key = orderId` ⇒ per-order ordering, huge parallelism |
| ⭐⭐ **A single key for everything** | ⭐⭐ total ordering, **one partition, one consumer — a bottleneck you built** |
| ⭐ The right question | ⭐⭐ **"ordering per what?"** — almost always per entity, never global |
| ⭐ Hot keys | ⭐⭐ a celebrity key overloads one partition (Day 323's fan-out problem again) |

> **⭐ This is Day 393's `MessageGroupId` and Day 329's shard key wearing a third name.** Ordering is
> always bought with parallelism, and the partition key is where you spend it.

## ⭐⭐ Why you cannot casually add partitions

```
⭐ partition = hash(key) % N
⭐ ⇒ ⭐⭐ change N from 3 to 6 and hash(key) % N maps EXISTING keys to DIFFERENT partitions.
⭐ ⇒ ⭐⭐ Key "order-42" was in P1 with three ordered events; new events go to P4.
⭐ ⇒ ⭐⭐ ORDERING FOR EXISTING KEYS IS BROKEN — permanently, silently, retroactively.
⭐ ⇒ ⭐ AND you can never DECREASE partitions at all.
```

| ⭐ So | |
|---|---|
| ⭐⭐ **Over-provision partitions up front** | ⭐ 2–3× your expected consumer count |
| ⭐ But not wildly | ⭐ each partition costs file handles, memory, and **increases end-to-end latency in rebalances** |
| ⭐ If you must expand | ⭐⭐ write to a **new topic** and migrate consumers, or accept the ordering break knowingly |

# Part 2 — ⭐⭐ Producer durability: the setting that lies

```
⭐ acks=0    ⇒ ⭐ fire and forget. ⭐⭐ Data loss is normal, not exceptional.
⭐ acks=1    ⇒ ⭐ the LEADER wrote it. ⭐⭐ Leader dies before replication ⇒ MESSAGE GONE.
⭐ acks=all  ⇒ ⭐ all IN-SYNC replicas wrote it.
⭐             ⭐⭐ ...but "all in-sync replicas" can be ONE replica.
```

```
⭐⭐ THE LIE, SPELLED OUT:
⭐   replication.factor = 3, ⭐⭐ min.insync.replicas = 1, acks = all
⭐   ⇒ two followers fall behind ⇒ ISR shrinks to {leader}
⭐   ⇒ ⭐⭐ "all in-sync replicas" = the leader alone ⇒ ⭐⭐ acks=all now means acks=1
⭐   ⇒ ⭐⭐ leader dies ⇒ ⭐⭐ ACKNOWLEDGED DATA IS LOST, and the producer was told "success".

⭐⭐ THE DURABLE CONFIGURATION, memorised as a triple:
⭐   ⭐⭐ replication.factor = 3 · min.insync.replicas = 2 · acks = all
⭐   ⇒ ⭐ tolerates ONE broker loss with zero data loss,
⭐     and ⭐⭐ REFUSES WRITES (NotEnoughReplicas) rather than silently accepting unsafe ones.
```

> **⭐⭐ Refusing the write is the feature.** `min.insync.replicas=2` means that when the cluster is too
> degraded to be durable, **producers get an error instead of a false success** — which is exactly the
> choice Day 330's CAP discussion said you have to make explicitly. **Availability was traded for
> durability, on purpose, in a config file.**

⚠️ **And `unclean.leader.election.enable` is the same choice at the other end** (Day 403): setting it
`true` lets an out-of-sync replica become leader — **the cluster stays available and silently discards
committed messages.** Keep it `false` unless you can articulate why not.

# Part 3 — ⭐⭐ The idempotent producer, and ordering under retries

```
⭐⭐ WITHOUT enable.idempotence:
⭐   producer sends msg → ⭐ broker writes it → ⭐⭐ the ACK is lost
⭐   → producer retries → ⭐⭐ THE MESSAGE IS IN THE LOG TWICE.  (Day 398's case 3, again)

⭐⭐ WITH enable.idempotence=true  (⭐ the DEFAULT since Kafka 3.0):
⭐   ⭐ producer gets a PID; ⭐ each message carries a per-partition SEQUENCE NUMBER
⭐   ⇒ ⭐⭐ the broker rejects a duplicate sequence ⇒ ⭐⭐ EXACTLY-ONCE WRITES TO THE LOG,
⭐     for free, per producer session.
```

| ⭐ Setting | ⭐ Why |
|---|---|
| ⭐⭐ `enable.idempotence=true` | ⭐⭐ dedup on retry; **also forces `acks=all` and bounded in-flight** |
| ⭐⭐ `max.in.flight.requests.per.connection ≤ 5` | ⭐⭐ **with idempotence, ordering is preserved up to 5**; without it, **>1 can reorder on retry** |
| ⭐ `retries` high + `delivery.timeout.ms` | ⭐ the real bound is the timeout, not the retry count |
| ⭐ `linger.ms` / `batch.size` | ⭐⭐ **the throughput/latency dial** — `linger.ms=5` often multiplies throughput for ~5 ms |
| ⭐ `compression.type=lz4`/`zstd` | ⭐ compresses the *batch* — large wins, and it stays compressed on disk |

⚠️ **The non-idempotent reordering bug is subtle and worth knowing**: with retries enabled and more than
one in-flight request, message 2 can succeed while message 1 is being retried — **so the log contains 2
before 1, for the same key.** People discover it as "our events arrive out of order sometimes" and
blame the consumer.

# Part 4 — ⭐ Anatomy of a produce, and what it costs

```
⭐ producer.send(record, callback)
⭐  → ⭐ serialise (key, value)         ⭐ Avro/Protobuf + a SCHEMA REGISTRY (Day 400)
⭐  → ⭐⭐ partitioner: hash(key) % N
⭐  → ⭐ accumulate into a per-partition BATCH   ⭐ (linger.ms waits for more)
⭐  → ⭐ sender thread ships the batch
⭐  → ⭐ broker appends to the partition file, replicates to followers
⭐  → ⭐⭐ ack when min.insync.replicas have it
⭐  → ⭐ callback fires  ⭐⭐ (send() is ASYNC — a bare send() with no callback swallows failures)
```

| ⭐ Trap | |
|---|---|
| ⭐⭐ **`send()` without a callback or `get()`** | ⭐⭐ **failures are silent** — the future is never inspected |
| ⭐ `send().get()` on every message | ⭐⭐ correct but **serialises everything** — throughput collapses |
| ⭐ The middle path | ⭐ async send with a callback that logs and increments an error metric |
| ⭐⭐ `buffer.memory` full | ⭐⭐ `send()` **blocks** (`max.block.ms`) — **backpressure reaching your request thread** |

> **⭐ That last row matters more than it looks: if the broker is slow, a producer with a full buffer
> blocks the calling thread.** Your web request now waits on Kafka. **Either bound it with
> `max.block.ms` and handle the failure, or produce from a separate executor** (Day 336's backpressure,
> in the client library).

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Expecting ordering across partitions** | ⭐⭐ ordering exists only within one |
| ⭐ No key when ordering is needed | ⭐ round-robin, no guarantee |
| ⭐⭐ **One key for everything** | ⭐⭐ a single-partition bottleneck you built |
| ⭐ Hot keys | ⭐ one partition saturated while others idle |
| ⭐⭐ **Increasing partitions on a keyed topic** | ⭐⭐ silently breaks ordering for existing keys, retroactively |
| ⭐⭐ **`acks=all` with `min.insync.replicas=1`** | ⭐⭐ a durability setting that guarantees nothing |
| ⭐ `unclean.leader.election=true` | ⭐⭐ silently discards committed data |
| ⭐ Idempotence off with in-flight > 1 | ⭐⭐ retries reorder messages for the same key |
| ⭐⭐ **`send()` with no callback** | ⭐⭐ silent failures |
| ⭐ `send().get()` per message | throughput collapses |
| ⭐ Ignoring `max.block.ms` | ⭐⭐ a slow broker blocks your request threads |
| `linger.ms=0` everywhere | leaving large throughput gains unclaimed |

## Interview questions

**Q: Where does ordering live in Kafka?**
Inside a partition and nowhere else. The partition is chosen by hashing the record key, so the key is
your ordering scope — key by order id and you get per-order ordering with as much parallelism as you
have partitions; key everything the same and you get total ordering with one consumer, which is a
bottleneck you constructed on purpose. The question to ask a requirement is always "ordering per what",
and the answer is almost never global. It is the same trade as an SQS message group or a database shard
key.

**Q: What is wrong with `acks=all` and `min.insync.replicas=1`?**
It reads as the safest setting and guarantees nothing. `acks=all` means all in-sync replicas have the
message, but if followers fall behind the in-sync set shrinks to just the leader, at which point
`acks=all` is `acks=1` — and if the leader then dies, acknowledged data is gone while the producer was
told it succeeded. The durable configuration is replication factor three, minimum in-sync replicas two,
acks all. The important consequence is that when the cluster is too degraded to be durable, producers get
an error instead of a false success. Refusing the write is the feature — it is choosing consistency over
availability explicitly, in a config file.

**Q: What does the idempotent producer solve?**
The lost-acknowledgement duplicate. The broker writes the message, the ack is lost, the producer retries,
and the log has it twice. With idempotence the producer gets an id and attaches a per-partition sequence
number, so the broker rejects duplicates — exactly-once writes into the log for that producer session,
essentially free, and it is the default from Kafka 3.0. It also fixes a subtler bug: without it, with
retries and multiple in-flight requests, message two can be written before message one is successfully
retried, so the same key ends up out of order and people blame the consumer.

**Q: Why can you not simply increase the partition count?**
Because the partition is `hash(key) % N`, so changing N remaps existing keys to different partitions. A
key with three ordered events in one partition starts writing to another, and ordering for existing keys
is broken permanently, silently and retroactively. You also cannot decrease partitions at all. So you
over-provision at creation — a couple of times your expected consumer count — and if you genuinely
outgrow it, you produce to a new topic and migrate consumers rather than expanding in place.

**Q: What can go wrong with the producer inside your web request?**
Two things people miss. `send()` is asynchronous and returns a future, so a bare `send()` with no
callback swallows failures entirely — the message is lost and nothing reports it. And if the broker is
slow, the producer's buffer fills and `send()` blocks up to `max.block.ms`, meaning your HTTP request
thread is now waiting on Kafka. That is backpressure arriving from the broker into your request path. The
fix is an async send with a callback that logs and increments an error metric, a bounded `max.block.ms`
with a defined failure behaviour, and for critical paths producing via the outbox instead.

## 🎙️ Articulation drill

**Two minutes:** *"How do you configure Kafka for durability?"*

**⭐ Give the triple and then the reason, because the reason is what proves understanding: replication
factor three, minimum in-sync replicas two, acks all. The subtlety is that `acks=all` alone means
nothing — if the in-sync set shrinks to the leader, `acks=all` is `acks=1`, and a leader failure loses
data the producer was told was safe.**

**⭐ Setting minimum in-sync replicas to two makes the cluster refuse writes when it is too degraded to
be durable, which is choosing consistency over availability deliberately rather than discovering the
choice during an incident. And I leave unclean leader election off, because turning it on keeps the
cluster available by silently discarding committed messages.**

**⭐ Then the producer half: idempotence on, which is the default now, so a lost acknowledgement does not
duplicate the message and retries cannot reorder writes for the same key.**
