# Part 1 — The problem AOP solves

Day 130 ended on this. Here it is concretely:

```java
@Service
public class OrderService {

    public Order place(CreateOrderRequest req) {
        long start = System.nanoTime();                        // metrics
        log.info("place start user={}", currentUser());        // logging
        if (!security.canPlace(currentUser())) throw new ForbiddenException();  // security
        Connection conn = dataSource.getConnection();          // transaction
        conn.setAutoCommit(false);
        try {
            Order order = doTheActualWork(req);                // ⭐ two lines of business logic
            conn.commit();
            return order;
        } catch (Exception e) {
            conn.rollback();
            throw e;
        } finally {
            conn.close();
            metrics.record("place", System.nanoTime() - start);
            log.info("place end");
        }
    }
}
```

**Two lines of business logic, twenty lines of infrastructure — repeated in every method of every
service.** That is a **cross-cutting concern**: a requirement that cuts across the module structure,
so no amount of good decomposition eliminates the duplication.

```java
@Service
public class OrderService {
    @Transactional
    public Order place(CreateOrderRequest req) {
        return doTheActualWork(req);                            // ⭐ that is the whole method
    }
}
```

**The infrastructure did not disappear. It moved into a proxy.**

# Part 2 — ⭐ How it works

```
Without AOP:      caller ──────────────────► OrderService
With AOP:         caller ──► PROXY ────────► OrderService
                             │
                             ├─ begin transaction
                             ├─ delegate to the target
                             └─ commit or roll back
```

Day 132 established where this happens: a **`BeanPostProcessor`** —
`AnnotationAwareAspectJAutoProxyCreator` — returns a proxy from
`postProcessAfterInitialization`. **Everything injected anywhere receives the proxy, not your
object.**

```java
@Service
class Inspector {
    Inspector(OrderService service) {
        System.out.println(service.getClass());
        // class com.acme.OrderService$$SpringCGLIB$$0     ← not OrderService
    }
}
```

## The two proxy mechanisms

| | **JDK dynamic proxy** | **CGLIB** |
|---|---|---|
| Requires | ⭐ **an interface** | a non-final **class** |
| Mechanism | `java.lang.reflect.Proxy` (Day 056A) | Bytecode subclassing |
| Proxy is | a *sibling* implementing the interface | a **subclass** of your class |
| `final` methods | n/a | ⚠️ **cannot be intercepted** |
| `private` methods | n/a | ⚠️ **cannot be intercepted** |
| Constructor | not called | ⚠️ called (Objenesis avoids this in modern Spring) |

```java
// JDK proxy — Day 056A, which you wrote by hand
Proxy.newProxyInstance(loader, new Class[]{PaymentGateway.class}, (p, method, args) -> {
    before();
    Object result = method.invoke(target, args);
    after();
    return result;
});
```

**Spring Boot 2.0+ defaults to CGLIB for everything** (`spring.aop.proxy-target-class=true`),
because JDK proxies only expose the interface — so injecting by concrete class fails, and any method
not on the interface is invisible.

**The consequences of CGLIB subclassing are the ones that bite:**

- **`final` classes cannot be proxied at all.** `@Transactional` on a `final class` silently does
  nothing. Kotlin's classes are final by default, which is why `kotlin-allopen` exists.
- **`final` methods are not intercepted.** The subclass cannot override them.
- **`private` methods are not intercepted.** Not visible to the subclass — and this is half of
  today's headline answer.

# Part 3 — ⭐⭐ Self-invocation

**The single most-asked Spring question, and the one most people cannot explain.**

```java
@Service
public class OrderService {

    public void processAll(List<Order> orders) {
        for (Order order : orders) {
            process(order);                    // 💀 NO TRANSACTION — an internal call
        }
    }

    @Transactional
    public void process(Order order) { … }     // works when called from OUTSIDE
}
```

**Why**, and this is the sentence to be able to produce:

```
External call:      caller → PROXY → (starts transaction) → target.process()   ✅
Internal call:      target.processAll() → this.process()                       ❌
                                          ↑ `this` is the TARGET, not the proxy
                                            the proxy is never involved
```

> **⭐ `this` is your object, not the proxy. Any behaviour the proxy adds is bypassed by an internal
> call.** The annotation is not ignored — the code that reads it never runs.

**It fails silently.** No exception, no warning, no log line. The method runs, the data is written
without a transaction, and a partial failure leaves inconsistent state that appears months later.

**The same applies to every proxy-based annotation:** `@Cacheable` does not cache, `@Async` runs
synchronously, `@PreAuthorize` does not check, `@Retryable` does not retry.

## The fixes, in order of preference

```java
// ⭐ 1. SEPARATE BEANS — the correct structural fix
@Service
class OrderBatchService {
    private final OrderProcessor processor;                    // ← a PROXY is injected
    void processAll(List<Order> orders) { orders.forEach(processor::process); }
}

@Service
class OrderProcessor {
    @Transactional public void process(Order order) { … }      // ✅ external call
}
```

```java
// 2. Self-injection — works, and looks odd
@Service
class OrderService {
    @Lazy private final OrderService self;                     // ⭐ @Lazy avoids the cycle
    OrderService(@Lazy OrderService self) { this.self = self; }

    void processAll(List<Order> orders) { orders.forEach(self::process); }
}
```

```java
// 3. AopContext — requires exposeProxy, and is explicit about the hack
@EnableAspectJAutoProxy(exposeProxy = true)
…
((OrderService) AopContext.currentProxy()).process(order);
```

```java
// 4. TransactionTemplate — no proxy at all, fully explicit
private final TransactionTemplate tx;
void processAll(List<Order> orders) {
    orders.forEach(o -> tx.execute(status -> { process(o); return null; }));
}
```

> **Option 1 is the right answer**, and the reason is not merely mechanical: **needing a transaction
> around a single item inside a loop is telling you that the item processing is a separate
> responsibility** (Day 090). The proxy limitation is surfacing a design signal.

Option 4 is genuinely good when you need fine-grained control — a transaction per batch of 100, for
instance — and it makes the boundary explicit rather than annotated.

## The other silent failures

```java
@Service
class OrderService {
    @Transactional private void helper() { }        // 💀 private — never intercepted
    @Transactional final void other() { }           // 💀 final — cannot be overridden
}

@Service
final class OrderService { }                        // 💀 final class — cannot be proxied at all
```

**All three fail silently.** Spring 6.0+ *can* log a warning for `@Transactional` on non-public
methods, but it is not on by default and it does not cover every case.

```properties
logging.level.org.springframework.transaction.interceptor=TRACE   # ⭐ prove it is applied
```

**Run that when a transaction is not behaving.** It prints every transaction the interceptor creates
— and its absence is the proof you need.

# Part 4 — Writing an aspect

The vocabulary, which is worth knowing because it names things you have been doing informally:

```
Aspect       the module of cross-cutting behaviour        (@Aspect class)
Join point   a point where behaviour can be applied       (a method execution in Spring)
Pointcut     an expression selecting join points          (execution(* com.acme..*(..)))
Advice       the behaviour itself                          (@Before, @Around, …)
Weaving      applying aspects                              (at runtime, via proxies)
```

⚠️ **Spring AOP's only join point is method execution on a Spring bean.** Not field access, not
constructors, not `private` methods, not internal calls. Full AspectJ (compile- or load-time weaving)
supports all of it and does not use proxies — but it needs a compiler plugin or an agent, and is
rarely worth it.

```java
@Aspect
@Component
public class TimingAspect {

    @Around("@annotation(com.acme.Timed)")                      // ⭐ annotation-driven
    public Object time(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();                               // ⭐ call the target
        } finally {
            metrics.record(pjp.getSignature().toShortString(), System.nanoTime() - start);
        }
    }
}
```

**You wrote this on Day 056A** as a dynamic proxy. `@Aspect` is the declarative form.

The advice types:

```java
@Before("…")                    before; cannot prevent the call
@AfterReturning("…")            after success
@AfterThrowing("…")             after an exception
@After("…")                     finally
@Around("…")                    ⭐ full control — can skip, retry, or transform the result
```

**`@Around` must call and return `proceed()`.** Forgetting to return its result means every method
returns `null` — a spectacular and confusing failure.

## Pointcut expressions

```java
execution(* com.acme.service.*.*(..))          // any method in the service package
execution(public * com.acme..*Service.*(..))   // .. = any depth
@annotation(com.acme.Timed)                    // ⭐ methods with an annotation
@within(org.springframework.stereotype.Service) // any method in an annotated class
within(com.acme.order..*)                       // any bean in a package tree
bean(*Repository)                               // ⭐ Spring-only: by bean NAME
args(String, ..)                                // by argument types
```

> **Prefer `@annotation(...)` pointcuts.** A package-based expression silently stops matching when
> code is moved (Day 135's fragile strings, again); an annotation is explicit at the call site, so a
> reader of the method can see that something is applied.

Name and reuse them:

```java
@Pointcut("@within(org.springframework.stereotype.Service)")
public void serviceMethods() { }

@Around("serviceMethods() && @annotation(timed)")
public Object time(ProceedingJoinPoint pjp, Timed timed) throws Throwable { … }
```

## Ordering

```java
@Aspect @Component @Order(1) class SecurityAspect { }     // outermost
@Aspect @Component @Order(2) class TxAspect { }
```

**Lower order is outermost.** It matters: a security check must run *outside* the transaction, or a
rejected call has already opened one. Spring's own transaction advisor has a defined order that you
can position relative to.

# Part 5 — When not to use AOP

Be honest about the costs, because this is where AOP earns its reputation for magic:

| Cost | Detail |
|---|---|
| **Invisible behaviour** | Nothing at the call site indicates a proxy is involved |
| **Debugging depth** | Stack traces gain proxy and interceptor frames |
| **Silent failures** | Self-invocation, `private`, `final` — no error |
| **Order dependence** | Multiple aspects interact in ways that are hard to predict |
| **Testing** | Unit tests bypass proxies entirely, so aspects are untested |

That last one deserves emphasis: **a plain unit test constructs your class with `new`, so no proxy
exists and no aspect applies.** `@Transactional` is therefore untested by unit tests by construction
— which is one more reason Day 097 argued for integration tests against a real database.

> **Use AOP for genuinely cross-cutting, uniform concerns: transactions, security, caching, metrics,
> retries, audit logging.**
>
> **Do not use it for business logic.** Behaviour that depends on the domain belongs in the domain,
> where it is visible, testable and debuggable. An aspect that changes what a method *means* is the
> worst kind of magic.

**Prefer Spring's built-in aspects to your own.** `@Transactional`, `@Cacheable`, `@Retryable` and
`@PreAuthorize` are tested, ordered correctly and understood by everyone who reads your code. A
bespoke aspect is a local dialect.

## Common mistakes

| Mistake | Consequence |
|---|---|
| ⭐ **Self-invocation** | **The annotation silently does nothing** |
| `@Transactional` on a `private` method | Never intercepted, silently |
| `@Transactional` on a `final` method or class | Cannot be proxied, silently |
| Expecting `this` to be the proxy | It is the target |
| Forgetting to return `proceed()`'s result | Every method returns `null` |
| Package-based pointcuts | Silently stop matching when code moves |
| Aspects containing business logic | Invisible, untestable behaviour |
| Ignoring aspect order | Security runs inside the transaction |
| Assuming unit tests exercise aspects | They construct with `new`; no proxy exists |
| Expecting field or constructor interception | Spring AOP only intercepts method execution |
| Many custom aspects | A local dialect nobody else can follow |

## Interview questions

**Q: ⭐ Why does `@Transactional` fail on self-invocation?**
Spring wraps the bean in a proxy that starts the transaction before delegating. An external call goes
through the proxy; an internal call uses `this`, which is the target object, so the proxy is never
involved and the transactional advice never runs. It fails silently — the method executes with no
transaction.

**Q: How do you fix it?**
Move the transactional method to a separate bean so the call becomes external — which is usually the
right design anyway. Alternatives are self-injection with `@Lazy`, `AopContext.currentProxy()` with
`exposeProxy`, or `TransactionTemplate` for explicit control.

**Q: JDK dynamic proxies versus CGLIB?**
JDK proxies implement an interface and require one; CGLIB subclasses the class, so it works without
an interface but cannot intercept `final` or `private` methods and cannot proxy a `final` class.
Spring Boot defaults to CGLIB.

**Q: Where in the lifecycle is the proxy created?**
In a `BeanPostProcessor`, in `postProcessAfterInitialization` — after construction and
initialisation. That is why the proxy does not exist during the constructor or `@PostConstruct`, and
why everything injected elsewhere receives the proxy rather than your object.

**Q: What can Spring AOP intercept?**
Only public method execution on Spring-managed beans, via proxies. Not fields, not constructors, not
`private` or `final` methods, and not internal calls. Full AspectJ weaving handles all of those but
requires a compiler plugin or a Java agent.

**Q: Define aspect, pointcut, advice and join point.**
An aspect is the module of cross-cutting behaviour; a join point is a place it can apply — in Spring,
a method execution; a pointcut is an expression selecting join points; advice is the behaviour, such
as `@Around`.

**Q: When would you not use AOP?**
For business logic. AOP adds invisible behaviour with no call-site indication, deepens stack traces,
fails silently in several cases, and is bypassed by unit tests. Reserve it for uniform cross-cutting
concerns and prefer Spring's built-in aspects to bespoke ones.

## 🎙️ Articulation drill

Three minutes: **"Why does `@Transactional` sometimes not work?"**

Explain the mechanism, not the rule: Spring creates a proxy in a `BeanPostProcessor`, everything
injected is the proxy, and an internal call uses `this` — the target — so the proxy is bypassed and
the advice never runs. Then the other silent cases: `private`, `final`, `final class`. Then the fix,
with the observation that splitting the bean is also the better design. Close with how you would
*prove* it: enable the transaction interceptor's TRACE logging.

If you can deliver this fluently, you can explain most of Spring.
