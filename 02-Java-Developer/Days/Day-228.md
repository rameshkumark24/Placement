# Day 228 🗃️

**J-228** · 🗃️ **The server cache** — ⭐⭐ server data was never client state

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: data that lives on your server and is merely displayed in the browser is
> a cache with a staleness policy, not application state — and once you name it correctly, refetching,
> deduplication, invalidation and the loading flicker stop being separate problems and become one
> problem you have been solving since Stage 5.**
>
> Today: ⭐ the reframe, staleness, ⭐⭐ invalidation, and what a query library actually buys.

---

# Part 1 — ⭐⭐ The reframe

```
⭐⭐ TWO KINDS OF DATA, AND THEY NEED DIFFERENT MACHINERY

⭐ CLIENT STATE                   ⭐ SERVER STATE (a CACHE)
⭐  · you own it                    · ⭐⭐ SOMEONE ELSE OWNS IT
⭐  · it is always correct          · ⭐⭐ YOUR COPY GOES STALE
⭐  · synchronous                   · async, can fail, can be slow
⭐  · no other writer               · ⭐ OTHER USERS CHANGE IT
⭐  ⇒ useState                      ⇒ ⭐⭐ A CACHE WITH A TTL AND
⭐  e.g. is the modal open,           AN INVALIDATION STRATEGY
⭐       the form draft              e.g. anything from your API

⭐   ⇒ ⭐⭐ PUTTING SERVER DATA IN useState IS THE CATEGORY ERROR
⭐     THAT CREATES: duplicate fetches, stale screens after a save,
⭐     loading flicker on every back-navigation, and two components
⭐     showing different values for the same row.
```

> ⭐ **You already own this vocabulary.** TTL, staleness, eviction, cache stampede,
> stale-while-revalidate — it is `@Cacheable` / `@CacheEvict` and everything you know about Redis.
> **This is that, in a browser.** The only new parts: the cache is per-tab and dies on refresh.

# Part 2 — Staleness is a setting, not an accident

```jsx
const { data, isPending, isError, error } = useQuery({
  queryKey: ["users", { role }],        // ⭐⭐ THE CACHE KEY
  queryFn: ({ signal }) => api(`/users?role=${role}`, { signal }),
  staleTime: 30_000,                    // ⭐ fresh for 30 s — no refetch
  gcTime: 5 * 60_000,                   // ⭐ keep unused data 5 min
});
```

```
⭐⭐ THE TWO CLOCKS PEOPLE CONFUSE

⭐   staleTime ⇒ ⭐ "how long is this data considered CURRENT?"
⭐               while fresh: ⭐⭐ NO REFETCH AT ALL, even on remount.
⭐               ⭐ ≈ your cache TTL.
⭐   gcTime    ⇒ "how long do I keep it after nothing is using it?"
⭐               ⭐ ≈ EVICTION POLICY. About MEMORY, not correctness.

⭐   ⭐⭐ staleTime: 0 (the default) MEANS EVERY MOUNT REFETCHES.
⭐     Safe, and why people say "it fetches constantly".
⭐     ⇒ ⭐ SET IT DELIBERATELY, PER QUERY.
```

| ⭐ Data | staleTime |
|---|---|
| Reference lists (countries, categories) | ⭐ Hours |
| A user profile | ⭐ 1–5 min |
| A dashboard count | ⭐ 30 s |
| Order status, anything live | ⭐⭐ 0 + refetch on focus/interval |

> ⭐⭐ **The killer feature is deduplication.** Five components asking for `["user", 7]` in the same
> tick produce **one** request. Hand-rolled hooks produce five. ⭐ It is request coalescing — the same
> thing you would build with a `ConcurrentHashMap` of in-flight futures to stop a cache stampede.

# Part 3 — ⭐⭐ Invalidation

```jsx
const qc = useQueryClient();

const { mutate, isPending } = useMutation({
  mutationFn: (body) => api("/users", { method: "POST", body }),
  onSuccess: () => {
    qc.invalidateQueries({ queryKey: ["users"] });   // ⭐⭐ "this is now stale"
  },
});
```

```
⭐⭐ AFTER A WRITE, YOUR CACHE IS WRONG. THREE OPTIONS.

⭐ ① ⭐⭐ INVALIDATE  — mark stale, refetch what is on screen.
⭐    ⭐ THE DEFAULT. Always correct, costs one request.
⭐    ⭐ ≈ @CacheEvict.
⭐ ② WRITE THROUGH  — put the server's response into the cache.
⭐    ⭐ ≈ @CachePut. Only valid if the response is the FULL object.
⭐ ③ ⭐ OPTIMISTIC   — update before the server answers, roll back
⭐    on failure. ⭐⭐ FASTEST AND MOST DANGEROUS — Day 278.

⭐ ⭐⭐ THE HIERARCHICAL KEY IS THE WHOLE DESIGN:
⭐   ["users"]                    invalidating this...
⭐   ["users", { role: "admin" }] ...also invalidates this ✅
⭐   ["users", 7]                 ...and this ✅
⭐   ⇒ ⭐ KEY DESIGN IS CACHE DESIGN — the same care you put into a
⭐     cache-name-plus-key scheme, except the PREFIX gives you
⭐     bulk eviction for free.
```

| ⭐ Bug | Cause |
|---|---|
| Screen stale after a save | ⭐⭐ Forgot to invalidate — **the most common bug with this library** |
| Everything refetches on any write | ⭐ Invalidating a too-short prefix |
| Two components disagree | ⭐⭐ Different key shapes for the same data |

# Part 4 — What you are actually buying

| ⭐ Problem | Hand-rolled (Day 227) | Library |
|---|---|---|
| Loading / error / empty | ✅ you wrote it | ✅ |
| Race + cancel | ✅ you wrote it | ✅ |
| **Dedupe identical requests** | ❌ | ⭐⭐ ✅ |
| **Cache across mounts** (back button) | ❌ | ⭐⭐ ✅ |
| Refetch on focus / reconnect | ❌ | ✅ |
| **Stale-while-revalidate** | ❌ | ⭐⭐ ✅ **no flicker** |
| Retry with backoff | ⭐ you could | ✅ |
| Pagination / infinite scroll | ❌ | ✅ |
| Devtools showing every cache entry | ❌ | ⭐ ✅ |

> ⭐⭐ **This is the correct shape of a "should we add a dependency?" answer** (Day 221): a list of
> named problems it deletes, and an honest note on cost — ~13 KB gzipped, a new mental model, and a
> real chance of misconfiguring `staleTime` and thinking the library is broken.

```
⭐⭐ WHAT IT DOES NOT SOLVE — say this too
⭐   · ⭐ IT IS NOT A STATE MANAGER. Modal open? Still useState.
⭐   · it does not make your API fast
⭐   · ⭐⭐ IT DOES NOT FIX A WATERFALL (Day 227) — it caches the
⭐     round trips, it does not remove the sequence
⭐   · the cache is per-tab and gone on refresh
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "why a query library instead of `useState` plus `useEffect`?"**

Lead with the reframe, because it is the actual insight. **Because server data was never client state.
It's a cache — someone else owns it, my copy goes stale, other users change it underneath me. Once I
name it correctly, refetching, deduplication, invalidation and the loading flicker collapse into one
problem I've been solving since Stage 5, with the same vocabulary: TTL, staleness, eviction.**

Then what it buys, mapped to things you already know. **Deduplication — five components asking for the
same user produce one request instead of five, which is request coalescing against a cache stampede.
A cache that survives unmount, so the back button is instant. Stale-while-revalidate, so I show old data
while fetching and there's no flicker. staleTime is my TTL and gcTime is my eviction policy — and they
get confused constantly.**

Then the part showing you configured rather than copied. **staleTime is a per-query decision. A country
list is an hour, a live order status is zero with refetch on focus. Most "it fetches constantly"
complaints are the default left in place.**

Close honestly. **It's not a state manager — modal open is still useState. It doesn't make my API fast,
and it doesn't fix a waterfall; it caches the round trips, it doesn't remove the sequence. And the most
common bug with it is mine: forgetting to invalidate after a write, which is exactly forgetting a
`@CacheEvict`.**
