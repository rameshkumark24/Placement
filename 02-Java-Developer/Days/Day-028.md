# L-028 · Primitives and their wrappers

## Java's original sin

Java has **two parallel type systems**, and everything today follows from that:

| | Primitives | Objects |
|---|---|---|
| Examples | `int`, `double`, `boolean` | `Integer`, `Double`, `Boolean`, `String` |
| Stored | Value directly (stack local, or inline in an object) | Reference on stack, object on heap *(Day 025)* |
| Default | `0`, `0.0`, `false` | `null` |
| Nullable | ❌ **Cannot be null** | ✅ |
| Methods | None | Yes |
| In generics | ❌ `List<int>` is illegal | ✅ |
| Memory | 4 bytes for an `int` | ~16 bytes for an `Integer` + 4–8 for the reference |

**Why primitives exist:** performance. In 1995, making every integer a heap object was unaffordable.
An `int` is a machine word; an `Integer` is a heap allocation with a header.

**The cost of that decision:** you now need wrappers to put numbers in collections, autoboxing to
make it bearable, and you inherit a family of subtle bugs. *(Project Valhalla is the ongoing attempt
to heal this split with value types.)*

## The eight primitives

| Type | Bits | Range | Wrapper |
|---|---|---|---|
| `byte` | 8 | −128 … 127 | `Byte` |
| `short` | 16 | −32,768 … 32,767 | `Short` |
| `int` | 32 | ±2.1 billion | `Integer` |
| `long` | 64 | ±9.2 quintillion | `Long` |
| `float` | 32 | ~7 decimal digits | `Float` |
| `double` | 64 | ~15 decimal digits | `Double` |
| `char` | 16 | 0 … 65,535 (**unsigned**) | `Character` |
| `boolean` | JVM-defined (~1 byte in arrays) | true/false | `Boolean` |

**Two worth noting:** `char` is the only unsigned type, and `boolean` has no defined size in the
spec — the JVM typically uses an `int` slot for a single boolean and a byte per element in arrays.

### Integer overflow is silent

```java
int max = Integer.MAX_VALUE;    // 2147483647
System.out.println(max + 1);    // -2147483648   ← wraps, no exception
```

**This is a real bug source.** The classic:

```java
int mid = (low + high) / 2;              // 💀 overflows when low+high > 2^31
int mid = low + (high - low) / 2;        // ✅
```

That binary-search bug existed in the JDK's own `Arrays.binarySearch` for nine years. It's on your
[DSA track](../Roadmap/DSA-Parallel-Track.md) trap list — now you know why.

Use `Math.addExact()` when you want an exception instead of silence.

## Autoboxing

Automatic conversion between primitive and wrapper, added in Java 5.

```java
Integer boxed = 42;          // autoboxing   → Integer.valueOf(42)
int unboxed = boxed;         // unboxing     → boxed.intValue()
List<Integer> list = new ArrayList<>();
list.add(5);                 // autoboxed
int x = list.get(0);         // unboxed
```

**Decompile it** (Day 024) and you'll see `Integer.valueOf` and `intValue` calls the compiler
inserted. Autoboxing is pure syntax sugar — the JVM knows nothing about it.

### Trap 1 — `NullPointerException` from unboxing

```java
Map<String, Integer> counts = new HashMap<>();
int n = counts.get("missing");     // 💥 NPE — get() returns null, unboxing calls null.intValue()
```

**The NPE has no visible `.` in the source.** That makes it genuinely confusing the first time. The
line looks like a simple assignment.

```java
Integer n = counts.get("missing");                   // null, fine
int n = counts.getOrDefault("missing", 0);           // ✅ safe
```

**Ternaries are worse**, because the conditional operator forces unboxing to find a common type:

```java
Integer a = null;
int b = 5;
Integer result = (flag) ? a : b;     // 💥 NPE even when flag is true —
                                     //    the ternary unboxes BOTH branches to int
```

That one has caught very experienced people.

### Trap 2 — performance in loops

```java
// 💀 ~2.1 billion Integer objects allocated
Long sum = 0L;
for (long i = 0; i < 2_000_000_000L; i++) sum += i;    // unbox, add, RE-BOX, every iteration

// ✅
long sum = 0L;
```

**Often 10–20× slower**, plus enormous GC pressure (Day 026). One wrong type declaration.

## The Integer cache — the interview question

```java
Integer a = 127, b = 127;
Integer c = 128, d = 128;

a == b     // TRUE
c == d     // FALSE   ← the whole question
```

### Why

`Integer.valueOf()` — which autoboxing calls — **caches instances from −128 to 127**:

```java
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];   // SAME object every time
    return new Integer(i);                                     // NEW object
}
```

So `a` and `b` are literally the same object; `c` and `d` are two different objects with equal
values.

**Why that range:** small integers are overwhelmingly the most common — loop counters, sizes, flags,
IDs. Caching them saves substantial allocation. The upper bound is tunable with
`-XX:AutoBoxCacheMax`, though almost nobody does.

**Caching also applies to** `Byte`, `Short`, `Long` (−128…127), `Character` (0…127) and `Boolean`
(both values). **`Float` and `Double` are never cached** — there's no useful small range.

### The real lesson

**`==` on wrappers compares references. It sometimes works, which is worse than never working.**

Exactly the same trap as `==` on Strings (Day 025). Both "work" for small/pooled values and then
break silently on real data.

```java
Integer a = 1000, b = 1000;
a == b            // false
a.equals(b)       // true      ← always use this
a.intValue() == b.intValue()   // true — explicit unboxing also works
```

**In an interview, don't stop at "use equals".** Say: *"`==` on boxed types compares references, and
`Integer.valueOf` caches −128 to 127 so it appears to work for small values. That's more dangerous
than if it never worked, because the bug only shows up with larger data."*

## When to use which

| Use | When |
|---|---|
| **Primitive** | Default. Local variables, fields, arithmetic, loop counters. |
| **Wrapper** | Generics (`List<Integer>`), when `null` is a meaningful "absent", reflection APIs |

**Never use a wrapper as a counter or accumulator.** Never use `==` on wrappers. If a field can be
absent, a wrapper's `null` is legitimate — but consider whether `Optional` (Day 058) or a default
would be clearer.

**Memory reality:** `int[1_000_000]` is ~4 MB. `List<Integer>` of the same is ~20 MB — object
headers, references, and cache-hostile scattered layout. That's the argument for primitive-specialised
streams (`IntStream`) and libraries like Eclipse Collections or fastutil in hot paths.

## Type this yourself

```java
import java.util.*;

public class BoxingDemo {
    public static void main(String[] args) {

        // ---- 1. The cache ----
        Integer a = 127, b = 127, c = 128, d = 128;
        System.out.println("127 == 127 : " + (a == b));     // true
        System.out.println("128 == 128 : " + (c == d));     // false
        System.out.println("equals     : " + c.equals(d));  // true

        Integer e = Integer.valueOf(127), f = new Integer(127);   // deprecated on purpose
        System.out.println("valueOf==new: " + (e == f));    // false — new always allocates

        // ---- 2. Unboxing NPE ----
        Map<String, Integer> counts = new HashMap<>();
        try {
            int n = counts.get("missing");                  // NPE with no visible dot
            System.out.println(n);
        } catch (NullPointerException ex) {
            System.out.println("\nNPE from unboxing a null — no '.' anywhere on that line");
        }
        System.out.println("Safe: " + counts.getOrDefault("missing", 0));

        // ---- 3. The ternary trap ----
        Integer nullable = null;
        int primitive = 5;
        try {
            Integer r = true ? nullable : primitive;        // NPE even though true picks nullable
            System.out.println(r);
        } catch (NullPointerException ex) {
            System.out.println("Ternary NPE: it unboxes BOTH branches to find a common type");
        }

        // ---- 4. Performance ----
        long start = System.nanoTime();
        Long boxedSum = 0L;
        for (long i = 0; i < 10_000_000L; i++) boxedSum += i;      // boxes every iteration
        System.out.printf("%nBoxed Long:      %,d ms%n", (System.nanoTime() - start) / 1_000_000);

        start = System.nanoTime();
        long primitiveSum = 0L;
        for (long i = 0; i < 10_000_000L; i++) primitiveSum += i;
        System.out.printf("Primitive long:  %,d ms%n", (System.nanoTime() - start) / 1_000_000);

        // ---- 5. Silent overflow ----
        System.out.println("\nMAX_VALUE + 1 = " + (Integer.MAX_VALUE + 1));
        int low = 2_000_000_000, high = 2_000_000_001;
        System.out.println("(low+high)/2      = " + ((low + high) / 2));      // negative!
        System.out.println("low+(high-low)/2  = " + (low + (high - low) / 2)); // correct
    }
}
```

**Decompile it** to prove autoboxing is compiler-inserted:

```bash
javac BoxingDemo.java
javap -c BoxingDemo | grep -E "valueOf|intValue|longValue"
```

You'll see `Integer.valueOf` and `intValue()` calls you never wrote — Day 024's skill applied.

**Record the two timings from part 4.** The ratio is boxing overhead plus GC pressure, measured.

## Common mistakes

| Mistake | Correction |
|---|---|
| `==` on wrappers | Compares references. Works accidentally to 127, then breaks. Use `equals`. |
| Wrapper as an accumulator | Boxes on every iteration. Use the primitive. |
| Assigning a possibly-null wrapper to a primitive | Unboxing NPE with no visible dereference. |
| Mixing wrapper and primitive in a ternary | Both branches unbox — NPE even on the non-null branch. |
| `new Integer(5)` | Deprecated. Always defeats the cache. Use `Integer.valueOf` or autoboxing. |
| Assuming overflow throws | It wraps silently. Use `Math.addExact` if you need detection. |
| `(low + high) / 2` in binary search | Overflows. Use `low + (high - low) / 2`. |

## Interview questions

**Q: Why does `Integer a = 127, b = 127; a == b` print true but `128` prints false?**
> Autoboxing calls `Integer.valueOf`, which caches instances from −128 to 127 and returns the same
> object for values in that range. Above it, each boxing allocates a new object, so `==` compares two
> distinct references. The real lesson is that `==` on wrappers compares identity, so it should never
> be used — and the caching makes it appear to work for small values, which is more dangerous than if
> it never worked.

**Q: What is autoboxing and what does it cost?**
> Automatic conversion between primitives and their wrappers, implemented by the compiler inserting
> `valueOf` and `xxxValue` calls. It costs allocation and GC pressure when it happens in a loop, and
> it introduces `NullPointerException` risk because unboxing a null wrapper throws.

**Q: Why does `int n = map.get(key)` throw NPE?**
> `get` returns `null` when the key is absent, and assigning to a primitive triggers unboxing, which
> calls `intValue()` on null. The NPE is confusing because there's no explicit dereference in the
> source. `getOrDefault` avoids it.

**Q: Primitive or wrapper — how do you choose?**
> Primitives by default, for performance and to eliminate null. Wrappers where the language requires
> an object — generics and collections — or where null genuinely means "absent". Never a wrapper for
> arithmetic or loop counters.

**Q: Why is `List<Integer>` much larger than `int[]`?**
> Each element is a separate heap object with a header, referenced by a pointer, so you pay roughly
> 16 bytes per object plus the reference instead of 4 bytes. The objects are also scattered rather
> than contiguous, which hurts cache locality.
