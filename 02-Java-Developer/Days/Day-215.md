# Part 1 — The subset

You are not learning all of JavaScript. You are learning the ~15% that appears in a React codebase.

```
⭐⭐ WRITE THESE, EVERY DAY
⭐   const / let ....... never var. const by default (≈ final).
⭐   arrow functions ... x => x * 2      (≈ a lambda)
⭐   destructuring ..... const { id, name } = user
⭐   spread ............ { ...user, name: "new" }   [...items, x]
⭐   template literals . `Hello ${name}`  (≈ "Hello %s".formatted)
⭐   map/filter/reduce . ≈ the Stream API, but on the array itself
⭐   optional chaining . user?.profile?.email   (≈ Optional chaining)
⭐   nullish coalescing  count ?? 0     ⭐⭐ NOT || — see Part 3
⭐   async / await ..... Day 216
⭐   modules ........... import / export

⭐⭐ REFUSE THESE, ALWAYS
⭐   var ............... function-scoped, hoisted, a bug generator
⭐   == ................ ⭐⭐ USE === . ALWAYS. NO EXCEPTIONS.
⭐   this in callbacks . arrow functions make it a non-issue
⭐   prototype fiddling  you are not writing a framework
⭐   with, eval ........ dead
```

| Java | JavaScript | ⭐ Note |
|---|---|---|
| `list.stream().map(...).toList()` | `xs.map(x => ...)` | ⭐ No terminal operation — arrays are eager, and there is no `.stream()`/`.collect()` ceremony |
| `.filter(p).findFirst()` | `xs.find(p)` | ⭐ Returns the value or `undefined`, **not an `Optional`** |
| `Map<K,V>` | object literal or `Map` | ⭐⭐ Object keys are **strings only**. `Map` if keys are objects. |
| `null` | `null` **and** `undefined` | ⭐⭐ Two of them. Part 2 — this is the real one. |
| `record Point(int x, int y)` | ⭐ a plain object `{x, y}` | ⭐⭐ No nominal type at runtime. Nothing checks its shape. |
| overloading | ⭐ does not exist | ⭐ One function per name; an options object replaces overloads |
| `void f(int a, int b)` | `function f(a, b = 1)` | ⭐ Defaults exist; **no keyword arguments** — use an options object |
| `class`, `extends` | `class`, `extends` | ⭐ Rarely used in React. Functions and closures dominate. |
| `final` | `const` | ⭐⭐ `const` prevents **rebinding**, not mutation — exactly like `final` on a reference |

# Part 2 — ⭐⭐ `null` vs `undefined`, which is the one that matters

Java has one absence. JavaScript has two, and your Jackson serialiser is about to produce both.

```
⭐⭐ THE DISTINCTION, PRACTICALLY

⭐   undefined = ⭐ "this was never set"
⭐               a missing object property, a missing argument,
⭐               a function with no return
⭐   null      = ⭐ "this was deliberately set to nothing"
⭐               ⭐⭐ AND IT IS WHAT YOUR JSON API SENDS.

⭐   JSON.parse('{"a": null}').a    // null       ⭐ from the wire
⭐   JSON.parse('{}').a             // undefined  ⭐ absent key

⭐⭐ ⇒ A NULL FIELD SERIALISED BY JACKSON ARRIVES AS null.
⭐   A FIELD OMITTED BY @JsonInclude(NON_NULL) ARRIVES AS undefined.
⭐   ⭐⭐ SAME JAVA FIELD. TWO DIFFERENT CLIENT-SIDE CASES,
⭐     DECIDED BY A SERIALISER ANNOTATION YOU PROBABLY SET ONCE
⭐     AND FORGOT.
```

| ⭐ Check | Catches | Use when |
|---|---|---|
| `x == null` | ⭐⭐ **both** `null` and `undefined` | The **one** place `==` is correct. Idiomatic, deliberate. |
| `x === null` | only `null` | You care that the server explicitly sent null. |
| `x === undefined` | only `undefined` | You care that a key was absent. |
| `x ?? fallback` | ⭐⭐ both, and **only** both | Defaults. **This is the one you want.** |
| `x \|\| fallback` | ⭐ also `0`, `""`, `false`, `NaN` | ⚠️ Almost always a bug — see below. |

```java
// ⭐ your Spring DTO
public record ItemDto(
    String name,
    Integer count,     // ⭐⭐ null on the wire (or absent, per @JsonInclude)
    String note        // ⭐ could be "" — a THIRD case
) {}
```

```javascript
// ❌ THE BUG — a real one, and it ships constantly
const count = item.count || 1;      // ⭐⭐ count of 0 BECOMES 1

// ✅ correct
const count = item.count ?? 1;      // only null/undefined fall back
```

> ⭐⭐ **`||` treats `0` and `""` as absent.** Every "the quantity resets to 1" and "the empty note
> shows the placeholder forever" bug is this line. **Default with `??`, always.** In Java you would
> have written `count != null ? count : 1` and been correct by accident; `||` is the trap that has no
> Java equivalent.

# Part 3 — The three traps that survive every style guide

### ⭐⭐ ① Equality

```
⭐   0 == "0"        // true      ⭐⭐ COERCION
⭐   0 == ""         // true
⭐   null == undefined  // true   ⭐ the one useful case
⭐   NaN === NaN     // false     ⭐⭐ NOTHING equals NaN
⭐   [] == false     // true      ⭐ do not think about this

⭐⭐ RULE: === EVERYWHERE. == ONLY AS `x == null`.
⭐   Use Number.isNaN(x), never x === NaN.
⭐   ⭐⭐ NOTE: === IS **NOT** Java's == ON OBJECTS PLUS equals().
⭐     For objects === is reference identity (like Java's ==);
⭐     ⭐ THERE IS NO equals() TO OVERRIDE. See ②.
```

### ⭐⭐ ② Objects and arrays compare by identity — and there is no `equals()`

```javascript
{ a: 1 } === { a: 1 }        // ⭐⭐ false. Always.
[1,2] === [1,2]              // false
```

> ⭐⭐ **In Java you would override `equals()` and `hashCode()` and move on. Here you cannot.** There
> is no value-equality protocol — every comparison of objects is reference identity, full stop. **This
> is not trivia: it is the engine of React's re-render behaviour (Day 232) and of the dependency-array
> bug on Day 226.** Hold onto it.

### ⭐ ③ Mutation is everywhere and React hates it

```javascript
// ❌ mutates — React may not re-render, because the reference is unchanged
items.push(newItem);
user.name = "new";

// ✅ new reference every time
const next = [...items, newItem];
const updated = { ...user, name: "new" };
```

| ⭐ Mutates (avoid on state) | ✅ Returns new |
|---|---|
| `push`, `pop`, `splice`, `sort`, `reverse` | `[...arr, x]`, `slice`, `toSorted`, `toReversed`, `map`, `filter` |

> ⭐ `sort()` **and** `reverse()` mutate in place *and* return the array — unlike
> `stream().sorted()`, which you are used to being non-destructive. `arr.sort()` on React state is a
> genuine bug. Use `toSorted()`, or `[...arr].sort()`.

# Part 4 — Streams, roughly

```javascript
// ⭐ the four you actually use — no .stream(), no .collect()
const names   = users.map(u => u.name);
const active  = users.filter(u => u.isActive);
const found   = users.find(u => u.id === id);        // ⭐ value or undefined
const anyLeft = users.some(u => u.isActive);         // ⭐ .every() for allMatch

// ⭐⭐ groupingBy, roughly
const byRole = Object.groupBy(users, u => u.role);
```

> ⭐ **`reduce` is legitimate for a running total and almost nothing else** — the same advice as
> `Collectors.reducing()`. A `reduce` that builds an object is a `for...of` loop made harder to read
> and impossible to breakpoint. ⭐⭐ And note there is **no lazy pipeline**: every `.map()` allocates a
> new array immediately, so chaining six of them over 100k items really does allocate six arrays.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "you came from Java — what actually bit you in JavaScript?"**

Do not say "the weird equality stuff", which is what everyone says and demonstrates nothing. Lead with
the one that shipped a bug. **Two kinds of absence. A null field arrives as `null` and a field my
serialiser omitted arrives as `undefined` — same Java field, two client cases, decided by a Jackson
annotation I set once and forgot. Then I defaulted with `||` the way I'd have written a null check in
Java, and a count of zero silently became one. `??` only falls back on null and undefined.**

Then the one that explains a whole framework. **Objects compare by reference and there's no `equals()`
to override — no value-equality protocol at all. That's not trivia, it's the engine of React's
re-render behaviour and of the dependency-array bug, and once I understood it the framework stopped
looking arbitrary.**

Close on discipline rather than cleverness. **Most of the language's reputation is features you can
just refuse to use — `var`, `==`, prototypes. The subset I write is small and boring on purpose. The
part I can't refuse is mutation: `sort` and `reverse` mutate in place and still return the array, which
is the opposite of `stream().sorted()`, so they sneak into code that looks pure. On React state that's
a real bug.**
