# Day 298

**L-298** · Why architecture exists — coupling, cohesion, and the cost of change

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Architecture is not the diagram. It is the answer to one question: when this changes, what
> else has to change?**
>
> Every principle in this stage — layers, ports, aggregates, modules — is an attempt to make that
> answer small. **Stage 8 opens here because without this question, patterns become decoration.**

---

# Part 1 — ⭐ Architecture is a bet about change

## ⭐ The only definition worth carrying

> **⭐ Architecture is the set of decisions that are expensive to reverse.**

Everything else is design, and design is cheap to change. **A method name is not architecture. Which
module owns the concept of "price" is.**

**⭐ The practical consequence: you cannot judge an architecture without knowing what is expected to
change.** A system that will never gain a second payment provider does not need a payment port. A
system that gains one every quarter needs nothing else so badly.

| Question | ⭐ What it actually decides |
|---|---|
| ⭐ **What changes often?** | ⭐ where the seams go |
| ⭐ **What changes rarely?** | what may be coupled freely |
| ⭐ **What changes for different reasons?** | ⭐ what must be separated (Day 090's SRP, by actor) |
| ⭐ **What always changes together?** | ⭐ **what must live together** |

**⭐ That last row is the one people get backwards.** Two things that always change together and are
kept in separate modules produce every change as a two-module change, a two-PR change, and
eventually a two-team change. **Separation has a cost, and the cost is paid on every change that
crosses it.**

## ⭐ The change-cost test — run this today

Pick a plausible change to your flagship. Not a hypothetical one — one a stakeholder could actually
ask for tomorrow.

```
⭐ "Add a 'currency' to every price."
⭐ "Support a second notification channel."
⭐ "One customer wants an approval step before dispatch."
```

Then answer, **without opening the editor**:

1. **How many files do I open?**
2. **How many of them are in a different package than the concept I am changing?**
3. **Can I be sure I found them all?**

**⭐ Question 3 is the real one.** A change that touches twelve files you can enumerate confidently is
fine. **A change that touches four files you are not sure about is architecture debt**, because the
uncertainty is what produces the production bug.

# Part 2 — ⭐ Coupling, precisely

**⭐ "Coupled" is used to mean nine different things.** Naming them is what makes it a tool rather
than an insult.

| Kind | Meaning | ⭐ Severity |
|---|---|---|
| ⭐ **Content** | one module reaches into another's internals | ⭐ worst |
| **Common** | both depend on shared mutable state | ⭐ very bad — a global, a static, a shared table |
| **Control** | one passes a flag telling the other *how* to behave | bad — `process(order, true)` |
| **Stamp** | passing a whole object when a field is needed | ⭐ mild — but it drags the type along |
| ⭐ **Data** | passing exactly what is needed | ⭐ **the goal** |
| ⭐ **Temporal** | A must be called before B, and nothing enforces it | ⭐ **invisible and dangerous** |

**⭐ Temporal coupling is the one that hurts in Java services**, because the compiler cannot see it:

```java
service.validate(order);      // ⭐ if you forget this line,
service.submit(order);        // ⭐ nothing complains — until production
```

**⭐ The fix is a type, not a comment.** `submit(ValidatedOrder)` cannot be called without validating,
because a `ValidatedOrder` can only be produced by `validate`. **That is Day 304's whole argument for
value objects, arriving early.**

## ⭐ Connascence — the sharper tool

**⭐ Coupling tells you two things are connected. Connascence tells you how badly, and lets you rank
fixes.** Two components are connascent if changing one requires changing the other.

```
⭐ WEAKEST → STRONGEST      (static — visible in the source)
   name → type → meaning → algorithm → position

⭐ (dynamic — only visible at runtime, all worse than any static form)
   execution order → timing → value → identity
```

| Form | Example | ⭐ Improve it by |
|---|---|---|
| **Name** | both use `orderId` | ⭐ fine — this is unavoidable and cheap |
| **Type** | both agree it is a `long` | fine |
| ⭐ **Meaning** | ⭐ `0` means pending, `1` means shipped | ⭐ **an enum — connascence of type** |
| **Algorithm** | both sides hash the same way | extract it to one place |
| ⭐ **Position** | ⭐ `new Rect(2, 5, 8, 3)` | ⭐ **a builder or named record** |
| ⭐ **Execution** | validate before submit | ⭐ **a type, as above** |
| ⭐ **Value** | two constants must stay equal | ⭐ derive one from the other |
| ⭐ **Identity** | both must reference the *same* instance | ⭐ **hardest — redesign** |

**⭐ Three rules that make this operational:**

1. ⭐ **Rule of degree** — connascence of meaning across 3 classes is annoying; across 300 it is
   fatal. **The same smell has different urgency at different scale.**
2. ⭐ **Rule of locality** — ⭐ **strong connascence is fine inside a small class and unacceptable
   across a module boundary.** Two private methods sharing execution order is not a problem. Two
   services sharing it is.
3. ⭐ **Rule of direction** — refactor toward weaker forms. `0`/`1` → enum is meaning → type, and it is
   a genuine improvement rather than a stylistic one.

> **⭐ This is the vocabulary that makes design review objective.** "I don't like this" becomes "this
> is connascence of meaning across four modules, and an enum makes it connascence of type."

# Part 3 — ⭐ Cohesion, and the package that proves you have none

**⭐ Cohesion is how well the things inside a module belong together.** Ranked, worst to best:

| Level | The module groups things because… | Verdict |
|---|---|---|
| ⭐ **Coincidental** | ⭐ they had nowhere else to go | ⭐ **`utils`, `helpers`, `common`** |
| **Logical** | they are the same *kind* of thing | ⭐ **`controllers`, `services`, `dtos`** |
| **Temporal** | they happen at the same time | `StartupTasks` |
| **Procedural / communicational** | they follow one another, or touch the same data | acceptable |
| ⭐ **Functional** | ⭐ **they collaborate to do one job** | ⭐ **the goal** |

**⭐ Two diagnoses you can make in ten seconds:**

- ⭐ **A `common` or `utils` package that more than three modules import** is coincidental cohesion
  with a global blast radius. Every change to it is a change to everything.
- ⭐ **Packages named `controller`, `service`, `repository`, `dto`** are *logical* cohesion — grouping
  by what things **are** rather than what they **do**. That is Day 141's package-by-layer, and
  Day 299 is entirely about why it rots.

> **⭐ The test: open one package. Does it contain one feature, or one technical category?** If a
> single user-visible change makes you edit four packages, your cohesion is logical and your coupling
> follows the change, not the structure.

## ⭐ Measure it — your repo already knows

**⭐ Git history is an objective cohesion metric**, and almost nobody uses it:

```bash
# ⭐ Which files change together most often? (temporal coupling, measured)
git log --name-only --pretty=format:"%H" --since="6 months ago"
```

**⭐ Two files that changed together in 80% of commits belong in the same module** — whatever the
folder structure says. **Two files in the same package that never change together are only
neighbours, not relatives.**

**⭐ This is the single most useful architecture exercise on a codebase you inherited**, and it is
exactly what Day 288's audit was doing when it looked for what the code was really shaped like.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Judging architecture without naming the expected change | ⭐ every argument becomes taste |
| ⭐ Separating things that always change together | ⭐ every change crosses a boundary, forever |
| Treating "coupled" as one thing | you cannot rank fixes |
| ⭐ Ignoring temporal coupling | ⭐ the compiler cannot see it; production can |
| ⭐ A `utils` package | ⭐ coincidental cohesion with global reach |
| Packages by technical type | ⭐ one feature change touches four packages |
| ⭐ Strong connascence across module boundaries | ⭐ the locality rule, violated |
| Adding abstraction "for flexibility" | flexibility for a change that never comes is pure cost |

## Interview questions

**Q: What is software architecture?**
The decisions that are expensive to reverse — which module owns a concept, where the transaction and
consistency boundaries are, what talks to what. Everything cheap to change is design. That definition
matters because it tells you where to spend review time: on the decisions you cannot walk back
cheaply.

**Q: How do you decide where to draw a boundary?**
By what changes, and for what reason. Things that change together for the same reason belong
together; things that change for different reasons belong apart — Day 090's SRP stated by actor. And
I check it empirically: files that co-change in git history are coupled in fact, whatever the package
structure claims.

**Q: What is connascence and why prefer it to "coupling"?**
Connascence is coupling with a ranking. It names nine forms from weakest (name) to strongest
(identity), which turns "this is coupled" into "this is connascence of meaning, and an enum makes it
connascence of type" — a concrete, arguable improvement. The locality rule is what makes it
practical: strong connascence is fine inside a class and unacceptable across a module boundary.

**Q: Is coupling always bad?**
No — a system with no coupling does nothing. The goal is weak, few, and visible dependencies pointing
in a deliberate direction. And decoupling has a real cost: every boundary you add is paid on every
change that crosses it, so separating things that always change together makes the system worse.

**Q: What is the worst kind of package in a codebase?**
`utils` or `common` — coincidental cohesion imported by everything, so it has global blast radius and
no owner. It is also where domain logic goes to hide, which is how the domain ends up with no home at
all.

## Mini task

1. **Run the change-cost test on your flagship** for three plausible changes. Write down the file
   count and, for each, whether you are *certain* you found them all.
2. **Extract the co-change data from your own repo.** List the top ten file pairs. **Mark any pair
   that lives in different packages** — each one is a boundary drawn in the wrong place.
3. Find one instance of **temporal coupling** in your code and remove it with a type.
4. Find one instance of **connascence of meaning** (a magic number, a boolean flag, a string status)
   and refactor it up to connascence of type. **Note how many files you had to touch** — that number
   is the degree.
5. **List every module that imports your `common`/`utils` package.** If it is more than three, split
   it by what the contents actually serve.
6. ⭐ Write a paragraph titled *"What this system is optimised to change"*. If you cannot write it,
   the architecture is accidental.

# 🚪 Exit questions

1. Define architecture in one sentence and say what it excludes.
2. What are the four questions that decide where a boundary goes?
3. Why is separating things that change together a mistake?
4. Name six kinds of coupling, worst to best.
5. What is temporal coupling and why is it the dangerous one in Java?
6. Give the connascence ladder, static and dynamic.
7. State the rules of degree, locality and direction.
8. Give the cohesion levels, and the two you can diagnose from package names alone.
9. How do you measure coupling empirically without reading the code?
10. What is the cost of a boundary, and when is it not worth paying?

**Two minutes:** *"How would you know whether a codebase you just joined is well architected?"*

**⭐ The marker: you name the change-cost test and the co-change measurement, rather than listing
patterns.** Someone who answers "does it use hexagonal architecture" has described a style; someone
who answers "I would pick three likely changes and count the files, then check git for what actually
co-changes" has described a method.
