# Part 1 — L-062 · Exception design

## The single organising question

> **Can this code do something meaningful about the failure?**

- **Yes** → catch it here, do the thing, do not rethrow.
- **No, but I can add context** → wrap with context and rethrow.
- **No, and I have nothing to add** → do not catch at all. Let it pass.

Almost every bad exception handling decision is a violation of the third case: catching something
you cannot act on, because catching *feels* responsible. It is not. An empty or log-only catch
block converts a loud failure into a quiet wrong answer, and quiet wrong answers are the most
expensive bugs there are.

## The four things a catch block may legitimately do

1. **Recover** — fall back to a cached value, a default, a secondary provider.
2. **Retry** — for a *transient* failure only, with backoff and a cap (Day 021's rules apply).
3. **Translate** — wrap in a layer-appropriate type, preserving the cause.
4. **Terminate cleanly** — at the top of the stack: log it once, return a 500, shut down.

Anything else is a smell. Notice "log it" is not on the list by itself — logging is what the
*terminate* case does, once, at the top.

## Where the boundary goes

```
┌─────────────────────────────────────────────┐
│ Controller / HTTP layer                     │  ← ONE global handler.
│   @RestControllerAdvice                     │    Maps exception type → status code.
├─────────────────────────────────────────────┤    Logs once. This is the only
│ Service layer  (business rules)             │    place that logs a stack trace.
│   throws domain exceptions:                 │
│   InsufficientFundsException                │  ← translate infra → domain HERE
├─────────────────────────────────────────────┤
│ Repository / DAO                            │
│   SQLException ──► DataAccessException      │  ← translate at the edge of the
├─────────────────────────────────────────────┤    technology
│ Driver / JDBC / HTTP client                 │
└─────────────────────────────────────────────┘
```

The rule the diagram encodes: **an exception type should never travel more than one layer above the
layer that understands it.** A `SQLException` reaching the controller means your persistence choice
has leaked into your web layer, and swapping the database would now change HTTP behaviour.

This is exactly what Spring does, and knowing it now means Stage 4's `@ControllerAdvice` and
`DataAccessException` will read as an implementation of a principle rather than framework trivia.

## Translation done properly

```java
// Repository — the edge of JDBC
public Optional<Account> findById(String id) {
    try {
        return Optional.ofNullable(jdbc.queryForObject(SQL, MAPPER, id));
    } catch (EmptyResultDataAccessException e) {
        return Optional.empty();                 // RECOVER — absence is not an error
    } catch (DataAccessException e) {
        throw new AccountLookupException(id, e); // TRANSLATE — keep the cause
    }
}
```

Two decisions in nine lines:

**"Not found" is not an exception.** It is an expected outcome of a lookup, so it is modelled in the
return type (`Optional`, Day 058) instead. Reserve exceptions for the *exceptional*. If your code
throws `NotFoundException` on half its calls, the exception is doing the job of a return value and
paying `fillInStackTrace` for the privilege.

**The infrastructure failure is translated but not swallowed.** `AccountLookupException` carries the
id — the thing the operator will search the logs for — and the cause preserves the SQL state.

## Context is the whole point of wrapping

Compare these two production log lines:

```
java.sql.SQLException: Connection is closed
```

```
com.acme.OrderProcessingException: Failed to process order ORD-88213
        for customer CUST-4471 during payment capture
    Caused by: java.sql.SQLException: Connection is closed
```

Same root cause. The second one tells you *which* order, *which* customer, and *which* step — and
you can start work immediately. **Wrapping without adding context is pure cost:** you paid an extra
frame and a new type and told the reader nothing.

So the test for a wrap is: *does the new exception say something the cause did not?* If not, do not
wrap. Let it propagate.

## Never swallow — and the two acceptable exceptions to that

```java
catch (Exception e) { }                      // 💀 never
catch (Exception e) { return null; }         // 💀 worse — the NPE appears three layers up
catch (Exception e) { e.printStackTrace(); } // 💀 unstructured, stderr, invisible in prod
```

Two cases where ignoring is genuinely correct — and both must say so explicitly:

```java
try {
    Thread.sleep(delay);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();       // RESTORE the flag — see below
    return;
}

try {
    return Integer.parseInt(userInput);
} catch (NumberFormatException e) {
    return defaultValue;                      // intentional: bad input has a defined fallback
}
```

**`InterruptedException` deserves its own paragraph**, because swallowing it is the most common
concurrency bug in Java and it comes back in Day 071. Catching it *clears* the thread's interrupt
flag. If you swallow it, the shutdown signal your executor just sent is now gone, and your thread
pool will hang on `shutdownNow()` forever. You have exactly two correct responses: propagate the
exception, or restore the flag with `Thread.currentThread().interrupt()` and return promptly.

## Exceptions across a service boundary

Once a call crosses a process boundary, exception *types* stop existing. What survives is a status
code and a body. So your top-level handler is a translation table:

```java
@RestControllerAdvice
class GlobalHandler {

    @ExceptionHandler(ValidationException.class)
    ResponseEntity<Problem> onValidation(ValidationException e) {
        return ResponseEntity.badRequest().body(Problem.of(400, e.getMessage()));
    }

    @ExceptionHandler(InsufficientFundsException.class)
    ResponseEntity<Problem> onFunds(InsufficientFundsException e) {
        return ResponseEntity.status(422).body(
            Problem.of(422, "Insufficient funds", Map.of("shortfall", e.getShortfallCents())));
    }

    @ExceptionHandler(Exception.class)
    ResponseEntity<Problem> onAnythingElse(Exception e) {
        String ref = UUID.randomUUID().toString();
        log.error("unhandled ref={}", ref, e);                 // the ONLY stack trace log
        return ResponseEntity.status(500).body(
            Problem.of(500, "Internal error", Map.of("ref", ref)));   // no internals leaked
    }
}
```

The `ref` pattern is worth stealing permanently. The user sees an opaque id, the log holds the full
trace keyed by that id, and support can jump straight to the incident. Meanwhile **the response body
never contains a stack trace, a SQL fragment, or a class name** — Day 020's security reasoning
applies here: leaked internals are reconnaissance. A stack trace tells an attacker your framework,
your versions, and often your directory layout.

Map the status codes deliberately (Day 010): 400 for malformed, 401 unauthenticated, 403
authenticated-but-forbidden, 404 absent, 409 conflict, 422 semantically invalid, 429 rate-limited,
500 our fault, 503 try later.

## Fail fast

```java
public Order(String id, List<Item> items, Money total) {
    this.id = Objects.requireNonNull(id, "id");
    if (items.isEmpty()) throw new IllegalArgumentException("order needs items");
    if (total.isNegative()) throw new IllegalArgumentException("total < 0: " + total);
    this.items = List.copyOf(items);          // Day 034A
    this.total = total;
}
```

An invalid object that is *allowed to exist* fails later, somewhere else, with a symptom that has
nothing to do with the cause. Validating in the constructor means the stack trace points at the
code that built the bad object — the code you actually need to fix.

Include the offending value in the message. `"total < 0: -450"` is debuggable; `"invalid total"` is
a second round trip.

## Code to type — retry that is not a retry storm

```java
public class Retry {

    static <T> T withRetry(Callable<T> op, int maxAttempts) throws Exception {
        Exception last = null;
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            try {
                return op.call();
            } catch (TransientException e) {        // ONLY transient failures retry
                last = e;
                if (attempt == maxAttempts) break;
                long base   = Math.min(1000L * (1L << (attempt - 1)), 30_000L);
                long jitter = ThreadLocalRandom.current().nextLong(base / 2);
                Thread.sleep(base / 2 + jitter);    // full-ish jitter
            } catch (Exception permanent) {
                throw permanent;                    // 400s never retry
            }
        }
        throw new RetryExhaustedException(maxAttempts, last);
    }
}
```

Four properties, each of which is a production incident if you omit it: a **cap** on attempts, an
**exponential** base, **jitter** so a thousand clients do not retry in lockstep, and a **hard
distinction between transient and permanent** — retrying a 400 is a loop that will never succeed and
will bill you for every attempt. This is the same rule the Web and App domains state as an API
safety invariant; here it is in Java.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Catching what you cannot act on | Failures become silent wrong answers |
| Wrapping with no added context | Extra noise, no information |
| Logging at every layer | One incident looks like four |
| Swallowing `InterruptedException` | Shutdown hangs; the pool never terminates |
| Exceptions for expected outcomes | Slow, and it obscures which failures are real |
| Stack traces in HTTP responses | Free reconnaissance for an attacker |
| Retrying non-transient failures | A guaranteed-to-fail loop that costs money |
| Validating late | The trace points at the symptom, not the cause |

## Interview questions

**Q: How do you decide whether to catch an exception?**
By asking whether this code can do something meaningful about it — recover, retry a transient
failure, add context and translate, or terminate cleanly. If none apply, do not catch.

**Q: How do exceptions cross layers in a well-designed system?**
Each layer translates the layer below into its own vocabulary, preserving the cause. Infrastructure
types never reach the web layer. One global handler maps domain types to status codes and logs once.

**Q: What is wrong with `catch (Exception e) { log.error(e); throw e; }`?**
It logs and rethrows, so the same incident is recorded at every layer, and it adds no context. Log
where you finally handle; propagate everywhere else.

**Q: What should an API return when something fails?**
A correct status code and a structured body with a stable machine-readable error code, a
human-readable message safe to display, and a correlation reference — never internals.

**Q: Why is swallowing `InterruptedException` dangerous?**
Catching it clears the interrupt flag, which is the cooperative cancellation signal. The thread no
longer knows it was asked to stop, and graceful shutdown hangs.
