# Day 098

**L-098** · TDD in practice — red / green / refactor on a real feature

**Time:** 3 hrs · **Mode:** NEW

> Today is mostly doing, not reading. You will build one real feature test-first, from the first
> failing assertion to a complete implementation, and watch the design emerge from the tests rather
> than being decided upfront.
>
> It also contains the honest part: **where TDD works, and where it does not.** Advocates who claim
> it always works are the reason many developers dismiss it.

---

# Part 1 — The loop

```
   ┌──────────────────────────────────────┐
   │  1. RED     write a failing test     │   ← it MUST fail, and for the right reason
   │  2. GREEN   make it pass, minimally  │   ← ugly is fine here
   │  3. REFACTOR clean up, tests green   │   ← Day 096, in miniature
   └──────────────────────────────────────┘
                cycle: 2–10 minutes
```

Three rules that people break, and what breaking each costs:

**1. Never write production code without a failing test.** Otherwise you write code you cannot be
sure is exercised.

**2. Watch the test fail first.** A test that has never failed might be testing nothing — a typo'd
assertion, a mis-annotated method, a stub that always returns true. Watching red is *verifying the
test*.

**3. Write the minimum to go green.** Deliberately, even absurdly minimal. This is the rule that
feels stupid and is the most valuable, because it forces the *next* test to be the one that drives
real generality.

## What TDD is actually for

> **TDD is a design technique that produces tests as a by-product.**

The tests are valuable. The larger benefit is that writing the test first forces you to use your API
before you build it, from the caller's perspective — and code that is awkward to call is awkward to
call *for everyone*, forever. You find that out in thirty seconds instead of after three classes
depend on it.

Secondary benefits worth naming: you always know the code is fully covered, you never debug for long
(the last two minutes of work is the only suspect), and you get a natural stopping point — when the
test passes, you are done, which resists gold-plating (Day 092's YAGNI).

# Part 2 — Do it: a rate limiter

Build a token-bucket rate limiter test-first. **Type every step. Do not read ahead to the final
implementation.**

The requirement: *allow N requests per window per key; reject the rest; refill over time.*

## Cycle 1 — the simplest thing that can fail

```java
// RED
@Test void allowsTheFirstRequest() {
    RateLimiter limiter = new RateLimiter(1, Duration.ofSeconds(1));
    assertTrue(limiter.tryAcquire("user-1"));
}
```

It does not compile. **That counts as red** — compilation failure is the first form of failing.

```java
// GREEN — minimally. Yes, really.
public class RateLimiter {
    public RateLimiter(int permits, Duration window) { }
    public boolean tryAcquire(String key) { return true; }
}
```

Returning a constant feels like cheating. It is not — it is the discipline. The next test will make
it insufficient, and that is how you know each piece of complexity was *demanded* by a requirement.

## Cycle 2 — force the counter

```java
// RED
@Test void rejectsTheSecondRequestWhenLimitIsOne() {
    RateLimiter limiter = new RateLimiter(1, Duration.ofSeconds(1));
    assertTrue(limiter.tryAcquire("user-1"));
    assertFalse(limiter.tryAcquire("user-1"));         // fails: returns true
}
```

```java
// GREEN
private int used = 0;
private final int permits;

public boolean tryAcquire(String key) {
    if (used >= permits) return false;
    used++;
    return true;
}
```

## Cycle 3 — force per-key state

```java
// RED
@Test void limitsEachKeyIndependently() {
    RateLimiter limiter = new RateLimiter(1, Duration.ofSeconds(1));
    assertTrue(limiter.tryAcquire("user-1"));
    assertTrue(limiter.tryAcquire("user-2"));          // fails: shared counter
}
```

```java
// GREEN
private final Map<String, Integer> used = new HashMap<>();

public boolean tryAcquire(String key) {
    int count = used.getOrDefault(key, 0);
    if (count >= permits) return false;
    used.put(key, count + 1);
    return true;
}
```

**Notice what just happened.** You did not decide "it needs a map" upfront — the third test made a
single counter impossible. That is the design emerging from requirements rather than from
speculation, and it is the whole argument for TDD.

## Cycle 4 — time, and the design decision it forces

```java
// RED
@Test void refillsAfterTheWindowElapses() {
    MutableClock clock = MutableClock.at("2026-08-14T10:00:00Z");
    RateLimiter limiter = new RateLimiter(1, Duration.ofSeconds(1), clock);

    assertTrue(limiter.tryAcquire("user-1"));
    assertFalse(limiter.tryAcquire("user-1"));

    clock.advance(Duration.ofSeconds(1));
    assertTrue(limiter.tryAcquire("user-1"));          // refilled
}
```

**This test cannot be written without injecting a `Clock`** — the alternative is `Thread.sleep(1000)`
in every test, which Day 097 ruled out. TDD surfaced the dependency because the test demanded it.
That is design pressure doing its job (Day 075's point about `Clock`, arrived at from the other
side).

```java
// GREEN
record Bucket(int used, Instant windowStart) { }

private final Map<String, Bucket> buckets = new HashMap<>();
private final Clock clock;

public boolean tryAcquire(String key) {
    Instant now = clock.instant();
    Bucket b = buckets.get(key);
    if (b == null || now.isAfter(b.windowStart().plus(window))) {
        buckets.put(key, new Bucket(1, now));
        return true;
    }
    if (b.used() >= permits) return false;
    buckets.put(key, new Bucket(b.used() + 1, b.windowStart()));
    return true;
}
```

## Cycle 5 — REFACTOR (tests stay green)

Nothing new is added here; this is Day 096 in miniature. Extract the decision, name the concepts,
remove the duplicated `buckets.put`:

```java
public class RateLimiter {
    private final int permits;
    private final Duration window;
    private final Clock clock;
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();

    public boolean tryAcquire(String key) {
        Instant now = clock.instant();
        Bucket updated = buckets.compute(key, (k, current) ->
                current == null || current.hasExpired(now, window)
                        ? Bucket.startingAt(now)
                        : current.consumeIfPossible(permits));
        return updated.lastAcquireSucceeded();
    }

    private record Bucket(int used, Instant windowStart, boolean lastAcquireSucceeded) {
        static Bucket startingAt(Instant now) { return new Bucket(1, now, true); }
        boolean hasExpired(Instant now, Duration window) {
            return now.isAfter(windowStart.plus(window));
        }
        Bucket consumeIfPossible(int permits) {
            return used >= permits ? new Bucket(used, windowStart, false)
                                   : new Bucket(used + 1, windowStart, true);
        }
    }
}
```

Note that `compute` on a `ConcurrentHashMap` (Day 053) also made this atomic per key — a
concurrency property that fell out of the cleanup rather than being bolted on.

## Cycle 6 onward — keep going

Write these yourself, one cycle each:

- Rejects when the limit is 5 and 6 requests arrive in the window.
- Partial refill: after half a window, are permits restored proportionally? *(This test forces you to
  decide between a fixed window and a true token bucket — a real design question surfaced by a
  test.)*
- Concurrency: 100 threads, limit 10 — exactly 10 succeed. Use a `CountDownLatch` starting pistol
  (Day 070).
- Memory: keys never seen again must not accumulate. **This is Day 027's leak, and it is the test
  most people never write.**

# Part 3 — Technique

## Triangulation

When you are unsure of the general rule, write a second, different test to force generality:

```java
assertEquals(4, sum(2, 2));      // GREEN: return 4;   ← absurd, and deliberate
assertEquals(7, sum(3, 4));      // now `return 4` is impossible → return a + b;
```

Use it when the abstraction is not obvious. When it is obvious, just write the real implementation —
this is a tool, not a ritual.

## The three implementation strategies

| Strategy | When |
|---|---|
| **Fake it** | Return a constant; let the next test force generality |
| **Obvious implementation** | You know the answer — write it. Most of the time. |
| **Triangulate** | The general rule is unclear; a second case reveals it |

## Outside-in vs inside-out

**Inside-out (classicist/Chicago):** start with the domain objects, build upward, use real
collaborators, test state. Produces solid units; risks building things the outside never needs.

**Outside-in (mockist/London):** start at the API boundary, mock collaborators that do not exist yet,
work inward. Ensures everything you build is needed; risks over-mocking and tests coupled to
interactions (Day 075).

**In practice:** outside-in to discover the interfaces, inside-out to build the logic behind them,
and Day 097's rule to keep the mocks few.

## When a test is hard to write

**That is information, not an obstacle.** The mapping is reliable:

| The test is hard because… | The design problem |
|---|---|
| Setup is 30 lines | Too many dependencies (Day 090's SRP) |
| You need six mocks | Same |
| You cannot construct the object in isolation | Hidden dependencies, `new` in the constructor |
| You must mock a static or a clock | Hard-coded dependency (Day 075) |
| You must test through three layers | The behaviour is in the wrong place (Feature Envy, Day 096) |
| You cannot assert without reflection | The behaviour is not exposed — is it needed at all? |

**Fix the design, not the test.**

# Part 4 — Where TDD does not fit

The honest section, and the one that makes the rest credible.

**TDD works well for:** business logic with clear inputs and outputs, algorithms, parsers, state
machines, bug fixes (reproduce with a failing test first — always), and refactoring safety nets.

**TDD works badly for:**

- **Exploratory work.** When you do not know what you are building, tests lock in a shape you are
  about to discard. **Spike first — write throwaway code to learn — then delete it and TDD the real
  thing** with what you now know.
- **UI layout and visual design.** You cannot assert "looks right". Snapshot tests help a little and
  break constantly.
- **Configuration and glue.** Testing that Spring wires two beans together tests Spring.
- **Performance work.** You need benchmarks and profiles (Day 076), not unit tests.
- **Code driven by an external contract you cannot yet see** — start with a real call, learn the
  actual response shape, then write tests against it.

> **Test-after is acceptable. Test-never is not.** The value is in having the tests; TDD is one
> reliable way to end up with them, not a moral position.

The strongest genuinely universal case is **bug fixing**: reproduce the bug with a failing test
before you fix it. That test proves the fix works and prevents the regression forever, and it costs
almost nothing because you had to reproduce the bug anyway.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Writing the test after the code, calling it TDD | No design pressure; the test is shaped by the code |
| Not watching the test fail | The test may verify nothing |
| Writing too much to get green | You skipped the design pressure of the next test |
| Skipping refactor | TDD without step 3 produces working, ugly code |
| Test cycles longer than ~10 minutes | Debugging returns |
| Testing implementation details | Every refactor breaks the tests (Day 075) |
| TDD-ing exploratory work | Locks in a design you are about to discard |
| Treating TDD as a moral position | Alienates people; the goal is tests, not ritual |

## Interview questions

**Q: What is TDD and what is it for?**
Red, green, refactor in short cycles. It is a design technique that produces tests as a by-product —
writing the test first forces you to use your API from the caller's side before committing to it.

**Q: Why must you watch the test fail?**
To verify the test. A test that never failed may be asserting nothing — a typo, a missing
annotation, a stub returning true.

**Q: Why write the minimum to pass, even absurdly?**
So that every piece of complexity is demanded by a requirement rather than by speculation. The next
test forces the generalisation, which is how the design emerges from the tests.

**Q: What does it mean when a test is hard to write?**
It is a design signal. Long setup means too many dependencies; needing to mock a clock or a static
means a hard-coded dependency; testing through three layers means the behaviour lives in the wrong
place. Fix the design.

**Q: When would you not use TDD?**
Exploratory work — spike first, then delete and TDD with what you learned — plus UI layout,
configuration glue and performance work. Test-after is fine; test-never is not.

**Q: What is triangulation?**
Writing a second, different test to force a general implementation when a constant would have passed
the first. It is a tool for when the abstraction is unclear, not a rule to apply always.

**Q: Do you TDD bug fixes?**
Always. Reproduce with a failing test first — you had to reproduce it anyway, and the test proves
the fix and prevents the regression.

## Mini task

1. Build the rate limiter through all six cycles yourself, committing after each green and each
   refactor. Do not look ahead.
2. Write the concurrency test with 100 threads and a latch. Note whether your implementation was
   already correct, and why.
3. Write the eviction test for keys never seen again, and fix the leak it exposes.
4. TDD a second thing from scratch: a Roman-numeral converter, an FSM for an order lifecycle
   (Day 095), or a CSV parser that handles quoted commas.
5. Take a bug you fixed recently. Write the failing test that would have caught it, retroactively.
   Note how long it took.
6. Try TDD on something exploratory and stop when it stops helping. Write down where the line was —
   that judgement is the point of the exercise.
7. Find a test in your codebase that breaks whenever you refactor. Diagnose whether it tests
   behaviour or implementation, and rewrite it.

## 🎙️ Articulation drill

Two minutes: **"Do you practise TDD?"**

Answer honestly and specifically. Describe the loop, give a concrete example where writing the test
first changed your design — the `Clock` injection is a perfect one — then name where you do not use
it and why. An answer with a boundary is far more credible than "yes, always", and interviewers who
know the technique will recognise the difference immediately.
