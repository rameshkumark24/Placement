# Day 241 📊

**J-241** · 📊 **Frontend performance** — ⭐⭐ why Actuator said 40 ms and the user waited 3 seconds

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: your server metrics measure the part of the wait you are responsible for
> and not the part the user experiences — DNS, TLS, the HTML, the bundle, the parse, the render and a
> waterfall of dependent requests all happen outside your histogram, and together they are usually the
> majority of the time.**
>
> Today: ⭐ the three vitals, ⭐⭐ the critical path, field vs lab, and the budget.

---

# Part 1 — ⭐⭐ Where the three seconds went

```
⭐⭐ MICROMETER: p99 = 40 ms. THE USER: 2.8 s. THE ACCOUNTING:

⭐   DNS + TCP + TLS ................  300 ms  ⭐ invisible to you
⭐   HTML (TTFB) ....................  150 ms
⭐   ⭐⭐ JS BUNDLE DOWNLOAD (600 KB) .. 1,200 ms  ⭐ ON 4G. THE BIG ONE.
⭐   ⭐ PARSE + EXECUTE ..............  400 ms  ⭐⭐ WORSE ON A CHEAP
⭐                                              PHONE THAN DOWNLOAD
⭐   React mount ....................  100 ms
⭐   ⭐ API CALL (your 40 ms) ........   40 ms  ⭐⭐ ← ALL YOU MEASURED
⭐   ⭐⭐ WATERFALL: 2 dependent calls .  400 ms
⭐   render + paint .................  200 ms
⭐                                    ─────────
⭐                                     ~2.8 s

⭐   ⇒ ⭐⭐ YOUR 40 ms IS **1.4%** OF THE WAIT.
⭐     ⭐ Optimising it to 20 ms is invisible. The bundle and the
⭐       waterfall are 57%.
```

> ⭐⭐ **This is why backend engineers under-invest here: your dashboards are honest about your layer
> and silent about every other one.** ⭐ It is the same lesson as a p99 that looks fine because you
> measured inside the connection pool rather than including the wait to acquire a connection.

# Part 2 — The three vitals

| ⭐ Metric | Measures | Good | ⭐⭐ Usual cause when bad |
|---|---|---|---|
| **LCP** — Largest Contentful Paint | ⭐ When the main content appears | < 2.5 s | ⭐⭐ A huge unoptimised hero image, slow TTFB, render-blocking resources |
| **INP** — Interaction to Next Paint | ⭐⭐ Responsiveness to *every* interaction | < 200 ms | ⭐ Long tasks blocking the main thread |
| **CLS** — Cumulative Layout Shift | ⭐ How much the page jumps | < 0.1 | ⭐⭐ Images with no dimensions, **a spinner replaced by taller content** (Day 240) |

```
⭐⭐ THE ONE PEOPLE MISUNDERSTAND: INP.
⭐   It is not "load time". It is ⭐ EVERY CLICK, TAP AND KEYPRESS
⭐   FOR THE WHOLE SESSION, reported at ~p98.
⭐   ⇒ ⭐⭐ ONE 800 ms INTERACTION IN A LONG SESSION FAILS THE PAGE,
⭐     EVEN IF EVERYTHING ELSE IS INSTANT.
⭐   ⇒ ⭐ IT IS A TAIL METRIC — you already know tails matter more
⭐     than averages, and this is that rule applied to interactions.
```

# Part 3 — ⭐⭐ The critical path

```
⭐⭐ WHAT BLOCKS THE FIRST PAINT — fix in this order

⭐ ① ⭐⭐ RENDER-BLOCKING RESOURCES
⭐    · <script> in <head> without defer  ⇒ ⭐ parsing STOPS
⭐    · every <link rel=stylesheet>       ⇒ ⭐⭐ CSS IS ALWAYS
⭐      RENDER-BLOCKING.
⭐    · ⭐ @import inside CSS ⇒ a SERIAL request. Never.

⭐ ② ⭐⭐ THE WATERFALL (Day 227) — the biggest structural win
⭐    HTML → JS → API → API → image
⭐    ⇒ ⭐ EACH ARROW IS A FULL ROUND TRIP THAT COULD NOT START EARLIER.
⭐    ⇒ ⭐⭐ FIXES: <link rel=preload> · route loaders · server
⭐      rendering · <link rel=preconnect> to your API origin
⭐      (saves DNS+TLS, ~100–300 ms, ONE LINE)

⭐ ③ BUNDLE SIZE — route splitting (Day 233), tree-shaking (Day 222)
⭐ ④ ⭐ IMAGES AND FONTS — Day 242, usually the largest bytes
```

```html
<!-- ⭐ four lines that are nearly free -->
<link rel="preconnect" href="https://api.example.com">   <!-- ⭐⭐ DNS+TLS early -->
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">
<script src="/app.js" defer></script>                     <!-- ⭐ never blocks -->
<img src="..." width="800" height="400">                  <!-- ⭐⭐ kills CLS -->
```

# Part 4 — Field vs lab, and the budget

```
⭐⭐ THEY ANSWER DIFFERENT QUESTIONS. YOU NEED BOTH.

⭐   LAB (Lighthouse, DevTools)
⭐     ⭐ Reproducible, debuggable, one device you chose.
⭐     ⭐⭐ IT IS NOT YOUR USERS. A perfect Lighthouse score with bad
⭐       field data is normal.
⭐   FIELD (RUM in prod)
⭐     ⭐⭐ REAL DEVICES, REAL NETWORKS, REAL P75. THE TRUTH.

⭐   ⇒ ⭐⭐ IT IS EXACTLY YOUR SYNTHETIC-MONITORING-VERSUS-MICROMETER
⭐     SPLIT. ⭐ Lab tells you WHY, field tells you WHETHER.
```

```javascript
// ⭐ ship this on day one — it is ~1 KB
import { onLCP, onINP, onCLS } from "web-vitals";
[onLCP, onINP, onCLS].forEach(fn => fn(m => {
  navigator.sendBeacon("/rum", JSON.stringify({    // ⭐⭐ survives unload
    name: m.name, value: m.value, path: location.pathname,
  }));
}));
```

## Today's build

1. ⭐⭐ **Run Lighthouse on your app, mobile profile, 4G throttle.** Write down LCP, INP, CLS.
2. ⭐ Open the Network waterfall and **draw the dependency arrows on paper.** Count the sequential hops.
3. ⭐⭐ Add `preconnect` to your API origin. Re-measure. **One line, usually 100–300 ms.**
4. ⭐ Split one route out of the main bundle. Re-measure.
5. ⭐⭐ Remove `width`/`height` from an image and watch CLS spike. Put them back.
6. ⭐ Ship the web-vitals beacon. **Compare field p75 with your lab score** — expect disagreement.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "your API is fast but the app feels slow — what do you do?"**

Do the accounting out loud. **First I stop looking at Micrometer, because it measures the part I'm
responsible for rather than the part the user experiences. On a typical page my forty-millisecond API
call is about one percent of the wait. DNS, TLS and HTML are three hundred milliseconds, the bundle is
over a second on 4G, parsing is another four hundred — worse than downloading on a cheap phone — and
then a waterfall of dependent requests. Optimising forty milliseconds to twenty is invisible.**

Then what you measure instead. **LCP for when content appears, INP for responsiveness, CLS for
stability. INP is the one people misread — it's every interaction across the session reported near p98,
so one eight-hundred-millisecond interaction fails the page even if everything else is instant. It's a
tail metric, and I already know tails matter more than averages.**

Then the fixes by leverage. **The waterfall first, because it's structural — preconnect to the API
origin is one line and often two hundred milliseconds, and route loaders remove a round trip. Then
bundle size, then images and fonts.**

Close on measurement discipline. **Lab and field answer different questions — it's the same split as
synthetic monitoring versus production metrics. Lighthouse tells me why, real-user monitoring tells me
whether, and a perfect Lighthouse score with bad field data just means my synthetic profile isn't my
users. The budget goes in CI so bundle growth is a decision somebody made.**
