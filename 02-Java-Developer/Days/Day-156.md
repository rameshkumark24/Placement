# Part 1 — Why a pool exists, and why its size is not what you think

**Opening a database connection is expensive**: TCP handshake, TLS negotiation, authentication, and
on PostgreSQL a **new operating-system process** forked on the server. That is 20–100 ms, per
connection, and PostgreSQL's process-per-connection model means each one also costs several megabytes
of server memory.

So you keep them open and lend them out. That is the whole idea, and HikariCP is Boot's default
implementation — chosen because it is dramatically faster than the alternatives at the one operation
that matters, `getConnection()`, which happens on every single query.

## ⭐ The sizing rule that surprises everyone

```yaml
spring.datasource.hikari:
  maximum-pool-size: 10          # ⭐ ten. Not 100.
  minimum-idle: 10               # ⭐ same as max — see below
  connection-timeout: 3000       # ms to wait for a connection
  idle-timeout: 600000
  max-lifetime: 1740000          # ⭐ must be < the DB's / proxy's idle cutoff
  leak-detection-threshold: 20000
  pool-name: orders-pool
```

**Ten connections serve more traffic than a hundred.** This is counter-intuitive and it is well
established — HikariCP's own documentation makes the argument, and the underlying reason is that a
database has a fixed number of cores and a fixed number of disks. Beyond that, extra concurrent
queries do not execute in parallel; they **context-switch, contend on locks, and thrash the buffer
cache.** Throughput goes *down* while latency goes up.

The formula that gets quoted:

```
connections = ((core_count × 2) + effective_spindle_count)
```

For an 8-core server with SSDs, that is around 16–20 — **for the entire application fleet**, not per
instance. Ten instances at `maximum-pool-size: 10` is 100 connections hitting a database sized for
20, and you have built a queue on the wrong side of the wire.

**`minimum-idle` should equal `maximum-pool-size`** for a server application. A fixed-size pool means
no connection-creation latency spikes during a traffic surge — which is precisely when you can least
afford a 50 ms handshake on the request path.

## ⭐ The `max-lifetime` trap

**A connection can die without the pool noticing.** A firewall, a load balancer, a cloud database
proxy, or the database's own `idle_in_transaction_session_timeout` may drop an idle TCP connection
silently. The pool then hands out a dead connection and you get an inexplicable
`SQLException: Connection reset` on one request in fifty.

`max-lifetime` must be **shorter than the shortest idle cutoff anywhere in the path** — database,
proxy, firewall, cloud load balancer. The default is 30 minutes; the recommendation is to set it a
few seconds *below* the infrastructure's limit. This is the standard cause of "our app throws random
connection errors after quiet periods", and it is invisible in local development where nothing sits
between the app and the database.

# Part 2 — ⭐ The exhaustion arithmetic, and the stall it produces

```
Tomcat threads:      200          (Day 145)
Hikari connections:   10
Query time:           50 ms
Slow query appears:  2000 ms
```

Under normal load, ten concurrent queries at 50 ms is 200 queries/second and nothing queues. Now one
query starts taking two seconds — a missing index (Day 110), a lock wait, a stats change.

**Ten connections × 2 s = five requests per second.** The other 195 Tomcat threads pile up inside
`getConnection()`. Every endpoint in the application now hangs, including the ones that never touch
the database, because the *threads* are gone.

**This is Day 154's cascading failure with a different resource**, and the diagnosis is the same
shape: the thing that broke and the thing you observe are in different places. `connection-timeout:
3000` is what converts it from a hang into fast, honest failures — the requests still fail, but they
fail in 3 seconds instead of parking a thread indefinitely, and your circuit breaker can act.

## The three metrics that name it instantly

Day 143 already exposed them:

| Metric | Meaning |
|---|---|
| `hikaricp_connections_active` | in use right now |
| ⭐ `hikaricp_connections_pending` | **threads waiting for a connection.** Above zero = the pool is the bottleneck |
| `hikaricp_connections_acquire_seconds` | how long acquisition takes. Should be microseconds |

**`pending > 0` sustained is the single most diagnostic number in a Spring service.** It says: the
problem is not your code, it is that there are not enough connections or they are being held too
long. Alert on it.

## Leak detection

```yaml
leak-detection-threshold: 20000
```

Logs a stack trace when a connection is held longer than 20 seconds without being returned — pointing
at the exact line that borrowed it. **Turn this on in staging permanently.** A leaked connection is
silent until the pool is empty, at which point the whole application stops and the stack traces show
200 threads waiting in `getConnection()` — telling you nothing about who took the connections.

# Part 3 — ⭐ What must never happen while holding a connection

```java
@Transactional                                   // ⭐ holds a connection for the whole method
public void placeOrder(CreateOrderRequest req) {
    Order order = repo.save(toOrder(req));
    PaymentResult result = paymentClient.charge(req);   // ❌❌ 800 ms HTTP call
    order.setPaymentId(result.id());                    //     holding a DB connection
}
```

**The transaction holds a connection for 800 ms while waiting on someone else's network.** Ten
connections and this endpoint caps at twelve requests per second — and it caps the *entire
application*, since every other endpoint shares the pool.

It is also Day 124's dual-write: if the charge succeeds and the transaction then rolls back, you have
taken money for an order that does not exist.

**The rule:**

> **A transaction may contain database work only. No HTTP calls, no message publishing, no file I/O,
> no `Thread.sleep`, no waiting on a lock held by anything outside the database.**

```java
public void placeOrder(CreateOrderRequest req) {
    Order order = orderTx.createPending(req);            // ⭐ short transaction, connection returned
    PaymentResult result = paymentClient.charge(req);    // no connection held
    orderTx.markPaid(order.id(), result.id());           // ⭐ second short transaction
}
```

Two short transactions with the slow work between them. The correctness gap between them is exactly
what Day 124's outbox pattern and Day 123's idempotency keys exist to close — Day 164 returns to this
with the transactional tooling.

**And the same rule catches a subtler case:** `spring.jpa.open-in-view: true` — Boot's default, and
Day 139's flagged wrong default — holds the connection **for the entire HTTP request**, including
JSON serialization and the time spent writing bytes to a slow mobile client. A 3-second response to a
phone on a bad connection holds a database connection for 3 seconds. **Set it to `false`.**

# Part 4 — `JdbcClient`, and when to drop below JPA

Spring 6.1's `JdbcClient` is the modern fluent API, and it is the right tool more often than people
expect.

```java
@Repository
class OrderReportRepository {
    private final JdbcClient db;

    List<RevenueByDay> revenue(LocalDate from, LocalDate to) {
        return db.sql("""
                select date_trunc('day', placed_at) as day,
                       sum(total)                   as revenue,
                       count(*)                     as orders
                from orders
                where placed_at >= :from and placed_at < :to
                group by 1 order by 1
                """)
            .param("from", from)                      // ⭐ bound, never concatenated
            .param("to", to)
            .query(RevenueByDay.class)                // ⭐ maps to a record
            .list();
    }
}
```

**Reach for this when:** the query is a report or aggregation, you need database-specific SQL (window
functions from D-09, `ON CONFLICT`, CTEs from D-10), you are doing a bulk operation, or the JPA
version would be a fight. **A read-only projection query has no business creating managed entities**
— Day 162 explains what that costs.

**The rule on parameters is absolute and it is Day 119b's:** `.param(...)`, never string
concatenation. `JdbcClient` gives you a `PreparedStatement`, which is the only real defence.

## Batch inserts, and the setting people forget

```java
jdbcTemplate.batchUpdate("insert into audit_log (id, action, at) values (?, ?, ?)", batchArgs);
```

For JPA:

```yaml
spring.jpa.properties.hibernate.jdbc.batch_size: 50
spring.jpa.properties.hibernate.order_inserts: true      # ⭐ required for batching to engage
spring.jpa.properties.hibernate.order_updates: true
```

**`batch_size` alone frequently does nothing**, because Hibernate can only batch consecutive
statements against the same table, and unordered inserts interleave. Without `order_inserts`, you set
the flag, see no improvement, and conclude batching does not work. Also note: **`IDENTITY` id
generation disables insert batching entirely** — Hibernate must execute each insert to learn the
generated id. Day 158 returns to this; it is a real reason to prefer a sequence.

## Read replicas, briefly

```java
@Transactional(readOnly = true)          // ⭐ routes to a replica with an AbstractRoutingDataSource
```

`readOnly = true` also tells Hibernate to skip dirty checking (Day 162), which is a genuine saving on
large result sets. **Mark every read-only service method with it** even without replicas.

The caveat is replication lag: write, then immediately read from a replica, and the row is not there
yet. That is Day 126's eventual consistency arriving in your own database, and it means a
read-after-write flow must be pinned to the primary.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `maximum-pool-size: 100` | throughput *falls*; the database thrashes |
| Sizing per instance, ignoring fleet total | 10 instances × 20 = 200 connections at a 20-connection database |
| `max-lifetime` above the infra idle cutoff | random `Connection reset` after quiet periods |
| No `connection-timeout` | pool exhaustion becomes an application-wide hang |
| No leak detection in staging | leaks are silent until total failure, then untraceable |
| ⭐ HTTP call inside `@Transactional` | connection held for the remote latency; also a dual-write |
| `open-in-view: true` | connection held for serialization and slow-client writes |
| Not alerting on `connections_pending` | the most diagnostic metric, unwatched |
| String-concatenated SQL | Day 119b |
| `batch_size` without `order_inserts` | batching silently never engages |
| `IDENTITY` ids with batch inserts | batching structurally impossible |
| No `readOnly = true` on reads | dirty checking on every entity, every read |

## Interview questions

**Q: How do you size a connection pool?**
Small — around `cores × 2 + spindles`, so typically 10–20 for the *whole fleet*, not per instance.
Bigger pools reduce throughput because the database has fixed cores and disks, so extra concurrency
becomes context switching and lock contention. And I set `minimum-idle` equal to max so a traffic
surge does not pay connection-creation latency.

**Q: Your service hangs on every endpoint but CPU is idle. What do you check?**
`hikaricp_connections_pending` first. If it is above zero, threads are queued for connections and the
problem is either a slow query holding connections or something holding one while doing non-database
work. Then a thread dump to see where they are parked, and the slow query log.

**Q: Why must you not call an HTTP service inside a transaction?**
It holds a database connection for the remote call's latency, so a single slow dependency throttles
every endpoint that shares the pool. It is also a dual-write: the remote call cannot be rolled back
with the transaction.

**Q: Why do you get random connection errors after an idle period?**
Something in the path — a firewall, proxy or the database itself — drops idle connections, and the
pool hands out a dead one. `max-lifetime` has to be shorter than the shortest idle timeout in the
path.

1. Set `maximum-pool-size: 5`. Add an endpoint that runs `select pg_sleep(2)`. Fire 50 concurrent

2. Add `connection-timeout: 1000`. Repeat. Note failure replaces the hang.
3. Watch `hikaricp_connections_pending` in `/actuator/prometheus` throughout both runs.
4. Borrow a connection and never close it. Set `leak-detection-threshold: 5000` and read the stack

5. Benchmark pool sizes 5, 10, 25, 100 against a fixed load. **Plot throughput.** Find the peak.

## 🎙️ Articulation drill

Two minutes: **"How do you configure and reason about a connection pool?"**

Start with the counter-intuitive part — small pools outperform large ones because the database has
fixed cores and disks — and give the fleet-wide sizing. Then the failure mode: ten connections and
one slow query throttles every endpoint in the application, so `connections_pending` is the metric
you alert on and `connection-timeout` is what turns a hang into a fast failure. Close on the rule
that prevents most of it: nothing but database work inside a transaction, and `open-in-view: false`
so serialization is not holding a connection.
