# Day 343 ⭐

**L-343** · ⭐ Consensus — Raft intuition, quorums, and why you should not build one

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Consensus is how a group of machines agrees on one thing — one leader, one value, one order —
> when any of them may fail and the network may lie.**
>
> You will never implement it. **The skill being tested is recognising when a problem needs it, and
> knowing why a consensus store is the wrong place for your actual data.**

---

# Part 1 — ⭐ What it is for

| ⭐ Use | ⭐ Example |
|---|---|
| ⭐⭐ **Leader election** | ⭐ which replica accepts writes; which instance runs the scheduled job (Day 178) |
| ⭐ **Distributed locks with leases** | Day 207 — a lock that expires if the holder dies |
| ⭐ **Replicated configuration / metadata** | ⭐ service registry, feature flags, shard maps |
| ⭐ **A replicated state machine** | ⭐ every node applies the same operations in the same order |
| Membership | who is currently in the cluster |

> **⭐ The unifying description: consensus turns "we each believe something" into "we all agree, and
> we can prove it".** Everything above reduces to agreeing on **one ordered log of decisions**.

⚠️ **What it is NOT for: your application data at volume.** Every write costs a round trip to a
majority and is replicated to every member. **Consensus stores are for small, critical,
infrequently-written state** — kilobytes to megabytes, not gigabytes.

---

# Part 2 — ⭐⭐ Quorum arithmetic

```
⭐ A cluster of N nodes. A majority is ⌊N/2⌋ + 1.
⭐ ⭐ Any two majorities must overlap — ⭐⭐ THAT is why one decision cannot be made twice.
```

| N | Majority | ⭐ Failures survived | ⭐ Verdict |
|---|---|---|---|
| 1 | 1 | 0 | no fault tolerance |
| ⭐ **3** | ⭐ **2** | ⭐ **1** | ⭐ **the standard choice** |
| ⭐ 4 | ⭐ **3** | ⭐ **1** | ⭐⭐ **strictly worse than 3 — one more machine, no more tolerance, more latency** |
| ⭐ **5** | 3 | ⭐ **2** | ⭐ for critical clusters |
| 7 | 4 | 3 | rarely worth the write latency |

> **⭐ The rule: N = 2f + 1 to survive f failures, and even N is always wasteful.** A 4-node cluster
> tolerates the same single failure as a 3-node one **while needing an extra acknowledgement on every
> write.** That is the cleanest thing to say about cluster sizing.

**⭐ And the split-brain answer falls straight out:** a 5-node cluster partitioned 3/2 has **one**
majority side, which keeps working; the minority cannot elect a leader **because it cannot reach a
majority**. Split 2/2 in a 4-node cluster and **neither side can proceed** — correct, but useless.

⚠️ **More nodes is not more availability past a point.** Every write waits for a majority, **so
latency rises with N** while tolerance grows slowly. **Three or five, almost always.**

# Part 3 — ⭐⭐ Raft in five minutes

```
⭐ Every node is FOLLOWER, CANDIDATE, or LEADER.  ⭐ Time is divided into numbered TERMS.

⭐ 1. ELECTION
⭐    A follower hears nothing from a leader for a RANDOMISED timeout (e.g. 150–300 ms)
⭐    → becomes CANDIDATE, increments the term, votes for itself, asks everyone for votes
⭐    → ⭐ a node votes at most ONCE per term
⭐    → ⭐⭐ a majority of votes ⇒ LEADER. A majority is needed, so ONE leader per term, always.
⭐    → ⭐ the randomised timeout is what prevents endless split votes

⭐ 2. LOG REPLICATION
⭐    Clients send writes to the LEADER only.
⭐    Leader appends to its log, sends AppendEntries to followers.
⭐    ⭐ Once a MAJORITY have stored the entry, it is COMMITTED and applied.
⭐    Followers that fall behind are caught up by the leader.

⭐ 3. SAFETY
⭐    ⭐⭐ A candidate can only win if its log is at least as up to date as the voters'.
⭐    ⇒ ⭐⭐ a new leader always contains every committed entry. Nothing committed is ever lost.
```

| ⭐ Property | ⭐ Why it matters |
|---|---|
| ⭐ **One leader per term** | ⭐⭐ **split brain is structurally impossible for committed writes** |
| ⭐ **Committed = a majority has it** | survives f failures |
| ⭐ Randomised election timeouts | ⭐ breaks symmetry — the trick that makes Raft simple |
| ⭐ **Followers never accept client writes** | ⭐ all ordering flows through one node |
| ⭐ Terms are a logical clock | ⭐ **a stale leader's messages are rejected because its term is old** |

> **⭐ The last row is the practical answer to Day 330's paused-node problem: a leader that was
> garbage-collecting for thirty seconds wakes up still believing it is leader — but its term is
> stale, so every message it sends is rejected.** That is consensus's built-in fencing, and it is the
> same idea as Day 207's fencing token.

**⭐ Paxos versus Raft, in one line:** they solve the same problem with the same guarantees; **Raft
was designed to be understandable**, with an explicit leader and a clean separation of election from
replication. **Say that and move on** — nobody needs a Paxos derivation in an interview.

# Part 4 — ⭐ Using it in practice

## ⭐ You do not implement it — you recognise the need

| ⭐ Need | ⭐ Reach for |
|---|---|
| ⭐ **Leader election / locks** | ⭐ etcd, ZooKeeper, Consul — **or a database row with a lease** |
| ⭐ Configuration and shard maps | etcd (Kubernetes uses it for exactly this) |
| Replicated database metadata | ⭐ embedded in the database (CockroachDB, TiDB, MongoDB elections) |
| ⭐ **A single-instance job** (Day 178) | ⭐⭐ **ShedLock on your existing database — do not add a cluster** |

> **⭐ The judgement being tested: "this needs consensus" followed by "so I would use etcd" is
> correct. "So I would implement Raft" is a red flag.** Consensus implementations take years to get
> right; the failure modes are subtle and the bugs are data loss.

⚠️ **And the reverse judgement matters as much: most things do not need consensus.** A leader-elected
scheduled job can often be replaced by an idempotent job that is safe to run three times (Day 178).
**Removing the need is better than satisfying it.**

## ⭐⭐ The cost, and the rule that follows

```
⭐ Every write:  client → leader → majority of followers → ack → apply
⭐ ⇒ ⭐ at least one extra network round trip, always
⭐ ⇒ ⭐ every member stores the entire dataset
⭐ ⇒ ⭐ writes do not scale by adding nodes — ⭐⭐ they get SLOWER
```

> **⭐⭐ The rule: never put high-volume data in a consensus store.** etcd's own guidance is a few
> gigabytes at most. **Configuration, locks, membership and shard maps — yes. Events, sessions, user
> data — no.** Teams that use etcd or ZooKeeper as a general datastore take down their control plane
> and, with it, everything that depends on it.

## ⭐ Leases, and the clock caveat

**⭐ A lease is a lock with an expiry, granted by the consensus group.** It is how leader election
becomes usable: **the leader must renew, and if it stops renewing, someone else may take over.**

⚠️ **A lease is only safe if the holder also stops acting when it cannot renew.** A paused leader
whose lease expired must **check before acting**, or you need fencing tokens downstream (Day 207,
Day 328). **Time-based leases assume bounded clock drift, so keep the lease longer than any plausible
pause and still fence.**

## ⭐ FLP, and why anything works at all

**⭐ The FLP result: in a fully asynchronous system, no deterministic algorithm can guarantee
consensus if even one node may fail** — because you cannot distinguish a crashed node from a slow one
(Day 330).

**⭐ Real systems escape it by assuming partial synchrony:** messages usually arrive within some
bound, so timeouts work most of the time. **Raft gives up guaranteed termination — an unlucky
sequence of timeouts can delay an election indefinitely in theory — in exchange for terminating
quickly in practice.** Safety is never given up; **only liveness is.**

> **⭐ That distinction is the one to state: consensus algorithms never sacrifice safety. They
> sacrifice liveness.** A partitioned Raft cluster stops making progress; **it never produces two
> conflicting answers.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Even-numbered clusters | ⭐⭐ **4 tolerates the same failures as 3, with more latency** |
| ⭐ Large clusters for availability | ⭐ writes get slower; tolerance grows slowly |
| ⭐⭐ **Bulk data in a consensus store** | ⭐⭐ **you take down the control plane and everything with it** |
| ⭐ Proposing to implement Raft | ⭐ **years of subtle bugs; the failure mode is data loss** |
| ⭐ Adding ZooKeeper for one scheduled job | ⭐ ShedLock on your database was enough |
| ⭐ **Leases without fencing** | ⭐ a paused leader acts on an expired lease (Day 207) |
| Assuming a leader is always current | its term may be stale |
| ⭐ Believing consensus gives availability | ⭐ **it gives safety; the minority stops entirely** |
| Confusing quorum reads with consensus | `W + R > N` is a heuristic (Day 328), not agreement |
| Ignoring that consensus stores are CP | a partition means the minority is down, by design |

## Interview questions

**Q: What problem does consensus solve?**
Getting a group of machines to agree on one ordered log of decisions despite failures and an
unreliable network. Everything it is used for — leader election, distributed locks with leases,
configuration, replicated state machines — reduces to that. The important corollary is what it is not
for: every write costs a round trip to a majority and is stored by every member, so it is for small
critical state, not application data.

**Q: Why are consensus clusters always odd-sized?**
Because you need a majority, and four nodes need three for a majority just as three do — so a
four-node cluster tolerates exactly one failure like a three-node one, while adding an extra
acknowledgement to every write. The formula is N equals two f plus one to survive f failures, and an
even N is always strictly worse than the odd number below it.

**Q: Explain Raft.**
Time is divided into numbered terms. A follower that hears nothing from a leader for a randomised
timeout becomes a candidate and asks for votes; a node votes once per term, so a majority means
exactly one leader per term. The leader takes all client writes, appends to its log and replicates;
an entry is committed once a majority has stored it. The safety rule is that a candidate can only win
if its log is at least as current as its voters', which guarantees a new leader holds every committed
entry.

**Q: How does it prevent split brain?**
Two majorities must overlap, so two leaders cannot both be elected in the same term. And a stale
leader — one that was paused and thinks it is still in charge — has an old term number, so every
message it sends is rejected. That is fencing built into the protocol, and it is the same idea as a
fencing token on a distributed lock.

**Q: Would you implement Raft?**
No. I would use etcd, ZooKeeper or Consul, or a database that embeds it. Implementations take years
to get right and the failure mode is silent data loss. More often I would question whether consensus
is needed at all — a single-instance scheduled job is usually better solved by making the job
idempotent and safe to run three times than by electing a leader.

**Q: Does consensus make a system more available?**
No — it makes it safe. During a partition the minority side stops entirely rather than serving
possibly-wrong answers, which is CP behaviour. Consensus algorithms never trade away safety; they
trade away liveness, which is why FLP does not stop them working in practice: they assume partial
synchrony, so they terminate quickly in the normal case and may stall in an unlucky one.

## Mini task

1. **Run a 3-node etcd or Consul cluster.** Kill one node — confirm it still works. Kill a second —
   confirm it stops.
2. ⭐ Run a **4-node** cluster and demonstrate it survives exactly one failure, like the 3-node one.
3. ⭐⭐ **Partition a 5-node cluster 3/2.** Confirm the majority serves and the minority refuses.
   Then partition 4 nodes 2/2 and confirm neither side works.
4. Implement **leader election** for a scheduled job using etcd leases. **Kill the leader and measure
   time to a new one.**
5. ⭐ **Pause the leader** (SIGSTOP) past its lease, let a new leader be elected, then resume it.
   **Observe that its writes are rejected** — that is the term acting as a fence.
6. ⭐ Solve the same scheduled-job problem with **ShedLock on PostgreSQL.** Compare operational cost
   honestly and decide which you would run.
7. ⭐ Write 100 MB into etcd and **measure write latency and memory as it grows.** Note where guidance
   says to stop.
8. ⭐ Measure **write latency versus cluster size** at 3, 5 and 7 nodes.
9. Read Raft's own diagram of states and terms, then **explain it aloud in two minutes with no
   notes.**

## 🎙️ Articulation drill

**Two minutes:** *"Only one instance should run this nightly job. How?"*

**⭐ The strong answer starts by trying to remove the requirement** — *"first, can the job be made
idempotent and safe to run three times? That removes the problem entirely."* **Then, if not, a lease
in the database (ShedLock) before a consensus store**, because a cluster is a real operational
commitment.

**⭐ Close with the caveat that shows depth: "and whichever I use, the job must tolerate briefly
having two runners — a paused holder can wake past its lease — so the work needs to be fenced or
idempotent anyway."** That is the sentence that says you have thought about it rather than named a
tool.
