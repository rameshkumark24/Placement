# Part 1 — L-019 · Where state lives

## The problem

Every HTTP request is independent. The server remembers nothing. Yet you log in once and stay logged
in across a hundred requests.

**The only solution: the client must send proof with every single request.** The question is *where
that proof is stored and how it travels* — and each answer has different security properties.

## The five places

| | Sent automatically? | Readable by JS? | Capacity | Expires |
|---|---|---|---|---|
| **Cookie** | ✅ every request to the domain | Only if not `HttpOnly` | ~4 KB | Configurable |
| **localStorage** | ❌ you attach it manually | ✅ always | ~5–10 MB | Never |
| **sessionStorage** | ❌ manual | ✅ always | ~5–10 MB | On tab close |
| **IndexedDB** | ❌ manual | ✅ always | Large | Never |
| **In memory (a JS variable)** | ❌ manual | ✅ | — | On page reload |

**The two properties that decide everything:** *sent automatically* and *readable by JavaScript*.
They pull in opposite directions, and that tension is the whole topic.

## Cookies

```http
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=3600; Path=/
```

The browser then sends `Cookie: session=abc123` on every matching request, automatically.

### The flags — and what each one defends against

| Flag | Effect | Defends against |
|---|---|---|
| **`HttpOnly`** | JavaScript **cannot** read it | **XSS stealing the session** |
| **`Secure`** | HTTPS only | Interception on plaintext HTTP |
| **`SameSite=Strict`** | Never sent cross-site | **CSRF** — but breaks inbound links |
| **`SameSite=Lax`** | Sent on top-level GET navigation only | CSRF, while keeping links working. **The modern default.** |
| **`SameSite=None`** | Always sent — requires `Secure` | Nothing. Only for genuine cross-site needs. |
| `Domain` / `Path` | Scope | Over-broad scoping |
| `Max-Age` / `Expires` | Lifetime | Indefinite sessions |

**`HttpOnly` is the single most important security flag on the web.** If an attacker injects
JavaScript into your page (XSS), the one thing they want is the session token. `HttpOnly` means
`document.cookie` simply doesn't show it — the attack fails at the last step.

### The CSRF problem — caused by the good feature

Cookies are sent **automatically on every request to the domain, including requests initiated by
other sites.**

```html
<!-- On evil.com, while you're logged into yourbank.com -->
<form action="https://yourbank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>
```

Your browser attaches your bank cookie. The bank sees an authenticated request. **That's CSRF**, and
it exists *because* cookies are automatic.

**Defences:**
1. **`SameSite=Lax` or `Strict`** — the modern primary defence, on by default in Chrome
2. **CSRF tokens** — a random value in the form that an attacker can't read cross-origin
3. **Check `Origin`/`Referer`** on state-changing requests

**Note the asymmetry:** token-in-header auth (`Authorization: Bearer ...`) is immune to CSRF,
because the browser doesn't attach it automatically — the attacker's page can't add it. But tokens
in `localStorage` are vulnerable to XSS, which cookies with `HttpOnly` are not.

**There is no option that avoids both.** You pick which attack you defend against structurally and
which you mitigate with discipline.

## Sessions vs tokens

### Server-side sessions

```
   Login → server creates a session, stores it (Redis/DB), sends the ID in a cookie
   Request → cookie arrives → server looks up the session → knows who you are
```

| ✅ | ❌ |
|---|---|
| **Revocable instantly** — delete the row | Requires a lookup on every request |
| Tiny cookie (just an ID) | Requires shared storage across instances |
| Can store arbitrary server-side data | Statefulness (mitigated by Redis) |
| Nothing sensitive leaves the server | |

### JWTs (stateless tokens)

```
   Login → server signs a token containing claims → client stores it
   Request → client sends token → server verifies the SIGNATURE — no lookup
```

```
   header.payload.signature
   eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsImV4cCI6MTcwMH0.dBjftJeZ4CVP...
```

| ✅ | ❌ |
|---|---|
| No lookup — verify the signature | **Cannot be revoked before expiry** |
| Works across services (Day 015, C-10: RS256) | Larger, sent on every request |
| Genuinely stateless — scales freely | Payload is **base64, not encrypted** — readable by anyone |
| | Easy to get wrong (`alg:none`, no expiry check) |

**The revocation problem is the big one.** Delete a user, ban an account, or have a token stolen —
and that token stays valid until it expires. The standard mitigation is short-lived access tokens
(5–15 min) plus a long-lived refresh token that *is* stored server-side and revocable.

Notice what that means: **you've reintroduced server state.** Which is why "JWTs are stateless" is
only half true in any system that needs revocation, and saying so is a good interview answer.

**Never put secrets in a JWT payload.** It's base64-encoded, not encrypted. Anyone can decode it —
paste one into jwt.io and read it. Signing proves it wasn't *tampered with*; it does not hide it.

### The decision

| Use | When |
|---|---|
| **Server-side sessions** | Monolith or few services, need instant revocation, browser client. **The sensible default.** |
| **JWT** | Multiple services verifying independently, mobile/third-party clients, revocation delay is acceptable |
| **Both** | Short JWT access token + revocable refresh token. What most production systems actually do. |

## Where to store a token in a browser

**The question people get wrong most often.**

| Storage | XSS | CSRF | Verdict |
|---|---|---|---|
| `localStorage` | ❌ **Fully exposed** | ✅ Immune | Common, and the weakest option |
| Non-`HttpOnly` cookie | ❌ Exposed | ❌ Vulnerable | Worst of both |
| **`HttpOnly` cookie** | ✅ **Protected** | ❌ Needs `SameSite`/CSRF token | **Best for browsers** |
| In-memory variable | ✅ Mostly | ✅ | Good, but lost on refresh |

**`HttpOnly` cookie + `SameSite=Lax` + `Secure` is the right default for a browser client.**

The reasoning: XSS is a *total* compromise — an attacker running JS in your page can read
`localStorage`, exfiltrate the token, and act as the user indefinitely. CSRF is *narrower* — the
attacker can trigger actions but can't read responses — and it has a clean structural defence in
`SameSite`.

**Pick the storage that resists the worse attack, then mitigate the other.**

> This is the "JWTs stored in httpOnly cookies where possible, not localStorage (XSS steals
> localStorage)" line in
> [`03-Web-Developer/06-Security.md`](../../03-Web-Developer/06-Security.md). Now you can defend it
> rather than follow it.

## localStorage vs sessionStorage

```js
localStorage.setItem('theme', 'dark');      // survives browser restart, per origin
sessionStorage.setItem('draft', '...');     // dies with the tab, per tab
```

Both: **synchronous** (blocks the main thread — Day 014), string-only, ~5–10 MB, same-origin scoped,
**always readable by JavaScript**.

**Good for:** UI preferences, drafts, non-sensitive cache.
**Never for:** session tokens, PII, anything an XSS shouldn't get.

## Where state lives — the full picture

Zoom out. "State" is a bigger question than auth:

| Layer | Holds | Example |
|---|---|---|
| **URL** | Shareable, bookmarkable UI state | `?page=2&sort=name&filter=open` |
| **Component memory** | Ephemeral UI | Is this dropdown open |
| **Client store** | Cross-component client state | Theme, cart before checkout |
| **Client cache** | A *copy* of server state | TanStack Query cache |
| **Cookie** | Identity | Session ID |
| **Server session / DB** | The **truth** | User, orders, balance |

**The most common architectural mistake is putting server state in a client store.** Your cart, your
user list, your orders — those live on the server. The client has a *cache* of them, which is why
TanStack Query exists (Day 241) and why hand-rolled `useState` + `useEffect` fetching goes wrong.

**And: URL state is underused.** Filters, pagination and tabs in the URL make the page shareable,
bookmarkable and back-button-correct — for free.

## Type this yourself

```java
import java.io.*;
import java.net.*;
import java.util.*;
import java.util.concurrent.*;

public class SessionServer {
    static final Map<String, String> sessions = new ConcurrentHashMap<>();

    public static void main(String[] args) throws IOException {
        ServerSocket server = new ServerSocket(8080);
        System.out.println("http://localhost:8080");

        while (true) {
            try (Socket client = server.accept()) {
                BufferedReader in = new BufferedReader(
                        new InputStreamReader(client.getInputStream()));
                String requestLine = in.readLine();
                if (requestLine == null) continue;

                String cookieHeader = null, h;
                while ((h = in.readLine()) != null && !h.isEmpty())
                    if (h.toLowerCase().startsWith("cookie:")) cookieHeader = h.substring(7).trim();

                String sessionId = null;
                if (cookieHeader != null)
                    for (String c : cookieHeader.split(";"))
                        if (c.trim().startsWith("session=")) sessionId = c.trim().substring(8);

                String path = requestLine.split(" ")[1];
                String status = "200 OK", setCookie = "", body;

                if (path.equals("/login")) {
                    String id = UUID.randomUUID().toString();
                    sessions.put(id, "ramesh");
                    // HttpOnly: JS cannot read it. SameSite=Lax: CSRF defence.
                    setCookie = "Set-Cookie: session=" + id
                              + "; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600\r\n";
                    body = "<h1>Logged in</h1><p>Try document.cookie in the console.</p>"
                         + "<a href='/'>home</a>";
                } else if (path.equals("/logout")) {
                    sessions.remove(sessionId);
                    setCookie = "Set-Cookie: session=; Max-Age=0; Path=/\r\n";
                    body = "<h1>Logged out</h1><a href='/'>home</a>";
                } else {
                    String user = sessions.get(sessionId);
                    body = user != null
                         ? "<h1>Hello " + user + "</h1><p>session=" + sessionId + "</p>"
                           + "<a href='/logout'>logout</a>"
                         : "<h1>Not logged in</h1><a href='/login'>login</a>";
                }

                byte[] out = body.getBytes();
                OutputStream os = client.getOutputStream();
                os.write(("HTTP/1.1 " + status + "\r\n"
                        + "Content-Type: text/html\r\n"
                        + setCookie
                        + "Content-Length: " + out.length + "\r\n"
                        + "Connection: close\r\n\r\n").getBytes());
                os.write(out);
                os.flush();
            }
        }
    }
}
```

**Four things to do:**

1. Visit `/login`, then `/`. **You stayed logged in across two independent stateless requests** —
   because the cookie travelled automatically.
2. **In the console, type `document.cookie`.** It's empty. `HttpOnly` working. Now imagine an XSS on
   this page: it cannot steal the session.
3. **Devtools → Application → Cookies.** See the flags. Uncheck `HttpOnly` in the code, restart, and
   try `document.cookie` again — now it's readable. **That's the whole difference.**
4. **Restart the server** with a session active. You're logged out — sessions were in memory. That's
   why production stores them in Redis, and why "sessions in Redis" appears in your stack.

## Common mistakes

| Mistake | Correction |
|---|---|
| Tokens in `localStorage` | Any XSS steals them permanently. Use an `HttpOnly` cookie for browser clients. |
| No `HttpOnly` | Defeats the main defence against session theft via XSS. |
| No `SameSite` | Leaves you open to CSRF. `Lax` is the sensible default. |
| Secrets in a JWT payload | It's base64, not encrypted. Anyone can read it. |
| "JWTs are stateless, so no revocation needed" | You need revocation. Short access tokens + a revocable refresh token — which reintroduces state. |
| Sessions in application memory | Lost on restart, not shared across instances. Use Redis. |
| Server state in a client store | The server is the truth; the client holds a cache. Use a query library. |
| Filters and pagination only in component state | Put them in the URL — shareable, bookmarkable, back-button-correct. |

## Interview questions

**Q: HTTP is stateless — how does a site know I'm logged in?**
> It doesn't remember. The client sends proof on every request, normally a cookie holding a session
> ID or a token. The server either looks the session up in shared storage, or verifies the token's
> signature.

**Q: Sessions or JWTs?**
> Sessions when you need instant revocation and have a browser client — the cookie is small and
> deleting the server-side record logs the user out immediately. JWTs when multiple services must
> verify independently without a shared session store, accepting that a token stays valid until it
> expires. In practice, short-lived JWT access tokens with revocable refresh tokens.

**Q: Where should a browser store an auth token?**
> An `HttpOnly`, `Secure`, `SameSite=Lax` cookie. `localStorage` is readable by any injected script,
> so a single XSS is a full account takeover. The cookie approach exposes you to CSRF instead, which
> has a clean structural defence in `SameSite` plus CSRF tokens. You choose to resist the worse
> attack structurally.

**Q: What is CSRF and why do cookies enable it?**
> Cookies are attached automatically to every request to their domain, including ones initiated by
> another site. So a form on an attacker's page can submit to your bank with your cookie attached.
> `SameSite` restricts cross-site sending; CSRF tokens add an unguessable value the attacker can't
> read.

**Q: What does `HttpOnly` protect against, and what doesn't it protect against?**
> It stops JavaScript reading the cookie, so an XSS can't exfiltrate the session token. It does
> nothing about CSRF — the cookie is still sent automatically, which is exactly what CSRF exploits.

# Part 2 — C-13 · Network debugging

The toolkit, in the order you'd reach for it.

| Tool | Answers | Layer |
|---|---|---|
| `ping` | Is the host reachable? What's the RTT? | 3 (ICMP) |
| `traceroute` | What path does it take? Where does it break? | 3 |
| `dig` / `nslookup` | Does the name resolve, and to what? | 7 (DNS) |
| `netstat` / `ss` | What's listening? What connections exist? In what state? | 4 |
| `lsof -i` | Which **process** owns which port? | 4 |
| `curl -v` | What exactly went over HTTP? | 7 |
| `openssl s_client` | Is TLS correct? | 6 |
| `tcpdump` / Wireshark | What's on the wire, byte by byte? | 2–7 |

## The diagnostic ladder

**Work bottom-up.** Most people start with `curl` and skip four layers.

```
  1. Does the name resolve?            dig example.com
  2. Is the host reachable?            ping example.com
  3. Where does the path break?        traceroute example.com
  4. Is the port open?                 telnet example.com 443   /  nc -zv example.com 443
  5. Is TLS valid?                     openssl s_client -connect example.com:443
  6. What does HTTP say?               curl -v https://example.com
  7. What's actually on the wire?      tcpdump / Wireshark
```

Each step assumes the previous succeeded. "The API is down" almost always resolves at step 1, 4 or 5
— and you find it in seconds instead of an hour.

## Reading the states — Day 008 applied

```bash
ss -tan | grep :8080        # Linux
netstat -ano | findstr :8080   # Windows
```

| State | Means | Action |
|---|---|---|
| `LISTEN` | Server is bound and waiting | Healthy |
| `ESTABLISHED` | Active connection | Healthy |
| **`TIME_WAIT`** (many) | Closing lots of connections | Usually normal; watch ephemeral port exhaustion |
| **`CLOSE_WAIT`** (growing) | **Your app isn't calling `close()`** | **Application bug — find the leak** |
| `SYN_SENT` (stuck) | Handshake not completing | Firewall dropping, or host unreachable |

## `curl -v`, read properly

```bash
curl -v https://example.com
```

```
* Connected to example.com (93.184.216.34) port 443     ← DNS + TCP worked (Days 007, 005)
* ALPN: server accepted h2                              ← protocol negotiated (Day 011)
* SSL connection using TLSv1.3 / AES_128_GCM_SHA256     ← TLS worked (Day 009)
* Server certificate: CN=example.com                    ← cert chain (Day 009)
> GET / HTTP/2                                          ← your request  (Day 010)
> Host: example.com
< HTTP/2 200                                            ← the response
< content-type: text/html
```

**Every line maps to a day you've now done.** `>` is sent, `<` is received, `*` is curl's commentary.

Useful flags: `-I` headers only · `-L` follow redirects · `-w "%{time_total}"` timing breakdown ·
`--resolve` test a host before DNS is switched (**invaluable during migrations**).

## Timing breakdown — find the slow part

```bash
curl -w "dns:%{time_namelookup} connect:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s https://example.com
```

That single command tells you whether slowness is DNS, TCP, TLS or the server. **It's the fastest
"why is this slow" tool there is**, and almost nobody uses it.

## Interview questions

**Q: A user says "the site is down". How do you diagnose it?**
> Work up the stack. Check DNS resolves, then that the host is reachable, then that the port accepts
> connections, then that TLS is valid, then what HTTP returns. Most incidents resolve at DNS, a
> closed port or an expired certificate, and going in order finds it in seconds.

**Q: What does a growing number of `CLOSE_WAIT` sockets indicate?**
> The application received a FIN but never called `close()`. It's a socket leak in application code,
> not a network problem, and it will eventually exhaust file descriptors.

**Q: How would you determine whether slowness is network or server?**
> `curl -w` with the timing variables breaks the request into DNS lookup, TCP connect, TLS handshake
> and time to first byte. If TTFB dominates, it's the server; if connect or TLS dominates, it's
> network or certificate configuration.
