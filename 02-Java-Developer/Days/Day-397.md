# Part 1 — ⭐⭐ The target architecture

```
⭐  Route 53 (alias, apex)
⭐    └→ ⭐⭐ CloudFront ── WAF, rate limiting ── /static/* → S3 (PRIVATE, OAC)
⭐            └→ /api/*  (uncached, TLS at the edge)
⭐                 └→ ⭐ ALB   ── PUBLIC subnets, 3 AZs
⭐                      └→ ⭐⭐ ECS Fargate ── PRIVATE subnets, 3 AZs, min 3 tasks
⭐                           ├→ ⭐ RDS Postgres Multi-AZ ── ISOLATED subnets
⭐                           ├→ ⭐ ElastiCache Redis (Multi-AZ) ── ISOLATED subnets
⭐                           ├→ ⭐ SQS + DLQ → worker service (scales on message age)
⭐                           ├→ ⭐ S3 (uploads, presigned) ── ⭐⭐ via GATEWAY ENDPOINT
⭐                           └→ ⭐ Secrets Manager / Parameter Store ── via task role
⭐
⭐  ⭐⭐ Observability: CloudWatch (AWS metrics + logs w/ RETENTION) · ADOT → traces · alarms → SNS
⭐  ⭐⭐ Everything above: TERRAFORM. ⭐⭐ Deployed by: GitHub Actions via OIDC. ⭐ No stored keys.
```

| ⭐ Every choice, traceable to a day | |
|---|---|
| 3 AZs, ≥3 tasks | ⭐⭐ static stability — survive an AZ loss with **no control-plane call** (Day 380) |
| Isolated data subnets | ⭐ no route to the internet in either direction (Day 383) |
| SG-to-SG chain | ⭐ no IP addresses in any rule (Day 384) |
| Multi-AZ RDS **+ JVM DNS TTL** | ⭐⭐ failover the application actually survives (Day 387) |
| ALB idle timeout < backend | ⭐⭐ no mystery 502s (Day 389) |
| Circuit breaker + grace period | ⭐ automatic rollback, no startup death loop (Day 390) |
| Gateway endpoint | ⭐⭐ NAT processing removed (Day 384, 396) |
| Log retention everywhere | ⭐⭐ the largest quiet line, closed (Day 394, 396) |
| OIDC, no access keys | ⭐ workload identity end to end (Day 369, 382) |

# Part 2 — ⭐⭐ Build order (dependencies flow one way)

| # | ⭐ Layer | ⭐ Contents | ⭐ Lifecycle |
|---|---|---|---|
| ⭐ 1 | ⭐⭐ **Foundation** | accounts, Organizations + SCPs, IAM Identity Center, **Terraform state bucket + lock table**, CloudTrail to a separate account | never changes |
| ⭐ 2 | ⭐⭐ **Network** | VPC per the CIDR plan, subnets ×3 tiers ×3 AZs, IGW, NAT, **endpoints**, flow logs | rarely |
| ⭐ 3 | ⭐ **Data** | RDS, ElastiCache, S3, backups, **KMS keys** | rarely — ⭐⭐ `prevent_destroy` |
| ⭐ 4 | ⭐ **Platform** | ECR, ECS cluster, ALB, target groups, **roles** | occasionally |
| ⭐ 5 | ⭐⭐ **Application** | task definition, service, autoscaling, alarms | ⭐⭐ **every deploy** |
| ⭐ 6 | ⭐ **Edge** | ACM (**`us-east-1` for CloudFront**), CloudFront, Route 53, WAF | rarely |
| ⭐ 7 | ⭐ **Pipeline** | OIDC role, workflows, promotion gates | occasionally |

> **⭐⭐ Separate Terraform state per layer, split by lifecycle** (Day 379). **A mistake in layer 5 must
> not be able to destroy layer 3.** Lower layers publish outputs (via remote state or SSM parameters);
> **dependencies flow strictly upward and never back down.**

⚠️ **The bootstrap chicken-and-egg: the Terraform state bucket cannot be created by the Terraform that
uses it.** Create it once, by hand or by a tiny separate configuration, **with versioning and a lock
table** — and write down that you did. **This is the one manual step that is legitimate.**

# Part 3 — ⭐ Well-Architected, read critically

| Pillar | ⭐ What it is really asking |
|---|---|
| ⭐ **Operational Excellence** | ⭐⭐ "can you deploy, observe and recover **without a human doing anything manual**?" |
| ⭐ **Security** | ⭐⭐ "**least privilege, no standing credentials, and can you prove who did what?**" |
| ⭐ **Reliability** | ⭐⭐ "what happens when a component fails — **and have you tried it?**" |
| ⭐ **Performance Efficiency** | ⭐ "did you measure, or did you guess?" |
| ⭐ **Cost Optimization** | ⭐⭐ "do you know your cost per request, and is it trending?" (Day 396) |
| ⭐ Sustainability | "are you running things nobody uses?" — largely the cost pillar, restated |

**⭐ The framework's real value is not the answers, it is that the questions are asked at all, on a
schedule.** Run the Well-Architected Tool once against your flagship; **treat the findings as a backlog,
not a scorecard.** And be willing to record **"accepted risk, because X"** — that is a legitimate
outcome and pretending otherwise produces theatre.

# Part 4 — ⭐⭐ Five questions your architecture must answer with evidence

```
⭐⭐ 1. WHAT HAPPENS IF AN AZ DISAPPEARS RIGHT NOW?
⭐    ⇒ ⭐⭐ Not "we're multi-AZ". ⭐⭐ "We ran at N+1 across three, we killed the tasks in one,
⭐       p99 rose 40ms, no requests failed, and NO SCALING ACTION WAS REQUIRED." (Day 380)

⭐⭐ 2. WHAT DOES IT COST, AND WHICH LINE IS LARGEST?
⭐    ⇒ ⭐ a number per month and a number per request, and the top three lines named. (Day 396)

⭐⭐ 3. HOW DOES A SECRET ROTATE?
⭐    ⇒ ⭐⭐ alternating users, both valid during changeover, pool recycled, tested under load. (Day 395)

⭐⭐ 4. HOW DO YOU ROLL BACK, AND WHEN DID YOU LAST DO IT?
⭐    ⇒ ⭐⭐ re-point the service at the previous immutable revision. ⭐ Timed. On purpose. (Day 390)

⭐⭐ 5. IF ONE CREDENTIAL LEAKED, WHAT IS THE BLAST RADIUS?
⭐    ⇒ ⭐⭐ which role, scoped to what, expiring when, logged where — ⭐ and who can become admin.
⭐       (Day 381, 382)
```

> **⭐⭐ Every one of these is answerable with a number or a date if you built it, and unanswerable if you
> only read about it.** That asymmetry is exactly what a senior interviewer is probing for.

## ⭐ Five questions to answer out loud, with real numbers

1. **What exactly makes a subnet public, and where does your data tier route?**
2. **What is your monthly bill, your cost per request, and your largest line?**
3. **What happened when you forced the RDS failover — and what did the application do?**
4. **Which of your services could an attacker reach with a leaked task role, and for how long?**
5. **Name one thing you deliberately did NOT optimise, and justify it.**

> **⭐ Question 5 is the one that separates people.** An engineer who has optimised everything has
> either an infinite budget or no judgement. **"I left the NAT gateways in all three AZs even though one
> would save sixty dollars, because losing egress in every zone to save sixty dollars is a bad trade" is
> a better answer than any saving.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ One Terraform state for everything | ⭐⭐ an app mistake can destroy the database |
| ⭐ Console changes on top of IaC | ⭐ silently reverted by the next apply |
| ⭐⭐ **Never running `destroy`/`apply` in a scratch account** | ⭐⭐ you do not know whether it rebuilds |
| ⭐ Building the edge before the network | circular dependencies and rework |
| ⭐ Certificate outside `us-east-1` for CloudFront | first-deploy failure, always |
| ⭐⭐ **Claiming multi-AZ without ever killing a zone** | ⭐⭐ a claim about AWS, not about you |
| ⭐ Treating Well-Architected as a scorecard | ⭐ it is a question list; accepted risk is a valid answer |
| ⭐ No `prevent_destroy` on data resources | one bad plan away |
| ⭐⭐ **Not knowing cost per request** | ⭐⭐ cost cannot be engineered if it is not measured |
| Optimising everything | no judgement, or no deadline |

## Interview questions

**Q: Walk me through your AWS architecture.**
Route 53 alias at the apex into CloudFront, which serves static assets from a private S3 bucket via an
origin access control and passes `/api/*` through uncached so TLS terminates at the edge and WAF sits in
front of everything. Behind that an ALB in public subnets across three availability zones, Fargate tasks
in private subnets, and RDS Multi-AZ plus Redis in isolated subnets with no internet route at all.
Asynchronous work goes through SQS with a dead letter queue to a worker that scales on the age of the
oldest message. Every security group rule references another security group rather than an address
range, there is an S3 gateway endpoint so image and object traffic never touches the NAT, and the whole
thing is Terraform in layers deployed by GitHub Actions through OIDC, so no access key exists anywhere.

**Q: How do you know it survives losing an availability zone?**
Because I did it. Three zones with N+1 capacity, then killed every task in one zone under load: p99 rose
about forty milliseconds, no requests failed, and — the part that matters — no scaling action was
required, because recovery that depends on launching new capacity depends on the control plane at exactly
the moment it is most likely to be strained. That is static stability, and it is the difference between
being multi-AZ on the invoice and being multi-AZ in production.

**Q: What is your cost per request?**
I track it on the same dashboard as p99, because it turns cost into something a design change can be
evaluated against and makes a regression visible — cost per request rising while traffic is flat is a
bug. I can also name my top three lines and what I did about each: log retention, which defaults to never
expire and was the largest; NAT data processing, which the S3 gateway endpoint mostly removed; and
compute, where the fixes were the current generation, Graviton, and a Savings Plan sized to the floor
rather than the average.

**Q: Which parts of this would you build differently at ten times the scale?**
The queue-based parts scale fine, and the edge is already right. What changes is the database: a single
Postgres primary becomes the constraint, so the first move is reads onto replicas with a sticky read
window for read-your-writes, and after that either partitioning by tenant or moving the highest-volume
table to a store designed for it. The second change is observability, because at ten times the traffic
the log volume and metric cardinality become one of the largest lines, and the answer is sampling and
Prometheus for application metrics rather than CloudWatch custom metrics. That is the design review
question I try to always ask — what does this cost and what breaks at ten times, not today.

**Q: What did you deliberately not do?**
Multi-region. It roughly doubles the cost and the operational surface, DNS failover realistically takes
minutes with a long tail of clients that never move, and the data story — either accepting write loss or
accepting cross-region latency on every write — is a much bigger commitment than people admit when they
say "active-active". For this product's availability target, three availability zones in one region with
tested failover is the better trade, and I would want a stated recovery objective from the business
before spending that.

## Mini task

1. ⭐⭐ Build the full architecture in **layered Terraform**, then `destroy` and `apply` it in a scratch
   account. **If it does not rebuild, it is not infrastructure as code.**
2. ⭐ Wire the pipeline with **OIDC** and confirm zero access keys exist in the account.
3. ⭐⭐ **Kill an AZ under load.** Record p99, failures and whether any scaling occurred.
4. ⭐⭐ **Force the RDS failover under load.** Record client-visible recovery. Fix the DNS TTL if it is
   bad, and repeat.
5. ⭐⭐ **Deploy under load** and prove zero dropped requests across a full rolling update.
6. ⭐ Ship a **deliberately broken image** and watch the circuit breaker roll it back.
7. ⭐⭐ **Rotate the database credential under load** with zero failures.
8. ⭐ Dump 100,000 messages into the queue and **graph the backlog draining** against your target.
9. ⭐ Produce **one end-to-end trace** from CloudFront to the database, with the trace id in the logs.
10. ⭐⭐ Put **cost per request** on the dashboard next to p99.
11. ⭐ Run the **Well-Architected Tool** and turn the findings into a backlog with at least one
    "accepted risk, because…".
12. ⭐⭐ Write a **one-page architecture document**: the diagram, the five questions answered with
    numbers, and the three things you chose not to do.

## 🎙️ Articulation drill

**Three minutes:** *"Tell me about a system you deployed to AWS."*

**⭐ Structure: the shape, then the evidence, then the trade.**

**⭐ The shape in four sentences** — edge, load balancer, private compute, isolated data; everything in
layered Terraform; deployed by a pipeline with no stored credential.

**⭐ Then the evidence, because this is where most answers stop and yours should not: we killed an
availability zone under load and p99 moved forty milliseconds with no failed requests and no scaling
action. We forced a database failover and the application recovered in eleven seconds, which it did not
the first time because the JVM was caching DNS forever. We rotate the database credential under load
with alternating users and zero failures. We deploy under load with zero dropped requests.**

**⭐ Then the trade, which is what makes it sound like a real system: we are single-region on purpose,
because multi-region doubles cost and operations while DNS failover still takes minutes — and our cost
per request is on the dashboard next to p99, so that decision can be revisited with numbers rather than
opinions.**
