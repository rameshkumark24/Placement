# Part 1 — Versioning, and the strategy that survives contact

Day 109's rule: **additive changes are safe, removals and semantic changes are not.** Version only
when you must break something.

| Strategy | Example | Verdict |
|---|---|---|
| **URI path** | `/api/v1/orders` | ⭐ **the default.** Visible in logs, trivially routable at the gateway, cacheable, obvious in a bug report |
| Header | `X-API-Version: 1` | purist-correct — the resource is the same, only the representation differs. But invisible in logs, easy to omit, painful to test with `curl`, and breaks naive caches |
| Media type | `Accept: application/vnd.acme.order.v2+json` | most REST-correct, most operationally annoying |
| Query param | `?version=2` | ❌ pollutes caching, easy to forget, mixes with filters |

**Choose URI path and be able to defend the choice.** The interview answer that lands: *"Header
versioning is more correct in theory, but versioning is an operational problem, not a purity problem
— and I want to see the version in an access log, route on it at the gateway, and reproduce a bug
with one curl."*

## Implementation, and where the version boundary sits

```java
@RestController
@RequestMapping("/api/v1/orders")
class OrderV1Controller {
    private final OrderService orders;

    @GetMapping("/{id}")
    OrderV1Response get(@PathVariable UUID id) {
        return OrderV1Response.from(orders.find(id));      // ⭐ mapping, not logic
    }
}

@RestController
@RequestMapping("/api/v2/orders")
class OrderV2Controller {
    private final OrderService orders;                     // ⭐ THE SAME service

    @GetMapping("/{id}")
    OrderV2Response get(@PathVariable UUID id) {
        return OrderV2Response.from(orders.find(id));
    }
}
```

**⭐ The rule that keeps versioning affordable: version the edge, never the core.** Two controllers
and two response DTOs; one service, one domain model, one repository. If you find yourself with
`OrderServiceV1` and `OrderServiceV2` you have forked your business logic, and every bug fix now has
to be applied twice — which means it will eventually be applied once.

If v2 genuinely needs different *behaviour*, that behaviour belongs in the service as a parameter or a
strategy, not as a duplicated class.

## Deprecation, done properly

```java
@Deprecated(since = "2026-08-01", forRemoval = true)
@GetMapping("/{id}")
ResponseEntity<OrderV1Response> get(@PathVariable UUID id) {
    return ResponseEntity.ok()
        .header("Deprecation", "@1754006400")                        // RFC 8594, epoch seconds
        .header("Sunset", "Wed, 01 Apr 2027 00:00:00 GMT")           // ⭐ RFC 8594
        .header("Link", "<https://api.acme.com/docs/v2>; rel=\"deprecation\"")
        .body(OrderV1Response.from(orders.find(id)));
}
```

**And the part that is not a header:**

```java
log.warn("deprecated_endpoint_called path={} clientId={} userAgent={}",
         req.getRequestURI(), clientId, req.getHeader("User-Agent"));
```

Day 109's core point: **you cannot remove an endpoint you cannot measure.** Emit a metric tagged by
client, watch it for a quarter, contact the three clients still calling it, then remove. Announcing a
sunset date and hoping is how you cause an outage on the removal date.

An interceptor (Day 151) reading `@Deprecated` from the `HandlerMethod` does this for every endpoint
at once — one of the cleanest legitimate uses of an interceptor.

# Part 2 — springdoc, and the code-first tension

```xml
<dependency>
  <groupId>org.springdoc</groupId>
  <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
  <version>2.6.0</version>
</dependency>
```

That is all. `/v3/api-docs` serves the spec, `/swagger-ui.html` serves the UI. It reads your
mappings, your DTOs, your Bean Validation annotations and your `ResponseEntity` types.

**Day 110's objection, stated fairly:** a generated spec describes what the code does. It cannot
describe what the code *should* do, it changes silently when the code changes, and it cannot be
reviewed before implementation — so the client team cannot start work from it.

**The honest resolution, and this is the interview-grade answer:**

> Use code-first generation, then **treat the generated spec as a build artefact and diff it in CI.**
> A change to the spec becomes a reviewable diff in a pull request. You get code-first's
> never-out-of-date property and contract-first's "someone approved this change" property.

```xml
<!-- generate the spec at build time -->
<plugin>
  <groupId>org.springdoc</groupId>
  <artifactId>springdoc-openapi-maven-plugin</artifactId>
  <executions><execution><goals><goal>generate</goal></goals></execution></executions>
</plugin>
```

Then a CI step: regenerate, `diff` against the committed `openapi.json`, fail if they differ without
the file being updated in the same commit. **A breaking change now shows up in code review as a
red diff instead of in production as a client outage.** Tools like `oasdiff` will even classify the
change as breaking or non-breaking automatically.

## Making the generated spec actually good

The default output is mediocre — it describes types but not meaning. Four things fix most of it:

```java
@Tag(name = "Orders", description = "Order placement and lifecycle")
@RestController
@RequestMapping("/api/v1/orders")
class OrderController {

    @Operation(summary = "Place an order",
               description = "Reserves stock and creates an order in PENDING status.")
    @ApiResponses({
        @ApiResponse(responseCode = "201", description = "Created"),
        @ApiResponse(responseCode = "422", description = "Insufficient stock",
                     content = @Content(schema = @Schema(implementation = ProblemDetail.class))),
        @ApiResponse(responseCode = "429", description = "Rate limited")
    })
    @PostMapping
    ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest req) { ... }
}
```

| Do this | Why |
|---|---|
| ⭐ **Document error responses** | the default spec shows only the happy path, and Day 149's problem shapes are the half clients get wrong |
| ⭐ **Return concrete types, never `ResponseEntity<?>`** | Day 146 — a wildcard erases the schema entirely and every generated client breaks |
| **Let Bean Validation carry constraints** | `@Min(1) @Max(100)` becomes `minimum`/`maximum` in the schema for free. Day 148 paying off twice |
| `@Schema(example = "...")` on DTO fields | examples are what make a spec usable by a human |

```java
public record CreateOrderRequest(
        @Schema(example = "P-42", description = "Catalogue product identifier")
        @NotBlank String productId,
        @Schema(example = "2") @Min(1) @Max(100) int quantity) { }
```

## Security schemes, so "Authorize" works

```java
@Bean
OpenAPI api() {
    return new OpenAPI()
        .info(new Info().title("Orders API").version("v1")
              .description("See https://api.acme.com/docs for the error catalogue."))
        .addSecurityItem(new SecurityRequirement().addList("bearer"))
        .components(new Components().addSecuritySchemes("bearer",
            new SecurityScheme().type(HTTP).scheme("bearer").bearerFormat("JWT")));
}
```

Without this the Swagger UI cannot send an `Authorization` header, so every endpoint returns 401 and
people conclude the docs are broken.

## ⭐ Do not expose Swagger UI in production

```yaml
springdoc:
  api-docs.enabled: ${SPRINGDOC_ENABLED:false}
  swagger-ui.enabled: ${SPRINGDOC_ENABLED:false}
```

Day 119's information disclosure: a public Swagger UI is **a complete, machine-readable map of your
attack surface**, including internal endpoints, parameter names for mass-assignment attempts, and
error shapes. It is the API equivalent of Day 143's `/actuator/mappings`.

Serve the spec to consumers as a published, versioned artefact from a docs site or a developer
portal — a *deliberate* publication of the contract you intend to support, which is not the same
thing as an always-live UI hanging off your production service.

# Part 3 — Generating clients, which is where the spec earns its keep

```xml
<plugin>
  <groupId>org.openapitools</groupId>
  <artifactId>openapi-generator-maven-plugin</artifactId>
  <configuration>
    <inputSpec>${project.basedir}/openapi.json</inputSpec>
    <generatorName>java</generatorName>
    <library>resttemplate</library>
  </configuration>
</plugin>
```

**This is the argument that wins over "the docs are enough".** A generated client means the consuming
team never hand-writes a DTO, never mistypes a field name, and — critically — **their build breaks
the day you make a breaking change**, at your merge rather than at their runtime.

It also disciplines you: sloppy specs generate awful clients, so the feedback loop pushes the spec's
quality up. If your generated client has a method called `getUsingGET1`, that is the spec telling you
your `@Operation` annotations are missing.

## Contract testing, briefly

An OpenAPI spec plus a validating filter in your integration tests means a response that drifts from
the spec fails a test rather than a client:

```java
// atlassian swagger-request-validator
mockMvc.perform(get("/api/v1/orders/{id}", id))
       .andExpect(openApi().isValid("openapi.json"));      // ⭐ response must match the contract
```

Day 184 covers testing properly. The point here is that a spec is only a contract if something
enforces it — otherwise it is documentation that drifts.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Versioning the service layer | forked business logic; fixes applied once instead of twice |
| Creating v2 for an additive change | Day 109 — adding a field is not breaking; a new version costs everyone |
| `Sunset` header with no usage metric | you cannot know who breaks on removal day |
| Swagger UI live in production | a published map of the attack surface |
| `ResponseEntity<?>` | schema erased; generated clients useless |
| Undocumented error responses | clients handle only the happy path |
| Generated spec never diffed | breaking changes ship silently |
| No security scheme | UI cannot authenticate; docs look broken |
| No examples | technically complete, practically unusable |
| Query-param versioning | caching and filter collisions |

## Interview questions

**Q: How do you version an API?**
URI path versioning, and I version only on breaking changes — additive is safe. Critically I version
the edge only: separate controllers and response DTOs, one shared service. Forking the service layer
means every bug gets fixed in one of two places.

**Q: Header versioning is more RESTful — why not use it?**
It is, and I would consider it for a machine-only API. But versioning is an operational concern: I
want the version in an access log, routable at the gateway, and reproducible with one curl. That
usually outweighs the purity argument.

**Q: Code-first or contract-first?**
Contract-first is better in principle because the spec can be reviewed and clients can start before
implementation. In practice I use springdoc and close the gap by generating the spec at build time,
committing it, and diffing it in CI — so a contract change is a reviewable diff rather than a
surprise.

**Q: How do you retire an endpoint safely?**
Deprecation and Sunset headers, docs, and a metric tagged by client. Then I watch usage for a
quarter, contact the remaining callers directly, and remove only when the metric is at zero. The
headers are the announcement; the metric is the evidence.

## 🎙️ Articulation drill

Two minutes: **"How do you version and document an API?"**

URI versioning for operational visibility, versioned only on genuinely breaking changes, and only at
the edge — two controllers, one service. Deprecation and Sunset headers plus a per-client usage
metric, because you cannot remove what you cannot measure. springdoc for the spec, with the honest
caveat that generation is code-first, closed by committing the spec and diffing it in CI so a
breaking change is a red diff at review time. Then the two things people forget: disable the UI in
production because it maps your attack surface, and generate clients from the spec so consumers break
at your merge rather than at their runtime.
