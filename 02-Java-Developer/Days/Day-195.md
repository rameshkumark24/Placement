# Part 1 — The setup, and what PostgreSQL actually gives you

```sql
create table accounts (id bigint primary key, owner text, balance numeric(19,2) not null);
insert into accounts values (1,'alice',1000), (2,'bob',1000);

create table doctors (id bigint primary key, name text, on_call boolean not null);
insert into doctors values (1,'alice',true), (2,'bob',true);
```

**Open two psql sessions. Call them A and B.**

| Level | Dirty read | Non-repeatable read | Phantom | ⭐ Write skew / lost update |
|---|---|---|---|---|
| `READ UNCOMMITTED` | ⭐ **PostgreSQL treats this as READ COMMITTED** | | | |
| ⭐ **`READ COMMITTED`** (default) | ❌ prevented | ✅ possible | ✅ possible | ✅ possible |
| **`REPEATABLE READ`** | ❌ | ❌ prevented | ⭐ ❌ **prevented too** | ✅ possible |
| ⭐ **`SERIALIZABLE`** | ❌ | ❌ | ❌ | ⭐ ❌ **prevented** |

**⭐ Two PostgreSQL-specific facts that differ from the SQL standard and from other engines:**

1. **`READ UNCOMMITTED` does not exist** — it silently behaves as `READ COMMITTED`. **Dirty reads are
   impossible in PostgreSQL**, because MVCC never exposes an uncommitted version (Day 194).
2. ⭐ **`REPEATABLE READ` also prevents phantoms**, which the standard does not require. PostgreSQL's
   implementation is snapshot isolation, which is stronger than the standard's `REPEATABLE READ`.

**That second point is a good interview detail**, and it is why MySQL and PostgreSQL differ in
behaviour at the same nominal level — Day 164's `Isolation.DEFAULT` warning, from the database side.

# Part 2 — ⭐ Reproduce the anomalies

## Experiment 1 — Non-repeatable read (`READ COMMITTED`)

```sql
-- A                                        -- B
begin;
select balance from accounts where id=1;    -- ⭐ 1000
                                            begin;
                                            update accounts set balance=500 where id=1;
                                            commit;
select balance from accounts where id=1;    -- ⭐⭐ 500 — SAME QUERY, DIFFERENT ANSWER
commit;
```

**⭐ At `READ COMMITTED`, each *statement* gets a fresh snapshot.** So two identical reads in one
transaction can disagree. Any calculation that reads a value twice is unsafe here.

## Experiment 2 — The same, prevented (`REPEATABLE READ`)

```sql
-- A
begin transaction isolation level repeatable read;
select balance from accounts where id=1;    -- 1000
                                            -- B updates to 500 and commits
select balance from accounts where id=1;    -- ⭐ STILL 1000 — the transaction's snapshot is fixed
commit;
```

**⭐ The whole transaction shares one snapshot**, taken at the first statement.

## Experiment 3 — Phantom read

```sql
-- A
begin;   -- READ COMMITTED
select count(*) from accounts where balance > 500;    -- ⭐ 2
                                            -- B inserts a new account with balance 900, commits
select count(*) from accounts where balance > 500;    -- ⭐⭐ 3 — a row APPEARED
commit;
```

**Repeat at `REPEATABLE READ` and it returns 2 both times** — PostgreSQL prevents phantoms there.

## ⭐ Experiment 4 — Lost update

```sql
-- A                                        -- B
begin;                                      begin;
select balance from accounts where id=1;    select balance from accounts where id=1;
-- both read 1000                           -- both read 1000
update accounts set balance = 1000 - 100;   
commit;                                     update accounts set balance = 1000 - 200;
                                            commit;
-- ⭐⭐ Final balance: 800. A's withdrawal of 100 VANISHED. No error.
```

**⭐ This is Day 165's lost update at the database level**, and it is the single most important
experiment on this page. **Run it. Watch money disappear with no error.**

**⭐ Four fixes, and knowing all four is the answer:**

```sql
-- 1. ⭐ Atomic UPDATE — no read-modify-write at all. BEST for a counter.
update accounts set balance = balance - 100 where id = 1;

-- 2. ⭐ Pessimistic lock — Day 165
select balance from accounts where id = 1 for update;

-- 3. ⭐ Optimistic — @Version, Day 165
update accounts set balance = :new, version = version + 1 where id = 1 and version = :old;

-- 4. ⭐ REPEATABLE READ — PostgreSQL ABORTS the second transaction
--    ERROR: could not serialize access due to concurrent update
```

**⭐ Note that fix 4 is free and automatic**: at `REPEATABLE READ`, PostgreSQL detects that A's row
was modified and aborts B rather than losing the update. **The cost is that you must handle the
serialisation error and retry** — which the application must be written to do.

## ⭐⭐ Experiment 5 — Write skew (the one `SERIALIZABLE` exists for)

**The rule: at least one doctor must remain on call.**

```sql
-- A                                             -- B
begin isolation level repeatable read;           begin isolation level repeatable read;
select count(*) from doctors where on_call;      select count(*) from doctors where on_call;
-- ⭐ 2, so it is safe for me to go off call     -- ⭐ 2, so it is safe for me to go off call
update doctors set on_call=false where id=1;     update doctors set on_call=false where id=2;
commit;                                          commit;
-- ⭐⭐ ZERO doctors on call. Both transactions were individually correct.
```

**⭐ This is why `SERIALIZABLE` exists, and it is the anomaly people cannot describe in interviews.**

Note what makes it different from a lost update: **the two transactions touched *different rows*.**
No row-level conflict exists, so `REPEATABLE READ` sees nothing wrong. Each read a state, made a
decision that was valid for that state, and wrote — and the *combination* violates an invariant
neither transaction could see.

**⭐ Run it at `SERIALIZABLE` and the second commit fails:**

```
ERROR: could not serialize access due to read/write dependencies among transactions
HINT:  The transaction might succeed if retried.
```

# Part 3 — ⭐ `SERIALIZABLE` in practice

**PostgreSQL implements Serializable Snapshot Isolation (SSI).** It does not lock; it **tracks
read/write dependencies between transactions and aborts one if the dependency graph contains a cycle
that could not occur in any serial order.**

| Property | Detail |
|---|---|
| ⭐ Guarantee | ⭐ **the result equals *some* serial execution.** The strongest guarantee available |
| ⭐ Cost | ⭐ **not locking — aborts.** Readers still do not block |
| ⭐ Requirement | ⭐⭐ **your application MUST retry on serialisation failure** |
| Overhead | tracking predicate locks; grows with concurrency |
| Caveat | ⭐ needs `default_transaction_isolation` set **consistently** — one non-serializable transaction can break the guarantee |

## ⭐ The retry loop is mandatory, not optional

```java
@Retryable(retryFor = CannotSerializeTransactionException.class,      // ⭐ Spring's translation
           maxAttempts = 3,
           backoff = @Backoff(delay = 50, multiplier = 2, random = true))   // ⭐ jitter, Day 123
@Transactional(isolation = Isolation.SERIALIZABLE)
public void goOffCall(Long doctorId) { ... }
```

**⭐ `SERIALIZABLE` without a retry loop converts a correctness problem into an availability problem**
— users see random errors under load. The retry must be **outside** the transaction (a new
transaction each attempt), which is why `@Retryable` sits above `@Transactional` here — Day 181's
composition order, in a different setting.

**⭐ And the method must be safe to re-run**, which is Day 123's idempotency requirement arriving
from the database.

## ⭐ When to use each level — the honest guidance

| Situation | Level |
|---|---|
| ⭐ **Most application work** | ⭐ **`READ COMMITTED`** (the default) + explicit locking or `@Version` where needed |
| A report needing a consistent view across many queries | ⭐ `REPEATABLE READ` |
| ⭐ **A multi-row invariant you cannot express as a constraint** | ⭐ `SERIALIZABLE` + retry |
| A simple counter | ⭐ **no isolation change — an atomic `UPDATE`** |

**⭐ And the alternative that beats all of them where it applies:**

```sql
alter table doctors add constraint at_least_one_on_call ...   -- ⭐ if expressible
create unique index ... ;                                      -- Day 187
exclude using gist (room_id with =, during with &&);          -- ⭐ Day 187 — write skew, solved
```

**A constraint holds regardless of isolation level, regardless of retry logic, and regardless of
which application wrote the row.** Day 187's exclusion constraint prevents the booking version of
write skew with no isolation change at all.

**⭐ The interview-grade summary: reach for a constraint first, an atomic statement second, explicit
locking third, and `SERIALIZABLE` when the invariant genuinely spans rows in a way none of those can
express.**

# Part 4 — Explicit locking, and `SELECT FOR UPDATE`'s variants

```sql
select * from accounts where id=1 for update;              -- ⭐ exclusive; others wait
select * from accounts where id=1 for no key update;       -- allows FK references
select * from accounts where id=1 for share;               -- others may read, not write
select * from jobs where status='PENDING'
  order by created_at for update skip locked limit 100;    -- ⭐⭐ Day 178's job claim
select * from accounts where id=1 for update nowait;       -- ⭐ error instead of waiting
```

**⭐ `SKIP LOCKED` is the primitive behind every well-built job queue** (Day 178, Day 184). Each
worker claims rows nobody else holds, without blocking. Without it, workers serialise on the same
rows and the queue does not parallelise.

**`NOWAIT` is underused** — it converts a queue-behind-a-lock into an immediate error you can handle,
which is often better than an unbounded wait (Day 165's lock timeout argument).

⚠️ ⭐ **A `FOR UPDATE` at `READ COMMITTED` re-reads the row after acquiring the lock** and applies
your `WHERE` clause to the *new* version. That is usually what you want and it can surprise you: the
row you locked may no longer match the predicate you selected on.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Assuming `READ COMMITTED` prevents lost updates | it does not — Experiment 4 |
| Read-modify-write without a lock or version | the default is silent data loss |
| ⭐ `SERIALIZABLE` with no retry loop | random user-visible errors under load |
| Retrying inside the transaction | the transaction is already aborted |
| Retrying without jitter | synchronised retry storms (Day 123) |
| ⭐ Assuming other databases behave identically at the same level | MySQL's `REPEATABLE READ` differs |
| Expecting `READ UNCOMMITTED` to do something | PostgreSQL ignores it |
| Reaching for `SERIALIZABLE` before a constraint | more expensive and less reliable |
| ⭐ Not knowing write skew | the anomaly interviews probe |
| `FOR UPDATE` in a long transaction | blocks others; Day 194's vacuum problem |
| No `SKIP LOCKED` in a job queue | workers serialise |

## Interview questions

**Q: What is write skew, and why doesn't `REPEATABLE READ` prevent it?**
Two transactions read overlapping data, each makes a decision valid for what it saw, and each writes
to a *different* row. Because no two transactions modify the same row, snapshot isolation sees no
conflict — but the combination violates an invariant neither could observe. The doctors-on-call case:
both check that two are on call, both go off call, and nobody is covering. `SERIALIZABLE` detects the
read/write dependency cycle and aborts one.

**Q: How does PostgreSQL implement `SERIALIZABLE`?**
Serializable Snapshot Isolation. It does not take locks; it tracks read/write dependencies and aborts
a transaction whose commit would create a cycle that no serial ordering could produce. So readers
still never block — but the application must retry on serialisation failure, and if it does not, a
correctness feature becomes an availability problem.

**Q: Two users update the same row at `READ COMMITTED`. What happens?**
The second write wins and the first is silently lost — no error. The fixes are an atomic `UPDATE`
that does the arithmetic in the database, `SELECT FOR UPDATE`, a version column, or `REPEATABLE
READ`, which detects the conflict and aborts the second transaction so you can retry.

**Q: What is PostgreSQL-specific about its isolation levels?**
`READ UNCOMMITTED` does not exist — MVCC makes dirty reads impossible — and `REPEATABLE READ` also
prevents phantoms, which the SQL standard does not require. So code that is correct on PostgreSQL at
`REPEATABLE READ` may not be on another engine at the same nominal level.

**Q: When do you use `SERIALIZABLE`?**
For a multi-row invariant I cannot express as a constraint. I try a constraint first — an exclusion
constraint prevents the booking form of write skew with no isolation change — then an atomic
statement, then explicit locking. `SERIALIZABLE` is correct and it costs aborts and a retry loop.
