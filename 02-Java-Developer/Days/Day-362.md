# Day 362

**L-362** · Images and layers — the cache, the tag lie, and the secret you cannot delete

**Time:** 3 hrs · **Mode:** NEW

> **⭐ An image is not a disk. It is a stack of tarballs plus a JSON config — and every one of those
> layers is permanent.**
>
> Two consequences dominate everything else: **the build cache is entirely determined by instruction
> order**, and **a secret written in any layer stays retrievable forever, even if a later layer
> deletes it.**

---

# Part 1 — ⭐ What an image actually is

```
⭐ IMAGE = ⭐ an ordered list of LAYERS (each a tar of filesystem changes)
⭐       + ⭐ a CONFIG (entrypoint, env, user, workdir, exposed ports)
⭐       + ⭐ a MANIFEST (which layers, which config, which architecture)
⭐
⭐ Every one is content-addressed by ⭐ sha256. ⭐ The image's digest covers the whole thing.
```

| ⭐ Property | ⭐ Consequence |
|---|---|
| ⭐ **Layers are content-addressed** | ⭐⭐ **identical layers are stored and transferred once, across all images** |
| ⭐ **Layers are ordered and additive** | ⭐⭐ **a later layer can hide a file but never remove its bytes** |
| ⭐ Each Dockerfile instruction makes one layer | ⭐ **`RUN`, `COPY`, `ADD` create layers; `ENV`, `LABEL` and friends only change config** |
| ⭐ **The digest is immutable** | ⭐ a tag is not — see Part 3 |
| Multi-arch is a manifest list | one tag, several architectures |

```bash
docker history myapp:1.0        # ⭐ every layer, its size, and the instruction that made it
docker inspect myapp:1.0        # ⭐ the config: entrypoint, user, env, healthcheck
```

# Part 2 — ⭐⭐ The build cache, and the ordering rule

> **⭐ For each instruction, Docker checks whether it has already built this exact instruction on
> top of this exact parent layer. If yes it reuses it. If no, that instruction and EVERY INSTRUCTION
> AFTER IT is rebuilt.**

```dockerfile
⭐ ✗ WRONG — one source change invalidates the dependency download
COPY . /app                     ⭐ ← changes on every commit
RUN mvn dependency:go-offline   ⭐ ← therefore re-downloads 300 MB EVERY BUILD
RUN mvn package

⭐ ✓ RIGHT — the dependency layer is cached until pom.xml changes
COPY pom.xml /app/              ⭐ ← changes rarely
RUN mvn dependency:go-offline   ⭐ ← cached across hundreds of builds
COPY src /app/src               ⭐ ← changes every commit
RUN mvn package -o
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐⭐ **Order from least-changing to most-changing** | ⭐⭐ **the single highest-value Dockerfile skill** |
| ⭐ `COPY` invalidates on **content**, not timestamp | so an unchanged file keeps the cache |
| ⭐⭐ **`RUN` invalidates on the command STRING only** | ⭐⭐ **`RUN apt-get update` is cached forever and silently serves stale package lists** |
| ⭐ A `.dockerignore` protects the cache | ⭐ `target/` or `.git` in the context busts `COPY .` constantly |
| ⭐ **BuildKit cache mounts** | ⭐ `--mount=type=cache,target=/root/.m2` — **persists across builds without living in a layer** |

⚠️ **The `apt-get update` trap is worth memorising.** Because the cache keys on the command text, an
`update` layer built six months ago is reused, and the following `install` then fetches versions the
index no longer matches. **Always combine them in one `RUN`:**

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*      ⭐ same layer, or the cleanup does nothing (Part 3)
```

⚠️ **And the `.dockerignore` is not only about size.** A 2 GB build context is slow to send to the
daemon, **but the real damage is that `COPY . .` sees a changed `target/` on every build and destroys
every downstream cache layer.**

# Part 3 — ⭐⭐ Layers are additive: two consequences that bite

## ⭐ 1. Deleting does not shrink

```dockerfile
RUN wget https://example.com/big-toolchain.tar.gz    ⭐ layer A: +900 MB
RUN tar -xzf big-toolchain.tar.gz                    ⭐ layer B: +900 MB
RUN rm big-toolchain.tar.gz                          ⭐ layer C: +0 MB (a whiteout marker)
⭐ ⇒ ⭐⭐ FINAL IMAGE: ~1.8 GB. The rm freed nothing.
```

**⭐ The fix is one `RUN`**, so the file never exists at layer boundaries:

```dockerfile
RUN wget ... && tar -xzf ... && rm big-toolchain.tar.gz     ⭐ one layer, net small
```

## ⭐⭐ 2. Secrets in any layer are permanent

```dockerfile
⭐ ✗ ALL OF THESE LEAK, PERMANENTLY:
COPY .env /app/.env
RUN echo "$API_KEY" > /app/key && ./build.sh && rm /app/key   ⭐ still in layer 1
ARG NPM_TOKEN                                                  ⭐ visible in `docker history`
```

| ⭐ Retrieval path | |
|---|---|
| ⭐ `docker history --no-trunc` | ⭐⭐ **shows `ARG` values and full `RUN` commands** |
| ⭐ **Extracting an intermediate layer's tar** | ⭐⭐ **any deleted file is still there** |
| Anyone who can pull the image | ⭐ **which, for a shared registry, is everyone** |

> **⭐ The rule: a secret that has ever been in a layer is compromised and must be rotated.** Deleting
> it, squashing the image or pushing a new tag does not help — **Day 296's lesson, at the image
> layer.**

**⭐ The correct mechanisms:**

| ⭐ Need | ⭐ Use |
|---|---|
| ⭐ **Build-time secret** (a private repo token) | ⭐⭐ **BuildKit secret mount** — `RUN --mount=type=secret,id=npmrc ...` — **never lands in a layer** |
| ⭐ Build-time SSH | `--mount=type=ssh` |
| ⭐ **Runtime secret** | ⭐⭐ **injected at run time** — never in the image at all (Day 364) |
| Non-secret build config | `ARG` is fine — and remember it is public |

# Part 4 — ⭐ Tags, digests, and the config

## ⭐⭐ A tag is a mutable pointer

```
⭐ myapp:1.2.3       → ⭐⭐ can be REPOINTED at any time by anyone with push access
⭐ myapp@sha256:ab12… → ⭐⭐ IMMUTABLE. That content, forever.
```

| ⭐ Consequence | |
|---|---|
| ⭐⭐ **`latest` is not a version** | ⭐⭐ it is a default tag name with no semantics whatsoever |
| ⭐ **Two pulls of the same tag can differ** | ⭐ so "we deployed 1.2.3" is not a reproducible statement |
| ⭐⭐ **Pin production by digest** | ⭐⭐ **the deployment references the digest; the tag is for humans** |
| ⭐ Tag immutability can be enforced | ⭐ most registries support it — **turn it on** |
| ⭐ Base images too | ⭐ `FROM eclipse-temurin:21-jre@sha256:…` makes your build reproducible |

⚠️ **Pinning base images by digest is a real trade-off, and say both sides:** it makes builds
reproducible and prevents a supply-chain surprise, **but it also means you stop receiving security
patches until someone updates the digest.** The answer is **pin plus an automated bump** (Dependabot
or Renovate) — pinning without automation is how images rot for two years.

## ⭐ The config that matters

| Field | ⭐ Note |
|---|---|
| ⭐ **`ENTRYPOINT` vs `CMD`** | ⭐ entrypoint is the program; **cmd is the default arguments** — `docker run img --flag` replaces CMD only |
| ⭐ **Both in exec form** | ⭐⭐ shell form breaks signals (Day 361) |
| ⭐ `USER` | ⭐ **set a non-root uid; the default is root** |
| `WORKDIR` | never `RUN cd` — it does not persist |
| ⭐ **`HEALTHCHECK`** | ⭐ useful for Compose; **Kubernetes ignores it and uses its own probes** |
| `EXPOSE` | documentation only — it publishes nothing |
| ⭐ **`ENV`** | ⭐ visible in `docker inspect` — **never a secret** |
| ⭐ OCI labels | ⭐ `org.opencontainers.image.revision` — **stamp the git SHA so you can trace a running image back to source** |

> **⭐ Stamping the git SHA as a label, and exposing it via Actuator's `build-info` (Day 143), is what
> makes "which commit is running in production?" a one-command answer** rather than an
> archaeological exercise.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ `COPY . .` before dependency resolution | ⭐⭐ **300 MB re-downloaded on every commit** |
| ⭐ `apt-get update` in its own layer | ⭐ cached forever; stale package index |
| ⭐ Downloading and deleting across layers | ⭐ **the image keeps both copies** |
| ⭐⭐ **Any secret in any layer** | ⭐⭐ **permanently retrievable — rotate it** |
| ⭐ `ARG` for a token | visible in `docker history` |
| ⭐ No `.dockerignore` | slow context **and** a destroyed cache |
| ⭐ **Deploying by tag** | ⭐ the tag can be repointed; the deploy is not reproducible |
| ⭐ `latest` in production | not a version |
| ⭐ Pinning base images with no update automation | ⭐ **two years of unpatched CVEs** |
| Shell-form ENTRYPOINT | signals lost (Day 361) |
| No `USER` | runs as root |
| ⭐ Secrets in `ENV` | ⭐ `docker inspect` shows them |
| No SHA label | you cannot map a running image to a commit |

## Interview questions

**Q: What is a Docker image?**
An ordered list of content-addressed layers, each a tar of filesystem changes, plus a config with the
entrypoint, user and environment, plus a manifest tying them together. Because layers are
content-addressed, identical ones are stored and transferred once across every image that uses them —
which is why pulling a new version of your app only downloads the layer that changed.

**Q: How does the build cache work, and what is the main rule?**
Each instruction is cached against its exact parent layer; the first miss invalidates everything
after it. So the rule is to order instructions from least-changing to most-changing — copy the
dependency manifest and resolve dependencies before copying source, or every commit re-downloads the
world. The subtlety is that `RUN` keys on the command string only, which is why `apt-get update`
alone is cached indefinitely and must be combined with the install.

**Q: You accidentally copied a `.env` file into an image and removed it in the next instruction. Are
you safe?**
No. Layers are additive — the later instruction writes a whiteout marker, but the bytes are still in
the earlier layer and anyone who can pull the image can extract them. `docker history` also exposes
build arguments and full `RUN` commands. The secret is compromised and must be rotated; the fix
afterwards is a BuildKit secret mount for build-time secrets, and runtime injection for everything
else.

**Q: Why is an image smaller after combining `RUN` instructions?**
Because each instruction is a layer, and deleting a file in a later layer does not reclaim the space
in an earlier one. Downloading a 900 MB archive, extracting it, then removing it across three
instructions produces an image containing all of it twice. Doing it in one `RUN` means the archive
never exists at a layer boundary, so it never enters the image.

**Q: Would you deploy by tag or by digest?**
Digest, with the tag kept for humans. A tag is a mutable pointer, so two pulls of `1.2.3` can return
different bytes and "we deployed 1.2.3" stops being reproducible. I would enable tag immutability in
the registry as well. The same applies to base images — pin them by digest, but pair that with
automated updates, because pinning without automation just means you stop getting security patches.

## Mini task

1. **Run `docker history --no-trunc` on an image you built.** Find the three largest layers and the
   instruction that created each.
2. ⭐ Build with `COPY . .` before dependency resolution. Change one source file and **time the
   rebuild.** Reorder and time it again. **Record both.**
3. ⭐ Add a `.dockerignore` excluding `target/` and `.git`. **Measure the build context size before
   and after.**
4. ⭐⭐ Copy a fake secret in, delete it in the next instruction, then **extract it from the
   intermediate layer's tar** to prove it is still there.
5. ⭐ Pass a token as `ARG` and **find it in `docker history --no-trunc`.**
6. ⭐ Rebuild using a **BuildKit secret mount** and confirm it appears in neither history nor any
   layer.
7. ⭐ Download-extract-delete across three `RUN`s and measure the image. **Combine into one and
   measure again.**
8. ⭐ Deploy by tag, **repoint the tag to a different build**, and demonstrate that the "same version"
   now runs different code. Switch to digest pinning.
9. Add OCI labels with the git SHA and **trace a running container back to its commit** in one
   command.

## 🎙️ Articulation drill

**Two minutes:** *"Our Docker builds take twelve minutes. Make them fast."*

**⭐ The answer is one diagnosis and three moves.** The diagnosis: **the cache is being invalidated
early**, almost certainly by copying source before resolving dependencies. Then: **reorder from
least-changing to most-changing, add a `.dockerignore` so the context does not bust `COPY`, and use a
BuildKit cache mount for the dependency directory so it persists without living in a layer.**

**⭐ The marker is that you talk about *ordering* before you talk about tooling** — a faster runner or
a bigger machine treats the symptom, while instruction order is the cause.
