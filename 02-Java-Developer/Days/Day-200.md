# Day 200

**L-200** · Partitioning — splitting a table without splitting the application

**Time:** 3 hrs · **Mode:** NEW

> Day 194 ended on a claim: **the right way to delete a year of old events is to drop a partition**,
> because a bulk delete of 200 million rows leaves 200 million dead tuples and a table that will not
> shrink.
>
> That is the strongest argument for partitioning and it is not the one people give. Today: how
> declarative partitioning works, the constraint that governs the whole design, and the honest
> assessment of when it is worth the complexity — because **partitioning a table that does not need
> it makes everything slower.**

---

# Part 1 — ⭐ The four real benefits, ranked

| # | Benefit | Note |
|---|---|---|
| ⭐ 1 | **Instant bulk deletion** | ⭐ `drop table events_2025_01` — no dead tuples, disk freed immediately |
| ⭐ 2 | **Partition pruning** | ⭐ the planner skips partitions that cannot match |
| 3 | **Smaller indexes** | each partition's index fits in memory (Day 189) |
| 4 | **Parallel maintenance** | vacuum and reindex per partition, not on a 2 TB monolith |

**⭐ Benefit 1 is usually the real reason**, and it is a data-lifecycle decision rather than a
performance one. A time-series table with a retention policy — events, logs, metrics, audit records —
gets partitioned so that expiry is a metadata operation.

**⭐ Benefit 2 is what people expect and it is conditional**, in a way covered in Part 3.

**⭐ What partitioning does NOT do:** it does not make a well-indexed lookup faster. An index on a
100-million-row table is about 4 levels deep; on 10 partitions of 10 million it is 3 levels. **You
saved one page read**, and paid planning overhead for it. **Partitioning is not an index
substitute.**

# Part 2 — Declarative partitioning

```sql
create table events (
    id          bigint generated always as identity,
    tenant_id   bigint not null,
    event_type  text not null,
    payload     jsonb,
    created_at  timestamptz not null,
    ⭐ primary key (id, created_at)      -- ⭐⭐ the partition key MUST be in every unique constraint
) partition by range (created_at);

create table events_2026_08 partition of events
    for values from ('2026-08-01') to ('2026-09-01');
create table events_2026_09 partition of events
    for values from ('2026-09-01') to ('2026-10-01');

create table events_default partition of events default;   -- ⭐ catches strays — see Part 4
```

**⭐ The constraint that governs the entire design:**

> **⭐ Every unique constraint and primary key must include the partition key.**

**PostgreSQL cannot enforce uniqueness across partitions**, because each partition has its own index
and there is no global one. So `primary key (id)` is impossible — it must be `(id, created_at)`.

**⭐ This has real application consequences:**

- **`select * from events where id = ?` scans every partition**, because `id` alone does not tell
  PostgreSQL which one holds it. Queries must carry the partition key.
- ⭐ **A foreign key *to* a partitioned table requires the full composite key**, which usually means
  child tables must also carry `created_at`.
- **Day 158's `@Id` becomes a composite `@IdClass` or `@EmbeddedId`** in JPA, which is more awkward
  than a single id.

**⭐ Design the partition key from the query pattern first**, because this constraint propagates
through the schema and the application. Getting it wrong is expensive to reverse.

## The three strategies

```sql
partition by range (created_at)                  -- ⭐ time series. The dominant case
partition by list (region)                       -- ⭐ discrete values: region, tenant tier
partition by hash (tenant_id)                    -- ⭐ even distribution when there is no natural range
```

```sql
-- ⭐ Sub-partitioning — use sparingly
create table events_2026_08 partition of events
    for values from ('2026-08-01') to ('2026-09-01')
    partition by hash (tenant_id);
```

**⭐ Hash partitioning by tenant is the interesting multi-tenant case** (Day 176): it distributes load
evenly and keeps a large tenant's data physically clustered. **But it prevents dropping data by
time**, which was benefit 1 — so range-by-time with hash sub-partitions is the combination, and it
multiplies the partition count.

# Part 3 — ⭐ Pruning, which is the benefit people assume they get

```sql
explain select count(*) from events where created_at >= '2026-08-01' and created_at < '2026-09-01';
-- ⭐ Seq Scan on events_2026_08   ← ONE partition. The others are not touched.
```

```sql
explain select count(*) from events where event_type = 'LOGIN';
-- ⭐⭐ Append → scans EVERY partition. No pruning.
```

> **⭐ Pruning only happens when the query filters on the partition key.** A query without it touches
> every partition, and is **slower** than it would have been on an unpartitioned table.

**⭐ Two things that silently defeat pruning:**

```sql
where created_at >= now() - interval '7 days'          -- ⭐ runtime pruning at execution, not planning
where date(created_at) = '2026-08-14'                  -- ❌ Day 189 — a function on the key
```

**⭐ The first is fine but works differently.** With a parameter or a volatile function the planner
cannot prune, so PostgreSQL prunes at **execution** time instead. In `EXPLAIN` (without `ANALYZE`)
every partition appears; with `ANALYZE` you see `(never executed)` on the skipped ones — **and if you
do not know that, you will conclude pruning is broken.**

```sql
set plan_cache_mode = force_custom_plan;   -- ⭐ for prepared statements over partitioned tables
```

**⭐ A generic plan cannot prune** (the parameter is unknown at planning time), so a JDBC prepared
statement executed six times may switch to a generic plan and lose pruning. This is a real and
confusing production regression, and it interacts with Day 197's PgBouncer prepared-statement
handling.

## ⭐ The costs, stated honestly

| Cost | Detail |
|---|---|
| ⭐ **Planning time** | ⭐ grows with partition count. **Keep it under a few hundred** |
| ⭐ **Queries without the key** | ⭐ **slower than unpartitioned** — every partition scanned |
| No global unique index | Day 187's constraints must include the key |
| ⭐ **Cross-partition joins** | more expensive |
| Operational surface | partitions must be created ahead of time — see Part 4 |
| ⭐ `autovacuum` per partition | more relations to track (Day 194) |

**⭐ Under a few hundred partitions PostgreSQL handles pruning efficiently; several thousand and
planning overhead becomes visible on every query.** Monthly partitions for ten years is 120 — fine.
Hourly partitions for a year is 8,760 — a problem.

# Part 4 — ⭐ Operating it

## ⭐ Automatic partition creation — the thing that will page you

> **⭐ If tomorrow's partition does not exist, every insert fails.**

```sql
create table events_default partition of events default;    -- ⭐ the safety net
```

**⭐ A default partition prevents the outage** — strays land there instead of erroring. But it has a
sharp edge: **attaching a new partition requires scanning the default partition** to prove no rows
belong in the new range, which takes a lock. **Treat the default as an alarm, not a destination** —
monitor it and expect it to be empty.

```sql
-- ⭐ pg_partman automates creation and retention
select partman.create_parent(
    p_parent_table := 'public.events',
    p_control      := 'created_at',
    p_interval     := '1 month',
    p_premake      := 4);                            -- ⭐ always 4 months ahead
update partman.part_config set retention = '12 months', retention_keep_table = false
where parent_table = 'public.events';                -- ⭐ automatic drops
```

**⭐ Use `pg_partman` or a scheduled job (Day 178), and alert if the newest partition is less than
two intervals ahead.** Hand-managed partitions are fine until the person who remembers goes on
holiday.

## ⭐ Converting an existing table — expand/contract again

```sql
-- 1. New partitioned table alongside
create table events_new (...) partition by range (created_at);
-- 2. Create partitions covering all existing data
-- 3. ⭐ Application writes to BOTH (or a trigger mirrors writes)
-- 4. ⭐ Backfill in batches (Day 166) — never one statement
-- 5. Verify counts match
-- 6. ⭐ Swap in one transaction:
begin;
  alter table events rename to events_old;
  alter table events_new rename to events;
commit;
-- 7. Wait. Then drop events_old.
```

**⭐ This is Day 166's expand/contract, a third instance** — after the column rename and Day 175's
token migration. **The shape keeps recurring: add the new, write both, migrate, wait, remove the
old.** Noticing that is worth more than any individual procedure.

⚠️ **PostgreSQL cannot convert a table to partitioned in place.** `ATTACH PARTITION` can adopt an
existing table as one partition, which helps, but the parent must be created partitioned.

## ⭐ Indexes and constraints on partitions

```sql
create index on events (tenant_id, created_at desc);   -- ⭐ cascades to every partition, incl. future
```

**Creating an index on the parent creates it on every partition automatically**, including ones
created later. ⚠️ **But `CREATE INDEX CONCURRENTLY` is not supported on a partitioned parent** — you
must build it concurrently on each partition and then attach it, which is a real operational wrinkle
on a live system.

## ⭐ Partitioning versus the alternatives

| Problem | Partitioning? |
|---|---|
| ⭐ Time-series data with retention | ⭐ ✅ **yes — the strongest case** |
| Table too large to vacuum in a window | ✅ yes |
| Queries slow on 500M rows, all filtered by date | ✅ yes |
| ⭐ Queries slow, filtered by user id | ⭐ ❌ **index it** (Day 190) |
| Table is 50M rows and "feels big" | ⭐ ❌ index it. 50M is not large |
| Multi-tenant isolation | ⭐ ⚠️ RLS (Day 176) is the security control; hash partitioning is a distribution choice |
| Need to scale writes beyond one machine | ⭐ ❌ that is **sharding**, not partitioning |

**⭐ The last row matters.** Partitioning splits a table within one database; sharding splits data
across machines. Partitioning does nothing for a write throughput ceiling — Day 213 discusses that
properly.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Partitioning a table that just needs an index | slower planning, no benefit |
| ⭐ Queries that omit the partition key | every partition scanned — worse than not partitioning |
| ⭐ Thousands of partitions | planning overhead on every query |
| Forgetting the key in the primary key | ⭐ it is not optional; PostgreSQL rejects it |
| ⭐ No future partitions created | ⭐ **inserts fail at midnight** |
| No default partition | same, with no safety net |
| Letting rows accumulate in the default | attaching new partitions requires scanning it |
| ⭐ Prepared statements losing pruning | generic plans cannot prune; `force_custom_plan` |
| Misreading `EXPLAIN` without `ANALYZE` | runtime pruning shows every partition |
| Expecting `CREATE INDEX CONCURRENTLY` on the parent | unsupported; per-partition then attach |
| Converting in place | not possible; expand/contract |
| ⭐ Expecting partitioning to scale writes | that is sharding |

## Interview questions

**Q: When do you partition a table?**
Primarily when there is a retention policy — a time-series table where deleting old data as a bulk
`DELETE` would leave hundreds of millions of dead tuples and a table that will not shrink. Dropping a
partition is instant and frees the disk immediately. Secondary benefits are pruning and smaller
per-partition indexes, but I do not partition to make an indexed lookup faster — that saves one page
read and costs planning time.

**Q: What is the constraint that shapes the whole design?**
Every unique constraint and primary key must include the partition key, because PostgreSQL cannot
enforce uniqueness across partitions. That propagates: lookups by id alone scan every partition,
foreign keys to the table need the composite key, and JPA needs a composite id. So the partition key
comes from the query pattern, decided first.

**Q: Why might a query on a partitioned table be slower?**
If it does not filter on the partition key there is no pruning, so it scans every partition and pays
planning overhead across all of them. Partitioning helps queries aligned with the key and hurts every
other one.

**Q: Your inserts started failing at midnight. What happened?**
Tomorrow's partition did not exist. A default partition catches strays as a safety net, and the real
fix is automated creation — `pg_partman` or a scheduled job creating several intervals ahead, with an
alert when the newest partition is less than two intervals out.

**Q: How do you partition an existing large table?**
Expand and contract, because you cannot convert in place. Create the partitioned table alongside,
write to both, backfill in batches, verify counts, swap names in one transaction, and drop the old
one after a wait. It is the same shape as a zero-downtime column rename.

## 🎙️ Articulation drill

Two minutes: **"When would you partition a table?"**

Lead with the retention argument, not the performance one — dropping a partition is instant and
creates no dead tuples, where deleting 200 million rows leaves 200 million of them and a table that
never shrinks. Then be honest about the cost: pruning only helps queries that filter on the partition
key, so every other query gets slower, and the key has to be in every unique constraint, which
propagates into foreign keys and your JPA mapping. Close with the two things it is not: not a
substitute for an index, and not sharding — it does nothing for a write ceiling on one machine.
