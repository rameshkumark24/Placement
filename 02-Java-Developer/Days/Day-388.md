# Day 388

**L-388** · ElastiCache — Redis on AWS, cluster mode, and the eviction policy that isn't

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ The default `maxmemory-policy` on ElastiCache Redis is `noeviction`. Which means when your cache
> fills up, it stops accepting writes and returns errors — a cache that fails closed.**
>
> Today: cluster mode and what it does to your Java client, the failover that is a DNS change *again*,
> **the cold-cache thundering herd that follows every failover**, and when a cache is quietly a database
> you forgot to back up.

---

# Part 1 — ⭐ The two engines, and why it is Redis

| | ⭐ Redis (Valkey) | Memcached |
|---|---|---|
| Data types | ⭐⭐ **strings, hashes, lists, sets, sorted sets, streams** | strings only |
| ⭐ Persistence | ⭐ optional (RDB/AOF) | none |
| ⭐ Replication / failover | ⭐⭐ **yes** | ⭐⭐ **no — a node loss is data loss** |
| ⭐ Atomic ops, Lua, transactions | ⭐⭐ yes — **the distributed lock and rate limiter live here** (Day 310) | no |
| Multi-threaded | ⭐ mostly single-threaded per shard | yes |

> **⭐ Choose Redis unless you have a specific reason not to.** Memcached's only real advantage is
> multi-threaded simple caching on a big box. **Everything Stage 8 and 9 built — the atomic conditional
> claim, the token bucket, the leaderboard, the lease with an expiry — needs Redis data structures.**

# Part 2 — ⭐⭐ Cluster mode, and what it does to your client

| | ⭐ Cluster mode **disabled** | ⭐⭐ Cluster mode **enabled** |
|---|---|---|
| Shape | ⭐ **one shard**: 1 primary + up to 5 replicas | ⭐⭐ **up to 500 shards**, each with replicas |
| ⭐ Scales | ⭐ reads only (vertically for writes) | ⭐⭐ **reads and writes, and memory** |
| ⭐⭐ **Your client** | ⭐ ordinary Redis client | ⭐⭐ **must be cluster-aware** |
| ⭐⭐ **Multi-key operations** | ⭐ work | ⭐⭐ **CROSSSLOT error unless keys hash to the same slot** |
| Endpoint | primary + reader endpoint | configuration endpoint |

```
⭐⭐ THE MIGRATION THAT BREAKS IN PRODUCTION:
⭐   MGET user:1 user:2 user:3      ⭐ fine on a single shard
⭐   ⇒ cluster mode enabled ⇒ ⭐⭐ "CROSSSLOT Keys in request don't hash to the same slot"
⭐   ⇒ ⭐ and so do MULTI/EXEC transactions and Lua scripts touching several keys.

⭐⭐ THE FIX — HASH TAGS: only the part in {braces} is hashed.
⭐   user:{42}:profile   user:{42}:settings   ⇒ ⭐⭐ same slot, multi-key ops work
⭐   ⇒ ⭐ Design your key names for this BEFORE you need cluster mode.
```

⚠️ **This is Day 326's consistent hashing showing through the abstraction.** Redis Cluster uses **16,384
hash slots** distributed across shards; resharding moves slots, not keys. **The reason multi-key
operations fail is that the two keys may live on different servers — which is not a Redis limitation, it
is arithmetic.**

| ⭐ Java clients | |
|---|---|
| ⭐⭐ **Lettuce** | ⭐⭐ Spring Boot's default; netty-based, **handles cluster topology refresh** — enable `adaptiveRefreshTriggers` |
| ⭐ Jedis | ⭐ blocking, needs a pool; simpler mental model |
| ⭐ Redisson | ⭐ higher-level (locks, maps); heavier |

> **⭐ With Lettuce, enable periodic *and* adaptive topology refresh.** Without it, the client keeps a
> stale view of the cluster after a failover and **sends commands to a node that is no longer the
> primary** — producing `MOVED` storms or errors long after AWS considers the failover complete.

# Part 3 — ⭐⭐ Eviction: the default that fails closed

```
⭐⭐ maxmemory-policy DEFAULT on ElastiCache = ⭐⭐ noeviction (volatile-lru on some older families)

⭐⭐ noeviction:   memory full ⇒ ⭐⭐ WRITES RETURN AN ERROR. ⭐ Your "cache" is now an outage.
⭐⭐ volatile-lru: evicts only keys WITH A TTL ⇒ ⭐⭐ if you forgot a TTL, it is UNEVICTABLE
⭐⭐ allkeys-lru:  ⭐⭐ evicts anything, least-recently-used ⇒ ⭐⭐ WHAT PEOPLE ACTUALLY MEANT
⭐   allkeys-lfu:  least-FREQUENTLY-used — better when a small hot set dominates
```

| ⭐ Set it deliberately | |
|---|---|
| ⭐⭐ **Pure cache** | ⭐⭐ `allkeys-lru` (or `allkeys-lfu`) — **it should always accept writes** |
| ⭐ Mixed cache + session store | ⭐ `volatile-lru`, **and every cache key must have a TTL** |
| ⭐⭐ Data you cannot lose | ⭐⭐ **this is not a cache. Use a database.** |

> **⭐⭐ "Redis started returning errors under load" is `noeviction` almost every time.** It is a
> parameter-group change and it is the first thing to check on any ElastiCache cluster you inherit.

⚠️ **`volatile-lru` with a forgotten TTL is worse than it sounds:** keys without a TTL cannot be evicted
at all, so as they accumulate the *evictable* portion shrinks until eviction cannot free enough — and
you get errors while the eviction metric says the policy is working. **Alarm on `Evictions`,
`DatabaseMemoryUsagePercentage` and `CacheMisses` together.**

# Part 4 — ⭐⭐ Failover, and the herd that follows

```
⭐ ElastiCache failover: a replica is promoted, and ⭐⭐ the PRIMARY ENDPOINT DNS is repointed.
⭐ ⇒ ⭐⭐ SAME JVM DNS CACHING TRAP AS DAY 387. Set networkaddress.cache.ttl.
⭐ ⇒ ⭐ Plus: enable Multi-AZ with automatic failover, or nothing is promoted at all.
```

```
⭐⭐ THEN THE SECOND PROBLEM, WHICH IS BIGGER:
⭐   Failover (or a restart, or a scale-out) ⇒ ⭐⭐ some or all of the cache is COLD.
⭐   ⇒ ⭐⭐ Every request that used to hit the cache now hits the DATABASE, simultaneously.
⭐   ⇒ ⭐⭐ The database, sized for 10% of traffic, receives 100% of it. ⭐⭐ It falls over.
⭐   ⇒ ⭐⭐ THE CACHE FAILOVER TOOK DOWN THE DATABASE.
```

| ⭐ Defence | ⭐ (Day 326, Day 340) |
|---|---|
| ⭐⭐ **Request coalescing / single-flight** | ⭐⭐ one loader per key; everyone else waits |
| ⭐⭐ **A bulkhead on database calls** | ⭐⭐ **a bounded pool means the DB is protected, not overwhelmed** |
| ⭐ Jittered TTLs | ⭐ so keys do not all expire in the same second |
| ⭐ Serve stale on error | ⭐ better than a stampede |
| ⭐ Load shedding | ⭐ shed before you fall over (Day 340) |

> **⭐ The insight worth carrying: a cache does not just improve latency — it hides your database's real
> capacity from you.** Every cache is an implicit promise that your database never has to serve the full
> load, **and you should know what happens the day it does.**

# Part 5 — ⭐ Operating it

| Concern | ⭐ Note |
|---|---|
| ⭐⭐ **In a VPC, in isolated subnets** | ⭐ SG referencing the app's SG (Day 384) |
| ⭐ **Encryption in transit + at rest**, AUTH/RBAC | ⭐⭐ Redis with no auth on an open SG has been mass-exploited for years |
| ⭐ Node sizing | ⭐ `r`-family; **memory is the constraint**, and leave ~25% headroom |
| ⭐⭐ **`reserved-memory-percent`** | ⭐⭐ without it, a background save can OOM the node |
| ⭐ Persistence (AOF/RDB) | ⭐⭐ usually the **wrong instinct** in a cache — costs performance, and if you need it you need a database |
| ⭐ **ElastiCache Serverless** | ⭐ pay per GB-hour and request; good for spiky and unknown workloads |
| ⭐ Metrics to alarm on | ⭐⭐ `Evictions`, `CacheMisses` ratio, `DatabaseMemoryUsagePercentage`, `CurrConnections`, **`EngineCPUUtilization`** |

⚠️ **Alarm on `EngineCPUUtilization`, not `CPUUtilization`.** Redis is effectively single-threaded per
shard, so a 4-core node showing 25% CPU may have its **engine thread saturated** — the node looks idle
and is completely maxed out. **This is a genuinely non-obvious metric distinction and it makes a good
interview line.**

| ⭐ And the classic latency killer | |
|---|---|
| ⭐⭐ **`KEYS *` in production** | ⭐⭐ O(N), blocks the single engine thread, **stalls every other client** — use `SCAN` |
| ⭐ Large values / big hashes | ⭐ one 50 MB value blocks everything while it serialises |
| Lua scripts that loop | same problem, self-inflicted |

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Leaving `maxmemory-policy` at `noeviction`** | ⭐⭐ a full cache returns write errors — an outage |
| ⭐ `volatile-lru` with keys that have no TTL | ⭐⭐ unevictable keys shrink the evictable set until it fails |
| ⭐⭐ **Enabling cluster mode without hash tags** | ⭐⭐ CROSSSLOT errors on MGET, MULTI and Lua |
| ⭐ Lettuce without topology refresh | ⭐ stale cluster view after failover |
| ⭐⭐ **JVM DNS caching** | ⭐⭐ same trap as RDS — the failover completes, you do not |
| ⭐ No Multi-AZ automatic failover | nothing gets promoted |
| ⭐⭐ **No stampede protection** | ⭐⭐ a cache failover takes down the database |
| ⭐ Uniform TTLs | synchronised expiry is a self-inflicted herd |
| ⭐ Alarming on `CPUUtilization` | ⭐⭐ `EngineCPUUtilization` is the real one |
| ⭐⭐ **`KEYS *` in production** | ⭐⭐ blocks the engine thread for everyone |
| ⭐ No `reserved-memory-percent` | a background save OOMs the node |
| ⭐ Treating a cache as durable | ⭐⭐ if you cannot lose it, it is a database |
| Redis reachable with no auth | mass-scanned, mass-exploited |

## Interview questions

**Q: What is the default eviction policy on ElastiCache and why does it matter?**
`noeviction` on most configurations, which means when memory fills the cache stops accepting writes and
returns errors. A cache that fails closed is an outage, and "Redis started erroring under load" is this
almost every time. For a pure cache the correct policy is `allkeys-lru` or `allkeys-lfu`, because a cache
should always accept a write and discard something old. `volatile-lru` only evicts keys with a TTL,
which sounds safer and is worse — keys without a TTL become unevictable, so the evictable portion
shrinks over time until eviction cannot free enough memory.

**Q: What breaks when you enable cluster mode?**
Multi-key operations. Keys are distributed across sixteen thousand three hundred and eighty-four hash
slots, and any command touching several keys requires them to be in the same slot, so MGET, MULTI/EXEC
and Lua scripts spanning keys start returning CROSSSLOT errors. The fix is hash tags — putting the shared
part of the key in braces so only that part is hashed — but that is a key naming decision you have to
make before you need cluster mode, not during the migration. The client also has to be cluster-aware and
refresh topology, or it keeps a stale view after failover.

**Q: A cache node failed over and the database fell over. Explain.**
The cache went cold. Every request that used to be served from memory went to the database
simultaneously, and the database was sized on the assumption that the cache absorbs ninety percent of
reads. The cache was hiding the database's real capacity, and the failover revealed it. The defences are
request coalescing so only one loader per key hits the database, a bounded connection pool acting as a
bulkhead so the database is protected rather than overwhelmed, jittered TTLs so keys do not expire
together, and serving stale data on error. The design question worth asking of any cached system is what
happens the day the cache is empty.

**Q: Which CPU metric do you alarm on for Redis?**
`EngineCPUUtilization`, not `CPUUtilization`. Redis processes commands on a single thread per shard, so
on a four-core node the overall CPU metric can read twenty-five percent while the engine thread is
completely saturated — the node looks idle and is maxed out. The related failure is any O(N) command on
that thread: `KEYS *` in production blocks every other client for the duration, which is why `SCAN`
exists.

**Q: Should you enable persistence on ElastiCache?**
Usually not. Persistence costs performance and adds a background save that can push a node into
out-of-memory territory if you have not reserved memory for it. More importantly, the instinct behind
the question is normally the real problem: if the data cannot be lost, it is not cache data and it
belongs in a database. Snapshots have a legitimate use for faster warm-up after a planned restart, but
that is a startup optimisation rather than a durability guarantee.

    each fires.

## 🎙️ Articulation drill

**Two minutes:** *"What happens when your cache goes away?"*

**⭐ This is the question that separates people who added a cache from people who operate one.** The
honest answer starts by admitting the exposure: **the database is sized on the assumption the cache
absorbs most reads, so an empty cache sends it a load it has never handled.**

**⭐ Then the defences, concretely: single-flight coalescing so one loader per key touches the database,
a bounded pool that acts as a bulkhead so the database is protected rather than flattened, jittered TTLs
so keys do not expire in the same second, and stale-on-error. And we know it works because we flushed
the cache under load in staging on purpose and watched p99 rather than assuming.**
