# Part 1 — ⭐ Why IaC, and the plan/apply cycle

| ⭐ Benefit | ⭐ Detail |
|---|---|
| ⭐⭐ **Reviewable** | ⭐⭐ **a firewall change is a diff a colleague reads before it exists** |
| ⭐ **Reproducible** | ⭐ a second environment is a variable file, not a fortnight |
| ⭐ **Drift is detectable** | ⭐ someone clicked in the console — **`plan` tells you** |
| ⭐ **Disaster recovery** | ⭐⭐ the infrastructure is rebuildable from source |
| Documentation | the code is what exists, not what someone remembers |

```
⭐ terraform plan    ⭐⭐ compute the diff between desired (code) and actual (state) — ⭐ CHANGES NOTHING
⭐ terraform apply   ⭐ execute that diff
⭐ ⇒ ⭐⭐ plan on every PR, ⭐ apply on merge. ⭐ The plan output IS the review artefact.
```

> **⭐ Posting `terraform plan` output into the pull request is the practice that makes IaC work.**
> A reviewer approves a specific set of changes — *"1 to add, 0 to change, 0 to destroy"* — rather
> than approving code and hoping. **`destroy` counts in a plan are what people actually read.**

⚠️ **Terraform is declarative and Kubernetes-like: it reconciles.** Which means **something changed
outside the code is a diff Terraform wants to revert** — so console changes are not just untracked,
**they get silently undone by the next apply.**

# Part 2 — ⭐⭐ State: the whole game

```
⭐ ⭐⭐ STATE maps your resource names to real cloud resource IDs.
⭐   aws_db_instance.main  →  db-prod-8a3f2
⭐
⭐ ⭐⭐ LOSE IT and Terraform believes nothing exists ⇒ ⭐⭐ the next apply CREATES A SECOND EVERYTHING.
```

| ⭐ Requirement | ⭐ Why |
|---|---|
| ⭐⭐ **Remote state** (S3, GCS, Terraform Cloud) | ⭐⭐ never on a laptop; **never in git** |
| ⭐⭐ **Locking** (DynamoDB, native) | ⭐⭐ **two concurrent applies corrupt state** |
| ⭐ **Versioning on the bucket** | ⭐ state corruption is recoverable |
| ⭐⭐ **Encryption at rest** | ⭐⭐ **state contains SECRETS in plaintext — database passwords, generated keys** |
| ⭐ Restricted access | ⭐ read access to state is read access to credentials |

⚠️ **The secrets-in-state fact surprises people and it is not fixable by being careful.** A resource
with a password attribute stores that password in state, **even if you passed it from a secret
manager.** **Treat the state file with the same protection as production credentials**, and prefer
resources that generate credentials the provider never returns.

## ⭐⭐ Blast radius: split the state

```
⭐ ✗ ONE state file for everything
⭐   ⇒ ⭐ every plan touches the whole estate ⇒ slow, and ⭐⭐ one mistake can destroy production
⭐
⭐ ✓ SPLIT BY LIFECYCLE and ENVIRONMENT:
⭐   network/     ⭐ changes yearly       ⭐ rarely applied
⭐   data/        ⭐ changes rarely       ⭐⭐ databases — protect it hardest
⭐   platform/    changes monthly
⭐   app/         ⭐ changes weekly       ⭐ applied constantly
⭐   × dev / staging / prod
```

| ⭐ Benefit | |
|---|---|
| ⭐⭐ **A mistake in `app/` cannot delete a database** | ⭐⭐ **the single best reason** |
| ⭐ Faster plans | ⭐ a small state plans in seconds |
| ⭐ Different approval rules | ⭐ `data/` needs two reviewers; `app/` needs one |
| ⭐ **Blast radius is bounded** | ⭐ this is Day 340's argument applied to infrastructure |

**⭐ Also: `prevent_destroy` on anything holding data**, and read every plan for its destroy count.

```hcl
⭐ lifecycle { prevent_destroy = true }     ⭐ on databases, buckets, anything stateful
```

# Part 3 — ⭐ Modules, and what Terraform is bad at

```hcl
⭐ module "service" {
⭐   source = "../../modules/service"
⭐   name   = "orders"
⭐   cpu    = 512
⭐   env    = var.environment
⭐ }
```

| ⭐ Practice | |
|---|---|
| ⭐ Modules for repeated shapes | one definition, many services |
| ⭐ **Version your modules** | ⭐ a module change should not surprise every consumer |
| ⭐ **Do not over-abstract** | ⭐⭐ a module with forty variables is worse than duplicated HCL |
| ⭐ Outputs for wiring | one layer's output is the next layer's input |
| ⭐ **`terraform fmt` and `validate` in CI** | plus `tflint` and a security scanner (`tfsec`/Checkov) |

## ⭐ What Terraform should not do

| ⭐ Not Terraform's job | ⭐ Use instead |
|---|---|
| ⭐⭐ **Application deployment** | ⭐⭐ **your pipeline** (Day 370) — apps deploy many times a day, infrastructure does not |
| ⭐ Anything imperative | a script |
| ⭐ **Secret values** | ⭐ a secret manager; Terraform creates the *slot*, not the value |
| Configuration management inside VMs | Ansible, or an image build |
| ⭐ Fast feedback loops | ⭐ `apply` is minutes; a deploy should be seconds |

> **⭐ The clean boundary: Terraform creates the things that hold your application; the pipeline puts
> the application in them.** Mixing them means every code deploy runs a plan against your entire
> infrastructure, **which is both slow and terrifying.**

## ⭐ Importing and drift

| ⭐ Situation | ⭐ Answer |
|---|---|
| ⭐ Resources created by hand | ⭐ `import` them, then let the plan converge — **expect a messy first diff** |
| ⭐ **Drift** | ⭐⭐ run `plan` on a schedule and **alert on any non-empty result** |
| Emergency console change | ⭐ acceptable — **then codify it the same day, or the next apply reverts it** |

# Part 4 — 🚪 ⭐⭐ STAGE 10 EXIT GATE — "ships own work"

## ⭐ The claim

> **⭐ You can take a change from your editor to production, observe it working, and undo it — without
> anyone else's help and without a manual step.**

## ⭐ The gate: fifteen items, each with evidence

```
⭐ CONTAINER
⭐  1. ⭐ Image < 300 MB, multi-stage, layered jar        ⭐ evidence: the before/after table (Day 366)
⭐  2. ⭐ Runs non-root, read-only rootfs, caps dropped
⭐  3. ⭐⭐ Survives its memory limit under load           ⭐⭐ evidence: 10 min at -m 512m, no exit 137
⭐  4. ⭐⭐ SIGTERM completes in-flight requests           ⭐⭐ evidence: a timed test with a live request
⭐  5. ⭐ No secret in any image layer                    ⭐ evidence: docker history + a layer extract

⭐ PIPELINE
⭐  6. ⭐⭐ PR feedback < 10 min (p95)                     ⭐ evidence: the measurement
⭐  7. ⭐⭐ ONE artefact, promoted by digest               ⭐⭐ evidence: digests compared across envs
⭐  8. ⭐ Migrations as a separate job, expand/contract
⭐  9. ⭐ Scanning in CI + a scheduled rescan
⭐ 10. ⭐⭐ A ROLLBACK, PRACTISED AND TIMED               ⭐⭐ evidence: the number, in the runbook

⭐ OPERATIONS
⭐ 11. ⭐ Deployed, reachable, with TLS
⭐ 12. ⭐⭐ RED + saturation + a BUSINESS metric          ⭐ evidence: the dashboard
⭐ 13. ⭐⭐ SLO-based burn-rate alerting, and ⭐⭐ EVERY ALERT HAS FIRED ONCE
⭐ 14. ⭐ Structured logs with trace_id; ⭐ a trace end to end across services
⭐ 15. ⭐⭐ A DEPLOY UNDER LOAD WITH ZERO DROPPED REQUESTS ⭐⭐ evidence: the load-test output
```

**⭐ Items 4, 7, 10, 13 and 15 are mandatory.** Each corresponds to a failure that is invisible until
it is not: **silent request loss on deploy, testing a different artefact than you shipped, an untested
rollback, alerts that do not work, and 502s nobody can reproduce.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **State in git** | ⭐⭐ secrets in plaintext, in history, forever |
| ⭐⭐ **No state locking** | ⭐⭐ two applies corrupt it |
| ⭐ No versioning on the state bucket | corruption is unrecoverable |
| ⭐⭐ **One state file for everything** | ⭐⭐ one mistake reaches production data |
| ⭐ No `prevent_destroy` on stateful resources | ⭐ a plan nobody read deletes a database |
| ⭐ Not reading the destroy count | the number that matters most in a plan |
| ⭐ **Deploying applications with Terraform** | slow, and every deploy plans your whole estate |
| ⭐ Secret values in variables | they land in state anyway |
| ⭐ Modules with forty variables | ⭐ worse than duplication |
| ⭐ **Console changes left uncodified** | the next apply reverts them |
| ⭐ No scheduled drift detection | you find out during an incident |
| ⭐⭐ **Claiming the gate without evidence** | ⭐ Day 287's standard — a claim is not a demonstration |

## Interview questions

**Q: What does infrastructure as code actually buy you?**
Review, primarily. A firewall or IAM change becomes a diff a colleague reads before it exists, rather
than something someone did in a console at 6pm. After that: reproducibility, so a second environment
is a variable file; drift detection, because a scheduled plan tells you someone clicked something;
and genuine disaster recovery, because the infrastructure is rebuildable from source.

**Q: Why is state so important?**
Because it maps your resource names to real cloud resource IDs, and losing it means Terraform believes
nothing exists — the next apply creates a duplicate of everything. So it lives remotely, versioned,
encrypted, with locking so two concurrent applies cannot corrupt it. And it contains secrets in
plaintext regardless of how carefully you passed them in, so read access to state is read access to
credentials.

**Q: How do you limit blast radius?**
Split state by lifecycle and environment — network, data, platform, application, each per environment.
A mistake in the application layer then cannot destroy a database, plans are fast because each state
is small, and different layers can carry different approval rules. Plus `prevent_destroy` on anything
stateful, and reading the destroy count on every plan, which is the number that actually matters.

**Q: Should Terraform deploy your application?**
No. Applications deploy many times a day and infrastructure changes rarely, so mixing them means every
code deploy runs a plan against your whole estate — slow and frightening. Terraform creates the things
that hold the application; the pipeline puts the application in them. The same boundary applies to
secrets: Terraform creates the slot, the secret manager holds the value.

**Q: What does "ships own work" mean to you?**
That I can take a change from my editor to production, see it working, and undo it, without another
person and without a manual step. Concretely: PR feedback under ten minutes, one artefact promoted by
digest, migrations as a separate expand-contract job, a deploy under load with zero dropped requests,
a rollback I have actually performed and timed, and alerting where every alert has fired at least
once so I know it works. Each of those is a number I can give you rather than a claim.
