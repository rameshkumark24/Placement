# Day 328

**L-328** · Replication — three topologies, three anomalies, and the failover that loses writes

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Replication is how you get read scale and availability. It is also how you get a user who
> writes a comment, refreshes, and cannot see it.**
>
> Day 201 covered PostgreSQL's mechanics. Today is the general theory: **the three topologies, the
> three lag anomalies with their fixes, and what actually happens to your writes during a failover.**

---

# Part 1 — ⭐ Why replicate, and the one thing it is not

| Reason | ⭐ Note |
|---|---|
| ⭐ **Read scaling** | ⭐ the usual driver — reads scale by copies (Day 324) |
| ⭐ **Availability** | ⭐ a replica can be promoted |
| ⭐ **Geographic latency** | ⭐ a local read replica removes 150 ms (Day 322) |
| Offline analytics | keep expensive queries off the primary |
| ⭐⭐ **NOT a backup** | ⭐⭐ **`DELETE FROM users` replicates in milliseconds** (Day 201) |

> **⭐ Say the backup line unprompted.** Replication protects against *machine* failure. It offers no
> protection whatsoever against *human* or *application* failure, because it faithfully copies the
> mistake. **Point-in-time recovery is the defence, and it is a different mechanism.**

# Part 2 — ⭐⭐ The three topologies

## ⭐ Single leader — the default

```
⭐ writes ──► LEADER ──async──► follower  (reads)
                     ──async──► follower  (reads)
```

| ⭐ Property | |
|---|---|
| ⭐ **No write conflicts, ever** | ⭐ **one ordering authority — this is the whole appeal** |
| Reads scale | add followers |
| ⭐ Writes do not scale | ⭐ one leader is the ceiling → Day 329 |
| ⭐ **Followers lag** | ⭐ **the anomalies in Part 3** |
| Failover is a real event | see Part 4 |

**⭐ Synchronous vs asynchronous — the durability dial:**

| Mode | ⭐ On leader failure | ⭐ Cost |
|---|---|---|
| ⭐ **Async** | ⭐⭐ **acknowledged writes can be LOST** | ⭐ fast — the default |
| ⭐ **Sync (all)** | ⭐ nothing lost | ⭐⭐ **one slow follower blocks every write** |
| ⭐⭐ **Semi-sync (≥1 of N)** | ⭐ survives one node's loss | ⭐⭐ **the practical choice** |

> **⭐ Fully synchronous replication to all followers is almost always wrong: it makes availability
> *worse*, because any follower being slow stops writes entirely.** Semi-synchronous — wait for at
> least one — gives durability without coupling your write latency to the slowest node.

## ⭐ Multi-leader — writes accepted in several places

```
⭐ Region A LEADER ⇄ replicate ⇄ Region B LEADER
⭐     ▲                              ▲
⭐   writes                        writes        ⭐ BOTH accept writes
```

| ⭐ Good for | ⭐ The cost |
|---|---|
| ⭐ Multi-region writes with local latency | ⭐⭐ **WRITE CONFLICTS — and they are unavoidable** |
| Offline-capable clients (a phone is a leader) | conflict resolution is now product logic |
| Surviving a region outage for writes | ⭐ **most systems should not do this** |

**⭐ Conflict resolution, honestly:**

| Strategy | ⭐ Verdict |
|---|---|
| ⭐ **Last-write-wins by timestamp** | ⭐⭐ **silently DISCARDS data, and clocks disagree** — see below |
| Highest node id wins | arbitrary, but deterministic |
| ⭐ Keep both, ask the user | ⭐ correct for documents; unusable at volume |
| ⭐⭐ **CRDTs** | ⭐⭐ **conflict-free by construction — counters, sets, collaborative text** |
| ⭐ **Avoid conflicts by routing** | ⭐⭐ **route each user's writes to one home region — the pragmatic answer** |

⚠️ **LWW is the trap.** It looks like a resolution and is actually a policy of losing data, **and it
depends on clocks that are not synchronised** — a node 200 ms fast wins every conflict. Cassandra's
LWW is well known for exactly this.

## ⭐ Leaderless — quorums (Dynamo, Cassandra)

```
⭐ The CLIENT (or a coordinator) writes to N replicas and waits for W acknowledgements.
⭐ Reads query N and wait for R responses.

⭐⭐ W + R > N  ⇒  the read set and write set OVERLAP  ⇒  you see the latest write.
```

| Config | ⭐ Behaviour |
|---|---|
| ⭐ N=3, W=2, R=2 | ⭐ **the standard — survives one node down for both reads and writes** |
| N=3, W=3, R=1 | fast reads, no write availability if any node is down |
| ⭐ N=3, W=1, R=1 | ⭐ **fastest, eventually consistent — W+R ≤ N, so stale reads are expected** |

| ⭐ Mechanism | ⭐ Purpose |
|---|---|
| ⭐ **Read repair** | a read notices a stale replica and fixes it |
| Anti-entropy | background comparison (Merkle trees) |
| ⭐ **Hinted handoff / sloppy quorum** | ⭐ writes accepted by *substitute* nodes during a partition — **available, but W+R>N no longer guarantees freshness** |

⚠️ **The honest caveat: `W + R > N` is weaker than it looks.** With sloppy quorums, concurrent writes,
or a failed write that partially succeeded, **you can still read stale data.** It is a good heuristic,
not linearizability — and saying so is a strong signal.

# Part 3 — ⭐⭐ The three lag anomalies

**⭐ Every one of these is a real, common user-visible bug, and each has a specific name and fix.**

## ⭐ 1. Read-after-write (read your own writes)

```
⭐ User posts a comment → write goes to the leader
⭐ Page refreshes → read hits a lagging follower → ⭐⭐ "your comment is gone"
```

| ⭐ Fix | ⭐ Trade |
|---|---|
| ⭐ **Read from the leader for N seconds after a write** | ⭐ simple, effective — **the usual answer** |
| ⭐ Read from the leader for anything the user can edit | coarse but safe |
| ⭐ **Track the write's log position; wait for a follower to reach it** | ⭐ precise; needs plumbing |
| Timestamp-based routing | clock-dependent — be careful |

## ⭐ 2. Monotonic reads — time appears to go backwards

```
⭐ Read 1 → follower A (up to date):    "3 comments"
⭐ Read 2 → follower B (lagging):        ⭐⭐ "1 comment"
```

| ⭐ Fix | |
|---|---|
| ⭐ **Pin a user to one replica** (hash the user id) | ⭐ **the standard fix** |
| Sticky routing at the session layer | same idea, higher up |

## ⭐ 3. Consistent prefix — causality inverted

```
⭐ Mr Poons: "How far into the future can you see?"
⭐ Mrs Cake: "About ten seconds."
⭐ ⇒ ⭐⭐ A reader on a partitioned/sharded system may see the ANSWER before the QUESTION.
```

| ⭐ Fix | |
|---|---|
| ⭐ Keep causally related writes in one partition | ⭐ the practical answer |
| ⭐ **Causal consistency / explicit dependency tracking** | ⭐ correct, and expensive (Day 331) |

> **⭐ These three are exactly the session guarantees of Day 331**, and being able to name the anomaly
> — *"that's a read-after-write violation"* — rather than describing it is what makes the answer
> sound practised.

# Part 4 — ⭐⭐ Failover, and where the writes go

```
⭐ 1. Detect       — the leader is unreachable   ⭐ or is it just slow? (Day 330)
⭐ 2. Elect        — choose the most up-to-date follower
⭐ 3. Reconfigure  — clients and replicas point at the new leader
⭐ 4. ⭐ Demote     — the old leader must NOT accept writes if it returns
```

| ⭐ Failure | ⭐ Detail |
|---|---|
| ⭐⭐ **Lost writes** | ⭐⭐ **with async replication, anything the old leader acknowledged but did not ship is GONE** |
| ⭐⭐ **Split brain** | ⭐⭐ **the old leader returns and accepts writes — two leaders, diverging data** |
| ⭐ Detection is a guess | ⭐ **too short a timeout → needless failovers; too long → extended downtime** |
| ⭐ Broken external references | ⭐ auto-increment ids reused; a discarded write's id now belongs to different data |
| Cascading load | the new leader gets a cold cache and the full load at once |

**⭐ The defences, and the first is the one to say:**

| ⭐ Defence | |
|---|---|
| ⭐⭐ **Fencing — the old leader is forcibly stopped or refuses to serve** | ⭐⭐ **STONITH, a fencing token, or a lease** (Day 207) |
| ⭐ **Semi-synchronous replication** | ⭐ bounds lost writes to zero for the acknowledged set |
| ⭐ A consensus-backed leader lease | ⭐ **only one leader can hold it — Day 343** |
| Manual failover for critical systems | slower, and far fewer split-brain incidents |

> **⭐ "A failover with asynchronous replication can lose acknowledged writes, and the old leader
> returning is split brain — so the design needs fencing, not just an election" is the sentence that
> shows you have thought past the happy path.** Most candidates describe promoting a replica and
> stop there.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Treating a replica as a backup | ⭐⭐ **a bad `DELETE` replicates instantly** |
| ⭐ Fully synchronous replication to all | ⭐ **one slow follower blocks every write** |
| ⭐ Reading from a replica right after writing | ⭐ **"my comment disappeared"** |
| ⭐ Round-robin reads across followers | ⭐ time appears to move backwards |
| ⭐ **Last-write-wins as conflict resolution** | ⭐⭐ **silent data loss, decided by unsynchronised clocks** |
| Multi-leader without a conflict strategy | divergence discovered in production |
| ⭐ Believing `W + R > N` means strong consistency | ⭐ sloppy quorums and concurrent writes break it |
| ⭐ **Failover with no fencing** | ⭐⭐ **split brain** |
| ⭐ Ignoring writes lost during failover | acknowledged data silently gone |
| Aggressive failure detection | failovers caused by a GC pause |
| Promoting a replica with a cold cache into full load | the new leader immediately falls over |

## Interview questions

**Q: Is a replica a backup?**
No. It protects against machine failure and nothing else — a mistaken delete or a buggy migration
replicates in milliseconds. Backups with point-in-time recovery protect against human and application
error, which is the more common cause of data loss, and the only proof they work is a restore you
have actually timed.

**Q: Synchronous or asynchronous replication?**
Semi-synchronous — wait for at least one follower. Fully asynchronous can lose acknowledged writes
during a failover; fully synchronous to every follower makes availability worse, because any slow
node blocks all writes. Waiting for one gives durability against a single node's loss without
coupling write latency to the slowest replica.

**Q: A user posts a comment and it disappears on refresh.**
Read-after-write violation — the write went to the leader and the refresh read a lagging follower.
The usual fix is to route that user's reads to the leader for a short window after a write, or for
anything they can edit. The precise version records the write's log position and waits for a follower
to catch up, which costs plumbing but avoids sending everything to the leader.

**Q: What is wrong with last-write-wins?**
It is not conflict resolution, it is a policy of discarding data, and it decides which write survives
using clocks that are not synchronised — a node two hundred milliseconds fast wins every conflict.
For counters and sets I would use CRDTs, which are conflict-free by construction. Better still, I
would route each user's writes to a single home region so conflicts do not arise.

**Q: What actually goes wrong during a failover?**
Three things. Writes the old leader acknowledged but had not shipped are lost, permanently, if
replication is asynchronous. The old leader can come back and keep accepting writes, which is split
brain and produces divergent data — so you need fencing, a lease or STONITH, not just an election.
And detection is a guess: too aggressive and a garbage-collection pause triggers a failover, too slow
and you extend the outage.

## Mini task

1. Set up a primary and two replicas. **Measure lag under a heavy write load.**
2. ⭐ **Reproduce read-after-write**: write, immediately read from a replica, and observe the missing
   row. Fix it with leader-reads-after-write and confirm.
3. ⭐ **Reproduce a monotonic-read violation** by alternating reads between two replicas with
   different lag. Fix it by pinning a user to one replica.
4. Kill the primary with async replication under load and **count the acknowledged writes that were
   lost.** Repeat with semi-sync.
5. ⭐⭐ **Create a split brain**: fail over, then bring the old primary back without fencing. **Write
   to both and inspect the divergence.**
6. Implement a **quorum** simulation with N=3 and try W/R combinations. Show where `W + R > N` still
   returns stale data with concurrent writes.
7. ⭐ Implement **last-write-wins** with two nodes whose clocks differ by 200 ms and **demonstrate the
   data loss.**
8. Set the failure detector to two seconds and **induce a GC pause** to trigger a spurious failover.

replicas change my failure story — a failover can lose acknowledged writes with async replication,

it.**
