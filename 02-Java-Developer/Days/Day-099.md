# Day 099

**L-099** · Debugging as a methodology — hypothesis-driven, bisection, reading stack traces

**Time:** 3 hrs · **Mode:** NEW

> who finds a bug in twenty minutes and one who spends two days is almost never tool knowledge. It
> is process. Most people debug by guessing and changing things; that works for easy bugs and fails
> completely on hard ones.

# Part 1 — The scientific method, applied

Debugging is science: you have an anomaly, you form hypotheses, and you run experiments that can
falsify them.

```
1. OBSERVE      What exactly happens? Exact message, exact inputs, exact conditions.
2. REPRODUCE    Make it happen on demand. ← the single highest-value step
3. HYPOTHESISE  What could cause this? List several, order by probability × cheapness to test.
4. PREDICT      "If hypothesis H is true, then X will be true."
5. EXPERIMENT   Test it. ONE variable at a time.
6. CONCLUDE     Confirmed → fix. Refuted → cross it off and take the next one.
7. VERIFY       Fix it, prove the fix, write the regression test.
```

The rule that matters most:

> **Change one thing at a time.** If you change three things and it works, you do not know what fixed
> it — and you may have introduced two new bugs. This feels slow and is the fastest route.

And the discipline that supports it: **write down what you have ruled out.** A hard bug takes hours;
without notes you will re-test the same hypothesis three times. A running list of "checked, not it"
is worth more than any tool.

## Reproduce first

An unreproducible bug cannot be reliably fixed — you can only *believe* you fixed it, and belief is
how "fixed" bugs come back.

Narrow it systematically:

| Question | Narrows to |
|---|---|
| Every request or some? | Data-dependent |
| One environment or all? | Configuration or data |
| One user or all? | Permissions, tenant data, locale |
| Started when? | A deploy, a config change, a data change, a cert expiry |
| Under load only? | Concurrency, pool exhaustion, timeouts |
| After running a while? | A leak, a cache, a `ThreadLocal` (Day 066A) |
| First request only? | Cold start, lazy initialisation, JIT warmup |

Then **minimise**: strip the reproduction to the smallest input and shortest path that still fails.
A 200-line reproduction hides the cause; a five-line one usually *shows* it. Delete-half-and-retest
is the technique — the same bisection as below, applied to input.

## Ordering hypotheses

Do not test in the order they occur to you. Order by **probability × cost to test**:

1. **What changed?** — the highest-probability hypothesis, always. A deploy, a config change, a
   dependency bump, a data migration, an expired certificate. `git log`, the deploy log, the change
   calendar.
2. **The boring explanations** — a typo, a wrong environment variable, a stale cache, a wrong branch,
   the wrong instance, DNS. These feel too dumb to check and are correct a remarkable fraction of the
   time.
3. **Your code** — before the framework's.
4. **The framework or library** — before the JVM's.
5. **The JVM, kernel or hardware** — almost never. If you conclude this, look harder for step 1.

> **"It worked yesterday" means something changed. Find the change.**

# Part 2 — Bisection

The most powerful debugging technique there is, and it works on four different axes.

**In time — `git bisect`** (Day 087). Known-good commit, known-bad commit, `git bisect run ./test.sh`,
nine steps over 500 commits.

**In code — comment out half.** Does it still fail? The bug is in the remaining half. Repeat. Crude,
effective, and it works when nothing else does.

**In data — halve the input.** A 10,000-row import fails; try the first 5,000, then 2,500. You will
find the one malformed row in about 14 steps.

**In configuration — start from a minimal known-good config and add settings back one at a time.**
Faster than removing from a broken one, because the working baseline is certain.

The mathematics is the point: **log₂ of the search space.** A thousand candidates is ten tests. Any
approach that examines candidates linearly is losing to this by two orders of magnitude, and that is
why bisection beats intuition on hard bugs.

# Part 3 — Reading a stack trace properly

```
Exception in thread "http-nio-8080-exec-3" java.lang.IllegalStateException: Cannot process
    at com.acme.OrderService.process(OrderService.java:87)          ← where it was THROWN
    at com.acme.OrderController.create(OrderController.java:34)     ← the caller
    ... 40 frames of Spring ...
Caused by: java.sql.SQLException: connection is closed              ← the ROOT CAUSE
    at org.postgresql.jdbc.PgConnection.checkClosed(PgConnection.java:783)
    ... 12 more
```

How to read one:

**1. Read the *last* `Caused by` first.** That is the root cause; everything above it is wrapping
(Day 061). People read from the top, find framework code, and conclude the framework is broken.

**2. Find the topmost frame that is *your* code.** Skip framework frames. That is where your code
made the call that failed.

**3. Note the thread name.** `http-nio-8080-exec-3` is a request thread; `pool-2-thread-1` is your
executor; `main` is startup. It tells you the context (Day 076).

**4. Beware `... 12 more`.** It elides frames shared with the enclosing trace — the information is
there, just not repeated.

**5. Watch for the missing trace entirely.** The JIT elides stack traces for exceptions thrown very
frequently at the same site (`-XX:-OmitStackTraceInFastThrow` disables it). An NPE with no trace at
all in production is usually this, not a logging bug.

Java 14+ **helpful NullPointerException messages** are worth knowing:

```
Cannot invoke "String.length()" because the return value of
"java.util.Map.get(Object)" is null
```

That tells you *which* of five chained calls was null — a question that previously required a
debugger. It is on by default from Java 15.

# Part 4 — Bug classes and their signatures

| Symptom | Usual cause | First move |
|---|---|---|
| Works locally, fails in prod | Config, data, or a version difference | Diff the configs and versions |
| Works alone, fails under load | Concurrency, pool exhaustion, timeouts | Thread dump (Day 076) |
| Fails intermittently | Race, ordering assumption, time, external dependency | Run it 1,000 times in a loop |
| Fails after hours | Leak, cache growth, `ThreadLocal`, fd exhaustion | Heap dump, `lsof` |
| Fails on the first request only | Lazy init, cold cache, JIT | Warm up and retest |
| Fails for one user | Data, permissions, locale, encoding | Get their exact input |
| Fails at month/year end | Date arithmetic, timezone | Test with a fixed `Clock` |
| Wrong number by a tiny amount | `double` for money (Day 042B) | Grep for `double` |
| Wrong characters | Charset (Day 063) | Check every encode/decode boundary |
| Sometimes 0 rows | `NOT IN` with NULL (Day 097) | Check for nullable columns |

## Heisenbugs

A bug that disappears when observed — add a log line and it goes away. Almost always **concurrency**:
the log statement changes timing, or is synchronised internally and accidentally provides the missing
happens-before edge (Day 065).

Do not chase it with print statements. Instead:

- Reason from the **memory model** — find the unsynchronised shared state.
- Use a thread dump under load rather than a debugger, which changes timing more.
- Run the operation from many threads in a tight loop until it fails reliably.
- Look for the usual suspects: a non-thread-safe field, check-then-act, a `SimpleDateFormat` shared
  between threads, an unsynchronised lazy initialisation.

## Rubber duck debugging

Explain the problem, out loud, line by line, to something that cannot help you.

It works — reliably enough that it has a name — because **explaining forces you to state your
assumptions explicitly**, and the bug is almost always in an assumption you never examined. The
sentence that ends "…and then it obviously returns the sorted list, wait" is the entire technique.

It is also why the articulation drill runs every day in this roadmap: the ability to explain
mechanism precisely is the same muscle.

# Part 5 — Prevention and the aftermath

**Make bugs shallow:**

- **Fail fast** with a clear message (Day 062) — the trace points at the cause, not a symptom three
  layers away.
- **Include the offending value.** `"total < 0: -450"`, not `"invalid total"`.
- **Correlation ids** (Day 073A) so you can pull one request's whole journey out of a million lines.
- **Assertions and invariant checks** at boundaries.
- **Structured logging** so "all failures for this user in the last hour" is a query.
- **Immutability** (Day 034A) — a value that cannot change cannot be changed by the wrong code.

## After the fix

Three things, none optional:

**1. Write the regression test.** You already reproduced it; the test costs almost nothing now and
prevents it forever (Day 098).

**2. Ask whether the same bug exists elsewhere.** If a `double` for money caused it, grep for the
other `double`s. A bug is usually an instance of a class of bug.

**3. Ask why it was not caught.** Missing test? Missing type? Missing constraint? Missing review
step? **Fix the class of bug, not just the instance** — that is what separates an engineer from a
patcher.

## Blameless post-mortems

For anything that reached production, write it down: timeline, impact, root cause, what went well,
what to change. **Blameless** because people who fear blame hide information, and hidden information
guarantees the next incident.

The most useful question is not "who made the mistake" but **"what made this mistake easy to make and
hard to catch?"** — a config that silently defaults, a test that could not have caught it, an alert
that did not fire.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Changing several things at once | Cannot tell what fixed it |
| Not reproducing first | You cannot know you fixed it |
| Reading a stack trace top-down | Blaming the framework instead of the root cause |
| Debugging by guessing | Works on easy bugs, fails on hard ones |
| Not writing down what you ruled out | Re-testing the same hypothesis |
| Assuming the library is broken | It is almost always your code |
| Print statements for a race | Changes timing; hides the bug |
| Fixing without a regression test | It comes back |
| Fixing the instance, not the class | The same bug appears elsewhere next month |
| Blame in a post-mortem | Information stops flowing |

## Interview questions

**Q: Walk me through how you debug something hard.**
Reproduce it reliably and minimise the reproduction; list hypotheses ordered by probability and cost;
start from "what changed"; test one variable at a time and record what is ruled out; bisect whenever
the search space is large. Then fix, verify, and write the regression test.

**Q: How do you read a stack trace?**
The last `Caused by` is the root cause, so read bottom-up. Then find the topmost frame in your own
code, and note the thread name for context.

**Q: A bug only happens in production. How do you approach it?**
Diff configuration, data and versions between environments; check what changed most recently; use
correlation ids to isolate the failing requests; take a thread dump or JFR recording if it is
load-dependent. Reproduce in a staging environment with production-shaped data before changing
anything.

**Q: A bug disappears when you add a log statement. What is it?**
Almost certainly concurrency — the logging changed the timing or added an accidental happens-before
edge. Reason from the memory model to find the unsynchronised shared state rather than adding more
prints.

**Q: What is bisection and where do you apply it?**
Binary search over a space: commits with `git bisect`, code by commenting out halves, data by halving
the input, configuration by adding settings back to a minimal baseline. It turns a thousand
candidates into ten tests.

**Q: What do you do after fixing a bug?**
Write the regression test, look for the same class of bug elsewhere, and ask why it was not caught —
then fix that gap too.

## Mini task

1. Take the last bug you fixed. Write the full seven-step process retrospectively, honestly. Note
   which steps you skipped and what they cost.
2. Practise `git bisect run` on a repository with a deliberately introduced failure (Day 087).
3. Take a 5,000-line input that breaks a parser and bisect it down to the offending line. Count the
   steps.
4. Write a program with a race condition. Add a log statement and observe it disappearing. Then find
   it by reasoning about the memory model instead.
5. Deliberately throw a wrapped exception three layers deep and practise reading the trace bottom-up.
6. Trigger a helpful NPE message on Java 15+ from a chain of four calls and confirm it names the
   right one.
7. Write a post-mortem for a bug you have fixed: timeline, impact, root cause, what made it easy to
   make and hard to catch, and one systemic change.
8. Find one bug class in your codebase — `double` for money, a shared `SimpleDateFormat`, a missing
   `NOT NULL` — and fix every instance, not just the one that bit you.

## 🎙️ Articulation drill

Two minutes: **"Tell me about the hardest bug you have debugged."**

This is one of the most common senior interview questions and it is assessing *method*, not the bug.
Structure it: the symptom, what made it hard, the hypotheses you ruled out and how, the technique
that cracked it (bisection, a thread dump, reading the memory model), the fix, the regression test,
and the systemic change you made so the class of bug could not recur. That last element is what
separates a good answer from a war story.
