# Day 259 🏗️

**P-259** · Authorization — RBAC, ownership, and tenant isolation

**Time:** 3 hrs · **Mode:** BUILD

> Day 258 answered *who are you*. **Today answers *what may you do* — and the two most common serious
> API vulnerabilities both live here**: IDOR (Day 119's number one) and cross-tenant leakage.
>
> **⭐ The property that makes authorization uniquely dangerous: the failure is a 200 with someone
> else's data.** Nothing throws, nothing logs, and every positive test passes. **A negative test is
> the only mechanism that will ever notice.**

---

# Part 1 — ⭐ Three layers, and what each can answer

| Layer | Question | ⭐ Cannot answer |
|---|---|---|
| ⭐ **URL rules** (Day 169) | "may any authenticated user reach this path?" | ⭐ **ownership — nothing is loaded yet** |
| ⭐ **Method security** (Day 174) | "may this user act on this record?" | — |
| ⭐ **The query itself** | ⭐ **it does not ask — it cannot return the row** | — |

> **⭐ Prefer the third wherever possible.** A missing annotation is a vulnerability; a missing
> `WHERE` clause is a query that returns nothing. **Day 147's principle applied to authorization:
> make the attack unrepresentable rather than blocked.**

```
⭐ Best:      /me/bookings/{id}  → findByPublicIdAndOwnerId(...)   ⭐ no id to forge, nothing to forget
⭐ Otherwise: @PreAuthorize("@bookingGuard.isOwner(#id, authentication)") in the SERVICE
```

**⭐ Combine Day 251's `/me/` contract decision with Day 255's scoped repository methods and IDOR is
structurally impossible for the majority of your endpoints** — which is a far stronger position than
"every endpoint has a guard annotation and I checked".

## ⭐ Roles versus permissions — decide now

```
⭐ Check permissions:  hasAuthority('booking:cancel:any')
⭐ Grant them to roles in the database
```

**Day 170's argument: checking `hasRole('ADMIN')` means adding a capability requires a code change
and a deploy; checking a permission makes it a database change.** Grant both, so roles remain
available for coarse checks.

**⭐ And Day 170's prefix trap will catch you**: `hasRole("ADMIN")` checks `ROLE_ADMIN`, while
`.authorities("ADMIN")` stores `ADMIN` literally. **The mismatch makes the endpoint unreachable for
everyone, with no error** — so write the test with a real admin user, not a mock with hand-set
authorities.

⭐ **Audit permission grants** (Day 165). You have replaced a reviewed code change with a database
row; without an audit trail nobody can answer "who gave support the refund permission?"

# Part 2 — ⭐ Tenant isolation, if your project is multi-tenant

**⭐ Day 176's four layers, and only one of them is a control.**

```
⭐ 1. The tenant comes from the AUTHENTICATED TOKEN — ⭐⭐ NEVER from a header
⭐ 2. A ThreadLocal TenantContext, ⭐ CLEARED IN A FINALLY
⭐ 3. Hibernate @Filter — ⭐ reduces mistakes, does NOT enforce
⭐⭐ 4. PostgreSQL Row-Level Security — ⭐⭐ THE ACTUAL CONTROL
```

**⭐ Why only layer 4 counts:** a missing `WHERE` clause, a native query, a `findById` with a foreign
id, or a `psql` session by an on-call engineer all bypass layers 1–3. **With RLS, an application bug
stops being a breach.**

```sql
alter table bookings enable row level security;
⭐ alter table bookings force row level security;      -- ⭐ applies to the table owner too
create policy tenant_isolation on bookings
    using (tenant_id = current_setting('app.tenant_id', true));
```

**⭐ Two operational cautions that make RLS silently do nothing:**

| Caution | Consequence |
|---|---|
| ⭐ **Without `force`** | ⭐ the table owner bypasses the policy entirely |
| ⭐ **The setting must be transaction-scoped** and set on every checkout | ⭐ a pooled connection carries the previous tenant's value |

**⭐ The second is Day 156's pool meeting Day 066A's leak, and it is the worst possible bug**: it
serves another tenant's data, intermittently, under load.

**⭐ And layer 2's `finally` has the same payload.** Test it: set `server.tomcat.threads.max=1`, issue
two requests as different tenants, and confirm the second does not see the first's data.

## ⭐ `tenant_id` in the indexes

**Day 176 and Day 188: `tenant_id` leads every composite index**, because every query filters on it.
Verify this against Day 250's index list today.

# Part 3 — ⭐⭐ The tests, which are the only defence

**⭐ Write these for every protected operation. This is not optional.**

```
⭐ 1. Anonymous                        → 401
⭐ 2. Authenticated, wrong role        → 403
⭐ 3. Authenticated, correct role      → 200
⭐⭐ 4. Alice reads Bob's record        → ⭐⭐ 404 (not 403 — Day 119's existence oracle)
⭐ 5. Alice modifies Bob's record      → 404
⭐ 6. Tenant A reads Tenant B's record → ⭐ empty / 404
⭐ 7. Tenant A LISTS                   → ⭐ zero of Tenant B's rows appear
⭐ 8. An X-Tenant-Id header            → ⭐ ignored entirely
```

**⭐ Tests 4 through 8 are the ones that catch the bugs that matter**, and they are also the ones
nobody writes. **Test 7 in particular** — a list endpoint that forgot the tenant filter returns 200
with a mix of tenants, and every other test still passes.

**⭐ You need a custom `@WithMockCustomUser`** backed by a `WithSecurityContextFactory`, because
`@WithMockUser` cannot express a principal with a `tenantId` and a `customerId`. **Build it today —
without it the ownership tests cannot be written at all.**

**⭐ And the destructive proof, once:**

```
⭐ Deliberately remove the tenant filter from ONE repository method.
⭐ Confirm ONLY the cross-tenant test fails — everything else stays green.
⭐ Restore it.
```

**⭐ That exercise demonstrates, to yourself, that the negative test is the only thing standing
there.** It is also a good story.

## ⭐ The gaps to close

| Gap | Fix | Day |
|---|---|---|
| ⭐ **`@Async` and `@Scheduled`** | ⭐ no security context — a `ThreadLocal` | 169, 177 |
| ⭐ **Collection endpoints** | ⭐ **filter in the query**, never `@PostFilter` | 174 |
| ⭐ **Self-invocation** | method security is AOP — the check never runs | 137, 174 |
| Missing `@EnableMethodSecurity` | every annotation silently inert | 174 |

**⭐ `@PostFilter` deserves the emphasis** (Day 174): it fetches everything and discards in memory,
which on a real dataset is a full load to return twelve rows — **and it breaks pagination, because the
page is filtered after it is cut.** Collection authorization is a query predicate.

# Part 4 — ⭐ The rest of Day 176's checklist, applied

**Run all twenty items against your project today. These are the ones most likely to fail right now:**

| # | Check | Day |
|---|---|---|
| ⭐ 1 | ⭐ `.anyRequest().authenticated()` **last in every chain** | 169 |
| ⭐ 2 | ⭐ Chains ordered **most-specific first** — ⭐ a `/**` chain first makes later ones dead | 169 |
| 3 | No `WebSecurityCustomizer.ignoring()` | 169 |
| ⭐ 4 | CSRF enabled wherever a cookie authenticates (your refresh endpoint) | 172 |
| ⭐ 5 | ⭐ CORS not `allowedOriginPatterns("*")` with credentials | 155 |
| ⭐ 6 | ⭐ `http.cors()` present, or preflight 401s | 155 |
| 7 | Actuator on a separate port, allow-listed | 143 |
| ⭐ 8 | ⭐ CSP header set — ⭐ **the one Spring does not set** | 169 |
| ⭐ 9 | ⭐ `forward-headers-strategy` behind a proxy — ⭐ or `Secure` never applies and rate limiting sees one IP | 155 |
| ⭐ 10 | ⭐ **Least-privilege database user** — no DDL for the application | 163b |

**⭐ Item 2 is the one that silently opens endpoints**, and it is easy to introduce when you add the
second chain for Actuator. **Test it: write a test asserting an admin endpoint 403s for a normal
user, and it will catch the ordering bug the day someone introduces it.**

**⭐ Item 9 has two consequences people forget**: `Secure` cookies are silently dropped because the
app thinks it is on HTTP, and Day 208's IP rate limiting treats the entire internet as one client.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ URL rules only | ⭐ IDOR — the top API vulnerability |
| ⭐ Guards instead of scoped queries | one forgotten annotation is a breach |
| ⭐ Tenant from a header | ⭐ "act as any tenant" — a total breach |
| ⭐ `TenantContext` not cleared in `finally` | ⭐ the next request serves another tenant's data |
| Relying on Hibernate `@Filter` alone | bypassed by `findById` and native queries |
| ⭐ RLS without `force` | the owner bypasses it silently |
| RLS setting not transaction-scoped | pooled connection carries the previous tenant |
| ⭐ `@PostFilter` on a collection | full load, and broken pagination |
| ⭐ A `/**` chain ordered first | later chains dead; endpoints public with no error |
| `hasRole`/`authorities` prefix mismatch | endpoint unreachable for everyone |
| ⭐ Method security expected in `@Async` | no context — a `ThreadLocal` |
| 403 instead of 404 across tenants or owners | existence oracle |
| ⭐ **No negative tests** | ⭐ the failure is a silent 200 |
| Application DB user with DDL rights | injection escalates to schema damage |

## 🎤 Defence questions

1. **⭐ How do you stop Alice reading Bob's booking?** (⭐ the strongest answer is "the query cannot
   return it")
2. **⭐ Why 404 rather than 403?**
3. **⭐ Where does the tenant id come from, and why never a header?**
4. **⭐ Which of your tenant-isolation layers is the actual control, and why the others are not?**
5. **⭐ What happens if you forget the tenant filter on one repository method?** (⭐ you have tested
   this)
6. **Why permissions rather than roles in your checks?**
7. **⭐ Why is `@PostFilter` wrong for your list endpoints?**
8. **⭐ How would you know if an authorization bug were introduced tomorrow?**
