# Part 1 — L-063 · I/O and NIO

## The one distinction that organises the whole API

Java's I/O library looks enormous. It is actually a 2×2 grid:

|  | **Bytes** | **Characters** |
|---|---|---|
| **Read** | `InputStream` | `Reader` |
| **Write** | `OutputStream` | `Writer` |

Everything else is a decorator over one of those four. `BufferedInputStream`, `GZIPInputStream`,
`DataInputStream`, `CipherInputStream` — all are `InputStream`s that wrap another `InputStream` and
add one behaviour. That is the **Decorator pattern**, and `java.io` is the canonical textbook
example of it. Once you see that, the class count stops being intimidating:

```java
var in = new DataInputStream(
             new BufferedInputStream(
                 new GZIPInputStream(
                     new FileInputStream("data.gz"))));
```

Read that inside out: file → decompress → buffer → typed reads. Each layer knows nothing about the
others. You can reorder or remove any layer.

**Bytes versus characters is the other axis, and it is where the bugs live.** A byte stream moves
bytes. A character stream moves `char`s, which means **a charset is involved** — and a charset is a
decision, so it should never be implicit.

```java
new FileReader("f.txt")                                     // 💀 platform default charset
new InputStreamReader(new FileInputStream("f.txt"), UTF_8)  // ✅ explicit
Files.readString(Path.of("f.txt"))                          // ✅ UTF-8 by definition
```

Java 18 made UTF-8 the default charset everywhere (JEP 400), which fixed a decade of "works on my
Linux box, mojibake on Windows" bugs — including the exact class of bug that mangles em-dashes when
a Windows tool reads a UTF-8 file as Windows-1252. **Still write the charset explicitly.** It
documents intent and it survives running on an older JVM.

## Buffering — the number that matters

```java
// Unbuffered: one read() syscall per byte
try (var in = new FileInputStream("10mb.bin")) {
    int b; long sum = 0;
    while ((b = in.read()) != -1) sum += b;      // ~10,000,000 syscalls
}

// Buffered: one syscall per 8 KB
try (var in = new BufferedInputStream(new FileInputStream("10mb.bin"))) {
    int b; long sum = 0;
    while ((b = in.read()) != -1) sum += b;      // ~1,280 syscalls
}
```

Both loops look identical. The second is typically **50–100× faster**, and Day 023's B-01 explains
exactly why: every unbuffered `read()` is a **system call**, which means a mode switch into the
kernel and back. The buffered version does one syscall per 8,192 bytes and serves the rest from a
`byte[]` in the heap.

This is the highest-value single fact in Java I/O. Measure it today; the number is more convincing
than the explanation.

Note the asymmetry on writes: buffering a writer means **data sits in memory until flush or close**.
If the process dies in between, that data is gone. `close()` flushes; try-with-resources therefore
flushes; a forgotten `close()` is how "the last few log lines are always missing" happens.

## `java.io` versus `java.nio.file`

The modern file API (`java.nio.file`, Java 7) replaces `java.io.File` outright:

| Old | New | Why the new one |
|---|---|---|
| `File` | `Path` | Immutable, filesystem-agnostic, works with zip filesystems |
| `file.delete()` | `Files.delete(p)` | Old returns a **boolean you will ignore**; new throws with a reason |
| `file.exists()` | `Files.exists(p)` | Symlink-aware via `LinkOption` |
| manual loops | `Files.readAllLines`, `Files.lines`, `Files.copy` | Correct and short |
| — | `Files.walk`, `WatchService` | Did not exist before |

The `delete()` example is the argument in miniature. `File.delete()` returns `false` for
"does not exist", "no permission", "not empty", and "locked by another process" — the same false,
with no way to distinguish. `Files.delete()` throws `NoSuchFileException`,
`DirectoryNotEmptyException`, or `AccessDeniedException`. That is Day 062's fail-fast principle
applied to an API.

## Code to type

```java
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.util.*;
import java.util.stream.*;

public class IoDemo {

    public static void main(String[] args) throws Exception {
        Path dir  = Files.createTempDirectory("ioDemo");
        Path file = dir.resolve("data.txt");

        // --- Write, three ways -------------------------------------------
        Files.writeString(file, "alpha\nbeta\ngamma\n", StandardCharsets.UTF_8);

        try (var w = Files.newBufferedWriter(dir.resolve("b.txt"), StandardCharsets.UTF_8)) {
            for (int i = 0; i < 5; i++) { w.write("line " + i); w.newLine(); }
        }

        Files.write(dir.resolve("c.bin"), new byte[]{1, 2, 3, 4});

        // --- Read, three ways --------------------------------------------
        System.out.println(Files.readString(file));                    // small files only
        System.out.println(Files.readAllLines(file));                  // small files only

        try (Stream<String> lines = Files.lines(file)) {               // LAZY — must close
            lines.filter(l -> l.contains("a"))
                 .map(String::toUpperCase)
                 .forEach(System.out::println);
        }

        // --- Path arithmetic: no string concatenation ---------------------
        Path p = Path.of("/var", "log", "app", "server.log");
        System.out.println(p.getFileName());              // server.log
        System.out.println(p.getParent());                // /var/log/app
        System.out.println(p.getNameCount());             // 4
        System.out.println(p.resolve("../old.log").normalize());  // /var/log/app/old.log
        System.out.println(Path.of("/var/log").relativize(p));    // app/server.log

        // --- Metadata -----------------------------------------------------
        System.out.println(Files.size(file) + " bytes");
        System.out.println(Files.getLastModifiedTime(file));
        System.out.println(Files.probeContentType(file));

        // --- Walk a tree ---------------------------------------------------
        try (Stream<Path> walk = Files.walk(dir)) {
            walk.filter(Files::isRegularFile).forEach(System.out::println);
        }

        // --- Buffering, measured -------------------------------------------
        Path big = dir.resolve("big.bin");
        byte[] payload = new byte[4 * 1024 * 1024];
        new Random(42).nextBytes(payload);
        Files.write(big, payload);

        System.out.printf("unbuffered %6d ms%n", time(() -> sum(new FileInputStream(big.toFile()))));
        System.out.printf("buffered   %6d ms%n", time(() ->
                sum(new BufferedInputStream(new FileInputStream(big.toFile())))));

        deleteRecursively(dir);
    }

    static long sum(InputStream raw) throws IOException {
        try (InputStream in = raw) {
            long s = 0; int b;
            while ((b = in.read()) != -1) s += b;
            return s;
        }
    }

    interface Job { long run() throws Exception; }

    static long time(Job j) throws Exception {
        long t0 = System.nanoTime(); j.run();
        return (System.nanoTime() - t0) / 1_000_000;
    }

    static void deleteRecursively(Path dir) throws IOException {
        try (Stream<Path> s = Files.walk(dir)) {
            s.sorted(Comparator.reverseOrder()).forEach(p -> {
                try { Files.delete(p); } catch (IOException e) { throw new UncheckedIOException(e); }
            });
        }
    }
}
```

Three details in that code are deliberate.

**`Files.lines` is lazy and holds an open file handle**, so it must be closed — it is
`AutoCloseable` precisely for that reason. `Files.readAllLines` loads everything into memory and
does not. Using `readAllLines` on a 2 GB log is an `OutOfMemoryError`; `Files.lines` streams it in
constant memory. That is the same laziness you learned in Day 059, now with a resource attached.

**Path arithmetic never uses string concatenation.** `resolve`, `relativize` and `normalize` handle
separators, `..` and absolute-versus-relative correctly. Building paths with `+ "/" +` is both a
portability bug and, when user input is involved, a **path traversal vulnerability** — normalize and
then verify the result is still inside your base directory:

```java
Path base = Path.of("/srv/uploads").toRealPath();
Path target = base.resolve(userSuppliedName).normalize();
if (!target.startsWith(base)) throw new SecurityException("traversal attempt");
```

That check is the Java form of the `../../etc/passwd` defence the Web domain's Phase 06 covers.

**Reverse-ordered walk for deletion** — children before parents, because a non-empty directory
cannot be deleted.

## `java.nio` the other thing: buffers and channels

Confusingly, "NIO" names two different things. `java.nio.file` is the modern file API above.
`java.nio` proper is buffers, channels and selectors — the machinery for scalable I/O.

```java
try (FileChannel ch = FileChannel.open(path, StandardOpenOption.READ)) {
    ByteBuffer buf = ByteBuffer.allocate(8192);
    while (ch.read(buf) != -1) {
        buf.flip();                       // switch from filling to draining
        while (buf.hasRemaining()) process(buf.get());
        buf.clear();                      // switch back
    }
}
```

A `ByteBuffer` has three cursors — `position`, `limit`, `capacity` — and one mode. `flip()` sets
`limit = position; position = 0`, turning "I have written up to here" into "read from the start to
here". **Forgetting `flip()` is the classic NIO bug**: you read zero bytes and cannot see why.

```
after writing 5 bytes:   [ a b c d e _ _ _ ]   pos=5  limit=8
after flip():            [ a b c d e _ _ _ ]   pos=0  limit=5
```

Two more capabilities worth knowing by name:

- **`ByteBuffer.allocateDirect`** allocates outside the heap so the kernel can DMA into it without
  a copy. Faster for large transfers, much slower to allocate, and not managed by GC in the usual
  way — use it for long-lived buffers only.
- **Memory-mapped files** (`FileChannel.map`) map a file into the address space, so reads are page
  faults rather than syscalls (Day 053's B-10). This is how Kafka and most databases read.

The third piece — **selectors** — is non-blocking I/O multiplexing, which is tomorrow's territory and
gets its full treatment in Day 064's B-13. Today, just know that `Selector` is Java's portable
wrapper over `epoll`/`kqueue`/IOCP.

## Common mistakes

| Mistake | Consequence |
|---|---|
| No buffering | 50–100× slower; millions of syscalls |
| `FileReader` / `new String(bytes)` | Platform charset; corrupt text on another machine |
| `Files.readAllLines` on a large file | `OutOfMemoryError` |
| Not closing `Files.lines` | File-handle leak; eventually "too many open files" |
| Building paths with `+ "/" +` | Portability bug and path traversal |
| Ignoring `File.delete()`'s boolean | Silent failure with no reason |
| Forgetting `flip()` | Reads nothing, no error |
| Buffered writer without close/flush | Last writes lost |
| `available()` as "the size" | It is only what can be read *without blocking* |

## Interview questions

**Q: Difference between a stream and a reader?**
Streams carry bytes; readers carry characters and therefore involve a charset. Use byte streams for
binary data, readers for text, and always state the charset.

**Q: Why is `BufferedInputStream` faster?**
It amortises system calls. Unbuffered `read()` is one syscall per byte — mode switch each time.
Buffered reads 8 KB per syscall and serves the rest from memory.

**Q: `java.io.File` versus `java.nio.file.Path`?**
`Path` is immutable and filesystem-agnostic; `Files` operations throw specific exceptions instead of
returning an uninformative boolean, and the API has tree walking, watching and streaming that
`File` never had.

**Q: How would you process a 50 GB file?**
Stream it: `Files.lines` or a buffered reader, constant memory, never `readAllLines`. If it is
binary and random-access, memory-map it.

**Q: What does `flip()` do?**
Switches a `ByteBuffer` from write mode to read mode by setting limit to the current position and
position to zero.
