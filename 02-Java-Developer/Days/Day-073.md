# Part 1 — L-073 · Why a build tool exists

Before Maven, a Java build was an Ant script: a hand-written list of "compile these, copy that, jar
it". Every project invented its own layout and its own targets, so joining a project meant learning
its build.

Maven's contribution was **convention over configuration**:

```
src/main/java        production sources
src/main/resources   production resources (config, templates) → onto the classpath
src/test/java        test sources
src/test/resources   test resources
target/              build output (never committed)
pom.xml              the project descriptor
```

Any Maven project in the world has this layout, so `mvn test` works without you reading anything.
That is the whole value proposition, and Gradle kept it.

A build tool gives you five things: a **standard layout**, **dependency resolution** (including
transitive dependencies), a **lifecycle**, **plugins**, and **reproducibility** — the same inputs
producing the same artifact on your laptop and in CI.

## Coordinates

```xml
<groupId>com.fasterxml.jackson.core</groupId>     <!-- who: reverse-domain namespace -->
<artifactId>jackson-databind</artifactId>         <!-- what -->
<version>2.17.1</version>                          <!-- which -->
<packaging>jar</packaging>                         <!-- jar | war | pom -->
```

`group:artifact:version` — **GAV** — uniquely identifies an artifact in a repository. Gradle writes
the same thing as `com.fasterxml.jackson.core:jackson-databind:2.17.1`.

A `-SNAPSHOT` suffix means "mutable, in development": Maven re-checks the remote for a newer build.
**Never depend on a SNAPSHOT in a release** — the same version string can resolve to different bytes
tomorrow, which destroys reproducibility.

## The lifecycle — the part people get wrong

Maven's default lifecycle is an **ordered sequence of phases**, and running a phase runs *every
phase before it*:

```
validate → compile → test → package → verify → install → deploy
```

| Phase | What it does |
|---|---|
| `compile` | `src/main/java` → `target/classes` |
| `test` | runs `src/test/java` (Surefire). **Failure stops the build.** |
| `package` | produces `target/*.jar` |
| `verify` | runs integration tests (Failsafe) and quality checks |
| `install` | copies the artifact into your **local** repo `~/.m2/repository` |
| `deploy` | uploads to a **remote** repository |

So `mvn package` also compiled and tested. `mvn install` did all of that and published locally. This
is why `mvn clean install` — the command you will type most often — is slow: it is doing seven
things.

`clean` belongs to a *separate* lifecycle and deletes `target/`. Use it when you suspect stale
output; skipping it is what makes incremental builds fast.

```bash
mvn clean install -DskipTests          # compiles tests, does not run them
mvn clean install -Dmaven.test.skip    # does not even compile them
mvn dependency:tree                    # ← the single most useful Maven command
mvn help:effective-pom                 # the POM after inheritance and interpolation
mvn -o ...                             # offline
mvn versions:display-dependency-updates
```

`plugin:goal` syntax (`dependency:tree`) invokes a goal directly, outside the lifecycle.

## Scopes — the table to actually memorise

```xml
<dependency>
  <groupId>org.projectlombok</groupId>
  <artifactId>lombok</artifactId>
  <version>1.18.32</version>
  <scope>provided</scope>
</dependency>
```

| Scope | Compile | Test | Runtime | Packaged | Use for |
|---|---|---|---|---|---|
| `compile` (default) | ✅ | ✅ | ✅ | ✅ | ordinary libraries |
| `provided` | ✅ | ✅ | ❌ | ❌ | servlet API, Lombok — the container supplies it |
| `runtime` | ❌ | ✅ | ✅ | ✅ | JDBC drivers — needed at run, not compiled against |
| `test` | ❌ | ✅ | ❌ | ❌ | JUnit, Mockito, Testcontainers |
| `import` | — | — | — | — | only in `<dependencyManagement>`, for BOMs |

Two consequences worth naming: a **JDBC driver at `compile` scope** is a design smell — it means
your code imports the driver instead of `java.sql`. And **JUnit at `compile` scope** ships your test
framework to production.

## Transitive dependencies and conflict resolution

You declare A; A needs B; B needs C. Maven pulls all three. That is transitivity, and it is where
the real problems live — because two of your dependencies will eventually want *different versions*
of the same library.

**Maven picks by "nearest wins":** the version at the shallowest depth in the tree. On a tie, the
**first declared** wins. It does **not** pick the newest.

```
your-app
├── library-A 1.0
│   └── guava 28.0        ← depth 2
└── library-B 2.0
    └── commons-x 3.0
        └── guava 31.0    ← depth 3

Maven resolves guava 28.0 — the nearer one, not the newer one.
```

If library-B needed a Guava 31 method, you get a `NoSuchMethodError` **at runtime**, not at compile
time — which is Day 076A's territory and one of the most confusing failures in Java.

**Gradle picks the highest version instead**, which is right more often in practice but still not
always.

The three tools for fixing it:

```bash
mvn dependency:tree -Dincludes=com.google.guava    # find who pulls it
```

```xml
<!-- 1. exclude a specific transitive -->
<dependency>
  <groupId>com.example</groupId><artifactId>library-B</artifactId><version>2.0</version>
  <exclusions>
    <exclusion><groupId>com.google.guava</groupId><artifactId>guava</artifactId></exclusion>
  </exclusions>
</dependency>

<!-- 2. pin the version for the whole build (does NOT add the dependency) -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.google.guava</groupId><artifactId>guava</artifactId><version>33.2.0-jre</version>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- 3. import a BOM — someone else's tested version matrix -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.3.0</version>
      <type>pom</type><scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

The **BOM** is the important one. Spring Boot's BOM declares consistent versions for ~200 libraries
that its team has tested together — which is why in a Spring Boot project you write dependencies
*without* versions. That is not magic; it is `dependencyManagement` inherited from a parent POM.

`dependencyManagement` declares *what version, if used*; `dependencies` declares *what is actually
used*. Confusing them is a common mistake — putting a dependency only in `dependencyManagement`
means it is never on your classpath at all.

## Multi-module

```
parent/
├── pom.xml                <packaging>pom</packaging>
├── common/pom.xml
├── service/pom.xml        depends on common
└── web/pom.xml            depends on service
```

```xml
<!-- parent -->
<packaging>pom</packaging>
<modules>
  <module>common</module><module>service</module><module>web</module>
</modules>
<properties>
  <java.version>21</java.version>
  <maven.compiler.release>21</maven.compiler.release>
</properties>
```

`mvn install` at the parent builds all modules in **dependency order** — Maven computes the graph,
you do not list it. Modules give you enforced boundaries: `web` cannot accidentally use an internal
class of `common` unless `common` exports it.

Use `-pl web -am` to build just one module and what it depends on.

## Gradle, in the differences that matter

```kotlin
// build.gradle.kts
plugins { java; id("org.springframework.boot") version "3.3.0" }

repositories { mavenCentral() }

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    runtimeOnly("org.postgresql:postgresql")
    compileOnly("org.projectlombok:lombok")
    annotationProcessor("org.projectlombok:lombok")
    testImplementation("org.junit.jupiter:junit-jupiter")
}

tasks.test { useJUnitPlatform() }
```

| | Maven | Gradle |
|---|---|---|
| Config | XML, declarative | Groovy/Kotlin DSL, programmable |
| Model | fixed lifecycle | **task graph** with declared inputs/outputs |
| Speed | slower | faster — incremental, build cache, daemon |
| Conflict rule | nearest wins | **highest wins** |
| Learning curve | shallow | steeper; a build script is code |
| Reproducibility | high by construction | needs discipline (it is a program) |

**`implementation` vs `api` is Gradle's genuinely better idea.** With `implementation`, your
dependency is *not* exposed to your consumers' compile classpath — so upgrading it does not force
them to recompile, and they cannot accidentally depend on your internals. Maven has no equivalent;
everything is effectively `api`. This is why large Gradle builds are faster: changing an
`implementation` dependency does not cascade.

Which to learn? **Maven for interviews and most enterprise Java; Gradle for Android and large
polyglot builds.** Know Maven's lifecycle and `dependency:tree` cold; be able to read a Gradle file.

## The wrapper — non-negotiable

```bash
./mvnw clean install        # committed to the repo
./gradlew build
```

The wrapper is a small script plus a properties file pinning the build-tool version, downloaded on
first use. **Commit it.** It removes "works on my machine because I have Maven 3.8" from the list of
things that can go wrong, and it means CI does not need Maven installed at all.

## Code to type

```bash
mvn archetype:generate -DgroupId=com.example -DartifactId=demo \
    -DarchetypeArtifactId=maven-archetype-quickstart -DinteractiveMode=false
cd demo

mvn dependency:tree
mvn clean package
java -cp target/demo-1.0-SNAPSHOT.jar com.example.App

# now add two dependencies that conflict and inspect
mvn dependency:tree -Dverbose        # shows OMITTED FOR CONFLICT lines
mvn help:effective-pom | head -60
```

The `-Dverbose` flag is the one to remember: it prints the versions Maven *rejected* and why, which
is exactly what you need when a `NoSuchMethodError` appears.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Assuming newest wins | Maven takes the *nearest*; you get an old version silently |
| No `dependencyManagement`/BOM | Version drift across modules |
| Declaring only in `dependencyManagement` | Not on the classpath at all |
| SNAPSHOT in a release | Non-reproducible builds |
| Test libraries at `compile` scope | Shipped to production |
| JDBC driver at `compile` scope | Your code compiles against the driver |
| Not committing the wrapper | "Works on my machine" |
| `mvn clean install` every time | Slow; `clean` throws away incremental work |
| Committing `target/` or `build/` | Repo bloat |
| Version ranges (`[1.0,2.0)`) | Builds change without you changing anything |

## Interview questions

**Q: What does `mvn install` do?**
Runs the lifecycle up to and including `install` — validate, compile, test, package, verify, install
— and places the artifact in the local `~/.m2` repository.

**Q: How does Maven resolve a version conflict?**
Nearest definition wins; on a tie, first declared. Not the highest version. Gradle uses highest.
Diagnose with `mvn dependency:tree -Dverbose`, fix with an exclusion, `dependencyManagement`, or a
BOM.

**Q: `compile` vs `provided` vs `runtime` vs `test` scope?**
Compile: everywhere and packaged. Provided: compile and test only, supplied by the container.
Runtime: not on the compile classpath but packaged — JDBC drivers. Test: test only.

**Q: What is a BOM?**
A POM imported into `dependencyManagement` that declares a tested, consistent set of versions, so
your dependencies need no version tags. Spring Boot's is the canonical example.

**Q: Maven vs Gradle?**
Maven is declarative XML with a fixed lifecycle — predictable and easy to read. Gradle is a
programmable task graph with incremental builds and caching, plus `implementation` versus `api`
separation that avoids recompiling consumers. Maven for most enterprise work, Gradle for Android and
large builds.

**Q: Why commit the wrapper?**
It pins the build-tool version per project, so every developer and CI runner builds identically
without installing anything.

## 🎙️ Articulation drill

Two minutes: **"A library method is throwing `NoSuchMethodError` at runtime but the code compiles.
What is happening and how do you fix it?"**

Two different versions on the classpath — compiled against one, running against another — because a
transitive resolved to the nearest rather than the newest. `mvn dependency:tree -Dverbose` to find
the omitted version, then exclude or pin via `dependencyManagement`/BOM. This is a real diagnosis,
not build-tool trivia, which is why it is the drill.
