# Part 1 — L-007 · DNS

## What it is

**DNS turns a name into an IP address.** `google.com` → `142.250.183.100`.

You need this because routing works on IP addresses (Day 006) and humans cannot remember them — and
because the mapping must be *changeable*. A server moves, its IP changes, and every user should
follow without editing anything. DNS is the indirection layer that makes that possible.

Think of it as **the internet's most important distributed database**, with a hierarchy that mirrors
the name itself, read right to left:

```
        www . google . com .
         │      │       │   │
         │      │       │   └── root (the trailing dot — usually invisible)
         │      │       └────── TLD:  .com
         │      └────────────── domain: google
         └───────────────────── subdomain: www
```

## The full resolution walkthrough

This is the interview answer. Learn it in order.

```
Browser wants www.example.com

 1. Browser cache            "have I looked this up recently?"        ~0 ms
      │ miss
 2. OS cache                 (Windows DNS Client service, nscd)       ~0 ms
      │ miss
 3. hosts file               C:\Windows\System32\drivers\etc\hosts    ~0 ms
      │ miss                 /etc/hosts on Linux/Mac
 4. RESOLVER  (your ISP's, or 8.8.8.8 / 1.1.1.1)
      │
      │ The resolver does the actual work — this is "recursive resolution"
      │
      ├──▶ 5.  ROOT server (one of 13 clusters, a.root-servers.net …)
      │         "who handles .com?"
      │    ◀──  "ask the .com TLD servers, here they are"
      │
      ├──▶ 6.  TLD server (.com)
      │         "who handles example.com?"
      │    ◀──  "ask ns1.example.com at 1.2.3.4"   ← this is the NS record
      │
      ├──▶ 7.  AUTHORITATIVE nameserver for example.com
      │         "what is www.example.com?"
      │    ◀──  "A record: 93.184.216.34, TTL 3600"   ← the actual answer
      │
      │ resolver caches it for TTL seconds
      ▼
 8. Answer returns to the OS, which caches it
 9. Answer returns to the browser, which caches it
10. Browser opens a TCP connection to 93.184.216.34    ← Day 005 starts here
```

**The key distinction:**

- **Recursive** — the resolver does the whole journey on your behalf and returns a final answer.
  That's steps 4–7.
- **Iterative** — each server returns a *referral* ("I don't know, ask them"), not an answer. That's
  what the root and TLD servers do.

Your machine makes one recursive query. The resolver makes several iterative ones. This split is
what keeps the root servers from being crushed — they answer tiny referrals, not real lookups.

## Record types

| Type | Maps | Example |
|---|---|---|
| **A** | Name → IPv4 | `example.com → 93.184.216.34` |
| **AAAA** | Name → IPv6 | `example.com → 2606:2800:220:1:248:1893:25c8:1946` |
| **CNAME** | Name → another name | `www.example.com → example.com` |
| **MX** | Mail servers | `example.com → mail.example.com, priority 10` |
| **TXT** | Arbitrary text | SPF, DKIM, domain verification |
| **NS** | Which nameservers are authoritative | `example.com → ns1.example.com` |
| **SOA** | Zone metadata, serial, refresh timers | one per zone |
| **PTR** | IP → name (reverse) | used in mail anti-spam checks |

**You have already used three of these without knowing it.** In
[`03-Web-Developer/10-Ship-Checklist.md`](../../03-Web-Developer/10-Ship-Checklist.md):
the `A` record pointing at Vercel, the `CNAME` for `www`, and the `TXT` record for Google Search
Console verification. Go back and read that section again tonight — it will read completely
differently now.

Same for email deliverability: SPF, DKIM and DMARC are all **TXT records**. That's why "your reset
emails go to spam" is a DNS problem.

## TTL — the thing that bites you

Every record carries a **TTL** in seconds. Resolvers cache for that long and will not re-ask.

```
example.com.   3600   IN   A   93.184.216.34
               ────
               cache this for 1 hour
```

**The practical consequence:** you change your DNS to point at a new server, and some users keep
hitting the old one for up to the TTL. There is no way to force a global flush. You cannot call
anyone.

**The discipline:**

1. Lower TTL to 60 seconds **at least 24 hours before** a planned migration (so the old high TTL has
   expired everywhere)
2. Make the change
3. Wait, verify, then raise the TTL back to 3600+

Get this wrong and you have a split-brain migration where some users see the old server for hours.

## Why DNS is a common outage cause

- **It's a hard dependency.** DNS down = everything down, even though every server is healthy.
- **TTL means slow rollback.** Bad change propagates in seconds, reverts over hours.
- **It uses UDP** (port 53) by default for speed — no handshake, one packet each way. Falls back to
  TCP for responses over 512 bytes and for zone transfers.
- **Classic DNS is unauthenticated** — a spoofed reply that arrives first wins (**DNS cache
  poisoning**). DNSSEC signs records to fix this; adoption is partial. DoH/DoT encrypt the query
  itself, which is a different problem (privacy, not authenticity).

> The 2016 Dyn outage took down Twitter, Reddit, Spotify and GitHub simultaneously — not by attacking
> them, but by attacking their DNS provider. It's a good example to have ready in a system design
> round when discussing single points of failure.

Finally, resolve from Java — because this is what happens inside `new Socket("example.com", 80)`:

```java
import java.net.InetAddress;

public class DnsDemo {
    public static void main(String[] args) throws Exception {
        long start = System.nanoTime();
        InetAddress[] all = InetAddress.getAllByName("google.com");
        long first = System.nanoTime() - start;

        for (InetAddress a : all) System.out.println(a.getHostAddress());
        System.out.printf("First lookup:  %,d µs%n", first / 1000);

        start = System.nanoTime();
        InetAddress.getAllByName("google.com");
        System.out.printf("Second lookup: %,d µs%n", (System.nanoTime() - start) / 1000);
    }
}
```

The second is dramatically faster — the JVM caches DNS too. (Worth knowing: the JVM's DNS cache TTL
is controlled by `networkaddress.cache.ttl`, and its default of caching *forever* in some
configurations has caused real outages when a service's IP changed. That's a genuine
production-incident story to have ready.)

## Common mistakes

| Mistake | Correction |
|---|---|
| "DNS is a server" | It's a distributed hierarchy: root, TLD, authoritative, plus caching resolvers. |
| Thinking your machine walks the tree | Your machine asks a resolver recursively. The resolver walks iteratively. |
| Expecting DNS changes to be instant | TTL governs it. Lower TTL 24h *before* a migration. |
| CNAME at the zone apex | Not allowed by the spec — `example.com` can't be a CNAME. Providers offer ALIAS/ANAME as a workaround. |
| "DNS uses TCP" | UDP/53 normally; TCP for large responses and zone transfers. |
| Assuming DNS is authenticated | It isn't, without DNSSEC. Spoofed replies are the basis of cache poisoning. |

## Interview questions

**Q: What happens when you type a URL and press Enter? (the DNS part)**
> The browser checks its cache, then the OS cache, then the hosts file. On a miss it queries the
> configured resolver recursively. The resolver queries a root server, which refers it to the TLD
> servers for `.com`, which refer it to the authoritative nameserver for the domain, which returns
> the A record. Each layer caches the result for its TTL, and the browser then opens a TCP connection
> to that IP.

**Q: Recursive vs iterative resolution?**
> In a recursive query the server is obliged to return a final answer, doing whatever work is needed.
> In an iterative query it returns the best referral it has. Clients query resolvers recursively;
> resolvers query the root and TLD servers iteratively.

**Q: A record vs CNAME?**
> An A record maps a name directly to an IPv4 address. A CNAME maps a name to another name, requiring
> a further lookup. A CNAME cannot coexist with other records at the same name and isn't permitted at
> the zone apex.

**Q: Why can't you change DNS instantly?**
> Resolvers worldwide cache records for their TTL and there's no mechanism to invalidate them.
> You lower the TTL well in advance of the change instead.

**Q: Why is DNS a single point of failure?**
> Every connection begins with a name lookup, so if DNS fails, healthy servers become unreachable.
> The 2016 Dyn attack demonstrated it at scale.

# Part 2 — C-05 · TCP II — retransmission, windows, flow control

## Retransmission

Day 005: every byte is numbered, and ACKs confirm receipt. So what happens on loss?

The sender starts a **retransmission timer** when it sends. No ACK before it fires → resend.

The timeout is not fixed. TCP measures the **RTT** continuously and computes a smoothed estimate
plus a variance margin:

```
   RTO = SRTT + 4 × RTTVAR
```

Too short and you flood the network with needless duplicates; too long and recovery is sluggish. The
adaptive estimate is the compromise.

### Fast retransmit — the clever bit

Waiting for a timeout is slow. TCP has a shortcut.

The receiver ACKs **the highest contiguous byte received**. If segment 2 is lost but 3, 4 and 5
arrive, the receiver can only keep saying "I still want 2":

```
   sent:  1  2  3  4  5
   lost:     ✗
   ACKs:  ack=2, ack=2, ack=2, ack=2     ← duplicate ACKs
                  └──────┬──────┘
              three duplicates → sender retransmits immediately,
              without waiting for the timer
```

**Three duplicate ACKs trigger an immediate retransmit.** This is *fast retransmit*, and it's why a
single lost packet costs milliseconds rather than a full timeout.

## The sliding window

Sending one segment and waiting for its ACK would be catastrophic:

```
  1 segment (1460 B) per 140 ms RTT = ~10 KB/s
```

That's dial-up speed on a gigabit link. The fix: **send many segments before any ACK returns.**

```
  bytes:  [ acked ][ sent, not yet acked ][ may send now ][ cannot send yet ]
          └────────────────┬──────────────────────────┘
                    the window

  ACK arrives → the whole window slides right → more may be sent
```

The window size determines throughput:

```
   throughput ≈ window size / RTT
```

To saturate a 100 Mbps link with 140 ms RTT you need a window of ~1.75 MB. This product —
**bandwidth × delay** — is the amount of data "in flight" on the wire, and it's why high-bandwidth
long-distance links need window scaling (the original 16-bit window field maxes at 64 KB, nowhere
near enough).

## Flow control vs congestion control

Two different problems, and mixing them up is a classic interview stumble.

| | Flow control | Congestion control |
|---|---|---|
| **Protects** | The **receiver** from being overwhelmed | The **network** from being overwhelmed |
| **Signal** | Receiver advertises a window in every ACK | Inferred from packet loss / delay |
| **Mechanism** | `rwnd` — receiver window | `cwnd` — congestion window |
| **Who decides** | The receiver, explicitly | The sender, by guessing |

The sender may send only:

```
   min(rwnd, cwnd)
```

**Flow control is explicit** — the receiver states its free buffer space. If the application isn't
reading fast enough, the buffer fills, the advertised window shrinks toward zero, and the sender
stops. That's the *zero window* condition, and the sender then probes periodically to ask whether
space has freed up.

**Congestion control is guesswork** — nobody tells the sender the network is congested; it infers it
from loss. That's Day 008, C-06.

> **Where this shows up in your code:** a slow consumer causes TCP backpressure all the way to the
> sender's `write()` call, which blocks. That is exactly the mechanism behind "backpressure" in
> reactive systems and message queues (Day 336). You'll meet the concept again three times; this is
> where it physically lives.

## Interview questions

**Q: How does TCP handle packet loss?**
> The sender keeps a retransmission timer based on a smoothed RTT estimate; if no ACK arrives it
> resends. It also uses fast retransmit — three duplicate ACKs indicate a gap, so it resends
> immediately without waiting for the timeout.

**Q: What is the sliding window and why does it exist?**
> It's the amount of unacknowledged data a sender may have in flight. Without it, throughput would be
> one segment per round trip. Throughput is roughly window size divided by RTT, so the window must be
> at least the bandwidth-delay product to saturate a link.

**Q: Difference between flow control and congestion control?**
> Flow control protects the receiver and is explicit — the receiver advertises its available buffer
> in every ACK. Congestion control protects the network and is inferred by the sender from packet
> loss. The sender is limited by the minimum of the two windows.

**Q: What are duplicate ACKs telling you?**
> That segments are arriving but with a gap. The receiver keeps acknowledging the last contiguous
> byte it has. Three duplicates is the signal to fast-retransmit the missing segment.
