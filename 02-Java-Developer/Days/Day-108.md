# Day 108

**L-108** · Filtering, sorting, searching, sparse fieldsets

**Time:** 3 hrs · **Mode:** NEW

> The rest of the collection interface. This is also the day where a *convenience* feature becomes a
> *vulnerability* class: every flexible query parameter you accept is user input that reaches your
> database, and the more expressive you make it, the closer you get to having accidentally exposed
> SQL over HTTP.

# Part 1 — Filtering

## The design ladder

There are four levels, and choosing the right rung is the whole decision:

**Level 1 — fixed parameters.** Simple, safe, limited.

```http
GET /orders?status=paid&customer_id=cus_17&created_after=2026-08-01
```

**Level 2 — operators in the value.**

```http
GET /orders?total=gte:1000&created_at=lt:2026-08-01&status=in:paid,shipped
```

**Level 3 — bracketed operators** (the JSON:API / Spring Data style).

```http
GET /orders?filter[total][gte]=1000&filter[status][in]=paid,shipped
```

**Level 4 — a query language** (RSQL, OData, or your own).

```http
GET /orders?q=total>=1000;status=in=(paid,shipped);customer.region=='TN'
```

> **Start at level 1 or 2. Go higher only when a real consumer demands it.** Level 4 is a parser, a
> permission model and an optimisation problem you now own forever — you have built a database query
> interface, and every capability you expose is one you must secure and index.

Whatever level you choose, be consistent across every collection endpoint (Day 103).

## The safe implementation

**This is the part that matters.** Every filter must map through an allow-list to a
parameterised query.

```java
// The allow-list: API field name → (column, permitted operators, type)
private static final Map<String, FilterSpec> FILTERABLE = Map.of(
    "status",      new FilterSpec("status",      Set.of(EQ, IN),           Type.ENUM),
    "total",       new FilterSpec("total_cents", Set.of(EQ, GT, GTE, LT, LTE), Type.MONEY),
    "created_at",  new FilterSpec("created_at",  Set.of(GT, GTE, LT, LTE), Type.INSTANT),
    "customer_id", new FilterSpec("customer_id", Set.of(EQ),               Type.ID)
);

public Query build(Map<String, String> params, TenantId tenant) {
    var sql  = new StringBuilder("SELECT * FROM orders WHERE tenant_id = ?");
    var args = new ArrayList<Object>(List.of(tenant.value()));      // ← tenant ALWAYS first

    for (var e : params.entrySet()) {
        FilterSpec spec = FILTERABLE.get(e.getKey());
        if (spec == null) throw new BadRequestException("unknown filter: " + e.getKey());

        var parsed = Operator.parse(e.getValue());                   // "gte:1000"
        if (!spec.operators().contains(parsed.op()))
            throw new BadRequestException("operator not allowed on " + e.getKey());

        sql.append(" AND ").append(spec.column())                    // ← column from the ALLOW-LIST
           .append(' ').append(parsed.op().sqlToken()).append(" ?"); // ← operator from an enum
        args.add(spec.type().coerce(parsed.value()));                // ← value PARAMETERISED
    }
    return new Query(sql.toString(), args);
}
```

Three invariants, and all three are non-negotiable:

1. **Column names come from the allow-list, never from the request.** A column name cannot be a bind
   parameter, so it is the one part that is string-concatenated — which is exactly why it must never
   originate from user input (Day 119b).
2. **Operators come from a closed enum**, never from the request string.
3. **Values are always bind parameters.** Never concatenated, no exceptions.

**Unknown filters must be rejected, not ignored.** A silently ignored `?customer_id=` in an
authorization-adjacent filter means the client thinks it scoped the query and it did not — which is
how a filter bug becomes a data-exposure bug.

## Filters are not authorization

```java
// ❌ the client "filters" by tenant — so it can filter by any tenant
GET /orders?tenant_id=other-company

// ✅ tenant comes from the authenticated principal and is applied unconditionally
WHERE tenant_id = ?    // ← from the token, ALWAYS, and never overridable by a parameter
```

This is Day 105's rule restated at the collection level: **scope the query by the caller before any
client filter is applied.** A filter narrows an already-authorized set; it never widens it.

## Filter semantics to document

- **Repeated key** — `?status=paid&status=shipped` is OR. Different keys are AND. Say so.
- **`null` filtering** — `?assigned_to=null` must mean `IS NULL`, not `= 'null'` (Day 097).
- **Ranges** — inclusive or exclusive? Use explicit `gte`/`lt` rather than ambiguous `from`/`to`.
- **Dates without a time** — `?created_at=2026-08-14` means the whole day in *which* timezone?
  Require an offset, or document that dates are UTC days.

# Part 2 — Sorting

```http
GET /orders?sort=-created_at,total
```

The `-` prefix for descending is the most common convention and it survives URL encoding cleanly.

```java
private static final Map<String, String> SORTABLE = Map.of(
    "created_at", "created_at",
    "total",      "total_cents",
    "status",     "status");

List<String> clauses = new ArrayList<>();
for (String field : sortParam.split(",")) {
    boolean desc = field.startsWith("-");
    String column = SORTABLE.get(desc ? field.substring(1) : field);
    if (column == null) throw new BadRequestException("cannot sort by " + field);
    clauses.add(column + (desc ? " DESC" : " ASC"));
}
clauses.add("id DESC");                                    // ← the mandatory tiebreaker (Day 107)
String orderBy = " ORDER BY " + String.join(", ", clauses);
```

Three rules:

**Allow-list the sortable fields.** The column name is concatenated — it must be a key lookup, and
`?sort=(SELECT...)` must be impossible.

**Always append a unique tiebreaker**, or pagination is unstable (Day 107).

**Only allow sorts you have an index for.** `?sort=-description` on ten million rows is a full sort
of the table, and you just let a client trigger it. **This is a denial-of-service vector disguised as
a feature** — cap the sortable set to indexed columns, or bound the result set for unindexed sorts.

Also decide and document **null ordering**: `NULLS FIRST` or `NULLS LAST`. Databases differ, and
"why does this row jump around" is otherwise unanswerable.

# Part 3 — Sparse fieldsets

```http
GET /orders?fields=id,status,total
GET /orders?fields[order]=id,status&fields[customer]=name      # JSON:API, per type
```

Lets the client fetch less — meaningful on mobile, where the payload is the latency.

```java
Set<String> requested = parse(fieldsParam);
Set<String> allowed = Set.of("id", "status", "total", "created_at", "customer");
if (!allowed.containsAll(requested)) throw new BadRequestException(…);
Set<String> selected = requested.isEmpty() ? DEFAULT_FIELDS : requested;
```

Two things people get wrong:

**Always include the id**, whatever the client asked for. A response object with no identity is
useless and clients will break.

**`fields` is not authorization.** Omitting a field on request does not mean the client may see it
when requested — the allow-list must be *per caller role*, not global. Otherwise `?fields=salary`
becomes a permission bypass.

The related feature (Day 103):

```http
GET /orders/42?include=customer,line_items
```

`fields` narrows; `include` widens. **Bound `include` explicitly** — an unbounded `include` graph
lets a client request `include=customer.orders.line_items.product` and generate a join fan-out that
takes the database down. Allow-list the include paths and limit the depth to one or two.

# Part 4 — Search

**Search is not filtering, and conflating them is the most common design error here.**

| | Filter | Search |
|---|---|---|
| Semantics | Exact, boolean | Fuzzy, ranked |
| Result | A set | An *ordered* list by relevance |
| Backed by | B-tree indexes | Inverted index |
| Parameter | `?status=paid` | `?q=blue running shoes` |

## The ladder again

**Level 1 — `LIKE`.** Fine for small tables and prefix matching.

```sql
WHERE name ILIKE :prefix || '%'          -- ✅ sargable, uses an index (Day 097)
WHERE name ILIKE '%' || :term || '%'     -- ❌ leading wildcard: FULL SCAN, every time
```

That second line is where most "our search got slow" incidents come from.

**Level 2 — the database's full-text search.** Sufficient for a great many applications, and it
avoids running a second system:

```sql
-- PostgreSQL
ALTER TABLE product ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || coalesce(description,''))) STORED;
CREATE INDEX ON product USING GIN (search_vector);

SELECT *, ts_rank(search_vector, query) AS rank
FROM product, plainto_tsquery('english', :q) query
WHERE search_vector @@ query
ORDER BY rank DESC, id DESC
LIMIT 20;
```

This gives you stemming ("running" matches "run"), stop-word removal and relevance ranking. **Use
`plainto_tsquery` or `websearch_to_tsquery` for user input**, never `to_tsquery` — the latter parses
operator syntax and throws on malformed input, so a user typing `&` gets a 500.

`pg_trgm` covers typo tolerance and substring search with an index:

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX ON product USING GIN (name gin_trgm_ops);
SELECT * FROM product WHERE name % :q ORDER BY similarity(name, :q) DESC;
```

**Level 3 — a dedicated engine** (Elasticsearch, OpenSearch, Typesense, Meilisearch). Needed when you
want faceting, synonyms, per-field boosting, typo tolerance at scale, or aggregations over hundreds
of millions of documents.

The cost is honest and large: **a second data store to keep in sync**, which means an indexing
pipeline, eventual consistency between the two, reindexing procedures, and one more thing to operate.

> **Do not add a search engine until PostgreSQL full-text search has actually failed you.** For most
> products it never does — and "we run Elasticsearch for a 40,000-row product catalogue" is a common,
> expensive mistake.

**Level 4 — vector / semantic search.** Embeddings plus approximate nearest neighbour, for meaning
rather than keywords: `pgvector` in PostgreSQL, or Pinecone/Qdrant/Weaviate. The state of the art is
**hybrid** — keyword and vector results fused (reciprocal rank fusion), because pure semantic search
is poor at exact matches like part numbers and names.

## Search that behaves

- **Debounce on the client**; rate limit on the server (Day 122). A search-as-you-type box is
  otherwise one request per keystroke.
- **Minimum query length** — a one-character search matches everything.
- **Timeout the query.** A pathological search must fail in 2 seconds, not hold a connection for 60.
- **Log queries that return zero results.** That log is the highest-value product-improvement dataset
  you will ever have: it is a list of things users wanted and could not find.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Column names from user input | **SQL injection** (Day 119b) |
| Concatenating filter values | Same |
| Ignoring unknown filters silently | The client believes it scoped the query and did not |
| Client-controlled tenant filter | Cross-tenant data exposure |
| Sorting on unindexed columns | A full sort of the table, triggered by a query string |
| No sort tiebreaker | Unstable pagination (Day 107) |
| `fields` treated as authorization | `?fields=salary` bypasses a permission |
| Omitting `id` from sparse fieldsets | Unusable responses |
| Unbounded `include` depth | Join fan-out; the database goes down |
| `LIKE '%term%'` on a large table | Full scan on every search |
| `to_tsquery` on raw user input | 500 on a malformed query |
| Elasticsearch for 40,000 rows | A second data store, for nothing |
| No search timeout or minimum length | Connections held; everything matches |
| Building a query language first | You now own a parser, a permission model and an optimiser |

## Interview questions

**Q: How do you implement filtering safely?**
Allow-list the filterable fields mapping API names to columns, take operators from a closed enum, and
bind every value as a parameter. Column names and operators are the only parts that get concatenated,
so they must never come from the request. Reject unknown filters rather than ignoring them.

**Q: Why must sortable fields be allow-listed?**
The column name is concatenated into `ORDER BY`, so an open sort parameter is injection. And sorting
on an unindexed column lets a client trigger a full table sort — a DoS in a query string.

**Q: What is the difference between filtering and search?**
Filtering is exact and boolean, backed by B-tree indexes, and returns a set. Search is fuzzy and
ranked, backed by an inverted index, and returns results ordered by relevance. They need different
implementations and different parameters.

**Q: When would you introduce Elasticsearch?**
When PostgreSQL full-text search has demonstrably failed — when you need faceting, synonyms, per-field
boosting, typo tolerance at scale or very large corpora. The cost is a second data store to keep in
sync, so it is not a default.

**Q: Why is `LIKE '%term%'` a problem?**
A leading wildcard cannot use a B-tree index, so every search is a full scan. Use full-text search,
or a trigram index if substring matching is genuinely required.

**Q: Is a sparse fieldset an authorization mechanism?**
No. The allow-list must be per caller role; otherwise requesting a field you would not normally be
sent becomes a permission bypass.

**Q: How far up the filtering ladder would you go?**
Fixed parameters or simple operators by default. A query language means owning a parser, a permission
model and an optimisation problem — only worth it with a real consumer requirement.

## Mini task

1. Implement the allow-listed filter builder. Then try to inject through the field name, the operator
   and the value in turn, and confirm all three fail.
2. Add a filter with no allow-list entry and confirm you get a clean `400` rather than silence.
3. Implement sorting with a tiebreaker. Then request a sort on an unindexed column over a million
   rows and time it — that is the DoS.
4. Implement sparse fieldsets, always including `id`. Then make the allow-list role-dependent.
5. Implement `?include=` with a depth limit, and demonstrate what an unbounded one would do with a
   three-level include on a table with fan-out.
6. Build a PostgreSQL `tsvector` column with a GIN index over 100,000 rows. Compare
   `ILIKE '%term%'` and `@@ plainto_tsquery` with `EXPLAIN ANALYZE`.
7. Send `&` as a search term to both `to_tsquery` and `plainto_tsquery`. Observe the difference.
8. Add `pg_trgm` and demonstrate typo-tolerant matching with `similarity()`.
9. Add a statement timeout to your search query and prove a pathological query fails cleanly.
10. Log zero-result searches for a day of synthetic traffic and read what it tells you.

## 🎙️ Articulation drill

Two minutes: **"Design the query interface for a collection endpoint."**

Filtering with an allow-list and bind parameters, sorting restricted to indexed columns with a
tiebreaker, keyset pagination (Day 107), sparse fieldsets with a role-aware allow-list, and search as
a *separate* concern with its own index. Then the security framing that ties it together: every one
of these parameters is user input reaching your database, so each is an allow-list decision — and
sorting on an unindexed column is a denial-of-service feature you shipped on purpose.
