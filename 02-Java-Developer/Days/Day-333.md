# Day 333

**L-333** · Message queues and event-driven architecture — and the distributed monolith

**Time:** 3 hrs · **Mode:** NEW

> **⭐ A queue buys you three things: buffering, decoupling and retries. It costs you one thing —
> nobody can see the flow of your system any more.**
>
> Day 306 warned about events-for-everything inside one process. Today is the distributed version,
> where the same mistake produces a system nobody can debug — **and where the choreography versus
> orchestration decision is the one that determines which system you get.**

---

# Part 1 — ⭐ What a queue actually buys

| ⭐ Benefit | ⭐ Concretely |
|---|---|
| ⭐ **Temporal decoupling** | ⭐ the consumer can be down; work is not lost |
| ⭐ **Load levelling** | ⭐⭐ **a 10× spike becomes a longer queue instead of an outage** |
| ⭐ **Retries and DLQs** | failure handling is infrastructure, not code |
| ⭐ Spatial decoupling | the producer does not know who consumes |
| Throughput | competing consumers scale horizontally |

| ⭐ Cost | ⭐ Concretely |
|---|---|
| ⭐⭐ **The flow becomes invisible** | ⭐⭐ **no stack trace crosses a queue** |
| ⭐ Eventual consistency, everywhere | Day 331's models now apply to your business logic |
| ⭐ **Ordering is no longer free** | Day 334 |
| ⭐ Duplicates are normal | Day 335 |
| Operational surface | brokers to run, lag to monitor, DLQs to drain |

> **⭐ The load-levelling point deserves its own sentence, because it is the strongest argument for a
> queue:** a synchronous system at 3× capacity **fails**; a queued system at 3× capacity **gets
> slower and catches up**. **That converts an outage into a latency incident**, which is almost
> always the better failure.

# Part 2 — ⭐⭐ Commands vs events

| | ⭐ Command | ⭐ Event |
|---|---|---|
| ⭐ **Meaning** | ⭐ **"do this"** | ⭐ **"this happened"** |
| Naming | ⭐ imperative — `ChargeCard` | ⭐ **past tense — `PaymentCaptured`** |
| ⭐ **Handlers** | ⭐ **exactly one** | ⭐ **zero to many** |
| Can it be rejected? | ⭐ yes — it is a request | ⭐ **no — it is a fact** |
| ⭐ Coupling | sender knows the receiver's job | ⭐ **sender knows nothing** |
| Channel | ⭐ a queue (point-to-point) | ⭐ a topic (pub/sub) |

⚠️ **Conflating them is the root cause of most bad event architectures.** An "event" that exactly one
service must handle, and whose failure means the business operation did not happen, **is a command
wearing past tense** — and calling it an event means nobody owns its failure.

> **⭐ The test: if I delete every consumer, is the producer still correct?** Yes → it is an event.
> No → it is a command, and the coupling is real whether you admit it or not.

## ⭐ Thin events vs event-carried state transfer

```
⭐ THIN:  { "orderId": "abc123" }                    ⭐ consumers call back for details
⭐ FAT:   { "orderId": "abc123", "customerId": ...,
⭐          "total": 4999, "currency": "GBP", ... }   ⭐ consumers need nothing else
```

| | ⭐ Thin | ⭐ Fat (state transfer) |
|---|---|---|
| ⭐ **Callback load** | ⭐⭐ **N consumers × every event = a read storm on the producer** | ⭐ none |
| Consumer availability | ⭐ needs the producer up | ⭐ **works while the producer is down** |
| ⭐ **Staleness** | ⭐ always current | ⭐ **the snapshot at emit time — and that is usually correct** |
| ⭐ Coupling | to the API | ⭐ **to the payload schema — which must then be versioned** |
| Size | small | ⭐ large; consider a claim-check for big payloads |

> **⭐ The default is fat, and the reason is availability: a thin event makes every consumer depend
> on the producer being up at consumption time**, which throws away the decoupling you bought the
> queue for. **The payload is a snapshot of a fact, and for a fact, the value at the time is the
> correct value.**

# Part 3 — ⭐⭐ Choreography vs orchestration

```
⭐ CHOREOGRAPHY — each service reacts to events; no coordinator
   Order ──OrderPlaced──► Payment ──PaymentCaptured──► Inventory ──Reserved──► Shipping
⭐   ✓ no central dependency, easy to add a consumer
⭐   ✗⭐⭐ NOBODY can see the whole flow. It exists only as a diagram someone drew once.

⭐ ORCHESTRATION — a coordinator drives the steps
              ┌────► Payment
   Saga ──────┼────► Inventory
              └────► Shipping
⭐   ✓⭐ the flow is in ONE place: readable, testable, and it has a state machine
⭐   ✗ a central component to build and operate
```

| ⭐ Choose choreography when | ⭐ Choose orchestration when |
|---|---|
| ⭐ **Consumers are genuinely optional** — analytics, notifications, search indexing | ⭐⭐ **the steps form a business transaction that must complete** |
| The producer does not care about outcomes | ⭐ **there is compensation to run on failure** (Day 342) |
| Adding a consumer must not touch the producer | ⭐ **somebody will ask "where is order 123 stuck?"** |

> **⭐ The rule worth memorising: orchestrate transactions, choreograph notifications.** A four-step
> chain of events where every step must happen is a distributed transaction with no coordinator —
> **which means no timeout, no compensation, no status, and no answer when it stops halfway.**

⚠️ **The failure signature of over-choreography is specific and worth naming: nobody can answer
"where is order 123?"** There is no state machine, no correlation view, and the flow is reconstructed
by grepping logs across five services. **That is the distributed monolith — the debugging cost of
microservices with none of the independence.**

# Part 4 — ⭐ Operating a queue

| Concern | ⭐ Answer |
|---|---|
| ⭐⭐ **The key metric** | ⭐⭐ **consumer lag / queue depth — and its DERIVATIVE.** Growing is the alarm, not the absolute number |
| ⭐ **Poison messages** | ⭐ retry with backoff, then a **DLQ** — never retry forever |
| ⭐ **A DLQ nobody reads** | ⭐⭐ **alert on DLQ depth > 0 with an owner, or it is a data-loss bucket** |
| ⭐ Ordering vs retries | ⭐ **retrying one message out of order breaks ordering — see Day 335** |
| Idempotency | ⭐ mandatory — at-least-once is the default (Day 335) |
| ⭐ **Schema evolution** | ⭐ **add optional fields; never remove or repurpose. Consumers deploy independently** |
| Backpressure | ⭐ a bounded queue and a producer that can be told to slow down (Day 336) |

⚠️ **The consumer-lag trap:** lag of 10,000 is meaningless without the drain rate. **10,000 messages
at 5,000/s is two seconds; at 10/s it is sixteen minutes and growing.** Alert on *time to drain*, or
on lag increasing over a window — **not on a fixed count.**

## ⭐ Which broker

| | ⭐ Best at | ⭐ Weak at |
|---|---|---|
| ⭐ **Kafka** | ⭐ **high throughput, retention, replay, ordered streams** | ⭐ per-message TTL, priorities, complex routing |
| ⭐ **RabbitMQ** | ⭐ **routing, priorities, per-message TTL, request/reply** | very high throughput, replay |
| ⭐ **SQS / cloud queues** | ⭐ **zero operations, effectively infinite scale** | ⭐ no replay; FIFO variants are slower |
| Redis Streams | ⭐ already have Redis; simple (Day 209) | durability guarantees are weaker |

> **⭐ The distinguishing question: do you need to replay?** Kafka retains a log, so a new consumer
> can read history and a bug can be fixed by reprocessing. **A traditional queue deletes on
> acknowledgement, so a consumer bug means the data is gone.** That single difference decides more
> than throughput does.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Events for everything | ⭐ **the distributed monolith — no flow is visible** |
| ⭐⭐ Commands named as events | ⭐⭐ **nobody owns the failure of a step that must happen** |
| ⭐ Choreographing a business transaction | ⭐ **no coordinator means no timeout, compensation or status** |
| ⭐ Thin events by default | ⭐ a read storm, and consumers depend on the producer being up |
| Fat events with no schema versioning | one producer change breaks five consumers |
| ⭐ Alerting on absolute lag | ⭐ **meaningless without the drain rate** |
| ⭐ Retrying poison messages forever | ⭐ the queue stops moving |
| ⭐ **A DLQ with no owner or alert** | ⭐⭐ **a silent data-loss bucket** |
| Assuming exactly-once | it is at-least-once (Day 335) |
| Unbounded queues | latency debt and eventual memory death (Day 336) |
| ⭐ Choosing Kafka without needing replay or ordering | ⭐ significant operational cost for nothing |

## Interview questions

**Q: What does a queue actually buy you?**
Three things: temporal decoupling, so the consumer can be down without losing work; load levelling,
so a spike becomes a longer queue rather than an outage; and retry handling as infrastructure. The
load levelling is the strongest argument — a synchronous system at three times capacity fails,
whereas a queued one gets slower and catches up, which converts an outage into a latency incident.

**Q: Command or event — why does it matter?**
A command says "do this", has exactly one handler and can be rejected; an event says "this happened",
has any number of handlers and is a fact. The test is whether deleting every consumer leaves the
producer correct. Calling a command an event is the root of bad event architectures, because a step
that must happen now has no owner for its failure and no status anyone can query.

**Q: Choreography or orchestration?**
Orchestrate transactions, choreograph notifications. Analytics, search indexing and emails are
genuinely optional consumers and should be events nobody coordinates. A four-step chain where every
step must complete is a distributed transaction, and choreographing it means no timeout, no
compensation and no answer when someone asks where order 123 is stuck — which is exactly how you get
a distributed monolith.

**Q: Should events carry data or just an id?**
Data, by default. A thin event makes every consumer call back, which is a read storm on the producer
and reintroduces the availability coupling the queue was supposed to remove. The objection is
staleness, but an event is a fact and the values at that moment are the correct ones. The real cost
is schema versioning — the payload is now a contract, so fields get added and never removed.

**Q: How do you monitor a queue?**
Consumer lag, but as a time-to-drain rather than a count — ten thousand messages is two seconds at
five thousand a second and sixteen minutes at ten. I alert on lag increasing over a window and on
time to drain exceeding the SLO. And I alert on DLQ depth above zero with a named owner, because a
dead-letter queue nobody reads is a data-loss bucket with extra steps.

## Mini task

1. **List every event in your flagship and apply the deletion test.** Any "event" that fails it is a
   command — **rename it and give its failure an owner.**
2. ⭐ Take one multi-step flow and **draw both versions** — choreographed and orchestrated. Then
   answer, for each: *"where is order 123 stuck?"*
3. ⭐ Convert one thin event to a fat one. **Measure the callback load you removed**, then take the
   producer down and confirm the consumer still works.
4. Add an optional field to an event payload and **deploy only the producer.** Confirm old consumers
   survive. Then remove a field and watch what breaks.
5. ⭐ **Build a poison message** that always fails. Watch it block the consumer, then add backoff and
   a DLQ. **Alert on DLQ depth.**
6. ⭐ Push a 10× spike into a synchronous endpoint and then the same spike through a queue.
   **Record what fails in each case.**
7. Instrument **time-to-drain** rather than raw lag, and set an alert on the derivative.
8. ⭐ Take one flow and **trace a single request across three services.** If you cannot without
   grepping, add a correlation id (Day 182) and try again.

## 🎙️ Articulation drill

**Three minutes:** *"Order placed, payment charged, stock reserved, shipment created. How do these
services communicate?"*

**⭐ The marker: you identify this as a business transaction and orchestrate it**, then explicitly
carve off the genuinely optional parts — the confirmation email, the analytics event, the search
index update — **as choreographed events.**

**⭐ Then answer the question before it is asked: "where is order 123 stuck?"** The orchestrator has a
state machine and can tell you. **A pure event chain cannot, and that is the whole argument.**
