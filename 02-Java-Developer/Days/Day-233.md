# Part 1 — Routes and nested layouts

```
⭐⭐ FILE-BASED ROUTING — the URL mirrors the folder tree
⭐   ⭐ It is @RequestMapping expressed as directories, with one
⭐     addition Spring MVC has no equivalent for: LAYOUTS THAT
⭐     PERSIST ACROSS NAVIGATIONS.

⭐   app/
⭐     layout.tsx          ⇒ wraps EVERYTHING  (nav, providers)
⭐     page.tsx            ⇒ /
⭐     orders/
⭐       layout.tsx        ⇒ wraps /orders/*   ⭐ persists across children
⭐       page.tsx          ⇒ /orders
⭐       [id]/page.tsx     ⇒ /orders/{id}      ⭐ @PathVariable
⭐       loading.tsx       ⇒ ⭐ shown while this route's data loads
⭐       error.tsx         ⇒ ⭐⭐ CATCHES ERRORS IN THIS SUBTREE ONLY
```

| ⭐ Why nested layouts matter | |
|---|---|
| **State survives navigation** | ⭐⭐ `/orders/1` → `/orders/2` **keeps the layout mounted** — the sidebar does not re-fetch, scroll holds, an open panel stays open |
| **Per-route error boundaries** | ⭐ One broken widget takes out its subtree, not the page (Day 240) |
| **Per-route loading** | ⭐ The shell renders immediately; only the changing part shows a skeleton |

# Part 2 — ⭐⭐ The URL is state

```
⭐⭐ WHAT BELONGS IN THE URL — one question:
⭐   ⭐ "IF THE USER SENT THIS LINK TO A COLLEAGUE, SHOULD THEY SEE
⭐     THE SAME THING?"  ⇒ IF YES, IT GOES IN THE URL.

⭐   ✅ ⭐ filters, sort, page number, search query, the active tab,
⭐      the selected record
⭐   ❌ ⭐ a dropdown's open/closed, an unsent form draft, hover state
⭐   ❌ ⭐⭐ ANYTHING SENSITIVE. The URL is in your access logs, your
⭐      CDN logs, the browser history, and pasted into chat windows.
⭐      ⭐⭐ A TOKEN IN A QUERY STRING IS A LEAKED TOKEN — and it is
⭐        already in the log file your team greps daily (Day 235).
```

```jsx
const [params, setParams] = useSearchParams();
const status = params.get("status") ?? "all";     // ⭐ ?? not || (Day 215)

function setStatus(next) {
  setParams(p => { p.set("status", next); p.delete("page"); return p; });
  //                              ⭐⭐ RESET PAGE — otherwise the user
  //                              lands on page 7 of a 2-page result set
}
```

| ⭐ What you get free | |
|---|---|
| **Refresh survives** | ⭐ The filtered view is still there |
| **Shareable** | ⭐⭐ "Here's the list of failed orders" is a link, not instructions |
| **Back/forward works** | ⭐ Users expect Back to undo a filter |
| **Server-renderable** | ⭐ The server can read the params and render with data (Day 234) |

> ⭐ **`replace` vs `push`.** Typing in a search box should `replace` — otherwise every keystroke is a
> history entry and Back requires eleven presses. Changing a *filter* should `push`.

# Part 3 — ⭐⭐ Loaders kill the waterfall

```
⭐⭐ WITHOUT A LOADER — the Day 227 staircase
⭐   click link → download route chunk → mount component
⭐              → useEffect fires → fetch → render
⭐   ⇒ ⭐ THE FETCH CANNOT START UNTIL THE CODE HAS ARRIVED.

⭐⭐ WITH A LOADER — both start at the click
⭐   click link → ⭐⭐ FETCH **AND** CHUNK DOWNLOAD, IN PARALLEL
⭐              → render with data already present
⭐   ⇒ ⭐ ONE ROUND TRIP SAVED ON EVERY NAVIGATION.
```

```jsx
export async function loader({ params, request }) {
  return { order: await api(`/orders/${params.id}`, { signal: request.signal }) };
}
```

> ⭐⭐ **This is the single biggest navigation-speed win available**, and it is architectural rather
> than an optimisation. ⭐ It is the same reasoning as resolving a `@ModelAttribute` before the
> handler runs, rather than letting the view template trigger lazy loads.

# Part 4 — Code splitting and prefetch

```jsx
const Reports = lazy(() => import("./Reports"));   // ⭐ its own chunk

<Suspense fallback={<Skeleton />}>
  <Reports />
</Suspense>
```

| ⭐ Split on | Not on |
|---|---|
| ⭐⭐ **Route boundaries** — the natural seam | ⭐ Every component (hundreds of tiny chunks is slower) |
| Heavy, rarely used deps — a chart lib, a PDF viewer | ⭐ Anything above the fold |
| Admin-only sections | |

```
⭐⭐ PREFETCH ON INTENT — the trick that makes navigation feel instant
⭐   onMouseEnter / onFocus on a link ⇒ start downloading its chunk.
⭐   ⭐ The user takes ~200–300 ms to actually click — enough time
⭐     to have the chunk ready.
⭐   ⇒ ⭐ MOST ROUTERS DO THIS. Know it is happening, and that it
⭐     costs bandwidth on mobile.
```

> ⭐ **Splitting the login route away from the dashboard is the highest-value split in most apps** —
> the first page a logged-out user sees should not ship code for a page they cannot reach.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you decide what goes in the URL?"**

Give the test. **One question: if the user sent this link to a colleague, should they see the same
thing? If yes, it belongs in the URL. Filters, sort, page number, search query, active tab. Those in
`useState` instead are features I've quietly deleted — refresh loses them, they can't be shared, and
Back does the wrong thing.**

Add the security exclusion. **Nothing sensitive. The URL is in my access logs, my CDN logs and the
browser history, and it gets pasted into chat. A token in a query string is already leaked before
anyone attacks me — it's sitting in a log file my team greps daily.**

Then the architectural win. **Fetching in a route loader instead of a component removes a round trip
per navigation. Without it, the click downloads the code chunk, the component mounts, and only then
does the fetch start — it can't begin until the code arrives. With a loader they run in parallel. It's
the same reasoning as resolving model attributes before the handler runs instead of letting the view
trigger lazy loads.**

Close on the detail that shows real use. **Nested layouts matter because state survives navigation —
moving between two orders keeps the sidebar mounted and the scroll position held, which server-rendered
MVC has no equivalent for. And a search box has to `replace` rather than `push`, or every keystroke
becomes a history entry and Back takes eleven presses.**
