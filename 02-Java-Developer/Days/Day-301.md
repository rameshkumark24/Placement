# Day 301

**L-301** · The repository pattern, done properly — and where Spring Data isn't one

**Time:** 3 hrs · **Mode:** NEW

> **⭐ A repository is the illusion that your aggregates are an in-memory collection. A DAO is a
> wrapper over a table.** Most Java codebases call the second one the first.
>
> That is not pedantry: the difference decides how many repositories you have, what they return, what
> methods they expose, and whether Day 305's aggregate boundaries survive contact with the database.

---

# Part 1 — ⭐ Repository vs DAO

| | ⭐ Repository | DAO |
|---|---|---|
| ⭐ **Unit** | ⭐ **one aggregate** | one table |
| Language | ⭐ domain terms — `findOverdue()` | data terms — `selectWhereStatus(int)` |
| Returns | ⭐ **domain objects** | rows, entities |
| ⭐ **Count in a system** | ⭐ **few — one per aggregate root** | ⭐ many — one per table |
| Mental model | ⭐ a collection you already have | ⭐ a database you must query |
| Leaks persistence? | ⭐ **no — that is its job** | yes, by design |

**⭐ The collection illusion is the whole idea:**

```java
Order order = orders.byId(id);      // ⭐ as if it were already in memory
order.ship();                       // ⭐ just call the method
orders.save(order);                 // ⭐ put it back
```

**⭐ Two consequences fall straight out of "one per aggregate", and both are practical:**

- ⭐ **No `OrderLineRepository`.** An order line is reached through its order. If you can load one
  independently, it is not part of the aggregate — and Day 305 will make you defend that.
- ⭐ **The repository saves the whole aggregate**, not the root row. Cascade, or an explicit save of
  the children — but one call, one consistency boundary, one transaction.

# Part 2 — ⭐⭐ Where `JpaRepository` stops being a repository

```java
public interface OrderRepository extends JpaRepository<Order, Long> { }
```

**⭐ You just handed every caller in the system: `findAll()`, `deleteAll()`, `flush()`,
`saveAndFlush()`, `getReferenceById()`, `findAll(Pageable)`, `findAll(Example)`, and — with
`JpaSpecificationExecutor` — the ability to compose arbitrary queries from anywhere.**

| Leak | ⭐ Consequence |
|---|---|
| ⭐ **`deleteAll()` / `deleteAllInBatch()`** | ⭐ on the public API of your domain, for everyone |
| ⭐ **`Pageable`, `Sort`, `Example`, `Specification`** | ⭐ **Spring Data types in your application layer — Day 300's rule, broken** |
| `flush()`, `saveAndFlush()` | ⭐ persistence-context mechanics (Day 162) leaking to use cases |
| ⭐ **`getReferenceById()`** | returns a proxy that throws later, elsewhere |
| ⭐ **Derived query names** | ⭐ `findByStatusAndCreatedAtBefore` — **the caller now expresses the rule** |

**⭐ That last one is the real damage, and it is subtle:**

```java
// ⭐ The rule "an order is overdue if it is unpaid for 30 days"
// ⭐ is now WRITTEN AT EVERY CALL SITE:
repo.findByStatusAndCreatedAtBefore(PENDING, now().minusDays(30));   // ⭐ in the batch job
repo.findByStatusAndCreatedAtBefore(PENDING, now().minusDays(30));   // ⭐ in the report
repo.findByStatusAndCreatedAtBefore(PENDING, now().minusDays(45));   // ⭐ ← and here it drifted
```

```java
// ⭐ The repository owns the concept. One definition. One place to change.
List<Order> findOverdue(Clock clock);
```

> **⭐ Derived query methods are Day 298's connascence of meaning, distributed across the codebase.**
> The `30` is a business rule sitting in three call sites, and nothing links them.

## ⭐ The fix — the interface is yours, Spring Data is the adapter

```java
// ⭐ application/ — the PORT. Domain language. No Spring types.
public interface Orders {
    Optional<Order> byId(OrderId id);
    List<Order> overdue(Instant asOf);
    void save(Order order);
}

// ⭐ adapter/out/persistence/ — the ADAPTER. Package-private.
@Repository
class JpaOrders implements Orders {

    private final OrderJpaRepository jpa;      // ⭐ Spring Data, hidden in here
    private final OrderMapper mapper;

    public Optional<Order> byId(OrderId id) {
        return jpa.findById(id.value()).map(mapper::toDomain);
    }

    public List<Order> overdue(Instant asOf) {
        return jpa.findByStatusAndCreatedAtBefore(PENDING, asOf)   // ⭐ the rule lives HERE
                  .stream().map(mapper::toDomain).toList();
    }

    public void save(Order order) { jpa.save(mapper.toEntity(order)); }
}

interface OrderJpaRepository extends JpaRepository<OrderEntity, Long> { ... }  // ⭐ package-private
```

**⭐ Three things this buys**, each concrete:

1. ⭐ **Callers see six methods, all in domain language.** Nobody can call `deleteAll()`.
2. ⭐ **You can swap the implementation for a test double** — a `HashMap`-backed `Orders` makes
   application-layer tests run in milliseconds without Testcontainers.
3. ⭐ **The `30 days` rule exists once.**

**⭐ The cost, stated honestly:** an extra interface, a mapper, and you give up ad-hoc derived queries
at call sites. **For CRUD modules that trade is bad and you should use `JpaRepository` directly** —
Day 300's per-module decision, applied again.

# Part 3 — ⭐ The four traps

## ⭐ Trap 1 — `save()` inside a transaction is a lie

```java
@Transactional
public void ship(OrderId id) {
    Order order = orders.byId(id).orElseThrow();
    order.ship();
    orders.save(order);            // ⭐ with JPA entities: does NOTHING. Dirty checking already did it.
}                                  // ⭐ with a domain model + mapper: REQUIRED.
```

**⭐ This is the most confusing thing about repositories in Spring**, and both behaviours are
defensible — but you must know which one you have:

| Model | `save()` | ⭐ Risk |
|---|---|---|
| JPA entity as domain object | ⭐ redundant (Day 162's dirty checking) | ⭐ **a forgotten `save()` still persists — so the code lies, and it breaks the day you move to a real domain model** |
| ⭐ **Separate domain + mapper** | ⭐ **required** | ⭐ **a forgotten `save()` silently loses the change** |

> **⭐ Always call `save()` explicitly, regardless.** It costs nothing under dirty checking and it
> makes the write visible at the call site — which is the only version of the code that survives a
> later refactor.

## ⭐ Trap 2 — the repository that returns entities

**If `Orders.byId` returns an `@Entity`, the persistence model is in the application layer**, and with
it lazy proxies, `LazyInitializationException` outside the transaction (Day 160), and Day 147's
serialization hazards. **The port's return type is the boundary. Guard it with an ArchUnit rule.**

## ⭐ Trap 3 — one repository per table

```
⭐ OrderRepository  OrderLineRepository  OrderAddressRepository  OrderStatusHistoryRepository
```

**⭐ Four repositories for one aggregate means four ways to modify an order without going through
`Order`** — so the invariants in `Order` are advisory. This is Day 299's Rot 2 arriving through the
persistence layer instead of the service layer.

## ⭐ Trap 4 — pagination, which genuinely does not fit

**⭐ A collection illusion has no natural notion of a page.** Three options, in order of preference:

| Option | ⭐ Verdict |
|---|---|
| ⭐ **Your own `Page`/`Slice` type in the application layer** | ⭐ **clean, small, worth it** |
| ⭐ **Bypass the repository for list/query reads** | ⭐ **best for reporting — Day 300's read exception** |
| Accept `Pageable` in the port | pragmatic; you have coupled to Spring Data, so say so |

**⭐ And keyset pagination (Day 107) does not fit the interface at all**, which is another argument for
reads bypassing the repository entirely: **queries want a query language, not a collection.**

# Part 4 — ⭐ Testing, and the in-memory repository

```java
class InMemoryOrders implements Orders {                 // ⭐ ~20 lines
    private final Map<OrderId, Order> store = new ConcurrentHashMap<>();
    public Optional<Order> byId(OrderId id) { return Optional.ofNullable(store.get(id)); }
    public void save(Order o) { store.put(o.id(), o); }
    public List<Order> overdue(Instant asOf) {
        return store.values().stream().filter(o -> o.isOverdue(asOf)).toList();
    }
}
```

| | ⭐ In-memory fake | Mockito mock | ⭐ Testcontainers (Day 184) |
|---|---|---|---|
| Speed | ⭐ instant | instant | ⭐ slow-ish |
| ⭐ **Behaviour** | ⭐ **real** | ⭐ **whatever you stubbed** | ⭐ **real, including SQL** |
| Catches | logic bugs | ⭐ almost nothing | ⭐ **mapping, constraints, N+1, locking** |
| Use for | ⭐ **application-layer tests** | ⭐ rarely — prefer a fake | ⭐ **the adapter itself** |

> **⭐ The rule: fake the port for use-case tests, and test the adapter against a real database.**
> Mocking a repository to assert `verify(repo).save(any())` tests that you wrote the line you wrote.

⚠️ **The fake must be tested against the same contract as the real one.** A shared abstract test class
run against both implementations — a *contract test* — is the thing that stops your fake from
drifting into a more forgiving database than the real one.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Extending `JpaRepository` publicly | ⭐ `deleteAll()` and `Specification` on your domain API |
| ⭐ Derived query names at call sites | ⭐ **the business rule is duplicated and drifts** |
| Returning entities from the port | Day 160's lazy proxies escape the transaction |
| ⭐ One repository per table | ⭐ four ways past the aggregate's invariants |
| ⭐ Omitting `save()` because dirty checking covers it | ⭐ correct today, silently wrong after the refactor |
| ⭐ `Pageable` in a domain port | Spring Data types inside the hexagon |
| ⭐ Mocking repositories in use-case tests | ⭐ asserts the code you wrote, catches nothing |
| A fake with no contract test | it diverges into a friendlier database |
| Repository methods that take SQL fragments | the abstraction is gone, keep the DAO instead |

## Interview questions

**Q: What is the difference between a repository and a DAO?**
A repository gives the illusion of an in-memory collection of aggregates and speaks the domain's
language; a DAO wraps a table and speaks the data's. The practical difference is count and
granularity — one repository per aggregate root, not per table — because a repository per table gives
callers a way around the aggregate's invariants.

**Q: Is Spring Data's `JpaRepository` a repository in that sense?**
Not as usually exposed. Extending it publicly puts `deleteAll`, `flush`, `Specification` and
`Pageable` on your domain API, and derived query names push business rules like "overdue means 30
days" into every call site. I define a small interface in domain terms and let a package-private
Spring Data repository be the adapter behind it — for the modules that have real rules. For CRUD
modules I use it directly and say so.

**Q: Do you need to call `save()` inside a transaction?**
With JPA entities as the model, no — dirty checking flushes at commit. I still call it, because it
costs nothing, makes the write visible at the call site, and is mandatory the moment there is a
separate domain model with a mapper. Relying on the implicit behaviour is a bug waiting for a
refactor.

**Q: How do you test code that uses a repository?**
An in-memory fake for use-case tests, and the real database via Testcontainers for the adapter. I
avoid mocking repositories — `verify(repo).save(any())` only asserts that I wrote the line I wrote. I
run one shared contract test against both the fake and the real adapter so the fake cannot drift into
a more permissive database.

**Q: How do you handle pagination without leaking Spring Data?**
Either a small `Page` type of my own, or — usually better — reads bypass the repository entirely.
Listing, filtering and reporting have no invariants to protect, so a projection query is both faster
and more honest than pretending a collection has pages. Keyset pagination in particular has no
sensible collection-shaped interface.

## Mini task

1. Take one aggregate. **Write the port** — six methods maximum, all in domain language, **no Spring
   types**.
2. Make the Spring Data interface **package-private** behind the adapter. Fix the compile errors:
   **each one is a caller that was reaching past your domain.**
3. **Grep for derived query methods across the codebase.** For each, ask: *is there a business rule in
   this method name?* Move those into the repository as named concepts.
4. Write the **in-memory fake** and a **contract test** run against both it and the real adapter.
5. ⭐ **Find a place where the same rule is expressed as two different derived queries with different
   constants.** (In a codebase of any size, there is one.)
6. Delete an `orders.save(order)` inside a transaction and confirm the change still persists. **Now
   write the comment you would need if you kept it deleted** — then put the call back.
7. Count repositories. **If it is more than your aggregate count, you have DAOs** — list which
   invariants they let callers bypass.
