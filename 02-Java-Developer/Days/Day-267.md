# Day 267 🏗️

**P-267** · File uploads — presigned URLs, and the eight ways this goes wrong

**Time:** 3 hrs · **Mode:** BUILD

> Day 126 established the pattern: **the file never touches your application.** Today you build it,
> and the reason it earns a full day is that **file upload is one of the densest security surfaces in
> a web application** — path traversal, content-type spoofing, stored XSS, SSRF, zip bombs and
> resource exhaustion all live here.
>
> **⭐ If your project has no file upload, build one anyway.** An avatar or an attachment is enough,
> and the security reasoning is worth more than the feature.

---

# Part 1 — ⭐ Why the file must not touch your application

```
❌ multipart POST → your app → validate → store
⭐ POST /uploads (metadata) → your app returns a PRESIGNED URL
⭐ Client PUTs the bytes DIRECTLY to object storage
⭐ Client POSTs /uploads/{id}/complete → your app verifies and records
```

**⭐ Four reasons the naive version fails** (Day 126):

| Reason | Detail |
|---|---|
| ⭐ **A thread per upload** | ⭐ a 50 MB upload on a slow mobile connection holds a Tomcat thread for minutes (Day 145) |
| ⭐ **Memory and disk** | multipart buffering; a handful of concurrent uploads exhausts either |
| ⭐ **It does not scale** | your application is now sized by bandwidth, not by logic |
| ⭐ **A connection is held** | ⭐ with `open-in-view: true` it would hold a database connection too |

**⭐ The presigned URL moves all of it to object storage**, which is built for exactly this. **Your
application handles metadata and authorization — bytes are someone else's problem.**

## ⭐ The three-step flow, and what each step must do

```
⭐ 1. INITIATE   — ⭐ AUTHORIZE, validate declared type and size, create a PENDING record,
                    return a presigned PUT valid for ~5 minutes with a CONSTRAINED key
⭐ 2. UPLOAD     — client → storage directly. Your application is not involved.
⭐ 3. COMPLETE   — ⭐ VERIFY the object exists, ⭐ verify its real size and type,
                    ⭐ scan it, then mark the record READY
```

**⭐ Step 3 is not optional and it is the step people omit.** Without it, a client can initiate,
never upload, and leave a `PENDING` row forever — or upload something entirely different from what it
declared. **The record is only trustworthy after your application has looked at the stored object.**

**⭐ And a cleanup job** (Day 264) removes `PENDING` records older than an hour, plus their orphaned
objects. **Every upload flow accumulates orphans; only a job removes them.**

# Part 2 — ⭐⭐ The eight security failures

### ⭐⭐ 1. Path traversal in the key

```
❌ key = "uploads/" + userProvidedFilename       ⭐ "../../../config/secrets.json"
⭐ key = "uploads/" + tenantId + "/" + UUID + extensionFromAllowList
```

> **⭐⭐ Never let the client influence the storage key.** Generate it entirely server-side. The
> original filename is *metadata in your database*, never part of a path.

### ⭐⭐ 2. Content-type spoofing

```
❌ Trusting the Content-Type header or the file extension
⭐ Sniff the MAGIC BYTES of the stored object, and reject if it disagrees with the declaration
```

**⭐ A `.jpg` that is actually an HTML file with a script tag becomes stored XSS the moment a browser
renders it.** Apache Tika or a magic-byte check on the first bytes is the defence.

### ⭐⭐ 3. Stored XSS on download

```
⭐ Content-Disposition: attachment; filename="..."
⭐ X-Content-Type-Options: nosniff
⭐ Serve user content from a SEPARATE ORIGIN
```

**⭐ The separate origin is the strongest control**: even if an HTML file is served, it runs in an
origin with no access to your cookies or your API (Day 155's same-origin policy working *for* you).

### ⭐ 4. Size limits at three layers

```
⭐ 1. The presigned URL's content-length-range condition   ← ⭐ storage enforces it
⭐ 2. Your application's declared-size check on initiate
⭐ 3. Verification of the ACTUAL size on complete
```

**⭐ Layer 1 is the one that matters**, because it is enforced by the storage service before a byte
reaches anything you pay for. **Without it, a client can PUT a 10 GB file to a presigned URL you
issued for a 2 MB avatar.**

### ⭐ 5. Zip bombs and decompression

**⭐ If you process archives or images: bound the *decompressed* size, not the compressed one.** A
42 KB zip can expand to petabytes; a small malicious PNG can allocate gigabytes in a decoder.

### ⭐ 6. SSRF via "import from URL"

**⭐ If you offer fetch-by-URL, it is Day 119's SSRF**: block private ranges, link-local
(`169.254.169.254` — cloud metadata), redirects to private ranges, and **resolve DNS then validate
the resolved IP** rather than the hostname.

### ⭐ 7. Authorization on download

```
⭐ A presigned GET, short-lived, ⭐ issued only after an ownership check
❌ A public bucket, or a guessable URL
```

**⭐ "Unguessable URL" is not authorization.** URLs leak — via referrers, browser history, shared
links, logs.

### ⭐ 8. Malware scanning

**⭐ Scan before marking `READY`**, asynchronously (Day 265) with the record in a `SCANNING` state.
**A file that has not been scanned must not be downloadable** — which means the state machine has
four states, not two.

# Part 3 — ⭐ The data model and the state machine

```
⭐ uploads: id, public_id, tenant_id, owner_id,
            storage_key,           ⭐ generated server-side
            original_filename,     ⭐ metadata only — NEVER used in a path
            declared_type, ⭐ verified_type, declared_size, ⭐ verified_size,
            checksum, status, created_at, completed_at
```

```
⭐ PENDING ──complete──► SCANNING ──clean──► READY
     │                       └──infected──► QUARANTINED
     └──expire (1h)──► ABANDONED   ⭐ the cleanup job (Day 264)
```

**⭐ Day 187's rule applies: encode the invariants as check constraints.**

```
⭐ READY implies verified_type is not null and checksum is not null
⭐ Only READY uploads may be downloaded — ⭐ enforced in the QUERY, not in a service check
```

**⭐ And Day 259's rule: the download query is scoped by owner and tenant**, so authorization is a
`WHERE` clause rather than a guard you can forget.

## ⭐ Idempotency and retries

**⭐ Day 123 applies: a client that times out on `complete` will retry.** Make it idempotent — the
same upload id completed twice returns the same result and does not re-scan or duplicate.

## ⭐ Deletion, and the orphan problem in both directions

| Direction | Problem |
|---|---|
| ⭐ **Delete the row, not the object** | ⭐ storage grows forever and you pay for it |
| ⭐ **Delete the object, not the row** | ⭐ a broken link and a 404 the user cannot understand |

**⭐ The correct order: mark the row deleted, then delete the object asynchronously — via the
outbox** (Day 263), so a crash between the two does not orphan anything. **This is a genuinely good
example of why the outbox exists**, and worth pointing at in an interview.

# Part 4 — ⭐ Test it as an attacker

**⭐ These eleven are the deliverable. Each corresponds to a failure above.**

```
⭐ 1.  filename "../../etc/passwd"        → ⭐ the storage key is unaffected
⭐ 2.  A .jpg containing HTML + <script>  → ⭐ REJECTED on complete (magic bytes)
⭐ 3.  Download that file if it slipped   → ⭐ Content-Disposition + nosniff prevent rendering
⭐ 4.  PUT 10 GB to a 2 MB presigned URL  → ⭐ REJECTED BY STORAGE
⭐ 5.  A zip bomb                          → ⭐ bounded, rejected
⭐ 6.  Import from http://169.254.169.254 → ⭐ blocked (Day 119)
⭐ 7.  Download another tenant's upload    → ⭐ 404
⭐ 8.  Download a SCANNING upload          → ⭐ 404
⭐ 9.  Reuse an expired presigned URL      → ⭐ rejected by storage
⭐ 10. Complete the same upload twice      → ⭐ idempotent
⭐ 11. Initiate and never upload           → ⭐ the cleanup job removes it
```

**⭐ Test 4 is the most satisfying to demonstrate**, because the rejection comes from the storage
service before your application is involved at all — which is the whole point of the pattern.

## ⭐ Metrics and limits

```
⭐ uploads_initiated_total, uploads_completed_total, uploads_abandoned_total
⭐ uploads_rejected_total{reason="type|size|scan"}    ← ⭐ by reason
⭐ upload_bytes_total per tenant                       ← ⭐ quota enforcement
```

**⭐ Rate-limit initiation** (Day 208): unlimited presigned URLs is unlimited storage cost, and it is
a trivially exploitable one because issuing a URL is cheap for you and free for the attacker.

**⭐ And enforce a per-tenant quota**, checked at initiate. Storage cost is the one resource in your
project that grows without any corresponding load.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Uploading through the application | threads and memory held; does not scale |
| ⭐⭐ **Client-influenced storage key** | ⭐⭐ path traversal |
| ⭐ Trusting `Content-Type` or the extension | ⭐ stored XSS |
| Serving user content from your origin | XSS with access to your cookies |
| ⭐ No `content-length-range` on the presigned URL | ⭐ a 2 MB URL accepts 10 GB |
| ⭐ Never verifying on complete | ⭐ the record describes a file that is not there |
| No cleanup job | orphaned rows and orphaned objects, forever |
| ⭐ Unbounded decompression | zip bomb |
| Fetch-by-URL without SSRF defence | cloud metadata credentials (Day 119) |
| ⭐ "Unguessable URL" as authorization | URLs leak |
| ⭐ Downloadable before scanning | malware distribution |
| Deleting the row but not the object | unbounded storage cost |
| ⭐ Deleting both without the outbox | orphans on a crash |
| No rate limit on initiate | unlimited storage cost |
| No per-tenant quota | one tenant's cost is everyone's |

## ⭐ Self-review

- [ ] ⭐ **Bytes never pass through the application** — presigned PUT
- [ ] ⭐ **The storage key is generated server-side**; the filename is metadata only
- [ ] ⭐ **Magic-byte verification on complete**; declared type rejected if it disagrees
- [ ] ⭐ Downloads: `Content-Disposition: attachment`, `nosniff`, ⭐ **a separate origin**
- [ ] ⭐ **Size bounded in the presigned URL**, and verified on complete
- [ ] Decompression bounded; SSRF blocked on any fetch-by-URL
- [ ] ⭐ **Download authorization is a `WHERE` clause**, scoped by owner and tenant
- [ ] ⭐ Four-state machine with **check constraints**; only `READY` is downloadable
- [ ] ⭐ Complete is **idempotent**; ⭐ a cleanup job removes abandoned uploads and orphans
- [ ] ⭐ Deletion via the **outbox**, so neither side orphans
- [ ] ⭐ **All eleven attack tests pass**
- [ ] Metrics by rejection reason; ⭐ **initiate rate-limited**; per-tenant quota enforced

## 🎤 Defence questions

1. **⭐ Why doesn't the file go through your application?**
2. **⭐ Where does the storage key come from, and why not the filename?**
3. **⭐ A user uploads `photo.jpg` containing HTML and a script tag. What happens?**
4. **⭐ How do you stop a 10 GB upload to a URL you issued for 2 MB?**
5. **⭐ What stops someone downloading another tenant's file?**
6. **⭐ What happens to an upload that is initiated and never completed?**
7. **⭐ How do you delete a file without orphaning the row or the object?**
8. **What is your defence against a zip bomb, and against SSRF?**

## ✅ Done when

- ⭐ All eleven attack tests pass
- ⭐ The 10 GB rejection is demonstrated coming **from storage**, not your code
- ⭐ The cleanup job removes both abandoned rows and orphaned objects
