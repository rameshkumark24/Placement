# Day 192

**L-192** · Join algorithms — three strategies, and why the planner picks wrong

**Time:** 3 hrs · **Mode:** NEW

> D-08 covered join *types* — inner, left, full, semi, anti — which is what the result contains.
> Today is join **algorithms** — *how* the rows are matched — which is what the query costs.
>
> Day 191 showed that the classic disaster plan is a nested loop with a large outer side. Today is
> why that is so bad, when each algorithm is correct, and how to give the planner what it needs to
> choose properly.

---

# Part 1 — The three algorithms

## ⭐ Nested Loop

```
for each row R in OUTER:
    for each matching row S in INNER:      ⭐ ideally an index lookup
        emit (R, S)
```

**Cost ≈ outer_rows × cost_of_one_inner_lookup.**

| | |
|---|---|
| ⭐ **Best when** | ⭐ **the outer side is small and the inner side is indexed on the join key** |
| Catastrophic when | ⭐ the outer side is large — 1M outer rows × a 0.5 ms lookup = **8 minutes** |
| Startup cost | ⭐ **zero** — first row emitted immediately, so it is ideal with `LIMIT` |

**⭐ The `LIMIT` property is why the planner reaches for it**: with `order by ... limit 10`, a nested
loop can stop after ten matches while a hash join must build its entire hash table first.

## ⭐ Hash Join

```
1. BUILD:  read the smaller side entirely, hash it on the join key   ⭐ needs work_mem
2. PROBE:  scan the larger side, look each row up in the hash table  ⭐ O(1) per row
```

| | |
|---|---|
| ⭐ **Best when** | ⭐ **joining two large sets on equality, and the smaller fits in `work_mem`** |
| Requires | ⭐ **an equality condition** — cannot do `<`, `>` or ranges |
| Startup cost | ⭐ high — nothing emitted until the build completes |
| Fails badly when | ⭐ the build side exceeds `work_mem` → **batches** (Day 191) |

```
Hash  (actual rows=2000000 loops=1)
  ⭐ Buckets: 65536  Batches: 16  Memory Usage: 4096kB
```

**⭐ `Batches: 16` means the hash table was split into 16 disk-backed passes.** Both sides get written
to and read from disk. `Batches: 1` is what you want, and it is usually one `work_mem` change away.

## Merge Join

```
1. Sort both sides on the join key (or read them already sorted from an index)
2. Walk both in lockstep — like merging two sorted lists
```

| | |
|---|---|
| **Best when** | ⭐ both sides are **already sorted** — index order or a prior sort |
| Also handles | range join conditions, unlike hash |
| Cost | ⭐ the sort dominates if the inputs are not already ordered |
| Nice property | output is sorted, so a later `ORDER BY` may be free |

**⭐ In practice merge joins are rarer than the other two**, because the sort usually costs more than
hashing. They appear when an index already provides the order — which is another payoff from
Day 190's rule 3.

# Part 2 — ⭐ How the planner chooses, and how it goes wrong

**The planner estimates the cost of every viable plan and picks the cheapest.** The estimate depends
on:

1. ⭐ **estimated row counts** from `pg_statistic`,
2. cost constants — `seq_page_cost`, `random_page_cost`, `cpu_tuple_cost`,
3. `work_mem` — whether a hash or sort fits.

> **⭐ The algorithm choice is downstream of the row estimate. Get the estimate wrong and the
> algorithm choice is wrong, and that is where nearly all bad join plans come from.**

## ⭐ The disaster, concretely

```
Nested Loop  (actual time=0.045..487213.334 rows=982341 loops=1)     ⭐ 8 minutes
  ->  Seq Scan on customers  (⭐ rows=1) (⭐ actual rows=982341 loops=1)
        Filter: (country = 'UK' and signup_date > '2020-01-01')
  ->  Index Scan using ix_orders_customer on orders
        (actual time=0.412..0.489 ⭐ loops=982341)
```

**The planner estimated 1 outer row**, so a nested loop looked free. **There were 982,341** — and now
it is doing a million index lookups. Day 191's Rule 1 and Rule 2 in one plan.

**⭐ Why the estimate was wrong: correlated columns.** `country = 'UK'` and `signup_date > '2020'`
were multiplied as if independent (Day 190). The fix is not to force a hash join — it is to fix the
estimate:

```sql
create statistics stx_customers (dependencies, ndistinct) on country, signup_date from customers;
analyze customers;
```

**⭐ Fix the estimate, not the plan.** A forced plan is correct for today's data and wrong when the
distribution changes; a fixed estimate keeps the planner making good decisions as the data evolves.

## ⭐ `random_page_cost` — the one cost constant worth changing

```sql
-- default assumes spinning disks: random I/O 4× the cost of sequential
random_page_cost = 4.0
-- ⭐ on SSD/NVMe, random and sequential are close
random_page_cost = 1.1
```

**⭐ The default is a 1990s hard-disk assumption**, and on SSDs it makes the planner systematically
*undervalue* index scans — preferring sequential scans and hash joins where an index nested loop
would win. **Setting `random_page_cost = 1.1` on SSD-backed storage is one of the highest-value
one-line changes available**, and it is still the default in a great many production databases.

`effective_cache_size` matters too — it tells the planner how much data is likely cached (OS cache
included), and setting it to ~75% of RAM makes index scans look correctly cheaper.

# Part 3 — ⭐ Diagnosing and influencing join plans

## The diagnostic switches

```sql
set enable_nestloop = off;      -- ⭐ "what would you do instead, and is it faster?"
set enable_hashjoin = off;
set enable_mergejoin = off;
```

**These are questions, not fixes** (Day 191). If disabling the nested loop makes the query 50× faster,
**you have learned the planner's cost model is wrong for this query** — and the remedy is statistics
or cost constants, not the switch. Never leave one on in production; a switch that helps today
produces a terrible plan when the data changes.

## Anti-joins, and the `NOT IN` trap

```sql
-- ❌ NOT IN with a nullable column: if ANY value is NULL, the result is EMPTY
select * from customers where id not in (select customer_id from orders);

-- ⭐ NOT EXISTS: null-safe, and plans as an efficient Anti Join
select * from customers c where not exists (select 1 from orders o where o.customer_id = c.id);

-- ⭐ also fine, also an Anti Join
select c.* from customers c left join orders o on o.customer_id = c.id where o.id is null;
```

**⭐ `NOT IN` with a nullable subquery column is a correctness bug, not just a performance one** —
D-07's three-valued logic, because `x NOT IN (1, NULL)` is `UNKNOWN`, never `TRUE`. It also usually
plans worse. **Use `NOT EXISTS`.**

Look for `Anti Join` and `Semi Join` in the plan — those are the efficient forms, and seeing them
confirms the rewrite worked.

## ⭐ Join order, and the planner's limit

```sql
join_collapse_limit = 8      -- ⭐ default
from_collapse_limit = 8
```

**⭐ Beyond 8 joined tables the planner stops considering all orderings** — the search space is
factorial — and joins them roughly in the order written. **So a 12-table query's performance can
depend on how you typed it**, which is a genuinely surprising fact.

**Options:** raise the limit (planning time grows fast), use `geqo` (the genetic optimiser, which is
already on by default beyond `geqo_threshold`), or — usually best — **break the query up with CTEs
or restructure it.** A 12-table join is often a reporting query that should be a materialized view
(Day 188).

## ⭐ CTEs are no longer optimisation fences

```sql
with recent as (select * from orders where placed_at > now() - interval '7 days')
select * from recent join customers using (customer_id);
```

**⭐ Before PostgreSQL 12, a CTE was always materialised** — an optimisation fence that people used
deliberately and were also bitten by. **From 12 onward it is inlined when referenced once**, so plans
changed on upgrade.

```sql
with recent as materialized     (...)     -- ⭐ force the old behaviour
with recent as not materialized (...)     -- ⭐ force inlining
```

**`materialized` is occasionally the right tool** — when a CTE is expensive and referenced several
times, computing it once beats inlining it three times. Knowing that the default changed is a good
interview detail.

# Part 4 — The application-side connection

## ⭐ This is Day 160's N+1, in the plan

```
loops=1000  on the inner index scan
```

**⭐ A nested loop with 1,000 loops *is* an N+1 — executed by the database instead of by
Hibernate.** The difference is enormous, though: one round trip and one plan, versus 1,000 round
trips. **The database doing 1,000 index lookups internally is often 100× faster than your application
issuing 1,000 queries**, because the network is the dominant cost (Day 160).

That is worth stating in an interview: **a join is almost always better than fetching in a loop, even
when the join plans as a nested loop.**

## Making the planner's job easy

| Do | Why |
|---|---|
| ⭐ **Index every foreign key** | Day 189 — a nested loop needs the inner side indexed |
| ⭐ **Filter early** | fewer rows into the join |
| **`ANALYZE` after bulk loads** | Day 189 #6 |
| ⭐ **`CREATE STATISTICS` on correlated columns** | Day 190 |
| **`random_page_cost = 1.1` on SSD** | stop undervaluing indexes |
| Avoid joining on expressions | `on lower(a.x) = lower(b.y)` needs matching expression indexes |
| ⭐ **Avoid joining on different types** | a cast blocks index use (Day 189 #2) |

## `work_mem` for joins

```sql
set work_mem = '256MB';        -- ⭐ session-level, for one heavy report
```

**⭐ Per operation, per connection** (Day 191). A hash join, a sort and an aggregate in one query is
three allocations. Raise it for the specific report; never globally.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Nested loop with a large outer side | thousands of index lookups; minutes |
| Fixing the plan instead of the estimate | correct today, wrong when data shifts |
| ⭐ Leaving `enable_nestloop = off` on | a diagnostic used as a remedy |
| ⭐ `random_page_cost = 4` on SSD | index scans systematically undervalued |
| `effective_cache_size` at its default | same effect |
| ⭐ `NOT IN` on a nullable column | returns nothing — a correctness bug |
| 12-table joins | the planner stops exploring orderings |
| Assuming CTEs are fences | changed in PostgreSQL 12 |
| Unindexed foreign keys | nested loops have no inner index |
| Joining on mismatched types | cast blocks the index |
| `work_mem` global | multiplied by connections and operations |
| Hash join with `Batches: 16` unnoticed | both sides spilled to disk |

## Interview questions

**Q: Name the three join algorithms and when each is right.**
Nested loop when the outer side is small and the inner is indexed on the join key — it also has zero
startup cost, so it is ideal with `LIMIT`. Hash join for two large sets on an equality condition,
provided the build side fits in `work_mem`. Merge join when both inputs are already sorted, typically
from an index, and it is the only one besides nested loop that handles range conditions.

**Q: A query does a nested loop with a million outer rows. What happened?**
The planner underestimated the outer row count — usually stale statistics or correlated columns
multiplied as if independent. The fix is the estimate, not the plan: `ANALYZE`, or extended
statistics on the correlated columns. Forcing a hash join is correct for today's data and wrong when
the distribution changes.

**Q: What is `random_page_cost` and why does the default matter?**
It is the planner's estimate of a random page read relative to a sequential one, and the default of
4.0 assumes spinning disks. On SSDs the real ratio is close to 1, so the default makes the planner
systematically avoid index scans. Setting it to about 1.1 is a one-line change with a large effect,
and it is still at the default in many production systems.

**Q: `NOT IN` or `NOT EXISTS`?**
`NOT EXISTS`. `NOT IN` against a nullable column returns no rows at all, because `x NOT IN (1, NULL)`
evaluates to unknown rather than true — that is a correctness bug, and it usually plans worse as
well.

**Q: Is a nested loop with 1,000 loops the same as an N+1?**
Structurally yes, and it is still far better, because it is one round trip and one plan rather than a
thousand. Network latency dominates in the application version, which is why a join is almost always
better than fetching in a loop even when it plans as a nested loop.

## Mini task

**One million customers, ten million orders.**

1. Write a join that plans as each of the three algorithms. **Capture all three plans.**
2. Force each of the other two with the `enable_*` switches and compare times and buffers.
3. Build the disaster: correlated `country`/`signup_date` filters producing a nested loop over a
   million outer rows. **Time it.** Add extended statistics. Re-run.
4. Set `random_page_cost = 4` then `1.1` on the same query. **Find one query whose plan changes.**
5. Force a hash join with `work_mem = '256kB'`. Find `Batches: N`. Raise it to `Batches: 1` and
   compare.
6. Write `NOT IN` against a nullable column and confirm **zero rows returned.** Rewrite as
   `NOT EXISTS` and find `Anti Join` in the plan.
7. Build a 10-table join. Reorder the `FROM` clause and compare plans. Then set
   `join_collapse_limit = 12` and compare again.
8. Write a CTE referenced three times. Compare `materialized` and `not materialized`.
9. Drop the index on a foreign key and re-run a join. **Watch the nested loop become a hash join or a
   disaster.**
10. Compare: 1,000 application queries in a loop, versus one join planning as a nested loop with
    `loops=1000`. **Time both.** Write the numbers down.
