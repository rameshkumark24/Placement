# L-009 · TLS and HTTPS

## What TLS actually gives you

**HTTPS is HTTP running inside a TLS tunnel.** Nothing about HTTP changes — same methods, same
headers, same text. TLS sits between TCP and HTTP and encrypts the payload.

```
   ┌──────────────────────────────┐
   │  HTTP    GET /account …      │  ← unchanged
   ├──────────────────────────────┤
   │  TLS     encrypt + auth      │  ← the new layer
   ├──────────────────────────────┤
   │  TCP     port 443            │
   ├──────────────────────────────┤
   │  IP                          │
   └──────────────────────────────┘
```

TLS provides exactly three things. Learn them as three, because interviewers ask you to separate
them and most people only name the first.

| Property | Means | Without it |
|---|---|---|
| **Confidentiality** | Nobody in the middle can read it | Coffee-shop WiFi reads your session cookie |
| **Integrity** | Nobody can modify it undetected | Your ISP injects ads; an attacker alters a bank transfer amount |
| **Authentication** | You're talking to who you think | You're on a perfect fake of your bank's site |

**Authentication is the one people forget, and it's the one that matters most.** Encryption to an
attacker is worthless — you'd have a beautifully private conversation with the wrong party. The
certificate system exists to solve *that*, not encryption.

## What TLS does NOT protect

Be precise here — this is where interviews separate people.

| Visible to an observer | Why |
|---|---|
| **Your IP and the server's IP** | IP headers must stay in the clear for routing (Day 001, C-01) |
| **The destination port** | Same reason — TCP header |
| **The DNS lookup** | Happens *before* TLS, unencrypted unless you use DoH/DoT |
| **The hostname (SNI)** | Sent in the clear at handshake start so the server knows which certificate to present |
| **Traffic size and timing** | Even encrypted, patterns leak information |

**So:** an observer on your network knows you visited `hdfcbank.com` and roughly how much you did
there. They don't know your password, your balance, or the pages you loaded.

Also, and this catches people:

- TLS protects data **in transit only**. Once it arrives it's plaintext on the server. Encryption at
  rest is a separate problem.
- TLS does not make a bad site safe. HTTPS means "the connection is private", not "this site is
  trustworthy". Phishing sites have valid certificates — they're free.
- **The padlock means encrypted, not honest.** Say this in an interview and you'll sound like
  someone who's thought about it.

## Symmetric vs asymmetric — and why both

| | Symmetric | Asymmetric |
|---|---|---|
| Keys | One shared secret | Public + private pair |
| Speed | Very fast | ~1000× slower |
| Problem | How do you share the key over an untrusted network? | Too slow for bulk data |
| Examples | AES-256-GCM, ChaCha20 | RSA, ECDSA, ECDHE |

**TLS uses both, and the reason is the whole design:**

1. **Asymmetric** during the handshake — to authenticate the server and agree on a shared secret
   without ever transmitting it
2. **Symmetric** for all the actual data — because it's fast enough for gigabytes

This is called a **hybrid cryptosystem**, and it's the standard answer to "why does TLS use both
kinds of encryption?"

## Certificates — how authentication works

A certificate binds **a public key** to **an identity**, signed by someone you already trust.

```
  Certificate for example.com
  ┌────────────────────────────────────────────┐
  │ Subject:      CN=example.com               │
  │ SAN:          example.com, www.example.com │  ← the field browsers actually check
  │ Public key:   <the server's public key>    │
  │ Valid:        2026-01-01 → 2026-04-01      │
  │ Issuer:       CN=R3, O=Let's Encrypt       │
  │ Signature:    <signed by the issuer>       │
  └────────────────────────────────────────────┘
```

### The chain of trust

```
   Root CA          (self-signed, pre-installed in your OS/browser trust store)
      │  signs
   Intermediate CA
      │  signs
   Your certificate
```

Your browser ships with ~150 root certificates. It trusts a site's certificate if it can build a
chain from that certificate up to a root it already has, with every signature valid and nothing
expired or revoked.

**Why intermediates exist:** the root's private key is kept offline, in a vault, air-gapped. If it
leaked, every certificate it ever signed would be worthless and the fix would be a global browser
update. Intermediates do the day-to-day signing and can be revoked without touching the root.

### The four checks the browser makes

1. **Signature valid** — chain verifies up to a trusted root
2. **Not expired** — within the validity window
3. **Hostname matches** — the SAN field covers the hostname you typed
4. **Not revoked** — via OCSP stapling or CRL

Fail any one and you get the full-page warning. **When you click through that warning, you are
disabling authentication** — you might be talking to anyone. That's why the browser makes it
deliberately annoying.

## The TLS 1.3 handshake

TLS 1.2 needed 2 round trips. **TLS 1.3 needs 1** — a substantial latency win given Day 006's
numbers.

```
   CLIENT                                            SERVER
     │                                                 │
     │  ClientHello                                    │
     │   · TLS versions I support                      │
     │   · cipher suites I support                     │
     │   · SNI: example.com          ← in the clear    │
     │   · key share (my ECDHE public value)           │
     │ ───────────────────────────────────────────────▶│
     │                                                 │
     │  ServerHello                                    │
     │   · chosen cipher suite                         │
     │   · key share (its ECDHE public value)          │
     │   · Certificate            ← encrypted in 1.3   │
     │   · CertificateVerify (proves it holds the      │
     │     private key for that cert)                  │
     │   · Finished                                    │
     │ ◀───────────────────────────────────────────────│
     │                                                 │
     │  [both sides now derive the same symmetric key] │
     │                                                 │
     │  Finished                                       │
     │ ───────────────────────────────────────────────▶│
     │                                                 │
     │  ══════ encrypted application data ══════       │
```

### The part worth actually understanding: ECDHE

**How do two parties agree on a secret over a channel everyone can read?**

Diffie-Hellman. The intuition, with paint:

1. Both agree publicly on a common colour — yellow
2. Each privately picks a secret colour and mixes it with yellow
3. They **exchange the mixtures** in public
4. Each adds their own secret to the received mixture

Both end with **yellow + secret A + secret B** — the same colour. An observer saw yellow and both
mixtures, but separating a mixture back into components is computationally infeasible.

The real version uses elliptic curve maths, but that's the shape of it.

**The "E" in ECDHE means ephemeral** — a fresh key pair for every session, discarded afterwards.
That gives **forward secrecy**: if the server's private key is stolen next year, and the attacker
has recorded all your traffic, **they still cannot decrypt it**, because the session key was never
derived from the long-term key and no longer exists.

Forward secrecy is a genuinely strong thing to be able to explain. Most people know "TLS encrypts";
far fewer can say why last year's traffic stays safe after a key compromise.

## Where certificates come from

**Let's Encrypt** issues free, automated, 90-day certificates via the ACME protocol. You prove you
control the domain (an HTTP challenge on a path, or a DNS TXT record — you've now met both), and a
certificate is issued and auto-renewed.

This is why HTTPS is universal now, and it's why the padlock proves nothing about honesty — anyone
who controls a domain gets one in 30 seconds.

**In practice you rarely handle this directly.** Vercel and Cloudflare provision and renew
automatically. But know:

- **Cloudflare SSL mode "Flexible" is a lie.** It encrypts browser→Cloudflare and leaves
  Cloudflare→origin **unencrypted**. The padlock shows, and the second leg is plaintext. Always use
  **Full (strict)** — this is exactly the item in
  [`03-Web-Developer/05-Security.md`](../../03-Web-Developer/05-Security.md), and now you know why
  it matters rather than just that it's on a checklist.
- **HSTS** tells browsers "only ever use HTTPS for this domain", preventing downgrade attacks. It's
  hard to undo, so enable it once you're confident.

## Type this yourself

```bash
# Inspect a real certificate chain
openssl s_client -connect google.com:443 -servername google.com </dev/null

# Just the certificate details
openssl s_client -connect github.com:443 -servername github.com </dev/null 2>/dev/null \
  | openssl x509 -noout -text | head -40

# Which TLS version and cipher was negotiated?
curl -v https://google.com 2>&1 | grep -i -E "SSL|TLS|cipher"
```

Look for: the negotiated **TLS version**, the **cipher suite**, the **SAN** list, the **issuer**, and
the **validity dates**. Then check the certificate in your browser (padlock → certificate details)
and match the fields.

Now in Java:

```java
import javax.net.ssl.*;
import java.security.cert.X509Certificate;

public class TlsInspect {
    public static void main(String[] args) throws Exception {
        SSLSocketFactory f = (SSLSocketFactory) SSLSocketFactory.getDefault();
        try (SSLSocket socket = (SSLSocket) f.createSocket("github.com", 443)) {
            socket.startHandshake();
            SSLSession session = socket.getSession();

            System.out.println("Protocol: " + session.getProtocol());
            System.out.println("Cipher:   " + session.getCipherSuite());

            for (java.security.cert.Certificate c : session.getPeerCertificates()) {
                X509Certificate x = (X509Certificate) c;
                System.out.println("---");
                System.out.println("Subject:  " + x.getSubjectX500Principal());
                System.out.println("Issuer:   " + x.getIssuerX500Principal());
                System.out.println("Expires:  " + x.getNotAfter());
            }
        }
    }
}
```

**Run it.** You'll see the chain: leaf → intermediate → (root, implicit). That's the trust chain
diagram above, printed from your own JVM.

> Worth knowing for later: the JVM has its own trust store (`cacerts`), separate from the OS. A
> corporate proxy with a custom root CA works in your browser and fails in Java with
> `PKIX path building failed` — a genuinely common and confusing production issue.

## Common mistakes

| Mistake | Correction |
|---|---|
| "HTTPS means the site is safe" | It means the connection is private and the server is who it claims. Phishing sites have valid certificates. |
| "TLS hides which site I visited" | The IP, port and SNI hostname are visible. Only the content is hidden. |
| Thinking TLS uses only asymmetric crypto | Asymmetric for the handshake, symmetric for the data. Asymmetric is far too slow for bulk. |
| "The certificate encrypts the data" | The certificate authenticates and carries a public key. The session key encrypts, and it's derived per session. |
| Clicking through certificate warnings | You've disabled authentication. The tunnel could terminate anywhere. |
| Using Cloudflare "Flexible" SSL | Origin traffic is plaintext. Use Full (strict). |
| Assuming TLS protects data at rest | It protects transit only. |

## Interview questions

**Q: What does TLS provide?**
> Confidentiality, integrity and authentication. Confidentiality via symmetric encryption of the
> payload, integrity via authenticated encryption, and authentication via the certificate chain
> proving the server holds the private key for a certificate signed by a trusted CA.

**Q: Why does TLS use both symmetric and asymmetric cryptography?**
> Asymmetric solves key distribution — you can establish a shared secret over an untrusted channel
> and verify identity — but it's around a thousand times slower. So it's used only during the
> handshake, and the resulting symmetric key encrypts the actual data.

**Q: Walk me through the TLS 1.3 handshake.**
> ClientHello with supported versions, cipher suites, SNI and an ECDHE key share. ServerHello with
> the chosen suite, its key share, its certificate, a CertificateVerify proving it holds the matching
> private key, and Finished. Both sides derive the same session key from the exchanged key shares,
> and the client sends Finished. One round trip, and application data follows encrypted.

**Q: What is forward secrecy?**
> Session keys are derived from ephemeral Diffie-Hellman key pairs that are discarded after the
> session and never derived from the server's long-term private key. So if that private key is later
> compromised, previously recorded traffic still cannot be decrypted.

**Q: What can a network observer still see over HTTPS?**
> Source and destination IPs, the port, the SNI hostname in the ClientHello, the DNS query unless
> encrypted, and traffic volume and timing patterns. The content and the specific URLs are protected.

**Q: How does the browser decide to trust a certificate?**
> It builds a chain from the certificate through any intermediates to a root in its trust store,
> verifies every signature, checks the validity dates, checks the hostname against the SAN field, and
> checks revocation status.
