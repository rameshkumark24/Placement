# Part 2 — ⭐⭐ Money, and the ledger

```java
// ⭐⭐ NEVER double, NEVER float. Minor units in a long, with the currency attached.
record Money(long minorUnits, Currency currency) {
    Money plus(Money o) {
        if (!currency.equals(o.currency)) throw new CurrencyMismatch();  // ⭐⭐ never silently convert
        return new Money(Math.addExact(minorUnits, o.minorUnits), currency);  // ⭐ addExact ⇒ overflow throws
    }
}
```

```
⭐⭐ THE DOUBLE-ENTRY LEDGER — the single most valuable idea in this round:
⭐   ⭐⭐ A balance is NOT a column you mutate. ⭐⭐ It is the SUM of immutable ledger entries.
⭐   Every transaction writes ⭐⭐ TWO OR MORE entries that SUM TO ZERO.
⭐
⭐   transfer 500 from A to B:
⭐     ⭐ (txn-9, account A, −500)
⭐     ⭐ (txn-9, account B, +500)
⭐   ⇒ ⭐⭐ money is never created or destroyed — it MOVES BETWEEN ACCOUNTS.
```

| ⭐⭐ Why this is worth the extra table | |
|---|---|
| ⭐⭐ **Correctness is checkable with one query** | ⭐⭐ `SELECT txn_id FROM entries GROUP BY txn_id HAVING SUM(amount) <> 0;` **— any row is a bug** |
| ⭐ Audit is free | ⭐ every balance change has a reason and a timestamp |
| ⭐⭐ **Reversal is a new entry pair, never a delete** | ⭐⭐ history is immutable, which is what auditors require |
| ⭐ External money has an account too | ⭐⭐ a top-up is `(bank_settlement, −500), (user, +500)` — **so the invariant still holds** |

⚠️ **The performance objection is real and you should raise it yourself: summing every entry per read is
O(n).** The answer is a **materialised balance updated in the same transaction as the entries**, with the
ledger as the source of truth and a **periodic reconciliation job** asserting they agree. **Say "the
cached balance is derived and reconciled" and you have pre-empted the follow-up.**

# Part 3 — ⭐⭐ The transfer, and the deadlock everybody writes

```java
@Transactional
public void transfer(TransferCommand cmd) {
    if (!idempotency.claim(cmd.requestId())) return;      // ⭐⭐ FIRST — Day 407's inbox

    // ⭐⭐ THE DEADLOCK: A→B locks A then B; B→A locks B then A. Two concurrent transfers deadlock.
    // ⭐⭐ THE FIX: ALWAYS ACQUIRE IN A TOTAL ORDER — sort the account ids.
    var ids = Stream.of(cmd.from(), cmd.to()).sorted().toList();
    Account first  = accounts.lockForUpdate(ids.get(0));   // ⭐ SELECT ... FOR UPDATE
    Account second = accounts.lockForUpdate(ids.get(1));

    Account from = cmd.from().equals(ids.get(0)) ? first : second;
    if (from.balance().lessThan(cmd.amount())) throw new InsufficientFunds();  // ⭐ inside the lock

    ledger.append(cmd.txnId(), cmd.from(), cmd.amount().negated());
    ledger.append(cmd.txnId(), cmd.to(),   cmd.amount());
    accounts.applyDelta(cmd.from(), cmd.amount().negated());   // ⭐ materialised balance, same txn
    accounts.applyDelta(cmd.to(),   cmd.amount());
}
```

| ⭐⭐ The four things being graded here | |
|---|---|
| ⭐⭐ **Ordered lock acquisition** | ⭐⭐ **the deadlock is the single most likely bug, and naming it unprompted is a strong signal** |
| ⭐⭐ **Idempotency claimed before any effect** | ⭐⭐ a retried transfer must not move money twice |
| ⭐⭐ **The balance check inside the lock** | ⭐⭐ check-then-act again (Day 479) — outside the lock it is a race |
| ⭐ Ledger and balance in **one** transaction | ⭐⭐ otherwise the reconciliation job finds drift you created |

> **⭐ The alternative worth naming: optimistic concurrency with a version column, retrying on conflict.**
> **Pessimistic locks are simpler and correct under contention; optimistic is faster when conflicts are
> rare.** For a wallet where a single account can be hot, **pessimistic with ordered acquisition is the
> safer default — and saying which you would pick and why is the answer.**

# Part 4 — ⭐⭐ The extensions (32–40)

| ⭐ Extension | ⭐ The good answer |
|---|---|
| ⭐⭐ **"Transfer between users on different shards."** | ⭐⭐ no single transaction ⇒ **a saga**: reserve on the source, credit the destination, compensate on failure — with **pending balance** as the semantic lock (Day 408) |
| ⭐⭐ **"The client retried and we double-charged."** | ⭐⭐ the idempotency key must be **client-supplied and unique per intent**, stored with the result so a retry returns the *original* response |
| ⭐ "Refund half of a transaction." | ⭐⭐ **a new entry pair referencing the original txn — never edit history** |
| ⭐ "Show a statement with a running balance." | ⭐ the ledger already is the statement; running balance is a window function |
| ⭐⭐ **"Two currencies."** | ⭐⭐ **one account per currency**, and a conversion is **two transactions plus an FX account** — never arithmetic across currencies |
| ⭐ "Scheduled/recurring transfers." | ⭐ a scheduler emitting the same idempotent command |

```
⭐⭐ THE IDEMPOTENCY DETAIL THAT SEPARATES CANDIDATES:
⭐   storing "seen this key" is only HALF the answer.
⭐   ⭐⭐ You must store the RESPONSE too, and return it on retry —
⭐   ⭐⭐ otherwise the retry gets 200-with-nothing or a confusing conflict, and the client
⭐     ⭐ does not know whether the transfer happened. ⭐⭐ Ambiguity is the failure mode in money.
```

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **`double` or `float` for money** | ⭐⭐ a financial defect, immediately disqualifying in this round |
| ⭐ Arithmetic across currencies | ⭐⭐ never — one account per currency |
| ⭐ No overflow handling | `addExact` costs nothing |
| ⭐⭐ **A mutable balance column as the source of truth** | ⭐⭐ no audit, no reversal, no checkable invariant |
| ⭐ Deleting or editing a ledger entry | ⭐⭐ history is immutable; reversal is a new pair |
| ⭐ Not raising the O(n) balance objection yourself | ⭐ they will |
| ⭐⭐ **Unordered lock acquisition** | ⭐⭐ the deadlock every candidate writes |
| ⭐ Balance check outside the lock | ⭐⭐ check-then-act |
| ⭐ Ledger and balance in separate transactions | ⭐⭐ self-inflicted drift |
| ⭐⭐ **Idempotency without storing the response** | ⭐⭐ the retry cannot tell whether it worked |
| ⭐ Cross-shard transfer answered with 2PC | ⭐⭐ saga with a pending balance |
| Refund implemented as an edit | auditors, and reality |

## Interview questions

**Q: How do you represent money?**
Minor units in a long with the currency attached, never a float or a double, and arithmetic that refuses
to operate across currencies rather than silently converting. I would also use `Math.addExact` so an
overflow throws instead of wrapping. Floating point in a billing path is not a style preference — it is a
defect, because a value like 0.1 is not representable and the errors accumulate in exactly the direction
nobody notices until reconciliation.

**Q: Why a ledger instead of a balance column?**
Because a balance column has no history, no reason for any change, and no way to check itself. With
double-entry, every transaction writes two or more immutable entries that sum to zero, so money moves
between accounts and is never created or destroyed — and correctness becomes one query: group the entries
by transaction and find any group whose sum is not zero. Every such row is a bug. It also makes reversal
a new entry pair rather than an edit, which is what audit requires. I would pre-empt the performance
objection: reads use a materialised balance updated in the same transaction, with the ledger as the source
of truth and a reconciliation job asserting they agree.

**Q: Two users transfer money to each other simultaneously. What happens?**
A deadlock, if you lock in the order the request gives you — A to B locks A then B while B to A locks B
then A, and both wait. The fix is to acquire locks in a total order, which for account ids means sorting
them before locking. That is the single most likely bug in this problem, and naming it before being asked
is worth more than the rest of the implementation. The alternative is optimistic concurrency with a
version column and retry, which is faster when conflicts are rare — but a wallet can have hot accounts,
so pessimistic locking with ordered acquisition is the safer default here.

**Q: The client retried the transfer and money moved twice. Fix it.**
An idempotency key supplied by the client, unique per intent, claimed before any effect — a unique
constraint insert, so a duplicate fails fast. But storing "seen this key" is only half the answer. You
have to store the response too and return the original one on retry, because otherwise the retrying client
receives either nothing or a conflict and still does not know whether the transfer happened. In money,
ambiguity is the failure mode: the customer support cost of "did it go through?" is higher than the cost
of the duplicate itself.

**Q: The two accounts are on different shards. Now what?**
There is no single transaction, so it becomes a saga: debit the source and move the amount into a pending
state, credit the destination, and compensate the source if the credit fails. The pending balance is a
semantic lock — it makes the intermediate state visible in the model rather than pretending the transfer
is atomic. Every step is idempotent because they will be retried, the compensation is idempotent too since
double refunds are a real incident, and there is a terminal state for manual intervention when the
compensation itself fails.

## 🎙️ Articulation drill

**Two minutes:** answer *"how do you make sure the money is right?"*

**⭐ "A balance isn't a column I mutate — it's the sum of immutable double-entry ledger entries, where
every transaction writes entries that sum to zero. That means money moves between accounts rather than
being created, and correctness is one query: group entries by transaction and find any group that doesn't
sum to zero. Any row it returns is a bug. External money has an account too, so a top-up is a debit
against a settlement account and a credit to the user, and the invariant still holds."**

deadlocks the moment two people send money to each other at the same time."**
