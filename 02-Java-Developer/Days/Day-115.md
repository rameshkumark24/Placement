# Day 115

**L-115** · Access vs refresh tokens, rotation, revocation, browser storage

**Time:** 3 hrs · **Mode:** NEW

> Day 114 ended on JWT's fundamental problem: a signed token cannot be un-issued. The refresh-token
> pattern is the standard answer, and today is how it actually works — including **reuse detection**,
> which is the part that turns a stolen token from a silent compromise into a detected incident.

---

# Part 1 — Why two tokens

A single token forces an impossible choice:

```
Long-lived  → convenient, and an unrevocable credential with a long stolen-token window
Short-lived → safe, and the user re-authenticates every 15 minutes
```

Two tokens with different properties resolve it:

| | **Access token** | **Refresh token** |
|---|---|---|
| Lifetime | **5–15 minutes** | days to months |
| Sent to | **every** API request | **only** the token endpoint |
| Format | JWT (self-contained, verified locally) | opaque random string |
| Server state | none | ✅ **stored, therefore revocable** |
| Exposure | high — every request, every service | low — one endpoint |
| Stolen ⇒ | valid for minutes | ⚠️ serious, hence rotation |

**The asymmetry is the whole design.** The frequently-transmitted credential is short-lived and
needs no state; the long-lived credential is transmitted rarely, to one endpoint, and is stored so it
can be revoked.

That resolves Day 114's revocation problem in practice: **revocation is not instant, it is bounded by
the access-token lifetime.** Revoke the refresh token and the user is out within fifteen minutes.
"Instant" is available if you need it, at the cost of a lookup per request — but 15 minutes is
acceptable for most systems, and *that* is the trade being made.

```
POST /login → { access_token (15 min), refresh_token (30 days) }

… 15 minutes pass, API returns 401 …

POST /token/refresh   { refresh_token }
     → { access_token (new), refresh_token (NEW — see rotation) }
```

# Part 2 — Refresh token rotation

**Single-use refresh tokens.** Every refresh returns a *new* refresh token and invalidates the old
one.

```java
public TokenPair refresh(String presented) {
    RefreshToken stored = repo.findByHash(sha256(presented))
            .orElseThrow(() -> new UnauthorizedException("unknown token"));

    if (stored.isRevoked()) {
        // ⭐ REUSE DETECTED — this token was already exchanged
        repo.revokeEntireFamily(stored.familyId());        // kill every descendant
        alertSecurity(stored.userId(), "refresh token reuse");
        throw new UnauthorizedException("token reuse detected");
    }
    if (stored.isExpired()) throw new UnauthorizedException("expired");

    stored.revoke();                                        // mark used
    RefreshToken next = RefreshToken.issue(stored.userId(), stored.familyId());   // same family
    repo.saveAll(List.of(stored, next));

    return new TokenPair(issueAccessToken(stored.userId()), next.raw());
}
```

## ⭐ Reuse detection — the mechanism worth understanding

Rotation alone limits a stolen token's usefulness. **Reuse detection turns theft into a detectable
event**, and the logic is elegant:

```
Legitimate client:  R1 → R2 → R3 → R4        each used exactly once
Attacker steals R3 and uses it first:
        attacker:   R3 → R4'
        user later: R3 → ✗ ALREADY USED  ⇒ REUSE DETECTED

Or the user gets there first:
        user:       R3 → R4
        attacker:   R3 → ✗ ALREADY USED  ⇒ REUSE DETECTED
```

**Either way, one of the two presents an already-used token — and you cannot tell which is the
attacker.** So the correct response is to **revoke the entire family**: every token descended from
the original login. Both parties are logged out, the legitimate user re-authenticates, and the
attacker has nothing.

This is why refresh tokens carry a **family id** (the login session) as well as their own id. It is
the design used by Auth0, Okta and the OAuth 2.0 Security BCP, and being able to explain the "you
cannot tell which is which, so kill both" reasoning is what makes the answer sound like understanding
rather than recall.

## Storing refresh tokens

**Store the hash, never the token** — the same rule as password-reset tokens (Day 112). A leaked
token table would otherwise be a set of live credentials.

```sql
CREATE TABLE refresh_token (
    id           UUID PRIMARY KEY,
    family_id    UUID NOT NULL,                    -- the login session
    user_id      BIGINT NOT NULL REFERENCES users(id),
    token_hash   CHAR(64) NOT NULL UNIQUE,         -- SHA-256 of the token
    issued_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at   TIMESTAMPTZ NOT NULL,
    revoked_at   TIMESTAMPTZ,
    device_label TEXT,                             -- for "your active sessions"
    ip           INET,
    user_agent   TEXT
);
CREATE INDEX ON refresh_token (family_id);
CREATE INDEX ON refresh_token (user_id) WHERE revoked_at IS NULL;   -- partial (Day 110)
```

SHA-256 is correct here, not argon2 — the token is already 256 bits of `SecureRandom` output, so
there is nothing to brute-force and no need for a slow hash.

That table also gives you a feature users expect: **"active sessions"** with device, location and
last-used, plus a revoke button per session.

## The concurrency problem — and it is real

A page firing three parallel requests all get `401`, all call refresh, and two of them present a
token the first has already rotated — **triggering a false reuse detection that logs the user out.**

This is the most common bug in a rotation implementation. Three fixes, and you need at least one:

1. **Client-side single-flight** — one in-flight refresh; other callers await the same promise. The
   primary fix, and it belongs in your HTTP client wrapper.
2. **A short grace window** — accept a rotated token for 10–30 seconds after rotation, returning the
   *same* successor rather than issuing a new one. This costs a small amount of safety.
3. **Idempotent refresh** — key the rotation by the presented token so a repeat within the window
   returns the previously-issued pair (Day 102's idempotency key, applied here).

# Part 3 — Browser storage, decided

Day 114 gave the table. This is the pattern to actually implement:

```
Access token   → IN MEMORY (a JavaScript variable). Never persisted.
Refresh token  → HttpOnly; Secure; SameSite=Strict cookie, Path=/auth/refresh
```

```http
Set-Cookie: __Host-rt=<token>; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh; Max-Age=2592000
```

Why each choice:

- **Access token in memory** — XSS can use it while the page is open, but cannot exfiltrate a
  durable credential. Closing the tab destroys it.
- **Refresh token `HttpOnly`** — JavaScript cannot read it at all, so XSS cannot steal the long-lived
  credential. This is the decisive protection.
- **`Path=/auth/refresh`** — the cookie is not attached to normal API calls, dramatically reducing
  exposure.
- **`SameSite=Strict`** — the refresh endpoint is never invoked cross-site, so `Strict` costs nothing
  here (unlike a session cookie, Day 113).
- **`__Host-` prefix** — no subdomain can overwrite it.

**On page load there is no access token**, so the app calls `/auth/refresh` once; the cookie is sent
automatically and a fresh access token comes back. The user stays logged in across refreshes without
any durable credential ever being reachable by script.

Because the refresh endpoint uses a cookie, it needs **CSRF protection** — `SameSite=Strict` plus a
double-submit token or a custom header requirement (Day 119).

## The 401 → refresh → retry interceptor

```javascript
let refreshing = null;                                   // ← the single-flight guard

async function apiFetch(url, options = {}) {
  let res = await fetch(url, withAuth(options));
  if (res.status !== 401) return res;

  refreshing ??= fetch('/auth/refresh', { method: 'POST', credentials: 'include' })
      .then(r => { if (!r.ok) throw new Error('refresh failed'); return r.json(); })
      .then(d => { accessToken = d.access_token; })
      .finally(() => { refreshing = null; });            // reset for the next cycle

  try { await refreshing; } catch { redirectToLogin(); return res; }

  return fetch(url, withAuth(options));                  // retry ONCE — never loop
}
```

Two rules: **retry exactly once** (a refresh that keeps failing must not become an infinite loop —
Day 062), and **share the in-flight promise** so parallel 401s produce one refresh.

# Part 4 — Logout and revocation

```java
public void logout(String refreshToken) {
    repo.findByHash(sha256(refreshToken)).ifPresent(RefreshToken::revoke);
    // the access token remains valid for up to 15 minutes — this is the accepted trade-off
}

public void logoutAllDevices(long userId) {
    repo.revokeAllForUser(userId);
    users.bumpTokenVersion(userId);       // ⭐ ALSO invalidates outstanding ACCESS tokens
}
```

**`logoutAllDevices` needs both halves.** Revoking refresh tokens stops new access tokens; the
`tokenVersion` claim (checked on every request against the user's current version — Day 114's
`credentials_changed_at` idea) invalidates the ones already issued. **Without the second half,
"log out everywhere" leaves a 15-minute window** — which is exactly the window that matters when the
reason is "this account was compromised".

Events that must revoke everything:

| Event | Why |
|---|---|
| Password change | The old credential may be compromised |
| Password reset | Same, and the reset may itself have been the attack |
| MFA enrolled or removed | The security posture changed |
| Email change | Account takeover vector |
| Reuse detected | An attacker holds a token |
| Admin action / account disabled | Obviously |

## Sliding vs absolute expiry

```
Sliding:   each refresh extends the window → an active user never re-authenticates
Absolute:  the family expires N days after LOGIN, regardless of activity
```

**Use both**, exactly as with sessions (Day 113): a 30-day sliding window inside a 90-day absolute
cap. Sliding alone means a stolen refresh token, kept alive by the attacker, never expires.

## Choosing lifetimes

| Context | Access | Refresh |
|---|---|---|
| Banking / high value | 5 min | 30 min, absolute |
| Standard web application | 15 min | 30 days sliding, 90 absolute |
| Mobile | 1 hour | 90 days sliding |
| Service-to-service | 5–60 min | often none — re-authenticate with a client credential |

**Mobile is longer because re-authentication is expensive on a phone** and the device itself is a
possession factor. Keychain and Keystore give storage protections a browser does not have.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Only one token type | Either unrevocable-and-long, or constant re-login |
| Refresh tokens that are not rotated | A stolen token is valid for its full lifetime, undetected |
| Rotation without reuse detection | Theft is silent |
| Reuse detection revoking one token, not the family | The attacker's branch survives |
| Storing refresh tokens in plaintext | The token table is a set of live credentials |
| No single-flight guard | Parallel 401s trigger false reuse detection and log users out |
| Retrying refresh in a loop | Infinite loop against your auth server |
| Refresh token readable by JavaScript | XSS steals the long-lived credential |
| No `Path` scoping on the refresh cookie | Sent with every request; needless exposure |
| Logout without bumping the token version | "Log out everywhere" leaves a 15-minute window |
| Sliding expiry with no absolute cap | A stolen token can be kept alive indefinitely |
| Not revoking on password change | The compromise persists through the fix |

## Interview questions

**Q: Why have both access and refresh tokens?**
To separate the frequently-transmitted credential from the long-lived one. The access token is short
and stateless so it can be verified without a lookup; the refresh token is stored, so it is
revocable, and is only ever sent to one endpoint.

**Q: What is refresh token rotation and why?**
Each refresh invalidates the presented token and issues a new one, so any token is single-use. That
bounds the value of a stolen token and, combined with reuse detection, makes theft detectable.

**Q: Explain reuse detection.**
If an already-used refresh token is presented, either the attacker or the legitimate user is
replaying — and you cannot tell which. So you revoke the entire token family from that login. The
legitimate user re-authenticates; the attacker is left with nothing.

**Q: Where do you store tokens in a browser?**
Access token in memory, refresh token in an `HttpOnly; Secure; SameSite=Strict` cookie scoped to the
refresh path. XSS can then use the session while the page is open but cannot exfiltrate a durable
credential.

**Q: How do you implement "log out from all devices"?**
Revoke every refresh token for the user *and* bump a token-version claim checked on each request —
otherwise already-issued access tokens stay valid for their remaining lifetime, which is exactly the
window that matters when the account is compromised.

**Q: What is the concurrency problem with rotation?**
Parallel requests all receive `401` and all attempt a refresh, so a stale token triggers a false
reuse detection and logs the user out. Fix with client-side single-flight, plus a short grace window
or idempotent refresh keyed by the presented token.

**Q: How does this compare with a session?**
It is a session with an optimisation: the refresh token is the session, and the access token is a
15-minute cache of the authorization decision that avoids a store lookup per request. Recognising
that is the honest framing.
