# Part 1 — The chain, from socket to response

```
        ┌─ Tomcat (or Jetty/Undertow) ──────────────────────────────────────────┐
 bytes  │  Connector (NIO)  →  parses HTTP  →  hands to a worker thread         │
   ──►  │      │                                                                │
        │      ▼                                                                │
        │  ┌─ Servlet Filter chain ─────────────────────────────────────────┐   │
        │  │  CharacterEncodingFilter                                       │   │
        │  │  ⭐ FilterChainProxy  (all of Spring Security lives HERE)      │   │
        │  │  your CorrelationIdFilter (Day 127)                            │   │
        │  │  ┌─ DispatcherServlet ────────────────────────────────────┐    │   │
        │  │  │  1  HandlerMapping        → which method?              │    │   │
        │  │  │  2  HandlerInterceptor.preHandle                       │    │   │
        │  │  │  3  HandlerAdapter                                     │    │   │
        │  │  │  4  ArgumentResolvers     → build the parameters       │    │   │
        │  │  │  5  ⭐ YOUR CONTROLLER METHOD                          │    │   │
        │  │  │  6  ReturnValueHandler / HttpMessageConverter → JSON   │    │   │
        │  │  │  7  HandlerInterceptor.postHandle                      │    │   │
        │  │  │  8  HandlerExceptionResolver (only if something threw) │    │   │
        │  │  │  9  HandlerInterceptor.afterCompletion                 │    │   │
        │  │  └────────────────────────────────────────────────────────┘    │   │
        │  └────────────────────────────────────────────────────────────────┘   │
        └───────────────────────────────────────────────────────────────────────┘
                                                                          ──► bytes
```

**Read that diagram twice. Nearly every Spring MVC question is answered by pointing at a box.**

The three facts that do the most work:

1. **Filters wrap the DispatcherServlet.** They are Servlet API, they know nothing about handlers,
   and they run for *every* request including 404s and static resources.
2. **Security is a filter.** So it runs *before* any interceptor, before argument resolution, before
   your controller — which is why an unauthenticated request never reaches your code and why an
   exception thrown in a security filter is **not** seen by `@RestControllerAdvice` (Day 149).
3. **Everything from step 1 to step 9 is inside one servlet**, and a `@ControllerAdvice` only covers
   steps inside it.

# Part 2 — Walking the steps with a real request

```http
POST /api/orders HTTP/1.1
Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJ...
X-Correlation-Id: 7f3a...

{"productId":"P-42","quantity":2}
```

### Step 0 — the thread

Tomcat takes a thread from its pool (`server.tomcat.threads.max`, default **200**) and that thread
is **occupied for the whole request** — including the 300 ms you spend waiting on the payment
gateway. This is Day 072's argument arriving in a framework: 200 threads means 200 concurrent
requests, no matter how idle they are. It is also why Day 072's virtual threads
(`spring.threads.virtual.enabled=true` on Boot 3.2+, Java 21) change the economics of exactly this
line and nothing else.

### Step 1 — `HandlerMapping`

`RequestMappingHandlerMapping` holds a map built at startup from every `@RequestMapping` it found. It
matches on path, method, `consumes`, `produces`, headers and params, then returns a
**`HandlerExecutionChain`** — the handler *plus the interceptors that apply to it*.

No match → `NoHandlerFoundException` or a container 404. **Note this happens before any of your code
runs**, which is why a 404 is not something your controller can intercept.

### Step 2 — `preHandle`

Interceptors run in registration order. Returning `false` **stops the chain** — and you must write
the response yourself, because nothing downstream will.

### Steps 3–4 — the adapter and argument resolvers

This is where "the framework builds your method parameters", and each resolver is worth knowing by
name because each is a distinct failure mode:

| Resolver | Handles | Fails as |
|---|---|---|
| `PathVariableMethodArgumentResolver` | `@PathVariable` | 500 if the name is not in the pattern |
| `RequestParamMethodArgumentResolver` | `@RequestParam` | **400** if required and absent |
| `RequestResponseBodyMethodProcessor` | ⭐ `@RequestBody` | reads the body with an `HttpMessageConverter` → `HttpMessageNotReadableException` |
| `ServletRequestMethodArgumentResolver` | `HttpServletRequest`, `Principal` | — |
| `ModelAttributeMethodProcessor` | ⭐ **no annotation at all** | binds query params by setter — Day 105's mass assignment |

**⭐ The single most important fact on this day:** a parameter with **no annotation** is not an
error. It falls through to `ModelAttributeMethodProcessor`, which constructs the object and populates
it from **request parameters** by name. So:

```java
@PostMapping("/orders")
Order create(CreateOrderRequest req) { }        // ❌ no @RequestBody
```

does not fail. It silently binds from the query string, ignores your JSON body entirely, and hands
you an object with every field null. **This is the actual answer to "why is my request body empty?"**
— and it is also Day 105's mass assignment, because query parameters an attacker controls are being
written into your object's fields.

**⭐ And the parameter-name fact behind half of the rest:**

```java
@GetMapping("/orders/{id}")
Order get(@PathVariable String id) { }
```

works only if parameter names survive compilation. Boot's Maven plugin sets `-parameters` for you; a
hand-rolled build or an old plugin does not, and then this fails at runtime with *"Name for argument
of type [java.lang.String] not specified"*. The universal fix is to be explicit —
`@PathVariable("id")` — and the universal diagnosis, when someone's app breaks only in their custom
build, is a missing `-parameters`.

### Step 5 — your method

Two lines of business logic, everything else was framework. That is Day 137's point restated.

### Step 6 — `HttpMessageConverter`

The return value goes to `RequestResponseBodyMethodProcessor`, which performs **content negotiation**:
it reads `Accept`, walks the registered converters, finds one that can write `Order` as
`application/json`, and asks it to. That converter is `MappingJackson2HttpMessageConverter`, holding
**the single `ObjectMapper`** that Day 150 configures.

No acceptable converter → **406 Not Acceptable**. That, and not a bug in your code, is what a
surprise 406 means: `produces` and `Accept` do not intersect.

### Step 8 — exceptions

If anything from step 3 onward threw, the `HandlerExceptionResolver` composite runs:

1. `ExceptionHandlerExceptionResolver` — ⭐ your `@ExceptionHandler` and `@RestControllerAdvice`
2. `ResponseStatusExceptionResolver` — `@ResponseStatus` and `ResponseStatusException`
3. `DefaultHandlerExceptionResolver` — the framework's own mapping (`HttpMessageNotReadable` → 400,
   `MethodArgumentNotValid` → 400, `HttpRequestMethodNotSupported` → 405)

**Nothing resolves it → the exception propagates out of the DispatcherServlet, up through your
filters, to the container**, which forwards to `/error` — Boot's `BasicErrorController` — producing
the generic whitelabel body. Day 149 replaces that.

**This is the mechanism behind the most-asked question of the whole block:** an exception thrown in a
*filter* is thrown outside the DispatcherServlet, so no `HandlerExceptionResolver` ever sees it. Your
beautiful RFC 7807 advice is bypassed and the client gets a whitelabel HTML error from a JSON API.
Day 151 covers the fix; the *reason* is this diagram.

### Step 9 — `afterCompletion`

Always runs, exception or not — the `finally` of the request. This is where you clear the MDC
(Day 127), because Day 066A's rule stands: a thread from a pool must be returned clean.

# Part 3 — Two things people get wrong about the shape

## `@Controller` vs `@RestController`

```java
@Controller
class PageController {
    @GetMapping("/home")
    String home() { return "home"; }              // ⭐ "home" = view name → templates/home.html
}

@RestController                                   // = @Controller + @ResponseBody
class OrderController {
    @GetMapping("/api/orders/{id}")
    Order get(@PathVariable String id) { ... }    // ⭐ object → HttpMessageConverter → JSON
}
```

Forget `@ResponseBody` on a plain `@Controller` in an API and the return value is treated as a **view
name**. You asked for JSON and got `Circular view path` or a 404 for a template named after your
entity's `toString()`. Diagnostic, not mysterious — step 6 never ran because step 6 was not selected.

## MVC vs WebFlux

| | Spring MVC | WebFlux |
|---|---|---|
| Model | thread per request | event loop, few threads |
| Blocking call | fine — it is your thread | ❌ **blocks the event loop**, collapses throughput |
| Return | `Order` | `Mono<Order>` / `Flux<Order>` |
| Debugging | ordinary stack traces | reactive traces, hard |
| When | ⭐ almost always | very high concurrency of I/O-bound work, SSE, streaming |

**With virtual threads in Java 21, MVC's main historical disadvantage largely evaporates.** The
honest interview answer is: MVC plus virtual threads gets most of WebFlux's scalability with none of
its cognitive cost, so WebFlux needs a specific justification — usually streaming or an existing
reactive data stack.

```yaml
logging.level.org.springframework.web: DEBUG
logging.level.org.springframework.web.servlet.mvc.method.annotation: TRACE

```

**Five lines, one per step.** When a request behaves strangely, this log tells you *which box* is

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Omitting `@RequestBody` | silently binds query params; body ignored; also mass assignment |
| `@Controller` instead of `@RestController` | return value read as a view name |
| Expecting `@ControllerAdvice` to catch filter exceptions | filters are outside the DispatcherServlet |
| Expecting an interceptor to run before security | security is a filter; filters run first |
| Blocking call in WebFlux | one slow call starves the whole event loop |
| Assuming a 404 reaches your controller | mapping failed before any handler was chosen |
| Not clearing MDC in `afterCompletion` | Day 066A's pooled-thread leak |
| Custom build without `-parameters` | `@PathVariable` breaks at runtime, only in that build |
| Confusing 406 with a bug | `produces` and `Accept` simply do not intersect |

## Interview questions

**Q: Walk me through what happens when a request hits a Spring Boot API.**
Tomcat parses it onto a pool thread, the servlet filter chain runs — security included — then the
DispatcherServlet finds a handler via `HandlerMapping`, runs interceptor `preHandle`, resolves
arguments (which is where `@RequestBody` invokes an `HttpMessageConverter`), calls my method,
converts the return value using content negotiation, and on any exception runs the
`HandlerExceptionResolver` chain, of which my `@RestControllerAdvice` is the first. `afterCompletion`
always runs.

**Q: Why is my `@RequestBody` object all nulls?**
Because I forgot the annotation. Without it the parameter falls through to the model-attribute
resolver, which binds from query parameters, so the JSON body is never read — and it is a mass
assignment surface at the same time.

**Q: Why doesn't my `@RestControllerAdvice` catch this exception?**
Because it was thrown in a filter, which is outside the DispatcherServlet, so no
`HandlerExceptionResolver` runs. It goes to the container's error dispatch instead.

**Q: MVC or WebFlux?**
MVC by default, and with virtual threads it now scales for I/O-bound work without the reactive
programming model. WebFlux where I genuinely need streaming or already have a reactive data layer.
