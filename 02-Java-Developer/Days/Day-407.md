> **⭐⭐ `save(order); publish(event);` is a bug. Two systems, no shared transaction — and one of the four

> detect.**

> the inbox on the other side that finally makes "effectively-once" true end to end.

# Part 1 — ⭐⭐ The dual-write problem

```java
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);              // ⭐ system 1: Postgres
    kafkaTemplate.send("orders", event);      // ⭐⭐ system 2: Kafka. ⭐⭐ NOT IN THE TRANSACTION.
}
```

| ⭐ What actually happens | ⭐ Result |
|---|---|
| ⭐ Both succeed | ✅ fine — **and this is the case you tested** |
| ⭐⭐ **DB commits, Kafka send fails** | ⭐⭐ **the order exists, nothing downstream ever knows** |
| ⭐⭐ **Kafka succeeds, DB transaction rolls back** | ⭐⭐ **an event for an order that does not exist** |
| ⭐⭐ **Kafka send succeeds, the ack is lost, the app crashes** | ⭐⭐ you cannot tell which case you are in |

```
⭐⭐ AND MOVING THE SEND AROUND DOES NOT FIX IT:
⭐   send before commit  ⇒ ⭐ event for a rolled-back order
⭐   send after commit   ⇒ ⭐⭐ order with no event (⭐ and the process can die in between)
⭐   send inside the txn  ⇒ ⭐⭐ meaningless — Kafka has no idea your transaction exists
⭐ ⇒ ⭐⭐ THERE IS NO ORDERING OF TWO INDEPENDENT SYSTEMS THAT IS ATOMIC.
⭐   ⭐ Two-phase commit would do it, and it is unavailable, slow and blocking (Day 342).
```

⚠️ **`@TransactionalEventListener(AFTER_COMMIT)` is the most common half-fix in the Spring world.** It
eliminates "event for a rolled-back order" — **and leaves the worst case fully intact**: the transaction
commits, the process dies before the listener publishes, **and the event is gone forever with no trace.**

# Part 2 — ⭐⭐ The outbox: use the transaction you already have

```sql
CREATE TABLE outbox (
  id             UUID PRIMARY KEY,
  aggregate_type TEXT NOT NULL,          -- ⭐ "Order"      → the topic
  aggregate_id   TEXT NOT NULL,          -- ⭐⭐ "order-42"  → THE PARTITION KEY (ordering, Day 401)
  event_type     TEXT NOT NULL,          -- "OrderPlaced"
  payload        JSONB NOT NULL,
  created_at     TIMESTAMPTZ DEFAULT now()
);
```

```java
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);                    // ⭐ same transaction
    outboxRepository.save(OutboxEvent.of(order));   // ⭐⭐ SAME TRANSACTION
}   // ⭐⭐ ONE COMMIT. Either BOTH rows exist or NEITHER does. Atomicity restored.
```

> **⭐⭐ That is the whole idea, and it is beautiful because it is not clever: you do not need a
> distributed transaction if you only write to one system.** The event becomes ordinary state, protected
> by ordinary ACID — **and publishing becomes a separate, retryable problem that cannot lose anything.**

| ⭐ Then a **relay** publishes and marks/deletes | ⭐ Two implementations |
|---|---|
| ⭐ **Polling publisher** | ⭐ `SELECT ... WHERE published = false ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED` |
| ⭐⭐ **CDC / log tailing** | ⭐⭐ **read the database's own write-ahead log — no query, no load, no polling latency** |

```
⭐ Polling publisher — honest assessment:
⭐   ✅ ⭐⭐ trivially simple, no new infrastructure, works everywhere. ⭐ START HERE.
⭐   ✅ SKIP LOCKED makes multiple relays safe
⭐   ⚠️ polling latency (⭐ 100 ms–1 s), ⭐ load on the table, ⭐ and the table needs cleaning up
⭐   ⚠️ ⭐⭐ ordering: use ORDER BY id, and publish keyed by aggregate_id so per-aggregate order holds
```

⚠️ **Delete or archive published rows.** An outbox table nobody prunes becomes a hundred-million-row
table whose index no longer fits in memory, **and then the polling query — running every 200 ms —
becomes your slowest query.** Delete on publish, or partition by day and drop partitions.

# Part 3 — ⭐⭐ CDC and Debezium

```
⭐⭐ CDC reads the database's REPLICATION LOG (Postgres WAL, MySQL binlog) —
⭐   ⭐⭐ the same stream a read replica consumes.
⭐ ⇒ ⭐⭐ zero query load, ⭐ millisecond latency, ⭐⭐ and it sees EXACTLY the committed order.
```

| ⭐ Debezium mechanics | |
|---|---|
| ⭐ **Snapshot then stream** | ⭐ reads the current table state, then follows the log |
| ⭐ Change event shape | ⭐⭐ `before`, `after`, `op` (c/u/d/r), source metadata (LSN, txId) |
| ⭐ One topic per table by default | ⭐ configurable |
| ⭐⭐ **Outbox Event Router SMT** | ⭐⭐ **reads your `outbox` table and publishes clean domain events** — the two patterns combined |

```
⭐⭐ CDC ON STATE TABLES vs CDC ON THE OUTBOX — this is the important choice:
⭐   ❌ CDC on `orders` directly:
⭐      ⇒ ⭐⭐ your INTERNAL SCHEMA becomes your PUBLIC EVENT CONTRACT
⭐      ⇒ ⭐⭐ a column rename is a breaking change for three other teams (Day 399's shared DB, reborn)
⭐      ⇒ ⭐ no domain meaning — consumers see "a row changed", not "an order was placed"
⭐   ✅ ⭐⭐ CDC on the OUTBOX table:
⭐      ⇒ ⭐⭐ you publish a DELIBERATE, VERSIONED event, and the internal schema stays private
⭐      ⇒ ⭐ atomic with the state change, low latency, no polling
⭐ ⇒ ⭐⭐ OUTBOX + CDC IS THE ANSWER. Raw table CDC is a shortcut you pay for later.
```

## ⚠️⚠️ The replication slot that fills your disk

```
⭐⭐ Postgres will NOT recycle WAL that an active replication slot has not consumed.
⭐   ⇒ Debezium (or the connector, or the whole Connect cluster) stops for six hours
⭐   ⇒ ⭐⭐ WAL ACCUMULATES INDEFINITELY
⭐   ⇒ ⭐⭐ THE DATABASE DISK FILLS ⇒ ⭐⭐ POSTGRES STOPS ACCEPTING WRITES. Total outage.
⭐   ⇒ ⭐⭐ Your event pipeline just took down your primary database.
```

| ⭐ Mandatory mitigations | |
|---|---|
| ⭐⭐ **Alarm on replication slot lag** (`pg_replication_slots.restart_lsn`) | ⭐⭐ **before disk, not after** |
| ⭐ Set `max_slot_wal_keep_size` | ⭐⭐ the slot is invalidated instead of the database dying — **choose which failure you want** |
| ⭐ Alarm on free disk on the DB volume | the last line of defence |
| ⭐ Drop unused slots immediately | ⭐⭐ an abandoned slot from a decommissioned connector is a time bomb |

> **⭐⭐ This is the single most important operational fact about CDC**, and it is the one that turns an
> elegant pattern into a 3am incident. **Anyone who has run Debezium in production knows it; anyone who
> has only read about it does not.**

| ⭐ Other CDC realities | |
|---|---|
| ⭐ The initial snapshot on a large table | ⭐ can take hours and hold locks (use incremental snapshots) |
| ⭐ DDL changes | ⭐ schema evolution flows through — **handle it deliberately** |
| ⭐ Deletes | ⭐⭐ produce a delete event **plus a tombstone** for compaction (Day 403) |
| ⭐ Kafka Connect is infrastructure | ⭐ a cluster to run, monitor and upgrade |

# Part 4 — ⭐⭐ The inbox, and effectively-once end to end

```java
// ⭐⭐ THE CONSUMER SIDE. Ten lines, and it is the whole answer to "exactly-once".
@Transactional
public void handle(OrderPlaced event) {
    try {
        inbox.insert(event.id());          // ⭐⭐ PRIMARY KEY on the event id
    } catch (DuplicateKeyException e) {
        return;                            // ⭐⭐ already processed — ack and move on
    }
    reserveStock(event);                   // ⭐⭐ the business change, SAME transaction
}   // ⭐⭐ commit: the dedup record and the effect are atomic. Redelivery is now harmless.
```

```
⭐⭐ OUTBOX (producer) + INBOX (consumer) = ⭐⭐ EFFECTIVELY-ONCE, END TO END,
⭐   ⭐ across two databases and a broker, ⭐⭐ WITH NO DISTRIBUTED TRANSACTION ANYWHERE.
⭐ ⇒ ⭐⭐ This is the practical answer to Day 334's "exactly-once is a lie" and
⭐   Day 403's Kafka-only guarantee. ⭐⭐ It is at-least-once delivery plus atomic deduplication.
```

| ⭐ Operational notes | |
|---|---|
| ⭐⭐ **The inbox table needs a retention policy** | ⭐ delete rows older than your maximum redelivery window |
| ⭐ The event id must be **stable across retries** | ⭐⭐ generated by the producer, not by the broker |
| ⭐ Works for any effect **inside the same database** | ⭐⭐ an email or a card charge still needs its own idempotency key |
| ⭐ Ordering | ⭐ partition by `aggregate_id` so a single aggregate's events stay ordered (Day 401) |

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **`save()` then `publish()`** | ⭐⭐ dual write — silent, undetectable event loss |
| ⭐ `AFTER_COMMIT` listener as the fix | ⭐⭐ fixes the mild case, leaves the worst one |
| ⭐ Reaching for 2PC | ⭐ unavailable, slow, blocking (Day 342) |
| ⭐⭐ **No cleanup on the outbox table** | ⭐⭐ the polling query becomes the slowest query in the system |
| ⭐ Polling without `SKIP LOCKED` | ⭐ relays block each other or double-publish |
| ⭐ Not keying the publish by aggregate id | ⭐⭐ per-aggregate ordering lost |
| ⭐⭐ **CDC directly on state tables** | ⭐⭐ your internal schema becomes an unversioned public contract |
| ⭐⭐ **No alarm on replication slot lag** | ⭐⭐ a stopped connector fills the disk and stops all writes |
| ⭐ Abandoned replication slots | ⭐⭐ a time bomb from a decommissioned connector |
| ⭐ Full snapshot on a huge table in production | hours of load and locks — use incremental |
| ⭐⭐ **No inbox on the consumer** | ⭐⭐ at-least-once means duplicates will arrive |
| ⭐ Dedup insert committed separately from the effect | ⭐⭐ you rebuilt the dual-write bug on the consumer side |
| Inbox table with no retention | grows forever |

## Interview questions

**Q: What is the dual-write problem?**
Writing to two systems in one logical operation with no shared transaction. Save the order and publish
the event: both may succeed, but the database can commit while the publish fails — leaving an order
nothing downstream knows about — or the publish can succeed while the transaction rolls back, producing
an event for an order that does not exist. Reordering the two does not help, because the process can die
between them, and two-phase commit is unavailable, slow and blocking. The Spring after-commit listener is
the common half-fix: it removes the event-for-a-rolled-back-order case and leaves the worst one, where
the commit lands and the process dies before publishing.

**Q: How does the outbox pattern solve it?**
By making sure you only ever write to one system. The event is inserted into an outbox table in the same
transaction as the state change, so either both rows exist or neither does — ordinary atomicity, no
distributed transaction. Publishing then becomes a separate, retryable problem that cannot lose anything,
handled either by a polling relay using `SELECT ... FOR UPDATE SKIP LOCKED` or by change data capture
reading the database's write-ahead log. The elegance is that it is not clever: you do not need a
distributed transaction if you only write to one place.

**Q: Should CDC read your tables directly?**
No, it should read your outbox table. Change data capture on state tables makes your internal schema the
public event contract, so renaming a column becomes a breaking change for three other teams — it is the
shared-database problem reappearing through a different door — and consumers receive "a row changed"
rather than "an order was placed", with no domain meaning. Outbox plus CDC gives you the best of both:
a deliberate versioned event, atomic with the state change, delivered with millisecond latency and no
query load. Debezium's outbox event router does exactly this.

**Q: What is the biggest operational risk with Debezium on Postgres?**
The replication slot. Postgres will not recycle write-ahead log that an active slot has not consumed, so
if the connector stops for a few hours, WAL accumulates until the database disk fills — and a full disk
means Postgres stops accepting writes. Your event pipeline has taken down your primary database. The
mitigations are alarming on slot lag rather than on disk, setting `max_slot_wal_keep_size` so the slot is
invalidated instead of the database dying — which is choosing which failure you want — and dropping
abandoned slots immediately, because a slot left behind by a decommissioned connector is a time bomb.

**Q: How do you get exactly-once end to end?**
You do not get exactly-once delivery, you get effectively-once processing, and it takes two halves. The
producer uses an outbox so the event cannot be lost or invented. The consumer uses an inbox: insert the
event id into a table with a primary key constraint, and if that conflicts the event has already been
processed, so return; otherwise perform the business change in the same transaction. Commit makes the
deduplication record and the effect atomic, so redelivery is harmless. That is at-least-once delivery
plus atomic deduplication, and it works across two databases and a broker with no distributed transaction
anywhere.
