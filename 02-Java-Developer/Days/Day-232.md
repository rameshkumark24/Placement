# Day 232 ⚡

**J-232** · ⚡ **Performance** — ⭐⭐ measure first, because most `useMemo` makes things slower

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: `useMemo` and `React.memo` are not free — each adds a comparison, an
> allocation and a permanent cache entry — so memoising something cheap is a straight loss, and a
> codebase full of defensive memos is usually slower and always harder to change than one with none.**
>
> Today: ⭐ measuring properly, ⭐⭐ the three memo tools and when each is a loss, and the fixes that
> beat memoisation.

---

# Part 1 — ⭐⭐ Measure, and measure the right thing

```
⭐⭐ THE ORDER. DO NOT SKIP A STEP.

⭐   ① ⭐⭐ IS IT ACTUALLY SLOW? To a USER, on a MID-RANGE PHONE,
⭐      on a THROTTLED NETWORK. ⭐ Not on your laptop.
⭐   ② ⭐⭐ WHICH PHASE? Use the Profiler:
⭐        · ⭐ NETWORK (waterfall, payload)   ⇒ Day 227/241 — usually this
⭐        · ⭐ RENDER (your functions)        ⇒ today
⭐        · ⭐ COMMIT (DOM writes, layout)    ⇒ Day 220
⭐   ③ ⭐ WHY is that component rendering? The Profiler tells you.
⭐   ④ ONLY NOW: change something. ⭐ Re-measure.

⭐   ⇒ ⭐⭐ MEASURE IN A PRODUCTION BUILD. ⭐ Profiling React dev mode
⭐     is benchmarking with -Xint and concluding the JVM is slow.
```

| ⭐ Symptom | ⭐⭐ Usual real cause |
|---|---|
| Page slow to appear | ⭐⭐ **Network** — waterfall, huge bundle, unoptimised images. **Not renders.** |
| Typing lags | ⭐ A big controlled form re-rendering expensive siblings |
| A list stutters on scroll | ⭐ Too many DOM nodes — virtualise or paginate (Day 230) |
| Interaction slow after data loads | ⭐ Genuine over-rendering — **today's material** |

> ⭐⭐ **Roughly nine times in ten, "React is slow" is a network or payload problem.** Reaching for
> `memo` first is optimising the layer you can see instead of the layer costing you — the same mistake
> as tuning GC when the real problem is an N+1 query.

# Part 2 — The three tools, and their real cost

| Tool | Memoises | ⭐ Cost |
|---|---|---|
| `useMemo(fn, deps)` | ⭐ A **value** | A deps compare + retaining the value forever |
| `useCallback(fn, deps)` | ⭐ A **function reference** | Same. ⭐⭐ It does *not* make the function faster. |
| `React.memo(Comp)` | ⭐ A **component's render** | A **props compare on every parent render** |

```jsx
// ❌ A LOSS. The compare costs more than the work.
const total = useMemo(() => a + b, [a, b]);
const name  = useMemo(() => `${first} ${last}`, [first, last]);

// ❌ A LOSS. Every prop is a new object, so memo NEVER hits.
const Row = React.memo(function Row({ item, style, onClick }) {...});
<Row item={i} style={{ margin: 4 }} onClick={() => f(i)} />
//              ⭐⭐ NEW OBJECT      ⭐⭐ NEW FUNCTION
//   ⇒ the compare runs, always fails, and you pay it every render.
//     ⭐ STRICTLY WORSE THAN NO memo AT ALL.

// ✅ A WIN. Expensive work, stable deps.
const sorted = useMemo(() => bigList.sort(cmp), [bigList]);   // 10k items
```

```
⭐⭐ React.memo ONLY HELPS IF **ALL** PROPS ARE REFERENTIALLY STABLE.
⭐   ⇒ one inline object, array or arrow function defeats it entirely.
⭐   ⇒ ⭐⭐ SO memo USUALLY ARRIVES WITH useCallback + useMemo IN TOW,
⭐     AND NOW YOU HAVE THREE CACHES TO KEEP CORRECT — each of which
⭐     can go stale if a dep is wrong (Day 226).
⭐   ⇒ ⭐ THE COMPLEXITY IS THE REAL COST, NOT THE CPU. It is the
⭐     same argument as caching a method whose key you cannot
⭐     reliably invalidate.
```

> ⭐ **The React Compiler changes this.** It inserts memoisation automatically and correctly, making
> hand-written memos redundant and often counterproductive. **Say that, then say the important half:
> it removes the busywork, not the measurement discipline.**

# Part 3 — ⭐⭐ The fixes that beat memoisation

```jsx
// ❌ typing in the form re-renders the 500-row table
function Page() {
  const [q, setQ] = useState("");
  return <><input value={q} onChange={e=>setQ(e.target.value)} />
           <HugeTable rows={rows} /></>;
}

// ✅ FIX 1 — ⭐⭐ MOVE STATE DOWN. Now typing re-renders one component.
function Page() { return <><SearchBox /><HugeTable rows={rows} /></>; }

// ✅ FIX 2 — ⭐ LIFT CONTENT UP (children as a stable prop)
function Panel({ children }) {
  const [open, setOpen] = useState(false);
  return <div>{open && children}</div>;   // ⭐⭐ children don't re-render
}
```

| ⭐ Fix | Beats memo because |
|---|---|
| **⭐⭐ Move state down** | The re-render never happens. **No cache to maintain, nothing to go stale.** |
| **Lift content up / `children`** | ⭐ `children` is created by the *parent*, so it is already stable |
| **Delete derived state** (Day 225) | ⭐ Fewer state updates ⇒ fewer renders, and no drift |
| **Fix the key** (Day 230) | ⭐ Stops mass remounting, far worse than re-rendering |
| **Fix the context split** (Day 231) | ⭐⭐ Stops app-wide renders from unrelated changes |
| **Debounce the input** | ⭐ One render per pause instead of per keystroke |
| **Paginate** (Day 230) | ⭐⭐ Fixes network, memory *and* render at once |

> ⭐⭐ **Every one of those is a structural fix.** A memo is a cache bolted onto a structure you did not
> change — and caches go stale, get invalidated wrongly, and outlive their usefulness. **Prefer the
> structure**, exactly as you would prefer fixing the query over caching its result.

# Part 4 — When to reach for `useTransition`

```jsx
const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);                        // ⭐ URGENT — the input
  startTransition(() => setResults(filter(e.target.value)));  // ⭐⭐ can lag
}
```

> ⭐ **This is priority, not speed** — thread priority for renders. The work costs the same; you have
> told React the keystroke matters more than the list, so the input never feels stuck.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you approach React performance?"**

Lead with discipline, not tools. **By measuring first, in a production build, on a throttled CPU —
profiling dev mode is benchmarking with `-Xint` and concluding the JVM is slow. And the first question
is which phase: network, render or commit. Nine times out of ten "React is slow" is a network
problem — a waterfall, a huge bundle, unoptimised images — and reaching for memo first is optimising
the layer I can see instead of the one costing me. Same mistake as tuning GC when the real problem is
an N+1 query.**

Then the counterintuitive part. **Memoisation isn't free. Every `useMemo` adds a comparison, an
allocation and a cache entry that lives forever. `React.memo` only helps if every prop is referentially
stable, so one inline object defeats it — and then the compare runs every render and always fails,
which is strictly worse than not having it. A codebase full of defensive memos is usually slower and
always harder to change.**

Then what you do instead. **Structural fixes: move state down so the expensive component never
re-renders, pass content as children so the reference is already stable, delete derived state, fix the
context split. Those remove the render rather than caching around it — and there's no cache to go
stale. It's preferring to fix the query over caching its result.**

Close on the honest current picture. **The React Compiler inserts this memoisation automatically and
correctly, which makes most hand-written memos redundant. It removes the busywork; it doesn't change
the measurement discipline.**
