# Part 1 — ⭐⭐ What they actually click, in order

```
⭐⭐ A REVIEWER'S FIRST 90 SECONDS IN YOUR REPO:
⭐ 1. ⭐⭐ THE README            — is there one, and does it explain the ARCHITECTURE or just `npm start`?
⭐ 2. ⭐ The directory layout   — does the structure express the domain, or is it Controller/Service/Repo?
⭐ 3. ⭐⭐ THE TEST FOLDER       — ⭐⭐ how many, what kind, and are they real assertions?
⭐ 4. ⭐ One "interesting" file — usually the biggest, or the one your README pointed at
⭐ 5. ⭐⭐ THE COMMIT HISTORY    — ⭐⭐ 4 commits called "update" tells them how you work
⭐ 6. ⭐ CI config              — is there a pipeline, and does the badge pass?
```

| ⭐ What each one signals | |
|---|---|
| ⭐⭐ **A README with an architecture diagram** | ⭐⭐ **you can communicate a system** — worth more than the code |
| ⭐ Package-by-feature over package-by-layer | ⭐ Day 300 — you think in domains |
| ⭐⭐ **Tests that assert behaviour** | ⭐⭐ vs tests that assert the mock was called |
| ⭐ Small, well-messaged commits | ⭐⭐ you have worked with other people, or thought about it |
| ⭐ A green pipeline | ⭐ Stage 10 was real |

⚠️ **A repository with no tests undoes your entire testing answer.** You can say all the right things
about the test pyramid; **if the folder is empty, the interviewer has already decided.** The repo is
evidence and the interview is testimony — **evidence wins.**

# Part 2 — ⭐⭐ The README that does the work for you

```markdown
# Flagship — multi-tenant project API

⭐⭐ ONE SENTENCE: what it is and who it is for.

## Architecture              ⭐⭐ ← the diagram. This is the single highest-value section.
  [ascii or an image: client → ALB → app → Postgres/Redis/S3, and the outbox path]

## Key decisions             ⭐⭐ ← 5 rows of Day 468's decision log, with the COSTS
| Decision | Why | Cost |

## Running it                ⭐ docker compose up. It must actually work.
## Testing                   ⭐ what kinds, how to run, what coverage means here
## What I'd do differently   ⭐⭐ ← two items. This section is disproportionately effective.
## Known limitations         ⭐⭐ ← single-region, no multi-tenancy at the DB level, etc.
```

| ⭐ Why this README wins | |
|---|---|
| ⭐⭐ **It answers the deep-dive questions before they are asked** | ⭐ decisions, costs, limits |
| ⭐⭐ **"What I'd do differently" in writing** | ⭐⭐ almost nobody does this, and it reads as unusual maturity |
| ⭐ It makes the reviewer's job easy | ⭐⭐ and reviewers reward that |
| ⭐ It is the artefact that survives after the call | ⭐ they may forward it to the hiring manager |

> **⭐ Spend an evening on the README. It is the highest return-per-hour work in this entire stage**,
> because it is read by more people than will ever interview you, **and it converts a repository into an
> argument.**

⚠️ **`docker compose up` must actually work on a clean machine.** Test it in a fresh container or on
someone else's laptop. **A README whose first instruction fails is worse than no README** — it is a
demonstration that you do not verify your own claims (Day 462's dead link, again).

# Part 3 — ⭐⭐ Commit history as evidence

| ⭐ What they see | ⭐ What it says |
|---|---|
| ⭐⭐ **"update", "fix", "asdf", "final"** ×40 | ⭐⭐ you have never worked where history mattered |
| ⭐ One enormous "initial commit" of the whole app | ⭐⭐ **it looks copied, whether or not it was** |
| ⭐ Small commits with imperative messages and a why | ⭐⭐ **you can be trusted in a shared repo** |
| ⭐ A branch and a merge with a real PR description | ⭐ you understand the workflow |
| ⭐ Commits at a plausible cadence over weeks | ⭐⭐ it was built, not acquired |

```
⭐⭐ THE MESSAGE FORMAT THAT COSTS NOTHING AND SIGNALS A LOT:
⭐   "Add transactional outbox for order events
⭐
⭐    Publishing after commit lost events when the process died between the two.
⭐    The event row is now written in the same transaction and a relay publishes it,
⭐    keyed by aggregate id so per-order ordering survives."
⭐ ⇒ ⭐⭐ The BODY explains WHY. ⭐ That is what makes a history readable in a year.
```

**⭐ If your history is already bad, do not rewrite it dishonestly.** Start writing good messages from
today; **a visible improvement partway through the log is itself a good signal**, and a suspiciously
perfect rewritten history is a worse risk than a scruffy real one.

# Part 4 — ⭐⭐ Defending code you would now write differently

```
⭐⭐ THEY WILL FIND THE 900-LINE SERVICE CLASS. ⭐ You know the one.

⭐ ❌ "I didn't have time."                      ⇒ ⭐⭐ everyone doesn't have time
⭐ ❌ "It's fine actually."                       ⇒ ⭐⭐ it is not, and they know
⭐ ✅ ⭐⭐ "That one grew — it started as order creation and accumulated pricing and
⭐      notification. ⭐⭐ It should be three: the order aggregate owns the invariants,
⭐      pricing is a separate policy because it changes for a different reason, and
⭐      notification belongs behind the outbox. ⭐⭐ I refactored the reporting module that
⭐      way (Day 307) and it took about a day — this one hasn't hurt me enough yet."
⭐ ⇒ ⭐⭐ You named it, you know the fix, you know the cost, and you have DONE it elsewhere.
⭐   ⭐ That is a stronger position than clean code you cannot explain.
```

| ⭐ The three-part shape | |
|---|---|
| ⭐ 1. **Name it accurately** | ⭐⭐ do not under- or over-state it |
| ⭐ 2. **Say what it should be** | ⭐ specifically, with the reason for the split |
| ⭐⭐ 3. **Say why it is still like that** | ⭐⭐ **"it hasn't hurt me enough yet" is a legitimate engineering answer** |

> **⭐ Priority is a real answer, and it is one that only experienced-sounding candidates give.** Every
> codebase has known debt; **the question is whether you know where it is, what it costs, and why it is
> not top of the list.** "I know, and here is the trade" beats both denial and apology.

## ⭐ The live code question

| ⭐ They may ask you to change something live | |
|---|---|
| ⭐⭐ **"Add a field to this endpoint"** | ⭐ can you navigate your own codebase quickly |
| ⭐ "Where would a rate limit go?" | ⭐⭐ do you know your own layering |
| ⭐ "Write a test for this method" | ⭐⭐ **the most common, and the most revealing** |
| ⭐ "Show me where tenancy is enforced" | ⭐ Day 469 — one place, or scattered |

**⭐ Practise navigating your own repo fast.** Fumbling in your own project is a bad look that has nothing
to do with your ability — **know where things are, keep the IDE search open, and say what you are looking
for as you look** (Day 466).

| ⭐⭐ **An empty test folder** | ⭐⭐ evidence beats testimony |

| ⭐⭐ **`docker compose up` that fails on a clean machine** | ⭐⭐ you do not verify your own claims |

## Interview questions

**Q: What does an interviewer look at in your repository?**
The README first — whether it explains the architecture or just how to start it. Then the directory
layout, then the test folder, then one interesting file, then the commit history, then CI. The test
folder is the one that decides things: I can say all the right things about the test pyramid, but if the
folder is empty the interviewer has already concluded. The repository is evidence and the interview is
testimony, and evidence wins.

**Q: What makes a good project README?**
An architecture diagram, five rows of the decision log including the costs, and two sections almost
nobody writes — "what I'd do differently" and "known limitations". Those answer the deep-dive questions
before they are asked, and having them in writing reads as unusual maturity. It is also the highest
return per hour of anything in interview preparation, because more people read the README than will ever
interview me, and it converts a repository into an argument. The one hard requirement is that the run
instruction actually works on a clean machine — a README whose first command fails is worse than no
README.

**Q: Your commit history is forty commits called "update". What does that tell someone?**
That I have never worked somewhere history mattered, which is a fair inference. The fix is not rewriting
it into something suspiciously perfect — a visible improvement partway through the log is a better signal
than a fabricated clean history. Going forward, the subject is imperative and the body explains why, not
what: the diff already shows what changed, so the message exists to explain the reason, which is what
makes a log readable a year later.

**Q: This service class is nine hundred lines. Defend it.**
I would not defend it, I would describe it accurately. It started as order creation and accumulated
pricing and notification, and it should be three things: the order aggregate owning the invariants,
pricing as a separate policy because it changes for a different reason, and notification behind the
outbox. I refactored the reporting module along exactly those lines and it took about a day. This one is
still like that because it has not hurt me enough yet — which is a real engineering answer. Knowing where
your debt is, what it costs and why it is not top of the list beats both denial and apology.

**Q: Can you add a field to this endpoint right now?**
Yes — and being fluent in my own codebase is something I practise, because fumbling in my own project
looks careless in a way that has nothing to do with ability. I would narrate as I go: the request DTO
here, the mapping, the entity, the migration, and the test that would have caught it missing. The
questions in this category — add a field, write a test for this method, show me where tenancy is enforced
— are really asking whether the structure I described in the abstract is the structure that actually
exists.

## Mini task

1. ⭐⭐ Rewrite your **README** with all seven sections, including the architecture diagram, the decision
   table with costs, "what I'd do differently" and "known limitations".
2. ⭐⭐ Test **`docker compose up` on a clean machine** — a fresh container or someone else's laptop.
3. ⭐ Open your repo as a stranger and **time yourself** finding: the outbox, the tenancy check, the
   auth filter, the slowest test.
4. ⭐⭐ Audit your **test folder.** Count tests that assert behaviour vs tests that assert a mock.
5. ⭐ Fix the **three worst-named tests** so their names state the behaviour.
6. ⭐⭐ Read your **last thirty commit messages.** Write down what they say about you.
7. ⭐ Write your next ten commits with **imperative subjects and why-bodies.**
8. ⭐⭐ Find your **largest file.** Write the three-part defence for it, out loud.
9. ⭐ Do the same for the **worst piece of code you know is in there.**
10. ⭐⭐ Have someone open your repo cold and ask you to **add a field and write a test**, live, narrated.

# 🚪 Exit questions

1. Give the six things a reviewer clicks, in order.
2. What does each one signal?
3. Why does an empty test folder undo your testing answer?
4. Give the seven README sections and name the two that are rare.
5. Why is the README the highest return-per-hour work here?
6. What must be true of the run instruction, and why?
7. What do forty "update" commits say, and what does one giant initial commit say?
8. Give the commit message format and what the body is for.
9. Why not rewrite a bad history?
10. Give the three-part defence of known debt.
11. Why is "it hasn't hurt me enough yet" a legitimate answer?
12. Name four live code questions and what each really tests.

## 🎙️ Articulation drill

**Two minutes:** share your screen, open your repo cold, and give the guided tour.

**⭐ Lead with the README's architecture section, then the one file you are proudest of and why, then —
deliberately — the file you are least proud of, with the three-part defence. Volunteering the weak spot
before it is found is the whole move: it converts a discovery into a disclosure.**

**⭐ Then be ready for the pivot: "write me a test for this method." Narrate the search, name the
behaviour you are asserting before you write it, and say out loud why you are not asserting on the mock.
That single sentence tells them more about your testing philosophy than any answer you could give in the
abstract.**
