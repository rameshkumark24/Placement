# Part 1 — L-070 · The coordination primitives

## `CountDownLatch` — a one-shot gate

```java
CountDownLatch latch = new CountDownLatch(3);

// workers
pool.submit(() -> { doWork(); latch.countDown(); });   // ← in a finally, always

latch.await();                                          // blocks until the count reaches 0
System.out.println("all three finished");
```

**The count only goes down and never resets.** Once it hits zero, `await()` returns immediately
forever after. That one-shot nature is the defining property: use it for *this has happened*, not
for a recurring rendezvous.

Two shapes it is used in:

```java
// A. Wait for N workers to finish
CountDownLatch done = new CountDownLatch(workers);
// each worker: try { ... } finally { done.countDown(); }
done.await(30, TimeUnit.SECONDS);       // ← ALWAYS the timeout overload

// B. Start N workers simultaneously (the "starting pistol")
CountDownLatch start = new CountDownLatch(1);
// each worker: start.await(); then run
start.countDown();                       // release everyone at once
```

Shape B is how you write a benchmark that actually measures contention rather than thread startup —
you will use it in today's mini task.

**`countDown()` must be in a `finally`.** If a worker throws before counting down, `await()` waits
forever. That, plus the timeout overload, are the two rules; either one alone leaves a hang.

Real uses: waiting for application startup (all caches warmed before accepting traffic), and
deterministic tests of concurrent code.

## `Semaphore` — N permits

```java
Semaphore sem = new Semaphore(5);        // 5 concurrent users allowed

sem.acquire();                            // blocks if none left
try { useConstrainedResource(); }
finally { sem.release(); }                // ← finally, always
```

A counting semaphore limits **how many threads may be inside a region at once**. `new Semaphore(1)`
is a *binary* semaphore, which behaves like a lock with one crucial difference: **it has no owner**,
so one thread may acquire and a different thread may release. That is a feature for signalling
between threads and a hazard if you meant a lock — a lock is reentrant and owner-checked, a
semaphore is neither.

Its real use is **resource throttling**, and this is the important framing: your thread pool bounds
your own concurrency, but a semaphore bounds concurrency *to something else*.

```java
// Never send more than 10 concurrent requests to a partner API,
// regardless of how many threads we have.
private final Semaphore apiLimit = new Semaphore(10);

public Response call(Request r) throws InterruptedException {
    if (!apiLimit.tryAcquire(2, TimeUnit.SECONDS))     // bounded wait, not indefinite
        throw new OverloadedException();
    try { return client.send(r); }
    finally { apiLimit.release(); }
}
```

This is a **bulkhead** (Day 069) at finer granularity, and it is how you honour a partner's rate
limit or protect a connection pool from being exhausted by one subsystem.

Two traps: `release()` without a prior `acquire()` **increases the permit count** — the semaphore
does not track who holds what, so a stray release permanently weakens the limit. And a `tryAcquire`
whose result you ignore is a limit that does nothing.

## `CyclicBarrier` — a reusable rendezvous

```java
CyclicBarrier barrier = new CyclicBarrier(4, () -> System.out.println("phase complete"));

// each of 4 threads:
for (int phase = 0; phase < 10; phase++) {
    computePhase(phase);
    barrier.await();                     // waits until all 4 arrive, then ALL proceed
}
```

The differences from a latch are the ones the interview asks about:

| | `CountDownLatch` | `CyclicBarrier` |
|---|---|---|
| Reusable | **no** | **yes** — resets automatically |
| Who waits | any thread, on the count | **the participating threads themselves** |
| Counts | down, by any thread | arrivals, one per participant |
| Barrier action | none | optional `Runnable` run by the last arriver |
| On failure | nothing | **`BrokenBarrierException` for everyone** |

That last row is a real behaviour: if any waiting thread is interrupted or times out, the barrier
*breaks* and every other participant gets a `BrokenBarrierException`. This is deliberate — a
phase-synchronous computation cannot proceed with a missing participant. Reset with `barrier.reset()`.

Use it for iterative parallel algorithms: simulations, matrix computations, anything where all
workers must finish phase N before any starts phase N+1.

`Phaser` (Java 7) generalises it with a variable number of participants that can register and
deregister; know the name.

## `Exchanger` — a two-party swap

```java
Exchanger<Buffer> ex = new Exchanger<>();
// producer: emptyBuffer = ex.exchange(fullBuffer);
// consumer: fullBuffer  = ex.exchange(emptyBuffer);
```

Two threads meet and swap objects. Niche — buffer recycling in a pipeline — but worth recognising.

## Choosing

```
Wait once for N things to complete?          → CountDownLatch
Limit concurrent access to K?                → Semaphore
All threads must finish phase N repeatedly?  → CyclicBarrier
Hand work from producers to consumers?       → BlockingQueue     ← usually the answer
Two threads swap a buffer?                   → Exchanger
```

# Part 2 — Producer-consumer

## Why it is the fundamental concurrency pattern

Producers create work, consumers process it, and a bounded queue sits between them. It gives you
four things at once:

1. **Decoupling** — neither side knows about the other.
2. **Rate smoothing** — bursts are absorbed by the queue.
3. **Backpressure** — when the queue is full, producers block. The system throttles itself.
4. **Independent scaling** — add consumers without touching producers.

Point 3 is the one people skip and the one that matters most. **A bounded queue is the mechanism
that stops a fast producer from destroying a slow consumer** — exactly the same argument as Day
069's bounded work queue, which is unsurprising since a thread pool *is* a producer-consumer system.

## `BlockingQueue`

```java
BlockingQueue<Task> queue = new ArrayBlockingQueue<>(100);

// producer
queue.put(task);                              // BLOCKS when full  ← the backpressure

// consumer
Task t = queue.take();                        // BLOCKS when empty
```

The four method families, and picking the wrong one is a classic bug:

| Operation | Throws | Returns special | **Blocks** | Times out |
|---|---|---|---|---|
| Insert | `add` | `offer` (false) | **`put`** | `offer(e, t, u)` |
| Remove | `remove` | `poll` (null) | **`take`** | `poll(t, u)` |
| Examine | `element` | `peek` | — | — |

`offer()` returning `false` and being ignored is silent data loss. `put()`/`take()` are what you
want for a pipeline; the timed variants are what you want when a stall must be detectable.

The implementations:

| Implementation | Bounded | Notes |
|---|---|---|
| `ArrayBlockingQueue` | **yes** | Circular array, one lock, fair option. The default choice. |
| `LinkedBlockingQueue` | optionally | Separate head/tail locks → higher throughput; **unbounded by default** ⚠️ |
| `SynchronousQueue` | capacity 0 | A direct hand-off; `put` waits for a `take`. Used by `newCachedThreadPool`. |
| `PriorityBlockingQueue` | unbounded | Ordered by comparator; no backpressure |
| `DelayQueue` | unbounded | Elements become available at a time — scheduling |
| `LinkedTransferQueue` | unbounded | `transfer()` waits for a consumer to receive |

You wrote `ArrayBlockingQueue` yourself yesterday-but-one — Day 067's `BoundedBuffer` **is** its
design: one lock, two conditions, a circular array.

## The poison pill — shutting a pipeline down

How do consumers know there is no more work? Not by an empty queue — empty just means "not right
now".

```java
private static final Task POISON = new Task("__STOP__");

// producer, when finished:
for (int i = 0; i < CONSUMER_COUNT; i++) queue.put(POISON);   // one per consumer

// consumer loop:
while (true) {
    Task t = queue.take();
    if (t == POISON) { queue.put(POISON); break; }   // optional: pass it on
    process(t);
}
```

One pill per consumer, or re-insert before breaking so it propagates. The alternative is a
`volatile boolean running` flag plus `poll(timeout)` so consumers wake up periodically to check it —
which is better when consumers must also respond to a shutdown that arrives mid-queue.

## Code to type — the full pipeline

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class ProducerConsumer {

    record Task(int id) {}
    static final Task POISON = new Task(-1);

    public static void main(String[] args) throws Exception {
        BlockingQueue<Task> queue = new ArrayBlockingQueue<>(10);   // small, to SHOW backpressure
        AtomicInteger processed = new AtomicInteger();
        int producers = 2, consumers = 3, perProducer = 50;

        CountDownLatch producersDone = new CountDownLatch(producers);
        CountDownLatch start = new CountDownLatch(1);               // starting pistol

        ExecutorService pool = Executors.newFixedThreadPool(producers + consumers);

        for (int p = 0; p < producers; p++) {
            final int pid = p;
            pool.submit(() -> {
                try {
                    start.await();
                    for (int i = 0; i < perProducer; i++) {
                        long t0 = System.nanoTime();
                        queue.put(new Task(pid * 1000 + i));
                        long blockedMs = (System.nanoTime() - t0) / 1_000_000;
                        if (blockedMs > 5)
                            System.out.printf("producer %d BLOCKED %d ms (backpressure)%n",
                                              pid, blockedMs);
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    producersDone.countDown();                      // finally — always
                }
            });
        }

        for (int c = 0; c < consumers; c++) {
            pool.submit(() -> {
                try {
                    while (true) {
                        Task t = queue.take();
                        if (t == POISON) break;
                        Thread.sleep(20);                           // consumers are slower
                        processed.incrementAndGet();
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });
        }

        long t0 = System.currentTimeMillis();
        start.countDown();                                          // fire

        producersDone.await();
        for (int i = 0; i < consumers; i++) queue.put(POISON);       // one pill each

        pool.shutdown();
        pool.awaitTermination(60, TimeUnit.SECONDS);

        System.out.printf("processed %d in %d ms%n",
                processed.get(), System.currentTimeMillis() - t0);
        System.out.println("queue empty: " + queue.isEmpty());
    }
}
```

Run it. **The "BLOCKED … (backpressure)" lines are the lesson** — producers generate faster than
three consumers can process, the 10-slot queue fills, and `put()` blocks. The system self-regulates
with no configuration, no monitoring, and no dropped work.

Then set the capacity to `Integer.MAX_VALUE` and re-run: the messages disappear, the producers
finish instantly, and the queue holds 100 tasks in memory. Scale that to a real workload and it is
the `OutOfMemoryError` from Day 069.

## Semaphore vs a bounded queue — which throttle?

Both limit load; they limit *different things*.

- **Bounded queue** limits **queued work** and blocks the producer. Use it between stages you own.
- **Semaphore** limits **concurrent in-flight operations** against a resource. Use it around a call
  to something external.

You often want both: a bounded queue in front of a pool of 20 threads, and a semaphore of 5 around
the partner API call those threads make.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `countDown()` not in a `finally` | `await()` hangs forever on a worker exception |
| `await()` with no timeout | An unrecoverable hang instead of a logged failure |
| Reusing a `CountDownLatch` | It does not reset; `await` returns immediately |
| `CyclicBarrier` where a latch belongs (or vice versa) | Wrong semantics; usually a hang |
| Ignoring `BrokenBarrierException` | Silent phase corruption |
| `release()` without `acquire()` | Permit count grows; the limit erodes |
| Ignoring `tryAcquire`'s result | The limit does nothing |
| `offer()` instead of `put()` | Silent data loss when full |
| Unbounded queue in a pipeline | No backpressure; OOM |
| Empty queue read as "work is finished" | Consumers exit early |
| Forgetting one poison pill per consumer | Consumers hang at `take()` |

## Interview questions

**Q: `CountDownLatch` vs `CyclicBarrier`?**
A latch is one-shot and counts down — any thread can count, any thread can wait, and once it reaches
zero it stays there. A barrier is reusable, the participants themselves wait for each other, it
resets after each release, and it can run a barrier action. Latch = "wait for N events"; barrier =
"all of us meet here, repeatedly".

**Q: Is a binary semaphore the same as a lock?**
No. A semaphore has no owner and is not reentrant, so a different thread can release it — useful for
signalling, dangerous if you meant mutual exclusion.

**Q: What is backpressure and how do you get it?**
The mechanism by which a slow consumer throttles a fast producer. A bounded queue provides it for
free: `put()` blocks when full. Unbounded queues remove it and convert overload into memory
exhaustion.

**Q: How do you shut down a producer-consumer pipeline?**
Poison pills — one per consumer — or a `volatile` running flag with `poll(timeout)`. An empty queue
is not a termination signal.

**Q: Which `BlockingQueue` and why?**
`ArrayBlockingQueue` when you want a hard bound and predictable memory; `LinkedBlockingQueue` with an
explicit capacity when throughput matters (separate head/tail locks); `SynchronousQueue` for direct
hand-off. Never rely on the unbounded defaults.

**Q: How do you limit concurrent calls to an external API?**
A semaphore sized to the allowed concurrency, acquired with a bounded `tryAcquire` and released in a
`finally` — independent of how many threads exist.

## 🎙️ Articulation drill

Two minutes: **"Design a system that ingests events faster than it can process them."**

Bounded queue for backpressure, a consumer pool sized by the I/O formula, a semaphore around the
downstream dependency, poison-pill shutdown, and an explicit decision about what happens when the
queue is full — block the producer, or reject with a 429 and let the client retry with jitter. That
last decision is the one interviewers push on, so have an answer.
