# Day 315

**L-315** · Splitwise — money, the penny problem, and settlement

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Split £10 between three people. Now make the numbers add up.**
>
> That is the whole interview. Everything else — groups, expenses, split strategies — is
> straightforward modelling, and **the candidate who says "£3.33 each" without noticing the missing
> penny has failed the only hard part of the problem.**

---

# Part 1 — ⭐ The model

```
   User ──── * GroupMembership * ──── Group
                                        │ 1
                                        ├──── * Expense          ⭐ an EVENT, never mutated
                                        │        ├─ paidBy: UserId
                                        │        ├─ amount: Money
                                        │        └─ splits: List<Split>   ⭐ who owes what
                                        │
                                        └──── * Settlement       ⭐ also an event

   SplitStrategy «interface»   ⭐ EQUAL | EXACT | PERCENTAGE | SHARES
```

| Decision | ⭐ Answer |
|---|---|
| ⭐ **Is an expense mutable?** | ⭐⭐ **No — it is an event. An "edit" is a reversal plus a new expense.** |
| ⭐ Is `Money` a value object? | ⭐ **yes** (Day 304) — and `BigDecimal`, never `double` (Day 042B) |
| Do groups own expenses? | ⭐ yes — the group is the aggregate (Day 305) |
| ⭐ **Are balances stored or derived?** | ⭐ **derived, then cached** — see Part 3 |

> **⭐ The immutable-expense decision is the one to volunteer.** *"An expense is a financial fact.
> If someone edits a six-month-old dinner, everyone's history silently changes and nobody can
> reconcile. So an edit writes a reversal and a replacement, and the ledger is append-only."*
> **That is Day 290's frozen-inputs argument arriving in a new problem**, and it is the mark of
> someone who has thought about money systems.

## ⭐ Split strategies

```java
public interface SplitStrategy {
    List<Split> split(Money total, List<UserId> participants, SplitInput input);
}
```

| Strategy | Input | ⭐ Validation that must exist |
|---|---|---|
| ⭐ **Equal** | none | ⭐ **the remainder — Part 2** |
| **Exact** | an amount each | ⭐ **must sum EXACTLY to the total — reject otherwise** |
| **Percentage** | a percentage each | ⭐ **must sum to exactly 100 — then the remainder problem again** |
| Shares | integer weights | proportional, then remainder |

⚠️ **Every strategy except "exact" ends in the same place: an indivisible remainder.** That is the
tell that this is one problem, not four.

# Part 2 — ⭐⭐ The penny problem

```
⭐ £10.00 split three ways.
⭐ 10.00 / 3 = 3.3333…
⭐ Round each to 3.33  →  3.33 × 3 = 9.99  →  ⭐ ONE PENNY HAS VANISHED.
```

**⭐ Vanishing pennies are not cosmetic.** They accumulate across thousands of expenses, balances stop
netting to zero, and the system loses the one property it must have: **the sum of all balances in a
group is exactly zero, always.**

## ⭐ The largest-remainder method

```java
public List<Split> splitEqually(Money total, List<UserId> participants) {
    int n = participants.size();
    long totalMinor = total.toMinorUnits();                    // ⭐ WORK IN PENNIES. Integers only.

    long base      = totalMinor / n;                           // ⭐ 333
    long remainder = totalMinor % n;                           // ⭐ 1 penny left over

    List<Split> splits = new ArrayList<>(n);
    for (int i = 0; i < n; i++) {
        long share = base + (i < remainder ? 1 : 0);           // ⭐ first `remainder` people pay 1 more
        splits.add(new Split(participants.get(i), Money.ofMinor(share, total.currency())));
    }
    return splits;                                             // ⭐ 3.34 + 3.33 + 3.33 = 10.00 EXACTLY
}
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐⭐ **Compute in minor units (integers)** | ⭐⭐ **there is no rounding error in integer arithmetic** |
| ⭐ **Distribute the remainder, do not drop it** | ⭐ the total is preserved by construction |
| ⭐ **Make the recipient deterministic** | ⭐ **not random — the same input must give the same split** (Day 290) |
| ⭐ Rotate who absorbs it across expenses | ⭐ fairness over time, if the product wants it |
| ⭐ **Assert `sum(splits) == total`** | ⭐ **a property test over thousands of random inputs** |

> **⭐ The sentence that wins this problem: "I do all money arithmetic in integer minor units and
> distribute the remainder deterministically, so the splits always sum exactly to the total — and I
> test that as a property over random amounts and party sizes."**

⚠️ **Percentages need the same treatment** — 33.33% three ways does not make 100%. **Compute each
share in minor units, then apply largest-remainder to the leftover.**

⚠️ **And the payer's own share:** if Alice pays £10 for three, Alice is owed £6.67, not £10.
**Getting this backwards is the single most common bug in a first implementation** — write the test.

# Part 3 — ⭐ Balances and settlement

## ⭐ Two representations

| | ⭐ Pairwise (`A owes B £5`) | ⭐ Net per user (`A: −£12`) |
|---|---|---|
| Memory | ⭐ O(n²) worst case | ⭐ **O(n)** |
| ⭐ **Answers "who do I pay?"** | ⭐ **directly** | ⭐ needs the simplification step |
| Matches user expectation | ⭐ **yes — people remember pairwise debts** | less intuitive |
| ⭐ **Simplification** | harder | ⭐ **natural** |

> **⭐ Splitwise itself keeps pairwise balances and offers simplification as an opt-in feature, for a
> real product reason: people object to being told to pay someone they never transacted with.**
> Saying that shows you thought about the domain, not just the graph algorithm.

**⭐ Derived or stored?** Derive from the expense log (it is the source of truth), **cache the
result, and invalidate on every new expense.** For a group with 100,000 expenses, keep a materialised
balance updated incrementally — **and re-derive periodically to detect drift.** That reconciliation
job is a strong detail: **a cached balance that has drifted from the ledger is a money bug you must
be able to detect.**

## ⭐ Debt simplification — the greedy algorithm

```
⭐ Net balances:  A: −40   B: −20   C: +30   D: +30      ⭐ (negative = owes)

⭐ Greedy: repeatedly match the largest debtor with the largest creditor.
⭐   A → C  30   (A: −10, C: 0)
⭐   A → D  10   (A:   0, D: −20 remaining… i.e. D still owed 20)
⭐   B → D  20   (B:   0, D: 0)
⭐ ⇒ 3 transfers instead of up to 4.
```

```java
// ⭐ Two priority queues: max-heap of debtors, max-heap of creditors
while (!debtors.isEmpty() && !creditors.isEmpty()) {
    var debtor   = debtors.poll();
    var creditor = creditors.poll();
    long amount  = Math.min(debtor.owes(), creditor.owed());
    transfers.add(new Transfer(debtor.user(), creditor.user(), Money.ofMinor(amount, ccy)));
    if (debtor.owes()   > amount) debtors.add(debtor.minus(amount));       // ⭐ push the remainder back
    if (creditor.owed() > amount) creditors.add(creditor.minus(amount));
}
```

| ⭐ Property | ⭐ Say it |
|---|---|
| ⭐ **Each step zeroes at least one person** | ⭐ **so at most n−1 transfers** |
| ⭐ **Not provably minimal** | ⭐⭐ **minimising transfers is NP-hard (subset-sum); greedy is a good heuristic** |
| ⭐ Requires balances to sum to zero | ⭐ **which the penny fix guarantees** |
| Deterministic tie-breaking | ⭐ otherwise the suggestion changes between refreshes |

> **⭐ Saying "this is greedy, it gives at most n−1 transfers, and the true minimum is NP-hard so I'm
> not claiming optimality" is exactly the kind of honest bound that scores.** Claiming it is optimal
> when asked is a fail.

# Part 4 — ⭐ Concurrency, and multi-currency

**⭐ Shared mutable state: the group's cached balances.**

```
⭐ Two people add expenses to the same group at the same time.
⭐ Both read balance −40, both write their delta, one update is lost.
```

| ⭐ Fix | Note |
|---|---|
| ⭐ **The ledger is append-only, so expenses never conflict** | ⭐ **the fundamental protection — writes are inserts** |
| ⭐ Balance updates as **relative deltas**, not absolute writes | `SET balance = balance + delta` — commutative |
| ⭐ **Optimistic version on the group** (Day 165) for absolute recomputes | the loser retries |
| Settlement needs care | ⭐ **two people settling the same debt concurrently — an idempotency key** (Day 122) |

> **⭐ The nice property to name: because expenses are immutable and balances are derived, concurrency
> is almost free — two inserts never conflict. The only contention is on the cached balance, and it
> can always be rebuilt from the log.** That is a genuine architectural payoff of the event decision
> in Part 1, and connecting the two is what makes the answer coherent.

## ⭐ Multi-currency — the extension that changes everything

| Question | ⭐ Answer |
|---|---|
| ⭐ **Can a group hold mixed currencies?** | ⭐ **the crux — if yes, "the balance" is a vector, not a number** |
| ⭐ **Which exchange rate?** | ⭐⭐ **the rate at expense time, stored ON the expense — never a live rate** |
| Can you net across currencies? | ⭐ only by fixing a group currency and converting at a recorded rate |
| Who bears the FX difference? | ⭐ a policy decision — say it must be one |

**⭐ The rule: store the original amount and currency, plus the converted amount and the rate used,
on the expense itself.** Re-converting later with today's rate makes historical balances change,
**which is the same class of bug as a mutable expense** — and pointing that out ties the whole
problem together.

---

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ `double` for money | ⭐ Day 042B — cumulative, silent, in a ledger |
| ⭐⭐ **£3.33 × 3 = £9.99** | ⭐⭐ **the missing penny — the whole interview** |
| ⭐ Rounding each share independently | the total is not preserved |
| ⭐ Random or non-deterministic remainder | the same expense splits differently on recompute |
| ⭐ **Mutable expenses** | ⭐ history changes; reconciliation impossible |
| ⭐ The payer owing their own full share | ⭐ **the most common first-implementation bug** |
| Percentages not validated to 100 | silent under- or over-allocation |
| ⭐ Stored balances with no re-derivation | ⭐ drift with no detector |
| Absolute balance writes | lost updates under concurrency |
| ⭐ Claiming minimal transfers | ⭐ it is NP-hard — greedy is a heuristic |
| Live FX rates for old expenses | history changes on every refresh |

## Interview questions

**Q: Split £10 three ways.**
Not £3.33 each — that is £9.99 and a penny has vanished. I compute in integer minor units: 1000 pence
divided by three is 333 with a remainder of one, and I give that penny to the first participant by a
deterministic rule. Splits then sum exactly to the total by construction, and I assert that as a
property test over random amounts and party sizes. The same applies to percentages and shares.

**Q: Are expenses mutable?**
No. An expense is a financial fact, so an edit is a reversal plus a replacement and the ledger is
append-only. If a six-month-old expense could be changed, everyone's historical balances would
silently change and there would be no way to reconcile a dispute. It also makes concurrency almost
free, because two people adding expenses are doing two inserts that cannot conflict.

**Q: Pairwise balances or net balances?**
Pairwise, with simplification offered rather than imposed. Net is O(n) and simplifies naturally, but
people object to being told to pay someone they never transacted with — so the product reason wins.
Either way I derive from the expense log, cache the result, and run a periodic re-derivation to
detect drift, because a cached balance that disagrees with the ledger is a money bug you need a
detector for.

**Q: How do you minimise the number of settlement payments?**
Greedily match the largest debtor with the largest creditor. Each step zeroes at least one person, so
it is at most n−1 transfers. I would not claim it is minimal — that is subset-sum and NP-hard — but
greedy is a good heuristic and it is deterministic if I break ties consistently. It also relies on
balances summing to exactly zero, which is what the remainder handling guarantees.

**Q: Now add multiple currencies.**
The key decision is whether a group can hold mixed currencies; if it can, a balance is a vector per
currency rather than a number. Either way the exchange rate used goes on the expense at the time it
is recorded, along with the original amount — because re-converting old expenses at today's rate
makes historical balances move, which is the same bug as a mutable expense. Who bears the FX
difference is a policy decision, and it needs to be an explicit one.

## Mini task

1. Implement `Money` in **integer minor units** with a currency. Make `double` impossible.
2. ⭐ Implement equal split with **largest-remainder**, then write the property test: for 10,000
   random amounts and party sizes 2–20, **assert the splits sum exactly to the total.**
3. **Write the naive version first and watch the property test fail.** Record the total pennies lost
   over 10,000 splits.
4. Implement exact, percentage and share strategies. **Validate each input and reject bad ones with
   a specific error.**
5. ⭐ Write the test for **the payer's own share** — Alice pays £10 for three and is owed £6.67.
6. Build the append-only ledger and **derive balances.** Then add a cache, and **write the
   reconciliation job that detects drift.** Corrupt the cache deliberately and confirm it fires.
7. ⭐ Implement greedy simplification with two heaps. **Assert transfers ≤ n−1 and that all balances
   reach zero.** Find a case where a human could do better with fewer transfers.
8. ⭐ Two threads adding expenses to one group concurrently: **confirm no lost update.** Then two
   threads settling the same debt — **add an idempotency key and confirm one settlement.**

# 🚪 Exit questions

1. Why is an expense an event rather than a mutable row?
2. Give the four split strategies and the validation each needs.
3. Show £10 three ways failing, then fix it.
4. Why integer minor units?
5. Why must the remainder recipient be deterministic?
6. What property must always hold across a group's balances?
7. Compare pairwise and net balances, including the product reason.
8. Stored or derived — and what job detects drift?
9. Give the greedy algorithm, its bound, and its honest limitation.
10. Why does the immutable ledger make concurrency easy?
11. Which rate applies to an old expense, and why?
