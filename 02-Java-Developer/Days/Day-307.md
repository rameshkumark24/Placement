# Day 307

**L-307** · Refactoring the flagship into clean architecture — the applied day

**Time:** 3+ hrs · **Mode:** BUILD

> **⭐ Nine days of principles are worth nothing until they survive contact with code you already
> wrote.**
>
> Today you refactor your Stage 7 flagship — **not all of it.** One module, in seven ordered steps,
> with the test suite green at every step, and a measured before/after number at the end. **The
> discipline of stopping is part of the exercise.**

---

# Part 1 — ⭐ Before you change anything: measure

**⭐ A refactor with no baseline is an opinion.** Thirty minutes, three numbers:

| Measurement | ⭐ How |
|---|---|
| ⭐ **Change cost** (Day 298) | ⭐ pick 3 plausible changes; **count files touched** |
| ⭐ **Domain test speed** | ⭐ **can any business rule be tested without Spring? Time it.** |
| ⭐ **Dependency violations** | ⭐ write the ArchUnit rules **first, expect failures**, record the count |
| Co-change coupling | top ten file pairs from git (Day 298) |
| Largest service | methods + constructor parameters (Day 302) |

```java
// ⭐ Write these BEFORE refactoring. They are your progress bar.
@ArchTest static final ArchRule domain_is_pure = ...        // ⭐ expect: 34 violations
@ArchTest static final ArchRule no_cycles = ...             // ⭐ expect: 3 cycles
@ArchTest static final ArchRule no_entities_in_app = ...    // ⭐ expect: 11 violations
```

> **⭐ Put the starting numbers in the ADR now**, because after the refactor you will not remember
> them and "it feels cleaner" is not a result. **These five numbers are what you show an interviewer,
> not the folder structure.**

## ⭐ Choose the module — and choose the right one

| Choose the module with… | ⭐ Avoid |
|---|---|
| ⭐ **the most business rules** | ⭐ **anything CRUD — Day 300 says do not** |
| ⭐ **the most invariants that are currently bypassable** | the module you understand least |
| ⭐ good existing test coverage | the one shipping a feature this week |
| a rule you have already had a bug in | ⭐ the biggest one — pick the *most rule-dense*, not the largest |

**⭐ One module. Write down which, and write down which modules you are deliberately not touching** —
that list is Day 288's discipline applied to your own current code.

# Part 2 — ⭐⭐ The seven steps, in order

**⭐ The order is not arbitrary: each step is behaviour-preserving on its own, and each one makes the
next cheaper. Commit after every step. Tests green at every commit.**

### ⭐ Step 1 — Value objects first (Day 304)

**⭐ Cheapest, highest yield, and it needs no structural change.** Replace primitives with types:
`Money`, `EmailAddress`, `OrderId`, `Quantity`, `DateRange`.

```
⭐ Success signal: the compile errors. Each one is a place a swap or a missing check was possible.
⭐ Then DELETE the validation those types made redundant, and count the deletions.
```

### ⭐ Step 2 — Close the invariants (Day 304, level 2)

Make state-changing setters private; expose named transitions (`ship()`, `cancel()`, `approve()`).

```
⭐ Success signal: every caller that no longer compiles was bypassing a rule.
⭐ Write each one down — that list belongs in the ADR.
```

### ⭐ Step 3 — Find the aggregate (Day 305)

Draw the boundary. Replace cross-aggregate object references with ids. Stop exposing mutable child
collections. **Delete the child repositories.**

```
⭐ Success signal: you can state one invariant that must hold at commit — and you demote at least
⭐ one candidate "invariant" to eventual consistency, deliberately.
```

### ⭐ Step 4 — Extract the ports (Day 300, Day 301)

Define `Orders`, `Payments`, `Clock` in the application package, **in domain language**. Move the
Spring Data interface behind a package-private adapter.

```
⭐ Success signal: the application package no longer imports org.springframework.data.
⭐ Delete every derived query name that encoded a business rule.
```

### ⭐ Step 5 — Split the service by use case (Day 302)

One class per use case, verb-named. `@Transactional` on those classes only. Commands as records.

```
⭐ Success signal: no application service contains an `if` about the business.
⭐ Record the dependency count per class — compare with the old constructor.
```

### ⭐ Step 6 — Separate the domain model from the entity (Day 300)

**⭐ The expensive step. Do it last, and only if steps 1–5 left a domain worth protecting.**

```
⭐ Success signal: ONE domain test with no Spring context. Time it. That number is the deliverable.
⭐ Write the mapper round-trip property test in the same commit — never later.
```

⚠️ **This is the step to skip if the module turned out to be thinner than you thought.** Skipping it
deliberately, and writing why, is a better outcome than a mapper nobody needed. **Steps 1–5 deliver
most of the value.**

### ⭐ Step 7 — Ratchet it (Day 299)

Turn the ArchUnit rules on for this package only. **Freeze violations elsewhere; fail the build on
new ones.**

```java
@ArchTest static final ArchRule domain_is_pure =
    classes().that().resideInAPackage("..orders.domain..")   // ⭐ scoped to the refactored module
        .should().onlyDependOnClassesThat().resideInAnyPackage("..orders.domain..", "java..");
```

# Part 3 — ⭐ The rules that keep this from becoming a rewrite

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐ **Tests green at every commit** | ⭐ a red suite means you cannot tell refactor from regression |
| ⭐ **No behaviour changes** | ⭐ **if you find a bug, write it down and fix it separately** |
| ⭐ **Timebox it** | ⭐ refactoring is not a project; it is how you work |
| ⭐ **One module** | scope creep here is indistinguishable from a rewrite |
| ⭐ **Commit per step** | ⭐ every step is independently revertible |
| ⭐ **Stop at the agreed scope** | ⭐ Day 296's discipline |

⚠️ **The characterisation-test move (Day 288) applies to your own code too.** If a rule has no test,
write the test *first* — asserting what it does now, not what it should do. **You cannot refactor
untested behaviour; you can only rewrite it and hope.**

## ⭐ The four ways this goes wrong

| Failure | ⭐ Symptom | ⭐ Fix |
|---|---|---|
| ⭐ **The big-bang refactor** | 200 files in one branch, unmergeable | ⭐ one module, commit per step |
| ⭐ **Ports for everything** | ⭐ an interface with one implementation, forever, over a CRUD table | ⭐ Day 300: decide per module |
| ⭐ **Refactoring while fixing bugs** | ⭐ **you can no longer bisect** (Day 087) | separate commits, separate PRs |
| ⭐ **Stopping at the folders** | packages renamed, entities still everywhere | ⭐ the ArchUnit rules decide, not the tree |

> **⭐ The last one is the most common and the most embarrassing in an interview.** Someone says "we
> use clean architecture" and their domain package imports `jakarta.persistence`. **The folder
> structure is the least important artefact of this entire day.**

# Part 4 — ⭐ Measure again, and write it down

**⭐ Re-run all five measurements. Then write the ADR.**

```markdown
# ADR-0xx — Clean architecture in the orders module

## Status
Accepted — applied to `orders` only.

## Context
⭐ Adding a field touched 7 files across 4 packages. No business rule could be tested
⭐ without a Spring context (fastest domain test: 2.1 s). 34 dependency-rule violations.

## Decision
⭐ Ports and adapters for `orders`. ⭐ NOT for `catalog` or `notifications` — those are CRUD,
⭐ and the mapping cost would exceed the benefit (Day 300).

## Consequences
⭐ + Domain rules test in 4 ms with no framework.       ⭐ + 11 bypassable invariants closed.
⭐ + A field change now touches 3 files in 1 package.   ⭐ − An OrderEntity + mapper to maintain.
⭐ − Two models to keep in step; round-trip property test added to mitigate.
⭐ − Pagination for order lists now bypasses the repository deliberately.

## Revisit when
⭐ The mapper exceeds ~150 lines, or a second module needs the same treatment
⭐ (then extract the pattern rather than copying it).
```

**⭐ The before/after table is the artefact you show an interviewer:**

| Measure | Before | After |
|---|---|---|
| Files touched to add a field | ⭐ 7 across 4 packages | ⭐ **3 in 1 package** |
| ⭐ **Fastest domain rule test** | ⭐ **2.1 s (`@SpringBootTest`)** | ⭐⭐ **4 ms (`new`)** |
| Bypassable invariants | ⭐ 11 | ⭐ **0** |
| Application-layer dependencies (max) | 14 | ⭐ **4** |
| ArchUnit violations in module | 34 | ⭐ **0, enforced in CI** |

> **⭐ "Two point one seconds to four milliseconds" is a sentence an interviewer remembers.** "We
> refactored to hexagonal architecture" is not.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No baseline measurements | ⭐ the result is an opinion |
| ⭐ Refactoring a CRUD module | ⭐ ceremony, and the team concludes the whole idea is bad |
| Behaviour changes mixed in | you cannot tell a refactor from a regression |
| ⭐ Refactoring untested rules | ⭐ that is a rewrite, and it will lose behaviour |
| Skipping step 1 | the expensive steps get done on unclear concepts |
| ⭐ Doing step 6 first | ⭐ a mapper for a model you had not yet found |
| ⭐ ArchUnit rules as a hard gate on the whole repo | 34 failures, and the rules get deleted |
| Renaming folders and stopping | the dependency arrows never moved |
| ⭐ Not writing the ADR | ⭐ the reasoning is gone in a month |

## ✅ Done when

- ⭐ **All five measurements recorded before and after**
- ⭐ **One domain rule tests with no Spring context**, and you have the timing
- ⭐ Every bypassable invariant in that module is closed, **with the caller list written down**
- ⭐ ArchUnit rules pass for the module and **run in CI as a ratchet**
- ⭐ **The ADR names the modules you deliberately did not refactor, and why**
- ⭐ **The other modules are untouched** — you stopped

# 🚪 Exit questions

1. What five things do you measure before starting, and why before?
2. How do you choose the module — and which ones do you refuse?
3. Give the seven steps in order and say why each precedes the next.
4. Which step is skippable, and what tells you to skip it?
5. Why must the test suite be green at every commit?
6. What do you do when you find a bug mid-refactor?
7. Why write characterisation tests for your own code?
8. Give the four failure modes and the fix for each.
9. Why is the folder structure the least important artefact?
10. What goes in the "revisit when" section, and why does it matter?
11. Which single number is the strongest interview artefact from this day?

## 🎙️ Articulation drill

**Three minutes:** *"Tell me about a refactor you did."*

**⭐ The structure that works: the number before, what you changed, the number after, what you
deliberately did not touch, and what it cost.** Five sentences.

**⭐ The marker is the fourth one.** Anyone can describe a refactor. **"I applied it to `orders` and
deliberately left `catalog` and `notifications` as plain CRUD, because the mapping cost would have
exceeded the benefit"** demonstrates that you were making an engineering decision rather than
applying a style — and it is the single most credible sentence you can say about architecture.
