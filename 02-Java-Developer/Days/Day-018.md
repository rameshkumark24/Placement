# Part 1 — L-018 · Choosing the right real-time technique

## The question that actually decides it

Before comparing anything, answer this:

> **Do you need client → server messages at high frequency, or only server → client?**

Most "real-time" features are **server → client only**: notifications, live dashboards, progress
bars, stock tickers, AI token streaming, activity feeds. For all of those, **SSE is the better
choice and almost nobody knows it exists.**

WebSockets are for genuinely bidirectional, high-frequency exchange: chat, collaborative editing,
multiplayer games, live cursors.

## Server-Sent Events — the underrated option

**SSE is one long-lived HTTP response that the server keeps writing into.** That's it. No new
protocol.

```http
GET /events HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: {"type":"notification","text":"New message"}

data: {"type":"price","value":142.50}

id: 1042
event: order-shipped
data: {"orderId":42}

```

Each message is `data: ...` followed by a **blank line**. Plain text. You can read it with `curl`.

```js
const es = new EventSource('/events');
es.onmessage = e => console.log(JSON.parse(e.data));
es.addEventListener('order-shipped', e => handleShipped(JSON.parse(e.data)));
```

**Four things you get for free that WebSockets make you build:**

1. **Automatic reconnection.** The browser reconnects on drop. You write no code.
2. **Event IDs and replay.** Send `id:` with each event; on reconnect the browser sends
   `Last-Event-ID`, so the server can resume from where the client left off. **This solves the
   "missed messages" problem that you have to hand-roll with WebSockets.**
3. **It's just HTTP.** Works through every proxy, load balancer and firewall. Same auth (cookies,
   `Authorization` header — which WebSockets *can't* set). Same status codes. Same compression.
4. **Named event types.** Route different events to different handlers natively.

**The limits:** one-way only, text only (base64 your binary), and over HTTP/1.1 browsers cap ~6
connections per domain — but **over HTTP/2 that limit vanishes** (Day 011), so on any modern stack
it's a non-issue.

## The decision table

| | Short polling | Long polling | **SSE** | **WebSocket** |
|---|---|---|---|---|
| Direction | C→S | C→S (simulated push) | **S→C only** | **Bidirectional** |
| Protocol | HTTP | HTTP | HTTP | ws:// (upgraded) |
| Overhead/message | ~800 B | ~800 B | **~20 B** | **~2–6 B** |
| Latency | Up to interval | ~0 | **~0** | **~0** |
| Auto-reconnect | N/A | Manual | **✅ built in** | ❌ you write it |
| Replay missed | ❌ | ❌ | **✅ `Last-Event-ID`** | ❌ you build it |
| Binary | ✅ | ✅ | ❌ (base64) | ✅ |
| Custom auth headers | ✅ | ✅ | ✅ | ❌ browser limitation |
| Works through proxies | ✅ | ✅ | ✅ | ⚠️ needs config |
| Stateless scaling | ✅ | ⚠️ | ⚠️ pinned | ❌ pinned |
| Implementation cost | Trivial | Low | **Low** | **High** |

## Choose by use case

| Need | Use | Why |
|---|---|---|
| Notifications, activity feed | **SSE** | One-way, reconnect and replay for free |
| Live dashboard / metrics | **SSE** | One-way |
| Progress bar for a long job | **SSE** | One-way, finite |
| **LLM token streaming** | **SSE** | One-way. This is exactly what ChatGPT and Claude use. |
| Stock/crypto ticker | **SSE** | One-way |
| Chat | **WebSocket** | Genuinely bidirectional |
| Collaborative editing | **WebSocket** | High-frequency both ways |
| Multiplayer game | **WebSocket** (or WebRTC/UDP) | Latency-critical, bidirectional |
| Live cursors / presence | **WebSocket** | High-frequency both ways |
| Status that changes every few minutes | **Polling** | Don't over-engineer. Seriously. |
| One-off "is my export ready?" | **Polling** | 30-second interval is fine |

**The most common architecture mistake here is reaching for WebSockets by default.** You take on
reconnection logic, heartbeats, sticky sessions, pub/sub fan-out, and a broken stateless model — to
push notifications one direction. SSE would have been ten lines.

**The second most common mistake is over-engineering the other way**: building any of this for data
that changes every five minutes. Polling at a sane interval is a legitimate, professional answer.

> This connects straight back to
> [`03-Web-Developer/05-API-Safety.md`](../../03-Web-Developer/05-API-Safety.md#2-the-polling-leak):
> "poll no faster than the data actually changes; 1s polling is almost never justified; if you need
> real-time, use SSE or WebSockets, not a 1-second poll." Now you can choose *which*.

## Type this yourself

An SSE server — compare its size to yesterday's WebSocket implementation.

```java
import java.io.*;
import java.net.*;
import java.time.*;

public class SseServer {
    public static void main(String[] args) throws IOException {
        ServerSocket server = new ServerSocket(8080);
        System.out.println("http://localhost:8080  (open sse.html)");

        while (true) {
            Socket client = server.accept();
            new Thread(() -> {
                try {
                    BufferedReader in = new BufferedReader(
                            new InputStreamReader(client.getInputStream()));
                    String requestLine = in.readLine();
                    String lastEventId = null;
                    String h;
                    while ((h = in.readLine()) != null && !h.isEmpty())
                        if (h.toLowerCase().startsWith("last-event-id:"))
                            lastEventId = h.split(":")[1].trim();

                    System.out.println(requestLine + "  Last-Event-ID: " + lastEventId);

                    OutputStream out = client.getOutputStream();
                    out.write(("HTTP/1.1 200 OK\r\n"
                            + "Content-Type: text/event-stream\r\n"
                            + "Cache-Control: no-cache\r\n"
                            + "Connection: keep-alive\r\n\r\n").getBytes());
                    out.flush();

                    // Resume from where the client left off — this is the killer feature
                    int id = lastEventId == null ? 0 : Integer.parseInt(lastEventId);

                    while (true) {
                        id++;
                        String event = "id: " + id + "\n"
                                     + "data: {\"n\":" + id + ",\"time\":\"" + LocalTime.now() + "\"}\n\n";
                        out.write(event.getBytes());
                        out.flush();                    // flush is essential — no buffering
                        Thread.sleep(1000);
                    }
                } catch (Exception e) {
                    System.out.println("Client disconnected: " + e.getMessage());
                }
            }).start();
        }
    }
}
```

```html
<!DOCTYPE html>
<html><body>
  <button id="stop">Close connection</button>
  <ul id="log"></ul>
<script>
  const es = new EventSource('/events');
  const log = m => { const li = document.createElement('li');
                     li.textContent = m; document.getElementById('log').prepend(li); };

  es.onopen    = () => log('[open]');
  es.onmessage = e  => log(e.data);
  es.onerror   = () => log('[error — browser will auto-reconnect]');

  document.getElementById('stop').onclick = () => { es.close(); log('[closed by client]'); };
</script>
</body></html>
```

**Three experiments — the third is the important one:**

1. **`curl -N http://localhost:8080/events`** — watch the stream in your terminal. You can read the
   raw protocol. Try that with a WebSocket.
2. **Compare the code.** SSE server: ~30 lines, no frame parsing, no masking, no SHA-1, no GUID.
   WebSocket server (Day 017): ~80 lines of protocol implementation.
3. **Kill the server while the page is open, then restart it.** The browser reconnects **by itself**,
   and your server log shows `Last-Event-ID` — so the stream resumes from the right number. **You
   wrote zero reconnection code.** With WebSockets you'd have written backoff, jitter, retry limits
   and a replay endpoint.

## Interview questions

**Q: When would you choose SSE over WebSockets?**
> When the data flow is server-to-client only, which covers most real-time features — notifications,
> dashboards, progress, token streaming. SSE is plain HTTP, so it works through existing proxies and
> auth, and gives automatic reconnection and replay via `Last-Event-ID` for free. WebSockets are
> worth their extra complexity only when you genuinely need high-frequency client-to-server messages.

**Q: How does an LLM chat interface stream tokens?**
> Almost always SSE. It's one-way server-to-client, works over plain HTTP, and the browser's
> `EventSource` handles reconnection. WebSockets would add bidirectionality nobody needs.

**Q: What does SSE give you that WebSockets don't?**
> Automatic browser reconnection, event IDs with `Last-Event-ID` replay so missed messages can be
> resumed, standard HTTP auth including custom headers, and transparent proxy traversal. With
> WebSockets you implement reconnection, heartbeats and replay yourself.

**Q: Is polling ever the right answer?**
> Yes — when data changes on the order of minutes and near-real-time delivery isn't required. A
> 30-second poll is simpler, stateless, cacheable and needs no connection management. Reaching for
> WebSockets for slowly-changing data is over-engineering.

# Part 2 — C-12 · Proxies, load balancers, CDN

## Forward vs reverse proxy

The difference is **whose side it's on**.

```
   FORWARD PROXY — acts for the CLIENT
   Clients ──▶ [proxy] ──▶ Internet
   The server sees the proxy's IP, not yours.
   Corporate filtering, VPNs, anonymity.

   REVERSE PROXY — acts for the SERVER
   Internet ──▶ [proxy] ──▶ Backend servers
   The client sees the proxy, not the backend.
   Nginx, Cloudflare, every production deployment.
```

**A reverse proxy is the single most useful box in web architecture.** It gives you:

- **TLS termination** — decrypt once at the edge; backends speak plain HTTP internally
- **Load balancing** across backends
- **Caching** of static and cacheable responses
- **Compression** (gzip/brotli)
- **Rate limiting** and WAF rules
- **A single public entry point**, hiding your topology
- **Header injection** — `X-Forwarded-For`, `X-Request-ID`

**This is what Cloudflare is** in your web domain, and what Nginx is on Day 367. Your Spring Boot app
sits behind one and never knows.

> Note the connection to REST constraint 5 (Day 016, layered system): a client cannot tell whether
> it's talking to the origin. **That constraint is what makes reverse proxies possible at all.**

## L4 vs L7 load balancing

The crucial distinction, and a reliable interview question.

| | **L4 (transport)** | **L7 (application)** |
|---|---|---|
| Reads | TCP/IP headers — IP + port | **The full HTTP request** |
| Can route on | 4-tuple only | **URL path, headers, cookies, method** |
| TLS | Passes through encrypted | **Terminates — must decrypt** |
| Speed | Very fast | Slower (parses HTTP) |
| Examples | AWS NLB, HAProxy TCP mode | AWS ALB, Nginx, Cloudflare |

**L4 moves packets. L7 understands requests.** The consequences:

```
   L7 can do this — L4 cannot:
     /api/*     → backend pool A
     /images/*  → backend pool B
     Cookie: canary=true → new version         ← canary deploys
     Header: Accept-Language: ta → India pool
```

**Why L4 is still used:** it's faster, protocol-agnostic (works for databases, gRPC streams, raw
TCP), and preserves end-to-end encryption because it never decrypts. AWS NLB handles millions of
requests per second with microsecond latency.

**Rule of thumb:** L7 for HTTP, L4 for everything else or when you need extreme throughput.

### Algorithms

| Algorithm | Behaviour |
|---|---|
| **Round robin** | Each in turn. Fine when requests are uniform. |
| **Least connections** | Fewest active connections wins. **Better for long-lived connections** — which is what you want for WebSockets and SSE. |
| **IP hash** | Same client → same backend. Poor man's sticky sessions. |
| **Weighted** | Bigger servers get more. |
| **Least response time** | Fastest wins. Best, most expensive to compute. |

### Health checks

The load balancer polls each backend and removes failures from rotation.

- **Liveness** — is the process alive? Restart if not.
- **Readiness** — can it serve traffic *now*? Remove from rotation if not.

**The distinction matters at deploy time.** A Spring Boot app that has started but hasn't finished
warming its connection pool is *live* but not *ready*. Send traffic and you get errors. This is
exactly the `/health` endpoint that "actually checks the DB" from
[`03-Web-Developer/09-Observability.md`](../../03-Web-Developer/09-Observability.md) — a check that
returns 200 unconditionally tells you nothing.

### Sticky sessions — and why to avoid them

The LB pins a client to one backend, usually via a cookie.

**Needed when** the server holds per-user state — in-memory sessions, or **WebSocket connections**
(Day 017).

**The costs are real:** uneven load distribution, a lost session when that server dies, and broken
autoscaling — a new instance receives no existing users. **The better answer is to externalise the
state** — sessions in Redis, pub/sub for WebSocket fan-out — so any server can serve any request.
That's REST constraint 2 (statelessness) again, and it's why it was worth naming as load-bearing.

## CDN

Geographically distributed caches near your users. Recall Day 006: 140 ms Chennai↔Oregon is physics.
**A CDN's only real trick is being physically closer.**

```
   Without: Chennai user ──── 140 ms RTT ────▶ Oregon origin
   With:    Chennai user ── 5 ms ──▶ Chennai edge ──▶ (cache hit: done)
```

| Caches well | Doesn't |
|---|---|
| Images, CSS, JS, fonts, video | Personalised HTML |
| Public API responses | Authenticated responses |
| Anything with a hash in the filename | Anything with `Cache-Control: private` |

**Cache invalidation is the hard part** — the reason for content-hashed filenames
(`app.a3f9c2.js`). New content, new URL, so the old cache entry is simply never requested again. No
purge needed. That's why bundlers hash filenames, and it pairs with `Cache-Control: immutable`.

Modern CDNs also do edge compute (Cloudflare Workers, Vercel Edge), origin shielding, DDoS
absorption, and WAF.

## Interview questions

**Q: Forward vs reverse proxy?**
> A forward proxy acts on behalf of clients — the destination server sees the proxy's address.
> A reverse proxy acts on behalf of servers — the client sees the proxy and never learns the backend
> topology. Reverse proxies provide TLS termination, load balancing, caching and rate limiting.

**Q: L4 vs L7 load balancing?**
> L4 routes on TCP/IP information — addresses and ports — so it's fast, protocol-agnostic and can
> pass TLS through untouched. L7 parses the HTTP request, so it can route on path, headers or
> cookies, enabling path-based routing and canary releases, but it must terminate TLS and costs more
> per request.

**Q: What are sticky sessions and why avoid them?**
> The load balancer pins a client to a specific backend, usually via a cookie, because that backend
> holds state. They cause uneven load, lose sessions when an instance dies, and break autoscaling.
> The better approach is externalising state to Redis so any instance can serve any request.

**Q: Liveness vs readiness?**
> Liveness asks whether the process is alive — if not, restart it. Readiness asks whether it can
> serve traffic right now — if not, remove it from the load balancer but don't restart it. A service
> that has started but hasn't warmed its connection pool is live but not ready.

**Q: How does a CDN reduce latency?**
> By serving content from a location physically near the user. Round-trip time is bounded by the
> speed of light in fibre, so the only way to beat it is to shorten the distance. Cache invalidation
> is usually handled by content-hashed filenames so new content has a new URL.
