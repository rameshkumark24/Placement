# Part 1 — What review is for

Not "finding bugs" — that is one of five purposes, and not the largest:

1. **Correctness** — catch defects, especially in paths tests do not cover.
2. **Knowledge transfer** — both ways. The reviewer learns the system; the author learns the
   conventions.
3. **Shared ownership** — after review, two people understand this code. That is the difference
   between a bus factor of one and two.
4. **Consistency** — the codebase stays coherent instead of becoming n personal styles.
5. **Design feedback** — the last cheap moment to change the structure.

Point 3 is the one to name in an interview, because it reframes review from gatekeeping to
risk-reduction.

**What review is *not*:** a compiler (automate it), a style guide (automate it), a test suite
(automate it), or a status ritual. **Automate everything a machine can check** so humans spend
attention on what only humans can judge — Day 088's rule.

# Part 2 — Reviewing

## The order to look in

Spend your attention top-down. If you find something at level 1, you may not need to read level 5 at
all.

**1. Does it solve the right problem?** Read the description and the ticket first. The most expensive
review comment is "this works, but it is not what we needed" — and it is only cheap if you make it
first.

**2. Correctness.**
- Edge cases: null, empty, zero, one, maximum, negative, boundary values (Day 097).
- Error paths — what happens when the dependency fails, times out, returns garbage?
- Concurrency: shared mutable state, check-then-act, visibility (Day 065).
- Resource handling: try-with-resources, connections closed, streams closed (Day 063).
- Off-by-one, inverted conditions, `==` on boxed types (Day 028).

**3. Security.** This is where a reviewer earns their keep, because tests rarely cover it:
- **Authorization** — is it checked, and against *this* user? Missing ownership checks are the most
  common real vulnerability (IDOR).
- Injection — parameterised queries, no string-built SQL.
- Secrets in code, config or **logs** (Day 073A).
- Deserialization of untrusted input (Day 063A).
- Input validation at the boundary; output encoding.
- New dependencies (Day 100A, tomorrow).

**4. Design.**
- Is the responsibility in the right place (Day 090)?
- Does it duplicate something that exists?
- Is the abstraction earning its keep, or is it speculative (Day 092)?
- Will the next person extend this correctly, or work around it?

**5. Tests.**
- Do they test **behaviour** or implementation (Day 075)?
- **Would they fail if the code were wrong?** — the question people forget to ask.
- Are error paths and boundaries covered?

**6. Readability.** Naming, function size, clarity (Day 089).

**7. Style.** ❌ Automated. If you are commenting on formatting, install a formatter instead.

## The questions that find real problems

Worth keeping as a literal checklist for your first year of reviewing:

- What happens if this is called **concurrently**?
- What happens if this **fails halfway** — is the state consistent?
- What happens with an **empty** collection? A **null**? A **very large** input?
- Is this **authorized** — and can user A pass user B's id?
- Does this run **inside a transaction**, and should it?
- Is this an **N+1 query**?
- Does this hold a **lock across I/O** (Day 066)?
- Is anything **unbounded** — a queue, a cache, a retry, a page size?
- Is this **idempotent**? What happens if it is retried?
- What does the **rollback** look like?

## How to say it

```
blocking:  This lets any authenticated user fetch any order — `orderId` comes from the
           path with no ownership check. We need `order.customerId() == currentUser.id()`
           before returning.

question:  Is the 30s timeout intentional? Upstream p99 is 1.2s, so a hung call would
           hold a pool thread for the whole window.

suggestion: `computeIfAbsent` would make this atomic and drop four lines. Non-blocking.

nit:       `isEmpty()` reads better than `size() == 0`. Take it or leave it.

praise:    The characterisation tests around the legacy path are excellent — that made
           the whole change reviewable.
```

**Labelling severity is the single highest-value habit in code review.** Without it, a stylistic
preference and a security bug arrive with identical weight and the author must guess which is
mandatory. `blocking:` and `nit:` alone change a team's review culture measurably.

Four more rules:

**Review the code, not the person.** "This method does X" not "you did X". It sounds like a small
thing; it is not, because the second form invites defence rather than thought.

**Ask rather than assert when you are unsure.** "What happens if `items` is empty?" is better than
"this breaks on empty" — you may be wrong, and the question gets the same fix without a correction to
walk back.

**Explain the why.** "Use `computeIfAbsent`" teaches nothing. "`computeIfAbsent` is atomic on a
`ConcurrentHashMap`; the get-then-put here can race" teaches the principle and applies to every
future case.

**Praise explicitly.** A review stream that is only ever criticism makes people avoid submitting and
makes them defensive when they do. Say what was good — and mean it.

## Size, speed and scope

**Review within one working day.** A PR waiting three days blocks the author, invites a rebase, and
grows conflicts. Speed of review is one of the highest-leverage things a team can improve.

**Beyond ~400 lines, quality collapses.** Studies and experience agree: past that, reviewers
skim. If a PR is large, either ask for it to be split or *say explicitly* that you reviewed it at a
lower depth — an honest "LGTM with reservations, I could not review this thoroughly" is far more
useful than a silent rubber stamp.

**Do not expand the scope.** "While you are here, could you also refactor X?" turns a two-day change
into a two-week one. File a ticket.

## When to approve

- **Approve** when it is correct and safe, even with `nit:` comments outstanding — trust the author.
- **Approve with comments** for non-blocking suggestions. Blocking on nits is how review becomes
  hated.
- **Request changes** only for blocking issues: correctness, security, or a design problem that will
  be expensive later.
- **If you disagree twice, take it to a call.** Text is a poor medium for design disagreement and an
  excellent medium for entrenching one.

# Part 3 — Receiving review

**Separate the code from yourself.** A comment on your code is not a comment on you. This is easy to
say and takes real practice; the sign you have got there is that a blocking comment produces
curiosity rather than a defence.

**Assume good intent.** Text has no tone. "Why is this here?" is almost always a genuine question.

**Respond to every comment** — fix it, or explain why not. Silence reads as dismissal, and
unresolved threads are how technical disagreements become interpersonal ones.

**If you disagree, say why with reasoning**, and be willing to be persuaded. "I chose X because Y —
does that address the concern?" is a good disagreement. "This is fine" is not.

**If a comment reveals a misunderstanding of your change, that is a documentation bug.** The reviewer
had the PR description and the diff and still misunderstood — improve the description or add a
comment in the code, because the next reader will have less than the reviewer did.

**Thank people for catching things.** They saved you a production incident.

# Part 4 — D-08 · Every join type

```
    A          B
  ┌────┐   ┌────┐
  │ 1  │   │ 2  │      1 = only in A     INNER      = 2
  │  ┌─┼───┼─┐  │      2 = in both       LEFT       = 1 + 2
  │  │ 2 │  │  │      3 = only in B      RIGHT      = 2 + 3
  └──┼─┬─┘  │  │                          FULL OUTER = 1 + 2 + 3
     │ 3 │  └──┘                          LEFT ANTI  = 1 only  (WHERE b.id IS NULL)
     └───┘                                CROSS      = every pairing
```

```sql
FROM a INNER JOIN b ON a.id = b.a_id          -- matches only
FROM a LEFT  JOIN b ON a.id = b.a_id          -- all of a; nulls where no match
FROM a RIGHT JOIN b ON a.id = b.a_id          -- all of b  (rewrite as LEFT for readability)
FROM a FULL  JOIN b ON a.id = b.a_id          -- all of both
FROM a CROSS JOIN b                           -- Cartesian product (Day 094)

-- ANTI-JOIN: rows of a with NO match. Two forms:
FROM a LEFT JOIN b ON a.id = b.a_id WHERE b.a_id IS NULL     -- ← the "outer join is null" idiom
WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id)       -- ← usually clearer AND faster

-- SEMI-JOIN: rows of a that HAVE a match, without duplicating a
WHERE EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id)
```

## The trap that catches everyone

```sql
-- ❌ this is an INNER JOIN wearing a LEFT JOIN's clothes
SELECT * FROM customer c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'PAID';          -- ← unmatched rows have status NULL, so this filters them OUT

-- ✅ the condition belongs in the ON clause
SELECT * FROM customer c
LEFT JOIN orders o ON c.id = o.customer_id AND o.status = 'PAID';
```

> **For an outer join: filters on the outer table go in `WHERE`; filters on the *optional* table go
> in `ON`.** Putting them in `WHERE` silently converts it to an inner join.

This is one of the most common SQL bugs in production and a standard interview question.

## Self joins

Joining a table to itself, for hierarchies and comparisons:

```sql
-- employees and their managers
SELECT e.name AS employee, m.name AS manager
FROM employee e
LEFT JOIN employee m ON e.manager_id = m.id;     -- LEFT: the CEO has no manager

-- pairs of employees in the same department, no duplicates
SELECT a.name, b.name
FROM employee a JOIN employee b
  ON a.dept_id = b.dept_id AND a.id < b.id;      -- ← a.id < b.id gives each pair ONCE
```

That `a.id < b.id` idiom is worth remembering: with `<>` you get both (X,Y) and (Y,X); with `<` you
get each pair exactly once.

## `GROUP BY` and aggregates

```sql
SELECT c.region, COUNT(*) AS orders, SUM(o.total_cents) AS revenue,
       AVG(o.total_cents)::int AS avg_order
FROM customer c
JOIN orders o ON o.customer_id = c.id
WHERE o.created_at >= DATE '2026-01-01'     -- filter ROWS first (Day 097)
GROUP BY c.region
HAVING COUNT(*) > 100                        -- filter GROUPS after
ORDER BY revenue DESC;
```

**Every non-aggregated column in `SELECT` must appear in `GROUP BY`** — except columns functionally
dependent on the grouped primary key, which PostgreSQL permits and MySQL historically allowed
carelessly (`ONLY_FULL_GROUP_BY` fixed that). Day 087's D-04 functional dependencies is exactly why
that exception is sound.

The `LEFT JOIN` + `COUNT` trap:

```sql
-- ❌ counts 1 for customers with no orders, because COUNT(*) counts the null-padded row
SELECT c.name, COUNT(*) FROM customer c LEFT JOIN orders o ON … GROUP BY c.name;

-- ✅ COUNT(column) skips nulls (Day 097)
SELECT c.name, COUNT(o.id) FROM customer c LEFT JOIN orders o ON … GROUP BY c.name;
```

## Join algorithms and join order

Which the optimiser chooses, and why it matters for Stage 5:

| Algorithm | How | Best when |
|---|---|---|
| **Nested loop** | For each row of A, look up in B | A is small and B has an index on the key |
| **Hash join** | Build a hash table on the smaller side, probe with the larger | Large, unsorted, equi-join |
| **Merge join** | Sort both, walk in step | Both already sorted (e.g. by index) |

**Nested loop without an index on the inner side is O(n×m)** — that is the shape of the query that
runs in 40 ms on your laptop's 100 rows and 40 seconds on production's 100,000.

Join order (Day 094's associativity and commutativity) is the optimiser's hardest problem: n tables
have up to n! orderings and the difference between best and worst is routinely 1000×. The optimiser
chooses using **table statistics**, which is why stale statistics produce sudden inexplicable
slowdowns and why `ANALYZE` is a real fix.

```sql
EXPLAIN ANALYZE SELECT …;      -- ← the tool. Stage 5 lives here.
```

Read it for: the join algorithm chosen, **estimated vs actual row counts** (a large divergence means
bad statistics), and where the time actually goes. A sequential scan is not automatically bad — on a
small table it is faster than an index lookup.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Reviewing style manually | Wastes the scarce resource on the automatable |
| No severity labels | Nits read as blockers and vice versa |
| Blocking on nits | Review becomes an obstacle people route around |
| Rubber-stamping a 2,000-line PR | Worse than no review — it launders responsibility |
| Reviews taking days | Blocks the author, grows conflicts |
| Expanding scope in review | A two-day change becomes two weeks |
| "You did X" | Invites defence instead of thought |
| Not responding to comments | Reads as dismissal |
| Filter on the optional table in `WHERE` | A LEFT JOIN silently becomes INNER |
| `COUNT(*)` with `LEFT JOIN` | Counts 1 instead of 0 |
| Missing join condition | Cartesian product |
| Assuming the optimiser is always right | Stale statistics produce terrible plans |

## Interview questions

**Q: What do you look for in a code review?**
In order: does it solve the right problem, correctness including edge and error paths, security
especially authorization, design and responsibility placement, whether the tests would fail if the
code were wrong, and readability. Style is automated.

**Q: How do you give feedback that gets acted on?**
Label severity — blocking, question, suggestion, nit — explain the *why* so it teaches rather than
instructs, ask rather than assert when unsure, comment on code not people, and say what was good.

**Q: What makes code review valuable beyond finding bugs?**
Shared ownership — after review, two people understand the code — plus knowledge transfer in both
directions and design feedback at the last cheap moment.

**Q: What is the difference between a LEFT JOIN filter in `ON` versus `WHERE`?**
A filter on the optional table in `WHERE` eliminates the null-padded rows, silently turning the outer
join into an inner join. Conditions on the optional table belong in `ON`.

**Q: How do you find rows in A with no match in B?**
An anti-join: `NOT EXISTS`, or `LEFT JOIN … WHERE b.key IS NULL`. `NOT EXISTS` is usually clearer and
avoids the `NOT IN` NULL trap.

**Q: What are the three join algorithms and when is each chosen?**
Nested loop for a small outer with an indexed inner; hash join for large unsorted equi-joins; merge
join when both inputs are already sorted. The optimiser chooses from statistics, which is why stale
statistics cause sudden slowdowns.

**Q: Why is join order hard?**
Joins are commutative and associative, so n tables have up to n! orderings with cost differences of
several orders of magnitude, and the optimiser must pick using estimated cardinalities.

## 🎙️ Articulation drill

Two minutes: **"How do you approach code review?"**

Cover both directions. As a reviewer: the priority order, automation of style, severity labels,
explaining why, and reviewing within a day. As an author: small PRs, a description with context,
self-review first, and responding to every comment. Then the framing that makes it senior — review is
primarily about shared ownership and knowledge transfer; catching bugs is a side benefit.
