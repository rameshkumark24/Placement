# Day 194

**L-194** · MVCC, vacuum, and bloat — the bill for never updating in place

**Time:** 3 hrs · **Mode:** NEW

> Day 186 established the fact: **PostgreSQL never updates a row in place.** An `UPDATE` writes a new
> tuple version; a `DELETE` only marks one dead. That single decision buys you MVCC — readers never
> block writers — and it creates a debt that something has to pay.
>
> **Vacuum is that payment**, and when it falls behind you get bloat, degraded index-only scans, and
> eventually the transaction ID wraparound emergency that takes a database offline. Today is the
> mechanism, the monitoring, and the three failure modes.

---

# Part 1 — ⭐ How visibility actually works

Every tuple carries `xmin` (the transaction that created it) and `xmax` (the transaction that deleted
it). Every transaction gets a **snapshot**: its own `xid`, plus the set of transactions in flight
when it started.

> **⭐ A tuple is visible to you if `xmin` committed before your snapshot, and `xmax` is either unset
> or belongs to a transaction that had not committed when your snapshot was taken.**

**That is the whole of MVCC**, and four properties fall straight out of it:

| Property | Why |
|---|---|
| ⭐ **Readers never block writers** | a reader looks at old versions; the writer adds new ones |
| ⭐ **Writers never block readers** | same |
| Each transaction sees a consistent point in time | its snapshot is fixed |
| ⭐ **Dead versions accumulate** | ⭐ **the bill** |

```sql
select ctid, xmin, xmax, * from orders where id = 1;
update orders set total = total + 1 where id = 1;
select ctid, xmin, xmax, * from orders where id = 1;    -- ⭐ new ctid, new xmin
```

**⭐ Writers still block writers.** Two transactions updating the same row serialise — the second
waits on the first's row lock. MVCC removes read/write contention, not write/write contention
(Day 196).

# Part 2 — ⭐ What vacuum does, and the three things people conflate

```sql
vacuum orders;                    -- ⭐ marks dead tuple space reusable. Does NOT shrink the file
vacuum analyze orders;            -- ⭐ + refresh statistics (Day 189 #6)
vacuum full orders;               -- ⭐⭐ rewrites the table. ACCESS EXCLUSIVE LOCK. Outage.
```

**⭐ The distinction that matters most:**

| | `VACUUM` | `VACUUM FULL` |
|---|---|---|
| Lock | ⭐ `SHARE UPDATE EXCLUSIVE` — **reads and writes continue** | ⭐ `ACCESS EXCLUSIVE` — **everything blocks** |
| Effect | space marked reusable **inside** the file | file rewritten, space returned to the OS |
| Disk needed | none | ⭐ **a full second copy of the table** |
| When | ⭐ **routinely, automatically** | ⭐ **almost never** — see Part 4 |

**⭐ `VACUUM FULL` on a large table in production is an outage**, and people run it because "vacuum
didn't free any disk space" — which is correct behaviour, not a failure. Plain vacuum makes space
*reusable*; the table stops growing rather than shrinking.

**Vacuum's four jobs:**

1. mark dead tuple space reusable,
2. ⭐ **remove dead index entries** — otherwise indexes bloat (Day 190),
3. ⭐ **update the visibility map** — which is what makes index-only scans work (Day 189),
4. ⭐ **freeze old transaction IDs** — Part 3's wraparound defence.

**⭐ Job 3 is the surprising one.** A table that is not vacuumed does not just get bigger — its
index-only scans silently degrade into heap fetches, because the visibility map is stale. That is a
performance cliff with no obvious cause.

## Autovacuum, and why its defaults are wrong for large tables

```
autovacuum_vacuum_scale_factor = 0.2      -- ⭐ vacuum when 20% of rows are dead
autovacuum_analyze_scale_factor = 0.1
autovacuum_vacuum_cost_limit = 200        -- ⭐ throttled — deliberately slow
autovacuum_max_workers = 3
```

**⭐ 20% of a 500-million-row table is 100 million dead tuples before autovacuum starts.** By then the
table is enormously bloated and the vacuum itself takes hours.

```sql
-- ⭐ per-table, for large or hot tables
alter table orders set (autovacuum_vacuum_scale_factor = 0.02,
                        autovacuum_analyze_scale_factor = 0.01,
                        autovacuum_vacuum_cost_limit = 1000);   -- ⭐ let it run faster
```

**⭐ The two adjustments that matter: lower the scale factor on big tables, and raise the cost limit
so autovacuum is not throttled to a crawl on modern hardware.** The default cost limit is another
setting calibrated for 2005 disks.

```sql
select relname, n_live_tup, n_dead_tup,
       round(100.0*n_dead_tup/nullif(n_live_tup+n_dead_tup,0),1) as dead_pct,
       last_autovacuum, autovacuum_count
from pg_stat_user_tables order by n_dead_tup desc limit 20;    -- ⭐ your bloat dashboard
```

# Part 3 — ⭐⭐ The three failure modes

## ⭐ Failure 1 — A long-running transaction blocks all vacuuming

> **⭐ Vacuum cannot remove a dead tuple that any open transaction might still need to see.**

**So one forgotten transaction — a session left `IDLE IN TRANSACTION`, a long analytics query, an
open psql window — prevents vacuum from cleaning *any* table**, database-wide. Bloat accumulates
everywhere while autovacuum runs and reclaims nothing.

```sql
select pid, state, now() - xact_start as xact_age, now() - state_change as idle_time, query
from pg_stat_activity
where state <> 'idle' or state = 'idle in transaction'
order by xact_start;                                    -- ⭐ oldest first
```

```
idle_in_transaction_session_timeout = '5min'      -- ⭐⭐ SET THIS. Kills abandoned transactions
statement_timeout = '30s'                         -- ⭐ per-role, not globally
```

**⭐ `idle_in_transaction_session_timeout` is one of the highest-value settings in PostgreSQL**, and
it is off by default. An application that opens a transaction and then makes an HTTP call (Day 156's
forbidden pattern) is exactly how this happens — the connection sits idle in transaction for the
duration of someone else's outage, and your vacuuming stops.

⚠️ **A replica with `hot_standby_feedback = on` does the same thing across servers** — a long query
on the replica prevents vacuum on the primary. Day 201.

## ⭐ Failure 2 — Bloat

**Symptoms:** the table is far larger than its data, sequential scans get slower, indexes stop fitting
in memory (Day 189).

```sql
-- pgstattuple gives exact numbers; it scans the table, so run it off-peak
create extension pgstattuple;
select * from pgstattuple('orders');                -- ⭐ dead_tuple_percent, free_percent
select * from pgstatindex('ix_orders_customer');    -- ⭐ avg_leaf_density — below ~50% is bloated
```

| Fix | Cost |
|---|---|
| ⭐ **Fix the cause** — the long transaction, or autovacuum tuning | ⭐ the real fix |
| ⭐ `reindex index concurrently` | ⭐ non-blocking (PG12+). **The right answer for index bloat** |
| `pg_repack` | rewrites the table with only a brief lock. ⭐ the right answer for table bloat |
| `VACUUM FULL` | ⭐ an outage. Only with a maintenance window and no `pg_repack` |

**⭐ Index bloat is more common and more damaging than table bloat**, because an index that no longer
fits in memory changes performance discontinuously. `reindex concurrently` is cheap; schedule it.

## ⭐⭐ Failure 3 — Transaction ID wraparound

**⭐ Transaction IDs are 32-bit.** After ~2 billion, they wrap — and a wrapped ID would make old rows
appear to be from the *future*, so they would become invisible. **That is silent data loss**, so
PostgreSQL refuses to let it happen.

**Vacuum prevents it by "freezing" old tuples** — marking them visible to everyone, forever.

```sql
select datname, age(datfrozenxid),
       round(100.0*age(datfrozenxid)/2147483648, 1) as pct_to_wraparound
from pg_database order by age(datfrozenxid) desc;      -- ⭐ monitor this
```

**⭐ The escalation, and the reason this is genuinely feared:**

| Age | What happens |
|---|---|
| 200M (`autovacuum_freeze_max_age`) | ⭐ **an aggressive anti-wraparound autovacuum starts — and it cannot be cancelled** |
| ~2B minus 40M | ⭐ **warnings in the log** |
| ~2B minus 3M | ⭐⭐ **THE DATABASE REFUSES ALL WRITES.** Single-user mode to recover |

**⭐ This has taken major services offline.** The pattern is always the same: something blocked
vacuum for a long time — a long transaction, an abandoned replication slot, or autovacuum disabled
"because it was causing load" — and nobody was monitoring `age(datfrozenxid)`.

**⭐ Monitor it. Alert at 50%.** It is one number, it moves slowly, and by the time PostgreSQL is
warning you the remediation window is short.

**And never disable autovacuum.** If it is causing load, tune the cost limit — turning it off
converts a performance problem into an outage on a delay.

# Part 4 — The application-side connection

**Everything on this page is caused or prevented by application behaviour.**

| Application pattern | Effect |
|---|---|
| ⭐ HTTP call inside a transaction (Day 156) | ⭐ a long transaction — blocks vacuum globally |
| ⭐ Connection returned to the pool without commit/rollback | ⭐ `idle in transaction` forever |
| `open-in-view: true` (Day 139) | transaction spans serialization and the client's network |
| ⭐ Frequent updates to a wide row | high dead-tuple churn |
| Many indexes on a hot table (Day 189) | more dead index entries to clean |
| Bulk `DELETE` of millions of rows | ⭐ enormous bloat — see below |

**⭐ Bulk deletes deserve their own note.** `delete from events where created_at < now() - interval
'1 year'` on 200 million rows leaves 200 million dead tuples, a very long vacuum, and a table that
does not shrink.

**⭐ The right answer is partitioning** (Day 200): `drop table events_2025_01` is instant, frees the
disk immediately, and creates no dead tuples at all. **That is the single strongest argument for
partitioning a time-series table**, and it is a data-lifecycle decision made at design time.

If you must bulk-delete, do it in **batches with a vacuum between**, so dead tuples are reclaimed
incrementally rather than all at once.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Not monitoring `n_dead_tup` and `age(datfrozenxid)` | both failures are silent until severe |
| ⭐ No `idle_in_transaction_session_timeout` | one abandoned session blocks all vacuuming |
| Long transactions (HTTP calls, `open-in-view`) | same |
| ⭐ Disabling autovacuum "because of load" | converts a performance problem into an outage |
| Default scale factor on huge tables | 20% dead before it starts |
| Default cost limit on modern hardware | autovacuum throttled to a crawl |
| ⭐ `VACUUM FULL` in production | `ACCESS EXCLUSIVE` — a full outage |
| Expecting `VACUUM` to shrink the file | it makes space reusable, by design |
| Ignoring index bloat | a discontinuous performance cliff |
| ⭐ Bulk-deleting millions of rows | massive bloat; partition instead |
| Ignoring `hot_standby_feedback`'s effect | a replica query blocks the primary's vacuum |

## Interview questions

**Q: What is vacuum for?**
PostgreSQL never updates in place, so every update leaves a dead tuple. Vacuum marks that space
reusable, removes dead index entries, updates the visibility map — which is what makes index-only
scans work — and freezes old transaction IDs to prevent wraparound. Without it you get bloat,
degraded index-only scans, and eventually a database that refuses writes.

**Q: `VACUUM` versus `VACUUM FULL`?**
Plain vacuum takes a light lock, runs concurrently with reads and writes, and makes space reusable
within the file. `VACUUM FULL` rewrites the table under an `ACCESS EXCLUSIVE` lock, needs a full
second copy on disk, and blocks everything — so it is effectively an outage. People run it because
plain vacuum did not return disk to the OS, which is correct behaviour rather than a failure.

**Q: Why does one long-running transaction cause database-wide bloat?**
Vacuum cannot remove a tuple version that any open transaction might still need to see. So a single
session left idle in transaction prevents cleanup everywhere, and autovacuum runs while reclaiming
nothing. `idle_in_transaction_session_timeout` is the defence, and it is off by default.

**Q: What is transaction ID wraparound?**
Transaction IDs are 32-bit, so after about two billion they wrap and old rows would appear to be from
the future — invisible. PostgreSQL prevents that by refusing writes as it approaches the limit, which
takes the database offline. Vacuum freezes old tuples to keep it from getting there. It is one number
to monitor and I alert at 50%.

**Q: How do you delete a year of old events?**
Partitioning — drop the partition. It is instant, frees the disk immediately and creates no dead
tuples. A bulk delete of 200 million rows leaves 200 million dead tuples and a table that will not
shrink.

## 🎙️ Articulation drill

Two minutes: **"Why does PostgreSQL need vacuum?"**

Start from the design decision — no in-place updates — and derive both the benefit and the bill:
readers never block writers, and dead versions accumulate. Then vacuum's four jobs, calling out the
visibility map because a table that is not vacuumed silently loses index-only scans. Then the three
failures, with the long-transaction one first, since it is caused by application code and is the most
common. Close on wraparound: it is one number that moves slowly and ends in a database that refuses
writes, so it is the easiest serious outage to prevent and one of the most embarrassing to have.
