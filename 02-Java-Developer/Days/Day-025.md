# L-025 · Where Java memory lives

## The map

```
 ┌────────────────────── JVM PROCESS MEMORY ──────────────────────────┐
 │                                                                    │
 │  ┌──────────── PER THREAD ─────────────┐                           │
 │  │  Thread 1        Thread 2           │                           │
 │  │  ┌──────────┐   ┌──────────┐        │                           │
 │  │  │  STACK   │   │  STACK   │        │  frames · locals ·        │
 │  │  │  ~1 MB   │   │  ~1 MB   │        │  operand stack ·          │
 │  │  │          │   │          │        │  return addresses         │
 │  │  └──────────┘   └──────────┘        │                           │
 │  │  PC register    PC register         │                           │
 │  └─────────────────────────────────────┘                           │
 │                                                                    │
 │  ┌──────────── SHARED BY ALL THREADS ──────────────────────────┐   │
 │  │                                                             │   │
 │  │   HEAP                        METASPACE (native memory)     │   │
 │  │   ┌───────────────────────┐   ┌─────────────────────────┐   │   │
 │  │   │ Young Gen             │   │ class metadata          │   │   │
 │  │   │  Eden │ S0 │ S1       │   │ method bytecode         │   │   │
 │  │   ├───────────────────────┤   │ static fields ──────────┼───┼──▶│
 │  │   │ Old Gen (Tenured)     │   │ runtime constant pool   │   │   │
 │  │   │   ...                 │   └─────────────────────────┘   │   │
 │  │   │   String pool ────────┼── (since Java 7, in the heap)   │   │
 │  │   └───────────────────────┘                                 │   │
 │  └─────────────────────────────────────────────────────────────┘   │
 └────────────────────────────────────────────────────────────────────┘
```

## Stack — per thread

**Every thread gets its own stack.** A frame is pushed per method call, popped on return.

Each frame holds:
- **Local variable array** — parameters and locals (slot 0 is `this` for instance methods — Day 024)
- **Operand stack** — the working area
- Reference to the runtime constant pool

**Properties:**
- **Automatic lifetime** — the frame vanishes on return. No GC involvement.
- **Fast** — allocation is moving a pointer
- **Small** — ~512 KB to 1 MB by default (`-Xss`)
- **Not shared** — one thread cannot see another's stack

```java
void method() {
    int x = 5;                    // the VALUE 5 is on the stack
    Object o = new Object();      // the REFERENCE is on the stack,
                                  // the OBJECT is on the heap
}                                 // frame popped: x and the reference are gone.
                                  // The object survives until GC collects it.
```

**This is the distinction people fluff in interviews.** Say it precisely:

> **Primitives that are local variables live on the stack. Objects always live on the heap; only the
> reference to them lives on the stack.**

### Why local variables are automatically thread-safe

Because each thread has its own stack, two threads running the same method have **separate copies**
of every local variable. There is no sharing, so there is no race.

**That is the whole reason** you don't synchronise access to locals, and it's the first thing to say
when asked "is this method thread-safe?" — check whether it touches anything outside its own frame.

## Heap — shared

**All objects and all arrays.** Created with `new`, destroyed by GC.

- **Shared across every thread** → hence synchronisation, `volatile`, the memory model (Day 065)
- Managed by GC (Day 026)
- Much larger (`-Xms` initial, `-Xmx` maximum)
- Allocation is fast (bump-the-pointer in Eden) but not free

### Generational layout

```
   YOUNG GENERATION                        OLD GENERATION
   ┌─────────┬──────┬──────┐              ┌───────────────────┐
   │  Eden   │  S0  │  S1  │  ──promote──▶│  Tenured          │
   └─────────┴──────┴──────┘              └───────────────────┘
   new objects here          survivors            long-lived objects
```

**The generational hypothesis: most objects die young.** Empirically true for almost all programs —
which is why the heap is split, and why young-gen collection can be extremely cheap. Day 026.

## Metaspace — native memory

Class metadata, method bytecode, **static fields**, and the runtime constant pool.

**Since Java 8, this is native memory outside the heap**, and it grows by default. Before Java 8 it
was **PermGen**, a fixed region inside the heap — and `OutOfMemoryError: PermGen space` was a
notorious failure, especially on application servers where redeploys leaked classloaders.

**Static fields live in Metaspace, but the objects they point to live on the heap.**

```java
class Cache {
    static Map<String, byte[]> data = new HashMap<>();   // the REFERENCE is in Metaspace
                                                          // the HashMap and its contents are on the heap
}
```

**This is the shape of the most common Java memory leak.** A static collection is reachable from a
GC root forever, so everything inside it is too. Day 027.

## The String pool — the question you will be asked

**Since Java 7, the string pool is in the heap** (it was in PermGen before). This matters because
pooled strings can now be garbage collected and the pool can grow with the heap.

```java
String a = "hello";                  // literal → the POOL
String b = "hello";                  // same pooled instance
String c = new String("hello");      // NEW object on the heap, NOT pooled
String d = c.intern();               // returns the POOLED instance

a == b        // true   — same pooled object
a == c        // false  — different objects
a.equals(c)   // true   — same contents
a == d        // true   — intern() returned the pooled one
```

```
   HEAP
   ┌────────────────────────────────────────────┐
   │  String pool                               │
   │   ┌──────────────┐                         │
   │   │  "hello"     │◀── a, b, d              │
   │   └──────────────┘                         │
   │                                            │
   │   ┌──────────────┐                         │
   │   │  "hello"     │◀── c   (new String)     │
   │   └──────────────┘                         │
   └────────────────────────────────────────────┘
```

**Why the pool exists:** string literals are everywhere and overwhelmingly repeated. Interning them
saves substantial memory.

**Why `new String("x")` is almost always wrong:** it deliberately creates a second object with
identical contents, defeating the pool. There's essentially no good reason to write it.

**And this is the mechanical reason `==` on strings is a bug:** it compares references. It
*sometimes works* for literals — which is worse than never working, because it hides the bug until
a string arrives from user input or a database. **Always `equals()`.**

### Compile-time constant folding

```java
String a = "hello";
String b = "hel" + "lo";              // folded to "hello" at COMPILE time → pooled
String c = "hel";
String d = c + "lo";                  // computed at RUNTIME → new object, not pooled

a == b    // true   — the compiler folded it (verify with javap, Day 024)
a == d    // false
```

**Decompile this.** `javap -c` shows `b` loading a single constant, while `d` emits a concatenation.
Day 024's skill, applied.

## Type this yourself

```java
public class MemoryDemo {

    static int staticCounter = 0;                 // reference in Metaspace
    int instanceField = 0;                        // lives inside the object, on the heap

    public static void main(String[] args) {

        // ---- 1. String pool identity ----
        String a = "hello";
        String b = "hello";
        String c = new String("hello");
        String d = c.intern();
        String e = "hel" + "lo";                  // compile-time folded
        String f = "hel";
        String g = f + "lo";                      // runtime concatenation

        System.out.println("a == b : " + (a == b));   // true  — pooled
        System.out.println("a == c : " + (a == c));   // false — new object
        System.out.println("a == d : " + (a == d));   // true  — interned
        System.out.println("a == e : " + (a == e));   // true  — constant folded
        System.out.println("a == g : " + (a == g));   // false — runtime concat
        System.out.println("a.equals(c): " + a.equals(c));

        // ---- 2. Stack is per-thread: no sharing, no race ----
        Runnable task = () -> {
            int local = 0;                        // EACH thread gets its own copy
            for (int i = 0; i < 100_000; i++) local++;
            System.out.println(Thread.currentThread().getName() + " local = " + local);
        };
        new Thread(task, "T1").start();
        new Thread(task, "T2").start();
        // Both print exactly 100000. Locals are never shared.

        // ---- 3. Heap IS shared: race condition ----
        Counter shared = new Counter();
        Runnable racy = () -> { for (int i = 0; i < 100_000; i++) shared.count++; };
        Thread t1 = new Thread(racy), t2 = new Thread(racy);
        t1.start(); t2.start();
        try { t1.join(); t2.join(); } catch (InterruptedException ignored) {}
        System.out.println("\nShared heap counter = " + shared.count
                         + "  (expected 200000 — run it a few times)");

        // ---- 4. Stack size ----
        try { depth(0); } catch (StackOverflowError err) {
            System.out.println("Stack depth reached: " + maxDepth);
        }
    }

    static class Counter { int count = 0; }       // on the HEAP → shared

    static int maxDepth = 0;
    static void depth(int d) { maxDepth = d; depth(d + 1); }
}
```

**Run it several times.** Three things to observe:

1. **The string identity results** — match each to the diagram above.
2. **Locals always give exactly 100000** for each thread. Per-thread stacks, no interference.
3. **The shared counter almost never gives 200000.** That's `count++` being three bytecode
   instructions (Day 024: `getfield`, `iadd`, `putfield`) on a **shared heap object**, with threads
   interleaving between them.

**Point 3 is the entire motivation for Days 065–068.** You've now produced a data race deliberately,
and you can explain it in terms of stack vs heap rather than as magic.

Then inspect a live heap:

```bash
java -Xmx256m MemoryDemo &
jps                        # find the PID
jmap -histo <pid> | head -20      # object histogram — what's on the heap
jcmd <pid> GC.heap_info           # generation sizes
jcmd <pid> VM.flags                # effective JVM flags
```

## Common mistakes

| Mistake | Correction |
|---|---|
| "Objects can be on the stack" | Objects are on the heap. Only references and primitive locals are on the stack. (Escape analysis may stack-allocate — an invisible JIT optimisation, not a language rule.) |
| "The string pool is in PermGen" | Since Java 7 it's in the heap. PermGen no longer exists at all since Java 8. |
| `==` to compare strings | Compares references. Works accidentally for literals, then breaks on runtime strings. Use `equals`. |
| `new String("x")` | Deliberately defeats the pool. Never do it. |
| "Static variables are on the heap" | The *reference* is in Metaspace; the object it points to is on the heap. |
| Thinking instance fields are on the stack | They live inside the object, which is on the heap. |
| Assuming local variables need synchronisation | Each thread has its own stack. Locals are inherently thread-safe. |

## Interview questions

**Q: Explain stack vs heap in Java.**
> The stack is per-thread and holds method frames — local variables, the operand stack, return
> addresses. It's automatically managed: a frame is created on call and destroyed on return. The heap
> is shared by all threads and holds every object and array; it's managed by the garbage collector.
> A local variable holding an object stores the reference on the stack while the object itself is on
> the heap.

**Q: Where do static variables live?**
> The static field itself is in the method area — Metaspace since Java 8. If it's a reference, the
> object it points to is on the heap. Because statics are GC roots, anything reachable from a static
> collection is never collected, which is a common source of memory leaks.

**Q: Where is the string pool?**
> In the heap since Java 7. Before that it was in PermGen, which had a fixed size and caused
> `OutOfMemoryError: PermGen space`. Moving it to the heap means pooled strings can be garbage
> collected and the pool can grow with the heap.

**Q: What's the difference between `"hello"` and `new String("hello")`?**
> The literal is interned in the string pool, so all identical literals share one instance.
> `new String` explicitly allocates a separate object with the same contents, so `==` between them is
> false while `equals` is true. `intern()` returns the pooled instance.

**Q: Why are local variables thread-safe?**
> Each thread has its own stack, so each execution of a method gets its own copy of every local.
> There's no shared state, so no synchronisation is needed. Only data reachable from the heap — via
> fields or statics — can be raced on.

**Q: What is PermGen and what replaced it?**
> A fixed-size region inside the heap holding class metadata and, before Java 7, the string pool. It
> was replaced by Metaspace in Java 8, which lives in native memory and grows dynamically, removing a
> whole class of `OutOfMemoryError: PermGen space` failures common on redeploying app servers.
