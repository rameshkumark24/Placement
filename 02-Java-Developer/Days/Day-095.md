# Day 095

**L-095** · Behavioural patterns — strategy, observer, command, template method, state

**Time:** 3 hrs · **Mode:** NEW

> Closes the pattern block. Behavioural patterns are about **how objects communicate and how
> responsibility is assigned** — and they are the group most changed by lambdas. Half of the Gang of
> Four's behavioural patterns are one line of Java 8 now, and knowing *which half* is the useful
> knowledge.

---

## Strategy

Encapsulate interchangeable algorithms behind one interface.

```java
public interface PricingStrategy { Money price(Order order); }

public class RegularPricing  implements PricingStrategy { … }
public class MemberPricing   implements PricingStrategy { … }
public class ClearancePricing implements PricingStrategy { … }

public class Checkout {
    private final PricingStrategy pricing;                 // injected — Day 091's DIP
    public Money total(Order o) { return pricing.price(o); }
}
```

This is **Day 090's Open/Closed answer** with a name: a new pricing rule is a new class, and
`Checkout` never changes.

**In modern Java it is usually a lambda:**

```java
public class Checkout {
    private final Function<Order, Money> pricing;
    public Checkout(Function<Order, Money> pricing) { this.pricing = pricing; }
}

new Checkout(order -> order.subtotal().times(0.9));
```

`Comparator` is the JDK's canonical strategy, and `Collections.sort(list, comparator)` is the pattern
in one line. So is every `Predicate` you pass to `filter` (Day 059).

**When the interface still earns its keep:** the strategy has more than one method, needs state,
needs a name for readability, or needs to be discovered by a container (`List<PricingStrategy>` —
Day 090). Otherwise, take the lambda.

## Observer

One-to-many notification: when the subject changes, all registered observers hear about it.

```java
public interface OrderListener { void onOrderPlaced(Order order); }

public class OrderService {
    private final List<OrderListener> listeners = new CopyOnWriteArrayList<>();   // Day 053

    public void addListener(OrderListener l) { listeners.add(l); }

    public void place(Order order) {
        repository.save(order);
        for (OrderListener l : listeners) {
            try { l.onOrderPlaced(order); }
            catch (Exception e) { log.error("listener {} failed", l, e); }   // ← isolate failures
        }
    }
}
```

Three production details that the textbook version omits, and all three are real bugs:

**1. Use a thread-safe list.** Registering a listener while iterating throws
`ConcurrentModificationException` (Day 052). `CopyOnWriteArrayList` is exactly right here — many
iterations, rare mutations (Day 053).

**2. Isolate listener failures.** One throwing listener must not prevent the others from running, and
must not fail the business operation. Catch per listener.

**3. `Observable`/`Observer` in the JDK are deprecated** (Java 9) — they were not thread-safe, not
generic, and required inheritance. Use your own interface, an event bus, or Spring's
`ApplicationEventPublisher`.

**The memory leak is the classic interview follow-up:** a listener registered and never removed keeps
the observer alive as long as the subject lives (Day 027's leak patterns). Either provide
`removeListener` and *use it*, or hold listeners weakly — and be aware that a lambda listener cannot
be unregistered unless you keep the reference.

Observer at scale becomes a **message queue** and eventual consistency (Stage 12); the pattern is the
in-process version of the same idea.

## Command

Wrap a request as an object, so it can be queued, logged, undone or replayed.

```java
public interface Command {
    void execute();
    void undo();
}

public class AddItemCommand implements Command {
    private final Cart cart; private final Item item;
    public void execute() { cart.add(item); }
    public void undo()    { cart.remove(item); }
}

public class CommandHistory {
    private final Deque<Command> done = new ArrayDeque<>();     // Day 051

    public void run(Command c) { c.execute(); done.push(c); }
    public void undo() { if (!done.isEmpty()) done.pop().undo(); }
}
```

**Undo is the property that justifies the pattern**, and it is why every editor has this shape. The
others follow: because a command is an object, it can be put on a queue, serialised, retried, or
written to a log and replayed — which is exactly what a **write-ahead log** is (Day 078's D-01) and
what **event sourcing** is (Stage 12).

`Runnable` is a command; every task you submit to an executor (Day 069) is this pattern. So is every
HTTP request handler, in a sense — a request is a command object.

The lambda form covers the no-undo case:

```java
executor.submit(() -> cart.add(item));
```

Keep the interface when you need `undo`, metadata, or serialisation.

## Template Method

Define an algorithm's skeleton in a base class; subclasses fill in steps.

```java
public abstract class DataImporter {
    // final — the ORDER is the invariant this class protects
    public final ImportResult importFrom(Path file) {
        validate(file);
        List<Record> records = parse(file);          // ← varies
        List<Record> cleaned = transform(records);   // ← varies, with a default
        int saved = persist(cleaned);
        notifyComplete(saved);
        return new ImportResult(saved);
    }

    protected abstract List<Record> parse(Path file);          // subclass MUST provide
    protected List<Record> transform(List<Record> r) { return r; }   // hook, optional
    protected void notifyComplete(int count) { }                     // hook, optional

    private void validate(Path f) { … }                        // fixed
    private int persist(List<Record> r) { … }                  // fixed
}

public class CsvImporter  extends DataImporter { … }
public class JsonImporter extends DataImporter { … }
```

**This is the one legitimate inheritance pattern** after Day 092's argument against inheritance, and
the reason is specific: the base class owns an **invariant that is the ordering itself**. Subclasses
cannot reorder the steps or skip validation, because `importFrom` is `final`.

Two rules that make it safe:

- **Make the template method `final`.** Otherwise a subclass overrides it and the invariant is gone.
- **Keep the hook count small.** Six abstract methods means the "skeleton" is doing nothing and you
  should have used composition.

`AbstractList`, `InputStream.read()`, and Spring's `JdbcTemplate` are all this. **`JdbcTemplate` is
the clearest example**: it owns connection acquisition, exception translation (Day 062) and cleanup —
you supply only the SQL and the row mapper, and you *cannot* forget to close the connection.

The composition alternative, when the ordering does not need protecting:

```java
public class ImportPipeline {
    private final Parser parser;
    private final Transformer transformer;      // strategy objects instead of subclasses
}
```

## State

An object changes behaviour when its internal state changes — implemented by *delegating to a state
object*, not by branching.

```java
// ❌ the smell: conditionals on a status field, scattered across methods
public void ship() {
    if (status == PAID) { status = SHIPPED; }
    else if (status == NEW) { throw new IllegalStateException("not paid"); }
    else if (status == CANCELLED) { throw new IllegalStateException("cancelled"); }
    // …repeat this chain in cancel(), refund(), deliver()
}
```

The problem is that the transition rules are **duplicated in every method** and there is no single
place to read them.

```java
public interface OrderState {
    default OrderState pay()    { throw new IllegalTransitionException(this, "pay"); }
    default OrderState ship()   { throw new IllegalTransitionException(this, "ship"); }
    default OrderState cancel() { throw new IllegalTransitionException(this, "cancel"); }
}

public enum OrderStatus implements OrderState {
    NEW       { public OrderState pay()    { return PAID; }
                public OrderState cancel() { return CANCELLED; } },
    PAID      { public OrderState ship()   { return SHIPPED; }
                public OrderState cancel() { return REFUNDING; } },
    SHIPPED   { public OrderState deliver(){ return DELIVERED; } },
    CANCELLED { },
    DELIVERED { };
}
```

**Every legal transition is now visible in one block**, and every illegal one throws by default
rather than by omission. Day 043 built exactly this with enums; here it has its name.

Two payoffs worth stating: you can generate a state diagram from the code, and adding a state is one
enum constant plus its legal transitions rather than an edit to five conditional chains.

**State vs Strategy** — the interview distinction: *structurally identical, different intent.*
Strategy is chosen by the **client** and does not change; State is changed by the **object itself**
as a consequence of its transitions.

## Chain of Responsibility, Iterator, Visitor, Mediator, Memento — briefly

**Chain of Responsibility** — pass a request along handlers until one deals with it. Servlet filters
(Day 066A), Spring Security's filter chain, and `try`/`catch` propagation (Day 061) are all this.

**Iterator** — sequential access without exposing the structure. Day 052; `Iterable` and `Iterator`
are built into the language via for-each.

**Visitor** — add operations to an object structure without modifying it, using double dispatch. It
is the one to be honest about: it is verbose, and **Java 21's pattern matching for switch over sealed
types replaces most uses** (Day 042):

```java
String describe(Shape s) {
    return switch (s) {                        // exhaustive over a sealed hierarchy
        case Circle c    -> "circle r=" + c.radius();
        case Square sq   -> "square s=" + sq.side();
        case Triangle t  -> "triangle";
    };
}
```

**Mediator** — objects communicate through a hub instead of directly, reducing n² coupling to n. An
event bus is one. The risk is the mediator becoming a god object.

**Memento** — capture and restore state without violating encapsulation. Undo (with Command),
snapshots, database savepoints.

## What lambdas replaced

| Pattern | Modern Java |
|---|---|
| Strategy | `Function`, `Predicate`, `Comparator` |
| Command (no undo) | `Runnable`, `Supplier` |
| Observer (single method) | `Consumer<Event>` |
| Template Method (single hook) | A higher-order function taking the varying step |
| Factory Method | `Supplier<T>` (Day 093) |
| Visitor over a closed hierarchy | `switch` pattern matching over sealed types |

**What survived**: multi-method interfaces, patterns needing state or identity (an unregisterable
listener, an undoable command), and anything a container must discover by type.

> **The patterns did not become wrong — the ceremony became unnecessary.** Naming this distinction is
> what separates someone who learned patterns in 2005 from someone who understands them.

## The honest warning

The Gang of Four book describes 23 patterns as *observations of recurring solutions*, not as a
catalogue to apply. The failure mode is real and common:

```java
// 💀 a codebase where patterns are the goal
AbstractSingletonProxyFactoryBean
SimpleBeanFactoryAwareAspectInstantiationStrategy
```

**Use a pattern when you have the problem it solves, and name it so others recognise the shape.** Do
not restructure working code to introduce one. If you cannot say in one sentence what problem the
pattern is solving here, do not use it.

## Common mistakes

| Mistake | Consequence |
|---|---|
| An interface where a lambda suffices | Ceremony |
| Non-thread-safe observer list | `ConcurrentModificationException` |
| Listener exceptions not isolated | One bad listener breaks the operation |
| Listeners never removed | Memory leak (Day 027) |
| Lambda listeners with no reference kept | Cannot ever unregister |
| Non-final template method | The invariant it protects is gone |
| Template method with six hooks | Should have been composition |
| State machine as scattered `if` chains | Transition rules duplicated and inconsistent |
| Confusing State with Strategy | Wrong ownership of the decision |
| Visitor where sealed + `switch` fits | Large amounts of unnecessary code |
| Applying patterns for their own sake | Indirection nobody can navigate |

## Interview questions

**Q: Strategy vs State?**
Structurally the same — delegate to an interchangeable object. The difference is intent and
ownership: the *client* picks a strategy and it does not change; the *object* changes its own state
as a result of transitions.

**Q: Which patterns do lambdas replace?**
Strategy, Command without undo, single-method Observer, single-hook Template Method and Factory
Method all collapse to a functional interface. Multi-method interfaces, stateful implementations and
container-discovered beans still need real types.

**Q: What is wrong with the JDK's `Observable`?**
Deprecated since Java 9 — not thread-safe, not generic, and it forces inheritance. Use your own
interface, an event bus, or Spring's event publisher.

**Q: Why must a template method be `final`?**
The base class exists to own the algorithm's ordering. If a subclass can override the template, the
invariant it protects disappears and the pattern provides nothing.

**Q: How do you model an order lifecycle?**
As a state machine — an enum where each constant declares its legal transitions and everything else
throws by default. All transitions are then visible in one place, and adding a state is one constant
rather than edits across five conditional chains.

**Q: What is Chain of Responsibility, and where have you seen it?**
Handlers arranged in a chain, each deciding to handle or pass along. Servlet filters, Spring
Security's filter chain, and exception propagation.
