# L-055 · Type erasure

## What it is

**Generic type information exists only at compile time. The compiler erases it and inserts casts.**

```java
// What you write
public class Box<T> {
    private T item;
    public T get() { return item; }
    public void set(T item) { this.item = item; }
}

// What the bytecode contains
public class Box {
    private Object item;                              // T → Object
    public Object get() { return item; }
    public void set(Object item) { this.item = item; }
}
```

**With a bound, `T` erases to the bound, not to `Object`:**

```java
class NumberBox<T extends Number> { T item; }
// erases to:
class NumberBox { Number item; }
```

**At the call site the compiler inserts the cast for you:**

```java
Box<String> box = new Box<>();
String s = box.get();

// compiles to:
String s = (String) box.get();      // ← the cast you no longer write
```

**Prove it yourself** (Day 024):

```bash
javap -c Box
# You will see Object in the descriptors, and checkcast at the call site.
```

## Why erasure — the honest reason

**Backward compatibility.** Java 5 had to run existing Java 1.4 code unchanged, and existing
libraries had to work with generic and non-generic clients simultaneously.

**Erasure meant no new bytecode, no new JVM, no recompiling the world.** A `List<String>` and a raw
`List` are the same class at runtime, so old code and new code interoperate freely.

**The alternative — reification, as C# chose — required changing the runtime.** C# did it because .NET
was young enough to afford it. Java wasn't.

**That's the trade: Java bought compatibility and paid with every restriction below.**

## What erasure costs you

### 1. No runtime type information

```java
List<String> strings = new ArrayList<>();
List<Integer> ints = new ArrayList<>();

strings.getClass() == ints.getClass();      // TRUE — both are just ArrayList

if (list instanceof List<String>) { }        // ❌ compile error
if (list instanceof List<?>) { }             // ✅ the only legal form
```

**You cannot ask an object what its type argument was.** That's why Jackson needs
`new TypeReference<List<User>>() {}` (Day 044) — an anonymous *subclass* records its type argument in
the class file, which erasure doesn't remove.

### 2. No generic array creation

```java
T[] array = new T[10];                  // ❌
List<String>[] arrays = new List<String>[10];   // ❌
```

**Because the JVM wouldn't know what to check on store.** Arrays are reified and check every write
(Day 031); generics are erased. **The two features are incompatible by design**, and this is the
sharpest expression of it.

```java
@SuppressWarnings("unchecked")
T[] array = (T[]) new Object[10];       // the workaround ArrayList uses
```

### 3. No overloading on type arguments

```java
void process(List<String> list) { }
void process(List<Integer> list) { }    // ❌ both erase to process(List)
```

**"Name clash: both methods have the same erasure."** A confusing error message the first time you
meet it.

### 4. No `static` context, no `instanceof`, no `new T()`

All from Day 054 — and all because `T` doesn't exist at runtime.

### 5. Catch clauses

```java
catch (MyException<String> e) { }        // ❌ — the JVM couldn't distinguish it
class MyException<T> extends Exception { }   // ❌ generic Throwable is banned entirely
```

## Bridge methods — the synthetic ones you'll see in stack traces

**Erasure breaks polymorphism, so the compiler patches it.**

```java
class Node<T> {
    public void set(T item) { }          // erases to set(Object)
}

class StringNode extends Node<String> {
    @Override public void set(String item) { }    // set(String) — a DIFFERENT signature!
}
```

**After erasure the parent has `set(Object)` and the child has `set(String)`.** Those are different
methods, so `set(String)` would *overload* rather than override — and dynamic dispatch (Day 038)
would call the wrong one:

```java
Node<String> n = new StringNode();
n.set("hello");           // the compiler emits invokevirtual set(Object) — which one runs?
```

**The compiler generates a bridge method:**

```java
class StringNode extends Node<String> {
    public void set(String item) { }                       // yours

    // SYNTHETIC, compiler-generated:
    public void set(Object item) { set((String) item); }   // ← the bridge
}
```

**The bridge overrides `set(Object)` and delegates to your real method, casting on the way.** That
restores correct dispatch.

**Verify it:**

```bash
javap -c StringNode
# You will see TWO set methods, one flagged ACC_BRIDGE ACC_SYNTHETIC
```

**Two practical consequences worth knowing:**

- **Bridge methods appear in stack traces**, which is confusing until you know what they are.
- **They're why `ClassCastException` can be thrown from a line you didn't write** — the cast lives
  inside the bridge:

```java
Node raw = new StringNode();      // raw type, no checking
raw.set(42);                       // 💥 ClassCastException inside the BRIDGE method
```

## Heap pollution

**A variable of a parameterised type refers to an object that isn't of that type.** The compiler
warns; erasure lets it happen.

```java
List<String> strings = new ArrayList<>();
List raw = strings;                      // raw type — unchecked
raw.add(42);                             // heap pollution! No error here.
String s = strings.get(0);               // 💥 ClassCastException — at a line that looks innocent
```

**The failure surfaces far from the cause**, which is what makes it nasty.

### Varargs + generics

```java
@SafeVarargs
static <T> List<T> listOf(T... items) { return Arrays.asList(items); }
```

**`T... items` becomes `T[]`, which is a generic array — which can't exist.** The compiler creates an
`Object[]` and warns about possible heap pollution.

```java
static <T> void unsafe(List<T>... lists) {
    Object[] array = lists;              // legal — arrays are covariant (Day 031)
    array[0] = List.of(42);              // heap pollution
    T first = lists[0].get(0);           // 💥 ClassCastException
}
```

**`@SafeVarargs` suppresses the warning and asserts you don't do that.** Only apply it when the method
**doesn't store anything into the varargs array and doesn't let it escape** — otherwise you're
silencing a real warning.

It's allowed on `static`, `final` and `private` methods only — ones that can't be overridden, since a
subclass could break the promise.

## Reifiable vs non-reifiable

| Reifiable — full type at runtime | Non-reifiable — type info erased |
|---|---|
| `String`, `Integer` | `List<String>` |
| `List` (raw) | `List<? extends Number>` |
| `List<?>` (unbounded wildcard) | `T` |
| `int[]`, `String[]` | `List<String>[]` |

**`List<?>` is reifiable** because the unbounded wildcard carries no information to erase — which is
exactly why `instanceof List<?>` is legal and `instanceof List<String>` isn't.

## What survives erasure — and it's more than people think

**Type arguments in the *class signature* are preserved in the class file**, even though the runtime
doesn't use them for checking:

```java
class StringList extends ArrayList<String> { }

var t = StringList.class.getGenericSuperclass();
// java.util.ArrayList<java.lang.String>   ← the String IS there
```

**That's the mechanism behind `TypeReference`, Spring's `ParameterizedTypeReference`, and Guice's
`TypeLiteral`.** Field, method-parameter and return-type generic signatures survive too, which is how
frameworks deserialise into `List<User>` correctly.

```java
Field f = MyClass.class.getDeclaredField("users");
f.getGenericType();          // java.util.List<com.app.User>
```

**"Erasure erases everything" is the common oversimplification.** What's erased is the *runtime type
of an instance*; declaration signatures survive in metadata. That distinction is a strong answer.

## Type this yourself

```java
import java.lang.reflect.*;
import java.util.*;

public class ErasureDemo {

    static class Node<T> {
        T item;
        public void set(T item) { this.item = item; System.out.println("   Node.set(Object)"); }
    }
    static class StringNode extends Node<String> {
        @Override public void set(String item) {
            super.item = item; System.out.println("   StringNode.set(String)");
        }
    }

    static class Holder { List<String> names; Map<String, List<Integer>> data; }
    static class StringList extends ArrayList<String> { }

    @SafeVarargs
    static <T> List<T> safeListOf(T... items) { return new ArrayList<>(Arrays.asList(items)); }

    public static void main(String[] args) throws Exception {

        // ---- 1. Same class at runtime ----
        System.out.println("--- erasure ---");
        List<String> a = new ArrayList<>();
        List<Integer> b = new ArrayList<>();
        System.out.println("   List<String>.getClass() == List<Integer>.getClass() : "
                + (a.getClass() == b.getClass()));

        // ---- 2. Heap pollution ----
        System.out.println("\n--- heap pollution ---");
        List<String> strings = new ArrayList<>();
        List raw = strings;                       // raw type
        raw.add(42);                              // no error HERE
        System.out.println("   raw.add(42) succeeded; list = " + strings);
        try {
            String s = strings.get(0);            // the cast fails HERE
        } catch (ClassCastException e) {
            System.out.println("   strings.get(0) → ClassCastException: " + e.getMessage());
            System.out.println("   ↑ the failure is FAR from the cause");
        }

        // ---- 3. Bridge methods ----
        System.out.println("\n--- bridge methods ---");
        for (Method m : StringNode.class.getDeclaredMethods())
            System.out.printf("   %-30s bridge=%b synthetic=%b%n",
                    m.getName() + Arrays.toString(m.getParameterTypes()),
                    m.isBridge(), m.isSynthetic());

        System.out.println("   calling through the parent type:");
        Node<String> n = new StringNode();
        n.set("hello");                            // dispatches via the bridge

        // ---- 4. ClassCastException from code you didn't write ----
        System.out.println("\n--- the bridge's hidden cast ---");
        Node rawNode = new StringNode();
        try { rawNode.set(42); }
        catch (ClassCastException e) {
            System.out.println("   rawNode.set(42) → CCE thrown INSIDE the bridge method");
        }

        // ---- 5. What SURVIVES erasure ----
        System.out.println("\n--- generic signatures survive in metadata ---");
        System.out.println("   StringList superclass: "
                + StringList.class.getGenericSuperclass());
        for (Field f : Holder.class.getDeclaredFields())
            System.out.println("   field " + f.getName() + " : " + f.getGenericType());

        // ---- 6. The TypeReference trick ----
        System.out.println("\n--- capturing a generic type ---");
        var ref = new TypeRef<List<String>>() { };
        System.out.println("   captured: " + ref.getType());

        // ---- 7. Safe varargs ----
        System.out.println("\n--- @SafeVarargs ---");
        System.out.println("   " + safeListOf("a", "b", "c"));
    }

    // The anonymous-subclass trick — the subclass's type argument is recorded
    static abstract class TypeRef<T> {
        Type getType() {
            return ((ParameterizedType) getClass().getGenericSuperclass())
                    .getActualTypeArguments()[0];
        }
    }
}
```

**Four things to observe:**

1. `List<String>` and `List<Integer>` are **literally the same class**.
2. **Heap pollution succeeds silently** and fails on a later, innocent-looking line.
3. **`StringNode` has two `set` methods**, one flagged bridge and synthetic — printed by reflection.
4. **The generic signatures ARE still there** for the superclass and the fields. That's the half of
   erasure people don't know about.

Then decompile:

```bash
javac ErasureDemo.java
javap -c -p 'ErasureDemo$StringNode'      # find both set methods and the checkcast in the bridge
```

## Interview questions

**Q: What is type erasure and why does Java use it?**
> Generic type information exists only at compile time; the compiler replaces type parameters with
> their bound — `Object` if unbounded — and inserts casts at call sites. Java chose it for backward
> compatibility: Java 5 had to run existing 1.4 bytecode and let generic and non-generic code
> interoperate without changing the JVM or recompiling every library. C# reified generics instead,
> because .NET was young enough to change its runtime.

**Q: What does erasure prevent you from doing?**
> Creating generic arrays, using `instanceof` with a type argument, instantiating a type parameter,
> declaring static members of a type parameter's type, overloading on differing type arguments since
> both erase to the same signature, and making a generic `Throwable`.

**Q: What is a bridge method?**
> A synthetic method the compiler generates to preserve polymorphism after erasure. If a subclass
> overrides a generic method with a concrete type — `set(String)` overriding `Node<T>.set(T)` — the
> erased signatures differ, so it would overload rather than override. The compiler adds a
> `set(Object)` that casts and delegates to `set(String)`, restoring correct dynamic dispatch. It's
> also why a `ClassCastException` can originate in a line you never wrote.

**Q: What is heap pollution?**
> When a variable of a parameterised type refers to an object that isn't of that type — typically
> through a raw type or an unchecked cast. Adding an `Integer` to a `List<String>` via a raw
> reference succeeds silently, and the `ClassCastException` surfaces much later at an unrelated
> retrieval, which is what makes it hard to trace.

**Q: When is `@SafeVarargs` appropriate?**
> When a generic varargs method neither stores anything into the varargs array nor lets it escape.
> The array is really an `Object[]` because generic arrays can't exist, so it can be aliased and
> polluted through array covariance. The annotation asserts you don't do that, and is only permitted
> on static, final or private methods — ones that can't be overridden.

**Q: Is all generic information erased?**
> No — that's the common oversimplification. The runtime type of an *instance* carries no type
> arguments, but generic *signatures* in class files survive: superclass type arguments, field types,
> method parameter and return types. That's what reflection exposes through `getGenericType`, and it's
> how Jackson's `TypeReference` and Spring's `ParameterizedTypeReference` work.
