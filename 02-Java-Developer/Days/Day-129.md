# Day 129

**L-129** · Webhooks — delivery guarantees, signature verification, replay protection

**Time:** 3 hrs · **Mode:** NEW

> Webhooks are HTTP callbacks: instead of a client polling you, **you call them**. Simple in concept,
> and they combine almost everything from this stage — retries, idempotency, HMAC signing, queues,
> SSRF and observability.
>
> The asymmetry worth noticing up front: **receiving a webhook is easy; sending them reliably is
> genuinely hard.**

---

# Part 1 — Why webhooks exist

```
POLLING                              WEBHOOKS
Client asks every 30 s               You call the client when something happens
❌ 2,880 requests/day per client     ✅ one request per actual event
❌ up to 30 s of latency             ✅ near-real-time
❌ wasteful at scale                 ❌ the client must expose an endpoint
✅ the client controls timing        ❌ delivery is not guaranteed
✅ trivially reliable                ❌ retries, ordering and security are your problem
```

**The trade is that you move complexity from the client to yourself.** A thousand integrators
polling is a thousand clients' problem; a thousand webhook subscriptions is *your* delivery system.

| Alternative | When |
|---|---|
| **Polling** | Few clients, latency tolerant, clients cannot expose endpoints |
| **Webhooks** | Many clients, near-real-time, standard for SaaS integrations |
| **WebSockets / SSE** (Day 018) | Browser clients, bidirectional or high frequency |
| **A message queue** (Day 125) | Internal services — do not use HTTP webhooks between your own services |

# Part 2 — Receiving a webhook

The easier side, and the one with the sharpest security requirement.

## ⭐ Verify the signature — first, always

**Your endpoint is on the public internet. Anyone can POST to it.** Without signature verification,
a webhook handler that credits an account is an open API for crediting accounts.

```java
@PostMapping("/webhooks/stripe")
public ResponseEntity<Void> handle(@RequestBody byte[] rawBody,          // ⭐ RAW bytes
                                   @RequestHeader("Stripe-Signature") String sigHeader) {

    // 1. Parse t= and v1= from the header
    long timestamp = parseTimestamp(sigHeader);
    String provided = parseSignature(sigHeader);

    // 2. ⭐ Reject stale — bounds the replay window (Day 115b)
    if (Math.abs(Instant.now().getEpochSecond() - timestamp) > 300)
        return ResponseEntity.badRequest().build();

    // 3. Recompute over timestamp + raw body
    String payload = timestamp + "." + new String(rawBody, UTF_8);
    String expected = hmacSha256Hex(payload, webhookSecret);

    // 4. ⭐ CONSTANT-TIME comparison
    if (!MessageDigest.isEqual(expected.getBytes(UTF_8), provided.getBytes(UTF_8)))
        return ResponseEntity.status(401).build();

    // 5. Idempotency — the same event WILL arrive twice (Day 123)
    if (!processedEvents.tryInsert(eventId(rawBody))) return ResponseEntity.ok().build();

    // 6. ⭐ ENQUEUE, do not process inline (Day 124)
    queue.enqueue(new ProcessWebhookJob(rawBody));

    // 7. Acknowledge FAST
    return ResponseEntity.ok().build();
}
```

**Every numbered step is load-bearing**, and three deserve emphasis:

**⚠️ `@RequestBody byte[]`, not a parsed object.** The signature covers the exact bytes sent. If your
framework deserializes and you re-serialize to verify, whitespace or key ordering differs and the
signature never matches — this is the single most common webhook-integration bug.

**The timestamp check is what prevents replay.** Without it, a captured request is valid forever.

**Enqueue rather than process inline.** Providers time out in 5–10 seconds and count a slow response
as a failure. Acknowledge in milliseconds and do the work in a job — this is Day 124's rule with an
external deadline attached.

## Receiving: the rest of the checklist

| Rule | Why |
|---|---|
| **Respond `2xx` fast** (< 1 s) | Providers time out and retry |
| **`2xx` means "received", not "processed"** | You will retry internally |
| **Idempotent by event id** | Retries and at-least-once delivery guarantee duplicates |
| **Handle out-of-order events** | `created` can arrive after `updated` — use the event timestamp |
| **Ignore unknown event types** | Providers add new ones without asking (Day 109) |
| **Do not trust the payload's data** | ⭐ It may be stale — re-fetch from the API for anything critical |
| **Log the raw body** | With secrets redacted — indispensable for debugging |

**"Do not trust the payload" is worth expanding.** A `payment.succeeded` webhook is a *notification
that something happened*, and by the time you process it the state may have changed again. For
anything financial, **treat the webhook as a trigger and re-read the authoritative state from the
provider's API.** Stripe's own documentation says exactly this.

# Part 3 — Sending webhooks

The hard side. You are now running a delivery system.

## The architecture

```
Event occurs
   ▼
OUTBOX (same transaction — Day 124)
   ▼
Fan out to every matching subscription
   ▼
Delivery QUEUE (Day 125)
   ▼
Worker: POST, sign, timeout, record the attempt
   ▼
2xx? → done      non-2xx / timeout? → retry with backoff → … → DEAD after N → alert the subscriber
```

**It is a queue, an outbox, retries and a DLQ — everything from Days 123–125 applied to HTTP.**

```sql
CREATE TABLE webhook_subscription (
    id, tenant_id, url, secret_hash, event_types TEXT[],
    status TEXT,                        -- ACTIVE | PAUSED | DISABLED
    consecutive_failures INT DEFAULT 0,
    created_at, disabled_at
);

CREATE TABLE webhook_delivery (
    id, subscription_id, event_id, event_type,
    payload JSONB,
    attempt INT, status TEXT,           -- PENDING | DELIVERED | FAILED | EXHAUSTED
    response_status INT, response_body TEXT,   -- ⭐ truncated; shown to the subscriber
    next_attempt_at TIMESTAMPTZ,
    created_at, delivered_at
);
CREATE INDEX ON webhook_delivery (next_attempt_at) WHERE status = 'PENDING';
```

## The payload and signature

```http
POST https://customer.example.com/hooks HTTP/1.1
Content-Type: application/json
X-Webhook-Id: evt_8f14e45f
X-Webhook-Timestamp: 1755172800
X-Webhook-Signature: v1=4a8f2c1e9b7d…
User-Agent: Acme-Webhooks/1.0

{
  "id": "evt_8f14e45f",
  "type": "order.created",
  "api_version": "2026-08-01",
  "created_at": "2026-08-14T10:22:01Z",
  "data": { "order_id": "ord_42", "status": "PAID" }
}
```

```java
String signed = timestamp + "." + body;                 // ⭐ timestamp INSIDE the signature
String signature = "v1=" + hmacSha256Hex(signed, subscription.secret());
```

**Sign the timestamp with the body**, or the timestamp can be altered and the replay window
extended. And version the signature scheme (`v1=`) so you can rotate the algorithm later — and send
**two signatures during a secret rotation** so subscribers can migrate without downtime (Day 115b's
two-key rotation).

## Retries

```
attempt 1  immediately
attempt 2  +1 min      ← with jitter (Day 123)
attempt 3  +5 min
attempt 4  +30 min
attempt 5  +2 hours
attempt 6  +12 hours
then: EXHAUSTED → email the subscriber, and after N consecutive failures DISABLE the subscription
```

**Auto-disable after sustained failure is not optional.** A subscriber whose endpoint has been dead
for a week is costing you a delivery attempt per event indefinitely, and at scale a few dead
endpoints consume real capacity. Disable, notify, and provide a re-enable path.

**Retry only on `5xx`, timeouts and `429`.** A `4xx` means the endpoint rejected it and will reject
it again (Day 123) — retrying is pure waste.

## ⚠️ The hazards of calling arbitrary URLs

**Sending webhooks means your servers make HTTP requests to URLs your customers chose.** Everything
from Day 119's SSRF section applies, and this is the most under-appreciated risk in webhook systems:

```java
// A subscriber registers: http://169.254.169.254/latest/meta-data/…
//                         http://localhost:8500/v1/kv/?recurse
//                         http://10.0.1.5:6379/
// ⇒ your webhook sender becomes an SSRF proxy INTO your own network
```

| Defence | Detail |
|---|---|
| **HTTPS only** | Reject `http://` at registration |
| **Validate the resolved IP** | Reject private, loopback, link-local and metadata ranges |
| **Connect to the validated IP** | Or DNS rebinding defeats the check (Day 119) |
| **No redirects** | Or re-validate every hop |
| **Egress proxy** | ⭐ Route all webhook traffic through a segment with no internal access |
| **Timeouts** | Connect 3 s, read 10 s — a slow endpoint must not hold a worker |
| **Cap the response size** | A 5 GB response body from a hostile endpoint |
| **Verify ownership at registration** | Send a challenge the subscriber must echo |

**The egress proxy is the architectural answer**, and it is the one that survives mistakes elsewhere.

## Slow consumers and isolation

**One slow subscriber must not delay everyone else.** With a single shared queue and a 10-second
timeout, one dead endpoint consumes workers and every other subscriber's deliveries queue behind it.

Fixes: per-subscription concurrency limits (a semaphore, Day 070), separate queues or partitions
keyed by subscription, and a **circuit breaker per subscription** (Day 123) so a consistently failing
endpoint is skipped quickly rather than waiting for a timeout every time.

## Ordering

**Do not promise it.** Retries alone break ordering — event 1 fails and is retried while event 2
succeeds immediately.

**Instead, make ordering unnecessary:** include `created_at` and a sequence number, and tell
subscribers to ignore events older than what they have already applied (last-write-wins). Where
per-entity ordering genuinely matters, serialise deliveries per entity and pause that entity's queue
on failure — which costs throughput and is why most providers do not offer it.

## What subscribers need from you

The operational features that separate a good webhook product from a frustrating one:

```
✅ A dashboard of recent deliveries with request and response bodies
✅ A manual "resend" button                    ⭐ the most requested feature
✅ Visible signing secret with rotation
✅ Event-type filtering per subscription
✅ A test/ping event to verify setup
✅ Email alerts on repeated failure and on auto-disable
✅ Documented retry schedule and timeout
✅ A sandbox mode
```

**The delivery log with replay is the feature that matters most.** Integration bugs are debugged from
"what exactly did you send me, and what did I return?", and without it every integration issue becomes
a support conversation.

## Common mistakes

| Mistake | Consequence |
|---|---|
| No signature verification | **Anyone can POST forged events** |
| Verifying against a re-serialized body | The signature never matches |
| No timestamp in the signature | Captured requests are valid forever |
| `String.equals` for signature comparison | Timing oracle |
| Processing inline | Provider timeout; retries; duplicates |
| Not idempotent by event id | Duplicate side effects |
| Trusting payload data as current | Acting on stale state |
| Failing on unknown event types | Breaks when the provider adds one |
| **Not validating subscriber URLs** | **SSRF into your own network** |
| No timeout on delivery | Workers held by dead endpoints |
| Shared queue with no isolation | One slow subscriber delays everyone |
| Retrying `4xx` | Guaranteed-to-fail attempts, forever |
| No auto-disable | Dead endpoints consume capacity indefinitely |
| Promising ordering | Retries break it |
| No delivery log or replay | Every integration issue is a support ticket |

## Interview questions

**Q: How do you secure a webhook endpoint?**
Verify an HMAC signature over the **raw** request bytes plus a timestamp, using a shared secret;
reject anything outside a five-minute window to prevent replay; compare in constant time; and be
idempotent by event id because duplicates are guaranteed.

**Q: Why must you use the raw body?**
The signature covers the exact bytes sent. Deserializing and re-serializing changes whitespace or key
order, so the recomputed signature never matches — the most common webhook integration bug.

**Q: Why enqueue rather than process inline?**
Providers time out in 5–10 seconds and treat a slow response as a failure, so they retry and you
process duplicates. Acknowledge in milliseconds and do the work in a background job.

**Q: What are the risks of *sending* webhooks?**
You are making HTTP requests to customer-controlled URLs, which is SSRF by design — a subscriber can
point you at cloud metadata or internal services. Enforce HTTPS, validate the resolved IP, connect to
that IP, refuse redirects, and route through an egress proxy with no internal access.

**Q: How do you handle a subscriber whose endpoint is down?**
Exponential backoff with jitter over hours, then mark the delivery exhausted and notify them. After N
consecutive failures, auto-disable the subscription with a re-enable path — otherwise dead endpoints
consume delivery capacity forever.

**Q: How do you stop one slow subscriber affecting others?**
Per-subscription concurrency limits, separate queues or partitions, short timeouts, and a circuit
breaker per subscription so a failing endpoint is skipped quickly.

**Q: Do you guarantee ordering?**
No — retries break it inherently. Include a timestamp and sequence number so subscribers can discard
stale events, and only serialise per entity if ordering is genuinely required, accepting the
throughput cost.

**Q: Should a subscriber trust the payload?**
Treat it as a notification, not as authoritative state. For anything financial, re-fetch the current
state from the API, because the payload is a snapshot that may already be out of date.

## 🎙️ Articulation drill

Three minutes: **"Design a webhook system for a SaaS product."**

Sending: outbox for atomicity, fan-out per subscription, a delivery queue with signed requests, short
timeouts, exponential backoff with jitter, auto-disable, per-subscription isolation and circuit
breakers, and an egress proxy because you are making requests to customer-controlled URLs. Receiving:
raw-body HMAC with a timestamp window and constant-time comparison, idempotent by event id, enqueue
and acknowledge fast. Close with the subscriber-facing half — a delivery log with replay — because
that is what makes the product usable rather than merely correct.
