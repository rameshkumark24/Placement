# Part 1 — L-033 · `static`

## What `static` means

**`static` means "belongs to the class, not to an instance."** One copy, shared by everything, for
the lifetime of the class.

```java
class Counter {
    static int total = 0;        // ONE copy, shared by all instances
    int instanceCount = 0;       // one copy PER instance

    Counter() { total++; instanceCount++; }
}

new Counter(); new Counter(); new Counter();
Counter.total          // 3   — accessed via the CLASS
```

**Where it lives** (Day 025): the static field is in **Metaspace**; the object it references is on
the heap.

```java
class Cache {
    static Map<String, byte[]> data = new HashMap<>();
    //     ↑ reference in Metaspace     ↑ HashMap and contents on the heap
}
```

**Static fields are GC roots** (Day 026). Anything reachable from one is immortal — which is why
the unbounded static collection is leak pattern #1 (Day 027).

## The four uses

### Static fields

Shared state. **Almost always a smell** unless the value is a constant.

```java
static final int MAX_SIZE = 100;                       // ✅ constant — fine
static final Logger log = LoggerFactory.getLogger(X.class);  // ✅ idiomatic
static int requestCount = 0;                            // ⚠️ mutable shared state
```

**Mutable static state is a shared-heap variable with no owner.** It's global state, and it brings
thread-safety problems (Day 065), test-isolation problems (one test's writes leak into the next), and
lifecycle problems.

**`static final` with an immutable value is fine.** `static` plus mutable is where trouble starts —
and note that `static final Map` is *not* immutable; the reference is final, the map isn't (Day 034).

### Static methods

```java
static int max(int a, int b) { return a > b ? a : b; }
```

Called on the class. **No `this`**, so they cannot access instance state and cannot be overridden
(see hiding, below).

**Good uses:** pure functions (`Math.max`), factory methods (`List.of`, `Integer.valueOf`),
utility classes.

**Bad use:** as a way to avoid dependency injection. A static method is a hard-coded dependency —
untestable, unmockable, unswappable. That's a real design cost, and Day 131 revisits it as the
argument for DI.

### Static blocks

```java
static {
    // runs ONCE, when the class is initialised
    CONFIG = loadConfiguration();
}
```

Runs during class initialisation, in source order with static field initialisers.

**Use sparingly.** Failure here throws `ExceptionInInitializerError`, which is confusing to debug —
it happens before any of your code appears to run, and the class becomes permanently unusable
(subsequent access throws `NoClassDefFoundError`).

### Static nested classes

```java
class Outer {
    static class Nested { }        // ✅ independent of any Outer instance
    class Inner { }                // ❌ holds a hidden reference to Outer.this
}

new Outer.Nested();                     // no Outer needed
new Outer().new Inner();                // requires an Outer instance
```

**Default to `static` for nested classes.** A non-static inner class holds an implicit reference to
its enclosing instance, which is leak pattern #5 (Day 027) — return one from a long-lived object and
you've pinned the outer object and everything it holds. Day 044 goes deeper.

## Initialisation order — the interview favourite

Two separate sequences. **Static happens once, per class. Instance happens per object.**

```
   CLASS INITIALISATION (once, on first active use)
   1. Static fields and static blocks — IN SOURCE ORDER
      (parent class first)

   OBJECT CREATION (every `new`)
   2. Instance fields and instance initialiser blocks — IN SOURCE ORDER
   3. Constructor body
      (and before all of that: the implicit or explicit super() call)
```

Put precisely, for `new Child()`:

```
   1. Parent static  (first time only)
   2. Child static   (first time only)
   3. Parent instance fields + init blocks
   4. Parent constructor body
   5. Child instance fields + init blocks
   6. Child constructor body
```

**Learn that six-line sequence.** It's asked verbatim.

### The trap this creates

```java
class Broken {
    Broken() {
        init();                 // calls the OVERRIDE, before Child's fields are initialised
    }
    void init() { }
}

class Child extends Broken {
    private String name = "set";

    @Override void init() {
        System.out.println(name);     // prints NULL — step 4 runs before step 5
    }
}
```

**Never call an overridable method from a constructor.** The subclass's fields haven't been
initialised yet, so the override sees defaults. This is a real bug and a classic *Effective Java*
item.

## Static hiding, not overriding

```java
class Parent { static void greet() { System.out.println("Parent"); } }
class Child extends Parent { static void greet() { System.out.println("Child"); } }

Parent p = new Child();
p.greet();          // prints "Parent" — resolved by the STATIC type
```

**Static methods are not polymorphic.** They're resolved at compile time from the declared type —
this is *hiding*, not overriding. (Day 024: `invokestatic`, not `invokevirtual`.)

**Same for fields:** field access is never polymorphic. `p.field` uses the static type too.

**Don't call a static method through an instance reference.** `p.greet()` compiles but is misleading;
write `Parent.greet()`.

## The static utility class idiom

```java
public final class StringUtils {      // final: cannot be subclassed
    private StringUtils() {           // private ctor: cannot be instantiated
        throw new AssertionError("No instances");
    }
    public static boolean isBlank(String s) { ... }
}
```

`final` + private constructor is the correct way to write a utility class. `Math`, `Collections` and
`Arrays` all do exactly this.

## Type this yourself

```java
public class StaticDemo {

    static { System.out.println("1. Parent static block"); }
    static int staticField = initStatic("2. Parent static field");

    { System.out.println("3. Parent instance block"); }
    int instanceField = initInstance("4. Parent instance field");

    StaticDemo() { System.out.println("5. Parent constructor"); }

    static int initStatic(String m)   { System.out.println(m); return 0; }
    int        initInstance(String m) { System.out.println(m); return 0; }

    // ---- the constructor-calls-override trap ----
    static class Base {
        Base() { System.out.println("   Base ctor calls init()"); init(); }
        void init() { }
    }
    static class Derived extends Base {
        private String name = "initialised";
        @Override void init() { System.out.println("   Derived.init sees name = " + name); }
    }

    // ---- hiding vs overriding ----
    static class P { static void stat() { System.out.println("   P.stat"); }
                     void inst() { System.out.println("   P.inst"); } }
    static class C extends P { static void stat() { System.out.println("   C.stat"); }
                     @Override void inst() { System.out.println("   C.inst"); } }

    public static void main(String[] args) {
        System.out.println("=== first instance ===");
        new StaticDemo();
        System.out.println("\n=== second instance (statics do NOT re-run) ===");
        new StaticDemo();

        System.out.println("\n=== constructor calling an override ===");
        new Derived();          // prints null — Derived's field isn't assigned yet

        System.out.println("\n=== static hiding vs instance overriding ===");
        P p = new C();
        p.stat();               // P.stat  — STATIC type wins
        p.inst();               // C.inst  — dynamic dispatch
    }
}
```

**Three things to observe:**

1. **Statics print once**, even though you create two instances. That's class initialisation vs
   object creation.
2. **`Derived.init` prints `null`.** The field assignment hasn't run yet — steps 4 and 5 of the
   sequence. This is the trap, reproduced.
3. **`p.stat()` prints `P.stat` but `p.inst()` prints `C.inst`.** Same reference, opposite dispatch
   behaviour. That contrast is the whole hiding-vs-overriding answer.

## Common mistakes

| Mistake | Correction |
|---|---|
| Mutable `static` fields | Global shared state — thread-unsafe, breaks test isolation, GC root. |
| `static final Map` treated as immutable | The *reference* is final; the map is still mutable. |
| Calling an overridable method from a constructor | The subclass's fields are still at defaults. |
| Expecting static methods to be polymorphic | They're hidden, not overridden — resolved by static type. |
| Calling a static method via an instance | Compiles but misleads. Use the class name. |
| Non-static nested class by default | Holds the enclosing instance — a leak. Prefer `static`. |
| Heavy work in a static block | Failures become `ExceptionInInitializerError`, then `NoClassDefFoundError`. |

## Interview questions

**Q: What does `static` mean, and where does a static field live?**
> It means the member belongs to the class rather than any instance — one copy, shared, for the
> class's lifetime. The field itself is in the method area, Metaspace since Java 8; if it's a
> reference, the object is on the heap. Static fields are GC roots, so anything reachable from one is
> never collected.

**Q: What's the initialisation order for `new Child()`?**
> Parent statics, then child statics — each once, on first use. Then for the object: parent instance
> fields and initialiser blocks in source order, parent constructor body, then child instance fields
> and blocks, then the child constructor body.

**Q: Why shouldn't a constructor call an overridable method?**
> The superclass constructor runs before the subclass's field initialisers, so an override invoked
> from the parent constructor sees the subclass's fields at their default values — typically null.
> It's a silent correctness bug.

**Q: Can static methods be overridden?**
> No. They can be *hidden* — a subclass may declare a method with the same signature — but resolution
> happens at compile time from the declared type, using `invokestatic` rather than `invokevirtual`. So
> a `Parent p = new Child()` call invokes the parent's version.

**Q: What's wrong with mutable static state?**
> It's global state with no owner. It's shared across threads, so it needs synchronisation; it leaks
> between tests, breaking isolation; it can't be substituted for testing; and as a GC root it retains
> everything it references for the life of the class.

**Q: Static or non-static nested class?**
> Static by default. A non-static inner class holds an implicit reference to its enclosing instance,
> which keeps the outer object alive as long as the inner one is reachable — a common memory leak, and
> unnecessary unless you genuinely need the outer instance.

# Part 2 — B-04 · Context switching

## What actually gets saved

The scheduler decides another thread should run. Concretely:

```
   1. Trap into the kernel (timer interrupt, or a blocking syscall)
   2. Save the current thread's CPU state into its PCB / TCB:
        • all general-purpose registers
        • program counter
        • stack pointer
        • status/flags register
        • floating-point and vector registers (often lazily)
   3. Scheduler picks the next thread                        (Day 036, B-05)
   4. Load that thread's saved state from its control block
   5. If it's a DIFFERENT PROCESS: switch the page table
        → the TLB is flushed or tagged
   6. Return to user mode, resume at the restored PC
```

## The direct cost vs the real cost

| | Cost |
|---|---|
| **Direct** — save/restore registers, scheduler | ~1–5 µs |
| **Indirect** — cold caches and TLB after the switch | **often much larger** |

**The indirect cost is what actually hurts.** Your thread had a working set in L1/L2 cache (Day 001).
Another thread runs and evicts it. When you resume, every access is a cache miss until the working
set is warm again — and Day 001's ladder says RAM is ~100× slower than L1.

**Thread↔thread switching is cheaper than process↔process**, because threads share an address space,
so the page table doesn't change and the TLB survives. That's Day 029's B-03 claim, mechanically
explained.

## Why this decides your thread pool size

```java
// 💀 200 threads on 8 cores
ExecutorService pool = Executors.newFixedThreadPool(200);
```

More runnable threads than cores means the scheduler is constantly switching. You pay switch cost
and cache thrash, and **throughput goes down while latency goes up**. Adding threads past a point
makes things strictly worse.

**The sizing rules** (Day 069 in full):

```
   CPU-bound:  threads ≈ number of cores          (+1 for pipeline stalls)
   I/O-bound:  threads ≈ cores × (1 + wait/compute)
```

**CPU-bound work gains nothing from more threads than cores.** I/O-bound work benefits, because
threads are blocked (Day 026, B-02: BLOCKED, not READY) and not competing for CPU at all.

**And this is precisely the argument for virtual threads** (Day 072): a blocked virtual thread is
unmounted from its carrier rather than occupying an OS thread, so 10,000 concurrent I/O operations
don't cause 10,000 threads' worth of switching.

## Voluntary vs involuntary

| | Cause |
|---|---|
| **Voluntary** | The thread blocks — I/O, lock wait, `sleep`. It gives up the CPU. |
| **Involuntary** | Time slice expired, or a higher-priority thread became runnable — preemption. |

**High involuntary switch counts mean CPU contention** — too many runnable threads. High voluntary
counts mean you're I/O-bound or lock-bound. **Distinguishing them tells you which problem you have**,
and that's a genuinely useful diagnostic:

```bash
pidstat -w -p <pid> 1        # cswch/s (voluntary) vs nvcswch/s (involuntary)
vmstat 1                     # 'cs' column — system-wide context switches
```

## Type this yourself

```java
import java.util.concurrent.*;

public class ContextSwitchCost {
    public static void main(String[] args) throws Exception {
        int cores = Runtime.getRuntime().availableProcessors();
        System.out.println("Cores: " + cores + "\n");

        // Pure CPU-bound work, varying pool size
        for (int threads : new int[]{1, cores, cores * 2, cores * 8, cores * 32}) {
            ExecutorService pool = Executors.newFixedThreadPool(threads);
            long start = System.currentTimeMillis();

            CountDownLatch done = new CountDownLatch(threads);
            long perThread = 200_000_000L / threads;
            for (int t = 0; t < threads; t++) {
                pool.submit(() -> {
                    long sum = 0;
                    for (long i = 0; i < perThread; i++) sum += i;   // CPU-bound, no blocking
                    done.countDown();
                    return sum;
                });
            }
            done.await();
            System.out.printf("%4d threads: %,5d ms%n", threads, System.currentTimeMillis() - start);
            pool.shutdown();
        }

        System.out.println("\nSame total work. Past core count, MORE threads is not faster —");
        System.out.println("and eventually gets slower from switching and cache thrash.");
    }
}
```

**Record the whole table.** You should see the time flatten around core count and then degrade. That
curve is the empirical answer to "how many threads should my pool have?" — and having measured it
yourself is far more convincing in an interview than quoting the formula.

Then watch the switches:

```bash
# Linux
pidstat -w -p <pid> 1 10
vmstat 1 10

# Windows — Performance Monitor: System → Context Switches/sec
```

## Interview questions

**Q: What happens during a context switch?**
> The kernel saves the current thread's register state — general-purpose registers, program counter,
> stack pointer, flags — into its control block, the scheduler picks the next thread, and its state is
> restored. If the switch is between processes, the page table changes too, which invalidates the TLB.

**Q: What actually makes context switching expensive?**
> The direct register save and restore is only a few microseconds. The larger cost is indirect: the
> incoming thread evicts the outgoing thread's working set from cache, so when it resumes it takes
> cache misses until the set is warm again. Process switches add TLB invalidation on top.

**Q: Why is switching between threads cheaper than between processes?**
> Threads in a process share an address space, so the page table doesn't change and TLB entries stay
> valid. A process switch changes the address space, forcing TLB flushes or tagging and cold address
> translations.

**Q: How do you size a thread pool?**
> For CPU-bound work, roughly the number of cores — more threads just add switching without adding
> throughput. For I/O-bound work, cores multiplied by one plus the ratio of wait time to compute time,
> because blocked threads aren't competing for CPU. And measure, because the formula is a starting
> point.

**Q: Voluntary vs involuntary context switches — what do they tell you?**
> A voluntary switch means the thread blocked on I/O or a lock and gave up the CPU. An involuntary
> switch means it was preempted because its time slice expired or a higher-priority thread became
> runnable. A high involuntary rate indicates CPU contention from too many runnable threads; a high
> voluntary rate indicates I/O or lock waiting.
