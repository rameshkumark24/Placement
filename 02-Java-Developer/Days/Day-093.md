# Day 093

**L-093** · Creational patterns — factory, builder, singleton (and why it is usually wrong)

**Time:** 3 hrs · **Mode:** NEW

> First of three pattern days. Read patterns as **vocabulary, not architecture**: their value is that
> "use a builder here" communicates a whole design in two words. Their danger is that people apply
> them for their own sake — a codebase where everything is a `AbstractFactoryProviderStrategy` is
> worse than one with no patterns at all.
>
> Most of these you have already used. Today they get names.

# Part 1 — The problem creational patterns solve

`new` is a hard-coded dependency (Day 091's DIP) and it is inflexible: it always returns exactly that
class, it cannot be varied, and it forces every caller to know the concrete type. Creational patterns
put a seam between "I need an object" and "here is how one is made".

---

## Static factory method

The simplest and most useful, and it is not even in the Gang of Four book — it is *Effective Java*
Item 1.

```java
public final class Money {
    private final long cents;
    private final Currency currency;

    private Money(long cents, Currency currency) { … }        // ← private constructor

    public static Money ofRupees(long rupees)  { return new Money(rupees * 100, INR); }
    public static Money ofCents(long cents)    { return new Money(cents, INR); }
    public static Money zero()                 { return ZERO; }               // cached
    public static Money parse(String s)        { … }
}
```

Five advantages over a constructor, and they are worth knowing individually:

1. **They have names.** `Money.ofRupees(50)` versus `new Money(50, true)` — you can have several
   with the same parameter types, which constructors cannot.
2. **They need not create a new object.** `Integer.valueOf` (Day 028's cache), `Boolean.valueOf`,
   `Optional.empty()`. This is where instance control lives.
3. **They can return a subtype.** `Collections.unmodifiableList` returns a private implementation;
   `EnumSet.of` returns `RegularEnumSet` or `JumboEnumSet` depending on size (Day 050) — and callers
   never know.
4. **The returned type can vary by input**, as in that `EnumSet` example.
5. **They reduce verbosity** and can validate before construction (Day 062's fail-fast).

The cost: a class with only private constructors cannot be subclassed — which is usually a feature
(Day 092), and it forces composition.

Conventions: `of`, `from`, `valueOf`, `getInstance`, `newInstance`, `create`, `parse`.

## Builder

**The problem: telescoping constructors.**

```java
// ❌
public Pizza(Size size) { … }
public Pizza(Size size, boolean cheese) { … }
public Pizza(Size size, boolean cheese, boolean pepperoni) { … }
public Pizza(Size size, boolean cheese, boolean pepperoni, boolean mushroom, boolean olives) { … }

new Pizza(LARGE, true, false, true, false);      // unreadable, and easy to transpose
```

Day 089 flagged boolean parameters; this is the same problem multiplied.

```java
public final class Pizza {
    private final Size size;
    private final Set<Topping> toppings;
    private final Crust crust;

    private Pizza(Builder b) {
        this.size = b.size;
        this.toppings = Set.copyOf(b.toppings);        // defensive copy — Day 034A
        this.crust = b.crust;
    }

    public static Builder builder(Size size) { return new Builder(size); }

    public static final class Builder {
        private final Size size;                        // required → constructor argument
        private final EnumSet<Topping> toppings = EnumSet.noneOf(Topping.class);
        private Crust crust = Crust.THIN;               // optional → sensible default

        private Builder(Size size) { this.size = Objects.requireNonNull(size); }

        public Builder topping(Topping t) { toppings.add(t); return this; }
        public Builder crust(Crust c)     { this.crust = c; return this; }

        public Pizza build() {
            if (toppings.size() > 8) throw new IllegalStateException("max 8 toppings");
            return new Pizza(this);                     // validate HERE, in one place
        }
    }
}

Pizza p = Pizza.builder(LARGE).topping(CHEESE).topping(MUSHROOM).crust(STUFFED).build();
```

Three design choices to notice:

**Required parameters go in the builder's constructor**, optional ones become methods. That gives you
compile-time enforcement of what is mandatory instead of a runtime check.

**Validation lives in `build()`**, so cross-field rules ("delivery address required if type is
DELIVERY") have one home and the object is never constructed invalid.

**The built object is immutable**, with defensive copies. A builder that produces a mutable object
has thrown away half the benefit.

**When to use one:** more than about four constructor parameters, several optional, several of the
same type (which makes transposition possible and silent), or you want immutability with flexible
construction. Below that, a constructor or a static factory is clearer.

Lombok's `@Builder` generates this; know how to write it by hand, because interviewers ask.

## Factory Method and Abstract Factory

**Factory Method** — a subclass decides which concrete class to create.

```java
public abstract class Dialog {
    protected abstract Button createButton();          // ← the factory method

    public void render() {                             // template — Day 095
        Button b = createButton();
        b.onClick(this::close);
        b.render();
    }
}
public class WindowsDialog extends Dialog {
    @Override protected Button createButton() { return new WindowsButton(); }
}
```

**Abstract Factory** — one object creates a *family* of related products that must be used together.

```java
public interface UiFactory {
    Button   createButton();
    Checkbox createCheckbox();
    Menu     createMenu();
}
public class MacUiFactory implements UiFactory { … }
public class WindowsUiFactory implements UiFactory { … }
```

**The distinguishing question is "one product or a consistent family?"** Abstract Factory exists to
guarantee you never mix a Mac button with a Windows checkbox — the *consistency* is the point, not
the creation.

In practice, in modern Java, these two are less common than they used to be. **A dependency injection
container is an abstract factory**, and a lambda or method reference (`Supplier<Button>`) replaces
most factory-method hierarchies in a single line:

```java
public class Dialog {
    private final Supplier<Button> buttonFactory;      // ← no subclass needed
    public Dialog(Supplier<Button> buttonFactory) { this.buttonFactory = buttonFactory; }
}
new Dialog(WindowsButton::new);
```

Say that in an interview — recognising which patterns the language has absorbed is a stronger signal
than reciting all 23.

## Prototype

Create by copying an existing instance, when construction is expensive or the configuration is
complex.

```java
public interface Prototype<T> { T copy(); }
```

Java's `Cloneable` is the broken built-in version (Day 041) — `clone()` is `protected` on `Object`,
the interface declares nothing, and the default is a shallow copy. **Use a copy constructor or a
static factory instead**, and note that with immutable objects (Day 034A) the whole pattern
evaporates: there is nothing to copy defensively.

# Part 2 — Singleton, and why it is usually wrong

## The correct implementations

If you must have one, there are exactly two good ways, both from Day 043 and Day 065:

```java
// 1. Enum — Joshua Bloch's recommendation. Serialization-safe and reflection-safe by spec.
public enum ConfigCache {
    INSTANCE;
    private final Map<String, String> values = loadOnce();
    public String get(String key) { return values.get(key); }
}

// 2. Holder idiom — lazy, thread-safe, no synchronization, no volatile
public final class ConnectionPool {
    private ConnectionPool() { }
    private static class Holder { static final ConnectionPool INSTANCE = new ConnectionPool(); }
    public static ConnectionPool getInstance() { return Holder.INSTANCE; }
}
```

The holder idiom works because **class initialisation is lazy and the JVM guarantees it runs exactly
once under its own lock** (Day 033). Double-checked locking (Day 065) is the version you should be
able to critique, not the one you should write.

## Why it is usually the wrong answer

**1. It is a global variable with a design pattern's reputation.** Every problem with globals
applies: any code can reach it, mutations come from anywhere, and you cannot reason locally.

**2. It hides dependencies.** A method calling `ConfigCache.INSTANCE.get(...)` has a dependency
invisible in its signature. You discover it when the test fails.

**3. It destroys testability.** You cannot substitute a fake (Day 075) without reflection or a
static-mocking library — and Day 075 made the point that needing to mock statics is itself a signal.

**4. Tests become order-dependent.** Shared mutable state across a test suite means test A's writes
affect test B (Day 074's flakiness rules).

**5. It violates SRP** — the class does its job *and* manages its own lifecycle, which are two
concerns and two actors.

**6. It is a lie under a class loader boundary.** "One per JVM" is really one per class loader
(Day 076A), so a servlet container or plugin system can have several.

## What to do instead

```java
// ❌
public class OrderService {
    public void place(Order o) { ConfigCache.INSTANCE.get("max.items"); }
}

// ✅ one instance, injected — "singleton scope" without the Singleton pattern
@Service
public class OrderService {
    private final Config config;
    public OrderService(Config config) { this.config = config; }
}
```

> **You almost always want *one instance*, not *the Singleton pattern*.** A DI container gives you
> exactly one instance, injected explicitly, replaceable in tests, with the dependency visible in the
> constructor. That is every benefit and none of the costs.

This is why Spring beans are singleton-scoped by default and yet nobody writes `getInstance()` in a
Spring application — and being able to draw that distinction is the whole point of the day.

**Where a real singleton is still defensible:** stateless utilities (`Math`), enums as constants,
logger factories, and a genuinely process-wide resource where the global nature *is* the requirement.
Even then, prefer injecting it.

## Object Pool — a brief note

Reuse expensive objects instead of creating them: HikariCP for JDBC connections, thread pools (Day
069). Correct for genuinely expensive resources with a hard external limit.

**Do not pool ordinary objects.** JVM allocation is a pointer bump in TLAB and young-generation
collection is nearly free (Day 026); pooling ordinary objects usually makes things slower *and*
introduces stale-state bugs. This is one of the most common misapplied optimisations in Java.

## Code to type

```java
// 1. Builder with required/optional split and cross-field validation
public final class HttpRequest {
    private final String method, url;
    private final Map<String, String> headers;
    private final byte[] body;
    private final Duration timeout;

    private HttpRequest(Builder b) {
        this.method = b.method; this.url = b.url;
        this.headers = Map.copyOf(b.headers);
        this.body = b.body == null ? null : b.body.clone();      // defensive
        this.timeout = b.timeout;
    }

    public static Builder builder(String method, String url) { return new Builder(method, url); }

    public static final class Builder {
        private final String method, url;
        private final Map<String, String> headers = new LinkedHashMap<>();
        private byte[] body;
        private Duration timeout = Duration.ofSeconds(30);

        private Builder(String method, String url) {
            this.method = Objects.requireNonNull(method);
            this.url = Objects.requireNonNull(url);
        }
        public Builder header(String k, String v) { headers.put(k, v); return this; }
        public Builder body(byte[] b)             { this.body = b.clone(); return this; }
        public Builder timeout(Duration d)        { this.timeout = d; return this; }

        public HttpRequest build() {
            if ("GET".equals(method) && body != null)
                throw new IllegalStateException("GET cannot have a body");     // cross-field
            if (!headers.containsKey("Host"))
                throw new IllegalStateException("Host header is required");
            return new HttpRequest(this);
        }
    }
}

// 2. Prove the singleton testability problem, then fix it
class LegacyOrderService {
    void place(Order o) {
        if (o.items().size() > Integer.parseInt(ConfigCache.INSTANCE.get("max.items")))
            throw new TooManyItemsException();
    }
}
// Try to unit-test the failure path with a max of 2 and no config file present.
// Then rewrite with constructor injection and write the same test in four lines.
```

Doing exercise 2 honestly is the point — **feel** the singleton being untestable before reading that
it is.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Telescoping constructors | Unreadable, transposable call sites |
| A builder producing a mutable object | Half the benefit thrown away |
| Validation in the builder's setters | Cross-field rules have no home |
| No defensive copies in `build()` | The builder can mutate the built object |
| Singleton as the default | Hidden dependencies, untestable, order-dependent tests |
| Double-checked locking by hand | Broken without `volatile` (Day 065) |
| `Cloneable` for copying | Shallow copy and a broken contract |
| Pooling ordinary objects | Slower, plus stale-state bugs |
| Abstract Factory for one product family | Ceremony where a `Supplier` would do |
| Patterns applied for their own sake | Indirection with no benefit |

## Interview questions

**Q: Static factory vs constructor — give three advantages.**
Names (so several factories can share a signature), no obligation to create a new instance (caching
and instance control), and the freedom to return a subtype chosen at runtime — as `EnumSet.of` does.

**Q: When would you use a builder?**
More than about four parameters, several optional, or several of the same type where transposition
would be silent. Required parameters go in the builder's constructor; cross-field validation goes in
`build()`; the result should be immutable.

**Q: How do you implement a singleton correctly in Java?**
An enum — serialization- and reflection-safe by specification — or the holder idiom, which relies on
the JVM's guaranteed one-time class initialisation. Double-checked locking needs `volatile` and is
worth knowing mainly as a critique.

**Q: Why is Singleton usually wrong?**
It is a global with hidden dependencies: callers do not declare it, tests cannot substitute it, state
leaks between tests, and it mixes the class's job with its own lifecycle. Use one injected instance
instead — you want *one instance*, not the pattern.

**Q: Factory Method vs Abstract Factory?**
Factory Method has subclasses decide which single product to create; Abstract Factory creates a
consistent *family* of related products so you cannot mix incompatible ones.

**Q: Which patterns has modern Java absorbed?**
Factory Method is often a `Supplier` or method reference, Abstract Factory is what a DI container
does, Strategy is a lambda, and Prototype largely disappears with immutability. Recognising this
matters more than reciting all 23 patterns.

## 🎙️ Articulation drill

Two minutes: **"How would you implement a singleton, and would you?"**

Answer the second half first — usually not, because you want one instance rather than the pattern,
and a container gives you that with the dependency visible and substitutable. Then show you *can*:
enum, or the holder idiom, with the reason each is thread-safe. Answering the design question before
the mechanics question is what distinguishes a senior answer here.
