# Part 2 — ⭐⭐ The trap: `ConcurrentHashMap` is not thread safety

```java
// ⭐⭐ WRONG — and it looks right, which is why it is the best probe in the round.
if (!map.containsKey(k)) {          // ⭐⭐ thread A checks: absent
    map.put(k, expensiveLoad(k));   // ⭐⭐ thread B checks between these two lines: also absent
}                                   // ⇒ ⭐⭐ BOTH LOAD. The map is thread-safe; YOUR SEQUENCE IS NOT.

// ⭐⭐ RIGHT — one atomic operation, and the map guarantees the mapping function runs ONCE per key
map.computeIfAbsent(k, this::expensiveLoad);
```

| ⭐⭐ The principle to state aloud | |
|---|---|
| ⭐⭐ **A thread-safe collection makes each *operation* atomic, not each *sequence* of operations** | ⭐⭐ check-then-act is the classic race |
| ⭐ The atomic composites you should know by name | ⭐⭐ `computeIfAbsent`, `compute`, `merge`, `putIfAbsent`, `replace(k, old, new)` |
| ⭐ Size, iteration, `containsKey` + `get` | ⭐⭐ **all weakly consistent — do not build invariants on them** |

⚠️ **And the counter-trap: `computeIfAbsent` holds a lock on the bin while the mapping function runs.**
A long load blocks other keys hashing to the same bin, **and a mapping function that recursively touches
the same map deadlocks.** So it is correct for cheap loads and dangerous for slow ones — **which is
exactly why the loading design in Part 4 exists.**

# Part 3 — ⭐⭐ The design (6–32)

```java
final class Entry<V> {
    final V value;
    final long expiresAtNanos;                   // ⭐⭐ nanoTime — MONOTONIC (Day 409)
    boolean isExpired(long now) { return now >= expiresAtNanos; }
}

public final class TtlLruCache<K, V> {
    private final int capacity;
    private final LinkedHashMap<K, Entry<V>> map;   // ⭐ access-order = LRU for free
    private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
```

| ⭐⭐ The three decisions worth defending | |
|---|---|
| ⭐⭐ **`System.nanoTime()` for expiry, not `currentTimeMillis()`** | ⭐⭐ **the wall clock can step backwards and un-expire your entries** (Day 409) |
| ⭐⭐ **`LinkedHashMap` in access-order mode** | ⭐ recency ordering with no hand-written linked list — **say you know the manual version too** (Day 476) |
| ⭐⭐ **Lazy expiry on read, plus eviction on write** | ⭐⭐ no sweeper thread; **but expired entries hold memory until touched** — state that cost |

```java
public V get(K key) {
    long now = System.nanoTime();
    lock.readLock().lock();
    Entry<V> e;
    try { e = map.get(key); } finally { lock.readLock().unlock(); }

    if (e == null) return null;
    if (e.isExpired(now)) {                       // ⭐⭐ expired ⇒ needs a WRITE lock to remove
        lock.writeLock().lock();
        try { map.remove(key, e); } finally { lock.writeLock().unlock(); }   // ⭐ remove(k, v): only if unchanged
        return null;
    }
    return e.value;
}
```

⚠️ **Two things to volunteer here.** First: **a `get` on a `LinkedHashMap` in access-order mode is a
structural modification**, so it cannot actually be done under a read lock — **which is a real reason to
prefer a `ConcurrentHashMap` plus a separate recency structure, or to accept approximate LRU.** Saying
that unprompted is a very strong signal. Second: **`remove(key, entry)` rather than `remove(key)`** — so
a concurrent refresh is not destroyed by a late expiry (Day 411's fencing instinct).

| ⭐ The lock choice, argued | |
|---|---|
| ⭐ `synchronized` | ⭐ simplest, correct, **one lock for everything** |
| ⭐⭐ **`ReadWriteLock`** | ⭐⭐ good when reads dominate; **worse than `synchronized` when writes are frequent** |
| ⭐⭐ **Striped locks** | ⭐⭐ lock per bucket — what `ConcurrentHashMap` does internally |
| ⭐ Lock-free | ⭐⭐ `ConcurrentHashMap` + `AtomicLong` counters + **approximate** LRU (what Caffeine does) |

> **⭐ The senior answer names the last row: "production caches like Caffeine do not maintain exact LRU
> under concurrency, because the bookkeeping costs more than the hit-rate gain. They batch access records
> in ring buffers and apply them asynchronously, so the eviction order is approximate."** **Knowing that
> exactness was traded away deliberately is the point.**

# Part 4 — ⭐⭐ The extension: the stampede (32–40)

```
⭐⭐ "1,000 threads request the same missing key at once. What happens?"
⭐ ❌ ⭐⭐ 1,000 loads of the same value ⇒ the origin is flattened ⇒ ⭐⭐ THE CACHE CAUSED THE OUTAGE
⭐ ✅ ⭐⭐ SINGLE-FLIGHT: the first requester loads; the other 999 WAIT ON THE SAME FUTURE.

⭐   ⭐⭐ The four-line answer:
⭐   ConcurrentHashMap<K, CompletableFuture<V>> inFlight;
⭐   CompletableFuture<V> f = inFlight.computeIfAbsent(k, key ->
⭐       CompletableFuture.supplyAsync(() -> load(key))            // ⭐⭐ off the map's lock
⭐           .whenComplete((v, ex) -> inFlight.remove(key)));      // ⭐⭐ ALWAYS clean up, incl. failure
⭐   return f.get(timeout);                                        // ⭐⭐ bounded wait, not forever
```

| ⭐ The follow-ups they will ask | |
|---|---|
| ⭐⭐ **"What if the load fails?"** | ⭐⭐ remove the future so the next caller retries — **and consider negative caching with a short TTL** so a persistently missing key does not stampede repeatedly |
| ⭐⭐ **"What if the load takes 30 seconds?"** | ⭐⭐ every waiter is blocked — **bound the wait and fail fast** rather than tying up the pool |
| ⭐ "Refresh-ahead?" | ⭐ serve the stale value and refresh asynchronously **before** expiry — no waiter ever blocks |
| ⭐ "Jittered TTLs?" | ⭐⭐ yes — **otherwise everything loaded together expires together** (Day 388) |

> **⭐⭐ Refresh-ahead is the answer that shows you have operated a cache: `expireAfterWrite` gives you a
> cliff where every waiter blocks; `refreshAfterWrite` serves the stale value and reloads in the
> background, so the p99 never contains a load.** **That trade — slightly stale versus occasionally
> slow — is a real product decision.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **"`ConcurrentHashMap`, so it's thread-safe"** | ⭐⭐ operations are atomic; **your sequence is not** |
| ⭐⭐ **Check-then-act (`containsKey` then `put`)** | ⭐⭐ two threads both load |
| ⭐ Long-running work inside `computeIfAbsent` | ⭐⭐ blocks the bin; recursion deadlocks |
| ⭐⭐ **`currentTimeMillis()` for expiry** | ⭐⭐ a backwards clock step un-expires entries |
| ⭐ `remove(key)` instead of `remove(key, value)` | ⭐ a late expiry destroys a fresh refresh |
| ⭐ Defaulting to `synchronized` with no comparison | ⭐⭐ the lock choice is the round |
| ⭐ `ReadWriteLock` on a write-heavy cache | ⭐ slower than `synchronized` |
| ⭐ Claiming exact LRU under concurrency is free | ⭐⭐ the bookkeeping costs more than it gains |
| ⭐⭐ **No stampede protection** | ⭐⭐ the cache becomes the cause of the outage |
| ⭐ Single-flight without cleanup on failure | ⭐⭐ a poisoned future served forever |
| ⭐ Unbounded wait on the shared future | ⭐ one slow load ties up every thread |
| ⭐ Uniform TTLs | synchronised expiry is a self-inflicted herd |
| No eviction at all | it is a memory leak with a nice API |

## Interview questions

**Q: Is a `ConcurrentHashMap` enough to make your cache thread-safe?**
No, and this is the most useful distinction in the round. A concurrent map makes each individual operation
atomic; it says nothing about a sequence of operations. Checking whether a key is absent and then putting
it is check-then-act — two threads can both observe absence and both load. The fix is an atomic composite
like `computeIfAbsent`, which guarantees the mapping function runs once per key. The counter-trap is that
`computeIfAbsent` holds a bin lock while the function runs, so it is right for cheap computation and wrong
for a slow remote load, which is why the loading path needs its own design.

**Q: Which clock do you use for expiry?**
`System.nanoTime`, because it is monotonic. The wall clock can be stepped backwards by NTP, and if expiry
is computed from it then entries that had expired become un-expired — which is a genuinely confusing bug
because it is intermittent and correlates with nothing in your code. Wall clock time is for displaying
when something expires; monotonic time is for deciding whether it has.

**Q: How do you handle a thousand threads requesting the same missing key?**
Single-flight. A map of in-flight futures keyed by cache key, populated with `computeIfAbsent`, so the
first caller starts the load and everyone else receives the same future and waits. Two details matter more
than the happy path: the future must be removed on completion including on failure, or a failed load is
served to every subsequent caller forever; and the wait has to be bounded, because otherwise one
thirty-second load ties up every thread in the pool. Without this the cache becomes the cause of the
outage rather than the protection against it.

**Q: What do real caches do about LRU under concurrency?**
They do not maintain it exactly. Keeping a strict recency order requires mutating a shared structure on
every read, which turns a read-mostly cache into a write-contended one — the bookkeeping costs more than
the hit-rate improvement is worth. Caffeine records accesses into per-thread ring buffers and applies them
asynchronously, so the eviction order is approximate and the read path stays cheap. The interesting part
is that exactness was traded away deliberately, and knowing that is more useful than being able to
implement textbook LRU.

**Q: Expire after write, or refresh after write?**
Expire-after-write creates a cliff: at the moment of expiry the next caller blocks for a full load, so
your p99 contains the origin's latency. Refresh-after-write serves the stale value and reloads in the
background, so no request ever waits — at the cost of occasionally serving data that is slightly out of
date. That is a product decision rather than a technical one, and I would ask which the domain tolerates.
I would also jitter TTLs regardless, because entries loaded together otherwise expire together and
recreate the stampede on a schedule.
