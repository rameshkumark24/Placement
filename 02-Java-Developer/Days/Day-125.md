# Part 1 — Delivery guarantees and the acknowledgement

```
Producer ──► [ Broker ] ──► Consumer
                  │              │
                  └──── ACK ◄────┘   "I have finished. You may delete it."
```

**The acknowledgement is the entire design.** Everything else follows from *when* you send it.

```java
// ❌ auto-ack — the broker deletes the message on DELIVERY
channel.basicConsume(queue, /*autoAck*/ true, handler);
// crash during processing ⇒ the message is GONE. At-most-once.

// ✅ manual ack — acknowledge only after the work is DONE
channel.basicConsume(queue, false, (tag, msg) -> {
    process(msg);                                     // if this throws or crashes…
    channel.basicAck(msg.getEnvelope().getDeliveryTag(), false);   // …this never runs
});
// ⇒ the broker redelivers. At-LEAST-once.
```

| Semantics | Ack timing | Result |
|---|---|---|
| **At-most-once** | Before processing | Fast; **messages lost on crash** |
| **At-least-once** | After processing | ✅ **The default choice** — duplicates possible |
| ~~Exactly-once~~ | — | **Does not exist** (Day 123) |

> **Ack after processing, and make the consumer idempotent.** That is at-least-once plus
> idempotency, which is what "exactly-once" always means in practice.

⚠️ **The mistake to internalise:** acking *before* processing is silent data loss that only appears
during a deploy or a crash — precisely when nobody is looking at the queue.

## Nack and requeue

```java
channel.basicAck(tag, false);          // done
channel.basicNack(tag, false, true);   // failed — REQUEUE it
channel.basicNack(tag, false, false);  // failed — do NOT requeue ⇒ to the DLQ
```

**The poison-message trap:** a message that always fails, requeued forever, is an infinite loop that
consumes a worker permanently. It is one of the most common queue outages.

> **Every requeue must be counted, and after N attempts the message goes to the dead-letter queue.**

# Part 2 — Visibility timeout

The pull-based model (SQS, and the same idea in most database queues):

```
1. Consumer calls receive() → the message becomes INVISIBLE to other consumers
2. A timer starts: the VISIBILITY TIMEOUT (default 30 s)
3a. Consumer deletes it before the timeout   ⇒ gone
3b. Timeout expires first                    ⇒ the message becomes VISIBLE AGAIN
```

**It is a lease, not a lock.** The consumer holds exclusive access for a bounded time; if it dies, the
lease lapses and someone else takes over. No coordination, no heartbeat protocol, and crash recovery
is automatic.

**⭐ The classic bug:** processing takes longer than the visibility timeout.

```
Visibility timeout: 30 s.  Job takes 45 s.

t=0   Worker A receives, starts
t=30  Timeout expires → the message reappears
t=31  Worker B receives THE SAME MESSAGE and starts
t=45  A finishes, deletes                       ← both did the work
t=76  B finishes, delete fails (already gone)
```

**Duplicate processing, and it will not reproduce in testing** because your test data processes in
two seconds.

Three fixes, and you want more than one:

1. **Set the timeout above the p99 processing time**, with margin.
2. **Extend the lease from inside a long job** — `ChangeMessageVisibility`, called periodically.
3. **Be idempotent**, because 1 and 2 can both fail.

**The trade-off in choosing it:** too short causes duplicate processing; too long means a crashed
worker's message is stuck for that whole period. There is no value that is right for every job, which
is an argument for separate queues per job type.

# Part 3 — The brokers

## RabbitMQ — a message broker with routing

```
Producer ──► EXCHANGE ──(binding rules)──► QUEUE ──► Consumer
```

| Exchange | Routes |
|---|---|
| `direct` | Exact routing-key match |
| `topic` | Pattern match — `order.*.created`, `#.error` |
| `fanout` | To every bound queue |
| `headers` | By header attributes |

**Push-based**, with `prefetch` controlling how many unacknowledged messages a consumer may hold —
which is the flow-control knob:

```java
channel.basicQos(10);       // ⭐ at most 10 unacked. Without this, one consumer takes EVERYTHING.
```

**`prefetch` unset is a real problem:** RabbitMQ pushes as fast as it can, so one consumer buffers
thousands of messages while others sit idle, and a crash redelivers all of them.

✅ Rich routing, priorities, delayed messages, mature. ❌ Throughput lower than Kafka; a queue that
grows very large degrades.

## AWS SQS — a managed queue

| | Standard | FIFO |
|---|---|---|
| Ordering | ❌ best-effort | ✅ per message-group |
| Duplicates | at-least-once | exactly-once *within a 5-minute dedup window* |
| Throughput | effectively unlimited | 3,000/s batched |

**Long polling is not optional** — without it you pay for empty receives and add latency:

```java
receiveMessage().withWaitTimeSeconds(20);        // ⭐ long poll
```

**FIFO's `MessageGroupId` is the important detail:** ordering is guaranteed *within a group*, and
different groups process in parallel. Use a per-entity id (`order-42`) so operations on one order are
ordered while throughput stays high. One group for everything serialises your entire queue.

✅ Zero operations, effectively infinite scale, built-in DLQ. ❌ AWS-only, no routing, 256 KB limit.

## Kafka — a distributed log, not a queue

**This is the one people misuse, because it is not a queue at all.**

```
Topic  ├─ Partition 0: [0][1][2][3][4] …      ← an APPEND-ONLY, IMMUTABLE log
       ├─ Partition 1: [0][1][2] …
       └─ Partition 2: [0][1][2][3] …

Consumer group A ── offset 3 on P0            each consumer tracks its OWN position
Consumer group B ── offset 1 on P0            ← independent; both read the same messages
```

The differences that matter:

| | Queue (RabbitMQ, SQS) | Kafka |
|---|---|---|
| On consume | Message **deleted** | **Retained** — consumers track an offset |
| Replay | ❌ gone | ✅ **reset the offset and re-read** |
| Consumers | Compete for messages | Each group reads **everything** |
| Ordering | Hard | ✅ **guaranteed within a partition** |
| Scaling unit | More consumers | **Partitions** — consumers ≤ partitions |
| Throughput | High | **Very high** — millions/s |

**Three consequences worth stating:**

**Replay is the reason to choose Kafka.** A bug corrupted six hours of data? Reset the offset and
reprocess. A new service needs the history? Read from the beginning. No queue can do this.

**Ordering is per partition, and the partition key decides it.** Key by entity id
(`order-42`) so all events for one order land in one partition and stay ordered; keying randomly
gives you throughput and no ordering at all.

**Consumers cannot exceed partitions.** Eight partitions means at most eight consumers in a group —
the ninth is idle. **Partition count is chosen up front and is painful to increase**, because it
changes the key→partition mapping.

✅ Replay, very high throughput, ordering, multiple independent consumers, event sourcing.
❌ Operationally heavy, no per-message ack or delay, no priorities, no per-message DLQ.

## Redis Streams and lists

`LPUSH`/`BRPOP` is a queue in two commands — genuinely fine for simple cases if you already run
Redis. **Redis Streams** adds consumer groups, acknowledgements and pending-entry tracking — a
middle ground between a list and a broker.

⚠️ **Durability is weaker.** Redis persistence is asynchronous by default, so a crash can lose recent
messages. Acceptable for jobs you can regenerate; not for payments.

## Choosing

```
Simple background jobs, already on Postgres     → the job table + SKIP LOCKED (Day 124) ⭐
Simple jobs, already on Redis                    → Redis Streams / a library
Complex routing, priorities, delays              → RabbitMQ
On AWS, want zero operations                     → SQS (+ SNS for fan-out)
Event streaming, replay, multiple consumers      → Kafka
High throughput with ordering per entity         → Kafka
```

> **Do not start with Kafka.** It is chosen for replay, ordering and throughput. If you want "run
> this job later", you want a queue — and quite possibly just a table.

# Part 4 — Patterns and hazards

## Fan-out

```
                  ┌──► email queue    ──► email worker
Event ──► TOPIC ──┼──► analytics queue──► analytics worker
                  └──► search queue   ──► indexer
```

One event, several independent consumers, each with its own retry and DLQ. RabbitMQ: a fanout or
topic exchange. AWS: SNS → several SQS queues. Kafka: several consumer groups.

**Independence is the point.** If the indexer is broken, email still works and the indexer's backlog
is contained.

## Ordering — and why it is expensive

Ordering guarantees cost parallelism. **Partition by entity, not globally:**

```
Kafka:  partition key = orderId       → ordered per order, parallel across orders
SQS FIFO: MessageGroupId = orderId    → same idea
```

**Even then, ordering across *different* topics or queues is not guaranteed.** The usual answer is to
stop needing it: include a version or timestamp and let consumers ignore out-of-order updates
(last-write-wins), or make handlers commutative.

## Backpressure

Day 070's principle, now distributed:

```
Producer 10,000/s ──► Queue ──► Consumers 1,000/s     ⇒ +9,000 messages every second
```

The queue absorbs bursts. It cannot absorb a sustained imbalance — it grows until the broker fills.
Options: scale consumers, rate limit producers (Day 122), or shed load. **A bounded queue that
rejects is usually better than an unbounded one that dies**, because rejection is visible.

## Message design

```json
{
  "id": "msg_8f14e45f",                    // ⭐ for consumer-side dedup (Day 123's inbox)
  "type": "order.created",
  "version": 2,                             // ⭐ schema version
  "occurred_at": "2026-08-14T10:22:01Z",
  "correlation_id": "req_a3f9c2e1",         // ⭐ trace it back to the request (Day 127)
  "data": { "order_id": "ord_42" }          // ⭐ IDs, not full objects (Day 124)
}
```

**Schema evolution is a versioning problem** (Day 109) and the rules are the same: adding optional
fields is safe, removing or renaming is breaking, and consumers must **ignore unknown fields**.
Kafka's schema registry with Avro enforces compatibility; without one, write the rules down.

**Keep messages small.** For a large payload, store it (S3) and send the reference — the
**claim-check pattern**.

## The hazards checklist

| Hazard | Defence |
|---|---|
| Poison message | Attempt counter → DLQ |
| Processing slower than the visibility timeout | Longer timeout, lease extension, idempotency |
| Consumer lag growing | Alert on lag/depth; scale consumers |
| Duplicates | Idempotent consumers, inbox dedup |
| Out-of-order | Partition by entity; version fields |
| Unbounded queue growth | Backpressure; bounded queues; alerting |
| Silent consumer death | ⭐ **Alert on zero throughput** (Day 124) |
| DLQ ignored | Alert on any message landing in it |
| One consumer hogging | `prefetch` / `basicQos` |
| Broker as a single point of failure | Clustering, replication, and know your `acks` setting |

**Producer durability is worth one line:** in Kafka, `acks=0` means fire-and-forget, `acks=1` means
the leader has it, and **`acks=all` means every in-sync replica has it**. Anything less than `all`
can lose messages on a broker failure — the same "durability is a spectrum" point as Day 117.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Auto-ack | Messages lost on crash — invisibly |
| Requeueing without a counter | A poison message loops forever |
| Visibility timeout below p99 processing time | Duplicate processing |
| Non-idempotent consumers | Duplicates become data corruption |
| No DLQ, or an unmonitored one | Silent data loss |
| No `prefetch` limit | One consumer buffers everything |
| Kafka for simple job queues | Heavy operations for no benefit |
| Too few Kafka partitions | Consumers cannot scale past the partition count |
| Random partition keys with ordering requirements | No ordering at all |
| Global ordering | Serialises everything; no parallelism |
| Large payloads in messages | Broker pressure; use claim-check |
| No message id | Consumer-side dedup is impossible |
| No schema versioning | Consumer changes become coordinated deploys |
| `acks=1` on critical topics | Message loss on broker failure |
| No lag or throughput alerting | You learn about the backlog from customers |

## Interview questions

**Q: What delivery guarantees exist, and which do you use?**
At-most-once (ack before processing — fast, loses messages) and at-least-once (ack after — the
default). Exactly-once does not exist at the transport level; what is sold as exactly-once is
at-least-once plus idempotent consumers.

**Q: What is a visibility timeout, and what is the classic bug?**
A lease: a received message is hidden from other consumers for a fixed period, and reappears if not
deleted in time. The classic bug is processing that takes longer than the timeout — the message
reappears and a second consumer processes it in parallel. Set it above p99, extend the lease from
long jobs, and be idempotent.

**Q: How is Kafka different from a queue?**
Kafka is an append-only log: messages are retained rather than deleted, consumers track their own
offsets, so multiple groups read everything independently and **you can replay by resetting the
offset**. Ordering is guaranteed within a partition, and consumers cannot exceed the partition count.

**Q: When would you choose Kafka?**
When you need replay, ordering per entity, very high throughput, or several independent consumers of
the same stream. Not for "run this job later" — that is a queue, and often just a database table.

**Q: What is a poison message?**
One that always fails and is requeued forever, consuming a worker indefinitely. Count attempts and
route to a dead-letter queue after N.

**Q: How do you handle ordering?**
Partition by entity id so events for one entity are ordered while different entities proceed in
parallel. Global ordering serialises everything. Where possible, remove the requirement with version
fields and last-write-wins.

**Q: What do you monitor?**
Consumer lag or queue depth, oldest message age, processing time, failure and retry rates, DLQ size —
and throughput itself, because silent consumer death leaves the API healthy while work stops.

**Q: What does `acks=all` mean and why does it matter?**
The producer waits until every in-sync replica has the message. `acks=1` returns once the leader has
it, so a leader failure before replication loses the message.
