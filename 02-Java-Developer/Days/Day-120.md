# Part 1 — Why caching works

**The latency ladder** (Day 001), which is the whole argument in one table:

```
L1 cache            ~1 ns
Main memory        ~100 ns
Redis, same DC     ~500 µs        ←  5,000× slower than memory
SSD random read      ~1 ms
Database query    1–100 ms        ←  and often 10× that with joins
Cross-region      ~50–150 ms
```

Caching works because of **locality**: a small fraction of data accounts for most requests (the
80/20 rule, and often far more extreme). A 95% hit rate turns an average 20 ms query into
`0.95 × 0.5 ms + 0.05 × 20 ms ≈ 1.5 ms`.

**The arithmetic worth doing before adding a cache:**

```
effective = hit_rate × cache_latency + (1 − hit_rate) × source_latency + cache_overhead
```

At a 50% hit rate you have added a network hop to half your requests for a halved cost on the other
half — often not worth the complexity. **Below roughly 80%, question whether the cache earns its
place.**

## Where caches live

```
Browser cache            (Day 102's Cache-Control)
   ▼
CDN / edge               static assets, and cacheable API responses
   ▼
Reverse proxy            nginx, Varnish
   ▼
Application in-process   Caffeine — nanoseconds, but per-instance
   ▼
Distributed cache        Redis, Memcached — shared, sub-millisecond
   ▼
Database buffer pool     (Day 078's D-01)
   ▼
Disk
```

**The cheapest cache is the one closest to the client.** An HTTP response cached at the CDN never
reaches your servers at all — which is why Day 102's caching headers are a performance tool, not
just a correctness detail.

**In-process vs distributed** is a real trade-off: Caffeine is ~100× faster than Redis but is
per-instance, so ten instances hold ten copies with ten different staleness states. Use in-process
for small, rarely-changing, tolerant-of-staleness data (configuration, feature flags, reference
data); Redis for anything that must be consistent across instances.

# Part 2 — The four patterns

## 1. Cache-aside (lazy loading) — the default

```java
public Order getOrder(String id) {
    Order cached = cache.get(key(id));
    if (cached != null) return cached;                  // HIT

    Order order = repository.findById(id).orElseThrow(); // MISS
    cache.set(key(id), order, Duration.ofMinutes(5));
    return order;
}
```

**The application owns the cache.** Simple, resilient (a cache failure degrades to slow, not
broken), and only requested data is cached.

Its costs: **the first request always misses**, there is a brief window of staleness after a write,
and the read-modify-write between get and set is racy — two concurrent misses both query the source.

> **Cache-aside is the right default.** Reach for the others when you have a specific reason.

## 2. Read-through

```java
// the CACHE loads on miss — the application only ever talks to the cache
Cache<String, Order> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(5))
    .build(id -> repository.findById(id).orElseThrow());   // ← the loader

Order order = cache.get(id);
```

Cleaner application code, and the loader is a single place to handle misses. Caffeine additionally
**deduplicates concurrent loads for the same key** — which solves cache-aside's racy-miss problem and
is a genuine reason to prefer it in-process.

The trade-off: the application now depends on the cache being available.

## 3. Write-through

```java
public void save(Order order) {
    repository.save(order);                      // write the source of truth FIRST
    cache.set(key(order.id()), order);           // then the cache
}
```

The cache is never stale. The costs are extra write latency and caching data that may never be read.

**Order matters:** source first, then cache. Reversed, a source failure leaves the cache holding data
that was never persisted — and that lie can survive for the whole TTL.

## 4. Write-behind (write-back)

```java
public void save(Order order) {
    cache.set(key(order.id()), order);
    writeQueue.offer(order);                     // persisted ASYNCHRONOUSLY
}
```

Very fast writes, and batching absorbs bursts. ⚠️ **A crash loses unpersisted writes**, so it is
correct only where loss is acceptable — view counters, analytics events, last-seen timestamps — and
wrong for anything transactional.

## Also worth naming

**Refresh-ahead** — proactively refresh entries before they expire, so popular keys never miss.
**Write-around** — write to the source only, and let reads populate the cache. Good for
write-heavy data that is rarely read back.

# Part 3 — The failure modes

## What to cache, and what not to

| ✅ Cache | ❌ Do not cache |
|---|---|
| Read-heavy, rarely changing (reference data, config) | Data that must be perfectly current (balances) |
| Expensive to compute (aggregates, reports) | Data written more often than read |
| Shared across many users | Per-user data with a low hit rate |
| Tolerant of brief staleness | Anything where staleness is a correctness bug |
| Small enough to fit | Very large objects that evict everything else |

## Negative caching

```java
// Without it, repeated requests for a non-existent id hit the database every time
Optional<Order> result = repository.findById(id);
cache.set(key(id), result.orElse(NULL_SENTINEL), result.isPresent() ? TTL : SHORT_TTL);
```

**Cache the absence too**, with a shorter TTL. Otherwise an attacker (or a buggy client) requesting
random ids bypasses the cache entirely — **cache penetration**, and it is a denial-of-service vector.
A Bloom filter in front is the scaled-up version.

## ⚠️ Multi-tenant cache keys

```java
cache.get("order:" + id);                          // 💀 CROSS-TENANT LEAK (Day 118)
cache.get("order:" + tenantId + ":" + id);         // ✅
```

**A cache key missing the tenant is a data breach that no `WHERE` clause can prevent** — the query
was correct; the cache returned another tenant's object before the query ran. Include every dimension
that affects the result: tenant, user (for personalised data), locale, and API version.

## Cache stampede

Day 121 covers it in full. The shape: a popular key expires, a thousand concurrent requests all miss,
and all thousand hit the database at once — often taking it down at the exact moment traffic is
highest.

## Consistency

**Cache invalidation is genuinely hard**, and the honest framing is that you are choosing how much
staleness to accept:

```
TTL only                  simple; stale for up to the TTL
Invalidate on write       fresher; a distributed-systems problem when writes come from many places
Write-through             never stale; slower writes, and it caches unread data
Versioned keys            "order:42:v7" — no invalidation needed, old entries just age out
```

**Versioned keys are under-used and elegant:** bump a version number on write and every stale key
becomes unreachable, expiring on its own. No invalidation message, no race, no distributed
coordination.

**The invalidation race is worth understanding**, because it is the source of the most confusing
cache bugs:

```
T1: read  → miss → query returns v1
T2: write → updates to v2, invalidates the cache (which is empty)
T1: sets the cache to v1                            ← STALE FOREVER, until the TTL
```

Mitigations: always set a TTL as a backstop, use versioned keys, or use Redis `SET … XX`/`NX`
semantics with a version check.

# Part 4 — D-14 · Isolation levels

## The anomalies

Concurrency permits specific interleavings. Each isolation level forbids more of them.

**Dirty read** — reading uncommitted data:

```
T1: UPDATE account SET balance = 500 WHERE id = 1;      (not committed)
T2: SELECT balance FROM account WHERE id = 1;   → 500   ← reads uncommitted
T1: ROLLBACK;                                            ← 500 never existed
```

**Non-repeatable read** — the same row, read twice, differs:

```
T1: SELECT balance FROM account WHERE id = 1;   → 1000
T2: UPDATE account SET balance = 500 WHERE id = 1; COMMIT;
T1: SELECT balance FROM account WHERE id = 1;   → 500     ← changed mid-transaction
```

**Phantom read** — the same *query* returns different rows:

```
T1: SELECT COUNT(*) FROM orders WHERE total > 1000;   → 5
T2: INSERT INTO orders (total) VALUES (2000); COMMIT;
T1: SELECT COUNT(*) FROM orders WHERE total > 1000;   → 6   ← a new row appeared
```

**Lost update** — two read-modify-write cycles interleave:

```
T1: SELECT stock → 10
T2: SELECT stock → 10
T1: UPDATE stock = 9;  COMMIT;
T2: UPDATE stock = 9;  COMMIT;      ← two sales, one decrement (Day 065's counter, in SQL)
```

**⭐ Write skew** — the one people have never heard of, and the reason `SERIALIZABLE` exists:

```
Rule: at least one doctor must remain on call.
Currently: Alice and Bob are both on call.

T1 (Alice): SELECT COUNT(*) FROM doctors WHERE on_call = true;  → 2, so it is safe to leave
T2 (Bob):   SELECT COUNT(*) FROM doctors WHERE on_call = true;  → 2, so it is safe to leave
T1: UPDATE doctors SET on_call = false WHERE name = 'Alice'; COMMIT;
T2: UPDATE doctors SET on_call = false WHERE name = 'Bob';   COMMIT;

⇒ NOBODY is on call. Each transaction was individually valid. They wrote DIFFERENT rows,
  so no write conflict was detected — but they read overlapping data and invalidated
  each other's premise.
```

**Write skew is not prevented by `REPEATABLE READ`** in most implementations, because there is no
write-write conflict to detect. This is the canonical example and worth memorising — it is the
clearest demonstration of what serializability actually buys.

## The levels

| Level | Dirty read | Non-repeatable | Phantom | Write skew |
|---|---|---|---|---|
| `READ UNCOMMITTED` | ✅ possible | ✅ | ✅ | ✅ |
| **`READ COMMITTED`** | ❌ | ✅ | ✅ | ✅ |
| `REPEATABLE READ` | ❌ | ❌ | ⚠️ varies | ✅ |
| **`SERIALIZABLE`** | ❌ | ❌ | ❌ | ❌ |

**Know your database's default and its actual behaviour**, because they differ:

| Database | Default | Notes |
|---|---|---|
| **PostgreSQL** | `READ COMMITTED` | `READ UNCOMMITTED` behaves as `READ COMMITTED`; `SERIALIZABLE` uses **SSI** |
| **MySQL/InnoDB** | `REPEATABLE READ` | Prevents phantoms via **next-key locks** — stronger than the standard requires |
| **Oracle** | `READ COMMITTED` | No `REPEATABLE READ`; `SERIALIZABLE` is snapshot isolation |
| **SQL Server** | `READ COMMITTED` | Locking by default; optionally MVCC-based |

Two facts that surprise people: **MySQL's default is one level stronger than PostgreSQL's**, and
**PostgreSQL's `REPEATABLE READ` is snapshot isolation** — it prevents phantoms for reads but still
permits write skew.

## What `SERIALIZABLE` costs

PostgreSQL implements it with **Serializable Snapshot Isolation (SSI)** — optimistic. It does not
block; it *detects* dangerous read-write dependency patterns and aborts one transaction:

```
ERROR: could not serialize access due to read/write dependencies among transactions
```

> **⭐ At `SERIALIZABLE`, your application MUST retry on serialization failures.** They are not bugs;
> they are the mechanism. Code that does not retry will surface them to users as errors under load.

```java
for (int attempt = 1; attempt <= 3; attempt++) {
    try { return doTransaction(); }
    catch (SQLException e) {
        if (!"40001".equals(e.getSQLState()) || attempt == 3) throw e;   // serialization_failure
        Thread.sleep(jitteredBackoff(attempt));                          // Day 062
    }
}
```

That retry loop is Day 062's retry pattern reappearing, and it is mandatory rather than optional
here.

## The practical answer

**Most applications should stay on `READ COMMITTED` and handle the specific races explicitly** —
which is cheaper than `SERIALIZABLE` across the board:

```sql
-- Pessimistic: lock the rows you read and intend to update
SELECT * FROM account WHERE id = 1 FOR UPDATE;      -- blocks other writers
SELECT * FROM orders WHERE … FOR UPDATE SKIP LOCKED; -- ⭐ queue workers, Day 125

-- Optimistic: a version column (Day 102's If-Match, in the database)
UPDATE account SET balance = 500, version = version + 1
WHERE id = 1 AND version = 7;
-- 0 rows updated ⇒ someone else won ⇒ reload and retry
```

**Atomic operations avoid the problem entirely** — this is the best answer where it applies:

```sql
UPDATE inventory SET stock = stock - 1 WHERE id = 1 AND stock > 0;
-- no read-modify-write, so no lost update, at ANY isolation level
```

> **Prefer an atomic statement to a transaction with a lock, and a lock to a higher isolation
> level.** Each step up costs concurrency.

`FOR UPDATE SKIP LOCKED` is the one to remember for Day 125: it is how you build a job queue in SQL —
each worker locks and claims different rows without blocking on each other.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Caching without measuring the hit rate | Complexity, latency added, no benefit |
| Cache keys missing the tenant or user | **Cross-tenant or cross-user data leak** |
| No negative caching | Cache penetration — a DoS with random ids |
| No TTL as a backstop | An invalidation race leaves data stale forever |
| Writing the cache before the source | The cache holds data that was never persisted |
| Write-behind for transactional data | Data loss on crash |
| In-process cache for data needing consistency | N instances, N staleness states |
| Not knowing your isolation level | Races you cannot reason about |
| Assuming `REPEATABLE READ` prevents write skew | It does not — that is what `SERIALIZABLE` is for |
| `SERIALIZABLE` with no retry logic | Serialization errors surface to users |
| Read-modify-write instead of an atomic update | Lost updates |
| `SELECT` then `UPDATE` with no `FOR UPDATE` | Lost update at `READ COMMITTED` |

## Interview questions

**Q: Which caching pattern would you use and why?**
Cache-aside as the default — simple, and a cache failure degrades to slow rather than broken.
Read-through when you want the loader centralised and concurrent-miss deduplication. Write-through
when staleness is unacceptable. Write-behind only where losing recent writes is acceptable.

**Q: How do you decide whether to add a cache?**
Compute the effective latency from the expected hit rate. Below about 80% you have added a hop to
most requests for a modest saving on the rest, and the staleness and invalidation complexity is
usually not worth it.

**Q: What is the most dangerous caching bug?**
A cache key missing a dimension that affects the result — tenant, user or locale. It returns another
party's data before any query runs, so no database-level control can prevent it.

**Q: What is write skew?**
Two transactions read overlapping data, each verifies a constraint, and each writes a *different* row
— so no write conflict is detected, but together they violate the invariant. The on-call doctors
example: both see two doctors on call, both leave, nobody is on call. Only `SERIALIZABLE` prevents
it.

**Q: What is the default isolation level, and what does it allow?**
PostgreSQL and Oracle default to `READ COMMITTED`, MySQL to `REPEATABLE READ`. `READ COMMITTED`
prevents dirty reads but permits non-repeatable reads, phantoms, lost updates and write skew.

**Q: What must you do when using `SERIALIZABLE` in PostgreSQL?**
Retry on serialization failures (SQLSTATE 40001). SSI is optimistic — it detects dangerous
dependency patterns and aborts a transaction, so retry logic is part of the contract rather than
error handling.

**Q: How do you prevent a lost update without raising the isolation level?**
An atomic statement (`SET stock = stock - 1 WHERE stock > 0`) where possible; otherwise pessimistic
locking with `SELECT … FOR UPDATE`, or an optimistic version column where a zero-row update signals a
conflict.

## 🎙️ Articulation drill

Three minutes: **"How would you add caching to a slow endpoint, and what could go wrong?"**

dimension that affects the result; negative caching; and the failure modes — staleness, the

your level, name what it permits, and prefer atomic statements to locks and locks to higher isolation.
