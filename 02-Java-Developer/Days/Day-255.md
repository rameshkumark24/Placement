# Day 255 🏗️

**P-255** · Persistence — repositories, projections, and proving the query count

**Time:** 3 hrs · **Mode:** BUILD

> Day 250 designed the schema and the indexes. Day 254 built the domain. **Today connects them** —
> and the discipline that makes this day different from a tutorial is that **every read path is
> written with its query count asserted from the first commit.**
>
> Day 160's lesson was that N+1 is invisible on small data and appears gradually in production.
> **The only durable defence is a test, and it costs nothing to add now.**

---

# Part 1 — ⭐ Repositories, curated

```
⭐ interface BookingRepository extends Repository<Booking, Long>   ← NOT JpaRepository
```

**⭐ Day 163's argument: `JpaRepository` publishes `findAll()` and `deleteAll()` on your domain API.**
Every caller in the codebase can then load or delete the entire table, and neither is something you
intended to offer.

**⭐ Declare exactly what the domain needs, and make the shapes safe:**

| Rule | Why |
|---|---|
| ⭐ **Every collection method takes a `Pageable`** | ⭐ nothing can return an unbounded result |
| ⭐ **`Optional<T>` for "may not exist"** | never `null` |
| ⭐ **Reads return projections, not entities** | Day 147, Day 161 |
| ⭐ **Derived names up to ~3 conditions**, then `@Query` | Day 163's readability limit |
| ⭐ **`:named` parameters, never `?1`** | reordering the signature breaks positional silently |
| ⭐ **A `JdbcClient` fragment** for reports | Day 156 — do not fight JPA |

**⭐ And the security shape from Day 174:**

```
⭐ Every by-id method takes the owner/tenant too:
   findByPublicIdAndOwnerId(...)  →  the WHERE clause makes IDOR impossible
```

**⭐ That is the strongest form of the defence** — not a guard you can forget, but a query that
returns nothing. Combine with `/me/` from Day 251 and the identifier never comes from the request at
all.

# Part 2 — ⭐ Fetching, decided per query

**Day 160's rule: `LAZY` everywhere, then fetch explicitly.**

```
⭐ Every @ManyToOne and @OneToOne:  fetch = LAZY     ← JPA's default is EAGER
⭐ default_batch_fetch_size: 25 set globally          ← Day 253's floor
```

**⭐ Then choose per read path** (Day 161's decision table):

| Read path | ⭐ Technique |
|---|---|
| ⭐ A list endpoint shipping DTOs | ⭐ **constructor projection** — no entity, N+1 impossible |
| A detail endpoint that will be modified | `@EntityGraph` |
| A detail endpoint, read-only | ⭐ projection |
| More than one collection needed | ⭐ **two queries, or `@BatchSize`** — never two fetch joins |
| Paginated + a collection | ⭐ **`@BatchSize`** — never `join fetch` |
| A report or aggregation | ⭐ `JdbcClient` |

**⭐ The projection-for-reads rule is the one that pays repeatedly**, because it makes the N+1
structurally impossible rather than defended against: there is no lazy reference to trigger.

**⭐ And `@Transactional(readOnly = true)` on every read path** (Day 162): it skips dirty checking,
and — more importantly here — **it means an accidental mutation inside a read is silently discarded
rather than persisted.**

# Part 3 — ⭐⭐ Assert the query count. Today, on every read path.

```
⭐ SQLStatementCountValidator.reset();
⭐ service.listBookings(userId, page);
⭐ SQLStatementCountValidator.assertSelectCount(1);
```

**⭐ This is the single most valuable habit in the persistence layer**, and Day 160 explained why:
every other defence — review, vigilance, documentation — decays. **A test fails the build the day
someone adds a `getRoom()` inside a loop, which is exactly when it is cheap to fix.**

**⭐ Do it for every list endpoint and every detail endpoint, as you write them.** Retrofitting means
finding the N+1s first, which is the expensive order.

**⭐ Then verify the fetch decisions are actually working:**

```
⭐ Turn on datasource-proxy (Day 157) in the dev profile — it logs the per-transaction query count
⭐ Confirm an index-only scan where you designed one (Day 189): Heap Fetches: 0
⭐ EXPLAIN ANALYZE your three heaviest queries against realistic data (Day 191)
```

## ⭐ Seed realistic data now

> **⭐ A dataset of 20 rows proves nothing.** Every plan is a sequential scan, every N+1 is fast, and
> every index appears unused (Day 189).

```
⭐ A seed script producing production-shaped volume: 100k+ rows in the main tables,
   with realistic skew — a few users with thousands of bookings, most with three.
```

**⭐ The skew matters as much as the volume.** Uniform test data hides the hot-partition and hot-key
problems (Day 206) and makes every query look equally fast.

**⭐ Then run the Day 193 workflow against your own project**: `pg_stat_statements` ordered by total
time, the top five, `EXPLAIN (ANALYZE, BUFFERS)` on each. **You will find something. That finding is
an interview story.**

# Part 4 — ⭐ Concurrency, wired in

**⭐ Your hard problem gets implemented today, and proven today.**

```
⭐ @Version on entities that two users can edit concurrently          (Day 165)
⭐ The exclusion constraint / atomic UPDATE / FOR UPDATE for the hard problem (Day 187/165)
⭐ The full chain: entity version → ETag → If-Match → 409             (Day 165, Day 251)
```

**⭐ And the proof, written as a test:**

```
⭐ Two threads, same resource, same instant, 100 iterations.
⭐ Assert exactly one succeeds and the other receives the documented error.
```

**⭐ This test is the centrepiece of your project's defence.** Day 249's `HARD-PROBLEM.md` promised
it; today it exists and passes. **It is also the answer to "what was the hardest part?"** — you can
describe the race, show the test that reproduces it, and show the constraint that makes it
impossible.

⚠️ **⭐ It must run against real PostgreSQL** (Day 184). An exclusion constraint, `SKIP LOCKED` and
serialisation errors do not exist in H2 — **so on H2 this test would pass while proving nothing.**

## ⭐ The transaction rules, applied

| Rule | Day |
|---|---|
| ⭐ **Boundary in the service, never the repository or controller** | 164 |
| ⭐ **No HTTP calls, no message publishing inside a transaction** | 156, 124 |
| `rollbackFor = Exception.class` | ⭐ 164 — the checked-exception footgun |
| `readOnly = true` on reads | 162 |
| ⭐ **Short** | 156, 194 — long transactions block vacuum globally |

**⭐ The second rule will bite you on Day 258 or 263** when something needs to call out or publish.
**The answer is already decided: two short transactions with the slow work between them, and the
outbox to close the gap** (Day 124).

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Extending `JpaRepository` | `findAll()` and `deleteAll()` on the domain API |
| ⭐ Unbounded `List<T>` returns | one caller from loading the table |
| By-id methods without the owner in the `WHERE` | IDOR waiting for a forgotten guard |
| ⭐ Leaving `@ManyToOne` eager | Day 160 — transitive, unoverridable |
| Returning entities from services | lazy loads outside the transaction (Day 147) |
| ⭐ **No query-count tests** | ⭐ the N+1 arrives gradually and invisibly |
| ⭐ Testing on 20 rows | every plan is a seq scan; nothing is proven |
| Uniform test data | hides skew, hot keys, hot partitions |
| ⭐ H2 for the concurrency test | ⭐ **it passes while proving nothing** |
| `join fetch` with `Pageable` | in-memory pagination over the whole table (Day 152) |
| Two collection fetch joins | cartesian product |
| ⭐ Transactions in repositories | no atomicity across calls |
| Network calls inside transactions | connection held; dual-write (Day 156, 124) |

## 🎤 Defence questions

1. **⭐ How do you know you have no N+1?** (⭐ the only good answer is "a test asserts the query count")
2. **⭐ Show me a read path and explain why it is a projection rather than an entity.**
3. **⭐ Walk me through what happens when two users book the same slot simultaneously.**
4. **⭐ Why is that enforced by the database rather than the service?**
5. **How does a client avoid overwriting another client's change?**
6. **⭐ Why did you seed 100,000 rows rather than 20?**
7. **⭐ What did `EXPLAIN ANALYZE` tell you that you did not expect?**
8. **Where are your transaction boundaries, and what is not allowed inside one?**

## ✅ Done when

- Every read path has a query-count test
- ⭐ **The concurrency test passes against real PostgreSQL**
- Realistic data is seeded and the heaviest queries have been explained
- The ETag/If-Match chain works end to end
