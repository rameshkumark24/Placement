# Day 361 ⭐

**L-361** · ⭐ Container internals — namespaces, cgroups, and the JVM that gets killed

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Docker is three Linux kernel features and a filesystem trick. Once you can name them, every
> confusing container behaviour becomes predictable.**
>
> And one of them causes the single most common Java-in-containers production failure: **a JVM that
> sizes its heap for the host machine and gets OOM-killed inside a 512 MB limit.**

---

# Part 1 — ⭐⭐ The three mechanisms

| Mechanism | ⭐ Controls | ⭐ In one word |
|---|---|---|
| ⭐ **Namespaces** | ⭐ what the process can **SEE** | ⭐ **visibility** |
| ⭐ **cgroups** | ⭐ what it can **USE** | ⭐ **quota** |
| ⭐ **Capabilities / seccomp / LSM** | ⭐ what it can **DO** | ⭐ **permission** |
| ⭐ **Union filesystem** | ⭐ what its **ROOT** looks like | ⭐ **layers** |

## ⭐ Namespaces — visibility

| Namespace | ⭐ Isolates | ⭐ Consequence |
|---|---|---|
| ⭐ **pid** | the process tree | ⭐⭐ **your app is PID 1 inside — see Part 3** |
| ⭐ **net** | interfaces, ports, routes | ⭐⭐ **`localhost` inside is the container, not the host** |
| ⭐ **mnt** | mount points | its own filesystem view |
| **uts** | hostname | `hostname` differs |
| **ipc** | shared memory, semaphores | |
| ⭐ **user** | uid/gid mapping | ⭐ **root inside can map to an unprivileged host user — the key hardening feature** |
| cgroup | the cgroup hierarchy view | |

```bash
⭐ # Prove it with no Docker at all:
sudo unshare --pid --fork --mount-proc bash
ps aux          # ⭐ you are PID 1, and the host's processes are invisible
```

> **⭐ That command is the whole demo.** A container is this, plus a root filesystem, plus limits —
> **and running it once removes the mystery permanently.**

## ⭐ cgroups — quota

| Controller | ⭐ Limits |
|---|---|
| ⭐ **memory** | ⭐⭐ RSS. **Exceed it and the kernel OOM-kills the process — no swap, no warning** |
| ⭐ **cpu** | ⭐ shares (relative weight) and **quota** (a hard ceiling per period) |
| io | block device bandwidth |
| pids | ⭐ maximum process count — **a fork-bomb defence** |

⚠️ **CPU limits are enforced by throttling, not slowing.** With a quota of 0.5 CPU, your process runs
at full speed for half of each 100 ms period and is **frozen for the rest** — which shows up as
latency spikes rather than uniform slowness. **A container throttled at the wrong moment looks like a
GC pause**, and `cpu.stat`'s `nr_throttled` is how you tell them apart.

## ⭐ Union filesystems — layers

```
⭐ overlayfs:
⭐   lowerdir  = the image layers (⭐ read-only, shared between containers)
⭐   upperdir  = the container's writable layer
⭐   merged    = what the process sees
⭐
⭐ ⭐⭐ COPY-ON-WRITE: modifying a file in a lower layer COPIES THE WHOLE FILE up first.
```

| ⭐ Consequence | |
|---|---|
| ⭐⭐ **The first write to a large file is slow** | ⭐ it is copied entirely, however small the change |
| ⭐ **Layers are shared** | ⭐ 100 containers from one image cost one copy of the read-only layers |
| ⭐⭐ **Deleting a file does not shrink the image** | ⭐⭐ a whiteout marker hides it; **the bytes remain in the lower layer** (Day 362) |
| ⭐ Write-heavy workloads want a volume | ⭐ **databases must never write to the container filesystem** |

# Part 2 — ⭐⭐ The JVM in a container

```
⭐ THE CLASSIC FAILURE (pre-JDK 10, and still hit via bad flags):
⭐   Host: 64 GB RAM, 32 cores.  Container limit: 512 MB, 0.5 CPU.
⭐   ⭐ JVM reads /proc/meminfo → sees 64 GB → ⭐⭐ default max heap = 16 GB
⭐   ⭐ JVM reads cpu count     → sees 32    → ⭐ sizes GC threads and the common ForkJoinPool for 32
⭐   ⇒ ⭐⭐ the heap grows past 512 MB ⇒ ⭐⭐ OOMKilled. ⭐ Exit 137. No Java stack trace at all.
```

| ⭐ Fix | ⭐ Detail |
|---|---|
| ⭐ `-XX:+UseContainerSupport` | ⭐ **on by default since JDK 10** — reads cgroup limits |
| ⭐⭐ **`-XX:MaxRAMPercentage=75`** | ⭐⭐ **the correct modern flag — a percentage of the LIMIT, not a fixed `-Xmx`** |
| ⭐ `-XX:InitialRAMPercentage` | avoid a slow ramp-up |
| ⭐ **Leave headroom** | ⭐⭐ heap is not the whole footprint — **metaspace, thread stacks, code cache, direct buffers and native memory live outside it** |
| ⭐ `-XX:ActiveProcessorCount` | ⭐ when CPU quota detection is wrong for your GC/pool sizing |

> **⭐ The insight to state: `MaxRAMPercentage` exists because a fixed `-Xmx` is wrong the moment the
> limit changes.** A percentage survives resizing the container; a hard number does not — **and
> someone changing the memory limit without changing `-Xmx` is a very common incident.**

⚠️ **Exit code 137 means SIGKILL (128 + 9) — almost always the OOM killer.** **Exit 143 is SIGTERM
(128 + 15) — a normal shutdown.** Knowing those two numbers saves an hour of confusion every time.

⚠️ **And "the JVM used more than my heap size" is not a bug.** Total RSS ≈ heap + metaspace + thread
stacks + code cache + direct buffers + GC structures. **Set `MaxRAMPercentage` to about 75% and leave
the rest**; `-XX:NativeMemoryTracking` is how you find out where the remainder went.

# Part 3 — ⭐⭐ PID 1, signals, and why shutdown fails

```dockerfile
⭐ ✗ SHELL FORM — the shell is PID 1, and it does NOT forward signals
CMD java -jar app.jar

⭐ ✓ EXEC FORM — java is PID 1 and receives SIGTERM directly
CMD ["java", "-jar", "app.jar"]
```

| ⭐ Problem with PID 1 | ⭐ Why |
|---|---|
| ⭐⭐ **PID 1 has no default signal handlers** | ⭐⭐ **an unhandled SIGTERM is IGNORED, not fatal** |
| ⭐ **Shell form breaks graceful shutdown** | ⭐ `/bin/sh` gets the signal, the JVM never does → **10-second wait, then SIGKILL** |
| ⭐ PID 1 must reap zombies | ⭐ orphaned children accumulate; use `--init` or `tini` if you spawn processes |
| ⭐ **The consequence** | ⭐⭐ **in-flight requests are killed on every deploy** (Day 286) |

> **⭐ This is the highest-value practical detail in the day.** A team with "graceful shutdown
> enabled" in Spring Boot and a shell-form `CMD` **has no graceful shutdown at all**, and the
> symptom is dropped requests on every deploy with nothing in the logs.

**⭐ The full graceful path, all four pieces required:**

```
⭐ 1. exec form CMD                    ⇒ the JVM is PID 1 and receives SIGTERM
⭐ 2. Spring `server.shutdown=graceful` ⇒ stop accepting, finish in flight (Day 143)
⭐ 3. a pre-stop delay                  ⇒ let the load balancer stop routing first (Day 286)
⭐ 4. terminationGracePeriod > your drain timeout ⇒ ⭐ or the platform SIGKILLs you mid-drain
```

# Part 4 — ⭐ Build one by hand, and the security layer

```bash
⭐ # A container, from primitives — no Docker:
mkdir -p /tmp/rootfs && docker export $(docker create alpine) | tar -x -C /tmp/rootfs
sudo unshare --pid --mount --uts --ipc --fork --mount-proc \
     chroot /tmp/rootfs /bin/sh
⭐ # ⇒ namespaces + a root filesystem. Add cgroup limits and you have reimplemented the core.
```

| ⭐ Security control | ⭐ What it does |
|---|---|
| ⭐ **Capabilities** | ⭐ split root into ~40 pieces — **drop all, add back only what you need** |
| ⭐ **seccomp** | ⭐ filter syscalls; Docker's default profile blocks ~44 dangerous ones |
| ⭐ **User namespaces** | ⭐⭐ **root inside maps to an unprivileged host uid — the strongest single hardening** |
| AppArmor / SELinux | mandatory access control on files and operations |
| ⭐ **Read-only root filesystem** | ⭐ plus a tmpfs for `/tmp` — **removes a whole class of persistence** |

```
⭐ THE PRACTICAL BASELINE, and it is four lines:
⭐   USER 10001                          ⭐ never root
⭐   --read-only --tmpfs /tmp            ⭐ immutable filesystem
⭐   --cap-drop=ALL                      ⭐ then add back nothing, usually
⭐   --security-opt=no-new-privileges    ⭐ setuid binaries cannot escalate
```

⚠️ **`--privileged` disables essentially all of it.** It is occasionally necessary (some CI, some
device access) and **should never appear in an application deployment** — treat seeing it as an
incident to investigate.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Shell-form `CMD` | ⭐⭐ **SIGTERM never reaches the JVM — no graceful shutdown** |
| ⭐ No `--init` when spawning children | zombie processes accumulate |
| ⭐⭐ **No JVM container flags** | ⭐⭐ **heap sized for the host → exit 137** |
| ⭐ A fixed `-Xmx` instead of a percentage | wrong the moment the limit changes |
| ⭐ Treating heap as total memory | ⭐ metaspace, stacks, code cache and direct buffers are extra |
| ⭐ **Not knowing 137 vs 143** | an hour lost on every incident |
| Blaming GC for CPU-throttling latency | ⭐ check `nr_throttled` |
| ⭐ Writing heavy data to the container filesystem | ⭐ copy-on-write cost; lost on restart |
| Running as root | needless privilege |
| ⭐ **`--privileged`** | ⭐⭐ all isolation disabled |
| Assuming `localhost` reaches the host | net namespace |
| Grace period shorter than the drain timeout | SIGKILL mid-drain |

## Interview questions

**Q: What makes a container a container?**
Three kernel features and a filesystem. Namespaces restrict what the process can see — its own
process tree, network stack, mounts, hostname and user mapping. cgroups restrict what it can use —
memory, CPU, I/O, process count. Capabilities and seccomp restrict what it can do. And overlayfs gives
it a root filesystem assembled from read-only layers plus a writable top layer. You can reproduce the
core with `unshare` and `chroot` in two commands.

**Q: Your Java service is killed in Kubernetes with exit code 137 and no stack trace. Why?**
137 is 128 plus 9 — SIGKILL, which means the kernel OOM killer, not the JVM. Almost always the JVM
sized its heap for the host rather than the cgroup limit, so it grew past the container's memory
cap. The fix is container support enabled plus `MaxRAMPercentage` around 75 rather than a fixed
`-Xmx`, because a percentage survives someone changing the limit and a fixed number does not. And
heap is not the whole footprint — metaspace, thread stacks, code cache and direct buffers are all
outside it, which is why you leave a quarter free.

**Q: Graceful shutdown is configured but requests are still dropped on deploy. What is wrong?**
Almost certainly a shell-form `CMD`, so `/bin/sh` is PID 1 and the JVM never receives SIGTERM. PID 1
also has no default signal handlers, so an unhandled signal is ignored rather than fatal — the
platform waits its grace period and then SIGKILLs. Fix the exec form, then check that the
termination grace period exceeds the application's drain timeout and that there is a pre-stop delay
so the load balancer stops routing first.

**Q: What does copy-on-write mean for you in practice?**
Modifying a file that lives in a read-only image layer copies the entire file into the writable layer
first, so the first write to a large file is disproportionately slow. It also means deleting a file
never shrinks an image — a whiteout marker hides it while the bytes remain below, which is why
secrets baked into an early layer stay retrievable. And it is why databases must use a volume rather
than the container filesystem.

**Q: How would you harden a container?**
Run as a non-root user, mount the root filesystem read-only with a tmpfs for scratch space, drop all
capabilities and add back only what is genuinely needed, enable no-new-privileges, and keep the
default seccomp profile. User namespaces are the strongest single addition, mapping root inside to an
unprivileged host uid. And `--privileged` should never appear in an application deployment.

## 🎙️ Articulation drill

**Three minutes:** *"Our Java service keeps restarting in production with exit 137."*

**⭐ The full diagnosis: 137 is SIGKILL, so the kernel killed it, so it exceeded its memory cgroup —
not a JVM `OutOfMemoryError`, which would have produced a stack trace.** Then the cause: the heap was
sized from host memory rather than the limit, **or the heap fits but the non-heap footprint pushed
total RSS over.**

**⭐ The marker is distinguishing an OOMKill from an `OutOfMemoryError` in the first fifteen
seconds.** They are entirely different failures with entirely different fixes, and **conflating them
is how teams spend a day tuning GC for a problem that was a missing flag.**
