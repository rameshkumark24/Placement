# Day 336

**L-336** · Distributed rate limiting and backpressure — the half nobody prepares

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Rate limiting protects you from other people. Backpressure protects you from yourself — and it
> is the one candidates cannot discuss.**
>
> Day 314 built a limiter in one process. Today: making it work across a fleet, and then the more
> important question — **what a system should do when it is asked to accept more work than it can
> possibly complete.**

---

# Part 1 — ⭐ Distributed rate limiting

**⭐ Three instances each allowing 100/min allows 300/min. Four ways to fix it, and the honest
ranking:**

| Approach | ⭐ Accuracy | ⭐ Cost |
|---|---|---|
| ⭐ **Divide the limit by N** | ⭐ poor — **breaks under uneven balancing and on every scale event** | free |
| ⭐⭐ **Central store, atomic script** (Day 208) | ⭐⭐ **exact** | ⭐ a network hop on every request |
| ⭐⭐ **Local buckets + async reconciliation** | ⭐ approximate, converges | ⭐⭐ **near-zero latency — the usual production answer** |
| Sticky routing by key | exact if routing holds | fragile; rebalancing breaks it |

```lua
-- ⭐ The central version: read, refill, decide, write — one round trip, atomic (Day 208)
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens')) or capacity
-- ⭐ refill lazily from elapsed time, then:
if tokens < 1 then return 0 end
redis.call('HSET', KEYS[1], 'tokens', tokens - 1, 'ts', now)
return 1
```

> **⭐ The pragmatic design worth describing: each instance holds a local bucket sized to its fair
> share plus a margin, and asynchronously reports usage to a central counter that redistributes
> allowance.** Enforcement is approximate for a second or two and costs no request latency —
> **and rate limits are a policy, not an invariant, so approximate is the correct trade.**

⚠️ **State the failure mode, per Day 314: if the central store is unreachable, do you fail open or
closed?** Open for general API throttling; **closed for login attempts, payments, and anything where
excess is a security or money problem.** It must be configurable per rule.

## ⭐ Layering — where limits actually go

```
⭐ CDN / WAF        ── volumetric attacks, per-IP floods       ⭐ cheapest place to reject
⭐ API gateway      ── per-API-key, per-plan quotas            ⭐ before your code runs
⭐ Service          ── per-user, per-endpoint business limits
⭐ ⭐ Downstream     ── ⭐⭐ YOUR OWN calls out — the one people forget
```

> **⭐ That last row is the interesting one: you must rate-limit yourself against your dependencies.**
> A batch job that hammers a third-party API, or a retry storm against your own database, is the
> same problem viewed from the other end — **and it is the one that causes your incidents rather
> than someone else's.**

# Part 2 — ⭐⭐ Backpressure — the actual topic

> **⭐ Backpressure is telling the producer to slow down, instead of accepting work you cannot
> finish.** Without it, a queue absorbs the excess — **and a queue that absorbs excess is a system
> that has converted a throughput problem into a memory problem, then into an outage.**

## ⭐⭐ Why an unbounded queue is not resilience

```
⭐ Arrival 1,000/s. Capacity 800/s. Unbounded queue.
⭐   after 1 minute:  ⭐ 12,000 queued → ⭐ 15 seconds of latency
⭐   after 10 minutes:⭐ 120,000 queued → ⭐ 2.5 MINUTES of latency
⭐   ⇒ ⭐⭐ every client has already timed out. You are doing work NOBODY IS WAITING FOR.
⭐   ⇒ ⭐⭐ then memory grows, GC thrashes, and the process dies with a full queue.
```

| ⭐ Truth | |
|---|---|
| ⭐⭐ **A queue converts an overload into latency, and latency into wasted work** | ⭐⭐ **it does not create capacity** |
| ⭐ **Work completed after the client gave up is pure waste** | ⭐ and it is consuming the capacity of live requests |
| ⭐ **Bound every queue** | ⭐ **a full bounded queue is a signal; an unbounded one is a lie** |

> **⭐ The sentence to have ready: "an unbounded queue doesn't absorb load, it hides it — until the
> latency has already made every response useless and the process runs out of memory."**

## ⭐⭐ Load shedding — the counterintuitive right answer

> **⭐ It is better to serve 70% of requests well than 100% of them badly.** At overload, rejecting
> excess **immediately** keeps the system inside its latency SLO for everyone it does serve.

| ⭐ Principle | ⭐ Detail |
|---|---|
| ⭐ **Reject fast, and cheaply** | ⭐ a 429/503 in 1 ms costs nothing; a timeout at 30 s costs a thread |
| ⭐⭐ **Shed by priority** | ⭐⭐ **drop analytics and prefetches before checkout** — this requires request classification |
| ⭐ Shed at the edge | the earlier you reject, the less capacity you burn |
| ⭐ **Include `Retry-After`** | ⭐ otherwise clients retry immediately and amplify (Day 325) |
| ⭐ Measure shed rate | ⭐ **it is a first-class SLI, not an error** |

⚠️ **Shedding without classification sheds randomly**, which means checkout requests are dropped at
the same rate as background polling. **Request priority must be an explicit attribute** — a header,
a route class, or a caller identity — **decided before you need it.**

# Part 3 — ⭐⭐ Deadline propagation — the elegant mechanism

```
⭐ Client sets a 2s deadline.
⭐   Gateway   receives deadline=2000ms  → ⭐ passes remaining 1950ms downstream
⭐   Service A receives deadline=1950ms  → ⭐ passes remaining 1700ms
⭐   Service B receives deadline=1700ms  → ⭐ its database call gets 1650ms
⭐
⭐ ⭐⭐ At ANY hop, if the remaining budget is already exhausted: FAIL IMMEDIATELY,
⭐ ⭐⭐ without doing the work. The client is gone; the work is worthless.
```

| ⭐ Benefit | |
|---|---|
| ⭐⭐ **No work is done for departed clients** | ⭐⭐ **the single biggest capacity saving under overload** |
| ⭐ Timeouts are consistent by construction | Day 154's budget, computed rather than guessed |
| ⭐ A slow dependency cannot consume the whole chain | each hop knows what it may spend |
| ⭐ **Cancellation propagates** | the database query is cancelled too |

> **⭐ This is what gRPC deadlines and `CancellationToken`-style plumbing exist for, and it is the
> single most underrated resilience mechanism.** Fixed per-hop timeouts (Day 154) are a decent
> approximation; **a propagated deadline is the correct version, because it accounts for time
> already spent.**

⚠️ **In Java, `Thread.interrupt` and reactive cancellation only work if the code checks.** A blocking
JDBC call does not abort on interruption unless a statement timeout is set — **so deadline
propagation must reach the actual I/O calls, not just the application layer.**

# Part 4 — ⭐ The mechanisms, and TCP as the model

| Mechanism | ⭐ Where |
|---|---|
| ⭐ **Bounded queues everywhere** | ⭐ thread pools, message buffers, channels |
| ⭐ **Bulkheads / semaphores** | ⭐ cap concurrent calls per dependency (Day 181) — **one slow dependency cannot take all threads** |
| ⭐ Reactive `request(n)` | the consumer pulls; the producer cannot outrun it |
| ⭐ **Consumer-driven polling** | ⭐ a Kafka consumer takes what it can handle — **backpressure by construction** |
| ⭐ Concurrency limits (adaptive) | ⭐ AIMD on observed latency — **finds capacity without configuration** |
| ⭐ **Deadlines** | as above |

> **⭐ TCP is the model to reference: the receiver advertises a window, the sender may not exceed it,
> and the window shrinks when the receiver falls behind.** Backpressure is not an exotic idea —
> **it is how every reliable transport has always worked**, and application systems that lack it are
> the anomaly.

**⭐ The adaptive concurrency-limit idea is worth naming**: instead of configuring a pool size,
measure latency and increase concurrency while latency is flat, decrease it when latency rises — the
same additive-increase/multiplicative-decrease shape as TCP congestion control. **It finds the right
limit under changing conditions, which a static number never does.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Per-instance limits across a fleet | ⭐ the effective limit is N× the configured one |
| ⭐ No fail-open/closed decision | the limiter becomes the outage |
| ⭐ Not limiting your own outbound calls | ⭐ **you DDoS your dependencies** |
| ⭐⭐ **Unbounded queues** | ⭐⭐ **latency debt, wasted work, then memory death** |
| ⭐ Treating a queue as capacity | ⭐ it is a buffer, not a server |
| ⭐ Doing work after the client timed out | ⭐ **capacity spent on nobody** |
| ⭐ Shedding without priority classes | ⭐ checkout dropped as readily as telemetry |
| ⭐ Rejecting with no `Retry-After` | immediate retries amplify the overload |
| Treating shed requests as errors | it is a deliberate SLI, not a bug |
| ⭐ Fixed timeouts instead of deadlines | ⭐ time already spent is not accounted for |
| Deadlines that stop at the app layer | the JDBC call runs on regardless |
| Static pool sizes under variable load | always wrong in one direction |

## Interview questions

**Q: How do you rate-limit across many instances?**
Exactly, with a central store and an atomic script, at the cost of a network hop per request; or
approximately, with local buckets that report usage asynchronously to a central counter that
redistributes allowance. I usually take the second, because a rate limit is a policy rather than an
invariant and being briefly imprecise is cheaper than adding a round trip to every request. Dividing
the limit by instance count is the one I avoid — it breaks under uneven balancing and every scale
event.

**Q: What is backpressure?**
Telling the producer to slow down rather than accepting work you cannot complete. The alternative is
a queue, and a queue does not create capacity — it converts overload into latency, and once latency
exceeds the client timeout you are spending capacity on work nobody is waiting for, before the
process eventually dies of memory exhaustion.

**Q: What is wrong with an unbounded queue?**
It hides the problem instead of absorbing it. At a thousand arrivals a second against eight hundred
of capacity, after ten minutes you have a hundred and twenty thousand queued items and two and a half
minutes of latency, so every client has given up and every completed item is waste. A bounded queue
that fills is a signal you can act on; an unbounded one is a lie that ends in an out-of-memory error.

**Q: Why shed load deliberately?**
Because serving seventy percent of traffic within the SLO is better than serving all of it outside
the SLO, which in practice means serving none of it usefully. Rejecting fast costs a millisecond
where a timeout costs a thread for thirty seconds. The important part is classification — shedding
without priorities drops checkout as readily as background telemetry — and a `Retry-After` header, or
clients retry immediately and amplify the overload.

**Q: What is deadline propagation?**
The client's remaining time budget travels with the request, and each hop passes on what is left. At
any point where the budget is already exhausted, the service fails immediately without doing the
work. It is the single biggest capacity saving under overload, because it stops the system doing work
for clients who have gone, and it makes timeouts consistent by construction rather than guessed
per hop. The caveat in Java is that it has to reach the actual I/O — a JDBC call will not abandon
itself without a statement timeout.

## 🎙️ Articulation drill

**Three minutes:** *"Your service is receiving 3× its capacity. What happens?"*

**⭐ The answer that separates candidates has two halves.** First the diagnosis: without backpressure
the queue grows, latency passes the client timeout, and every completed request is waste before the
process dies of memory exhaustion. **Then the design**: bounded queues, shed by priority with a
`Retry-After`, and propagate deadlines so no hop starts work for a client that has already gone.

**⭐ Close on the counterintuitive line — "I'd rather serve 70% of traffic well than 100% badly" —
because deliberately rejecting work is the part that sounds wrong until you explain it, and it is
exactly what the interviewer is checking for.**
