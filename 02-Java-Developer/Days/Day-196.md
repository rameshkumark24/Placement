# Day 196

**L-196** · Locks and deadlock debugging — finding what is blocking what

**Time:** 3 hrs · **Mode:** NEW

> Day 195 showed that MVCC removes read/write contention but **not write/write contention**. Today is
> that contention: which lock modes conflict, how to find the blocker in thirty seconds during an
> incident, and why the `ALTER TABLE` that "should be instant" took the whole application down.
>
> **The lock queue is the part people do not know**, and it is the cause of the worst outages on this
> page.

# Part 1 — The two families

## Row locks — acquired by writes

| Mode | Taken by | Conflicts with |
|---|---|---|
| `FOR KEY SHARE` | a foreign key check | `FOR UPDATE` |
| `FOR SHARE` | `SELECT FOR SHARE` | `FOR UPDATE`, `FOR NO KEY UPDATE` |
| `FOR NO KEY UPDATE` | ⭐ `UPDATE` of non-key columns | `FOR UPDATE`, `FOR SHARE` |
| ⭐ `FOR UPDATE` | ⭐ `SELECT FOR UPDATE`, `DELETE` | ⭐ everything |

**⭐ Row locks are stored in the tuple itself, not in a lock table**, so PostgreSQL can hold millions
without exhausting memory — unlike some engines with a fixed lock table that escalate to table locks
under pressure. **PostgreSQL never escalates row locks to table locks**, which is a genuine
advantage worth knowing.

## ⭐ Table locks — the ones that cause outages

| Mode | Taken by | Blocks |
|---|---|---|
| `ACCESS SHARE` | ⭐ every `SELECT` | only `ACCESS EXCLUSIVE` |
| `ROW SHARE` | `SELECT FOR UPDATE` | |
| `ROW EXCLUSIVE` | ⭐ `INSERT`, `UPDATE`, `DELETE` | `SHARE` and above |
| `SHARE UPDATE EXCLUSIVE` | ⭐ `VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY` | itself, and above |
| `SHARE` | ⭐ `CREATE INDEX` (non-concurrent) | ⭐ **all writes** |
| `SHARE ROW EXCLUSIVE` | some `ALTER TABLE` | |
| ⭐⭐ `ACCESS EXCLUSIVE` | ⭐ most `ALTER TABLE`, `DROP`, `TRUNCATE`, `VACUUM FULL`, `REINDEX` | ⭐ **EVERYTHING, including SELECT** |

**⭐ `ACCESS EXCLUSIVE` blocks reads.** That is the mode behind Day 166's and Day 194's warnings, and
it is why a "quick schema change" can stop an application dead.

# Part 2 — ⭐⭐ The lock queue, and the outage nobody expects

> **⭐ PostgreSQL's lock queue is FIFO. A waiting lock request blocks every request behind it, even
> ones that would not have conflicted with the current holder.**

**This is the most important paragraph on the page.** Watch it happen:

```
1. A long SELECT is running on `orders`            → holds ACCESS SHARE
2. ALTER TABLE orders ADD COLUMN ... arrives       → ⭐ WAITS for ACCESS EXCLUSIVE
3. ⭐⭐ Every subsequent SELECT queues BEHIND the ALTER — even though SELECTs
   do not conflict with each other
4. ⭐ Within seconds, every connection is waiting. The application is down.
```

**⭐ One slow query plus one instant `ALTER TABLE` equals a total outage.** The `ALTER` itself would
have taken 2 milliseconds.

**⭐ The defence is one line, and every migration should have it:**

```sql
set lock_timeout = '3s';                    -- ⭐⭐ give up rather than queue
alter table orders add column region text;
```

**If the lock cannot be taken in three seconds, the migration fails and you retry later** — instead
of taking the application down while it waits. **Put `lock_timeout` in every migration file**
(Day 166); it is the single most valuable habit in database change management.

For very hot tables, retry in a loop with a short timeout:

```sql
do $$ begin
  for i in 1..50 loop
    begin
      set local lock_timeout = '100ms';
      alter table orders add column region text;
      return;
    exception when lock_not_available then perform pg_sleep(0.5);
    end;
  end loop;
end $$;                                      -- ⭐ nibble at it until a gap appears
```

# Part 3 — ⭐ Finding the blocker in thirty seconds

**⭐ This query is the one to memorise. It answers "what is blocking what?" directly.**

```sql
select blocked.pid            as blocked_pid,
       blocked.usename        as blocked_user,
       blocking.pid           as blocking_pid,
       blocking.usename       as blocking_user,
       blocked.wait_event_type, blocked.wait_event,
       now() - blocked.query_start as blocked_for,
       blocked.query          as blocked_query,
       blocking.query         as blocking_query,
       blocking.state         as blocking_state
from pg_stat_activity blocked
join lateral unnest(pg_blocking_pids(blocked.pid)) as bpid on true      -- ⭐ the key function
join pg_stat_activity blocking on blocking.pid = bpid
where cardinality(pg_blocking_pids(blocked.pid)) > 0
order by blocked_for desc;
```

**⭐ `pg_blocking_pids(pid)` is the function that makes this trivial** and most people do not know it
exists. It returns the process IDs actually blocking a given process — following the chain, not just
the immediate holder.

**⭐ Read `blocking.state` first.** If it says `idle in transaction`, the blocker is not running a
query at all — an application opened a transaction and went away (Day 194's failure 1, Day 156's
forbidden HTTP call). That is a bug in the application, not a slow query.

```sql
select pg_cancel_backend(pid);      -- ⭐ cancel the query, keep the connection. TRY THIS FIRST
select pg_terminate_backend(pid);   -- ⭐ kill the connection — rolls back the transaction
```

**⭐ Always `pg_cancel_backend` first.** It is gentler and usually sufficient. `pg_terminate_backend`
kills the connection, which the application's pool must then handle (Day 156).

## The lock detail view

```sql
select l.pid, l.locktype, l.mode, l.granted, l.relation::regclass as table, a.query
from pg_locks l join pg_stat_activity a on a.pid = l.pid
where not l.granted;                                    -- ⭐ everything currently waiting
```

# Part 4 — ⭐ Deadlocks

```
-- A                                        -- B
begin;                                      begin;
update accounts set balance=900 where id=1; update accounts set balance=900 where id=2;
                                            -- ⭐ each now holds one row
update accounts set balance=900 where id=2; update accounts set balance=900 where id=1;
-- ⭐⭐ A waits for B's row; B waits for A's row. Circular wait.
```

**⭐ PostgreSQL detects it after `deadlock_timeout` (default 1 second) and kills one transaction:**

```
ERROR:  deadlock detected
DETAIL: Process 1234 waits for ShareLock on transaction 5678; blocked by process 5679.
        Process 5679 waits for ShareLock on transaction 5677; blocked by process 1234.
HINT:   See server log for query details.
```

```
log_lock_waits = on              -- ⭐ log any wait longer than deadlock_timeout
deadlock_timeout = '1s'
```

**⭐ `log_lock_waits = on` is the setting that makes lock problems diagnosable after the fact.**
Without it you learn about deadlocks only from application errors, with no context.

## ⭐ The four causes, and their fixes

### ⭐ 1. Inconsistent lock ordering — the classic

**Fix: always acquire locks in a consistent order**, and the easiest consistent order is **ascending
primary key**:

```java
// ⭐ sort the ids before locking — a codebase-wide convention (Day 165)
List<Long> ids = requestedIds.stream().sorted().toList();
for (Long id : ids) repo.lockById(id);
```

**⭐ It must be a convention, not a local fix**, because a deadlock needs only two methods that
disagree. A single `for (var item : order.getItems())` iterating in insertion order is enough to
break it.

### ⭐ 2. Foreign key locks — the invisible one

**Inserting a child row takes a `FOR KEY SHARE` lock on the parent.** So two transactions inserting
order items for the same product, while also updating the product, can deadlock **without either
statement mentioning a lock.** This one is genuinely hard to spot from the code.

### 3. Index or unique-constraint conflicts

Two transactions inserting the same unique value: the second waits for the first to commit or roll
back. With two such values inserted in opposite orders, that is a deadlock.

### ⭐ 4. Upserts in different orders

```sql
insert into stock (product_id, qty) values (...) on conflict (product_id) do update ...;
```

`ON CONFLICT` takes locks, so **batch upserts must be sorted by key** — the same rule as cause 1,
and the most common modern instance of it.

## ⭐ The design-level fixes, which are better than lock ordering

| Fix | Note |
|---|---|
| ⭐ **Shorter transactions** | ⭐ **the single most effective change.** Less time holding locks, less overlap |
| ⭐ **Atomic single statements** | `update ... set qty = qty - 1 where ...` locks and releases in one step |
| ⭐ **`SKIP LOCKED` for queues** | Day 178 — workers never contend at all |
| ⭐ **Retry with jittered backoff** | ⭐ **deadlocks are normal under concurrency.** Retry them |
| Reduce hot rows | a single counter row every transaction touches is a serialisation point |

**⭐ The last point on retries is the one to internalise: a deadlock is not necessarily a bug.** Under
high concurrency they occur, PostgreSQL resolves them correctly by aborting one transaction, and the
right response is a bounded retry with jitter (Day 123) — exactly as with `SERIALIZABLE` in Day 195.

```java
@Retryable(retryFor = DeadlockLoserDataAccessException.class,     // ⭐ Spring's translation
           maxAttempts = 3, backoff = @Backoff(delay = 50, multiplier = 2, random = true))
@Transactional
public void transfer(Long from, Long to, BigDecimal amount) { ... }
```

**⭐ Alert on the deadlock *rate*, not on individual deadlocks.** A rising rate means contention is
growing and the design needs attention; a handful a day is normal operation.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ No `lock_timeout` in migrations | one slow query + one `ALTER` = total outage |
| Not knowing the queue is FIFO | the outage above is inexplicable |
| ⭐ `ALTER TABLE` during peak traffic | maximum chance of queueing behind a long query |
| Inconsistent lock ordering | deadlocks |
| Ordering fixed locally, not as a convention | two methods that disagree is enough |
| Not knowing FK inserts take parent locks | deadlocks with no visible lock statement |
| Unsorted batch upserts | the modern common case |
| ⭐ No retry on deadlock | user-visible errors for a normal, recoverable event |
| Retrying without jitter | synchronised retries re-collide |
| ⭐ `log_lock_waits` off | lock problems undiagnosable after the fact |
| `pg_terminate_backend` as the first response | kills the connection; cancel first |
| Long transactions | Day 194 and this page share the same root cause |

## Interview questions

**Q: An `ALTER TABLE ADD COLUMN` took the application down. It should be instant. Why?**
The lock queue is FIFO. The `ALTER` needed `ACCESS EXCLUSIVE` and had to wait behind a long-running
`SELECT` holding `ACCESS SHARE` — and while it waited, every new query queued behind *it*, including
reads that would never have conflicted with each other. Within seconds every connection was blocked.
The fix is `lock_timeout` in every migration, so it gives up rather than queues.

**Q: How do you find what is blocking a query?**
`pg_blocking_pids()` joined against `pg_stat_activity`. That gives me the blocked query, the blocking
query, how long it has waited, and the blocker's state. If the state is `idle in transaction`, the
blocker is not even running a query — an application opened a transaction and abandoned it, which is
an application bug.

**Q: What causes deadlocks and how do you fix them?**
Inconsistent lock ordering, mostly — including invisible cases where inserting a child row takes a
key-share lock on the parent, and unsorted batch upserts. The fix is a codebase-wide ordering
convention, usually ascending primary key. But the more effective fixes are structural: shorter
transactions, atomic single statements, `SKIP LOCKED` for queues — and a bounded jittered retry,
because deadlocks are a normal event under concurrency, not necessarily a bug.

**Q: Does PostgreSQL escalate row locks to table locks?**
No. Row locks live in the tuple itself, so it can hold millions without exhausting a lock table.
That avoids the escalation behaviour some engines have under heavy write load.

## Mini task

1. Reproduce the deadlock in two sessions. **Read the full error and the server log entry.**
2. Turn on `log_lock_waits` and `deadlock_timeout = '200ms'`. Re-run and read the log detail.
3. ⭐ **Reproduce the outage**: run a 60-second query, then `ALTER TABLE ADD COLUMN`, then try a
   simple `SELECT` from a third session. **Watch the `SELECT` block on a table nobody is modifying.**
4. Add `set lock_timeout = '2s'` before the `ALTER` and confirm it fails instead of queueing.
5. Write the `pg_blocking_pids` query. **Memorise it.** Use it to diagnose step 3.
6. Reproduce a deadlock via foreign key locks — two transactions inserting children of the same
   parent and updating it. **Confirm no lock statement appears anywhere in your SQL.**
7. Write an unsorted batch upsert running concurrently. Deadlock it. Sort the batch. Confirm it stops.
8. Add the `@Retryable` deadlock handler and prove recovery under 50 concurrent transfers.
9. Compare the deadlock rate of a read-modify-write transfer against a single atomic `UPDATE`.
10. Leave a session `idle in transaction`, then find it with the blocking query and cancel it.

## 🎙️ Articulation drill

Two minutes: **"A migration took the site down. Walk me through it."**

Tell the story with the mechanism: the `ALTER` needed an exclusive lock, a long query held a shared
one, and because the lock queue is FIFO, every subsequent read queued behind the waiting `ALTER` —
including reads that never conflicted with anything. Then the fix, which is one line: `lock_timeout`
in every migration so it gives up rather than queues. Close by showing you could have diagnosed it
live — `pg_blocking_pids` joined to `pg_stat_activity`, and if the blocker's state is idle in
transaction, the problem is application code, not the database.
