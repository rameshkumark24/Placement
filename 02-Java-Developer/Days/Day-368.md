# Day 368

**L-368** · CI/CD concepts — the pipeline as a quality gate

**Time:** 3 hrs · **Mode:** NEW

> **⭐ A pipeline is not automation of the steps you used to do by hand. It is a sequence of gates
> ordered so that the cheapest one that can reject a change runs first.**
>
> And the thing that decides whether any of it works is not tooling. **It is whether people trust the
> result — which flaky tests destroy faster than anything else.**

---

# Part 1 — ⭐ The distinctions people conflate

| Term | ⭐ Means |
|---|---|
| ⭐ **Continuous Integration** | ⭐⭐ **everyone merges to trunk frequently, and every merge is verified** |
| ⭐ **Continuous Delivery** | ⭐ every commit produces a **releasable** artefact; releasing is a button |
| ⭐ **Continuous Deployment** | ⭐ every passing commit **goes to production automatically** |

> **⭐ The one people get wrong: CI is a branching and merging practice, not a tool.** A team with
> GitHub Actions and four-week feature branches **is not doing continuous integration** — they are
> running tests occasionally on divergent code. **Saying that is a stronger answer than naming
> tools.**

⚠️ **Long-lived branches fight CI by construction** (Day 088). The longer a branch lives, the larger
its eventual merge and the less each individual build told you. **Trunk-based development with short
branches, behind feature flags where needed, is what makes the pipeline meaningful.**

---

# Part 2 — ⭐⭐ Ordering the pipeline: fail fast, fail cheap

```
⭐ ORDER BY (cost to run) ÷ (probability of catching something)

⭐  10 s  ⭐ format, lint, compile           ⭐ catches the most, costs the least
⭐  60 s  ⭐ unit tests                       (Day 097)
⭐  90 s  ⭐ build the artefact ONCE          ⭐⭐ everything downstream uses THIS artefact
⭐   2 m  ⭐ integration tests (Testcontainers, Day 184)
⭐   1 m  ⭐ dependency + image scanning      (Day 363)
⭐   3 m  ⭐ deploy to staging + smoke tests
⭐  10 m  ⭐ end-to-end / performance         ⭐ often nightly rather than per-PR
```

| ⭐ Principle | ⭐ Why |
|---|---|
| ⭐⭐ **Fail fast** | ⭐ a formatting error should not wait behind a ten-minute test suite |
| ⭐⭐ **Build once, promote many** | ⭐⭐ **the artefact tested in staging is bit-identical to the one in production** |
| ⭐ **Parallelise independent stages** | scanning and integration tests need not be sequential |
| ⭐ **Per-PR vs per-merge vs nightly** | ⭐ not everything belongs on every push |
| Cache aggressively | dependencies, Docker layers (Day 362) |

## ⭐⭐ Build once, promote many

```
⭐ ✗ build in CI → build again for staging → build again for production
⭐   ⇒ ⭐⭐ three different artefacts. You tested one and shipped another.
⭐
⭐ ✓ build ONE image, tagged by commit SHA
⭐   ⇒ promote the SAME DIGEST through dev → staging → production
⭐   ⇒ ⭐⭐ config comes from the environment, never the build (Day 360, Day 373)
```

> **⭐ This is Day 287's checklist item 1 and it is the single most important pipeline property.**
> If the artefact is rebuilt per environment, **every test result is about a different binary** — and
> the class of bug that produces is unfalsifiable from the logs.

⚠️ **The corollary: an image must never be built with environment-specific configuration.** The
moment you have `Dockerfile.prod`, you have lost the property, **and the staging tests stopped
meaning anything.**

# Part 3 — ⭐⭐ Flaky tests: the thing that actually kills CI

```
⭐ A suite that fails 5% of the time for no reason produces:
⭐   1. ⭐ "just re-run it" as a reflex
⭐   2. ⭐⭐ people stop reading failures
⭐   3. ⭐⭐ a REAL failure is re-run three times and then merged
⭐ ⇒ ⭐⭐ THE PIPELINE NOW PROVIDES NOTHING, while costing everything.
```

| ⭐ Policy | ⭐ Detail |
|---|---|
| ⭐⭐ **Quarantine, do not blind-retry** | ⭐⭐ **move it out of the blocking suite, file a ticket with an owner and a deadline** |
| ⭐ Track flakiness as a metric | ⭐ a per-test failure rate on unchanged code |
| ⭐ **Automatic retry is a trap** | ⭐ it hides the flake and, worse, hides real intermittent bugs |
| ⭐ Common causes | ⭐ **shared state, time, ordering, real network, `sleep`-based waits, ports** |
| ⭐ **A flaky test often means flaky code** | ⭐⭐ a race in the test is sometimes a race in the system |

> **⭐ The last row is worth pausing on.** A test that intermittently fails on a concurrency assertion
> may be correctly detecting a real race (Day 310). **Deleting or retrying it discards a genuine
> finding** — which is why quarantine with an owner, rather than retry, is the policy.

⚠️ **Trust is the real asset.** A pipeline people believe blocks bad changes; a pipeline people work
around is an expensive delay. **Every "re-run the build" is a small withdrawal from that account.**

# Part 4 — ⭐ Environments, releases, and measuring

## ⭐ Deploy ≠ release

> **⭐ A feature flag decouples deploying code from releasing behaviour** (Day 372). Code ships dark,
> is enabled for 1% of users, then 100%, **and disabled instantly without a rollback** — which turns
> a deploy from an event into a routine.

| ⭐ Benefit | |
|---|---|
| ⭐ Deploys become small and frequent | ⭐ smaller changes are easier to diagnose |
| ⭐ **Rollback of behaviour is a config change** | ⭐⭐ seconds, not a redeploy |
| ⭐ Trunk-based development becomes possible | unfinished work ships disabled |
| ⭐ **The cost** | ⭐ flags accumulate — **they need an expiry and a removal ticket** |

## ⭐ The four DORA metrics

| Metric | ⭐ What it reveals |
|---|---|
| ⭐ **Deployment frequency** | how small your batches are |
| ⭐ **Lead time for change** | commit → production |
| ⭐⭐ **Change failure rate** | ⭐ what fraction of deploys cause an incident |
| ⭐⭐ **Mean time to restore** | ⭐⭐ **the one that matters most — you will ship bugs; how fast do you recover?** |

> **⭐ The counter-intuitive finding worth citing: teams that deploy more often have LOWER change
> failure rates**, because each change is smaller, the path is well practised, and rollback is
> routine. **Deploying rarely is not safer — it is a way of accumulating risk into a single event.**

## ⭐ Pipeline hygiene

| ⭐ Practice | |
|---|---|
| ⭐ **Pipeline as code, in the repo** | ⭐ reviewed, versioned, and it changes with the code it builds |
| ⭐ **A pipeline must be re-runnable** | ⭐ idempotent, no manual steps |
| ⭐ **Every artefact traceable to a commit** | ⭐ SHA in the tag, the labels, and `build-info` (Day 362) |
| ⭐ Fast feedback target | ⭐⭐ **under 10 minutes for PR feedback, or people context-switch away** |
| ⭐ **Deployment is the same mechanism everywhere** | ⭐ staging is a rehearsal only if it uses the production path |
| Rollback tested, not assumed | Day 283 |

⚠️ **A staging deploy that uses a different mechanism than production is not a rehearsal.** If
production deploys via a pipeline and staging via someone's laptop, **the first time you exercise the
real path is during a real deploy.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Calling a build server "CI" | ⭐⭐ CI is a merging practice, not a tool |
| ⭐ Long-lived feature branches | ⭐ each build tells you less; merges get bigger |
| ⭐⭐ **Rebuilding per environment** | ⭐⭐ **you tested one artefact and shipped another** |
| ⭐ `Dockerfile.prod` | the same failure, wearing a filename |
| ⭐ Slow checks before fast ones | ⭐ a lint error found after ten minutes |
| ⭐⭐ **Auto-retrying flaky tests** | ⭐⭐ hides both the flake and real intermittent bugs |
| ⭐ Ignoring flakiness | ⭐ the pipeline stops being believed |
| ⭐ **PR feedback over ~10 minutes** | people stop waiting and start batching |
| Manual steps in the pipeline | not re-runnable, not auditable |
| ⭐ Artefacts not traceable to a commit | "what is running?" has no answer |
| ⭐ **Staging deployed differently from production** | the real path is never rehearsed |
| Feature flags with no expiry | ⭐ permanent branching in the code |
| Deploying rarely "for safety" | larger batches, worse failure rate |

## Interview questions

**Q: What is continuous integration?**
A practice, not a tool: everyone merges to trunk frequently and every merge is automatically
verified. A team with a build server and four-week feature branches is not doing CI — they are
running tests occasionally on code that has already diverged. Long-lived branches fight it by
construction, because the longer a branch lives, the bigger the merge and the less each build told
you.

**Q: How do you order the stages?**
By cost divided by the probability of catching something, so the cheapest thing that can reject a
change runs first — formatting and compilation in seconds, unit tests next, then the artefact build,
then integration tests, scanning, and staging smoke tests. Independent stages run in parallel, and
I aim for pull-request feedback under ten minutes, because past that people stop waiting and start
batching changes.

**Q: What is the most important property of a pipeline?**
Build once, promote many. One image tagged by commit SHA, and the same digest moves through staging
to production with configuration injected from the environment. If it is rebuilt per environment then
every test result is about a different binary, and the resulting class of bug is impossible to
diagnose from the logs. The moment there is a `Dockerfile.prod`, that property is gone.

**Q: What do you do about flaky tests?**
Quarantine with an owner and a deadline — never blind retry. Automatic retries hide the flake and,
worse, hide genuine intermittent bugs; a test that intermittently fails a concurrency assertion may
be correctly detecting a real race. The deeper issue is trust: once people reflexively re-run
failures, a real failure gets re-run three times and merged, and the pipeline is costing everything
while providing nothing.

**Q: Deploying more often is riskier, isn't it?**
The evidence says the opposite. Teams that deploy frequently have lower change failure rates, because
each change is smaller and easier to diagnose, the deployment path is well practised, and rollback is
routine rather than an emergency. Deploying rarely does not remove risk, it accumulates it into one
large event. And feature flags decouple deploy from release, so shipping code and enabling behaviour
become two separate, individually reversible decisions.

## Mini task

1. **Draw your current pipeline as a sequence with timings.** Reorder it by cost-to-catch and
   **measure the new time-to-first-failure.**
2. ⭐ Verify **build once, promote many**: confirm the digest deployed to staging is byte-identical to
   the one in production. **If you cannot, that is the finding.**
3. ⭐ Add the commit SHA to the image tag, the OCI labels and `build-info`. **Then answer "what commit
   is in production?" in one command.**
4. ⭐ **Measure PR feedback time.** If it is over ten minutes, parallelise and cache until it is not.
5. ⭐⭐ **Run your test suite 50 times on unchanged code.** Any test that fails even once is flaky —
   **list them.**
6. ⭐ Quarantine the flakiest, file it with an owner, and **investigate whether it is finding a real
   race.**
7. ⭐ Introduce a deliberate lint error and **measure how long until the pipeline tells you.**
8. ⭐ Implement one feature behind a **flag.** Deploy it disabled, enable for a subset, then **disable
   it without a redeploy** and time that.
9. ⭐ Instrument the **four DORA metrics** for the last month. Compute change failure rate honestly.
10. Compare how staging and production are deployed. **If they differ, make them identical.**

## 🎙️ Articulation drill

**Three minutes:** *"Describe the pipeline for a change from commit to production."*

**⭐ The structure: lint and compile in seconds, unit tests, then the artefact built ONCE and tagged
by SHA; integration tests and scanning in parallel against that artefact; deploy the same digest to
staging via the production mechanism; smoke test; promote the identical digest to production behind a
feature flag.**

**⭐ The marker is saying "the same digest" explicitly at each promotion.** It is the property most
pipelines quietly lack, **and naming it — along with a rollback you have actually timed (Day 283) —
is what makes the description sound like something you have operated rather than diagrammed.**
