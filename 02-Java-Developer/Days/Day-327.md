# Day 327

**L-327** · CDN and object storage — and the upload that must not touch your API

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Two components that remove more load from a system than any amount of application tuning — and
> one pattern, presigned URLs, that is the correct answer to every "how do you handle file uploads?"
> question you will ever be asked.**

---

# Part 1 — ⭐ What a CDN actually does

| Job | ⭐ Detail |
|---|---|
| ⭐ **Serve cached content from the edge** | ⭐ 20 ms instead of 150 ms across an ocean (Day 322) |
| ⭐ **Absorb the bulk of traffic** | ⭐ **a 95% offload means your origin sees 5% of requests** |
| ⭐ **Terminate TLS near the user** | ⭐ the handshake is 2–3 round trips — **at 150 ms each, that is half a second saved** |
| ⭐ Keep warm connections to the origin | no new TCP+TLS per request |
| ⭐ **Absorb DDoS** | ⭐ hundreds of Tbps of capacity that you do not have |
| Compress, transform images | at the edge, per client |

> **⭐ The TLS point is underrated and worth saying.** Even for *uncacheable* content, routing through
> a CDN helps: the expensive handshake happens 20 ms away, and the CDN's long-lived origin connection
> carries the request the rest of the way. **A CDN is a latency tool, not only a caching tool.**

## ⭐ Push vs pull

| | ⭐ Pull (origin-fetch) | ⭐ Push |
|---|---|---|
| How | ⭐ **first request misses, CDN fetches and caches** | you upload to the CDN |
| ⭐ Best for | ⭐ **almost everything** | ⭐ large files with predictable, spiky demand |
| Cost | ⭐ **the first user pays the latency** | storage everywhere, even for cold objects |
| Operations | ⭐ **nothing to manage** | a publish pipeline |

**⭐ Default to pull.** Mention push for a scheduled release — a game patch, a launch video — **where
you know a million people want the same object at 9am and you do not want a million-way origin
stampede** (Day 326's thundering herd, at the CDN layer; the real mitigation is *request
collapsing*, which good CDNs do automatically).

## ⭐⭐ Cache keys and invalidation

```
⭐ Default cache key = host + path + (some) query string
⭐ ⇒ ⭐ /avatar?v=1 and /avatar?v=2 are DIFFERENT objects.
⭐ ⇒ ⭐⭐ /page?utm_source=twitter fragments your cache into thousands of copies.
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐ **Strip tracking parameters from the cache key** | ⭐ **otherwise every marketing link is a separate cache entry** |
| ⭐ `Vary: Accept-Encoding` — fine | one variant per encoding |
| ⭐⭐ **`Vary: User-Agent` — never** | ⭐⭐ **thousands of variants; the hit rate collapses to nearly zero** |
| ⭐ Cookies in the key | ⭐ **a per-user cache is not a cache** |
| ⭐ `Cache-Control: public, max-age, s-maxage` | ⭐ `s-maxage` targets the CDN specifically |

⚠️ **Purging is slow and unreliable — usually seconds to minutes, sometimes per-POP.**

> **⭐ The answer is versioned URLs, not purges: `/static/app.a3f9c2.js` with a one-year
> `max-age, immutable`.** A new build is a new URL, so there is nothing to invalidate. **The HTML
> that references it gets a short TTL.** That two-tier pattern — **immutable assets, short-lived
> HTML** — is the standard and should be stated as such.

| Also worth naming | |
|---|---|
| ⭐ **`stale-while-revalidate`** | ⭐ serve the stale copy instantly, refresh in the background — **removes the miss latency entirely** |
| ⭐ `stale-if-error` | ⭐ **serve stale content when the origin is down — free availability** |
| ⭐ Signed URLs / signed cookies | ⭐ **private content through a CDN, with an expiry** |
| Origin shield | one mid-tier cache collapses requests from many POPs |

# Part 2 — ⭐ Object storage

| ⭐ Property | ⭐ Consequence |
|---|---|
| ⭐ **Flat namespace, key → blob** | "directories" are a prefix convention, nothing more |
| ⭐ **Objects are immutable** | ⭐ **you replace, never append or edit in place** |
| ⭐ **Effectively unlimited, ~11 nines of durability** | ⭐ far beyond what you can build |
| ⭐ **Very cheap storage, expensive egress** | ⭐⭐ **egress is the cost model — hence the CDN in front** |
| ⭐ High latency per object (tens of ms) | ⭐ **terrible for small, frequent reads** |
| ⭐ HTTP-native | ⭐ **the browser can talk to it directly — Part 3** |

| ⭐ Store here | ⭐ Do not store here |
|---|---|
| ⭐ Images, video, documents, user uploads | ⭐ **anything queried by attribute** |
| Backups, logs, data-lake files | ⭐ **session state** (latency) |
| ⭐ Static site assets | ⭐ **small objects read thousands of times/second** |
| Build artefacts | anything needing a transaction |

⚠️ **The metadata rule: blobs in object storage, metadata in the database.** The row holds the id,
owner, content type, size, and the object key; **the bytes never go in the database.** Storing images
as `BYTEA`/`BLOB` bloats every backup, destroys the buffer pool (Day 186), and makes replication
crawl.

⚠️ **And "unlimited" hides two real limits:** listing a prefix with millions of objects is slow and
paginated — **keep an index in your database rather than listing the bucket** — and per-prefix request
rates are throttled, so **a key scheme beginning with a timestamp creates a hot prefix.** Random or
hashed prefixes spread it.

# Part 3 — ⭐⭐ The presigned URL pattern

```
⭐ THE WRONG WAY — the one candidates draw by default
   client ──100 MB──► your API ──100 MB──► object storage
⭐   ✗ your bandwidth paid twice        ✗ a request thread held for minutes
⭐   ✗ request size limits              ✗ the upload dies with a deploy
⭐   ✗ ⭐⭐ 1,000 concurrent uploads = 1,000 occupied threads (Day 322's Little's Law)

⭐ THE RIGHT WAY
   1. client ──► your API:  "I want to upload a 100 MB video"
   2. your API: authorise, create a DB row (status=PENDING), ⭐ return a PRESIGNED PUT URL
   3. client ──100 MB──► ⭐ OBJECT STORAGE DIRECTLY    ⭐ your API is not involved
   4. object storage ──event──► your API: "upload complete"   ⭐ → status=READY
```

| ⭐ Property | ⭐ Why it matters |
|---|---|
| ⭐ **Bytes never traverse your service** | ⭐⭐ **no bandwidth cost, no thread held, no size limit** |
| ⭐ **The URL is scoped and expiring** | ⭐ one key, one method, one content type, N minutes |
| ⭐ **Authorisation stays in your API** | ⭐ you decide *before* issuing the URL |
| ⭐ **Completion is an event** | ⭐ **and it can be lost — see below** |
| ⭐ Resumable/multipart for large files | ⭐ a dropped mobile connection does not restart 100 MB |

⚠️ **Two failure cases you must name, because they are the follow-up questions:**

1. ⭐ **The upload completes but the notification is lost** → the row stays `PENDING` forever.
   **A reconciliation job checks pending rows against the bucket** — the same reconciliation instinct
   as Day 317's ATM journal.
2. ⭐ **The client abandons after getting the URL** → an orphan row, and possibly an orphan object.
   **A lifecycle rule deletes incomplete uploads after N days**, and the job cleans the rows.

**⭐ Downloads are the mirror image:** issue a **presigned GET** or a **signed CDN URL** with a short
expiry rather than proxying bytes. **Same reasoning, same benefits.**

> **⭐ "The bytes never touch my API — I authorise and hand out a scoped, expiring URL, then reconcile
> the completion event" is the complete answer to file handling**, and it works for uploads,
> downloads, private media and exports.

# Part 4 — ⭐ The default architecture for anything with media

```
                        ⭐ CDN (immutable URLs, long TTL)
                          │            ▲
       browser ───────────┘            │ origin fetch (rare)
          │  ⭐ presigned PUT           │
          ▼                            │
   ⭐ OBJECT STORAGE ◄─────────────────┘
          │ ⭐ event
          ▼
   ⭐ your API ──► database (metadata only)  ──► ⭐ async pipeline: transcode, thumbnail, scan
```

| ⭐ Consequence | |
|---|---|
| ⭐ **Your servers handle metadata and authorisation only** | ⭐ small, fast, cheap requests |
| ⭐ **Storage and bandwidth scale without you** | |
| ⭐ **Processing is asynchronous** | ⭐ the upload succeeds; the thumbnail arrives later |
| ⭐ Serving cost is dominated by CDN egress | ⭐ **which is exactly what Day 323's bandwidth estimate predicted** |

⚠️ **Never trust the client's declared content type or size.** The presigned URL should constrain
both, **and the async pipeline must verify the actual bytes** — content sniffing, size checks, and a
malware scan for user-generated content. **A file named `.jpg` is not a JPEG.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Proxying uploads through the API** | ⭐⭐ **threads held for minutes; bandwidth paid twice; size limits** |
| ⭐ Streaming downloads through the API | same, in reverse — and it defeats the CDN |
| ⭐ **Blobs in the database** | ⭐ bloated backups, wrecked buffer pool, slow replication |
| ⭐ No reconciliation for lost completion events | rows stuck `PENDING` forever |
| No lifecycle rule for abandoned uploads | orphaned objects, paid for indefinitely |
| ⭐ **`Vary: User-Agent`** | ⭐⭐ **the CDN hit rate collapses** |
| ⭐ Tracking parameters in the cache key | ⭐ every marketing link is a separate entry |
| ⭐ Relying on purges for deploys | ⭐ **slow and unreliable — version the URL instead** |
| Short `max-age` on immutable assets | throwing away the easiest cache win |
| ⭐ No `stale-if-error` | you were one header away from surviving an origin outage |
| ⭐ Timestamp-prefixed object keys | ⭐ a hot prefix and throttling |
| Listing a bucket to find things | slow and paginated — index in the database |
| Trusting the declared content type | a `.jpg` that is an executable |

## Interview questions

**Q: How do you handle a 100 MB file upload?**
The bytes never touch my API. The client asks for permission, I authorise, write a pending metadata
row and return a presigned PUT URL scoped to one key, method, content type and a short expiry. The
client uploads straight to object storage, and a completion event flips the row to ready. Otherwise
I am paying for the bandwidth twice, holding a request thread for minutes, and a deploy in the middle
kills the upload.

**Q: What happens if that completion event is lost?**
The row stays pending forever, so there is a reconciliation job that checks pending rows against the
bucket and resolves them — the same instinct as an ATM journal. The mirror case is a client that
takes the URL and never uploads, which a lifecycle rule cleans up after a few days along with the
orphaned rows.

**Q: Should images go in the database?**
No — metadata in the database, bytes in object storage, with the row holding the object key. Blobs
bloat every backup, evict useful pages from the buffer pool, and slow replication, and you lose the
ability to serve them from a CDN without proxying. Object storage is cheaper, more durable than
anything I would build, and HTTP-native, which is what makes presigned URLs possible.

**Q: How do you invalidate CDN content on deploy?**
I do not — I version the URL. Assets get a content hash in the filename and a one-year immutable
cache header, so a new build is a new URL and there is nothing to purge. The HTML that references
them gets a short TTL. Purges are slow, sometimes per-POP, and unreliable enough that I would not put
a deploy behind one.

**Q: A CDN only helps cacheable content, right?**
Not only. It terminates TLS near the user, and a handshake is two or three round trips — across an
ocean that is most of half a second saved before any content is served. It also keeps warm
connections to the origin, absorbs DDoS, and with `stale-if-error` can serve content while the origin
is down. It is a latency and availability tool as much as a caching one.

## Mini task

1. ⭐ **Implement the presigned upload flow** end to end: authorise, pending row, presigned PUT,
   direct upload, completion event, ready.
2. **Measure both ways**: 100 MB through your API versus direct. Record thread occupancy, memory and
   time.
3. ⭐ **Drop the completion event** and write the reconciliation job that fixes it.
4. Abandon an upload after getting the URL; add a **lifecycle rule** plus a row-cleanup job.
5. ⭐ Put a CDN in front of a static site with **content-hashed filenames and immutable headers.**
   Deploy a change and confirm **zero purges** were needed.
6. Add `utm_source` to a URL and **measure the hit-rate collapse** if it is part of the cache key.
   Strip it and re-measure.
7. ⭐ Enable `stale-if-error`, **take the origin down, and confirm the site still serves.**
8. Upload an executable renamed to `.jpg`. **Confirm your pipeline rejects it on actual content, not
   the extension.**
9. Create objects with timestamp-prefixed keys, then hashed prefixes, and **compare request-rate
   behaviour.**

## 🎙️ Articulation drill

**Two minutes:** *"Users upload profile photos. Design it."*

**⭐ The answer that scores has one shape: authorise → presigned URL → direct upload → event →
async processing → serve through a CDN with versioned URLs.** Then the two failure cases, unprompted:
lost completion events need reconciliation, abandoned uploads need lifecycle rules.

**⭐ The failure mode is drawing bytes flowing through your service.** It is the default instinct, it
is what most candidates draw, **and every follow-up — "what about 100 MB?", "what about a thousand
concurrent uploads?" — is designed to expose it.**
