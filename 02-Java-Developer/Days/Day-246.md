# Day 246 🔗

**J-246** · 🔗 **The full-stack contract** — ⭐⭐ making a renamed DTO field a build failure

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: the boundary between your API and your client is the only place in your
> whole system with no type checking and no test — both sides are individually correct and nothing
> compares them — so the single highest-leverage thing you can build is a generated client that turns
> a contract change into a compile error.**
>
> Today: ⭐ the drift, ⭐⭐ generation from springdoc, versioning, and what generation does **not** give you.

# Part 1 — ⭐⭐ The gap

```
⭐⭐ EVERY OTHER BOUNDARY IN YOUR SYSTEM IS CHECKED:

⭐   Java method → method ............ ⭐ javac
⭐   Java → Postgres ................. ⭐ the schema + Flyway
⭐   component → component ........... ⭐ TypeScript
⭐   ⭐⭐ SPRING → REACT ................ **NOTHING**

⭐   ⇒ ⭐ you rename UserDto.fullName → UserDto.name
⭐   ⇒ ⭐ javac: clean ✅   your @WebMvcTest: green ✅
⭐        tsc: clean ✅   ⭐ every frontend test passes (⭐⭐ THE MOCKS
⭐        WERE UPDATED BY HAND, OR NEVER)
⭐   ⇒ ⭐⭐ PRODUCTION RENDERS THE WORD "undefined" TO A CUSTOMER.
⭐     ⭐ THE MOST-TESTED SYSTEM IN THE WORLD DOES NOT CATCH THIS,
⭐       BECAUSE BOTH SIDES ARE CORRECT AND NOBODY COMPARED THEM.
```

| ⭐ The four ways teams "solve" this | Reality |
|---|---|
| Careful communication | ⭐ Works until someone is on holiday |
| Hand-written TS types | ⭐⭐ A **second** source of truth that drifts silently — worse than none, because it looks safe |
| Integration tests against a live API | ⭐ Catches it slowly, only for paths you tested |
| ⭐⭐ **Generate the client from the spec** | ⭐ Catches it **at compile time**, for every field, free |

# Part 2 — ⭐⭐ Generation

```
⭐⭐ THE PIPELINE — and note that step 1 already exists

⭐   ① springdoc-openapi ⇒ ⭐ /v3/api-docs  (⭐⭐ FREE. Already there.)
⭐   ② generator ⇒ TypeScript types + a typed client
⭐   ③ ⭐ COMMIT THE OUTPUT ⇒ diffs are REVIEWABLE in the PR
⭐   ④ ⭐⭐ CI REGENERATES AND FAILS IF THE DIFF IS NON-EMPTY
⭐      ⇒ ⭐ "you changed the API and did not regenerate" becomes a
⭐        BUILD FAILURE, WITH THE DIFF ATTACHED.
```

```bash
# ⭐ one command
npx openapi-typescript http://localhost:8080/v3/api-docs -o src/api/schema.d.ts
```

```typescript
// ⭐⭐ now every call is checked against the real contract
const { data, error } = await client.GET("/users/{id}", {
  params: { path: { id } },      // ⭐ wrong param name ⇒ compile error
});
data.nmae;                       // ⭐⭐ COMPILE ERROR. THE TYPO IS CAUGHT.
```

```java
// ⭐⭐ make the generated output good by making the spec good
@Operation(operationId = "getUser")        // ⭐⭐ becomes the CLIENT METHOD NAME
@ApiResponses({
  @ApiResponse(responseCode = "200"),
  @ApiResponse(responseCode = "404", content = @Content(
      schema = @Schema(implementation = ProblemDetail.class))),  // ⭐ typed errors
})
@GetMapping("/users/{id}")
UserPublic get(@PathVariable UUID id) { ... }   // ⭐ a DTO, never the entity
```

| ⭐ Spec hygiene | Why |
|---|---|
| **`operationId` on every route** | ⭐⭐ Readable generated method names |
| **Declare error responses** | ⭐ Otherwise the client types errors as `unknown` |
| **⭐⭐ A DTO return type, never the entity** | A method returning the entity generates a type with **every column** — Day 236, now also a code-generation problem |
| **Bean Validation annotations** | ⭐⭐ springdoc emits `@Min`/`@Size` into the schema, so **your rules travel to the client for free** (Day 229) |

# Part 3 — Versioning the contract

```
⭐⭐ TWO VERSIONS ARE ALWAYS LIVE (Day 245's stale tab).
⭐   ⇒ ⭐ EVERY API CHANGE IS EITHER ADDITIVE OR A MIGRATION.

⭐   ✅ SAFE (additive)
⭐     · add an OPTIONAL field       · add a new endpoint
⭐     · ⭐ add an enum value ⇒ ⭐⭐ ONLY IF CLIENTS HANDLE UNKNOWN
⭐       VALUES. An exhaustive switch BREAKS — add a default first.

⭐   ❌ BREAKING (needs a migration)
⭐     · remove or rename a field   · change a type
⭐     · make an optional field required
⭐     · ⭐⭐ NARROW AN ENUM

⭐   ⭐⭐ EXPAND–MIGRATE–CONTRACT — ⭐ THE SAME DANCE AS A FLYWAY
⭐     COLUMN RENAME, WHICH YOU HAVE ALREADY DONE:
⭐     ① ADD the new field alongside the old (both populated)
⭐     ② SHIP the client that reads the new one
⭐     ③ ⭐ WAIT for old clients to age out (MEASURE IT — below)
⭐     ④ REMOVE the old field
```

> ⭐ **"Wait for old clients to age out" needs a number.** Send a build id header from the client and
> log it. **Then "how many users are still on the old contract?" is a query rather than a guess** —
> and that is what makes step ④ safe instead of nervous.

# Part 4 — ⭐⭐ What generation does NOT give you

```
⭐⭐ SAY THIS PART OUT LOUD — IT IS WHERE PEOPLE OVERTRUST THE TOOL.

⭐   ❌ ⭐⭐ IT DOES NOT VALIDATE AT RUNTIME. The generated type is
⭐      still erased (Day 218). If the server sends something the
⭐      spec does not describe — ⭐ A BUG, A PROXY, AN ERROR PAGE —
⭐      ⭐⭐ YOU GET THE undefined ANYWAY.
⭐      ⇒ ⭐ KEEP ZOD AT THE BOUNDARY (Day 219). Generation kills
⭐        the DRIFT; validation catches the LIE.
⭐   ❌ IT DOES NOT CHECK **SEMANTICS**. `amount: number` says
⭐      nothing about pence vs pounds. ⭐⭐ A UNIT CHANGE PASSES
⭐      EVERY TYPE CHECK AND BILLS SOMEONE 100×.
⭐      ⭐ (And note BigDecimal serialises to a JS number — which
⭐        cannot represent every BigDecimal. Send money as a
⭐        STRING or in minor units.)
⭐   ❌ IT DOES NOT TEST BEHAVIOUR — Day 244 still applies.
```

| ⭐ Layer | Catches |
|---|---|
| Generated types | ⭐⭐ Shape drift, at compile time |
| Runtime validation (Zod) | ⭐ The server lying about its own spec |
| ⭐⭐ Contract tests | Behaviour: does 404 actually return the `ProblemDetail` you documented? |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you keep the frontend and backend in sync?"**

Name the gap precisely. **The API-to-client boundary is the only place in my system with no type
checking and no test. I rename a DTO field, javac is clean, my `@WebMvcTest` is green, TypeScript
compiles, every frontend test passes because the mocks were updated by hand or never — and production
renders the word "undefined" to a customer. Both sides are individually correct and nothing compared
them.**

Then the fix, and why the cheap alternative is worse. **I generate the TypeScript client from the
OpenAPI spec springdoc already produces. Hand-written types are worse than none, because they're a
second source of truth that drifts silently while looking safe. The output is committed so diffs are
reviewable, and CI regenerates and fails on a non-empty diff.**

Add the bonus that follows from the spec being good. **springdoc emits my Bean Validation annotations
into the schema, so my `@Min` and `@Size` rules travel to the client for free — that's the mechanism
that stops client and server validation drifting. And it immediately showed me endpoints returning
entities rather than DTOs, because those generate a type with every column.**

Then versioning. **Two versions are always live because of open tabs, so every change is additive or a
migration — expand, migrate, contract, the same dance as a Flyway column rename. I send a build id from
the client so "how many users are still on the old contract" is a query rather than a guess.**

Close on the limits. **Generation kills drift; it doesn't validate at runtime. And no type check catches
a unit change from pounds to pence — or that a BigDecimal serialises to a JS number that can't represent
every BigDecimal, which is why money goes over the wire as a string or in minor units.**
