# L-038 · How polymorphism actually works

## The two kinds

| | Static (compile-time) | Dynamic (runtime) |
|---|---|---|
| Also called | Ad-hoc polymorphism, early binding | Subtype polymorphism, late binding |
| Mechanism | **Overloading** | **Overriding** |
| Decided by | The **declared** type of arguments | The **actual** type of the object |
| Decided when | Compile time, by `javac` | Runtime, by the JVM |
| Bytecode | Target baked into the instruction | `invokevirtual` / `invokeinterface` |

**When someone says "polymorphism" without qualification they mean the dynamic kind.** But being able
to name both, and say which is resolved when, is the better answer.

## Dynamic dispatch — the mechanism

```java
Animal a = new Dog();
a.speak();          // which speak() runs?
```

The compiler only knows `a` is an `Animal`. The JVM must choose at runtime.

### The vtable

Each class gets a **virtual method table** — an array of pointers to the actual method
implementations, built by the JVM at class-load time (Day 023).

```
   Animal's vtable                 Dog's vtable
   ┌───┬──────────────────┐        ┌───┬──────────────────┐
   │ 0 │ Animal.toString  │        │ 0 │ Animal.toString  │  ← inherited, same slot
   │ 1 │ Animal.equals    │        │ 1 │ Animal.equals    │
   │ 2 │ Animal.speak     │        │ 2 │ Dog.speak        │  ← OVERRIDDEN, same slot index
   │ 3 │ Animal.eat       │        │ 3 │ Animal.eat       │  ← inherited
   └───┴──────────────────┘        │ 4 │ Dog.fetch        │  ← added by Dog
                                   └───┴──────────────────┘
```

**The key property: a method occupies the same slot index in every subclass's table.**

So `a.speak()` becomes:

```
   1. Read the object header → get its class pointer          (Day 025 — every object has a header)
   2. Read the class's vtable
   3. Jump to slot 2                                          ← index known at COMPILE time
```

**Three memory reads and an indirect jump.** Constant time, regardless of hierarchy depth. That's why
dynamic dispatch is cheap.

```
   Object on heap
   ┌──────────────────┐
   │ header ──────────┼──▶ Class metadata (Metaspace)
   │  · class pointer │     ┌──────────────┐
   │  · mark word     │     │  vtable      │
   ├──────────────────┤     │  [0] ...     │
   │ fields           │     │  [1] ...     │
   └──────────────────┘     │  [2] Dog.speak ──▶ actual code
                            └──────────────┘
```

**`invokevirtual` is what does this** (Day 024). The compiler emits the slot; the JVM resolves through
the object's class.

### Interfaces are harder

`invokeinterface` can't use a fixed slot index, because a class can implement many interfaces and
there's no consistent ordering across them.

```java
interface Flyer  { void move(); }
interface Swimmer { void move(); }
class Duck implements Flyer, Swimmer { public void move() { } }
```

Historically this meant a search through an interface method table — slower than `invokevirtual`.
Modern JVMs use **itables** plus inline caching, so the gap is now negligible in practice. Worth
knowing the distinction exists; not worth optimising for.

## What the JIT does — and this is the interesting part

Day 023 mentioned speculative devirtualisation. Here's what it means concretely.

**The JIT profiles each call site.** If only one implementation has ever been seen:

```java
// Source
for (Shape s : shapes) { total += s.area(); }

// What C2 effectively compiles, if every s has been a Circle:
for (Shape s : shapes) {
    if (s.getClass() == Circle.class) {          // cheap guard
        total += s.radius * s.radius * PI;       // INLINED — no call at all
    } else {
        deoptimise();                             // fall back if the assumption breaks
    }
}
```

**Monomorphic call sites — one observed type — are inlined completely.** The virtual call disappears.

| Call site | Observed types | JIT behaviour |
|---|---|---|
| **Monomorphic** | 1 | Inline with a guard — effectively free |
| **Bimorphic** | 2 | Inline both with a type check |
| **Polymorphic** | 3+ | **Megamorphic** — falls back to a real vtable lookup |

**This is why "virtual calls are slow" is a 2005 opinion.** In practice most call sites are
monomorphic, and the JIT removes the call entirely.

**It's also why `final` on a method doesn't help performance** (Day 034) — the JIT already achieves
the same result speculatively, and can deoptimise if a second implementation appears.

**And it's why microbenchmarks mislead:** a benchmark that exercises three implementations makes the
call site megamorphic, while production might be monomorphic. You measured a different program.

## Static dispatch — overloading

```java
void handle(Object o) { System.out.println("Object"); }
void handle(String s) { System.out.println("String"); }

Object o = "I am a String";
handle(o);        // prints "Object"
```

**The compiler chose `handle(Object)` because the *declared* type of `o` is `Object`.** The runtime
type is irrelevant — the choice was baked into the bytecode by `javac` (Day 032's resolution phases).

**This is the interview question that separates people.** The two mechanisms look similar and behave
oppositely:

```java
Animal a = new Dog();
a.speak();                  // Dog.speak    — DYNAMIC, runtime type wins
process(a);                 // process(Animal) — STATIC, declared type wins
```

**Overriding uses the runtime type. Overloading uses the compile-time type.**

### Double dispatch and the visitor pattern

Because Java dispatches dynamically on the *receiver* but statically on the *arguments*, you cannot
directly dispatch on two types at once:

```java
void collide(Asteroid a, Ship s) { }
void collide(Ship s, Asteroid a) { }

Entity e1 = getAsteroid(), e2 = getShip();
collide(e1, e2);        // ❌ won't compile — the compiler only sees Entity
```

**The visitor pattern** (Day 095) works around this with two chained virtual calls — the first
dispatches on the receiver's type, the second on the argument's. That's *why* visitor looks
convoluted: it's manually simulating a dispatch mechanism Java doesn't have.

## Type this yourself

```java
public class DispatchDemo {

    static class Animal { String speak() { return "..."; } }
    static class Dog extends Animal { @Override String speak() { return "Woof"; } }
    static class Cat extends Animal { @Override String speak() { return "Meow"; } }

    // Static dispatch — chosen by DECLARED type
    static String describe(Animal a) { return "an animal"; }
    static String describe(Dog d)    { return "a dog"; }
    static String describe(Cat c)    { return "a cat"; }

    public static void main(String[] args) {

        // ---- 1. Dynamic dispatch: runtime type wins ----
        Animal[] animals = { new Dog(), new Cat(), new Animal() };
        System.out.println("--- dynamic (overriding) ---");
        for (Animal a : animals)
            System.out.println("   " + a.getClass().getSimpleName() + " -> " + a.speak());

        // ---- 2. Static dispatch: DECLARED type wins ----
        System.out.println("\n--- static (overloading) ---");
        Animal asAnimal = new Dog();
        Dog    asDog    = new Dog();
        System.out.println("   describe(asAnimal) = " + describe(asAnimal));  // "an animal" !
        System.out.println("   describe(asDog)    = " + describe(asDog));     // "a dog"
        System.out.println("   SAME OBJECT, different declared type, different method");

        // ---- 3. Monomorphic vs megamorphic ----
        int n = 50_000_000;

        Animal[] mono = new Animal[1000];
        for (int i = 0; i < mono.length; i++) mono[i] = new Dog();          // ONE type

        Animal[] mega = new Animal[1000];
        for (int i = 0; i < mega.length; i++)
            mega[i] = switch (i % 3) { case 0 -> new Dog();
                                       case 1 -> new Cat();
                                       default -> new Animal(); };          // THREE types

        // warm up the JIT first — Day 002
        for (int i = 0; i < 1_000_000; i++) { mono[i % 1000].speak(); mega[i % 1000].speak(); }

        long start = System.nanoTime();
        int len = 0;
        for (int i = 0; i < n; i++) len += mono[i % 1000].speak().length();
        long monoTime = System.nanoTime() - start;

        start = System.nanoTime();
        for (int i = 0; i < n; i++) len += mega[i % 1000].speak().length();
        long megaTime = System.nanoTime() - start;

        System.out.printf("%n--- call site shape ---%n");
        System.out.printf("   monomorphic (1 type):  %,5d ms%n", monoTime / 1_000_000);
        System.out.printf("   megamorphic (3 types): %,5d ms%n", megaTime / 1_000_000);
        System.out.println("   (len=" + len + " — prevents dead-code elimination)");
    }
}
```

**Two things to do:**

1. **`describe(asAnimal)` returns `"an animal"` for a `Dog`.** Same object as `asDog`, different
   declared type, different method chosen. Decompile with `javap -c` (Day 024) and you'll see two
   different `invokestatic` targets hard-coded — proving `javac` decided, not the JVM.

2. **Compare the monomorphic and megamorphic timings.** The monomorphic loop is typically
   meaningfully faster because the JIT inlined the call away. That gap *is* speculative
   devirtualisation, measured.

Then watch it happen:

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining DispatchDemo 2>&1 | grep -i speak
```

Look for `inline (hot)` on the monomorphic site and `virtual call` on the megamorphic one.

## Common mistakes

| Mistake | Correction |
|---|---|
| "Polymorphism means overriding" | It's both. Overloading is static polymorphism, overriding dynamic. |
| Expecting overloads to dispatch on runtime type | They're resolved at compile time from declared types. |
| "Virtual calls are slow, use `final`" | Obsolete. Monomorphic sites are inlined by the JIT. |
| Benchmarking with several implementations | You made the site megamorphic; production may be monomorphic. |
| Thinking dispatch cost grows with hierarchy depth | It's a fixed vtable slot — constant time. |
| Trying to overload on two runtime types | Java dispatches dynamically only on the receiver. Use visitor. |

## Interview questions

**Q: What is polymorphism in Java?**
> Two forms. Static polymorphism is overloading, resolved by the compiler from the declared types of
> the arguments. Dynamic polymorphism is overriding, resolved by the JVM at runtime from the actual
> type of the receiver. When people say polymorphism unqualified they usually mean the dynamic form.

**Q: How does the JVM know which overridden method to call?**
> Each class has a virtual method table built at class-load time, where every method occupies the same
> slot index across the hierarchy. `invokevirtual` carries the slot index, resolved at compile time,
> and at runtime the JVM reads the object's class pointer from its header, looks up that slot in the
> class's vtable, and jumps. It's constant time regardless of hierarchy depth.

**Q: Are virtual method calls expensive?**
> Not usually. Most call sites are monomorphic — only one implementation is ever seen — and the JIT
> inlines the method entirely behind a cheap type guard, so the call disappears. Only megamorphic
> sites, with three or more observed types, fall back to a real vtable lookup. This is also why adding
> `final` for performance doesn't help.

**Q: What does this print, and why?**
```java
Object o = "hello";
void f(Object o) { print("Object"); }
void f(String s) { print("String"); }
f(o);
```
> `"Object"`. Overload resolution happens at compile time using the declared type, which is `Object`.
> The runtime type being `String` is irrelevant — `javac` already baked the target into the bytecode.

**Q: Why can't you dispatch on two runtime types at once?**
> Java dispatches dynamically only on the receiver; arguments are resolved statically. So a method
> taking two supertype-declared arguments can't select an overload based on both runtime types. The
> visitor pattern simulates it with two chained virtual calls.
