# L-006 · How data physically moves

## What the Internet is

Not a thing. **A network of networks that agreed on a common protocol.**

There is no central Internet computer, no master routing table, no one in charge. There are hundreds
of thousands of independently operated networks — **Autonomous Systems** — that agreed to speak IP
to each other and to exchange routing information.

```
   Your laptop
       │  WiFi
   Home router  ──────────  (your local network, 192.168.1.0/24)
       │
   ISP access network        (Airtel / Jio / ACT — AS number, e.g. AS9498)
       │
   ISP core / regional
       │
   ┌───┴─────────────────────────────────────┐
   │  Internet Exchange Point (IXP)          │   ← where networks physically meet
   │  e.g. NIXI Chennai, DE-CIX Mumbai       │      and hand traffic to each other
   └───┬─────────────────────────────────────┘
       │
   Transit provider / submarine cable         (Tata, Bharti, Level3)
       │
   Destination ISP / cloud provider AS        (AWS = AS16509)
       │
   Data centre network
       │
   The server
```

Every one of those hops is a **separate company with separate equipment**, cooperating because a
protocol says how. That's the actual achievement of the internet — not the technology, the agreement.

## Packets

Your data does not travel as a stream. It's chopped into **packets**.

```
   "GET /index.html HTTP/1.1\r\nHost: ..."     (say 3,000 bytes)
                    │
                    ▼  split by TCP
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ seg 1    │ │ seg 2    │ │ seg 3    │      each ≤ MSS (~1460 bytes)
   │ 1460 B   │ │ 1460 B   │ │ 80 B     │
   └──────────┘ └──────────┘ └──────────┘
        │            │            │
        ▼            ▼            ▼   each wrapped in TCP + IP headers (Day 001, C-01)
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ packet 1 │ │ packet 2 │ │ packet 3 │     → onto the wire, independently routed
   └──────────┘ └──────────┘ └──────────┘
```

**MTU** (Maximum Transmission Unit) is the largest frame a link can carry — 1500 bytes on Ethernet.
Subtract 20 bytes IP header + 20 bytes TCP header and you get **MSS ≈ 1460 bytes** of actual payload.

### Why packets instead of a continuous stream

1. **Sharing.** If one machine sent a 4 GB file as one unit, it would monopolise every link on the
   path for minutes. Packets interleave, so thousands of conversations share a link.
2. **Failure isolation.** Lose one packet, resend one packet — not the whole transfer.
3. **Independent routing.** Each packet can take a different path. If a link dies mid-transfer,
   later packets route around it and the connection survives.
4. **No setup in the network.** Routers hold no per-connection state. That's what makes the internet
   scale to billions of simultaneous conversations — the state lives at the endpoints, not in the
   middle.

**That last point is the deepest design decision on the internet**, and it has a name: the
*end-to-end principle*. Intelligence at the edges, dumb fast pipes in the middle. It's why the
internet could grow from four nodes to billions without redesigning the core.

It's also the same instinct as stateless HTTP (Day 016) and stateless services scaling horizontally
(Day 324). Same idea, three layers apart.

## Routers

A router is a computer with multiple network interfaces and one job: **look at a packet's
destination IP, consult the routing table, forward it out the right interface** (Day 004, C-03).

Per packet, at line rate, millions of times a second.

```
   packet arrives on eth0, destination 142.250.183.100
        │
        ▼
   longest prefix match against routing table
        │
        ├─ 192.168.1.0/24  → local          no match
        ├─ 10.0.0.0/8      → 192.168.1.254  no match
        └─ 0.0.0.0/0       → 192.168.1.1    MATCH (default route)
        │
        ▼
   decrement TTL (64 → 63)
   recompute IP header checksum
   rebuild the layer-2 frame with the next hop's MAC (ARP, Day 002)
        │
        ▼
   forward out the interface toward 192.168.1.1
```

**Three things to notice:**

1. **The router rebuilds the Ethernet frame every hop.** The IP packet survives end to end; the
   layer-2 frame is destroyed and recreated at each hop. This is why MAC addresses are local-only
   (Day 002) — the MAC in the frame you sent is gone after the first hop.
2. **TTL decrements every hop.** Starts at 64 (Linux) or 128 (Windows). Hits zero → packet dropped,
   ICMP "time exceeded" sent back. That's the loop-prevention mechanism, and it's what `traceroute`
   exploits.
3. **The router never looks above layer 3.** It doesn't parse TCP, doesn't know about HTTP, doesn't
   care that your payload is encrypted. This is exactly why HTTPS routes fine (Day 001, C-01).

## BGP — how routes are discovered

Routers don't guess. Autonomous Systems tell each other which IP ranges they can reach, using
**BGP** (Border Gateway Protocol).

> "I am AS16509 (Amazon). I can reach 52.0.0.0/8."

Neighbouring ASes propagate that, appending themselves to the path. Every router builds a picture of
which neighbour gets it closest to any destination.

**BGP runs on trust and is famously fragile.** If an AS announces a route it doesn't own, traffic is
misdirected — a *BGP hijack*. It has taken down large parts of the internet by accident more than
once (Pakistan Telecom accidentally blackholing YouTube globally in 2008; a Level3 misconfiguration
in 2017). Understanding this is a strong senior-level signal in a system design conversation
(Stage 9).

## The physical layer, honestly

- **Last mile** — WiFi (radio), fibre, or 4G/5G to your ISP
- **Metro/regional** — fibre optic, light pulses in glass
- **Long haul** — fibre along rail lines and highways
- **Intercontinental** — **submarine cables.** ~99% of international traffic. Physical cables on the
  ocean floor. India connects via cables landing at Chennai, Mumbai, Cochin.

**Satellites are not the internet's backbone.** Geostationary satellites add ~500 ms RTT from the
altitude alone. Starlink's low orbit helps, but glass on the seabed still wins for bulk traffic.

### Speed of light is your budget

Light in fibre: ~200,000 km/s (slower than in vacuum, because glass).

Chennai → Oregon is ~14,000 km. One way: 70 ms. Round trip: **140 ms minimum**, physics, before any
router queuing, before the TCP handshake, before TLS.

```
  TCP handshake (1 RTT)             140 ms
  TLS 1.3 handshake (1 RTT)         140 ms
  HTTP request + response (1 RTT)   140 ms
                                    ───────
  First byte, absolute best case    420 ms
```

**You cannot optimise your way past this.** No amount of code makes light faster. The only fixes are
architectural, and now you know why each exists:

- **CDNs** — put the content physically closer (Day 327)
- **Connection reuse / keep-alive** — pay the handshake once (Day 011)
- **Connection pooling** — never pay it per query (Day 197)
- **Choosing an AWS region near your users** (Day 380)
- **Reducing round trips** — HTTP/2 multiplexing, batching (Day 011)

> **Interview framing:** when someone asks "how would you make this faster", latency questions
> almost always resolve to "reduce round trips or shorten the distance". That's a much better
> starting point than "add a cache" said reflexively.

## Type this yourself

```bash
tracert google.com          # Windows
traceroute google.com       # Linux/Mac
```

**Read the output carefully.** Each line is one router that decremented TTL to zero and replied. You
are watching the path being discovered hop by hop.

- The first hop is your router (192.168.x.1)
- The next few are your ISP
- Then names appear with city codes — `chn`, `bom`, `sin`, `lax`. **You can read the geography.**
- Watch the latency jump when it crosses a continent — that's the submarine cable

```bash
ping google.com                    # note the RTT and the TTL in the reply
ping -n 20 google.com              # Windows: 20 pings, watch the variance
```

**RTT variance is queuing.** The minimum is close to physics; anything above it is a router holding
your packet in a buffer behind other traffic.

Now try:

```bash
tracert aws.amazon.com
tracert bbc.co.uk
```

Compare the hop count and where the latency jumps. **Write the three traceroutes in your notes with
the point at which each left India.**

## Common mistakes

| Mistake | Correction |
|---|---|
| "The internet is the web" | The web (HTTP) is one application on the internet. Email, DNS, SSH, games are others. |
| Thinking there's a central authority | It's independently operated networks agreeing on protocols. ICANN coordinates names and numbers; nobody runs the routing. |
| Assuming all packets take the same route | Each is routed independently and may take different paths. Reordering is normal — TCP fixes it (Day 005). |
| "Satellites carry the internet" | ~99% of intercontinental traffic is submarine fibre. |
| Ignoring the speed of light in latency estimates | 140 ms Chennai↔Oregon RTT is a floor set by physics. Design around it. |
| Thinking a router reads your HTTP | It reads the IP header only. That's why encryption doesn't break routing. |

## Interview questions

**Q: What happens to a packet at each router hop?**
> The router does a longest-prefix-match lookup on the destination IP, decrements TTL, recomputes the
> header checksum, resolves the next hop's MAC via ARP, rebuilds the layer-2 frame, and forwards. The
> IP packet persists end to end; the link-layer frame is rebuilt at every hop.

**Q: Why is data sent as packets?**
> Link sharing, failure isolation, independent routing around failures, and — most importantly — it
> keeps per-connection state out of the network. Routers are stateless with respect to connections,
> which is what lets the internet scale.

**Q: What is TTL and why does it exist?**
> A hop counter in the IP header, decremented at each router and dropped at zero. It prevents packets
> circulating forever when routing tables are temporarily inconsistent. `traceroute` sends
> deliberately low TTLs so each hop reveals itself via an ICMP time-exceeded reply.

**Q: What is BGP and why is it a risk?**
> The protocol by which Autonomous Systems advertise which IP prefixes they can reach. It operates on
> trust, so a network advertising prefixes it doesn't own can misdirect global traffic — a BGP hijack.

**Q: What limits how fast a request to a server on another continent can be?**
> The speed of light in fibre. Chennai to the US west coast is ~140 ms round trip minimum. With TCP
> and TLS handshakes that's ~420 ms to first byte before any server work. Only CDNs, connection reuse
> and fewer round trips help.
