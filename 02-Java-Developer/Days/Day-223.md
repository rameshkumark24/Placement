# Day 223 ⚛️

**J-223** · ⚛️ **React's actual model** — ⭐⭐ UI as a function of state, and what a re-render is not

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a re-render is React calling your function again to get a description of
> the screen, comparing it to the last description, and touching only the DOM nodes that differ — so
> "re-render" costs a function call and a diff, not a repaint, and almost every React rule you will
> meet is a consequence of your function being called many times.**
>
> Today: the loop, ⭐ JSX as function calls, ⭐⭐ what actually triggers a render, and purity.

---

# Part 1 — The loop

```
⭐⭐ THE ENTIRE MODEL, AND THERE IS NO MORE THAN THIS

⭐   ① state changes
⭐   ② ⭐ REACT CALLS YOUR COMPONENT FUNCTION AGAIN
⭐   ③ it returns a DESCRIPTION of the UI (plain objects — "elements")
⭐   ④ ⭐⭐ REACT DIFFS that description against the previous one
⭐   ⑤ ⭐ it applies the MINIMAL DOM CHANGES (this is the expensive bit)
⭐   ⑥ the browser paints

⭐   ⇒ ⭐⭐ YOUR FUNCTION IS NOT "DRAWING". IT IS ANSWERING A QUESTION:
⭐     "GIVEN THIS STATE, WHAT SHOULD THE SCREEN LOOK LIKE?"
⭐     ⭐ It will be asked A LOT, and must answer the same way every
⭐       time for the same state. THAT is the purity rule.
```

| ⭐ Myth | Reality |
|---|---|
| *"Re-render = the DOM is rebuilt"* | ⭐⭐ No. Your function runs and a diff happens. **The DOM is touched only where the description changed.** |
| *"Re-renders are expensive"* | ⭐ Usually microseconds. **Chasing them before measuring is the #1 wasted effort** (Day 232) |
| *"Re-render = the component remounts"* | ⭐⭐ **No** — state survives a re-render. It dies only on *unmount*, or a changed `key` (Day 230) |

> ⭐ **The closest thing you know is a `toString()` that builds a whole view object, plus a differ.**
> Not a servlet writing to a response, and not Swing mutating widgets — **a pure function returning a
> value, called repeatedly.**

# Part 2 — JSX is function calls

```jsx
const el = <Button size="lg" onClick={f}>Save</Button>;
// ⭐ compiles to roughly:
const el = jsx(Button, { size: "lg", onClick: f, children: "Save" });
// ⇒ ⭐⭐ A PLAIN OBJECT. Not DOM. Not HTML. A description.
```

| ⭐ Rule | Why |
|---|---|
| **Components are capitalised** | ⭐⭐ `<button>` = the DOM tag; `<Button>` = your function. Lowercase yours and React renders an unknown HTML element **silently**. |
| **`className`, not `class`** | `class` is reserved. Also `htmlFor`, camelCase `onChange`. |
| **One parent** | Return `<>…</>` — a fragment adds no DOM node |
| **`{}` embeds an expression** | ⭐ An *expression*, not a statement — like a lambda body without braces. No `if` inside JSX |

```jsx
{isLoading && <Spinner />}                    // ⭐ conditional
{items.length === 0 ? <Empty /> : <List/>}    // ⭐ either/or

{count && <Badge n={count} />}
// ⭐⭐ THE BUG: count === 0 renders the literal "0" on screen,
//    because 0 is falsy AND a valid React child.
//    ✅ {count > 0 && <Badge n={count} />}
```

> ⭐ **That `0` bug is Day 215's falsy trap** in a place it renders visibly. `&&` returns the *left*
> value when falsy, and React prints `0` while skipping `false`, `null` and `undefined`. **In Java `0
> && x` would not even compile** — this is the cost of truthiness.

# Part 3 — ⭐⭐ What actually triggers a render

```
⭐⭐ EXACTLY THREE THINGS

⭐   ① ⭐ A setState call on this component  (with a CHANGED value)
⭐   ② ⭐⭐ THE PARENT RE-RENDERED ⇒ children re-render TOO, BY DEFAULT,
⭐      EVEN IF THEIR PROPS ARE IDENTICAL.
⭐   ③ ⭐ A context value this component consumes changed

⭐⭐ NOT ON THE LIST — none of these cause a render:
⭐   · mutating an object or array in place  ⇒ ⭐⭐ THE SILENT BUG
⭐   · changing a plain variable inside the component
⭐   · a ref's .current changing
⭐   · time passing, a fetch resolving without setState
```

```jsx
// ❌ nothing happens — same array reference, so React sees no change
items.push(newItem);
setItems(items);              // ⭐⭐ Object.is(prev, next) is TRUE ⇒ BAIL OUT

// ✅ new reference
setItems([...items, newItem]);
```

> ⭐⭐ **React compares with `Object.is`, which for objects is reference identity — and there is no
> `equals()` to override** (Day 215). This is exactly why immutable updates are not a style
> preference: **they are the mechanism by which React can tell that anything happened at all.** If you
> have used `List.copyOf` and records for defensive copying, this is that instinct made load-bearing.

```jsx
// ⭐⭐ the functional update — use it whenever the next value depends on the previous
setCount(c => c + 1);
setCount(c => c + 1);      // ⇒ +2 ✅

setCount(count + 1);
setCount(count + 1);       // ⇒ ⭐⭐ +1 ONLY. `count` is EFFECTIVELY FINAL
                           //    within this render. Both lines read the same value.
```

> ⭐ **`count` is captured for that render, like an effectively-final local captured by a lambda.** You
> already know that a lambda closes over the *value*, not the variable — same rule, and it is the
> stale-closure bug on Day 226 in miniature.

# Part 4 — Purity, and why StrictMode double-invokes

```jsx
// ❌ impure — a side effect during render
function Bad({ id }) {
  logView(id);                 // ⭐⭐ fires TWICE in dev, unpredictably in prod
  return <div/>;
}

// ❌ impure — mutating a prop
function Bad2({ user }) { user.name = user.name.trim(); return <p>{user.name}</p>; }

// ✅ pure — same input, same output, no outside changes
function Good({ user }) { return <p>{user.name.trim()}</p>; }
```

```
⭐⭐ WHY STRICTMODE CALLS YOUR COMPONENT TWICE IN DEV

⭐   NOT a bug and NOT something to disable. ⭐ It is a DETECTOR:
⭐   ⇒ if calling your function twice changes the result or the world,
⭐     ⭐⭐ YOUR COMPONENT IS IMPURE and React's scheduler is allowed
⭐     to break it — it may render, discard, and render again.
⭐   ⇒ ⭐ "my API is called twice in dev" is StrictMode CORRECTLY
⭐     telling you the fetch does not belong there. Day 226/227.
```

| ⭐ Allowed during render | ⭐⭐ Never during render |
|---|---|
| Read props/state, compute, return JSX | `fetch`, `setState`, `localStorage`, DOM reads/writes, mutating props, `Math.random()` into output |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "explain React's model."**

Give the loop in one breath, then correct the usual misunderstanding. **State changes, React calls my
component function again, it returns a description of the UI as plain objects, React diffs that against
the previous description and touches only the DOM nodes that differ. So a re-render costs a function
call and a diff, not a repaint — which is why chasing re-renders before measuring is the most common
wasted effort in React.**

Then the consequence that explains the rules. **My function gets called many times and must answer the
same way every time for the same state. That's the purity rule, and everything else falls out of it.
StrictMode double-invoking in development isn't noise to disable — it's a detector: if calling my
function twice changes the result or the world, my component is impure and React's scheduler is allowed
to break it.**

Close on the mechanism, tying it to what you already know. **React compares with reference identity and
there's no `equals()` to override, so mutating an array and setting it back is a no-op — React bails
out. Immutability isn't a style preference here, it's the mechanism by which React can tell anything
happened. And `setCount(count + 1)` twice only adds one because `count` is effectively final within
that render — it's lambda capture: the closure took the value, not the variable.**
