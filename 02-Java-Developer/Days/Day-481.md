# Day 481

**L-481** · System design round 1 — a URL shortener, and the scoring rubric

**Time:** 3 hrs (45 min round + 2 hrs review) · **Mode:** DRILL · **⭐ SD round 1 of 5**

> **⭐⭐ System design rounds are scored on structure before content. A candidate who covers six things in
> a deliberate order beats one who covers nine in the order they occurred to them — because the second
> one is indistinguishable from someone who read a list.**
>
> Today: the 45-minute framework as a scored round, **the shortener done properly including the
> estimation that decides the design**, and the rubric you will reuse for all five rounds.

---

# Part 1 — ⭐⭐ The framework, as a clock

```
⭐ 0–5    ⭐⭐ REQUIREMENTS — functional, non-functional, ⭐⭐ AND EXPLICITLY OUT OF SCOPE
⭐ 5–10   ⭐⭐ ESTIMATION — ⭐⭐ QPS, storage, bandwidth. ⭐ Round aggressively. Say the assumptions.
⭐ 10–15  ⭐ API and the data model
⭐ 15–25  ⭐⭐ THE HIGH-LEVEL DESIGN — boxes, arrows, and the request path
⭐ 25–38  ⭐⭐ DEEP DIVE on the one or two things that are actually hard
⭐ 38–43  ⭐⭐ FAILURE, SCALE, TRADE-OFFS — ⭐ what breaks, and what you would do at 10×
⭐ 43–45  ⭐ what you left out, and your questions
```

| ⭐⭐ Three rules that carry the round | |
|---|---|
| ⭐⭐ **Say the block you are entering** | ⭐⭐ *"I'll do estimation next"* — **it makes you legible, which is the score** |
| ⭐⭐ **Let the numbers drive the design** | ⭐⭐ estimation that does not change a decision is theatre |
| ⭐⭐ **Ask which direction to go deep** | ⭐ *"I can go deep on the ID scheme or on the read path — which is more interesting to you?"* |

# Part 2 — ⭐⭐ The round: design a URL shortener

## ⭐ 0–5 — requirements

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| ⭐ shorten a long URL → short code | ⭐⭐ **read-heavy: ~100:1 reads to writes** |
| ⭐ redirect a short code → original | ⭐⭐ **redirect latency is the product** — target p99 < 50 ms |
| ⭐ optional custom alias | ⭐ high availability; a dead link is a broken promise |
| ⭐ optional expiry | ⭐ links must be **hard to guess** if privacy matters |
| ⭐⭐ **Out of scope:** analytics dashboards, user accounts, spam detection | ⭐ say it |

## ⭐⭐ 5–10 — estimation that changes the design

```
⭐   100M new URLs/day  ⇒ ⭐ 100M / 86,400 ≈ ⭐⭐ ~1,200 writes/sec
⭐   ⭐⭐ reads at 100:1  ⇒ ⭐⭐ ~120,000 reads/sec  ⭐ (peak ~2× ⇒ 240k)
⭐
⭐ ⭐ STORAGE: 500 bytes/record × 100M/day × 365 × 5 years ≈ ⭐⭐ ~90 TB
⭐ ⭐ KEYSPACE: base62, 7 chars ⇒ 62⁷ ≈ ⭐⭐ 3.5 TRILLION ⇒ ⭐ 7 characters is enough for a century
⭐
⭐ ⭐⭐ WHAT THE NUMBERS DECIDED — say this explicitly:
⭐   ⭐⭐ 120k reads/sec ⇒ ⭐⭐ this is a CACHE problem, not a database problem
⭐   ⭐ 90 TB ⇒ ⭐ it does not fit on one machine ⇒ partitioning is required
⭐   ⭐ 1,200 writes/sec ⇒ ⭐⭐ modest — a single write path is fine
```

> **⭐ That four-line "what the numbers decided" block is the highest-value thirty seconds in the round.**
> Most candidates compute numbers and then design as if they had not. **Explicitly converting each
> estimate into a decision is what estimation is for.**

## ⭐ 10–15 — API and data model

```
⭐ POST /urls   {url, alias?, expiresAt?}  → ⭐ 201 {shortUrl}
⭐ GET  /{code}                             → ⭐⭐ 301 or 302 — AND THIS IS A REAL DECISION:
⭐    ⭐⭐ 301 permanent ⇒ browsers cache it ⇒ ⭐⭐ fewer requests, ⭐⭐ NO ANALYTICS, cannot change target
⭐    ⭐⭐ 302 temporary ⇒ every click hits you ⇒ ⭐ analytics and editability, ⭐⭐ more load
⭐    ⇒ ⭐⭐ "302 if clicks matter commercially, 301 if pure redirect efficiency does." ⭐ Ask.
```

| ⭐ Table | |
|---|---|
| `urls(code PK, long_url, owner_id, created_at, expires_at)` | ⭐ partition by `code` |
| ⭐ Why `code` as the partition key | ⭐⭐ **every read is by code — the access pattern decides the key** (Day 329) |

## ⭐⭐ 15–25 — the ID scheme, which is the actual design problem

| ⭐ Approach | ⭐ Verdict |
|---|---|
| ⭐ **Hash the URL, take 7 chars** | ⭐⭐ **collisions** ⇒ you must check-and-retry ⇒ a read before every write |
| ⭐ **Random 7 chars** | ⭐ same collision problem, but no dedup of identical URLs |
| ⭐⭐ **A global counter, base62-encoded** | ⭐⭐ **no collisions ever** — but the counter is a single point of contention |
| ⭐⭐ **RANGE-ALLOCATED COUNTER** | ⭐⭐ **each app server claims a block of 10,000 ids, then hands them out locally** |
| ⭐ Snowflake-style | ⭐ works, but ids are long and time-ordered (guessable) |

```
⭐⭐ THE RANGE ALLOCATION ANSWER, which is the one to give:
⭐   ⭐ a key-generation service holds a counter; ⭐⭐ each app instance atomically claims [n, n+10000)
⭐   ⇒ ⭐⭐ ONE coordination call per 10,000 ids ⇒ ⭐ contention is effectively zero
⭐   ⇒ ⭐⭐ NO collisions, NO read-before-write, ⭐ and it survives the counter service being briefly down
⭐   ⚠️ ⭐ Cost: ⭐⭐ ids are LOST when an instance dies mid-block — ⭐ and that is fine, the keyspace is 3.5 trillion
⭐   ⚠️ ⭐⭐ And they are SEQUENTIAL, therefore ENUMERABLE ⇒ ⭐⭐ if privacy matters, scramble within the block.
```

⚠️ **Volunteering the enumerability problem is a strong move.** Sequential base62 codes mean anyone can
walk your entire link set. **"If links can be private, I'd permute the counter with a reversible bijection
before encoding — the ids stay collision-free and stop being guessable"** is a complete answer to a
problem most candidates never notice.

# Part 3 — ⭐⭐ Deep dive: the read path (25–38)

```
⭐   client → ⭐⭐ CDN/edge (for hot codes) → ⭐ LB → ⭐ stateless app → ⭐⭐ Redis → ⭐ partitioned DB
⭐
⭐ ⭐⭐ 120k reads/sec against a database is the wrong shape. ⭐ The distribution saves you:
⭐   ⭐⭐ link popularity is a power law ⇒ ⭐⭐ ~20% of codes serve ~80% of traffic
⭐   ⇒ ⭐⭐ a cache holding the hot set gets a very high hit rate on a small memory footprint
⭐   ⇒ ⭐ cache-aside, long TTLs (⭐⭐ mappings are immutable, so staleness is not a concern)
⭐   ⇒ ⭐⭐ negative caching for codes that do not exist — ⭐ otherwise a scanner drives 100% misses to the DB
```

| ⭐ The failure question, answered concretely | |
|---|---|
| ⭐⭐ **Cache dies** | ⭐⭐ every read hits the database — **is it sized for 120k/sec? No.** So: single-flight, a bulkhead, and jittered TTLs (Day 388) |
| ⭐ A database partition dies | ⭐ that slice of codes 404s; replicas + failover |
| ⭐⭐ **Expiry** | ⭐⭐ **lazy on read** rather than a scan — a background cleaner only reclaims storage |
| ⭐ Global users | ⭐⭐ mappings are immutable ⇒ **read replicas per region are safe** — a rare case where geo-replication is easy |

> **⭐ The immutability observation is the best one in this problem: a short code's mapping never changes,
> which means caching, replication and CDN edge storage are all trivially correct.** **Say why a design
> is easy, not just what it is** — recognising that the data model removed a class of problem is the
> senior read.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Drawing boxes at minute two** | ⭐⭐ you designed before you knew the shape |
| ⭐⭐ **Estimation that changes no decision** | ⭐⭐ theatre; the numbers exist to decide things |
| ⭐ Not announcing blocks | ⭐⭐ structure is the score, and it must be audible |
| ⭐ Hashing for id generation without mentioning collisions | ⭐ read-before-write on every request |
| ⭐ A single global counter with no range allocation | ⭐⭐ a contention point on the write path |
| ⭐⭐ **Not noticing sequential ids are enumerable** | ⭐⭐ the privacy hole nobody spots |
| ⭐ "Add Redis" with no hit-rate reasoning | ⭐⭐ the power law is the actual argument |
| ⭐ No negative caching | ⭐⭐ a scanner drives every miss to the database |
| ⭐ 301 vs 302 chosen without stating the trade | ⭐ it decides whether analytics exist at all |
| ⭐⭐ **Not answering "what if the cache dies?"** | ⭐⭐ the database is not sized for the full read load |
| ⭐ Going deep on the easy part | ⭐⭐ CRUD depth instead of the id scheme |
| Trying to cover everything | breadth without depth reads as a list |

## Interview questions

**Q: How do you structure a system design round?**
Six blocks in a fixed order, announced as I enter them: requirements including what I am explicitly not
building, estimation, API and data model, high-level design, a deep dive on the genuinely hard part, then
failure and trade-offs. Announcing the blocks matters as much as the content, because structure is what
is being scored and it has to be audible. And I ask which direction to go deep, because forty-five
minutes buys depth on one or two things and the interviewer knows which one they want to hear about.

**Q: Your estimation says 120,000 reads per second. So what?**
That is exactly the right question, and converting each number into a decision is the point of estimating
at all. A hundred and twenty thousand reads a second says this is a caching problem rather than a
database problem. Ninety terabytes over five years says it does not fit on one machine, so partitioning
is required rather than optional. And twelve hundred writes a second says the write path is modest and
does not need anything clever. Estimation that does not change a decision is theatre.

**Q: How do you generate the short codes?**
Range-allocated counters. A key generation service holds a counter and each application instance
atomically claims a block of ten thousand ids, then hands them out locally — so there is one coordination
call per ten thousand ids, no collisions ever, and no read-before-write. Hashing the URL means collisions
and therefore a check on every write; a single shared counter is a contention point on the write path.
The cost of range allocation is that ids are lost when an instance dies mid-block, which is irrelevant
against a keyspace of three and a half trillion. The real caveat is that the ids are sequential and
therefore enumerable — so if links can be private, I would permute the counter with a reversible bijection
before base62 encoding.

**Q: Why is caching so effective here?**
Two reasons, and the second is the interesting one. Link popularity follows a power law, so a small
fraction of codes serve most of the traffic and a modest cache gets a very high hit rate. And the mapping
from code to URL is immutable, so there is no staleness concern at all — TTLs can be long, replicas can
be regional, and edge caching is trivially correct. That immutability removes an entire class of problem,
and noticing that the data model made the design easy is worth saying out loud rather than just
benefiting from it.

**Q: What happens if the cache goes down?**
Every read goes to the database, which is not sized for a hundred and twenty thousand requests per second
— so the honest answer is that it would fall over without protection. The defences are single-flight so
one loader per code hits the database, a bounded connection pool acting as a bulkhead, and jittered TTLs
so the hot set does not expire together. I would also add negative caching, because otherwise a scanner
walking random codes produces a hundred percent miss rate and drives every one of those to the database.

## Mini task

1. ⭐⭐ Run the **full 45-minute round**, recorded, with the clock visible and blocks announced aloud.
2. ⭐⭐ Do the estimation and write the **"what the numbers decided"** block. Four lines.
3. ⭐ Justify the partition key **from the access pattern**, out loud.
4. ⭐⭐ Compare all **five id schemes** and defend range allocation, including its two costs.
5. ⭐ Design the **permutation** that makes sequential ids non-enumerable.
6. ⭐⭐ Compute the **cache hit rate** needed to keep the database under 5,000 reads/sec. Work backwards
   from that to the memory required.
7. ⭐ State the **301 vs 302 trade** in both directions and pick one with a reason.
8. ⭐⭐ Answer **"what if the cache dies?"** with three concrete defences.
9. ⭐ Add **negative caching** and explain the scanner scenario.
10. ⭐⭐ Score with the 12-row rubric. Rows 1, 2, 5, 7, 9 and 11 decide it.

## 🎙️ Articulation drill

**Two minutes:** the estimation block, alone, out loud.

**⭐ "A hundred million new links a day is about twelve hundred writes a second. Reads are roughly a
hundred to one, so a hundred and twenty thousand a second, call it two hundred and forty at peak. At five
hundred bytes a record over five years that is about ninety terabytes. Base sixty-two with seven
characters is three and a half trillion codes, so seven characters lasts effectively forever."**

**⭐ Then the block that most candidates skip, and the reason to do estimation at all: "So the numbers say
three things. A hundred and twenty thousand reads a second means this is a caching problem, not a
database problem. Ninety terabytes means it doesn't fit on one machine, so partitioning is required. And
twelve hundred writes a second means the write path is modest and I shouldn't spend the round on it."**
