**L-205** · Persistence — RDB, AOF, and what "durable" means for Redis

# Part 1 — RDB: point-in-time snapshots

```
save 900 1        # ⭐ snapshot if ≥1 key changed in 900s
save 300 10
save 60 10000
dbfilename dump.rdb
rdbcompression yes
```

```
BGSAVE            ⭐ fork a child; the parent keeps serving
SAVE              ⭐⭐ NEVER in production — blocks the single thread until complete
LASTSAVE
```

**⭐ How `BGSAVE` works, and the fact that governs your memory sizing:**

> **⭐ Redis `fork()`s. The child writes the snapshot from its copy-on-write view of memory while the
> parent keeps serving.**

**⭐ Copy-on-write means the fork is initially free — the child shares the parent's pages.** But every
page the *parent* modifies during the save must be copied.

```
⭐ Worst case: a write-heavy instance touching most pages during a save
   → memory usage approaches 2× the dataset
```

**⭐ This is the most important operational fact about Redis persistence**, and it causes real
outages: an instance holding 8 GB on a 12 GB host runs fine until a snapshot coincides with a write
burst, memory doubles, and the OOM killer takes Redis.

```
vm.overcommit_memory = 1     # ⭐ REQUIRED — otherwise fork() fails on a large instance
```

**⭐ Redis logs a warning about this at startup and people ignore it.** Without overcommit enabled,
`fork()` fails when Redis holds more than half the host's memory, so **background saves and AOF
rewrites silently stop working** — and you discover it when you need the snapshot.

| RDB | |
|---|---|
| ✅ Compact single file, ⭐ **fast to load** | |
| ✅ Minimal impact on normal operation | |
| ✅ ⭐ Good for backups and replica seeding | |
| ❌ ⭐ **Loses everything since the last snapshot** — minutes | |
| ❌ ⭐ Fork can double memory and cause a latency spike | |

# Part 2 — AOF: an append-only command log

```
appendonly yes
appendfsync everysec          # ⭐⭐ THE decision — see below
aof-use-rdb-preamble yes      # ⭐ hybrid: RDB snapshot + AOF tail
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

**Every write command is appended to a log.** On restart, Redis replays it.

## ⭐⭐ `appendfsync` — the durability dial

| Setting | fsync | ⭐ Data loss on crash | Throughput |
|---|---|---|---|
| `always` | ⭐ every command | ⭐ **zero** | ⭐ **drastically reduced** |
| ⭐ **`everysec`** | ⭐ once per second | ⭐ **up to 1 second** | ⭐ near-full |
| `no` | OS decides | ⭐ up to 30s | full |

**⭐ `everysec` is the standard choice and the answer to give**: bounded loss of about one second, at
near-full throughput. `always` makes Redis fsync-bound, which throws away the reason you chose an
in-memory store.

**⭐ Compare Day 186's `synchronous_commit`.** The shape is identical — a durability dial trading a
bounded loss window for throughput — but PostgreSQL's *default* is the safe end and Redis's is not,
which is a fair summary of the two systems' priorities.

## ⭐ AOF rewrite — and the fork again

**The log grows forever**, so Redis periodically rewrites it as the minimal command set producing the
current state. **`BGREWRITEAOF` forks**, with the same copy-on-write memory risk as `BGSAVE`.

**⭐ `aof-use-rdb-preamble yes` is the right modern default:** the rewritten AOF begins with a compact
RDB snapshot followed by an incremental command tail. **You get RDB's fast loading and AOF's small
loss window in one file.**

| AOF | |
|---|---|
| ✅ ⭐ **At most one second of loss with `everysec`** | |
| ✅ Human-readable; a bad command can be edited out | |
| ✅ `redis-check-aof --fix` truncates a partial write | |
| ❌ ⭐ Larger file, ⭐ **slower restart** (without the RDB preamble) | |
| ❌ Rewrites fork — the same memory hazard | |

# Part 3 — ⭐ Choosing, and the honest numbers

| Use | Configuration |
|---|---|
| ⭐ **Pure cache** (rebuildable from PostgreSQL) | ⭐ **persistence OFF** — see below |
| ⭐ **Sessions** (Day 113) | ⭐ AOF `everysec` — logging everyone out is a real incident |
| Rate limiters, counters | RDB only, or nothing — losing a window is harmless |
| ⭐ **Queues, locks, anything authoritative** | ⭐ AOF `everysec` + replication — ⭐ **and reconsider Redis** |
| Analytics (HyperLogLogs) | RDB — approximate data, approximate recovery |

**⭐ Turning persistence off for a pure cache is a deliberate, correct choice**, and people hesitate
to make it. If PostgreSQL is the source of truth, an empty Redis after a restart costs you a cold
cache, not data — and you avoid the fork memory spike, the disk I/O, and the latency it causes.

**⭐ But it demands one thing: your application must survive a cold cache.** A cache that everything
depends on being warm is a stampede waiting for a restart (Day 121). **Test it by flushing Redis
under load** — if the database falls over, persistence is not your real problem.

## ⭐ The numbers, stated plainly

| Configuration | RPO |
|---|---|
| No persistence | ⭐ **everything** |
| RDB, `save 300 10` | ⭐ **up to 5 minutes** |
| AOF `everysec` | ⭐ **~1 second** |
| AOF `always` | ⭐ 0 on that node — ⭐ **but see below** |
| ⭐ **+ async replication** | ⭐ **does not improve RPO** — Day 201 |

**⭐ The last row is the one that catches people, and it is the crux of Day 207's lock argument:**

> **⭐ Redis replication is asynchronous. A failover promotes a replica that may be missing the last
> writes — even with `appendfsync always` on the master.** The master's disk was durable; the replica
> never saw the data.

**⭐ So Redis has no configuration giving RPO 0 across a failover.** `WAIT numreplicas timeout` waits
for replicas to *acknowledge receipt*, not to fsync, and it is not a consensus protocol. **Say this
plainly in an interview** — it is the honest boundary of what Redis offers, and it is exactly why
Day 207's naive lock is unsafe.

# Part 4 — Operating it

## Backups

```bash
# ⭐ the RDB file IS the backup — copy it
redis-cli BGSAVE && cp /var/lib/redis/dump.rdb /backup/dump-$(date +%F).rdb
redis-cli --rdb /backup/live-dump.rdb          # ⭐ pull a snapshot without touching the server's file
```

**⭐ Day 201's rule applies unchanged: test the restore.** Load the RDB into a scratch instance,
verify `DBSIZE` and spot-check keys, and **time it — that is your RTO.** A 20 GB RDB takes minutes to
load, during which Redis is unavailable.

## ⭐ Monitoring the things that fail silently

```
INFO persistence
rdb_last_bgsave_status:ok               ⭐⭐ ALERT if "err"
aof_last_write_status:ok                ⭐⭐ ALERT if "err"
aof_last_bgrewrite_status:ok
rdb_changes_since_last_save:14238       ⭐ how much is currently at risk
rdb_last_bgsave_time_sec:12             ⭐ how long the fork blocked
latest_fork_usec:284102                 ⭐⭐ 284ms — the whole server paused for this
```

**⭐ `rdb_last_bgsave_status:err` is the alert people never set**, and it is the one that matters
most: **saves have been silently failing** — usually because `fork()` cannot allocate — and you have
no backup at all. Everything looks healthy from the outside.

**⭐ `latest_fork_usec` is the latency you cannot see any other way.** The fork itself pauses the
single thread, and on a large instance it can be hundreds of milliseconds — a periodic latency spike
with no slow command to blame.

## ⭐ The interaction with `maxmemory` (Day 206's subject)

```
maxmemory 4gb
maxmemory-policy allkeys-lru
```

**⭐ `maxmemory` must leave room for the fork's copy-on-write overhead and for replication buffers.**
A common rule is **setting `maxmemory` to about 50–60% of the host's RAM on a persistent,
write-heavy instance** — which surprises people who set it to 90% and are then OOM-killed during a
snapshot.

## ⭐ Redis as a system of record — the honest position

**⭐ You can configure Redis to be reasonably durable. You should still rarely make it the system of
record**, and the reasons are not about `appendfsync`:

- ⭐ **No RPO-0 failover.** Async replication, no consensus.
- **No constraints, no foreign keys, no transactions with rollback** (Day 203).
- ⭐ **Everything must fit in memory** — an order of magnitude more expensive per gigabyte.
- **No point-in-time recovery** to an arbitrary second (Day 201's PITR).

**⭐ The right framing: PostgreSQL is the system of record, Redis is the fast derived layer** —
cache, sessions, counters, rate limits, queues, locks. Persistence protects you from a *restart*, not
from needing the source of truth.

**Where you genuinely need Redis-like speed with strong durability**, the answer is a different tool
— Redis Enterprise, KeyDB, DragonflyDB, or accepting the trade and designing around it.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `vm.overcommit_memory` not set | ⭐ forks fail; saves silently stop |
| ⭐ `maxmemory` at 90% of RAM with persistence | OOM-killed during a snapshot fork |
| ⭐ `SAVE` instead of `BGSAVE` | blocks the single thread |
| `appendfsync always` by reflex | fsync-bound; throws away the point of Redis |
| Persistence on for a pure cache | fork spikes and I/O for data you can rebuild |
| ⭐ Never testing a cold start | a restart becomes a stampede (Day 121) |
| ⭐ Not alerting on `rdb_last_bgsave_status` | backups silently absent |
| Ignoring `latest_fork_usec` | invisible periodic latency spikes |
| ⭐ Believing replication improves RPO | it is async — Day 207's whole argument |
| Never testing an RDB restore | Day 201's item 39 |
| Using Redis as a system of record casually | no constraints, no PITR, no RPO-0 failover |

## Interview questions

**Q: RDB or AOF?**
Usually both, with `aof-use-rdb-preamble` so the rewritten AOF starts with a compact snapshot and
appends commands after it — fast restart and a one-second loss window in one file. RDB alone loses
everything since the last snapshot, which can be minutes. AOF alone restarts slowly without the
preamble.

**Q: What does `appendfsync everysec` actually promise?**
At most about one second of writes lost if the process or host dies. `always` gives zero at a large
throughput cost; `no` leaves it to the OS and can lose tens of seconds. `everysec` is the standard
choice — bounded loss, near-full throughput.

**Q: What is the risk of a background save?**
It forks, and copy-on-write means every page the parent modifies during the save is copied — so a
write-heavy instance can approach double its memory. That is why `maxmemory` should be well under
half the host's RAM on a persistent instance, and why `vm.overcommit_memory` must be enabled or the
fork simply fails and saves stop happening silently.

**Q: Can Redis give you zero data loss?**
On a single node with `appendfsync always`, yes for a process crash. **Across a failover, no** —
replication is asynchronous, so a promoted replica may be missing the master's last writes even if
the master's disk was durable. There is no configuration that gives RPO 0 across failover, and that
is exactly why a Redis distributed lock cannot be a safety guarantee.

**Q: Would you use Redis as your primary database?**
Rarely, and not because of persistence settings. No constraints, no rollback, no point-in-time
recovery, no RPO-0 failover, and everything must fit in memory at an order of magnitude more cost per
gigabyte. PostgreSQL is the system of record; Redis is the fast derived layer.

## Mini task

1. Load 4 GB into Redis. Run `BGSAVE` under a heavy write load and **watch `used_memory_rss`
   climb.** Record the peak.
2. Check `latest_fork_usec` after that save. **Convert it to milliseconds** and consider it as a
   latency spike.
3. Disable `vm.overcommit_memory`, fill more than half the host's RAM, and **watch `BGSAVE` fail.**
   Confirm `rdb_last_bgsave_status:err` — and note nothing else looks wrong.
4. Benchmark writes with `appendfsync` set to `no`, `everysec` and `always`. **Three numbers.**
5. Kill Redis with `kill -9` under load at each setting. **Count the lost writes each time.**
6. Restart with a 4 GB AOF without the RDB preamble, then with it. **Compare load times.**
7. Set up a master and replica with `appendfsync always`. Write, kill the master immediately, promote
   the replica. **Find the missing writes.** That experiment is Day 207's premise.
8. Copy an RDB to a fresh instance. Verify `DBSIZE` and **time the load. That is your RTO.**
9. Turn persistence off entirely and `FLUSHALL` under production-like load. **Watch what happens to
   your database.**
10. Set `maxmemory` to 90% of the host and force a save under write load. Observe the OOM killer.

## 🎙️ Articulation drill

Two minutes: **"How durable is Redis?"**

Give numbers, not adjectives: RDB loses up to the snapshot interval, AOF `everysec` loses about a
second, `always` loses nothing on that node at a large throughput cost. Then the boundary that
matters most — replication is asynchronous, so no configuration gives zero loss across a failover,
and a promoted replica can be missing writes the master had already fsynced. Close on the operational
half: the fork can double memory, `vm.overcommit_memory` must be on or saves silently stop, and the
two `INFO` status fields are the alerts nobody sets.
