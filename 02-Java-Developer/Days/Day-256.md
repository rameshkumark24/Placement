# Day 256 🏗️

**P-256** · The service layer — orchestration, transactions, and what does not belong here

**Time:** 3 hrs · **Mode:** BUILD

> Day 254 put the rules in the domain. **The service layer's job is therefore narrower than most
> people make it**: load, delegate, persist, and decide the transaction boundary.
>
> **⭐ If your service methods are long, the domain is anaemic** — the logic that should be enforcing
> invariants in the entity has leaked into a place where every caller must remember to call it.

---

# Part 1 — ⭐ What a service method actually does

> **⭐ A service method: opens a transaction, loads the aggregate, calls a domain method, persists,
> and maps the result. Anything else is either domain logic in the wrong place or a controller
> concern that leaked down.**

```
⭐ 1. @Transactional              — the boundary is a business decision (Day 164)
⭐ 2. Load the aggregate           — scoped by owner/tenant in the query (Day 255)
⭐ 3. Call the domain method       — booking.cancel(now, actor) — the RULES ARE THERE
⭐ 4. Rely on dirty checking       — no explicit save() needed (Day 162)
⭐ 5. Map to a response DTO        — the entity never leaves (Day 147)
```

**⭐ Step 3 is the whole design.** The service does not check whether cancellation is allowed — the
domain does. That is what makes the rule apply identically when the caller is a scheduled job, a
Kafka consumer or an admin CLI.

## ⭐ The four things that belong in a service and nowhere else

| Concern | Why here |
|---|---|
| ⭐ **The transaction boundary** | "these succeed or fail together" is a business statement |
| ⭐ **Orchestration across aggregates** | the domain owns one aggregate; coordination is above it |
| ⭐ **Calls to other systems** | ⭐ and therefore the decision of what is inside vs outside the transaction |
| ⭐ **Authorization that needs loaded state** | Day 174 — record-level, in the service |

## ⭐ The five things that must not be here

| Not here | Where it belongs |
|---|---|
| ⭐ Business rules and guards | ⭐ the domain (Day 254) |
| HTTP concerns — status codes, headers | the controller (Day 146) |
| ⭐ SQL and fetch strategy | the repository (Day 255) |
| ⭐ Entities in the signature | ⭐ services take and return DTOs (Day 147) |
| Framework types — `HttpServletRequest` | the web layer |

**⭐ The fourth is the one people compromise on**, and it erodes fast: once a service returns an
entity, the controller imports the entity, and Day 147's boundary is gone within a month.

# Part 2 — ⭐ Transaction boundaries, decided deliberately

**⭐ The question for every service method: what must be atomic with what?**

```
⭐ Atomic together:  the booking row + the participants + the outbox entry
⭐ NOT atomic:       the booking + the confirmation email
                     the booking + the payment authorisation
```

**⭐ Day 156's rule, which will now bite you for the first time:**

> **⭐ No HTTP calls, no message publishing, no file I/O inside a transaction.**

```
❌ @Transactional
   save(booking); paymentClient.authorise(booking);   ⭐ 800ms holding a connection
                                                      ⭐ and an unrollbackable side effect

⭐ Correct:
   tx1: create the booking as PENDING + write an outbox entry
   (no transaction) — the slow work happens here
   tx2: mark it CONFIRMED
```

**⭐ Two short transactions with the slow work between them**, and the correctness gap between them is
closed by Day 124's outbox and Day 123's idempotency key. **This is the single most important
structural decision in the service layer**, and it is where the "why did you do it that way?"
question has the best possible answer.

## ⭐ Propagation, used sparingly

| | |
|---|---|
| ⭐ `REQUIRED` | ⭐ **the default, and correct ~95% of the time** |
| ⭐ `REQUIRES_NEW` | ⭐ only when the inner work must survive the outer rollback — ⭐ **and it holds a second connection** (Day 164) |
| `MANDATORY` | ⭐ on internal methods that must never run standalone — underused |

**⭐ If you reach for `REQUIRES_NEW`, write down why in a comment**, because Day 164's pool deadlock
is real: at concurrency equal to the pool size, every request holds one connection and waits for a
second.

## ⭐ The three failure modes to avoid from the first service

| Failure | Defence |
|---|---|
| ⭐ **Self-invocation** | ⭐ `this.method()` bypasses the proxy — split the bean (Day 164) |
| ⭐ **Catching inside the transaction** | ⭐ caught means **committed** — a half-completed operation |
| ⭐ **Checked exception, no `rollbackFor`** | ⭐ partial commit — set `rollbackFor = Exception.class` globally |

**⭐ Verify the first one today** rather than trusting it:

```
⭐ logging.level.org.springframework.transaction.interceptor: TRACE
```

**Absence of a transaction line is the evidence** (Day 137, Day 164).

# Part 3 — ⭐ Authorization in the service, and the shape that removes it

**Day 174: URL rules answer reachability; the service answers ownership.**

```
⭐ Preferred:  the query is scoped   → findByPublicIdAndOwnerId(...)   ⭐ IDOR impossible
⭐ Otherwise:  @PreAuthorize with a guard bean, in the SERVICE
```

**⭐ Always prefer the scoped query.** A missing annotation is a vulnerability; a missing `WHERE`
clause is a query that returns nothing. **Day 147's principle applied to authorization: make the
attack unrepresentable rather than blocked.**

**⭐ And the checks live in the service, not the controller** (Day 174), because the scheduled job and
the message consumer never pass through a controller. **The fair counter-argument — an internal job
legitimately acting without a user — is handled explicitly** with a system principal or a separate
documented method, not by moving the check upward and hoping.

**⭐ Write the negative test as you write the method:**

```
⭐ Alice cannot cancel Bob's booking          → 404 (not 403 — Day 251)
⭐ A USER cannot perform an ADMIN transition  → 403
```

**Day 169's point: an authorization bug returns 200 to the wrong person.** It throws nothing, logs
nothing, and passes every positive test. **The negative test is the only mechanism that notices.**

# Part 4 — ⭐ Side effects, and the rule that decides where they go

**⭐ For every side effect, one question:**

> **⭐ If the process dies one second from now, does it matter that this never happened?**

| Answer | Mechanism | Day |
|---|---|---|
| ⭐ **No, loss is fine** | ⭐ `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` | 177, 179 |
| ⭐ **Yes, it must not be lost** | ⭐ **the outbox** — written in the same transaction | 124 |
| It must be atomic with the write | `BEFORE_COMMIT`, or just do it inline | 179 |

**⭐ The failure this prevents is Day 179's: sending an email inside the transaction means sending it
for bookings that then roll back.** `AFTER_COMMIT` fixes that and **still loses the email if the
process dies between commit and the listener** — which is fine for a confirmation email and not fine
for a payment capture.

**⭐ Deciding this per side effect, and writing the decision down, is a strong defence point.** Most
candidates have one mechanism and use it for everything.

## ⭐ Idempotency, at the service boundary

**Day 123, and your API promised it on Day 251:**

```
⭐ An Idempotency-Key on POST → a unique constraint on the key
⭐ Same key, same request  → return the original result
⭐ Same key, different body → 422 (a client bug — say so)
```

**⭐ And the marker must commit in the same transaction as the work** (Day 185A), or you mark and
crash (losing it) or work and crash (duplicating it).

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Long service methods | ⭐ the domain is anaemic; rules bypassed by other callers |
| ⭐ Entities in service signatures | Day 147's boundary erodes within a month |
| ⭐ HTTP call inside a transaction | ⭐ connection held; unrollbackable side effect |
| ⭐ Self-invocation | ⭐ no transaction, no error, no clue |
| ⭐ Catching an exception inside a transaction | commits partial work |
| No `rollbackFor` | checked exception → partial commit |
| `REQUIRES_NEW` casually | two connections; pool deadlock at scale |
| ⭐ Authorization only in the controller | jobs and consumers bypass it |
| ⭐ Guards instead of scoped queries | a forgotten annotation is a breach |
| ⭐ No negative authorization tests | the bug is a silent 200 |
| Side effects with one mechanism for all cases | emails for rolled-back work, or lost payments |
| Idempotency marker in a separate transaction | duplicate or lost work |

## ⭐ Self-review

- [ ] ⭐ Every service method reads as **load → delegate → persist → map**
- [ ] ⭐ **No business rules in services** — they are in the domain
- [ ] ⭐ Services take and return **DTOs**; no entity escapes
- [ ] ⭐ Transaction boundaries chosen deliberately; ⭐ **no network calls inside**
- [ ] `rollbackFor = Exception.class`; `readOnly = true` on reads
- [ ] ⭐ **Self-invocation verified absent** via interceptor TRACE logging
- [ ] ⭐ Authorization in the service, ⭐ **preferring scoped queries over guards**
- [ ] ⭐ **A negative authorization test per protected operation**
- [ ] ⭐ Every side effect classified by the loss question, ⭐ **and the outbox exists where needed**
- [ ] Idempotency keys honoured, with the marker in the same transaction

## 🎤 Defence questions

1. **⭐ Why are your service methods so short?**
2. **⭐ Where is the transaction boundary, and what is deliberately outside it?**
3. **⭐ You call a payment API. Walk me through the transaction structure and why.**
4. **⭐ How do you prevent Alice from cancelling Bob's booking — and why that mechanism?**
5. **Why is the authorization check not in the controller?**
6. **⭐ Which side effects are in the outbox and which are `AFTER_COMMIT`, and how did you decide?**
7. **What happens if a client sends the same `Idempotency-Key` twice?**
8. **⭐ How do you know `@Transactional` is actually applied?**

## ✅ Done when

- Every core-flow operation has a service method following the five-step shape
- ⭐ **No network call is inside a transaction**
- Every protected operation has a negative authorization test
- ⭐ Every side effect has a documented mechanism and a reason
