# Day 288 🏗️

**P-288** · The rebuild — why you are doing this, and what it must prove

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ NexOps already exists. That is the point.**
>
> The flagship proved you can build something correctly from scratch with every decision recorded
> before it was made. **This project proves something different and, in a job, more useful: that you
> can take a system that already exists — one you wrote under time pressure, without the knowledge
> you now have — and understand it well enough to justify it, critique it, and rebuild the parts that
> were wrong.**
>
> **⭐ You will spend most of your career on systems you did not design.** This is the rehearsal.

---

# Part 1 — ⭐ What this project must prove that the flagship did not

| The flagship proved | ⭐ NexOps must prove |
|---|---|
| You can design before building | ⭐ **You can reverse-engineer a design from code** |
| You can record decisions as you make them | ⭐ **You can reconstruct decisions nobody recorded** |
| You can build correctly | ⭐ **You can critique your own past work honestly** |
| You can operate what you built | ⭐ **You can improve something without rewriting it** |

**⭐ The last row is the one hiring managers care about most.** "I would rewrite it" is the answer of
someone who has never had to keep a system running. **"Here is what I would change, in what order,
and what I would leave alone" is the answer of an engineer.**

## ⭐ The three questions this project answers

> **⭐ 1. Why does this system exist, and what does it actually do?**
> **⭐ 2. Which decisions were right, which were wrong, and which were right *at the time*?**
> **⭐ 3. What would you change, in what order, and what would you deliberately not touch?**

**⭐ Question 2's third category is the sophisticated one.** A decision made with less time, less
knowledge or different constraints can be *correct then and wrong now* — and being able to
distinguish that from a mistake is the difference between critique and blame.

# Part 2 — ⭐ The archaeology, before you change anything

**⭐ Do not open the code with the intention of fixing it. Open it with the intention of understanding
it.**

### ⭐ Pass 1 — What does it do? (from the outside)

```
⭐ Run it. Use it. ⭐ Write down what it does in USER language, not technical language.
⭐ What is the one thing it is for? ⭐ Who would miss it if it vanished?
```

**⭐ If you cannot state the purpose in one sentence, that is your first finding** — and it is a
finding about the *system*, not about your memory.

### ⭐ Pass 2 — What is in it? (structure without judgement)

```
⭐ Draw the components and how they communicate.
⭐ Draw the data flow: ⭐ what comes in, what is stored, what goes out.
⭐ List the external dependencies. ⭐ For each: what happens if it is unavailable?
```

**⭐ Draw this from the code, not from memory.** Memory reconstructs the design you intended; the code
contains the design you shipped, and the gap between them is the most interesting thing you will find
today.

### ⭐ Pass 3 — Where is the risk?

```
⭐ Where does money, safety or a decision that matters get computed?     → ⭐ the risk engine
⭐ Where does untrusted input enter?                                     → ⭐ the RAG pipeline
⭐ Where is state mutated concurrently?
⭐ Where would a bug be silent rather than loud?
```

**⭐ The fourth question is the one that finds the real problems.** A crash is reported; **a wrong risk
score is believed.**

### ⭐ Pass 4 — Run the audits you now know how to run

**⭐ You have twenty stages of tooling that did not exist for you when this was written:**

| Audit | Day |
|---|---|

what you expected to find.**

# Part 3 — ⭐ The findings document, written without blame

```markdown
# docs/AUDIT.md

## What it does
⭐ One paragraph, user language.

## Architecture as built
⭐ A diagram from the code. ⭐ Note where it differs from what you remember intending.

## Findings
| # | Finding | ⭐ Severity | ⭐ Evidence | ⭐ Right at the time? |
|---|---------|-----------|-----------|--------------------|
| 1 | No index on risk_events(entity_id) | High | ⭐ EXPLAIN: seq scan, 40k rows | ⭐ No — always wrong |
| 2 | Risk weights hardcoded | Medium | ⭐ RiskEngine.java:88 | ⭐ Yes — one client, no config need |
| 3 | Embeddings regenerated on every query | High | ⭐ cost: £X/month | ⭐ No — a caching miss |
```

> **⭐⭐ The "right at the time?" column is the most valuable one in the document.** It forces the
> distinction between a mistake and a trade-off made under different constraints — and **being able
> to say "that was correct given what I knew and what I had; here is what changed" is a much stronger
> position than either defending it or apologising for it.**

**⭐ Severity should reflect blast radius, not effort:**

| Severity | Meaning |
|---|---|
| ⭐ **Critical** | ⭐ data loss, a security hole, or a **silently wrong answer** |
| High | user-visible failure, or unbounded cost |
| Medium | performance, maintainability |
| Low | style, minor duplication |

**⭐ A silently wrong risk score is Critical**, above an outage — because an outage is noticed and a
wrong answer is acted upon.

# Part 4 — ⭐ Scope the rebuild, and resist rewriting

> **⭐⭐ You are not rewriting NexOps. You are rebuilding three things by hand and fixing what the
> audit found.**

```
⭐ REBUILD BY HAND:  the data model · ⭐ the risk engine · ⭐ the RAG pipeline
⭐ FIX:              everything Critical and High from the audit
⭐ LEAVE ALONE:      ⭐ everything else — ⭐ and be able to say why
```

**⭐ "Leave alone" is a deliberate decision, not neglect.** Day 096's strangler pattern: **you improve
a system incrementally, in the places that matter, while it keeps working.** A rewrite is what people
propose when they do not understand the system well enough to change it safely.

**⭐ Write down what you are not touching and why.** It is the answer to "what would you do
differently?" that demonstrates judgement rather than enthusiasm.

## ⭐ Set up the safety net first

**⭐ Before changing anything, make it possible to know you broke something:**

```
⭐ 1. ⭐ CHARACTERISATION TESTS — capture current behaviour, ⭐ including behaviour you think is wrong
⭐ 2. Testcontainers against the real database          (Day 184)
⭐ 3. CI running on every push                          (Day 253)
⭐ 4. ⭐ A golden dataset for the risk engine: inputs → current outputs
⭐ 5. ⭐ A golden query set for RAG: questions → current answers
```

**⭐ Characterisation tests are the key idea and they are counter-intuitive**: they assert what the
code *currently does*, including bugs. **They are not correctness tests — they are change detectors.**
When you rebuild the risk engine, they tell you exactly which behaviours changed, and then you decide
for each one whether the change is a fix or a regression.

**⭐ Items 4 and 5 are the same idea for the two hardest components**, and they are what make
Days 291–295 possible at all: **you cannot safely rebuild a scoring engine or a retrieval pipeline
without a baseline to compare against.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Opening the code to fix rather than to understand | ⭐ you find what you expected, not what is there |
| ⭐ Drawing the architecture from memory | you document the intent, not the system |
| ⭐ Mixing evidence and judgement | ⭐ the findings become opinions |
| ⭐ No "right at the time?" column | ⭐ critique becomes blame, and reads badly |
| Severity by effort rather than blast radius | the wrong things get fixed first |
| ⭐ **Deciding to rewrite** | ⭐ signals you cannot change a system safely |
| ⭐ Changing anything before characterisation tests | ⭐ you cannot tell a fix from a regression |
| Not writing down what you are leaving alone | the judgement is invisible |
