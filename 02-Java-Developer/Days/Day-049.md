# Part 1 — `LinkedHashMap`

## What it adds

**A `HashMap` plus a doubly-linked list threading through all entries**, giving predictable iteration
order.

```java
static class Entry<K,V> extends HashMap.Node<K,V> {
    Entry<K,V> before, after;        // ← the extra links
}
transient LinkedHashMap.Entry<K,V> head, tail;
final boolean accessOrder;           // false = insertion order, true = access order
```

```
   Hash buckets (as HashMap)          The linked list (iteration order)
   ┌────┐
 0 │ ●──┼──▶ [C]                       head → [A] ⇄ [B] ⇄ [C] ⇄ [D] ← tail
   ├────┤
 1 │ ●──┼──▶ [A] ─▶ [D]
   ├────┤
 2 │ ●──┼──▶ [B]
   └────┘
```

**Two structures over the same nodes.** Lookup uses the buckets (O(1)); iteration follows the list.

**Cost:** two extra references per entry, and slightly slower writes. **Benefit:** deterministic
iteration, and — with `accessOrder` — an LRU cache almost for free.

## Access order — the LRU trick

```java
new LinkedHashMap<>(capacity, loadFactor, accessOrder);
//                                        ↑ true = move to the end on every get()
```

With `accessOrder = true`, **`get()` moves the entry to the tail**. So the head is always the
least-recently-used entry.

Combine that with an override:

```java
public class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LRUCache(int capacity) {
        super(capacity, 0.75f, true);          // ← access order
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;               // evict the head when over capacity
    }
}
```

**That's an entire LRU cache in five lines.** `removeEldestEntry` is called after every insertion; if
it returns true, the head — the least recently used — is removed.

**Both operations are O(1):** the hash lookup is O(1) and the list relink is O(1).

### The from-scratch version — know both

You will sometimes be asked to implement it *without* `LinkedHashMap`. The design is the same:

```
   HashMap<K, Node>  +  doubly-linked list
   ─────────────────────────────────────────
   get(k):   look up the node in O(1), unlink it, move to tail       → O(1)
   put(k,v): insert, move to tail; if over capacity, remove head     → O(1)
```

**The two structures are both necessary.** The map gives O(1) lookup; the list gives O(1) eviction of
the oldest. A list alone would be O(n) to find; a map alone has no order.

**Use a sentinel head and tail** so unlinking never needs null checks — that's the detail that makes
the implementation clean, and interviewers notice it.

## Where `LinkedHashMap` shows up

- **LRU caches** — as above
- **Deterministic iteration** — config maps, JSON serialisation where field order matters
- **Reproducible tests** — `HashMap`'s order can change between runs and JDK versions
- Spring's `LinkedCaseInsensitiveMap`, Jackson's ordered maps

# Part 2 — `TreeMap`

## What it is

**A red-black tree** — a self-balancing binary search tree. Keys are kept in sorted order.

| | `HashMap` | `TreeMap` |
|---|---|---|
| Structure | Bucket array | Red-black tree |
| `get`/`put` | **O(1)** avg | **O(log n)** guaranteed |
| Order | None | **Sorted** |
| Null keys | ✅ one | ❌ NPE |
| Needs | `hashCode`/`equals` | `Comparable` or a `Comparator` |
| Range queries | ❌ | ✅ **the reason to use it** |

**Use `TreeMap` when you need ordering or range queries. Otherwise `HashMap`.**

## Red-black trees — enough to explain

A BST with five invariants that together guarantee balance:

```
   1. Every node is red or black
   2. The root is black
   3. Every leaf (nil) is black
   4. A red node's children are both black    ← no two reds in a row
   5. Every path from a node to its descendant leaves
      contains the same number of black nodes
```

**Why this guarantees O(log n):** rules 4 and 5 together mean the longest path is at most **twice**
the shortest — you can't have two reds in a row, and every path has equal black-height. So the height
is bounded by 2·log₂(n+1).

**Why red-black rather than AVL?**

| | Red-black | AVL |
|---|---|---|
| Balance | Looser — height ≤ 2 log n | Stricter — height ≤ 1.44 log n |
| Lookup | Slightly slower | **Slightly faster** |
| Insert/delete rotations | **Fewer** — at most 2 (insert), 3 (delete) | More |
| Best for | **Write-heavy** | Read-heavy |

**Red-black trades a little lookup speed for much cheaper rebalancing**, which suits a general-purpose
map. That's the answer, and it's the same trade `HashMap` makes when treeifying a bucket (Day 048).

**You don't need to memorise the rotation cases.** Know the invariants, why they bound the height,
and the trade-off against AVL.

## The `NavigableMap` API — the actual reason to use `TreeMap`

```java
TreeMap<Integer, String> map = new TreeMap<>();

map.firstKey();  map.lastKey();
map.floorKey(5);        // greatest key ≤ 5
map.ceilingKey(5);      // smallest key ≥ 5
map.lowerKey(5);        // greatest key < 5   (strict)
map.higherKey(5);       // smallest key > 5   (strict)

map.headMap(10);        // keys < 10          — a VIEW
map.tailMap(10);        // keys ≥ 10
map.subMap(5, 10);      // 5 ≤ key < 10
map.descendingMap();    // reversed view

map.firstEntry(); map.pollFirstEntry();     // retrieve and remove
```

**These are all O(log n) and impossible on a `HashMap`.** Real uses:

- **Rate limiting** — "how many events in the last 60 seconds" via `tailMap(now - 60_000)`
- **Time-series lookups** — "the price as of this timestamp" via `floorEntry(t)`
- **Interval and range matching** — IP-to-region tables, tiered pricing
- **Leaderboards** — `descendingMap()` with `subMap` for pagination

**`floorEntry` on a timestamp key is a genuinely useful pattern** and worth remembering — it answers
"the most recent value at or before this time" in O(log n).

## The comparator trap

**`TreeMap` determines equality by `compareTo`/`compare`, never by `equals`.**

```java
TreeMap<String, Integer> ci = new TreeMap<>(String.CASE_INSENSITIVE_ORDER);
ci.put("hello", 1);
ci.put("HELLO", 2);
ci.size();              // 1 — the comparator says they're the same key
```

**Same phenomenon as `BigDecimal` in a `TreeSet`** (Day 041): a comparator inconsistent with `equals`
makes sorted and hashed collections disagree.

## Type this yourself

```java
import java.util.*;

public class OrderedMapsDemo {

    static class LRUCache<K, V> extends LinkedHashMap<K, V> {
        private final int capacity;
        LRUCache(int capacity) { super(capacity, 0.75f, true); this.capacity = capacity; }
        @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
            return size() > capacity;
        }
    }

    public static void main(String[] args) {

        // ---- iteration order ----
        System.out.println("--- iteration order ---");
        List<String> keys = List.of("banana", "apple", "cherry", "date");
        Map<String,Integer> hash = new HashMap<>(), linked = new LinkedHashMap<>(), tree = new TreeMap<>();
        for (int i = 0; i < keys.size(); i++) {
            hash.put(keys.get(i), i); linked.put(keys.get(i), i); tree.put(keys.get(i), i);
        }
        System.out.println("   HashMap:       " + hash.keySet());
        System.out.println("   LinkedHashMap: " + linked.keySet() + "   ← insertion");
        System.out.println("   TreeMap:       " + tree.keySet() + "   ← sorted");

        // ---- access order ----
        System.out.println("\n--- accessOrder = true ---");
        LinkedHashMap<String,Integer> access = new LinkedHashMap<>(16, 0.75f, true);
        access.put("a",1); access.put("b",2); access.put("c",3);
        System.out.println("   after puts:    " + access.keySet());
        access.get("a");
        System.out.println("   after get(a):  " + access.keySet() + "   ← 'a' moved to the end");

        // ---- LRU eviction ----
        System.out.println("\n--- LRU cache, capacity 3 ---");
        LRUCache<String,Integer> lru = new LRUCache<>(3);
        lru.put("a",1); lru.put("b",2); lru.put("c",3);
        System.out.println("   " + lru.keySet());
        lru.get("a");                                   // 'a' becomes most recent
        System.out.println("   after get(a):  " + lru.keySet());
        lru.put("d",4);                                 // evicts the LRU — which is now 'b'
        System.out.println("   after put(d):  " + lru.keySet() + "   ← 'b' evicted, not 'a'");

        // ---- NavigableMap ----
        System.out.println("\n--- NavigableMap ---");
        TreeMap<Integer,String> prices = new TreeMap<>();
        prices.put(0,"free"); prices.put(100,"basic"); prices.put(500,"pro"); prices.put(2000,"enterprise");
        for (int spend : new int[]{50, 100, 499, 5000})
            System.out.printf("   spend %,5d → tier %s   (floorEntry)%n",
                    spend, prices.floorEntry(spend).getValue());
        System.out.println("   ceilingKey(300)  = " + prices.ceilingKey(300));
        System.out.println("   headMap(500)     = " + prices.headMap(500));
        System.out.println("   subMap(100, 2000)= " + prices.subMap(100, 2000));
        System.out.println("   descendingMap()  = " + prices.descendingMap());

        // ---- sliding-window rate limit ----
        System.out.println("\n--- rate limiting with tailMap ---");
        TreeMap<Long,String> events = new TreeMap<>();
        long now = System.currentTimeMillis();
        for (int i = 0; i < 10; i++) events.put(now - i * 1000L, "event" + i);
        System.out.println("   events in the last 5s: " + events.tailMap(now - 5000).size());

        // ---- comparator vs equals ----
        System.out.println("\n--- comparator inconsistent with equals ---");
        TreeMap<String,Integer> ci = new TreeMap<>(String.CASE_INSENSITIVE_ORDER);
        ci.put("hello",1); ci.put("HELLO",2);
        System.out.println("   TreeMap(CASE_INSENSITIVE) size = " + ci.size() + " → " + ci);
        Map<String,Integer> hm = new HashMap<>();
        hm.put("hello",1); hm.put("HELLO",2);
        System.out.println("   HashMap size = " + hm.size());

        // ---- performance ----
        int n = 1_000_000;
        Map<Integer,Integer> h = new HashMap<>(), t = new TreeMap<>();
        long start = System.currentTimeMillis();
        for (int i = 0; i < n; i++) h.put(i, i);
        long ht = System.currentTimeMillis() - start;
        start = System.currentTimeMillis();
        for (int i = 0; i < n; i++) t.put(i, i);
        long tt = System.currentTimeMillis() - start;
        System.out.printf("%n--- %,d puts ---%n   HashMap: %,5d ms%n   TreeMap: %,5d ms  (O(log n))%n",
                n, ht, tt);
    }
}
```

**The LRU result is the one to internalise:** after `get("a")`, inserting `"d"` evicts **`b`**, not
`a` — because accessing `a` made it recent. That's access-order working.

## Interview questions

**Q: How would you implement an LRU cache?**
> Two structures: a hash map for O(1) lookup and a doubly-linked list for O(1) eviction of the oldest.
> On `get`, find the node in the map and move it to the tail. On `put`, insert at the tail and if over
> capacity remove the head. In Java you can get this from `LinkedHashMap` with access order enabled and
> `removeEldestEntry` overridden, which is about five lines — but the underlying design is the map plus
> list, and I'd use sentinel head and tail nodes to avoid null checks when unlinking.

**Q: How does `LinkedHashMap` maintain order?**
> It extends `HashMap` and adds `before` and `after` references to each node, threading a doubly-linked
> list through all entries alongside the bucket structure. Lookup still uses the buckets in O(1);
> iteration follows the list. With access order enabled, `get` also moves the entry to the tail.

**Q: `HashMap` or `TreeMap`?**
> `HashMap` unless you need ordering. `TreeMap` gives O(log n) rather than O(1), but provides sorted
> iteration and the `NavigableMap` operations — `floorKey`, `ceilingKey`, `subMap`, `headMap` — which
> are impossible on a hash map. Those matter for range queries: time-series lookups, tiered pricing,
> sliding-window rate limiting.

**Q: What is a red-black tree and why use it over AVL?**
> A self-balancing BST with colour invariants: no two consecutive red nodes, and every root-to-leaf
> path has the same black height. Together those bound the longest path at twice the shortest, giving
> O(log n). Red-black is less strictly balanced than AVL, so lookups are marginally slower, but it
> needs far fewer rotations on insert and delete — at most two and three respectively — which suits a
> general-purpose mutable map.

**Q: Why can a `TreeMap` have fewer entries than a `HashMap` with the same keys?**
> `TreeMap` decides key equality using the comparator or `compareTo`, not `equals`. A case-insensitive
> comparator treats `"hello"` and `"HELLO"` as the same key, so only one entry exists. It's the same
> inconsistency that makes a `TreeSet` of `BigDecimal` 1.0 and 1.00 hold one element while a `HashSet`
> holds two.
