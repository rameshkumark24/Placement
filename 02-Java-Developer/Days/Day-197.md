# Day 197

**L-197** · Connection pooling and PgBouncer — the layer between the pool and the database

**Time:** 3 hrs · **Mode:** NEW

> Day 156 sized HikariCP and explained why a small pool outperforms a large one. Day 186 gave the
> reason: **one OS process per connection.** Today is what happens when one application pool is not
> enough — twenty service instances, serverless functions, or an analytics tool — and the connection
> count arithmetic stops working.
>
> **PgBouncer is the answer, and its pooling modes have consequences that will break your
> application if you do not know them.**

---

# Part 1 — ⭐ The arithmetic that forces the decision

```
20 service instances × 10 connections    = 200
+ 3 background workers × 5               =  15
+ analytics tool                         =  20
+ admin sessions                         =   5
                                         ⭐ 240 backend processes
```

**⭐ At ~10 MB of process memory each that is 2.4 GB before a single query runs**, plus scheduler
pressure, plus `work_mem` allocations per operation (Day 191). A database sized for 20–40 effective
connections (Day 156's formula) is being asked to host 240.

**⭐ And you cannot solve it by shrinking each pool**, because below about 5 connections per instance
a traffic spike queues at the application (Day 156's `connections_pending`). **The application's
needs and the database's needs are genuinely in conflict — that is the problem PgBouncer solves.**

```
20 instances × 10 = 200 client connections
              ↓
        ⭐ PgBouncer
              ↓
        ⭐ 25 server connections to PostgreSQL
```

**⭐ It works because connections are mostly idle.** A pool of 10 with 3 in use at any moment means
7 idle backends per instance doing nothing but consuming memory. PgBouncer multiplexes the *active*
work onto a small shared set.

# Part 2 — ⭐⭐ The three pooling modes

| Mode | A server connection is held for | Multiplexing |
|---|---|---|
| **Session** | ⭐ the whole client connection | ⭐ almost none — barely better than direct |
| ⭐ **Transaction** | ⭐ **one transaction** | ⭐⭐ **excellent. The mode you want** |
| Statement | one statement | ⭐ maximum, and **breaks transactions entirely** |

**⭐ Transaction mode is the answer**, and it comes with a specific list of things that stop working.

## ⭐⭐ What breaks in transaction mode

> **⭐ Between transactions, your next query may land on a completely different server connection.**
> **Anything that is session state is therefore unreliable.**

| Feature | Status |
|---|---|
| ⭐ `SET` outside a transaction | ❌ **lost** — use `SET LOCAL` inside one |
| ⭐ **Prepared statements** (server-side) | ⭐⭐ **broken** — see below |
| `LISTEN` / `NOTIFY` | ❌ broken |
| Advisory locks (session-scoped) | ❌ broken — use transaction-scoped `pg_advisory_xact_lock` |
| Temporary tables | ❌ broken |
| `WITH HOLD` cursors | ❌ broken |
| `SET LOCAL` inside a transaction | ⭐ ✅ fine |
| `pg_advisory_xact_lock` | ⭐ ✅ fine |

### ⭐ The prepared statement problem — the one that catches Java

**The JDBC driver uses server-side prepared statements by default** (after `prepareThreshold`
executions, default 5). It prepares a statement on connection X, then later tries to execute it on
connection Y, which has never seen it:

```
org.postgresql.util.PSQLException: ERROR: prepared statement "S_3" does not exist
```

**⭐ Two fixes, and the second is much better:**

```
# ⭐ PgBouncer 1.21+ — tracks prepared statements across server connections
max_prepared_statements = 200
```

```
jdbc:postgresql://bouncer:6432/app?prepareThreshold=0     -- ⭐ the older workaround
```

**⭐ `max_prepared_statements` in PgBouncer 1.21+ is the correct modern answer** — you keep prepared
statements and their plan caching. `prepareThreshold=0` disables server-side prepares entirely, which
works and costs you re-planning on every execution.

**⭐ This is the single most common PgBouncer-plus-Java failure**, and it is intermittent — it only
appears once a statement has been executed enough times to be prepared, so it passes testing and
fails under production load.

## Configuration

```ini
[databases]
app = host=postgres port=5432 dbname=app

[pgbouncer]
pool_mode = transaction              # ⭐
max_client_conn = 1000               # ⭐ client-side — can be large
default_pool_size = 25               # ⭐⭐ SERVER connections per user/database. THE number
reserve_pool_size = 5
reserve_pool_timeout = 3
max_prepared_statements = 200        # ⭐ PgBouncer 1.21+
server_idle_timeout = 600
query_wait_timeout = 120             # ⭐ how long a client waits for a server connection
auth_type = scram-sha-256            # ⭐ never md5
```

**⭐ `default_pool_size` is the number that must obey Day 156's formula**, not `max_client_conn`.
Clients can be 1,000; server connections should be ~25.

**⭐ And you now have two pools in series**, which needs deliberate sizing:

```
HikariCP (per instance) → PgBouncer → PostgreSQL
   10 × 20 = 200        →    25     →    25 backends
```

**Hikari's `connection-timeout` and PgBouncer's `query_wait_timeout` must be consistent**, or a
client gives up while PgBouncer is still queueing it — or worse, waits far longer than the
application's own budget (Day 154).

# Part 3 — Monitoring, and the numbers that matter

```sql
-- ⭐ connect to PgBouncer's admin database
psql -p 6432 -U pgbouncer pgbouncer

show pools;      -- ⭐⭐ cl_active, cl_waiting, sv_active, sv_idle, maxwait
show stats;      -- queries per second, average query and wait time
show clients;
show servers;
```

**⭐ The two numbers to alert on:**

| Metric | Meaning |
|---|---|
| ⭐ `cl_waiting` | ⭐ **clients queued for a server connection.** Sustained above zero = `default_pool_size` too small, or queries too slow |
| ⭐ `maxwait` | ⭐ **the longest current wait, in seconds.** Anything above a second is a user-visible stall |

**⭐ These are the PgBouncer analogue of Day 156's `hikaricp_connections_pending`**, and the same
reading applies: if clients are waiting, either there are not enough server connections or the
queries holding them are too slow. **Check query duration before raising the pool size** — raising it
to compensate for slow queries just moves the contention into PostgreSQL.

## When PgBouncer is not the answer

| Situation | Better answer |
|---|---|
| ⭐ One application, one pool, ~20 connections | ⭐ **you do not need PgBouncer.** Do not add a hop |
| Long transactions holding connections | ⭐ fix the transactions (Day 156, Day 194) |
| Slow queries | ⭐ fix the queries (Day 193) |
| Needing session features | session mode — but then it buys little |
| ⭐ Read scaling | ⭐ **read replicas** (Day 201), not more connections |

**⭐ PgBouncer solves a connection *count* problem. It does not solve a slow-query problem, and
adding it to hide one makes diagnosis harder** by putting another queue between the symptom and the
cause.

**And it is another hop**: ~0.1–0.5 ms of latency, plus a component that can fail. Run it as a
sidecar next to the application or with a highly-available pair — a single shared PgBouncer is a
single point of failure for every service that uses it.

## Alternatives

| Tool | Note |
|---|---|
| ⭐ **PgBouncer** | ⭐ the standard. Single-threaded, tiny, extremely reliable |
| **pgcat** | Rust, multi-threaded, adds load balancing and sharding |
| **Odyssey** | Yandex's multi-threaded pooler |
| ⭐ **RDS Proxy / Cloud SQL connectors** | managed; ⭐ good fit for serverless, where connection storms are the core problem |
| PgPool-II | also does replication and load balancing — ⭐ more moving parts than most need |

**⭐ PgBouncer is single-threaded**, so a very high-throughput system may need multiple instances or a
multi-threaded alternative. In practice one PgBouncer handles a great deal of traffic, because it
does almost nothing per request.

# Part 4 — ⭐ The serverless problem

**⭐ Serverless is where connection pooling breaks down completely**, and it is worth understanding
because it is the case where the standard advice fails.

```
1,000 concurrent Lambda invocations
→ ⭐ each is a separate process with its own pool
→ ⭐ 1,000+ connections, each used for one query then abandoned
→ ⭐ PostgreSQL forks 1,000 processes and dies
```

**⭐ The application-side pool is useless here** because there is no long-lived process to pool
*into*. Each invocation starts cold, connects, runs one query, and freezes.

| Fix | Note |
|---|---|
| ⭐ **A pooler in front** (PgBouncer, RDS Proxy) | ⭐ **the standard answer** — the pooler holds the durable connections |
| ⭐ **HTTP-based data APIs** (Neon, Supabase, Aurora Data API) | ⭐ no persistent connection at all |
| Keep functions warm | partial and unreliable |
| Do not use serverless for a chatty database workload | ⭐ often the honest answer |

**This is also the general shape of the answer for any highly elastic workload**: the durable
connections have to live somewhere that does not scale with request concurrency.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Session mode expecting multiplexing | barely better than connecting directly |
| ⭐ Transaction mode with server-side prepares | intermittent "prepared statement does not exist" |
| ⭐ `SET` outside a transaction | silently lost; use `SET LOCAL` |
| Session-scoped advisory locks | broken; use `pg_advisory_xact_lock` |
| `LISTEN`/`NOTIFY` in transaction mode | broken |
| `default_pool_size` too large | you have reproduced the problem you were solving |
| Mismatched Hikari and PgBouncer timeouts | clients give up mid-queue, or wait past their SLA |
| ⭐ Not monitoring `cl_waiting` and `maxwait` | the pooler's own saturation is invisible |
| Raising the pool size instead of fixing slow queries | moves contention into PostgreSQL |
| Adding PgBouncer for one small application | needless hop and failure point |
| A single shared PgBouncer | one SPOF for every service |
| ⭐ Serverless straight to PostgreSQL | connection storm; the database forks and dies |

## Interview questions

**Q: Why would you add PgBouncer?**
Because PostgreSQL uses one OS process per connection, so a few hundred connections is real memory
and scheduler cost — and twenty service instances each needing a pool of ten adds up faster than the
database can absorb. PgBouncer multiplexes those onto a small set of server connections, which works
because connections are mostly idle.

**Q: What breaks in transaction pooling mode?**
Anything that is session state, because the next transaction may land on a different server
connection: `SET` outside a transaction, `LISTEN`/`NOTIFY`, temporary tables, session-scoped advisory
locks, and server-side prepared statements. The prepared-statement one is the classic Java failure —
the JDBC driver prepares after five executions, so it passes testing and fails intermittently under
load. Modern PgBouncer handles it with `max_prepared_statements`.

**Q: How do you size the two pools?**
`default_pool_size` follows the database's capacity — Day 156's formula, so around 25 — while
`max_client_conn` can be large because client connections are cheap. And the timeouts have to be
consistent: Hikari's connection timeout and PgBouncer's `query_wait_timeout` need to agree, or a
client gives up while still queued.

**Q: What does PgBouncer not fix?**
Slow queries or long transactions. It solves a connection *count* problem, and adding it to mask a
slow-query problem just puts another queue between the symptom and the cause. If `cl_waiting` is
high, I check query duration before raising the pool size.

**Q: What is the serverless connection problem?**
Each invocation is a separate process, so there is nothing to pool into — a thousand concurrent
functions is a thousand connections used for one query each, and PostgreSQL forks a thousand
processes. The durable connections have to live in a pooler or a managed proxy, or you use an
HTTP-based data API with no persistent connection at all.

## 🎙️ Articulation drill

Two minutes: **"When and why would you use PgBouncer?"**

Start with the arithmetic — one process per connection, twenty instances with pools of ten, and a
database sized for twenty-five — and note that the application's needs and the database's needs are
genuinely in conflict, which is the problem being solved. Transaction mode, and immediately name what
it breaks, leading with server-side prepared statements because that is the Java failure and it is
intermittent. Close on what it does *not* solve: it is a connection-count fix, not a slow-query fix,
and putting it in front of slow queries just adds a queue between you and the cause.
