# Part 1 — The lost update, and why it is the default

```
Time  Alice                          Bob
 t1   read order (total = 100)
 t2                                  read order (total = 100)
 t3   set total = 150, commit
 t4                                  set total = 200, commit    ⭐ Alice's change is gone
```

**No error. No warning. At `READ_COMMITTED` — PostgreSQL's default — this is simply what happens.**
Both transactions read a committed value, both wrote, the second won.

**This is the single most common data-integrity bug in web applications**, because the read and the
write are in *different HTTP requests*, so no database transaction spans them. The user opened an
edit form at 10:00 and saved at 10:04; someone else saved at 10:02.

# Part 2 — ⭐ Optimistic locking, the default answer

```java
@Entity
public class Order {
    @Version                                     // ⭐ one annotation
    private long version;
}
```

```sql
-- Hibernate generates this automatically on every update
update orders set total = ?, version = 4 where id = ? and version = 3;   -- ⭐ the guard
```

**If the row's version is no longer 3, zero rows update, and Hibernate throws
`OptimisticLockException`** — surfaced by Spring as `ObjectOptimisticLockingFailureException`
(Day 157's translation). Alice's transaction fails instead of silently losing.

**Why optimistic is the default choice:** no locks are held between the read and the write, so
readers never block and the database does no extra work. **You pay only when a conflict actually
occurs** — and in most systems conflicts are rare. Pessimistic locking pays on every access to protect
against something that happens 0.1% of the time.

Notes that matter:

- **`long`, not `Long`.** A null version on a detached entity makes Hibernate treat it as new.
- **Any `@Version` type works** — `int`, `long`, `Instant`, `short`. A timestamp is readable but has
  clock-resolution collisions; an integer is safer.
- ⭐ **Bulk updates do not increment it** (Day 162), so those rows escape the check entirely.
- **The version increments on any dirty field**, which means two people editing *different* fields
  still conflict. That is usually correct (they may be logically related) and occasionally annoying.

## Connecting it to HTTP — Day 102 and Day 150, completed

```java
@PutMapping("/{id}")
ResponseEntity<OrderResponse> update(@PathVariable UUID id,
                                     @RequestHeader(IF_MATCH) String ifMatch,
                                     @Valid @RequestBody UpdateOrderRequest req) {
    Order updated = service.update(id, req, parseVersion(ifMatch));   // ⭐ client's version
    return ResponseEntity.ok().eTag("\"" + updated.getVersion() + "\"").body(from(updated));
}
```

```java
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
ProblemDetail conflict() {
    var p = ProblemDetail.forStatusAndDetail(CONFLICT,
            "This record was changed by someone else. Reload and try again.");
    p.setType(URI.create("https://api.acme.com/problems/concurrent-modification"));
    return p;                                                          // ⭐ Day 149
}
```

**The full chain, and being able to state it end to end is the interview answer:** the entity version
becomes the `ETag`, the client returns it as `If-Match`, the service passes it into the update, the
database `where version = ?` enforces it, the failure becomes a 409 with an actionable message.
**Day 102's HTTP semantics and D-15's database theory are the same mechanism at two layers.**

## Making the client's version actually bind

```java
@Transactional
public Order update(UUID publicId, UpdateOrderRequest req, long expectedVersion) {
    Order order = repo.findByPublicId(publicId).orElseThrow();
    if (order.getVersion() != expectedVersion) {
        throw new ObjectOptimisticLockingFailureException(Order.class, publicId);  // ⭐ fail early
    }
    order.apply(req);
    return order;                                     // dirty checking writes it (Day 162)
}
```

The explicit check matters: without it, the version loaded *now* is written back, so the client's
stale version never participates and the guard protects only against a conflict in the last few
milliseconds. `@Lock(LockModeType.OPTIMISTIC_FORCE_INCREMENT)` is the JPA-native alternative.

# Part 3 — Pessimistic locking, and when it is genuinely right

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)               // ⭐ select ... for update
@Query("select s from Stock s where s.productId = :id")
Optional<Stock> findForUpdate(@Param("id") Long id);
```

```java
@Transactional
public void reserve(Long productId, int qty) {
    Stock stock = repo.findForUpdate(productId).orElseThrow();   // ⭐ row locked here
    if (stock.getAvailable() < qty) throw new InsufficientStockException();
    stock.setAvailable(stock.getAvailable() - qty);
}                                                                 // ⭐ lock released at commit
```

| Mode | SQL | Meaning |
|---|---|---|
| `PESSIMISTIC_READ` | `for share` | others may read, not write |
| `PESSIMISTIC_WRITE` | ⭐ `for update` | exclusive |
| `PESSIMISTIC_FORCE_INCREMENT` | `for update` + version bump | both |

**Use it when contention is high and a retry is expensive or unacceptable** — inventory on a flash
sale, a seat booking, a ledger balance. Optimistic locking under heavy contention degrades badly: 100
concurrent buyers means 99 failures and 99 retries, which is worse than 99 short waits.

**⭐ The three costs, each a real incident:**

1. **Readers block**, so throughput on that row is serialised.
2. ⭐ **Deadlock**, if two transactions lock the same rows in different orders. **The fix is a
   consistent lock ordering** — always lock by ascending id — and it must be a codebase-wide
   convention, because a deadlock needs only two methods that disagree.
3. **A held lock plus a slow operation is an outage.** Day 156's rule is doubly true here: an HTTP
   call while holding `for update` blocks every other buyer for that duration.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))   // ⭐ ms
```

**Always set a lock timeout.** Without it, a blocked transaction waits indefinitely, holding its own
connection and its own locks — the classic cascade into a pool-exhausted, fully-stalled service.

## The third option people forget

```sql
update stock set available = available - :qty
where product_id = :id and available >= :qty;      -- ⭐ atomic, no read, no lock held across a round trip
```

**One statement, no lock held across application code, no lost update, no retry.** Zero rows updated
means insufficient stock. **For a simple counter this beats both locking strategies** and it should be
the first thing you consider — the ORM's read-modify-write habit makes people forget that SQL can do
the arithmetic.

# Part 4 — Auditing

## Level 1 — who and when, on the entity

```java
@EntityListeners(AuditingEntityListener.class)
@MappedSuperclass
public abstract class Auditable {
    @CreatedDate    @Column(updatable = false) private Instant createdAt;
    @LastModifiedDate                          private Instant updatedAt;
    @CreatedBy      @Column(updatable = false) private String createdBy;
    @LastModifiedBy                            private String updatedBy;
}
```

```java
@Configuration
@EnableJpaAuditing(auditorAwareRef = "auditorAware")
class AuditConfig {
    @Bean AuditorAware<String> auditorAware() {
        return () -> Optional.ofNullable(SecurityContextHolder.getContext().getAuthentication())
                             .filter(Authentication::isAuthenticated)
                             .map(Authentication::getName);     // ⭐ empty for jobs — handle it
    }
}
```

Four fields, one annotation. **The gap:** it records only the *latest* change. "What was the total
before?" and "who set it to 500 last Tuesday?" are unanswerable.

**And the hole from Day 162:** this is built on `@PrePersist`/`@PreUpdate`, so **bulk JPQL updates and
native SQL leave no audit trail at all.** If auditing is a compliance requirement, that hole is not
acceptable and you need database triggers or Hibernate Envers.

## Level 2 — full history with Envers

```java
@Entity
@Audited                                        // ⭐ that is the whole setup
public class Order { }
```

Envers creates `orders_AUD` with a revision number and writes a row per change. Then:

```java
AuditReader reader = AuditReaderFactory.get(em);
Order asOfLastTuesday = reader.find(Order.class, orderId, revisionNumber);
List<Number> revisions = reader.getRevisions(Order.class, orderId);
```

**What it costs, stated honestly:** roughly double the write volume, an audit table that grows without
bound and needs a retention policy, and schema migrations that must be applied to both tables.
`@Audited` on a hot, high-write entity is a real performance decision, not a free feature.

**And it shares the hole:** Envers is also listener-based, so bulk operations bypass it.

## Level 3 — domain events, which are usually what people actually want

```java
@Entity
public class Order extends AbstractAggregateRoot<Order> {
    public void ship(String trackingNumber) {
        this.status = SHIPPED;
        registerEvent(new OrderShippedEvent(id, trackingNumber, Instant.now()));   // ⭐
    }
}
```

Spring Data publishes registered events when the aggregate is saved.

**⭐ The distinction that matters:** Envers records *field changed from X to Y*. A domain event records
*the order was shipped, by this user, with this tracking number*. **The second is what a support agent
or an auditor actually needs**, and it is what a business rule can be written against. Field-level
history is forensic; domain events are meaningful.

Most systems want domain events for the business narrative, and Envers or triggers only where a
regulator specifically requires field-level history.

**And the delivery caveat:** these events fire in-process. Anything that must not be lost — a
notification, a downstream update — needs Day 124's outbox, not an event listener.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| No `@Version` on a concurrently-edited entity | silent lost updates; the default behaviour |
| `Long version` instead of `long` | null version treated as a new entity |
| Not passing the client's version into the update | the guard only covers the last few ms |
| Assuming isolation prevents lost updates | it does not at `READ_COMMITTED` |
| Expecting `@Version` on bulk updates | not incremented; check bypassed |
| Pessimistic locks with no timeout | indefinite wait; pool exhaustion |
| Inconsistent lock ordering | deadlocks |
| Slow work while holding `for update` | serialises every other user of that row |
| Read-modify-write where one atomic UPDATE would do | needless locking or retries |
| Optimistic locking under heavy contention | retry storms; use pessimistic or atomic SQL |
| Auditing only via listeners, with compliance needs | bulk and native operations leave no trace |
| Envers on a hot entity without thinking | doubles write volume; unbounded table |
| Field history where a domain event was wanted | forensic data nobody can interpret |

## Interview questions

**Q: Two users edit the same record. What happens by default?**
The second write wins and the first is silently lost — at `READ_COMMITTED` that is simply the
behaviour, and because the read and write are in different HTTP requests no transaction spans them.
`@Version` fixes it: the update carries `where version = ?`, updates zero rows on a conflict, and
throws.

**Q: Optimistic or pessimistic?**
Optimistic by default — no locks held, readers never block, and you pay only when a conflict actually
happens, which is rare. Pessimistic when contention is high and a retry is expensive, like inventory
on a flash sale. And for a simple counter, an atomic `update ... where available >= ?` beats both.

**Q: How does optimistic locking connect to HTTP?**
The entity's version becomes the `ETag`, the client sends it back as `If-Match`, the service compares
it and the database enforces it in the `where` clause, and the failure becomes a 409 with a message
telling the user to reload. The same mechanism at two layers.

**Q: What are the risks of pessimistic locking?**
Readers block, deadlocks if lock ordering is inconsistent, and any slow operation while holding the
lock serialises every other user of that row. All three need a lock timeout as a backstop.

**Q: How do you audit changes?**
Spring Data auditing for created/updated by and when; Envers when field-level history is genuinely
required, accepting doubled writes and an unbounded table; and domain events for the business
narrative, which is usually what people actually want. All listener-based approaches share one hole:
bulk and native statements bypass them.

## 🎙️ Articulation drill

Two minutes: **"How do you handle concurrent updates?"**

Start with the failure — at read-committed the second write silently wins, and in a web application
the read and write are in different requests so no transaction covers them. Then optimistic locking
as the default and *why*: no locks held, cost paid only on actual conflict. Trace the full chain
through ETag and `If-Match` to a 409, because that shows you have connected the database mechanism to
the API contract. Then name when you would switch: high contention where retries are worse than
waits — and add the option most people forget, that a single atomic UPDATE with a guard clause beats
both for a counter.
