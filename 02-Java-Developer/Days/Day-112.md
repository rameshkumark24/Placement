# Part 1 — Hashing is not encryption

The distinction people get wrong, stated precisely:

| | Hashing | Encryption | Encoding |
|---|---|---|---|
| Reversible | ❌ **never** | ✅ with the key | ✅ trivially |
| Key | none | required | none |
| Output size | fixed | proportional to input | proportional |
| Purpose | verification, integrity | confidentiality | representation |
| Example | argon2, SHA-256 | AES-GCM | base64, URL-encoding |

> **Base64 is not encryption. It is not security of any kind.** It is a way to represent bytes as
> ASCII. Anyone can decode it instantly.

**Passwords must be hashed, never encrypted.** Encryption implies a key, a key can be stolen, and a
stolen key reveals every password in plaintext. Hashing has no key to steal — the system *cannot*
recover the original, which is exactly the property you want.

> **If a site can email you your existing password, it stored it recoverably. That is a
> disqualifying finding.**

## Why a fast hash is the wrong tool

```java
// 💀 all of these are WRONG for passwords
MessageDigest.getInstance("MD5")
MessageDigest.getInstance("SHA-1")
MessageDigest.getInstance("SHA-256")
```

These are **designed to be fast** — that is their purpose, for verifying file integrity at gigabytes
per second. Speed is precisely what you do not want here.

A modern GPU computes roughly **50–100 billion SHA-256 hashes per second**. A rig with eight of them
exhausts the entire 8-character printable-ASCII space in **under an hour**.

Add **rainbow tables** — precomputed hash→plaintext maps for common passwords — and an unsalted
SHA-256 dump is not cracked, it is *looked up*.

> **Password hashing must be deliberately, tunably slow.** That is the entire design goal, and it is
> the sentence to lead with in an interview.

# Part 2 — Salt

**A salt is a unique random value per password, stored alongside the hash.**

```
hash = H(salt || password)
stored: salt$hash
```

What it prevents, specifically:

**1. Rainbow tables.** A precomputed table must now be built per salt, which makes precomputation
worthless.

**2. Identical passwords producing identical hashes.** Without a salt, two users with `password123`
have the same hash — so cracking one cracks both, and the *pattern* leaks: an attacker sees which
accounts share a password and which is the most common one in your database.

Properties:

- **Unique per password** — not per application, not per user-and-reused.
- **Cryptographically random** (`SecureRandom`, never `Random` — Day 015's C-10).
- **At least 16 bytes.**
- **Not secret.** The salt is stored in plaintext next to the hash and that is correct — its job is
  to defeat precomputation, not to be a secret.
- **New on every password change.**

Modern algorithms generate and embed the salt for you. **You should never be writing salt-handling
code**; if you are, you are using the wrong library.

## Pepper — the optional extra

A **pepper** is a secret value, the same for the whole application, mixed in and stored *separately
from the database* — in an HSM, a KMS, or at minimum an environment variable.

```
hash = argon2(password || pepper)
```

The threat it addresses is specific: **a database-only compromise.** An attacker with a SQL injection
dump but no filesystem or secret-store access cannot crack anything, because they are missing the
pepper.

The costs, which is why it is optional: **rotating it requires rehashing every password** (usually
done lazily at next login), it adds operational complexity, and it provides nothing if the attacker
gets application-level access too.

> **Salt is mandatory. Pepper is a defensible extra for high-value systems.** The better modern
> approach is `argon2` with a **secret key parameter**, or HMAC the password with the pepper key
> before hashing — both avoid the length-extension and concatenation subtleties.

# Part 3 — The right algorithms

## The choices

| Algorithm | Year | Resists | Verdict |
|---|---|---|---|
| **Argon2id** | 2015 | CPU + **memory** + parallelism | ✅ **first choice** (PHC winner) |
| **scrypt** | 2009 | CPU + memory | ✅ good |
| **bcrypt** | 1999 | CPU | ✅ acceptable; ⚠️ **72-byte input limit** |
| **PBKDF2** | 2000 | CPU only | ⚠️ only when FIPS compliance requires it |
| SHA-256/512 | — | nothing | ❌ never, alone |
| MD5, SHA-1 | — | nothing | ❌ also broken as hashes |

**Why memory-hardness matters, and this is the key insight of the modern generation:** a GPU has
thousands of cores but comparatively little memory per core, and an ASIC is cheap to build for a
computation that needs no memory. **Requiring 64 MB per hash makes massive parallelism expensive** —
you cannot run 10,000 concurrent hashes on a GPU with 8 GB of RAM. PBKDF2 and bcrypt are CPU-hard
only, which is why Argon2id and scrypt are preferred.

**The bcrypt 72-byte limit is a real trap.** Input beyond 72 bytes is silently ignored, so a 200-
character passphrase is effectively truncated — and some implementations also mishandle embedded null
bytes. If you use bcrypt, either cap the password length in validation or pre-hash with SHA-512 and
base64 the result (which introduces its own subtleties). Argon2 has no such limit.

## Parameters, and what they mean

**Argon2id** — OWASP's current guidance:

```
m = 19456 KiB (19 MiB)     memory cost      ← the expensive dimension
t = 2                      iterations (time cost)
p = 1                      parallelism
```

Alternatives that trade memory for time: `m=47104 (46 MiB), t=1, p=1` or `m=9216 (9 MiB), t=4, p=1`.

**bcrypt** — cost factor 10–12 in 2026. **The cost is a power of two**: cost 12 is 2^12 = 4096
iterations, so each increment *doubles* the work.

**Target: 250–500 ms per hash on your production hardware.** That is imperceptible to a legitimate
user logging in once, and it is devastating to an attacker who must do it billions of times. **Tune
it by measuring on your own hardware**, not by copying a number.

The tension to be aware of: a slow hash is also a **denial-of-service** surface, since each login
attempt costs you real CPU. Rate limit login endpoints (Day 122), and consider a work-factor budget
per IP.

## Java

```java
// Argon2id via Spring Security Crypto (needs BouncyCastle)
Argon2PasswordEncoder encoder = Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8();
String hash = encoder.encode(rawPassword);
boolean ok  = encoder.matches(rawPassword, hash);

// bcrypt
BCryptPasswordEncoder bcrypt = new BCryptPasswordEncoder(12);
```

**The stored value is self-describing** — algorithm, parameters and salt are all inside it:

```
$argon2id$v=19$m=19456,t=2,p=1$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
 ↑algorithm  ↑version ↑parameters        ↑salt        ↑hash

$2b$12$LQv3c1yqBWVHxkd0LHAkCOYz6TtxMQJqhN8/LewKyDkNiWMEZ0aFe
 ↑bcrypt ↑cost ↑───────salt(22)──────↑─────────hash──────────
```

That self-description is what makes upgrades possible:

```java
// DelegatingPasswordEncoder — the production pattern
Map<String, PasswordEncoder> encoders = Map.of(
    "argon2", Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8(),
    "bcrypt", new BCryptPasswordEncoder(12));
PasswordEncoder encoder = new DelegatingPasswordEncoder("argon2", encoders);

// stored as {bcrypt}$2b$10$… or {argon2}$argon2id$…
// verifies BOTH; new passwords use argon2
```

## Upgrading a legacy hash store

You cannot rehash without the plaintext, so:

**Strategy A — lazy upgrade (standard).** On successful login you hold the plaintext for a moment;
rehash with the new algorithm and replace the stored value.

```java
if (encoder.matches(raw, stored)) {
    if (encoder.upgradeEncoding(stored)) {          // outdated algorithm or parameters
        user.setPasswordHash(encoder.encode(raw));
        repository.save(user);
    }
    return success(user);
}
```

Most active users migrate within weeks. Dormant accounts stay on the old hash — which is why you pair
it with:

**Strategy B — hash the hash (for an urgent upgrade).** Wrap every existing hash immediately:

```
new = argon2(old_md5_hash)
```

Every stored value is protected by argon2 *today*, without needing anyone to log in. Store which
scheme applies, verify by applying the same chain, and migrate to a clean argon2 hash lazily at next
login. This is what you do the day you discover the previous team used unsalted MD5.

# Part 4 — The rest of the password system

## Password policy — what modern guidance actually says

**NIST SP 800-63B reversed decades of advice**, and knowing the reversal is a strong interview
signal:

| ❌ Obsolete | ✅ Current |
|---|---|
| Composition rules (upper + digit + symbol) | **No composition rules** |
| Forced periodic expiry | **No expiry** — only on evidence of compromise |
| Maximum length limits | **Minimum 8, allow at least 64** |
| Blocking paste | **Allow paste** — password managers need it |
| Security questions | ❌ Not acceptable as a factor |
| — | ✅ **Check against known-breached password lists** |
| — | ✅ Allow all printable characters, including spaces and Unicode |

The reasoning: composition rules produce `Password1!` — predictable transformations that attackers
model perfectly, while *reducing* the effective search space and pushing users to write passwords
down. Forced rotation produces `Password1!` → `Password2!`. **Length and non-reuse do far more work
than complexity.**

The single most effective control is **checking against breached lists**:

```java
// Have I Been Pwned, using k-anonymity — you never send the password or its full hash
String sha1 = sha1Hex(password).toUpperCase();
String prefix = sha1.substring(0, 5);                  // send only 5 hex characters
String suffix = sha1.substring(5);
// GET https://api.pwnedpasswords.com/range/{prefix} → ~500 suffixes with counts
boolean breached = response.lines().anyMatch(l -> l.startsWith(suffix));
```

The k-anonymity design is worth understanding: the server sees a 5-character prefix matching hundreds
of thousands of possible passwords, so it learns nothing — and you get a definitive answer. Rejecting
breached passwords blocks credential stuffing, which is how most account takeovers actually happen.

## Password reset — the most-attacked flow

```java
String token = generateToken();                        // 32 bytes from SecureRandom
store(user.id(), sha256(token), Instant.now().plus(15, MINUTES), /*used*/ false);
sendEmail(user.email(), configuredBaseUrl + "/reset?token=" + token);   // ← NOT the Host header
```

Every element is a defence:

| Rule | Attack prevented |
|---|---|
| **`SecureRandom`, ≥32 bytes** | Token prediction (`Random` is seeded and predictable) |
| **Store the *hash* of the token** | A database leak otherwise hands over live reset tokens |
| **Short expiry (15–60 min)** | Window of exposure |
| **Single use — invalidate on use** | Replay |
| **Invalidate on password change** | Stale tokens |
| **Configured base URL** | `Host`-header injection sending the token to an attacker (Day 105) |
| **Identical response for unknown email** | User enumeration (Day 111) |
| **Rate limit per email and per IP** | Mass reset spam |
| **Invalidate all sessions after reset** | The attacker's existing session survives otherwise |
| **Email the user that a reset occurred** | Detection |

**The "store the hash of the token" rule is the one most often missed.** A reset token stored in
plaintext is a password equivalent — anyone with read access to that table can take over any account
without knowing a password.

## Storage and operational hygiene

- **Never log a password**, in any form, at any level — including in a request-body dump (Day 073A).
- **Never put a password in a URL** — URLs land in access logs, browser history, and `Referer`
  headers.
- **Always TLS.** A perfectly hashed password sent over HTTP is plaintext on the wire.
- **Column type:** `varchar(255)` or larger — argon2 output plus parameters is long, and you will
  change algorithms.
- **Never return the hash** in any API response (Day 105's response-DTO rule).
- **Rehash on login when parameters change** (`upgradeEncoding`).

## Common mistakes

| Mistake | Consequence |
|---|---|
| SHA-256 or MD5 for passwords | Billions of guesses per second on a GPU |
| No salt | Rainbow tables; identical passwords visible |
| One salt for the whole application | Same as no salt against a targeted attack |
| `Random` instead of `SecureRandom` | Predictable salts and tokens |
| **Encrypting** passwords | A stolen key reveals everything |
| Emailing a password back | Proof it was stored recoverably |
| bcrypt with a >72-byte password | Silently truncated |
| Copying a work factor without measuring | Too weak, or a self-inflicted DoS |
| Composition rules and forced expiry | `Password1!` → `Password2!` |
| Blocking paste | Defeats password managers |
| No breached-password check | Credential stuffing succeeds |
| Reset tokens stored in plaintext | The token table is a master key |
| Reset URL built from the `Host` header | Token delivered to the attacker |
| Not invalidating sessions after a reset | The attacker keeps their session |
| Logging request bodies containing passwords | Plaintext passwords in your log pipeline |

## Interview questions

**Q: How do you store passwords?**
Hash them with a deliberately slow, memory-hard algorithm — Argon2id, or bcrypt as an acceptable
alternative — with a unique random salt per password, tuned to about 250–500 ms on production
hardware. Never encrypt, never a fast hash, and check new passwords against breached lists.

**Q: Why not SHA-256?**
It is designed to be fast — tens of billions of hashes per second on a GPU — which is exactly wrong
for passwords. Password hashing must be tunably slow.

**Q: What is a salt and what does it prevent?**
A unique random value per password, stored alongside the hash. It defeats precomputed rainbow tables
and stops identical passwords producing identical hashes, which would otherwise let one crack break
many accounts and reveal password-sharing patterns.

**Q: Does the salt need to be secret?**
No. Its purpose is to defeat precomputation, not to be secret. A *pepper* is the secret one, stored
outside the database, and it protects against a database-only compromise.

**Q: Why is memory-hardness important?**
GPUs and ASICs parallelise cheap computations massively but have limited memory per core. Requiring
tens of megabytes per hash makes that parallelism expensive, which bcrypt and PBKDF2 do not.

**Q: How do you migrate from MD5 to Argon2?**
Lazily on login with a `DelegatingPasswordEncoder` — verify the old scheme, rehash with the new one
while you have the plaintext. For urgency, wrap every existing hash immediately with
`argon2(old_hash)` so nothing is left unprotected, then clean up lazily.

**Q: What does current password-policy guidance say?**
NIST reversed the old advice: no composition rules, no forced expiry, a minimum of 8 with at least 64
allowed, allow paste and all characters — and check against known-breached lists, which is the single
most effective control.

**Q: How do you build a secure password reset?**
A high-entropy `SecureRandom` token, **stored hashed**, short-lived, single-use, delivered to a URL
built from configured configuration rather than the `Host` header, with identical responses for
unknown emails, rate limiting, and all sessions invalidated on completion.

## Mini task

1. Hash the same password with SHA-256, bcrypt(12) and Argon2id. Time 1,000 iterations of each.
   Record the ratio.
2. Hash `password123` twice with each. Observe that SHA-256 produces identical output and the other
   two do not.
3. Tune Argon2 parameters on your machine to land between 250 and 500 ms. Record the values.
4. Decode a bcrypt and an Argon2 hash by hand, identifying algorithm, parameters, salt and digest.
5. Implement `DelegatingPasswordEncoder` with bcrypt as legacy and argon2 as current. Create a bcrypt
   user, log in, and confirm the stored hash upgraded to argon2.
6. Implement the "hash the hash" migration for a table of unsalted MD5 hashes, and verify logins
   still work.
7. Implement the HIBP k-anonymity check. Test it with `password123` and with a random 20-character
   string. Confirm you never transmit the full hash.
8. Build the full reset flow with every rule from the table. Then break each rule in turn and write
   down the exact attack it enables.
9. Attempt bcrypt with a 100-character password and demonstrate that characters past 72 are ignored.
10. Grep a project's logs and code for anywhere a password could be logged — request-body dumps,
    `toString`, debug statements.
