# Day 318

**L-318** · A logging framework & a notification service — designing for extension

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Both problems ask the same thing: build something whose entire purpose is to be extended by
> people you will never meet.**
>
> And both have a hard question that is not about the pattern. **Logging's is what happens when the
> queue is full. Notification's is what happens when one channel is down.**

---

# Part 1 — ⭐ The logging framework

```
   Logger("com.app.orders")
      │  ⭐ 1. is this level enabled?      ← level, INHERITED from the parent logger
      │  ⭐ 2. build the LogEvent          ← lazily; see the parameterised-message rule
      ▼
   Appender[]  ──► Formatter ──► destination     ⭐ console, file, socket, ELK
      ⭐ (also inherited, and ADDITIVE up the tree)
```

## ⭐ The hierarchy — the part most candidates miss

**⭐ Logger names form a tree by dot-separated prefix, and both level and appenders are inherited.**
That is the feature that makes a real logging framework usable:

```
⭐ root                 = WARN,  appenders: [console]
⭐ com.app              = INFO   ⭐ inherits console
⭐ com.app.orders       = (none) ⭐ inherits INFO from com.app
⭐ com.app.orders.sql   = DEBUG, appenders: [file]   ⭐ console + file (ADDITIVE)
```

| ⭐ Rule | ⭐ Design |
|---|---|
| ⭐ **Effective level = nearest ancestor with a level set** | ⭐ walk up on lookup, then **cache it** |
| ⭐ **Appenders are additive by default** | ⭐ with an `additivity=false` escape hatch |
| ⭐ Loggers are cached by name | ⭐ `getLogger()` must be cheap — it is called from static initialisers |
| ⭐ **Reconfiguration invalidates the cache** | the subtle bug: changing `com.app`'s level must affect children |

> **⭐ Say it: "the logger name is a path, and configuration resolves up the tree. That is why you can
> turn on DEBUG for one package without touching anything else, and it is the feature the whole
> design exists for."**

## ⭐ The performance rule that explains the API

```java
log.debug("Loaded " + orders.size() + " orders for " + customer);   // ⭐ string built ALWAYS
log.debug("Loaded {} orders for {}", orders.size(), customer);      // ⭐ built only if DEBUG is on
if (log.isDebugEnabled()) log.debug(expensive());                   // ⭐ for genuinely costly arguments
log.debug("state: {}", () -> expensiveDump());                      // ⭐ supplier form — best of both
```

**⭐ This is the single most useful thing to know about logging design**, and it explains an API
people use without understanding: **the placeholder form exists so the message is not constructed
when the level is disabled.** In a hot path with debug off, concatenation is pure waste — and it is
one of the most common real performance findings.

## ⭐⭐ The hard question: the async appender's queue

```
⭐ log call ──► BlockingQueue<LogEvent> ──► one writer thread ──► disk/socket
                        │
                        ⭐ WHAT HAPPENS WHEN IT IS FULL?
```

| Policy | ⭐ Consequence | ⭐ Right when |
|---|---|---|
| ⭐ **Block** | ⭐⭐ **logging now degrades your application — an outage caused by the log sink** | ⭐ audit logs you may not lose |
| ⭐ **Drop newest** | ⭐ you lose the events during the incident — **exactly the ones you need** | rarely |
| ⭐ **Drop oldest** | ⭐ **keeps the most recent, which is usually what you want** | ⭐ **the good default** |
| ⭐ Drop by level | ⭐⭐ **discard DEBUG/INFO, never ERROR** | ⭐⭐ **the best answer** |

> **⭐ The insight: an application must not fail because its logging destination is slow.** A blocking
> queue plus a slow disk turns a logging problem into a request-latency problem — **and this is a
> real production outage pattern.** Dropping by level, with a counter of how many were dropped, is
> the answer that shows operational experience.

⚠️ **Also required: a shutdown hook that flushes.** An async appender loses the last few seconds by
default — **including, very often, the exception that caused the shutdown.**

| Other details worth naming | |
|---|---|
| ⭐ **Capture the thread name and MDC at call time, not write time** | ⭐ the writer thread is a different thread (Day 182) |
| Ordering across appenders | not guaranteed, and does not need to be |
| ⭐ **Never let an appender throw into the caller** | a broken log sink must not break a request |
| Rolling files | size/time-based, with a retention count |

# Part 2 — ⭐ The notification service

```
   Event ──► Router ──► [preferences, rules] ──► Channel(s) ──► Provider
                                                    │
                            ⭐ EMAIL · SMS · PUSH · IN_APP · WEBHOOK
```

```java
public interface NotificationChannel {
    ChannelType type();
    DeliveryResult send(Notification notification);      // ⭐ never throws into the router
    boolean supports(Recipient recipient);               // ⭐ no phone number ⇒ no SMS
}
```

**⭐ The core design decision, and it is Day 308's table again:** a registry of channels, **never a
`switch (type)`**. A new channel is a new class plus a registration — **and that is the requirement
the problem is really testing.**

## ⭐ The layers, in order

| Layer | ⭐ Responsibility | ⭐ Detail that scores |
|---|---|---|
| ⭐ **Preferences** | which channels a user allows, per category | ⭐ **opt-out must be per category, not global** |
| ⭐ **Quiet hours** | do not wake people at 3am | ⭐ **in the recipient's timezone — the classic bug** |
| ⭐ **Rules/routing** | ⭐ which channels for which event | ⭐ **rules as data** (Day 290) |
| ⭐ **Templating** | one template per (event, channel, locale) | ⭐ SMS has 160 chars; email does not |
| ⭐ **Rate limiting** | ⭐ per user, per category | ⭐ **Day 314's token bucket, reused** |
| ⭐ **Deduplication** | the same event twice | ⭐ an idempotency key on (event id, user, channel) |
| ⭐ **Delivery** | send, retry, record | ⭐ **per-channel isolation — see below** |

## ⭐⭐ The hard question: one channel is down

```
⭐ An order ships. Send email + SMS + push.
⭐ The SMS provider is timing out at 30 seconds.
⭐ ⇒ Does the email go out?
```

| ⭐ Requirement | ⭐ Design |
|---|---|
| ⭐ **Channels must not block each other** | ⭐ **fan out to independent tasks; never a sequential loop** |
| ⭐ **A failing channel must not retry forever** | ⭐ a circuit breaker per provider (Day 181) |
| ⭐ **Retries must not duplicate** | ⭐ the provider call needs an idempotency key |
| ⭐ **Retry with backoff and jitter** | ⭐ 1s, 4s, 16s — **jitter, or the whole fleet retries together** |
| ⭐ **Give up somewhere** | a dead-letter record a human can inspect |
| ⭐ **Failure is per (notification × channel)** | ⭐ **the delivery record is one row per attempt per channel** |

> **⭐ Say it: "delivery status belongs to the pair of notification and channel, not to the
> notification. 'Sent' is not a property of an event — an order-shipped email can succeed while the
> SMS is still retrying."** That one modelling sentence answers half the follow-ups in this problem.

## ⭐ Two extensions that are always asked

| "Now add…" | ⭐ Answer |
|---|---|
| ⭐ **Digests** ("one email an hour, not forty") | ⭐ a buffer per (user, category) with a flush window — **and a priority escape so urgent messages bypass it** |
| ⭐ **Priority** | ⭐ **separate queues, not a priority field** — a single queue behind 10,000 marketing messages delays the password reset |
| Scheduled sends | a due-time index and a poller — Day 178's distributed scheduling problem |
| Multi-language | template per locale; fall back to default |

**⭐ The separate-queues point is the good one.** A priority field inside one queue still puts the
urgent message behind whatever is currently being processed; **separate queues with separate workers
is the design that actually delivers on the promise.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No logger hierarchy | ⭐ you cannot enable DEBUG for one package — the whole point |
| ⭐ String concatenation in log calls | ⭐ messages built when the level is off |
| ⭐⭐ **A blocking async queue** | ⭐⭐ **a slow log sink becomes a slow application** |
| Dropping newest under pressure | you lose exactly the incident's events |
| ⭐ No flush on shutdown | ⭐ the last seconds — often the fatal exception — are lost |
| MDC read on the writer thread | wrong correlation ids on every line |
| ⭐ An appender that throws | a broken sink breaks the request |
| ⭐ `switch (channelType)` | ⭐ a new channel edits every switch |
| ⭐⭐ **Sequential channel delivery** | ⭐⭐ **one slow provider blocks all the others** |
| ⭐ Delivery status on the notification | you cannot represent "email sent, SMS failing" |
| Retries with no idempotency key | duplicate texts to real people |
| ⭐ Quiet hours in server time | ⭐ 3am messages to half your users |
| Global opt-out only | users unsubscribe from everything to stop one thing |
| A priority field in one queue | urgent messages still queue behind bulk |

## Interview questions

**Q: What makes a logging framework more than a `println` wrapper?**
The hierarchy. Logger names are dot-separated paths, and level and appenders resolve up that tree, so
you can turn on DEBUG for one package without touching anything else. That resolution is cached, and
the subtle bug is forgetting to invalidate the cache when configuration changes, so a level change on
a parent silently does not reach its children.

**Q: Why does the logging API use `{}` placeholders?**
So the message is not built when the level is disabled. String concatenation happens before the call
regardless of level, so a debug line in a hot path costs allocation and formatting even in
production. The placeholder form defers it, and the supplier form defers genuinely expensive
arguments entirely.

**Q: Your async appender's queue is full. What do you do?**
Not block — a slow log destination must never become application latency, and that is a real outage
pattern. I drop by level: discard DEBUG and INFO, keep WARN and ERROR, and increment a dropped-event
counter so the loss is visible. If the logs are audit records that may not be lost, that is a
different product and blocking or spilling to disk becomes defensible — but then it is a durability
requirement, not logging.

**Q: An order ships and the SMS provider is timing out. What happens to the email?**
It goes out. Channels fan out to independent tasks rather than a sequential loop, so one provider
cannot block the others, and each provider has its own circuit breaker. Delivery status lives on the
notification-and-channel pair rather than the notification, so "email delivered, SMS retrying" is
representable — which it has to be, because it is the normal case.

**Q: How would you add priority?**
Separate queues with separate workers, not a priority field. A field still leaves the password-reset
message behind whatever the single queue is currently working through. With separate queues the
urgent path has its own capacity, and I can size and monitor it independently.

## Mini task

1. Implement the **logger hierarchy** with inherited levels and additive appenders. Test: set
   `com.app` to INFO, assert `com.app.orders` inherits it, **then change the parent and assert the
   child follows.**
2. Cache the effective level, **then reproduce the stale-cache bug** and fix it.
3. Benchmark concatenation vs placeholders with the level **disabled**, one million calls. **Record
   both numbers.**
4. ⭐ Build the async appender. **Fill the queue with a deliberately slow sink** and measure caller
   latency under each of the four policies. Implement drop-by-level with a counter.
5. Kill the process with events queued. **Add a shutdown flush and confirm the last events arrive.**
6. Capture MDC at call time; then move it to write time and **watch the correlation ids scramble.**
7. ⭐ Build the notification router with three channels. **Make one sleep 30 seconds and assert the
   other two still deliver within a second.**

   idempotency key. **Force a duplicate send and confirm one delivery.**
9. Implement quiet hours **in the recipient's timezone** and write the test that fails in server
   time.

## 🎙️ Articulation drill

**Two minutes:** *"One of your notification providers starts timing out. Walk me through what your
system does."*

**⭐ The full answer has four beats:** the channels fanned out independently so nothing else is
blocked · the circuit breaker opens after N failures so you stop hammering a dead provider ·
retries are backed off, jittered and idempotent · **and the delivery record is per channel, so the
system's state is "email delivered, SMS failing" rather than a single ambiguous flag.**

**⭐ That last beat is the modelling answer, and it is the one that distinguishes a design from a
list of libraries.**
