# Day 252 🚪🏗️

**P-252** · The design review gate — before a single line of code

**Time:** 3 hrs · **Mode:** REVIEW · **Gate**

> **⭐ Today you review your own design as if someone else wrote it, and you do it out loud.**
>
> Four days of decisions are now committed to files. The cost of changing them is currently a text
> edit. **From tomorrow it becomes a migration, a refactor, and every call site** — so this is the
> last cheap opportunity to find the thing you got wrong.
>
> Day 100 taught code review from both sides. **Today is that, applied to a design, with you on both
> sides.**

# Part 1 — ⭐ The self-review, done adversarially

**⭐ Print your four documents. Read them in this order, looking for a specific failure each time.**

### ⭐ Pass 1 — `SCOPE.md`: is this finishable?

| Question | ⭐ Fail signal |
|---|---|
| Can one person build this in the days allotted? | ⭐ "if everything goes well" |
| Is there **one** core flow? | you list three "core" flows |
| ⭐ Did anything creep back in from the out-of-scope list? | ⭐ **the most common failure** |
| Would cutting 30% still leave a defensible project? | ⭐ if no, you have no margin |

**⭐ Cut something today.** Not because it is bad, but because a finished project with four features
beats an abandoned one with seven, and **you will not have this clarity again once you are attached
to code you have written.**

### ⭐ Pass 2 — requirements: can you test every line?

| Question | Fail signal |
|---|---|
| ⭐ Does every AC map to exactly one test? | an AC you cannot imagine asserting |
| ⭐ Does every writing story answer "what if two at once?" | ⭐ silence |
| Does every NFR have a number? | "fast", "reliable" |
| ⭐ Are system-triggered transitions listed? | you found a new one — good, add the job |

### ⭐ Pass 3 — the schema: what will hurt in a year?

| Question | Fail signal |
|---|---|
| ⭐ Which column will need splitting or widening? | ⭐ you have not asked |
| Is every invariant a constraint, not a convention? | "the service always sets it" |
| ⭐ Is the hard problem enforced **in the schema**? | it is enforced in a service method |
| Is anything unbounded? | an events table with no partitioning and a retention policy |
| ⭐ Does every query in the list have an index? | ⭐ and is the leading column right? |

### ⭐ Pass 4 — the contract: would you consume this?

| Question | Fail signal |
|---|---|
| ⭐ Does the client need three calls where one would do? | you found this at the mock stage — fix it |
| Is every error documented and actionable? | a `type` with no "client should" |
| ⭐ Can a client detect and avoid a lost update? | no `ETag`/`If-Match` |
| Can a client retry safely? | no `Idempotency-Key` |

# Part 2 — ⭐ The five ADRs, and the section that matters

**⭐ By the end of today you have five ADRs committed** (Day 101's format):

| ADR | Subject |
|---|---|
| 0001 | Project choice and scope |
| 0002 | Schema and identity decisions |
| 0003 | API contract decisions |
| ⭐ **0004** | ⭐ **The hard problem: how concurrency is handled** |
| ⭐ **0005** | ⭐ **Technology choices** — and the ones you rejected |

**⭐ ADR-0004 is the one an interviewer will read first if you show them the repository.** It should
contain Day 249's `HARD-PROBLEM.md` promoted into a decision record: the failure precisely stated,
three candidates with honest trade-offs, the choice, and **how you will prove it**.

**⭐ ADR-0005 must name what you rejected and why**, because that is where the reasoning lives:

```markdown
## Considered and rejected
- ⭐ MongoDB — the domain is relational and needs cross-entity constraints (Day 213's questions)
- ⭐ Redlock for booking exclusivity — not a safety guarantee; the exclusion constraint is (Day 207)
- ⭐ Kafka — the outbox plus a poller is sufficient at this volume; ⭐ Kafka is an operational
     commitment I do not need yet (Day 185A)
- ⭐ Microservices — one deployable, one team of one. ⭐ Splitting would add network calls and
     distributed transactions to solve an organisational problem I do not have
```

**⭐ That last entry is worth writing carefully.** "Why is this not microservices?" is asked
constantly, and **"because a modular monolith was correct for the constraints"** is a much stronger
answer than an apology.

# Part 3 — ⭐ Rehearse the defence, out loud, recorded

**⭐ This is the part people skip and it is the highest-return hour of the design phase.** You will
give these answers dozens of times. Find out now which ones you cannot give.

### ⭐ The five-minute walkthrough

**Record yourself.** Problem, users, the one core flow, the hard problem, the architecture in one
sentence, and **one decision with its trade-off**.

**⭐ Play it back and check three things:**

| Check | Fail signal |
|---|---|
| ⭐ Did you say what it *does* before what it *uses*? | ⭐ you opened with "Spring Boot, PostgreSQL, Redis" |
| ⭐ Did you name a trade-off unprompted? | you described only benefits |
| Did you finish inside five minutes? | you are still on the schema at minute six |

**⭐ Opening with the tech stack is the most common self-inflicted wound.** The technology is
uninteresting; the problem and the decisions are what is being assessed.

### ⭐ The twelve questions

**Answer each aloud, without notes. Any you cannot answer is a design hole, not a memory problem.**

1. What does it do, in thirty seconds?
2. ⭐ **What is the hardest technical problem, and how did you solve it?**
3. ⭐ **What happens when two users do that simultaneously?** Walk me through it.
4. ⭐ **Why is that enforced in the database rather than the application?**
5. Why is your primary key not in the URL?
6. ⭐ **Why 404 rather than 403 for someone else's record?**
7. ⭐ **How does a client avoid overwriting another client's change?**
8. What happens if a client retries a request that timed out?
9. ⭐ **What breaks first at 100× the traffic?**
10. ⭐ **What did you deliberately leave out, and why?**
11. Why this datastore? What would change your mind?
12. ⭐ **Why is this not microservices?**

**⭐ Question 9 deserves preparation.** The answer is usually one of: the connection pool (Day 156),
an unindexed query that is fine at current volume (Day 189), a single-instance job (Day 178), or the
hot key in your cache (Day 206). **Knowing which, for your own design, is a strong signal.**

### ⭐ Then get it reviewed by a human

**⭐ Send the four documents to someone and ask them to find the flaw.** A peer, a mentor, a
community. **The specific ask matters: "what would you push back on?" gets you far more than "does
this look good?"**

# Part 4 — ⭐ Set up the tracks you will run on

**⭐ Before tomorrow's first line of code, put the rails in place.** Every one of these is
significantly harder to add later.

| Track | Set up today |
|---|---|
| ⭐ **Repository** | branch protection, ⭐ a PR template with a checklist (Day 100) |
| ⭐ **CI skeleton** | ⭐ build + test on every push — **even with zero tests** |
| ⭐ **Issue list** | ⭐ one issue per acceptance criterion, in dependency order |
| **Definition of done** | ⭐ written down — see below |
| ⭐ **A decision log** | `docs/adr/` — you will add to it weekly |

### ⭐ Your definition of done, written now

```markdown
# docs/DEFINITION-OF-DONE.md
A feature is done when:
- [ ] ⭐ Acceptance criteria have tests, and they pass
- [ ] ⭐ A negative authorization test exists (Day 169 — the failure is a 200 to the wrong person)
- [ ] ⭐ Query count asserted where it touches the database (Day 160)
- [ ] Errors follow the contract; new ones are in ERRORS.md
- [ ] ⭐ The OpenAPI diff is reviewed (Day 251)
- [ ] Logs are structured with the correlation ID (Day 182)
- [ ] ⭐ It is deployed and I have seen it work in the deployed environment
```

**⭐ Writing this today is what stops "done" from drifting to "it compiles" in week four.**

### ⭐ Deploy the empty application

**⭐ Before writing a feature, deploy something.** A Spring Boot app with a health endpoint, in a
container, on a real host, with a metric visible.

**⭐ The reason is Day 185's checklist: it is far easier to satisfy incrementally.** A project deployed
on day one gets deployed a hundred times; a project deployed at the end gets deployed once, badly,
under time pressure — and every item on the production checklist arrives at the same moment.

## 🚪 ⭐ The gate — you may not proceed until

- [ ] ⭐ **Scope cut at least once today**
- [ ] Every AC is testable; every NFR has a number
- [ ] ⭐ The hard problem is enforced **in the schema**, and you can state why
- [ ] ⭐ **All five ADRs committed**, each with an honest consequences section
- [ ] ⭐ ADR-0005 names what you **rejected**
- [ ] ⭐ You recorded the five-minute walkthrough and **it opens with the problem, not the stack**
- [ ] ⭐ You answered **all twelve questions aloud**, and fixed the design where you could not
- [ ] ⭐ **A human has reviewed it and you acted on at least one piece of feedback**
- [ ] CI runs; the definition of done is written
- [ ] ⭐ **An empty application is deployed with a health check**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Skipping the review because "it is my own project" | ⭐ the whole point is finding it while it is cheap |
| Reviewing without looking for a specific failure | you confirm rather than examine |
| ⭐ Not cutting scope | ⭐ the leading cause of an unfinished flagship |
| Not rehearsing aloud | you discover you cannot explain it in the interview |
| Opening the walkthrough with the tech stack | you sound like a CV |
| ⭐ ADRs with no consequences section | a press release |
| ⭐ Not deploying the empty app | Day 185's checklist arrives all at once, at the end |
| No CI until there are tests | there are never tests |

## ✅ Done when

- Every gate box is ticked
- ⭐ **You changed at least one design decision as a result of today**
- The repository has five ADRs, a running CI, and a deployed health check
