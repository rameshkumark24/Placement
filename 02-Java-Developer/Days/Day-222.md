# Part 1 — Why there is a build

Java compiles to bytecode, ships a jar, and reads config at runtime. **The browser inverts all three.**

| ⭐ Job | Why |
|---|---|
| **Transform** | TS → JS, JSX → function calls. ⭐ The browser knows neither. |
| **Bundle** | ⭐ 400 modules = 400 requests without it. ⭐⭐ Closest thing to a fat jar — but the *user* downloads it. |
| **⭐⭐ Tree-shake** | Delete code nobody imports. **The main size lever.** ⭐ Nothing in Maven does this; an unused class in a jar costs disk, not user time. |
| **Minify** | Rename locals, strip whitespace. ⭐ ~40% before gzip |
| **Hash filenames** | ⭐⭐ `app.9f2c1a.js` → cache **forever**, invalidate by *changing the name*. Day 245. |
| **Split** | ⭐ Per-route chunks so the login page does not ship the dashboard |

```
⭐⭐ DEV VS PROD ARE DIFFERENT PROGRAMS
⭐   dev   ⇒ no bundling, source as written, hot reload, huge
⭐   prod  ⇒ bundled, tree-shaken, minified, hashed, split
⭐   ⇒ ⭐⭐ NEVER MEASURE PERFORMANCE IN DEV MODE. React alone is
⭐     several times slower there. ⭐ It is benchmarking with
⭐     -Xint and concluding the JVM is slow.
```

# Part 2 — Modules and tree-shaking

```javascript
export function a() {}
export function b() {}
import { a } from "./x";        // ⭐⭐ b is DELETED from the bundle
```

```
⭐⭐ THE THREE THINGS THAT DEFEAT TREE-SHAKING

⭐ ① import * as _ from "lodash"   ⇒ ⭐⭐ THE WHOLE LIBRARY SHIPS.
⭐    ✅ import debounce from "lodash/debounce"

⭐ ② ⭐ CommonJS deps (require/module.exports). ⭐⭐ CJS IS DYNAMIC,
⭐    so the bundler CANNOT PROVE an export is unused — much like
⭐    ⭐ REFLECTION DEFEATS ANY JAVA SHRINKER (ProGuard needs
⭐      keep-rules for the same reason).

⭐ ③ ⭐⭐ SIDE EFFECTS. If importing a module DOES something —
⭐    registers a polyfill, mutates a prototype — dropping it would
⭐    change behaviour, so it is kept.
⭐    ⇒ "sideEffects": false is you PROMISING it is safe to drop.
```

> ⭐ **`import type { User } from "./types"`** — the `type` keyword guarantees the import vanishes at
> compile time and cannot drag a runtime module into the bundle.

# Part 3 — ⭐⭐ The leaked secret

```
⭐⭐ THE HABIT THAT DOES NOT PORT.

⭐   In Spring: application.properties holds your DB password, it
⭐     stays on the server, and only your code reads it. ⭐ SAFE.
⭐   In the browser: ⭐⭐ THERE IS NO SERVER SIDE. The bundle IS the
⭐     deliverable, and the user has it.

⭐   .env
⭐     VITE_API_URL=https://api.example.com     ⭐ fine — public anyway
⭐     VITE_STRIPE_SECRET=sk_live_abc123        ⭐⭐ NOW PUBLIC. FOREVER.

⭐   ⇒ the bundler INLINES it as a literal string in app.js
⭐   ⇒ ⭐⭐ ANYONE CAN VIEW-SOURCE, Ctrl-F "sk_live", AND BILL YOU.
⭐   ⇒ ⭐ AND IT IS IN GIT HISTORY, EVERY CDN CACHE, AND PROBABLY AN
⭐     ARCHIVE. ⭐⭐ ROTATION IS THE ONLY FIX.
```

| ⭐ Rule | |
|---|---|
| **The prefix is a warning, not a guard** | ⭐⭐ `VITE_` / `NEXT_PUBLIC_` exists to make you *say* "this is public". It **exposes**. |
| **A frontend has no secrets** | ⭐ Publishable keys yes (`pk_live_`), secret keys never |
| **Minification ≠ security** | ⭐⭐ Renaming locals is not encryption — and unlike a jar, there is no "well, they'd have to decompile it" comfort. **One click prettifies it.** |
| **Grep before deploy** | ⭐ `grep -rE "sk_live\|secret\|BEGIN PRIVATE" dist/` in CI |

```javascript
// ❌ the shape that leaks
const res = await fetch("https://api.openai.com/v1/...", {
  headers: { Authorization: `Bearer ${import.meta.env.VITE_OPENAI_KEY}` }
});   // ⭐⭐ your key, in the browser, on every visitor's machine

// ✅ your Spring API holds the key and enforces the limits
const res = await api("/ai/summarise", { method: "POST", body: { text } });
//    ⭐ and THAT endpoint checks auth, rate-limits, and caps spend
```

> ⭐⭐ **This is the "huge surprise bill" failure from the repo README, in its exact form.** A key in a
> bundle is scraped by bots within hours. **The fix is architectural: the browser calls *your* API, and
> your API holds the credential** — which is the shape you already use for every other downstream
> service.

# Part 4 — Source maps, and the debugging trade

| ⭐ Option | Effect |
|---|---|
| **No source maps** | ⭐ Stack traces read `a.js:1:48211` — undebuggable, like a stack trace with no line numbers |
| **⭐⭐ Public source maps** | Readable traces for you *and* readable source for everyone. **Fine for most apps** — the bundle was already readable |
| **⭐ Upload to Sentry, don't serve** | Readable traces in your tooling, no `.map` on the CDN. **The default you want** (Day 279) |

> ⭐ **Source maps do not leak secrets that were not already leaked.** The bundle contains everything;
> the map only makes it pleasant to read — it is shipping the debug symbols, not the source of truth.
> **If a source map would expose something, you had already exposed it.**

```
⭐⭐ THE BUNDLE BUDGET — set it before you need it
⭐   initial JS  < 150–200 KB gzipped
⭐   ⇒ ⭐ CI FAILS THE BUILD when exceeded, so growth is a decision
⭐     someone made rather than drift nobody saw.
```

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "what actually ships in your frontend build, and what can't?"**

Start with the habit that doesn't port, since that is the concrete risk. **In Spring, config lives in
`application.properties` on the server and only my code reads it. In the browser there is no server
side — the bundle is the deliverable and the user has it. So every value that reaches the build is a
value I've published, and the only question is whether I meant to.**

Make the failure concrete. **The one people actually ship is a secret key in an env var. The bundler
inlines it as a literal string, so it's view-source and Ctrl-F away, and it's simultaneously in git
history, every CDN cache and probably an archive — rotation is the only fix. The `VITE_` prefix isn't a
guard, it's a warning label meaning "this will be exposed." And minification isn't protection: unlike a
jar, there's not even the "they'd have to decompile it" comfort — it's one click to prettify.**

Then the architectural fix. **A frontend has no secrets. If a call needs a credential, the browser calls
my API and my API holds it — which also gives me the place to enforce auth, rate limits and a spend cap.
That's the same shape I already use for every downstream service.**

Close on the thing people get backwards. **Source maps. They don't leak anything the bundle didn't
already contain — they're debug symbols, not the source of truth. Teams give up production debugging
over that misunderstanding. I upload them to Sentry rather than serving them.**
