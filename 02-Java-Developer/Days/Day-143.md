**L-143** · Actuator — health, readiness, metrics, and the endpoints that leak

# Part 1 — What you get, and what you should expose

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

By default over HTTP, Boot exposes **`/actuator/health` only**. That default is correct, and every
change to it should be deliberate.

| Endpoint | What it gives you | Expose? |
|---|---|---|
| `health` | up/down + component detail | ✅ public path OK, **details restricted** |
| `info` | build version, git commit | ✅ useful for "what is actually deployed?" |
| `metrics`, `prometheus` | Micrometer meters (Day 128) | ✅ internal only |
| `env` | **every property and its source** | 🔒 internal + authenticated |
| `configprops` | every `@ConfigurationProperties` bean, bound | 🔒 internal + authenticated |
| `loggers` | read **and change** log levels at runtime | 🔒 — this one is a write endpoint |
| `threaddump` | Day 076's thread dump over HTTP | 🔒 |
| `heapdump` | **downloads the entire heap** | 🔒🔒 contains passwords, tokens, customer data |
| `mappings` | every URL the app serves | 🔒 a map of your attack surface |
| `beans`, `conditions` | Day 140's conditions report | 🔒 |
| `shutdown` | **stops the application** | ❌ disabled by default; leave it off |

**`heapdump` and `shutdown` are the two that turn a misconfiguration into an incident.** A heap dump
contains every string in memory: database passwords, JWT signing keys, session tokens, customer PII.
It is a complete compromise in one HTTP GET. This is not hypothetical — publicly exposed Actuator
endpoints are a standing category in internet-wide scans, and `env`/`heapdump` are what the scanners
look for.

## The configuration you actually want

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus       # ⭐ allow-list, never "*"
      base-path: /actuator
  endpoint:
    health:
      show-details: when-authorized           # ⭐ not "always"
      show-components: when-authorized
      probes:
        enabled: true                         # ⭐ liveness + readiness groups
  server:
    port: 9090                                # ⭐ separate port
  info:
    env:
      enabled: true
```

Two decisions there are worth stating explicitly.

**`include: health,info,prometheus`, never `*`.** Day 108's principle — allow-list, never deny-list —
applies here exactly. With `*`, adding a dependency that ships a new endpoint exposes it silently.

**`management.server.port: 9090`.** The management port is separate from the application port, so
your ingress or load balancer publishes 8080 to the internet and 9090 goes nowhere near it. This is
the single highest-value line in the file: it makes the exposure question a network fact rather than
a configuration promise. Combine with `management.server.address: 127.0.0.1` where the metrics
scraper is a sidecar.

# Part 2 — Health, and Day 128's distinction implemented

With `probes.enabled: true` you get three endpoints:

```
/actuator/health              ← aggregate, everything
/actuator/health/liveness     ← ⭐ "is this JVM broken beyond recovery?"
/actuator/health/readiness    ← ⭐ "should this instance receive traffic?"
```

**The rule from Day 128, restated as a wiring rule:**

> **A dependency check belongs in readiness, never in liveness.**

If the database is down and it appears in your *liveness* check, Kubernetes kills every pod. The pods
restart, still cannot reach the database, and are killed again. You have converted a database outage
into a full crash-loop with no capacity left to serve the cached or degraded responses you could
otherwise have served. That is Day 128's outage, and the wiring above is what prevents it.

Boot gets this right by default: `LivenessStateHealthIndicator` reflects only *internal application
state* — it goes down when the application context has failed irrecoverably, not when Redis is
unreachable. **Your job is to not break that default** by adding dependency indicators to the
liveness group.

```yaml
management:
  endpoint:
    health:
      group:
        readiness:
          include: readinessState, db, redis      # ⭐ dependencies go here
        liveness:
          include: livenessState                  # ⭐ and nowhere else
```

## A custom indicator, and the mistake inside it

```java
@Component
public class PaymentGatewayHealthIndicator implements HealthIndicator {

    private final PaymentGateway gateway;

    @Override
    public Health health() {
        try {
            var status = gateway.ping();                    // ⭐ must have a short timeout
            return Health.up().withDetail("latencyMs", status.latencyMs()).build();
        } catch (Exception e) {
            return Health.status("DEGRADED")                // ⭐ not DOWN — see below
                         .withDetail("error", e.getClass().getSimpleName())
                         .build();
        }
    }
}
```

Three things to get right:

1. **Bound the check.** A health indicator with no timeout means an unhealthy dependency makes your
   health endpoint hang, which makes the probe time out, which takes the pod out for a reason that
   was never the pod's fault. Health checks must be fast and must fail fast.
2. **Do not put the exception message in the detail.** `withDetail("error", e.getMessage())` will
   happily publish `Connection refused: payments-db.internal:5432 user=orders_rw` — an internal
   hostname, port and username, on an endpoint you may have made public. Class name only.
3. **Choose the status honestly.** If payments being down should not stop this instance from serving
   reads, it must not make readiness `DOWN`. Register it as a custom status outside the
   readiness group, or your monitoring will remove all capacity for a partial failure.

```yaml
management.endpoint.health.status.order: DOWN, OUT_OF_SERVICE, DEGRADED, UP
management.endpoint.health.status.http-mapping.DEGRADED: 200      # ⭐ still serving
```

## Kubernetes wiring

```yaml
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 9090 }
  failureThreshold: 3
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 9090 }
  failureThreshold: 2
  periodSeconds: 5
startupProbe:                                # ⭐ the one people forget
  httpGet: { path: /actuator/health/liveness, port: 9090 }
  failureThreshold: 30
  periodSeconds: 5
```

**The startup probe is not optional for a JVM.** A Spring Boot app can take 20–60 seconds to start.
Without a startup probe, the liveness probe begins immediately, fails three times, and Kubernetes
kills the pod *while it is still starting* — forever. This is one of the most common "my app won't
deploy" causes, and the symptom (endless restarts, no useful logs) points nowhere near the cause.

# Part 3 — Metrics, and the two lines that make them usable

Actuator ships Micrometer, which is Day 128's RED and USE metrics with a real implementation.

```xml
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

You get, for free: `http_server_requests_seconds` (count, sum, max, by `uri`/`method`/`status`/
`outcome` — that is RED), JVM memory and GC, thread counts, `hikaricp_connections_*` (Day 156's
saturation signal), and Tomcat thread-pool usage.

```java
@Bean
MeterRegistryCustomizer<MeterRegistry> commonTags(
        @Value("${spring.application.name}") String app,
        @Value("${ENVIRONMENT:local}") String env) {
    return r -> r.config().commonTags("application", app, "environment", env);
}
```

**Without common tags, every metric from every service lands in one undifferentiated pile** and you
cannot answer "what is the p99 for the orders service in production?" Add them on day one; adding
them later invalidates every dashboard and alert built before.

## ⭐ The cardinality rule, restated because it is the one that breaks Prometheus

```java
Timer.builder("order.processing").tag("orderId", id).register(registry);  // ❌ catastrophic
```

Day 128 gave the principle. The Spring-specific version: **`uri` is tagged with the *template*, not
the path.** `/orders/{id}`, not `/orders/8842`. Boot does this correctly for `@RequestMapping`
handlers, and *incorrectly* — meaning by raw path — for anything that 404s or is handled outside the
mapping layer. That is why a scanner hitting random URLs can blow up your metrics store, and why
`management.metrics.web.server.max-uri-tags` exists as a circuit breaker.

**Custom business metrics are where the value is:**

```java
@Service
class OrderService {
    private final Counter placed;
    private final Timer  duration;

    OrderService(MeterRegistry registry) {
        this.placed   = Counter.builder("orders.placed").register(registry);
        this.duration = Timer.builder("orders.duration").publishPercentileHistogram().register(registry);
    }
}
```

`publishPercentileHistogram()` is what lets you compute a p99 **across instances**. Without it you get
per-instance percentiles, and averaging percentiles is meaningless — a fact worth being able to state
in an interview.

# Part 4 — The endpoints that end an incident quickly

**`/actuator/loggers` — raise a log level without a deploy:**

```bash
curl -X POST localhost:9090/actuator/loggers/com.acme.payment \
  -H 'Content-Type: application/json' -d '{"configuredLevel":"DEBUG"}'
```

This is genuinely the fastest path from "something is wrong in payments" to seeing the detail, and it
reverts with `{"configuredLevel":null}`. It is also a **write** endpoint: an attacker who reaches it
can set root to `TRACE` and turn your logging pipeline into a denial-of-service against your own disk
and log bill. Authenticate it.

**`/actuator/env/<key>` — settle the config argument** (Day 142). Shows every source with an opinion.

**`/actuator/threaddump`** — Day 076's thread dump without shell access to the pod. In a hang, this
is the first request you make.

**`/actuator/heapdump`** — Day 076 again. Downloads a `.hprof`. Note it **pauses the JVM** while
writing and produces a file the size of your heap; on a 4 GB heap under load this is itself an
outage-adjacent action. Deliberate use only.

**`/actuator/info` — make it say something useful:**

```xml
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <executions><execution><goals><goal>build-info</goal></goals></execution></executions>
</plugin>
```
```yaml
management.info.git.mode: full
```

Now `/actuator/info` reports the exact git commit running. "Which version is in production?" becomes
a curl instead of a conversation, and during an incident that question is asked within the first two
minutes.

## Securing it

```java
@Bean
SecurityFilterChain actuator(HttpSecurity http) throws Exception {
    http.securityMatcher(EndpointRequest.toAnyEndpoint())
        .authorizeHttpRequests(a -> a
            .requestMatchers(EndpointRequest.to(HealthEndpoint.class, InfoEndpoint.class)).permitAll()
            .anyRequest().hasRole("ACTUATOR"))
        .httpBasic(withDefaults());
    return http.build();
}
```

`EndpointRequest` is the correct matcher because it tracks `management.endpoints.web.base-path`; a
hand-written `/actuator/**` pattern silently stops matching the day someone changes the base path.
Day 169 covers the filter chain properly — the point today is that **network isolation and
authentication are both required.** Either alone has failed in production for someone.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| `exposure.include: "*"` | new dependency silently exposes a new endpoint |
| Management on the application port | one ingress misconfiguration from a public heap dump |
| `show-details: always` | leaks internal hostnames, versions and error text |
| DB check in the **liveness** group | database outage becomes a cluster-wide crash loop |
| No `startupProbe` | slow JVM start is killed by liveness forever |
| Health indicator with no timeout | slow dependency takes your pod out of service |
| `e.getMessage()` in health details | connection strings and usernames published |
| High-cardinality metric tags | metrics store falls over; Day 128's rule |
| No common tags | dashboards cannot separate services or environments |
| No `build-info` | nobody can tell what is deployed during an incident |

## Interview questions

**Q: Liveness vs readiness, and what happens if you get it wrong?**
Liveness asks whether the process is unrecoverable and should be restarted; readiness asks whether it
should receive traffic. Dependency checks belong only in readiness — put the database in liveness and
a database outage becomes every pod restarting in a loop, which removes the capacity that could have
served degraded responses.

**Q: Which Actuator endpoints are dangerous?**
`heapdump` above all — it is every secret and every piece of customer data in one file. Then `env`
and `configprops` for configuration, `loggers` because it is a write endpoint, and `mappings` as a
map of the attack surface. `shutdown` is off by default and should stay off.

**Q: How would you diagnose a hung production instance with Actuator?**
`/actuator/threaddump` first to see where threads are parked, `/actuator/metrics` for pool saturation
— Hikari active connections and Tomcat busy threads — and `/actuator/loggers` to raise the level on
the suspect package without a deploy.

**Q: Why is a startup probe needed for a JVM service?**
Because a Boot app can take 30–60 seconds to start, and without one the liveness probe starts failing
immediately and kills the pod mid-startup, forever.

## 🎙️ Articulation drill

Two minutes: **"How do you make a Spring Boot service observable and safe to operate?"**

Actuator on a separate port with an allow-list, never `*`. Health split into liveness and readiness
with dependencies only in readiness, and the reason — otherwise a database outage becomes a crash
loop. A startup probe because the JVM is slow to start. Micrometer to Prometheus with common tags and
bounded cardinality. `build-info` so the deployed commit is a curl away. Then close on the endpoint
you would never expose and why: a heap dump is every secret in the process in one file.
