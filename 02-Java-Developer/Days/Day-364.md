# Day 364

**L-364** · Volumes, networks, and injecting configuration

**Time:** 3 hrs · **Mode:** NEW

> **⭐ An image is immutable and identical everywhere. Everything that must differ — data, network
> position, configuration, secrets — is attached from outside at run time.**
>
> That is the whole of today, and it is where most container bugs actually live: **`localhost` that
> is not the host, a mount whose permissions are wrong, and a secret sitting in an environment
> variable that `docker inspect` prints on demand.**

---

# Part 1 — ⭐ Storage: the container filesystem is a lie

> **⭐ Everything written to the container's own filesystem disappears when it is removed** — and it
> is slow anyway, because of copy-on-write (Day 361).

| Mount type | ⭐ What it is | ⭐ Use for |
|---|---|---|
| ⭐ **Named volume** | ⭐ Docker-managed storage | ⭐⭐ **database data, anything durable** |
| ⭐ **Bind mount** | ⭐ a host path mapped in | ⭐ **development source mounting; config files** |
| ⭐ **tmpfs** | memory-backed, never on disk | ⭐ scratch space, and **secrets at run time** |

```
⭐ -v pgdata:/var/lib/postgresql/data      ⭐ named volume — survives `docker rm`
⭐ -v ./src:/app/src                        ⭐ bind mount — host path, live editing
⭐ --tmpfs /tmp                             ⭐ memory only, gone at exit
```

⚠️ **The bind-mount permission problem is the single most common local-development frustration.** The
container's user has a UID (say 10001); your host files are owned by UID 1000. **The container writes
files the host user cannot edit, or cannot write at all.** Fixes: run the dev container with your own
UID (`--user $(id -u):$(id -g)`), or use a named volume, or on Linux match the UIDs deliberately.
**On macOS and Windows, Docker's file sharing hides this — and adds significant I/O latency because
it crosses a VM boundary** (Day 360).

⚠️ **And say the durability rule plainly: a database in a container without a named volume loses
everything on `docker rm`.** It works perfectly until the first time someone recreates the container,
**which is a very expensive way to learn.**

# Part 2 — ⭐⭐ Networking, and the bug everyone hits

```
⭐ ⭐⭐ `localhost` INSIDE a container is THE CONTAINER — not your host, not another container.
⭐ It has its own network namespace (Day 361), its own loopback, its own ports.
```

| Network mode | ⭐ Behaviour |
|---|---|
| ⭐ **bridge** (default) | ⭐ private network; **publish ports to reach it from the host** |
| ⭐⭐ **user-defined bridge** | ⭐⭐ **the same, PLUS automatic DNS by container name** |
| host | ⭐ shares the host's stack — no isolation, no port mapping, **Linux only** |
| none | no networking at all |

```
⭐ ✗ jdbc:postgresql://localhost:5432/db     ⭐⭐ inside a container this means "me"
⭐ ✓ jdbc:postgresql://postgres:5432/db      ⭐ the service name on a user-defined network
```

> **⭐ Container-name DNS only works on a user-defined network, not the default bridge.** That is why
> Compose creates one automatically — and why `docker run` containers cannot see each other by name
> until you create a network and attach them.

| ⭐ Detail | |
|---|---|
| ⭐ **`-p 8080:8080`** | host:container. **`EXPOSE` publishes nothing** (Day 362) |
| ⭐ **Binding to `127.0.0.1` inside** | ⭐⭐ the app is unreachable even with `-p` — **bind to `0.0.0.0`** |
| ⭐ Reaching the host from a container | ⭐ `host.docker.internal` (Desktop) or the gateway IP |
| ⭐ **Publishing exposes to the world** | ⭐ `-p 127.0.0.1:5432:5432` binds only to loopback — **do this for databases** |

⚠️ **`-p 5432:5432` on a cloud VM publishes your database to the internet** if the firewall allows
it. **Always scope the host interface** unless you intend public access.

# Part 3 — ⭐⭐ Configuration and secrets

## ⭐ The 12-factor rule, and its limit

> **⭐ Configuration comes from the environment, not the image** — so one image runs in every
> environment (Day 360, Day 142).

| Mechanism | ⭐ Good for | ⭐ Problem |
|---|---|---|
| ⭐ **Environment variables** | ⭐ simple scalar config | ⭐⭐ **visible in `docker inspect`, `/proc/<pid>/environ`, and often in crash dumps and logs** |
| ⭐ **Mounted files** | ⭐⭐ **secrets, certificates, structured config** | needs a mount |
| ⭐ A config server / secret manager | rotation, audit, central control | a dependency at startup |
| ⭐ **Baked into the image** | ⭐⭐ **never** | breaks the one-image rule |

```
⭐ ✗ -e DB_PASSWORD=hunter2          ⭐⭐ inspectable by anyone with daemon access; leaks into logs
⭐ ✓ mount a file, pass DB_PASSWORD_FILE=/run/secrets/db  ⭐ read it at startup
⭐ ✓ or fetch from a secret manager at startup, with the identity coming from the platform
```

| ⭐ Why files beat env vars for secrets | |
|---|---|
| ⭐⭐ **Not in `docker inspect`** | ⭐ env vars are; **anyone with daemon access reads them** |
| ⭐ **Not inherited by child processes** | ⭐ a subprocess or a crash reporter can dump the whole environment |
| ⭐ **Rotatable in place** | ⭐⭐ update the file, signal the app — **an env var requires a restart** |
| ⭐ Can live on tmpfs | never touches disk |

⚠️ **And Day 362's rule stands above all of this: a secret must never be in the image at any layer.**
Build-time secrets use BuildKit mounts; runtime secrets are injected. **`ENV` in a Dockerfile is
public.**

## ⭐ Spring Boot specifics

```
⭐ SPRING_DATASOURCE_URL          → spring.datasource.url      ⭐ relaxed binding does the mapping
⭐ SPRING_PROFILES_ACTIVE=prod
⭐ ⭐ config tree: mount files under /config and set spring.config.import=configtree:/config/
⭐ ⇒ ⭐⭐ file-per-key, which is exactly what Kubernetes secrets and Docker secrets produce
```

**⭐ `configtree:` is the detail worth knowing** — it turns a directory of files into properties, so
mounted secrets become ordinary Spring configuration with **no env var and no code change.**

# Part 4 — ⭐ Runtime settings that are not optional

| Setting | ⭐ Why |
|---|---|
| ⭐⭐ **`--memory` and `--cpus`** | ⭐⭐ **without limits one container can starve every other on the host** |
| ⭐ **JVM percentage flags** | ⭐ meaningless unless a limit exists (Day 361) |
| ⭐ **`--restart`** policy | ⭐ `on-failure` / `unless-stopped`; **`always` restarts even after a manual stop** |
| ⭐ **`HEALTHCHECK`** | ⭐ Compose and swarm use it; **Kubernetes ignores it** (Day 365, Day 377) |
| ⭐ Log to **stdout/stderr** | ⭐⭐ 12-factor — **the platform collects; never write log files inside a container** |
| ⭐ **Log rotation** | ⭐ the default json-file driver grows without limit — **set `max-size` and `max-file`** |
| `--init` | reap zombies if you spawn processes (Day 361) |

⚠️ **Unbounded container logs filling the host disk is a genuinely common outage**, and the fix is
two lines of daemon config. **It is also invisible until the disk is full**, at which point
everything on the host fails at once.

**⭐ The healthcheck that is worth writing:**

```dockerfile
⭐ HEALTHCHECK --interval=10s --timeout=3s --start-period=40s --retries=3 \
⭐   CMD curl -fsS http://localhost:8080/actuator/health/readiness || exit 1
```

> **⭐ `--start-period` is the field people omit and then blame the healthcheck.** A JVM takes 20–40
> seconds to become ready; without a start period it is marked unhealthy and restarted **before it
> ever finishes starting**, producing an infinite restart loop that looks like a crash.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Database data on the container filesystem | ⭐⭐ **gone on `docker rm`** |
| ⭐ Heavy writes to the container filesystem | copy-on-write cost |
| ⭐⭐ **`localhost` to reach another container** | ⭐⭐ **it means "me"** |
| ⭐ Container names on the default bridge | ⭐ DNS needs a user-defined network |
| ⭐ Binding to `127.0.0.1` inside the container | unreachable despite `-p` |
| ⭐ **`-p 5432:5432` on a public host** | ⭐⭐ your database is on the internet |
| ⭐⭐ **Secrets in environment variables** | ⭐⭐ `docker inspect`, `/proc`, crash dumps, child processes |
| ⭐ Secrets in the image | permanent (Day 362) |
| ⭐ Config baked in | breaks the one-image rule |
| ⭐ **No memory or CPU limits** | ⭐ one noisy container starves the host |
| ⭐ No `--start-period` on a JVM healthcheck | ⭐⭐ restart loop before startup completes |
| ⭐ **No log rotation** | ⭐ the host disk fills and everything dies together |
| Writing log files inside the container | invisible, unrotated, lost |
| `--restart always` for a debugging container | it comes back after you stop it |

## Interview questions

**Q: Where does container data go?**
Anything durable goes in a named volume; the container's own filesystem is ephemeral and slow because
of copy-on-write, and it disappears on removal. Bind mounts are for development and config files, and
tmpfs for scratch or secrets you do not want on disk. A database container without a named volume
works perfectly right up until someone recreates it.

**Q: Your app can't reach the database at `localhost:5432`. Why?**
Because `localhost` inside a container is the container — it has its own network namespace and its
own loopback. On a user-defined network, containers resolve each other by name, so the URL should
point at the service name. The default bridge does not provide that DNS, which is why Compose creates
a user-defined network automatically.

**Q: Why not put secrets in environment variables?**
Because they are readable by anyone with daemon access via `docker inspect` and via `/proc`, they are
inherited by every child process, they often end up in crash dumps and log lines, and they cannot be
rotated without a restart. Mounted files fix all four — and with Spring's config tree a directory of
mounted secret files becomes ordinary properties with no code change and no environment variable at
all.

**Q: Why do containers need explicit resource limits?**
Because without them one container can consume the host's memory and CPU and starve everything else,
and because the JVM's percentage-based heap flags are meaningless with no limit to be a percentage
of. Limits are also what make behaviour predictable — a container that works because it happened to
have sixty-four gigabytes available is not a container that works.

**Q: Your JVM container restarts in a loop and the healthcheck is failing. First guess?**
No start period. A Spring Boot application takes twenty to forty seconds to become ready, so a
healthcheck with no `--start-period` marks it unhealthy and triggers a restart before it has ever
finished starting. The second guess is the check hitting liveness when it should hit readiness, or
hitting a deep health endpoint that depends on the database.

## 🎙️ Articulation drill

**Two minutes:** *"Walk me through everything you attach to a container at run time and why."*

**⭐ The structure: a volume for anything durable, a network so it can find its peers by name, config
from the environment so one image runs everywhere, secrets as mounted files rather than environment
variables, resource limits so the JVM can size itself and the host stays fair, a healthcheck with a
start period, and log rotation.**

**⭐ The marker is the secrets sentence** — *"environment variables are visible in `docker inspect`,
in `/proc`, to every child process, and cannot be rotated without a restart, so secrets are files"* —
**because it is the one most people get wrong and the one with the most direct security
consequence.**
