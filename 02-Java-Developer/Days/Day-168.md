# Part 1 — `@Cacheable`, and what it actually generates

```java
@Configuration
@EnableCaching                                   // ⭐ without this, every annotation is inert
class CacheConfig { }
```

```java
@Service
public class ProductService {

    @Cacheable(cacheNames = "products", key = "#id")
    public ProductDto findById(Long id) { ... }              // ⭐ returns a DTO, not an entity

    @CachePut(cacheNames = "products", key = "#result.id()")
    public ProductDto update(Long id, UpdateProductRequest req) { ... }   // ⭐ always runs, then caches

    @CacheEvict(cacheNames = "products", key = "#id")
    public void delete(Long id) { ... }

    @CacheEvict(cacheNames = "products", allEntries = true)
    public void reindexAll() { ... }
}
```

| Annotation | Behaviour |
|---|---|
| `@Cacheable` | ⭐ check first — **skip the method entirely** on a hit |
| `@CachePut` | ⭐ **always execute**, then store. For updates |
| `@CacheEvict` | remove. `beforeInvocation = true` to evict even if the method throws |
| `@Caching` | combine several |

**⭐ It is a proxy (Day 137), so every constraint applies:** self-invocation does not cache, `private`
and `final` methods are invisible, and calling from within the same bean silently does nothing.

**And note what is cached:** a `ProductDto`, not a `Product` entity. Day 167's argument — caching the
DTO skips entity hydration, mapping and (with Redis) even deserialization cost relative to a database
round trip. **Never cache a managed entity**: it carries proxies, it is not serializable in any
reliable way, and a lazy association inside it will explode on deserialization.

# Part 2 — ⭐ The four defaults you must change

### 1. There is no TTL by default

```java
@Bean
RedisCacheConfiguration cacheConfiguration() {
    return RedisCacheConfiguration.defaultCacheConfig()
        .entryTtl(Duration.ofMinutes(10))                  // ⭐⭐ MANDATORY
        .disableCachingNullValues()                        // see #2
        .serializeValuesWith(SerializationPair.fromSerializer(jsonSerializer()));
}

@Bean
RedisCacheManagerBuilderCustomizer perCacheTtl() {
    return b -> b
        .withCacheConfiguration("products",  config(Duration.ofMinutes(30)))
        .withCacheConfiguration("inventory", config(Duration.ofSeconds(10)))   // ⭐ volatile
        .withCacheConfiguration("countries", config(Duration.ofDays(1)));      // ⭐ static
}
```

**Without a TTL, entries live until evicted by memory pressure — which is forever for anything
regularly read.** A bug that writes a wrong value caches it permanently, and the only fix is a manual
flush during an incident.

**Day 121's rule: every cache entry has a TTL, and the TTL expresses how stale you can tolerate this
data being.** Inventory: seconds. Product descriptions: minutes. Country list: a day.

### 2. `null` results are cached — or worse, not

```java
@Cacheable(cacheNames = "products", unless = "#result == null")     // ⭐ decide deliberately
```

**Caching nulls prevents cache penetration** — repeated lookups for a non-existent id going to the
database every time, which is a trivially exploitable load amplifier if ids come from the request.

**Not caching them means a missing entity is queried every time.** Neither is universally right:
cache nulls with a *short* TTL where ids are user-supplied; do not cache them where absence is
common and cheap.

### 3. ⭐ JDK serialization is the default and it must go

Spring Data Redis defaults to `JdkSerializationRedisSerializer`. Day 068's argument applies in full:

- **`readObject` on untrusted bytes is remote code execution.** Anyone who can write to your Redis can
  execute code in your JVM. Redis is frequently deployed with no authentication on an internal
  network, so "untrusted" is a lower bar than people assume.
- The output is unreadable — you cannot inspect a cached value with `redis-cli`.
- It is **version-fragile**: add a field to the DTO and every cached entry fails to deserialize after
  deploy, throwing on read rather than missing cleanly.

```java
GenericJackson2JsonRedisSerializer jsonSerializer() {
    ObjectMapper m = JsonMapper.builder()
        .addModule(new JavaTimeModule())
        .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)      // Day 150
        .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)   // ⭐ tolerate added fields
        .activateDefaultTyping(BasicPolymorphicTypeValidator.builder()
                .allowIfSubType("com.acme.")                          // ⭐⭐ ALLOW-LIST, never LaissezFaire
                .build(), DefaultTyping.NON_FINAL)
        .build();
    return new GenericJackson2JsonRedisSerializer(m);
}
```

**⭐ `activateDefaultTyping` with `LaissezFaireSubTypeValidator` is itself a deserialization
vulnerability** — it is the JSON equivalent of the gadget-chain problem, and it appears in a great
many blog posts. **Restrict it to your own packages.**

### 4. Key generation is not what you want

The default `SimpleKeyGenerator` concatenates all parameters. A method taking a `Pageable` produces a
key containing the `Pageable`'s `toString()` — unstable across versions and unreadable.

```java
@Cacheable(cacheNames = "products", key = "'cat:' + #category + ':p' + #page")     // ⭐ explicit
```

**Always specify the key.** And design it as Day 121 said — **key by version rather than deleting**:

```java
@Cacheable(cacheNames = "products", key = "'v' + @cacheVersion.current() + ':' + #id")
```

A version bump invalidates everything atomically with no delete storm, and rollback is a version
decrement.

# Part 3 — What Spring's abstraction does not give you

### ⭐ Stampede protection

Day 121's problem: a popular key expires, 500 concurrent requests all miss, and 500 identical queries
hit the database at once.

**`@Cacheable` has no protection against this.** `sync = true` exists and only locks *within one JVM*
— six instances means six concurrent rebuilds, which is better than 500 but is not a solution.

```java
@Cacheable(cacheNames = "products", key = "#id", sync = true)     // ⭐ per-instance only
```

**The real fixes are Day 121's:** jittered TTLs so keys do not expire together, a distributed lock
(Redisson) for genuinely expensive rebuilds, or stale-while-revalidate — serve the stale value and
refresh in the background, which needs a manual `RedisTemplate` implementation.

### Dropping to `RedisTemplate` for the patterns that matter

```java
@Service
public class RateLimiter {                                  // ⭐ Day 122
    private final StringRedisTemplate redis;

    private static final RedisScript<Long> SCRIPT = RedisScript.of("""
        local current = redis.call('INCR', KEYS[1])
        if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
        return current
        """, Long.class);                                   // ⭐ atomic — Day 122's script

    public boolean allow(String key, int limit, int windowSeconds) {
        Long count = redis.execute(SCRIPT, List.of("rl:" + key), String.valueOf(windowSeconds));
        return count != null && count <= limit;
    }
}
```

**Redis is not only a cache**, and the annotation abstraction hides everything that makes it useful:
rate limiting (Day 122), idempotency keys (Day 123), distributed locks, session storage (Day 113),
sorted sets for leaderboards, streams. **`@Cacheable` for caching; `RedisTemplate` for everything
else.**

### Operational essentials

```yaml
spring.data.redis:
  host: ${REDIS_HOST}
  timeout: 500ms                     # ⭐⭐ Day 154's rule — Redis is a network call
  lettuce.pool: { max-active: 16, max-idle: 8 }
```

```java
@Bean
CacheErrorHandler cacheErrorHandler() {
    return new CacheErrorHandler() {                        // ⭐⭐ the most important bean here
        public void handleCacheGetError(RuntimeException e, Cache c, Object key) {
            log.warn("cache get failed, falling through to source", e);   // ⭐ do NOT rethrow
        }
        // ... put/evict/clear likewise
    };
}
```

**⭐ Without this, Redis being down takes your application down.** The default handler rethrows, so a
cache failure becomes a 500 on every cached endpoint. **A cache must degrade to a slow application,
never to a broken one** — and this is the single most common way a cache causes the outage it was
meant to prevent.

Set `maxmemory-policy allkeys-lru` on the Redis side, so a full Redis evicts rather than refusing
writes.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ No `CacheErrorHandler` | Redis down = application down |
| ⭐ JDK serialization | RCE surface, unreadable, breaks on any DTO change |
| `LaissezFaireSubTypeValidator` | reintroduces the deserialization vulnerability in JSON |
| No TTL | a bad value is cached permanently |
| Not deciding about nulls | penetration, or repeated queries for missing rows |
| Caching entities | proxies, lazy explosions, unserializable |
| Forgetting `@EnableCaching` | every annotation silently inert |
| `@Cacheable` self-invocation | Day 137, again |
| Relying on `sync = true` in a cluster | per-JVM only |
| No jitter on TTLs | synchronised expiry → stampede |
| Default key generator | unstable, unreadable keys |
| No Redis timeout | Day 154 — a slow Redis parks your threads |
| Deleting keys instead of versioning | delete storms; no rollback |

## Interview questions

**Q: Where do you cache, and why not the second-level cache?**
At the service method, caching the DTO — that skips entity hydration, mapping and the database round
trip, and I control invalidation explicitly. The second-level cache is keyed by primary key so it
does not serve queries, and it goes stale on bulk updates and any external writer.

**Q: What must you change from Spring's cache defaults?**
Four things: add a TTL per cache, decide about caching nulls, replace JDK serialization with JSON
under an allow-listed type validator, and add a `CacheErrorHandler` so Redis being down degrades to a
slow application rather than a broken one.

**Q: Does `@Cacheable` protect against a cache stampede?**
No. `sync = true` locks only within one JVM, so six instances give six concurrent rebuilds. Real
protection is jittered TTLs, a distributed lock for expensive rebuilds, or stale-while-revalidate —
none of which the annotation provides.

**Q: Why is JDK serialization in Redis dangerous?**
`readObject` on attacker-controlled bytes is remote code execution, and Redis is often deployed with
weak or no authentication on an internal network. It is also unreadable in `redis-cli` and breaks on
every DTO change.

## 🎙️ Articulation drill

Two minutes: **"How do you add caching to a Spring service?"**

At the service method, caching DTOs, with a TTL per cache chosen from how stale that data may be.
JSON serialization with an allow-listed type validator, never JDK serialization, because
deserializing attacker-controlled bytes is code execution. A `CacheErrorHandler` so a Redis outage
degrades to a slow application rather than a broken one. Then be honest about the limit of the
abstraction: `@Cacheable` gives you no stampede protection across instances, so jittered TTLs or a
distributed lock, and drop to `RedisTemplate` for rate limits, idempotency keys and locks.
