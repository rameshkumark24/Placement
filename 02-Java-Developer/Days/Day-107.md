# Day 107

**L-107** · Pagination — offset vs cursor vs keyset · why offset breaks at scale
**D-10** · SQL IV — subqueries, correlated subqueries, CTEs, recursive CTEs

**Time:** 3 hrs · **Mode:** NEW

> Pagination looks trivial and has two failure modes that only appear in production: **it gets slower
> the deeper you go**, and **it silently skips and duplicates rows** when the data changes underneath
> it. Both have the same fix, and it is a design decision you cannot retrofit without breaking
> clients.

---

# Part 1 — Offset pagination and its two failures

```http
GET /orders?page=3&size=20
```

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 40;
```

Simple, universally understood, supports jumping to any page. And it breaks in two ways.

## Failure 1 — O(offset)

```sql
LIMIT 20 OFFSET 100000
```

**The database must produce 100,020 rows and discard 100,000 of them.** `OFFSET` is not a seek — it
is a count-and-throw-away. Cost grows linearly with depth:

```
OFFSET 0        →   0.4 ms
OFFSET 1000     →   3 ms
OFFSET 100000   →  180 ms
OFFSET 1000000  → 1900 ms        ← the same 20 rows
```

Worse: a crawler or a scripted client walking your entire dataset makes the *total* cost quadratic,
and page 5000 requests are indistinguishable from an attack in your metrics — because in effect they
are one.

## Failure 2 — the shifting window

This one is subtler and causes data loss that nobody notices.

```
t0: page 1 → rows 1–20  (of 100)
t1: someone inserts a new row at the top
t2: page 2 → OFFSET 20 → what WAS row 20 is now row 21
              ⇒ the client sees row 20 TWICE and never sees... nothing, in this case
              ⇒ on a DELETE, the client SKIPS a row entirely
```

For a list of blog posts, an annoyance. For a **paginated export**, a reconciliation job, or a
"process every pending order" loop, it is **silent data loss** — and it will not reproduce in
testing, because your test data does not change mid-scan.

## And the tiebreaker bug

Day 097 flagged this and it belongs here as the third failure:

```sql
ORDER BY created_at DESC              -- ❌ ties order arbitrarily and INCONSISTENTLY
ORDER BY created_at DESC, id DESC     -- ✅ total order
```

Without a unique final sort key, rows with equal `created_at` may come back in a different order on
each query — so page boundaries move even with no writes at all.

# Part 2 — Keyset (cursor) pagination

Instead of "skip 100,000 rows", say **"give me rows after this specific point"**:

```sql
SELECT * FROM orders
WHERE (created_at, id) < ('2026-08-14 10:22:01', 8814)     -- ← row-value comparison
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

With an index on `(created_at DESC, id DESC)`, the database **seeks directly to that point** and
reads 20 rows. **Constant cost at any depth** — page 1 and page 50,000 take the same time.

The row-value syntax `(a, b) < (x, y)` is standard SQL and is exactly what you want — it means
"`a < x`, or (`a = x` and `b < y`)". Writing it out by hand is a classic source of off-by-one bugs:

```sql
-- the manual expansion, if your database lacks row-value comparison (e.g. older MySQL)
WHERE created_at < :ts OR (created_at = :ts AND id < :id)
```

## The cursor

Never expose raw column values — encode them opaquely:

```java
record Cursor(Instant createdAt, long id) {
    String encode() {
        return Base64.getUrlEncoder().withoutPadding()
                .encodeToString((createdAt.toEpochMilli() + ":" + id).getBytes(UTF_8));
    }
    static Cursor decode(String s) { … }   // ← validate on the way back in (Day 105)
}
```

```json
{
  "data": [ … ],
  "page": {
    "next": "MTc1NTE3MjgwMDo4ODE0",
    "has_more": true
  }
}
```

**Opaque cursors are a versioning decision, not obfuscation.** Because clients treat the string as
meaningless, you can change the underlying sort key, add a tiebreaker, or switch from a timestamp to
a sequence number **without breaking anyone**. Expose `?after_id=8814` and that value is now a public
contract forever (Day 103).

Two hardening notes: **sign or HMAC the cursor** if a forged one could leak data or cause an
expensive query, and **validate it on decode** — it crossed the trust boundary (Day 105).

## The trade-offs, honestly

| | Offset | Keyset |
|---|---|---|
| Deep-page performance | ❌ O(offset) | ✅ O(1) |
| Stable under writes | ❌ skips and duplicates | ✅ |
| Jump to page N | ✅ | ❌ **next/prev only** |
| Show "page 7 of 42" | ✅ | ❌ needs a separate `COUNT` |
| Sort by arbitrary columns | ✅ | ⚠️ needs an index per sort order |
| Implementation | trivial | moderate |

**Keyset's real cost is that you cannot jump to page 7.** For an infinite scroll, an API feed, or an
export, that is not a requirement. For an admin table where a human clicks "page 7", it is.

> **The honest rule: keyset for APIs and infinite scroll; offset only for small, bounded, human-
> browsed lists — and cap the maximum offset.**

```java
if (offset > 10_000) throw new BadRequestException("offset too large; use cursor pagination");
```

That cap is worth adding to any offset endpoint you keep. It converts a slow-query incident into a
clean `400`.

## Total counts

```sql
SELECT COUNT(*) FROM orders WHERE …;      -- a FULL SCAN on a large filtered table
```

An exact count on 50 million rows is expensive and usually pointless — nobody needs to know there are
exactly 4,182,993 results.

```sql
-- an estimate, from the planner's statistics — microseconds
EXPLAIN (FORMAT JSON) SELECT * FROM orders WHERE status = 'PAID';
```

The practical designs: return `has_more` instead of a total (fetch `limit + 1` and check whether you
got an extra row); return an approximate count above a threshold ("10,000+ results", which is what
Google does); or compute the exact count only when the filter is selective.

## Bounding page size

```java
int size = Math.min(Math.max(requestedSize, 1), MAX_PAGE_SIZE);   // clamp, do not reject
```

**Always cap it.** `?size=1000000` is a denial-of-service vector otherwise (Day 105's unbounded-input
rule). Document the default and the maximum.

# Part 3 — D-10 · Subqueries and CTEs

## Subquery forms

```sql
-- SCALAR: returns one value
SELECT name, (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS order_count
FROM customer c;

-- IN / NOT IN: a set  ⚠️ NOT IN + NULL (Day 097)
SELECT * FROM customer WHERE id IN (SELECT customer_id FROM orders WHERE total > 10000);

-- EXISTS: a semi-join (Day 100) — stops at the first match
SELECT * FROM customer c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- DERIVED TABLE: a subquery in FROM
SELECT region, avg_total FROM (
    SELECT region, AVG(total) AS avg_total FROM orders GROUP BY region
) t WHERE avg_total > 5000;
```

## Correlated subqueries — and why they are slow

```sql
-- CORRELATED: the inner query references the outer row, so it runs ONCE PER OUTER ROW
SELECT c.name FROM customer c
WHERE (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) > 5;
```

**A correlated subquery is a loop.** One million customers means one million inner queries. Modern
optimisers often rewrite them into joins or semi-joins, but not always — and when they cannot, the
query goes from milliseconds to minutes.

```sql
-- ✅ the same thing as an aggregate + join: ONE pass
SELECT c.name
FROM customer c
JOIN (SELECT customer_id, COUNT(*) AS n FROM orders GROUP BY customer_id) o
  ON o.customer_id = c.id
WHERE o.n > 5;
```

**`EXISTS` is the exception**: it is correlated by nature but becomes a semi-join, and it can stop at
the first matching row — which is why `EXISTS` usually beats `IN` and always beats
`COUNT(*) > 0`:

```sql
WHERE (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) > 0    -- ❌ counts ALL rows
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)        -- ✅ stops at the first
```

## CTEs — Common Table Expressions

```sql
WITH recent_orders AS (
    SELECT * FROM orders WHERE created_at >= now() - interval '30 days'
),
customer_totals AS (
    SELECT customer_id, SUM(total_cents) AS total, COUNT(*) AS n
    FROM recent_orders GROUP BY customer_id
)
SELECT c.name, t.total, t.n
FROM customer_totals t
JOIN customer c ON c.id = t.customer_id
WHERE t.total > 100000
ORDER BY t.total DESC;
```

CTEs are **readability**, principally: a query built from named steps rather than nested derived
tables. They can also be referenced more than once, which a derived table cannot.

⚠️ **The optimisation-fence caveat**, which is a genuine interview differentiator: in PostgreSQL
**before version 12**, a CTE was always materialised — an optimisation fence — so predicates could
not be pushed into it (Day 094's selection pushdown), sometimes making a CTE dramatically slower than
the equivalent subquery. From PG 12 they are inlined when it is safe, and you can force either:

```sql
WITH x AS MATERIALIZED     (…)      -- force the fence
WITH x AS NOT MATERIALIZED (…)      -- force inlining
```

Know which version you are on before assuming a CTE is free.

## Recursive CTEs — hierarchies

The tool for tree and graph traversal in SQL:

```sql
WITH RECURSIVE subordinates AS (
    -- ANCHOR: the starting row(s)
    SELECT id, name, manager_id, 1 AS depth
    FROM employee WHERE id = 1

    UNION ALL

    -- RECURSIVE: joins back to the CTE itself
    SELECT e.id, e.name, e.manager_id, s.depth + 1
    FROM employee e
    JOIN subordinates s ON e.manager_id = s.id
    WHERE s.depth < 10                       -- ← ALWAYS bound the depth
)
SELECT * FROM subordinates ORDER BY depth, name;
```

The structure is always the same: **anchor `UNION ALL` recursive term**, where the recursive term
references the CTE. Execution repeats the recursive term against the previous iteration's rows until
it produces none.

Uses: org charts, category trees, bill-of-materials, threaded comments, graph reachability, and
generating series.

**Two things that must be right:**

- **`UNION ALL`, not `UNION`.** `UNION` deduplicates, which costs a sort on every iteration.
- **Bound the depth.** A cycle in the data (employee A manages B manages A) is an infinite loop that
  will consume all available memory. A depth guard, or a visited-path array, is mandatory.

```sql
-- cycle-safe with a path array (PostgreSQL)
WITH RECURSIVE t AS (
    SELECT id, ARRAY[id] AS path, false AS cycle FROM node WHERE id = 1
    UNION ALL
    SELECT n.id, t.path || n.id, n.id = ANY(t.path)
    FROM node n JOIN edge e ON e.to_id = n.id JOIN t ON e.from_id = t.id
    WHERE NOT t.cycle
)
SELECT * FROM t WHERE NOT cycle;
```

Also useful, and worth knowing as a trick:

```sql
-- generate a date series with no calendar table
WITH RECURSIVE dates AS (
    SELECT DATE '2026-01-01' AS d
    UNION ALL SELECT d + 1 FROM dates WHERE d < DATE '2026-12-31'
)
SELECT * FROM dates;
```

**Data-modelling note:** recursive CTEs are the right tool for occasional traversal of a shallow
hierarchy. For deep or frequently-queried trees, consider a **materialised path**
(`/1/17/42/`), **nested sets**, or a **closure table** — precomputed structures that turn a recursion
into an index range scan. And if traversal *is* your access pattern, that is the argument for a graph
database (Day 078's D-01).

## Common mistakes

| Mistake | Consequence |
|---|---|
| Offset pagination on a large table | Linear slowdown; page 5000 is a slow query |
| No maximum offset | A crawler produces a quadratic scan |
| `ORDER BY` with no unique tiebreaker | Unstable page boundaries even with no writes |
| Offset pagination for an export | Silently skipped and duplicated rows |
| Exposing raw cursor values | The sort key becomes a permanent public contract |
| Unvalidated cursors | A forged cursor is unvalidated input |
| Unbounded page size | `?size=1000000` is a DoS |
| `COUNT(*)` on every page | A full scan per request |
| Correlated subquery over a large outer set | One inner query per row |
| `COUNT(*) > 0` instead of `EXISTS` | Counts everything to answer a yes/no |
| Assuming CTEs are free | Optimisation fence before PostgreSQL 12 |
| `UNION` instead of `UNION ALL` in a recursive CTE | A sort per iteration |
| No depth bound on recursion | A data cycle exhausts memory |

## Interview questions

**Q: Why does `OFFSET` get slow?**
It is not a seek — the database produces every preceding row and discards it, so cost grows linearly
with the offset. `LIMIT 20 OFFSET 100000` reads 100,020 rows to return 20.

**Q: What is the *correctness* problem with offset pagination?**
Inserts and deletes shift the window between requests, so clients duplicate or silently skip rows.
For an export or a batch job, that is data loss that will never reproduce in testing.

**Q: How does keyset pagination work?**
Instead of skipping N rows, filter on the last row's sort key: `WHERE (created_at, id) < (?, ?)` with
a matching index. The database seeks to that point, so cost is constant at any depth.

**Q: Why make cursors opaque?**
So the sort key is not a public contract. With an opaque cursor you can change the sort, add a
tiebreaker or change the underlying column without breaking clients.

**Q: When would you still use offset?**
Small, bounded, human-browsed lists where "jump to page 7" is a genuine requirement — with a hard cap
on the maximum offset.

**Q: Why is a correlated subquery slow, and what is the exception?**
It executes once per outer row, so it is a loop. `EXISTS` is the exception because it becomes a
semi-join and can stop at the first match.

**Q: What is a recursive CTE and what must you be careful about?**
An anchor query unioned with a term that references the CTE itself, repeated until it yields no rows
— used for hierarchies. Use `UNION ALL`, and always bound the depth or track visited nodes, because a
cycle in the data is an infinite loop.

**Q: Are CTEs free?**
Not necessarily. Before PostgreSQL 12 they were an optimisation fence — always materialised — so
predicates could not be pushed inside, sometimes making them much slower than the equivalent
subquery.

## 🎙️ Articulation drill

Two minutes: **"How would you paginate an API returning millions of rows?"**

Keyset with an opaque cursor and a matching composite index, because offset is O(offset) *and*
unstable under writes. Name both failures — the performance one is well known and the
skip-and-duplicate one is what shows you have actually operated a system. Then the trade-off: no
jumping to page N, so offer offset only where a human genuinely browses, with a hard cap.
