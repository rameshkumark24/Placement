## ⭐ The nouns, pruned

| Noun | ⭐ Verdict |
|---|---|
| ParkingLot, Floor, Spot | ⭐ **entities** |
| Ticket | ⭐ **entity** — it has identity and a lifecycle |
| Vehicle | ⭐ **value object** — a plate and a type, no lifecycle here |
| VehicleType, SpotSize, TicketStatus | ⭐ **enums** |
| Money, Duration, LicensePlate, SpotId | ⭐ **value objects** (Day 304) |
| ⭐ Car, Truck, Bike | ⭐ **DELETED — enum values, not classes** |
| ⭐ Attendant, Admin | ⭐ **deleted — actors, not model** |
| EntryGate, ExitGate, DisplayBoard | ⭐ **deleted from scope**, mentioned as extension points |

> **⭐ Say the vehicle decision out loud, because it is the one everyone gets wrong:** *"Car, Truck and
> Bike differ in size, not behaviour, so they're an enum with a size — not three subclasses. I'd
> switch to subtypes if, say, trucks needed a different pricing algorithm."*

## ⭐ The one interesting decision: which spots fit which vehicles

**⭐ Three options. Pick one and say why the others lose:**

| Option | ⭐ Verdict |
|---|---|
| ⭐ `if (vehicle == BIKE && spot == SMALL)` chains | ⭐ **N×M `if`s; every new type edits every branch** |
| ⭐ **Ordinal comparison — `spot.size >= vehicle.size`** | ⭐ **simple, but assumes a total order** |
| ⭐⭐ **A fit matrix / `Set<SpotSize>` per vehicle type** | ⭐⭐ **data, not code — new type is a data change** |

```java
enum VehicleType {
    BIKE(EnumSet.of(SMALL, MEDIUM, LARGE)),
    CAR(EnumSet.of(MEDIUM, LARGE)),
    TRUCK(EnumSet.of(LARGE));                     // ⭐ EV or handicapped spots break the ordinal
    private final Set<SpotSize> fits;             // ⭐ assumption — say that
    boolean fitsIn(SpotSize size) { return fits.contains(size); }
}
```

> **⭐ The sentence that scores: "ordinal comparison works until you add a spot type that isn't on the
> size axis — an EV bay or an accessible bay. So I'll express fit as data."** That is anticipating
> the interviewer's extension question before it arrives.

## ⭐ The classes

```
        ParkingLot 1 ──◆ 1..* Floor 1 ──◆ 1..* Spot        ⭐ composition = one aggregate?
             │                                              ⭐ ← NO. See below.
             │ 1
             ├──── * Ticket ──── SpotId (by identity)
             │
             ├──── SpotAllocator     «interface»  ⭐ strategy: nearest / first-fit / by-floor
             └──── PricingStrategy   «interface»  ⭐ strategy: hourly / slab / day-rate
```

⚠️ **The aggregate decision, and it is Day 305 exactly:** a lot with 2,000 spots is **not** one
aggregate — every park would load and lock all of them. **`Spot` is its own tiny aggregate with a
`FloorId`; the lot is a lookup structure, not a consistency boundary.** Say this. It is the single
most senior-sounding thing available in this problem.

## ⭐ The data structure that makes allocation O(1)

```java
// ⭐ Not a scan of 2,000 spots. An index, maintained on every state change.
Map<SpotSize, NavigableSet<Spot>> free;    // ⭐ ordered by distance-to-lift for "nearest"
```

| Structure | ⭐ Cost | ⭐ Say |
|---|---|---|
| ⭐ Linear scan of all spots | ⭐ O(n) per park | ⭐ "fine for 200 spots, not for 20,000" |
| ⭐ **`Map<SpotSize, Deque<Spot>>`** | ⭐ **O(1)** | ⭐ **first-fit, the default** |
| ⭐ **`Map<SpotSize, PriorityQueue<Spot>>`** | O(log n) | ⭐ "nearest to the lift" |
| Per-floor counters only | O(1) | ⭐ good for the display board, not for allocation |

# Part 3 — ⭐ Minutes 25–40: the code

```java
public record Vehicle(LicensePlate plate, VehicleType type) { }

public final class Spot {
    private final SpotId id;
    private final SpotSize size;
    private final AtomicReference<Optional<LicensePlate>> occupant =
            new AtomicReference<>(Optional.empty());

    // ⭐ THE method. Atomic check-then-act — Day 310.
    boolean tryOccupy(Vehicle vehicle) {
        if (!vehicle.type().fitsIn(size)) return false;              // ⭐ the invariant, inside the object
        return occupant.compareAndSet(Optional.empty(), Optional.of(vehicle.plate()));
    }

    void release() { occupant.set(Optional.empty()); }
    boolean isFree() { return occupant.get().isEmpty(); }
}
```

```java
public interface SpotAllocator { Optional<Spot> allocate(Vehicle vehicle); }
public interface PricingStrategy { Money priceFor(Duration stayed, VehicleType type); }
```

```java
public final class ParkingService {                                  // ⭐ Day 302: orchestration only

    private final SpotAllocator allocator;
    private final PricingStrategy pricing;
    private final Tickets tickets;                                   // ⭐ a port (Day 301)
    private final Clock clock;                                       // ⭐ never LocalDateTime.now()

    public Ticket park(Vehicle vehicle) {
        Spot spot = allocator.allocate(vehicle).orElseThrow(() -> new LotFull(vehicle.type()));
        Ticket ticket = Ticket.issue(TicketId.next(), vehicle, spot.id(), clock.instant());
        tickets.save(ticket);
        return ticket;
    }

    public Money exit(TicketId id) {
        Ticket ticket = tickets.byId(id).orElseThrow(TicketNotFound::new);
        Money fee = pricing.priceFor(ticket.durationUntil(clock.instant()), ticket.vehicleType());
        ticket.close(fee, clock.instant());                          // ⭐ the state rule lives on Ticket
        tickets.save(ticket);
        spots.byId(ticket.spotId()).release();                       // ⭐ released AFTER pricing
        return fee;
    }
}
```

```java
// ⭐ The default strategy — and the two edge cases that show you thought about it
public final class HourlyPricing implements PricingStrategy {
    public Money priceFor(Duration stayed, VehicleType type) {
        long hours = Math.max(1, (stayed.toMinutes() + 59) / 60);    // ⭐ round UP; minimum ONE hour
        return rates.get(type).times((int) hours);
    }
}
```

# Part 4 — ⭐ Minutes 40–45: the closing ninety seconds

## ⭐ Concurrency (volunteer it)

```
⭐ "Shared mutable state is the free-spot index. Two cars can be handed the same spot —
⭐  classic check-then-act. I've made occupy() a compare-and-set, so exactly one wins and
⭐  the allocator moves to the next candidate. No lock, and two cars taking DIFFERENT spots
⭐  never contend at all.

⭐  The index itself needs to be concurrent — I'd use a ConcurrentLinkedDeque per size, and
⭐  accept that it can hand out a stale candidate, because tryOccupy() is the real arbiter.

⭐  Multi-instance: that CAS becomes an optimistic version column on the spot row, or a
⭐  partial unique index on (spot_id) where released_at is null. Same algorithm — the
⭐  database is the arbiter instead of the CPU."
```

## ⭐ Extensions — with honest costs

| "Now add…" | ⭐ Cost |
|---|---|
| ⭐ **Dynamic/surge pricing** | ⭐ **one new `PricingStrategy` — free, by design** |
| ⭐ **Nearest-to-lift** | ⭐ **one new `SpotAllocator` — free, by design** |
| Multiple entry gates | ⭐ nothing changes — the CAS already handles it |
| EV bays, accessible bays | ⭐ a new `SpotSize` + a fit-matrix entry — **because fit is data** |
| ⭐ **Reservations** | ⭐⭐ **the expensive one — a spot now has a *future* state, so `isFree()` becomes `isFreeBetween(from, to)` and allocation becomes an interval query** |
| Lost ticket | a flat penalty; a plate → open-ticket index |
| Monthly passes | a different pricing strategy plus an identity check |

> **⭐ Naming reservations as the expensive one is the highest-value answer here**, because it is the
> extension interviewers use to see whether you understand your own model. **A boolean cannot
> represent time.**

## ⭐ What you cut

> *"I cut real payments, receipts, the display boards, multi-lot, and reporting. The one I'd add
> first is the exit-panel flow, because unpaid tickets are the real-world failure."*

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ `Car`/`Truck`/`Bike` subclasses | ⭐ inheritance for a data difference (Day 092) |
| ⭐ Scanning all spots to allocate | ⭐ O(n) per arrival — say the index |
| ⭐ Ordinal size comparison, unexamined | ⭐ breaks on the first non-size spot type |
| ⭐ `if (spot.isFree()) spot.occupy()` | ⭐⭐ **two cars, one spot** |
| ⭐ The whole lot as one aggregate | ⭐ every park locks 2,000 spots |
| Pricing logic inside the service | not swappable; and it is a domain rule |
| Releasing the spot before pricing | the duration is gone |
| ⭐ No minimum charge / no rounding rule | ⭐ a 4-minute stay is free — always state the rule |
| `LocalDateTime.now()` in the domain | untestable pricing (Day 300) |
| ⭐ Not volunteering concurrency | ⭐ the marks were free |

## Interview questions

**Q: Why an enum for vehicle type instead of subclasses?**
Because they differ in data — size and what they fit in — not behaviour. Three subclasses with no
overridden method is inheritance used as a label. If trucks needed a genuinely different pricing
algorithm I would switch, but I would put that in a strategy rather than the vehicle anyway.

**Q: How does a vehicle get matched to a spot?**
As data, not code. Each vehicle type carries the set of spot sizes it fits. Ordinal comparison —
spot size at least vehicle size — works until you add a spot that is not on the size axis, like an EV
or accessible bay, and then every comparison is wrong. Expressing fit as a set means a new spot type
is a data change.

**Q: Two cars arrive at the same time. What happens?**
Both can be offered the same spot, because finding a free spot and taking it are two operations. I
make `tryOccupy` a compare-and-set on the spot's occupant, so exactly one succeeds and the other
moves to the next candidate — no lock, and cars taking different spots never contend. With multiple
instances, that becomes an optimistic version column or a partial unique index; it is the same
algorithm with the database as arbiter.

**Q: Is the parking lot one aggregate?**
No. If it were, every arrival would load and lock two thousand spots and you would have one writer
for the whole lot. The spot is the aggregate — it holds its own occupancy invariant — and the lot is
an index over spots, not a consistency boundary.

**Q: Now add reservations.**
That is the expensive one. Occupancy stops being a boolean and becomes a timeline, so `isFree()`
becomes `isFreeBetween(from, to)` and allocation becomes an interval query — a per-spot sorted set of
intervals, or an exclusion constraint if the database supports it. I would also need a no-show policy
and an expiry, because a held spot that nobody claims is worse than no reservation system.
