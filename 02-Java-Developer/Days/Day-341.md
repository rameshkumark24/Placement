# Day 341

**L-341** · API gateway, service discovery, and the service mesh

**Time:** 3 hrs · **Mode:** NEW

> **⭐ The moment you have more than one service, three problems appear: how does the outside world
> reach you, how do services find each other, and who enforces the rules on every call.**
>
> Each has a standard answer, each answer is over-adopted, and **knowing when you do not need one is
> the part that distinguishes a design from a shopping list.**

---

# Part 1 — ⭐ The API gateway

```
   clients ──► ⭐ GATEWAY ──► order-service
                   │      ──► user-service
                   │      ──► search-service
       ⭐ TLS · authN · rate limit · routing · request id · CORS
```

| ⭐ The gateway SHOULD do | ⭐ It must NOT do |
|---|---|
| ⭐ **TLS termination** and certificate management | ⭐⭐ **business logic — this is how you rebuild an ESB** |
| ⭐ **Authentication** — validate the token once (Day 173) | ⭐ per-service authorisation decisions |
| ⭐ **Rate limiting and quotas** (Day 336) | data transformation that encodes domain rules |
| ⭐ Routing, versioning, canaries | ⭐ **anything a team needs to change weekly** |
| ⭐ **Correlation id injection** (Day 338) | orchestration of business workflows |
| Request/response logging, CORS, compression | |

> **⭐ The rule: the gateway holds edge concerns — things true of every request regardless of what it
> does.** The moment it contains an `if` about orders, **you have created a component that every team
> must queue to change**, which is a bottleneck with a bus factor.

⚠️ **Authentication at the gateway does not mean the services can trust anything.** A service must
still verify the caller — **otherwise anything inside the network can impersonate the gateway.** Pass
a signed identity, or verify the token again; **"the gateway checked it" is how internal breaches
become total** (Day 176's zero-trust argument).

## ⭐ Aggregation and the BFF

| Pattern | ⭐ When |
|---|---|
| ⭐ Gateway aggregation — one client call fans out to three services | ⭐ mobile clients, where round trips are expensive |
| ⭐⭐ **BFF — one gateway per client type** | ⭐⭐ **when web and mobile need genuinely different shapes** |
| GraphQL at the edge | ⭐ clients with varied and changing data needs |

**⭐ The BFF's justification is ownership: the mobile team owns the mobile BFF**, so shaping data for
mobile does not require a change in a shared component. **The cost is another deployable per client
type**, and the failure mode is BFFs accumulating business logic — the same trap as the gateway.

⚠️ **The gateway is a single point of failure and it is on every request path.** It must be
replicated, autoscaled, load-tested at peak and **as simple as you can make it** — because its
failure is total, not partial.

# Part 2 — ⭐ Service discovery

> **⭐ The problem: instances come and go — deploys, autoscaling, failures — so hard-coded addresses
> are wrong within minutes.**

| Approach | ⭐ How | ⭐ Trade |
|---|---|---|
| ⭐ **DNS** | a name resolves to instance IPs | ⭐⭐ **TTL caching means removals are slow — bad for failover** (Day 325) |
| ⭐ **Client-side** (Eureka, Consul) | client fetches the registry and load-balances itself | ⭐ no extra hop; **every client needs the logic** |
| ⭐ **Server-side** | a load balancer or proxy holds the list | ⭐ language-agnostic; **one more hop** |
| ⭐⭐ **Platform-native** (Kubernetes Services) | ⭐ the platform maintains endpoints from readiness probes | ⭐⭐ **the default now — nothing to run** |

| ⭐ Detail that matters | |
|---|---|
| ⭐ **Registration must be automatic** | manual registries go stale immediately |
| ⭐⭐ **Deregistration on failure is the hard part** | ⭐⭐ **a crashed instance cannot deregister itself — you need health checks and TTLs** |
| ⭐ Readiness gates membership | Day 325 — not liveness |
| ⭐ **Stale entries send traffic to nothing** | ⭐ so clients need retries against a *different* instance |

> **⭐ Say it: on Kubernetes, discovery is solved and you should not add Eureka or Consul for it.**
> Services get a stable DNS name, endpoints are maintained from readiness probes, and removal is
> event-driven rather than TTL-driven. **Adding a second registry is a component to run for a problem
> the platform already handles.**

# Part 3 — ⭐⭐ The service mesh

```
   ┌── pod ──────────────┐          ┌── pod ──────────────┐
   │  app  ◄──► ⭐ SIDECAR │ ◄──mTLS──► ⭐ SIDECAR ◄──► app │
   └─────────────────────┘          └─────────────────────┘
                     ▲                        ▲
                     └──── ⭐ CONTROL PLANE ───┘
                       (policy, certs, config, telemetry)
```

**⭐ The sidecar intercepts all network traffic and applies, without touching your code:**

| ⭐ Capability | ⭐ Otherwise you would |
|---|---|
| ⭐⭐ **mTLS between every service, with rotation** | ⭐⭐ **implement it per language — the strongest single argument for a mesh** |
| ⭐ Retries, timeouts, circuit breaking (Day 339) | configure Resilience4j in Java, something else in Go, nothing in Python |
| ⭐ **Traffic splitting** — canary, blue/green, mirroring | build it into the gateway or the app |
| ⭐ **Uniform telemetry** — RED metrics for every hop, free | instrument each service consistently |
| Authorisation policy between services | scatter it across codebases |

| ⭐ Costs | |
|---|---|
| ⭐ **Latency per hop** | ⭐ typically 1–3 ms each way — **noticeable in a deep chain** |
| ⭐ Resource overhead | a proxy per pod: CPU and memory, multiplied |
| ⭐⭐ **A control plane to operate and upgrade** | ⭐⭐ **and it is now on the critical path of your network** |
| ⭐ Debugging is harder | ⭐ **"is it my service, my sidecar, or the policy?"** |

> **⭐ The decision, stated as a threshold: not worth it at five services in one language. Seriously
> consider it at fifty services across several languages, or when mTLS everywhere is a compliance
> requirement.** In between, **Resilience4j plus your existing observability plus the gateway covers
> most of it** — and saying that is a stronger answer than adopting a mesh because it is modern.

⚠️ **Sidecarless and ambient modes are the current direction** — moving L4 concerns into a per-node
component and keeping a proxy only where L7 features are needed, to cut the per-pod cost. **Worth
mentioning as awareness; not worth designing around.**

## ⭐ North-south vs east-west

| | ⭐ North-south | ⭐ East-west |
|---|---|---|
| Traffic | ⭐ clients → your system | ⭐ service → service |
| Handled by | ⭐ **the API gateway** | ⭐ **the mesh, or client libraries** |
| Concerns | authN, rate limits, TLS, public contracts | mTLS, retries, discovery, internal policy |
| ⭐ Trust | ⭐ **untrusted — validate everything** | ⭐ **not automatically trusted either** (zero trust) |

**⭐ Keeping the two separate is the clean mental model**, and it explains why a gateway is not a mesh
and a mesh is not a gateway — **even though many products now do both.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Business logic in the gateway | ⭐⭐ **an ESB — every team queues to change one component** |
| ⭐ Services trusting "the gateway checked it" | ⭐ anything inside the network can impersonate it |
| ⭐ A gateway not load-tested at peak | it is on every request; its failure is total |
| ⭐ **DNS as the failover mechanism** | ⭐ TTL caching means minutes of traffic to dead hosts |
| ⭐ A manual or stale registry | traffic to instances that no longer exist |
| ⭐ **Registration without automatic deregistration** | ⭐⭐ **crashed instances stay in rotation** |
| Liveness gating registry membership | Day 325 — use readiness |
| ⭐ Adding Consul or Eureka on Kubernetes | ⭐ a second registry for a solved problem |
| ⭐ **A mesh at five services** | ⭐ a control plane on your critical path, for retries you already had |
| Ignoring per-hop mesh latency | 2 ms × 8 hops is a real budget item |
| BFFs accumulating domain logic | the gateway trap, one layer down |

## Interview questions

**Q: What belongs in an API gateway?**
Edge concerns — things true of every request regardless of what it does: TLS termination,
authentication, rate limiting, routing, canaries, correlation ids, CORS. Not business logic. The
moment it contains an `if` about orders, every team has to queue behind one component to ship, and
you have rebuilt an enterprise service bus.

**Q: If the gateway authenticates, do services still need to?**
Yes. Otherwise anything that reaches the network can impersonate the gateway, and one compromised pod
becomes total access. The gateway validates the external token and passes a signed internal identity;
each service still verifies it and makes its own authorisation decision, because authentication is
not authorisation.

**Q: How do services find each other?**
On Kubernetes, the platform does it — a stable DNS name backed by endpoints maintained from readiness
probes, with removal event-driven rather than TTL-driven. I would not add Eureka or Consul for
discovery there. Off-platform, a registry with automatic registration and, more importantly,
automatic deregistration, because a crashed instance cannot remove itself — that is what health
checks and TTLs are for. Plain DNS is poor for failover because clients cache beyond the TTL.

**Q: When is a service mesh worth it?**
When mTLS everywhere is a requirement, or when you have enough services in enough languages that
implementing retries, timeouts, circuit breaking and consistent telemetry per stack is genuinely
worse than running a control plane. Not at five services in one language, where Resilience4j and
existing observability cover it. The costs are real: a millisecond or three per hop, a proxy per pod,
a control plane on the critical path, and a third place a failure could be hiding.

**Q: What is the difference between north-south and east-west traffic?**
North-south is clients reaching your system and is the gateway's job — external contracts,
authentication, quotas. East-west is service to service and is the mesh's or the client library's job
— mTLS, discovery, retries, internal policy. Keeping them separate is what stops a gateway from
slowly becoming an orchestrator. Neither is automatically trusted, which is the zero-trust point.

## Mini task

1. **List everything your gateway does.** Mark each as an edge concern or business logic. **Move the
   second category out.**
2. ⭐ **Call a service directly, bypassing the gateway, with no token.** If it answers, your services
   trust the network — fix it.
3. Load-test the gateway at peak and **compare its capacity with the services behind it.**
4. ⭐ Kill an instance without graceful shutdown and **measure how long it stays in the registry.**
   That window is your failure blast radius.
5. Change readiness to failing and **confirm the instance leaves rotation** without being killed.
6. ⭐ Deploy a mesh in a test cluster and **measure the added latency per hop.** Multiply by your
   deepest chain.
7. ⭐ Implement retries and circuit breaking **twice** — once in Resilience4j, once as mesh policy.
   **Compare the effort and decide honestly which you would run.**
8. ⭐ Enable mTLS between two services in the mesh, then **capture traffic and confirm it is
   encrypted.**
9. Draw your system marking every hop as north-south or east-west, **and note which component owns
   each concern.**

## 🎙️ Articulation drill

**Three minutes:** *"You have eight services. Do you need a service mesh?"*

**⭐ The marker: you answer "probably not" and say what you would do instead** — Resilience4j for
retries and breakers, the platform for discovery, the gateway for edge concerns, existing tracing for
telemetry. **Then name the one thing that would change your mind: mTLS everywhere as a compliance
requirement, or a third language entering the estate.**

**⭐ Declining a technology with a specific trigger for reconsidering it is a stronger answer than
adopting it**, because it shows you have priced the control plane rather than assumed it is free.
