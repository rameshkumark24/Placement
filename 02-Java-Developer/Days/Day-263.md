# Day 263 🏗️

**P-263** · The outbox in anger — the dual-write, actually solved

**Time:** 3 hrs · **Mode:** BUILD

> Day 124 established the dual-write problem. Day 256 decided which of your side effects must not be
> lost. **Today you build the mechanism, and the standard is that you can demonstrate both failure
> modes and show that neither loses data.**
>
> **⭐ This is one of the two or three things in the whole project that will most distinguish it.**
> Almost every project publishes events with a direct call inside a transaction and has never
> considered what happens when the process dies between the commit and the publish.

---

# Part 1 — ⭐ The problem, demonstrated before it is fixed

```
❌ @Transactional
   repo.save(booking);
   eventPublisher.send("booking.created", event);     ⭐ a dual write
```

**⭐ Two failure modes, and both are silent:**

| Failure | Result |
|---|---|
| ⭐ **Send succeeds, transaction rolls back** | ⭐ an event for a booking that does not exist |
| ⭐ **Transaction commits, send fails** | ⭐ a booking nobody downstream knows about |

**⭐ Reproduce both today, before implementing the fix.** Throw after the send; kill the process
between the commit and the send. **Seeing your own system produce a phantom event is what makes the
pattern stick** — and it is the story you will tell.

## ⭐ The outbox

```
⭐ outbox_messages: id, aggregate_type, aggregate_id, event_type, payload jsonb,
                    created_at, ⭐ published_at, ⭐ attempts, ⭐ last_error
```

```
⭐ tx: save(booking) + insert into outbox   ← ⭐ ONE transaction. Atomic. No window.
⭐ Then: a poller reads unpublished rows and sends them, with retries.
```

> **⭐ The event commits with the business data or not at all. That is the entire point, and it is why
> no amount of retry logic around a direct publish is equivalent.**

**⭐ Write it via `@TransactionalEventListener(BEFORE_COMMIT)`** (Day 179) so the domain still emits a
domain event and the outbox row is a consequence — rather than every service method remembering to
insert one.

# Part 2 — ⭐ The poller, built with Day 178's lessons

```sql
⭐ select * from outbox_messages
   where published_at is null and attempts < 10
   order by created_at
   ⭐ for update skip locked
   limit 100;
```

**⭐ `FOR UPDATE SKIP LOCKED` is the primitive that makes this work on every instance
simultaneously** (Day 178, Day 195): each poller claims a distinct batch, none block each other, and
duplicate execution becomes parallelism rather than duplication. **You do not need ShedLock for the
outbox poller** — and knowing why is a good answer.

**⭐ The partial index is mandatory, not an optimisation** (Day 190):

```sql
create index ix_outbox_unpublished on outbox_messages (created_at)
    where published_at is null;                        -- ⭐ 0.01% of the table
```

**⭐ Without it the poller scans a table that grows forever and gets slower every day** — Day 190's
job-poller case, in your own project.

## ⭐ The four things the poller must get right

| # | Requirement | Why |
|---|---|---|
| ⭐ 1 | **Mark published in the same transaction as the claim** | ⭐ or you send and crash, then send again forever |
| ⭐ 2 | **Bounded retries with backoff** | ⭐ a permanently-failing message must not block or spin |
| ⭐ 3 | **A dead-letter state after N attempts**, with `last_error` | ⭐ a message you cannot send is data loss you must see |
| ⭐ 4 | **Delete or archive published rows** | ⭐ Day 194 — the table grows forever, and bulk deletes bloat |

**⭐ Point 4 deserves a decision now**: either partition the outbox by day and drop partitions
(Day 200 — instant, no dead tuples), or delete published rows in small batches with the partial index
doing the work. **A bulk `delete from outbox where published_at is not null` on ten million rows is
Day 194's bloat problem.**

## ⭐ Ordering — decide it explicitly

**⭐ `SKIP LOCKED` gives you parallelism and therefore *no global ordering*.** If two events for the
same booking must arrive in order, claim by aggregate:

```sql
⭐ ... where aggregate_id = any (select distinct aggregate_id from claimed_batch)
⭐ or: partition the poll by hash(aggregate_id) so one worker owns an aggregate
```

**⭐ Most systems do not need global ordering and do need per-aggregate ordering.** Say which you
chose and why — it is a real distributed-systems decision and most candidates have not thought about
it.

# Part 3 — ⭐ At-least-once, and the consumer half

> **⭐ The outbox guarantees at-least-once. It makes duplicates *certain*, not merely possible** — a
> publish that succeeds before the row is marked will be republished.

**⭐ That is fine, and it is only fine because the consumer is idempotent** (Day 185A). **The two
halves are one design:**

```
⭐ Producer: the outbox guarantees at-least-once
⭐ Consumer: idempotency makes at-least-once sufficient
```

```
⭐ processed_events: event_id primary key, processed_at
⭐ The marker and the work commit in the SAME transaction   (Day 185A)
```

**⭐ Three ways to be idempotent, best first:**

| | |
|---|---|
| ⭐ 1 | **Naturally idempotent** — `set status = CONFIRMED` is safe any number of times |
| ⭐ 2 | **A processed-events table** with a unique constraint, in the work's transaction |
| 3 | Upsert on a business key — `on conflict do nothing` |

**⭐ And the test that proves it, which is today's deliverable:**

```
⭐ Deliver the same event twice → assert exactly one effect
```

## ⭐ Where the events go

| Transport | When | Day |
|---|---|---|
| ⭐ **In-process listener** | ⭐ single service — ⭐ still worth the outbox for durability | 179 |
| ⭐ **Redis Streams** | already running Redis; ⭐ volume fits memory | 209 |
| **Kafka** | the log is a system of record; retention in days | 185A |
| Debezium CDC | ⭐ no poller at all — reads the WAL | 201 |

**⭐ The honest note for a single-service project: the outbox is worth building even with an
in-process consumer**, because it is durability, not distribution. **And say that** — "I used an
outbox with an in-process handler because the requirement was not losing the effect, not crossing a
process boundary" is a better answer than adding Kafka to justify the pattern.

# Part 4 — ⭐ Prove it

**⭐ Four tests and two demonstrations. These are the evidence.**

```
⭐ 1. Roll back after writing the outbox row → ⭐ NO row, NO event
⭐ 2. Kill the process between commit and publish → ⭐ the poller sends it on restart
⭐ 3. Same event delivered twice → ⭐ exactly one effect
⭐ 4. A permanently failing message → ⭐ dead-lettered after N attempts, last_error populated
```

```
⭐ Demo A: three poller instances running → ⭐ no message sent twice, none stuck
⭐ Demo B: 10,000 messages queued → ⭐ measure throughput and the lag metric
```

**⭐ Test 2 is the one that matters.** It is the exact failure that a direct publish cannot survive,
and demonstrating recovery is what turns the pattern from a diagram into something you have operated.

## ⭐ The metrics, without which it is unoperable

```
⭐ outbox_unpublished_count      — ⭐ a GAUGE. Alert if it grows steadily
⭐ outbox_oldest_unpublished_age — ⭐ THE key metric — lag, in seconds
⭐ outbox_published_total, outbox_failed_total, outbox_dead_lettered_total
```

**⭐ Alert on `oldest_unpublished_age`, not on the count.** A count of 5,000 during a burst is
healthy; **one message stuck for twenty minutes is a broken poller**, and only the age metric
distinguishes them.

**⭐ And alert on `dead_lettered_total > 0`.** A dead-lettered message is an effect that never
happened — a confirmation email never sent, a downstream system never told. **A dead-letter queue
nobody watches is silent data loss** (Day 185A).

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Publishing inside a transaction | ⭐ the dual write, both directions |
| ⭐ `AFTER_COMMIT` + a direct publish for critical work | ⭐ lost if the process dies in between |
| ⭐ Marking published in a separate transaction | send-and-crash → resend forever |
| ⭐ No partial index on the outbox | ⭐ the poller gets slower every day |
| ⭐ Unbounded retries | a poison message spins forever |
| ⭐ No dead-letter state | a permanently failing message is invisible |
| ⭐ Never deleting published rows | ⭐ unbounded growth, then a bulk delete and bloat |
| Bulk-deleting published rows | Day 194 — partition and drop instead |
| ⭐ Assuming ordering with `SKIP LOCKED` | events for one aggregate arrive out of order |
| ⭐ Non-idempotent consumer | ⭐ at-least-once becomes duplicate side effects |
| Marker in a different transaction from the work | duplicate or lost work |
| ⭐ Alerting on count rather than age | bursts page you; a stuck poller does not |
| A DLQ nobody watches | silent data loss |

## ⭐ Self-review

- [ ] ⭐ **Both dual-write failures reproduced** before implementing the fix
- [ ] The outbox row is written in the **same transaction**, via `BEFORE_COMMIT`
- [ ] ⭐ Poller uses **`FOR UPDATE SKIP LOCKED`** and runs safely on every instance
- [ ] ⭐ **Partial index** on unpublished rows
- [ ] Published marked in the claim's transaction; retries bounded; ⭐ **dead-letter state exists**
- [ ] ⭐ **A retention decision made** — partition-and-drop or batched deletes
- [ ] Ordering requirement decided and documented
- [ ] ⭐ **Consumer idempotent, with the marker in the work's transaction**
- [ ] ⭐ **All four tests and both demonstrations pass**
- [ ] ⭐ Metrics emitted; ⭐ **alerts on lag AGE and on dead-lettered count**

## 🎤 Defence questions

1. **⭐ Why not just publish after saving?** (⭐ both failure directions)
2. **⭐ Walk me through what happens if the process dies right after the commit.**
3. **⭐ Why doesn't your poller need a distributed lock?**
4. **⭐ Your outbox guarantees at-least-once. What makes that acceptable?**
5. **⭐ Do events for one booking arrive in order? How do you know?**
6. **⭐ What happens to a message that can never be sent?**
7. **⭐ How does the outbox table not grow forever?**
8. **⭐ Which metric tells you the poller is stuck, and why not the queue depth?**

## ✅ Done when

- ⭐ Both dual-write failures reproduced, then made impossible
- ⭐ Kill-between-commit-and-publish recovers automatically
- ⭐ Duplicate delivery produces one effect
- ⭐ Lag-age and dead-letter alerts configured
