# Day 309

**L-309** · UML that earns its keep — class, sequence, and the state diagram nobody draws

**Time:** 3 hrs · **Mode:** NEW

> **⭐ You need about 15% of UML. The rest is a certification syllabus.**
>
> Today is the notation that changes a conversation — plus the whiteboard mechanics of drawing it
> under time pressure without running out of space, which is a real skill and nobody teaches it.

# Part 1 — ⭐ The class diagram

```
        ┌─────────────────────────┐
        │      ParkingLot         │   ⭐ name
        ├─────────────────────────┤
        │ - id: LotId             │   ⭐ - private  + public  # protected
        │ - floors: List<Floor>   │
        ├─────────────────────────┤
        │ + park(v: Vehicle): Ticket   │   ⭐ only the methods that MATTER
        │ + release(t: Ticket): Money  │
        └─────────────────────────┘
```

⚠️ **Do not write getters, setters or constructors on a whiteboard.** They cost a third of your
space and communicate nothing. **Show the two or three methods the design is about.**

## ⭐ The five relationships — and the one that actually matters

| Notation | Name | ⭐ Means |
|---|---|---|
| `───────` | Association | "knows about" |
| `───────◇` | Aggregation | ⭐ "has, but they live independently" |
| ⭐ **`───────◆`** | ⭐ **Composition** | ⭐⭐ **"owns — dies with me"** |
| `───────▷` | Inheritance | `extends` |
| `- - - -▷` | Realization | `implements` |

**⭐ Only the filled diamond is worth arguing about, and here is why it is not pedantry:**

> **⭐ Composition ≈ the aggregate boundary (Day 305).** If a `Spot` cannot exist without its `Floor`,
> they are in one aggregate: one repository, one transaction, one lock, deleted together.
> **Drawing a filled diamond is claiming a consistency boundary**, and interviewers who know DDD hear
> it as one.

**⭐ Multiplicity is where the real questions hide** — write it on every line:

```
⭐ ParkingLot 1 ────◆ 1..* Floor 1 ────◆ 1..* Spot
⭐ Ticket 1 ──── 0..1 Payment           ⭐ ← "0..1" forces: unpaid tickets exist. For how long?
⭐ User 1 ──── 0..* Vehicle             ⭐ ← "0..*" forces: a user with no vehicle is legal?
```

**⭐ Every `0..` you write is a question the interviewer was going to ask.** Writing them first makes
you look like you thought about the edge cases, which you now have.

## ⭐ What to leave off

| Leave off | Why |
|---|---|
| ⭐ Getters, setters, constructors | ⭐ noise, and a third of the board |
| Every field | ⭐ show identity, state, and the key relationships |
| Package names, stereotypes | nobody is generating code from this |
| ⭐ Classes you are not going to build | ⭐ they invite questions you cannot answer |

# Part 2 — ⭐ The sequence diagram

**⭐ Draw exactly one, for the hardest flow — the one with a race, a rollback, or three
collaborators.**

```
 Driver      EntryPanel      SpotAllocator      Floor           TicketService
   │              │                │              │                   │
   │──park(veh)──►│                │              │                   │
   │              │──allocate(t)──►│              │                   │
   │              │                │──reserve()──►│                   │  ⭐ ATOMIC — see Day 310
   │              │                │◄──spot───────│                   │
   │              │                │              │                   │
   │              │────────────── issueTicket(spot, veh) ────────────►│
   │              │◄───────────────────── ticket ─────────────────────│
   │◄──ticket─────│                │              │                   │
   │              │                │              │                   │
   │              │        ⭐ alt [no spot available]                  │
   │◄──LotFull────│                │              │                   │
```

| Element | Notation | ⭐ Use it for |
|---|---|---|
| ⭐ **Synchronous call** | ⭐ solid line, filled arrowhead | the normal case |
| ⭐ **Return** | dashed line | ⭐ only when the value matters |
| ⭐ **Asynchronous** | ⭐ solid line, **open** arrowhead | ⭐ **events, queues — say "fire and forget"** |
| `alt` | a box with a dashed divider | ⭐ **the failure branch — draw it** |
| `loop` | a labelled box | batch operations |
| ⭐ **Activation bar** | ⭐ the thin rectangle on a lifeline | ⭐ **shows how long something is held — see below** |

**⭐ Two things a sequence diagram shows that a class diagram cannot**, and both are what the
interviewer is probing:

1. ⭐ **Where the transaction starts and ends.** Draw a bracket down the side. **If it spans a call
   to an external system, you have just drawn Day 302's worst bug and can say so.**
2. ⭐ **Where the lock is held.** The activation bar over `Floor` is the critical section. **If it
   extends across the ticket-service call, your lock is too coarse** — and you have found that
   yourself, visually, before being told.

> **⭐ That is the whole argument for drawing one: it makes duration visible, and every concurrency
> and latency problem in LLD is a duration problem.**

# Part 3 — ⭐⭐ The state diagram — the highest-value one nobody draws

**⭐ When state is the problem — vending machines, ATMs, elevators, orders, bookings — a state
diagram is worth more than everything else on the board.**

```
              ┌────────┐  addItem   ┌────────┐   pay    ┌────────┐
     ────────►│ DRAFT  │───────────►│ PLACED │─────────►│  PAID  │
              └────────┘            └────────┘          └────────┘
                   │                     │                   │ ship
                   │ cancel              │ cancel            ▼
                   ▼                     ▼              ┌─────────┐
              ┌───────────┐◄─────────────┘              │ SHIPPED │
              │ CANCELLED │      ⭐ NOTE: no arrow      └─────────┘
              └───────────┘      ⭐ from PAID → CANCELLED.        │ deliver
                                 ⭐ Refund is a DIFFERENT path.   ▼
                                                            ┌───────────┐
                                                            │ DELIVERED │
                                                            └───────────┘
```

**⭐ Four things it gets you in about ninety seconds:**

| ⭐ Gets you | ⭐ How |
|---|---|
| ⭐ **The complete list of transitions** | ⭐ which becomes the entity's method list (Day 304) |
| ⭐ **The illegal transitions, explicitly** | ⭐ **the missing arrow is the design statement** |
| ⭐ **Terminal states** | anything with no outgoing arrow — say so |
| ⭐ **The guard conditions** | `[if paid]` on an arrow is an invariant, written down |

> **⭐ The strongest sentence available on a whiteboard: "there is deliberately no arrow from PAID to
> CANCELLED — once money has moved, cancellation is a refund, which is a different flow with a
> different invariant."** That is one sentence, and it demonstrates domain thinking, invariant
> awareness and scope discipline simultaneously.

**⭐ And it maps directly to code** — Day 304's named transitions, or Day 317's state pattern:

```java
public void ship(Instant when) {
    if (status != PAID) throw new IllegalTransition(status, SHIPPED);   // ⭐ every missing arrow
    ...
}
```

## ⭐ What never to draw in an interview

| Diagram | Why not |
|---|---|
| ⭐ **Use case diagrams** | ⭐ stick figures and ellipses; a bulleted list is faster and clearer |
| Activity diagrams | a sequence diagram says more per square inch |
| Component/deployment | ⭐ that is Stage 9's HLD, not LLD |
| ER diagrams | ⭐ **unless asked** — the class diagram already has the model |

# Part 4 — ⭐ Whiteboard mechanics

**⭐ A genuine skill, and running out of space wastes five minutes you do not have.**

```
┌──────────────────────────────────────────────────────────┐
│ SCOPE:  in — park, unpark, price   out — reservations    │  ⭐ top-left, small, permanent
├───────────────────────────────┬──────────────────────────┤
│                               │                          │
│   ⭐ CLASS DIAGRAM            │   ⭐ CODE                │
│   (centre-left, biggest)      │   (right third)          │
│                               │                          │
├───────────────────────────────┤                          │
│  ⭐ sequence / state (bottom) │                          │
└───────────────────────────────┴──────────────────────────┘
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐ **Scope in the top-left corner, never erased** | you will refer back to it under pressure |
| ⭐ **Start the main class left of centre, not centre** | ⭐ relationships grow in both directions |
| ⭐ **Boxes small, gaps large** | ⭐ you will add fields; you cannot add space |
| ⭐ **One area reserved for code** | do not let the diagram eat it |
| ⭐ **Never erase a decision — cross it out** | ⭐ **"I considered X, moved to Y" is visible reasoning** |
| Enums as a bare list, not boxes | they are data |

**⭐ Remote rounds:** practise in the tool they use (a shared doc, Excalidraw, CoderPad). **In a
text-only editor, use indented text for the class model and go straight to code** — do not try to
draw ASCII boxes under time pressure. **The model can be a list of class names with their fields and
one line of relationships.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Getters and setters on the board | ⭐ a third of your space, zero information |
| ⭐ No multiplicity | ⭐ **you skipped the edge-case questions** |
| Arguing aggregation vs composition abstractly | ⭐ only worth it as an aggregate-boundary claim |
| ⭐ No sequence diagram for the hard flow | ⭐ duration stays invisible — locks and transactions unexamined |
| ⭐ Skipping the `alt` branch | the failure path is where the marks are |
| ⭐ Not drawing a state diagram for a state problem | ⭐ **the cheapest 90 seconds in the round** |
| Drawing every transition and no missing ones | ⭐ the missing arrow is the design statement |
| Use case diagrams | slow, low-information, dated |
| ⭐ Running out of board | ⭐ five minutes lost to re-drawing |
| Erasing rejected ideas | your reasoning becomes invisible |

## Interview questions

**Q: What is the difference between aggregation and composition, and does it matter?**
Aggregation is "has, independently"; composition is "owns, and they die together". It matters when
you read it as an aggregate boundary — a filled diamond says one repository, one transaction, one
lock, deleted together. As pure notation it is not worth arguing about; as a claim about consistency
it is the most important line on the diagram.

**Q: What do you get from a sequence diagram that a class diagram cannot give you?**
Duration. The activation bar shows how long a lock is held and the bracket shows where the
transaction starts and ends — so a call to an external system inside that bracket, or a lock held
across three collaborators, becomes visible rather than theoretical. Every concurrency and latency
problem in low-level design is a duration problem.

**Q: When do you draw a state diagram?**
Whenever state is the problem — vending machines, ATMs, orders, bookings, elevators. Ninety seconds
gives me the complete transition list, which becomes the entity's methods; the terminal states; the
guard conditions; and, most usefully, the transitions I am deliberately excluding. The missing arrow
from PAID to CANCELLED is a stronger statement about the domain than anything else I could draw.

**Q: How much UML do you actually use?**
Class diagrams with multiplicity, one sequence diagram for the hard flow, and a state diagram when
state is the problem. I skip use case and activity diagrams — a bulleted list of actors and flows
carries the same information in a quarter of the time and space.

**Q: How do you manage whiteboard space?**
Scope in the top-left, never erased. Main class left of centre because relationships grow both ways.
Small boxes, large gaps, because I can add fields but not space. A third of the board reserved for
code before I start drawing. And I cross out rejected ideas rather than erasing them, so the
reasoning stays visible.

## Mini task

1. Draw the **class diagram** for one Stage 8 problem **with multiplicity on every line.** For each
   `0..`, write the question it raises.
2. Mark every **composition diamond** and say out loud which aggregate it declares.
3. Draw the **sequence diagram** for the hardest flow, **with the transaction bracket and the lock
   activation bar.** Find one thing wrong with your own design from the picture alone.
4. Add the **`alt` failure branch.** Most designs have no answer for it until it is drawn.
5. ⭐ Draw the **state diagram** for an order or a booking. **Then list every transition you did NOT
   draw and justify each absence in one sentence.**
6. Turn that state diagram into **Java method signatures with guards.** They should map one to one.
7. ⭐ **Do a full 45-minute run on physical paper the size of a whiteboard** and see whether your
   layout survives. Then do the same in a plain text editor with no drawing at all.

## 🎙️ Articulation drill

**Two minutes:** draw a state diagram for a **hotel booking** and narrate it — including every
transition you are deliberately leaving out.

**⭐ The marker: you spend more time on the missing arrows than the present ones.** Anyone can list
BOOKED → CHECKED_IN → CHECKED_OUT. **"There is no arrow from CHECKED_OUT back to anything — it is
terminal; a dispute is a separate flow"** is domain reasoning, and it is what the diagram was for.
