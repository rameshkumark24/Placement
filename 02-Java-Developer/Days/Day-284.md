# Day 284 🏗️

**P-284** · Infrastructure — where it runs, and how it survives losing something

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ The most defensible infrastructure choice is the smallest one that meets your stated
> availability target** — and Day 249 gave you that target as a number. Most projects are
> over-architected for a requirement nobody wrote down.
>
> **⭐ Today's real deliverable is not the infrastructure. It is the answer to "what happens when you
> lose this?" for every component** — and having tested at least two of those answers.

---

# Part 1 — ⭐ Right-size it from the NFR

**Day 249's availability target decides the architecture. Read it, then choose:**

| Target | Downtime/month | ⭐ What it justifies |
|---|---|---|
| ⭐ **99.5%** | ⭐ **3.6 hours** | ⭐ **a single instance is defensible** — say so |
| 99.9% | 43 minutes | 2+ instances, managed database, automated deploys |
| 99.95% | 22 minutes | multi-AZ, automated failover, on-call |
| 99.99% | 4 minutes | multi-region, ⭐ a different budget entirely |

> **⭐ "I targeted 99.5%, which is why I run two instances in one availability zone with a managed
> database and did not build multi-region" is a much stronger answer than an architecture diagram
> with no target behind it.**

**⭐ The mistake to avoid is the opposite of under-engineering**: a Kubernetes cluster, a service
mesh and three regions for a project with fifty users signals that you cannot size a solution — which
is a worse impression than a simple deployment defended well.

## ⭐ Choosing the platform, honestly

| Option | ⭐ Right when |
|---|---|
| ⭐ **A VM + Docker Compose** | ⭐ one service, 99.5% — ⭐ **completely defensible** |
| ⭐ **A managed container platform** (ECS, Cloud Run, App Runner) | ⭐ **the sweet spot for most flagships** |
| Managed Kubernetes | several services, or the team already runs it |
| Self-managed Kubernetes | ⭐ almost never for a project |

**⭐ Managed container platforms are the pragmatic default**: you get rolling deploys, health checks,
autoscaling and secrets without operating a control plane. **And say what you gave up** — less
control over networking and scheduling than Kubernetes offers.

**⭐ The database is not a place to save money by self-hosting.** A managed PostgreSQL gives you
automated backups, PITR, patching and failover — all of Day 201's machinery — for less than the time
it takes to build any one of them badly.

# Part 2 — ⭐ Infrastructure as code, and why it matters here

```
⭐ Terraform (or the equivalent) for everything: network, database, service, secrets, DNS, alerts
⭐ ⭐ REMOTE STATE with locking     ← ⭐ local state is a single point of failure you cannot recover
⭐ Separate state per environment
```

**⭐ Three reasons this is worth the time on a project this size:**

| Reason | Detail |
|---|---|
| ⭐ **Reproducible** | ⭐ you can rebuild the environment from scratch — ⭐ and you will test this |
| ⭐ **Reviewable** | an infrastructure change is a diff, like Day 251's contract |
| ⭐ **Documented by construction** | the code *is* the answer to "how is this set up?" |

**⭐ The test that proves it: destroy your staging environment and rebuild it from the code.** If that
works, your disaster recovery is real; if it does not, you have documentation that happens to be
executable.

**⭐ And it is a strong defence point** because most candidates configured their infrastructure by
clicking, and cannot answer "how would you recreate this?"

## ⭐ Secrets in infrastructure

```
⭐ A secret manager — never Terraform variables committed anywhere
⭐ The application reads them at runtime (Day 142) — ⭐ config tree or environment injection
⭐ Rotation is a documented, practised procedure (Day 283)
```

⚠️ **⭐ Terraform state contains secret values in plaintext.** Encrypt the state bucket, restrict
access to it, and **treat it as sensitive as the secrets themselves** — this catches almost everyone
once.

# Part 3 — ⭐⭐ The failure matrix

> **⭐⭐ For every component: what happens when you lose it, and have you tried?**

| Component lost | ⭐ Expected behaviour | Tested? |
|---|---|---|
| ⭐ **One application instance** | ⭐ traffic shifts; no user impact | ⭐ **kill one under load** |
| ⭐ **All instances** | total outage; ⭐ recovery is automatic restart | |
| ⭐ **The database** | ⭐ readiness down, ⭐ **liveness UP** — ⭐ no crash loop (Day 128) | ⭐ **stop it** |
| ⭐ **Redis** | ⭐ **degraded, not broken** (Day 266) | ⭐ **stop it** |
| ⭐ **Object storage** | uploads fail; ⭐ the rest of the API works | |
| ⭐ **An external API** | ⭐ circuit opens; fallback path (Day 181) | ⭐ **WireMock delay** |
| The whole availability zone | ⭐ outage at 99.5% — ⭐ **an accepted, stated risk** | |

**⭐ Test at least the four marked ones today, against the deployed instance, under load.**

**⭐ The database row is the one that has caused real outages** (Day 128): if a dependency check is in
the *liveness* probe, a database blip becomes every pod crash-looping — removing the capacity that
could have served cached or degraded responses. **Verify it rather than assume it.**

## ⭐ Resource limits, sized from measurement

```
⭐ requests = the p50 you MEASURED     ← not a guess
⭐ limits   = the p99 plus headroom
⭐ ⭐ Memory limit ≥ what MaxRAMPercentage implies, plus non-heap  (Day 282)
```

**⭐ Two failure modes, and they fail differently:**

| Limit | ⭐ Failure |
|---|---|
| ⭐ **Memory too low** | ⭐ **OOM-killed** — abrupt, and the pod restarts |
| ⭐ **CPU too low** | ⭐ **throttled** — ⭐ latency degrades and nothing is "wrong" |

**⭐ CPU throttling is the more insidious one**: no error, no restart, just p99 latency climbing while
CPU usage looks fine because it is being capped. **Watch `container_cpu_cfs_throttled_seconds` if
your platform exposes it.**

**⭐ And a JVM needs CPU headroom at startup** for JIT compilation — a tight CPU limit makes startup
slow enough to fail the startup probe, which looks like a deployment problem.

# Part 4 — ⭐ Backups, network, and cost

## ⭐⭐ Backups, and the only test that counts

```
⭐ Automated daily backups + PITR                       (Day 201)
⭐⭐ RESTORE ONE. TODAY. INTO A SCRATCH DATABASE.
⭐⭐ TIME IT. That number IS your RTO.
```

> **⭐⭐ Day 185's item 39, and the one item on that checklist whose failure is unrecoverable.** Every
> organisation has backups; a meaningful proportion discover during an incident that the restore
> takes eleven hours, or that the one table that mattered was excluded.

**⭐ Verify three things**: it restores, the row counts match, and **the elapsed time is within your
stated RTO.** A restore that works but exceeds your RTO is a failed test.

**⭐ Also back up what is not in the database**: object storage (versioning and lifecycle rules), and
the infrastructure code itself.

## ⭐ Network and TLS

```
⭐ TLS terminated at the load balancer, ⭐ HTTP → HTTPS redirect, ⭐ HSTS
⭐ The database in a private subnet — ⭐ NOT publicly reachable
⭐ Security groups: only what is needed
⭐⭐ forward-headers-strategy set   ← ⭐⭐ or Secure cookies drop and IP rate limiting sees ONE IP
```

**⭐ The last line is Day 155's, and it breaks two things silently**: `Secure` cookies are never
applied because the application believes it is on HTTP, and Day 208's per-IP rate limit treats the
entire internet as one client. **Test it behind the real proxy.**

## ⭐ Cost, which is an engineering constraint

```
⭐ Know your monthly cost. ⭐ Know the largest line item. ⭐ Set a budget alert.
```

**⭐ "It costs £40 a month, mostly the managed database, and I set a budget alert at £60" is a
genuinely good answer** — it demonstrates that you treat cost as a constraint rather than someone
else's problem. **Most candidates have never looked.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Over-architecting for no stated target | signals you cannot size a solution |
| ⭐ No availability target | ⭐ every architecture decision is unjustifiable |
| Self-managed Kubernetes for one service | enormous operational cost |
| Self-hosting the database | you now owe backups, PITR, patching and failover |
| ⭐ Click-configured infrastructure | ⭐ unreproducible; "how would you rebuild this?" has no answer |
| ⭐ Local Terraform state | ⭐ a single point of failure you cannot recover |
| ⭐ Unencrypted state bucket | ⭐ secrets in plaintext |
| ⭐ **Never testing a component failure** | ⭐ the behaviour is a hope |
| ⭐ Dependency checks in liveness | ⭐ a database blip crash-loops the fleet |
| ⭐ Memory limit below the JVM's implied need | OOM-killed |
| ⭐ CPU limit too tight | ⭐ silent throttling; slow startup fails the probe |
| ⭐ **Untested backups** | ⭐ discovered during the incident |
| Database publicly reachable | one credential leak from total compromise |
| ⭐ No forwarded-headers config | `Secure` cookies dropped; rate limiting broken |
| Not knowing the cost | a constraint you are ignoring |

## ⭐ Self-review

- [ ] ⭐ The platform choice is **justified by Day 249's availability target**
- [ ] ⭐ Everything is **in code**; ⭐ **remote encrypted state**
- [ ] ⭐ **Staging destroyed and rebuilt from code** — successfully
- [ ] Secrets in a manager, injected at runtime, rotatable
- [ ] ⭐ **The failure matrix is complete**, ⭐ with at least four rows **actually tested**
- [ ] ⭐ Database stopped → ⭐ **readiness down, liveness up, no crash loop**
- [ ] ⭐ Redis stopped → degraded, not broken
- [ ] ⭐ Resource limits **derived from measurement**; ⭐ CPU throttling checked
- [ ] ⭐ **A restore performed and TIMED**; ⭐ the number recorded as RTO
- [ ] TLS, HSTS, private database subnet, ⭐ **forwarded headers verified behind the real proxy**
- [ ] ⭐ **Monthly cost known**; a budget alert set

## 🎤 Defence questions

1. **⭐ What is your availability target, and what did it rule out?**
2. **⭐ Why this platform rather than Kubernetes — or rather than a VM?**
3. **⭐ How would you recreate this environment from nothing?**
4. **⭐ What happens when the database goes away?** (⭐ you have tried it)
5. **⭐ What happens when Redis goes away?**
6. **⭐ How long does a restore take?** (⭐ measured, not estimated)
7. **⭐ How did you size your memory and CPU limits?**
8. **⭐ What does it cost, and what is the biggest line item?**

## ✅ Done when

- ⭐ Staging has been rebuilt from code
- ⭐ **Four failure scenarios tested under load**
- ⭐ **A restore has been performed and timed**
- ⭐ The cost is known and alerted on
