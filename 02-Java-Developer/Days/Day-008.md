# Part 1 — L-008 · What a connection actually is

## The answer that unlocks everything

**A TCP connection is not a physical thing. It is shared state held in memory at both endpoints.**

There is no circuit. No reserved path. No router anywhere knows your connection exists (Day 006 —
routers are stateless with respect to connections). What exists is:

```
   YOUR MACHINE                             SERVER
   ┌────────────────────────┐               ┌────────────────────────┐
   │ Socket / TCB           │               │ Socket / TCB           │
   │  state: ESTABLISHED    │               │  state: ESTABLISHED    │
   │  local:  1.2.3.4:51234 │               │  local:  5.6.7.8:443   │
   │  remote: 5.6.7.8:443   │◀── nothing ──▶│  remote: 1.2.3.4:51234 │
   │  send seq:  84721      │    in between │  send seq:  22910      │
   │  recv seq:  22910      │               │  recv seq:  84721      │
   │  send buffer, recv buf │               │  send buffer, recv buf │
   │  rwnd, cwnd, RTT est   │               │  rwnd, cwnd, RTT est   │
   └────────────────────────┘               └────────────────────────┘
```

That structure has a name — the **Transmission Control Block (TCB)**. A "connection" is two TCBs
that agree with each other.

**Three consequences that people find surprising, and interviewers like:**

1. **You can unplug the cable and the connection survives.** Both TCBs still exist. If you plug back
   in before timeouts fire, data resumes. The connection was never in the cable.
2. **Connections cost memory, not bandwidth.** Each open connection is buffers and bookkeeping at
   both ends. This is why "max connections" is a real limit on a server (and why `ulimit -n` and
   Postgres's `max_connections` exist — Day 197).
3. **A "half-open" connection is possible and dangerous.** If the server crashes and reboots, its
   TCB is gone but yours still says ESTABLISHED. You'll happily send data into a void until a
   timeout or RST tells you otherwise. This is exactly why **connection pools need validation
   queries** and why load balancers have health checks.

> This is the concept that makes Day 197 (connection pooling) and Day 069 (thread pools) make sense.
> Both are pools of expensive *state*, not of anything physical.

## The state machine

TCP is formally a state machine. You don't need to memorise all eleven states, but you must know
these six and be able to explain what causes each transition.

```
                        CLOSED
                          │
            passive open  │  active open (connect)
        ┌─────────────────┴─────────────────┐
        ▼                                   ▼
     LISTEN                            SYN_SENT
        │  recv SYN                         │  recv SYN-ACK
        │  send SYN-ACK                     │  send ACK
        ▼                                   │
    SYN_RCVD ──── recv ACK ────────────▶ ESTABLISHED ◀──┘
                                             │
                    ┌────────────────────────┴──────────────┐
      close() first │                                       │ recv FIN first
                    ▼                                       ▼
              FIN_WAIT_1                                CLOSE_WAIT
                    │                                       │  app calls close()
                    ▼                                       ▼
              FIN_WAIT_2                                 LAST_ACK
                    │  recv FIN                             │
                    ▼                                       ▼
               TIME_WAIT ──── 2×MSL ────▶ CLOSED         CLOSED
```

### The two states you'll actually debug

**`TIME_WAIT`** — the side that closed *first* holds here for ~60 s (2 × maximum segment lifetime).

Why: a delayed duplicate from this connection could otherwise arrive during a *new* connection on
the same 4-tuple and be accepted as valid data. Also ensures the final ACK can be retransmitted if
lost.

Practical effect, and you will hit this:

```bash
# Stop your Spring Boot app, restart immediately:
# → Address already in use
ss -tan | grep TIME-WAIT | wc -l     # they're all sitting there
```

A busy server that closes many short connections accumulates thousands of `TIME_WAIT` sockets,
consuming ephemeral ports. Fixes: `SO_REUSEADDR`, keep-alive so you close fewer connections, or make
the *client* close first so the burden sits there.

**`CLOSE_WAIT`** — you received a FIN but **your application hasn't called `close()`**.

`CLOSE_WAIT` piling up is never the network's fault. **It is always a bug in your code** — a socket
you forgot to close. Remember Day 004, where you commented out `client.close()` and watched
descriptors leak? That leak shows up here.

```bash
ss -tan | grep CLOSE-WAIT      # if this number grows, find the leak
```

**Interview-grade line:** *"Growing `CLOSE_WAIT` means the application isn't closing sockets;
growing `TIME_WAIT` means it's closing a lot of them, which is normal but can exhaust ephemeral
ports."* Being able to say that separates people who've operated a service from people who haven't.

## TCP vs UDP — the decision

| | TCP | UDP |
|---|---|---|
| Connection | Yes — handshake first | No |
| Reliable | Yes | No |
| Ordered | Yes | No |
| Flow/congestion control | Yes | No |
| Header | 20 bytes | 8 bytes |
| Speed | Slower to start | Immediate |
| Use for | HTTP, SSH, databases, anything correctness-critical | DNS, video/voice, gaming, metrics |

**The reasoning that matters:** use UDP when *late data is worthless*. In a voice call, a
retransmitted packet from 300 ms ago is useless — you've already moved past that audio. Better to
drop it and continue. TCP's insistence on delivering everything in order actively hurts there,
because one lost packet stalls everything behind it (**head-of-line blocking** — the exact problem
HTTP/3 solves on Day 011).

## RST — the third way to end

Besides a graceful FIN, either side can send **RST** (reset) to tear down immediately.

Common causes:
- Connecting to a port with nothing listening → immediate RST (this is why "connection refused" is
  fast, while a firewalled port just hangs — it drops silently instead)
- The application crashed with data still in flight
- A firewall or load balancer killing an idle connection

**"Connection reset by peer"** is one of the most common production errors you'll ever read. Now you
know exactly what it means: the other end sent an RST rather than a FIN.

## Type this yourself

```java
import java.net.*;
import java.io.*;

public class ConnectionStates {
    public static void main(String[] args) throws Exception {
        ServerSocket server = new ServerSocket(9090);
        System.out.println("LISTEN on 9090 — check with: netstat -an | findstr 9090");

        new Thread(() -> {
            try {
                Socket s = server.accept();
                System.out.println("ESTABLISHED — check netstat again");
                Thread.sleep(30_000);              // deliberately do NOT close
                System.out.println("Server finally closing");
                s.close();
            } catch (Exception e) { e.printStackTrace(); }
        }).start();

        Thread.sleep(1000);
        Socket client = new Socket("localhost", 9090);
        Thread.sleep(2000);

        client.close();                            // client closes FIRST
        System.out.println("Client closed. Server has NOT. Check for CLOSE_WAIT now:");
        System.out.println("  netstat -an | findstr 9090");
        Thread.sleep(60_000);
    }
}
```

Run it and check `netstat` at each printed prompt. **You will watch a socket sit in `CLOSE_WAIT`
because the server hasn't called `close()`** — the exact bug pattern, reproduced deliberately.

Then:

```bash
# Prove RST is instant
telnet localhost 9999          # nothing listening → immediate "connection refused"
```

## Interview questions

**Q: What is a TCP connection?**
> Shared state at the two endpoints — a Transmission Control Block at each end holding the 4-tuple,
> sequence numbers, buffers and timers. Nothing exists in the network; routers hold no per-connection
> state. A connection is two endpoints agreeing they're connected.

**Q: What is `TIME_WAIT` and why does it exist?**
> The state of the side that closed first, held for twice the maximum segment lifetime. It ensures
> delayed duplicates from the old connection can't be accepted by a new connection on the same
> 4-tuple, and allows the final ACK to be retransmitted if lost.

**Q: What does a growing number of `CLOSE_WAIT` sockets tell you?**
> That the application received a FIN but never called `close()`. It's a resource leak in the
> application code, not a network problem.

**Q: When would you choose UDP over TCP?**
> When late data has no value and latency matters more than completeness — real-time voice and video,
> gaming, DNS queries, metrics. TCP's in-order delivery causes head-of-line blocking, so one lost
> packet stalls everything behind it, which is worse than simply dropping it.

**Q: What causes "connection reset by peer"?**
> The peer sent an RST rather than closing gracefully — typically the process died, nothing was
> listening on the port, or an intermediary such as a firewall or load balancer terminated the
> connection.

# Part 2 — C-06 · Congestion control

## The problem

Flow control (Day 007, C-05) stops you overwhelming the **receiver**, and the receiver tells you its
limit explicitly.

Nothing tells you the **network's** limit. Routers have finite buffers; when they overflow they drop
packets. If every sender simply blasted at full speed, everyone's packets would be dropped, everyone
would retransmit, and throughput would collapse to near zero.

That actually happened. **The internet suffered congestion collapse in 1986** — throughput between
Berkeley and LBL fell from 32 kbps to 40 bps, a factor of 1000. Van Jacobson's congestion control
algorithms are the fix, and they're still what runs today.

## The core idea

The sender maintains a **congestion window (`cwnd`)** — its own guess at how much the network can
take — and may send only `min(rwnd, cwnd)`.

**Packet loss is treated as the congestion signal.** There's no other feedback available, so TCP
infers: "a packet was dropped, therefore a buffer overflowed, therefore I'm sending too fast."

## Slow start

Begins conservatively and **doubles every RTT** — exponential, despite the name:

```
   cwnd
    │                    ╱ ssthresh reached → switch to linear
  16│                  ╱
    │                ╱
   8│              ╱
    │            ╱
   4│          ╱
    │        ╱
   2│      ╱
   1│    ╱
    └────────────────────────────▶ RTT
     1   2   3   4   5
```

"Slow" refers to the *starting point*, not the growth rate. Ten round trips gets you to 1024
segments.

**This is why the first few hundred milliseconds of a connection are slow**, and therefore why
connection reuse (keep-alive, pooling) matters so much: a fresh connection restarts slow start and
throws away everything the old one learned about the path.

## AIMD — the steady state

Once past a threshold, TCP switches to **Additive Increase, Multiplicative Decrease**:

- **No loss** → `cwnd += 1` per RTT (cautious, linear probing upward)
- **Loss** → `cwnd /= 2` (immediate, aggressive backoff)

```
   cwnd
    │      ╱│      ╱│      ╱│         classic "sawtooth"
    │    ╱  │    ╱  │    ╱  │
    │  ╱    │  ╱    │  ╱    │
    │╱      │╱      │╱      │
    └───────┴───────┴───────┴────▶ time
          loss    loss    loss
```

**Why asymmetric?** Because the cost of being wrong is asymmetric. Sending slightly too slowly wastes
a little bandwidth. Sending too fast contributes to collapse. AIMD is also *provably fair* — flows
sharing a bottleneck converge to an equal share, which is the property that makes the internet work
at all with billions of independent senders and no coordinator.

## The variants worth naming

| Algorithm | Signal | Note |
|---|---|---|
| **Tahoe** (1988) | Loss | On loss, drop `cwnd` to 1 and restart slow start. Brutal. |
| **Reno** | Loss | Adds fast recovery — halve rather than reset. The classic. |
| **CUBIC** | Loss | Linux default. Cubic growth curve, much better on high bandwidth-delay links. |
| **BBR** (Google) | **Bandwidth + RTT** | Doesn't wait for loss. Models the path's actual capacity. |

**BBR is the interesting one.** Loss-based algorithms have a flaw: modern routers have huge buffers,
so a sender fills them *without loss*, which adds enormous queuing delay (**bufferbloat**) — you get
throughput but terrible latency. BBR measures the bottleneck bandwidth and minimum RTT directly and
paces to that, keeping buffers empty.

Mentioning BBR and bufferbloat is a genuine senior signal in a networking or system design
conversation.

## Interview questions

**Q: What is congestion control and how does it differ from flow control?**
> Congestion control protects the network from being overwhelmed and is inferred by the sender from
> packet loss. Flow control protects the receiver and is explicit, advertised in every ACK. The
> sender sends the minimum of the congestion window and the receive window.

**Q: Explain slow start.**
> A connection begins with a small congestion window and doubles it every round trip until it hits a
> threshold or loses a packet. It's exponential growth from a conservative start, so a new connection
> takes several RTTs to reach full speed — which is the main argument for connection reuse.

**Q: What is AIMD and why is the asymmetry deliberate?**
> Additive increase, multiplicative decrease: grow the window by one segment per RTT, halve it on
> loss. The asymmetry reflects asymmetric risk — under-sending wastes bandwidth, over-sending risks
> collapse — and it makes competing flows converge on a fair share of a bottleneck.

**Q: What problem does BBR solve?**
> Loss-based algorithms only back off when a buffer overflows, so with large router buffers they fill
> them and add huge queuing latency — bufferbloat. BBR estimates bottleneck bandwidth and minimum RTT
> and paces to that, achieving high throughput with low latency.
