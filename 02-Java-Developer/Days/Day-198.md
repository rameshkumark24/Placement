# Day 198

**L-198** · JSONB — schemaless columns in a relational database

**Time:** 3 hrs · **Mode:** NEW

> D-16 covered NoSQL and CAP, and asked when a document model fits. **`jsonb` is PostgreSQL's answer
> to a large fraction of that question**: you can have document storage, indexed and queryable,
> inside a database with transactions, constraints and joins.
>
> Today is how it works, how to index it, and — the part that matters most — **the discipline that
> stops `jsonb` becoming the EAV table Day 188 warned you about.**

---

# Part 1 — `json` vs `jsonb`, and why it is not a close call

| | `json` | ⭐ `jsonb` |
|---|---|---|
| Storage | ⭐ the exact text you sent | ⭐ **parsed binary** |
| Whitespace and key order | preserved | ⭐ **not preserved** |
| Duplicate keys | ⭐ kept | ⭐ **last one wins** |
| Insert speed | ⭐ faster (no parsing) | slower |
| ⭐ **Query speed** | ⭐ **re-parsed every access** | ⭐ **fast** |
| ⭐ **Indexable** | ❌ **no** | ⭐ ✅ **GIN** |

**⭐ Use `jsonb`. Always.** The only case for `json` is when you must return a document byte-identical
to what was submitted — a signature payload, a webhook body you verify an HMAC over (Day 129). That
is a genuine but narrow case.

```sql
alter table products add column attributes jsonb not null default '{}'::jsonb;
```

# Part 2 — Querying, and the operator that decides your index

```sql
select attributes -> 'colour'            from products;  -- ⭐ returns jsonb
select attributes ->> 'colour'           from products;  -- ⭐ returns text
select attributes #> '{specs,weight}'    from products;  -- nested, jsonb
select attributes #>> '{specs,weight}'   from products;  -- nested, text

-- ⭐⭐ CONTAINMENT — the operator that GIN indexes
where attributes @> '{"colour":"red"}'                     -- ⭐ indexable
where attributes @> '{"specs":{"weight":500}}'             -- ⭐ nested, indexable

-- existence
where attributes ? 'warranty'                              -- ⭐ has this key
where attributes ?| array['warranty','guarantee']          -- any of these keys
where attributes ?& array['colour','size']                 -- all of these keys

-- ⭐ equality on an extracted value — NOT indexable by a default GIN index
where attributes ->> 'colour' = 'red'                      -- ⚠️ see Part 3
```

**⭐ The distinction that governs everything:**

> **`@>` (containment) uses a GIN index. `->>` (extraction) does not — it is Day 189's "function on
> the column" in a new costume.**

**⭐ So `where attributes @> '{"colour":"red"}'` and `where attributes ->> 'colour' = 'red'` return
the same rows and have completely different plans.** Prefer `@>` wherever it expresses what you mean.

## Numeric and range comparisons

```sql
where (attributes ->> 'weight')::numeric > 500      -- ⭐ containment cannot express ranges
```

**⭐ `@>` is equality-only**, so any range query on a `jsonb` value needs extraction — and therefore
an **expression index** (Part 3). This is the most common reason a `jsonb` query is slow despite a
GIN index existing.

## Building and modifying

```sql
update products set attributes = attributes || '{"discontinued": true}'::jsonb;   -- ⭐ merge
update products set attributes = attributes - 'discontinued';                     -- remove a key
update products set attributes = jsonb_set(attributes, '{specs,weight}', '600');  -- ⭐ set a path

-- ⭐ expand an array into rows — the bridge back to relational
select p.id, elem ->> 'name'
from products p, jsonb_array_elements(p.attributes -> 'tags') elem;
```

**⭐ `jsonb_array_elements` is the function that makes `jsonb` joinable**, and it is how you write a
report over document data without giving up SQL.

# Part 3 — ⭐ Indexing, and choosing between three options

### ⭐ 1. GIN with the default operator class

```sql
create index ix_products_attrs on products using gin (attributes);
```

Supports `@>`, `?`, `?|`, `?&`. **Indexes every key and every value** — flexible, and the largest and
most write-expensive option (Day 190).

### ⭐ 2. `jsonb_path_ops` — smaller and faster, for containment only

```sql
create index ix_products_attrs on products using gin (attributes jsonb_path_ops);
```

**⭐ Typically 2–3× smaller and faster than the default**, because it indexes hashes of whole paths
rather than every key and value separately. **The trade: it supports only `@>`** — no key-existence
operators.

**⭐ If your queries are all containment, `jsonb_path_ops` is the right choice**, and most people
never learn it exists.

### ⭐ 3. An expression B-tree index — for one hot field

```sql
create index ix_products_colour on products ((attributes ->> 'colour'));
create index ix_products_weight on products (((attributes ->> 'weight')::numeric));
```

**⭐ This is the answer for the range-query case and for a single frequently-filtered field.** It is
tiny compared to a GIN index, supports ordering and ranges, and costs almost nothing on writes.

**⭐ The rule: GIN for ad-hoc containment across many keys; an expression index for the two or three
fields you filter on constantly.** Most schemas want both.

### ⭐ 4. The option people forget — a generated column

```sql
alter table products
  add column colour text generated always as (attributes ->> 'colour') stored;
create index on products (colour);
```

**⭐ Day 188's generated column applied to `jsonb`.** You get a real, typed, indexable,
constraint-able column that cannot drift from the document — and existing queries against
`attributes` still work. **This is the cleanest way to promote a field out of the document once it
has proven to be structural**, and it is the migration path from "we put it in JSON" to "it is a
column".

# Part 4 — ⭐⭐ The discipline: when `jsonb` is right, and when it is EAV in disguise

## ⭐ Good uses

| Use | Why |
|---|---|
| ⭐ **Genuinely heterogeneous attributes** | a laptop has RAM, a shirt has a collar size. No sane column set |
| ⭐ **Third-party payloads stored verbatim** | a webhook body, an API response you may need later |
| ⭐ **Sparse, rarely-queried metadata** | flags and settings nobody filters on |
| **Event payloads in an audit or outbox table** | Day 124, Day 165 — the shape varies by event type |
| ⭐ **A schema in genuine flux** | early product work, before the shape is known |

## ⭐ Bad uses — and the four warning signs

| Sign | What it means |
|---|---|
| ⭐ **Every row has the same keys** | ⭐ **it is a table. Use columns** |
| ⭐ **You filter or join on a field constantly** | promote it to a column |
| ⭐ **You need a foreign key on it** | ⭐ `jsonb` cannot have one. That relationship is unprotected |
| **You need `NOT NULL` or a type guarantee** | a check constraint is a poor substitute for a typed column |

**⭐ The costs you accept by putting a field in `jsonb`:**

- **No foreign keys.** A `customer_id` inside a document references nothing enforceable.
- ⭐ **No type safety.** Today `"weight": 500`, tomorrow `"weight": "500g"`, and your cast throws in
  production.
- ⭐ **Poor planner estimates.** Statistics on `jsonb` predicates are weak, which is Day 191's
  pattern 1 — bad estimates give bad plans, and extended statistics do not help here.
- **Larger rows**, since keys are repeated in every row.
- ⭐ **Every reader must know the undocumented shape**, which is the EAV problem exactly.

**⭐ The interview-grade rule:**

> **Structure what you know. Use `jsonb` for what varies. And when a `jsonb` field becomes something
> you filter on every day, promote it to a column — with a generated column if you want both.**

## Validation, since the database will not do it for you

```sql
alter table products add constraint attrs_shape check (
    jsonb_typeof(attributes) = 'object'
    and attributes ? 'category'                                   -- ⭐ required key
    and jsonb_typeof(attributes -> 'weight') in ('number','null') -- ⭐ type of a field
);
```

**⭐ Without a constraint like this, `jsonb` accepts literally anything** — including `"[1,2,3]"` or
`"null"` where you expected an object. Day 187's argument: the database is the last line of defence,
and here it defends nothing unless you tell it to.

## From Java

```java
@JdbcTypeCode(SqlTypes.JSON)                       // ⭐ Hibernate 6 — native, no custom type needed
@Column(columnDefinition = "jsonb")
private ProductAttributes attributes;              // ⭐ a real class, not Map<String,Object>
```

**⭐ Map it to a typed class, not a `Map<String,Object>`.** The map version gives up every remaining
guarantee — you get `Object` values, casts at every call site, and no compile-time check that a field
exists. A record with the fields you expect restores type safety at the boundary, and Day 150's
Jackson configuration applies unchanged.

⚠️ **`jsonb` columns and Hibernate dirty checking (Day 162):** a mutable `jsonb` field modified
in place may not be detected as dirty, or may be flagged dirty on every flush depending on the type's
`equals`. **Prefer immutable value objects and replace the whole field.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Using `json` instead of `jsonb` | not indexable; re-parsed on every access |
| ⭐ `->>` where `@>` would do | the GIN index is not used |
| Expecting `@>` to handle ranges | it is equality-only; use an expression index |
| Default GIN when `jsonb_path_ops` would do | 2–3× larger and slower |
| GIN on a write-heavy column | Day 190 — severe write amplification |
| ⭐ Same keys in every row | it is a table; use columns |
| ⭐ Expecting foreign keys inside `jsonb` | the relationship is unenforced |
| No shape constraint | the column accepts anything, including a bare array |
| Assuming `"500"` and `500` are interchangeable | a cast throws in production |
| ⭐ Mapping to `Map<String,Object>` | gives up the last of the type safety |
| Mutating a `jsonb` field in place | dirty checking may miss it (Day 162) |
| Ignoring weak planner estimates | Day 191 pattern 1, with no extended-statistics fix |

## Interview questions

**Q: `json` or `jsonb`?**
`jsonb`, effectively always. It is stored parsed, so queries are fast and it can be indexed with GIN;
`json` stores the raw text and is re-parsed on every access and cannot be indexed. The only reason
for `json` is needing the document back byte-identical — a payload you verify a signature over.

**Q: How do you index a `jsonb` column?**
It depends on the queries. A GIN index for ad-hoc containment across many keys, and `jsonb_path_ops`
rather than the default if all my queries are containment, since it is two to three times smaller. An
expression B-tree index for the two or three fields I filter on constantly, which also handles ranges
— containment cannot. And a generated column when a field has clearly become structural.

**Q: When is `jsonb` the wrong choice?**
When every row has the same keys — that is a table. When I filter or join on a field constantly, it
should be a column. And whenever I need a foreign key or a type guarantee, because `jsonb` gives me
neither. The warning sign is that reading the code requires knowing an undocumented shape, which is
the EAV problem with better syntax.

**Q: Why is `attributes ->> 'colour' = 'red'` slow despite a GIN index?**
Because extraction is a function on the column, so the containment index does not apply — it is the
same class of problem as `lower(email)`. Either write it as `@> '{"colour":"red"}'`, or build an
expression index on the extraction.

## Mini task

**500,000 products with varied attributes.**

1. Store the same data in `json` and `jsonb`. Compare storage size and query time. Try to index the
   `json` column.
2. Write the same filter with `@>` and with `->>`. **Compare plans with a GIN index present.**
3. Build the default GIN index and a `jsonb_path_ops` one. **Compare sizes.** Test both against a
   containment query and a key-existence query.
4. Write a range query on a numeric attribute. Confirm the GIN index is not used. Add the expression
   index.
5. Time 100k inserts with no index, with GIN, and with an expression index. **Three numbers.**
6. Add a generated column for `colour`, index it, and compare against the GIN containment query.
7. Insert `"weight": "500g"` where the rest are numbers. **Watch the cast throw.** Add the shape
   constraint.
8. Insert a bare array into the column. Confirm it is accepted without the constraint.
9. Use `jsonb_array_elements` to write a report joining document tags to a real table.
10. Map it in Hibernate with `@JdbcTypeCode(SqlTypes.JSON)` to a record. Then to
    `Map<String,Object>`. **Compare the call sites.**

## 🎙️ Articulation drill

Two minutes: **"When would you use `jsonb`?"**

Frame it as a boundary, not a feature: structure what you know, and use `jsonb` for what genuinely
varies — heterogeneous product attributes, third-party payloads, event bodies. Then be explicit about
what you gave up: no foreign keys, no type guarantees, and weak planner estimates. Name the warning
sign that it has gone wrong — every row having the same keys — and the exit path, which is promoting
the field to a generated or real column once it proves structural. Close on indexing, because that is
where the depth shows: `@>` uses GIN, `->>` does not, and ranges need an expression index.
