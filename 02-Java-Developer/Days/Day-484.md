# Day 484

**L-484** · System design round 4 — a payment system

**Time:** 3 hrs (45 min round + 2 hrs review) · **Mode:** DRILL · **⭐ SD round 4 of 5**

> **⭐⭐ This is the round where availability is not the goal. A payment system that is briefly
> unavailable is an inconvenience; a payment system that double-charges is a refund queue, a chargeback,
> and a regulator — so every trade in this design goes the other way from the previous three.**
>
> Today: idempotency as the central requirement rather than a detail, **the ledger at system scale**,
> reconciliation as a first-class component, and the webhook that arrives before your own database
> commits.

# Part 1 — ⭐ Requirements and the inversion (0–10)

| ⭐ Functional | ⭐⭐ Non-functional — note how different these are |
|---|---|
| ⭐ initiate a payment | ⭐⭐ **correctness over availability** — refuse rather than guess |
| ⭐ handle provider callbacks | ⭐⭐ **exactly-once *effects*** (Day 407) |
| ⭐ refunds, partial refunds | ⭐⭐ **auditable — every state change has a reason and a trail** |
| ⭐ payouts to merchants | ⭐ p99 under a few seconds is fine; **the user expects a wait here** |
| ⭐ Out of scope: fraud scoring, PCI card storage (use a vault/token), FX | ⭐⭐ **reconciliation is IN scope — it is the design** |

```
⭐   10M payments/day ⇒ ⭐ ~120/sec, ⭐ peak ~1,000/sec ⇒ ⭐⭐ THROUGHPUT IS NOT THE PROBLEM.
⭐ ⇒ ⭐⭐ WHAT THE NUMBERS DECIDED: ⭐⭐ this is not a scale problem, it is a CORRECTNESS problem.
⭐   ⭐⭐ Say that out loud at minute 8 — ⭐ it reframes the entire round, correctly.
```

> **⭐ Recognising that estimation *rules out* a scaling conversation is as valuable as estimation that

# Part 2 — ⭐⭐ Idempotency, as the central design

```
⭐⭐ THE CLIENT SUPPLIES AN IDEMPOTENCY KEY ON EVERY PAYMENT INITIATION.
⭐   ⇒ ⭐ INSERT it with a UNIQUE constraint before doing anything
⭐   ⇒ ⭐⭐ conflict ⇒ the request is a RETRY ⇒ ⭐⭐ RETURN THE STORED ORIGINAL RESPONSE
⭐   ⇒ ⭐⭐ storing "seen" without storing the RESPONSE is only half the answer (Day 480)
⭐
⭐ ⭐⭐ AND THE HARD CASE: the retry arrives while the FIRST request is still in flight.
⭐   ⇒ ⭐⭐ the row exists but has no response yet
⭐   ⇒ ⭐⭐ return 409 with "in progress", ⭐ NOT a new payment and NOT a 500.
⭐   ⇒ ⭐ The client polls. ⭐⭐ Ambiguity is the enemy; a clear "wait" is a good answer.
```

| ⭐ Idempotency scope questions the interviewer will ask | |
|---|---|
| ⭐⭐ **How long do you keep keys?** | ⭐⭐ at least as long as clients retry — **24 hours minimum, 7 days is safer** |
| ⭐ Same key, different body? | ⭐⭐ **reject with a conflict** — it is a client bug, and silently accepting it is worse |
| ⭐ Who generates the key? | ⭐⭐ **the client, per intent** — a server-generated id cannot deduplicate a lost response |

## ⭐⭐ The payment state machine

```
⭐   INITIATED → ⭐ AUTHORIZED → ⭐ CAPTURED → ⭐ SETTLED
⭐        ↘ FAILED        ↘ VOIDED      ↘ REFUNDED / PARTIALLY_REFUNDED
⭐        ↘ ⭐⭐ PENDING_UNKNOWN  ⇒ ⭐⭐ THE STATE PEOPLE OMIT, AND IT IS THE IMPORTANT ONE
```

| ⭐⭐ Why `PENDING_UNKNOWN` matters | |
|---|---|
| ⭐⭐ **A provider call times out** | ⭐⭐ the charge may or may not have happened — **you genuinely do not know** |
| ⭐ Wrong answers | ⭐⭐ marking it failed (the customer was charged) or succeeded (they were not) — **both are incidents** |
| ⭐⭐ **Right answer** | ⭐⭐ record the ambiguity explicitly, **then resolve it by querying the provider** with your reference |
| ⭐ This is Day 398's case 3 | ⭐⭐ **the state machine is where "did it happen?" gets an honest home** |

⚠️ **Every state transition is append-only with a reason, and there is no path that skips states.** A
payment that goes from `INITIATED` straight to `REFUNDED` because someone wrote an update by hand is how
reconciliation breaks — **the state machine must be enforced in code, not by convention.**

# Part 3 — ⭐⭐ The ledger, webhooks, and reconciliation (25–38)

```
⭐⭐ THE LEDGER (Day 480, at system scale): balances are sums of immutable double-entry rows.
⭐   a capture writes: ⭐ (txn, customer_receivable, −100), (txn, merchant_payable, +97),
⭐                     ⭐ (txn, platform_revenue, +3)
⭐   ⇒ ⭐⭐ sums to zero. ⭐⭐ The fee is not a subtraction — it is an ENTRY.
⭐   ⇒ ⭐⭐ INVARIANT: SELECT txn_id FROM entries GROUP BY txn_id HAVING SUM(amount) <> 0;
⭐     ⭐⭐ Run it continuously. ⭐ Any row is a bug, and you want to find it before the auditor does.
```

## ⭐⭐ The webhook race that catches everyone

```
⭐⭐ You call the provider. ⭐ They process it. ⭐⭐ Their WEBHOOK arrives at your server
⭐   ⭐⭐ BEFORE your own HTTP response has returned and your transaction has committed.
⭐   ⇒ ⭐⭐ The webhook handler looks up the payment and DOES NOT FIND IT.
⭐ ⇒ ⭐⭐ WRONG: ignore it, or 404 it. ⭐ The provider retries a few times and then gives up,
⭐   and your payment is stuck in PENDING forever.
⭐ ⇒ ⭐⭐ RIGHT: ⭐⭐ persist the webhook as a RAW EVENT keyed by provider reference, ALWAYS ack it,
⭐   and process it asynchronously — ⭐⭐ so it can be applied when the payment appears.
⭐   ⇒ ⭐ And webhooks are at-least-once and out of order, so processing is idempotent and
⭐     ⭐⭐ state transitions are guarded — a late AUTHORIZED must not overwrite CAPTURED.
```

| ⭐ Webhook rules | |
|---|---|
| ⭐⭐ **Verify the signature** | ⭐⭐ an unauthenticated webhook endpoint is a way to mark payments as paid |
| ⭐⭐ **Ack fast, process async** | ⭐⭐ a slow handler causes provider retries, which cause duplicates |
| ⭐ Store the raw payload | ⭐ you will need it during a dispute |
| ⭐ Guard transitions by state | ⭐⭐ out-of-order events are normal, not exceptional |

## ⭐⭐ Reconciliation is a component, not a script

| | |
|---|---|
| ⭐⭐ **Daily: the provider's settlement file vs your ledger** | ⭐⭐ **three buckets: matched, in-yours-only, in-theirs-only** |
| ⭐ In-theirs-only | ⭐⭐ **money moved and you did not record it** — the worst bucket |
| ⭐ In-yours-only | ⭐ you recorded something that did not happen, or it is timing |
| ⭐⭐ **A break queue with an owner** | ⭐⭐ **exceptions go to humans, with an SLA** — this is not optional in payments |
| ⭐ Metric | ⭐⭐ **unreconciled value and age**, alarmed — the health metric of the whole system |

> **⭐⭐ Naming reconciliation unprompted is the single strongest move available in this round.** Most
> candidates design the happy path and stop. **Saying "no distributed payment system is correct by
> construction — you assume drift and detect it daily" is what someone who has worked on money says.**

# 🚪 Failure and trade-offs (38–43)

| ⭐ Question | ⭐ Answer |
|---|---|
| ⭐⭐ **The provider is down** | ⭐⭐ **queue and retry with backoff**; do **not** fail the customer immediately — and **do not silently route to a second provider mid-flight**, because you cannot tell whether the first one charged |
| ⭐ Your database is down at capture time | ⭐⭐ **refuse to call the provider** — never take money you cannot record |
| ⭐⭐ **A retried refund** | ⭐⭐ idempotency key on the refund too; **double refunds are a real incident** (Day 408) |
| ⭐ Payouts to merchants | ⭐⭐ a batch process, **idempotent per payout period**, with its own ledger entries |
| ⭐ Ordering of events | ⭐⭐ guarded transitions; **out-of-order is the normal case** |
| ⭐ Multi-region | ⭐⭐ **usually single-region and honest about it** — cross-region consistency for money is not worth the complexity at this scale |

⚠️ **"Refuse to call the provider if you cannot record the result" is a rule worth stating explicitly.**
Availability instincts from the other rounds say degrade and continue; **here, taking money you cannot
record creates a liability you will discover in reconciliation weeks later.** The whole round is that
inversion.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Designing for scale in a 1,000 TPS system** | ⭐⭐ misreads the problem entirely |
| ⭐⭐ **Idempotency mentioned but not designed** | ⭐⭐ it is the central requirement here |
| ⭐ Storing "seen" without the response | ⭐⭐ the retry cannot tell whether it worked |
| ⭐ Server-generated idempotency keys | ⭐ cannot deduplicate a lost response |
| ⭐ Accepting the same key with a different body | ⭐⭐ silently wrong; reject it |
| ⭐⭐ **No `PENDING_UNKNOWN` state** | ⭐⭐ a timeout forces you to guess, and both guesses are incidents |
| ⭐ State transitions by direct update | ⭐⭐ reconciliation breaks and nobody knows why |
| ⭐ Fees as subtraction rather than a ledger entry | ⭐ the invariant no longer holds |
| ⭐⭐ **404-ing an early webhook** | ⭐⭐ the payment is stuck in pending forever |
| ⭐ Slow webhook handlers | ⭐⭐ provider retries become duplicates |
| ⭐ Unsigned webhook endpoints | ⭐⭐ anyone can mark payments as paid |
| ⭐⭐ **No reconciliation** | ⭐⭐ drift is assumed in this domain, not hypothetical |
| ⭐ Failing over providers mid-transaction | ⭐⭐ you cannot tell whether the first charged |
| Calling the provider when you cannot record it | a liability discovered weeks later |

## Interview questions

**Q: What does estimation tell you here?**
That throughput is not the problem. Ten million payments a day is about a hundred and twenty a second and
maybe a thousand at peak, which any single well-configured database handles. So the interesting
constraints are not scaling ones, and saying that around minute eight reframes the round correctly.
Recognising that estimation has ruled a conversation *out* is as useful as having it force one in — a
candidate who spends fifteen minutes sharding a thousand-TPS system has misread what is hard here.

**Q: How does idempotency work?**
The client supplies a key per payment intent, and I insert it with a unique constraint before doing
anything else. A conflict means this is a retry, and I return the stored original response — storing that
the key was seen without storing the response is only half the answer, because the retrying client
otherwise still does not know whether the payment happened. The hard case is a retry arriving while the
first request is still in flight: the row exists but has no response yet, and the right answer is a
conflict saying "in progress" so the client polls, rather than creating a second payment or returning an
error. In payments, ambiguity is the enemy and a clear "wait" is a good answer.

**Q: The call to the provider times out. What state is the payment in?**
Genuinely unknown, and the design has to say so. Marking it failed means the customer may have been
charged for nothing; marking it succeeded means you may have shipped goods for free. Both are incidents.
So there is an explicit `PENDING_UNKNOWN` state that records the ambiguity, and a resolver that queries
the provider with your reference to find out what actually happened. That state is the one candidates
omit, and it is where "did it happen?" gets an honest home rather than a guess.

**Q: The provider's webhook arrives before your own transaction commits. What happens?**
The handler looks up the payment and does not find it — and the wrong response is a 404, because the
provider retries a few times and then gives up, leaving the payment stuck in pending forever. The right
answer is to persist the webhook as a raw event keyed by the provider reference, acknowledge it
immediately, and process it asynchronously so it can be applied once the payment appears. Webhooks are
also at-least-once and can arrive out of order, so processing is idempotent and transitions are guarded —
a late authorised event must never overwrite a captured state. And the endpoint verifies the signature,
because an unauthenticated webhook is a way for anyone to mark payments as paid.

**Q: How do you know the system is correct?**
By assuming it is not and detecting drift. The ledger gives a continuous invariant — group entries by
transaction and find any group that does not sum to zero — and beyond that there is daily reconciliation
against the provider's settlement file, producing three buckets: matched, in ours only, and in theirs
only. That last bucket is the worst, because it means money moved and we did not record it. Breaks go to
a queue with an owner and an SLA, and the health metric of the whole system is unreconciled value and its
age. No distributed payment system is correct by construction; you build the detector and you staff it.
