# Day 292 ⭐🏗️

**P-292** · The RAG pipeline I — ingestion, chunking, and the decisions that decide quality

**Time:** 3+ hrs · **Mode:** BUILD

> **⭐ Retrieval-augmented generation is a search problem wearing an AI hat.** The model is the part
> everyone talks about and the part you have least control over; **the retrieval is where quality is
> actually won or lost**, and it is ordinary engineering.
>
> **⭐ The single most useful reframe for this block: if the right chunk is not in the retrieved set,
> no model can answer correctly.** Everything on this day is about making sure it is.

---

# Part 1 — ⭐ The pipeline, and where the failures live

```
⭐ INGEST → ⭐ CHUNK → ⭐ EMBED → ⭐ STORE → ⭐ RETRIEVE → ⭐ RANK → ⭐ ASSEMBLE → ⭐ GENERATE
```

**⭐ Where quality is lost, in order of how often it is the cause:**

| Stage | ⭐ Failure |
|---|---|
| ⭐ **Chunk** | ⭐⭐ **the answer is split across two chunks, so neither contains it** |
| ⭐ **Retrieve** | ⭐ the right chunk exists and does not rank in the top k |
| ⭐ **Assemble** | ⭐ the right chunk is retrieved and truncated out of the context |
| Embed | a model mismatch between index and query time |
| Generate | ⭐ the model ignores the context, or invents |

**⭐ Two-thirds of RAG quality problems are chunking and retrieval**, which are search engineering —
not prompt engineering. **Day 199's full-text work applies more directly than anything model-shaped.**

## ⭐ Before rebuilding: measure what you have

**⭐ Day 288's golden query set is the baseline. Turn it into a measurement.**

```markdown
# docs/RAG-BASELINE.md
| Query | ⭐ Expected source | ⭐ Retrieved in top-5? | ⭐ Answer correct? |
```

**⭐ Two separate numbers, and separating them is the whole diagnostic:**

| Metric | ⭐ What it isolates |
|---|---|
| ⭐ **Retrieval recall@k** | ⭐ **is the right chunk being found?** |
| ⭐ **Answer correctness** | ⭐ given the right chunk, is the answer right? |

> **⭐⭐ If recall@5 is 60%, no amount of prompt engineering fixes 40% of your queries.** People spend
> weeks tuning prompts against a retrieval problem, because they never measured the two separately.

**⭐ Fifty queries with known correct sources is enough to be useful**, and building that set is the
highest-value hour of this day.

# Part 2 — ⭐⭐ Chunking — the decision that matters most

**⭐ The tension is simple and unavoidable:**

```
⭐ Chunks too SMALL → ⭐ context is lost; the answer spans several chunks
⭐ Chunks too LARGE → ⭐ the embedding is diluted; irrelevant text crowds the context
```

| Strategy | ⭐ When |
|---|---|
| Fixed size (e.g. 512 tokens) | ⭐ simple, and ignores structure — **a poor default** |
| ⭐ **Structural** (heading, section, paragraph) | ⭐⭐ **usually best — respects the document** |
| ⭐ **Sentence-window** | embed a sentence, ⭐ **retrieve its neighbours for context** |
| Recursive character splitting | pragmatic middle ground |
| ⭐ **Semantic** (split on topic shift) | expensive; occasionally worth it |

**⭐ Structural chunking is the right default because documents already carry their own boundaries.**
A section heading is a human's judgement about where one idea ends — **use it rather than counting
tokens through it.**

## ⭐ The five rules

```
⭐ 1. ⭐ OVERLAP — 10–20%, so an answer at a boundary appears in both chunks
⭐ 2. ⭐ NEVER split mid-sentence, and preferably not mid-paragraph
⭐ 3. ⭐ CARRY THE HEADING into the chunk — ⭐ "Refund Policy > Exceptions" changes its meaning
⭐ 4. ⭐ KEEP TABLES AND LISTS WHOLE — ⭐ half a table is worse than no table
⭐ 5. ⭐ STORE THE PROVENANCE — document, section, page, ⭐ version
```

**⭐ Rule 3 is the cheapest large improvement available.** A chunk reading "this does not apply to
digital goods" is nearly meaningless embedded alone; prefixed with its heading path it is precise —
**and both the embedding and the model benefit.**

**⭐ Rule 5 is not optional for NexOps.** A risk system that cites a source must be able to show
*which version* of which document — **and Day 289's event-versus-entity distinction applies: an
answer given last month cited the document as it was then.**

## ⭐ Metadata is what makes filtering possible

```
⭐ chunk: id, document_id, ⭐ document_version, ⭐ section_path, ⭐ page,
         content, ⭐ token_count, ⭐ tenant_id, ⭐ effective_from/to, embedding
```

**⭐ `tenant_id` is a security control here**, exactly as in Day 259: **a vector search without a
tenant filter returns another tenant's documents**, and it is a particularly bad leak because the
model will then quote them fluently.

**⭐ `effective_from/to` handles the superseded-policy problem**: an old version of a document must
stop being retrievable when it stops being current, **and the assessment that cited it must still be
able to show what it said.**

# Part 3 — ⭐ Embeddings, and the operational realities

## ⭐ The model choice, and the constraint that follows

```
⭐ Dimensions, cost, latency, ⭐ and whether it can run locally
```

> **⭐⭐ The constraint people discover too late: changing the embedding model means re-embedding
> everything.** Index and query embeddings must come from the same model — **so the model choice is a
> migration, and it must be planned like one.**

```
⭐ Store the model NAME AND VERSION with every embedding.
⭐ A model change is an expand/contract migration (Day 166):
⭐   add a second embedding column → backfill → switch queries → wait → drop
```

**⭐ That is the third instance of expand/contract in this project**, and naming the pattern when it
recurs is itself a good answer.

## ⭐ The cost mistake, and it is a large one

```
❌ ⭐ Re-embedding unchanged content on every ingestion run
⭐ Hash the chunk content; ⭐ re-embed ONLY if the hash changed
```

**⭐ Day 288's audit may well have found this.** It is the most common expensive bug in a RAG
pipeline: a nightly re-ingest that re-embeds the entire corpus **costs the same as the initial build,
every night, forever** — and nothing looks wrong.

```
⭐ Batch embedding calls               ← ⭐ far cheaper than one per chunk
⭐ Retry with jitter on rate limits    ← Day 123, Day 154
⭐ ⭐ A COST METRIC per ingestion run   ← ⭐ or you find out from the invoice
```

## ⭐ Where to store the vectors

| Option | ⭐ When |
|---|---|
| ⭐ **`pgvector`** | ⭐⭐ **default — one database, transactional, filters in the same query** |
| A dedicated vector database | very large scale, or specific features |
| In-memory | prototypes only |

**⭐ Day 199's argument transfers almost word for word**: an external index is a dual write you
reconcile forever (Day 124), **while `pgvector` keeps chunks and embeddings in one transaction and
lets you combine a vector search with a tenant filter and a date filter in one query.**

**⭐ And if you do use an external store, feed it from the outbox** (Day 263) — not a dual write, not
a nightly full reindex.

```
⭐ HNSW index for approximate search — ⭐ know that it is APPROXIMATE
⭐ Tune ef_search: ⭐ recall vs latency — and MEASURE the trade, do not guess it
```

# Part 4 — ⭐ Ingestion as a pipeline you can operate

**⭐ Ingestion is a background job, so Days 263–265 apply in full.**

```
⭐ Idempotent — ⭐ re-ingesting the same document produces the same chunks (content hashing)
⭐ Incremental — ⭐ only changed documents
⭐ Resumable — ⭐ a failure at document 4,000 of 5,000 does not restart from zero
⭐ Observable — ⭐ documents/chunks processed, ⭐ failures BY REASON, ⭐ cost
⭐ Bounded — batched, one transaction per batch (Day 264)
```

**⭐ Failures by reason is the useful breakdown**: a corrupt PDF, an unsupported format, an
embedding-API error and a timeout need different responses, **and a single `ingestion_failures_total`
tells you nothing about which.**

## ⭐ Handle the document types honestly

| Type | ⭐ Reality |
|---|---|
| Plain text, Markdown | ⭐ easy — structure is explicit |
| ⭐ **PDF** | ⭐⭐ **genuinely hard** — columns, headers, footers, tables |
| HTML | strip navigation and boilerplate, or you embed the menu |
| ⭐ **Scanned images** | needs OCR; ⭐ **quality is variable and must be measured** |

**⭐ PDF extraction quality is the silent killer of RAG projects**, and it is worth stating: a
two-column PDF extracted naively interleaves the columns, producing text that is grammatically
plausible and semantically nonsense. **The embedding of nonsense is confidently wrong.**

**⭐ Spot-check extraction output by hand** — read fifty extracted chunks. **It is unglamorous and it
finds more quality problems than any amount of retrieval tuning.**

## ⭐ Deletion and the right to be forgotten

```
⭐ Deleting a document must delete its chunks AND its embeddings — ⭐ via the outbox (Day 267)
⭐ ⭐ And anything derived: cached answers, retrieval logs containing the content
```

**⭐ The second line is the one people miss.** If you log retrieved chunks for debugging (and you
should), **those logs contain the content you were asked to delete** — which is a compliance problem
hiding in an observability decision.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Tuning prompts to fix a retrieval problem | ⭐⭐ weeks spent on the wrong stage |
| ⭐ Not measuring recall separately from correctness | you cannot tell which stage is failing |
| ⭐ Fixed-size chunking by default | ignores document structure |
| ⭐ No overlap | ⭐ boundary answers are lost |
| ⭐ Not carrying the heading into the chunk | ⭐ chunks lose their meaning |
| Splitting tables | half a table is worse than none |
| ⭐ No provenance or version | citations cannot be verified |
| ⭐ **No `tenant_id` filter on vector search** | ⭐⭐ **cross-tenant leak, quoted fluently** |
| ⭐ Not storing the embedding model version | a model change becomes unmanageable |
| ⭐ **Re-embedding unchanged content** | ⭐⭐ **the full corpus cost, every run, forever** |
| No cost metric | you learn from the invoice |
| An external vector store, dual-written | Day 124's problem |
| Forgetting HNSW is approximate | unexplained recall gaps |
| ⭐ Not inspecting extracted text | ⭐ confidently embedded nonsense |
| Deleting documents but not derived data | a compliance problem in your logs |

## ⭐ Self-review

- [ ] ⭐ **Recall@k and answer correctness measured SEPARATELY** on the golden set
- [ ] ⭐ Chunking is **structural**, with ⭐ overlap, ⭐ heading paths, ⭐ tables kept whole
- [ ] ⭐ **Provenance stored**: document, version, section, page
- [ ] ⭐ **`tenant_id` on every chunk and in every retrieval query**
- [ ] `effective_from/to` handles superseded documents
- [ ] ⭐ **Embedding model name and version stored**; a model change planned as expand/contract
- [ ] ⭐ **Content-hash caching** — unchanged chunks are not re-embedded
- [ ] ⭐ Batched calls, jittered retries, ⭐ **a cost metric per run**
- [ ] Vectors in `pgvector`, or fed from the outbox if external
- [ ] ⭐ Ingestion is **idempotent, incremental, resumable, observable**
- [ ] ⭐ **Failures broken down by reason**
- [ ] ⭐ **Fifty extracted chunks read by hand**
- [ ] ⭐ Deletion removes chunks, embeddings ⭐ **and derived data including logs**

## 🎤 Defence questions

1. **⭐ If an answer is wrong, how do you tell whether it was retrieval or generation?**
2. **⭐ What is your recall@5?**
3. **⭐ How do you chunk, and why that way?**
4. **⭐ What happens to an answer that spans a chunk boundary?**
5. **⭐ What stops a vector search returning another tenant's documents?**
6. **⭐ What happens if you change the embedding model?**
7. **⭐ How much does an ingestion run cost, and what did you do about it?**
8. **⭐ How good is your PDF extraction — and how do you know?**
9. **⭐ A customer asks you to delete their document. What exactly gets deleted?**

## ✅ Done when

- ⭐ **Recall and correctness are measured separately**, with numbers
- ⭐ Chunking is structural with provenance and heading paths
- ⭐ **Unchanged content is not re-embedded**, with the cost saving measured
- ⭐ Fifty extracted chunks have been read by hand
