# Day 482

**L-482** · System design round 2 — a news feed

**Time:** 3 hrs (45 min round + 2 hrs review) · **Mode:** DRILL · **⭐ SD round 2 of 5**

> **⭐⭐ The whole round turns on one multiplication: a user with 200 followers generates 200 feed writes,
> and a user with 100 million followers generates 100 million. That single asymmetry is why the answer is
> hybrid, and a candidate who reaches it by arithmetic rather than by recall is unmistakable.**
>
> Today: fan-out on write versus on read, **the celebrity problem worked with numbers**, ranking versus
> chronological, and the pagination bug that everyone ships.

---

# Part 1 — ⭐ Requirements and estimation (0–10)

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| ⭐ post content | ⭐⭐ **feed load p99 < 200 ms** — it is the app's first screen |
| ⭐⭐ **view a feed of posts from people you follow** | ⭐⭐ **read-heavy: ~100:1** |
| ⭐ follow / unfollow | ⭐ eventual consistency is acceptable — **a post appearing 5s late is fine** |
| ⭐ Out of scope: comments, DMs, ads, moderation | ⭐ **but a post NOT appearing at all is not** |

```
⭐ 300M daily active users · ⭐ each opens the feed 10× ⇒ ⭐⭐ 3B feed reads/day ≈ ⭐⭐ ~35,000 reads/sec
⭐ 50M posts/day ⇒ ⭐ ~600 writes/sec — ⭐⭐ trivially small, ⭐⭐ which is exactly the trap
⭐ ⭐⭐ average following ≈ 200 ⇒ ⭐⭐ fan-out on write = 600 × 200 = ⭐⭐ 120,000 feed writes/sec
⭐ ⇒ ⭐⭐ WHAT THE NUMBERS DECIDED: ⭐⭐ 600 writes/sec is nothing; ⭐⭐ 120,000 FAN-OUT writes is a system.
⭐   ⭐ The post is cheap. ⭐⭐ THE DISTRIBUTION IS THE PROBLEM.
```

# Part 2 — ⭐⭐ The two models, and why neither wins

| | ⭐ Fan-out on WRITE (push) | ⭐ Fan-out on READ (pull) |
|---|---|---|
| ⭐ On post | ⭐⭐ **write into every follower's feed list** | ⭐ write once |
| ⭐ On read | ⭐⭐ **read one list — very fast** | ⭐⭐ **query N followees and merge — slow** |
| ⭐ Cost | ⭐⭐ write amplification | ⭐⭐ read amplification |
| ⭐⭐ **Good for** | ⭐⭐ **normal users; read-heavy workloads** | ⭐⭐ **celebrities; inactive users** |
| ⭐ Storage | ⭐⭐ one entry per follower per post — **large** | ⭐ minimal |

```
⭐⭐ THE CELEBRITY MULTIPLICATION — say these two numbers side by side:
⭐   a normal user, 200 followers  ⇒ ⭐ 200 feed writes.
⭐   ⭐⭐ one celebrity, 100M followers ⇒ ⭐⭐ 100,000,000 FEED WRITES FOR ONE POST.
⭐   ⇒ ⭐⭐ At any reasonable write rate that takes MINUTES, during which the feed is inconsistent
⭐     — and a handful of such accounts can saturate the entire fan-out pipeline.
⭐ ⇒ ⭐⭐ THEREFORE: HYBRID. ⭐ Push for normal accounts; ⭐⭐ PULL for accounts above a follower threshold.
⭐   ⇒ ⭐ Feed read = ⭐ the precomputed list ⭐⭐ MERGED at read time with the few celebrities you follow.
```

| ⭐ The details that make hybrid real | |
|---|---|
| ⭐⭐ **Where is the threshold?** | ⭐⭐ *"I'd start around 100k followers and tune it — it's a knob, not a constant"* |
| ⭐ How many celebrities does one user follow? | ⭐⭐ **a handful** — so the read-time merge is cheap |
| ⭐ Storage for the precomputed feed | ⭐ cap it at ~500–1,000 entries per user; **older pages fall back to pull** |
| ⭐⭐ **Inactive users** | ⭐⭐ **do not fan out to someone who has not opened the app in 30 days** — a large, cheap saving |

> **⭐ That last row is the one that impresses.** A huge share of fan-out writes goes to dormant accounts.
> **Skipping them, and backfilling lazily when they return, cuts the write volume dramatically with no
> user-visible change** — and it is the kind of optimisation that only comes from thinking about who is
> actually reading.

# Part 3 — ⭐⭐ The deep dive (25–38)

```
⭐ post → ⭐ post service → ⭐⭐ post store (source of truth)
⭐                        ↘ ⭐⭐ fan-out queue → workers → ⭐ feed store (Redis lists per user)
⭐
⭐ read → ⭐ feed service → ⭐⭐ precomputed list ⊕ ⭐⭐ celebrity posts (pulled) → ⭐ merge → ⭐ hydrate
```

| ⭐ Component | ⭐ Note |
|---|---|
| ⭐⭐ **Feed store holds POST IDs, not post content** | ⭐⭐ **hydrate at read time — otherwise an edited or deleted post is wrong in a billion copies** |
| ⭐ Fan-out via a queue | ⭐⭐ asynchronous, retryable, and it absorbs the celebrity burst |
| ⭐ Feed list capped and trimmed | ⭐ `LTRIM` on push |
| ⭐⭐ **Hydration is a batch multi-get** | ⭐ from a post cache — **this is where the N+1 lives** |

⚠️ **Storing post *content* in every follower's feed is the classic wrong answer**, and the reason is
worth stating: **a deletion or edit would require rewriting a hundred million copies.** Storing ids makes
delete a single write and edit free, **at the cost of one batch lookup per feed read** — which is
precisely the right trade.

## ⭐ Ranking, and the honest limit

| | |
|---|---|
| ⭐ Chronological | ⭐ trivial: the list is already ordered |
| ⭐⭐ **Ranked** | ⭐⭐ score = f(recency, affinity, engagement) — **computed at read time over ~500 candidates** |
| ⭐ Why at read time | ⭐⭐ **the score depends on the viewer**, so it cannot be precomputed per post |
| ⭐ The trade | ⭐⭐ ranking makes "why is this post missing?" unanswerable, and **it breaks simple pagination** |

## ⭐⭐ The pagination bug everyone ships

```
⭐⭐ OFFSET-BASED PAGINATION ON A LIVE FEED IS ALWAYS WRONG:
⭐   page 1 = items 0–19. ⭐ Three new posts arrive. ⭐ page 2 = items 20–39
⭐   ⇒ ⭐⭐ items 17, 18, 19 have shifted to 20, 21, 22 ⇒ ⭐⭐ THE USER SEES THEM TWICE.
⭐ ⇒ ⭐⭐ CURSOR PAGINATION: the cursor is the last seen (timestamp, post_id) —
⭐   ⭐ stable under insertion, and it works with ranking if the cursor encodes the score too.
```

# Part 4 — ⭐ Failure and trade-offs (38–43)

| ⭐ Question | ⭐ Answer |
|---|---|
| ⭐⭐ **Fan-out workers fall behind** | ⭐⭐ feeds get stale, **nothing is lost** — the queue is the buffer. **Alarm on message age, not depth** (Day 393) |
| ⭐⭐ **A post is missing from a feed** | ⭐⭐ the fan-out failed ⇒ a DLQ with an alarm; **and a read-time backfill for the last N minutes as a safety net** |
| ⭐ Feed store dies | ⭐⭐ fall back to pull for everyone — **degraded and slow, but the product still works** |
| ⭐ Follower count changes | ⭐ crossing the celebrity threshold flips the strategy — **it must be idempotent both ways** |
| ⭐ Unfollow | ⭐⭐ **do not rewrite the feed** — filter at read time; the list self-cleans as it trims |

> **⭐ The unfollow answer is a small but excellent one.** The naive design deletes that user's posts from
> every follower's feed list, which is another fan-out. **Filtering at read time costs almost nothing and
> the entry ages out naturally** — and recognising that is the same instinct as not storing post content.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Choosing push or pull without the multiplication** | ⭐⭐ the arithmetic *is* the answer |
| ⭐ Reciting "hybrid" without the celebrity numbers | ⭐⭐ recall, not reasoning |
| ⭐ No threshold, or a threshold presented as fixed | ⭐ it is a tunable knob |
| ⭐⭐ **Fanning out to dormant users** | ⭐⭐ a large fraction of writes, for nobody |
| ⭐⭐ **Storing post content in the feed** | ⭐⭐ a delete becomes a hundred million writes |
| ⭐ No cap on feed length | ⭐ unbounded storage per user |
| ⭐ Hydration one post at a time | ⭐⭐ N+1 on the hottest path in the product |
| ⭐ Synchronous fan-out | ⭐⭐ a celebrity post blocks the write path |
| ⭐⭐ **Offset pagination** | ⭐⭐ duplicates on every insertion |
| ⭐ Ranking without mentioning it breaks pagination | ⭐ and makes missing posts unexplainable |
| ⭐ Alarming on queue depth rather than message age | ⭐ depth without a rate says nothing |
| ⭐ Rewriting feeds on unfollow | ⭐⭐ filter at read time instead |
| No answer for "a post never appeared" | that is the one unacceptable failure |

## Interview questions

**Q: Fan-out on write or on read?**
Both, and the arithmetic is what forces it. A normal user with two hundred followers generates two
hundred feed writes per post, which is nothing. A celebrity with a hundred million followers generates a
hundred million writes for one post, which takes minutes and can saturate the entire pipeline. So the
answer is hybrid: push for normal accounts so reads are a single list lookup, pull for accounts above a
follower threshold, and merge the two at read time. The threshold is a tunable knob — I would start
somewhere around a hundred thousand followers and adjust based on what the pipeline actually tolerates.

**Q: What is the biggest optimisation people miss?**
Not fanning out to dormant users. A large fraction of feed writes go to accounts that have not opened the
app in a month, and skipping them with a lazy backfill when they return removes a substantial share of
the write volume with no user-visible change at all. It comes from asking who is actually reading these
feeds rather than treating the follower graph as the workload.

**Q: What do you store in the feed?**
Post ids, never post content. If you denormalise the content into every follower's feed, a deletion or an
edit means rewriting up to a hundred million copies, and that is unworkable — whereas with ids a delete
is one write and an edit is free. The cost is one batch multi-get to hydrate the ids at read time, which
is the right trade. That hydration has to be a batch lookup, because doing it one post at a time is an
N+1 on the single hottest path in the product.

**Q: How do you paginate a feed?**
With a cursor, never an offset. Offsets are wrong on any list that receives insertions at the head: you
read items zero to nineteen, three new posts arrive, and items twenty to thirty-nine now include three
you have already seen. The cursor is the last item you saw — a timestamp and post id pair, or the score
and id if the feed is ranked — which is stable under insertion. It is a small detail that is shipped
wrongly constantly, and users experience it as duplicate posts.

**Q: A user says a post never appeared in their feed. What happened?**
The fan-out for that follower failed, which is the one unacceptable failure in this system — stale is
fine, missing is not. So fan-out jobs go through a queue with retries and a dead letter queue that has an
alarm on it, and I would add a read-time safety net: when building the feed, also pull posts from the
last few minutes directly, so a fan-out that is late or lost is invisible to the user. And I would alarm
on the age of the oldest message in the fan-out queue rather than its depth, because depth without a
drain rate tells you nothing.

## 🎙️ Articulation drill

**Two minutes:** the fan-out decision, out loud, arithmetic first.

**⭐ "Six hundred posts a second is nothing. But average following is about two hundred, so fan-out on
write is a hundred and twenty thousand feed writes a second — the post is cheap and the distribution is
the problem. And it gets worse: a normal user with two hundred followers is two hundred writes, while one
celebrity with a hundred million followers is a hundred million writes for a single post, which takes
minutes and can saturate the whole pipeline."**

**⭐ "So neither model alone works. Push for normal accounts so a feed read is one list lookup, pull for
accounts above a follower threshold, and merge at read time — a user follows only a handful of
celebrities, so the merge is cheap. The threshold is a knob rather than a constant. And I'd skip fan-out
entirely for users who haven't opened the app in a month, backfilling when they return, because a large
share of those writes are for nobody."**
