# Part 2 — ⭐⭐ The key factory

```typescript
// src/api/keys.ts — ⭐⭐ ONE FILE. THE WHOLE CACHE DESIGN LIVES HERE.
export const keys = {
  orders: {
    all:    ["orders"] as const,
    list:   (f: OrderFilters) => [...keys.orders.all, "list", f] as const,
    detail: (id: string)      => [...keys.orders.all, "detail", id] as const,
  },
  users: {
    all:    ["users"] as const,
    me:     ()                => [...keys.users.all, "me"] as const,
  },
} as const;
```

| ⭐ Why a factory rather than inline arrays | |
|---|---|
| **Typos become compile errors** | ⭐⭐ `["oders", id]` inline is a **silent cache miss forever** — no error, just a refetch every time and two components disagreeing |
| **Hierarchy is enforced** | ⭐ `invalidate(keys.orders.all)` provably covers list **and** detail |
| **Filters are part of the key** | ⭐⭐ Different filters are different cache entries |
| **One place to read** | ⭐ "What does invalidating orders touch?" is answerable in ten seconds |

> ⭐⭐ **Key design is cache design** (Day 228) — the same care you would put into a cache-name and key
> scheme, except the **prefix gives you bulk eviction for free**, which `@CacheEvict` does not.

# Part 3 — The hook shape

```typescript
export function useOrders(filters: OrderFilters) {
  return useQuery({
    queryKey: keys.orders.list(filters),
    queryFn: ({ signal }) => client.GET("/orders", { params: { query: filters }, signal }),
    staleTime: 30_000,                    // ⭐ decided, not defaulted (Day 228)
  });
}

export function useCreateOrder() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (body: CreateOrder) =>
      client.POST("/orders", {
        body,
        headers: { "Idempotency-Key": body.clientId },   // ⭐⭐ Day 229
      }),
    onSuccess: () => qc.invalidateQueries({ queryKey: keys.orders.all }),
  });                                     // ⭐⭐ THE LINE PEOPLE FORGET
}
```

```
⭐⭐ THE FOUR DECISIONS EACH HOOK MAKES EXPLICIT

⭐   ① THE KEY        ⇒ what this data IS
⭐   ② ⭐ staleTime    ⇒ how current it must be. ⭐⭐ NEVER LEAVE AT
⭐                       THE DEFAULT WITHOUT DECIDING.
⭐   ③ ⭐⭐ INVALIDATION ⇒ what this write makes wrong (@CacheEvict)
⭐   ④ ⭐ RETRY        ⇒ safe? (Day 227 — never a bare POST)
```

| ⭐ Resource | staleTime | ⭐ Why |
|---|---|---|
| `users.me` | ⭐ 5 min | Changes rarely |
| `orders.list` | 30 s | ⭐ Others create orders |
| `orders.detail` | ⭐⭐ 0 | The screen you act on |
| Reference data | ⭐ 1 hr | It does not change |

# Part 4 — ⭐⭐ The request id, end to end

```
⭐⭐ THE TRANSPORT LAYER OWNS EVERY CROSS-CUTTING CONCERN, ONCE:

⭐   · ⭐ AUTH        ⇒ credentials + single-flight refresh (Day 235)
⭐   · ⭐⭐ 401        ⇒ refresh once, retry once, then redirect.
⭐                     ⭐ A SCREEN MUST NEVER HANDLE A 401 ITSELF.
⭐   · ERROR MAPPING ⇒ ApiError with status + parsed ProblemDetail
⭐   · ⭐ RETRY       ⇒ 5xx/429 with jitter; NEVER 4xx
⭐   · ⭐⭐ TRACING    ⇒ a request id per call, sent as a header
⭐   · TIMEOUTS      ⇒ AbortSignal.timeout on every request
```

```typescript
const requestId = crypto.randomUUID();
headers["X-Request-Id"] = requestId;
// ...on failure:
reportError(err, { requestId, path, status });   // ⭐ Day 279
```

```java
// ⭐⭐ the Spring side — put it in the MDC and every log line carries it
@Component
class RequestIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain) throws IOException, ServletException {
        String id = Optional.ofNullable(req.getHeader("X-Request-Id"))
                            .orElseGet(() -> UUID.randomUUID().toString());
        MDC.put("requestId", id);            // ⭐⭐ NOW IT IS IN EVERY LOG LINE
        res.setHeader("X-Request-Id", id);
        try { chain.doFilter(req, res); } finally { MDC.remove("requestId"); }
    }
}
```

> ⭐⭐ **This is the highest-value fifteen lines in your whole observability setup.** A user's
> screenshot now contains an id you can grep across your entire log aggregation — **the difference
> between debugging a report and dismissing it.** ⭐ You already do this between services; the browser
> is just one more hop that was missing from the trace.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how is your frontend's API layer structured?"**

State the principle and the enforcement together. **Three layers. A transport layer owning auth,
refresh, error mapping, retries and timeouts. A query layer of one hook per resource owning the cache
key, staleness and invalidation. And screens, which call hooks and never learn a URL exists. The test
is grepping components for `fetch` — every hit is a component that silently opted out of auth, retry
and caching. There's a lint rule so it stays true, which is ArchUnit for the frontend: a layering rule
the build enforces rather than a convention people remember.**

Then the key factory. **All cache keys come from one typed factory. An inline typo'd key is a silent
cache miss forever — no error, just a refetch every time and two components disagreeing about the same
record. In a factory it's a compile error, and the prefix hierarchy gives me bulk invalidation, which
`@CacheEvict` doesn't.**

Then what each hook decides. **The key, staleness, what a write invalidates, and whether retry is safe.
I never leave staleTime at the default without deciding. And mutations carry an idempotency key,
because a double-click on a create endpoint made two records.**

Close on the operational piece. **Every request carries a generated request id as a header; a Spring
filter puts it in the MDC so every log line has it, and errors report it from the browser. That's
fifteen lines, and it means a user's screenshot contains an id I can grep across the whole log
aggregation — the difference between debugging a report and dismissing it. I already traced between
services; the browser was the hop that was missing.**
