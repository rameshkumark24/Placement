# Part 1 — The four, with their Redis implementations

## ⭐ 1. Fixed window — simplest, and wrong at the boundary

```lua
-- ⭐ atomic: INCR and conditional EXPIRE in one script (Day 203)
local current = redis.call('INCR', KEYS[1])
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return current
```

```java
String key = "rl:fixed:" + clientId + ":" + (System.currentTimeMillis() / 60_000);
Long count = redis.execute(SCRIPT, List.of(key), "60");
boolean allowed = count <= limit;
```

**⭐ Day 122's boundary problem, in numbers: with a limit of 100 per minute, a client can send 100 at
12:00:59 and 100 more at 12:01:00 — 200 requests in one second.** The window resets on a wall-clock
boundary, so the effective burst is double the limit.

**Cheapest option: one counter per window. Use it when a 2× burst is tolerable.**

## ⭐⭐ 2. Sliding window log — exact, using a sorted set

```lua
local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)      -- ⭐ drop entries outside the window
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, ARGV[4])                  -- ⭐ ARGV[4] = a unique id
    redis.call('EXPIRE', key, math.ceil(window / 1000))    -- ⭐ so idle keys disappear
    return {1, limit - count - 1}
end
return {0, 0}
```

**⭐ This is Day 204's pattern: the score is the timestamp**, so "how many in the last 60 seconds" is
`ZREMRANGEBYSCORE` followed by `ZCARD` — two range operations on an ordered structure.

**⭐ Exactly correct — no boundary effect at all.** The cost is memory: **one sorted-set member per
request**. A limit of 1,000 per minute across 10,000 clients is 10 million members, which is
hundreds of megabytes.

⚠️ **`ARGV[4]` must be unique** — two requests in the same millisecond with the same member overwrite
rather than add, and one silently escapes the count. Use a UUID or a counter.

## ⭐⭐ 3. Sliding window counter — the practical default

```lua
-- ⭐ two fixed-window counters, weighted by how far into the current window we are
local prev = tonumber(redis.call('GET', KEYS[1]) or 0)
local curr = tonumber(redis.call('GET', KEYS[2]) or 0)
local weight = 1 - (tonumber(ARGV[1]) / tonumber(ARGV[2]))     -- ⭐ elapsed fraction
local estimate = prev * weight + curr
if estimate < tonumber(ARGV[3]) then
    redis.call('INCR', KEYS[2])
    redis.call('EXPIRE', KEYS[2], tonumber(ARGV[4]))
    return 1
end
return 0
```

**⭐ Two counters, an approximation, and no boundary burst.** If you are 25% into the current minute,
it counts 75% of the previous minute's total plus everything so far in this one.

**⭐ This is the right default for most APIs**: fixed-window memory cost (two integers per client),
sliding-window behaviour, and error under about 1% in practice.

## ⭐ 4. Token bucket — the one that allows bursts on purpose

```lua
local tokens_key, ts_key = KEYS[1], KEYS[2]
local rate, capacity, now, requested = tonumber(ARGV[1]), tonumber(ARGV[2]),
                                       tonumber(ARGV[3]), tonumber(ARGV[4])
local tokens = tonumber(redis.call('GET', tokens_key) or capacity)
local last   = tonumber(redis.call('GET', ts_key) or now)
-- ⭐ refill lazily: no background timer needed
tokens = math.min(capacity, tokens + (now - last) * rate)
local allowed = tokens >= requested
if allowed then tokens = tokens - requested end
redis.call('SET', tokens_key, tokens, 'EX', math.ceil(capacity / rate) * 2)
redis.call('SET', ts_key, now, 'EX', math.ceil(capacity / rate) * 2)
return {allowed and 1 or 0, tokens}
```

**⭐ The lazy refill is the elegant part**: no background process adds tokens. Each request computes
how many *would* have accumulated since the last one.

**⭐ Token bucket is the right choice when bursts are legitimate** — a mobile client syncing after
being offline, a batch import, a page that legitimately fires eight requests at once. **A sliding
window rejects that burst; a token bucket absorbs it** while still bounding the sustained rate.

**⭐ And `requested` lets you charge different costs per operation** — a search costs 5 tokens, a
simple read costs 1. That is a genuinely useful capability the other three algorithms lack.

# Part 2 — ⭐ The design decisions that matter more than the algorithm

## ⭐ What do you limit by?

| Key | Problem |
|---|---|
| ⭐ **IP address** | ⭐ NAT and corporate proxies share one IP; a botnet has thousands |
| ⭐ **User / API key** | ⭐ **the best signal** — but only after authentication |
| Endpoint | a cheap read and an expensive report should not share a budget |
| ⭐ **Tenant** (Day 176) | one tenant must not starve another |

**⭐ The answer is layered, not singular:**

```
rl:ip:{ip}                  →  1000/min   ⭐ coarse — catches unauthenticated floods
rl:user:{userId}            →   300/min   ⭐ the real limit
rl:user:{userId}:search     →    30/min   ⭐ expensive endpoints separately
rl:tenant:{tenantId}        → 10000/min   ⭐ fairness between tenants
```

**⭐ And the login endpoint needs both** (Day 170): by IP catches one machine spraying many accounts;
by username catches a botnet targeting one account. **Neither alone is sufficient**, and that is a
point worth making explicitly.

## ⭐ What do you tell the client?

```
HTTP/1.1 429 Too Many Requests
⭐ Retry-After: 30
⭐ RateLimit-Limit: 300
⭐ RateLimit-Remaining: 0
⭐ RateLimit-Reset: 30
```

**⭐ `Retry-After` is what makes a well-behaved client back off correctly** instead of retrying
immediately and making it worse (Day 154). Returning 429 without it is telling a client to stop
without saying when to resume — so it guesses, usually badly.

**⭐ Send the limit headers on *successful* responses too**, so clients can throttle themselves before
being rejected. And remember Day 155: **`exposedHeaders` is required or the browser cannot read
them** — a rate limiter whose headers are invisible to the client is half a feature.

## ⭐⭐ What happens when Redis is down?

> **⭐ Fail open or fail closed? This is the question interviewers use to separate answers.**

| Choice | Consequence |
|---|---|
| ⭐ **Fail open** (allow) | ⭐ availability preserved; **abuse protection gone** |
| ⭐ **Fail closed** (reject) | ⭐ protection preserved; **your API is down** |

**⭐ The right answer is per-endpoint, and saying so is the answer:**

- ⭐ **General API traffic: fail open.** A rate limiter is a protection mechanism; it must not become
  the outage. Day 168's `CacheErrorHandler` argument, applied to limits.
- ⭐ **Login, password reset, payment: fail closed** — or fall back to a local in-process limiter.
  Losing rate limiting on the login endpoint during a Redis outage is an invitation to credential
  stuffing precisely when you are least able to notice.

```java
try {
    return limiter.tryConsume(key);
} catch (RedisConnectionFailureException e) {
    log.warn("rate_limiter_unavailable endpoint={}", endpoint);
    metrics.counter("ratelimit.degraded").increment();      // ⭐ alert on this
    return endpoint.isSensitive() ? localFallback.tryConsume(key) : true;
}
```

**⭐ A local per-instance fallback is the pragmatic middle ground**: with ten instances a 300/min
limit becomes an effective 3,000/min, which is far better than unlimited and far better than down.

# Part 3 — Making it correct and cheap

## ⭐ Atomicity is not optional

```java
// ❌ three round trips and a race — two requests both see 99 and both pass
Long count = redis.opsForValue().increment(key);
if (count == 1) redis.expire(key, ttl);
if (count > limit) reject();
```

**⭐ Under concurrency this over-admits**, and the excess is proportional to concurrency — precisely
when the limit matters most. **Every implementation on this page is a single Lua script for exactly
that reason** (Day 203).

## ⭐ Latency, and where the limiter runs

**⭐ A rate limiter adds a Redis round trip to every request** — about 0.5 ms, on the critical path of
100% of traffic. Three ways to reduce it:

| Approach | Note |
|---|---|
| ⭐ **Limit at the gateway/ingress** | ⭐ **best** — rejected traffic never reaches your application at all |
| A local first-tier check | reject obvious violators without touching Redis |
| Pipeline with another Redis call | if you are already making one |

**⭐ Limiting at the edge is the architecturally correct place**: nginx, Envoy, an API gateway or a
CDN rejects the flood before it consumes a connection, a thread and a database connection in your
service. **Application-level limiting is for per-user and per-tenant fairness, which the edge usually
cannot express.**

## Memory

| Algorithm | Per client |
|---|---|
| Fixed window | ⭐ one integer |
| Sliding counter | ⭐ two integers |
| Token bucket | two values |
| ⭐ **Sliding log** | ⭐ **one sorted-set member per request** |

**⭐ Always set a TTL on every rate-limit key.** An idle client's key must disappear, or Day 204's
rule applies: an unbounded collection of keys is a memory leak with a delay.

## Bucket4j — the library worth knowing

```java
Bucket bucket = Bucket.builder()
    .addLimit(Bandwidth.classic(300, Refill.greedy(300, Duration.ofMinutes(1))))
    .addLimit(Bandwidth.classic(20,  Refill.greedy(20,  Duration.ofSeconds(1))))   // ⭐ burst cap
    .build();
```

**⭐ Bucket4j with a Redis backend gives you tested, atomic token buckets** and — the useful part —
**multiple simultaneous bandwidths**, so you can express "300 per minute *and* no more than 20 per
second". That combination catches the client who spends their whole minute's budget in two seconds,
which a single limit cannot.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Non-atomic check-then-increment | over-admits exactly under load |
| Fixed window where bursts matter | ⭐ 2× the limit at the boundary |
| Sliding log at scale | one member per request — hundreds of MB |
| Non-unique member in the sliding log | requests silently uncounted |
| ⭐ No TTL on limit keys | unbounded key growth |
| ⭐ Limiting by IP only | NAT punishes shared users; botnets bypass it |
| Limiting by username only on login | one IP sprays thousands of accounts |
| ⭐ 429 without `Retry-After` | clients retry immediately and worsen it |
| Headers not in `exposedHeaders` | ⭐ invisible to browsers (Day 155) |
| ⭐ No decision about Redis being down | you find out during the outage |
| Failing closed on general traffic | the limiter becomes the outage |
| ⭐ Failing open on login | credential stuffing when you can least see it |
| Limiting only in the application | the flood still consumes threads and connections |
| One budget for cheap and expensive endpoints | a report and a health check share a limit |

## Interview questions

**Q: Implement a rate limiter with Redis.**
A Lua script, so the check and the increment are atomic — a non-atomic version over-admits precisely
under concurrency. For the algorithm I default to a sliding window counter: two fixed-window counters
weighted by elapsed time, which gives sliding behaviour at fixed-window memory cost with about 1%
error. A sliding log with a sorted set is exact but stores one member per request.

**Q: Why is fixed window insufficient?**
The boundary. With 100 per minute, a client sends 100 at 12:00:59 and 100 more at 12:01:00 — 200 in
one second, double the intended limit — because the window resets on a wall-clock boundary.

**Q: What do you limit by?**
Layered: by IP as a coarse pre-authentication defence, by user or API key as the real limit, by
endpoint so an expensive report does not share a budget with a cheap read, and by tenant for
fairness. For login specifically, both IP and username — by IP alone a botnet bypasses it, by
username alone one machine sprays thousands of accounts.

**Q: What happens when Redis is down?**
It depends on the endpoint, and that is the answer. General traffic fails open, because a protection
mechanism must not become the outage. Login, password reset and payment fail closed, or fall back to
a local per-instance limiter — losing rate limiting on login during a Redis outage is exactly when
you cannot afford it. And I alert on the degraded state either way.

**Q: Where should rate limiting live?**
At the edge for volumetric protection, because traffic rejected at the gateway never consumes a
thread or a database connection. In the application for per-user and per-tenant fairness, which the
edge usually cannot express. Both, at different granularities.
