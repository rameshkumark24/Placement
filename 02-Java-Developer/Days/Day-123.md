# Part 1 — The two generals, and why exactly-once is a fiction

```
Client ──── POST /payments ────► Server
                                   │ charges the card ✅
Client ◄──── ✗ TIMEOUT ────────────┘ response lost

Did the payment succeed? The client CANNOT KNOW.
```

**The client cannot distinguish "the request never arrived" from "it arrived and the response was
lost".** No protocol fixes this — it is the Two Generals Problem, and it is provably unsolvable.

So there are exactly three delivery semantics:

| Semantics | Meaning | Cost |
|---|---|---|
| **At-most-once** | Never retry | Requests are silently lost |
| **At-least-once** | Retry until acknowledged | **Duplicates** |
| ~~Exactly-once~~ | The dream | **Impossible at the transport level** |

> **"Exactly-once" is always at-least-once delivery plus idempotent processing.** When a vendor
> claims exactly-once semantics, that is what they have built. Being able to say this sentence is the
> whole point of the day.

So: **retry (at-least-once), and make the operation safe to repeat (idempotent).**

# Part 2 — Idempotency keys

Day 102 established that `POST` is not idempotent. The key makes it so.

```http
POST /payments
Idempotency-Key: 8f14e45f-ea4d-4b2e-9f8a-1c2d3e4f5a6b
Content-Type: application/json

{"amount": "1499.00", "currency": "INR", "card": "tok_abc"}
```

**The client generates the key** — one per logical operation, reused across every retry of *that*
operation. A new key means a new payment.

## The server side, done correctly

```java
public Response process(String idempotencyKey, Request request) {
    String fingerprint = sha256(canonicalJson(request));

    // 1. Atomically claim the key — INSERT, not check-then-act
    try {
        repo.insert(new IdempotencyRecord(idempotencyKey, fingerprint, IN_PROGRESS, now()));
    } catch (DuplicateKeyException e) {
        IdempotencyRecord existing = repo.get(idempotencyKey);

        // 2. ⭐ Same key, DIFFERENT body ⇒ a client bug. Refuse.
        if (!existing.fingerprint().equals(fingerprint))
            throw new ConflictException("Idempotency-Key reused with a different payload");

        // 3. Still running ⇒ tell the client to retry shortly
        if (existing.status() == IN_PROGRESS)
            throw new ConflictException("request in progress", Duration.ofSeconds(2));

        // 4. Completed ⇒ return the STORED response. Do NOT re-execute.
        return existing.response();
    }

    // 5. First time — execute, then persist the result
    try {
        Response response = doTheWork(request);
        repo.complete(idempotencyKey, response);      // ⚠️ ideally in the SAME transaction
        return response;
    } catch (Exception e) {
        repo.fail(idempotencyKey, e);                 // decide: retryable, or terminal?
        throw e;
    }
}
```

Each numbered step exists for a reason:

**1. Claim atomically.** A `SELECT` then `INSERT` is check-then-act (Day 065): two concurrent retries
both find nothing and both execute. Rely on the unique constraint and catch the violation — the
database does the mutual exclusion for you.

**2. Fingerprint the request body.** The same key with a different payload means the client is
confused, and executing it would be a silent correctness bug. **Stripe returns an error here, and so
should you.**

**3. Handle the in-progress case.** Two retries can genuinely overlap. Returning `409` with a short
`Retry-After` is better than blocking or double-executing.

**4. Return the stored response**, including the original status code — not a new `200`. The client
must see the same outcome it would have seen originally.

**5. Persist the result with the work.** If the record and the payment are written in separate
transactions, a crash between them means the payment happened and the key says it did not — so the
retry charges again. **Ideally the idempotency record and the business write are one transaction.**

## Scope, expiry and failures

```sql
CREATE TABLE idempotency_record (
    key          TEXT NOT NULL,
    tenant_id    UUID NOT NULL,
    user_id      BIGINT NOT NULL,
    endpoint     TEXT NOT NULL,
    fingerprint  CHAR(64) NOT NULL,
    status       TEXT NOT NULL,            -- IN_PROGRESS | COMPLETED | FAILED
    response     JSONB,
    status_code  INT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at   TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (tenant_id, user_id, endpoint, key)     -- ⭐ scoped, not global
);
```

**Scope the key to the tenant, user and endpoint.** A globally unique key space means one client's
UUID collision affects another, and it lets a client probe for other clients' keys.

**Expire records after 24 hours** (Stripe's window). Retries happen within minutes; storing keys
forever is unbounded growth.

**The subtle question: what do you store for a failure?** If the operation failed with a `500`, a
retry *should* re-execute. If it failed with a `422` validation error, a retry will fail identically
and the stored response is correct. **Store terminal failures; let retryable ones re-execute.**

## Making operations naturally idempotent

Better than a key when it applies:

```sql
-- Natural key + upsert
INSERT INTO payments (external_id, amount) VALUES (?, ?)
ON CONFLICT (external_id) DO NOTHING;

-- State-transition guard (Day 095) — the second attempt matches no rows
UPDATE orders SET status = 'SHIPPED' WHERE id = ? AND status = 'PAID';

-- Absolute values, never deltas
SET quantity = 5          ✅ idempotent
SET quantity = quantity+1 ❌ not
```

> **Design the operation to be idempotent before reaching for a key.** A unique constraint on a
> natural identifier is simpler, cheaper and impossible to forget.

# Part 3 — Retries

## What may be retried

| Response | Retry? | Why |
|---|---|---|
| Connection refused / timeout | ✅ | May never have arrived |
| `500`, `502`, `503`, `504` | ✅ | Server-side, likely transient |
| `429` | ✅ **after `Retry-After`** | Explicitly asked to |
| `408` Request Timeout | ✅ | |
| `400`, `422` | ❌ | Retrying identical input fails identically |
| `401`, `403` | ❌ | Refresh the token first, then retry once |
| `404` | ❌ (usually) | ⚠️ except immediately after a create — read-after-write lag |
| `409` | ⚠️ depends | Idempotency in-progress: yes. Version conflict: reload first. |

**Retrying a `400` is a loop that can never succeed**, and it still costs you money and capacity
(Day 062).

## Backoff with jitter — the part that matters

```java
public <T> T withRetry(Callable<T> op, int maxAttempts) throws Exception {
    Exception last = null;
    for (int attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
            return op.call();
        } catch (RetryableException e) {
            last = e;
            if (attempt == maxAttempts) break;

            long cap  = Math.min(30_000, 200L * (1L << (attempt - 1)));    // exponential, CAPPED
            long wait = ThreadLocalRandom.current().nextLong(cap);          // ⭐ FULL JITTER
            Thread.sleep(e.retryAfter().map(Duration::toMillis).orElse(wait));
        }
    }
    throw new RetriesExhaustedException(maxAttempts, last);
}
```

**Why full jitter rather than "exponential plus a bit of randomness":**

```
1,000 clients fail simultaneously (a deploy, a restart, a brief outage).

No jitter:      all retry at 200 ms, then 400 ms, then 800 ms
                ⇒ 1,000 SIMULTANEOUS requests at each step — the outage repeats, forever
Full jitter:    each waits uniformly in [0, cap)
                ⇒ 1,000 requests spread evenly across the window
```

AWS's published analysis found **full jitter** — `random(0, cap)`, discarding the base entirely —
produced the lowest total work and lowest completion time. Not `base + random`; the whole interval.

> **This is the same principle as Day 121's TTL jitter and Day 071's livelock fix. Randomness breaks
> synchronisation.** Three different problems, one idea.

## The retry rules

| Rule | Why |
|---|---|
| **Cap the attempts** (3–5) | Otherwise it is an infinite loop |
| **Cap the backoff** (~30 s) | 2^10 seconds is 17 minutes |
| **Full jitter** | Prevents synchronised waves |
| **Honour `Retry-After`** | The server knows better than your formula |
| **Retry only idempotent operations** — or use a key | Otherwise you double-charge |
| **Do not retry at every layer** ⚠️ | See below |
| **Add a circuit breaker** | Stop calling a dependency that is down |
| **Track the retry budget** | Cap retries at ~10% of total requests |

## ⭐ Retry amplification

The trap that turns a small incident into an outage:

```
Client retries 3× → Gateway retries 3× → Service A retries 3× → Service B
                                                       ⇒ 27 requests to B for ONE user action
```

**Retries multiply across layers.** A dependency that is already struggling receives an order of
magnitude more load precisely when it can least handle it.

> **Retry at ONE layer — normally the outermost that can safely do so — and pass failures through
> everywhere else.**

The complementary control is a **retry budget**: allow retries only while they are under ~10% of
total request volume. Under a real outage, retries are then automatically suppressed instead of
amplifying. This is what gRPC and Envoy implement, and naming it is a strong interview signal.

## Circuit breakers

```
CLOSED ──(failure rate > 50%)──► OPEN ──(after 30 s)──► HALF_OPEN
   ▲                              │                        │
   └───(trial succeeds)───────────┴──(trial fails)─────────┘

OPEN ⇒ fail IMMEDIATELY without calling. Protects the dependency AND your own threads.
```

The second benefit is the one people miss: an open breaker stops *your* threads blocking on a dead
dependency, which is what prevents a downstream failure from exhausting your thread pool (Day 069)
and cascading.

## Timeouts — the precondition

**A retry without a timeout is meaningless.**

```java
HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build();
request.timeout(Duration.ofSeconds(5));
```

**Timeout budget:** if your endpoint must answer in 3 seconds and you call three services, you cannot
give each a 3-second timeout. Allocate a budget and **propagate the remaining deadline downstream**
so nobody does work whose result will be discarded.

# Part 4 — D-15 · Concurrency control

**How a database implements isolation** (Day 120's D-14).

## Two-Phase Locking — pessimistic

```
GROWING phase:   acquire locks, never release
SHRINKING phase: release locks, never acquire
```

**Strict 2PL** — hold every lock until commit — is what most locking databases implement, because it
also guarantees recoverability.

```
Shared (S) lock       for reads   — many readers may share
Exclusive (X) lock    for writes  — one writer, and it blocks readers
```

**2PL guarantees serializability.** Its costs are lock contention, blocking, and **deadlock** — which
the database detects with a wait-for graph and resolves by killing a victim transaction (Day 071's
theory, now in the database).

## ⭐ MVCC — Multi-Version Concurrency Control

**The idea that makes modern databases fast**, and the reason PostgreSQL, Oracle and InnoDB behave as
they do:

> **Writers create a new *version* of a row instead of overwriting it. Readers see the version that
> was current when their snapshot began.**
>
> ⇒ **Readers never block writers, and writers never block readers.**

```
Row id=1, balance=1000

T1 (started at txid 100) reads  → sees version created before 100 → 1000
T2 (txid 105) updates to 500    → writes a NEW version, marks the old one dead at 105
T1 reads again                  → STILL 1000  (its snapshot is unchanged)
T3 (txid 110) reads             → 500
```

In PostgreSQL every row carries `xmin` (the transaction that created it) and `xmax` (the one that
deleted it); visibility is decided by comparing those against the reader's snapshot.

**Three consequences that explain a great deal of PostgreSQL's behaviour:**

**1. `UPDATE` is really `INSERT` + mark-dead.** So an update writes a whole new row version, which is
why updating one column of a wide row is not cheap and why write amplification is real.

**2. Dead tuples accumulate and must be reclaimed — that is what `VACUUM` does.** Without it, tables
bloat and performance degrades. **Autovacuum not keeping up is one of the most common PostgreSQL
production problems.**

**3. Long-running transactions block cleanup.** `VACUUM` cannot remove a version any open transaction
might still need, so an idle-in-transaction session for hours prevents reclamation database-wide.
**"Never leave a transaction open" (Day 117) is not tidiness — it is an operational requirement.**

MySQL/InnoDB uses **undo logs** rather than in-place versions, so old versions live in a rollback
segment. Same idea, different bookkeeping, and it is why InnoDB does not need vacuum but *does* need
purge.

## Optimistic vs pessimistic — choosing

| | Pessimistic (`SELECT … FOR UPDATE`) | Optimistic (version column) |
|---|---|---|
| Assumes | Conflicts are likely | Conflicts are rare |
| Cost when no conflict | Lock overhead, blocking | **None** |
| Cost when conflict | Waiting | Wasted work + retry |
| Deadlock possible | ✅ | ❌ |
| Works across requests | ❌ locks cannot span HTTP calls | ✅ |
| Fits | Hot rows, short transactions | Web applications, long think-time |

```java
// Optimistic — this is what JPA's @Version does (Stage 5), and Day 102's If-Match over HTTP
UPDATE account SET balance = ?, version = version + 1 WHERE id = ? AND version = ?;
// 0 rows ⇒ someone else committed first ⇒ reload and retry
```

**Optimistic is right for web applications** because a user's edit spans a page render, thinking
time, and a submit — you cannot hold a database lock across that. Pessimistic is right for a short,
hot, contended transaction inside a single request.

**The queue pattern, which is genuinely useful** (and appears again on Day 125):

```sql
SELECT * FROM jobs WHERE status = 'PENDING'
ORDER BY created_at LIMIT 10
FOR UPDATE SKIP LOCKED;               -- ⭐ workers claim DIFFERENT rows without blocking
```

`SKIP LOCKED` turns a table into a work queue: each worker locks and claims disjoint rows, and none
of them wait.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Believing exactly-once delivery exists | A design built on a false premise |
| Retrying non-idempotent operations | Double charges |
| `SELECT` then `INSERT` for the idempotency key | Concurrent retries both execute |
| Not fingerprinting the request body | A reused key silently returns the wrong result |
| Idempotency record in a separate transaction | Crash between them ⇒ double execution on retry |
| Globally-scoped keys | Cross-client collisions and probing |
| Retrying `400`/`422` | A loop that can never succeed |
| No jitter | Synchronised retry waves; the outage repeats |
| `base + random` instead of full jitter | Less effective spread |
| Retries at every layer | 27× amplification |
| No retry budget | Retries amplify precisely during an outage |
| No cap on attempts or backoff | Infinite loops, 17-minute waits |
| Retry without a timeout | Waiting forever, then retrying |
| Not propagating the deadline | Work done whose result is discarded |
| Long-running transactions in PostgreSQL | `VACUUM` blocked; table bloat |
| Pessimistic locking across HTTP requests | Impossible — use optimistic |

## Interview questions

**Q: Can you guarantee exactly-once delivery?**
No — the Two Generals Problem makes it impossible, because a client cannot distinguish a lost request
from a lost response. What is called exactly-once is at-least-once delivery plus idempotent
processing.

**Q: How do idempotency keys work?**
The client sends a unique key per logical operation, reused on retries. The server atomically claims
the key with an insert, fingerprints the request body to reject a reused key with different content,
and stores the response so a retry returns the original outcome instead of re-executing.

**Q: What is the most common bug in an idempotency implementation?**
Check-then-act — a `SELECT` followed by an `INSERT` — so two concurrent retries both find nothing and
both execute. Rely on the unique constraint and catch the violation. The second is writing the
idempotency record in a different transaction from the work.

**Q: Why full jitter rather than exponential backoff?**
Without jitter, every client that failed at the same moment retries at the same moment, so the burst
repeats at each step. AWS's analysis found full jitter — a uniform wait in `[0, cap)` — minimised both
total work and completion time.

**Q: What is retry amplification?**
Retries at multiple layers multiply: three layers at three attempts each is 27 requests downstream
for one user action, arriving exactly when the dependency is already failing. Retry at one layer, and
enforce a retry budget capping retries at around 10% of traffic.

**Q: What is MVCC and why does it matter?**
Writers create new row versions rather than overwriting, and readers see the version current at their
snapshot — so readers never block writers and writers never block readers. It is why PostgreSQL
`UPDATE` is insert-plus-mark-dead, why `VACUUM` exists, and why long-running transactions block
cleanup database-wide.

**Q: Optimistic or pessimistic locking?**
Optimistic for web applications, because a user edit spans render, think time and submit, and you
cannot hold a lock across that — a version column detects the conflict at write time. Pessimistic for
short, hot, contended transactions within a single request.

**Q: How would you build a job queue in SQL?**
`SELECT … FOR UPDATE SKIP LOCKED` — each worker locks and claims a disjoint set of rows without
blocking on the others.

## 🎙️ Articulation drill

Three minutes: **"A payment request times out. What happens next?"**

The client cannot know whether it succeeded — Two Generals — so it retries with the same idempotency
key. The server recognises the key, sees the completed record and returns the original response
without re-charging. Then the client-side rules: retry only retryable statuses, full jitter, capped
attempts, honour `Retry-After`, one retry layer only, circuit breaker, timeout budget. Close with
"exactly-once is at-least-once plus idempotency" — it is the sentence that shows you understand the
whole problem.
