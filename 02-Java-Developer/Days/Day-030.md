# L-030 · The language mechanics

## Integer division and modulo

```java
5 / 2        // 2      — integer division TRUNCATES toward zero
5.0 / 2      // 2.5    — one double operand promotes the whole expression
5 % 2        // 1
-5 % 3       // -2     ← the sign follows the DIVIDEND, not the divisor
5 % -3       // 2
1 / 0        // ArithmeticException: / by zero
1.0 / 0      // Infinity  ← floating point does NOT throw
0.0 / 0.0    // NaN
```

**Two traps worth carrying:**

**`-5 % 3` is `-2`, not `1`.** In Java the result takes the sign of the dividend. So `%` is *not*
safe for "wrap into range" on possibly-negative values:

```java
int index = (hash % size);                    // 💀 can be negative
int index = Math.floorMod(hash, size);        // ✅ always non-negative
```

That's a real bug when hashing — and it's exactly why `HashMap` uses `& (n-1)` with a power-of-two
table size rather than `%` (Day 048).

**Integer division throws; floating-point division doesn't.** `1/0` is an exception, `1.0/0` is
`Infinity`. If a calculation silently produces `Infinity` or `NaN`, it propagates through everything
downstream without complaint.

## Floating point

```java
0.1 + 0.2 == 0.3        // FALSE
0.1 + 0.2               // 0.30000000000000004
```

**Because binary floating point cannot represent 0.1 exactly**, any more than decimal can represent
1/3. IEEE 754 stores the nearest representable value, and the errors accumulate.

**Never use `float`/`double` for money.** Full treatment on [Day 042B](Day-042B.md); for today, know
the rule and that `BigDecimal` is the answer.

```java
Math.abs(a - b) < 1e-9        // compare doubles with a tolerance, never with ==
```

## `&` vs `&&`

```java
if (list != null && !list.isEmpty())     // ✅ short-circuits — safe
if (list != null &  !list.isEmpty())     // 💥 NPE — evaluates BOTH sides
```

| | Short-circuits | Use for |
|---|---|---|
| `&&` `\|\|` | ✅ stops as soon as the result is known | **Always, in conditions** |
| `&` `\|` `^` | ❌ evaluates both | Bitwise ops on integers |

**Short-circuiting is a correctness feature, not an optimisation.** The null-check idiom above
depends on it entirely.

## Increment operators

```java
int x = 1;
int a = x++;     // a = 1, x = 2   (post: use, then increment)
int b = ++x;     // b = 3, x = 3   (pre: increment, then use)

int x = 1;
int r = x++ + ++x;    // 1 + 3 = 4
```

**Java evaluates left to right, always.** (Unlike C, where this is undefined behaviour.)

**Don't write code like that.** It appears in interviews as a puzzle; writing it in real code is a
defect. The one genuinely useful thing to remember:

```java
i++     // NOT atomic — read, add, write (Day 025's data race, Day 068's CAS)
```

## `switch` — statement vs expression

### The old statement form

```java
switch (day) {
    case MONDAY:
    case TUESDAY:
        type = "Start";
        break;              // ← forget this and you FALL THROUGH
    case SATURDAY:
        type = "Weekend";
        break;
    default:
        type = "Mid";
}
```

**Fall-through is the default**, which is the wrong default — accidental fall-through has caused real
outages, most famously in Apple's "goto fail" TLS bug (structurally the same class of error).

### The modern expression form (Java 14+)

```java
String type = switch (day) {
    case MONDAY, TUESDAY -> "Start";
    case SATURDAY, SUNDAY -> "Weekend";
    default -> "Mid";
};
```

| | Statement | Expression |
|---|---|---|
| Produces a value | ❌ | ✅ |
| Fall-through | ✅ (the default!) | ❌ — impossible with `->` |
| Exhaustiveness checked | ❌ | ✅ **compile error if a case is missing** |
| Multiple labels | Stacked `case`s | `case A, B ->` |

**Use the arrow form always.** Two real benefits: no accidental fall-through, and **exhaustiveness
checking** — with an enum or sealed type, the compiler fails the build if you add a variant and
forget to handle it. That turns a runtime bug into a compile error.

For a multi-statement branch, use `yield`:

```java
int size = switch (type) {
    case SMALL -> 10;
    case LARGE -> {
        log.info("large requested");
        yield 100;                       // yield, not return
    }
};
```

**Pattern matching for switch** (Java 21) is Day 042 — it makes this far more powerful.

## `var` — local type inference (Java 10+)

```java
var list = new ArrayList<String>();          // ✅ ArrayList<String>
var count = 0;                                // ✅ int
var entry = map.entrySet().iterator().next(); // ✅ saves a very long type name
```

**Where `var` is forbidden:**

```java
var x;                    // ❌ no initialiser
var x = null;             // ❌ can't infer
var[] arr = {1,2};        // ❌
class A { var f = 1; }    // ❌ fields
void m(var p) { }         // ❌ parameters
var m() { }               // ❌ return types
```

**`var` is local variables only.** It's not dynamic typing — the type is fixed at compile time, just
inferred.

**When to use it:** when the type is obvious from the right-hand side, or the type name is long and
adds nothing.

```java
var users = new HashMap<String, List<Order>>();     // ✅ obvious, saves repetition
var result = process(data);                          // ❌ what IS result? Be explicit.
```

**The test: can a reader tell the type without an IDE?** If not, write it out.

## Text blocks (Java 15+)

```java
String sql = """
    SELECT u.id, u.name
    FROM users u
    WHERE u.active = true
    """;
```

Incidental indentation is stripped relative to the **closing delimiter's** position — move `"""`
left and more whitespace is preserved.

```java
String s = """
    no trailing newline\
    continues on the same line""";        // \ suppresses the line terminator
```

Use for SQL, JSON, HTML. Far better than concatenated escaped strings.

## Enhanced for and labelled break

```java
for (String s : list) { }          // Iterator under the hood (Day 024)
for (int x : array) { }            // plain indexed loop, no iterator

outer:
for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        if (found) break outer;    // breaks BOTH loops
    }
}
```

**Labelled break is legitimate** for escaping nested loops — much cleaner than a flag variable. Not
`goto`; it can only jump *out*.

## Type this yourself

```java
public class OperatorDemo {
    public static void main(String[] args) {

        // ---- 1. Division and modulo ----
        System.out.println("5 / 2      = " + (5 / 2));
        System.out.println("5.0 / 2    = " + (5.0 / 2));
        System.out.println("-5 % 3     = " + (-5 % 3));        // -2 !
        System.out.println("floorMod   = " + Math.floorMod(-5, 3));  // 1
        System.out.println("1.0 / 0    = " + (1.0 / 0));       // Infinity, no exception
        System.out.println("0.0 / 0.0  = " + (0.0 / 0.0));     // NaN

        // ---- 2. Floating point ----
        System.out.println("\n0.1 + 0.2  = " + (0.1 + 0.2));
        System.out.println("== 0.3     ? " + (0.1 + 0.2 == 0.3));
        System.out.println("within 1e-9? " + (Math.abs((0.1 + 0.2) - 0.3) < 1e-9));

        // ---- 3. Short circuit is a CORRECTNESS feature ----
        String s = null;
        System.out.println("\n&& safe : " + (s != null && s.length() > 0));
        try {
            boolean b = (s != null & s.length() > 0);          // both sides evaluated
        } catch (NullPointerException e) {
            System.out.println("&  NPE  : single & evaluated both sides");
        }

        // ---- 4. Increment order ----
        int x = 1;
        System.out.println("\nx++ + ++x = " + (x++ + ++x) + "   (left to right: 1 + 3)");

        // ---- 5. Switch expression + exhaustiveness ----
        for (Day d : Day.values()) System.out.println(d + " -> " + classify(d));

        // ---- 6. var ----
        var map = new java.util.HashMap<String, java.util.List<Integer>>();
        map.computeIfAbsent("a", k -> new java.util.ArrayList<>()).add(1);
        System.out.println("\nvar map = " + map);

        // ---- 7. Text block ----
        System.out.println("""

            {
              "status": "ok"
            }""");
    }

    enum Day { MON, TUE, SAT, SUN }

    // Remove one case and try to compile — the compiler REJECTS it (no default needed)
    static String classify(Day d) {
        return switch (d) {
            case MON, TUE -> "Weekday";
            case SAT, SUN -> "Weekend";
        };
    }
}
```

**Do this experiment:** delete `case SAT, SUN ->` and compile. You get
**`the switch expression does not cover all possible input values`** — a compile error, not a runtime
surprise. That exhaustiveness check is the single best reason to use switch expressions, and it gets
much more powerful with sealed types on Day 042.

## Common mistakes

| Mistake | Correction |
|---|---|
| `%` on possibly-negative values | Sign follows the dividend. Use `Math.floorMod`. |
| `==` on doubles | Compare with a tolerance. |
| `float`/`double` for money | Use `BigDecimal` (Day 042B). |
| `&` instead of `&&` in a condition | Loses short-circuiting, which the null-check idiom depends on. |
| Forgetting `break` in a switch statement | Use the arrow form — fall-through is impossible. |
| `var` where the type isn't obvious | Hurts readability. Use it only when the RHS says the type. |
| Expecting `1.0/0` to throw | It's `Infinity`, and it propagates silently. |

## Interview questions

**Q: What does `-5 % 3` return in Java, and why does it matter?**
> `-2`. The result takes the sign of the dividend. It matters when using modulo to map a hash into a
> bucket range, because a negative hash produces a negative index. `Math.floorMod` gives the
> mathematical result.

**Q: Difference between `&` and `&&`?**
> `&&` short-circuits — if the left operand determines the result, the right isn't evaluated. `&`
> always evaluates both. It's a correctness issue, not just performance: `x != null && x.foo()` relies
> on short-circuiting to avoid an NPE.

**Q: What's the advantage of a switch expression over a switch statement?**
> It produces a value, the arrow form makes fall-through impossible, and with an enum or sealed type
> the compiler enforces exhaustiveness — so adding a new variant and forgetting to handle it becomes a
> compile error instead of a runtime bug.

**Q: Where can you use `var`?**
> Local variables with an initialiser, including loop variables and try-with-resources. Not fields,
> parameters, return types, or without an initialiser. It's compile-time inference, not dynamic
> typing.

**Q: Why doesn't `0.1 + 0.2 == 0.3`?**
> Binary floating point can't represent 0.1 or 0.2 exactly, so each is stored as the nearest
> representable value and the errors accumulate. Compare with a tolerance, and use `BigDecimal` for
> money.
