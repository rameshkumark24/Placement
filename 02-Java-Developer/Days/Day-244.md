# Day 244 🧪

**J-244** · 🧪 **Testing the frontend** — ⭐⭐ behaviour, not implementation

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a frontend test is worth having only if it would fail for a reason a user
> would care about — which rules out testing that a component called `setState`, and rules in testing
> that clicking Save shows a confirmation and that a failed request shows a retry.**
>
> Today: ⭐ the pyramid corrected, testing behaviour, ⭐⭐ mocking at the network boundary, and the
> handful of E2E tests that earn their cost.

---

# Part 1 — The shape

```
⭐⭐ THE FRONTEND PYRAMID IS SQUATTER THAN YOURS

⭐   ⭐ E2E (Playwright) ......... 5–10 total ⇒ ⭐⭐ CRITICAL PATHS
⭐   ⭐⭐ COMPONENT/INTEGRATION ... THE BULK ⇒ render a real tree,
⭐        (Testing Library)         click real things
⭐   ⭐ UNIT ..................... only pure logic ⇒ formatters,
⭐        reducers, validators

⭐   ⇒ ⭐⭐ WHY SQUAT: A COMPONENT IN ISOLATION IS RARELY WHERE THE
⭐     BUG IS. Frontend bugs live in the WIRING — the wrong prop,
⭐     the missing state, the request that never fired.
⭐   ⇒ ⭐ IT IS THE SAME REASON @SpringBootTest / @WebMvcTest CATCHES
⭐     MORE THAN A MOCKITO UNIT TEST OF ONE SERVICE: the wiring is
⭐     where the mistakes are.
```

| ⭐ Worth testing | ⭐⭐ Theatre |
|---|---|
| The form submits and shows a confirmation | ⭐ That a `<Button>` renders its children |
| A failed request shows an error + retry | ⭐⭐ That `useState` was called |
| The empty state appears with zero results | Snapshot tests of whole pages |
| ⭐ Permissions hide the delete button | ⭐ That a `className` is `"btn-primary"` |

> ⭐⭐ **Snapshots deserve their own warning.** A whole-page snapshot fails on every legitimate change,
> so the routine becomes "run `-u`, glance, commit" — **a test that trains people to approve diffs
> without reading them.**

# Part 2 — ⭐⭐ Query the way a user would

```jsx
test("shows an error and lets the user retry", async () => {
  server.use(http.post("/api/orders", () => HttpResponse.error()));
  render(<OrderForm />);

  await userEvent.type(screen.getByLabelText(/email/i), "a@b.com");
  await userEvent.click(screen.getByRole("button", { name: /save/i }));

  expect(await screen.findByRole("alert")).toHaveTextContent(/could not save/i);
  expect(screen.getByRole("button", { name: /retry/i })).toBeEnabled();
});
```

```
⭐⭐ THE QUERY PRIORITY — AND WHY IT IS ALSO AN ACCESSIBILITY TEST

⭐   ① ⭐⭐ getByRole      ⇒ how assistive tech finds it. USE THIS.
⭐   ② getByLabelText     ⇒ form fields
⭐   ③ getByText          ⇒ non-interactive content
⭐   ④ ⭐ getByTestId      ⇒ LAST RESORT.

⭐   ⇒ ⭐⭐ IF YOU CANNOT SELECT IT BY ROLE, A SCREEN READER USER
⭐     PROBABLY CANNOT FIND IT (Day 239).
⭐     ⭐ YOUR TEST SUITE HAS BECOME AN ACCESSIBILITY LINTER FOR FREE.
```

| ⭐ Rule | |
|---|---|
| **`userEvent`, not `fireEvent`** | ⭐ It fires the *real* sequence — pointerdown, focus, keydown, input |
| **`findBy*` for async** | ⭐⭐ Retries until it appears. ⭐ It is Awaitility, built in. |
| **Never assert on state** | ⭐ Assert on what is rendered. State is implementation. |

# Part 3 — ⭐⭐ Mock at the network, not the module

```javascript
// ❌ mocking the module — couples the test to your code's structure
vi.mock("./api", () => ({ getUsers: vi.fn(() => [{id:1}]) }));
// ⭐⭐ RENAME THE FUNCTION AND THE TEST STILL PASSES WHILE THE APP
//    IS BROKEN. It asserted a call, not a behaviour.

// ✅ MSW — intercept the HTTP request itself
const server = setupServer(
  http.get("/api/users", () => HttpResponse.json([{ id: 1, name: "Ada" }])),
);
```

| ⭐ Why the network boundary | |
|---|---|
| **Your code runs unchanged** | ⭐⭐ Wrapper, parsing, error mapping, retry — **all exercised** |
| **Refactors don't break tests** | ⭐ The HTTP contract is what you asserted |
| **Errors are realistic** | ⭐⭐ Return a real 500 with an HTML body and confirm Day 217's wrapper handles it |

> ⭐ **This is the WireMock argument you already accept**: stubbing at the transport tests your client
> code, and mocking the client class tests nothing but your mock. ⭐⭐ MSW is WireMock for the browser.

```javascript
// ⭐⭐ the tests that matter most are the failure ones
http.get("/api/users", () => new HttpResponse(null, { status: 500 }));
http.get("/api/users", () => HttpResponse.json({...}, { status: 403 }));
http.get("/api/users", async () => { await delay(5000); ... });  // ⭐ slow
http.get("/api/users", () => HttpResponse.error());              // ⭐ offline
```

> ⭐ **Most frontend suites test only the success path**, which is the path that already works. **The
> four handlers above are the value** — and they are the four states of Day 240.

# Part 4 — The E2E tests that earn their cost

```
⭐⭐ E2E IS EXPENSIVE: SLOW, FLAKY, FAILS FOR NON-BUG REASONS.
⭐   ⭐ KEEP IT TO PATHS WHERE FAILURE IS UNACCEPTABLE:

⭐   ① ⭐⭐ SIGN UP → LOG IN → LOG OUT
⭐   ② ⭐⭐ THE ONE WORKFLOW YOUR APP EXISTS FOR
⭐   ③ ⭐ PAYMENT / anything irreversible
⭐   ④ ⭐ ONE PERMISSION TEST: the wrong user CANNOT reach the thing
⭐        (Day 236, proved from the outside)

⭐   ⇒ ⭐⭐ 5–10 TESTS. ⭐ A 200-TEST E2E SUITE IS ONE PEOPLE RE-RUN
⭐     UNTIL IT PASSES, WHICH IS THE SAME AS HAVING NONE.
```

| ⭐ Flake control | |
|---|---|
| **Never `waitForTimeout`** | ⭐⭐ Wait for a *condition* — the same rule as never `Thread.sleep`ing in an integration test |
| **Reset state per test** | ⭐ A seeded DB, not "run them in order" |
| **⭐⭐ Trace on failure** | Playwright's trace viewer turns "flaky in CI" into a video |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you test a frontend?"**

Give the filter first. **A test is worth having only if it would fail for a reason a user cares about.
That rules out asserting a component called setState, and rules in that clicking Save shows a
confirmation and that a failed request shows a retry.**

Then the shape, mapped to what you know. **Mostly integration tests that render a real tree and click
real things, only a handful of end-to-end, and unit tests for pure logic. Frontend bugs live in the
wiring — the wrong prop, the missing state, the request that never fired. It's the same reason a
`@WebMvcTest` catches more than a Mockito unit test of one service.**

Then the technique with the free benefit. **I query by role, the way assistive technology does. If I
can't select an element by role, a screen reader user probably can't find it — so the suite becomes an
accessibility linter for free.**

Then mocking, which is where most suites go wrong. **I mock at the network with MSW, not the module —
MSW is WireMock for the browser. A module mock means renaming a function leaves the test passing while
the app is broken; it asserted a call, not a behaviour. Intercepting HTTP means my wrapper, parsing and
retry actually run. And the handlers that matter are the failure ones: a 500 with an HTML body, a 403,
a slow response, and offline. Most suites test only the success path, which is the path that already
works.**

Close on E2E discipline. **Five to ten tests on paths where failure is unacceptable, and never a fixed
sleep — wait for a condition, the same rule as never `Thread.sleep`ing in an integration test.**
