# Part 2 — ⭐ The five that matter most

**⭐ Day 185's ranked short list. If any is ❌, fix it today before anything else.**

```
⭐ 1. Timeouts on every outbound call    — ⭐ prevents total death from someone else's problem
⭐ 2. Liveness/readiness split correctly — ⭐ prevents turning an outage into a crash loop
⭐ 3. Validated configuration            — ⭐ turns a misconfiguration into a rolled-back deploy
⭐ 4. A TESTED restore                   — ⭐⭐ the only failure that is unrecoverable
⭐ 5. Dependency scanning                — ⭐ most breaches are known CVEs
```

**⭐ Item 4 is the only one on the entire list whose failure cannot be recovered from.** Everything
else is downtime; that one is data loss.

# Part 3 — ⭐⭐ The final defence rehearsal

## ⭐ The fifteen-minute walkthrough, recorded

```
⭐ 1.  The problem and the one core flow                       (1 min)
⭐ 2.  The architecture, and ⭐ WHY IT IS THIS SMALL            (1 min)
⭐⭐ 3. THE HARD PROBLEM — the race, the fix, ⭐ THE TEST       (3 min)
⭐ 4.  Auth: five validations, ⭐ reuse detection               (2 min)
⭐ 5.  The outbox: ⭐ the dual write, demonstrated              (2 min)
⭐ 6.  ⭐ Load test: the before/after table                     (2 min)
⭐ 7.  ⭐ Chaos: what you broke and how fast you knew           (2 min)
⭐ 8.  ⭐ What you left out, and what you would do at 100×      (2 min)
```

**⭐ Play it back against five checks:**

| Check | ⭐ Fail signal |
|---|---|
| ⭐ Opened with the **problem**, not the stack | "Spring Boot, PostgreSQL, Redis…" |
| ⭐ **Showed a test**, not a description | you talked about the race |
| ⭐ **Cited numbers** | "it's pretty fast" |
| ⭐ Named a trade-off **unprompted** | only benefits |
| ⭐ Said what you **deliberately did not build** | it sounded finished and unconsidered |

## ⭐ The thirty questions, cold

**⭐ Everything from Days 262 and 270, plus:**

```
⭐ 1. What is your throughput, and what saturated first?
⭐ 2. Show me a performance improvement with numbers.
⭐ 3. How long does a rollback take?
⭐ 4. How long does a restore take?
⭐ 5. Which alerts have you seen fire?
⭐ 6. What happens when the database goes away?
⭐ 7. What did you break on purpose, and what did you learn?
⭐ 8. What is your availability target, and what did it rule out?
⭐ 9. What does it cost to run?
⭐ 10. What would you do at 100× traffic?
```

**⭐ These ten are the ones almost no candidate can answer**, because they require having operated the
system rather than built it. **That is the entire point of Days 281–287.**

```markdown
⭐ # Project — one paragraph: what, who for, why not trivial
⭐ ## The hard problem      ← ⭐ the race, the fix, ⭐ a LINK TO THE TEST
⭐ ## Architecture          ← one diagram, ⭐ and why it is this small
⭐ ## Performance           ← ⭐ THE BEFORE/AFTER TABLE
⭐ ## Running it            ← ⭐ under five minutes from a fresh clone
⭐ ## Decisions             ← ⭐ links to the ADRs
⭐ ## What I left out       ← ⭐ KNOWN-GAPS.md and FUTURE.md
```

**⭐ The hard-problem section goes second, immediately after the pitch.** It is the reason the project
is interesting, and **a link to the two-thread test is the strongest thing on the page.**

## ⭐ The repository contents

```
⭐ docs/adr/          ⭐ every decision, with honest consequences
⭐ docs/RUNBOOK.md    ⭐ every alert
⭐ docs/POSTMORTEM-*  ⭐⭐ the incident you caused deliberately
⭐ docs/KNOWN-GAPS.md ⭐ what is missing and why
⭐ docs/FUTURE.md     ⭐ what you would do next, with measurements behind it
⭐ openapi.yaml       ⭐ diffed in CI
```

**⭐ The postmortem is the differentiator.** Almost no portfolio project contains one, and it
demonstrates something no feature can: **that the system was operated.**
