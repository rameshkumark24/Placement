# Part 1 — The tree and the API

```
⭐⭐ THE DOM IS NOT YOUR HTML. It is a LIVE TREE the browser built
⭐   from your HTML and then kept mutating. View-source shows what
⭐   was SENT; DevTools shows the DOM as it is NOW.
⭐   ⇒ ⭐ they differ the moment any JS runs. ⭐⭐ IF YOU CAME FROM
⭐     THYMELEAF, THIS IS THE SHIFT: the server-rendered page is
⭐     the STARTING STATE, not the page.
```

```javascript
document.querySelector(".item")          // ⭐ first match, or null
document.querySelectorAll(".item")       // ⭐ STATIC NodeList — a snapshot
document.getElementsByClassName("item")  // ⭐⭐ LIVE collection — mutates
                                         //    while you iterate it. Avoid.
                                         //    (≈ iterating a list you're editing
                                         //     without ConcurrentModificationEx)

el.textContent = "safe";                 // ⭐⭐ ALWAYS THIS
el.innerHTML   = userInput;              // ⭐⭐ XSS. Day 243. Never with user data.

el.classList.add("active");              // ⭐ not el.className = — that clobbers
el.dataset.userId                        // reads data-user-id
```

| ⭐ Task | The call |
|---|---|
| Create | `document.createElement("div")` |
| Insert | `parent.append(child)` — ⭐ takes strings *and* nodes |
| Remove | `el.remove()` |
| ⭐⭐ Attribute vs property | `el.getAttribute("value")` is the *initial* HTML; `el.value` is the *current* state. **They diverge as soon as the user types** — the root of half of all form bugs. |

> ⭐ **That last row has no Java analogue and catches everyone once.** The attribute is what the
> server sent; the property is live state. They are two different things with one name.

# Part 2 — Events

```javascript
button.addEventListener("click", (e) => {
  e.preventDefault();     // ⭐ stop the default (form submit, link nav)
  e.stopPropagation();    // ⭐ stop bubbling — sparingly, it hides bugs
});
```

```
⭐⭐ THE THREE PHASES — and only bubbling matters day to day

⭐   CAPTURE   window -> ... -> target   (addEventListener(..., true))
⭐   TARGET    the element itself
⭐   BUBBLE    target -> ... -> window   ⭐ THE DEFAULT

⭐⭐ ⇒ DELEGATION: ONE listener on the container, not 500 on rows.
⭐   list.addEventListener("click", e => {
⭐     const row = e.target.closest("[data-id]");   // ⭐ closest() is the trick
⭐     if (!row) return;
⭐     open(row.dataset.id);
⭐   });
⭐   ⇒ ⭐ works for rows added LATER — no re-binding after a re-render.
⭐     ⭐⭐ REACT USES EXACTLY THIS INTERNALLY.
```

| ⭐ Trap | |
|---|---|
| **Listeners keep objects alive** | ⭐⭐ Every un-removed `addEventListener` on `window`/`document` is a leak holding the whole closure — **a listener leak, exactly like an unclosed resource or an unremoved `ApplicationListener`.** `{ signal }` removes a batch at once. |
| **`e.target` vs `e.currentTarget`** | ⭐ `target` is what was clicked (maybe a child `<span>`); `currentTarget` is what you attached to |
| **Passive listeners** | ⭐ `{ passive: true }` on `scroll`/`touchmove` — the browser need not wait for you before scrolling |

# Part 3 — ⭐⭐ Layout thrashing, the cost model nobody mentions

```
⭐⭐ THE BROWSER BATCHES YOUR WRITES. IT CANNOT BATCH YOUR READS.

⭐   You set 5 styles ⇒ the browser queues them, plans ONE layout.
⭐   ⭐⭐ THEN YOU READ el.offsetHeight — and it must FLUSH everything
⭐     queued and recompute layout SYNCHRONOUSLY to answer.
⭐     That is a FORCED REFLOW.

⭐   ❌ for (const el of rows) {
⭐        el.style.height = (el.offsetHeight + 10) + "px";
⭐      }              ⭐⭐ READ-WRITE-READ-WRITE ⇒ N FORCED REFLOWS
⭐                     ⇒ 500 rows can take SECONDS.

⭐   ✅ const hs = rows.map(el => el.offsetHeight);   // ⭐ READ ALL
⭐      rows.forEach((el,i) => el.style.height = hs[i]+10+"px"); // WRITE ALL
⭐                     ⭐⭐ ONE REFLOW. 100× faster, same output.
```

> ⭐⭐ **This is N+1 queries.** Interleaving cheap operations with a synchronising one turns a batch
> into a loop of round trips — exactly what lazy loading in a loop does to Hibernate. **You already
> know the fix: fetch the set, then process.** Here it is *read all, then write all*.

| ⭐ Forces a reflow when read | |
|---|---|
| `offsetTop/Left/Width/Height`, `clientWidth/Height`, `scrollTop/Height` | `getComputedStyle()`, `getBoundingClientRect()`, `el.focus()` |

# Part 4 — ⭐⭐ Why frameworks exist

Not because the DOM API is verbose. Because of these.

| ⭐ The real problem | What the DOM gives you |
|---|---|
| **State lives in two places** | ⭐⭐ Your JS variable *and* the DOM text both hold "the count". They drift, and nothing tells you. **This is the killer.** |
| **Every update is a manual diff** | You must work out *which* of 40 elements changed and touch exactly those |
| **Handlers must be rebound** | Re-render the list, lose the listeners (unless you delegate) |
| **No composition** | ⭐ There is no unit called "a component" — only functions that happen to make elements |

```
⭐⭐ THE FRAMEWORK'S ONE PROMISE

⭐   ❌ IMPERATIVE:  "the count changed, so find #count and set its text,
⭐                    and toggle the badge, and update aria-label..."
⭐   ✅ DECLARATIVE: "here is what the screen looks like FOR THIS STATE."
⭐                   ⭐⭐ THE FRAMEWORK WORKS OUT THE MINIMAL CHANGES.

⭐   ⇒ ⭐⭐ ONE SOURCE OF TRUTH. The DOM becomes a PROJECTION of state,
⭐     never a place state is STORED. Drift becomes impossible rather
⭐     than merely unlikely.
⭐   ⇒ ⭐ IT IS THE SAME REASON YOU DERIVE A BALANCE FROM ENTRIES
⭐     INSTEAD OF STORING IT ALONGSIDE THEM.
```

> ⭐ **When you genuinely do not need one:** a static page, a form that posts normally, a page with
> three interactions. **Thymeleaf plus a little vanilla JS is smaller, faster, and has no build step
> — and for a server-rendered admin screen it is often the correct call.** Knowing this is a stronger
> answer than defaulting to React, and interviewers ask precisely because most candidates cannot say
> when the framework is wrong.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "why React instead of just the DOM, or Thymeleaf?"**

Reject the shallow answer first. **It isn't that the DOM API is verbose — `querySelector` and `append`
are fine. The real problem is that state ends up living in two places: my JavaScript variable holds the
count and the DOM text holds the count, and nothing keeps them in sync. They drift, and there's no
error when they do.**

Then the promise, in one sentence. **A framework makes the DOM a projection of state rather than a
place state is stored. I describe what the screen looks like for a given state and it works out the
minimal changes — so drift becomes impossible instead of merely unlikely. It's the same reason I derive
a balance from entries instead of storing it alongside them.**

Add the cost model, because it connects to something you already debug. **The DOM batches writes but
can't batch reads, so reading `offsetHeight` forces a synchronous layout recalculation. Interleaving
reads and writes over five hundred rows turned a millisecond of work into seconds — that's N+1 queries
wearing a different hat, and the fix is the same shape: do all the reads, then all the writes.**

Close by naming when not to. **For a server-rendered admin screen with three interactions, Thymeleaf
plus a little vanilla JS is smaller, faster and has no build step. The framework earns its place when
there's enough client state that keeping it in sync by hand becomes the job.**
