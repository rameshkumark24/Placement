# Day 363

**L-363** · Multi-stage builds, image size, and scanning

**Time:** 3 hrs · **Mode:** NEW

> **⭐ A naive Java image is around 800 MB, and roughly 600 MB of it is a compiler and a build tool
> that will never run in production.**
>
> Multi-stage builds delete that in four lines. **But the reason size matters is not disk — it is
> pull time on every node on every deploy, and attack surface you have to keep patched.**

---

# Part 1 — ⭐ Why size matters, precisely

| ⭐ Cost | ⭐ Detail |
|---|---|
| ⭐⭐ **Pull time × nodes × deploys** | ⭐⭐ 800 MB across 50 nodes, ten deploys a day, is real minutes and real bandwidth |
| ⭐ **Scale-out latency** | ⭐ a new node under load waits on the pull before it serves |
| ⭐⭐ **Attack surface** | ⭐⭐ **every package is a CVE you must triage**, even ones you never call |
| Registry storage and egress | multiplied by every tag you keep |
| ⭐ Cold-start time | ⭐ matters most exactly when you are scaling under pressure |

> **⭐ The framing that lands: size is not a tidiness concern, it is a latency and security concern.**
> A 200 MB image scales out four times faster than an 800 MB one **and has a fraction of the packages
> to patch.**

# Part 2 — ⭐⭐ Multi-stage builds

```dockerfile
⭐ ───────── STAGE 1: BUILD (thrown away) ─────────
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn -q dependency:go-offline   ⭐ cached, not a layer
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -q -o package -DskipTests

⭐ ───────── STAGE 2: RUNTIME (shipped) ─────────
FROM eclipse-temurin:21-jre                     ⭐ JRE, not JDK — ⭐ no compiler in production
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar   ⭐ ONLY the artefact crosses the boundary
USER 10001                                       ⭐ never root (Day 361)
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75","-jar","/app/app.jar"]   ⭐ exec form
```

| ⭐ What it achieves | ⭐ Number |
|---|---|
| ⭐⭐ **The build toolchain never ships** | ⭐ Maven, the compiler, the `.m2` cache, the source — **all gone** |
| ⭐ Typical result | ⭐⭐ **~800 MB → ~230 MB** |
| ⭐ **Build secrets cannot leak into the final image** | ⭐ they existed only in a discarded stage (Day 362) |
| ⭐ Stages can be parallel and targeted | `--target build` for CI test stages |

## ⭐⭐ Spring Boot layered jars — the second, larger win

**⭐ A fat jar is one 60 MB file, so one line of code changed means a 60 MB layer to push and pull.**
Boot can explode it into layers ordered by change frequency (Day 144):

```dockerfile
FROM eclipse-temurin:21-jre AS extract
COPY app.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

FROM eclipse-temurin:21-jre
⭐ ORDER MATTERS: least-changing first
COPY --from=extract dependencies/          ./    ⭐ ~50 MB, changes when pom.xml changes
COPY --from=extract spring-boot-loader/    ./
COPY --from=extract snapshot-dependencies/ ./
COPY --from=extract application/           ./    ⭐⭐ ~1 MB, changes EVERY COMMIT
ENTRYPOINT ["java","org.springframework.boot.loader.launch.JarLauncher"]
```

> **⭐ The payoff: a normal code change pushes and pulls about one megabyte instead of sixty.** Across
> a fleet and a day of deploys that is the difference between deploys feeling instant and feeling
> like an event — **and it costs four lines.**

# Part 3 — ⭐ Choosing a base image

| Base | ⭐ Size | ⭐ Trade |
|---|---|---|
| `temurin:21-jdk` | ~450 MB | ⭐ build stage only |
| ⭐ **`temurin:21-jre`** | ⭐ ~230 MB | ⭐ **a sane default — a shell for debugging** |
| `-jre-alpine` | ~170 MB | ⭐⭐ **musl libc — see the warning** |
| ⭐ **`-jre-jammy`/slim** | ~220 MB | fewer packages, glibc |
| ⭐⭐ **distroless java21** | ⭐ ~190 MB | ⭐⭐ **no shell, no package manager — smallest CVE surface** |
| ⭐ **jlink custom runtime** | ⭐⭐ **~80–120 MB** | ⭐ only the JDK modules you use — **the real win** |

⚠️ **Alpine deserves a specific warning for Java.** It uses musl rather than glibc, and that has
produced real, hard-to-diagnose problems: **DNS resolution differences, native library
incompatibilities, and historically worse JVM performance.** Official musl builds exist and are
better now, **but "smaller" is not automatically "better" here** — and being able to say *why* is
what matters.

⚠️ **Distroless has a real operational cost: there is no shell, so `docker exec` gives you nothing.**
That is excellent for security and painful at 3am. **The answer is `:debug` variants for
investigation plus ephemeral debug containers on Kubernetes** — and deciding that consciously rather
than discovering it during an incident.

**⭐ `jlink` is the most Java-specific optimisation and it is underused:** build a runtime containing
only the modules your application actually requires (`jdeps` tells you which). **A typical Spring Boot
app needs a fraction of the full JRE**, and the result is both smaller and has less to patch.

# Part 4 — ⭐⭐ Scanning, and the supply chain

## ⭐ Three things to scan, and they are different

| Layer | ⭐ Finds | ⭐ Tooling |
|---|---|---|
| ⭐ **Base image OS packages** | glibc, openssl, curl CVEs | Trivy, Grype, registry scanning |
| ⭐ **Application dependencies** | ⭐ your jars (Day 100A) | dependency scanning, OWASP, Snyk |
| ⭐ **Configuration** | root user, no limits, writable root | ⭐ Dockle, Hadolint, policy checks |

```
⭐ THE RULE FROM DAY 282, restated:
⭐  1. ⭐ SCAN IN CI on every build — fail on Critical/High with a fixable version
⭐  2. ⭐⭐ SCAN ON A SCHEDULE — ⭐⭐ your image did not change, but the CVE database did
⭐  3. ⭐ Rebuild on base-image updates, automatically
```

> **⭐ Point 2 is the one teams miss.** An image that passed its scan on Monday can be critically
> vulnerable on Friday **without a single byte changing**, because the vulnerability was disclosed in
> between. **A scheduled rescan of what is actually deployed is the control that catches it.**

⚠️ **Failing the build on every Critical is how scanning gets switched off.** Many findings are in
packages your application never invokes, or have no fix available. **The workable policy: fail on
Critical/High *with a fix available*, track the rest with an expiry date, and require an explicit
documented exception** — otherwise the alert becomes noise (Day 338's fatigue argument, applied to
security).

## ⭐ Hardening the final image

```dockerfile
⭐ USER 10001:10001                    ⭐ non-root, numeric (so Kubernetes can verify runAsNonRoot)
⭐ # run with: --read-only --tmpfs /tmp --cap-drop=ALL --security-opt=no-new-privileges
```

| ⭐ Control | |
|---|---|
| ⭐ **Numeric UID, not a name** | ⭐ Kubernetes' `runAsNonRoot` cannot resolve names |
| ⭐ **Read-only root filesystem** | ⭐ plus a tmpfs — **the JVM needs a writable `/tmp`** |
| ⭐ No shell in production images | distroless, if you accept the debugging cost |
| ⭐ **No build tools, no `curl`, no package manager** | ⭐ each is a post-exploitation tool |

## ⭐ SBOM and provenance

| Artefact | ⭐ What it answers |
|---|---|
| ⭐ **SBOM** (SPDX/CycloneDX) | ⭐⭐ **"is Log4Shell in anything we run?" — answerable in seconds instead of a week** |
| ⭐ **Signing** (cosign) | ⭐ this image came from our pipeline |
| Provenance attestation | ⭐ **which commit, which builder, which inputs** |

> **⭐ The SBOM's value is proved by the incident it is for.** When the next Log4Shell lands, the
> question is "which of our 200 images contains it?" — **and generating and storing an SBOM per build
> turns that from an archaeology project into a query.** That is a genuinely persuasive argument to
> make, and it is Day 100A's supply-chain work becoming operational.

```
⭐ MEASURE: image size · pull time on a cold node · CVE count by severity
⭐          ⭐ bytes pushed per code-only change (⭐ layering working?) · build duration
```

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Shipping the JDK and Maven | ⭐⭐ **600 MB of build tooling in production** |
| ⭐ Single-stage builds | source, caches and secrets all ship |
| ⭐ **A fat jar as one layer** | ⭐ 60 MB pushed for a one-line change |
| ⭐ Layered COPY in the wrong order | the cache benefit disappears |
| ⭐ **Alpine for Java without checking** | ⭐ musl DNS and native-library surprises |
| ⭐ Distroless with no debugging plan | ⭐⭐ no shell at 3am |
| ⭐ Named user instead of numeric UID | `runAsNonRoot` cannot verify it |
| ⭐ **Scanning only in CI** | ⭐⭐ the CVE database changes; your image did not |
| ⭐ Failing on every Critical regardless of fixability | ⭐ scanning gets disabled |
| ⭐ **No SBOM** | the next Log4Shell is a week of archaeology |
| Leaving `curl` and a package manager in the image | post-exploitation tooling, pre-installed |
| Optimising size while ignoring layering | you fixed the wrong number |

## Interview questions

**Q: Why does image size matter?**
Not disk — pull time and attack surface. Every deploy pulls the image on every node, so an
eight-hundred-megabyte image makes scale-out slower exactly when you are scaling under load, and
every package in it is a CVE somebody has to triage. A two-hundred-megabyte image is four times
faster to distribute and has a fraction of the patching burden.

**Q: How do multi-stage builds help?**
The build stage has the JDK, Maven and your source; the runtime stage starts from a JRE and copies
only the artefact across. The toolchain never ships — typically eight hundred megabytes down to about
two-thirty — and build-time secrets cannot leak into the final image because they only ever existed
in a discarded stage.

**Q: What is the bigger win for a Spring Boot app?**
Layered jars. A fat jar is a single sixty-megabyte layer, so a one-line change pushes and pulls all
sixty. Extracting it into dependencies, loader, snapshot dependencies and application — copied in
that order — means a normal code change moves about a megabyte. Across a fleet and ten deploys a day
that is the difference between deploys feeling instant and feeling like an event.

**Q: Alpine or distroless?**
Neither by default. Alpine uses musl rather than glibc, which has caused real DNS and native-library
problems for JVM workloads, so "smaller" is not automatically better. Distroless is genuinely good
for attack surface but has no shell, which is painful during an incident unless you have planned for
debug variants or ephemeral debug containers. For most teams a slim glibc JRE is the sane default,
and `jlink` is the underused option — a custom runtime with only the modules you use gets you to
around a hundred megabytes with less to patch.

**Q: How do you handle vulnerability scanning without it becoming noise?**
Scan three separate things — base image packages, application dependencies and configuration — and
scan on a schedule as well as in CI, because an image that passed on Monday can be critical on Friday
without changing. The policy matters more than the tool: fail on Critical and High where a fix
actually exists, track the rest with an expiry and a documented exception. Failing on everything is
how scanning ends up switched off.

## Mini task

1. **Build a single-stage image** for your flagship and record its size. **Convert to multi-stage**
   and record it again.
2. ⭐ Implement **layered jars.** Change one line of code and **measure bytes pushed** before and
   after. **Record both numbers.**
3. ⭐ Deliberately reverse the layered `COPY` order and **confirm the benefit disappears.**
4. ⭐ Build the same app on `jre`, `jre-alpine` and **distroless.** Compare size, then **try
   `docker exec` on each** — feel the debugging cost.
5. ⭐⭐ Build a **`jlink` custom runtime** using `jdeps` output. **Record the size** against the full
   JRE.
6. ⭐ Add a **BuildKit cache mount** for `.m2` and measure the rebuild time saved.
7. ⭐ Run **Trivy** on your image. Categorise findings into fixable and not, and **write the policy
   you would actually enforce.**
8. ⭐⭐ **Generate an SBOM** and answer, from it alone: *"do we ship log4j-core, and which version?"*
9. Run with `--read-only --cap-drop=ALL` and **fix everything that breaks.**
10. ⭐ Set up a **scheduled rescan** of a deployed image and confirm it reports a CVE that did not
    exist at build time.

## 🎙️ Articulation drill

**Two minutes:** *"Our container images are 900 MB and deploys are slow."*

**⭐ Three moves, in order of value.** Multi-stage so the JDK and Maven never ship — most of the
saving, four lines. **Then layered jars, because the real number is not image size but bytes moved
per deploy, and that goes from sixty megabytes to one.** Then base image choice, with the honest
caveat that Alpine is not a free win for the JVM.

**⭐ The marker is measuring the right thing.** *"Total size matters for cold starts; bytes-per-deploy
matters for every deploy — and layering fixes the second, which is the one you feel ten times a
day."*
