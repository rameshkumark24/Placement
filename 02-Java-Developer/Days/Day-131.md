# Day 131

**L-131** · Dependency injection — constructor vs setter vs field

**Time:** 3 hrs · **Mode:** NEW

> Three ways to inject a dependency, and **one correct default**. The argument is not stylistic:
> constructor injection produces objects that cannot exist in an invalid state, and the other two do
> not.
>
> This is Day 091's DIP and Day 034A's immutability, applied.

---

# Part 1 — The three styles

## ⭐ Constructor injection — the answer

```java
@Service
public class OrderService {
    private final OrderRepository repository;      // ⭐ final
    private final PaymentGateway payments;

    public OrderService(OrderRepository repository, PaymentGateway payments) {
        this.repository = Objects.requireNonNull(repository);
        this.payments = Objects.requireNonNull(payments);
    }
}
```

**Since Spring 4.3, `@Autowired` is unnecessary on a single constructor** — the container uses it
automatically. Adding it is noise.

Five properties, and each one is a concrete benefit:

| Property | Why it matters |
|---|---|
| **Fields can be `final`** | Immutable after construction; thread-safe by construction (Day 065's final-field rule) |
| **Cannot exist half-built** | No `NullPointerException` from a dependency that was never set |
| **Dependencies are visible in the signature** | The class documents what it needs |
| **Testable with plain `new`** | No Spring, no reflection, no mocking framework required |
| **Circular dependencies fail at startup** | Loudly, at the right time — see Part 2 |

**The testability point is the strongest one:**

```java
// ✅ constructor injection — a plain unit test
var service = new OrderService(new InMemoryOrderRepo(), new FakeGateway());   // Day 075
```

No `@SpringBootTest`, no context to start, no reflection. **A test that runs in three milliseconds
instead of three seconds** changes how often you run it.

## Setter injection — for genuinely optional dependencies

```java
@Service
public class ReportService {
    private ExportPlugin plugin;                    // cannot be final

    @Autowired(required = false)
    public void setPlugin(ExportPlugin plugin) { this.plugin = plugin; }
}
```

Legitimate only when the dependency is **truly optional** or must be **reconfigurable at runtime**.
Both are rare. The cost is that the object exists before it is complete, so every use must
null-check.

**The modern alternative is better:**

```java
public ReportService(Optional<ExportPlugin> plugin) { … }        // ⭐ explicit optionality
public NotificationService(List<NotificationChannel> channels) { … }  // ⭐ zero or more (Day 090)
```

`Optional<T>` and `List<T>` in the constructor express optionality *and* keep the field final. That
`List<T>` form is Spring's Open/Closed idiom from Day 090 — adding a `@Component` registers it with
no edit anywhere.

## 💀 Field injection — never

```java
@Service
public class OrderService {
    @Autowired private OrderRepository repository;      // 💀
    @Autowired private PaymentGateway payments;         // 💀
}
```

Shorter, and wrong in six ways:

| Problem | Consequence |
|---|---|
| **Cannot be `final`** | Mutable; no final-field safe-publication guarantee |
| **Untestable without reflection** | `new OrderService()` compiles and every field is null |
| **Hides dependency count** | A class with twelve `@Autowired` fields looks tidy — it is not |
| **Only works inside Spring** | The class is unusable as a plain object |
| **Circular dependencies succeed silently** | The problem is hidden rather than surfaced |
| **Reflection sets private fields** | Slower startup, and it is why `final` is impossible |

**The hidden-dependency-count point is the one that damages codebases over time.** Constructor
injection makes an eight-dependency class *look* wrong — a constructor with eight parameters is
visibly a Single Responsibility violation (Day 090). Field injection lets the same class look
perfectly neat, so nobody notices, and it grows to fifteen.

> **The constructor's ugliness is a feature. It is design feedback.** (Day 098's "hard to test means
> badly designed", arriving from another direction.)

Spring itself flags it: **IntelliJ warns "Field injection is not recommended"**, and Spring's own
documentation recommends constructors.

## Lombok

```java
@Service
@RequiredArgsConstructor            // ⭐ generates a constructor for all final fields
public class OrderService {
    private final OrderRepository repository;
    private final PaymentGateway payments;
}
```

Genuinely good: constructor injection with none of the boilerplate. The one caution is that the
generated constructor's *parameter order* follows field declaration order, so reordering fields of
the same type silently swaps arguments in any hand-written call.

# Part 2 — ⭐ Circular dependencies

```java
@Service class A { A(B b) { … } }
@Service class B { B(A a) { … } }
```

```
***************************
APPLICATION FAILED TO START
***************************

The dependencies of some of the beans form a cycle:
   a defined in file [A.class]
┌─────┐
|  a  ← b
└─────┘
```

**With constructor injection this is impossible to build**, because neither object can be constructed
first. Spring fails at startup with a diagram.

**With field injection it succeeds**, because Spring constructs both empty objects and then sets the
fields. **The cycle still exists — you just cannot see it**, and it will surface later as a
partially-initialised object during some other operation.

> **A circular dependency is a design problem, not a wiring problem.** It means two classes have a
> responsibility that belongs to a third, or one direction of the relationship is unnecessary.

## Fixing it properly

```java
// ❌ the workarounds
@Lazy A(B b)                                   // injects a PROXY — defers, does not fix
@Autowired private B b;                        // hides it
spring.main.allow-circular-references=true     // ⚠️ disabled by default since Boot 2.6 — for a reason
```

```java
// ✅ extract the shared responsibility into a third component
@Service class A { A(SharedLogic shared) { … } }
@Service class B { B(SharedLogic shared) { … } }

// ✅ or invert one direction with an event (Spring's ApplicationEventPublisher)
@Service class A {
    private final ApplicationEventPublisher events;
    void doWork() { events.publishEvent(new WorkDone(id)); }    // A no longer knows about B
}
@Service class B { @EventListener void on(WorkDone e) { … } }   // B listens
```

**Boot 2.6 disabled circular references by default**, which broke applications on upgrade — and
correctly so. The fix is to fix the design; the property is a migration aid, not a solution.

# Part 3 — Ambiguity and the annotations that resolve it

```java
public interface PaymentGateway { … }

@Component class StripeGateway  implements PaymentGateway { }
@Component class RazorpayGateway implements PaymentGateway { }

@Service
class OrderService {
    OrderService(PaymentGateway gateway) { … }   // 💥 which one?
}
```

```
NoUniqueBeanDefinitionException: expected single matching bean but found 2
```

Four resolutions, in order of preference (Day 136 covers `@Profile` in full):

```java
// 1. ⭐ @Qualifier — explicit, and the clearest
OrderService(@Qualifier("stripeGateway") PaymentGateway gateway) { … }

// 2. @Primary — a default when one is usually right
@Component @Primary class StripeGateway implements PaymentGateway { }

// 3. Inject ALL of them and choose — Day 090's OCP idiom
OrderService(Map<String, PaymentGateway> gateways) { … }        // name → bean
OrderService(List<PaymentGateway> gateways) { … }               // all, ordered by @Order

// 4. A custom qualifier annotation — type-safe, no string
@Qualifier @Retention(RUNTIME) public @interface Stripe { }
@Component @Stripe class StripeGateway implements PaymentGateway { }
OrderService(@Stripe PaymentGateway gateway) { … }
```

**Option 4 is underused and strictly better than a string qualifier** — a typo becomes a compile
error rather than a startup failure, and refactoring tools follow it.

⚠️ **Matching by parameter name is a fallback that will bite you.** If no qualifier is present, Spring
falls back to matching the bean name against the parameter name — so renaming a constructor parameter
can break wiring. It also requires `-parameters` compilation. Be explicit.

# Part 4 — Injecting values

```java
@Service
public class PaymentService {
    private final String apiKey;
    private final Duration timeout;

    public PaymentService(@Value("${payment.api-key}") String apiKey,
                          @Value("${payment.timeout:5s}") Duration timeout) { … }   // default after :
}
```

**⭐ Prefer typed configuration properties to scattered `@Value`:**

```java
@ConfigurationProperties(prefix = "payment")
@Validated                                                  // ⭐ Day 105's validation, at startup
public record PaymentProperties(
        @NotBlank String apiKey,
        @DefaultValue("5s") Duration timeout,
        @Min(1) @Max(10) int maxRetries) { }

@Service
public class PaymentService {
    private final PaymentProperties props;
    public PaymentService(PaymentProperties props) { … }
}
```

Four reasons this is better, and the last is the important one:

- **Type-safe and grouped** — related settings travel together (Day 096's Data Clumps).
- **Validated at startup** — a missing key fails the application immediately rather than on the first
  payment at 3 AM. That is Day 062's fail-fast, applied to configuration.
- **Documented and discoverable** — IDE autocompletion in `application.yml`.
- **Testable** — construct the record directly, no property source needed.

> **Configuration errors should be startup failures, never runtime failures.** A service that boots
> successfully and then fails on its first real request has hidden the problem until the worst
> moment.

# Part 5 — What injection actually does

Worth knowing, because it explains several behaviours you will meet:

```
1. Scan and register BeanDefinitions            (Day 135)
2. For each singleton, in dependency order:
     a. resolve constructor arguments — recursively creating dependencies
     b. instantiate via reflection
     c. inject fields and setters (if any)
     d. run BeanPostProcessors — ⭐ THIS IS WHERE PROXIES ARE CREATED (Day 137)
     e. call lifecycle callbacks                (Day 133)
3. Publish ContextRefreshedEvent
```

**Two consequences to carry forward:**

**Proxies are created after construction**, at step (d) — so a dependency you inject may be a proxy
rather than the object you expect. That is why `getClass()` on an injected bean can print
`OrderService$$SpringCGLIB$$0`, and it is why Day 137's self-invocation problem exists.

**Constructor arguments are resolved recursively**, so the container computes the correct
construction order from the graph. That is the composition root from Day 130, automated — and it is
also why a cycle is unresolvable.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Field injection | Untestable, non-final, hides dependency count, hides cycles |
| `@Autowired` on a single constructor | Unnecessary since Spring 4.3 |
| Setter injection by default | Objects can exist half-built |
| Working around a cycle with `@Lazy` | Defers the symptom; the design problem remains |
| `allow-circular-references=true` | Re-enables what Boot disabled for good reason |
| Relying on parameter-name matching | Renaming a parameter breaks wiring |
| String `@Qualifier` everywhere | Typos become startup failures; refactoring misses them |
| `@Value` scattered across classes | Ungrouped, unvalidated, undiscoverable |
| Configuration validated lazily | Fails on the first real request instead of at boot |
| Ten constructor parameters treated as normal | It is SRP feedback — split the class |
| Reordering Lombok fields of the same type | Silently swaps arguments at hand-written call sites |

## Interview questions

**Q: Which injection type do you use and why?**
Constructor injection. Fields can be `final`, the object cannot exist half-built, dependencies are
visible in the signature, it is testable with plain `new`, and circular dependencies fail loudly at
startup instead of being hidden.

**Q: What is wrong with field injection?**
Fields cannot be final, the class is untestable without reflection, it works only inside Spring, it
conceals how many dependencies a class has, and it allows circular dependencies to succeed silently
— so a design problem never surfaces.

**Q: Why is a constructor with eight parameters useful information?**
It makes a Single Responsibility violation visible. Field injection lets the same class look tidy,
so nobody notices it growing. The awkwardness is design feedback.

**Q: How do you resolve a circular dependency?**
Fix the design — extract the shared responsibility into a third component, or invert one direction
with an application event. `@Lazy` and `allow-circular-references` defer the symptom without
resolving it, which is why Boot 2.6 disabled the latter by default.

**Q: Two beans implement the same interface. How does Spring choose?**
It does not — it throws `NoUniqueBeanDefinitionException`. Resolve with `@Qualifier`, a `@Primary`
default, a custom qualifier annotation (type-safe, preferred), or by injecting all of them as a
`List` or `Map` and selecting at runtime.

**Q: `@Value` or `@ConfigurationProperties`?**
`@ConfigurationProperties` with `@Validated` — grouped, type-safe, validated at startup, and
discoverable in the IDE. Configuration errors should fail the boot, not the first request.

**Q: When does Spring create proxies?**
In a `BeanPostProcessor` after construction, which is why an injected dependency may be a proxy
rather than the raw object — and why self-invocation bypasses the proxy's behaviour.

## 🎙️ Articulation drill

Two minutes: **"Constructor, setter or field injection — and why?"**

Constructor, and give the reasons as *properties of the object* rather than preferences: final
fields, no half-built state, visible dependencies, testable without a framework, cycles caught at
startup. Then the observation that a large constructor is useful design feedback that field injection
suppresses. Close with `@ConfigurationProperties` and fail-fast configuration, because that is the
same principle applied to values rather than collaborators.
