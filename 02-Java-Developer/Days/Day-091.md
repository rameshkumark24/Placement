# Part 1 — L · Liskov Substitution

## The statement

> **Subtypes must be substitutable for their base types.** Anywhere the program uses a `Base`,
> passing a `Derived` must not break it.

Barbara Liskov's formal version: if `S` is a subtype of `T`, then objects of type `T` may be replaced
with objects of type `S` **without altering any of the desirable properties of the program**.

The compiler enforces *syntactic* substitutability — the method exists with the right signature. LSP
is about **behavioural** substitutability, which the compiler cannot check. That gap is where the
bugs live.

## The canonical example, and why it is actually right

```java
class Rectangle {
    protected int width, height;
    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {          // "a square IS-A rectangle" — mathematically true
    @Override void setWidth(int w)  { this.width = w; this.height = w; }
    @Override void setHeight(int h) { this.width = h; this.height = h; }
}

// A test that passes for Rectangle and fails for Square
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;        // ← Square gives 16
}
```

The lesson people miss: **the mathematical relationship is not the issue. The mutability is.**
`Square` is a perfectly fine subtype of an *immutable* `Rectangle`, because there is no `setWidth`
to violate. IS-A is a statement about *behaviour under the operations the type offers*, not about
taxonomy.

## The four rules that make a subtype safe

Derived from LSP, and these are what to actually say:

| Rule | Meaning |
|---|---|
| **Preconditions cannot be strengthened** | The subtype must not demand more from callers |
| **Postconditions cannot be weakened** | It must not promise less |
| **Invariants must be preserved** | The base type's guarantees must still hold |
| **History constraint** | The subtype must not allow state changes the base forbids |

```java
// ❌ strengthened precondition
class Account       { void withdraw(Money m) { … } }
class SavingsAccount extends Account {
    @Override void withdraw(Money m) {
        if (m.isGreaterThan(Money.of(1000)))
            throw new IllegalArgumentException("max 1000");   // ← base accepted any amount
    }
}
```

Existing code that works with `Account` now throws when handed a `SavingsAccount`. Note Java
*partially* enforces this: an override cannot declare broader checked exceptions or a narrower return
type. It cannot enforce anything about argument *values*, which is exactly where the violation
above lives.

The most famous real violation is in the JDK:

```java
List<String> list = Arrays.asList("a", "b");
list.add("c");        // UnsupportedOperationException — a List that is not a List
```

`Collections.unmodifiableList` and `List.of` do the same. `Arrays.asList` returns a fixed-size list,
so it satisfies the interface syntactically and violates it behaviourally. This is a design mistake
the JDK cannot now fix, and it is a good, honest example to cite.

## How to avoid violating it

- **Prefer composition to inheritance** (Day 092). Most LSP violations are inheritance used for code
  reuse rather than for substitutability.
- **Prefer immutability** — the rectangle problem disappears.
- **Do not override a method to do nothing or to throw.** That is the clearest signal the hierarchy
  is wrong.
- **Write tests against the base type and run them for every subtype.** If a subtype fails the base's
  test suite, you have your answer mechanically:

```java
abstract class AccountContractTest {
    abstract Account createAccount(Money openingBalance);

    @Test void withdrawReducesBalance() {
        Account a = createAccount(Money.of(500));
        a.withdraw(Money.of(200));
        assertEquals(Money.of(300), a.balance());
    }
}
class SavingsAccountTest extends AccountContractTest { … }   // must pass the SAME tests
```

That pattern — an abstract contract test extended per implementation — is the practical enforcement
of LSP, and mentioning it in an interview is unusually strong.

# Part 2 — I · Interface Segregation

> **No client should be forced to depend on methods it does not use.**

```java
// ❌ a fat interface
public interface Worker {
    void work();
    void eat();
    void sleep();
    void attendMeeting();
}

public class RobotWorker implements Worker {
    public void work() { … }
    public void eat()   { throw new UnsupportedOperationException(); }   // ← LSP violation too
    public void sleep() { throw new UnsupportedOperationException(); }
    public void attendMeeting() { … }
}
```

**A fat interface forces LSP violations**, which is why these two principles travel together: the
only way to implement a method you have no meaning for is to break the contract.

```java
// ✅ segregated
public interface Workable { void work(); }
public interface Feedable { void eat(); }
public interface Restable { void sleep(); }

public class HumanWorker implements Workable, Feedable, Restable { … }
public class RobotWorker implements Workable { … }
```

The second, less obvious cost of fat interfaces is **recompilation and redeployment coupling**: every
implementation must change when the interface gains a method, even implementations that do not care.
In a large codebase or a shared library that is a real tax. (Java 8's `default` methods soften it —
that is largely why they exist, to let `Collection` gain `stream()` without breaking every
implementation — but a default that throws is the fat-interface problem again.)

The JDK gets this right in one place worth pointing at: `ReadWriteLock` exposes `readLock()` and
`writeLock()` as separate `Lock` objects rather than one interface with eight methods.

**Where ISP goes wrong:** one-method interfaces everywhere. If a client genuinely uses all six
methods of a repository, six interfaces is worse. **Segregate by client, not by method** — the
question is "which groups of callers use which subsets?"

# Part 3 — D · Dependency Inversion

## The statement

> **High-level modules should not depend on low-level modules. Both should depend on abstractions.**
> **Abstractions should not depend on details. Details should depend on abstractions.**

```java
// ❌ high-level business logic depends on a low-level detail
public class OrderService {
    private final PostgresOrderRepository repo = new PostgresOrderRepository();
    private final SmtpEmailSender email = new SmtpEmailSender();
    // Cannot test without a database and an SMTP server.
    // Cannot change either without editing this class.
}
```

```java
// ✅ both depend on an abstraction owned by the HIGH-level module
public interface OrderRepository {                 // defined next to OrderService
    void save(Order order);
    Optional<Order> findById(OrderId id);
}

public class OrderService {
    private final OrderRepository repo;
    private final NotificationSender notifier;

    public OrderService(OrderRepository repo, NotificationSender notifier) {   // injected
        this.repo = repo;
        this.notifier = notifier;
    }
}

// the DETAIL implements the abstraction
public class PostgresOrderRepository implements OrderRepository { … }
```

**The word "inversion" is the part people miss.** Without DIP, the dependency arrow points from
business logic → database. With DIP, the *database implements an interface the business logic
defines*, so the arrow points inward. Ownership of the interface moves to the high-level module —
that is the inversion.

```
Without DIP:   OrderService ────────────────►  PostgresRepository

With DIP:      OrderService ───► OrderRepository  ◄─── PostgresRepository
                (high level)      (owned by the      (low-level detail)
                                   high level)
```

This is the entire basis of **hexagonal / ports-and-adapters architecture** (Stage 8), and it is why
Spring's constructor injection exists. When Stage 4 shows `@Service` classes taking repository
interfaces in their constructors, it is this principle, not framework convention.

Two things it buys immediately:

- **Testability** — pass a fake or a mock (Day 075) with no infrastructure at all.
- **Deferred decisions** — the persistence choice can change without touching business rules.

**Dependency Injection is not Dependency Inversion.** DI is the *mechanism* (pass dependencies in);
DIP is the *principle* (depend on abstractions the high-level module owns). You can inject a concrete
class and satisfy DI while violating DIP entirely.

**And the caveat:** an interface with exactly one implementation that will never have another is
ceremony. Introduce the abstraction where you have a real reason — a test seam, a genuine second
implementation, or a module boundary you are deliberately protecting.

# Part 4 — D-05 · Normalization

## Why

Day 087's D-04 named the anomalies: redundancy, update inconsistency, insertion anomaly, deletion
anomaly. **Normalization is the systematic removal of them**, driven by functional dependencies.

## The forms

Take this unnormalised table:

```
enrollment(sid, sname, sphone[], cid, cname, instructor, instr_office, grade)
```

### 1NF — atomic values, no repeating groups

`sphone[]` holding `"9876,9877"` violates it. Fix: a separate `student_phone` table (it is a 1:N).

**Every relational table is in 1NF by definition** — the model requires atomic attributes (Day
081's D-02). The interview point is being able to recognise the violation: comma-separated lists,
`phone1`/`phone2`/`phone3` columns, or a JSON blob you then query into.

### 2NF — no partial dependencies

*In 1NF, and every non-key attribute depends on the **whole** key.*

Key is `{sid, cid}`. But `sid → sname` — a non-key attribute depending on *part* of the key. That is
a partial dependency.

```sql
student(sid PK, sname)
course(cid PK, cname, instructor, instr_office)
enrollment(sid, cid, grade, PRIMARY KEY (sid, cid))
```

**2NF only has anything to say when the key is composite.** With a single-attribute key, no partial
dependency is possible.

### 3NF — no transitive dependencies

*In 2NF, and no non-key attribute depends on another non-key attribute.*

In `course`: `cid → instructor` and `instructor → instr_office`, so `cid → instr_office`
transitively. Change an instructor's office and you must update every course they teach.

```sql
course(cid PK, cname, instructor_id FK)
instructor(instructor_id PK, name, office)
```

The classroom formulation is worth memorising:

> **Every non-key attribute depends on the key, the whole key, and nothing but the key — so help me
> Codd.**

### BCNF — the stricter version

*For every dependency X → Y, X must be a superkey.*

3NF permits one exception BCNF does not: a dependency whose determinant is not a superkey but whose
dependent attribute is part of a candidate key.

```
teaching(student, course, instructor)
  { student, course } → instructor        (a student takes a course from one instructor)
  instructor → course                     (each instructor teaches exactly one course)

Candidate keys: {student, course} and {student, instructor}
```

`instructor → course` has a non-superkey determinant, so this is 3NF but not BCNF. The anomaly is
real: you cannot record that an instructor teaches a course until a student enrols.

```sql
instructor_course(instructor PK, course)
student_instructor(student, instructor, PRIMARY KEY (student, instructor))
```

⚠️ **This decomposition is lossless but not dependency-preserving** — `{student, course} → instructor`
can no longer be enforced by a single table's constraints. That trade-off is exactly why 3NF is
often the practical stopping point, and being able to state it is the mark of understanding rather
than memorisation.

| Form | Removes | Test |
|---|---|---|
| 1NF | Repeating groups | Atomic values only |
| 2NF | Partial dependencies | Non-key depends on the *whole* key |
| 3NF | Transitive dependencies | No non-key → non-key |
| BCNF | Remaining determinant anomalies | Every determinant is a superkey |
| 4NF | Multivalued dependencies | Independent multi-valued facts split |
| 5NF | Join dependencies | Rare in practice |

Two guarantees to know by name: a decomposition should be **lossless** (joining the pieces returns
exactly the original — always achievable) and **dependency-preserving** (all FDs enforceable without
a join — always achievable to 3NF, not always to BCNF).

## Deliberate denormalization

> **Normalize until it hurts; denormalize until it works.**

Normalize first, always. Then denormalize *with evidence* — a measured slow query, not an intuition.

| Technique | Buys | Costs |
|---|---|---|
| Duplicate a column to avoid a join | One less join on a hot path | Must be kept in sync |
| Store a computed aggregate (`order_count`) | O(1) instead of a scan | Wrong if an update is missed |
| Materialised view | Pre-joined, indexed | Staleness; refresh cost |
| Historical snapshot on the row | **Correctness**, not speed | Storage |

That last row is the one people misclassify. `order_line.unit_price_at_purchase` looks like
denormalization and is not — the price *when the order was placed* is a genuinely different fact from
today's price. **If the product price changes, historical orders must not change.** Copying it is the
correct model, not an optimisation.

The rules when you do denormalize: write down *why*, make the sync path explicit (a trigger, a
transactional write, or a scheduled reconciliation), and add a check that detects drift. Undocumented
denormalization becomes a data-integrity bug nobody can explain a year later.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Inheriting for code reuse | LSP violations; fragile base class |
| Overriding a method to throw | The clearest possible LSP violation |
| Mutable base types with constrained subtypes | The Rectangle/Square trap |
| Fat interfaces | Forced `UnsupportedOperationException` |
| One method per interface, always | Fragmentation |
| Confusing DI with DIP | Injecting a concrete class satisfies neither goal |
| Interfaces with one permanent implementation | Ceremony |
| Denormalizing without measuring | Complexity with no benefit |
| Denormalizing without a sync path | Silent data drift |
| Stopping at 3NF without knowing why | Cannot defend the choice |

## Interview questions

**Q: Explain LSP with an example.**
A subtype must be behaviourally substitutable, not just syntactically. `Square extends Rectangle`
breaks code that sets width and height independently — and the real culprit is mutability, not the
mathematics. The JDK's own `Arrays.asList().add()` throwing is a live example.

**Q: What are the rules a subtype must obey?**
Preconditions cannot be strengthened, postconditions cannot be weakened, invariants must hold, and
the history constraint must be respected.

**Q: How do you enforce LSP in practice?**
Write a contract test against the base type and run it for every subtype. Prefer composition and
immutability so the situation does not arise.

**Q: What is Interface Segregation and how does it relate to LSP?**
Clients should not depend on methods they do not use. A fat interface forces implementations to
throw for methods they cannot support — which is an LSP violation. Segregate by client, not by
method.

**Q: What is being "inverted" in Dependency Inversion?**
The direction of the dependency and the *ownership of the interface*. The high-level module defines
the abstraction and the low-level detail implements it, so the arrow points inward instead of
outward.

**Q: Is Dependency Injection the same as Dependency Inversion?**
No. DI is the mechanism for supplying dependencies; DIP is the principle that both sides depend on
an abstraction the high-level module owns. Injecting a concrete class is DI without DIP.

**Q: What is BCNF, and why do people stop at 3NF?**
BCNF requires every determinant to be a superkey. The BCNF decomposition is always lossless but not
always dependency-preserving, so enforcing some constraints would require a join — a real cost, which
is why 3NF is often the practical stopping point.

**Q: When would you denormalize?**
With measured evidence of a problem, a documented reason, an explicit sync mechanism and a drift
check. And note that storing a historical value like the price at purchase is not denormalization at
all — it is a different fact.
