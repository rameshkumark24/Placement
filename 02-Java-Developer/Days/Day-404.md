# Day 404

**L-404** · RabbitMQ — and when it beats Kafka

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ In RabbitMQ, acknowledging a message deletes it. In Kafka, acknowledging moves a number. Every
> other difference between the two — replay, redelivery, priority, routing, retention — follows from
> that one line.**
>
> Today: exchanges and routing as a genuine capability, **the prefetch default that lets one consumer
> take everything**, quorum queues (which are Raft, ten days early), and **an honest table of when
> RabbitMQ is the better tool.**

---

# Part 1 — ⭐⭐ The model, and the one difference that generates the rest

```
⭐⭐ RABBITMQ:  producer → EXCHANGE → (binding, routing key) → QUEUE → consumer → ack → ⭐⭐ DELETED
⭐⭐ KAFKA:     producer → TOPIC PARTITION (append) → consumer reads at an OFFSET → ⭐⭐ DATA REMAINS
```

| ⭐ Because the broker owns the message | ⭐ Because the log owns the message |
|---|---|
| ⭐⭐ **per-message ack, nack and requeue** | ⭐⭐ **replay from any offset, at any time** |
| ⭐⭐ **priority queues** | ⭐⭐ **many independent consumer groups, free** |
| ⭐⭐ **per-message TTL and delayed delivery** | ⭐⭐ retention as a product feature |
| ⭐⭐ **complex routing** (topic/fanout/headers) | ⭐ ordering per key, at volume |
| ⭐ consumers scale independently of partitions | ⭐⭐ **stream processing over history** |
| ⭐⭐ **no replay — once acked, it is gone** | ⭐⭐ **no per-message redelivery or priority** |

> **⭐ Neither is "better".** RabbitMQ is a **smart broker with dumb consumers**; Kafka is a **dumb log
> with smart consumers.** Almost every comparison question is really asking whether you understand that
> sentence.

## ⭐ Exchanges — routing as infrastructure

| Exchange | ⭐ Routing |
|---|---|
| ⭐ **direct** | ⭐ exact routing key match — a plain work queue |
| ⭐⭐ **topic** | ⭐⭐ pattern match: `order.*.eu`, `payment.#` — **the useful one** |
| ⭐ **fanout** | broadcast to every bound queue |
| headers | match on header attributes; rarely worth it |

```
⭐⭐ WHAT TOPIC EXCHANGES BUY YOU, concretely:
⭐   publish "order.created.eu"
⭐   ⇒ queue "eu-fulfilment"  bound to  order.*.eu
⭐   ⇒ queue "all-audit"      bound to  order.#
⭐   ⇒ queue "created-only"   bound to  order.created.*
⭐   ⇒ ⭐⭐ THE BROKER decides who gets what. Adding a consumer is a BINDING, not a code change.
⭐   ⇒ ⭐⭐ In Kafka this is either separate topics or filtering in every consumer.
```

# Part 2 — ⭐⭐ Prefetch: the default that ruins your load balancing

```
⭐⭐ basicQos(prefetch) = how many UNACKED messages one consumer may hold.

⭐⭐ prefetch = 0 (unlimited, the naive default in some clients):
⭐   ⇒ ⭐⭐ the FIRST consumer to connect grabs the ENTIRE queue into its local buffer
⭐   ⇒ ⭐⭐ every other consumer sits IDLE while one is overloaded
⭐   ⇒ ⭐⭐ and if it dies, thousands of messages redeliver at once
⭐   ⇒ ⭐ Symptom: "we added consumers and nothing got faster."

⭐⭐ prefetch = 1  ⇒ ⭐ perfect fairness, ⭐⭐ but a network round trip per message — slow
⭐⭐ prefetch = 10–100 ⇒ ⭐⭐ the practical range. ⭐ Tune with: prefetch ≈ throughput × latency.
```

| ⭐ Ack modes | |
|---|---|
| ⭐⭐ **Manual ack after processing** | ⭐⭐ at-least-once — **the correct default** |
| ⭐ `autoAck=true` | ⭐⭐ acked on delivery — **at-most-once, silent loss** (Day 402's auto-commit, again) |
| ⭐ `basicNack(requeue=true)` | ⭐⭐ **infinite redelivery loop if the failure is permanent** |
| ⭐⭐ `basicNack(requeue=false)` | ⭐⭐ **routes to the dead letter exchange — this is what you want** |

⚠️ **`requeue=true` on a poison message is RabbitMQ's version of the blocked partition**, except it spins
instead of blocking: the message is redelivered instantly, fails instantly, forever, **burning CPU and
filling logs.** Always requeue with a bounded count, or nack to a DLX.

## ⭐ Retries with delay — the TTL + DLX trick

```
⭐ RabbitMQ has no native delayed delivery (without a plugin). ⭐⭐ The standard recipe:
⭐   1. nack(requeue=false) ⇒ message goes to ⭐ "retry.5s" queue
⭐   2. ⭐⭐ "retry.5s" has message-TTL 5000 and NO consumer, with its DLX pointing BACK to the work queue
⭐   3. ⭐⭐ the message expires ⇒ dead-letters ⇒ lands back in the work queue, 5 seconds later
⭐   ⇒ ⭐ chain retry.5s → retry.1m → retry.10m → ⭐⭐ final DLQ, alarmed.
```

**⭐ Note the shape is identical to Kafka's retry topics** (Day 402) — **different mechanism, same
pattern.** Delayed retry is a distributed-systems idiom, not a product feature.

# Part 3 — ⭐⭐ Quorum queues: Raft, ten days early

| | ⭐ Classic mirrored queues | ⭐⭐ Quorum queues |
|---|---|---|
| Status | ⭐⭐ **deprecated/removed** | ⭐⭐ **the default choice now** |
| Replication | ad-hoc mirroring | ⭐⭐ **Raft consensus** (Day 410) |
| ⭐ Split brain | ⭐⭐ possible, with silent divergence | ⭐⭐ **impossible — majority wins** |
| ⭐ Requires | — | ⭐⭐ **an odd number of nodes; a majority must be up** |
| Trade-off | faster, unsafe | ⭐ slower per message, **correct** |
| ⭐ Poison handling | manual | ⭐ built-in `delivery-limit` |

> **⭐ Quorum queues are the same trade as Kafka's `min.insync.replicas=2`: the queue refuses to accept
> writes rather than accept them unsafely when a majority is unavailable.** Every serious messaging
> system eventually arrives at "a majority must agree", **which is why Day 410 exists.**

| ⭐ Other operational realities | |
|---|---|
| ⭐⭐ **Queues are not for storage** | ⭐⭐ a deep queue degrades the broker; RabbitMQ is happiest near-empty |
| ⭐ Lazy queues / message paging | ⭐ for deep backlogs, at a latency cost |
| ⭐⭐ **Memory/disk alarms** | ⭐⭐ the broker **blocks publishers** when memory is high — backpressure that reaches your request thread |
| ⭐ Connections vs channels | ⭐ one connection per process, **a channel per thread** — never share channels |
| ⭐ Publisher confirms | ⭐⭐ without them, `basicPublish` is fire-and-forget — **the message may never have arrived** |

⚠️ **"Publisher confirms off" is the RabbitMQ equivalent of `acks=0`.** The default publish is
asynchronous and unconfirmed; **enable confirms for anything that matters**, and handle the negative
confirm.

# Part 4 — ⭐⭐ The choice, made properly

| ⭐ Choose **RabbitMQ / SQS** | ⭐ Choose **Kafka** |
|---|---|
| ⭐⭐ **a work queue with competing consumers** | ⭐⭐ **replay is a requirement** |
| ⭐⭐ per-message retry, priority, delay, TTL | ⭐⭐ **several independent consumers of one stream** |
| ⭐⭐ **complex routing decided by the broker** | ⭐ ordering per key at high volume |
| ⭐ RPC-style request/reply | ⭐ retention as a feature ("replay last Tuesday") |
| ⭐ consumer count independent of any partition count | ⭐⭐ **stream processing / event sourcing substrate** |
| ⭐ low operational appetite | ⭐ you already run it and have the expertise |

```
⭐⭐ THE TWO-QUESTION SHORTCUT:
⭐   1. ⭐⭐ "Will anyone ever need to REPLAY this?"                  ⇒ yes ⇒ ⭐⭐ Kafka
⭐   2. ⭐⭐ "Do I need per-message priority, delay or redelivery?"   ⇒ yes ⇒ ⭐⭐ RabbitMQ
⭐   ⇒ ⭐ Both yes? ⭐⭐ Use both — this is extremely common and not a failure of design.
⭐   ⇒ ⭐ Neither, and you are on AWS? ⭐⭐ SQS. Zero operations (Day 393).
```

> **⭐ And the honest third option: many teams should use neither yet.** A database table with a status
> column and a polling worker is a perfectly good queue **up to a few thousand messages a minute**, and
> it has no new operational surface. **The outbox pattern (Day 407) starts exactly there.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Unlimited prefetch** | ⭐⭐ one consumer takes the whole queue; adding consumers does nothing |
| ⭐ prefetch=1 for throughput work | ⭐ a round trip per message |
| ⭐⭐ **`autoAck=true`** | ⭐⭐ at-most-once — silent loss on crash |
| ⭐⭐ **`nack(requeue=true)` on a permanent failure** | ⭐⭐ an instant infinite redelivery spin |
| ⭐ No DLX, no alarm | failures vanish |
| ⭐⭐ **No publisher confirms** | ⭐⭐ publish is fire-and-forget; messages silently never arrive |
| ⭐ Sharing a channel across threads | ⭐ channels are not thread-safe |
| ⭐⭐ **Using a queue as storage** | ⭐⭐ deep queues degrade the broker; memory alarms block publishers |
| ⭐ Classic mirrored queues today | ⭐⭐ deprecated; split brain is possible |
| ⭐ An even number of quorum nodes | ⭐ no majority benefit, more cost |
| ⭐⭐ **Choosing Kafka for a work queue** | ⭐⭐ operational weight for capability you never use |
| ⭐ Choosing RabbitMQ when replay is required | it cannot, at all |
| Introducing a broker before a database table is inadequate | new operational surface for nothing |

## Interview questions

**Q: What is the fundamental difference between RabbitMQ and Kafka?**
Acknowledging in RabbitMQ deletes the message; acknowledging in Kafka moves a number. Everything else
follows. Because the broker owns the message, RabbitMQ can do per-message acknowledgement, redelivery,
priority, per-message TTL and delayed delivery, and rich routing decided centrally. Because the log owns
the message, Kafka can replay from any point, support many independent consumer groups for free, and
treat retention as a feature. The shorthand I use is that RabbitMQ is a smart broker with dumb consumers,
and Kafka is a dumb log with smart consumers.

**Q: A team added consumers to a RabbitMQ queue and throughput did not improve. Why?**
Prefetch. If the quality-of-service prefetch is unlimited, the first consumer to connect pulls the entire
queue into its local buffer, so every other consumer sits idle waiting for messages that have already
been dispatched. It also means a crash redelivers thousands of messages at once. Prefetch of one gives
perfect fairness but costs a network round trip per message, so the practical range is tens, tuned
roughly as throughput times processing latency.

**Q: How do you do delayed retries in RabbitMQ?**
There is no native delayed delivery without a plugin, so the standard recipe uses TTL and dead lettering.
Nack the message without requeue so it dead-letters into a retry queue that has a message TTL and no
consumer, with its own dead letter exchange pointing back at the work queue. The message sits there until
it expires, then dead-letters back into the work queue — a delay implemented entirely with expiry. Chain
several with increasing TTLs and terminate in a real dead letter queue with an alarm. It is structurally
the same as Kafka's retry topics, which is a sign that delayed retry is an idiom rather than a product
feature.

**Q: What are quorum queues?**
Replicated queues built on Raft, and now the default choice since classic mirrored queues were
deprecated. Because writes require a majority, split brain is impossible and the queue refuses to accept
messages rather than accept them unsafely when a majority is unavailable — exactly the same trade as
Kafka's minimum in-sync replicas. They are slower per message than mirrored queues and require an odd
node count. It is a good illustration that every serious messaging system converges on "a majority must
agree".

**Q: Kafka or RabbitMQ for a new system?**
Two questions decide it. Will anyone ever need to replay this stream — if yes, Kafka, because RabbitMQ
cannot at all. Do I need per-message priority, delay or redelivery — if yes, RabbitMQ, because Kafka
cannot without contortions. If both, using both is common and not a design failure. If neither and I am
on AWS, SQS, because it has no operational surface. And there is an honest fourth answer: at low volume,
a database table with a status column and a polling worker is a perfectly good queue with no new
infrastructure, and the outbox pattern starts exactly there.

1. ⭐⭐ Set **unlimited prefetch** with three consumers and **watch one take everything.** Then tune it.
2. ⭐ Measure throughput at prefetch 1, 10 and 100. **Plot it.**
3. ⭐ Use `autoAck=true`, kill the consumer mid-processing, and **count the lost messages.**
4. ⭐⭐ Nack with `requeue=true` on a permanently failing message and **watch the instant spin.** Then fix
   it with a DLX.
5. ⭐⭐ Build the **TTL + DLX delayed retry chain**: 5s → 1m → 10m → DLQ. Alarm on the DLQ.
6. ⭐ Build a **topic exchange** with three bindings and prove the broker routes correctly with **no
   consumer-side filtering.**
7. ⭐⭐ Turn on **publisher confirms** and prove that without them a publish to a full/blocked broker is
   silently lost.
8. ⭐⭐ Create a **quorum queue**, stop a minority of nodes and confirm it works; stop a majority and
   confirm it **refuses** rather than diverges.
9. ⭐ Fill the broker's memory and **watch publishers get blocked** — backpressure reaching your request
   thread.
10. ⭐⭐ Take one real requirement from your flagship and **answer the two-question shortcut** in writing,
    including why the other option is wrong.

## 🎙️ Articulation drill

**Two minutes:** *"Kafka or RabbitMQ?"*

**⭐ Refuse to rank them and give the generative difference instead: an ack in RabbitMQ deletes the
message, an ack in Kafka moves a number. From that alone you can derive everything — RabbitMQ gets
per-message redelivery, priority, delay and broker-side routing; Kafka gets replay, many independent
consumer groups, and retention as a feature.**

**⭐ Then decide it with two questions: will anyone ever need to replay this, and do I need per-message
priority or delay? Both yes means using both, which is common. Neither, on AWS, means SQS.**

**⭐ And the answer that shows judgement rather than knowledge: at low volume, neither — a table with a
status column and a polling worker is a perfectly good queue with no new operational surface, and that is
exactly where the outbox pattern begins.**
