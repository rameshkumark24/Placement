# Day 347

**L-347** · Design 3 — a distributed rate limiter as a service

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Every other system in this stage is allowed to take 50 milliseconds. This one is on the path
> of every request in the company, so its budget is under one millisecond.**
>
> That single constraint eliminates most designs before you draw them — **and it is why the correct
> answer is approximate enforcement, which sounds wrong until you say why.**

---

# Part 1 — ⭐ Requirements, and the constraint that decides everything

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| Allow/deny a request against a rule | ⭐⭐ **p99 latency < 1 ms — it is on every request** |
| ⭐ **Multiple rules per request** (per-IP, per-user, per-endpoint) | ⭐⭐ **availability > that of everything it protects** |
| ⭐ Rules changeable without a deploy | ⭐ accuracy: **approximate is acceptable** — see below |
| Return `retryAfter` and remaining quota | ⭐ scale: 1M checks/s across the fleet |
| ⭐ Per-tenant plans and quotas | ⭐ fail-open or fail-closed, **per rule** |

```
⭐ ESTIMATE
⭐   500k requests/s to the platform, ⭐ ~3 rules checked each ⇒ ⭐⭐ 1.5M checks/s
⭐   Distinct keys: 10M users + 50M IPs ⇒ ⭐ tens of millions of counters
⭐   State per counter: ~50 B ⇒ ⭐ a few GB — ⭐ fits in memory, easily
```

> **⭐ Two conclusions, said out loud.** The state is small and fits in RAM — **so this is not a
> storage problem.** And 1.5 million checks a second at a 1 ms budget means **a network round trip
> per check is a large fraction of the budget** — which is what makes the central-store design, the
> obvious one, the wrong default.

⚠️ **The availability requirement is the one candidates miss.** A limiter with 99.9% availability in
front of a 99.99% service **has made the platform less available.** It must be more reliable than
what it protects, **which argues for it being a library or a sidecar rather than a remote service.**

---

# Part 2 — ⭐ The shape: library, sidecar, or service

| ⭐ Form | ⭐ Latency | ⭐ Trade |
|---|---|---|
| ⭐⭐ **In-process library** | ⭐⭐ **microseconds** | ⭐ one per language; upgrades need redeploys |
| ⭐ **Sidecar** (Day 341) | ⭐ ~0.2 ms (localhost) | ⭐ language-agnostic; a proxy per pod |
| ⭐ Remote service | ⭐⭐ **1–5 ms — usually blows the budget** | ⭐ central, easy to operate, **and a new SPOF** |
| ⭐ **At the gateway** (Day 341) | free — already in the path | ⭐ only for edge rules, not internal ones |

> **⭐ The recommendation: rules are evaluated in-process or in a sidecar; a central service owns the
> rules and the global counters, and is never on the request path.** That separation — **decision
> local, coordination remote** — is the design.

---

# Part 3 — ⭐⭐ The deep dive: local decisions with global truth

```
⭐ Each instance holds LOCAL token buckets (Day 314) for the keys it has seen.
⭐ Every ~100 ms it reports consumption to a central counter and receives an updated ALLOWANCE.

⭐   instance A ──usage──►┐
⭐   instance B ──usage──►│ ⭐ AGGREGATOR (sharded by key) ──► redistributes allowance
⭐   instance C ──usage──►┘
```

## ⭐ The allowance algorithm

```
⭐ Global limit for key K: 1000/min. ⭐ Three instances currently seeing traffic for K.

⭐ NAIVE: each gets 333.       ⭐ ✗ if traffic is 90/5/5, instance A is throttled at 333
⭐                              ⭐   while 660 of the global budget goes unused.

⭐⭐ WEIGHTED BY OBSERVED DEMAND:
⭐   each instance reports its consumption rate; the aggregator allocates in proportion,
⭐   ⭐ holds back a small reserve, and instances that exhaust their share request more.
⭐   ⇒ ⭐ converges within a sync interval; ⭐ overshoot is bounded by (reserve + one interval)
```

| ⭐ Property | ⭐ Value |
|---|---|
| ⭐ **Decision latency** | ⭐⭐ **a local memory lookup — microseconds** |
| ⭐ **Accuracy** | ⭐ exact over a minute; **may briefly overshoot by roughly one sync interval's traffic** |
| ⭐ Coordination cost | ⭐ **one message per instance per interval**, not per request |
| ⭐ **On aggregator failure** | ⭐⭐ **instances keep using their last allowance — Day 339's static stability** |

> **⭐ That last row is the strongest point available in this design.** The aggregator being down does
> **not** take the limiter down; each instance continues enforcing its last-known share. **The system
> degrades from "globally accurate" to "locally accurate", which is exactly the right failure
> mode** — and it is a genuine example of static stability rather than a slogan.

## ⭐ When exact enforcement is required

**⭐ Some limits are not policies — they are invariants.** Login attempts, one-time-passcode sends,
free-tier hard caps that cost money.

```
⭐ For those: a central atomic operation (Day 208's Lua), accepting the round trip.
⭐ ⭐ And say the trade: you accept ~1 ms and a dependency, because being wrong costs more than being slow.
```

**⭐ So the real design has two tiers**, and naming them is the mature answer:

| Tier | ⭐ Mechanism | ⭐ Used for |
|---|---|---|
| ⭐ **Approximate** (default) | local buckets + async reconciliation | API throttling, fairness, abuse damping |
| ⭐ **Exact** | ⭐ central atomic increment | ⭐ **security and money limits** |

# Part 4 — ⭐ Rules, sharding, and failure

## ⭐ Rules as data (Day 290, again)

```json
{ "id": "api-per-user", "match": {"path": "/api/*"}, "key": "user:{userId}",
  "limit": 1000, "window": "1m", "burst": 200, "priority": 10, "onFailure": "open" }
```

| ⭐ Requirement | ⭐ Design |
|---|---|
| ⭐ **Change a limit without deploying** | rules pushed from config; hot-reloaded |
| ⭐ **Several rules per request** | ⭐⭐ **check ALL, consume from ALL only if all pass** (Day 314) |
| ⭐ Precedence | most specific wins; evaluate in priority order |
| ⭐ **Rollout safety** | ⭐ a "shadow" mode that records what *would* have been blocked |

⚠️ **Shadow mode is the detail that shows operational sense.** A new rule that would have blocked 30%
of a customer's traffic must be discovered **in a metric, not in an incident** — and that is exactly
Day 291's shadow-mode idea reappearing.

## ⭐ Sharding the aggregator

| ⭐ Concern | ⭐ Answer |
|---|---|
| ⭐ Which node owns a key | ⭐ **consistent hashing** on the key (Day 326) |
| ⭐ **A hot key** — one tenant is 40% of traffic | ⭐⭐ **consistent hashing does not help; split the key across sub-counters** and sum |
| Rebalancing | ⭐ counters are ephemeral — **losing one shard's state means brief over-allowance, not corruption** |
| Persistence | ⭐ **none needed** — this is derived state with a one-minute memory |

> **⭐ "The state is disposable" is worth saying explicitly.** It removes durability, backup and
> replication from the design entirely, **and it is why losing a shard is a minor event.**

## ⭐ Failure, and bottlenecks

| ⭐ Failure | ⭐ Behaviour |
|---|---|
| ⭐ Aggregator down | ⭐ **last allowance retained** — degrade to local enforcement |
| ⭐⭐ **Rule store down** | ⭐⭐ **keep the last known rules in memory — never fail because config is unreachable** |
| ⭐ Central store down (exact tier) | ⭐ **fail closed for security limits, open for throttling** — per rule (Day 336) |
| A limiter bug | ⭐ **a global kill switch that disables enforcement** — and it must be tested |

```
⭐ MONITOR: check latency p99 · ⭐ SHED/BLOCK RATE as a first-class SLI (Day 336)
⭐          allowance convergence time · aggregator staleness · ⭐ blocks per tenant
⭐ CUT:     a UI, historical analytics, per-request quota accounting
⭐ AT 10×:  more aggregator shards; ⭐ nothing structural — the request path never changed
```

---

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ A remote call per check | ⭐⭐ **1–5 ms on every request in the company** |
| ⭐ A limiter less available than what it protects | ⭐ **you reduced platform availability** |
| ⭐ Equal allowance split | ⭐ throttling one instance while the global budget is unused |
| ⭐ **Consuming before all rules pass** | tokens spent on rejected requests (Day 314) |
| ⭐ Unbounded key map | a memory leak (Day 314) — bound it with an LRU |
| ⭐ Consistent hashing offered for a hot key | ⭐ wrong tool; split the key |
| ⭐ **Failing because the rule store is unreachable** | ⭐⭐ config unavailability becomes an outage |
| One global fail-open/closed policy | security limits and throttling need opposite answers |
| ⭐ No shadow mode | a new rule blocks a customer in production |
| ⭐ Persisting counters | ⭐ durability for state with a one-minute lifetime |
| No kill switch | a limiter bug has no fast remedy |

## Interview questions

**Q: What is the hard constraint here?**
Latency. This sits on every request in the company, so the budget is under a millisecond, and a
network round trip per check consumes most of it. That single fact eliminates the obvious design — a
central service asked on every request — and pushes the decision in-process or into a sidecar, with
a central component that owns rules and global counters but is never on the request path.

**Q: How do you enforce a global limit without a global lookup?**
Local token buckets with periodic reconciliation. Each instance reports consumption every hundred
milliseconds and receives an allowance weighted by observed demand rather than split evenly, because
an even split throttles the busy instance while most of the global budget goes unused. Overshoot is
bounded by the reserve plus one sync interval, and that is acceptable because a rate limit is a
policy rather than an invariant.

**Q: When is approximate not acceptable?**
When the limit is a security or money control — login attempts, one-time passcode sends, hard
free-tier caps. Those get a central atomic operation and pay the round trip, because being wrong
costs more than being slow. So the design has two tiers, and knowing which limits belong in which is
the actual judgement.

**Q: What happens when your aggregator dies?**
Nothing dramatic. Instances keep enforcing their last-known allowance, so the system degrades from
globally accurate to locally accurate rather than failing. That is static stability — it keeps
working from state it already has instead of needing something to happen during the failure. The same
applies to the rule store: the last known rules stay in memory, because a limiter that fails when its
config is unreachable has turned a config outage into a platform outage.

**Q: One tenant is forty percent of your traffic. What happens to your sharding?**
Their key hashes to one aggregator shard, and consistent hashing does not help because that is
precisely what hashing does. I split the key into sub-counters — the same key-splitting fix as a hot
cache key — and sum them, accepting a little extra reconciliation. The state is disposable anyway, so
rebalancing is cheap: losing a shard means brief over-allowance, not corruption.

2. ⭐ Implement the **central-store** design and **measure p99 check latency.** Compare with the same
   check done in-process.
3. ⭐ Implement **local buckets with reconciliation.** Run three instances with 90/5/5 traffic split
   and **compare even allocation against demand-weighted.**
4. ⭐ **Measure the overshoot**: drive traffic at 3× the limit and count how many requests were
   allowed above the global cap. **Vary the sync interval and plot it.**
5. ⭐⭐ **Kill the aggregator under load** and confirm enforcement continues from the last allowance.
6. Implement two-tier rules and **verify the exact tier holds a hard cap precisely** across three
   instances.

8. ⭐ Make one key 40% of traffic; **saturate one shard**, then split the key and re-measure.
9. ⭐ Implement **shadow mode.** Deploy a deliberately harsh rule and confirm it blocks nothing while
   reporting what it would have blocked.

    for a test drive.**

## 🎙️ Articulation drill

**Three minutes:** *"Design a rate limiter used by every service in the company."*

**⭐ Lead with the constraint, not the algorithm.** *"This is on the path of every request, so the
budget is under a millisecond and the availability must exceed everything it protects — which rules
out asking a remote service per check."* **Everything else follows from that sentence.**

**⭐ Then the two markers**: demand-weighted local allowance with bounded overshoot, and **the
two-tier split** — approximate for throttling, exact for security and money. **Candidates who give
one uniform mechanism have not noticed that "1000 API calls a minute" and "5 login attempts" are
different kinds of rule.**
