# Part 1 — ⭐⭐ There is no global "now"

| ⭐ Source of error | ⭐ Magnitude |
|---|---|
| ⭐ NTP synchronisation | ⭐ typically **1–50 ms**, worse on a busy or virtualised host |
| ⭐⭐ **NTP corrections** | ⭐⭐ **the clock can JUMP — forwards or BACKWARDS** |
| ⭐ VM pauses / live migration | ⭐ hundreds of ms of frozen or skipped time |
| ⭐ Leap seconds | ⭐⭐ historically, entire outages |
| ⭐⭐ **A badly configured host** | ⭐⭐ **minutes or hours out, and nothing tells you** |

```
⭐⭐ THE JAVA DISTINCTION THAT IS ABOUT CORRECTNESS, NOT STYLE:
⭐   ⭐⭐ System.currentTimeMillis()  ⇒ wall clock. ⭐⭐ NOT MONOTONIC — can go BACKWARDS.
⭐   ⭐⭐ System.nanoTime()           ⇒ monotonic. ⭐⭐ Meaningless as a date; correct for DURATIONS.
⭐
⭐   ⭐⭐ long start = System.currentTimeMillis();  ... ⭐⭐ NTP steps the clock back 40 ms ...
⭐   ⭐⭐ long took  = System.currentTimeMillis() - start;   ⇒ ⭐⭐ NEGATIVE DURATION.
⭐   ⇒ ⭐ Your timeout fires immediately, or never. Your latency metric records -40.
⭐ ⇒ ⭐⭐ RULE: currentTimeMillis for "what time is it", nanoTime for "how long did that take".
```

## ⭐⭐ Last-write-wins loses data, quietly

```
⭐   Node A (clock +8 ms): write X="blue"   at t=1000
⭐   Node B (clock −3 ms): write X="green"  at t=1002   ⭐⭐ ACTUALLY LATER IN REAL TIME
⭐   ⇒ stamped: A = 1008, ⭐⭐ B = 999
⭐   ⇒ ⭐⭐ LWW keeps A. ⭐⭐ The genuinely later write is SILENTLY DISCARDED.
⭐ ⇒ ⭐ This is Cassandra's and DynamoDB's default conflict resolution.
⭐   ⭐⭐ It is not a bug — it is a documented trade you are supposed to have understood.
```

| ⭐ When LWW is acceptable | ⭐ When it is not |
|---|---|
| ⭐ Caches, sessions, presence | ⭐⭐ **counters, balances, sets, shopping carts** |
| ⭐ Idempotent full-object overwrites by one owner | ⭐⭐ **anything where two writers can be concurrent** |
| ⭐ Data you can recompute | ⭐ anything where a lost write is a lost order |

# Part 2 — ⭐⭐ Happened-before, and logical clocks

```
⭐⭐ LAMPORT'S HAPPENED-BEFORE (→), the foundation of everything here:
⭐   a → b  if:  ⭐ a and b are in the same process and a came first
⭐               ⭐ OR a is a send and b is the matching receive
⭐               ⭐ OR transitively through a chain
⭐   ⭐⭐ If NEITHER a → b NOR b → a, the events are CONCURRENT.
⭐   ⇒ ⭐⭐ "Concurrent" does NOT mean simultaneous. It means CAUSALLY UNRELATED —
⭐     ⭐⭐ neither could have influenced the other. That is the useful definition.
```

## ⭐ Lamport clocks — a counter, and its limit

```
⭐ Each process keeps a counter L:
⭐   on any local event:  L = L + 1
⭐   on send:             attach L
⭐   on receive:          ⭐⭐ L = max(L, received) + 1

⭐ ✅ ⭐⭐ GUARANTEE: a → b implies L(a) < L(b).
⭐ ❌ ⭐⭐ THE CONVERSE IS FALSE: L(a) < L(b) does NOT mean a → b.
⭐ ⇒ ⭐⭐ So you get a total order, but you CANNOT DETECT CONFLICTS —
⭐   two concurrent writes just get different numbers and one looks "later".
```

## ⭐⭐ Vector clocks — detecting concurrency

```
⭐ Each process keeps a VECTOR of counters, one per node: [A:2, B:5, C:1]
⭐   local event: increment your own
⭐   on receive:  ⭐⭐ element-wise max, then increment your own

⭐⭐ COMPARING:
⭐   V1 < V2  (every element ≤, at least one <)   ⇒ ⭐ V1 happened-before V2
⭐   V1 > V2                                       ⇒ ⭐ V2 happened-before V1
⭐   ⭐⭐ NEITHER                                    ⇒ ⭐⭐ CONCURRENT ⇒ A GENUINE CONFLICT
⭐
⭐   [A:2,B:1] vs [A:1,B:2] ⇒ ⭐⭐ neither dominates ⇒ ⭐⭐ two SIBLINGS. Both are real writes.
```

| ⭐ Cost | |
|---|---|
| ⭐⭐ **Size grows with the number of writers** | ⭐ pruning is needed, and pruning risks false ordering |
| ⭐⭐ **Your application must resolve siblings** | ⭐⭐ **Dynamo returned both values to the client — the shopping cart merge** |
| ⭐ Version vectors | ⭐ the per-object variant most systems actually use (Riak, Voldemort) |

> **⭐⭐ The famous example is worth carrying: Amazon's cart merged siblings by union, so a concurrent
> "remove item" could resurrect a deleted item.** That is not a bug in vector clocks — **it is the
> correct behaviour of the merge function they chose**, and it shows that conflict *detection* is the
> easy half; **conflict *resolution* is a domain decision.**

# Part 3 — ⭐ Hybrid clocks and TrueTime

| Approach | ⭐ Idea |
|---|---|
| ⭐⭐ **HLC (hybrid logical clock)** | ⭐⭐ physical time in the high bits, a logical counter in the low bits — **close to wall clock, and never goes backwards** |
| ⭐ Used by | ⭐ CockroachDB, MongoDB, YugabyteDB |
| ⭐⭐ **TrueTime (Spanner)** | ⭐⭐ **atomic clocks and GPS give a bounded uncertainty interval `[earliest, latest]`** |
| ⭐⭐ **Commit-wait** | ⭐⭐ **Spanner WAITS OUT the uncertainty (~7 ms) before acknowledging a commit** |
| ⭐ What that buys | ⭐⭐ external consistency: if T1 commits before T2 starts, T1's timestamp really is smaller |

> **⭐ The lesson from TrueTime is not "buy atomic clocks".** It is that **Google bought certainty with
> latency** — deliberately delaying every commit by the clock uncertainty. **Nobody else gets to skip
> that trade; they just hide it in a weaker guarantee.**

# Part 4 — ⭐⭐ What you should actually do

```
⭐⭐ THE PRACTICAL RULES, for systems that will never implement a vector clock:

⭐ 1. ⭐⭐ NEVER order events across machines by wall clock.
⭐ 2. ⭐⭐ Use a VERSION NUMBER per entity, and compare-and-swap on it.
⭐      UPDATE orders SET status=?, version=version+1 WHERE id=? AND version=?
⭐      ⇒ ⭐⭐ rowsAffected = 0 means someone else wrote first. ⭐⭐ THIS DETECTS THE CONFLICT.
⭐ 3. ⭐⭐ Use an IDEMPOTENCY KEY per operation, so retries are safe (Day 398, 407).
⭐ 4. ⭐ Use a SEQUENCE from a single source when you need a real order — a database sequence,
⭐      a Kafka offset (Day 401), a stream version (Day 405).
⭐ 5. ⭐ Use nanoTime for durations, currentTimeMillis for timestamps, and NEVER mix them.
⭐ 6. ⭐ Timestamps are for HUMANS and reporting. ⭐⭐ Versions are for CORRECTNESS.
```

| ⭐ Distributed id generation | |
|---|---|
| ⭐ **UUIDv4** | ⭐ no coordination; **random, so it destroys index locality** |
| ⭐⭐ **UUIDv7 / ULID** | ⭐⭐ **time-prefixed and sortable — the modern default**, keeps B-tree inserts local |
| ⭐ **Snowflake** | ⭐ timestamp + machine id + sequence — sortable, compact |
| ⭐⭐ **Snowflake's failure** | ⭐⭐ **if the clock goes backwards, ids repeat** — implementations must **refuse to issue** until time catches up |
| ⭐ Database sequence | ⭐ perfectly ordered, and a coordination point |

⚠️ **The Snowflake clock-drift failure is the concrete cost of everything above.** A node whose clock
steps backwards can mint ids it already issued. **Correct implementations block rather than emit — and
that means an id generator can refuse to work because NTP corrected the clock**, which is exactly the
kind of failure that only makes sense once you accept there is no global now.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Ordering cross-machine events by wall clock** | ⭐⭐ skew silently reverses the order |
| ⭐⭐ **`currentTimeMillis()` for durations** | ⭐⭐ negative elapsed times; timeouts that fire wrongly |
| ⭐ `nanoTime()` treated as a date | ⭐ it has no epoch |
| ⭐⭐ **Last-write-wins on data with concurrent writers** | ⭐⭐ silent, undetectable data loss |
| ⭐ Not knowing your database's default is LWW | ⭐ it is, in Cassandra and DynamoDB |
| ⭐ Thinking "concurrent" means "at the same time" | ⭐⭐ it means causally unrelated |
| ⭐ Believing Lamport order implies causality | ⭐⭐ only the forward implication holds |
| ⭐ Vector clocks without a resolution strategy | ⭐⭐ detection is easy; resolution is a domain decision |
| ⭐ Union-merging siblings blindly | ⭐ deleted items resurrect |
| ⭐ Pruning vector clocks carelessly | false ordering conclusions |
| ⭐⭐ **UUIDv4 as a clustered primary key** | ⭐⭐ random inserts destroy index locality — use v7/ULID |
| ⭐ Snowflake without clock-regression handling | ⭐⭐ duplicate ids |
| Using timestamps for correctness | versions are for correctness |

## Interview questions

**Q: Why can you not order events by timestamp across machines?**
Because clocks disagree. NTP typically leaves you tens of milliseconds apart, corrections can step a clock
backwards, virtual machines pause and resume, and a misconfigured host can be wildly wrong with nothing
reporting it. So two writes five milliseconds apart can be stamped in the wrong order, and if your
conflict resolution is last-write-wins the genuinely later write is silently discarded. That is the
default in Cassandra and DynamoDB — not a bug, a documented trade you are expected to have understood.
For ordering you need something that does not depend on physical clocks: a version per entity, a
sequence, or a log offset.

**Q: What is the difference between `currentTimeMillis` and `nanoTime`?**
`currentTimeMillis` is the wall clock, which is meaningful as a date and is not monotonic — it can jump
forwards or backwards when NTP corrects. `nanoTime` is monotonic but has no epoch, so it is meaningless
as a date and only valid for measuring durations. Using the wall clock to measure elapsed time can
produce negative durations, which turns into timeouts that fire immediately or never and latency metrics
with impossible values. The rule is wall clock for "what time is it", monotonic for "how long did that
take", and never subtract one kind from the other.

**Q: What does "concurrent" mean in a distributed system?**
Not "at the same time" — causally unrelated. Under Lamport's happened-before relation, one event precedes
another if they are in the same process in order, or one is a send and the other the matching receive, or
transitively. If neither precedes the other, they are concurrent, meaning neither could have influenced
the other. That is the useful definition, because concurrent events are exactly the ones that can
genuinely conflict, and any two writes that are causally ordered do not need conflict resolution at all.

**Q: Lamport clocks or vector clocks?**
A Lamport clock is a single counter that guarantees if a happened before b then a's counter is smaller —
but not the converse, so you get a total order and you cannot detect conflicts; two concurrent writes just
get different numbers and one appears later. Vector clocks keep a counter per node, so comparing them
gives three outcomes rather than two: one dominates, the other dominates, or neither, which means
genuinely concurrent. That third outcome is the point. The cost is that the vector grows with the number
of writers and your application has to resolve siblings — which is a domain decision, as Amazon's cart
showed when union-merging resurrected deleted items.

**Q: How do you handle ordering in a system you are actually building?**
I do not use time for correctness. Every entity gets a version number and updates are compare-and-swap on
it, so a zero-row update tells me someone else wrote first — conflict detected, cheaply, with no clocks
involved. Operations get idempotency keys so retries are safe. Where I need a real order I take it from a
single source: a database sequence, a Kafka offset, a stream version. And for identifiers I use UUIDv7 or
ULID rather than v4, because time-prefixed ids stay sortable and keep index inserts local. Timestamps
still exist — for humans and reporting — but they never decide who wins.

## 🎙️ Articulation drill

**Two minutes:** *"Two nodes write to the same key. Who wins?"*

**⭐ Start by rejecting the obvious answer: not "whoever has the later timestamp", because clocks disagree
by tens of milliseconds and can step backwards — so last-write-wins can silently discard the genuinely
later write, and that is the documented default in Cassandra and DynamoDB.**

**⭐ The correct question is whether the writes are causally related or concurrent. Vector clocks answer
that: if neither dominates, they are genuinely concurrent and you have a real conflict, at which point
detection is done and resolution is a domain decision — Amazon's cart merged siblings by union, which
resurrected deleted items, and that was the merge function's fault rather than the clock's.**

**⭐ For a system I am building, I do not use time for correctness at all: a version per entity with
compare-and-swap detects the conflict cheaply, idempotency keys make retries safe, and any real ordering
comes from a single source like a sequence or a log offset. Timestamps are for humans; versions are for
correctness.**
