# Day 149

**L-149** · Global exception handling — Day 104's error contract, implemented

**Time:** 3 hrs · **Mode:** NEW

> Day 104 designed the error contract: **RFC 7807 `application/problem+json`**, a stable `type` URI,
> a human `title`, a per-occurrence `detail`, and machine-readable extensions. Day 145 showed exactly
> where in the request chain an exception can be caught — and where it cannot.
>
> Today those combine into one `@RestControllerAdvice` that produces a consistent error for every
> failure mode, and an honest account of the three places this approach does not reach.

---

# Part 1 — The default, and why it is unacceptable

Throw a `RuntimeException` from a handler and Boot returns:

```json
{
  "timestamp": "2026-08-14T10:23:45.123+00:00",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/api/orders/42"
}
```

Three problems, in ascending order of importance:

1. **No machine-readable code.** A client cannot distinguish "out of stock" from "payment declined"
   from "database down" — all 500s with identical bodies.
2. **Different shapes for different failures.** A validation error, a 404 and a 500 all produce
   different JSON. Every client writes three parsers.
3. **⭐ And when you "fix" it badly, it leaks.** Turning on `server.error.include-message=always` and
   `include-stacktrace=always` — which people do while debugging and forget — publishes exception
   messages and stack traces to the internet. That is Day 119's information disclosure: table names,
   internal hostnames, library versions and file paths, handed to an attacker for free.

**`include-stacktrace` must be `never` in production. Non-negotiable.**

# Part 2 — The advice

Boot 3 ships `ProblemDetail`, so RFC 7807 needs no custom class.

```java
@RestControllerAdvice
class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);
    private static final URI BASE = URI.create("https://api.acme.com/problems/");

    // ── 1. Domain: not found ──────────────────────────────────────────
    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException e) {
        var p = ProblemDetail.forStatusAndDetail(NOT_FOUND, e.getMessage());
        p.setType(BASE.resolve("order-not-found"));       // ⭐ stable, documented, versioned
        p.setTitle("Order not found");
        return p;
    }

    // ── 2. Domain: business rule violated ─────────────────────────────
    @ExceptionHandler(InsufficientStockException.class)
    ProblemDetail stock(InsufficientStockException e) {
        var p = ProblemDetail.forStatusAndDetail(UNPROCESSABLE_ENTITY, e.getMessage());
        p.setType(BASE.resolve("insufficient-stock"));
        p.setTitle("Insufficient stock");
        p.setProperty("productId", e.productId());        // ⭐ extension members
        p.setProperty("available", e.available());
        return p;                                          // client can act on this
    }

    // ── 3. Body validation (Day 148) ──────────────────────────────────
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail invalidBody(MethodArgumentNotValidException e) {
        var p = ProblemDetail.forStatusAndDetail(BAD_REQUEST, "Request validation failed");
        p.setType(BASE.resolve("validation-error"));
        p.setTitle("Validation failed");
        p.setProperty("errors", e.getBindingResult().getFieldErrors().stream()
                .map(f -> Map.of("field", f.getField(), "message", f.getDefaultMessage()))
                .toList());                                // ⭐ ALL errors, not the first
        return p;
    }

    // ── 4. ⭐ Param/path validation — the different exception ─────────
    @ExceptionHandler(ConstraintViolationException.class)
    ProblemDetail invalidParam(ConstraintViolationException e) {
        var p = ProblemDetail.forStatusAndDetail(BAD_REQUEST, "Request validation failed");
        p.setType(BASE.resolve("validation-error"));
        p.setProperty("errors", e.getConstraintViolations().stream()
                .map(v -> Map.of("field", v.getPropertyPath().toString(),
                                 "message", v.getMessage()))
                .toList());
        return p;
    }

    // ── 5. Malformed JSON ─────────────────────────────────────────────
    @ExceptionHandler(HttpMessageNotReadableException.class)
    ProblemDetail unreadable(HttpMessageNotReadableException e) {
        var p = ProblemDetail.forStatusAndDetail(BAD_REQUEST, "Request body is malformed");
        p.setType(BASE.resolve("malformed-request"));
        return p;                                          // ⭐ e.getMessage() would leak class names
    }

    // ── 6. Optimistic locking (Day 165) ───────────────────────────────
    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    ProblemDetail conflict(ObjectOptimisticLockingFailureException e) {
        var p = ProblemDetail.forStatusAndDetail(CONFLICT,
                "The resource was modified by another request. Re-read and retry.");
        p.setType(BASE.resolve("concurrent-modification"));
        return p;                                          // ⭐ retryable — say so
    }

    // ── 7. ⭐ The catch-all ───────────────────────────────────────────
    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception e, HttpServletRequest req) {
        String correlationId = MDC.get("correlationId");   // Day 127
        log.error("Unhandled exception cid={} path={}", correlationId, req.getRequestURI(), e);
        var p = ProblemDetail.forStatusAndDetail(INTERNAL_SERVER_ERROR,
                "An unexpected error occurred.");           // ⭐ nothing internal
        p.setType(BASE.resolve("internal-error"));
        p.setProperty("correlationId", correlationId);      // ⭐ the whole trick
        return p;
    }
}
```

## ⭐ The catch-all is the most important handler, for two reasons

**It logs everything and tells the client nothing.** The stack trace, the SQL, the internal hostname
— all in your logs. The client gets a sentence and a correlation ID.

**And the correlation ID closes the loop.** A customer reports "I got an error, ID `7f3a-...`". You
run one query against your log store and see the exact stack trace, the exact request, the exact
downstream call. Day 127 built the plumbing; **this handler is the payoff, and it is the single
highest-value line in the whole file.**

Without it you get support tickets saying "it broke around 3pm" and you go log-diving. Day 104
promised this; today delivers it.

## `ErrorResponseException` — the shortcut for the simple cases

```java
throw new ErrorResponseException(HttpStatus.NOT_FOUND,
        ProblemDetail.forStatusAndDetail(NOT_FOUND, "Order %s not found".formatted(id)), null);
```

Boot renders it as `problem+json` without an advice entry. Useful for one-offs; a handler per
*domain* exception type is still better, because it keeps the `type` URIs and titles in one file
where they can be reviewed against the published error catalogue.

## Extending `ResponseEntityExceptionHandler`

```java
@RestControllerAdvice
class GlobalExceptionHandler extends ResponseEntityExceptionHandler { ... }
```

Gives you framework-exception handling (405, 415, 406, unreadable body) already mapped to
`ProblemDetail`, with `protected` hooks to override. **Worth it** — but note the gotcha: its methods
return `ResponseEntity<Object>` with a different signature than the plain `@ExceptionHandler` style,
so you override rather than add, and mixing the two conventions carelessly is where people end up
with two handlers for the same exception.

# Part 3 — Status code selection, which is where most people slip

| Situation | Status | Note |
|---|---|---|
| Malformed JSON, wrong type, missing required param | **400** | the request is not parseable/bindable |
| Not authenticated | **401** | ⭐ historically misnamed "Unauthorized" — it means *unauthenticated* |
| Authenticated, not permitted | **403** | Day 111's distinction |
| Resource does not exist | **404** | ⭐ **also use for "exists but you may not see it"** — Day 119's IDOR mitigation. A 403 confirms existence |
| Method not allowed | **405** | framework |
| `Accept` unsatisfiable | **406** | Day 145 step 6 |
| Version conflict, duplicate create | **409** | |
| `If-Match` failed | **412** | Day 102 |
| Payload too large | **413** | |
| `Content-Type` unsupported | **415** | Day 145 step 1 |
| **Well-formed but semantically invalid / business rule** | **422** | ⭐ see below |
| Rate limited | **429** | with `Retry-After` — Day 122 |
| Unexpected | **500** | never with detail |
| Downstream failed | **502/503/504** | with `Retry-After` on 503 |

**⭐ 400 vs 422 is the distinction interviewers probe.** 400 means *I could not parse or bind your
request*. 422 means *I understood you perfectly and I am refusing*. "Insufficient stock", "credit
limit exceeded", "order not cancellable in status SHIPPED" are all 422. Using 400 for both means the
client cannot tell "fix your code" from "tell the user why".

**The honest caveat:** 422 comes from WebDAV and some API styles use 400 throughout. Either is
defensible — *inconsistency* is not. Pick one, document it, apply it everywhere.

# Part 4 — ⭐ The three places `@RestControllerAdvice` does not reach

This is the part most write-ups omit, and it is exactly what Day 145's diagram predicts.

### 1. Exceptions thrown in filters

A JWT filter throwing on an expired token throws **outside the DispatcherServlet**, so no
`HandlerExceptionResolver` runs. Your advice never sees it and the client gets a whitelabel HTML page
from a JSON API.

**Fix — write the problem JSON in the filter itself:**

```java
} catch (JwtException e) {
    var p = ProblemDetail.forStatusAndDetail(UNAUTHORIZED, "Token invalid or expired");
    p.setType(URI.create("https://api.acme.com/problems/invalid-token"));
    response.setStatus(401);
    response.setContentType("application/problem+json");
    objectMapper.writeValue(response.getOutputStream(), p);
    return;                                                  // ⭐ do not continue the chain
}
```

### 2. Spring Security's 401 and 403

Also filters. They are produced by `AuthenticationEntryPoint` and `AccessDeniedHandler`, which must be
configured separately (Day 169) or you get Security's default body — inconsistent with everything
else your API returns.

### 3. Errors after the response has started

Day 147's case: an exception thrown *during* serialization, after the status line and headers are
committed. Nothing can change the status to 500 — the bytes are gone. The client sees a 200 with
truncated JSON.

**There is no handler-level fix. The fix is not to serialize things that can fail** — which is
Day 147's DTO argument, and `open-in-view: false` so the failure appears in your tests rather than in
production.

### And the two adjacent gaps

- **404 for an unmapped URL** never reaches a handler (Day 145 step 1) unless you set
  `spring.mvc.throw-exception-if-no-handler-found: true` — the default in Boot 3.2+ — which converts
  it into a `NoResourceFoundException` your advice can catch.
- **`@Async` and `@Scheduled` methods** run off the request thread entirely. No advice, no MDC, and by
  default an uncaught exception in a `@Scheduled` method is logged and swallowed. Day 177.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `include-stacktrace=always` in production | Day 119 information disclosure |
| `e.getMessage()` in the response | leaks SQL, table names, internal hosts |
| No catch-all handler | one unmapped exception type and the contract breaks |
| Catch-all without a correlation ID | support cannot connect a report to a log line |
| Handling only `MethodArgumentNotValidException` | param violations return 500 (Day 148) |
| Returning the first validation error only | client fixes one field per round trip |
| 400 for business rule violations | client cannot distinguish "bad code" from "tell the user" |
| 403 for another tenant's resource | confirms it exists — IDOR oracle |
| Advice expected to catch filter exceptions | Day 145 — it is outside the servlet |
| Security 401/403 left as default | inconsistent error shape on the two most common failures |
| Unstable `type` URIs | clients key off them; changing one is a breaking change (Day 109) |

## Interview questions

**Q: How do you handle errors consistently across an API?**
One `@RestControllerAdvice` producing RFC 7807 `problem+json` with a stable `type` URI per error
class, plus extension members clients can act on. A catch-all that logs the full exception and
returns a sentence and a correlation ID. And separate wiring for the paths advice cannot reach —
security's entry point and deny handler, and any custom filter.

**Q: 400 or 422?**
400 when I could not parse or bind the request; 422 when I understood it and am refusing on a
business rule. The distinction tells the client whether to fix the request or show the user a
message. Either convention is defensible if applied consistently.

**Q: Why doesn't your advice catch the JWT filter's exception?**
Because filters run outside the DispatcherServlet, so no `HandlerExceptionResolver` is involved. The
filter has to write the problem JSON itself.

**Q: What goes in a 500 response?**
A generic sentence and a correlation ID. Everything else goes to the logs. The correlation ID is what
turns a support ticket into a single log query.

## 🎙️ Articulation drill

Two minutes: **"How do you do error handling in a Spring Boot API?"**

One advice, RFC 7807, stable type URIs, extension members that let a client act. A catch-all that
logs everything and returns a correlation ID — and say why that ID matters, because it turns "it
broke this afternoon" into one log query. Then demonstrate depth by naming the boundary: advice only
covers what happens inside the DispatcherServlet, so filter exceptions and Spring Security's 401 and
403 need their own wiring, and a failure during serialization cannot be rescued at all.
