# Day 304

**L-304** · DDD I — ubiquitous language, entities, and value objects

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Domain-driven design is usually taught as a bag of patterns. It is not. It is one claim: the
> code should use the words the business uses, meaning exactly what the business means.**
>
> Everything tactical — entities, value objects, aggregates — exists to make that possible. **And the
> single highest-yield technique in the whole of LLD comes from here: make illegal states
> unrepresentable.**

---

# Part 1 — ⭐ The ubiquitous language

**⭐ The rule: one word, one meaning, one bounded context, and the code uses it.** If the business says
"consignment", there is a class called `Consignment` — not `ShipmentDTO2`, not `OrderData`.

| Symptom | ⭐ What it means |
|---|---|
| ⭐ **Translation in every meeting** ("what you call an account, we call a customer") | ⭐ two contexts collided (Day 305) |
| ⭐ A class named `OrderInfo`, `OrderData`, `OrderDetails` alongside `Order` | ⭐ **nobody knows what the concepts are** |
| Business says "approve", code says `setStatus(2)` | ⭐ the language is lost at the boundary |
| ⭐ **A term that means two things in one codebase** | ⭐ **guaranteed bug — it is Day 298's connascence of meaning** |

**⭐ The `Info`/`Data`/`Details` suffix test is the fastest read of a codebase's health.** Those
suffixes mean "another version of a thing we could not name", and each one is a concept that was
never modelled.

> **⭐ The interview version: the strongest thing you can say about a design is that a domain expert
> could read the class names and method names and recognise their own job.** `order.ship()` passes.
> `orderService.updateStatus(order, 3)` does not.

# Part 2 — ⭐ Entities vs value objects

| | ⭐ Entity | ⭐ Value object |
|---|---|---|
| ⭐ **Identity** | ⭐ **has an id; survives change** | ⭐ **is its value** |
| Equality | ⭐ by id (Day 158) | ⭐ **by all fields** (Day 040) |
| Mutability | ⭐ changes over time | ⭐ **immutable — always** |
| Example | `Order`, `Customer`, `Account` | `Money`, `Address`, `DateRange`, `EmailAddress`, `OrderId` |
| Lifecycle | created, changes, archived | ⭐ created and discarded |
| ⭐ **Test** | ⭐ "if every field changed, is it still the same thing?" | ⭐ "if any field changed, is it a different one?" |

**⭐ The identity test decides it, and the answer is contextual — which is the interesting part:**

- ⭐ A **£10 note** is a value object to a shop (any £10 note will do) and an **entity** to the
  central bank (serial numbers are tracked). **Same real-world thing, different context, different
  model.** That is Day 305's bounded contexts arriving early.
- ⭐ A **seat** is a value object in a cinema listing and an entity during booking.

## ⭐ Value objects are the highest-yield change you can make

**⭐ Primitive obsession is the number one LLD smell**, and it produces bugs the compiler was capable
of preventing:

```java
// ⭐ Before — every one of these is a bug waiting for a swap
void transfer(String fromAccount, String toAccount, BigDecimal amount, String currency) { }
transfer(to, from, amount, currency);        // ⭐ compiles. Runs. Wrong.

// ⭐ After — the compiler now enforces the domain
void transfer(AccountId from, AccountId to, Money amount) { }
transfer(to, from, money);                   // ⭐ still compiles — same type. See below.
```

⚠️ **Honest caveat: value objects fix *type* confusion, not *role* confusion.** `from` and `to` are
both `AccountId`, so a swap still compiles. **The fix for that is a command object with named fields
(Day 302) or a builder** — and knowing this limit is what separates someone who has used the
technique from someone who has read about it.

```java
public record Money(BigDecimal amount, Currency currency) implements Comparable<Money> {

    public Money {                                            // ⭐ compact constructor = the invariant
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        if (amount.scale() > currency.getDefaultFractionDigits())
            throw new IllegalArgumentException("Too many decimal places for " + currency);
    }

    public Money plus(Money other) {
        requireSameCurrency(other);                           // ⭐ THE rule, in ONE place, forever
        return new Money(amount.add(other.amount), currency);
    }

    public Money times(int qty) { return new Money(amount.multiply(BigDecimal.valueOf(qty)), currency); }

    private void requireSameCurrency(Money other) {
        if (!currency.equals(other.currency))
            throw new CurrencyMismatch(currency, other.currency);
    }
}
```

**⭐ What that one record deleted from the rest of the codebase:**

| Deleted | ⭐ Where it used to live |
|---|---|
| ⭐ **Currency-mismatch checks** | ⭐ every place two amounts met — or, more often, nowhere |
| ⭐ **`double` for money** | ⭐ Day 042B's fatal bug, now structurally impossible |
| Rounding decisions | scattered; now one policy |
| ⭐ **`null` amounts** | ⭐ rejected at construction — cannot exist |
| ⭐ `amount` and `currency` drifting apart | ⭐ **they are one value now** |

> **⭐ The general principle: a value object is where you put a rule so that it cannot be forgotten.**
> Not "so it is tidy" — **so that no future caller, in any file, at any hour, can skip it.**

## ⭐ Records, and the two things they do not give you

**Java records (Day 042) are close to a purpose-built value-object syntax** — final fields,
value-based `equals`/`hashCode` (Day 040's contract, correct by construction), and a compact
constructor for invariants. **Two gaps:**

1. ⭐ **Records are shallowly immutable.** `record Order(List<Item> items)` hands out the same mutable
   list. **Copy defensively in the compact constructor** (Day 034A) — `items = List.copyOf(items)`.
2. ⭐ **No validation happens on deserialization paths that bypass constructors.** Jackson uses the
   canonical constructor, so it is fine; **reflection-based frameworks and JPA are not.**

# Part 3 — ⭐⭐ Make illegal states unrepresentable

**⭐ The most valuable idea in this stage, and it is not a DDD-specific one.**

```java
// ⭐ Representable but illegal: a shipped order with no shipping date.
class Order {
    OrderStatus status;
    Instant shippedAt;      // ⭐ null when shipped? shipped when null? nothing says.
    String trackingNumber;  // ⭐ meaningful only sometimes
}
```

**⭐ Three techniques, in increasing strength:**

| Technique | ⭐ Prevents |
|---|---|
| ⭐ **Validate in the constructor** | an object existing in an invalid state |
| ⭐ **Named transitions, no setters** | ⭐ **an object being *moved* into an invalid state** |
| ⭐ **Sealed types per state** | ⭐ **the invalid state having no representation at all** |

```java
// ⭐ Level 2 — transitions, not setters. Achievable everywhere, and usually enough.
public final class Order {
    private OrderStatus status;
    private Instant shippedAt;

    public void ship(Instant when) {
        if (status != PAID) throw new OrderNotPayable(id, status);   // ⭐ ONE way in
        this.status = SHIPPED;
        this.shippedAt = when;                                       // ⭐ can never be forgotten
    }
}
```

```java
// ⭐ Level 3 — sealed interfaces (Day 042). The illegal combination cannot be typed.
public sealed interface Order permits Draft, Paid, Shipped, Cancelled { }

public record Draft(OrderId id, List<Line> lines) implements Order { }
public record Paid(OrderId id, List<Line> lines, PaymentRef ref) implements Order { }
public record Shipped(OrderId id, List<Line> lines, PaymentRef ref,
                      Instant shippedAt, TrackingNumber tracking) implements Order { }  // ⭐ both mandatory
```

**⭐ With sealed types, "a shipped order with no shipping date" is not a bug you must test for — it is
a program that does not compile.** And pattern matching (Day 042) makes exhaustive handling a
compiler check: add a state, and every `switch` over `Order` fails to compile until handled.

⚠️ **Level 3 fights JPA hard** — one table, four types, no no-arg constructors. **Use it in the domain
and map to a single flat entity in the adapter (Day 300)**, or accept level 2. **Level 2 is the
pragmatic default and gets you most of the value.**

> **⭐ And notice the symmetry with Day 189: encoding invariants in the schema — CHECK constraints and
> partial unique indexes — is the same technique at the storage layer.** Two independent layers where
> the illegal state has no representation. **That is defence in depth for correctness, not
> security.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `String` for ids, emails, currencies | ⭐ **swapped arguments compile; every rule must be remembered** |
| ⭐ `double` for money | ⭐ Day 042B — silent, cumulative, and in the ledger |
| Value objects with setters | it is now an entity with no identity — the worst of both |
| ⭐ Records with mutable collections | ⭐ shallow immutability; copy defensively |
| ⭐ Public setters on state fields | ⭐ **the transition rule is bypassable** |
| ⭐ `Info` / `Data` / `Details` suffixes | ⭐ concepts that were never named |
| Booleans for state | ⭐ two booleans = four states, and two are illegal |
| ⭐ Entity equality by all fields | ⭐ breaks the moment anything changes (Day 158) |
| Sealed hierarchies fought through JPA | map in the adapter instead |
| DDD patterns with no language work | the vocabulary is where the value was |

## Interview questions

**Q: What is the difference between an entity and a value object?**
An entity has identity that survives change — if every field changed it is still the same order.
A value object *is* its value: change any field and it is a different one, so it is immutable and
equal by all fields. The classification is contextual — a banknote is a value object to a shop and an
entity to the central bank — which is why the same real-world thing gets modelled differently in
different contexts.

**Q: Why bother with a `Money` type instead of `BigDecimal` plus a currency string?**
Because the rule "you cannot add two different currencies" then exists in exactly one place and
cannot be forgotten by any future caller. It also makes `double` for money structurally impossible,
keeps amount and currency from drifting apart, and rejects nulls at construction. A value object is
where you put a rule so it cannot be skipped.

**Q: What does "make illegal states unrepresentable" mean?**
Design types so an invalid combination cannot be constructed. Three levels: validate in the
constructor so an invalid object cannot exist; expose named transitions instead of setters so it
cannot be moved into an invalid state; and sealed types per state so the invalid combination has no
representation at all — a shipped order without a shipping date stops being a test case and becomes a
compile error. Level two is the pragmatic default; level three fights JPA, so I keep it in the domain
and flatten in the adapter.

**Q: Do value objects eliminate argument-swap bugs?**
They eliminate type confusion, not role confusion. `transfer(AccountId, AccountId)` still lets you
swap source and destination. The fix for that is a named command object or a builder — I would not
claim the type system solves it alone.

**Q: What is the ubiquitous language and how would I know if you had one?**
One term, one meaning, used identically by the business and the code. You would know by reading the
class and method names: `order.ship()` versus `orderService.updateStatus(order, 3)`. And by the
absence of `Info`/`Data`/`Details` suffixes, each of which is a concept nobody managed to name.

## Mini task

1. **List every domain term in your flagship and the class that represents it.** Any term with no
   class is a missing concept; any class with no term is invented.
2. ⭐ **Write `Money`.** Reject mismatched currencies, wrong scale, and null. **Then delete every
   currency check elsewhere in the codebase and count them.**
3. Replace `String` ids with typed ids for one aggregate. **Count the compile errors — each is a
   place a swap was possible.**
4. Find a class with two booleans. **Enumerate the four states and name the illegal ones.** Replace
   with an enum or a sealed type.
5. Take one entity with a status. **Make every setter private, add named transitions.** Compile, and
   list every caller that was bypassing a rule.
6. ⭐ Model one aggregate with **sealed types per state**. Add a fifth state and confirm every
   `switch` fails to compile.
7. ⭐ Take one invariant you enforced in Java today and **also enforce it in the schema** as a CHECK
   constraint (Day 189). **Then insert an illegal row with raw SQL and watch the database refuse.**

**⭐ The markers, in order: `double` is fatal for money; the two `String`s make a swap compile; the

strongest signal in the whole answer.
