# Part 1 — ⭐ Pub/Sub: fire and forget, literally

```
SUBSCRIBE orders:events
PUBLISH orders:events '{"type":"OrderPlaced","id":"8842"}'
PSUBSCRIBE orders:*                -- ⭐ pattern subscription
```

> **⭐ Pub/Sub is at-most-once with no persistence. A message published when no subscriber is
> connected is gone. There is no queue, no acknowledgement, no replay, no history.**

**⭐ Three consequences that decide every use:**

1. ⭐ **A subscriber that disconnects for two seconds misses everything published in those two
   seconds** — including during a deploy, a GC pause, or a network blip.
2. ⭐ **A slow subscriber is disconnected.** Redis buffers per client, and when
   `client-output-buffer-limit pubsub` is exceeded, the subscriber is dropped — silently, from the
   publisher's point of view.
3. ⭐ **Publishing is O(N) in subscribers**, on the single thread (Day 203). Ten thousand subscribers
   on a hot channel is real work per message.

**⭐ So the rule is simple:**

| Good for | Bad for |
|---|---|
| ⭐ **Cache invalidation fan-out** across instances | ⭐ anything that must not be lost |
| ⭐ **Live dashboards, presence, typing indicators** | ⭐ job dispatch |
| ⭐ **WebSocket fan-out across instances** (Day 180) | domain events |
| Configuration reload signals | anything needing replay |

**⭐ Day 180's use is the canonical one**: each application instance subscribes and re-broadcasts to
its own connected WebSocket clients. Losing a message during a deploy means one missed chat line,
which the client's reconnect logic recovers — acceptable.

**⭐ And note the cluster caveat:** in Redis Cluster, Pub/Sub messages are broadcast to every node,
which does not scale. `SSUBSCRIBE`/`SPUBLISH` (sharded Pub/Sub, Redis 7+) confines a channel to one
shard — use it in cluster mode.

# Part 2 — ⭐⭐ Streams: an append-only log with consumer groups

```
XADD orders * type OrderPlaced id 8842        -- ⭐ * = auto-generate the ID (ms-sequence)
XLEN orders
XRANGE orders - +                              -- ⭐ read history — Pub/Sub cannot do this
XREAD COUNT 10 BLOCK 5000 STREAMS orders $     -- ⭐ blocking read of new entries
```

**⭐ A Stream is Kafka's model in Redis**: an ordered, persistent, replayable log with IDs that are
timestamps plus a sequence number.

## ⭐ Consumer groups — the part that makes it a real queue

```
XGROUP CREATE orders processors 0 MKSTREAM
XREADGROUP GROUP processors worker-1 COUNT 10 BLOCK 5000 STREAMS orders >
    -- ⭐ '>' = entries never delivered to this group
XACK orders processors 1723640000-0            -- ⭐ acknowledge
XPENDING orders processors                     -- ⭐⭐ what is delivered but unacknowledged
XAUTOCLAIM orders processors worker-2 60000 0  -- ⭐⭐ steal entries idle > 60s
```

**⭐ This gives you everything Day 185A required of a broker:**

| Property | Mechanism |
|---|---|
| ⭐ **Load balancing across workers** | ⭐ each entry goes to one consumer in the group |
| ⭐ **At-least-once delivery** | ⭐ unacknowledged entries stay in the Pending Entries List |
| ⭐ **Crash recovery** | ⭐ `XAUTOCLAIM` reassigns entries from a dead worker |
| Independent consumer groups | each group has its own position — fan-out *and* queueing |
| ⭐ **Replay** | `XRANGE`, or a new group starting at `0` |

**⭐ `XPENDING` and `XAUTOCLAIM` are the pair that matters.** A worker that crashes mid-processing
leaves its entries in the PEL; another worker claims them after an idle timeout. **That is the
visibility-timeout mechanism of Day 125, implemented — and it is exactly what Day 204's `LMOVE` list
pattern was approximating badly.**

## ⭐ Bounding the stream — non-optional

```
XADD orders MAXLEN ~ 1000000 * type OrderPlaced id 8842   -- ⭐ approximate trim, cheap
XTRIM orders MINID ~ 1723000000000                         -- ⭐ trim by time
```

**⭐ A stream grows forever otherwise** — Day 204's rule, with the extra sting that Redis is
memory-resident, so an unbounded stream is an out-of-memory error rather than a large table.

**⭐ Use `~` (approximate).** Exact trimming is O(N); approximate trims to whole nodes and is
effectively free.

⚠️ **⭐ And the trap: trimming removes entries even if they are still pending.** A slow consumer group
can have its unacknowledged entries deleted underneath it. **Set `MAXLEN` well above your worst-case
backlog, and monitor `XPENDING` and the group lag.**

## ⭐⭐ Streams versus Kafka — the honest comparison

| | Redis Streams | Kafka |
|---|---|---|
| Durability | ⭐ **memory + AOF; async replication (Day 205)** | ⭐ **disk, replicated, acked** |
| Retention | ⭐ bounded by **memory** | ⭐ **disk — days or weeks** |
| Throughput | very high | ⭐ higher, and horizontally scalable |
| Partitioning | ⭐ manual (multiple streams) | ⭐ built in |
| Ordering | per stream | per partition |
| ⭐ **Operational weight** | ⭐⭐ **already running Redis** | a cluster to operate |
| Ecosystem | thin | ⭐ Connect, Streams, Schema Registry |

**⭐ The decision, stated as an interview answer:**

> **⭐ Redis Streams when you already run Redis, the volume fits in memory, and losing the last second
> on a failover is acceptable. Kafka when the log is a system of record, retention is measured in
> days, or you need horizontal scale.**

**⭐ The durability line is the deciding one**, and it goes back to Day 205: **Redis replication is
asynchronous, so a failover can lose recently-added entries.** For a work queue where the work is
also recorded in PostgreSQL, that is recoverable. For an event log that *is* the record of what
happened, it is not.

**⭐ And Day 124's outbox pattern makes Streams perfectly viable**: PostgreSQL holds the outbox
durably, a poller publishes to a Stream, and consumers are idempotent (Day 185A). The Stream is a
transport, not the record — and then its durability limits stop mattering.

# Part 3 — Choosing among all the messaging options

| Need | Tool |
|---|---|
| ⭐ Fan-out where loss is fine | ⭐ **Pub/Sub** |
| ⭐ Work queue, already running Redis | ⭐ **Streams + consumer groups** |
| Simple queue, low volume | List + `BLPOP`/`LMOVE` (⭐ Streams are better) |
| ⭐ Delayed / scheduled jobs | ⭐ **sorted set by run-at time** (Day 204) |
| ⭐ Event log as a system of record | ⭐ **Kafka** (Day 185A) |
| Complex routing, per-message TTL, priority | RabbitMQ |
| ⭐ **Must not be lost, ever** | ⭐ **the outbox in PostgreSQL** (Day 124) + any transport |

**⭐ The last row is the reframe:** the durability question is answered by where the record lives, not
by which broker carries it. **An outbox in a durable database plus an idempotent consumer makes the
transport's guarantees far less critical** — which is why Day 185A's two halves fit together.

# Part 4 — 🚪 Redis block gate (Days 203–209)

## ⭐ The build

**One service using Redis correctly for six distinct jobs. No library shortcuts for items 3–5.**

1. **Cache** — versioned keys, jittered TTLs, `allkeys-lfu`, `CacheErrorHandler` degrading on failure
2. **Sessions** — AOF `everysec`, correct cookie flags (Day 172)
3. ⭐ **Rate limiter** — sliding-window counter in Lua, layered keys, `Retry-After`, a documented
   fail-open/fail-closed decision per endpoint
4. ⭐ **Distributed lock** — Redisson, ⭐ **plus a fencing token checked by PostgreSQL**
5. ⭐ **Work queue** — Streams with a consumer group, `XAUTOCLAIM` recovery, `MAXLEN ~` trimming,
   idempotent consumers
6. **Leaderboard** — sorted set with `ZRANK`, bounded with `ZREMRANGEBYRANK`

**Then prove it:**

- ⭐ `redis-cli --bigkeys` finds nothing unbounded
- ⭐ **Stop Redis under load** — the cache degrades, the sensitive endpoints fail closed, nothing 500s
  unexpectedly
- ⭐ **Kill a worker mid-job** — `XAUTOCLAIM` recovers the entry
- ⭐ **`SIGSTOP` the lock holder for 40 seconds** — confirm the fencing token rejects its stale write

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Pub/Sub for anything that matters | messages published to nobody are gone |
| Expecting Pub/Sub to buffer | there is no queue |
| Not knowing slow subscribers are dropped | silent message loss |
| Pub/Sub in cluster mode without sharded channels | broadcast to every node |
| ⭐ Streams without `MAXLEN` | unbounded memory — an OOM, not a large table |
| Exact `MAXLEN` instead of `~` | O(N) trim |
| ⭐ Trimming below the pending backlog | unacknowledged entries deleted |
| Never calling `XACK` | the PEL grows forever |
| No `XAUTOCLAIM` | a crashed worker's entries are stuck |
| Not monitoring group lag | a falling-behind consumer is invisible |
| ⭐ Streams as a system of record | async replication loses recent entries |
| Lists where Streams belong | no acks, no groups, no recovery |

## Interview questions

**Q: Pub/Sub or Streams?**
Pub/Sub only where loss is acceptable — cache invalidation fan-out, WebSocket broadcast across
instances, presence. It is at-most-once with no persistence, so a subscriber that disconnects for two
seconds misses everything in that window, and slow subscribers are dropped. Streams for anything
resembling a queue: consumer groups, at-least-once via the pending list, and `XAUTOCLAIM` to recover
a crashed worker's entries.

**Q: Redis Streams or Kafka?**
Streams when I already run Redis, the volume fits in memory, and losing the last second on a failover
is acceptable. Kafka when the log is the system of record, retention is days, or I need horizontal
scale. The deciding property is durability — Redis replication is asynchronous, so a failover can
lose recent entries.

**Q: How do you make Streams safe enough for important work?**
Put the durable record elsewhere. An outbox in PostgreSQL written in the same transaction as the
business data, a poller publishing to the Stream, and idempotent consumers — then the Stream is a
transport rather than the record, and its durability limits stop being critical.

**Q: What breaks in a Streams consumer group?**
Not acknowledging, so the pending list grows without bound. Not running `XAUTOCLAIM`, so a crashed
worker's entries are stuck forever. And trimming with a `MAXLEN` below the pending backlog, which
deletes entries a slow consumer has not processed — so I set it well above the worst case and monitor
`XPENDING`.
