# Part 1 — L-078 · The filesystem

## Everything is a file

The defining Unix idea: **regular files, directories, devices, sockets, pipes and even kernel state
are all accessed through the same file API** — `open`, `read`, `write`, `close` (Day 004, Day 023's
B-01). One interface, so `cat`, `grep` and redirection work on all of them.

```bash
cat /proc/cpuinfo          # kernel state, read as a file
echo 1 > /proc/sys/net/ipv4/ip_forward   # kernel config, written as a file
cat /dev/urandom | head -c 16 | xxd      # a device, read as a file
```

That is why Day 071's `/proc/<pid>/status` worked: the kernel exposes process state as a filesystem.

## The hierarchy — what actually matters

| Path | Contains | You care because |
|---|---|---|
| `/etc` | System-wide config | `/etc/passwd`, `/etc/hosts`, `/etc/systemd` |
| `/var/log` | Logs | Where your app's logs land |
| `/var/lib` | Application state | Docker images, database files |
| `/usr/bin`, `/usr/local/bin` | Executables | Where `java` lives; `/usr/local` = manually installed |
| `/opt` | Self-contained third-party | JDK installs often here |
| `/home/<user>` (`~`) | User files | `~/.m2`, `~/.ssh`, `~/.bashrc` |
| `/tmp` | Scratch, **cleared on reboot** | Never store anything you need |
| `/proc`, `/sys` | Kernel interfaces (virtual) | Day 071's diagnostics |
| `/dev` | Devices | `/dev/null`, `/dev/urandom` |
| `/mnt`, `/media` | Mount points | Attached volumes |

**There is one tree.** Unlike Windows, other disks are *mounted into* it rather than given letters —
`/mnt/data` might be a different physical device, and nothing above it knows or cares.

```bash
df -h                 # what is mounted where, and how full
du -sh /var/log/*     # what is using space  ← the disk-full investigation
lsblk                 # block devices
```

`df` versus `du` is a real interview question: **`df` asks the filesystem, `du` sums files**. When
they disagree, the classic cause is a **deleted file still held open by a process** — the space is
not freed until the last file descriptor closes.

```bash
lsof +L1              # files with 0 links: deleted but still open
```

That is a genuinely common production incident: someone `rm`s a 40 GB log while the app still has it
open, `du` shows the space gone, `df` still shows the disk full, and the only fix is restarting the
process or truncating via `/proc/<pid>/fd/N`.

## Paths

```bash
/var/log/app.log        # absolute
./config/app.yml        # relative to cwd
../sibling/file         # parent
~/.ssh/id_ed25519       # home
```

**A filename is bytes, not text.** Spaces, newlines and `-` are all legal in filenames, which is why
you quote variables (`"$file"`) and why `find -print0 | xargs -0` exists (Day 080).

A leading `-` is the hazard: `rm -rf` on a file called `-rf` is not what you meant. Use `rm ./-rf`
or `rm -- -rf`.

## Permissions

```
-rwxr-xr--  1 ram  devs  4096 Aug 14 10:22 script.sh
│└┬┘└┬┘└┬┘     │     │
│ │  │  └── other:  r--  (4)
│ │  └───── group:  r-x  (5)
│ └──────── owner:  rwx  (7)
└────────── type: - file, d dir, l symlink, s socket, b/c device
```

Numeric mode is octal: **r=4, w=2, x=1**. So `755` = `rwxr-xr-x`, `644` = `rw-r--r--`,
`600` = `rw-------`.

```bash
chmod 755 script.sh
chmod +x script.sh            # symbolic
chmod u+rw,go-rwx secret.key  # = 600
chmod -R 755 dir/             # recursive ⚠️ makes every FILE executable too
chmod -R u+rwX,go+rX dir/     # ✅ capital X = execute only on DIRECTORIES
chown ram:devs file
```

That capital `X` is the detail worth keeping: lowercase `x` marks everything executable, which is
both wrong and a security smell; `X` applies the execute bit only to directories and to files that
already had it.

**On a directory the bits mean something different**, and this trips people constantly:

| Bit | On a file | On a directory |
|---|---|---|
| `r` | read contents | **list** entries |
| `w` | modify contents | **create/delete** entries |
| `x` | execute | **enter / traverse** it |

So a directory with `r` but no `x` lets you see names and nothing else; `x` without `r` lets you
access a known path but not list it. And note **deleting a file depends on the *directory's* write
bit, not the file's** — you can delete a file you cannot write.

The three special bits:

```bash
chmod 4755 prog     # setuid  — runs as the file's OWNER (how `passwd` works). Dangerous.
chmod 2775 dir      # setgid  — new files inherit the directory's group. Useful for shared dirs.
chmod 1777 /tmp     # sticky  — only the owner can delete their files. Why /tmp is safe.
```

`umask` decides default permissions: the typical `022` means new files are `644` and new directories
`755`.

## Users, groups and the key files

```bash
id                    # uid, gid, groups — run this first when permissions confuse you
whoami
sudo -u appuser cmd
groups ram
```

| File | Holds |
|---|---|
| `/etc/passwd` | Users: name, uid, gid, home, shell. **World-readable, no passwords** |
| `/etc/shadow` | Password hashes. `root`-only |
| `/etc/group` | Groups and members |
| `/etc/sudoers` | Who may `sudo` what. **Edit only with `visudo`** |

`/etc/passwd` being world-readable is deliberate — it maps uids to names, which every `ls -l` needs.
Password hashes moved to `/etc/shadow` precisely so they were not.

**`root` (uid 0) bypasses all permission checks.** Which is why:

> **Never run your application as root.** A compromised process inherits its privileges. Give the
> service its own user with the minimum it needs — and note this is exactly the `USER appuser`
> line in a Dockerfile, and the reason it matters.

## Links

```bash
ln    target hardlink      # another NAME for the same inode
ln -s target symlink       # a small file containing a PATH
ls -li                     # -i shows inode numbers
```

A **hard link** is a second directory entry pointing at the same inode (Day 060's B-12). Delete one
name and the data survives while any name remains — the inode's link count is what `rm` decrements.
Hard links cannot cross filesystems and cannot point at directories.

A **symlink** is a tiny file whose contents are a path. It can cross filesystems and point at
directories, and it **dangles** if the target disappears. Every `/usr/bin/java` on a machine with
multiple JDKs is a symlink chain — `readlink -f $(which java)` resolves it.

## Code to type

```bash
mkdir -p ~/lab/{a,b,c} && cd ~/lab
echo "secret" > a/key.txt

ls -l a/key.txt                     # note the default mode from umask
chmod 600 a/key.txt && ls -l a/key.txt

# directory x-bit
chmod 600 a && ls a                 # permission denied? read without traverse
chmod 700 a && ls a

# deletion depends on the DIRECTORY
chmod 444 a/key.txt
rm a/key.txt                        # prompts, but succeeds — you own the directory

# links
echo hello > orig.txt
ln orig.txt hard.txt
ln -s orig.txt soft.txt
ls -li orig.txt hard.txt soft.txt   # same inode for the first two
rm orig.txt
cat hard.txt                        # still works
cat soft.txt                        # dangling

# the df/du divergence, reproduced
python3 -c "
import time
f=open('/tmp/big','wb'); f.write(b'0'*200_000_000); f.flush()
import os; os.remove('/tmp/big')
print('deleted; still open'); time.sleep(120)" &
sleep 2; df -h /tmp; du -sh /tmp; lsof +L1 | head
```

That last block is the one to actually run — seeing `df` and `du` disagree, then finding the culprit
with `lsof +L1`, is the whole lesson in one experiment.

# Part 2 — D-01 · Why databases exist

## The question nobody asks

You can write records to a file. Why is there a whole category of software for it?

Try to build it yourself and the requirements appear one at a time:

1. **Find one record among ten million** without reading the file → you need an **index**.
2. **Two users write at once** → you need **concurrency control**.
3. **Power fails mid-write** → you need **durability and atomicity**.
4. **Move money between accounts** — both updates or neither → you need **transactions**.
5. **Prevent an order referencing a customer who does not exist** → you need **constraints**.
6. **Answer a question you did not anticipate** → you need a **query language**.
7. **Ten teams, one dataset** → you need **access control** and **a schema as a contract**.

A DBMS is what you get after solving all seven properly. **The alternative is not "no database" —
it is a worse database you wrote by accident**, which is the honest framing when someone proposes
storing state in flat files.

## The problems with file-based storage

| Problem | Meaning |
|---|---|
| **Data redundancy** | The same customer address in four files |
| **Inconsistency** | Update three of the four |
| **No integrity enforcement** | Nothing stops `age = -5` or an orphaned order |
| **Concurrent-access anomalies** | Two withdrawals both read the old balance |
| **Atomicity failures** | Debit succeeds, credit fails, money vanishes |
| **Data–program dependence** | Change the record layout, recompile every program |
| **No ad-hoc querying** | Every new question is a new program |

That last pair is the deepest. **Data independence** — the ability to change storage without
changing application code — is the central contribution of the database field, and the
three-schema architecture is how it is achieved.

## The three-schema architecture (ANSI/SPARC)

```
   External level   ← views: what each application sees
        │  logical data independence
   Conceptual level ← the logical schema: tables, columns, constraints
        │  physical data independence
   Internal level   ← files, pages, indexes, storage layout
```

**Physical data independence:** add an index, change the page size, move to an SSD — no application
changes. **Logical data independence:** split a table, and applications using a view over it keep
working.

This is why SQL says *what* you want and not *how* to get it. You do not write "use the index on
`customer_id`"; the optimiser decides, and it can change its mind next release without breaking you.

## DBMS components

```
   SQL query
       ▼
 ┌──────────────┐   parse, validate against the catalog
 │   Parser     │
 ├──────────────┤   rewrite; choose a PLAN using statistics
 │  Optimizer   │   ← "which index, which join order, which algorithm"
 ├──────────────┤
 │  Executor    │   run the plan
 ├──────────────┤
 │ Buffer pool  │   ← pages cached in memory. Day 057's B-11 page replacement, again
 ├──────────────┤
 │Storage engine│   pages on disk, B-tree indexes
 ├──────────────┤
 │Txn + recovery│   locks/MVCC, and the WAL
 └──────────────┘
```

Two components to fix in mind now, because everything in Stage 5 builds on them:

**The buffer pool** is a page cache in RAM using an LRU-style replacement policy — which is
literally Day 057's page-replacement material applied to database pages. "Is it in the buffer pool?"
is the difference between 100 nanoseconds and 100 microseconds.

**The write-ahead log (WAL)** is how durability is achieved without writing data pages on every
commit: **the log record is flushed before the data page is modified on disk**. After a crash,
replay the log. This is the same idea as the filesystem journaling from Day 060's B-12, and it is
the answer to "how can a commit be durable if the page is still in memory?"

## The families

| Type | Model | Use when |
|---|---|---|
| **Relational** | Tables, SQL, ACID | Default. Structured data with relationships |
| Document | JSON documents | Schema varies per record; aggregate reads |
| Key-value | `get`/`put` | Cache, session store (Redis) |
| Wide-column | Sparse rows, partition keys | Huge write volume (Cassandra) |
| Graph | Nodes and edges | Traversal-heavy: social, fraud rings |
| Time-series | Timestamped points | Metrics |
| Vector | Embeddings, ANN search | Semantic search (Pinecone, pgvector) |

**Start relational.** PostgreSQL handles JSON, full-text search, geospatial and vectors, so "we need
a document database" is often "we need a `jsonb` column". The interesting question in an interview
is not which you would pick but *what would make you pick otherwise* — and the honest answers are
scale characteristics and access patterns, not data shape alone.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `chmod -R 777` to "fix" permissions | World-writable; a genuine security finding |
| `chmod -R +x` instead of `+X` | Every data file marked executable |
| Running the app as root | Compromise becomes host compromise |
| Unquoted `$file` in scripts | Breaks on spaces; can be an injection |
| Storing state in `/tmp` | Gone on reboot |
| Assuming `du` and `df` agree | Miss the deleted-but-open file |
| Editing `/etc/sudoers` directly | A syntax error locks out `sudo` — use `visudo` |
| Flat files as a database | You will reimplement a DBMS badly |

## Interview questions

**Q: What do the permission bits mean on a directory?**
`r` lists entries, `w` creates and deletes them, `x` traverses. Deleting a file depends on the
directory's write bit, not the file's.

**Q: Hard link vs symlink?**
A hard link is another name for the same inode — same filesystem, no directories, data survives
while any name remains. A symlink is a file containing a path; it crosses filesystems, points at
directories, and dangles if the target goes.

**Q: `df` says full, `du` says there is space. Why?**
A deleted file still held open by a process. Find it with `lsof +L1`; the space returns when the
descriptor closes.

**Q: Why not just use files instead of a database?**
Because you then have to build indexing, concurrency control, atomicity, durability, constraints and
a query language yourself — and data independence, so storage changes do not force code changes.

**Q: What is a WAL and why does it make commits fast *and* durable?**
The log record is flushed to disk before the data page changes. A sequential log write is far
cheaper than random page writes, and recovery replays the log — so you get durability without
writing every page at commit.

**Q: What is physical data independence?**
The ability to change storage structures — indexes, layouts, hardware — without changing application
code, because applications address the conceptual schema, not the internal one.
