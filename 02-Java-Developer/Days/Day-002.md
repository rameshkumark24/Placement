# Part 1 — L-002 · Source code to execution

## What it is

The CPU understands exactly one thing: **machine code** — binary instructions specific to its
architecture (x86-64, ARM64). `public class Main` means nothing to it.

Something must translate. There are two strategies, and Java uses both.

| | Compiler | Interpreter |
|---|---|---|
| **When** | Ahead of time, once | At runtime, every time |
| **Output** | A machine-code file | Nothing — it just acts |
| **Speed to start** | Slow (compile step) | Instant |
| **Speed to run** | Fast | Slow (re-analysing every line) |
| **Errors found** | At compile time | When that line is reached |
| **Portable** | No — per platform | Yes — the interpreter is the portable part |
| **Examples** | C, Go, Rust | Classic Python, Ruby, JS (originally) |

## Why it exists — the tradeoff Java refused to accept

C compiles to machine code: fast, but you compile separately for every platform, and a pointer bug
corrupts memory silently.

Classic interpreters are portable but slow, because the work of understanding a line is redone on
every execution — including every iteration of a loop.

**Java's answer: do both.** Compile once to a portable intermediate form, then compile *that* to
machine code at runtime, on the parts that turn out to be hot.

```
   Main.java                    ← you write this
       │
       │  javac  (compile, ahead of time)
       ▼
   Main.class                   ← BYTECODE. Portable. Not machine code.
       │
       │  java   (JVM starts, class loader reads it)
       ▼
   ┌─────────────────────────────────────────────┐
   │  JVM                                        │
   │                                             │
   │   Interpreter  ──── runs bytecode now       │
   │        │                                    │
   │        │  method called many times?         │
   │        ▼                                    │
   │   JIT compiler ──── compiles THAT method    │
   │        │            to native machine code  │
   │        ▼                                    │
   │   Native code  ──── runs at C-like speed    │
   └─────────────────────────────────────────────┘
```

**This is why "Java is slow" is a 1998 opinion.** Startup is slower than C because of the JVM boot
and the interpretation phase, but steady-state throughput on a long-running server is comparable —
sometimes better, because the JIT optimises using information a static compiler never has (which
branch is actually taken, which type actually shows up at this call site).

That trade — slow start, fast steady state — is exactly right for a server that runs for weeks. It
is exactly wrong for a CLI tool that runs for 40 ms, which is why GraalVM native image exists
(Day 185B).

## How it works inside

### Step 1 — `javac`: source → bytecode

```
Main.java
   │
   ├─▶ Lexical analysis    "public", "class", "Main", "{"  → tokens
   ├─▶ Parsing             tokens → Abstract Syntax Tree
   ├─▶ Semantic analysis   type checking, scope resolution  ← most of your compile errors
   ├─▶ Bytecode generation
   ▼
Main.class
```

`javac` does **not** produce machine code. It produces bytecode: instructions for an imaginary
machine — the Java Virtual Machine. That machine doesn't exist in silicon, which is exactly the
point.

### Step 2 — the class loader

When you run `java Main`, the JVM must find and load `Main.class`. This is the **class loader**
(Day 023 in depth):

1. **Loading** — find the `.class` file, read the bytes, create a `Class` object
2. **Linking** — verify the bytecode is legal and safe, prepare static fields with defaults,
   resolve symbolic references
3. **Initialisation** — run static initialisers

The **verification** step matters more than it sounds. The JVM checks that the bytecode doesn't
underflow the stack, jump to arbitrary addresses, or violate type safety. This is why a Java program
can't corrupt memory the way a C program can — the guarantee is enforced *before* anything runs.

Loading is **lazy**: a class is loaded the first time it's actually needed, not at startup. That's
why a missing dependency can surface twenty minutes into a run rather than immediately —
`NoClassDefFoundError` in production at 3am (Day 076A).

### Step 3 — execute, then JIT

The interpreter starts executing bytecode immediately. Meanwhile the JVM counts how often each
method runs. Past a threshold (~10,000 invocations for C2), the **JIT compiler** compiles that
method to native code, and subsequent calls use the compiled version.

The JIT can do things `javac` cannot:
- **Inlining** — paste a small method's body into its caller, removing call overhead
- **Escape analysis** — if an object never leaves a method, allocate it on the stack, or not at all
- **Speculative optimisation** — "this call site has always been `ArrayList`, compile for that and
  keep a guard in case it changes"

**This is why microbenchmarks lie.** Run a loop 10 times and you measure the interpreter. Run it 10
million times and you measure JIT-compiled code. The two differ by 10–100×. When you benchmark Java,
you must warm up first — and this is exactly what JMH exists to handle.

## Look at the bytecode yourself

```java
public class Bytecode {
    public static void main(String[] args) {
        int a = 5;
        int b = 10;
        int c = a + b;
        System.out.println(c);
    }
}
```

```bash
javac Bytecode.java
javap -c Bytecode          # -c disassembles
```

You'll see roughly:

```
 0: iconst_5              // push 5 onto the operand stack
 1: istore_1              // pop it into local variable 1  (a)
 2: bipush 10             // push 10
 4: istore_2              // pop into local variable 2     (b)
 5: iload_1               // push a
 6: iload_2               // push b
 7: iadd                  // pop two, add, push result
 8: istore_3              // pop into local variable 3     (c)
 9: getstatic ... System.out
12: iload_3
13: invokevirtual ... println
16: return
```

**Notice: the JVM is a stack machine.** No registers in the bytecode — values are pushed and popped
on an operand stack. The JIT maps that onto real registers later.

Now do this, and compare:

```java
String s = "a" + "b" + "c";          // compile it, javap it
String t = a + b + c;                // where a,b,c are String variables
```

The first is folded to a single constant `"abc"` at compile time. The second becomes
`StringBuilder` calls (or `invokedynamic` on modern Java). **That is the actual reason `+=` in a
loop is fatal** — you're allocating a new builder every iteration. You'll meet this again on
Day 029, and now you'll already know why.

## Type this yourself

```java
public class JitWarmup {
    static int compute(int n) {
        int total = 0;
        for (int i = 0; i < n; i++) {
            total += i % 7;
        }
        return total;
    }

    public static void main(String[] args) {
        // Cold: interpreted.
        long start = System.nanoTime();
        compute(1_000);
        System.out.printf("Cold run:  %,d ns%n", System.nanoTime() - start);

        // Warm it up — force the JIT to compile it.
        for (int i = 0; i < 100_000; i++) {
            compute(1_000);
        }

        // Hot: JIT-compiled.
        start = System.nanoTime();
        compute(1_000);
        System.out.printf("Hot run:   %,d ns%n", System.nanoTime() - start);
    }
}
```

Same method, same input. Run it and write both numbers in your notes. The gap is the JIT.

Then run it again with `java -Xint JitWarmup` (interpreter only, JIT disabled) and see what happens
to the hot number.

## Common mistakes

| Mistake | Correction |
|---|---|
| "Java is compiled" / "Java is interpreted" | Both. `javac` compiles to bytecode; the JVM interprets, then JIT-compiles hot paths to native. |
| "Bytecode is machine code" | Bytecode targets the JVM, an abstract machine. Machine code targets a physical CPU. |
| Benchmarking without warmup | You measured the interpreter. Warm up, or use JMH. |
| "The JVM makes Java slow" | Startup, yes. Steady-state throughput is competitive — the JIT uses runtime information a static compiler doesn't have. |
| Expecting all classes to load at startup | Loading is lazy and on first use, which is why missing classes surface late. |

## Interview questions

**Q: Is Java compiled or interpreted?**
> Both, in sequence. `javac` compiles source to platform-independent bytecode ahead of time. At
> runtime the JVM interprets that bytecode, profiles it, and the JIT compiler compiles frequently
> executed methods to native machine code. So it's compiled twice, to two different targets.

**Q: What is bytecode and why does it exist?**
> An instruction set for the JVM rather than a physical CPU. It exists to decouple compilation from
> the target platform: compile once, and any JVM on any architecture can run it. It's also
> verifiable, which is what gives Java its memory-safety guarantee.

**Q: What does the JIT do that `javac` cannot?**
> It has runtime information. It can inline based on actual call frequency, do escape analysis on
> observed object lifetimes, and speculatively optimise for the types that actually appear at a call
> site, with a guard to deoptimise if that assumption breaks.

**Q: Why is the first request to a Java service slower than the thousandth?**
> Class loading is lazy, and the JIT hasn't compiled the hot paths yet, so early requests run
> interpreted. This is why production readiness checks and load balancer warm-up periods matter for
> JVM services.

# Part 2 — C-02 · Physical & data link layer

## The physical layer

Turning bits into something that travels: voltage on copper, light pulses in fibre, radio waves in
WiFi. Its only job is **"can I get a 1 or a 0 to the other end of this cable"**.

That's genuinely all. It has no idea what a message is.

## The data link layer

One job: **move a frame from this device to the next device on the same physical network.**

Not to the destination. To the **next hop**. That distinction is the whole reason the network layer
exists tomorrow (C-03).

### MAC addresses

Every network interface has a 48-bit **MAC address**, burned in at manufacture:

```
  a4:83:e7:2b:19:f0
  └───┬───┘ └───┬──┘
   vendor    device
```

| | MAC | IP |
|---|---|---|
| Layer | Data link (2) | Network (3) |
| Scope | This local network only | Globally routable |
| Assigned by | Manufacturer, permanent | Network/DHCP, changes |
| Answers | "which device on this cable?" | "which machine on the internet?" |

**Analogy that actually holds:** IP is the postal address on the envelope. MAC is "hand it to the
person at the next desk". The envelope keeps its address the whole journey; who you hand it to
changes at every step.

### Switches

A switch connects devices on a local network and learns, by watching traffic, which MAC address
lives on which physical port. It builds a MAC address table and forwards frames only to the correct
port — unlike an old hub, which shouted everything to everyone.

```
                  ┌──────────────┐
     Laptop ──────┤ Port 1       │
      a4:83...    │              │   MAC table (learned):
                  │              │     a4:83... → Port 1
     Phone ───────┤ Port 2       │     b2:11... → Port 2
      b2:11...    │              │     c9:40... → Port 3
                  │              │
     Printer ─────┤ Port 3       │
      c9:40...    └──────────────┘
```

### ARP — the glue between IP and MAC

You want to send to `192.168.1.15`. The link layer needs a MAC address. How do you get one from an
IP?

**Address Resolution Protocol:**

1. Host broadcasts to the whole local network: *"who has 192.168.1.15? Tell a4:83:e7:2b:19:f0"*
2. The machine with that IP replies directly: *"192.168.1.15 is at b2:11:c4:88:02:9a"*
3. The asker caches the mapping in its ARP table (`arp -a` to see yours)

**ARP has no authentication.** Anyone on the network can reply "that IP is at *my* MAC" — that's
**ARP spoofing**, and it's the basis of local-network man-in-the-middle attacks. It's also a direct
argument for why you use HTTPS on a coffee-shop WiFi: the transport can be hijacked, so the
encryption has to sit above it.

## Type this yourself

```bash
arp -a                    # your ARP cache: IP → MAC mappings
ipconfig /all             # Windows: your MAC ("Physical Address") and IP
ping 192.168.1.1          # ping your router, then check arp -a again
```

Watch the ARP table gain an entry after the ping. You just observed the resolution happen.

## Interview questions

**Q: Difference between a MAC address and an IP address?**
> MAC is a permanent hardware identifier at layer 2, meaningful only within a local network segment.
> IP is a logical, assigned address at layer 3 that is globally routable. MAC gets a frame to the
> next hop; IP gets a packet to the final machine.

**Q: What is ARP and why is it a security concern?**
> ARP resolves an IP address to a MAC address on a local network by broadcasting a request. It has
> no authentication, so any host can reply falsely and claim another host's IP — ARP spoofing —
> which enables man-in-the-middle attacks on a shared network.

**Q: Hub vs switch?**
> A hub repeats every frame to every port. A switch learns which MAC is on which port and forwards
> only where needed, which reduces collisions and prevents casual traffic snooping.
