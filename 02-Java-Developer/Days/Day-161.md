# Part 1 — The cost of an entity, so the alternative makes sense

Loading an entity is not "a row in an object". For every row Hibernate:

1. instantiates the entity and every embeddable,
2. creates lazy **proxies** for each association,
3. registers it in the **persistence context**,
4. **takes a snapshot of every field** for dirty checking (Day 162),
5. keeps both the object and the snapshot alive until the transaction ends.

**That is roughly double the memory and a per-field comparison at flush time — for data you are
going to serialize and discard.** Loading 10,000 entities to produce a report is paying full
transactional machinery for a read-only operation.

```java
@Transactional(readOnly = true)     // ⭐ skips dirty checking; cheapest entity read
```

Useful, and still not free. A projection skips all five steps.

# Part 2 — The five techniques, ordered by preference for reads

### ⭐ 1. Constructor (DTO) projection — the default for reads

```java
public record OrderSummary(UUID id, String customerName, BigDecimal total, Instant placedAt) {}

@Query("""
    select new com.acme.order.OrderSummary(o.publicId, c.name, o.total, o.placedAt)
    from Order o join o.customer c
    where o.status = :status
""")
List<OrderSummary> summaries(@Param("status") OrderStatus status);
```

**One query, four columns, no entities, no proxies, no snapshots, and N+1 is structurally
impossible.** The fully-qualified class name in JPQL is ugly; it is the price of the best read path
in JPA.

### 2. Interface projection — less typing, Spring Data only

```java
public interface OrderView {
    UUID getPublicId();
    BigDecimal getTotal();
    String getCustomerName();          // ⭐ resolves the nested path customer.name
}

List<OrderView> findByStatus(OrderStatus status);      // ⭐ no @Query needed at all
```

**Spring Data selects only the columns the interface declares.** Excellent for simple cases.

⚠️ **The trap:** the moment you add a method that is *not* a plain property — anything using `@Value`
with SpEL, or a default method touching multiple fields — it becomes an **open projection**, and
Spring Data must load **the whole entity** to evaluate it. You lose the column selection silently and
the interface still compiles. If performance is the reason you used a projection, keep it closed.

### 3. `join fetch` — when you need managed entities

```java
@Query("select distinct o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(@Param("id") Long id);
```

**Use when you will modify the result**, because dirty checking needs managed entities. Day 160's
three constraints apply in full: `distinct`, one collection maximum, never with `Pageable`.

### 4. `@EntityGraph` — declarative, and composable

```java
@EntityGraph(attributePaths = {"customer", "shippingAddress"})
Optional<Order> findByPublicId(UUID publicId);

@EntityGraph(attributePaths = {"items", "items.product"})     // ⭐ nested paths work
List<Order> findByStatus(OrderStatus status);
```

Cleaner than JPQL for `@ManyToOne`s, and it layers onto derived query methods with no `@Query` at
all.

**Named graphs, for reuse across several queries:**

```java
@NamedEntityGraph(name = "Order.full", attributeNodes = {
    @NamedAttributeNode("customer"),
    @NamedAttributeNode(value = "items", subgraph = "items")
}, subgraphs = @NamedSubgraph(name = "items", attributeNodes = @NamedAttributeNode("product")))
@Entity public class Order { }
```

**`FETCH` vs `LOAD`:** `FETCH` (the default) treats everything not in the graph as lazy, ignoring the
mapping's declared fetch type. `LOAD` keeps the mapping's defaults for unlisted attributes. **`FETCH`
is what you want** — it makes the graph the complete statement of what loads.

### 5. `Tuple` / `Object[]` — avoid

```java
List<Object[]> rows = em.createQuery("select o.id, o.total from Order o").getResultList();
BigDecimal total = (BigDecimal) rows.get(0)[1];      // ❌ index and cast — nothing checks either
```

Reordering the select list breaks this at runtime with a `ClassCastException` and nothing at compile
time. Use a record.

# Part 3 — Beyond JPQL: native queries and Specifications

## Native queries, safely

```java
@Query(value = """
        select o.public_id as id, c.name as customerName, sum(oi.qty) as itemCount
        from orders o
        join customers c   on c.id = o.customer_id
        join order_items oi on oi.order_id = o.id
        where o.placed_at > :since
        group by o.public_id, c.name
        """, nativeQuery = true)
List<OrderStatsView> stats(@Param("since") Instant since);      // ⭐ interface projection
```

**Reach for native SQL when JPQL cannot express it:** window functions (D-09), recursive CTEs (D-10),
`ON CONFLICT`, database-specific full-text search, or an aggregation that JPQL makes unreadable.

**Three rules:**
1. ⭐ **Always `:named` parameters** — Day 119b. Concatenation is injection, and `nativeQuery = true`
   removes JPQL's structural protection.
2. **Alias every column to match the projection's property names**, or the mapping fails at runtime.
3. **Native queries are not portable and are not validated at startup.** A typo is found by the first
   caller, so a test that executes each one is not optional.

## Specifications — dynamic filters, done safely

Day 108's problem: a search endpoint with eight optional filters. String-concatenating a `WHERE`
clause is injection; writing 2⁸ query methods is absurd.

```java
class OrderSpecs {
    static Specification<Order> hasStatus(OrderStatus s) {
        return s == null ? null : (root, q, cb) -> cb.equal(root.get("status"), s);
    }
    static Specification<Order> placedAfter(Instant t) {
        return t == null ? null : (root, q, cb) -> cb.greaterThan(root.get("placedAt"), t);
    }
}

Page<Order> results = repo.findAll(
        Specification.where(hasStatus(status)).and(placedAfter(from)), pageable);
```

**The Criteria API builds the query as a tree, so values are always bound parameters — injection is
structurally impossible**, which is the real reason to use it over string building.

**Two costs, stated honestly:** Criteria code is verbose and hard to read, and `root.get("status")`
is a **string** — a renamed field fails at runtime, not compile time. The JPA metamodel generator
(`Order_.status`) fixes the second and is worth enabling. If your query is static, plain JPQL is more
readable; Specifications earn their place only for genuinely dynamic filters.

**And the N+1 warning:** `Specification` returns entities, so it inherits every fetch concern from
Day 160. Combine with `@EntityGraph` on the repository method, or accept `default_batch_fetch_size`
as the floor.

# Part 4 — Reading a lot of rows without dying

```java
@Query("select o from Order o where o.placedAt < :cutoff")
@QueryHints(@QueryHint(name = HINT_FETCH_SIZE, value = "500"))       // ⭐ JDBC fetch size
Stream<Order> streamOld(@Param("cutoff") Instant cutoff);
```

```java
@Transactional(readOnly = true)
public void archive(Instant cutoff) {
    try (Stream<Order> stream = repo.streamOld(cutoff)) {            // ⭐ MUST close
        Iterator<Order> it = stream.iterator();
        int n = 0;
        while (it.hasNext()) {
            archive(it.next());
            if (++n % 500 == 0) {
                em.flush();
                em.clear();                                          // ⭐⭐ or you OOM anyway
            }
        }
    }
}
```

**`em.clear()` is the line that makes this work.** Streaming avoids materialising the result list —
but every entity you touch is still added to the persistence context, which grows without bound until
the transaction ends. Streaming a million rows without clearing gives you the same
`OutOfMemoryError` you were avoiding, just later. Day 162 explains the mechanism.

**Also required on PostgreSQL: `HINT_FETCH_SIZE`.** Without it the driver buffers the entire result
set in memory before returning the first row, defeating streaming completely. (PostgreSQL also
requires autocommit off, which `@Transactional` gives you.)

**The honest alternative:** for a genuine bulk operation, a single `update`/`delete` statement or a
`JdbcClient` batch beats streaming entities. Day 162 covers what bulk statements cost.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Loading entities to build a read-only DTO | proxies, snapshots, double memory, for data you discard |
| Interface projection with a `@Value`/default method | becomes an open projection; loads the whole entity silently |
| `Object[]` results | index-and-cast; breaks on any select-list change |
| Native query with concatenated parameters | Day 119b injection |
| Native query column aliases not matching | runtime mapping failure |
| No test executing each native query | typos found by the first user |
| `Specification` without `@EntityGraph` | Day 160's N+1, unchanged |
| String field names in Criteria without the metamodel | renames break at runtime |
| Streaming without `em.clear()` | OOM anyway |
| Streaming without a fetch-size hint on PostgreSQL | driver buffers everything |
| Not closing the `Stream` | connection and cursor leak (Day 156) |
| `@EntityGraph(type = LOAD)` by habit | unlisted attributes keep mapping defaults; graph no longer complete |

## Interview questions

**Q: How do you avoid loading entities for a read?**
A constructor projection into a record — one query, only the columns needed, no proxies, no
persistence-context registration, no dirty-check snapshot, and N+1 is impossible because there is no
lazy reference to trigger. Interface projections are lighter to write, as long as they stay closed.

**Q: What does an entity actually cost over a projection?**
Instantiation plus a proxy per association, registration in the persistence context, and a full
field snapshot for dirty checking — roughly double the memory and a per-field comparison at flush,
for data being serialized and thrown away.

**Q: `join fetch` or `@EntityGraph`?**
Same effect. `@EntityGraph` is cleaner for `@ManyToOne`s and composes with derived query methods;
`join fetch` when I am already writing JPQL or need `where` conditions on the joined collection. Both
are for when I need managed entities — if I am only reading, a projection beats both.

**Q: Why use Specifications?**
Dynamic filters. The Criteria API builds a tree, so values are always bound parameters and injection
is structurally impossible — unlike concatenating a `WHERE` clause. The cost is verbosity and
string-based field names, which the metamodel generator fixes.

**Q: How do you process a million rows?**
Stream with a JDBC fetch-size hint, in a read-only transaction, clearing the persistence context
every few hundred rows — otherwise it grows unbounded and I OOM regardless. Though for a genuine bulk
update, one SQL statement beats all of it.

## 🎙️ Articulation drill

Two minutes: **"How do you fetch data efficiently with JPA?"**

Start from the insight that most work is reading and reading does not need entities — then justify it
with what an entity costs: proxies, persistence-context registration, and a full snapshot for dirty
checking. Projections for reads, `@EntityGraph` or `join fetch` when you need managed entities to
modify, Specifications for dynamic filters because Criteria makes injection structurally impossible.
Close on the large-result case: stream with a fetch-size hint and clear the persistence context
periodically, or you get the out-of-memory error you were trying to avoid.
