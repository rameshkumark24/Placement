# Part 1 — Indexes, and what carries over

```javascript
db.orders.createIndex({ customerId: 1 })
db.orders.createIndex({ customerId: 1, placedAt: -1 })           // ⭐ compound
db.orders.createIndex({ orderNumber: 1 }, { unique: true })
db.orders.createIndex({ status: 1 }, { partialFilterExpression: { status: "PENDING" } })  // ⭐ partial
db.orders.createIndex({ "items.sku": 1 })                        // ⭐ multikey — indexes array elements
db.orders.createIndex({ description: "text" })                   // text search
db.stores.createIndex({ location: "2dsphere" })                  // geospatial
db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })   // ⭐⭐ TTL index
```

**⭐ Day 190's leftmost-prefix rule applies unchanged**: `{ customerId: 1, placedAt: -1 }` serves
queries on `customerId`, and on both — **not on `placedAt` alone.**

## ⭐ The extra clause: the ESR rule

> **⭐ Equality, Sort, Range — in that order.**

```javascript
db.orders.find({ status: "PENDING", placedAt: { $gt: cutoff } }).sort({ total: -1 })
db.orders.createIndex({ status: 1, total: -1, placedAt: 1 })     // ⭐ E, S, R
```

**⭐ MongoDB's version differs from PostgreSQL's "equality then range" because sort placement is
explicit and matters more.** If the sort field comes after the range field, **MongoDB must perform an
in-memory sort** — and that sort is capped at 32 MB by default:

```
⭐ "Sort exceeded memory limit of 33554432 bytes"
```

**⭐ That error is a hard failure, not a slow query**, which is stricter than PostgreSQL's spill to
disk (Day 191). `allowDiskUse: true` on an aggregation permits spilling, but **the right fix is an
index that provides the sort order** — Day 190's rule 3, with a harder consequence for ignoring it.

## ⭐ Multikey indexes — the array feature with a sharp edge

```javascript
db.orders.createIndex({ "items.sku": 1 })      // ⭐ one index entry PER ARRAY ELEMENT
```

**⭐ A document with 50 items produces 50 index entries.** So multikey indexes are larger and more
expensive to maintain than they look, and **a compound index cannot have two multikey fields** —
that would be a cartesian product of entries, and MongoDB refuses to create it.

**⭐ This constrains Day 211's embedding decisions**: embedding two arrays you both need to query
means you cannot index them together.

## ⭐ TTL indexes — the feature with no PostgreSQL equivalent

```javascript
db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })
```

**⭐ Documents are deleted automatically once past `expiresAt`.** Excellent for sessions, tokens and
temporary data — this is Day 113's session expiry handled by the database.

⚠️ **⭐ Deletion runs about once a minute, so documents live past their expiry briefly** — never rely
on a TTL index for a security boundary. **Check the expiry in your query too**, exactly as you would
not rely on a cache TTL for authorization.

## ⭐ Reading the plan

```javascript
db.orders.find({ customerId: 42 }).explain("executionStats")
```

```
"winningPlan": { "stage": "IXSCAN", "indexName": "customerId_1" }
"executionStats": {
  "nReturned": 12,
  ⭐ "totalKeysExamined": 12,
  ⭐ "totalDocsExamined": 12,
  "executionTimeMillis": 0
}
```

**⭐ The diagnostic is the ratio of `totalDocsExamined` to `nReturned`** — MongoDB's version of
Day 191's "estimated versus actual".

| Reading | Meaning |
|---|---|
| ⭐ `docsExamined ≈ nReturned` | ⭐ the index is doing its job |
| ⭐ `docsExamined >> nReturned` | ⭐ **scanning and discarding — a wrong or missing index** |
| ⭐ `keysExamined >> nReturned` | the index is used but not selective |
| ⭐ **`COLLSCAN`** | ⭐ **no index used at all** |
| ⭐ **`SORT` stage present** | ⭐ **in-memory sort — the 32 MB risk** |

**⭐ A `SORT` stage in the winning plan is the thing to hunt for**, because it is the one that fails
outright rather than degrading.

```javascript
db.setProfilingLevel(1, { slowms: 100 })      // ⭐ log slow operations
db.system.profile.find().sort({ millis: -1 }).limit(10)
```

**⭐ The profiler is MongoDB's `pg_stat_statements`** (Day 202) — and **the same discipline applies:
look at total cost, not just the slowest single operation.**

# Part 2 — The aggregation pipeline

```javascript
db.orders.aggregate([
  { $match: { placedAt: { $gte: cutoff }, status: "DELIVERED" } },   // ⭐⭐ FILTER FIRST
  { $unwind: "$items" },                                              // ⭐ array → one doc per element
  { $group: { _id: "$items.sku",
              revenue: { $sum: { $multiply: ["$items.qty", "$items.unitPrice"] } },
              units:   { $sum: "$items.qty" } } },
  { $sort: { revenue: -1 } },
  { $limit: 20 },
  { $lookup: { from: "products", localField: "_id", foreignField: "sku", as: "product" } },
  { $project: { sku: "$_id", revenue: 1, units: 1, name: { $first: "$product.name" }, _id: 0 } }
])
```

**Compare the SQL:**

```sql
select oi.sku, p.name, sum(oi.qty * oi.unit_price) as revenue, sum(oi.qty) as units
from order_items oi
join orders o   on o.id = oi.order_id
join products p on p.sku = oi.sku
where o.placed_at >= :cutoff and o.status = 'DELIVERED'
group by oi.sku, p.name order by revenue desc limit 20;
```

**⭐ Be honest about this comparison: the SQL is shorter, more readable, and more familiar to more
people.** The aggregation pipeline is powerful and it is not a productivity win for relational-shaped
reporting — which is Day 210's warning made concrete.

## ⭐⭐ The two rules that decide pipeline performance

> **⭐ Rule 1 — `$match` first, and as narrowly as possible.**

**⭐ Only a `$match` at the start of the pipeline can use an index.** Once `$group`, `$unwind` or
`$project` has run, the documents are intermediate results with no index behind them. A `$match`
placed after a `$group` filters in memory over everything.

**⭐ MongoDB's optimiser moves some `$match` stages earlier automatically**, but not through
`$group`, `$unwind` or most `$project` stages. **Write it first yourself.**

> **⭐ Rule 2 — `$project` early to drop fields you do not need.**

Less data through each stage means less memory and less risk of the limits below.

## ⭐ The limits that bite

| Limit | Value | Fix |
|---|---|---|
| ⭐ **Per-stage memory** | ⭐ **100 MB** | ⭐ `allowDiskUse: true`, or `$match` harder |
| ⭐ **Result document size** | 16 MB | ⭐ use a cursor, or `$limit` |
| In-memory sort (find) | 32 MB | ⭐ an index providing the order |
| `$lookup` | ⭐ executes per input document | ⭐ **`$match` and `$limit` before it** |

**⭐ `$lookup` after `$limit` rather than before is often a hundred-fold difference** — look up 20
products, not 400,000. **It is the pipeline's version of Day 152's N+1 lesson**, and the ordering in
the example above is deliberate.

## Useful stages

| Stage | Use |
|---|---|
| ⭐ `$facet` | ⭐ several aggregations in one pass — counts and a page together |
| `$bucket` / `$bucketAuto` | histograms |
| ⭐ `$merge` / `$out` | ⭐ write results to a collection — **a materialised view** (Day 188) |
| `$graphLookup` | recursive traversal — Day 188's recursive CTE |
| ⭐ `$setWindowFields` | ⭐ window functions — D-09, arriving in MongoDB |

```javascript
// ⭐ $merge = a materialised view, refreshed on a schedule (Day 178)
{ $merge: { into: "daily_revenue", on: "_id", whenMatched: "replace" } }
```

**⭐ Day 188's argument transfers exactly: an expensive aggregation that feeds a dashboard should be
precomputed with `$merge` on a schedule**, not run live per request.

# Part 3 — The operational differences worth knowing

## ⭐ Index builds

```javascript
db.orders.createIndex({ status: 1 })     // ⭐ MongoDB 4.2+: builds without blocking writes by default
```

**⭐ Unlike PostgreSQL, where `CREATE INDEX CONCURRENTLY` is opt-in** (Day 189), MongoDB builds
non-blocking by default on modern versions. **Still build during low traffic** — it consumes
significant I/O and memory.

## ⭐ The working set must fit in memory

**⭐ MongoDB's WiredTiger cache defaults to about 50% of RAM**, and — like PostgreSQL (Day 186) — it
relies on the OS page cache as a second tier.

```javascript
db.serverStatus().wiredTiger.cache
// ⭐ "bytes read into cache" rising steadily = the working set exceeds the cache
```

**⭐ Indexes especially must fit.** An index that no longer fits falls off a performance cliff rather
than degrading smoothly — Day 189's warning, unchanged.

## ⭐ Covered queries

```javascript
db.orders.createIndex({ customerId: 1, status: 1 })
db.orders.find({ customerId: 42 }, { status: 1, _id: 0 }).explain()
// ⭐ "stage": "PROJECTION_COVERED" — no document read at all
```

**⭐ Day 189's index-only scan.** Note `_id: 0` is required — `_id` is returned by default and is not
in the index, which would force a document fetch. **That single omission is why most attempted
covered queries are not covered.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Ignoring ESR | an in-memory sort that fails at 32 MB |
| Sort field after the range field | same |
| ⭐ `$match` late in the pipeline | no index; filters in memory over everything |
| ⭐ `$lookup` before `$limit` | lookups per input document instead of per result |
| Not projecting early | more data through every stage |
| ⭐ Two multikey fields in one compound index | MongoDB refuses; discovered late |
| Multikey on large arrays | one index entry per element |
| ⭐ Relying on a TTL index for security | deletion is ~1 minute behind |
| Missing `_id: 0` in a covered query | fetches the document anyway |
| ⭐ Ignoring `docsExamined` vs `nReturned` | the key diagnostic, unused |
| Not using the profiler | Day 202's discipline, skipped |
| Live aggregations for dashboards | ⭐ use `$merge` and a schedule |
| Index build during peak | heavy I/O even when non-blocking |

## Interview questions

**Q: How do you design a MongoDB index for a query?**
ESR — equality fields first, then the sort field, then range fields. The sort position is the part
people miss: if the sort field comes after a range field, MongoDB does an in-memory sort, and that
fails outright at 32 megabytes rather than spilling to disk. So the index has to supply the order.

**Q: How do you read `explain` output?**
The ratio of `totalDocsExamined` to `nReturned`. If they are close, the index is doing its job; if
documents examined vastly exceeds documents returned, I am scanning and discarding, which means a
missing or wrong index. A `COLLSCAN` means no index at all, and a `SORT` stage means an in-memory
sort I should have indexed away.

**Q: What are the rules for an aggregation pipeline?**
`$match` first and as narrowly as possible, because only a leading `$match` can use an index —
after a `$group` or `$unwind` the documents are intermediate results with nothing behind them.
Project early to shrink what flows through. And put `$lookup` after `$limit`, because it runs per
input document, so looking up twenty results instead of four hundred thousand inputs is a hundredfold
difference.

**Q: How does aggregation compare to SQL?**
It is capable — it has grouping, joins via `$lookup`, recursion via `$graphLookup` and window
functions via `$setWindowFields`. It is also longer and harder to read for relational-shaped
reporting, which is one of the honest costs of choosing MongoDB for data that is relational.

**Q: What is a TTL index good for, and what is its limit?**
Automatic expiry of sessions, tokens and temporary data — the database deletes them for you. But the
background deletion runs about once a minute, so documents can outlive their expiry briefly. I never
rely on it as a security boundary; the query checks the expiry too.

## 🎙️ Articulation drill

Two minutes: **"How do you make a MongoDB query fast?"**

ESR for the index, and explain the sort placement specifically — because an in-memory sort fails at
32 MB rather than spilling, which is a harder failure than the relational equivalent. Then `explain`,
and give the one ratio you look at: documents examined against documents returned. For aggregations,
`$match` first because only a leading match can use an index, and `$lookup` after `$limit` because it
runs per input document. Close on the honest note: for relational-shaped reporting the SQL equivalent
is shorter and clearer, and that is a real cost of the choice.
