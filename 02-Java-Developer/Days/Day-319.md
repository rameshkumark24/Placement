# Part 1 — Snake & Ladder: the over-modelling test

```java
class Snake  { int head; int tail; }      // ⭐ ← two classes
class Ladder { int start; int end; }      // ⭐ ← for one concept
```

> **⭐ A snake and a ladder are the same thing: a jump from one square to another. One goes down, one
> goes up.** `record Jump(int from, int to)` — and `to > from` is a ladder.

**⭐ Say why it matters, because "fewer classes" is not the reason:** with one type, the board is a
`Map<Integer, Integer>` and the move logic is one lookup. **With two types, every rule — chained
jumps, validation, rendering — is written twice**, and the two copies drift.

| Element | ⭐ Model |
|---|---|
| Board | ⭐ `Map<Integer, Jump>` + a size |
| Dice | ⭐ **an interface** — `Dice.roll()`. Six-sided, loaded, or **fixed for tests** |
| Player | ⭐ id + position; a `Deque<Player>` for turn order |
| Game | the loop, the win check, the rule variants |

**⭐ The probes, and each has a real answer:**

| Probe | ⭐ Answer |
|---|---|
| ⭐ **Exact landing to win?** | ⭐ a rule variant — overshoot bounces back, or the move is void. **Ask** |
| Roll a 6 → roll again | a rule, with a cap (three sixes = turn lost) |
| ⭐ **A jump landing on another jump** | ⭐ **chain it in a loop — and bound the loop, because a cycle hangs the game** |
| Multiple dice | the `Dice` interface already covers it |
| ⭐ **Testing** | ⭐ **inject a scripted `Dice` — a game with random dice cannot be unit tested** |

> **⭐ The `Dice` interface is the highest-value line in this problem** — it is Day 300's `Clock` port
> in a different costume, and it turns an untestable game into a deterministic one.

# Part 2 — ⭐⭐ Chess: where legality actually lives

## ⭐ The one place inheritance is right

**⭐ Day 311 argued against `Car extends Vehicle`. Chess is the opposite case, and the contrast is
worth stating out loud:**

```java
public abstract class Piece {
    protected final Colour colour;
    // ⭐ PSEUDO-legal: does this piece move like that, and is the path clear?
    public abstract boolean canReach(Board board, Square from, Square to);
}

final class Bishop extends Piece {
    public boolean canReach(Board b, Square from, Square to) {
        return from.isDiagonalTo(to) && b.isPathClear(from, to);
    }
}
```

> **⭐ "Vehicle types differ in data, so an enum. Chess pieces differ in *behaviour* — a bishop and a
> knight compute completely different move sets — so subclasses."** Making that comparison
> unprompted demonstrates that Day 092's rule is a judgement, not a slogan.

**⭐ The alternative worth naming:** a `MovementStrategy` per piece type, composed rather than
inherited — **better if a piece can change its movement** (fairy chess variants, promotion). **Say
you would use inheritance here and switch to strategy if variants were in scope.**

## ⭐⭐ The insight the problem exists to test

```
⭐ Pseudo-legal: the piece moves that way and the path is clear.
⭐ LEGAL:        pseudo-legal AND it does not leave YOUR OWN KING in check.
```

**⭐ You cannot determine that by looking at the piece, the source square, or the target square.**
A pinned bishop moves like a bishop and its path is clear — **and the move is still illegal.**

```java
public boolean isLegal(Move move) {
    if (!move.piece().canReach(board, move.from(), move.to())) return false;   // ⭐ pseudo-legal
    Board after = board.apply(move);                                           // ⭐⭐ SIMULATE
    return !after.isInCheck(move.piece().colour());                            // ⭐ then evaluate
}
```

| ⭐ Consequence | ⭐ Design impact |
|---|---|
| ⭐ **You must be able to apply a move without committing** | ⭐ **an immutable board, or apply/undo** |
| ⭐ `isInCheck` needs every enemy move | ⭐ generate opponent pseudo-legal moves against the king's square |
| ⭐ **Checkmate = in check AND no legal move exists** | ⭐ **generate all legal moves; empty means mate** |
| ⭐ **Stalemate = NOT in check AND no legal move** | ⭐ **same computation, opposite check flag — say this** |
| Cost | ⭐ each candidate move triggers a full evaluation — fine at this scale, and worth naming |

> **⭐ Checkmate and stalemate falling out of the same computation, differing only by whether you are
> currently in check, is the most satisfying thing to say in this problem** — and it proves the model
> is right.

## ⭐ The three special moves — and what each one breaks

**⭐ Interviewers use these deliberately, because each destroys a different naive assumption.**

| Move | ⭐ What it breaks | ⭐ What the model needs |
|---|---|---|
| ⭐ **Castling** | ⭐ "the position is enough" | ⭐⭐ **history — has this king or rook EVER moved?** Plus: not in check, not through check, not into check |
| ⭐ **En passant** | ⭐ "a capture happens on the target square" | ⭐⭐ **the PREVIOUS move — and it is only legal immediately** |
| ⭐ **Promotion** | ⭐ "a piece keeps its type" | ⭐ the move carries a chosen piece type; **the default-to-queen assumption is wrong (underpromotion)** |

> **⭐ The design conclusion, and it is the real deliverable: the board is not a position — it is a
> position plus a move history.** Three separate rules need history, so a design that stores only the
> 8×8 grid cannot express the game. **State this as a conclusion you reached, not a fact you recall.**

⚠️ **Threefold repetition and the fifty-move rule need history too** — repetition needs a hash of every
past position (Zobrist hashing is the standard trick). **Mention it; do not build it.**

## ⭐ Undo, and the command pattern

```java
public record Move(Piece piece, Square from, Square to,
                   Optional<Piece> captured,        // ⭐ REQUIRED for undo
                   Optional<PieceType> promotedTo,
                   boolean wasCastling, Optional<Square> enPassantCaptured) { }
```

**⭐ A move must record what it destroyed, or it cannot be undone** — and undo is needed by the
simulation in `isLegal` anyway if the board is mutable. **Immutable boards avoid this entirely at the
cost of allocation; say which you chose and why.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Separate `Snake` and `Ladder` | ⭐ every rule written twice, then they drift |
| ⭐ A concrete `Random` dice | ⭐ **the game cannot be unit tested** |
| Unbounded chained jumps | a cycle hangs the game |
| ⭐ Not asking about exact landing | you implemented a variant nobody agreed |
| ⭐⭐ **Legality decided from the piece alone** | ⭐⭐ **pinned pieces move; the model is wrong** |
| ⭐ No way to apply a move speculatively | ⭐ check detection is impossible |
| ⭐ Checkmate special-cased | ⭐ it is "no legal moves + in check" — same code as stalemate |
| ⭐ **A board with no history** | ⭐⭐ **castling, en passant and repetition cannot be expressed** |
| Auto-promoting to queen | underpromotion is legal and sometimes necessary |
| A move that does not record the captured piece | undo is impossible |
| ⭐ Enum-with-switch for piece movement | six unrelated algorithms in one method |

## Interview questions

**Q: How do you model snakes and ladders?**
As one concept — a jump from one square to another, where upward is a ladder. Two classes means every
rule is written twice and the copies drift. I also make the dice an interface, because a game driven
by a real random source cannot be unit tested; a scripted dice makes the whole thing deterministic.

**Q: Chess pieces — inheritance, or an enum with a switch?**
Inheritance here, and this is the contrast with vehicle types in the parking problem. Vehicles differ
in data, so an enum. A bishop and a knight compute genuinely different move sets, so behaviour
differs and subclasses earn their place. If pieces could change how they move — variants, or richer
promotion — I would compose a movement strategy instead.

**Q: How do you decide whether a move is legal?**
You cannot decide it from the piece. A pinned bishop moves like a bishop with a clear path and the
move is still illegal. So legality is two stages: pseudo-legal, meaning the piece moves that way and
the path is clear; then simulate the move on a copy of the board and check whether your own king is
attacked. That requirement — applying a move speculatively — is what forces either an immutable board
or an apply/undo pair.

**Q: How do you detect checkmate?**
Generate every legal move for the side to play. If there are none and the king is in check, it is
checkmate; if there are none and the king is not in check, it is stalemate. Both fall out of the same
computation, differing only by the check flag, which is a good sign the model is right.

**Q: What does castling tell you about your design?**
That a board position is not enough. Castling depends on whether the king and rook have ever moved,
en passant depends on the immediately preceding move, and threefold repetition depends on every
previous position. Three separate rules need history, so the board has to be position plus move
history — that is the conclusion the special moves force.

## Mini task

1. Implement Snake & Ladder with **one `Jump` type** and a `Dice` interface. Write a **fully
   deterministic** game test with a scripted dice.
2. Add chained jumps **with a bound**, and write the test where a cycle would otherwise hang.
3. Implement the exact-landing rule **both ways** behind a flag, and note that you had to ask.
4. ⭐ Implement chess **pseudo-legal** movement for all six pieces.
5. ⭐⭐ **Write the pinned-piece test**: a bishop that can reach the square but whose move exposes the
   king. **Confirm your pseudo-legal code allows it, then add simulation and confirm it is refused.**
6. Implement `isInCheck` and then **checkmate and stalemate from the same generator.** Test with
   Fool's Mate and a known stalemate position.
7. ⭐ Add **castling** and watch it force move history into the board. Test all four illegal cases:
   king moved, rook moved, through check, into check.
8. ⭐ Add **en passant** and confirm it is only legal on the immediately following move.
9. Add **promotion with a chosen type** and test underpromotion to a knight.
10. Implement undo with the captured piece recorded, and **assert board equality after
    move-then-undo** over 1,000 random legal moves.

## 🎙️ Articulation drill

**Three minutes:** *"Design chess. Start with how you decide whether a move is legal."*

**⭐ The marker is one sentence: "I can't decide legality by looking at the piece — a pinned bishop
still moves like a bishop, so I have to apply the move to a copy of the board and ask whether my own
king is attacked."** Everything else in the design follows from it: immutable boards or undo, move
generation, and checkmate detection.

**⭐ The second marker: you reach "the board must include move history" as a conclusion drawn from
castling and en passant**, rather than asserting it up front. Showing the derivation is what
distinguishes designing from remembering.
