# Day 269 🏗️

**P-269** · Search and reporting — the read path that has different rules

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Reporting is where a well-designed transactional schema meets a genuinely different access
> pattern**, and forcing them through the same code is how projects acquire an eight-second dashboard
> query and a set of unreadable Criteria expressions.
>
> Day 188 said it plainly: **if the write path and the report path prefer different shapes, the
> report is a materialized view — not a heroically tuned query.**

---

# Part 1 — ⭐ Reporting is not CRUD, and should not use CRUD's tools

**⭐ Three properties make a report different:**

| Property | Consequence |
|---|---|
| ⭐ **It aggregates across many rows** | JPA's per-row machinery is pure overhead |
| ⭐ **It is read-only and tolerates staleness** | ⭐ so it can be precomputed |
| ⭐ **It needs SQL features JPQL cannot express** | window functions, CTEs, `GROUPING SETS` |

```
⭐ Use JdbcClient for reports (Day 156). Not JPA. Not Criteria.
```

**⭐ Day 157's argument: forcing every query through JPA produces unreadable Criteria
reimplementations of `GROUP BY`.** A report is a place where SQL is the better language, and a
`JdbcClient` fragment on your repository (Day 163) keeps the caller's view clean.

```
⭐ .sql("""...""").param("from", from).query(RevenueByDay.class).list()
```

**⭐ Bound parameters always** (Day 163b) — a report is where people concatenate, because the query is
built from a filter set.

## ⭐ Use the SQL you learned

**⭐ D-09's window functions and D-10's CTEs exist for exactly this**, and using them is both simpler
and faster than doing the work in Java:

| Need | ⭐ SQL |
|---|---|
| Running totals, rank within group | ⭐ window functions |
| Hierarchies, recursive traversal | ⭐ recursive CTE |
| Multi-level subtotals | `GROUPING SETS` / `ROLLUP` |
| "Top N per group" | ⭐ `row_number() over (partition by ...)` |

**⭐ The "top N per group" case is worth calling out**: done in Java it is N+1 queries or an
in-memory sort of everything; done with a window function it is one query. **If you have that pattern
in your project, rewrite it today** — it is a good before-and-after.

# Part 2 — ⭐ Precompute what does not need to be live

> **⭐ Day 193's second question, above the whole optimisation workflow: does this need to be live?**

```
⭐ create materialized view daily_booking_stats as ...
⭐ create unique index on daily_booking_stats (day, room_id);   ⭐⭐ REQUIRED for concurrent refresh
⭐ refresh materialized view concurrently daily_booking_stats;
```

**⭐ Without the unique index, `refresh` takes an `ACCESS EXCLUSIVE` lock and every dashboard reader
blocks** (Day 188). **With `concurrently`, nobody notices.**

**⭐ Refresh from a scheduled job** (Day 264) with all of Day 264's rules — locked or idempotent,
metered, and with a non-execution alert. **A materialized view whose refresh silently stopped is a
dashboard showing last Tuesday's numbers**, and nobody notices for a week.

**⭐ Choose the refresh interval from tolerable staleness** — the same reasoning as a cache TTL
(Day 168). A revenue chart: hourly. A live occupancy count: not a materialized view at all.

**⭐ The alternative, for a counter you read constantly** (Day 188): a maintained count column with a
**reconciliation job**, because it will drift. **The reconciliation is not optional** — and running
it and finding a discrepancy is a good story.

# Part 3 — ⭐ Search, sized honestly

**⭐ Match the tool to the volume and the requirement. Do not skip a step.**

| Requirement | ⭐ Tool | Day |
|---|---|---|
| Exact / prefix match | ⭐ a B-tree index — `like 'foo%'` **does** use one | 189 |
| ⭐ **Substring, modest volume** | ⭐ **trigram GIN** — ⭐ never `like '%x%'` on a B-tree | 190 |
| ⭐ **Real word search with ranking** | ⭐ full-text: generated `tsvector` + `setweight` | 199 |
| ⭐ **Typo tolerance** | ⭐ **full-text *plus* trigram fallback** | 199 |
| Faceting, synonyms, relevance tuning | ⭐ a dedicated engine — ⭐ and a sync problem | 199 |

**⭐ Two implementation details that cost an evening if hit cold** (Day 199):

```
⭐⭐ websearch_to_tsquery for user input — ⭐ to_tsquery THROWS on a stray operator → a 500
⭐⭐ coalesce() around EVERY nullable field — ⭐ one NULL makes the whole document unsearchable
```

**⭐ The second is genuinely nasty**: a booking with a null description silently disappears from all
search results, and nothing errors.

**⭐ And a generated column, not a trigger** (Day 199): a generated `tsvector` **cannot drift**,
whereas a trigger-maintained one is bypassed by bulk updates (Day 162).

## ⭐ The boundary, stated in an ADR

**⭐ Day 199's argument, and the strongest part of it is not size:**

> **⭐ An external search index is a dual write you reconcile forever** (Day 124). A generated column
> cannot drift, is transactionally consistent, and combining search with tenant and status filters is
> one query.

**⭐ Write the ADR: PostgreSQL search, up to N documents, because search is a feature and not the
product — and if we cross that line, the index is fed from the outbox, not dual-written.** That last
clause is what shows you have thought past the decision.

# Part 4 — ⭐ Make it fast, and prove it

## ⭐ Run Day 193's workflow on your own reports

```
⭐ 1. pg_stat_statements ordered by TOTAL time — ⭐ not mean          (Day 202)
⭐ 2. EXPLAIN (ANALYZE, BUFFERS) on the top three
⭐ 3. ⭐ Estimated vs actual rows → the biggest gap first
⭐ 4. ⭐ Multiply by loops → where is the time REALLY?
⭐ 5. ONE hypothesis, ONE change, ⭐ re-measure BUFFERS
```

**⭐ Day 202's insight applies directly here**: your slowest query is probably a report, but your
*most expensive* query is probably a fast one called constantly. **Order by total time and you may
find the report is not the problem at all.**

**⭐ The findings you are most likely to get** (Day 191's patterns):

| Finding | Fix |
|---|---|
| ⭐ `Sort Method: external merge Disk:` | ⭐ raise `work_mem` **for that session only** |
| ⭐ Correlated-column misestimate | ⭐ `CREATE STATISTICS` (Day 190) |
| ⭐ A nested loop over a large outer side | ⭐ fix the estimate, not the plan (Day 192) |
| Missing index on a filter column | add it |
| ⭐ Genuinely necessary aggregation over millions | ⭐ **precompute it** |

## ⭐ Bound every report

```
⭐ 1. A REQUIRED date range — ⭐ no unbounded "all time"
⭐ 2. A statement_timeout for the reporting role   (Day 202)
⭐ 3. Row limits, with pagination
⭐ 4. ⭐ readOnly = true — and route to a replica if you have one (Day 201)
```

**⭐ Point 1 is the highest-value constraint**: an unbounded report is a query whose cost grows
forever, and it will eventually be run by someone at peak traffic.

**⭐ Point 2 is the backstop.** A separate database role for reporting with a `statement_timeout` and
read-only privileges (Day 163b's least privilege) means a runaway report cannot hold a connection
indefinitely or write anything.

## ⭐ Exports — stream them

```
⭐ StreamingResponseBody + NDJSON or CSV, with a JDBC fetch-size hint
⭐ em.clear() every N rows if entities are involved      (Day 161)
```

**⭐ Never build a 500 MB list in memory** (Day 150). And be honest about the limit: the status is
committed before the body is written, **so a mid-stream failure cannot become a 500** (Day 149's
third gap) — NDJSON at least lets the consumer detect truncation.

**⭐ For genuinely large exports, the better design is asynchronous**: enqueue a job (Day 264), write
to object storage, and email a presigned link (Day 267). **That is a nice example of three of this
week's days composing.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Reports through JPA/Criteria | unreadable, slow, and fighting the tool |
| ⭐ Doing aggregation in Java | N+1 or an in-memory sort of everything |
| Concatenating filter values into report SQL | Day 163b — injection |
| ⭐ Materialized view without a unique index | ⭐ `refresh` blocks every reader |
| ⭐ No non-execution alert on the refresh job | ⭐ a dashboard showing last week |
| A counter column with no reconciliation | drift is certain |
| ⭐ `like '%x%'` on a B-tree | a scan, and a DoS vector |
| ⭐ `to_tsquery` on raw user input | ⭐ a user's typo is a 500 |
| ⭐ Missing `coalesce` in the tsvector | ⭐ one NULL hides the whole document |
| A trigger-maintained tsvector | drifts on bulk updates |
| ⭐ Unbounded reports | cost grows forever; run at peak eventually |
| No `statement_timeout` for reporting | a runaway query holds a connection |
| ⭐ Building a large export in memory | OOM under concurrency |
| ⭐ Optimising by mean time | Day 202 — you tune the wrong query |

## 🎤 Defence questions

1. **⭐ Why don't your reports go through JPA?**
2. **⭐ Which report is precomputed, and how did you choose the refresh interval?**
3. **⭐ What happens if the refresh job stops running — and would you know?**
4. **⭐ Why PostgreSQL search rather than Elasticsearch?** (⭐ lead with the sync problem)
5. **⭐ What happens if a user types `c++` into your search box?**
6. **⭐ What did `pg_stat_statements` tell you, and why did you order by total time?**
7. **⭐ Show me a query you improved, with the numbers.**
8. **⭐ How do you export a million rows without an OOM?**
