# Day 299

**L-299** · Layered architecture — and the four ways it rots

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Layers are the default architecture of every Java codebase you will ever join, and almost all
> of them have rotted the same four ways.**
>
> Today is not "layers are bad". Layers are fine. **Today is about knowing exactly what fails, so
> that when Day 300 inverts one dependency you understand precisely which failure it fixes — and
> which three it does not.**

---

# Part 1 — The classic layering, stated honestly

```
   ┌──────────────────────────────┐
   │  Presentation  (controllers) │  ⭐ HTTP in, HTTP out
   ├──────────────────────────────┤
   │  Application   (services)    │  ⭐ use cases, transactions
   ├──────────────────────────────┤
   │  Domain        (?)           │  ⭐ ← in most codebases, EMPTY
   ├──────────────────────────────┤
   │  Persistence   (repositories)│  ⭐ JPA, SQL
   └──────────────────────────────┘
              │  ⭐ dependencies point DOWN
              ▼
```

**⭐ What layering genuinely buys you**, and it is not nothing:

| Benefit | Real? |
|---|---|
| ⭐ **Everyone knows where to look** | ⭐ yes — the biggest real benefit, and underrated |
| ⭐ **One place for cross-cutting concerns** | yes — transactions on the service layer (Day 164) |
| **Testability of the middle** | partly — only if the bottom is mockable |
| **Swappable persistence** | ⭐ **no — see Part 2** |

## ⭐ Closed layers, open layers, and the sinkhole

**⭐ A closed layer must be passed through; an open layer may be skipped.**

Most teams eventually let controllers call repositories directly for simple reads, which opens the
application layer. **This is a real decision with a real trade-off**, and it should be written down
rather than discovered:

| | ⭐ Closed (no skipping) | ⭐ Open (skipping allowed) |
|---|---|---|
| Change isolation | ⭐ strong — a persistence change stops at the service | ⭐ weak — leaks to controllers |
| ⭐ **Pass-through code** | ⭐ **lots — the sinkhole** | little |
| Where transactions go | ⭐ unambiguous | ⭐ **ambiguous — the real cost** |

> **⭐ The architecture sinkhole anti-pattern: a request passes through four layers and each one just
> calls the next.** When 80% of your requests are pure pass-through, the layers are costing you
> typing and buying nothing.

**⭐ The correct response is not to delete the layers, and not to open them everywhere.** It is to
notice that a system where most operations are pass-through is a *CRUD system*, and CRUD systems
should be built as CRUD — two layers, no ceremony — while the parts with real rules get the full
treatment. **Uniform architecture across non-uniform complexity is itself a design error**, and
Day 306's modular monolith is where that observation becomes a structure.

# Part 2 — ⭐⭐ The four rots

## ⭐ Rot 1 — the dependency direction is wrong

```java
// ⭐ domain/Order.java — the "domain" layer
import jakarta.persistence.*;              // ⭐ persistence
import com.fasterxml.jackson.annotation.*; // ⭐ presentation
```

**⭐ The domain layer, which is supposed to be the stable centre, imports the two most volatile
layers.** The arrow on your diagram points down; the arrow in the source points up.

**⭐ The consequence is not theoretical, and it is not "you can't swap the database".** You will never
swap the database. The consequences that actually bite:

| Real consequence | Where you met it |
|---|---|
| ⭐ **Domain tests need a database** | slow tests, so fewer tests get written |
| ⭐ **A JPA quirk changes your model** | Day 158: an id strategy dictating `equals` |
| ⭐ **Serialization drives your fields** | Day 147: entities as DTOs, lazy proxies serialised |
| ⭐ **Business rules cannot be read** | they are buried among annotations |

**⭐ The claim "layering lets you swap the persistence layer" is false in practice and you should stop
making it in interviews.** With JPA entities as the domain model, the persistence choice is *in* the
domain. **Day 300's fix is real, but its benefit is testability and change locality — not database
portability.**

## ⭐ Rot 2 — the domain layer is empty (the anemic model)

```java
class Order {                          // ⭐ 40 fields
    private OrderStatus status;        // ⭐ 40 getters, 40 setters
}                                      // ⭐ zero behaviour

class OrderService {                   // ⭐ 2,400 lines
    void ship(Long id) {
        Order o = repo.findById(id).orElseThrow();
        if (o.getStatus() != PAID) throw new IllegalStateException();  // ⭐ the rule, outside the object
        if (o.getItems().isEmpty()) throw new IllegalStateException();
        o.setStatus(SHIPPED);          // ⭐ anyone else can also call setStatus
        o.setShippedAt(now());         // ⭐ and forget this line
    }
}
```

**⭐ Two things are wrong, and only the second is fatal.**

1. It is procedural code with data structures. That is a style objection, and Fowler's "anemic domain
   model" critique is often overstated — **plenty of good systems are transaction scripts**, and for
   genuine CRUD that is the right answer.
2. ⭐ **The invariant is not protected.** `setStatus(SHIPPED)` is public. **The rule "only a paid order
   ships" exists in one method, and nothing prevents the second caller** — the batch job, the admin
   endpoint, the migration script — from skipping it.

> **⭐ The diagnostic question: can this object be put into an invalid state by calling its public
> methods?** If yes, the rule lives outside the thing it constrains, and it will eventually be
> bypassed. That is the argument for Day 304–305, and it is a correctness argument, not an
> aesthetic one.

## ⭐ Rot 3 — package by layer means every change is a four-package change

```
com.app.controller.OrderController      ⭐ add one field to an order…
com.app.service.OrderService            ⭐ …touch four packages,
com.app.repository.OrderRepository      ⭐ …in four PRs' worth of diff noise,
com.app.dto.OrderDto                    ⭐ …and nothing is private to the feature
```

**⭐ This is Day 298's logical cohesion, and it has a second effect people miss: nothing can be
package-private.** `OrderService` must be public for the controller package to see it. **Every class
is public, so every class is API, so nothing can be changed safely.**

**⭐ Package by feature (Day 141) fixes both:**

```
com.app.orders.OrderController      ⭐ one feature, one package
com.app.orders.OrderService         ⭐ ← can be package-private
com.app.orders.Order                ⭐ ← internals stay internal
com.app.orders.OrderApi             ⭐ ← the ONE public type others may use
```

> **⭐ The real prize is not tidiness. It is that `package-private` becomes a working access control
> for your module** — the only encapsulation Java gives you for free, and layering throws it away.

## ⭐ Rot 4 — the shared layer becomes a hub

`common`, `core`, `util`, `shared`, `base`. **It starts as three genuine helpers and ends as the
place where anything used twice goes.** Then:

- ⭐ **Everything depends on it**, so every change is high-risk.
- ⭐ **It depends on everything**, because the helpers needed types — so you get **cycles**.
- ⭐ **Nobody owns it**, so nothing is ever deleted from it.

**⭐ The rule: a shared module may contain code with no domain knowledge whatsoever.** A `StringUtils`
qualifies. A `OrderHelper` never did.

# Part 3 — ⭐ Detecting rot mechanically

**⭐ Architecture that is not tested is architecture that used to be true.** ArchUnit turns a diagram
into a failing build:

```java
@AnalyzeClasses(packages = "com.app")
class ArchitectureTest {

    @ArchTest  // ⭐ Rot 1
    static final ArchRule domain_is_pure =
        noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("..controller..", "..repository..",
                                "jakarta.persistence..", "org.springframework..");

    @ArchTest  // ⭐ Rot 4 — cycles
    static final ArchRule no_cycles =
        slices().matching("com.app.(*)..").should().beFreeOfCycles();

    @ArchTest  // ⭐ layering, enforced
    static final ArchRule layers = layeredArchitecture().consideringAllDependencies()
        .layer("Web").definedBy("..controller..")
        .layer("App").definedBy("..service..")
        .layer("Persistence").definedBy("..repository..")
        .whereLayer("Web").mayNotBeAccessedByAnyLayer()
        .whereLayer("Persistence").mayOnlyBeAccessedByLayers("App");
}
```

| Check | ⭐ Catches |
|---|---|
| ⭐ **No cycles between slices** | ⭐ **the single highest-value rule — run it first** |
| Domain imports nothing framework | Rot 1 |
| Controllers never touch repositories | the open-layer drift |
| ⭐ **Entities never leave the persistence package** | ⭐ Day 147, enforced by the build |
| `@Transactional` only on the application layer | Day 164's boundary, enforced |

**⭐ Add these to an existing codebase as a ratchet, not a gate**: freeze the current violations, fail
the build on *new* ones. A rule that fails on day one gets deleted; a rule that fails only on
regressions gets kept.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Claiming layers let you swap the database | ⭐ untrue with JPA entities as the model — and interviewers know |
| ⭐ Entities annotated for JPA *and* Jackson | ⭐ two volatile layers pinned into the stable one |
| ⭐ Public setters on a state field | ⭐ **the invariant is bypassable — the fatal one** |
| Opening layers ad hoc | the transaction boundary becomes ambiguous |
| ⭐ Full ceremony on genuine CRUD | ⭐ the sinkhole — pass-through code with no benefit |
| Package by layer | four-package changes; nothing can be package-private |
| ⭐ A `common` module with domain knowledge | ⭐ a hub with cycles and no owner |
| ⭐ No ArchUnit tests | ⭐ the diagram documents the past |
| Adding arch tests as a hard gate on legacy code | 400 failures on day one; the rules get deleted |

## Interview questions

**Q: What is wrong with layered architecture?**
Nothing inherently — it is legible and it gives cross-cutting concerns a home. What rots is
specific: the domain ends up importing persistence and serialization, so the stable layer depends on
the volatile ones; the domain layer ends up empty, so invariants sit in services where any caller can
bypass them; packaging by layer forces everything public; and the shared module becomes a hub with
cycles. Three of those four are fixable without abandoning layers.

**Q: Does layering let you replace your database?**
Not with JPA entities as your model — the persistence technology is in your domain types, so it is
not a swap, it is a rewrite. The honest benefits are that domain logic becomes testable without
infrastructure and that a persistence change stops at one boundary. I would not claim portability I
have not demonstrated.

**Q: What is an anemic domain model, and is it always wrong?**
Data classes with getters and setters and all behaviour in services. It is not always wrong —
straightforward CRUD is well served by transaction scripts. It becomes wrong the moment an object has
an invariant, because a public setter means the rule can be bypassed by the next caller. That is a
correctness problem, not a style problem.

**Q: How do you stop an architecture from drifting?**
Test it. ArchUnit rules for cycles, dependency direction, and entities not escaping the persistence
package, run in CI. On a legacy codebase I add them as a ratchet — freeze existing violations, fail
only on new ones — because a rule that fails on day one gets deleted rather than fixed.

**Q: What is the architecture sinkhole?**
When most requests pass through every layer without any layer doing work. It is a signal that the
system is mostly CRUD, and the right response is not to delete the layers globally but to stop
applying uniform ceremony to non-uniform complexity — simple modules stay simple, the two modules
with real rules get the full structure.

## Mini task

1. **Draw your flagship's real dependency graph**, not the intended one — `jdeps`, IntelliJ's
   analysis, or ArchUnit. **Find every arrow that points the wrong way.**
2. Add **the cycle rule** to your build. Fix or freeze what it finds.
3. Add **the domain-purity rule**. Count the violations — the count is your Rot 1 score.
4. Take one entity with a status field. **Make every setter that changes state private**, and expose
   named transitions instead. **Compile, and see how many callers were bypassing the rule.**
5. Convert **one feature** from package-by-layer to package-by-feature. Then make everything you can
   package-private. **Note which classes resisted** — those are your real module API.
6. ⭐ Open your `common`/`util` package. **Move anything that mentions a domain concept out of it.**
   What remains is what should have been there.
7. Count your pass-through methods (service methods that only call the repository). **If it is over
   half, write down which parts of the system are genuinely CRUD** — Day 306 needs that list.

invert the persistence dependency and keep the rest"** is an engineering claim with a scope.
