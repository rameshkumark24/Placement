# Day 105

**L-105** · Request validation & the trust boundary — never trust the client

**Time:** 3 hrs · **Mode:** NEW

> One rule underlies every security day in this stage, and today is the day it gets stated precisely:
> **everything that crosses the trust boundary is attacker-controlled until you validate it.**
>
> Not "might be" — *is*. Design as though every request came from someone actively trying to break
> your system, because some of them did.

---

# Part 1 — The trust boundary

## Where it is

```
   ATTACKER-CONTROLLED                    │   YOUR CODE
   ─────────────────────────────────────  │  ─────────────────
   URL path and query string              │
   Every request header                   │   ← THE BOUNDARY
   Cookies                                │      validate here
   Request body                           │
   Uploaded files (name, type, content)   │
   Anything from a browser, mobile app,   │
   or third-party webhook                 │
```

**The client is not your client.** Your React app is not what sends the request — `curl` is, or a
script, or a modified app, or a proxy. The JavaScript you wrote runs on a machine you do not control
and can be edited with the browser's developer tools in ten seconds.

Therefore:

> **Client-side validation is a user-experience feature. It is not a security control.** It exists to
> give instant feedback and reduce round trips. It provides exactly zero protection, and must be
> duplicated on the server without exception.

## What people forget is attacker-controlled

The body is obvious. These are the ones that cause incidents:

| Input | Attack |
|---|---|
| `Host` header | Cache poisoning; password-reset links pointing at the attacker's domain |
| `X-Forwarded-For` | Spoofed IP → bypasses IP rate limiting and allowlists |
| `Referer` | CSRF checks based on it are bypassable |
| `Content-Type` | Parser confusion; bypassing CSRF protections |
| `User-Agent`, `Accept-Language` | Injected into logs and dashboards → log injection, stored XSS |
| Uploaded **filename** | Path traversal (`../../etc/passwd`), null bytes |
| Uploaded **MIME type** | Client-declared and trivially forged |
| Cookie values | Fully controlled unless signed |
| **JWT payload** | Controlled until the signature is verified (Day 114) |
| Webhook payloads | Anyone can POST — until you verify the signature (Day 129) |

**The `Host` header one is worth expanding**, because it is subtle and common: if you build a
password-reset URL as `https://" + request.getHeader("Host") + "/reset?token=…`, an attacker sets
`Host: evil.com`, requests a reset for a victim's email, and the victim receives a legitimate-looking
email whose link sends the token to the attacker. **Use a configured base URL, never the `Host`
header.**

# Part 2 — Validating properly

## Allow-list, never deny-list

```java
// ❌ deny-list: a race against every encoding you have not thought of
if (input.contains("<script>")) reject();      // <ScRiPt>, <img onerror=>, %3Cscript%3E, …

// ✅ allow-list: define what is permitted; everything else is rejected
if (!input.matches("^[a-zA-Z0-9 .,'-]{1,100}$")) reject();
```

> **You cannot enumerate everything bad. You can enumerate what is good.**

Every deny-list in security history has been bypassed. Every one.

## Validate structurally, at the boundary

```java
public record CreateOrderRequest(
        @NotBlank @Size(max = 64)        String customerId,
        @NotEmpty @Size(max = 100)       List<@Valid LineItem> items,
        @NotNull @DecimalMin("0.01") @DecimalMax("1000000.00") BigDecimal declaredTotal,
        @Email @Size(max = 254)          String notifyEmail,
        @Pattern(regexp = "^[A-Z]{2}$")  String countryCode
) { }

public record LineItem(
        @NotBlank @Pattern(regexp = "^[A-Z0-9-]{1,32}$") String sku,
        @Min(1) @Max(999)                                int quantity
) { }
```

Bean Validation annotations are convenient, but the important part is the **checklist** behind them —
apply it whether or not you have a framework:

| Check | Why |
|---|---|
| **Presence** | Required vs optional, explicitly |
| **Type** | `"abc"` in a numeric field |
| **Length / size** | ⚠️ **Every string and every collection.** See below. |
| **Range** | Negative quantities, absurd prices |
| **Format** | Email, date, enum membership, regex — **bounded** (Day 063B) |
| **Cross-field** | End after start, total matching the lines |
| **Business rules** | Does the SKU exist? Is the customer active? |

**Bounding length is not optional**, and it is the check people skip. An unbounded string field is:

- a memory exhaustion vector (a 500 MB "name"),
- a ReDoS amplifier (Day 063B — exponential backtracking needs a long input),
- a database error at insert time instead of a clean `422`,
- and a log-flooding vector.

**Set a maximum request body size at the server level too**, as a backstop for everything you forgot.

## Parse, don't validate

The stronger discipline, and the one worth internalising:

```java
// ❌ validate then pass the raw type around — every later function must trust the check happened
void register(String email) {
    if (!isValid(email)) throw …;
    sendMail(email);              // did anyone validate this? You must go and look.
}

// ✅ parse into a type that cannot hold an invalid value
public record EmailAddress(String value) {
    private static final Pattern SHAPE = Pattern.compile("^[^@\\s]{1,64}@[^@\\s]{1,189}$");
    public EmailAddress {
        Objects.requireNonNull(value);
        if (value.length() > 254 || !SHAPE.matcher(value).matches())
            throw new ValidationException("email", "invalid_format");
    }
}

void register(EmailAddress email) { sendMail(email); }   // ← the TYPE carries the guarantee
```

**Once it is an `EmailAddress`, it is valid — permanently and everywhere.** No downstream function
needs to re-check, and the compiler enforces that raw strings cannot slip through. This is Day 096's
Primitive Obsession fix, applied as a security control.

It is also why Day 062's fail-fast constructor validation matters: the object cannot exist in an
invalid state.

## Mass assignment — the vulnerability inside your DTO

```java
// 💀 binding the request straight to the entity
@PostMapping("/users")
public User create(@RequestBody User user) {          // User has: id, email, role, isVerified…
    return repository.save(user);
}
```

```json
POST /users
{"email": "attacker@evil.com", "password": "x", "role": "ADMIN", "isVerified": true}
```

**You just let the client set their own role.** This is **mass assignment** (OWASP API3), and it is
one of the most common real API vulnerabilities. GitHub was famously compromised this way in 2012.

The fix is a dedicated request DTO containing **only the fields a client is allowed to set**:

```java
public record CreateUserRequest(String email, String password, String displayName) { }

@PostMapping("/users")
public UserResponse create(@Valid @RequestBody CreateUserRequest request) {
    User user = new User(request.email(), hash(request.password()), Role.USER, false);
    return UserResponse.from(repository.save(user));   // ← separate RESPONSE DTO too
}
```

**Separate DTOs in both directions.** The response DTO stops you leaking `password_hash`,
`internal_notes` or `deleted_at` because someone added a column to the entity. **An entity should
never be a wire type**, and this single rule prevents an entire vulnerability class.

*(The same applies to updates: a `PATCH` DTO must not contain `id`, `createdAt`, `role`, or
`balance`.)*

## Validate authorization separately — and always

Validation says the *shape* is right. It says nothing about whether **this caller** may do this.

```java
// ❌ validated, and completely broken
@GetMapping("/orders/{id}")
public Order get(@PathVariable @Pattern(regexp="^ord_[a-z0-9]{8}$") String id) {
    return repository.findById(id).orElseThrow();     // ← ANY user can read ANY order
}

// ✅
public Order get(@PathVariable String id, @AuthenticationPrincipal User caller) {
    Order order = repository.findById(id).orElseThrow(NotFoundException::new);
    if (!order.belongsTo(caller)) throw new NotFoundException();   // 404, not 403 (Day 104)
    return order;
}
```

**IDOR — Insecure Direct Object Reference — is the single most common serious API vulnerability**
(Day 119). It is not a validation failure; it is a *missing authorization check*, and no amount of
input validation prevents it.

The most reliable structural defence is to **scope every query by the caller** rather than fetching
and then checking:

```java
repository.findByIdAndCustomerId(id, caller.id())     // ← cannot return someone else's row
```

That way the check cannot be forgotten, because there is no unscoped query to call.

# Part 3 — Sanitisation, encoding, and where each belongs

**Validate on input. Encode on output.** These are different operations and confusing them causes
both bugs and vulnerabilities.

```java
// Input: reject what is not allowed
if (!name.matches("^[\\p{L} .'-]{1,100}$")) reject();

// Output: encode for the destination context
html.append(HtmlUtils.htmlEscape(name));          // → HTML
sql.setString(1, name);                            // → SQL, via a PREPARED STATEMENT (Day 119b)
json.writeString(name);                            // → JSON, via a real serializer
log.info("user {} registered", sanitiseForLog(name));   // → logs: strip CR/LF
```

**The destination decides the encoding.** A string that is safe in JSON may be dangerous in HTML;
one safe in HTML may break a shell command. **Never** hand-roll escaping — use the library for the
target format.

Two specific ones:

**Log injection.** A `\n` in user input lets an attacker forge log lines — including fake
"authentication successful" entries. Strip or escape CR and LF before logging user data (Day 073A).

**Path traversal.** Day 063 covered the check; it belongs here too:

```java
Path base = Path.of("/srv/uploads").toRealPath();
Path target = base.resolve(userFilename).normalize();
if (!target.startsWith(base)) throw new SecurityException("traversal");
```

Better still: **never use a client-supplied filename as a path.** Generate your own (a UUID) and
store the original name as metadata only.

## Where validation belongs — all four layers

Defence in depth, because each layer catches what the others miss:

| Layer | Catches |
|---|---|
| **Client** | UX only. Zero security value. |
| **API boundary (DTO)** | Shape, type, size, format. Rejects with a clean `422`. |
| **Domain** | Business invariants — the constructor cannot build an invalid object |
| **Database** | `NOT NULL`, `CHECK`, `UNIQUE`, foreign keys — the last line (Day 081) |

**The database layer is not redundant.** It is the only layer that constrains *every* writer —
including a second service, a migration script, and a person with `psql`. Day 081's principle:
constraints belong in the database, and the application check is the convenience.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Relying on client-side validation | Trivially bypassed with `curl` |
| Deny-lists | Bypassed by an encoding you did not think of |
| Unbounded string or collection sizes | Memory exhaustion, ReDoS, DB errors |
| Binding the request body to an entity | **Mass assignment** — the client sets their own role |
| Returning the entity | Leaks columns added later |
| Trusting the `Host` header | Password-reset links to the attacker's domain |
| Trusting `X-Forwarded-For` | Rate limits and allowlists bypassed |
| Trusting a client-declared MIME type | Malicious upload accepted |
| Using a client filename as a path | Path traversal |
| Validating but not authorizing | **IDOR** |
| Fetch-then-check instead of scoped queries | The check gets forgotten |
| Sanitising on input instead of encoding on output | Corrupted data and residual XSS |
| Logging raw user input | Log injection, forged entries |
| Skipping database constraints | Bad data arrives by another path |

## Interview questions

**Q: Why is client-side validation not a security control?**
The client is not under your control — the request can come from `curl`, a modified app or a proxy.
Client validation is UX; every check must exist on the server.

**Q: Allow-list or deny-list?**
Allow-list. You cannot enumerate everything malicious, especially across encodings, but you can
enumerate what is legitimate.

**Q: What is mass assignment and how do you prevent it?**
Binding a request body directly to an entity, so a client can set fields like `role` or `isVerified`.
Prevent it with a dedicated request DTO containing only client-settable fields — and a separate
response DTO so you do not leak columns either.

**Q: What is "parse, don't validate"?**
Convert input into a type that cannot represent an invalid value — an `EmailAddress` rather than a
validated `String`. The guarantee then travels with the type and no downstream code needs to
re-check.

**Q: Which headers are attacker-controlled?**
All of them. `Host` (password-reset link hijacking), `X-Forwarded-For` (rate-limit bypass),
`Referer`, `Content-Type` and `User-Agent` all cause real incidents when trusted.

**Q: Is validation the same as authorization?**
No. Validation checks the shape of the input; authorization checks whether this caller may perform
this operation on this resource. A perfectly validated request can still be IDOR — scope queries by
the caller so the check cannot be omitted.

**Q: Where does validation belong?**
At every layer: the boundary for shape, the domain for invariants, the database for the constraints
that bind every writer. The client layer is UX only.

## Mini task

1. Take an endpoint you have and write out every input crossing the trust boundary — path, query,
   every header, cookies, body. For each, write what an attacker could put there.
2. Build a mass-assignment vulnerability deliberately: bind a request to an entity with a `role`
   field and escalate yourself to admin with `curl`. Then fix it with a request DTO.
3. Do the same in reverse: return the entity and observe `passwordHash` in the response. Fix it with
   a response DTO.
4. Write an `EmailAddress` value type with validation in the constructor. Refactor one method chain
   to take it instead of `String`.
5. Send a 10 MB string in a field with no `@Size` and observe what fails and where. Add the bound and
   a server-level body-size limit.
6. Build the `Host`-header vulnerability: construct a reset URL from the header, then send
   `Host: evil.com` and observe the link.
7. Write an IDOR: fetch by id with no ownership check, and access another user's record. Fix it two
   ways — a check after the fetch, and a scoped query — and argue which is safer.
8. Log a username containing `\n2026-08-14 INFO Authentication successful for admin` and read your
   log file.
9. Add `CHECK` and `NOT NULL` constraints to a table, then try to insert bad data through a path that
   bypasses your application validation.

## 🎙️ Articulation drill

Two minutes: **"How do you validate input in an API?"**

Start with the boundary and the principle that everything crossing it is attacker-controlled. Then:
allow-lists, the full checklist with size bounds emphasised, request and response DTOs to prevent
mass assignment and over-exposure, parse-don't-validate so the type carries the guarantee, and
authorization as a *separate* concern enforced by scoped queries. Close with defence in depth ending
at database constraints.
