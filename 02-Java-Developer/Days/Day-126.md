> File upload looks like a solved problem and is a reliable source of outages and vulnerabilities. The

# Part 1 — Why the naive approach fails

```java
@PostMapping("/upload")
public String upload(@RequestParam MultipartFile file) throws IOException {
    byte[] bytes = file.getBytes();                    // 💀 the WHOLE file in heap
    Files.write(Path.of("/uploads/" + file.getOriginalFilename()), bytes);  // 💀 traversal
    return "ok";
}
```

Five failures:

**1. `getBytes()` loads the entire file into heap.** A 2 GB upload is an `OutOfMemoryError` — and ten
concurrent 200 MB uploads are the same thing.

**2. `getOriginalFilename()` is attacker-controlled** (Day 105). `../../etc/cron.d/evil` writes
outside your directory.

**3. A request thread is held for the entire transfer.** A user on a slow mobile connection uploading
50 MB holds a thread for minutes. Two hundred such users exhaust the pool (Day 069).

**4. The file is on local disk** — lost when the container restarts, invisible to your other
instances, and not backed up.

**5. No size limit, no type validation, no virus scan.**

# Part 2 — ⭐ Presigned URLs

**The architecture that fixes four of the five at once: the client uploads directly to object
storage. The bytes never touch your server.**

```
1. Client  → your API:      "I want to upload invoice.pdf, 2 MB, application/pdf"
2. Your API:                authorize, validate, generate a PRESIGNED URL (5 min expiry)
3. Your API → client:       { uploadUrl, objectKey }
4. Client  → S3 DIRECTLY:   PUT the bytes            ← your server is not involved
5. Client  → your API:      "done, key=uploads/…"
6. Your API:                verify the object exists, check size and type, record it
```

```java
@PostMapping("/uploads/presign")
public PresignResponse presign(@Valid @RequestBody PresignRequest req, @AuthenticationPrincipal User user) {

    if (!ALLOWED_TYPES.contains(req.contentType())) throw new ValidationException("type");
    if (req.sizeBytes() > MAX_SIZE)                 throw new ValidationException("size");

    // ⭐ WE generate the key. The client's filename is metadata only.
    String key = "tenants/%s/users/%s/%s/%s"
            .formatted(user.tenantId(), user.id(), UUID.randomUUID(), sanitise(req.filename()));

    PutObjectRequest put = PutObjectRequest.builder()
            .bucket(bucket).key(key)
            .contentType(req.contentType())
            .contentLength(req.sizeBytes())          // ⭐ binds the size — see below
            .build();

    PresignedPutObjectRequest presigned = presigner.presignPutObject(b -> b
            .signatureDuration(Duration.ofMinutes(5))
            .putObjectRequest(put));

    uploadRepo.recordPending(key, user.id(), req);
    return new PresignResponse(presigned.url().toString(), key);
}
```

| Gain | Why |
|---|---|
| No memory pressure | The bytes never enter your JVM |
| No held threads | Your request is ~5 ms |
| No bandwidth cost through your servers | Often a large saving |
| Scales with S3, not with you | |
| Resumable and multipart for free | S3 handles it |

**The constraints that make it safe** — and getting these wrong is the whole risk:

- **You generate the key**, never the client. Otherwise a client writes to another tenant's prefix.
- **Bind content-type and content-length into the signature.** Without them, the client declares a
  2 MB PDF and uploads a 5 GB executable — the presigned URL permits whatever the signature did not
  constrain.
- **Short expiry** — 5 minutes. A presigned URL is a bearer credential (Day 115b).
- **Verify server-side after the callback.** Do not trust step 5: `HeadObject` and check the real
  size and type. The client may never have uploaded anything.
- **Never presign a `PUT` to a path the client controls.**

For downloads, presign a `GET` with a short expiry — that is how you serve private files without
proxying them, and it is why "our images are behind auth" does not have to mean "our servers stream
every image".

## When you must proxy the upload

Sometimes you cannot avoid it — an on-premise deployment, or a mandatory synchronous virus scan.
**Then stream; never buffer:**

```java
@PostMapping(value = "/upload", consumes = MULTIPART_FORM_DATA_VALUE)
public UploadResponse upload(HttpServletRequest request) throws Exception {
    ServletFileUpload upload = new ServletFileUpload();
    upload.setFileSizeMax(MAX_SIZE);                   // ⭐ enforced DURING the stream
    upload.setSizeMax(MAX_REQUEST_SIZE);

    FileItemIterator it = upload.getItemIterator(request);
    while (it.hasNext()) {
        FileItemStream item = it.next();
        if (item.isFormField()) continue;

        try (InputStream in = item.openStream()) {
            s3.putObject(req -> req.bucket(bucket).key(generatedKey), fromInputStream(in, size));
        }                                              // ← constant memory (Day 063)
    }
}
```

**`setFileSizeMax` aborts mid-stream**, which is the point — a limit that only checks after receiving
2 GB has already cost you the 2 GB.

Spring: `spring.servlet.multipart.max-file-size` and `max-request-size`, plus a limit at the reverse
proxy (`client_max_body_size` in nginx) so oversized requests are rejected before reaching Java at
all.

# Part 3 — Security

**Uploads are one of the highest-risk features in any application**, because you are accepting
attacker-controlled bytes and later serving them.

## The checklist

```java
// 1. NEVER use the client's filename as a path (Day 063, Day 105)
String key = UUID.randomUUID() + extensionFrom(declaredType);
// store the original name as METADATA only

// 2. Content type: verify by MAGIC BYTES, not the declared header
byte[] header = readFirst(bytes, 16);
DetectedType actual = magicBytes.detect(header);          // Apache Tika
if (!ALLOWED.contains(actual)) reject();
if (!actual.matches(declaredContentType)) reject();       // mismatch is itself suspicious

// 3. Extension must match the detected content — no double extensions
if (key.matches(".*\\.(php|jsp|asp|exe|sh|jar)($|\\.).*")) reject();

// 4. Size limits at EVERY layer: proxy, framework, presigned signature

// 5. Virus scanning (ClamAV) — asynchronously, quarantined until clean

// 6. Serve from a DIFFERENT origin, with the right headers
```

**Magic-byte checking is the one people skip.** `Content-Type: image/png` is a client-supplied header
(Day 105) and a `.png` extension is a filename. Only the first bytes of the file tell you what it
actually is — and a file that *declares* PNG but *is* a PHP script is an attack, not a mistake.

## ⭐ Serving uploaded files safely

The vulnerability that makes uploads dangerous is not the upload — it is the **download**.

```
❌ https://app.acme.com/uploads/evil.html
   Same origin as your app ⇒ script in that file runs with your app's cookies and localStorage.
   That is stored XSS with a full session takeover.

✅ https://user-content-acme.com/…       ← a SEPARATE origin
   or presigned S3 URLs on the storage domain
```

```http
Content-Disposition: attachment; filename="report.pdf"    # force download, do not render
X-Content-Type-Options: nosniff                            # ⭐ stop MIME sniffing
Content-Security-Policy: default-src 'none'; sandbox
Content-Type: application/octet-stream                     # for anything not explicitly safe
```

**`nosniff` matters specifically here:** without it, browsers inspect content and may render a file
as HTML despite its declared type — so an "image" containing HTML becomes a script execution.

**Serving user content from your application's origin is how upload features become account
takeover.** GitHub, Google and Discord all use separate content domains for exactly this reason.

## Large files and resumability

**Multipart upload** (S3): split into ≥5 MB parts, upload in parallel, retry individual parts, and
complete. A failed part costs one part, not the whole transfer.

**`tus`** is the open resumable-upload protocol if you need resumability outside S3.

**Always set a lifecycle rule to abort incomplete multipart uploads** after a few days — abandoned
parts are invisible in the bucket listing and **you are billed for them indefinitely**. This is a
genuinely common surprise on a cloud bill.

## Post-processing

```
Upload → PENDING → [ virus scan ] → [ generate thumbnails ] → [ extract text ] → READY
```

**All of it is background work** (Day 124), triggered by an S3 event or your callback. The record
carries a status, and the UI shows "processing" — because a synchronous 30-second image pipeline is
the request-cycle mistake all over again.

# Part 4 — D-16 · NoSQL and CAP

## The families

| Type | Model | Examples | Fits |
|---|---|---|---|
| **Relational** | Tables, SQL, ACID | PostgreSQL, MySQL | ✅ The default |
| **Document** | JSON documents | MongoDB, DynamoDB | Varying shape; aggregate reads |
| **Key-value** | `get`/`put` | Redis, Memcached | Cache, sessions (Day 113) |
| **Wide-column** | Partition + clustering keys | Cassandra, ScyllaDB | Huge write volume, time series |
| **Graph** | Nodes and edges | Neo4j | Traversal — fraud rings, social |
| **Time-series** | Timestamped points | TimescaleDB, InfluxDB | Metrics |
| **Search** | Inverted index | Elasticsearch | Full-text (Day 108) |
| **Vector** | Embeddings + ANN | pgvector, Pinecone | Semantic search |

> **Start relational.** PostgreSQL does JSON (`jsonb`), full-text, geospatial, time-series
> (TimescaleDB) and vectors (`pgvector`) competently. "We need a document database" is very often
> "we need a `jsonb` column".

The honest reasons to add another store: **an access pattern the relational model serves badly**
(deep graph traversal, ranked full-text), or **a scale characteristic it cannot reach** (millions of
writes per second). Not "our data is unstructured" — that usually means the schema has not been
thought about yet.

## ⭐ CAP, stated correctly

> **In the presence of a network Partition, you must choose between Consistency and Availability.**

**What CAP does not say**, and this is where nearly everyone gets it wrong:

- ❌ **"Pick two of three."** Partitions are not a choice — networks fail. **P is mandatory**, so the
  real choice is C or A *during a partition*.
- ❌ **"NoSQL is AP, SQL is CP."** Configuration decides this. Cassandra can be tuned for strong
  consistency; MongoDB defaults to CP.
- ❌ **"C means ACID's consistency."** CAP's C is **linearizability** — every read sees the most
  recent write. ACID's C is declared constraints (Day 117). **Different words, different meanings.**

```
Partition: the cluster splits into two halves that cannot communicate.
  CP  → the minority side REFUSES requests    (correct, unavailable)
  AP  → both sides accept                     (available, divergent — reconcile later)
```

Examples: **CP** — PostgreSQL with synchronous replication, MongoDB, HBase, ZooKeeper. **AP** —
Cassandra and DynamoDB by default, Riak.

**PACELC is the more useful refinement**, and citing it is a strong signal:

> **If Partition: choose A or C. Else (normal operation): choose Latency or Consistency.**

That "else" is what you actually live with daily. There is no partition 99.99% of the time, and you
are still trading latency against consistency on every request — a synchronous replica read is
consistent and slow; an async replica read is fast and possibly stale.

## Consistency models

```
Strong / linearizable   every read sees the latest write
Sequential              all clients see operations in the same order
Causal                  causally-related operations are ordered
Read-your-writes        ⭐ YOU see your own writes            ← the one users notice
Monotonic reads         you never see time go backwards
Eventual                converges, eventually
```

**Read-your-writes is the one that produces bug reports.** A user edits their profile, the write goes
to the primary, the read hits a replica that has not caught up, and the profile shows the old value.
**Fix by routing a user's reads to the primary for a short window after their write**, or by using a
consistency token — Zanzibar's "zookie" (Day 118) is exactly this idea.

## Polyglot persistence

```
PostgreSQL     orders, users, payments        — the source of truth
Redis          sessions, cache, rate limits
Elasticsearch  product search
S3             files
Kafka          event stream
```

**Every store you add costs**: another thing to operate, back up, secure, monitor and staff — plus a
new **consistency problem** between it and your source of truth.

> **One source of truth. Everything else is a derived, rebuildable projection.** If Elasticsearch is
> lost you reindex from PostgreSQL; if PostgreSQL is lost you have an incident.

That rule is what keeps polyglot persistence manageable, and it is the sentence to lead with.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `getBytes()` on an upload | OOM on a large file |
| Client filename as a path | Path traversal |
| Trusting the declared content type | An executable uploaded as an "image" |
| No magic-byte verification | Same |
| No size limit at every layer | Memory and disk exhaustion |
| Files on local disk | Lost on restart; invisible to other instances |
| Serving user content from your origin | **Stored XSS with session access** |
| Missing `nosniff` and `Content-Disposition` | The browser renders it as HTML |
| Presigned URL without content-length bound | A 5 GB upload against a 2 MB signature |
| Client-supplied object key | Writing into another tenant's prefix |
| Trusting the client's "upload complete" | Records that reference nothing |
| No lifecycle rule for incomplete multipart | Invisible, permanent storage charges |
| Synchronous post-processing | The request-cycle mistake again |
| "Pick two of three" for CAP | P is not optional |
| Confusing CAP's C with ACID's C | Two different properties |
| Adding a datastore without a source of truth | An unresolvable consistency problem |

## Interview questions

**Q: How would you handle file uploads at scale?**
Presigned URLs so the client uploads directly to object storage — the bytes never touch the
application, so there is no memory pressure, no held threads and no bandwidth cost. The server
authorizes, generates the key itself, binds content-type and length into the signature, and verifies
the object afterwards with `HeadObject`.

**Q: What must a presigned URL constrain?**
The key (server-generated), the content type, the content length, and a short expiry — it is a bearer
credential. Anything not bound by the signature is something the client may substitute.

**Q: How do you validate an uploaded file's type?**
By magic bytes, using something like Tika. The `Content-Type` header and the extension are both
client-supplied; only the file's leading bytes indicate what it actually is, and a mismatch between
declared and detected type is itself a signal.

**Q: Why serve uploads from a different domain?**
Because a file rendered on your origin runs with your cookies and localStorage — an uploaded HTML
file becomes stored XSS with full session access. A separate content domain, plus `nosniff` and
`Content-Disposition: attachment`, contains it.

**Q: State CAP correctly.**
During a network partition you must choose between consistency and availability. Partition tolerance
is not optional — networks fail — so "pick two of three" is wrong. And CAP's consistency is
linearizability, not ACID's constraint checking.

**Q: What is PACELC and why is it more useful?**
It adds the normal case: if partitioned, choose availability or consistency; *else*, choose latency or
consistency. Since partitions are rare, the latency-versus-consistency trade is the one you actually
make on every request.

**Q: Which consistency model do users notice?**
Read-your-writes. A user edits their profile, the read hits a lagging replica, and their change
appears not to have saved. Route their reads to the primary briefly after a write, or use a
consistency token.

**Q: How do you manage polyglot persistence?**
One source of truth, everything else a derived projection that can be rebuilt from it. Losing the
search index is a reindex; losing the source of truth is an incident.

## Mini task

1. Build the naive upload endpoint and OOM it with a large file under a small heap.
2. Implement path traversal via the client filename and write outside the upload directory. Fix it
   with a server-generated key.
3. Implement presigned `PUT` uploads end to end with MinIO or S3. Confirm no bytes pass through your
   server by watching its network usage.
4. Omit the content-length binding and upload a file far larger than declared. Then bind it and
   confirm the rejection.
5. Upload a PHP script named `photo.png` with `Content-Type: image/png`. Detect it with magic bytes
   and reject it.
6. Serve an uploaded HTML file from your app's origin and execute JavaScript that reads
   `document.cookie`. Then serve it from a separate origin with `nosniff` and `Content-Disposition`
   and confirm it is inert.
7. Implement streaming upload with `setFileSizeMax` and confirm it aborts mid-stream rather than
   after receiving everything.
8. Do a multipart upload, abandon it, and find the orphaned parts. Write the lifecycle rule.
9. Wire post-processing as a background job with a status field, and show the UI's pending state.
10. Set up PostgreSQL streaming replication, write to the primary, read from the replica immediately,
    and reproduce the read-your-writes problem. Then fix it by routing.
11. Store the same data as normalised tables and as a `jsonb` column. Query both and compare the
    plans (Day 110).
