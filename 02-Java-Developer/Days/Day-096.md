# Part 1 — What refactoring is, exactly

> **Refactoring is a change to the internal structure of software that makes it easier to understand
> and cheaper to modify — without changing its observable behaviour.** — Martin Fowler

Two words carry the whole definition.

**"Without changing behaviour"** — if behaviour changes, it is not refactoring, it is a rewrite or a
bug fix. This is not pedantry: it determines what you may do without tests, what you must tell a
reviewer, and whether you may deploy it separately.

**"Easier to modify"** — refactoring is *investment*, justified by a change you are about to make.

> **Refactor when you are about to change something and the current structure is in the way.**
> Not on a schedule. Not as a "cleanup sprint" — those get cancelled and produce risk with no
> feature attached.

Kent Beck's formulation is the practical one:

> **"Make the change easy, then make the easy change."**

Two commits, in that order (Day 085): first a behaviour-preserving restructure, then the feature.
The reviewer can verify the first is safe by inspection and see the second in isolation.

## The precondition

**You need tests, or a mechanical guarantee, or both.** Without one, you are not refactoring — you
are editing and hoping.

Order of preference:

1. **Existing tests** covering the behaviour you are preserving. Run them before you start, so you
   know they were green.
2. **Characterisation tests** — write tests that capture what the code *currently* does, bugs
   included, purely to detect change. This is the standard technique for legacy code with no tests,
   and it is legitimate: you are not endorsing the behaviour, you are pinning it.
3. **IDE-automated refactorings**, which are mechanically safe: rename, extract method, inline,
   change signature, move. Use the IDE rather than typing — it updates every reference, including in
   strings and Javadoc, and it will not miss one.

```java
// A characterisation test: not "this is right", but "this is what it does today"
@Test void characterise_legacyDiscount() {
    assertEquals(93.5, legacy.calc(100, 3, true), 0.001);
    assertEquals(0.0,  legacy.calc(0, 0, false), 0.001);
    assertEquals(-5.0, legacy.calc(-5, 1, false), 0.001);   // ← probably a bug. Pin it anyway.
}
```

Pin the bug, refactor, *then* fix the bug in a separate commit. Fixing it during the refactor makes
the diff unreviewable and the failure ambiguous.

# Part 2 — The smells catalogue

A **smell** is not a bug. It is a surface indication that usually corresponds to a deeper problem —
a heuristic for where to look.

## Bloaters

| Smell | Detection | Refactoring |
|---|---|---|
| **Long Method** | > ~30 lines, or you must scroll | Extract Method, Replace Conditional with Polymorphism |
| **Large Class** | Many fields, many responsibilities (Day 090) | Extract Class, Extract Subclass |
| **Long Parameter List** | > 3–4 parameters | Introduce Parameter Object, Builder (Day 093) |
| **Primitive Obsession** | `String email`, `double money`, `int status` | Replace Primitive with Object |
| **Data Clumps** | The same 3 parameters travel together everywhere | Extract Class from them |

**Primitive Obsession is the most valuable one to internalise**, because fixing it prevents whole
categories of bug at compile time:

```java
// ❌ every one of these is a runtime bug waiting
public void transfer(String fromAccount, String toAccount, double amount) { … }
transfer(toId, fromId, amount);          // transposed — compiles fine, moves money the wrong way

// ✅
public void transfer(AccountId from, AccountId to, Money amount) { … }
transfer(toId, fromId, amount);          // still compiles — but now write:
public void transfer(SourceAccount from, TargetAccount to, Money amount) { … }
```

And `Money` rather than `double` is Day 042B; `EmailAddress` rather than `String` gives validation
one home rather than fourteen.

**Data Clumps** is the smell that most reliably reveals a missing concept: if `street`, `city`,
`postcode` appear together in six signatures, `Address` is a class that wants to exist.

## Object-orientation abusers

| Smell | Meaning |
|---|---|
| **Switch Statements** on type | Missing polymorphism (Day 090) |
| **Refused Bequest** | A subclass overrides to throw — LSP violation (Day 091) |
| **Temporary Field** | A field set only during one operation — extract it into a method object |
| **Alternative Classes with Different Interfaces** | Two classes doing the same job, incompatibly |

## Change preventers

| Smell | Meaning |
|---|---|
| **Divergent Change** | One class changes for many different reasons — SRP violation |
| **Shotgun Surgery** | One change requires edits in many classes — the inverse |
| **Parallel Inheritance Hierarchies** | Adding a subclass here forces one there |

**Divergent Change and Shotgun Surgery are opposites, and they matter because the cure for one causes
the other.** Divergent Change means split the class. Shotgun Surgery means gather the scattered
behaviour into one place. Over-applying SRP produces Shotgun Surgery; over-consolidating produces
Divergent Change. That tension is Day 092's meta-point in concrete form.

Detecting Shotgun Surgery mechanically: look at your commit history for files that always change
together (Day 085's `git log`). If six files appear in the same commit every time, they are one
concept spread across six files.

## Dispensables

Dead code, speculative generality (Day 092's YAGNI), duplicate code, comments substituting for
clarity (Day 089), data classes with no behaviour, and *lazy classes* that do too little to justify
existing.

**Delete dead code without ceremony.** It is in Git (Day 084). A `@Deprecated` method with no callers
is dead; a commented-out block is dead; an unreachable branch is dead.

## Couplers

| Smell | Meaning |
|---|---|
| **Feature Envy** | A method uses another object's data more than its own — **move it there** |
| **Inappropriate Intimacy** | Two classes know each other's internals |
| **Message Chains** | `a.getB().getC().getD()` — Law of Demeter (Day 092) |
| **Middle Man** | A class that only delegates — inline it |

**Feature Envy is the most actionable smell in the catalogue.** The fix is mechanical and almost
always right:

```java
// ❌ this method lives in ReportGenerator but is entirely about Order
public Money totalWithTax(Order order) {
    return order.subtotal()
                .plus(order.shipping())
                .plusPercent(order.taxRate());
}

// ✅ move it to Order
public class Order {
    public Money totalWithTax() { return subtotal.plus(shipping).plusPercent(taxRate); }
}
```

This is also "tell, don't ask" (Day 092) arrived at from the other direction.

# Part 3 — The core refactorings

## Extract Method

The most-used refactoring there is. The trigger: **you are about to write a comment explaining what
a block does** (Day 089).

```java
// before
void printOwing() {
    printBanner();
    // print details            ← the comment is the signal
    System.out.println("name: " + name);
    System.out.println("amount: " + outstanding);
}

// after
void printOwing() {
    printBanner();
    printDetails(outstanding);
}
private void printDetails(Money outstanding) { … }
```

Name the extracted method after **what it does, not how**. If you cannot name it, the block was not
one thing — which is itself the finding.

## Replace Conditional with Polymorphism

Day 090's OCP refactoring:

```java
// before
double speed() {
    switch (type) {
        case EUROPEAN: return baseSpeed();
        case AFRICAN:  return baseSpeed() - loadFactor() * numberOfCoconuts;
        case NORWEGIAN_BLUE: return isNailed ? 0 : baseSpeed(voltage);
    }
}
// after: three subclasses, or an enum with behaviour (Day 043)
```

## Introduce Parameter Object

```java
// before
Report generate(LocalDate start, LocalDate end, String region, boolean includeVoid) { … }
// after
Report generate(ReportCriteria criteria) { … }
```

The gain is not shorter signatures — it is that `ReportCriteria` can now **validate itself**
(`end` after `start`) in one place instead of at every call site.

## Replace Magic Number / Extract Constant · Replace Temp with Query · Decompose Conditional

```java
// Decompose Conditional — the condition gets a name
if (date.isBefore(SUMMER_START) || date.isAfter(SUMMER_END)) { charge = q * winterRate + fee; }
// →
if (isWinter(date)) { charge = winterCharge(quantity); } else { charge = summerCharge(quantity); }
```

## Extract Class

The Large Class fix. **Split by responsibility (Day 090's actors), not by size.** Move the fields
first, then the methods that use only those fields; anything left that uses both is the seam you
must think about.

## Inline — the reverse refactorings

Every refactoring has an inverse, and applying the inverse is equally legitimate: Inline Method
(when the body is as clear as the name), Inline Class (when a class no longer does enough),
Collapse Hierarchy (when a subclass adds nothing). **Refactoring is bidirectional** — moving toward
abstraction is not automatically progress, which is Day 092's point again.

# Part 4 — Doing it safely

## The loop

```
1. Ensure tests exist and are GREEN.       ← never start from red
2. Make ONE small change.
3. Run the tests.                          ← seconds, not minutes
4. Commit.
5. Repeat.
```

**The discipline is step size.** Ten small refactorings each verified take less total time than one
large one, because when the large one breaks you have no idea which part did it. If you are ever more
than five minutes from a green build, the step was too big — revert and take a smaller one.

**Commit after each step.** Then a mistake costs one `git reset` (Day 087), not an afternoon.

## Legacy code — the strangler pattern

For code you cannot safely change all at once:

```
1. Write characterisation tests around the seam you will touch.
2. Extract an interface over the old implementation.
3. Build the new implementation behind the same interface.
4. Route a small percentage of traffic to the new one (a feature flag — Day 088).
5. Compare outputs in production; widen when they agree.
6. Delete the old implementation.
```

Named after the strangler fig, which grows around a tree until the tree is gone. It works at every
scale — one class or one service — and it is the answer to "how would you replace a legacy system
without a big-bang rewrite?", which is a common system-design question.

The related technique for testing untestable code is **Sprout Method / Sprout Class**: rather than
untangling a 400-line method to add behaviour, write the new behaviour in a new, fully-tested method
and call it from the old one. The old code stays as bad as it was; the *new* code is clean, and you
have not risked anything.

## What not to do

- **Do not refactor and change behaviour in one commit.** Unreviewable, and when something breaks you
  cannot tell which half did it.
- **Do not refactor without a reason.** "It offended me" is not a business case; "I need to add
  X and this structure blocks it" is.
- **Do not refactor on a branch for three weeks.** You will merge-conflict with everything (Day 086).
  Small, continuous, merged daily.
- **Do not rewrite when you mean refactor.** A rewrite discards years of accumulated bug fixes and
  edge cases that nobody documented — that is exactly what all the ugly special cases *are*.

## Tooling

```bash
# IDE: prefer the automated versions — they update every reference
Rename          Shift+F6      (IntelliJ)
Extract Method  Ctrl+Alt+M
Extract Field   Ctrl+Alt+F
Inline          Ctrl+Alt+N
Change Signature Ctrl+F6
```

Static analysis to find the smells: SonarQube, Error Prone, SpotBugs, PMD, IntelliJ inspections.
**Track the trend, not the absolute number** — a codebase with 4,000 warnings is not going to zero,
but it can stop growing, and a ratchet ("no new warnings") is achievable where a cleanup is not.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Refactoring without tests | Silent behaviour change |
| Starting from a red build | You cannot tell what you broke |
| Steps too large | Cannot isolate the failure |
| Refactoring mixed with behaviour change | Unreviewable diff, ambiguous failures |
| Fixing a bug during a refactor | Same |
| Refactoring with no upcoming change | Risk with no return |
| A three-week refactoring branch | Merge hell |
| Rewriting instead of refactoring | Loses undocumented edge cases |
| Typing renames instead of using the IDE | Missed references in strings and Javadoc |
| Treating every smell as mandatory | Smells are heuristics, not defects |

## Interview questions

**Q: What is refactoring?**
Changing internal structure without changing observable behaviour, to make the code easier to
understand and cheaper to change. If behaviour changes, it is not refactoring.

**Q: When do you refactor?**
When about to make a change that the current structure obstructs — make the change easy, then make
the easy change. Not on a schedule, and not as a standalone cleanup project.

**Q: How do you refactor code with no tests?**
Write characterisation tests that pin current behaviour, bugs included, then refactor in small
verified steps, then fix the bugs separately. Prefer IDE-automated refactorings, which are
mechanically safe.

**Q: Name five smells and their refactorings.**
Long Method → Extract Method. Feature Envy → Move Method. Primitive Obsession → Replace Primitive
with Object. Switch on type → Replace Conditional with Polymorphism. Data Clumps → Extract Class.

**Q: What is the difference between Divergent Change and Shotgun Surgery?**
Divergent Change is one class changing for many reasons — split it. Shotgun Surgery is one change
touching many classes — consolidate. They are opposites, and over-correcting one produces the other.

**Q: How would you replace a legacy system without a big-bang rewrite?**
The strangler pattern: put an interface in front of the old implementation, build the new one behind
it, route traffic gradually behind a flag, compare outputs, then delete the old one.

**Q: Why not just rewrite?**
Because the ugly special cases in old code are usually undocumented bug fixes and edge cases learned
the hard way. A rewrite discards that knowledge and rediscovers it in production.

## Mini task

1. Take Day 089's `OrderProcessor` (or your own worst method) and refactor it in at least eight
   commits, running tests between each. Note the total time.
2. Write characterisation tests for a method you do not understand. Include at least one test that
   pins behaviour you believe is wrong.
3. Find a Primitive Obsession in your code — a `String` id or a `double` amount — and introduce a
   type. Count the bugs the compiler now catches.
4. Find a Data Clump of three parameters travelling together and extract the class they imply.
5. Find a Feature Envy method and move it to the class whose data it uses.
6. Use IntelliJ's Extract Method, Introduce Parameter Object and Change Signature on real code —
   do not type them by hand.
7. Apply an inverse refactoring: find an abstraction that is not earning its keep and inline it.
8. Sketch a strangler plan for one legacy class you have: the interface, the new implementation, the
   flag, and the comparison method.
9. Run SonarQube or IntelliJ inspections on a project and pick the three findings you would actually
   act on. Justify ignoring the rest.

## 🎙️ Articulation drill

Two minutes: **"You have inherited a 2,000-line class with no tests and you need to add a feature.
What do you do?"**

Do not say "rewrite it". Characterisation tests around the seam you must touch, sprout the new
behaviour into a clean tested method, extract an interface if you need a substitute, small verified
steps with a commit each, and a strangler plan if it is worth replacing at all. Calm, incremental and
test-first is the answer being assessed.
