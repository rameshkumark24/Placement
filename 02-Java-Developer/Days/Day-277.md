# Day 277 📡

**J-277** · 📡 **Real-time in the UI** — ⭐⭐ the update that arrives while the user is typing

**Time:** 3 hrs · **Mode:** BUILD

> ⭐⭐ **The sentence to own: adding real-time updates means your screen now has two writers — the user
> and the server — and the interesting engineering is not the transport, it is deciding what happens
> when a push arrives for a record the user is currently editing.**
>
> Today: ⭐ the transport decision, ⭐⭐ reconnection, merging pushes into the cache, and the conflict.

# Part 1 — The transport decision

| | ⭐ Polling | ⭐⭐ SSE | WebSocket |
|---|---|---|---|
| Direction | ⭐ Client asks | ⭐ Server → client | ⭐ Both |
| Over HTTP | ✅ | ✅ ⭐⭐ **Works with your existing auth, cookies and proxies** | ⭐ Upgrade — often needs LB config |
| Auto-reconnect | ⭐ N/A | ⭐⭐ **Built in**, with `Last-Event-ID` | ⭐ You write it |
| Spring support | ⭐ Any endpoint | ⭐⭐ `SseEmitter` — trivial | ⭐ `@ServerEndpoint` / STOMP |
| ⭐ Cost | ⭐⭐ N clients × 1/interval | ⭐ 1 held connection each | 1 each |

```
⭐⭐ THE DECISION, HONESTLY

⭐   ⭐⭐ POLLING IS THE RIGHT DEFAULT MORE OFTEN THAN PEOPLE ADMIT.
⭐     refetchInterval: 30_000 is ONE LINE, has no connection state,
⭐     no reconnection logic, and survives every proxy on earth.
⭐     ⭐ If "within 30 seconds" is fine, YOU ARE DONE.
⭐   ⭐⭐ SSE IS THE RIGHT UPGRADE. One-way is what you actually need
⭐     — ⭐ notifications, status changes, progress — and you get
⭐     reconnection free. ⭐⭐ AND IT IS PLAIN HTTP, SO YOUR COOKIE
⭐     AUTH AND FILTER CHAIN JUST WORK.
⭐   ⭐ WEBSOCKET ONLY WHEN THE **CLIENT** MUST PUSH CONTINUOUSLY:
⭐     chat, collaborative editing, live cursors.

⭐   ⇒ ⭐⭐ "I USED POLLING BECAUSE 30 SECONDS WAS THE REQUIREMENT"
⭐     IS A **STRONGER** ANSWER THAN AN UNNECESSARY WEBSOCKET.
```

> ⭐ **The connection-count trap.** Each SSE connection holds a server resource. ⭐⭐ On Tomcat's
> thread-per-request model, `SseEmitter` releases the thread — **but a naive blocking implementation
> does not, and 500 concurrent users exhaust your thread pool.** Know which you built.

# Part 2 — ⭐⭐ Reconnection is the whole problem

```
⭐⭐ THE CONNECTION **WILL** DROP. Wifi, sleep, a proxy idle timeout
⭐   (60 s is common), a deploy. ⭐ THE QUESTION IS ONLY WHAT HAPPENS
⭐   NEXT.

⭐   ⭐⭐ EventSource RECONNECTS AUTOMATICALLY — ⭐ BUT THAT IS NOT
⭐     ENOUGH ON ITS OWN:
⭐   ① ⭐⭐ EVENTS DURING THE GAP ARE **LOST** unless the server
⭐      replays from Last-Event-ID.
⭐   ② ⭐ so ON RECONNECT, **REFETCH** — do not assume the stream
⭐      catches you up.
⭐   ③ ⭐⭐ SHOW CONNECTION STATE. A user staring at stale data
⭐      believing it is live is worse than one who knows it is stale.
```

```jsx
useEffect(() => {
  const es = new EventSource("/api/events", { withCredentials: true });
  es.addEventListener("order.updated", e => applyEvent(JSON.parse(e.data)));
  es.onopen  = () => { setLive(true); qc.invalidateQueries(); };  // ⭐⭐ RESYNC
  es.onerror = () => setLive(false);      // ⭐ EventSource retries itself
  return () => es.close();                // ⭐⭐ CLEANUP (Day 226)
}, []);
```

| ⭐ Must do | Why |
|---|---|
| **Close on unmount** | ⭐⭐ Otherwise N navigations = N held connections (Day 226) |
| **⭐⭐ Refetch on reconnect** | The gap is invisible otherwise |
| **A heartbeat event** | ⭐ Proxies kill idle connections; a comment every 20 s keeps it alive |
| **Show live/stale** | ⭐⭐ A small dot. **Honesty about staleness is a feature.** |

# Part 3 — Merging pushes into the cache

```jsx
function applyEvent(evt) {
  qc.setQueryData(keys.orders.detail(evt.id), old =>
    old && evt.version > old.version ? { ...old, ...evt.data } : old);
  //     ⭐⭐ VERSION CHECK — OR AN OUT-OF-ORDER EVENT OVERWRITES
  //        NEWER DATA WITH OLDER DATA, SILENTLY.
  qc.invalidateQueries({ queryKey: keys.orders.all, exact: false });
}
```

```
⭐⭐ THREE RULES FOR APPLYING A PUSH

⭐ ① ⭐⭐ EVENTS ARRIVE OUT OF ORDER AND MORE THAN ONCE.
⭐    ⭐ You already know this from Stage 12. ⭐⭐ CARRY A VERSION OR
⭐      TIMESTAMP AND DROP ANYTHING NOT NEWER.
⭐ ② ⭐ PREFER "INVALIDATE" OVER "WRITE THE PAYLOAD IN".
⭐    ⭐⭐ AN EVENT IS A HINT THAT SOMETHING CHANGED, NOT NECESSARILY
⭐      A COMPLETE, AUTHORISED VIEW OF IT — the event may carry
⭐      fields THIS user is not allowed to see.
⭐ ③ ⭐⭐ NEVER PUSH DATA THE USER MAY NOT READ. The stream is an
⭐    API SURFACE. ⭐ Filter events per subscriber on the SERVER
⭐      (Day 236) — a stream is exactly where the tenant filter gets
⭐      forgotten, because it does not look like a query.
```

# Part 4 — ⭐⭐ The update that arrives while they are typing

```
⭐⭐ THE SITUATION EVERY REAL-TIME UI EVENTUALLY HITS:
⭐   The user has been editing the notes field for two minutes.
⭐   A push says the order changed.

⭐   ❌ ⭐⭐ OVERWRITE THE FORM ⇒ THEIR WORK VANISHES MID-SENTENCE.
⭐      ⭐ The single worst thing real-time can do.
⭐   ❌ IGNORE IT ⇒ they save over someone else's change.

⭐   ✅ ⭐⭐ THE ANSWER: **NEVER MUTATE A DIRTY FORM. NOTIFY INSTEAD.**
⭐      ① form NOT dirty ⇒ ⭐ update silently. No ceremony.
⭐      ② ⭐⭐ FORM DIRTY ⇒ keep their text, show a banner:
⭐         "This order was updated by Sam. [Review changes]"
⭐      ③ ⭐ ON SAVE, SEND THE VERSION ⇒ the server's optimistic
⭐         lock returns 409 ⇒ show the conflict honestly (Day 276).

⭐   ⇒ ⭐⭐ THE UI'S JOB IS TO **SURFACE** THE CONFLICT. THE SERVER'S
⭐     @Version IS WHAT ACTUALLY PREVENTS THE LOST UPDATE.
⭐     ⭐ A banner is not a concurrency control.
```

| ⭐ Rule | |
|---|---|
| **Dirty state is sacred** | ⭐⭐ Never destroy unsaved input for any reason |
| **⭐ Batch bursts** | 40 events in a second must not be 40 re-renders — buffer and flush |
| **Do not animate every change** | ⭐⭐ A list that reshuffles constantly is unusable |

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how did you do real-time?"**

Start by justifying the smallest thing. **I started with a thirty-second refetch interval, because the
requirement was "within thirty seconds" and that's one line with no connection state and no
reconnection logic. Then I moved to SSE, because the updates are one-way and it's plain HTTP — my
existing cookie auth and Spring filter chain work unchanged, and reconnection is built in. I didn't use
a WebSocket, because the client never needs to push continuously.**

Then the part that is actually hard. **The transport isn't the engineering; reconnection is. The
connection will drop — wifi, sleep, a sixty-second proxy idle timeout, a deploy. EventSource reconnects
itself, but events during the gap are lost, so on reconnect I refetch rather than assuming the stream
caught me up. And I show a live-versus-stale indicator, because a user staring at stale data believing
it's live is worse off than one who knows.**

Then correctness. **Events arrive out of order and more than once — same as any at-least-once consumer
— so each carries a version and I drop anything not newer. And I mostly treat an event as a hint that
something changed rather than writing its payload into the cache, because an event isn't necessarily an
authorised view for this subscriber. Filtering per subscriber happens on the server, and a stream is
exactly where the tenant filter gets forgotten, because it doesn't look like a query.**

Close on the interesting case. **The screen now has two writers, so a push can arrive while someone is
typing. Overwriting a dirty form destroys their work mid-sentence, which is the worst thing real-time
can do. So a clean form updates silently, a dirty form keeps its text and shows a banner saying who
changed it — and the save sends the version, so the server's optimistic lock returns a 409. The banner
surfaces the conflict; `@Version` is what actually prevents the lost update.**
