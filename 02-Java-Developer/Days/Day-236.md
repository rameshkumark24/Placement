# Day 236 🚫

**J-236** · 🚫 **Authorization is server-side or it doesn't exist** — ⭐⭐ a hidden button is not a permission

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: everything the browser does is a suggestion the user can decline — they
> can edit your JavaScript, flip a variable in DevTools, or skip your app entirely and call the API
> with curl — so a UI that hides a button has changed what is *convenient*, not what is *permitted*,
> and the only place permission exists is the endpoint.**
>
> Today: the model, ⭐ the four bypasses, ⭐⭐ mirroring rules without enforcing them, and the leak
> that is not a button.

---

# Part 1 — The model

```
⭐⭐ TWO DIFFERENT JOBS THAT SOUND LIKE ONE

⭐   THE CLIENT'S JOB ⇒ ⭐ SHOW THE USER WHAT IS RELEVANT.
⭐     Hiding a Delete button they cannot use is GOOD UX.
⭐     ⭐⭐ IT IS NOT SECURITY AND MUST NEVER BE COUNTED AS ANY.

⭐   THE SERVER'S JOB ⇒ ⭐⭐ @PreAuthorize, ON EVERY REQUEST.
⭐     Decide whether THIS actor may do THIS thing to THIS resource.

⭐   ⇒ ⭐⭐ THE TEST: IF I DELETE YOUR ENTIRE FRONTEND AND CALL THE
⭐     API WITH curl, IS ANYTHING DIFFERENT? IF YES, YOUR
⭐     AUTHORIZATION IS IN THE WRONG PLACE.
```

| ⭐ The four bypasses, none exotic | |
|---|---|
| **The console** | ⭐ Un-hide the element and click it; or set `isAdmin = true` in React DevTools |
| **The API directly** | ⭐⭐ `curl -X DELETE /api/orders/7 --cookie ...` — **your UI is not involved** |
| **A modified bundle** | ⭐ Save the JS, edit the check, serve it locally |
| **A stale client** | ⭐⭐ Yesterday's bundle with yesterday's rules, still open in a tab. **Not even an attack** — just a user who has not refreshed. |

# Part 2 — ⭐⭐ Mirror the rules, do not implement them

```jsx
// ❌ THE CLIENT DECIDING — brittle, duplicated, wrong the moment
//    the server's rules change
{user.role === "ADMIN" && <DeleteButton id={o.id} />}

// ✅ THE SERVER DECIDING, THE CLIENT REFLECTING
{o.permissions.canDelete && <DeleteButton id={o.id} />}
```

```java
// ⭐ Spring — the server states what this actor may do with this row
public record OrderDto(UUID id, BigDecimal total, Permissions permissions) {}

public record Permissions(boolean canDelete, boolean canRefund) {}

// ⭐⭐ computed by the SAME code that ENFORCES it
@Component("orderRules")
class OrderRules {
    public boolean canRefund(Order o, User actor) {
        return o.status() == PAID && !o.refunded()
            && (actor.isAdmin() || actor.id().equals(o.ownerId()));
    }
}

@PreAuthorize("@orderRules.canRefund(#order, authentication.principal)")
public void refund(Order order) { ... }        // ⭐⭐ ENFORCEMENT

// ⭐ and the serialiser calls the SAME bean to build Permissions
```

| ⭐ Why this beats a role check in JSX | |
|---|---|
| **One source of truth** | ⭐⭐ The rule that renders the button is the rule in `@PreAuthorize`. **They cannot drift.** |
| **Rules are rarely just roles** | ⭐ "Owner *or* admin, if not archived, within 30 days" does not fit `role === "ADMIN"` |
| **The client stays dumb** | ⭐ New rule ⇒ server change only. No frontend deploy. |
| **It stays honest** | ⭐⭐ You are *reflecting* a decision, not *making* one |

> ⭐ **Keep enforcement and projection in the same bean.** If `canRefund` is computed in the mapper and
> enforced by a separate `@PreAuthorize` expression, they will diverge — and the divergence saying
> *"yes"* in the mapper and *"no"* in the handler is merely annoying, while the reverse is a
> vulnerability.

# Part 3 — ⭐⭐ The leak that is not a button

```
⭐⭐ HIDING A FIELD IS NOT REDACTING IT.

⭐   GET /api/users/7  ⇒
⭐     { "id":7, "name":"Ada", "email":"...",
⭐       "salary": 95000,          ⭐⭐ NOT RENDERED. STILL SENT.
⭐       "passwordHash": "$2b$..." ⭐⭐ NOT RENDERED. STILL SENT. }

⭐   ⇒ ⭐ THE UI SHOWS name ONLY. ⭐⭐ THE DATA IS IN THE NETWORK TAB,
⭐     THE BROWSER CACHE, AND ANY LOGGING PROXY.

⭐   ⇒ ⭐⭐ THIS IS WHY "NEVER RETURN AN ENTITY FROM A CONTROLLER"
⭐     (Day 147) IS A RULE. ⭐ Returning the JPA entity serialises
⭐     EVERY FIELD, INCLUDING ONES ADDED NEXT YEAR BY SOMEONE ELSE.
⭐     ⭐⭐ THE FRONTEND IS WHERE YOU FINALLY *SEE* THE PAYLOAD AND
⭐       REALISE THE RULE WAS NOT PEDANTRY.
```

```java
// ⭐⭐ a DTO is an ALLOW-LIST, and that is the point
public record UserPublic(UUID id, String name) {}   // ⭐ cannot leak a new field

@GetMapping("/users/{id}")
UserPublic get(@PathVariable UUID id) { return mapper.toPublic(repo.get(id)); }
```

| ⭐ Also check | |
|---|---|
| **List endpoints** | ⭐ `GET /orders` returning *everyone's* orders because the filter is in the UI |
| **Error messages** | ⭐⭐ A 403 body containing the resource you were not allowed to see |
| **Search / autocomplete** | ⭐ Frequently the endpoint nobody scoped to the tenant |
| **⭐⭐ `@JsonIgnore` as the only defence** | It protects *that* field. A DTO protects *every field you did not list.* |
| **404 vs 403** | ⭐⭐ `403` on a resource that exists confirms it exists. For sensitive ids, `404` is safer. |

# Part 4 — What good looks like

```
⭐⭐ THE THREE LAYERS, EACH DOING ONLY ITS OWN JOB

⭐   ① UI       ⇒ hide/disable what the server said is not allowed.
⭐                ⭐ PURELY COSMETIC. NEVER TRUSTED.
⭐   ② ⭐⭐ API   ⇒ @PreAuthorize ON EVERY REQUEST. THE ONLY BOUNDARY.
⭐                ⭐ scope every query by actor — a repository method
⭐                  that takes the actor, not one that trusts a filter
⭐   ③ ⭐ DATA   ⇒ RLS / an ownership column as the backstop for the
⭐                day someone writes a query that forgot the filter

⭐   ⇒ ⭐⭐ AND A TEST THAT PROVES IT: for each protected endpoint,
⭐     call it as the WRONG user and assert 403/404.
⭐     ⭐ @WithMockUser makes this three lines. ⭐⭐ IF THAT TEST DOES
⭐       NOT EXIST, THE AUTHORIZATION IS A CLAIM, NOT A FACT.
```

## Today's build

1. ⭐⭐ **Break your own app.** Hide a button by role, click it from the console, then call the endpoint with curl. **Confirm the damage.**

3. ⭐⭐ **Open DevTools and read every response body.** Find one field you never render. Remove it with a DTO.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you handle authorization in the frontend?"**

Refuse the premise, politely. **I don't. Authorization is server-side or it doesn't exist. Everything
the browser does is a suggestion the user can decline — they can edit my JavaScript, flip a flag in
DevTools, or skip the app entirely and use curl. My test is: if I delete the whole frontend and call
the API directly, is anything different? If yes, it's in the wrong place.**

Then what the client does, and why the shape matters. **The UI's job is showing what's relevant — good
UX, zero security. But I don't put role checks in JSX. The server sends a permissions object per
resource, computed by the same bean the `@PreAuthorize` expression calls. So the rule that renders the
button is the rule that guards the endpoint, and they can't drift. It also handles real rules, which
are rarely just roles — owner or admin, if not archived, within thirty days.**

Then the leak that isn't a button. **Hiding a field isn't redacting it. If the endpoint returns a salary
and I just don't render it, it's still in the network tab and any logging proxy. This is where "never
return an entity from a controller" stops being pedantry — returning the JPA entity serialises every
field, including ones someone adds next year. A DTO is an allow-list, which is why it beats
`@JsonIgnore`: `@JsonIgnore` protects that field, a DTO protects every field I didn't list.**

Close on proof. **Every protected endpoint has a test that calls it as the wrong user and asserts a 403
or 404 — `@WithMockUser` makes it three lines. Without that test, the authorization is a claim rather
than a fact.**
