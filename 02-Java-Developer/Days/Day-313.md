# Day 313

**L-313** · LRU cache — and the design problem hiding behind the algorithm

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ "Implement an LRU cache" is a DSA question. "Design a cache" is an LLD question. They are asked
> with the same words, and answering the wrong one is the failure mode.**
>
> The tell: if they say *O(1)*, they want the data structure. If they say *design*, they want
> eviction policies as strategies, TTL, thread-safety, stats and listeners — **and then the question
> of why real caches deliberately do not implement exact LRU.**

# Part 1 — ⭐ The data structure, by hand

**⭐ HashMap for O(1) lookup + doubly linked list for O(1) reordering. Neither works alone**, and
saying why is the first thirty seconds:

| Structure alone | ⭐ Fails because |
|---|---|
| `HashMap` | ⭐ no order — cannot find the least-recently-used |
| ⭐ `LinkedList` | ⭐ O(n) lookup |
| `TreeMap` by timestamp | O(log n), and the key moves on every access |
| ⭐ **Both, cross-linked** | ⭐ **O(1) for everything** |

```java
public class LruCache<K, V> {

    private final class Node {                       // ⭐ the list node holds the key
        K key; V value; Node prev, next;             // ⭐ ← so eviction can remove from the map
    }

    private final int capacity;
    private final Map<K, Node> index = new HashMap<>();
    private final Node head = new Node(), tail = new Node();   // ⭐ SENTINELS — no null checks anywhere

    public LruCache(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be positive");
        this.capacity = capacity;
        head.next = tail; tail.prev = head;
    }

    public Optional<V> get(K key) {
        Node node = index.get(key);
        if (node == null) return Optional.empty();
        moveToFront(node);                                     // ⭐ a read MUTATES the structure
        return Optional.of(node.value);
    }

    public void put(K key, V value) {
        Node existing = index.get(key);
        if (existing != null) { existing.value = value; moveToFront(existing); return; }

        if (index.size() == capacity) {                        // ⭐ evict BEFORE inserting
            Node lru = tail.prev;
            unlink(lru);
            index.remove(lru.key);                             // ⭐ THIS is why the node stores the key
        }
        Node node = new Node(key, value);
        index.put(key, node);
        linkAfterHead(node);
    }
}
```

**⭐ The three details interviewers check:**

| Detail | ⭐ Why |
|---|---|
| ⭐ **Sentinel head and tail** | ⭐ **no null checks in link/unlink — halves the bug surface** |
| ⭐ **The node stores its key** | ⭐ **eviction must remove from the map; without it you cannot** |
| ⭐ **`get` mutates** | ⭐ a read reorders the list — **which is the concurrency problem in Part 3** |

⚠️ **`LinkedHashMap(capacity, 0.75f, true)` with `removeEldestEntry` gives you this in four lines.**
**Say you know that** — then say *"I'll write it by hand since that's what's being asked"*, or **use
it if the problem is really about the surrounding design.** Knowing when the four-line answer is the
right one is itself a signal.

# Part 2 — ⭐ The design problem: policies as strategies

**⭐ The moment they say "now make it configurable", the algorithm stops being the point.**

```java
public interface EvictionPolicy<K> {
    void recordAccess(K key);      // ⭐ on get and on put
    void recordInsert(K key);
    K evictionCandidate();         // ⭐ who dies next
    void remove(K key);
}
```

| Policy | ⭐ Structure | ⭐ Good for |
|---|---|---|
| ⭐ **LRU** | hash map + DLL | ⭐ recency-correlated access — **the default** |
| **FIFO** | a queue | insertion-order expiry; cheapest |
| ⭐ **LFU** | ⭐ **frequency buckets** — see below | ⭐ stable hot sets |
| Random | array + index | ⭐ **surprisingly competitive, and free** |
| ⭐ **TinyLFU / sampled** | sketch + sample | ⭐ **what real caches do — Part 3** |

**⭐ LFU in O(1) is the follow-up question**, and the structure is worth knowing:

```
⭐ freq 1 ──► [D] ⇄ [C]        ⭐ a doubly linked list of FREQUENCY buckets,
⭐ freq 2 ──► [B]              ⭐ each holding a DLL of keys at that frequency.
⭐ freq 5 ──► [A]              ⭐ access → move the key to the next bucket (create if absent).
                              ⭐ evict → the LRU end of the LOWEST bucket. All O(1).
```

⚠️ **LFU's real flaw, which is the good answer to "LRU or LFU?": a key hammered once during a spike
stays cached forever.** The fix is ageing — periodically halve all frequencies — **which is exactly
what Redis's LFU does** (Day 206).

## ⭐ TTL — and the mistake everyone makes

```java
// ⭐ WRONG: a background thread scanning for expiries — a thread per cache, and a full scan
// ⭐ RIGHT: LAZY expiry on read, plus optional bounded sampling

public Optional<V> get(K key) {
    Node node = index.get(key);
    if (node == null) return Optional.empty();
    if (clock.instant().isAfter(node.expiresAt)) {          // ⭐ expire on read
        remove(key); stats.recordExpiry(); return Optional.empty();
    }
    moveToFront(node);
    return Optional.of(node.value);
}
```

| ⭐ Point | |
|---|---|
| ⭐ **Lazy expiry costs nothing when idle** | ⭐ the entry occupies memory until read — usually fine |
| ⭐ **Sampled active expiry for memory pressure** | ⭐ **exactly Redis's design** (Day 206) |
| ⭐ **A `Clock` port, never `Instant.now()`** | ⭐ **otherwise TTL is untestable** (Day 300) |
| Per-entry TTL beats a global one | callers know their own freshness needs |

# Part 3 — ⭐⭐ Thread safety, and why real caches are not exact LRU

**⭐ The shared mutable state is the linked list — and here is the killer property:**

> **⭐ Every `get` writes.** A read-heavy cache with exact LRU has a write-heavy data structure, so a
> `ReadWriteLock` buys nothing: **every reader takes the write lock.**

| Approach | ⭐ Verdict |
|---|---|
| ⭐ One `synchronized` lock | ⭐ **correct; a single point of contention on every read** |
| ⭐ `ReadWriteLock` | ⭐ **useless here — `get` mutates. Say this; it is the insight.** |
| ⭐ **Striped: N independent shards by `hash(key)`** | ⭐ **simple, effective — but LRU becomes per-shard** |
| ⭐⭐ **`ConcurrentHashMap` + approximate recency** | ⭐⭐ **what Caffeine and Guava actually do** |

**⭐ The senior answer, and it is genuinely interesting:**

```
⭐ Reads go to a ConcurrentHashMap — fully concurrent, no ordering work at all.
⭐ Access events are appended to a per-thread RING BUFFER (lossy — drops under contention).
⭐ ONE thread drains the buffers and replays them onto the eviction structure.
⭐ ⇒ Eviction order is APPROXIMATE. Deliberately.
```

> **⭐ The line to say: "exact LRU ordering is not worth the contention it costs. Caffeine batches
> access records and applies them asynchronously, so the ordering is approximate — and its hit rate
> is *better* than exact LRU because it uses TinyLFU admission. Precision in the eviction order was
> never the goal; hit rate was."**

**⭐ That reframing — the metric is hit rate, not ordering fidelity — is the strongest thing you can
say in this problem**, and it connects to Day 206's observation that Redis samples rather than
maintaining true LRU.

## ⭐ The rest of the design surface

| Feature | ⭐ Design note |
|---|---|
| ⭐ **Stats** | ⭐ hits, misses, evictions, expiries, load time — **hit rate is the only number that matters** |
| ⭐ **Removal listener** | ⭐ must carry the *cause* (evicted / expired / replaced / explicit) |
| ⭐ **Loading cache** (`get(key, loader)`) | ⭐ **must dedupe concurrent loads for the same key — see below** |
| Weight-based sizing | ⭐ capacity in bytes, not entries — a `Weigher<K,V>` |
| Bulk operations | `getAll` with one loader call for the misses |

⚠️ **Cache stampede is the trap in the loading cache** (Day 206's four failure modes): a hot key
expires and 500 threads call the loader at once. **`ConcurrentHashMap.computeIfAbsent` dedupes them —
but it holds a bin lock across your loader, which may be a database call.** The real fix is a
per-key `CompletableFuture` placed in the map so that latecomers await the in-flight load without
holding any lock. **Naming both the problem and why the obvious fix is dangerous is the mark here.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No key in the list node | ⭐ **eviction cannot clean the map — a leak** |
| ⭐ No sentinels | null checks everywhere; off-by-one bugs at the ends |
| ⭐ Forgetting that `get` reorders | ⭐ **the entire thread-safety analysis is wrong** |
| ⭐ `ReadWriteLock` for an LRU | ⭐ every reader takes the write lock — no gain |
| Evicting after insert | capacity briefly exceeded; awkward with weights |
| ⭐ A background thread per cache for TTL | ⭐ threads and scans for nothing — go lazy |
| `Instant.now()` inside the cache | TTL untestable |
| ⭐ A loader inside `computeIfAbsent` | ⭐ **a bin lock held across a database call** |
| No removal cause | listeners cannot distinguish eviction from expiry |
| ⭐ Claiming exact LRU under concurrency | ⭐ real caches deliberately do not — know why |

## Interview questions

**Q: Why a hash map and a doubly linked list?**
The map gives O(1) lookup; the list gives O(1) reordering and O(1) removal of the least recent. Either
alone fails — a map has no order, a list has O(n) lookup. The two details that matter are sentinel
head and tail nodes, so link and unlink need no null checks, and storing the key inside the node, so
eviction can also remove it from the map.

**Q: Would you use `LinkedHashMap` instead?**
In production, yes — access-ordered `LinkedHashMap` with `removeEldestEntry` is four lines, and I
would say so. In an interview asking me to implement it, I write it by hand. The judgement being
tested is whether I know both, and when the four-line answer is the right one.

**Q: How do you make it thread-safe?**
Carefully, because every `get` mutates the list — so a read-write lock is useless, every reader takes
the write lock. A single lock is correct but becomes the contention point on a read-heavy workload.
Striping by key hash works, with LRU then being per-shard. What real caches do is decouple the two:
reads hit a `ConcurrentHashMap`, access events go to lossy per-thread ring buffers, and one thread
replays them onto the eviction structure — so ordering is approximate on purpose.

**Q: Isn't approximate LRU worse?**
Not on the metric that matters. Exact ordering costs contention on every read; hit rate is what a
cache is for. Caffeine's approximate ordering with TinyLFU admission achieves a better hit rate than
exact LRU, because admission control keeps a one-off scan from evicting the hot set. Redis makes the
same trade by sampling rather than maintaining true LRU.

**Q: How would you implement TTL?**
Lazily — check expiry on read and evict there — because a background scanning thread per cache costs
threads and full scans to reclaim memory nobody is asking for. Under memory pressure I would add
bounded random sampling, which is Redis's design. Per-entry TTL rather than global, and the clock
comes from an injected `Clock` so the behaviour is testable.

**Q: A hot key expires and five hundred threads miss at once.**
Cache stampede. I put a `CompletableFuture` for the in-flight load into the map, so the first thread
loads and the other 499 await the same future — one database call, no lock held. `computeIfAbsent`
also dedupes, but it holds a bin lock across the loader, which is a network call, so it stalls every
other key in that bin.

## Mini task

1. **Write the LRU by hand** with sentinels. Then delete the key from the node and **find the leak
   with a memory assertion.**
2. Write it again with `LinkedHashMap` in four lines. **Compare and note when each is right.**
3. Extract `EvictionPolicy` and implement **LRU, FIFO and LFU.** Run all three over the same access
   trace and **compare hit rates.**
4. ⭐ Implement **LFU with frequency buckets** in O(1). Then reproduce its flaw: spike a key 10,000
   times, then never touch it, and **watch it outlive genuinely hot keys.** Add ageing.
5. Add **per-entry TTL with an injected `Clock`.** Write a test that advances time rather than
   sleeping.
6. ⭐ **Benchmark the single-lock version** with 8 reader threads. Then shard it 16 ways and
   benchmark again. **Record both numbers.**
7. ⭐ **Reproduce a stampede**: 500 threads, one expired hot key, a loader that sleeps 100 ms. Count
   loader invocations. Fix it with a `CompletableFuture` and count again.
8. Add a removal listener carrying the cause, and assert all four causes fire.
