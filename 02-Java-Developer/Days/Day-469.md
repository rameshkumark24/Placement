# Day 469

**L-469** · Project defence III — the failure interrogation

**Time:** 3 hrs · **Mode:** NEW · **⭐ Project defence drills, 3 of 5**

> **⭐⭐ "What breaks first?" is the highest-information question anyone can ask about your system, and
> the difference between a good and a weak candidate is that one of them has already asked it of
> themselves.**
>
> Today: the six failure questions, **the bottleneck answer that must contain a number**, what happens
> when each component disappears, the security interrogation, and **the 10× question answered as a
> sequence rather than a wish.**

# Part 1 — ⭐⭐ The six questions, and what each is testing

| ⭐ Question | ⭐⭐ Testing |
|---|---|
| ⭐⭐ 1. **"What breaks first under load?"** | ⭐⭐ have you load-tested, or are you guessing |
| ⭐⭐ 2. **"What happens if the database goes down?"** | ⭐ degradation design (Day 339) |
| ⭐ 3. **"Where is your single point of failure?"** | ⭐⭐ can you name it without defensiveness |
| ⭐ 4. **"How do you know it's working right now?"** | ⭐ observability, SLOs, alerting (Day 374) |
| ⭐⭐ 5. **"What's the worst bug you shipped?"** | ⭐⭐ Day 465's failure story, in technical form |
| ⭐⭐ 6. **"What happens at 10× traffic?"** | ⭐⭐ the sequencing question — Part 4 |

```
⭐⭐ THE ONE-SENTENCE RULE FOR ALL SIX:
⭐   ⭐⭐ An answer without a NUMBER or a MEASUREMENT is an opinion.
⭐   ❌ "I think the database would be the bottleneck."
⭐   ✅ ⭐⭐ "The database. At 500 rps the connection pool saturates — 40 connections against
⭐      a db.t3.medium's ~400 limit was fine, but p99 goes from 240 ms to 1.8 s at 800 rps
⭐      because requests queue on pool acquisition. I found it with k6, not by reasoning."
```

# Part 2 — ⭐⭐ "What breaks first?" — the bottleneck answer

| ⭐ Candidate bottlenecks, in the order they usually appear | |
|---|---|
| ⭐⭐ 1. **The database connection pool** | ⭐⭐ almost always first — tasks × pool > `max_connections` (Day 387) |
| ⭐ 2. A single slow query | ⭐ N+1, or a missing index found under concurrency |
| ⭐ 3. The application thread pool | ⭐ blocked on a slow downstream (Day 398) |
| ⭐ 4. CPU on the JVM | ⭐⭐ usually GC before compute |
| ⭐ 5. The cache, when cold | ⭐ the stampede (Day 388) |
| ⭐ 6. Network / cross-AZ | ⭐ rarely, and usually as cost first (Day 396) |

```
⭐⭐ THE ANSWER HAS FOUR PARTS:
⭐   1. ⭐ WHICH component, named
⭐   2. ⭐⭐ AT WHAT LOAD — a number
⭐   3. ⭐⭐ HOW YOU KNOW — the test, not the theory
⭐   4. ⭐ WHAT YOU WOULD DO — the next fix, and the one after it
```

> **⭐ Part 3 is what separates this from a textbook answer.** "I ran a load test and watched it break" is
> worth more than a correct guess, **because the correct guess is available to anyone who has read the
> same material.** Stage 7's Day 286 and Stage 10's measurements exist so you can answer part 3.

# Part 3 — ⭐⭐ "What happens if X disappears?"

**⭐ Go component by component. For each: what fails, what still works, what the user sees, and what
alerts.**

| ⭐ Component gone | ⭐⭐ The answer |
|---|---|
| ⭐⭐ **Database** | ⭐⭐ writes fail; **cached reads survive for the TTL**; health check does **not** fail (Day 389); users see 503 on writes and stale reads; the alert is error rate + `DatabaseConnections` |
| ⭐⭐ **Redis** | ⭐⭐ **everything still works, slower** — read-through degrades to the database. ⭐⭐ But: **is the database sized for 100% of reads?** (Day 388) |
| ⭐ **The queue / broker** | ⭐ the outbox accumulates; **nothing is lost**; consumers catch up (Day 407) — ⭐⭐ **this is why the outbox matters** |
| ⭐ **One ECS task** | ⭐ ALB drains it, the service replaces it, **zero dropped requests** — measured (Day 397) |
| ⭐⭐ **One availability zone** | ⭐⭐ N+1 across three; p99 rises ~40 ms; **no scaling action required** (Day 380) |
| ⭐ **S3** | ⭐ uploads and downloads fail; the rest of the API is unaffected — **it is not on the read path** |
| ⭐ **The auth provider / key** | ⭐⭐ existing tokens work until expiry; new logins fail — a real degradation to state |

⚠️ **The Redis row contains the trap.** Most people answer "it still works, just slower" and stop. **The
follow-up is "so your database now serves the reads the cache was absorbing — is it sized for that?"**
Answering that unprompted is a strong signal, and it is the exact lesson from Day 388.

| ⭐ Question | ⭐ What must be true |
|---|---|
| ⭐⭐ "How do you stop tenant A reading tenant B's data?" | ⭐⭐ **enforced in one place, not per query** (Day 259) |
| ⭐ "What happens if a token is stolen?" | ⭐ short access TTL, **refresh rotation with reuse detection** (Day 258) |
| ⭐ "Where do secrets live?" | ⭐⭐ not in the image, not in env vars, workload identity (Day 372) |

# Part 4 — ⭐⭐ The 10× question

```
⭐⭐ "WHAT HAPPENS AT 10× TRAFFIC?" — the wrong answer is a wish list. The right answer is a SEQUENCE.

⭐ ⭐⭐ "It breaks in a specific order, and I know the order:
⭐   1. ⭐ the connection pool saturates first — ⭐ fix: shrink per-task pools, then RDS Proxy
⭐   2. ⭐⭐ then the single primary becomes the write ceiling — ⭐ fix: reads to replicas with a
⭐      sticky read window, because read-your-writes breaks otherwise
⭐   3. ⭐⭐ then the cache stampede on cold start becomes real — ⭐ fix: single-flight + jittered TTLs
⭐   4. ⭐ then log volume and metric cardinality become the largest cost line — ⭐ fix: sampling
⭐   5. ⭐⭐ then writes genuinely need partitioning by tenant — ⭐⭐ and THAT is the expensive one,
⭐      so I would delay it as long as the numbers allow."
⭐ ⇒ ⭐⭐ Ordered, each with a fix, and an explicit statement of which fix is expensive.
```

| ⭐ Why the sequence beats the list | |
|---|---|
| ⭐⭐ **It proves you know what is *actually* first** | ⭐ rather than reciting scaling techniques |
| ⭐ Each item has a cheap fix until one does not | ⭐⭐ naming the expensive one is the judgement |
| ⭐ It invites the follow-up you want | ⭐ "how would you shard?" — and you have Day 329 |
| ⭐⭐ **It converts "would it scale?" into "here is the runway"** | ⭐⭐ which is what an engineer actually needs to know |

> **⭐ And the honest closing line: "I have not run it at 10×; I have load-tested to 500 rps and the
> ordering above comes from where it degraded when I pushed it."** **Distinguishing measured from
> projected is the credibility move** — and it is the same instinct as Day 463.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **A bottleneck answer with no number** | ⭐⭐ an opinion, not a finding |
| ⭐ "I think it would be the database" | ⭐⭐ correct guesses are available to everyone |
| ⭐ Never having load-tested | ⭐⭐ every answer becomes theory |
| ⭐⭐ **"Redis dies, it just gets slower"** and stopping | ⭐⭐ misses that the database now serves 100% of reads |
| ⭐ Health check that fails when the DB fails | ⭐⭐ a blip becomes a total outage (Day 389) |
| ⭐ No answer for "how do you know it works right now?" | ⭐ no SLO, no alerting |
| ⭐ Defensiveness about a single point of failure | ⭐⭐ naming it calmly is the signal |
| ⭐⭐ **10× answered as a wish list** | ⭐⭐ reciting techniques, not knowing the order |
| ⭐ Not naming which fix is expensive | ⭐ that is the judgement being tested |
| ⭐ Claiming 10× is fine | ⭐⭐ nothing is fine at 10× |
| ⭐ Blurring measured and projected | ⭐⭐ the credibility move, skipped |
| Tenancy enforced per-query rather than centrally | one missed WHERE clause is a breach |

## Interview questions

**Q: What breaks first under load?**
The database connection pool, at around eight hundred requests per second. Forty connections per task
against a db.t3.medium's roughly four hundred limit was fine until the fleet scaled out, and then p99
goes from about two hundred and forty milliseconds to nearly two seconds because requests queue on pool
acquisition rather than on the query itself. I know that because I load-tested it with k6 and watched it
degrade, not because I reasoned about it — and the first fix is shrinking the per-task pool rather than
enlarging the database, because pool size is almost always chosen by superstition.

**Q: What happens if Redis goes down?**
Everything still works, slower, because the cache is read-through and falls back to the database. But
the answer people stop at is the incomplete one: the database is now serving one hundred percent of reads
when it was sized on the assumption the cache absorbs most of them. So the real answer includes the
defence — single-flight coalescing so one loader per key hits the database, a bounded pool acting as a
bulkhead, and jittered TTLs — and the fact that I tested it by flushing the cache under load rather than
assuming.

**Q: Where is your single point of failure?**
The database primary. Multi-AZ gives me automatic failover with no data loss, and I have forced it under
load and measured eleven seconds of client-visible impact — it was forty minutes the first time because
the JVM was caching DNS indefinitely. But it is still one writer, so a failover is an availability event
and the write ceiling is a single instance. I would rather name that plainly than describe the system as
having no single point of failure, which is almost never true and is immediately checkable.

**Q: What happens at ten times the traffic?**
It breaks in a specific order and I know the order. The connection pool saturates first, fixed by smaller
pools and then RDS Proxy. Then the single primary becomes the write ceiling, fixed by moving reads to
replicas with a sticky read window, because read-your-writes breaks otherwise. Then the cache stampede on
cold start becomes a real risk. Then log volume and metric cardinality become the largest cost line, fixed
by sampling. And then writes genuinely need partitioning by tenant — which is the expensive one, so I
would delay it as long as the numbers allow. I should say I have not run it at ten times; that ordering
comes from where it degraded when I pushed it in load testing.

**Q: How do you stop one tenant reading another's data?**
It is enforced in one place rather than in every query, because relying on each query to carry the right
filter means one missed clause is a data breach. So tenancy is applied at the persistence boundary and
there is a test that asserts a query without a tenant context fails rather than returning everything.
That is the shape that matters — a control that fails closed and is impossible to forget, rather than a
convention that depends on everyone remembering.

## Mini task

1. ⭐⭐ **Load-test your flagship until it breaks.** Record which component, at what load, with the graph.
2. ⭐ Write the **four-part bottleneck answer** with real numbers.
3. ⭐⭐ For **every component**, write what fails, what survives, what the user sees, and what alerts.
4. ⭐⭐ **Kill Redis under load** and confirm your database survives. If it does not, that is this week's
   work (Day 388).
5. ⭐ Verify your **health check does not touch the database.** Prove it by stopping the database.
6. ⭐⭐ **Kill an AZ under load** and record p99, failures, and whether any scaling occurred.
7. ⭐ Answer **"how do you know it's working right now?"** by opening your dashboard and pointing.
8. ⭐⭐ Write the **10× sequence** — five ordered items, each with a fix, one marked expensive.
9. ⭐ Mark each item as **measured** or **projected.** Say so aloud.
10. ⭐⭐ Run the **five security questions** with someone attacking each answer twice.

# 🚪 Exit questions

1. Give the six failure questions and what each tests.
2. State the rule that applies to all six answers.
3. Give the four parts of a bottleneck answer, and which one separates you.
4. List six bottlenecks in the order they typically appear.
5. What is the trap in the Redis answer?
6. What must be true of your health check, and why?
7. Why does an intact outbox make the broker's failure survivable?
8. Give the AZ-failure answer with the phrase that matters.
9. Why should you name your single point of failure calmly?
10. Give the five-item 10× sequence with fixes.
11. Why does the sequence beat a list, and which item carries the judgement?
12. What is the credibility move at the end of the 10× answer?

## 🎙️ Articulation drill

**Three minutes:** have someone ask all six failure questions in a row, fast, with no preparation gap.

**⭐ The target is that every answer contains either a number you measured or an explicit "I have not
measured this — here is my reasoning". No answer should be a bare opinion, and no answer should be
defensive.**

**⭐ The one to practise hardest is the Redis question, because the incomplete answer is so natural: "it
still works, just slower" is true and it stops one sentence early. The complete answer continues — "which
means the database is now serving the reads it was never sized for, so the real question is whether it
survives an empty cache, and I tested that by flushing it under load."**
