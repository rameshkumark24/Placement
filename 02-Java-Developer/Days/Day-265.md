# Day 265 🏗️

**P-265** · Async work — executors, context, and the boundary of what may be lost

**Time:** 3 hrs · **Mode:** BUILD

> Day 263 handled what must not be lost. **Today handles everything else** — the notification email,
> the thumbnail, the analytics ping, the parallel fan-out that turns three sequential 300 ms calls
> into one.
>
> **⭐ The discipline of this day is drawing the line and defending it.** `@Async` is in-memory and
> in-process, so a restart drops the queue — and most projects use it for things that should have
> been in the outbox.

---

# Part 1 — ⭐ Configure the executor, because the default is wrong

```
⭐ @EnableAsync — or every annotation is silently synchronous
```

**⭐ Boot's default has an unbounded queue**, and Day 071's submission algorithm means the maximum
pool size is therefore **never reached**:

```
⭐ tasks > corePoolSize → queue (unbounded) → ⭐ maxPoolSize NEVER used
⭐ Result: 8 threads and an infinite backlog that grows until the heap is gone.
```

```
⭐ ThreadPoolTaskExecutor:
   corePoolSize 8, maxPoolSize 16
   ⭐⭐ queueCapacity 200          ← BOUNDED. This is Day 070's backpressure.
   ⭐ CallerRunsPolicy             ← the submitting thread runs it; the producer slows down
   ⭐ threadNamePrefix "async-"    ← readable thread dumps (Day 076)
   ⭐ waitForTasksToCompleteOnShutdown + awaitTerminationSeconds  (Day 133)
```

**⭐ `CallerRunsPolicy` is the choice to defend**: when the queue is full the system *degrades* rather
than collapsing. `AbortPolicy` throws (honest, but you must handle it); a silent `DiscardPolicy` is
almost never right.

## ⭐ Separate pools per workload

```
⭐ @Async("emailExecutor")      — slow, external, tolerant of delay
⭐ @Async("thumbnailExecutor")  — CPU-bound
```

**⭐ One shared pool means a slow email provider blocks thumbnail generation** (Day 071's bulkhead
argument). **Isolate workloads that fail independently**, or your least important dependency takes
down your most important path.

## ⭐ Virtual threads — what they change and what they do not

```
⭐ spring.threads.virtual.enabled: true    (Boot 3.2+, Java 21)
```

**⭐ For I/O-bound async work this removes the sizing problem entirely** (Day 072). **Two caveats from
Day 072 still stand:** they do not help CPU-bound work, and **a bound is still how you get
backpressure** — unlimited virtual threads means unlimited concurrent database calls, which just
moves the collapse into the connection pool (Day 156).

# Part 2 — ⭐⭐ The four things that do not cross the thread boundary

**⭐ All four are `ThreadLocal`s. It is one fact, four times.**

| Lost | Symptom in your project |
|---|---|
| ⭐ **`SecurityContext`** | ⭐ `@PreAuthorize` in an async method sees anonymous (Day 169) |
| ⭐ **MDC** | ⭐ async logs cannot be joined to the request (Day 182) |
| ⭐ **`TenantContext`** | ⭐⭐ **the async task operates on the wrong tenant, or none** (Day 176) |
| ⭐ **The transaction** | ⭐ a new thread has **no** transaction (Day 164) |

```
⭐ A TaskDecorator that CAPTURES on the caller and CLEARS in a finally.
```

**⭐ The `finally` is as important as the propagation** (Day 066A): async threads are pooled, so a
context left behind is inherited by the next unrelated task — **which for `SecurityContext` or
`TenantContext` means running someone else's work as the wrong user or tenant.**

**⭐ Test it:** run two async tasks as different tenants on a single-thread executor and confirm the
second does not inherit the first's context.

## ⭐⭐ The transaction one is the dangerous one

```
❌ @Transactional
   save(booking);
   asyncService.notifyWarehouse(booking.getId());   ⭐ a DIFFERENT THREAD
```

**⭐ Two independent bugs** (Day 177):

| | |
|---|---|
| ⭐ **A race** | ⭐ the async method may run *before* the commit — an intermittent "not found" that never reproduces locally |
| ⭐ **No rollback linkage** | if the transaction rolls back, the notification was already sent |

```
⭐ @TransactionalEventListener(AFTER_COMMIT) + @Async     ← ⭐ commit first, then hand off
```

**⭐ And Day 263's boundary applies: `AFTER_COMMIT` + `@Async` still loses the work if the process
dies in between.** That is fine for a thumbnail and not fine for a payment capture.

# Part 3 — ⭐ The line: `@Async` or the outbox?

> **⭐ The test: if this pod is killed one second from now, does it matter that this never happened?**

| Work in your project | ⭐ Mechanism |
|---|---|
| Analytics ping, cache warm | ⭐ `@Async`, loss fine |
| Thumbnail generation | ⭐ `@Async` **if regenerable on demand**; outbox if not |
| ⭐ **Booking confirmation email** | ⭐ **the outbox** — a customer not told is a support ticket |
| ⭐ **Payment capture, downstream sync** | ⭐ **the outbox**, always |
| ⭐ **Parallel fan-out to reduce latency** | ⭐ `@Async` returning `CompletableFuture` |

**⭐ Go through every async call in your project today and classify it.** Most projects have one
mechanism and use it for everything; **having made the decision per effect, and written it down, is a
strong defence point** (Day 256).

## ⭐ Exceptions in `void @Async` methods vanish

```
⭐ AsyncConfigurer.getAsyncUncaughtExceptionHandler():
     ⭐ log with full context + ⭐ increment a failure counter + ⭐ ALERT
```

**⭐ A `void` `@Async` method's exception goes nowhere** — no caller receives it, no advice applies
(different thread), and the default handler logs at a level nobody watches. **Silent failure**
(Day 177).

**⭐ Configure this today and alert on the counter.** It applies only to `void` methods; futures carry
their own exception.

## ⭐ Parallel fan-out, bounded

```
⭐ CompletableFuture.allOf(a, b, c).orTimeout(3, SECONDS).join();
```

**⭐ Two rules** (Day 177): **always bound it** — otherwise one slow dependency holds the caller's
thread indefinitely (Day 154) — and remember **the caller is still blocked**, so this reduces latency,
not thread consumption.

# Part 4 — ⭐ Shutdown, and proving it works

```
⭐ server.shutdown: graceful
⭐ spring.lifecycle.timeout-per-shutdown-phase: 30s
⭐ executor.setWaitForTasksToCompleteOnShutdown(true) + awaitTerminationSeconds(30)
⭐ A pre-stop delay AFTER the pod is marked unready   ← ⭐ Day 185's item people miss
```

**⭐ The pre-stop delay matters because load balancers take seconds to notice a pod is unready.**
Shutting down the instant `SIGTERM` arrives drops requests that were routed a moment earlier.

**⭐ And be honest about the limit** (Day 177): graceful shutdown drains in-flight tasks on a *clean*
shutdown. **A `SIGKILL`, an OOM kill or a node failure still loses everything queued** — which is
exactly why the classification in Part 3 matters.

## ⭐ The tests

```
⭐ 1. Print the thread name in an async method → ⭐ confirm it is NOT the caller's
⭐ 2. Self-invocation → ⭐ confirm it runs SYNCHRONOUSLY (Day 137's proxy)
⭐ 3. Log the correlation ID, security context and tenant inside → ⭐ all present via the decorator
⭐ 4. Two tasks, different tenants, ONE thread → ⭐ no leakage
⭐ 5. Throw from a void @Async → ⭐ the handler fires and the counter increments
⭐ 6. Async called from inside a transaction → ⭐ reproduce the race, then fix with AFTER_COMMIT
⭐ 7. Fill the queue → ⭐ confirm CallerRunsPolicy slows the producer rather than throwing
⭐ 8. Queue 1,000 tasks and kill -9 → ⭐ COUNT WHAT WAS LOST
```

**⭐ Test 8 is the one that justifies the whole day.** Losing a thousand analytics pings is fine;
seeing the same number for confirmation emails is the argument for the outbox, **measured in your own
system.**

**⭐ Test 2 deserves emphasis** because `@Async` self-invocation fails differently from
`@Transactional`: the only symptom is "it was slower than expected", which nobody investigates
(Day 177).

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No `@EnableAsync` | every annotation silently synchronous |
| ⭐ **Default unbounded queue** | ⭐ max pool never reached; OOM under load |
| One shared executor | a slow workload starves every other |
| No rejection policy chosen | exceptions, or silent discards |
| ⭐ **No `TaskDecorator`** | security, tenant and correlation context all lost |
| ⭐ **Not clearing context in `finally`** | ⭐ the next task runs as the previous user or tenant |
| ⭐ `@Async` called from inside a transaction | ⭐ a race against commit, plus a dual write |
| ⭐ `void` return with no exception handler | ⭐ failures vanish |
| Unbounded `CompletableFuture.join()` | one slow call blocks the caller forever |
| Self-invocation | silently synchronous, no symptom but latency |
| ⭐ `@Async` for work that must not be lost | ⭐ a restart drops it |
| No pre-stop delay | in-flight requests dropped on every deploy |
| Believing graceful shutdown covers a `SIGKILL` | it does not |

## 🎤 Defence questions

3. **⭐ Why must the `TaskDecorator` clear in a `finally`?**
4. **⭐ Which of your async work is `@Async` and which is in the outbox — and how did you decide?**

7. **What does graceful shutdown cover, and what does it not?**
8. **⭐ How many tasks did you lose when you killed the process?**
