# Day 300 ⭐

**L-300** · ⭐ Clean & hexagonal architecture — ports, adapters, and the dependency rule

**Time:** 3 hrs · **Mode:** NEW

> **⭐ There is exactly one idea here, and it fits on a line: source dependencies point inward,
> toward the thing that changes least.**
>
> Everything else — ports, adapters, the concentric circles, the four names for the same diagram — is
> presentation. **Today is about applying the one idea honestly, including saying out loud what it
> does not buy you.**

---

# Part 1 — ⭐⭐ The dependency rule

```
        ┌──────────────────────────────────────────┐
        │  Adapters:  Web · JPA · Kafka · S3       │   ⭐ volatile, replaceable
        │   ┌──────────────────────────────────┐   │
        │   │  Application: use cases          │   │   ⭐ orchestration, transactions
        │   │   ┌──────────────────────────┐   │   │
        │   │   │  Domain: entities, VOs,  │   │   │   ⭐ stable, pure Java
        │   │   │  invariants, policies    │   │   │
        │   │   └──────────────────────────┘   │   │
        │   └──────────────────────────────────┘   │
        └──────────────────────────────────────────┘
              ⭐ SOURCE DEPENDENCIES POINT INWARD ONLY
              ⭐ CONTROL FLOW crosses both ways — that is the point
```

**⭐ Two sentences that resolve most of the confusion:**

1. ⭐ **Nothing in an inner circle may name anything in an outer circle** — no import, no annotation,
   no type in a signature.
2. ⭐ **Control flow still goes outward** (a use case must save something). **The dependency is
   inverted by an interface the inside owns** — Day 091's DIP, applied to a whole architecture rather
   than a class.

**⭐ The mechanism, in six lines:**

```java
// ⭐ INSIDE — application layer. The interface is DEFINED here, in domain terms.
public interface Orders {                 // ⭐ a PORT
    Optional<Order> byId(OrderId id);
    void save(Order order);
}

// ⭐ OUTSIDE — persistence adapter. It depends INWARD, on the port.
@Repository
class JpaOrders implements Orders { ... } // ⭐ an ADAPTER
```

> **⭐ The whole trick is *where the interface lives*.** An interface next to its JPA implementation
> buys nothing — the domain still imports the persistence package. **An interface owned by the
> application, implemented outside, reverses the arrow.** That is the entire technique.

## ⭐ Driving and driven ports — the distinction people miss

| | ⭐ Driving (primary, left) | ⭐ Driven (secondary, right) |
|---|---|---|
| Who calls whom | ⭐ **outside calls in** | ⭐ **inside calls out** |
| Example port | `PlaceOrder` use case | `Orders`, `PaymentGateway`, `Clock` |
| Example adapter | REST controller, CLI, test | JPA repo, HTTP client, Kafka producer |
| ⭐ Is DIP needed? | ⭐ **no** — the arrow already points inward | ⭐ **yes — this is where inversion happens** |

**⭐ The asymmetry is the useful part.** A controller depending on a use case interface is ordinary.
**A use case depending on a persistence interface it defines itself is the inversion**, and it is the
only place the technique does any work.

# Part 2 — ⭐ What it actually buys, and what it does not

**⭐ Be precise here, because the standard claims are oversold and interviewers know it.**

| Claim | ⭐ Verdict |
|---|---|
| ⭐ "You can swap PostgreSQL for MongoDB" | ⭐ **overstated.** You never will, and Day 211's model differences would not survive the port anyway |
| ⭐ "You can swap the web framework" | ⭐ **rarely true, rarely wanted** |
| ⭐ **"Domain logic is testable with no infrastructure"** | ⭐ **TRUE, and this is the real prize** |
| ⭐ **"Business rules are readable in one place"** | ⭐ **true, and undersold** |
| ⭐ **"A vendor change stops at one adapter"** | ⭐ **true — Stripe → Adyen is the realistic case** |
| ⭐ **"Framework upgrades don't touch the rules"** | ⭐ true — Day 185B's Jakarta migration touched adapters only |
| "It's always worth it" | ⭐ **false — see Part 4** |

**⭐ The test that proves it works:**

```java
@Test  // ⭐ no Spring, no database, no Testcontainers, 3 ms
void an_unpaid_order_cannot_ship() {
    Order order = Order.draft(customerId, items);         // ⭐ plain constructor
    assertThatThrownBy(order::ship)
        .isInstanceOf(OrderNotPayable.class);
}
```

> **⭐ If your domain rules need `@SpringBootTest`, you do not have a domain layer — you have a
> framework with business logic in it.** That single test is the honest measure of whether the
> architecture is real, and it is worth far more than the diagram.

# Part 3 — ⭐ The layout, concretely

```
com.app.orders
├── domain/                  ⭐ pure Java. NO Spring, NO JPA, NO Jackson.
│   ├── Order.java              entity + invariants
│   ├── OrderId.java            value object
│   ├── Money.java              value object
│   └── OrderNotPayable.java    domain exception
├── application/             ⭐ use cases + PORTS
│   ├── PlaceOrder.java         driving port (interface or class)
│   ├── PlaceOrderService.java  the use case — @Transactional lives HERE
│   ├── Orders.java             ⭐ driven port — owned by the inside
│   └── Payments.java           ⭐ driven port
└── adapter/                 ⭐ everything framework
    ├── in/web/OrderController.java     + OrderRequest/OrderResponse DTOs
    ├── out/persistence/JpaOrders.java  + OrderEntity + OrderMapper
    └── out/payment/StripePayments.java
```

**⭐ Note what is NOT in the domain package**, and why each one matters:

| Absent | Why |
|---|---|
| ⭐ `@Entity` | ⭐ Day 158's id strategy would dictate `equals`; JPA needs a no-arg constructor, which breaks invariants |
| ⭐ `@JsonProperty` | Day 147 — the wire format would drive the model |
| `@Component` | ⭐ domain objects are `new`-ed, not injected |
| ⭐ `LocalDateTime.now()` | ⭐ **a `Clock` port — otherwise time is untestable** |
| `UUID.randomUUID()` | ⭐ same reason — an `IdGenerator` port, or pass ids in |

## ⭐ The mapping question — the honest cost

**⭐ A separate `OrderEntity` means writing a mapper**, and this is the most common reason teams
abandon the approach:

| Option | Cost | ⭐ When |
|---|---|---|
| ⭐ **Separate `Order` and `OrderEntity` + mapper** | ⭐ real, ongoing, ~2× the classes | ⭐ **modules with genuine rules** |
| ⭐ **One class, JPA-annotated, used as the domain object** | ⭐ the arrow is not inverted | ⭐ **CRUD modules — and it is fine** |
| Annotate the domain class but forbid JPA features | ⭐ **the worst of both** — looks pure, is not | never |

**⭐ Choose per module, not per codebase, and write the choice down.** Day 306 makes that
per-module choice structural, and Day 307 applies it to your flagship.

⚠️ **The mapper is where bugs hide.** A field added to the entity and forgotten in the mapper is a
silently-dropped value. **Property-based round-trip tests** (`map(unmap(x)) == x`) cost twenty
minutes and remove the entire class of bug.

## ⭐ Enforce it or lose it

```java
@ArchTest
static final ArchRule domain_is_pure =
    classes().that().resideInAPackage("..domain..")
        .should().onlyDependOnClassesThat()
        .resideInAnyPackage("..domain..", "java..", "javax.money..");

@ArchTest
static final ArchRule adapters_never_talk_to_each_other =
    noClasses().that().resideInAPackage("..adapter.out..")
        .should().dependOnClassesThat().resideInAPackage("..adapter.in..");
```

**⭐ Also worth encoding: no `@Transactional` outside `application`, no entity type in a
`application` signature, and no adapter-to-adapter dependency** (an outbound adapter calling an
inbound one is a cycle wearing a costume).

# Part 4 — ⭐⭐ When NOT to do this

**⭐ The most valuable thing you can say about clean architecture in an interview is where you would
not use it.**

| Situation | ⭐ Do instead |
|---|---|
| ⭐ **The module is genuinely CRUD** | ⭐ **controller → Spring Data repo. Two layers. Ship it.** |
| ⭐ **The rules are one `if`** | ⭐ ports are pure overhead |
| A prototype with an unknown domain | ⭐ you cannot draw a boundary you have not learned yet |
| A tiny team, a short-lived service | ⭐ the mapping cost dominates |
| ⭐ **Read-heavy reporting** | ⭐ **query the database directly — a projection through a domain model is slow and pointless (Day 161)** |

> **⭐ The reporting exception is worth stating explicitly, because it is the most common real-world
> compromise:** commands go through the domain, complex reads bypass it entirely with a projection
> query. That is CQRS's useful half, and it is not a violation — **it is an acknowledgement that
> reads have no invariants to protect.**

**⭐ The failure mode of over-applying it is real:** four files and two mappers to add one field to a
CRUD form. **Teams that experience that abandon the approach entirely, including in the two modules
where it was earning its keep.** Applying it selectively is what makes it survivable.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Interface next to its implementation | ⭐ **the arrow is not inverted — no benefit at all** |
| ⭐ `@Entity` on the domain object, called "clean" | ⭐ the dependency is still there, now hidden |
| ⭐ Entities crossing the port boundary | ⭐ the adapter's model leaks into the inside |
| `now()` inside the domain | ⭐ time is untestable; flaky tests follow |
| ⭐ Applying it uniformly | ⭐ **four files per CRUD field → the team abandons it entirely** |
| An untested mapper | ⭐ silently dropped fields |
| ⭐ Adapter calling adapter | a cycle in disguise |
| ⭐ Claiming database portability | ⭐ unprovable, and the interviewer will ask if you have done it |
| ⭐ Routing reports through the domain | ⭐ slow, and there is no invariant to protect |
| No ArchUnit rules | ⭐ it is clean for one sprint |

## Interview questions

**Q: What is the dependency rule?**
Source dependencies point inward only — nothing in an inner circle names anything in an outer one.
Control flow still goes both ways; when the inside needs the outside, it defines an interface in its
own terms and the outside implements it. So the whole technique reduces to where the interface
lives.

**Q: What is a port and what is an adapter?**
A port is an interface owned by the inside; an adapter is an implementation living outside. Driving
ports are use cases called by controllers or tests; driven ports are things the application needs —
persistence, payments, a clock. The inversion only matters on the driven side; on the driving side
the dependency already points the right way.

**Q: What does hexagonal architecture actually buy you?**
Domain rules testable in milliseconds without infrastructure, business logic readable in one place,
and vendor or framework changes contained in one adapter. I would not claim you can swap databases —
you never do, and with JPA entities as the model it was never true anyway. The measurable proof is a
domain test that runs with no Spring context.

**Q: When would you not use it?**
CRUD modules, single-rule modules, prototypes where the domain is not yet understood, and reporting
reads — I query directly for those, because a read has no invariant to protect. I would decide per
module rather than per codebase, because applying it uniformly means four files to add a field to a
form, and that is how teams abandon it in the two modules where it was earning its keep.

**Q: How do you keep it from drifting?**
ArchUnit in CI: the domain depends only on the JDK, no `@Transactional` outside the application
layer, no entity types in application signatures, no adapter-to-adapter dependencies. Without tests
an architecture describes the past.

## Mini task

1. Take **one feature** from your flagship — the one with the most rules — and restructure it into
   `domain` / `application` / `adapter`.
2. ⭐ **Write one domain test with no Spring context and no database.** Time it. **That number is the
   deliverable.**
3. Introduce a **`Clock` port** and delete every `now()` from the domain. Write a test that asserts
   behaviour at a fixed instant.
4. Write the **mapper**, then write a **round-trip property test** for it. Add a field to the entity
   and *deliberately forget* the mapper — confirm the test catches it.
5. Add the **three ArchUnit rules**. Deliberately break each one and confirm the build fails.
6. ⭐ **Pick a second module and deliberately do NOT apply this.** Write one paragraph in an ADR
   (Day 101) explaining why — that paragraph is worth more in an interview than the refactor.
7. Count the files needed to add a field, before and after, **for both modules**. Put both numbers in
   the ADR.

# 🚪 Exit questions

1. State the dependency rule and the one thing that makes it work.
2. Why does control flow crossing outward not violate it?
3. Distinguish driving and driven ports; where does inversion actually happen?
4. Which three benefits are real and which two are oversold?
5. What is the one test that proves the domain layer exists?
6. Name five things that must not appear in a domain package, with reasons.
7. What is the honest cost of a separate entity, and how do you defend the mapper?
8. When is annotating the domain class with `@Entity` the right call?
9. Give five situations where you would not apply this.
10. Why is bypassing the domain for reporting reads not a violation?
11. Give four ArchUnit rules that keep it true.

## 🎙️ Articulation drill

**Three minutes:** *"Explain hexagonal architecture and tell me when you wouldn't use it."*

**⭐ Two markers.** First, you explain it as *where the interface lives* rather than by describing a
hexagon. Second — **and this is the one that separates people — you spend a third of your answer on
when not to use it**, and you name the reporting-read exception. Anyone can recite the circles;
someone who has actually shipped it knows where it costs more than it returns.
