# Day 187

**L-187** · Data types and constraints — the database as the last line of defence

**Time:** 3 hrs · **Mode:** NEW

> Day 105 drew the trust boundary and Day 148 put validation at it. Both said the same thing from
> different directions: **application validation is a user-experience feature; the database
> constraint is the guarantee.**
>
> Today is why. Application code is bypassed by a batch job, a bulk update (Day 162), a migration, a
> psql session, and by the version of the code running beside yours during a rolling deploy. **The
> constraint is the only rule that every one of those paths obeys.**

# Part 1 — Choosing types, and the ones that cost you

| Need | ⭐ Use | Not |
|---|---|---|
| Text | ⭐ **`text`** | `varchar(n)` — see below |
| Money | ⭐ **`numeric(19,4)`** | ❌ `float`/`double` (Day 106) |
| Whole numbers | `integer`, `bigint` | — |
| Timestamps | ⭐ **`timestamptz`** | ❌ `timestamp` — see below |
| Dates | `date` | — |
| Booleans | `boolean` | ❌ `char(1)`, `smallint` |
| Enumerated values | ⭐ `text` + a `check`, or a lookup table | ⚠️ `enum` type — see below |
| Identifiers | `bigint` + `uuid` (Day 158) | — |
| Semi-structured | `jsonb` (Day 198) | ❌ `json`, ❌ `text` |
| IP addresses | `inet`, `cidr` | `text` |
| Ranges | ⭐ `tstzrange`, `daterange` | two columns |

## ⭐ `text` over `varchar(n)`

**In PostgreSQL these are the same type internally with identical performance.** `varchar(n)` adds
only a length check — and that check becomes a **schema migration** the day the limit is wrong.

```sql
alter table users alter column bio type varchar(1000);   -- ⭐ rewrites the table, exclusive lock
```

**Use `text`, and enforce length with a `check` constraint** if the limit is a business rule:

```sql
alter table users add constraint bio_length check (length(bio) <= 1000) not valid;
alter table users validate constraint bio_length;        -- ⭐ Day 166's non-blocking pattern
```

Changing a `check` is a cheap constraint swap; changing `varchar(n)` is a table rewrite.

## ⭐ `timestamptz`, always

**The names are misleading.** `timestamptz` does **not** store a timezone — it stores a UTC instant
and converts on input and output using the session's `TimeZone`. `timestamp` stores wall-clock digits
with no meaning attached.

```sql
set timezone = 'America/New_York';
select '2026-11-01 01:30:00'::timestamp;      -- ⭐ ambiguous — that time occurs TWICE (DST)
select now()::timestamptz;                     -- ⭐ an unambiguous instant
```

**Day 106's rule and Day 158's mapping, at the storage layer.** `timestamptz` maps to `Instant`;
`timestamp` maps to `LocalDateTime` and means different moments to different readers.

## ⭐ `enum` types — the trap

```sql
create type order_status as enum ('PENDING','SHIPPED','DELIVERED');
```

Compact and fast, and **you cannot remove a value, and adding one in the middle requires recreating
the type** — which means rewriting every table that uses it. `ALTER TYPE ... ADD VALUE` cannot run
inside a transaction block in older versions, which collides with Flyway (Day 166).

```sql
status text not null check (status in ('PENDING','SHIPPED','DELIVERED'))   -- ⭐ trivially altered
```

**A `check` constraint or a lookup table gives the same guarantee and can be changed with one
statement.** Use the lookup table when the set is data (countries, currencies) and the check when it
is code (a state machine).

## Storage facts worth knowing

**⭐ Column order affects table size**, because of alignment padding. `(bool, bigint, bool, bigint)`
wastes 14 bytes per row to padding; `(bigint, bigint, bool, bool)` wastes none. On 100 million rows
that is 1.4 GB — which is 1.4 GB of extra pages to read (Day 186). **Order columns widest-first for
large tables.**

**⭐ `NULL` is nearly free** — it is a bit in the tuple's null bitmap, not a stored value. So a wide
sparse table is cheaper than it looks, and "use an empty string instead of NULL to save space" is
backwards.

**⭐ TOAST:** values over ~2KB are compressed and moved to a side table automatically. A `text`
column holding 1MB documents does not bloat the main table — but `select *` fetches it, which is one
more argument for Day 161's projections.

# Part 2 — ⭐ Constraints, and why each one is a bug you will never have

```sql
create table orders (
    id            bigint      generated always as identity primary key,          -- ⭐ 1
    public_id     uuid        not null default gen_random_uuid(),
    customer_id   bigint      not null references customers(id) on delete restrict, -- ⭐ 2
    status        text        not null check (status in ('PENDING','SHIPPED','DELIVERED')), -- ⭐ 3
    total         numeric(19,4) not null check (total >= 0),                      -- ⭐ 4
    quantity      integer     not null check (quantity between 1 and 1000),
    placed_at     timestamptz not null default now(),
    shipped_at    timestamptz,
    version       bigint      not null default 0,                                 -- Day 165

    constraint uq_orders_public_id unique (public_id),
    constraint shipped_after_placed check (shipped_at is null or shipped_at >= placed_at),  -- ⭐ 5
    constraint shipped_has_timestamp check                                        -- ⭐ 6
        ((status = 'SHIPPED') = (shipped_at is not null))
);
```

| | Constraint | The bug it makes impossible |
|---|---|---|
| 1 | primary key | duplicate or missing identity |
| 2 | foreign key | ⭐ an order referencing a customer that does not exist |
| 3 | check on status | a typo'd or invented status value, forever |
| 4 | `total >= 0` | a negative order total from a bad refund calculation |
| 5 | cross-column check | shipped before it was placed |
| 6 | ⭐ **state consistency** | ⭐ `SHIPPED` with no shipped date — the bug that breaks reports |

**⭐ Constraint 6 is the pattern most people never write, and it is the most valuable.** It encodes
a *state machine invariant* in the schema: the status and its supporting data cannot disagree. That
is a whole class of "the data is weird" incidents made impossible.

**⭐ `on delete` is a business decision, not a default:**

| Action | Meaning |
|---|---|
| ⭐ `restrict` / `no action` | ⭐ **the safe default.** Deleting a referenced customer fails |
| `cascade` | ⚠️ deleting a customer deletes their orders — Day 159's warning |
| `set null` | orphan the child |

**`cascade` on `customer → orders` is how order history disappears.** Choose it only for genuine
compositions (`order → order_items`).

## ⭐ Partial unique indexes — the soft-delete constraint

```sql
create unique index uq_users_email_active
    on users (lower(email)) where deleted_at is null;      -- ⭐ Day 184's H2 argument, concretely
```

**"Email must be unique among active users, and a deleted user's email may be reused."** A plain
unique constraint cannot express that. This is also the exact case Day 184 used to argue against
H2 — a test suite proving "duplicates are rejected" against a database with no partial indexes proves
it against a constraint production does not have.

## Exclusion constraints — the one nobody knows

```sql
create extension btree_gist;
alter table bookings add constraint no_double_booking
    exclude using gist (room_id with =, during with &&);   -- ⭐ no overlapping ranges, ever
```

**⭐ This makes double-booking structurally impossible**, atomically, without a lock or a
read-then-write race. The application version of this is a `select ... for update`, a check, and an
insert — three statements, a race window, and a bug under concurrency. **One constraint, no race.**

It is also D-14's **write skew** — the anomaly `SERIALIZABLE` exists to prevent — solved by a
constraint instead of an isolation level. Day 195 returns to this; the point today is that
**a constraint beats an isolation level, because it holds regardless of how the row is written.**

# Part 3 — Adding constraints to a live table

**Day 166's rule: a constraint that scans the table holds a lock while it does.**

```sql
-- ❌ scans the whole table under ACCESS EXCLUSIVE — minutes of blocked writes
alter table orders add constraint total_positive check (total >= 0);

-- ⭐ two steps, no write blocking
alter table orders add constraint total_positive check (total >= 0) not valid;  -- instant
alter table orders validate constraint total_positive;                          -- scans, SHARE UPDATE only
```

**`not valid` means "enforce for new and updated rows, do not check the existing ones yet".** New
writes are constrained immediately; the backfill validation runs without blocking writers.

**Same pattern for foreign keys.** And for `not null`, Day 166's four-step sequence — because
`alter column set not null` scans under an exclusive lock (though PostgreSQL 12+ can skip the scan if
an equivalent validated `check` already exists, which is exactly why the four-step version works).

## Deferrable constraints

```sql
alter table orders add constraint fk_customer foreign key (customer_id)
    references customers(id) deferrable initially deferred;   -- ⭐ checked at COMMIT
```

Useful for circular references and bulk loads where rows arrive out of order. **Use sparingly** — a
deferred violation surfaces at commit, far from the statement that caused it, which makes it harder
to debug and interacts badly with Day 162's flush ordering.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Validation only in the application | bypassed by jobs, bulk updates, migrations, psql, and the other running version |
| `varchar(n)` | a limit change becomes a table rewrite |
| ⭐ `timestamp` instead of `timestamptz` | ambiguous at DST; different meaning per reader |
| `float` for money | Day 106 |
| ⭐ `enum` types | cannot remove a value; adding one is a migration hazard |
| Random column order on a huge table | gigabytes of alignment padding |
| Avoiding NULL "to save space" | NULL is a bit; this is backwards |
| No cross-column checks | `SHIPPED` with no shipped date |
| `on delete cascade` by default | order history deleted with a customer |
| Plain unique with soft deletes | a deleted user's email can never be reused |
| Application-side overlap checking | a race; use an exclusion constraint |
| Adding a constraint without `not valid` | table scan under an exclusive lock |

## Interview questions

**Q: Why put constraints in the database when you already validate in the application?**
Because application validation is bypassed by every path that is not the application — batch jobs,
bulk `UPDATE`s, migrations, a psql session, and crucially the previous version of your own code
running beside the new one during a rolling deploy. The constraint is the only rule every writer
obeys.

**Q: `text` or `varchar(n)`?**
`text`. In PostgreSQL they are the same type with identical performance, and `varchar(n)` turns a
changed length limit into a table rewrite. If the limit is a business rule I express it as a `check`,
which can be swapped cheaply.

**Q: `timestamp` or `timestamptz`?**
Always `timestamptz`. It stores a UTC instant and converts on input and output; plain `timestamp`
stores wall-clock digits with no meaning, so it is ambiguous at a DST boundary and means different
moments to different readers.

**Q: How do you prevent double-booking a room?**
An exclusion constraint with a range type — `exclude using gist (room_id with =, during with &&)`.
It makes overlaps structurally impossible with no read-then-write race, which is the write-skew
anomaly solved by a constraint rather than by raising the isolation level.

**Q: How do you add a check constraint to a 100-million-row table without downtime?**
`add constraint ... not valid`, which is instant and enforces on new and updated rows, then
`validate constraint`, which scans under a lock that does not block writers.

## 🎙️ Articulation drill

Two minutes: **"Where does data validation belong?"**

Both places, for different reasons — the application for a good error message, the database for the
guarantee — and justify the second by listing what bypasses the first, including the previous version
of your own code during a rolling deploy. Then show range: a `check` that encodes a state-machine
invariant so `SHIPPED` cannot exist without a shipped date, a partial unique index so soft-deleted
emails can be reused, and an exclusion constraint so double-booking is impossible without a lock —
which is write skew solved by a constraint rather than an isolation level.
