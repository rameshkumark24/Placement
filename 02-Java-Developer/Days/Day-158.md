# Part 1 — The entity, and the requirements people skip

```java
@Entity
@Table(name = "orders", indexes = {
        @Index(name = "ix_orders_customer_placed", columnList = "customer_id, placed_at")   // ⭐ D-11
})
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "orders_seq")
    @SequenceGenerator(name = "orders_seq", sequenceName = "orders_seq", allocationSize = 50)
    private Long id;

    @Column(nullable = false, updatable = false)
    private UUID publicId;                             // ⭐ what the API exposes

    @Column(name = "customer_id", nullable = false)
    private Long customerId;

    @Enumerated(EnumType.STRING)                       // ⭐⭐ never ORDINAL
    @Column(nullable = false, length = 20)
    private OrderStatus status;

    @Column(nullable = false, precision = 19, scale = 4)   // ⭐ money
    private BigDecimal total;

    @Column(nullable = false, updatable = false)
    private Instant placedAt;                          // ⭐ never LocalDateTime

    @Version
    private long version;                              // ⭐ Day 165

    protected Order() { }                              // ⭐ JPA requires it; protected, not public
}
```

**Four requirements JPA imposes on the class itself**, each with a failure that is not obvious:

| Requirement | If you break it |
|---|---|
| A **no-arg constructor**, `public` or `protected` | Hibernate cannot instantiate it — startup or runtime failure |
| The class **not `final`** | no proxy can be created, so ⭐ **lazy loading silently becomes eager** |
| Methods **not `final`** | the same, per method |
| A **non-final id field** | reflection cannot set it |

The `final` rule is the interesting one: Hibernate creates a subclass proxy for lazy references
(Day 137's CGLIB mechanism, in a different context). A `final` entity cannot be subclassed, so
Hibernate quietly loads it eagerly instead. No error, just extra queries — which is why entities are
one of the few places where Java's "prefer immutability" advice genuinely does not apply.

# Part 2 — ⭐ Id generation, and the choice that decides batching

| Strategy | SQL | Batching | Verdict |
|---|---|---|---|
| `IDENTITY` | auto-increment column | ❌ **impossible** | works, but see below |
| **`SEQUENCE`** | a database sequence | ✅ ⭐ | **the default choice on PostgreSQL/Oracle** |
| `TABLE` | a row in a table, locked | ✅ | ❌ slow and contended. Avoid |
| `AUTO` | provider decides | varies | ⚠️ hides the decision |
| **assigned UUID** | you set it | ✅ | ⭐ good for distributed ids — with a caveat |

### Why `IDENTITY` kills batch inserts

Hibernate needs the id **immediately** after persisting, because the persistence context (Day 162) is
keyed by id. With `IDENTITY`, the id only exists once the INSERT has actually run — so Hibernate must
execute each INSERT separately and read the generated key back. `jdbc.batch_size` is then simply
ignored, silently.

With `SEQUENCE` and `allocationSize = 50`, Hibernate fetches a block of 50 ids in one round trip,
assigns them in memory, and can batch all 50 inserts into one statement. **Inserting 10,000 rows goes
from 10,000 round trips to roughly 200.**

**`allocationSize` must match the database sequence's `INCREMENT BY`.** Mismatch it and you get
duplicate-key violations under concurrency — the classic symptom of copying `allocationSize = 50`
onto a sequence created with the default increment of 1.

The cost of blocks is gaps in the id sequence when an application restarts. **Ids are not a count;
gaps are free.** Anyone treating them as a business-visible sequence has a requirements problem, not
a technical one.

### ⭐ The two-id pattern

```java
private Long id;          // internal: sequence, batchable, 8 bytes, index-friendly
private UUID publicId;    // external: what appears in URLs and JSON
```

Day 119's IDOR argument: a sequential id in a URL lets anyone enumerate your entire dataset and tells
a competitor your order volume from two purchases. A UUID does not.

The reason not to just use a UUID as the primary key is index behaviour (D-11): a random UUID
inserts into a random point of the B+ tree, so every insert dirties a different page and the index
fragments. **UUIDv7 fixes this** — it is time-ordered, so it inserts at the right-hand edge like a
sequence while remaining unguessable. If your database and driver support it, a UUIDv7 primary key is
a good single-id answer; otherwise, the two-id pattern is the safe one.

# Part 3 — ⭐⭐ `equals` and `hashCode` for entities

Day 049 gave the contract. Here is the twist that makes the naive answer wrong.

```java
Order order = new Order();          // id is null — not yet persisted
Set<Order> set = new HashSet<>();
set.add(order);                     // hashed on id == null
repo.save(order);                   // ⭐ Hibernate assigns id = 42
set.contains(order);                // ❌ FALSE — it is in the set and cannot be found
```

**The hash code changed while the object was in a hash-based collection**, so it is in the wrong
bucket. Day 049's rule — hash on immutable fields — meets a field that is *mutable exactly once*, at
the worst possible moment.

Three broken approaches, each shipped constantly:

| Approach | Breaks when |
|---|---|
| Default (identity) | the same row loaded in two sessions gives two unequal objects |
| `Objects.hash(id)` | ⭐ the id is assigned after insertion — the bug above |
| All fields | any field changes; also triggers lazy loads *inside* `equals` |

### The two correct answers

**Option A — a business/natural key**, when a genuine one exists:

```java
@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Order other)) return false;
    return publicId != null && publicId.equals(other.publicId);   // ⭐ assigned at construction
}
@Override public int hashCode() { return Objects.hash(publicId); }
```

This works because `publicId` is a `UUID` you assign **in the constructor**, before persistence. It
never changes, so the hash is stable across the whole lifecycle. **This is the best answer and it is
another argument for the two-id pattern.**

**Option B — the Vlad Mihalcea pattern**, when the id is database-generated:

```java
@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || Hibernate.getClass(this) != Hibernate.getClass(o)) return false;  // ⭐ proxy-safe
    return id != null && id.equals(((Order) o).getId());
}
@Override public final int hashCode() {
    return getClass().hashCode();          // ⭐⭐ CONSTANT — deliberately
}
```

**The constant hash code looks wrong and is correct.** It is stable across the id assignment, which is
the only property the `HashSet` contract actually requires. The cost is that all entities of a type
land in one bucket — irrelevant, because you are never putting ten thousand entities in a `HashSet`;
you are putting the handful in one order's `items` collection.

Note `Hibernate.getClass()` rather than `getClass()`: a lazy proxy's class is a generated subclass, so
`getClass() != getClass()` for an entity and its own proxy. Day 137's proxies, biting in a new place.

**And `id != null &&` matters:** two unpersisted entities must not be equal to each other just
because both ids are null.

# Part 4 — Column mapping, and the four that go wrong silently

### ⭐ `@Enumerated(EnumType.STRING)` — always

```java
@Enumerated(EnumType.ORDINAL)      // ❌ stores 0, 1, 2 — the DEFAULT
private OrderStatus status;
```

**`ORDINAL` is the default and it is a data-corruption bug waiting for a code review.** Insert a new
constant in the middle of the enum and every existing row's meaning shifts: yesterday's `SHIPPED` is
today's `CANCELLED`. The data does not change; the interpretation does. `STRING` costs a few bytes
and is readable in a `SELECT`.

The `STRING` caveat: renaming a constant now breaks reads. Treat enum constant names as part of the
schema, and use a `@Converter` if you need the two to differ.

### Dates — Day 106's rule, in the database

```java
private Instant placedAt;              // ⭐ maps to timestamptz. Unambiguous
private LocalDate  deliveryDate;       // ✅ correct where a calendar date is meant
private LocalDateTime bad;             // ❌ no zone — means different instants to different readers
```

**Store instants in UTC as `timestamptz`.** `LocalDateTime` at a DST boundary is genuinely ambiguous —
one wall-clock time occurs twice.

### Money

```java
@Column(precision = 19, scale = 4) private BigDecimal total;    // ⭐
private double wrong;                                          // ❌ Day 106
```

**Specify `precision` and `scale` explicitly**, or the DDL Hibernate would generate defaults to
`(19,2)` and `validate` may accept a column that silently rounds. Four decimal places is the usual
choice because tax and unit-price calculations need more precision than the final displayed amount.

### `@Transient`, `@Basic(fetch = LAZY)`, and large columns

```java
@Lob @Basic(fetch = FetchType.LAZY) private String contractText;   // ⚠️ needs bytecode enhancement
@Transient private BigDecimal displayTotal;                        // not persisted
```

**Lazy *basic* fields require bytecode enhancement to work at all.** Without the Hibernate enhancement
plugin the annotation is ignored and the 2 MB column loads on every query. If you have a large
column, the reliable answer is a separate entity with a `@OneToOne`, or simply not selecting it — a
projection (Day 161).

## Embeddables — value objects that are not entities

```java
@Embeddable
public record Address(String line1, String city, String postcode, String country) { }

@Entity
public class Customer {
    @Embedded private Address billing;
    @Embedded @AttributeOverride(name = "line1", column = @Column(name = "ship_line1"))
    private Address shipping;                         // ⭐ same type, different columns
}
```

**Embeddables are the right tool far more often than people use them.** `Address`, `Money`,
`DateRange` are value objects with no identity — they belong to their owner, they are compared by
value, and they live in the owner's table. Modelling them as entities adds a table, a join and an id
for something with no independent existence.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `EnumType.ORDINAL` (the default) | inserting an enum constant silently reinterprets every row |
| ⭐ `IDENTITY` on PostgreSQL | batch inserts impossible, silently |
| `allocationSize` ≠ sequence `INCREMENT BY` | duplicate-key violations under concurrency |
| `equals`/`hashCode` on a generated id | object lost inside its own `HashSet` |
| `getClass()` instead of `Hibernate.getClass()` | entity ≠ its own proxy |
| `equals` over all fields | triggers lazy loads inside `equals` |
| `final` entity class or methods | lazy loading silently becomes eager |
| Sequential id in the URL | Day 119 enumeration |
| Random UUIDv4 primary key | index fragmentation on every insert |
| `LocalDateTime` for an instant | ambiguous at DST |
| `double` for money | Day 106 |
| No `precision`/`scale` | silent rounding |
| `@Lob` lazy without enhancement | annotation ignored; loads every time |
| Entities for value objects | needless tables, joins and ids |

## Interview questions

**Q: Why can't `equals` and `hashCode` use a generated id?**
Because the id is null before persistence and assigned during it. If the object is in a `HashSet`
when that happens, its hash changes while it sits in a bucket and it can never be found again — not
even by `contains(itself)`. Either hash on a business key assigned at construction, or return a
constant from `hashCode`, which is stable and is all the contract requires.

**Q: Why `SEQUENCE` over `IDENTITY`?**
Because `IDENTITY` makes batch inserts impossible — Hibernate must run each insert to learn the
generated key. `SEQUENCE` with an allocation size fetches ids in blocks, so inserts batch. The cost
is gaps in the numbering, which do not matter.

**Q: Why is `EnumType.ORDINAL` dangerous?**
It stores the enum's position. Insert a constant in the middle and every existing row's meaning
changes with no data modification and no error. `STRING` costs a few bytes and is readable.

**Q: Why must an entity class not be `final`?**
Hibernate creates a subclass proxy for lazy references. A `final` class cannot be proxied, so lazy
loading silently degrades to eager — no error, just more queries.

## 🎙️ Articulation drill

Two minutes: **"How do you map an entity, and what are the decisions that matter?"**

Id strategy first, and say *why*: `SEQUENCE` over `IDENTITY` because `IDENTITY` makes batch inserts
structurally impossible. Then the two-id pattern for IDOR safety. Then `equals`/`hashCode`, and
explain the bug rather than the rule — the id is assigned after the object may already be in a hash
set, so the hash changes in place and the object is lost. Close on `EnumType.STRING`, and frame it
correctly: `ORDINAL` is the default, and it silently reinterprets every existing row the day someone
adds a constant in the middle.
