# Part 1 — The filter

```java
@Component
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {   // ⭐ Day 151

    private final JwtService jwt;
    private final UserDetailsService users;
    private final ObjectMapper mapper;

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {

        String header = req.getHeader(HttpHeaders.AUTHORIZATION);
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res);                      // ⭐ NOT an error — let the chain decide
            return;
        }

        try {
            Claims claims = jwt.parseAccessToken(header.substring(7));   // ⭐ verifies; see Part 2

            if (SecurityContextHolder.getContext().getAuthentication() == null) {   // ⭐ don't overwrite
                var principal = users.loadUserByUsername(claims.getSubject());
                var auth = new UsernamePasswordAuthenticationToken(
                        principal, null, principal.getAuthorities());
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));

                SecurityContext context = SecurityContextHolder.createEmptyContext();
                context.setAuthentication(auth);
                SecurityContextHolder.setContext(context);              // ⭐ Day 169
            }
        } catch (JwtException e) {
            SecurityContextHolder.clearContext();
            writeProblem(res, 401, "invalid-token", "Token is invalid or expired");  // ⭐ Day 149
            return;                                                     // ⭐ stop the chain
        }
        chain.doFilter(req, res);
    }
}
```

**Four decisions in that code that most implementations get wrong:**

1. ⭐ **A missing header is not an error.** Continue the chain and let `AuthorizationFilter`
   (Day 169) decide — otherwise every `permitAll` endpoint breaks.
2. ⭐ **Write the problem JSON yourself.** Day 149's first gap: this is a filter, so
   `@RestControllerAdvice` will never see the exception. Without this the client gets a whitelabel
   HTML page from a JSON API.
3. **Do not overwrite an existing authentication.** Another filter may have authenticated already.
4. **`OncePerRequestFilter`.** Day 151 — error re-dispatch otherwise parses the token twice.

**Registration** (Day 169):
```java
.addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
```

## ⭐ The database call per request

`loadUserByUsername` on every request defeats a large part of the point of a JWT. Three options:

| Approach | Trade-off |
|---|---|
| Load from the database each time | ⭐ authoritative; revocation and role changes are instant. Costs a query |
| **Build the principal from claims** | ⭐ **zero queries.** Roles are as stale as the token's lifetime |
| Cache the `UserDetails` (Day 168) | middle ground; cache TTL is now the staleness window |

**Build from claims, and keep access tokens short (5–15 minutes) so staleness is bounded.** That
lifetime *is* your role-change latency, and stating it that way is the right framing: it is a
deliberate trade, not an oversight.

# Part 2 — ⭐ Parsing safely: every Day 114 attack, closed

```java
@Service
public class JwtService {

    private final SecretKey key;                       // ⭐ ≥256 bits for HS256
    private final JwtParser parser;

    public JwtService(JwtProperties props) {           // Day 142 — validated properties
        this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(props.secret()));
        this.parser = Jwts.parser()
            .verifyWith(key)
            .sig().add(Jwts.SIG.HS256).and()           // ⭐⭐ 1. ALGORITHM ALLOW-LIST
            .requireIssuer(props.issuer())             // ⭐ 2.
            .requireAudience(props.audience())         // ⭐ 3.
            .clockSkewSeconds(30)                      // ⭐ 4.
            .build();
    }

    public Claims parseAccessToken(String token) {
        Claims claims = parser.parseSignedClaims(token).getPayload();
        if (!"access".equals(claims.get("typ"))) {     // ⭐⭐ 5. TOKEN TYPE CONFUSION
            throw new JwtException("wrong token type");
        }
        return claims;
    }
}
```

| # | Defence | Day 114's attack |
|---|---|---|
| 1 | ⭐ **Algorithm allow-list** | `alg:none` and RS256→HS256 confusion. **The single most important line** |
| 2 | Issuer check | a token from another system with the same key |
| 3 | Audience check | a token for a different service in the same estate |
| 4 | Clock skew | valid tokens rejected by a few seconds of drift |
| 5 | ⭐ **Token type claim** | ⭐ **a refresh token used as an access token** |

**⭐ Number 5 is the one almost nobody implements and it is a genuine privilege escalation.** If both
tokens are signed with the same key and neither says what it is, a 30-day refresh token is accepted
as an access token — turning your carefully short 15-minute access window into 30 days. **Every token
must state its type, and every parse must check it.**

**Number 1 is worth being precise about.** Modern JJWT versions default to rejecting `none` and to
verifying with the configured key type, so the naive code is safer than it was in 2018. **State the
allow-list anyway** — it is one line, it survives a library upgrade, and it is the difference between
"the library happens to protect me" and "I configured this".

## The secret

```yaml
jwt:
  secret: ${JWT_SECRET}        # ⭐ 256+ bits, base64, from the environment (Day 142)
  issuer: https://api.acme.com
  audience: acme-web
  access-token-ttl: PT15M
  refresh-token-ttl: P30D
```

**Never a literal in `application.yml`, never committed** (Day 085). A leaked HMAC secret means an
attacker mints tokens for any user with any role — total compromise, and no log entry anywhere,
because the tokens are perfectly valid.

**For anything beyond a single service, use RS256 or ES256.** Then consumers verify with a public key
and only the issuer can sign — which is Day 175's resource-server model and the reason it scales.

# Part 3 — Refresh rotation and reuse detection

Day 115's design, implemented.

```java
@Entity
public class RefreshToken {
    @Id private UUID id;
    private Long userId;
    private String tokenHash;                 // ⭐ HASH, never the token (Day 171)
    private UUID familyId;                    // ⭐ the rotation chain
    private Instant expiresAt;
    private Instant usedAt;                   // ⭐ non-null = already used
    private boolean revoked;
}
```

```java
@Transactional
public TokenPair refresh(String presented) {
    RefreshToken stored = repo.findByTokenHash(hash(presented))
            .orElseThrow(() -> new BadCredentialsException("invalid refresh token"));

    if (stored.getUsedAt() != null) {                       // ⭐⭐ REUSE DETECTED
        repo.revokeFamily(stored.getFamilyId());            // ⭐ kill every token in the chain
        log.warn("refresh_token_reuse_detected userId={} family={}",
                 stored.getUserId(), stored.getFamilyId()); // ⭐ alert on this
        throw new BadCredentialsException("invalid refresh token");   // ⭐ same generic message
    }
    if (stored.isRevoked() || stored.getExpiresAt().isBefore(Instant.now())) {
        throw new BadCredentialsException("invalid refresh token");
    }

    stored.setUsedAt(Instant.now());                        // ⭐ single use
    RefreshToken next = issueInSameFamily(stored);          // ⭐ rotation
    return new TokenPair(newAccessToken(stored.getUserId()), next.rawToken());
}
```

**⭐ Why reuse detection is the clever part, restated because it is the interview answer:** a refresh
token is single-use, so a *second* use means two parties hold it — the legitimate client and a
thief. You cannot tell which is which, so you **revoke the entire family**, logging both out. The
real user re-authenticates with a password; the attacker cannot. **A stolen refresh token becomes
useless the moment either party uses it after the other.**

**Three implementation notes:**

- **Store the hash**, so a leaked database is not a set of live credentials.
- **Same generic error for every failure**, or the response distinguishes "expired" from "reused"
  and tells an attacker what happened.
- **Alert on `refresh_token_reuse_detected`** (Day 143). It is one of the highest-signal security
  events you can emit — a spike means credential theft, not a bug.

## Delivering the pair (Day 172's hybrid)

```java
@PostMapping("/api/v1/auth/refresh")
ResponseEntity<AccessTokenResponse> refresh(
        @CookieValue("refresh_token") String refreshToken) {           // ⭐ HttpOnly cookie
    TokenPair pair = tokens.refresh(refreshToken);
    return ResponseEntity.ok()
        .header(SET_COOKIE, refreshCookie(pair.refreshToken()).toString())
        .body(new AccessTokenResponse(pair.accessToken(), 900));       // ⭐ access token in the body
}
```

Access token in the body, held in memory by the client. Refresh token in an `HttpOnly`, `Secure`,
`SameSite=Strict` cookie scoped to `/api/v1/auth/refresh`.

# Part 4 — ⭐ Revocation, which is the honest weak point

**Day 114's core problem: a signed token is valid until it expires. There is no "delete".** The
options, with their real costs:

| Approach | Cost |
|---|---|
| ⭐ **Short access tokens (5–15 min)** | **the primary answer.** Revocation latency = the TTL |
| Denylist of revoked `jti` in Redis | ⭐ a lookup per request — you have reintroduced state, but only for the exceptional case |
| ⭐ **`tokensValidAfter` per user** | one timestamp; token rejected if `iat` precedes it. Cheap if cached, and it revokes *everything* at once |
| Revoke the refresh token only | access token still works until it expires — usually acceptable |

```java
// The tokensValidAfter approach — a good default
if (claims.getIssuedAt().toInstant().isBefore(user.getTokensValidAfter())) {
    throw new JwtException("token revoked");
}
```

**Set `tokensValidAfter = now()` on logout-everywhere, password change, and role revocation.** One
column, no per-token bookkeeping, and it handles the cases that actually matter.

**⭐ The honest framing for an interview:** JWT revocation is a trade, not a solved problem. You are
choosing "no per-request state" and paying "revocation is not instant". **If your requirement is
instant revocation, sessions are the correct tool** (Day 172) — and saying that shows judgement
rather than reciting a workaround.

## Logout, which is not what people expect

```java
@PostMapping("/api/v1/auth/logout")
ResponseEntity<Void> logout(@CookieValue(name = "refresh_token", required = false) String rt) {
    if (rt != null) tokens.revokeFamily(hash(rt));         // ⭐ this is the real logout
    return ResponseEntity.noContent()
        .header(SET_COOKIE, expiredRefreshCookie().toString())
        .build();
}
```

**Logout revokes the refresh token and clears the cookie. The access token remains valid until it
expires** — which is why the 15-minute TTL matters. The client discards it; a thief who already has
it keeps it for those minutes. **Say this plainly rather than pretending logout is instant.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ No algorithm allow-list | `alg:none`, algorithm confusion (Day 114) |
| ⭐ No token type claim | a 30-day refresh token works as an access token |
| No issuer/audience validation | a token from another service is accepted |
| No clock skew tolerance | spurious 401s under normal drift |
| Missing header treated as an error | every public endpoint breaks |
| No `ProblemDetail` written in the filter | whitelabel HTML from a JSON API |
| Not `OncePerRequestFilter` | token parsed twice on error dispatch |
| Long-lived access tokens | revocation latency measured in days |
| Storing refresh tokens in plaintext | a leaked table is live credentials |
| No rotation | a stolen refresh token works for 30 days |
| No reuse detection | theft is undetectable |
| Different errors for expired vs reused | tells the attacker what happened |
| Secret in `application.yml` | full compromise, silently |
| HS256 shared across services | any service can mint tokens for any other |
| Sensitive data in claims | ⭐ a JWT is **signed, not encrypted** — base64, readable by anyone |
| Claiming logout is instant | it is not; be honest about the window |

## Interview questions

**Q: Walk me through JWT authentication in Spring.**
A `OncePerRequestFilter` before `UsernamePasswordAuthenticationFilter` extracts the bearer token,
parses it against an algorithm allow-list with issuer, audience and token-type checks, builds an
`Authentication` from the claims and puts it in the `SecurityContext`. On failure it clears the
context and writes RFC 7807 itself, because a filter is outside the DispatcherServlet so the error
advice never sees it.

**Q: Which validations does the library not do for you?**
The ones that matter most: pinning the algorithm, and checking a token-type claim. Without the type
check, a long-lived refresh token is accepted as an access token, which silently converts a 15-minute
window into 30 days.

**Q: How do you handle refresh tokens?**
Single-use with rotation, stored as hashes, grouped into a family. A second use of a token means two
parties hold it, so I revoke the whole family and alert — a stolen token becomes useless as soon as
either party uses it after the other. The refresh token lives in an `HttpOnly` cookie scoped to the
refresh path; the access token stays in memory.

**Q: How do you revoke a JWT?**
Honestly — you largely don't. Short access tokens bound the window, refresh revocation stops renewal,
and a per-user `tokensValidAfter` timestamp handles password changes and logout-everywhere in one
column. If the requirement is genuinely instant revocation, sessions are the right tool and I would
say so.
