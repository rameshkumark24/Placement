# Part 1 — Status codes, decided properly

## The families

```
1xx  informational      103 Early Hints
2xx  success            the request worked
3xx  redirection        go elsewhere
4xx  CLIENT error       the caller must change something
5xx  SERVER error       we broke; the caller may retry
```

The 4xx/5xx boundary is the one that matters operationally:

> **4xx means "do not retry this unchanged". 5xx means "this might work if you try again".**

That is not philosophy — it drives client retry logic (Day 123), your alerting thresholds, and your
error budget. **Returning 500 for a validation failure is a real operational bug**: it pages someone,
pollutes your error rate, and tells the client to retry something that can never succeed.

## The codes worth knowing precisely

| Code | Meaning | Use when |
|---|---|---|
| `200` | OK | Success with a body |
| `201` | Created | + `Location` header |
| `202` | Accepted | Async; include a status URL |
| `204` | No Content | Success, nothing to say |
| `301` / `308` | Moved permanently | 308 preserves the method; 301 historically did not |
| `304` | Not Modified | Conditional GET (Day 102) |
| `400` | Bad Request | Malformed — unparseable JSON, wrong types |
| `401` | **Unauthenticated** | No or invalid credentials. Must send `WWW-Authenticate`. |
| `403` | **Forbidden** | Authenticated, but not allowed |
| `404` | Not Found | Absent — **or hiding a 403, deliberately** |
| `405` | Method Not Allowed | Must send `Allow: GET, POST` |
| `406` / `415` | Not Acceptable / Unsupported Media Type | Content negotiation (Day 102) |
| `409` | Conflict | Duplicate, version conflict, illegal state transition |
| `410` | Gone | Permanently removed — more useful than 404 for deprecation |
| `412` | Precondition Failed | `If-Match` failed (Day 102) |
| `422` | Unprocessable Content | Syntactically valid, semantically wrong |
| `429` | Too Many Requests | Rate limited. **Must send `Retry-After`.** |
| `500` | Internal Server Error | We broke |
| `502` / `503` / `504` | Bad Gateway / Unavailable / Gateway Timeout | Upstream problems |

**`401` vs `403` is the distinction people fail on**, and the naming does not help — `401` is named
"Unauthorized" but means *unauthenticated*.

```
401 = "I do not know who you are."          → the client should log in
403 = "I know who you are, and no."         → logging in again will not help
```

**`400` vs `422`:** `400` for "I cannot parse this"; `422` for "I parsed it and it is wrong" — a
negative quantity, an end date before a start date, a state transition that is not legal. Some APIs
use `400` for both and document it; that is acceptable. What is not acceptable is using them
interchangeably at random.

## The `404`-instead-of-`403` decision

```
GET /orders/42        (belongs to another customer)
→ 403? "This exists, and it is not yours."     ← confirms existence
→ 404? "There is no such thing here."          ← reveals nothing
```

**Returning `404` prevents enumeration**: a `403` confirms the resource exists, which lets an
attacker map your data by probing ids (Day 119's IDOR). The cost is debuggability — a legitimate user
with a permission problem sees "not found" and is confused.

The usual resolution: **`404` for resources the caller has no relationship with, `403` where the
caller is legitimately in scope but lacks a specific permission.** Decide it once, document it, apply
it everywhere.

# Part 2 — The error contract

## RFC 7807 / RFC 9457 — Problem Details

There is a standard, and using it means clients and tooling already understand your errors:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.acme.com/problems/insufficient-funds",
  "title": "Insufficient funds",
  "status": 422,
  "detail": "Account ends 4471 is short by ₹450.00 for this transfer.",
  "instance": "/transfers/8f14e45f",

  "balance": "1050.00",
  "required": "1500.00",
  "trace_id": "a3f9c2e1"
}
```

| Field | Meaning |
|---|---|
| `type` | A **stable URI** identifying the problem class. The machine-readable identity. |
| `title` | A short human summary, constant for the type |
| `status` | Duplicates the HTTP status, for when the body is logged alone |
| `detail` | This *specific* occurrence — may include values |
| `instance` | Which request/resource this occurred on |
| *extensions* | Any additional members you need |

**`type` is the important field.** Clients must branch on a stable machine-readable identifier, never
on `detail` or on the status code alone — those change. A stable `type` is the contract; everything
else is presentation.

**Note `Content-Type: application/problem+json`**, which is what makes it a standard rather than
your own shape.

## Validation errors need a list

A single `detail` is wrong for form validation — the client wants to highlight every bad field at
once (the same argument as Day 074's `assertAll`).

```json
{
  "type": "https://api.acme.com/problems/validation-error",
  "title": "Request validation failed",
  "status": 422,
  "errors": [
    { "field": "email",     "code": "invalid_format",  "detail": "Not a valid email address." },
    { "field": "age",       "code": "out_of_range",    "detail": "Must be between 18 and 120." },
    { "field": "items[2].quantity", "code": "too_small","detail": "Must be at least 1." }
  ],
  "trace_id": "a3f9c2e1"
}
```

Three properties that matter: **all errors at once**, a **machine-readable `code`** per error so the
client can localise the message, and a **path** (`items[2].quantity`) that lets the client attach the
error to the right input.

## What must never appear in an error

```json
// 💀 every line of this is a finding
{
  "error": "org.postgresql.util.PSQLException: ERROR: duplicate key value violates unique
            constraint \"users_email_key\"\n  Detail: Key (email)=(ram@example.com) already exists.",
  "stackTrace": ["com.acme.UserService.create(UserService.java:42)", "..."],
  "query": "INSERT INTO users (email, password_hash) VALUES ('ram@…', '$2a$…')"
}
```

That leaks the database engine, the schema, table and column names, your package structure, and a
password hash — free reconnaissance (Day 062, Day 119). It also confirms that `ram@example.com` is a
registered user, which is an account-enumeration vulnerability on its own.

```json
// ✅
{ "type": ".../email-already-registered", "title": "Email already registered",
  "status": 409, "trace_id": "a3f9c2e1" }
```

> **Log the detail, return the reference.** The `trace_id` in the response corresponds to the full
> stack trace in your logs (Day 073A's MDC). Support can find the incident in one query; the client
> learns nothing exploitable.

*(And note: if this endpoint is public signup, even `409 email already registered` enables
enumeration. The privacy-preserving pattern is to return `202` regardless and send an email that
differs — "here's your reset link" versus "someone tried to sign up with your address".)*

## Consistency and the 5xx rule

**One error shape for the entire API.** A client should write one error handler, not one per
endpoint. That means your framework's default error page must be replaced too — a `404` from your
router and a `404` from your handler must look identical.

**5xx bodies say nothing.** "Internal error" plus a trace id. The client cannot act on the detail and
an attacker can.

# Part 3 — D-09 · Aggregates and window functions

## Aggregates and `GROUP BY`

```sql
SELECT region,
       COUNT(*)                    AS orders,
       COUNT(DISTINCT customer_id) AS customers,
       SUM(total_cents)            AS revenue,
       AVG(total_cents)::int       AS avg_order,
       MIN(created_at)             AS first_order,
       PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY total_cents) AS median
FROM orders
WHERE created_at >= DATE '2026-01-01'      -- rows first (Day 097)
GROUP BY region
HAVING SUM(total_cents) > 100000            -- groups after
ORDER BY revenue DESC;
```

Day 097 and Day 100 covered `WHERE` vs `HAVING` and the `COUNT(*)` vs `COUNT(col)` trap. Two
additions:

**`GROUPING SETS`, `ROLLUP` and `CUBE`** compute several groupings in one pass:

```sql
SELECT region, product_category, SUM(total_cents)
FROM orders GROUP BY ROLLUP (region, product_category);
-- gives: per (region, category), per region, and the grand total — in one query
```

**`FILTER`** is far cleaner than `CASE WHEN` inside an aggregate, and it is standard SQL:

```sql
SELECT
  COUNT(*)                                   AS total,
  COUNT(*) FILTER (WHERE status = 'PAID')    AS paid,
  COUNT(*) FILTER (WHERE status = 'REFUNDED')AS refunded,
  SUM(total_cents) FILTER (WHERE created_at >= now() - interval '7 days') AS last_week
FROM orders;
```

## Window functions — the big one

> **An aggregate collapses rows into one. A window function computes across a set of rows and
> *keeps every row*.**

That single sentence is the whole concept, and it is the most common interview question on this
topic.

```sql
SELECT
  name,
  region,
  salary,
  AVG(salary) OVER (PARTITION BY region)                         AS region_avg,
  salary - AVG(salary) OVER (PARTITION BY region)                AS diff_from_avg,
  RANK()       OVER (PARTITION BY region ORDER BY salary DESC)   AS rank_in_region,
  ROW_NUMBER() OVER (PARTITION BY region ORDER BY salary DESC)   AS row_num,
  DENSE_RANK() OVER (PARTITION BY region ORDER BY salary DESC)   AS dense_rank
FROM employee;
```

Every employee row survives, and each carries its region's average alongside its own salary. With
`GROUP BY` you would have lost the individual rows.

### The `OVER` clause

```sql
OVER (
    PARTITION BY region              -- like GROUP BY, but does not collapse
    ORDER BY salary DESC             -- ordering within the partition
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW    -- the FRAME
)
```

**The frame is where people get caught.** Adding `ORDER BY` to a window changes the default frame
from the whole partition to `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — which is exactly
why a running total works:

```sql
SUM(amount) OVER (ORDER BY created_at)                      -- RUNNING total (default frame)
SUM(amount) OVER ()                                          -- grand total on every row
SUM(amount) OVER (PARTITION BY customer_id)                  -- per-customer total on every row
AVG(amount) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)   -- 7-day moving average
```

### The ranking functions

| Function | 100, 100, 90 gives |
|---|---|
| `ROW_NUMBER()` | 1, 2, 3 — arbitrary tie-break |
| `RANK()` | 1, 1, 3 — gaps after ties |
| `DENSE_RANK()` | 1, 1, 2 — no gaps |
| `NTILE(4)` | quartile buckets |
| `PERCENT_RANK()` | relative position 0–1 |

### `LAG` and `LEAD` — comparing to neighbours

```sql
SELECT
  month,
  revenue,
  LAG(revenue)  OVER (ORDER BY month)                      AS prev_month,
  revenue - LAG(revenue) OVER (ORDER BY month)             AS change,
  ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
        / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS pct_change
FROM monthly_revenue;
```

**Month-over-month growth with no self-join.** This is the query that makes window functions worth
learning — the self-join version is three times longer and slower.

Note `NULLIF(x, 0)` guarding the division (Day 097).

### The classic problem: top-N per group

Asked in almost every SQL interview:

> *"The top 3 highest-paid employees in each department."*

```sql
-- ❌ you cannot filter on a window function in WHERE —
--    windows are computed AFTER WHERE (Day 097's evaluation order)
SELECT * FROM employee
WHERE RANK() OVER (PARTITION BY dept ORDER BY salary DESC) <= 3;   -- ERROR

-- ✅ wrap it
SELECT * FROM (
  SELECT name, dept, salary,
         DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
  FROM employee
) ranked
WHERE rnk <= 3;
```

**Window functions are evaluated after `WHERE`, `GROUP BY` and `HAVING`, but before `ORDER BY` and
`LIMIT`** — which is precisely why the subquery is required. Being able to explain *why* rather than
just knowing the trick is the difference between a memorised and an understood answer.

### Deduplication — the other classic

```sql
-- keep only the most recent row per customer
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
  FROM orders
)
SELECT * FROM ranked WHERE rn = 1;
```

Use `ROW_NUMBER` here, not `RANK` — ties would return several rows and defeat the deduplication.

### Named windows

```sql
SELECT name,
       RANK()       OVER w AS rank,
       DENSE_RANK() OVER w AS dense_rank,
       LAG(salary)  OVER w AS prev_salary
FROM employee
WINDOW w AS (PARTITION BY dept ORDER BY salary DESC);
```

Define it once. Cleaner, and it makes it obvious that the three functions share a window.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `500` for validation failures | Pages someone; tells the client to retry the impossible |
| `200` with `{"success": false}` | Every client must parse the body to know it failed |
| Confusing `401` and `403` | Clients retry the login uselessly, or give up wrongly |
| `403` where enumeration matters | Confirms which resources exist |
| Stack traces or SQL in the response | Reconnaissance; schema disclosure |
| One error at a time in validation | Client round-trips per field |
| Clients branching on `detail` text | Breaks when you rephrase the message |
| Different error shapes per endpoint | A handler per endpoint |
| Framework default error pages left in | Two shapes for the same status |
| `429` without `Retry-After` | Clients retry immediately and make it worse |
| Filtering a window function in `WHERE` | Syntax error — wrap it in a subquery |
| `RANK` where `ROW_NUMBER` is meant | Ties break deduplication |
| Forgetting `ORDER BY` changes the frame | A "total" is silently a running total |

## Interview questions

**Q: `401` vs `403`?**
`401` means unauthenticated — the credentials are missing or invalid, and it must include
`WWW-Authenticate`. `403` means authenticated but not permitted, so retrying the login will not help.

**Q: When do you return `404` instead of `403`?**
When confirming existence would enable enumeration. A `403` tells an attacker the resource exists;
`404` reveals nothing. The usual policy is `404` for resources the caller has no relationship with,
`403` where they are in scope but lack a permission.

**Q: `400` vs `422`?**
`400` for malformed input you cannot parse; `422` for well-formed input that is semantically invalid.

**Q: What does a good error response contain?**
A stable machine-readable `type`, a human-readable title and detail, the status, a per-field list for
validation errors with codes, and a trace id — following RFC 7807 with
`Content-Type: application/problem+json`. Never internals.

**Q: Why should clients not branch on the message?**
Messages get rephrased and localised. The stable `type` (or a per-field `code`) is the contract.

**Q: Difference between an aggregate and a window function?**
An aggregate collapses a group into one row; a window function computes over a set of rows and
returns a value for every row, so the detail rows survive.

**Q: How do you get the top 3 per group?**
`DENSE_RANK()` (or `ROW_NUMBER()`) partitioned by the group and ordered by the metric, wrapped in a
subquery or CTE and filtered there — because window functions are evaluated after `WHERE`.

**Q: When would you use `LAG`?**
Comparing a row to its predecessor — month-over-month change, time between events, detecting gaps —
without a self-join.

## 🎙️ Articulation drill

Two minutes: **"How do you design error responses for an API?"**

One shape for the whole API, RFC 7807 with `application/problem+json`, a stable `type` clients branch
on, per-field codes for validation, a trace id instead of internals, correct status codes with the
4xx/5xx retry meaning, and a documented `404`-vs-`403` policy. Then the framing: an API is judged by
its errors, because that is when the developer using it is stressed.
