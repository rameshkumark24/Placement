# Part 1 — Why OIDC exists

Using bare OAuth for login produces a specific vulnerability, and it is worth seeing before the fix:

```
❌ The naive "login with OAuth":
1. App gets an access token from the provider
2. App calls /userinfo with it → { "sub": "17", "email": "ram@…" }
3. App logs the user in as that email
```

**The flaw: an access token is a bearer credential (Day 115b), and the app never verified who it was
issued *to*.** An attacker with a token issued for *their own* application — obtained legitimately
from a user of that app — can present it to yours. Your app calls `/userinfo`, gets the victim's
identity, and logs the attacker in as them.

This is the **confused deputy problem**, and it broke real implementations. It is the reason OIDC's
ID token exists.

> **OIDC's contribution: a token that is *about the user*, issued *to a specific application*, and
> cryptographically verifiable.**

# Part 2 — The ID token

```json
// header
{ "alg": "RS256", "kid": "abc123" }

// payload
{
  "iss": "https://accounts.google.com",       // issuer         ✅ verify
  "sub": "108734829374829374",                // ⭐ the STABLE user id
  "aud": "your-client-id.apps.googleusercontent.com",   // ✅ MUST be YOUR client id
  "exp": 1755176400,                          // ✅ verify
  "iat": 1755172800,
  "nonce": "n-0S6_WzA2Mj",                    // ✅ must match what you sent
  "at_hash": "…",                             // binds this ID token to the access token
  "auth_time": 1755172700,                    // when the user actually authenticated
  "amr": ["pwd", "mfa"],                      // how — auth methods
  "email": "ram@example.com",
  "email_verified": true,                     // ⚠️ CHECK THIS
  "name": "Ram Kumar",
  "picture": "https://…"
}
```

**It is a JWT** (Day 114), so everything from that day applies — signature verification with a pinned
algorithm, JWKS key lookup by `kid`, and validation of `iss`, `aud` and `exp`.

## The three claims that matter most

**⭐ `sub` is the user identifier — never the email.**

```java
// ❌ emails change; two providers can assert the same email; it is a mutable attribute
User user = repo.findByEmail(claims.get("email"));

// ✅ (issuer, subject) is the stable, globally unique identity
User user = repo.findByIssuerAndSubject(claims.getIssuer(), claims.getSubject());
```

`sub` is stable and unique **within an issuer**, so the key is the pair. A user who changes their
email at Google keeps the same `sub`; a user whose old email is reassigned to someone else does not
inherit their account.

**⚠️ `email_verified` must be checked.** If a provider lets a user set an unverified email, and you
match accounts by email, an attacker registers `victim@company.com` at a permissive provider and
takes over the victim's account at your service. **This is a real and repeated account-takeover
pattern** — the "Sign in with X" account-linking vulnerability class.

**`aud` must equal your client id.** This is the check that closes the confused-deputy hole above: a
token minted for another application will not carry your client id, so it is rejected.

## `nonce` — replay protection

```java
String nonce = randomUrlSafe(32);
session.put("oidc_nonce", nonce);
// authorization request: &nonce=<nonce>&scope=openid profile email
// ... on the ID token:
if (!nonce.equals(claims.get("nonce"))) throw new SecurityException("nonce mismatch");
```

**`state` and `nonce` are different and you need both** (this is a favourite interview question):

| | Protects | Bound to |
|---|---|---|
| **`state`** | The **authorization request** — CSRF on the callback | Your session |
| **`nonce`** | The **ID token** — replay of a previously issued token | The token itself |

`state` stops someone else's flow being completed in your session. `nonce` stops a *previously
captured, still-valid* ID token being injected into a new flow.

## The flow

```
1. GET /authorize?response_type=code
                 &scope=openid profile email        ← "openid" is what makes it OIDC
                 &client_id=…&redirect_uri=…&state=…&nonce=…
                 &code_challenge=…&code_challenge_method=S256      (PKCE, Day 116)

2. User authenticates and consents

3. Redirect back with ?code=…&state=…

4. POST /token → { access_token, id_token, refresh_token }
                                 ↑ THE ADDITION over plain OAuth

5. VERIFY the ID token, then create YOUR OWN session (Day 113) or tokens (Day 115)
```

**Step 5's second half is the one people skip.** The provider's tokens authenticate the *user to
you*, once. After that you issue your own session or tokens. Do not use Google's access token as your
application's credential — it has the wrong audience, the wrong lifetime, and you cannot revoke it.

## Discovery and endpoints

```http
GET https://accounts.google.com/.well-known/openid-configuration
```
```json
{ "issuer": "https://accounts.google.com",
  "authorization_endpoint": "…/o/oauth2/v2/auth",
  "token_endpoint": "…/token",
  "userinfo_endpoint": "…/v3/userinfo",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
  "id_token_signing_alg_values_supported": ["RS256"] }
```

**Discovery means you configure one URL** and everything else is fetched — including the JWKS
location, so key rotation is automatic. Cache it, and cache the JWKS (Day 114).

`/userinfo` returns the same claims but *fresh*; the ID token is a snapshot from login. Use the ID
token for identity, `/userinfo` if you need current profile data later.

## The verification checklist

```java
// 1. signature — pinned algorithm, key by kid from JWKS      (Day 114)
// 2. iss   == the discovered issuer, exactly
// 3. aud   == your client id       ← closes the confused deputy hole
// 4. exp   not passed, iat not absurdly old, small clock skew allowance
// 5. nonce == the value you stored
// 6. azp   == your client id, if present and multiple audiences
// 7. email_verified == true, before using email for anything
// 8. auth_time within max_age, if you requested one
```

**Use a library.** `spring-security-oauth2-client`, Nimbus, or your provider's SDK. Every item above
is a place where a missing check is silently exploitable.

## Account linking — the hard part

The genuinely difficult design problem, and worth thinking through:

```
A user signs up with a password (ram@example.com), then later "Sign in with Google"
using the same address. Same person? Probably. Prove it.
```

| Approach | Verdict |
|---|---|
| Auto-link on matching email | ⚠️ **Only if `email_verified` is true AND you verified yours** |
| Auto-link on unverified email | ❌ **Account takeover** |
| Require the user to log in with the existing method first, then link | ✅ **Safest** |
| Never link — separate accounts | ✅ Safe, and confusing for users |

**The safe pattern:** if an account exists with that email, do not link automatically. Ask the user to
sign in with their existing method, then attach the provider from within an authenticated session.
Slightly more friction; removes an entire vulnerability class.

## Logout

OIDC logout is genuinely messy, and it is honest to say so:

- **RP-initiated logout** (`end_session_endpoint`) — redirect the user to the provider to sign out
  everywhere.
- **Front-channel** and **back-channel logout** — the provider notifies your application when a
  session ends elsewhere.

Most applications implement local logout only, and accept that the provider session persists — which
is why clicking "log out" on one site does not sign you out of Google. Knowing why is enough.

# Part 3 — D-13 · ACID

## The four properties, precisely

```sql
BEGIN;
  UPDATE account SET balance = balance - 500 WHERE id = 1;
  UPDATE account SET balance = balance + 500 WHERE id = 2;
COMMIT;
```

### A — Atomicity: all or nothing

The transaction is indivisible. A crash between the two updates leaves **neither** applied.

**Mechanism:** the write-ahead log (Day 078's D-01). Every change is logged before the data page is
modified, so recovery can **undo** uncommitted work and **redo** committed work.

Atomicity is about **failure**, not about concurrency. That distinction matters.

### ⭐ C — Consistency: the one everybody gets wrong

**Consistency does not mean "the data is correct".** It means:

> **A transaction moves the database from one valid state to another, where "valid" means
> *satisfying every declared constraint*** — primary keys, foreign keys, `CHECK`, `UNIQUE`, `NOT
> NULL`, and triggers.

**The database guarantees only what you declared.** If your business rule is "balance must never go
negative" and there is no `CHECK (balance >= 0)`, the database will cheerfully let it. Consistency is
therefore **a shared responsibility**: the database enforces your declared constraints atomically;
*you* must declare them (Day 081).

This is the property most often described incorrectly, and stating it precisely is a strong interview
signal. Many database theorists argue C does not belong in the list at all, since it is a property of
the schema rather than of the transaction system.

### I — Isolation: concurrent transactions do not interfere

**The strongest form, serializability, means the outcome equals *some* serial ordering** of the
concurrent transactions. In practice databases offer weaker levels for performance, each permitting
specific anomalies — that is Day 120's D-14, and it is the property with the most nuance.

Isolation is about **concurrency**, where atomicity is about failure.

### D — Durability: committed means permanent

Once `COMMIT` returns, the change survives a crash, a power loss, a restart.

**Mechanism:** the WAL is `fsync`ed to disk before `COMMIT` returns (Day 063's flush-versus-fsync).
Data pages may still be in memory; the log is what makes it durable.

⚠️ **Durability is a spectrum, not a boolean**, and this is worth knowing:

```sql
SET synchronous_commit = off;    -- COMMIT returns before the WAL is flushed
```

That makes commits dramatically faster and means **a crash can lose the last few hundred
milliseconds of committed transactions**. It is a legitimate choice for analytics or event ingestion
and unacceptable for payments. Similarly, a lying disk controller with a volatile write cache can
break durability regardless of what the database does — which is why cloud storage guarantees are
part of your durability story.

## Transactions in practice

```java
// Java, plain JDBC — before Spring does it for you (Stage 4)
try (Connection conn = dataSource.getConnection()) {
    conn.setAutoCommit(false);                       // ← BEGIN
    try {
        debit(conn, from, amount);
        credit(conn, to, amount);
        conn.commit();
    } catch (Exception e) {
        conn.rollback();                             // atomicity
        throw e;
    }
}
```

**Autocommit is on by default in JDBC**, so every statement is its own transaction — which means the
two-statement transfer above is *not* atomic unless you turn it off. That is the single most common
transaction bug in plain JDBC code.

Rules worth stating now, before Stage 4 makes them automatic:

| Rule | Why |
|---|---|
| **Keep transactions short** | They hold locks; long ones block others (Day 066's lock scope) |
| **Never do I/O inside a transaction** | An HTTP call holding a database lock for 2 seconds |
| **Never wait for user input inside one** | The lock is held for minutes |
| **Set a statement timeout** | A runaway query must not hold locks indefinitely |
| **Order operations consistently** | Prevents deadlock (Day 071's lock ordering — it applies here too) |

That last one is Day 071 reappearing: two transactions updating accounts A and B in opposite orders
deadlock exactly as two threads taking locks in opposite orders do. The database *detects* it and
kills one transaction with a serialization error — **so your application must be prepared to retry**,
which is Day 123.

## Savepoints and nesting

```sql
BEGIN;
  INSERT INTO orders …;
  SAVEPOINT after_order;
  INSERT INTO analytics …;          -- optional; may fail
  ROLLBACK TO SAVEPOINT after_order; -- undo just that, keep the order
COMMIT;
```

**There are no true nested transactions in SQL** — savepoints are the mechanism, and this is exactly
what Spring's `PROPAGATION_NESTED` uses under the hood (Stage 4, Day 137).

## Distributed transactions — and why you avoid them

Across two databases or two services, ACID stops being free. **Two-phase commit (2PC)** exists —
prepare, then commit — but it blocks if the coordinator fails after prepare, and it couples
availability across every participant.

The practical alternatives, which Stage 12 develops: the **Saga** pattern (a sequence of local
transactions with compensating actions), the **outbox** pattern (write the event in the same
transaction as the data, publish it asynchronously), and idempotency (Day 123) so retries are safe.

For today: **know that ACID is a single-database guarantee, and that reaching for 2PC is usually a
sign the boundaries are wrong.**

## Common mistakes

| Mistake | Consequence |
|---|---|
| Using bare OAuth for login | Confused deputy — a token from another app logs in as its user |
| Not validating `aud` on the ID token | The same vulnerability |
| Using `email` as the user key | Emails change and are reassigned |
| Not checking `email_verified` | **Account takeover** via a permissive provider |
| Auto-linking accounts on unverified email | Same |
| Confusing `state` with `nonce` | One of the two protections is missing |
| Using the provider's access token as your session | Wrong audience, wrong lifetime, unrevocable |
| Not caching discovery and JWKS | A fetch per login against the provider |
| Autocommit left on for a multi-statement operation | **Not atomic** |
| Believing "C" means the data is correct | It means declared constraints hold |
| Assuming durability is absolute | `synchronous_commit=off` and volatile caches weaken it |
| Doing HTTP calls inside a transaction | Locks held for seconds |
| Inconsistent update order across transactions | Deadlock |
| Not handling serialization failures | Lost work under contention |

## Interview questions

**Q: What does OIDC add to OAuth 2.0?**
An ID token — a signed JWT about the *user*, issued to a specific audience — plus a `nonce`, standard
claims, a `/userinfo` endpoint and discovery. It turns delegated authorization into standardised
authentication.

**Q: Why can't you just use an OAuth access token to log someone in?**
An access token is a bearer credential with no verifiable audience from your perspective. An attacker
can present a token issued for *their* application, and your `/userinfo` call returns the victim's
identity — the confused deputy problem. The ID token's `aud` claim closes it.

**Q: `state` versus `nonce`?**
`state` protects the authorization *request* against CSRF and is bound to your session. `nonce`
protects the ID *token* against replay and is bound into the token. You need both.

**Q: Why use `sub` rather than `email` as the user id?**
`sub` is stable and unique within the issuer; email is mutable and can be reassigned. The correct key
is the `(iss, sub)` pair.

**Q: Why does `email_verified` matter?**
If you match accounts by email and the provider allows unverified addresses, an attacker registers
the victim's email at a permissive provider and takes over the account. Check the claim, and prefer
requiring an authenticated session before linking providers.

**Q: State the four ACID properties precisely.**
Atomicity — all or nothing, via the WAL's undo. Consistency — the transaction moves the database
between states satisfying every *declared* constraint; it does not mean the data is semantically
correct. Isolation — concurrent transactions do not interfere, with the strength depending on the
isolation level. Durability — a committed change survives a crash, because the log is fsynced before
commit returns.

**Q: Which ACID property do people describe wrongly?**
Consistency. It is about declared constraints, not correctness — the database enforces only what you
declared, so undeclared business rules are not protected at all.

**Q: Is durability absolute?**
No. `synchronous_commit=off` returns from commit before the WAL is flushed, trading a window of
possible loss for throughput, and a volatile disk write cache can break the guarantee independently
of the database.

**Q: Why avoid distributed transactions?**
Two-phase commit blocks if the coordinator fails after the prepare phase and couples the availability
of every participant. Sagas with compensating actions, the outbox pattern and idempotent retries are
the practical alternatives.
