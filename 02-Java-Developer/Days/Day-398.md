# Day 398

**L-398** · The eight fallacies — and the ninth, which is the real one

**Time:** 3 hrs · **Mode:** NEW · **⭐ Stage 12 opens**

> **⭐⭐ You cannot tell a dead node from a slow one. Every distributed system you will ever build is a
> workaround for that single sentence.**
>
> Today: the eight fallacies with a price attached to each, **partial failure as the property that makes
> distribution categorically different rather than merely harder**, and the cost table you should be
> able to recite before you split anything into two services.

---

# Part 1 — ⭐ The eight fallacies, with what each one costs

| # | ⭐ Fallacy | ⭐ What it costs when believed |
|---|---|---|
| ⭐ 1 | **The network is reliable** | ⭐⭐ **no retries, no idempotency — duplicate charges and lost work** |
| ⭐ 2 | **Latency is zero** | ⭐⭐ **the N+1 call in a loop; 200 calls × 1 ms = a 200 ms p50 you cannot explain** |
| ⭐ 3 | **Bandwidth is infinite** | ⭐ whole objects over the wire; Day 396's cross-AZ bill |
| ⭐ 4 | **The network is secure** | ⭐ no mTLS, no authz between services — one breach reaches everything |
| ⭐ 5 | **Topology doesn't change** | ⭐⭐ **hard-coded IPs, cached DNS** (Day 387 — twice already) |
| ⭐ 6 | **There is one administrator** | ⭐ someone else's deploy changes your dependency's behaviour at 14:00 |
| ⭐ 7 | **Transport cost is zero** | ⭐⭐ serialisation, TLS handshakes, GC pressure from marshalling |
| ⭐ 8 | **The network is homogeneous** | ⭐ one service's 30-second timeout meets another's 2-second one |

```
⭐⭐ AND THE NINTH, WHICH SUBSUMES MOST OF THEM:
⭐⭐   "FAILURE IS DETECTABLE."
⭐   ⇒ ⭐⭐ It is not. A node that has crashed and a node that is in a 12-second GC pause
⭐     look IDENTICAL from the outside. ⭐⭐ A TIMEOUT IS A GUESS ABOUT THE FUTURE.
⭐   ⇒ ⭐ Everything in this stage — quorums, leases, fencing, consensus — exists because
⭐     ⭐⭐ you must ACT on that guess without the guess ever becoming certain.
```

> **⭐ This is why Day 340's timeouts, Day 393's visibility timeout and Day 411's fencing tokens are the
> same conversation.** The system must remain correct **when the guess is wrong**, because it will
> regularly be wrong.

# Part 2 — ⭐⭐ Partial failure: the categorical difference

```
⭐ IN A MONOLITH:  order.save()  ⇒ ⭐ it returns, or it throws. ⭐ TWO outcomes.

⭐⭐ ACROSS A NETWORK: orderClient.save()  ⇒ ⭐⭐ FIVE outcomes:
⭐   1. ⭐ succeeded, you know it
⭐   2. ⭐ failed before doing anything, you know it
⭐   3. ⭐⭐ SUCCEEDED, and the RESPONSE was lost      ⇒ you believe it failed
⭐   4. ⭐⭐ still running, slowly                      ⇒ you timed out and moved on
⭐   5. ⭐⭐ failed HALFWAY                             ⇒ partial state exists somewhere
```

| ⭐ Consequence | |
|---|---|
| ⭐⭐ **"Did it happen?" is unanswerable in general** | ⭐⭐ so you must make the answer **not matter** |
| ⭐⭐ **⇒ retry, and therefore idempotency** | ⭐⭐ at-least-once + idempotent = **effectively once** (Day 335) |
| ⭐ ⇒ every mutation needs a client-supplied key | ⭐ the idempotency key, not a server-generated id |
| ⭐ ⇒ every operation needs a deadline | ⭐ (Day 336) — a call with no deadline is a resource leak |
| ⭐⭐ ⇒ **compensations replace rollback** | ⭐⭐ there is no distributed `ROLLBACK` (Day 408) |

⚠️ **Case 3 is the one people never handle.** The write succeeded, the acknowledgement was lost, the
client retries, **and now there are two orders.** Every "we got charged twice" incident is case 3, and
**the fix is never "make the network reliable" — it is an idempotency key on the write path.**

# Part 3 — ⭐⭐ The cost of one network hop

| | ⭐ In-process call | ⭐⭐ Network call |
|---|---|---|
| ⭐ Latency | ⭐ ~1 ns | ⭐⭐ **~0.5–1 ms same AZ — a million times more** |
| ⭐ Failure modes | ⭐ exception | ⭐⭐ **five (above), plus timeout tuning** |
| ⭐ Types | ⭐ compiler-checked | ⭐⭐ **a serialisation contract you must version** (Day 400) |
| ⭐ Refactor | ⭐ IDE, atomic | ⭐⭐ **a coordinated deploy across teams** |
| ⭐ Debugging | ⭐ one stack trace | ⭐⭐ **distributed tracing, or nothing** (Day 376) |
| ⭐ Transaction | ⭐ ACID, free | ⭐⭐ **a saga you designed and operate** |
| Cost | free | ⭐ cross-AZ bytes (Day 396) |

```
⭐⭐ AND THE MULTIPLICATION THAT KILLS SYNCHRONOUS CHAINS:
⭐   5 synchronous dependencies, each 99.9% available
⭐   ⇒ ⭐⭐ 0.999^5 = 99.5%  ⇒ ⭐⭐ 3.6 hours of downtime a month, from components
⭐     that are each "three nines". ⭐ You did not build a fault-tolerant system.
⭐     ⭐⭐ You built a system that fails if ANY of five things fails.
⭐ ⇒ ⭐ Async breaks the multiplication: a queued call survives the callee being down (Day 399).
```

> **⭐⭐ Distribution is a cost you pay to buy something specific — independent deployment, independent
> scaling, team autonomy, or fault isolation.** If you cannot name which of those you are buying,
> **you are paying the cost for nothing** (Day 306's modular monolith).

# Part 4 — ⭐ What you must therefore write, every time

| ⭐ Requirement | ⭐ Because |
|---|---|
| ⭐⭐ **Timeouts on every call** | ⭐⭐ **the default in most clients is "forever"** — one slow dependency exhausts your threads |
| ⭐ **Deadlines propagated** | ⭐ don't do work nobody is waiting for (Day 336) |
| ⭐⭐ **Retries with backoff, jitter and a BUDGET** | ⭐⭐ naive retries turn a blip into a **retry storm** (Day 413) |
| ⭐⭐ **Idempotency keys on mutations** | ⭐⭐ because of case 3 |
| ⭐ **Circuit breakers / bulkheads** | ⭐ stop cascades (Day 340) |
| ⭐ **Trace context on every hop** | ⭐ debugging is otherwise archaeology |
| ⭐ **Explicit degradation** | ⭐ what still works when this dependency is gone? |

```java
// ⭐ The shape of every remote call in a distributed system, in one place
@Retry(name = "pricing")              // ⭐ backoff + jitter, bounded attempts
@CircuitBreaker(name = "pricing", fallbackMethod = "cachedPrice")   // ⭐ degrade
@TimeLimiter(name = "pricing")        // ⭐⭐ a deadline, always
CompletableFuture<Price> price(String sku, String idempotencyKey) { ... }
```

⚠️ **And the rule that costs teams the most when skipped: retries must be bounded system-wide, not
per-hop.** Three retries at each of four layers is **81 requests** for one user action. **A retry budget
— "no more than 10% of traffic may be retries" — is what actually prevents the storm.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Assuming a timeout means it did not happen** | ⭐⭐ case 3 — it may have fully succeeded |
| ⭐ No idempotency key on mutations | ⭐⭐ duplicate orders, duplicate charges |
| ⭐⭐ **No timeout on a client call** | ⭐⭐ the default is often infinite; threads exhaust |
| ⭐ Retries without backoff, jitter or a budget | ⭐⭐ a retry storm amplifies the outage |
| ⭐ Per-hop retries multiplying | ⭐ 3⁴ = 81 requests per user action |
| ⭐⭐ **Synchronous chains of five services** | ⭐⭐ availability multiplies down to 99.5% |
| ⭐ Treating a remote call like a local one | ⭐⭐ six orders of magnitude and five failure modes |
| ⭐ Distributing without naming what it buys | ⭐⭐ all the cost, none of the benefit |
| No trace context | debugging becomes archaeology |
| Believing failure detection is solvable | ⭐⭐ it is not — design for the wrong guess |

## Interview questions

**Q: Which fallacy matters most?**
The one that is usually left off the list: that failure is detectable. A crashed node and a node in a
twelve-second garbage collection pause are indistinguishable from outside, so a timeout is a guess about
the future rather than an observation. Everything else in distributed systems — quorums, leases, fencing
tokens, consensus — exists because you have to act on that guess while knowing it will regularly be
wrong. Most of the classic eight follow from it: you retry because you cannot tell, and you need
idempotency because you retry.

**Q: What is partial failure and why does it change how you write code?**
In a single process a call returns or throws — two outcomes. Across a network there are five: it
succeeded and you know; it failed cleanly; it succeeded but the response was lost; it is still running
slowly and you gave up; or it failed halfway leaving partial state. The third is the one nobody handles
and it is behind every "we were charged twice" incident. Since "did it happen" is not answerable in
general, you make it not matter — client-supplied idempotency keys on every mutation, deadlines on every
call, and compensating actions instead of rollback, because there is no distributed rollback.

**Q: Five services each with three nines. What is the availability of a synchronous chain through all
of them?**
About 99.5%, which is roughly three and a half hours of downtime a month — you have combined five
reliable components into one unreliable system, because the chain fails if any link fails. That
arithmetic is the strongest argument for asynchronous communication, since a queued call survives the
callee being down entirely. It is also the argument for degradation: if a dependency is not on the
critical path for the user's outcome, the call should be able to fail without failing the request.

**Q: What is a retry budget and why does per-call retry configuration not suffice?**
Because retries compose multiplicatively. Three attempts at each of four layers is eighty-one requests
for one user action, so a dependency that slows down slightly gets hit with an order of magnitude more
traffic exactly when it is struggling — the retry storm. A budget caps retries as a fraction of total
traffic, typically around ten percent, so amplification is bounded no matter how many layers exist.
Retries also need jitter, because synchronised retries from thousands of clients arrive as a spike, and
they need to be paired with a circuit breaker so a persistently failing dependency stops being retried at
all.

**Q: When should you not distribute?**
When you cannot name what you are buying. Distribution costs six orders of magnitude in call latency,
five failure modes instead of two, a versioned serialisation contract, coordinated deploys, and a
transaction model you have to build yourself. You pay that to buy independent deployment, independent
scaling, team autonomy or fault isolation. If none of those is the actual constraint, a modular monolith
gives you the boundaries without the network, and you can extract a service later when the boundary has
proven itself.

## Mini task

1. ⭐⭐ Take one remote call in your flagship and **enumerate all five outcomes.** Write what your code
   currently does in each.
2. ⭐⭐ Reproduce **case 3**: make the server succeed and drop the response. Confirm your client creates a
   duplicate. Then add an **idempotency key** and confirm it does not.
3. ⭐ Audit every HTTP and JDBC client for a **timeout.** Find at least one with none.
4. ⭐⭐ Add a **retry budget** and prove that a failing dependency does not receive amplified traffic.
5. ⭐ Introduce **500 ms of latency** into a dependency and watch what happens to your thread pool.
6. ⭐⭐ Compute your **synchronous availability chain** — list your dependencies and multiply.
7. ⭐ Convert one synchronous dependency to **asynchronous** and recompute.
8. ⭐ Add **jitter** to your retries and compare the arrival pattern under load.
9. ⭐⭐ Write down, for your flagship, **what still works** when each dependency is down. If any answer is
   "nothing", that is the work item.
10. ⭐ For each of the eight fallacies, name **one line of your own code** that assumes it.
