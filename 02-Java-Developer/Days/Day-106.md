# Day 106

**L-106** · Serialization, content negotiation, JSON pitfalls (dates, floats, big ints)

**Time:** 3 hrs · **Mode:** NEW

> Serialization looks solved — annotate a class, get JSON. It is not solved, and the failures are
> *silent*: a value that arrives subtly wrong is worse than one that fails to arrive. Today is the
> four data types that corrupt in transit, and how Jackson actually works.

---

# Part 1 — What JSON can and cannot represent

JSON has **six** types: `string`, `number`, `boolean`, `null`, `array`, `object`. That is all.
Everything else in your language is an encoding *convention* you and the client must agree on.

| Java | JSON | Risk |
|---|---|---|
| `String` | string | ✅ safe |
| `int`, `short` | number | ✅ safe |
| `long` | number | ⚠️ **breaks above 2^53 in JavaScript** |
| `BigDecimal` | number | 💀 **precision lost via double** |
| `double` | number | 💀 already wrong for money (Day 042B) |
| `LocalDate` / `Instant` | string | ⚠️ format must be agreed |
| `enum` | string | ✅ if you send the name |
| `byte[]` | string | base64, by convention |
| `Map<K,V>` | object | keys must be strings |
| `null` | null | ⚠️ absent vs null are different |

**JSON has no integer/float distinction and no defined precision.** RFC 8259 says implementations
vary and warns that interoperability is only assured within IEEE-754 double range. Everything below
follows from that one gap.

---

## Pitfall 1 — Large integers

```json
{"id": 9007199254740993}
```

```javascript
JSON.parse('{"id": 9007199254740993}').id      // → 9007199254740992   ← silently WRONG
Number.MAX_SAFE_INTEGER                        // 9007199254740991 = 2^53 - 1
```

JavaScript numbers are doubles. Any integer above 2^53 loses precision **without any error**.

This is not hypothetical: **Twitter had to add `id_str` to every API object** because their snowflake
ids exceeded 2^53 and every JavaScript client was mangling them.

```java
// The fix — serialize as a string
public record OrderResponse(
    @JsonSerialize(using = ToStringSerializer.class) long id,
    …
) { }

// Or globally
mapper.registerModule(new SimpleModule()
    .addSerializer(Long.class, ToStringSerializer.instance)
    .addSerializer(Long.TYPE, ToStringSerializer.instance));
```

> **Send every identifier as a string** (Day 103). It costs two quote characters and removes an
> entire failure class — including the one where you later change from `long` to a UUID.

---

## Pitfall 2 — Decimals and money

```java
BigDecimal price = new BigDecimal("1499.99");
```

```json
{"price": 1499.99}
```

Serialized as a JSON number, and the client parses it into a double — Day 042B's problem, now across
a network. Then `0.1 + 0.2` in the client is `0.30000000000000004`, and someone's invoice is off by a
paisa.

Three defensible representations:

```json
{"price": "1499.99", "currency": "INR"}          // ✅ string + explicit currency
{"price_cents": 149999, "currency": "INR"}       // ✅ integer minor units — Stripe's choice
{"price": {"amount": "1499.99", "currency": "INR", "scale": 2}}   // ✅ explicit object
```

Minor units are cleanest for arithmetic. **Beware the assumption that every currency has two decimal
places** — JPY has zero, KWD has three, so hard-coding ÷100 is a bug in any international system.

```java
mapper.enable(DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS);   // never parse into a double
```

## Pitfall 3 — Dates and times

The single most common source of production bugs in APIs.

```json
{"created": 1755172800}                    // ❌ seconds or millis? Which timezone?
{"created": "14/08/2026"}                  // ❌ 14 August or... it is ambiguous by locale
{"created": "2026-08-14T10:22:01"}         // ❌ no offset — 10:22 WHERE?
{"created": "2026-08-14T10:22:01Z"}        // ✅ ISO 8601, explicit UTC
{"created": "2026-08-14T15:52:01+05:30"}   // ✅ ISO 8601 with offset
```

> **Always ISO 8601, always with an explicit offset, and store UTC.**

```java
mapper.registerModule(new JavaTimeModule());
mapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);   // ← or you get epoch numbers
```

Type choice matters, and Day 042A covered it:

| Type | Use for |
|---|---|
| `Instant` | A moment in time — timestamps, `created_at` |
| `LocalDate` | A calendar date with no time — birthdays, invoice dates |
| `LocalDateTime` | ⚠️ **Almost never in an API.** No offset, so it is ambiguous. |
| `ZonedDateTime` | When the *zone* matters — a recurring meeting in Asia/Kolkata |
| `OffsetDateTime` | A moment plus a known offset |

**The "store the zone, not the offset" rule for future events:** a meeting at 09:00 Asia/Kolkata next
year must be stored with the zone id, because if the government changes the offset — and governments
do — a stored offset produces the wrong wall-clock time.

## Pitfall 4 — `null` versus absent

```json
{"name": "Ram", "nickname": null}     // "clear the nickname"
{"name": "Ram"}                        // "leave the nickname alone"
```

Two different intents, and most deserializers collapse them to the same `null` field. For a `PATCH`
(Day 102) the difference decides whether you erase data.

```java
// Distinguish them explicitly
public record UpdateUserRequest(
    JsonNullable<String> nickname          // openapi-jackson-nullable, or Optional<Optional<T>>
) { }

// present & non-null  → set it
// present & null      → clear it
// absent              → leave it
```

If you do not need the distinction, say so in your docs and use merge-patch semantics (Day 102),
where `null` explicitly means delete.

# Part 2 — Jackson, precisely

## The annotations that matter

```java
public record OrderResponse(
    @JsonProperty("order_id") String id,                    // rename on the wire
    @JsonIgnore              String internalNotes,          // never serialize
    @JsonInclude(NON_NULL)   String couponCode,             // omit when null
    @JsonFormat(shape = STRING, pattern = "yyyy-MM-dd") LocalDate deliveryDate,
    @JsonSerialize(using = MoneySerializer.class) Money total
) { }

@JsonIgnoreProperties(ignoreUnknown = true)     // ← tolerate fields you do not know
public record CreateOrderRequest(String sku, int quantity) { }
```

**`ignoreUnknown = true` on requests is the right default** and it is a versioning decision (Day 109):
a newer client sending a field your version does not know should not fail. Being strict here makes
every client upgrade a coordinated deployment.

*(The counter-argument is real: silently ignoring a misspelled field means a client thinks it set
something it did not. Some APIs return the ignored fields in a warning. Pick a position and document
it.)*

## Global configuration you should always set

```java
ObjectMapper mapper = JsonMapper.builder()
    .addModule(new JavaTimeModule())
    .addModule(new ParameterNamesModule())          // constructor params without @JsonProperty
    .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
    .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
    .enable(DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS)
    .serializationInclusion(JsonInclude.Include.NON_NULL)
    .propertyNamingStrategy(PropertyNamingStrategies.SNAKE_CASE)   // pick ONE (Day 103)
    .build();
```

**`ObjectMapper` is thread-safe once configured** and expensive to create — one instance, shared, as
a singleton bean. Creating one per request is a real and common performance bug.

## ⚠️ Polymorphic deserialization — the security part

Day 063A established that Java's native serialization is an RCE hazard because the *payload names the
class*. Jackson can be made to do exactly the same thing:

```java
mapper.enableDefaultTyping();                        // 💀 REMOVED in Jackson 2.10+ for this reason
mapper.activateDefaultTyping(LaissezFaireSubTypeValidator.instance);   // 💀 equally dangerous
```

With default typing enabled, the JSON carries a class name, and Jackson instantiates it — reproducing
the gadget-chain vulnerability in a format everyone believes is inert. This has produced dozens of
CVEs.

**The safe form is an explicit, closed set of subtypes:**

```java
@JsonTypeInfo(use = Id.NAME, property = "type")
@JsonSubTypes({                                       // ← an ALLOW-LIST (Day 105)
    @Type(value = CardPayment.class,  name = "card"),
    @Type(value = UpiPayment.class,   name = "upi"),
    @Type(value = WalletPayment.class,name = "wallet")
})
public sealed interface Payment permits CardPayment, UpiPayment, WalletPayment { }
```

The `sealed` interface (Day 042) means the compiler enforces that the annotation list is complete.
**Never `Id.CLASS`; never default typing.**

## Records, and why they are the right DTO

```java
public record CreateOrderRequest(String sku, int quantity) { }
```

Jackson supports records natively from 2.12. They are immutable (Day 034A), the canonical constructor
runs so **compact-constructor validation is guaranteed** (Day 105's parse-don't-validate), and there
are no setters to allow partial construction.

Two gotchas worth knowing: a record with **one component** can be ambiguous with a delimited value —
add `@JsonCreator(mode = PROPERTIES)`; and records need `ParameterNamesModule` plus `-parameters`
compilation, or every component needs `@JsonProperty`.

# Part 3 — Content negotiation and formats

```http
Accept: application/json
Content-Type: application/json; charset=utf-8
Accept: application/problem+json                  # errors (Day 104)
Accept: application/vnd.acme.v2+json              # media-type versioning (Day 109)
```

Day 102 covered `q` values, `406` and `415`. The practical addition: **`charset=utf-8` is the only
correct answer** — JSON is UTF-8 by specification (RFC 8259), and any other encoding is a bug
somebody will hit with a name containing a non-ASCII character (Day 063).

## When JSON is not the answer

| Format | Use when |
|---|---|
| **JSON** | The default. Human-readable, universal. |
| **Protobuf / gRPC** | Internal service-to-service — 3–10× smaller, typed, schema-enforced |
| **MessagePack / CBOR** | Binary JSON — smaller, no schema needed |
| **Avro** | Event streaming (Kafka) — schema registry, strong evolution rules |
| **NDJSON** | Streaming many records — one JSON object per line |
| **CSV** | Data export to spreadsheets |

**NDJSON is the answer to "how do I return a million records"**, and it is under-used:

```
{"id":1,"name":"a"}
{"id":2,"name":"b"}
```

The client processes each line as it arrives — constant memory on both sides — rather than waiting
for a single 400 MB array to be fully built and parsed.

That connects to the biggest serialization performance question:

## Streaming versus binding

```java
// ❌ builds the whole object graph in memory — an OOM on a large payload
List<Order> orders = mapper.readValue(hugeJson, new TypeReference<>() {});

// ✅ streaming — constant memory
try (JsonParser parser = mapper.getFactory().createParser(input)) {
    while (parser.nextToken() != JsonToken.END_ARRAY) {
        Order order = mapper.readValue(parser, Order.class);
        process(order);                   // one at a time
    }
}
```

Same reasoning as Day 063's `Files.lines` versus `readAllLines`, and Day 059's laziness. **Bind for
normal payloads; stream for anything unbounded.** And bound the request size regardless (Day 105).

## Serialization security summary

| Risk | Mitigation |
|---|---|
| Default typing → RCE | Never enable it; use explicit `@JsonSubTypes` with sealed types |
| Leaking internal fields | Separate response DTOs; never serialize entities (Day 105) |
| Unbounded payload | Server body-size limit + streaming |
| Deep nesting → stack overflow | `StreamReadConstraints` (max depth, max string length) |
| Duplicate keys | Enable `FAIL_ON_READING_DUP_TREE_KEY` — parsers differ, which enables smuggling |
| Secrets in `toString` | Records print every component (Day 073A) — override it |

```java
JsonFactory.builder().streamReadConstraints(
    StreamReadConstraints.builder().maxNestingDepth(50).maxStringLength(1_000_000).build());
```

That nesting limit matters: a deeply nested array (`[[[[[…]]]]]`) is a few kilobytes and can blow the
parser's stack. Jackson 2.15+ has defaults, but set them deliberately.

## Common mistakes

| Mistake | Consequence |
|---|---|
| `long` ids as JSON numbers | Silently mangled above 2^53 in JavaScript |
| `BigDecimal` as a JSON number | Precision lost through a client-side double |
| Epoch timestamps | Ambiguous units, no timezone information |
| Dates without an offset | Wrong by hours across clients |
| `LocalDateTime` in an API | Ambiguous by construction |
| Storing an offset for a future event | Wrong when the government changes the rules |
| Not distinguishing null from absent | `PATCH` erases fields silently |
| `FAIL_ON_UNKNOWN_PROPERTIES` on requests | Every client change needs a coordinated deploy |
| Default typing in Jackson | RCE — the Day 063A vulnerability in JSON |
| `ObjectMapper` per request | Real, measurable performance loss |
| Serializing entities | Leaks columns added later |
| Binding an unbounded payload | `OutOfMemoryError` |
| Assuming two decimal places for currency | Wrong for JPY, KWD and others |

## Interview questions

**Q: Why send an id as a string?**
JSON numbers are parsed as doubles in JavaScript, so any integer above 2^53 loses precision silently.
Twitter added `id_str` for exactly this. Strings also let you change the id format later without a
breaking change.

**Q: How do you represent money in an API?**
As a string amount with an explicit currency code, or as integer minor units. Never a JSON number,
because the client parses it into a double. And do not assume two decimal places — JPY has zero.

**Q: What date format do you use and why?**
ISO 8601 with an explicit offset, stored and transmitted in UTC. Epoch numbers are ambiguous about
units, and a datetime without an offset is ambiguous about location. For future events, store the
zone id rather than an offset.

**Q: `null` versus absent in a `PATCH`?**
They mean different things — clear the field versus leave it alone — and most deserializers collapse
them. Either model the tri-state explicitly, or adopt merge-patch semantics where null means delete,
and document it.

**Q: Why is Jackson's default typing dangerous?**
It puts a class name in the payload and instantiates it, reproducing Java deserialization's
gadget-chain RCE in JSON. Use explicit `@JsonSubTypes` with a sealed hierarchy — an allow-list.

**Q: How do you serialize a very large response?**
Stream it — NDJSON, or Jackson's streaming API — so memory stays constant on both sides instead of
building the whole graph.

**Q: Should you fail on unknown properties in a request?**
Usually not — tolerating them lets clients evolve independently. The trade-off is that a misspelled
field is silently ignored, so document the choice.

## 🎙️ Articulation drill

Two minutes: **"What are the pitfalls of JSON APIs?"**

Four data types that corrupt silently — big integers, decimals, dates, and null-versus-absent — with
the fix for each. Then the two that are security rather than correctness: default typing as RCE, and
serializing entities as data leakage. Close on streaming for unbounded payloads. The word *silently*
is what makes this list matter; a value that fails loudly is not a problem.
