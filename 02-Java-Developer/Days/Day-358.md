# Day 358

**L-358** · Design 14 — autocomplete

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Autocomplete fires on every keystroke, so it receives roughly ten times the traffic of the
> search it feeds — at a fraction of the latency budget.**
>
> That single ratio rules out doing any work at query time. **The answer is that all the work happens
> offline, and the query is a lookup of a precomputed answer.**

---

# Part 1 — ⭐ Requirements and the ratio

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| Suggestions for a prefix, ranked by popularity | ⭐⭐ **p99 < 100 ms end to end, including the network** |
| ⭐ Top 5–10 results | ⭐ **stale by hours is fine** — except for trending |
| Handle typos (optional) | ⭐⭐ **10× the QPS of search itself** |
| ⭐ Filter profanity and manipulated queries | availability: **degrade to no suggestions, never error** |
| Personalisation (optional) | |

```
⭐ ESTIMATE
⭐   10M searches/day ⇒ ~120 searches/s
⭐   ⭐⭐ 20 characters typed per search, debounced to ~4 requests
⭐   ⇒ ⭐⭐ ~500 autocomplete queries/s for 120 searches — ⭐ peak ~1,500/s
⭐   Corpus: top 100M distinct queries · ⭐ top 10 results each, precomputed
```

> **⭐ The conclusion to state immediately: at 100 ms and 10× the volume, there is no budget for a
> search.** So the design is **precompute everything offline, serve from memory, and make the query
> path a hash lookup.**

---

# Part 2 — ⭐⭐ The deep dive: the trie with precomputed top-K

```
⭐ NAIVE TRIE: walk to the prefix node, then traverse the whole subtree, collect, sort, take 10.
⭐   ⇒ ⭐⭐ prefix "a" has millions of descendants. UNBOUNDED work at query time.

⭐⭐ TRIE WITH TOP-K STORED AT EACH NODE:
⭐   Each node caches ⭐ the top 10 completions of its own prefix, precomputed offline.
⭐   ⇒ ⭐⭐ query = walk k characters, read a list. O(prefix length). No traversal at all.
```

| ⭐ Property | |
|---|---|
| ⭐⭐ **Query cost independent of subtree size** | ⭐⭐ **"a" costs the same as "antidisestablish"** |
| ⭐ Memory cost rises | ⭐ 10 entries at **every** node — but nodes store references, not strings |
| ⭐ **Updates are expensive** | ⭐⭐ a new popular query must update top-K at every ancestor node — **which is why builds are offline** |
| ⭐ Compression | ⭐ an FST or DAWG merges shared suffixes — **often 5–10× smaller than a plain trie** |

> **⭐ The idea in one line: move the work from query time to build time, because you serve a billion
> queries and build once an hour.** That asymmetry is the entire justification, and it is a general
> pattern worth naming.

## ⭐ The offline pipeline

```
⭐ query logs ──► aggregate counts (last N days, time-decayed)
⭐            ──► ⭐ filter: profanity, PII, adult, manipulated, rare (< threshold)
⭐            ──► ⭐ build trie/FST with top-K at each node
⭐            ──► ⭐ SHARD and distribute to serving nodes (an atomic swap, like Day 337's alias)
```

| ⭐ Detail | |
|---|---|
| ⭐ **Time-decayed counts** | ⭐ last week weighs more than last year — otherwise nothing ever changes |
| ⭐ **Threshold on frequency** | ⭐⭐ a query seen twice must not appear — **it may be someone's private search** |
| ⭐ Build cadence | ⭐ hourly is typical; **the whole structure is rebuilt, not mutated** |
| ⭐ **Atomic swap** | ⭐ build the new index, load it, switch a pointer — **rollback is switching back** |

⚠️ **The privacy threshold is a genuine requirement, not a nicety.** Suggesting a query that only one
person has ever typed **leaks that person's search** — and this has caused real incidents. **A
minimum frequency, plus filtering anything resembling personal data, is mandatory.**

# Part 3 — ⭐ Serving, sharding, and trending

## ⭐ Sharding by prefix

| ⭐ Approach | ⭐ Trade |
|---|---|
| ⭐ **By first character** | ⭐ simple — **26 shards, wildly uneven ("s" ≫ "z")** |
| ⭐⭐ **By first 2–3 characters, with rebalancing** | ⭐⭐ **finer buckets, assigned to balance measured load** |
| Replicate everything | ⭐ **viable if the compressed index fits in memory — often it does** |

> **⭐ Say the simplest answer first: if the FST fits in a few gigabytes, replicate it to every node
> and shard nothing.** Every node answers every prefix, scaling is adding replicas, and there is no
> routing tier. **Reaching for sharding when replication fits is over-engineering** — and this is one
> of the few designs where the whole dataset genuinely fits.

## ⭐⭐ Trending — the hot layer

```
⭐ PROBLEM: an hourly build cannot surface a query that became popular ten minutes ago.
⭐⭐ FIX: a small, fast-updating HOT LAYER merged at query time.
⭐   main index (hourly, 100M queries) ⊕ hot layer (streaming counts, last 15 min, ~thousands)
⭐   ⇒ ⭐ merge two small top-K lists — a handful of comparisons, negligible cost
```

**⭐ This two-tier structure — a large slow index plus a small fast one, merged at read time — is the
same shape as [Day 348](Day-348.md)'s memtable-plus-SSTables** and worth naming as such. **A general
technique, not a trick.**

## ⭐ The client is part of the design

| ⭐ Client behaviour | ⭐ Effect |
|---|---|
| ⭐⭐ **Debounce ~150 ms** | ⭐⭐ **20 keystrokes become ~4 requests — an 80% reduction, for free** |
| ⭐ **Cancel in-flight requests** | ⭐ stops out-of-order responses overwriting newer ones |
| ⭐ Cache locally per prefix | ⭐ **backspacing costs nothing** |
| ⭐ **Prefetch on prefix** | results for "lond" often contain those for "londo" |
| Fail silently | ⭐ **no suggestions is fine; an error toast is not** |

> **⭐ Debouncing is the cheapest optimisation in this design and it lives entirely in the client.**
> Mentioning it shows you are designing the *system*, not just the server.

# Part 4 — ⭐ Typos, personalisation, and what breaks

| Feature | ⭐ Approach and its cost |
|---|---|
| ⭐ **Fuzzy matching** | ⭐ edit distance ≤ 1–2 — **expensive in a trie; restrict to short prefixes or run a separate correction pass** |
| ⭐ Personalisation | ⭐ **blend a small per-user history layer with the global top-K** — a third merge, same shape as trending |
| Multi-language | one index per locale; **route by locale** |
| Result diversity | avoid ten near-identical suggestions |
| ⭐ **Manipulation defence** | ⭐ someone typing a query a million times must not shape suggestions — **cap per-user contribution** |

⚠️ **Fuzzy matching is where autocomplete designs get expensive**, because edit-distance search over a
trie explodes combinatorially. **The honest answer is to restrict it — apply correction only when the
exact prefix returns too few results, and only for prefixes over ~4 characters.**

| ⭐ Breaks first | ⭐ Mitigation |
|---|---|
| ⭐ Memory per node | ⭐ FST compression; store references not strings |
| ⭐ **Short-prefix load** ("a", "s") | ⭐ these are the hottest keys — **cache aggressively; they never change between builds** |
| Build time as the corpus grows | incremental aggregation; the build is embarrassingly parallel |
| ⭐ **Index distribution** | a multi-gigabyte artefact to every node — stagger the rollout |
| Cold start after a deploy | ⭐ **load the index before accepting traffic** — a readiness gate (Day 325) |

```
⭐ MONITOR: ⭐ p99 latency · ⭐⭐ suggestion click-through rate (the quality metric)
⭐          ⭐ zero-suggestion rate (Day 337's most actionable signal) · index age · build duration
⭐ CUT:     fuzzy matching, personalisation, multi-language, entity-aware suggestions
⭐ AT 10×:  ⭐ add replicas — ⭐ the index is read-only, so this scales linearly
```

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ Traversing the subtree at query time | ⭐⭐ **prefix "a" has millions of descendants** |
| ⭐ Computing rankings at query time | ⭐ there is no budget — precompute |
| ⭐ Updating the trie in place on every query | ⭐ **updates touch every ancestor; rebuild instead** |
| ⭐ **No frequency threshold** | ⭐⭐ **you suggest one person's private search** |
| No time decay | last year's queries never fade |
| ⭐ Sharding by first character | ⭐ "s" and "z" differ by orders of magnitude |
| ⭐ **Sharding when the index fits in memory** | ⭐ over-engineering; replicate instead |
| ⭐ No hot layer | trending queries take an hour to appear |
| ⭐ **No client debounce** | ⭐ 5× the traffic, for nothing |
| Not cancelling in-flight requests | an older response overwrites a newer one |
| ⭐ Unrestricted fuzzy matching | combinatorial explosion |
| ⭐ Erroring on failure | ⭐ **no suggestions is an acceptable degradation; an error is not** |
| Serving before the index is loaded | a cold node returns nothing |

## Interview questions

**Q: What is the defining constraint?**
Volume against latency. Autocomplete fires on every keystroke, so it takes roughly ten times the
traffic of the search it feeds, with a budget of about a hundred milliseconds including the network.
There is no room to run a search, rank results or compute anything — so every answer is precomputed
offline and the query path is a lookup.

**Q: What is the data structure?**
A trie, but the important part is that each node stores the precomputed top-K completions for its own
prefix. A naive trie walks to the node and then traverses the subtree, which for the prefix "a" is
millions of descendants — unbounded work at query time. With top-K cached at each node the query is
O(prefix length) and costs the same for "a" as for a long word. In production it is compressed as an
FST, which merges shared suffixes and is typically several times smaller.

**Q: How do updates work?**
They do not, at query time. A new popular query would have to update the top-K list at every ancestor
node, so instead the whole index is rebuilt offline — typically hourly — from time-decayed query log
counts, filtered for profanity, personal data and low-frequency entries, then distributed and swapped
in atomically. You serve a billion queries and build once an hour, and that asymmetry is what
justifies the design.

**Q: What about queries that just became popular?**
A small hot layer with streaming counts over the last fifteen minutes, merged with the main index at
query time. Both are tiny top-K lists so the merge is a handful of comparisons. It is the same shape
as an LSM tree — a large slow structure plus a small fast one combined at read time — which is a
general technique worth recognising.

**Q: How do you shard it?**
Probably not at all. A compressed FST of the top hundred million queries often fits in a few
gigabytes, so I replicate it to every node: every node answers every prefix, scaling is adding
replicas, and there is no routing tier. If it did not fit, I would shard by the first two or three
characters with buckets assigned to balance measured load, because sharding by first character alone
is wildly uneven.

**Q: Anything in the client?**
The cheapest win in the whole design. A hundred-and-fifty-millisecond debounce turns twenty
keystrokes into about four requests, which is an eighty percent traffic reduction for a few lines of
JavaScript. Plus cancelling in-flight requests so a slow older response cannot overwrite a newer one,
caching per prefix so backspacing is free, and failing silently — no suggestions is an acceptable
degradation, an error message is not.

1. **Run the 45-minute framework**, timed, with **the data structure as the deep dive.**
2. ⭐ Build a **naive trie** over 1M queries and measure query time for prefixes "a" and
   "antidisestablish". **Then add precomputed top-K at each node and re-measure both.**
3. ⭐ Measure memory for a plain trie versus an **FST** over the same corpus.
4. Build the **offline pipeline** with time-decayed counts. **Compare suggestions with and without

   privacy bug** — then reinstate it.
6. ⭐ Implement the **hot layer** and merge at query time. Make a query trend and **measure how long
   it takes to surface**, with and without it.
7. ⭐ Implement an **atomic index swap.** Deploy a new build under load and **assert zero failed
   queries**, then roll back.
8. ⭐ Add a **client debounce** and measure the request-rate reduction. Then remove cancellation and
   **reproduce an out-of-order overwrite.**
9. ⭐ Add fuzzy matching **unrestricted** and measure latency. Restrict it to prefixes over four
   characters with too few exact results, and re-measure.
10. Instrument **click-through rate and zero-suggestion rate**; change one ranking input and see
    both move.

## 🎙️ Articulation drill

**Two minutes:** *"A user types 'lo'. What happens in the next fifty milliseconds?"*

**⭐ The trace: the client has debounced and cancelled the previous request · the request reaches a
node holding the whole index in memory · walk two characters · read the precomputed top-10 stored at
that node · merge with the small hot layer · return.** **No search, no ranking, no traversal.**

**⭐ Then the sentence that frames it: "all the work happened an hour ago, offline, because we serve a
billion of these and build once."** Recognising that a workload with an extreme read-to-write ratio
should move all computation to build time is a transferable insight — and it is why this design looks
so different from every other one in the stage.
