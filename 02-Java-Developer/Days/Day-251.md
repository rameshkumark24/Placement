# Day 251 🏗️

**P-251** · The API contract — OpenAPI before any controller

**Time:** 3 hrs · **Mode:** BUILD

> Day 110 argued contract-first and Day 153 admitted the honest tension: springdoc generates from
> code, which is code-first. **Today you resolve it the way that gives you both** — write the
> specification by hand now, generate from code later, and diff them in CI.
>
> **⭐ Writing the contract before the controller forces you to design the API rather than let it
> emerge from your entities**, which is how APIs end up exposing exactly the shape of the database
> that Day 147 spent a day arguing against.

---

# Part 1 — ⭐ Resource design, from Day 103

**⭐ Start from the requirements, not the schema.** The API is a contract with a client, not a view of
your tables.

```
⭐ /api/v1/rooms                       GET   list        POST create
⭐ /api/v1/rooms/{roomId}              GET   PUT   DELETE
⭐ /api/v1/rooms/{roomId}/availability GET   ⭐ a sub-resource, not a verb
⭐ /api/v1/bookings                    GET   POST
⭐ /api/v1/bookings/{bookingId}        GET   DELETE
⭐ /api/v1/bookings/{bookingId}/status PUT   ⭐ state transition as a sub-resource
⭐ /api/v1/me/bookings                 GET   ⭐⭐ identity from the token — Day 174
```

**⭐ Three design decisions in that list worth defending:**

| Decision | Reason |
|---|---|
| ⭐ `/bookings/{id}/status` rather than `/bookings/{id}/cancel` | ⭐ Day 103 — a state transition is a sub-resource, not a verb in the path |
| ⭐ `/me/bookings` rather than `/users/{id}/bookings` | ⭐ **Day 174 — the identity comes from the token, so IDOR is structurally impossible** |
| ⭐ Versioned path from day one | Day 153 — visible in logs, routable at the gateway |

**⭐ The `/me/` pattern is the strongest security decision you can make at contract time**, and it
costs nothing: there is no id to forge, so there is no ownership check to forget.

## ⭐ Status codes, decided now

**Day 149's table, applied to your acceptance criteria** — and Day 249 already forced most of these
decisions:

| Situation | Code |
|---|---|
| Booking created | ⭐ **201 + `Location`** |
| Cancelled | ⭐ **204**, and 204 again on repeat (idempotent) |
| Not authenticated | 401 |
| Authenticated, not permitted | 403 |
| ⭐ **Someone else's booking** | ⭐ **404, not 403** — Day 119's existence oracle |
| Malformed body | 400 |
| ⭐ **Valid but violates a business rule** (too late to cancel) | ⭐ **422** |
| ⭐ **Overlapping booking** | ⭐ **409** |
| `If-Match` failed | 412 |
| Rate limited | 429 + `Retry-After` |

**⭐ Write the 400-versus-422 rule into the spec's description and apply it everywhere.** Day 149:
either convention is defensible; inconsistency is not.

# Part 2 — ⭐ Write the OpenAPI document by hand

```
docs/openapi.yaml        ⭐ hand-written, committed, reviewed
```

**⭐ For every endpoint, specify all five:**

| | |
|---|---|
| ⭐ 1 | Request schema — ⭐ **only fields a client may send** (Day 147) |
| ⭐ 2 | Response schema — ⭐ **only fields a client may see** |
| ⭐ 3 | ⭐ **Every error response**, with `ProblemDetail` and a stable `type` URI |
| ⭐ 4 | Constraints — `minimum`, `maxLength`, `format` (Day 148 gives these free later) |
| ⭐ 5 | ⭐ **Examples** — the thing that makes a spec usable by a human |

**⭐ Point 3 is what separates a real contract from a generated one.** Day 153: the default generated
spec documents only the happy path, and the error shapes are exactly what clients get wrong.

```yaml
# ⭐ Define the problem types once, reference them everywhere
components:
  schemas:
    Problem:
      type: object
      properties:
        type:   { type: string, format: uri, example: "https://api.acme.com/problems/booking-overlap" }
        title:  { type: string, example: "Room already booked" }
        status: { type: integer, example: 409 }
        detail: { type: string }
        instance: { type: string }
```

## ⭐ The error catalogue — a separate, permanent document

```markdown
# docs/ERRORS.md
| type URI                | Status | When                                    | ⭐ Client should |
|-------------------------|--------|-----------------------------------------|------------------|
| /problems/booking-overlap | 409  | the slot is taken                        | ⭐ offer alternative times |
| /problems/too-late-to-cancel | 422 | within 2 hours of start              | ⭐ show the policy |
| /problems/validation-error | 400  | malformed request                       | fix the request |
| /problems/rate-limited   | 429    | too many requests                        | ⭐ honour Retry-After |
```

**⭐ The `type` URI is a contract**, so changing one is a breaking change (Day 153). Deciding them now
and writing them down means you will not invent a fifth error format at 11pm in week three.

**⭐ And the "client should" column is the point of RFC 7807.** An error the client can *act* on is
worth far more than one it can only display.

# Part 3 — ⭐ The cross-cutting contract decisions

**⭐ Decide these once, apply everywhere, and write them into the spec's description.**

| Decision | Choice | Day |
|---|---|---|
| ⭐ **Pagination** | ⭐ keyset with an opaque cursor for feeds; `Slice` not `Page` (no count query) | 107, 152 |
| ⭐ **Sorting** | ⭐ an **allow-list**, with a unique tie-break column always appended | 108, 152 |
| ⭐ **Filtering** | named parameters, allow-listed — never a query language | 108 |
| ⭐ **Timestamps** | ⭐ ISO-8601 UTC, `Instant` — never `LocalDateTime` | 106, 150 |
| ⭐ **Money** | ⭐ `numeric`, serialised as a string, with an explicit currency | 106, 150 |
| ⭐ **IDs** | ⭐ `public_id` UUID in every response — never the internal id | 158 |
| ⭐ **Nulls** | omit on responses; ⭐ **decide PATCH semantics explicitly** | 150 |
| ⭐ **Idempotency** | ⭐ an `Idempotency-Key` header on POST | 123 |
| ⭐ **Concurrency** | ⭐ `ETag` on GET, `If-Match` **required** on PUT | 102, 150, 165 |
| ⭐ **Correlation** | `X-Correlation-Id` accepted and echoed | 127, 151 |

**⭐ The `If-Match` decision is the one that most demonstrates seniority**, and it is worth stating in
the spec explicitly: *"PUT requires `If-Match`; requests without it are rejected with 428."*
**That turns last-write-wins into a client error rather than silent data loss** (Day 165).

**⭐ And the `Idempotency-Key` decision** means a client that times out and retries a booking creation
does not create two bookings — Day 123's argument, and it is directly relevant because your domain
has a concurrency problem.

# Part 4 — ⭐ Validate the contract before building against it

### ⭐ 1. Lint it

```bash
npx @stoplight/spectral-cli lint docs/openapi.yaml     # ⭐ catches inconsistencies you cannot see
```

### ⭐ 2. Mock it and use it

```bash
npx @stoplight/prism-cli mock docs/openapi.yaml        # ⭐ a running API from the spec alone
```

**⭐ Then write the client calls you expect the frontend to make, against the mock.** This is the
highest-value hour of the day: **you will find missing fields, awkward shapes and endpoints that
require three calls where one would do — before any of it is expensive.**

### ⭐ 3. Generate a client and read it

```bash
openapi-generator-cli generate -i docs/openapi.yaml -g java --library resttemplate
```

**⭐ Day 153's argument: a bad spec generates an awful client.** If the generated method is called
`getUsingGET1`, your operation IDs and descriptions are missing. **The generated client is a
readability test for your contract.**

### ⭐ 4. Commit it and plan the CI diff

**⭐ From Day 253 onward, springdoc will generate a spec from your code. The plan is:**

```
⭐ CI regenerates the spec → diffs it against docs/openapi.yaml
⭐ A difference fails the build unless the committed file changed in the same commit
⭐ oasdiff classifies the change as breaking or non-breaking
```

**⭐ That is Day 153's resolution of the contract-first tension**, and it gives you the property that
matters: **a breaking change appears as a red diff at review time rather than as a client outage.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Designing the API from the entities | ⭐ you have published your schema (Day 147) |
| ⭐ Verbs in paths | Day 103 |
| ⭐ `/users/{id}/bookings` instead of `/me/bookings` | an ownership check you can forget |
| Documenting only the happy path | clients get the errors wrong |
| ⭐ Unstable `type` URIs | breaking change (Day 153) |
| Inconsistent 400/422 | client cannot tell "fix your code" from "tell the user" |
| ⭐ 403 for another user's resource | existence oracle |
| Offset pagination on a public API | someone will iterate to page 50,000 |
| ⭐ No `If-Match` on PUT | silent lost updates |
| ⭐ No `Idempotency-Key` on POST | a timeout creates two bookings |
| `LocalDateTime` on the wire | Day 106 |
| Internal ids in responses | Day 119 |
| ⭐ Not exercising the spec via a mock | you find the problems after implementing |

## 🎤 Defence questions

1. **⭐ Why `/me/bookings` rather than `/users/{id}/bookings`?**
2. **What is the difference between a 400 and a 422 in your API?**
3. **⭐ Why 404 rather than 403 for someone else's booking?**
4. **⭐ How does a client avoid overwriting another client's change?**
5. **⭐ What happens if a client's request times out and it retries a booking creation?**
6. **How would you add a field without breaking existing clients — and remove one?**
7. **⭐ How do you know your implementation still matches this contract?**

## ✅ Done when

- `docs/openapi.yaml` is committed and lints clean
- You have exercised it against a mock and **revised it as a result**
- `ERRORS.md` and ADR-0003 are committed
- ⭐ **Still no application code**
