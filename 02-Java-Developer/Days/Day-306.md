# Day 306 ⭐

**L-306** · ⭐ The modular monolith — the architecture you should default to

**Time:** 3 hrs · **Mode:** NEW

> **⭐ The default answer to "monolith or microservices?" is neither. It is a monolith with real
> internal boundaries — one deployable, many modules, each with an enforced public API.**
>
> This is the most useful architectural position you can hold in an interview in 2026, because it is
> **defensible, unfashionable enough to require reasons, and correct for almost every system you will
> be asked to design.**

---

# Part 1 — ⭐⭐ Why this is the default

**⭐ The honest framing: microservices solve an organisational problem, and you pay for them in
distributed-systems problems.** If you do not have the organisational problem, you have bought the
bill without the goods.

| | ⭐ Modular monolith | Microservices |
|---|---|---|
| ⭐ **Transactions across modules** | ⭐ **one ACID transaction** | ⭐ Saga, compensations, partial failure |
| ⭐ **A call between modules** | ⭐ **a method call — ns, cannot fail** | ⭐ network — ms, times out, retries, duplicates |
| ⭐ **Refactoring a boundary** | ⭐ **an IDE rename** | ⭐ coordinated deploys, versioned APIs |
| Debugging a request | ⭐ one stack trace | distributed tracing, seven services |
| ⭐ **Local development** | ⭐ **run it** | docker-compose, or stubs, or hope |
| Deploy independence | ⭐ none — one artefact | ⭐ real |
| Scale independence | ⭐ none — scale the whole thing | ⭐ real |
| Failure isolation | ⭐ weak — a leak kills everything | ⭐ real |
| Team independence | ⭐ requires discipline | ⭐ enforced by the network |
| ⭐ **Operational cost** | ⭐ **one pipeline, one dashboard** | ⭐ ×N, plus a platform team |

**⭐ The four legitimate reasons to split a service out — and you need at least one:**

1. ⭐ **A team boundary that is causing real deploy contention.** (Conway's law: the architecture will
   match the org chart whether you plan it or not.)
2. ⭐ **A genuinely different scaling profile** — one module needs 40 instances and the rest need 3.
3. ⭐ **Failure isolation that actually matters** — the report generator must not take down checkout.
4. ⭐ **A different technology is genuinely required** — a Python ML service, a Go proxy.

> **⭐ "It's more scalable" and "it's modern" are not on the list**, and the honest counter is that a
> single Boot instance handles several thousand requests per second and scales horizontally behind a
> load balancer just fine. **The wall you hit first is almost always the database (Stage 5), and
> splitting services does not move that wall.**

**⭐ And the killer argument, worth memorising:** *you cannot draw the right service boundaries before
you understand the domain, and you understand the domain about a year in.* **Modules can be redrawn
with a rename; services cannot.** So build modules first, and extract when a reason from the list
above shows up — **which is exactly the path that produced the successful microservice migrations,
and the reverse path is where the horror stories come from.**

# Part 2 — ⭐ What makes a module a module

> **⭐ A module = a bounded context (Day 305) + an enforced public API + private internals + its own
> data.** All four. Three out of four is a package.

```
com.app
├── orders/                       ⭐ MODULE
│   ├── OrderApi.java             ⭐ ← PUBLIC. The only type others may reference.
│   ├── OrderPlaced.java          ⭐ ← PUBLIC event
│   ├── OrderSummary.java         ⭐ ← PUBLIC read model (a record, not an entity)
│   └── internal/                 ⭐ ← everything else, package-private where possible
│       ├── Order.java                aggregate (Day 305)
│       ├── PlaceOrderService.java
│       └── JpaOrders.java
├── billing/
│   ├── BillingApi.java
│   └── internal/...
└── shipping/
    └── ...
```

| ⭐ Rule | ⭐ Enforcement |
|---|---|
| ⭐ **Only `*Api` types are referenced across modules** | ArchUnit / Spring Modulith |
| ⭐ **No module touches another's tables** | ⭐ **schema per module; DB user has no rights on the others** |
| ⭐ **No entity crosses a module boundary** | pass ids and records |
| ⭐ **No cycles between modules** | ⭐ ArchUnit slices rule — the highest-value one |
| ⭐ Each module owns its transactions | Day 302's boundary, per module |

## ⭐ The four ways to enforce it, ranked by strength

| Mechanism | Strength | ⭐ Cost |
|---|---|---|
| ⭐ **Package-private + an `internal` package** | ⭐ moderate — free, immediate | ⭐ needs package-by-feature (Day 299) |
| ⭐ **ArchUnit tests** | ⭐ **strong — and readable as documentation** | a test class |
| ⭐ **Spring Modulith** | strong, plus generated docs and module tests | a dependency |
| ⭐ **Maven/Gradle multi-module** (Day 073) | ⭐⭐ **strongest — the compiler cannot see it** | ⭐ slower builds, real friction |
| Java Platform Module System | strongest in theory | ⭐ rarely worth the pain in Spring apps |

```java
@ArchTest
static final ArchRule modules_expose_only_their_api =
    classes().that().resideInAPackage("..orders.internal..")
        .should().onlyBeAccessed().byClassesThat().resideInAPackage("..orders..");

@ArchTest
static final ArchRule no_module_cycles =
    slices().matching("com.app.(*)..").should().beFreeOfCycles();
```

**⭐ Start with ArchUnit.** Multi-module Gradle is stronger but slows every build and makes early
boundary changes painful — **and early boundary changes are the entire benefit of not being
microservices.**

# Part 3 — ⭐⭐ How modules talk

**⭐ Two mechanisms, and choosing wrongly is the main way a modular monolith degrades into a
distributed monolith with no network.**

| | ⭐ Direct call (`BillingApi`) | ⭐ Event (`OrderPlaced`) |
|---|---|---|
| Coupling | ⭐ caller knows the callee | ⭐ **caller knows nothing** |
| Consistency | ⭐ **same transaction — atomic** | ⭐ eventual |
| Failure | ⭐ **propagates — caller can react** | isolated, retried |
| ⭐ **Direction** | ⭐ creates a dependency arrow | ⭐ **creates none** |
| Debugging | ⭐ one stack trace | ⭐ harder — the flow is implicit |

> **⭐ The rule: call when you need the answer or the atomicity. Publish when you are informing.**

```java
// ⭐ CALL — you need the result, and it must be atomic with your own change
CreditCheck result = billingApi.checkCredit(customerId, total);
if (result.declined()) throw new CreditDeclined();

// ⭐ PUBLISH — you are informing. Shipping and analytics are not your business.
events.publish(new OrderPlaced(orderId, customerId, total, at));
```

⚠️ **The most common failure: everything becomes an event, "for decoupling".** Now no dependency is
visible, the flow cannot be read from any single file, ordering bugs appear, and **you have all the
debugging cost of microservices with none of the deployment benefit.** Events for *notification*;
calls for *collaboration*.

⚠️ **The second failure: a cycle through events.** `orders` publishes, `billing` handles and
publishes, `orders` handles that. **ArchUnit cannot see this** — the classes do not reference each
other. **Draw the event flow separately and check it for cycles by hand**, or use Spring Modulith's
generated documentation.

## ⭐ One database, many schemas — the seam that makes extraction possible

```sql
CREATE SCHEMA orders;   CREATE SCHEMA billing;   CREATE SCHEMA shipping;

-- ⭐ The enforcement that actually works:
GRANT USAGE ON SCHEMA orders TO app_orders;
REVOKE ALL ON SCHEMA billing FROM app_orders;   -- ⭐ the database says no
```

| Rule | ⭐ Why |
|---|---|
| ⭐ **One schema per module** | ⭐ the extraction seam |
| ⭐ **No cross-schema queries** | ⭐ **the single rule that decides whether extraction is a week or a year** |
| ⭐ **No cross-schema foreign keys** | ⭐ an FK is a permanent join between two modules' lifecycles |
| ⭐ Cross-module data via the API | slower, and correct |
| ⭐ Read models duplicated deliberately | Day 305: duplication across contexts is right |

**⭐ The genuine loss, and name it before an interviewer does: you give up joins.** "Orders with
customer names" becomes two queries and an in-memory join, or a denormalised read model kept up to
date by events. **That is a real cost you are paying now to keep an option open later** — and if you
are certain you will never extract, taking the join is a legitimate decision. Write it down either
way.

⚠️ **A single shared connection pool means one module's slow queries starve the others** (Day 156).
Failure isolation is the thing a monolith genuinely does not give you. **Say so.**

# Part 4 — ⭐ Extraction, when the day comes

**⭐ If the modules are clean, this is a two-week job rather than a two-year programme:**

```
⭐ 1. Confirm the reason        — team, scaling, isolation, or technology. Written down.
⭐ 2. Verify the seam           — zero cross-schema access; all traffic through the Api type
⭐ 3. Make the API remote-shaped — coarse-grained, no chatty loops (an N+1 over the network)
⭐ 4. Replace the in-process Api with an HTTP/gRPC client — SAME INTERFACE
⭐ 5. Handle what is now possible — timeouts, retries, idempotency, breakers (Day 154, Day 181)
⭐ 6. Move the schema           — with the module's own migrations (Day 166)
⭐ 7. Replace transactions with a saga where the boundary is now crossed
```

**⭐ Step 5 is where the real work is, and step 3 is where designs fail.** An interface that was fine
in-process — `getCustomer()` called in a loop over 500 orders — becomes 500 network calls. **Design
module APIs coarse-grained from the start and this problem never exists.**

> **⭐ The strongest version of this argument in an interview: "I would start as a modular monolith
> with schema-per-module, because that keeps extraction a two-week job — and I would only extract
> when I have one of four specific reasons, none of which is scale."** That answer demonstrates you
> have thought about the trade rather than picked a side.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Microservices before the org needs them | ⭐ distributed-systems cost, none of the benefit |
| ⭐ Splitting on anything but bounded contexts | ⭐ distributed transactions and chatty calls |
| ⭐ Modules with no enforcement | ⭐ **it is a monolith with hopeful package names** |
| ⭐ Cross-schema queries "just this once" | ⭐ **the extraction seam is gone silently** |
| Cross-schema foreign keys | two modules' lifecycles welded |
| ⭐ Events for everything | ⭐ **the distributed monolith's debugging cost, in one process** |
| ⭐ Cycles through event handlers | ⭐ invisible to ArchUnit |
| Entities crossing module boundaries | the internal model is now public API |
| ⭐ Fine-grained module APIs | ⭐ an N+1 waiting for the day you extract |
| Multi-module Gradle on day one | slow builds, and boundaries you cannot yet redraw |
| ⭐ Claiming failure isolation | ⭐ one pool, one heap — say the truth |

## Interview questions

**Q: Monolith or microservices?**
Modular monolith, by default. Microservices solve an organisational problem — independent deploys,
independent scaling, failure isolation, team autonomy — and you pay for them in distributed
transactions, network failure modes, and an operational platform. If you do not have the
organisational problem you have bought the bill without the goods. And you cannot draw correct
service boundaries before you understand the domain, which takes about a year; modules can be redrawn
with a rename, services cannot.

**Q: What makes something a module rather than a package?**
An enforced public API, private internals, its own data, and a boundary that matches a bounded
context. Enforcement is the word that matters — ArchUnit rules for API-only access and no cycles,
package-private internals, and schema-per-module with database grants that make cross-module access
fail. Without enforcement it is a monolith with hopeful package names, and it lasts about two
sprints.

**Q: How should modules communicate?**
Direct calls through the other module's API type when I need the answer or need atomicity; events
when I am informing others of a fact. The failure mode is making everything an event for
"decoupling" — then no dependency is visible, the flow cannot be read from any file, and you have the
debugging cost of a distributed system inside one process. Events also create cycles that ArchUnit
cannot see, so I check the event flow separately.

**Q: Why schema per module, and what does it cost?**
It is the extraction seam. As long as no module queries another's schema and there are no
cross-schema foreign keys, pulling one out is a two-week job. The cost is real: I give up joins
across modules, so cross-module reads become two queries or a denormalised read model kept current by
events. That is a price paid now to keep an option open later, and if I were certain I would never
extract, taking the join would be a legitimate choice.

**Q: When would you extract a service?**
Four reasons: a team boundary causing deploy contention, a genuinely different scaling profile,
failure isolation that actually matters, or a technology requirement. Not scale in general — the wall
is usually the database, and splitting services does not move it. When one of those appears, I verify
the seam, make the API coarse-grained so it does not become an N+1 over the network, swap the
in-process implementation for an HTTP client behind the same interface, then add timeouts, retries,
idempotency and a saga where the transaction used to be.

## Mini task

1. **Draw your flagship's modules by bounded context.** Not by layer. **Name each module's public
   API — if it has more than five types, the boundary is wrong.**
2. Add the **cycle rule** and the **API-only rule** in ArchUnit. **Count the violations.**
3. Move each module's internals into an `internal` package and make everything you can
   package-private. **List what resisted** — that is your real API.
4. ⭐ **Split your database into schemas.** Create one DB user per module with grants only on its own
   schema. **Run the test suite and watch the cross-module access fail.**
5. Find one cross-module `@ManyToOne` and replace it with an id plus an API call. **Measure the cost.**
6. ⭐ **Draw the event flow separately from the call graph and look for a cycle.** Most systems with
   more than four handlers have one.
7. ⭐ **Pick your most extractable module and write the one-page extraction plan** — the seam check,
   the API changes, and every failure mode that becomes possible. **Do not extract it.**
8. Write an ADR (Day 101): *"Why this is a modular monolith and what would change my mind."*

# 🚪 Exit questions

1. Give six axes on which a modular monolith beats microservices, and four where it loses.
2. Give the four legitimate reasons to extract a service.
3. Why is "it's more scalable" not one of them?
4. Why can you not draw service boundaries early?
5. Give the four properties of a real module.
6. Rank four enforcement mechanisms and say which to start with.
7. Give the rule for calls vs events.
8. What goes wrong when everything is an event?
9. Why can ArchUnit not see event cycles?
10. Give the schema rules and the cost you accept.
11. Which failure isolation does a monolith genuinely lack?
12. Walk the seven extraction steps and say where designs fail.

## 🎙️ Articulation drill

**Three minutes:** *"Would you build this as microservices?"* — for any system you are asked to
design.

**⭐ The marker: you answer with a default and a trigger, not a preference.** "Modular monolith,
schema per module, extract when one of these four things is true" is an engineering position.
"Microservices, for scalability" is a fashion statement — **and the follow-up, "what would you split
on?", ends it.**

**⭐ Second marker: you name what a monolith genuinely does not give you** — failure isolation and
independent deploys — **before the interviewer does.** Defending a position by admitting its cost is
what makes the position credible.
