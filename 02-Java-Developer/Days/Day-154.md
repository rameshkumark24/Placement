# Day 154

**L-154** · Calling other services — `RestClient`, `WebClient`, and the timeout that isn't set

**Time:** 3 hrs · **Mode:** NEW

> Day 123 established retries, exponential backoff with full jitter, and idempotency keys. Day 128
> established that a dependency's latency becomes your latency. Today is the client side of that,
> and it opens with the single most common production failure in Java services:
>
> **`new RestTemplate()` has no timeouts. None. It will wait forever.** One slow dependency then
> consumes all 200 Tomcat threads (Day 145) and your service stops responding — to every endpoint,
> including the ones that do not touch that dependency at all. That is a **cascading failure**, and
> it is one missing configuration line.

# Part 1 — Which client, in 2026

| Client | Status | Use |
|---|---|---|
| `RestTemplate` | ⚠️ **maintenance mode** since Spring 5. Not deprecated, not receiving features | existing code only |
| **`RestClient`** | ⭐ Spring 6.1+ | **the default for new synchronous code.** `WebClient`'s fluent API, blocking semantics, no reactive dependency |
| `WebClient` | fully supported | reactive stacks, streaming, genuine parallel fan-out |
| **HTTP interface** (`@HttpExchange`) | Spring 6+ | ⭐ declarative, like Feign but built in. Excellent for a stable third-party contract |

**The interview answer:** `RestClient` for new synchronous code because it gives you the modern API
without dragging in a reactive stack you then have to reason about; `WebClient` when I am already
reactive or need to fan out concurrently; `RestTemplate` only in code that already uses it.

```java
@Configuration
class PaymentClientConfig {

    @Bean
    RestClient paymentRestClient(RestClient.Builder builder,
                                 PaymentGatewayProperties props,      // Day 142
                                 ObservationRegistry observations) {

        var factory = new HttpComponentsClientHttpRequestFactory(httpClient(props));

        return builder
            .baseUrl(props.url())
            .requestFactory(factory)
            .defaultHeader("User-Agent", "acme-orders/1.4")           // ⭐ they will thank you
            .requestInterceptor(correlationIdInterceptor())           // Day 127
            .defaultStatusHandler(HttpStatusCode::isError, (req, res) -> {
                throw new PaymentGatewayException(res.getStatusCode(), safeBody(res));
            })
            .observationRegistry(observations)                        // ⭐ metrics per call
            .build();
    }
}
```

**Inject `RestClient.Builder`, do not call `RestClient.create()`.** The auto-configured builder
already carries Boot's observation registry, message converters and any customisers other starters
registered — the same argument as Day 150's `ObjectMapper`.

# Part 2 — ⭐ Timeouts, and the four levels people forget

```java
private CloseableHttpClient httpClient(PaymentGatewayProperties props) {
    var connectionConfig = ConnectionConfig.custom()
            .setConnectTimeout(Timeout.ofSeconds(2))          // ⭐ 1. TCP + TLS handshake
            .setSocketTimeout(Timeout.ofSeconds(5))           // ⭐ 2. between bytes
            .build();

    var pool = PoolingHttpClientConnectionManagerBuilder.create()
            .setDefaultConnectionConfig(connectionConfig)
            .setMaxConnTotal(100)                             // ⭐ 4. pool size
            .setMaxConnPerRoute(50)                           // ⭐⭐ default is 5 (!)
            .build();

    var requestConfig = RequestConfig.custom()
            .setConnectionRequestTimeout(Timeout.ofSeconds(1))  // ⭐ 3. waiting for a pooled conn
            .setResponseTimeout(Timeout.ofSeconds(5))
            .build();

    return HttpClients.custom()
            .setConnectionManager(pool)
            .setDefaultRequestConfig(requestConfig)
            .evictIdleConnections(TimeValue.ofSeconds(30))
            .build();
}
```

| Timeout | Bounds | Typical | If unset |
|---|---|---|---|
| **Connect** | TCP + TLS handshake | 1–3 s | hangs until OS timeout — minutes |
| **Socket / response** | time between bytes | 3–10 s | ⭐ **waits forever** |
| **Connection request** | waiting for a free pooled connection | 0.5–2 s | queues invisibly behind a saturated pool |
| **Total request** | the whole call | ≤ your own SLA | slow calls stack |

**The third one is the one nobody sets and it is the one that hides the outage.** With
`maxConnPerRoute = 5` — Apache HttpClient's *default* — the sixth concurrent request to that host
waits for a connection. Your socket timeout never fires because no socket was ever opened. Your
metrics show the dependency responding in 50 ms while your endpoint takes 30 seconds, and everyone
looks at the wrong service for an hour.

**Set all four. Then set the pool size to match your actual concurrency**, which is a number you can
compute: peak RPS × p99 latency in seconds. 200 RPS at 100 ms needs ~20 connections, not 5.

## The budget rule

> **Your timeout must be shorter than your caller's timeout.**

If your API promises 2 seconds and you allow 5 seconds to the payment gateway, your caller gives up
while you are still waiting — you burn a thread on a request nobody will read, and the client retries
into a service already saturated with abandoned work.

```
client → 3s → your API → 2s → payment gateway → 1.5s → their DB
```

Each layer must leave room for its own processing and retries. **A retry inside a budget must fit
inside the budget**: two attempts at 2 seconds each does not fit a 3-second promise, so either the
per-attempt timeout drops or the retry does.

# Part 3 — Retries, from Day 123

```java
@Bean
RetryTemplate paymentRetry() {
    return RetryTemplate.builder()
        .maxAttempts(3)
        .exponentialBackoff(200, 2.0, 2000, true)   // ⭐ last arg = full jitter (Day 123)
        .retryOn(ResourceAccessException.class)      // ⭐ timeouts and connection failures
        .retryOn(HttpServerErrorException.ServiceUnavailable.class)
        .build();
}
```

**Day 123's rules, restated as client rules:**

| Rule | Detail |
|---|---|
| ⭐ **Retry only idempotent operations** | GET, PUT, DELETE freely. **POST only with an idempotency key** the server honours — otherwise a timeout on a successful charge, retried, charges twice |
| ⭐ **Jitter is mandatory** | without it, every instance retries at the same millisecond. That is a synchronised thundering herd against a service already struggling |
| **Retry 429/503/504 and timeouts. Never 4xx** | a 400 will be 400 forever; retrying it is pure load |
| **Honour `Retry-After`** | the server told you when to come back. Ignoring it is how a partial outage becomes total |
| **Cap total attempts and total time** | three attempts, and a total budget, or a retry storm outlives the incident |

## The circuit breaker, and why retries alone are dangerous

**Retries make an overloaded dependency worse.** If payments is failing because it is saturated,
three attempts per request means you are now sending three times the load into the thing that is
already on fire. A circuit breaker is what stops that:

```java
@CircuitBreaker(name = "payments", fallbackMethod = "paymentUnavailable")
@Retry(name = "payments")                                   // ⭐ resilience4j: retry INSIDE breaker
public PaymentResult charge(ChargeRequest req) { ... }

PaymentResult paymentUnavailable(ChargeRequest req, Throwable t) {
    log.warn("payments circuit open, degrading", t);
    return PaymentResult.deferred();                         // ⭐ queue it (Day 124's outbox)
}
```

After a failure threshold the breaker **opens** and calls fail immediately — no thread held, no load
added, and the dependency gets room to recover. After a wait it goes **half-open** and lets a probe
through.

The fallback is where the design happens: `PaymentResult.deferred()` writes to the outbox and returns
"pending" instead of failing the order. Day 124's argument — the customer's order succeeds, the
charge follows when payments recovers. **A fallback that just rethrows has bought you nothing but a
faster failure**, which is still worth something, but far less.

Day 181 covers Resilience4j properly.

# Part 4 — The four details that separate a working client from a good one

### 1. Propagate the correlation ID

```java
ClientHttpRequestInterceptor correlationIdInterceptor() {
    return (request, body, execution) -> {
        String cid = MDC.get("correlationId");                       // Day 151's filter put it there
        if (cid != null) request.getHeaders().add("X-Correlation-Id", cid);
        return execution.execute(request, body);
    };
}
```

**This is what makes distributed tracing work at all.** Without it, Day 127's correlation ID stops at
your service boundary and an incident spanning three services needs three separate log hunts. With
it, one ID follows the request through the whole call graph.

Micrometer Tracing does this automatically with W3C `traceparent` — use it if you have it; the manual
version is worth writing once so you know what it is doing.

### 2. Be a tolerant reader

```java
@Bean
RestClient partnerClient(RestClient.Builder builder) {
    var mapper = JsonMapper.builder()
        .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)   // ⭐ opposite of Day 150
        .build();
    return builder.messageConverters(c -> c.add(0, new MappingJackson2HttpMessageConverter(mapper)))
                  .build();
}
```

Day 150's rule with its second half: **strict on what you accept, tolerant of what you receive.**
A partner adding a field to their response is an additive change (Day 109) and must not break you.
This needs a *separate* mapper from the one serving your API.

### 3. Never log the response body blindly

```java
throw new PaymentGatewayException(status, safeBody(res));   // truncated, redacted
```

A payment gateway's error body can contain a PAN fragment, a customer's address, or an auth token.
Day 127's rule applies to responses you receive, not just requests you serve.

### 4. Test with a real HTTP server, not a mocked client

```java
@RestClientTest(PaymentClient.class)
class PaymentClientTest {
    @Autowired MockRestServiceServer server;
    @Autowired PaymentClient client;

    @Test void mapsGatewayErrorTo422() {
        server.expect(requestTo("/charges"))
              .andExpect(header("X-Correlation-Id", notNullValue()))   // ⭐ assert the plumbing
              .andRespond(withStatus(SERVICE_UNAVAILABLE));
        assertThatThrownBy(() -> client.charge(req)).isInstanceOf(PaymentGatewayException.class);
    }
}
```

Day 075's argument: **mocking `RestClient` itself tests nothing** — it asserts that you called a
method you wrote. `MockRestServiceServer` (or WireMock, which can also simulate delays and connection
resets) exercises real serialization, real headers, real status handling. Only a real server can
verify that your timeout actually fires.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ `new RestTemplate()` / `RestClient.create()` | **no timeouts** — one slow dependency exhausts every thread |
| No connection-request timeout | pool exhaustion is invisible; you blame the wrong service |
| `maxConnPerRoute` left at 5 | silent queueing at trivial concurrency |
| Timeout longer than the caller's | you work on requests nobody is waiting for |
| Retrying POST without an idempotency key | double charges (Day 123) |
| Retry without jitter | synchronised herd against a struggling service |
| Retry without a circuit breaker | you triple the load on the thing that is failing |
| Retrying 4xx | pure waste |
| Ignoring `Retry-After` | partial outage becomes total |
| Not propagating the correlation ID | tracing stops at your boundary |
| Strict JSON parsing on a partner's response | their additive change breaks you |
| Logging the raw response body | PII and tokens in your logs |
| Mocking the client in tests | tests the mock, not the integration |
| `block()` on a `WebClient` inside WebFlux | starves the event loop (Day 145) |

## Interview questions

**Q: What is the most common way a Java service falls over from a dependency?**
No timeouts on the HTTP client. `RestTemplate` and a bare `RestClient` default to unlimited, so a slow
dependency parks Tomcat threads until all 200 are gone, and then every endpoint fails — including the
ones that never call that dependency. It is a cascading failure caused by one missing config line.

**Q: Which timeouts do you set?**
Connect, socket/response, connection-request, and a total budget. The connection-request one is the
one people miss, and it hides pool exhaustion — the dependency looks fast while your endpoint is
slow, so everyone debugs the wrong service.

**Q: How do you retry safely?**
Only idempotent operations, or POST with an idempotency key the server honours. Exponential backoff
with full jitter, a capped attempt count and total budget, only on 429/503/504 and timeouts, honouring
`Retry-After` — and always behind a circuit breaker, because retries alone multiply load on a
dependency that is already failing.

**Q: `RestClient` or `WebClient`?**
`RestClient` for new synchronous code — same fluent API, no reactive stack to reason about.
`WebClient` when I am already reactive or genuinely fanning out concurrently.

## 🎙️ Articulation drill

Two minutes: **"How do you call another service safely?"**

Open with the failure: no timeouts means one slow dependency takes your entire service down, because
every Tomcat thread ends up parked on it. Then the four timeouts, sized inside your own SLA so you
never work on a request the caller has abandoned. Retries only where they are idempotent, with full
jitter, honouring `Retry-After`, behind a circuit breaker — because retries alone multiply load on a
failing dependency. Correlation ID propagated so tracing crosses the boundary. Close on the testing
point: you cannot verify a timeout against a mocked client, so the test needs a real HTTP server that
can be made slow.
