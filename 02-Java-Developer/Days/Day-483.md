# Part 1 — ⭐ Requirements and estimation (0–10)

| ⭐ Functional | ⭐ Non-functional |
|---|---|
| ⭐ 1:1 messaging | ⭐⭐ **delivery latency p99 < 200 ms** — this *is* the product |
| ⭐ group messaging | ⭐⭐ **messages must never be lost** — stronger than a feed |
| ⭐⭐ **online/offline presence** | ⭐⭐ **ordering must be consistent for both participants** |
| ⭐ delivery + read receipts | ⭐ offline users receive on reconnect |
| ⭐ message history | ⭐ Out of scope: E2E encryption, voice/video, media pipeline |

```
⭐ 50M DAU · ⭐ 40 messages/user/day ⇒ ⭐ 2B messages/day ≈ ⭐⭐ ~23,000 messages/sec (peak ~50k)
⭐ ⭐⭐ CONCURRENT CONNECTIONS: ~10M ⇒ ⭐⭐ at ~50k sockets per server ⇒ ⭐⭐ ~200 gateway servers
⭐ ⭐ storage: 2B × ~200 bytes ≈ 400 GB/day ⇒ ⭐ ~150 TB/year ⇒ partitioning required
⭐
⭐ ⭐⭐ WHAT THE NUMBERS DECIDED:
⭐   ⭐⭐ 10M persistent connections ⇒ ⭐⭐ the gateway tier is SEPARATE from business logic and scales differently
⭐   ⭐⭐ 200 servers ⇒ ⭐⭐ THE ROUTING PROBLEM: which of 200 boxes holds this recipient?
⭐   ⭐ 23k msg/sec ⇒ modest — ⭐ the connections, not the throughput, are the difficulty
```

# Part 2 — ⭐⭐ Connections and routing

| ⭐ Transport | ⭐ Verdict |
|---|---|
| ⭐⭐ **WebSocket** | ⭐⭐ **the answer** — bidirectional, low overhead per message |
| ⭐ Long polling | ⭐ the fallback for restrictive networks; higher latency and overhead |
| ⭐ Server-sent events | ⭐ server→client only; you still need a POST for sending |
| ⭐⭐ Mobile push (APNs/FCM) | ⭐⭐ **for offline users — you cannot hold a socket on a backgrounded phone** |

```
⭐⭐ THE ROUTING PROBLEM, which is the heart of the round:
⭐   user A is connected to gateway-17 · user B is connected to gateway-143
⭐   ⇒ ⭐⭐ A's message arrives at gateway-17, which has NO SOCKET to B.
⭐
⭐ ⭐⭐ THE ANSWER — a CONNECTION REGISTRY:
⭐   ⭐ Redis: user_id → gateway_id, ⭐⭐ with a TTL refreshed by heartbeat
⭐   ⇒ gateway-17 looks up B, finds gateway-143, ⭐⭐ and forwards over an internal channel
⭐   ⇒ ⭐ the internal hop is a message bus or direct RPC between gateways
⭐   ⚠️ ⭐⭐ THE REGISTRY IS THE HOT PATH AND A SINGLE POINT OF FAILURE — ⭐ replicate it, and
⭐     ⭐⭐ make a stale entry harmless: forwarding to the wrong gateway must FAIL and fall back
⭐     to the offline path, never silently drop.
```

| ⭐ Alternative worth naming | |
|---|---|
| ⭐ **Consistent hashing** users to gateways | ⭐ no registry lookup — **but a client cannot choose which gateway it lands on**, so you need a redirect on connect |
| ⭐⭐ **A pub/sub topic per user** | ⭐⭐ each gateway subscribes for its connected users; **the broker does the routing** — simpler, and it costs broker capacity |

# Part 3 — ⭐⭐ Ordering, delivery and the state machine

```
⭐⭐ ORDERING CANNOT COME FROM CLIENT TIMESTAMPS. ⭐ Two phones, two clocks (Day 409).
⭐   ⇒ ⭐⭐ the SERVER assigns a per-conversation SEQUENCE NUMBER on receipt
⭐   ⇒ ⭐⭐ ordering is per CONVERSATION, not global — ⭐ which is the same partitioning insight as
⭐     a Kafka key or an SQS message group. ⭐ Sequence numbers are monotonic within a conversation.
⭐   ⇒ ⭐ clients sort by sequence, and can detect a GAP — ⭐⭐ which is how they know to re-sync.
```

| ⭐⭐ The delivery state machine | |
|---|---|
| `SENT` | ⭐ the server accepted it and assigned a sequence — **this is the ack the sender waits for** |
| `DELIVERED` | ⭐ the recipient's device acknowledged receipt |
| `READ` | ⭐ the recipient opened the conversation |
| ⭐⭐ **Each transition is its own message** | ⭐⭐ receipts flow back through the same path, and **they are also messages that can be lost** |

```
⭐⭐ THE IDEMPOTENCY REQUIREMENT — the same as everywhere else in this roadmap:
⭐   the client generates a MESSAGE ID (a UUID) before sending.
⭐   ⇒ ⭐⭐ a retry after an ambiguous timeout carries the SAME id ⇒ the server deduplicates
⭐   ⇒ ⭐⭐ without this, a flaky mobile network produces DUPLICATE MESSAGES —
⭐     which is the single most user-visible bug this system can have (Day 407).
```

| ⭐ Offline delivery | |
|---|---|
| ⭐⭐ **Registry lookup finds no connection** | ⭐⭐ persist to the recipient's **pending queue** and send a mobile push |
| ⭐ On reconnect | ⭐⭐ **the client sends its last-seen sequence per conversation; the server sends everything after it** |
| ⭐ Why not "send all unread" | ⭐ the client's cursor is the reliable source — server-side unread flags drift |

# Part 4 — ⭐⭐ Groups, storage, and the deep dive

## ⭐ Group chat = Day 482, again

| ⭐ Group size | ⭐ Strategy |
|---|---|
| ⭐ Small (< ~500) | ⭐⭐ **fan-out on write** — write into each member's stream; reads are trivial |
| ⭐⭐ **Large (100k members)** | ⭐⭐ **fan-out on read** — one copy in the group's log, members read from it |
| ⭐ The parallel | ⭐⭐ **exactly the celebrity problem** — say so; it demonstrates transfer rather than recall |

## ⭐⭐ Storage and partitioning

| | |
|---|---|
| ⭐⭐ **Partition by `conversation_id`** | ⭐⭐ **because every read is "the last N messages of this conversation"** — the access pattern decides it (Day 329) |
| ⭐ Clustering key | ⭐ `sequence DESC` — the newest page is one contiguous read |
| ⭐ Store | ⭐⭐ a wide-column store fits (Cassandra/DynamoDB); **write-heavy, key-based reads, no joins** |
| ⭐ Hot conversation | ⭐⭐ a single huge group is a hot partition — **shard the conversation by time bucket** |
| ⭐ Retention | ⭐ archive cold history to object storage; the recent window stays hot |

⚠️ **The one thing you must not do: partition by `user_id`.** A 1:1 conversation would then live in two
partitions and every read would be a scatter-gather merge. **Partitioning by conversation makes the
common read a single-partition query, and it is the decision the whole storage design hangs on.**

# 🚪 Failure and trade-offs (38–43)

| ⭐ Question | ⭐ Answer |
|---|---|
| ⭐⭐ **A gateway server dies** | ⭐⭐ ~50k clients reconnect at once — **a thundering herd.** Clients need **jittered reconnect backoff**, or the surviving gateways get a synchronised spike |
| ⭐ The registry has a stale entry | ⭐⭐ forwarding fails ⇒ **fall back to the offline path** — never drop |
| ⭐⭐ **A message is acknowledged then lost** | ⭐⭐ **do not ack until it is persisted** — the sender's `SENT` state must mean durable |
| ⭐ Duplicate delivery | ⭐ client-side dedup on message id |
| ⭐ Clock skew between phones | ⭐⭐ irrelevant — server sequence numbers order everything |
| ⭐ A user on three devices | ⭐⭐ **the registry maps a user to a *set* of connections**, and read state is per-device with a per-user cursor |

> **⭐ The jittered-reconnect answer is the one that marks operational experience.** Losing a gateway
> holding fifty thousand sockets creates an instantaneous, synchronised reconnect storm against the
> remaining servers — **and without client-side jitter, recovering from one failure cascades into
> several.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Not noticing the routing problem** | ⭐⭐ it is the actual design problem in this round |
| ⭐ A registry with no TTL or heartbeat | ⭐ dead entries route into the void |
| ⭐ Treating a stale registry entry as fatal | ⭐⭐ it must fail into the offline path |
| ⭐⭐ **Ordering by client timestamp** | ⭐⭐ two phones, two clocks — Day 409 |
| ⭐ Global sequence numbers | ⭐⭐ per conversation is what is needed, and it partitions |
| ⭐⭐ **No client-generated message id** | ⭐⭐ a flaky network produces duplicate messages |
| ⭐ Acking before persisting | ⭐⭐ `SENT` becomes a lie |
| ⭐ Server-side unread flags as the sync source | ⭐ the client cursor is more reliable |
| ⭐⭐ **Partitioning by user id** | ⭐⭐ every conversation read becomes scatter-gather |
| ⭐ Fan-out on write for a 100k-member group | ⭐⭐ the celebrity problem, unrecognised |
| ⭐ No jittered reconnect | ⭐⭐ one dead gateway becomes a cascade |
| Forgetting mobile push for offline users | you cannot hold a socket on a backgrounded phone |

## Interview questions

**Q: What is the core design problem in a chat system?**
Routing, because this is the one system in the round set where the server is not stateless. Ten million
concurrent connections across roughly two hundred gateway servers means the recipient's socket lives on
one specific box, and the sender's message arrives somewhere else. So you need a connection registry —
user to gateway, in Redis, with a TTL refreshed by heartbeat — and an internal forwarding hop. The
registry is then on the hot path and is a single point of failure, so it is replicated, and a stale entry
has to fail into the offline path rather than silently dropping the message.

**Q: How do you order messages?**
Not by client timestamp, because two phones have two clocks and skew reorders the conversation. The
server assigns a sequence number per conversation on receipt, so ordering is per conversation rather than
global — which is the same insight as a Kafka partition key or an SQS message group, and it is also what
lets the storage partition cleanly. Clients sort by sequence and can detect a gap, which is how they know
to re-sync rather than silently displaying an incomplete thread.

**Q: How do you stop duplicate messages?**
The client generates a message id before sending, so a retry after an ambiguous timeout carries the same
id and the server deduplicates on it. This matters more here than almost anywhere else because mobile
networks produce ambiguous timeouts constantly — the message was delivered and the acknowledgement was
lost — and a duplicate message is the single most visible bug this product can have. It is the same
client-supplied idempotency key as everywhere else, just with a much higher failure rate driving it.

**Q: How do you partition the message store?**
By conversation id, because every read is "the last N messages of this conversation", so that keeps the
common query on a single partition, clustered by sequence descending so the newest page is one contiguous
read. Partitioning by user id is the trap: a one-to-one conversation would then span two partitions and
every read becomes a scatter-gather merge. The one weakness is a single enormous group being a hot
partition, which I would handle by sub-sharding that conversation by time bucket.

**Q: A gateway server holding fifty thousand connections dies. What happens?**
Fifty thousand clients detect the drop and reconnect simultaneously, which is a thundering herd against
the surviving gateways — and if reconnection is immediate and uniform, recovering from one failure
cascades into more. So clients reconnect with exponential backoff and jitter, and the load balancer
spreads them. Their sessions are re-registered on new gateways, and each client sends its last-seen
sequence per conversation so the server can replay anything missed. Nothing is lost because messages are
persisted before being acknowledged.
