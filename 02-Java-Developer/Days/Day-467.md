# Day 467

**L-467** · Project defence I — the narrative and the whiteboard

**Time:** 3 hrs · **Mode:** NEW · **⭐ Project defence drills, 1 of 5**

> **⭐⭐ You need three versions of each project — thirty seconds, three minutes, and forty-five minutes —
> and the thirty-second one is the hardest, because it must contain a hook you are willing to be
> interrogated on.**
>
> Today: the three lengths, **the architecture diagram you can draw from memory in ninety seconds**, the
> hook you plant deliberately, and how to describe a personal project without apologising for it.

---

# Part 1 — ⭐⭐ Three lengths, three jobs

| ⭐ Length | ⭐ Where | ⭐ Job |
|---|---|---|
| ⭐⭐ **30 seconds** | ⭐ recruiter screen, "tell me about yourself" | ⭐⭐ **plant a hook** |
| ⭐⭐ **3 minutes** | ⭐ "walk me through a project" | ⭐⭐ **problem → shape → hard part → outcome** |
| ⭐ **45 minutes** | ⭐ the deep dive round | ⭐⭐ **survive interrogation of every decision** |

```
⭐⭐ THE 30-SECOND VERSION — four sentences, and the last one is the hook:
⭐   "It's a multi-tenant SaaS API — teams, projects, role-based access, the usual shape.
⭐    I built it in Spring Boot with Postgres and Redis, containerised, running on ECS.
⭐    ⭐⭐ The interesting part was making event publishing reliable: I had a dual-write bug
⭐    ⭐⭐ where the order committed and the event silently never fired, so I moved to a
⭐    ⭐⭐ transactional outbox. It holds p99 under 250 ms at 500 rps."
⭐ ⇒ ⭐⭐ You have now CHOSEN the next question. ⭐ That is the point of a hook.
```

| ⭐⭐ Hook criteria | |
|---|---|
| ⭐⭐ **You can go four levels deep on it** | ⭐ Day 463's ladder |
| ⭐⭐ **It is a decision, not a feature** | ⭐⭐ "I used JWT" is not a hook; "refresh rotation with reuse detection" is |
| ⭐ It has a number attached | ⭐ numbers invite "how did you measure that?" — which you want |
| ⭐ It is not the most obvious thing | ⭐⭐ everyone says "I built a REST API" |

> **⭐ Planting a hook is the difference between being interviewed and steering an interview.** You cannot
> control what they ask, **but you can make one thing so much more interesting than the rest that asking
> about it is the natural move.**

# Part 2 — ⭐⭐ The 3-minute version

```
⭐⭐ FOUR BEATS, roughly 45 seconds each:
⭐ 1. ⭐ THE PROBLEM      what it does and for whom — ⭐⭐ in ONE sentence, no feature list
⭐ 2. ⭐ THE SHAPE        the architecture in five nouns and the data flow
⭐ 3. ⭐⭐ THE HARD PART    ⭐⭐ ONE genuine difficulty, what you tried, what you chose, WHY
⭐ 4. ⭐ THE OUTCOME      numbers, what it runs on, ⭐⭐ and one honest limitation
```

⚠️ **Beat 4's honest limitation is not a weakness, it is a credibility device.** *"It is single-region;
multi-region would double the cost and the DNS failover is minutes, so for this it was not worth it"*
tells them you evaluated it. **A project with no stated limits reads as a project nobody stress-tested.**

| ⭐ What to leave out of three minutes | |
|---|---|
| ⭐⭐ **The feature list** | ⭐⭐ nobody is buying it |
| ⭐ The tech stack recited as a list | ⭐ five nouns in the architecture is enough |
| ⭐ How long it took you | ⭐ irrelevant, and it invites a comparison you cannot win |
| ⭐⭐ **Apologising for it being a side project** | ⭐⭐ see Part 4 |

# Part 3 — ⭐⭐ The diagram you can draw in ninety seconds

```
⭐⭐ PRACTISE THIS UNTIL IT IS MUSCLE MEMORY. On a whiteboard or a shared canvas.

⭐   client ──▶ CloudFront ──▶ ALB ──▶ [ ECS tasks: Spring Boot ] ──┬──▶ Postgres (Multi-AZ)
⭐                                                                   ├──▶ Redis
⭐                                                                   ├──▶ S3 (presigned)
⭐                                                                   └──▶ outbox ▶ relay ▶ queue ▶ worker
⭐
⭐ ⭐⭐ RULES: ⭐ boxes and arrows only · ⭐⭐ label every arrow with WHAT FLOWS ·
⭐   ⭐⭐ mark the ONE place state lives · ⭐ mark the trust boundary · ⭐ mark where it would break first.
```

| ⭐ Drawing discipline | |
|---|---|
| ⭐⭐ **Draw the request path first, left to right** | ⭐⭐ then add the async path underneath |
| ⭐ Do not draw everything | ⭐⭐ five to eight boxes; detail arrives on demand |
| ⭐⭐ **Say what you are drawing as you draw it** | ⭐ silence at a whiteboard is dead air (Day 466) |
| ⭐ Leave room on the right | ⭐⭐ they will ask you to extend it |
| ⭐ Know the numbers on it | ⭐ task count, instance size, rps, p99 |

**⭐⭐ Then be able to answer, pointing at the diagram: where does it break first, what is the bottleneck,
and what happens if each box disappears.** Those three questions are asked in almost every deep dive
(Day 469), and answering them *at* the diagram is far stronger than answering them in the abstract.

# Part 4 — ⭐⭐ How to talk about a personal project

```
⭐⭐ NEVER: "It's just a side project, so..."   ⭐⭐ "It's not production, but..."
⭐   ⇒ ⭐⭐ You have pre-discounted your own evidence. The panel now discounts it further.

⭐⭐ INSTEAD, state the scope factually and let the operating record speak:
⭐   ⭐ "It's my own system — I designed it, built it, and I run it.
⭐     ⭐⭐ It's deployed on AWS through a pipeline with no stored credentials, it has SLO-based
⭐     ⭐⭐ alerting, I've forced a database failover and measured recovery at eleven seconds,
⭐     ⭐⭐ and I deploy under load with zero dropped requests."
⭐ ⇒ ⭐⭐ That is not a smaller claim than "I worked on a production service".
⭐   ⭐⭐ In several respects it is a LARGER one, because you owned ALL of it.
```

| ⭐ Where a personal project is genuinely weaker | ⭐ Say it plainly if asked |
|---|---|
| ⭐ Real traffic and real users | ⭐⭐ "load-tested to 500 rps; it has not served 500 rps of real users" |
| ⭐ Multi-year maintenance | ⭐ "I have not lived with a five-year-old codebase" |
| ⭐ Working within a team's constraints | ⭐⭐ **and this is a real gap — do not pretend otherwise** |
| ⭐ Legacy, migrations, other people's decisions | ⭐ acknowledge and move on |

> **⭐ Volunteering those four is stronger than being caught by them.** It shows you know the difference
> between what you have proven and what you have not — **which is the same instinct as Day 463's resume
> honesty, and interviewers read it the same way.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **No hook in the short version** | ⭐⭐ you surrendered control of the next question |
| ⭐ A hook you cannot defend to level 4 | ⭐⭐ you steered them into your weakest ground |
| ⭐ A feature as the hook | ⭐ "I used JWT" invites nothing |
| ⭐⭐ **Reciting a feature list** | ⭐⭐ nobody is buying the product |
| ⭐ The stack as a list of nouns | ⭐ says nothing about decisions |
| ⭐ Mentioning how long it took | invites an unwinnable comparison |
| ⭐⭐ **No stated limitation** | ⭐⭐ reads as never stress-tested |
| ⭐⭐ **Cannot draw the architecture from memory** | ⭐⭐ the single most visible failure in a deep dive |
| ⭐ Unlabelled arrows | ⭐ a box diagram with no flows is decoration |
| ⭐ Drawing in silence | dead air |
| ⭐ Drawing everything | detail should arrive on demand |
| ⭐⭐ **"It's just a side project"** | ⭐⭐ pre-discounting your own evidence |
| Pretending a personal project taught you team constraints | it did not, and it is obvious |

## Interview questions

**Q: Tell me about a project you have built.**
In four sentences with a hook at the end: it is a multi-tenant SaaS API with teams, projects and
role-based access; Spring Boot, Postgres and Redis, containerised on ECS; the interesting part was making
event publishing reliable after I found a dual-write bug where the order committed and the event silently
never fired, which I fixed with a transactional outbox; and it holds p99 under two hundred and fifty
milliseconds at five hundred requests per second. The last two sentences are deliberate — they choose
what gets asked next, and they are ground I can defend four levels deep.

**Q: Can you draw the architecture?**
Yes, and I practise it as muscle memory — request path left to right first, then the async path
underneath, five to eight boxes, every arrow labelled with what flows, and the one place state lives
marked explicitly. I keep room on the right because I will be asked to extend it. And I can answer three
things pointing at it: where it breaks first, what the bottleneck is, and what happens if each box
disappears. Answering those at the diagram is much stronger than answering them in the abstract.

**Q: It is a personal project though — how is that comparable to production experience?**
I would not pre-discount it, and I would give the operating record rather than the feature list: I
designed it, built it and I run it, it deploys through a pipeline with no stored credentials, it has
SLO-based alerting, I have forced a database failover and measured eleven seconds of client-visible
recovery, and I deploy under load with zero dropped requests. In terms of breadth of ownership that is
larger than most production roles, not smaller. Where it is genuinely weaker is real traffic, multi-year
maintenance, and working inside a team's constraints — and I would name those myself rather than be
caught by them.

**Q: Why does the short version need a "hook"?**
Because you cannot control what you are asked, but you can make one thing so much more interesting than
the rest that asking about it is the natural next move. A hook has to be a decision rather than a
feature, has to survive four levels of follow-up, and ideally carries a number, because a number invites
"how did you measure that?" — which is a question I want. Planting one is the difference between being
interviewed and steering an interview.

**Q: What limitation would you name unprompted?**
That it is single-region on purpose. Multi-region roughly doubles the cost and the operational surface,
DNS failover realistically takes minutes with a tail of clients that never move, and the data story is a
much bigger commitment than "active-active" makes it sound. For this system's availability target, three
zones in one region with a tested failover was the better trade. Naming that unprompted is a credibility
device — a project with no stated limits reads as one nobody stress-tested.

## Mini task

1. ⭐⭐ Write the **30-second version** of the flagship, ending in a hook. Then the same for NexOps.
2. ⭐⭐ Check each hook against the four criteria. **Run the level-4 ladder on it** (Day 463).
3. ⭐ Write the **3-minute version** in four beats. Time it — if it runs over 3:30, cut beat 1.
4. ⭐⭐ Add an **honest limitation** to beat 4 of both.
5. ⭐⭐ Draw the flagship architecture **from memory, in 90 seconds, narrating.** Record it. Repeat until
   it is fluent.
6. ⭐ Label every arrow with **what flows.** Mark state, the trust boundary, and where it breaks first.
7. ⭐ Write the **numbers on the diagram**: tasks, instance size, rps, p99, database size.
8. ⭐⭐ Do the same for **NexOps** — retrieval path, evaluation loop, cost per query.
9. ⭐⭐ Practise answering **"what happens if this box disappears?"** for every box.
10. ⭐ Record yourself describing the project **without ever apologising for it.** Count the hedges and
    remove them.

## 🎙️ Articulation drill

**Three minutes, recorded, twice:** the flagship, then NexOps.

**⭐ Beat 1 in one sentence, no features. Beat 2 as five nouns and the flow between them. Beat 3 as one
genuine difficulty — what you tried, what you chose and why, including the option you rejected. Beat 4
as numbers plus one honest limitation.**

**⭐ Then play it back and check three things: did you say a feature list, did you apologise for it, and
did you plant something you actually want to be asked about. If a stranger listening could not name the
one interesting decision in the project, the hook is not there yet.**
