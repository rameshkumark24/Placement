# Day 320

**L-320** · Food delivery & cab booking — matching supply to demand

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Both problems are the same shape: a pool of moving supply, a stream of demand, and a matching
> decision made in under a second.**
>
> The mistake that defines a weak answer is treating matching as **assignment**. It is not — **it is
> an offer that can be declined**, and everything interesting follows from that.

---

# Part 1 — ⭐ Finding nearby supply

**⭐ You cannot scan 50,000 drivers per request.** The interviewer wants to see you pick a spatial
index and know its trade:

| Structure | ⭐ How | ⭐ Trade |
|---|---|---|
| ⭐ **Grid / geohash cells** | ⭐ bucket by fixed cell; search cell + 8 neighbours | ⭐ **simple, O(1) update — uneven density** |
| ⭐ **Quadtree** | subdivide where dense | ⭐ adapts to density; **rebalancing under constant movement is the cost** |
| ⭐ **S2 / H3** | hierarchical cells on a sphere | ⭐ **what real systems use** — no pole distortion |
| ⭐ Redis `GEOADD`/`GEOSEARCH` | a sorted set of geohashes | ⭐ **the pragmatic production answer** (Day 204) |
| k-d tree | balanced spatial tree | ⭐ **bad here — poor at frequent updates** |

> **⭐ The property that decides it: drivers move constantly, so updates dominate reads.** A grid is
> an O(1) remove-and-insert; a k-d tree needs rebalancing. **Say that reason, not the name.**

⚠️ **Two details that show you thought about geography:** cell size is a real tuning parameter
(too small → search many cells; too big → too many candidates), and **you must search neighbouring
cells** or a driver twenty metres away across a cell boundary is invisible. **Then filter by true
distance**, because cell membership is an approximation.

⚠️ **And straight-line distance is not travel time.** A driver 500 m away across a river is further
than one 2 km away on the same road. **Name it, then say you would rank on an ETA from a routing
service and fall back to haversine.** Interviewers notice.

# Part 2 — ⭐⭐ Matching is an offer, not an assignment

```
⭐ WRONG:  find nearest driver → set trip.driver = driver → done
⭐         (the driver is asleep, or declines, and the rider waits forever)

⭐ RIGHT:  find candidates → OFFER to the best one, with a 15-second timeout
⭐         → accepted?  assign, notify both
⭐         → declined or timed out? → offer to the next → after N, widen the radius / surge
```

**⭐ This turns matching into a protocol with state, and that state is the design:**

```
   DRIVER:   OFFLINE → AVAILABLE → OFFERED → EN_ROUTE → ON_TRIP → AVAILABLE
                          ▲            │
                          └────────────┘  ⭐ decline / timeout returns them to the pool

   TRIP:     REQUESTED → MATCHING → ASSIGNED → STARTED → COMPLETED
                             │
                             └──► NO_DRIVERS_FOUND     ⭐ a real terminal state — model it
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐ **An offered driver is removed from the pool** | ⭐ **otherwise they get three simultaneous offers** |
| ⭐ **The offer has a hard timeout** | ⭐ **a driver who put the phone down must not freeze a rider** |
| ⭐ Decline is a first-class outcome | it feeds acceptance-rate metrics |
| ⭐ **Rider-side timeout too** | ⭐ tell them "no drivers" rather than spinning forever |
| Re-offer widens the search | radius and price both grow |

> **⭐ The offered-driver-leaves-the-pool rule is the concurrency answer**, and it is Day 316's seat
> hold again: **an offer is a reservation with an expiry.** Say that connection out loud — **three
> problems in this stage are the same mechanism**, and noticing is the point.

```java
// ⭐ Exactly Day 310's CAS. Two riders cannot be offered the same driver.
boolean tryOffer(Driver d) {
    return d.status().compareAndSet(AVAILABLE, OFFERED);
}
```

## ⭐ Choosing which driver — a cost function, again

```java
int cost(Driver d, Request r) {
    return etaSeconds(d, r.pickup())                    // ⭐ dominant term
         + penalty(d.acceptanceRate())                  // ⭐ reliability
         - bonus(d.idleSeconds())                       // ⭐ fairness — the longest-waiting driver
         + penalty(d.vehicleMismatch(r.requirements())); // ⭐ hard filters first, though
}
```

**⭐ Day 312's elevator dispatcher, unchanged.** Hard constraints (vehicle class, accessibility,
capacity) **filter**; soft preferences **score**. Confusing the two is a common error — **a
wheelchair-accessible requirement is not a penalty term.**

# Part 3 — ⭐ Where the two problems diverge

## ⭐ Cab booking: two parties, live tracking

| Concern | ⭐ Design |
|---|---|
| ⭐ **Fare** | ⭐ base + distance + time + surge, as a **strategy** — and **frozen at trip end** (Day 290) |
| ⭐ **Surge** | ⭐ a multiplier per cell per time window, **shown before booking and locked into the trip** |
| Location updates | ⭐ high-volume writes; **latest-wins, no history needed for matching** |
| Cancellation | a fee window; a state, not a delete |
| ⭐ **Trip is an event record** | ⭐ immutable once completed — disputes need the frozen fare inputs |

⚠️ **Surge that changes mid-trip is a support nightmare.** **Quote, lock, charge the locked
multiplier** — the same frozen-inputs rule as Day 290's risk scores and Day 315's exchange rates.
**Three appearances is a pattern worth naming in an interview.**

## ⭐ Food delivery: three parties, and time is the hard part

```
⭐ Customer ──order──► Restaurant ──prepares──► Courier ──delivers──► Customer
⭐              ⭐ THE question: WHEN do you dispatch the courier?
```

| ⭐ Dispatch timing | ⭐ Consequence |
|---|---|
| ⭐ At order time | ⭐ the courier waits 20 minutes at the restaurant — wasted capacity |
| ⭐ When food is ready | ⭐ **the customer waits for a courier to arrive — cold food, long ETA** |
| ⭐⭐ **At `readyAt − travelTimeToRestaurant`** | ⭐⭐ **the right answer, and it needs a prep-time ESTIMATE** |

> **⭐ That estimate is the interesting modelling object**: per restaurant, per item count, per time of
> day, and it must be **learned from actuals and corrected as the order progresses**. Saying "prep
> time is an estimate that updates, and dispatch is scheduled against it" is the strongest sentence
> available in the food-delivery variant.

| Also | ⭐ Design |
|---|---|
| ⭐ **Batching** | ⭐ one courier, two nearby orders — **only if the detour cost is under a threshold** |
| ⭐ Restaurant rejection | ⭐ a state, with automatic refund and re-offer |
| Order state machine | longer than a trip's: PLACED → ACCEPTED → PREPARING → READY → PICKED_UP → DELIVERED |
| ⭐ **Partial failure** | ⭐ food made, no courier available — **a real state needing a policy** |
| Live ETA | recomputed from courier position, not a fixed promise |

# Part 4 — ⭐ Concurrency and scale

| ⭐ Shared mutable state | ⭐ Guard |
|---|---|
| ⭐ **Driver status** | ⭐ **CAS `AVAILABLE → OFFERED`** — the whole race |
| The spatial index | ⭐ a concurrent map per cell; **staleness is fine — `tryOffer` is the arbiter** |
| Surge multipliers per cell | read-mostly; recomputed on a schedule |
| ⭐ Trip state | ⭐ one aggregate, conditional updates (Day 316) |

**⭐ The reasoning to voice:** *"the index can be stale, because it only produces candidates — the
compare-and-set on the driver's status is what decides. So I never need a lock over the index."*
**That is the same argument as the parking lot's free-spot list**, and repeating it deliberately
shows you have a principle rather than a memorised answer.

| ⭐ Scale question | ⭐ Answer |
|---|---|
| ⭐ **Location updates at 50k drivers × every 4s** | ⭐ **12.5k writes/s — in-memory or Redis, never the primary database** |
| Matching across instances | ⭐ shard by geographic cell — locality makes it natural |
| ⭐ Hotspot cells (a stadium at 10pm) | ⭐ the grid's weakness; subdivide dynamically or use H3 resolution levels |

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐⭐ **Assigning instead of offering** | ⭐⭐ **riders wait on drivers who are not there** |
| ⭐ Not removing an offered driver from the pool | ⭐ three riders, one driver |
| No offer timeout | one unresponsive driver freezes a request |
| ⭐ Scanning all drivers | ⭐ O(n) per request |
| ⭐ Only searching the containing cell | ⭐ a driver 20 m away across a boundary is invisible |
| ⭐ Ranking by straight-line distance | ⭐ the driver across the river |
| Hard constraints as score penalties | a wheelchair user gets a non-accessible car |
| ⭐ **Surge changing mid-trip** | ⭐ disputes with no defensible answer |
| ⭐ Dispatching couriers at order time | wasted capacity waiting at restaurants |
| ⭐ **No prep-time estimate** | ⭐ **the dispatch decision has no basis** |
| Batching with no detour cap | both customers get cold food |
| ⭐ No `NO_DRIVERS_FOUND` state | the request hangs forever |
| Location writes to the primary database | 12k writes/s at your transactional store |

## Interview questions

**Q: How do you find nearby drivers?**
A spatial index keyed by cell — geohash, S2 or H3 — searching the containing cell plus its neighbours
and then filtering by true distance. The deciding property is that drivers move constantly, so
updates dominate reads: a grid is an O(1) remove-and-insert, while a k-d tree needs rebalancing. In
production I would use Redis geospatial commands rather than building it.

**Q: What is wrong with assigning the nearest driver?**
Drivers decline. Matching is an offer with a timeout, not an assignment — you offer to the best
candidate, remove them from the pool while the offer is live, and fall through to the next on decline
or timeout, widening the radius as you go. The rider needs a timeout too, so "no drivers available"
is a real terminal state rather than an infinite spinner.

**Q: Two riders request at the same moment and the same driver is nearest to both.**
The status is the shared mutable state, so it is a compare-and-set from AVAILABLE to OFFERED — exactly
one wins and the other rider's search moves to its next candidate. The spatial index is allowed to be
stale, because it only produces candidates; the CAS is the arbiter. It is the same structure as a
parking spot and a seat hold, which is a nice reassurance that the shape is right.

**Q: When do you dispatch a courier?**
Not at order time — the courier waits twenty minutes at the restaurant. Not when the food is ready —
then the customer waits for travel. You dispatch at the estimated ready time minus the courier's
travel time to the restaurant, which means the prep-time estimate is a first-class object: per
restaurant, per basket size, per time of day, learned from actuals and corrected as the order
progresses.

**Q: How do you handle surge pricing?**
As a multiplier per cell per time window, shown before booking and locked into the trip. A surge that
changes mid-trip produces disputes you cannot defend. That is the same frozen-inputs rule as a risk
score computed from a versioned ruleset and an expense recorded with the exchange rate of the day —
anything a customer is charged for must be reproducible from what was true at the time.

## Mini task

1. Build a **grid index** with add, move and `nearby(point, radius)` searching neighbouring cells.
   **Test the boundary case**: a driver 20 m away in an adjacent cell.
2. **Tune the cell size**: measure candidates returned and cells scanned across three sizes.
3. ⭐ Implement the **offer protocol** with a timeout and fall-through. **Test: three drivers, all
   decline, assert the request reaches `NO_DRIVERS_FOUND`.**
4. ⭐ Implement `tryOffer` with CAS and run **two riders against one driver, 1,000 times**. Assert
   exactly one offer.
5. Build the **cost function** with hard filters separated from soft scores. **Add an accessibility
   requirement and confirm it filters rather than penalises.**
6. Implement fare as a strategy with a **locked surge multiplier**, and write the test that fails
   when surge is read at completion time.
7. ⭐ Build the **dispatch scheduler**: given `readyAt` and a courier ETA, dispatch at the right
   moment. **Then make the restaurant late and confirm the schedule corrects.**
8. Implement **two-order batching with a detour cap.** Measure the second customer's delivery time
   with and without it.

## 🎙️ Articulation drill

**Three minutes:** *"A rider opens the app and taps 'request'. Take me through the next fifteen
seconds."*

**⭐ The full answer: cell lookup plus neighbours → filter by true distance and hard constraints →
score with a cost function → offer to the best with a 15-second timeout, removing them from the pool
via a compare-and-set → decline or timeout falls through to the next → after N attempts, widen the
radius, and if nothing, a real "no drivers" state.**

**⭐ The word that decides the round is "offer".** Candidates who say "assign" have designed a system
that strands riders on drivers who are not looking at their phones — and every follow-up will expose
it.
