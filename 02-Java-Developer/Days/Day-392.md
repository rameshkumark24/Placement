# Day 392

**L-392** · The edge — Route 53, CloudFront and API Gateway

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ Putting CloudFront in front of S3 usually makes your bill smaller, not larger — because
> CloudFront egress is cheaper per gigabyte than S3 egress, and the origin fetches behind it are free.
> Almost nobody expects the CDN to be the cheap option.**
>
> Today: alias records and why they beat CNAMEs, **the cache key that quietly makes your CDN useless**,
> DNS failover's honest limits, and **ALB versus API Gateway decided on what each one actually charges
> for.**

---

# Part 1 — ⭐ Route 53

| Record | ⭐ Note |
|---|---|
| ⭐⭐ **Alias** | ⭐⭐ **AWS-specific: free queries, works at the zone apex, tracks the target's IPs** |
| CNAME | ⭐⭐ **cannot exist at the apex** — `example.com` cannot be a CNAME |
| A / AAAA | ordinary addresses |
| ⭐ TXT | domain verification, SPF/DKIM |

> **⭐ Use alias records for every AWS target — ALB, CloudFront, S3 website, API Gateway.** They are
> free, they follow the target as its addresses change, **and they solve the apex problem that
> otherwise forces you into a redirect from `example.com` to `www`.**

| ⭐ Routing policy | ⭐ For |
|---|---|
| Simple | one target |
| ⭐ **Weighted** | ⭐⭐ **canary at DNS level, blue/green traffic shifting** (Day 371) |
| ⭐ **Latency** | ⭐ multi-region: send users to the nearest healthy region |
| ⭐ **Failover** | ⭐ primary + secondary with a health check |
| Geolocation / geoproximity | compliance and content localisation |
| Multivalue answer | poor man's load balancing with health checks |

## ⭐⭐ DNS failover is slow, and you must say so

```
⭐ Route 53 health check detects failure   ⭐ ~30–90s (3 failed checks × 10–30s)
⭐ + record TTL expiry                     ⭐ 60s if you set it low; ⭐⭐ often 300s+ in practice
⭐ + ⭐⭐ RESOLVER CACHING that ignores TTL  ⭐⭐ ISPs, corporate resolvers, browsers
⭐ + ⭐⭐ THE JVM's OWN DNS CACHE            ⭐⭐ Day 387, again
⭐ ─────────────────────────────────────
⭐ ⇒ ⭐⭐ REALISTIC FAILOVER: MINUTES, and a long tail of clients that never move.
```

⚠️ **So DNS failover is a *disaster recovery* mechanism, not a *high availability* one.** Within a
region, availability comes from a load balancer with health checks (Day 389) — **something that fails
over in seconds because it does not involve clients at all.** Confusing the two is how a "multi-region
active-active" design turns out to take eleven minutes to shed a bad region.

# Part 2 — ⭐⭐ CloudFront, and the cache key that decides everything

```
⭐⭐ THE MISTAKE THAT MAKES A CDN POINTLESS:
⭐   "Forward all headers and all cookies to the origin."
⭐   ⇒ ⭐⭐ every distinct header/cookie combination is a SEPARATE CACHE ENTRY
⭐   ⇒ ⭐⭐ every user has different cookies ⇒ ⭐⭐ CACHE HIT RATIO ≈ 0
⭐   ⇒ ⭐⭐ You are now paying CloudFront to be a slow, expensive proxy.
```

| ⭐ Cache key rule | |
|---|---|
| ⭐⭐ **Include only what changes the response** | ⭐ usually: path, and maybe `Accept-Encoding` |
| ⭐ **Forward but do not cache on** | ⭐⭐ headers the origin needs (`Authorization`) can be forwarded **without** being in the key |
| ⭐ Normalise | ⭐ strip tracking query strings (`utm_*`) from the key |
| ⭐⭐ **Measure `CacheHitRate`** | ⭐⭐ **this is the metric that says whether the CDN is working at all** |

| ⭐ Feature | ⭐ Why it matters |
|---|---|
| ⭐⭐ **OAC (Origin Access Control)** | ⭐⭐ **the bucket stays private; only CloudFront can read it** (Day 386) |
| ⭐ **Behaviours by path** | ⭐ `/static/*` cached hard, `/api/*` passed through with no cache |
| ⭐ **Origin Shield** | ⭐ an extra caching layer that shields the origin from many edge misses |
| ⭐ **Signed URLs / cookies** | ⭐ paid or private content, expiring |
| ⭐ CloudFront Functions / Lambda@Edge | ⭐⭐ Functions for cheap header rewrites; Edge for real logic |
| ⭐ **WAF, Shield** | ⭐ rate limiting and DDoS absorption **at the edge, before your origin** |
| ⭐ Compression, HTTP/3 | free wins |

## ⭐⭐ The cost inversion, stated plainly

```
⭐ S3 direct to internet        ≈ ⭐ $0.09/GB
⭐ CloudFront to internet       ≈ ⭐ $0.085/GB (and lower at volume)
⭐ ⭐⭐ CloudFront ← S3 origin fetch = ⭐⭐ FREE
⭐ ⇒ ⭐⭐ CloudFront is CHEAPER PER GB *AND* most requests never reach S3 at all
⭐      (no per-request charge, no origin egress). ⭐⭐ Cheaper AND faster AND more private.
```

⚠️ **The two operational gotchas.** Certificates for CloudFront **must be in `us-east-1`** regardless of
where anything else lives (Day 380) — this fails on your first deploy, always. And **cache invalidation
is slow and charged beyond 1,000 paths a month**: the correct approach is **versioned filenames**
(`app.a3f9c1.js`), so you never invalidate at all. **Invalidation is a fix for a naming mistake.**

# Part 3 — ⭐⭐ API Gateway, and when the ALB is the better answer

| | ⭐ REST API | ⭐⭐ HTTP API |
|---|---|---|
| ⭐ Price | ⭐ ~$3.50 per million | ⭐⭐ **~$1.00 per million** |
| ⭐ Features | ⭐⭐ **API keys, usage plans, request validation, WAF, private endpoints, caching** | ⭐ JWT auth, CORS, simpler |
| ⭐ Verdict | ⭐ when you need those specific features | ⭐⭐ **the default choice** |

| ⭐ What API Gateway is genuinely worth paying for | |
|---|---|
| ⭐⭐ **Authorizers** | ⭐ JWT/Lambda auth **before** the request reaches your code |
| ⭐⭐ **Usage plans and API keys** | ⭐⭐ per-customer rate limits — hard to build yourself |
| ⭐ Throttling | ⭐ a real load-shedding layer in front of everything (Day 340) |
| ⭐ Direct service integrations | ⭐ SQS/DynamoDB with **no Lambda at all** |
| Request validation, WAF, private APIs | ⭐ real, if you need them |

```
⭐⭐ THE CONSTRAINT NOBODY READS UNTIL IT BITES:
⭐   ⭐⭐ API Gateway has a HARD 29-SECOND INTEGRATION TIMEOUT.
⭐   ⇒ ⭐ no long-running synchronous requests, ⭐⭐ no long-polling, ⭐ no big synchronous exports.
⭐   ⇒ ⭐ The right answer is 202 Accepted + a job id + polling or WebSockets (Day 340).
```

## ⭐ ALB or API Gateway?

| ⭐ Choose **ALB** | ⭐ Choose **API Gateway** |
|---|---|
| ⭐⭐ **a container fleet already exists** | ⭐⭐ **Lambda backends** |
| ⭐⭐ **high, steady request volume** | ⭐ spiky or low volume |
| ⭐ you handle auth in the app | ⭐⭐ **you want auth, throttling and keys as infrastructure** |
| ⭐⭐ **cost matters at scale** | ⭐ per-customer usage plans matter |

```
⭐⭐ THE ARITHMETIC, since this is really a cost decision:
⭐   1 BILLION requests/month:  ⭐ ALB ≈ tens of dollars (LCU-based)
⭐                              ⭐⭐ HTTP API ≈ $1,000  ·  REST API ≈ $3,500
⭐ ⇒ ⭐⭐ At high steady volume the ALB is an order of magnitude cheaper.
⭐   ⭐ At low volume API Gateway is nearly free and gives you far more.
```

# Part 4 — ⭐ Putting the edge together

```
⭐ user
⭐  → ⭐ Route 53 (alias, latency or failover policy)
⭐  → ⭐⭐ CloudFront   ⭐ static cached hard · ⭐ /api/* passthrough · ⭐ WAF + rate limiting here
⭐        ├→ ⭐ S3 (private, OAC) for assets
⭐        └→ ⭐ ALB → ECS tasks in private subnets (Day 389, 390)
```

| ⭐ Why route the API through CloudFront too, even uncached | |
|---|---|
| ⭐⭐ **TLS terminates at the edge** | ⭐⭐ the handshake happens near the user — **real latency win on mobile** |
| ⭐ The connection to origin is **kept warm** | ⭐ AWS backbone, not the public internet |
| ⭐⭐ **One place for WAF, rate limiting and Shield** | ⭐⭐ before anything of yours is touched |
| ⭐ One domain, no CORS | ⭐ `/api/*` and `/` are the same origin |

> **⭐ "Static assets at the edge, API through the edge uncached, WAF at the edge, origin private" is a
> complete and defensible edge design**, and it is four sentences long.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ CNAME at the zone apex | ⭐ not allowed — use an alias record |
| ⭐ Paying for queries you could get free | alias queries to AWS targets are free |
| ⭐⭐ **Treating DNS failover as high availability** | ⭐⭐ minutes, plus clients that never move |
| ⭐ Long TTLs on records you intend to fail over | ⭐ your RTO is the TTL |
| ⭐⭐ **Forwarding all headers and cookies** | ⭐⭐ cache hit ratio ≈ 0; a CDN that only adds a hop |
| ⭐ Never looking at `CacheHitRate` | ⭐⭐ the one metric that says it is working |
| ⭐ Tracking parameters in the cache key | ⭐ one entry per campaign link |
| ⭐⭐ **Certificate not in `us-east-1` for CloudFront** | ⭐⭐ first-deploy failure, every time |
| ⭐⭐ **Relying on invalidation instead of versioned filenames** | ⭐⭐ slow, charged, and a naming problem in disguise |
| ⭐ Public bucket instead of OAC | more expensive and less private (Day 386) |
| ⭐⭐ **Synchronous request over 29s through API Gateway** | ⭐⭐ hard timeout — needs 202 + polling |
| ⭐ REST API where HTTP API would do | ⭐ 3.5× the price for unused features |
| ⭐⭐ **API Gateway in front of a busy container fleet** | ⭐⭐ an order of magnitude more than an ALB |

## Interview questions

**Q: Why is an alias record better than a CNAME?**
Three reasons. Queries against alias records to AWS targets are free. They work at the zone apex, where a
CNAME is not allowed — so `example.com` can point directly at a load balancer instead of redirecting to
`www`. And they track the target's addresses as they change, which matters because an ALB's IPs are not
stable. For any AWS target, alias is simply the correct choice.

**Q: How fast is DNS failover?**
Slower than people plan for. Health check detection is thirty to ninety seconds, then the record TTL has
to expire, then you are at the mercy of resolvers and clients that ignore TTLs — including the JVM's own
DNS cache. Realistically it is minutes with a long tail of clients that never move at all. So DNS
failover is a disaster recovery mechanism for losing a region, not a high availability mechanism. Within
a region, availability comes from a load balancer with health checks, because that fails over in seconds
without involving clients.

**Q: A team added CloudFront and latency did not improve. What do you check first?**
Cache hit rate. The usual cause is a cache key that includes all headers and all cookies, so every user's
request is a unique key and nothing is ever served from cache — you have paid for an extra network hop.
The rule is that the cache key contains only what actually changes the response; headers the origin needs,
like `Authorization`, can be forwarded without being part of the key. I would also strip tracking query
parameters, since otherwise every campaign link is its own cache entry.

**Q: Is putting CloudFront in front of S3 more expensive?**
No, it is usually cheaper, which surprises people. CloudFront egress is priced slightly below S3 egress
and falls further at volume, origin fetches from S3 to CloudFront are free, and most requests never reach
S3 at all so you avoid the per-request charges too. On top of that the bucket can stay private behind an
origin access control, and you get somewhere to attach WAF and rate limiting. Cheaper, faster and more
private simultaneously — which is rare enough to be worth remembering.

**Q: ALB or API Gateway?**
It is mostly a cost and feature question. API Gateway gives you authorizers, per-customer usage plans and
API keys, throttling and request validation as infrastructure rather than code, and it integrates
natively with Lambda — at low volume it is nearly free and worth a lot. But at a billion requests a month
it is around a thousand dollars for the HTTP API and three and a half thousand for REST, against tens of
dollars for an ALB. So: Lambda backends or spiky low volume, API Gateway. An existing container fleet at
steady high volume, an ALB. And whichever I pick, I would remember the twenty-nine-second hard timeout
API Gateway imposes, which rules out long synchronous requests entirely.

## Mini task

1. ⭐ Create an **alias record at the apex** pointing at your ALB. Confirm a CNAME there is rejected.
2. ⭐ Set up a **weighted policy** and shift 10% of traffic to a second target group (Day 371).
3. ⭐⭐ Configure **failover with a health check**, break the primary, and **time the real failover from a
   client's perspective.** Compare it to the ALB's.
4. ⭐⭐ Put CloudFront in front of S3 with **OAC** and prove the bucket is unreachable directly.
5. ⭐⭐ Deliberately forward all cookies, load-test, and **watch `CacheHitRate` collapse.** Then fix the
   cache policy and compare.
6. ⭐ Add a **`/api/*` behaviour** with caching disabled and origin request policy forwarding
   `Authorization`.
7. ⭐ Deploy with a certificate in the **wrong region** and read the error. Then issue one in `us-east-1`.
8. ⭐⭐ Switch to **versioned asset filenames** and confirm you never need an invalidation again.
9. ⭐ Attach **WAF with a rate-based rule** at CloudFront and prove it blocks a flood before your origin
   sees it.
10. ⭐⭐ **Price your own traffic** through an ALB, an HTTP API and a REST API. Write the three numbers
    down and pick with the arithmetic.
