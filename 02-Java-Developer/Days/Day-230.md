# Day 230 🔑

**J-230** · 🔑 **Lists, keys and reconciliation** — ⭐⭐ the index key corrupts data

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: a key tells React which item is *which* across renders, so using the
> array index means "the thing in position 2" rather than "order 4471" — and when the list reorders,
> React keeps the old component's state in the new position, which moves a user's typing and a
> checkbox onto the wrong record.**
>
> Today: reconciliation, ⭐⭐ the index-key data corruption, ⭐ `key` as a remount tool, and long lists.

---

# Part 1 — How reconciliation decides

```
⭐⭐ REACT COMPARES OLD TREE TO NEW TREE, POSITION BY POSITION:

⭐   ① DIFFERENT TYPE at this position ⇒ ⭐⭐ DESTROY the old subtree,
⭐      BUILD the new one. ⭐ ALL STATE INSIDE IS LOST.
⭐   ② SAME TYPE ⇒ ⭐ KEEP the instance, UPDATE the props.
⭐      ⭐⭐ STATE SURVIVES.
⭐   ③ IN A LIST ⇒ ⭐⭐ **key** DECIDES WHAT "THIS POSITION" MEANS.

⭐   ⇒ ⭐⭐ THE RULE THAT EXPLAINS EVERYTHING TODAY:
⭐     **SAME KEY + SAME TYPE = SAME COMPONENT INSTANCE = SAME STATE.**
⭐   ⇒ ⭐ THE KEY IS AN IDENTITY, NOT AN INDEX — the same distinction
⭐     as an entity's @Id versus its position in a List.
```

# Part 2 — ⭐⭐ Why the index key corrupts data

```jsx
// ❌ the default people reach for
{orders.map((order, i) => <OrderRow key={i} order={order} />)}
```

```
⭐⭐ THE FAILURE, STEP BY STEP

⭐   orders = [A, B, C]           keys = 0, 1, 2
⭐   ⭐ the user ticks the checkbox on row B (key 1) — that checkbox
⭐     is LOCAL STATE inside OrderRow.

⭐   ⭐ now A is deleted:
⭐   orders = [B, C]              keys = 0, 1

⭐   ⭐⭐ REACT SEES: key 0 exists, key 1 exists, key 2 is gone.
⭐     ⇒ IT KEEPS instance 0 (which held A's state) and gives it B's props.
⭐     ⇒ IT KEEPS instance 1 (which held B's state — THE TICKED BOX)
⭐       and gives it C's props.

⭐   ⇒ ⭐⭐ THE TICK IS NOW ON ORDER C. THE USER TICKED B.
⭐     NOTHING ERRORS. THE SCREEN LOOKS COMPLETELY NORMAL.
⭐     ⇒ ⭐⭐ IF THAT CHECKBOX MEANS "REFUND THIS ORDER",
⭐       YOU HAVE JUST REFUNDED THE WRONG CUSTOMER.
```

| ⭐ Symptom | Real cause |
|---|---|
| Typing appears in the wrong row | ⭐⭐ Index keys + reorder |
| A checkbox moves after a delete | ⭐⭐ Index keys |
| An input keeps a value after filtering | ⭐ Index keys |

```jsx
// ✅ a STABLE IDENTITY that belongs to the DATA
{orders.map(o => <OrderRow key={o.id} order={o} />)}
```

| ⭐ Key source | Verdict |
|---|---|
| `item.id` from the server | ⭐⭐ ✅ **Correct** — it is the `@Id` |
| `crypto.randomUUID()` at render | ⭐⭐ ❌ New every render ⇒ **remounts everything, every time** |
| `JSON.stringify(item)` | ❌ Changes when any field changes ⇒ remount on edit |
| ⭐ Index | ⭐ **Only** when the list is static, never reordered, never filtered, and items hold no state. **It stops being true the day someone adds sorting.** |
| Composite `` `${a}-${b}` `` | ✅ When there is no single id — ⭐ a composite key |

> ⭐⭐ **Keys are local to their array, not global.** Two sibling lists may both use key `"1"`. And a
> key is not a prop — `props.key` is `undefined`.

# Part 3 — ⭐ `key` as a deliberate remount

```jsx
// ⭐⭐ change the key ⇒ different identity ⇒ React DESTROYS and REBUILDS
//    ⇒ all internal state resets. Exactly what you want here.
<ProfileEditor key={userId} user={user} />
```

| ⭐ Use it for | Instead of |
|---|---|
| Resetting a form when the record changes | ⭐⭐ `useEffect(() => setDraft(""), [id])` |
| Restarting an animation | A manual reset flag |
| Forcing a third-party widget to rebuild | An imperative `.destroy()` dance |

> ⭐ **This is the *one* legitimate way to reset state from the outside**, and it reads as intent
> rather than a workaround. ⭐⭐ It is the difference between mutating a bean back to defaults and
> **just constructing a new one** — the second is obviously safer, and this is that.

# Part 4 — Long lists

```
⭐⭐ THE NUMBERS, ROUGHLY
⭐   < 100 rows      ⇒ ⭐ do nothing. Really.
⭐   100–1,000       ⇒ ⭐ memoise the row (Day 232) if you MEASURED
⭐   1,000+          ⇒ ⭐⭐ VIRTUALISE — render only the ~20 visible
⭐   ⇒ ⭐ BUT FIRST ASK THE REAL QUESTION: WHY IS THE SERVER SENDING
⭐     10,000 ROWS? ⭐⭐ PAGINATION IS USUALLY THE CORRECT FIX, AND
⭐     IT FIXES THE PAYLOAD, THE SERIALISATION AND THE MEMORY TOO.
```

| ⭐ Approach | Cost |
|---|---|
| **Pagination / infinite scroll** | ⭐⭐ Fixes payload, Jackson serialisation time, memory *and* render. **Try this first.** |
| **Virtualisation** | ⭐ Fixes render only. Breaks Ctrl-F and naive "select all". |
| **Both** | ⭐ Genuinely large datasets |

> ⭐⭐ **Virtualising a list you should have paginated is optimising the wrong layer** — you still
> serialised 10,000 rows and sent them over the wire. Same instinct as fixing a slow endpoint by
> caching the response instead of fixing the query.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "why not use the array index as a key?"**

Do not say "it's a performance thing" — that undersells it entirely. **A key tells React which item is
which across renders. It's an identity, like an entity's `@Id`, not a position in a list. An index says
"the thing in slot two" instead of "order 4471", so when the list changes React matches by position and
any state inside the row stays with the position rather than the record.**

Then walk the failure, because the concreteness lands. **Three rows, the user ticks the middle
checkbox, and the first row gets deleted. React sees keys zero and one still exist, keeps those
instances and hands them the new props. The instance holding the tick is now rendering a different
order. Nothing errors and the screen looks normal — and if that checkbox means "refund this order",
I've refunded the wrong customer.**

State the category. **That's a data-integrity bug presenting as a UI glitch, which is exactly why it
survives review.**

Close on the flip side, which shows you understand the mechanism rather than the rule. **The same
mechanism is useful deliberately: changing a key destroys and rebuilds a component, so putting the
record id as the key on an editor resets the form when the selection changes. That's the idiomatic way
to reset state from outside — it's constructing a new object instead of mutating an existing one back
to its defaults, and it replaces an effect that would have done it badly.**
