# Part 1 — ⭐⭐ Envelope encryption

```
⭐⭐ ENCRYPT:
⭐   1. app calls ⭐⭐ GenerateDataKey(keyId)
⭐   2. KMS returns ⭐⭐ TWO things: ⭐ a PLAINTEXT data key ⭐⭐ and an ENCRYPTED copy of it
⭐   3. app encrypts the data LOCALLY with the plaintext key   ⭐ (fast, any size)
⭐   4. ⭐⭐ app WIPES the plaintext key from memory
⭐   5. app stores ⭐⭐ [encrypted data + encrypted data key] together

⭐⭐ DECRYPT:
⭐   1. app calls ⭐ Decrypt(encryptedDataKey) → plaintext data key
⭐   2. decrypt the data locally, ⭐ wipe the key again
```

| ⭐⭐ Why this design | |
|---|---|
| ⭐⭐ **KMS never sees your data** | ⭐⭐ only 4 KB keys cross the boundary — **a terabyte is encrypted locally** |
| ⭐ Fast | ⭐ local AES; **one KMS call per object, not per byte** |
| ⭐⭐ **The master key never leaves KMS** | ⭐⭐ it is in an HSM and **cannot be exported, by anyone** |
| ⭐ Cacheable | ⭐ reuse a data key for a batch — fewer KMS calls, **at some blast-radius cost** |

> **⭐ Every AWS "encryption at rest" checkbox is this.** S3 SSE-KMS, EBS volumes, RDS storage — **they
> all do the data key dance for you.** Knowing that means you can explain what the checkbox actually
> does rather than just that you ticked it.

⚠️ **What encryption at rest actually protects against is narrow and worth stating honestly: a stolen
disk, a decommissioned drive, an accidentally shared snapshot, a mis-set bucket.** **It does nothing
against a compromised application**, because the application is authorised to decrypt. **Anyone claiming
encryption at rest as a general security control is overselling it** — and saying so is a credibility
marker.

# Part 2 — ⭐⭐ Key policies: the one place IAM is not enough

```
⭐⭐ THE KMS KEY POLICY IS AUTHORITATIVE.
⭐   ⇒ ⭐⭐ An account ADMINISTRATOR with AdministratorAccess has NO access to a key
⭐     whose policy does not grant it. ⭐ This is unique among AWS services.
⭐   ⇒ ⭐⭐ And a key policy that grants nobody anything is UNRECOVERABLE without AWS support.
⭐   ⇒ ⭐ Which is why every key policy starts by delegating to IAM for the account root.
```

| ⭐ Mechanism | |
|---|---|
| ⭐ **Key policy** | ⭐ the resource policy — required, authoritative |
| ⭐ **Grants** | ⭐ programmatic, temporary, fine-grained — what AWS services use internally |
| ⭐⭐ **Encryption context** | ⭐⭐ **additional authenticated data** — key/value pairs that must match on decrypt |
| ⭐ Aliases | `alias/app-prod` — **use these, never raw key ids, so rotation and replacement are invisible** |

**⭐⭐ Encryption context is the underused one.** Passing `{"tenant":"acme"}` at encrypt time means
**decryption fails unless the same context is supplied** — so a leaked ciphertext for tenant A cannot be
decrypted by a call claiming tenant B, **and the context appears in CloudTrail**, making the audit log
say *what was decrypted and for whom*.

## ⭐ Key types, and when a customer-managed key is worth it

| | ⭐ AWS-managed (`aws/s3`) | ⭐⭐ Customer-managed (CMK) |
|---|---|---|
| Cost | ⭐ free | ⭐ **$1/month** + $0.03 per 10,000 requests |
| ⭐ Policy control | ⭐⭐ **none** | ⭐⭐ **yours** |
| ⭐ Cross-account | ⭐ no | ⭐⭐ **yes** |
| ⭐⭐ **Can be disabled/deleted** | ⭐ no | ⭐⭐ **yes — the "revoke everything" button** |
| Rotation | annual, automatic | configurable |

> **⭐ A customer-managed key earns its dollar when you need one of four things: a key policy, cross-
> account access, an audit trail scoped to your key, or the ability to disable it.** That last one is
> the real argument: **disabling a CMK renders every object encrypted with it unreadable, immediately.**
> It is the closest thing AWS has to a **crypto-shredding** control, and it is how you honour "delete
> all this tenant's data" for data spread across backups you cannot reach.

## ⭐⭐ What rotation does not do

```
⭐ KMS automatic key rotation (annual, or on demand):
⭐   ⇒ ⭐ creates NEW backing key material; ⭐ old material is RETAINED
⭐   ⇒ ⭐⭐ NEW encryptions use the new material; ⭐⭐ OLD CIPHERTEXTS ARE NOT RE-ENCRYPTED
⭐   ⇒ ⭐⭐ THE KEY ID AND ARN DO NOT CHANGE — nothing in your application changes at all
⭐ ⇒ ⭐⭐ So rotation limits the volume encrypted under one key. ⭐ It does NOT undo a compromise
⭐   of old material, ⭐ and it is NOT a substitute for re-encrypting if you must.
```

# Part 3 — ⭐⭐ Secrets Manager vs Parameter Store

| | ⭐ Parameter Store (SSM) | ⭐⭐ Secrets Manager |
|---|---|---|
| ⭐ Price | ⭐⭐ **standard params FREE**; advanced $0.05/mo | ⭐ **$0.40/secret/month** + API calls |
| ⭐⭐ **Rotation** | ⭐ none built in | ⭐⭐ **built-in, with Lambda rotation functions** |
| ⭐ Cross-region replication | ⭐ manual | ⭐ built in |
| ⭐ Size | 4 KB standard / 8 KB advanced | 64 KB |
| ⭐ Resource policy | advanced tier | ⭐ yes |
| ⭐ Native integrations | ⭐ ECS, CloudFormation | ⭐⭐ **RDS, Redshift, DocumentDB rotation** |

```
⭐⭐ THE HONEST RULE:
⭐   ⭐ Config and low-churn secrets  ⇒ ⭐⭐ Parameter Store (SecureString). It is FREE.
⭐   ⭐ Anything you will actually ROTATE ⇒ ⭐⭐ Secrets Manager. You are paying for rotation.
⭐ ⇒ ⭐⭐ Day 372's line, restated: a secret manager you never rotate from is
⭐    an expensive environment variable — ⭐ and here it costs $0.40 a month to prove it.
```

## ⭐⭐ Caching, because per-request `GetSecretValue` is slow and billed

```java
// ⭐⭐ WRONG: an API call, ~50ms and a charge, on every request
String pw = secretsClient.getSecretValue(r -> r.secretId("db")).secretString();

// ⭐⭐ RIGHT: the AWS Secrets Manager caching client — TTL-based refresh, no per-request call
private static final SecretCache CACHE = new SecretCache();   // ⭐ default TTL ~1 hour
String pw = CACHE.getSecretString("db");
```

⚠️ **The cache TTL and the rotation window interact, and this is where rotation outages come from.** If
the secret rotates and your cache holds the old value for an hour, **you need both credentials valid for
longer than that TTL** — which is exactly why the two-user strategy exists.

# Part 4 — ⭐⭐ Rotation that does not cause an outage

```
⭐⭐ THE SINGLE-USER STRATEGY (the naive one):
⭐   change the password ⇒ ⭐⭐ EVERY cached credential is instantly invalid
⭐   ⇒ ⭐⭐ every pool with an open connection fails on its next authentication
⭐   ⇒ ⭐⭐ a small outage on EVERY rotation ⇒ so people disable rotation. ⭐ Predictably.

⭐⭐ THE ALTERNATING-USERS STRATEGY (the correct one):
⭐   two database users, app_a and app_b. ⭐ The secret points at ONE of them.
⭐   Rotation: ⭐ change the password of the user NOT in use → ⭐⭐ then switch the secret to it.
⭐   ⇒ ⭐⭐ BOTH sets of credentials are valid throughout. ⭐ Cached values keep working.
⭐   ⇒ ⭐⭐ THIS IS DAY 372's "two credentials valid at once", implemented.
```

| ⭐ The four rotation stages Secrets Manager uses | |
|---|---|
| `createSecret` | generate the new value as `AWSPENDING` |
| `setSecret` | apply it in the database |
| ⭐ `testSecret` | ⭐⭐ **actually connect with it** — the step that prevents a broken rotation |
| `finishSecret` | promote `AWSPENDING` → `AWSCURRENT` |

> **⭐ And the application must still participate** (Day 372): re-read without a restart, **recycle the
> connection pool**, retry authentication failures once after refreshing. **Rotation is a system
> property, not a service feature.**

⚠️ **Test rotation on a schedule, in staging, under load.** An untested rotation is Day 283's untested
backup: **it works right up until the first time it matters, at which point it is a 3am outage that
nobody has ever practised.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Trying to encrypt large data directly with KMS | ⭐ 4 KB limit — envelope encryption exists for this |
| ⭐ A KMS call per record instead of per object/batch | ⭐ latency and request charges |
| ⭐⭐ **Assuming admins can use any key** | ⭐⭐ the key policy is authoritative |
| ⭐⭐ **A key policy that locks everyone out** | ⭐⭐ unrecoverable without support |
| ⭐ Referencing raw key ids instead of aliases | ⭐ key replacement becomes a code change |
| ⭐ Never using encryption context | ⭐⭐ free tenant isolation and audit detail, unused |
| ⭐⭐ **Believing rotation re-encrypts old data** | ⭐⭐ it does not — only new encryptions use new material |
| ⭐ Overselling encryption at rest | ⭐⭐ it does nothing against a compromised application |
| ⭐ Secrets Manager for static config | ⭐ Parameter Store is free |
| ⭐⭐ **`GetSecretValue` on every request** | ⭐⭐ ~50 ms and a charge, per request |
| ⭐⭐ **Single-user rotation** | ⭐⭐ a small outage every rotation, so rotation gets disabled |
| ⭐ Cache TTL longer than the dual-validity window | rotation breaks exactly the clients that cached |
| ⭐ No `testSecret` step | a rotation that "succeeded" with credentials that do not work |
| Never testing rotation | Day 283 — untested means broken |

## Interview questions

**Q: Explain envelope encryption.**
KMS will only encrypt about four kilobytes, but it protects petabytes, and envelope encryption is how
both are true. The application asks KMS for a data key and gets two things back: a plaintext key and an
encrypted copy of the same key. It encrypts the data locally with the plaintext key, wipes that from
memory, and stores the encrypted data next to the encrypted data key. To decrypt, it sends the encrypted
data key to KMS, gets the plaintext back and decrypts locally. So KMS never sees your data, the master
key never leaves the hardware module, and you make one KMS call per object rather than per byte. Every
AWS encryption-at-rest checkbox is doing exactly this for you.

**Q: What does a KMS key policy do that IAM does not?**
It is authoritative, which makes KMS unique. An account administrator with full administrator access has
no access to a key whose policy does not grant it — permissions cannot be added from the identity side
alone. The consequence people discover the hard way is that a key policy granting nobody anything is
unrecoverable without AWS support, which is why every key policy starts by delegating to IAM for the
account. It is worth knowing because it is the one place where "I'm an admin" is not the end of the
conversation.

**Q: What does automatic key rotation actually change?**
It creates new backing key material and retains the old. New encryptions use the new material; existing
ciphertexts are not re-encrypted, and the key id and ARN do not change, so nothing in your application
changes at all. That means rotation limits how much data is encrypted under any single piece of key
material — it does not undo a compromise of old material and it is not a substitute for re-encrypting if
you genuinely need to. If you need old data unreadable, the tool is disabling or deleting the key, which
is effectively crypto-shredding.

**Q: Secrets Manager or Parameter Store?**
Parameter Store for configuration and low-churn secrets, because standard parameters are free and
SecureString gives you KMS encryption anyway. Secrets Manager where you will actually rotate, because
rotation with the managed Lambda functions and the native RDS integration is the thing you are paying
forty cents a month per secret for. The test is simple: if you are never going to rotate it, you are
paying for a feature you do not use — which is the same point as saying a secret manager you never rotate
from is an expensive environment variable.

**Q: How do you rotate a database password without an outage?**
Alternating users. Two database users exist and the secret points at one of them; rotation changes the
password of the user that is not currently in use and then switches the secret to point at it. Both sets
of credentials are valid throughout, so cached values and open connections keep working — which matters
because clients cache secrets, and a cache TTL longer than the changeover window is exactly what breaks
single-user rotation. On the application side you still need to re-read without restarting, recycle the
connection pool since it holds authenticated connections, and retry an auth failure once after
refreshing. And you test it in staging under load on a schedule, because an untested rotation is an
untested backup.

## Mini task

1. ⭐⭐ Implement **envelope encryption by hand**: `GenerateDataKey`, encrypt locally, store both, decrypt.
   **Do not use a helper library.**
2. ⭐ Add **encryption context** and prove decryption fails when it does not match.
3. ⭐⭐ Write a key policy that **excludes an administrator** and confirm the admin is denied.
4. ⭐ Reference the key by **alias** everywhere, then swap the alias to a new key and confirm nothing in
   your code changed.
5. ⭐ Enable rotation, then **verify old ciphertexts still decrypt** and that the ARN is unchanged.
6. ⭐⭐ **Disable a CMK** and observe every object encrypted with it become unreadable. Re-enable it.
7. ⭐ Move static config to **Parameter Store** and compare the monthly cost with Secrets Manager.
8. ⭐⭐ Replace per-request `GetSecretValue` with the **caching client**. Measure the latency difference.
9. ⭐⭐ Set up **single-user rotation** for RDS and **prove it causes a brief outage under load.**
10. ⭐⭐ Switch to the **alternating-users strategy** and prove rotation now causes **zero** failed
    requests. This is the real exercise of the day.

## 🎙️ Articulation drill

**Two minutes:** *"How do you rotate a database credential with no downtime?"*

**⭐ Lead with why the naive version fails: change one password and every cached credential and open
pool becomes invalid at once, so every rotation is a small outage — which is why teams turn rotation
off.**

**⭐ Then the mechanism: two database users, the secret pointing at one; rotation changes the password of
the idle one and then switches the pointer, so both are valid throughout and cached secrets keep
working. The rotation function includes a `testSecret` stage that actually connects, so a broken rotation
fails before it is promoted. And the application still has to participate — re-read without restarting,
recycle the pool because it holds authenticated connections, and retry once after refresh.**

**⭐ Close with the standard that makes it true: we run it in staging under load on a schedule, because
an untested rotation is an untested backup.**
