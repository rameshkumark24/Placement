# Part 1 — ⭐ Dashboards that survive an incident

> **⭐ The test: can someone who did not build it answer "is this service healthy?" in five seconds
> without scrolling?** If not, the dashboard is decoration.

```
⭐ ┌─────────────────────────────────────────────────────┐
⭐ │ ⭐⭐ SLO BURN + error ratio  │ ⭐ p50/p95/p99 latency  │  ⭐ top row = the verdict
⭐ ├─────────────────────────────┼───────────────────────┤
⭐ │ request rate by endpoint    │ ⭐ SATURATION: pools,  │  ⭐ second row = the cause
⭐ │                             │   queues, threads     │
⭐ ├─────────────────────────────┴───────────────────────┤
⭐ │ dependencies: DB, cache, downstream — RED for each  │  ⭐ third row = whose fault
⭐ ├─────────────────────────────────────────────────────┤
⭐ │ ⭐ business metric (orders/min)  │ deploy annotations│  ⭐ ← ⭐⭐ "did a deploy do this?"
⭐ └─────────────────────────────────────────────────────┘
```

| ⭐ Rule | ⭐ Why |
|---|---|
| ⭐⭐ **Top-left is the most important panel** | ⭐ people read there first, under stress |
| ⭐ **Order: verdict → cause → blame → business** | matches how an incident is actually diagnosed |
| ⭐⭐ **Deploy annotations on every graph** | ⭐⭐ **"what changed?" answered visually in one second** |
| ⭐ **Template variables** | ⭐ one dashboard for every service and environment, not fifty copies |
| ⭐ Consistent units and axes | a p99 in ms next to one in seconds misleads |
| ⭐ **Linked from every alert** | the alert takes you to the right view (Part 3) |

⚠️ **Deploy annotations are the cheapest high-value feature in Grafana** and are routinely missing.
**Most incidents correlate with a change**, and a vertical line on the graph converts a twenty-minute
argument into a glance.

⚠️ **Resist the fifty-panel dashboard.** More panels mean slower loading, more Prometheus load, and
less chance anyone finds the one that matters. **Build one overview per service and separate deep
dashboards for investigation.**

# Part 2 — ⭐⭐ Burn-rate alerting, implemented

```
⭐ SLO: 99.9% of requests succeed over 30 days
⭐ ⇒ ⭐ error budget = 0.1% = ⭐ 43 minutes of failure per month

⭐ BURN RATE = current error rate ÷ the sustainable rate (0.001)
⭐   1×    ⇒ budget lasts exactly 30 days
⭐   ⭐ 14.4× ⇒ ⭐⭐ the entire month's budget is gone in ~2 hours ⇒ ⭐⭐ PAGE
⭐   ⭐ 6×    ⇒ gone in ~5 hours                                  ⇒ ⭐ page
⭐   ⭐ 3×    ⇒ gone in ~10 hours                                 ⇒ ⭐ ticket
⭐   ⭐ 1×    ⇒ on budget                                          ⇒ nothing
```

```yaml
⭐ - alert: HighErrorBudgetBurn
  expr: |
    ⭐ (job:error_ratio:5m  > 14.4 * 0.001)      ⭐ SHORT window — is it happening NOW?
    ⭐ and
    ⭐ (job:error_ratio:1h  > 14.4 * 0.001)      ⭐⭐ LONG window — is it SUSTAINED?
  for: 2m
  labels:   { severity: page }
  annotations:
    ⭐ runbook: https://…/runbooks/high-error-burn
    ⭐ dashboard: https://…/d/service-overview?var-service={{ $labels.job }}
```

| ⭐ Why two windows | |
|---|---|
| ⭐⭐ **Long window = signal** | a real problem, not a blip |
| ⭐⭐ **Short window = still true** | ⭐⭐ **stops the alert firing for an hour after recovery** |
| ⭐ Both must breach | ⭐ removes flapping without a long `for:` delaying real pages |

| ⭐ It beats static thresholds in both directions | |
|---|---|
| ⭐ **A 30-second 5% blip** | ⭐ barely dents the budget ⇒ **no page** — a static ">1%" rule would fire |
| ⭐⭐ **A 0.5% bleed for a week** | ⭐⭐ **exhausts the budget ⇒ pages** — a static ">1%" rule never fires |

> **⭐ That second row is the argument.** A slow bleed is the failure mode static thresholds are
> structurally incapable of catching, **and it is the one that quietly consumes a quarter's
> reliability.**

⚠️ **This requires an SLO, which requires choosing an SLI users actually feel** (Day 322). **You
cannot burn-rate alert on CPU** — there is no budget, because nobody experiences CPU.

# Part 3 — ⭐ Alertmanager, and what makes an alert actionable

| Feature | ⭐ Purpose |
|---|---|
| ⭐⭐ **Grouping** | ⭐⭐ **one incident, one notification — not forty pods paging separately** |
| ⭐ **Inhibition** | ⭐ a cluster-down alert suppresses every dependent service alert |
| ⭐ Routing | severity and team → the right destination |
| ⭐ **Silences** | ⭐ during planned work — **time-boxed, with a reason** |
| Repeat interval | re-notify if still firing and unacknowledged |

**⭐ Every alert must have four things, and an alert missing any of them should be deleted:**

```
⭐ 1. ⭐⭐ A RUNBOOK LINK       — what to check, what to do, how to escalate (Day 285)
⭐ 2. ⭐ A DASHBOARD LINK      — templated to the affected service
⭐ 3. ⭐⭐ AN OWNER             — a team, not "engineering"
⭐ 4. ⭐⭐ A USER IMPACT SENTENCE — "customers cannot complete checkout", not "cpu > 80%"
```

> **⭐ The impact sentence is the one that changes behaviour.** An alert that says what a user cannot
> do gets triaged correctly at 3am by someone who did not write it; **an alert naming a metric
> requires the responder to reconstruct the consequence before they can act.**

## ⭐ Symptom, not cause — restated with examples

| ⭐ Delete this | ⭐ Keep this |
|---|---|
| CPU > 80% | ⭐ **p99 latency above SLO** |
| A pod restarted | ⭐ error ratio burning budget at 14.4× |
| ⭐ Disk 70% full | ⭐⭐ **disk full in under 4 hours at the current rate** |
| Queue depth > 1000 | ⭐ **time-to-drain > 10 min and rising** (Day 333) |
| ⭐ A cache node down | ⭐ **cache hit rate below X and database load rising** |
| Heap usage > 75% | ⭐ **OOMKills occurring, or GC pause time above budget** |

**⭐ The pattern: causes are for dashboards, symptoms are for pages.** Keep the cause metrics —
you need them the moment you start investigating — **but do not wake anyone for them.**

# Part 4 — ⭐⭐ Alert fatigue is the real failure mode

```
⭐ 40 alerts a week, 3 of them real
⭐ ⇒ ⭐ responders start skimming
⭐ ⇒ ⭐⭐ a real page is acknowledged and not read
⭐ ⇒ ⭐⭐ THE PAGER NOW COSTS SLEEP AND PROVIDES NOTHING
```

| ⭐ Measure this about your alerts | ⭐ Target |
|---|---|
| ⭐⭐ **Alerts per on-call shift** | ⭐⭐ **under ~2 actionable pages per night, or the rotation burns out** |
| ⭐⭐ **% that led to an action** | ⭐⭐ **under 50% means half your pages are noise** |
| ⭐ % auto-resolved with no action | ⭐ **these should be tickets, not pages** |
| Time to acknowledge | rising = disengagement |
| ⭐ **Alerts never fired in 6 months** | ⭐ untested — **it may not work at all** |

> **⭐ The rule that fixes it: an alert that did not lead to action is a bug in the alert.** Fix the
> threshold, downgrade it to a ticket, or delete it. **Doing nothing is choosing to erode trust in
> every other alert you own.**

⚠️ **An alert that has never fired is not proof of stability — it is untested code.** Day 285's
requirement stands: **every alert should have fired at least once, deliberately if necessary**, so
you know the query is right and the routing works.

## ⭐ The operational rituals

| ⭐ Practice | |
|---|---|
| ⭐ **A weekly alert review** | ⭐ every page from the last week: real, noise, or missing a runbook? |
| ⭐ **On-call handover** | what is still open, what is silenced and why |
| ⭐⭐ **Silences must expire** | ⭐⭐ **a permanent silence is a deleted alert that still looks alive** |
| ⭐ Post-incident: was there an alert? | ⭐ if you found out from a customer, **that is the finding** |
| ⭐ **Alerts as code, reviewed** | ⭐ in the repo, versioned, diffable — never edited in a UI |

⚠️ **The most damaging alert configuration is a permanent silence.** The alert still appears in the
list, still looks like coverage, **and will never notify anyone again** — which is strictly worse than
deleting it, because it creates false confidence.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ A dashboard that needs scrolling to judge health | ⭐ nobody uses it under stress |
| ⭐⭐ **No deploy annotations** | ⭐⭐ "what changed?" takes twenty minutes instead of one second |
| ⭐ Fifty panels on one dashboard | slow, and the right panel is unfindable |
| ⭐ Copy-pasted dashboards per service | fifty things to update; use variables |
| ⭐⭐ **Static error thresholds** | ⭐⭐ blips page, slow bleeds do not |
| ⭐ A single-window burn alert | ⭐ keeps firing after recovery |
| ⭐ Burn-rate alerting on CPU | there is no budget; users do not feel CPU |
| ⭐ **Alerts with no runbook** | not actionable at 3am |
| ⭐ **No user-impact sentence** | the responder must reconstruct the consequence |
| ⭐ No grouping | ⭐ forty pods, forty pages |
| ⭐⭐ **Permanent silences** | ⭐⭐ false confidence — worse than deleting the alert |
| ⭐ Alerts that never fired | untested; may not work |
| Editing alerts in a UI | unreviewed, unversioned, undiffable |
| ⭐ Ignoring the actioned-percentage | ⭐ trust erodes until nothing is read |

## Interview questions

**Q: What makes a dashboard good?**
That someone who did not build it can answer "is this healthy?" in five seconds without scrolling.
Top-left is the verdict — SLO burn and error ratio — then latency, then saturation, then dependencies,
then a business metric. Deploy annotations on every graph, because most incidents correlate with a
change and a vertical line answers "what changed?" instantly. And template variables rather than fifty
copied dashboards.

**Q: How do you alert on reliability?**
On error-budget burn rate, not a static threshold. If the SLO is 99.9% over thirty days, the budget is
forty-three minutes, and burning at fourteen times the sustainable rate consumes it all in about two
hours — that pages. Three times over a longer window is a ticket. I use two windows, long for signal
and short to confirm it is still happening, which stops the alert firing for an hour after recovery
without a long delay on real pages.

**Q: Why is that better than "error rate above one percent"?**
It is better in both directions. A thirty-second five percent blip barely touches the budget, so it
does not page — a static rule would. And a half-percent bleed for a week exhausts the budget entirely,
so it does page — a static rule never fires at all. That slow bleed is the failure mode static
thresholds are structurally incapable of catching, and it is the one that quietly consumes a
quarter's reliability.

**Q: What must every alert have?**
A runbook link, a dashboard link templated to the affected service, a named owning team, and a
sentence describing user impact rather than a metric. The impact sentence is the one that matters —
"customers cannot complete checkout" gets triaged correctly by someone who did not write it, whereas
"cpu greater than eighty percent" makes the responder reconstruct the consequence before they can
act.

**Q: How do you know your alerting is working?**
By measuring the alerts themselves: pages per on-call shift, the percentage that led to an action, the
percentage that auto-resolved with nobody doing anything, and how many have never fired in six months.
Below fifty percent actioned means half the pages are noise and people are already skimming. An alert
that did not lead to action is a bug in the alert — fix it, downgrade it to a ticket, or delete it.
And an alert that has never fired is untested code, not evidence of stability.

## 🎙️ Articulation drill

**Three minutes:** *"Your team is getting forty pages a week and three are real. Fix it."*

**⭐ Do not start with tooling.** Start with the audit: **count pages, actioned percentage,
auto-resolved percentage** — that is the diagnosis. Then delete or downgrade everything under fifty
percent actioned, **replace cause-based alerts with symptom-based ones**, add grouping and inhibition
so one incident is one notification, and **move reliability alerting to multi-window burn rate.**

alert."** That single rule is what stops the list growing back, **because it makes deletion the
default rather than an exception.**
