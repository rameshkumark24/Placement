# Day 305 ⭐

**L-305** · ⭐ DDD II — aggregates, domain events, bounded contexts

**Time:** 3 hrs · **Mode:** NEW

> **⭐ One sentence carries this entire day: the aggregate is the consistency boundary, and therefore
> the transaction boundary, and therefore the lock boundary, and therefore the contention boundary.**
>
> Get it right and transactions are short, locks are narrow and invariants hold. Get it wrong and you
> get either corrupted data or a system that deadlocks under load — **and the mistake looks identical
> to a modelling preference until production.**

---

# Part 1 — ⭐⭐ The aggregate

**⭐ An aggregate is a cluster of objects treated as one unit for data changes, with one entity — the
root — as the only way in.**

```
   ┌─────────── Order (AGGREGATE ROOT) ───────────┐
   │   OrderId, Status, Money total               │  ⭐ only the root has a repository
   │   ┌────────────────────────────────────┐     │  ⭐ only the root is referenced from outside
   │   │  OrderLine  ×N   (inside)          │     │  ⭐ the whole thing loads and saves together
   │   └────────────────────────────────────┘     │  ⭐ ONE transaction, ONE version, ONE lock
   └──────────────────────────────────────────────┘
              │ ⭐ CustomerId  ← by ID only, never an object reference
              ▼
        [ Customer — a DIFFERENT aggregate ]
```

## ⭐ The four rules

| Rule | ⭐ Why |
|---|---|
| ⭐ **1. Protect true invariants inside one boundary** | ⭐ a rule spanning two aggregates cannot be transactionally enforced without locking both |
| ⭐ **2. Design SMALL aggregates** | ⭐ **large aggregates are the contention bug** — see Part 2 |
| ⭐ **3. Reference other aggregates by identity** | ⭐ stops accidental loading and accidental modification |
| ⭐ **4. Update other aggregates eventually** | ⭐ one transaction changes one aggregate; the rest follows by event |

**⭐ Rule 3 is the one people resist, and it is the highest-value one:**

```java
// ⭐ Wrong — an object reference across an aggregate boundary
class Order {
    @ManyToOne Customer customer;                 // ⭐ now you can do:
}
order.getCustomer().changeAddress(newAddress);    // ⭐ ← two aggregates changed in one transaction,
                                                  // ⭐   by code that thought it was editing an order
```

```java
// ⭐ Right — an identity reference
class Order {
    private final CustomerId customerId;          // ⭐ you literally cannot modify a customer from here
}
```

> **⭐ The `@ManyToOne` in your JPA entities is not the problem — the aggregate boundary having no
> representation in the code is.** Day 300's separate domain model is where this becomes real: the
> domain `Order` holds a `CustomerId`, and the `OrderEntity` in the adapter may hold whatever
> Hibernate needs.

## ⭐ How to find the boundary — three questions

1. ⭐ **What rule must be true at the instant a transaction commits?** *"An order's total equals the
   sum of its lines"* — total and lines are in one aggregate. *"A customer's lifetime spend equals
   the sum of their orders"* — **that one does not need to be instantaneously true**, so orders and
   customers are separate.
2. ⭐ **What is deleted together?** Delete an order, its lines go. Delete a customer, orders do not.
3. ⭐ **What does a user change in one action?**

> **⭐ Rule 1's real content: most "invariants" are not invariants.** They are reports that may lag by
> a second. **Every one you demote from "must be true now" to "must be true soon" makes the
> aggregate smaller, the transaction shorter and the system faster.** That trade is the central
> judgement of this day.

# Part 2 — ⭐⭐ The large-aggregate failure

**⭐ The textbook example, and it is real.** Model `Product` as a child of `Category`, because a
category "contains" products:

```java
class Category {                    // ⭐ AGGREGATE ROOT
    private List<Product> products; // ⭐ 40,000 of them
}
```

| Failure | ⭐ Mechanism |
|---|---|
| ⭐ **Every product edit loads 40,000 rows** | the aggregate loads whole (Day 160) |
| ⭐ **Every edit bumps ONE version column** | Day 165's optimistic locking, on the *category* |
| ⭐⭐ **Two people editing two different products conflict** | ⭐⭐ **`OptimisticLockException` — they changed nothing in common** |
| Transaction duration explodes | Day 194's vacuum, Day 196's lock queue |
| ⭐ Concurrency drops to **one writer per category** | ⭐ you have serialised 40,000 independent things |

**⭐ The fix is one line of modelling:** `Product` is its own aggregate root holding a `CategoryId`.
Now two edits touch two rows and two version columns, and they do not conflict.

> **⭐ This is why "design small aggregates" is a performance rule and not a purity rule.** The
> aggregate is the unit of contention. **Ask: how many concurrent writers does this boundary permit?**
> If the answer is one, and the real world has many, you have found the bottleneck before it exists.

**⭐ The counter-pressure, stated fairly:** small aggregates mean more eventual consistency, more
events, and rules that are briefly violated. **That is a genuine cost, and the answer is not always
"smaller".** The question is always: *does this rule have to be true at commit, or within a second?*

## ⭐ The root is the only door

```java
// ⭐ Wrong — reaching past the root
orderLineRepository.save(line);          // ⭐ the order's total is now inconsistent
order.getLines().add(newLine);           // ⭐ a mutable collection escaped

// ⭐ Right
order.addLine(productId, quantity, price);   // ⭐ recalculates the total; enforces max lines
orders.save(order);
```

**⭐ Two mechanical requirements**, both easy to forget:

- ⭐ **Collections are exposed as `List.copyOf(lines)`** or not at all (Day 034A). A leaked mutable
  collection defeats the whole design in one line.
- ⭐ **One repository per aggregate root** — Day 301's rule, now with its justification: extra
  repositories are extra doors past the invariants.

# Part 3 — ⭐ Domain events

**⭐ Rule 4 needs a mechanism.** When one transaction may change one aggregate, everything else
happens afterwards:

```java
public final class Order {
    private final List<DomainEvent> events = new ArrayList<>();

    public void ship(Instant when) {
        if (status != PAID) throw new OrderNotPayable(id, status);
        this.status = SHIPPED;
        this.shippedAt = when;
        events.add(new OrderShipped(id, customerId, when));   // ⭐ recorded, not published
    }

    public List<DomainEvent> pullEvents() {                   // ⭐ drained by the application service
        var copy = List.copyOf(events); events.clear(); return copy;
    }
}
```

| ⭐ Property | ⭐ Why it matters |
|---|---|
| ⭐ **Past tense, always** | ⭐ `OrderShipped`, not `ShipOrder` — an event is a fact, a command is a request |
| ⭐ **Recorded inside, published outside** | the domain has no publisher dependency (Day 300) |
| ⭐ **Immutable, with an occurred-at** | it is history |
| ⭐ **Carries ids, not object graphs** | ⭐ rule 3, again — and it keeps the payload stable |

**⭐ Delivery — and this is where designs quietly break (Day 179, Day 263):**

| Approach | ⭐ Guarantee |
|---|---|
| ⭐ Publish in-process, same transaction | ⭐ **atomic, but a slow handler extends your transaction** |
| ⭐ `@TransactionalEventListener(AFTER_COMMIT)` | ⭐ **the handler may never run — the process can die between commit and handler** |
| ⭐⭐ **Outbox table, written in the same transaction** | ⭐⭐ **at-least-once, actually reliable** (Day 124, Day 263) |

> **⭐ Say the failure out loud in interviews: `AFTER_COMMIT` is not delivery.** It is the right
> default for things that may be lost — a cache eviction, a metric. **It is wrong for anything a user
> or another system depends on**, and the outbox is the fix, at the price of a table and a poller.

## ⭐ Eventual consistency, and the compensating action

**⭐ If the second aggregate's update fails, there is no rollback** — the first transaction committed.
Three answers, and you should name which you chose:

| Answer | ⭐ When |
|---|---|
| ⭐ **Retry until it succeeds** | ⭐ handler is idempotent (Day 122) — the usual answer |
| ⭐ **Compensating action** | ⭐ payment captured but stock gone → refund. This is the Saga (Stage 9) |
| ⭐ **Accept the inconsistency** | a report is briefly stale — often entirely fine |

# Part 4 — ⭐ Bounded contexts

**⭐ The strategic half of DDD, and the more valuable one.** A bounded context is a boundary within
which a term has exactly one meaning.

```
   ⭐ "Customer" means four different things:

   Sales        │ Support        │ Billing         │ Shipping
   ─────────────┼────────────────┼─────────────────┼──────────────
   lead source  │ ticket history │ tax id          │ address
   pipeline     │ SLA tier       │ payment method  │ delivery notes
   deal size    │ satisfaction   │ credit limit    │ access codes
```

**⭐ The wrong answer is one shared `Customer` class with forty fields, which is what "reuse" produces
— and it couples four teams to one type forever.** The right answer is four `Customer` types, one per
context, linked by a shared identifier.

> **⭐ This is the single most counter-intuitive idea in DDD: deliberate duplication of a concept is
> correct.** Not duplicated *code* — duplicated *concept*, because they are genuinely different
> things that share a name and an id.

## ⭐ Context relationships, and the one that matters

| Pattern | Meaning |
|---|---|
| ⭐ **Shared kernel** | a small shared model, changed only by agreement — ⭐ keep it tiny |
| **Customer/Supplier** | downstream needs influence upstream's roadmap |
| **Conformist** | downstream just accepts the upstream model |
| ⭐⭐ **Anti-corruption layer** | ⭐⭐ **you translate at the boundary and never let their model in** |
| Published language | a versioned contract between both (Day 109, Day 110) |

```java
// ⭐ The ACL — the pattern that pays for itself against every legacy system and vendor
class LegacyCustomerAdapter implements Customers {
    public Customer byId(CustomerId id) {
        LegacyCustRec rec = soapClient.getCust(id.value());   // ⭐ their model stops HERE
        return new Customer(id, new EmailAddress(rec.getEml()),  // ⭐ your model starts here
                            CreditLimit.of(rec.getCrLim(), rec.getCcy()));
    }
}
```

**⭐ Without an ACL, the legacy system's field names, null semantics and 1980s abbreviations spread
through your codebase** — and you inherit their model permanently. **With one, the damage is one
class**, and that class is where you write the comment explaining what `crLim` means.

**⭐ And the practical payoff: a bounded context is a module (Day 306) and, if it must be, a service
(Stage 9).** Bounded contexts are the only *principled* place to cut a monolith. Cutting anywhere
else produces distributed transactions and chatty calls — **which is the actual reason most
microservice migrations fail.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Large aggregates | ⭐⭐ **one writer per boundary; unrelated edits collide** |
| ⭐ Object references across aggregates | ⭐ two aggregates modified in one transaction, by accident |
| ⭐ A repository per child entity | ⭐ doors past the invariants (Day 301) |
| Exposing a mutable child collection | the root's rules are advisory |
| ⭐ Treating a report as an invariant | ⭐ **an oversized aggregate for a rule that could lag a second** |
| ⭐ Present-tense event names | commands and events conflated |
| Events carrying whole object graphs | payload coupling; stale data |
| ⭐ `AFTER_COMMIT` for critical work | ⭐ **it is not delivery — a crash loses it** |
| No compensating action named | inconsistency with no plan |
| ⭐ One shared `Customer` across four contexts | ⭐ **forty fields, four teams, one type** |
| ⭐ Integrating without an ACL | ⭐ the vendor's model becomes yours, permanently |
| Splitting services on anything but contexts | distributed transactions and chatty calls |

## Interview questions

**Q: What is an aggregate and how do you find the boundary?**
A cluster of objects changed as one unit, with a root as the only entry point. I find it by asking
what must be true the instant a transaction commits — an order's total matching its lines, yes; a
customer's lifetime spend matching their orders, no, that can lag. What is deleted together, and what
a user changes in one action, are the other two questions. Most candidate invariants turn out to be
reports, and demoting them makes the aggregate smaller.

**Q: Why do small aggregates matter?**
Because the aggregate is the unit of contention, not just of consistency. If `Category` contains
40,000 products, every product edit loads them all and bumps one version column, so two people
editing two different products get an optimistic lock failure despite sharing nothing. Making
`Product` its own root with a `CategoryId` turns one writer per category into one writer per product.
It is a throughput decision disguised as a modelling decision.

**Q: How do you update two aggregates?**
One transaction changes one aggregate; the second is updated afterwards via a domain event. That
means eventual consistency, so I name the failure plan: retry with an idempotent handler, a
compensating action if the effect is externally visible, or explicit acceptance if it is only a
stale report. And I use an outbox rather than `AFTER_COMMIT` for anything that must not be lost —
`AFTER_COMMIT` runs after the commit succeeded, so a crash in between loses the event silently.

**Q: What is a bounded context, and why not have one shared model?**
A boundary in which a term has exactly one meaning. `Customer` in sales, support, billing and
shipping share only an id — the fields, rules and lifecycles differ. A shared class becomes forty
fields owned by four teams, and every change is cross-team. Deliberate duplication of the concept is
correct here, which is counter-intuitive but is what keeps the contexts independent.

**Q: What is an anti-corruption layer?**
A translation boundary in front of a system whose model you do not want — a legacy service, a vendor
API. You convert into your own types at the edge, so their field names, null semantics and
abbreviations never spread. Without it you inherit their model permanently; with it the damage is one
class, which is also the one place worth documenting what their fields actually mean.

## Mini task

1. **Draw your flagship's aggregates.** For each, write the invariant that justifies the boundary.
   **Any aggregate with no invariant should be split.**
2. ⭐ **Find your largest aggregate and ask: how many concurrent writers does it permit?** If the
   answer is one and reality has many, split it and **prove it with a concurrent test.**
3. Reproduce the contention bug: two threads updating two different children of one root under
   optimistic locking. **Watch one fail.** Split the aggregate; re-run; both succeed.
4. Replace one cross-aggregate object reference with an id. **Find every place that was traversing
   it** — each was a hidden second-aggregate write.
5. Record a domain event in the aggregate and drain it in the application service. **Make the
   handler throw, and observe that the first transaction still committed.**
6. ⭐ Move that event to an **outbox** (Day 263). **Kill the process between commit and handler** and
   confirm the event still gets delivered. Then do the same with `AFTER_COMMIT` and lose it.
7. ⭐ Take one term with two meanings in your system and **write both definitions.** Split the class.
8. Write an **ACL** for one external integration. List every foreign concept it stopped.

boundaries."*

**⭐ Two markers.** First — **you justify each boundary with an invariant that must hold at commit,
and you explicitly demote one candidate rule to eventual consistency, out loud.** Second — **you

actually learn this rule — after the `OptimisticLockException`s start.
