>

# Part 1 — ⭐ The dashboard, in three tiers

**⭐ One dashboard, read top to bottom, answering three questions in order.**

### ⭐ Tier 1 — Is it working? (RED, Day 128)

```
⭐ Request rate · ⭐ Error rate (4xx and 5xx SEPARATED) · ⭐ Latency p50/p95/p99
```

**⭐ Separate 4xx from 5xx.** A rising 4xx rate is usually a client change or an attack; a rising 5xx
rate is you. **Combining them means neither signal is readable.**

### ⭐ Tier 2 — Is the business working?

```
⭐ bookings_created_total · booking_conflicts_total · uploads_completed_total
⭐ refresh_token_reuse_detected_total · outbox_oldest_unpublished_age
```

> **⭐ Business metrics are what make a project look operated rather than deployed.**
> `booking_conflicts_total` is your hard problem, observable in production — **"I can show you how
> often the concurrency guard actually fires" is a very strong thing to say.**

**⭐ And a business metric detects outages that technical metrics miss**: bookings dropping to zero
while every technical metric is green means something is broken in a way no health check covers.

### ⭐ Tier 3 — Why? (USE, Day 128)

```
⭐ hikaricp_connections_pending   ← ⭐⭐ THE most diagnostic number (Day 156)
⭐ JVM heap, GC pause time · Tomcat busy threads
⭐ Redis hit ratio and evictions · ⭐ CPU throttling (Day 284)
⭐ Circuit-breaker state (Day 181) · ⭐ Replication lag (Day 201)
```

**⭐ `connections_pending` above zero means the pool is the bottleneck** — either not enough
connections or queries holding them too long. **It is the first number to look at when everything is
slow and CPU is idle.**

# Part 2 — ⭐⭐ Alerts — few, actionable, and tested

> **⭐⭐ Alert on symptoms users feel, not on causes.** "CPU is 80%" is not an alert; "the error rate
> is above 1%" is.

**⭐ The rule that keeps alerting useful:**

> **⭐⭐ Every alert must be actionable. If the response is "watch it", it is a dashboard, not an
> alert.** Alert fatigue is how the real one gets ignored.

### ⭐ The alerts your project needs

| Alert | ⭐ Why |
|---|---|
| ⭐ **Error rate > 1% for 5 min** | users are affected |
| ⭐ **p99 > SLO for 10 min** | ⭐ your Day 249 number, finally enforced |
| ⭐ **Health check failing** | the service is down |
| ⭐ **`connections_pending` > 0 for 5 min** | ⭐ pool saturation |
| ⭐ **`outbox_oldest_unpublished_age` > 5 min** | ⭐ the poller is stuck (Day 263) |
| ⭐ **`outbox_dead_lettered_total` > 0** | ⭐ an effect that never happened |
| ⭐⭐ **A job has not succeeded in N hours** | ⭐⭐ **the alert nobody writes** (Day 264) |
| ⭐ **Circuit breaker opened** | ⭐ a dependency is failing and you are degrading |
| ⭐ **`refresh_token_reuse_detected` > 0** | ⭐ credential theft (Day 258) |
| ⭐ **Disk > 80%, certificate expiring < 14 days** | slow-moving, entirely preventable |
| ⭐ **`age(datfrozenxid)` > 50%** | ⭐ wraparound (Day 194) — slow, and ends in a refused-write outage |

**⭐ Two of these deserve emphasis:**

- ⭐ **The job non-execution alert** (Day 264): a failing job is noisy and gets noticed; **a job that
  silently stopped is invisible for weeks.**
- ⭐ **The reuse-detection alert** (Day 258): one of the highest-signal security events you can emit,
  and almost no project has any security alerting at all.

### ⭐⭐ Test every alert by making it fire

```
⭐⭐ An untested alert is a hope. MOST untested alerts do not work.
```

**⭐ Break each condition deliberately and confirm the notification arrives** — wrong threshold, wrong
label, wrong routing, notification channel misconfigured. **All four are common and all four are
silent.**

**⭐ Then record for each: the time from cause to notification.** That is your detection time, and it
is half of your incident duration.

# Part 3 — ⭐ Runbooks, and the two-minute test

```markdown
## ⭐ Alert: connections_pending > 0
⭐ Means:  requests are queued for a database connection.
⭐ Impact: latency climbing on every endpoint, ⭐ including those not touching the database.
⭐ Check:  1. pg_stat_activity — long-running queries? idle in transaction?
          2. hikaricp_connections_active — at max?
          3. Recent deploy? A new slow query?
⭐ Do:     Kill the blocking query (pg_cancel_backend). If a deploy caused it, roll back.
⭐ Escalate: if the pool is saturated with fast queries, capacity is the issue.
```

**⭐ Every alert needs one.** Five lines is enough, and **writing them now — while you remember why
each alert exists — is far easier than at 3 a.m.**

**⭐ An alert with no runbook wakes someone who must then reconstruct the system's behaviour from
scratch**, which is how a ten-minute incident becomes an hour.

## ⭐⭐ The two-minute drill

> **⭐⭐ "A customer saw an error at 3pm." Can you find it in under two minutes?**

```
⭐ 1. The customer quotes a correlation ID from the error response   (Day 149)
⭐ 2. One query in your log store → ⭐ the exact request, stack trace, user and tenant
⭐ 3. The trace id → ⭐ the waterfall showing WHERE the time went     (Day 182)
```

**⭐ Practise this today, timed.** Trigger a real 500 in the deployed instance, take the ID from the
response, and find the log line. **If that takes more than two minutes, something in Day 182's chain
is missing** — usually the MDC field is not indexed, or the async path lost the ID.

**⭐ Then do the harder version**: find a request that was slow rather than failed. That requires
tracing, and it is the thing that separates "we have logs" from "we are observable".

# Part 4 — ⭐ SLOs, log cost, and the incident you write up

## ⭐ SLOs and error budgets

```
⭐ Availability: 99.5% → ⭐ 3.6 hours/month of error budget
⭐ Latency:      p99 < 500ms for 99% of requests
```

**⭐ The error budget is what makes an SLO useful**: it converts "be reliable" into a number you can
spend. **Budget remaining → ship features. Budget exhausted → stop and fix reliability.**

**⭐ Track burn rate, not just the total.** Burning a month's budget in an hour is an incident;
burning it evenly is a capacity conversation.

## ⭐ Log cost and retention

```
⭐ INFO in production — ⭐ NEVER DEBUG (Day 182)
⭐ Raise a package to DEBUG for ten minutes via /actuator/loggers during an incident
⭐ ⭐ Tiered retention: 7 days INFO, ⭐ 1 year for errors and audit
⭐ Sample high-volume routine events
```

**⭐ Estimate your monthly log volume and cost today.** It is a real engineering constraint, and
**"DEBUG left on just in case" costs a fortune, slows the application, and buries the lines that
matter.**

**⭐ And check the scrubbing** (Day 182): search your log store for `password`, `Bearer `, and a
customer email. **Finding one is the point of the exercise** — then add the scrubbing converter.

## ⭐⭐ Write up one incident

**⭐ Cause one deliberately** — Day 286's subject — **and write a blameless postmortem:**

```markdown
⭐ Summary · ⭐ Impact (users affected, duration) · ⭐ Timeline (detection → mitigation → resolution)
⭐ Root cause (the five whys) · ⭐ What went well · ⭐ What did not
⭐ Action items — ⭐ with owners
```

> **⭐⭐ A postmortem in your repository is one of the strongest artefacts this project can contain.**
> It demonstrates that you have operated the system, not merely built it — **and "tell me about a
> time something broke" becomes a document you can point at.**

**⭐ The most valuable line is usually "how long until we detected it?"**, because that number is
what your alerting is actually for.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Alerting on causes not symptoms | ⭐ noise; the real alert is ignored |
| ⭐ Alerts that are not actionable | alert fatigue |
| ⭐ **Untested alerts** | ⭐ **most do not work** |
| ⭐ No runbooks | ⭐ a ten-minute incident becomes an hour |
| ⭐ **No job non-execution alert** | ⭐ a stopped job is invisible for weeks |
| ⭐ No security alerting | credential theft goes unnoticed |
| Combining 4xx and 5xx | neither signal is readable |
| ⭐ No business metrics | ⭐ outages that technical metrics miss |
| ⭐ Correlation ID not queryable | the two-minute drill fails |
| ⭐ The ID lost across async boundaries | Day 265's decorator is broken |
| ⭐ DEBUG in production | cost, latency, noise |
| Uniform trace sampling | ⭐ the traces you need are the ones dropped (Day 182) |
| ⭐ Secrets or PII in logs | a breach in your log store |
| No SLO | reliability is a feeling |
| ⭐ Never writing a postmortem | the strongest artefact, unwritten |
