# Day 335

**L-335** · Delivery semantics — why exactly-once is a lie, and what to build instead

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Exactly-once delivery is impossible. Exactly-once processing is straightforward. The gap
> between those two sentences is the entire topic.**
>
> Say the first one in an interview and you have already distinguished yourself from most
> candidates — **provided you immediately follow it with the second, and the mechanism.**

---

# Part 1 — ⭐⭐ The three semantics, and the impossibility

| Semantic | ⭐ Mechanism | ⭐ Failure |
|---|---|---|
| ⭐ **At-most-once** | ⭐ acknowledge **before** processing | ⭐ **crash after ack → message lost** |
| ⭐ **At-least-once** | ⭐ acknowledge **after** processing | ⭐ **crash before ack → message redelivered** |
| ⭐ **Exactly-once (delivery)** | ⭐⭐ **does not exist** | — |

```
⭐ WHY IT CANNOT EXIST — the two generals, concretely:

⭐ Consumer processes the message. Sends the ack. The network drops the ack.
⭐ ⇒ The broker cannot distinguish "processed, ack lost" from "never processed".
⭐ ⇒ It must choose: redeliver (⭐ at-least-once) or not (⭐ at-most-once).
⭐ ⇒ ⭐⭐ There is no third option. Adding another acknowledgement just moves the problem.
```

> **⭐ The resolution, stated as one sentence: at-least-once delivery plus an idempotent consumer
> gives you effectively-once processing.** That is what every system claiming exactly-once actually
> does, **including Kafka's** — and knowing that is the difference between quoting a feature and
> understanding it.

⚠️ **Choose at-most-once only when loss is genuinely cheaper than duplication** — a metrics sample, a
best-effort presence ping. **For anything a user or a ledger depends on, at-least-once is the only
defensible default.**

---

# Part 2 — ⭐⭐ Making the consumer idempotent — four mechanisms

## ⭐ 1. Naturally idempotent operations — free, and the best option

```
⭐ SET status = 'SHIPPED'          ⭐ idempotent — run it ten times, same result
⭐ balance = balance - 50          ⭐⭐ NOT idempotent — ten times is a disaster
⭐ INSERT ... ON CONFLICT DO NOTHING  ⭐ idempotent
```

**⭐ Design the operation to be idempotent before reaching for machinery.** Absolute assignments are
idempotent; relative modifications are not. **Where a delta is unavoidable, carry the expected prior
state or a version and make it conditional** — which is Day 316's conditional update, again.

## ⭐ 2. Deduplication by message id

```java
if (!processed.add(messageId)) return;   // ⭐ already handled — skip
process(message);
```

| ⭐ Problem | ⭐ Answer |
|---|---|
| ⭐ **The dedup store grows forever** | ⭐ TTL it — **but the TTL must exceed your maximum redelivery window** |
| ⭐⭐ **Two operations, not one** | ⭐⭐ **crash between "mark processed" and "process" loses the message; crash the other way duplicates it** |
| Scale | one lookup per message |

⚠️ **The second row is the flaw people miss.** Dedup-then-process is not atomic, **so you have simply
moved the problem.** It is acceptable when the window is small and the operation is cheap to retry —
**but the next mechanism is strictly better.**

## ⭐⭐ 3. Dedup inside the same transaction — the correct answer

```java
@Transactional
public void handle(Message msg) {
    // ⭐ The dedup record and the business change COMMIT TOGETHER — atomically
    int inserted = jdbc.update(
        "INSERT INTO processed_messages(id) VALUES (?) ON CONFLICT DO NOTHING", msg.id());
    if (inserted == 0) return;                    // ⭐ already processed — same transaction, safe
    applyBusinessChange(msg);                     // ⭐ same transaction
}
```

> **⭐ This is the whole answer, and it fits in ten lines.** Because the dedup marker and the effect
> share a transaction, **there is no window in which one exists without the other.** A redelivery
> after a crash finds no marker and reprocesses; a redelivery after success finds the marker and
> stops. **Say "the dedup key and the side effect commit in the same transaction" and you have
> demonstrated the point of the whole day.**

## ⭐ 4. Idempotency keys at the API boundary

**⭐ For external effects — charging a card, sending an SMS — the key travels to the third party**
(Day 122). `Idempotency-Key: <uuid>` on the payment request, and **the provider deduplicates on their
side.** Without that, your transaction cannot protect an effect that happens elsewhere.

⚠️ **The genuinely unsolvable case, worth naming: side effects with no idempotency support.** An SMS
gateway with no key means at-least-once produces duplicate texts. **The honest answer is "I record
that I sent it before sending, accept a small chance of loss on crash, or accept duplicates — and I
choose per message which is worse."**

# Part 3 — ⭐ What Kafka's "exactly-once" actually covers

```
⭐ COVERED:     consume from topic A → transform → produce to topic B → commit offset
⭐              ⭐ all atomic, because offsets are written to Kafka as part of the transaction

⭐ NOT COVERED: consume → ⭐ write to PostgreSQL → commit offset
⭐              ⭐⭐ two systems, no shared transaction — you are back to at-least-once
```

| ⭐ Feature | ⭐ Scope |
|---|---|
| Idempotent producer | ⭐ de-duplicates **producer retries** within a partition |
| ⭐ Transactions (`transactional.id`) | ⭐ atomic across **Kafka** topics and offsets |
| ⭐ `read_committed` consumers | do not see uncommitted transactional messages |
| ⭐⭐ **External side effects** | ⭐⭐ **not covered — this is the important line** |

> **⭐ So the answer to "does Kafka give exactly-once?" is: within Kafka, effectively yes, for
> stream processing. The moment you write to a database, call an API or send an email, you are back
> to at-least-once and you need idempotency.** That precision is what interviewers are listening
> for.

**⭐ The producer side has a mirror problem, and it is Day 263's outbox:** writing to your database
and publishing to Kafka are two systems. **A crash between them loses the event or emits one for a
transaction that rolled back.** The outbox — write the event into a table in the same transaction,
publish from there — is the fix, and it is at-least-once by construction.

# Part 4 — ⭐⭐ Ordering versus retries — the conflict nobody mentions

```
⭐ Partition ordered: [ m1, m2, m3, m4 ]
⭐ m2 fails. Now what?

⭐ (a) Block and retry m2      ⭐⭐ head-of-line blocking — the partition stops. Ordering preserved.
⭐ (b) DLQ m2, continue        ⭐⭐ throughput preserved. ORDERING BROKEN for that key.
⭐ (c) Retry topic per key     ⭐ ordering preserved per key; complex
```

| ⭐ Choose | ⭐ When |
|---|---|
| ⭐ **Block** | ⭐⭐ **ordering is a correctness requirement** — a balance, a state machine. **Alert loudly, because the partition is stalled** |
| ⭐ **DLQ and continue** | ⭐ ordering is a nicety; throughput matters more |
| ⭐ Per-key retry queue | ⭐ **you need both** — park the key, let others flow |

> **⭐ The trap: teams enable a DLQ for resilience without noticing they have silently given up the
> ordering guarantee they designed the keys for.** If order events must be applied in order and one
> is dead-lettered, **the next one applies to a state that never happened.** Naming this trade
> explicitly is the mark of someone who has run a keyed consumer in production.

⚠️ **And the sequencing defence: make handlers order-tolerant where you can.** If the event carries a
version or timestamp, a handler that ignores anything older than what it has already applied is
**robust to both reordering and duplication** — which is Day 331's monotonic-writes guarantee,
implemented in the consumer.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ Claiming exactly-once delivery | ⭐⭐ **it does not exist; the follow-up ends the round** |
| ⭐ At-most-once for anything that matters | silent loss |
| ⭐ Relative updates in a consumer | ⭐ **a redelivery double-charges** |
| ⭐⭐ Dedup outside the transaction | ⭐⭐ **the gap between marking and doing is the bug** |
| A dedup store with no TTL | unbounded growth |
| ⭐ A TTL shorter than the redelivery window | duplicates get through |
| ⭐ Relying on Kafka EOS for database writes | ⭐ **not covered — two systems** |
| ⭐ Publishing to a broker inside a database transaction | the dual-write problem; use an outbox |
| ⭐⭐ Enabling a DLQ on a keyed, ordered stream | ⭐⭐ **ordering silently abandoned** |
| Blocking retries with no alert | the partition stalls invisibly |
| No version/timestamp on events | handlers cannot be made order-tolerant |

## Interview questions

**Q: Can you guarantee exactly-once delivery?**
No — it is impossible. The consumer processes a message and acknowledges; if the acknowledgement is
lost, the broker cannot distinguish "processed but ack lost" from "never processed", so it must
either redeliver or not. What is achievable is exactly-once processing: at-least-once delivery plus
an idempotent consumer, which is what every system claiming exactly-once actually implements.

**Q: How do you make a consumer idempotent?**
First by design — absolute assignments are naturally idempotent, relative ones are not, so I make the
operation conditional or carry the expected prior version. Where I need a marker, I insert the
message id and apply the business change in the same transaction, so there is no window where one
exists without the other. Dedup-then-process as two steps just moves the problem to a smaller
window.

**Q: Doesn't Kafka provide exactly-once?**
Within Kafka. Its transactions make consume-transform-produce atomic including the offset commit,
because the offsets live in Kafka. The moment the side effect is external — a database write, a
payment API, an email — there is no shared transaction and you are back to at-least-once with an
idempotent handler. The producer side has the mirror problem, which is why the outbox pattern exists.

**Q: A message keeps failing on an ordered partition. What do you do?**
It is a genuine trade. Blocking and retrying preserves ordering but stalls the partition, so it needs
a loud alert. Dead-lettering it preserves throughput but breaks the ordering guarantee I designed
the keys for — the next event for that entity applies to a state that never happened. If I need both,
a per-key retry queue parks that key while others flow. The mistake I want to avoid is enabling a DLQ
for resilience and silently losing ordering.

**Q: What about an SMS gateway with no idempotency support?**
Then exactly-once is genuinely unavailable and the choice is explicit: record that I sent before
sending and accept a small chance of loss on a crash, or record after and accept occasional
duplicates. I choose per message class which is worse — a duplicate marketing message is fine, a
duplicate one-time passcode is not — and I document it rather than pretending the problem is solved.

## Mini task

1. Build an at-least-once consumer that does `balance = balance - amount`. **Redeliver a message and
   watch the balance go wrong.**
2. ⭐ Fix it with a **dedup insert plus the business change in one transaction.** Redeliver 100 times
   and assert the balance is correct.
3. ⭐ Implement dedup **outside** the transaction, then **kill the process in the gap.** Reproduce
   both failure directions — a lost message and a duplicate.
4. Set the dedup TTL **shorter** than the redelivery window and reproduce a duplicate getting
   through.
5. ⭐ Use Kafka transactions for consume-transform-produce and confirm atomicity. **Then add a
   PostgreSQL write and demonstrate that it is not covered.**
6. Implement the **outbox** on the producer side (Day 263) and kill the process between commit and
   publish. **Confirm the event still arrives.**
7. ⭐⭐ On a keyed ordered topic, **dead-letter one message and demonstrate the resulting incorrect
   state.** Then implement blocking retry with an alert, and a per-key retry queue.
8. ⭐ Add a version to your events and make one handler **order-tolerant.** Deliver events shuffled
   and duplicated, and **assert the final state is correct.**

## 🎙️ Articulation drill

**Two minutes:** *"How do you guarantee a payment is only charged once?"*

**⭐ The answer has four beats and they must be in this order.** Exactly-once delivery is impossible,
so the design is at-least-once plus idempotency · **the idempotency key and the charge record commit
in the same database transaction** · the key is also passed to the payment provider, because their
side effect is outside my transaction · and the operation is written as a conditional update rather
than a decrement.

**⭐ Candidates who answer "Kafka gives exactly-once" get one follow-up — "and the database write?" —
and have nothing.**
