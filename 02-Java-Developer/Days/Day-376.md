# Day 376

**L-376** · Distributed tracing with OpenTelemetry

**Time:** 3 hrs · **Mode:** NEW

> **⭐ Metrics tell you that p99 got worse. Logs tell you what one service said. Only a trace tells
> you where the four hundred milliseconds went across six services — and that is a question the other
> two cannot answer at all.**
>
> The theory is short. **The parts that decide whether tracing is useful are sampling, propagation
> through queues, and whether anyone can get from an alert to a trace in one click.**

---

# Part 1 — ⭐ The model

```
⭐ TRACE = one request's whole journey. ⭐ SPAN = one operation within it.
⭐
⭐ trace 4bf92f…
⭐ ├─ span: POST /orders            [gateway]    420 ms
⭐ │  ├─ span: POST /orders         [orders]     405 ms
⭐ │  │  ├─ span: SELECT customers  [postgres]     8 ms
⭐ │  │  ├─ span: POST /authorize   [payments]  ⭐ 340 ms  ⭐⭐ ← there it is
⭐ │  │  │  └─ span: HTTP stripe.com          ⭐ 335 ms
⭐ │  │  └─ span: INSERT orders     [postgres]    12 ms
⭐ │  └─ span: publish OrderPlaced  [kafka]        3 ms
```

| ⭐ Concept | |
|---|---|
| ⭐ **Trace id** | ⭐ the same across every service — **the join key for logs too** (Day 375) |
| ⭐ Span id + parent span id | builds the tree |
| ⭐ **Attributes** | ⭐ `http.status_code`, `db.statement`, `order.id` — **searchable dimensions** |
| ⭐ **Events** | timestamped points inside a span — an exception, a cache miss |
| ⭐ Span kind | server, client, producer, consumer, internal |

> **⭐ The value proposition in one line: a trace shows you the *specific* slow request, not the
> aggregate.** A p99 tells you 1% of requests are slow; **a trace of one of them tells you which
> downstream call it was, with the exact statement and the exact 335 milliseconds.**

## ⭐ Context propagation

```
⭐ W3C standard header, sent on every hop:
⭐   traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
⭐                 └ver └────── trace id ──────────┘ └── span id ───┘ └flags(sampled)
```

**⭐ It is a header, and that is all.** Every hop reads it, creates a child span, and passes a new
one downward. **Losing it anywhere breaks the trace into disconnected fragments** — which is what
makes the queue case in Part 3 matter.

# Part 2 — ⭐ OpenTelemetry, and the free start

| ⭐ Component | ⭐ What it is |
|---|---|
| ⭐ **API** | what your code calls — stable, vendor-neutral |
| ⭐ **SDK** | the implementation: sampling, batching, exporting |
| ⭐ **Instrumentation** | ⭐ libraries that trace Spring, JDBC, Kafka, HTTP clients automatically |
| ⭐⭐ **Collector** | ⭐⭐ a separate process that receives, processes and exports — **see below** |
| ⭐ OTLP | the wire protocol |

```bash
⭐ THE ZERO-CODE START — genuinely this short:
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=orders \
     -Dotel.exporter.otlp.endpoint=http://collector:4317 \
     -jar app.jar
⭐ ⇒ ⭐ Spring MVC, JDBC, Hikari, RestClient, Kafka, Redis — ⭐⭐ ALL traced, no code changes.
```

> **⭐ Start with the agent.** It produces a genuinely useful trace of every framework boundary before
> you write a line, **and the manual spans you add afterwards are for business operations the
> framework cannot see** — "risk evaluation", "invoice generation" — not for re-tracing what the
> agent already covers.

## ⭐⭐ Why the Collector exists

```
⭐ app ──OTLP──► ⭐ COLLECTOR ──► backend(s)
⭐                    ⭐ batch · retry · ⭐ REDACT · ⭐ TAIL-SAMPLE · enrich · fan out
```

| ⭐ Benefit | |
|---|---|
| ⭐⭐ **Applications do not know the backend** | ⭐⭐ **change vendors by editing collector config, not 40 services** |
| ⭐ **Redaction in one place** | ⭐ strip a token that appeared in a URL attribute |
| ⭐⭐ **Tail sampling** | ⭐⭐ **only possible centrally — the app cannot know the trace was slow** |
| Batching and retry | the application stays fast and unaware |
| Enrichment | add cluster, region, deployment metadata |

⚠️ **Without a Collector, sampling decisions must be made in each application at the start of a
request** — which is precisely the head-based sampling that keeps the boring traces (Day 338). **The
Collector is what makes the good sampling strategy possible at all.**

# Part 3 — ⭐⭐ Sampling, and the two hard cases

## ⭐ Head vs tail, restated with the numbers

| | ⭐ Head-based | ⭐⭐ Tail-based |
|---|---|---|
| Decides | ⭐ at the first span | ⭐⭐ **after the trace completes** |
| Keeps | ⭐ a random 1% | ⭐⭐ **100% of errors, 100% over p99, ~0.1% of the rest** |
| ⭐ Cost | low | ⭐ the Collector buffers every trace until it finishes |
| ⭐ **Usefulness** | ⭐⭐ **you almost never have the slow one** | ⭐⭐ **you have every one that mattered** |

> **⭐ The whole argument: at 1% head sampling, a slow request has a 1% chance of being recorded — so
> when someone asks about *that* request, you do not have it.** Tail sampling keeps a tiny volume that
> is entirely composed of the traces you would have chosen deliberately.

⚠️ **The sampling decision must be consistent across services.** The `sampled` flag travels in
`traceparent`, and **parent-based sampling means downstream services honour the upstream decision** —
otherwise you get half a trace, which is worse than none because it looks complete.

## ⭐⭐ Propagation through queues — the gap teams leave

```
⭐ HTTP: ⭐ the agent propagates automatically.
⭐ ⭐⭐ QUEUES: the trace ENDS at `publish` and a NEW one starts at `consume` — unless you carry it.
⭐
⭐ ⇒ ⭐ inject traceparent into a MESSAGE HEADER on publish
⭐ ⇒ ⭐ extract it on consume and link the consumer span to the producer
⭐ ⇒ ⭐⭐ use a LINK rather than a parent for batch consumption — one batch, many source traces
```

**⭐ This is the single most common gap in a real tracing setup** (Day 338 flagged it). Kafka and
RabbitMQ instrumentation usually handles it **if you use the instrumented client**, but a custom
producer, a scheduled poller, or an outbox publisher **silently breaks the chain** — and the symptom
is asynchronous work that appears to come from nowhere.

⚠️ **The other gap is the thread boundary.** Context is held in a thread-local, **so submitting work
to an executor loses it** unless the executor is wrapped (`Context.taskWrapping(...)`), or you use the
instrumented one. **Every `@Async` method (Day 177) is a place the trace can quietly end.**

# Part 4 — ⭐ Making it useful

## ⭐ Correlating the three signals

| ⭐ Link | ⭐ Mechanism |
|---|---|
| ⭐⭐ **Metric → trace** | ⭐⭐ **exemplars** — a histogram bucket carries an example trace id (Day 338) |
| ⭐⭐ **Trace → logs** | ⭐ `trace_id` in every log line (Day 375) |
| ⭐ **Logs → trace** | the same field, in reverse |
| ⭐ Trace → the code | ⭐ span attributes with the service version |

> **⭐ Exemplars are the piece that closes the loop.** Click the slow bucket on a latency histogram
> and land on an actual slow trace — **which turns "p99 got worse" into "here is one of them" in one
> click**, and is the difference between having tracing and using it.

## ⭐ What to instrument manually

| ⭐ Worth a span | ⭐ Not worth one |
|---|---|
| ⭐ **A business operation** — "score risk", "settle invoice" | a getter |
| ⭐ A loop over N external calls | ⭐ **every iteration** — that is a cardinality problem in disguise |
| ⭐ **A cache lookup with hit/miss as an attribute** | trivial in-memory work |
| An explicit fallback or degraded path (Day 339) | anything the agent already covers |

⚠️ **Attributes are searchable dimensions and therefore have a cost.** Adding a high-cardinality
attribute to every span **is affordable in a trace backend in a way it is not in Prometheus** — but
adding a full request body is not. **Identifiers, yes; payloads, no** (Day 375's rules apply).

## ⭐ The honest costs

| ⭐ Cost | |
|---|---|
| ⭐ Agent overhead | ⭐ typically a few percent — **measure it on your workload, do not assume** |
| ⭐ **Storage** | ⭐ tail sampling makes this small; head sampling at 100% does not |
| ⭐ **Collector as a dependency** | ⭐⭐ it must fail open — **never block the app if it is down** |
| Learning curve | span kinds, context, propagators |

⚠️ **The Collector being unreachable must be a no-op, not an error.** An SDK configured to block or
retry aggressively when the Collector is down **turns an observability outage into a service
outage** — the same failure mode as a blocking metrics client (Day 358A).

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Head-based 1% sampling** | ⭐⭐ **you almost never have the slow trace** |
| ⭐ Inconsistent sampling across services | half a trace, looking complete |
| ⭐⭐ **No propagation through queues** | ⭐⭐ async work appears to come from nowhere |
| ⭐ Context lost across an executor | ⭐ every `@Async` silently ends the trace |
| ⭐ **No exemplars** | ⭐ you cannot get from a metric to a trace |
| ⭐ **No `trace_id` in logs** | ⭐⭐ the three signals never join |
| ⭐ Manual spans duplicating the agent | noise, and overhead |
| ⭐ A span per loop iteration | thousands of spans per trace |
| ⭐ Request bodies as span attributes | PII and cost (Day 375) |
| ⭐ **Exporting directly to a vendor** | 40 services to change when you switch |
| ⭐⭐ **A blocking exporter** | ⭐⭐ the Collector goes down and takes the app with it |
| Assuming the agent overhead is zero | measure it |

## Interview questions

**Q: What does tracing tell you that metrics and logs cannot?**
Where the time went, across services, for one specific request. A metric says one percent of requests
are slow; a log says what one service printed. A trace shows the whole tree — that four hundred
milliseconds was three hundred and thirty-five in a call to Stripe — with the causal structure
intact. That is a question the other two signals cannot answer at all.

**Q: How do you start with OpenTelemetry in Java?**
The Java agent, with no code changes: service name and an OTLP endpoint on the command line, and
Spring MVC, JDBC, the connection pool, HTTP clients, Kafka and Redis are all traced immediately. Then
I add manual spans only for business operations the framework cannot see — a risk evaluation, an
invoice run — not for re-tracing what the agent already covers.

**Q: How do you sample?**
Tail-based, in the Collector: keep every error, every trace above the p99, and a fraction of a percent
of the rest. Head-based sampling decides at the first span, so at one percent you have a one-percent
chance of holding the slow trace someone is asking about — you keep the boring ones and lose the
interesting ones. Tail sampling is only possible centrally, which is one of the main reasons the
Collector exists. And the decision has to propagate, so downstream services honour it and you never
get half a trace.

**Q: Where do traces usually break?**
Two places. Queues — the trace ends at publish and a new one starts at consume unless the trace
context is carried in a message header, and batch consumers need links rather than a single parent.
And thread boundaries — context lives in a thread-local, so handing work to an executor loses it
unless the executor is wrapped, which makes every `@Async` method a place the trace can quietly end.

**Q: How do the three signals connect?**
Exemplars link a metric to a trace — a latency histogram bucket carries an example trace id, so you
click the slow bucket and land on an actual slow request. The trace id in every log line links the
trace to logs in both directions. That loop is what makes the investment worthwhile; without
exemplars you have tracing you never quite reach from the alert that told you something was wrong.

## Mini task

1. ⭐ Attach the **OTel Java agent** to your flagship with no code changes. **Confirm you get a full
   trace across services.**
2. ⭐ Add a **manual span** for one business operation with meaningful attributes.
3. ⭐ Run a **Collector** and point the app at it. Then **change backends by editing collector config
   only** — prove the app did not change.
4. ⭐⭐ Configure **head-based 1% sampling.** Make 1% of requests slow and **measure how often you
   actually capture one.** Switch to tail sampling and repeat.
5. ⭐ Break sampling consistency deliberately and **observe a half-trace** that still looks complete.
6. ⭐⭐ Publish to Kafka with a **custom producer** and confirm the trace ends. **Inject `traceparent`
   into a header, extract on consume, and reconnect it.**
7. ⭐ Submit work to an unwrapped executor and **watch the context disappear.** Wrap it and confirm.
8. ⭐ Enable **exemplars** on your latency histogram and **click from the p99 bucket straight to a
   trace.**
9. ⭐ Confirm `trace_id` is in every log line and **query logs by a trace id from a slow trace**
   (Day 375).
10. ⭐ **Stop the Collector under load** and confirm the application is entirely unaffected.
11. ⭐ Measure the **agent's overhead** on your own workload with tracing on and off.

## 🎙️ Articulation drill

**Three minutes:** *"p99 latency doubled an hour ago. Find out why."*

**⭐ The path, and every step is one click:** look at the latency histogram → **use an exemplar to jump
from the slow bucket into an actual slow trace** → read the span tree to find which child dominates →
take that span's `trace_id` and pull every log line from every service for that request → check
whether it correlates with a deploy annotation (Day 374).

**⭐ The marker is the exemplar.** Anyone can say "I would look at traces"; **saying how you get from
the metric that alerted you to a specific trace, without searching, is the part that only exists if
you have wired it up.**
