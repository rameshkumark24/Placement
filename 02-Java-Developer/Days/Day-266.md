# Day 266 🏗️

**P-266** · Caching — measured, not assumed

**Time:** 3 hrs · **Mode:** BUILD

> Day 260 added caching where it was obviously right. **Today you prove it was**, and remove what was
> not — because **a cache that nobody measures is a cache nobody can remove**, and it will live in
> the codebase forever on the assumption that it helps.
>
> Day 167 gave the discipline: check the query plan before caching, and compare puts against hits.
> **Today applies both to your own project.**

---

# Part 1 — ⭐ Justify every cache, or delete it

**⭐ For each cache in your project, answer four questions in writing:**

| # | Question | ⭐ Failing answer |
|---|---|---|
| ⭐ 1 | **What is the underlying query's plan?** | ⭐ "I never looked" — Day 191 |
| ⭐ 2 | **Is it slow because of work, or a missing index?** | ⭐ a `Seq Scan` you could have indexed |
| ⭐ 3 | **What is the hit ratio?** | "I assume it is high" |
| ⭐ 4 | **How stale may this be, and who decided?** | the TTL was copied |

> **⭐ Day 167's argument, in your project: a cache is not a fix for a missing index.** The first
> request is still slow, every cold cache after a deploy is still slow, and you have added
> invalidation complexity to avoid a one-line change.

**⭐ Run `EXPLAIN (ANALYZE, BUFFERS)` on every cached query today.** If any is doing a sequential scan
you could index away, **delete the cache and add the index instead.** That is a genuinely good
interview story: *"I had a cache on the availability query; the plan showed a missing composite
index; I removed the cache and the p99 improved without the invalidation complexity."*

## ⭐ The hit-ratio test

```
⭐ Instrument hits, misses and PUTS per cache.
⭐ ⭐ If puts exceed hits, the cache costs more than it saves — DELETE IT.
```

**⭐ Day 167's number.** A cache serving a long tail of one-off lookups pays serialization, memory and
eviction on every miss to serve fewer reads than that. **This is a common outcome and almost nobody
checks.**

```
⭐ Expose the ratio via Micrometer and put it on a dashboard (Day 143).
```

# Part 2 — ⭐ Key design, and the one that is a security control

```
⭐ {service}:{tenant}:{entity}:{id}:v{version}
⭐ orders:t42:booking:7f3a:v3
```

| Rule | Why |
|---|---|
| ⭐⭐ **Tenant in the key** | ⭐⭐ **a shared key serves tenant A's data to tenant B — a breach** |
| ⭐ **Version in the key** | ⭐ invalidation is one `INCR`, no enumeration (Day 206) |
| ⭐ **Never unescaped user input** | `user:{name}` with a name of `1:admin` collides |
| Short but readable | keys are stored per entry — 40 chars × 10M is 400 MB |

**⭐ The tenant rule belongs on Day 259's security checklist too**, and it is worth testing
explicitly: **cache a value as tenant A, request it as tenant B, and confirm a miss.**

## ⭐ Versioned invalidation — why it beats deletion

```
⭐ INCR ver:booking:7f3a   → ⭐ EVERY derived key for that booking is unreachable at once
```

**⭐ Three properties deletion cannot give you** (Day 206):

| | |
|---|---|
| ⭐ 1 | Atomic invalidation of every derived key — no enumeration |
| ⭐ 2 | ⭐ **No `KEYS`/`SCAN` pattern delete** — which Day 203 showed is an outage or slow |
| ⭐ 3 | ⭐ **Rollback** — decrement and the old cache is live again |

**⭐ And the emergency switch: `INCR ver:global` invalidates everything instantly**, without
`FLUSHALL` blocking the single thread.

# Part 3 — ⭐ The failure modes, reproduced in your project

**⭐ Day 206's four. Reproduce each, then fix it, then confirm.**

### ⭐ 1. Stampede

```
⭐ Expire a hot key, fire 200 concurrent requests → ⭐ COUNT the database queries
```

| Fix | Note |
|---|---|
| ⭐ **Jittered TTLs** | ⭐ prevents *synchronised* expiry — always do this |
| ⭐ **Stale-while-revalidate** | ⭐ best UX — serve stale, refresh in background |
| A distributed lock on rebuild | Day 207 — for genuinely expensive rebuilds |

**⭐ `@Cacheable(sync = true)` locks within one JVM only** (Day 168). With three instances that is
three concurrent rebuilds — better than 200, **not a solution.** Say so.

### ⭐ 2. Penetration

```
⭐ 10,000 requests for non-existent ids → ⭐ every one reaches the database
```

**⭐ Exploitable if ids come from the request.** Fix with short-TTL negative caching, or a Bloom
filter of existing ids.

### ⭐ 3. Avalanche

**⭐ A million keys written at deploy time with identical TTLs expire in the same second.** Same
one-line fix: **jitter.**

**⭐ And Day 206's second reason for jitter: expiry is lazy plus sampled**, so a mass expiry creates a
*deletion burst* that competes with command execution on Redis's single thread.

### ⭐ 4. Hot key

```
⭐ Find your hottest key. If one key is >20% of traffic, put a small Caffeine cache in front.
```

**⭐ A two-tier cache with a 5-second local TTL absorbs hot keys entirely**, and 5 seconds of
staleness is usually acceptable for exactly the data that is hot.

# Part 4 — ⭐ Configure Redis correctly, and prove it can disappear

## ⭐ The four defaults that must change (Day 168, Day 206)

```
⭐ 1. maxmemory-policy: allkeys-lfu   ← ⭐ the DEFAULT IS noeviction: writes FAIL when full
⭐ 2. A TTL on EVERY cache            ← ⭐ without one, a bad value is cached permanently
⭐ 3. JSON serialization with an ALLOW-LISTED type validator
        ⭐⭐ NOT JdkSerialization — readObject on attacker bytes is RCE (Day 068)
        ⭐⭐ NOT LaissezFaireSubTypeValidator — the JSON equivalent of the same hole
⭐ 4. A CacheErrorHandler that LOGS and FALLS THROUGH  ← ⭐⭐ or Redis down = application down
```

**⭐ Item 1's `volatile-*` trap** (Day 206): if some keys have no TTL they are never eviction
candidates, and **when only those remain Redis behaves as `noeviction` and writes fail.** One
forgotten `SET` without a TTL can do this over time.

**⭐ Item 3 also matters for a mundane reason**: JDK serialization is version-fragile, so **adding a
field to a DTO makes every cached entry fail to deserialize after deploy** — throwing on read rather
than missing cleanly.

**⭐ LFU over LRU** (Day 206): LRU's pathology is that one batch job touching a million keys makes
them all "recently used" and **evicts your entire working set.** Access in a real cache is skewed, so
frequency predicts reuse better than recency.

## ⭐⭐ The proof: stop Redis under load

```
⭐ 1. Stop Redis while a load test runs.
⭐ 2. ⭐ Confirm the application degrades — slower, NOT broken. No 500s.
⭐ 3. Restart it. Confirm recovery without intervention.
⭐ 4. Then FLUSHALL under load → ⭐ watch the database.
```

> **⭐⭐ If step 4 takes your database down, the cache is not a cache — it is an undeclared
> dependency**, and that is a capacity problem wearing a performance costume (Day 168).

**⭐ Also set a Redis timeout** (Day 154): Redis is a network call, so a slow Redis without a timeout
parks your threads. **500 ms is generous.**

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Caching instead of indexing | first request and every cold cache still slow |
| ⭐ Never measuring hits versus puts | ⭐ a net-negative cache lives forever |
| ⭐ **No tenant in the key** | ⭐⭐ cross-tenant data leak |
| Delete-based invalidation of derived keys | you cannot enumerate them safely |
| `KEYS pattern` to invalidate | Day 203's outage |
| ⭐ `maxmemory-policy` left at `noeviction` | ⭐ writes fail instead of evicting |
| `volatile-*` with untagged keys | effectively `noeviction` over time |
| ⭐ No TTL | a bad value is cached permanently |
| ⭐ No jitter | stampede, avalanche and an expiry burst |
| ⭐ **JDK serialization** | ⭐ an RCE surface, and breaks on any DTO change |
| `LaissezFaireSubTypeValidator` | reintroduces the deserialization hole |
| ⭐ **No `CacheErrorHandler`** | ⭐ Redis down takes the application down |
| No Redis timeout | a slow Redis parks your threads |
| Relying on `sync = true` in a cluster | per-JVM only |
| ⭐ Never testing with Redis stopped | the dependency is undeclared until it fails |
| Caching authorization decisions | ⭐ a stale permission is a security bug |
