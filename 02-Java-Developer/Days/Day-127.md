# Day 127

**L-127** · Structured logging, correlation IDs, log levels, what never to log

**Time:** 3 hrs · **Mode:** NEW

> Day 073A covered the SLF4J mechanics. Today is logging as an **observability** discipline — how you
> answer questions about a running system, which is a different problem from writing log statements.
>
> The framing that matters: **logs are a queryable dataset, not a diary.**

---

# Part 1 — The three pillars

```
LOGS     discrete events with detail        "what happened in THIS request?"
METRICS  aggregated numbers over time       "how is the system behaving overall?"   (Day 128)
TRACES   one request across many services   "where did the 3 seconds go?"
```

They answer different questions and none substitutes for the others:

| Question | Pillar |
|---|---|
| Is the system healthy? | Metrics |
| Why did *this* request fail? | Logs |
| Which service made it slow? | Traces |
| How many failed in the last hour? | Metrics |
| What exactly did this user experience? | Logs, joined by correlation id |

**The economics differ sharply.** Metrics are cheap and constant-cost regardless of traffic — a
counter is a counter. Logs scale with request volume and are the expensive one; a service at 10,000
requests per second logging 10 lines per request produces around 8 billion lines a day, and at
typical aggregator pricing that is a serious budget line.

> **Use metrics for "how much" and logs for "what happened".** Logging a line per request to count
> requests is paying for a counter you could have had for free.

# Part 2 — Structured logging

```
2026-08-14 10:22:01 INFO  Order 88213 shipped to Chennai in 240ms
```

Readable by a human, **unqueryable by a machine**. To answer "p99 shipping duration for Chennai last
week" you need a regex over text, and it breaks the moment someone rewords the message.

```json
{"ts":"2026-08-14T10:22:01.123Z","level":"INFO","logger":"OrderService",
 "msg":"order shipped","order_id":"ord_88213","city":"Chennai","duration_ms":240,
 "request_id":"req_a3f9c2e1","user_id":"usr_17","tenant_id":"tnt_9","service":"orders",
 "version":"1.4.2","thread":"http-nio-8080-exec-3"}
```

Now every one of those is a queryable field:

```
level:ERROR AND service:orders AND duration_ms:>1000
tenant_id:tnt_9 AND request_id:req_a3f9c2e1        ← one request's entire journey
```

**The rule that makes it work:** keep `msg` a **stable, low-cardinality string** and put every
variable in a field.

```java
log.info("order shipped", kv("order_id", id), kv("city", city), kv("duration_ms", ms));
```

Stable messages let you **group by message** — "how many times did 'payment declined' happen today?"
— which is impossible if the id is embedded in the text.

```java
// Java: logstash-logback-encoder
log.atInfo()
   .addKeyValue("order_id", order.id())
   .addKeyValue("duration_ms", elapsed)
   .log("order shipped");
```

**Configure the encoder once, globally**, and log to **stdout** — the platform collects it (Day
073A). Files in a container are lost on restart.

# Part 3 — ⭐ Correlation IDs

**The single highest-value practice in this day.** Without it, a million interleaved lines are
unusable; with it, one request's entire journey is one query.

```java
public class CorrelationFilter implements Filter {
    public static final String HEADER = "X-Request-Id";

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        String id = Optional.ofNullable(((HttpServletRequest) req).getHeader(HEADER))
                .filter(s -> s.matches("[A-Za-z0-9-]{1,64}"))   // ⭐ validate — it is user input
                .orElseGet(() -> UUID.randomUUID().toString());

        MDC.put("request_id", id);
        MDC.put("user_id", currentUserId());
        MDC.put("tenant_id", currentTenantId());
        ((HttpServletResponse) res).setHeader(HEADER, id);       // ⭐ return it to the client
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                                          // ⭐ MANDATORY (Day 066A)
        }
    }
}
```

Four details, each of which is a bug if omitted:

**Accept an incoming id** so a trace spans services, but **validate it** — it crossed the trust
boundary (Day 105), and an unvalidated value with a newline is log injection.

**Return it in the response header.** A user reporting a problem can quote it, and support goes
straight to the request. This turns "it was slow yesterday afternoon" into one query.

**`MDC.clear()` in a `finally`.** MDC is `ThreadLocal`-backed (Day 066A), so a pooled thread
otherwise carries one request's id into the next — and you will debug the wrong user's problem.

**Propagate it downstream:**

```java
// outbound HTTP
request.header("X-Request-Id", MDC.get("request_id"));

// into a background job or a message (Day 124, Day 125)
job.setCorrelationId(MDC.get("request_id"));
```

And across an async hand-off, because MDC does **not** propagate to a pool thread:

```java
Map<String, String> ctx = MDC.getCopyOfContextMap();
executor.submit(() -> {
    MDC.setContextMap(ctx);
    try { work(); } finally { MDC.clear(); }
});
```

## Distributed tracing

The formalised version — **OpenTelemetry** and W3C Trace Context:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ↑ver ↑───── trace id ─────────────↑ ↑── span id ──↑ ↑flags
```

```
trace_id: one request across ALL services
span_id:  one operation within it, with a parent
```

A trace shows *where* the time went:

```
[────────────── GET /orders/42 · 340 ms ──────────────]
  [── auth 12 ms ──]
                    [──── order-service 310 ms ────]
                      [─ db query 40 ms ─]
                                          [──── payment-service 250 ms ────]   ← the culprit
```

**Put the trace id in your logs** and the two pillars join:

```java
MDC.put("trace_id", Span.current().getSpanContext().getTraceId());
```

**Sampling is what makes it affordable:** trace 1–10% of requests plus all errors and slow requests.
**Tail-based sampling** — decide after the request completes, so you keep the interesting ones — is
the better model where your collector supports it.

# Part 4 — Levels, and what never to log

## Levels by audience (Day 073A, restated as the operational rule)

| Level | Means | Who acts |
|---|---|---|
| `ERROR` | Something failed needing a human | **on-call** — should page |
| `WARN` | Recovered, degraded, approaching a limit | reviewed next morning |
| `INFO` | A significant business event | support, audit |
| `DEBUG` | Diagnostic detail, off in production | developer |
| `TRACE` | Firehose | developer, briefly |

> **`ERROR` means someone should be woken up.** If nobody would act, it is not an error.

**Alert fatigue is a safety problem, not a tidiness one.** Once `ERROR` fires 400 times a day for a
retryable timeout, the team mutes it and misses the real one. **A user's invalid input is not an
error** — it is `INFO` at most.

## What to log

```java
// ✅ INFO — business events, one line each
log.atInfo().addKeyValue("order_id", id).addKeyValue("amount_cents", amt).log("order placed");

// ✅ WARN — degraded but handled
log.atWarn().addKeyValue("attempt", n).addKeyValue("provider", "stripe")
   .log("payment provider slow, retrying");

// ✅ ERROR — with the exception as the LAST argument (Day 073A)
log.atError().addKeyValue("order_id", id).setCause(e).log("payment capture failed");

// ✅ boundary logging — one line in, one line out, with duration
log.atInfo().addKeyValue("method","POST").addKeyValue("path","/orders")
   .addKeyValue("status",201).addKeyValue("duration_ms",55).log("request completed");
```

**One structured line per request at the boundary** is the highest-value log in any service: status,
duration, path, user, tenant and correlation id. It answers most questions on its own.

**What not to log:** every method entry (that is what tracing is for), successful health checks
(gigabytes of nothing), inside tight loops, or anything a metric would answer better.

## ⭐ What must never be logged

| Never | Why |
|---|---|
| Passwords — even wrong ones | Plain text, in a file, shipped to a vendor |
| Full card numbers, CVV | PCI-DSS; CVV must never be stored at all |
| Tokens, JWTs, API keys, session ids | A log reader becomes an authenticated user |
| `Authorization` / `Cookie` headers | Same |
| **Full request/response bodies** | Contains all of the above |
| National ids, addresses, DOB | GDPR / DPDP personal data |
| Encryption keys | It happens |

**Logs are the softest target in a system** (Day 073A): copied to an aggregator, retained for months,
readable by the whole team plus support plus the vendor, backed up, rarely encrypted.

```java
// mask, do not omit — you still want to know a card was involved
log.atInfo().addKeyValue("card_last4", pan.substring(pan.length() - 4)).log("charged");

// prefer an opaque id over the personal data itself
log.atInfo().addKeyValue("user_id", user.id()).log("user logged in");   // not the email
```

**The most reliable defence is at the type level** (Day 073A): a secret whose `toString` cannot leak
it.

```java
public final class ApiKey {
    private final char[] value;
    @Override public String toString() { return "ApiKey[REDACTED]"; }
}
```

⚠️ **Records are a hazard** — the generated `toString` prints every component, so a record holding a
token will print it. Override it.

**Log injection** (Day 105) belongs here too: a `\n` in user input lets an attacker forge log lines,
including fake "authentication successful" entries. Strip CR and LF from any user-controlled value —
and note that **structured JSON logging largely solves this by construction**, because the encoder
escapes the value rather than concatenating it.

# Part 5 — Operating logs

## Volume and cost control

```
Sampling            log 1% of successful requests; 100% of errors
Level per logger    DEBUG for one package, WARN for a noisy library (Day 073A)
Rate limiting       cap repeats of the same message per minute
Retention tiers     7 days hot (searchable) · 90 days cold (S3) · then delete
Drop noise          health checks, static assets, successful heartbeats
```

**Sampling successful requests while keeping every error is the highest-leverage single change** —
errors are what you search for, and they are a tiny fraction of traffic.

⚠️ **Log volume is a denial-of-service vector.** An endpoint that logs a line per validation failure,
hit in a loop, fills your disk or your quota. Rate limit repeated messages.

## The pipeline

```
Application → stdout → collector (Fluent Bit, Vector) → aggregator (Loki, Elastic, Datadog)
```

**Never write to files in a container** and never let the application talk to the aggregator
directly — an aggregator outage must not become an application outage. Write to stdout and let the
platform buffer.

## Retention and deletion

Regulatory reality, worth knowing: **GDPR's right to erasure applies to logs.** If logs contain
personal data, you must be able to delete a user's data from them — which is close to impossible in
an append-only store, and is the practical argument for **logging opaque ids rather than personal
data**. Then erasure is a matter of deleting the mapping, not rewriting years of logs.

## Making logs useful in an incident

```
1. Alert fires (Day 128)
2. Find the correlation id from the error
3. Query all logs for that id — the whole journey across services
4. Find the trace id, see where the time went
5. Widen: all errors of this type in the last hour; which tenant, which endpoint, which version
```

**Step 5 is why fields matter.** With `tenant_id`, `version` and `endpoint` as fields, "is this one
customer or everyone?" and "did this start at the last deploy?" are single queries — and those two
questions resolve most incidents.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Unstructured text logs | Unqueryable; regexes break on rewording |
| Variables in the message string | Cannot group by message |
| No correlation id | A million interleaved lines, unusable |
| Not validating an incoming request id | Log injection |
| Not returning the id to the client | Support cannot locate the request |
| `MDC` without `clear()` in a `finally` | One request's context on another's logs |
| Assuming MDC crosses an executor | Empty context on pool threads |
| `ERROR` for expected failures | Alert fatigue; real errors muted |
| Logging every method entry | Cost, no signal — use tracing |
| Logging request bodies | Credentials in a third-party system |
| A record holding a secret | `toString` prints it |
| Writing to files in a container | Lost on restart |
| Application talking to the aggregator directly | An aggregator outage becomes yours |
| No sampling | Cost that scales with traffic |
| Unbounded repeated log lines | Disk or quota exhaustion |
| Personal data in logs | Erasure requests become impossible |

## Interview questions

**Q: Why structured logging?**
Because logs are a dataset. With fields you can query `duration_ms:>1000 AND tenant_id:x`; with text
you need a regex that breaks when someone rewords the message. Keep the message stable and
low-cardinality so you can also group by it.

**Q: What is a correlation id and why does it matter?**
A unique id per request, attached to every log line via MDC, propagated to downstream services and
background jobs, and returned to the client. It turns interleaved logs into one queryable journey,
and lets a user quote the id from their error page.

**Q: What are the three pillars, and how do they differ in cost?**
Logs (discrete events), metrics (aggregates) and traces (a request across services). Metrics are
cheap and constant-cost; logs scale with traffic and are the expensive one — so use metrics for "how
much" and logs for "what happened".

**Q: Why is `MDC.clear()` mandatory?**
MDC is `ThreadLocal`-backed, so on a pooled thread the previous request's context persists into the
next one — you end up debugging the wrong user's problem. It also does not propagate across an
executor hand-off, which must be handled explicitly.

**Q: What should never be logged?**
Passwords, tokens, card data, `Authorization` headers, full request bodies and personal data. Logs
are copied to aggregators, retained for months and widely readable. Log opaque ids, mask what must
appear, and make secret types redact in `toString`.

**Q: How do you control log costs?**
Sample successful requests while keeping all errors, set levels per logger, rate limit repeated
messages, drop health-check noise, and tier retention — hot searchable storage for a week, cold
object storage after that.

**Q: How do logs and traces work together?**
Put the trace id in the log context. Then an error log links to the trace showing where the time
went, and a slow span links to the logs explaining what it was doing.

## 🎙️ Articulation drill

Two minutes: **"How would you debug a production issue a user reported an hour ago?"**

Ask for the correlation id from their error page; query every service's logs for it to get the full
journey; open the trace to see where the time went; then widen — all errors of that type in the last
hour, grouped by tenant, endpoint and version, to establish blast radius and whether it started at a
deploy. Every step depends on a decision made *before* the incident, which is the real point of the
day.
