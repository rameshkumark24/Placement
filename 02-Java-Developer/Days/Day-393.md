# Day 393

**L-393** · SQS, SNS and EventBridge — choosing the right pipe

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ A visibility timeout is a lease with an expiry. It is the same mechanism as Day 320A's seat
> hold, the same as a distributed lock, and the same as a Kafka consumer's session — and once you see
> that, SQS stops being a product and becomes a pattern you already know.**
>
> Today: the four services separated by what only they can do, **the visibility timeout mistake that
> silently doubles your processing**, FIFO's real throughput, and **queue depth as the only correct
> autoscaling metric for workers.**

---

# Part 1 — ⭐⭐ Four pipes, four different jobs

| | ⭐ SQS | ⭐ SNS | ⭐ EventBridge | ⭐ Kinesis |
|---|---|---|---|---|
| ⭐ Shape | ⭐⭐ **queue — one consumer group** | ⭐⭐ **fan-out, push** | ⭐⭐ **content-based router** | ⭐⭐ **ordered replayable stream** |
| ⭐ Retention | ⭐ up to 14 days | ⭐⭐ **none — deliver or fail** | ⭐ archive (optional) | ⭐ 24h–365d |
| ⭐ Consumers | ⭐⭐ **competing — each message to ONE** | ⭐ all subscribers get a copy | ⭐ all matching rules | ⭐⭐ **many independent, each at its own offset** |
| ⭐ Ordering | ⭐ FIFO queues only | no | no | ⭐⭐ **per shard** |
| ⭐⭐ **Only it can** | ⭐⭐ **buffer and absorb backpressure** | ⭐ low-latency fan-out incl. SMS/email | ⭐⭐ **route on content + REPLAY + cross-account** | ⭐⭐ **replay from an offset, many readers** |

```
⭐⭐ THE STANDARD PATTERN, and it is standard for a reason:
⭐   ⭐⭐ SNS topic → several SQS queues → each with its own consumer
⭐   ⇒ ⭐ fan-out (SNS) + ⭐⭐ buffering, retry and DLQ per consumer (SQS)
⭐   ⇒ ⭐⭐ one slow consumer CANNOT slow the others, and each retries independently.
⭐   ⇒ ⭐ SNS alone has no retention: a subscriber that is down MISSES the message.
```

> **⭐ Decision rule in one line: SQS to buffer work, SNS to notify many, EventBridge to route on content
> or to replay, Kinesis/MSK when several independent consumers need the same ordered stream at
> volume.** (Day 333's "ordering lives in the partition" is the Kinesis shard, exactly.)

# Part 2 — ⭐⭐ The visibility timeout, properly understood

```
⭐ ReceiveMessage → ⭐⭐ the message becomes INVISIBLE for `visibilityTimeout` seconds
⭐   ⇒ consumer finishes → ⭐ DeleteMessage → gone
⭐   ⇒ consumer crashes or is slow → ⭐⭐ it becomes VISIBLE AGAIN and another consumer takes it
```

```
⭐⭐ THE MISTAKE:
⭐   visibilityTimeout = 30s, ⭐ but processing takes 45s
⭐   ⇒ at t=30 ⭐⭐ a SECOND consumer starts the SAME message while the first is still working
⭐   ⇒ ⭐⭐ duplicate CONCURRENT processing — double charges, double emails, corrupted state
⭐   ⇒ and the first consumer's DeleteMessage at t=45 ⭐⭐ silently fails or deletes the wrong receipt
```

| ⭐ The three fixes, in order | |
|---|---|
| ⭐ 1. Set the timeout above **p99** processing time | ⭐ the easy 80% |
| ⭐⭐ 2. **Heartbeat: `ChangeMessageVisibility`** | ⭐⭐ **extend the lease while you work — this is the real answer for variable work** |
| ⭐⭐ 3. **Be idempotent anyway** | ⭐⭐ **at-least-once is the guarantee; duplicates are normal, not exceptional** |

> **⭐⭐ Say the connection out loud, because it is the Stage 8 pattern card:** a limited resource
> (the message) claimed by an atomic operation (`ReceiveMessage`) and **held with an expiry that must be
> renewed**. **The seat hold, the distributed lock, the Kafka session timeout and the SQS visibility
> timeout are one mechanism with four names** (Day 320A, Day 359).

## ⭐ The rest of the operational surface

| Setting | ⭐ Get it right |
|---|---|
| ⭐⭐ **`maxReceiveCount` + DLQ** | ⭐⭐ **without it, a poison message retries forever and burns money** |
| ⭐ **Long polling** (`WaitTimeSeconds: 20`) | ⭐⭐ fewer empty receives — **cheaper and lower latency**; short polling is a default worth changing |
| ⭐ Message retention | up to 14 days |
| ⭐ Batch (10 messages) | ⭐ 10× fewer API calls — a real cost lever |
| ⭐ `ApproximateAgeOfOldestMessage` | ⭐⭐ **the health metric that matters** — depth alone can mislead |
| ⭐ Redrive | ⭐ move messages from the DLQ back after a fix |
| Message size | 256 KB — **larger goes to S3, with a pointer in the message** |

⚠️ **A DLQ nobody looks at is a silent data loss mechanism.** Alarm on `ApproximateNumberOfMessages` on
**every** DLQ, with a threshold of one. **The point of a DLQ is that a human finds out.**

# Part 3 — ⭐ FIFO, and what ordering really costs

| | ⭐ Standard | ⭐⭐ FIFO |
|---|---|---|
| ⭐ Throughput | ⭐ effectively unlimited | ⭐⭐ **300 msg/s (3,000 batched)** per queue; high-throughput mode raises it per group |
| ⭐ Ordering | best effort | ⭐⭐ **strict, within a message group** |
| ⭐ Duplicates | ⭐ at-least-once | ⭐ 5-minute dedup window |
| ⭐⭐ **The unit of ordering** | — | ⭐⭐ **`MessageGroupId`** |

```
⭐⭐ MessageGroupId IS THE PARTITION KEY, and it is the whole design decision:
⭐   groupId = orderId    ⇒ ⭐ per-order ordering, ⭐⭐ massive parallelism  ⭐ (usually right)
⭐   groupId = "all"      ⇒ ⭐⭐ total ordering, ⭐⭐ ONE consumer at a time  ⭐ (a bottleneck you built)
⭐ ⇒ ⭐⭐ Ordering is bought with parallelism. Choose the SMALLEST scope that is actually required.
```

> **⭐ Most systems do not need FIFO.** They need **idempotent consumers** and **ordering within one
> entity** — which is a `MessageGroupId` of the entity id, not global ordering. **"Do you need global
> ordering, or ordering per customer?" is the question that resolves it**, and the answer is almost
> always per-customer.

# Part 4 — ⭐ SNS and EventBridge

| SNS | |
|---|---|
| ⭐ Subscribers | ⭐ SQS, Lambda, HTTP, email, SMS, **mobile push** |
| ⭐⭐ **Message filtering** | ⭐⭐ subscribers receive only matching messages — **filter at the topic, not in your code** |
| ⭐ FIFO topics | pair with FIFO queues |
| ⭐⭐ **No retention** | ⭐⭐ **a subscriber that is down misses it** — which is why SNS→SQS exists |

| EventBridge | ⭐ What it uniquely gives |
|---|---|
| ⭐⭐ **Rules matching on event content** | ⭐⭐ routing logic as configuration rather than code |
| ⭐⭐ **Archive and replay** | ⭐⭐ **replay last Tuesday's events into a new consumer** — nothing else here does this |
| ⭐ **Schema registry** | discoverable event shapes, generated bindings |
| ⭐ **Scheduler** | ⭐ cron, at scale, with a target — **the modern replacement for a cron box** |
| ⭐ Partner/SaaS + AWS service events | ⭐ react to `RDS failover`, `ECS deployment`, `GuardDuty finding` |
| ⭐ Cross-account buses | ⭐ a real integration boundary |

> **⭐ EventBridge's archive-and-replay is the feature that decides architectures.** Being able to
> **replay a day of production events into a brand-new consumer** turns a risky migration into a
> rehearsal — and it is Day 335's "events are facts" made operational.

⚠️ **EventBridge is higher latency (~half a second) and lower throughput than SNS, and it is billed per
event published.** It is a **router**, not a hot path. **For low-latency fan-out at volume, SNS→SQS is
still correct.**

# Part 5 — ⭐⭐ Scaling workers on the queue

```
⭐⭐ SCALE WORKERS ON QUEUE DEPTH — never on CPU (Day 389).
⭐   Target tracking on ⭐⭐ `ApproximateNumberOfMessagesVisible` per task
⭐   or better: ⭐⭐ `ApproximateAgeOfOldestMessage` — ⭐ this is your ACTUAL SLO
⭐ ⇒ "no message waits more than 60 seconds" is a target you can scale against directly.
```

| ⭐ Why the queue makes autoscaling work at all | |
|---|---|
| ⭐⭐ **It absorbs the spike** | ⭐⭐ Day 389's 4–10 minute scale-out becomes acceptable — **the queue holds the burst** |
| ⭐ It converts a throughput problem into a latency one | ⭐⭐ **you fall behind instead of falling over** |
| ⭐ It makes Spot viable | ⭐ a killed worker's message reappears (Day 385) |
| ⭐ It gives natural backpressure | ⭐ depth *is* the signal (Day 336) |

> **⭐⭐ This is the deepest point of the day: a queue converts "we cannot handle this load" into "we are
> N minutes behind", which is a recoverable state rather than an outage.** That single transformation is
> why async architectures survive traffic that synchronous ones die to.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Visibility timeout below processing time** | ⭐⭐ duplicate concurrent processing |
| ⭐ No heartbeat for variable-length work | ⭐ the p99 tail double-processes |
| ⭐ Assuming exactly-once from SQS | ⭐⭐ at-least-once — be idempotent (Day 335) |
| ⭐⭐ **No DLQ or no `maxReceiveCount`** | ⭐⭐ a poison message retries forever |
| ⭐⭐ **A DLQ with no alarm** | ⭐⭐ silent data loss |
| ⭐ Short polling left on | ⭐ empty receives cost money and add latency |
| ⭐ Not batching | 10× the API calls |
| ⭐ Watching depth but not message age | ⭐⭐ age is the SLO |
| ⭐⭐ **FIFO with one message group** | ⭐⭐ a single-consumer bottleneck you built yourself |
| ⭐ FIFO when idempotency was the real need | 300/s ceiling for nothing |
| ⭐⭐ **SNS with no SQS in between** | ⭐⭐ a down subscriber misses the message permanently |
| ⭐ Filtering in consumer code | SNS filter policies do it at the topic |
| ⭐ EventBridge on a latency-critical path | ⭐ ~500 ms, and billed per event |
| ⭐⭐ **Scaling workers on CPU** | ⭐⭐ queue depth or message age |

## Interview questions

**Q: What is a visibility timeout and what goes wrong with it?**
When a consumer receives a message it becomes invisible for the timeout period; delete it and it is gone,
crash and it reappears for someone else. The failure is setting the timeout below actual processing
time — with a thirty-second timeout and forty-five-second processing, a second consumer starts the same
message while the first is still working, so you get duplicate concurrent processing: double charges,
double emails, corrupted state. Fixes in order: set it above p99, heartbeat with
`ChangeMessageVisibility` for variable work, and be idempotent regardless, because at-least-once is the
guarantee. It is the same lease-with-expiry mechanism as a seat hold or a distributed lock.

**Q: SQS, SNS or EventBridge?**
SQS when you need to buffer work for competing consumers, with retry and a dead letter queue. SNS when
you need low-latency fan-out to many subscribers — but SNS has no retention, so a subscriber that is down
misses the message entirely, which is why the standard pattern is SNS to several SQS queues, giving
fan-out plus independent buffering and retry per consumer. EventBridge when routing depends on event
content, or when you need archive and replay, or cross-account buses — replay is the feature nothing else
here has, and it turns a risky consumer migration into a rehearsal. It is slower and billed per event, so
it is a router, not a hot path.

**Q: When do you need a FIFO queue?**
Less often than people think. The question to ask is whether you need global ordering or ordering per
entity, and the answer is almost always per entity — which means a standard queue with idempotent
consumers, or a FIFO queue with the message group set to the entity id. Setting one message group for
everything gives you total ordering and a single-consumer bottleneck you built on purpose. Ordering is
bought with parallelism, so you choose the narrowest ordering scope that is genuinely required.

**Q: How do you autoscale queue workers?**
On queue depth, and preferably on the age of the oldest message, because that is the actual service
objective — "no message waits more than sixty seconds" is something you can scale against directly. Never
on CPU, because an I/O-bound worker sits at low CPU while the backlog grows. The deeper point is that the
queue is what makes autoscaling viable at all: scale-out takes minutes, and the queue holds the burst
during that window. It converts "we cannot handle this load" into "we are three minutes behind", which is
recoverable rather than an outage.

**Q: What is the point of a dead letter queue?**
To stop a poison message from retrying forever and to make sure a human finds out. Without
`maxReceiveCount` and a DLQ, a message that always fails is reprocessed indefinitely, burning money and
potentially blocking throughput. But a DLQ that nobody watches is just a slower way to lose data, so the
non-negotiable part is an alarm on every DLQ with a threshold of one message. Then redrive puts them back
once the bug is fixed.

## 🎙️ Articulation drill

**Two minutes:** *"Why put a queue in front of this?"*

**⭐ Not "for decoupling" — that is the answer everybody gives.** The precise version: **a queue converts
a throughput failure into a latency one.** Without it, a spike exceeds capacity and the system returns
errors; with it, the spike is absorbed and the system falls *behind* — which is a recoverable state you
can scale out of, and which makes autoscaling's four-to-ten-minute lag survivable.

**⭐ Then the operational half that shows you have run one: at-least-once delivery means the consumer is
idempotent by design, the visibility timeout is above p99 with a heartbeat for long jobs, there is a dead
letter queue with an alarm at one message — and the workers scale on the age of the oldest message,
because that is the actual SLO.**
