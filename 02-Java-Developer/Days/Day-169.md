# Day 169 ⭐

**L-169** · The Spring Security filter chain — the mechanism everything else rests on

**Time:** 3+ hrs · **Mode:** NEW · **Marquee day**

> **Spring Security is not a library you configure — it is a chain of filters you assemble**, and
> almost every "why doesn't my security config work?" question is answered by naming which filter ran
> and in what order.
>
> Day 145 already placed it: **Security is a servlet filter, so it runs before the DispatcherServlet,
> before any interceptor, before argument resolution.** That single fact explains why preflight
> requests 401 (Day 155), why `@RestControllerAdvice` cannot catch a 401 (Day 149), and why an
> unauthenticated request never reaches your code.
>
> This is the Security block's Day 145. The next seven days derive from it.

# Part 1 — What is actually installed

```
Servlet container
  └── DelegatingFilterProxy  ("springSecurityFilterChain")   ← ⭐ one servlet filter
        └── FilterChainProxy                                  ← ⭐ Spring bean, holds N chains
              ├── SecurityFilterChain #1  (matches /api/**)
              │     ├── DisableEncodeUrlFilter
              │     ├── WebAsyncManagerIntegrationFilter
              │     ├── SecurityContextHolderFilter      ⭐ loads/clears the SecurityContext
              │     ├── HeaderWriterFilter               ⭐ security headers
              │     ├── CorsFilter                       ⭐ Day 155 — only if http.cors()
              │     ├── CsrfFilter                       ⭐ Day 172
              │     ├── LogoutFilter
              │     ├── <your JwtAuthenticationFilter>   ⭐ Day 173 goes here
              │     ├── UsernamePasswordAuthenticationFilter
              │     ├── RequestCacheAwareFilter
              │     ├── SecurityContextHolderAwareRequestFilter
              │     ├── AnonymousAuthenticationFilter    ⭐ "not logged in" is an Authentication
              │     ├── SessionManagementFilter
              │     ├── ExceptionTranslationFilter       ⭐⭐ turns exceptions into 401/403
              │     └── AuthorizationFilter              ⭐ the LAST one — the decision point
              └── SecurityFilterChain #2  (matches /actuator/**)
```

**Three structural facts worth memorising:**

1. **`DelegatingFilterProxy` is the bridge.** The servlet container knows nothing about Spring beans,
   so one registered filter delegates to a Spring-managed `FilterChainProxy`. That is why security
   filters can be beans with dependencies injected.
2. ⭐ **`FilterChainProxy` picks *one* chain — the first whose matcher matches — and runs only that
   one.** Chains do not compose. This is the source of the most confusing configuration bug in
   Spring Security, covered in Part 3.
3. ⭐ **`AuthorizationFilter` is last.** Authentication happens *earlier*, by whichever filter
   recognises the credential. **Authentication and authorization are separate filters at separate
   points** — Day 111's distinction, made structural.

# Part 2 — The three objects the whole framework moves around

```java
public interface Authentication extends Principal {
    Object getPrincipal();                              // ⭐ who — usually UserDetails
    Object getCredentials();                            // ⭐ proof — cleared after authentication
    Collection<? extends GrantedAuthority> getAuthorities();   // ⭐ what they may do
    boolean isAuthenticated();
}
```

```java
SecurityContext ctx = SecurityContextHolder.getContext();
Authentication auth = ctx.getAuthentication();
```

**⭐ `SecurityContextHolder` is a `ThreadLocal`** (Day 066A), and that produces two consequences you
will hit:

- **It must be cleared at the end of the request**, or a pooled Tomcat thread carries the previous
  user's identity into the next request. `SecurityContextHolderFilter` does this in a `finally` —
  Day 151's rule, implemented by the framework.
- ⭐ **It does not propagate to a new thread.** `@Async` methods, `CompletableFuture` callbacks and
  parallel streams start with an **empty** security context, so `@PreAuthorize` there sees an
  anonymous user. Day 177 covers the fix (`DelegatingSecurityContextExecutor`); the *reason* is this
  line.

**The three-state model people miss:**

| State | `Authentication` |
|---|---|
| Not authenticated | ⭐ an `AnonymousAuthenticationToken` — **not null** |
| Authenticated | a real token with authorities |
| Failed | an exception thrown by the authenticating filter |

**`getAuthentication() != null` is not an authentication check.** Anonymous users have a token too.
Check `isAuthenticated()` and that it is not the anonymous token — or better, let
`AuthorizationFilter` decide and never write the check yourself.

## ⭐ `ExceptionTranslationFilter` — where 401 and 403 come from

It wraps everything downstream and catches exactly two exceptions:

| Exception | Handler | Result |
|---|---|---|
| `AuthenticationException` | `AuthenticationEntryPoint` | ⭐ **401** — "who are you?" |
| `AccessDeniedException` | `AccessDeniedHandler` | ⭐ **403** — "you may not" |

**And the subtlety that decides real behaviour:** if the current user is *anonymous* and an
`AccessDeniedException` is thrown, Spring returns **401, not 403** — because an anonymous user being
denied means they should log in, not that they are forbidden. Day 111's distinction, applied
correctly by the framework.

**This is why Day 149's advice cannot produce these responses.** They are generated inside a filter,
before the DispatcherServlet. To make them RFC 7807 you must configure the handlers:

```java
http.exceptionHandling(e -> e
    .authenticationEntryPoint((req, res, ex) -> writeProblem(res, 401, "Authentication required"))
    .accessDeniedHandler((req, res, ex)      -> writeProblem(res, 403, "Insufficient permissions")));
```

**Without this, your API returns two different error formats** — RFC 7807 everywhere except the two
most common failures.

# Part 3 — Configuring it, and the ordering bug everyone hits

```java
@Configuration
@EnableWebSecurity
class SecurityConfig {

    @Bean
    @Order(1)                                             // ⭐ MOST SPECIFIC FIRST
    SecurityFilterChain actuator(HttpSecurity http) throws Exception {
        http.securityMatcher(EndpointRequest.toAnyEndpoint())        // Day 143
            .authorizeHttpRequests(a -> a
                .requestMatchers(EndpointRequest.to(HealthEndpoint.class)).permitAll()
                .anyRequest().hasRole("ACTUATOR"))
            .httpBasic(withDefaults());
        return http.build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain api(HttpSecurity http, JwtAuthenticationFilter jwt) throws Exception {
        http.securityMatcher("/api/**")
            .csrf(AbstractHttpConfigurer::disable)                   // ⭐ Day 172 justifies this
            .cors(withDefaults())                                    // ⭐ Day 155 — required
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(a -> a
                .requestMatchers("/api/v1/auth/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/v1/products/**").permitAll()
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())                       // ⭐⭐ deny by default
            .addFilterBefore(jwt, UsernamePasswordAuthenticationFilter.class)
            .exceptionHandling(e -> e
                .authenticationEntryPoint(problemEntryPoint())
                .accessDeniedHandler(problemDeniedHandler()));
        return http.build();
    }
}
```

## ⭐ The multiple-chain bug

**Chains are evaluated in `@Order` and the *first match wins* — the rest never run.**

```java
@Bean @Order(1) SecurityFilterChain a(HttpSecurity http) {
    http.securityMatcher("/**")          // ❌ matches everything
        .authorizeHttpRequests(x -> x.anyRequest().permitAll());
    return http.build();
}
@Bean @Order(2) SecurityFilterChain b(HttpSecurity http) {
    http.securityMatcher("/api/admin/**")     // ⭐ NEVER REACHED
        .authorizeHttpRequests(x -> x.anyRequest().hasRole("ADMIN"));
    return http.build();
}
```

**Your admin endpoints are public.** No error, no warning, and the configuration reads as though it
works. **Rule: order chains most-specific first, and a `/**` chain is always last.**

## ⭐ Rule ordering inside a chain — the same trap, one level down

```java
.authorizeHttpRequests(a -> a
    .requestMatchers("/api/**").authenticated()          // ❌ matches /api/admin/** too
    .requestMatchers("/api/admin/**").hasRole("ADMIN")   // ⭐ never evaluated
)
```

**First match wins here too.** Any authenticated user reaches `/api/admin/**`.

**And the rule that prevents the worst outcome:**

> **`.anyRequest().authenticated()` must be the last line of every chain.** Deny by default. A new
> endpoint added next year is protected until someone deliberately opens it — Day 108's allow-list
> principle, applied to routing.

## Never use `WebSecurityCustomizer.ignoring()`

```java
@Bean WebSecurityCustomizer ignore() {
    return web -> web.ignoring().requestMatchers("/public/**");   // ❌
}
```

**This bypasses the entire filter chain** — no security headers, no CSRF, no context. Boot 3 logs a
warning about it. Use `.permitAll()` instead: the request still goes through the chain and still gets
its headers.

# Part 4 — Security headers, and testing what you built

`HeaderWriterFilter` writes sensible defaults; two need attention.

```java
http.headers(h -> h
    .frameOptions(f -> f.sameOrigin())                       // clickjacking
    .httpStrictTransportSecurity(hsts -> hsts.maxAgeInSeconds(31536000).includeSubDomains(true))
    .contentSecurityPolicy(csp -> csp.policyDirectives(
        "default-src 'self'; frame-ancestors 'none'; object-src 'none'")));   // ⭐ not default
```

| Header | Default | Note |
|---|---|---|
| `X-Content-Type-Options: nosniff` | ✅ on | prevents MIME sniffing |
| `X-Frame-Options: DENY` | ✅ on | clickjacking |
| `Cache-Control: no-store` | ✅ on | ⭐ authenticated responses must not be cached |
| **HSTS** | ✅ only over HTTPS | ⭐ needs `forward-headers-strategy` (Day 155) or it never sets |
| **CSP** | ❌ **off** | you must set it |

## Testing — and it must be tested, because a misconfiguration is silent

```java
@WebMvcTest(OrderController.class)
@Import(SecurityConfig.class)                                // ⭐ or the real config is not applied
class OrderControllerSecurityTest {

    @Test void anonymousIsRejected() throws Exception {
        mockMvc.perform(get("/api/v1/orders")).andExpect(status().isUnauthorized());
    }

    @Test @WithMockUser(roles = "USER")
    void userCannotReachAdmin() throws Exception {
        mockMvc.perform(get("/api/v1/admin/users")).andExpect(status().isForbidden());
    }

    @Test @WithMockUser(roles = "ADMIN")
    void adminCan() throws Exception {
        mockMvc.perform(get("/api/v1/admin/users")).andExpect(status().isOk());
    }
}
```

**⭐ Write a negative test for every protected endpoint.** Day 097's argument with a security edge:
an authorization bug does not throw, does not log, and does not fail any positive test — the endpoint
returns 200 to the wrong person. **A test asserting 403 is the only thing that notices.**

```yaml
logging.level.org.springframework.security: DEBUG     # ⭐ prints the chain, filter by filter
```

Boot also logs the **full ordered filter list** at startup on DEBUG. When behaviour surprises you,
read that list first — it is the diagram above, printed for your actual configuration.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ A `/**` chain ordered before a specific one | later chains never run — endpoints silently public |
| ⭐ Broad rule before specific inside a chain | first match wins; admin routes open |
| Missing `.anyRequest().authenticated()` | new endpoints default to open |
| `WebSecurityCustomizer.ignoring()` | bypasses the whole chain — no headers, no context |
| Expecting `@RestControllerAdvice` to format 401/403 | generated in a filter (Day 149) |
| No `AuthenticationEntryPoint`/`AccessDeniedHandler` | two error formats in one API |
| Forgetting `http.cors()` | preflight 401 (Day 155) |
| `getAuthentication() != null` as an auth check | anonymous users have a token |
| Assuming the context propagates to `@Async` | it is a `ThreadLocal` |
| No CSP | the one header Spring does not set |
| No negative authorization tests | the failure is a 200 to the wrong user |

## Interview questions

**Q: How does Spring Security work?**
A single servlet filter, `DelegatingFilterProxy`, delegates to `FilterChainProxy`, which selects the
first matching `SecurityFilterChain` and runs its filters in order. Authentication happens in whichever
filter recognises the credential; `AuthorizationFilter` runs last and makes the access decision; and
`ExceptionTranslationFilter` wraps them to convert `AuthenticationException` into 401 and
`AccessDeniedException` into 403.

**Q: Why does adding a second `SecurityFilterChain` break things?**
Because chains do not compose — the first whose matcher matches is the only one that runs. A `/**`
chain ordered first makes every later chain dead configuration, so endpoints you believe are
protected are public, with no error.

**Q: Where does a 401 come from, and why can't your `@RestControllerAdvice` format it?**
`ExceptionTranslationFilter` catches `AuthenticationException` and delegates to the
`AuthenticationEntryPoint`. That happens in a filter, outside the DispatcherServlet, so no
`HandlerExceptionResolver` is involved — the entry point and access-denied handler must be configured
separately.

**Q: Why is the security context missing in an `@Async` method?**
`SecurityContextHolder` is a `ThreadLocal`, and a new thread does not inherit it. That is also why it
must be cleared at the end of every request — Tomcat threads are pooled.

## 🎙️ Articulation drill

Three minutes: **"Explain how Spring Security processes a request."**

Walk it as a chain: one servlet filter delegating to `FilterChainProxy`, which picks the first
matching chain — and stop there to say that chains do not compose, because that single fact is the
most common configuration bug. Then authentication by whichever filter recognises the credential,
`AuthorizationFilter` last as the decision point, and `ExceptionTranslationFilter` wrapping both to
produce 401 and 403. Close by connecting it outward: this all happens before the DispatcherServlet,
which is why preflight requests fail without `http.cors()` and why your error advice never sees a 401.
