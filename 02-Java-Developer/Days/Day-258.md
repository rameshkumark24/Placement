# Part 1 — ⭐ Registration and login

## ⭐ Password storage — Day 171, applied

```
⭐ DelegatingPasswordEncoder with argon2 as idForEncode
⭐ UserDetailsPasswordService for upgrade-on-login  ← ⭐ implement it NOW, not "later"
⭐ Work factor CALIBRATED on your hardware: 250–500 ms per hash
⭐ A test asserting that timing, so a hardware change is caught
```

**⭐ Implementing the upgrade path on day one costs twenty minutes and is a strong defence point**:
"I chose `DelegatingPasswordEncoder` because the algorithm prefix means I can change the default
without locking anyone out, and `UserDetailsPasswordService` upgrades hashes at login." **Almost no
project does this.**

## ⭐ The rules around the encoder

| Rule | Day |
|---|---|
| ⭐ **Length not composition** — 12+ min, ⭐ **128 max** (hash-CPU DoS) | 171 |
| ⭐ **Breach check via HIBP k-anonymity** — send 5 SHA-1 chars, match locally | 171 |
| ⭐ **Identical response and timing** for unknown user and wrong password | 170 |
| ⭐ **Rate limit by IP *and* username** | ⭐ 170, 208 |
| ⭐ **Never log the password** — including in a body-logging filter | 151 |

**⭐ The both-keys rate limit deserves emphasis**: by IP alone, a botnet bypasses it; by username
alone, one machine sprays thousands of accounts. **Neither is sufficient, and saying that is a strong
answer** (Day 208).

**⭐ Password hashing is deliberately slow, so an unthrottled login is a CPU denial-of-service
vector** — 400 ms per attempt means a handful of requests per second per core. **That is the reason
the rate limit is mandatory, not a nice-to-have.**

# Part 2 — ⭐⭐ The JWT filter — every attack closed

**Day 173's five validations. Implement all five and be able to name the attack each prevents.**

```
⭐ 1. ALGORITHM ALLOW-LIST     → alg:none, RS256→HS256 confusion (Day 114)
⭐ 2. requireIssuer             → a token from another system sharing the key
⭐ 3. requireAudience           → a token for a different service in the estate
⭐ 4. clockSkewSeconds(30)      → valid tokens rejected by ordinary drift
⭐⭐ 5. A TOKEN TYPE CLAIM      → ⭐⭐ a REFRESH token used as an ACCESS token
```

> **⭐⭐ Number 5 is the one almost nobody implements, and it is a privilege escalation.** If both
> tokens are signed with the same key and neither states what it is, **a 30-day refresh token is
> accepted as an access token** — your carefully short 15-minute window is silently 30 days.

**⭐ Demonstrate each closure.** Craft an `alg:none` token by hand and send it. Send your refresh
token as a bearer token. **Those two demonstrations are the best material you will produce today**,
because they turn "I implemented JWT" into "I tested it against these specific attacks".

## ⭐ The filter's four implementation decisions

| Decision | Reason |
|---|---|
| ⭐ **A missing header is not an error** — continue the chain | ⭐ or every `permitAll` endpoint breaks |
| ⭐ **The filter writes `ProblemDetail` itself** | ⭐ Day 149's first gap — advice never sees a filter exception |
| ⭐ **Do not overwrite an existing authentication** | another filter may have authenticated |
| ⭐ **`OncePerRequestFilter`** | error re-dispatch otherwise parses the token twice (Day 151) |

## ⭐ The secret, and the algorithm choice

```
⭐ 256+ bits, from the environment, NEVER in application.yml    (Day 142, Day 085)
⭐ Consider RS256 — then only the issuer can sign               (Day 175)
```

**⭐ A leaked HMAC secret means an attacker mints valid tokens for any user with any role — with no
log entry anywhere**, because the tokens are genuinely valid. **That is why the secret is treated
like a private key, and why asymmetric signing limits the blast radius.**

**⭐ And know the alternative you did not take** (Day 175): a resource server with `issuer-uri` does
all five validations *plus* JWKS key rotation, which a hand-rolled HMAC implementation cannot do at
all. **"I hand-rolled it to demonstrate understanding of the mechanism; in production I would use a
resource server, and here is why" is a much better answer than either alone.**

# Part 3 — ⭐⭐ Refresh rotation and reuse detection

**Day 115 and Day 173's design. This is the part that distinguishes the project.**

```
⭐ RefreshToken: id, userId, tokenHash, familyId, expiresAt, usedAt, revoked
```

```
⭐ On refresh:
   1. Look up by HASH of the presented token            ⭐ never store the token itself
   2. ⭐⭐ If usedAt is not null → REUSE DETECTED:
         ⭐ revoke the ENTIRE FAMILY
         ⭐ log refresh_token_reuse_detected + increment a metric
         ⭐ return the SAME generic error as every other failure
   3. If revoked or expired → the same generic error
   4. Mark used, issue a new token in the same family
```

> **⭐ Why revoking the whole family is correct, and this is the interview answer:** a refresh token
> is single-use, so a *second* use proves two parties hold it — the legitimate client and a thief.
> **You cannot tell which is which, so you revoke both.** The real user re-authenticates with a
> password; the attacker cannot. **A stolen refresh token becomes useless the moment either party
> uses it after the other.**

**⭐ Three details that matter:**

| | |
|---|---|
| ⭐ **Store the hash** | a leaked table is otherwise a set of live credentials (Day 171) |
| ⭐ **One generic error for every failure** | otherwise the response distinguishes expired from reused |
| ⭐ **Alert on the reuse metric** | ⭐ **one of the highest-signal security events you can emit** |

**⭐ That last point is worth building today** (Day 143): a spike in `refresh_token_reuse_detected`
means credential theft, not a bug. **Most projects have no security metrics at all.**

## ⭐ Delivery — Day 172's hybrid

```
⭐ Access token  → the response body, held IN MEMORY by the client
⭐ Refresh token → HttpOnly + Secure + SameSite=Strict cookie,
                   ⭐ path scoped to /api/v1/auth/refresh
```

**⭐ This gets both properties**: XSS cannot exfiltrate a long-lived credential from `localStorage`,
and the refresh token is unreadable by script and sent to exactly one endpoint. **CSRF concern is
then confined to one path**, which `SameSite=Strict` already covers.

**⭐ And the CSRF decision must be stated, not defaulted** (Day 172): `csrf().disable()` is safe for
bearer tokens in a header and **unsafe the moment a cookie authenticates a request**. Your refresh
endpoint uses a cookie — **so document why it is protected and how.**

## ⭐ Logout, honestly

```
⭐ Revoke the refresh family + clear the cookie.
⭐ The ACCESS TOKEN remains valid until it expires — which is why the TTL is 15 minutes.
```

**⭐ Say this plainly rather than claiming logout is instant.** And implement `tokensValidAfter` per
user (Day 173) so a password change kills everything immediately — one column, no per-token
bookkeeping.

# Part 4 — ⭐ Prove it

**⭐ Every item below is a test you write today.** They are also, collectively, the strongest section
of your test suite to show an interviewer.

```
⭐ 1.  alg:none token                    → 401
⭐ 2.  Token signed with the wrong key   → 401
⭐ 3.  Expired token                     → 401
⭐ 4.  Wrong issuer / audience           → 401
⭐⭐ 5. REFRESH token as a bearer token   → 401   ← ⭐ the type-claim test
⭐ 6.  Missing header on a public route  → 200
⭐ 7.  Unknown user vs wrong password    → ⭐ identical body AND comparable timing
⭐⭐ 8. Refresh token reused              → ⭐ family revoked, both sessions dead
⭐ 9.  Password change                   → all tokens invalid immediately
⭐ 10. Login rate limit                  → 429 with Retry-After, by IP and by username
⭐ 11. Filter rejection                  → RFC 7807 body, ⭐ not whitelabel HTML
```

**⭐ Then do the manual demonstrations**, because they are what you will describe:

```
⭐ Decode your own token at jwt.io — ⭐ confirm nothing sensitive is in the claims
    (a JWT is SIGNED, not encrypted — anyone can read it)
⭐ Craft alg:none by hand and send it
⭐ Reuse a refresh token and watch both sessions die
```

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ No algorithm allow-list | `alg:none`, algorithm confusion |
| ⭐⭐ No token-type claim | ⭐ a 30-day refresh token works as an access token |
| No issuer/audience checks | a token from elsewhere is accepted |
| ⭐ Filter throwing without writing a response | whitelabel HTML from a JSON API |
| Missing header treated as an error | public endpoints break |
| ⭐ Refresh tokens stored in plaintext | a leaked table is live credentials |
| ⭐ No rotation | a stolen refresh token works for 30 days |
| ⭐⭐ No reuse detection | ⭐ theft is undetectable |
| Different errors for expired vs reused | tells the attacker what happened |
| ⭐ Secret in `application.yml` | full compromise, silently, with valid tokens |
| Long access-token TTL | revocation latency in days |
| ⭐ Sensitive data in claims | base64, readable by anyone |
| ⭐ Unthrottled login | credential stuffing **and** hash-CPU DoS |
| Claiming logout is instant | it is not — be honest about the window |
| ⭐ No `AuthenticationEntryPoint` | Security's 401 has a different shape from every other error |
