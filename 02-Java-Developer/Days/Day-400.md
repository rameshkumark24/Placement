# Day 400

**L-400** · gRPC and protobuf — and the schema evolution rules that never change

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ In protobuf the field *number* is the contract, not the field name. You can rename every field
> in a message and nothing breaks; reuse one number and you corrupt data silently.**
>
> Today: the evolution rules that make a binary contract safe to change, gRPC's four call types and
> its built-in deadline propagation, **the load balancing trap that sends all your gRPC traffic to one
> pod**, and when REST is simply the better answer.

---

# Part 1 — ⭐⭐ Protobuf, and the field number

```protobuf
syntax = "proto3";
package orders.v1;

message Order {
  string id           = 1;    // ⭐⭐ THE NUMBER is the wire identity
  string customer_id  = 2;
  int64  amount_cents = 3;    // ⭐ money as an integer, never a float (Day 357)
  reserved 4;                 // ⭐⭐ a deleted field — NEVER REUSE 4
  reserved "discount";        // ⭐ and never reuse the name either
  repeated Item items = 5;
  Status status       = 6;
}

enum Status {
  STATUS_UNSPECIFIED = 0;     // ⭐⭐ 0 MUST be the unknown/default — proto3 has no null
  STATUS_PLACED      = 1;
}
```

| ⭐⭐ The evolution rules — memorise these | |
|---|---|
| ⭐⭐ **Never change a field's number** | ⭐⭐ **it is the identity on the wire** |
| ⭐⭐ **Never reuse a number** after deleting | ⭐⭐ **old data decodes into the new field — silent corruption** |
| ⭐⭐ **Use `reserved`** for both number and name | ⭐ the compiler then stops you |
| ⭐ **Adding a field is always safe** | ⭐ old readers ignore unknown fields |
| ⭐⭐ **Never change a type** | ⭐ some are wire-compatible (`int32`/`int64`), most are not |
| ⭐ **Do not make a field required-by-convention later** | ⭐ old writers will not send it |
| ⭐⭐ **Enum 0 = UNSPECIFIED** | ⭐⭐ proto3 has no null; an unset enum reads as 0 |

⚠️ **The silent corruption is worth picturing.** You delete `discount` (field 4), and six months later
someone adds `priority` as field 4. **A message written before the deletion now decodes its old discount
bytes into `priority`.** No error, no exception — **just wrong data.** `reserved` exists entirely to
make this impossible.

| ⭐ Other things worth knowing | |
|---|---|
| ⭐ **Unknown field preservation** | ⭐ proto3 keeps unknown fields on round-trip — **so a proxy does not destroy new fields** |
| ⭐⭐ **`optional` in proto3** | ⭐⭐ gives you real presence detection — **"absent" vs "zero" matters for PATCH semantics** |
| ⭐ `oneof` | a tagged union; adding a case is safe |
| ⭐ Size | ⭐ typically **3–10× smaller than JSON**, and far cheaper to parse |
| ⭐⭐ **It is not human-readable** | ⭐⭐ **you cannot `curl` it** — this is a real operational cost |

# Part 2 — ⭐ gRPC: the four call types and what they change

| Type | ⭐ Shape | ⭐ Use |
|---|---|---|
| ⭐ **Unary** | 1 → 1 | ⭐ 95% of everything |
| ⭐ **Server streaming** | 1 → N | ⭐ large result sets, live feeds — **pagination without pages** |
| Client streaming | N → 1 | uploads, batched telemetry |
| ⭐ **Bidirectional** | N ↔ N | chat, real-time sync |

| ⭐ What gRPC gives you for free | |
|---|---|
| ⭐⭐ **HTTP/2 multiplexing** | ⭐ many concurrent calls on one connection, no head-of-line blocking at the app layer |
| ⭐⭐ **Deadlines, propagated** | ⭐⭐ **built into the protocol** — Day 336's deadline propagation, without a custom header |
| ⭐ **Cancellation** | ⭐ the client hanging up actually stops server work |
| ⭐ Typed errors + status codes | ⭐ `DEADLINE_EXCEEDED`, `UNAVAILABLE`, `FAILED_PRECONDITION` |
| ⭐ Generated clients in every language | the schema *is* the client |
| ⭐ Interceptors | tracing, auth, metrics in one place |

```java
// ⭐⭐ The deadline is part of the call, and it travels to every downstream hop
OrderResponse r = stub
    .withDeadlineAfter(200, TimeUnit.MILLISECONDS)   // ⭐⭐ propagated automatically
    .place(request);
```

> **⭐ Deadline propagation is the single best technical argument for gRPC in a service mesh.** In REST
> you build it yourself and someone forgets; **in gRPC it is the protocol, so a 200 ms budget at the
> edge really is 200 ms at depth four** — and downstream services stop doing work nobody is waiting for.

## ⭐ Retries, and the safety condition

| | |
|---|---|
| ⭐ gRPC service config supports retry policies | per-method backoff, retryable status codes |
| ⭐⭐ **Only retry `UNAVAILABLE` and similar** | ⭐⭐ retrying `INTERNAL` or `DEADLINE_EXCEEDED` may duplicate a completed write |
| ⭐⭐ **`DEADLINE_EXCEEDED` is case 3** | ⭐⭐ **you do not know whether it happened** (Day 398) — idempotency key required |
| ⭐ Hedging | send a second request after a delay — **only for idempotent reads** |

# Part 3 — ⭐⭐ The load balancing trap

```
⭐⭐ HTTP/2 MULTIPLEXES: ⭐ one long-lived TCP connection carries ALL calls.
⭐ ⇒ ⭐⭐ An L4 load balancer balances CONNECTIONS, not requests.
⭐ ⇒ ⭐⭐ Your client opens ONE connection ⇒ ⭐⭐ 100% of its traffic goes to ONE backend pod.
⭐ ⇒ ⭐⭐ You scale to twenty replicas and nineteen of them stay idle.
```

| ⭐ Fix | ⭐ Note |
|---|---|
| ⭐⭐ **Client-side load balancing** | ⭐⭐ resolve all endpoints (**headless service DNS**) and round-robin across them |
| ⭐⭐ **An L7 proxy that speaks gRPC** | ⭐ Envoy, a service mesh, or an ALB with a gRPC target group |
| ⭐ Periodic connection recycling | ⭐ `maxConnectionAge` on the **server** forces re-balancing |
| ⭐ NLB alone | ⭐⭐ **does not fix it** — it is L4 (Day 389) |

⚠️ **This is one of the most common "we deployed gRPC and it did not scale" incidents**, and it looks
like a performance problem rather than a routing one. **The tell: one pod at 90% CPU while the rest are
at 3%.** Naming this in an interview lands very well because it is specific and non-obvious.

# Part 4 — ⭐⭐ gRPC or REST — decided

| ⭐ Choose **gRPC** | ⭐ Choose **REST + JSON** |
|---|---|
| ⭐⭐ **internal service-to-service** | ⭐⭐ **public APIs, third parties, browsers** |
| ⭐ high call volume, latency-sensitive | ⭐ human debuggability matters |
| ⭐ you want a schema and generated clients | ⭐ consumers you do not control |
| ⭐ streaming is genuinely needed | ⭐ caching by HTTP intermediaries matters |
| ⭐ polyglot services with strict contracts | ⭐ webhooks, integrations, docs-driven APIs |

| ⭐ The honest costs of gRPC | |
|---|---|
| ⭐⭐ **Not `curl`-able** | ⭐ `grpcurl` exists, and reflection must be enabled — **but it is friction** |
| ⭐⭐ **Browsers cannot speak it** | ⭐⭐ gRPC-Web needs a proxy |
| ⭐ Load balancing needs thought | ⭐ see Part 3 |
| ⭐ A build step and generated code in the repo | ⭐ manageable, but real |
| Debugging binary payloads in production | ⭐⭐ log the decoded form, or you will regret it |

> **⭐ The mature position: gRPC inside, REST at the edge.** That is what most large systems converge on,
> and **it lets you take the strict contract and the deadline propagation internally without asking the
> outside world to change.**

## ⭐ Contracts, whichever you pick

| ⭐ Practice | |
|---|---|
| ⭐⭐ **Schema in a shared, versioned repo** | ⭐ generated per language in CI |
| ⭐⭐ **Backward-compatibility check in the pipeline** | ⭐⭐ `buf breaking` — **the change is refused, not discussed** |
| ⭐ **Consumer-driven contract tests** | ⭐ Pact — the consumer's expectations run against the provider's build |
| ⭐⭐ **Version in the package** (`orders.v1`) | ⭐⭐ a breaking change is a **new package running alongside**, never an edit |

⚠️ **The rule that actually prevents outages: both versions must run at once** — which is Day 371's
expand/migrate/contract, applied to a schema instead of a database. **Deploy the reader that understands
both, then the writer that emits the new shape, then remove the old.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Reusing a deleted field number** | ⭐⭐ old messages decode into the new field — silent corruption |
| ⭐ Not using `reserved` | ⭐ nothing stops the reuse |
| ⭐ Renaming a field and expecting breakage | ⭐ names are irrelevant on the wire — the *number* is the contract |
| ⭐ Changing a field's type | ⭐ most are not wire-compatible |
| ⭐⭐ **Enum without a 0 = UNSPECIFIED** | ⭐⭐ unset reads as your first real value |
| ⭐ Ignoring `optional` for presence | ⭐ "absent" and "zero" become indistinguishable |
| ⭐⭐ **L4 load balancing gRPC** | ⭐⭐ one pod gets everything |
| ⭐ Retrying non-idempotent calls on `DEADLINE_EXCEEDED` | ⭐⭐ duplicates — it is case 3 |
| ⭐ gRPC for a public/browser API | ⭐ needs a proxy; no human debuggability |
| ⭐ No breaking-change check in CI | ⭐⭐ compatibility becomes a code review opinion |
| ⭐ Editing `v1` instead of adding `v2` | ⭐⭐ both versions must run at once |
| Logging raw binary payloads | undebuggable in production |

## Interview questions

**Q: What are the schema evolution rules for protobuf?**
The field number is the wire identity, so never change one and never reuse one after deleting a field —
mark it `reserved` for both the number and the name so the compiler enforces it. Adding fields is always
safe because old readers ignore unknown ones. Never change a type, since only a few are wire-compatible.
And in proto3 the zero value of an enum must be an explicit UNSPECIFIED, because there is no null and an
unset field reads as zero. The reuse rule is the one that causes real damage: a message written before a
field was deleted will decode its old bytes into whatever now holds that number, with no error at all.

**Q: What does gRPC give you that REST does not?**
A schema with generated clients, a much smaller and cheaper binary encoding, HTTP/2 multiplexing, real
cancellation, and — the one I care about most — deadlines as part of the protocol. In REST you have to
build deadline propagation yourself and somebody eventually forgets, so a two-hundred-millisecond budget
at the edge becomes unbounded at depth four. In gRPC the deadline travels automatically, so downstream
services stop doing work nobody is waiting for. The costs are honest too: you cannot curl it, browsers
need a proxy, and load balancing needs deliberate handling.

**Q: A team moved to gRPC and one pod is at ninety percent CPU while the others are idle. What
happened?**
HTTP/2 multiplexes many calls over one long-lived connection, and an L4 load balancer balances
connections rather than requests — so a client that opens one connection sends all of its traffic to a
single backend forever. Scaling to twenty replicas leaves nineteen idle. The fixes are client-side load
balancing over all resolved endpoints, usually via headless service DNS, or an L7 proxy that understands
gRPC such as Envoy or a mesh. A server-side max connection age also helps by forcing periodic
rebalancing. It presents as a performance problem and is actually a routing one.

**Q: When would you not use gRPC?**
At the edge. Public APIs, third-party integrations and anything a browser calls directly are better as
REST with JSON — consumers you do not control need human-readable payloads, documentation-driven
contracts and the ability to debug with curl, and gRPC-Web requires a proxy. The pattern most large
systems converge on is gRPC inside and REST at the boundary, which gets you the strict contract and
deadline propagation internally without imposing anything on the outside world.

**Q: How do you make a breaking change to a service contract?**
You do not make it breaking. Version in the package name, so a genuinely incompatible change becomes a
new package running alongside the old one rather than an edit. Then it is expand, migrate, contract:
deploy readers that understand both shapes, then writers that emit the new shape, then remove the old
once nothing emits it. And the compatibility check belongs in CI — a tool like `buf breaking` refuses
the change rather than leaving it to a reviewer's judgement, which is what turns the rule into a
guarantee.

## 🎙️ Articulation drill

**Two minutes:** *"How do you version a service contract?"*

**⭐ Start from the protobuf rule because it generalises: the field number is the contract, not the name
— so renames are free, additions are free, and the only genuinely dangerous act is reusing a deleted
number, which decodes old bytes into a new field with no error at all. `reserved` exists to make that
impossible, and it belongs in the diff that deletes the field.**

**⭐ Then the process: version in the package name so a breaking change becomes a new package running
beside the old one, never an edit; expand, migrate, contract, because both versions have to run at
once; and a breaking-change check in CI so compatibility is a build failure rather than a reviewer's
opinion.**
