# Part 1 — L-084 · The object model

## Git is a content-addressed key-value store

That is the whole thing. `.git/objects` is a database mapping **SHA-1 hash → content**. The key *is*
the hash of the value, so identical content is stored once, ever, and any change to content changes
its address.

There are exactly **four object types**:

| Object | Contains |
|---|---|
| **blob** | File *contents*. No name, no permissions, no history |
| **tree** | A directory: a list of (mode, type, hash, name) entries pointing at blobs and trees |
| **commit** | A snapshot: one tree hash, zero or more parent hashes, author, committer, message |
| **tag** | An annotated tag: an object hash, a name, a tagger, a message |

```
commit 3f2a1b…
  ├── tree 9c8d7e…                          "the whole project at this moment"
  │     ├── blob 5a4b3c…  README.md
  │     ├── blob 1f2e3d…  pom.xml
  │     └── tree 7b6c5d…  src/
  │           └── tree …   main/java/
  │                 └── blob …  App.java
  ├── parent 8e7f6a…                         ← the previous commit
  ├── author  Ram <ram@…>  1755172800 +0530
  └── message "Add health endpoint"
```

Three consequences follow immediately, and they answer most Git confusion:

**1. A commit is a *snapshot*, not a diff.** Git stores the complete tree each time. Diffs are
*computed* when you ask for them. (Packfiles delta-compress on disk, but that is storage
optimisation invisible to the model.)

**2. Git does not track renames.** It stores blobs by content. `git log --follow` and rename
detection in `git diff` are **heuristics run at display time** — Git compares contents and guesses.
That is why moving a file and editing it heavily can lose the "rename" label.

**3. The hash covers everything, including history.** A commit's hash includes its parent's hash,
which includes *its* parent's — so **the hash of a commit fixes the entire history behind it**. Alter
any past commit and every descendant hash changes. That is why `git rebase` on a shared branch is
disruptive, and why a Git repository is tamper-evident.

## Build a commit by hand

**Type all of this.** This is the exercise that makes the model concrete.

```bash
mkdir gitlab && cd gitlab && git init
```

```bash
# 1. Create a BLOB — the content, nothing else
echo "hello world" | git hash-object -w --stdin
# 3b18e512dba79e4c8300dd08aeb37f8e728b8dad

git cat-file -t 3b18e5      # blob
git cat-file -p 3b18e5      # hello world
git cat-file -s 3b18e5      # 12

# The hash is deterministic — the same content anywhere gives the same hash
echo "hello world" | git hash-object --stdin      # same value, on any machine, forever
```

Why that specific hash? Git hashes `"blob 12\0hello world"` — the type, a space, the byte length, a
NUL, then the content. You can verify it:

```bash
printf 'blob 12\0hello world\n' | sha1sum        # matches
```

```bash
# 2. Create a TREE via the index
git update-index --add --cacheinfo 100644,3b18e512dba79e4c8300dd08aeb37f8e728b8dad,greeting.txt
git write-tree
# 68aba62e560c0ebc3396e8ae9335232cd93a3f60

git cat-file -p 68aba6
# 100644 blob 3b18e512…    greeting.txt
```

**The tree is where the filename lives** — not the blob. That is exactly why renaming is free (a new
tree, the same blob) and why Git has no rename records.

```bash
# 3. Create a COMMIT
echo "first commit" | git commit-tree 68aba62e560c0ebc3396e8ae9335232cd93a3f60
# a1b2c3d4…

git cat-file -p a1b2c3
# tree 68aba62e560c0ebc3396e8ae9335232cd93a3f60
# author Ram <ram@example.com> 1755172800 +0530
# committer Ram <ram@example.com> 1755172800 +0530
#
# first commit
```

```bash
# 4. Point a REF at it — this is the only thing that makes it visible
git update-ref refs/heads/main a1b2c3d4…
git log                                    # your hand-built commit
cat .git/refs/heads/main                   # just a file containing the hash
cat .git/HEAD                              # ref: refs/heads/main
```

You just made a commit with no `git add` and no `git commit`. **Everything else in Git is
convenience on top of these four steps.**

## Refs — branches are trivial

```bash
cat .git/refs/heads/main      # a 40-character hash. That is all a branch is.
cat .git/HEAD                 # "ref: refs/heads/main" — a pointer to a pointer
```

> **A branch is a 41-byte file containing a commit hash.**

Which explains a great deal:

- Creating a branch is instant — it writes one file. There is nothing to copy.
- "Moving" a branch rewrites that file. `git reset --hard` moves the pointer; the commits are
  untouched.
- **HEAD** normally holds `ref: refs/heads/<branch>`. In **detached HEAD** it holds a raw commit
  hash — that is the entire mystery: HEAD points at a commit instead of at a branch, so new commits
  have no branch to advance and become unreachable when you leave.
- Deleting a branch deletes a pointer, not commits. The commits survive until garbage collection,
  which is why the reflog can rescue them (Day 087).

```bash
git symbolic-ref HEAD          # what HEAD points at
git rev-parse HEAD             # the commit hash
git rev-parse main~2           # two commits back
git rev-parse HEAD^{tree}      # the tree of the current commit
```

Ref namespaces: `refs/heads/*` local branches, `refs/remotes/origin/*` remote-tracking branches,
`refs/tags/*` tags. Nothing magic — files under `.git/refs`, or lines in `.git/packed-refs`.

## The three areas

```
  Working tree  ──git add──▶  Index (staging)  ──git commit──▶  Repository
  (your files)                (a proposed tree)                 (objects + refs)
        ▲                            │                                │
        └──────git checkout──────────┴──────git reset ────────────────┘
```

**The index is a real file** — `.git/index` — containing a list of paths, modes and blob hashes. It
is a *staged tree waiting to be written*, which is why:

- `git add` creates a blob **immediately** and records it in the index. Editing the file afterwards
  means the index holds the older content — the cause of "I fixed it but the commit is still wrong".
- `git status` compares three things: working tree ↔ index ↔ HEAD.
- `git diff` is working tree vs index; `git diff --staged` is index vs HEAD; `git diff HEAD` is
  working tree vs HEAD.

```bash
git ls-files -s          # the index: mode, blob hash, stage, path
```

## Reachability and garbage collection

An object is **reachable** if you can walk to it from a ref (branch, tag, HEAD) or the reflog. This
is exactly Day 026's GC reachability, applied to a commit graph.

```bash
git fsck --lost-found        # unreachable objects
git reflog                   # HEAD's history — how "lost" commits are found
git gc                       # pack and prune unreachable objects (after ~2 weeks)
```

> **Nothing committed is truly lost for about two weeks.** A "destroyed" branch is a ref that moved;
> the commits are still there, and the reflog knows where they were. Internalising this removes most
> of the fear people have of Git.

## Why hashes matter for integrity

Because a commit hash covers its whole ancestry, **you cannot alter history without changing every
subsequent hash.** If your local `main` and the server's `main` share a hash, you have bit-for-bit
identical history — no diffing required. This is the same content-addressing idea as Docker image
layers and IPFS.

Git is migrating from SHA-1 to SHA-256 for collision resistance; SHA-1 collisions (SHAttered, 2017)
do not practically break Git, which adds extra detection, but the migration is underway. Know this
exists.

# Part 2 — D-03 · ER modelling

## The purpose

An **entity-relationship model** is a design-time picture of the data *before* you write tables. Its
value is that it forces the questions tables let you skip: what is a thing, what identifies it, and
how many of each relate to how many of the other.

| ER concept | Notation | Becomes |
|---|---|---|
| **Entity** | rectangle | A table |
| **Attribute** | oval | A column |
| **Key attribute** | underlined | Primary key |
| **Relationship** | diamond | A foreign key or a join table |
| **Cardinality** | 1:1, 1:N, M:N | Determines *where* the key goes |
| **Weak entity** | double rectangle | Depends on an owner for identity |

## Cardinality decides the schema

```
  1:1     Person ──── Passport
          → foreign key on EITHER side, with UNIQUE. Put it on the optional side.

  1:N     Customer ──< Order
          → foreign key on the MANY side (order.customer_id). Never on the one side.

  M:N     Student >──< Course
          → a JOIN TABLE (enrollment) with both foreign keys as a composite key.
```

**The 1:N rule is the one to say instantly: the foreign key goes on the "many" side.** A customer
cannot hold a list of order ids in a column — that would violate 1NF (Day 081's D-02).

**M:N always becomes a third table.** And that table almost always earns its own attributes —
`enrolled_on`, `grade` — at which point it stops being a mechanical artefact and becomes an entity
in its own right. That transformation is the sign your model is maturing.

Participation matters too: **total** participation (every order must have a customer) becomes
`NOT NULL`; **partial** (a customer may have no orders) becomes nullable or simply no constraint.

## Worked example — a library

**Entities:** `member`, `book`, `book_copy`, `loan`, `author`.

The interesting decision is `book` versus `book_copy`. A library owns five physical copies of one
title. If you model only `book`, you cannot say which copy is on loan, and you end up with a
`copies_available` counter that goes wrong under concurrency. Splitting them makes each physical
copy a row you can lend.

```sql
CREATE TABLE member (
    id         BIGSERIAL PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,             -- natural key, uniquely constrained
    name       TEXT NOT NULL,
    joined_on  DATE NOT NULL DEFAULT CURRENT_DATE
);

CREATE TABLE book (
    id     BIGSERIAL PRIMARY KEY,
    isbn   CHAR(13) NOT NULL UNIQUE,             -- natural key
    title  TEXT NOT NULL
);

CREATE TABLE author (
    id   BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

-- M:N — a book has many authors, an author writes many books
CREATE TABLE book_author (
    book_id   BIGINT NOT NULL REFERENCES book(id)   ON DELETE CASCADE,
    author_id BIGINT NOT NULL REFERENCES author(id) ON DELETE RESTRICT,
    ordinal   SMALLINT NOT NULL DEFAULT 1,          -- author order on the cover
    PRIMARY KEY (book_id, author_id)
);

-- WEAK ENTITY: a copy has no identity without its book
CREATE TABLE book_copy (
    book_id     BIGINT NOT NULL REFERENCES book(id) ON DELETE RESTRICT,
    copy_no     SMALLINT NOT NULL,
    acquired_on DATE NOT NULL,
    PRIMARY KEY (book_id, copy_no)                  -- composite: owner + discriminator
);

-- 1:N from both member and book_copy
CREATE TABLE loan (
    id          BIGSERIAL PRIMARY KEY,
    member_id   BIGINT NOT NULL REFERENCES member(id) ON DELETE RESTRICT,
    book_id     BIGINT NOT NULL,
    copy_no     SMALLINT NOT NULL,
    borrowed_on DATE NOT NULL DEFAULT CURRENT_DATE,
    due_on      DATE NOT NULL,
    returned_on DATE,                               -- NULL = still out
    FOREIGN KEY (book_id, copy_no) REFERENCES book_copy(book_id, copy_no),
    CHECK (returned_on IS NULL OR returned_on >= borrowed_on)
);

-- one copy can be on loan only once at a time
CREATE UNIQUE INDEX one_active_loan_per_copy
    ON loan (book_id, copy_no) WHERE returned_on IS NULL;
```

Four modelling decisions worth naming, because they are what an interviewer probes:

**`book_copy` is a weak entity** — copy 3 means nothing without knowing *of which book*, so its key
is the owner's key plus a discriminator.

**`returned_on IS NULL` encodes "currently on loan"** rather than a separate boolean, which cannot
drift out of sync with the date.

**The partial unique index enforces the real business rule** — one active loan per copy — in the
database rather than in application code. That is Day 081's constraint principle made concrete, and
it holds even if a second service starts writing.

**`ON DELETE RESTRICT` on `member`** means you cannot delete a member with loan history. Correct: the
history is a fact, and deleting it would falsify the record. Use a `deactivated_on` column instead —
**soft delete for anything with history**.

## Common modelling errors

| Error | Fix |
|---|---|
| Comma-separated list in a column | It is an M:N — make the join table |
| M:N modelled with two foreign keys | Impossible; you need the third table |
| Foreign key on the "one" side of 1:N | Put it on the many side |
| No unique constraint on the natural key | Surrogate id lets duplicates in |
| Storing derived values (`total`, `age`) | Compute, or accept the sync burden deliberately |
| `CASCADE` on historical records | Silent data loss |
| One table with 60 nullable columns | Two or three entities wearing a trenchcoat |

## Common mistakes

| Mistake | Consequence |
|---|---|
| Thinking commits store diffs | Rebase, cherry-pick and merge all become confusing |
| Expecting Git to track renames | It infers them; heavy edits lose the inference |
| Believing a deleted branch loses commits | Panic instead of `git reflog` |
| Editing a file after `git add` | You commit the earlier content |
| Fearing detached HEAD | It is just HEAD holding a hash instead of a branch name |
| Rewriting shared history | Every descendant hash changes for everyone |

## Interview questions

**Q: What are Git's four object types?**
Blob (contents), tree (a directory listing pointing at blobs and trees), commit (a tree plus
parents plus metadata), and annotated tag. All are content-addressed by the hash of their contents.

**Q: Does Git store diffs or snapshots?**
Snapshots. Each commit references a complete tree; diffs are computed on demand. Packfiles delta
compress on disk, but that is invisible to the model.

**Q: What is a branch?**
A file containing a commit hash. Creating, deleting and moving one is a pointer operation — which is
why branching is instant and why deleting a branch does not delete commits.

**Q: What is detached HEAD?**
HEAD holding a commit hash directly instead of `ref: refs/heads/<name>`. Commits made there advance
no branch, so they become unreachable when you check out something else — recoverable via the reflog.

**Q: Why does rewriting history change every later commit?**
A commit's hash includes its parent's hash. Change anything about an ancestor and every descendant's
hash necessarily changes, so the rewritten commits are new objects.

**Q: How do you map a M:N relationship to tables?**
A join table with foreign keys to both sides, usually with a composite primary key — and it often
gains its own attributes, at which point it is an entity.

**Q: Where does the foreign key go in a 1:N relationship?**
On the "many" side. Putting a list on the "one" side would violate first normal form.
