# Part 1 — L-036 · Encapsulation

## What encapsulation actually is

**Not "make fields private and add getters."** That's the mechanism, and applying it thoughtlessly
produces classes that are exactly as exposed as public fields.

**Encapsulation is: hide the representation, expose the behaviour.** The caller should depend on
what your object *does*, not on how it stores anything.

```java
// 💀 Encapsulation theatre — private fields, but the representation is fully exposed
class Account {
    private double balance;
    public double getBalance()          { return balance; }
    public void setBalance(double b)    { balance = b; }      // any caller can set anything
}

account.setBalance(account.getBalance() - 100);   // the LOGIC lives outside the object
```

Every rule about balances — can't go negative, must be logged, must be atomic — is now the caller's
problem, repeated at every call site, and one of them will get it wrong.

```java
// ✅ Behaviour exposed, representation hidden
class Account {
    private BigDecimal balance;

    public void withdraw(BigDecimal amount) {
        if (amount.signum() <= 0) throw new IllegalArgumentException("must be positive");
        if (balance.compareTo(amount) < 0) throw new InsufficientFundsException();
        balance = balance.subtract(amount);
        audit.log(WITHDRAWAL, amount);
    }

    public BigDecimal balance() { return balance; }    // read-only; BigDecimal is immutable
}
```

**The invariant is now enforced in one place and cannot be bypassed.** That's the point.

> **The test:** could you change the internal representation — `double` to `BigDecimal`, a field to a
> computed value, one field to three — without changing a single caller? If not, you haven't
> encapsulated anything.

**A setter for every field is a design smell.** Ask what the caller is actually trying to *do*, and
name a method after that.

## The four access levels

| Modifier | Same class | Same package | Subclass (other package) | Anywhere |
|---|---|---|---|---|
| `private` | ✅ | ❌ | ❌ | ❌ |
| *(default / package-private)* | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

**Default to `private`. Widen only when required.** Narrowing later is a breaking change; widening is
not.

### The two people misunderstand

**`protected` includes package access.** It's *wider* than package-private, not a sibling of it — a
class in the same package can access a `protected` member without any inheritance relationship.

**`protected` is part of your public API.** Once you make a member protected, every subclass anywhere
can depend on it, so you can never change it. *Effective Java*: design and document for inheritance,
or prohibit it (Day 034).

**Package-private is underused.** It's the natural visibility for collaborating classes within one
feature package — visible to the code that needs it, invisible to everything else. Most Java codebases
would be improved by using it more and `public` less.

## Package structure

Two competing schemes:

```
   LAYERED (by technical role)        FEATURE-BASED (by domain)
   com.app.controller/               com.app.order/
     UserController                    OrderController
     OrderController                   OrderService
   com.app.service/                    OrderRepository
     UserService                       Order
     OrderService                    com.app.user/
   com.app.repository/                 UserController
     UserRepository                    UserService
   com.app.model/                      UserRepository
     User, Order                       User
```

| | Layered | Feature-based |
|---|---|---|
| A change to one feature touches | **Every package** | **One package** |
| Package-private is useful | ❌ (collaborators are in different packages) | ✅ **Very** |
| Scales to a large codebase | Poorly | Well |
| Familiar from tutorials | ✅ | Less so |

**Feature-based packaging is better**, and the decisive argument is package-private: with layered
packaging, `OrderService` and `OrderRepository` sit in different packages, so every collaboration must
be `public`. With feature packaging, only `OrderController` need be public and the rest of the feature
is sealed off.

This is Day 141 in the Spring stage; deciding it now saves a refactor later.

## JPMS — the module system (overview)

Java 9's module system adds a level above packages.

```java
// module-info.java
module com.app.orders {
    requires com.app.common;              // dependencies, declared
    exports com.app.orders.api;           // ONLY this package is visible outside
    // com.app.orders.internal is INVISIBLE, even though its classes are public
}
```

**The problem it solves:** `public` used to mean "visible to the entire world". A class marked
`public` because another package in your own library needed it was also visible to every consumer, so
it became part of your API by accident.

**Modules add strong encapsulation at the JAR level:** a package not `exports`ed is unreachable
outside the module, even for `public` classes, and even via reflection unless `opens`.

**Reality check:** the JDK itself is modularised, which is why `--illegal-access` warnings and
`InaccessibleObjectException` exist when a library reflects into JDK internals. **Most applications
still don't use JPMS** — Spring Boot fat JARs use the classpath. Know what it is and why it exists;
you're unlikely to author `module-info.java` soon.

## Getters, setters, and what to expose

```java
// 💀 leaks the internal list — Day 034A
public List<Item> getItems() { return items; }

// ✅
public List<Item> items() { return List.copyOf(items); }
public void addItem(Item i) { items.add(i); }        // behaviour, with room for validation
```

**Records change the convention:** accessors are named `items()`, not `getItems()`. Modern Java
codebases increasingly drop the `get` prefix for value types. Be consistent within a codebase; note
that frameworks relying on the JavaBeans convention (older Jackson configs, some JSP tooling) still
expect `getX`.

## Type this yourself

```java
import java.math.BigDecimal;
import java.util.*;

public class EncapsulationDemo {

    // ---- Encapsulation theatre ----
    static class LeakyAccount {
        private BigDecimal balance = BigDecimal.ZERO;
        private final List<String> history = new ArrayList<>();
        public BigDecimal getBalance()            { return balance; }
        public void setBalance(BigDecimal b)      { balance = b; }
        public List<String> getHistory()          { return history; }   // leaks internals
    }

    // ---- Real encapsulation ----
    static class SafeAccount {
        private BigDecimal balance = BigDecimal.ZERO;
        private final List<String> history = new ArrayList<>();

        public void deposit(BigDecimal amount) {
            requirePositive(amount);
            balance = balance.add(amount);
            history.add("deposit " + amount);
        }

        public void withdraw(BigDecimal amount) {
            requirePositive(amount);
            if (balance.compareTo(amount) < 0)
                throw new IllegalStateException("insufficient funds");
            balance = balance.subtract(amount);
            history.add("withdraw " + amount);
        }

        public BigDecimal balance()        { return balance; }             // BigDecimal is immutable
        public List<String> history()      { return List.copyOf(history); } // defensive copy
        private static void requirePositive(BigDecimal a) {
            if (a.signum() <= 0) throw new IllegalArgumentException("must be positive");
        }
    }

    public static void main(String[] args) {
        LeakyAccount leaky = new LeakyAccount();
        leaky.setBalance(new BigDecimal("-1000000"));                 // no rule stops this
        leaky.getHistory().add("fabricated entry");                    // internals mutated
        System.out.println("Leaky balance: " + leaky.getBalance());
        System.out.println("Leaky history: " + leaky.getHistory());

        SafeAccount safe = new SafeAccount();
        safe.deposit(new BigDecimal("500"));
        try { safe.withdraw(new BigDecimal("1000")); }
        catch (IllegalStateException e) { System.out.println("\nBlocked: " + e.getMessage()); }
        try { safe.deposit(new BigDecimal("-100")); }
        catch (IllegalArgumentException e) { System.out.println("Blocked: " + e.getMessage()); }
        try { safe.history().add("fabricated"); }
        catch (UnsupportedOperationException e) { System.out.println("Blocked: history is a copy"); }

        System.out.println("\nSafe balance: " + safe.balance());
        System.out.println("Safe history: " + safe.history());
    }
}
```

**The point:** both classes have `private` fields. Only one is encapsulated.

## Interview questions

**Q: What is encapsulation?**
> Hiding an object's internal representation and exposing behaviour instead, so callers depend on
> what it does rather than how it stores data. Private fields with public getters and setters for
> every field is not encapsulation — the representation is still fully exposed and the invariants
> still live in the callers.

**Q: What's the difference between `protected` and package-private?**
> `protected` is wider: it grants access to subclasses in other packages *and* to everything in the
> same package. Package-private grants access only within the package. `protected` also becomes part
> of your public API, since any subclass anywhere can depend on it.

**Q: Layered or feature-based packages?**
> Feature-based. A change to one feature stays in one package, and it makes package-private useful —
> only the entry point needs to be public and the rest of the feature is sealed off. With layered
> packaging, collaborating classes sit in different packages so everything has to be public.

**Q: What problem does JPMS solve?**
> Before modules, `public` meant visible everywhere, so a class made public for internal reuse became
> part of your API by accident. Modules let a JAR declare which packages it exports, so unexported
> packages are inaccessible outside the module even if their classes are public — strong
> encapsulation at the JAR level.

# Part 2 — B-05 · CPU scheduling

## The problem

More runnable threads than cores. The scheduler decides who runs next, and it's optimising several
things that conflict:

| Goal | Wants |
|---|---|
| **Throughput** | Maximise work completed |
| **Latency / response time** | Minimise time to first response |
| **Fairness** | No task starves |
| **Efficiency** | Minimise context switches (Day 033, B-04) |

**You cannot maximise all of them.** Optimise for throughput and interactive tasks feel sluggish.
Optimise for latency and you switch more, costing throughput. Every algorithm below is a different
point on that trade-off.

## The algorithms

### FCFS — First Come First Served

Run to completion, in arrival order. Non-preemptive.

**The convoy effect:** one long task blocks everything behind it. A 10-second job arriving before ten
100 ms jobs makes them all wait 10 seconds.

Simple, terrible for interactivity. Essentially never used for CPU scheduling — but it *is* how a
single-threaded task queue behaves, which is worth recognising.

### SJF — Shortest Job First

**Provably optimal for average waiting time.** And unusable, because you can't know a job's length in
advance. Approximated by predicting from past behaviour.

**Starvation:** a long job may never run if short ones keep arriving.

### Priority scheduling

Highest priority first. **Starvation** again — a low-priority task can wait forever.

**Aging** fixes it: raise a task's priority the longer it waits.

**Priority inversion** — the famous failure:

```
   LOW-priority task holds a lock
   HIGH-priority task needs that lock → blocks
   MEDIUM-priority task preempts LOW → LOW never releases the lock
   → HIGH is effectively blocked by MEDIUM
```

**This nearly killed the Mars Pathfinder mission in 1997** — the rover kept resetting, and the fix
uploaded from Earth enabled *priority inheritance*, where the lock holder temporarily inherits the
waiter's priority. It's a great story to have ready, and it's the reason Java's
`Thread.setPriority()` is essentially a hint the OS may ignore.

### Round Robin

Each task gets a fixed **time quantum**, then goes to the back of the queue. Preemptive.

**The quantum is the whole trade-off:**
- **Too small** → excellent responsiveness, but context-switch overhead dominates (Day 033, B-04)
- **Too large** → degenerates toward FCFS

Typically 10–100 ms. Fair and simple; no starvation.

### MLFQ — Multi-Level Feedback Queue

Multiple queues at different priorities, and **tasks move between them based on observed behaviour**:

```
   Q0 (highest, quantum 10ms)  ← new tasks start here
        │ used the full quantum? demote
        ▼
   Q1 (quantum 20ms)
        │ used the full quantum? demote
        ▼
   Q2 (lowest, quantum 40ms)   ← CPU-bound tasks sink here
```

**The insight: infer the job type from behaviour rather than asking.** A task that blocks quickly is
interactive — keep it high priority. A task that burns its whole quantum is CPU-bound — demote it;
it cares about throughput, not latency.

Periodic **priority boost** returns everything to the top, preventing starvation and handling tasks
that change behaviour.

**This approximates SJF without needing to know job lengths** — which is why MLFQ underpinned
traditional Unix and Windows schedulers.

### Linux CFS — Completely Fair Scheduler

Modern Linux (until the EEVDF replacement landed in 6.6) tracks **virtual runtime** per task and
always runs the one with the lowest — the task that has had the least CPU so far.

```
   vruntime += actual_runtime × (weight_of_nice_0 / weight_of_this_task)
```

- Tasks are kept in a red-black tree ordered by vruntime — O(log n) to pick the next
- **`nice` values scale the weight**, so a higher-priority task's vruntime advances more slowly and
  it gets a larger share
- No fixed time slices; the target latency is divided proportionally

**The model:** rather than approximating fairness with queues and quanta, track how much CPU each
task *should* have had and always run the one furthest behind.

## Why this matters in Java

- **`Thread.setPriority()` is a hint.** The mapping to OS priorities is platform-dependent and often
  ignored. Never rely on it for correctness.
- **More runnable threads than cores means more switching, not more work** — Day 033's measurement.
- **Blocked threads aren't scheduled at all** (Day 026, B-02: BLOCKED vs READY), which is exactly why
  I/O-bound pools can exceed core count.
- **Virtual threads move scheduling into the JVM** (Day 072). The JVM's `ForkJoinPool` schedules
  virtual threads onto carriers, so you now have two schedulers stacked — and the JVM's has better
  information about what your tasks are doing.

## Type this yourself

```bash
# Linux
nice -n 10 java YourApp             # start with lower priority
chrt -p <pid>                       # scheduling policy of a running process
cat /proc/<pid>/sched               # vruntime and scheduling stats
top -H -p <pid>                     # per-THREAD view

# Windows
Get-Process java | Select-Object Id, PriorityClass, Threads
```

```java
public class SchedulingDemo {
    public static void main(String[] args) throws Exception {
        // Priorities are a HINT. Run this a few times and watch the results vary.
        Runnable work = () -> {
            long count = 0;
            long end = System.currentTimeMillis() + 2000;
            while (System.currentTimeMillis() < end) count++;
            System.out.printf("%s (priority %d): %,d iterations%n",
                    Thread.currentThread().getName(),
                    Thread.currentThread().getPriority(), count);
        };

        Thread low  = new Thread(work, "LOW");
        Thread high = new Thread(work, "HIGH");
        low.setPriority(Thread.MIN_PRIORITY);      // 1
        high.setPriority(Thread.MAX_PRIORITY);     // 10

        low.start(); high.start();
        low.join();  high.join();

        System.out.println("\nIf the counts are similar, the OS ignored the priorities.");
    }
}
```

**Run it several times.** On most systems the counts are close, which demonstrates the point: Java
thread priorities are advisory. **Never build correctness on them.**

## Interview questions

**Q: What is the convoy effect?**
> Under first-come-first-served scheduling, one long-running task blocks every shorter task behind it,
> so average waiting time becomes terrible. It's the main argument for preemptive scheduling.

**Q: What is priority inversion and how is it fixed?**
> A high-priority task blocks on a lock held by a low-priority task, and a medium-priority task
> preempts the low-priority one, so the lock is never released and the high-priority task is
> indirectly blocked by the medium one. The fix is priority inheritance — the lock holder temporarily
> inherits the highest waiting priority. It famously caused the Mars Pathfinder resets in 1997.

**Q: How does a multi-level feedback queue work?**
> Multiple priority queues with different time quanta. Tasks start at the highest priority and are
> demoted if they consume their full quantum, so CPU-bound tasks sink and interactive tasks that block
> early stay high. A periodic boost returns everything to the top to prevent starvation. It
> approximates shortest-job-first without needing to know job lengths.

**Q: How does Linux CFS decide what to run?**
> It tracks each task's virtual runtime — actual runtime scaled by its weight, which derives from its
> nice value — and always runs the task with the lowest vruntime, kept in a red-black tree. Rather
> than approximating fairness with quanta, it tracks how much CPU each task should have received and
> runs whichever is furthest behind.

**Q: Does `Thread.setPriority()` do anything in Java?**
> It's a hint that maps to platform priorities in an implementation-dependent way and is frequently
> ignored. It should never be relied on for correctness — use proper synchronisation or explicit
> queueing instead.
