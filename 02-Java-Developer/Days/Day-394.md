**L-394** · CloudWatch, X-Ray and CloudTrail — observability with a price tag

# Part 1 — ⭐⭐ CloudWatch metrics, and what they cost

| | |
|---|---|
| ⭐ Resolution | ⭐ standard **1 minute**; high-resolution 1 second (costs more) |
| ⭐⭐ **A metric = name + a UNIQUE set of dimensions** | ⭐⭐ `Latency{service=api,endpoint=/orders}` is **one** metric |
| ⭐⭐ **Pricing** | ⭐⭐ **~$0.30 per custom metric per month** |
| ⭐ Retention | 15 months, automatically rolled up |
| ⭐ API cost | ⭐ `PutMetricData` and `GetMetricData` are billed per call too |

```
⭐⭐ CARDINALITY WITH A PRICE TAG:
⭐   latency{endpoint, status, customer_id}
⭐   ⭐ 20 endpoints × 5 statuses × ⭐⭐ 10,000 customers = ⭐⭐ 1,000,000 metrics
⭐   ⇒ ⭐⭐ $300,000 PER MONTH.
⭐ ⇒ ⭐⭐ In Prometheus, high cardinality kills the server. In CloudWatch, IT SENDS AN INVOICE.
⭐   ⭐ Same lesson (Day 373), different failure mode: ⭐⭐ NEVER put an unbounded id in a dimension.
```

## ⭐⭐ CloudWatch vs Prometheus — decided, not fudged

| | ⭐ CloudWatch | ⭐ Prometheus / AMP |
|---|---|---|
| ⭐ Model | ⭐ push | ⭐ pull (Day 373) |
| ⭐⭐ **AWS service metrics** | ⭐⭐ **only source — ALB, RDS, SQS, Lambda** | ⭐ via exporters, awkwardly |
| ⭐⭐ **Application metrics** | ⭐ expensive at cardinality | ⭐⭐ **cheap, and PromQL is far better** |
| Query | Metrics Insights (SQL-ish) | ⭐⭐ PromQL |
| Operations | ⭐ zero | ⭐ real, unless you use AMP |

> **⭐ The sensible split, and it is worth saying as a recommendation rather than a survey: CloudWatch
> for AWS-service metrics (you have no alternative), Prometheus for application metrics (cheaper and
> better queries), Grafana over both** (Day 374). **Alarms can live in either; the burn-rate alerting
> from Day 374 is much easier to express in PromQL.**

## ⭐⭐ Embedded Metric Format — metrics out of logs, free of extra calls

```json
{ "message": "order placed", "orderId": "o-123", "durationMs": 47,
  "_aws": { "Timestamp": 1755100000000,
    "CloudWatchMetrics": [{ "Namespace": "Orders",
      "Dimensions": [["Service"]], "Metrics": [{ "Name": "durationMs", "Unit": "Milliseconds" }] }] },
  "Service": "checkout" }
```

**⭐⭐ Write one structured log line; CloudWatch extracts a metric from it.** No `PutMetricData` call, no
extra latency on your request path, **and the high-cardinality fields stay in the log (queryable via
Logs Insights) while only the low-cardinality dimensions become billed metrics.** It is a genuinely
elegant answer to the cardinality problem and most people have never heard of it.

# Part 2 — ⭐⭐ Alarms, and the one that silently stops working

| ⭐ Concept | |
|---|---|
| ⭐ States | `OK`, `ALARM`, ⭐⭐ **`INSUFFICIENT_DATA`** |
| ⭐ Evaluation | ⭐ "M out of N datapoints breaching" — **use M-of-N to kill flapping** |
| ⭐⭐ **`TreatMissingData`** | ⭐⭐ `missing` (default) · `notBreaching` · `breaching` · `ignore` |
| ⭐ Composite alarms | ⭐⭐ **AND/OR of alarms — the fix for alarm storms** (Day 374) |
| ⭐ Anomaly detection | a learned band rather than a fixed threshold |

```
⭐⭐ THE SILENT FAILURE:
⭐   Alarm: ErrorRate > 1%, ⭐⭐ TreatMissingData = notBreaching
⭐   ⇒ ⭐⭐ THE SERVICE STOPS ENTIRELY. No requests ⇒ no metric published ⇒ MISSING data
⭐   ⇒ ⭐⭐ "notBreaching" ⇒ the alarm goes to OK. ⭐⭐ TOTAL OUTAGE, ALARM GREEN.
⭐ ⇒ ⭐ FIX: for availability-critical metrics use ⭐⭐ `breaching`, and pair with a
⭐        ⭐⭐ separate "no data received" alarm. ⭐ Absence of signal IS a signal.
```

> **⭐⭐ "Absence of signal is a signal" is the sentence to carry out of this day.** It is the same class
> of bug as Day 373's `rate()` window returning nothing: **the dashboard is empty and the alarm is
> green, and both of those look like health.**

| ⭐ Composite alarms, concretely | |
|---|---|
| ⭐ Instead of | 40 instance alarms paging at 3am |
| ⭐⭐ **Do this** | ⭐⭐ `ALARM(service_error_rate) AND NOT ALARM(dependency_down)` → **one page with a cause attached** |

# Part 3 — ⭐⭐ Logs, and the default that costs the most

```
⭐⭐ CloudWatch Logs default retention = ⭐⭐ NEVER EXPIRE.
⭐ ⇒ ⭐⭐ Ingestion ~$0.50/GB, storage ~$0.03/GB-month, FOREVER, on every log group
⭐    created automatically by every Lambda, every ECS task, every service you ever tried.
⭐ ⇒ ⭐⭐ SET RETENTION ON EVERY LOG GROUP. ⭐ It is the single highest-ROI one-line change
⭐    on most AWS bills (Day 396), and it is missing almost everywhere.
```

| ⭐ Tool | |
|---|---|
| ⭐ **Logs Insights** | ⭐ query language over log groups; **billed per GB scanned** — so **always narrow the time range first** |
| ⭐⭐ **Subscription filters** | ⭐⭐ stream logs to Kinesis/Firehose → **S3 or OpenSearch or a third party** |
| ⭐ Metric filters | ⭐ turn a log pattern into a metric (**pre-EMF approach**) |
| ⭐ Live Tail | ⭐ real-time; useful, billed per minute |

```
⭐ /* Logs Insights: the p99 of your own duration field */
⭐ fields @timestamp, durationMs
⭐ | filter service = "checkout" and ispresent(durationMs)
⭐ | stats count(*), pct(durationMs, 99) as p99 by bin(5m)
```

> **⭐ The archive pattern worth knowing: 7–14 days of retention in CloudWatch Logs for interactive
> debugging, plus a subscription filter to Firehose → S3 with a lifecycle to Glacier for compliance.**
> **You keep everything and stop paying CloudWatch prices for the part you never query.**

⚠️ **Container Insights and enhanced monitoring are excellent and are billed per metric per resource per
month.** On a large fleet they can become a surprisingly big line. **Turn them on deliberately, on the
services that need them.**

# Part 4 — ⭐ X-Ray, ADOT, and CloudTrail

| | |
|---|---|
| ⭐ **X-Ray** | ⭐ AWS-native tracing: service map, sampling rules, integrated with Lambda/API GW |
| ⭐⭐ **ADOT (AWS Distro for OpenTelemetry)** | ⭐⭐ **the portable choice** — OTel SDK/collector, export to X-Ray *and/or* anywhere else |
| ⭐ Verdict | ⭐⭐ **instrument with OpenTelemetry** (Day 376); **export to X-Ray if you want the AWS service map** |

**⭐ The reason to prefer OTel is not ideology, it is that instrumentation is the expensive part.** Code
annotated with a vendor SDK is a migration; **code annotated with OTel is a config change.** X-Ray's
sampling and service map are good; **the SDK lock-in is the part you avoid.**

## ⭐⭐ CloudTrail — not observability, audit

| | |
|---|---|
| ⭐⭐ **Every API call in the account** | ⭐⭐ **who, when, from where, with which credential, and the parameters** |
| ⭐ Management events | ⭐ on by default, 90 days in the console |
| ⭐ Data events | ⭐ S3 object-level, Lambda invokes — **off by default, high volume, billed** |
| ⭐⭐ **Organization trail to a separate account** | ⭐⭐ **the log the compromised account cannot delete** |
| ⭐ CloudTrail Lake / Athena | queryable history |

```
⭐⭐ THE QUESTIONS ONLY CLOUDTRAIL ANSWERS:
⭐   "Who deleted the security group at 02:14?"
⭐   "Which role read that secret, and from what IP?"
⭐   "Did anyone assume the break-glass role this month?"   (Day 382)
⭐ ⇒ ⭐⭐ And it must live in ANOTHER ACCOUNT, or the first thing an attacker does is turn it off.
```

⚠️ **GuardDuty deserves a line here: it reads CloudTrail, VPC flow logs and DNS logs and flags things
like "these credentials are being used from an unusual location" or "this instance is talking to a known
mining pool".** It is cheap, requires no instrumentation, and **is the fastest way to detect exactly the
IMDS credential theft Day 382 described.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Unbounded ids in metric dimensions** | ⭐⭐ each unique combination is a billed metric |
| ⭐ Using CloudWatch for high-cardinality app metrics | ⭐ Prometheus is cheaper and queries better |
| ⭐ Never hearing of EMF | ⭐⭐ paying for API calls and cardinality unnecessarily |
| ⭐⭐ **`TreatMissingData: notBreaching` on availability alarms** | ⭐⭐ **total outage, alarm green** |
| ⭐ No "no data received" alarm | ⭐ absence of signal goes unnoticed |
| ⭐ Single-datapoint alarms | flapping and alert fatigue (Day 374) |
| ⭐ 40 instance alarms instead of a composite | an alarm storm with no cause |
| ⭐⭐ **Log groups with no retention** | ⭐⭐ paying forever for logs from a service deleted in 2024 |
| ⭐ Logs Insights over unbounded time ranges | billed per GB scanned |
| ⭐ Container Insights on everywhere by default | a large, quiet line item |
| ⭐ Instrumenting with a vendor SDK | ⭐⭐ instrumentation is the expensive part — use OTel |
| ⭐⭐ **CloudTrail in the same account only** | ⭐⭐ the attacker's first action is disabling it |
| Confusing CloudTrail with logging | it is audit, not observability |

## Interview questions

**Q: How does CloudWatch's cost model change how you use it?**
Custom metrics are billed per unique metric per month, and a metric is a name plus a distinct set of
dimensions. So putting anything unbounded in a dimension — a customer id, a request id — multiplies into
hundreds of thousands of billed metrics. It is the same cardinality lesson as Prometheus with a different
failure mode: Prometheus falls over, CloudWatch sends an invoice. The practical answer is to keep
dimensions low-cardinality and use Embedded Metric Format, where you write one structured log line and
CloudWatch extracts the metric from it — the high-cardinality fields stay in the log where you can query
them, and only the dimensions you chose become billed metrics.

**Q: An alarm on error rate stayed green during a complete outage. How?**
Because no requests meant no metric was published, so the alarm had missing data, and `TreatMissingData`
was set to `notBreaching`. Missing data was interpreted as health. For availability-critical metrics you
either treat missing as breaching, or you pair the alarm with a separate one that fires when no data has
been received at all. The general principle is that absence of signal is a signal — it is the same class
of failure as a PromQL rate window that returns nothing, where the graph is empty and the alert never
fires, and both of those look exactly like health.

**Q: CloudWatch or Prometheus?**
Both, for different things. CloudWatch is the only source for AWS service metrics — ALB request counts,
RDS connections, SQS queue depth — so you are using it whether you like it or not. Prometheus is better
and cheaper for application metrics, because cardinality is not billed per series and PromQL is a far
better query language, particularly for the burn-rate alerting that SLO alerting needs. Grafana sits over
both. I would not pretend one replaces the other.

**Q: What is the single biggest cost mistake people make with CloudWatch?**
Log group retention, which defaults to never expiring. Every Lambda, every ECS task and every service you
ever experimented with creates a log group that accumulates forever at ingestion and storage prices. On
most accounts, setting retention on every log group is the highest return one-line change there is. The
better pattern is short retention in CloudWatch for interactive debugging plus a subscription filter to
Firehose and S3 for anything that needs long-term keeping, with a lifecycle rule to Glacier — you keep
everything and stop paying CloudWatch rates for the part you never query.

**Q: What is CloudTrail for, and where should it live?**
It is audit, not observability. It records every API call in the account — who, when, from where, with
which credential and with what parameters — which makes it the only thing that answers "who deleted the
security group at two in the morning" or "which role read that secret". It has to be an organization
trail delivered into a separate, locked-down account, because if it lives only in the account being
attacked then disabling it is the attacker's first move. Pairing it with GuardDuty is worthwhile, since
that reads the same data and flags things like credentials suddenly being used from an unexpected
location — which is exactly the metadata-service credential theft you harden IMDSv2 against.

   saving.**

   vendor SDK code.

    exactly who did it. Enable **GuardDuty**.

## 🎙️ Articulation drill

**Two minutes:** *"How is your AWS system observed?"*

**⭐ Split it three ways deliberately: CloudWatch for AWS service metrics because there is no
alternative; Prometheus for application metrics because cardinality is not billed per series and PromQL
expresses burn-rate alerting properly; OpenTelemetry for traces, exported wherever, because
instrumentation is the expensive part and vendor SDKs turn a config change into a migration.**

**⭐ Then the two operational details that mark experience: every log group has a retention setting,
because the default is forever and it is the largest quiet line on most bills — and availability alarms
treat missing data as breaching, because a service that stops entirely publishes no metrics, and an alarm
that reads that as health is worse than no alarm at all.**
