# Day 204

**L-204** · Redis data structures — the reason it is not just a cache

**Time:** 3 hrs · **Mode:** NEW

> **⭐ "Redis is a cache" is the most limiting misconception about it.** It is a data-structure
> server, and the difference matters: a sorted set gives you a leaderboard, a rate limiter and a
> delay queue for free, and a HyperLogLog counts a hundred million unique visitors in twelve
> kilobytes.
>
> Today is the full toolkit, with the complexity of every operation — because Day 203's rule stands:
> **an O(N) command blocks the entire server.**

---

# Part 1 — Strings, hashes, lists

## Strings — and the fact that they are not just strings

```
SET key value EX 3600 NX          ⭐ set with TTL, only if absent — one atomic command
GET key
INCR counter                      ⭐ O(1) atomic. Day 203's guarantee
INCRBY counter 5
INCRBYFLOAT price 1.5
APPEND log "line\n"
SETRANGE / GETRANGE               ⭐ operate on part of a string
STRLEN key
```

**⭐ `SET key value EX 3600 NX` in one command replaces the old `SETNX` + `EXPIRE` pair**, which had
a fatal gap — if the client died between them the key lived forever. Day 207 builds on exactly this.

**⭐ `INCR` is the answer to Day 195's lost update**, achieved without locks, versions or isolation
levels: the increment happens on the single thread, so it cannot interleave.

## ⭐ Hashes — the memory-efficiency workhorse

```
HSET user:1000 name alice email a@b.com logins 42
HGET user:1000 name               ⭐ O(1)
HMGET user:1000 name email        ⭐ O(N) in fields requested
HGETALL user:1000                 ⚠️ O(N) — fine for 10 fields, not for 100,000
HINCRBY user:1000 logins 1        ⭐ atomic field increment
HDEL user:1000 email
HRANDFIELD user:1000 3
```

**⭐ Day 203's argument: one hash instead of N keys saves 50–100 bytes per field**, and below
`hash-max-listpack-entries` (default 128) it uses a compact packed encoding that is dramatically
smaller again.

⚠️ **⭐ A hash cannot have per-field TTLs** in most versions — expiry is per key. That single
limitation decides many designs: if fields must expire independently, they must be separate keys.

## Lists — a linked list, so ends are cheap and middles are not

```
LPUSH queue job1                  ⭐ O(1)
RPOP queue                        ⭐ O(1)
LRANGE list 0 9                   ⭐ O(N) in the range — first 10 is cheap
LINDEX list 5000                  ⚠️ ⭐ O(N) — it walks the list
LLEN list                         O(1)
LTRIM log 0 999                   ⭐ keep only the newest 1000 — capped log
⭐ BLPOP queue 5                   ⭐ BLOCKING pop, 5s timeout
⭐ LMOVE src dst LEFT RIGHT        ⭐ atomic move — reliable queue pattern
```

**⭐ `BLPOP` is why lists make workable job queues** — a worker blocks rather than polling, so there
is no busy loop and latency is near zero.

**⭐ And `LMOVE` is the reliability fix**, which is the thing most list-queue implementations get
wrong:

```
⭐ LMOVE jobs processing LEFT RIGHT     -- atomically claim: leaves the job visible in `processing`
-- ... do the work ...
LREM processing 1 job                   -- remove only on success
```

**⭐ With a plain `RPOP`, a worker that crashes after popping loses the job permanently** — there is
no record it was ever taken. `LMOVE` into a processing list means a reaper can return abandoned jobs.
That is at-least-once delivery (Day 185A) built from two commands.

**⭐ But be honest: for real queueing, Streams (Day 209) are better** — they have consumer groups,
acknowledgements and pending-entry tracking built in. Lists are the lightweight option.

# Part 2 — Sets and ⭐ sorted sets

## Sets

```
SADD tags:post:1 redis database
SISMEMBER tags:post:1 redis       ⭐ O(1)
SMEMBERS tags:post:1              ⚠️ O(N) — Day 203's blocking hazard
SCARD tags:post:1                 O(1)
⭐ SINTER set1 set2                ⭐ intersection — O(N×M)
SUNION / SDIFF
SINTERCARD 2 set1 set2 LIMIT 100  ⭐ count only, with a cap — cheaper
SRANDMEMBER / SPOP
```

**⭐ Set intersection is the underused power feature**: "users who like both X and Y" is one command.
But `SINTER` on two million-member sets blocks the server — use `SINTERCARD` with a `LIMIT` when you
only need a count or a sample.

## ⭐⭐ Sorted sets — the most valuable structure in Redis

**Every member has a score. Members are kept ordered by score, and lookups by member are O(1).**

```
ZADD leaderboard 1500 alice 1200 bob
ZINCRBY leaderboard 50 alice           ⭐ atomic score increment
ZSCORE leaderboard alice               O(1)
ZRANK / ZREVRANK leaderboard alice     ⭐ O(log N) — the player's position
ZRANGE leaderboard 0 9 REV WITHSCORES  ⭐ top 10 — O(log N + 10)
ZRANGEBYSCORE leaderboard 1000 2000    ⭐ range by score
ZREMRANGEBYSCORE k -inf 1699999999     ⭐⭐ delete everything older than a timestamp
ZCOUNT leaderboard 1000 2000           O(log N)
```

**⭐ `ZRANK` in O(log N) is remarkable.** "What is this player's position among ten million?" is a
query no other structure answers cheaply — in PostgreSQL it is a window function over the whole
table.

**⭐ The four patterns that make sorted sets the workhorse:**

| Pattern | Score is | Key operation |
|---|---|---|
| ⭐ **Leaderboard** | the score | `ZREVRANGE`, `ZRANK` |
| ⭐ **Sliding-window rate limiter** (Day 208) | ⭐ **the timestamp** | `ZREMRANGEBYSCORE` + `ZCARD` |
| ⭐ **Delay / priority queue** | ⭐ **the run-at time** | `ZRANGEBYSCORE 0 now` |
| **Time-series index** | the timestamp | `ZRANGEBYSCORE` |

**⭐ Using the timestamp as the score is the trick worth internalising.** It turns a sorted set into a
time-ordered index where "everything in the last minute" and "everything due now" are both single
range commands — and `ZREMRANGEBYSCORE` prunes old entries in one call.

```
-- ⭐ A delay queue in three commands
ZADD scheduled 1723640000 "job:8842"                    -- run at this epoch second
ZRANGEBYSCORE scheduled -inf 1723639999 LIMIT 0 100     -- what is due
ZREM scheduled "job:8842"                                -- claim it
```

⚠️ **That claim is not atomic across the two commands** — two workers can both see the job. **Wrap it
in a Lua script** (Day 203), which is the same lesson as Day 178's `SKIP LOCKED`.

# Part 3 — ⭐ The probabilistic and bit structures

## ⭐ HyperLogLog — 100 million uniques in 12 KB

```
PFADD visitors:2026-08-14 user:1 user:2 user:3
PFCOUNT visitors:2026-08-14                        ⭐ ~0.81% standard error
PFMERGE visitors:week visitors:day1 visitors:day2  ⭐ merge across periods
```

| | Set | ⭐ HyperLogLog |
|---|---|---|
| 100M unique visitors | ⭐ **several GB** | ⭐⭐ **12 KB** |
| Accuracy | exact | ⭐ ~0.81% error |
| Can list members? | ✅ | ❌ **never** |
| Mergeable | `SUNION` (expensive) | ⭐ `PFMERGE` (cheap) |

**⭐ The trade is exact membership for a 400,000× memory reduction**, and for analytics that is
almost always the right trade — nobody needs the exact list of yesterday's unique visitors, and
"1,204,000 ± 1%" is as useful as "1,203,847".

**⭐ `PFMERGE` is the property people miss:** daily HyperLogLogs merge into a weekly or monthly unique
count **without double-counting**, which a sum of daily counts cannot do.

## Bitmaps — one bit per user

```
SETBIT active:2026-08-14 1000 1          ⭐ user 1000 was active today
GETBIT active:2026-08-14 1000
BITCOUNT active:2026-08-14               ⭐ how many active
BITOP AND active:week active:d1 active:d2 ... ⭐ active EVERY day — retention
BITPOS active:2026-08-14 1
```

**⭐ 10 million users = 1.25 MB per day.** A year of daily activity is under 500 MB, and
`BITOP AND` across seven days answers "who was active every day this week" in one command.

**⭐ The constraint: it only works with dense small integer ids.** Bitmaps index by offset, so a UUID
user id needs a mapping to a sequential integer first — which is one more argument for Day 158's
two-id pattern.

## Geospatial

```
GEOADD stores 13.361 38.115 "store:1"
GEOSEARCH stores FROMLONLAT 13.36 38.11 BYRADIUS 5 km ASC COUNT 10
```

**⭐ Built on sorted sets with a geohash score** — which is why it is fast, and why "nearest ten
stores" is a single command with no PostGIS.

# Part 4 — ⭐ Choosing, and the complexity discipline

| Need | Structure |
|---|---|
| Cache a value, a counter | ⭐ String |
| An object with several fields | ⭐ **Hash** — memory efficiency |
| A simple job queue | List + `BLPOP`/`LMOVE` (⭐ Streams are better — Day 209) |
| Membership, tags, intersections | Set |
| ⭐ **Ranking, ranges, delay queues, rate limits** | ⭐⭐ **Sorted set** |
| ⭐ **Unique counting at scale** | ⭐ **HyperLogLog** |
| Per-user boolean over dense ids | Bitmap |
| Proximity search | Geo |
| ⭐ **Event log with consumer groups** | ⭐ Stream (Day 209) |

## ⭐ The complexity discipline

> **⭐ Day 203's rule governs every choice here: an O(N) command on a large structure blocks the
> entire server. Know the complexity of every command you ship.**

| Safe | ⭐ Dangerous at scale |
|---|---|
| `GET`, `HGET`, `SISMEMBER`, `ZSCORE` — O(1) | ⭐ `HGETALL`, `SMEMBERS`, `LRANGE 0 -1` — O(N) |
| `ZADD`, `ZRANK`, `ZRANGEBYSCORE` — O(log N) | ⭐ `SINTER`, `SORT`, `KEYS` — O(N) or worse |
| `LPUSH`, `RPOP` — O(1) | ⭐ `LINDEX` mid-list, `LINSERT` — O(N) |

**⭐ And the rule that prevents the slow accumulation: bound every collection.**

```
LTRIM recent:events 0 999                       -- ⭐ cap a list
ZREMRANGEBYRANK leaderboard 0 -10001            -- ⭐ keep only the top 10,000
ZREMRANGEBYSCORE window -inf (now - 3600)       -- ⭐ drop entries older than an hour
```

**⭐ A collection that only ever grows is a memory leak with a delay**, and because Redis is
memory-resident it ends in eviction (Day 206) or an out-of-memory error rather than merely a slow
query. **Every write that adds to a collection should be paired with the trim that bounds it.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ "Redis is just a cache" | you rebuild leaderboards, rate limits and delay queues elsewhere |
| Separate keys per field | ⭐ 50–100 bytes overhead each |
| Expecting per-field TTLs on a hash | expiry is per key |
| ⭐ `HGETALL`/`SMEMBERS` on huge structures | O(N) — blocks the server |
| `LINDEX` into a long list | O(N) |
| ⭐ `RPOP` for a job queue | a crashed worker loses the job; use `LMOVE` |
| Non-atomic claim from a sorted set | two workers get the same job; use Lua |
| ⭐ Unbounded collections | a memory leak with a delay |
| Sets where a HyperLogLog would do | gigabytes instead of kilobytes |
| Expecting to list HyperLogLog members | you cannot, ever |
| Summing daily unique counts | ⭐ double-counts; use `PFMERGE` |
| Bitmaps with sparse or UUID ids | offsets require dense integers |
| Shipping a command without knowing its complexity | Day 203's outage |

## Interview questions

**Q: Why is Redis more than a cache?**
Because it is a data-structure server. A sorted set gives me a leaderboard with O(log N) rank
queries, a sliding-window rate limiter, and a delay queue — all from one structure by choosing what
the score means. A HyperLogLog counts a hundred million uniques in twelve kilobytes. Those are not
cache features; they are things I would otherwise build badly somewhere else.

**Q: What makes sorted sets so useful?**
Ordering by score with O(1) member lookup and O(log N) rank. The trick is choosing what the score
represents: the score itself for a leaderboard, the timestamp for a sliding-window rate limiter or a
time index, and the run-at time for a delay queue — and `ZREMRANGEBYSCORE` prunes old entries in one
command.

**Q: When would you use a HyperLogLog?**
Counting uniques at scale where approximate is fine — daily unique visitors, distinct search terms.
Twelve kilobytes instead of gigabytes, at about 0.8% error. And crucially `PFMERGE` combines daily
counts into a weekly unique without double-counting, which summing daily totals cannot do. I never
use it when I need the actual members.

**Q: How would you build a job queue on a list, and what is wrong with it?**
`LPUSH` to add, `BLPOP` to block-and-consume. The flaw is that a worker crashing after the pop loses
the job — there is no record it was taken. `LMOVE` into a processing list fixes that and lets a
reaper recover abandoned jobs. But for real queueing, Streams have consumer groups and
acknowledgements built in.

**Q: What is the discipline that governs all of this?**
Knowing the complexity of every command, because one thread means an O(N) command blocks every
client. And bounding every collection — a structure that only grows is a memory leak, and in an
in-memory store that ends in eviction or an OOM, not just a slow query.

## Mini task

1. Store 100,000 users as separate keys, then as hashes. **Compare total memory.**
2. Build a leaderboard with 1M players. `ZRANK` a random player and **time it.** Compare with the
   equivalent PostgreSQL window function.
3. Build a delay queue with sorted sets. Run two workers claiming with `ZRANGEBYSCORE` + `ZREM`.
   **Find the double-claim.** Fix it with Lua.
4. Build a list queue with `RPOP`. Kill a worker mid-job. **Confirm the job is gone.** Rewrite with
   `LMOVE` and a reaper.
5. Count 10 million uniques with a Set and with a HyperLogLog. **Compare memory and the error.**
6. `PFMERGE` seven daily HyperLogLogs. Compare against the sum of the seven counts. **Explain the
   difference.**
7. Build a bitmap of daily active users for 1M users over 7 days. `BITOP AND` for weekly retention.
   Measure memory.
8. `HGETALL` a hash with 500,000 fields and **time how long other clients block.**
9. Let a sorted set grow to 5M members with no trim. Watch memory. Add `ZREMRANGEBYRANK`.
10. `GEOADD` 100,000 stores and find the nearest ten. Compare with a PostGIS query.

## 🎙️ Articulation drill

Two minutes: **"What can Redis do beyond caching?"**

Lead with the reframe — it is a data-structure server — then make it concrete with sorted sets, and
show range by explaining that the *score's meaning* is the design decision: the score for a
leaderboard, the timestamp for a rate limiter, the run-at time for a delay queue. Add HyperLogLog
with the numbers, because twelve kilobytes for a hundred million uniques is the kind of fact that
lands. Close on the discipline: every command's complexity matters because one thread means O(N)
blocks everyone, and every collection needs a bound or it is a memory leak.
