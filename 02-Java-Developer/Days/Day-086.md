**L-086** · Branching, merge vs rebase, fast-forward, three-way merge

**Time:** 3 hrs · **Mode:** NEW

> The argument everyone has, with an actual answer. Both operations are trivial once you hold Day
> 084's model: **merge creates a commit with two parents; rebase creates new commits with different
> parents.** Everything else — including the whole controversy — follows from that one sentence.

# Part 1 — Branching

## What a branch costs

Nothing. A branch is a 41-byte file (Day 084). Creating one writes a file; switching moves HEAD and
updates the working tree.

```bash
git switch -c feature/rate-limit        # create and switch (modern)
git checkout -b feature/rate-limit      # same thing (older, overloaded)
git switch main
git switch -                            # previous branch
git branch -v                           # local branches + last commit
git branch -a                           # including remote-tracking
git branch --merged main                # safe to delete
git branch --no-merged main             # NOT yet merged — check before deleting
git branch -d old                       # refuses if unmerged
git branch -D old                       # force
git branch -m old new                   # rename
```

`git switch` and `git restore` were added in Git 2.23 to split `checkout`'s two unrelated jobs —
moving HEAD and overwriting files. Use them; `checkout` doing both is why people accidentally destroy
work with it.

Naming: `feature/…`, `fix/…`, `chore/…`, or `<ticket>/short-description`. Pick one and be
consistent — the value is that `git branch -a` on a shared repo stays readable.

## Fast-forward — the base case

```
Before:            After git merge feature (fast-forward):

main                                     main
  ▼                                        ▼
  A ── B                                   A ── B ── C ── D
        \                                            ▲
         C ── D                                   feature
              ▲
           feature
```

When `main` is a **direct ancestor** of `feature`, there is nothing to merge — Git just moves the
`main` pointer forward. **No merge commit, no new objects.** That is a fast-forward.

```bash
git merge feature              # fast-forwards if possible
git merge --no-ff feature      # force a merge commit anyway
git merge --ff-only feature    # fail if a fast-forward is not possible
```

`--no-ff` is a deliberate choice on some teams: it preserves the fact that a group of commits was one
feature, and makes the whole feature revertable as a unit (`git revert -m 1 <merge>`). The cost is a
merge commit for every branch, which some teams find noisy. Both positions are defensible; know why
each exists.

`--ff-only` is the safe default for pulling: it refuses rather than silently creating a merge commit.

## Three-way merge

When both branches have moved, Git performs a three-way merge using three snapshots:

```
        ┌── C ── D ──┐            base   = B  (the merge base: common ancestor)
  A ── B             M            ours   = E  (main's tip)
        └── E ───────┘            theirs = D  (feature's tip)
```

For every file, Git compares `ours` and `theirs` **against the base**:

| base → ours | base → theirs | Result |
|---|---|---|
| unchanged | changed | take theirs |
| changed | unchanged | take ours |
| changed identically | changed identically | take either |
| **changed differently** | **changed differently** | **conflict** |

**Only the last row conflicts.** This is why merges are usually automatic: most changes touch
different files or different regions, and Git resolves them by comparing to the common ancestor
rather than guessing.

```bash
git merge-base main feature      # the base commit Git will use
```

Knowing the merge base explains otherwise-baffling merges. If someone rebased or force-pushed, the
base moves, and a merge that should have been clean suddenly conflicts everywhere.

The resulting merge commit has **two parents** — that is the only structural difference between it
and an ordinary commit.

## Rebase

```
Before:                    After git rebase main (on feature):

  A ── B ── E   main          A ── B ── E          main
        \                            \
         C ── D  feature              C' ── D'     feature
```

Rebase **replays** each of your commits onto a new base. Mechanically:

1. Find the commits on `feature` not on `main` (C and D).
2. Reset `feature` to `main`'s tip.
3. Apply each commit's *diff* in order, creating **new commits** C′ and D′.

**C′ is not C.** Different parent → different hash → a different object, even with identical content
and message. The originals still exist (reachable via the reflog) until garbage collection.

That single fact generates the whole rule:

> ## The Golden Rule of Rebasing
> **Never rebase commits that exist outside your repository.**

If someone else has C, and you replace it with C′, their history and yours have diverged with no
common ancestor for that work. Their next merge duplicates every commit, or produces conflicts that
make no sense. This is the actual mechanism behind "rebase is dangerous" — it is not dangerous, it
is *rewriting*, and rewriting shared history is the problem.

Practically: **rebase your own unpushed feature branch freely; never rebase `main` or a branch
someone else has pulled.**

## Merge vs rebase — the comparison

| | Merge | Rebase |
|---|---|---|
| History | True, with branch topology | Linear |
| Commits | Preserved exactly | **Rewritten** (new hashes) |
| Merge commits | Yes | No |
| Conflicts | Once, at the merge | Potentially **once per commit** |
| Safe on shared branches | ✅ | ❌ |
| `git log` readability | Noisier, but honest | Clean, but fictional |
| Bisect | Works | Works, often better (linear) |
| Recovering from a mistake | Easy | Reflog |

**The pragmatic policy most teams converge on:**

```
Rebase your feature branch onto main to keep it current  (your commits, unpushed or yours alone)
Merge the feature branch into main via a pull request     (a permanent, shared record)
```

You get a clean, linear feature history *and* a preserved record of when the feature landed. This is
also what `pull.rebase true` (Day 085) gives you on every `git pull`: your local commits are replayed
on top of upstream rather than generating a merge commit for every sync.

## Interactive rebase — the cleanup tool

```bash
git rebase -i HEAD~5
git rebase -i main
```

```
pick   a1b2c3 Add rate limiter
squash d4e5f6 fix typo                 ← fold into the previous commit
squash 7g8h9i fix typo again
reword j1k2l3 Add config for limiter   ← change the message
edit   m4n5o6 Extract validator        ← stop here to amend
drop   p7q8r9 debug logging            ← remove entirely
```

Commands: `pick`, `reword`, `edit`, `squash` (combine, keep both messages), `fixup` (combine, discard
this message), `drop`, and `exec` to run a command after a commit.

This is how a branch with "wip", "fix typo", "actually fix it", "revert that" becomes three clean
commits before review. **It is expected practice on most teams** — you clean up before you ask
someone to read it.

```bash
git commit --fixup <hash>          # marks a commit as a fixup for another
git rebase -i --autosquash main    # automatically orders and marks them
```

That pair is worth adopting: fix review comments with `--fixup` commits as you go, then one
`--autosquash` rebase folds each into the right original commit with no manual reordering.

```bash
git rebase --continue / --skip / --abort     # --abort always gets you out
```

**`--abort` is the safety net.** A rebase that has gone wrong is always recoverable — either abort
mid-flight, or afterwards find the original tip in `git reflog` and `git reset --hard` to it.

## Squash merge and the three PR strategies

| Strategy | Result on main | Use when |
|---|---|---|
| **Merge commit** (`--no-ff`) | Full branch history + a merge commit | You want the true record; revert the feature as a unit |
| **Squash merge** | **One commit** per PR | Feature branches are messy; you want main readable |
| **Rebase merge** | Commits replayed linearly, no merge commit | Branch history is already clean and meaningful |

Squash merge is the most common default on GitHub because it makes `main` a clean list of features
and does not require contributors to curate their history. Its cost: individual commits are lost, so
a large PR becomes one giant unbisectable commit — which is an argument for smaller PRs, not against
squashing.

## `cherry-pick`

```bash
git cherry-pick <hash>              # apply one commit's diff here
git cherry-pick A..B                # a range
git cherry-pick -x <hash>           # ← record the source hash in the message
```

Applies a commit's *change* onto the current branch as a **new commit with a new hash**. The correct
use is a hotfix that must exist on both `main` and a release branch. **The wrong use is as a
substitute for merging** — cherry-picking many commits between long-lived branches means the same
change exists twice with different hashes, and the eventual merge conflicts confusingly.

`-x` should be habitual: it appends "(cherry picked from commit …)", which is the only trace of
where the change came from.

## Code to type

```bash
mkdir mergelab && cd mergelab && git init && git commit --allow-empty -m "root"

printf 'line1\nline2\nline3\n' > f.txt && git add . && git commit -m "Add f"

# fast-forward
git switch -c ff && printf 'line4\n' >> f.txt && git commit -am "Add line4"
git switch main && git merge ff                 # "Fast-forward"
git log --oneline --graph --all

# three-way, no conflict — different regions
git switch -c a && sed -i '1s/line1/LINE-ONE/' f.txt && git commit -am "Change line1"
git switch main && git switch -c b && printf 'line5\n' >> f.txt && git commit -am "Add line5"
git switch main && git merge a && git merge b   # second one makes a merge commit
git log --oneline --graph --all

# three-way, conflict — same line
git switch -c x && sed -i '2s/.*/from-x/' f.txt && git commit -am "x edits line2"
git switch main && sed -i '2s/.*/from-main/' f.txt && git commit -am "main edits line2"
git merge x                                      # CONFLICT — leave it for tomorrow
git merge --abort

# rebase: watch the hashes change
git switch x && git log --oneline -1             # note the hash
git rebase main
git log --oneline -1                             # DIFFERENT hash, same content
git reflog | head                                # the original is still there

# interactive
git switch -c messy
for m in "wip" "fix typo" "actually fix" "done"; do
  echo "$m" >> notes.txt && git add . && git commit -m "$m"
done
git rebase -i HEAD~4        # squash them into one, reword it
git log --oneline -3
```

**Run every block.** The rebase hash-change and the reflog recovery are the two that convert
understanding into confidence.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Rebasing a pushed shared branch | Everyone's history diverges; duplicate commits |
| `git push --force` on a shared branch | Overwrites others' work — use `--force-with-lease` |
| Rebasing a long branch with many commits | Conflict resolution repeated per commit (enable `rerere`) |
| Expecting rebase to preserve hashes | New parent means a new object, always |
| Deleting a branch without `--no-merged` check | Losing unmerged work (recoverable via reflog) |
| Cherry-picking instead of merging | The same change twice, with different hashes |
| Cherry-pick without `-x` | No record of the origin |
| Long-lived branches | Merge pain grows superlinearly — merge often |
| `git checkout` for both jobs | Accidental file overwrites; use `switch`/`restore` |

**`--force-with-lease` deserves emphasis:** it refuses to push if the remote has commits you have not
seen, so you cannot silently overwrite a colleague's push. Make it your default; plain `--force` is
almost never what you actually want.

## Interview questions

**Q: Merge vs rebase?**
Merge creates a commit with two parents, preserving history exactly. Rebase replays your commits onto
a new base, creating new commits with new hashes and a linear history. Rebase your own unpushed work;
merge to integrate into shared branches.

**Q: What is a fast-forward?**
When the target is a direct ancestor of the source, Git just advances the pointer — no merge commit
and no new objects.

**Q: How does a three-way merge work?**
Git finds the merge base (common ancestor) and compares both tips against it. If only one side
changed a region, take that side; if both changed the same region differently, conflict.

**Q: State the golden rule of rebasing and explain the mechanism.**
Never rebase commits that exist outside your repository. Rebase creates *new* commits; if others have
the originals, their history and yours no longer share those commits, producing duplicates and
confusing conflicts.

**Q: When would you cherry-pick?**
A hotfix that must land on both `main` and a release branch. Not as a substitute for merging, because
it duplicates changes under different hashes.

**Q: Squash merge — pros and cons?**
`main` becomes one clean commit per feature and contributors need not curate history; but individual
commits are lost, so a large PR becomes one unbisectable commit. Favours small PRs.

**Q: Why `--force-with-lease` rather than `--force`?**
It fails if the remote has commits you have not fetched, so you cannot overwrite someone else's push.

## 🎙️ Articulation drill

Two minutes: **"Do you prefer merge or rebase?"**

The wrong answer is a preference. The right answer is the mechanism — rebase rewrites, merge records
— followed by the policy: rebase locally to stay current, merge to integrate, never rewrite what
others have. Add that you use `--force-with-lease` and `rerere`, and it is clear you have actually
lived with this.
