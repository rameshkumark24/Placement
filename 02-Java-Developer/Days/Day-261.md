# Day 261 🏗️

**P-261** · Testing the backend — the pyramid, and the tests that catch what matters

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ You have been writing tests since Day 253.** Today is the audit: is the suite fast, does it
> catch the things that actually break, and does it prove the claims you will make in an interview?
>
> **⭐ The target is not a coverage number.** Day 281 asks for 80%+, and coverage measures which lines
> ran, not which behaviours are protected. **A suite with 90% coverage and no negative authorization
> test protects nothing that matters.**

---

# Part 1 — ⭐ Audit the shape of the suite

```
⭐ Count your tests by type. The distribution should look like Day 097's pyramid.
```

| Type | Target | ⭐ Warning sign |
|---|---|---|
| ⭐ **Plain JUnit — domain** | ⭐ **the majority; runs in <1 s total** | ⭐ few, or none |
| Slices (`@WebMvcTest`, `@DataJpaTest`) | a solid layer | absent |
| ⭐ **Integration (Testcontainers)** | ⭐ dozens, ⭐ **one shared context** | ⭐ hundreds |
| End-to-end | a handful | many, and flaky |

**⭐ Two diagnoses to make honestly:**

> **⭐ If most tests need a Spring context, your business logic is not separable from the framework** —
> which is a design problem the test suite is reporting (Day 183).

> **⭐ If the suite takes more than a few minutes, it is the context cache** (Day 183). Turn on
> `logging.level.org.springframework.test.context.cache: DEBUG`, count the contexts created, and
> collapse them onto Day 253's shared base class.

**⭐ Measure it today**: total suite time, and time for the domain-only tests. **The second number
should be under a second**, and if it is not, Day 254's ArchUnit rule is probably failing quietly or
the domain is anaemic.

# Part 2 — ⭐ The tests that catch what actually breaks

**⭐ Ordinary tests catch ordinary bugs. These eight catch the bugs that reach production.**

### ⭐ 1. Negative authorization — one per protected operation

```
⭐ Anonymous → 401 · wrong role → 403 · other user's record → 404 · other tenant → empty
```

**⭐ Day 169's argument, and it is the single highest-value category here: an authorization bug is a
200 with someone else's data.** It throws nothing, logs nothing, and passes every positive test.

### ⭐ 2. Query count — one per read path

```
⭐ SQLStatementCountValidator.assertSelectCount(1);
```

**⭐ Day 160: the only durable defence against N+1**, because review and vigilance decay and a test
fails the build the day someone adds a `getRoom()` inside a loop.

### ⭐⭐ 3. Concurrency — the hard problem

```
⭐ Two threads, same resource, 100 iterations → exactly one succeeds
```

**⭐ This is the centrepiece.** It must run against real PostgreSQL (Day 184) — on H2 an exclusion
constraint, `SKIP LOCKED` and serialisation errors do not exist, **so the test would pass while
proving nothing.**

### ⭐ 4. Idempotency

```
⭐ The same Idempotency-Key twice → one booking, the same response
⭐ Cancel twice → 204 both times
```

### ⭐ 5. The state machine — from every illegal source

**⭐ Day 254: testing only the legal transitions means a removed guard is not caught.** A test
asserting `cancel()` throws from `COMPLETED` is what stops someone "simplifying" it away.

### ⭐ 6. The error contract

```
⭐ Every entry in ERRORS.md has a test that triggers it and asserts the type URI
```

### ⭐ 7. Time

```
⭐ An injected Clock, fixed in tests    (Day 183)
⭐ Test the 2-hour cancellation boundary at 2h+1s and 2h−1s
⭐ Test across a DST boundary
```

**⭐ `Instant.now()` scattered through the code produces the classic flaky test that fails at midnight
or twice a year.** Injecting a `Clock` is a small discipline with a large payoff, and it lets you
test the boundary rather than approximate it.

### ⭐ 8. Failure of dependencies

```
⭐ Redis down          → degrades, does not break        (Day 168)
⭐ A slow HTTP dependency (WireMock delay) → ⭐ the timeout fires, the circuit opens (Day 154, 181)
⭐ The database down   → readiness down, ⭐ liveness UP   (Day 128)
```

**⭐ Day 184: you cannot test a timeout against a mocked client.** A mock returns instantly; only a
real server that is genuinely slow proves the timeout, the retry and the breaker behave as
configured.

# Part 3 — ⭐ Keep it fast and honest

## ⭐ The rules

| Rule | Day |
|---|---|
| ⭐ **`static` containers on a shared base class** | 184 |
| ⭐ **No `@Transactional` on integration tests** | ⭐ 184 — rollback hides `AFTER_COMMIT` listeners and commit-time failures |
| ⭐ **No `Thread.sleep`** — Awaitility | 183 |
| ⭐ **No mocking repositories to test queries** | 183 — it asserts you called a method you wrote |
| ⭐ **`@DirtiesContext` almost never** | 183 — it evicts the cache; everything after pays |
| ⭐ **Pin container image tags exactly** | 184 — `postgres:16.4-alpine`, not `16-alpine` |
| Reuse locally, never in CI | 184 |

**⭐ The `@Transactional` rule is the one people resist**, and Day 184's reason is concrete: your
project has `AFTER_COMMIT` listeners (Day 256) and an outbox — **rollback means the entire
notification path is untested.** Truncate between tests instead.

## ⭐ Coverage, read correctly

```
⭐ Add JaCoCo. Look at what is NOT covered, ⭐ not at the number.
```

| ⭐ Must be covered | ⭐ Acceptable to miss |
|---|---|
| ⭐ Domain rules and every transition | getters, `toString` |
| ⭐ Authorization paths | configuration classes |
| ⭐ Error handling | generated code |
| Concurrency guards | trivial mappers |

**⭐ A coverage gate is useful; a coverage target is theatre.** Set a floor that fails the build on a
regression, and spend your attention on the uncovered branches rather than on the percentage.

## ⭐ Mutation testing — the one high-value addition

```
⭐ PIT (pitest) on the domain package only
```

**⭐ Mutation testing changes your code and checks whether a test fails.** It is the only tool that
distinguishes "this line ran" from "this behaviour is protected" — **and it will find assertions you
thought you had.** Run it on the domain only; the whole application is slow and the domain is where
the value is.

## ⭐ Flakiness — fix it, never retry it

```
⭐ Run the suite 20 times. ⭐ Any test that fails once is broken.
```

**⭐ Sources, in order of frequency:** shared mutable state between tests, `Thread.sleep`, real time
instead of an injected clock, test-order dependence, and genuine concurrency in the code.

**⭐ Never add a retry to a flaky test.** It hides a real bug — often a genuine race in the
application — and it destroys trust in the whole suite.

# Part 4 — ⭐ Prove the claims you will make

**⭐ Today, produce the evidence for each claim you intend to make in an interview.**

| Claim | ⭐ Evidence |
|---|---|
| ⭐ "It handles concurrent bookings correctly" | ⭐ the two-thread test, on real PostgreSQL |
| ⭐ "No N+1" | ⭐ query-count assertions, and the plan output |
| "Authorization is enforced" | the negative test suite |
| ⭐ "It degrades when Redis is down" | ⭐ the test, plus a manual demonstration under load |
| ⭐ "Refresh token theft is detected" | ⭐ the family-revocation test |
| "It handles 200 rps" | ⭐ a load test — see below |

## ⭐ Load test it, once, properly

```
⭐ k6 or Gatling against the DEPLOYED instance, at your Day 249 NFR target
```

**⭐ Record four numbers: p50, p99, error rate, and what saturated first.** That last one is Day 248's
defence question — *what breaks first at 100× traffic?* — **and now you have measured it rather than
guessed.**

**⭐ Watch during the run:** `hikaricp_connections_pending` (Day 156), `http_server_requests` p99,
CPU, and your business metrics. **The thing that saturates first is almost always the connection
pool, an unindexed query, or a single-instance job.**

**⭐ Then fix the top finding and re-measure.** That before-and-after pair — a number, a change, a
number — is the strongest single artefact this project can produce.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Chasing a coverage number | 90% coverage with no negative authorization test |
| ⭐ Mostly integration tests | slow feedback; the design problem goes unreported |
| ⭐ Many Spring contexts | minutes of startup (Day 183) |
| ⭐ `@Transactional` on integration tests | ⭐ `AFTER_COMMIT` and the outbox untested |
| ⭐ H2 for the concurrency test | ⭐ **passes while proving nothing** |
| Mocking repositories | tests the mock |
| `Thread.sleep` | flaky and slow |
| ⭐ Retrying a flaky test | hides a real race; destroys trust |
| ⭐ `Instant.now()` in the code | untestable boundaries; midnight failures |
| Unpinned container tags | the suite changes when upstream publishes |
| ⭐ Only legal state transitions tested | a removed guard is not caught |
| ⭐ Never load testing | "what breaks first?" is a guess |

## 🎤 Defence questions

1. **⭐ What is your test strategy?** (⭐ shape and reasoning, not a coverage number)
2. **⭐ How do you know there is no N+1?**
3. **⭐ How do you know two users cannot double-book?** (⭐ and why H2 would not prove it)
4. **⭐ What does your suite catch that a compile does not?**
5. **⭐ What is your coverage, and why is that not the interesting question?**
6. **⭐ Have you load tested? What saturated first, and what did you do about it?**
7. **⭐ Do you have flaky tests?** (⭐ "no, and here is how I checked" is the answer)
8. **Why is there no `@Transactional` on your integration tests?**

## ✅ Done when

- ⭐ The eight categories exist and pass
- ⭐ Twenty consecutive green runs
- ⭐ **A load test result with a before-and-after for one fix**
