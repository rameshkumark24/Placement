# Day 151

**L-151** · Filters vs interceptors vs AOP — choosing the right hook

**Time:** 3 hrs · **Mode:** NEW

> Three mechanisms exist for "run something around a request", and people pick by familiarity rather
> than by fit. Day 145's diagram already contains the answer: **they sit at different points in the
> chain, so they see different things and can do different things.**
>
> Today is the decision table, the two cross-cutting concerns everyone implements wrong at least once
> — correlation IDs and request logging — and the wrapper trick that makes body logging possible at
> all.

---

# Part 1 — The three, positioned

| | **Filter** | **Interceptor** | **AOP** |
|---|---|---|---|
| API | Servlet (`jakarta.servlet`) | Spring MVC | Spring AOP (Day 137) |
| Position | ⭐ **wraps the DispatcherServlet** | inside it | around the bean method |
| Runs for | **every** request — static resources, 404s, errors | mapped handlers only | any bean method |
| Knows the handler? | ❌ no | ✅ yes — `HandlerMethod` | ✅ it *is* the method |
| Can read/modify the body? | ✅ (with a wrapper) | ⚠️ awkward | ✅ typed arguments |
| Can short-circuit? | ✅ don't call `chain.doFilter` | ✅ `preHandle` → `false` | ✅ don't call `proceed` |
| Exceptions caught by advice? | ❌ **no** (Day 149) | ✅ yes | ✅ yes |
| Ordering | `@Order` / `FilterRegistrationBean` | registration order | `@Order` |
| Works outside HTTP? | ❌ | ❌ | ✅ ⭐ jobs, consumers, `@Scheduled` |

**The decision rule, in one line each:**

- **Filter** — you need it for *every* request including ones that never reach a handler, or you need
  to wrap the request/response objects. Security, correlation IDs, CORS, compression, rate limiting.
- **Interceptor** — you need to know *which handler* was selected. Per-endpoint auditing, feature
  flags keyed on the method, adding annotations-driven behaviour to controllers.
- **AOP** — the concern is about a *bean method*, not a request. Transactions, caching, retries,
  metrics on service methods — and crucially, things that must also apply when the caller is a Kafka
  consumer or a scheduled job.

**The last point is the one that decides most real arguments.** If the behaviour must apply to an
order placed by a scheduled job as well as by HTTP, it cannot live in a filter or an interceptor —
Day 146 and Day 148 both made this argument from different directions.

# Part 2 — Filters, done properly

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)              // ⭐ before security, so security logs carry it
public class CorrelationIdFilter extends OncePerRequestFilter {

    private static final String HEADER = "X-Correlation-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {

        String cid = req.getHeader(HEADER);
        if (cid == null || cid.isBlank() || cid.length() > 64 || !cid.matches("[A-Za-z0-9._-]+")) {
            cid = UUID.randomUUID().toString();       // ⭐ validate — this ends up in logs
        }
        MDC.put("correlationId", cid);
        res.setHeader(HEADER, cid);                   // ⭐ echo it so the caller can quote it
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                              // ⭐⭐ Day 066A — non-negotiable
        }
    }
}
```

Four things there are load-bearing:

1. **`OncePerRequestFilter`, not `Filter`.** A plain filter runs again on every `FORWARD`, `INCLUDE`
   and `ERROR` dispatch — so a request that errors passes through your filter twice, generating two
   correlation IDs and two log entries for one request. This is the single most common filter bug.
2. **`MDC.clear()` in `finally`.** Day 066A's `ThreadLocal`-in-a-pool leak, exactly. Miss it and the
   next request on that Tomcat thread logs with the previous customer's correlation ID — which is
   worse than no ID, because it is confidently wrong during an incident.
3. **Validate the incoming header.** It is attacker-controlled and it lands in your logs. A newline
   in it is **log injection** — the attacker forges log lines. A 10 KB value is a log-storage attack.
   Day 127 raised this; the filter is where it is enforced.
4. **Order before security.** Then Spring Security's own authentication-failure logs already carry
   the ID, which is exactly when you most want it.

## Explicit registration, when you need URL scoping

```java
@Bean
FilterRegistrationBean<RateLimitFilter> rateLimit(RateLimitFilter f) {
    var reg = new FilterRegistrationBean<>(f);
    reg.addUrlPatterns("/api/*");                    // ⭐ not /actuator, not static
    reg.setOrder(20);
    return reg;
}
```

**A `@Component` filter applies to `/*`** — everything, including `/actuator/health` on every probe
interval. For a rate limiter or an expensive filter that is both wasteful and wrong: you do not want
readiness probes consuming a rate-limit budget.

## ⭐ The body problem, and the wrapper that solves it

**A servlet request body is a stream. Read it once and the controller gets nothing.** So the naive
"log the request body" filter breaks every POST endpoint in the application — and it breaks them by
producing empty DTOs, which looks like a Jackson problem and sends people hunting in the wrong place.

```java
@Component
@Order(30)
public class RequestLoggingFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {

        var wrappedReq = new ContentCachingRequestWrapper(req, 8192);   // ⭐ cap the cache
        var wrappedRes = new ContentCachingResponseWrapper(res);
        long start = System.nanoTime();
        try {
            chain.doFilter(wrappedReq, wrappedRes);
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            log.info("http_request method={} path={} status={} durationMs={}",     // Day 127
                     req.getMethod(), req.getRequestURI(), wrappedRes.getStatus(), ms);
            wrappedRes.copyBodyToResponse();          // ⭐⭐ MANDATORY — or the client gets nothing
        }
    }
}
```

`ContentCachingRequestWrapper` buffers bytes as they are read, so `getContentAsByteArray()` works
*after* the controller has consumed the stream — not before.

**`copyBodyToResponse()` is not optional.** The response wrapper buffers everything and writes
nothing until you call it. Forget it and every response body in the application is empty, with a
correct status code. That symptom — 200 OK, zero-length body, no exception anywhere — is one of the
more baffling bugs in Spring, and this line is the entire cause.

**And the rule that matters more than the mechanics:** if you log bodies at all, log them
**redacted, size-capped, and only for selected endpoints**. A login request body is a password in
your log store. Day 127's rule stands — structured fields, never raw payloads, for anything
authentication- or PII-adjacent.

# Part 3 — Interceptors, and the one thing only they can do

```java
@Component
class AuditInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (handler instanceof HandlerMethod hm) {              // ⭐ the whole point
            Audited audited = hm.getMethodAnnotation(Audited.class);
            if (audited != null) {
                req.setAttribute("auditAction", audited.value());
            }
        }
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        Object action = req.getAttribute("auditAction");
        if (action != null) auditLog.record(action, currentUser(), res.getStatus(), ex);
    }
}
```

```java
@Configuration
class WebConfig implements WebMvcConfigurer {
    @Override public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(auditInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/health", "/api/public/**");
    }
}
```

**The `HandlerMethod` is the reason interceptors exist.** A filter cannot know which controller
method will run; an interceptor gets the method object and can read its annotations. Anything of the
form "behave differently based on an annotation on the handler" is an interceptor's job.

**The three callbacks, and the trap in the middle one:**

| Callback | Runs | Note |
|---|---|---|
| `preHandle` | before the handler | `false` stops everything — **you must write the response** |
| `postHandle` | after the handler, **before rendering** | ⭐ **skipped entirely if the handler threw**, and for `@ResponseBody` the response may already be committed, so header changes here are silently lost |
| `afterCompletion` | always | the `finally`. Cleanup and timing go here |

`postHandle` being skipped on exception is why timing and cleanup must live in `afterCompletion` —
a timer started in `preHandle` and stopped in `postHandle` silently under-reports by omitting every
failed request, which is precisely the population you care about.

# Part 4 — AOP for the request-shaped concerns that are not requests

```java
@Aspect
@Component
class TimedAspect {
    private final MeterRegistry registry;

    @Around("@annotation(com.acme.Timed)")
    Object time(ProceedingJoinPoint pjp) throws Throwable {
        var sample = Timer.start(registry);
        String outcome = "success";
        try {
            return pjp.proceed();
        } catch (Throwable t) {
            outcome = "failure";
            throw t;
        } finally {
            sample.stop(registry.timer("method.duration",
                    "method", pjp.getSignature().toShortString(), "outcome", outcome));
        }
    }
}
```

**This works for an HTTP request, a Kafka consumer, a `@Scheduled` job and a test** — because it is
attached to the method, not to the transport. That is the whole argument for AOP over the other two.

**And Day 137's constraint still applies in full:** it is a proxy, so self-invocation does not
trigger it, `private` and `final` methods are invisible, and the annotated method must be called from
outside the bean. If a `@Timed` annotation appears to do nothing, that is the first hypothesis.

## The combined order, which is the thing to be able to state

```
Filter.doFilter (before)                        ← order 10, 20, 30…
  Security filter chain
    Interceptor.preHandle                       ← registration order
      AOP around advice (controller, if proxied)
        ⭐ CONTROLLER METHOD
          AOP around advice (service — @Transactional, @Cacheable)
            ⭐ SERVICE METHOD
      Interceptor.postHandle                    ← skipped if it threw
      HandlerExceptionResolver → @RestControllerAdvice
    Interceptor.afterCompletion                 ← always
Filter.doFilter (after)                         ← reverse order
```

Two consequences fall straight out of that picture:

- **A filter's `finally` runs after the advice has produced the error response**, so a filter sees the
  final status code — which is why request logging belongs in a filter, not an interceptor.
- **`@Transactional` on the service commits before `postHandle` runs**, so an interceptor cannot roll
  back the transaction. Anything that must participate in the transaction has to be inside it —
  Day 133's `@TransactionalEventListener` is the tool.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Plain `Filter` instead of `OncePerRequestFilter` | runs again on ERROR/FORWARD dispatch — duplicate IDs and logs |
| ⭐ Reading the body in a filter without a wrapper | stream consumed; controller gets empty DTOs |
| ⭐ Forgetting `copyBodyToResponse()` | every response body empty, no error anywhere |
| No `MDC.clear()` in `finally` | pooled thread carries the last request's ID (Day 066A) |
| Not validating the incoming correlation header | log injection and log-storage attacks |
| `@Component` filter applied to `/*` | runs on every actuator probe and static file |
| Timing in `postHandle` | silently excludes every failed request |
| Header changes in `postHandle` for `@ResponseBody` | response already committed; silently lost |
| Interceptor for a rule that jobs also need | invisible to every non-HTTP caller |
| Expecting an interceptor to roll back a transaction | commit already happened |
| Logging raw bodies | passwords and PII in the log store |
| AOP on a self-invoked or `private` method | Day 137 — silently does nothing |

## Interview questions

**Q: Filter, interceptor or AOP?**
Filter when it must run for every request including ones that never reach a handler, or when I need
to wrap the request or response — security, correlation IDs, CORS. Interceptor when I need to know
which handler was selected, typically to read an annotation on the method. AOP when the concern
belongs to a bean method rather than to HTTP, which is the deciding factor if the same operation also
arrives from a job or a consumer.

**Q: Why `OncePerRequestFilter`?**
Because the servlet container re-dispatches for errors, forwards and includes, and a plain filter runs
on each one. For anything stateful — a correlation ID, a timer, a rate-limit decrement — that means
doing the work multiple times per request.

**Q: You want to log request and response bodies. What breaks?**
The body is a one-shot stream, so reading it in a filter leaves nothing for the controller. You need
`ContentCachingRequestWrapper`, and on the response side `ContentCachingResponseWrapper` plus
`copyBodyToResponse()` or every response goes out empty. And I would cap, redact and scope it,
because a login body in the log store is a password in the log store.

**Q: Why is timing in `postHandle` wrong?**
It does not run when the handler throws, so the metric excludes exactly the requests that failed.
`afterCompletion` always runs.

## Mini task

1. Write `CorrelationIdFilter`. Confirm the ID appears in logs and is echoed in the response header.
2. **Delete `MDC.clear()`.** Set `server.tomcat.threads.max=1`, send two requests with different IDs,
   and watch the second log the first's ID. Put it back.
3. Extend plain `Filter` instead of `OncePerRequestFilter`, trigger a 500, and count how many times
   the filter ran.
4. Write a body-logging filter **without** the wrapper. Watch every POST arrive with null fields.
   Add `ContentCachingRequestWrapper`.
5. Add `ContentCachingResponseWrapper` and omit `copyBodyToResponse()`. Confirm 200 with an empty
   body. Add it back.
6. Write `@Audited` + an interceptor that reads it from the `HandlerMethod`. Confirm a filter cannot
   do this.
7. Start a timer in `preHandle`, stop it in `postHandle`. Throw from the handler. Watch the metric
   vanish. Move it to `afterCompletion`.
8. Write the `@Timed` aspect. Call the method from a controller (works) and then from another method
   in the same bean (does nothing) — Day 137, one more time.

## 🎙️ Articulation drill

Two minutes: **"How do you implement a cross-cutting concern in Spring?"**

Position the three by where they sit in the chain, then give the deciding question: does this concern
belong to HTTP, to a handler, or to a method? Correlation IDs are a filter because they must cover
requests that never reach a handler. Annotation-driven behaviour is an interceptor because only it
has the `HandlerMethod`. Transactions and retries are AOP because a Kafka consumer needs them too.
Then close on the two operational details that show you have shipped this: `OncePerRequestFilter`
because of error re-dispatch, and clearing the MDC in a `finally` because Tomcat threads are pooled.
