**P-293** · The RAG pipeline II — retrieval, ranking, and evaluation

# Part 1 — ⭐⭐ Vector search alone is not enough

**⭐ Embeddings capture *semantic similarity*. They are systematically bad at some things:**

| ⭐ Vector search fails on | ⭐ Example |
|---|---|
| ⭐ **Exact identifiers** | ⭐ a product code, an error code, a policy number |
| ⭐ **Rare terms** | a proper noun the model has barely seen |
| ⭐ **Negation** | "not covered" and "covered" embed closely |
| ⭐ **Numbers and dates** | "within 30 days" versus "within 60 days" |
| Acronyms and jargon | domain-specific, absent from training |

**⭐ The identifier case is the one users notice immediately**: someone searches for `ERR-4471` and
gets semantically-related documents that do not mention it. **Keyword search finds it instantly.**

## ⭐⭐ Hybrid search — usually the biggest single improvement

```
⭐ 1. Vector search  → top 50 by semantic similarity
⭐ 2. ⭐ Keyword search (Day 199's full-text) → top 50 by BM25/ts_rank
⭐ 3. ⭐ FUSE the two rankings
```

**⭐ Reciprocal Rank Fusion is the standard and it is genuinely simple:**

```
⭐ score(doc) = Σ over rankings of  1 / (k + rank)      ⭐ k ≈ 60
```

**⭐ Why RRF rather than blending the scores**: vector similarity and BM25 are on incomparable scales,
so weighting them requires tuning that does not transfer between corpora. **RRF uses only the
*ranks*, so it needs no normalisation and works out of the box** — which is why it has become the
default.

**⭐ And you already have the keyword half** (Day 199): a generated `tsvector` column with `setweight`,
plus `websearch_to_tsquery` so a user's stray operator is not a 500.

**⭐ Measure the improvement on Day 292's golden set.** Recall@5 going from 0.62 to 0.85 by adding
keyword search is a very good number to be able to quote, and it is a common magnitude.

# Part 2 — ⭐ Filter before you search, and rank after

## ⭐ Metadata filtering is a correctness and security requirement

```
⭐ WHERE tenant_id = :tenant                      ← ⭐⭐ SECURITY (Day 259, Day 292)
⭐   AND effective_from <= now() AND (effective_to IS NULL OR effective_to > now())
⭐   AND document_type = ANY(:allowed)
⭐ ORDER BY embedding <=> :query_embedding LIMIT 50
```

**⭐ `pgvector` doing this in one query is its main advantage over an external store** (Day 292): the
filter and the vector search are the same statement, so **there is no "retrieve then filter" step
that can return fewer than k results** — or, worse, be forgotten.

⚠️ **⭐ Filtering interacts badly with approximate indexes.** With HNSW, a highly selective filter can
mean the approximate search explores mostly non-matching vectors and **returns fewer good results
than an exact search would.** Measure recall *with your real filters applied*, not on the unfiltered
corpus — this is a common and confusing quality gap.

## ⭐ Reranking — expensive, and often worth it

```
⭐ Retrieve 50 cheaply → ⭐ rerank with a cross-encoder → keep the top 5
```

**⭐ Why it works: a bi-encoder embeds query and document separately, so it never compares them
directly. A cross-encoder reads both together** and is substantially more accurate — **but cannot be
precomputed, so it only runs on the shortlist.**

| | ⭐ Cost | ⭐ Benefit |
|---|---|---|
| ⭐ Cross-encoder rerank | ⭐ latency + per-query cost | ⭐ **often the second-largest recall gain after hybrid** |
| ⭐ LLM rerank | expensive, slow | best quality; ⭐ rarely justified |

**⭐ Measure it on the golden set before adopting it.** If hybrid search already gets recall@5 to 0.95,
reranking buys you little for real latency — **and knowing that, rather than adding it because it is
recommended, is the point.**

## ⭐ The other techniques, ranked by value-per-effort

| Technique | ⭐ Verdict |
|---|---|
| ⭐ **Query expansion** (synonyms, acronyms) | ⭐ cheap, effective for jargon |
| ⭐ **Sentence-window retrieval** | ⭐ embed small, ⭐ **return neighbours for context** — very effective |
| **HyDE** (generate a hypothetical answer, embed that) | works; adds a model call |
| **Multi-query** (rephrase, retrieve for each, fuse) | good for ambiguous queries; N× cost |
| Parent-document retrieval | retrieve the chunk, return its parent section |

**⭐ Sentence-window is the underrated one**: it directly addresses Day 292's chunking tension by
**embedding at a granularity that ranks well and returning at a granularity that answers well.**

# Part 3 — ⭐⭐ Evaluation — the part that makes everything else measurable

> **⭐⭐ Without an evaluation harness you are tuning by anecdote.** Every change "feels better", and
> nothing is comparable.

```markdown
# eval/golden-set.yaml  — ⭐ 50–200 queries
- query: "What is the refund window for digital goods?"
  ⭐ expected_sources: ["policy-v3#refunds-digital"]
  ⭐ expected_answer_contains: ["14 days"]
  ⭐ must_not_contain: ["30 days"]      ⭐ the superseded answer
```

**⭐ The `must_not_contain` field is the one people omit and it catches the worst failure**: retrieving
a superseded document and answering confidently from it (Day 292's `effective_to`).

## ⭐ The metrics, and what each isolates

| Metric | ⭐ Isolates |
|---|---|
| ⭐ **Recall@k** | ⭐ is the right chunk retrieved at all? |
| ⭐ **MRR / NDCG** | is it ranked highly? |
| ⭐ **Context precision** | ⭐ how much retrieved context is irrelevant noise? |
| ⭐ **Faithfulness** | ⭐⭐ **is the answer supported by the retrieved context?** |
| ⭐ **Answer correctness** | is it right? |

**⭐ Faithfulness is the metric that detects hallucination**, and it is separable from correctness: an
answer can be *correct* and *unfaithful* — the model knew it from training rather than from your
documents. **For a risk system that is a failure**, because the citation is then fictional.

**⭐ Run the harness in CI.** A retrieval change that improves one query and breaks four is exactly
what an evaluation set catches and what manual testing never does.

## ⭐ LLM-as-judge, used carefully

**⭐ For faithfulness and correctness at scale, a model can grade** — with three caveats worth
stating:

```
⭐ 1. Calibrate against human judgement on a subset first
⭐ 2. ⭐ Judges are biased — toward longer answers, and toward their own outputs
⭐ 3. ⭐ Pin the judge model and version — ⭐ otherwise your metric moves when they update it
```

**⭐ Point 3 is a real operational trap**: your quality metric changes because the provider updated
the judge, and you spend a day investigating a regression that did not happen.

# Part 4 — ⭐ Assembly, and operating retrieval

## ⭐ Building the context

```
⭐ Order by relevance — ⭐ but put the BEST chunk FIRST or LAST
⭐ Include provenance with every chunk so the model can cite
⭐ Budget tokens explicitly; ⭐ truncate at a CHUNK boundary, never mid-chunk
⭐ Deduplicate near-identical chunks
```

**⭐ The position effect is real and worth knowing**: models attend most reliably to the beginning and
end of a long context and are weakest in the middle — **so a highly-ranked chunk buried in the middle
of a large context may as well not have been retrieved.**

**⭐ Which is an argument for fewer, better chunks**: five well-ranked chunks usually beat twenty
mediocre ones, and cost less.

## ⭐ Latency and cost

```
⭐ Time each stage: ⭐ embed query · ⭐ vector search · ⭐ keyword search · rerank · generate
```

**⭐ Generation almost always dominates**, which means the retrieval optimisations that matter are
about *quality*, not speed. **But measure it** — an unindexed metadata filter or a missing HNSW index
can make retrieval the bottleneck, and that is a Day 189 problem with a Day 189 fix.

```
⭐ ⭐ Cache the embedding of repeated queries      ← ⭐ common queries repeat far more than expected
⭐ Cache full answers for identical queries        ← ⭐ with a version-aware key (Day 266)
```

**⭐ The answer cache key must include the document corpus version**, or you serve an answer from
superseded documents after an ingestion — **which is Day 266's versioned-key pattern applied to a new
kind of staleness.**

## ⭐ Observability

```
⭐ retrieval_recall_at_k (from CI runs)  · ⭐ retrieved_chunk_count
⭐ ⭐ zero_result_queries_total           ← ⭐ THE most diagnostic — nothing was retrieved
⭐ query_latency by stage · ⭐ tokens_used and cost per query
⭐ ⭐ LOG THE RETRIEVED CHUNK IDS with every answer  ← ⭐ or you cannot debug a bad answer
```

**⭐ Logging retrieved chunk ids is what makes a bad answer diagnosable at all** — without it, "the
answer was wrong" is unfalsifiable. ⚠️ **And remember Day 292's point: those logs contain document
content**, so they are subject to retention and deletion rules.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ **Vector search alone** | ⭐⭐ identifiers, rare terms and negation fail |
| ⭐ Blending vector and BM25 scores directly | incomparable scales; untransferable tuning |
| ⭐ **No tenant filter in retrieval** | ⭐⭐ cross-tenant leak, quoted fluently |
| ⭐ Measuring recall without real filters | ⭐ approximate search degrades under selective filters |
| Adding a reranker without measuring | latency and cost for an unknown gain |
| ⭐ **No evaluation harness** | ⭐⭐ tuning by anecdote; regressions invisible |
| ⭐ No `must_not_contain` cases | superseded answers pass |
| ⭐ Not separating faithfulness from correctness | ⭐ hallucination looks like success |
| ⭐ Unpinned judge model | your metric moves on their release schedule |
| Truncating mid-chunk | a fragment that misleads |
| ⭐ Burying the best chunk mid-context | ⭐ effectively not retrieved |
| Twenty mediocre chunks | worse answers, higher cost |
| ⭐ Answer cache without a corpus version | ⭐ answers from superseded documents |
| ⭐ **Not logging retrieved chunk ids** | ⭐ bad answers are undiagnosable |
