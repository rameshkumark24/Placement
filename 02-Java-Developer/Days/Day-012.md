# Part 1 — L-012 · What HTML actually is

## The answer

**HTML is a markup language that describes the structure and meaning of a document. It is not a
programming language.**

Say the second sentence with conviction, then justify it:

| Programming language has | HTML has |
|---|---|
| Variables | ❌ |
| Conditionals | ❌ |
| Loops | ❌ |
| Functions | ❌ |
| Computation of any kind | ❌ |

**HTML cannot compute anything.** It is not Turing-complete. It describes; it does not decide. You
cannot write "if the user is logged in, show this" in HTML — you need a server (Java, on Day 130+)
or JavaScript (Day 014) to *produce different HTML*.

**Markup** means annotating text with meaning. It comes from publishing — an editor "marking up" a
manuscript with instructions. HTML does exactly that:

```html
<p>The quick brown fox</p>
```

The tags don't change the text. They say *what the text is*: this run of characters is a paragraph.

## The three-way split — say this in an interview

| | What it is | Analogy |
|---|---|---|
| **HTML** | Structure and meaning | The skeleton |
| **CSS** | Presentation | The appearance |
| **JavaScript** | Behaviour | The muscles |

Any one can exist without the others. HTML alone renders — unstyled, but readable. That's not an
accident; it's the design. **Progressive enhancement**: content first, then styling, then behaviour.
A page that renders nothing without JavaScript has abandoned the model.

## HTML is a tree

This is the part that matters most, because it's the bridge to everything else.

```html
<html>
  <head>
    <title>My page</title>
  </head>
  <body>
    <h1>Hello</h1>
    <p>Some <strong>bold</strong> text</p>
  </body>
</html>
```

The browser parses that into a tree:

```
                    html
                   /    \
               head      body
                |        /    \
             title     h1      p
               |        |     /  \
           "My page" "Hello" "Some" strong
                                      |
                                   "bold"
```

**Every element is a node. Nesting is parent-child. Siblings are ordered.**

Why this matters, and it's four things at once:

1. **CSS selectors traverse this tree.** `body > p strong` is a path through it. Descendant,
   child, sibling combinators — all tree navigation.
2. **JavaScript manipulates this tree.** `document.querySelector` searches it; `appendChild` inserts
   into it.
3. **React's virtual DOM is a copy of this tree**, and reconciliation is a tree diff (Day 233).
   When you learn React, you will be learning *an algorithm over this structure*.
4. **It's the same shape as JSON, XML and your Java object graph.** A tree of nodes with typed
   children. Once you see that, `Jackson` serialising an object graph and a browser parsing HTML are
   the same kind of operation.

## HTML vs the DOM — the distinction people miss

**They are not the same thing.** This is a great interview differentiator.

```
   HTML             the text you (or your server) sent — a string of bytes
     │
     │  browser parses
     ▼
   DOM              a live, in-memory tree of objects
     │
     │  JavaScript mutates it
     ▼
   DOM ≠ HTML       the tree no longer matches the source you sent
```

**Three things follow:**

- **"View Source" shows the HTML. Devtools' Elements panel shows the DOM.** They differ the moment
  any JavaScript runs. If you've ever been confused that devtools shows elements not in view-source
  — that's this.
- **The browser repairs broken HTML while parsing.** Unclosed tags, wrong nesting — the spec defines
  exactly how to recover. So the DOM may have a structure you never wrote.
- **The DOM is an API, not a file format.** It's the object model your code programs against.

## Semantic HTML — why the tag choice matters

These render identically:

```html
<div class="header">Site name</div>
<header>Site name</header>
```

But the second carries **meaning**, and four different consumers read it:

| Consumer | Uses the meaning for |
|---|---|
| **Screen readers** | "Navigate to the main content" — impossible with anonymous `<div>`s |
| **Search engines** | Understanding page structure and importance |
| **Browsers** | Reader mode, autofill, keyboard behaviour |
| **Other developers** | Reading your markup a year later |

```html
<header>  <nav>  <main>  <article>  <section>  <aside>  <footer>
<h1>–<h6>  <p>  <ul>/<ol>/<li>  <table>  <form>  <label>  <button>
```

**The one that catches everyone:**

```html
<div onclick="submit()">Submit</div>     <!-- ❌ -->
<button onclick="submit()">Submit</button> <!-- ✅ -->
```

The `<div>` is not focusable, not reachable by keyboard, not announced as a button, doesn't respond
to Enter or Space, and won't submit a form. You'd have to reimplement all of that — badly. The
`<button>` gives you every one of those behaviours for free.

**This is the same accessibility rule** you already have in
[`03-Web-Developer/02-Design-System.md`](../../03-Web-Developer/02-Design-System.md) ("semantic HTML
— real `<button>`, `<nav>`, `<main>`"). Now you know *why* it's on that checklist.

## How the browser gets from HTML to pixels

Preview of Day 015, but the shape matters today:

```
   bytes → characters → tokens → nodes → DOM
                                          │
   CSS ────────────────────────► CSSOM ───┤
                                          ▼
                                    Render tree
                                          │
                                       Layout      (where and how big — "reflow")
                                          │
                                        Paint      (fill in pixels)
                                          │
                                      Composite    (layer the results)
```

Two consequences worth carrying now:

- **CSS is render-blocking.** The browser won't paint until the CSSOM is built, to avoid a flash of
  unstyled content. This is why CSS goes in `<head>`.
- **Synchronous `<script>` blocks parsing.** The parser stops, fetches, executes, then resumes —
  because the script might call `document.write`. This is why scripts go at the end of `<body>`, or
  use `defer`/`async`.

## Type this yourself

Serve HTML from the server you built. This closes the loop — you're now producing the document the
browser will parse into a tree.

```java
import java.io.*;
import java.net.*;

public class HtmlServer {
    public static void main(String[] args) throws IOException {
        ServerSocket server = new ServerSocket(8080);
        System.out.println("http://localhost:8080");

        String html = """
            <!DOCTYPE html>
            <html lang="en">
            <head>
              <meta charset="utf-8">
              <title>Hand-served</title>
            </head>
            <body>
              <header><h1>I served this from Java</h1></header>
              <main>
                <p>Parsed into a <strong>tree</strong> by the browser.</p>
                <ul><li>One</li><li>Two</li></ul>
                <button id="btn">Click</button>
              </main>
              <script>
                document.getElementById('btn').onclick = () => {
                  const p = document.createElement('p');
                  p.textContent = 'Added by JS — in the DOM, NOT in view-source';
                  document.querySelector('main').appendChild(p);
                };
              </script>
            </body>
            </html>
            """;

        while (true) {
            try (Socket client = server.accept()) {
                BufferedReader in = new BufferedReader(
                        new InputStreamReader(client.getInputStream()));
                in.readLine();
                while (true) { String h = in.readLine(); if (h == null || h.isEmpty()) break; }

                byte[] body = html.getBytes("UTF-8");
                OutputStream out = client.getOutputStream();
                out.write(("HTTP/1.1 200 OK\r\n"
                        + "Content-Type: text/html; charset=utf-8\r\n"
                        + "Content-Length: " + body.length + "\r\n"
                        + "Connection: close\r\n\r\n").getBytes());
                out.write(body);
                out.flush();
            }
        }
    }
}
```

**Now do these four things, in order — this is the whole lesson:**

1. Load it. Press **Ctrl+U** (View Source). That's the HTML your Java sent.
2. Open **devtools → Elements**. Same tree.
3. **Click the button.**
4. Look at Elements again — there's a new `<p>`. Now press **Ctrl+U** again.

**The new paragraph is not in view-source.** You have just seen, concretely, that the DOM and the
HTML are different things. The HTML was a one-time message; the DOM is a living structure.

Then, in the devtools console:

```js
document.body                              // the node
document.querySelectorAll('li')            // a NodeList
document.querySelector('main').children    // tree navigation
document.querySelector('h1').parentElement // upward
document.title = "Changed";                // mutate — watch the tab
```

Finally, break it deliberately:

```html
<p>Unclosed paragraph
<div>Block inside</div>
```

Serve that, then compare view-source with Elements. **The browser silently restructured your
markup.** That's error recovery, and it's why the DOM can differ from your HTML even before any
JavaScript runs.

## Common mistakes

| Mistake | Correction |
|---|---|
| "HTML is a programming language" | No variables, conditionals, loops or functions. It describes structure. |
| Treating HTML and the DOM as the same | HTML is the source text; the DOM is the live parsed tree. They diverge as soon as JS runs. |
| `<div>` for everything | Semantic elements carry meaning that assistive tech, search engines and browsers act on. |
| `<div onclick>` instead of `<button>` | Loses focusability, keyboard activation, and screen-reader role. |
| Skipping heading levels | `<h1>` then `<h3>` breaks the document outline screen readers rely on. |
| Thinking `<br>` is how you space things | That's CSS. `<br>` is a line break *within* content, like an address. |
| Assuming view-source shows what's rendered | It shows what the server sent. Devtools shows the current DOM. |

## Interview questions

**Q: What is HTML?**
> A markup language that describes the structure and semantics of a document. It annotates content
> with meaning — this is a heading, this is a paragraph, this is navigation. It isn't a programming
> language: no variables, conditionals, loops or computation. The browser parses it into a tree
> called the DOM.

**Q: What's the difference between HTML and the DOM?**
> HTML is the source text sent over the wire. The DOM is the in-memory object tree the browser builds
> from it, which JavaScript can then modify. They diverge as soon as script runs — view-source shows
> the HTML, devtools shows the DOM. The browser also repairs malformed markup during parsing, so the
> DOM can differ even without JavaScript.

**Q: Why does semantic HTML matter?**
> The tag communicates meaning to consumers other than the visual browser: screen readers use it for
> navigation and announcements, search engines for structure, and browsers for built-in behaviour.
> A `<button>` is focusable, keyboard-activatable and announced as a button; a clickable `<div>` is
> none of those.

**Q: How do HTML, CSS and JavaScript relate?**
> HTML is structure and meaning, CSS is presentation, JavaScript is behaviour. They're deliberately
> separable so a page degrades gracefully — content remains readable without CSS or JS.

**Q: Why is HTML a tree, and where does that matter?**
> Elements nest, giving a natural parent-child hierarchy. CSS selectors are paths through that tree,
> the DOM API is tree traversal and mutation, and React's virtual DOM diffing is a tree comparison.

# Part 2 — C-08 · DNS internals

*Reinforcement and depth on Day 007. If you're solid on the resolution walkthrough, this is a
RECALL candidate.*

## Recursive vs iterative — precisely

| | Recursive | Iterative |
|---|---|---|
| Asked by | Client (stub resolver) → resolver | Resolver → root/TLD/authoritative |
| Obligation | Must return a **final answer** | May return a **referral** |
| Work done by | The resolver | Spread across the hierarchy |

Root servers **only** answer iteratively. If they answered recursively, thirteen server clusters
would be doing the entire internet's DNS work. The referral model is what makes DNS scale.

## The caching layers

```
  Browser cache        seconds–minutes    (Chrome: chrome://net-internals/#dns)
  OS cache             follows TTL        (ipconfig /displaydns)
  Router cache         follows TTL
  ISP resolver cache   follows TTL        ← the big one, serving millions
  Authoritative        the source of truth
```

**Each layer independently honours TTL.** That's why a change propagates unevenly — different users
sit behind different caches with different remaining TTLs. There is no flush command that reaches
them all.

## Negative caching

Failures are cached too. If a name doesn't exist, `NXDOMAIN` is cached for the duration in the
zone's **SOA minimum** field.

**The practical trap:** you query a hostname before creating the DNS record, get `NXDOMAIN`, then
create the record — and it appears "not to work" for the negative-cache duration. People then spend
an hour debugging a record that's already correct.

## Record types — extended

Beyond Day 007's table:

| Type | Use |
|---|---|
| **SRV** | Service discovery — protocol, port and host (used by Kubernetes internally) |
| **CAA** | Which CAs may issue certificates for this domain — a real defence against mis-issuance (Day 009) |
| **ALIAS / ANAME** | Provider-specific CNAME-like record that *is* legal at the zone apex |
| **DNSKEY / RRSIG / DS** | DNSSEC — signatures proving records are authentic |

**Why CNAME is illegal at the apex:** a CNAME means "this name is an alias for another, and has no
other records". But the apex `example.com` must also carry SOA and NS records. The conflict is
structural, which is why providers invented ALIAS/ANAME — they resolve the target server-side and
return an A record.

**You've already hit this.** In
[`03-Web-Developer/10-Deploy-and-Launch.md`](../../03-Web-Developer/10-Deploy-and-Launch.md) the DNS
table uses an `A` record at `@` and a `CNAME` at `www`. Now you know that asymmetry isn't arbitrary.

## DNS security

| Threat | Mechanism | Defence |
|---|---|---|
| **Cache poisoning** | Forged reply accepted by a resolver | DNSSEC; source-port randomisation |
| **Eavesdropping** | Queries are plaintext UDP — your ISP sees every domain | DoH / DoT |
| **DDoS amplification** | Small query → large reply, spoofed source | Rate limiting, response rate limiting |
| **Hijacking** | Registrar account compromised | Registrar lock, 2FA on the registrar account |

**DNSSEC signs records** (authenticity). **DoH/DoT encrypt the query** (privacy). Different problems,
frequently confused — worth stating clearly if asked.

## Type this yourself

```bash
dig +trace www.github.com            # full walk, again — it should feel routine now
dig +short NS google.com             # authoritative nameservers

dig +short google.com @1.1.1.1       # bypass your ISP resolver
dig nonexistent-abc123.example.com   # NXDOMAIN — then repeat, note it's instant
```

That last pair demonstrates negative caching directly.

## Interview questions

**Q: Why don't root servers answer recursively?**
> They'd have to perform the entire internet's resolution work. Returning referrals keeps their job
> tiny and constant, which is what allows thirteen server clusters to underpin global DNS.

**Q: What is negative caching?**
> Caching of `NXDOMAIN` responses, for the duration in the zone's SOA minimum field. It prevents
> repeated queries for nonexistent names, but means a newly created record can appear broken until
> the negative cache expires.

**Q: Why can't you use a CNAME at the zone apex?**
> A CNAME means the name is purely an alias and can carry no other records, but the apex must carry
> SOA and NS records. Providers offer ALIAS/ANAME records, which resolve the target server-side and
> return an A record instead.

**Q: DNSSEC vs DoH — what does each solve?**
> DNSSEC provides authenticity by cryptographically signing records, defending against spoofing and
> cache poisoning. DoH and DoT provide confidentiality by encrypting the query in transit, defending
> against eavesdropping. They address different threats.
