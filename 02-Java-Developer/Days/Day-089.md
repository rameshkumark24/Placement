# Day 089

**L-089** · Clean code — naming, function size, side effects, and when a comment is a failure

**Time:** 3 hrs · **Mode:** NEW

> Opens the craft block. Everything from here to Day 101 is about code that *other people* — and
> future you — can change safely. That is the whole point: code is read far more often than it is
> written, and every hour spent making it readable is repaid every time someone opens the file.

# Part 1 — L-089

## The premise

> **You do not write code for the compiler. The compiler accepts anything that parses.**

You write it for the person who opens the file in eighteen months to change one thing under time
pressure, with no context and no access to you. Optimise for that reader.

The measurable consequence: the **cost of change** is what dominates a codebase's lifetime economics,
and readability is the largest single input to it.

## Naming

Naming is the highest-leverage thing in this whole day, because a good name removes the need for a
comment, a lookup and often a whole abstraction.

```java
// ❌
int d;                       // elapsed time in days
List<int[]> l;
if (x.get(0) == 4) { … }
public void proc(Data d, boolean f) { … }

// ✅
int elapsedTimeInDays;
List<Cell> flaggedCells;
if (cell.status() == FLAGGED) { … }
public void archiveOrder(Order order, boolean notifyCustomer) { … }
```

The rules that matter:

**Reveal intent.** The name should answer *why it exists, what it does, how it is used*. If it needs
a comment to explain, the name failed.

**Length should scale with scope.** `i` is fine as a three-line loop index. A field on a class that
lives for years is not the place for `mgr`. Inversely, a long name for a tiny scope is noise.

**No disinformation.** `accountList` that is a `Set` is worse than `accounts`. Drop type names from
identifiers entirely — the type is already declared.

**Make distinctions meaningful.** `Customer`, `CustomerData`, `CustomerInfo`, `CustomerObject` in one
codebase is four names conveying nothing. Noise words — `Data`, `Info`, `Manager`, `Processor`,
`Helper`, `Util` — usually mark a class that has no clear responsibility.

**Use searchable names.** `MAX_RETRIES = 3` can be found; the literal `3` cannot. This is the actual
argument against magic numbers, and it is stronger than "it's unclear".

**Class = noun, method = verb.** `OrderValidator.validate()`, not `OrderValidation.orderValidate()`.

**One word per concept.** Pick `fetch`, `get`, or `retrieve` and use it consistently for the same
kind of operation. Three synonyms across one codebase force the reader to check whether the
difference is meaningful.

**Use the domain's vocabulary.** If the business says "policy holder", the class is `PolicyHolder`,
not `InsuredPerson`. A translation layer between conversation and code is a permanent tax.

## Functions

```java
// ❌ 60 lines, four levels of nesting, three responsibilities
public void processOrder(Order order) {
    if (order != null) {
        if (order.getItems() != null && !order.getItems().isEmpty()) {
            double total = 0;
            for (Item item : order.getItems()) {
                if (item.getPrice() != null) {
                    total += item.getPrice() * item.getQuantity();
                    if (item.isDiscounted()) { … }
                }
            }
            // … 40 more lines: tax, shipping, payment, email, persistence
        }
    }
}
```

```java
// ✅
public void processOrder(Order order) {
    validate(order);
    Money total = pricing.totalFor(order);
    Receipt receipt = payments.charge(order.customer(), total);
    orders.save(order.paidWith(receipt));
    notifications.orderConfirmed(order);
}
```

The guidelines, in descending order of importance:

**1. Do one thing.** The real test: *can you extract another function from it with a meaningful name
that is not just a restatement?* If yes, it did more than one thing.

**2. One level of abstraction per function.** Do not mix `chargeCustomer(...)` with
`sb.append(item.name())` in one body. Mixed levels are what make a function hard to skim.

**3. Small.** Twenty lines is a lot. Five is common. This is a consequence of 1 and 2, not a rule to
enforce with a linter.

**4. Few arguments.** Zero is best, three is a lot, four wants an object. Beyond that, the argument
list is a struct in disguise:

```java
// ❌ what does the third boolean mean at the call site?
sendEmail(to, subject, body, true, false, true);

// ✅
sendEmail(EmailRequest.builder()
        .to(to).subject(subject).body(body)
        .html(true).trackOpens(false).highPriority(true)
        .build());
```

**Boolean parameters are a specific smell** — `render(true)` is unreadable at the call site and
usually means the function does two things. Two functions (`renderPreview()` / `renderFinal()`) are
almost always better.

**5. Command-query separation.** A function either *does* something or *answers* something, never
both. `boolean set(String key, String value)` is ambiguous — did it set, or check?

**6. Avoid output arguments.** `appendFooter(report)` mutating its argument surprises the reader;
`report.withFooter()` returning a value does not.

## Nesting and guard clauses

```java
// ❌ arrow code
public String describe(Order order) {
    if (order != null) {
        if (order.isPaid()) {
            if (order.hasItems()) {
                return "paid order with " + order.itemCount() + " items";
            } else { return "paid but empty"; }
        } else { return "unpaid"; }
    } else { return "no order"; }
}

// ✅ guard clauses — handle the exceptional first and return
public String describe(Order order) {
    if (order == null)      return "no order";
    if (!order.isPaid())    return "unpaid";
    if (!order.hasItems())  return "paid but empty";
    return "paid order with " + order.itemCount() + " items";
}
```

**Guard clauses flatten nesting and put the happy path at the bottom, unindented.** The rule of thumb:
more than two levels of indentation inside a method is a signal to extract or invert.

"Single exit point" is an old convention from languages without exceptions or destructors. In Java it
produces exactly the arrow code above; early returns are clearer.

## Side effects

```java
// ❌ the name says one thing, the body does another
public boolean checkPassword(String user, String password) {
    User u = repository.find(user);
    if (u != null && encoder.matches(password, u.hash())) {
        Session.initialize(u);       // ← SIDE EFFECT the name does not mention
        return true;
    }
    return false;
}
```

The caller believes they are asking a question. They are also creating a session. Now the method
cannot be used for validation alone, and someone will be surprised at 2 AM.

> **A function's name is a contract. Anything it does that the name does not imply is a bug in
> waiting.**

Related: **avoid temporal coupling** — methods that must be called in a specific order with nothing
enforcing it.

```java
// ❌
service.configure(config);
service.connect();
service.send(msg);          // NPE if you forget the first two

// ✅ make it impossible to get wrong
Connection conn = Service.connect(config);   // returns a usable object or throws
conn.send(msg);
```

## Comments

> **A comment is a failure to express yourself in code.** Not always avoidable — but always worth one
> attempt to avoid.

```java
// ❌ explains what the code already says
// increment i
i++;

// ❌ explains bad code instead of fixing it
// check if the employee is eligible for full benefits
if (e.flags & HOURLY && e.age > 65) { … }

// ✅ fix the code, delete the comment
if (employee.isEligibleForFullBenefits()) { … }
```

**Comments that are genuinely valuable** — and this is the shorter, more important list:

```java
// WHY, not what: the reason a reader could never infer
// Provider caps us at 100 rps per key; bursting triggers an hour-long ban.
private static final int MAX_RPS = 90;

// A non-obvious consequence
// Sorted by insertion order — the export format requires it, do not switch to HashMap.
private final Map<String, Field> fields = new LinkedHashMap<>();

// A warning
// Not thread-safe. Callers must hold the ledger lock.

// A deliberate deviation from the obvious
// Deliberately not using computeIfAbsent: the mapping function calls back into
// this map, which would deadlock (JDK-8071667).

// TODO with an owner and a ticket
// TODO(ram, JIRA-4471): remove once the v1 API is retired, Q1 2027.

/** Javadoc on public API — contract, params, exceptions, thread-safety. */
```

**The worst comments are the ones that lie**, and every comment drifts toward lying because nothing
verifies it. That is the real argument for expressing intent in code: the compiler checks code, and
nothing checks prose.

Delete commented-out code. It is in Git (Day 084) and nobody will ever restore it — but everyone who
reads it will wonder whether they can delete it.

## Formatting and structure

- **Vertical density**: related lines together, blank lines between concepts. A blank line is a
  paragraph break.
- **The newspaper metaphor**: highest-level concepts at the top, details below. A reader should be
  able to stop reading part-way and still have learned something.
- **Declare variables close to use.** A block of ten declarations at the top of a method is a
  language limitation from 1972, not a style.
- **Formatting is not a code-review topic.** Install a formatter (`spotless`, `google-java-format`),
  run it in CI, and never discuss it again. This is Day 088's "automate style" rule.

## The Boy Scout Rule

> **Leave the code cleaner than you found it.**

Not "stop and refactor the module" — rename one bad variable, extract one long block, delete one
stale comment, while you are in there for another reason. Small, continuous improvement is the only
kind that actually happens; the "we'll do a cleanup sprint" plan never survives contact with a
roadmap.

The counterweight, so this does not become sabotage: **keep the cleanup out of the behaviour-change
commit** (Day 085). Rename in one commit, change behaviour in another, so the reviewer can see what
actually changed.

## Code to type — refactor this

```java
public class OrderProcessor {
    public double calc(List<Object[]> items, int type, boolean flag) {
        double t = 0;
        for (int i = 0; i < items.size(); i++) {
            Object[] it = items.get(i);
            double p = (Double) it[1];
            int q = (Integer) it[2];
            if (type == 1) {
                t += p * q;
            } else if (type == 2) {
                t += p * q * 0.9;
            } else if (type == 3) {
                t += p * q * 0.8;
            }
            if (flag) {
                if ((Boolean) it[3]) {
                    t -= p * q * 0.05;
                }
            }
        }
        if (t > 1000) { t = t * 0.95; }
        return t + (t * 0.18);
    }
}
```

Refactor it in stages, committing each separately:

1. Name everything. What is `type`? What is `flag`? What is `0.18`?
2. Replace `Object[]` with a record.
3. Replace the `int type` with an enum carrying its own multiplier.
4. Extract the bulk discount and the tax.
5. Split the loop from the totalling.

Your target is something like:

```java
public record LineItem(String sku, Money unitPrice, int quantity, boolean clearance) {
    Money subtotal() { return unitPrice.times(quantity); }
}

public enum CustomerTier {
    STANDARD(1.00), SILVER(0.90), GOLD(0.80);
    private final double multiplier;
    CustomerTier(double m) { this.multiplier = m; }
    Money applyTo(Money amount) { return amount.times(multiplier); }
}

public class OrderPricing {
    private static final Money BULK_THRESHOLD = Money.of(1000);
    private static final double BULK_DISCOUNT = 0.05;
    private static final double CLEARANCE_DISCOUNT = 0.05;
    private static final double GST_RATE = 0.18;

    public Money totalFor(List<LineItem> items, CustomerTier tier, boolean applyClearance) {
        Money subtotal = items.stream()
                .map(item -> lineTotal(item, tier, applyClearance))
                .reduce(Money.ZERO, Money::plus);
        return withTax(withBulkDiscount(subtotal));
    }

    private Money lineTotal(LineItem item, CustomerTier tier, boolean applyClearance) {
        Money base = tier.applyTo(item.subtotal());
        return applyClearance && item.clearance()
                ? base.minusPercent(CLEARANCE_DISCOUNT) : base;
    }

    private Money withBulkDiscount(Money subtotal) {
        return subtotal.isGreaterThan(BULK_THRESHOLD)
                ? subtotal.minusPercent(BULK_DISCOUNT) : subtotal;
    }

    private Money withTax(Money amount) { return amount.plusPercent(GST_RATE); }
}
```

Note what changed beyond formatting: `double` became `Money` (Day 042B — this was money in a
`double`, a real bug), the magic numbers became named constants, and the enum absorbed the
conditional chain. **That last move is the seed of Day 090's Open/Closed Principle** — adding a tier
is now adding an enum constant, not editing an `if`.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Names that need a comment | The comment drifts; the name stays wrong |
| Type names in identifiers (`accountList`) | Lies when the type changes |
| `Manager`, `Helper`, `Util` classes | No clear responsibility; becomes a dumping ground |
| Boolean parameters | Unreadable call sites; the function does two things |
| Functions over ~30 lines | Multiple responsibilities, untestable |
| Deep nesting | Use guard clauses |
| Hidden side effects | Callers surprised; the method cannot be reused |
| Temporal coupling | Runtime failure with no compile-time signal |
| Comments explaining *what* | Noise that will eventually lie |
| Commented-out code | Everyone afraid to delete it |
| Style arguments in review | Install a formatter |
| Cleanup mixed into a behaviour commit | Unreviewable diff |

## Interview questions

**Q: What makes code readable?**
Names that reveal intent, small functions doing one thing at one level of abstraction, shallow
nesting via guard clauses, no hidden side effects, and comments reserved for *why*. The target reader
is someone changing it in eighteen months with no context.

**Q: When is a comment appropriate?**
When it says something the code cannot: the business reason for a constant, a non-obvious
consequence, a warning about thread-safety, a deliberate deviation, or public-API Javadoc. Comments
explaining *what* the code does should be replaced by better names.

**Q: How long should a function be?**
Short enough to do one thing at one level of abstraction. The test is whether you can extract another
meaningfully named function from it — if you can, it did more than one thing.

**Q: What is wrong with a boolean parameter?**
The call site is unreadable (`render(true)`), and it usually means the function branches into two
behaviours — which should be two functions.

**Q: What is the Boy Scout Rule and how do you apply it without derailing?**
Leave the code cleaner than you found it — small improvements while you are already in the file — but
commit the cleanup separately from the behaviour change so the diff stays reviewable.
