# Part 1 — The naive version, and everything wrong with it

```jsx
// ❌ the one in every tutorial
function Users() {
  const [users, setUsers] = useState([]);
  useEffect(() => {
    fetch("/api/users").then(r => r.json()).then(setUsers);
  }, []);
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}
```

```
⭐⭐ SEVEN BUGS IN SIX LINES

⭐ ① ⭐⭐ NO ERROR HANDLING — a 500 renders as an empty list (Day 217)
⭐ ② no loading state — a flash of "no users" before data arrives
⭐ ③ ⭐⭐ NO EMPTY STATE — "0 users" and "still loading" look identical
⭐ ④ ⭐ RACE — a fast id change lets the OLD response win (Day 217)
⭐ ⑤ ⭐⭐ SETS STATE AFTER UNMOUNT — leak + a React warning
⭐ ⑥ no cache — every mount refetches, back button = full reload
⭐ ⑦ ⭐ NO RETRY — one blip and the screen is permanently empty
```

# Part 2 — ⭐ The honest hand-rolled version

```jsx
function useQuery(key, fetcher) {
  const [state, setState] = useState({ status: "loading" });  // ⭐ Day 218 union

  useEffect(() => {
    const controller = new AbortController();
    let ignore = false;

    setState({ status: "loading" });        // ⭐ reset when key changes

    fetcher(controller.signal)
      .then(data => { if (!ignore) setState({ status: "success", data }); })
      .catch(err => {
        if (err.name === "AbortError") return;      // ⭐⭐ NOT an error
        if (!ignore) setState({ status: "error", error: err });
      });

    return () => { ignore = true; controller.abort(); };   // ⭐ Day 226
  }, [key]);                                // ⭐⭐ PRIMITIVE key, not an object

  return state;
}

function Users() {
  const q = useQuery("users", (signal) => api("/users", { signal }));

  if (q.status === "loading") return <Skeleton rows={5} />;
  if (q.status === "error")   return <ErrorBox error={q.error} onRetry={...} />;
  if (q.data.length === 0)    return <Empty action="Invite someone" />;
  return <ul>{q.data.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}
```

| ⭐ Line | Fixes |
|---|---|
| `AbortController` | ⭐⭐ The race **and** the wasted bandwidth |
| `ignore` flag | ⭐ The set-after-unmount |
| `AbortError` returns early | ⭐⭐ A cancel is **not a failure** and must never render an error |
| Discriminated union | ⭐ Makes "loading with data" unrepresentable — a sealed interface with exhaustive handling |
| `key` is primitive | ⭐⭐ Day 226's infinite loop, avoided by construction |

> ⭐ **This is ~25 lines and it still has no cache, no dedupe, no refetch-on-focus, no retry and no
> pagination.** That gap is the entire argument for Day 228 — **and you can now state it precisely.**

# Part 3 — Retries, and what must never be retried

```
⭐⭐ RETRY ONLY WHAT IS SAFE AND WHAT MIGHT SUCCEED

⭐   ✅ RETRY: network error · 502 · 503 · 504 · 429 (⭐ obey Retry-After)
⭐   ❌ NEVER: 400 · 401 · 403 · 404 · 422
⭐      ⭐⭐ THESE FAIL IDENTICALLY EVERY TIME.

⭐   ⭐⭐ AND NEVER BLIND-RETRY A NON-IDEMPOTENT POST.
⭐     "create order" retried after a TIMEOUT may create TWO orders —
⭐     ⭐ THE RESPONSE WAS LOST, NOT THE REQUEST.
⭐     ⇒ ⭐⭐ SEND AN IDEMPOTENCY KEY, OR DO NOT RETRY.
⭐       (The rule you already apply to any at-least-once consumer.)
```

```jsx
const delay = Math.min(1000 * 2 ** attempt, 30_000)
            + Math.random() * 250;        // ⭐⭐ JITTER — or every client
                                          //    retries in lockstep and you
                                          //    DDoS your own recovery
```

| ⭐ Rule | |
|---|---|
| **Cap attempts (3)** | ⭐ Infinite retry is a client-side outage amplifier |
| **Exponential + jitter** | ⭐⭐ Thundering herd — you met it in Stage 12 |
| **Do not retry on mount loops** | ⭐ A failing mount that retries forever is Day 226's bill again |

# Part 4 — ⭐⭐ The waterfall

```
⭐⭐ WHERE THE REQUEST SHOULD LIVE — and the default is NOT the component

⭐   ① ⭐ THE ROUTE / LOADER — start fetching when NAVIGATION starts,
⭐      not when the component mounts. ⭐⭐ SAVES A FULL ROUND TRIP.
⭐   ② ⭐ THE SERVER — render with data already present (Day 234)
⭐   ③ the component — fine for genuinely component-local data

⭐⭐ THE WATERFALL — the failure this prevents:
⭐   <Page> fetches user
⭐     └ <Profile> mounts AFTER, fetches profile
⭐        └ <Avatar> mounts AFTER, fetches image
⭐   ⇒ ⭐⭐ THREE SEQUENTIAL ROUND TRIPS THAT COULD HAVE BEEN ONE.
⭐     Each child cannot even START until its parent resolved.
⭐   ⇒ ⭐ THIS IS N+1 QUERIES — the LAZY-LOADING-IN-A-LOOP BUG YOU
⭐     ALREADY FIX WITH `JOIN FETCH` — ⭐⭐ EXCEPT EACH "QUERY" IS
⭐     200 ms OVER THE INTERNET INSTEAD OF 2 ms TO POSTGRES.
```

> ⭐⭐ **The waterfall is the biggest frontend performance mistake, and it is invisible in Micrometer**
> — each request is fast, the page is slow. **Hoist fetches up, run them in parallel, or move them to
> the route.** It is `JOIN FETCH` thinking applied to the network.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "how do you fetch data in React?"**

Reject the obvious answer with reasons. **Not `useEffect` plus `fetch`. That six-line version has seven
bugs: no error handling so a 500 renders as an empty list, no distinction between loading and empty, a
race where an old response wins, state set after unmount, no cache, no retry.**

Then the version you built. **A hook returning a discriminated union — loading, error, empty, success —
so all four are handled exhaustively and "loading with data" is unrepresentable. An AbortController
cancels superseded requests, and an abort returns early because a cancel isn't a failure.**

Then the honest limit. **That's twenty-five lines and it still has no cache, no dedupe, no refetch on
focus and no pagination. That gap is exactly why I use a query library — I can name what I'm buying
rather than adopting a dependency I can't justify.**

Close on the mistake that actually costs users time. **The waterfall. A page fetches a user, the child
mounts and fetches a profile, its child fetches an avatar — three sequential round trips that could
have been one, and each is individually fast so it's invisible in Micrometer. It's lazy loading in a
loop, except each "query" is two hundred milliseconds over the internet instead of two milliseconds to
Postgres. The fix is the same instinct as `JOIN FETCH`: hoist the fetches up, or move them to the route
so they start when navigation starts rather than when a component mounts.**
