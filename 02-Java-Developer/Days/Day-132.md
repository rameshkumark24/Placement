# Day 132

**L-132** · The IoC container — `BeanDefinition`s, `ApplicationContext`, the two-phase startup

**Time:** 3 hrs · **Mode:** NEW

> What the container *is*, rather than how to use it. Two ideas carry the whole day: **a bean is
> described before it is created**, and **startup happens in two phases with a different extension
> point for each**.
>
> Once you have those, `@Transactional` proxies, `@ConfigurationProperties` binding and
> auto-configuration all stop being magic.

---

# Part 1 — Bean definitions

**Spring does not build objects when it reads your annotations. It builds *descriptions*.**

```java
public interface BeanDefinition {
    String getBeanClassName();
    String getScope();                    // singleton, prototype, request…   (Day 134)
    boolean isLazyInit();
    boolean isPrimary();
    String[] getDependsOn();
    ConstructorArgumentValues getConstructorArgumentValues();
    MutablePropertyValues getPropertyValues();
    String getInitMethodName();           //                                   (Day 133)
    String getDestroyMethodName();
}
```

```
@Component class OrderService { … }
        ▼  scanning (Day 135)
BeanDefinition { class = "com.acme.OrderService", scope = "singleton", lazy = false, … }
        ▼  instantiation
OrderService@4f3a1b  (possibly wrapped in a proxy)
```

**The separation is what makes Spring extensible.** Because a definition is data, it can be
inspected and *modified* before any object exists — which is how `@ConfigurationProperties` binding,
profile filtering, auto-configuration and Spring Data's repository generation all work.

```java
ConfigurableApplicationContext ctx = SpringApplication.run(App.class, args);

ctx.getBeanDefinitionCount();
ctx.getBeanDefinitionNames();
BeanDefinition bd = ((ConfigurableListableBeanFactory) ctx.getBeanFactory())
        .getBeanDefinition("orderService");
```

**Run that today.** A trivial Boot application has hundreds of definitions, almost none of which you
wrote — that list is the auto-configuration surface (Day 140).

## Bean names

```
@Component class OrderService        → "orderService"        (decapitalised class name)
@Component("orders") class …          → "orders"
@Bean OrderService orderService()     → "orderService"        (the METHOD name)
@Bean(name = "primaryOrders") …       → "primaryOrders"
```

**Names must be unique**, and a later definition with the same name **silently overrides** an earlier
one unless overriding is disabled — which Boot 2.1 did by default, because silent override was a
frequent and baffling bug.

```properties
spring.main.allow-bean-definition-overriding=true   # ⚠️ a migration aid, not a fix
```

# Part 2 — The container hierarchy

```
BeanFactory                     the minimal container: getBean, wiring, lifecycle
   ▲
ApplicationContext              + events, i18n, resources, environment, AOP integration
   ▲
ConfigurableApplicationContext  + refresh(), close(), post-processor registration
   ▲
AnnotationConfigServletWebServerApplicationContext    ← what Boot actually creates for a web app
```

**`BeanFactory` versus `ApplicationContext` is a standard interview question**, and the practically
useful difference is one word:

| | `BeanFactory` | `ApplicationContext` |
|---|---|---|
| Instantiation | **Lazy** — on `getBean` | **Eager** — singletons at startup ⭐ |
| Events, i18n, resources | ❌ | ✅ |
| `BeanPostProcessor` | manual registration | automatic |
| Use | almost never directly | ✅ always |

> **Eager instantiation is the important property.** Singletons are created at startup, so a missing
> dependency, an ambiguous bean or a bad configuration value **fails the boot** rather than failing
> on the first request at 3 AM.

That is Day 062's fail-fast principle at the container level, and it is why `@Lazy` should be a
deliberate exception rather than a default.

# Part 3 — ⭐ The two-phase startup

**The single most useful thing in this day.** `refresh()` is the container's startup, and it splits
into two clearly separated phases.

```
─────────── PHASE 1: DEFINITIONS ───────────
1. Prepare the environment (property sources, profiles)
2. Load BeanDefinitions        (scanning, @Bean methods, imports)
3. ⭐ Run BeanFactoryPostProcessors  ← MODIFY THE DEFINITIONS. No objects exist yet.
       · ConfigurationClassPostProcessor — processes @Configuration, @Import, @Bean
       · PropertySourcesPlaceholderConfigurer — resolves ${…}
       · your own

─────────── PHASE 2: OBJECTS ───────────────
4. Register BeanPostProcessors
5. Instantiate all non-lazy singletons, in dependency order
       for each: construct → inject → ⭐ BeanPostProcessor.before
                                     → @PostConstruct / afterPropertiesSet / initMethod
                                     → ⭐ BeanPostProcessor.after   ← PROXIES CREATED HERE
6. Publish ContextRefreshedEvent
7. (Boot) start the web server, publish ApplicationReadyEvent
```

## The two post-processors, distinguished

**This is the distinction people get wrong**, and the names are unhelpfully similar:

| | `BeanFactoryPostProcessor` | `BeanPostProcessor` |
|---|---|---|
| Operates on | **Definitions** (metadata) | **Instances** (objects) |
| Runs | Phase 1 — before any bean exists | Phase 2 — around each bean's creation |
| Can | Add, remove or modify definitions | Wrap a bean in a proxy, or replace it |
| Example | `ConfigurationClassPostProcessor` | `AnnotationAwareAspectJAutoProxyCreator` ⭐ |

```java
// Phase 1 — change what will be built
@Component
class MyDefinitionProcessor implements BeanFactoryPostProcessor {
    @Override public void postProcessBeanFactory(ConfigurableListableBeanFactory bf) {
        BeanDefinition bd = bf.getBeanDefinition("orderService");
        bd.setLazyInit(true);                              // no object has been created yet
    }
}

// Phase 2 — change or wrap what WAS built
@Component
class MyInstanceProcessor implements BeanPostProcessor {
    @Override public Object postProcessAfterInitialization(Object bean, String name) {
        if (bean instanceof PaymentGateway gw) {
            return Proxy.newProxyInstance(…);              // ⭐ Day 056A — you built this
        }
        return bean;
    }
}
```

> **⭐ `postProcessAfterInitialization` returning a different object is how every Spring proxy is
> created.** `@Transactional`, `@Cacheable`, `@Async`, `@PreAuthorize` — all of them are a
> `BeanPostProcessor` returning a proxy instead of your bean.

**Two consequences to carry forward:**

**What gets injected into other beans is the proxy**, not your object — which is precisely why
self-invocation bypasses it (Day 137). You now know the mechanism, not just the rule.

**A `BeanPostProcessor` is instantiated early**, before ordinary beans, so **anything it depends on
is also created early — before other post-processors can proxy it**. That is why you occasionally
see a warning that a bean "is not eligible for getting processed by all BeanPostProcessors", and it
is a real cause of `@Transactional` mysteriously not working on a bean injected into a
post-processor.

# Part 4 — `@Configuration` and the proxying you did not ask for

```java
@Configuration
public class AppConfig {

    @Bean
    public DataSource dataSource() { return new HikariDataSource(config); }

    @Bean
    public OrderRepository orderRepository() {
        return new JdbcOrderRepository(dataSource());     // ⭐ a direct method call
    }

    @Bean
    public AuditRepository auditRepository() {
        return new JdbcAuditRepository(dataSource());     // ⭐ called AGAIN
    }
}
```

**How many `DataSource` objects exist?** One.

`@Configuration` classes are themselves **CGLIB-proxied**, and the proxy intercepts `@Bean` method
calls: the first call creates and registers the bean, and every later call returns the *same*
instance from the container.

```java
@Configuration(proxyBeanMethods = false)     // ⭐ no proxy — each call constructs a NEW object
```

**`proxyBeanMethods = false` is the modern default in Spring's own auto-configuration**, because the
proxy costs startup time and CGLIB does not work in a native image. It is safe **only if `@Bean`
methods never call each other** — pass the dependency as a parameter instead:

```java
@Bean OrderRepository orderRepository(DataSource ds) { return new JdbcOrderRepository(ds); }
```

**That parameter form is strictly better** and should be your habit: no proxy needed, no
inter-method calls, and the dependency is explicit.

`@Component` classes are **not** proxied this way, so a `@Bean` method inside a `@Component` really
does run again on each call — a subtle and genuinely confusing difference sometimes called "lite
mode".

# Part 5 — `@Bean` versus `@Component`

```java
@Component                    // ✅ YOUR classes — you can annotate them
class OrderService { }

@Configuration
class AppConfig {
    @Bean                     // ✅ THIRD-PARTY classes, or construction requiring logic
    ObjectMapper objectMapper() {                                    // Day 106
        return JsonMapper.builder().addModule(new JavaTimeModule()).build();
    }
}
```

| | `@Component` | `@Bean` |
|---|---|---|
| Where | On the class | On a method in `@Configuration` |
| Requires editing the class | ✅ | ❌ |
| Construction logic | constructor only | ✅ arbitrary |
| Several instances of one type | ❌ | ✅ |
| Discovered by | scanning (Day 135) | explicit declaration |

> **`@Component` for classes you own; `@Bean` for classes you do not, or where construction needs
> logic.** You cannot annotate `ObjectMapper` — it belongs to Jackson.

The stereotype annotations are all `@Component` with different semantics:

```
@Component   generic
@Service     business logic       — semantic only
@Repository  persistence          — ⭐ NOT semantic only: adds exception translation
@Controller / @RestController     — MVC handler mapping
```

**`@Repository` does real work**: it enables `PersistenceExceptionTranslationPostProcessor`, which
converts vendor-specific `SQLException`s into Spring's unchecked `DataAccessException` hierarchy —
Day 062's layer-translation principle, implemented by a post-processor.

# Part 6 — Getting at the container

```java
@Component
class ContainerInspector implements ApplicationContextAware {
    private ApplicationContext ctx;
    @Override public void setApplicationContext(ApplicationContext ctx) { this.ctx = ctx; }
}

// or just inject it
@Component
class Inspector {
    Inspector(ApplicationContext ctx) { … }
}
```

⚠️ **Needing `getBean()` in application code is a design smell** — it is the Service Locator pattern,
which reintroduces exactly the hidden dependency that DI removed (Day 131). Legitimate uses:
framework code, dynamic lookup by runtime name, and tests.

For dynamic lookup, prefer the typed forms:

```java
ObjectProvider<PaymentGateway> provider;      // ⭐ lazy, optional, stream-able
provider.getIfAvailable();
provider.stream().filter(g -> g.supports(type)).findFirst();
```

`ObjectProvider` is the right tool when you need a bean *sometimes*, and it keeps the dependency
visible in the constructor.

## Common mistakes

| Mistake | Consequence |
|---|---|
| Confusing the two post-processor types | Cannot reason about when to hook in |
| Expecting a `@Bean` method to run per call in a `@Component` | It does — no proxy there |
| `proxyBeanMethods = false` with inter-method calls | Duplicate objects; two connection pools |
| Duplicate bean names | Silent override (before Boot 2.1) |
| `@Lazy` everywhere | Startup failures become 3 AM runtime failures |
| `getBean()` in business logic | Service Locator; hidden dependencies |
| Depending on a bean from a `BeanPostProcessor` | That bean skips later post-processors — no `@Transactional` |
| `@Component` on a third-party class | You cannot annotate what you do not own |
| Assuming `@Service` differs from `@Component` | It does not — but `@Repository` does |

## Interview questions

**Q: What is a `BeanDefinition`?**
Metadata describing how to create a bean — class, scope, constructor arguments, lifecycle methods —
registered during phase one before any object exists. Because it is data, it can be inspected and
modified, which is how auto-configuration, property binding and Spring Data all work.

**Q: `BeanFactory` versus `ApplicationContext`?**
`ApplicationContext` extends `BeanFactory` with events, internationalisation, resource loading and
automatic post-processor registration — and, most usefully, it instantiates singletons **eagerly**,
so wiring and configuration errors fail the boot rather than the first request.

**Q: Describe Spring's startup.**
Two phases. First, load bean definitions and run `BeanFactoryPostProcessor`s, which can modify those
definitions while no objects exist. Second, instantiate singletons in dependency order, running
`BeanPostProcessor`s around each one — and it is there, in `postProcessAfterInitialization`, that
proxies are created.

**Q: How are Spring's proxies created?**
A `BeanPostProcessor` returns a different object from `postProcessAfterInitialization` — a JDK or
CGLIB proxy wrapping your bean. Everything injected elsewhere receives the proxy, which is exactly
why self-invocation bypasses the added behaviour.

**Q: Why are `@Configuration` classes proxied?**
So that a direct call between `@Bean` methods returns the container-managed singleton rather than
constructing a new object. `proxyBeanMethods = false` disables it for faster startup and native-image
compatibility, and is safe only if `@Bean` methods never call each other — pass dependencies as
method parameters instead.

**Q: `@Component` or `@Bean`?**
`@Component` for classes you own; `@Bean` for third-party classes you cannot annotate, or where
construction requires logic or several instances of one type.

**Q: Does `@Service` behave differently from `@Component`?**
No — it is semantic. `@Repository` *is* different: it enables exception translation from
vendor-specific `SQLException`s to Spring's unchecked `DataAccessException` hierarchy.

## 🎙️ Articulation drill

Two minutes: **"What happens when a Spring application starts?"**

Two phases: definitions loaded and modified by `BeanFactoryPostProcessor`s while no objects exist,
then singletons instantiated in dependency order with `BeanPostProcessor`s wrapping them — which is
where every proxy is created. Close with the consequence: what gets injected is the proxy, not your
object, which is why an internal call bypasses `@Transactional`. Explaining that from the lifecycle
rather than as a memorised rule is the whole point of the day.
