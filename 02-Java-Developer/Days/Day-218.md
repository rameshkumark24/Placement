# Day 218 🛡️

**J-218** · 🛡️ **TypeScript** — ⭐⭐ structural typing after a career of `implements`

**Time:** 3 hrs · **Mode:** NEW

> ⭐⭐ **The sentence to own: TypeScript checks the *shape* of a value rather than its declared type,
> so a class satisfies an interface by having the right methods and never by saying so — which
> deletes most of the ceremony you are used to, and also deletes the runtime guarantee you have been
> quietly relying on since your first day of Java.**
>
> Today: why *you* should insist on it, ⭐ structural vs nominal, ⭐⭐ erasure compared honestly, and
> the config that decides whether any of it is real.

---

# Part 1 — Why the backend engineer insists

```
⭐⭐ THE ARGUMENT THAT WINS, AND IT IS NOT "FEWER BUGS"

⭐   Your API returns a shape. ⭐ THE CLIENT ASSUMES A SHAPE.
⭐   ⭐⭐ NOTHING CHECKS THAT THESE ARE THE SAME SHAPE.

⭐   You rename UserDto.fullName -> UserDto.name.
⭐   ⭐ javac: every Java caller fails to compile. ✅
⭐   ⭐ The React app: renders "undefined" to a customer. ❌
⭐     ⭐⭐ NO ERROR. NO CRASH. JUST THE WORD "undefined" ON SCREEN.

⭐   ⇒ ⭐⭐ TYPESCRIPT + A GENERATED CLIENT (Day 246) TURNS THAT
⭐     INTO A BUILD FAILURE. That is the whole argument, and it is
⭐     a BACKEND argument — it protects YOUR contract.
```

| ⭐ Objection | Answer |
|---|---|
| *"It slows me down"* | ⭐ For a script, yes. For a codebase you return to in three months, the annotation is documentation you would otherwise not write. |
| *"React apps are small"* | Until they are not. ⭐⭐ The refactor you are afraid to do is the cost of not having types. |
| *"Types don't catch real bugs"* | ⭐ They catch exactly one class — **shape drift** — which happens to be the most common client-side production bug and the one with no runtime symptom. |

# Part 2 — ⭐⭐ Structural, not nominal

```typescript
type HasId = { id: string };

function show(x: HasId) { console.log(x.id); }

show({ id: "a", extra: 1 });   // ⭐ fits — it HAS an id.
                               // ⭐⭐ NOTHING DECLARED ANYTHING.
```

```java
// ⭐ Java — nominal. The declaration is the whole mechanism.
interface HasId { String id(); }
record User(String id, String name) implements HasId {}   // ⭐⭐ MUST SAY SO
// ⇒ a record with an id() method but no `implements` DOES NOT FIT.
```

| | Java | TypeScript |
|---|---|---|
| **Matching** | ⭐ nominal — by declared name | ⭐⭐ **structural — by shape** |
| **Declaration needed** | ✅ `implements` | ❌ none |
| **Two identical shapes** | ⭐ different, incompatible types | ⭐⭐ the same type |
| **Enforced at runtime** | ✅ ⭐ `instanceof` works | ❌ ⭐⭐ **nothing survives** |

```
⭐⭐ WHY THIS IS ACTUALLY GOOD NEWS FOR YOU

⭐   · ⭐ NO ADAPTER CLASSES to make a third-party type fit your
⭐     interface — if the shape matches, it matches.
⭐   · ⭐⭐ YOU CAN TYPE SOMEONE ELSE'S OBJECT WITHOUT OWNING IT.
⭐   · ⭐ Day 246's generated client works precisely BECAUSE of this:
⭐     the generated types describe shapes, and your code just fits.

⭐⭐ AND THE THING YOU LOSE, WHICH IS REAL:
⭐   ⭐ In Java, `x instanceof User` is a RUNTIME FACT. In TypeScript
⭐     there is NO User at runtime AT ALL — see Part 3.
```

# Part 3 — ⭐⭐ Erasure, compared honestly

You already know erasure. **TypeScript's is more total than Java's, and the difference matters.**

```
⭐⭐ JAVA ERASURE            ⭐⭐ TYPESCRIPT ERASURE
⭐  List<String> -> List     ⭐ EVERYTHING -> nothing
⭐  ⭐ THE CLASS SURVIVES     ⭐⭐ THERE IS NO TYPE AT RUNTIME AT ALL
⭐  instanceof List ✅        ⭐ instanceof User ❌ (User doesn't exist)
⭐  getClass() ✅             ⭐ no reflection over types
⭐  Jackson can deserialise   ⭐⭐ JSON.parse RETURNS A PLAIN OBJECT
⭐    INTO a typed object       AND YOU **ASSERT** ITS TYPE

⭐   ⇒ ⭐⭐ SO `const u: User = await res.json()` CHECKS NOTHING.
⭐     ⭐ It is `(User) someObject` with NO ClassCastException —
⭐       a cast that can never fail and can always be wrong.
⭐   ⇒ ⭐⭐ THAT IS WHY DAY 219 PAIRS TYPES WITH A RUNTIME VALIDATOR
⭐     AT THE BOUNDARY. It is your `@Valid`, which you already
⭐     believe in — you just have to add it yourself.
```

# Part 4 — The subset you write, and `strict`

```typescript
type User = {
  id: string;
  name: string;
  email?: string;          // ⭐ optional  -> string | undefined
  role: "admin" | "user";  // ⭐⭐ UNION OF LITERALS — better than an enum here
  createdAt: string;       // ⭐ a STRING on the wire, not an Instant
};

// ⭐⭐ discriminated union — models your four states exactly (Day 217)
type Result<T> =
  | { status: "loading" }
  | { status: "error"; error: ApiError }
  | { status: "success"; data: T };

function render(r: Result<User[]>) {
  switch (r.status) {
    case "loading": return <Skeleton />;
    case "error":   return <ErrorBox e={r.error} />;   // ⭐ r.error known here
    case "success": return <List items={r.data} />;    // ⭐⭐ r.data known here
  }                     // ⭐ forget a case and the compiler tells you
}
```

> ⭐⭐ **The discriminated union is a sealed interface with pattern matching**, and it is the most
> useful thing in this stage. It makes the four states of Day 217 *unrepresentable-if-wrong*: you
> cannot have `data` while `status` is `"loading"`. Same "make illegal states unrepresentable"
> argument you apply in Stage 8.

```typescript
const a: any = JSON.parse(text);
a.foo.bar.baz;              // ⭐⭐ COMPILES. CRASHES AT RUNTIME.
                            //    `any` disables checking, and it SPREADS.

const u: unknown = JSON.parse(text);
u.foo;                      // ✅ compile error — good
if (isUser(u)) u.name;      // ⭐ must narrow first. THIS is the right default.
```

```jsonc
// tsconfig.json — ⭐⭐ without these, TypeScript is decoration
{ "compilerOptions": {
    "strict": true,                        // ⭐⭐ THE ONE THAT MATTERS
    "noUncheckedIndexedAccess": true,      // ⭐ arr[0] is T | undefined — correct!
    "exactOptionalPropertyTypes": true } }
```

> ⭐⭐ **`strict: false` is the most common way a TypeScript codebase is fake** — everything untyped
> becomes implicit `any` and `null` is assignable everywhere. ⭐ It is the equivalent of compiling
> Java with every warning suppressed and calling it type-safe. **Ban `any` in CI**; where you need an
> escape hatch, `unknown` plus a narrowing function forces the check to be *written*.

## 🎙️ Articulation drill

⭐⭐ **Two minutes: "why TypeScript?"**

Do not say "fewer bugs" — everyone says it. Make it a contract argument, which is a backend argument.
**My API returns a shape and the client assumes a shape, and nothing checks those are the same. I
rename a field on a DTO and javac catches every Java caller, while the React app renders the literal
word "undefined" to a customer — no error, no crash. TypeScript plus a client generated from my OpenAPI
spec turns that into a build failure. It protects my contract, not just their code.**

Then the conceptual shift, since it is the interesting difference. **It's structurally typed, not
nominally. A value fits an interface by having the right shape, never by declaring it — so there's no
`implements`, no adapter classes to make a third-party type fit, and two identical shapes with
different names are the same type. That's why a generated client works so cleanly: it describes shapes
and my code just fits.**

Then the thing you lose, which is where Java experience actually helps. **Erasure is more total than
Java's. Java erases the type argument but keeps the class, so `instanceof` still works. TypeScript has
nothing at runtime at all — so annotating a JSON response as `User` is a cast that can never fail and
can always be wrong. That's why the boundary gets a runtime validator; it's `@Valid`, which I already
believe in, except I have to add it myself.**

Close on what makes it real. **`strict: true`, or it's decoration — without it everything untyped is
implicit `any`, which is compiling Java with all warnings suppressed and calling it type-safe. And
`any` is banned in CI, because it doesn't skip one check, it spreads to everything derived from it.**
