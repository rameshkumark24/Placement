# Day 331

**L-331** · Consistency models — from linearizable to eventual, and what users actually notice

**Time:** 3 hrs · **Mode:** NEW

> **⭐ "Eventually consistent" is not a consistency model. It is the absence of one — a promise that
> the system will agree at some unspecified point, with no statement about what you may see before
> then.**
>
> Today is the spectrum between "one copy" and "no promises", the two words people constantly
> confuse — *serializable* and *linearizable* — and the four session guarantees that fix almost every
> user-visible bug in practice.

---

# Part 1 — ⭐⭐ The spectrum

```
⭐ STRONGEST ─────────────────────────────────────────────────► WEAKEST
⭐  Linearizable → Sequential → Causal → Session guarantees → Eventual
⭐   (one copy)     (one order)  (cause    (your own view      (agree
⭐                                before    is sensible)        someday)
⭐                                effect)
⭐ COST:   high latency, ────────────────────────────► free
⭐         unavailable under partition                available always
```

| Model | ⭐ Guarantee | ⭐ Cost |
|---|---|---|
| ⭐ **Linearizable** | ⭐⭐ **behaves as if there were one copy; real-time order respected** | ⭐ a quorum round trip on **every read** |
| **Sequential** | all nodes see the same order — ⭐ **but not necessarily real time** | cheaper; surprising |
| ⭐ **Causal** | ⭐⭐ **causally related operations are seen in order; concurrent ones may differ** | ⭐⭐ **the sweet spot — available under partition** |
| ⭐ **Session guarantees** | ⭐ **your own experience is coherent** | ⭐ cheap; usually enough |
| Eventual | ⭐ replicas converge if writes stop | free |

## ⭐ Linearizability, precisely

> **⭐ Once a write completes, every subsequent read — by anyone, anywhere — returns that value or a
> later one.** There is a single point in time where the write "takes effect", and it lies between
> the call and the response.

```
⭐ A: write(x=1) ├────────┤
⭐ B:                       read(x) ├──┤  ⭐ MUST return 1 (B started after A finished)
⭐ C:            read(x) ├──────────────┤ ⭐ MAY return 0 or 1 (concurrent — either is legal)
```

| ⭐ Where you genuinely need it | ⭐ Why |
|---|---|
| ⭐ **Leader election / distributed locks** | ⭐ two leaders is a correctness disaster (Day 330) |
| ⭐ **Uniqueness constraints** | two users cannot both claim one username |
| ⭐ **The last unit of inventory** | ⭐ Day 316's seat, distributed |
| Balances before a debit | you cannot spend money twice |

⚠️ **The cost is not theoretical.** A linearizable read must confirm with a quorum that it is not
serving stale data — **so reads cost a network round trip, and during a partition the minority side
cannot serve them at all.**

## ⭐⭐ Serializable vs linearizable — the confusion to end

| | ⭐ Serializable | ⭐ Linearizable |
|---|---|---|
| ⭐ **About** | ⭐ **transactions over many objects** | ⭐ **single-object operations** |
| ⭐ **Guarantees** | ⭐ some serial order exists | ⭐ **real-time order is respected** |
| Comes from | database isolation (Day 195) | distributed systems |
| ⭐ **Missing piece** | ⭐⭐ **the order need not match real time — a transaction can be ordered "before" one that finished earlier** | it says nothing about multi-object transactions |
| ⭐ **Both together** | ⭐⭐ **strict serializability** — what Spanner provides | |

> **⭐ They are orthogonal, and that is the whole answer.** Serializable says *"as if run one at a
> time"*; linearizable says *"as if there were one copy, and time moves forward"*. **PostgreSQL's
> `SERIALIZABLE` on a single node gives you the first and, incidentally, the second. Reading from a
> replica gives you neither.**

# Part 2 — ⭐⭐ Causal consistency — the practical sweet spot

```
⭐ Alice: "Has the report shipped?"        (post A)
⭐ Bob:   "Yes, this morning."              (post B — a REPLY, so B depends on A)
⭐
⭐ ⭐⭐ A reader must never see B before A.  ⭐ That is causal consistency.
⭐ ⭐   Two unrelated posts may appear in any order — nobody notices or cares.
```

| ⭐ Property | |
|---|---|
| ⭐⭐ **Available during partitions** | ⭐⭐ **the strongest model that is — this is why it matters** |
| ⭐ Matches human expectation | ⭐ people notice effects before causes; they do not notice unrelated reordering |
| Implemented by | ⭐ vector clocks, dependency tracking, or **keeping related data in one partition** |
| ⭐ Cost | ⭐ metadata per write, and it grows with the number of writers |

> **⭐ The practical shortcut worth naming: most systems get causal consistency for free by keeping
> causally related data in the same partition.** A conversation thread, a user's own timeline, one
> aggregate (Day 305) — **if it is on one shard with one leader, causality is automatic.** That is
> another reason Day 329's shard key matters.

## ⭐ The four session guarantees

**⭐ These are what actually eliminate user-visible bugs, and each maps to a Day 328 anomaly:**

| Guarantee | ⭐ Prevents | ⭐ Implementation |
|---|---|---|
| ⭐ **Read your writes** | ⭐ **"my comment vanished"** | read from the leader after writing |
| ⭐ **Monotonic reads** | ⭐ **time going backwards** | pin the user to one replica |
| ⭐ **Monotonic writes** | ⭐ your own writes applied out of order | serialise a session's writes |
| ⭐ Writes follow reads | ⭐ **replying to something that then disappears** | track the read version into the write |

> **⭐ The insight that makes this section useful: users do not notice global inconsistency. They
> notice their own inconsistency.** Two strangers seeing a like count of 41 and 42 is invisible;
> **one user seeing their own comment disappear is a support ticket.** So session guarantees buy
> almost all the perceived correctness of strong consistency at almost none of the cost.

# Part 3 — ⭐ Eventual consistency, honestly

| ⭐ What it promises | ⭐ What it does not |
|---|---|
| ⭐ Replicas converge **if writes stop** | ⭐⭐ **no bound on when** |
| ⭐ Eventually you see the value | ⭐ **any guarantee about what you see meanwhile** |
| High availability | ⭐ that reads move forward, or that causality holds |

⚠️ **"Eventually" in practice is usually milliseconds — and occasionally hours**, during a partition,
a paused replica, or a backlogged queue. **Designs that are correct at 10 ms of lag and broken at
10 minutes are the ones that fail in incidents**, and the honest question is: *what is the maximum
lag this design tolerates before it is wrong?*

**⭐ Convergence needs a rule**, and the choice matters (Day 328):

| Rule | ⭐ Verdict |
|---|---|
| ⭐ Last-write-wins | ⭐ **converges by discarding data; depends on clocks** |
| ⭐ **CRDTs** | ⭐⭐ **converge with no loss — but only for types with a merge function** |
| Application merge | correct, and it is now your problem |

**⭐ CRDTs are worth one concrete sentence:** a counter that only increments, a set that only grows, a
last-writer-wins register per field — **operations that are commutative, associative and idempotent
converge regardless of order or duplication.** That is why they underpin collaborative editors and
shopping carts, **and why a plain "set the value" operation can never be one.**

# Part 4 — ⭐ Choosing, per operation

**⭐ The same system uses several models. Say which, and why.**

| Operation | ⭐ Model | ⭐ Reason |
|---|---|---|
| ⭐ **Claim a username** | ⭐ **linearizable** | uniqueness is a correctness invariant |
| ⭐ **Buy the last item** | ⭐ **linearizable** | ⭐ overselling is a real-world cost |
| ⭐ Post + reply thread | ⭐ **causal** | effects must not precede causes |
| ⭐ **Your own profile edit** | ⭐ **read your writes** | ⭐ **the classic anomaly** |
| A follower count | ⭐ eventual | nobody can tell, and nobody cares |
| ⭐ A feed | ⭐ eventual + monotonic | ⭐ stale is fine; going backwards is not |
| Analytics | eventual | minutes of lag are acceptable |

> **⭐ The framing that turns this into engineering: "how stale can this be, in seconds, before a
> user is harmed?"** That question has a number, the number chooses the model, and the model chooses
> the mechanism. **"We need strong consistency" without that number is a preference, not a
> requirement.**

⚠️ **And the cost asymmetry to state: strong consistency is not just slower — it is less
available.** A linearizable read cannot be served by a partitioned minority at all. **So choosing it
everywhere converts every network problem into an outage**, which is exactly the failure Day 330
warned about.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ "Eventually consistent" as a model | ⭐ **it says nothing about what you see meanwhile** |
| ⭐⭐ Confusing serializable with linearizable | ⭐⭐ **different axes — one is transactions, one is real time** |
| ⭐ Believing `SERIALIZABLE` on a replica is strong | ⭐ you have neither guarantee |
| ⭐ Strong consistency everywhere | ⭐ **every partition becomes an outage** |
| ⭐ Eventual consistency for uniqueness or inventory | ⭐ **duplicate usernames, oversold stock** |
| ⭐ Ignoring session guarantees | ⭐ **the bugs users actually report** |
| Round-robin replica reads | monotonic-read violations |
| ⭐ No staleness budget | ⭐ **"strong consistency" as a preference, not a requirement** |
| ⭐ Assuming lag is always milliseconds | correct at 10 ms, broken at 10 minutes |
| LWW without acknowledging the loss | convergence by deletion |
| Expecting CRDTs to solve everything | they need a commutative merge; "set to X" is not one |

## Interview questions

**Q: What is linearizability?**
The system behaves as if there were a single copy, and real-time order is respected — once a write
completes, every later read anywhere returns that value or a newer one. The cost is that a read must
confirm with a quorum, so it costs a round trip, and during a partition the minority side cannot
serve it at all.

**Q: Serializable or linearizable — what is the difference?**
Different axes. Serializable is about transactions over multiple objects and says some serial order
exists; it does not promise that order matches real time, so a transaction can be ordered before one
that visibly finished earlier. Linearizable is about single objects and does promise real-time order.
Both together is strict serializability, which is what Spanner provides. PostgreSQL's SERIALIZABLE on
one node gives you both incidentally; reading from a replica gives you neither.

**Q: What is causal consistency and why does it matter?**
Operations that are causally related are seen in order by everyone, while concurrent ones may be
seen differently. It matters because it is the strongest model that stays available during a
partition, and because it matches what people notice — nobody spots two unrelated posts being
reordered, but everyone spots a reply appearing before the thing it replies to. Most systems get it
free by keeping causally related data in one partition.

**Q: Which consistency model for a social feed?**
Eventual, with monotonic reads. Nobody can tell whether a like count is 41 or 42, so paying for
linearizability there converts every network hiccup into an outage. But a feed that goes backwards
because a user hit a lagging replica is obvious, so I pin a session to one replica. And read-your-
writes for anything the user posted themselves, because their own content disappearing is the bug
they will report.

**Q: How do you decide?**
Per operation, from a number: how stale can this be, in seconds, before a user is harmed? Uniqueness
and inventory tolerate zero, so linearizable. A reply thread needs causality. A feed tolerates
seconds. Analytics tolerate minutes. Without that number, "we need strong consistency" is a
preference — and it is an expensive one, because strong consistency is not just slower, it is less
available.

## 🎙️ Articulation drill

**Three minutes:** *"What consistency model does your system need?"*

**⭐ The answer that scores refuses to give one answer.** Go operation by operation with a staleness
budget in seconds for each: **zero for uniqueness and inventory, so linearizable; causality for
threads; seconds for feeds with monotonic reads pinned per session; minutes for analytics.**

**⭐ Then name the asymmetry unprompted**: strong consistency is not merely slower, it is less
available, so applying it everywhere means every network problem becomes an outage. **That sentence
connects today to Day 330 and is the one that makes the whole answer sound like a decision rather
than a preference.**
