# Day 119

**L-119** · API security — OWASP API Top 10, IDOR, mass assignment, SSRF, CSRF

**Time:** 3 hrs · **Mode:** NEW

> The attack catalogue. Several of these you have met piecemeal across the stage; today they become a
> system you can apply as a checklist. **The single most important fact in this day: the top three
> API vulnerabilities are all authorization failures**, not injection — which is the opposite of what
> most developers expect.

# Part 1 — The OWASP API Security Top 10 (2023)

| | Risk | In one line |
|---|---|---|
| **API1** | **Broken Object Level Authorization (BOLA/IDOR)** | Any user can access any object by id |
| **API2** | Broken Authentication | Weak tokens, no expiry, credential stuffing |
| **API3** | **Broken Object Property Level Authorization** | Mass assignment + excessive data exposure |
| **API4** | Unrestricted Resource Consumption | No rate limits, no size caps, expensive queries |
| **API5** | **Broken Function Level Authorization** | Admin endpoints reachable by ordinary users |
| **API6** | Unrestricted Access to Sensitive Business Flows | Automation abuse — bulk buying, spam |
| **API7** | **Server Side Request Forgery (SSRF)** | The server fetches a URL the attacker chose |
| **API8** | Security Misconfiguration | Debug on, CORS wide open, defaults unchanged |
| **API9** | Improper Inventory Management | Forgotten `/v1`, staging exposed, undocumented endpoints |
| **API10** | Unsafe Consumption of Third-Party APIs | Trusting an upstream's response blindly |

**Three of the top five are authorization.** Injection does not even appear in its own right —
because frameworks made parameterised queries the default, while authorization is something every
team must implement themselves, on every endpoint, for every object.

---

## ⭐ API1 — IDOR / BOLA

```http
GET /api/orders/1042        → your order      ✅
GET /api/orders/1043        → someone else's  💀
```

**The most common serious API vulnerability there is.** Day 105 and Day 111 covered it; here it is as
a discipline.

**Why it is so common:** the endpoint *is* authenticated, so it feels protected. The missing check is
per-object, and there is no compiler error, no test failure and no log entry when you forget it.

**Detection is trivial**, which is why attackers find these first:

```bash
for id in $(seq 1000 1100); do
  curl -s -o /dev/null -w "$id %{http_code}\n" -H "Authorization: Bearer $TOKEN" \
       https://api.acme.com/orders/$id
done                          # any 200 that is not yours is a finding
```

**Defences, in order of strength:**

```java
// 1. ✅ SCOPED QUERY — the unsafe version does not exist
repo.findByIdAndCustomerId(id, principal.id()).orElseThrow(NotFoundException::new);

// 2. ✅ Row-level security (Day 118) — enforced beneath all application code

// 3. ⚠️ Unguessable ids — DEFENCE IN DEPTH ONLY, never the control
// UUIDs make enumeration harder. They do not make access checks unnecessary.

// 4. ✅ Return 404, not 403 (Day 104) — do not confirm existence
```

**Point 3 is the one people get wrong.** "We use UUIDs so IDOR is not a problem" is false — ids leak
through URLs, logs, shared links, `Referer` headers and other API responses. Unguessability raises the
cost of *discovery*; it does not authorize anything.

## API3 — Object property level authorization

Two halves, both from Day 105:

**Mass assignment** — the client sets fields it should not:

```json
POST /users  {"email":"x@y.z", "password":"…", "role":"ADMIN", "isVerified":true}
```

**Excessive data exposure** — the response contains fields it should not:

```json
GET /users/17  → {"id":17,"email":"…","passwordHash":"$2b$…","internalNotes":"…","ssn":"…"}
```

The second is often *worse*, because it is invisible: the mobile app displays three fields, the API
returns thirty, and every one of them is in the client's memory and in every proxy log.

**One fix covers both: separate request and response DTOs. Never serialize an entity** (Day 105).

## API5 — Function level authorization

```http
GET  /api/users/me         ✅ every user
GET  /api/admin/users      💀 is this actually restricted?
DELETE /api/orders/1042    💀 is DELETE checked as carefully as GET?
```

Two patterns worth testing for explicitly:

**Hidden endpoints are not protected endpoints.** An admin route absent from the UI is still
reachable, and it is often the least-reviewed code in the system.

**Method-level gaps.** `GET /orders/42` is checked; `DELETE /orders/42` is not, because it was added
later. Test every method on every endpoint with a low-privilege token.

**The structural fix: deny by default.**

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/public/**").permitAll()
    .requestMatchers("/api/admin/**").hasAuthority("admin:manage")
    .anyRequest().authenticated());        // ← everything not listed is DENIED
```

An allow-list of public routes with a deny-all default means a new endpoint is protected by
construction. The reverse — deny-listing admin paths — means every new endpoint is public until
someone remembers.

## ⭐ API7 — SSRF

**The server fetches a URL the attacker controls.** Underestimated, and severe: your server sits
inside the network perimeter, so it can reach things the attacker cannot.

```http
POST /api/import  {"url": "https://example.com/data.csv"}     ← looks harmless

{"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"}  💀 AWS credentials
{"url": "http://localhost:8500/v1/kv/?recurse"}                              💀 Consul secrets
{"url": "http://10.0.1.5:6379/"}                                             💀 internal Redis
{"url": "file:///etc/passwd"}                                                💀 local files
```

**The cloud metadata endpoint is the classic target** — `169.254.169.254` returns IAM credentials on
AWS with IMDSv1, which is exactly how the 2019 Capital One breach worked. Enforce **IMDSv2**
(token-required) on every instance; that single setting defeats the most valuable SSRF target.

**Where SSRF hides:** webhook URL registration, image fetch-by-URL, PDF generation from a URL, link
previews, XML parsers with external entities (XXE), file imports, and any "fetch this for me"
feature.

**Defending it properly — allow-list, and validate after resolution:**

```java
URI uri = URI.create(userUrl);

// 1. scheme allow-list
if (!Set.of("https").contains(uri.getScheme())) reject();

// 2. resolve DNS ONCE, and validate the resulting IP
InetAddress addr = InetAddress.getByName(uri.getHost());
if (addr.isLoopbackAddress() || addr.isLinkLocalAddress()
        || addr.isSiteLocalAddress() || addr.isAnyLocalAddress()
        || isMetadataAddress(addr)) reject();

// 3. ⚠️ connect to THAT IP — do not resolve again
//    (otherwise DNS rebinding: the first lookup is safe, the second is 169.254.169.254)

// 4. disable redirects, or re-validate every hop
// 5. timeouts, response size caps, no credentials forwarded
```

**Steps 2 and 3 together are the part that is usually wrong.** Validating the hostname and then
letting the HTTP client resolve it again is a **TOCTOU** gap — DNS rebinding returns a safe address
for the validation lookup and an internal one for the actual connection. You must connect to the IP
you validated.

**The strongest defence is architectural:** route all outbound user-driven fetches through a
dedicated **egress proxy** in a network segment with no access to internal services or metadata. Then
an SSRF reaches nothing worth having, regardless of application-level mistakes.

## CSRF

Not in the API Top 10 (it targets browser-cookie sessions rather than token APIs), but essential.

```html
<!-- on evil.com, while the victim is logged into bank.com -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>
```

**The browser attaches bank.com's cookies automatically.** The attacker cannot *read* the response —
same-origin policy (Day 020) — but the state change has happened, and for a transfer that is
sufficient.

| Defence | How |
|---|---|
| **`SameSite=Lax` or `Strict`** | The cookie is not sent on a cross-site `POST` (Day 113) |
| **Synchronizer token** | A per-session token in a hidden field, verified server-side |
| **Double-submit cookie** | The same random value in a cookie and a header; the attacker cannot read the cookie to set the header |
| **Custom header requirement** | Cross-site `fetch` cannot set custom headers without a CORS preflight the server refuses |
| **Origin/Referer check** | Verify the `Origin` header — but it is a header (Day 105), so use it as one layer only |

**Token-based APIs sending credentials in an `Authorization` header are immune by construction** —
the browser does not attach that header automatically, so a cross-site form submission carries no
credential. **That is the strongest argument for header-based tokens over cookies.**

But note the corollary from Day 115: if you put the refresh token in a cookie (which you should),
**that endpoint needs CSRF protection**.

`SameSite=Lax` is now the browser default, which has quietly killed most classic CSRF. Keep tokens
for state-changing operations anyway — `Lax` still permits cross-site `GET`, older browsers differ,
and defence in depth is cheap here.

## API4 & API6 — Resource consumption and business-flow abuse

```http
GET /api/orders?limit=1000000               # unbounded page size (Day 107)
POST /api/reports {"dateRange":"10 years"}  # an expensive query
GET /api/search?q=a&sort=description        # a full sort on an unindexed column (Day 108)
POST /graphql {deeply nested query}          # exponential resolution
```

Every one is a denial of service delivered through a legitimate feature. The controls: **bound
everything** — page size, request body size, query depth, date ranges, result counts, upload size,
and a statement timeout on every query.

**API6 is different and interesting:** the endpoint works correctly and is being *used* abusively.
Buying every concert ticket in three seconds, creating ten thousand accounts, scraping the entire
catalogue. No individual request is invalid.

Defences are behavioural rather than technical: rate limits per user and per IP (Day 122), CAPTCHA on
sensitive flows, device fingerprinting, anomaly detection, and business rules ("maximum four tickets
per customer").

## API8 & API9 — Misconfiguration and inventory

**Misconfiguration checklist:**

```
❌ Debug endpoints in production (/actuator/env, /debug, /swagger with try-it-out)
❌ Stack traces in responses (Day 104)
❌ Access-Control-Allow-Origin: *  WITH  Allow-Credentials: true   ← the combination is fatal
❌ Default credentials
❌ Directory listing
❌ Missing security headers
❌ Verbose Server / X-Powered-By headers
```

**That CORS combination deserves its own line.** `Allow-Origin: *` with `Allow-Credentials: true` is
rejected by browsers — but reflecting the request's `Origin` header while allowing credentials is
*accepted*, and it means any site can make authenticated requests to your API and read the responses.
That is a complete bypass of the same-origin policy (Day 020). **Allow-list origins explicitly.**

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), camera=()
```

**API9 — inventory** is the boring one that causes real breaches: an old `/v1` still running with the
vulnerability you fixed in `/v2`, a staging environment with production data and no authentication, a
forgotten subdomain, an undocumented internal endpoint reachable from outside. **You cannot secure
what you do not know exists.** Maintain an inventory (Day 110's OpenAPI spec is one), and sunset old
versions properly (Day 109).

## API10 — Unsafe consumption of third-party APIs

The trust boundary (Day 105) runs in *both* directions. A response from an upstream service is
untrusted input: validate it, bound its size, time it out, and never render it without encoding.
A partner API returning `<script>` in a product name is stored XSS in your application.

# Part 2 — The security checklist

Run this against any API you build or inherit:

```
AUTHENTICATION
□ Passwords hashed with argon2/bcrypt, tuned                     (112)
□ Tokens: short-lived access, rotating refresh, reuse detection  (114, 115)
□ No secrets in tokens; algorithm pinned; aud/iss/exp validated  (114)
□ MFA available; breached-password check                         (111, 112)
□ Rate limiting on login and password reset                      (122)
□ No user enumeration on login, signup or reset                  (111)

AUTHORIZATION
□ Every object access scoped to the caller — no unscoped query   (105, 111)
□ Deny by default at the routing layer                           (API5)
□ Every HTTP method checked, not just GET                        (API5)
□ Row-level security for multi-tenancy                           (118)
□ A cross-tenant test per resource                               (118)

INPUT / OUTPUT
□ Allow-list validation, bounded sizes, at the boundary          (105)
□ Separate request and response DTOs                             (105)
□ Parameterised queries everywhere                               (119b)
□ Encoding on output, per destination context                    (105)
□ SSRF: allow-list + IP validation + egress proxy                (API7)

TRANSPORT & CONFIG
□ HTTPS only, HSTS, secure cookie flags                          (113)
□ CORS allow-listed — never reflected origin with credentials    (API8)
□ Security headers set                                           (API8)
□ Debug endpoints and stack traces off in production             (104)

OPERATIONS
□ Rate limits per user, per IP, per key                          (122)
□ Bounded pagination, query depth, body size, timeouts           (API4)
□ Audit log of denials; alert on enumeration patterns            (111)
□ Dependency scanning in CI                                      (100A)
□ Old versions sunset; inventory maintained                      (109, API9)
□ Secrets in a manager, rotated, never in source                 (115b)
```

## Common mistakes

| Mistake | Consequence |
|---|---|
| Assuming authentication implies authorization | IDOR on every endpoint |
| UUIDs treated as an access control | Ids leak; access is still unauthorized |
| `403` where enumeration matters | Confirms which objects exist |
| Serializing entities | Excessive data exposure |
| Binding requests to entities | Mass assignment |
| Deny-listing admin paths | Every new endpoint is public by default |
| Checking `GET` but not `DELETE` | Method-level authorization gap |
| Validating a URL then letting the client re-resolve it | DNS rebinding SSRF |
| IMDSv1 enabled | SSRF yields cloud credentials |
| Reflected `Origin` with `Allow-Credentials` | Complete same-origin bypass |
| Unbounded page size, depth or body | Denial of service via a feature |
| Forgotten `/v1` or staging environment | The vulnerability you already fixed |
| Trusting an upstream API's response | Stored XSS from a partner |

## Interview questions

**Q: What is the most common serious API vulnerability?**
Broken object level authorization — IDOR. The endpoint authenticates correctly but never checks
whether *this* caller may access *this* object, so changing an id in the URL returns someone else's
data. It is API1 because it is ubiquitous and trivially discoverable.

**Q: Do UUIDs prevent IDOR?**
No. They make enumeration harder, but ids leak through logs, URLs, shared links and other responses.
Unguessability is defence in depth; the control is a scoped query or row-level security.

**Q: What is SSRF and why is it severe?**
The server fetches an attacker-supplied URL, and the server sits inside the network perimeter — so it
can reach cloud metadata, internal services and local files the attacker cannot. The classic target
is the AWS metadata endpoint, which is how Capital One was breached.

**Q: How do you defend against SSRF?**
Allow-list schemes and hosts, resolve DNS once and validate the resulting IP against private, loopback
and link-local ranges, connect to *that* IP so DNS rebinding cannot switch it, disable or re-validate
redirects, cap size and time — and architecturally, route outbound fetches through an egress proxy
with no internal access. Enforce IMDSv2.

**Q: What is CSRF and why are token APIs immune?**
A cross-site request that the browser automatically attaches cookies to, performing a state change as
the victim. APIs sending credentials in an `Authorization` header are immune, because the browser does
not attach that header automatically. Cookie-based endpoints — including a refresh endpoint — still
need `SameSite` plus a token.

**Q: Why are three of the top five API risks authorization?**
Because frameworks made injection defences the default, while authorization must be implemented by
hand on every endpoint for every object — with no compiler error, no test failure and no log entry
when it is forgotten.

**Q: What is the danger with CORS?**
Reflecting the request's `Origin` while setting `Allow-Credentials: true` lets any site make
authenticated cross-origin requests and read the responses — a complete same-origin bypass. Allow-list
origins explicitly.

## Mini task

1. Build a deliberately vulnerable API with IDOR, mass assignment, excessive exposure, an unprotected
   admin route and SSRF. Exploit each one yourself with `curl`.
2. Write the enumeration script and run it against your own API. Fix every `200` that should not be.
3. Fix each vulnerability, then re-run every exploit and confirm it fails.
4. Build an SSRF endpoint. Reach `169.254.169.254` (or a local service). Add hostname validation, then
   defeat it with DNS rebinding using a rebinding service. Then fix it by connecting to the validated
   IP.
5. Test every HTTP method on every endpoint with a low-privilege token. Record any gaps.
6. Configure CORS with a reflected origin plus credentials, then demonstrate a cross-origin
   authenticated read from another origin.
7. Build a CSRF proof of concept against a cookie-session endpoint with no `SameSite`, then add
   `SameSite=Lax` and confirm it fails, then a `GET` version and confirm `Lax` is insufficient.
8. Set every security header and verify with `curl -I` and securityheaders.com.
9. Run the full checklist against a real project you have. Count the gaps honestly.
10. Run OWASP ZAP or Burp against your API and triage the findings.

## 🎙️ Articulation drill

Three minutes: **"How do you secure an API?"**

Lead with the counter-intuitive fact — the top risks are authorization, not injection — then IDOR and
the scoped-query fix, deny-by-default routing, request and response DTOs, SSRF with the egress-proxy
architecture, then transport and configuration, then the operational controls. Structure it as the
checklist's five sections; a systematic answer beats a list of attack names.
