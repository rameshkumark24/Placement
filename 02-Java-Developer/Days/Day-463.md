# Day 463

**L-463** · The resume II — numbers, honesty, and the line-by-line defence

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ "I don't have any numbers" is almost never true. You measured p99 before and after a cache, you
> ran a load test, you cut an image from 480 MB to 180 MB, you took a deploy from eleven minutes to four.
> Stages 10 through 12 exist partly so this page can have numbers on it.**
>
> Today: where metrics come from, **the exact line between confident and dishonest**, the defence drill
> that finds every weak bullet before an interviewer does, and tailoring without rewriting.

---

# Part 1 — ⭐⭐ Where the numbers come from

| ⭐ Category | ⭐ Metrics you already have |
|---|---|
| ⭐⭐ **Latency** | ⭐⭐ p50/p95/**p99 before and after**, at a stated load (Day 266, 286) |
| ⭐ **Throughput** | ⭐ rps sustained in a load test; messages/sec drained (Day 393) |
| ⭐ **Errors** | ⭐ error rate before/after; **dropped requests during a deploy** (Day 389) |
| ⭐⭐ **Delivery** | ⭐⭐ **build time, deploy time, rollback time** (Day 370) |
| ⭐ **Artefact** | ⭐ image size, cold-start time, memory footprint (Day 363) |
| ⭐ **Cost** | ⭐⭐ **monthly bill, cost per request, a saving with the mechanism** (Day 396) |
| ⭐ **Scale** | ⭐ rows, tenants, documents indexed, concurrent users tested |
| ⭐ **Quality** | ⭐ coverage delta, mutation score, flaky-test count (Day 281) |
| ⭐ **Reliability** | ⭐⭐ "zero dropped requests across a rolling deploy under 300 rps" (Day 397) |

```
⭐⭐ THE FORM THAT SURVIVES SCRUTINY — always include the CONDITIONS:
⭐   ❌ "Improved performance by 70%"
⭐      ⇒ ⭐⭐ 70% of what, measured how, under what load? ⭐ Unfalsifiable, therefore worthless.
⭐   ✅ "Cut p99 from 820 ms to 240 ms at 500 rps (k6, 10-minute soak)"
⭐      ⇒ ⭐⭐ checkable, and it survives "how did you measure that?" — which WILL be asked.
```

| ⭐ If you genuinely have no number | |
|---|---|
| ⭐⭐ **Go and measure it now** | ⭐⭐ the project still exists; a load test is an afternoon |
| ⭐ Use a **scale** figure instead | ⭐ "indexed 240k documents", "12 tenants, 40k rows" |
| ⭐ Use a **decision** instead of a metric | ⭐⭐ "chose X over Y because Z" is also evidence |
| ⭐ Never invent one | ⭐⭐ see Part 2 |

# Part 2 — ⭐⭐ The line between confident and dishonest

```
⭐⭐ THE TEST: ⭐⭐ Would the person who watched me do this recognise the description?

⭐ ✅ ⭐ CONFIDENT FRAMING — the same truth, told well
⭐    did: added a Kafka consumer with retry topics and a DLT to a side project
⭐    wrote: "Built an idempotent Kafka consumer with retry topics and a dead-letter
⭐            topic; verified exactly-once effects across 50 redeliveries."
⭐    ⇒ ⭐⭐ every word is true and you can go three levels deep. ⭐ This is not exaggeration.

⭐ ❌ ⭐⭐ DISHONEST — a claim about scale or role you did not have
⭐    wrote: "Designed Kafka topology handling 40k msg/s for a production trading platform."
⭐    ⇒ ⭐⭐ untrue, unrecoverable when probed, ⭐⭐ and it ends the interview quietly rather than loudly.

⭐ ⚠️ ⭐ THE GREY ZONE — team work described as solo
⭐    ⇒ ⭐⭐ Fix it with one word: "on a team of four, I owned the payments service."
⭐      ⭐⭐ Naming your scope makes you MORE credible, not less.
```

| ⭐⭐ Rules that keep you safe and still sound strong | |
|---|---|
| ⭐⭐ **Say "I" for what you did, "we" for the team, and name your part** | ⭐⭐ ambiguity reads as inflation |
| ⭐ Personal projects are labelled personal projects | ⭐⭐ **and are not weaker for it** if they are operated, not just built |
| ⭐ Never claim scale you did not run | ⭐ "load-tested to 500 rps" ≠ "served 500 rps in production" |
| ⭐⭐ **If asked "did you do this alone?", answer plainly** | ⭐⭐ the honest answer costs nothing; hesitation costs everything |

> **⭐ The commercial reality worth naming: inflated resumes usually pass the screen and fail the loop.**
> You get the interview and lose it in the first ten minutes, **having burned the company and a
> reference.** A precise resume gets fewer callbacks and converts far better — **and conversion is the
> only number that matters.**

# Part 3 — ⭐⭐ The line-by-line defence drill

```
⭐⭐ FOR EVERY BULLET, write the interviewer's three follow-ups and answer them out loud.

⭐ Bullet: "Implemented a transactional outbox so events are never lost."
⭐   Q1 ⭐ "Why did you need it — what was wrong with publishing after commit?"
⭐   Q2 ⭐⭐ "How does the relay work, and what happens if it publishes twice?"
⭐   Q3 ⭐⭐ "How do you know it works? Show me the failure you reproduced."
⭐ ⇒ ⭐⭐ If any answer is thin, you have TWO options and only two:
⭐   ⭐ (a) go and learn/measure it properly, or ⭐⭐ (b) DELETE THE BULLET.
⭐   ⭐⭐ There is no third option called "hope they don't ask".
```

| ⭐ Depth ladder — how far each bullet must go | |
|---|---|
| ⭐ Level 1 | **What** you did |
| ⭐⭐ Level 2 | ⭐⭐ **Why that approach, and what you rejected** |
| ⭐⭐ Level 3 | ⭐⭐ **How it fails, and what you measured** |
| ⭐ Level 4 | ⭐ What you would do differently, and at 10× scale |

**⭐⭐ A bullet that survives level 3 is an asset. A bullet that dies at level 2 is a trap you set for
yourself.** Run this on all of them; it typically takes two hours and removes a third of the document.

# Part 4 — ⭐ Tailoring, versions, and the review protocol

```
⭐⭐ 80 / 20 TAILORING:
⭐   80% of the resume is FIXED — it is what you have actually done.
⭐   ⭐⭐ 20% is REORDERED per role: which project is first, which bullets appear,
⭐     which skills lead, and matching the JD's exact vocabulary.
⭐ ⇒ ⭐⭐ Rewriting from scratch per application is a sign the base document is unfocused.
```

| ⭐ Situation | ⭐ Lead with |
|---|---|
| ⭐ Backend role | ⭐ flagship API, data modelling, outbox, performance numbers |
| ⭐ Platform/DevOps-leaning | ⭐ pipeline, containers, IaC, observability, cost |
| ⭐ Product/startup | ⭐⭐ **shipped end to end, alone, and operated it** |
| ⭐ AI-adjacent | ⭐ NexOps: retrieval, evaluation, prompt injection, cost per query |

| ⭐ The review protocol | |
|---|---|
| ⭐ 1. Read it **aloud** | ⭐ anything you stumble over is badly written |
| ⭐⭐ 2. **Ten-second test** on a stranger | ⭐⭐ ask what they remember — it should be your best thing |
| ⭐ 3. Plain-text parse test | ⭐ Day 462 |
| ⭐⭐ 4. **The defence drill** | ⭐⭐ Part 3 — the one that actually changes outcomes |
| ⭐ 5. Every link opened | ⭐ weekly |
| ⭐ 6. LinkedIn reconciled | ⭐⭐ contradictions get noticed |

⚠️ **One resume-adjacent thing worth saying: the cover letter is rarely read at large companies and
occasionally decisive at small ones.** If you write one, **four sentences**: what you build, one specific
thing about *them* that is true, the one project most relevant, and what you want. **A generic cover
letter is worse than none because it proves you sent fifty.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **"Improved performance by 70%"** | ⭐⭐ unfalsifiable, and it dies to "measured how?" |
| ⭐ Numbers without conditions | ⭐ "500 rps" means nothing without duration and setup |
| ⭐ Claiming "I have no metrics" | ⭐⭐ the project still exists — go and measure |
| ⭐⭐ **Claiming production scale you never ran** | ⭐⭐ unrecoverable when probed |
| ⭐ "We" everywhere with no stated scope | ⭐⭐ ambiguity reads as inflation |
| ⭐ Hiding that a project was personal | ⭐ operated personal projects are strong; hiding is not |
| ⭐⭐ **A bullet that dies at level 2** | ⭐⭐ a trap you set for yourself |
| ⭐ Skipping the defence drill | ⭐ the interviewer runs it for you, live |
| ⭐ Rewriting the resume per application | ⭐ the base document is unfocused |
| ⭐ Not matching the JD's vocabulary | ⭐ the screen is often keyword-based |
| ⭐ Generic cover letters | ⭐⭐ proof you sent fifty |
| LinkedIn contradicting the resume | it gets noticed, and it looks careless |

## Interview questions

**Q: How do you measure the impact of your work?**
Before and after, under stated conditions. For performance that means percentile latency at a named load
with a named tool and duration, not a percentage improvement — a percentage with no baseline is
unfalsifiable and dies immediately to "measured how?". For delivery it is build time, deploy time and
rollback time. For cost it is the monthly bill and the cost per request. And where I genuinely have no
number, the honest move is to go and measure it, because the project still exists and a load test is an
afternoon.

**Q: Did you build this alone?**
On personal projects, yes, and I say so plainly — a project I designed, built, deployed and operated is
not weaker for being personal, it is just labelled accurately. On team work I name my scope in one
clause: on a team of four I owned the payments service. Being specific about scope makes me more
credible rather than less, because ambiguity between "I" and "we" is the thing interviewers read as
inflation.

**Q: Where is the line between selling yourself and overstating?**
Whether the person who watched me do it would recognise the description. Describing a side-project Kafka
consumer as an idempotent consumer with retry topics and a dead-letter topic verified across fifty
redeliveries is confident framing of a true thing — every word survives three follow-ups. Describing it
as designing a topology handling forty thousand messages a second for a production trading platform is a
claim about scale and role I did not have, and it cannot be recovered once probed. The practical
consequence is that inflated resumes tend to pass the screen and fail the loop, which is the worst
possible trade.

**Q: How do you know your resume will hold up?**
I run a defence drill on it. For every bullet I write the three follow-ups an interviewer would ask and
answer them aloud, and each bullet has to survive four levels: what I did, why that approach and what I
rejected, how it fails and what I measured, and what I would do differently at ten times the scale. A
bullet that dies at level two is a trap I set for myself, so it either gets learned properly or deleted.
It takes about two hours and usually removes a third of the document.

**Q: Do you tailor your resume?**
Eighty percent stays fixed, because it is what I actually did. The twenty percent that moves is ordering
— which project leads, which bullets appear, which skills come first — and matching the job
description's exact vocabulary, since the first pass is often keyword-based. If I find myself rewriting
from scratch for each application, that tells me the base document is unfocused rather than that the
roles are different.

## Mini task

1. ⭐⭐ Build a **metrics inventory** for both projects: latency, throughput, errors, build/deploy times,
   image size, cost, scale, coverage. **Go and measure anything missing.**
2. ⭐ Rewrite every number to include its **conditions** — load, tool, duration.
3. ⭐⭐ Find every bullet where "we" is ambiguous and **add your scope in one clause.**
4. ⭐⭐ Run the **defence drill** on all bullets. Record yourself. Mark each as survives-L2, L3 or L4.
5. ⭐⭐ **Delete or fix** everything that dies before level 3.
6. ⭐ Apply the **"would they recognise this?"** test to every claim.
7. ⭐ Produce **two tailored versions** — backend-leaning and platform-leaning — by reordering only.
8. ⭐ Extract the exact vocabulary from three real job descriptions and reconcile it with your wording.
9. ⭐ Do the **ten-second test** on two people. Compare what they remember.
10. ⭐ Reconcile **LinkedIn** with the resume, line by line.
11. ⭐ Write one **four-sentence cover letter** for a company you actually want.
12. ⭐⭐ Put a **weekly reminder** to open every link on the document.

# 🚪 Exit questions

1. Name six categories of metric you already possess.

3. What must always accompany a throughput figure?

6. Give the confident, dishonest and grey-zone versions of one claim.

## 🎙️ Articulation drill

**Two minutes:** *"Pick the bullet you are proudest of and defend it."*

**⭐ Take the outbox line and run the ladder out loud. What: events are published through a transactional
outbox rather than after commit. Why: because save-then-publish is a dual write, and the failure nobody
detects is a committed order whose event never fired — so the event goes into the same transaction as the
state change and a relay publishes it.**

**⭐ Then the part that separates a defended bullet from a decorated one: how I know it works. I killed
the process between the commit and the publish and reproduced the lost event, then added the outbox and
reproduced the same kill with no loss. And the consumer inserts a dedup key in the same transaction as
its effect, so fifty redeliveries produce one outcome — which I tested.**

**⭐ Finish with the limit, because volunteering it is what makes the rest believable: the relay polls, so
there is up to a second of latency, and at higher volume I would move it to change data capture on the
outbox table.**
