# Day 289 🏗️

**P-289** · Re-deriving the data model — from the requirements, not the code

**Time:** 3 hrs · **Mode:** BUILD

> **⭐ Today you design the schema NexOps should have had, without looking at the schema it has.**
>
> That order matters. If you start from the existing tables you will rationalise them — every schema
> looks reasonable from the inside. **Deriving it independently and then diffing is the only way to
> see what the original actually got wrong**, as opposed to what merely looks unfamiliar.

---

# Part 1 — ⭐ Derive it blind

**⭐ Close the code. Work from the behaviour you documented on Day 288.**

```
⭐ 1. List the ENTITIES from the domain language, not from the tables
⭐ 2. For each: what is its lifecycle? ⭐ what makes it unique? what must always be true of it?
⭐ 3. Draw the relationships: ⭐ cardinality, ⭐ owning side, ⭐ on delete
⭐ 4. Draw the AGGREGATE boundaries — ⭐ what must change atomically together
⭐ 5. Identify the EVENTS — ⭐ things that happened, whose values must be frozen (Day 188)
```

**⭐ Step 5 is where risk systems most often go wrong**, and it is worth dwelling on:

> **⭐⭐ A risk score is an event, not an entity.** It describes *what was computed, from what inputs,
> under which rules, at what time.* **If the score is recomputed on read, or if it references the
> current rule weights rather than the ones used, then last month's assessment silently changes when
> you tune a parameter** — and every audit trail in the system becomes fiction.

**⭐ Day 188's event-versus-entity test, applied here:**

| Value | ⭐ Event or entity? |
|---|---|
| ⭐ The risk score produced by an assessment | ⭐ **event — frozen, with its inputs** |
| ⭐ The weights used to produce it | ⭐ **frozen with the event** (or a version reference) |
| ⭐ The entity's *current* risk classification | ⭐ entity — derived from the latest event |
| An entity's name at assessment time | ⭐ event — copied |

**⭐ If NexOps stores a score without the inputs and the rule version that produced it, that is a
Critical finding**, because it means no assessment can be explained or reproduced — which for a risk
system is the whole product.

# Part 2 — ⭐ Apply Day 188's checklist to your derived model

**⭐ Run all twelve. These are the ones most likely to differ from the original.**

| # | Check | ⭐ Why it matters here |
|---|---|---|
| ⭐ 2 | **Events copy their values** | ⭐ scores must be reproducible |
| ⭐ 4 | **A check constraint per state invariant** | ⭐ an assessment cannot be `COMPLETE` with no score |
| 5 | `not null` unless absence is meaningful | ⭐ a null score and a zero score are different things |
| ⭐ 6 | ⭐ `timestamptz`, `numeric` | ⭐ a score computed at a wall-clock time is ambiguous |
| ⭐ 7 | **An index per query pattern** | Day 288's audit almost certainly found gaps |
| ⭐ 10 | **Nothing unbounded** | ⭐ an assessments table with no retention plan |
| ⭐ 11 | **Migratable with expand/contract** | ⭐ can you version the rules without a rewrite? |
| 12 | Write path vs report path | ⭐ risk dashboards are a different shape |

**⭐ Item 11 deserves specific thought for a risk system**: rule weights *will* change. **Design the
schema so that changing them is a normal operation, not a migration** — which usually means the rules
are data with a version, not constants in code.

## ⭐ The identity and audit decisions

```
⭐ Internal bigint + external UUID          (Day 158, Day 250)
⭐ version bigint for optimistic locking     (Day 165)
⭐ created_at / created_by, immutable        (Day 165)
```

**⭐ And for a risk system, an append-only history is not optional:**

| Approach | Verdict here |
|---|---|
| Audit columns only | ⭐ **insufficient** — only the latest state |
| Envers / shadow tables | ⭐ field-level history, doubled writes |
| ⭐ **Append-only assessment events** | ⭐⭐ **correct — the assessment IS the record** |

**⭐ Day 165's distinction applies exactly**: field-level history is forensic; **a domain event is
meaningful.** "Assessment computed for entity X, score 0.82, using ruleset v4, from these inputs, at
this time" is what a regulator, a customer or a support agent actually needs.

# Part 3 — ⭐⭐ The diff — and this is the exercise

**⭐ Now open the existing schema and compare, table by table, column by column.**

```markdown
# docs/SCHEMA-DIFF.md
| Area | ⭐ As built | ⭐ As derived | ⭐ Verdict |
|------|-----------|--------------|-----------|
| Risk score storage | ⭐ a column on entity, overwritten | ⭐ an append-only event with inputs | ⭐ **Critical — no reproducibility** |
| Rule weights | ⭐ constants in Java | ⭐ versioned rows | ⭐ High — a redeploy to tune |
| Timestamps | `timestamp` | ⭐ `timestamptz` | ⭐ High — ambiguous |
| Entity → assessments | ⭐ `@OneToMany` collection | ⭐ unidirectional + Pageable | Medium (Day 159) |
| Document chunks | no index on doc_id | ⭐ indexed | High |
```

**⭐ Four categories for every difference**, and the middle two are where the thinking is:

| Category | Meaning |
|---|---|
| ⭐ **Genuinely wrong** | it was always a mistake — fix it |
| ⭐ **Right then, wrong now** | ⭐ constraints changed — fix it, and say what changed |
| ⭐ **Different but equivalent** | ⭐ **leave it alone.** Not every difference is an improvement |
| ⭐ **My derivation is worse** | ⭐ ⭐ **this will happen — write it down** |

> **⭐⭐ The fourth category is the most valuable thing you can find today.** Discovering that your
> original design handled something your fresh derivation missed means the original had a reason you
> had forgotten — **and finding it is a much better story than a list of things you got wrong.**

**⭐ The third category is a discipline**: a difference is not automatically an improvement, and
changing something because it is unfamiliar is how rebuilds introduce regressions.

# Part 4 — ⭐ Migrate what you decided to change

**⭐ Every schema change here is on a system with data. Day 166 applies in full.**

```
⭐ 1. ⭐ Expand/contract for anything renamed, split or narrowed
⭐ 2. ⭐ set lock_timeout = '3s' at the top of every migration   (Day 196)
⭐ 3. ⭐ create index CONCURRENTLY, with executeInTransaction=false
⭐ 4. ⭐ Batched backfills — never one statement over the whole table
⭐ 5. ⭐ Characterisation tests green after every migration       (Day 288)
```

**⭐ The score-history change is the interesting migration**, and it is a good worked example:

```
⭐ Expand:   add the assessment_events table; write BOTH on every assessment
⭐ Backfill: create events from the current scores — ⭐ marked as reconstructed,
             ⭐ because you CANNOT recover the inputs that produced them
⭐ Migrate:  reads switch to the event table
⭐ Wait:     ⭐ keep the old column — it is your rollback path
⭐ Contract: drop it
```

**⭐ The "marked as reconstructed" detail is the honest part.** You cannot invent the inputs that
produced a historical score. **Recording that those rows are reconstructed rather than authentic is
exactly the kind of integrity a risk system needs**, and pretending otherwise would be worse than the
original bug.

## ⭐ Then fix the indexes the audit found

```
⭐ Every foreign key you filter or join on          (Day 189 — Postgres does not create these)
⭐ A partial index for any queue-shaped query        (Day 190)
⭐ The composite order from the query, not the table (Day 190's ESR-style reasoning)
```

**⭐ Re-run Day 288's `EXPLAIN` on the top five queries afterwards and record before/after buffers.**
That table is the evidence.

## ⭐ Traps

| Trap | Consequence |
|---|---|
| ⭐ Looking at the existing schema first | ⭐ you rationalise it instead of evaluating it |
| ⭐ Treating every difference as an improvement | ⭐ you introduce regressions for unfamiliarity |
| ⭐ Not recording where your derivation is worse | ⭐ you lose the best finding of the day |
| ⭐ Storing a score without its inputs and rule version | ⭐⭐ **no assessment can be explained** |
| Rules as constants in code | tuning requires a deploy |
| Recomputing historical scores on read | ⭐ the past changes when you change a parameter |
| `timestamp` for an assessment time | ambiguous at DST; unusable as evidence |
| Audit columns instead of an event log | only the latest state survives |
| ⭐ Migrating without expand/contract | downtime, or no rollback |
| ⭐ Backfilled events presented as authentic | ⭐ integrity damage worse than the original bug |
| No `lock_timeout` | Day 196's outage |

## 🎤 Defence questions

1. **⭐ Why is a risk score an event rather than a column?**
2. **⭐ Can you reproduce an assessment from six months ago?** (⭐ and could you before?)
3. **⭐ What happens to historical scores when you change a rule weight?**
4. **⭐ Which of your original schema decisions turned out to be better than your new one?**
5. **⭐ How did you change the schema without downtime?**
6. **⭐ Why did you leave some differences alone?**
7. **⭐ How do you know the migration did not break anything?**
