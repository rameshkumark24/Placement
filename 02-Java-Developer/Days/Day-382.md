# Day 382

**L-382** · IAM II — roles, STS, and the death of the access key

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ A role is a set of permissions with no credentials attached. You do not log into it — you are
> *vouched for*, and you receive keys that expire.**
>
> Today: **the two policies every role has and why they answer different questions**, the SDK credential
> chain your Java app is already using, ECS's execution-role-versus-task-role confusion, and **the
> claim that there is no longer any good reason for a long-lived access key to exist.**

---

# Part 1 — ⭐⭐ Users vs roles

| | ⭐ IAM user | ⭐⭐ IAM role |
|---|---|---|
| Credentials | ⭐⭐ **permanent access key + secret** | ⭐⭐ **none — issued on demand, expire in 15 min–12 hrs** |
| ⭐ Rotation | ⭐ manual, therefore not done | ⭐⭐ **automatic and continuous** |
| If leaked | ⭐⭐ **valid until someone notices** | ⭐ valid for minutes |
| Who can use it | whoever holds the key | ⭐ whoever the **trust policy** names |
| ⭐ Audit trail | "user X did it" | ⭐ "role X, assumed by Y, session `deploy-42`" |

```
⭐⭐ THE RULE: create IAM users only for humans who cannot use SSO, and ideally not even then.
⭐⭐ For everything else — applications, CI, other accounts, other services — use ROLES.
```

> **⭐ The last honest excuse for a long-lived key was CI, and OIDC removed it** (Day 369). **In 2026, an
> `AKIA...` in a repository, a `.env`, a Jenkins credential store or a laptop is a finding, not a
> practice.**

## ⭐⭐ The two policies on every role

```
⭐⭐ TRUST POLICY        ⭐ "WHO is allowed to become this role?"     (a resource policy on the role)
⭐⭐ PERMISSION POLICY   ⭐ "WHAT may this role do once assumed?"     (identity policies attached)
```

```json
// Trust policy — an ECS task may become this role
{ "Version": "2012-10-17", "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ecs-tasks.amazonaws.com" },
    "Action": "sts:AssumeRole",
    "Condition": { "ArnLike": {
      "aws:SourceArn": "arn:aws:ecs:eu-west-1:111122223333:*" } } }] }
```

⚠️ **These are separate questions and people conflate them constantly.** "The role has S3 access but my
task cannot use it" is almost always a **trust policy** problem, not a permissions problem. **When
debugging: `sts:AssumeRole` failures are trust; `AccessDenied` on the actual call is permissions.**

# Part 2 — ⭐ STS: how a role becomes credentials

```
⭐ 1. A principal calls  sts:AssumeRole(roleArn, sessionName)
⭐ 2. STS checks the role's TRUST POLICY
⭐ 3. ⭐ STS returns: AccessKeyId + SecretAccessKey + ⭐⭐ SessionToken + Expiration
⭐ 4. ⭐⭐ The SDK refreshes automatically before expiry — you never write this code
```

| ⭐ STS operation | ⭐ Used for |
|---|---|
| ⭐ `AssumeRole` | ⭐ cross-account, service roles, human escalation |
| ⭐⭐ `AssumeRoleWithWebIdentity` | ⭐⭐ **OIDC — GitHub Actions (Day 369), EKS IRSA, mobile apps** |
| `AssumeRoleWithSAML` | corporate IdP federation |
| ⭐ `GetSessionToken` | MFA-protected calls for a user |

| ⭐ Detail worth knowing | |
|---|---|
| ⭐⭐ **Role chaining is capped at 1 hour** | ⭐⭐ assuming a role *from* an assumed role ignores longer durations |
| ⭐ Session name appears in CloudTrail | ⭐ **put something identifying in it** — `deploy-pr-482` |
| ⭐⭐ **`ExternalId`** | ⭐⭐ for third parties — prevents the **confused deputy** |
| Session policies | further narrow a specific session |

⚠️ **The confused deputy, concretely:** you let a SaaS vendor's account assume your role. Another of
their customers asks them to do something and — if the vendor does not isolate correctly — they assume
*your* role. **`ExternalId` is a shared secret in the trust condition that only you and the vendor know,
so their other customers cannot induce it.** If a vendor does not ask you for an ExternalId, that is a
signal about the vendor.

# Part 3 — ⭐⭐ How your Java application gets credentials

```
⭐⭐ The AWS SDK for Java v2 DEFAULT credential provider chain, in order:
⭐ 1. Java system properties            aws.accessKeyId / aws.secretAccessKey
⭐ 2. Environment variables             AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY
⭐ 3. Web identity token from a file    ⭐⭐ EKS IRSA / OIDC
⭐ 4. Shared config/credentials file    ~/.aws/credentials  (profiles, SSO)
⭐ 5. ⭐ ECS container credentials       AWS_CONTAINER_CREDENTIALS_RELATIVE_URI
⭐ 6. ⭐ EC2 instance metadata (IMDS)    169.254.169.254
```

```java
// ⭐⭐ Correct: say nothing. The chain finds the right thing in every environment.
S3Client s3 = S3Client.builder().region(Region.EU_WEST_1).build();

// ⭐⭐ Wrong: hard-coded, unrotatable, and it now works ONLY where those keys exist.
S3Client bad = S3Client.builder()
    .credentialsProvider(StaticCredentialsProvider.create(
        AwsBasicCredentials.create("AKIA...", "secret")))   // ⚠️ never
    .build();
```

> **⭐⭐ The whole point of the chain is that the *same jar* runs on your laptop with SSO, in CI with
> OIDC, and in ECS with a task role — with no code change and no configuration difference.** The moment
> you pass credentials explicitly, you have coupled the artefact to an environment (Day 368's build
> once, promote many, in credential form).

## ⭐⭐ IMDSv2 — the SSRF that becomes credential theft

```
⭐ IMDSv1: a plain GET to 169.254.169.254/latest/meta-data/iam/security-credentials/<role>
⭐ ⇒ ⭐⭐ ANY server-side request forgery in your app can fetch the instance's AWS credentials.
⭐ ⇒ ⭐⭐ This is the shape of the most famous cloud breach there is.

⭐ IMDSv2: PUT a token first (X-aws-ec2-metadata-token-ttl-seconds), send it on every GET,
⭐         and ⭐⭐ the response has a hop limit of 1 so it will not traverse a proxy or container hop.
```

| ⭐ Action | |
|---|---|
| ⭐⭐ **Require IMDSv2** on every instance | `HttpTokens: required` in the launch template |
| ⭐ Set `HttpPutResponseHopLimit: 1` | ⭐ (2 if containers on EC2 need it — know why you raised it) |
| ⭐ Disable IMDS entirely where unused | ⭐ Fargate tasks do not need it |
| ⭐ Alarm on `MetadataNoToken` metric | ⭐ tells you who still uses v1 before you enforce |

# Part 4 — ⭐⭐ The ECS two-role confusion, settled

| | ⭐⭐ Execution role | ⭐⭐ Task role |
|---|---|---|
| ⭐ Used by | ⭐⭐ **the ECS agent, before your code runs** | ⭐⭐ **your application code** |
| ⭐ Needs | ⭐ pull from ECR, write to CloudWatch Logs, **read secrets for env injection** | ⭐ S3, SQS, DynamoDB — whatever the app calls |
| If missing/wrong | ⭐⭐ **the task never starts** — `CannotPullContainerError` | ⭐ the app starts, then gets `AccessDenied` |
| Managed policy | `AmazonECSTaskExecutionRolePolicy` | ⭐⭐ **hand-written, least privilege** |

> **⭐ The diagnostic shortcut: if the task never starts, look at the execution role. If the task starts
> and then fails on an API call, look at the task role.** That one sentence resolves most ECS IAM
> tickets (Day 390).

⚠️ **A subtlety worth knowing: if you inject a Secrets Manager value as an environment variable in the
task definition, the *execution* role needs the `secretsmanager:GetSecretValue` permission, not the task
role** — because the agent resolves it before your process exists. **And that injection makes it an
environment variable, which Day 372 told you not to do for secrets.**

## ⭐ The equivalents everywhere else

| Platform | ⭐ Mechanism |
|---|---|
| ⭐ EC2 | instance profile → a role attached to the instance |
| ⭐ ECS / Fargate | ⭐ task role (+ execution role) |
| ⭐⭐ EKS | ⭐⭐ **IRSA or Pod Identity** — service account ↔ role |
| ⭐ Lambda | ⭐ the execution role |
| ⭐⭐ GitHub Actions | ⭐⭐ **OIDC federation** (Day 369) |
| Human | ⭐ IAM Identity Center (SSO) → temporary session, no key |

**⭐⭐ Every row is the same idea Day 372 called workload identity: the platform signs an assertion about
which workload this is, and AWS trusts the assertion instead of a stored password.**

# Part 5 — ⭐ Humans, and the account you actually log into

| ⭐ Practice | |
|---|---|
| ⭐⭐ **Root user: MFA, then never used** | ⭐⭐ a handful of tasks genuinely need it; nothing else ever |
| ⭐⭐ **IAM Identity Center (SSO)** | ⭐⭐ humans get **temporary** credentials via `aws sso login` |
| ⭐ Break-glass role | ⭐ admin access that **alerts when assumed** — not admin access that is always on |
| ⭐ MFA condition on destructive actions | `aws:MultiFactorAuthPresent` (Day 381) |
| ⭐ Session duration short by default | 1 hour; extend deliberately |

> **⭐ The break-glass pattern is worth internalising: nobody holds standing administrator access.
> Admin exists as a role that anyone on-call can assume — and assuming it fires an alert into the team
> channel.** Access is not blocked; **it is observed.** That trade is far more sustainable than a
> permissions regime people route around.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Long-lived access keys for applications or CI** | ⭐⭐ unrotated, leaked, valid until noticed — OIDC removed the excuse |
| ⭐ Confusing trust policy with permission policy | ⭐ debugging the wrong one for an hour |
| ⭐⭐ **Hard-coding credentials in the SDK builder** | ⭐⭐ couples the artefact to one environment |
| ⭐ Not knowing the credential chain order | ⭐ a stale `~/.aws/credentials` silently wins over the role |
| ⭐⭐ **IMDSv1 left enabled** | ⭐⭐ any SSRF becomes credential theft |
| ⭐ Hop limit raised without knowing why | re-opens the container-hop path |
| ⭐⭐ **Mixing up ECS execution and task roles** | ⭐ task won't start vs task gets AccessDenied |
| ⭐ Third-party role trust with no `ExternalId` | ⭐⭐ confused deputy |
| ⭐ Expecting a chained role to last 12 hours | capped at 1 hour |
| ⭐ Generic session names | CloudTrail shows `Session1` and tells you nothing |
| Standing admin access for humans | ⭐ prefer break-glass that alerts |

## Interview questions

**Q: What is an IAM role and how does it differ from a user?**
A role is a set of permissions with no attached credentials. You assume it through STS and receive
temporary keys with an expiry, and the SDK refreshes them for you. A user has a permanent access key and
secret which nobody rotates, which is valid until somebody notices it leaked, and which offers a worse
audit trail — CloudTrail shows the role, who assumed it, and the session name. The rule I work to is
that users exist only for humans who cannot use SSO, and everything else uses roles.

**Q: How does your application on ECS get AWS credentials?**
It does nothing. The SDK's default credential provider chain walks system properties, environment
variables, a web identity token file, the shared config file, the ECS container credentials endpoint,
and finally instance metadata. On ECS it finds the task role via the container credentials URI and
refreshes automatically. The point is that the same jar runs on my laptop under SSO, in CI under OIDC
and in ECS under a task role with no code change — the moment you pass credentials explicitly you have
coupled the artefact to one environment.

**Q: Why does IMDSv2 exist?**
Because with v1 the metadata endpoint answered a plain GET, so any server-side request forgery in the
application could fetch the instance's role credentials and use them from anywhere. v2 requires a PUT to
obtain a session token first and sets a response hop limit of one, so the response will not traverse a
proxy or an extra network hop. It converts a whole class of application vulnerability from
credential theft back into an ordinary SSRF. I require it on every instance and alarm on the
`MetadataNoToken` metric before enforcing.

**Q: Explain the ECS execution role versus the task role.**
The execution role belongs to the ECS agent and is used before your code exists — pulling the image from
ECR, creating the log stream, resolving injected secrets. The task role is what your application code
uses at runtime. The diagnostic is simple: if the task never starts, it is the execution role; if the
task starts and then gets access denied on an API call, it is the task role. The catch is that
Secrets Manager injection into environment variables needs the *execution* role's permission, because
the agent resolves it before your process runs.

**Q: What is `ExternalId` for?**
It defends against the confused deputy. If you let a SaaS vendor's account assume a role in your
account, another of their customers might induce them to assume your role. ExternalId is a value in the
trust policy condition that only you and the vendor know, so a third party cannot cause that assumption
to happen. Practically, if a vendor asks you to trust their account and does not ask you for an
ExternalId, that tells you something about how they isolate customers.

## Mini task

1. ⭐ Create a role with a trust policy for `ecs-tasks.amazonaws.com` and a minimal permission policy.
   **Write both from scratch.**
2. ⭐ Break the trust policy deliberately. **Observe that the failure is `AssumeRole`, not
   `AccessDenied`** — and internalise the difference.
3. ⭐⭐ Assume a role from the CLI with `--role-session-name` set to something identifying. **Find that
   session name in CloudTrail.**
4. ⭐⭐ Write a Java program using the **default chain only**. Run it on your laptop with SSO and inside a
   container with a task role — **same jar, no changes.**
5. ⭐ Set a stale `~/.aws/credentials` and **watch it win over the role.** Understand the chain order in
   your hands, not on paper.
6. ⭐⭐ Launch an instance with **IMDSv1 allowed**, `curl` the credentials from it, then **enforce IMDSv2
   and confirm the same curl fails.**
7. ⭐ Set up **IAM Identity Center** and log in with `aws sso login`. **Delete your IAM user afterwards.**
8. ⭐⭐ Find every access key in your account with `aws iam list-access-keys` per user. **Delete or
   justify each.**
9. ⭐ Configure a **break-glass admin role** with a CloudTrail-driven alert on assumption.
10. ⭐⭐ Set up **cross-account access** to a second account with an `ExternalId`, and prove access fails
    when the ExternalId is wrong.

## 🎙️ Articulation drill

**Two minutes:** *"Where does your application's AWS credential come from?"*

**⭐ The answer should contain no credential.** The task runs with a role; the SDK's default chain finds
the container credentials endpoint; STS issues keys that expire in an hour and the SDK refreshes them.
**Nothing is stored, nothing is rotated by hand, and nothing has to change between my laptop, CI and
production.**

**⭐ Then close on the hardening, because it shows you have thought about the failure: "IMDSv2 is
required with a hop limit of one, so an SSRF in the application cannot be escalated into credential
theft — and PassRole is scoped, so nobody can attach a role they were not meant to."**
