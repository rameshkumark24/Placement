# Day 389

**L-389** · ELB and Auto Scaling — health checks, draining, and the 502 nobody can reproduce

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ If your backend's idle timeout is shorter than the load balancer's, the load balancer will reuse
> a connection the backend has just closed — and you get intermittent 502s that no test reproduces and
> no log explains.**
>
> Today: ALB versus NLB decided properly, **the health check that must not check your database**,
> deregistration delay as Day 378's `preStop` problem at the load balancer layer, and **why autoscaling
> protects you from trends and not from spikes.**

# Part 1 — ⭐⭐ ALB vs NLB

| | ⭐⭐ ALB (L7) | ⭐⭐ NLB (L4) |
|---|---|---|
| Understands | ⭐ HTTP/HTTPS, gRPC | ⭐ TCP/UDP/TLS only |
| ⭐ Routing on | ⭐⭐ **path, host, header, method, query** | ⭐ port only |
| ⭐ Latency added | ~ms | ⭐⭐ **microseconds** |
| ⭐⭐ **Source IP** | ⭐ replaced — use `X-Forwarded-For` | ⭐⭐ **preserved** (with target-type instance/ip) |
| ⭐ Static IP | ⭐ no — **it is a DNS name that changes** | ⭐⭐ **yes, one Elastic IP per AZ** |
| ⭐ Features | ⭐⭐ WAF, auth (OIDC/Cognito), redirects, fixed responses, sticky sessions | ⭐ minimal, very fast |
| ⭐ Scaling | ⭐ scales up but **needs warm-up for huge spikes** | ⭐⭐ handles millions of connections instantly |

> **⭐ Decision in one line: HTTP service ⇒ ALB. Non-HTTP protocol, a need for the client's real source
> IP at TCP level, extreme throughput, or a customer who demands a static IP to whitelist ⇒ NLB.**
> Everything else about them follows from L7 versus L4.

⚠️ **"The ALB has a static IP" is false and it breaks things.** The ALB is a DNS name whose addresses
change. **Never resolve it once and cache the IP** — that is the JVM DNS trap again (Day 387), and it is
why a customer's firewall whitelist against an ALB stops working randomly. **If they need to whitelist
an address, they need an NLB.**

| ⭐ Also worth knowing | |
|---|---|
| ⭐ **Cross-zone load balancing** | ⭐⭐ **ALB: on and free. NLB: OFF by default** — and enabling it incurs cross-AZ transfer charges |
| ⭐ NLB off ⇒ uneven load | ⭐ each zone's traffic stays in that zone; **2 targets in AZ-A and 10 in AZ-B get equal share per zone** |
| ⭐ Target types | `instance`, `ip` (**required for Fargate awsvpc**), `lambda`, `alb` (behind an NLB) |
| Idle timeout | ⭐⭐ **ALB default 60s — see Part 3** |

# Part 2 — ⭐⭐ Health checks: the fleet-wide outage waiting in a config file

```
⭐⭐ THE MISTAKE, IN ONE LINE:
⭐   the ALB health check hits /health, and /health checks the DATABASE.
⭐   ⇒ ⭐ the database has a 5-second blip
⭐   ⇒ ⭐⭐ EVERY target fails its health check SIMULTANEOUSLY
⭐   ⇒ ⭐⭐ the ALB has zero healthy targets ⇒ ⭐⭐ 503 for everything
⭐   ⇒ ⭐⭐ a degraded dependency became a TOTAL OUTAGE, and the fleet may also be restarting.
```

| ⭐ Endpoint | ⭐ What it must check |
|---|---|
| ⭐⭐ **Load balancer health check** | ⭐⭐ **"is this process alive and serving?" — NOTHING downstream** |
| ⭐⭐ **Readiness (registration)** | ⭐ "is it warmed and ready for traffic?" — pools created, caches primed |
| ⭐ Deep/dependency check | ⭐⭐ **a separate endpoint, for humans and dashboards, NEVER wired to the LB** |

> **⭐⭐ This is exactly Day 377's liveness-probe argument, at a different layer, with the same
> consequence.** The rule generalises: **any automated remediation that keys on a shared dependency
> converts a partial failure into a total one.**

| ⭐ Tuning that matters | |
|---|---|
| ⭐ `HealthyThreshold` / `UnhealthyThreshold` | ⭐ 2 and 2 is usually right — **1 is too twitchy** |
| ⭐ Interval and timeout | ⭐⭐ timeout must be **well under** interval |
| ⭐⭐ **Detection time = interval × unhealthy threshold** | ⭐⭐ 30s × 2 = **one minute of errors before removal** — tune it deliberately |
| ⭐ `HealthCheckGracePeriod` (ASG/ECS) | ⭐⭐ **a JVM needs 30–90s or the platform kills it during startup, forever** |

# Part 3 — ⭐⭐ The two connection-lifetime bugs

## ⭐⭐ Bug 1: the idle timeout race — intermittent 502s

```
⭐ ALB idle timeout        = 60s (default)
⭐ Your backend keep-alive = ⭐⭐ 60s or LESS  (Tomcat default connectionTimeout / keepAliveTimeout)

⭐ ⇒ ⭐⭐ At ~60s both decide to close. The ALB picks a pooled connection at the exact
⭐     moment the backend is closing it ⇒ ⭐⭐ 502 Bad Gateway.
⭐ ⇒ ⭐⭐ Low rate, unreproducible, no error in the application log — because the
⭐     application never saw a request.

⭐⭐ THE FIX: BACKEND IDLE TIMEOUT MUST BE STRICTLY GREATER THAN THE ALB'S.
⭐   ALB 60s ⇒ ⭐ server.tomcat.keep-alive-timeout = 65s (and maxKeepAliveRequests high/unlimited)
⭐   ⇒ ⭐⭐ the ALB always closes first, so the race cannot happen.
```

> **⭐⭐ This is the highest-value operational fact on this day.** Intermittent 502s with nothing in the
> application log is *the* signature. **`HTTPCode_ELB_5XX_Count` rising while `HTTPCode_Target_5XX_Count`
> stays flat proves the application never saw the request** — that single metric comparison is how you
> diagnose it in thirty seconds.

## ⭐⭐ Bug 2: deregistration — Day 378 at the load balancer

```
⭐ Deregistration delay (connection draining), ⭐ default 300 SECONDS:
⭐   target deregistering ⇒ ⭐ no NEW requests, ⭐ existing ones finish, ⭐ then removed

⭐⭐ THE TWO WAYS TO GET THIS WRONG:
⭐   TOO SHORT ⇒ ⭐⭐ in-flight requests killed mid-response ⇒ 502s on every deploy
⭐   TOO LONG  ⇒ ⭐ deploys crawl; 300s per batch × several batches
⭐⭐ SET IT TO: your p99 request duration + a margin. ⭐ For a normal API: 30s, not 300s.
```

| ⭐ The full graceful shutdown chain, at last complete | |
|---|---|
| 1 | ⭐⭐ **Target deregistering** — ALB stops sending new requests |
| 2 | ⭐ `preStop` / `StopTimeout` grace begins (Day 378, Day 390) |
| 3 | ⭐ Application stops accepting, finishes in-flight (Day 361) |
| 4 | ⭐ Deregistration delay elapses |
| 5 | ⭐⭐ **Container receives SIGTERM and exits cleanly — zero dropped requests** |

⚠️ **All five must line up, and the ordering constraint is the point: the load balancer must stop
sending before the process stops listening.** Every zero-downtime deployment is this sequence, and every
502-on-deploy is one step of it missing.

# Part 4 — ⭐⭐ Auto Scaling: what it can and cannot do

| Policy | ⭐ Verdict |
|---|---|
| ⭐⭐ **Target tracking** | ⭐⭐ **the default choice** — "keep this metric at X" and AWS does the maths |
| ⭐ Step scaling | ⭐ different responses at different breach sizes; more control, more tuning |
| Simple scaling | ⭐ legacy — has a cooldown that blocks further action |
| ⭐ **Scheduled** | ⭐⭐ **the most underrated** — you know Monday 9am happens |
| ⭐ Predictive | ML on historical patterns; genuinely useful for daily cycles |

## ⭐⭐ Scale on the right metric

| ⭐ Metric | ⭐ For |
|---|---|
| ⭐⭐ **`RequestCountPerTarget`** | ⭐⭐ **the best default for a web service** — directly proportional to load |
| ⭐ `TargetResponseTime` | ⭐ scale when latency degrades — closer to the SLO |
| ⭐⭐ **Queue depth / message age** | ⭐⭐ **the right metric for workers** (Day 393) |
| ⭐ CPU | ⭐⭐ **wrong for an I/O-bound JVM** — it waits on the database at 30% CPU (Day 378) |

## ⭐⭐ The latency chain nobody budgets for

```
⭐ metric publication      ⭐ 1–2 min (CloudWatch standard resolution)
⭐ alarm evaluation        ⭐ 1–3 min (evaluation periods)
⭐ instance launch + boot  ⭐ 1–3 min   (⭐ Fargate task: ~30–60s)
⭐ ⭐⭐ JVM start + warm-up  ⭐⭐ 30–120s (⭐ JIT — it is SLOW before it is fast)
⭐ health check passes     ⭐ ~30s
⭐ ────────────────────────────────────
⭐ ⭐⭐ TOTAL: 4–10 MINUTES from load arriving to capacity serving.
```

> **⭐⭐ Therefore: autoscaling protects you from a TREND, not from a SPIKE.** A flash sale, a marketing
> email or a viral post arrives in seconds and your capacity arrives in minutes. **The answers for
> spikes are different ones: scheduled scaling ahead of known events, headroom, a queue to absorb the
> burst (Day 393), and load shedding to protect what capacity you have (Day 340).**

⚠️ **Two more autoscaling details worth carrying:** set `HealthCheckType` to `ELB` rather than `EC2` so
an instance that boots but fails to serve is replaced; and use **instance warm-up / `default_cooldown`**
so the group does not launch a second wave while the first is still starting — **the classic
oscillation where you scale to 40 instances and back to 4 in ten minutes.**

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐ Whitelisting an ALB's IP address | ⭐⭐ it is a DNS name; the address changes |
| ⭐ NLB with cross-zone off, uneven targets | ⭐ per-zone equal share ⇒ badly skewed load |
| ⭐⭐ **Health check that touches the database** | ⭐⭐ a dependency blip becomes a total outage |
| ⭐ No health check grace period | ⭐⭐ the JVM is killed during startup, in a loop |
| ⭐ Thresholds of 1 | flapping on a single dropped packet |
| ⭐⭐ **Backend idle timeout ≤ ALB idle timeout** | ⭐⭐ intermittent 502s with nothing in the app log |
| ⭐ Not comparing ELB 5xx to Target 5xx | ⭐ the 30-second diagnosis, unused |
| ⭐⭐ **Deregistration delay left at 300s** | ⭐ deploys crawl |
| ⭐⭐ Deregistration delay too short | ⭐⭐ in-flight requests killed |
| ⭐⭐ **Scaling an I/O-bound JVM on CPU** | ⭐⭐ it never triggers, or triggers on GC |
| ⭐⭐ **Expecting autoscaling to absorb a spike** | ⭐⭐ 4–10 minutes; the spike is over or you are |
| ⭐ `HealthCheckType: EC2` | ⭐ a booted but broken instance stays in service |
| No warm-up ⇒ oscillation | scale to 40 and back to 4 |
| Sticky sessions to avoid fixing state | ⭐ Day 324 — uneven load and no real fix |

## Interview questions

**Q: ALB or NLB?**
ALB for HTTP services, because you get routing on path, host and header, WAF, TLS termination, redirects
and authentication — everything that requires understanding the request. NLB for non-HTTP protocols,
extreme throughput, when you need the client's real source IP at the TCP layer, or when a customer needs
a static IP to whitelist, since an ALB is a DNS name whose addresses change. That last point matters:
people whitelist a resolved ALB address and it silently stops working weeks later.

**Q: What should the load balancer health check check?**
Only that this process is alive and able to serve. Never a downstream dependency. If the health check
queries the database, a five-second database blip fails every target simultaneously, the load balancer
finds zero healthy targets, and a degraded dependency becomes a complete outage. It is the same argument
as a Kubernetes liveness probe that checks the database, and the general rule is that any automated
remediation keyed on a shared dependency converts a partial failure into a total one. A deep dependency
check is fine as a separate endpoint for dashboards, just never wired to the load balancer.

**Q: You are seeing intermittent 502s that nobody can reproduce and nothing appears in the application
log. What is your first hypothesis?**
An idle timeout race. The ALB keeps connections alive for sixty seconds by default; if the backend's
keep-alive timeout is the same or shorter, both sides decide to close around the same moment and the
ALB occasionally sends a request down a connection the backend is closing. The application never sees
the request, which is why the log is empty. The diagnosis takes thirty seconds — compare
`HTTPCode_ELB_5XX_Count` against `HTTPCode_Target_5XX_Count`; if the first is rising and the second is
flat, the request never arrived. The fix is making the backend's idle timeout strictly longer than the
load balancer's so the ALB always closes first.

**Q: How do you deploy without dropping requests?**
Five things have to line up in order. The target is deregistered so the load balancer stops sending new
requests; a pre-stop grace period covers the propagation delay; the application stops accepting and
finishes in-flight work; the deregistration delay is set to roughly p99 request duration plus margin
rather than the five-minute default; and only then does the container get SIGTERM and exit. The
ordering constraint is the whole thing — the load balancer must stop sending before the process stops
listening. Every 502-on-deploy is one of those five missing.

**Q: Can autoscaling handle a traffic spike?**
No, and being clear about that is important. Add up the chain: metric publication one to two minutes,
alarm evaluation one to three, instance launch and boot one to three, JVM start and JIT warm-up another
thirty seconds to two minutes, then health checks. That is four to ten minutes before new capacity
serves a request. Autoscaling handles trends. Spikes need different tools — scheduled scaling ahead of
known events, deliberate headroom, a queue to absorb the burst, and load shedding to protect the
capacity you do have. Also, scale on request count per target rather than CPU, because an I/O-bound JVM
sits at thirty percent CPU while its latency triples.

   change.**

    degrades.

## 🎙️ Articulation drill

**Two minutes:** *"We get 502s a few times an hour and cannot reproduce them."*

**⭐ Ask one question first, because it splits the problem in half: is `HTTPCode_ELB_5XX_Count` rising
while `HTTPCode_Target_5XX_Count` is flat? If so the application never received the request, and the
cause is connection-level rather than code.**

**⭐ Then name the two candidates: an idle timeout race, where the backend's keep-alive is not strictly
longer than the ALB's sixty seconds, so the ALB reuses a connection the backend is closing — and
deregistration, where targets leave the pool before the load balancer stops sending. Both are
configuration inequalities rather than bugs, which is exactly why nobody finds them by reading code.**
