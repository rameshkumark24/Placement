# Day 391

**L-391** · Lambda — the execution model, cold starts, and when serverless is wrong

**Time:** 3 hrs · **Mode:** NEW

> **⭐⭐ Lambda concurrency is not threads. One environment serves exactly one request at a time — so a
> hundred concurrent requests means a hundred JVMs, each with its own heap, its own JIT and its own
> connection.**
>
> Today: the execution model that explains every Lambda surprise, **why Java is the worst-case language
> for cold starts and what SnapStart actually does about it**, the retry behaviour that makes
> idempotency mandatory, and **the cost crossover where a small container is simply cheaper.**

---

# Part 1 — ⭐⭐ The execution model

```
⭐⭐ COLD START                              ⭐⭐ WARM INVOKE
⭐ 1. download code / image                 ⭐ 1. run handler
⭐ 2. start the runtime (⭐⭐ JVM boot)       ⭐ ⇒ ⭐⭐ that is all.
⭐ 3. ⭐⭐ INIT phase — static blocks,
⭐    constructor, Spring context
⭐ 4. run handler
```

| ⭐⭐ The three facts that explain everything | |
|---|---|
| ⭐⭐ **One environment = one concurrent request** | ⭐⭐ **concurrency is horizontal, never threaded** |
| ⭐⭐ **The environment is REUSED between invocations** | ⭐⭐ **static state survives — a feature and a bug** |
| ⭐⭐ **INIT runs once per environment, not per request** | ⭐⭐ **put expensive setup there — it is also billed differently** |

```java
public class Handler implements RequestHandler<S3Event, String> {

    // ⭐⭐ INIT phase — runs ONCE per environment. Clients, pools, config go here.
    private static final S3Client S3 = S3Client.create();
    private static final ObjectMapper MAPPER = new ObjectMapper();

    // ⚠️⚠️ AND THE BUG: this is SHARED across every invocation in this environment.
    private static final List<String> SEEN = new ArrayList<>();   // ⭐⭐ leaks, and races

    public String handleRequest(S3Event event, Context ctx) { ... }
}
```

> **⭐⭐ "It works locally and produces impossible data in production" is almost always static state
> reused across invocations.** The environment persists for minutes; **anything mutable and static is
> shared by every request that lands there.** Reuse clients and pools deliberately; **never accumulate
> request state statically.**

| ⭐ Concurrency controls | |
|---|---|
| ⭐ Account limit | ⭐ 1,000 concurrent by default (raisable) — **shared across all functions** |
| ⭐⭐ **Reserved concurrency** | ⭐⭐ guarantees capacity for a function **and caps it** — the way to stop one function starving the others |
| ⭐⭐ **Provisioned concurrency** | ⭐⭐ **pre-initialised environments — no cold start, billed continuously** |
| Throttling | over the limit ⇒ `TooManyRequestsException` (429), retried for async sources |

# Part 2 — ⭐⭐ Cold starts, and why Java is the hard case

| Runtime | ⭐ Typical cold start |
|---|---|
| ⭐ Python / Node | ⭐ 100–300 ms |
| ⭐ Go / Rust | ⭐ 20–100 ms |
| ⭐ Java, plain handler | ⭐ 400 ms – 1 s |
| ⭐⭐ **Java + Spring Boot** | ⭐⭐ **3–10 SECONDS** |

```
⭐⭐ WHY JAVA IS WORST-CASE HERE:
⭐   ⭐ JVM startup itself
⭐   ⭐⭐ CLASS LOADING — thousands of classes, and Spring's classpath scan
⭐   ⭐⭐ JIT NEVER WARMS UP — a short-lived environment runs interpreted or C1 forever.
⭐      ⭐⭐ Everything that makes the JVM fast at minute five is useless at second one.
⭐   ⭐ Reflection and proxy generation at context startup
```

| ⭐ Mitigation | ⭐ What it really costs |
|---|---|
| ⭐⭐ **SnapStart** | ⭐⭐ **snapshot after INIT, restore on invoke — 10× improvement, and free** |
| ⭐ Provisioned concurrency | ⭐⭐ **you are now paying for idle capacity — i.e. servers** |
| ⭐ Avoid Spring; plain handler + manual wiring | ⭐ real, and unpopular |
| ⭐⭐ **GraalVM native image** | ⭐ ~50 ms starts; **long builds, reflection configuration, real friction** |
| ⭐ More memory | ⭐⭐ memory also scales **CPU** — often faster *and* cheaper (Part 4) |
| Tiered compilation stop-at-1 | small win, easy |

## ⭐⭐ SnapStart, and the state it breaks

```
⭐ SnapStart: run INIT, ⭐⭐ take a Firecracker microVM SNAPSHOT, then restore it per invoke.
⭐ ⇒ ⭐⭐ Spring Boot cold start ~6s → ~600ms. ⭐ No extra charge.

⭐⭐ BUT THE SNAPSHOT FREEZES STATE, and these break:
⭐   ⭐⭐ open connections (DB, HTTP) — restored dead
⭐   ⭐⭐ SecureRandom seeds — ⭐⭐ EVERY RESTORED ENVIRONMENT GETS THE SAME SEED
⭐   ⭐ cached credentials with an expiry
⭐   ⭐ anything time-based captured at INIT
⭐ ⇒ ⭐ FIX: ⭐⭐ CRaC hooks — beforeCheckpoint() / afterRestore() — reseed and reconnect.
```

⚠️ **The `SecureRandom` one deserves its own alarm.** If you generate tokens, session IDs or nonces from
a seed captured before the snapshot, **every restored environment produces the same sequence.** That is a
security bug produced entirely by a performance feature, **and it is exactly the kind of detail that
makes an interview answer memorable.**

# Part 3 — ⭐⭐ Retries, idempotency and event sources

| Invocation type | ⭐ Retry behaviour |
|---|---|
| ⭐ **Synchronous** (API Gateway, ALB) | ⭐ no retry by Lambda — **the caller decides** |
| ⭐⭐ **Asynchronous** (S3, SNS, EventBridge) | ⭐⭐ **retried twice automatically**, then DLQ / on-failure destination |
| ⭐⭐ **Poll-based** (SQS, Kinesis, DynamoDB Streams) | ⭐⭐ **retried until success or the queue's `maxReceiveCount`** |

```
⭐⭐ THEREFORE: ⭐⭐ EVERY asynchronously invoked Lambda MUST BE IDEMPOTENT.
⭐ Not "should be". ⭐⭐ Retries are automatic, invisible, and not optional.
⭐ ⇒ Day 335's ten-line consumer, unchanged: dedup key insert + the business change,
⭐   ⭐⭐ in ONE transaction. Conflict on insert ⇒ already processed ⇒ ack and return.
```

| ⭐ Event source detail worth knowing | |
|---|---|
| ⭐⭐ **SQS + Lambda partial batch failure** | ⭐⭐ report `batchItemFailures` — **otherwise ONE bad message replays the WHOLE batch** |
| ⭐ Kinesis/DynamoDB Streams | ⭐⭐ **ordered per shard, and a poison pill BLOCKS the shard** — set `bisectBatchOnFunctionError` and a retry limit |
| ⭐ Function timeout vs SQS visibility timeout | ⭐⭐ **visibility timeout ≥ 6× function timeout** (AWS's own rule) |
| Max function duration | ⭐ 15 minutes — a hard ceiling |

# Part 4 — ⭐⭐ Cost, and the crossover point

```
⭐ Lambda billing = ⭐ requests ($0.20 per million) + ⭐⭐ GB-SECONDS ($0.0000166667)
⭐ ⭐⭐ Memory setting also sets CPU — 1,769 MB ≈ 1 full vCPU.

⭐⭐ THE COUNTER-INTUITIVE OPTIMISATION:
⭐   128 MB, runs 8s  = 1.00 GB-s
⭐   ⭐⭐ 1024 MB, runs 0.8s = ⭐⭐ 0.80 GB-s  ⇒ ⭐⭐ MORE MEMORY IS FASTER *AND* CHEAPER.
⭐   ⇒ ⭐ Use AWS Lambda Power Tuning. ⭐⭐ Never leave a Java function at 512 MB by default.
```

```
⭐⭐ THE CROSSOVER, with real numbers:
⭐   100 ms function @ 512 MB, ⭐ 10 REQUESTS/SECOND, all month
⭐   = 26M requests + ~1.3M GB-s ≈ ⭐ $27/month  ⇒ ⭐⭐ Lambda wins easily
⭐
⭐   Same function at ⭐ 500 REQUESTS/SECOND
⭐   ≈ 1.3B requests + 65M GB-s ≈ ⭐⭐ $1,350/month
⭐   ⭐⭐ vs two t4g.medium behind an ALB ≈ ⭐⭐ $70/month.
⭐ ⇒ ⭐⭐ SUSTAINED HIGH THROUGHPUT IS WHERE SERVERLESS INVERTS. Know roughly where your line is.
```

> **⭐⭐ The honest verdict, which is what an interviewer is actually testing:** Lambda is excellent for
> **event-driven glue** (S3 triggers, cron, stream processing), **spiky or low-volume APIs**, and
> **anything where the alternative is a server idling at 2%.** It is a poor fit for **a sustained-
> throughput Java web service**, where it is slower *and* more expensive than a container — **and being
> willing to say that is worth more than enthusiasm for it.**

| ⭐ Other real constraints | |
|---|---|
| ⭐ 15-minute maximum | ⭐ long jobs need Batch, Fargate or Step Functions |
| ⭐⭐ **No connection pooling that works** | ⭐⭐ **one connection per environment × N environments floods RDS** ⇒ RDS Proxy (Day 387) |
| ⭐ 10 GB `/tmp`, 10 GB image | fine for most |
| ⭐ VPC-attached Lambda | ⭐⭐ **Hyperplane ENIs fixed this — the old "10-second VPC cold start" advice is obsolete** |
| ⭐ Local testing | ⭐ harder; SAM helps; **integration tests matter more** |

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| ⭐⭐ **Thinking concurrency is threads** | ⭐⭐ 100 concurrent = 100 JVMs, 100 connections |
| ⭐⭐ **Mutable static state** | ⭐⭐ shared across invocations — leaks and impossible data |
| ⭐ Creating clients inside the handler | ⭐ pays initialisation on every request |
| ⭐ No reserved concurrency | ⭐ one function starves every other |
| ⭐⭐ **Spring Boot on Lambda without SnapStart** | ⭐⭐ 3–10 second cold starts |
| ⭐⭐ **SnapStart without CRaC hooks** | ⭐⭐ dead connections, and **identical `SecureRandom` seeds** |
| ⭐ Provisioned concurrency as the default fix | ⭐ you are paying for idle servers — that was the thing you left |
| ⭐⭐ **Assuming a Lambda runs once** | ⭐⭐ async invocations retry twice, automatically |
| ⭐ No partial batch failure reporting | ⭐⭐ one bad message replays the whole batch |
| ⭐ Visibility timeout under 6× function timeout | duplicate concurrent processing |
| ⭐⭐ **Leaving memory at the default** | ⭐⭐ often slower *and* more expensive |
| ⭐ Traditional connection pooling | floods RDS — use RDS Proxy |
| ⭐⭐ **Lambda for sustained high-throughput APIs** | ⭐⭐ the cost inverts, badly |
| Repeating obsolete VPC cold-start advice | Hyperplane fixed it years ago |

## Interview questions

**Q: How does Lambda concurrency work?**
Each execution environment handles exactly one request at a time, so concurrency scales horizontally by
creating more environments, not by threading inside one. A hundred concurrent requests means a hundred
JVMs, each with its own heap and its own database connection — which is why traditional connection
pooling is an anti-pattern there and RDS Proxy exists. Environments are reused between invocations, so
initialisation code runs once per environment rather than per request, and anything mutable and static is
shared by every request that lands on it.

**Q: Why is Java bad for Lambda cold starts, and what do you do?**
Three compounding reasons: JVM startup, class loading — which Spring's classpath scanning multiplies —
and the fact that JIT never warms up, so the very thing that makes the JVM fast at minute five is
useless at second one. A plain handler is several hundred milliseconds; Spring Boot is three to ten
seconds. SnapStart is the right first answer: it snapshots the microVM after initialisation and restores
it per invoke, giving roughly a tenfold improvement at no extra charge. The catch is that a snapshot
freezes state, so connections come back dead and — the important one — every restored environment
inherits the same `SecureRandom` seed, so anything generating tokens must reseed in an `afterRestore`
hook.

**Q: Does a Lambda run exactly once?**
No, and designing as if it does is a real bug. Asynchronous invocations from S3, SNS or EventBridge are
retried twice automatically before going to a dead letter queue, and poll-based sources retry until
success or the queue's receive limit. So every asynchronously invoked function must be idempotent — a
dedup key insert plus the business change in one transaction, where a conflict on insert means it was
already processed. With SQS specifically you also need to report partial batch failures, otherwise one
bad message causes the entire batch to be replayed.

**Q: How do you tune a Lambda's cost?**
Counter-intuitively, usually by giving it more memory. Memory and CPU are the same dial, so a function at
128 megabytes taking eight seconds costs one gigabyte-second, while the same function at a gigabyte
taking eight hundred milliseconds costs 0.8 — faster and cheaper simultaneously. Power Tuning finds the
sweet spot empirically. A Java function left at the default is almost always on the wrong side of that
curve.

**Q: When is Lambda the wrong choice?**
Sustained high throughput. At ten requests per second a hundred-millisecond function costs tens of
dollars a month and is obviously right. At five hundred requests per second the same function is over a
thousand dollars a month, against maybe seventy for two small instances behind a load balancer — because
you are paying per request for capacity you could rent continuously. It is also wrong above fifteen
minutes of work, and wrong where cold start latency is user-visible and SnapStart is not enough. Lambda
is excellent for event-driven glue, cron, stream processing and spiky low-volume APIs, and I would say
so rather than defend it everywhere.

## 🎙️ Articulation drill

**Two minutes:** *"Should we build this on Lambda?"*

**⭐ Answer with a boundary rather than a preference.** Lambda is excellent where the work is
event-driven, spiky or low-volume — S3 triggers, cron, stream processing, anything whose alternative is
a server idling at two percent. **It inverts on sustained throughput: per-request pricing beats renting
a machine right up until you would have kept the machine busy anyway.**

**⭐ Then show the Java-specific depth: cold starts are the real constraint because JIT never warms up in
a short-lived environment, SnapStart fixes most of it for free by snapshotting after init — and its
catch is that restored environments inherit frozen state, including the same `SecureRandom` seed, so
anything issuing tokens has to reseed in an afterRestore hook.**
